# [Model Loader] Bound fastsafetensors peak memory with the 0.4 fit planner

[Upstream PR](https://github.com/vllm-project/vllm/pull/55985) · state: open · merged: False

## Original PR description

## Purpose

`--load-format fastsafetensors` stages a whole shard per rank in device memory
before distributing it, so peak load memory tracks the checkpoint's shard layout
rather than the memory actually available. Where a shard is large relative to
free memory, the load runs out of memory on a model that otherwise fits.

fastsafetensors 0.4 provides a fit planner for exactly this: whole-file loads
while headroom is ample, per-file chunk budgets declining as the device fills.
Its budget is caller-supplied by design (`parallel_loader.py`, 0.4.0):

> **The caller picks the number — it knows what else lives on the device and,
> under broadcast loading, must pass the same value on every rank (e.g.
> all-reduce(MIN) of each rank's free memory)** so the plan stays identical
> across ranks.

This PR computes that budget from free device memory, agrees it across ranks
with all-reduce MIN, and passes it — with `use_chunk_budget_as_allocation_size`
for how chunks are sized, `accumulate_resident` for whether the consumer's
memory grows during the load, and `BudgetInfeasibleError` handled for a plan
that cannot be satisfied. It raises the dependency floor from
`fastsafetensors >= 0.3.3` to `>= 0.4`, which is where the planner lands.

## meta-models/Muse-Glimmer-30B

Public checkpoint, 55.5 GiB in 2 shards: largest shard 46.52 GiB, largest tensor
2.505 GiB. Single 96 GB card, weight-load time from vLLM's own log line:

| loader | weight load |
| --- | ---: |
| default (`auto`) | 52.74 s |
| `fastsafetensors`, main + 0.4.0 | **OOM** — `Tried to allocate 46.52 GiB`, 38.31 GiB free |
| `fastsafetensors`, this PR | **10.16 s** |

The planner needs twice the largest tensor, 5.01 GiB. Reported independently by
the fastsafetensors maintainer on a single 80 GB A100/H100
(foundation-model-stack/fastsafetensors#71).

## What this changes

- **Device memory budget**, derived from free device memory and reduced with
  all-reduce MIN so every rank plans identically. Shards larger than the budget
  load in sub-shard chunks, each capped at `2 x` the largest tensor the load
  keeps: a chunk must hold that tensor, the second copy lets the producer read
  ahead, and beyond it the cap stops binding (measured: `T` +7.4% load time,
  `2T` +2.4%, `4T` identical to uncapped). The budget carries the reason when
  it is absent -- asked for, residency not modellable, free memory unreadable,
  or no memory to reserve from -- so an unplanned load can be explained.
  Planned loads select buffered reads up front, since the 0.4 GDS copier cannot
  chunk; `VLLM_FASTSAFETENSORS_DEVICE_MEMORY_BUDGET=0` selects GDS instead.
- **`accumulate_resident=False`.** Every quant method reachable from this loader
  creates its parameters at model-init time, so the load only copies into memory
  already allocated — measured on the default path, free device memory is
  unchanged across `load_weights()`. Online quantization is the exception: it
  materializes a smaller quantized parameter than the bytes it reads, which the
  plan would over-charge, so those loads are left unplanned unless a budget is
  set explicitly.
- **The budget all-reduce is unconditional**, with `0` meaning unbounded. A rank
  returning early — no reading, too little free memory, an unplannable consumer —
  would leave the others blocked in the reduce while it went on to the loader's
  broadcast sequence.
- **An infeasible plan raises**, naming the shortfall, rather than falling back
  to whole-shard staging — which needs a buffer at least as large as the tensor
  the plan could not place, so it is more likely to run out of memory, not less.
- **`VLLM_FASTSAFETENSORS_ALL_LOCAL`** (opt-in, off by default). Every rank reads
  the whole checkpoint from storage instead of one rank reading and
  broadcasting. Enable it when ranks read from storage they do not share: on
  2x GB10 over RoCE, each node reading its own NVMe copy loads
  Qwen3.5-122B-A10B-FP8 in 16.6 s against 21.8 s broadcasting (n=2 per arm,
  non-overlapping). On a single node whose ranks share one NVMe it is a loss
  (43.2 s against 29.6 s), because the extra reads land on the contended device
  and the broadcast being avoided is cheap.
- **`VLLM_FASTSAFETENSORS_DEVICE_MEMORY_BUDGET`** overrides the derived budget;
  `0` removes the bound and stages whole shards. An escape hatch for a plan you
  believe is wrong, not a remedy for insufficient memory — and not the only
  route to an unbounded load, since one also runs unbounded when no budget can
  be derived.

Docs: `LoadConfig.load_format` now lists `"fastsafetensors"`, and the extension
page gains `VLLM_FASTSAFETENSORS_QUEUE_SIZE`, the TP>1 GDS behavior, when
`ALL_LOCAL` pays, the online-quant exemption, and the `2 x largest tensor`
planning floor that decides whether a checkpoint is loadable by this format.

## Found deploying it at TP4 + DCP2 on 4x GB10 (DeepSeek-V4.1-Flash, 475 GiB)

- **Budget agreed on gloo, not CUDA over `WORLD`.** vLLM computes on the
  TP/DCP/EP subgroups, so `WORLD` often has no NCCL communicator at load time
  and the 8-byte budget `all_reduce` created one. NCCL's proxy connect pins
  ~9.19 MiB of host memory per connection for the communicator's lifetime,
  invisible to `torch.cuda.host_memory_stats()`. Reducing on
  `get_world_group().cpu_group` issues no NCCL collective during the load, as
  `--load-format auto` issues none. Host `Shmem` after load:

  | | Shmem after load | MemAvailable after release | boot |
  | --- | ---: | ---: | --- |
  | `--load-format auto` | 8.21 GiB (+0.00) | 31.08 GiB | healthy |
  | fastsafetensors, CUDA reduce | 12.06 GiB (**+3.85**) | 27.60 GiB | dies in FlashInfer autotune |
  | fastsafetensors, gloo reduce | 8.35 GiB (**+0.13**) | 30.12 GiB | healthy |

  Wasteful on a discrete GPU; on unified memory it comes out of the pool that
  KV cache and graph capture need.
- **EP filter honoured.** `default_loader` did not pass `local_expert_ids` to
  `fastsafetensors_weights_iterator`, so under expert parallelism this format
  read every expert while `auto` skips the ones the rank does not own (experts
  are ~85-90% of weight bytes). Now both formats select the same tensors. A
  `tensor_filter` is incompatible with broadcast, so a filtered load reads
  all-local. Verified on Qwen3-Coder-Next-FP8 (512 experts) at TP2 +
  `--enable-expert-parallel --enable-ep-weight-filter`: `loading 256/512
  experts` on both ranks, and generations byte-identical to `auto`.
- **Chunk cap sized from kept tensors.** `_safetensors_largest_tensor` takes the
  loader's predicate, so a tensor that is never read cannot set the cap. With
  DeepSeek-V4.1-Flash's on-disk Engram tables it was 183 GiB instead of
  2.47 GiB, and the cap bounded nothing.

With all three the model boots and serves (count-to-100 exact, 30/30
structured-output gate, 7/7 vision + tool calling, KV pool unchanged), loading
in 54-63 s per rank against 133-177 s for `auto` on the same local shards.

## Validation

Three tests added to `tests/model_executor/model_loader/fastsafetensors_loader/`:

- `test_fastsafetensors_sub_shard_chunking` — a 384 MiB budget forces GPT-2's
  522 MiB shard to load as four chunks, which must still match
  `safetensors_weights_iterator` bitwise.
- `test_fastsafetensors_budget_infeasible` — a 1 MiB budget must raise
  `BudgetInfeasibleError` naming the shortfall, covering the no-fallback policy.
- `test_fastsafetensors_accumulate_resident_skips_derived_budget` — the same
  budget that raises above must load when the consumer's residency cannot be
  modelled, covering the online-quant exemption.

All run single-rank. At TP=2 on a checkpoint that already fits
(DeepSeek-V4-Flash, 3.4 GiB shards) load time is unchanged: 29.26 / 29.62 /
29.68 s against 28.62 / 30.00 s for stock.

Rebased on `19b0efce3`. On GB10 at `47232f3c7` (torch 2.14.0) with fastsafetensors
0.4.0, the `fastsafetensors_loader/` suite goes from 3 passed (base) to 6 passed. Upstream
#60152 now filters the shard list before this iterator; the planner sees
the filtered list, identically on every rank.

Lockfiles (`requirements/test/{cpu,cuda,rocm}.txt`) regenerated against
fastsafetensors 0.4.0 — one line per file, no other dependency changes.

## Model evaluation

This changes how weight bytes reach the device, not what they are; the chunking
path asserts bitwise equality against the reference safetensors iterator.

Generation across loaders at TP=2 with expert parallelism on DeepSeek-V4-Flash
was correct and coherent in every configuration. Token-level identity is not
asserted — that configuration is not reproducible run-to-run even at
`temperature=0` with a fixed seed.

**`use_chunk_budget_as_allocation_size` is dropped.** It allocated every chunk at the planner's budget rather than its span, so staging tracked available memory instead of the checkpoint: at a derived budget on DeepSeek-V4-Flash it reserved 24.0 GiB to move 6.8 GiB of tensors. Taking the cap; declining the power-of-two rounding. Both in 6de72dda8, now `2 x largest_tensor`.

DeepSeek-V4-Flash has `largest_tensor = 0.9863 GiB`, so `pow2(T) = 1.0 GiB` — 1.4% headroom, about the worst case the rounding produces. Warm cache, n >= 2:

| cap | load time | allocated |
| --- | ---: | ---: |
| `T` (pow2 here) | 35.9 s | 2.05 GiB |
| `2T` | 34.3 s | 3.47 GiB |
| uncapped | 33.5 s | 6.77 GiB |

`2T` costs +2.4%, the pow2 cliff +7.4%. `4T` is byte-identical to uncapped, because it exceeds the largest shard and the cap stops binding — so `2T` sits mid-slope rather than on a plateau.

It's a trade rather than a dismissal: pow2 does allocate less. In our regime, buying ~1.4 GiB we have no use for at 4.9% of load time is the wrong side of it; on a device where that GiB mattered your rounding would be the better choice. The cliff is why I'd rather not have the multiple depend on where `T` falls relative to a power of two — clean hidden dimensions and stacked MoE experts land on them routinely.

One thing worth noting since it isn't visible from the diff: the cap that was there before this change (largest *shard*) never bound where the planner was already chunking, so it was a no-op on exactly the checkpoints it was meant for.
