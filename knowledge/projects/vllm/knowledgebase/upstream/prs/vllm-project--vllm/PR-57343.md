# [Perf][KV Offload] Select the canonical load path by fragment size

[Upstream PR](https://github.com/vllm-project/vllm/pull/57343) · state: open · merged: False

## Original PR description

## Purpose

Fixes #57342. Choose the CPU→GPU load path from the copy sizes actually submitted, not the page size.

### User case

1. `canonical_layout=True` with a mapping that has more than one run per page
   (e.g. split K/V view, 8 KV heads × 128, bf16, block_size 16, TP=2).
2. The page is 32 KiB, so `_select_swap_blocks_fn` picks `cuMemcpyBatchAsync`.
3. But `_fill_canonical_ops` submits one copy per fragment: 2 × 16 KiB,
   exactly the small-copy regime #42212 moved to Triton.
4. Canonical loads are 2.4–3.8x slower than direct, and the batch call blocks
   the model runner thread for the whole copy (~826 ms for a 32K-token hit).

The fix passes the fragment sizes to the selector and applies the existing
28 KiB threshold and 8-byte alignment check to them.

Unchanged: the direct layout, the default CUDA path (packed K‖V under LBHNC is
one run per page), stores (always DMA), and the Triton chunk size (still
page-derived).

Not a duplicate: no open PR touches the selector. Neighbours are #48936, #53971,
#53544. The threshold itself being device-dependent is tracked separately in
#57555.

Load time, A30, 32 KiB page as 2 × 16 KiB, 80 layers, median of 7, byte-exact:

| prefix | direct | canonical before | canonical after |
|---:|---:|---:|---:|
| 1K | 10.7 ms | 26.0 ms | 6.7 ms |
| 32K | 216 ms | 826 ms | 212 ms |

No model eval: the change only picks between two byte-exact copy primitives.

<details>
<summary>Measurement details and chunk-size choice</summary>

- Standalone harness: verbatim `_swap_blocks_kernel`, single `cuMemcpyBatchAsync`
  call as in `swap_blocks_batch`. Driver 535 with CUDA 12.8 forward-compat
  libcuda. Full table (incl. 4K) and environment are in #57342.
- Sizing the Triton chunk to the fragment was slower for 512 B fragments
  (408 ms vs 356 ms, 32K tokens) and within 2–4% for 1–2 KiB, so it stays
  page-derived.

</details>

every changed line and ran the tests and measurements on my own hardware.

One concern is that this change still relies on a single empirically tuned `THRESHOLD_BYTES`, while the DMA/Triton crossover likely depends on both payload size and descriptor count. `_select_swap_blocks_fn` runs at handler initialization and does not know the actual batch size N; the Triton wrapper only falls back to DMA for very small N.

In a local H100 sweep, for example, DMA was faster for 28 KiB descriptors at N=64, while Triton was faster at N=256. Similarly, the crossover for 8 KiB descriptors moved between N=16 and N=64.

Could we add a small size × descriptor-count benchmark, or document why a single 28 KiB cutoff is expected to generalize across workloads and devices? If runtime autotuning is out of scope for this PR, this seems like a good follow-up for a per-device/per-N dispatch policy. The fragment-size fix itself still makes sense.
