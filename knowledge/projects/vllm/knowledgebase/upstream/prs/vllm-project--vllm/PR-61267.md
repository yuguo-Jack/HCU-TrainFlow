# [Bugfix][LoRA] respect `attention_k_eq_v=True` QKK LoRA layers

[Upstream PR](https://github.com/vllm-project/vllm/pull/61267) · state: closed · merged: True

## Original PR description



## Overview



Fix LoRA weight loading on `attention_k_eq_v` full-attention layers (e.g. `google/gemma-4-31b-it`), where the V slice of the packed `qkv_proj` received no LoRA delta even though HF applies the `k_proj` LoRA to V.

## Claims



- On `attention_k_eq_v` full-attention layers, the `k_proj` LoRA is now packed into both the K and V slices of `qkv_proj`. This matches HF, where `value_states = key_states` (pre-`k_norm`), so a PEFT `k_proj` adapter also changes V.
- Adds an optional per-module `lora_packed_modules` override that `LoRAModelManager._register_packed_modules` checks before the class-level `packed_modules_mapping`.

## Details



On `attention_k_eq_v` checkpoints, full-attention layers have no `v_proj`. For base weights, `_gemma4_layer_weights_mapper` loads `k_proj` into both the K and V shards of `qkv_proj`. LoRA packing has no equivalent: it used the class-level `packed_modules_mapping` (`q_proj, k_proj, v_proj`) for every layer. The adapter has no `v_proj` for these layers, so the V slice was packed as `None` and V lost the `k_proj` LoRA delta.

- joanvelja · comment · 2026-10-28T12:07:17Z · [source](https://github.com/vllm-project/vllm/pull/61267#issuecomment-6468556577)

+1 on this fix, and on its semantics over #62034's. Packing the `k_proj` LoRA into both the K and V slices keeps the base parameter as `qkv_proj` and adapters PEFT-canonical. A `qkk_proj` rename changes the base module's name for every consumer.

Our Gemma-4 26B-A4B and 31B RL runs have the same bug, on vLLM 0.28 and 0.32.0. The trainer's V moves with the `k_proj` LoRA, but the served V doesn't, so on the k_eq_v layers the sampling policy silently differs from the trained one. We carry a fix as a downstream patch, and two parts of it might be useful here:

1. **Derive the packing from the model's own stacked mapper**, instead of a per-module `lora_packed_modules` override. `_gemma4_layer_weights_mapper` already declares that `k_proj` fills shards `["k", "v"]` of `qkv_proj`. Our patch asks the mapper which shards each packed sub-module's weight fills, using the same `mapper.apply` call the loader makes, and packs the sub-module into each of those slots. LoRA packing then follows base loading by construction:
   - it covers `Gemma4ForCausalLM` and the multimodal `language_model.model` nesting without per-class wiring;
   - it covers any future one-to-many mapping (an AST scan of 0.32.0's model files finds `gemma4.py:107` as the only list shard id today);
   - it raises on any duplication other than QKV shards of a `MergedQKVParallelLinearWithLoRA`.

   It hooks `_register_packed_modules` and is ~75 lines including the docstring. Happy to open it as a follow-up or fold it in here, whichever you prefer.
2. **An HF-parity e2e test.** The packed-weights unit test checks slots, not the served policy. Ours does this:
   - builds a tiny random Gemma-4 with sliding and k_eq_v full-attention layers (no download);
   - writes a PEFT adapter with nonzero B on `k_proj`;
   - compares vLLM `prompt_logprobs` (fp16) against HF fp32 with the LoRA merged, with bounds mean|Δ| ≤ 0.02 and k3 ≤ 0.01.

   CPU calibration of that harness (HF stand-ins, not vLLM yet):

   | case | mean\|Δ\| | k3 |
   |---|---|---|
   | fp16 noise floor | 0.005–0.007 | — |
   | what main serves (V from base `W_k`, K with the LoRA) | 0.252 | 0.052 |

   So main should fail both bounds by 5–12×. A control with the LoRA only on sliding layers has zero gap. The test also asserts that the adapter's effect, and the K-only gap, are more than 10× the bound, so a vLLM that serves none of the adapter, or K's alone, can't pass. GPU numbers against main and against the fix are pending; I'll post them here.

One more edge case worth deciding: a `v_proj` LoRA key on a k_eq_v layer has no target. We make that fail the load rather than pack or drop it.

I looked at that indeed, but the nasty part is that gemma-4 has both sliding layers and full attentions and only the full attention layers are the "k equals v" layers. As `packed_modules_mapping` is keyed by the leaf module name, it is hard to represent the two different layout, [q, k, v] for SWA and [q, k, k] for full attentions.

I think keeping within the existing mechanism is doable by giving a new leaf name (like `qkk_proj`) with its own mapping, but it would affect all gemma families and ends up with quite a lot of codebase changes.
