# [Bugfix][LoRA] respect `attention_k_eq_v=True` QKK LoRA layers

[Upstream PR](https://github.com/vllm-project/vllm/pull/61267) · state: open · merged: False

## Original PR description



## Overview



Fix LoRA weight loading on `attention_k_eq_v` full-attention layers (e.g. `google/gemma-4-31b-it`), where the V slice of the packed `qkv_proj` received no LoRA delta even though HF applies the `k_proj` LoRA to V.

## Claims



- On `attention_k_eq_v` full-attention layers, the `k_proj` LoRA is now packed into both the K and V slices of `qkv_proj`. This matches HF, where `value_states = key_states` (pre-`k_norm`), so a PEFT `k_proj` adapter also changes V.
- Adds an optional per-module `lora_packed_modules` override that `LoRAModelManager._register_packed_modules` checks before the class-level `packed_modules_mapping`.

## Details



On `attention_k_eq_v` checkpoints, full-attention layers have no `v_proj`. For base weights, `_gemma4_layer_weights_mapper` loads `k_proj` into both the K and V shards of `qkv_proj`. LoRA packing has no equivalent: it used the class-level `packed_modules_mapping` (`q_proj, k_proj, v_proj`) for every layer. The adapter has no `v_proj` for these layers, so the V slice was packed as `None` and V lost the `k_proj` LoRA delta.

- cjackal · comment · 2026-10-14T07:18:44Z · [source](https://github.com/vllm-project/vllm/pull/61267#discussion_r4267854069)

File: `vllm/lora/model_manager.py` · line 831

I looked at that indeed, but the nasty part is that gemma-4 has both sliding layers and full attentions and only the full attention layers are the "k equals v" layers. As `packed_modules_mapping` is keyed by the leaf module name, it is hard to represent the two different layout, [q, k, v] for SWA and [q, k, k] for full attentions.

I think keeping within the existing mechanism is doable by giving a new leaf name (like `qkk_proj`) with its own mapping, but it would affect all gemma families and ends up with quite a lot of codebase changes.

- linitra24 · comment · 2026-10-15T06:24:07Z · [source](https://github.com/vllm-project/vllm/pull/61267#discussion_r4279759120)

File: `vllm/lora/model_manager.py` · line 831

I see the limitation with the leaf-name-based mapping. My concern was mainly about introducing an implicit convention through a dynamically attached module attribute.
I was wondering whether `packed_modules_mapping` could support per-layer overrides, but I haven't worked through the implications for its other consumers, so I'm not sure that would actually be simpler.

- cjackal · comment · 2026-10-16T15:43:11Z · [source](https://github.com/vllm-project/vllm/pull/61267#discussion_r4296467993)

File: `vllm/lora/model_manager.py` · line 831

I think per-layer override approach touches quite a lot of vllm codebase - many places like target-module matching, lora wrapper selection, worker_manager assume leaf-name keys , which made me think that touching all of them is an overkill for a single consumer model architecture (I do not know other models that sets "k equals v" layer).

Instead I made a PR for what I have mentioned before (of defining `qkk_proj` as a new leaf name) at #62034, please take a look. If it still doesn't look nice then I'll give a shot for per-layer override approach.
