# [Perf][Spec Decode] DSpark: run the top-k Markov walk in one kernel

[Upstream PR](https://github.com/vllm-project/vllm/pull/64033) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Adds `dspark_fused_topk_walk` (off by default): with `dspark_draft_topk`, DSpark's sequential Markov walk over the top-k candidates runs in one Triton launch per request instead of ~100 small kernels, and the two full-vocabulary passes per decode step (`fill_(-inf)` and the per-step `gumbel_sample`) are removed. Builds on the top-k projection from #49969.

## Claims

Qwen3.8-27B-FP8 + DSpark drafter (8 draft tokens, top-k 64, probabilistic), 1x H100:

- `vllm bench serve` (Spec-Bench, temperature 0.6, 6 interleaved fresh-server pairs): **TPOT −1.3% (mean) and −2.3% (p99) at concurrency 32, output throughput +1.5%**, better in 6/6 pairs; TPOT −1.4% (mean) at concurrency 1.
- `vllm bench forward`: decode step **150–370 µs faster (0.72–0.95%)** for batch 1–32.
- The Markov top-k sampling path itself (everything after the draft lm_head): **242 → 92 µs at batch 1, 1121 → 578 µs at batch 32**; ncu: 105 → 17 kernels, DRAM traffic 700 → 419 MB at batch 32. What remains is mostly `torch.topk` (untouched).
- Lossless: the kernel samples exactly the bf16 values it writes to the draft logits cache. Draft logits differ from the per-step loop by at most 1 bf16 ULP (accumulation order of the 256-wide dot); GSM8K accuracy and acceptance length unchanged.

## Details

- **Kernel** (`dspark/topk_walk.py`): grid = (num_reqs,), 8 warps. Each program walks the draft steps: `W1[prev]` → dot with the `W2[ids]` tile (64 × rank, prefetched during the previous step since the candidate ids are known up front, so only the `W1[prev]` load is on the serial chain) → fp32 accumulate → one bf16 rounding of `values + scale * bias` (as `baddbmm` does) → write the 64 values to the cache → Gumbel-max over the 64 candidates with the same noise helpers, seed (`spec_step_seed`), position and token-id keys as `gumbel_sample`; ties go to the smallest token id like the dense argmax, and a NaN score falls back to the argmax's own candidate so `prev` always stays a valid id. `gumbel_noised_argmax` is split into `gumbel_noised_logits` + max so the kernel can tie-break by id; behaviour of existing callers is unchanged.
- **Sparse cache maintenance**: when the walk is in use, `draft_logits` is filled with `-inf` once (`draft_logits_spec`), and the walk keeps the k ids it wrote per (slot, step) and resets exactly those before writing new ones, the same scheme as DFlash2's `_cache_draft_logits_kernel` but inside the walk so it costs no extra launch. A `tl.debug_barrier()` separates the reset from the writes because an id can be both stale and new. Only the DSpark sampler writes `draft_logits`, so the invariant holds.
- **Batch-sharded draft logits (#63554)** are supported: like `gumbel_sample` and DFlash2, the walk writes (and resets) only the rows this rank owns, at `shard_row(req_state)`.
- **Confidence head** still works: its Markov embeddings are computed once from `[anchor, draft_tokens[:, :-1]]` for both the fused and the per-step path.
- **Falls back** to the per-step loop (one warning at load) for a reduced draft vocabulary (d2t, greedy or probabilistic), draft watermarking, the online acceptance estimator, a quantized/retained-NVFP4 `markov_w2`, or a `top_k × rank` tile above 128 × 256 (larger tiles spill registers). Weights are read from the Markov modules at launch, so weight reloads are picked up.
- No CPU–GPU sync added: no host reads, fixed buffers, safe under FULL CUDA graphs (validated by the replay test and the e2e and serving runs).
- **Not a duplicate**: #62958 (int8 W2 walk) and #63181 (ROCm fused GEMV + epilogue) cover the full-vocabulary path and do not apply with `dspark_draft_topk`; #61869 is the DSv4.1 specialized decode. #56694 also edits `_sample_sequential_topk`, but changes the candidate set (base ∪ Markov top-k) rather than fusing the walk; the two would conflict textually and the kernel would need the union candidates if #56694 lands. Happy to coordinate with its author.
