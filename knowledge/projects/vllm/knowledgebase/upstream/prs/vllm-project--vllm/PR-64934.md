# [Bugfix][Frontend] Normalize developer role to system for Mistral renderer

## Overview

Fixes #64793

When serving Mistral models using `--tokenizer-mode mistral`, passing an input message with `role: "developer"` via the OpenAI Responses API (`POST /v1/responses`) or Chat Completions fails with a `mistral_common` Pydantic `ValidationError` because `mistral-common` only accepts `{"system", "user", "assistant", "tool"}`.

This PR normalizes `role: "developer"` to `"system"` in `safe_apply_chat_template` for the Mistral renderer, mirroring the behavior already established in `vllm/renderers/hf.py` (#43590).

## Claims

- Calling `safe_apply_chat_template` with `role: "developer"` messages no longer raises a `mistral_common` `ValidationError`.
- Developer messages are mapped to `system` role for Mistral models and yield the exact same prompt tokens as system messages without mutating caller input messages in-place.

## Details

- Reuses `_convert_developer_to_system` from `vllm/renderers/hf.py` inside `vllm/renderers/mistral.py:safe_apply_chat_template`.
- Emits a one-time info log `Mistral tokenizers do not support the 'developer' message role. Converting developer messages to 'system' role.`.
- **Difference from #64861:**
  1. Uses defensive `msg.get("role") == "developer"` lookup instead of `msg["role"]` so malformed/partial dicts do not raise an unhandled `KeyError` before `mistral_common` validation (`_validate_apply_chat_template_args` / `ChatCompletionRequest` handles validation downstream).
  2. Reuses `tests/renderers/test_mistral.py`'s existing lightweight `MockModelConfig` / `MockVllmConfig` test harness (adding `multimodal_config: Any = None`) instead of instantiating a full `VllmConfig(ModelConfig(...))`, avoiding extra HuggingFace config/network resolution during unit tests while still exercising the real `MistralTokenizer` and `MistralRenderer.render_messages_async` path.
