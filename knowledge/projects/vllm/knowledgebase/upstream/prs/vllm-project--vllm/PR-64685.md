# [Rust Frontend] gRPC Render service with streaming Detokenize; multimodal, LoRA, logprobs and stop strings for render

[Upstream PR](https://github.com/vllm-project/vllm/pull/64685) · state: open · merged: False

## Original PR description

## Overview

Adds a `vllm.Render` gRPC service to the Rust frontend, the gRPC counterpart of the render/derender API. It also fills the gaps the Rust render path had compared with Python's: multimodal inputs, LoRA adapter names, and logprobs on detokenize.

- `Tokenize` renders a chat request into prompt token IDs plus the generation settings that rendering decides.
- `Detokenize` parses the output of `Inference.Generate` into answer text, reasoning, tool calls and logprobs, applying stop strings.
- `DetokenizeStream` does the same incrementally over the chunks of `Inference.GenerateStream`.

No engine is needed for these RPCs. The Rust frontend has no HTTP derender on main yet, so `Detokenize` is its first engine-free tool-call and reasoning parsing path. Motivation: running llm-d against the Rust frontend over gRPC.

## Related work (not a duplicate)

I searched open PRs for gRPC render, derender, the Rust render path, and render with multimodal, LoRA or `features`. No open PR adds a gRPC render service or multimodal/LoRA render to the Rust frontend. Two overlap in purpose:

- **#36102** adds a gRPC server to the Python `vllm launch render` (`VllmRender`: `RenderChat`, `RenderCompletion`). This PR serves the Rust frontend, and also covers the return path (Detokenize). The two protos are independent; aligning them is worth a maintainer decision.
- **#53418 / #53419** (draft) add HTTP `/derender` to the Rust frontend, with the stream state carried by the client. `Detokenize` here is gRPC, keeps the stream state on the server, and supports stop strings and tool/reasoning parsing in streams. Both build on `ChatRequestProcessor`, so whichever lands second rebases onto the shared decode path.

## Claims

**gRPC `vllm.Render` (`render.proto`)**
- **`Tokenize(ChatRequest)`** returns:
  - `prompt_token_ids`, already truncated;
  - the tool-call parser's `structural_tag`, which already includes the answer's structured-output constraint;
  - the effective `skip_special_tokens`;
  - the `engine_reasoning_gate`;
  - preprocessed `media` as the `PreprocessedMediaFeatures` that `Inference.Generate` accepts.

  The client copies these into its own `GenerateRequest`. `omit_media_kwargs` returns only media hashes and placeholder ranges, for routers.
- **`ChatRequest`** has typed messages, including image, video and audio parts. Besides the chat fields it carries only the inputs that change rendering: structured output, `truncate_prompt_tokens`, `skip_special_tokens` and `model`. LoRA adapter names are accepted as `model`.
- **`Detokenize(ChatRequest, prompt_token_ids, SequenceOutput)`** runs the tokens through the same decoder and chat output processor that serving uses, through a new `ChatRequestProcessor::detokenize`. It returns content, reasoning, tool calls, the reasoning token count, decoded per-token logprobs and `finish_info`. That `finish_info` is Generate's, with only `finish_reason`, `stop_reason` and `num_output_tokens` replaced, so KV/EC transfer params, `num_cached_tokens` and the reported EOS token ID pass through. A NOT_FINISHED `finish_info` does not end the output.
- **Stop strings in Detokenize:** `stop_strings`, `include_stop_strings` and `min_new_tokens` on `DetokenizeRequest`. `Inference.Generate` cannot check stop strings when `output_text` is false, so Detokenize cuts the output at the first stop string past `min_new_tokens`, and also applies a stop string that Generate reported. A reported stop string that the decoded output does not contain is rejected (`INVALID_ARGUMENT`) rather than reported as length. Stop strings are validated by `TextDecodeOptions::validate`, shared with text requests.
- **`DetokenizeStream(stream DetokenizeStreamRequest)`:** the first message is a `DetokenizeRequest`, each later one the `SequenceOutput` of one GenerateStream chunk. Responses carry content, reasoning, tool-call and logprob deltas; the last one carries `finish_info`. Text that may begin a stop string is held back; at a match the server ends the stream, and the client cancels GenerateStream. Only the start message's stop strings apply, and a chunk reporting another stop string is rejected, because text before it may already have been sent. Both RPCs share `ChatRequestProcessor::detokenize_stream`.
- **Where it is served:** on `vllm-rs render` (new `--grpc-port`) and on the main server's gRPC listener, including gRPC health.

**`vllm-rs render` server (HTTP and gRPC)**
- **Multimodal.** The server now loads the multimodal processors (`--language-model-only` turns this off). New `--dtype` sets the tensor dtype; `auto` follows the model config, running float32 checkpoints in bfloat16 like vLLM's `auto`.
- **`--limit-mm-per-prompt`**, set to the engine's limits, rejects the same over-limit requests at render time.
- **LoRA.** `--lora-modules` adapter names are accepted as `model` and passed through to generate, as Python does. They are listed in `/v1/models`, and no adapter weights are loaded.

**HTTP render ↔ generate**
- **Chat render returns Python's `features` object** (`mm_hashes`, `mm_placeholders`, base64 MessagePack `kwargs_data`). It honors `mm_payload: "none"` and the deprecated `return_mm_kwargs: false`.
- **`/inference/v1/generate` accepts `features`**, so a multimodal render response can be submitted unchanged.

## Details

- **Why Tokenize takes no `GenerateRequest`.** Rendering only depends on the chat input, the answer constraint (which the parser composes into its grammar) and prompt truncation. Returning only what rendering decides avoids duplicated or must-be-unset fields. In exchange, the client copies the returned fields into its `GenerateRequest`, as documented on `TokenizeResponse`.
- **Tool schemas as JSON strings.** Tool `parameters_json` is a JSON string, because `google.protobuf.Struct` does not keep key order and the schema is rendered into the prompt.
- **Deviations from Python's HTTP `features`:**
  - Placeholder ranges also carry an optional `is_embed` mask, because Qwen-VL-style models use sparse placeholders. Python's own TODO notes this gap, and Python's generate ignores the field.
  - Rust render does not emit `mm_metadata`.
  - Rust generate rejects items without `kwargs_data`, since the Rust frontend has no multimodal processor cache to resolve them from. It ignores `mm_metadata`, which only repeats a subset of each item's kwargs.
- **MessagePack encoding.** Kwargs use the engine protocol's MessagePack encoding. An existing test decodes bytes from Python's `MsgpackEncoder`. A new shared `mm_wire` module holds the codec and the `is_embed` conversion for both formats.
- **Model dtype.** The render server only resolves the dtype for multimodal models, so text-only models never fail on an unusual config dtype. Operators must set `--dtype` to match the engine whenever the engine overrides the config dtype.
- **Stop strings vs Python's derender.** Python's non-streaming derender only applies the request's stop strings when the host reported a stop without a reason, and its streaming derender rejects stop strings. Rust Detokenize always applies the requested stop strings, because Generate with `output_text = false` never checked them. When Generate did check them, this finds the same match. `DetokenizeStream` supports stop strings, because it keeps the decoder state on the server for the whole stream.
- **Limitations:**
  - no RAG `documents`;
  - no HTTP derender;
  - completions render takes no multimodal input, matching Python, whose completions API has no media input either.
- **Proto crate version.** `vllm-proto` 0.6.0 → 0.7.0. New fields on existing messages break Rust struct literals, so this is a minor bump in 0.x. The two `DetokenizeStreamRequest` oneof variants are boxed in codegen.
- **Pre-existing, not changed here:** a tools request to a server with tool parsing disabled fails as an internal error (`ParserDisabled` is not a request validation error), over both HTTP and gRPC.
