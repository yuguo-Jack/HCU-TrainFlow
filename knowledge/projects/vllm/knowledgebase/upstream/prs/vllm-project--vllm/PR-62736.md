# [ROCm][Kernel] Add split-K and shape-based tiles to Triton W4A16 on gfx950

[Upstream PR](https://github.com/vllm-project/vllm/pull/62736) · state: open · merged: False

## Original PR description



## Overview

Add split-K and shape/CU-count-based tile selection to `TritonW4A16LinearKernel` on gfx950 (MI355X). This is the INT4 weight-only kernel vLLM selects for GPTQ/compressed-tensors W4A16 checkpoints on MI355X; today it launches a 2D grid with fixed tiles, which leaves most of the 256 CUs idle on decode shapes.

Related: #47525 (split-K for this kernel on MI100, closed by author without review). #52983 (open, gfx90a-only dequant change) touches the same file but a different code path; the two are orthogonal.

## Claims

- Qwen3.8-27B W4A16 (GPTQ, group 128), TP=1, MI355X serving: **2.53x output throughput** (350 -> 885 tok/s) and **2.8x lower TPOT** (84.2 -> 29.8 ms) at concurrency 32. GSM8K unchanged (0.962 -> 0.962).
- Kernel microbenchmarks over 133 (M, N, K) cases from Qwen3.8-27B and Llama-3.1-8B/70B (TP1/TP8): geo-mean **3.72x** (decode M<=64: 4.7-6.6x, prefill M>=128: 1.9-2.3x).
- Split-K output is deterministic (fixed-order fp32 reduction, no atomics).
- Only gfx950 changes behavior; gfx1x, MI300 and CUDA paths are untouched.

## Details

**Root cause.** For decode (M<=64) the old ROCm config produces `cdiv(N, BLOCK_N)` workgroups, e.g. 80 for N=5120 on a 256-CU part, so the kernel streams weights at 0.1-0.5 TB/s out of ~8 TB/s HBM. This made W4A16 Qwen3.8-27B ~3.4x slower per token than BF16 despite moving 4x fewer weight bytes.

**Change.**
- The kernel gains `SPLIT_K` (grid dim 2). Each split accumulates a contiguous range of K tiles and stores fp32 partials `[SPLIT_K, M, N]`; a small Triton kernel sums them in fixed order and casts once. With `SPLIT_K == 1` the kernel is identical to before.
- `_gfx950_config(M, N, K)` picks tiles and split from the shape and `num_compute_units()`: decode splits K (power of two, >= 256 K per split) until the grid reaches ~8 workgroups/CU; prefill picks the largest `BLOCK_M` that still fills the GPU and allows at most a 2-way split. Fitted to an exhaustive sweep (geo-mean within 5.6% of per-shape best on decode, 3.9% on prefill).
- gfx950 launches with `num_stages=2, matrix_instr_nonkdim=16`: Triton otherwise selects 32x32 MFMA for `BLOCK_M >= 32`, measured ~20% slower on these tiles.

**Tradeoffs / limitations.**
- Split-K allocates a transient fp32 `[SPLIT_K, M, N]` scratch per call. The selection rule bounds it at ~34 MB for decode (<= 8 WGs/CU x 64x64 tiles) and ~101 MB for prefill (2-way split only while the grid is <= 384 tiles of 256x128); it comes from the caching allocator and works under CUDA graph capture (e2e above runs with graphs). A fused atomic/semaphore reduction was avoided to keep results deterministic and stream-safe.
- 256x256 tiles are excluded: they hit an AMDGPU backend crash ("Virtual register defs don't dominate all uses") with Triton 3.8.
- W4A16 is still ~25% behind BF16 end-to-end; closing that gap needs inner-loop dequant/layout work, not tile selection, and is left for a follow-up.
- MI300 (gfx942) likely benefits from the same approach but was not measured, so it is not enabled here.

Environment: MI355X, ROCm vLLM container (vllm 0.30.1rc1.dev493, torch 2.13.0, triton 3.8.0) with the patched `triton_w4a16.py` from this branch loaded over it.
