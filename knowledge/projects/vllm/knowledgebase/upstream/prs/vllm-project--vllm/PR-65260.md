# [Bugfix][KV Connector] Forward num_threads to non-UCX NIXL backends

[Upstream PR](https://github.com/vllm-project/vllm/pull/65260) · state: open · merged: False

## Original PR description

## Overview

`NixlConnector` reads `kv_connector_extra_config.num_threads` but forwards it to NIXL only when UCX is the sole backend. With any non-UCX backend configured, the value is silently dropped. This PR forwards an explicitly set `num_threads` to every backend and leaves the default behavior unchanged.

## Claims

- An explicitly set `num_threads` now reaches every backend:
  - in the agent config (`nixl_agent_config(num_threads=...)`), where NIXL maps it to each backend's own parameter;
  - in the explicit `create_backend` loop used when `ucx_backend_params` is set.
- When `num_threads` is not set, behavior is unchanged: UCX alone keeps the UCX-tuned default of `4`, and non-UCX backends keep NIXL's defaults. No new default is introduced for any backend.
- `num_threads` is documented in `docs/features/nixl_connector_usage.md`.

## Validation

- Root cause traced in the source at `main` (see Details). NIXL already forwards `nixl_agent_config.num_threads` to its backends ([`nixl/_api.py`](https://github.com/ai-dynamo/nixl/blob/a2165b56/src/api/python/_api.py#L259-L266)), so the value is lost on the vLLM side.
- `pre-commit run --files <changed files>`: all hooks pass.
- `pytest tests/v1/kv_connector/unit/test_nixl_connector.py -k "backend_params or num_threads"`:
  - with this PR: 11 passed
  - on `main` (same tests): 3 failed, 8 passed

    ```text
    FAILED tests/v1/kv_connector/unit/test_nixl_connector.py::test_ucx_backend_params[extra_config3-agent_backends3-created_backends3]
    FAILED tests/v1/kv_connector/unit/test_nixl_connector.py::test_nixl_num_threads[extra_config3-agent_backends3-8]
    FAILED tests/v1/kv_connector/unit/test_nixl_connector.py::test_nixl_num_threads[extra_config5-agent_backends5-2]
    ```

- Validated internally end to end in a 1P1D NixlConnector deployment with the LIBFABRIC backend: requests succeed with and without `num_threads`, and the configured value now reaches the LIBFABRIC backend (previously dropped).

## Details

**Root cause.** In `NixlBaseConnectorWorker.__init__`, `num_threads` is dropped in two places:
1. Agent config: the branch for non-UCX backends builds `nixl_agent_config(backends=..., capture_telemetry=True)` without `num_threads`.
2. Explicit backend creation (with `ucx_backend_params`): only UCX can receive `num_threads`, and only when it is the sole backend. Every other backend gets `{}`.

**Flow touched** (worker init only; the transfer path is unchanged):
1. The worker reads `backends`, `num_threads` and `ucx_backend_params` from `kv_connector_extra_config`.
2. It builds `nixl_agent_config`. In normal mode NIXL creates the backends from `config.backends`, passing `num_threads` under each backend's own name.
3. In explicit mode (with `ucx_backend_params`), the agent is created with `backends=[]` and vLLM calls `create_backend(name, params)` for each backend.
4. The backends then use the value, e.g. LIBFABRIC sizes its descriptor post thread pool and UCX its worker threads.

**Why the default is not forwarded.** The default of `4` is tuned for UCX, to avoid exhausting UAR doorbell pages on Mellanox NICs. Forwarding it unconditionally would quietly change thread counts for every non-UCX user, and in mixed `["UCX","LIBFABRIC"]` setups, which get no `num_threads` today. Only an explicitly set value is forwarded.

**Mixed backends.** With `["UCX","LIBFABRIC"]` and `num_threads: N`, both backends get `N`. To set them separately: `NIXL_LIBFABRIC_NUM_THREADS` overrides LIBFABRIC's value inside NIXL, and in explicit mode `ucx_backend_params.num_threads` overrides UCX's value, since it is applied after `num_threads`.

**Tests.** I extended the existing `ucx_backend_params` test with a mixed-backend explicit case, and added a parametrized test that checks the agent config receives `num_threads` (UCX-only default, LIBFABRIC with and without an explicit value, mixed). These use the same `NixlWrapper`/`nixl_agent_config` stubs as the existing backend-params test.

**Not a duplicate.** I searched open and closed issues and PRs for `num_threads`, LIBFABRIC, non-UCX and `nixl_agent_config` under NixlConnector. No PR forwards `num_threads` to non-UCX backends. #59877 and #61638 edit the same `nixl_agent_config(...)` lines to add sync-mode arguments, but they keep the non-UCX branch without `num_threads`. Whichever of these merges first will cause a small textual conflict for the others.
