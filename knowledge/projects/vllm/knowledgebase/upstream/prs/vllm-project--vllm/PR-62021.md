# [Bugfix][Distributed] Use a file rendezvous for offline single-node DP

[Upstream PR](https://github.com/vllm-project/vllm/pull/62021) · state: open · merged: False

## Original PR description

## The failure

[AMD CI build 14810](https://buildkite.com/vllm/amd-ci/builds/14810), group `(MI300) Distributed Features`, on the `data_parallel_offline.py` example:

```
torch.distributed.DistNetworkError: The server socket has failed to listen on any local network address. port: 44122, useIpv6: false, code: -98, name: EADDRINUSE, message: address already in use
```

## The problem

An offline data-parallel launcher picks the group's port by probing: it binds port 0, reads back whatever the kernel assigned, closes the socket, and hands the bare number to every rank through `VLLM_DP_MASTER_PORT`. The ranks bind it later, from other processes.

Nothing owns the port in between, so any process on the host can take it and the kernel will hand it out again on the next probe. Rank 0 then cannot open the store and the remaining ranks wait out the full init timeout, so a job that fails this way also runs about ten minutes longer than normal. This is the generic probe-then-bind race: the launcher chooses a port it never binds.

## Where it is tracked

[RFC #51275](https://github.com/vllm-project/vllm/issues/51275) catalogues the probe-then-bind sites and lists `data_parallel_offline.py` as **Uncovered**. This PR covers that row. Related, none of which cover this path:

- #51018 fixed the same race for the DP world group, but only when a coordination store exists, which offline runs do not have.
- #61102 changes the port pool the probe draws from, so the race remains.
- #58312 applies the file-store pattern to the MoE test launcher.

## How often

Rarely, but it blocks the whole group, and it depends on the state of the node rather than on the code, which is why it looks random.

- One failure in the last ten AMD nightlies (14162 through 14707 passed, 14810 failed). Retrying on a different node cleared it.
- Of 2000 consecutive port probes on a CI host, 141 (about 7%) returned a number an earlier probe had already handed out.
- Under sustained connection churn, 3 of 25 probed ports could no longer be bound 3 seconds later, with the same `EADDRINUSE`. Ports that passed through `TIME_WAIT` are the usual reason.

## The change

The number stays, but it is no longer used as a port. Ranks treat it as a rendezvous token and meet on a file store named after it, in a temporary directory owned by the launcher. Every rank derives the same path on its own from values it already has, so no extra coordination is needed and concurrent runs get separate directories. The launcher removes its directory once the ranks exit; one left behind by a killed run is harmless, because the next run's writes shadow it.

This applies only when every rank rendezvous on this host. Multi-node rendezvous and AITER custom all-reduce, which requires a TCP store, keep the previous behaviour.

## Tests

`tests/v1/engine/test_dp_world_group_port.py` gains a case that holds the launcher's port with another socket and then brings up two offline ranks; it reproduces the CI failure exactly on `main` and passes with this change. `tests/utils_/test_network_utils.py` covers the new path helpers.
