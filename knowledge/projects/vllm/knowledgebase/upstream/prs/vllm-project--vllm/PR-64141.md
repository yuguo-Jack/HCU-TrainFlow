# [Bugfix][Attention] Avoid overwriting shared KV cache during scale view creation

[Upstream PR](https://github.com/vllm-project/vllm/pull/64141) · state: closed · merged: False

## Original PR description

## Overview

Remove the two inline scale-cache fills from Triton attention so that creating a layer's scale views cannot overwrite already-written cache contents.

Fixes #63944.

Based on the issue author's analysis and suggested fix. Both fills were still present in main at `274a5e19a18460ed41d47117398494b721e3df16`.

## Claims

- Preserve live hybrid-model state and existing per-token-head KV scales when scale views are first created.
- Keep the fix to two deleted lines, with no new initialization, binding, or storage registry.
- Extend the existing per-token-head KV accuracy test with Jamba, without CI configuration changes.

## Validation

Prior local validation used an RTX 4090, vLLM 0.32.0, PyTorch 2.13.0+cu130, MRV2, eager execution, BF16 weights, INT8 per-token-head KV, TP=1, and seed 42. Baseline and modified cases used separate cold-start processes.

| Model | Baseline | Without the fills |
| --- | --- | --- |
| Qwen3.5-4B, real weights | First request produced garbled text from generated token 2; later requests were correct | A diagnostic method replacement disabling only the two fills restored the first response to `4` followed by EOS; repeated requests and the 1-to-10 continuation were correct |
| Granite-4.0-H-350M, real weights | First view creation changed a cumulative 378,694 bytes of live Mamba2 state; first/repeated requests diverged from generated token 2 | No observed state changes; both requests matched the baseline's repeated request |
| Gemma-4-E2B-it, original configuration with random weights | 506 scale entries changed to 1; first/repeated requests differed | No observed changes; both requests matched the baseline's repeated request |

The Qwen reproducer enabled prefix caching and respected EOS, with a 96-token generation limit. It replaced only the two fill statements with `pass` in `_ensure_scale_caches()` at runtime; it did not add binding hooks or early initialization. The corrected arithmetic responses had token IDs `[19, 248046]`. This was a diagnostic intervention, not execution of the committed branch's regression tests.

The Granite/Gemma experiments applied the two-line runtime patch directly, disabled prefix caching, and used two identical requests with `ignore_eos=True` for a fixed 12-token decode window. The Gemma run is a structural reproducer, not checkpoint accuracy validation. Counts above sum snapshot observations and are not deduplicated physical-address counts. These small reproductions do not constitute a full model accuracy evaluation.

Regression coverage reuses `tests/models/quantization/test_per_token_kv_cache.py::test_per_token_head_kv_cache_accuracy`, adding `ai21labs/Jamba-tiny-dev` alongside the existing Llama model. ## Details

`_ensure_scale_caches()` creates strided float32 aliases into packed KV storage. Those views span every physical block, including pages whose current owner is another hybrid cache group. Its first call can occur after preceding stateful layers have already written their state. Filling the scale aliases then overwrites that live state. A KV-sharing layer can similarly reset scales written by its source layer.

Valid new KV writes compute and store their own scales without reading the previous scale. Historical or shared KV must retain its corresponding scales. INT8/FP8 and INT4 readers mask out-of-range tail loads; a full-pool fill does not establish block ownership or make an unwritten valid slot correct.

Related PR #51091 deduplicates initialization but retains the first fill for each registered view. That does not cover #63944, where the first fill itself overwrites another cache group's live state.

Scope limitations: the Jamba regression covers INT4/INT8/FP8 on the MRV2 eager path and the selected cache layout. It does not directly check byte preservation across all layouts or validate CUDA Graph, sleep/wake, or connector behavior. Reserved-block dummy/capture reads require their own initialization/masking contracts and are not covered by the normal valid-slot argument above. No performance or universal model-compatibility claim is made.
