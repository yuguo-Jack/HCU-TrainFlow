# [Bugfix][Multimodal] Recover PyNvVideoCodec decoder slots after failures

[Upstream PR](https://github.com/vllm-project/vllm/pull/59597) · state: closed · merged: True

## Original PR description

## Problem

PyNvVideoCodec has two failure modes:

- A failed decode can poison a cached decoder, causing later valid videos to fail.
- Resolution changes can grow PyNvVideoCodec 2.2.3's cached frame pool and leak the replaced decoder until GPU memory is exhausted.

## Fix

- Reject unsupported streams before decoder construction and retire failed slots.
- Construct decoders with bounded dimensions; default bounds cover both input orientations only when they fit codec limits and the reserved memory budget.
- Decode 32 frames at a time, synchronizing and releasing each batch.
- Keep routine rebuild cleanup stream-local and reserve device-wide recovery for failed requests.

## Validation

Rebased onto `main` at `3fe917abb1`. On GB200 with PyTorch 26.06, Torch 2.13.0+cu130, and PyNvVideoCodec 2.0.4:

```bash
.venv-gpu/bin/python -m pytest tests/multimodal/test_video.py -k pynvvideocodec -v
# 31 passed, 1 H100/H200-only skip

.venv-gpu/bin/python -m pytest tests/multimodal/test_gpu_ipc_memory.py -v
# 18 passed
```

Full pre-commit passed on all changed files. For a generated 300-frame 1080p long-GOP video, `CreateDemuxer` took 0.228 ms median and fetching 256 frames in chunks of 32 took 0.174 s versus 0.177 s in one batch. Earlier GB200 Video-MME validation covered 10 videos x 2 passes with stable GPU memory. Full 300-video H200 validation is pending.

No duplicate open PR was found. AI assistance was used; the human submitter is responsible for reviewing and validating the change.

**Verification:** In `_validate_decoder_caps` (vllm/multimodal/video_decoders/pynvvideocodec.py:349-350), the default path returns hardware caps `width_max, height_max`, not the video's actual resolution. `_construct` (lines 160-182) passes these into `SimpleDecoder`, sizing the native frame pool at hardware max.

`gc.collect()` runs in the API-server process and holds the GIL for the whole collection, so it pauses the asyncio loop and the other renderer threads, i.e. streaming/tokenization for all requests, not just video ones. Its cost grows with the frontend heap. `recover()` is reachable by any input that passes the caps check but fails later (e.g. a truncated/corrupt bitstream), so a client can also trigger it repeatedly.

Is it needed given `decoder.stop()`, the `del decoder`s and the unchained re-raise? If a specific cycle keeps the native decoder alive, can we break it directly? If it is needed, could you share the measured pause on a realistic heap? The device sync + `empty_cache()` are fine by me: they only touch the frontend's own context and only on the failure path.
