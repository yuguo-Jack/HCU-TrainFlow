# [Bugfix][Parser] Preserve token IDs in non-streaming engine parsing

[Upstream PR](https://github.com/vllm-project/vllm/pull/65303) · state: open · merged: False

## Original PR description



## Overview

Rebase of #50676 (by @yimdev, kept as co-author) onto current main, with its conflicts resolved. Fixes #64326: non-streaming `DelegatingParser.parse()` ignored `model_output_token_ids`, so tool-call or `</think>` markers that the model wrote as ordinary text were parsed as real markers.

Related: #60256 fixes the reasoning-marker half of this by a different route; this PR also covers tool-call markers and `tool_choice="none"`. Happy to coordinate if reviewers prefer one approach.

## Claims

- Non-streaming `parse()` now runs one token-aligned engine pass when the reasoning and tool adapters share a parser engine (or there is only a tool adapter). Literal marker text stays in `content` instead of becoming a tool call or ending reasoning.
- Covers `tool_choice="none"`, and keeps Mistral pre-v11 on its legacy JSON-array extraction.
- No change to streaming, or to parser pairs that use different engines (they keep the existing text-based path).

## Details

**Root cause:** `DelegatingParser.parse()` ran `extract_reasoning()` and then `_extract_tool_calls()` on decoded text only. A marker the model spelled with ordinary tokens decodes to the same string as the special token, so it was treated as structural.

**Fix (from #50676):** when token IDs are available and both adapters share an engine, `parse()` calls the new `parse_model_output()` on the adapter mixin, which runs `ParserEngine.parse()` once with the token IDs. Tool-only parsers start in `CONTENT`. `_classify_tool_choice()` is factored out so `parse()` and `_extract_tool_calls()` use the same tool-choice rules.

**Changes on top of #50676 while rebasing:**
- `_classify_tool_choice()` now also treats `ToolChoiceCustom` as named, matching what main added to `_extract_tool_calls()` since #50676 was opened.
- `test_delegating_replay.py`: uses `cfg.terminal_literal()` / `cfg.terminal_literals`, since `terminals` values can now be tuples. The tool-opening marker is found from the `CONTENT` transitions (covers `TOOL_REQUESTS_START`), and the literal-marker test only runs for parsers whose tool marker is a token-ID terminal. `minimax_m3` and `plamo3`, added after #50676, match their tool marker by text, so a literal marker can't be told apart there.

**Limitation:** mixed-engine reasoning/tool pairs still use the text path (TODO kept in code). For qwen3, the literal `<tool_call>` marker is now kept as text, but the function-open prefix still opens a call from `CONTENT`. That part is engine-side and tracked in #58147, so a quoted tool call is still extracted there (consistent with streaming).

| real tool call | correct | correct |

The with-ids path now matches streaming on all 6 rows; the base had 4/6
diverged. Streaming itself is untouched: my six delta-batching forms give one
outcome on base and head alike.

What's left is the qwen3 tool half. It is now consistent between the one-pass
and streaming paths: the quoted call is still extracted, with the start-marker
text in `content`.

still opens a call from CONTENT (CONTENT → FUNC_PREFIX). That's engine-side,
tracked in #58147; a routing-only change can't reach it. GLM came out all-good

Mixed-engine pairs still take the text path, per the TODO kept in the code —
