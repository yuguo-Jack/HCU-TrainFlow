# [Rust Frontend] Let the handshake owner serve a range of DP ranks

[Upstream PR](https://github.com/vllm-project/vllm/pull/64450) · state: closed · merged: True

## Original PR description

## Overview

Let the Rust handshake owner (managed `vllm-rs serve`) serve a range of the data parallel ranks, so several Rust frontends can split one DP deployment. The change is limited to `vllm-engine-core-client`: there is no CLI, Python, or INIT wire change, and nothing sets a nonzero start rank until vllm-project/vllm#64451 adds the `vllm-rs serve` flags.

Stack: vllm-project/vllm#64449 → this PR → vllm-project/vllm#64451.

## Claims

- `TransportMode::HandshakeOwner` takes `engine_start_index` and a deployment-wide `data_parallel_size` next to `engine_count`, like `TransportMode::Bootstrapped`. Existing callers keep internal LB by passing start rank 0 and their engine count as the DP size, with unchanged behavior.
- The frontend whose range starts at rank 0 handshakes with every rank but registers only its own engines. Other frontends handshake only with their own engines and find the coordinator through READY `dp_stats_address`.
- The in-process coordinator publishes its wave state on a frontend-facing XPUB (`frontend_stats_publish_address`), in the tuple format of Python's coordinator, so the frontends of other ranks stamp requests with the current wave.
- A misconfigured multi-frontend deployment fails at startup with a clear error instead of hanging: an engine of an unexpected rank, a remote rank's engine that joins headless, or, under coordinated DP, engines that report different `parallel_config_hash`.

## Validation

- `hybrid_lb_frontends_split_ranks_and_follow_rank_zero_coordinator`: two frontends (ranks 0 and 1) and a mock engine that handshakes with both, as a Python engine on a hybrid-LB node does. Each frontend connects only to its own engine, and the rank-1 frontend stamps requests with the wave that rank 0's coordinator advanced to. Fails without the registration filtering.
- `coordinator_publishes_wave_state_to_frontend_subscribers`: a subscriber receives the current state on subscribe and each new state after wave transitions, checked byte for byte against the msgpack tuple.
- `partitioned_handshake_rejects_unexpected_ranks_and_headless_remote_engines` and `handshake_checks_parallel_config_hashes_only_for_coordinated_dp` (dense ranks with different hashes still connect).
- `cargo nextest run --workspace` in `rust/`: 2382 passed; `cargo clippy --workspace --all-targets -- -D warnings` is clean.
- End to end through vllm-project/vllm#64451 on GB200 with a MoE model: hybrid and external DP LB, including a burst sent to one frontend only, which completes while the other ranks' engines follow its waves. See vllm-project/vllm#64451 for the results.

## Details

Python's `vllm serve` supports hybrid DP LB (`--data-parallel-hybrid-lb`, one frontend per node) and external DP LB (`--data-parallel-rank`, one frontend per rank). Standalone `vllm-rs serve` supports only internal DP LB, because its handshake owner assumes it owns every engine. This PR adds the transport and coordinator side; vllm-project/vllm#64451 adds the CLI.

Roles, as in Python's `launch_core_engines`:

- The frontend whose range starts at rank 0 binds the shared handshake and handshakes with all `data_parallel_size` engines, so engines of other ranks fetch the coordinator addresses and the DP rendezvous there. Those engines take their input/output addresses from their own frontend, so only rank 0's own engines register with it. For MoE it runs the in-process coordinator, which `server/src/config.rs` now enables only for this frontend.
- Other frontends handshake only with their own engines, on a local endpoint, and subscribe to rank 0's coordinator publish address from READY `dp_stats_address`.
- An engine on another node handshakes with rank 0 first and then with its own frontend, through Python's existing `client_handshake_address` path; vllm-project/vllm#64451 passes that address to the managed engines.

Coordinator publish: the in-process coordinator tracks no request counts, so it publishes Python's wave-only update `(None, wave, engines_running)` after every wave transition and to each new subscriber (zmq.rs XPUB registers a subscription only when `recv()` yields it). A separate task woken by `Notify` sends the latest state, so a slow subscriber cannot block wave control toward the engines. The socket is bound whenever the coordinator runs, as in Python, although only hybrid and external LB have subscribers.

Startup checks:

- The rank-range and remote-headless checks run only when a frontend serves a subset of the ranks, which leaves internal LB as on `main`. Python also applies both to internal LB (there, remote engines must be headless); that is left for a follow-up.
- Python compares each engine's `parallel_config_hash` with the frontend's own `ParallelConfig`. The Rust frontend has no `ParallelConfig`, so it requires all engines to agree. Like Python, it checks only under coordinated DP, whose ranks share collectives.

The first two commits are a helper rename and a mechanical split of the mock engine handshake into steps. The new tests account for about 530 of the added lines, including mock-engine support for the two-handshake engine; the rest is about 340 lines of non-test code.
