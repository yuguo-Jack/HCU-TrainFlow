# [Security] Add hash collision defense for prefix cache with non-crypto hashes

[Upstream PR](https://github.com/vllm-project/vllm/pull/54727) · state: open · merged: False

## Original PR description

When using non-cryptographic hash algorithms (xxhash/xxhash_cbor) for prefix caching, hash collisions can cause cache poisoning where a request receives incorrect KV cache data from an unrelated prompt.

Add insertion-time content verification that stores a token fingerprint alongside each cached block and rejects colliding insertions with a warning. The defense is automatically enabled when the configured hash algorithm is xxhash or xxhash_cbor, with zero overhead on the default sha256 path.

- KeitaToyama-hub · comment · 2026-09-08T22:06:15Z · [source](https://github.com/vllm-project/vllm/pull/54727#issuecomment-5592507548)

I agree that xxHash intentionally trades collision resistance for speed. Our concern is whether that trade-off is worthwhile for prefix caching.

The measurements included in the vulnerability report show 221.2 ns for XXH3-128 versus 402.6 ns for SHA-256 on a 128-byte input. With the default 16-token blocks, even a 4096-token prompt (256 blocks) would therefore incur only about 46 us of additional hashing work when using SHA-256.

For perspective, LLM serving TTFT（Time to First Token）is measured in milliseconds; representative vLLM serving benchmarks report TTFTs on the order of tens of milliseconds. Thus, the estimated hashing overhead is likely on the order of 0.1% of TTFT or less. Since TTFT excludes the subsequent token-generation time, the overhead as a fraction of end-to-end request latency would be even smaller.

Given that these collisions can lead to application-level cache-integrity failures, this seems like a very small performance benefit in exchange for a substantial security loss. Since SHA-256 is already the default, we recommend removing the xxHash prefix-cache option rather than only documenting the risk.
