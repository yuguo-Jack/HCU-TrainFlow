# [Feature][MRV2] Add typed pipeline side-input transport

[Upstream PR](https://github.com/vllm-project/vllm/pull/53102) · state: open · merged: False

## Original PR description

## Overview

Add a registry-driven PP tensor transport interface for MRV2, including per-field
SP layouts and shared buffer handling over the existing tensor-dict channel.

## Claims

- Register hidden states, residuals, shared top-k indices and multimodal encoder
  embeddings centrally. Models select their fields, shapes, dtypes and send/receive
  directions at initialization.
- Preserve TP slice-send/all-gather for complete tensors. Send already-SP-sharded
  fields directly to the matching TP lane, allowing both layouts in one batch.
- Share allocation and input preparation across dummy runs, capture and execution.
  Full-graph output buffers retain each field's captured shape for replay.
- Migrate the DeepSeek V3.2 NVIDIA backbone to the shared API while retaining
  upstream layer-sharing detection. Preserve legacy factory imports, optional
  buffers and dtype-converting receives for models without explicit dtype bindings.
- Relay multimodal encoder outputs and their CPU mask to compatible drafters,
  without changing text embedding weights, sampled-token synchronization or
  upstream auxiliary-hidden-state relay.

## Validation

Local CPU validation (macOS arm64, Python 3.12):

```text
.venv/bin/python -m pytest -q -p no:cacheprovider tests/distributed/test_pp_transport.py
42 passed
```

Includes real three-stage Gloo relay and four-process PP2TP2 communication with
mixed replicated/sharded tensors, alternating batch sizes, stable buffer
addresses, invalid layouts, legacy dtype conversion and `torch.compile` fullgraph
tracing with the eager backend. Removing the per-field SP communication override
makes the PP2TP2 regression fail. The suite is wired into CPU CI.

All applicable pre-commit checks passed on the nine PR files, including Ruff,
mypy, markdownlint, SPDX and test-to-CI wiring.

An additional run including unchanged MOSS Audio tests had 57 passes and four
fixture setup errors from the local environment's missing `orjson` dependency.
These are not counted as successful model tests.

GPU serving, model accuracy, CUDA graph replay, `VLLM_GPU_SYNC_CHECK=error` and
performance validation remain pending. CPU tracing does not validate CUDA graph
replay. Keep this PR as a draft; no GPU accuracy or performance gain is claimed.

## Details

- `PPTransportTensor(sequence_parallel=True)` uses `ceil(global_tokens / tp_size)`
  local rows; other fields retain the global token dimension. The model owns SP
  padding and collectives, and adjacent stages must agree on each field's layout.
- Runtime buffer handling does not read device tensor values on the host. Bound
  top-k buffers retain their addresses; variable-length multimodal payloads stay
  outside the target model's compiled input schema.
- Models expose `pp_transport` on their top-level module. Existing models without
  a binding keep full-tensor behavior. MRV1's communication policy is unchanged.
- This framework does not remove existing model SP+PP restrictions. Sharded PP
  with ubatching/DBO is rejected because its global-token slicing needs separate
  shard-aware support. Full-tensor PP and ubatching remain unchanged.
- Related work: #54347 enables K3 SP+PP using a model-wide layout flag. This PR
  provides reusable, mixed per-field layouts, registry and multimodal relay;
  it does not duplicate K3 enablement. Upstream shared-indexer boundary handling
  from #59961 is reused rather than reimplemented. #50410 is unchanged.
- See `docs/design/pp_transport.md` for integration examples. The branch is merged
  with upstream main `5d55ef1590c92213e3893dc8e8712f7f2e0bc508`.

AI assistance was used for implementation and local checks. Human review of the
diff and GPU validation remain required before marking ready.

- xsxszab · comment · 2026-11-03T22:21:28Z · [source](https://github.com/vllm-project/vllm/pull/53102#issuecomment-6616885482)

Some GPU results relevant to the SP transport part of this PR. I compared gathering SP shards at PP boundaries with sending them directly.

Setup: 8×B300, MRV2, MegaMoE with model-level SP. SP under PP was enabled with local model patches.

- **Gather**: gather SP shards before returning from each stage, then use the default TP slice-send/all-gather transport.
- **Direct**: send shards rank-to-rank using the runner change from #54347.

Throughput change with direct transfers relative to gather, with runs interleaved:

| Config | Hand-off per token (bf16 elements) | Decode | Mixed | Prefill |
|---|---|---|---|---|
| Step5 PP2×TP2 | 4096 | −0.8% | 0.0% | +1.7% |
| Step5 PP2×TP4 | 4096 | +0.5% | 0.0% | +0.9% |
| Kimi K3 PP2×TP4 | 5×7168 | +0.1% | +0.2% | +0.9% |
| Kimi K3 PP4×TP2 | 7×7168 | −0.3% | +0.5% | +0.8% |

All differences are within run-to-run noise, and GSM8K results are identical. The two extra all-gathers per boundary take less than 1% of step time—about 0.8 ms for an 8192-token step at Kimi's width.

On this setup, direct SP transfers show no measurable throughput benefit. They may be more beneficial with slower TP links, such as PCIe or cross-node connections. Happy to share the patches if useful.
