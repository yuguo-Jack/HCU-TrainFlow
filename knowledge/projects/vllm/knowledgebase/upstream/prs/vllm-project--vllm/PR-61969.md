# [Bugfix][Sampler] Support TP-sharded logits in MinTokensLogitsProcessor

[Upstream PR](https://github.com/vllm-project/vllm/pull/61969) · state: open · merged: False

## Original PR description



## Overview



`MinTokensLogitsProcessor` writes `-inf` at stop-token positions using **global** token ids.
When the LM head output is TP-sharded (vocab-parallel logits fed to the sampler), `logits`
only spans the rank-local vocabulary shard, so those ids index out of bounds and crash all
TP ranks. This change translates the ids to rank-local columns when the CPU-side index
tensors are built.

Fixes #61966

## Claims



- Fixes the OOB crash (`index 248044 exceeds bounds 31040`) on backends that feed sharded
  logits to the sampler (observed on vllm-ascend, 910B2C, TP8, 248320-vocab model).
- Unsharded path (default, all current GPU flows) is byte-identical: the translation is the
  identity mapping when `tp_size == 1`.
- Hot kernels (`apply()`, `_mask_stop_token_logits()`) are untouched: no new device ops, no
  shape changes at mask time.
- Adds CPU-only unit tests that reproduce the crash on main (`IndexError`) and pass with
  the fix.

## Validation



- New tests `tests/v1/sample/test_min_toks_sharded_logits.py` (CPU-only, no model weights;
  the TP rank is simulated by monkeypatching `get_tensor_model_parallel_rank`):
  - On pristine main, 4/5 tests fail with `IndexError: index 30 is out of bounds for
    dimension 1 with size 25`, hitting all three consuming paths (`apply()`, the restore
    read in `_mask_stop_token_logits()`, `apply_with_spec_decode()`).
  - With this change: 5/5 pass. Run: `pytest tests/v1/sample/test_min_toks_sharded_logits.py -v`
- Independent simulation (8 ranks, vocab 248320, EOS ids 248044/248046): per-rank masking is
  bit-identical to full-vocab masking on every rank; no duplicate index pairs; padded vocab
  bounds covered.
- Production soak on vllm-ascend (910B2C, TP8, 1P1D + MTP3): crash reproduced 100% before
  the fix; 0 occurrences across a 2h44m multi-stage benchmark (5 concurrency levels up to
  32, prompt lengths up to 64k) after.

## Details



- Root cause: the index tensors are built in the **global vocabulary coordinate system**,
  while the tensor being indexed is in the **rank-local shard coordinate system**; both
  `update_state()` and `apply_with_spec_decode()` consume global ids.
- Fix: compute `shard_start` / `shard_end` in `__init__` via the existing helpers
  `pad_vocab_size()` + `vocab_range_from_global_vocab_size()` (padding-correct); new
  `_local_stop_ids()` helper maps in-shard ids to `tok - shard_start` and drops ids owned by
  other ranks; index-list construction in `update_state()` / `apply_with_spec_decode()` goes
  through it.
- Why build-time translation instead of clamped indices + `torch.where` at mask time:
  clamped out-of-shard entries can collide with a valid entry on the same column, and
  duplicate-index assignment has undefined write order, so an invalid entry can revert a
  legitimate `-inf`. Build-time translation never creates duplicate indices. These index
  tensors are already rebuilt with data-dependent sizes on every `update_state()` (sparse
  processor), so build-time filtering introduces no new shape-variance class.
- Limitation: the default GPU flow all-gathers logits before sampling, so the buggy path is
  not naturally reachable in mainline CI; the unit tests exercise it directly. The indexing
  contract is violated by any caller that feeds sharded logits (first-party ecosystem
  backends, e.g. vllm-ascend `enable_reduce_sample`).

**1. TP > 1 with full-vocabulary logits loses stop-token masking**

For all four cases, the vocabulary size is 100, the global stop ID is 40, `min_tokens=1`, and the output-token list is empty. With TP=4, the PR's padded vocabulary is 128, giving 32 columns per shard.

| Input to the processor | Expected masked columns | Baseline | PR head |

| TP=1, rank=0, full logits `[1, 100]` | `[40]` | `[40]` | `[40]` |
| TP=4, rank=0, full logits `[1, 100]` | `[40]` | `[40]` | **`[]`** |

| TP=4, rank=0, local logits `[1, 32]` | `[]` | `IndexError` | `[]` |

The local-shard cases confirm the fix, but TP size alone does not establish whether the sampler receives local or gathered logits. The [default LM-head path gathers TP logits and trims them to the original vocabulary](https://github.com/vllm-project/vllm/blob/fa75d3456d60a5ffe923818c4b495295675b38e1/vllm/model_executor/layers/logits_processor.py#L180-L199).

In the TP=4/rank=0/full-vocabulary case, the PR infers the range `[0, 32)`, drops global ID 40, and builds `logits_slice=[[], []]`, even though column 40 exists in the actual input. With a synthetic stop-token logit of 10.0, the baseline changes it to `-inf` and argmax moves from 40 to 99; the PR leaves it at 10.0 and argmax remains 40. This demonstrates the masking regression at the processor boundary; it is not a claim about an end-to-end model generation run.

from types import SimpleNamespace
from unittest.mock import patch

import torch

from vllm import SamplingParams
from vllm.config import VllmConfig
from vllm.v1.sample.logits_processor.builtin import MinTokensLogitsProcessor
from vllm.v1.sample.logits_processor.interface import BatchUpdate

for tp, rank, width in [(1, 0, 100), (4, 0, 100), (4, 1, 32), (4, 0, 32)]:
    config = SimpleNamespace(
        model_config=SimpleNamespace(get_vocab_size=lambda: 100),
        parallel_config=SimpleNamespace(tensor_parallel_size=tp),
    )
    try:
        with patch("vllm.distributed.get_tensor_model_parallel_rank", return_value=rank):
            processor = MinTokensLogitsProcessor(config, torch.device("cpu"), False)
            processor.update_state(BatchUpdate(
                batch_size=1, removed=[], moved=[],
                added=[(0, SamplingParams(min_tokens=1, stop_token_ids=[40]), None, [])],
            ))
            logits = torch.arange(width, dtype=torch.float32).reshape(1, width) / 100
            if width == 100:
                logits[0, 40] = 10.0
            elif rank == 1:
                logits[0, 8] = 10.0
            indices = [index.tolist() for index in processor.logits_slice]
            result = processor.apply(logits)
            masked = torch.isneginf(result[0]).nonzero().flatten().tolist()
            print(f"TP={tp} rank={rank} width={width}: indices={indices}, "
                  f"masked={masked}, argmax={result.argmax(-1).item()}")
    except Exception as error:
        print(f"TP={tp} rank={rank} width={width}: {type(error).__name__}: {error}")

try:
    MinTokensLogitsProcessor(VllmConfig(), torch.device("cpu"), False)

Thanks @Ondre119 for the careful CPU-level comparison — both findings are real, and both are fixed in 9bed96d.

**1. TP>1 + full-vocabulary logits.** Agreed — TP size alone does not determine the logits layout. The processor now builds index tensors in both coordinate systems and selects at mask time from the actual logits width: `logits.shape[1] < vocab_size` → rank-local (build-time-translated, out-of-shard ids dropped, no duplicate indices); otherwise → global ids (baseline behavior, also covering padded all-gathered logits). Your case 2 (TP=4, rank=0, full `[1,100]`) now masks column 40 and argmax moves off the stop token. The layout contract is documented on the processor: sharded logits are indexed locally, full-vocabulary logits globally, selected per call by width.

**2. Bare `VllmConfig()` construction.** The constructor now falls back to global-only indexing when `model_config` is None (missing `parallel_config` is treated as TP=1), so the three existing `test_min_tokens_` tests run unmodified again.

**Tests**: added cases for the full-vocab path with TP=4 (masking on any rank across `apply()`, structured-output restore, and `apply_with_spec_decode()`) plus None-config construction. Red/green on CPU using the same method as yours: the 3 new full-vocab tests and the None-config test fail on the previous head, 10/10 pass with the fix.

Happy to have you rerun the probe — cases 1/4 (local-shard) are unchanged, cases 2/3 and the legacy-constructor check should now pass.
