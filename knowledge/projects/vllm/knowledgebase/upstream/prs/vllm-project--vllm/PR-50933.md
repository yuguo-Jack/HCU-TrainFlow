# [Bugfix] Resolve $ref/$defs in tool schemas and preserve definitions

[Upstream PR](https://github.com/vllm-project/vllm/pull/50933) · state: open · merged: False

## Original PR description

## Purpose

Fixes #46924. Supersedes #46925 (incomplete fix) and #46170 (`pop`→`get` only).

Tool schemas generated by Pydantic v2 use `$defs`/`$ref` to define nested types. Two bugs caused nested object arguments (e.g. `{"kind": "week"}`) to be double-encoded as JSON strings:

1. **No `$ref` resolution** — `find_tool_properties()` returned raw `$ref` pointers, and `extract_types_from_schema()` fell back to `["string"]` for unresolved references. This caused nested objects to be treated as strings.

2. **Destructive `pop("$defs")`** — `_get_tool_schema_defs()` used `params.pop("$defs", {})`, mutating the tool's parameter dict. On the streaming/engine path where `_get_tool_schema_defs` runs before `find_tool_properties`, the `$defs` were already gone, making ref resolution impossible even if added.

### Fix

- Add `_resolve_refs()` helper that inlines `$ref` pointers against `$defs` (Pydantic v2) and `definitions` (JSON Schema draft-07), with JSON Pointer escape decoding (`~0`→`~`, `~1`→`/`) and bounded recursion for cyclic schemas.
- Extract `_resolved_tool_properties()` to unify resolution for both definition namespaces.
- Update `find_tool_properties()` to resolve refs before returning — all downstream callers (qwen3_coder, deepseek_v32, seed_oss, glm4_moe, parser engine) automatically get concrete type information.
- Change `params.pop("$defs", {})` to `params.get("$defs", {})` in `_get_tool_schema_defs()` so definitions survive for subsequent argument coercion.

### Credit

This fix incorporates insights from:
- @hclsys who identified the `pop` ordering issue in #46925
- @alexeldeib who provided a complete supplementary patch with legacy defs support, cycle protection, and JSON Pointer decoding based on production traffic

- percymcn · comment · 2026-08-10T19:36:54Z · [source](https://github.com/vllm-project/vllm/pull/50933#issuecomment-5245057929)

Reimplemented `_resolve_refs` / `_resolved_tool_properties` from the diff verbatim and ran them against real `pydantic==2.13.4` output before writing this, so everything below is measured rather than read.

**It works, and the parts that are easy to get wrong are right here.** The motivating shape resolves completely, the `~1`/`~0` decoding is applied in the RFC 6901 order, the `seen` guard preserves a recursive `$ref` instead of expanding it, and `setdefault` keeps sibling keywords rather than letting the referent overwrite them. Moving `pop` → `get` is the right call independent of everything else.

**Three ordinary Pydantic types still come out with an unresolved `$ref`**, which means `extract_types_from_schema()` still falls back to `["string"]` for them — i.e. the double-encoding this PR exists to fix is still live for those arguments:

| model field | emitted by pydantic as | after `_resolved_tool_properties` |
|---|---|---|
| `period: Inner` *(control)* | `{"$ref": …}` | resolved ✅ |
| `many: List[Inner]` *(control)* | `items: {"$ref": …}` | resolved ✅ |
| `lookup: Dict[str, Inner]` | `additionalProperties: {"$ref": …}` | **`$ref` survives** ❌ |
| `pair: Tuple[Inner, Inner]` | `prefixItems: [{"$ref": …}, …]` | **`$ref` survives** ❌ |
| draft-07 tuple | `items: [ … ]` (a list) | **not descended** ❌ — the guard is `isinstance(value, dict)` |

The recursion in `_resolve_refs` enumerates `anyOf`/`oneOf`/`allOf`, `properties` and dict-form `items`, so anything in another subschema-bearing position is copied through untouched.

**Separately, a pointer *into* a definition is not resolved.** `def_name` is the whole tail, so

```json
{"$ref": "#/$defs/T/properties/kind"}
```

looks for a definition literally named `T/properties/kind`, finds none, and returns the raw ref. That matters more here than in a library that only ever sees pydantic output, because tool schemas on this path are **caller-supplied** — any OpenAI-compatible client can post arbitrary JSON Schema — and `zod-to-json-schema` emits exactly this form for a re-used sub-schema (`z.object({a: Inner, b: Inner.shape.one})`).

**A fix for both, verified on the four shapes above** (control unchanged, `Dict`/`Tuple` resolved, recursive `Node` still correctly left as a `$ref`):

```python
# 1. resolve the tail against the document instead of assuming it is one name
tail = ref_path[len(ref_prefix):]
toks = [t.replace("~1", "/").replace("~0", "~") for t in tail.split("/")]
for n in range(len(toks), 0, -1):            # longest literal name first
    name = "/".join(toks[:n])
    if name not in defs:
        continue
    cur, ok = defs[name], True
    for t in toks[n:]:                        # then walk what is left
        if isinstance(cur, dict) and t in cur:
            cur = cur[t]
        elif isinstance(cur, list) and t.isdigit() and int(t) < len(cur):
            cur = cur[int(t)]
        else:
            ok = False
            break
    if ok and isinstance(cur, dict):
        ...                                   # existing setdefault + recurse

# 2. descend the other subschema positions
elif key in ("anyOf", "oneOf", "allOf", "prefixItems") and isinstance(value, list): ...
elif key in ("items", "additionalProperties") and isinstance(value, dict): ...
```

(Longest-first matters if you ever see a definition whose *name* contains a `/` — `zod-to-json-schema` reproduces the name you pass it verbatim, so `zodToJsonSchema(s, "v1/User")` produces both `#/definitions/v1/User` and pointers into it, and the two spellings are indistinguishable without consulting the document.)

**Test-design note.** `TestRefResolutionOnRequestPath` uses the `period: Inner` shape, which is exactly the case that already works — so a regression test built on it passes with or without the three fixes above. The distinguishing fixture is a `Dict[str, Model]` or a `Tuple[Model, Model]` argument, asserting that the resolved properties contain no `"$ref"` anywhere, rather than asserting the resolved shape.

**The three missed subschema positions are real as unresolved refs, but they are not currently observable.** I checked `ParserEngine._coerce_value` rather than assuming: its dict branch only consults `schema["properties"]` and its list branch only dict-form `items`. `additionalProperties`, `prefixItems` and list-form `items` are never read, so whether the `$ref` under them is resolved makes no difference to the emitted arguments. | shape | `$ref` survived | arguments |
|---|---|---|

I've descended them anyway (plus `contains` and `not`) — it's a few lines and it stops the gap from becoming live the moment `_coerce_value` learns about those keywords — but I don't want the PR to claim it fixes something that was not broken.

**One thing your review did not cover, which I'd rather flag than quietly fix here.** `_coerce_value` returns early for string values — it json-parses and returns without descending — and on the XML parameter path every value arrives as a string.
