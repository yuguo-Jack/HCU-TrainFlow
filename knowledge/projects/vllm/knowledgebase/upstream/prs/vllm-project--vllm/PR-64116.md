# [Perf][Model Runner V2] Pass a shared top_k to FlashInfer sampling as an int

[Upstream PR](https://github.com/vllm-project/vllm/pull/64116) · state: open · merged: False

## Original PR description



## Overview

FlashInfer 0.7.2 has a faster path in `top_k_top_p_sampling_from_logits`: it selects the top k first, then runs softmax and top-p over only those k values (flashinfer-ai/flashinfer#3461). It only takes that path when `top_k` is a Python int, and the Model Runner V2 sampler always passes a per-row tensor. This PR passes an int when every request in the batch has the same top_k, which is the default for models whose `generation_config` sets one (Qwen3 uses 20, Gemma 64).

## Claims

- `flashinfer_sample` with top_k 20 and top_p 0.95 is 2.3-3.3x faster on B200, and 1.4-3.1x faster on H100 at batch 32 and above or vocab 262144 (1.0-1.13x at vocab 151936, batch 1-8).
- Qwen3-8B on one H100 with its default sampling parameters: TPOT -0.4% at batch 1, -0.8% at 32 and -2.9% at 256.
- Batches with mixed top_k, or with greedy, seeded or processed-logprob requests, take the same path as before. The KV cache size does not change.

Sampling op:

```python
import torch
from flashinfer.testing import bench_gpu_time_with_cupti
from vllm.v1.sample.ops.topk_topp_sampler import flashinfer_sample

batch, vocab = 32, 151936
logits = (torch.randn(batch, vocab, device="cuda") * 4).to(torch.bfloat16).float()
top_p = torch.full((batch,), 0.95, device="cuda")
for top_k in (torch.full((batch,), 20, dtype=torch.int32, device="cuda"), 20):
    times = bench_gpu_time_with_cupti(
        lambda: flashinfer_sample(logits, top_k, top_p),
        dry_run_iters=10, repeat_iters=100, cold_l2_cache=True,
    )
    print(type(top_k).__name__, sorted(times)[len(times) // 2] * 1e3, "us")
```

## Details

- Semantics: The fast path keeps exactly k tokens, while the per-row path keeps every token tied with the k-th logit. I checked how much that matters on real traffic by recording the logits the sampler hands FlashInfer for 128 chat requests x 384 tokens, with each model's default parameters, and comparing the two distributions exactly:

  | model | decode steps | k-th logit tied | token k survives top_p | mean TV | max TV |
  |---|---|---|---|---|---|
  | Qwen3-8B | 49,152 | 24% | 0 | 3e-07 | 0.0104 |
  | Qwen3-30B-A3B | 49,152 | 26% | 0 | 2e-07 | 0.0095 |

  Ties are common, but top_p 0.95 already drops the token at position k, so the distribution barely moves: 1 step out of 98,304 had a total variation above 0.01. Seeded requests never use FlashInfer, so seeded outputs do not change.
- No GPU sync: `get_uniform_top_k` reads the CPU copy of top_k that the sampler already keeps, so there is no GPU sync.
- Profiling: Since #57926 the profiling pass gives every request `SamplingParams.for_sampler_warmup()`, which now shares one top_k and would take the fast path. The per-row path needs two more batch x vocab fp32 buffers (1,188 MiB at 1024 x 151936), so a later mixed batch would use memory the profiler never saw. The profiling pass now alternates top_k to keep those buffers in the measured peak. The fast path itself peaks at 0.33 MiB and keeps nothing between calls beyond FlashInfer's fixed 1 MiB top-k scratch buffer (H100 and B200).
- JIT: The warmup after KV cache allocation samples with one shared top_k, so it already exercises the fast path and its FlashInfer `topk` module before serving.
- CI coverage: These tests run on H200 MIG slices in CI, and the FlashInfer sampler needs more than 16 SMs. The dispatch test stubs `flashinfer_sample`, so it runs on any CUDA GPU. The distribution test skips wherever the FlashInfer sampler is unsupported, like the rest of `TestFlashInferDistributionMatch`.
- Related PRs: #60993 (opt-in Cake sampler), #62612 (fp64 Gumbel with FlashInfer), #62512 (sampler JIT overlap). None of them changes how top_k is passed to `top_k_top_p_sampling_from_logits`.
