# [ROCm][Perf] Allow DSA indexer native decode above next_n=2

[Upstream PR](https://github.com/vllm-project/vllm/pull/59421) · state: open · merged: False

## Original PR description

## Purpose

On ROCm, `_supports_native_decode` is `next_n in (1, 2)`, so MTP with 2+ speculative tokens is flattened to one row per draft token and each row re-reads its sequence's KV. The AITER paged kernels have no such limit. This adds `VLLM_ROCM_INDEXER_NATIVE_DECODE_MAX_NEXT_N` (default 2, today's behaviour) to raise the cap.

**Needs #59420** above `next_n = 2` (otherwise `Memory access fault` in warm-up).

## Test Plan

GLM-5.3, TP4, MI355X, `deepseek_mtp`, cap = 8, Gluon decode, #59420 applied, CUDA graphs on. Throughput sweep, GPQA Diamond, RULER niah_single_2 (64k).

A correctness dependency to account for here: #64855 reports ragged native decode selecting wrong KV rows, including the `next_n > 2` case this PR enables.

At `c5a1ecb7`, the source still has both reported patterns:

- [`use_native`](https://github.com/vllm-project/vllm/blob/c5a1ecb72790ab6077464b0d11c360c72c61a5ef/vllm/v1/attention/backends/mla/indexer.py#L1630-L1644) checks the step maximum/cap, without excluding requests with `0 < decode_len < max_decode_len`. The native bound still subtracts `max_decode_len`, rather than each request's length.
- The ROCm path packs Q by request, then passes token-order `weights[:num_padded_tokens]` unchanged ([source](https://github.com/vllm-project/vllm/blob/c5a1ecb72790ab6077464b0d11c360c72c61a5ef/vllm/v1/attention/ops/rocm_aiter_mla_sparse.py#L1504-L1532)). After a short request, those rows no longer align.

Could the ragged-step fallback from #64855 be included or tracked as a dependency, retaining uniform and zero-length tail-padding controls? This is a source-only cross-check, not an independent ROCm/CUDA or model run; the GPU validation in that report belongs to its author. AI-assisted review.
