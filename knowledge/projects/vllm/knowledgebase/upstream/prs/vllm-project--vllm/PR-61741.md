# [Core][Scheduler] Context-aware long prefill chunking

[Upstream PR](https://github.com/vllm-project/vllm/pull/61741) · state: open · merged: False

## Original PR description

`--long-prefill-token-threshold` cuts a long prefill into fixed-size chunks so it can't eat the whole token budget. That bounds how many prefill tokens land in a step, but not how long the step takes

Each chunk token attends over everything already computed for that prompt, so the per-token cost of a chunk grows with how deep into the prompt it is. With a very long cold prompt the same threshold-sized chunk gets slower and slower as the prefill goes on, and every decode batched with it waits on that step. Everyone else's TPOT climbs for as long as the long prefill runs, and it's worst near the end of the prompt

This adds an opt-in context budget that shrinks the cap as the prefill's context grows, so each chunk costs about the same however far into the prompt it is:

```
cap = budget / (1 + num_computed_tokens / scale)
```

with a small floor so huge prompts keep making progress, and never above the existing threshold

- it only kicks in where `long_prefill_token_threshold` already caps a chunk, so a request alone in the batch is still never capped (there's nobody to stall)
- ordinary prompts keep the plain threshold, it only applies to prefills with a lot left to do or a lot of context already computed (both gates are derived from the scale)
- with the default budget of 0 the helper returns exactly the old cap
- setting the budget without a threshold raises an error instead of silently doing nothing
- encoder-decoder models already zero the threshold, they zero the budget too

The trade-off is the long prompt's own TTFT. It gets more, smaller chunks, so it finishes later. That's the right call for interactive multi-tenant serving where one huge prompt shouldn't stall everyone else, and it's why this is off by default

Flags:

- `--long-prefill-context-budget` (default 0, off): the chunk cap at zero context
- `--long-prefill-context-scale` (default 262144): the context depth at which the cap halves. It roughly tracks where a chunk's attention cost catches up with its dense cost, so it depends on the model and backend, dense attention probably wants a smaller value than sparse MLA

Heads up: the cap produces more distinct chunk sizes than a fixed threshold. On backends that specialize kernels on token count, the very first long prefill at new chunk sizes can hit one-time Triton compiles and stall for a bit. After that the shapes are cached

It's plain integer math in the scheduler, no new state and no new CPU/GPU sync

Related: #61080 (defer mode) and #58420 (SRPF) change which prefill runs, this changes how big each chunk is. They don't touch the same code
