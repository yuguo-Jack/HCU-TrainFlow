# [Core][KV Connector] Share in-flight external-prefix KV loads

[Upstream PR](https://github.com/vllm-project/vllm/pull/57418) · state: open · merged: False

## Original PR description

Concurrent requests for the same externally cached prefix can allocate separate GPU destinations and transfer the prefix repeatedly. This change lets eligible requests share pending GPU blocks and wait for one load.

The block pool indexes exact pending prefixes by the existing hash/group namespace and pins their blocks with transfer-owned references. Pending entries are separate from readable prefix-cache hits; failed loads cannot be discovered, and completion removes the pending entry and releases its pins. The scheduler retains connector eligibility, request waiters, and completion/failure-policy handling. Successful loads are published before releasing an aborted initiating request. Followers cancel independently; failed readers detach before local recomputation. Pending loads prevent connector-cache resets.

Initial support is explicitly opt-in for the built-in CPUOffloadingSpec with built-in LRU/ARC policies: prefix caching enabled, one FullAttentionSpec group, exact contiguous block-aligned partial-prompt prefixes, including prefixes extending a local hit. Full-prompt loads, speculation, context parallelism, encoder inputs, custom specs/policies, and other connectors retain existing behavior. Cache salts and token-hash isolation are preserved.

Addresses #44882. Duplicate checks covered issue comments, open PRs referencing the issue, and area searches. #48189 closed unmerged; #44295 changes connector convoy handling, rather than shared core allocation/lifetime. #53067 and #55724 address connector context and admission. NIXL is being pursued as a separate follow-up by NolenLiang.

`failed_recving` also needs to mark the shared load as failed. The connector contract guarantees that failed receives are included in `finished_recving`, but `_complete_shared_prefix_load()` only observes failures reported through `invalid_block_ids`.

If the owner reports `finished_recving={owner_id}` and `failed_recving={owner_id}` without invalid block IDs, the entry is still published through `cache_blocks()` and all followers are released. Under `failure_policy="fail"`, only the owner is failed; under `"recompute"`, only the owner is reset, so followers can run on the failed shared destination.

Please propagate request-level receive failure to the shared entry and all participants before publishing or waking them, and add tests for `failed_recving` under both failure policies, including the case where the owner has already been aborted. The tests should verify that followers either receive `FINISHED_ERROR` or release the shared blocks and recompute locally, and that failed blocks never enter the normal prefix cache.
