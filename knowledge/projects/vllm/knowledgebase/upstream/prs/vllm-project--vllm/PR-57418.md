# [Core][KV Connector] Share in-flight external-prefix KV loads

[Upstream PR](https://github.com/vllm-project/vllm/pull/57418) · state: open · merged: False

## Original PR description

Concurrent requests for the same external prefix currently allocate separate GPU destinations, or wait behind connector-side load gating. This change lets eligible followers attach to the initiating request's blocks with ordinary block-pool reference counts and wait for one transfer.

The scheduler tracks exact pending prefixes using existing prefix-cache hashes. It publishes successful loads before releasing an aborted initiating request and wakes every remaining follower. Cancelling a follower releases only its references. Failed loads either fail affected requests or detach all readers before recomputation; pending entries also prevent connector-cache resets.

Initial support is opt-in, enabled for the built-in CPUOffloadingSpec with built-in LRU/ARC policies: prefix caching enabled, one FullAttentionSpec group, exact contiguous block-aligned partial-prompt hits, including hits extending a local prefix. Full-prompt hits, speculative decoding, context parallelism, encoder inputs, custom specs/policies, and other connectors retain existing behavior. Cache salts and token-hash isolation remain intact.

Addresses #44882. Duplicate checks covered the issue comments, open PRs referencing the issue, and related area searches. #48189 was closed without merging. Open #44295 changes connector-side convoy handling; it does not implement shared core allocation or this lifecycle. #53067 and #55724 address connector context and async admission respectively.

- GentleCold · comment · 2026-09-18T06:31:55Z · [source](https://github.com/vllm-project/vllm/pull/57418#issuecomment-5726141463)

`failed_recving` also needs to mark the shared load as failed. The connector contract guarantees that failed receives are included in `finished_recving`, but `_complete_shared_prefix_load()` only observes failures reported through `invalid_block_ids`.

If the owner reports `finished_recving={owner_id}` and `failed_recving={owner_id}` without invalid block IDs, the entry is still published through `cache_blocks()` and all followers are released. Under `failure_policy="fail"`, only the owner is failed; under `"recompute"`, only the owner is reset, so followers can run on the failed shared destination.

Please propagate request-level receive failure to the shared entry and all participants before publishing or waking them, and add tests for `failed_recving` under both failure policies, including the case where the owner has already been aborted. The tests should verify that followers either receive `FINISHED_ERROR` or release the shared blocks and recompute locally, and that failed blocks never enter the normal prefix cache.
