# [Perf][DSv4.1] DeepSeek-V4.1-Flash specialized decode on GB300

[Upstream PR](https://github.com/vllm-project/vllm/pull/61868) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

This PR adds an NVIDIA specialized decode for DeepSeek-V4.1-Flash on GB300, for the small decode batches that agentic serving runs. It supports:
- one GB300 tray at TP4;
- DSpark speculative decoding with 5 draft tokens;
- FULL-graph decode steps of up to 384 rows (64 requests × 6 tokens). Prefill, mixed batches and larger batches fall back to the stock forward.

It is opt-in via `--additional-config '{"decode_backend": "latency_specialized"}'`, the same switch as #61867. With the default (`auto`), the model runs exactly as on upstream `main`. The model changes are all under `vllm/models/deepseek_v41/nvidia/`; outside it, the PR only adds tests and a CI step.

The integration follows #61867: the model owns a decode executor that takes over FULL-graph decode steps. The stacked follow-up #61869 puts the DSpark draft model on the same executor. Both follow the RFC #59665 fast-track process. Related: #57448 (DeepSeek-V4.1 tracking), #59725 (Cake kernels).

## Claims

DeepSeek-V4.1-Flash on one GB300 tray with DSpark, the same build with the switch on and off:
- Decode step (one speculative step, including the draft): **18.3% faster at batch 1** (5,355 → 4,375 µs), 13.7% at batch 8 and 11.3% at batch 32.
- InferenceX AgentX traces: **P90 interactivity up 16–24%** at every concurrency from 1 to 64, with throughput per GPU up 1–6% and TTFT unchanged.
- GSM8K, GPQA-Diamond, AIME25 and RULER NIAH stay within one point of the switch-off model, and the DSpark acceptance length does not change.

## Details

### Where the time goes

Agentic workloads such as AgentX send long multi-turn conversations (median 350K tokens of context, almost all prefix-cached) and wait for each reply before sending the next turn. Each server therefore decodes only 1 to 64 requests at a time, and users see the time per output token.

At batch 1, stock vLLM's speculative step takes about 5.4 ms: one target forward that verifies six tokens, plus the DSpark draft. There is no single hotspot.

- **GPU.** A step runs about 1,600 kernels, most of them a few microseconds long. One target layer without an indexer is a serial chain of about 105 µs: about 50 µs of attention (quantize, `wq_a`/`wkv`, norm-quant, `wq_b`, KV insert, index build, `q_lens` and counter fixes, FMHA, `wo`, publish, all-reduce) and about 53 µs of MoE (front 14, GEMM1 19, GEMM2 12, finalize and all-reduce 6). The GEMMs see 1 to 48 rows but run kernels tuned for larger batches; the all-reduce + mHC at each of the 80 sublayer boundaries is fused only up to 16 rows; and layers with the sparse-attention indexer add their own chain of small kernels (logits, top-k and index tables).
- **Host.** The host loop is busy about 4.95 ms of the 5.37 ms step, and about 2.2 ms of that builds attention metadata for the target's and the draft's KV-cache groups. A GPU-only speed-up beyond about 0.4 ms would just expose the host.

So the executor removes kernels and launch gaps, uses kernels sized for 1 to 8 rows, moves independent work onto side streams, and takes host work out of the step loop.

### What changed

Each row is one optimization and the saving we measured when it was added, as a batch-1 decode-step ABBA on one tray unless a batch is named. They were measured one at a time on a development branch, so they do not add up exactly to the end-to-end figure. The full list of paths and their gates is in `nvidia/specialized_decode/AGENTS.md`.

| Optimization | Why | Saving when added |
| --- | --- | --- |
| **Fused all-reduce + mHC** | | |
| One fused Lamport all-reduce + mHC kernel at every sublayer boundary up to 384 rows (stock: 16). The next layer's mHC coefficients are computed on a side stream up to 48 rows. | Above 16 rows, the stock path runs a separate all-reduce, mHC and copies at each boundary. | −11.4% at batch 8 (48-row cap); −4.5% at batch 32 (384-row cap) |
| The fused kernel also writes the next attention input as MXFP8. | That removes a separate quantize kernel per layer. | −54 µs |
| `wo_b`'s GEMM epilogue stores straight into the fused kernel's mailbox. | That removes a copy kernel; the fused kernel then only collects. | −41 µs |
| The MoE finalize is deferred into the fused kernel at the Engram and final boundaries too, in a residual-only variant. | These boundaries previously ran the finalize and all-reduce separately. | −36 µs |
| The aux hidden-state means for DSpark are computed on the mHC side stream. | They were on the critical path. | −23 µs |
| **GEMMs for 1–8 rows** | | |
| Routed experts: one fused front kernel (routing, MXFP8 quantization, permutation) and two `tcgen05` GEMM kernels, all in CuTe DSL. The top-k reduction is left to the next boundary's fused kernel. | FlashInfer's TRT-LLM-gen MoE path is tuned for larger M and launches more kernels. | −192 µs (GEMMs), −114 µs (front and finalize) |
| `fused_wqa_wkv`, `wq_b` and `wo_b` on FlashInfer's low-latency CuTe DSL MXFP8 GEMM, with tactics pinned per shape. | The stock MXFP8 GEMM is a persistent kernel sized for larger batches. Pinning keeps the fastest measured tactic per shape instead of the autotuner's pick. | −53 µs, then −62 µs from pinning |
| Compressor, indexer-weight and indexer `wk` projections on vLLM's low-batch BF16 split-K GEMM. The index key store reads `wk`'s FP32 output. | At 1–8 rows these skinny GEMMs give cuBLAS few output tiles; split-K spreads the long K over the SMs. | −60 µs |
| LM head on FlashInfer's CuTe DSL BF16 GEMM, and logits gathered with the custom all-gather. | The stock path uses cuBLAS plus an NCCL all-gather. | −15 µs, −27 µs |
| **Sparse-attention indexer and attention** | | |
| Compressed layers that share an index source reuse one sparse-index table. Sparse-MLA decode launches on a KV-counter buffer that is zeroed once. | Each layer rebuilt the same table and zeroed counters before every launch. | −207 µs (1,578 → 1,486 kernels per step) |
| The tables of every KV-cache group are built once per key, on a side stream. | Each group rebuilt its tables serially. | −103 µs |
| Candidate blocks are selected with `cooperative_topk` over the valid columns. | The stock top-k scans the padded width. | −86 µs |
| Indexer query, compressor and index-key work, and candidate expansion with its MQA-logits schedule, run on side streams. Each joins at its first reader. | They are independent of the attention chain until then. | −50 µs, −33 µs |
| Dense indexer rows are sharded over the TP ranks and all-gathered, on pure-decode steps of at least 8 requests. | The indexer is replicated on every rank, and its cost grows with batch and context. | −1.9% at batch 8, −7.6% at batch 32 |
| **Host and launch overhead** | | |
| Attention-metadata builds are recorded into CUDA graphs at capture, one per decode batch shape and KV-cache group, and replayed. | These Python and Triton builds were about 2 ms of the host loop. | −86 µs, then −27 µs |
| Each Engram layer's KV projection chain (table-row lookup, all-gather, MXFP8 quantize, `wkv` GEMM) runs ahead of the layer on the Engram prefetch stream. | It reads only table rows looked up from the token IDs, so it need not wait for the layer's input. Each Engram layer's main-stream span drops from 70 to 6 µs. | −90 µs |
| Decode steps skip the per-request replay-start upload when the device already holds zeros. | Decode steps only ever upload zeros. | −24 µs |

### vLLM integration

As in #61867, the model owns a decode executor (`specialized_decode/runtime/decode.py`). With the switch on, the model returns a model state subclass (`specialized_decode/runtime/model_state.py`) that builds the executor once the weights are loaded, then tunes and compiles its kernels before memory profiling. For each forward, the model asks the executor for a step (`plan()`). Only FULL-graph captures of pure decode steps of up to 384 rows get one. The backbone runs its embedding and Engram hashing as usual, then hands its decoder layers to the step (`run()`). Every other forward runs the stock layers, which the executor does not modify.

| Package (`nvidia/specialized_decode/`) | Contents |
| --- | --- |
| `__init__.py` | The opt-in, and `unsupported()`, which lists every requirement the deployment misses |
| `runtime/` | The executor and its per-step gates, the model state, warm-up, attention-metadata CUDA graphs |
| `boundary/` | The mHC between sublayers on the fused all-reduce + mHC kernel, and the publishing `wo_b` GEMM |
| `attention/` | Low-batch MXFP8 and BF16 projections, the row-sharded indexer, candidate overlap, shared sparse-index tables and the sparse-MLA decode |
| `moe/` | The MoE step with a deferred finalize, and the low-batch routed-expert kernels in CuTe DSL |
| `engram/` | The Engram KV projection ahead of the decoder layers |
| `logits/` | The low-batch LM head and the logits gather |

**Scope.** The switch is validated on one deployment:
- GB300 (SM103), MRV2, TP=4, with no PP, DP, EP or CP and no micro-batching;
- DSpark without adaptive verification;
- `FLASHINFER_MLA_SPARSE_DSV41` with an fp8 KV cache and the MXFP4 indexer with sparse logits;
- FULL graphs for decode only;
- no `torch.compile` of the model (the executor runs inside the forward), and no sleep mode (the routed-expert GEMMs and the publishing `wo_b` bind weight addresses);
- DeepGEMM and NVLink multicast;
- no LoRA, KV transfer or batch invariance.

Any other deployment raises at start-up on every TP rank, listing every missing requirement. Eligibility is combined across ranks with a MIN all-reduce, so ranks always agree. We made it an opt-in because the set is validated end to end on this one deployment; within it, each path still dispatches at run time on host state that every rank shares, as #59665 asks. It can become the default on that deployment in a follow-up.

**Rank lockstep.** The paths contain cross-rank collectives, so a rank that diverged would hang rather than fall back. Every per-step gate therefore reads only host state that all TP ranks share: row and request counts, and the graph mode. Nothing is read back from the GPU in steady state. For example, the row-sharded indexer runs only on even row slices, because DeepGEMM's paged MQA logits need 8-byte-aligned indices on every rank.

**With the switch off.** Inside `nvidia/`, the shared files take small seams with the same behavior:
- `model.py`: the backbone hands its decoder layers to the executor's step when it gets one, and the model picks the model state class;
- `model_state.py`: the replay-start upload and the attention-metadata build become methods, which the executor's model state overrides;
- `vl_model.py`: takes the model state class from the language model;
- `ops/o_proj.py`: a `wo_b_proj` keyword for the publishing `wo_b`;
- `ops/cute_dsl/all_reduce_mhc.py`: the fused all-reduce + mHC source is parameterized by its row count and variants, and built at 16 rows as before when the switch is off.

**FlashInfer version.** Three paths use FlashInfer internals: the publishing `wo_b` GEMM, the fused kernel's MXFP8 layer input, and the pinned MXFP8 GEMM tactics. They run only on `flashinfer-python==0.7.2`, the version `main` pins; the internals they use are unchanged from 0.7.1, where they were first checked. On any other version, each warns once and takes the stock path, so a FlashInfer bump should recheck them.
