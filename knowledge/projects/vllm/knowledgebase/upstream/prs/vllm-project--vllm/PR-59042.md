# [Bugfix][MoE] Apply expert_map remapping for CUTLASS FP4 MOE expert parallel

[Upstream PR](https://github.com/vllm-project/vllm/pull/59042) · state: closed · merged: True

## Original PR description

## Purpose
Fixes silent MoE corruption when running CUTLASS NVFP4 or MXFP4 MoE with expert parallelism.

CutlassExpertsFp4 and CutlassExpertsMxfp4 accepted expert_map in apply() but never used it. With EP enabled, `topk_ids` stayed in global expert space while weights are local, so tokens were to the wrong experts. 
This showed up as degenerate outputs (e.g. ~0% GSM8K on RedHatAI/GLM-5.3-MXFP4 with DP=8 / EP=8 see issue #58729 ).

PR remaps global `topk_ids` local ids via `expert_map` before CUTLASS FP4/MXFP4 grouped GEMM.

Changes:
- Move the existing Triton `remap_topk_to_local` kernel from `gpt_oss_triton_kernels_moe.py` into `fused_moe/utils.py` and reuse it from both GPT-OSS Triton and CUTLASS paths.
- Add `out_dtype` support (int32 for CUTLASS, int64 default for GPT-OSS) in the `remap_topk_to_local` kernel.
- Fix misleading CutlassExpertsFp8 comment: FP8 EP already applies expert_map in moe_permute, not in the CUTLASS kernel itself.
- Relax `_supports_parallel_config` for `CutlassExpertsFp4` / `CutlassExpertsMxfp4`: allow EP with allgather_reducescatter; still block FlashInfer NVLink / DeepEP HT backends (same as FP8).
- `make_mxfp4_moe_kernel` validation so compressed-tensors CUTLASS bypass fails fast on unsupported parallel configs (adapted from #59033 ).
- Supersedes #59033 (guard-only PR that rejected all EP)
