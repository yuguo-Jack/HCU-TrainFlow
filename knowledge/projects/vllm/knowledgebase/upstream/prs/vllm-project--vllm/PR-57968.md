# [AuxOutput] Add Mooncake backend with keys-only R3 output

[Upstream PR](https://github.com/vllm-project/vllm/pull/57968) · state: open · merged: False

## Original PR description

## Summary

Add a Mooncake backend on top of the AuxOutput implementation merged in #45635.
This PR targets `main` and does not include the legacy commit stack.
It promotes the validated implementation reviewed in aoshen02/vllm#7 upstream.

Duplicate check: no open upstream PR implements this keys-only R3 storage
backend. #57966/#57025 concern prefix omission/KV-offload compatibility, not
publishing complete R3 to Mooncake for external retrieval. The fork PR is the
earlier review copy, not a separate upstream proposal.

```text
GPU worker R3 -> existing background writer -> Mooncake full blocks
EngineCore   -> clip accepted boundaries    -> Mooncake boundary/tail objects
TITO HTTP    -> ordered aux_output_keys only
trainer      -> get(keys), concatenate      -> complete R3
```

- Reuse native Mooncake batch I/O, existing configuration/setup and background
  writer. SHM remains the default.
- Return keys on the terminal TITO response, including stored partial tails;
  no inline R3 with Mooncake. Publication completes before exposing final keys.
  Requests with string stops publish incremental keys internally so API-side
  termination can deliver complete R3; HTTP still exposes keys only at completion.
- Share full-block keys across instances and DP ranks using block hash and
  reset generation. P/D must use the same generation, model/R3 profile,
  hash configuration/seed, block size and Mooncake store.
- No new RPC, ACK protocol, publisher thread, TTL registry or retry state.
  Retention is deployment-owned; missing/evicted objects fail explicitly.
- EngineCore owns a separate client for boundaries finalized after Scheduler
  stop/length handling. Scheduler shutdown closes it; closing the Worker client
  in another process cannot release it. This does not delete remote objects.

## Profiling follow-up (2026-09-22)

Same frozen runtime and 256K/four-turn workload as above, one DP4 deployment,
32 concurrent conversations, cross-host RDMA retrieval with four native readers.
Each backend has two unprofiled controls and one profiled run (Slurm 29958.60).

Mean control throughput: **SHM 0.596435 vs Mooncake 0.743928 request-turns/s
(+24.7%)**. Mean workload duration: 214.65s vs 172.07s; about 95% of the time
saved is in the three warm/prefix-reuse turns. This compares complete delivery
paths, not intrinsic RDMA versus shared-memory read speed.

Mean per-request Mooncake costs over 192 warm requests in the two controls:

| Stage | Wall time |
| --- | ---: |
| Native batch get, including lookup/transfer/wait | 526 ms |
| Copy buffers to bytes and release handles | 36.5 ms |
| Final bytes concatenation | 10.2 ms |
| Whole get_concatenated, including the above | 578 ms |
| Separate per-client lock wait | 1486 ms |

SHM materializes R3, encodes NumPy/Base64 and sends it through HTTP; Mooncake
returns keys and fetches raw bytes separately. Mean warm-request HTTP completion
is 17.88s vs 4.26s; post-HTTP retrieval/decoding/checking is 1.84s vs 2.45s.
Mooncake therefore adds post-HTTP work but saves substantially more on HTTP delivery.

For 128 profiled requests, the client HTTP read chain consumes 97.49 vs 6.28
CPU seconds, JSON decoding 8.23 vs 0.77; SHM also spends 14.04 CPU seconds on
Base64 decoding. HTTP body volume is 11.61 GB vs 0.89 GB, with Mooncake still
fetching another 8.71 GB of raw R3. The dominant observed saving is avoiding the
large Python HTTP/JSON/Base64 path, not eliminating data transfer or concatenation.
Mooncake publication/flush waiting is higher; not every stage is faster.

Profile timings are inclusive CPU totals, not additive request latency.
Profiling reduces throughput by 11.8% (SHM) and 3.3% (Mooncake); the table and
throughput comparison use unprofiled controls. Native API time is not pure RDMA
wire time, and exported function profiles do not fully account for native CPU.
The SHM after-control used a restarted, re-warmed server after a profiler-export
failure. These two controls are not a confidence interval.

All six phases passed 768 request checks and 576 cached-prefix R3 equality
checks, with identical prefix-hit counts and zero preemptions. This retains the
fixed-token/model-weight, memory-capacity and frozen-image limitations above;
it does not establish model quality or cross-backend bitwise equality.

## Mooncake PD + R3 handoff (2026-09-22)

Enable `MooncakeConnector` with the Mooncake Aux backend. P runs the full
prompt with `max_tokens=1` and no R3 prompt cropping; D receives the same prompt
and the normal KV-transfer parameters plus:

```json
"aux_output_prefix": {"block_size": 4, "keys": ["<P full block>", "<P tail>"]}
```

The block size is the R3/hash granularity (4 in this test), not the KV page size.
D reuses shared full-block keys directly. Scheduler sends only the key for
an unaligned first-forward boundary; Worker restores that block's missing
prefix and joins newly computed R3. Aligned starts require no restore read.
No full-prefix import or republication is needed. P objects remain immutable;
the caller must keep source objects available.
The configuration-level KV connector/PD blacklist has now been removed for
both Aux backends. This is not a claim that every connector/backend implements
remote R3 handoff; this PR's tested handoff is Mooncake PD + Mooncake Aux.

Identical keys retain the first published value. After a cache miss and
recomputation, returned R3 may therefore differ from the latest execution.
This is an explicit accepted limitation; no overwrite or version mapping
is introduced. Fresh tail keys can also wrap slices of older full objects.
