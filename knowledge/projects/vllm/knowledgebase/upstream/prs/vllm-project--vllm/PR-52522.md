# [Feature] Batch-invariant support for speculative decoding

[Upstream PR](https://github.com/vllm-project/vllm/pull/52522) · state: open · merged: False

## Original PR description

## 1. Summary

This PR extends batch invariance to stochastic speculative decoding. A seeded
request now follows the same sampling and speculative-decoding path when batch
size, request order, or scheduling changes, including KV-cache preemption.

The implementation has two main parts:

~~1. Independent deterministic RNG streams for proposal sampling, acceptance,
   and residual sampling.~~
**Update on 8.27:** RNG-stream separation is handled separately in woosuk/mrv2-draft-gumbel-decouple branch. In particular, [commit 214a205](https://github.com/vllm-project/vllm/tree/woosuk/mrv2-draft-gumbel-decouple) separates draft Gumbel noise from acceptance/recovery noise. Since that issue is orthogonal to speculative batch invariance, I’ve removed the RNG-domain changes from this PR.

2. Preemption recovery that reconstructs the discarded proposal at the same
   logical boundary before verification.

The validated methods are EAGLE3, DFlash, and DSpark with probabilistic draft
sampling and standard rejection sampling. I didn't find a proper model with MTP to
test, because GDN hasn't been supported with batch-invariance now.

An exact open-PR search for speculative batch invariance found no duplicate.
Related issue: https://github.com/vllm-project/vllm/issues/27433. Broader searches 
found adjacent batch-invariance and speculative-decoding work,
but none covering this proposal RNG and preemption-recovery design. No issue
number was provided for an issue-specific duplicate check. AI assistance was
used for implementation, review, testing, and documentation. The human
submitter remains responsible for reviewing every changed line and reproducing
the reported tests before submission.

## 2. Method

~~### 2.1 Independent deterministic RNG streams~~

~~Proposal, acceptance, and residual sampling use separate RNG domains. Each draw
is derived from the request seed and its logical token position, so unrelated
requests cannot change its random sequence through batching or scheduling. The
bonus target token continues to use the normal target-sampling stream.~~

### 2.2 Preemption recovery and KV-cache boundary

A speculative proposal spans two scheduler steps: one step creates `K` draft
tokens, and the next verifies those tokens plus one bonus target token. If the
request is preempted between these steps, retaining only the request tokens is
not enough: the proposal and the worker-side hidden state used to create it have
been released.

For example, let the request contain `L = 4` committed tokens:

```text
A B C D
```

Before preemption, the proposal is produced as follows:

```text
execute C -> target hidden state h_C
sample D from h_C
draft from (h_C, D) -> P1 P2
```

The logical state is therefore:

```text
computed tokens:       A B C
sampled next token:          D
pending proposal:              P1 P2
```

On preemption, the scheduler records only the proposal length (`K = 2`) and
uses the normal cleanup path to release KV-cache blocks and worker state. On
recovery it performs:

```text
prefix-cache hit:      A B       # at most L - 2 tokens
replay:                    C     # reconstruct h_C
known next token:             D
regenerate:          (h_C, D) -> P1 P2
verify atomically:               P1 P2 + bonus token
```

An `L - 1` hit would cache `A B C` and skip the forward pass for `C`. Its KV
entries are available, but `h_C`, which the drafter needs, is not. Executing
`D` instead would advance to `h_D` and build the proposal for the next logical
position. Limiting the hit to `L - 2` therefore recreates the same `(h_C, D)`
input and, with the position-based draft RNG stream, the same proposal as the
non-preempted execution. Scheduling the subsequent `K + 1` verification as one
unit prevents another partial boundary from being introduced.

## 3. Evaluation

### 3.1 Serving configuration

The two runs for each method use the same target/speculative model pair and
change only `VLLM_BATCH_INVARIANT`.

| Method | Target model | Speculative model | Speculative tokens |
| --- | --- | --- | ---: |
| EAGLE3 | `Qwen/Qwen3-8B` | `RedHatAI/Qwen3-8B-speculator.eagle3` | 3 |
| DFlash | `Qwen/Qwen3-8B` | `z-lab/Qwen3-8B-DFlash-b16` | 16 |
| DSpark | `Qwen/Qwen3-4B-FP8` | `deepseek-ai/dspark_qwen3_4b_block7` | 7 |

The command below uses placeholders so that the same serving setup can be
reused for each row.

```bash
export TARGET_MODEL="TARGET_MODEL_ID"
export DRAFT_MODEL="DRAFT_MODEL_ID"
export SPEC_METHOD="eagle3"       # eagle3, dflash, or dspark
export SPEC_TOKENS="3"            # 3, 16, or 7 respectively
export SPEC_CONFIG="{
  \"model\": \"${DRAFT_MODEL}\",
  \"method\": \"${SPEC_METHOD}\",
  \"num_speculative_tokens\": ${SPEC_TOKENS},
  \"draft_sample_method\": \"probabilistic\",
  \"rejection_sample_method\": \"standard\",
  \"enable_adaptive_verification\": false
}"

# BI off
VLLM_USE_V2_MODEL_RUNNER=1 VLLM_BATCH_INVARIANT=0 \
vllm serve "$TARGET_MODEL" \
  --max-model-len 2048 \
  --enable-prefix-caching \
  --enable-chunked-prefill \
  --async-scheduling \
  --speculative-config "$SPEC_CONFIG"

# BI on
VLLM_USE_V2_MODEL_RUNNER=1 VLLM_BATCH_INVARIANT=1 \
vllm serve "$TARGET_MODEL" \
  --max-model-len 2048 \
  --enable-prefix-caching \
  --enable-chunked-prefill \
  --async-scheduling \
  --speculative-config "$SPEC_CONFIG"
```

For DSpark, the evaluation added `"attention_backend":"FLASH_ATTN"` to
`SPEC_CONFIG`. DFlash used `--max-num-seqs 128` for model warmup.

### 3.2 GSM8K end-to-end results

All 1,319 GSM8K test examples were served twice per configuration: concurrency
32 in natural order and concurrency 64 in reverse order. Every request used a
stable unique seed with temperature `0.6`, top-k `20`, top-p `0.95`, and at most
256 output tokens. Exact BI requires identical token IDs, text, and finish
reason between the two phases. Accuracy and throughput below are from the
concurrency-64 phase.

| --- | --- | --- | ---: | ---: | ---: | ---: |
| EAGLE3 | off | FAIL | 401 | 88.32% | 28.92 | 3468.76 |
| EAGLE3 | on | PASS | 0 | 88.02% | 21.68 | 2614.11 |
| DFlash | off | FAIL | 187 | 87.79% | 11.08 | 1335.24 |
| DFlash | on | PASS | 0 | 87.79% | 10.50 | 1270.43 |
| DSpark | off | FAIL | 118 | 83.17% | 42.67 | 5398.54 |

| Method | Accuracy delta | Req/s delta | Output tok/s delta |

| DSpark | -0.23 pp | -3.26% | -4.24% |

These throughput runs validate invariance across concurrency and request order;
they did not trigger KV-cache preemption. The focused E2E test below uses a
small KV-cache allocation and asserts that preemption occurred before comparing
serial and batched token IDs.

### 3.3 Minimal tests

The first test checks independent RNG domains, batch splitting, and the target
bonus-token stream. The second forces speculative decoding and KV-cache
preemption, then checks exact batch invariance.

```bash
#!/usr/bin/env bash
set -euo pipefail

.venv/bin/python -m pytest -q \
  tests/v1/spec_decode/test_rejection_sampler_utils.py::test_spec_rng_streams_are_batch_invariant \
  tests/v1/e2e/spec_decode/test_stochastic_batch_invariance.py::test_spec_batch_invariance_with_preemption
```

The E2E test requires one CUDA GPU with at least 32 GB of memory and access to
the configured public model artifacts.
