# [ROCm][RDNA][Perf][MoE] Use w2 scatter + topk sum for the tk 3.8 OAI MoE combine on RDNA

[Upstream PR](https://github.com/vllm-project/vllm/pull/64055) · state: open · merged: False

## Original PR description



## Overview

On RDNA, combine the triton_kernels 3.8 OAI Triton MoE output the way v0.29's `matmul_ogs` did. The w2 `matmul` scatters its rows to token order, and `masked_moe_sum` adds the top-k rows. This replaces the fp32 `zeros` + `index_add_` + cast, which cost about 20% of gpt-oss-20b GPU time on gfx1201.

## Claims

- gpt-oss-20b on Radeon AI PRO R9700 (gfx1201): **+17.6% throughput** over main (10.57 → 12.43 req/s), 1.7% above v0.29 (12.22). Without this PR, main is 13.5% below v0.29.
- Radeon Pro W7900 (gfx1100): **+2.0%** over main (7.69 → 7.84 req/s, measured on main db3b0f0fae), level with v0.29 (7.86). The combine is cheaper on gfx1100 (about 45 µs vs about 590 µs per call), so the gain there is smaller.
- MoE output is **bitwise identical** to the `index_add_` path. GSM8K shows no change beyond run-to-run noise.
- No change outside RDNA: the new path, including building the scatter index, is gated on `on_rdna()`.

## Details

**Root cause.** #55934 moved the OAI Triton MoE to triton_kernels 3.8. Its `matmul` dropped `matmul_ogs`'s top-k reduce but kept the in-kernel row scatter (`scatter_indx`, see `matmul_details/_matmul.py`). The port passed `scatter_indx=None` and combined with an atomic fp32 `index_add_` instead. On gfx1201 that kernel runs at about 590 µs per call (about 1.8 µs per token) and is 19% of the forward.

**Change.** On RDNA, `RoutingData` (3.8) carries `scatter_indx`, the existing sorted-row → `token * topk + slot` order as int32 (otherwise `None`). w2 is called with it, so `y` comes out as `(M * topk, K)` in token order, and `masked_moe_sum` (now accepting `topk_ids=None`) sums each token's rows in fp32 and writes bf16. Same arithmetic, so the output is identical. Expert-map `-1` slots stay exact zeros, because the epilogue computes `(acc + bias) * gamma` with gamma 0.

**Split-K is unaffected.** 3.8 already disables split-K for ragged MXFP4 (`is_ragged_mx`), as `matmul_ogs` did (`not w_has_mx`).

**Why gate on RDNA.** That is the hardware validated here. CDNA and NVIDIA likely benefit too, but scatter changes the w2 store path there (for example, no TMA store on Hopper), so removing the gate needs validation by those owners.

**Limitations:**
- The scatter variant of the w2 `matmul` is a new Triton specialization. The JIT monitor logs one `define_kernel.<locals>._empty_fn` compile at first use, the same class of message the baseline already logs for `_topk_forward` and the bitmatrix kernels.
- `OAITritonExperts` (the modular / expert-parallel class) still uses `index_add_`.
