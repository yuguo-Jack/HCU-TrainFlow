# [ROCm][Perf] Triton sigmoid+bias top-k when MoE grouping eliminates nothing

[Upstream PR](https://github.com/vllm-project/vllm/pull/63076) · state: closed · merged: True

## Original PR description

## Overview

AITER `biased_grouped_topk` runs an LDS group scan even when the grouping cannot eliminate any expert — that is, when `topk_group >= num_expert_group`, so every group is selected. This adds a register-resident Triton sigmoid+bias top-k and substitutes it at `rocm_aiter_ops.biased_grouped_topk`, the single call site both ROCm routers reach.

Previously this PR specialised `rocm_aiter_grouped_topk` only. Moving it to the wrapper came out of review (thanks @simondanielsson) and covers both paths without touching routing metadata:

| caller | group arguments it passes |
|---|---|
| `GroupedTopKRouter` | the model's own `1/1` for a degenerate router |
| `FusedTopKBiasRouter` | a count synthesised to fit an AITER kernel — measured `2/2` for a 64-expert router — with `topk_group == num_expert_group` |

`vllm/model_executor/layers/fused_moe/experts/rocm_aiter_moe.py` is no longer modified; the diff is three files, additions only.

## Claims

- 1.67×–2.15× on the routing op on gfx942, and 1.16×–1.57× per shape on gfx950, under CUDA graph replay, across the configurations listed below.
- The gate stops at 512 experts and top-8. On gfx950 the kernel loses at top-16 (896-expert top-16 down to 0.62×), so those routers keep AITER — see *Scope and bounds*.
- Equivalent to the call it replaces whenever no group is eliminated, including `num_expert_group == topk_group > 1`, which is the shape `FusedTopKBiasRouter` produces.
- Eager execution is **not** faster, so it is excluded by the substitution rather than claimed as a win.
- Selected expert ids match AITER on 3323 of 3328 routing calls in a live Moonlight-16B-A3B forward and on 1248 of 1248 in Kimi-VL-A3B.
- **Scope: single-token batches only (`_MAX_TOKENS = 1`), as suggested in review**, i.e. one request decoding without speculation, which is where the end-to-end gain is. Larger batches keep AITER.
- End to end on MI355X with current `main`, five models with 64 to 384 experts, 1k to 32k context: **single-request decode is 0.4% to 4.2% faster on every model**, and higher concurrency is within noise; nothing regresses beyond the same-arm drift. GSM8K is unchanged on GLM-5.3-Flash and Kimi-K2.6. Earlier gfx942 runs were within noise.
- No new env var, and no change to router selection or to the advertised routing method.

## Dispatch scope: why this is restricted to CUDA graph steps

The kernel's advantage is device time. Timed from a plain Python loop it is *slower* — it is a Triton launch from Python against a single C++ dispatch, and that overhead is not amortised.

Because the gate is a token-count bound rather than an execution-phase check, eager steps can reach it, so this was measured end to end with `--enforce-eager`, interleaved B-A-B-A on Moonlight:

| in / out | concurrency | AITER tok/s | ungated PR tok/s | Δ | same-arm drift |
|---|---:|---:|---:|---:|---|
| 64 / 256 | 8 | 488.7 | 471.8 | **−3.5%** | 0.6% / 1.2% |
| 64 / 256 | 32 | 1910.4 | 1876.9 | **−1.8%** | 0.8% / 0.1% |
| 1024 / 1024 | 8 | 780.8 | 758.1 | **−2.9%** | 0.8% / 0.2% |
| 1024 / 1024 | 32 | 3008.8 | 2915.3 | **−3.1%** | 0.0% / 0.9% |

Consistent sign and a magnitude several times the drift, so this is a real regression, not noise. The dispatch therefore substitutes only while a CUDA graph is being captured, tested with `torch.cuda.is_current_stream_capturing()` as `custom_all_reduce.py` and `sparse_attn_indexer.py` already do, and eager steps keep AITER. An earlier revision tested `get_forward_context().cudagraph_runtime_mode` instead; that misses every FULL graph under the V2 model runner, which captures them with the forward context set to `NONE` (`vllm/v1/worker/gpu/cudagraph_utils.py`), so on current main it substituted only inside PIECEWISE graphs. Re-running the same eager A/B with the check in place:

|---|---:|---:|---:|---:|---|
| 64 / 256 | 8 | 490.2 | 492.5 | +0.5% | 0.7% / 0.1% |
| 64 / 256 | 32 | 1934.9 | 1933.3 | −0.1% | 1.2% / 0.0% |
| 1024 / 1024 | 8 | 787.1 | 786.8 | −0.0% | 0.1% / 1.0% |
| 1024 / 1024 | 32 | 3018.7 | 3009.5 | −0.3% | 1.9% / 0.8% |

Instrumentation observed no Triton dispatches with `enforce_eager=True`. With graphs enabled, on current main and MI355X, a server records these substitution decisions while it captures its graphs:

| model | cudagraph mode | substituted with the forward-context check | substituted with the stream-capture check |
|---|---|---:|---:|
| Kimi-Linear-48B-A3B | `FULL_DECODE_ONLY` (forced by the model) | 0 of 2912 | 494 of 2912 |
| Moonlight-16B-A3B | `FULL_AND_PIECEWISE` | 988 of 8190 | 1482 of 8190 |

494 is 19 captured decode sizes up to 128 tokens times 26 MoE layers; the remaining decisions are larger captured sizes, the profiling run and warm-up runs, all of which keep AITER. Those counts are with the earlier `_MAX_TOKENS = 128`; with the current `_MAX_TOKENS = 1` a Moonlight server substitutes 78 of 8190 decisions, all of them in the 1-token graphs, and keeps AITER everywhere else.

The advantage shrinks as the router widens on gfx950; it does not grow. The slow launches are the tie fallback: when a row has two experts with exactly equal biased scores among its top-k, the fast path picks more than k and that row redoes the selection, and the launch waits for its slowest row. bf16 logits make exact ties common enough at top-16 to matter (0.8% of rows at 896 experts, so about one 32-row launch in five), which is where the 0.6× launches come from. Rows above 512 experts or top-8 therefore stay on AITER.

### Routing comparison on live models

Comparing generated text between arms is not a usable instrument on this setup: it is not deterministic run to run — two baseline-only runs of the same four greedy prompts already diverge. Instead both kernels were run on identical inputs inside a live forward, AITER into the real buffers and the new kernel into scratch, with generation continuing on the AITER result so the measurement cannot perturb the run.

|---|---:|---:|---:|
| Moonlight-16B-A3B | 3328 | 3323 | 4.77e-07 |

Both have `n_group=1`, `topk_group=1`, `scoring_func="sigmoid"`, `noaux_tc`, `norm_topk_prob=true`, 64 experts, top-6. **The 8k/1k and 64k/1k points are now measured.** The earlier report that they could not be served was wrong, and the reason is worth stating because it is a bug in the benchmark harness rather than in serving.

`vllm bench serve --dataset-name random` samples token ids from `tokenizer.vocab_size`. For this checkpoint that is **163842**, while the model's embedding has `config.vocab_size` = **163840** rows, so ids 163840 and 163841 index past the table and the embedding gather faults. The dataset emits a *contiguous run* of ids, so a 65536-token prompt covers 40% of the vocabulary and nearly always includes one of the two; an 8192-token prompt covers 5%, which is why 8k completed under some seeds and not others. On stock vLLM, with no part of this PR installed, the identical 8192 configuration completes 3/3 with `--seed 7` and faults 3/3 with `--seed 1234`:

| seed | completed | `Memory access fault` |
|---|---|---|
| 7 | 8, 8, 8 | 0 |
| 1234 | 0, 0, 0 | 1 |

That also explains the fault seen earlier on a different machine with Kimi-VL, where the kernel named in the HSA exception was `at::native::vectorized_gather_kernel` — the embedding gather.

Replacing the synthesised prompts with real text (a custom dataset whose maximum token id is 138177, verified below the embedding size) removes the fault entirely: 8 of 8 runs complete at 64k with zero faults.

## Details

### Why the substitution sits at the wrapper

Review asked whether a model with no grouping should simply not be routed to `GroupedTopKRouter`. Two things make the wrapper the better place.

First, the advertised routing method is not a label. `layer.py:378` takes it from `router.kernel_routing_method_type` and stores it on the MoE config, where the AITER mxfp4 expert kernels consume it: `_supports_routing_method` lists `[Renormalize, RenormalizeNaive, DeepseekV4, DeepSeekV3]`, `self.renormalize` is derived from the same tuple, and the apply path branches on `DeepSeekV3` to pick `score_mode="sigmoid"`. `MiniMax2` is in none of them, so degenerating `num_expert_group` 1 → None would make those backends refuse these models and would flip `renormalize` to False for a checkpoint whose config says `norm_topk_prob: true`.

Second, and more decisively, changing the router would not remove the op. Calling `fused_topk_bias` directly — the routine `FusedTopKBiasRouter` uses — with a 64-expert, top-6 sigmoid+bias router on ROCm with AITER enabled:

```
synthesised group count for 64 experts: 2
biased_grouped_topk CALLED 1x with (num_expert_group, topk_group) = (2, 2)
```

`_aiter_get_num_expert_group` picks a divisor AITER has a kernel for, with `topk_group == num_expert_group` so the grouping is a no-op. A model moved off `GroupedTopKRouter` would still reach the grouped kernel, with a fabricated two-group configuration in place of its real single group.

Specialising at `rocm_aiter_ops.biased_grouped_topk` covers both callers, needs no routing-metadata change, and generalises the condition from "one group" to "no group is eliminated".

### Relation to #49870

[#49870](https://github.com/vllm-project/vllm/pull/49870) short-circuits the same degenerate shape for the case where AITER fused MoE is **not** enabled, which this PR does not touch.

### Scope and bounds

`can_use_sigmoid_bias_flat_topk` requires `topk_group >= num_expert_group`, a contiguous bias of exactly `num_experts`, and bounded token/expert/topk counts. The scoring function is not checked: at this call site the op is AITER's biased (sigmoid) top-k by construction, so matching that op is the contract. `_MAX_EXPERTS = 512` and `_MAX_TOPK = 8` are where the gfx950 measurements above stop showing a win: up to there the mean per shape is 1.16×–1.57× and no launch falls below 0.92×, even with a forced tie; at top-16 single tied rows pull launches to 0.62×–0.78×. An earlier revision of this PR accepted up to 1024 experts and top-32, set to cover the widest router in this family without having measured it there; the gfx950 sweep showed that was wrong, and those routers, Kimi-K3 (896 / top-16) among them, now keep AITER. `_MAX_TOKENS = 1` restricts it to single-token batches, one request decoding without speculation, where the end-to-end sweep shows a gain on every model; at larger batches the gain was within noise, so those keep AITER.

### Limitations

- Micro and unit tests on gfx942 and gfx950. The MI355X e2e and GSM8K runs are on current `main`; the gfx942 e2e, NIAH and GPQA runs are on an older build, see the next point.
- The e2e and accuracy comparisons used the container's own older vLLM build for both arms, because today's `main` cannot start against this image's AITER (`aiter.ops.flydsl.moe_common` missing, `fused_moe()` without `swiglu_limit`). Both arms are that same build differing only in this kernel. Unit and micro results are against `db3b0f0fa`.
