# [Bugfix] KVQuantMode: give CUSTOM its own value (it aliased OCTAVE_K3V4)

[Upstream PR](https://github.com/vllm-project/vllm/pull/63691) · state: open · merged: False

## Original PR description

## Purpose

`KVQuantMode.CUSTOM` and `KVQuantMode.OCTAVE_K3V4` share the value 12. #59774 (Octave KV) and #52670 (pluggable KV cache dtypes) landed the same day and each took the next free value. On an `IntEnum` a repeated value makes the second name an alias of the first, so on `main` today:

```python
>>> KVQuantMode.CUSTOM is KVQuantMode.OCTAVE_K3V4
True
>>> KVQuantMode.CUSTOM.is_octave
True
>>> get_kv_quant_mode("octave_k3v4").is_custom_mode
True
```

So a registered dtype whose handler returns `CUSTOM` is treated as Octave by everything that checks `is_octave`, and `octave_k3v4` reports itself as a custom mode.

This PR moves `CUSTOM` to 15 and marks the enum `@unique`, so a future collision raises at import (`ValueError: duplicate values found in <enum 'KVQuantMode'>`) instead of creating a silent alias. Nothing persists these values, so renumbering is safe.

Not a duplicate: no open PR touches `KVQuantMode` values (searched `KVQuantMode CUSTOM`, `OCTAVE_K3V4`).

## Test Plan

```bash
pytest -q tests/config/test_kv_cache_dtype.py
```

`test_backend_sentinel_properties` now also asserts that `CUSTOM` is neither TurboQuant nor Octave and that no other mode is a custom mode.

## Test Result

- With this PR: 6 passed.
- With the old values (`CUSTOM = 12`, no `@unique`): `test_backend_sentinel_properties` fails at `assert mode.is_octave is False`.
- With `@unique` and `CUSTOM = 12`: importing `vllm.v1.kv_cache_interface` raises `ValueError: duplicate values found in <enum 'KVQuantMode'>: CUSTOM -> OCTAVE_K3V4`.

No effect on model output for the built-in dtypes; only the value of the `CUSTOM` sentinel changes.

AI assistance (Claude Code) was used to write this change; I reviewed every line and ran the tests above.
