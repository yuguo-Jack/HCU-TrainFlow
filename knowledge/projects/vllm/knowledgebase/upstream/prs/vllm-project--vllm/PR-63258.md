### Multithreading or multiprocessing?
 
- vllm launch render Qwen/Qwen3-0.6B --renderer-num-workers 8
- vllm launch render Qwen/Qwen3-0.6B --api-server-count 8

https://github.com/noooop/snippet/blob/main/benchmarks/renderer/bench_online.py

<img width="1183" height="888" alt="image" src="https://github.com/user-attachments/assets/cfab9d43-76fd-435d-b5fd-137478b8330c" />

--renderer-num-workers uses multithreading for preprocessing, while --api-server-count uses multiprocessing. Because of Python’s GIL, Python multithreading is inferior to multiprocessing, and as the number of cores increases, the probability that multiprocessing wins increases.

The load-balancing mechanism introduced in #60723 is essential; without it, using --api-server-count would utilize only about two cores.

VLLM_USE_FASTOKENS=1 is said to provide a 10x speedup. Yes—if the comparison can only be made in a single process—and fast token acceleration only works with multiprocessing (--api-server-count), not multithreading (--renderer-num-workers). However, in my tests it only delivers about a 2x speedup with --api-server-count 2, and increasing api-server-count further has no effect. I’m not sure why fast token acceleration cannot be scaled further with multiprocessing, and I hope we can find a way to do so.

🔴 With `--api-server-count` > 1, render servers using `--tool-parser-plugin` or `--reasoning-parser-plugin` fail at startup. The single-process path serves them fine. The plugin is imported only by `init_parser_plugin` inside `setup_server`, which now runs in the launcher (multi.py:122). Spawned workers never import it, so `ParserManager.get_parser` raises "has not been registered" when building `OnlineRenderer`. Fix: call `init_parser_plugin(args)` at the start of `run_worker_proc`, before `build_and_serve_renderer`, the way `run_server_worker` in api_server/entry.py:183 does for `vllm serve` workers.

<details>
<summary>Why this was flagged</summary>

Trigger: `vllm launch render <model> --api-server-count 2 --enable-auto-tool-choice --tool-parser-plugin my_parser.py --tool-call-parser my_parser`, or the same with `--reasoning-parser-plugin`. `RenderSubcommand.cmd` (launch.py:65-69) routes this to `run_multi_launch`. There, `setup_server` (launcher.py:366-371) calls `init_parser_plugin` and `validate_api_server_args` in the launcher process only, so validation passes. Each worker is started with the "spawn" context, so it is a fresh interpreter that has not imported the plugin file. In the worker, `run_worker_proc` (multi.py:30-82) calls `build_and_serve_renderer` → `init_render_app_state` → `OnlineRenderer.__init__` → `ParserManager.get_parser`. `ToolParserManager.get_tool_parser` raises KeyError, and parser_manager.py:49 turns that into TypeError "... which has not been registered". The worker dies, `_wait_for_first_exit` returns, and the launcher tears down every worker. On the single-process path (`run_launch_fastapi`), `setup_server` runs in the serving process, so the plugin is registered and the server starts.

**Verification:** Workers are started with `multiprocessing.get_context("spawn")`, so each worker is a fresh interpreter whose parser registries hold only the built-in parsers. `run_worker_proc` (multi.py:38-82) calls `build_vllm_config(args)` and then `build_and_serve_renderer`. It never calls `init_parser_plugin`. The workers crash, `_wait_for_first_exit` returns, and the launcher tears the whole set down.

</details>

🔴 Operators running `vllm launch render --api-server-count N` get exit status 0 when a worker crashes or times out at startup. The single-process path exits nonzero there. `_wait_for_first_exit` only logs a nonzero `exitcode`, then `_run_multi_launch` returns normally at multi.py:156. A barrier timeout or error makes the worker `return` silently at multi.py:79, so it exits 0 and is logged at info level. Fix: treat any worker exit the launcher did not start as a failure. Raise (like `wait_for_completion_or_failure` in v1/utils.py) so the process exits nonzero, and log the barrier failure and exit nonzero instead of returning.

<details>
<summary>Why this was flagged</summary>

Trigger: N>1 via RenderSubcommand.cmd (launch.py:65-69), where one worker dies, e.g. build_vllm_config raises for a bad model arg or the process is OOM-killed. _wait_for_first_exit (multi.py:85-104) sees exitcode != 0 and only calls logger.error. _run_multi_launch then returns, the ExitStack runs v1.utils.shutdown on the rest, and run_multi_launch returns without an exception, so the CLI exits 0. If startup_barrier.wait times out or breaks, run_worker_proc hits `except Exception: return` (multi.py:77-79) with no log. That worker exits 0 and the launcher logs it at info level, so the whole server stops cleanly with status 0 and no error. On base, the single-process run_launch_fastapi let exceptions propagate, giving a nonzero exit. The api_server multiprocess path raises RuntimeError on a nonzero worker exit (wait_for_completion_or_failure in vllm/v1/utils.py). Supervisors such as systemd Restart=on-failure or k8s restartPolicy OnFailure will not restart the crashed render server.

**Verification:** `_run_multi_launch` ends at multi.py:156 (`_wait_for_first_exit(processes)`) without checking the code. The ExitStack then runs `shutdown(processes)` and `run_multi_launch` returns normally, so the CLI exits 0. The same misconfiguration therefore gives a nonzero exit with one API server and exit 0 with N>1. This affects only the new multi-worker path, so it is not pre-existing.

</details>

- claude[bot] · comment · 2026-10-27T09:30:08Z · [source](https://github.com/vllm-project/vllm/pull/63258#discussion_r4387049335)

File: `vllm/entrypoints/launchers/render/multi.py` · line None

🟡 (optional) If the render launcher is SIGKILLed or OOM-killed, its workers keep serving the port forever. A restarted multi-worker launcher then silently shares traffic with the stale orphans. Workers never watch the launcher, and render has no engine whose death would stop them. Only the launcher's `ExitStack` stops workers, through `shutdown(processes)`, and that never runs on SIGKILL. Fix: make each worker exit when the launcher dies. For example, pass a pipe whose EOF starts graceful shutdown, like `death_pipe` in multiproc_executor.py, or set `PR_SET_PDEATHSIG` in `run_worker_proc`.

<details>
<summary>Why this was flagged</summary>

The trigger is `vllm launch render <model> --api-server-count 2` where only the launcher PID gets SIGKILL. Examples are `kill -9`, the OOM killer, or a supervisor that does not kill the process group. Workers are spawned at multi.py:139-143 and nothing ever checks the parent. `serve_http` starts its `watchdog_loop` only when `engine_client is not None`, and render sets `state.engine_client = None` (render/app_state.py:119), so no engine-death path ends the workers either. The orphaned workers hold dup'd fds of the listening socket and keep accepting connections. The launcher bound that socket with SO_REUSEPORT (`setup_server(args, reuse_port=num_api_servers > 1)`, multi.py:124). A new multi-worker launcher run by the same user on that port therefore binds without EADDRINUSE. The kernel then splits connections between old and new workers, which may run a different model or config. On base, the render server was a single process, so a SIGKILL freed the port completely.

**Verification:** Trigger: `--api-server-count N` (N>1) where only the launcher PID is SIGKILLed. multi.py:139-155 gives workers no death pipe or PR_SET_PDEATHSIG, and their only teardown (multi.py:137) never runs on SIGKILL. A restarted multi-worker launcher also sets SO_REUSEPORT, so the kernel load-balances connections between the stale orphans and the new workers. Render ran as one process before this change.

</details>

File: `vllm/entrypoints/launchers/render/multi.py` · line 140

🟡 (optional) With `--api-server-count` > 1, a SIGTERM or Ctrl-C SIGKILLs render workers 5 seconds later and ignores `--shutdown-timeout`, so in-flight requests are dropped. The single-process path drains them instead. `exit_stack.callback(shutdown, processes)` passes no timeout, so `vllm.v1.utils.shutdown` uses its 5.0s best-effort default. Fix: when shutdown was requested by a signal, pass the configured `shutdown_timeout` to `shutdown(processes, timeout=...)`, as `run_multi_api_server` does in serve.py:392-402. Keep the short default for crash teardown.

<details>
<summary>Why this was flagged</summary>

Trigger: `vllm launch render <model> --api-server-count 2`, then SIGTERM to the launcher (for example a k8s pod stop or rolling deploy) while slow requests are in flight, such as large multimodal renders. `run_multi_launch` (multi.py:166-176) turns SIGTERM into KeyboardInterrupt, and the ExitStack runs `shutdown(processes)` (registered at multi.py:134) with timeout=None. `vllm/v1/utils.py:613-616` then sets timeout = 5.0, sends SIGTERM to the workers and kills any still alive after 5s. Each worker's `serve_http` signal_handler had started a graceful uvicorn drain, and that drain is cut off. On the single-process path (`run_launch_fastapi`), SIGTERM reaches `serve_http` (launcher.py:255-285), which has no engine_client and so no forced timeout, and uvicorn finishes open requests. The multi-process API server honors `--shutdown-timeout` via `vllm_config.shutdown_timeout` (serve.py:392-402). The render launcher does neither, so `--shutdown-timeout` has no effect, and clients see connection resets for requests running longer than 5s.

**Verification:** Trigger: `--api-server-count` > 1, and the launcher gets SIGTERM while a render request is still running past 5s. multi.py:134 registers `exit_stack.callback(shutdown, processes)` with no timeout, so vllm/v1/utils.py:613-616 sets `timeout = 5.0` and kills any worker still alive. On the base branch, `RenderSubcommand.cmd` always used the single-process draining path, where those requests finished.

</details>
