# [Bugfix] Fix FlashInfer non-causal draft attention (DFlash/DSpark) on Blackwell

[Upstream PR](https://github.com/vllm-project/vllm/pull/48167) · state: closed · merged: True

## Original PR description

## Purpose

DFlash/DSpark drafts on Blackwell had near-zero acceptance or crashed with an illegal memory access when the drafter used FlashInfer; Hopper was fine.

Root cause: non-causal attention skips trtllm-gen and runs FlashInfer's prefill wrapper, which is only CUDA-graph-replayable when constructed with `use_cuda_graph=True` and persistent buffers — vLLM does not use that mode for draft attention, so replaying a captured `run()` after `plan()` returns wrong output, then an IMA as sequences grow. On SM100 the FlashInfer builder claimed `UNIFORM_BATCH` graph support based on trtllm-gen, so drafts were FULL-graph captured on this path; SM90's support level already kept them eager. Kernel numerics are fine (FI eager == FA eager, identical accepted tokens).

Fixes:
- Prefer FLASH_ATTN for SM100 non-causal attention (CUDA-graph-safe default).
- FlashInfer `get_cudagraph_support` only claims `UNIFORM_BATCH` for causal attention.
- Draft speculators build attention metadata under the draft's attention config and honor its cudagraph support; DFlash/DSpark fall back to eager draft attention with a warning (the model runner initializes the speculator's cudagraph manager after `set_attn`).

Follow-up: adopt the prefill wrapper's cuda-graph mode for draft attention to restore full graphs for FlashInfer drafts.

## Test Plan

B300 (SM103): `vllm serve Qwen/Qwen3-8B --spec-method <m> --spec-model <d> --spec-tokens 7 --speculative-config '{"attention_backend": <b>}'`, greedy completions.

Larger draft, GSM8K acceptance (NVFP4 target needs bf16 KV + autotune off): `vllm serve txn545/Qwen3.5-35B-A3B-NVFP4 --kv-cache-dtype bfloat16 --kernel-config '{"enable_flashinfer_autotune": false}' --speculative-config '{"model":"z-lab/Qwen3.5-35B-A3B-DFlash","method":"dflash","num_speculative_tokens":7}'`, then `python tests/evals/gsm8k/gsm8k_eval.py --port 8000 --num-questions 200`.

Your analysis correctly isolates the memory‑access fault to FlashInfer's non‑causal draft attention, where the prefill wrapper runs without use_cuda_graph=True, leading to corrupted outputs on Blackwell while Hopper remains unaffected. This situation is analogous to the challenges faced in [Oklahoma Property Database](https://oklahomacountyassessorss.org/tangible-personal-property/) where a single mis‑indexed field can invalidate an entire query. The discrepancy between SM100’s full‑graph capture and SM90’s eager mode explains why the bug manifests only on the newer architecture, and adjusting the graph‑capture branch or enforcing eager execution for draft attention should resolve the issue. Implementing these safeguards will help maintain consistency across hardware generations.
