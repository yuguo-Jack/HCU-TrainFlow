# [Bugfix][ROCm] Handle MoE padding sentinel in AITER fused experts

[Upstream PR](https://github.com/vllm-project/vllm/pull/57036) · state: open · merged: False

## Original PR description

VLLM_MOE_SKIP_PADDING (enabled by default) lets the topk kernels mark cudagraph padding rows by writing -1 into topk_ids, so downstream MoE kernels can skip work for them. The AITER fused-expert path never handled that sentinel and passed topk_ids straight into aiter.fused_moe, where moe_sorting indexes the expert weights with the raw id. A value of -1 reads outside the weight buffer and trips a GPU memory access fault:

  Memory access fault by GPU node-9 on address 0x7f255b5b2000.
  Reason: Unknown.

This reproduces on DeepSeek-V4.1-Flash (MXFP4 experts, TP=4, MI355X): the profiling run builds a fully synthetic batch whose rows are all marked as padding, so every routing index is -1 and all ranks fault before the server can start. It is not limited to startup -- trailing cudagraph padding rows are marked the same way on real batches.

Neutralize the sentinel where the other AITER dtype fixups happen: route padding rows to expert 0 with zero weight, contributing nothing to the output. The rewrite is branchless so it remains cudagraph-capturable.
