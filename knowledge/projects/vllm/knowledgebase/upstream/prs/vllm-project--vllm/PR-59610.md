# [ROCm][Perf] Fold the MXFP4 dense activation quant into SiLU-mul and RMSNorm with AITER

[Upstream PR](https://github.com/vllm-project/vllm/pull/59610) · state: open · merged: False

## Original PR description

On ROCm with AITER the MXFP4 dense linear (Triton afp4wfp4 path) quantizes its bf16 input inside `gemm_with_dynamic_quant`, so the quant is invisible to the fusion passes and every down_proj and qkv/gate_up input costs a separate `dynamic_mxfp4_quant` launch. This PR emits that quant as its own op when a fold is enabled and adds two patterns to the AITER fusion passes:

- SiLU-mul + MXFP4 quant -> `fused_reduce_act_mul_and_mxfp4_quant` (in `RocmAiterSiluMulFp8GroupQuantFusionPass`), runs with `fuse_act_quant`. On ROCm with AITER linear `+quant_fp8` is enabled, so that is on by default at -O1 and up.
- RMSNorm (with and without the residual add) + MXFP4 quant -> `fused_rms_mxfp4_quant` (in `RocmAiterRMSNormQuantFusionPass`). Opt-in via the new `PassConfig.fuse_norm_mxfp4_quant`, off at every -O level, and only applies together with `fuse_norm_quant`.

The quant is only split out of `gemm_with_dynamic_quant` when the model is compiled and one of the folds is on, so enforce_eager and -O0 keep the single call.

Depends on https://github.com/ROCm/aiter/pull/6024. The SiLU fold needs `round_to_input_dtype` so it rounds silu(a)*b to bf16 once, like the compiled native silu_and_mul, and `transpose_scale` so the scales come out column-major like `dynamic_mxfp4_quant` (the layout the afp4wfp4 configs are tuned for). Both are added in that AITER PR. A probe checks the AITER signature, and on an AITER without them neither pattern registers and nothing changes. With them the SiLU fold is bit exact: output matches the unfused path byte for byte. Against `+silu_and_mul` it can be one fp4 code off, because the `_C` kernel rounds silu to bf16 before the multiply.

The RMSNorm fold stays opt-in because it isnt bit exact, and `fuse_norm_quant` alone is on by default on ROCm. `fused_rms_mxfp4_quant` quantizes the fp32 normed value as it comes out of its own reduction, while the unfused path writes rms_norm to bf16 and quantizes that. Some values land on a different e2m1 code, and greedy output diverges somewhere in every sequence I checked (84/84 prompts). Full sets, Llama-3.1-8B MXFP4, greedy, paired against the same stack without the fold:

| | without | with RMSNorm fold | delta (paired SE) |
|---|---|---|---|
| GSM8K (1319, 4-shot) | 722 | 752 | +2.27 pp (1.40) |
| ARC-Challenge (1172, 0-shot) | 882 | 866 | -1.37 pp (1.11) |
| MMLU (14042, 5-shot) | 8782 | 8763 | -0.14 pp (0.36) |

Nothing moves by 2 SE, but GSM8K and ARC-C each move by more than one in opposite directions and individual outputs change, so I left it off by default. It's another 4.8-10.0% at decode on top of the SiLU fold (one round) for anyone who is fine with that.

Decode, Llama-3.1-8B MXFP4 (amd/Llama-3.1-8B-Instruct-MXFP4-W4A4-MLCAL-C1000-GPTQ), TP=1 on one MI355X, idle GPU, clock pinned with perf_determinism (sclk CV under 0.07%), one process per config, compile and inductor caches off. ms/token is decode only, the p50 wall of a 128 token run minus the p50 wall of a 1 token run, over 127 tokens, mean of two rounds, RMSNorm column one round. AITER is main plus ROCm/aiter#6024. With `fuse_act_quant` off neither fold runs and the linear keeps the single `gemm_with_dynamic_quant` call, same path as main, so thats the baseline:

| batch | fold off | this PR (default) | + RMSNorm fold |
|---|---|---|---|
| 1 | 2.656 | 2.528 (-4.8%) | 2.407 (-9.4%) |
| 8 | 2.932 | 2.821 (-3.8%) | 2.662 (-9.2%) |
| 16 | 2.946 | 2.873 (-2.5%) | 2.704 (-8.2%) |
| 32 | 3.219 | 3.130 (-2.8%) | 2.943 (-8.6%) |
| 64 | 3.931 | 3.756 (-4.5%) | 3.382 (-14.0%) |

With the default config the output tokens are the same as with the fold off at every batch above, on 84 greedy prompts, and on all 1319 GSM8K problems (same token ids per problem, 722/1319).

The AITER side matters for bs64. With the old launch tile in `fused_reduce_act_mul_and_mxfp4_quant` (1x128 on 4 warps) the fused kernel was slower than silu_mul + quant at M=64, and the SiLU fold cost about 2% at bs64 (the full cudagraph replay of the decode step was 77-87 us slower, so it's GPU side). ROCm/aiter#6024 switches that path to one warp over a 256/512 wide row, and the fold is faster at every batch.

#59153 folds act_mul + MXFP4 quant for the ASM (`gemm_a4w4`) path. This PR covers the Triton afp4wfp4 path, and both need the same fix to the `gemm_with_dynamic_quant` fake (arguments in the op's order). I'll rebase on whichever lands first.

On ROCm/aiter#6024 the question came up wether this should target `gemm_afp4wfp4_preshuffle` instead. I measured it on the same setup with preshuffle on all four linears, tuned preshuffle configs, the HIP quant and the SiLU fold with shuffled scales: 7.8-13.2% slower than this PR at bs 1-32 and 3.8% faster at bs64, so for this model the fold stays on the plain afp4wfp4 path. While doing that I found `is_triton_gemm_afp4wfp4_presh_ws_tuned` probes with K = 4 * k_bytes while AITER looks the config up with 2 * K_bytes, so the ASM env path picks preshuffle for the wrong shapes. Thats a separate fix, not in this PR.

Tests: `tests/compile/passes/test_rocm_aiter_mxfp4_quant_fusion.py` (pattern counts and outputs for SiLU with and without `+silu_and_mul`, RMSNorm and fused-add RMSNorm, bitwise equal to the unfused path on native silu_and_mul, plus which pass config / compile mode makes the linear split the quant), wired into the `(MI355) Fusion and Compile FP8` job. 37 passed on MI355X with AITER main plus ROCm/aiter#6024. pre-commit on the changed files passes.

Yes, done in 4795496, both env vars are gone.

The SiLU-mul fold now just follows `fuse_act_quant`. It's bit exact against the compiled native silu_and_mul + quant, and on ROCm with AITER linear `+quant_fp8` is on, so `enable_act_fusion` already turns it on at -O1 and up. Same default the env var had.

For the RMSNorm fold I didnt want to rely on `fuse_norm_quant` alone. That flag is on by default here for the same reason, and this fold isnt bit exact: the fused kernel quantizes the fp32 norm output, so greedy output changes (GSM8K +2.27 pp, ARC-C -1.37 pp on Llama-3.1-8B, table in the description). So it's behind a new `PassConfig.fuse_norm_mxfp4_quant`, False at every -O level, and it only does something together with `fuse_norm_quant`. If you'd rather not add a field for this I can drop the RMSNorm fold from this PR and keep only the SiLU one.

On the split: the linear now only emits the quant as its own op when the mode is VLLM_COMPILE and one of the folds is on, so enforce_eager and -O0 keep the single `gemm_with_dynamic_quant` call. `test_mxfp4_linear_splits_quant_only_for_a_fold` covers that.

Rechecked on MI355X with ROCm/aiter#6024 applied, the test file is 37 passed. Served Llama-3.1-8B MXFP4 decode, previous head vs this one:
- default: SiLU fold fires, token ids are the same as the previous head at bs 1-64 and on 84 greedy prompts, speed within 0.6%. GSM8K / ARC-C / MMLU 722 / 882 / 8782 with the same answer on every problem as the run in the description
- `fuse_act_quant=False`: no fold, same tokens, 3.7-4.5% slower per token
- `fuse_norm_mxfp4_quant=True`: both folds fire, same tokens and the same 752 / 866 / 8763 as with the old env var, 3.0-6.8% faster than default

The description is updated to the new switches, with decode numbers rerun at this head on AITER main plus ROCm/aiter#6024.
