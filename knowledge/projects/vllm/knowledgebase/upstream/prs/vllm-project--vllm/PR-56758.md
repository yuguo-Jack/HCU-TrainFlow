# [Scheduler] Add --max-num-active-seqs to cap RUNNING admission

[Upstream PR](https://github.com/vllm-project/vllm/pull/56758) · state: closed · merged: True

## Original PR description

## Purpose

`max_num_seqs` currently does two jobs: it sizes the model runner (per-request buffers and CUDA graph capture) and it caps how many requests the scheduler will admit into RUNNING.

Those should be independent. Keeping runner/graph capacity large while admitting fewer decode requests lets a deployment hold a smaller decode batch without recapturing graphs or shrinking static buffers.

This adds an optional admission cap. Default `None` is current behavior (`max_num_seqs`).

This is not `--max-num-queued-reqs`. That limit is enforced in the API server across DP ranks and returns HTTP 503. This flag only gates WAITING → RUNNING inside one engine.

## Approach

- New `SchedulerConfig.max_num_active_seqs` / `--max-num-active-seqs`.
- Must be `<= max_num_seqs`. `None` uses `max_num_seqs`.
- The WAITING admission loop stops when `len(running) + streaming_slots >= max_num_active_seqs`.
- No preemption: lowering the cap takes effect as requests finish.
- Model runner, KV sizing, and cudagraph capture still follow `max_num_seqs`.

## Usage

```bash
vllm serve ... \
  --max-num-seqs 128 \
  --max-num-active-seqs 16
```
