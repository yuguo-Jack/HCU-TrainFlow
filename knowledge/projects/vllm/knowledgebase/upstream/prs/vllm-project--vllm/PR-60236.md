# [ROCm][Perf][MLA][DCP] gfx942: run causal DCP verify on AITER single-token asm decode

[Upstream PR](https://github.com/vllm-project/vllm/pull/60236) · state: open · merged: False

## Original PR description

## Purpose

On gfx942, causal DCP verify (qlen > 1) currently runs on Triton segmented MLA
where it fits in LDS, and on the generic Triton split-KV decode otherwise
(#58555). This PR runs gfx942 verify on AITER's non-persistent single-token asm
decode whenever gfx942 ships a kernel for the DCP-gathered head count, which
covers Kimi-K3 (96) and DeepSeek-V3 (128). Each verify token becomes one qlen-1
row with its own causal KV window, the row view that #58555 already builds.

* New route `ASM_ROWS`, checked before TRITON and SEGMENTED on gfx942. It has
  its own config gate, `_asm_rows_dcp_verify_supported` (gfx942, DCP > 1,
  interleave 1). Head counts with no asm kernel keep the #58555 routing:
  segmented MLA where it fits in LDS, the generic Triton split-KV decode
  otherwise. No new env var.
* Query heads are padded to a count the gfx942 kernel can launch: bf16
  16/32/128, fp8 16/128. Counts with no kernel (above 128) never reach AITER,
  which would otherwise abort; they take the fallback above.
* KV splits per row: `min(cdiv(CUs, 2*rows), max_kv_len // 128, 64)`, floor 2.
  AITER's own choice stops at 16 splits, which is up to 1.89x slower at low
  batch. One split skips AITER's reducer, and the fp8 kernel then writes no LSE.
* The unpad helpers now take the same `target_heads` as `get_mla_padded_q`.
  Before, a repeat-interleaved pad (for example 64→128) was unpadded as a
  prefix slice. This also fixes CPRR's 8→16 case.

The segmented verify code itself is unchanged.

## Test Plan

```
pytest tests/v1/attention/test_rocm_aiter_mla_dcp_verify_gfx942.py \
       tests/v1/attention/test_rocm_aiter_mla_mtp_split.py \
       tests/v1/attention/test_rocm_aiter_mla_dcp_cprr.py \
       tests/v1/attention/test_rocm_aiter_mla_dcp_cprr_numerics.py \
       tests/v1/attention/test_rocm_aiter_mla_fp8_decode_routing.py
```

The DCP verify test runs the real builder and `forward_mqa` for 8 simulated
ranks and compares against a dense causal reference. It covers asm rows on the
Kimi-K3 768-token blocks, a shape segmented MLA fits, 64 heads padded to 128,
and DeepSeek-V3 MTP with fp8 KV and an fp8 query, each next to its Triton or
segmented baseline. The baselines disable asm rows by stubbing its head lookup,
the path taken when gfx942 has no kernel for the head count.
`test_asm_rows_heads_fall_back_without_a_kernel` checks which counts fall back.

## Test Result

MI325X (torch 2.12 / ROCm 7.15, amd-aiter 0.1.24.post1): 581 passed, 4 skipped
(gfx950-only).

**Kernel sweep** (810 verify shapes, 8-rank DCP: 16–128 heads, bf16/fp8, block
16/64/768, qlen 2–6, 1–32 requests, 1K–16K local tokens):

| asm rows vs         | shapes | geomean | min   | max   |
| ------------------- | ------ | ------- | ----- | ----- |
| current route (all) | 810    | 4.12x   | 1.01x | 19.0x |
| segmented MLA       | 513    | 4.35x   | —     | —     |
| Triton split-KV     | 297    | 3.74x   | 1.24x | —     |

The split rule is within 3.3% of the best split count on average (worst 1.26x).
Building the asm-rows metadata costs ~60 µs per step: 792/810 shapes recover it
within 4 MLA layers, and all of them within 30.

**Accuracy** (180 configs, 8-rank LSE combine): bf16 error is the same on all
routes. fp8 at 4K local tokens: max error 0.0090 (asm) vs 0.0116 (segmented)
and 0.0168 (Triton); mean error ~0.0006 vs ~0.0003. Empty local shards give
LSE −inf and combine correctly.

**E2E**: Kimi-K3 + DSpark (5 draft tokens), TP8/EP8/DCP8, MI325X. Same server,
restarted per arm. The Triton arm is the #58555 routing on `main`; the ASM arm
is this PR. These runs used an earlier revision with a temporary switch between
the two; the switch has since been removed with no change to either path.
