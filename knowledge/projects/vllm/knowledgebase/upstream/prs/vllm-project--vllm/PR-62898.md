# [Kernel][MoE] Accept the single-variant MXFP4 moe_backend aliases

[Upstream PR](https://github.com/vllm-project/vllm/pull/62898) · state: open · merged: False

## Original PR description



## Overview

`map_mxfp4_backend()` maps four `moe_backend` names to exactly one MXFP4 activation variant, but none of them is in the `MoEBackend` literal, so `--moe-backend` and `--kernel-config` reject them at argument parsing and those mapping entries are unreachable. For a model whose MXFP4 MoE selector ignores `quantization_config.moe.activation`, these names are the only way to request an activation-quantized variant: `aiter` and `flashinfer_*` walk their variants BF16-first. The env path from #58819 covers only the AITER fused-MoE path for the model types it names.

## Claims

- Add `aiter_mxfp4_fp8`, `aiter_mxfp4_mxfp4`, `flashinfer_trtllm_afp8` and `flashinfer_cutlass_afp8` to `MoEBackend` and document them in `KernelConfig.moe_backend`.
- Selection logic is unchanged; none of these backends is chosen unless requested by name.

| alias | backend |
|---|---|
| `aiter_mxfp4_fp8` | `AITER_MXFP4_FP8` (W4A8) |
| `aiter_mxfp4_mxfp4` | `AITER_MXFP4_MXFP4` (W4A4) |
| `flashinfer_trtllm_afp8` | `FLASHINFER_TRTLLM_MXFP4_MXFP8` |
| `flashinfer_cutlass_afp8` | `FLASHINFER_CUTLASS_MXFP4_MXFP8` |

## Validation

8x MI355X, an MXFP4 MoE checkpoint served with `--moe-backend aiter_mxfp4_mxfp4`: the log reports `Using 'AITER_MXFP4_MXFP4' Mxfp4 MoE backend` instead of `AITER_MXFP4_BF16`; gsm8k 0.95 (default backend about 0.955). This PR only makes the backend selectable; any speed or accuracy difference belongs to the backend.

New `tests/config/test_moe_backend_aliases.py`: each alias parses from `--moe-backend <alias-with-dashes>` through `EngineArgs` and maps to exactly one backend.

## Details

With `--kernel-config '{"moe_backend": "aiter_mxfp4_mxfp4"}'` the failure is a pydantic `literal_error` on `KernelConfig.moe_backend`; with `--moe-backend` it is the argparse `invalid choice` above.
