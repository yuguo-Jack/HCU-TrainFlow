# [Bugfix][Parser] Preserve token IDs in non-streaming engine parsing

[Upstream PR](https://github.com/vllm-project/vllm/pull/50676) · state: open · merged: False

## Original PR description



## Purpose

Non-streaming serving already passes the generated token IDs to
`Parser.parse()`, but `DelegatingParser` discarded them before invoking its
reasoning and tool parser-engine adapters. The fallback text-only parse could
therefore mistake ordinary text such as `[TOOL_CALLS]` or `[TOOL_RESULTS]` for
a structural Mistral v11 token.

This change keeps the original model text aligned with its token IDs and parses
it once when the active reasoning and tool adapters use the same parser engine,
or when only an engine tool parser is configured. Tool-only parsing starts in
`CONTENT`, and `tool_choice="none"` still suppresses tool calls while preserving
literal marker text.

The shared `ParserEngine.parse()` method remains the public non-streaming entry
point. A protected `_parse_non_streaming()` hook lets Mistral retain its pre-v11
JSON-array extraction without duplicating request initialization or tool-call
conversion. Mixed/legacy parser combinations keep the existing text fallback;
this PR does not pair transformed content with the original full token-ID span.

### Duplicate-work check

I searched open issues and PRs using `Mistral v11 non-streaming markers`,
`TOOL_RESULTS`, `TOOL_CALLS`, `parser engine token IDs`, and
`non-streaming tool parser`. No open issue or PR covers this non-streaming
token/text identity bug.

PR #46529 identified the same general token-ID loss, but it remained a draft
and was closed without merge. It added parallel token-ID methods to several
reasoning/tool parser interfaces and attempted a two-stage handoff of rewritten
content plus separately sliced IDs. This PR instead uses the existing
`Parser.parse(..., model_output_token_ids=...)` contract and performs one pass
only where both phases share the same engine (or only the engine tool parser is
present), avoiding an expanded legacy interface and potentially misaligned
text/ID pairs.

PR #46843 subsequently merged the serving-side plumbing in three entrypoint
files, so the current base already supplies token IDs; it does not make
`DelegatingParser` consume them. The current Mistral engine-adapter path was
merged later in #48947 and was not part of #46529.

The closest open PRs are adjacent but non-duplicating:

- #48320 fixes Mistral v11 streaming boundaries when content and multiple tool
  calls arrive in one delta.
- #42868 skips tool parsing for streaming `tool_choice="none"`.
- #50015 seeds Gemma4 non-streaming state from the prompt.

## Test Plan

The regression coverage uses the public `ParserManager`/`DelegatingParser.parse`
path and supplies text plus precisely aligned token IDs. It verifies:

- literal `[TOOL_CALLS]` and `[TOOL_RESULTS]` text inside Mistral v11 arguments;
- literal marker preservation with `tool_choice="none"`;
- tool-only parsing beginning in `CONTENT`;
- pre-v11 Mistral JSON-array behavior;
- all registered same-engine reasoning/tool adapter replay samples.

Commands:

```bash
.venv/bin/python -m pytest tests/parser/engine/test_parser_engine.py -q
.venv/bin/python -m pytest tests/parser/engine/test_delegating_replay.py -q
.venv/bin/python -m pytest tests/parser/mistral/test_tool_calls.py -q
PATH="$PWD/.venv/bin:$PATH" VLLM_USE_FLASHINFER_SAMPLER=0 \
  .venv/bin/python -m pytest \
  tests/tool_use/mistral/test_mistral_tool_calls.py -q -k ministral-3b
.venv/bin/pre-commit run
```

## Test Result

Before the fix, ordinary marker text encoded as normal tokens was interpreted
from its decoded spelling: `[TOOL_CALLS]` could split one call into two, while
`[TOOL_RESULTS]` could be silently removed. The token-aware direct engine parse
returned the expected single call.

With this change:

```text
tests/parser/engine/test_parser_engine.py:       101 passed
tests/parser/engine/test_delegating_replay.py:   892 passed
tests/parser/mistral/test_tool_calls.py:          147 passed
Ministral-3B tool-use evaluation:                   7 passed, 7 deselected
pre-commit:                                      all hooks passed
```

### Model evaluation

The repository's Mistral tool-use E2E suite was run with
`mistralai/Ministral-3-3B-Instruct-2512` on an NVIDIA RTX 5070 Ti (16 GiB).
All seven selected cases passed, covering named, auto, required, none,
no-tools, tool-result, parallel, streaming, and non-streaming behavior as
provided by the suite. `VLLM_USE_FLASHINFER_SAMPLER=0` was used because the
local runner did not have a CUDA toolkit for FlashInfer JIT compilation.

The exact literal-marker regression additionally uses the pinned
`mistralai/Mistral-Small-3.2-24B-Instruct-2506` tokenizer revision
`95a6d26c4bfb886c58daf9d3f7332c857cb27b43`. The 24B weights were not loaded on
the 16 GiB development GPU; parser behavior was validated with the real
tokenizer and aligned generated-token fixtures.
