# [Bugfix] Don't crash DeepGEMM MegaMoE warmup when get_bf16_mega_gate_config is missing

[Upstream PR](https://github.com/vllm-project/vllm/pull/61657) · state: closed · merged: True

## Original PR description




**Before:** A server started with `--moe-backend deep_gemm_mega_moe` on a model whose MoE layers use the bf16 mega gate crashes during kernel warmup with `AttributeError: module 'deep_gemm' has no attribute 'get_bf16_mega_gate_config'`.

**After:** Warmup completes. When DeepGEMM does not export `get_bf16_mega_gate_config`, the MegaMoE warmup buckets M values by `block_m` only.

## Overview

#60468 made `_get_fp8_fp4_mega_moe_m_values` call `dg.get_bf16_mega_gate_config` to pick one warmup M per gate config. #61149 moved the DeepGEMM pin to `6ce1c5ec`, which no longer exports that op. Every MegaMoE warmup that uses the mega gate now fails:

```
kernel_warmup.py:244 -> deep_gemm_warmup.py:511 -> :504 -> :366
AttributeError: ... has no attribute 'get_bf16_mega_gate_config'
```

This PR checks `hasattr(dg, "get_bf16_mega_gate_config")` and uses an empty gate config when the op is missing.

## Claims

- MegaMoE warmup no longer crashes when the installed DeepGEMM lacks `get_bf16_mega_gate_config`.
- Behavior is unchanged when the op is present.

## Validation

Existing unit tests:

```
VLLM_USE_PRECOMPILED=1 uv pip install -e .
pytest -q tests/model_executor/test_deep_gemm_warmup.py
# 8 passed
```

Real module, with the vendored DeepGEMM from the precompiled wheel (`vllm.third_party.deep_gemm`): `hasattr(dg, "get_bf16_mega_gate_config")` is `False`, and `_get_fp8_fp4_mega_moe_m_values` (EP=4, 256 experts, top-k 6, 8192 tokens, mega gate on) now returns `[106, 256, 602, 2565, 7901, 8192]` instead of raising.

End to end on 4x B300: a DeepSeek-V4 checkpoint with `--tensor-parallel-size 4 --enable-expert-parallel --moe-backend deep_gemm_mega_moe --kv-cache-dtype fp8 --max-model-len 8192` finishes DeepGEMM warmup (1254/1254), passes `/health`, and answers a completion request ("The capital of France is" -> " Paris.").

No open PR fixes this: searching open PRs for `get_bf16_mega_gate_config` finds none, and #61538, which edits the same function, keeps the call.

## Details

Coverage trade-off: without gate configs, warmup no longer picks one M per distinct bf16 mega gate config. Gate configs that do not line up with a `block_m` bucket are not warmed and will JIT on the first request that hits them. This costs first-request latency, not correctness.

## Follow-up

A follow-up PR will reintroduce `get_bf16_mega_gate_config` in vllm-project/DeepGEMM and bump the vLLM pin, which restores full warmup coverage for the mega gate. This guard can stay afterwards so a mismatched external `deep_gemm` install does not crash the server.
