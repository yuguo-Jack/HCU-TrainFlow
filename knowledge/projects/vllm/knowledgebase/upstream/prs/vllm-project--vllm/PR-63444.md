# [Perf][MRV2] Batch the draft-token reset of newly added requests

[Upstream PR](https://github.com/vllm-project/vllm/pull/63444) · state: closed · merged: False

## Original PR description

## Overview

`RequestState.add_request()` zeroes the new request's row of `draft_tokens` immediately, which is one small GPU op and one kernel launch per added request. Defer the reset and do all of them in a single `index_fill_` in `apply_staged_writes()`.

## Claims

- Removes one GPU op and one kernel launch per request admitted while speculative decoding is on; a step that admits many new requests now pays one.
- **No measurable throughput change at the size tested** (see Validation). This is a launch-count cleanup, not a speedup: the removed op is tiny, and at 4,000 requests its cost is below run-to-run noise. It is worth landing because it removes a per-request launch from the admission path at no behavioural cost, and because the benefit grows with the number of requests admitted per step — but no benchmark in this PR demonstrates that growth, so the claim is kept to what was measured.
- Behaviour is unchanged, including for a slot re-added within the same step.
- Nothing is recorded when speculative decoding is off.

## Validation

Environment: 1x H100 80GB, vLLM main @ 2d40c0609f (nightly wheel), torch 2.14.0+cu130, FlashInfer 0.7.2, Model Runner V2 (`VLLM_USE_V2_MODEL_RUNNER=1`).

## Details

The reset is replaced by recording the slot index in a host-side list; `apply_staged_writes()` then zeroes all recorded rows with one `index_fill_` fed by a single asynchronous pinned host-to-device upload of the indices, and clears the list.

Ordering is preserved. `add_request()` has a single caller, `GPUModelRunner.add_requests()`, which calls `req_states.apply_staged_writes()` a few lines later in the same method and under the same condition, so a slot can never be recorded without being reset in the same step. The reset lands before `prepare_inputs()` reads `draft_tokens` in `combine_sampled_and_draft_tokens()`, and before the proposers write them back at the end of `execute_model()`. The only earlier reader, `update_pp_decode_requests()`, already ran before `add_request()` zeroed the row, so its ordering is unaffected.

**CPU/GPU synchronization.** The change adds none. `req_idx` is a host-side integer, the index list is uploaded with the pinned, non-blocking `async_tensor_h2d` helper, and `index_fill_` is a single device-side kernel; nothing reads a GPU tensor from the host. The net effect on the main execution thread is strictly fewer launches than before.

**Trade-off.** The reset is no longer visible at the `add_request()` call site, which is a small readability cost: a caller that added a request and read `draft_tokens` without applying the staged writes would now see stale values. That pattern does not exist in the runner, and the new tests pin the contract.

### Duplicate check

Searched open vLLM issues and PRs on 2026-10-22: `gh search issues --repo vllm-project/vllm --state open` for "draft_tokens" and "RequestState add_request", and `gh pr list --state open --search "states.py staged writes"`. The closest open PR is #62018, which fuses the `StagedWriteTensor` writes of `RequestState.add_request()` into fewer calls. It is a different mechanism (fusing correlated staged writes, not removing the per-request `draft_tokens` zeroing) and does not touch the draft-token path, but it edits the same file, so whichever lands second should expect a small conflict in `vllm/v1/worker/gpu/states.py`. Nothing open duplicates this change.

Two other open PRs, #59908 and #63210, also touch `vllm/v1/worker/gpu/states.py` / `buffer_utils.py`, but not the draft-token path, and both merge cleanly with this PR (checked with `git merge-tree` on 2026-10-22).
