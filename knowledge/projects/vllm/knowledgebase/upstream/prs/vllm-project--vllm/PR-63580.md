# [Bugfix][Rust Frontend] Return 400 instead of 500 when tool parsing is disabled

[Upstream PR](https://github.com/vllm-project/vllm/pull/63580) · state: open · merged: False

## Original PR description



## Overview

The Rust frontend returns HTTP 500 for a chat request with `tools` when tool parsing is disabled; the Python frontend returns 400. This PR classifies `ParserDisabled` as a request validation error so the Rust frontend also returns 400.

Related: #62321 (same class of 500-vs-400 misclassification, but on `/tokenize` and `/detokenize`; see Details for why this is not a duplicate).

## Claims

- `POST /v1/chat/completions` with `tools` (and `tool_choice` omitted or not `none`) returns 400 `BadRequestError` instead of 500 when no tool parser is configured, matching the Python frontend.
- No other behavior changes: `ParserDisabled` is only constructed in `resolve_tool_parser`, which only runs when tool parsing is enabled for the request.

## Validation

**Reproducer (before the fix)**, `vllm/vllm-openai:latest` (v0.32.0), `Qwen/Qwen3-0.6B`, no tool parser flags:

```bash
curl -s -w '\nHTTP %{http_code}\n' localhost:8000/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"Qwen/Qwen3-0.6B",
       "messages":[{"role":"user","content":"What is the weather in Taipei?"}],
       "tools":[{"type":"function","function":{"name":"get_weather",
         "parameters":{"type":"object","properties":{"city":{"type":"string"}},
         "required":["city"]}}}]}'
```

| Frontend | Status | Message |
|---|---|---|
| Python | 400 | `"auto" tool choice requires --enable-auto-tool-choice and --tool-call-parser to be set` |
| Rust | 500 | `failed to submit chat request: tool parsing is disabled by frontend configuration` |

**Regression test**: `chat_completions_with_tools_returns_400_when_tool_parser_disabled` in `rust/src/server/src/routes/tests.rs` sends the request through the HTTP route against the mock engine, with the tool parser set to `ParserSelection::None`.

- With the fix: passes (400, `BadRequestError`).
- Without the fix (reverting `rust/src/chat/src/error.rs`): fails with `left: 500, right: 400`.

**Test commands and results** (run from `rust/`):

| Command | Result |
|---|---|
| `cargo test -p vllm-server --all-features` | 510 passed |
| `cargo test -p vllm-chat --all-features --no-fail-fast` | All pass except 3 `roundtrip` tests (`roundtrip_kimi_k25`, `roundtrip_mimo_v26`, `roundtrip_step5`), which fail locally while loading Hugging Face model files. They fail the same way without this change. |
| `cargo fmt --all -- --check` | Pass |
| `cargo clippy --workspace --all-targets --all-features --locked -- -D warnings` | Pass |

**Model evaluation**: not applicable. The request is rejected before it is submitted to the engine, so model output, accuracy, and serving performance are unaffected.

## Details

**Root cause.** The request path is `chat_completions` → `ChatLlm::chat` → `ChatRequestProcessor::prepare` → `DefaultChatOutputProcessor::with_response_template` → `resolve_tool_parser`. When the tool parser selection is `None`, `resolve_tool_parser` returns `vllm_chat::Error::ParserDisabled { kind: "tool" }`. The handler maps it with `chat_submit_error`, which returns 400 only when `is_request_validation_error()` is true. `ParserDisabled` was not in that list, so it fell through to `server_error!` (500).

**Why 400.** The client can fix the request by removing `tools`, like other errors already in the list such as `UnsupportedMultimodalContent` (an image sent to a text-only model). `rust/AGENTS.md` also asks for parity with the Python frontend's error status codes. Returning 500 makes clients treat a healthy server as faulty: OpenAI SDKs retry 5xx, and it counts toward server-error alerting.

**Not a duplicate.** #62321 and its work (`/tokenize` by @MuonChaser, `/detokenize` in #62775) cover endpoints that wrap every error in `server_error!`. Here, `/v1/chat/completions` already uses `chat_submit_error`; the gap is a single missing variant in `is_request_validation_error`. I found no open issue or PR for this case (searched for `tool parsing is disabled`, `is_request_validation_error`, and Rust frontend tool parser / status code PRs).

**Deviation from Python.** The status code now matches, but the message does not: Python names the flags to set, while Rust only says tool parsing is disabled. Aligning the message is out of scope for this PR.

**Testing scope.** Error mapping is validated with the in-process route test against the mock engine, following the Validation section of `rust/AGENTS.md`. The test asserts the status code and error type only; I can also assert the message if preferred.

**Follow-up.** `ParserUnavailableForModel` (parser selection `Auto`, but no parser is known for the served model) also returns 500. I left it out because it looks closer to a server configuration problem that might be better detected at startup. I'll open a separate issue to discuss it.
