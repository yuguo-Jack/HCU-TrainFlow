- NicolasHug · comment · 2026-06-25T09:35:15Z · [source](https://github.com/vllm-project/vllm/pull/44598#issuecomment-4797819713)

As requested by @Isotr0py I benchmarked this against TorchCodec and against the previous `pyav` backend in https://github.com/vllm-project/vllm/pull/46609 (see results there). Here are my 2 cents:

- This new pyav backend is much faster than the previous pyav backend on sparse sampling, but slower on dense sampling (with high number of threads, which is the current vllm default).
- TorchCodec is faster than *both* pyav backends on both sampling scenarios: TC is much faster on dense sampling , and a tiny bit faster on sparse sampling.

The reason TC is faster is that it's smart about when it should seek vs just decode frames forwards. I recently implemented a heuristic for that (see https://github.com/meta-pytorch/torchcodec/issues/1488). You could implement the same heuristic for pyav, although of course it's up to you to decide whether you want to own that complexity within vllm, or let TorchCodec handle it.

My note also explains why your new pyav implementation is slower than the previous one on dense sampling: sometimes, it's just better to NOT seek! And this is especially true with large number of threads in `FRAME` threading (what this PR is doing).

----

What this PR is doing via `_demux_keyframes()` is what TorchCodec's does by default: it scans the file to find the keyframes, which allows for exact and fast seeking behavior. It's worth noting that this scan strategy *can* be detrimental:


- for long videos, it's sometimes just better not to scan, because the scan isn't free! See e.g. https://meta-pytorch.org/torchcodec/stable/generated_examples/decoding/approximate_mode.html#performance-frame-decoding-and-clip-sampling
- typically when the video is streaming from the web, you definitely don't want to scan for keyframes because that would download / materialize the entire stream in memory. Streaming videos is not supported by vllm at the moment I think, but it could be in the future?

TorchCodec solves all this already, and allows to *not* scan via `seek_mode="approximate"`. If you want to allow that with the pyav backend, you'd need yet another implementation, potentially many.

----

On keyframe sampling: TorchCodec exposes a *private* `VideoDecoder(...)._get_key_frame_indices()` method. I'm happy to expose it publicly if you need it.
