# [Perf] Drop BasevLLMParameter's Python `__torch_function__`

[Upstream PR](https://github.com/vllm-project/vllm/pull/63785) · state: closed · merged: True

## Original PR description




## Overview

`BasevLLMParameter` overrides `__torch_function__` with a Python classmethod. The override only forwards to `Parameter`'s disabled implementation. Since #62326, quantized weights and scales stay `BasevLLMParameter` subclasses after `process_weights_after_loading`. As a result, every eager op that takes one of them goes through Python `handle_torch_function`. This PR removes the override. The subclasses then inherit `torch._C._disabled_torch_function_impl` from `Parameter`, which torch short-circuits in C++.

## Claims

- Fixes a host-side regression from #62326 on steps that run outside full CUDA graphs: prefill and mixed prefill+decode steps.
- GLM-5.2-FP8, TP4 on one GB300 node, same-node A/B against main on 3 nodes:
  - c1 TTFT for 1024-token prompts drops from 220.4 to 207.0 ms (-6.1%);
  - worker `execute_model` host time drops 8.7 ms per prefill step (-4.5%) and 11.2 ms per mixed step (-4.4%);
  - TPOT is unchanged: pure decode replays full CUDA graphs and dispatches no ops.
- No behavior change:
  - #62326's guarantees are untouched: the same parameter objects, classes, loader attributes and `data_ptr`;
  - op results were plain tensors before (`super().__torch_function__` is the disabled implementation) and still are;
  - greedy outputs are identical and GSM8K is within run-to-run noise.

## Details

**Root cause.**
- #23036 added the override, together with a torch-2.7-only `traceable_tensor_subclasses` Dynamo workaround (`_torch27_patch_tensor_subclasses`).
- #33209 removed the workaround when torch < 2.8 support was dropped, but left the override.
- The override does nothing at runtime: it calls `super().__torch_function__`, i.e. `Parameter`'s `_disabled_torch_function_impl`. Its presence still makes torch treat these parameters as having a Python torch function. Every op, and every Python-level `Tensor` method or property access on them, then goes through `handle_torch_function` and the classmethod.
- Before #62326, most quantization methods re-registered plain `Parameter`s in `process_weights_after_loading`, so FP8/FP4 weights and scales did not pay this cost.
- #62326 keeps the original objects so that reload and RL refit keep their loader metadata. The quantized weights and scales of every linear and MoE layer now pay this cost on every eager op.

**Fix.** Delete the override. `BasevLLMParameter` then behaves like `torch.nn.Parameter`:
- `__torch_function__` is the disabled implementation;
- `isinstance`, class, attributes and object identity are unchanged;
- op results stay plain tensors.

This keeps everything #62326 relies on. A global monkey-patch or unwrapping params after loading would undo #62326's goal.

**Scope.**
- Only steps that dispatch ops eagerly benefit: prefill, mixed and piecewise steps. Full-CUDA-graph decode is unchanged.
- The gain grows with the number of quantized layers and ops per step.

## Why this is not a duplicate

- `gh pr list --repo vllm-project/vllm --state open` searches found no PR that touches `BasevLLMParameter.__torch_function__` or the overhead from #62326. Search terms: `__torch_function__`, `BasevLLMParameter`, `replace_parameter`, `62326`, `torch_function overhead`, `handle_torch_function`, `ModelWeightParameter overhead`.
- #62407 (part 3 of the #62326 series, open) changes which params stay registered and does not touch `parameter.py`. This PR is independent of it and helps it as well.
- The only earlier change to the override is #25613, reverted by #25681. It returned `NotImplemented` on torch < 2.8 for a Dynamo bug and did not remove the dispatch.
- No upstream issue covers it.
