# [HiSparse] Support the extensible KV cache

[Upstream PR](https://github.com/vllm-project/vllm/pull/65214) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

Lets HiSparse run on the extensible KV cache (#56492), which previously excluded it. HiSparse's device pool is reserved and grown like any other KV cache. Its host pool stays outside it.

## Claims

- HiSparse uses the extensible KV cache by default.
- At default flags, GPU+host KV capacity grows by 16% and throughput matches `main`. GSM8K under heavy host offload also matches `main`.
- HiSparse with NIXL P/D and with the Mooncake store connector works on the extensible cache.
- Fixes two warmup crashes that removing the gate exposed:
  - the FlashInfer HiSparse autotune read hot blocks that had not been committed;
  - context-prefill warmup overflowed the hot group's fixed-size block-table rows.

## Validation

All runs on B200 with `VLLM_USE_V2_MODEL_RUNNER=1`, against base 3b6eeb0606.

**Default flags.** GLM-5.3-NVFP4, TP4, no `--gpu-memory-utilization`. Two runs each, server restarted for every point.
```

  --max-num-batched-tokens 4096 --kv-cache-dtype fp8 --block-size 64 \
  --attention-config '{"hisparse_config":{}}' \
  --kv-transfer-config '{"kv_connector":"HiSparseConnector","kv_role":"kv_both","kv_connector_extra_config":{"host_pool_gib":64}}'
vllm bench serve --dataset-name random --random-input-len 16384 --random-output-len 1024 \
  --num-prompts 2c --max-concurrency c --ignore-eos --seed 42
```

## Details

- **Host-resident tensors stay out of the extensible paths.** `ExtensibleKVCache`, `committed_views`/`committed_kv_cache_tensors` and `shrink_kv_cache_configs` skip `host_resident` tensors. `host_resident` is an existing generic field.
- **The post-extend cache dict matches the fixed path's.** The runner keeps the dict `init_kv_cache` returned (`kv_caches_by_layer`); `extend_kv_cache` swaps in the committed views and passes it to `runner.kv_caches` and the connectors. Host layers keep their views and HiSparse's hot slabs stay out. `committed_views` gives layers laid out over the raw buffer (`has_layer_views=False`) the committed prefix, and `rebind_hisparse_device_caches` rebinds HiSparse's resident and hot views over it, so they span the committed blocks rather than the reservation. CUDA graphs captured before extend stay valid: the base address does not move.
- **Autotune:** the HiSparse autotune commits `cdiv(topk, hot_block_size)` blocks before tuning.
- **Warmup:** clamps reservations to the spec's block-table row length (`max_num_blocks_per_req`), which bounds HiSparse's fixed-size hot rows. Mamba is exempt: in non-align modes `MambaManager` can hold more blocks than its row length.
- **Considered:** feature-owned `if hisparse:` branches in the model runner and `extend_kv_cache`. That is more code, and it still needs the same planning changes.
- **Not covered:** sleep/wake with HiSparse on the extensible cache.

File: `vllm/v1/worker/extensible_kv_cache.py` · line None

**Blocking:** after extend, the dict passed to `runner.kv_caches` and the connector no longer matches the fixed-size path for HiSparse.

On the fixed path, `bind_hisparse_kv_caches` deletes every `*_hisparse_hot` entry ("nothing downstream binds or registers it") and replaces every `*_hisparse_resident` entry with the handle's view. Here the dict is rebuilt from `committed_views()`, which knows nothing about HiSparse. Since `HiSparseHotSpec.has_layer_views` is False, each hot layer gets `self.buffer.full_view()`, a flat uint8 tensor over the **whole reservation**. That goes to:

- `runner.kv_caches`: `copy_kv_cache_blocks_inplace(self.kv_caches, num_blocks, ...)` in the V2 runner would `divmod(reservation_bytes, num_blocks)` on it, which either trips the remainder assert or copies bytes at the wrong offsets in the hot slab (if CoW block copies can occur with HiSparse).
- the KV connector: this breaks the `committed_views` contract that connectors "must not see the reservation". NIXL happens to skip these layers (no spec), but e.g. `TransferTopology(tensor_shape=next(iter(kv_caches.values())).shape)` reads whichever entry is first, and connectors that walk every entry would register the whole reservation.

The host-layer `update` below patches one symptom of this mismatch. A simpler fix that covers all of it: keep the dict `init_kv_cache` returned on the runner, and here rebuild it as
```python
kv_caches = {name: committed.get(name, view) for name, view in initial_kv_caches.items()}
```
That gives exactly the fixed path's keys, keeps the host-resident layers without a special case, and drops the hot slabs. It would also be worth asserting in `test_hisparse_extensible_kv_cache` that the post-extend `runner.kv_caches` / connector dict keys match the fixed-size run.

- njhill · comment · 2026-11-02T21:51:23Z · [source](https://github.com/vllm-project/vllm/pull/65214#discussion_r4448212219)

File: `vllm/v1/worker/gpu/warmup.py` · line None

Lower priority / optional: this adds a HiSparse-specific `isinstance` to the generic warmup reservation. I realize this function already special-cases a few spec types, but here the spec already exposes the bound: `HiSparseHotSpec.max_num_blocks_per_req()` returns `blocks_per_request`. Clamping every spec by `kvcache_spec.max_num_blocks_per_req(vllm_config, max_model_len)` (the block-table row length) would express the same thing generically. It should be a no-op for other attention specs, since `num_tokens` is already capped at `max_model_len`, and it avoids the warmup knowing about HiSparse.
