# [Perf][XPU][Kernel] Use small-M tiles for the Triton W8A8 INT8 GEMM

[Upstream PR](https://github.com/vllm-project/vllm/pull/64190) · state: open · merged: False

## Overview

On XPU, W8A8 INT8 linears run through `triton_scaled_mm`, and for M <= 64 its heuristic picks a 64-row tile with a 256-deep K step. This changes the tile for M <= 64 on XPU to `(next_power_of_2(M), 32, 128)` with 8 warps. Other platforms, and M > 64 on XPU, keep the current tiles.

Related: #45126 changes the same heuristic for NVIDIA and leaves non-CUDA platforms alone, so the two do not overlap in behaviour, but it moves this `if` chain into a helper and changes how `num_warps` is passed, so whichever lands second needs a rebase. vllm-project/vllm-xpu-kernels#196 proposes a oneDNN W8A8 INT8 GEMM for XPU; it is compared below.

## Claims

On Arc Pro B70, Qwen3.8-27B shapes:

- The INT8 GEMMs of one forward pass at TP=1 shapes go from 408 to 555 GB/s (67% to 91% of the 608 GB/s memory bandwidth) at M = 1, and from 408 to 492 GB/s (67% to 81%) at M = 64.
- That is 1.21x to 1.45x less time at TP=1 shapes and 1.23x to 1.36x at TP=2 shapes, for M = 1 to 64, and within 1.5% (TP=1) and 2.6% (TP=2) of the best tile found for each M.
- End to end, TP=2, W8A8 INT8: 23.49 to 32.67 tok/s at one request (**+39%**); 16, 32 and 64 concurrent requests **+28%**, **+24%** and **+13%**.
- For int8 inputs the result does not depend on the tile: accumulation is in int32, so a different tiling gives the same sums. End to end at temperature 0 the output is identical before and after, token ids and top-5 logprobs.

### End to end

## Details

At small M the GEMM reads every weight once and does little else, so it is bound by memory bandwidth. The current heuristic serves M <= 64 with a 64-row tile and a 256-deep K step, so at M = 1 sixty-three of the 64 rows are padding, and with 64- or 128-wide N tiles there are only 64 to 272 work-groups per call on these shapes. Narrower N tiles give more work-groups.

`BLOCK_M` still has to cover M. Each work-group reads the full K extent of its N tile, so every additional row block reads the whole weight again. That is why a fixed 8-row tile loses to the current tiles at M = 32, and why `BLOCK_M` follows `next_power_of_2(M)`. Tiles of 1, 2 and 4 rows compile and are 0.4 to 3% faster than 8 rows at M = 1 to 4, so `BLOCK_M` is not floored.

One expression rather than a per-M or per-shape table, because it stays within 2.6% of the best found at every M on both TP=1 and TP=2 shapes. `BLOCK_N` 32 with 8 warps was chosen over 64 with 4 warps because the latter, the best tile at M = 4 on TP=2 shapes, is 3.5% off there in the worst case and 9.8% off at TP=1, M = 32. `num_warps` was not passed before, so the launch now passes the default 4 explicitly outside this branch; that does not change the other paths.

The cut at 64 is where the current heuristic's second branch ends, and the sweep above shows why the rule should not go further: at M = 96 and 128 a 128-row tile with 16 warps is 19 to 36% faster than the rule. The current tiles above 64 are slow on XPU as well, but that is a prefill change with different validation, left for a separate PR.

The branch is gated on `current_platform.is_xpu()`, so CUDA and ROCm keep the current tiles. It reads only the shape, so it adds no host-device synchronisation. It is taken per call with the real M because `triton_scaled_mm` runs inside the `int8_scaled_mm_func` custom op since #57331, which torch.compile does not trace into. Under an XPU graph that M is the padded capture size.

The branch does not look at the input dtype, so fp8 inputs to `triton_scaled_mm` on XPU take it too, and with fp32 accumulation their result can differ in the last bits between tiles. No XPU linear passes fp8 here: `TritonFP8ScaledMMLinearKernel` is CUDA and ROCm only, and XPU FP8 linears use their own kernels. The fp8 cases of the tests above pass.

End to end at one request a decode step shortens by 12.0 ms (42.6 to 30.6 ms), more than the 8.0 ms the kernel sum predicts. I have not traced where the rest comes from.

I have only measured an Arc Pro B70; other Intel GPUs may prefer other tiles.

## AI disclosure

Claude Code with Opus 5.5 medium (Anthropic) read the kernel and its XPU dispatch, found that the 64-row tile was the cause, wrote the change, built the INT8 checkpoint, ran the tile sweeps and the end-to-end measurements, built the INT8 path of vllm-project/vllm-xpu-kernels#196 for the comparison, and drafted parts of this description. I asked whether INT8 decode was slower than memory bandwidth allows, which started this. The first version covered only M <= 8, with the cut taken from the tile height; I questioned the limit, and the sweep over M = 1 to 32 that followed led to `BLOCK_M` following M. I had the sweep repeated on TP=1 shapes, which moved `BLOCK_N` and the warp count to values that hold on both. I asked whether 64 concurrent requests could gain as well, which extended the range to M = 64, and what the cut at 64 rests on, which led to the sweep at M = 96 to 256. I had a separate agent re-check the measurements from the raw logs; it found an unverified claim that 8 rows is the smallest XMX tile, which led to dropping the floor, and a reproduction command with an environment variable this image ignores. I asked it to look for overlapping PRs, which found #45126 and vllm-project/vllm-xpu-kernels#196. For the comparison it proposed building the whole package; I had it pick only the INT8 changes onto current headers instead. I dropped the tests it proposed to add, since the existing ones already reach the changed branch. I reviewed the diff and the description in full.
