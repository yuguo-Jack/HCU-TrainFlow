# [Bugfix][Tool Parser] Keep dots string "null" literal and surface invalid booleans

[Upstream PR](https://github.com/vllm-project/vllm/pull/60516) · state: open · merged: False

## Original PR description

## What

`DotsToolParser._convert_param_value` checked `value.lower() == "null"` before looking at the schema type, so a string-typed parameter sent the literal text `null` came back as `None`, and the boolean branch mapped anything that was not `true`/`1` to `False`, so `"maybe"` or `"yes"` silently became `false`. Both rewrite the arguments the model actually produced; client-side schema validation then sees a value the model never sent (`null` is not a `string`, and a silently-false flag can flip tool behavior).

Repro (CPU, no serving needed):

```python
from vllm.tool_parsers.dots_tool_parser import DotsToolParser
p = DotsToolParser.__new__(DotsToolParser)
p._convert_param_value("null", "string")    # -> None (should be "null")
p._convert_param_value("maybe", "boolean")  # -> False (should stay "maybe")
```

## Fix

- `null` converts to `None` only when the schema admits null: a `{"type": [..., "null"]}` union, a bare `{"type": "null"}`, or `anyOf`/`oneOf`/`allOf` with a null arm. `_resolve_param_type` used to drop the null member of those unions; it now forwards them as a list so the converter can see the admission.
- Boolean conversion maps only `true`/`1` and `false`/`0`; any other text passes through unchanged so schema validation rejects it instead of silently reading `false`.
- Non-nullable scalars (`integer`, `number`, `boolean`) receiving the text `null` now keep the raw text too, consistent with how invalid numbers were already passed through.

Valid inputs are unchanged: nullable unions still turn `null` into `None`, valid booleans still convert, and numeric parsing is untouched.

## Why not a duplicate

#54678 touches the same file but fixes catastrophic regex backtracking (ReDoS) in the block/invoke patterns; it does not change value conversion. No open PR or issue covers the null/boolean coercion in this parser (searched `dots tool parser`, `dots_tool_parser`, `dots null`).

## Tests

New cases in `tests/tool_parsers/test_dots_tool_parser.py`, all red before the fix:

- `test_convert_param_value_null_only_when_schema_allows`: string keeps `"null"`, unions and bare `null` type still get `None`, non-nullable scalars keep raw text.
- `test_convert_param_value_boolean_rejects_invalid_text`: true/false/1/0 convert, `"maybe"`/`"yes"` pass through.
- `test_non_stream_xml_null_literal_and_anyof_nullable`: end-to-end through `extract_tool_calls` with `anyOf: [string, null]`.
