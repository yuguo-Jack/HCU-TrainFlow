# [Bugfix][KV Offload][P2P] Retain unconfirmed source WRITEs across session teardown

[Upstream PR](https://github.com/vllm-project/vllm/pull/64250) · state: closed · merged: True

## Original PR description



## Overview

Part of #63602 (gap 3). When a P2P session is torn down, the source no longer releases a NIXL WRITE that may still be running. It keeps that transfer's handle, its source pins and the peer's old registration until the transport reports the transfer stopped, bounded at 120 s.

## Claims

- `ServerRole.close()` no longer releases `PROC`/`PEND` transfers or fails (unpins) the store jobs they read.
- `remove_remote_peer()` no longer frees the descriptor list and remote agent that a running transfer was prepped against.
- A reconnect under the same `peer_id` never sees the old session's retained transfers.
- Retention is bounded. Past `_RETAINED_HOLD_CAP_S` (120 s) the transfer is force-released with an error log, so a wedged handle can't permanently shrink the cache.

## Details

**Root cause.** On reap, `_reap_dead_sessions` / `_reap_idle_sessions` call `session.close()` and then `ServerRole.close()`. That ran `transport.cancel(all inflight)` in the default `"immediate"` mode and returned every store job as failed. The manager then called `remove_remote_peer()`. Releasing a `PROC` handle does not stop the RDMA WRITE (`NixlTransport.cancel` docstring; #59790 saw a WRITE land after `remove_remote_agent`). So this unpinned CPU blocks the NIC may still read, and freed NIXL request and descriptor state while it was still in use. `_drain_abort` and `_timeout_pending_store_jobs` already refuse to do this, and teardown was the one path that didn't.

**Change.**
- **`ServerRole.close()`** cancels in `"wait"` mode. Transfers that are still running come back as `SessionCloseResult.retained` (`tid → store job_ids`), and their jobs are left out of `failed_stores`.
- **`NixlTransport.remove_remote_peer()`**
  - Marks the peer's in-flight entries `retired`. `poll()` skips retired entries, so a reconnected session under the same id can't receive a stale completion.
  - Defers releasing the old dlist and remote agent until no retired transfer references them.
  - `poll_retired()` releases transfers that have stopped. It uses the same terminal rule as wait-mode cancel: done, a non-PROC state, or `NIXL_ERR_REMOTE_DISCONNECT`. It does not charge the peer, since a reconnected peer under that id isn't at fault.
- **`DataTransport`** gets default `poll_retired()` / `force_release_retired()`, so other transports need no change.
- **Manager**
  - Keeps `_retained` and calls `_poll_retained()` once per poll round. A store job fails (unpins) only once no retained transfer reads it.
  - Past 120 s it calls `force_release_retired()` and logs an error.
  - Shutdown keeps its existing bounded drain, now including retained transfers.

**Tradeoffs and limits.**
- The 120 s cap is a judgment call: after it, the old unsafe release happens anyway, but rarely and loudly instead of on every teardown. Whether NIXL/UCX teardown can fence a stalled WRITE, which would let the cap shrink or go away, is the open fencing question in #63602.
- This is the source side only. Consumer slot reuse after disconnect is #61667.
- This PR should land before #63715 (consumer disconnect on a missed AbortAck), because that change makes teardowns more frequent. The gap 2 source-side stall deadline is stacked on this PR and follows separately.

Complexity: about 190 non-test lines (medium), all within `vllm/v1/kv_offload/tiering/p2p/`. No core components are touched.
