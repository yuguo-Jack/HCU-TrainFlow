# [ROCm][Perf] Fuse act_and_mul into the AITER MXFP4 GEMM's activation quant

[Upstream PR](https://github.com/vllm-project/vllm/pull/59153) · state: open · merged: False

## Original PR description

## Purpose

On ROCm with AITER, the MXFP4 linear quantizes its input inside `gemm_with_dynamic_quant`. That is a custom op Inductor cannot fuse into. So a SiLU- or GELU-and-mul feeding an MXFP4 `down_proj` runs three kernels: an activation kernel, a HIP MXFP4 quant kernel, then the GEMM.

AITER already ships a single kernel for the first two, `act_mul_and_mxfp4_quant`. This PR uses it on the ASM GEMM path.

- **`gemm_with_dynamic_quant` gains an optional `activation`** (`"silu"`, `"gelu"`, `"gelu_tanh"`). When set, `x` is the concatenated gate/up tensor.
  - On the ASM path, the op runs `act_mul_and_mxfp4_quant(..., shuffle=True)` and passes the result to `gemm_a4w4`.
  - The small-M preshuffle branch (M <= 64 with tuned weights) applies the activation and keeps its own quant, because below M = 32 it needs unshuffled scales.
  - The Triton GEMM path (ASM off) is never rewritten. On MI355X the fused kernel measured 7% slower there than Inductor's act_and_mul plus `dynamic_mxfp4_quant`.
- **`RocmAiterActMulMxfp4GemmFusionPass`** rewrites `act_and_mul -> gemm_with_dynamic_quant(..., True, ...)` into the single call. It is registered under `fuse_act_quant` next to `RocmAiterSiluMulFp8GroupQuantFusionPass`.
- **`MatcherGeluAndMul`** matches `GeluAndMul` in both its custom-op and native forms, and reports the activation the matched graph actually computes. On ROCm, `GeluAndMul.forward_native` drops the tanh approximation, so a native-form match is replaced with `"gelu"`, not `"gelu_tanh"`. That keeps the rewrite semantics-preserving.
- **Fake implementation fix.** The fake for `gemm_with_dynamic_quant` now takes its arguments in the same order as the op. Before, `x_scales` came before `rocm_use_aiter_fp4_asm_gemm`, so `out_dtype` could not reach the fake positionally.

The pass is opt-in through the existing `fuse_act_quant` flag. `enable_act_fusion` already turns that flag on for NVFP4 models, because "FP4 quant is always custom so Inductor cannot fuse it". The same reasoning covers MXFP4, and a follow-up can extend that default.

## Test Plan

New test: `tests/compile/passes/test_rocm_aiter_act_mul_mxfp4_fusion.py`, ROCm with AITER, gfx950. It covers the ASM and Triton GEMM paths x SiLU / GELU / GELU-tanh x custom-op and native forms x 16 and 256 tokens. It asserts:
- the pass matches exactly once on the ASM path and never on the Triton path;
- the fused call carries the activation the matched graph computed (exact GELU for the native form on ROCm);
- against the exact fp32 product, the fused output is no less accurate than the unfused output (within 5%).

```
pytest tests/compile/passes/test_rocm_aiter_act_mul_mxfp4_fusion.py
```

The AITER ASM MXFP4 GEMM exists only on gfx950. The test therefore skips on the MI300 "PyTorch Compilation Passes" Buildkite step and runs on MI355X. `pre-commit run --files <changed files>` passes locally: ruff, typos, mypy-3.10, test tethering, SPDX, forbidden imports, and torch.cuda calls.

End to end: `vllm serve` with Gemma 4 31B (`amd/gemma-4-31B-it-MXFP4`, whose MLP is `GeluAndMul("tanh")` feeding an MXFP4 `down_proj`) on one MI355X, TP1, MTP k=2, FP8 KV cache. The only change between runs is `--compilation-config '{"pass_config":{"fuse_act_quant":...}}'`. Measurements:
- prefill throughput with 16 concurrent 10K-token prompts: one warm-up, then three measured runs;
- GSM8K, 250 problems, temperature 0.

## Test Result

The unit test passes, 24 cases, on MI355X (gfx950) with the `vllm/vllm-openai-rocm:nightly` image from 2026-09-28 (vLLM 0.30.1rc1.dev143, AITER 0.1.22.post1), with this PR's files applied.

End to end, same image, `VLLM_ROCM_USE_AITER=1`:

| `VLLM_ROCM_USE_AITER_FP4_ASM_GEMM` | `fuse_act_quant` | Prefill req/s (3 runs) | GSM8K 250 |
|---|---|---|---|
| 1 | false | 2.76, 2.76, 2.76 | 98.8% |
| 1 | true | 2.81, 2.81, 2.81 (+1.8%) | 98.8% |

The debug log's `fusion pass matches` shows the pass matching in the compiled pieces that hold the MLPs. The same fusion, applied as a model patch on vLLM `v0.30.0`, measured +1.5% to +1.8% prefill with GSM8K unchanged.

A side observation while measuring, not changed here. With `VLLM_ROCM_USE_AITER_FP4_ASM_GEMM` unset (its default), this model runs its linears on AITER's Triton FP4 GEMM:

| Mode | Prefill req/s |
|---|---|
| default (unset) | 1.89 |
| ASM GEMM enabled | 2.77 (+47%) |

It may be worth enabling the ASM GEMM by default on gfx950.
