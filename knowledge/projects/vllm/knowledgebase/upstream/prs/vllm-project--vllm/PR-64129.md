# [Perf][DCP] Sparse indexer: key only significant bits in the DCP top-k merge

[Upstream PR](https://github.com/vllm-project/vllm/pull/64129) · state: closed · merged: True

## Original PR description




## Overview

Since #61149 (DeepGEMM 2026-09-30), the SM100 MQA logits of the sparse indexer are BF16. Under DCP they are upcast to FP32 before the top-k, so the low 16 bits of every candidate score that reaches the DCP top-k merge are zero. The merge selector, `StableTopKFromGatheredCandidatesKernel`, radix-sorts the 64-bit key `score << 32 | ~token_id` in 11-bit passes. BF16 scores almost always tie at the top-k boundary. The radix then also walks the 16 zero score bits and the constant high bits of the token id, and each of those passes funnels every remaining candidate into a single histogram bin.

This PR packs only the bits that carry information into the key: the 16 high score bits when the logits were BF16, and the token-id bits that positions below `max_model_len` need. The selected set is unchanged.

## Claims

- Removes the DCP top-k merge cost that #61149 added. It applies to every DSA model with a sparse indexer under DCP on SM100 (DeepSeek-V3.2, GLM-5.x).
  - With BF16 scores, the selector costs 1.6-1.7x what it costs with FP32 scores.
  - With this PR it is back to the FP32 cost. Per call at top-2048 on GB300:
    - DCP4: 16.7 → 10.6 us (FP32: 10.4), and 21.0 → 11.5 us on concentrated scores;
    - DCP8: 24.8 → 14.5 us (FP32: 14.3), and 32.2 → 19.0 us.
- GLM-5.3, TP4 DCP4 on one GB300 node, 60k-token prompts, 4 runs per variant on 2 nodes:
  - the selector goes from 21.0 to 14.2 us per call in decode (21 calls per step);
  - c1 TPOT p50 drops from 13.55 to 13.44 ms (-0.8%);
  - c2 TPOT p50 drops from 17.77 to 17.65 ms;
  - c8 ITL p50 drops from 19.30 to 19.13 ms.
- No behavior change:
  - The selection uses the same total order: score at the precision it was computed in, then the smaller token id.
  - Main and this PR select the same set:
    - in unit tests with forced boundary ties;
    - on 28.4M rows merged in GLM-5.3 runs and checked against main's selector. 97% of the rows with more than 2048 candidates had a tie at the boundary.
  - FP32 logits keep 32 score bits.
  - GSM8K is within run-to-run noise.

## Details

**Root cause.**
- #61149 made the SM100 MQA logits (`fp8_fp4_mqa_logits`, `fp8_fp4_paged_mqa_logits`) BF16. `sparse_attn_indexer` upcasts them (`as_fp32_logits`) whenever DCP is on.
- `StableTopKFromGatheredCandidatesKernel` builds `score_key << 32 | ~token_id` and runs up to 6 radix passes (11 bits each, the last one 9). It stops at the first pass whose threshold bin fits.
- With FP32 scores, the first 1-2 passes usually resolve the boundary. A BF16 score is complete after the first 16 key bits (passes 1-2), and it often ties at the boundary. The radix then continues:
  - pass 3 sees the 10 low score bits, which are all zero, plus the top id bit;
  - pass 4 sees id bits 30-20, which are constant because ids are below `max_model_len` (16 bits for a 64k context);
  - only passes 5-6 separate the tied candidates.
  - In the passes that separate nothing, every remaining candidate falls into one histogram bin, and the shared-memory atomics serialize on it.

**Fix.**
- `CompileKey` gains `score_bits` and `id_bits`.
- The key is `score_key >> (32 - score_bits)` followed by the low `id_bits` of `~token_id`, packed at the top of the 64-bit word. With BF16 logits and a 64k context, that is 32 bits and 3 passes.
- Padding keys stay 0 and still decode to -1.
- The order is unchanged:
  - the dropped score bits are zero for upcast BF16 values;
  - `~id & mask` preserves the order of ids below `2**id_bits`.
- `sparse_attn_indexer` (DSA) and the GLM-5.3-Flash kpool indexer pass the following:
  - `score_bits=16` when the raw logits are BF16;
  - `id_bits` from `max_model_len`, or `max_pool_len` for kpool pool ids.
  - On a DCP rank whose prefill chunk is empty (no logits to inspect), `score_bits` follows the platform. That keeps it on the warmed-up key. 32 bits would also select correctly.
- Warm-up compiles the SM100 key: 16 score bits, and id bits for `max_model_len // index_kpool`.
- The last radix pass can now be narrower than the 512-thread block. For example, a 30-bit key gives passes of 11, 11 and 8 bits. The bin scan now covers whole block slices; bins at or above `num_bins` stay zero.

**Scope.**
- Only DCP > 1 with BF16 indexer logits (SM100) changes speed. FP32 logits keep 32 score bits.
- DCP = 1 does not run the merge.
- No new host syncs: `score_bits` comes from the logits dtype and the platform, and `id_bits` from `max_model_len`. All three are host-side metadata.
- No new CI step: the new test runs in the existing B200 "V1 Attention" step (`pytest v1/attention`), which has CuTeDSL.

** Not a blocker **

One thing on the benchmarks. They all use `max_model_len=65536`, which conveniently gives a 32-bit BF16 key that fits in 3 passes. At DSv4’s 1M you need 4 more. That pushes it to a 4th pass. 

I ran the selector alone on a sm100. At DCP8 that extra pass costs 1.5–4.7 µs, so the speedup can go from ~1.7× down to ~1.3×. At DCP4 I didn’t see a consistent difference. 

In any case, this PR is still faster in every config I tried and always picks the right tokens, so this _could be a follow-up_.

For (future) reference: roughly what I mean: pick the pass widths at compile time instead of fixed 11-bit passes:

```Python
max_bits = 12 if -(-used_bits // 12) < -(-used_bits // 11) else 11
num_passes = -(-used_bits // max_bits)
base, extra = divmod(used_bits, num_passes)
pass_bits = tuple(base + (i < extra) for i in range(num_passes))
# 32 -> (11,11,10), 34 -> (12,11,11), 36 -> (12,12,12), 48 -> (12,12,12,12)
```

then unroll the passes with `range_constexpr` (early exit on finished), size the histogram as `1 << max(pass_bits)`, and clear only the bins each pass scans.
