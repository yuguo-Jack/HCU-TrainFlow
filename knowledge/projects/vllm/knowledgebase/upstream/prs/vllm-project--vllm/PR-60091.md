# [ROCm][DSv4.1][Perf] Pass output_size to repeat_interleave in the Torch combine_topk_swa_indices

[Upstream PR](https://github.com/vllm-project/vllm/pull/60091) · state: open · merged: False

## Original PR description

## Purpose

On gfx950 the ROCm V4.1 sparse prefill uses the Torch `combine_topk_swa_indices`, once per layer per prefill chunk. Its two `torch.repeat_interleave(x, query_lens)` calls pass no `output_size`, so each one syncs with the host twice, to size the output and to validate `repeats`. On DeepSeek-V4.1-Flash that is 160 host syncs per prefill step (40 layers), and the GPU drains at each one.

This PR passes `output_size=num_tokens` to both calls. The caller slices `topk_indices` and `query_start_loc` with the same chunk bounds, so `query_lens` sums to `num_tokens`. Outputs are bit-identical, and decode and the NVIDIA paths are unchanged.

## Test Plan

MI350X (gfx950), DeepSeek-V4.1-Flash, TP=4 with expert parallelism, `VLLM_ROCM_USE_AITER=1`, `max_num_batched_tokens=16384`. Measured on the ROCm image's vLLM `0.3.1.dev160+gd05da62e9`, whose `combine_topk_swa_indices` is byte-identical to main; every measured step runs a single prefill chunk, as it would on main. Main and this PR were swapped in place on one server and interleaved in rotated order with the same seeds.

```bash
VLLM_ROCM_USE_AITER=1 vllm serve deepseek-ai/DeepSeek-V4.1-Flash -tp 4 --enable-expert-parallel \
    --max-model-len 16384 --max-num-seqs 768 --no-enable-prefix-caching

B="--model deepseek-ai/DeepSeek-V4.1-Flash --dataset-name random --random-input-len 8192 --ignore-eos"
vllm bench serve $B --random-output-len 1 --max-concurrency 1 --num-prompts 24          # TTFT
vllm bench serve $B --random-output-len 1 --random-range-ratio 0.25 --num-prompts 256   # prefill
vllm bench serve $B --random-output-len 1024 --random-range-ratio 0.25 \
    --max-concurrency 64 --num-prompts 192                                              # serving

pytest tests/v1/attention/test_rocm_aiter_triton_sparse_mla.py -v   # <paste result>
python tests/evals/gsm8k/gsm8k_eval.py                              # 1319 questions, 5-shot
```

Against main on five metadata cases (non-zero `query_start_loc` base, 1-token query, zero-query slot, 16K-token request, SWA-only layer), the outputs are bit-identical, and the host syncs per call drop from 7 to 3 under `torch.cuda.set_sync_debug_mode("warn")`.

## Test Result

Mean of 3–5 reps per arm; main's and this PR's ranges are disjoint in every row.

| workload | metric | main | this PR | Δ |
|---|---|---:|---:|---:|
| 8192 in, concurrency 1 | median TTFT (ms) | 340.7 | 321.1 | −5.7 % |
| 8192 ± 25 % in, rate inf | prompt tok/s | 31,440 | 32,443 | +3.2 % |
| 8K/1K ± 25 %, concurrency 64 | output tok/s | 1,717 | 1,763 | +2.7 % |
| | median TTFT (ms) | 608.7 | 572.2 | −6.0 % |
| | median TPOT (ms) | 33.34 | 32.47 | −2.6 % |
| | P99 ITL (ms) | 359.9 | 340.3 | −5.4 % |

That is about 20 ms saved per prefill step, roughly 120 µs per removed sync. GSM8K (1319 questions, 5-shot, greedy): main 0.9014, this PR 0.9083, standard error ±0.008.
