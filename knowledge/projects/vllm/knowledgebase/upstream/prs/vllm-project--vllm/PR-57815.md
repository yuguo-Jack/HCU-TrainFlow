# [Bugfix][Determinism] Refuse batch-invariant mode on the sparse indexer

[Upstream PR](https://github.com/vllm-project/vllm/pull/57815) · state: open · merged: False

## Original PR description

## Summary

`VLLM_BATCH_INVARIANT=1` looks like it works on DSA / sparse-indexer models. It
does not: the indexer's top-k has no batch-invariant backend, so which keys a
row attends to can change with the rest of the batch.

Every path is batch-dependent:

| backend | what makes it batch-dependent |
| --- | --- |
| `auto` | switches kernels at `AUTO_COOPERATIVE_MAX_ROWS` (64) rows — `indexer_topk.py:_resolve_auto` |
| `per_row` | picks among three algorithms from the **padded column count**, i.e. the batch's longest sequence (`sampler.cu`, `kSortingAlgorithmThreshold` / `kSplitWorkThreshold`); on gfx950 it also splits a row across blocks by row count |
| `persistent` | sizes its cooperative launch from occupancy and the batch's max sequence length, and falls back to `per_row` when the launch does not fit (`topk.cu`) |
| `cooperative` | only applicable under the 64-row cap, so it is by definition batch-conditional |

None of this changes the logits. It changes tie-breaking and therefore the
selection — and a different sparse selection is a different forward pass, not a
rounding difference.

The failure mode is silent: output drifts with concurrency instead of raising,
which is exactly what #53257 (DeepSeek-V4-Flash non-deterministic at
temperature=0, rate scales with concurrency) and #54521 (Qwen3.8-Flash-Next
greedy decoding non-deterministic from `persistent_topk`) describe.

This PR refuses at construction, naming the batch-dependent inputs, instead of
serving results the flag promises are batch-invariant.

## Why this matters beyond a debug flag

The GLM-5 tech report attributes an RL training collapse to exactly this class
of mismatch: a non-deterministic sparse selection "caused drastic performance
degradation during RL after only a few steps, accompanied by a sharp drop in
entropy." Rollout/training mismatch in sparse selection is not cosmetic, and a
flag that claims to eliminate it while not doing so is worse than no flag.

## Not a duplicate

- #55122 (`[Kernel] Make persistent_topk deterministic`) makes **one kernel**
  deterministic for a fixed launch. Complementary and necessary — but batch
  invariance also requires the *dispatch* not to change with the batch, which is
  what this PR is about. With #55122 merged, a row still takes a different
  kernel at 64 rows and a different algorithm when another request lengthens the
  padded width.
- #55958 (`Refuse batch-invariant mode on unsupported platforms`) applies the
  same philosophy at the platform level; this is the sparse-indexer case.
- #57129, #57109, #56084, #56258 add or gate indexer top-k backends; none of
  them is about batch invariance.

## Alternative considered

Pinning `auto` to a single backend under the flag. Rejected: it would still not
be batch-invariant, because `per_row`'s algorithm choice follows the padded
column count, so the guarantee would still be false — just harder to notice.
Making one backend genuinely invariant (fixed algorithm, batch-independent
padding) is kernel work and belongs in a separate change.

## Review rounds

A later adversarial round, told about the fixes already made and asked for new
defects, found two that the current revision addresses. Both are about the
reference backend's selection, not about pinning it:

- **P1 — `topk` does not pin tie order.** `torch.topk` documents that the
  order of equal values "is not guaranteed to be stable and may vary across
  different invocations", and the CUDA implementation dispatches differently by
  row count. A filtered row is nothing *but* ties, so selecting with `topk`
  left the very property this PR is pinning the backend for undefined.
- **P2 — a short row could lose one of its own tokens.** With the row shorter
  than the budget, an in-row `-inf` column tied with the padding and could lose
  to it. Both kernels emit `0..seq_len-1` in that case
  (`cooperative_topk.cuh:495`, `persistent_topk.cuh:934`), so the reference was
  dropping a token the kernels return, and `sparse_utils.py` treats the
  resulting `-1` as absent — a different attended set, not just a different
  order.

Both come from the same root: expressing the selection through float sentinels.
The revision drops that and orders by **(in row, score, column index)**
directly — a stable sort by score, then a stable sort that lifts the row's own
columns above the padding they tie with. Nothing rewrites a score any more, so
the previous revision's floor-clamp special case is gone too, and a genuine
score sitting at `finfo.min` keeps its rank (`test_a_filtered_column_never_outranks_a_real_score`).

Three tests cover the new contract: `test_padding_columns_never_fill_the_tail_of_a_short_row`
(replacing an assertion that encoded the P2 bug), `test_a_filtered_column_beats_padding_in_a_short_row`,
and `test_tied_scores_resolve_the_same_way_in_every_batch`.
