# [Bugfix][KV Offload][P2P] Drop a timed-out store job's blocks from the round's parked supply

[Upstream PR](https://github.com/vllm-project/vllm/pull/59329) · state: closed · merged: True

## Original PR description

## Purpose

In the symmetric P2P KV offload tier, a decode instance asks a peer whether it holds a prompt's KV, and the peer pins the matching blocks in its own cache until the fetch arrives. If the fetch is late, the pin times out and the peer's engine frees those cache slots for reuse, but the round still advertises the blocks as available. A fetch that arrives after the timeout then RDMA-reads slots that may already hold another request's KV, and reports success. The decode instance would continue generating from someone else's cache. This PR withdraws the advertised blocks when their pin times out, so the late fetch fails fast and the request prefills locally.

Concretely, in `vllm/v1/kv_offload/tiering/p2p/session/server.py`:

- Answering a lookup, the server pins the blocks through a store job and parks them in the fetch round: `add_stored_blocks` (`:94`) records them in `available` and the job in `pending_job_ids`.
- `_timeout_pending_store_jobs` (`:1121`) fails a job older than `_STORE_TIMEOUT_S` (`:40`, 30 s) with `StoreResult(success=False)`. The tiering manager maps that to a failed `JobResult` (`p2p/manager.py:859`), and the engine unpins the slots.
- The round's `available` entries and `pending_job_ids` are left as they were. A late `FetchMsg` matches them in `on_fetch` and submits the transfer.

**Fix:** when store jobs time out, remove their entries from every round's `available` map and `pending_job_ids`. The late fetch then has unmatched demand and takes the existing fail-fast path for symmetric rounds (`server.py:372`): `TransferDoneMsg(success=False)`, and the consumer prefills locally. The PD case where the prefiller finishes first has the same problem when its store stays parked longer than `_STORE_TIMEOUT_S` before the fetch arrives, and this fix covers it too: `finish()` has already set `finishing`, so `on_fetch` fails the round (thanks @liranschour for pointing this out and for reproducing the bug).

**Not a duplicate:** #53453 added a one-round-trip rejection of a late fetch for stores the *manager* reaps while still unbound (`_reaped_stores`). This PR covers the other case: a store job already bound to a session that `_timeout_pending_store_jobs` fails. #58168 (draft) edits `server.py` elsewhere and does not reference these identifiers. No open PR touches `_timeout_pending_store_jobs`.
