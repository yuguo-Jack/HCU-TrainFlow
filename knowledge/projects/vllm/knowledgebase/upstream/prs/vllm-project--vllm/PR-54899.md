# [ROCm][MLA][DCP] Pad the AITER MLA decode head count to a native tile

[Upstream PR](https://github.com/vllm-project/vllm/pull/54899) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Pads the AITER MLA decode head count up to one that AITER runs natively. DCP-gathered counts such as 48, 80 and 112 otherwise fold into 16-head pseudo-batches, and each pseudo-batch reads the KV cache again. The pad target comes from `aiter.get_mla_decode_shape_support` (ROCm/aiter#6107), which is in AITER v0.1.27. vLLM pins v0.1.27 since #63774. Padding is always on; there is no new env var.

Based on main `c1d8fade8d`. 3 files, +357/-15: `vllm/v1/attention/backends/mla/rocm_aiter_mla.py`, `tests/v1/attention/test_rocm_aiter_mla_mtp_split.py`, `tests/v1/attention/test_rocm_aiter_mla_dcp_cprr.py`.

## Claims

- **Faster decode for folded DCP head counts.** MLA decode kernel time on MI355X (gfx950), AITER v0.1.27, fp8 Q and KV, qlen 1, LSE on:

  | Pad | Batch 52, 16K KV per request | Batch 8, 8K KV |
  |---|---|---|
  | 48→64 | 274.3 → 112.9 us (**2.43x**) | 107.6 → 54.9 us (1.96x) |
  | 80→96 | 360.7 → 180.4 us (**2.00x**) | 105.5 → 57.6 us (1.83x) |
  | 112→128 | 586.6 → 185.7 us (**3.16x**) | 106.6 → 58.1 us (1.84x) |

- **No head-count table in vLLM.** The target comes from the installed AITER. For example, 96 heads is native on gfx950 fp8 at qlen ≤ 6, so 96 stays at 96 for K ≤ 6 and pads to 128 only when the group also has non-causal blocks at qlen 7 or 8.
- **Only folded counts change.** bf16 is never padded, and neither are 16 or fewer heads or counts AITER already runs natively, so for example DeepSeek-style 128 heads at TP1/2/4/8 (16/32/64/128 per GPU) is unchanged. On gfx950 fp8 the query gives 40/48→64, 80→96 and 112→128.
- **Older or failing AITER keeps working.** If the query is missing (AITER < v0.1.27) or raises, the builder logs once and keeps main's head count.

## Details

**Why the fold is slow.** When AITER's persistent MLA decode gets a head count it does not run natively, the metadata planner folds the heads into `num_heads / 16` pseudo-batches of 16. Each pseudo-batch reads its request's KV range again. Decode is KV-bandwidth bound, so 48, 80 and 112 heads read the cache 3, 5 and 7 times. Padding Q with replicated heads, and slicing the extra heads off afterwards, reads it once.

**Why the AITER query.** Whether a head count is native depends on the arch, the Q and KV dtypes, the head count and `max_seqlen_qo`. Whether a kernel exists also depends on LSE and causality, and the answer has changed between AITER releases. A wrong guess aborts the process on the first decode. The padded count also sizes the persistent buffers and is captured in CUDA graphs, so vLLM must know it at init. `get_mla_decode_shape_support` answers from the same C++ rules the planner uses. Its defaults (`persistent`, `fast_mode`, `page_size=1`, no `cp_world_size`) match the launch it is asked about.

**Target selection.** The padded count is the smallest multiple of 16 that the query reports `native` and `supported is True` at every shape the plain decode launches. The search runs from the aligned count up to 2x it, capped at 128. If no count fits, if the aligned count is ≤ 16, or if the query is missing or raises, the aligned count is kept, which is main's behavior.

**Design**

- **One count per run.** `AiterMLAMetadataBuilder.__init__` resolves the padded count once, because it sizes the persistent buffers and is captured in CUDA graphs.
  - **Buffer sizing.** The buffers are sized for both the padded count and the existing count (cprr's count when cprr is on) at every decode qlen, using the per-qlen sizing from #63116. AITER's buffer needs are not monotonic in the head count: a folded 48 can need more than a native 64.
  - **Planning and launch.** The plain route plans `get_mla_metadata_v1` at the padded count. `AiterMLADecodeMetadata.padded_num_heads` carries it to `forward_mqa`, which pads q and unpads o and lse with it.
- **Which shapes are queried.** Only the plain persistent asm decode is padded. `resolve_padded_mla_num_heads` queries the `(qlen, return_lse, causal)` shapes that route can launch:
  - **Under DCP:** causal qlen 1 with LSE. Causal qlen > 1 takes cprr, segmented or Triton, including #62990's right-aligned adaptive verification.
  - **Without DCP:** causal qlen 1..K.
  - **Groups with non-causal multi-token blocks:** non-causal qlen 1..K as well.
- **Buffer sizing also fixes a main bug.** With DCP and cprr, main sized the shared buffers for cprr's count only, but also planned the plain decode's count into them. At 112 plain / 128 cprr, a guard region showed writes past `reduce_indptr` and `reduce_final_map`. Sizing for both counts removes that.
- **The fp8 non-causal qlen-2 guard** checks the count the batch launches at. A padded 64/96/128 block is no longer refused because of its unpadded 48/80/112.
- **Unchanged routes.** cprr runs at its own native count. Segmented, Triton, Gluon and non-persistent batches run at the aligned count, as on main.

**Limitations**

- **No opt-out.** There is no env var to turn padding off. If AITER's query reports a shape as native that its kernel then mishandles, the affected configs need an AITER fix or downgrade.
- **AITER's native 64-head fp8 kernel is not deterministic at long KV.** At batch 52/ctx 4K and batch 16/ctx 16K, repeated runs on identical inputs give different outputs. 1–10 of 3,328 rows reach up to ~0.26 max relative error, always in heads 32–63. This happens on AITER 0.1.26 and 0.1.27 alike, and 96 and 128 heads are clean. It already affects every model with 64 decode heads, and it affects 48→64 here: real heads 32–47 land in that range. To be reported to AITER separately.
- **Kimi-K3 fused q-prep (DCP1 only).** The fused decode writes q into a buffer sized at the aligned count. A padded count makes `get_mla_padded_q` copy q once per MLA layer instead of viewing it. Output is unchanged; the copy costs a little of the gain.
- **Conservative shape set.** Groups with non-causal blocks query every qlen 1..K, so padding may be refused because of shapes the scheduler never produces.
- **gfx942 is untested.** No MI300 was available. The target follows whatever the query reports there.
- **Speed-ups are kernel measurements.** The only end-to-end number is the earlier 96→128 Kimi-K3 run on AITER 0.1.19 (DCP8/TP8, conc 52): 459 → 169 us per MLA layer, median ITL 52.7 → 43.3 ms.

**Pre-existing issues on main, not addressed here**

- **Folded 48-head DCP decode crashes.** Main's folded 48-head plain DCP decode intermittently hits `HSA_STATUS_ERROR_MEMORY_FAULT` (see End-to-end). The root cause is not identified. With AITER ≥ v0.1.27 this config pads to 64 and no longer takes that path; with an older AITER it still does.

**Tests** (12 cases in `tests/v1/attention/test_rocm_aiter_mla_mtp_split.py`; no new file, no Buildkite change)

- `test_resolve_padded_mla_num_heads` (4): target selection against a fake query. Covers 48→64, the 2x cap, 96→128 with non-causal blocks, and 16 never padding. Under DCP, causal groups query only qlen 1 with LSE.
- `test_resolve_padded_mla_num_heads_without_a_working_query` (2): a missing query and a query that raises both keep the aligned count.
- `test_padded_plain_decode_plans_at_the_padded_count` (2): plain plans at the padded count and cprr at its own.
- `test_padded_plain_decode_unpads_output_and_lse` (1): a 48-head decode padded to 64 comes back at 48 heads, in order.
- `test_builder_sizes_metadata_for_the_padded_head_count` (2): with 64 native, the builder sizes for 48 and 64 at every qlen; with nothing native, for 48 only.
- `test_a_two_token_fp8_block_is_allowed_when_padded_to_a_fold` (1): a 48-head fp8 non-causal qlen-2 block padded to 64 is planned at 64 instead of being refused.

The builder test stubs that replace `MLACommonMetadataBuilder.__init__` now also set `non_causal_multi_token_decode`, which the real init always sets and the padding search reads. This affects two tests in `mtp_split`, including #63116's, and one in `dcp_cprr`.
