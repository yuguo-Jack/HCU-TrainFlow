# [Bugfix][Tool Parser] LFM2: constrain forced tool_choice to the native format and parse hyphenated tool names

[Upstream PR](https://github.com/vllm-project/vllm/pull/64750) · state: open · merged: False

## Original PR description



## Overview

Fixes two `lfm2` tool-parser bugs that together make LFM2.5 agents loop on the same tool call under `tool_choice="required"`:

1. Forced `tool_choice` (`required`/named) was decoded as a JSON tool-call list instead of LFM2's trained `<|tool_call_start|>[name(k=v)]<|tool_call_end|>` block. An `lfm2` structural tag now constrains it to the native block.
2. Tool names with hyphens (`sub-task-ending`) came back as content. They are now parsed.

Related: #57989 (the same hyphen fix for FunctionGemma).

## Claims

- On a [ToolSandbox](https://github.com/apple-aiml-research/ToolSandbox) turn where the search already succeeded, `LiquidAI/LFM2.5-2.6B` repeats it in 28/30 samples on `main` and ends the subtask in 30/30 with this PR.
- `required`/named calls are decoded in the native block and parsed by `Lfm2ToolParser`, like `auto`. `auto` is constrained only when a structural tag applies anyway (a `strict` tool, `--tool-strict-level`, `parallel_tool_calls=false`), and plain text stays valid.
- Hyphenated names parse in streaming and non-streaming, including parallel blocks that mix them with plain names.

## Validation

**Reproducer.** ToolSandbox's contacts task with `tool_choice="required"`, at the turn after a successful `search_contacts(relationship="friend")`. The harness adds a `sub-task-ending` tool, which is the correct next call.

```bash
vllm serve LiquidAI/LFM2.5-2.6B --enable-auto-tool-choice --tool-call-parser lfm2 --reasoning-parser qwen3
curl -s localhost:8000/v1/chat/completions -H 'Content-Type: application/json' -d @toolsandbox_repro.json \
  | jq -r '.choices[].message.tool_calls | map(.function.name) | join(",")' | sort | uniq -c
```

## Details

**Forced tool_choice.** `Lfm2ToolParser` had no `structural_tag_model`, so forced calls got the generic JSON schema and bypassed the parser. Outside its trained format the model copies its previous call: after `</think>`, the JSON prefix `[{"name": "` gives `search` 0.53 / `sub` 0.32 at the first token, while `<|tool_call_start|>[` gives `sub` 1.00. The fix registers `get_lfm2_structural_tag` (like `hermes`, `longcat` and `plamo3`; nothing shared changes): the start token, then `[` + an allowed name + `(`, then free text up to the end token. The sentinels are strings because request validation compiles the tag without a tokenizer, and the arguments use `AnyTextFormat` because LFM2 tokens such as `(city` span the forced prefix. `VLLM_ENFORCE_STRICT_TOOL_CALLING=0` restores the old behavior.

**Hyphenated names.** `ast.parse` reads `sub-task-ending(...)` as a subtraction. Requested names that aren't identifiers are swapped for `_lfm2_tool_alias_N` at call positions before parsing and restored afterwards. Names not in `request.tools` are left alone.

**Limitations.** Only the first call's name is constrained. Further calls and all arguments are free text, so arguments aren't checked against the schema, even for `strict` tools. `parallel_tool_calls=false` is enforced after parsing, not by the grammar.

**Docs.** New LFM2.5 section in `docs/features/tool_calling.md`. The LFM rows in `docs/models/supported_models.md` now list LFM2.5 checkpoints; the deprecated LFM2 and LFM2-VL examples are dropped.

**Not a duplicate.** No open upstream PR covers LFM2 tool calling or an `lfm2` structural tag. #52900 (Rust-frontend LFM2 parser) is unaffected.

File: `vllm/tool_parsers/structural_tag_registry.py` · line None

The grammar only pins `[name(` and then accepts any text up to the end sentinel, so an unclosed call like `<|tool_call_start|>[get_weather(<|tool_call_end|>` is still grammatical. With `tool_choice="required"` that means the parser fails `ast.parse`, returns the raw text as content, and the client gets `finish_reason="stop"` with no tool call.

The template always renders `)]` before the sentinel, so we can close the hole by ending the tag with `)]<|tool_call_end|>`.
