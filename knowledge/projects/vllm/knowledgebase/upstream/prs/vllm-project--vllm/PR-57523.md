## Purpose

DeepSeek-V4.1 has two KV records of its own: the 528 B MXFP8 record (all 512 dims fp8 e4m3, RoPE included, 16 UE8M0 scales) and the 288 B NVFP4 compressed record (e2m1 pairs, 32 e4m3 scales), both in the interleaved layout of #61371. This PR makes gfx950 use them. It supersedes #57463 and the earlier version of this PR, folded into one change.

### Problem

On gfx950 today:

1. **`fp8` stores the wider V4 record.** The V4.1 record is gated on SM100, so gfx950 keeps the 584 B V4 record for both caches: 56 B per token more than the model's own format, about 9% of the KV capacity.
2. **`nvfp4_ds_mla` is rejected.** The NVFP4 compressed cache is gated on SM100 too, and its e2m1 pack is PTX, which aborts every worker at startup on ROCm (`unknown asm constraint 'f'`).

Switching gfx950 to these records runs into three more:

3. **NVFP4 beside the V4 record loses capacity.** Next to 584 B sliding-window pages, the 9,216 B NVFP4 pages make the KV-cache packer split the 40 sliding-window layers into 14 groups of 2–3, so capacity drops (−11.9% at 8K context) instead of rising.
4. **aiter's sparse MLA and the mono decode layer read only the V4 record.** With `VLLM_ROCM_USE_AITER_TRITON_SPARSE_MLA` (#60154) set, a 528 B or 288 B cache would raise in aiter's cache classifier; with `--monokernel` (#60397), a layer on the 528 B record falls back to FFN only.
5. **The MXFP8 prefill gather is slow at long context.** It runs a fixed 128-worker grid with one dependent-load chain per token, so a 512K prompt would prefill 13% slower than on the V4 record.

### Fix

1. The gfx950 sparse decode tile reads the record each cache publishes (584, 528 or 288 B, by width), with an MXFP8 branch (32-dim scales, RoPE quantized, always e4m3fn), and gfx950 writes the 528 B record by default. The launch asserts each width is one of these, so an unknown record fails instead of falling into the V4 branch.
2. The tile gains an NVFP4 branch (`v_cvt_scalef32_pk_f32_fp4`), `_fp32x2_to_fp4x2` gains a gfx950 branch (`v_cvt_scalef32_pk_fp4_f32`), and a layer whose kernel reads NVFP4 opts in through `reads_nvfp4_compressed_cache`.
3. Both land together, so `nvfp4_ds_mla` always pairs the NVFP4 compressed cache with the 528 B sliding-window record.
4. When aiter actually serves attention, or a standalone `fp8` instance uses `--monokernel`, gfx950 keeps the 584 B record. With a KV connector both P/D peers use the 528 B record regardless of decode flags; legacy Mono uses its FFN-only path there. With `nvfp4_ds_mla`, aiter remains disabled in attention and metadata alike. Record selection uses this effective backend decision, not the raw environment variable.
5. On ROCm the MXFP8 gather sizes its grid by length, as the V4 one does: 131,072 rows take 114 µs instead of 778 µs (V4: 134 µs).

Shared code is touched only on ROCm branches: `_use_v41_mxfp8_kv_record()` takes the `VllmConfig` and gains an `is_rocm()` branch into the ROCm module, `DeepseekV4Attention` gains `reads_nvfp4_compressed_cache` (default `False`), `_fp32x2_to_fp4x2` gains a gfx950 constexpr branch, and the MXFP8 gather's grid is sized by length on ROCm. CUDA paths are unchanged.
