# [ROCm][Perf][Muse Spark] Add MI300X FP8 W8A8 fused-MoE config for E=32,N=4096

[Upstream PR](https://github.com/vllm-project/vllm/pull/63727) · state: open · merged: False

## Original PR description

## Overview

Adds a Triton fused-MoE tile config for `E=32, N=4096, fp8_w8a8` on MI300X. That is the per-rank expert shape of Muse Spark (`amd/Muse-Spark-Open-816B-A42B-Quark-PTPC-FP8`: 256 experts, top-8, `moe_intermediate_size` 4096) at TP8 + `--enable-expert-parallel`, with per-token FP8 activations. No MI300X file existed for this shape, so every batch size used `get_default_config`.

The file has 16 batch sizes, from 8 to 8192. Batch 1–7 resolve to the batch 8 entry, which is the default tile. Batch sizes 512–8192 were tuned with `benchmarks/kernels/benchmark_moe.py --tune --enable-expert-parallel --tp-size 8 --dtype fp8_w8a8`. For 1–256 that tune is misleading under EP: it routes every token over the 32 local experts, so each local expert sees 8× the rows it sees in serving, and the tuned picks for 8–32 were slower than the default tiles. Batch sizes 1–256 were re-tuned with routing over all 256 experts and an `expert_map` that keeps one rank's 32 experts, with `num_stages` in {1, 2}. Batch 8 keeps the default tiles, which measured fastest. The entries for batch 1, 2 and 4 were level with the default tiles and are dropped.

## Claims

- Serving, TP8 + EP on 8× MI300X: +23.6% total throughput at 1k/1k, +15.5% at 8k/1k and +11.6% at 16k/1k with 64 concurrent requests, and +24.8% at 1k/8k c64. Median TPOT at c64 drops 10–20% (for example 50.2 → 40.5 ms at 1k/1k).
- +2.8% to +4.9% at 16 and 32 concurrent requests. At 1–8 concurrent requests the change is within −1.2% to +2.0%.
- GSM8K is unchanged (0.9507 → 0.9507). This is a config-only change; numerics differ only by tile-dependent accumulation order.

## Validation

**Kernel, one MI300X.** With serving-like routing (all 256 experts, one rank's `expert_map`), batch 1–8 runs the default tiles, and the new tiles are 5–7% faster at 16–32 and 23–29% faster at 48–128.

**Serving.** `amd/Muse-Spark-Open-816B-A42B-Quark-PTPC-FP8`, TP8 + `--enable-expert-parallel --moe-backend triton` on 8× MI300X, `vllm/vllm-openai-rocm:nightly-83c078d955` with this file mounted, `vllm bench serve` random dataset with 1k output tokens (8k for the 1k/8k row). The server log confirms the file was loaded ("Using configuration from …/E=32,N=4096,device_name=AMD_Instinct_MI300X,dtype=fp8_w8a8.json").

**Commands.** Both arms use the same image and flags; the only difference is this file mounted over `vllm/model_executor/layers/fused_moe/configs/` in the installed package.

```bash
# Server (TP8 + EP, 8× MI300X)
VLLM_ROCM_USE_AITER=1 VLLM_ROCM_MUSE_MOE_REDUCE_DTYPE=bf16 \
VLLM_USE_BREAKABLE_CUDAGRAPH=1 SAFETENSORS_FAST_GPU=1 \
vllm serve amd/Muse-Spark-Open-816B-A42B-Quark-PTPC-FP8 \
  --tensor-parallel-size 8 --enable-expert-parallel --moe-backend triton \
  --dtype bfloat16 --distributed-executor-backend mp --language-model-only \
  --compilation-config '{"cudagraph_mode":"FULL_AND_PIECEWISE"}' \
  --attention-backend ROCM_AITER_FA --enable-chunked-prefill \
  --no-enable-prefix-caching --max-model-len 32768 --max-num-seqs 128 \
  --max-num-batched-tokens 8192 --gpu-memory-utilization 0.90 \
  --reasoning-parser muse

# One serving point: ISL, OSL and C from the table, prompts = 3 × C (4 at c1)
vllm bench serve --backend vllm --model amd/Muse-Spark-Open-816B-A42B-Quark-PTPC-FP8 \
  --dataset-name random --random-input-len <ISL> --random-output-len <OSL> \
  --random-range-ratio 0 --ignore-eos --max-concurrency <C> --num-prompts <N> \
  --seed 6 --percentile-metrics ttft,tpot,itl,e2el

# Accuracy (lm-eval 0.4.13)
lm_eval --model local-completions --tasks gsm8k --num_fewshot 5 --seed 4321 \
  --model_args model=amd/Muse-Spark-Open-816B-A42B-Quark-PTPC-FP8,base_url=http://localhost:8000/v1/completions,num_concurrent=64,max_retries=3,tokenized_requests=False,tokenizer=<checkpoint dir>

# Re-tune of batch sizes 1-256 (routing over 256 experts, one rank's 32 kept).
# The MOE_TUNE_* variables belong to the local patch of benchmark_moe.py that is
# not part of this PR; batch sizes 512-8192 used the unpatched script from Overview.
MOE_TUNE_PTPC=1 MOE_TUNE_GLOBAL_E=256 MOE_TUNE_NUM_STAGES=1,2 \
python3 benchmarks/kernels/benchmark_moe.py --model <checkpoint dir> --trust-remote-code \
  --tp-size 8 --enable-expert-parallel --dtype fp8_w8a8 --tune --batch-size <B> --save-dir <dir>
```

Two warm-up runs (1k and 8k input, 16 output tokens, 16 requests at concurrency 16) precede each sweep so Triton autotune stays out of the measured window.

## Details

- **Tuning under EP.** The small-batch re-tune used `benchmark_moe.py` modified locally to route over the global expert count with an `expert_map`; that modification is not part of this PR.
- **What selects an entry.** The key is tokens per step on a rank, not concurrency, and vLLM uses the nearest key. Prefill runs at up to 8192 tokens whatever the concurrency, so it uses the large entries at c1 too, which is why c1 TTFT also drops (8k: 632 → 599 ms, 16k: 1.28 → 1.21 s). Decode at c1–8 runs at batch 1–8. Entry 8 is the default tile and batch 1–7 resolve to it, so decode below batch 8 runs as on main; the entries for 1, 2 and 4 were level with the default in kernel timing, and the c1–8 serving deltas are noise. The decode gain starts at batch 16: kernel +5–7% at 16–32 and +23–29% at 48–128, serving +3.7% at c16 and +2.8% at c32.
- **Context length.** The tile is chosen by tokens per step, which chunked prefill caps at `--max-num-batched-tokens` (8192). A 16k prompt already runs two full 8192-token chunks, so every entry up to 8192 is exercised by the 16k rows. Longer context changes attention and KV traffic, not these tiles. The sweep stops at 16k (`--max-model-len 32768`); 64k and 128k were not run.
- **Scope.** Applies to MI300X only (`device_name=AMD_Instinct_MI300X`) and to the E=32 shape, that is TP8 + EP without redundant experts.
