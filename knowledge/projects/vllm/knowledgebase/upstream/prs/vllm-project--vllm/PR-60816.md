# [ROCm][Bugfix][Qwen4Exp] Fix Qwen3.8-Flash-Next W4A4 MoE pad at TP1 and EP

[Upstream PR](https://github.com/vllm-project/vllm/pull/60816) · state: open · merged: False

## Original PR description

## Overview

Fixes Qwen3.8 Flash Next (`amd/Qwen3.8-Flash-Next-Quark-MXFP4`) on ROCm AITER at TP1 and under expert parallelism (EP4, TEP8), where GSM8K drops to 0.74. At MoE `tp_size == 1`, `rocm_aiter_fused_experts` doubles `intermediate_pad`. That is the convention #44679 introduced for the BF16/W4A16 path, but the W4A4 SiLU path gets the pad doubled a second time inside AITER, so it masks live weights. This PR skips the doubling for W4A4 SiLU only, and removes `_requires_qwen38_tep8_emulation`, which worked around the same bug at TEP8 by falling back to OCP MX emulation.

Existing work:
* #46201 removes the same rounding for every path and has been in draft with conflicts since June. 
* #55104 aligns the W4A4 allocation to 128 instead of 256, which leaves Flash Next with no intermediate pad at TP1 and EP and so hides this bug for that shape (measured below), but the double count stays for any W4A4 SiLU width with a pad of 64 or more, and the guard stays.
* #59812 zeroes the pads only on the DeepSeek V4.1 opt-in A4W4 branch, which Flash Next does not take.

## Claims

- GSM8K at TP1, EP4 and TEP8 goes from 0.715–0.754 to 0.958–0.967, on par with TP2 (0.966), which this PR does not change. 596–648 problems fixed against 5–12 broken per config.
- The emulation guard `_requires_qwen38_tep8_emulation` did not protect the checkpoint card's recipe: with `VLLM_ROCM_USE_AITER_FUSION_SHARED_EXPERTS=1` each rank holds 65 local experts, the guard requires exactly 64, and stock TEP8 runs the native kernel at 0.746. This PR fixes that kernel path for both settings.
- Without fused shared experts, where the guard did fire, TEP8 runs the native AITER W4A4 kernel instead of OCP MX emulation at the same accuracy (0.9666 vs 0.9674) and 2.6x the output throughput at 8k/1k concurrency 4 (388 vs 152 tok/s), 1.9x at concurrency 32 (1351 vs 723).
- With MTP (3 speculative tokens), TP1 GSM8K goes from 0.7233 to 0.9666 and the mean acceptance length from 3.27 to 3.54.
- No change for any shape without an intermediate pad, for TP > 1, and for every activation and quant path other than W4A4 SiLU.

## Details

- **The double count.** Flash Next's MoE width is 640, which ROCm stores at 768, so `intermediate_pad` is 128. At `tp_size == 1`, vLLM doubles that to 256, and AITER's stage 1 multiplies by 2 again for the fused gate/up weight (`n_pad_zeros = intermediate_pad // 64 * 64 * 2`). Stage 1 then masks 512 rows where 256 is correct, and stage 2 (`k_pad_zeros = intermediate_pad // 128 * 128`) zeroes 256 live activation channels where 128 is correct.
- **Why TEP8 too.** Under expert parallelism, `FusedMoEParallelConfig` sets the MoE `tp_size` to 1, so EP4 and TEP8 take the same branch with the same 768 storage. TEP8 is the case the emulation guard was added for, but it matches on `num_local_experts == 64`, and the fused shared expert raises that to 65 (`ExpertMapManager` adds it to the local count), so with the card's recipe the guard never fires. EP4 was never covered. At 768, CK-Tile's `inter_dim % 256` scale issue does not apply.
- **Scope.** The doubling stays for every other path. #44679 measured gpt-oss BF16 accuracy with it at TP1, and this PR does not re-validate those paths. The new condition is "W4A4 and SiLU", not a model check. In practice it only changes behaviour for shapes that carry an intermediate pad at MoE `tp_size == 1`: the other W4A4 SiLU MoE checkpoints we know of (DeepSeek, Kimi, Qwen3, MiniMax, GLM) have per-partition widths that are multiples of 256 at MoE `tp_size == 1`, so their pad is 0 and doubling it was a no-op.
- **Refactor.** The rounding moves into `aiter_moe_pads`, a pure function, so it can be unit-tested without a model. The SITU pass-through is unchanged. Both touched files are ROCm-only paths; nothing changes on CUDA.

**Limitations and CI gaps.**

- gfx950 only. The W4A4 MXFP4 MoE path does not run on gfx942, so there is nothing to compare there.
- The MTP draft layer is BF16 in this checkpoint, so its MoE takes the BF16 path, which this PR leaves alone. The MTP row checks the W4A4 target's verification.
- The end-to-end runs used `nightly-43b4aaea` with this change applied. The branch has since been rebased onto main, and the code is unchanged apart from the docstring and two pruned test cases.
- The unit tests run in the AMD kernels CI job. The accuracy runs happened outside CI.
