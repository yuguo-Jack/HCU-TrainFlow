# [Bugfix][Multimodal] Normalize native-rate PyAV audio

[Upstream PR](https://github.com/vllm-project/vllm/pull/62296) · state: open · merged: False

## Original PR description



## Overview

PyAV decoding without a sample-rate change casts integer PCM to float32 without normalizing it, and leaves packed stereo samples interleaved. Convert those frames to float-planar audio before collecting them so explicit PyAV media loading produces the expected waveform.

## Claims

- Native-rate signed and unsigned PCM have normalized amplitudes, correct per-channel sample counts, and correct mono averaging.
- Format conversion preserves the source sample rate and channel layout.

## Validation

- `uv run --offline --no-project --python .venv/bin/python -m pytest tests/multimodal/media/test_audio.py -q`: **33 passed**. The five added regressions fail on the base commit.
- `pre-commit run --files vllm/multimodal/media/audio.py tests/multimodal/media/test_audio.py`: passed.
- Real vLLM generation with `openai/whisper-tiny` at `169d4a4`, RTX 5070 Ti, MRV2, fp16, eager mode, temperature 0 and max_tokens 64. A 3.33-second synthetic English PCM16 clip was decoded through explicit `AudioMediaIO(audio_backend="pyav")` and compared with soundfile under the same model settings:

| Input at 16 kHz | Before | After |
|---|---|---|
| Mono PCM16 | Empty transcript | All 11 output token IDs match soundfile |
| Duplicate-channel stereo PCM16 | Empty transcript; doubled waveform length | All 11 output token IDs match soundfile |

Both corrected waveforms also match soundfile exactly. The reference transcript was “The quick brown fox jumps over the lazy dog.” This is a small decoding regression check, not a general ASR accuracy benchmark. Model runs used one sequence, 2048 batched tokens, a 128 MiB KV cache, and disabled optional FlashInfer autotuning.

## Details

Reuse `AudioResampler(format="fltp")` for native-rate frames and collect its output through the existing loop. Channel averaging then operates on planar samples. The existing sample-rate-changing path retains its current behavior.

I checked the open PR inventory and related audio-loader changes, including large PRs whose initial file lists were truncated; none of the inspected changes fixes this conversion. #51022 changes channel-reduction performance and #51894 adds a channel-count guard.
