# [Kernel][Fusion] Fuse GELU-tanh+Mul with dynamic per-token FP8 quantization

[Upstream PR](https://github.com/vllm-project/vllm/pull/64212) · state: open · merged: False

## Original PR description

## Overview

Adds a CUDA kernel, `gelu_tanh_and_mul_per_token_quant`, and the `(GeluAndMul, per-token dynamic FP8)` row in the manual activation+quant fusion registry, as part of the manual fusion port (#43501, #43224). When GELU runs as the CUDA `gelu_and_mul` op, Gemma3 and Gemma 4 FP8-dynamic MLPs produce the down projection's input in one kernel instead of `gelu_tanh_and_mul` followed by `dynamic_per_token_scaled_fp8_quant`.

## Claims

- Output is unchanged: byte-identical to the two kernels it replaces on every call of real Gemma3 and Gemma 4 generations, on L4, H100 and B200.
- On the CUDA-op path, MLP activation+quant is 1.41-1.79× faster. On Gemma-4-31B (H100) it is 1.47× faster than main and 1.36× faster than the compiled kernel.
- bs32 latency improves 1.46% on Gemma-4-31B (H100), and 3.35% (L4), 1.63% (H100) and 2.71% (B200) on Gemma3-1B.
- The `torch.compile` default path is unchanged. The row only replaces the CUDA `gelu_and_mul` op.

## Details

- **Design.** One thread block per token: compute the row and its absmax, then quantize with `scaled_fp8_conversion`, from shared memory when the row fits. The GELU expression and rounding are copied from `gelu_tanh_kernel` and `act_and_mul_kernel`, which is what keeps the output identical.
- **Default path.** Under `torch.compile`, Inductor fuses GELU with the quantization using its own FP8 rounding, so the row skips that path and output stays unchanged.
- **Limits.** On Gemma3-1B this path stays behind compiled latency, about 6.5% on H100 and 6-8% on B200, against 0.5% at bs32 on an L4. The other per-token quant calls are the largest remaining piece (64.1 ms on H100, 68.4 ms on B200), and this PR does not touch them. On Gemma-4-31B, total GPU time is level with compiled, but I have no compiled latency. The block size was chosen on the L4: it averages 0.9% / 1.6% (H100) and 0.8% / 1.4% (B200) warm / flushed from the best, worst 14% / 21% and 11% / 17% at d=6912, 256 tokens. 4B end to end and gsm8k were not run on H100 or B200.
- **Scope.** Dense `Gemma3MLP` and `Gemma4MLP`. Gemma 4 MoE layers fuse the activation in their expert kernels. `Gemma4Unified` is not checked.
- **CI.** The Quantization job is disabled (#63608), so the Gemma3 test runs in the H100 Fusion E2E Quick job. Gemma-4-31B is validated outside CI.
- **Related.** #58664 (SiLU per-token), #59467 (NVFP4 GELU) and #64854 (static FP8 GELU) do not add this row. #59467 adds the same `gemma3.py` line, and #59467 and #64854 add the same `gemma4.py` line. I can merge this kernel with #58664's into one activation-templated kernel as a follow-up.
