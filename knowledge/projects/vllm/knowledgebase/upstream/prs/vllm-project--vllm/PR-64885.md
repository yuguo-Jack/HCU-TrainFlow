# [Bugfix][Pooling] Enable Matryoshka dimensions for EmbeddingGemma 2

[Upstream PR](https://github.com/vllm-project/vllm/pull/64885) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Fixes #64845. EmbeddingGemma 2 is trained with Matryoshka Representation Learning, and its model card lists 128, 256, 512 and 768 as supported dimensions. None of its published configs (`config.json`, `config_sentence_transformers.json`, `sentence_bert_config.json`) declares this, so vLLM treats the model as non-Matryoshka and rejects every request that sets `dimensions`. Today users need `--hf-overrides '{"matryoshka_dimensions": [...]}'` to get the documented behavior.

This PR sets `matryoshka_dimensions = [128, 256, 512, 768]` in `EmbeddingGemma2ModelConfig.verify_and_update_model_config`, the same hook `JinaForRankingConfig` uses to set `embedding_size`.

## Claims

- Without overrides, `dimensions` of 128, 256 and 512 are accepted, and other values are rejected with the existing "only supports Matryoshka dimensions" error.
- A config that already declares `matryoshka_dimensions` or `is_matryoshka` (from the Hub or from `--hf-overrides`) is left unchanged. The hook runs after overrides are applied.
- No change for requests without `dimensions`, or for other models.
- The pooler truncates before it normalizes (`seqwise/heads.py`), which matches the model card's "re-normalize after truncating".

**768 still fails the range check until #60978 merges.** vLLM reports `embedding_size` as the text hidden size (512) instead of `embedding_dim` (768), and #60978 fixes that. The two PRs don't touch the same code and can land in either order.

## Validation

```bash
pytest -q tests/models/test_embedding_gemma2_config.py
# 5 passed
```

On CPU, I built `ModelConfig` from the model's published `config.json` and ran `PoolingParams(dimensions=d).verify()` on it:

| `dimensions` | main | this PR | this PR + #60978 |
|---|---|---|---|
| unset | OK | OK | OK |
| 128 / 256 / 512 | rejected (not Matryoshka) | OK | OK |
| 300 | rejected (not Matryoshka) | rejected (not in [128, 256, 512, 768]) | rejected |
| 768 | rejected (not Matryoshka) | rejected (range [1, 512]) | OK |

With `--hf-overrides '{"matryoshka_dimensions": [256]}'`, only 256 is accepted. With `'{"is_matryoshka": true}'`, any size is accepted, and with `'{"is_matryoshka": false}'`, `dimensions` stays disabled. All three behave as on main.

- `test_sets_matryoshka_dimensions_from_model_card` fails on main and passes with this change.
- `test_keeps_declared_matryoshka_config` checks that a declared `matryoshka_dimensions` or `is_matryoshka` is kept, including `null` and `false`.
- `test_matryoshka_parity` (added to `tests/models/multimodal/pooling/test_embedding_gemma2.py`, gated on `EG2_MODEL_PATH` like the other tests there) compares 128/256/512-d vLLM outputs with Sentence Transformers' `truncate_dim` plus `normalize_embeddings`. I don't have a GPU, so I haven't run it. The reporter's `--hf-overrides` run in the issue exercises the same code path at 256 and 512.

Ruff lint and format pass on the changed files.

## Question

No other model in vLLM sets `matryoshka_dimensions` from its config hook; it normally comes from the checkpoint's `config.json`. Is setting it here OK, or would you rather it come from the model's config on the Hub?

### Verification

Server launched with:
```bash
vllm serve google/embeddinggemma-2 --runner pooling --max-model-len 2048
```

#### 1. Before (`e5196e2959a42908313510f55fa21f213a48802e`)
Sending a request with `dimensions=256` reproduced the documented bug (`400 Bad Request`):
```bash
curl -s http://localhost:8000/v1/embeddings \
  -H "Content-Type: application/json" \
  -d '{"model": "google/embeddinggemma-2", "input": ["hello"], "dimensions": 256}'
```

**Server log:**
```text
INFO: 127.0.0.1:55553 - "POST /v1/embeddings HTTP/1.1" 400 Bad Request
```

**Response:**
```json
{
  "error": {
    "message": "Model 'google/embeddinggemma-2' does not support Matryoshka embeddings; dimensions must be unset (received dimensions=256).",
    "type": "BadRequestError",
    "param": null,
    "code": 400
  }
}
```

#### 2. After (PR branch `fix-embeddinggemma2-matryoshka`) `de8cb9d2ae3d7a30dcfb1acce41ad458cc321965`
