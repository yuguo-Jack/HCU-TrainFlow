# [Bugfix][XPU] Forward num_splits to the XPU flash attention kernel

[Upstream PR](https://github.com/vllm-project/vllm/pull/58131) · state: open · merged: False

## Original PR description

## Purpose

The XPU flash attention shim in `vllm/_xpu_ops.py` accepts `num_splits` and then
drops it: it is listed in the "not used in xpu kernel currently" block and never
forwarded to `vllm_xpu_kernels.flash_attn_interface.flash_attn_varlen_func`. So
the `max_num_splits = 1` that `VLLM_BATCH_INVARIANT` sets in
`vllm/v1/attention/backends/flash_attn.py` never reaches the kernel, which keeps
choosing its own split count via `get_num_splits()`. This PR forwards it as
`num_splits_kv` and moves the parameter out of the stale comment block that made
the omission look deliberate.

The determinism suite could not catch this. `_random_prompt(10, 50)` in
`tests/v1/determinism/utils.py` only pads when the target exceeds 50 words, so it
returns roughly 16 tokens: the KV of every request fits inside a single kernel
block and no backend has a split to be inconsistent about. This PR adds
`_prompt_with_tokens(target_tokens)`, which tokenizes with the test model to hit
an exact token count, and uses ~2k-token prompts in the bs=1 vs bs=N test.

A residual violation survives this fix and is a **separate** defect, not
addressed here: the XPU kernel serves decode (`max_seqlen_q == 1`) from
`cutlass_paged_decode_interface` and prefill from
`cutlass_chunk_prefill_interface`, and those two reduce over KV differently
(the decode path has its own FP32 `max_logits`/`exp_sums` and a cross-sub-group
SLM epilogue). A prefix-cache hit that leaves a single query token therefore
disagrees with the cold prefill whatever the split count is, so no argument to
this shim can align them. That belongs in `vllm-xpu-kernels`; XPU users who need
batch invariance should keep using `TRITON_ATTN`, as
`docs/features/batch_invariance.md` already documents.

## Why this is not a duplicate

- #55881 also concerns XPU batch invariance but only touches
  `vllm/platforms/xpu.py` backend selection; it does not touch
  `vllm/_xpu_ops.py`, and the dropped `num_splits` is unfixed on `main`.
- #55958 is the ROCm equivalent of the backend-selection change, not the shim.
- `gh pr list --repo vllm-project/vllm --state open --search "num_splits_kv"`
  returns nothing.

## Test plan

XPU (Intel(R) Arc(TM) Pro B70 Graphics, single card, `Qwen/Qwen3-1.7B`):

- `VLLM_BATCH_INVARIANT=1 VLLM_ATTENTION_BACKEND=FLASH_ATTN pytest -sq
  tests/v1/determinism/test_batch_invariance.py::test_logprobs_bitwise_batch_invariance_bs1_vs_bsN`
  with the longer prompts: 21-23 of 32 prompts mismatch before this change,
  1-2 of 32 after it. (FLASH_ATTN has to be forced; it is not the batch-invariant
  backend for XPU.)
- `VLLM_BATCH_INVARIANT=1 pytest -sq
  tests/v1/determinism/test_batch_invariance.py::test_decode_logprobs_match_prefill_logprobs`
  on `TRITON_ATTN`: 1 passed in 151.18s.
- Instrumented shim: all 364 kernel calls in a batch-invariant run now receive
  `num_splits_kv=1`, including the 112 decode-shaped calls with
  `max_seqlen_q=1`; the remaining decode-vs-prefill residual (~9e-02) is
  reproducible and deterministic, which is what identifies it as the separate
  kernel-side defect described above.

CUDA (NVIDIA L40S, single card, vLLM 0.28.1rc1.dev609+gc69d5d72a):
`VLLM_BATCH_INVARIANT=1 pytest -sq ...::test_logprobs_bitwise_batch_invariance_bs1_vs_bsN`
passes on all 6 params (FLASH_ATTN/FLEX_ATTENTION/TRITON_ATTN x flex block
shapes) both before and after this change; 417.50s -> 435.93s, i.e. the longer
prompts add 4.4% to that test.

No model-quality impact is expected on CUDA: the source change is inside the XPU
shim only, and the test change only lengthens prompts.
