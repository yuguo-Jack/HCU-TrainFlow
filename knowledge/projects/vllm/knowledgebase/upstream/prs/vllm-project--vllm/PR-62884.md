# [Bugfix][Core] Release libgomp workers before forking engine processes

[Upstream PR](https://github.com/vllm-project/vllm/pull/62884) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

A forked EngineCore can deadlock during startup if the process that launches it has already run a multi-threaded torch CPU op. The cause is libgomp, which has no fork handler. This PR pauses the parent's OpenMP runtime in `get_mp_context()` before vLLM forks a process, so the child starts with a fresh OpenMP thread pool.

This is what has made `(H200 MIG 35GB) Language Models (Extended Pooling) Shard 2/4` hang in the scheduled full builds since [96139](https://buildkite.com/vllm/ci/builds/96139) (also [96247](https://buildkite.com/vllm/ci/builds/96247)). It probably also explains the unexplained hang that `default_torch_num_threads=1` works around in #50130 / #50560 and in several `tests/plugins_tests` offline runners.

## Claims

- A process launched through `get_mp_context()` in `fork` mode no longer deadlocks in its first OpenMP parallel region after the parent has used OpenMP.
- `test_bge_m3.py` followed by `test_colbert.py` in a single pytest process, which is how `automatic_shard` now groups them, passes instead of hanging until the 900 s timeout.
- `spawn` mode, non-Linux platforms, and OpenMP runtimes other than libgomp behave as before.

## Validation

All runs use one GPU (GB300, aarch64) with torch 2.13.0+cu132 and its bundled `torch/lib/libgomp.so.1`. kernrec was not enabled, so it plays no part in the hang.

## Details

**Root cause.** GNU libgomp creates its worker threads lazily and keeps them for reuse. After `fork()` the child has only the forking thread, but libgomp still believes the old team exists, so the child's first parallel region with more than one thread waits forever on a barrier. Intel and LLVM OpenMP install `pthread_atfork` handlers for this; libgomp does not. In the CI shard, `test_bge_m3.py` does CPU `torch.einsum` / `torch.allclose` in the pytest process, which starts the pool. The colbert fixture then calls `vllm_runner`, which forks EngineCore because CUDA is not initialized in the parent. The forked child hangs in MRV2's `UvaBuffer` `torch.zeros(..., pin_memory=True)`, a large CPU fill that runs in parallel. `automatic_shard` started putting these two files in the same shard in 96139, which is why the job began failing without a related code change. Users can hit the same thing by running torch CPU work before `LLM(...)` in one process.

`set_multiprocessing_worker_envs()` already notes the constraint ("a forked child whose parent had run a parallel region deadlocks"). Until now vLLM just assumed the parent had not run a parallel region. #58946 makes the forked EngineCore load weights with multiple threads on purpose, so forcing the child down to one thread would undo that.

**Fix.** When `get_mp_context()` resolves to `fork`, it calls `omp_pause_resource_all(omp_pause_hard)` (OpenMP 5.0) on every loaded libgomp. This joins the idle workers, so the child starts with no pool and builds a fresh one. The parent rebuilds its own pool on its next parallel region, which costs one round of thread creation. libgomp keeps a pool per calling thread, and the thread that calls `get_mp_context()` is the one that later calls `proc.start()`, so this releases exactly the pool the child would inherit. Pools owned by other threads are left alone. Errors are suppressed: no `/proc` (non-Linux), a libgomp without the symbol (GCC < 9), or no libgomp loaded at all make it a no-op.

A process can have more than one libgomp loaded. In my local test process, scikit-learn's bundled `libgomp-<hash>.so` sits next to torch's `libgomp.so.1`. Pausing only the first match released scikit-learn's copy and left torch's pool in place, so the child still hung. To find every copy, the scan in `find_loaded_library()` is split out into `find_loaded_libraries()`, which uses the same filename matching. `find_loaded_library()` still returns the first match, exactly as before.

`decorate_logs()` now reads the process name from `multiprocessing.current_process()` instead of `get_mp_context().current_process()`. The result is identical, but child processes no longer go through the pause during log setup. A pause there would be a no-op for vLLM-forked children. It would deadlock, though, in a child whose own parent forked it without pausing; I confirmed that in a standalone repro.

**Limitations.** If the parent runs another parallel region between `get_mp_context()` and `proc.start()`, the pool comes back and the child can still hang. No vLLM call site does that today. Once this lands, the `default_torch_num_threads=1` workarounds in tests could be removed, but that is left out of this PR.

**Not a duplicate.** Searched open PRs and issues for `libgomp`, `omp_pause_resource`, `fork OpenMP deadlock`, `fork hang EngineCore` and `test_colbert`. Nothing addresses this. #50130 / #50560 removed or kept the thread workaround for a single test without identifying the cause.
