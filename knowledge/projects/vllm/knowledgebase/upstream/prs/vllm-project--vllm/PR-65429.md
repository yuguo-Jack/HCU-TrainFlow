# [Kernel][Attention] Segment sliding windows in split-K; split-K for non-causal speculative rows (supersedes #61760)

[Upstream PR](https://github.com/vllm-project/vllm/pull/65429) · state: open · merged: False

## Original PR description

Supersedes #61760 (open since 2026-10-15, not tested on the DSpark draft). Credit for the idea and the kernel changes goes to the author of #61760.



## Purpose

Make the Triton unified-attention split-K (3D) launch usable for a **non-causal sliding-window** multi-query decode, and make it split the **window** instead of the whole sequence.

This is #61760 (zhentaocc) rebased on current main and narrowed to what we could validate; the idea and the kernel changes are theirs (`Co-authored-by` on both commits). What is different from #61760:
- Rebased on current main, and only the two kernel changes (below) plus tests. No new heuristics.
- Measured on gfx950 (MI355X) with a real model: MiniMax-M3.1-Flash DSpark draft (window 4096, 5 draft layers, 16 q heads : 1 kv head per rank at TP4, head size 128, fp8 KV and fp8 query, block size 128, 7 query rows per request).
- Tests for that shape (below) and a negative control: with the pre-change kernel/helper, 137 of the 270 `splitk`/admission tests fail.

### Why it matters

DSpark/DFlash drafters run **non-causal** attention: `config/speculative.py` does `dflash_config.setdefault("causal", False)`, and the MiniMax-M3.1 draft is all sliding-window (4096). On main:
1. non-causal multi-row decode is excluded from split-K (`or not use_causal`), so the draft always takes the **2D launch**, one program per query row, each walking the whole window serially (~129 tiles of 32 keys, ~1.4 us/tile);
2. even where split-K is used, `tiles_per_segment` is computed from the full `seq_len`, so at long context the window falls in one or two of the 16 segments and the others return immediately.

In-server profile (rank 0, MiniMax-M3.1-Flash TP4, 150K-token requests, 5 draft layers): `kernel_unified_attention` is **179 us per call, 0.89 ms per decode step**, independent of batch and context, with no `reduce_segments` kernel (the 2D path), i.e. ~8-10% of the decode step.

### Changes
1. `compute_tile_loop_bounds`: with a pruned sliding window, split the window's tiles over the segments (`reduce_segments` is unchanged; its segment count still derives from `seq_len`). Shared by the diff-KV kernel, whose reducer uses the same formula.
2. `unified_attention`: admit non-causal rows (`max_seqlen_q <= MAX_3D_QUERY_LEN`) to split-K, with at least `min(next_power_of_2(num_seqs), 8)` tiles per segment for non-causal launches (kernel and `reduce_segments` get the same constexpr).

Scope: validated end to end only on the MiniMax-M3.1 DSpark draft (non-causal, window 4096). Other non-causal users (other DFlash drafters, other backends) and other window sizes are covered by the unit tests only.

### Accuracy

Real (non-synthetic, `rejection_sample_method=standard`, greedy) acceptance length, chat requests at 2K/8K/30K/100K context, 6 requests per length, same prompts: main 3.90 (5368 accepted / 1852 drafts) vs this PR 3.92 (5378 / 1839). Not included (follow-up): the split-K admission threshold `128 // num_heads_kv` leaves 19-32 concurrent requests on the 2D launch (7 rows each). Raising it to 256 (same scratch size when `max_num_seqs <= 64`) measured -2.1% / +0.5% / -0.9% / -2.4% / -1.2% decode step at N=12/16/20/24/32 (8K context, max-num-seqs 64), below the noise-plus-benefit bar, so it is left out.
