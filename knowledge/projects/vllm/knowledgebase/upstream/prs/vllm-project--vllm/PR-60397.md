# [ROCm][Perf][DSv4.1] Mono decode layer for DeepSeek-V4.1-Flash on MI355X

[Upstream PR](https://github.com/vllm-project/vllm/pull/60397) · state: closed · merged: True

## Original PR description

## Purpose

Opt-in (`VLLM_ROCM_MONO_DECODE=1`, meant as the one switch for every model's mono decode kernels) fast path for DeepSeek-V4.1-Flash decode on MI355X (gfx950). Every backbone layer of a decode step runs on persistent FlyDSL launches:

| Launch | Layers | Stages |
|---|---|---|
| K1 | 30 standard layers | the mHC attention seam, then the attention front: wqkv, q/kv norms, the KV insert, wq_b |
| K2 | 30 standard layers | the attention back (split attention, combine, wo_a, wo_b), the attention TP all-reduce, the FFN seam, the MoE (router, top-6, shared expert, MXFP4 experts) and its TP all-reduce |
| FFN | the other 10 | after vLLM's attention seam and attention: the attention TP all-reduce (wo_b's unreduced output pushed to every rank), then K2's FFN seam and MoE |

All TP all-reduces run in-kernel over symmetric peer memory. K1 + K2 replace the ~40 kernels this path launches per standard layer today; the FFN launch replaces the attention all-reduce, the FFN seam and the MoE's kernels on the others.

**Scope**
- **Layers:** K1 + K2 on the 30 backbone layers with the standard mHC seam and no compressor or indexer of their own: 3–7, 9–13, 15–19, 21–23, 25–27, 29–31, 33–35, 37–39. The FFN launch on the other 10: layer 0 (embedding-broadcast seam), the Engram layer 1, and the compressor/indexer layers 2, 8, 14 (also Engram), 20, 24, 28, 32, 36.
- **Steps:** decode only, ≤ 48 rows (8 requests × 1 + 5 DSpark drafts), TP2 or TP4, eager or a FULL CUDA graph. K1 + K2 also need causal SWA windows and `fp8_ds_mla` KV records.
- **Everything else** runs as before: the DSpark draft layers, and prefill, mixed or larger steps. The paths take and return the same tensors at the layer boundary, so they interleave freely.

### Layout

```
vllm/models/deepseek_v41/amd/mono_decode.py   eligibility per layer / per step, vLLM tensors -> kernel inputs
vllm/models/deepseek_v41/amd/mono/
    runner.py     DSV41MonoLayer: scratch, epoch, peer memory, the launches
    layer.py      K1 / K2 and the FFN launch, composed from the stages below
    attention/    attention stages
    stages/       seam.py (mHC seams, attention reduce), moe.py, moe_shape.py, moe_plan.py, router.py, gemv.py, dims.py
    common/       tagged mailbox, device ops, MX helpers, build keys, peer memory
```

`stages/` and `common/` are adapted from ROCm/ATOM's DeepSeek-V4.1 mono decode (MIT License, commit 97359d6). Each adapted file names its origin and keeps AMD's copyright notice. The changes from ATOM:
- the seams are specialized to these layers;
- vLLM's numerics: f32 router logits, the shared expert reading vLLM's row-major FP8 weights, vLLM's `mxfp8_e4m3_quantize` and `silu_and_mul_with_clamp`;
- hand-offs carry epoch tags instead of per-step mailbox clears, so no host step hook and the launches are graph-safe. ATOM's clears also wiped what another step width had laid out differently; without them each width gets a scratch of its own;
- ATOM's engine-side modules are dropped.

### Design

- **Weights** are read in place, with no second copy. The attention linears stay vLLM's row-major MXFP8 (32×32 E8M0 scales). The routed experts stay in AITER's shuffled MXFP4 layout.
- **Path selection.** The model is not torch.compiled, so the per-step decision is plain Python. It runs when a FULL graph is captured (uniform decode) and on every eager step. PIECEWISE (breakable) captures are always declined, because they are replayed for mixed batches.
- **wo_b's reduce on the FFN-launch layers.** Their `wo_b` is built with `reduce_results=False`, as the sequence-parallel path already does. A decode step hands the partial to the FFN launch; any other step reduces it in the decoder layer with the same `tensor_model_parallel_all_reduce`. ROCm's preshuffled-FP8 `wo_b` path now honors `reduce_results` as the linear does. This also fixes a bug on main: with sequence parallelism and an FP8-block checkpoint, `wo_b` was all-reduced and then reduce-scattered.
- **TP ranks stay in lockstep.** Every rank must take the same path at every layer, since the kernels wait on each other's pushes. The conditions read only metadata that all ranks hold alike.
- **Failure modes.** An explicit opt-in that cannot run raises: a CDNA version outside the kernels' (`get_cdna_version()` in `CDNA_VERSIONS`, CDNA4 / gfx950 today, so a later generation is one entry once ported), TP other than 2 or 4, FlyDSL missing, expert / data parallelism or EPLB, `VLLM_ROCM_USE_AITER_MOE_A4W4_DSV4`, a routed-expert backend other than `AITER_MXFP4_BF16`, or fewer than 256 compute units (a partitioned GPU: every CTA of a launch must stay resident). The MoE and shared-expert tensors are checked for the kernels' shapes and dtypes at the first step, as the attention ones are. A layer outside the kernels' scope is logged once.
- **All-reduces are exact:** fp32 sum in rank order, then bf16. At ≤ 48 rows vLLM's own decode all-reduces are below the INT4 quick-reduce threshold, so the current path runs them exact too.
- **A scratch per step width.** Hand-offs between CTAs are tagged mailbox pairs in a scratch laid out per step width. Each width has its own scratch, allocated at its first (eager) step: 3–16 MB, and at most 8 widths under DSpark. So a word one width polls as a tag only ever holds tags. The MoE's task counters outlive a width and live in the epoch buffer.
- **Dependencies:** the `flydsl` wheel, plus two small AITER helpers that path already depends on: `aiter.ops.flydsl.kernels.buffer_ops` (FlyDSL's wheel no longer ships it) and `UncachedIpcHeap` for peer memory.

## Test Plan

- `pytest tests/models/test_dsv41_mono_decode.py` (CPU, wired into the MI355 Basic Models job): a decode step takes the mono path and hands the kernels `[blocks, block, 584]` cache views. A padded FULL-graph step takes it too (the kernels skip pad rows, whose slot is -1). PIECEWISE steps, prefill or mixed steps, more decode tokens than rows, non-causal windows, missing metadata, more than 48 rows and the first layer all take the original path. Deployments the kernels cannot run raise.
- `pytest tests/models/test_dsv41_mono_numerics.py` (4 × MI355, its own CI step). One layer with random weights in the checkpoint's formats, at TP2 and TP4: the kernels against the ops vLLM runs for the same decode step (the mHC seams, the ROCm attention chain, the all-reduce, `DeepseekV4MoE`). Each stage is checked on its own input, by cosine and relative error, for the whole layer and the FFN launch, at 1×6 and 8×6 rows. Then both widths' launches are captured in one graph and replayed 300 times, bit for bit against the first run.
- `pytest tests/models/test_dsv41_mono_layers.py` (same CI step). A five-layer DeepSeek-V4.1-Flash at TP2 and TP4 holding both layer kinds the mono path takes: the whole layer at a ratio-2 and a ratio-1 consumer, and the FFN launch at the sliding-window and KV / index-source layers. It is served with mono on and off on the same random weights, and every decoder layer's outputs at every decode token must match. It runs `DeepseekV4DecoderLayer.forward` as the engine does, so a change to the layer that the kernels do not follow fails it.
- Race stress: the whole layer and the FFN launch in one HIP graph, 48-row and 6-row steps alternating, every intermediate compared bit for bit with the first run. 100K replays each on layers 3 and 9 (ratio 2) and 21 (ratio 1).
- Compile-only build (`COMPILE_ONLY=1`) of the in-tree kernels: K1 and K2 at TP2 and TP4, M = 6 and 48, both layer types.
- No regression of K1 + K2: K2's FFN half is factored out and shared with the FFN launch. K2 disassembles instruction-identical to the first commit's (TP2 M=6 ratio 1, TP4 M=48 ratio 2), and the whole-layer accuracy check reproduces its earlier numbers exactly.
- FFN launch, kernel level: against vLLM's FFN half (the attention all-reduce, `MHCPreDelayedOp`, `DeepseekV4MoE` with its all-reduce) on the real weights of the 10 layers, with the attention partial from a real ROCm attention chain. 48 points: TP2/TP4 × concurrency 1/2/4/8 × 1–6 tokens per request; the 10 layers chained in one HIP graph, cold weights.
- Kernel level (MI355X): the layer against vLLM's own modules (`DeepseekV4MoE`, the mHC seams, the ROCm attention chain, the all-reduce) in a TP process group, with real checkpoint weights. 96 points: TP2/TP4 × concurrency 1–8 × 1–6 tokens per request × the two layer types. Timing: 8 layers chained in one HIP graph, cold weights, vLLM's path captured under `graph_capture`.
- GSM8K: InferenceX's task, 5-shot, full 1,319, temperature 0, concurrency 8, DSpark block rejection; TP2 for K1 + K2 alone, TP2 and TP4 with the FFN launch.
- AgentX e2e with the InferenceX#3690 recipe (this tree's image, a8w4 MoE, INT4 quick reduce), golden DSpark acceptance 3.51, 3600 s per point, c1/c2/c4/c8 at TP2 and TP4.
- Accuracy, per RFC #59665: GPQA-Diamond and AIME25 at TP2, thinking on with `reasoning_effort` high, 8 requests in flight a server (every decode step within 48 rows), against the same build with `VLLM_ROCM_MONO_DECODE=0`. Long context: RULER NIAH (single, multikey 2 and 3) at 32K, 128K and 256K.

Thanks for this, nice speedups. Tested on MI355X (2 GPUs): this branch installed into `vllm/vllm-openai-rocm:nightly-81198e97ba` and `nightly-rocm100-81198e97ba` (both cover the merge-base). Unit test 26/26 on both. E2E on the InferenceX MI355X recipe at TP2 (DSpark, 64K): GSM8K 5-shot, first 400 questions, greedy, 8 in flight — 0.940 ± 0.012 mono vs 0.938 ± 0.012 mono off. The numerics CI fix (5037c51b66) matches what I'd verified locally, and build 93658 is green.

### Would like to see before merge

**1. Reject expert parallelism in `create`.** The kernels assume every rank holds all 384 experts with a TP-sharded intermediate; with EP the per-rank layout differs and they read garbage (past the end of `w13` under DP × EP). In practice, the recipe above plus `--enable-expert-parallel` hangs at startup with mono on, in 2 of 2 runs — both ranks stall in the post-capture warmup inside a Triton kernel load, GPUs idle — while the same EP config starts and serves with mono off. I haven't pinned down the mechanism, but either way `create` should reject EP. A few other configurations also pass `create` and compute wrongly (`VLLM_ROCM_USE_AITER_MOE_A4W4_DSV4=1`, non-AITER MoE backends, per-row 1x32 shared-expert scales); rejecting EP is the one I'd insist on, the rest could be a follow-up.

**2. A relative-error bound in the numerics test.** Negative control: kernel routed scale (`stages/moe.py` `SCALE`) 1.5 → 1.45 still passes — cosine only moves 0.999988 → 0.999924 while relative L2 error goes 0.49% → 3.2%. At 1.2 it does fail. A relative-error bound (say 1.5%, 3x baseline) would catch it.

### Recommended, fine as follow-ups

**3. Check the loaded MoE / shared-expert tensors.** Nothing checks them the way `AttnWeights.check` does for attention, and the buffer resources use `num_records = 0xFFFFFFFF`, so a layout mismatch reads garbage instead of faulting. #60793 (Kimi-K3 mono MoE) shows the pattern inside the MoE runner — quant-method class, router class, EP/EPLB/DP, bias and padding flags — and #60216 (GLM-5) does it in one `mono_decode_unsupported_reason()`.

**4. Liveness guards.** `BLOCKS = 256` is hardcoded, tasks spread across all 256 CTAs, CTA 0 waiting on every CTA's mark. A partitioned MI355X (CPX/DPX) passes the CDNA4 check with fewer CTUs than that, and I believe the launch then deadlocks — an assert on `multi_processor_count` (times occupancy) in `create` would catch it. And all spins are unbounded (`common/sync.py` `_spin`): one rank raising in Python after its peer has launched K2 wedges the peer's GPU with no error. A deadline plus `s_trap` would turn that into a crash. #60683 (Kimi-K3) declining the path with a KV connector is the same hazard handled up front.

**5. A short race-stress test in the tree.** The stress test that found the per-width scratch bug isn't in the repo. A few hundred graph replays alternating 48-row and 6-row steps, compared bit for bit, would guard the sync protocol, which is the most fragile part here. The current test runs each shape once, eagerly.

**6. Wiring, briefly.** Building the runner after loading rather than at the first decode step would fail fast at startup and close the `peer.bytes.zero_()` ordering gap (#60683 allocates its scratch at model init); deciding the step once per step instead of per layer would make rank agreement structural rather than incidental; and the cached weight references going stale on reload is the #60389 bug class. Also: `common/` (mailboxes, epochs, peer memory) is model-independent and now exists in four trees (#59705, #60683, #60793, this one) — worth settling on one home before the next copy.

### Nits

- The numerics test runs TP2 only, so the TP4 padded-intermediate path (576 → 640) has no coverage.
- `rocm.py` honoring `reduce_results` in `_bpre_attn_gemm` also fixes a main bug: with sequence parallel and an FP8-block checkpoint, `wo_b` gets all-reduced and then reduce-scattered. Worth a line in the description.
- The description says padded batches take the original path; padded FULL-graph batches do take the mono path (pad rows skipped via `slot < 0`).
- `front.py` derives the valid top-k count from `min((pos + 1) // ratio, 512)`, while vLLM's decode path counts the `>= 0` entries. These agree only if every indexer writes its valid entries as a prefix — is that guaranteed?
- `scratch_layout`: `front_scratch` and the MoE layout both define `x8`/`x8s`, so the second `place()` silently wins (harmless today). Asserting unique region names would keep it from coming back as a tagged-pair collision.

| TP2, pass@1 | Reference (mono off) | Mono, before the fix | Mono, with the fix |
|---|---|---|---|

With the fix, AIME25 is within noise of the reference. Its two remaining empty samples are q4 seed 7 and q13 seed 4. q13 is a long problem: about 40K tokens at the median, up to about 61K. q4 normally takes about 3K tokens, so a loop there is a clear derailment. To check whether mono derails more often, q4 was sampled 96 more times on each arm, with the same settings and 8 in flight. Mono answered 96/96 with no loop. The reference answered 95/96: one sample looped to the 64K cap. Across all q4 samples, the reference loops as often as mono (1 in 120 vs 1 in 112), so these loops come from the model at this temperature, not from the kernels.

**The bug.** Before the fix, mono was 1.5 pp below the reference on AIME25. Four of its 480 samples ran out the 64K budget without an answer; the reference had none. Looking for the cause, a race stress test found one. The test replays the whole layer and the FFN launch in one CUDA graph, alternating 48-row and 6-row steps, and compares every intermediate bit for bit with the first run.

The race: the kernels hand data between CTAs through tagged mailbox pairs, in a scratch laid out per step width. Every width shared one buffer, so a word one width polls as a tag could hold another width's plain data. In the failing case, 6-row attention partials lay under 48-row tag words. When one equaled the current tag, a poll took a stale value as published. It came from this PR's adaptation of ATOM's kernels, not from ATOM. ATOM zeroes every mailbox buffer before each step, which also wipes whatever another width left. This PR replaced those clears with epoch tags, to drop the host step hook and stay graph-safe, but kept the shared scratch. The fix gives each width its own scratch. The stress test is now clean over 100K replays on each of three layers, and kernel time is unchanged (24 points, mean ratio 1.000).

**Numerical closeness, sampling noise removed** (measured before the fix). Greedy decoding of the same 128 prompts (30 AIME25 + 98 GPQA-D, 4,096 tokens), with top-5 logprobs, on four TP2 servers: mono on, mono off, and a second of each as controls. Good call. Added in 7c69067326 and c25b7e9420: `tests/models/test_dsv41_mono_layers.py`, in the same MI355 CI step (4 GPUs), at TP2 and TP4.

It serves a five-layer DeepSeek-V4.1-Flash (`hf_overrides`) holding both layer kinds this PR changes:
- layers 2 and 4, a ratio-2 and a ratio-1 consumer, run whole on the mono kernels;
- layers 0, 1 and 3 (the sliding-window layer and the KV / index sources) keep vLLM's attention and run the FFN launch.

The model runs twice on the same random weights, with `VLLM_ROCM_MONO_DECODE` on and off. Every `DeepseekV4DecoderLayer` output, `x` and the residual stream, must match at every decode token taken in a decode-only step. So it exercises the real `forward`: the hook, the per-step path choice, `weights()` off the layer, the metadata, and the top-k from the real indexer layers. It also checks that every layer took its mono path on every step. At TP4 it adds that size's own kernel builds, the padded routed intermediate (576 → 640) and the hand-offs across four ranks.

Details that made it reliable:
- **Weights:** plain dummy weights leave the E8M0 scales zero, so both paths agree trivially. A test-only loader fills checkpoint-range weights before post-load processing (with the routed experts' padding zero, as the loader keeps it). They're small enough that the random stack isn't chaotic: at larger scales, atomics' order alone moves vLLM's own logits run to run.
- **Row matching:** a request's row and step differ between engines, so rows are matched by prompt length and position.
- **Bounds:** layer 0 at a request's first decode token sees identical inputs on both paths and gets the op-level test's 1.5%. Deeper layers inherit small differences, which random weights amplify to 2–4%, so they get 8%.
- **Routing near-ties:** a token whose top-6 routing is a near-tie on vLLM's path may pick another expert. Once it does, it carries the flip in its residual stream, so its later layers aren't compared. Every other token is checked at every layer.
- **Sensitivity:** a routed scale off by 3% fails it at layer 0, at both TP sizes. A layer the kernels no longer follow would be off on every token.

It takes about 1.5 minutes at TP2 and 3 at TP4.
