# [ROCm][DSv4.1] Enable DSpark adaptive verification

[Upstream PR](https://github.com/vllm-project/vllm/pull/58151) · state: closed · merged: True

## Original PR description

## Purpose

Enable confidence-scheduled adaptive verification for `DeepseekV41ForCausalLM` on ROCm.

This PR extends the existing validated ROCm flattened-query mechanism to V4.1 and adds adaptive-only graph-support declarations for the two builders. Fixed-width DSpark behavior is unchanged.

AI assistance was used for this PR.

## Implementation

- Allow the V4.1 indexer backend to use the ROCm device/CPU query-length mismatch capability.
- Extend ROCm flattened device-query handling to `DeepseekV41ForCausalLM`.
- Report `AttentionCGSupport.ALWAYS` for the V4.1 ROCm compressed sparse-MLA and sparse-SWA builders only when adaptive verification is enabled.
- Add focused policy coverage, a fixed-K regression test, and a gfx950 graph-replay test for changed device query boundaries and stable persistent metadata buffers.

## Validation stack

- 4x MI355X (gfx950), TP=4, `deepseek-ai/DeepSeek-V4.1-Flash`; expert parallel enabled for baseline and disabled for the matched mono-off/on (referring to #60397) comparison
- ROCm nightly `vllm/vllm-openai-rocm:nightly-7d0b4e57aac4c4323225b0eee9ae960ce75ffffe` (vLLM `0.31.1rc1.dev253+g7d0b4e57a.rocm723`)
- nightly source `7d0b4e57aa` plus this PR's exact four-file patch
- Matched EP-off accuracy and throughput tests were run with `VLLM_ROCM_MONO_DECODE=0` and `1`, and the EP-on baseline used mono decode off
- #60397's mono path does not support EP, so mono's direct effect is measured by the matched EP-off pair

The primary validation matrix below used standard rejection sampling. With the adaptive block-rejection out-of-bounds fix now merged in [#60945](https://github.com/vllm-project/vllm/pull/60945), block rejection matched standard rejection on GSM8K accuracy and TP4 throughput.

All 54 cells completed 880/880 requests with zero failures. In the EP-on baseline, adaptive relative to fixed K=5 was -1.9% at C4 and +3.5% to +13.2% from C16 to C256; it beat no speculation by 27.7% at C128 and 14.2% at C256. In the matched EP-off comparison, adaptive relative to fixed was -2.2% at C4 and +4.7% to +15.0% from C16 to C256 with mono off; with mono on it was -1.6% at C4 and +4.6% to +11.7% from C16 to C256. Adaptive beat no speculation at every measured concurrency in all three configurations.

The mono launches were confirmed active in all three mono-on server logs. Their direct performance effect matched #60397's scope: at C4 mono improved no speculation by 76.5%, fixed K=5 by 35.4%, and adaptive by 36.3%. Above C4 the fixed/adaptive mono-on/off difference was mostly within about 2%, because a full K=5 verify reaches the mono path's 48-row ceiling at eight requests.
