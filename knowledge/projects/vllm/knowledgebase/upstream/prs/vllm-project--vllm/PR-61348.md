# [Feature][Spec Decode] Per-request draft retention for structured output under PP

[Upstream PR](https://github.com/vllm-project/vllm/pull/61348) · state: open · merged: False

## Original PR description

## Overview

Under PP, a structured-output request is rescheduled `pp_size` steps after it was sampled and other microbatches overwrite the single latest-batch slot in `DraftTokensHandler` in between. The scheduler's deferred grammar fetch then returns the wrong batch's drafts; the request's own stay `-1` and — since #54442 — fail closed: the drafts are rejected and the request decodes with no spec acceptance. This change keeps the latest drafts **per request** on the worker so the fetch returns each request's own drafts.

Follow-up to the discussion in #60902 (per-request draft store, @njhill); pattern from @zebgop-ops's patch in #54437 (request-keyed, vs #56802's step-keyed snapshots). Related: #54437 (async-path staleness bug class), #54442 (merged; makes stale drafts fail closed — this change removes the staleness instead of rejecting on it), #61326 (non-async PP+spec batch-queue serialization; independent mechanism, no file overlap).

**Not a duplicate:** #56802 proposed step-keyed snapshot identity (closed unmerged); this is request-keyed retention living where the drafts are produced. #54442 settles correctness; this recovers the acceptance rate it pays for staleness. Searched for prior per-request-store PRs: none found (`gh search issues --repo vllm-project/vllm "per-request draft store"` / `"draft tokens handler"` PRs → only #54437/#56802/#60902 context).

## Claims

- Structured output + spec decode + PP + async scheduling: draft acceptance collapses under concurrency without this change (84.7% → 0.4–9.5% measured) and decode slows 2.4×; with the store, acceptance is restored to the single-request level and content validity is unchanged (fail-closed holds in both arms — the loss is purely acceptance/throughput).
- Concurrency-1 is a built-in control: no interleaving → no staleness → store and no-store behave the same (2.1s vs 2.3s wall), isolating the effect to the staleness mechanism.
- The D2H fast path for batches without structured-output requests is preserved (no per-step copy added for unstructured workloads).

**Reachability note (negative result, measured):** the non-deferred engine-core branch (bitmask computed without any draft fetch) was suspected reachable under PP (@zebgop-ops, #54437: "from reading the code; I did not isolate it experimentally"). Instrumented across 296 structured requests at concurrency 1–32 (PP=2, async): **0 hits** — with the V2 stagger (`decode_stagger = pp_size`) and queue capacity `pp_size + 1`, the prior output is still in flight at every reschedule, so structured batches always take the deferred branch. The fetch insertion for that branch was therefore dropped from this PR as unreachable-by-measurement; if a config exists where it fires, it is a small follow-up.

## Details

**Root cause:** `DraftTokensHandler` holds one slot for the latest structured batch (`draft_tokens_np`). Under PP + async, the deferred fetch for request R (rescheduled `pp_size` steps after sampling) reads whatever batch overwrote the slot last; the req_ids don't match R, `update_draft_token_ids_in_output` skips them (scheduler.py:2571), and R's scheduled spec tokens stay `-1`. #54442 then rejects those positions (`grammar_invalid_drafts`), so every overlapped step decodes at acceptance ≈ 0.

**Fix:** `_draft_tokens_by_req: dict[req_id, drafts]`, written at `set_draft_tokens` time — structured batches store NumPy views of the pinned async copy (one `copy_event` fences all queued copies; `record_stream` guards the source tensor), unstructured batches store an int (the draft width) so synchronous scheduling keeps the speculative slots as `-1` placeholders. `get_draft_tokens()` returns every retained request's drafts (fresh lists — scheduler validation may mutate them). Retention is bounded by an assert on `max_num_reqs`: `discard(req_id)` from `_remove_request` (finished, preempted, or re-added) keeps the dict at the live request count, so the bound is unreachable in correct operation — if it ever fires, it is a canary for a missed removal path, not a silent drop.

**Tradeoffs and limitations:**
- Retained state is K ints per request on CPU (trivial); the `max_num_reqs` assert replaces the earlier LRU backstop — an LRU could silently evict drafts needed for grammar validation, which is worse than a loud canary.
- Batches without structured-output requests still skip the D2H copy entirely (fast path unchanged); only retention of already-copied structured batches changes.
- Measured on ngram_gpu + OLMoE at PP=2; MTP/EAGLE under PP share the same handler and fetch path (the #54437 production reports were MTP PP=4), but our acceptance numbers are ngram-specific.
- The e2e differential is GPU-marked and not in CI (multi-GPU + structured-output + spec-decode coverage gap); the unit tests guard the retention contract and the reproducer above regenerates the e2e numbers.

**Consolidation:** the implementation converged with @yzong-rh's benchmarked per-request-dict branch (co-authored; his A/B harness produced the table above), and @tomasruizt's e2e reproducer + CUDA worker tests are integrated (co-authored). - ArcheyChen · comment · 2026-10-16T09:32:17Z · [source](https://github.com/vllm-project/vllm/pull/61348#issuecomment-6212529133)

Thanks for picking this up — this is the half of #54437 we never got in. Our numbers from a different stack (a fork, DeepSeek-V4-Flash, PP=2, DSpark K=7, posted in #54437) line up with yours: about 2.4× on an all-grammar load, and grammar requests back to plain-text speed once the hand-off works.

One thing from our own implementation that I'd want covered here, because it changes the failure mode rather than just the speed.

Once the scheduler gets real ids instead of `-1`, #54442's fail-closed no longer applies to them. If, for some step, the scheduler's copy for a request differs from the drafts the worker actually verifies, the bitmask rows are built by advancing the grammar over the wrong tokens and then applied to the worker's real drafts, with nothing invalidated. Nothing errors; the request can accept a token its grammar does not allow. That is what bit us: a step-keyed snapshot taken when the drafts were *proposed* matched 100% of lookups and still silently corrupted requests, always at the row where acceptance had stopped on the previous step. What fixed it was snapshotting what the worker *consumed*, after `prepare_inputs`.

With a per-request dict and at most one step in flight per request, I'd expect proposal time and consumption time to coincide on MRV2, so this may well be a non-issue here. But it is the one property the e2e test can't see: schema validation only fails when the model happens to want an invalid token at that exact row, and acceptance metrics look healthy either way. Two cheap ways to pin it down:

- a worker-level test that drives PP-style interleaving and asserts that the ids `get_draft_tokens()` returns for a request equal the row the worker reads as that request's `draft_sampled` on its next step;
- or a debug-gated check in the worker that compares the scheduled spec tokens of structured requests against `draft_sampled` and logs or asserts on a mismatch, which is how we found ours.

Happy to help with either. On testing: our deployment is a fork on an older base that carries our own step-keyed version, so I can't drop this PR in as-is; I'll run it on our PP=2 setup and report the same table once I can.
