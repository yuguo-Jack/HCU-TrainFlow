# [ROCm][Perf][DSv4.1] One-launch decode SWA metadata on gfx950

[Upstream PR](https://github.com/vllm-project/vllm/pull/63994) · state: closed · merged: False

## Original PR description

## Overview

`DeepseekV41ROCMAiterSparseSWAMetadataBuilder.build` runs once per SWA KV cache group on every step, and on a decode step each build launches 8 small kernels before the decode graph can start. #60731 added `swa_decode_meta`, which builds the same metadata for a decode batch of up to 32 rows with one launch, but gated it to gfx942 together with the gfx942-only helpers. The kernel is plain Triton and writes the buffers that the gfx950 attention reads, so this PR also runs it with `--monokernel` on gfx950. The other helpers in `amd/ops` stay gfx942-only.

## Claims

- DeepSeek-V4.1-Flash, MI355X, TP4, `--monokernel`, c=16: a decode step runs 49 fewer kernels before its first layer (42 instead of 91), and that section takes 0.220 ms instead of 0.416 ms.
- In a 12-point sweep against `main`, mean TPOT is 0.4% to 2.2% lower at every point with c ≤ 32 (8 of 8), and within ±0.5% at c ≥ 64, where decode batches exceed 32 rows and keep the current path.
- The metadata is identical to vLLM's ops. GSM8K and NIAH match `main` within run-to-run noise.
- Mixed and prefill steps, decode batches of more than 32 rows, and runs without `--monokernel` keep the current path.

The metadata itself is bit-identical (see Correctness), so the spread comes from nondeterministic serving (batch composition under async scheduling).

### Correctness

`test_dsv41_gfx942_decode_meta.py::test_swa_decode_meta_matches_vllm_ops` runs vLLM's ops and the one-launch kernel on 300 random decode batches (causal and the DSpark draft block, block sizes 64 and 128, padded tokens, replay starts, null blocks) and requires every output to be equal. It passes on MI355X.

The SWA comparison test now also runs in `:amd: (MI355) DeepSeek-V4.1 Mono Decode Numerics`; it already ran on MI300.

## Details

**Changes.** `amd/ops/__init__.py` gains `swa_decode_meta_enabled()`, true with `--monokernel` on gfx942 or gfx950, and `swa_decode_meta.build` uses it instead of `enabled()`. `topk_pack`, the gfx942 top-k, the candidate logits, the Markov sampling and the draft LM head keep `enabled()`.

**Limitations.** Decode batches of more than 32 rows (for example c=64 without speculative decoding) keep the 8-launch build. Benchmarked only on MI355X at TP4.

### Existing PRs

I searched open vllm-project/vllm PRs for the SWA metadata builder, `swa_decode_meta` and gfx950 decode metadata.

- [#58352](https://github.com/vllm-project/vllm/pull/58352) packs the ragged decode metadata straight into the graph buffers, removing the 2 copies of each build. On gfx950 with `--monokernel`, batches of up to 32 rows no longer reach that code after this PR; larger batches and runs without `--monokernel` still do.
- [#57756](https://github.com/vllm-project/vllm/pull/57756) changes the gfx950 sparse decode to consume dense top-k indices and fuses the metadata construction. It predates `swa_decode_meta`.
