# [KV Connector][NIXL] Report completed pulls before the next model output

[Upstream PR](https://github.com/vllm-project/vllm/pull/63936) · state: open · merged: False

## Original PR description

## Overview

Report successful NIXL pulls before the next model output so the decoder can admit requests sooner. Set `"enable_early_recv": true` in the decoder's `--kv-transfer-config`; disabled by default.

## Claims

Supports `uni` and single-node `mp`, TP, sync/async scheduling, and NIXL pull inside MultiConnector; decoder PP=1. Existing threads perform polling. Successful receives share the normal all-worker quorum; transfer failures retain normal recovery.

## Validation

Head `49c901449`, base `df028dffa`. Since `053f5967e`, workers spin between polls instead of sleeping. In a CPU-only probe with a no-op poll, an RPC that arrives while a pull is pending is picked up 3–15 µs later than on main at p50 (sleep: ~150 µs later), with the same waiting-thread CPU as main. **20 focused tests passed**, covering quorum, failure deferral, NIXL one-shot reporting, scheduler admission/abort, and terminal polling errors. Five local negative controls confirmed that the shortened tests reject premature completion, lost failure votes, missing lifecycle updates, and nonterminal exceptions. Changed-file pre-commit including mypy passed; source hashes match validation.

```bash
HF_HUB_OFFLINE=1 VLLM_TARGET_DEVICE=cpu CUDA_VISIBLE_DEVICES='' \
uv run --no-project .venv/bin/python -m pytest -q \

  tests/v1/kv_connector/unit/test_nixl_connector.py::test_early_recv_reports_successes_only_through_poll \
  tests/v1/kv_connector/unit/test_nixl_connector.py::test_early_recv_leaves_failures_to_the_step \
  tests/v1/kv_connector/unit/test_output_aggregator.py
```

Dedicated IPC/idle-loop tests were removed to keep the regression suite focused. Earlier `860085f7a` Qwen3-0.6B NIXL P/D, TP2 + MultiConnector, mp/async off/on checks returned identical 32-token outputs for 32 requests. On H200 with Qwen3-8B TP1 (NIXL pull, `mp`, 96 background decode streams, one 4K-token handoff per second, 240 handoffs per arm), median decoder first-token latency on this head was 97.2 ms vs 106.1 ms on main with async scheduling (vLLM's default here, −8.4%) and 93.2 ms vs 93.9 ms with sync; background ITL p50 stayed within 0.1 ms of main and worker CPU matched main. Uni serving/fault recovery, stalled TP8 performance, ROCm/Mamba and heterogeneous layouts remain validation gaps. Upstream CI is separate.

## Details

Completion flows from worker post-processing through IPC/quorum counting to the existing scheduler lifecycle. Known-failed early votes use the normal output replay queue; no extra ready-failure set or aggregate override is needed. The public aggregator is unchanged. Each worker reports a load once; no speculative rank/load deduplication is added. Unexpected MP poll/channel errors terminate the worker and use its existing monitor, including while paused; uni marks polling errors terminal.

Disabled mode retains the ordinary aggregator and scheduling paths, with added flag checks/forwarding calls. Between RPCs, workers spin with `sched_yield` like `MessageQueue.dequeue()` and poll every 0.2 ms while pulls are pending; an RPC that arrives during a poll waits for it. Post-processing uses the current worker stream; metrics still use ordinary outputs. KV pressure can delay admission.

#51919 uses additional notification threads; this implementation reuses existing threads. AI assistance was used for implementation and validation.

- xsxszab · comment · 2026-10-29T05:54:57Z · [source](https://github.com/vllm-project/vllm/pull/63936#issuecomment-6489169748)

Small idea to simplify the worker loop: could we combine waiting for the next RPC with waiting for the next poll?

At the top of each iteration, run the poll if it is due; otherwise wait for an RPC, but only until the next poll is due. This replaces both `wait_for_poll()` and the post-step poll.

```python
rpc_mq = self.rpc_broadcast_mq
early_kv_recv = self.early_kv_recv

while True:
    if early_kv_recv is not None:
        timeout = early_kv_recv.time_until_poll()  # None: nothing to poll for
        if timeout is not None:
            if timeout <= 0:
                get_watch_dog().feed()
                early_kv_recv.poll()
                continue
            with get_watch_dog().disable():
                if not early_kv_recv.wait_for_rpc(rpc_mq, timeout):
                    continue

    with get_watch_dog().disable():
        rpc_request = rpc_mq.dequeue(indefinite=True)
    self._execute_worker_rpc(rpc_request)

    if early_kv_recv is not None and rpc_request[0] in (
        "execute_model",
        "sample_tokens",
    ):
        early_kv_recv.step_rpc_done()
    del rpc_request
```

This needs two new `EarlyKVRecvSender` methods in place of `wait_for_poll()`:

- `time_until_poll()` returns the seconds until `_next_poll`, or `None` when no poll is needed.
- `wait_for_rpc(rpc_mq, timeout)` spins on `rpc_mq.readable()` with `sched_yield()` for up to `timeout` seconds. It returns `True` once an RPC is ready or the queue is shutting down, and returns `False` when the poll is due.
- `step_rpc_done()` would also set `_next_poll = 0.0`, making the poll due at the top of the next iteration. This preserves immediate post-step polling without a separate call after the step or any assumption about the RPC duration.

Happy to prototype this and compare CPU usage and latency if the direction looks useful.

A follow-up on prefill performance: early receive helps more at larger chunked-prefill token budgets on a busy prefill instance.

Tested with Qwen3-32B, PP=4, and Mooncake Store. Cache-hit requests load an 8K-token prefix plus 128 new tokens at 2 req/s; background 4K-token prefills at 4 req/s keep the instance busy without saturating it.
| `--max-num-batched-tokens` | Step time p50 | Mean TTFT change | p90 TTFT change, 95% bootstrap CI |
|---|---:|---:|---:|
| 2048 | 39 ms | −16 ms | −38 ms [−47, −27] |
| 8192 | 182 ms | −48 ms | −163 ms [−226, −116] |
| 16384 | 188 ms | −54 ms | −169 ms [−249, −77] |

At the larger budgets, p90 TTFT drops by about 17–20%, while the median barely moves. This is consistent with scheduling at step boundaries: most hits gain little, but an earlier completion signal can let some requests enter an earlier step and save roughly a full step.

8192 and 16384 perform similarly because fewer than 8K tokens are usually queued at this load, so their actual step times are nearly the same.
