# [Bugfix] Fall back to auto for unquantized MoE layers when --moe-backend is marlin

[Upstream PR](https://github.com/vllm-project/vllm/pull/60219) · state: closed · merged: True

## Original PR description

## Overview

Fixes #56832. With `--moe-backend marlin`, an unquantized MoE layer (here, the BF16 MTP draft of an NVFP4 model) now uses the auto-selected unquantized backend instead of raising `ValueError`. `humming` already works this way. Related: #56964 discusses the same fix.

## Claims

- `vllm serve RadixArk/Qwen3.8-Flash-Next-NVFP4 --moe-backend marlin --speculative-config '{"method":"mtp",...}'` now starts and serves requests with MTP speculative decoding. Before this change, loading the draft model failed with `ValueError: moe_backend='marlin' is not supported for unquantized MoE`.
- Quantized MoE layers still use Marlin. Only unquantized MoE layers change: they now use the auto-selected backend instead of raising.
- A new unit test checks that `marlin` and `humming` give the same unquantized backend as `auto`.

## Details

**Root cause.** `--moe-backend` is one global value (`KernelConfig.moe_backend`). It reaches every MoE layer, quantized or not. The MTP draft inherits it unless `speculative_config.moe_backend` is set. This checkpoint has NVFP4 main experts, but it excludes `mtp.*` from quantization and stores those experts in BF16. So `mtp.layers.48.mlp.experts` correctly gets `UnquantizedFusedMoEMethod`, with `moe_backend='marlin'`. A debug run showed that the draft keeps `ModelOptNvFp4Config` and gets no quant method only because its prefix matches `mtp.*`, so the draft is not losing its quant config by mistake. Marlin has no BF16 MoE kernel: `MarlinExperts._supports_quant_scheme` lists only quantized schemes. `select_unquantized_moe_backend` already lets `humming`, another quantization-only backend, fall through to `auto` (#41652), but `marlin` was not in that list. So it reached `map_unquantized_backend`, which has no entry for it and raises.

**Fix.** Add `"marlin"` to the fall-through list in `vllm/model_executor/layers/fused_moe/oracle/unquantized.py`, and update the comment. Quantized layers go through other oracles, so they keep Marlin. The NVFP4 experts above still log `Using 'MARLIN'`.

**Why the draft override is not enough.** Users can work around the draft case with `"moe_backend": "auto"` in `--speculative-config`, but that override only reaches the draft. In a quantized checkpoint, MoE layers of the main model that are left unquantized (`modules_to_not_convert` / `ignore` / `exclude_modules`) go through the same function with the same global value. No flag reaches them. This change covers them too, but that case was not run end to end here.

**Behavior change.** `--moe-backend marlin` on a model whose MoE layers are all unquantized used to fail at load with a clear error. Now it loads on the auto-selected backend. Only the `Using ... Unquantized MoE backend` info line shows that Marlin was not used. This matches `humming`. No existing test asserts the old error: the tests that set `marlin` all use quantized models, which go through a different oracle.

**Limitations.** Other quantization-only backends still raise the same error for unquantized layers, for example `flashinfer_cutedsl`, `flashinfer_b12x`, `b12x`, `cutlass` and `deep_gemm`. This PR leaves them alone to keep the fix small. A general rule ("no unquantized kernel → auto") could replace the list if maintainers prefer. For the same reason, the comment in `vllm/config/speculative.py` about the draft inheriting the target's `--moe-backend` is still true for those backends, so it is unchanged.
