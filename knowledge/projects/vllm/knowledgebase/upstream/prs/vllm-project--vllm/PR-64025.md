# [ROCm][Perf][Qwen4Exp] Pass the true W4A4 SiLU intermediate pad to AITER

[Upstream PR](https://github.com/vllm-project/vllm/pull/64025) · state: open · merged: False

## Original PR description

## Overview

`aiter_moe_pads` rounds the W4A4 SiLU intermediate pad down to a multiple of 64. This PR passes it unrounded, so that Qwen3.8-Flash-Next (`amd/Qwen3.8-Flash-Next-Quark-MXFP4`) at TP4 reaches AITER's FLAT MXFP4 1-stage MoE kernels. At TP4 the per-rank intermediate width of 160 is stored as 256, a pad of 96, which reaches AITER as 64 today.

**Existing work:**
* [ROCm/aiter#5757](https://github.com/ROCm/aiter/pull/5757) adds the FLAT 16x32, 16x160 and 16x320 tiles and Flash-Next's tuned rows. [ROCm/aiter#7012](https://github.com/ROCm/aiter/pull/7012)  lets them run on vLLM's padded stored widths; this PR needs it and stays in draft until it is merged and released. At TP2 (320 stored as 384, pad 64) the AITER change alone is enough, because 64 is already a multiple of 64.

Not a duplicate: searched open PRs for "aiter_moe_pads", "intermediate_pad aiter", "W4A4 intermediate pad" and "Flash-Next TP4 MoE". #61816 drops the pad on the MXFP4 W4A16 path, which this does not touch. #46201 (draft, predates `aiter_moe_pads`) removes all of the rounding; this changes only the W4A4 SiLU intermediate pad.

## Claims

- With [ROCm/aiter#7012](https://github.com/ROCm/aiter/pull/7012), Flash-Next at TP4 gains 13–16% output throughput at 8k/1k concurrency 1–4 and 10% at 8 and 16 (164 → 186 tok/s at C1, 1005 → 1107 at C16). Concurrency 32 is flat.
- GPQA-Diamond is unchanged: 0.909 → 0.914 (mean of two repeats per arm), 6 problems fixed and 5 broken, exact McNemar p = 1.0.
- No change at M ≥ 32 (prefill, high concurrency) or on AITER releases without [ROCm/aiter#7012](https://github.com/ROCm/aiter/pull/7012): both run the same 2-stage kernel as with the rounded pad.
- No change at TP1 or TP2 for Flash-Next, whose pads (128 and 64) are already multiples of 64, or for any other activation or quantization.

## Details

* **Root cause.** On the AITER W4A4 path, vLLM rounds the expert weights up at load time and passes the zero-filled delta to `fused_moe` as `intermediate_pad`. AITER's FLAT kernels launch over `inter_dim - intermediate_pad` and look up their tuned row at that width. Rounding 96 down to 64 tells AITER the width is 192, which has no tuned row, so the call silently runs 2-stage.
* **Why the other AITER paths are unaffected.** CK-Tile stage 1 rounds the pad itself (`n_pad_zeros = intermediate_pad // 64 * 64 * 2`), and stage 2 uses `intermediate_pad // 128 * 128`, so both get the same values as before. FlyDSL stage 1 sizes its grid with a ceiling division over `inter_dim - intermediate_pad`, and stage 2 masks the K tail at that width and skips only whole pad chunks; SITU already passes 96 unrounded to the same kernels. At this shape AITER has no tuned FlyDSL row and uses CK.
* The hidden pad is still rounded, and every other activation and quantization keeps its current rounding. Nothing changes on CUDA.

**Limitations and CI gaps.**

* gfx950 only. The FLAT kernels exist only for gfx950, and the W4A4 MXFP4 MoE path does not run on gfx942.
* One serving run per cell, without a control-versus-control baseline; the C ≤ 16 gains match the kernel table, and C = 32, where both arms run the same kernel, is level.
* TP4 only. TP1 and TP2 pass the same pad as before.
* The unit test runs in the AMD kernels CI job. The kernel, throughput and accuracy runs happened outside CI.
