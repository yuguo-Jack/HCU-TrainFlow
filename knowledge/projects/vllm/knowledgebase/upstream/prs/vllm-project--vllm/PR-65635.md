# [Rust Frontend] Export vllm:cache_config_info like Python

[Upstream PR](https://github.com/vllm-project/vllm/pull/65635) · state: open · merged: False

## Original PR description



## Overview

The Rust frontend does not export `vllm:cache_config_info`, which the Python frontend exports as an info gauge labeled with every `CacheConfig.metrics_info()` field plus `engine`. This PR has the engine report `CacheConfig.metrics_info()` in its ready response, and the Rust frontend export the gauge from it, one series per engine. Closes vllm-project/vllm#65277.

## Claims

- With `VLLM_USE_RUST_FRONTEND=1`, `/metrics` exports `vllm:cache_config_info`, value `1`, one series per engine, with the same label set as the Python frontend (every `CacheConfig.metrics_info()` field plus `engine`).
- Like Python, the gauge exists only when engines record stats (Python creates it with its stat logger).
- Engine side: `EngineCoreReadyResponse` gains an optional `cache_config_info: dict[str, str]`, set from the engine's `CacheConfig` after initialization. The Python frontend ignores it.

## Details

**Why the engine reports the labels.** The Rust frontend has no source for most of these fields: the startup handshake carries only `num_gpu_blocks`, `block_size` and `kv_cache_size_tokens`, while Python's label set is the whole `CacheConfig.metrics_info()`. The labels describe the engine's cache, so the engine reports them after initialization (`EngineCoreProc._make_ready_response`, one line plus the field). On the Rust side, `vllm-engine-core-client` decodes the field, and `SchedulerStatsRecorder::new`, where the per-engine metric handles are resolved, sets one series per engine. The family lives with the other scheduler-stats families in `vllm-metrics`.

**Differences from the Python frontend.** Label values come from the engine's config after initialization, not from the Python frontend's copy of it:
- Labels the Python frontend never syncs carry the engine's resolved values: on `Qwen/Qwen3-0.6B`, `kv_cache_layout` `LBHNC`, `hash_block_size` `16` and `cache_hit_alignment_tokens` `16`, where Python reports `None`; on the hybrid `Qwen/Qwen3.5-0.8B`, also `mamba_page_size_padded`.
- Under DP, each engine's series carries that engine's own capacity labels. The Python frontend's copy sums `num_gpu_blocks` across engines and keeps the first engine's `kv_cache_size_tokens` and `kv_cache_max_concurrency` (`MPClient._apply_ready_response`), and repeats those values on every engine's series.

**Not a duplicate.** vllm-project/vllm#65462 (opened 2026-11-03) also targets this metric, but exports only the three capacity labels the handshake already carries. That keeps the Rust family's label set different from Python's, so queries and dashboards that select other labels (for example `tests/v1/core/prefix_cache/test_hybrid_prefix_cache_hit_rate.py` reads `mamba_block_size`) would not work on the Rust frontend. This PR exports the full label set from the engine. No other open PR covers it.
