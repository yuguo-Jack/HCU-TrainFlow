# [HiSparse] GLM-5.3-Flash support

[Upstream PR](https://github.com/vllm-project/vllm/pull/61243) · state: open · merged: False

## Original PR description

## Purpose

Make HiSparse work, and pay off, on GLM-5.3-Flash (`Glm5NextForConditionalGeneration`). Fixes #59176.

Flash is the first hybrid model on HiSparse (11 of 45 layers sparse MLA, the rest KDA). It hit startup failures, serving bugs, and a device layout that used *more* GPU memory per request than no HiSparse.

## Changes

**Startup**
- Read `index_topk` from `hf_text_config`, because Flash's top-level config is multimodal.
- `resolve_hisparse_specs` groups only the MLA specs. The KDA and tail-ring groups need the KV layout, which isn't resolved yet at that point.

**Serving**
- Skip per-layer host mirrors outside connector steps. CUDA graph capture raised "HiSparse layer 0 mirrored twice" and startup hung.
- **Core, one line (`gpu/model_runner.py`):** pass `attn_metadata` to `kv_connector.pre_forward` on PIECEWISE and eager steps, as FULL steps already do.
  - Under breakable CUDA graphs (the default for Flash), PIECEWISE replay skips Flash's in-layer HiSparse prepare, which lives in the captured KV-update op.
  - With host-resident pages, the swap-row counter then overflows. This reproduces on B200 with the line reverted.
  - Other connectors ignore the kwarg.
- The kpool indexer places the tail right after the selected pools. This leaves no `-1` gaps in top-k rows, which `FLASH_ATTN_MLA_SPARSE` read as pages and crashed on (Hopper).
- Backends declare `supports_hisparse()`, and selection with HiSparse on skips sparse-MLA backends without a HiSparse path. On Hopper, FlashInfer SM90 read stale KV on prefix hits, and GSM8K fell from 0.901 to 0.745. SM90 support is #61277.

**Device layout** (`vllm/v1/hisparse/`). Every pool block is the size of the largest page, which on Flash is a ~1.1 MB KDA group.
- Hot/resident groups pack up to that page instead of the indexer page, going from 22 groups to 4.
- The indexer block fills that page with whole 256-token kernel pages: 12 on Flash, instead of one 128-token block.
  - The prefix-cache hash block is unchanged.
- KDA (align-mode Mamba) blocks take the indexer kernel page (256 tokens) instead of the hybrid attention block, which HiSparse groups don't use (`_align_hybrid_block_size`).
  - Otherwise multi-page indexer blocks would grow the scheduler block to 9216 tokens (bf16) and 47872 (fp8).
  - It is now the indexer block: 3072 and 2816 tokens, vs 2304 and 4352 before this PR. Capacity is unchanged.
- **Core (`worker/utils.py`):** a 12-page block isn't a whole number of kernel pages from the next block, and padding it would grow every pool block to ≈4.3 MB.
  - Instead, `map_kv_cache_to_kernel_blocks` numbers kernel blocks in units of gcd(block stride, kernel block size).
  - Only specs that opt in with the new `kernel_block_alignment`, met by that unit, get this; the HiSparse indexer declares 16 B.
  - Other specs, including DeepSeek-V4/V4.1, keep the startup `ValueError`.
  - Whole-kernel-block layouts map as before, and kernel block ids are checked against the int32 range.
- Pure-MLA models keep one indexer page per block. GLM-5.3-NVFP4 groups are unchanged (all 64-token, 10.98× at 139k).

This grows the scheduler block size dramatically on Flash (bf16: 2304 → 9216 tokens, fp8: 4352 → 47872), which coarsens prefix-cache boundaries; is there something we can do about this?

- LucasWilkinson · comment · 2026-11-04T04:16:15Z · [source](https://github.com/vllm-project/vllm/pull/61243#discussion_r4463504815)

File: `vllm/v1/worker/utils.py` · line None

Before this PR, an int `block_stride_alignment` only meant "pad the block stride to a multiple of N bytes". Here it also becomes permission for `map_kv_cache_to_kernel_blocks` to split blocks that are not a whole number of kernel pages apart: instead of raising the ValueError, it builds a view whose stride(0) is gcd(block stride, page size), i.e. smaller than a kernel page.

That applies to every compressed spec that already declares an int (e.g. the DSv4.1 indexer's 256 B for DeepGEMM), not just the HiSparse indexer, and their kernels weren't checked against that addressing.

- LucasWilkinson · comment · 2026-11-04T04:28:16Z · [source](https://github.com/vllm-project/vllm/pull/61243#discussion_r4463578966)

File: `vllm/v1/worker/utils.py` · line None

The naming is confusing here: `page_stride` is now gcd(block stride, page size), which can be smaller than a page, so it is no longer the stride between pages. Kernel block ids also stop being page indices (consecutive pages are `page_step` ids apart), but `page_step` / `kernel_block_stride` still read as page units.
