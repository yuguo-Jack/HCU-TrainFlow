# [Perf][Attention] Serve PrefixLM prefill with FlashAttention-2 in the Triton backend

[Upstream PR](https://github.com/vllm-project/vllm/pull/65222) · state: open · merged: False

## Original PR description



## Overview

Serve PrefixLM prefill batches with FlashAttention-2 inside the Triton attention backend on Ampere/Ada GPUs.
Motivated by #63114 (mammoth-1 / elephant-1, which requires `TRITON_ATTN`); this PR does not depend on its code.

## Claims

- elephant-1 on one A100-80GB (11 questions over a ~14.7k-token state, unique state per request, cold prefix cache):
  **+25-28% decisions/s** at concurrency 1/4/8 (7.00 / 6.99 / 6.95 vs 5.61 / 5.56 / 5.47) and lower p50 latency.
- Attention falls from 37% to 18% of GPU time; GEMMs (now 70%) become the bottleneck.
- No decision changes: 0 flips in 880 question-level comparisons against the Triton output; max probability difference
  0.032, mean 0.003 (the spread between two batching settings of the unchanged Triton path).
- Every other batch, and every layer with a sliding window, ALiBi, softcap, sinks or a quantized KV cache, is unchanged.

## Validation

A100-80GB PCIe (SM 8.0), driver 580, torch 2.14.0+cu130, vLLM `c9af9acc6` wheel with the #63114 head (`af2ee49`) Python
overlay, `--attention-backend TRITON_ATTN`, `--enable-prefix-caching`, `--max-num-batched-tokens 32768`. 64 saved
SmartFAQ requests via `POST /v1/systemone`; a unique nonce is prepended to every state so no prefix-cache hit is
possible. A fresh server per arm; one window per cell, so no confidence interval.

| decisions/s | Triton (before) | This PR | p50 latency before -> after |
| --- | ---: | ---: | --- |
| c1 | 5.61 | 7.00 | 2.2 s -> 1.7 s |
| c4 | 5.56 | 6.99 | 7.9 s -> 6.3 s |
| c8 | 5.47 | 6.95 | 15.6 s -> 12.1 s |

An earlier run of the same comparison gave 5.43 / 5.52 / 5.42 before and 6.98 / 6.99 / 6.92 after.
Flips against the Triton output on identical inputs: c1 0/176, c4 0/352, c8 0/352 (max probability difference
0.019 / 0.021 / 0.032, mean 0.0029 / 0.0032 / 0.0032).
Kernel check (paged layout, block size 576, head_dim 256): state prefill 23 ms/layer with FA2 vs 69 ms/layer for
the Triton kernel; output within 2e-3 of PyTorch SDPA.

Unit test, A100:

```bash

```

Before the change the forward pass already matches the dense reference; the failure is the assertion that the fast
path was taken.

**Coverage gap.** `tests/v1/attention` runs in CI only on H100 and B200. The fast path and its test are SM 8.x only,
so CI skips them; the validation above was run by hand on an A100. The end-to-end numbers need the #63114 model, which
is not in tree, so reviewers cannot reproduce them from main alone. The unit test is self-contained. The tests and
benchmark were run on the #63114 head's version of `triton_attn.py`; on `main` this file differs only by an unrelated
quantized-KV scale-cache change (5 lines).

## Details

- **Design.** In a PrefixLM prompt, a query in bidirectional range `[start, end]` attends to keys `0..end`: plain
  non-causal attention over `end + 1` keys. Each (request, range) piece becomes one FA2 varlen sequence sharing the
  request's block table, so a batch whose queries are all inside ranges is a single FA2 call. If any token falls
  outside a range (decode, mixed batches, images surrounded by text), `fa2_prefix_lm` is `None` and nothing changes.
- **Why Triton and not FlashAttention.** The FlashAttention backend serves `mm_prefix` only through FA4
  (`supports_mm_prefix`), which does not run on SM 8.x, so Triton is the only backend there.
- **Scope.** SM 8.x only: FA2 also imports on Hopper/Blackwell, but nothing was measured there, so they stay on Triton.
- **Cost.** For batches carrying mm_prefix ranges, O(requests) Python per step on CPU tensors; no GPU sync. No change
  for batches without ranges.
- **Not covered.** Mixed prefill/decode batches, chunked prefill ending inside a range, sliding-window layers
  (Gemma 4 text layers), quantized KV cache.
- **Duplicates checked** (2026-11-02): #65186 / #60659 (Triton GDN prefill checkpoints, different change), #46558
  (FlashInfer mm-prefix), #42175 and #50294 (closed, FA4 `mm_prefix`). None sends PrefixLM prefill to FA2 on SM 8.x.
