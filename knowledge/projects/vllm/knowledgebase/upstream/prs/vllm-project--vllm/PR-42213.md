# [Bugfix] Fix streaming stop handling during tool parsing

[Upstream PR](https://github.com/vllm-project/vllm/pull/42213) · state: open · merged: False

## Original PR description

## Purpose

Fixes #42210.

When streaming auto tool parsing ends before a valid tool-call delta is emitted, vLLM can drop parser-buffered raw text and incorrectly finish as `tool_calls`. This PR flushes the buffered suffix as plain assistant `content` whenever generation reaches a terminal finish before a tool call is streamed, preserving the engine's original `finish_reason`, such as `stop` or `length`.

If a real tool-call delta has already been streamed, the response still finishes as `tool_calls`.

Using `previous_texts[i]` here will cause content duplication in the streaming response if any content was already emitted for this choice in previous chunks. `previous_texts[i]` is an accumulated string of all text generated so far. When flushing the buffer at the end of the stream, only the portion of the text that has not yet been sent to the client should be included in the `delta_message`. To fix this, track the length of the text already emitted for each choice and only send the remaining suffix from `previous_texts[i]`.
