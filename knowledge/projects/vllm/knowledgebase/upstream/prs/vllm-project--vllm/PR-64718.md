# [2/2][MRV2] Abort sibling microbatches when one fails

[Upstream PR](https://github.com/vllm-project/vllm/pull/64718) · state: open · merged: False

   #64668 [1/2][MRV2] Remove the dependency of MRV2 DBO from MRV1

Stacked on top of #64668. The diff below contains that PR's three commits too, so review only the last commit. This replaces #64310, which carried the same fix directly on main.

## Overview

Unwind DBO workers when a sibling raises, so MRV2 reports the original exception instead of hanging in `UBatchRunner.finish()`.

Related: #55586 (closed, unmerged predecessor) and #63476 (merged error-selection fix). #63476 chooses among recorded errors; it cannot release a surviving worker waiting for another handoff. A search of open DBO/peer-abort PRs found no other matching fix.

## Claims

- Publish the first microbatch failure and wake CPU handoff and startup-barrier waiters.
- Preserve the original microbatch and exception even when cleanup hooks raise secondary errors and the sibling finishes first.
- Unregister partially entered contexts and allow a healthy subsequent run on the same runner.

On the low-latency hook path, base exits through the secondary `AttributeError` instead. In both base and this PR, the peer rank still waits for its transport timeout; the PR does not change that timeout. In base, the peer's second microbatch then waits out a second timeout.

## Details

An exceptional context exit used to wake its neighbor once, just like a normal exit. If the survivor yields again, the departed worker cannot hand control back, so `finish()` joins forever. Minimal case A:

```python
def forward(self, input_ids, positions, **kwargs):
    i = dbo_current_ubatch_id()
    dbo_yield()
    if i == 0:
        raise ValueError("original microbatch failure")
    dbo_yield()
    return input_ids.float().unsqueeze(-1)
```

Case B moves microbatch 1's failure before its first yield while microbatch 0 yields twice. The old #55586 hang test stops after the exit notification and already terminates on main; its hook test registers while the peer is still parked and registered. They miss these post-exit handoffs.

A shared failure tuple is recorded under a lock before waking every CPU event and aborting the ready barrier. Waiters check it before and after waiting. `__exit__` records the original failure before running cleanup hooks; failed `__enter__` unregisters partial state; the worker catch covers failures before context entry. After joins, MRV2 reports only this shared failure, without a redundant worker-error dictionary. Each run gets fresh failure state, and a broken startup barrier is reset before reuse.

**MRV1.** `ubatching.py` is shared, so the V1 runner's DBO path also stops hanging. This matters on main, where `--enable-dbo` runs on V1 unless `VLLM_USE_V2_MODEL_RUNNER=1` is set. V1's `_run_ubatches` is unchanged: it does not catch worker exceptions. A survivor that is still parked now exits with `UBatchAbortedError` instead of hanging, so `_cat_ubatch_outputs` sees missing outputs. A survivor that had already finished behaves as on base. V1 does not get the original-error reporting. It is removed by #63373, so this PR leaves it alone. The tests here exercise only MRV2's `UBatchRunner` and import nothing from V1.

The unit tests validate at the CUDA protocol-component level. The cross-GPU A/B adds real DeepEP HT and NIXL EP transports, but it drives the protocol from a standalone script, not from `UBatchRunner` or a model; no model weights or attention execution are involved. Full-model serving, performance, CUDA device-fault recovery, failure during graph capture/replay, thread-creation failures and legacy-specific behavior remain unqualified. Healthy graph capture/replay coverage is distinct from recovery after a capture failure. No normal-path performance claim is made.
