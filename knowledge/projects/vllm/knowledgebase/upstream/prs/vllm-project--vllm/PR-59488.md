# [Perf][DeepSeek V4.1] Humming indexed MoE GEMM with EP on Hopper, and a named MoE activation format

[Upstream PR](https://github.com/vllm-project/vllm/pull/59488) · state: open · merged: False

## Original PR description

## Purpose

With `--moe-backend humming` and expert parallelism, Humming runs DeepSeek-V4.1's MXFP4 experts on its grouped GEMM. On Hopper the indexed GEMM is much faster for this model. This PR makes `get_humming_moe_gemm_type()` return `indexed` when all of these hold:

- the experts are MXFP4 with DeepSeek V4 routing;
- `model_type` is `deepseek_v41` or `deepseek_v41_text`;
- the device is CUDA SM90;
- there are no all2all kernels, or the backend is `allgather_reducescatter`.

Without EP, Humming already picks indexed, so nothing changes there. `VLLM_HUMMING_MOE_GEMM_TYPE` still overrides the choice. Since #56997, Humming is the default MXFP4 MoE backend on SM90, so V4.1 with EP on Hopper otherwise runs the grouped GEMM by default; this PR moves that default path to indexed too. The rule applies with BF16 activations and with per-token FP8 activations (`--quantization-config.moe.activation fp8_per_token`).

The MXFP4 MoE method (DeepSeek V4/V4.1, Kimi-K3, plain mxfp4) now runs `quantization_config.moe.activation`:

```bash
vllm serve deepseek-ai/DeepSeek-V4.1-Flash -tp 8 --enable-expert-parallel \
    --moe-backend humming --quantization-config.moe.activation fp8_per_token
```

- Humming takes the named format as a fixed input schema, with its input-schema fallback off.
- Other explicit backends must run the named format, and `auto` keeps only the backends that do. Before, these models ignored the name on every backend. Now a backend that does not run it stops vLLM, on every platform (CUDA, ROCm, XPU, CPU). The DeepSeek V4 MegaMoE backends (`deep_gemm_mega_moe`, `aiter_mega_moe`) build their own experts and do not read the name. On ROCm, the Kimi-K3 AITER path, which skips the backend selector, now refuses a named activation instead of ignoring it. For example, `fp8_per_token` with `flashinfer_trtllm` now stops vLLM instead of running MXFP8. A draft model with its own `speculative_config.moe_backend` inherits the target's `quantization_config`, so the same rule applies to it.
- The startup log prints the format Humming runs: `Humming MoE activations: fp8_per_token (group size 0, scale dtype float32)`. The line appears for every Humming MoE model, gpt-oss included.
- On SM90 Humming, `mxfp8` and `fp8_per_block_dynamic` stop vLLM at startup, before the weights load. Humming has no e8m0 input scales on WGMMA, and humming 0.1.16 rejects fp32 group scales with MXFP4 weights (#60600). Group-wise scales are also 1.2x to 24x slower than per-token in the SM90 Humming GEMM at M >= 256 (numbers in the review reply).
- `VLLM_HUMMING_INPUT_QUANT_CONFIG` still works as on main, with no early check: a format Humming cannot run fails while the weights convert, as before. With `--moe-backend humming`, setting it together with `moe.activation` is an error.
- gpt-oss is unchanged. With no name, nothing changes.

`test_humming_deepseek_v41_hopper_uses_indexed_gemm_with_ep` calls `get_humming_moe_gemm_type` and checks that V4.1 with EP gets indexed, with and without `allgather_reducescatter`, and that DeepEP, SM100 and DeepSeek V4 keep the grouped GEMM. It does not need the humming package.

`test_deepseek_v4_mxfp4_backend_must_run_named_activation` checks on any GPU that `auto` and `flashinfer_trtllm` refuse `fp8_per_token`, and that `humming` refuses the env JSON plus a name ("not both"). `test_humming_deepseek_v4_activation_on_sm90` checks that SM90 Humming accepts `fp8_per_token` and refuses `mxfp8`. It skips on other GPUs, so in CI it runs only in the optional H100 FP8 MoE kernels job; `kernels-moe-test` runs on L4. The Kimi-K3 AITER refusal has no unit test: it is a short guard, and a test would have to mock the whole K3 path.

`user_moe_activation_override()` (was `_user_moe_activation_override()`) is now public because `quantization/mxfp4.py` imports it; the existing monkeypatches in `test_b12x.py`, `test_ocp_mx_moe.py` and `test_gfx950_moe.py` use the new name.

Startup check: `vllm serve deepseek-ai/DeepSeek-V4.1-Flash -tp 8 --enable-expert-parallel --moe-backend humming` on 8x H200, with these additions:

- A: `--quantization-config.moe.activation fp8_per_token` and DSpark speculative decoding (`--speculative-config '{"method":"dspark","num_speculative_tokens":1}'`; V4.1 has no classic MTP draft), then one completion request.
- B: `--quantization-config.moe.activation mxfp8`.
- C: `--quantization-config.moe.activation fp8_per_block_dynamic`.
- D: `--quantization-config.moe.activation fp8_per_token` with `VLLM_HUMMING_INPUT_QUANT_CONFIG='{"dtype":"float8e4m3"}'`.
- E: only `VLLM_HUMMING_INPUT_QUANT_CONFIG='{"dtype":"float8e4m3"}'`, then one completion request.
- `auto`: no `--moe-backend` and no activation name, then one completion request.

Throughput: offline `LLM` runs of DeepSeek-V4.1-Flash on 8x H200, TP8+EP, `--moe-backend humming`, 2 repeats. Prefill is 16 random 8192-token prompts with 1 output token. Decode is 64 random 512-token prompts with 256 output tokens. The GEMM type was set with `VLLM_HUMMING_MOE_GEMM_TYPE`.

Indexed vs grouped throughput:

| Activations | Prefill | Decode |
|---|---|---|
| BF16 | +47% | +63% |
| per-token FP8 (reference) | +24% | +36% |

For reference, with FP8 at decode, grouped is 16% slower than Marlin (2,222 vs 2,648 output tok/s) and indexed is 14% faster.

I think it is interesting to support this, but I am a bit skeptical about how safe it is to make it the default, i.e., assume per-token FP8 quantization has no accuracy impact over BF16/grouped-FP8.

Notably, on Blackwell where FP8 activations are already the default, we use MXFP8 (group-32 e8m0 scales), or block-FP8 (group-128); both much finer-grained than one scale per token row. I suspect per-token FP8 is too coarse, and GSM8K is simply not a rigorous enough eval to study real accuracy impact.

I would either make the per-token FP8 path opt-in for now, or evaluate this more exhaustively before making it default, e.g. on agentic evals.

- simon-veitner-redhat · comment · 2026-10-08T09:40:51Z · [source](https://github.com/vllm-project/vllm/pull/59488#issuecomment-6057082702)

@LopezCastroRoberto Thanks, agreed. The latest push makes the activation format an explicit, named choice. It uses the existing typed field instead of a new env string, because those names are documented, validated at parse time, and shared with gpt-oss:

```bash
--moe-backend humming --quantization-config.moe.activation fp8_per_token
```

- The names come from `QUANT_KEY_NAMES` (`fp8_per_token`, `fp8_per_block_dynamic`, `mxfp8`). Each name is one scale layout on every arch. A named format turns Humming's input-schema fallback off, so it runs as named or vLLM stops.
- It applies to the MXFP4 MoE method: DeepSeek V4/V4.1, Kimi-K3 and plain mxfp4 checkpoints. A backend that cannot run the name stops vLLM at startup, also on SM100f. For example, `fp8_per_token` with `flashinfer_trtllm` or `auto` no longer runs MXFP8 silently.
- On SM90 Humming, `mxfp8` and `fp8_per_block_dynamic` stop vLLM at startup, before the weights load. `mxfp8` needs e8m0 input scales, which Humming's WGMMA path does not have. humming 0.1.16 rejects `fp8_per_block_dynamic` (fp32 group-128 scales) with MXFP4 weights, although vLLM's supported-pairs table lists it for Hopper. I opened #60600 for that mismatch.
- The startup log prints the resolved format, for example `Humming MoE activations: fp8_per_token (group size 0, scale dtype float32)`. It also does so for the old `VLLM_HUMMING_INPUT_QUANT_CONFIG` path, which still works. Setting both the env JSON and the name is an error.
- With no name nothing changes: Marlin with BF16 stays the default for V4.1 on Hopper.
- gpt-oss is unchanged: its selector still drops Humming when an activation is named.

Why SM90 gets only per-token: I ran a dense-GEMM microbenchmark of the Humming MXFP4 GEMM on H200 (not the MoE path). Group scales rescale the WGMMA accumulators once per group:

| shape, M | BF16 | per-token | g128 | g32 (MXFP8 numerics) |
|---|---|---|---|---|
| w13 (2048x4096), 256 | 16.8 us | 14.6 us | 31.7 us | 74.7 us |
| w13 (2048x4096), 4096 | 110.9 us | 72.2 us | 535.7 us | 1720 us |
| w2 (4096x1024), 256 | 13.3 us | 12.9 us | 15.9 us | 38.2 us |
| w2 (4096x1024), 4096 | 66.1 us | 53.5 us | 218.4 us | 917.7 us |

At M >= 256, group scales are 1.2x to 24x slower than per-token. Matching SM100f's MXFP8 on Hopper first needs e8m0 input scales on WGMMA in Humming.

On a synthetic outlier test, the relative error against a BF16-input reference was 0.022-0.024 for per-token, 0.015-0.020 for g128 and g32 with fp32 scales, and 0.025-0.027 for MXFP8 numerics (e8m0 scales). That is not a model eval.

FP8 stays opt-in, so the eval sweep I promised on 10-01 does not gate this PR. I will post it separately.

- Metric: P90 request interactivity (1/TPOT, tok/s).
- The indexed run used `VLLM_HUMMING_MOE_GEMM_TYPE=indexed`, which is the GEMM type this PR selects by default for V4.1 + EP on SM90. The log shows `Using indexed gemm for humming moe` and `HummingIndexedExperts`.

| Humming indexed (this PR's rule) | 1 | 105.93 | 143.8 | 0.75 |
| Marlin (`--moe-backend marlin`) | 4 | 110.68 / 111.29 / 111.05 / 113.95 | 147.9-150.2 | 0.70-0.82 |

- Grouped vs Marlin was an interleaved 3A+3B comparison on fresh servers: +32.8%, and every Marlin run was above every grouped run.
