# [CI] Pin DeepSeek-V4.1-Flash-NVFP4 eval to its FP8-Engram revision

[Upstream PR](https://github.com/vllm-project/vllm/pull/61763) · state: closed · merged: True

## Original PR description



## Overview

Pin `tests/evals/gsm8k/configs/DeepSeek-V4.1-Flash-NVFP4-DSpark-TP4.yaml` to HF revision `3431dde3` of `nvidia/DeepSeek-V4.1-Flash-NVFP4`, the last revision before the checkpoint stored its Engram tables as MXFP4. This is a stopgap until #61530 adds MXFP4 Engram support; revert the pin when #61530 merges.

## Claims

- `(B200) LM Eval Spec Decode` stops failing at weight loading with `AssertionError: engram shard (…, 128) does not fit param (…, 256)`. Example on the v0.32.0 release branch: https://buildkite.com/vllm/ci/builds/94968. Main's last pass (94756, 10:00Z Oct 14) predates the checkpoint change, so main fails the same way on its next run.
- CI only. No vLLM code changes.

## Validation

- `config.json` at the pinned revision has no `engram_embed_*` fields, which is the FP8 Engram layout the current loader expects. Revision `main` has `engram_embed_quant: mxfp4`, `engram_embed_block_size: 32`, `engram_embed_scale_dtype: ue8m0` and `engram_embed_layers: [1, 14]`.
- `--revision <sha>` in `server_args` is already used by `DeepSeek-V2-Lite-Instruct-FP8-TP1-PCP2-ROCm.yaml`, and the YAML still parses.
- Not run: the full 4xB200 GSM8K eval. 4-GPU B200 capacity is scarce right now, and this step's CI run on this PR is the end-to-end check.

## Details

**What changed upstream.** At 16:40Z on Oct 14, HF PR #2 on `nvidia/DeepSeek-V4.1-Flash-NVFP4` ("Store Engram lookup tables as MXFP4", commit `c48dca0146`) merged. It rewrote shards 47 and 48 and `config.json`, and the checkpoint shrank from about 491 GiB to about 400 GiB. vLLM support for that format is #61530, which is still in review. Every vLLM version without #61530 fails on the current `main` revision. This PR only keeps CI testing the format vLLM currently supports.

**Tokenizer and remote code.** HF PR #2 touched only shards 47/48, `config.json` and the README, so the tokenizer and `trust_remote_code` files are identical at both revisions.

**Release branch.** This also needs a cherry-pick to `releases/v0.32.0` if v0.32.0 ships without #61530.

Not a duplicate: I searched open PRs for this checkpoint and for revision pins and found nothing.
