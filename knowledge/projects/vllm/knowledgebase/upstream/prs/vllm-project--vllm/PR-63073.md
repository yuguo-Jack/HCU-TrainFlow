# [Perf][ROCm][GLM-5.3-Flash] Gluon KDA spec decode kernel for gfx950

[Upstream PR](https://github.com/vllm-project/vllm/pull/63073) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

**This PR depends on #63071 and includes its commit. Only the last commit is new.**

#63071 adds a deferred-state mode to the Triton KDA spec decode kernel for GLM-5.3-Flash on ROCm. On MI355X that kernel is limited by VALU issue:
- Triton holds 8 state rows × 4 K columns per lane, so every K reduction takes 5 DPP levels per row.
- Each token also pays IEEE divisions and range-fixed exponentials per element.
- The token loop takes about 900 instructions per wave.

I tried other BV and num_warps values, 2D loads, prefetching the next token and reordering the output math. None of them helped.

This PR adds a Gluon kernel with the same contract. On gfx950 it is used when the shapes fit: K a power of 2, V a multiple of 32, and per-head beta.

AITER's Gluon `fused_recurrent_kda` has no deferred mode on gfx950 (`cache_state_updates` hits a static_assert). Without that mode it is slower than the deferred Triton kernel: 249 µs vs 159 to 223 µs at 64 sequences × 8 tokens.

Related: #61761 (DFlash2 performance on ROCm), #61434 (the GDN deferred state).

## Claims

- GLM-5.3-Flash + DFlash2, MI355X TP2: step time at c=64 is 4.5% lower than with the Triton deferred kernel (57.4 → 54.8 ms). Output tok/s goes up at c=1, c=16 and c=64.
- The kernel is 1.4× to 1.7× faster for spec steps of 16 or more sequences. At 1 sequence it is also faster, which removes the c=1 cost of #63071.
- After a chain of spec steps, the state matches an fp64 reference to 1.3e-7, the same as the Triton kernel. GSM8K: 0.9727, vs 0.9704 with the Triton kernel.
- Other GPUs, and shapes that do not fit, still use the Triton kernel.

## Validation

**End to end.** Breakable CUDA graphs (#63070), `max_cudagraph_capture_size` 2048, `ROCM_ATTN` drafter (#63069). Both rows ran on the same GPU pair. Output tok/s; step time is TPOT × acceptance length:

| deferred KDA kernel | c=1 | c=16 | c=64 | c=64 step | GSM8K |
|---|---|---|---|---|---|
| Triton (#63071) | 380.2 | 2240.0 | 4664.3 | 57.4 ms | 0.9704 |
| Gluon (this PR) | 395.7 | 2372.0 | 4709.0 | 54.8 ms | 0.9727 |

The c=1 step time drops from 11.87 to 11.46 ms (−3.5%). That is 2.3% below the per-token kernel on main (11.73 ms).

**Kernel.** 32 heads, K = V = 128, fp32 state. Times are in µs, Triton → Gluon, measured as CUDA-graph replay (plain `do_bench` is launch-bound for these kernels and reads 2–3× too high):

| sequences | T=1 | T=8, 1 accepted | T=8, 4 accepted | T=8, 8 accepted |
|---|---|---|---|---|
| 1 | 5.2 → 4.6 | 19.4 → 13.6 | 20.9 → 15.0 | 25.4 → 15.9 |
| 16 | 12.1 → 13.4 | 42.1 → 31.6 | 49.1 → 33.0 | 58.6 → 35.2 |
| 64 | 44.8 → 44.3 | 138.9 → 92.4 | 164.6 → 107.3 | 197.9 → 118.4 |
| 128 | 88.6 → 85.7 | 285.0 → 200.4 | 338.0 → 223.7 | 422.1 → 242.8 |

T=1 is bound by state bandwidth (about 6 TB/s), so it cannot get much faster.

**Test.** `test_fused_recurrent_kda_defer_spec_state` now runs with both kernels. The Gluon cases run on gfx950 only.
- On MI355X, `tests/models/glm5next/test_kda_recurrent.py` gives 18 passed and 14 skipped. The skipped tests need CUDA.
- Separately, I checked both kernels against an fp64 reference over a chain of random spec steps. The state error is 1.3e-7 for both. That script is not part of this PR.

## Details

**Layout.** One warp owns a [32, K] slab of a head's fp32 state. Each lane holds 8 contiguous K columns, which is one 16-byte bf16 load, and K is spread over 16 lanes (layout `[1,8]/[4,16]/[1,1]`).
- K reductions stay inside the warp.
- Nothing changes layout inside the token loop.
- Of SPT_K ∈ {4, 8, 16, 32} × BV ∈ {16, 32, 64} × 1, 2 or 4 warps, (8, 32, 1 warp) was the fastest.

**Fewer instructions.**
- There is one division per token-wide scalar.
- The per-element gate uses `v_rcp_f32` and `v_exp_f32` (1 ulp) through inline asm.
- The token loop goes from 887 to 511 instructions.

**Records.** A record holds:
- the normalized k;
- the decay a = exp(gate);
- the delta-rule error err = sigmoid(beta) · (v − (a·S)ᵀk).

So the replay is S = a·S + err ⊗ k, with no reductions and no gate math. The token loop and the replay apply the update through the same helper, so a replayed state is bit-identical to the one the token loop computed.

**Kernel choice.** The Gluon and Triton records are not interchangeable. So the kernel is chosen only from the model shapes and the device (`_on_gfx950()`, cached), never per batch. Every step of a process uses the same kernel.
