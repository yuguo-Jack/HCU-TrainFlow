# [Bugfix] Fix IPC handle leak in CustomAllreduce during CUDA graph memory profiling

[Upstream PR](https://github.com/vllm-project/vllm/pull/46515) · state: open · merged: False

## Original PR description

## Purpose

PR #30515 introduced `profile_cudagraph_memory()` which captures temporary CUDA graphs to estimate per-graph memory cost. When custom allreduce is active during these captures, IPC handles are opened via `cudaIpcOpenMemHandle` for graph buffer registration, but never closed when the temporary graphs are discarded.

This leaks GPU memory (stale IPC mappings + driver-side resources) until the CustomAllreduce destructor runs at engine shutdown.

**Root Cause**

The leak flow inside `profile_cudagraph_memory()`:

```plain
graph_capture() context
 → _warmup_and_capture() captures temporary CUDA graphs
   → model forward → custom_all_reduce() → C++ allreduce()
     → stream is capturing → graph_unreg_buffers_.push_back(ptr)
 → register_graph_buffers()
   → cudaIpcGetMemHandle + cudaIpcOpenMemHandle for each buffer
   → IPC mappings stored in ipc_handles_ map
 → CUDAGraphWrapper.clear_all_graphs()
   → CUDA graphs destroyed, rank-data slots released
 → Temporary input tensors freed (cudaFree)
 → ipc_handles_ entries NEVER closed with cudaIpcCloseMemHandle  ← LEAK
```

The stale IPC mappings hold references to freed physical pages and consume driver-side resources. They persist for the lifetime of the CustomAllreduce object (i.e., the entire engine session).

Moreover, according to [CUDA API Documentation](https://docs.nvidia.com/cuda/cuda-driver-api/group__CUDA__MEM.html#group__CUDA__MEM),

> Calling [cuMemFree](https://docs.nvidia.com/cuda/cuda-driver-api/group__CUDA__MEM.html#group__CUDA__MEM_1g89b3f154e17cc89b6eea277dbdf5c93a) on an exported memory region before calling [cuIpcCloseMemHandle](https://docs.nvidia.com/cuda/cuda-driver-api/group__CUDA__MEM.html#group__CUDA__MEM_1gd6f5d5bcf6376c6853b64635b0157b9e) in the importing context will result in **undefined behavior**.

**Fix**

Adding a `close_graph_ipc_handles()` method that:

1. Calls `cudaIpcCloseMemHandle` for every IPC mapping in `ipc_handles_`
2. Clears the `ipc_handles_` map and `graph_unreg_buffers_`
3. Resets the `d_rank_data_base_` cursor to `d_rank_data_origin_` so subsequent graph captures can reuse the rank-data slots

Called in two places:

+ `profile_cudagraph_memory()` — in the `finally` block after `clear_all_graphs()`
+ `shutdown()` — before tearing down the model

## Test Plan

Run with custom allreduce enabled (disable `fuse_allreduce_rms` on Hopper/Blackwell to force the custom AR path):

```bash
vllm serve <model> --tensor-parallel-size 2 \
  --compilation-config '{"pass_config": {"fuse_allreduce_rms": false}}'
```

Check logs for:

```plain
Registering 388 cuda graph addresses   ← profiling phase (LEAKED)
Registering 9894 cuda graph addresses  ← real capture phase (OK)
```

The 388 IPC handles from profiling are leaked and never reclaimed.

## Test Result

+ Verified with Qwen3-30B-A3B on 2×H20 (TP=2, 97871 MiB each) with `fuse_allreduce_rms=false`
+ Confirmed custom allreduce is triggered (`Registering 388/9894 cuda graph addresses`)
+ With the fix, the 388 profiling IPC handles are properly closed before real capture
+ GPU memory comparison:

| Metric | Before fix | After fix |
| --- | --- | --- |
| GPU 0 memory | 85537 MiB | 85381 MiB |
| GPU 1 memory | 85537 MiB | 85381 MiB |
| Savings | — | **~156 MiB / GPU** |


The ~156 MiB reduction per GPU corresponds to the leaked IPC mappings (388 handles × 2 GPUs) that held references to freed physical pages and driver-side resources. With the fix, these are reclaimed immediately after `profile_cudagraph_memory()` completes.
