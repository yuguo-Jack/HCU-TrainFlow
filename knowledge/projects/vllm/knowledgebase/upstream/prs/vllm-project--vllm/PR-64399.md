## CRI MXFP MoE integration: hardware validation, model performance and accuracy controls

### Summary

- Native ARK CRI kernels were built successfully and exercised through vLLM.
- MXFP8 activations × MXFP4 weights passed real-device kernel/model smoke tests
  and now also have a complete 48-layer model evaluation.
- MXFP8, normal MXFP4 and FWHT+MXFP4 use the same complete 48-layer
  Qwen3-30B-A3B MXFP4 checkpoint, with an independent INT4 W4A16 accuracy reference.
- All four complete-model configurations produced coherent English/Chinese responses.
- The MXFP8-activation control measured PPL **13.680705** and GSM8K **24/32
  (75.000%)** on the fixed subsets. It was slower than normal MXFP4 in every
  timed case; decode-heavy batch latency was **9.71–13.27×** normal MXFP4.
- **No model-level FWHT speedup was demonstrated:** prefill-heavy cases were
  approximately tied; decode-heavy cases had 1.48–3.29% higher latency.
- Quantitative accuracy results in this comment cover the INT4 W4A16 reference,
  normal MXFP4 baseline, MXFP8-activation control and FWHT+MXFP4 configuration.
  These are preliminary subset results; no accuracy-equivalence claim is made.
- Performance results shown here cover only MXFP8, normal MXFP4 and FWHT+MXFP4;
  INT4 W4A16 is retained only as an accuracy reference.

The full ARK XPU extension compiled and linked successfully (289 build steps).
Runtime capability checks confirmed `sycl_target=cri` and `has_mxfp_bdpas=True`.

translation unit; the pinned SYCL-TLA headers were retained for ordinary kernels.

| Mode | Selector | Routed-expert computation | Coverage reported here |
| --- | --- | --- | --- |
| MXFP8 × MXFP4 | `ark_mxfp8` | Dynamic group-32 E4M3 activations × E2M1 weights | Full 48-layer model, quality subset, performance, E2E; native tests and earlier 12-layer smoke |
| Normal MXFP4 × MXFP4 | `ark_mxfp4` | Raw activations quantized to MXFP4, without FWHT; original packed weights retained | Full 48-layer model, quality subset, performance, E2E |
| FWHT+MXFP4 × MXFP4 | `ark_mxfp4_fwht` | Normalized H32 activation transform + MXFP4 quantization; matching expert-weight basis transform/requantization | Full 48-layer model, quality subset, qualitative generation, performance, E2E; earlier 12-layer smoke |
| INT4 W4A16 accuracy reference | `VLLM_XPU_INC_WNA16_BACKEND=auto` | Existing ARK WNA16 method | Full 48-layer model, quality subset |

Both expert projections, `w13` and `w2`, use the selected ARK path in prefill and
decode. Decode uses the same grouped GEMM entry points, not a separate optimized
decode kernel or a W4A16 fallback for the MXFP modes. Attention and non-MoE
linears retain their checkpoint-specific existing backends.

For the normal/FWHT ablation, both modes use the same ARK FP4 grouped GEMM.
Normal quantization uses `_quant_only=True`. FWHT transforms both expert weight
projections as `W @ H32` at loading, then requantizes them. This is a runtime
preparation step applied to the existing MXFP4 checkpoint, rather than loading
a pre-rotated checkpoint export.

### 2. Models and exact revisions

| Purpose | Model | Layers | Revision |
| --- | --- | ---: | --- |
| MXFP8/normal MXFP4/FWHT full-model comparison | [INCModel/Qwen3-30B-A3B-AutoRound-MXFP4-W4A4](https://huggingface.co/INCModel/Qwen3-30B-A3B-AutoRound-MXFP4-W4A4) | 48 | `30056176cb3d122602172e39c33a0b36edda93a4` |
| Independent accuracy reference | [INCModel/Qwen3-30B-A3B-AutoRound-INT4-W4A16](https://huggingface.co/INCModel/Qwen3-30B-A3B-AutoRound-INT4-W4A16) | 48 | `80c3cd0bba6dbdc49d50ddeabfe232543cbd5a0a` |
| Initial loader/dispatch smoke | [INCModel/Qwen3-30B-A3B-12L-MXFP4-test](https://huggingface.co/INCModel/Qwen3-30B-A3B-12L-MXFP4-test) | 12 | `59a244387c2c55a085a65384280943322d36da0f` |

The MXFP4 checkpoint uses symmetric E2M1 weights, E8M0 scales, group size 32, and
`auto_round:llm_compressor` packing. The INT4 checkpoint uses symmetric integer
weights, group size 32, and `auto_round:auto_gptq` packing. **INT4 packed codes/scales
were not reinterpreted as MXFP4.** INT4 is an independent reference, not a
same-format FWHT ablation.

**The checkpoints also differ outside MoE.** A follow-up audit of both pinned
configs and tensor indexes checked all 48 layers: the INT4 checkpoint stores
all 192 attention `q/k/v/o` projections as packed INT4, while the MXFP4
checkpoint explicitly keeps those 192 projections at 16 bits. Both retain an
unquantized LM head. The INT4 accuracy reference therefore differs in attention
projection quantization as well as MoE and is not an isolated MoE-only accuracy
ablation. The MXFP8/normal/FWHT ablation retains the same non-MoE configuration.

The MXFP8 control is **MXFP8 activations × MXFP4 weights**, not MXFP8 weights or
a separate MXFP8 checkpoint. The `ark_mxfp8` selector changes the routed-expert
activation format to group-32 E4M3 with E8M0 scales. It retains the same original
packed MXFP4 expert weights as normal `ark_mxfp4`; neither control rotates weights.
The checkpoint name contains W4A4, but the explicit selector determines the
activation format for these routed-expert operations.

Every full-model run inspected all 48 routed MoE layers. Observed methods were
`INCARKMxfp4MoEMethod` with the requested MXFP8/normal/FWHT selector, and
`INCARKWNA16MoEMethod` for the INT4 reference.

| Setting | Value |
| --- | --- |

| Engine/request seed | 42 |
| Performance sampling | Greedy, fixed output length, `ignore_eos=True`, detokenization disabled |
| Warmup/timed iterations | 2 warmups + 5 timed iterations per case |

Measurements are wall-clock times for an entire offline `LLM.generate` batch,
with XPU synchronization around timed runs. They include engine scheduling,
attention, activation quantization, expert routing, and MoE GEMMs. They exclude
model loading and one-time FWHT weight preparation. Fixed synthetic input token
IDs were generated using NumPy RNG seed 42; their hashes match across the three
MXFP performance runs.
The MXFP8 control was measured in a later sequential run, not interleaved with
the original normal/FWHT runs; the runtime, GPU UUID, engine settings,
evaluation data and benchmark input hashes were checked against the originals.

These are **batch end-to-end latencies, not kernel timings, serving TTFT, or
measured TPOT**. The output-length-1 cases are prefill-heavy and output-length-64 cases are
decode-heavy, but both include all work needed for the complete request.

**Do not compare these rows as one prefill step versus one decode step.**
Generating one token normally requires one prompt forward pass; generating
64 tokens normally requires the prompt pass plus 63 sequential incremental
passes. The rows also have different input lengths (512 versus 32). A larger
total latency for the 64-output case does not by itself indicate slower
per-step decoding. Matched-input first-token and incremental-token timings
would be needed for that comparison.

**Interpretation:** prefill-heavy normal/FWHT results are approximately tied;

change expert routing despite identical prompt IDs and sampling settings.

The MXFP8 control has **4.01× / 1.95×** normal MXFP4 latency for the batch-1 /
batch-8 prefill-heavy cases, and **13.27× / 9.71×** for the corresponding
decode-heavy cases. These are measurements of the current integration, not an
intrinsic MXFP8 hardware throughput comparison. This same-workload gap remains
even after accounting for the 64 output tokens; it is separate from the
prefill-heavy versus decode-heavy total-latency comparison.

#### Decode accounting and implementation overhead

For illustration only, divide each batch-1 32-input/64-output latency by 64:

| Configuration | Whole request (s) | E2E time divided by output tokens (ms) |
| --- | ---: | ---: |
| Normal MXFP4 | 4.282115 | 66.908 |
| MXFP8 A × MXFP4 W | 56.819599 | 887.806 |
| FWHT MXFP4 | 4.345646 | 67.901 |

This normalization includes prefill and engine overhead; it is **not measured
TPOT**. For batch 8, dividing batch latency by 64 gives time per output-token
position across the batch; dividing by 512 gives aggregate time per emitted
token. Neither quantity is an isolated decode-kernel latency.

Source inspection identifies a concrete extra cost in the configured MXFP8
BDPAS path: on a staging refresh, it expands/transposes the packed E2M1 weight
payloads to FP8 staging for **all experts**, then transposes their scales.
The normal/FWHT native FP4 path reads packed weights directly and refreshes
only weight-scale staging. Workspaces are shared by shape, not resident per
layer, so switching between same-shaped layers requires staging to be refreshed
again; inference tensors without mutation counters also force refreshes.

For this 48-layer model (128 experts, hidden size 2048, intermediate size 768),
refreshing both projections in every layer entails approximately **13.5 GiB of
packed-weight reads plus 27 GiB of expanded-payload writes per forward pass**,
before scale traffic and GEMM reads. These are source-derived logical traffic
counts, not profiler measurements. Repeating this work per decode position is
a plausible major contributor to the MXFP8 gap, not an unavoidable property of
MXFP8 arithmetic. Both MXFP4 modes still use grouped prefill GEMMs for small
decode batches, and the MXFP grouped modes incur host-synchronized routing
metadata. No dedicated small-token MXFP decode implementation was validated here.

No runtime profiling breakdown was collected, so the exact contribution of
staging versus GEMM, quantization and routing remains unmeasured. The current
MXFP8 path is not a performance win in these cases.

### 5. Model accuracy and qualitative generation

The quantitative accuracy table below covers the INT4 W4A16 reference, normal
MXFP4 baseline, MXFP8-activation control and FWHT+MXFP4 configuration, using the
same evaluation subsets and settings. Generation examples remain qualitative
smoke checks, not evidence of accuracy equivalence.

#### Evaluation methodology

- **WikiText-2 subset:** first 8192 token IDs of the test split, split into
  sixteen non-overlapping 512-token chunks. The first token in each chunk is
  unscored, giving **8176 scored tokens**. PPL is computed from actual prompt-token
  log probabilities. This is not a full WikiText-2 benchmark or sliding-window PPL.
- **GSM8K subset:** first 32 test questions, zero-shot chat, thinking disabled,
  greedy decoding, seed 42, maximum 256 generated tokens per question. Numerical
  answer extraction reuses the existing vLLM evaluation helper, which extracts
  the last number; therefore truncation can materially affect the score.
- **Qualitative generation:** six prompts covering English QA, multiplication,
  English-to-Chinese translation, Chinese explanation, Python generation, and
  simple word arithmetic. Thinking disabled, greedy, maximum 128 output tokens.

equal aggregate scores do not establish accuracy equivalence.

The GSM8K sample is small, not random, and includes truncated answers. These
are preliminary subset results, not full benchmark scores. No BF16 accuracy

### 7. Known limitations and unsupported configurations

- The native XPU W4A16 reference attempt was rejected by the installed
  `XPUExperts` implementation because it supports Xe2/Xe3, not CRI. Architecture
  checks were not bypassed. The successful INT4 run uses ARK WNA16.
- The default native INC MXFP4 `auto` backend was not benchmarked. The normal
  baseline in these tables is explicitly **ARK `ark_mxfp4`**, not `auto`.
- Triton attention was selected because the installed XPU FlashAttention wheel
  rejects CRI. The MoE GEMMs still use ARK CRI BDPAS.
- ARK grouped routing metadata requires host synchronization: eager execution
  is required and graph capture is unsupported.
- Optional static routing caches were disabled because native device writes do
  not increment the mutation counter those caches use.
- TP=1 only was validated. TP>1, expert parallelism, production serving load,
  long-context behavior, and full benchmark accuracy were not validated.
- INT4 is an independent accuracy reference, not a MoE-only accuracy ablation:
  its attention projections are also INT4, unlike those in the MXFP4 model.
- The FWHT path does not accept a pre-rotated checkpoint format; it transforms
  and requantizes expert weights at loading.
- No kernel-only performance comparison, matched-input TTFT/TPOT measurement,
  or runtime profiling breakdown of the MXFP8 latency gap is included. The
  staging discussion above is source analysis, not a measured attribution.

### Conclusion

The integration is exercised on real CRI hardware, including successful native
kernel tests and complete-model MXFP8/normal/FWHT runs. It establishes a working
end-to-end calling path. The current model-level measurements show near-tied
prefill-heavy batch latency and modestly slower FWHT decode-heavy latency; a performance
win is not demonstrated in these cases. The MXFP8-activation control has lower
subset PPL than normal MXFP4 but substantially higher latency in the current
implementation. Quantitative accuracy figures reported here cover INT4 W4A16,
normal MXFP4, MXFP8 activations × MXFP4 weights and FWHT+MXFP4; they are not full
benchmarks.
