# [Misc] Use multithreading to accelerate server memcpy.

[Upstream PR](https://github.com/vllm-project/vllm/pull/59123) · state: open · merged: False

## Original PR description




## Purpose

Server CPUs usually need multithreading to saturate copy bandwidth. Multimodal data copying and KV cache offloading may benefit from this.

Server CPUs, such as the Xeon Gold 6554S, can only reach 7 GiB/s for single-threaded memcpy, which is frustrating. With 8 threads, it can reach around 26 GiB/s (hope it can reach 40 GiB/s.). Desktop processors such as the 9800X3D can reach 21 GiB/s on a single core, which is already basically saturated, so multi-threaded acceleration isn’t needed.


Ideally, there would be a multithreaded version of np.ascontiguousarray.




### Benchmark

- Buffers: src 4 GiB (each 4 KiB page filled with distinct bytes to force physical allocation) + dst 4 GiB (touched page by page)
- Workload: 2048 random 1 MiB blocks (fixed LCG seed), 2 GiB per call
- Working set 2 GiB ≫ L3 (60 MB), ensuring DRAM bandwidth is what's measured
- Environment: `OMP_PROC_BIND=close OMP_PLACES=cores numactl --cpunodebind=0 --membind=0`
- Timing: 1 warmup run + 5 timed runs averaged

###  Results

| T | Cython memcpy | Cython NT loop | Rust memcpy | Rust NT loop | Rust vs Cython NT |
|---|---|---|---|---|---|
| 1 | 7.48 | 10.54 | 6.89 | 9.40 | -11% |
| 2 | 13.58 | 19.41 | 13.42 | 17.13 | -12% |
| 4 | 22.64 | 33.30 | 19.37 | 22.89 | -31% |
| 8 | 30.92 | 45.67 | 23.00 | 28.46 | -38% |
| 16 | 41.91 | **49.44** | 25.32 | 27.54 | -44% |
| 24 | 42.53 | 47.13 | 23.12 | 25.20 | -47% |
| 32 | 42.62 | 42.96 | 20.68 | 16.97 | -60% |

**Cython+OpenMP+NT surpasses numba and Rust rayon, so should we let some vLLM modules use Cython?**
