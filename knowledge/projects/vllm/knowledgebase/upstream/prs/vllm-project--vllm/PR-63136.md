# [Bugfix][Core] Reserve only the blocks a spec decode step adds when admitting async KV loads

[Upstream PR](https://github.com/vllm-project/vllm/pull/63136) · state: open · merged: False

## Original PR description

## Purpose

With a KV connector doing async loads (P/D decode side, offloading) and spec decode enabled, a request whose remote-hit prompt needs exactly the free KV blocks is never admitted: the scheduler reserves a flat extra block for its first spec step even when that step fits in the block the request already has. The request spins at the head of `waiting` forever with no error. Follow-up to #57104 / #59880, found while testing the scheduler (not a production incident).

### Example

- block_size 32, 4 usable blocks, `num_speculative_tokens=1`, max_model_len 128
- 1 request A: 126-token prompt, full remote hit (needs 4 blocks); nothing else running

#### Step 1 — A arrives

`allocate_slots(A, num_new_tokens=126, ..., reserved_blocks=0 inflight + 1 spec margin)`
- A needs `cdiv(126, 32) = 4` blocks
- free = 4, minus 1 reserved = 3 < 4 → `allocate_slots` returns None → `break`

- result:
```
waiting = [A]
A.status = WAITING   (never reaches WAITING_FOR_REMOTE_KVS)
```

#### Step 2 onward — Same cycle

Nothing is running, so no block is ever freed. Peek `waiting` → A → same allocation → fails → `break`. Spin forever, and every request behind A waits too (FCFS).

But A did not need the extra block: after the load, its spec step grows it from 126 to 128 tokens, which is still 4 blocks (2 free slots in the last block). The same happens for any prompt already at `max_model_len` (`allocate_slots` caps the slots, so the step adds nothing).

## Root Cause

#57104 fixed the opposite mismatch (reserve too little → promoted request can't get its spec block). It did so with a flat margin precomputed in `Scheduler.__init__`: `cdiv(1 + num_spec + lookahead, block_size)` per non-Mamba group, i.e. 1 block for any `num_spec < block_size`, charged against every async load regardless of where the request's sequence ends.

Whether the spec step needs a new block depends on the request: `cdiv(min(n + 1 + spec + lookahead, max_model_len), bs) - cdiv(n, bs)` is 1 when the step crosses a block boundary (the #57104 case) and 0 when it doesn't. This PR computes that per request (`_spec_decode_step_blocks`) instead of using the flat 1, so the #57104/#59880 cases still reserve the block and the fitting case is admitted. `_request_remaining_blocks` uses the same `max_model_len` cap.

Not the same as "blocks exactly match max_model_len": the trigger is prompt length relative to the block boundary (e.g. 126 of 128 slots) or being at `max_model_len`; either way the request needs exactly the free blocks.

```python
from unittest.mock import patch
from tests.v1.kv_connector.unit.utils import create_vllm_config, create_scheduler, create_request

cfg = create_vllm_config(block_size=16, num_speculative_tokens=1)
sched = create_scheduler(cfg, num_blocks=4)  # 3 usable blocks
req = create_request(request_id=1, num_tokens=40, do_remote_prefill=True, max_tokens=1)
sched.add_request(req)
with patch.object(sched.connector, "get_num_new_matched_tokens", return_value=(40, True)):
    for _ in range(3):
        sched.schedule()
print(req.status)  # main: RequestStatus.WAITING forever; fixed: WAITING_FOR_REMOTE_KVS
```

Tradeoff: for sliding-window groups `get_num_blocks_to_allocate` may cap the real reservation below `cdiv(num_tokens, block_size)`, so the per-request margin can still over-reserve by one block there; same conservative direction as before, never under-reserves.

Not duplicating open work: #61845 fixes a different livelock (`_mamba_block_aligned_split` vs `_reserve_prefill_lookahead`, Mamba align + MTP L≥2); #62979 is the HiSparse host-page analogue and does not change the GPU-pool margin.
