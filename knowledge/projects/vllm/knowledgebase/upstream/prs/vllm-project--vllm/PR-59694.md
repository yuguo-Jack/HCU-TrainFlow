# [Bugfix][Rust Frontend] Use server-reported prompt_tokens in vllm-bench

[Upstream PR](https://github.com/vllm-project/vllm/pull/59694) · state: closed · merged: True

## Original PR description

## Purpose

Fixes #59576. Port #38654 to the Rust `vllm-bench`.

Python `vllm bench serve` takes each request's input length from the server's `usage.prompt_tokens`. The Rust bench still used the client-side estimate:

- `ChunkUsage` only deserialized `completion_tokens`, so the `openai` and `openai-chat` backends dropped `prompt_tokens`; `ResponsesUsage` likewise dropped `input_tokens` in `openai-responses`.
- `calculate_metrics` and the steady-state window summed `input_requests[i].prompt_len` (the client estimate) instead of `outputs[i].prompt_len`.

As a result, Total input tokens and input/total token throughput were under-reported whenever the server counted more tokens than the client estimate: chat-template tokens and, most visibly, multimodal tokens in `random-mm` / VLM benchmarks. Rust and Python results for the same server didn't match.

This PR:
- adds `prompt_tokens` to `ChunkUsage` and a `ChunkUsage::apply` helper that both streaming backends (`openai`, `openai-chat`) call, so the usage rule lives in one place;
- reads `usage.input_tokens` from the `response.completed` / `response.incomplete` event in `openai-responses`, as Python's `async_request_openai_responses` does;
- sums `output.prompt_len` in `calculate_metrics` and the steady-state window, as Python's `serve.py` does, and removes the now-unused `input_requests` parameter from both, together with the `Vec<SampleRequest>`s that `calculate_multi_turn_metrics` built only to pass it in;
- renames the dry-run line to "Estimated total input tokens", since it still sums the client estimate and will no longer match real runs (most visibly for multimodal);
- updates the stale `steady_state::compute` and `calculate_embedding_metrics` docs.

If the server omits the count, or reports `0` (some OpenAI-compatible servers send placeholder zeros in usage chunks), `output.prompt_len` keeps the client-side estimate it is initialized with.

### Behavior change: multi-turn

Multi-turn total and per-turn input now come from each turn's server-reported `prompt_tokens`, which include chat-template and image tokens, so they are higher than before for chat and multimodal datasets. #51109 (merged) already switched these totals to `request_output.prompt_len`; this PR makes that value the server count. The `max_model_len` pre-filter in `multi_turn.rs` still uses the client estimate, since it runs before any request is sent.

## Not a duplicate

I checked open PRs that touch `rust/src/bench/src/backends/` or `rust/src/bench/src/metrics/`:

- #55809 adds server queue time / TTFT to the detailed results. Different change; it touches the same backend files, so a textual conflict is possible but no overlap in behavior.
- #51109 (multi-turn input-token accounting) is merged; this branch is synced with `main` and keeps its multi-turn test.
- #60177 rewrites the chat SSE test helper; the new completions test uses its own small helper to avoid touching that.

## Test Plan

New tests:
- `openai_chat::tests::test_usage_prompt_tokens_override_prompt_len`: the server reports `prompt_tokens = 128` against a client estimate of 100, so `output.prompt_len == 128`.
- `openai_chat::tests::test_missing_prompt_tokens_keeps_client_prompt_len`: the server omits `prompt_tokens`, so `output.prompt_len` stays 100 and `output_tokens` is still 3.
- `openai_completions::tests::test_usage_prompt_tokens_override_prompt_len`: same as the chat test, for `/v1/completions`.
- `openai_responses::tests::test_terminal_usage_input_tokens_override_prompt_len`: `input_tokens = 128` in `response.completed` sets `prompt_len == 128`.
- `backends::tests::chunk_usage_ignores_zero_prompt_tokens`: `prompt_tokens = 0` keeps the client estimate.
- `calculator::tests::test_total_input_uses_output_prompt_len`: outputs reporting 128 give `total_input == 256`.

Multi-turn is covered by `calculator::tests::test_multi_turn_metrics_use_request_prompt_lengths` from #51109. In the steady-state tests, outputs are now the only source of input lengths (`mk_full` sets `prompt_len: 10`, and `compute_constant_concurrency_matches_full_run` checks `input_throughput`).

Commands:
```bash
cargo test -p vllm-bench --lib
cargo clippy -p vllm-bench --all-targets --locked -- -D warnings
cargo fmt --all -- --check
```

End-to-end: a mock OpenAI-compatible server that reports `usage.prompt_tokens = 128` for every request, `--dataset-name random --random-input-len 100 --random-output-len 8 --num-prompts 32 --max-concurrency 8`, run against both the `openai-chat` (`/v1/chat/completions`) and `openai` (`/v1/completions`) backends, compared with Python `vllm bench serve`.

Thanks for the fix, and for the before/after numbers against Python. Using `usage.prompt_tokens` is the right call. I merged this onto current `main`: no conflicts, `cargo test -p vllm-bench` passes (195), and clippy `-D warnings` and fmt are clean. A few things before it lands:

1. **The `openai-responses` backend also needs the server count.** #59489 merged on 10-20. In `openai_responses.rs`, `ResponsesUsage` only reads `output_tokens`, so that backend keeps the client estimate in `prompt_len`. After this PR, chat and completions would report server counts while responses reports client estimates. Please read `usage.input_tokens` from the `response.completed` / `response.incomplete` event into `prompt_len` (Python does this in `async_request_openai_responses`), and add a test for it.

2. **Remove `input_requests` instead of renaming it to `_input_requests`.** Please remove it from `calculate_metrics`, `steady_state::compute` and their callers. That also removes the `Vec<SampleRequest>` that `calculate_multi_turn_metrics` builds for the overall metrics and again for each turn, only to pass it in. One catch: once those are gone, nothing reads `TurnOutput.cumulative_input_tokens`, and `clippy -D warnings` fails with `dead-code`. Please either drop the field or keep it with a reason.

3. **Multi-turn input counts change, but the PR description doesn't say so.** Total and per-turn input switch from `cumulative_input_tokens` to the server's `prompt_tokens`, which include chat-template and image tokens. Meanwhile, the `max_model_len` filter in `multi_turn.rs` still uses the client estimate. I think the change is right, but please call it out in the description and add a multi-turn test. It also overlaps with #51109, so please coordinate with @reidliu41 on which one lands first.

4. **Tests:**
   - Please add a completions-backend test like `test_usage_prompt_tokens_override_prompt_len`.
   - The steady-state test fixtures build `requests` from `o.prompt_len`, so request lengths always equal output lengths and the tests can't tell which one is used. Please make them differ in at least one test.

5. **Stale docs and output:**
   - The `steady_state::compute` doc still says the request list is used "for input-token attribution".
   - The `calculate_embedding_metrics` doc still lists `output.prompt_len` vs `input_requests[i].prompt_len` as a difference from `calculate_metrics`.
   - The dry-run "Total input tokens" (`benchmark.rs`) still sums the client estimate, so it will no longer match real runs, most visibly for multimodal. Renaming it to "Estimated total input tokens" would make that clear.

6. **Optional:**
   - Only accept `prompt_tokens > 0`. vLLM never sends 0 here, but some OpenAI-compatible servers send placeholder zeros in usage chunks, which would quietly turn `total_input` into 0.
   - The usage block is now duplicated in chat and completions. A small `ChunkUsage::apply(&self, &mut RequestFuncOutput)` helper in `backends/mod.rs` would keep the two in sync.
