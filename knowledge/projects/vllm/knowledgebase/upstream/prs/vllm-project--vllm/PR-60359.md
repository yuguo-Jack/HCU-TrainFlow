# [Bugfix][Structured Output] Reject unsupported regex inside groups

[Upstream PR](https://github.com/vllm-project/vllm/pull/60359) · state: closed · merged: True

## Original PR description

## Overview

`validate_regex_is_buildable` only walked `BRANCH` and `MAX_REPEAT` nodes, so any
construct `outlines_core` cannot build was accepted as soon as it sat inside a group.
Fixes #60344.

## Claims

- `\b`, backreferences and look-arounds are now rejected wherever they appear, not
  only at the top level of the pattern.
- Lazy, possessive and atomic groups were leaking the same way and are covered too.
- Patterns that merely look like a word boundary (`[\b]`, `a\\b`) are still accepted.

## Validation

`_check_unsupported` recursed into two node types, so these three all passed
validation and then blew up in `StructuredOutputManager._create_grammar` with
`Failed to build DFA`:

```python
validate_regex_is_buildable(r"(a\b)")
validate_regex_is_buildable(r"((a)\2)")
validate_regex_is_buildable(r"(a(?=b))")
```

Two parametrized tests in `tests/v1/structured_output/test_validation.py` cover the
newly rejected patterns and the lookalikes that must stay accepted. Both are
pure-stdlib and run under the existing `cpu_test` marker:

```
pytest tests/v1/structured_output/test_validation.py -k regex -v
```

Before this change the ten rejection cases fail (nine of them are accepted when they
should not be; `a\b` alone was already caught) and the seven acceptance cases pass.
After it, all seventeen pass. `ruff format` and `ruff check` are clean on both files.

## Details

Rather than adding `SUBPATTERN` to the list of node types to recurse into, I made the
recursion structural: whatever the node, any `SubPattern` reachable in its value gets
walked. The enumeration is what went wrong in the first place, and `MIN_REPEAT`,
`POSSESSIVE_REPEAT` and `ATOMIC_GROUP` were missing for the same reason — `(?:a\b)*?`
and `(?>a\b)` were accepted as well. Listing those explicitly would also mean guarding
the constants, since they only exist on 3.11+. `BRANCH` keeps its own arm because its
sub-patterns live in a list rather than directly in the tuple.

The check stays on the parse tree, which is what keeps `[\b]` (a backspace literal in a
character class) and `a\\b` (an escaped backslash) out of the rejection: a text-level
scan for `\b` would reject both, and that would be worse than the bug.

I left `_prefix_needs_context` alone. It has the same narrow node handling, but an
unrecognised node there just means the walk keeps looking for an anchor, so it errs
toward rejecting rather than admitting a pattern that cannot be built.

Not a duplicate: no open PR mentions #60344 or this function.
