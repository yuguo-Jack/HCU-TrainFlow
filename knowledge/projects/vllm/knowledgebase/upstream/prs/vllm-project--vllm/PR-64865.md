# [Feature][Core] Reset prefix cache without preempting running requests

[Upstream PR](https://github.com/vllm-project/vllm/pull/64865) · state: open · merged: False

## Original PR description



## Overview

Adds `keep_running_requests` to `reset_prefix_cache` (Python API and `POST /reset_prefix_cache`), so the prefix cache can be cleared under load without preempting running requests. Fixes #64853.

## Claims

- `?keep_running_requests=true` / `reset_prefix_cache(keep_running_requests=True)` returns true while requests are running. They keep their blocks and progress, and new requests can't hit anything cached before the reset.
- Default and `reset_running_requests` behavior is unchanged.
- Setting both flags returns 400 from the endpoint (ValueError from the Python API).

## Validation

- With the change: `pytest tests/v1/core/test_scheduler.py tests/v1/core/test_async_scheduler.py tests/v1/core/test_prefix_caching.py tests/v1/core/prefix_cache tests/v1/simple_kv_offload/test_scheduler.py` gives 881 passed, 9 failed. The 9 are `test_diffusion_*`, which fail the same way on main on this machine (CPU model runner doesn't support diffusion models).
- pre-commit (ruff, mypy, typos, markdownlint) passes on the changed files.

Left to CI (needs GPU): `tests/v1/core/test_reset_prefix_cache_e2e.py` now also runs keep mode. It resets mid-run, checks outputs match the no-reset run, and checks a new request with the same long prompt gets `num_cached_tokens == 0`. I haven't run a live server with this change.

No model eval: the default path is unchanged and the new mode only changes what's in the prefix cache.

## Details

`BlockPool.reset_prefix_cache` refuses unless every block except the null block is free. Everything after that check already clears hashes on all blocks, in-use ones included, which is the same state `evict_blocks` leaves in-use blocks in after a KV load failure. So the flag just skips that check (`allow_used_blocks` at the pool/manager level).

Two places assumed in-use blocks always keep their hash:
- SimpleCPU offload store completion asserted the GPU block still had a hash. It now skips that block; refs are still released.
- `aux_output_connector.reset()` bumps the generation, and the worker asserts no output is in flight when that happens. Keep mode skips it; the existing rows stay valid since weights didn't change.

Semantics and limitations:
- Running requests keep caching blocks they fill after the reset, and those can be hit later. Not for use after weight updates; the docstrings and docs say so.
- Blocks held by WAITING_FOR_REMOTE_KVS requests and parked streaming sessions are handled the same way.
- KV events: `AllBlocksCleared`, then running requests may emit `BlockStored` with a parent hash that was cleared.
- HiSparse: running requests drop unpinned GPU pages and read them back from host.
- `reset_external` behaves as today; a connector reset can still fail with transfers in flight.
- The Rust frontend ignores the new query param for now (serde drops unknown fields), so it does a default reset. Happy to add it here or in a follow-up.
- Out-of-tree schedulers overriding `reset_prefix_cache` with the old two-arg signature need the new arg, same as when `reset_connector` was added.

Not a duplicate: no open PR references #64853 or `keep_running_requests`. #60764 and #60573 touch the same scheduler function for other reasons. I asked on the issue whether a third bool or a single mode param is preferred; no maintainer reply yet.

**<sub><sub>![P2 Badge](https://img.shields.io/badge/P2-yellow?style=flat)</sub></sub>  Prevent cleared partial prefixes from being cached again**

With hybrid fine-grained prefix caching, clearing pool hashes alone does not keep pre-reset entries invalidated: the next decode allocation calls `FullAttentionManager.cache_blocks()`, whose `_cache_partial_tail_block()` re-registers the existing prompt-tail hash. For example, in a group with 16-token blocks, 4-token hashes, and an 11-token prompt, the cached 8-token entry disappears at reset but becomes an 8-token per-group lookup hit again on the next decode iteration, without those prompt tokens being recomputed. Keep-running mode needs to suppress re-registration of pre-reset partial entries, while still allowing newly completed prefixes to be cached; otherwise the advertised invalidation does not hold.
