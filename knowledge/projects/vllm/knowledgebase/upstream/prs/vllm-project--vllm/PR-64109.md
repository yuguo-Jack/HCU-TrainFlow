# [Core][Spec Decode] Back only the tail of DFlash/DSpark sliding-window drafter KV

[Upstream PR](https://github.com/vllm-project/vllm/pull/64109) · state: open · merged: False

## Original PR description

## Purpose

A DFlash or DSpark drafter's sliding-window layers get a plain `SlidingWindowSpec`, so their KV is managed like a target SWA layer's:

- every prefill chunk allocates drafter blocks for the whole chunk;
- the per-request reservation (`max_admission_blocks_per_request`, which also sizes the startup check) grows with `max_num_batched_tokens`;
- a prefix hit at `h` needs the drafter's window before `h` cached.

None of that is needed for these drafters. Their context KV at a position is a projection of the target's hidden state at that position, and draft attention only runs past the last target token. So:

- an allocation whose target tokens end at `T` only needs drafter blocks from `T - tail_tokens` on. `T` counts drafts still in flight, which is what the margin over the window is for;
- once nothing is in flight (processed tokens, a request's first allocation, a hit lookup), the window is enough, as for plain sliding window;
- a hit at `h` for a request of `L` tokens only needs cached drafter blocks in `[L - sliding_window + 1, h)`. Lower blocks are never read, and the target prefill from `h` rewrites the drafter context KV for the rest.

Related: RFC #59117 reports the pool collapse a DFlash drafter causes on hybrid models. This PR addresses one of the effects it measures, the per-request drafter block demand. It does not change grouping or page padding, and needs no separate pool.

## Changes

- **`DFlashSlidingWindowSpec(SlidingWindowSpec)`** adds three fields: `num_speculative_tokens`, `max_in_flight_steps` and `num_lookahead_tokens`.
  - Its `tail_tokens` is `sliding_window + num_speculative_tokens * max_in_flight_steps`. An allocation's target-token end `T` counts the drafts of every step in flight; if all of them are rejected, the next draft step still reads only the window below the accepted tokens.
  - Lookahead slots sit above `T`, so they are covered by the allocation itself and by the admission cap, not by the tail.

  Its `max_admission_blocks_per_request` is the smaller of the sliding-window bound and the processed prefix's window plus one tail per in-flight step. The startup reservation and the admission gate therefore stop scaling with chunk size.
- **`DFlashSlidingWindowManager`**:
  - allocations leave the blocks below the tail null;
  - frees and first allocations (prefix hits, KV-connector loads) keep the plain sliding-window rule, `sliding_window - 1` tokens below the processed ones. They see no drafts in flight;
  - frees walk past the null runs between earlier tails;
  - `find_longest_cache_hit` takes `num_request_tokens` and requires cached blocks only in the window before the request end.
- **`HybridKVCacheCoordinator`** passes `num_request_tokens = max_cache_hit_length + 1` to DFlash groups. Underestimating it only asks for more cached blocks.
- **`get_global_kv_cache_groups`** gives the spec to a `dflash`/`dspark` drafter's own `SlidingWindowSpec` layers (`spec.is_draft`), only on Model Runner V2.
  - MRV2's DFlash/DSpark context-KV writer already maps positions whose block is null to `PAD_SLOT_ID`. The V1 kernel would write them into block 0, so the V1 runner keeps the plain spec.
  - Target SWA layers, full-attention draft layers and `SlidingWindowMLASpec` drafts are unchanged.
- **Promotion to full attention** (hybrid manager disabled, or page sizes that cannot be unified) drops the new fields.

There is no change for EAGLE/MTP drafters, and none when no drafter layer is sliding-window.

**KV connectors need no change.** A load is a first allocation, so the drafter group holds the same blocks as plain sliding window, and a connector that moves the window (NIXL, Mooncake, MoRIIO, offloading) fills every block it holds. A tail-sized load would instead leave the blocks below the window unfilled but cached, and sizing the exchange by each side's tail would make prefill and decode lists differ whenever their in-flight steps differ.

## Not a duplicate

I searched open PRs for DFlash/DSpark sliding window, drafter KV and #59117. Related, but not the same change:

- #60320 computes the windowed draft context only for trailing rows. Its gate requires that dropped rows cannot be served later (prefix caching off). With this spec, drafter blocks below the tail are never backed or cached, so the two are complementary.
- #61261 adds `draft_context_window` to bound draft attention for quality. It does not change KV allocation.
- #47926 masks prefix-restored tokens out of the draft context. Here a hit only uses drafter blocks that are cached, so they hold KV written by the request that cached them.
- #63795 covers sliding-window MLA draft layers, which this PR leaves as they are.

New tests:

- `test_dflash_window_backs_only_each_chunks_tail`: two 40-token chunks back only their trailing tails, and freeing reaches the earlier tail above a null run and keeps only the window of the processed tokens.
- `test_dflash_window_admission_cap_counts_in_flight_tails` and `test_dflash_window_admission_cap_covers_lookahead_slots`: the cap bounds the real holding, including the drafts' lookahead slots.
- `test_dflash_window_tail_covers_reads_after_rejected_drafts`: with one or two steps in flight, and every alignment of the tail start, a step whose drafts were all rejected still reads only backed blocks. It fails with `window + num_speculative_tokens` (two steps in flight) and with `window` alone.
- `test_dflash_window_hit_needs_only_the_window_before_request_end`: the hit rule, including a hit that does not need the tail's first block and a hit below the window that needs no drafter KV at all.
- `test_dflash_window_load_holds_only_the_window`: a KV-connector load holds the same blocks as plain sliding window.
- `test_dflash_drafter_hit_needs_cached_drafter_kv_only_in_its_window`: the hit rule end to end through `KVCacheManager`, with a full-attention target group.
- `test_dflash_drafter_sliding_window_layers_back_only_their_tail`: the spec applies only to a dflash/dspark drafter's own SWA layers, on MRV2.

  - **Setup:** `Qwen/Qwen3.8-27B` (BF16) with `RedHatAI/Qwen3.8-27B-speculator.dspark` (5 sliding-window layers, window 2048), `method: dspark`, K = 7, MRV2, prefix caching on, `--max-model-len 32768`.

  - **Tail:** measured on the first commit, where `tail_tokens` was `window + K + 128`. The current tail, `window + K × in-flight steps`, is shorter.
