# [KV offload] Add max_recompute_pending_tokens to skip waiting on short in-flight offloads

[Upstream PR](https://github.com/vllm-project/vllm/pull/57959) · state: open · merged: False

## Original PR description

## Purpose

When a KV offload lookup hits chunks whose GPU->CPU store is still in flight (`HIT_PENDING`), the scheduler always defers the request until the store completes, even if only a chunk or two are pending. Behind a backlog of serialized stores that wait can reach tens of seconds, which shows up as large `vllm:kv_offload_lookup_async_delay_seconds` observations. Recomputing a handful of tokens would have been far cheaper.

This PR adds a `kv_connector_extra_config` option, `max_recompute_pending_tokens`, that bounds the wait:

- If the run of chunks from the first pending chunk to the end of the hit would gain at most this many tokens (rounded down to whole chunks), the prefix lookup is cut before the first pending chunk. The request loads the ready prefix immediately and recomputes the rest.
- The partial-tail lookup applies the same budget.
- `RETRY` results still defer (the chunk's location is unknown), as do pending chunks inside a sliding-window group's required window.
- Negative values are rejected at spec construction.
- Default is `0`, which keeps the current always-wait behavior, so this is a no-op unless opted in.

The option is documented in `docs/features/kv_offloading_usage.md`.

### Not a duplicate

Searched open PRs for `HIT_PENDING offload recompute` and `max_recompute_pending_tokens`. The closest is #53087, which is complementary rather than overlapping: it adds a wall-clock deadline (`hit_pending_timeout_s`) inside `TieringOffloadingManager` for *stalled* primary-tier writes. This PR is a token-budget decision in the connector scheduler that applies to all offloading specs and avoids the wait up front when the pending run is small, rather than timing out after the fact.

- `_maximal_prefix_lookup` unit cases: short pending run is cut before the first pending chunk, a run one chunk over budget defers, a leading pending chunk within budget is a miss, and `RETRY` defers regardless of budget.

Got 2 points from Claude (have not verified):

1. Split RETRY out of pending in the partial-tail loop (scheduler.py:1032). Right now boundary_pending is set by both HIT_PENDING and RETRY, so any non-zero budget makes RETRY stop deferring — contradicting your own doc row. Keep two flags; gate only the pending one.

2. Gate on the highest awaitable pending boundary, not max_boundary (scheduler.py:1050). max_boundary - complete_boundary is the best case at the top candidate, but the pending boundary can be far lower, so the feature under-triggers exactly where it's meant to fire. Also skip boundaries that had a MISS in another group — those can never become hits, so deferring for them buys nothing.
