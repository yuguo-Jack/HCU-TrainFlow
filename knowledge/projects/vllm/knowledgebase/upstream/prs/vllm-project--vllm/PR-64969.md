# [ROCm][Perf] Run fp8 DCP cprr MLA verify at 96 native heads when AITER supports it

[Upstream PR](https://github.com/vllm-project/vllm/pull/64969) · state: open · merged: False

## Original PR description

Draft for early review. No blocking issues.

## Overview

DCP multi-token verify on ROCm AITER pads Kimi-K3's 96 gathered heads (TP8/DCP8) to 128 for the round-robin (cprr) decode. AITER's fp8 cprr kernel runs 96 heads natively for qlen <= 6 on gfx950. This PR asks AITER's shape planner (`get_mla_decode_shape_support`, AITER v0.1.27, as pinned in `docker/Dockerfile.rocm_base`) and skips the padding when it reports 96 native for every qlen the cprr route can take.

## Claims

- With fp8 KV, 96 DCP-gathered heads and AITER v0.1.27 on gfx950, the cprr verify plans, sizes its buffers and launches at 96 heads. Output and LSE are bit-identical to the 128-padded run on the 96 real heads.
- Padding is kept for AITER without the planner (v0.1.26 and older), bf16 KV, qlen > 6 and every other head count.
- `forward_mqa` per layer, 72 requests, qlen 5, on MI355X: -9.0% (ASM) and -12.1% (OPUS) at 128K context, -25% and -31% at 32K.

## Validation

- CPU unit tests: 38 passed; the 8 new tests fail on main. GPU numerics test: 6 passed. pre-commit clean.
- Native 96 and padded 128 give bit-identical output and LSE, ASM and OPUS.
- The end-to-end gain was measured together with OPUS and is not isolated.

<details><summary>Validation details and timings</summary>

Measured for this PR on one MI355X GPU, with the vLLM ROCm nightly `3966924d` image Python (torch 2.13.0+rocm10.0.0) and this branch's files overlaid on the image's `vllm` package:

- CPU, no GPU visible: `pytest tests/v1/attention/test_rocm_aiter_mla_dcp_cprr.py`, 38 passed; on main the 8 new tests fail (the builder test with `assert 128 == 96`). `test_rocm_aiter_mla_mtp_split.py` and `test_rocm_aiter_mla_head_padding.py` give the same result before and after. pre-commit clean.
- GPU: `pytest tests/v1/attention/test_rocm_aiter_mla_dcp_cprr_numerics.py` (real builder and kernel), 6 passed. The image's AITER v0.1.26 has no planner query, so `k3-96` runs padded there. Both files run in `:amd: (MI355 DPX) V1 Attention`, where the pinned AITER v0.1.27 should take `k3-96` down the native path.
- Planner query on real AITER v0.1.27 (gfx950): fp8 96 heads native at qlen 1-6 (ASM kernel `mla_a8w8_qh32_qseqlen4_gqaratio32_lse_cprr_ps`; OPUS `supported=None`), folded from qlen 7. The PR's function returns True at qlen 5 and 6 with and without OPUS, False at qlen 7, for bf16 and for other counts. On v0.1.26 it returns False.
- Native 96 vs padded 128 through `AiterMLAMetadataBuilder` and `forward_mqa` (AITER v0.1.26, native forced): bit-identical output and LSE on all 8 DCP ranks at 256 context and on rank 0 at 32K and 128K, ASM and OPUS. Both stay within the numerics test's fp32-reference bounds.
- The same decode called directly on AITER v0.1.26 and v0.1.27, every DCP rank against an fp32 causal reference, global lengths 261 and 4101: max relative error 0.014-0.030 for 96 and 128 heads, ASM and OPUS; 96 bit-identical to 128.

Earlier measurements, not re-run: kernel-only microbenchmark at 128K, ASM 1090 -> 1036 us/layer and OPUS 822 -> 783. In a decode-only server with 72 requests (native 96 + OPUS vs base), query copies fell from 3.0 to 1.2 ms/step, and step time dropped 8.7 ms at 128K and 10.5 ms at 160K.

<details><summary>End-to-end benchmark</summary>

Kimi-K3 1P1D on 2 nodes of 8x MI355X: TP8 + DCP8 per role, FP8 KV cache, DSpark speculative decoding with 4 draft tokens, Mooncake RDMA. vLLM ROCm nightly `3966924d` (AITER v0.1.26) with native 96 applied as a runtime patch, plus `AITER_MLA_USE_OPUS=1`.

| Concurrency | Base tok/s/GPU | Native 96 + OPUS tok/s/GPU | Change |
|---|---|---|---|
| 48 | 12,546.5 | 13,076.3 | +4.2% |
| 72 | 14,836 | 15,909 | +7.2% |

GSM8K with native 96 + OPUS: 0.958-0.965.

The native-96 share was not isolated: both columns differ by native 96 and by OPUS, which is only an AITER env var. On this image's AITER v0.1.26 the PR itself keeps padding, because the planner query is missing. Not re-run on main or AITER v0.1.27.

</details>

<details><summary>Notes</summary>

- Only fp8 at 96 heads is probed, since it is the only shape measured. 128 is already native and fp8 48, 80 and 112 fold in AITER. The planner also reports bf16 native, which was not measured, so bf16 keeps its current path.
- The planner is asked once per metadata builder, for qlen `_MIN_CPRR_QLEN` through the builder's max decode qlen. AITER caches the answers.
- Not run: bf16 KV, qlen > 6, gfx942 (the cprr route is gfx950-only), end to end on main.
- The query runs at builder init, so there is no new host sync in the decode step.

Not a duplicate: #59966 speeds up the 96 -> 128 query pad this skips, and #54899 uses the same AITER query for the plain decode route; neither changes the cprr head count. AI assistance (Claude in Cursor) was used to write the change, the tests and this description.

</details>
