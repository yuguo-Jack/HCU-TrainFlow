# [Bugfix] Roll back failed file-plugin imports

[Upstream PR](https://github.com/vllm-project/vllm/pull/61075) · state: open · merged: False

## Original PR description

## Overview

Roll back the module cache when a file plugin fails to load, so a later import cannot reuse a partially initialized module. Preserve any module-cache entry replaced by the failed import.

## Claims

- Failed file imports remove a newly registered partial module or restore the original cached object, including a blocked (`None`) entry.
- Ordinary failures and interruptions re-raise their original exception after cleanup. Successful plugin loading retains its current behavior.

## Validation

The same CPU pytest command produced **5 failed, 8 passed, 1 deselected** against the original helper and **13 passed, 1 deselected** with the fix. The five behavioral cases cover failed-plugin reuse and restoration of a module or `None` after `RuntimeError` or `KeyboardInterrupt`, using real temporary Python files and ordinary package initialization:

```bash
pytest tests/utils_/test_import_utils.py --confcutdir=tests/utils_ -q -p no:cacheprovider -k "not placeholder"
```

The pre-existing placeholder test depends on installed vLLM distribution metadata, which this source-only CPU environment lacks, so it was excluded. Existing plugin loading and module-discovery checks and all new rollback cases executed. No model, GPU, or hosted CI execution is claimed.

The existing Buildkite `async-engine-inputs-utils-worker` lane runs `pytest -v -s utils_` and includes both `vllm/utils/` and `tests/utils_` as source dependencies. These cases extend its existing test file.

The full normal `pre-commit run --files vllm/utils/import_utils.py tests/utils_/test_import_utils.py` command passed, including mypy and test tethering; `git diff --check` passed.

## Details

`import_from_path()` registers its new module before executing the file. An exception leaves that partial module behind; `import_plugin()` can then treat it as successfully loaded on a later attempt. Save the prior cache state, restore it on `BaseException`, and re-raise. This only rolls back the module-cache entry; arbitrary plugin side effects are outside its scope.

Searches for `import_from_path`, failed plugin imports and partial-module imports found no matching open repair. The actual diff of #52026 changes parser-plugin logging namespaces, while this fix changes failure cleanup in the shared importer. Merged #45241 added the site-packages plugin path; its diff does not repair the module cache.

All 5,055 Python/stub blobs at base `1789f095` were scanned. The shared wrapper is the only production caller of `import_from_path()`; both reasoning and tool parser managers call that wrapper and keep their successful behavior. A later default-branch comparison inspected four changed Python blobs and found no added or changed importer references. This runs during plugin loading, outside model execution; no serving performance or model-output improvement is claimed.

AI assistance was used in investigation, implementation and testing. The submitting human reviewed every changed line, personally ran the scoped utility tests, and confirmed DCO 1.1 for this exact patch.
