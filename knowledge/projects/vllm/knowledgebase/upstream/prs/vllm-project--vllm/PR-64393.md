# [Bugfix][KV Offload] SimpleCPUOffload: remove the disk tier's file on graceful shutdown

[Upstream PR](https://github.com/vllm-project/vllm/pull/64393) · state: open · merged: False

## Original PR description

## Purpose

`SimpleCPUOffloadConnector` does not override `shutdown()`, and `SimpleCPUOffloadWorker` has no `shutdown()`, so `DiskBackend.shutdown()` never runs outside unit tests. Each worker's slot file, `<disk_path>.rank_<N>`, outlives every exit. It holds prompt-derived KV (mode `0600`) and is only removed when the next start on that node reuses the path. `docs/usage/metrics.md` already describes the file as "unlinked at startup and shutdown".

This PR wires the shutdown through and makes it safe to call on the teardown path:

- `SimpleCPUOffloadConnector.shutdown()` calls `SimpleCPUOffloadWorker.shutdown()`, which shuts down the `DiskBackend`. The scheduler role opens no files, and the CPU backend is unchanged.
- `DiskBackend.shutdown()`:
  - **Unlinks first**, before waiting for the IO threads, so a kill during the wait still leaves no file.
  - **Removes only its own file.** `init()` records the `(st_dev, st_ino)` of the file it created; shutdown unlinks `disk_path` only if it still refers to that inode. A file another process has since created at the same path (e.g. the next start) is left alone.
  - **Drops queued transfers** and stops between blocks of a running one. It still waits for the DMAs it already issued, so no copy into a staging buffer is in flight when its thread exits.
  - **Bounds the wait:** one 2 s budget for both IO threads (previously up to 10 s each).
  - **Then releases resources:** once both threads have exited, it closes the fd and unregisters the pinned staging buffers (`cudaHostUnregister`, new `unpin_tensor()`). If a thread is still alive, the fd and buffers are kept, with one warning.
  - Idempotent, a no-op before `init()`, and never raises.

**Why the unregister is part of this PR.** With `shutdown()` actually called, the IO threads exit and the backend can be garbage-collected. A staging buffer freed while still registered can come back from the allocator. The next `cudaHostRegister` on that range then fails with `cudaErrorHostMemoryAlreadyRegistered`, e.g. for a second `LLM` with the disk backend in the same process.

Docs: a short "Disk files of `SimpleCPUOffloadConnector`" section in `docs/features/kv_offloading_usage.md`.

Not covered: `SIGKILL`, OOM kills, node failure, or any exit that skips Python cleanup. Those still leave the file until the next start on that node replaces it (documented).

- `test_shutdown_removes_disk_file_and_is_idempotent`: `connector.shutdown()` removes `rank_0`, leaves `rank_1` alone, closes the fd and stops both IO threads; a second call leaves a new file at the path alone.
- `test_shutdown_keeps_a_file_another_process_put_at_the_same_path`: the inode guard.
- `test_shutdown_drops_queued_transfers`: with the store thread busy and 3 stores queued, none of the queued ones run.
- `test_shutdown_unregisters_staging_buffers_exactly_once`: both buffers are unregistered once and then freed (weakrefs).
- `test_shutdown_keeps_staging_buffers_registered_while_an_io_thread_runs`: past the join budget, nothing is unregistered, the fd stays open and the file is still removed.
