# [Bugfix][Rust Frontend] Accept empty message content like the Python frontend

[Upstream PR](https://github.com/vllm-project/vllm/pull/64471) · state: closed · merged: True

## Original PR description

## Overview

The Rust frontend rejects empty user message content on `/v1/chat/completions/render` and `/tokenize` with `400 BadRequestError: message content cannot be empty`, while the Python frontend renders it as a normal (empty) turn. This PR drops the Rust-only content check so both frontends accept the same requests.

Fixes #64433 (second bug, see #62741 below for the first one).

## Claims

- `POST /v1/chat/completions/render` accepts `{"role": "user", "content": ""}` and `{"role": "user", "content": []}` and returns `200` with non-empty `token_ids`.
- `POST /tokenize` accepts the same two payloads and returns `200` with non-empty `tokens`.
- `messages: []` is still rejected with `400` (`messages cannot be empty`); only the content check is removed.
- Rust/Python parity for chat-message validation is restored: the removed check was Rust-only and never existed in the Python frontend.

## Details

**Root cause.** `validate_messages()` in `rust/src/server/src/routes/openai/utils/types.rs` is shared by the chat-completions render path and the `/tokenize` chat form. It was introduced in #44222 together with `/tokenize` and added a `user`-message content check (`Text("")` / `Parts([])` → 400) that has no counterpart in the Python frontend (`vllm/renderers/`), which accepts empty content and renders an empty turn. Empty content is legal in the OpenAI schema, so the Rust frontend was stricter than both Python and the API spec.

**Design.** Minimal fix: delete the content loop, keep the `messages` non-empty check (both frontends still require at least one message). Net −8 lines in production code (low complexity, no new abstractions, no behaviour change outside these two routes); the only two call sites are `routes/openai/chat_completions/types.rs` and `routes/openai/tokenize/types.rs`.

**Tests.** `tokenize_chat_empty_message_content_returns_400` asserted the old (incorrect) behaviour and is replaced by `tokenize_chat_accepts_empty_message_content`; a new `render_chat_accepts_empty_message_content` covers the render route. Both assert `200` plus a non-empty token list for `""` and `[]`, so a regression that silently produces an empty prompt is also caught.

**Tradeoffs / limitations.** Empty turns are now tokenized (a few template control tokens) instead of rejected — same cost profile as Python. Validation was done at the route level; no local GPU/Python environment was available to run a side-by-side end-to-end comparison against the Python frontend, so the parity claim is based on the Python renderer's code path (no empty-content rejection there) rather than a live diff of responses.
