# [Bugfix] Apply DCP slot-mapping localization only to context-parallel KV cache groups

[Upstream PR](https://github.com/vllm-project/vllm/pull/57260) · state: closed · merged: False

## Original PR description

## Purpose

`_compute_slot_mappings_kernel` (`vllm/v1/worker/gpu/block_table.py`) applies the decode-context-parallel (DCP) owner/local transform to **every** KV cache group whenever `CP_SIZE > 1`. Before this PR the CP branch was unconditional:

```python
virtual_block_size = kv_block_size * CP_SIZE
virtual_block_indices = positions // virtual_block_size
virtual_block_offsets = positions % virtual_block_size
is_local = virtual_block_offsets // CP_INTERLEAVE % CP_SIZE == cp_rank
...
local_positions = virtual_block_indices * kv_block_size + local_offsets
```

Only full-attention and MLA KV is actually sharded across DCP ranks. Groups holding **replicated** per-rank state index *global* positions on every rank:

* Mamba/GDN recurrent state (`MambaSpec`),
* sliding window and chunked local (`SlidingWindowSpec`, `ChunkedLocalAttentionSpec`),
* the `KpoolTailSpec` scratch group (`vllm/v1/kv_cache_interface.py:970`, a `SlidingWindowSpec` subclass with block size 4).

For those groups the transform is wrong twice over: `is_local` PADs out `(cp_size - 1) / cp_size` of their tokens, and the tokens that survive are rewritten to `virtual_block_indices * kv_block_size + local_offsets`, i.e. the wrong slot. It fails silently — no assert, no shape error, just corrupted state.

The rest of the stack already knows which groups are sharded: `dcp_world_size_for_kv_cache_spec(spec, dcp_world_size)` (`vllm/v1/core/kv_cache_utils.py:709`) returns the process DCP size for `FullAttentionSpec`/`MLAAttentionSpec` and `1` for everything else, and `KVCacheCoordinator` (`vllm/v1/core/kv_cache_coordinator.py:143`) and the offload manager (`vllm/v1/simple_kv_offload/manager.py:304`) already route through it. The slot-mapping kernel was the one place that did not.

**The fix**

* `BlockTables.__init__` takes a per-group `cp_enabled: list[bool] | None` (`vllm/v1/worker/gpu/block_table.py:30`), stored and uploaded next to the existing `slot_mapping_enabled` (`:55`, `:123`) and passed to the kernel (`:229`).
* The kernel loads `group_cp` (`vllm/v1/worker/gpu/block_table.py:349`) and gates the CP branch on it: a non-CP group owns every token (`is_local |= group_cp == 0`, `:353`) and keeps its global positions (`local_positions = tl.where(group_cp, ..., positions)`, `:359`).
* `GPUModelRunner.initialize_kv_cache` derives the list per group from `dcp_world_size_for_kv_cache_spec(spec, self.parallel_config.decode_context_parallel_size) > 1` (`vllm/v1/worker/gpu/model_runner.py:605`) and passes it to `BlockTables` (`:675`).

`cp_enabled` defaults to all-`True`, so `CP_SIZE == 1` and every existing caller behave exactly as before; the only behaviour change is for a non-full-attention group under DCP > 1.

**Scope.** This is not a theoretical case: any Mamba+attention hybrid running `--decode-context-parallel-size > 1` has a replicated Mamba group alongside sharded attention. DeepSeek-V3.2 never tripped it because it has neither a Mamba group nor a kpool tail group. The change is hardware-agnostic — Python config plumbing plus a predicate in an existing Triton kernel, no new kernel and no device-specific code.

**Provenance.** Found while designing decode-context-parallel support for GLM-5.3-Flash's pooled DSA indexer on 4x NVIDIA CMP 170HX (GA100, sm_80) with an out-of-tree Ampere sparse-attention backend. Neither that model's DCP support nor that backend is part of this PR — the pooled indexer still rejects DCP upstream, so this PR does **not** enable DCP for it. The fix is preventive there and a live correctness fix for the hybrid models that do run DCP today.

## Test Plan

New unit tests, in the style of the files they join:

* `tests/v1/worker/test_gpu_block_table.py`
  * `test_slot_mappings_localize_only_context_parallel_groups[cp_rank=0..3]` — two groups under `cp_size=4`, one `cp_enabled=True` (block size 16) and one `cp_enabled=False` (block size 4). The sharded group must match the localized reference; the replicated group must get global positions with **no** `PAD_SLOT_ID`.
  * `test_slot_mappings_localize_every_group_by_default` — omitting `cp_enabled` yields `[True]` and the old localized mapping, pinning the no-op default.

Two things from this PR that may still be useful there:

2. One thing worth confirming on #56723's default: with `AttentionSpec.dcp_sharded = True` and the override coming from `impl.dcp_world_size`, `SlidingWindowSpec` / `ChunkedLocalAttentionSpec` groups stay marked sharded unless their backend reports `dcp_world_size == 1`.
