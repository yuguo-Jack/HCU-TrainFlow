# [Bugfix][DSv4.1] Seed the -1 sentinel in the prefill sparse index workspace

[Upstream PR](https://github.com/vllm-project/vllm/pull/60613) · state: closed · merged: True

## Original PR description



## Overview

Port #55299 to the DeepSeek-V4.1 copy of `combine_topk_swa_indices`: seed a caller-provided `out=` buffer with the `-1` sentinel before the kernel writes each row's valid prefix. Without it, DeepSeek-V4.1-Flash prefill through FlashMLA mega attention reads stale indices and produces NaN; in our deployment this surfaced as an intermittent illegal memory access.

## Claims

- Fixes NaN attention outputs in DSv4.1 FlashMLA mega-attention prefill for rows whose combined index list is shorter than the padded width: the first 127 tokens of a fresh prompt, the rows right after an SWA bounded-replay start, and compressed-layer rows that have fewer than `index_topk` candidates.
- The NaN spreads through the KV cache into later tokens and layers, including the indexer, where `top_k_per_row_prefill` turns NaN logits into out-of-range indices (#49896). In our downstream build, which also runs the decoder replay tail as one FULL CUDA graph (not in `main`), those indices reached `_compute_global_topk_indices_and_lens_kernel` and crashed with an illegal memory access; this fix removes that crash there.
- One line, identical to the #55299 fix in `deepseek_v4`.

## Validation

GB200, DeepSeek-V4.1-Flash, FlashMLA mega attention, MXFP4 indexer cache, breakable CUDA graphs (`FULL_AND_PIECEWISE`). The kernel repro was run twice: with our vLLM 0.30-based build, and with `main`'s `cache_utils.py` (e161a0798c) loaded over it, with identical results. `main`'s combine kernel additionally masks invalid top-k candidates, but like ours it never writes `[combined_len, width)`. The E2E run used the downstream build.

|---|---|---|
| Kernel repro (below), `main`'s `combine_topk_swa_indices` + `fused_norm_rope_attn_rope_cast_fwd`, `out=` pre-filled with in-range indices of NaN KV rows; NaN output rows | 96/300 (SWA-only, width 128), 768/1200 (ratio 2, width 640), 352/700 (ratio 1, width 640) | 0 / 0 / 0, no stale tail entry |
| Same kernel, tail entries set to `-1`, out of range, or pointing at finite rows | output bit-identical in all three | n/a |

No test is added, as in #55299: CI has no GB200 runner exercising DSv4.1 FlashMLA mega attention, so the validation above was done outside CI.

In the downstream build, a GPU core dump of the crash places it in `_compute_global_topk_indices_and_lens_kernel` (block-table load) in the replay-tail FULL graph, and per-row NaN probes show the first real-row NaN at the layer-1 input (layer 0 is pure SWA). No accuracy eval was run: rows that never hit a stale tail are unchanged (second row of the table), and the change only restores the sentinel the kernel contract already assumes.

import vllm.v1.attention.ops.flashmla  # noqa: F401  registers _flashmla_C
from vllm.models.deepseek_v41.common.ops import combine_topk_swa_indices
from vllm.models.deepseek_v41.common.ops.fused_layout import WV_GROUP_SIZE
from vllm.models.deepseek_v41.nvidia.flash_mla_mega_attn import (
    _HEAD_DIM_V, _ROPE_ARGS, _SF_ARGS, alloc_mega_attn_output,
)

H, D, W, TOPK = 64, 512, 128, 512
dev = "cuda"
g = torch.Generator(device=dev).manual_seed(0)


def case(n, top_k, ratio, comp_rows):
    m = comp_rows + n + 2048  # kv rows: compressed | swa | never written
    kv = (torch.randn(m, 1, D, device=dev, generator=g) * 0.5).bfloat16()
    kv[comp_rows + n :] = float("nan")
    q = (torch.randn(n, H, D, device=dev, generator=g) * 0.5).bfloat16()
    pos = torch.arange(n, dtype=torch.int32, device=dev)
    col = torch.arange(TOPK, device=dev)[None, :]
    topk = torch.where(col < ((pos + 1) // max(ratio, 1))[:, None], col, -1).int()
    width = (top_k + W + 127) // 128 * 128
    # A workspace slice holding stale in-range indices from an earlier call.
    idx_ws = (comp_rows + n + torch.arange(width, device=dev)).repeat(n, 1).int()
    lens_ws = torch.empty(n, dtype=torch.int32, device=dev)
    qsl = torch.tensor([0, n], dtype=torch.int32, device=dev)
    seq = torch.tensor([n], dtype=torch.int32, device=dev)
    idx, lens = combine_topk_swa_indices(
        topk, qsl, seq, seq, W, ratio, top_k, m, comp_rows, out=(idx_ws, lens_ws)
    )
    out = alloc_mega_attn_output(n, H // WV_GROUP_SIZE, torch.device(dev))
    torch.ops._flashmla_C.fused_norm_rope_attn_rope_cast_fwd(
        q, kv, idx.unsqueeze(1), D**-0.5, _HEAD_DIM_V, torch.zeros(H, device=dev),
        lens, False, 0.0, pos, *_ROPE_ARGS,
        torch.randn(65536, 64, device=dev, generator=g), H // WV_GROUP_SIZE,
        *_SF_ARGS, out.data, out.scale,
    )
    nan = ((out.data.view(torch.uint8) & 0x7F) == 0x7F).flatten(1).any(1)
    print(f"ratio={ratio} width={width} nan_rows={int(nan.sum())}/{n}")


case(300, 0, 0, 0)      # SWA-only layer
case(1200, TOPK, 2, 1024)
case(700, TOPK, 1, 1024)

## Details

`combine_topk_swa_indices` writes `[0, combined_len)` of each row and relies on the rest being `-1`, which `topk_length` pairs with. The `out=None` branch gets that from `torch.full(-1)`; the `out=` branch does not seed it. Both NVIDIA callers pass a workspace slice (`flash_mla_mega_attn.py` prefill, `flashmla.py`), so the tail holds whatever an earlier user of the arena left there.

The FlashMLA prefill kernel processes the index list in whole `B_TOPK` tiles (the reason for the 128 alignment) and still loads the KV rows of a tile's entries past `topk_length`, masking them to p = 0. A stale in-range index that lands on a `kv_ws` row this call did not write brings in arbitrary bytes, and 0 * NaN = NaN, so the masked entry still poisons the output row. Rows with a short window are the ones with a tail: at layer 0 (width 128) a fresh prompt's positions 0-126; in compressed layers (width 640) every row with fewer than 512 top-k candidates or a window shorter than 128 (for example right after an SWA bounded-replay start).

#55299 fixed exactly this in `deepseek_v4/common/ops/cache_utils.py`. The `deepseek_v41` package was added afterwards by #56228 from an older copy of that file: its `combine_topk_swa_indices` matched the pre-#55299 V4 version line for line when it was added, and has never had the line.

Cost: one memset of `rows x width` int32 per call (about 20 MiB for an 8K-token chunk at width 640). Writing the tail inside the Triton kernel would avoid it, but would duplicate the padded-width formula in the kernel and diverge from the V4 fix; this keeps the fix the same in both packages.

Not a duplicate: open PRs touching `combine_topk_swa_indices` are ROCm-only (#60091, #56638). #59131 reworks the same prefill path but still passes the workspace as `out=`, so it depends on this fix as well.
