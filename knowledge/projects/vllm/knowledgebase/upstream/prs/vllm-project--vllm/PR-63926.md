# [Bugfix][Rust Frontend] Match Python logprob token strings and name the SSE charset

[Upstream PR](https://github.com/vllm-project/vllm/pull/63926) · state: open · merged: False

## Overview

Fixes items 2 and 3 of #63917 (Rust frontend parity with the Python frontend):

- Logprob token strings match the Python frontend: special tokens keep their text, and candidates that are part of a multi-byte character split across byte-fallback tokens are repaired with the preceding tokens (or reported as `""`) instead of showing `�`. Completions `text_offset` follows and indexes into the returned text again.
- Streamed responses send `Content-Type: text/event-stream; charset=utf-8`.

Items 1, 4 and 5 of the issue are left out: they need a call on whether the difference is intended.

## Claims

- When detokenization is enabled, logprob tokens (sampled, top-k candidates, and echoed prompt tokens) are decoded with `skip_special_tokens=false`, matching the Python frontend's `convert_ids_list_to_tokens` (`tokenizer.decode([tid])`). The generated `text` still follows the request's `skip_special_tokens`.
- A candidate whose own decode ends in U+FFFD is completed with up to four preceding sampled tokens (prompt tokens for prompt logprobs), as in the Python frontend's `_verify_tokens` / `_correct_decoded_token`: it gets the text it completes, or `""` while the sequence is still incomplete. The sampled context carries across engine updates.
- Completions `text_offset` is built by summing these token strings, so it follows both changes.
- `sse_response` sets `text/event-stream; charset=utf-8`, which the Python frontend gets from Starlette for every `text/*` media type. This covers chat completions, completions and `/inference/v1/generate` streaming.

## Details

**Special tokens.** `decode_position_logprobs` decoded every candidate with the request's `skip_special_tokens`, which defaults to true, so a special token decoded to `""` (and several of them collapsed into one key of the completions `top_logprobs` dict). The Python frontend detokenizes logprob tokens with `tokenizer.decode([tid])` regardless of that flag. Since every caller would now pass `false`, the parameter is gone from `decode_logprobs` / `decode_prompt_logprobs`, and one helper, `decode_logprob_token`, owns the rule.

**Split characters.** `SampledContext` keeps the last four sampled tokens (each position's first entry, as in the Python frontend's `_get_sampled_context_ids`); `decoded_text_event_stream` owns one per request so the context crosses engine updates. `repair_split_character` is a direct port of `_correct_decoded_token`: it tries growing context windows, attributes the bytes of trailing context tokens that are incomplete on their own to the candidate, and falls back to the longest common prefix when tokenizer normalization changes the prefix. For prompt logprobs the context starts after the unscored first prompt token, as in the Python frontend (its first entry is `None`).

#63773 (SentencePiece leading spaces) edits the same decode call; whichever lands second needs a small rebase.

**Charset.** Axum's `Sse` sets `text/event-stream` without a charset. The bytes are UTF-8 either way, but clients that default `text/*` to ISO-8859-1 (e.g. `requests` with `iter_lines(decode_unicode=True)`) turn non-ASCII deltas into mojibake. The three route tests that asserted the old header are updated.
