# [Rust Frontend] Support --enable-log-outputs and --enable-log-deltas

[Upstream PR](https://github.com/vllm-project/vllm/pull/63769) · state: closed · merged: True

## Original PR description

## Overview

Python logs generated outputs when `--enable-log-outputs` is set, on chat, completions (vllm-project/vllm#62205) and raw generate, with `--enable-log-deltas` (default true) controlling the per-update lines. The Rust frontend declared both flags as unsupported placeholders, so `vllm serve --enable-log-requests --enable-log-outputs` with `VLLM_USE_RUST_FRONTEND=1` failed at startup. This PR implements both.

Supersedes inactive vllm-project/vllm#57186 (chat only, last commit 2026-09-17).

## Claims

- `--enable-log-outputs` and `--enable-log-deltas` are real Rust frontend flags, also accepted through `--args-json`. As in Python, `--enable-log-outputs` requires `--enable-log-requests`.
- With them, Rust logs one line per streamed update (when deltas are on) and one complete line per choice on chat and completions, and the output token IDs on non-streaming raw generate. Each line carries the text and finish reason at INFO and the token IDs at DEBUG, inside the request span.

- Route tests against the mock engine (`routes/tests.rs`, `log_outputs_*`): chat stream (reasoning delta, content delta, complete line), non-streaming chat, completions stream with and without deltas, non-streaming completions, raw generate (token IDs only), and nothing logged when disabled. They capture the `vllm_server::routes::output_log` events through a global test subscriber and mark any event outside a request span. The chat stream ends on `length`, so its last delta line must carry the finish reason. The five logging tests fail with the INFO line removed.
- `log_outputs_logs_chat_deltas_sent_before_a_stream_error`: an engine error after `Hello` still logs the held delta.
- `log_outputs_logs_chat_text_released_at_finish_with_its_update`: with tools, the parser releases a held-back `<tool_ca` only at finish, and the last delta logs `Hello<tool_ca` as one update with the finish reason.
- CLI tests: flag combinations to `OutputLogging`, the `--args-json` path, and `serve_rejects_log_outputs_without_log_requests` (fails without the check).

## Details

Python: `RequestLogger.log_outputs` (`vllm/entrypoints/serve/utils/request_logger.py`), called from chat streaming (`chat_completion/serving.py:750-776, 928-944`), non-streaming chat (`:1156-1185`), completions (`completion/serving.py:271-281, 425-437, 489-498`) and raw generate (`token_in_token_out/serving.py:569-585`). The `--enable-log-requests` dependency comes from `RequestLogger` existing only when request logging is on.

Changes:

- CLI (`vllm-cmd`): the two flags become `SharedRuntimeArgs` fields and resolve into `ApiServerOptions.log_outputs: OutputLogging` (`Disabled`, `Complete`, `CompleteAndDeltas`), so an options value cannot carry "deltas without outputs". `Config::validate` checks the `--enable-log-requests` requirement, so it also covers the standalone binary.
- Server (`vllm-server`): a small `routes::output_log` module holds the shared line format. The chat, completions and generate handlers log where they already assemble each response and emit the `--enable-log-requests` summary. The chat stream keeps a `StreamDeltaLog` next to `PendingChatChunk` and ends one update per `LogprobsDelta`, the same boundary the SSE chunks use. Raw generate now builds its non-streaming response inside the request span, so its lines (and the existing `generate finished` summary) carry the request ID.

These are HTTP-response logs, so they live in the route layer that builds each response; the CLI layer owns flag parsing and passes a typed option down.

Differences from Python, by design:

- Rust logs through `tracing` with structured fields (`stream="delta"|"complete"`, `output`, `finish_reason`, `token_ids`; the request ID comes from the span), not Python's formatted message.
- The chat "streaming complete" line describes the output like the non-streaming line (content, or the tool calls) and carries the real finish reason. Python logs the raw decoded text with `finish_reason: streaming_complete`; the Rust chat layer never sees the raw text.
- To give the stream's last delta line its finish reason, each update's line is held until the next update ends or the stream finishes. If the stream fails or the client disconnects first, the held update is flushed without a finish reason, so output already sent is never missing from the log.
- `--max-log-len` is still unsupported in Rust, so outputs are never truncated, which matches Python's default.
- Python's inverse spelling `--disable-log-deltas` is not a Rust flag, so `vllm-rs serve` rejects it as unknown; under the Python launcher, `--args-json` carries `"enable_log_deltas": false`.
