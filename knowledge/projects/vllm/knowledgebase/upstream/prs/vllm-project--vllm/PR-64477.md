# [Bugfix][Model] Preserve fp32 second_per_grid_ts and compute Qwen2.5-VL temporal M-RoPE IDs in fp32

[Upstream PR](https://github.com/vllm-project/vllm/pull/64477) · state: open · merged: False

## Original PR description

## Overview

For Qwen2.5-VL video inputs, vLLM currently produces temporal M-RoPE position IDs that differ by one or more (up to 3 positions on a 12003-frame, 400.5 s clip at 29.97 fps) from both the exact integer timestamps and the reference Qwen2.5-VL / HuggingFace `transformers` implementation (`get_rope_index`), due to two precision conversions:
1. `InputProcessingContext._postprocess_output` (`vllm/multimodal/processing/context.py`) casts every floating-point tensor returned by the HF processor, including the time-step metadata `second_per_grid_ts`, to `self.model_config.dtype` (`bfloat16` by default).
2. `Qwen2_5_VLForConditionalGeneration.get_mrope_input_positions` (`vllm/model_executor/models/qwen2_5_vl.py`) computes `(grid_indices[0] * t_factor).astype(np.int64)` in `float64` instead of `float32` (`(torch.arange(llm_grid_t, dtype=torch.float32) * t_factor).long()`), truncating downward by 1 at integer boundaries (`t = 25k`) when the processor's `float32` representation of `2 / fps` rounds below the exact rational value (such as `fps` in `{25, 50, 100}`).

No open issue or PR fixes both root causes (`gh pr list --repo vllm-project/vllm --state open --search "second_per_grid_ts"`):
- `#60352` (open) and `#62413` (draft) add an opt-in `keep_dtype_keys` mechanism to the same `InputProcessingContext._postprocess_output` cast for Voxtral and Whisper; if `#60352` lands first, `second_per_grid_ts` can be registered through that opt-in.
- `#47407` (open, stale since 2026-09-05) edits `grid_indices[0] = (grid_indices[0] * t_factor).astype(np.int64)` in `qwen2_5_vl.py` to bound temporal positions, without preserving `float32` `second_per_grid_ts` or matching HF's `float32` truncation.
- `#50274` (open) touches only Omni files for presampled videos.

**AI assistance disclosure:** AI assistance (Antigravity / Gemini) was used during the investigation, test authoring, and preparation of this PR.

## Claims

- Exempts the time-step metadata key `second_per_grid_ts` from the `self.model_config.dtype` cast in `InputProcessingContext._postprocess_output`, keeping the `float32` tensor produced by `Qwen2_5_VLProcessor` (while leaving `video_second_per_grid` untouched so Qwen2.5-Omni / Qwen3-Omni are unaffected; fixing the Omni `video_second_per_grid` path is out of scope for this PR).
- Computes the temporal M-RoPE index in `Qwen2_5_VLForConditionalGeneration.get_mrope_input_positions` using explicit `float32` PyTorch arithmetic (`(torch.arange(llm_grid_t, dtype=torch.float32) * t_factor).long().numpy()`), matching Qwen2.5-VL's `get_rope_index_25` and HF `transformers` bit-for-bit.

## Validation

Standalone reproducer comparing the old and new temporal ID expressions against Qwen2.5-VL's reference `get_rope_index_25`:

```python
import numpy as np
import torch

# Case 1: fps=25.0 (all frames), temporal_patch_size=2, tokens_per_second=2.0
# Exact temporal ID at t=25 is 25 * (2 / 25) * 2 = 4.
spg_f32 = torch.tensor([2.0 / 25.0], dtype=torch.float32)  # 0x3da3d70a < 0.08
t_factor = spg_f32.item() * 2.0
grid_t = 101

old_ids = (np.arange(grid_t) * t_factor).astype(np.int64)
new_ids = (torch.arange(grid_t, dtype=torch.float32) * t_factor).long().numpy()
ref_ids = (torch.arange(grid_t, dtype=torch.float32) * spg_f32.item() * 2.0).long().numpy()

print("fps=25 at t=25,50,75,100 -> old:", old_ids[[25, 50, 75, 100]], "new:", new_ids[[25, 50, 75, 100]], "ref:", ref_ids[[25, 50, 75, 100]])

# Case 2: fps=7.0 under model_config.dtype=bfloat16
spg_bf16 = torch.tensor([2.0 / 7.0], dtype=torch.float32).to(torch.bfloat16)
old_bf16_ids = (np.arange(99) * (spg_bf16.item() * 2.0)).astype(np.int64)
new_f32_ids = (torch.arange(99, dtype=torch.float32) * (torch.tensor([2.0 / 7.0], dtype=torch.float32).item() * 2.0)).long().numpy()
print("fps=7 mismatches from bf16 cast:", int((old_bf16_ids != new_f32_ids).sum()), "/ 99")
```

```text
fps=7 mismatches from bf16 cast: 14 / 99
```

## Details

1. In `InputProcessingContext._postprocess_output`, `BatchFeature` floating-point outputs are cast to `self.model_config.dtype` (`bfloat16` by default). For a Qwen2.5-VL video item (`supports_mm_device_do_normalize = True`, so pixel tensors arrive as `uint8`), `second_per_grid_ts` is a scalar time interval per video used on CPU to compute integer M-RoPE position IDs, not a model activation. Casting `2 / sampled_fps` to `bfloat16` introduces up to `2^-8` relative error (for example, on a 198-frame, 28.3 s clip at 7 fps with every frame kept, giving 99 temporal patches, 14 of 99 IDs are 1 too low; on a 12003-frame, 400.5 s clip at 29.97 fps sampled to 768 frames by vLLM's `qwen2_vl` loader, giving 384 patches, 321 of 384 IDs are 1-3 too high, with last ID 801 instead of 798). Note that because the exemption is keyed by `second_per_grid_ts`, other consumers of `second_per_grid_ts` (`mimo_v2_omni` and the Transformers backend) also receive `float32` seconds now; they were not tested here.
2. Even when `second_per_grid_ts` remains `float32`, `seconds.data.item()` promotes the `float32` value `s = RN32(2 / fps)` to a Python `float` (`float64`). When `s < 2 / fps` (such as `fps = 25`, where `RN32(0.08) = 0.07999999821186066`), multiplying by `np.indices` in `float64` keeps `25 * s * 2 = 3.999999910593033 < 4`, which `.astype(np.int64)` truncates to `3` instead of `4`. In `float32` (`torch.arange(llm_grid_t, dtype=torch.float32) * t_factor`), `RN32(25 * RN32(0.16)) = 4.0`, matching Qwen's reference `get_rope_index_25` and HF `transformers`.
