# [Metrics] Add vllm:kv_admission_refusals counter

[Upstream PR](https://github.com/vllm-project/vllm/pull/64133) · state: open · merged: False

## Original PR description

Adds a per-engine Prometheus counter, `vllm:kv_admission_refusals{reason}` (`vllm:kv_admission_refusals_total`), for waiting requests the scheduler refuses KV cache blocks, labeled by the check in `allocate_slots` that refused them.

## Overview

When `allocate_slots` returns `None` for a waiting request, the request stays at the head of the queue and everything behind it waits. Today nothing says why. The pool may be too small for the request, free blocks may be short, or blocks may be free but held back by the `--watermark` headroom or by the reserve for in-flight async KV loads. `vllm:kv_cache_usage_perc` and `vllm:num_requests_waiting` show that requests wait, not what blocks them, and the remedies differ: more memory, a lower watermark, or fewer concurrent P/D loads.

This PR records the reason at the point `allocate_slots` refuses, most fundamental first:

| `reason` | Refused because |
|---|---|
| `exceeds_pool_capacity` | the request needs more blocks than the pool has |
| `insufficient_free_blocks` | not enough free blocks |
| `watermark` | it would fit without the watermark headroom |
| `inflight_load_reserve` | it would fit without the blocks reserved for in-flight prefills (`reserved_blocks`, async KV load admissions) |

## Claims

- `vllm:kv_admission_refusals_total{reason}` counts waiting requests refused KV cache blocks, labeled by the check in `allocate_slots` that refused them.
- Each request is counted at most once per reason while it waits. The queue head is retried every step, so counting attempts would measure the step rate rather than refusals; and its reason can flip as free blocks hover around a threshold (e.g. `insufficient_free_blocks` ↔ `watermark`), so each reason already counted for it is remembered. A request is forgotten once admitted or finished.
- No behavior change: `allocate_slots` makes the same decision and only records why it returned `None`.

## Validation

New unit tests in `tests/v1/core/test_scheduler.py` (6 usable blocks, `block_size=16`):
- `test_stats_report_kv_admission_refusals`:
  - with one 3-block request running and a 2-block watermark, a second 3-block request is refused for `watermark`, and is counted once although it's retried every step;
  - with the watermark removed, it's admitted, and a third request is refused for `insufficient_free_blocks`;
  - finishing the refused request drops its entry, and the counts reset once reported.
- `test_kv_refusal_reason_inflight_load_reserve`: `allocate_slots(..., reserved_blocks=4)` records `inflight_load_reserve`; a request larger than the pool records `exceeds_pool_capacity`; a successful allocation clears the reason.
- `test_kv_refusal_counted_once_per_reason_while_waiting`: a waiting request is refused `watermark`, `insufficient_free_blocks`, `watermark`, `insufficient_free_blocks` as another request takes and frees blocks, and is counted once for each reason. It fails if a request is recounted each time its reason changes.

New logger test `test_kv_admission_refusals_counter` in `tests/v1/metrics/test_histogram_buckets.py`: all four reason series exist at 0 for both engines, `PrometheusStatLogger.record(..., engine_idx=1)` increments only engine 1's `watermark` and `insufficient_free_blocks` counters, and an unknown reason is ignored rather than raising.

```bash
pytest tests/v1/metrics/test_histogram_buckets.py -k kv_admission_refusals

       tests/v1/core/test_kv_cache_utils.py tests/v1/metrics/test_stats.py \

```

All new tests are `cpu_test` (module-level marker), so they run in CI. The last command plus `tests/v1/metrics/test_histogram_buckets.py` gives 591 passed; the 63 failures are the same ones that fail on unmodified `main` in my CPU-only environment (missing GPU / multimodal dependencies). `ruff check`, `ruff format` and `mypy` (1.20.2, as in pre-commit) are clean.

End-to-end on GKE, on an earlier revision of this PR that counted a request again whenever its reason changed. With the per-reason dedup, a request that flips between reasons is no longer recounted, so the counts below are an upper bound for the current code. The other review changes (the `last_refusal_reason` reset and passing `reserved_blocks` to `_refusal_reason()`) don't change which reason is recorded. vllm-torchtpu pins vLLM v0.32.0, so I cherry-picked the commit onto `v0.32.0` (clean) and deployed it with stock vllm-torchtpu `main`, which has no plugin copy of this counter. Setup: TPU v5e, Qwen2.5-7B-Instruct, P/D via llm-d with `TPUConnector` + Raiden, `block_size=128`, 109 KV blocks per engine, `--watermark 0.05` on decode only. A load job overloaded the single decode engine with shared-prefix and bursts of concurrent unique ~600-token prompts; counters over 300 s:

| Engine | `exceeds_pool_capacity` | `insufficient_free_blocks` | `watermark` | `inflight_load_reserve` | Max waiting for capacity |
|---|---|---|---|---|---|
| prefill (no watermark, no async loads) | 0 | **114** | 0 | 0 | 51 |
| decode (`--watermark 0.05`, P/D loads) | 0 | **31** | **79** | **8** | 15 |

Each reason shows up where its check applies: prefill has neither a watermark nor async loads, so only `insufficient_free_blocks`. On decode, most refusals came from the 5-block watermark rather than a lack of free blocks, which a dashboard couldn't tell apart before.

## Details

- **Where:**
  - `KVCacheManager.allocate_slots()` clears `last_refusal_reason` on entry and sets it at its two `return None` sites, via `_refusal_reason(num_blocks, watermark_blocks, reserved_blocks)`, which checks each reserve explicitly;
  - `Scheduler` reads it where a waiting request fails to allocate (`_record_kv_refusal`), keeps the reasons already counted for each waiting request in `_kv_refusal_reasons` (dropped on admission and in `_free_request`), and `make_stats()` drains the counts into the new `SchedulerStats.kv_admission_refusals`;
  - `PrometheusStatLogger` increments the counter, skipping any reason it doesn't know.
- **Reason order:** when several reserves are involved, the most fundamental one wins. A request blocked by both the watermark and the in-flight reserve counts as `watermark`, so `inflight_load_reserve` means only the reserve stood in the way.
- **Not included:** requests queued behind a refused head are not counted (they never reach `allocate_slots`). A `head_of_line` reason could be a follow-up if reviewers want it. Running requests that fail to grow are handled by preemption and already counted by `vllm:num_preemptions`.
- **Always registered:** all four reason series exist from startup at 0. Refusals happen with or without a KV connector, so unlike connector-only metrics (e.g. `vllm:kv_load_failed_tokens`, registered only with `kv_transfer_config`) the counter isn't gated. It is also listed in `EXPECTED_METRICS_V1` and documented automatically in the generated metrics list (`gen:metrics-general`) on the [metrics page](https://docs.vllm.ai/en/latest/usage/metrics.html).
- **Rust frontend:** its `SchedulerStats` decoder ignores unknown fields, so it is unaffected. It doesn't export this counter yet.
- This is part of the same HBM KV cache observability effort as #64026 (`vllm:kv_load_failed_tokens`), and pairs with #64093 (`vllm:kv_admission_reserved_blocks`) (the sizes of the reserves this counter attributes refusals to).
