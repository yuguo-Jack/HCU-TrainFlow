# [Perf][Attention] Cache TritonAttentionImpl K/V cache views per tensor (#64572)

[Upstream PR](https://github.com/vllm-project/vllm/pull/64890) · state: open · merged: False

## Original PR description



## Overview

Cache the derived K/V cache views per kv_cache tensor identity in TritonAttentionImpl (matching #64571 for FlashAttentionImpl) instead of re-deriving transpose(1, 2).split(...) and FP8 dtype views on every attention call.

Fixes #64572

## Claims

- Caches derived key_cache and value_cache views (including FP8 view retyping and ROCm pointer-range metadata) on TritonAttentionImpl keyed by kv_cache tensor identity.
- Clears _kv_view_cache during profiling KV cache teardown alongside _k_scale_cache and _v_scale_cache so profiling buffers are released cleanly.

## Validation

```bash
pytest tests/v1/attention/test_triton_attn_kv_view_cache.py -v
```

## Details

TritonAttentionImpl previously ran kv_cache.transpose(1, 2).split(...) and two view(self.fp8_dtype) calls on every forward, do_kv_cache_update, do_rope_and_kv_cache_update, and per-token-head quantized cache access, even though the resulting views depend only on the allocated kv_cache tensor's storage, shape, and strides. Caching the derived views per kv_cache identity removes this repeated host-side view construction across all layers on eager steps while rebuilding automatically when the profiling KV cache is replaced by the runtime cache.

## Overall assessment

LGTM pending the two questions below (both robustness/clarity, neither blocking). The caching is keyed on tensor identity, folds in the FP8 retype, covers every call site, and — importantly — is cleared in **both** teardown paths, so it doesn't pin the profiling KV cache.

## Questions

1. **Shared single-slot cache across two writers with different split sizes.** `_get_kv_views` splits at `self.head_size` and `_pth_key_value_caches` splits at `kv_cache.shape[-1] // 2`, but both write the same `self._kv_view_cache` slot. I convinced myself these never mix on a single impl instance: the PTH path (`_pth_key_value_caches`) is only reached when `self._is_per_token_head_quant` is true, `do_kv_cache_update` returns early before the `_get_kv_views` block for PTH, and `do_rope_and_kv_cache_update` is gated by `fused_rope_kvcache_supported()` which returns `False` for PTH. Since `_is_per_token_head_quant` is fixed per instance, exactly one writer is ever used. Could you add a one-line comment to `_kv_view_cache` noting that the two writers are mutually exclusive per-instance? It's a non-obvious invariant, and a future refactor that calls `_get_kv_views` from a PTH path would silently cache a wrong-sized view.

2. **`do_kv_cache_update` FP8 guard change.** On `main`, `do_kv_cache_update` retypes unconditionally under `is_quantized_kv_cache(...)`, whereas `_get_kv_views` adds the `key_cache.dtype != self.fp8_dtype` guard that the `forward` path already had. This looks intentional and harmless to me — viewing an already-fp8 tensor to the same dtype is a no-op view — but it is a behavior harmonization in the `do_kv_cache_update` path, so flagging it explicitly in case the unconditional form was load-bearing for some backend.

## Nits

1. The cache is single-slot (last tensor wins). If an impl ever alternated between two live `kv_cache` tensors it would rebuild every call — no correctness issue, just lost perf. In practice each impl is bound to one tensor for its lifetime so this is fine; a comment to that effect would help.

2. The new test covers the MRV2 teardown (`clear_layer_kv_caches`) but not the V1 `_cleanup_profiling_kv_cache` path in `gpu_model_runner.py`. The latter is the exact path where the analogous FA caching regressed in #64571 (pinned profiling tensor). It's structurally identical here so I'm not worried, but a matching assertion would close the loop given the history.

## What I checked and found safe

- **All four call sites are covered.** forward else-branch, `do_kv_cache_update`, and `do_rope_and_kv_cache_update` all route through `_get_kv_views`; the per-token-head site `_pth_key_value_caches` gets its own inlined identity cache. Nothing left re-deriving views per call.

- **Teardown is safe in both paths — this was my main concern given #64571.** The cache tuple `(kv_cache, key_cache, value_cache)` holds a strong ref to the (profiling) `kv_cache`. Both `_cleanup_profiling_kv_cache` (gpu_model_runner.py) and `clear_layer_kv_caches` (worker/utils.py) set `layer.impl._kv_view_cache = None` right alongside the existing `_k_scale_cache`/`_v_scale_cache` clears, using the same `hasattr` convention. So the profiling buffer is released on teardown and not pinned — the regression caught on #64571 is not reintroduced. As belt-and-suspenders, the `cache[0] is not kv_cache` identity check would also force a rebuild when the runtime cache replaces the tensor, even if a teardown were ever skipped.

- **`set_triton_ptr_range` semantics are preserved.** On `main` the forward path rebinds `kv_cache = kv_cache.transpose(1, 2)` and passes the *transposed* tensor as the `region`, while `_get_kv_views` passes the original *un-transposed* `kv_cache`. These are equivalent: `set_triton_ptr_range` computes `region_end` from `data_ptr()` + `sum((n-1)*stride)`, `transpose` leaves `data_ptr()` unchanged, and that byte-extent sum is permutation-invariant over dims — so the AMD 32-bit buffer-addressing bound is unchanged. The ROCm-only gate and the fact that the PTH path never calls `set_triton_ptr_range` are both preserved.

- **FP8 retype is folded into the cache**, so the quantized path no longer does two `view(self.fp8_dtype)` calls per forward/update — matching the intent of the issue.

- **Attr-name convention matches ours (#64571).** Naming the slot `_kv_view_cache` and declaring it as a class attribute means the two existing `hasattr`-based teardowns pick it up for free, so the two backends stay symmetric.

- **Scope is correct.** `TritonAttentionImpl` is the only class touched; other backends share the pattern but are out of scope for #64572 (FA is covered by #64571).

Nice work — happy to approve once the mutual-exclusion comment (Q1) is added; the rest are optional.
