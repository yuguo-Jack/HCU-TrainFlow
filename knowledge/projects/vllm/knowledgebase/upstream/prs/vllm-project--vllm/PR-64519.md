# [MRV2][DBO] Split eager decode steps for hybrid recurrent models

[Upstream PR](https://github.com/vllm-project/vllm/pull/64519) · state: open · merged: False

## Original PR description

## Overview

Eager decode DBO for hybrid attention/recurrent models in MRV2, the first slice of #64439. **Draft: static review, CPU unit tests and a single-GPU kernel-level check; no model was loaded and model outputs are not qualified.**

## Claims

- Each DBO microbatch builds its recurrent metadata with its own metadata builder (`ubatch_idx`), over its own requests' original state slots. The existing `UBatchRunner` slicing already provides the per-microbatch requests, block tables and request mapping.
- Hybrid and attention-free models split only uniform decode steps. `dbo_prefill_token_threshold` is raised above `max_num_batched_tokens`, so the existing DP vote keeps every step with a prefill unsplit and no request's recurrent state is divided between microbatches.
- Allowed only with eager execution, synchronous scheduling, prefix caching off (`mamba_cache_mode == "none"`), DCP=1, no speculative decoding and no RecoverSSM. The align prefix-state path and RecoverSSM's per-step recording are not microbatch-aware and stay rejected.
- Per-step state hooks (`preprocess_state`, `postprocess_state`) still run once per step, outside the microbatches.

```bash
VLLM_USE_V2_MODEL_RUNNER=1 pytest -q tests/test_config.py -k hybrid_dbo
VLLM_TARGET_DEVICE=cpu pytest -q --noconftest tests/v1/worker/test_mamba_hybrid_model_state.py
```

The CPU component test slices a real `InputBatch` into two decode microbatches and builds them with two real GDN metadata builders; each microbatch's state indices equal its own requests' slots.

The GPU test runs the real GDN decode kernels (`_forward_core`, bound to random weights and state pools, no checkpoint) through the real `UBatchRunner`: per-microbatch metadata from `MambaHybridModelState.prepare_attn`, two interleaved DBO threads with a `dbo_yield` handoff, and metadata read from the per-microbatch forward context. Over two decode steps with five requests on scattered state slots, reversed request order and DP padding, the core-attention output and the conv/SSM state pools match one unsplit batch bit for bit (`rtol=0, atol=0`). The runner's config disables expert parallelism so no EP process group is needed; real EP all-to-all is not exercised. `tests/v1/worker` and `tests/test_config.py` are selected by existing CI steps.

## Details

Production change: **+28/-3** (`mamba_hybrid.py` +1/-1, `vllm/config/vllm.py` +27/-2). In eager mode the GDN and Mamba builders take state indices directly from the sliced block table and do not touch their persistent graph buffers; recurrent layers read the current microbatch's metadata from the forward context that DBO swaps per thread. Dummy runs keep writing to the reserved null block.

Unlike the issue's plan, no model/backend allowlist is added: the mechanism depends only on builder and slot slicing. Model qualification is still required before this leaves draft.

Duplicate checks: searched `64439 in:body`, "hybrid DBO" and "mamba microbatch ubatch" among open PRs; none implements this. #55688/#52962 (ReplaySSM), #55260 (GDN kernels) and #63483 (pure-TP DBO) are distinct, as listed in the issue.

Before readiness: real hybrid MoE DBO off/on output/logprob comparison with both microbatch IDs observed on both ranks; finished/new requests, slot reuse and idle-rank recovery; performance and memory. Prefill splitting, FULL graphs, prefix-state caching, speculative decoding and RecoverSSM are later slices. AI assistance was used for implementation, review and tests.
