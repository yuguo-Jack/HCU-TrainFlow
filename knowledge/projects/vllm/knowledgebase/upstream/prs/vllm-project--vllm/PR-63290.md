# [ROCm][Perf] Muse Spark: run the AITER MXFP4 experts on the native top-k routes

[Upstream PR](https://github.com/vllm-project/vllm/pull/63290) · state: closed · merged: False

## Original PR description



## Overview

Muse Spark normalizes each expert's output before the top-k weighted sum, so its MoE must return the unweighted per-route outputs `[T, top_k, H]`. On ROCm, the MXFP4 experts get them by repeating the normed input `top_k` (8) times and running AITER `fused_moe` with one route per row. The activation quantization, the sort and the stage-1 input then work on 8× more rows than there are tokens, in each of the 60 MXFP4 MoE layers. This PR runs AITER on the native `[T, top_k]` routes with one input row per token. The kernels and tiles stay the same, and only stage 2 is replaced by its per-route writer, so the route outputs are bitwise identical.

## Claims

- **Recipe default (TP8 + EP8 + DSpark), 8×MI355X:**
  - Single-request TTFT is −8% at 2k tokens and −12% at 8k and 16k tokens.
  - On random 8k in / 1k out, output throughput is +6% at concurrency 16, +7% at 32 and +10% at 64. Mean TTFT is −9% to −12% at every concurrency.
- **Bitwise-identical outputs.** Under TP8 + EP8, greedy outputs (text and every logprob) are identical to the base. The unit tests compare the per-route and the finalized outputs bit for bit. GSM8K is unchanged (paired exact McNemar p = 0.38).
- **The KV cache grows by 1%**, because the profile run no longer allocates the `[T * top_k, H]` MoE input.
- **Default on.** `VLLM_ROCM_MUSE_ROUTE_NATIVE_MOE=0` keeps the repeated input. Batch sizes whose AITER config has no per-route stage 2 keep it automatically, as does every batch size if the installed AITER lacks one of the internals used.
- No change to core files: everything is in `vllm/models/muse_spark/amd/`, plus one env var in `vllm/envs.py`.

## Details

**How.**

- `ops/route_native_moe.py` calls AITER's `_fused_moe_impl` on the native `[T, top_k]` routes with unit weights and one input row per token. `_metadata_transform` returns the config that the repeated call (`get_padded_M(T * top_k)` rows, top 1, or top 2 under EP) would use, so both paths run the same stage-1 and stage-2 kernels and tiles. `_stage2_override` replaces stage 2 with its per-route writer into the `[T, top_k, H]` route output: `flydsl_moe_stage2(return_per_slot=True)` for FlyDSL v1, `mxfp4_moe_gemm2(epilog="reduce")` for v2.
- Under EP, non-local routes are not written. The existing fused finalize already masks them through the expert map, so the finalize is unchanged.
- `MuseSparkAiterExperts.uses_route_native(num_tokens)` decides per batch size, and the pre-expert norm asks it, so it writes one row per token instead of `top_k`. The decision is a static lookup of the AITER config, and the batch size, the weight shapes and the tuned CSV are the same on every rank, so all ranks agree without a collective. It is cached per batch size, so graph capture and replay see a fixed path.
- Batch sizes whose config has no per-route stage 2 (one-stage asm, `ksplit > 1`, non-FP4 activations) keep the repeated input. Under TP, so do batches below 65 tokens: with 256 experts per rank, sorting the `top_k`-wide routes costs more than the smaller input saves there (single-GPU norm → MoE → finalize: −9% to −11% at 24 tokens, about +2% at 48–64). The EP rank shape gains at every batch size (+1% to +13% at 8–256 tokens). The DSpark draft has no MoE and the BF16 layers (first and last) use the Triton experts; neither is affected.

**Limitations.**

- *AITER internals.* The entry points used (`_fused_moe_impl` with `_metadata_transform` / `_stage2_override`, the FlyDSL stage-2 wrappers and helpers) are AITER internals; they are present in AITER 0.1.24 and 0.1.26. `_aiter_has_per_route_hooks()` turns the path off when one is missing, and the bitwise tests catch semantic drift. A public per-route output option in AITER's `fused_moe` would remove these internals.
- *First use of a prefill bucket.* The per-route stage-2 variants are not in AITER's precompiled FlyDSL cache, so a new prefill batch-size bucket compiles its variant on first use. Under TP, the first 2k request of a fresh server took 4.4 s instead of 0.23 s; later requests are unaffected. Under EP the first request showed no extra time. The profile-run and graph-capture sizes compile at startup.
- AITER logs `no tuned FlyDSL config` once per new key, because `_fused_moe_impl` looks up the native `topk = 8` key before `_metadata_transform` replaces it. The kernels that run are the repeated call's.
- The expert map is read once after weight loading. EPLB would re-register it, but the Muse ROCm path rejects EPLB.

**Complexity.** The PR adds 436 non-test lines: `ops/route_native_moe.py` (340: the AITER call, the config mirror, the two per-route stage-2 writers and the capability check), `muse_moe_runner.py` (+84: the batch-size decision and the wiring), `model.py` (+4: one row per token in the pre-expert norm), `envs.py` (+8). There is no new kernel: AITER's existing stage-1 and stage-2 kernels and tuning tables run through its `_metadata_transform` / `_stage2_override` hooks, and the finalize is unchanged.
