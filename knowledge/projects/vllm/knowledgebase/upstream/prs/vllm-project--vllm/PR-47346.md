# [Bugfix][V1] Surface out-of-range token ids as a clear per-request error

[Upstream PR](https://github.com/vllm-project/vllm/pull/47346) · state: open · merged: False

## Original PR description

## Purpose

An out-of-range token id coming from the model (e.g. NaN/overflow in the forward pass yields a garbage sampled id) is currently handled poorly by the fast (Rust `DecodeStream`) detokenizer path:

- It is passed straight to `tokenizers.DecodeStream.step`, which raises a cryptic `TypeError: argument 'id': StreamInput must be either an integer or a list of integers`.
- The existing `except (OverflowError, TypeError)` handler — added in #24351 / #26445 for the rare **in-range** overflow in #21951 — logs a **full traceback per token** and returns an empty token.

So when the model produces *systematically* corrupt ids, you get thousands of stack traces plus a silently empty / garbage completion, with no clear signal of the real problem. Seen in the wild on ROCm gfx950 serving DeepSeek-R1 with an fp8 KV cache, where a metadata bug (since fixed by #46997) corrupted decode output into out-of-range (negative) token ids: ~19k tracebacks followed by engine death, and on well-formed prompts a silent accuracy collapse.

## Change

- `FastIncrementalDetokenizer`: validate `0 <= token_id < vocab_size` **before** the `DecodeStream` step and raise a clear `InvalidTokenIDError` naming the id and valid range. This is also stricter than the Rust binding, which silently accepts any `u32` (so an in-`u32`-range but out-of-vocab id would otherwise be mis-decoded rather than flagged).
- `OutputProcessor`: catch `InvalidTokenIDError` and abort **only that request** (`FinishReason.ABORT`) with a single clear log line; the server and other in-flight requests keep running.
- In-range step overflows still fall through to the existing recover path, so **#21951 behavior is unchanged**. Because out-of-range ids now raise before that `except`, the per-token traceback flood is also gone.

**Not a duplicate of #24351 / #26445** — those added the catch-and-recover for the in-range overflow; this refines it so genuinely *out-of-range* ids (a corruption signal, not a detok glitch) fail loudly and per-request instead of being silently swallowed.

Draft: opening for discussion on the chosen behavior (per-request abort vs. rate-limited recover) before marking ready.

## Test Plan / Result

Added `test_fast_inc_detok_out_of_range_token_id` (parametrized over negative and >= 2^31 ids), using an ungated fast tokenizer so it runs without gated-model access.

```
$ pytest tests/v1/engine/test_fast_incdec_prefix_err.py -k out_of_range -q
4 passed, 1 deselected
```

The pre-existing `test_fast_inc_detok_invalid_utf8_err_case` is unmodified (it needs a gated tokenizer, not runnable in my environment).
