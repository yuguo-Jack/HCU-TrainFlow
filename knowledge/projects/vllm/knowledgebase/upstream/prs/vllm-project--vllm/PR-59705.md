# [ROCm][Perf][MiniMax-M3] Fused sparse-layer decode (mono decode kernel)

[Upstream PR](https://github.com/vllm-project/vllm/pull/59705) · state: open · merged: False

## Original PR description

These changes are ported from **[ROCm/ATOM#2419](https://github.com/ROCm/ATOM/pull/2419)**

## Summary
One fused FlyDSL launch per sparse layer per rank, for decode steps of 1..16 tokens. K1 (input norm, QKV GEMV, QK-norm/RoPE, K/V and index cache insert, indexer scoring) is fused in front of K4 (top-k selection, split attention, `o_proj` + all-reduce, post-attention norm, router, MoE + all-reduce), so a sparse layer's norms, attention, both all-reduces and its MoE become a single kernel. 57 of MiniMax-M3's 60 layers run this way; the embedding, dense layers 0-2 and the final norm stay on the original modules.  

Enabled by default if below conditions met
Build-time checks
- Tensor parallel size is 4
- No PP/DP
- `VLLM_ROCM_SHUFFLE_KV_CACHE_LAYOUT=1`
- KV cache dtype is fp8
- Index cache dtype is fp8
- Block size is 128
- No expert parallelism

Per-step checks
- Enabled only for pure decodes and max tokens <=16 
- PIECEWISE cudagraphs not supported

- akii96 · comment · 2026-10-05T13:40:15Z · [source](https://github.com/vllm-project/vllm/pull/59705#issuecomment-5995648410)

Thanks @ukannika! We're both porting the same ATOM kernel, so it makes sense to combine our work 🤝 

I'll take #59653 out of draft once aiter#6047 lands. It needs those kernels, so I'm waiting for that first.

Your PR supports checkpoints that already have FP8 attention weights, mine does not. Right now mine only works with weights converted at load, so it would reject your MiniMax-M3-MXFP4-AttnFP8 checkpoint. Your weights.py already handles both cases, and I'd love to bring that in with you as co-author 🙏 

On graph capture and padding, here's what mine covers today. The kernel is set up on a normal step before graphs are captured. It's set up again if the KV cache moves, and it raises an error if a graph capture reaches it first. aiter#6047 also fixes padding rows changing which experts the real rows use, and adds a test for that. If you have other cases in mind, send them over.

On FP8 at load: you're right. Once the flag is on, the regular path uses the FP8 qkv_proj and o_proj too. GSM8K is 0.948 with the flag on and off. I'll make this clear in the flag's docs. Once your checkpoint support is in, users can choose either option.

On TP: the scales don't change with TP. The qkv scales are per output row, so splitting across GPUs doesn't affect them. For o_proj, vLLM takes the max across GPUs before computing the scales, so each GPU ends up with the same scale it would get without TP.

On additional_config: I'd keep the flag in attention_config, next to minimax_m3_msa_decode_backend, where it's typed and validated. additional_config is an untyped dict, so a typo would just be ignored. Happy to go either way if maintainers prefer.

A few things in #59705 we could fix together:
- Nothing sets indexer_cp, so the long-context path never runs. AITER only supports one index head for now. I can add the rest there.
- The KV cache addresses are saved once, which causes the profiler TODO. Mine sets up again when the cache moves, which would fix that.
- The per-step logs Chuan mentioned. Mine logs once at startup.
