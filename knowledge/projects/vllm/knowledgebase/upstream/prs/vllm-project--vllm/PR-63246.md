# [ROCm][Perf][Muse Spark] TEP8 variant of the specialized decode (draft, stacked on #62766)

[Upstream PR](https://github.com/vllm-project/vllm/pull/63246) · state: closed · merged: False

## Original PR description



## Overview

**Draft, stacked on #62766** (TP8 specialized decode; its commit is the first commit here, review only the top commit). Adds a TEP8 variant: with `--enable-expert-parallel` on the TP8 deployment, K2 runs attention TP8 and the experts expert-parallel, so TP8 and TEP8 can be compared under the same mono kernel. Related: RFC #60904, #62622.

## Claims

- `--monokernel --enable-expert-parallel` serves Muse Spark Open MXFP4 on 8x MI355X with K2 built for expert parallelism (`K2Build.moe == "ep"`): rank r holds experts `[32 r, 32 r + 32)` whole instead of a 512-column slice of all 256.
- TP8 builds, scratch layout and runtime behavior are unchanged by design.
- **TEP8 is slower than TP8 at every width measured (kernel level, +12% to +26% per layer).** This PR is the comparison variant, not a proposal to replace TP8; it is only worth merging if the numbers change.

- Correctness: K2 TEP8 vs TP8 built from the same 256 logical experts: identical routing and stream; branch relative difference 3.9e-3 (about one bf16 rounding), including a forced case with all 64 picks on rank 0 (more than one a2 staging chunk). GSM8K 5-shot greedy, 1319 questions, c1, DSpark real verify, first version of the TEP8 kernel: 0.945, mean acceptance length 3.97, median TPOT 2.71 ms (TP8 mono baseline: 0.955, 4.02, 2.35-2.57 ms).
- AgentX c1 (DSpark acceptance fixed at 4.05, prefix caching, 1M context, AITER #6336 attention): interactivity p50 334 tok/s, ITL 2.99 ms for TEP8 mono, vs 273 / 3.66 ms for stock TEP8. No TP8 mono AgentX number from me.
- Resources of the 8-row EP build: 256 VGPRs (the limit), 0 scratch, 115 KB LDS (TP8: 232 VGPRs, 44 KB).

## Details

- Only the experts' stages differ. The union and gate/up reuse the TP8 stages at the EP geometry (`spec.EP_GEOM`); `stages/experts_ep.py` is the new down stage: the a2 rows of this rank's local picks are staged in LDS in one poll round trip, wave w multiplies four K steps of every local slot's w2, and the waves' fp32 parts are summed in wave order and rounded once. A local pick pushes its row, every other pick pushes exact zeros, so the column-owner reduce, the post-expert norm, the route weights and the unpooler are the TP8 code unchanged.
- Why TEP8 loses: under TP8 every rank streams a 1/8 slice of each touched expert; under TEP8 the rank holding the most experts streams them whole. On real 8-token windows (AgentX traces) the busiest TEP8 rank reads about 1.7x the expert bytes of a TP8 rank. Per-stage timeline at 8 rows: gate/up +2.9 us, down +4.7 us, owner reduce +2.1 us, the rest the same; the expert stages already run near HBM bandwidth.
- Runtime: EP accepted with TP8, DP1, linear placement, no EPLB, `mono_core=tensor`, `mono_front=stock`; the expert map must be this rank's linear 32 (vLLM's global-to-local ids or AITER's 0/1 mask).
- Limitations / follow-ups: Phase B/C cores are not supported with EP; the owner still waits on all 8 ranks' pushes (zeros included); the previous revision's ISA-pin test (which showed the TP8 binaries unchanged) was removed from #62766, so TP8 codegen is unchanged only by construction. A mailbox base in the new a2 poll was made provably wave-uniform to satisfy the compile gate's no-waterfall check, untested.
- Benchmark scripts (K2 TP8-vs-TEP8 timing with a per-stage clock, equivalence check, routing-imbalance study) are not in this PR; the timeline instrumentation was kept out to keep the diff small.
