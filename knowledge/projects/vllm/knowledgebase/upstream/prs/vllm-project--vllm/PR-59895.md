# [Bugfix] Normalize Marlin int8-activation group scales by abs().max()

[Upstream PR](https://github.com/vllm-project/vllm/pull/59895) · state: closed · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

**Depends on #48926. Landing order: land with or after #48926, never before.**

- This PR fixes #59403 alongside #48926 (also reported in #48905). Neither change is a complete fix on its own.
- #48926 makes the kernel read int16 group scales as signed. This PR normalizes them by `abs().max()` so negative group scales survive the int16 cast.
- Not a duplicate of #48926: that PR only changes the kernel read in the two `marlin_template.h` files. This PR only changes the Python scale normalization and adds tests. No other open PR touches `marlin_act_int8_process_scales`. The split was discussed in #59403.

## Claims

- `marlin_act_int8_process_scales` stores int16 group scales bounded to `[-4096, 4096]` for any sign pattern. Before, it overflowed when the most negative scale exceeded 8x the largest positive one, or when every scale was negative.
- With #48926 applied, int8-activation Marlin GEMM is correct for mixed, skewed negative, and all negative group scales (GPTQ and AWQ, fp16 and bf16).
- No change for checkpoints with only positive scales (`abs().max() == max()`).
- End to end, a symmetric AutoRound W4A8 checkpoint goes from 0.0% to 74.0% on GSM8K with #48926 and this PR (W4A16 reference: 76.7%).

## Validation

Setup: L40S (sm89), driver 580, CUDA 13.0, torch 2.13.0+cu130, vLLM at `84bcbc6`. Main kernels from the precompiled wheel. #48926 kernels built by applying its diff and rebuilding `_C_stable_libtorch` and `_moe_C_stable_libtorch` (`TORCH_CUDA_ARCH_LIST=8.9`).

New GPU test `test_marlin_gemm_int8_act_negative_group_scales`, failures out of 8 cases per pattern:

| Kernel read | Python helper | `mixed` | `skewed_neg` | `all_neg` |
|---|---|---|---|---|
| `uint16` (main) | `max()` (main) | 8 fail | 8 fail | pass* |
| `uint16` (main) | `abs().max()` (this PR) | 8 fail | 8 fail | 8 fail |
| `int16` (#48926) | `max()` (main) | pass | 8 fail | pass |
| `int16` (#48926) | `abs().max()` (this PR) | **pass** | **pass** | **pass** |

\* Passes by accident on main: dividing by a negative `max()` flips both the stored values and the global scale, so the signs cancel, as long as nothing overflows.

New CPU test `test_marlin_act_int8_process_scales_signed`: main helper fails `skewed_neg` and `all_neg`, this PR passes all 6.

- `pytest tests/kernels/moe/test_moe.py -k marlin`: 305 passed, 6 skipped (includes 54 `test_fused_marlin_moe` cases with int8 activations).

Symmetric is the AutoRound default.
- 50.4% of its group scales are negative, matching the report in #59403. No tensor hits the overflow or all negative cases.
- GSM8K, full test set (1319 questions), 5-shot, greedy, via `tests/evals/gsm8k/gsm8k_eval.py::evaluate_gsm8k_offline`:

| W4A8, #48926 + this PR | 74.0% | 0.0% |

- For this checkpoint the end to end fix comes from #48926. The 1.1 point gap between the last two rows is within GSM8K noise and should not be read as an improvement. This PR covers the skewed and all negative cases, which the unit tests exercise but this checkpoint does not hit.

## Details

Root cause, Python half: `marlin_act_int8_process_scales` computed `s / s.max() * 4096` before the int16 cast. `max()` only bounds the positive side. A negative scale more than 8x the largest positive one lands below -32768 and wraps. If all scales are negative, `max()` itself is negative and the ratios can be arbitrarily large. `abs().max()` bounds both sides by construction.

Root cause, kernel half: the `kS8` branch reads these int16 values as `uint16_t`. That is #48926 and is not repeated here.

Landing order: land with or after #48926, never before. On a kernel that still reads `uint16`, `abs().max()` keeps all negative scales negative, which turns the accidental all negative pass above into a failure.

Tests:
- `test_marlin_gemm` and `test_fused_marlin_moe` now call `marlin_act_int8_process_scales` instead of copying the old `max()` normalization inline. Those inline copies plus always positive scales from `marlin_quantize` are why existing tests never caught this.
- The GPU test builds negative scales by scaling whole rows of `marlin_s` together with the matching `w_ref` rows. The marlin scale permutation only reorders within a row, so the reference stays exact.

Limitation: when negative and positive scales differ a lot in magnitude (the `skewed_neg` case), the smaller scales get fewer int16 levels. This is inherent to the 4096 normalization and well within the existing test tolerance.
