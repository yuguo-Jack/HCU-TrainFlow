# [ROCm][Kimi-K3] Enable encoder graph capture for Kimi-K3 Vision Tower

[Upstream PR](https://github.com/vllm-project/vllm/pull/63086) · state: open · merged: False

## Original PR description

## Overview

Implements `SupportsEncoderCudaGraph` for `KimiK3ForConditionalGeneration` on AMD ROCm (MI355X), so the Kimi-K3 vision tower (`MoonViT3dPretrainedModel` + `KimiK25MultiModalProjector`) can be replayed from captured graphs via `cudagraph_mm_encoder=True`.

An earlier revision of this PR also added `torch.compile` for the vision tower (`compile_mm_encoder`). That part was dropped after review (thanks @simondanielsson): profiling showed Inductor fuses only norms, residual adds and GELU (full tower 301 -> 275 kernels, about 1% of GPU time), because GEMMs, AITER FMHA and `packed_qk_rope` (about 94% of time) are opaque kernels. The gain comes from graph replay, not fusion.

Related PRs and why this is not a duplicate:

- #53011: avoids eager `torch.compile` in the Kimi K2.5 vision helper (bugfix, not encoder cudagraphs).
- #44394 and #56820: add encoder CUDA graph support for other models (PaddleOCR-VL, Ling-3.0-flash-VL) on the same `SupportsEncoderCudaGraph` interface. This PR only implements the interface for Kimi-K3.

No other open PR implements `SupportsEncoderCudaGraph` for Kimi-K3. 

## Changes

- `vllm/models/kimi_k3/amd/model.py`: `SupportsEncoderCudaGraph` (item specs, item selection, capture inputs, replay buffers, graph and eager forwards). Auto-inferred budgets are capped at 512 tokens; larger inputs use the existing eager path of `EncoderCudaGraphManager`. See [discussion](https://github.com/vllm-project/vllm/pull/63086#discussion_r4440377966) .
- `tests/models/multimodal/generation/test_vit_cudagraph.py`: test correctness of graph-vs-eager and token cap limit

The feature is opt-in (`cudagraph_mm_encoder`, default off); default behavior is unchanged.

## Validation

### Encoder-level profile (MI355X, full vision tower, 512x512 image)

Wall time per encoder call: eager 7.1 ms, cudagraph replay 4.5 ms. The kernel list is identical; the gain is removed launch overhead and idle gaps between small kernels, so it is largest for small images. Full traces and kernel breakdown: see the profiling section already posted in this description.

### Serving (MI355X, TP=8, 9-point sweep, 3 repetitions per configuration, default config)

A = eager vision tower. D = `cudagraph_mm_encoder=true` only, no manual overrides — budgets auto-infer to `[64, 128, 256, 512]`, i.e. just turning the flag on. Interleaved A/D/A/D/A/D, fresh server boot each. One point, `768x1024`, sits above the 512-token cap so it runs eagerly under D too — a neutral control for the cutoff.

Result: speedup visible both at the serving level and encoder profile.

Note on noise: each sweep point runs 96 prompts (3 reps = ~5h GPU compute), and only one point (256x256 @ conc=16, mean TTFT -13.35%) individually clears the noise band — every other point is inside noise on its own. That's expected: the vision tower runs once per prompt (one image per prompt), so it's a small slice of total request cost, and a clear per-call win in the encoder microbenchmark (7.1ms eager -> 4.5ms graphed) shows up as a small, only-geomean-resolvable gain at the serving level. The geomean (not any single point) is the evidence for a real effect.

| metric | D vs A (geomean) | noise floor |
|---|---|---|
| Mean TTFT | -3.92% ± 1.60 | ≤4.0%/point — reliable |
| Median TTFT | -0.87% ± 5.39 | up to 25%/point — directional only |
| Throughput | +3.12% ± 1.85 | ≤7.7%/point |
| TPOT | -2.83%/-2.11% | expected flat; within noise, decode path untouched |

Above-cap control (`768x1024`, eager under D): throughput +2.71%, mean TTFT +3.30% — flat/noisy as expected, confirms traffic above the cutoff isn't regressed.

## Scope and limitations

- ROCm only; the NVIDIA model is unchanged. Deduplicating the encoder-graph methods between `amd/model.py` and `nvidia/model.py` into a common mixin is planned as a follow-up PR once this merges.
- Default auto-inferred budgets are capped at 512 tokens; larger inputs run eagerly. See [discussion](https://github.com/vllm-project/vllm/pull/63086#discussion_r4440377966)
- Serving statistics: 3 repetitions on a single node, 96 prompts/point (32 at conc=1/4, 256 at conc=64), fixed seeds per point. Geomean deltas are reliable (stdev ≤1.9%); per-point deltas are noisier — below ~4% for mean TTFT, ~8% for throughput/TPOT, ~25% for median TTFT isn't distinguishable from noise. The vision tower runs once per prompt, so a real per-call improvement is a small fraction of total request time and only resolves at the geomean level, not per point.

## Profiling the vision tower: eager vs `torch.compile` vs encoder cudagraph

Setup: one MI350X, bf16, random weights, full Kimi-K3 vision tower (patch embed + 27 layers + merge), single image, B=1, 20 iterations per mode, `torch.profiler` (CPU+CUDA). All four modes run the same encoder-metadata path, so the only differences are compile and graph replay. Cudagraph was captured manually with `torch.cuda.CUDAGraph`. Wall time is the average over back-to-back iterations; "GPU busy" is the summed kernel time.

| input | tokens | mode | wall us | GPU busy us | kernels |
|---|---|---|---|---|---|
| 512x512 | 1296 | eager | 7115 | 4605 | 301 |
| 512x512 | 1296 | compile | 6763 | 4553 | 275 |
| 512x512 | 1296 | cudagraph | 4485 | 4560 | 301 |
| 512x512 | 1296 | compile+cudagraph | 4471 | 4489 | 275 |
| 768x1024 | 4144 | eager | 11318 | 11317 | 301 |
| 768x1024 | 4144 | compile | 11279 | 11302 | 275 |
| 768x1024 | 4144 | cudagraph | 11300 | 11234 | 299 |
| 768x1024 | 4144 | compile+cudagraph | 11273 | 11289 | 274 |

Outputs match eager (cosine >= 0.99998 in all modes).

**Per-layer kernel list (one `MoonViTEncoderLayer`, 4144 tokens).** Which operators get fused:

| Eager (11 kernels, 318.8 us) | Compiled (10 kernels, 316.4 us) |
|---|---|
| AITer FMHA, 104.9 us | AITer FMHA, 105.3 us |
| 4 GEMMs, 157.2 us | 4 GEMMs, 157.3 us |
| `packed_qk_rope`, 14.9 us | `packed_qk_rope`, 14.6 us |
| 2x layer-norm, 19.1 us | `triton_per_fused_rms_norm` 7.2 us + `triton_per_fused_rms_norm_add` 7.8 us |
| GELU, 11.9 us | `triton_poi_fused_gelu` 17.4 us |
| 2x residual add, 10.8 us | `triton_poi_fused_add` 6.7 us |

(`profile_layer_fusion.py`, `layer_fusion.json`.) GELU is not fused into a GEMM epilogue because the GEMMs are external library kernels.

**What compile changes.** Kernel count drops 301 -> 275. Inductor fuses only the norm / add / GELU / elementwise work (about 140 small kernels become about 110 Triton kernels). GEMMs (109), AITer FMHA (27) and `packed_qk_rope` (27) are opaque to Inductor and unchanged, and they are 83-87% of GPU time. GPU busy time moves by about 1% (4605 -> 4553 us, 11317 -> 11302 us).

**What cudagraph changes.** Same kernels, no launch gaps. At 512x512 the tower is launch-bound in eager (7.1 ms wall for 4.6 ms of GPU work); replay brings wall to 4.5 ms (-37%). At 768x1024 the GPU is already saturated (wall = GPU time), so graphs give nothing for a single image, consistent with the neutral large-image serving points.

**Serving (TP=8, MI355X, 3 reps, paired):** compile only is neutral (throughput +0.11% +/- 0.72%, TPOT +0.03% +/- 0.87%, TTFT -0.27% +/- 1.25%). Cudagraph + compile at 512x512 conc=16: throughput +3.4%, TPOT -3.4%, TTFT -2.4%.

**Reading.** In this tower the benefit comes from the encoder cudagraph; compile contributes a few percent of wall time only where the tower is launch-bound, and that is also what cudagraph removes. I will drop the `torch.compile` part of this PR.

## Evidence for `_MAX_ENCODER_CUDAGRAPH_TOKEN_BUDGET` (now 512)

Replying to the question on `amd/model.py:73`. The original value (1040) was a based on earlier serving benchmarks, not a measured crossover, so I measured it and lowered it to 512 in the latest commit. Data below.

### What was measured
Vision tower only (no projector), one MI350X, bf16, random weights, image `vllm/vllm-openai-rocm:nightly-335dd77b09...` with this PR's two model files. A small script emulates `EncoderCudaGraphManager`: one graph per token budget, captured on `max_batch_size` padded items; replay copies the real batch into the static buffers and always computes the full padded budget; a batch uses the smallest budget that holds its output tokens. Budgets are in post-merge encoder output tokens (1 token = 4 patches). Times are medians (7 blocks x 20 iterations), eager = forward with metadata prepared outside the loop, replay = after copying the batch into the graph buffers. Re-runs agreed within 1-2%.

Three budget sets were compared:
- **A**: `[768, 1040]`, 2 items per graph (what the serving A/D sweep in this PR used).
- **B**: the auto-inferred default with a 1040 cap: `[64, 128, 256, 512, 1024, 1040]`, 16 items.
- **C**: the new default with a 512 cap: `[64, 128, 256, 512]`, 8 items (`min(512 // 64, 64)`).

```python
"""Eager vs padded budget-graph replay for the Kimi-K3 vision tower (tower only,
no projector), emulating EncoderCudaGraphManager: graphs are captured per token
budget with max_batch_size items and replay always computes the full padded budget.

Part 1: latency sweep (real batch -> smallest budget >= its output tokens).
Part 2: memory cost per captured budget (shared graph pool, ascending budgets).
"""

import argparse
import json
import math
import os
import tempfile

import torch

from vllm.config import CompilationConfig, VllmConfig, set_current_vllm_config
from vllm.distributed import (
    destroy_distributed_environment,
    destroy_model_parallel,
    init_distributed_environment,
    initialize_model_parallel,
)
from vllm.model_executor.models.kimi_k25_vit import MoonViT3dPretrainedModel
from vllm.transformers_utils.configs.kimi_k3 import KimiK3VisionConfig

KH = KW = 2
MAX_BATCH = 2
SERVING_BUDGETS = [768, 1040]
EXTRA_BUDGETS = [2080, 4160]
MULTI_ITEM_CASES = [(4, 256), (4, 1024), (8, 512), (16, 1024)]
SINGLE_TOKENS = [64, 144, 256, 324, 484, 576, 768, 900, 1036, 2080, 4160]
PAIR_TOKENS = [128, 324, 648, 968, 2080]  # total output tokens, split in 2 items
DEV = torch.device("cuda")


EXACT_GRIDS = {1036: [1, 56, 74]}


def grid_for(out_tokens):
    if out_tokens in EXACT_GRIDS:
        g = EXACT_GRIDS[out_tokens]
        return g, g[1] // KH * (g[2] // KW)
    ow = math.ceil(math.sqrt(out_tokens))
    oh = math.ceil(out_tokens / ow)
    return [1, oh * KH, ow * KW], oh * ow


def capture_grids(budget):
    return [grid_for(math.ceil(budget / MAX_BATCH))[0] for _ in range(MAX_BATCH)]


def timeit(fn, iters, repeats=7):
    for _ in range(20):
        fn()
    torch.cuda.synchronize()
    times = []
    for _ in range(repeats):
        s, e = torch.cuda.Event(enable_timing=True), torch.cuda.Event(enable_timing=True)
        s.record()
        for _ in range(iters):
            fn()
        e.record()
        torch.cuda.synchronize()
        times.append(s.elapsed_time(e) * 1000 / iters)
    return sorted(times)[len(times) // 2]


def patches(grids):
    return sum(t * h * w for t, h, w in grids)


def capture(model, budget, pool):
    grids = capture_grids(budget)
    px = torch.zeros(patches(grids), 3, 14, 14, device=DEV)
    meta = model.prepare_encoder_cudagraph_metadata(
        grids,
        max_batch_size=MAX_BATCH,
        max_seqlen_override=max(budget * KH * KW, max(t * h * w for t, h, w in grids)),
        device=DEV,
    )
    for _ in range(3):
        model(px, None, encoder_metadata=meta)
    torch.cuda.synchronize()
    g = torch.cuda.CUDAGraph()
    with torch.cuda.graph(g, pool=pool):
        out = model(px, None, encoder_metadata=meta)
    return {"graph": g, "px": px, "meta": meta, "out": out}


def main():
    global MAX_BATCH
    ap = argparse.ArgumentParser()
    ap.add_argument("--iters", type=int, default=20)
    ap.add_argument("--out", default="/work/cudagraph_threshold.json")
    ap.add_argument("--budgets", type=int, nargs="+", default=SERVING_BUDGETS)
    ap.add_argument("--extra-budgets", type=int, nargs="*", default=EXTRA_BUDGETS)
    ap.add_argument("--max-batch", type=int, default=MAX_BATCH)
    args = ap.parse_args()
    MAX_BATCH = args.max_batch

    cfg = VllmConfig(compilation_config=CompilationConfig(compile_mm_encoder=False))
    v_cfg = KimiK3VisionConfig()
    fd, tmp = tempfile.mkstemp()
    os.close(fd)
    torch.set_default_dtype(torch.bfloat16)
    with set_current_vllm_config(cfg):
        init_distributed_environment(
            world_size=1,
            rank=0,
            distributed_init_method=f"file://{tmp}",
            local_rank=0,
            backend="nccl",
        )
        initialize_model_parallel(1, 1)
        torch.manual_seed(0)
        model = MoonViT3dPretrainedModel(v_cfg).to(device=DEV, dtype=torch.bfloat16)
    model.eval()
    for p in model.parameters():
        p.data.normal_(0.0, 0.02) if p.ndim >= 2 else p.data.fill_(0.01)

    results = {"memory": [], "latency": []}
    with set_current_vllm_config(cfg), torch.inference_mode():
        # Part 2 + capture: ascending budgets in one shared pool, like the manager.
        pool = torch.cuda.graph_pool_handle()
        graphs = {}
        torch.cuda.synchronize()
        torch.cuda.empty_cache()
        free0 = torch.cuda.mem_get_info()[0]
        prev_free = free0
        for b in args.budgets + args.extra_budgets:
            torch.cuda.empty_cache()
            graphs[b] = capture(model, b, pool)
            torch.cuda.synchronize()
            torch.cuda.empty_cache()
            free = torch.cuda.mem_get_info()[0]
            row = {
                "budget": b,
                "incremental_mib": (prev_free - free) / 2**20,
                "cumulative_mib": (free0 - free) / 2**20,
            }
            prev_free = free
            results["memory"].append(row)
            print("memory", row, flush=True)

        # Part 1: latency.
        def run_case(name, out_grids):
            tokens = sum(h // KH * (w // KW) for _, h, w in out_grids)
            px = torch.randn(patches(out_grids), 3, 14, 14, device=DEV)
            meta_e = model.prepare_encoder_cudagraph_metadata(
                out_grids, max_batch_size=None, device=DEV
            )
            eager_gpu = timeit(lambda: model(px, None, encoder_metadata=meta_e), args.iters)

            def eager_e2e():
                m = model.prepare_encoder_cudagraph_metadata(
                    out_grids, max_batch_size=None, device=DEV
                )
                model(px, None, encoder_metadata=m)

            eager_e2e_us = timeit(eager_e2e, args.iters)
            row = {
                "case": name,
                "items": len(out_grids),
                "output_tokens": tokens,
                "eager_gpu_us": eager_gpu,
                "eager_e2e_us": eager_e2e_us,
            }
            budget = next((b for b in sorted(graphs) if b >= tokens), None)
            if budget is not None and len(out_grids) <= MAX_BATCH:
                gi = graphs[budget]

                def prep():
                    return model.prepare_encoder_cudagraph_metadata(
                        out_grids, max_batch_size=MAX_BATCH, device=DEV
                    )

                def copy_in(m):
                    for k, buf in gi["meta"].items():
                        src = m.get(k)
                        if buf is None or src is None:
                            continue
                        if src.ndim == 0:
                            buf.copy_(src)
                        else:
                            buf.zero_()
                            buf[: src.shape[0]].copy_(src)
                    gi["px"].zero_()
                    gi["px"][: px.shape[0]].copy_(px)

                def graph_e2e():
                    copy_in(prep())
                    gi["graph"].replay()

                m0 = prep()
                copy_in(m0)
                row["prepare_padded_us"] = timeit(prep, args.iters)
                row["copy_in_us"] = timeit(lambda: copy_in(m0), args.iters)
                row["prepare_eager_us"] = timeit(
                    lambda: model.prepare_encoder_cudagraph_metadata(
                        out_grids, max_batch_size=None, device=DEV
                    ),
                    args.iters,
                )
                row["budget"] = budget
                row["graph_replay_us"] = timeit(gi["graph"].replay, args.iters)
                row["graph_e2e_us"] = timeit(graph_e2e, args.iters)
                row["in_serving_range"] = budget in args.budgets
            results["latency"].append(row)
            print(row, flush=True)

        for n in SINGLE_TOKENS:
            run_case(f"single_{n}", [grid_for(n)[0]])
        for n in PAIR_TOKENS:
            g = grid_for(math.ceil(n / 2))[0]
            run_case(f"pair_{n}", [g, g])
        for k, n in MULTI_ITEM_CASES:
            if k <= MAX_BATCH:
                g = grid_for(math.ceil(n / k))[0]
                run_case(f"items{k}_{n}", [g] * k)

    with open(args.out, "w") as f:
        json.dump(results, f, indent=1)
    print("wrote", args.out)
    destroy_model_parallel()
    destroy_distributed_environment()
    if os.path.exists(tmp):
        os.unlink(tmp)


if __name__ == "__main__":
    main()
```

It follows the same convention as Qwen3-VL (`qwen3_vl.py`): the smallest realistic input. A 224x224 image is 16x16 patches at patch size 14, which is 8x8 = 64 tokens after the 2x2 merge, and K3 has the same patch size and merge. I added a comment saying so.

Smaller items are not excluded: anything up to 64 tokens replays the 64-token graph, padded. I measured whether a lower minimum would be worth it (tower only, MI350X, bf16, single item, eager vs replay):

| output tokens | graph used | eager (ms) | replay (ms) | replay / eager |
|---|---|---|---|---|
| 16 | 16 | 6.2 | 1.48 | 0.24 |
| 36 | 64 | 6.4 | 2.24 | 0.35 |
| 49 | 64 | 6.4 | 2.25 | 0.35 |
| 64 | 64 | 6.4 | 2.28 | 0.35 |

So the 64 graph already gives about 0.35x of eager for every item from 17 to 64 tokens. A smaller graph would save about 0.8 ms more but adds about 0.18 GiB in my measurement (1.87 vs 1.69 GiB total. More memory used is away from KV cache so would I prefer not change it for a gain this small.

Data: same script as the cap data, with budgets 16/32/64/128/256/512; tower only, emulated manager, single GPU.

Ran the cap=1024 e2e probe (2 reps, same candidate image as the main D sweep, `encoder_cudagraph_token_budgets` overridden to `[64,128,256,512,1024]`). `768x768` (~752 tokens) is the point that's eager under cap=512 but should graph under cap=1024; `1024x1024` (~1337 tokens) is the above-cap eager control; `512x512` and `768x1024` are anchors shared with the main sweep.

| point | conc=1 | conc=16 |
|---|---|---|
| 768x768 | 34 hits / 0 miss | 128 hits / 0 miss |
| 1024x1024 | 0 hits / 34 miss | 0 hits / 128 miss |

So the probe tested what it was supposed to: `768x768` ran graphed, `1024x1024` ran eager.

Deltas vs eager (cap=1024 vs eager, 2 reps):

| point | mean TTFT delta |
|---|---|
