# [Bugfix][Kimi-K3] Fall back from the latent-MoE tail fusion under sleep mode

[Upstream PR](https://github.com/vllm-project/vllm/pull/64583) · state: closed · merged: True

## Original PR description



## Overview

On SM100 at TP 8 or 16, `LatentMoERunner` raises `ValueError: K3 latent-MoE tail fusion does not support sleep mode.` when `--enable-sleep-mode` is set, so Kimi-K3 cannot start with sleep mode, which the process checkpoint lifecycle (#62570) requires. The runner now falls back to the default latent-MoE path with a warning, as it already does for unsupported TP sizes. No open PR or issue addresses the sleep-mode raise. #64276 and #65582 change the same block; whichever merges later needs a rebase.

## Claims

- Kimi-K3 starts with `--enable-sleep-mode` on SM100 at TP 8 and 16, on the default latent-MoE path.
- Without sleep mode nothing changes, and DBO or ubatching with the tail fusion still raises.

## Validation

- The new `test_sleep_mode_falls_back_to_default_path` fails on main and passes with this change. Both tests build the runner with the file's existing stand-ins and need no GPU. A regression test through `LLM` needs Kimi-K3 on 8 B300s, which CI does not have, so the end-to-end run below is the validation outside CI.

- `pre-commit run` on the changed files passes.
- End to end on vLLM 0.31.0 with an equivalent local change (the tail fusion turned off whenever sleep mode is on), on 8x B300: `nvidia/Kimi-K3-NVFP4` at TP 8 and DCP 8 with sleep mode, captured and restored with ai-dynamo/snapshot. Without the change the engine raised the error above at startup. With it, a restored replica returned the same text as a cold replica running the tail fusion, with per-token logprobs 0.01-0.09 apart, and served 861 requests at 48 concurrent with no errors. This exact diff has not been run end to end.

## Details

**Why fall back.** The raise came in with the runner without a stated reason. On the same GPUs the K3 specialized decode already treats sleep mode as a reason to run the stock forward (`specialized_decode/runtime/__init__.py`), and the TP-size check just above falls back with a warning. Sleep mode now does the same, before the tail op is initialized.

**Tradeoff.** Under sleep mode Kimi-K3 loses the tail fusion's speedup, which we have not measured. Making the tail fusion work across sleep and wake is out of scope.

- aoshen02 · comment · 2026-11-04T15:15:50Z · [source](https://github.com/vllm-project/vllm/pull/64583#issuecomment-6634350280)

For context on why the tail fusion and checkpointing conflict: `fused_add_multicast_gemm.py` allocates its Lamport mailbox with `symm_mem.empty` + `symm_mem.rendezvous` and uses the NVLink `multicast_ptr`. PyTorch symmetric memory keeps the multicast object and the peer imports for the buffer's lifetime. A live multicast object hangs `cuCheckpointProcessCheckpoint`, even unbound and unmapped, and a held peer import makes `cuCheckpointProcessRestore` fail.

Plain sleep without a checkpoint probably doesn't need the fallback: the mailbox stays resident and keeps its addresses. I haven't verified that for K3. If it holds, the fallback could be limited to the checkpoint paths, so RL users on plain sleep keep the fusion.

To keep the fusion under checkpoint as well, the mailbox can be allocated as a vLLM-owned cuMem buffer that releases the multicast object and peer imports on suspend, keeps the virtual addresses, and rebinds them at the same addresses on resume. CUDA graphs keep their pointers. That is what aoshen02/vllm#239 (`VmmSymmetricBuffer`, `CudaCommunicator.allocate_symmetric_buffer()`) does for DeepSeek-V4.1's AllReduceMHC, which has the same Lamport mailbox + multicast layout. On GB300, TP4 under the checkpoint executor ran 3 sleep/wake cycles with all driver calls returning 0. Mean TPOT at c=1 was 4.20 ms, against 4.26 ms for the default configuration. The K3 change would be the mailbox allocation in `fused_add_multicast_gemm.py`.

So this PR works as a stopgap, and the tail fusion could later move to the suspendable buffer.
