# [Perf][Core] Add sha256_int32 prefix-cache hash over int32 token buffers

[Upstream PR](https://github.com/vllm-project/vllm/pull/63454) · state: open · merged: False

## Original PR description



## Overview

Add an opt-in prefix-cache hash algorithm, `--prefix-caching-hash-algo sha256_int32`, that hashes each block's token ids as raw int32 bytes, reading the request's int32 token buffer in place instead of pickling one Python int per token. Stacked on #62702 (requests keep token ids in an int32 `TokenBuffer`); only the last commit belongs to this PR.

## Claims

- Block hashing of a new 135K-token request (CPU, real `Request`): 4.50 -> 1.02 ms with 256-token hash blocks, 7.72 -> 2.90 ms with 64-token blocks.
- P/D decode instance of DeepSeek-V4.1-Flash (DEP8, B200): the engine input thread spends 18.3 -> 10.6 ms per new request while holding the GIL the engine loop needs, so decode runs faster per user (table below).
- The default (`sha256`) and its hashes are unchanged. `sha256_int32` hashes differ from `sha256`, so instances that share a prefix cache or KV store must use the same algorithm.

## Validation

```bash
pytest tests/v1/core/test_kv_cache_utils.py tests/v1/test_request.py \
  tests/v1/core/prefix_cache/test_partial_prefix_cache_primitives.py
```

101 passed (3 new: `sha256_int32` cases of the existing block-hash tests, which compare the in-place buffer path with hashing the token tuple, with multimodal extra keys and with tokens appended after hashing). The same 17 KV-cache-layout tests fail on #62702 without this PR (offline image environment).

End to end: DeepSeek-V4.1-Flash 2P1D on 16x B200 (prefill 2x DEP4, decode DEP8, NIXL, Mooncake store on prefill), AgentX traces (~130K-token prompts) at 2,048 concurrent sessions, MRV2, 30 minutes per arm. Only the decode instance changed, using int32 token storage like #62702 and a prototype of this hashing:

| decode instance | sha256 | sha256_int32 |
|---|---|---|
| input thread per new request | 18.3 ms | 10.6 ms |
| ITL p50 | 9.2 ms | 8.4 ms |
| per-user tok/s p10 / p50 | 99 / 108 | 107 / 119 |
| output tok/s per GPU | 4,900 | 5,008 |
| TTFT p50 | 1.83 s | 1.84 s |

Prefix-cache hit rate unchanged (96.5%). Separate runs, not interleaved.

## Details

- Block input: SHA-256 over the parent hash, the token count (8 bytes), the token ids as int32 in native byte order, and the pickled extra keys if any. Token sequences that are not buffers (other callers of `hash_block_tokens`) are converted with `array("i", ...)` and give the same hash. The `NONE_HASH` seed is hashed as with `sha256`.
- `get_request_block_hasher` takes a memoryview of `request._all_token_ids` only for this algorithm and releases it before returning, since an exported array cannot grow.
- Opt-in rather than a new default: `sha256` hashes are shared across processes (deterministic `NONE_HASH` seed) by KV stores and the P2P tier, so changing them silently would split caches across versions.
- Related: #43789 adds MessagePack variants, which still encode one Python int per token.
- AI assistance (Claude Code) was used to find, write and validate this change.
