# [Bugfix] Reject mismatched float16/bfloat16 kv_cache_dtype with model dtype

[Upstream PR](https://github.com/vllm-project/vllm/pull/61450) · state: closed · merged: False

## Original PR description

## Issue

Fixes #61314 (and #60859 on the same code path).

A `bfloat16` checkpoint with an explicit `kv_cache_dtype="float16"` (or the
reverse pair) crashes during CUDA-graph capture on the FlashAttention and
FlashInfer backends because those kernels require query and key tensors to
share a dtype. Quantized linear layers (`quantization="fp8"`) do not change
the attention query dtype, so the crash happens identically on the online
fp8 quantization path reported in #61314.

## What this PR does

Add a config-level check in `VllmConfig.__post_init__` that rejects any
unquantized `float16`/`bfloat16` `kv_cache_dtype` that does not match the
checkpoint dtype, before the attention backend is selected or CUDA-graph
capture runs. The error is a descriptive `ValueError` with a hint to use
`auto` or the matching dtype.

Quantized KV cache dtypes (`fp8`, `fp8_e4m3`, `nvfp4`, `*_per_token_head`, …)
are intentionally left alone — they have their own per-backend support checks
and a different failure mode. `auto` is also skipped because it resolves to
the model dtype.

## Root cause

FlashAttention `mha_varlen_fwd` asserts `query and key must have the same dtype`.
The engine accepted the mismatched pair until backend selection or graph
capture, which is late for a user-facing configuration error. This check runs
right after `try_verify_and_update_config()`, so model hooks (e.g. DeepSeek
V3.2 rewriting an explicit `bfloat16` cache to `auto`) still run first.

## Validation

```bash
.venv/bin/python -m pytest tests/test_config.py::test_post_init_rejects_mismatched_float_kv_cache -q
```

Tested cases:
- Rejects `float16` KV with `bfloat16`, `float16` with `float32` model dtypes
- Accepts matching dtypes (`float16`+`float16`, `bfloat16`+`bfloat16`)
- Accepts `auto` and quantized KV dtypes (`fp8`) regardless of model dtype

End-to-end `LLM.generate` was not run (this sandbox has no CUDA GPU).

## Not a duplicate of existing open PRs

#60885 and #60951 both address #60859 on the same plain-dtype path. This PR
reuses the same fix shape (`_reject_mismatched_float_kv_cache` in
`VllmConfig.__post_init__`) and additionally frames it as also covering the
online fp8 quantization crash reported in #61314 — the same underlying issue
because quantized linear layers do not affect attention query dtype. If one
of the existing PRs lands first, the overlapping hunks will merge cleanly.
