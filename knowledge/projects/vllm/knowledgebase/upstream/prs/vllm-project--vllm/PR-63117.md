# [Bugfix][ROCm] Take the AITER MLA KV cache dtype from the group's spec

[Upstream PR](https://github.com/vllm-project/vllm/pull/63117) · state: open · merged: False

## Original PR description

## Overview

`AiterMLAMetadataBuilder` takes the KV cache dtype from the global `cache_config.cache_dtype`, but a KV cache group can use another dtype. With a speculative draft that sets its own `kv_cache_dtype`, the target model runner still builds the draft groups' metadata with the target's config, and DSpark and DFlash draft prefill reuses it. `kv_cache_dtype_skip_layers` keeps some MLA layers in bf16 under a global fp8 cache. This PR takes the dtype from the group's spec.

This was reported and approved in #55591, which its author closed without merging.

Found by Hyperloom.

## Claims

- A bf16 draft under an fp8 target gets bf16 decode metadata in draft prefill. On main, the metadata it reuses from the target runner is built for fp8. The draft's own decode builders already use the draft dtype since #63251.
- A layer in `kv_cache_dtype_skip_layers` gets bf16 decode under an fp8 cache; on main it gets fp8.
- A bf16 target with an fp8 draft KV cache no longer fails at startup with `KeyError: torch.uint8`.
- No change when every group uses the global dtype.

## Validation

Kimi-K3 truncated to 8 layers (`--hf-overrides`, `--load-format dummy`), TP4, CUDA graphs on, 24 concurrent requests, on the vLLM ROCm nightly image built from main at 40941f2c4b, with a debug hook (not part of this PR) that logs each AITER MLA builder's decode dtype and how often it builds metadata:

| Case | Builder | main | this PR |
|---|---|---|---|
| fp8 target, bf16 DSpark draft, 2 and 7 draft tokens | target runner, draft layers (reused by draft prefill, 100+ builds) | fp8 | bf16 |
| | speculator, draft layers | bf16 | bf16 |
| bf16 target, fp8 DSpark draft, 7 draft tokens | target runner, draft layers | fails at startup: `KeyError: torch.uint8` | fp8, serves |
| `--kv-cache-dtype fp8 --kv-cache-dtype-skip-layers 3` | layer 3, bf16 cache (100+ builds) | fp8 | bf16 |

The `KeyError` also reproduces with the stock nightly vLLM. All other runs start and serve requests; since #63251, main no longer fails at startup with 2 draft tokens.

Dummy weights cannot show wrong attention, so each side's metadata plan was checked against aiter directly on the same image (aiter 0.1.27): bf16 Q and KV cache, 16 heads, 32 requests, max abs error against a PyTorch reference. Draft prefill is causal, at the target's verify length (draft tokens + 1):

Kimi-Linear-48B-A3B, TP1, `--kv-cache-dtype fp8 --kv-cache-dtype-skip-layers 3 4 11 12`, measured at 15a78aa88e before #63116 (which does not change this config). A builder dump shows the skipped MLA group set up as fp8 on main and bf16 with this PR. GSM8K, 5-shot, greedy, 1319 items, shows no measurable change:

Unit tests on the same nightly image, `pytest tests/v1/attention/test_rocm_aiter_mla_mtp_split.py`: this PR 75 passed; main fails `draft-bf16-kv-under-fp8-target`, `draft-fp8-kv-under-bf16-target` and `skip-layer-bf16-kv`.

## Details

The builder already reads `kv_cache_spec.cache_dtype_str` for fused DCP prefill; this PR uses the same value for the segmented DCP verify LDS check and the decode setup. The existing `bf16-group` case of `test_builder_init_sizes_decode_metadata_and_filters_dcp_maps` asserted the fp8 decode setup for a bf16 group; it is now one of the cases above and expects the group's dtype. On main, rejection sampling keeps the served output correct; the mismatch only affects the draft.

CI does not run a DSpark draft on MI355X. Kimi-Linear scores 0.88 on GSM8K with a bf16 KV cache and 0.36 with an fp8 KV cache on main; that gap is unrelated to this PR.

- BaoYunkai · comment · 2026-11-04T11:16:42Z · [source](https://github.com/vllm-project/vllm/pull/63117#issuecomment-6629230755)

Both, depending on the direction:

1. **Crash.** A bf16 target with an fp8 draft KV cache fails at startup on main: the target model runner builds the AITER MLA builders for every KV cache group with the target's config, so the draft's fp8 group (`torch.uint8` storage) takes the bf16 path and raises `KeyError: torch.uint8`. Reproduced on the stock nightly image (main at 40941f2c4b), 4x MI355X, with the same truncated target and draft as in #63116:

```bash
VLLM_ROCM_USE_AITER=1 vllm serve moonshotai/Kimi-K3 \
  --trust-remote-code --load-format dummy \
  --tensor-parallel-size 4 --max-model-len 4096 \
  --hf-overrides '{"text_config": {"num_hidden_layers": 8, "linear_attn_config": {"full_attn_layers": [4, 8], "gate_lower_bound": -5.0, "head_dim": 128, "kda_layers": [1, 2, 3, 5, 6, 7], "num_heads": 96, "short_conv_kernel_size": 4, "use_full_rank_gate": true}}}' \
  --speculative-config '{"model": "/path/to/Kimi-K3-DSpark-trunc8", "method": "dspark", "num_speculative_tokens": 7, "attention_backend": "ROCM_AITER_MLA", "kv_cache_dtype": "fp8"}'
```

With this PR it starts and serves.

2. **Numerics.** An fp8 target with a bf16 draft starts fine, but DSpark draft prefill reuses the target's metadata, which is planned for fp8. On a bf16 cache that plan gives wrong attention at query lengths 5–7, i.e. 4–6 draft tokens. Calling aiter directly (16 heads, causal, 32 requests), the max abs error at lengths 5/6/7 is 3.66/3.71/4.32 with fp8-planned metadata vs 0.0006/0.04/0.18 with bf16-planned; lengths 2–4 and 8 match either way. Rejection sampling keeps the output correct, so this would show up as a lower acceptance rate rather than wrong text; I haven't measured acceptance with real weights.

3. With `kv_cache_dtype_skip_layers` and no speculative decoding, decode runs at query length 1, where both plans agree, so I don't expect an accuracy change there (Kimi-Linear GSM8K showed none).
