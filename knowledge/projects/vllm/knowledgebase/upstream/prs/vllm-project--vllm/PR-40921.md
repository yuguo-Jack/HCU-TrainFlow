# Bugfix: fix RMSNormGated input_guard torch.compile dynamo tracing on CUDA

[Upstream PR](https://github.com/vllm-project/vllm/pull/40921) · state: open · merged: False

## Original PR description




## Purpose

This PR  fixes  #40919  a startup dynamo failure when serving Qwen3.5

`vllm/model_executor/layers/fla/ops/utils.py::input_guard` currently uses:

```python
torch.accelerator.device_index(tensor.device.index)
```

On PyTorch 2.11, Dynamo cannot trace `device_index.__init__` in fullgraph mode, causing engine initialization to fail during the profiling run.

The fix keeps the generic accelerator path for non-CUDA devices (like tpu), but uses the original CUDA-specific context manager for CUDA tensors.

- izhuhaoran · comment · 2026-04-26T18:27:24Z · [source](https://github.com/vllm-project/vllm/pull/40921#issuecomment-4322699740)

@ZJY0516 

Update: I dug further and found this is not specific to backend="eager".

The key difference is the custom-op path. With backend="inductor", vLLM defaults most custom ops to disabled (`custom_ops` gets `none`), so `RMSNormGated` uses the native path. With backend="eager", custom ops default to enabled, so `RMSNormGated.forward_cuda()` is used and Dynamo traces into

```
 ctx = torch.accelerator.device_index(tensor.device.index)
 ```
 
That is what triggers the Dynamo skiplist error.

we can reproduce the same failure with backend="inductor" by explicitly enabling that custom op:

```
python -m vllm.entrypoints.cli.main serve Qwen/Qwen3.5-35B-A3B-FP8 --gpu-memory-utilization 0.9 --tensor-parallel-size 2 --max-num-seqs 512 --no-enable-prefix-caching --host 127.0.0.1 --port 8000 --no-async-scheduling --compilation-config='{"backend": "inductor", "cudagraph_mode": "FULL_AND_PIECEWISE", "custom_ops": ["+rms_norm_gated"]}' --speculative_config '{"method":"qwen3_next_mtp","num_speculative_tokens":2}'  --reasoning-parser qwen3 --language-model-only 
```

This fails at the same line with:

```
torch._dynamo.exc.Unsupported: Attempted to inline function marked as skipped
```

So the trigger is not the eager backend itself, but whether `rms_norm_gated` dispatches to the custom-op `forward_cuda` path. It's not a Pytorch's bug and default inductor command works because it avoids that path. 

So I think this PR is still needed, or any better ideas ?

The tracing issue with `torch.accelerator.device_index` likely affects all accelerator backends when using `torch.compile`. Since this module also supports XPU (Intel), it is recommended to generalize this fix to use the device-specific context manager for both CUDA and XPU. This ensures consistent behavior and avoids tracing failures on Intel platforms as well.

```suggestion
            if tensor.device.type in ("cuda", "xpu"):
                ctx = getattr(torch, tensor.device.type).device(tensor.device.index)
            else:
                ctx = torch.accelerator.device_index(tensor.device.index)
```
