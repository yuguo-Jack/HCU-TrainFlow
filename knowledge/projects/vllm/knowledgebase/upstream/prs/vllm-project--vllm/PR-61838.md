# [Perf][Model] Support torch.compile for the PaddleOCR-VL vision encoder

[Upstream PR](https://github.com/vllm-project/vllm/pull/61838) · state: open · merged: False

## Original PR description



## Overview

Adds `torch.compile` support for the PaddleOCR-VL vision encoder. `SiglipEncoderLayer` gets the `@support_torch_compile` decorator behind `compile_mm_encoder`, following Qwen2.5-VL, Qwen3-VL and Pixtral ([#57168](https://github.com/vllm-project/vllm/pull/57168)). Nothing changes unless `compile_mm_encoder=True`.

## Claims

- `compile_mm_encoder=True` compiles PaddleOCR-VL's 27 SigLIP encoder layers. The first layer compiles in about 4 s, the other 26 reuse it, and restarts load from the cache.
- With `vllm bench serve` on H100, throughput rises by 1.8–7.3% and mean TTFT falls by 3.3–9.8% at concurrency 1–256. The gain exceeds the trial-to-trial range at concurrency 64–256.
- On the full OmniDocBench recognition set, throughput rises by 1.4% and accuracy is unchanged within BF16 noise.

## Validation

Setup: H100, PaddleOCR-VL-1.6 (`c5630ab`) in BF16, base `2631afd3f`. Both versions use `-cc.mode=3 -cc.cudagraph_mode=FULL_DECODE_ONLY` and differ only in `-cc.compile_mm_encoder`.

**OmniDocBench recognition.** 19,251 regions from all 1,651 public pages, concurrency 64, prefix caching off, 32 warmup crops, one measured pass per version. The harness is the same as in [#61458](https://github.com/vllm-project/vllm/pull/61458).

| Metric | Compile off | Compile on |
| --- | ---: | ---: |
| Throughput, crops/s | 76.58 | 77.65  |
| EngineCore CPU time, ms/crop | 13.64 | 13.43 |
| Text NED ↓ | 0.015787 | 0.015652 |
| Formula NED ↓ | 0.062234 | 0.062199 |
| Table TEDS ↑ | 0.952008 | 0.951610 |


**`vllm bench serve` (random-mm).** The serve flags, bench flags, image mix and seeds for c=32–256 match #61458. c=1 and c=8 were added with 128 and 256 prompts. Each configuration ran 3 trials, alternating off and on per trial. Throughput is the mean, with min–max in parentheses; TTFT is the mean of the per-trial means. All 11,520 requests succeeded.

| Concurrency | Off req/s | On req/s | Gain | Mean TTFT off → on |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 7.35 (7.22–7.53) | 7.66 (7.40–7.80) | +4.2% | 50.8 → 45.8 ms (−9.8%) |
| 8 | 29.24 (28.05–30.19) | 29.93 (29.35–30.27) | +2.3% | 139.5 → 128.5 ms (−7.9%) |
| 32 | 49.35 (46.45–51.90) | 50.24 (47.57–52.24) | +1.8% | 312.7 → 299.1 ms (−4.3%) |
| 64 | 52.68 (50.61–55.00) | 56.52 (54.67–58.78) | +7.3% | 598.5 → 565.6 ms (−5.5%) |
| 128 | 56.64 (54.72–57.66) | 59.21 (58.52–60.05) | +4.5% | 1,118 → 1,065 ms (−4.8%) |
| 256 | 55.31 (54.06–56.30) | 58.68 (56.43–61.11) | +6.1% | 2,163 → 2,091 ms (−3.3%) |

P99 TTFT improved at c=1, 8, 32 and 128, and was slightly worse at c=64 (+2.2%) and c=256 (+0.6%). This sweep ran on an H100 shared with other jobs; alternating the variants spreads that interference across both.

**Outputs, TP and sync checks.** 32 text-image prompts, including one with two images, at temperature 0 with `VLLM_GPU_SYNC_CHECK=error`. Off and on outputs were identical for 32 of 32 prompts at both TP=1 and TP=2, and no syncs were flagged. At TP=2, the all-gather inside the attention layer compiles and runs correctly.

## Details

**Scope.** Only `SiglipEncoderLayer` is compiled; the layers account for nearly all encoder time. The patch embedding and projector contain per-image Python loops (position-embedding interpolation and the 2×2 merge `rearrange`), which would cause graph breaks or recompiles. `hidden_states` is `[1, num_patches, hidden]`, so its dynamic dimension is 1.

**Encoder-only speedup.** Measured by timing eager and compiled encoders alternately on the same scheduled batches:

| Batch | Eager | Compiled | Speedup |
| --- | ---: | ---: | ---: |
| 1 image, 192 tokens | 15.1 ms | 10.8 ms | 1.40× |
| 1 image, 609 tokens | 15.0 ms | 12.1 ms | 1.24× |
| 1 image, 2,160 tokens | 68.6 ms | 65.2 ms | 1.05× |
| 8 images, 3,794–5,021 tokens | 81.6–119.1 ms | 75.8–112.5 ms | 1.06–1.08× |



**Relation to other PRs.** [#44394](https://github.com/vllm-project/vllm/pull/44394) adds encoder CUDA graphs for PaddleOCR-VL. The two PRs are independent: this one does not touch the code paths #44394 changes, and it applies with or without encoder graphs. Running both together, where the encoder graphs would capture the compiled layers, is not covered here. No open or closed PR adds encoder compilation for PaddleOCR-VL.

<summary>Reproduction</summary>

Model: `PaddlePaddle/PaddleOCR-VL-1.6` @ `c5630abae1d940eafe0697512a0325494b02ab42`. Use the same commands for both variants, changing only `-cc.compile_mm_encoder`.

```bash
vllm serve "$MODEL_PATH" \
  --served-model-name paddleocr-vl --dtype bfloat16 \
  --host 127.0.0.1 --port 18356 \
  --max-model-len 16384 --max-num-seqs 512 \
  --max-num-batched-tokens 4096 --gpu-memory-utilization 0.18 \
  --kv-cache-memory-bytes 8589934592 --no-enable-prefix-caching \
  --mm-processor-cache-gb 4 --seed 42 \
  -cc.mode=3 -cc.cudagraph_mode=FULL_DECODE_ONLY \
  -cc.compile_mm_encoder=true   # or false
```

Synthetic benchmark. Seeds: c=1 → 1042–1044, c=8 → 1142–1144, c=32 → 42–44, c=64 → 142–144, c=128 → 242–244, c=256 → 342–344. Prompts and warmups: c=1 → 128/8, c=8 → 256/16, others → 512/32.

```bash
vllm bench serve \
  --backend openai-chat --base-url http://127.0.0.1:18356 \
  --endpoint /v1/chat/completions --model paddleocr-vl \
  --tokenizer "$MODEL_PATH" --dataset-name random-mm \
  --random-input-len 64 --random-output-len 64 --random-range-ratio 0 \
  --random-mm-base-items-per-request 1 \
  --random-mm-num-mm-items-range-ratio 0 \
  --random-mm-limit-mm-per-prompt '{"image": 1, "video": 0}' \
  --random-mm-bucket-config \
  '{(224, 224, 1): 0.25, (448, 896, 1): 0.25, (896, 448, 1): 0.25, (896, 896, 1): 0.25}' \
  --temperature 0 --ignore-eos --request-rate inf \
  --num-prompts "$NUM_PROMPTS" --num-warmups "$NUM_WARMUPS" \
  --max-concurrency "$CONCURRENCY" --seed "$SEED"
```

OmniDocBench uses the same dataset, revisions, crop extraction, prompts, token limits and scoring as #61458.
