# [ROCm][Quantization][MOE] Enable fused shared experts for MXFP8 checkpoints

[Upstream PR](https://github.com/vllm-project/vllm/pull/57916) · state: open · merged: False

## Original PR description

## Purpose
`is_shared_expert_quant_fse_compatible` only recognises `DeepseekV4FP8Config`, `QuarkConfig` and `Fp8Config`, and refuses everything else, so [MiniMax-M3-MXFP8](https://huggingface.co/MiniMaxAI/MiniMax-M3-MXFP8) (a `ModelOptMxFp8Config` checkpoint) hits the fallthrough and `VLLM_ROCM_USE_AITER_FUSION_SHARED_EXPERTS=1` is a no-op that only logs a warning. Shared-expert fusion was enabled for this exact model by #46545 (Jun 26) and worked until #51695 (Aug 18) introduced this refuse-by-default quantization gate, which silently turned it back off; CI missed it because `test_models_fse_init` covers `minimax_m3` but installs a `QuarkConfig`. 

This adds the missing `ModelOptMxFp8Config` branch: MXFP8 carries a single whole-model quant algo plus `exclude_modules` and no per-layer config, so consistent exclusion of routed and shared experts is exactly what guarantees the shared expert has the same weight format as the routed slot it is appended into. Partially excluded packed shards are already rejected by `is_layer_skipped`, and MXFP8 is always 1x32 block-scaled with a leading expert dimension on its scales.
## Test Plan
Serving A/B on MiniMax-M3-MXFP8, TP4 on MI355X, identical stack with and without the fix, to
show the now-reachable fused path is a win on throughput and neutral on quality: 8K/1K
throughput at concurrency 1/16/64, and gsm8k on the full 1319-doc test split, 5-shot.

## Test Result
`tests/model_executor/layers/test_fused_shared_expert.py`, run on MI355X in
`vllm/vllm-openai-rocm:nightly`:

| arm | result |
|---|---|
| unmodified `main` | 84 passed |
| new cases, unpatched `vllm` | 5 failed, all `shared-expert FSE quantization compatibility is not implemented for ModelOptMxFp8Config` |
| patched | 89 passed |

### Serving A/B

`MiniMaxAI/MiniMax-M3-MXFP8`, TP4 on MI355X, in `vllm/vllm-openai-rocm:nightly`
(image id `d65c1f85e583`, `vllm 0.3.1.dev190+g3df4ae153`). Both arms run the same image and
the same command below; the only difference is whether this patch is applied before the
server starts. Env for both arms:

```
VLLM_ROCM_USE_AITER=1
VLLM_ROCM_USE_AITER_FUSION_SHARED_EXPERTS=1
VLLM_ROCM_SHUFFLE_KV_CACHE_LAYOUT=1
VLLM_ROCM_QUICK_REDUCE_QUANTIZATION=INT4
```

```bash
vllm serve MiniMaxAI/MiniMax-M3-MXFP8 \
    --host 127.0.0.1 --port $PORT \
    --language-model-only \
    --tensor-parallel-size=4 \
    --max-model-len=131072 \
    --block-size=128 \
    --kv-cache-dtype=fp8 \
    --gpu-memory-utilization=0.85 \
    --max-num-seqs=64 \
    --max-num-batched-tokens=32768 \
    '--attention-config={"backend":"ROCM_AITER_FA","indexer_kv_dtype":"fp8"}' \
    --moe-backend=aiter \
    --no-enable-prefix-caching \
    '--compilation-config={"cudagraph_mode":"FULL_DECODE_ONLY","max_cudagraph_capture_size":512}'
```

Note that `VLLM_ROCM_USE_AITER_FUSION_SHARED_EXPERTS=1` is set in *both* arms; without the
patch it is simply ignored, which is the bug. The logs confirm the arms really differ:
unpatched emits 228 `not implemented for ModelOptMxFp8Config` refusals (57 MoE layers x 4
ranks) and builds the aiter MoE with `128, 4` experts, patched emits none and builds
`129, 5`, the extra slot being the fused shared expert.
