# [Bugfix][Frontend] Handle malformed Anthropic tool arguments

[Upstream PR](https://github.com/vllm-project/vllm/pull/57244) · state: open · merged: False

## Original PR description

## Overview

Stop non-streaming `/v1/messages` from failing when a tool call's arguments aren't a JSON object, e.g. a call cut off at `max_tokens`. Part of #48273.

## Claims

- Truncated, invalid or non-object arguments now become `input: {}` with a warning, instead of an HTTP 500.
- Empty arguments become `{}` without a warning.

## Validation

```bash
pytest -v tests/entrypoints/anthropic/test_anthropic_messages_conversion.py
```

129 passed. Without the fix the 6 new cases fail: `""` and truncated JSON raise `JSONDecodeError`, `[...]`, `42` and `true` fail pydantic validation of the content block, and `null` comes back as `input: null`. pre-commit passes on both files. CPU only, no model needed; not tested against a running server.

## Details

`messages_full_converter` calls `json.loads(tool_call.function.arguments)` without a guard, but tool parsers don't guarantee valid JSON there (`deepseekv31_tool_parser` passes a raw regex match through). The OpenAI route forwards `arguments` as a string, so only the Anthropic route has to decode it. Falling back to `{}` keeps the rest of the response. The warning logs the tool call id and name but not the arguments, which can contain prompt text.

#52519 makes the same change to the converter, together with an unrelated realtime STT fix. This PR maps non-object JSON to `{}` rather than `{"value": ...}`, which isn't part of the tool's schema. Happy to close this one if you'd rather go with #52519.
