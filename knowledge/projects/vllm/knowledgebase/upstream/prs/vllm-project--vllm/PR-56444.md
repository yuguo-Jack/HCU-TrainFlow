# [Bugfix][Qwen4Exp] Support N-gram PLE with pipeline parallelism

[Upstream PR](https://github.com/vllm-project/vllm/pull/56444) · state: open · merged: False

## Original PR description

## Overview

Carry raw Qwen4Exp PLE token IDs through pipeline-parallel intermediate tensors on NVIDIA and AMD. Fixes #55515.

## Claims

- Pipeline stages can receive PLE token IDs alongside hidden states when PLE is configured.
- Configurations without PLE retain the existing hidden-state-only tensor contract.
- The new backend-parametrized tests run in separate processes to avoid duplicate custom-op registration.

## Validation

- `uv run --no-project --python 3.12 python -m compileall -q tests/models/qwen4_exp/test_config.py vllm/models/qwen4_exp/amd/model.py vllm/models/qwen4_exp/nvidia/model.py`: passed locally.
- `git diff --check`: passed locally.
- `tests/models/qwen4_exp/test_config.py`: attempted locally; collection stopped on missing dependencies (first Pillow, then Pydantic in a temporary overlay). No test assertion ran. The reviewer ran the proposed process isolation locally and reported 15 passed.
- Ruff could not start locally because Windows Application Control blocked the executable.
- End-to-end Qwen4Exp PLE with pipeline parallelism: not run locally; the reported reproducer needs a three-GPU environment.

## Details

The prior guard rejected PLE with pipeline parallelism because later ranks did not receive raw `input_ids`. The models now add int32 token IDs to the PP intermediate tensors only when PLE is configured; PLE converts them to int64 at use. Hidden-state allocation continues to use `make_empty_intermediate_tensors_factory`.

An issue discussion proposed allowing only configurations whose PLE layers stay on the first stage. This implementation transports token IDs to later stages as well, including partitions that place a PLE layer there. No other open PR implementing that transport was found when this PR was opened.

AI assistance was used to inspect the data flow, prepare the implementation and tests, and address review feedback. The human submitter remains responsible for reviewing, validating, and defending the change.

`tests/models/qwen4_exp/test_config.py` no longer passes as a file. The three new `[amd]` cases import `vllm.models.qwen4_exp.amd.model` into an interpreter that already holds the CUDA one, and `vllm::qwen4_exp_grouped_gemma_rmsnorm` is registered twice:

```
RuntimeError: Tried to register an operator (vllm::qwen4_exp_grouped_gemma_rmsnorm(...))
with the same name and overload name multiple times.
```

On this PR's base (`d848c4ed3d`) the file passes all 9 tests; at `a36a841b9a` it has 3 failures and 12 passes. The failures occur during the backend import, before the new PP assertions run.

Could these three use `@spawn_new_process_for_each_test`, as the backend-parametrized MTP test in the same file already does? I applied it to the three locally and the file goes to 15 passed, so it keeps both backends covered while isolating their custom-op registrations.

Separately, could we retain `make_empty_intermediate_tensors_factory` for hidden states and add only the PLE input ids? This reuses the existing allocation helper and keeps the implementation smaller:

```python
self._empty_hidden_states = make_empty_intermediate_tensors_factory(
    ["hidden_states"], config.hidden_size * config.hc_count
)

def make_empty_intermediate_tensors(self, batch_size, dtype, device):
    tensors = self._empty_hidden_states(batch_size, dtype, device)
    if self.config.ple_layer_ids:
        tensors["input_ids"] = torch.zeros(batch_size, dtype=torch.int32, device=device)
    return tensors
```
