# [Bugfix][Rust Frontend] Open a new assistant turn after a final assistant message in the DeepSeek V4/V4.1 renderer

[Upstream PR](https://github.com/vllm-project/vllm/pull/62189) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Rust-frontend fix for #46256 (DeepSeek V4 / V4.1 renderer, `rust/src/chat/src/renderer/deepseek.rs`). When the last message is an assistant message and `add_generation_prompt=true` (`StartNewAssistant`, the default), the prompt ends at `<｜end▁of▁sentence｜>` without an `<｜Assistant｜>` turn prefix. The model then returns empty or garbled text with HTTP 200. This PR appends the turn prefix in that case. `continue_final_message` and `add_generation_prompt=false` are unchanged. **Behaviour change:** an assistant prefill sent *without* `continue_final_message` now starts a new turn instead of continuing after EOS (see Details).

## Claims

- When the final message is an assistant message and `add_generation_prompt=true`, the prompt now equals the DeepSeek reference encoding of the conversation followed by the reference assistant turn prefix. That prefix is `<｜Assistant｜><think>` in thinking mode and `<｜Assistant｜></think>` in chat mode. The comparison is token-for-token.
- These prompts are token-identical to before:
  - prompts that do not end in an assistant message;
  - prompts that use `continue_final_message` or `add_generation_prompt=false`.
- Fixes empty and garbled replies on DeepSeek-V4.1-Flash. Example: with thinking off, `[user, assistant(answer)]` gave empty replies 25/200 times before this change and 0/200 after.

## Validation

**Reference encoder.** The reference encoder has no generation-prompt control. It writes `<｜Assistant｜>` + think token only after a user-like message; its README calls this the assistant turn prefix. So a conversation that ends with an assistant message is encoded as closed history ending at EOS. That is why the old output in the "before" column matches the reference: the reference has no "start a new turn" output to compare against. `add_generation_prompt=true` asks for a new turn, so this PR appends the same turn prefix the reference encoder uses. The choice between `<think>` and `</think>` follows the reference rule for the turn after the last user message.

The server's `/tokenize` output was compared, as token ids, against `encoding/encoding.py` from `deepseek-ai/DeepSeek-V4.1-Flash@df42c109`. 7 conversation shapes were tested, each with thinking on and off:

| Shape | before | after |
|---|---|---|
| ends with user (2 shapes) | = reference | = reference (unchanged) |
| ends with assistant (5 shapes): plain, with `reasoning_content`, after a multi-turn history, with a system message, with `tool_calls` | = reference closed history (ends at EOS, no turn prefix) | = reference + `<｜Assistant｜>` + `<think>`/`</think>` |

**Unchanged paths render identically.** The exact lm-eval requests from our quality runs were re-rendered with both binaries:

| Requests | identical |
|---|---|
| GSM8K 8-shot (1,319) | 1,319 / 1,319 |
| IFEval (541) | 541 / 541 |
| HumanEval-instruct + `continue_final_message` (164) | 164 / 164 |
| HumanEval-instruct, prefill **without** `continue_final_message` (164) | 0 / 164: each differs by exactly the 2 opener tokens (see Behaviour change) |

**End-to-end.** Setup: DeepSeek-V4.1-Flash on 4×H200 with TP4, image `vllm/vllm-openai:nightly-92044241`, `VLLM_USE_RUST_FRONTEND=1`, with speculative decoding through the model's built-in draft module (`--speculative-config '{"method":"dspark","num_speculative_tokens":5,"draft_sample_method":"probabilistic","rejection_sample_method":"block","enable_adaptive_verification":false}'`). The same Rust sources were built with and without this change and swapped into the same container. Sampling: T=1.0, top_p=0.95.

| Request (no extra flags) | before | after |
|---|---|---|
| `[user, assistant(answer)]`, thinking off, 200 requests: empty replies | 25 | 0 |
| `[user, assistant(answer)]`, thinking on, 20 requests: `</think>` in content | 4 | 0 |
| `[user, assistant(answer)]`, thinking on, 20 requests: replies with a reasoning block | 0 | 20 |
| `[user, assistant(answer, reasoning_content)]`, thinking on, 20 requests: empty replies | 14 | 0 |
| `[system, user, assistant(tool_calls)]`, no tool result, 20 requests each (chat / thinking): reply is empty or starts with `<｜begin▁of▁sentence｜>` | 20 / 19 | 0 / 0 |
| 20 other shapes (user-terminated, streaming, tools, `reasoning_effort`, inline/trailing system, long history, `json_schema`), 11 requests each | clean | clean |

A 900 s serving benchmark at concurrency 16 gives the same throughput before and after (132,437 vs. 131,919 tok/s, within noise). This is expected, because rendering cost does not change.

**Unit tests** (`rust/src/chat`, Rust 1.95, `main` @ `21e09ea9`):
- `cargo test --lib deepseek`: 73 passed before this change, 76 after it.
- Control: with only the new tests and no renderer change, the V4.1 and V4 new-turn tests fail. The continuation / closed-history test passes on both.
- `roundtrip_deepseek_v41` passes, and `cargo fmt --check` is clean.
- The refactor that computes `next_rendered_entry` once is render-neutral. A binary with the full PR renders all the requests above token-identically to a binary with the original fix:
  - 2,188 lm-eval requests;

  - 340 saved end-to-end request bodies.
  So the end-to-end numbers carry over.

## Details

- **Root cause:** the render loop calls `write_assistant_transition` only after user-like entries.
- **Change** (`deepseek.rs`, +34 / −23):
  - `next_rendered_entry` is now computed once per entry.
  - A final assistant entry with `add_generation_prompt()` true calls the existing `write_assistant_transition`, with the same arguments the user path uses.
- **Tests:** full `expect!` snapshots.
  - New turn after a complete answer: one V4.1 test (`thinking` off/on) and one V4 test (`enable_thinking` off/on).
  - V4.1 prefill rendered with `continue_final_message` and with `add_generation_prompt=false`: unchanged.
  - The existing V4 test `system_to_assistant_transitions_…` checks a transition, not the trailing prompt. It now pins `NoGenerationPrompt`, as the shared fixtures do; its expected strings are unchanged.
- **Behaviour change:**
  - A client that sends an assistant prefill without `continue_final_message` used to continue after EOS. It now gets a new turn instead.
  - Measured impact: lm-eval `humaneval_instruct` sends such a prefill. Without `continue_final_message` its pass@1 goes from 0.4207 to 0.0000. The old score already came from continuing after EOS, which is not a supported format.
  - Why exactly 0: lm-eval scores `doc["prompt"]` plus the reply cut at its first `` ``` ``. In the new turn the model writes a complete fenced answer: 160/164 replies start with `` ```python ``, so the cut keeps nothing and the program is the bare function stub. The other 4 replies are reasoning-style prose with no code before the cut, so the program is the stub followed by prose. All 164 fail. The low score measures the scorer's assumption (the reply continues the prefill), not a broken reply.
  - With `continue_final_message=true` the same task scores 0.9573 before and 0.9634 after.
  - Score noise: HumanEval has 164 problems, so one problem is about 0.006. These runs are greedy, but outputs are not bit-reproducible under batching and speculative decoding. Differences of 1–2 problems, such as 0.9573 vs 0.9634 on token-identical prompts, are run-to-run noise.
  - Alternative considered: treating a trailing assistant message as a prefix by default (continue in place). That recovers this prefill case (0.9756 without the flag). But it breaks completed answers: when the final assistant message was a full answer, 15/20 greedy and 9/20 sampled replies were empty. It would also contradict the documented meaning of `StartNewAssistant`, so it was not adopted.
  - A request that ends with an assistant `tool_calls` message and no tool result now also gets a new turn. Over 20 requests each:
    - chat mode: the model re-issued the call 14 times and replied in text 6 times;
    - thinking mode: it re-issued the call 1 time and replied 19 times that no result came back.
    Before this change, 20/20 (chat) and 19/20 (thinking) replies were empty or started with `<｜begin▁of▁sentence｜>`. The OpenAI API rejects this request shape. Rejecting it in vLLM would be a request-validation change, which is out of scope for this PR.
  - If maintainers prefer, I can add a debug log for the prefill-without-`continue_final_message` case.
- **Prior work:**
  - #57882 (Python V4.1 tokenizer) used the same semantics: "opens a fresh assistant turn after a completed assistant message". It received no review and was closed by its author.
  - #56593 (merged) covers a final user message with `add_generation_prompt=false`.
- **Python frontend:** this PR changes only the Rust frontend. The Python tokenizers still have the gap (#46256, and #46257 for V4), so the two frontends render this case differently until the Python side is fixed. A follow-up PR can port the same semantics to `deepseek_v41.py`.
- **Coverage:** unit tests cover the new path for both V4 and V4.1. The end-to-end runs used V4.1-Flash only.
