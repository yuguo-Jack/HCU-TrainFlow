# [ROCm][Perf] Capture the routed MoE chain before the shared-expert aux branch for small decode batches

[Upstream PR](https://github.com/vllm-project/vllm/pull/65509) · state: open · merged: False

## Original PR description

### What
(Gated version: only for MoE inputs of <= 64 tokens, see below.)
`SharedExperts.maybe_forward_async(..., defer_launch=True)` records the input-ready event as before, but during **CUDA/HIP graph capture on ROCm only** it postpones enqueuing the aux-stream work; `MoERunner` launches it (via `wait()`) after the routed experts have been captured. The dependency graph is unchanged; only capture order changes. Eager mode, prefill, CUDA, and other callers (`deepseek_v41/nvidia/.../step.py`) are unchanged (`defer_launch` defaults to False; `wait()` launches pending work).

### Why
In the MiniMax-M3.1 MXFP4 decode graph (TP4, MI355X) each MoE layer forks the shared expert onto an aux stream; the routed chain (router, top-k, sort, gemm1, gemm2) is the layer's critical path (traces: routed chain ends at ~102 us after the router start at N=4, shared chain at ~40 us). HIP graphs keep the first captured branch of a fork on the parent stream and move later branches to another queue; because the shared experts are captured first, the routed chain pays the cross-queue start delay and the join hop. In existing rank-0 decode traces (run/traces/decode_clean, 8.3k layers each at N=1 and N=4): router end -> routed top-k start = 7.2-7.4 us (p10-p90 6.9-8.3), vs 4.3-4.4 us for the shared branch that stayed on the stream; routed gemm2 end -> join add = 5.8-6.0 us.

### Evidence (measured)
- Unit tests (`tests/kernels/moe/test_shared_experts_deferred_launch.py`, MI355X, rebased on main ff74259): 22 passed (graph vs eager results identical at 8/64/65/128 tokens, with/without deferral, explicit/implicit launch, idempotent launch, no-op outside capture, deferral on for <=64 tokens and off above).
- Synthetic multi-stream graph benchmark (spin kernels with trace-matched durations, 20 layers per graph, median of 50 replays; mechanics of stream hops only, not real kernels): per-layer time cur 120.5 us -> 117.6-118.2 us (N=4), 72.3 -> 69.2 us (N=1); the router->first-routed-kernel gap in the timeline drops from ~6.2 us to ~4.0 us and the join gap from ~5.7 to ~4.3 us. Variants that keep the shared branch captured first show no gain. Script: graph_fork_bench.py.

### Real-graph measurements (full TP4 server, MI355X, DSpark, 150K ctx; torch-profiler window of 60 steps, rank 0)
Fork/join gaps on the real decode graph, medians over all 57 MoE layers x 60 steps (3420 samples), same server settings, installed tree vs this change alone vs a tree with several other launch-removal changes:

| | router_gemm end -> routed top-k start | routed gemm2 end -> next main-stream kernel (join) |
|---|---|---|
| installed (N=4 / N=16) | 7.7 / 7.5 us | 6.1 / 6.0 us |
| this change only (N=4 / N=16) | 4.7 / 4.6 us | 5.1 / 4.5 us |
| full stack (N=4 / N=16) | 4.6 / 4.6 us | 4.5 / 4.5 us |

So the predicted effect on the graph is confirmed: the routed chain starts ~3 us earlier and the join is ~1-1.5 us shorter, about 4-4.5 us per MoE layer (~0.25 ms/step over 57 layers, profiled timeline; the routed chain is now on the main stream and the shared experts on the aux stream). MoE-block latency (post-attn norm end -> next all-reduce) median, profiled: N=4 90.3 -> 85.6 us, N=16 140.5 -> 134.5 us.

### Step level (decode_bench p50, 150K context, DBO off, `VLLM_ROCM_USE_SKINNY_GEMM=0`, 5 repeats per arm)
Why gated: an earlier ungated version of this change (deferral at every batch size) was +2.9% slower at N=16 (all 5 repeats with the change slower than all 5 without) and +0.4% at N=12, although the fork/join gaps were shorter. I do not know why larger batches lose, so the deferral is now enabled only for MoE inputs of <= 64 tokens (8 requests x 8 rows with DSpark 7).

A/B of the gated version: arm **S0** = a tree without this change (it already contains other, separate launch-removal changes), arm **S1** = S0 + this change; S0 was also run again at the end to check drift (agrees within 0.14 ms at every N). ms, medians; noise of this benchmark about +-0.1-0.2 ms:

The N >= 12 regression of the ungated version is gone (N=16 +2.9% -> -0.3%). The gain remains only at N=1 and N=2 (-1.7%, -1.3%); N=3..8 are within the noise (N <= 8 average -0.25%). A profile window with the gate confirms the mechanism: at N=4 the router -> top-k gap is 4.6 us and the gemm2 -> join gap 4.6 us against 7.6 and 6.1 us without the change; at N=16 (above the gate) both gaps are unchanged (7.9 and 6.0 us). So this is a harmless change with a small win at 1-2 requests, not a broad speedup.

"What is 17*23? Answer briefly." gives 391 with this change. GSM8K and the AgentX replay were not run for this change alone.

### Limitations
ROCm graph-capture only. Relies on the HIP graph runtime keeping the first captured branch on the parent stream (observed, not documented).
