# [Perf][MoE] Size NIXL dispatch from synchronized execution slices

[Upstream PR](https://github.com/vllm-project/vllm/pull/63485) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

NIXL EP sizes every dispatch with the static `max_tokens_per_rank` reservation (typically `max_num_batched_tokens`, e.g. 8192), so expert workspaces, zeroing and grouped-GEMM grids scale with 8192 rows even when a decode step has a few dozen tokens per rank. This PR passes the synchronized DP/SP execution size instead and keeps the static value as the reservation bound. DeepEP v2 already does the same (`deepep_v2.py`, `num_max_tokens_per_rank` bounded by `max(num_tokens_across_dp)`).

Related: #61156 takes a different approach to the same cost by lowering the static NIXL bound to 1024 with synchronized chunking. The two can combine; I'll coordinate there.

## Claims

- NIXL dispatch capacity = max synchronized execution tokens across DP ranks (EP-local SP sizes when sequence parallelism is active), aligned to NIXL's receive extent (a multiple of 4 across dispatchers), and bounded by `max_tokens_per_rank`. The capacity is identical on every rank because it comes from the same CPU DP metadata, including during CUDA graph capture.
- The NIXL buffer reservation is unchanged.
- For `BatchedExperts`, the fused output is a contiguous `[E, M, K]` view of the runtime dispatch shape, while the workspace keeps its static reservation.

## Validation

- `pre-commit run --files <changed files>`: all hooks pass.
- `pytest tests/kernels/moe/test_moe_layer.py -k nixl_ep` on 2x H200 (DP2/EP2, real NIXL dispatch/combine checked against the reference MoE): 52/52 subcases pass before and after (BF16, FP8 blocked, ModelOpt FP8; `m=222` against a 256-token reservation, so both the runtime capacity and the `BatchedExperts` view are exercised). This used main's test files on the `77154ca611` base described below.

Historical A/B on an older snapshot (2026-09-20/21, H200, DP8/EP8, DeepSeek-V2-Lite BF16, NIXL EP, `batched_triton`, rank loads `[63,97,80,80,80,80,80,80]`, FULL graph bucket 128). The two runs' source patches differ only by this change. They were measured under Nsight, so the numbers are per-step kernel timings, not serving throughput.

| dispatch capacity, DBO off | 8192 | 128 |

End-to-end A/B, no profiler. Before is main@`77154ca611`, the last commit with a cu129 precompiled wheel, which matches this host's driver. After is the same commit with this change cherry-picked. The `nixl_ep.py` code path is unchanged on main since then. Setup: 2x H200, DP2/EP2, DeepSeek-V2-Lite BF16, NIXL EP, `batched_triton`, FULL CUDA graphs, DBO off.

The mean difference (−0.33 pt, about 4 of 1319 questions) is within the before side's own run-to-run spread (0.68 pt), so I read it as noise: vLLM is not batch invariant, and the smaller expert `M` can select a different batched-Triton tile configuration.

## Details

- `_get_runtime_dispatch_capacity()` reads `dp_metadata.local_sizes` (set by `sp_local_sizes()` under SP) or `num_tokens_across_dp_cpu`. Both are CPU values, so there is no GPU sync.
- The alignment only affects undersized warmup shapes. With 8 dispatchers it is a no-op.
- The `modular_kernel.py` change applies to every `BatchedExperts` backend. For batched experts `M_full` is `a1q.size(1)`, the dispatched row count. DeepEP low-latency and the naive batched prepare/finalize still dispatch with their static capacity, so `M_full` equals the old `fused_out_shape[1]` and the view is unchanged for them. The workspace reservation still uses the static shape.
- CI: the H100 FusedMoE layer step has no nixl installed, so `has_nixl_ep()` skips every `nixl_ep` case in `test_moe_layer.py`. The second commit installs the KV connector dependencies in that step, as the fault tolerance step does, so these cases run in CI. Locally the `nixl_ep` cases add about 3 minutes.

**Problem**

NIXL EP dispatch uses the static `max_tokens_per_rank` reservation (typically 8192), even when a decode step processes only a few dozen tokens per rank.

**Proposed Fix**

Size dispatch from the synchronized DP/SP execution size, following DeepEP v2, while retaining the static reservation bound. Align the NIXL receive extent and adjust the shared `BatchedExperts` output view.

The production change is **+33/−1 lines**; CI adds **2 lines**.

**Validation**

Baseline: older main `77154ca611`; comparison: the same base plus this change. Setup: 2×H200, DP2/EP2, DeepSeek-V2-Lite BF16, FULL CUDA Graphs, DBO off.

- Output throughput: **+27%** across two measured rounds per configuration after warmup.
- Mean TPOT: **−23%**.
- GSM8K: three runs per configuration; mean 34.95% → 34.62%, with the difference smaller than the baseline's 0.68-point run-to-run spread.
- GPU tests: all **52/52** `nixl_ep` MoE subcases passed per side.
- CI: the two-line change installs NIXL so existing H100 FusedMoE tests run instead of being skipped.

These results apply to the older base above; current-head end-to-end validation remains outstanding. Full settings and individual results are in the description.
