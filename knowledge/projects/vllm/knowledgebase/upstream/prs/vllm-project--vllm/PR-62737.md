# [Bugfix][Compile] Write vllm_compile_cache.py atomically

[Upstream PR](https://github.com/vllm-project/vllm/pull/62737) · state: open · merged: False

## Original PR description



## Overview

Fixes #60410. `CompilerManager.save_to_file` now writes `vllm_compile_cache.py` to a uniquely named temp file in the same directory and `os.replace()`s it into place, instead of truncating and rewriting the live index.

## Claims

- If a save fails or is interrupted (ENOSPC, crash), the index is no longer truncated, so the next startup still loads the previous index instead of failing in `ast.literal_eval`.
- A process that reads the index while another one is saving it (deployments sharing `VLLM_CACHE_ROOT` with the same hash) sees either the complete old index or the complete new one, never a partial file.
- On failure the temp file is removed and the original error is re-raised, as before.

## Validation

New regression test `tests/compile/test_compiler_interface.py::test_failed_save_keeps_previous_cache_index`. It saves an index, then makes the next save's `write()` raise `OSError(ENOSPC)`, and asserts:
- the error propagates;
- the previous index reloads unchanged through `initialize_cache`;
- no temp file is left behind.

Run on a CPU-only Linux VM (torch 2.14 CPU, vLLM built from source for CPU):

```
$ python -m pytest -q tests/compile/test_compiler_interface.py -p no:cacheprovider
6 passed, 2 warnings in 9.32s                  # this branch
1 failed, 5 passed, 2 warnings in 6.43s        # same tests against main's backends.py
FAILED tests/compile/test_compiler_interface.py::test_failed_save_keeps_previous_cache_index
E       SyntaxError: invalid syntax              # the failed save left a 0-byte index
```

Concurrent read/write, using a local stress script (not added to the repo):
- 2 processes re-save a ~1.27 MB index in a loop for 6 s while 2 processes repeatedly run `initialize_cache` on the same directory.
- Before: 7 of 2147 reads failed with `SyntaxError`.
- After: 0 of 1842 reads failed, and no temp files were left over.
- The file mode is unchanged (0o664 under umask 002 in both cases).

`pre-commit run --files vllm/compilation/backends.py tests/compile/test_compiler_interface.py` passes (ruff, mypy, typos, test tethering). CPU cannot drive this path end to end, because `CpuPlatform` downgrades `VLLM_COMPILE`. The new test runs in the existing "PyTorch Compilation" job, which runs every `tests/compile/test_*.py`.

## Details

- Root cause: `open(self.cache_file_path, "w")` truncates the live index before the new contents are written, and `initialize_cache` parses it with `ast.literal_eval` and no fallback.
- The approach is the one proposed in the issue and already used for the AOT artifact in `vllm/compilation/decorators.py`: a temp file in the same directory (so the rename is atomic), then `os.replace`.
- The temp name uses `random_uuid()` rather than the PID because containers that share a cache volume often have the same PIDs. `vllm.utils.random_uuid` is already imported through `vllm.config`.
- `weight_utils.atomic_writer` is not reused:
  - it would pull the model-loader module into `vllm/compilation` (#57311 is moving it for that reason);
  - its `mkstemp` creates 0600 files, which other users of a shared cache could not read. `open(tmp, "w")` keeps the umask permissions the index has today.
- Out of scope:
  - the issue's optional "treat an unparsable index as empty" fallback;
  - fsync (power-loss durability, which `decorators.py` does not do either);
  - the compiled artifacts themselves.
- If the process is killed between writing and replacing, a `vllm_compile_cache.py.<hex>.tmp` file can be left behind. It is never read.
- Not a duplicate: the only earlier PR for this issue, #60440, was closed unmerged on 2026-10-17 after a broken rebase (892 files changed). Searches for open PRs matching `60410 in:body`, `vllm_compile_cache`, `save_to_file` and `compile cache atomic` found nothing else touching this function (#57311 moves `atomic_writer` and does not touch `backends.py`).
