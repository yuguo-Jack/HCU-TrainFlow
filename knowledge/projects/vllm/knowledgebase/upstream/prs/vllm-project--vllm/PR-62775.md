# [Rust Frontend] Fix /detokenize returning 500 for out-of-range token IDs

[Upstream PR](https://github.com/vllm-project/vllm/pull/62775) · state: open · merged: False

## Original PR description

## What this fixes

Closes the detokenize half of #62321.

`POST /detokenize` returns **HTTP 500** when the request contains a token ID that is outside the model's vocabulary. This is wrong — the failure is caused by invalid client-supplied data and should be **400**.

```bash
curl localhost:8000/detokenize -H 'Content-Type: application/json' \
  -d '{"model": "...", "tokens": [1, 99999999, 2]}'
# before: 500 {"error":{"message":"detokenize failed: ...","type":"InternalServerError",...}}
# after:  400 {"error":{"message":"token id 99999999 is out of range for vocabulary size ...","type":"BadRequestError",...}}
```

## Root cause

The handler unconditionally wrapped every error from `tokenizer.decode()` in `server_error!`, which produces a 500:

```rust
Err(e) => server_error!("detokenize failed: {}", e.to_report_string()).into_response(),
```

The natural fix — mapping the error the way `chat_submit_error` / `text_submit_error` do — is not possible here because `TokenizerError` is a flat `struct TokenizerError(String)` with no `is_request_validation_error()` method. We cannot distinguish a client-caused failure from a backend failure after `decode()` returns.

## Fix

Pre-validate token IDs against the tokenizer's reported vocabulary size before calling `decode()`. Any ID `>= vocab_size` is an unambiguous client error and gets a 400 with a message that names the offending ID. If all IDs are in range and `decode()` still fails, that is a genuine backend fault and the existing `server_error!` (500) is appropriate.

Backends that cannot report their vocabulary size return `usize::MAX` from `vocab_size()`; on 64-bit targets no `u32` can reach that bound, so validation is silently skipped for those backends.

## Tests

- **Integration test** (`detokenize_out_of_range_token_id_returns_400` in `routes/tests.rs`): sends a request containing the existing `UNKNOWN_DECODE_TOKEN_ID = 10_000` constant through the full HTTP stack and asserts a 400 `BadRequestError` response whose message names the bad ID.
- **Unit test** (`out_of_range_token_id_produces_invalid_request` in `tokenize.rs`): pins the boundary detection logic and the shape of the resulting `ApiError` without requiring a running server.

## Scope

This PR covers only `/detokenize`. The `/tokenize` error-classification fix (replacing `server_error!` with `text_submit_error` at the three sites in `tokenize_completion` and `tokenize_chat`) is being handled separately by @Muonchaser per the issue thread.
