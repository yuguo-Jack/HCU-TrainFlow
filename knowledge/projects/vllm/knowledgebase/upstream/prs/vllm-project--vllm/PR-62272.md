# [Core] Per-request auxiliary readouts in generation (MRV2)

[Upstream PR](https://github.com/vllm-project/vllm/pull/62272) · state: open · merged: False

## Original PR description



## Overview

Adds an opt-in, per-request output for generation: a model that implements `SupportsAuxReadout` declares named float32
readouts (for example an N-way decision head). They are computed from the hidden-state rows that `compute_logits`
reads, only for requests that set `SamplingParams.aux_readouts`, and are returned in `CompletionOutput.aux_readouts`.
The engine must be started with `--enable-aux-readouts`; without it, nothing changes.

First PR of RFC #62145. It is the stateless part only: no intermediate-layer capture, no branch with its own KV/GDN
state, and no Decisions API change.

## Claims

- **New output.** Row `i` of `aux_readouts[name]` is the readout computed from the hidden state that the logits of
  generated token `i` were computed from. It is a float32 CPU tensor `[len(token_ids), width]`, returned with the
  final output. `output_kind=DELTA` is rejected, because a DELTA final output carries only its last tokens.
- **Off by default, no work unless asked.**
  - With the flag off, the runner holds no readout state, and requests that set `aux_readouts` are rejected.
  - With the flag on, a step in which no scheduled request asked does no readout work.
  - Requests that did not ask get `None`.
- **No change to generation.**
  - Readouts are computed after the forward, next to `compute_logits`; CUDA graph dispatch is untouched.
  - No host synchronization is added. This was checked with `VLLM_GPU_SYNC_CHECK=error`, including a negative
    control (see Validation).
- **Small.** 246 added and 2 changed library lines (docstrings included) across 13 files, following the path
  that `prompt_token_id_logprobs_dict` already takes. Model Runner V2 only. The engine refuses at start-up with
  speculative decoding, tensor, pipeline or context parallelism.
- **Checked model contract.** A head that returns anything other than `[rows, sum(aux_readout_dims)]` raises a
  `ValueError` naming the model and the expected shape; this check reads tensor metadata only.

## Details

**Why this is not duplicate work.**
- #59543 (open) returns the raw last hidden state per generated token to the client.
- This PR returns a model-defined head's few floats from the same rows, through the same kind of path.
- If #59543 lands first, this change can share its runner gather and transport, leaving only the
  `SupportsAuxReadout` call. RFC #62145 asks whether the two should be one channel.
- The existing `aux_output_connector` (routed experts) is built for per-token captures keyed by KV block hashes, with
  its own store. A few floats at the sampled rows do not need that machinery, so this PR does not use it.

**Design.**
- `SupportsAuxReadout` has two members: `aux_readout_dims` (name → width) and
  `compute_aux_readouts(hidden_states) -> [num_rows, total_width]`. Widths are recorded in `_ModelInfo`, so the
  frontend can validate names without loading the model.
- In `sample_tokens`, the runner gathers the asking requests' rows by the same `logits_indices` that `sample()` used.
  It calls the model once per step and splits the result per request into `ModelRunnerOutput.aux_readouts`.
- `AsyncOutput` copies the readouts to the host on the output copy stream.
- The scheduler cuts each request's rows to its kept tokens, into `EngineCoreOutput.new_aux_readouts`, appended last.
- The output processor concatenates the rows on finish and slices them by name.

**Tradeoffs and limitations.**
- Readouts are returned with the final output only, and only through the Python API (no OpenAI-compatible field yet).
- Not supported yet: speculative decoding, tensor, pipeline and context parallelism. They are refused at
  start-up. Tensor parallelism is refused because it was not validated and a head may read TP-sharded weights
  (the test head reads rows of `lm_head`).
- During chunked prefill, the row of a chunk that does not finish the prompt is computed and discarded, like its
  logits (Model Runner V2 computes one logits row per scheduled request).
- Readouts follow the precision of the hidden state. Across a prefix-cache hit they match the engine's logits for that
  request, not bit-for-bit the readout of an uncached run.
- Not covered by this change, but met while validating it: a model that subclasses an existing architecture and is
  registered under a new name does not get that architecture's name-keyed config adjustments (`MODELS_CONFIG_MAP`).
  For Qwen3.5 the GDN state dtype then resolves to `auto`, and in our hybrid check 2 of 8 sequences differ from
  stock (logprob gap 0.0078). That stock resolves to float32 is read from `MODELS_CONFIG_MAP`, not observed: in our
  matched runs we set float32 explicitly on both sides. With `--mamba-ssm-cache-dtype float32` they match. This happens
  with or without readouts. Should it be documented, or should a subclass inherit its parent's adjustments?
- Tested on NVIDIA only. The new tests also run in the ROCm mirror of "V1 Sample", which we could not run.
