# [Bugfix][Quantization] Honor activation scheme in MXFP8 linear selection

[Upstream PR](https://github.com/vllm-project/vllm/pull/65288) · state: open · merged: False

## Original PR description



## Overview

Quark's MXFP8 path drops `activation_quant_key`, so a weight-only checkpoint can select a backend that quantizes activations to FP8. This fix passes the key through kernel selection: weight-only requests select Marlin or emulation, preserving unquantized activations. Fixes #65193.

## Claims

- Explicit weight-only requests skip W8A8 kernels; forcing an incompatible backend fails during selection.
- Callers that omit the activation key retain existing W8A8 selection and A16 fallback behavior.
- Regression coverage includes real Quark layer construction and checkpoint loading through `LLM.generate`.

## Details

- **Compatibility:** the selector/config default is `kMxfp8Dynamic`; explicit `None` requests weight-only execution. Selection reuses the existing activation override resolution and adds a `_supports_quant_scheme` gate.
- **Backend support:** `input_quant_key()` describes external input/fusion support and does not identify internal activation precision. Marlin and emulation explicitly accept weight-only requests and retain the existing A16 fallback for W8A8. Other MXFP8 implementations default to requiring dynamic MXFP8 activations. The gate adds no inference hot-path work or synchronization; backend performance can differ and was not benchmarked.
- **Related work:** the pre-submission duplicate check found no open PR directly fixing #65193. #63378 covers MoE and leaves dense MXFP8 for follow-up; #59460 covers fallback reporting/enforcement and identifies this missing key as a gap. Reconciliation may be needed if #59460 lands first. The issue author had announced a staged implementation, but no matching open PR was found at submission.
