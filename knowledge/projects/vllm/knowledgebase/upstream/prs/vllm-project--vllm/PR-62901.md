# [Core][DP] Add a DP-global prefill gate for prefill_schedule_interval

## Overview

Draft, to settle the mechanism first. This overlaps draft #51199 (adaptive prefill delayer for DP serving), which targets the same lockstep problem with per-rank delay budgets and acknowledgments; we would like maintainers to pick one approach before either is reviewed in detail. It builds on #54627 (`prefill_schedule_interval` outside DP).

With `--prefill-schedule-interval N` (PSI), DP ranks admit new prefills only every N steps, except that a rank whose last release could not drain its queue (`prefill_capacity_bound`) releases on every step. Under sustained load that exception sets the step shape: a backlogged rank runs a long mixed step on most off-cadence steps while the other ranks, with nothing to prefill, run decode and then wait for it in the lockstep EP collectives. On DP8/EP8 + MTP1, 8x MI355X, PSI 8, chat-like 8k-class prompts at c=1024, 82% of wall time was in mixed steps (median 720 ms vs 81 ms decode-only), and 12-13% of all rank-time was spent waiting on another rank's prefill.

## Claims

- New `SchedulerConfig.prefill_release_min_dp_ranks` / `--prefill-release-min-dp-ranks K` (default 0 = off). With PSI > 1 and K > 0, off-cadence steps release prefills on every rank if at least K DP ranks have prefill work, and defer them on every rank otherwise, including capacity-bound ranks. Cadence steps are unchanged.
- The count is one CPU `SUM` all-reduce of an int32 over the DP group per step, in `_has_global_unfinished_reqs`. With K = 0 or PSI = 1 nothing changes and no collective is issued.
- On 8x MI355X: +10.5% tok/s/GPU at matched interactivity on chat-like prompts (out-of-tree equivalent, older vLLM), about +2% on random 8k/1k on main, with median TTFT at c1024 roughly halved on main. Scheduling only; gsm8k unchanged.

## Details

**Where the count runs.** `_has_global_unfinished_reqs` is reached once per step by every rank with the same `step_counter`, including idle ranks. A first prototype all-reduced at the start of `_process_engine_step` and deadlocked at c=1024: an idle rank runs that method without reaching the step-end sync, so the gloo sequence shifted.

**Prefill work.** New `SchedulerInterface.has_prefill_work()`, defaulting to "any waiting request". `Scheduler` excludes blocked waiting requests and includes running requests still mid-prompt.

**Guards kept.** A rank with no decode work to protect never defers, so a throttled step is never an empty step. The scheduler ignores `prefill_capacity_bound` only when the gate is on.

**Why an integer.** At c1024, K=4 < K=6 < K=8 = dp_size. If K = dp_size is always best a boolean would do; we kept an integer for deployments with more skewed per-rank load, which we did not test.

**Not tested.** This branch alone on hardware (only stacked with our other open branches, above), a chat-like A/B on main, multi-node DP, `--data-parallel-hybrid-lb` and elastic EP (the count uses the current `dp_group`, which elastic EP reinitializes). The per-step all-reduce cost was not measured separately; it is included in the numbers above.

Thanks, that makes sense. I pushed 67d5aa5822:
- **Fail-open:** under the gate, a capacity-bound rank still defers with its peers, but the scheduler now counts releases in a row that leave its queue backed up.
