# [Bugfix][Model] GLM-5.x: load ModelOpt NVFP4 MLA projections into BF16 fused_qkv_a_proj

[Upstream PR](https://github.com/vllm-project/vllm/pull/59833) · state: open · merged: False

## Original PR description

## Overview

Load ModelOpt NVFP4 MLA projections into GLM-5.x's BF16 targets. Consume unused `input_scale` tensors from W4A4 checkpoints instead of failing with a `KeyError`.

## Claims

- Dequantize packed NVFP4 `q_a_proj`, `kv_a_proj_with_mqa`, `q_b_proj` and `o_proj` weights when their model targets stay BF16. Actual quantized targets keep the normal loader path.
- Ignore checkpoint activation scales only when the target has no matching scale parameter. This covers the [W4A4 review feedback](https://github.com/vllm-project/vllm/pull/59833#discussion_r4236819606) for `vroomfondel/GLM-5.3-Flash-NVFP4-W4A4`.
- Use the same helper in the main model and MTP. Preserve NoPE padding and fused-shard loading.

## Details

`fused_qkv_a_proj` is always BF16. The existing loader only dequantizes FP8 checkpoints, so ModelOpt NVFP4 MLA weights fail with `assert param_data.shape == loaded_weight.shape`. The helper buffers packed uint8 `weight`, e4m3 per-16 `weight_scale` and fp32 `weight_scale_2`, then loads their BF16 dequantization. It runs before the FP8 helper because both accept `.weight_scale`.

W4A4 checkpoints also store activation `input_scale`. BF16 projections have no destination parameter for it, so it must be consumed without buffering or marking a weight as loaded. A registered activation-scale parameter still uses normal loading.

This extends the existing PR in response to review. The original duplicate search found no other PR or issue covering NVFP4 MLA projections in the GLM-5.x loader (`fused_qkv_a_proj nvfp4`, `glm5next nvfp4 q_a_proj`, `kv_a_proj_with_mqa nvfp4`, and the assertion text). The NVFP4 MoE scale mismatch in #54974 and #55073 is separate. A follow-up open-PR search for `glm5next input_scale` found no overlap.
