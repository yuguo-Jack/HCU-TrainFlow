# [Perf][ROCm][MiniMax-M3.1] Add opt-in parallel decode top-k

[Upstream PR](https://github.com/vllm-project/vllm/pull/65032) · state: closed · merged: False

## Original PR description

## Overview

Add an opt-in parallel decode top-16 selector for MiniMax-M3.1 on gfx950, replacing the fixed FlyDSL w26 selector in the NVFP4 indexer.

Superseded by [#65267](https://github.com/vllm-project/vllm/pull/65267), which targets `main` and includes the review follow-up. This PR was automatically closed when its target branch was deleted.

## Claims

- Preserve selected block IDs, ordering, tie handling and causal boundaries.
- Use runtime shape metadata to avoid new row/stride specializations during mixed-batch serving.
- Enable with `VLLM_ROCM_MINIMAX_M3_1_PARALLEL_TOPK=1`; default off. FP8 indexers, including C4 mono decode, bypass this path.

## Details

Small `heads × rows <= 16` batches fuse selection and last-arriver merge; larger batches use staged merging. Scratch and counters are isolated by device, stream and shape.

The recipe adds opt-in `parallel_topk`; MI355 Buildkite kernel CI selects the new tests. Scoreboard enablement targets #4671's C16/C32 NVFP4 lane, `zip_override_tp4_dspark7.roles.agg.env`: set the flag to `"1"` in an image containing this patch and the text-only DBO startup fix noted above. Correctness CI does not enable serving; global default-on is not planned. Recipe validation, interactive command checks and documentation discovery passed.

Related work: #64130 targets sampling; #55122 changes C++ persistent top-k; #59980 targets index scoring; #64264 prebuilds existing FlyDSL kernels.

Thanks for the AgentX table and the ordering checks. Asks:

1. Please add an in-tree pytest for `parallel_decode_topk` (vs the existing FlyDSL selector) covering ties / NaN / causal boundaries / query_len in {1,4,8} and at least one CUDA-graph replay path. The local harness results are useful, but this kernel should not land without repo tests.

2. Please repeat the 900s AgentX comparison at least once more on the same pinned image (or report seed-to-seed variance). A single arm with intervening work on the node is too thin for a +7.8% p90 claim.

3. Please document the intended enablement path. Default-off behind `VLLM_ROCM_MINIMAX_M3_PARALLEL_TOPK` is fine for landing, but note whether the MiniMax recipe / CI image will set it, and when default-on is planned. Otherwise this will not show up in production numbers.

4. In the fused path, the last-arriver merge uses `atomic_add` + `volatile` loads + `atomic_xchg` reset. Please confirm (and ideally test) that a graph-captured launch with varying `seq_lens` cannot leave a non-zero counter if a prior launch took the adaptive early-exit path on some rows and the merge path on others. The PR claims concurrent replay passed; please point to that case or add it to the pytest above.

5. Minor: the env name says `M3` while the PR targets MiniMax-M3.1. Prefer `VLLM_ROCM_MINIMAX_M3_1_PARALLEL_TOPK` (or a shared MiniMax decode flag) to avoid confusion with other M3 paths.
