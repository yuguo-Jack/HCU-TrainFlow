# [Bugfix][LoRA] Refuse adapters with LoRA on modules vLLM does not wrap

[Upstream PR](https://github.com/vllm-project/vllm/pull/63489) · state: closed · merged: True

## Original PR description

## Overview

Fixes #63278. A PEFT adapter can carry LoRA weights for a layer that vLLM keeps as a plain `nn.Linear`, such as `bert.pooler.dense` in BERT models trained with `target_modules="all-linear"`. vLLM loaded these adapters and ignored those weights without a warning, so outputs differed from transformers + PEFT. vLLM now refuses such an adapter at load and names the modules, as discussed in #60211.

## Claims

- An adapter with LoRA weights on a module that vLLM cannot apply LoRA to fails to load with a `ValueError` naming the modules, for example `bert.pooler.dense` on BERT and `classifier.dense` on RoBERTa. On main these adapters load and their outputs differ from transformers + PEFT.
- On a running server, `/v1/load_lora_adapter` returns the error, the adapter is not registered, and the server stays healthy.
- Adapters whose LoRA weights all land on modules vLLM wraps load as before.
- Weights the LoRA manager already skips on purpose are still skipped: layers on another pipeline stage, layers outside `--lora-target-modules`, tower and connector layers without a PunicaWrapper, the non-gated MoE `mixer.gate`, and linear layers no LoRA layer can wrap.

## Details

Root cause: `check_unexpected_modules` in `vllm/lora/lora_model.py` compares only the last part of each module name with the expected suffixes, which come from the model's `LinearBase` layers. BERT's encoder has `LinearBase` layers named `dense`, so `bert.pooler.dense` passes, although `BertPooler.dense` is a plain `nn.Linear` that `_create_lora_modules` never wraps. `activate_adapter` only reads weights for wrapped modules, so the pooler LoRA is never used. RoBERTa's `classifier.dense` takes the same path.

Change: `_create_lora_modules` records the layers it skips because `is_supported_lora_module` rejects them although their name ends in a LoRA target suffix. `check_unexpected_modules` treats LoRA weights on those layers as unexpected, so the adapter is refused while its checkpoint is read, before the LoRA model is built. It is never cached and never evicts another adapter, including on in-place reloads.

What stays skipped, and why:

- Weights for a `PPMissingLayer` or for a path through one belong to another pipeline stage, which applies them.
- Weights outside `--lora-target-modules` are excluded by the user.
- Weights without a PunicaWrapper, such as tower and connector layers when `enable_tower_connector_lora` is off, are already logged as ignored at startup.
- The non-gated MoE `mixer.gate` is a `GateLinear` and linear layers no LoRA layer can wrap are `LinearBase` too, so `is_supported_lora_module` accepts them and they keep their current behavior.
- Names that match no module of the model at all also keep their current behavior. That case, such as a text-only adapter on a multimodal wrapper with no name mapping, is what the draft #60039 covers. It raises only when no weight matches and warns on a partial match, so the pooler case would only log a warning there. The two changes do not overlap in code and can land in either order.

Once a model wraps a head linear, as #60211 does for RoBERTa's `classifier.dense`, its LoRA weights load and this check no longer fires for it.

Limits:

- The server returns 500 for this error, as it does for other `add_lora` failures.
- Pipeline and expert parallel runs were not tested, only covered by the `PPMissingLayer` and expert name handling described above.
- The new test downloads `cross-encoder/ms-marco-MiniLM-L6-v2` and writes a small adapter in the test, so it needs no PEFT.
