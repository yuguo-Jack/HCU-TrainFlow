# [Bugfix][LoRA] Account for CLIP CLS rows in LLaVA-NeXT-Video tower mappings

[Upstream PR](https://github.com/vllm-project/vllm/pull/62097) · state: open · merged: False

## Original PR description

## Overview

Fixes item 7 of #61608. With `--enable-tower-connector-lora`, LLaVA-NeXT-Video's `get_mm_lora_token_counts()` counts 576 tower rows per frame, but vLLM's CLIP tower prepends a CLS token, so its LoRA layers actually see 577. The tower LoRA buffer is sized from this count, so encoder profiling overflows it and the engine fails to start:

```
$ vllm serve llava-hf/LLaVA-NeXT-Video-7B-hf --enable-lora --enable-tower-connector-lora
...
  File "vllm/lora/ops/triton_ops/lora_shrink_op.py", line 291, in _lora_shrink
    assert token_lora_mapping.size(0) == M
AssertionError
...
RuntimeError: Engine core initialization failed. See root cause above.
```

When startup does pass (e.g. `max_num_batched_tokens=16384`), the runtime mapping is still one row per frame short, so the last rows of each video get the next request's adapter, or none.

The fix computes the per-frame tower count from the config with `get_num_image_tokens()` (577 for CLIP, unchanged for SigLIP), the same way `llava_next.py` does. #61799 fixes the same bug in `llava.py`; no open PR touches these counts in `llava_next_video.py`.
