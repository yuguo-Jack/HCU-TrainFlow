# [Frontend] Tokenize the /v1/systemone state once per decision and let big decisions take turns

[Upstream PR](https://github.com/vllm-project/vllm/pull/61251) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Fixes #61249. The decision endpoints, `/v1/systemone` and `/v1/decisions`, now tokenize the shared state once per decision instead of once per question. A 64-question decision on a 27k-token state now runs at about the speed of its engine work. Big decisions also take turns in the engine, so a burst of them does not make small decisions wait for the whole burst. This applies to next-token models and to Decision 3.0 (D3) models.

The branch is on main 7020600b1d.

## Claims

- On Qwen3-4B, a 64-question decision on a 27k-token state takes 0.91 s instead of 2.91 s on its own. At 16 concurrent decisions it takes 8.24 s instead of 45.6 s (p50). `/v1/decisions` shows the same gains: 0.87 s instead of 2.74 s, and 7.65 s instead of 43.8 s.
- During a burst of 64 big decisions, a 1-question decision waits 1.99 / 3.49 s p50 / p95 (2.02 / 60.5 s on main). Throughput is 65 questions/s instead of 21.
- Answers are unchanged. With `VLLM_BATCH_INVARIANT=1`, all 634 Qwen3-4B answers on both endpoints are bit-identical to main.
- DiffusionGemma gets the same kind of win: 3.49 s → 1.59 s on its own, and 49.5 s → 12.7 s p50 at 16 concurrent decisions.
- On D3 (`vllm-sr/d3-mini`), a bystander waits 5.53 / 7.17 s instead of 58.7 / 109.7 s during a burst of 32 big decisions, at the same throughput.

## Validation

Every run compares this branch with main 7020600b1d. Each tree runs on its own H200. The server flags are `--max-model-len 32768` and `--gpu-memory-utilization 0.90`, with the default `--renderer-num-workers 1`. For Qwen3-4B this gives a `max_num_batched_tokens` of 8192.

Each concurrent client has its own state, and every state is warmed once before the timed rounds. Every decision has 64 questions unless a row says otherwise.

- **Bystander:** a 1-question decision on a short state, sent every second during the burst.
- **Floor:** `/v1/completions` with `max_tokens=1` on the same 64 prompts as token ids, so it measures the engine work alone.

No run had errors or preemptions.

## Details

**Root cause.** `NextTokenStrategy.read` rendered each question's user turn through `preprocess_chat`, once per question. That is two renderer pool jobs per question: the chat template and a full tokenization. The pool has one worker by default.

A 64-question decision on a 27k-token state spent about 2 s there, and every other request queued behind it. `D3Strategy.read` encoded each question's full prompt with the tokenizer on the event loop.

**Tokenize once.** For more than one question, the next-token read renders every question's prompt with the chat template, as the per-question path does. It then splits the rendered texts after the last `\n\n` they all share. That point falls right after the state in each strategy's own prompt format, before LiquidAI d1's `QUESTION:` header.

The read then tokenizes the text before the split once. For each question it tokenizes a short window: the last 64 characters before the split plus the question's own text. A decision costs N template renders, one tokenization of the shared prefix and N + 1 short ones, instead of a full tokenization per question.

Each prompt is the prefix ids plus the ids of its window after the head. The joined prompts still go through `preprocess_cmpl`, so the token length check and `cache_salt` apply as before. The prefix goes through the renderer's tokenize path with the request's tokenize params, so an oversized state still fails the character check before tokenization. A single question keeps the per-question render, which is cheaper there.

D3 builds its own prompts, so it applies the same split and head check to its prompt texts, after the media prefix when the request has media.

The read falls back to the full per-question render in these cases:
- the request has images (next-token models);
- the renderer returns token ids instead of text (Mistral tokenizers, prompt embeds);
- the prompts share no `\n\n`;
- a question's text after the split starts with whitespace, which could join a newline run longer than the head window;
- the last 64 characters before the split tokenize differently with a question after them.

The last check is a heuristic for tokenizers whose split depends on the next characters.

`OnlineRenderer.build_chat_params` is now shared with `preprocess_chat`.

**Why the gate.** With tokenization fast, every decision in a burst sends all its reads to the engine within a second or two. The engine serves them in arrival order. So a 1-question decision that arrives during a burst of long decisions waits for the whole burst.

**The gate.** It lives in the frontend.

- A decision with more than one question counts as big when its prompts hold more tokens than `max_num_batched_tokens`.
- With the prefix cache on, the shared state counts once, as the cache computes it once. Without it, as for D3, every prompt counts in full.
- At most two big decisions have reads in the engine at a time, and the rest wait in FIFO order.
- An admitted decision still sends all its reads at once, so its state stays in the prefix cache.
- Short decisions and 1-question decisions skip the gate.
- Under `--scheduling-policy priority` the gate is off, because the engine already orders requests by priority.
- The gate reads the scheduler and cache config when a decision arrives.

**One gate for both endpoints.** `/v1/systemone` and `/v1/decisions` share one read strategy, so they share one gate. A big decision on either endpoint takes a slot from the other.

**Coverage.** Qwen3, Qwen3.5, Qwen3.5-MoE, DiffusionGemma, LiquidAI d1 and D3 splice and are gated. DiffusionGemma and d1 inherit `read()` from the next-token strategy. Clef-Omni and Clef-Flash encode their own prompts and read a whole decision as one pooling request, so they never splice and are not gated.

**Limits.**
- The gate is per API server process, so N API servers admit up to 2N big decisions. `api_server_count` defaults to the data-parallel size.
- `--max-num-queued-reqs` and `--max-num-queued-tokens` do not count decisions waiting at the gate, so a waiting decision can still get a 503 when its reads are added.
- Under `--scheduling-policy priority` the gate is off. A bystander then needs a lower priority value than the burst to get through quickly.
- When every decision in a burst shares one cached state, the gate trades some throughput for the bystander's latency.
- 1-question decisions on a long state are not gated. A bystander behind 64 of them waits as it would behind 64 long completions.
- Generative scoring (`generative_scoring/serving.py`) fans out its reads the same way. I left that for a separate change.

**Size.** +193 / −48 non-test lines, in `strategies.py` and `online_renderer.py`.
