# [MRV2][Spec Decode] Context Aware Sparse LM Head

[Upstream PR](https://github.com/vllm-project/vllm/pull/59740) · state: open · merged: False

## Original PR description

## Overview

**+13.8% decode at c=1 (+7.7% at c=4) from the sparse LM head alone**, with average AL unchanged (+0.1%), on Qwen3.8-Flash-Next-NVFP4 + MTP (k=3) on one DGX Spark. It composes with quantization: +23.3% with NVFP4 rows, and +5.5 to 7.9% on top of a full NVFP4 draft head (#59973) across draft lengths k=3 to 8. On Nemotron 3.5 Lightning MTP (k=7) the draft step is 0.816x of dense with BF16 rows. Addresses #58578.

**Why:** an MTP drafter reads the target's full lm_head for every draft token (248k x 2560 in BF16 on Flash-Next), so on bandwidth-bound GPUs the head dominates the draft step, while only a small, context-dependent part of the vocabulary is likely. A fixed list alone loses 5.7% of average AL and 33% on multilingual SPEED-Bench prompts. **How:** the drafter scores a fixed token list plus, per draft token, the rows outside it that score best under a rank-256 projection of the lm_head, and computes exact logits only for those rows. The target still verifies with its full head, so only the acceptance length can change.

Opt-in keys in `speculative_config`: `draft_token_map` (SGLang `.pt` or JSON list) and `draft_token_map_dynamic_rows`; with `draft_lm_head_quantization` only the copied rows are quantized. Supported on Qwen3.5, Qwen4Exp and NemotronH MTP. Draft-vocabulary handling moves into model code: one `DraftVocab` helper returns target-vocabulary logits, and EAGLE3, DFlash and DSpark use it instead of their own `draft_id_to_target_id` scatter.

## Results

Disclaimers:
- Low-concurrency feature: dynamic rows are gathered per token, so the gain shrinks with tokens per step (c=4 above; Lightning at c=8 measured +2.8% aggregate for BF16 rows over dense).
- Lightning step time is measured with forced acceptance (AL 3.75, 22 prompts, 1024 tokens); real AL comes from standard rejection at c=8 (44 prompts, up to 4096 tokens); projected decode = real AL / step time.
- Multilingual AL drops 5 to 8% on Flash-Next (a static list alone loses 30% or more).
- Every comparison is a same-node pair.

<details><summary>Design details</summary>

- `vllm/model_executor/layers/draft_vocab.py`: `DraftVocab.compute_logits` returns target-vocabulary logits that are `-inf` outside the draft vocabulary; `get_top_tokens` keeps local-argmax greedy drafting without full logits. The subset is either a checkpoint-pruned head with `draft_id_to_target_id` (EAGLE3, DFlash, DSpark) or the `draft_token_map` rows of a shared full head.
- MTP drafters share the target lm_head only inside `load_eagle_model`, so the rows are copied right after sharing; that is the one speculator-side hook.
- Quantized rows use the platform's weight-only kernels (`init_wfp8_a16_linear_kernel`, `init_nvfp4_linear_kernel`).

</details>

This PR does not change verification, add `draft_token_map` to EAGLE3/DFlash/DSpark (they already prune in the checkpoint), or support lm_heads quantized in the checkpoint (rejected at load, #60226). `draft_token_map` needs tensor parallel size 1.

- kosztyua · comment · 2026-10-05T14:37:58Z · [source](https://github.com/vllm-project/vllm/pull/59740#issuecomment-5996702123)

Hi @stecasta, we tried this on our TP2 setup (2× DGX Spark, eager, MTP k=4, nvidia/Qwen3.8-Flash-Next-NVFP4, MRV2) with dynamic rows extended to TP>1. Two things came up:

1. **Splitting the list by vocab shard leaves it almost entirely on rank 0.** Frequent tokens have low ids: with the Qwen tokenizer on ~17M tokens of code/docs, 97% of a top-32k frequency list falls in the first half of the vocab. So at TP2 the static part doesn't shrink. Splitting the sorted list into equal contiguous chunks (each rank fetches the rows it doesn't own once at load, with one all-reduce) fixes that and keeps the gathered columns in sorted-id order, so `restrict`/`scatter`/`to_target` are unchanged.
2. **Dynamic rows at TP>1:** we all-reduce the Gram once so every rank uses the same basis. Each rank picks `ceil(rows / tp)` off-list rows from its own shard, and greedy drafting reduces local `(logit, id)` pairs with one small all-gather, so no per-token id exchange is needed. Probabilistic drafting with dynamic rows is still rejected at TP>1.

Results (32k list = ids 0..32767 + added tokens, greedy 1024-token decode, each arm a fresh start):

| draft head | decode c=1 | AL |
|---|---:|---:|
| BF16 full head | 36.9 tok/s | 2.693 |
| FP8 full head (#56577) | 43.7 | 2.693 |
| 32k + 16k dynamic (8k/rank) | 44.8 | 2.695 |
| 32k + 32k dynamic (16k/rank) | 44.0 | 2.695 |

Greedy outputs were byte-identical across arms. That's about +21% over the BF16 head at TP2 with no AL loss on our prompts, though only marginal over an FP8 full head at TP2. At c=4 the dynamic arms were within run-to-run noise of the FP8 head. Your existing tests pass unchanged; the by-shard layout test is replaced by emulated-TP2 tests for the balanced split and the dynamic-row argmax (17/17 on CPU).

If it's useful, I can rebase this onto your branch and push it for you to pull in.

Since a few more people are following this thread now, here's the fuller picture on our side — thanks for the patience with a longer comment.

**What we're actually trying to fix.** We didn't start from this PR's mechanism; we started from a narrower problem. The draft vocabularies shipped today (this PR's included, and the kit we built on) are frequency-ranked on English and code. That's not a neutral default — it means speculative decoding speeds up English the most and helps non-English speakers the least, by construction, unless someone extends the list for their language. We built a Korean 65k file for `nvidia/Qwen3.8-Flash-Next-NVFP4` first (+54% decode on Korean prompts over the shipped en+code list, acceptance 1.33 → 2.16, zero replacement characters) and are extending the same recipe to roughly 19 more languages across Asia, Africa and the Western languages not yet covered. It's a non-profit, public-interest effort on our side — no customer data, no paid product behind it, Apache-2.0: https://github.com/veneta-ai/mtp-draft-vocab-ko.

**What we learned here.** Three things changed how we think about this: the context-aware dynamic rows (static list + per-token rank-256-SVD-picked rows) are a real answer to the exact problem we have — a per-language static file is a workaround, not a fix, and this design doesn't need one; @kosztyua's TP>1 data caught a failure mode we hadn't tested for yet (sharding a frequency-sorted list by vocab range puts ~97% of it on one rank, so naive TP>1 barely shrinks anything — the fix is a balanced contiguous-chunk split); and @stecasta's read of our own +54% number was right — that's list-vs-list on a language the baseline doesn't cover, not a speedup over an unrestricted head, and worth saying plainly rather than letting readers assume the bigger claim.

**Our plan once this merges.** We'll open a follow-up PR wiring the four model classes we've measured — plain EAGLE (`yuhuili/EAGLE-LLaMA3.1-Instruct-8B` on Llama 3.1 8B, +13.4% decode), `exaone4_5_mtp` (EXAONE 4.5, +7.0%), `glm4_moe_mtp`, and `deepseek_mtp` — into the shared `DraftVocab` helper rather than keep our own attach-at-load mechanism around. #60387 closes once that's up. We're watching for the merge and will follow up here.
