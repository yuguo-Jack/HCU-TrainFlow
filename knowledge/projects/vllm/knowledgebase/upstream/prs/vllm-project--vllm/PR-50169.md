# [Core][Spec Decode] Fix KV cache allocation for sliding-window drafters and local-attention pool sizing

[Upstream PR](https://github.com/vllm-project/vllm/pull/50169) · state: open · merged: False

## Original PR description

## Purpose

Three fixes around KV cache allocation for local-attention models and spec-decode
drafters. Found via Laguna-S-2.1 + DFlash, but only one commit is model-specific.
On current main (GB10, Laguna-S-2.1-NVFP4, DFlash, fp8 KV, max_model_len
131072, max_num_seqs 16, 23.1 GB KV pool) the series takes the KV pool from
415,517 to 871,430 tokens (2.1x), with draft acceptance unchanged.

1. Drafter layers of EAGLE-family speculators get scattered across KV cache
   groups by the strided group assignment in
   `_get_kv_cache_groups_uniform_page_size`. Fix: identify drafter layers
   (index >= target layer count, gated on `use_eagle()`) and give dedicated
   groups to the specs whose drafter layers would otherwise share a group with
   target layers. Sharing corrupts the drafter's absolute-slot context writes,
   which resolve through the target's block table: on Laguna-S-2.1 draft
   acceptance falls to 0.29% versus 26.67% with a dedicated group, at an
   identical pool size. On the V1 model runner the same layout instead trips
   the assertion in `SpecDecodeBaseProposer.validate_same_kv_cache_group` at
   startup. Separation is conditional because regrouping changes the
   group-size heuristic's inputs: separating regardless cut Qwen3.5-9B's pool
   from 863k to 185k tokens. Works for any PP size; the strided layout still
   applies to target layers.
2. `laguna_dflash.py` cleared the drafter's `attn.sliding_window`, forcing
   FullAttentionSpec on all 6 drafter layers (measured 38% of the pool for KV
   outside the window the drafter never reads). The `DFlashQwen3Model` base
   class already supports windowed draft layers; the clearing appears to be a
   workaround for the group-sharing corruption fixed in commit 1. Qwen3.5 DFlash
   avoids that corruption because its per-layer specs already give one group
   per layer, so its drafter never shares. Fix: keep the checkpoint-declared
   window.
3. `SlidingWindowSpec` and `ChunkedLocalAttentionSpec` charge the global
   `max_in_flight_tokens` bound to every request when sizing the pool. Since
   `sum_r (window - 1 + in_flight_r) <= R*(window - 1) + max_in_flight_tokens`,
   per-request sizing only needs the request's share of the allowance. Fix:
   amortize over `max_num_seqs`; the runtime admission gate is unchanged, and
   sizing is identical to today at `max_num_seqs = 1`. Without this, fixes 1
   and 2 barely show (347k to 352k tokens), because sliding layers are charged
   almost like full attention.

## Scope

- Commit 1: any EAGLE-family drafter (eagle/eagle3/mtp/dflash/dspark) over a
  hybrid target. All in-tree EAGLE-family implementations register drafter
  layers with indices continuing after the target's
  (`start_layer_id=target_layer_num` / `mtp_start_layer_idx=num_hidden_layers`),
  so identification cannot misclassify a target layer; unparseable names are
  skipped. No speculative config means grouping is unchanged.
- Commit 2: Laguna only. Removes a divergence from its own base class.
- Commit 3: every model using SlidingWindowSpec (Gemma 2/3/4, gpt-oss,
  Command R, EXAONE 4, and others), SlidingWindowMLASpec by inheritance, and
  ChunkedLocalAttentionSpec (Llama 4 style local attention). Broadest behavior
  change of the three; can be split into its own PR if preferred. The chunked
  local part is unit-tested only (no such model available for E2E here).

## Not duplicating existing PRs

- #35062: same root cause as commit 1 (referenced in the commit message),
  stalled on rebase since June. Differences: per-spec drafter groups (a single
  merged group would mix specs for hybrid drafters), identification gated to
  `use_eagle()` (independent `draft_model` drafters number from 0), rebased
  with tests. Happy to defer to a revived #35062; will comment there.
- #46032: relaxes the same-group invariant for `DraftModelProposer` only.
  EAGLE-family proposers still assert a single group. Complementary.
- Nothing open covers commits 2 or 3.

- d3nb · comment · 2026-08-18T15:15:26Z · [source](https://github.com/vllm-project/vllm/pull/50169#issuecomment-5330216396)

**Commit 3 can relax the startup feasibility gate below what runtime admission requires (hybrid MLA + sliding-window, large `max_model_len`)**

Thanks for this series — we carry commit 3 (`f401599bb`) downstream because without it our
config cannot start at all. Reporting a correctness concern about that commit specifically.

**Symptom.** The engine starts, logs a max-concurrency above 1.0 for `max_model_len`, and then
never schedules a single request of that size. The request sits in the waiting queue
indefinitely: `num_requests_waiting=1`, `num_requests_running=0`,
`iteration_tokens_total` stays at 0, `kv_cache_usage_perc` stays at 0. Cancelling the client
clears the queue and the server stays healthy. This is the #39734 deadlock shape.

**Why commit 3 is implicated.** `max_memory_usage_bytes` feeds
`_check_enough_kv_cache_memory` ("can we serve at least one request at `max_model_len`") and
`get_max_concurrency_for_kv_cache_config` (the logged concurrency). Commit 3 divides the
in-flight term by `max_num_seqs` there. The runtime path is unchanged and still charges the
full allowance: `allocate_slots(..., full_sequence_must_fit=scheduler_reserve_full_isl)`
(default `True`) computes the whole sequence via `get_num_blocks_to_allocate(...,
apply_admission_cap=True)` and compares against actual free blocks. So the startup gate can
pass at a pool the runtime gate will always reject.

**Config** (identical across all rows): vLLM v0.27.1 with only commit 3 applied;
DeepSeek-V4-Pro (MLA + two sliding-window sizes) + DSpark speculative decoding
(`num_speculative_tokens=7`); DP4 x EP4, prefill on 4x B300 (267.69 GiB each);
`max_model_len=1048576`, `max_num_seqs=64`, `max_num_batched_tokens=8192`,
`block_size=256`, fp8 KV, chunked prefill and prefix caching on, async scheduling on.

| `gpu_memory_utilization` | prefill KV pool | single 1,000,000-token request |
| --- | --- | --- |
| 0.94 | 9.60 GiB / 7,176 blocks | never scheduled (>12 min, zero iteration tokens) |
| 0.955 | 13.61 GiB / 10,179 blocks | never scheduled |
| 0.96 | 14.55 GiB / 10,880 blocks (DP0), 11,180 (DP1-3) | admitted, HTTP 200 in 176-187 s |

At 0.94 the startup log reads:

```text
GPU KV cache size: 1,780,544 tokens
Maximum concurrency for 1,048,576 tokens per request: 1.70x
```

Back-solving that line (`num_blocks / concurrency`) gives **4,226 blocks per `max_model_len`
request**, while the runtime gate demands **10,180-10,880 blocks** for a slightly smaller
(1,000,000-token) request — a **2.4-2.6x under-estimate**. The engine advertises 1.70x
concurrency for a request size it cannot admit even once.

A coarse bisect at 0.94 (7,176 blocks) puts the largest schedulable prompt between 300,000
and 400,000 tokens: 300k completes in 35 s, 400k is never scheduled.

**Supporting datapoint for the direction of the error.** Without commit 3, on the same model
and `max_model_len`, `_check_enough_kv_cache_memory` demands 15.36 GiB and refuses to start
at 0.95 (12.27 GiB available). That is above the 13.6-14.55 GiB the runtime actually needs,
i.e. the un-amortized gate errs conservatively. The amortized gate crosses below it.

**We tested commit 1 (`ecb28b3fa`) on this config; it does not address this.** Rebased onto
v0.27.1 (4 of 5 hunks apply; the `same_type_layers` hunk needs a manual rebase because v0.27.1
inserts a "further merge same-type layers" step after that loop). Applicability checks passed
before running: `use_eagle()` covers `dspark`, and this model's DSpark drafter registers its
attention layers as `layers.{num_hidden_layers + i}`, so `_identify_drafter_layers` finds them.
With the commit applied, the startup accounting is unchanged — `Maximum concurrency` stays at
2.57x/2.65x and the DP0 pool at 10,873 vs 10,860 blocks — and the runtime behaviour is
unchanged too. The conditional separation appears not to trigger here, i.e. our drafter layers
already have their groups to themselves. No regression from it either.

**Operational consequence.** Because the gate passes, the operator ends up choosing
utilization from the wrong number, and the remaining device headroom has to absorb both
CUDA graph capture and execution scratch. With CUDA graphs enabled at the utilization that
admits 1M, graph capture takes 3.94 GiB/device and prefill then dies mid-request with
`torch.OutOfMemoryError: Tried to allocate 976.00 MiB ... 857-869 MiB is free`, killing the
engine core. Reproduced twice, with and without commit 1. Our current workaround is asymmetric:
CUDA graphs on the decode instance only, prefill forced eager. That restores throughput
(decode-side ITL P95 71 ms -> 15 ms on an internal agent benchmark) while keeping 1M
schedulable, but it is a workaround for the accounting gap, not a fix.

**Suggested direction.** If the amortized value is the right one for aggregate pool-capacity
planning, it may still be worth having `_check_enough_kv_cache_memory` — and ideally the
logged `Maximum concurrency` — use the same per-request bound the runtime admission gate uses
(`max_admission_blocks_per_request` with the full `max_in_flight_tokens`), so that "can one
`max_model_len` request fit" and "will the scheduler admit it" cannot disagree.

**What we did not establish.** We did not isolate which KV cache group's accounting produces
the 2.4x gap — only the aggregate. We have not written or tested a patch for the gap itself.
Happy to run any candidate on this config.

- stu-cao · comment · 2026-10-09T03:36:26Z · [source](https://github.com/vllm-project/vllm/pull/50169#issuecomment-6073753156)

A data point relevant to commit 2 (keeping the drafter's checkpoint-declared window). It comes from a different model, but it is the same mechanism you'd get with a windowed Laguna drafter.

In #60560 we root-caused a DFlash2 acceptance drop (~40% → 27–29% at 32 concurrent sessions) that occurs only when the drafter's layers form a real sliding-window KV cache group. When `SlidingWindowManager` frees a block, the worker's block table keeps the old id. FA4 loads KV in 128-key tiles on SM100, so with 64-token pages the tile holding the window start can include one page that lies wholly outside the window. Once that freed block is reused, its bytes can decode as fp8 NaN, and masked NaN still reaches the attention output.

Two conditions hide it, so the GB10 checks here may not show it:
- **Low concurrency.** It nearly vanishes at concurrency 1 (37.9%), because freed blocks are rarely reused in time.
- **Tile size.** It needs the attention kernel's KV tile to be larger than the KV page. FA4 picks 64-key tiles on SM12x (for head dim > 64), so 64-token pages are safe there, while SM100 uses 128-key tiles.

It's worth re-checking Laguna acceptance on an SM100 GPU under sustained concurrency before relying on the windowed drafter. The fix, #60767 (nulling freed sliding-window entries in the worker's forward-pass block tables), would cover this PR's case too.
