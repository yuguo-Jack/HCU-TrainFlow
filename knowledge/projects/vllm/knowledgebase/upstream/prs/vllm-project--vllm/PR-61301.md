# [Bugfix][LoRA] Respect moe_backend and guard fully-sharded LoRAs in MoE selection

[Upstream PR](https://github.com/vllm-project/vllm/pull/61301) · state: open · merged: False

## Original PR description



## Overview

Fixes #61286

This PR resolves two related issues in unquantized MoE LoRA backend selection:
1. When LoRA is enabled, `select_unquantized_moe_backend()` previously checked `_trtllm_bf16_lora_supported()` first without honoring `moe_config.moe_backend`, silently overriding `--moe-backend triton` on SM100-family GPUs.
2. The TRT-LLM LoRA path (`TrtLlmBf16LoRAExperts`) calls `apply_w13_lora(..., add_inputs=False)`, but `fused_moe_lora` asserts that `add_inputs=False` is only supported when `fully_sharded=False`. Consequently, running with `--fully-sharded-loras` crashed at `profile_run` with an AssertionError.

## Claims

- **Honor explicit `--moe-backend`**: When LoRA is enabled, passing `--moe-backend triton` now explicitly selects Triton on all platforms (including SM100) instead of being overridden by FlashInfer TRT-LLM.
- **Guard `--fully-sharded-loras` in TRT-LLM LoRA path**: `TrtLlmBf16LoRAExperts.is_supported_config()` now marks `fully_sharded_loras=True` as unsupported. Under `auto` selection, the oracle gracefully falls back to Triton (which supports fully-sharded LoRA). If `--moe-backend flashinfer_trtllm` is explicitly requested with `--fully-sharded-loras`, a descriptive `ValueError` is raised at configuration time rather than crashing during `profile_run`.
- **Pass `fully_sharded_loras` to `FusedMoEConfig`**: Added `fully_sharded_loras: bool = False` to `FusedMoEConfig` and populated it in `FusedMoEFactory`.
- **Comprehensive Unit Tests**: Added unit test coverage for explicit Triton selection with TRT-LLM available, fallback to Triton under `fully_sharded_loras=True`, and configuration error when explicit TRT-LLM is combined with `fully_sharded_loras=True`.

## Details

### Root Cause
In `vllm/model_executor/layers/fused_moe/oracle/unquantized.py`:
- `select_unquantized_moe_backend()` checked `if moe_config.is_lora_enabled:` and immediately checked `if _trtllm_bf16_lora_supported(moe_config): return FLASHINFER_TRTLLM, TrtLlmBf16LoRAExperts`. It never inspected `moe_config.moe_backend`.
- `_TrtLlmLoRAExpertsBase` did not implement `is_supported_config()`, inheriting from `mk.FusedMoEExperts` which has no awareness of `fully_sharded_loras`. When `TrtLlmBf16LoRAExperts.apply()` is executed, it calls `apply_w13_lora(add_inputs=False)`, where `_fused_moe_lora` asserts `assert add_inputs or not fully_sharded`.

### Solution
1. In `select_unquantized_moe_backend()`:
   - Check if `runner_backend == "triton"`; if so, directly return Triton.
   - If `runner_backend == "flashinfer_trtllm"`, check `TrtLlmBf16LoRAExperts.is_supported_config()` and raise `ValueError` if unsupported.
   - If `runner_backend in ("auto", "humming")`, query `_trtllm_bf16_lora_supported(moe_config)` and only select `TrtLlmBf16LoRAExperts` if supported, otherwise falling back to Triton.
2. In `_TrtLlmLoRAExpertsBase`:
   - Implement `is_supported_config()` to return `(False, "kernel does not support fully_sharded_loras")` when `moe_config.fully_sharded_loras` is True.
3. In `FusedMoEConfig` and `FusedMoEFactory`:
   - Propagate `fully_sharded_loras` from `lora_config`.
