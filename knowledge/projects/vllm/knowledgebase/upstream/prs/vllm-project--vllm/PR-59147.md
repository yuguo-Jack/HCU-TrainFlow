# [Bugfix][GLM-5.3-Flash] Honor `--mamba-ssm-cache-dtype` for the KDA recurrent state

[Upstream PR](https://github.com/vllm-project/vllm/pull/59147) · state: closed · merged: True

## Original PR description

## Purpose

`Glm5NextLinearAttention.get_state_dtype()` and `Glm5NextForCausalLM.get_mamba_state_dtype_from_config()` call `MambaStateDtypeCalculator.kda_state_dtype()` without the SSM cache dtype. As a result, the KDA recurrent state is always float32, and `--mamba-ssm-cache-dtype bfloat16` is **silently ignored** for GLM-5.3-Flash. Kimi-K3's KDA already passes it through.

This PR passes `cache_config.mamba_ssm_cache_dtype` in both places. `Glm5NextForConditionalGeneration` delegates to the causal-LM class, so it is fixed too.

Why it matters: with bfloat16 the recurrent state page halves. Mamba align-mode prefix caching sizes the attention block from that page, so at TP2 the block shrinks from 2304 to 1280 tokens. With speculative decoding, each running request holds `2 + num_speculative_tokens` state blocks per group, so on decode instances this state is what bounds concurrency.

## Test Plan

- New test `tests/models/glm5next/test_kda_state_dtype.py`:
  - `auto` / `float32` / `bfloat16` must reach both the model-level and the layer-level recurrent-state dtype;
  - the bf16 case fails on main.
- Existing tests: `tests/models/glm5next`.
- End to end: GLM-5.3-Flash, TP2, B300, with `--mamba-ssm-cache-dtype bfloat16`:
  - the KV-cache spec now reports the bf16 state page;
  - teacher-forced NLL on long-context prompts is unchanged within run-to-run noise vs the float32 state.

## Test Result

- `tests/models/glm5next`: 14 passed.
- With bf16 state, a spec-decoding decode instance (K=4, P/D serving) fits ~1.25× more concurrent requests before running out of state blocks (≈64 → 80+).

AI assistance (Claude) was used; every line was reviewed and the tests above were run by the submitter.

I tested the same change (the same two call sites, as a local patch) on nightly `8cbd5d03`, and it helps a long-context agentic workload. Sharing the numbers in case they are useful for review.

Setup: GLM-5.3-Flash, 4× B200, TP1 × DP4 + EP, FP8 KV cache, MTP K=5, `--prefix-match-unit 16`, `SimpleCPUOffloadConnector` (300 GB per rank). MoE ran through the MegaMoE path from #60895, so the absolute numbers are not stock-main numbers. One run per arm.

Startup, per rank:

| | fp32 state | `--mamba-ssm-cache-dtype bfloat16` |
|---|---:|---:|
| Attention block size (tokens) | 8,960 | 4,864 |
| GPU KV cache size (tokens) | 8,821,237 | 9,676,485 (+9.7%) |

InferenceX AgentX trace replay (aiperf), 96 concurrent sessions, 3,600 s, mean prompt about 120K tokens:

| | fp32 state | bf16 state |
|---|---:|---:|
| Output tok/s | 3,332 | 3,454 (+3.7%) |
| Total tok/s | 402,628 | 417,912 (+3.8%) |
| TTFT mean / p50 / p99 (s) | 0.81 / 0.49 / 5.99 | 0.75 / 0.44 / 6.02 |
| ITL mean (ms) | 19.5 | 17.9 |
| Prompt tokens served from the GPU prefix cache | 71.2% | 86.8% |
| Prompt tokens reloaded from host offload | 22.8% | 7.5% |
| Preemptions | 2 | 0 |

`vllm bench serve`, random 1024 in / 1024 out at concurrency 128: 11,691 → 12,289 output tok/s (+5.1%).

Accuracy, with real MTP acceptance:

- GSM8K (lm-eval, 5-shot, 1,319 questions): bf16 0.9735 ± 0.0044, fp32 0.9704 ± 0.0047.
- Key-to-value retrieval from a ~120K-token prompt (24 prompts × 4 positions): 96/96 for both.

The throughput arms used synthetic acceptance (length 3.61). The measurements were run with AI assistance (Claude Code).
