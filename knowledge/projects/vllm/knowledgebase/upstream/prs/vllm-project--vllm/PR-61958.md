# [Perf][Multimodal] Chunk Qwen3-VL vision blocks to cut the encoder profiling peak

[Upstream PR](https://github.com/vllm-project/vllm/pull/61958) · state: closed · merged: False

## Original PR description



## Overview

At startup, vLLM profiles the Qwen3-VL-family vision tower (Qwen3-VL, Qwen3.5/3.6/3.8 VLMs) on one max-size image (65,536 patches). The activation peak of that eager pass is about 12× the hidden states, and the KV cache loses that memory. This PR runs the per-token parts of each vision block in 8,192-token chunks for images above that size, which brings the peak down to about 5×. On a 32 GB RTX 5090 serving Qwen3.8-27B-NVFP4, that gives the KV cache about 1 GiB more, or +14.6 % tokens.

Related: #51537 (open) removes the q/k copy in the same `Qwen2_5_VisionAttention` code to cut latency, and says it leaves the tower-level peak unchanged. The two changes are independent. #49540 changes what the language-model side profiles, not the encoder.

## Claims

- Qwen3.8-27B-NVFP4 on 1× RTX 5090: the startup activation peak (CUDA-graph estimate excluded) drops from about 1.69 to 0.70 GiB, and the KV cache grows from 86,935 to 99,641 tokens (+14.6 %) at `--max-num-seqs 32` and from 82,923 to 95,629 (+15.3 %) at `--max-num-seqs 100`.
- On a KV-bound load (1k in / 256 out, concurrency 64), the most requests running at once goes from 25 to 29. Output throughput is +4 to +5 % (3/3 pairs), and median TTFT at concurrency 32 is 27–35 % lower.
- Vision tower latency is unchanged (0.99–1.01×). Images with ≤ 8,192 patches never take the new path, so their output is unchanged.
- Images with more than 8,192 patches (about 2.1 MP) get different bf16 rounding. They are no further from an fp32 reference than before (table below).

## Validation

Setup: 1× RTX 5090 32 GB (power capped at 500 W), main at a8be1500ba, torch 2.14.0+cu130, `vllm serve nvidia/Qwen3.8-27B-NVFP4 --max-model-len 32768 --max-num-seqs {32,100}`. All other options are defaults (MRv2, CUDA graphs, FLASH_ATTN ViT backend, prefix caching). A = main, B = this PR. Each server start was repeated, and the memory numbers are identical across repeats. The GPU runs used an earlier revision of this commit. The only differences are that the backend check is now inlined and `is_compiling()` is checked first; neither changes the eager path.

**Memory / capacity** (from the engine's startup log)

| max-num-seqs | activation peak A → B | KV tokens A → B | max running (c=64) A → B |
|---|---|---|---|
| 32 (2 starts/arm) | 1.69 → 0.70 GiB | 86,935 → 99,641 (+14.6 %) | 25 → 29 |
| 100 (2 starts/arm) | 1.69 → 0.70 GiB | 82,923 → 95,629 (+15.3 %) | 24 → 27 |

With image/video profiling turned off (`--limit-mm-per-prompt '{"image":0,"video":0}'`, warm compile cache), the floor from the language model alone is 0.27–0.28 GiB, so after this PR the peak (0.70 GiB) still comes from the vision tower.

**Serving** (`vllm bench serve --dataset-name random --random-input-len 1024 --random-output-len 256 --ignore-eos --request-rate inf`, 96 prompts at c=32 and 192 at c=64). The three pairs are A/B run back to back:

| pair | output tok/s c=32 | output tok/s c=64 | median TTFT c=32 | median TTFT c=64 |
|---|---|---|---|---|
| 32 seqs, pair 1 | 769.7 → 764.9 (−0.6 %) | 772.0 → 812.3 (+5.2 %) | 1187 → 863 ms | 9944 → 10017 ms |
| 32 seqs, pair 2 | 831.7 → 845.7 (+1.7 %) | 850.2 → 885.4 (+4.1 %) | 1232 → 807 ms | 9310 → 9360 ms |
| 100 seqs | 733.6 → 772.3 (+5.3 %) | 727.5 → 765.2 (+5.2 %) | 1351 → 902 ms | 13420 → 9881 ms |

This workload has a lot of prefill, and B runs more requests per step, so TPOT goes up by about 5–10 % at 32 seqs (it is flat at 100 seqs). Throughput moves much less than capacity. Absolute numbers differ between pairs: the first start of each pair compiled from a cold cache and the second loaded a warm one. Each pair compares like with like.

**Vision tower alone** (real Qwen3.8 vision weights, synthetic inputs, median of 5 runs; peak measured above the inputs)

| patches | peak A → B | latency B/A | B vs A | A vs fp32 ref | B vs fp32 ref |
|---|---|---|---|---|---|
| 65,536 (profiled max) | 1.696 → 0.716 GiB | 0.995 | rel-L2 2.05e-2 | 2.34e-2 | 2.12e-2 |
| 24,576 | 0.636 → 0.337 GiB | 0.989 | rel-L2 1.93e-2 | 2.33e-2 | 2.42e-2 |
| 12,288 (two images, chunked) | 0.321 → 0.231 GiB | 1.008 | bit-exact | | |
| 4,096 | 0.106 → 0.097 GiB | 1.002 | bit-exact | | |

Repeated runs of A are bit-exact. The fp32 reference is the same tower in fp32 with SDPA. The chunked 12,288-patch case is bit-exact, which suggests the differences at larger sizes come from GEMM kernel selection at different M rather than from the chunked code path. I have not tested that directly.

**End-to-end accuracy:** I ran DocVQA validation on 200 questions whose images are larger than 2.2 MP (2.6 MP and larger, so all of them go through the chunked path), greedy, 8 concurrent requests, both arms sharing one compile cache. ANLS went from 0.9622 to 0.9614 (−0.0008; paired bootstrap 95 % CI [−0.018, +0.015]), with 183/200 answers identical. I did not run A against itself, and batching across concurrent requests is not deterministic, so the 17 differing answers are not all due to this PR.

**Tests**
- `pytest tests/models/multimodal/test_qwen3_vl_vision.py`: 1 passed (CPU, fp32). The test runs a tiny tower with chunk boundaries inside an image and across two images, checks that every block takes the chunked path, and compares the result with the unchunked path. It caught 6/6 injected bugs: wrong RoPE slice, dropped residual, wrong MLP, misplaced K, wrong sin slice, and residual not added after proj.
- `pre-commit run --files <changed files>`: passed.
- CI: the test is marked `cpu_test`, like `test_conformer_encoder.py` and `test_aria.py` in the same folder. As far as I can tell, no current Buildkite step runs those files. The Qwen3-VL `core_model` tests use images below the threshold, so CI does not exercise the chunked path on GPU.

## Details

- **Where the peak comes from:** while the attention half of a block runs, the eager pass holds the residual, `norm1(x)`, qkv (3u), the contiguous q/k copy (2u), the rotated q/k (2u), the context and the projection. The MLP half holds fc1 and its GELU (3.7u each). `pos_embeds` (1u) also stays alive for the whole forward. Here u = tokens × hidden × 2 B, which is 0.14 GiB for the max image.
- **Change:** in `Qwen3_VisionBlock.forward`, for inputs longer than `_VIT_CHUNK_TOKENS` (8,192) and only when the block is not being compiled, `_forward_chunked` does the following:
  1. Writes norm1 → qkv → RoPE chunk by chunk into preallocated q/k/v buffers.
  2. Runs attention once over the whole sequence, with the same varlen call and `cu_seqlens` as before.
  3. Computes `x + proj(context)` chunk by chunk into a new buffer.
  4. Adds the MLP output in place, chunk by chunk.

  Separately, `Qwen3_VisionTransformer.forward` releases `pos_embeds` once it has been added, but only when it created the metadata itself.
- **Scope:** the chunked path is used with FLASH_ATTN / ROCM_AITER_FA and TORCH_SDPA. It is not used with FlashInfer (cuDNN expects V at the interleaved QKV stride) or with FP8 ViT attention, which quantizes Q/K/V itself. In both cases behavior is the same as today. The `is_compiling()` check comes first, so a compiled encoder (`compile_mm_encoder=True`) traces the same graph as before and gets no size guard.
- **Not validated:** ROCm, TP > 1 for the vision tower (the row-parallel `proj` and MLP `fc2` then each do one all-reduce per chunk, so up to 16 per block for the max image instead of 2), and encoder CUDA graphs with a budget above 8,192 tokens.
- **Where it matters:** GPUs whose KV pool is small compared with the encoder peak. On a 5090, the default `max_num_seqs=256` does not start with or without this PR (OOM while profiling CUDA graph memory; with that fixed, vLLM rejects 256 seqs because only 113 Mamba blocks fit). The gains above are for the reduced `--max-num-seqs` that 5090 users already have to set. On 80 GB GPUs I expect a few percent at most; I have not measured that.
- **Duplicate check:** I searched open and closed PRs for ViT/vision encoder chunking and peak memory (Qwen3-VL, qwen3_vl, MMEncoderAttention, encoder profiling) and found no PR doing this. #51537 and #43580 touch the same code for other reasons.
