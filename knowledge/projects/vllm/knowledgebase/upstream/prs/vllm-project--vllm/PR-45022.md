# [Bugfix][Model] Voxtral realtime: fix boot OOM and engine crash at max_model_len

[Upstream PR](https://github.com/vllm-project/vllm/pull/45022) · state: closed · merged: True

## Original PR description

Fixes for Voxtral realtime, all in the model and the realtime entrypoint. The unbounded-duration part is #45833 (stacked).

### Update 2026-10-05

Reworked after @andylolu2's review: no core changes anymore. Scheduler, runner and output_processor changes dropped (#58942 covers ERROR/ABORT, #42502 the generic scheduler guard).

### Fixes

- **Boot OOM (#38233)**: profiling runs one audio item of `max_model_len` tokens. With the default `max_model_len` (131072) that OOMs at boot on 16 GB. New `VoxtralRealtimeProcessingInfo`: the profiling audio is the largest streaming chunk (the prefix, 39 tokens), `{"audio": 1}` per update. The item size stays `max_model_len` because it also sizes the encoder cache: a paused session keeps its last chunk cached until it resumes, and a cache sized to one chunk deadlocks concurrent sessions (0/12 at `--max-num-batched-tokens 256`).
- **Engine crash at `max_model_len`**: a streaming session reaching the limit kills the EngineCore (`illegal memory access`) and every other session with it. `VoxtralRealtimeBuffer` now counts submitted tokens and ends the stream before `max_model_len`, so the session finishes normally.
- **WebSocket disconnect**: cancelling the generation task doesn't abort the engine request, the slot stays held. Cleanup now aborts it.

### Tests

RTX 4090 Laptop 16 GB, `--hf-overrides` sliding window 256, PIECEWISE:

- `--max-model-len 131072`: main OOMs during profiling, this PR boots.
- concurrent realtime streams: same transcripts, throughput and memory as with the previous runner change, no OOM. 12 sessions at `--max-num-batched-tokens 256`: 12/12, same as main.
- `--max-model-len 512`, 70 s streams over websocket: streams stop at the cap, client gets `transcription.done`, next session OK.

```
pytest tests/models/multimodal/generation/test_voxtral_realtime.py -k max_model_len   # 2 passed
```

`test_voxtral_realtime_generator_max_model_len` fails with `EngineDeadError` without the buffer cap.

1. In gpu_model_runner._reanchor_requests, head_size = kv.shape[-1] drives both the rotary style (is_neox = head_size == 128) and the shift factor (d_grp = D if is_neox else pool*D). My concern is narrower: one dimension is carrying two independent properties (rotary convention AND which shift to apply), and pool = block_pool_size or downsample_factor or 1 has no equivalent guard at all. If a future audio_config exposes neither attribute, pool silently becomes 1 and every encoder key is under-rotated with no assert to catch it -- the same silent-corruption failure mode the theta check at vllm/config/vllm.py:1134 was added to prevent. Could is_neox and the expansion factor be carried explicitly per KV group from config, with the expansion factor validated at startup alongside theta/scaling, rather than the factor being inferred and defaulted at runtime?

2. The re-rotation only has algebra coverage: test_reanchor_math.py proves R(-D)*R(p)*k == R(p-D)*k for both NeoX-128 and GPT-J-64, and the scheduler tests cover bookkeeping against a simulated model -- but nothing runs a real attention forward, triggers one re-anchor on a live KV layout, and asserts decode output is unchanged. I think the new `_streaming_finish_outputs` path still needs one more frontend-side change.

However, when this reaches `OutputProcessor.process_outputs()`, streaming-input requests are handled specially ([code](https://github.com/vllm-project/vllm/blob/46f74e144b33b01684674e3c808babb19835d17b/vllm/v1/engine/output_processor.py#L659)):

  ```python
  if req_state.streaming_input:
      request_output.finished = False
```
  That means the `RequestOutput` delivered to `AsyncLLM.generate()` is still marked unfinished even though the scheduler has already freed the request. Since AsyncLLM.generate() exits based on out.finished, the websocket/client can keep waiting for another queue item that will never arrive.

```python
terminal_stream_finish = (
      req_state.streaming_input
      and finish_reason in (FinishReason.LENGTH, FinishReason.ERROR, FinishReason.ABORT)
  )

if request_output := req_state.make_request_output(...):
    if req_state.streaming_input and not terminal_stream_finish:
        request_output.finished = False
```

There is also a smaller scheduler-side reason propagation issue in the `_handle_stopped_request()` path.

  In `Scheduler.update_from_output()`, `finish_reason` is captured before calling `_handle_stopped_request()` ([code](https://github.com/vllm-project/vllm/blob/5e27b2baf481518410a9aa5d6b2840cbb2d6ba49/vllm/v1/core/sched/scheduler.py#L1659)):

```python
  finish_reason = request.get_finished_reason()
  finished = self._handle_stopped_request(request)
```
  But after your fix `_handle_stopped_request()` can apply a queued streaming update and then change the request status to `FINISHED_LENGTH_CAPPED`, In that case, the previously captured finish_reason only reflect the earlier stop reason.

  Suggested fix: 
```python
  finished = self._handle_stopped_request(request)
  if finished:
      finish_reason = request.get_finished_reason()
      kv_transfer_params = self._free_request(request)
```
Noticed that non-terminal streaming request cannot be updated ([code](https://github.com/vllm-project/vllm/blob/5e27b2baf481518410a9aa5d6b2840cbb2d6ba49/vllm/v1/core/sched/scheduler.py#L1657))
```python
  # Capture finish_reason BEFORE _handle_stopped_request, which may
  # reset the status to WAITING for streaming requests that continue.
```
So we should only recapture stopping reason if the request is finished.

- **`get_max_audio_tokens` sliding-window cap** — gated on `text_config.sliding_window is not None`, so standard Voxtral (`sliding_window=None`) is untouched and only the realtime decoder's window-bounded audio budget changes. Correct framing of #38233.

- **`max_model_len` graceful finish (scheduler)** — the property that matters is that the upstream `assert num_new_tokens > 0` invariant is preserved for classic one-shot requests, and it is: both the clamp and the graceful-finish branch are gated on `request.resumable`, and non-resumable requests are never clamped, so they always reach the assert with tokens to schedule. The pooling-at-`prompt_len == max_model_len` edge in the comment is the right reason to keep that asymmetry.

- **Client-finish drain path** — I specifically chased the worry that a session length-capped *inside* `add_request()`/`schedule()` (outside `update_from_output`) buffers into `_streaming_finish_outputs` and could be stranded if it was the only in-flight request. It's safe: `finish_requests → _free_request` adds the id to `finished_req_ids`, so `has_requests()` stays true for exactly one more `step()`, and that step's `update_from_output` drains the buffer and emits `finish_reason=LENGTH`. `test_add_request_max_model_len_notifies_client` covers exactly this end-to-end. Buffering and mirroring the failed-KV-load path is the right call.

- **STOP→LENGTH re-read** after `_handle_stopped_request` applies a queued chunk — needed so the client gets `LENGTH` rather than the stale reason; covered by `test_update_from_output_resume_into_cap_reports_length`.

- **Profiling bound** — `encoder_budget // max_toks` under `supports_realtime` matches the runtime encoder-admission bound (`_try_schedule_encoder_inputs` / `EncoderCacheManager`) instead of the `max_num_seqs ×` over-estimate, and the `max(1, …)` floor avoids under-profiling. Reasonable.

- **Silent-hang** — removing the `asyncio.wait_for(VLLM_ENGINE_ITERATION_TIMEOUT_S)` around `input_stream.get()` is justified: an idle token-feedback wait isn't a hang, and a genuine failure ends the stream and cancels the feeder via the `finally` block. The #44461 overlap is already noted.

Optional nit (non-blocking): the `num_tokens >= max_model_len` warn-and-finish block is duplicated nearly verbatim between `_handle_stopped_request` and the `add_request` resume path — could fold into a small helper.

LGTM on the bug-fix scope; the resumable-gating and the buffered-finish drain are the two subtle bits and both hold up. (Disclosure: review assisted by AI tooling; every changed line and the paths above were read and traced by hand.)

```python
def get_max_audio_tokens(self) -> int:
```

```python
class VoxtralRealtimeBuffer:
    def __init__(..., max_model_len: int | None = None):
        ...
        self._max_model_len = max_model_len

    async def get_input_stream(self) -> AsyncGenerator[TokensPrompt]:
        n_tokens = 0
        for frame_size, num_tokens in self._generate_frame_size_and_num_tokens():
            n_tokens += num_tokens
            if self._max_model_len is not None and n_tokens >= self._max_model_len:
                logger.warning(
                    "Stopping audio stream as it reached max_model_len.",
                    n_tokens=n_tokens,
                    max_model_len=self._max_model_len,
                )
                return
            ...
```
