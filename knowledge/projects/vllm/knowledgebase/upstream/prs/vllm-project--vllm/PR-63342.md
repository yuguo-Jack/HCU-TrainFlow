# [ROCm][Perf][Kimi-K3] Use block_m=128 for the fused KDA prefill conv1d

[Upstream PR](https://github.com/vllm-project/vllm/pull/63342) · state: closed · merged: True

## Original PR description

## Purpose
#52968 fused the KDA prefill q/k/v conv into AITER's `causal_conv1d_split_qkv_triton_tile_fn` with `block_m=8`, which is slower than the three convs it replaced.
- `block_m=8 -> 128`, bit-identical output.
- `KimiK3ROCmKDAMetadataBuilder.build` prebuilds the `block_m=128` schedule from `query_start_loc_cpu` (own buffers), so AITER does not fall back to `_build_chunk_schedule` and sync.

## Test Plan
- `pytest tests/models/kimi_k3/test_amd_kda_fused_conv1d.py` (new test: prebuilt schedule matches AITER's, BLOCK_M=8 entry intact, no D2H sync under `set_sync_debug_mode("error")`).
- Kimi-K3 TP8 DCP8 on MI355X, image `vllm/vllm-openai-rocm:nightly-rocm100-df6603f0583375f244d1ac6d36265462b7490392`, #63297 on both sides.
- MI325X kernel sweep, same image.

- xaguilar-amd · CHANGES_REQUESTED · 2026-10-24T19:16:50Z · [source](https://github.com/vllm-project/vllm/pull/63342#pullrequestreview-5639563272)

Thanks a lot for the work! The per-call numbers make a clear case for 128.

One **blocking issue** I see: `compute_causal_conv1d_metadata` only prebuilds the schedule for BLOCK_M=8 (from CPU data, to avoid a sync). With block_m=128, AITER misses nums_dict and falls back to `_build_chunk_schedule`, which does `query_start_loc.diff().to("cpu")` and `.item()`, then copies the result back from unpinned memory. So each prefill step now has a device-to-host sync on the first KDA layer.

Suggestion: could you build the 128 schedule in KimiK3ROCmKDAMetadataBuilder.build from query_start_loc_cpu instead? Please don't just add 128 to the list in the shared helper: it reuses one batch_ptr / token_chunk_offset_ptr pair across block sizes, so the two entries would alias.

Other comments:

- Is the 14,636 tok/s/GPU number block_m=128 (not a revert of #52968), on the same image as 14,255, with #63297 on both sides? Please add the serve and bench commands.

- Please add TTFT/TPOT at c1 and c4 and one long-ISL point (≥64k), same image on both sides.

- This path also runs on gfx942 so we should check everything is fine there too. An MI325X kernel sweep would cover it.

- xaguilar-amd · comment · 2026-10-26T09:46:13Z · [source](https://github.com/vllm-project/vllm/pull/63342#issuecomment-6412984110)

Thanks @hyukjlee , this addresses everything from my review, and CI is green. So LGTM.

For the record, I measured the sync I flagged on an MI325X, using an 8192-token prefill step and one torch thread. The fallback blocks the host until all queued GPU work drains. On a GPU-bound step that costs about 50–100 µs per prefill step. It only gets large (a few ms) when the rest of the step is launch-bound. So the cost is real but small, but the fix is worth keeping.

A few optional cleanups if you want to improve it further. None of them would block the merge for me.

**optional**: _to_device duplicates async_tensor_h2d in vllm/utils/torch_utils.py, which already stages through pinned memory.

**optional**: build_conv1d_chunk_schedule only needs the sequence lengths, since it calls .diff() right away. Passing lengths removes the zeros + cumsum rebuild in build().
