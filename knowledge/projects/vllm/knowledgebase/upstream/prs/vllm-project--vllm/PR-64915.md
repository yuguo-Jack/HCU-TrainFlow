# [Perf][MRV2] Enable varlen decode graphs for fixed-width speculation

[Upstream PR](https://github.com/vllm-project/vllm/pull/64915) · state: closed · merged: False

## Original PR description

## Overview

Fixed-width speculative decoding produces mixed query lengths when requests enter or finish a batch. Model Runner V2 enabled variable-length decode graphs only for adaptive verification and classified cached one-token extensions as prefills. Eligible decode batches therefore fell back to eager execution, increasing CPU launch overhead and rank skew around MoE collectives.

This PR reuses existing variable-length CUDA Graph support for fixed-width speculation and allows one-token extensions over an existing KV cache to replay decode graphs. Genuine prefills remain excluded. No new configuration flags are required.

Automatic selection requires compatible target attention and excludes microbatched and prefill-context-parallel paths. Unsupported configurations keep uniform decode graphs.

## Claims

DeepSeek-V4.1-Flash, MXFP8 × MXFP4, 4×Rubin (GPUs 0–3), DP/EP=4, TP=1, ISL=131072, OSL=1024, concurrency=256. DSpark uses 5 draft tokens, adaptive verification disabled, `max_num_seqs=76`, and `max_num_batched_tokens=456`. No clock locking; each case used a fresh server, 7-minute warmup, and 5-minute measurement.

| Backend | Before PR (output tokens/s) | After PR (output tokens/s) | Improvement |
|---|---:|---:|---:|
| DeepGEMM | 20,862 | 39,943 | +91.5% |
| FlashInfer | 14,910 | 39,567 | +165.4% |

FlashInfer was 28.5% below DeepGEMM before and 0.9% below after. All four cases completed without request errors. The FlashInfer baseline did not meet the harness's 5% warmup-stability criterion; the other three did.

A separate 10-second, rank-0 target-step profile after measurement showed:

| Backend | Eager / graph steps before | Eager / graph steps after |
|---|---:|---:|
| DeepGEMM | 58 / 193 (23.1% / 76.9%) | 0 / 417 (0% / 100%) |
| FlashInfer | 47 / 0 (100% / 0%) | 0 / 421 (0% / 100%) |

These percentages describe that profile window, not the entire throughput run, and exclude draft-model steps. Both arms used the same tuning settings; this is not an autotuning-versus-heuristic comparison.

## Details

Mixed decode rows now use the existing varlen graph descriptors when the attention builders support their maximum query length. Cached one-token extensions include the final prompt token after a prefix-cache hit or KV transfer; other prefills keep their existing fallback.

A follow-up capacity check and documentation update are committed locally as `6f1891fb42`, but **have not been published to this PR** because local HTTPS/SSH authentication is unavailable and the GitHub connector denies code writes (403). The check conservatively keeps uniform graphs when `max_num_seqs * draft_query_len > max_num_batched_tokens`; adaptive verification is unchanged. It does not duplicate the general varlen request-padding changes in #63225. Capturing more decode shapes can increase startup work and graph memory; those costs are not quantified by the throughput results above.

- njhill · comment · 2026-11-02T18:54:51Z · [source](https://github.com/vllm-project/vllm/pull/64915#issuecomment-6585580511)

Thanks for this, but I don't think the premise holds on current main. Mixed query lengths at admission and completion should already be avoided:

- **Admission:** the scheduler pads one-token extensions (prefix-cache hit, KV transfer, resume) to `1 + num_spec_tokens` with placeholder drafts, and declines to schedule rather than schedule unpadded (`scheduler.py` ~L1306-1330, #55126). The runner already treats these padded tails as decodes for uniform graphs (`prefill_runs_as_decode_np` / `decode_graph_eligible` in `gather_batch_req_state`). The `has_prefill` -> `decode_graph_eligible` change at the varlen dispatch is therefore close to a no-op.
- **Completion:** async scheduling skips the partial-draft final step at `max_tokens` (explicitly to preserve uniform decode), structured-output trimming re-pads drafts with `-1`, and finished requests simply leave an otherwise uniform batch.

Concerns with the change itself:

- `varlen_decode=True` *replaces* the uniform decode graphs (`cudagraph_utils.py`, the `elif ... not self.varlen_decode` branch), with `num_reqs = min(num_tokens, max_num_reqs)`. So steady-state uniform batches for every eligible fixed-width spec-decode deployment would replay graphs padded to up to `(1+k)x` the request count (attention metadata, draft pass padded to `max_num_seqs`). That's a potential regression for the common case and hasn't been measured.
- The FlashInfer baseline shows 0 graph steps. Occasional short rows can't explain that, so something else is preventing uniform-graph replay there, and switching graph families just masks it. That's worth root-causing separately.
- The remaining sources of short rows I can see are narrow, e.g. the `max_model_len` clip on running requests. If that's what's being hit (`max_model_len` ≈ ISL+OSL), I'd consider the benchmark unrealistic rather than a reason to change the default graphs.

Could you share the actual per-request query-length mix in the eager steps of the baseline, the `max_model_len` used, and why FlashInfer never replays a uniform graph? I'd expect the fix to be something targeted that keeps uniform graphs as the default. Also, real-model correctness validation is still outstanding, and the description says `6f1891fb42` isn't published, but it appears to be on the PR already.
