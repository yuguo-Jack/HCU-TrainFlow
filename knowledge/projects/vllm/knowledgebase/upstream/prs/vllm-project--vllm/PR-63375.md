# [Bugfix] Keep valid Hermes tool calls when a later region is malformed

[Upstream PR](https://github.com/vllm-project/vllm/pull/63375) · state: open · merged: False

## Original PR description

## Overview

FIX #63358

A Hermes response can contain a valid `<tool_call>` and then a later region that is not a call. Non-streaming parsing dropped every call, and streaming never sent the text after the bad region. Each region is now parsed on its own: valid calls are kept, and the first region that cannot be a call, plus the text after it, is content.

This is not a duplicate of #63327. That PR restores streaming text after a stray tag in prose (#63309) and does not change non-streaming `extract_tool_calls`. A valid call followed by a bad region still loses the call on current main. This change covers that case and also keeps the stray-tag prose path consistent.

AI assistance was used to prepare this patch. The parser change is limited to Hermes (Longcat inherits it) plus an opt-in flush at stream end.

## Claims

- A valid tool call before a malformed `<tool_call>` region is returned, on both streaming and non-streaming paths.
- The malformed region and the text after it are returned as content. Streaming and non-streaming agree, including an empty unclosed tag flushed when generation ends.
- A lone bad region still returns the original text and no tool calls.
- A well-formed tool call is unchanged: only the prefix before the first call is content, and text after a successful call is still omitted.
- A literal `<tool_call>` in prose is content, not a dropped suffix and not a tool call, even if the prose contains `"name"`.

## Validation

Parser-only bug. No model weights or generation are involved, so there is no model evaluation.

`ruff` 0.14.0 `check` and `format --check` passed on:

- `vllm/tool_parsers/hermes_tool_parser.py`
- `vllm/parser/abstract_parser.py`
- `tests/tool_parsers/test_hermes_tool_parser.py`

This machine cannot `import vllm` from the checkout (`transformers` requires `huggingface-hub<1.0`, and 1.15.0 is installed), so pytest was not run here. The new cases were executed by loading `hermes_tool_parser.py` from `HEAD` and from this branch.

Input:

```text
First. <tool_call>
{"name": "get_weather", "arguments": {"city": "Paris"}}
</tool_call> Second. <tool_call>not json</tool_call> Third.
```

`HEAD`:

- non-streaming: `tools_called=False`, content is the entire raw string (the weather call is dropped)
- streaming: content is `First. `, tool name `get_weather`, and ` Second. <tool_call>not json</tool_call> Third.` is never sent

This branch:

- both paths: one `get_weather` call with `{"city": "Paris"}`
- both paths: content is `First.  Second. <tool_call>not json</tool_call> Third.`

Stray prose `The literal <tool_call> tag opens a call. Done.`:

- `HEAD` streaming content is `The literal `
- this branch, both paths: the full sentence and no tool call

The same loader checked chunk sizes 1, 3, and 8 for the issue's other trailing regions (`<tool_call>`, `<tool_call> opens a call. Done.`, `<tool_call></tool_call> Third.`), a normal tool call, two sequential calls, and plain text. Streaming matched non-streaming.

CI selects `tests/tool_parsers` from `.buildkite/test_areas/misc.yaml` when `vllm/tool_parsers/` changes.

## Details

`extract_tool_calls` ran `json.loads` on every regex match inside one `try`. Any bad region raised and the fallback returned the raw string with no calls.

`extract_tool_calls_streaming` walked regions in order and `break`ed when a region had no tool name, so later text was left unsent. `_extract_content` also stops at the first `<tool_call>` and never resumes.

The patch splits regions by the start and end tags. A region is a call only when its body is a JSON object with `name` and `arguments`. The first failure ends tool parsing. If at least one call succeeded, content is the prefix before the first call plus everything after the last good call. If none succeeded, the raw string is returned, which preserves the old fallback for a single bad region and for incomplete JSON such as a missing closing brace.

Streaming uses the same split. A body that does not start with `{`, or a closed body that is not a call, is emitted as content and later tags are not parsed. An empty unclosed tag stays buffered, because a JSON payload may still arrive, but the prose before that tag is sent. `finish_streaming` emits the held tag when generation ends. Hermes sets `flush_streaming_on_finish` so the serving flush calls it without turning Hermes into an engine-based parser. That flag would change `_engine_based` for the whole delegating parser and is not required here.

An incomplete `{...` region that has already streamed a function name is not retracted if the final JSON is invalid. The streaming API cannot take a tool call back, and that incomplete-name case already streamed a call on main.
