# [Bugfix] Fix out-of-bounds write of non-inplace final_state in fused recurrent delta-rule kernels

[Upstream PR](https://github.com/vllm-project/vllm/pull/62778) · state: open · merged: False

## Original PR description

## Overview

Fixes #61800. The bug shows with `inplace_final_state=False` and a dense `[B, T]` batch where `B > 1`. In that case, `fused_recurrent_gated_delta_rule` allocates `final_state` with `T` rows, but the kernel writes one row per token of the whole batch. So every sequence after the first writes past the end of the buffer. This PR allocates `B * T` rows. It makes the same change in the six other wrappers that allocate the same buffer for the same kernel store.

Compared with #61808, this fix:

- Also repairs the six other wrappers that have the same short buffer: `fused_recurrent_kda` (same kernel), `fused_sigmoid_gating_delta_rule_update`, and the four GLM-5.3-Flash copies. With [#61808](https://github.com/vllm-project/vllm/pull/61808), the reproducer's call through `fused_recurrent_kda` still gives 64 `Invalid __global__ write` errors at `fused_recurrent.py:166`, and the same call through sigmoid gating gives 96.
- Does not change the varlen result. With `cu_seqlens`, `N * T` returns 36 rows for 12 tokens, and rows 12 to 35 are never written. `B * T` equals `T` there, because the wrappers require `B == 1` with `cu_seqlens`.
- Adds tests that fail without the fix. [#61808](https://github.com/vllm-project/vllm/pull/61808) adds no test.

## Claims

- No more out-of-bounds write in `fused_recurrent_gated_delta_rule_fwd_kernel` for a dense batch with `B > 1` and `inplace_final_state=False`. The returned `final_state` now holds all `B * T` per-token states. Before, it held only the states of the first sequence.
- The same one-line change (`T` to `B * T`) in `ops/kda.py`, `ops/fused_sigmoid_gating.py`, and the GLM-5.3-Flash `{nvidia,amd}/ops/third_party/kda/{fused_recurrent,kernels}.py`. That is 7 lines in total outside `tests/`.
- Nothing changes for the varlen layout (`B == 1`) or for `inplace_final_state=True`. Every in-tree caller uses `inplace_final_state=True`.
- New tests cover all 7 changed lines.

## Validation

Setup: 1 x NVIDIA GeForce RTX 5090 (driver 615.71.09), torch 2.14.0+cu130, vLLM `0.32.1rc1.dev117+gdf3bd094a` (base commit `df3bd094aeea829f27baa0a5282830464f601d9f`), compute-sanitizer 2025.3.0.0.

Reproducer. This is the script from the issue, with the import path changed to the one `main` uses:

```python
import torch
from vllm.third_party.flash_linear_attention.ops.fused_recurrent import fused_recurrent_gated_delta_rule

torch.manual_seed(0)
dev = "cuda"
B, T, H, HV, K, V = 2, 1, 1, 1, 16, 16
q = torch.randn(B, T, H, K, device=dev)
k = torch.nn.functional.normalize(torch.randn(B, T, H, K, device=dev), dim=-1)
v = torch.randn(B, T, HV, V, device=dev)
g = -torch.rand(B, T, HV, device=dev)
beta = torch.rand(B, T, HV, device=dev)
h0 = torch.randn(B * T, HV, V, K, device=dev)
o, final_state = fused_recurrent_gated_delta_rule(q, k, v, g, beta, scale=K ** -0.5, initial_state=h0,
                                                  inplace_final_state=False, use_qk_l2norm_in_kernel=True)
torch.cuda.synchronize()
print("final_state rows:", final_state.shape[0], "expected at least", B * T)
```

## Details

Root cause. In non-inplace mode, the kernel stores the state after token `i_t` of sequence `i_n` at row `bos + i_t` of `final_state` (`fused_recurrent.py:164`). For dense input, `bos = i_n * T` (`fused_recurrent.py:74`), so the kernel writes rows `0 .. B*T-1`. The wrapper allocated `q.new_empty(T, HV, V, K)` (`fused_recurrent.py:206`), which is only correct when `B == 1`. In the reproducer, the buffer is one row (1024 bytes). Sequence 1 (block `(0,0,1)`) writes row 1, which starts at byte 1024. This matches the sanitizer's "1 bytes after the nearest allocation ... of size 1024 bytes". A debug print showed `final_state.stride(0) == HV*V*K`, so the stride is correct and only the row count is wrong.

Why `B * T` and not `N * T`. `B * T` is the token count that the wrapper already uses for `o`, and that the kernel already uses as `all` for dense input. For dense input `N == B`, so the two give the same size. With `cu_seqlens`, `N` is the number of sequences and `T` is the total token count, so `N * T` allocates too many rows and returns rows that are never written. `B * T` stays `T` there.

The same defect in other places. These wrappers allocate the same `T`-row buffer for the same `(bos + i_t)` store, and they get the same change:

- `ops/kda.py`, `fused_recurrent_kda_fwd`: launches the same kernel with `IS_KDA=True`.
- `ops/fused_sigmoid_gating.py`, `fused_sigmoid_gating_delta_rule_update`: launches a copy of the kernel.
- `vllm/models/glm5next/{nvidia,amd}/ops/third_party/kda/fused_recurrent.py` and `kernels.py`: GLM-5.3-Flash copies of both wrappers.

A grep of `vllm/` for this store and for the non-inplace `new_empty` finds exactly these 7 sites. The `kimi_k3` copies `assert inplace_final_state`, so the bug does not affect them.

Tests. Each new case runs a dense `B=3, T=4` non-inplace batch. It then checks that the per-token states and outputs match those of the same tokens packed as varlen. The varlen path was already correct before the fix. The FLA cases (`gdn`, `kda`, `sigmoid_gating`) are in a new file, `tests/kernels/fla/test_fused_recurrent.py`, which the "FLA Ops Kernels" CI step runs. The glm5next cases (`kda`, `gdn`) are added to `tests/models/glm5next/test_kda_recurrent.py`, which imports the AMD copies on ROCm. They are not in `tests/kernels/fla` because that step also runs on XPU, and the glm5next kernels support only CUDA and ROCm.

Not changed in this PR:

- The `Returns:` docstring of `fused_recurrent_gated_delta_rule` says `final_state` is `[N, HV, V, K]`. With `inplace_final_state=False` it is `[B * T, HV, V, K]`. The docstring was already wrong before this PR.
- Without `ssm_state_indices`, the kernel reads `initial_state` at row `bos` (a token offset), but the docstring says `[N, HV, V, K]`. This is a read, and it needs a separate change.

No in-tree caller uses `inplace_final_state=False`, so this change does not affect serving.
