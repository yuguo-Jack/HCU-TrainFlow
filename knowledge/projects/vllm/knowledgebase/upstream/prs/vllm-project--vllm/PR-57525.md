# [Security] Bound OpenCV video decode frame walks

[Upstream PR](https://github.com/vllm-project/vllm/pull/57525) · state: open · merged: False

## Original PR description

## Summary
The default OpenCV video decoder walks every source frame up to the last sampled index via sequential `cap.grab()`. Uniform sampling always includes that last index, so decode CPU tracks container frame count rather than the small number of returned frames. A long, highly compressible video stays under the download-size cap and can occupy a media worker for the full walk. This adds `VLLM_MAX_VIDEO_DECODE_FRAMES` (default 36000, `0` disables) and rejects over-budget walks before either OpenCV grab loop starts.

## Changes
- `vllm/envs.py`: add `VLLM_MAX_VIDEO_DECODE_FRAMES`.
- `vllm/multimodal/video_decoders/base.py`: reject walks above the cap.
- `vllm/multimodal/video_decoders/opencv.py`: enforce the cap in `read_frames` (covers recovery and non-recovery paths).
- `docs/usage/security.md`: document the new decode-size guard.
- Tests for under-limit, over-limit (both recovery modes), disable-with-0, and the `VideoMediaIO` entry point.

## Codepath coverage
- Chat / messages / responses / batch / `/invocations` / gRPC / offline `LLM.generate` all reach `VideoMediaIO` → OpenCV `read_frames`: covered.
- `video/jpeg` base64 and TorchCodec / PyNvVideoCodec / DeepStream do not use this grab loop: N/A.
- GLM-5.1 seek-based `read_frames` override does not use the sequential grab loop unless `frame_recovery=True` (then it calls the shared `read_frames`): covered on that recovery path.

## Duplicate-work check
Searched open, draft, and recently merged PRs for OpenCV `read_frames`, `cap.grab`, video decode frame/duration limits, and `video_decoders/opencv`. #55582 speeds GLM sampler index selection; #46836 adds an encoded-file size guard; #51969 clamps request `num_frames` for `video/jpeg`. None of those bound the OpenCV sequential grab loop.
