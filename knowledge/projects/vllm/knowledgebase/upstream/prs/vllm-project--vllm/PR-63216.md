# [RL] Support per-parameter destination layouts for NCCL M2N

[Upstream PR](https://github.com/vllm-project/vllm/pull/63216) · state: open · merged: False

## Original PR description

## Summary

This PR adds a per-parameter destination-layout contract to NCCL M2N weight
transfer.

[#60934](https://github.com/vllm-project/vllm/pull/60934) made the source mesh
and placement parameter-specific. This PR completes the other half: every
parameter now carries a complete resolved destination layout through planning,
collective agreement, commit hashing, and its existing `m2n.reshard()` call.

```text
parameter P
    source mesh P + source placement P
                    │
                    ▼
      transfer route for P's source group
                    │
                    ▼
destination mesh P + destination placement P
```

Parameters with different destination layouts reuse the transfer communicator
associated with their canonical source group. This PR does not create an M2N
session or communicator for every mesh.

Together with #60934, this completes the per-parameter mesh contract requested
by [#60563](https://github.com/vllm-project/vllm/issues/60563) for
two-dimensional layouts over the existing participant sets.

Fixes #60563.

## Stack

This PR is stacked on:

1. [#60934 — Per-parameter source layouts](https://github.com/vllm-project/vllm/pull/60934)
2. [#60949 — Rank-local destination targets](https://github.com/vllm-project/vllm/pull/60949)

## Motivation

Before this PR, parameters could have different destination placements, but
those placements were interpreted over one destination mesh selected for the
entire update.

That common mesh cannot directly represent a model containing multiple
inference-side layouts. For example:

```text
dense.weight:
    source mesh A + placement A
        → destination mesh X + placement X

experts.weight:
    source mesh B + placement B
        → destination mesh Y + placement Y
```

A parameter whose native destination layout did not match the fixed mesh had
to use the existing full-tensor fallback when permitted.

This PR makes the destination mesh part of each parameter's resolved
destination record. The complete layout is agreed before communicator creation
and supplied to that parameter's `m2n.reshard()` operation.

This avoids both alternatives described in #60563:

- Normalizing every supported parameter to one common mesh before transfer.
- Creating a separate M2N session for every mesh.

Parameters without a supported native destination may still use the existing
explicitly allowed full-fallback path.

## Design

### Per-parameter destination record

`M2NDestination` and `M2NWireDestination` now contain:

```python
mesh_dims: tuple[int, int]
```

The wire representation continues to retain:

- Placement.
- Sharded tensor dimension.
- Number of shards.
- Worker shard index.
- Semantic target identity.
- Staging coordinates.

The shard coordinates authenticate which shard each worker claims to own. They
are retained alongside `mesh_dims`, not inferred from it after agreement.

The wire schema is incremented from version 5 to version 6. Peers using an
older schema are rejected during initialization.

### Collective agreement

The existing initialization agreement now validates each parameter's complete
destination layout.

For every destination record, it verifies:

- The mesh is two-dimensional.
- The mesh covers the complete ordered inference-worker set.
- Placement and shard count agree with the mesh.
- The worker's shard index matches its mesh coordinate.
- The local tensor shape matches the declared sharding.
- Workers agree on all invariant destination fields.
- Any configured fixed destination constraint is satisfied.

The complete destination plans, including mesh dimensions and shard
coordinates, are included in the existing commit digest.

No additional agreement phase or per-parameter handshake is introduced.

### Runtime execution

Trainer and inference workers use the agreed destination record for the current
parameter:

```python
dst_mesh, dst_placements = resolve_layout(
    M2NMesh(destination.mesh_dims, source_group_size),
    destination.placements,
)
```

They pass that layout to the existing `m2n.reshard()` call.

Changing the destination mesh between consecutive parameters does not recreate
the communicator.

This PR does not change:

- Transfer-route membership or communicator count.
- Parameter order.
- Transfer-wave scheduling.
- CUDA streams or synchronization.
- Source iteration.
- Staging-pool behavior.
- Failure, retry, abort, or shutdown handling.
- Packed NCCL behavior.

## Optional model-derived layout resolution

The per-parameter destination-layout contract is the primary change.

As a convenience, this PR also provides an opt-in resolver that derives each
parameter's destination layout from existing vLLM model and loader metadata:

```python
M2NTrainerInitInfo(
    ...,
    auto_dst_mesh=True,
)
```

For `N` inference workers, the built-in resolver selects:

| Destination type | Resolved mesh |
|---|---:|
| Semantic target with `S` shards | `(N / S, S)` |
| Recognized TP loader with `tp_size=S` | `(N / S, S)` |
| Replicated direct loader | `(N,1)` |
| Full fallback | `(N,1)` |

Semantic targets fail closed when their shard count or worker shard coordinate
is invalid.

Recognized direct loaders retain the existing permitted-or-forbidden
full-fallback policy when their TP metadata does not match the destination
topology.

The resolver is currently the built-in production path that populates
heterogeneous destination layouts. This PR does not expose an arbitrary
caller-authored destination-plan API.

## Configuration behavior

Model-derived resolution is explicitly opt-in:

| `auto_dst_mesh` | `dst_mesh_dims` | Behavior |
|---|---|---|
| `False` | `None` | Existing flat `(N,1)` behavior |
| `False` | Explicit dimensions | Existing fixed destination constraint |
| `True` | `None` | Resolve a destination layout per parameter |
| `True` | Explicit dimensions | Reject during initialization |

Existing callers that omit both options retain their current configuration
behavior.

Replicated direct destinations and full fallback continue to use `(N,1)`,
including when the fixed constraint for sharded parameters uses another
factorization.

This preserves configuration semantics, not mixed-version wire compatibility:
schema-5 and schema-6 peers cannot participate in the same session.

## Observability

The plan summary now distinguishes the optional fixed constraint from the
resolved parameter layouts:

```json
{
  "destination_mesh_constraint": null,
  "destination_mesh_counts": [
    {"dims": [4, 4], "parameter_count": 378},
    {"dims": [1, 16], "parameter_count": 188},
    {"dims": [16, 1], "parameter_count": 471}
  ]
}
```

Existing destination-mode and payload summaries remain available.

## Current scope

The contract is model-independent, but currently supports two-dimensional
destination layouts over the same ordered inference-worker set.

This PR does not add:

- Different destination-worker subsets per parameter.
- Destination-rank permutations.
- Generator pipeline parallelism.
- Arbitrary externally supplied per-parameter destination plans.
- New transfer scheduling.
- New model-specific semantic target APIs.

Partitioned trainer source groups are currently required to have equal rank
counts. This is a new restriction relative to the broader source-group contract
in #62853 and is stated explicitly rather than presented as unchanged
source-topology support.

## Validation

### AArch64 regression suite

The final patch was tested on an AArch64 compute node with four GB200 GPUs:

```text
243 passed, 14 warnings in 188.92s
```

Coverage includes:

- Legacy configuration and opt-in resolver behavior.
- Rejection of an explicit fixed constraint with model-derived resolution.
- Parameter-specific TP, semantic, replicated, and fallback layouts.
- Fixed-constraint match and mismatch behavior.
- TP-rank validation.
- Fail-closed semantic shard validation.
- Wire-schema round trips and rejection.
- Cross-worker layout and coordinate agreement.
- Commit-digest sensitivity to destination meshes.
- Trainer and worker calls using consecutive different layouts.
- Existing staging, rank-local destination, and failure behavior.

### Two-node mixed-layout canary

A two-node hardware canary used four trainer GPUs on one node and four
inference GPUs on another. The roles occupied different NVLink domains and
communicated over InfiniBand/GDRDMA.

One transfer plan used two existing transfer routes and three destination
layouts:

| Parameter | Destination mesh | Loading mode |
|---|---:|---|
| TP2 parameter | `(2,2)` | `IN_PLACE` |
| Semantic EP4 parameter | `(1,4)` | `SHARDED_STAGING` |
| Replicated parameter | `(4,1)` | `IN_PLACE` |

Ten update rounds completed. Every destination element was checked after every
update.

This verifies that consecutive parameters can use different destination
layouts through existing M2N communicators without changing collective
ordering.

## Synthetic performance evidence

The heterogeneous destination layouts enabled by this PR were compared with an
explicit fixed destination constraint.

Both configurations used the same PR commit, binary, allocation, NCCL
configuration, and update lifecycle:

```text
Fixed destination constraint:
    auto_dst_mesh=False
    dst_mesh_dims=(1,16)

Per-parameter destination layouts:
    auto_dst_mesh=True
    dst_mesh_dims=None
```

The built-in resolver populated the per-parameter layouts, but planning and
agreement occurred during initialization, outside the repeated update timing.

This is not a comparison against NCCL broadcast, PR3, or another vLLM
revision.

### Setup

- Eight AArch64 nodes and 32 GB200 GPUs.
- Sixteen trainer GPUs in one NVLink domain.
- Sixteen inference GPUs in a separate NVLink domain.
- Cross-role communication over InfiniBand/GDRDMA.
- Two eight-rank trainer source groups.
- Qwen3-235B-A22B-shaped synthetic BF16 parameter manifest.
- 1,037 parameters and 437.896 GiB of logical weights per update.
- One excluded cold update.
- Two runs and ten retained warm updates per configuration.
- Execution order: fixed, per-parameter, per-parameter, fixed.
- Source preparation and exact-value validation excluded from the timed region.

Every destination element was validated after every update.

The synthetic manifest resolved as:

| Parameter class | Count | Fixed destination constraint | Per-parameter destination layouts |
|---|---:|---|---|
| TP4 dense | 378 | Full fallback, `(16,1)` | Direct, `(4,4)` |
| EP16 expert | 188 | `(1,16)` | `(1,16)` |
| Replicated | 471 | `(16,1)` | `(16,1)` |

### Results

| Destination configuration | Mean update wall time | Median | Sample σ | Logical bytes ÷ time |
|---|---:|---:|---:|---:|
| Fixed `(1,16)` constraint | 1.746 s | 1.743 s | 0.0126 s | 250.81 GiB/s |
| Per-parameter layouts | 1.244 s | 1.241 s | 0.0075 s | 352.02 GiB/s |

For this synthetic workload, per-parameter destination layouts provided:

- **1.40× speedup.**
- **28.8% lower mean weight-update wall time.**
- **26.9% lower planned receiver-buffer fanout.**
- Planned receiver-buffer fanout decreased from 661.3 GiB to 483.7 GiB per
  update.

The performance change comes primarily from transferring TP4 dense parameters
into their native `(4,4)` destination layout instead of reconstructing a
complete tensor through `FULL_FALLBACK` on every inference worker.

The measured boundary includes M2N transfer and destination loading/local work.
It is not a transport-only measurement.

Planned receiver-buffer fanout describes destination buffers and replication.
It is not measured NCCL protocol or InfiniBand traffic. Aggregate InfiniBand
transmit counters were effectively unchanged, so these results should not be
presented as an IB-traffic reduction.

This is a synthetic weight-transfer benchmark. It does not include checkpoint
loading, optimizer work, generation, or an end-to-end RL iteration. Qwen is
used only to provide a realistically scaled mixed-layout parameter manifest;
the contract is not Qwen-specific.
