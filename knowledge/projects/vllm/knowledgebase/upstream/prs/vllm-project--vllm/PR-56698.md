# [Bugfix][Core] Profile and validate kv_cache_memory_bytes instead of skipping the profile

[Upstream PR](https://github.com/vllm-project/vllm/pull/56698) · state: open · merged: False

## Original PR description

## Purpose

`--kv-cache-memory-bytes` never checked the size it was handed. The branch returned before `memory_profiling` ran, logged "skipped memory profiling", and passed the number straight through. Nothing compared it against what the model needs for itself, so a size that is too large starts fine, serves short requests, and then OOMs in the middle of one once traffic reaches the activation peak.

The same measurement gap exists under `gpu_memory_utilization`, but it stays hidden there: the KV size is derived from a budget that is only a fraction of the device, so whatever the profile missed lands in the part the utilization fraction left unallocated. A pinned size has no such slack — the operator sized it to use what was free — so the pinned cache and the unprofiled activation peak compete for the same free memory.

There is a second half to it. Even when the profile does run, it forwards with `skip_attn=True`, because there is no KV cache yet to attend against. The attention activations, and the device memory those kernels take the first time they launch, are simply not in the figure. Harmless where slack absorbs it; not harmless when the cache was pinned to that figure.

## What this changes

Run the profile for a pinned size too, and check the value against the result. If it does not fit, fail at startup and report the largest size admitted by this profile. Refusing rather than quietly capping is deliberate: a pinned size is an explicit capacity decision, and silently reducing it hides the one number this option exists to control. Starting anyway is worse — the bytes are spent either way, and the failure just moves to a request.

When a size is pinned, extend the profile with attention: build the same minimal KV cache the CUDA graph profiling already uses, run a short ladder of batch widths through it, then tear it down. The ladder is not redundant with its widest rung, since the caching allocator keeps whole segments per size class and a served mix of widths costs more than the widest one alone. Then account for what the allocator holds beyond the live peak — `memory_profiling` measures `allocated_bytes.all.peak`, which is the right call where slack absorbs the difference and the wrong one where there is none. The ladder runs inside `memory_profiling` but outside the split limit #58430 puts around `profile_run()`, so that overhead is measured under the allocator settings serving uses. The check also keeps `profile_run()`'s own peak, which resetting the counter for the ladder would otherwise drop.

All of it sits inside the pinned branch; outside it, the only change is the V1 profiling teardown described below. A size restored by `VLLM_ENABLE_STARTUP_PLAN` keeps the existing fast path, since a fully profiled boot of the same configuration already measured it.

The attention profile is best effort: if the minimal KV cache cannot be built, startup continues with the old estimate. Since #53558, minimal-config construction no longer changes `num_gpu_blocks_override`. V1's profiling teardown reuses `clear_layer_kv_caches()`, which now clears quantized scale views independently of `kv_cache`.

## What it deliberately does not do

The reported figure is an upper bound, not a safe setting, and the error message says so. The profile forwards against a *minimal* KV cache, so peaks that scale with context length are still outside it. No margin is applied here — the number is what the profile can account for, and the operator is told to leave room under it.

A percentage margin was the first thing I tried, and I dropped it. The shortfall scales with the model's activation footprint rather than with the cache, so a fraction of the cache size wastes memory wherever the cache is large; and a fraction fitted to a single measurement is not evidence, it just reproduces that measurement.

## Test Plan

Startup runs with the command from #62277 (`Qwen3.8-27B-NVFP4`, a 4.5 GiB pin, sleep mode, MTP with three speculative tokens, `--language-model-only`), with nvfp4 KV and a two-rank pipeline-parallel split of 16/48 layers, warm compile caches.

Unit tests cover the V1 profiling teardown.

- maxtonhuang · comment · 2026-10-18T10:13:34Z · [source](https://github.com/vllm-project/vllm/pull/56698#issuecomment-6248631971)

Tested this PR against #62277 on an RTX 5090 with Qwen3.8-27B-NVFP4, sleep mode and a 4.5 GiB pinned KV budget. Four cold starts succeeded: two with fp8 KV and two with nvfp4 KV; the two nvfp4 runs also served a short request. Separately, #59893 plus the existing split-limit scope addresses the KV-allocation OOM reported in #62277 while preserving the current fast path. Removing that branch here would supersede those changes.

Two notes from reading the diff:

1. `_profile_attention_for_pinned_kv()` calls `torch.accelerator.reset_peak_memory_stats()` inside the `memory_profiling` block, after `profile_run()`. `memory_profiling` reads `allocated_bytes.all.peak` on exit (`transient_peak_headroom = after_profile.torch_peak - after_profile.torch_allocated`, `vllm/utils/mem_utils.py`), so an earlier peak from `profile_run()` itself is lost if the later allocations do not reach it, and the new check could accept a pin that does not fit. Keeping the maximum allocated peak across both phases, and measuring the ladder's allocator overhead separately, would avoid that.
2. With `VLLM_ENABLE_STARTUP_PLAN=1`, the plan sets `kv_cache_memory_bytes` so that memory profiling and graph estimation are skipped (`vllm/v1/worker/startup_plan.py`). With this PR those starts profile again, and the plan's "Memory profiling will be skipped" log no longer holds.

@maxtonhuang Thanks for testing this on that setup, it's good to have the nvfp4 runs in there.

Both notes were right, and I've pushed a fix. The pinned check now keeps `profile_run()`'s own peak and takes the larger of it and the final measurement, with the allocator overhead still measured over the attention ladder alone. Plan-applied boots keep the existing fast path, and only sizes the operator pinned go through the new measurement.

Testing the same model and pinned-budget setup with PP=2 also showed that the ladder ran inside the split-limit scope, so the allocator overhead it measured came from the temporary profiling split limit. The limit now covers only `profile_run()`, and the ladder runs with the serving allocator settings.
