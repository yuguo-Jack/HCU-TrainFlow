# [Feature][Kernel] Triton autotune lora

[Upstream PR](https://github.com/vllm-project/vllm/pull/62955) · state: open · merged: False

## Original PR description

## Purpose

Depends on #59492.

Builds on the generic Triton autotune warmup (`--kernel-config.enable_triton_autotune`) and adds a LoRA table for the `lora_shrink` and `lora_expand` Triton kernels. LoRA ships no tuned configs, so without a user file in `VLLM_TUNED_CONFIG_FOLDER` every shape uses the heuristic default. With this PR, each GPU and model can tune its own launch configs at startup.

cc @vanshbhatia-amd 

Changes:

- **Shapes from the LoRA weights.** Shrink and expand shapes are read from the allocated `lora_a_stacked` / `lora_b_stacked` of every `BaseLinearLayerWithLoRA` and of `lm_head` (`LogitsProcessorWithLoRA`). No adapter has to be loaded. Linear layers are tuned up to `max_num_batched_tokens`, and `lm_head` up to `max_num_seqs × (1 + num_speculative_tokens)`.
- **M buckets.** 1, 16, 32, …, 4096, up to the first bucket at or above each shape's token limit.
- **Bounded search.** At most 12 configs are timed per M bucket. The search starts from the default config plus up to 2 winners from the nearest M buckets already tuned on the same rank (same op and slice count). All starting points are snapped to the search grid. It then expands one-step neighbors of the fastest config that hasn't been expanded yet.
- **Search space.**
  - Shrink: `block_m` 16–128, `block_n` 16 plus a rank-sized tile, `block_k` 64/128, `split_k` 2–32.
  - Expand: `block_m` 16–64, `block_n` 32–256, `num_warps` 2/4/8.
  - `block_m` is capped by M, and shrink configs whose `block_k × split_k` exceeds K are rejected.
- **Timing.** CUDA graph replays of 10 launches. A candidate stops after one replay if it is more than 1.5× slower than the best so far.
- **Correctness and noise guard.** A winner must match the default config's output (rtol 1e-2). It must also beat the default by at least 2% in a side-by-side re-timing, otherwise the default is kept.
- **Isolated scratch state.** Tuning uses scratch weights, which are removed from the `data_ptr`-keyed `_LORA_A_PTR_DICT` / `_LORA_B_PTR_DICT` caches afterwards. Buckets whose scratch tensors need more than half the free memory are skipped.
- **Partial-cache resume.** Only missing M buckets are tuned. Ops with a user file in `VLLM_TUNED_CONFIG_FOLDER` are skipped unless `VLLM_TRITON_AUTOTUNE_FORCE=1`. Batch-invariant mode is never tuned.
- **Config lookup in `lora/ops/triton_ops/utils.py`.**
  - `load_lora_op_config` gains the autotune cache as a lookup layer.
  - Path, load and save helpers are shared by the loader and the warmup table. Saving clears the lookup caches.
  - The autotune cache uses the platform device name (`AMD_Instinct_MI300X_SHRINK.json`, `..._EXPAND_TRUE.json`), because `torch.cuda.get_device_name()` can be empty on ROCm. Files in `VLLM_TUNED_CONFIG_FOLDER` keep the existing naming.
  - `override_lora_op_config` lets the tuner run candidates through the real `lora_shrink` / `lora_expand` path.

Lookup priority: `VLLM_TUNED_CONFIG_FOLDER`, then the autotune cache, then the default.

Scope: LoRA linear layers and `lm_head`. Fused MoE LoRA and the embedding LoRA path are not tuned and keep their defaults.

## Testing

AMD Instinct MI300X, ROCm container, Triton 3.8.0.

```bash
pytest tests/lora/test_lora_autotune.py   # 24 passed (new)
pytest tests/lora/test_punica_ops.py      # 4273 passed
```

**End to end.** `unsloth/Llama-3.2-3B-Instruct` with the `jeeejeee/llama32-3b-text2sql-spider` adapter, `--max-lora-rank 16`, and Qwen3-8B with LoRA enabled. All runs used fresh Triton, vLLM and autotune cache directories. Generations matched the autotune-off output, and a second launch reused the saved cache and did not retune.

## Notes for reviewers

- **Fewer candidates, not exhaustive.** A 12-config budget can miss the true optimum. On the shapes above it lands within 1% of an exhaustive search over the same grid. The worst entry, qkv at M=128 with 4 adapters, is 1.24× slower than exhaustive but still faster than the default.
- **Search lists come from an MI300X sweep.** Nothing is keyed on GPU name, but the value lists were pruned from an MI300X sweep over Llama-3.2-3B shapes. They have not been checked on NVIDIA GPUs.
- **Startup cost.** Triton compile time dominates (about 0.3–0.7 s per config, versus about 5 ms to time one), and configs are compiled one at a time. TP splits the items across ranks.
- **First-use compiles.** No extra LoRA warmup is added. Tuned configs for buckets the standard warmup doesn't reach (for example M ≥ 1024) compile the first time they're used during serving. After that, Triton's disk cache serves them.
- **Expand `add_inputs`.** It is inferred from the layer's `apply` path and the dual-stream setting, which decides between `EXPAND_TRUE` and `EXPAND_FALSE`.
- **Shapes sharing a table key.** Two shapes that map to the same `max_loras/num_slices/m/k/n` entry share one config, and the last one tuned wins.
- **Forced re-tune with a user file.** `VLLM_TRITON_AUTOTUNE_FORCE=1` re-tunes ops that have a user file, but the user file still takes priority at lookup.
- **Inference path is mostly unchanged.** `get_lora_op_configs` gains an override check and the autotune cache layer, and the kernels are untouched.

Tested this on MI355X (gfx950, Triton 3.8.0), applied on top of a recent vLLM ROCm nightly at `9763edd`, and it works.

- Unit tests: 45/45 passed (core autotune tests plus `test_lora_autotune.py`), and `tests/lora/test_punica_ops.py` passed 4274/4274.
- End to end with `unsloth/Llama-3.2-3B-Instruct` + `jeeejeee/llama32-3b-text2sql-spider`: tuned 78 configs in 43 s. The warm start reused them (startup was 94 s cold and 26 s warm). The adapter produced 4/4 expected SQL outputs, identical to the defaults.
- Decode latency with the adapter active (3 A/B runs) vs default configs: **1.07x / 1.07x / 1.06x / 1.16x** at batch 1 / 8 / 32 / 128.
- `Qwen/Qwen3-8B`, TP2, `--max-loras 4`: 86 items were split 43/43 across ranks and tuned in 37 s, and the warm start reused the cache.

I also tested it together with #59492, #61686, #61688 and #62955 combined (Qwen3-30B-A3B-FP8, TP4): 105/105 unit tests passed, 54 configs were tuned across 4 ranks in 155 s, and decode latency improved 1.15–1.24x across batch sizes 1–128. Greedy outputs were identical to the defaults, and GSM8K was unchanged.
