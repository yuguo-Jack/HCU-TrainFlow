# [Bugfix][KV Events] Prevent replay truncation when the send queue fills

[Upstream PR](https://github.com/vllm-project/vllm/pull/63224) · state: closed · merged: True

## Original PR description



## Overview

This PR fixes a case where a slow KV-event subscriber can lose replayed batches and the completion marker, leaving it waiting indefinitely.

## Claims

- Set the replay socket's send high-water mark to `buffer_steps + 1`, allowing room for the retained history and its completion marker.
- Add a regression test for a subscriber that waits until the replay burst has finished before reading.

## Validation

- Before the fix, the regression fails with `Replay stalled after 2000 batches`.
- With the fix, all 17 tests in `tests/distributed/test_events.py` pass.

## Details

`ZmqEventPublisher` uses a PUB socket for live events and a separate ROUTER socket for replay. After publishing each batch, it saves the sequence number and payload in an in-memory buffer, which retains up to 10,000 batches by default. Subscribers that detect a sequence gap can request those batches, and the publisher sends them in one burst, followed by a completion marker.

The replay socket keeps ZMQ's default send limit of 1,000 queued messages per client. If a subscriber cannot read quickly enough and that queue fills, the ROUTER silently drops further messages, potentially including the marker. Clients can wait for replay to finish before processing more live events, so losing the marker can freeze its KV routing index.

We set the replay send limit to `buffer_steps + 1` (which matches the buffer size, i.e. the upper limit of how many messages are cached in the replay buffer) before binding the socket. This lets one full replay and its marker fit without requiring the subscriber to read concurrently. Queue memory remains bounded, although the larger limit allows more memory per client.

Thanks, this is a real gap.

ZMQ sets an internal threshold of [half the HWM](https://github.com/zeromq/libzmq/blob/v4.3.5/src/pipe.cpp#L470). The subscriber side only tells the publisher how much it has read each time it crosses that [threshold](https://github.com/zeromq/libzmq/blob/v4.3.5/src/pipe.cpp#L201-L202). Between reports, the publisher can still **count up to about `HWM/2` messages as unread** even after the subscriber has read them. It treats that stale count as part of the queue when checking [whether the queue is full](https://github.com/zeromq/libzmq/blob/v4.3.5/src/pipe.cpp#L536). When the check trips, `ROUTER` silently [drops the message](https://github.com/zeromq/libzmq/blob/v4.3.5/src/router.cpp#L185), which can include the end-of-replay marker.


**Solution**: With `HWM = buffer_steps + 1`, a replay that follows earlier replays can lose its tail and marker. With 2×, a full replay plus its marker always fits, whatever the stale count.

**Why not fix in ZMQ?**  The stale read count is intentional in libzmq: reads are acknowledged every `HWM/2` messages to avoid per-message signaling ([ref](https://github.com/zeromq/libzmq/blob/v4.3.5/src/pipe.cpp#L452-L470)), and `SNDHWM` is documented as approximate. So the caller has to size the HWM with headroom; 2× is the minimum that guarantees a full replay plus its marker fits.
