# [Core] Let VLLM_WORKER_SHUTDOWN_TIMEOUT_SECONDS set the EngineCore cleanup grace after an immediate abort

[Upstream PR](https://github.com/vllm-project/vllm/pull/63260) · state: closed · merged: True

## Original PR description

With the default `--shutdown-timeout 0`, the process manager sends EngineCore a SIGTERM and then kills it with SIGKILL straight away on every platform except ROCm, which gets 15 s since #52281. This PR lets an explicitly set `VLLM_WORKER_SHUTDOWN_TIMEOUT_SECONDS` set that cleanup window on every platform. Defaults stay the same. This is the vLLM follow-up promised in vllm-project/ci-infra#685 ([review thread](https://github.com/vllm-project/ci-infra/pull/685#discussion_r4355552793)).

ci-infra#685 records the GPU kernels each CI process launches. A recording counts as complete only if it ends with a footer, which the CUPTI injection library writes from `atexit` and the ROCProfiler SDK tool writes from `tool_fini`. In CUDA build [vllm/ci 96247](https://buildkite.com/vllm/ci/builds/96247), 4,400 of 18,118 recordings had no footer. Matching them against the job logs, 540 are EngineCore processes killed right after `stopping engine client mode=abort timeout=0s`, and another 391 are TP/EP workers killed in the same process-tree kill. In the CPU offload job, for example, all 8 servers log `send sigterm` and `force killing remaining process EngineCore` within 1 ms of each other. EngineCore already handles SIGTERM by leaving its busy loop and exiting normally through `sys.exit` in the spawn bootstrap (`RemoteOpenAIServer` forces spawn), so all it needs is time.

`VLLM_WORKER_SHUTDOWN_TIMEOUT_SECONDS` is already documented as the "timeout in seconds for engine and worker process shutdown", and the client finalizer already uses it to shut down the EngineCore process manager, so this PR adds no new knob. Making the grace opt-in keeps the fast CUDA shutdown default unchanged. A user who sets the variable on ROCm now gets that value instead of the fixed 15 s. The kernel recorder exports `=30` on recording runs (ROCm today, and CUDA with vllm-project/ci-infra#685).

- `get_engine_process_shutdown_timeout()` returns `VLLM_WORKER_SHUTDOWN_TIMEOUT_SECONDS` when the variable is explicitly set and both the request timeout and the process budget are zero. This covers the API server, multi-API-server/headless, and DP supervisor paths, plus the `RemoteOpenAIServer` test budget, because they all call this function.
- If the variable is unset, nothing changes: CUDA still gets 0 s and ROCm still gets 15 s. A positive `--shutdown-timeout` whose remaining budget has run out still gets no extra grace.
- The log line no longer says "ROCm", since the grace can now apply on any platform.

Validated on MI300X, `facebook/opt-125m`, `vllm serve` started under the ci-infra#685 ROCm kernel recorder, one completion, then SIGTERM. To reproduce the CUDA behaviour on ROCm, the harness sets `ROCM_ENGINE_PROCESS_SHUTDOWN_TIMEOUT_S = 0` in the API server process. Each run counts whether the EngineCore recording ends with the recorder's `# end` footer, which is written by the exit hook and never runs after SIGKILL.

| Config (TP=1, 10 runs each) | EngineCore footer | force-killed | SIGTERM to server exit |
|---|---|---|---|
| main, 0 s grace, `VLLM_WORKER_SHUTDOWN_TIMEOUT_SECONDS=30` | 0/10 | 10/10 | 0.82 s median |
| this PR, 0 s grace, env unset (default) | 0/10 | 10/10 | 0.77 s |
| this PR, 0 s grace, `VLLM_WORKER_SHUTDOWN_TIMEOUT_SECONDS=30` | 10/10 | 0/10 | 2.84 s (2.52-3.27) |
| this PR, ROCm default (15 s), env unset | 10/10 | 0/10 | 2.82 s |

With TP=2 (3 runs each), the env var takes runs from 15/24 footered recordings to 24/24. Without it, EngineCore and both TP workers, which own the kernel names, are killed. Shutdown takes 0.87 s without the grace and 6.93 s with it. The grace is an upper bound: shutdown takes as long as EngineCore actually needs to tear down.
