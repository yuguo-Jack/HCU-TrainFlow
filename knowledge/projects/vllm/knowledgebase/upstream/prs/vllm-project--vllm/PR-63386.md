# [Perf][GLM-5.3] GLM-5.3 latency-specialized decode on B200 (CuTe DSL)

[Upstream PR](https://github.com/vllm-project/vllm/pull/63386) · state: open · merged: False

## Original PR description

## Overview

An opt-in decode path for GLM-5.3 (`GlmMoeDsaForCausalLM`) at TP8 on 8xB200 (SM100) and 8xB300 (SM103), following the specialized-decode RFC (#60904). With `--additional-config '{"decode_backend": "latency_specialized"}'`, CuTe DSL kernels run the 78 target layers inside vLLM's FULL uniform-decode CUDA graphs for steps of B requests of 1 + K tokens with B (1 + K) <= 16 rows (16 requests at MTP off, 4 at K = 3), at any static MTP K from 0 to 7. The specialized MTP drafter follows in #63387.

The only core edit is the registry entry: `GlmMoeDsaForCausalLM` (GLM-5 to GLM-5.3) now resolves to `vllm.models.glm53`. On SM10x that is a subclass of the DeepSeek-V3.2 model whose hooks do nothing under the default `decode_backend=auto`; elsewhere it is a thin subclass of `vllm.models.deepseek_v32`'s class that refuses `latency_specialized` and unknown `decode_backend` values.

Terms: the *switch* is the `decode_backend` setting and its startup checks; the *segment* is the set of CUDA graphs and buffers the switch installs for the claimed decode shapes.

**Revision 2** (this push). Revision 1 served one request at a time. This revision:
- serves batched decode: up to 16 rows per step, one set of row tiers (4 / 8 / 16 rows) for every (B, K) rather than a path per batch size (re the batching question in the revision-1 review);
- reads vLLM's default `flashinfer_trtllm` (trtllm-gen) MoE experts in place instead of requiring DeepGEMM MoE, so prefill keeps vLLM's default MoE backend;
- runs uniform steps above 16 rows on vLLM's own CUDA graphs in the same deployment, and drops `--max-num-seqs 1`;
- drops the copied FlashInfer MLA metadata builder (upstream's has the same draft-metadata update);
- passes the repository's pre-commit hooks and mypy, adds a B200 CI step and a supported-models entry;
- is rebased on current main.

## Claims

- MTP off: lower TPOT than stock for 1 to 16 requests at 8K to 128K prompts. The gap is largest at small batch (about -48% at B = 1) and narrows as the batch grows (about -15% at B = 16); table below.
- GSM8K is within noise of stock: 0.918 vs 0.913 at MTP off, 0.908 vs 0.902 at MTP 3.
- In the runs below, decode steps of up to 16 rows ran on this path; the server log's count of steps that fell back to the stock forward stayed at 0.
- With the default `decode_backend=auto`, behavior is unchanged.

## Validation

All runs on 8xB200. Each speed comparison ran both arms on one node; the GSM8K arms at MTP 3 ran on two nodes. Stock = this commit's parent (current main) with no additional config; this change adds `--additional-config '{"decode_backend": "latency_specialized"}'`.

```bash
vllm serve zai-org/GLM-5.3 --tensor-parallel-size 8 --block-size 64 \
  --attention-backend FLASHINFER_MLA_SPARSE --kv-cache-dtype fp8 \
  --compilation-config '{"cudagraph_mode": "FULL_DECODE_ONLY"}' \
  --max-model-len 131072 --max-num-batched-tokens 16384 --enable-prefix-caching \
  --max-num-seqs 16 [--additional-config '{"decode_backend": "latency_specialized"}']
# MTP 3 rows add: --speculative-config '{"method": "mtp", "num_speculative_tokens": 3}' and --max-num-seqs 4
```

## Details

**Design.** One claim function (`switch.shape_path`) maps every (K, B) to a build: the one-request build (4 rows), a lone 8-row build, whole row groups on tier 8 or 16, or packed rows on tier 8 or 16. Index selection runs request-parallel over the eight ranks on the packed tiers. MoE is W8A16 up to eight live rows and W8A8 above. Cross-rank exchange uses flag-in-data mailboxes in a torch symmetric-memory arena.

| Area | Change |
| --- | --- |
| Kernels (`vllm/models/glm53/nvidia/ops/cute_dsl/`) | prologue, sharded index selector, fused MLA worker, fused MoE (routed + shared, W8A16 and W8A8), dense FFN; row tiers 4/8/16 are compile-time parameters of the same kernels. Logits are vLLM's `compute_logits` |
| Weights | MoE experts (vLLM's `flashinfer_trtllm` tensors), dense FFN, FP8 linears, indexer and embedding are read in place. Each layer's attention also gets absorbed-query pages: W_UK x W_UQ (nope part) precomputed from the checkpoint and re-quantized to block-scaled FP8; with the other added forms this is +0.7 to 0.9 GiB per rank at load |
| vLLM integration | the model class owns the hooks: the forward offers each uniform decode step to the installed segment, `process_weights_after_loading` builds it. `Glm53ModelState` (Model Runner V2) overrides `add_request`, `remove_request`, `preprocess_state` (per-step accounting), `initialize_kv_cache` (rebuild over the final KV pool) and `custom_sampler` (compiles request-time Triton kernels at startup and returns `None`). No other core file changes |
| FlashInfer | skips the `trtllm_batch_decode_mla` autotune, whose tuning graphs slow the later decode-graph replay |

**Requirements.** The switch refuses to start, on every TP rank, unless: SM100 or SM103; TP8 without PP, EP, DP, DCP or PCP; Model Runner V2 with FULL CUDA graphs for decode batches only (`FULL_DECODE_ONLY` or `FULL_AND_PIECEWISE`, not `--enforce-eager`); FlashInfer MLA sparse with fp8 KV cache; MoE backend `auto` or `flashinfer_trtllm`; speculative decoding, if any, is MTP with a static K (no dynamic speculative decoding or adaptive verification); no LoRA, KV connector, batch-invariant mode, micro-batching or sleep mode. After loading it also checks the GLM-5.3 geometry and the FP8 linear form. Every prefill, mixed step and uniform step above 16 rows runs vLLM's stock layers.

**Tradeoffs and limits.**
- Memory per rank at MTP off, `--max-num-seqs 16`: the segment arena (5.6 GiB, allocated inside vLLM's profiling window), the tier graphs (+3.1 GiB graph pool) and the added weight forms (+0.7 to 0.9 GiB) shrink the KV pool by 6.2 GiB, from 1,571,456 to 1,428,992 tokens (-9.1%). The arena is 2.4 to 5.6 GiB by K and `--max-num-seqs` (README table). vLLM's CUDA-graph memory estimate does not match the segment's graphs (README).
- CUDA graph capture sizes: the path sets the sizes up to its largest graph (the row tiers), keeps vLLM's or the user's sizes above it up to `--max-num-seqs` x (1 + K), and always adds that size.
- Cold start: the CuTe host wrappers compile once per node (about 40 s per rank), cached under `VLLM_CACHE_ROOT`. A fully cold node took about 20 minutes to the first ready server, so it needs `VLLM_ENGINE_READY_TIMEOUT_S=3600`; warm restarts take about 2 minutes.
- Index keys on the narrow builds are written on ranks 0 to 2 only and broadcast to the other ranks before any stock step, a switch to a wide tier or a request's removal.
- Locality-aware arena placement (CUDA locality domains) is used when the driver supports it and falls back to plain memory otherwise; `decode_backend` is the only user-facing setting.
- Scope: GLM-5.3 only; B (1 + K) <= 16 rows per step on the specialized path.

**CI.** A dedicated B200 step (`glm53-unit-tests-b200`) runs `pytest -v -s models/glm53`; the tests skip without SM100 or the CuTe DSL package. Most tests are host-side (shape mapping, switch, weight forms, rebuild); kernel numerics are checked by building every served entry and by the served runs above, not by a per-kernel reference test in CI. The served TP8 path needs a full 8-GPU node and is validated outside CI.

**Not a duplicate.** vLLM's other specialized decode paths (Kimi K3 in `vllm/models/kimi_k3`, DeepSeek-V4.1 in `vllm/models/deepseek_v41`) serve other architectures; `vllm/models/glm5next` is GLM-5.3-Flash (`Glm5NextForCausalLM`), a different model. #61311 proposes shared abstractions for specialized decode; this PR does not depend on it and can adopt them if they land first.
