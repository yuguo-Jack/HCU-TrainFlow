# [Bugfix] Fix KV cache memory leak when all requests finish with connector

[Upstream PR](https://github.com/vllm-project/vllm/pull/46579) · state: closed · merged: False

## Original PR description

fix: https://github.com/vllm-project/vllm/issues/46502
When a KV connector (e.g. MooncakeStore) returns delay_free_blocks=True for a finished request, the GPU blocks are held until the async store completes. However, InprocClient.dp_engines_running() always returned False, so the step loop exited immediately after the output processor cleared the request — without waiting for the async store to finish. GPU memory was leaked until the next round of requests triggered step().

Fix by delegating dp_engines_running() to scheduler.has_finished_requests(), which detects pending delayed KV connector frees. The output processor already tracks unfinished requests, so has_requests() is not needed here.

Previous commits:
When a KV connector (e.g. MooncakeStore) returns delay_free_blocks=True for a finished request, the GPU blocks are held until the async store completes. However, after update_from_output() clears finished_req_ids, the scheduler had no way to know that deferred frees were still pending.

Two changes:

1. InprocClient.dp_engines_running(): delegate to scheduler.has_finished_requests() instead of returning False, so the step loop keeps running while delayed frees are pending.
2. Scheduler.has_finished_requests(): when finished_req_ids is empty and a KV connector is configured, compare len(self.requests) against the total count in all active queues (waiting + skipped_waiting + running). Requests with delay_free_blocks=True remain in self.requests but are removed from all queues, so the count mismatch is detected.

hi @ApostaC as the second issue is already fixed upstream, I have reverted those changes and kept only the fix for the first issue, could you please take a look at this?
