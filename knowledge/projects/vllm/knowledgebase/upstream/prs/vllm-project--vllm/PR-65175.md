# [Spec Decode] Support XPress + Acceptance Estimator

[Upstream PR](https://github.com/vllm-project/vllm/pull/65175) · state: closed · merged: True

## Original PR description

## Overview

Adaptive verification does nothing for XPress today. The acceptance estimator is created, but XPress never feeds it, so the AV budget reads an uninitialised confidence buffer and prunes every draft after the first. Turning AV on makes XPress about 3x slower than leaving it off.

This wires XPress to the estimator, using the logits the draft tokens are sampled from.

## Performance

One H100, Qwen3-8B with the XPress b16 draft, 15 draft tokens, greedy, prefix caching off, SPEED-Bench throughput_1K shuffled with seed 42. AIPerf runs a concurrency grid of 1, 8, 32, 64 and 128 with 30 s cells and 3 trials. Throughput is output tokens in the steady window of each cell, median over the trials.

![Throughput-interactivity pareto](https://raw.githubusercontent.com/tomasruizt/vllm/assets/xpress-av/xpress-av-pareto.png)

AV off is the same curve on both commits, within 1%, which is also the spread between trials. On main, AV on verifies one token per step and loses 26% to 71% of throughput. Here it costs 8% at c1 and c8, and from c32 up it is faster than AV off: the budget verifies fewer drafts (AL 3.0 to 3.3 against 3.5 to 3.7), which makes each target step cheaper and more than pays for the shorter accept run.

## Claims

- AV on no longer collapses: acceptance length 1.08 to 7.26 on the e2e case (7.39 with AV off), acceptance rate 0.005 to 0.42.
- Throughput goes from a 26-71% loss on main to an 8% cost at c1 and c8, and a 21-40% gain from c32 up, because the budget spends fewer verified drafts per step.
- Accuracy is unchanged: GSM8K 0.885 with AV on and off, 1,319 questions.
- AV off is untouched. The draft is bit-identical, and both commits measure within 1% in every cell.

## Validation

The existing Qwen3-8B + XPress b16 case gets an `enable_adaptive_verification` variant in `tests/v1/e2e/spec_decode/acceptance_rates/xpress/test_xpress.py`. It runs in the nightly XPress job, so no buildkite change is needed.

## Details

`draft_token_confidence_probs` is allocated with `torch.empty` and only written by `_maybe_predict_acceptance`. DFlash and DSpark call it, XPress did not, so the AV budget read uninitialised survivals and the estimator never saw a single feature or verdict.

`jacobi_refine_greedy` now returns the logits of its last pass next to the draft ids, and `XPressSpeculator` hands them to the estimator. Both paths return exactly the logits the argmax ran on, the summed bias over the vocabulary or the top-C candidate scores when `xpress_topc` is set. Nothing is computed when AV is off.

The draft is unchanged, so AV now only decides how many draft tokens to verify, which is what it was meant to do.
