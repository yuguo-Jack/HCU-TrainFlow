# [CI] Enroll the MI300 Batch Invariance (Distributed) mirror in automatic sharding

[Upstream PR](https://github.com/vllm-project/vllm/pull/65585) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Enrolls the AMD mirror of Batch Invariance (Distributed) in `automatic_shard`. Its base H100 step is already enrolled. The mirror was dropped from #64272 because two of its commands differ only in env vars (`VLLM_TEST_MODEL=` OLMoE vs Granite): when the plan put them on different shards, the shard plugin matched the Granite command to OLMoE's plan entry and ran none of its tests. vllm-project/ci-infra#889 (merged) fixes that, so the mirror can shard. No commands change.

## Claims

| Job | Plan |
|---|---|
| `batch-invariance-distributed-4xh100` AMD mirror | 2 shards |

- Every test of every command runs in exactly one shard, including both `VLLM_TEST_MODEL` commands when they land on different shards.

## Validation

- Planned with ci-infra main's planner (with #889) against main's timings: 2 shards, about 3% more machine time for the second job's setup.
- The sharding harness (real generator, mock test tree) passes in PR mode and main mode: every test runs once.
- `split_check.py` finds no step whose jobs each run the whole suite.
- The mirror passed every recent main run, daily and nightly.
- A staging build with #889's generator ran this mirror in 2 shards, OLMoE on one and Granite on the other, with the same test count as main.
- On this head, `/ci run` (#99854) passed. The mirror was left out because its base step is nightly-only, so scoped build #99860 ran it: 2 shards, both passed with no retries, every command's passed count matches the latest main nightly (11 tests, OLMoE and Granite 1 each), machine time within 5%.

## Details

- **Why it was held:** the plugin found its plan entry by pytest arguments alone, and env-var prefixes aren't arguments. #889 has each shard export the command's position so the plugin picks the right entry.
- **Timeouts unchanged.** `timeout_in_minutes` stays per job. Fallback-aware timeouts belong in a central timeout setting.
