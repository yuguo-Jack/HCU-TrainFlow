# [Bugfix][Platform] Keep PIN_MEMORY eager; avoid resolving platform during import vllm

[Upstream PR](https://github.com/vllm-project/vllm/pull/63601) · state: closed · merged: True

## Original PR description



## Overview

Reworks #60766: keeps `PIN_MEMORY` a plain eagerly-computed module global (instead of a lazy module `__getattr__` plus `is_pin_memory_available()` calls in the `torch_utils` hot paths), and fixes the underlying import-order problem instead: `import vllm` resolved `current_platform` and loaded platform plugins while vLLM was half-imported.

## Claims

- `import vllm` doesn't resolve the platform (same as #60766), including with `VLLM_TRITON_FORCE_FIRST_CONFIG=1`, which #60766 didn't cover.
- An out-of-tree platform plugin whose `register()` imports from `vllm.utils.torch_utils` is detected correctly, both for `import vllm` and `from vllm import LLM`.
- `PIN_MEMORY` is a plain module global again; `async_tensor_h2d` / `np_to_pinned_tensor` read it directly.
- Out-of-tree platform plugin detection failures are now logged as warnings rather than silently (debug) falling back to another platform.

## Details

**Root cause.** `vllm/__init__.py` → `vllm.env_override` → `from vllm.utils.torch_utils import is_torch_equal, is_torch_equal_or_newer` → module-level `PIN_MEMORY = is_pin_memory_available()` → `current_platform` resolution → plugin `register()` runs against a partially initialized `torch_utils`. The `ImportError` was swallowed in `resolve_current_platform_cls_qualname`, so another platform was silently selected.

**Changes.**
- `is_torch_equal*` move to a new dependency-free `vllm/utils/torch_version.py` (re-exported from `torch_utils`, so existing imports keep working). `env_override` and `envs` import from it, so `import vllm` no longer imports `torch_utils` at all.
- `PIN_MEMORY` is assigned at the end of `torch_utils.py`. Other paths (e.g. `from vllm import LLM` → `vllm.config.cache` → `torch_utils`) still resolve the platform while importing `torch_utils`; with the assignment last, a plugin importing anything else from `torch_utils` finds it already defined. The restored `test_platform_plugins` (runs `from vllm import LLM`) covers this.
- The `VLLM_TRITON_FORCE_FIRST_CONFIG` autotuner patch is installed on import of `vllm.triton_utils` rather than in `env_override`, since importing that package resolves the platform. All vLLM Triton kernels import through it, so the patch is still in place before any autotuning; a third-party `triton.autotune` kernel run before `vllm.triton_utils` is imported would no longer be patched.
- Plugin Integration CI step now also triggers on the files involved (it didn't run for #45424, which introduced the regression).

**Not addressed (also not addressed by #60766).** `import vllm.config` still resolves the platform (`vllm/config/compilation.py` imports `current_platform` at module level), and a plugin whose `register()` needs the platform itself (e.g. imports `PIN_MEMORY` or `vllm.triton_utils`) can't work under any of these schemes.
