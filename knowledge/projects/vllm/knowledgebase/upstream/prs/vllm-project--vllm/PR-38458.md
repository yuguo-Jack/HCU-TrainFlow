## Summary

## What the document covers

- **Architecture**: GitHub Actions (linting) vs. Buildkite (GPU tests), and how the dynamic pipeline generator works
- **Triggering CI**: `ready` / `ready-run-all-tests` labels, file changes that force a full run, `ci-no-fail-fast`, docs-only detection
- **What gets tested**: All 27 test-area groups and 5 hardware-test groups with descriptions
- **Hardware infrastructure**: Full mapping of `device` values → agent queues → physical hardware (L4, H100, H200, B200, GH200, A100, AMD MI*, Intel, Ascend, ARM)
- **Step definition reference**: Full field reference table; `source_file_dependencies` explained; AMD mirror steps
- **Required vs. optional tests**: How to unblock optional tests in the Buildkite UI; soft-fail behavior
- **Adding new tests**: Step-by-step guide (find the YAML, write the step, choose hardware, set dependencies, sharding, CPU/hardware tests)
- **Checking CI results**: Buildkite UI guide, CI dashboard, test analytics
- **Investigating failures**: Quick checklist, reproducing locally with the CI Docker image, links to `failures.md`
- **Multi-node tests**, **common CI patterns**, **key resources table**

![critical](https://www.gstatic.com/codereviewagent/critical.svg)

The `docker run` command for reproducing failures is syntactically incorrect and uses a misleading image for pull request debugging.

1.  **Incorrect Command**: The command as written is missing a line continuation `\` after the image name. This would cause `pytest` to run on the host machine, not inside the container, failing to reproduce the CI environment.
2.  **Misleading Image**: It suggests using `vllm-ci-postmerge-repo:latest`, which is for the `main` branch. A contributor debugging their PR needs to use `vllm-ci-test-repo` with their specific commit hash to test their own changes.

These issues can cause significant confusion and prevent users from reproducing CI failures correctly. The instructions should be corrected for both syntax and content. I've also removed the redundant `docker pull` from the example for conciseness.

```suggestion
3. **Reproduce locally**: Run the failing test in the correct CI Docker image.
   For PRs, use `vllm-ci-test-repo:<commit_hash>`.
    ```bash
    # Example for a PR failure. Get commit hash from PR page.
    COMMIT_HASH="<your_commit_hash>"
    docker run --gpus all --rm \
      -v $HOME/.cache/huggingface:/root/.cache/huggingface \
      public.ecr.aws/q9t5s3a7/vllm-ci-test-repo:${COMMIT_HASH} \
      pytest tests/failing/test_foo.py::test_name -v
    ```
```
