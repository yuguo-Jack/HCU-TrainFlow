# [Frontend] Support CustomToolCall in the non-Harmony Responses API

[Upstream PR](https://github.com/vllm-project/vllm/pull/57322) · state: closed · merged: True

## Original PR description

## Purpose

First of the smaller PRs splitting #56285 per review ("I'd suggest prioritizing support for CustomToolCall first"). @chaunceyjiang

`type=custom` tools are presented to the shared function-tool parsers as a single-string `input` function shim: the schema is generated by `custom_tool_parameters`, a grammar `format` is folded into the description, and schema lookup / xgrammar structural tags / named `tool_choice` with `type=custom` all see the same shim (`vllm/tool_parsers/utils.py`, `structural_tag_registry.py`, `vllm/parser/abstract_parser.py`, and the `tool_choice` validator in `responses/protocol.py`). Completed calls stream as `response.custom_tool_call_input.delta` / `.done` events (with a streaming-safe partial decoder, including surrogate-pair handling, so the concatenated deltas are always a prefix of the final input) and materialize as `ResponseCustomToolCall` items with `ctc_` ids; replaying a `custom_tool_call` / `custom_tool_call_output` item re-encodes the payload through the same shim, so multi-turn Codex-style sessions round-trip with no server-side storage.

**Overlap disclosure.** #56418 ("Preserve custom_tool_call on non-Harmony Responses routes", open since 2026-09-11) implements the same shim approach and its own description already notes the overlap with #56285. This PR is the CustomToolCall subset of #56285 and additionally covers the `ToolChoiceCustom` acceptance paths in `DelegatingParser` (forced/named tool choice, required-tool streaming extraction) and tests for forced custom tools against the GLM 4.7 structural-tag parser; #56418 additionally covers `tool_choice=none` and namespace flattening. Whichever lands first, the other can be reduced to the remainder — happy to rebase or fold whichever direction maintainers prefer. #49882 proposes the opposite (reject custom tools) and is superseded by either implementation.

## Known limitation

Custom tools do not honor `--tool-strict-level`: `_dump_tool_for_xgrammar` emits no `strict` for a `CustomTool` and `_with_tool_strict` only pins `FunctionTool` / `ChatCompletionToolsParam`, so under `strict_level=parameter` a custom tool's `{"input": ...}` arguments stay unconstrained while sibling function tools are pinned. Nothing that worked before breaks; full strict support can be a follow-up.

New: custom tool output item + history replay through the shim + input decode/partial-decode (incl. surrogate pairs); `custom_tool_call_input` streaming events end-to-end through the processor; `arguments.done` emitted even without prior deltas; forced `tool_choice` (required and named `type=custom`) sees custom tools in JSON schema and structural tags, incl. the GLM 4.7 parser. Unchanged from main: encrypted-content rejection behavior, function-call streaming, serving paths.

I think the bigger concern here is that we're effectively modeling a custom tool as a function tool with an `{"input": string}` schema.

https://developers.openai.com/api/docs/guides/function-calling?api-mode=responses

One of the main semantics of a custom tool is that its input is free-form text and does not need to be wrapped in JSON. More importantly, `format=grammar` (CFG)  is supposed to constrain the generated custom-tool input, while this implementation only adds the grammar to the tool description, so it cannot actually enforce that constraint.

The handwritten partial JSON decoder also seems to be a consequence of this shim: we first force the free-form payload into JSON, then need to decode it again while streaming.

Would it make sense to either support custom-tool input natively in the parser/structured-output path, or initially support only plain custom tools and explicitly leave `format=grammar` unsupported?

- sfeng33 · comment · 2026-09-22T03:44:49Z · [source](https://github.com/vllm-project/vllm/pull/57322#discussion_r4068282063)

This guards `data` being a dict, but not the shape of `tools` or of each entry, so a malformed body now raises a bare `AttributeError` (HTTP 500) instead of the pydantic `ValidationError` (400/422) it produced before this validator existed. Each of these returns a 4xx on `main` and a 500 with the patch:

- `tools=[None]` — `None.model_dump()`.

Because this runs `mode="before"`, it fires ahead of the field validation that would otherwise reject these cleanly, so any client with a slightly wrong body gets a 500 rather than a message telling them what's wrong.

- sfeng33 · comment · 2026-09-22T03:44:49Z · [source](https://github.com/vllm-project/vllm/pull/57322#discussion_r4068282070)

File: `vllm/entrypoints/openai/responses/streaming_events.py` · line None

This fallback reports a truncated fragment as the complete input rather than surfacing that something went wrong. When the final decode isn't an extension of what was already streamed, `payload` becomes `state.tool_call_payload` — whatever prefix happened to be emitted — and that value goes out in both `custom_tool_call_input.done` and the `output_item.done` item.

Reproduced through `SimpleStreamingEventProcessor` with two chunks, `'{"a": "xy"'` then `', "input": "hello"}'`:

- streaming emits `custom_tool_call_input.done(input="xy")` and an output item with `input="xy"`
- `decode_custom_tool_input` on the same complete arguments returns `"hello"`

So the client is handed `"xy"` — a fragment of an unrelated key — marked complete, and the streaming and non-streaming paths disagree on identical model output. `_emit_custom_tool_input_delta` compounds it by dropping any non-prefix delta, so nothing upstream ever signals the divergence.

The mismatch is only reachable because of the single-key fallback in `_custom_tool_payload` (see my comment on `utils.py`); fixing that one removes most of the divergence. For whatever remains, I'd rather see the authoritative final `decode_custom_tool_input` value win — emit the correcting delta even when it isn't a clean extension — than have `done` report a prefix it knows is wrong.

This fallback unwraps *any* single-key object, not just the `input` shim, which defeats the bare-text pass-through the docstring on `decode_custom_tool_input` promises just below. A custom tool exists precisely to carry a freeform payload, so a model that emits its payload directly rather than through the `{"input": ...}` shim gets silently rewritten whenever that payload is a one-key JSON object:

```python
>>> decode_custom_tool_input('{"file": "a.py"}')
'a.py'
```

The tool receives `a.py` instead of the JSON object the model actually produced, and there's no way for the caller to tell the two apart afterwards. Unwrapping only the exact `CUSTOM_TOOL_INPUT_KEY` and passing everything else through keeps the shim working and preserves the documented behavior:

```python
def _custom_tool_payload(parsed: Any) -> str | None:
    if not isinstance(parsed, dict):
        return None
    value = parsed.get(CUSTOM_TOOL_INPUT_KEY)
    return value if isinstance(value, str) else None
```

This also removes the main way streaming and non-streaming can disagree (see my comment on `streaming_events.py:1118`). If the fallback is deliberate — covering a model that wraps the payload under its own key — it'd help to say which model in a comment, since as written it fires for every single-key payload.
