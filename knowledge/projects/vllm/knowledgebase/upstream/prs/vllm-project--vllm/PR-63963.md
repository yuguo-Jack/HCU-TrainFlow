# [Rust Frontend] Accept list-form chat templates like Transformers

[Upstream PR](https://github.com/vllm-project/vllm/pull/63963) · state: closed · merged: True

## Original PR description

## Overview

`tokenizer_config.json` may store `chat_template` as a list of named templates instead of a string. `NousResearch/Hermes-3-Llama-3.1-8B` ships `[{"name": "default", ...}, {"name": "tool_use", ...}]`. On Python, Transformers collects the list into a dict when it loads the tokenizer, and vLLM resolves the template per request through `tokenizer.get_chat_template(chat_template, tools=tools)` (`vllm/renderers/hf.py` `resolve_chat_template`): with tools it uses `tool_use` if present, otherwise `default`. On Rust, `HfTokenizerConfig.chat_template` is `Option<String>`, so parsing `tokenizer_config.json` fails and the frontend does not start for such models. This PR parses both forms and selects the named template per request like Transformers.

## Claims

- A model whose `tokenizer_config.json` stores `chat_template` as a list of named templates loads on the Rust frontend.
- Requests with tools render with the `tool_use` template when present; requests without tools render with `default`.
- For `NousResearch/Hermes-3-Llama-3.1-8B`, the Rust renderer's prompts match Transformers byte for byte, with and without tools.
- A configured `--chat-template`, a dedicated template file, and a request-level `chat_template` override keep their precedence over tokenizer-config templates.

## Details

- `vllm-text` parses `chat_template` as `HfChatTemplate::{Single, Named}`, the owner of the `tokenizer_config.json` schema. It exposes the two names Transformers selects on its own: `default_template()` and `tool_use_template()`. A later list entry wins over an earlier one with the same name, as in Transformers' dict.
- `HfChatRenderer` compiles the `tool_use` template next to the default one and picks it when the request has tools (`request.tools()`, the same tools it passes to the template). Other requests use the default. A configured `--chat-template` or a dedicated template file still replaces every tokenizer-config template, `tool_use` included, as before. A request-level `chat_template` override still wins.

**Ownership and layering.** The schema and Transformers' naming convention live where `tokenizer_config.json` is parsed (`vllm-text`). The per-request choice lives in the HF renderer, the only consumer that compiles and renders the template. Each named template is compiled once at load, and its content format is detected separately, as Python does for the template it resolves.

**Not covered.**

- Python also resolves a request `chat_template` (with `--trust-request-chat-template`) that names one of the model's templates. Rust compiles the string as a literal template, as it already did.
- Transformers' `additional_chat_templates/` directory is not read either; dedicated-file discovery is unchanged.
- `/tokenize` with an explicit `tools: []`: Python passes `[]` to Transformers, which selects `tool_use`. Rust lowers omitted and empty tools to the same empty vector, so it selects `default`. This only affects `/tokenize`; chat completions and render reject `tools: []` with 400, as Python does. The same lost presence already makes Rust pass no `tools` variable where Python passes `[]`, independent of this PR. Fixing it means carrying tool presence through `ResolvedToolContext`, which is a separate change.

Python reference: Transformers `PreTrainedTokenizerBase.get_chat_template` and `vllm/renderers/hf.py` `resolve_chat_template`.

Not a duplicate: no open PR accepts list-form `chat_template` in the Rust frontend.
