# [Bugfix][Reasoning] Strip <think> from multi-token streaming deltas in Ernie4.5 and HY4 parsers

[Upstream PR](https://github.com/vllm-project/vllm/pull/60195) · state: open · merged: False

## Original PR description

## Overview

Fixes the Ernie4.5 and HY4 copies of the start-marker leak from #55195. #55210 and #56262 both patch `basic_parsers.py` and the Olmo3 parser; neither touches `ernie45_reasoning_parser.py` or `hy_v4_reasoning_parser.py`, which carry their own streaming logic (see the file-level breakdown in the issue thread). This PR is limited to those two files so it does not overlap with either open PR.

## Claims

- Streaming output of `ernie45` and `hy_v4` no longer contains the literal `<think>` when the start marker arrives in the same delta as following tokens. Streaming now matches the non-streaming result for the same text.
- When the start token id is present but its text was skipped during detokenization, `hy_v4` no longer slices from index -1, which dropped the reasoning text.
- No change for single-token deltas or for streams where `<think>` is absent from the output (the usual case, since both chat templates inject it into the prompt).

## Validation

Reproducer, before the change (deltas `["<think>reasoning words", "</think>", "answer words"]`):

```
ernie45: streaming     reasoning='<think>reasoning words' content='answer words'
ernie45: non-streaming reasoning='reasoning words' content='answer words'
hy_v4:   streaming     reasoning='<think>reasoning words' content='answer words'
hy_v4:   non-streaming reasoning='reasoning words' content='answer words'
```

Tests added:

- `tests/reasoning/test_ernie45_reasoning_parser.py`: two cases (`<think>` plus text in one delta; `<think>...</think>` plus text in one delta), compared against the non-streaming result on the same text, using the real `baidu/ERNIE-4.5-21B-A3B-Thinking` tokenizer.
- `tests/reasoning/test_hy_v4_reasoning_parser.py` (new): same two cases plus "start token id present, text absent", driven through `HYV4ReasoningExtractor` with a synthetic vocab, so no checkpoint or `trust_remote_code` is needed.

Both new ernie45 cases and two of the three hy_v4 cases fail on main and pass with this change.

Commands run (macOS, CPU only, `PYTHONPATH=$PWD`, `--confcutdir=tests/reasoning` to skip the GPU-oriented root conftest):

```
pytest tests/reasoning/test_ernie45_reasoning_parser.py tests/reasoning/test_hy_v4_reasoning_parser.py
# 13 passed

pytest tests/reasoning/  (all files except test_hunyuan_* and test_kimi_k2_*, which need trust_remote_code)
# 464 passed

pre-commit run --files <the four changed files>   # all hooks pass
pre-commit run mypy-3.12 --hook-stage manual --files <the two parser files>   # pass
```

No model evaluation: the change only affects how an existing output string is split in streaming mode; generated tokens are unchanged.

## Details

Root cause: both parsers special-case a delta that is exactly one special token (returned as `None`), but a delta holding `<think>` plus more tokens falls through to the "reasoning continues" branch, which returns `delta_text` untouched. The non-streaming path partitions on `<think>` and drops it, so the two paths disagreed.

Fix: when the start token id is in `delta_token_ids`, strip the marker text from `delta_text` before the existing branches run. The `find() != -1` guard matters because with `skip_special_tokens` the id can be present while the text is not; the previous `hy_v4` code sliced from `-1 + len(start_token)` in that case.

Not covered here on purpose: the same unguarded `find()` pattern for the end marker (`</think>`), which is a separate behavior and would widen the diff beyond this issue.
