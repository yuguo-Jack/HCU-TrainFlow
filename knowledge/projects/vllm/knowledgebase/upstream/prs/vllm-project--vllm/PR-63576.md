# [Bugfix][ROCm][DSv4.1] Await krdy before K2's combine reads klen in index-source launches

[Upstream PR](https://github.com/vllm-project/vllm/pull/63576) · state: closed · merged: True

## Original PR description

- In K2's `stage_combine` (`mono/attention/back.py`), an index source now waits for its token's `krdy` flag and reads `klen` past the per-XCD caches (CM_DEV), as `stage_split` already does.
- Non-index launches are unchanged: both are behind `const_expr("krdy" in c)`.

An index-source K2 rebuilds the key table (`kt`/`klen`) itself in the same launch. #61082 made the split stage wait for that, but the combine still read `klen` with a plain load and no wait, so it can see the previous launch's key count. Whether that breaks anything depends on how the stale count compares with the real one:

| Previous launch's `klen` vs this launch's | What the combine does | Before | After |
|---|---|---|---|
| Equal | Merges the right chunks by luck | Correct | Correct |
| Smaller | Merges too few chunks | Wrong attention output: 3,791 of 8,704 MXFP8 codes of the attention output wrong (`Case(ratio=2, R=17, T=1, index=True)`, TP2) | Correct |
| Larger | Waits on split chunks that are never published | Hang: the unbounded `_spin` never returns (killed at 420 s, 3/3 runs, TP2) | Correct |

That is the index-source failure caught by the slow-reference test in #63486, and the intermittent index-source hang seen while stressing it.

| Check (MI350X, AITER v0.1.26) | Before | After |
|---|---|---|
| Index-source vs reference, TP2 | 0/3 pass | 39/40 pass (10 + 30 loop) |
| Index-source vs reference, TP4 | 0/2 pass | 3/3 pass |
| Long-then-short index sequence, TP2 | 3/3 hang | 3/3 pass |
| Same token pair, both orders, TP2 | 0/3 pass | 15/15 pass |
| Rest of the DSv4.1 mono numerics / layers / decode tests | - | 7 passed + 1 skipped / 4 passed + 1 skipped / 85 passed |

The one failing TP2 run in the 40 failed the relative-error check before per-row logging was added; the 30 logged runs after it were bit-identical (rel 0.006460). Index launches were not exercised on gfx942, which shares this code.

**Performance.** One layer step (K1 + index select + K2 + FFN) captured as a CUDA graph of 20 steps, 200 replays, 5 base and 5 fix runs interleaved. Each index case runs after its non-index twin so that the stale `klen` equals the correct one and the base result is valid. Median per step:

| Case | Base (us) | Fix (us) | Fix - base (us) |
|---|---|---|---|
| TP2, index, R=17 short | 448.1-450.8 | 448.6-450.6 | -0.1 to +0.1 |
| TP2, index, R=17 long | 451.1-452.3 | 450.7-451.6 | -0.6 to +0.2 |
| TP2, index, R=4 x T=6 | 554.0-557.4 | 555.8-558.2 | -0.1 to +1.3 |
| TP4, index, R=17 short | 306.3-308.0 | 307.1-307.5 | -0.3 to +0.6 |
| TP4, index, R=17 long | 307.6-309.2 | 308.0-308.9 | -0.6 to +0.6 |
| TP4, index, R=4 x T=6 | 366.5-367.8 | 367.0-368.5 | +0.7 to +0.8 |
| Non-index control (unchanged code) | - | - | -0.3 to +0.4 |

Every delta is within the ~1 us (0.2-0.3%) run-to-run noise of the unchanged control: the `krdy` flag is normally published long before the combine reaches it, so the cost is one device-scope poll and a CTA barrier per combine unit.

This unblocks #63486, whose DSv4.1 index-source test is a plain test that depends on this fix.
