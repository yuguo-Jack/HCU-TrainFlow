# [Bugfix][KV Offload] Preserve stored event prefix order

[Upstream PR](https://github.com/vllm-project/vllm/pull/63249) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

Preserve offload store key order so self-describing `BlockStored` events remain
parent-before-child within a transfer job. This prevents KV-aware routers from
dropping child blocks when a parent mapping has not been indexed yet.

## Claims

- Keep `TransferJobStatus.keys` in prefix order and deduplicate keys while
  retaining their first occurrence.
- Do not change the KV-event wire format or guarantee ordering across separate
  secondary-tier jobs, tiers, or promotion events; router-side pending/replay
  still covers those cases.

## Details

The missing prefix order resulted from three assumptions rather than a decision
that order was unnecessary:

- [`#39186`](https://github.com/vllm-project/vllm/pull/39186) introduced
  `TransferJobStatus.keys` as set-backed job bookkeeping before offload events
  existed.
- [`#43468`](https://github.com/vllm-project/vllm/pull/43468) made stored events
  self-describing and explicitly treated key order as irrelevant because each
  payload contains its parent hash. The order-independent test and
  “key order is free” comment codified that assumption.
- A consumer test in
  [`#52103`](https://github.com/vllm-project/vllm/pull/52103#issuecomment-6251409146)
  later showed that llm-d still needs the parent event indexed first. The author
  confirmed the gap in
  [this reply](https://github.com/vllm-project/vllm/pull/52103#issuecomment-6255856451).

`prepare_store()` returns keys in prefix order, but the scheduler stored them in
a set. This can emit a child first even when transfer completion is FIFO. The
scheduler now preserves job order without removing set-style deduplication.

Secondary tiers are intentionally outside the ordering guarantee. FS/OBJ jobs
complete asynchronously and may become distinct raw events; tier aggregation
emits primary and secondary events by tier, not by parent topology. Therefore
this change fixes intra-job ordering but does not reorder across secondary jobs,
tiers, or promotions. Those cases remain a consumer concern.

Duplicate-work check: no open PR directly fixes this ordering path. #63129
addresses reused-key metadata lifecycle, and #52103 refactors event provenance
and removals while still retaining set-backed job keys.

AI assistance was used for investigation, implementation, and tests. The human
submitter must review every changed line and rerun the validation above.

I want to clarify the old `key order is free` assumption and why this PR intentionally narrows it.

That statement is correct at the payload level: each self-describing `BlockStored` contains its own tokens, parent hash, and block size, so the tracker can construct the payload without seeing the previous event.

It does not imply that a consumer can update its index in arbitrary order. For a child block, llm-d needs the parent engine hash to resolve an existing engine-hash -> request-key mapping before it can compute the child request key:

Thanks for working on this. From my point of view, `chunk_idx` is only used internally to sort stored events parent-first. No downstream consumer reads it directly; llm-d only relies on the resulting order, while Dynamo does not.
