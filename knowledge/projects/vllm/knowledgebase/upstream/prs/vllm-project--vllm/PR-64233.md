# [Bugfix][torch.compile] Read traced sources with source encoding

[Upstream PR](https://github.com/vllm-project/vllm/pull/64233) · state: open · merged: False

## Original PR description

## Overview

Refs #64204. This addresses only the separate Windows source-encoding side note, not the torch 2.11 Triton kernel side-table failure.

Read traced Python sources with `tokenize.open` in both compile-cache paths so their contents and hashes do not depend on the process locale.

## Claims

- AOT source verification and JIT cache hashing now use Python's source-encoding rules, including UTF-8 defaulting and PEP 263 encoding cookies.
- A forced-cp1252 regression proves that UTF-8 source produces the same hash as its actual content instead of a hash of locale-decoded text.

## Validation

New regression, run against the unmodified production files and then the fixed files:

```bash
VLLM_TARGET_DEVICE=cpu uv run --no-project .venv/bin/python -m pytest tests/compile/test_aot_compile.py::test_compute_code_hash_uses_source_encoding -v
```

- Baseline: 1 failed. The computed hash differed from `_compute_code_hash_with_content` because cp1252 decoded the UTF-8 bytes into different text.
- Fixed: 1 passed. The test was run again after restoring the fixed files and passed again.

Complete affected test file on the same environment:

```bash
VLLM_TARGET_DEVICE=cpu uv run --no-project .venv/bin/python -m pytest tests/compile/test_aot_compile.py -q
```

| Production sources | Result |
| --- | --- |
| Baseline plus the new regression | 10 failed, 20 passed, 2 skipped |
| Fixed | 9 failed, 21 passed, 2 skipped |

The only failure-set difference is the new regression changing from failed to passed. The other 9 failures are identical on both runs and come from the existing local CPU/native-AOT environment. In particular, the existing real-LLM GPT2 cache test fails during engine initialization on both versions; it is not counted as a successful validation.

Pre-commit on all three changed files passed, including ruff check, ruff format, mypy, typos, and the Buildkite test-tethering check:

```bash
uv run --no-project --with pre-commit pre-commit run --files vllm/compilation/caching.py vllm/compilation/backends.py tests/compile/test_aot_compile.py
```

Not run: a Windows server, CUDA execution, a real model AOT roundtrip, or model evaluation. This change affects source decoding and cache identity, not model outputs. No performance claim is made.

## Details

On a non-UTF-8 Windows locale, an unqualified text `open` can decode UTF-8 source into different text or reject it. The AOT source check can then report a source mismatch and recompile, while the sibling JIT path can omit the unreadable file from its hash.

`tokenize.open` is the standard Python source reader: it defaults to UTF-8 and honors an explicit PEP 263 coding cookie. Applying it to both existing readers fixes the root cause without introducing another hash implementation or changing inference behavior. Correcting a previously locale-dependent hash can cause a one-time cache miss after upgrade, which is safer than deriving cache identity from incorrectly decoded text.

This is not a duplicate of #62628. That PR consolidates the JIT/AOT hashing implementations and tolerates unreadable files; it does not fix their source decoding. The changes are complementary. If #62628 lands first, the same decoding change is needed in its consolidated helper.
