# [Kernel] Avoid redundant SM100 blockwise FP8 scale padding

[Upstream PR](https://github.com/vllm-project/vllm/pull/58506) · state: open · merged: False

## Original PR description

## Purpose

The SM100 blockwise FP8 GEMM requires the leading dimension of its
column-major activation scales to be divisible by four for TMA scale-factor
copies.

The current implementation handles a non-aligned `M > 64` by allocating a
temporary padded scale tensor and issuing a `cudaMemcpy2DAsync` before every
GEMM. This is correct and significantly faster than falling back to the
`swapAB` kernel, but the allocation and copy are unnecessary when vLLM owns
the activation quantization step.

This PR makes the vLLM CUTLASS block-FP8 path produce TMA-aligned activation
scales directly during quantization. The GEMM then derives the physical scale
extent from `a_scales.stride(1)` and consumes the aligned tensor without an
additional allocation or copy.

The aligned scale view is backed by an explicitly allocated physical
`[K / group_size, aligned_M]` tensor. This is important because
`empty_strided((M, SF_K), (1, aligned_M))` only allocates through the last
logical element; it does not include the trailing padding after the final
scale column. SM100 TMA may read that complete four-row atom.

The change preserves compatibility with direct custom-op callers:

- TMA-aligned scales with complete physical backing use the zero-allocation,
  zero-copy fast path.
- Valid aligned-stride views without complete tail padding automatically fall
  back to a padded copy instead of being rejected or read out of bounds.
- Packed, non-aligned scales retain the existing temporary-padding fallback.
- The existing `M <= 64` `swapAB` heuristic is unchanged.
- There is no public API change.

The persistent storage overhead is at most three FP32 scale entries per
`K / 128` scale column, while the per-GEMM temporary allocation is removed
from the normal vLLM path.

### Lossless behavior

This is a physical-layout optimization only. It does not change the logical
scale values, FP8 quantization, kernel math, accumulation type, or output
type.

Packed and aligned paths were compared with `torch.equal` for
`M = 13, 64, 65, 66, 67, 125, 511, 1026, 2047`:

| Comparison | Result | Maximum absolute difference |
|---|---:|---:|
| Quantized FP8 activations | Bitwise identical | 0 |
| Logical FP32 scales | Bitwise identical | 0 |
| GEMM-only BF16 output | Bitwise identical | 0 |
| Quantization + GEMM BF16 output | Bitwise identical | 0 |

The separately reported 0.11%-0.15% relative error is the expected error of
the FP8/BF16 result relative to an FP32 dequantized reference. Both the packed
baseline and aligned fast path have the same error and are bitwise identical
to each other.

The compatibility fallback was also compared against the complete-backing
fast path for `M = 13, 65, 66, 67, 1026`, covering both `swapAB` and non-swap
kernels. Every BF16 output was bitwise identical with a maximum absolute
difference of zero.

## Test Plan

1. Rebuild the stable-ABI CUDA extension with the SM100 CUTLASS kernels.
2. Run focused correctness tests for both scale layouts across:
   - the `M = 64/65` dispatch boundary;
   - all non-zero `M % 4` residue classes;
   - tiny, medium, and multi-scale-atom `M` values;
   - a non-128-aligned weight dimension.
3. Compare packed and aligned quantization outputs and GEMM outputs bitwise.
4. Construct exact-size CUDA allocations for aligned-stride scale views and
   verify that incomplete backing storage safely takes the copy fallback.
5. Run Compute Sanitizer on both the incomplete-backing fallback and the
   complete-backing zero-copy path.
6. Benchmark both paths after five warmup iterations:
   - GEMM-only: reuse the output tensor to isolate scale-padding overhead;
   - end-to-end: include activation quantization, full backing allocation,
     storage validation, and GEMM.
7. Run the repository pre-commit hooks on all modified files.

## Test Result

### Correctness

- Stable-ABI SM100 extension build: **PASS**
- Focused CUDA correctness cases: **9/9 PASS**
- Bitwise packed-versus-aligned comparison: **9/9 PASS**
- Exact-size fallback-versus-fast-path comparison: **5/5 PASS**
- Compute Sanitizer on the 532-byte fallback allocation: **0 errors**
- Compute Sanitizer on the 544-byte direct-TMA allocation: **0 errors**
- Pre-commit hooks, including Ruff, clang-format, mypy, and test tethering:
  **PASS**

For `M=65` and two scale columns, an aligned-stride logical tensor requires
only 532 bytes, while a direct TMA read requires 544 bytes of physical
backing. Forcing the 532-byte allocation through the direct path produced six
invalid global reads in Compute Sanitizer. The final implementation detects
this condition and uses the padded-copy fallback; it completes with zero
sanitizer errors and is bitwise identical to the 544-byte fast path.

### Performance

Measured on an NVIDIA L20D. Each value is the arithmetic mean across these
five model GEMM shapes:

- `N=5120, K=4096`
- `N=4096, K=2048`
- `N=512, K=4096`
- `N=4096, K=256`
- `N=4608, K=4096`

The production-equivalent benchmark includes quantization, full aligned
backing allocation, storage validation, and GEMM.

`Speedup = packed baseline wall time / aligned fast-path wall time`; higher is
better. Each value below is the arithmetic mean of the five shapes.

| M | Quantization + GEMM wall-time speedup |
|---:|---:|
| 65 | 1.113x |
| 511 | 1.076x |
| 2,047 | 1.028x |
| 8,191 | 1.018x |
| 63,798 | 1.009x |

The benefit is largest for smaller token counts, where the allocation and copy
are a significant fraction of the GEMM latency. For large compute-bound GEMMs,
the improvement converges toward 1%, while narrow `N` or `K` shapes still show
larger gains.

Selected per-shape end-to-end results:

| M | N | K | Packed wall time | Aligned wall time | Speedup |
|---:|---:|---:|---:|---:|---:|
| 65 | 5,120 | 4,096 | 0.0496 ms | 0.0451 ms | 1.099x |
| 65 | 4,096 | 2,048 | 0.0479 ms | 0.0411 ms | 1.165x |
| 65 | 512 | 4,096 | 0.0483 ms | 0.0435 ms | 1.111x |
| 65 | 4,096 | 256 | 0.0432 ms | 0.0394 ms | 1.096x |
| 63,798 | 5,120 | 4,096 | 1.7296 ms | 1.7222 ms | 1.004x |
| 63,798 | 512 | 4,096 | 0.6518 ms | 0.6376 ms | 1.022x |

No documentation update is required because this change does not alter the
public interface or supported model set.
