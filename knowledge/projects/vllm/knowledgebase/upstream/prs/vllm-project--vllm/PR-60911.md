# [ROCm][Bugfix] Run TheRock's ROCm SDK preload before promoting libtorch_cpu.so

[Upstream PR](https://github.com/vllm-project/vllm/pull/60911) · state: open · merged: False

## Original PR description



## Overview

Fixes a regression introduced by #56190 - on TheRock-based PyTorch wheels, `import vllm` aborts if `LD_LIBRARY_PATH` points to a system ROCm installation:

```text
CommandLine Error: Option 'spirv-expand-step' registered more than once!
```

This PR runs PyTorch's TheRock SDK preload before promoting `libtorch_cpu.so` with `RTLD_GLOBAL`.

cc @mawong-amd (author of #56190)

## Claims
- Restores `import vllm` (and the `vllm` CLI) in the affected environment.
- Preserves #56190's early `libtorch_cpu.so` promotion for GPU profiling.
- Leaves non-TheRock ROCm wheels, CUDA, and CPU behavior unchanged.


## Validation

**Environment:** TheRock ROCm 7.13.0a20260515 wheels, PyTorch 2.11.0+rocm7.13.0a20260515, system ROCm 7.13.0 (`LD_LIBRARY_PATH=/opt/rocm-7.13.0/lib`), Python 3.12, vLLM main `08567505`; re-validated after rebasing onto `1a3a7a8f0`.

**Test command:**

```bash
# Reproduce the crash on unpatched main / verify the fix
# (TheRock torch wheels + a system ROCm at /opt/rocm-7.13.0)
LD_LIBRARY_PATH=/opt/rocm-7.13.0/lib python -c "import vllm, torch"
```

| `vllm/env_override.py` version | Result |
|---|---|
| Before #56190 (`48cb12c1^`) | Pass |
| Main (`08567505`) | **Abort**, exit 134 |
| Main + this PR | **Pass** |

- **End-to-end:** 15 successful `vllm bench throughput` runs on R9700 (gfx1201) with an earlier revision of this fix (same preload, called before the `libtorch_cpu.so` existence check). Without the fix, import aborts.
- **Profiling:** A stand-in library exporting `rocprofiler_configure` confirmed the symbol remains discoverable with preload → promotion → `import torch` ordering.
- **Library loading:** Confirmed no system ROCm libraries were loaded with the fix. The second SDK initialization loaded no additional libraries (`_ALL_CDLLS` remained at 20 entries).
- **Checks:** `pre-commit run` passed (including ruff, mypy).

The mixed-ROCm setup is not available in CI, so the crash was validated manually.

## Details

**Root cause.** TheRock wheels preload ROCm libraries via `torch/_rocm_init.py` during `import torch`. #56190 instead loads `libtorch_cpu.so` first, so its dependencies can resolve to system ROCm libraries through `LD_LIBRARY_PATH`. Mixing system and wheel LLVM libraries triggers duplicate LLVM option registration and aborts the process.

**Fix.** Load `torch/_rocm_init.py` by path and call `initialize()` before the `RTLD_GLOBAL` promotion. This reuses PyTorch's build-specific preload list without importing torch or hard-coding dependencies. On wheels without `_rocm_init.py`, nothing changes. A second initialization during `import torch` is harmless in the tested build because `rocm_sdk` caches preloaded libraries. The public `rocm_sdk.initialize_process()` has no default library list, and a minimal hard-coded list still loaded `libroctracer64` from system ROCm in our test.

The promotion still happens before `import torch`, preserving #56190's one-shot `rocprofiler_configure` discovery behavior. The profiling check used a stand-in because this torch build does not export that symbol.

**Related, not fixed here:** ROCm/rocm-systems#13009 reports the same LLVM abort through a different loading path (`rocprofv3`, without vLLM or `LD_LIBRARY_PATH`).

**Workaround without this PR:** `env -u LD_LIBRARY_PATH vllm ...`
