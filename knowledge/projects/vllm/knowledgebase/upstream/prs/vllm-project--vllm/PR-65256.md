# [Quantization] Keep E8M0 scale bytes when loading into uint8 params

[Upstream PR](https://github.com/vllm-project/vllm/pull/65256) · state: open · merged: False

## Original PR description

## Purpose

Part of #64418 (load plan, item L6).

MXFP4/MXFP8 scale parameters (compressed-tensors and ModelOpt MXFP8, linear and MoE) are `uint8`, and
their loaders end in a plain `copy_`. When the source is `float8_e8m0fnu`, `copy_` converts it by value
(2^(b-127) cast to an integer), which gives wrong bytes. This PR copies a `float8_e8m0fnu` source into a
`uint8` destination as `view(torch.uint8)`, so the parameter holds the checkpoint's bytes. Under the load
plan's view rule (§4) these names then stay direct.

No cold-start change: every MX checkpoint we checked stores its scales as `U8`, and the check leaves every
dtype pair except E8M0 → `uint8` untouched. The E8M0 path is reached only by an `F8_E8M0` checkpoint or by
a weight-transfer sender (RL trainer, direct reload) that types the scales as E8M0.

## Changes

- `view_e8m0_as_uint8(dst, src)` in `vllm/model_executor/utils.py`. It is called at the shared copy
  points:
  - the 6 `copy_` calls in the vLLMParameter load methods (`parameter.py`);
  - the top of `RoutedExperts.weight_loader`;
  - `default_weight_loader`.
- **Sites covered:**
  - CT `W4A4Mxfp4` / `W4A8Mxfp4` / `W8A8Mxfp8` linear and their MoE methods;
  - ModelOpt `KMxfp8Static` 1x32 and `ModelOptMxFp8FusedMoE`.
  - Quark OCP-MX (linear and MoE) and INC MXFP8 MoE use the same copy points, but are not separately
    tested.
- **Not covered:** INC MXFP8 linear, INC MXFP4 linear and FP-Quant linear. These go through the v1
  `linear.py` loaders, which copy elsewhere. Left for a follow-up.
- **Cost:** two dtype comparisons per `copy_`, no allocation. Non-E8M0 sources take the unchanged path.
- **Alternative considered:** wrapping each site's scale loader. That changes the loader's identity and
  signature, which EPLB placement (`expert_id` in the signature) and NCCL M2N (`__func__` match) rely on.
- **Test:** `tests/quantization/test_e8m0_scale_loader.py`, run in the "Quantized MoE" job.

## Test plan

```
pytest -v tests/quantization/test_e8m0_scale_loader.py
```

- Each of the 6 vLLMParameter load methods (`_assert_and_load`, column, row, merged-column, qkv,
  per-tensor shard), at TP=1 and TP=2 rank 1. The TP=2 row case uses a narrowed, non-contiguous source.
- CT W8A8 MXFP8 MoE scales through the real `RoutedExperts.weight_loader`. The test also asserts the
  scale params keep the layer's own loader.
- `default_weight_loader`.
- Every case runs with a `uint8` source and the same bytes as `float8_e8m0fnu`. Every source except the
  small per-tensor shard covers all 256 byte values (including 0x00, 0x7F, 0xFE and 0xFF = NaN).
- No GPU kernels run, but `default_vllm_config` is needed for the MoE layer.

No regression. For each row, the quant method and MoE/GEMM backend were taken from the server log of both arms, and
they match the expected path. "swapped" means B then A.

- **Weights are identical.** All checkpoints store their scales as `U8`, so the new check never fires at cold
  start. A tensor fingerprint after cold start (every registered parameter and buffer, plus off-registry kernel
  tensors) found 0 differing tensors for both the MXFP4 and the 0.6B MXFP8 model. For the 0.6B model, the
  Inductor kernels of the two arms are also identical, apart from cache-path comments, and offline greedy tokens match.
- **GSM8K:** gaps above 1 pt do not follow the arm. On MXFP4, B's 0.8438 in the first swapped pass is an outlier:
  B scored 0.8613 and 0.8597 in its other runs, and the second swapped pass gave 0.8597 for both arms. On MXFP8 30B
  the sign flips with the order. On 0.6B the arms differ by at most one question.
- **Throughput:** the 30B rows are within about ±4%, and the sign flips between orders. The 0.6B model is
  host-bound (about 2.8 ms TPOT) and swings ±5% between runs of the same arm (A: 15732 to 16605, B: 15169 to 16183).
  Its first pass showed B lower in both orders, but the repeat pass did not.
- **KV cache:** on the CuteDSL MXFP8 models, the first arm on a fresh node keeps a larger warmup transient peak
  (2.41 vs 2.1 GiB on MXFP8 30B, 3.02 vs 2.06 GiB on 0.6B). That costs it about 0.4% (30B) or 1% (0.6B) of KV
  tokens. The gap follows run order, not the arm: in the swapped MXFP8 30B pass, B is the arm with 1.584M.
- The MXFP8 30B swapped pass ran as a separate job on a different node (rack1-11, not rack1-03). The MXFP4 second
  swapped pass ran on rack1-16 and the 0.6B repeat on rack1-05.
- No models were skipped. Not covered here: the INC / FP-Quant linear paths, which are out of scope (see Changes),
  and Quark OCP-MX and INC MXFP8 MoE, which use the same copy points but have no checkpoint in this A/B.
