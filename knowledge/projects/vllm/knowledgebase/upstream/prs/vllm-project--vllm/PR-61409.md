# [CI] Run the Clef pooler test on GPU

[Upstream PR](https://github.com/vllm-project/vllm/pull/61409) · state: closed · merged: True

## Original PR description



## Overview

Run `tests/models/multimodal/pooling/test_clef_omni.py` (added in #61064) on the GPU. As a CPU test it broke engine startup for every later test in the multimodal pooling shard.

## Claims

- Fixes `CUDA error: initialization error` at engine startup for the tests after `test_clef_omni.py` in `pytest models/multimodal/pooling -m 'not core_model'` (clip, colmodernvbert, colpali, colqwen3: 3 failed + 22 errors locally).
- Test-only change; no runtime code is touched.

## Validation

Reproducer — the clef test followed by any engine test in one pytest process:

```bash
cd tests
pytest -q models/multimodal/pooling/test_clef_omni.py \
  "models/multimodal/pooling/test_clip.py::test_models[float-openai/clip-vit-base-patch32]"
```

| | Result (GB200) |
|---|---|
| `main` | `1 failed, 1 passed` — EngineCore: `torch.AcceleratorError: CUDA error: initialization error` |
| This PR | `2 passed`; vLLM now logs "We must use the `spawn` multiprocessing start method" |

- `test_clef_omni.py` alone passes repeatedly on GPU with the original tolerances (`atol=1e-5, rtol=1e-4`).
- Full shard `pytest -v -s models/multimodal/pooling -m 'not core_model'` with this change: clip, colmodernvbert, colpali, and all 18 colqwen3 cases pass; no `initialization error` remains. Remaining local failures are unrelated and also fail standalone on `main`: `test_colpali_v2_multimodal_text_query_image_docs` (forced `FLASH_ATTN` rejects the block size on GB200) and three `test_embedding_gemma2.py` unit tests (local transformers lacks `embedding_gemma2`).

## Details

Root cause: the test fed CPU tensors through `PoolingMetadata.build_pooling_cursor` and `JointSchemaPooler`, both of which allocate pinned host memory (`pin_memory=PIN_MEMORY`, `async_tensor_h2d`). Pinning creates a CUDA context in the pytest process without going through torch's lazy init, so `torch.cuda.is_initialized()` stays `False`. `_maybe_force_spawn` therefore keeps `fork`, and the forked EngineCore fails to initialize CUDA. The shard only recovered once a later test (`test_colqwen3_5.py`) initialized CUDA through torch, flipping vLLM to `spawn`.

This test only runs in the GPU "Multimodal Models (Extended Pooling)" step, so running it on `current_platform.device_type` matches the directory and production (`hidden_states.device`), and CUDA is initialized through torch so vLLM correctly picks `spawn`. Alternatives considered: skipping pinning for CPU targets in `build_pooling_cursor` (touches shared runtime code for a test-only issue, and the pooler's `async_tensor_h2d` would still pin), or forcing `spawn` for the whole shard (slower, and hides the cause).

Not a duplicate: no open PR touches `test_clef_omni.py` or this failure.
