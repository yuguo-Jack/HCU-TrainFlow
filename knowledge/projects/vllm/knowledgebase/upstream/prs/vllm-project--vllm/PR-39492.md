## Code Review

This pull request implements a global request limit across multiple API servers using shared memory. It introduces the `--max-unfinished-requests` parameter and updates the `load_aware_call` decorator to reject requests with a 503 error when the limit is reached. Review feedback identifies several critical issues: the shared memory array is not updated during request completion, leading to stale data; a race condition exists in the limit-checking logic; and the shared array should use a lock to ensure consistent reads during summation.

- gemini-code-assist[bot] · comment · 2026-04-10T10:13:10Z · [source](https://github.com/vllm-project/vllm/pull/39492#discussion_r3063590583)

![critical](https://www.gstatic.com/codereviewagent/critical.svg)

The current implementation of multi-server load tracking has a critical flaw: the `shared_unfinished_requests` array is only updated during the increment phase in `load_aware_call`. It is **not** updated when a request completes (in `decrement_server_load` or `listen_for_disconnect`). 

This means that once a worker process increments its slot in the shared array, that value remains stale even after the request finishes, until that same worker receives a *new* request. In a multi-server setup, this will lead to incorrect 503 Service Unavailable errors because the global sum will over-count finished requests as still active. 

You must ensure that `shared_unfinished_requests[server_index]` is updated whenever `server_load_metrics` is decremented.

File: `vllm/entrypoints/utils.py` · line None

![high](https://www.gstatic.com/codereviewagent/high-priority.svg)

There is a race condition here. The shared array is updated with the `server_load_metrics` value *before* it is incremented (which happens at line 154). Additionally, `sum(shared_array)` is called before the current process's intent to take a slot is globally visible. Under high concurrency, multiple API servers could see a `total_unfinished < max_unfinished` and all proceed, exceeding the limit by up to `num_api_servers - 1`.

To improve accuracy, you should calculate the total by summing the other workers' values and adding the current worker's local count, and then update the shared array *after* the local increment.

```suggestion
                # Multi-server: check total using current local count
                server_index = getattr(raw_request.app.state, "server_index", 0)
                total_unfinished = sum(shared_array) - shared_array[server_index] + raw_request.app.state.server_load_metrics
            else:
                # Single server: check local count directly
                total_unfinished = raw_request.app.state.server_load_metrics

            if total_unfinished >= max_unfinished:
                return _make_overloaded_response()

        raw_request.app.state.server_load_metrics += 1
        if max_unfinished is not None and shared_array is not None:
            shared_array[server_index] = raw_request.app.state.server_load_metrics
```

- gemini-code-assist[bot] · comment · 2026-04-10T10:13:10Z · [source](https://github.com/vllm-project/vllm/pull/39492#discussion_r3063590593)

![high](https://www.gstatic.com/codereviewagent/high-priority.svg)

Using `lock=False` for the multiprocessing Array is risky when combined with `sum(shared_unfinished_requests)` in the API servers. While each worker only writes to its own index, the `sum()` operation iterates over the array and is not atomic. This can lead to inconsistent results or torn reads (though less likely for simple integers). 

Given that `num_api_servers` is typically small, the performance overhead of a lock is negligible compared to the benefit of a consistent global count. Consider using `lock=True` (the default) to ensure that the `sum()` operation in `vllm/entrypoints/utils.py` sees a consistent snapshot of the array.

```suggestion
        shared_unfinished_requests = mp_context.Array("i", num_api_servers, lock=True)
```
