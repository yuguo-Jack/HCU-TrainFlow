# [K3] Optimize K3 recover ssm kernel times

[Upstream PR](https://github.com/vllm-project/vllm/pull/52993) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Purpose
PR #51855 added an option to use the ReplaySSM-like recover method.  But the new approach, although improving memory footprint and so occupancy, actually hurt run time.  The approach should be faster, but it is simple triton vs highly optimized non-triton.  Here we make some small tweaks to improve the new output-only verify kernel and the kda and convolution end-of-step commit kernels.

## Test Plan
No new tests.  This just changes kernel internals and reorders two kernels so are covered by existing tests.  We also wrote some one-off checkers that, on fake input, found the output within expected numerical differences (due to changes in associativity) from the old kernels.

@benchislett has run e2e tests.

## Test Result
@benchislett to add correctness results.
On perf, small speed improvements, about half a millisecond per step on batches 1,8,32,and 3ms on batch 128.

---
We make a few simple changes that result in a substantial speedup.
### For commit:
The biggest is that we change the KDA recover from a backward recurrence to a forward recurrence, which is the bulk of the speedup.  This also lets us save register state when operating in ALIGN_MODE (for prefix caching).

We reorder the computation to go plan -> kda commit -> conv commit, vs the more natural plan -> conv commit -> kda commit, and then add PDL between kda and conv.  This lets us overlap kda with conv, especially as while they both depend on plan, neither depends on the other for inputs and they have separate outputs. And as kda blocks are longer-tailed the re-reordering is beneficial.  However, because commit does not run with cuda graphs, the PDL could hurt more in host overhead than it helps, so we do not enable it.

Lastly, for both kernels we retune num-warps and the number of output elements each handles.  ALIGNED_MODE on and off want slightly different values.  PDL does not impact the preferred values.

To guide optimization we wrote a microbenchmark (not submitted) and optimized for B300, matching the original PRs experiment.  We can only match the original PR numbers if we assume that the original PR was actually run with the kernels in unaligned mode.  Our microbenchmark assumes TP=8, times the span from plan start to end of the second of conv or kda commit, simulates cold and hot L2 cache inputs, and runs with a cuda graph and CUPTI timing.  Although commit does not run under a cuda graph, using one is the best way to get consistent, low-noise timings.

For ease of experimentation we had all requests uniform in terms of # accepted (using 5 below, slightly higher than the 4.2 average in the e2e nsys measurements in the original PR), and also uniform in bondary behavior.   We observed runtime affine in # accepted, as expected (not shown).  We ran in either unaligned, aligned with no boundary crossed, or aligned with boundary crossed at the second token.  The latter case would never happen at larger batches, we would expect a mix of aligned and unaligned, but it shows the costs.  

We get about 2x speedup across batches and align modes, more at the more production relevant aligned but no boundary.  

Note due to how vLLM groups KDA layers that share block tables, the commit kernels (plan, commit kda, compact conv, etc.) are launched on 5 or 4 layers at a time, not all 69 as you'd hope.  I have a follow-on commit that groups them together which helps time further, especially as nsys shows the lack of cuda graphs causes substantial gaps at smaller batches.

Results below, times are plan -> kda commit -> conv compact span.  Small batch, with only 5 layers per invocation, is largely launch bound and so not much improvement is possible, and even larger batches there is not that much work.  You can see more than 2x speedup at larger batches.   Experimenting with the kernels at 69 layers at a time, we found grouping would improve total time for all layers by 3x for batch 1, 1.2x at batch 32, and 1.05x at batch 256 (not shown).

### For verify:
Small changes here but surprisingly worth a lot.  We had a similar microbenchmark as above but for verify.  PDL surprisingly hurts us, so we report only the kernel time, not the span, although we ran and timed the conv1d -> verify span.

We hoisted dt_bias out of the loop, which resulted in enough code gen change to be worth a win.  Then we retuned the value-slice and num_warp params.  We found value-slice should vary with batch size, which is typical as smaller value slices are less efficient but better saturate the machine if there isn't enough work.  And that num-warps should be 1 everywhere.  Also added some cache hints as state and V are not shared across blocks (value slicing) but everything else is. Surprises:  Passing gate lower bound does change the results a little.  As noted above, PDL does not help.  A tiny bit in some places but regresses enough others that I left it off, vs making it a heuristic.  I also spent a while trying to get a good result with a full chunk/prefill-style UT transform, in Triton, having had good results with that for Mamba-2 layers.  Whether due to the per-channel decay (unlikely) or the triangular inverse (likely), I found many bad ways to write it, and with a lot of work I got a version that (for T=8) only tied the recurrence above.  I expected big wins, but Triton limitations make it quite challenging.  I'm sure in CuTe it'd be very fast.  As is, it would have the cost and benefit that the runtime would be independent of T.  But as it is much more complicated, and as T=8 is probably more of an upper than lower bound for draft_length + 1, better to stick with the recurrence.
