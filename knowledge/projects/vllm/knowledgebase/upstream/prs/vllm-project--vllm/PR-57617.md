# [Perf][GLM-5.3-Flash] Batch paired KDA gate projections (f_b_proj/g_b_proj) into one bmm

[Upstream PR](https://github.com/vllm-project/vllm/pull/57617) · state: open · merged: False

## Original PR description

## What

`f_b_proj` and `g_b_proj` in the GLM-5.3-Flash KDA layer are two same-shape
BF16 GEMMs (`[M, 128] x [128, 1024]` per rank at TP8) applied to adjacent
`head_dim`-wide shards of the merged `in_proj_qkvbfg_a` output. Run them as
one batched GEMM:

- the paired weight is stacked in `process_weights_after_loading`, which runs
  on every load/refit — the stack cannot go stale and no allocation happens
  inside the captured forward;
- inputs are read in place via `as_strided` on the existing projection
  buffer — no copies, no layout change;
- non-BF16 weights keep the two-Linear path.

## Historical benchmarks (H20, BF16, CUDA graph replay)

Paired f_b+g_b per KDA layer per step: 5.4 -> 4.4 us for M=1..64
(-17% to -22%, decode and spec-verify shapes); no regression at large M
(within 1% at M=8192). Numerics: bit-identical to the two-Linear path
(max_abs_diff = 0, M=1..256).

## Historical GPU validation

  `test_kda_paired_projection.py`: bit-identical vs the two Linears
  (M=1/5/64/256), paired weight rebuilt on re-run of
  `process_weights_after_loading`, disabled for non-BF16 weights.
- Greedy e2e smoke (12 prompts x 256 tokens, temp=0, spec decode on):
  coherent outputs.

Related: #56298 fixes the stale lazy cache for the merged conv weight — this
change builds its paired weight in the post-load hook instead of caching it
in forward. #57318 speeds up a GDN projection with FlashInfer; different op.
