# [Bugfix] Fall back from DeepGEMM and FlashInfer sampling when nvcc is missing

[Upstream PR](https://github.com/vllm-project/vllm/pull/60514) · state: open · merged: False

## Original PR description

## Overview

Fixes #60261. On a host with no CUDA toolkit, vLLM picks DeepGEMM for block-FP8 linear layers. DeepGEMM's JIT then asserts in `process_weights_after_loading`. With this PR, `is_deep_gemm_supported()` checks for the nvcc that DeepGEMM's JIT will use, and the FlashInfer top-k/top-p sampler checks `has_flashinfer()`. Both now fall back instead of crashing.

## Claims

- Block-FP8 models load on a host without a CUDA toolkit. vLLM selects `CutlassFp8BlockScaledMMKernel` and logs one warning that says why DeepGEMM is off.
- When `has_flashinfer()` is False, the FlashInfer top-k/top-p sampler is not used. vLLM falls back to native sampling. If `VLLM_USE_FLASHINFER_SAMPLER=1` is set, it raises the existing `RuntimeError`.
- Hosts with a CUDA toolkit still use DeepGEMM and the FlashInfer sampler.

## Validation

Hardware: 1 × NVIDIA GeForce RTX 5080 (SM120). The issue reports an RTX PRO 4000 Blackwell, which is also SM120. Software: vLLM `0.31.1rc1.dev23+g43b4aaea3` (commit `43b4aaea3e40e20ef53ce2bfecfa1b72060bf2b5`), editable install.

Reproducer (`reproduce.py`):

```python
from vllm import LLM
LLM("Qwen/Qwen3-0.6B-FP8", max_model_len=2048)
print("LLM loaded successfully")
```

It is run with the CUDA toolkit hidden: `CUDA_HOME` points to a path that does not exist, and there is no nvcc on `PATH`.

```bash
CUDA_HOME=/nonexistent_cuda_home_9x7z \
JIT_NVCC_COMPILER=/nonexistent_nvcc_9x7z \
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin \
VLLM_ENGINE_READY_TIMEOUT_S=3600 \
.venv/bin/python -P reproduce.py
```

In the issue, `CUDA_HOME` is not set. Here it is set to a bad path, because DeepJIT does not look past a `CUDA_HOME` that is set, so the bad path also blocks the `/usr/local/cuda` fallback. Both cases fail the same assertion at the same line. The crash also reproduced in the `vllm/vllm-openai:nightly` image at the same commit.

## Details

**Root cause.** DeepGEMM has no prebuilt kernels. Every op (`set_pdl`, `transform_sf_into_required_layout`, `fp8_gemm_nt`) goes through DeepJIT. On first use, DeepJIT calls `deep_jit::CUDA::find_cuda_toolkit()`, which asserts that a CUDA home exists and that its nvcc is executable. `is_deep_gemm_supported()` checked only three things: the arch, `VLLM_USE_DEEP_GEMM`, and `has_deep_gemm()`, which only checks that the module imports. So DeepGEMM was picked over CUTLASS on hosts where it cannot run. The "Failed to set DeepGEMM PDL" warning is the same assertion, hit earlier in `_apply_pdl()` and caught there. Replacing the layout transform would not help, because `fp8_gemm_nt` fails the same way without a toolkit. The crash would only move to the first forward pass.

**DeepGEMM change.** The new `_deep_gemm_nvcc_path()` follows `find_cuda_toolkit()` at the pinned DeepJIT commit `3732a3b9`, the submodule of the DeepGEMM fork `1e1842a8` in `cmake/external_projects/deepgemm.cmake`:

- The CUDA home is `CUDA_HOME`, else `CUDA_PATH`, else two levels above `which nvcc`, else `/usr/local/cuda`. It must exist.
- nvcc is `DG_JIT_NVCC_COMPILER`. If that is not set, it is `DJ_JIT_NVCC_COMPILER`. If that is empty or not set, it is `<home>/bin/nvcc`. It must be executable.

This is the same approach `has_flashinfer()` already uses for FlashInfer (commit `1fde8ff7d`, #58360). The change adds about 40 lines of non-test code.

**Sampler change.** A second defect sat behind the first one. With only the DeepGEMM change, the reproducer got past weight loading and CUDA graph capture. It then died in sampler warmup when FlashInfer tried to JIT-build its sampling module (`FileNotFoundError: [Errno 2] No such file or directory: 'ninja'`). `flashinfer_sampler_supported()` is the only FlashInfer user that never calls `has_flashinfer()`. This failure is not caused by the reproducer removing `ninja` from `PATH`. With `ninja` back on `PATH` and no nvcc, FlashInfer sampling still fails with a `RuntimeError` (`Could not find nvcc and default cuda_home='/usr/local/cuda' doesn't exist`). `flashinfer-cubin` is not on PyPI (see `requirements/cuda.txt`), so a plain `pip install vllm` without nvcc hits this too. The sampler change could go in its own PR if you prefer, but the reproducer does not pass without it.

**Tests.** The new `tests/utils_/test_deep_gemm_utils.py` covers the toolkit search. Buildkite already runs it through `pytest -v -s utils_`. The new `test_flashinfer_sampler_fallback_when_flashinfer_disabled` covers the sampler gate. It only needs CUDA, so it also runs on the 16-SM `v1/sample` lane.

**Needs maintainer attention.**

- An existing test, `test_flashinfer_sampler_fallback_when_jit_cannot_target_gpu`, expects the error `SM 12.x requires CUDA >= 12.9`. On a GPU host where `has_flashinfer()` is False, the new gate runs first and the error is now "FlashInfer kernels are disabled", so the test fails there. It passes when a toolkit is present, as on CI. Its skip helper `_flashinfer_topk_topp_supported()` says it mirrors the sampler gate, but it no longer does. The likely follow-up is to add `has_flashinfer()` to that helper. I did not change existing tests.

**Limitations.**

- The check only tests that nvcc exists. DeepJIT also asserts that nvcc is CUDA 12.9 or newer. A host with CUDA 12.4–12.8, or with no host compiler, still crashes as before. Covering that would need a subprocess call at kernel selection time.
- Some DeepGEMM users still check only `has_deep_gemm()`: the sparse attention indexers, `vllm/v1/attention/backends/mla/indexer.py` and `vllm/v1/worker/ubatch_utils.py`. Without a toolkit they can still reach the assertion. They are not on this model's path, and several have no other kernel to fall back to.
- `DeepGemmFp8BlockScaledMMKernel.is_supported()` still gives the reason "Currently, only Hopper and Blackwell GPUs are supported.", and the docstring of `is_deep_gemm_supported()` is unchanged. The new warning gives the real reason.
