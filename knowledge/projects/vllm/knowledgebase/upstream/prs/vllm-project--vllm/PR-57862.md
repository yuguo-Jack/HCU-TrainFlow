# [XPU][UT] Deflake GPT2 score tests with reruns

[Upstream PR](https://github.com/vllm-project/vllm/pull/57862) · state: closed · merged: True

## Original PR description

## Overview

On XPU, `HfRunner.generate_greedy_logprobs_limit()` produce different outputs across repeated runs with identical model inputs. This causes occasional failures for gpt2 hf-vs-vllm test. This PR deflakes it with reruns

## Claims

- The gpt2 hf-vs-vllm score unit test consistently passed on CUDA but occasionally failed on XPU.
- The failure on xpu is caused by indeterministic calculation of `aten.addmm.default`.
- Adding reruns fix the issue.

## Validation

to reproduce:
```
pytest -v -s 'tests/models/language/generation/test_common.py::test_models[False-False-5-32-openai-community/gpt2]'
```

Before this PR, the test was flaky across six runs (passes and failures are random):

```text
3 passed
1 failed at Test1
2 failed at Test7
```

The failures were caused by nondeterministic HF reference generation. For the same input, HF output varied between runs while vLLM output remained stable. eg: 

```text
# run_1
Test1 token_idx=10 hf_token=2099 vllm_token=318

# run_2
Test1 token_idx=10 hf_token=318  vllm_token=318
```

After this PR:
- The ut passed.
- `pre-commit run --all-files`: passes.

> can we narrow down which op (I suppose it's torch op) caused invariance?

Repeated BF16 `HfRunner` inference showed numerical drift in XPU `aten.addmm.default`. In the oneDNN matmul path (see https://github.com/pytorch/pytorch/blob/main/aten/src/ATen/native/mkldnn/xpu/detail/Matmul.cpp#L191-L195), deterministic execution is disabled by default and enabled when the corresponding PyTorch setting is on.

The patch now enables `torch.backends.mkldnn.deterministic = True` only around the XPU HF `generate()` call and restores its previous value afterward. Please take another look. Thanks! @jikunshang
