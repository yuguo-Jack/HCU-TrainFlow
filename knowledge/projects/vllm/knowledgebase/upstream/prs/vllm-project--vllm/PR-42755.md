# [Model][Hardware][AMD][Kernel] Part 2/2 -> Enable e2e QK Norm + RoPE + KV Cache runtime fusion for Qwen3-30B-A3B on ROCM_ATTN

## Original PR description

## Purpose

**Depends on #42749** (Part 1). Please review #42749 first.
This PR currently shows Part 1's diff as well because Part 1 hasn't merged yet. Once #42749 merges, I'll rebase this branch onto `main` and force-push, and the diff will reduce to just the 2 incremental commits in this PR.

This is **Part 2** of a stacked PR series that splits the original
`jhu96/optimize-qwen30b` branch (PR:  https://github.com/vllm-project/vllm/pull/39527) into two reviewable PRs.

- Enable e2e runtime QK Norm + RoPE + KV Cache fusion for Qwen3-30B. At compile time, we swap the aforementioned fusion pattern & fuse with aiter's high-performance HIP kernel `fused_qk_norm_rope_cache_pts_quant_shuffle ` for all decoder layers that satisfy a preset token compile range guarded by `rope_kvcache_fusion_max_token_num`. 
- For ROCM_ATTN, modifications were needed on both the prefill and decode path kernels (prefill Triton, decode Triton 2D for non-power-of-2 block sizes, and decode paged attention ll4 GFX9 variants) so that they can read the value cache in the interleaved mode, which the fused kernel writes in when shuffle=True. The key cache read logic remains untouched, as the fused kernel already writes in the format expected by the prefill and decode paths.
- When shuffle=True, the fused kernel writes K with shape (blocks, heads, dim/x, block_size, x) and V with shape (blocks, heads, block_size/x, dim, x). Decode paths already natively read K in the same format, but they currently hardcode reading from the V cache with an expected shape of (blocks, heads, dims, block_size).

## Test Plan

To test this fusion out, please pass the attached toggle through the pass config under the `--compilation-config` when launching with `vllm serve`:

`'pass_config': {
        'fuse_qk_norm_rope_kvcache': True,
        'rope_kvcache_fusion_max_token_num': 256
}`

For example, something like this:

`VLLM_ROCM_USE_AITER=1 \
vllm serve /path-to-your/Qwen3-30B-A3B \
  --host 0.0.0.0 \
  --port 8080 \
  --attention-backend ROCM_ATTN \
  --no-enable-prefix-caching \
  -O1 \
  --compilation-config '{
    "pass_config": {
      "fuse_qk_norm_rope_kvcache": true,
      "rope_kvcache_fusion_max_token_num": 256
    }
  }`

In addition, one can verify the unit test for this fusion with:
` pytest tests/compile/passes/test_qk_norm_rope_kvcache_fusion.py -v`
`

## Code Review

This pull request implements a new fusion pass, `QkNormRopeKvCacheFusionPass`, designed to combine QK-normalization, RoPE, and KV cache updates into a single AITER kernel on ROCm. The implementation includes support for an interleaved V-cache layout across C++ and Triton attention kernels, along with new IR matchers for RMSNorm to facilitate pattern matching. Feedback identifies a bug in the `chunked_prefill_paged_decode` Triton kernel where `HEAD_SIZE` is used instead of `BLOCK_DMODEL`, and raises a concern about the potential for silent correctness issues if the interleaved V-cache layout is enabled without guaranteed fusion coverage.

Right, this was intentional. When this fusion pass is active, the pass manager checks whether the pass is within the applicable max token range set by `pass_config.rope_kvcache_fusion_max_token_num` so it knows which graphs to substitute with fusion and which to leave out. It's currently set to 256, so anything below or at the pass will fire (decode graphs), and anything above it will not (prefill graphs). The unfused prefill graphs use `do_kv_cache_update`, which, before my change, could not write in interleaved_v layout for the V cache under shuffle. Thus, when this fusion is active, you'd have prefill graphs writing in the normal shuffle, then decode graphs reading in the expected interleaved_v shuffle for V (K was the same throughout), which results in incoherent responses since the KV Cache layouts aren't aligned (KV Cache corruption). To align it, I had to set the interleaved_v_cache() layout for every layer, regardless of whether or not every compiled graph substituted the fusion. If this fusion is active, the prefill graph writes interleaved v, and decode graphs read in interleaved v. Prefill graphs write in the layout decode expects.

For correctness, with the pass disabled but interleaved v layout left on, test_prefix_prefill.py reads the interleaved layout through the Triton prefill and chunked-prefill decode kernels, and `test_paged_attention` in test_attention.py as well; these tests still pass.
