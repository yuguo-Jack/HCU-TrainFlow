# feat: add windowed hidden-state capture for vLLM rollout

[Upstream PR](https://github.com/vllm-project/vllm/pull/57736) · state: open · merged: False

## Original PR description

## Summary

Adds response-window hidden-state capture for rollout training (#56916). Callers select a response range `[start, end)` and receive only those hidden-state rows, with optional aligned raw top-k logprobs.

The window is collected during generation through the AuxOutput Connector, reducing GPU-to-CPU transfers compared with full-response capture. It supports final hidden states and configured speculative auxiliary outputs.

## Implementation

- Python API: `SamplingParams.extra_args["hidden_state_capture"]`; the engine resolves response offsets after tokenization.
- Copies selected rows to pinned CPU memory and delivers them through the existing output-completion event.
- Tracks accepted tokens across speculative rejection and KV preemption; supports DELTA and FINAL_ONLY delivery.
- Validates requests at admission, enforces `max_logprobs` and a configurable capture-memory budget, and reports unavailable capture data per request.

API examples and supported configurations: [documentation](https://github.com/vx120/vllm/blob/windowed-hidden-state-collection/docs/features/speculative_decoding/windowed_hidden_states.md). This PR exposes the Python API.

## Performance

Measured on RTX 5090 32GB GPUs: Qwen3-4B + DSpark block-7, BF16, MRV2, CUDA Graphs, 7 speculative tokens; 512 input/output tokens, batch 4, 8 requests, window `[128,160)`. Results are the median of two paired rounds after warmup, using synthetic repeated-text prompts.

| Configuration | Throughput gain vs full capture¹ | Generation-time overhead vs capture off |
|---|---:|---:|
| TP1 | **6.61%** | **0.10%** |
| TP2 | **15.04%** | **0.32%** |

**D2H volume drops from approximately 15.1 MiB to 0.94 MiB per request (94% reduction).**

¹ Includes CPU delivery and export; both modes export the same 32 rows. Including export, Window/Off elapsed-time overhead is 0.55% on TP1 and 1.97% on TP2.

| Configuration | Capture off (tokens/s) | Full capture (tokens/s) | Window capture (tokens/s) | Window TTFT P95 |
|---|---:|---:|---:|---:|
| TP1 | 2939.17 | 2742.09 | **2923.23** | 115.35 ms |
| TP2 | 3346.09 | 2852.42 | **3281.39** | 106.34 ms |

Throughput includes export. Each entry is the median across measured rounds; the improvement percentages above use paired per-round ratios.

Additional measurements:

- **Unreached window:** zero hidden-state D2H; generation time stays within 0.2% of capture off on both TP1 and TP2.
- **Pinned memory:** approximately 39 KiB active after window settlement; allocator lifetime peaks of 2.23 MiB on TP1 and 2.13 MiB on the TP2 returning rank.
- **EAGLE3 TP1:** a separate one-round smoke benchmark passed correctness and showed 1.40% Window/Full throughput improvement with 0.18% generation-time overhead vs capture off (128 input/output tokens, batch 2, two requests, 32-row window).

> ## 第一性原理：审计所采用的必要契约
> R1. 对 L 个 prompt token，第 j 个生成 token 由 h[L-1+j] 预测。因此 response [a,b) 对应 absolute [L-1+a,L-1+b)。这里返回的是预测该 response token 的 hidden state，不是消耗该 token 后的下一位置状态。RFC #56916 明确规定这一语义。 R2. 一个实际 forward 的第 i 个请求占用 query_start_loc[i:i+2] 指定的行，其绝对起点为该 forward 开始前的 computed token 数。必须先对所有请求推进 row offset，再按各自窗口取交集；不能按采集请求重新紧密编号。 R3. speculative forward 可以产生未被接受的候选 row。GPU 先按窗口复制，scheduler 再按实际交付的 token 区间过滤；同一 mask 必须用于 positions 和 states。 R4. CPU payload 可读必须晚于 D2H 完成，且 graph output 在覆盖前必须完成读取。MRV2 当前在 main stream 排队复制，output-copy stream wait_stream(main_stream) 后记录 event，get_output 同步 event，建立传递的 happens-before。blocking=True/False 不改变这个就绪契约。 R5. 每个请求独立拥有 plan/buffer；窗口完成和请求终止需要清理 worker plan。输出结果不得因为 DELTA coalescing、内部 ID 改写或 FINAL_ONLY 延迟而丢失。 R6. 校验对象必须是实际执行的参数；不支持的组合应明确拒绝或返回说明，不能先校验另一份参数再执行不兼容请求。 R7. copied_bytes/copy_ms 是提交或执行过的复制开销，不应因 row 后来被过滤、重算或没有新 token 而消失。有效 row 数和复制开销是不同指标。 R8. capture 未开启时不应引入无关调度、模型输出或全局等待策略变化；性能优化需要对应 feature-off 和 CPU 开销证据。

> frozen plan 防止同批请求共享计划后被原地重写；replace 是重新绑定 request_id 所需，而不是冗余复制大 tensor。 finished_hidden_capture_req_ids 与 finished_req_ids 生命周期不同：窗口可以在 generation 结束前完成；不能简单合并成只有 finished_req_ids。 query_start_loc 的验证防止 prompt-logprob batch 实际行边界错配；不能用“采集请求每请求一行”的假设替代。 accepted positions/state 同 mask、去重和显式 sparse positions 支持 speculative rejection、短结果与 replay；不要用连续 arange 填补实际缺失 row。 pinned CPU buffer + non_blocking copy 与 output event 传递同步是 Graph buffer reuse 正确性的必要组合；不能只删除 event wait 来换吞吐。 RequestOutput.add 的非空合并保证异步 collector 比消费端更快时早期 DELTA capture 不丢；直接覆盖为 None 会破坏该契约。 HTTP schema 的 dtype/shape 和 Base64 原始 bytes 避免 BF16 经 NumPy 浮点转换而变值。MRV1 同步复制与 MRV2 异步复制的开销作用域不同，copy_ms 不能统一称为纯 GPU copy duration。 空行、括号、许可和注释已逐行列入 ledger；它们不承担独立运行时逻辑，不能把“每一行必要”解释为每个空行都有算法必要性。

[P2] Finalize capture when a stop string ends the request in the frontend

Capture is finalized in the scheduler only when its window completes or the scheduler observes the request stopping. A stop string is detected later in this output processor: it emits a finished response and aborts EngineCore. If generation stops inside the capture window, the scheduler's buffered rows are discarded without `finish()`, including a partial capture that satisfies `min_rows`. The finished response can therefore contain neither a capture nor a skip reason. A CPU output-processor probe confirms the stop-string path returns `finished=True`, both capture fields unset, and the request in `reqs_to_abort`.

Please coordinate capture finalization with frontend stop handling, or explicitly reject capture with stop strings until that combination is supported. Add a regression test that stops inside the window after meeting `min_rows`, and distinguish it from EOS/max-token termination.
