# [ROCm][Perf] AITER FlyDSL kernels for the QSA indexer and sparse GQA

[Upstream PR](https://github.com/vllm-project/vllm/pull/59437) · state: open · merged: False

## Original PR description

## Purpose

vLLM hook for [ROCm/AITER#5996](https://github.com/ROCm/aiter/pull/5996) (draft, head `d8713662d1` or later): the FlyDSL QSA K1 indexer and K2 sparse GQA. Both kernels read vLLM's strided per-layer cache views in place (K2 since `d10d02a`, K1 since `8deab1a`), and `qsa_k1_selection_serves` (from `663bd6f`) rejects token budgets outside K1's baked contract. Keep this PR as a draft until #5996 is in an AITER release that vLLM's ROCm image pins.

On ROCm, Qwen4Exp QSA runs three Triton/HIP stages: paged MQA scoring over the compressed indexer cache, HIP top-k, and Triton sparse paged GQA. ROCm/aiter#5996 implements the scoring+top-k half (K1) and the sparse GQA (K2) in FlyDSL.

With `--attention-config.qwen4_exp_qsa_backend flydsl`:

- `QSAIndexer._select` calls `flydsl_select_paged_tokens`. K1 writes the compressed block ids, then the existing Triton `expand_qsa_block_indices_cuda` builds the token indices. The output is the same `[tokens, 2051]` buffer as before, so MTP's `skip_topk` reuse is unaffected. Rows are chunked by the same fp32 score-workspace cap as the Triton path.
- `Qwen4ExpQSAFlashAttentionImpl.forward_qsa` calls `flydsl_sparse_paged_attention`, which runs K2 directly on the K|V cache views into the existing output.
- Anything a kernel cannot serve (the kernel's own `*_serves` checks, K1's token budget, a strided output) logs once and stays on Triton. If the option is set but AITER has no FlyDSL QSA module, startup fails rather than silently falling back.
- The kernels are called directly rather than through `aiter.ops.flydsl.qsa_layer`, because the indexer and attention run at different points in the layer (top-k reuse across MTP steps, cache update in between). #5996 now admits the TP2/TP4/TP8 shards to `auto`, so the shape no longer forces this.

The option defaults to `triton` (FlyDSL stays opt-in): at TP2 the FlyDSL path is currently slower than the Triton path in every measured cell (below).

The one positive repeat at 8k c4 is a slow flag-off cell (385 tok/s against 462–470 in the other three), not a FlyDSL win. The loss grows with concurrency and context, and its TPOT is the same in every repeat, so it is the kernels, not the node.

```bash
# plus the checkpoint card's ROCm environment and flags, identical in both arms
vllm serve amd/Qwen3.8-Flash-Next-Quark-MXFP4 --tensor-parallel-size 2 \
  --attention-config.qwen4_exp_qsa_backend flydsl \
  --max-model-len 262144 --max-num-seqs 256 --no-enable-prefix-caching --trust-remote-code
vllm bench serve --model amd/Qwen3.8-Flash-Next-Quark-MXFP4 --dataset-name random \
  --random-input-len 8192 --random-output-len 1024 --random-range-ratio 1.0 \
  --max-concurrency 64 --num-prompts 128
```
