# [Model] Dory: opt-in FP4 tensor-core MLP prefill for W4A16 NVFP4 checkpoints

[Upstream PR](https://github.com/vllm-project/vllm/pull/63197) · state: closed · merged: False

## Original PR description


> Stacked on #60149 ([Model] Add Dory support, still open): this branch is based on its head, so the diff includes #60149 until it lands; the change of this PR is the last commit. Tracking issue: #63152.

## Overview

W4A16 NVFP4 checkpoints run every linear through Marlin (BF16 activations x FP4 weights). That is at the bandwidth roofline for decode but BF16-compute bound for prefill. This PR adds an **opt-in** path for Dory: with `--hf-overrides '{"fp4_prefill_min_tokens": 128}'`, steps of at least 128 tokens run the MLP linears (`gate_up_proj`, `down_proj`) as NVFP4 x NVFP4 CUTLASS GEMMs (`cutlass_scaled_fp4_mm`), with activations quantized to NVFP4 on the fly. Smaller steps (decode) keep the Marlin path bit for bit. Off by default.

## Claims

- 1,500-token prefill on **GB10 (DGX Spark): 1.49-1.50x faster** at 1, 2 and 4 loops; on B100 1.05-1.27x.
- Steps below the threshold are unchanged bit for bit (unit test), and the option is ignored with a warning on GPUs without FP4 tensor cores (H100) and on non-W4A16 checkpoints.
- **Numerics change for prefill-sized steps** (FP4 activation rounding in the MLP): ARC-Easy 71.9 → 70.1, ARC-Challenge 70.4 → 65.2 at 2 loops. This is why it is opt-in.

## Validation

**Speed** (Dory1.0-4B NVFP4 W4A16, offline `LLM.generate`, one 1,500-token random prompt, `max_tokens=1`, 3 warmups, median of 10; run-to-run spread within ±1.5%):

| GPU | loops | Marlin (ms) | FP4 MLP prefill (ms) | speedup |
|---|---|---|---|---|
| GB10 | 1 | 187.8 | 125.1 | 1.50x |
| GB10 | 2 | 284.1 | 190.3 | 1.49x |
| GB10 | 4 | 481.8 | 321.3 | 1.50x |
| B100 | 1 | 33.1 | 31.5 | 1.05x |
| B100 | 2 | 51.1 | 46.6 | 1.10x |
| B100 | 4 | 97.6 | 76.8 | 1.27x |

**Quality** (GB10, 2 loops, zero-shot multiple choice scored from the first-token logprobs of the answer letter, full ARC test sets: 2,376 Easy + 1,172 Challenge):

| | ARC-Easy | ARC-Challenge | first-token top-1 agreement vs Marlin | mean \|Δ logprob(top-1)\| vs Marlin |
|---|---|---|---|---|
| BF16 checkpoint (reference) | 77.0 | 73.4 | | |
| NVFP4, Marlin (default) | 71.9 | 70.4 | | |
| NVFP4, FP4 MLP prefill | 70.1 | 65.2 | 93.7% (3,323 / 3,548) | 0.140 |

For scale, BF16 → NVFP4 Marlin itself has 93.6% top-1 agreement and a mean |Δ logprob| of 0.155 on the same prompts. Repeating each arm gave identical results (deterministic). Running only `gate_up_proj` in FP4 recovers part of the loss (ARC 300+300 subset: 70.4 / 67.3) at a smaller gain (214 vs 284 ms); FP4 activations in the attention linears cost noticeably more accuracy, so they stay on Marlin.

**Tests**: `tests/models/test_dory_fp4_prefill.py`: for both MLP shapes and M in {1, 8, 127, 128, 512, 1536}, M < 128 must equal Marlin bit for bit, and M >= 128 must match Marlin on unit-norm inputs (cosine > 0.99, relative error < 0.1). 12 passed on GB10 and B100; skipped on H100. Added as a B200 step in `models_basic.yaml` (needs FP4 tensor cores). `pre-commit` passes.

**No-op elsewhere**: on H100 the engine logs `Dory fp4_prefill_min_tokens needs FP4 tensor cores (CUTLASS NVFP4 GEMM); ignored on this GPU.` and every linear stays on the regular NVFP4 kernel (`_fp4_prefill_min_tokens` returns 0, so no layer is registered for the FP4 path).

## Details

- **Static activation scale.** Every Dory MLP input is unit-norm (`gate_up_proj` reads the `justnorm`'d residual stream, `down_proj` a `justnorm`'d SwiGLU output), so `|x_i| <= 1`; the global activation scale maps 1.125 (headroom for BF16 rounding) to the FP4 range and needs no calibration. The block scales cover each 16-element block. The layer-0 MLP reads the raw embeddings (no bound) and stays on Marlin.
- **Weights.** The serialized FP4 weights are already retained via the existing `_retain_weight_for_gather` hook; their block scales are swizzled once on first use. Memory cost: ~1.1 GB for Dory1.0-4B (the FP4 MLP weights next to the Marlin copy).
- **Dispatch.** `vllm::dory_fp4_linear` is a custom op that picks the path from the token count at runtime, so FULL CUDA graphs for decode sizes (< 128) are unaffected. Decode steps that reach 128 tokens after padding also take the FP4 path.
- **Scope.** Dory only, because the unit-norm bound is what makes a static scale safe. A general W4A16 → W4A4 prefill switch would need calibrated or dynamic activation scales.
