# [Bugfix][CPU] Don't crash DP x TP when a DP rank's assigned NUMA nodes don't exist

[Upstream PR](https://github.com/vllm-project/vllm/pull/64499) · state: open · merged: False

## Original PR description

## Overview

On a 2-NUMA CPU host, DP=2 × TP=2 with explicit binds crashes at start-up: DP rank 1's workers raise `IndexError` in `CPUWorker.__init__`. This PR falls back to the visible NUMA nodes, with a warning, when none of a DP rank's assigned nodes exists on the host. Each worker then binds memory to the node of its first CPU, as on v0.32.0. Fixes #64497 

## Claims

- DP=2 × TP=2 with explicit binds (`VLLM_CPU_OMP_THREADS_BIND="36-41|42-47|84-89|90-95"`) on a 2-NUMA host starts and serves. On main it fails with `IndexError: list index out of range`.
- DP=2 × TP=1 with auto binding is unchanged: DP rank 0 binds to node 0 and DP rank 1 to node 1.
- DP=2 × TP=2 with auto binding is unchanged: it still stops with the existing `Not enough allowed NUMA nodes` assertion. The fallback lives only in the worker; `get_visible_memory_node()`, which auto binding uses, is untouched.
- On DP rank 1, `CpuPlatform.get_current_memory_usage()` reports the visible nodes' usage instead of 0 bytes.

## Details

**Root cause.**
- `get_physical_gpu_ids_for_local_dp_rank()` gives each DP rank a block of `world_size` device ids, numbered as for GPUs: DP rank 1 of DP=2 × TP=2 gets `[2, 3]`.
- `CPUWorker` reads those ids as NUMA node ids: it calls `get_visible_memory_node(parallel_config.assigned_physical_gpu_ids)`.
- On a 2-node host, nodes 2 and 3 don't exist, so the filtered list is `[]` and the fallback `allowed_memory_nodes[0]` raises.
- `CpuPlatform.get_current_memory_usage()` reads the same ids, so on DP rank 1 it reports 0 bytes; it now uses the same fallback.

**Why the fallback is narrow.** The fallback is a new `get_worker_memory_nodes()`, used by `CPUWorker` and `CpuPlatform.get_current_memory_usage()`; `get_visible_memory_node()` is unchanged. Auto binding (`OMPProcessManager`) also calls `get_visible_memory_node()`. Returning all nodes there would let two DP engines auto-bind to the same cores without an error, so keeping it unchanged keeps the existing assertion.

**Placement after the fallback.** Each worker binds memory to the node of its first allowed CPU. With libgomp (torch's default OpenMP runtime), the worker is already pinned to its bind list at this point, so DP rank 1's workers bind to node 1, as shown above.

**Out of scope.** The device-id numbering is GPU-centric. A follow-up could compute per-DP-rank NUMA node sets on CPU directly, or derive each worker's node from its own bind list.

**Not a duplicate.** No open issue or PR reports this crash. The closest open PR, #47336, addresses DP engine processes sharing one NUMA node, which is a different bug. The closed #38055 fixed a different `IndexError` in `CPUWorker`: a global rank index on multi-node layouts.
