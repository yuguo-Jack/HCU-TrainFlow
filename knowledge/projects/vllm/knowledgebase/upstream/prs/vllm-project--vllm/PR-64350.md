# [MRV2] Stage-local eager DBO with pipeline parallelism

[Upstream PR](https://github.com/vllm-project/vllm/pull/64350) · state: open · merged: False

## Original PR description

## Overview

Draft for **stage-local eager DBO with pipeline parallelism in MRV2**, tracked in #64334.

**Work in progress, opened to reserve and discuss this scope. Only static review and CPU unit tests are complete. This is not ready to merge.** CUDA graph support will be a separate follow-up.

## Claims

- Allow PP+DBO in MRV2 only for explicit `--enable-dbo`, NIXL EP, DP>1 with expert parallelism, TP=1, synchronous scheduling and no CUDA graphs. Every other PP+DBO combination is still rejected.
- Reuse the existing intermediate-tensor slicing/merging, per-stage DP agreement, PP transport ownership and last-stage sampling.
- No claim of distributed model correctness, throughput improvement or TPOT reduction.

## Details

The production change is **+17/-4** in `VllmConfig._get_dbo_unsupported_features`. It replaces the unconditional PP rejection with one condition and reuses `ParallelConfig.use_batched_dp_moe` for the EP and DP>1 requirement. It checks `cudagraph_mode == NONE` rather than `enforce_eager`, because CUDA graphs are the actual limitation. The platform is left to the existing DBO all2all-backend check.

The existing `UBatchRunner` already slices each `IntermediateTensors` key and merges outputs before the worker sends a complete batch to the next stage. The new CPU test checks that round trip through `slice_model_inputs` and `merge_ubatch_outputs`. The draft does not introduce a new PP transport, scheduling algorithm or cross-stage microbatch protocol.

```mermaid
flowchart LR
    A[Complete batch at PP stage 0] --> B[Two local DBO microbatches]
    B --> C[Merge intermediate tensors]
    C -->|Existing full-batch PP transfer| D[PP stage 1 local DBO]
    D --> E[Merge and sample original rank-local batch]
```

Async scheduling resolves to enabled by default, so users must pass `--no-async-scheduling`; the docs state this.

Before readiness:
- [ ] Qualify a real PP2 × DP2 × TP1 model and confirm both microbatch IDs execute on all four workers.
- [ ] Validate imbalance, idle-rank recovery, request-slot reuse and complete-batch PP boundaries.
- [ ] Compare outputs/logprobs and document the supported model/backend scope.
- [ ] Measure the relevant end-to-end costs before making any performance claim.

This is main-based and does not stack the separate staging/FA3/metadata-fusion/abort PRs. Related work was checked: #50738 explicitly excludes PP; #63483 adds pure-TP DBO and retains the PP restriction; #53948 handles the PP receive queue; #63373 removes MRV1. No open implementation of this same scoped eager PP+DBO feature was found in the current search.
