# [ROCm][Perf][MiniMax-M3.1] Fuse the FFN-side MXFP8 activation quant into the post-attention norm and swiglu

[Upstream PR](https://github.com/vllm-project/vllm/pull/65478) · state: open · merged: False

## Original PR description


## Purpose

On ROCm, MiniMax-M3.1 decode runs one separate Triton `_kernel` launch (the MXFP8 activation quant, `_mxfp8_quant_triton_kernel`) in front of several MXFP8 linears. #63637 fused it into `input_layernorm` for `qkv_proj`. Two more per-layer launches remain on the FFN side:

1. post-attention add+RMSNorm -> quant -> `gate_up_proj` (dense MLP, or the MoE shared expert), every layer, every N.
2. swiglu -> quant -> `down_proj`, every layer when the GEMM does not already quantize in-kernel (decode batches with more than 2 requests, i.e. M = 8N > 16). Dense layers skip the separate quant in the same way when the in-GEMM quant applies.

This PR (two commits) turns both into epilogues of kernels that already run:

- **Commit 1**: `_gemma_fused_add_rmsnorm_kernel` gets an `ALSO_BF16` mode: it writes the MXFP8 values/scales and the bf16 normed rows (the router and routed experts need bf16). New `allreduce_gemma_rms_norm_mxfp8` (all-reduce + that norm) returns `None` when a fused all-reduce+norm kernel applies, so that path is untouched. The MoE passes the quantized rows to the shared expert through `set_prequant` (checked by data pointer + shape, consumed once).
- **Commit 2**: the dense MLP / shared expert call the existing `swiglu_oai_quantize_mxfp8` (fp32 swiglu + quant in one pass) and give `down_proj` a `QuantizedActivation`; skipped where the GEMM already quantizes in-kernel (M <= 16, K <= 1024).

Related: #63637 (same idea for input_layernorm -> qkv_proj); the fp32 swiglu kernel is from the MiniMax-M3 AMD ops. Not covered by any open PR that I could find.

## What changes per decode step (main model, 60 layers)

Trace evidence (torch profiler, TP4, DSpark 7-token drafts so M = 8 x requests; rank-0 profile windows at N=1, 2, 4 and 16): `_kernel.kd` per step = 145 at N=1 and N=2, 202 at N>=4 (profiled durations ~1.6x inflated).

| Launch removed | Layers | N=1 (M=8) | N=2 (M=16) | N>=3 (M>=24) |
|---|---|---|---|---|
| post-attn quant for gate_up (commit 1) | 60 | no (aiter fused AR+norm runs) | yes | yes |
| swiglu quant for down_proj (commit 2), shared expert | 57 | no (in-GEMM quant) | no (in-GEMM quant) | yes |
| swiglu quant for down_proj (commit 2), dense layers | 3 | yes | yes | yes |

Still unfused after this PR: the `o_proj` input quant (K=2048; in-GEMM quant did not win above M=16 in my sweep), layer 0's input norm, and the DSpark draft layers.

def graph_time(fn, iters=200, reps=20):
    fn(); torch.cuda.synchronize()
    g = torch.cuda.CUDAGraph()
    with torch.cuda.graph(g):

    ts.sort(); return ts[len(ts)//2]

## Limitations

- No gain at N=1 for the post-attention fusion (the aiter fused all-reduce+norm kernel has no quant output); a quant-emitting variant of that kernel could plug into `allreduce_gemma_rms_norm_mxfp8`.
- Relies on the `RocmDotScaledMxfp8LinearKernel` consuming row-major E8M0 scales (same condition as #63637).
- Dispatch assumption: the MoE runner hands the shared expert the layer's own input tensor; otherwise the hand-off is ignored and the linear quantizes itself (correct, just not fused).

Context: we've been working the MXFP8 *activation scheme* invariant on the

## What I checked and found safe

- **Norm epilogue is bit-identical to the unfused path.** The new `ALSO_BF16`
  branch in `gemma_rmsnorm.py` stores the normed row *before* the `QUANT_MXFP8`
  block and still re-casts through `out.to(x_ptr.dtype.element_ty)`, so the FP8
  values and E8M0 scales are computed from the same input-dtype-rounded row as
  `norm -> mxfp8_e4m3_quantize`. The bitwise-eq test covers bf16/fp16 and N in
  {2048, 6144}.
- **Scale layout / scheme contract matches the consumer.** The fused ops emit
  row-major `[M, N//32]` E8M0 scales (not swizzled) under `kMxfp8Dynamic`, which
  is exactly what `RocmDotScaledMxfp8LinearKernel` consumes (row-major, not
  swizzled). The gate `_can_fuse_input_norm_mxfp8` requires that kernel +
  `supports_quantized_input(...)`, so a FlashInfer-style consumer that wants
  swizzled scales under the same key can never receive these — the same
  layout-vs-key distinction matters here and it's handled correctly.
- **`down_proj` in-GEMM-quant carve-out** reproduces the kernel's own decision
  (`0 < M <= _FUSED_QUANT_MAX_M and _select_fused_quant_cfg(...) is not None`),
  so no double-quant / no missed fusion; the test pins `in_gemm == (m<=16 and
  k<=1024)`.
- **Prequant hand-off is fail-safe:** `forward` only substitutes when the
  incoming `x` is a tensor with matching `data_ptr()` and `shape`, consumes it
  once, else falls back to self-quantization. DP/EP paths fall back cleanly.
- **Batch-invariant mode is fully disabled** (`_can_fuse_input_norm_mxfp8`
  returns False under `VLLM_BATCH_INVARIANT`), so the `down_proj` path not
  re-checking it is harmless.
- **`None`-deferral keeps the fused-AR / N=1 path byte-for-byte unchanged.**
- **Perf claims appropriately scoped** (per-launch savings + exact launch-count
  reduction are the credible core; e2e correctly not claimed).

## Questions (non-blocking)

1. The fused swiglu path is numerically *different* (not bit-identical) by
   design — it quantizes the fp32 activation directly and skips the bf16
   round-trip the unfused chain does (~1.9-2.4% of E4M3 bytes differ, and your
   test only bounds it as *at least as close* to the fp32 ref). The op documents
   this, but the substitution at the `MiniMaxM3MLP.forward` call site is silent —
   a one-line comment there would save the next reader the trip.
2. The 6 failing kernel tests (`moe_align_block_size` missing) reproduce on the
   base commit too, i.e. a test-machine extension gap, not a regression — agreed,
   but worth confirming they pass on a real gfx950 CI image before merge.
3. `return_normed=self.is_moe_layer`: confirming the dense path has no consumer
   of the post-attn normed output other than `gate_up_proj` (which takes MXFP8
   directly), so discarding `normed` for dense is safe.
