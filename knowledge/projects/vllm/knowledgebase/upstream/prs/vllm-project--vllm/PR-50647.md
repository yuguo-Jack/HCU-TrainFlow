# [Kimi K3] Add EPLB support

[Upstream PR](https://github.com/vllm-project/vllm/pull/50647) · state: open · merged: False

## Original PR description

## Summary

Add complete Kimi K3 EPLB metadata and redundant-expert support for both the main Kimi Linear model and its MTP model.

This change makes Kimi K3 expose the model-level MoE metadata expected by the v1 EPLB controller, constructs FusedMoE/MegaMoE with the physical expert layout, loads checkpoint weights into redundant physical expert slots, and keeps physical-expert metadata synchronized after a rearrangement.

The implementation is intentionally model-specific. It does not change the generic EPLB policy, communication implementation, or scheduling algorithm.

## Why this change is needed

Before this PR, Kimi K3 instantiated its MoE layers without exposing the complete `MixtureOfExperts` contract used by EPLB:

- the model did not report its MoE layer list to `EplbState`;
- logical, physical, redundant, and rank-local expert counts were not tracked consistently;
- FusedMoE was not constructed with Kimi's EPLB/redundant-expert configuration;
- MegaMoE only allocated the original logical experts;
- checkpoint expert mappings did not populate redundant physical slots;
- the MTP MoE container did not register its expert layers with EPLB.

As a result, the generic EPLB controller could not safely build and update Kimi K3 expert maps.

## Implementation

### Main Kimi K3 model

`vllm/models/kimi_k3/nvidia/model.py` now:

1. Derives the expert layout from the runtime parallel configuration:

   - `n_logical_experts` remains the checkpoint/model expert count;
   - `n_redundant_experts` comes from `EPLBConfig` when EPLB is enabled;
   - `n_physical_experts = n_logical_experts + n_redundant_experts`;
   - `n_local_physical_experts = n_physical_experts / ep_size`.

2. Validates physical-expert divisibility only for paths that require it: MegaMoE or EPLB. This avoids changing ordinary non-EPLB FusedMoE behavior.

3. Constructs MegaMoE with the physical expert count and correct rank-local physical range.

4. Constructs FusedMoE with:

   ```python
   enable_eplb=self.enable_eplb
   num_redundant_experts=self.n_redundant_experts
   ```

5. Includes redundant physical slots in `fused_moe_make_expert_params_mapping`, so every redundant replica receives its initial logical-expert checkpoint weights.

6. Adds `KimiK3MixtureOfExperts`, which exposes the model-level metadata required by EPLB:

   - `moe_mlp_layers`;
   - `moe_layers`;
   - `num_moe_layers`;
   - logical/physical/local/redundant expert counts;
   - routed/shared expert counts;
   - expert-group count.

7. Implements `update_physical_experts_metadata()` so the model and individual Kimi MoE layers remain synchronized when the physical layout changes.

8. Makes `KimiLinearForCausalLM` implement this shared Kimi K3 MoE interface and registers every real, non-PP-placeholder Kimi MoE layer.

### MTP model

`vllm/models/kimi_k3/nvidia/mtp.py` now:

- makes `KimiK3MTP` implement `KimiK3MixtureOfExperts`;
- registers all MTP MoE layers with the same metadata path as the main model;
- includes redundant expert slots when constructing the MTP checkpoint expert mapping.

This keeps main-model and MTP expert registration consistent without duplicating EPLB bookkeeping logic.

### Rank-load metric

The figure and reported balancedness use the raw 16-rank arrays emitted by the experiment:

```text
[EPLB_TRACE] rank_load ... rank_tokens=[rank0, ..., rank15]
```

Rank balancedness is calculated as:

```text
mean(rank_tokens) / max(rank_tokens)
```

This is deliberately calculated from `rank_tokens` rather than reusing the generic `EPLB step: balancedness=...` log field, because this experiment specifically measures aggregate EP-rank imbalance.

### Rearrangement cost

The EPLB run produced 24 formal `committed=True` rearrangements during the evaluation:

- cumulative CUDA-event-measured rearrangement time: **933.8124 seconds**;
- median rearrangement duration: **38.88 seconds**;
- maximum rearrangement duration: **39.87 seconds**;
- total EPLB evaluation wall time: **1466.50 seconds**;
- control evaluation wall time: **463.11 seconds**;
- wall-time difference: **1003.39 seconds**.

The measured rearrangement GPU time is 63.7% of the EPLB run's complete wall time and is close to the observed wall-time difference. The CUDA-event value is not claimed to be a complete wall-clock measurement: CPU coordination, collectives, and scheduling can add additional time.

Because this run used `use_async=false`, every rearrangement was on the synchronous inference path:

```text
EplbState.step()
  -> EplbState.rearrange()
  -> rearrange_expert_weights_inplace()
  -> commit expert maps
  -> resume forward execution
```

The generic EPLB implementation also has an asynchronous worker mode, but async EPLB was not evaluated in these two runs and no async performance claim is made here.

## Limitations and follow-up work

- The current `rank_load` window aggregates prefill and decode tokens. It does not yet produce separate prefill-only and decode-only imbalance statistics.
- This comparison validates synchronous EPLB only. Async EPLB requires a separate experiment.
- The observation-only load accounting used for the control run was an experiment overlay and is not part of this model-support PR.
- The runtime experiments used the PR commit as their model-support baseline plus temporary observability instrumentation. The PR itself remains limited to the Kimi K3 model/MTP support and the uploaded experiment documentation.
- The comparison demonstrates that the rearrangement algorithm improves rank balance, but the tested `step_interval=64` synchronous configuration is too expensive for this workload. This is a configuration/runtime-policy result, not a correctness failure in the Kimi K3 registration patch.
