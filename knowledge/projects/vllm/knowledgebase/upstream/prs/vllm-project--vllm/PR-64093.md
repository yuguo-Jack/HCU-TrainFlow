# [Metrics] Add vllm:kv_admission_reserved_blocks gauge

[Upstream PR](https://github.com/vllm-project/vllm/pull/64093) · state: open · merged: False

## Original PR description

Adds a per-engine Prometheus gauge, `vllm:kv_admission_reserved_blocks{kind}`, for the free KV cache blocks the scheduler holds back from admissions: the watermark, and the reserve for in-flight prefills applied to async KV load admissions.

## Overview

`allocate_slots` refuses an admission unless the request's blocks fit within the free blocks minus two reserves:

- **watermark** (`--watermark`): headroom kept free when admitting waiting/preempted requests while others are running;
- **in-flight load reserve**: an async KV load holds its blocks for the whole transfer and can't be preempted, so the scheduler admits one only if it leaves free the blocks the in-flight prefills still need (`_inflight_prefill_reserved_blocks()`, passed as `reserved_blocks`).

Neither is exported. On a dashboard, `vllm:kv_cache_usage_perc` can show free blocks while waiting requests, especially P/D decode loads, are still refused. This gauge shows how much of the free pool is held back, so `free - reserved` is the capacity admissions actually see.

## Claims

- `vllm:kv_admission_reserved_blocks{kind="watermark"}` reports `KVCacheManager.watermark_blocks` while requests are running, and 0 otherwise, matching when `allocate_slots` applies it (`has_scheduled_reqs`).
- `vllm:kv_admission_reserved_blocks{kind="inflight_load"}` reports the reserve an async KV load admission currently faces: the blocks in-flight prefills still need plus the spec decode step blocks, the same `reserved_blocks` value the scheduler passes to `allocate_slots`. It is 0 without a KV connector, since there are no async loads to gate.
- Both are current levels, recomputed on every stats update, so a Prometheus scrape every 15–60 s sees the reserve in effect rather than a value that was reset after a single step.
- No behavior change. The only new work is one sum over the in-flight prefills per stats update (`_inflight_prefill_reserved_blocks()`), only with a KV connector.

## Validation

New unit tests in `tests/v1/core/test_scheduler.py`:
- `test_stats_report_admission_reserved_blocks` (mock async KV connector):
  - with nothing running or in flight, both kinds read 0;
  - with an async load in progress, `inflight_load` equals `_inflight_prefill_reserved_blocks()` (> 0) on every update, not just once, and `watermark` stays 0 because nothing is running;
  - once a request is running, `watermark` reports the manager's `watermark_blocks`.
- `test_stats_report_no_inflight_load_reserve_without_connector`: without a KV connector, `inflight_load` is 0 even while a chunked prefill is in flight.

New logger test `test_kv_admission_reserved_blocks_gauge` in `tests/v1/metrics/test_histogram_buckets.py`: `PrometheusStatLogger.record(..., engine_idx=1)` with `num_watermark_blocks=5`, `num_inflight_load_reserved_blocks=3` sets both `kind` series for engine 1 and leaves engine 0 at 0.

```bash
pytest tests/v1/core/test_scheduler.py -k "admission_reserved_blocks or inflight_load_reserve"
pytest tests/v1/metrics/test_histogram_buckets.py -k kv_admission_reserved_blocks
pytest tests/v1/core/test_scheduler.py tests/v1/core/test_prefix_caching.py \
       tests/v1/metrics/test_stats.py tests/v1/kv_connector/unit/test_kv_load_failure_recovery.py
```

All new tests are `cpu_test` (module-level marker), so they run in CI. The scheduler, stats, logger and load-failure test files give 266 passed; the 63 failures are the same ones that fail on unmodified `main` in my CPU-only environment (missing GPU / multimodal dependencies). The main scheduler test fails on the previous revision (a gauge that resets after one update, and a watermark reported with nothing running). `ruff check`, `ruff format` and `mypy` (1.20.2, as in pre-commit) are clean.

End-to-end on GKE, on the previous revision of this PR, where `inflight_load` was the largest reserve applied since the last update (so it was non-zero only in single steps) and `watermark` was always the configured value. The current gauge reports the level in effect instead, so `inflight_load` should be non-zero far more often than below, and `watermark` 0 whenever nothing runs. vllm-torchtpu pins vLLM v0.32.0, so I cherry-picked the commit onto `v0.32.0` (clean, same 5 files) and deployed it with stock vllm-torchtpu `main`, which has no plugin copy of this gauge. Setup: TPU v5e, Qwen2.5-7B-Instruct, P/D via llm-d with `TPUConnector` + Raiden, `block_size=128`, 109 KV blocks per engine, `--watermark 0.05` on decode only. A load job overloaded the single decode engine with concurrent P/D requests; the gauge was read once a second for 300 s:

| Engine | `kind` | Non-zero reads | Min / max | Expected |
|---|---|---|---|---|
| decode | `watermark` | 280 / 300 | 0 / **5** | `int(0.05 × 109)` = 5 |
| decode | `inflight_load` | 25 / 300 | 0 / **4** | non-zero only in steps where an async KV load admission was considered while other prefills were in flight |
| prefill (no watermark, KV producer) | `watermark` | 0 / 300 | 0 / 0 | 0 |
| prefill | `inflight_load` | 0 / 300 | 0 / 0 | 0 (no async loads) |

The gauge reads 0 until the engine's first scheduler step: like the other scheduler gauges, it updates only when the engine reports stats.

## Details

- **`inflight_load` is a level, not a per-step event.** It is recomputed on every stats update as the reserve an async load admission would face now. An earlier revision reported only the largest reserve applied since the last update, which reset to 0 on the next step (~10–30 ms) and so was invisible to most scrapes. Computing it costs one sum over the in-flight prefills per update.
- **`watermark` follows `allocate_slots`.** The watermark is applied only to waiting/preempted requests while others are running, so the gauge reports it only while requests are running and 0 otherwise.
- **Always registered:** reads 0/0 with no watermark and no KV connector. Unlike connector-only metrics (e.g. `vllm:kv_load_failed_tokens`, registered only with `kv_transfer_config`), the watermark applies without a KV connector, so the gauge isn't gated. It is also listed in `EXPECTED_METRICS_V1` and documented automatically in the generated metrics list (`gen:metrics-general`) on the [metrics page](https://docs.vllm.ai/en/latest/usage/metrics.html).
- **Rust frontend:** its `SchedulerStats` decoder ignores unknown fields, so it is unaffected. It doesn't export this gauge yet.
- This is part of the same HBM KV cache observability effort as #64026 (`vllm:kv_load_failed_tokens`).
