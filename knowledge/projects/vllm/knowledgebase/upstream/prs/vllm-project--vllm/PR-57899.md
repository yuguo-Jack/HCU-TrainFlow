# [Experimental] Add CUDA graph discard and lazy recapture to sleep/wake

[Upstream PR](https://github.com/vllm-project/vllm/pull/57899) · state: open · merged: False

## Original PR description

## Purpose

Add an opt-in level-1 sleep mode that destroys the model's FULL CUDA graphs,
serves eagerly after memory is fully restored, and recaptures one graph shape
at each idle boundary. The default sleep path is unchanged.

This provides an optional memory/latency trade-off for deployments that release
GPU capacity while an engine sleeps. In a matched Qwen3.8-27B BF16 TP2 test
(35 capture shapes, 8 GiB KV cache per GPU), enabling this option increased
memory that a separate process could allocate and write by **0.193359375 GiB
per GPU**, from 92.1953125 to 92.388671875 GiB. Both runs used the same candidate
source, with the option off/on; both cycles on both GPUs had the same result.

Memory snapshots account for the difference: 0.142578125 GiB in the graph
private pool, 0.03125 GiB in cuBLAS workspace allocations, 0.00244140625 GiB
in persistent graph outputs, and 0.01708984375 GiB in cached free blocks.
This is the combined effect of the option; it is not a measurement of CUDA
graph executable memory alone.
The driver can retain physical allocations after graph destruction. The
option does not promise to reclaim all graph-related device memory.

#59160 offloads the graph pool while retaining graphs; #59909 releases that
pool without backing it up and retains graphs. A separate matched comparison
against #59909 found an additional 0.05078125 GiB/GPU reduction with this
option. For four prompts generating 16 tokens each, median first-generation
time after wake was 1.111 s versus 0.416 s, followed by 4.345 s of
client-observed recapture wait. Medians use the final three of four rounds;
the wait includes polling/RPCs. Post-recapture residency was equal.
Steady-state median sleep was 0.627 s versus 0.557 s and wake was 0.630 s
versus 0.641 s. First sleep was 12.058 s versus 12.017 s and is excluded from
those medians. These measurements describe extra sleep-time capacity and
its recovery cost, not a general throughput improvement.

## Behavior

- Enable with `VLLM_SLEEP_DISCARD_GRAPHS=1` and the V2 runner. Only level 1 is
  supported; partial wake does not resume scheduling or recapture.
- A completed request after wake enables idle recapture. Each idle boundary
  captures at most one configured shape, largest first. Continuous traffic can
  postpone completion. A request arriving during capture waits for that shape.
- Recapture reuses its capture stream and preserves cached pinned host buffers
  used for weight backups. It does not replace PyTorch's global functions.
- Graph retirement resets custom-allreduce graph registrations while retaining
  static registrations. Participating workers close peer mappings before any
  worker frees the corresponding cached storage.
- A recoverable single-worker allocation failure leaves execution eager until
  another full wake. Multi-worker capture failures terminate the executor:
  a peer may already be blocked inside a collective. Multiprocess and Ray RPCs
  use the configured execution timeout for capture, sleep and wake. The `uni`
  executor cannot interrupt a blocked CUDA operation.
- If graph-pool offloading is also requested, discard takes precedence; no
  cuMem graph pool is retained for discarded graphs.
- An engine failure ends pending synchronous and asynchronous management
  calls instead of leaving their futures unresolved.
- Failed destructive transitions prevent resume. Worker termination is initiated
  before the fatal engine error is propagated to clients.

## Scope

Linux/CUDA, unquantized models, cuMem sleep, V2, FULL or FULL_DECODE_ONLY graphs,
without `torch.compile` or asynchronous scheduling. The default model list is
Qwen3 dense and MoE. Other architectures require
`VLLM_SLEEP_DISCARD_GRAPHS_EXTRA_MODELS`; testing a text path does not establish
multimodal correctness.

Tensor and pipeline parallelism were validated. Data parallelism is permitted
by configuration, but a multi-data-parallel-group lifecycle result is not
included in this evidence. Expert parallelism is restricted to a single
data-parallel engine group. Context parallelism, EPLB,
encoder CUDA graphs, speculative decoding, LoRA, transfers, extra weight
offloaders and communicator suspension are rejected.

## Related work and dependencies

This branch includes the prerequisite fix from #59228 at
`85eac2a2102b42520017dd0f1f06719e2916c826`, authored by aoshen02, to fix
freeing cuMem allocations while asleep. That fix and its tests are a
prerequisite, not a new contribution of this PR. The prerequisite is kept in a separate commit with its original author.

#59537 caches a capture stream globally per device. This candidate currently
reuses a stream only within the opt-in graph-discard manager. Once #59537 is
available as a dependency, the local stream parameter and cache should be
removed in favor of that shared implementation. The overlap is explicit;
this revision does not silently change the default capture stream.

## Validation

Local validation results: 61 graph-manager/worker unit tests, 7 client failure
regressions, and 18 allocator tests passed. With the final #59228 native extension, Qwen3.8-27B completed TP2 20-cycle
checks with the default communication path, forced custom allreduce, and the
Ray executor: all three tests passed (485.61 s). These lifecycle tests use
four capture shapes; the capacity comparison uses 35. The forced custom
allreduce test recorded 69,800 calls per GPU.
Four-GPU TP4 and TP2/PP2 tests passed. Batch sizes 1, 2, and 8 with mixed input
lengths generated exactly 96 tokens per request and matched their references
before sleep, after wake, and after recapture. A partial-capture allocation
failure recovered eagerly and recaptured after the next sleep/wake.

Qwen3-30B-A3B TP2 expert parallelism passed with TritonExperts and PYNCCL.
The final #59228 extension passed three Qwen3.8-27B shutdown cases: single
GPU asleep, TP2 asleep, and TP2 after waking only weights. The final Qwen3.8-27B TP2 fault run passed all five phases (preparation,
warmup, capture, sleep and wake), checking worker exit before explicit
client shutdown. The test RPC timeout was 30 s; production defaults are
unchanged. These results
span explicitly recorded candidate revisions; allocator-dependent claims
require the rebuilt #59228 extension. No results from the removed
driver-reclamation experiment apply.

The local target environment is PyTorch 2.14.0+CUDA 13.0, Ray 2.56.1, and four
H20 GPUs. The main requested model is the local Qwen3.8-27B checkpoint, whose
configuration declares `Qwen3_5ForConditionalGeneration`. Small-model fault
tests supplement the large-model lifecycle tests.

The proposed Buildkite job runs the repository's sleep lifecycle tests on two
GPUs. It has not been run by upstream CI. Model-specific tests and four-GPU
tests have explicit hardware/checkpoint requirements.

## Reproducing the lifecycle checks

Use a CUDA build with the prerequisite allocator fix and the matching native
extensions. On a two-GPU host, with the model checkpoint available locally:

```bash
CUDA_VISIBLE_DEVICES=0,1 VLLM_PLUGINS= \
VLLM_WORKER_MULTIPROC_METHOD=spawn \
VLLM_SLEEP_DISCARD_GRAPHS_EXTRA_MODELS=Qwen3_5ForConditionalGeneration \
SLEEP_GRAPH_TEST_MODEL=/path/to/Qwen3.8-27B \
SLEEP_GRAPH_TEST_DTYPE=bfloat16 SLEEP_GRAPH_TEST_ROUNDS=20 \
SLEEP_GRAPH_TEST_GPU_MEMORY_UTILIZATION=0.8 \
SLEEP_GRAPH_TEST_RPC_TIMEOUT_SECONDS=30 \
python -m pytest tests/v1/cudagraph/test_sleep_graphs.py \
  -k test_graph_discard_sleep_tensor_parallel -q -s
```

This selects the default/custom-allreduce multiprocessing cases and the Ray
case. For the five failure phases, use the same environment with
`-k failure_terminates`. These are lifecycle checks, not the 35-shape capacity
measurement. Multi-node placement and multi-data-parallel-group lifecycle
are not claimed as validated by this revision.

Updated the implementation and description after adversarial review and GPU validation.

The candidate revision changes the earlier failure-handling contract. A
multi-worker capture allocation failure terminates the executor instead of
attempting to recover one rank locally while peers may be waiting in a
collective. The regression injects failures during preparation, warmup and
capture, and also during sleep and wake; it checks worker exit before explicit
client cleanup.

The candidate also retires custom-allreduce graph registrations, preserves all
static registrations, and waits for peer mappings to close before releasing
storage. A separate test forces custom allreduce and asserts that it actually
runs, rather than relying on a configuration flag.

Repeated recapture exposed two additional costs: distinct warmup streams kept
separate cuBLAS workspaces, and the high-level capture context flushed pinned
host caches used by the next sleep. The candidate reuses the stream and uses
the low-level capture API during idle recapture, retaining synchronization and
exception cleanup without flushing host memory.
