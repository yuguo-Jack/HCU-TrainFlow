# [Bugfix][Frontend] Reject NaN logit_bias values instead of banning the token

[Upstream PR](https://github.com/vllm-project/vllm/pull/62038) · state: open · merged: False

## Original PR description

## Overview

A NaN value in `logit_bias` is clamped to -100 and silently bans the token, instead of being rejected.

## Claims

- `SamplingParams.from_optional` raises a validation error (`parameter="logit_bias"`) when any bias is NaN.
- Finite and infinite values behave as before: they are clamped to [-100, 100].

## Validation

`tests/test_sampling_params.py` (2 new tests):

```
pytest tests/test_sampling_params.py
  main:        2 failed, 62 passed
  this branch: 64 passed
```

Also, on main a JSON body with `"logit_bias": {"5": NaN}` parsed into `ChatCompletionRequest` gives `to_sampling_params(...).logit_bias == {5: -100.0}`; on this branch it raises `VLLMValidationError`. `ruff check` and `ruff format --check` pass on the changed files. I ran the tests on CPU with the xgrammar import stubbed. I did not run a live server, so the HTTP path is checked at the request-model level only. Model evaluation does not apply: no sampling math changes for valid input.

## Details

`min(100.0, max(-100.0, bias))` returns -100.0 for NaN because every comparison with NaN is false. Python's JSON parser accepts the `NaN` literal and pydantic accepts it for `float`, so a request can reach this. The clamp now goes through one helper used by both the fast path and the non-integer-key path in `from_optional`.

Not a duplicate: open PRs and issues searched for `logit_bias` with NaN, non-finite, validation and clamp. #52686 (tests) and #55164 (size limit) do not touch NaN; #46612 (non-integer keys) is merged.
