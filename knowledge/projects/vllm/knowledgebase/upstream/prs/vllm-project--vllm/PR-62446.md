# [Frontend] Return flat logprobs as arrays on the generate endpoint

[Upstream PR](https://github.com/vllm-project/vllm/pull/62446) · state: open · merged: False

## Original PR description



## Overview

Give `sampling_params.flat_logprobs` a wire format on `/inference/v1/generate`: in tokens mode the choice carries `flat_logprobs`, three base64 `.npy` arrays of shape `[num_tokens, k + 1]` (token ids, logprobs, ranks; the sampled token in column 0), instead of one object per candidate in `logprobs.content`. Tokens-mode requests without stop strings also stop detokenizing, since nothing in that response carries text, and `FlatLogprobs.append_fast` extends its lists instead of appending element by element. Independent of #62342; the two touch neighbouring lines of the same serving method.

## Claims

- With the default single API server, `logprobs=8` or `logprobs=20` with `flat_logprobs=true` runs at the same throughput as `logprobs=0` on R1-Distill-Qwen-1.5B, Qwen3-4B and Qwen2.5-7B-Instruct: 2.0 to 2.8x main at k=8 and 4.1 to 5.4x at k=20, two trials each with no overlap.
- API-server CPU per generated token at k=8 with `flat_logprobs=true` falls 4 to 5x (95–105 to 21–25 µs with one API server, 64–79 to 18–23 µs with eight) and the response is 2.7x smaller (447 to 166 bytes per token; 975 to 360 at k=20).
- The `logprobs.content` shape is unchanged for clients that do not set `flat_logprobs`; those requests still gain 64 to 113% at k=8 on one API server from the detokenization skip and the container change.

## Details

With `logprobs=k`, main builds `k + 1` `Logprob` dataclasses per generated token on every step, decodes each candidate's text, keeps all of them alive until the request finishes, then builds a pydantic object per candidate for the response. py-spy on a single API server at k=8 puts 40% of its time in the response build and 20% in the per-step objects and decoding, which is why `logprobs=8` costs 50–60% of throughput there.

- `FlatLogprobs` (behind `sampling_params.flat_logprobs`, added for the GC overhead of `list[dict[int, Logprob]]`) already stores a request's logprobs as primitive lists, but nothing served it: `ServingTokens` indexed it per position, which rebuilds the dicts. The new `flat_logprobs` choice field serializes those lists directly as `.npy` arrays, like `routed_experts` and `prompt_token_id_logprobs` do on the same endpoint. Every position has exactly `k + 1` entries in the engine's layout (sampled first, then the top-k, which repeats the sampled token when it ranks there), so the arrays are 2-D and need no offsets; `logprobs.content` deduplicates that case, the one shape difference. Values are the engine's float32, not clamped, so `-inf` survives. In a stream the arrays are per chunk.
- Only `output_mode="text"` needs detokenized output, and stop strings need it in both modes; a tokens-mode request without stop strings now gets `detokenize=False`, the per-request form of what `--tokens-only` forces server-wide. That removes the per-candidate `convert_ids_list_to_tokens` and the incremental detokenizer for those requests. Requests with stop strings keep both.
- `append_fast` extends the four lists instead of appending in a Python loop; `islice` keeps the zip truncation it replaces.

After this, the single API server's largest remaining cost at k=8 is the msgpack decode of the sampling-mask arrays (40% of its time), not logprobs.
