# [Rust Frontend][gRPC] Accept per-worker weight update arrays

[Upstream PR](https://github.com/vllm-project/vllm/pull/63583) · state: open · merged: False

## Original PR description



## Overview

Fix the Rust gRPC `UpdateWeights` handler rejecting per-worker JSON object arrays. Accept a JSON object or an array of per-worker JSON objects, matching the Rust HTTP and Python weight-transfer interfaces.

## Claims

- Accepts both supported JSON shapes for `update_info_json` while keeping `init_info_json` restricted to a JSON object.
- Preserves the supplied update metadata when forwarding it to the engine client.

## Validation

- `cd rust && cargo test -p vllm-server grpc::tests::control_forwards_weight_update_without_pause_guard -- --exact --nocapture` — passed.
- `cd rust && cargo test -p vllm-server grpc::tests::control_ -- --nocapture` — 6 passed.
- `.venv/bin/python -m pytest tests/v1/worker/test_gpu_worker_weight_transfer.py -q` — 15 passed.
- `cd rust && cargo +stable fmt --all -- --check` and `git diff --check` — passed.
- With the updated regression test and the original handler, the focused test failed with `InvalidArgument: update_info_json must contain a JSON object`. Restoring the fix made the same test pass.

The Rust tests exercise gRPC handling and metadata forwarding with a scripted mock engine. The Python tests separately cover worker behavior, including rank-based payload selection.

The gRPC regression test is covered by the existing Rust Frontend Cargo CI job. The live GPU checks were run separately.

Live GPU validation also passed on NVIDIA A100 80GB GPUs with Qwen3-0.6B, BF16, eager execution, TRITON_ATTN, and CUDA IPC. The Rust binary was rebuilt with `cd rust && cargo build -p vllm-cmd --locked`; existing Python/CUDA extensions were reused (PyTorch 2.14.0+cu126).

| Configuration | Update payload | Parameter SHA-256 digests restored | Generation matches baseline |
| --- | --- | --- | --- |
| TP=1 | Object | 226/226 | Yes |
| TP=1 | One-worker object array | 226/226 | Yes |
| TP=2 | Object | 452/452 across both workers | Yes |
| TP=2 | Two-worker object array | 452/452 across both workers | Yes |

Each case records a baseline, pauses generation, zeros the GPU weights, verifies that their digests differ, and restores the checkpoint through gRPC `StartWeightUpdate` / `UpdateWeights` / `FinishWeightUpdate`. After resuming, both eight-token greedy generations exactly match the baseline for the same TP configuration. Weight digests and resets use the existing HTTP `/weight_checker`; weight-transfer control and inference use the real Rust gRPC services. Each TP=2 array element contains IPC handles for only its corresponding GPU, exercising worker-specific selection. Weight-version updates also pass.

Validation covered IPC weight transfer with TP=1 and TP=2. NCCL weight transfer, data-parallel replicas, multi-node operation, task accuracy, and throughput were not evaluated.

## Details

The gRPC handler previously parsed both `init_info_json` and `update_info_json` as JSON objects. Python's weight-transfer path also accepts per-worker object arrays, and the worker selects the local payload by rank. The handler now parses JSON values first, retains object-only validation for initialization, and accepts an update object or an array whose elements are all objects. The engine client forwards the JSON value unchanged.

This change is limited to the Rust gRPC request validation and forwarding path; it does not change tensor transport or worker rank selection. No issue specifically reporting this gRPC validation mismatch was found.
