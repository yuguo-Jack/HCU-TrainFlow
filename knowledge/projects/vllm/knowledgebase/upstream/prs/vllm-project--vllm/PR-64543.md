# [Bugfix][Model] Fix dots_ocr vision tower QKV split for TP > 1

[Upstream PR](https://github.com/vllm-project/vllm/pull/64543) · state: open · merged: False

## Original PR description

## Overview

`DotsVisionAttention` used a QKV-split helper meant for a differently sharded
layer, scrambling q/k/v at TP > 1 so `dots.ocr` repeated one sentence for every
image region. Split the local shard instead. Fixes #64541.

## Claims

- `DotsVisionAttention` now splits QKV correctly under TP: TP=2 with the
  default weight-sharded encoder matches the TP=1 reference again. Confirmed on
  Ascend 910B3 (12/12 layout blocks) and on CUDA (2× A800, byte-identical
  output).
- Adds a `dots_ocr` entry to the VLM generation tests with
  `tensor_parallel_size=2`, so the 2×L4 `Models - Distributed` CI job exercises
  the vision tower under tensor parallelism.
- No behaviour change at TP=1: the previous helper degenerated to the same
  local `chunk(3)`, which is why single-card serving was already correct.

## Validation

### End-to-end reproducer (before/after, 2× Ascend 910B3, vLLM 0.30.0)

Same image, prompt and sampling parameters in all runs:

| # | code | TP | mm encoder | result |
|---|------|----|-----------|--------|
| 0 | before | 2 | weights (default) | broken: 4× identical "I am sorry ... blurry image of a person" |
| 1 | before | 2 | `--mm-encoder-tp-mode data` | correct: 12 layout blocks |
| 2 | after | 2 | weights (default) | correct: 12 layout blocks |
| 3 | before | 1 | weights | correct: 12 layout blocks (reference) |

Run 1 bypasses the vision *weight* TP path (`disable_tp=True`, the encoder sees
`tp_size == 1`), which isolates the failure to the TP-sharded ViT rather than to
the LM or the processor.

After the fix, run 2 matches run 3:

- 12/12 layout blocks with identical categories and bounding boxes;
- extracted text identical character-for-character except for one empty
  `<td></td>` cell in a different column inside a table row (same length,
  sampling at `temperature=0.1`);
- 52 s for the full page versus 8 s for the degenerate pre-fix output.

A CPU-only script in the issue shows the same layout mismatch without any
accelerator (it only simulates the all-gather + `chunk(3)` on a token-index
tensor).

### Fix confirmed on CUDA (2× A800 80GB PCIe)

Environment: vLLM 0.32.0, torch 2.13.0, transformers 5.19.0, driver 580.105.08,
2× A800 80GB PCIe (sm_80, PCIe interconnect), model `rednote-hilab/dots.ocr`
(6.08 GB, 2 shards), OpenAI-compatible server with
`--max-model-len 4096 --trust-remote-code`, sampling `temperature=0.1`, `seed=0`.
The image was a synthetic A4 layout page (title, two-column body, 3×3 table),
not the document used in the NPU run, so the post-fix result is compared against
the TP=1 reference for the same image instead of block counts.

| # | code | TP | mm encoder | output len | repeated-paragraph rate | matches TP=1 ref | latency |
|---|------|----|-----------|-----------|------------------------|------------------|---------|
| 0 | before | 2 | weights | 6095 | 93% | no | 6.6 s |
| 1 | after | 2 | weights | 1117 | 0% | yes, byte-identical | 1.7 s |
| 2 | before | 2 | `--mm-encoder-tp-mode data` | 1117 | 0% | yes | 1.6 s |
| 3 | before | 1 | weights | 1117 | 0% | reference | 3.6 s |
| 4 | after | 1 | weights | 1117 | 0% | yes | 2.0 s |

- Pre-fix TP=2 with the default weight-sharded encoder reproduces the reported
  failure: the same paragraph is emitted 6+ times regardless of image content.
- Post-fix TP=2 output is byte-for-byte identical to the TP=1 reference.
- The `--mm-encoder-tp-mode data` control was unaffected before the fix, which
  isolates the defect to the TP-sharded vision weights rather than the LM or the
  processor.
- TP=1 output is unchanged by the patch.

The degenerate text differs from the NPU run ("license plate" paragraph vs.
"I am sorry ... blurry image of a person"). Both are attractor states reached
when the vision embeddings are noise, and the failure mode — identical text for
every image region — is the same.

Note: this run applied the two-state patch (PR diff on/off) to the installed
0.32.0 wheel instead of building this branch from source, because the container
had no `nvcc`. `dots_ocr.py` in the 0.30/0.31/0.32 releases still contains the
same pre-fix `split_qkv` call, so the two states are semantically the PR's
before/after.

## Details

### Root cause

`DotsVisionAttention` builds its QKV with `QKVParallelLinear`, so each TP rank
already owns the local `[q | k | v]` shard. It nevertheless called
`Qwen2VisionAttention.split_qkv()`, a helper written for Qwen2-VL's
`ColumnParallelLinear`, where each rank holds a *slice of the whole packed*
`[q | k | v]` tensor. At TP > 1 that helper all-gathers and re-splits:

```
QKVParallelLinear (TP=2):   [q0 k0 v0] | [q1 k1 v1]
all_gather(dim=-1):         [q0 k0 v0 | q1 k1 v1]
chunk(3):                   (q0+k0), (v0+q1), (k1+v1)
rank0 -> q=q0 (ok),   k=v0 (wrong), v=k1 (wrong)
rank1 -> q=k0 (wrong), k=q1 (wrong), v=v1 (ok)
```

The vision embeddings become noise, so the LM collapses to a fixed sentence for
every region. At TP=1 the helper degenerates to a plain `chunk(3)` on the full
tensor, which is why single-card serving was correct.

### Fix

`DotsVisionAttention.forward` splits the local tensor directly
(`x.chunk(3, dim=-1)` + reshape), exactly as `glm_ocr.py` already does for the
same attention layout.

### Scope and risk

- Diff is 24 added / 2 deleted lines across two files; no core component is
  touched.
- TP=1 output is unchanged by construction.
- The test uses `rednote-hilab/dots.ocr`, the checkpoint already registered in
  `tests/models/registry.py`; the Ascend reproducer used `dots.mocr`, which has
  the same architecture, and the A800 run used `dots.ocr` itself.
- Only the default (weight-sharded) encoder path was broken; users on
  `--mm-encoder-tp-mode data` were unaffected.
- Verified on two independent backends (Ascend 910B3 and CUDA A800); the
  CUDA run also confirms TP=1 output is unchanged.

### Related work

No duplicate: #63074 (`dots.ocr: support encoder CUDA graph`) is open and edits
other hunks of `dots_ocr.py` (CUDA-graph wiring), not the QKV split, so the two
