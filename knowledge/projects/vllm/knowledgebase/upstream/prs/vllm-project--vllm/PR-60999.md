# [Bugfix] Reject non-int values for integer SamplingParams fields

[Upstream PR](https://github.com/vllm-project/vllm/pull/60999) · state: open · merged: False

## Original PR description

## Overview

Fixes #60998. `InputProcessor` now validates request params with the same msgspec decode that EngineCore applies, so a value EngineCore would reject (e.g. a float or bool in an `int` field) fails the request with `VLLMValidationError` instead of hanging `LLM.generate()`.

Reworked per review: the first version type-checked 8 fields by hand in `_verify_args()`. That missed fields (`n`, `stop_token_ids`, `routed_experts_prompt_start`) and rejected `IntEnum` values that worked before.

## Claims

- Any `SamplingParams` / `PoolingParams` field that EngineCore's decoder would reject now fails the request on the client side. This covers `max_tokens=2.5`, `n=True`, `stop_token_ids=[True]` and `routed_experts_prompt_start=1.5`, with no per-field list to keep in sync.
- `IntEnum` values for `int` fields (e.g. `max_tokens`, `top_k`) are still accepted.
- The added cost is about 4 µs per request for typical params and about 9 µs for heavy ones (benchmark below).

## Details

**Root cause:** `SamplingParams` construction only range-checks its integer fields (e.g. `max_tokens < 1`), and a float or bool passes a range check. `EngineCoreRequest` is decoded with msgspec, which is strict about `int`. The decode runs in `EngineCore.process_input_sockets` outside any try/except, so the input thread dies and the client never gets a response or an error.

**Fix:** at the end of `InputProcessor._validate_params`, after `verify()` has normalized the params (e.g. nested-list `prompt_logprob_token_ids` to an ndarray), round-trip the params through `MsgpackEncoder` / `MsgpackDecoder(type(params))`, the same codec EngineCore uses, and turn `msgspec.ValidationError` into `VLLMValidationError`. `SamplingParams` itself is unchanged.

- A fresh encoder/decoder is built per call: `process_inputs_async` runs on the renderer's thread pool, and the codecs are documented as not thread-safe. Reusing one would save about 2 µs per request.
- The check runs outside `_verify_args()`, because decoding re-runs `__post_init__` and would recurse.

**Compatibility:**
- Whole floats like `4.0` are rejected rather than coerced, matching what EngineCore's decoder accepts.
- If the params cannot be encoded at all (e.g. a custom object or numpy integer in `extra_args`), the check is skipped: an in-process engine (`VLLM_ENABLE_V1_MULTIPROCESSING=0`) never encodes them and keeps working, and a multiprocess client fails at send with the same `TypeError` as on main.
- OpenAI server behavior is unchanged. Pydantic already rejects fractional values and coerces `4.0` to `4` and `true` to `1` before `SamplingParams` is built.

**Not in scope:** making `process_input_sockets` survive a decode error, which would turn any future decode failure into an error response instead of a hang. That is a larger change to core and is better as a separate PR.

**Why this isn't a duplicate:** no open PR references #60998, and no open PR touches `SamplingParams` type validation (checked with `gh pr list --search` before opening).

🔴 In-process engines (`VLLM_ENABLE_V1_MULTIPROCESSING=0`) now fail requests that worked on the base branch when `extra_args` holds a value msgpack cannot encode, such as a custom object or numpy int. The new round trip runs `MsgpackEncoder().encode(params)` for every engine mode. InprocClient never serializes, so these values used to reach the engine untouched. The resulting `TypeError` is not caught and escapes as a raw error, not a `VLLMValidationError`. Fix: run the check only when the params will actually be serialized (multiprocess clients). Alternatively, check only the declared typed fields and leave `Any`-typed payloads alone.

<summary>Why this was flagged</summary>
