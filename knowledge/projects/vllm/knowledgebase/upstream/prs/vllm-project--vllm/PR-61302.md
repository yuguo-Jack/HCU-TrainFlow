# [Doc] Host model recipes in recipes/

[Upstream PR](https://github.com/vllm-project/vllm/pull/61302) · state: closed · merged: True

## Original PR description



## Overview

Host the deployment recipes for models served by vLLM in this repository under `recipes/models/<hf_org>/<hf_repo>.yaml` (186 recipes). [recipes.vllm.ai](https://recipes.vllm.ai) keeps rendering them from [vllm-project/recipes](https://github.com/vllm-project/recipes), which reads this directory at a pinned commit. Companion PR: vllm-project/recipes#1095.

## Claims

- **Recipes:** `recipes/models/` holds the 186 non-omni recipes, identical to vllm-project/recipes main (as of 92fb889) except that `meta.difficulty`, which nothing reads, is dropped. `recipes/models/` is excluded from the `typos` hook in `pyproject.toml`: the guides carry multilingual examples and model or flag names.
- **Rendering:** recipes.vllm.ai renders the same commands from this directory.
- **No engine changes:** nothing in the vLLM Python, C++ or Rust code or the package changes.
- **Ownership:** `.github/CODEOWNERS` assigns `recipes/` to @esmeetu.
- **PR check:** `.github/workflows/recipes.yml` validates every PR that touches `recipes/`. It calls vllm-project/recipes' reusable `validate-recipes.yml`, which runs the same strict assemble and JSON API build the renderer runs after merge. It is read-only and needs no secrets, so it also runs for fork PRs.
- **Authoring docs:** the `model-recipes` agent skill now points recipe authoring at `recipes/models/`, and `recipes/README.md` explains how to preview a change.

## Validation

- **Rendering from this branch:** vllm-project/recipes#1095 pins `esmeetu/vllm@98ed489` (this branch). Its build produces 215 recipes, 186 of them from here and 29 omni recipes that stay in the recipes repo for now.
  - All 21,723 generated JSON files match the current recipes main, apart from a new `source` field in each file. The only other difference is the dropped `meta.difficulty`.
  - Preview: https://vllm-recipes-git-fork-esmeetu-content-sources-inferact-inc.vercel.app
- **pre-commit:** passes, including `typos`, `markdownlint`, `check-agent-files`, and the sign-off check.
- **CI:** no Buildkite test area depends on `recipes/`, so this PR triggers no GPU tests.

## Details

**Why here.** Recipe flags track vLLM's flags, kernels and defaults. Keeping the recipes next to the code lets a PR that renames or removes a flag update the affected recipes in the same change, and lets people with that context review them. Recently merged recipe changes show the coupling:
- vllm-project/recipes#1091 dropped the removed `VLLM_PLE_CPU_OFFLOAD`.
- vllm-project/recipes#1082 switched the ROCm attention backend after a regression in v0.31.0.

**Ownership after the split.**
| Content | Repository |
| --- | --- |
| Recipes for models served by vLLM | vllm (this PR) |
| Omni recipes | vllm-omni (follow-up) |
| Ascend NPU content | vllm-ascend, as overlays. An overlay can only add keys, and only for hardware its granted scope covers, so it can never change the NVIDIA/AMD commands. |
| Schema, hardware vocabulary, command synthesis, site, JSON API | vllm-project/recipes |

**How changes reach the site.** A workflow in vllm-project/recipes checks this directory every 20 minutes. When the directory's tree hash changes, it validates the new content with the full build and then commits the new pin, which redeploys the site. If validation fails, the site stays on the last good pin and an issue is opened.

**Merge order.** vllm-project/recipes#1097, which adds the reusable workflow this PR's `recipes` check calls, is merged, so the check now runs. After this PR merges, vllm-project/recipes#1095 switches the site to read these recipes from vLLM main and removes them from the recipes repo. From this PR's merge on, recipe edits go here.

**Open questions for maintainers.**
- Location: a top-level `recipes/` directory, or somewhere else?
- The PR check references the reusable workflow at `@main` rather than a pinned SHA, unlike vLLM's other workflows. That is deliberate: recipes are validated against the renderer that publishes them, so a pinned SHA would need a bump in vLLM for every schema change. Is that acceptable?
- Make the `Recipes` check required in branch protection? As written it runs only on PRs that touch `recipes/`, so a required check would wait forever on every other PR. Requiring it would mean dropping the `paths` filter and skipping the job internally.

**Limitations.**
- The change adds about 41k lines (1.7 MB) of YAML.
- Until both PRs merge, any recipe change merged to vllm-project/recipes main has to be re-synced here. One sync has been needed so far.
- Ascend content is still inline in these recipes. It moves to vllm-ascend overlays in a follow-up.
- vLLM PRs get no online preview yet. Preview locally from a vllm-project/recipes checkout, as `recipes/README.md` describes; a Vercel preview is a planned follow-up.
- Merged recipe changes reach recipes.vllm.ai within about 30 minutes, not immediately. vllm-project/recipes checks this directory every 20 minutes, validates the new content, and redeploys. If validation fails, the site keeps the previous version and an issue is opened.
