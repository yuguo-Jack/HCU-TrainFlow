# [Perf][Startup] Compile per_block_cast_to_fp8 on first use

[Upstream PR](https://github.com/vllm-project/vllm/pull/65590) · state: open · merged: False

## Original PR description



## Overview

`vllm/utils/deep_gemm.py` decorates `per_block_cast_to_fp8` with a module-level `torch.compile(dynamic=True, backend="inductor")`. Building that wrapper calls `_TorchCompileInductorWrapper.get_compiler_config()`, which imports `torch._inductor.compile_fx` and `torch._inductor.async_compile`, so every process that imports this module loads most of the Inductor stack. The API server and the engine core import it through `vllm.forward_context` → `dp_utils` → `ubatch_utils`, but the function is only called while processing weights. This PR compiles it on first call instead. Part of #59433.

## Claims

- `import vllm.v1.engine.core` no longer loads `torch._inductor.async_compile`. On CUDA, the `torch._inductor` module count after that import drops from 198 to 17. The `vllm.entrypoints.openai.api_server` import drops by 561 modules on CPU.
- `per_block_cast_to_fp8` returns bit-identical results to the old compiled function, keeps its signature and defaults, and keeps `__wrapped__` (used by `tests/quantization/test_online.py`).
- Scope: worker modules still import Inductor through other module-level `torch.compile` uses (e.g. `vllm/v1/sample/ops/logprobs.py`, `vllm/v1/spec_decode/utils.py`), and workers compile anyway. With the default `UniProcExecutor`, the engine core loads the worker, so there the import is deferred rather than avoided. The clear win is the API server process, and the engine core when workers run in separate processes.

## Details

- `_compiled_per_block_cast_to_fp8` is a `functools.cache` factory that returns the `torch.compile` wrapper, and the public `per_block_cast_to_fp8` calls it. A race on the first call can build two wrappers at worst; Dynamo caches by code object, so it still compiles once.
- `functools.wraps(..., assigned=())` only sets `__wrapped__`, so the public function keeps its own name and still pickles by reference.
- All in-tree callers (`quantization/online/fp8.py`, `quantization/utils/fp8_utils.py`) run in `process_weights_after_loading`, not under Dynamo tracing or CUDA graph capture.
- CI: `lazy_imports.py` currently runs only in the `(CPU) Params, Env, Tokenizers, Parser` job, which is commented out in `.buildkite/test_areas/misc.yaml` (#63609). #64414 restores it.
- Not a duplicate: no open PR changes `per_block_cast_to_fp8`. #57310 (`env_override.py`) handles a different `torch._inductor` edge. It and my structured-output PR also edit the end of `lazy_imports.py`, so whichever lands later needs a trivial rebase.
