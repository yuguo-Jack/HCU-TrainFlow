# [Perf][DiffusionGemma] Canvas packing + canvas swap: up to 10x lower short-request latency under load

[Upstream PR](https://github.com/vllm-project/vllm/pull/62581) · state: open · merged: False

## Original PR description



## Overview

Every DiffusionGemma request gets the full served canvas (256 tokens, about two paragraphs). Each denoising step computes and budgets all 256 positions, whether the reply is 14 tokens or 250, so under load short replies queue behind work that is mostly padding. When the scheduler preempts a request mid-block, the half-denoised canvas is discarded and the block restarts from noise.

This PR adds two opt-in mechanisms to the MRV2 runner. Both are off by default.

- **Canvas packing** (`VLLM_DIFFUSION_PACK_SPANS`): two requests share one canvas. A per-sequence span mask in Triton unified attention keeps each request's queries off the other's keys. A per-request RoPE remap gives each request the positions it would have if served alone.
- **Canvas swap** (`VLLM_DIFFUSION_CANVAS_SWAP`, `VLLM_DIFFUSION_CANVAS_SWAP_CAP`): on preemption, the request's in-flight block (canvas, step, stability history, self-conditioning embeds, pending logprobs) is stashed in a bounded host-RAM FIFO. It is restored after the re-prefill, so the block resumes where it stopped.

**Not a duplicate.** No open PR or issue covers canvas packing or preemption-safe canvas state (searched `diffusion canvas`, `DiffusionGemma preempt`, `DiffusionGemma packing`, `span mask triton`, `diffusion_canvas_length`). #60663 fuses self-conditioning kernels. #57250 and #59107 added client-chosen per-request canvas widths, which need the reply length up front; packing does not (see Details).

## Claims

- **Up to 10x lower short-request latency on real traffic shapes.** On Azure code traces, short-request p50 is 10.0-13.9x lower and p99 14.4-16.0x lower than vanilla, with goodput unchanged (3 seeds, H100).
- **Preempted requests no longer restart their block.** They resume at the saved denoising step, and host memory stays bounded (default 64 canvases).
- **Packed requests are isolated.** No cross-tenant marker leaks in any run, and output quality is within one point of vanilla.
- **No behavior change by default.** With the env vars unset, the new kernel path is compiled out (`USE_SPAN_MASK` constexpr) and the model state skips all new bookkeeping.

## Details

**Root cause.** The served canvas width doubles as `num_speculative_tokens`, so every running request schedules a full canvas of query tokens per denoising step and writes KV for all of it. On the Azure code window the median reply is 14 tokens, so about 95% of each canvas is padding that still costs compute and batch budget. Separately, `remove_request` on preemption drops all per-slot diffusion state, so the resumed request re-denoises its block from noise.

**Design.**
- The span table is a persistent `[max_num_reqs, 4, 3]` int32 buffer gathered per step, so packed forwards stay capturable by FULL CUDA graphs. The mask is one extra AND in `compute_kv_seq_mask`.
- Packing is restricted to `TRITON_ATTN`. Other backends raise at the first forward instead of silently ignoring the mask.
- Canvas swap hooks a new `ModelState.note_preempted` (no-op by default). It skips stashing a block that has not started, to avoid thrash. It keeps the existing stash when a request is re-preempted during its re-prefill.
- The scheduler drops draft tokens that arrive for a request after it was preempted. They were drafted against freed KV and would otherwise be scheduled alongside the resume prefill.

**Why not just `diffusion_canvas_length`?** A per-request width (#57250) helps only when the client knows the reply length up front. Packing needs no length labels: a reply that outgrows its half-canvas overflows and continues. The baseline above predates per-request widths, so a comparison against `main` with `diffusion_canvas_length=128` is still open.

**Where it loses.** Packing pays off when most replies fit in half a canvas and the server is near saturation. At low load, or when few replies are short, packed requests are slower than solo. On the unfavorable window, long jobs are up to 43% slower. That is why it is opt-in.

**Limitations.**
- Packed requests must fit in one canvas (`max_tokens <= canvas_length`).
- Packing requires `TRITON_ATTN`.
- The pack layout (`lenA,lenB,split`) is global, and the client builds the packed prompt and splits the output. Moving it to a per-request `extra_args` option, next to `diffusion_canvas_length`, is a natural follow-up.
- With `selective` packing and prefix caching, an unpacked prompt that begins with a packed prompt's tokens can reuse KV computed under the packed mask. Use `cache_salt` for packed traffic.
- A stash for a request aborted while preempted stays until FIFO eviction (bounded by the cap).
- Stash and restore copy to and from host memory only on preemption, never in steady state.
