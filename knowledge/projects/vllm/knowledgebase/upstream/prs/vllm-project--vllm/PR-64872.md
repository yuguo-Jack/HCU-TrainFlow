# [Kernel] Let --linear-backend deep_gemm override the DeepGemm model a…

[Upstream PR](https://github.com/vllm-project/vllm/pull/64872) · state: open · merged: False

## Original PR description

## Overview

On Blackwell, vLLM turns off DeepGEMM for the FP8 linear layers of Qwen3.5 because of the GSM8K accuracy drop reported in #37804 and #38083. No option turns it back on.

I measured Qwen3.5-35B-A3B-FP8 on one B200, and the drop seems to come from thinking. `gsm8k_eval.py` sends a plain-text prompt without the chat template. With this prompt, the model opens a `<think>` block in almost every response. With DeepGEMM, the model reasons inside the block more often: in 313 responses per run, against 196 with vLLM's default settings. Much of this reasoning hits the 256-token output limit or a stop string before the model gives an answer. Answers that do finish within the token limit are about 96.5% correct with or without DeepGEMM.

With the chat template and thinking off, I saw no real difference. [lm-eval](https://github.com/EleutherAI/lm-evaluation-harness)'s `gsm8k`  scored all three servers I tested within 0.7 points of each other.

So users should have a way to turn DeepGEMM back on for these models. With this PR, `--linear-backend deep_gemm` overrides vLLM's choice and logs a warning.

## Claims

1. **The default does not change.** Without an explicit request, vLLM still turns DeepGEMM off for the listed model types, and the warning now says how to turn it back on.
2. **An explicit request turns DeepGEMM back on.** Either `--linear-backend deep_gemm` or `deep_gemm` for `fp8_block_w8a8` in `linear_backend_per_quant` works. The per-quantization setting wins.
3. **The config and the kernel agree.** `quant_config.use_deep_gemm` stays `True`, so weight dequantization expects DeepGEMM's layout.
4. **The GSM8K drop comes from thinking.** DeepGEMM tips a near tie after `<think>` toward reasoning, which often doesn't finish within the output limit. Answers that finish are equally accurate (see Details).

## Validation

  Servers:

  ```bash
  # Default: DeepGEMM stays off for the FP8 linear layers
  vllm serve Qwen/Qwen3.5-35B-A3B-FP8 --port 8000 --kv-cache-dtype fp8 --max-model-len 4096

  # Opt-in
  vllm serve Qwen/Qwen3.5-35B-A3B-FP8 --port 8000 --kv-cache-dtype fp8 --max-model-len 4096 \
      --linear-backend deep_gemm

Measurements, three runs of each on each server:

  ```bash
  python3 tests/evals/gsm8k/gsm8k_eval.py --port 8000

  lm_eval --model local-chat-completions \
      --model_args model=Qwen/Qwen3.5-35B-A3B-FP8,base_url=http://127.0.0.1:8000/v1/chat/completions,num_concurrent=64,tokenizer_backend=none \
      --tasks gsm8k --apply_chat_template \
      --gen_kwargs '{"max_gen_toks": 256, "chat_template_kwargs": {"enable_thinking": false}}'
  ```

  | Server | `gsm8k_eval.py` | lm-eval `gsm8k` |
  |---|---|---|
  | Default | 0.788 / 0.775 / 0.786 | 0.901 / 0.901 / 0.898 |
  | `--linear-backend deep_gemm` | 0.751 / 0.745 / 0.739 |  0.901 / 0.901 / 0.905 |

## Details

These measurements used vLLM v0.28.0, which is older than this branch. For the DeepGEMM server, I modified the v0.28.0 source code to remove the model types from the auto-disable list. The run of this branch in Validation shows the same pattern: a drop with the plain-text prompt, and none with the chat template. So the version does not change the conclusion.

### Setup

- `Qwen/Qwen3.5-35B-A3B-FP8` on one B200, vLLM v0.28.0, BF16 KV cache, default scheduler limits.
- Three servers. All run the MoE experts with `FLASHINFER_TRTLLM`, and differ in the linear layers and in where E8M0 scales are used:

  | Server | Linear layers | E8M0 scales |
  |---|---|---|
  | Default | CUTLASS | MoE inputs |
  | DeepGEMM | DeepGEMM | MoE inputs and linear layers |
  | `VLLM_USE_DEEP_GEMM=0` | CUTLASS | None |

- Every check runs the 1,319 test questions 5-shot with greedy decoding, three times on each server.
- The probe is my script for looking inside `gsm8k_eval.py`'s score, which reports only the total. The probe imports that script's prompts, output limit, stop strings, and answer extraction, and sends the same requests. It saves every response with the two most likely tokens at each step and their log-probabilities. These show how each response ended, and how close greedy decoding came to choosing the other token.

### Accuracy

Mean of three runs, with the lowest and highest in parentheses.

| Check | `VLLM_USE_DEEP_GEMM=0` | Default | DeepGEMM |
|---|---:|---:|---:|
| `gsm8k_eval.py` | 80.0% (79.4–81.1) | 79.8% (78.2–81.4) | 71.1% (70.7–71.7) |
| Probe | 80.9% (80.4–81.3) | 78.9% (78.2–79.9) | 71.0% (70.0–72.1) |
| Probe, 1,024 tokens | 85.6% (85.4–86.1) | 84.9% (83.5–85.7) | 75.3% (74.8–76.0) |
| lm-eval `gsm8k` | 90.0% (89.8–90.1) | 90.7% (90.4–90.9) | 90.2% (89.5–90.7) |

- `gsm8k_eval.py` and the probe send the same plain-text prompt, with a 256-token output limit unless noted.
- lm-eval uses the chat template with thinking off.

### Where the answers are lost

Answers that finish are 96–97% correct on every server. DeepGEMM loses accuracy because more of its responses never finish. The probe's responses, averaged over three runs:

| Server | Reasoned | Empty block | No `<think>` | Cut off | Stopped while thinking | Ended | Accuracy of ended |
|---|---:|---:|---:|---:|---:|---:|---:|
| `VLLM_USE_DEEP_GEMM=0` | 163 | 1,153 | 3 | 188 | 47 | 1,084 | 96.5% |
| Default | 196 | 1,122 | 1 | 204 | 58 | 1,057 | 96.5% |
| DeepGEMM | 313 | 1,003 | 3 | 256 | 122 | 941 | 96.8% |
| `VLLM_USE_DEEP_GEMM=0`, 1,024 tokens | 163 | 1,153 | 3 | 109 | 54 | 1,156 | 95.9% |
| Default, 1,024 tokens | 173 | 1,146 | 0 | 107 | 61 | 1,151 | 96.2% |
| DeepGEMM, 1,024 tokens | 322 | 995 | 2 | 158 | 158 | 1,003 | 96.0% |

The first three columns count what the response did after `<think>`. The next three count how it ended. Each group adds up to 1,319.

- **Reasoned**: wrote text inside the thinking block.
- **Empty block**: wrote `<think>`, a blank line, and `</think>`, then answered.
- **Cut off**: hit the output limit.
- **Stopped while thinking**: wrote `Question`, one of `gsm8k_eval.py`'s stop strings, before closing the block.
- **Ended**: finished the answer, nearly always with `<|endoftext|>` right after `#### N`.

Compared with the default server, DeepGEMM reasoned in 117 more responses per run, left 116 more unfinished, and got 104 fewer correct. With 1,024 tokens, it still left 148 more unfinished.

### Why DeepGEMM reasons more often

The probe saves the log-probabilities of the two most likely tokens at every step. At the token right after `<think>`, those two are `\n\n`, which leads to an empty block and an answer, and `\n`, which starts reasoning. For each question, the gap is log p(`\n\n`) − log p(`\n`), in nats. A positive gap means the model answers at once, and a negative gap means it reasons.

1. **The choice is nearly a tie.** Across all questions and runs, the gap was never larger than 0.625 nats in either direction, and most reasoning started from an exact tie.
2. **DeepGEMM moves the gap toward reasoning.** Pairing each question across a default run and a DeepGEMM run, the gap is about 0.055 nats lower on average with DeepGEMM, in every run pair. Between two runs of the same server, the average change is 0.006 nats or less.
3. **That token is where the runs split.** Most questions that the default server answered correctly and DeepGEMM did not, 230 of 251, first differed at the token right after `<think>`.
4. **lm-eval never reaches this choice.** With the chat template and thinking off, the prompt already ends with a closed `<think></think>` block.
