# [CI] Keep vLLM log propagation on through the first LLM init in caplog_vllm

[Upstream PR](https://github.com/vllm-project/vllm/pull/61535) · state: closed · merged: True

## Original PR description



## Overview

Fixes `:nvidia: (H200 MIG 35GB) Entrypoints Integration (Multimodal) shard 1/2`. It has failed on every main build since #61477 sharded the step (94629, 94631, 94632, 94633, 94635, 94636), each time at `test_mm_cache_stats[lru-image_urls0]` with `assert 0 == 1`. Example: https://buildkite.com/vllm/ci/builds/94629#01a13792-397c-4bfb-a00a-3ab1f367640a

## Claims

- `caplog_vllm` now captures vLLM logs even when its test is the first in the process to build an `LLM`.
- This replaces the per-test workaround #61477 added to `test_mm_cache_external_injection.py`. Every `caplog_vllm` user is covered, about 180 call sites.
- Test-only change.

## Validation

Ran both test files in one fresh pytest process, which is what the shard does, on an H200. CI image for main `87e7dce3a7`, which fails in CI:

| | `pytest entrypoints/multimodal/llm/test_mm_cache_stats.py entrypoints/multimodal/llm/test_mm_cache_external_injection.py` |
|---|---|
| main | `1 failed, 4 passed`: `test_mm_cache_stats[lru-image_urls0]`, the same failure as CI |
| this PR | `5 passed` |

## Details

**Root cause.**
1. `caplog_vllm` relies on vLLM records propagating to the root logger. Its dependency `temporary_enable_log_propagate` sets `propagate=True` on the `vllm` logger before the test runs.
2. The test then builds an `LLM`. `configure_logging_if_needed` sees a new logging config and re-runs `dictConfig(DEFAULT_LOGGING_CONFIG)`, which sets `propagate=False` on the `vllm` logger.
3. After that, `do_log_stats()` writes to the console but nothing reaches `caplog`, so `len(caplog_vllm.records)` is 0.

This only happens when the test is the first in the process to configure logging. Before #61477, earlier tests in the same process had already done it. In the new shard, `test_mm_cache_stats` is first. #61477 hit the same thing in `test_mm_cache_external_injection.py` and worked around it inside that test.

**Fix.** The fixture also sets `propagate=True` in `vllm.logger.DEFAULT_LOGGING_CONFIG` for its duration, using `monkeypatch.setitem`. A reconfiguration during the test then keeps propagation on. `monkeypatch` restores both values afterwards, as the old manual restore did.

Not a duplicate: I searched open PRs for `test_mm_cache_stats`, `caplog_vllm` and log propagation, and found nothing related.
