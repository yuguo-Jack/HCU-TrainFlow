# [Rust Frontend] Match reasoning delimiters by token identity

[Upstream PR](https://github.com/vllm-project/vllm/pull/62892) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

Make the Rust reasoning parsers built on `DelimitedReasoningParser` (Qwen3, DeepSeek R1 / V3 / V4 / V4.1, GLM-4.5 / 4.7, Kimi K2, MiMo, Kimi, Cohere, Seed-OSS, MiniMax M2 / M3, Step3 / 3.5 / 5, Nemotron V3, Hy) end reasoning only at the dedicated end-delimiter token, so `</think>` written with ordinary tokens (the model quoting the tag) stays reasoning. This matches how the Python parsers detect these delimiters while streaming. Independent of the DSML tool-parser stack (#62874 → #62875); no shared files.

## Claims

- An ordinary-token `</think>` (or the family's end delimiter) inside reasoning no longer ends reasoning and leaks the rest of the reasoning into content.
- An ordinary-token start delimiter in content stays content.
- An ordinary partial delimiter (`</thi`) streams immediately instead of being held back.
- MiniMax M3 drops a response-leading `</mm:think>` only when it is the dedicated token.
- Output with the dedicated tokens parses exactly as before.

## Details

**Two commits.**

1. *Test-only:* reasoning tests fed `DecodedText::unattributed` text, gave delimiter tokens synthetic IDs, or had mock engines emit `<think>` as byte tokens. They now feed output in the serving shape: `vllm_tokenizer::test_utils::decode_chunks` encodes the chunks with the test tokenizer's configured tokens, decodes them through the incremental decoder, and splits at the chunk boundaries. Parser behavior is unchanged in this commit; the full suite passes on the current implementation.
2. *Fix:* `DelimitedReasoningParser` builds its delimiters, with their optional framing text, as `Marker`s guarded by the token IDs the builder already resolves (a family whose tokenizer lacks a delimiter token already fails construction with `MissingToken`), and matches them through the shared marker scanner over the attributed buffer, the utilities added for Kimi K3 in #58358. MiniMax M3's drop of a response-leading `</mm:think>` uses the same guarded marker.

**Root cause.** The parser found the delimiter with `str::find` and held back partial matches with `partial_prefix_len`, so it could not tell the dedicated token from the same bytes spelled by ordinary tokens.

**Why token identity, and why for every family.** The Python parsers already detect these delimiters by token ID when streaming. The parser engine treats `token_id_terminals` that resolve in the vocabulary as strict once it has seen token IDs (`streaming_parser_engine.py`, `_process_lex_tokens`), and the legacy thinking parsers end reasoning only when `end_token_id in delta_token_ids`. Feeding `A ` + ordinary-token `</think>` + ` B` + dedicated `</think>` + `C` through `ParserManager` on `main` with the real tokenizers gives reasoning `A </think> B` / content `C` when streaming for `deepseek_v4`, `deepseek_v3`, `deepseek_r1`, `qwen3`, `glm45`, `glm47`, `mimo`, `kimi_k2`, `minimax_m2`, `seed_oss`, `step3p5`, and `step5`. Two exceptions:

- Python's non-streaming path splits by text, because `DelegatingParser.parse` calls `extract_reasoning(model_output)` without token IDs. So one output parses differently in Python depending on `stream`. The Rust parser uses one state machine for both and follows the streaming behavior.
- The legacy Python `minimax_m3` reasoning parser matches by text in both paths, while `</mm:think>` is an added token; the M3 engine parser config already lists `<mm:think>` / `</mm:think>` as token-ID terminals.

DeepSeek's own streaming output parser for V4 / V4.1 also matches `</think>` only as the added token ([deepseek-recipe `output_parser.rs`](https://github.com/deepseek-ai/deepseek-recipe/blob/935817c66f5d6e64838f419692545f06787e485f/deepseek-recipe/src/stream/output_parser.rs#L338-L408)).

**Known limitations:**

- The reasoning region of the output grammar still ends at the delimiter text. Under a reasoning-aware constrained decode, an ordinary-token `</think>` would end reasoning for XGrammar but not for the parser. The model strongly prefers the dedicated token, so this is unlikely. A token-level end boundary (supported by XGrammar 0.2.7) is a separate change.
- Callers must feed attributed output; fed unattributed text, the parser never crosses a delimiter. The serving path and the chat roundtrip harness are attributed.

Not a duplicate: open PRs touching reasoning parsers add or fix individual Python or Rust parsers; none changes how the Rust delimited parser matches delimiters.
