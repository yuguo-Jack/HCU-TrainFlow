## Purpose
The purpose is to allow use of NVFP4 quantized models across multiple platforms by providing default a NVFP4 dequantization code path.

Currently this a WIP, but it does work, providing inference capability of NVFP4 W4A4 or W4A16 quantized models, tested on a a few different MoEs and Dense models.

This is a transfer from my custom implementation in a highly modified VLLM branch so it will take time to correctly extract the working code for NVFP4 emulation and disentangle from the other modifications I've made in that branch.

There remain a few things to be finished:
- 1: It applies the global scalar to the group scalar once and casts to FP16 instead of applying at run time in place. This saves the compute at the cost of memory miss-alignment. The net result was +10% decode speed and greater than 10% prefill speed, the cost, is a violation of the 128b AMD memory transfer limitation, requiring extra memory activity.
- 2: The fused kernel is not right, flat out. It runs poorly, but it does run. There is something escalating the compute requirements far beyond what it should I need to identify and correct.

## Test Plan
Profile more models for quality and speeds to ensure this is performing as expected for 4 bit models.

## Code Review

This pull request introduces NVFP4 emulation to allow NVFP4 quantized models to run on a wider range of hardware. The changes add emulation paths for both linear and MoE layers, including a new Triton kernel for fused MoE. My review found two critical issues related to the configuration of the emulation path for MoE layers, in both `modelopt` and `compressed-tensors` formats. The quantization configuration is not correctly set up, which will lead to runtime errors. I've provided suggestions to fix these issues.

![critical](https://www.gstatic.com/codereviewagent/critical.svg)

The `get_fused_moe_quant_config` method returns `g1_alphas=None` for the emulation path, which is incorrect. The `apply` method for `CompressedTensorsW4A4Nvfp4MoEMethod` should use an emulation path that calls `fused_experts`, which in turn uses `dequant_nvfp4`. This dequantization function expects a `global_scale` tensor, which is derived from `g1_alphas`. Passing `None` will cause a runtime error.

Since `process_weights_after_loading` bakes the global weight scale into the group scales for the emulation path, the `global_scale` for dequantization should be 1.0. Therefore, `g1_alphas` and `g2_alphas` should be initialized to tensors of ones.

Additionally, the `apply` method for this class is missing the emulation path. The computation of `g1_alphas` and `g2_alphas` in `process_weights_after_loading` also appears to be dead code for the emulation path and should probably be removed to avoid confusion.

```python
        if self.use_emulation:
            return nvfp4_moe_quant_config(
                g1_alphas=torch.ones(layer.num_experts,
                                     device=layer.w13_weight_scale.device),
                g2_alphas=torch.ones(layer.num_experts,
                                     device=layer.w2_weight_scale.device),
                a1_gscale=layer.w13_input_scale_quant,
                a2_gscale=layer.w2_input_scale_quant,
                w1_scale=layer.w13_weight_scale,
                w2_scale=layer.w2_weight_scale,
            )
```

- gemini-code-assist[bot] · comment · 2025-12-19T03:32:07Z · [source](https://github.com/vllm-project/vllm/pull/31001#discussion_r2633474659)

File: `vllm/model_executor/layers/quantization/modelopt.py` · line 1644

![critical](https://www.gstatic.com/codereviewagent/critical.svg)

The `fused_experts` call for the emulation path will fail because `self.moe_quant_config` is not correctly configured. `ModelOptNvFp4FusedMoE` inherits `get_fused_moe_quant_config` from `ModelOptFp8MoEMethod`, which returns an FP8 configuration. This means `nvfp4_scheme` will be `None` in `fused_experts`, and the NVFP4 dequantization path will not be taken. The `uint8` quantized weights will be passed to a matmul operation that expects floating-point tensors, causing a runtime error or incorrect results.

To fix this, `ModelOptNvFp4FusedMoE` needs its own `get_fused_moe_quant_config` method that returns a `nvfp4_moe_quant_config`. It also likely needs a `process_weights_after_loading` method to prepare the scales for the emulation path, similar to what's done for other quantization schemes.
