# [Core][KV Connector][Mooncake] Support MRV2 prefill PCP in Mooncake

[Upstream PR](https://github.com/vllm-project/vllm/pull/49109) · state: open · merged: False

## Original PR description

## Overview

Enable producer-only MRV2 prefill context parallelism for Mooncake by selecting PCP0 as the sender for each replicated TP/PP KV shard. Preserve all-worker save completion so a non-sending replica does not break connector composition.

## Claims

- Only PCP0 owns the producer bootstrap/listener/transfer path; replicas do not register duplicate TP/PP identities or send duplicate KV.
- All workers report delayed-save completion. Noncanonical ranks acknowledge only final block-bearing metadata, not the earlier allocation announcement; polling consumes that completion once.
- Producer PCP requires DCP=1. Consumers and `kv_both` require PCP=1. The documented setup uses PP=1 and DP=1.
- No model, attention kernel, scheduler, or replay workaround is included.

## Details

With DCP1, MRV2 gathers the latent KV before cache insertion, so PCP ranks at the same TP/PP position retain replicated logical KV. Mooncake discovery identifies DP/TP/PP workers without a PCP coordinate. Letting every replica register/send therefore collides on ownership and duplicates transport.

The completion lifecycle is separate from sender ownership:

1. Scheduler allocation announces a transfer with empty blocks; replicas must not acknowledge completion yet.
2. Final block-bearing metadata follows producer completion and requests delayed block release. Noncanonical replicas acknowledge this metadata once; PCP0 retains responsibility for the actual transfer.
3. D requests KV from the canonical worker. The scheduler waits for all local worker completions before freeing the producer's blocks.

The default world-size completion protocol follows the composability invariant in merged NIXL [#53903](https://github.com/vllm-project/vllm/pull/53903). Dynamic remote fan-out/fan-in accounting remains unchanged.

Duplicate/reuse checks: ordinary Mooncake PCP remains tracked in [#60523](https://github.com/vllm-project/vllm/issues/60523); [#61974](https://github.com/vllm-project/vllm/pull/61974) excludes PCP; [#45340](https://github.com/vllm-project/vllm/pull/45340) addresses aligned CP-sharded layouts rather than this asymmetric replicated producer setup. [#62916](https://github.com/vllm-project/vllm/pull/62916) separately addresses multi-node PCP engine-ID synchronization. None replaces this ownership change.

Yes, I think we can rely on pcp_rank > 0 not participating in KV sending here. In the merged MRV2 PCP implementation [#46570](https://github.com/vllm-project/vllm/pull/46570), PCP splits the prefill computation, but the latent K/V is all-gathered across the PCP group before cache insertion. So the PCP ranks end up holding replicated copies of the same logical KV cache. Having the other PCP ranks send as well would just duplicate the transfer and completion notification, which is why we use pcp_rank == 0 as the canonical sender for each TP/PP shard.

My understanding is that `need_send` and `pull_tasks_count` are mainly about dynamic remote fan-out and fan-in, especially for heterogeneous TP/PP. We could account for PCP there, but both paths would then need special handling for the non-sending PCP replicas, and it would mix local ownership with remote transfer topology. Using `get_finished_count()` to express the number of local workers that can actually report finished_sending seems a bit clearer, so the producer count becomes world_size / pcp_size.
