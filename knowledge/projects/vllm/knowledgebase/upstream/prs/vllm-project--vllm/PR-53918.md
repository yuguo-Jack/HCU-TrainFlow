# [ROCm][Perf] Enable AITER fuse_qk_norm_rope_kvcache for Gemma4 (head_dim 512 + V-norm)

[Upstream PR](https://github.com/vllm-project/vllm/pull/53918) · state: open · merged: False

## Original PR description

## Purpose

Enable the AITER fused QK-norm + RoPE + KV-cache path (`fuse_qk_norm_rope_kvcache` / `QkNormRopeKvCacheFusionPass`) for **Gemma4** (`RedHatAI/gemma-4-31B-it-FP8-block`). Gemma4 was blocked by two kernel-side gaps and, as it turned out, two pattern-matching gaps:

1. **head_dim 512** — Gemma4's full-attention layers use `head_dim=512`; the pass only supported `{64,128,256}`.
2. **Weightless V-norm** — every Gemma4 attention layer applies `v_norm = RMSNorm(head_dim, has_weight=False)`; the fused op wrote V to the cache un-normalized and the pattern passed V through un-normed, so it never matched.
3. **`layer_name` as a graph input** — under the default `VLLM_USE_LAYERNAME=1` (torch ≥ 2.11 opaque `LayerName`), the pattern's baked constant `layer_name` never matched; threaded it as a pattern input (mirrors `RopeKVCacheFusionPass`).
4. **Two attention shapes** — sliding (256) and full (512) collapse into a duplicate pattern once `layer_name` is a wildcard; fixed by restoring the `split_with_sizes` sizes as literals so each shape stays a distinct, correctly-replaced pattern.

This is the **AITER KV-cache** fusion path (`rope_common.h` / `fused_qk_norm_rope_cache_pts_quant_shuffle`), distinct from #53115 (the non-AITER `fused_qk_norm_rope` / `libtorch_stable` norm+RoPE path) and complementary to #52901 (AITER gated-QKV variant for Qwen3-Next, which touches the same pass for a different feature).

**Depends on** a companion ROCm/aiter change adding head_dim 512 + a weightless V-norm to `fused_qk_norm_rope_cache_pts_quant_shuffle` (ROCm/aiter#5027). The `SUPPORTED_FUSED_QK_NORM_ROPE_KVCACHE_HEAD_DIMS` guard already skips 512 layers when the kernel lacks it.

## Test Plan

- `pytest tests/compile/passes/test_rocm_aiter_qk_norm_rope_kvcache_fusion.py` — extended with Gemma4's `gemma4_sliding` (256) and `gemma4_full` (512) shapes and a `has_v_norm` parametrization.
- E2E on `RedHatAI/gemma-4-31B-it-FP8-block`, `ROCM_AITER_UNIFIED_ATTN`, `--kv-cache-dtype fp8`, `--compilation-config '{"splitting_ops": [], "pass_config": {"fuse_qk_norm_rope_kvcache": true}}'`; gsm8k via `lm_eval`.

## Test Result

- Fusion replaces **60/60** attention layers (both head_dim 256 and 512) under the default `VLLM_USE_LAYERNAME=1`. Trace shows a single fused `mrope_utils::fused_mrope_rms_kv_kernel` per attention layer and **0 separate `reshape_and_cache` / `rotary_embedding` / attention rms_norm** kernels in decode.
- **Correctness — gsm8k (5-shot, `lm_eval`, limit 500):** baseline strict 0.722, `splitting_ops:[]`-only 0.732, decode-fused 0.706, full-fused (prefill+decode) 0.734 — all within ±0.02, i.e. statistically equivalent. Decode fusion additionally validated on the full 1319-sample set: flexible 0.729 / strict 0.720 vs 0.726 baseline. The full-fused number confirms the fused kernel is also correct on the ragged (variable-length) prefill/mixed layout, not just uniform decode.

### Serving performance

`RedHatAI/gemma-4-31B-it-FP8-block`, 1×MI300X, `ROCM_AITER_UNIFIED_ATTN`, `--kv-cache-dtype fp8`, input 1024 / output 256, `--num-prompts 8×conc`, median across seeds 0/1/2. Two fusion configs, both with `splitting_ops: []`:

- **decode-fused** — default `rope_kvcache_fusion_max_token_num` (256): fuses decode only (the pass's out-of-box behavior).
- **full-fused** — `rope_kvcache_fusion_max_token_num = 16384`: also fuses prefill / mixed batches (opt-in).

Takeaways:

- Decode fusion gives a consistent **+3 to +7% output throughput** and **−6 to −9% ITL**, largest at low–mid concurrency (kernel-launch overhead dominates) and tapering toward c=64 as the step becomes GEMM-bound.
- Extending the fusion into prefill (**full-fused**) is **net-positive, not merely neutral**: it matches or slightly beats decode-only throughput at every point and gives the best TPOT at high concurrency (c=64: −4.2% vs −0.7%). It stays opt-in via `rope_kvcache_fusion_max_token_num`; the default remains decode-only.
- **Control:** `splitting_ops: []` with the fusion **off** is within ≤1% of the default baseline across the sweep, so the gains are from the fusion, not the splitting-ops change.
- ITL (median of individual token gaps) is the more stable decode-latency metric here; the c=8 TPOT baseline is a noisy point (TPOT is a per-request mean, sensitive to scheduling), so read the −18.5% at c=8 with that caveat.
- **TTFT is high-variance across seeds.** For decode-fused the prefill path is unchanged, so its ≈0% TTFT deltas are expected. For full-fused the +53% spike at c=8 is an outlier that does not fit the trend (its other points are −2.1% / −1.3% / +3.1% / −1.9%) and decode-fused is −0.2% at the same point — so it reads as noise, not a systematic prefill regression. Treat the TTFT column as "no material change," pending more seeds.
- Kernel-level: the fused op is ~2× cheaper than the separate rms_norm×3 + reshape_and_cache it replaces, and stays inside the CUDA graph (no host stall).

Isn't returning `rms_norm(v)` in the pattern but the raw qkv slice of `v` in the replacement relying on the attention backend only reading V from the KV cache?

That holds for `ROCM_AITER_UNIFIED_ATTN`, but `ROCM_AITER_FA` also opts into this fusion, and its prefill/extend paths read the value argument directly (`flash_attn_varlen_func(v=prefill_value)`). Gemma4 can't hit this because its head_dim 512 layers rule out FA.

But if the test model also ran unified_attention_with_output on a prefill-shaped batch (`BatchSpec(seq_lens=[64], query_lens=[64])`) with a <=256 head size, I'd expect ROCM_AITER_FA to diverge from the unfused path when `v_norm=True`. If that's right, could the `v_norm` variants be registered only for backends that read V from the cache, with a comment like the one on `_unfused_kv_views` in the MRoPE path?
