# [Bugfix] Reset stale cuMem error state at allocation entry

[Upstream PR](https://github.com/vllm-project/vllm/pull/60081) · state: open · merged: False

## Original PR description



## Overview

Reset stale cuMem error state at the start of `my_malloc`, so a previous native failure does not reject the next valid allocation. Add a CUDA regression test that fails without the fix.

Related to the allocation-entry portion of item 3 in #36651. [The issue's status update](https://github.com/vllm-project/vllm/issues/36651#issuecomment-5892039123) identifies sticky `error_code` as still outstanding. cc @aoshen02

## Claims

- A previous native failure no longer poisons a subsequent valid cuMem allocation.
- The reset occurs before `ensure_context`; current-operation errors still reach the existing error checks.
- The regression checks successful allocation, allocator pointer tracking and tensor contents after a real driver error, without exhausting VRAM or directly writing the error variable.

## Details

`CUDA_CHECK` updates process-global `error_code` on failure, but success does not clear it. Previously, `my_malloc` could perform a successful granularity query and then return null because of an earlier error. Source reasoning suggests a genuine `cuMemCreate` failure can leave this state too; that natural OOM sequence was not tested here.

The test deterministically produces a native zero-sized VA reservation error through `my_malloc(0, ...)`, then allocates through the normal Torch cuMem pool. Zero-sized reservation failure was observed on the tested driver; this is not a claim about ordinary zero-element Torch allocations. Python create/map and unmap/release wrappers clear errors before raising, so this test deliberately exercises the native allocator entry instead.

Same-day open-PR searches on 2026-10-05 for `36651 in:body`, `my_malloc`, `cumem error_code` and `"cumem_allocator"`, followed by inspection of the related diffs, found no identical entry fix. #36535 already proposes resets in create/map, unmap/release and free, but not `my_malloc`; this follows that error-isolation idea at the missing allocation entry. #44866 addresses allocation-failure cleanup, and #59228 addresses freeing asleep allocations. Neither is replaced by this change.

Scope is intentionally limited: sleep/wake stale-error handling, resource cleanup and `my_free` sizing are unchanged. The reset is an unsynchronized write to process-global state; cross-thread allocator serialization was not established, and this does not guarantee concurrent error isolation. ROCm runtime was not tested; the new test skips non-CUDA platforms. The original production workloads in #36651 were not reproduced.
