# [Bugfix] Preserve independent tokenizer code_revision in snapshot resolution

[Upstream PR](https://github.com/vllm-project/vllm/pull/61272) · state: closed · merged: True

## Original PR description

## Overview

Preserve an independent Hugging Face tokenizer `code_revision` when resolving a Hub ID to a local data snapshot. This applies the same guard the processor path already has (introduced in #60825) to the tokenizer resolver.

## Claims

- Before this change, `resolve_tokenizer_args` rewrote `tokenizer_name` to a data-revision snapshot unconditionally. Transformers reads dynamic tokenizer code from a local directory as-is, so a `code_revision` distinct from the data revision was silently shadowed: the code from the data snapshot was loaded, and invalid/older code revisions were silently accepted instead of rejected.
- After this change, default and matching code/data revisions keep the snapshot optimization (byte-identical token IDs vs direct Transformers loading in the regression fixture), while a distinct code revision is passed to Transformers with the Hub ID intact.

## Validation

Linux x86_64 container (Ubuntu, Python 3.12.13, Torch 2.13.0+cpu, Transformers 5.19.0, HF Hub 2.2.0), native source build of this branch (`VLLM_TARGET_DEVICE=cpu`, editable install). Normal production imports and `get_tokenizer` were exercised; no AST extraction or tokenizer stubs.

Pinned fixture: `hf-internal-testing/test_dynamic_tokenizer` at data revision `08a35780b7a78794436d8654aafa26ee0165c149` (repo has exactly two commits; `73293ac504e43f4a895688b57c65cebe24f01a38` predates the tokenizer code and contains only `.gitattributes`).

- With the fix: `pytest tests/tokenizers_/test_basic.py -q -p no:cacheprovider` → **10 passed** (6 pre-existing + 4 new: 2 parametrized rejection cases, matching/default control pair, and a resolver-contract test).
- A/B discriminative check: reverting only the `code_revision` guard in `vllm/tokenizers/registry.py` and re-running → **3 failed** (`test_tokenizer_code_revision_rejects_missing_code[unknown-revision]` and `[revision-without-code]` both `DID NOT RAISE OSError`; `test_tokenizer_code_revision_distinct_from_revision` assertion on kept Hub ID), 2 passed (matching/default controls). Guard restored, 10 passed again.
- `pre-commit run --files vllm/tokenizers/registry.py tests/tokenizers_/test_basic.py`: passed (Ruff, mypy, SPDX, test tethering included).
- `git diff --check`: passed.

### How to test

```bash
.venv/bin/python -m pytest tests/tokenizers_/test_basic.py -k code_revision -q -p no:cacheprovider
pre-commit run --files vllm/tokenizers/registry.py tests/tokenizers_/test_basic.py
```

Manual reproduction: call `get_tokenizer` with `tokenizer_mode="hf"`, `trust_remote_code=True`, the pinned data revision above, and either `code_revision="never"` or the older code commit. Before this fix both calls load code from the data snapshot (no error); after the fix both fail with the Transformers missing-revision/missing-code error. With omitted or matching `code_revision`, encoding `"hello world"` remains equal to direct `AutoTokenizer.from_pretrained`.

## Details

`resolve_tokenizer_args` previously resolved every HF tokenizer to a directory pinned to the data `revision`. Dynamic code cannot be re-selected against a local directory, so forwarding `code_revision` in kwargs cannot restore the requested code selection. The fix preserves the Hub ID when the two revisions differ, mirroring the processor path from #60825. This deliberately gives up the snapshot request reduction for independently versioned code, as the processor path already does.

The tests extend the existing tokenizer suite and use its supported `skip_global_cleanup` marker (tokenizers only, no GPU models). They remain wired into the existing tokenizer CI area.

Scope is direct `get_tokenizer(..., code_revision=...)` loading. No `vllm serve --code-revision` regression, inference accuracy improvement, or performance gain is claimed. Full tokenizer-suite, serving E2E, GPU and model evaluations were not run; the targeted validation above must not be read as those results.

Duplicate-work searches covered #60825 references, open PRs matching `code_revision` + tokenizer keywords, and `get_non_weight_snapshot_path`. No open PR for this tokenizer guard was found at the time of checking; nearby #54780 addresses a different caller. AI assistance was used for investigation, implementation, tests and review (Hermes Agent); the submitter reviewed every changed line and ran the tests above.
