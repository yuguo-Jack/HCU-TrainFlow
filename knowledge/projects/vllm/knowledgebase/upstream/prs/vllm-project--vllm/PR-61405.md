# [Bugfix] Pass the INT8 input global scales to the compressed-tensors Marlin MoE

[Upstream PR](https://github.com/vllm-project/vllm/pull/61405) · state: open · merged: False

## Original PR description



## Overview

With `VLLM_MARLIN_INPUT_DTYPE=int8`, compressed-tensors WNA16 MoE models give wrong output on the Marlin MoE backend. This PR passes the INT8 input global scales to the MoE quant config, as the AWQ path does (`auto_awq.py`).

Related: #58326 routes compressed-tensors W4A8-INT MoE checkpoints to this path. #59895 (issues #59403 and #48905) fixes a different problem in `marlin_act_int8_process_scales()`: negative group scales. #49039 changes the INC/AutoRound path.

Duplicate check: I searched the open PRs and issues for `a1_gscale`, `VLLM_MARLIN_INPUT_DTYPE`, "input_global_scale MoE" and "marlin int8 activation MoE". #58326, #57091 and #59895 change nearby code, but none of them passes `a1_gscale` / `a2_gscale` in `compressed_tensors_moe_wna16.py`. All three merge with this PR without a conflict.

AI assistance was used for this PR (Claude Code): the root-cause analysis, the patch, the test, the test scripts and this description. I reviewed every changed line and the test results.

## Claims

- Fixes the wrong output of compressed-tensors INT4 MoE models with `VLLM_MARLIN_INPUT_DTYPE=int8` on the Marlin backend. On main: NLL 12.55 instead of 1.04, MTP acceptance 0 %, empty content for 8 of 8 greedy prompts.
- With the fix, the prompt log-likelihood is within 0.16 % of BF16 activations, and the MTP acceptance is 70 % (BF16: 72 %).

## Details

Root cause:

1. With INT8 activations, `_process_weights_marlin()` (`fused_moe/oracle/int_wna16.py`) calls `marlin_act_int8_process_scales()` for w13 and w2 when the layer has more than one group. That function scales the group scales to a maximum of 4096, stores them as int16, and returns the factor `max / 4096`.
2. `CompressedTensorsWNA16MoEMethod.process_weights_after_loading()` registers the factors as `w13_input_global_scale` and `w2_input_global_scale`.
3. `CompressedTensorsWNA16MoEMethod.get_fused_moe_quant_config()` does not pass them to `make_wna16_moe_quant_config()`. `MarlinExperts` multiplies the per-token activation scales by `a1_gscale` / `a2_gscale`. Without them, the outputs of both GEMMs are wrong by the factor.

With BF16 activations, and with the other WNA16 backends, the layer has no such attributes, so `getattr()` returns `None` and nothing changes.

Scope: the bug occurs whenever Marlin runs the MoE with INT8 activations: with `--moe-backend marlin`, or on a GPU where Marlin is the first supported WNA16 MoE backend (Humming outranks Marlin only on compute capability 9.0).
