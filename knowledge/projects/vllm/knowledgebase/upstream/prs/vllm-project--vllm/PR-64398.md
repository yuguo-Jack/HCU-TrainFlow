# [Quantization] Support CT channel FP8 requantization

[Upstream PR](https://github.com/vllm-project/vllm/pull/64398) · state: open · merged: False

## Original PR description




## Overview

Allow symmetric per-channel compressed-tensors FP8 linear checkpoints to use the existing online re-quantization targets. This implements the compressed-tensors channel-FP8 source portion of [RFC #59062](https://github.com/vllm-project/vllm/issues/59062).

## Claims

- Decode checkpoint-layout weights before kernel-specific processing, then reuse existing target quantization and source-parameter cleanup.
- Support MXFP4 and FP8-block targets in real-model regression coverage; keep unsupported source schemes explicitly rejected.
- Add a targeted H200 MIG CI step and document an MXFP4/Marlin example for Hopper.

## Validation

Tested on 2×H100 80GB, PyTorch 2.14.0+cu130, compressed-tensors 0.17.0, FlashInfer 0.7.2.post1 and Humming 0.1.18. The Python checkout uses an ABI-compatible precompiled wheel from `0beab6c25`; no C++/CUDA code is changed.

Hugging Face downloads were unavailable. Local model tests used complete, trained Qwen3-0.6B and Qwen3-4B weights exported with compressed-tensors' symmetric per-channel FP8 min/max quantizer. The results below describe these local exports. The committed CI test targets `RedHatAI/Qwen3-0.6B-FP8-dynamic`.

```bash
# local_model_test substitutes the local checkpoint path only.
.venv/bin/python -m pytest -p local_model_test -v \
  tests/quantization/test_online.py::test_compressed_tensors_fp8_source_dequantization \
  tests/quantization/test_online.py::test_weight_loading_requantization \
  tests/quantization/test_online.py::test_compressed_tensors_channel_fp8_requantization
```

The final checkout passes all 12 cases. Without the implementation, the same MXFP4 LLM regression fails during loading:

```text
NotImplementedError: The quantization method ...CompressedTensorsLinearMethod
does not implement dequantize_weight, so re-quantization from this checkpoint
is not supported.
```

For an independent reference, compressed-tensors decoded the 0.6B checkpoint into BF16; the existing BF16→MXFP4 path then used the same Marlin backend. Inputs cover batches 1/8/32, short and long prompts, and 32 generated tokens per request.

| Comparison | Result |
| --- | --- |
| Original vs patched native FP8, TP1 eager | Identical parameters and 41/41 token sequences |
| CT→MXFP4 vs independently decoded BF16→MXFP4, TP1 eager | All 112 linear layers' weights/scales identical; 41/41 token sequences |
| Reference comparison, TP2 eager / TP1 compile+graphs | Weights/scales identical; 41/41 token sequences in each configuration |
| Reference comparison, TP2 compile+graphs | Weights/scales identical; 40/41 token sequences with default execution, 41/41 with batch invariance enabled |

Initial TP1 eager comparisons also had identical logprobs. Repeated runs show logprob differences, including on the unchanged native path and with batch invariance enabled; token equality is not a bitwise-logprob claim. Raw comparison results retain these differences and the default TP2 sequence mismatch.

GSM8K evaluation: all 1,319 test questions, first five training examples as fixed completion-style demonstrations, greedy decoding, 1,024 generated-token budget, maximum context 4,096, seed 11, no chat/thinking template.

| Local Qwen3-4B configuration | Correct | Accuracy | Length-truncated answers |
| --- | ---: | ---: | ---: |
| Original native CT FP8 | 1,140 / 1,319 | 86.43% | 29 |
| Patched native CT FP8 | 1,145 / 1,319 | 86.81% | 27 |
| Patched CT FP8→MXFP4, Marlin | 1,046 / 1,319 | 79.30% | 179 |

Native A/B evaluations were separate runs with batch invariance disabled. Their small difference is run-to-run variation, not an accuracy improvement attributed to this patch. MXFP4 has a clear accuracy/length-budget tradeoff here. In the 0.6B model, the 112 linear layers' stored weight/scale parameters decrease from 421.31 MiB to 223.13 MiB; embeddings, KV cache and runtime buffers are excluded.

Baseline and patched GSM8K runs used `df028dffa` as their common base. The relevant quantization and Qwen model code is unchanged by the final rebase; regression tests and model/reference controls were rerun after rebasing. Pre-commit checks pass, including mypy, documentation lint, Buildkite step keys and test tethering. Markdown lint used the pinned hook with the available Node runtime because its automatic Node download stalled.

## Details

`CompressedTensorsLinearMethod` delegates to an optional scheme-level `dequantize_weight` method. `CompressedTensorsW8A8Fp8` accepts symmetric channel weights and evaluates `weight.float() * weight_scale.float()`, returning `layer.orig_dtype` in checkpoint `(N, K)` layout. This runs before source PWAL, which would otherwise transpose or repack the tensors. Existing online methods retain responsibility for target conversion and cleanup.

Scope is linear W8A8 symmetric channel FP8. Per-tensor/block-scaled FP8, other compressed-tensors schemes and MoE are unchanged. The source FP8 kernel must still be constructible on the selected device. Open-PR/RFC checks on 2026-10-28 found no equivalent compressed-tensors channel-source adapter; the native `Fp8LinearMethod` work discussed in the RFC is a separate producer.

MXFP4 validation explicitly selects Marlin. Auto-selected Humming encountered an NVRTC compilation error in this environment on both the existing BF16→MXFP4 path and the new CT→MXFP4 path. ROCm/Blackwell and upstream CI have not been run. The H100s were shared with existing workloads, so there is no throughput or latency claim.
