# [Frontend][v0.30.0][Reference only] Backport Messages min_tokens and ignore_eos

[Upstream PR](https://github.com/vllm-project/vllm/pull/65380) · state: open · merged: False

## Original PR description

## Purpose

**Reference-only draft; please do not merge.** Backport the implementation in #65057 (commit `641dd090541c6c1b9488c00c14b601913a0718bb`) to `releases/v0.30.0`, based on `ced6857afa0ea7b2e3f0846a62e1394e90f15607`.

In v0.30.0, `/v1/messages` does not declare or forward `min_tokens` and `ignore_eos`. A P/D proxy cannot therefore apply these controls to its one-token prefill request through this endpoint. This change declares the two vLLM extension fields and forwards them to `ChatCompletionRequest`, allowing existing `SamplingParams` validation and sampling behavior to apply. Defaults remain `min_tokens=0` and `ignore_eos=false`.

The two implementation files match the currently deployed and tested v0.30.0 files byte-for-byte after normalizing Windows line endings:
- `vllm/entrypoints/anthropic/protocol.py`: SHA256 `7244d90e8cae612a3389d9cf296239e025f4f6c1fef6aa5c5c894992defa0539`
- `vllm/entrypoints/anthropic/serving.py`: SHA256 `97042f0f6e5cce9ec6404d2bcd5f447910cf6bef6a9bd3db9e954b852ef198ee`

Backport adaptations: omit newer-main multimodal/watermarking context, omit documentation for the unavailable `/v1/messages/render` route, and document the deployed one-token prefill setting `max_tokens=1, min_tokens=1` (which does not require `ignore_eos=true`).

Related work: #47613 targets `main` and overlaps on `min_tokens`; #65057 is the original reference draft. This is explicitly a release-specific reference requested for an existing deployment, not a competing merge candidate. Searches for open `releases/v0.30.0` PRs mentioning `min_tokens` or `ignore_eos` found none.

- Live Messages validation: `max_tokens=1, min_tokens=2` returns HTTP 400 with the expected `SamplingParams` validation error.
- Controlled badcase sampling on the deployed DeepSeek-V4.1 / Ascend P service: `max_tokens=1`, `temperature=1`, `do_remote_decode=true`; both diagnostic groups use `ignore_eos=true` so sampled EOS remains observable in returned KV metadata. Changing only `min_tokens` produced EOS ID 1 in **6/8** requests with `min_tokens=0`, versus **0/8** with `min_tokens=1`.
- Full proxy regression: five rounds of four original badcases, retaining the clients' `max_tokens=32000` and streaming setting. The proxy's P requests used `max_tokens=1, min_tokens=1, ignore_eos=false`. **20/20** final responses completed successfully with `tool_use`; captured P first tokens had **0 EOS**, **0 unknown token IDs**, and **0 missing KV transfer parameters**. These requests all selected one P endpoint; this is not coverage of every DP instance.
- These are targeted serving regressions, not a general accuracy benchmark or a production failure-rate estimate. Backend KV-transfer behavior and proxy configuration are outside this diff. The backport validation did not restart or change the serving processes.
