# [Metrics] Add delivery counters for the KV event publisher

[Upstream PR](https://github.com/vllm-project/vllm/pull/59797) · state: open · merged: False

## Original PR description

## Overview

Adds Prometheus delivery counters for the KV cache event publisher, so operators can see how many event batches reach the transport, how many are lost to send errors, and whether the outbound queue is backing up. Also fixes a latent `Queue.join()` hang on the publisher's error path.


## Claims

- Three new metrics, picked up automatically by the Production Metrics docs generator:
  - `vllm:kv_event_batches_published` (Counter), batches handed to the transport
  - `vllm:kv_event_batches_errored` (Counter), batches discarded after a send raised
  - `vllm:kv_event_batches_queued` (Gauge), batches waiting to be sent
- Fixes a latent bug in `ZmqEventPublisher._publisher_thread`: `task_done()` was only reached when a send succeeded, so a single failed batch left the queue's unfinished-task count permanently above zero and `Queue.join()` would hang forever. It is now in a `finally`.
- No behaviour change for anything that does not opt in. `EventPublisher.get_stats()` returns `None` by default, so `NullEventPublisher` and third-party publishers are unaffected.

## Validation

Extends `tests/distributed/test_events.py`, which already runs in CI via `.buildkite/test_areas/distributed.yaml` and `.buildkite/test-amd.yaml`. Three tests added:

- `test_null_publisher_reports_no_stats`, the no-op publisher reports no counters.
- `test_publisher_stats_count_published_batches`, published batches are counted and the queue drains to empty.
- `test_publisher_stats_count_send_errors`, an induced `zmq.ZMQError` is counted, and `_event_queue.join()` returns rather than hanging. This is the regression guard for the `task_done()` fix.

## Details

KV cache events are published from the scheduler via a background thread in `ZmqEventPublisher`. When that thread fails to send a batch, the batch is discarded and the only trace is a log line. A subscriber tracking sequence numbers sees a gap, but nothing on the server side quantifies how often this happens or whether the queue is backing up.

Counts are tracked in `ZmqEventPublisher`, exposed through a new `get_stats()` hook on `EventPublisher`, and carried to the frontend on the existing `SchedulerStats` path already used by `kv_connector_stats`. Only the publisher thread mutates the counters and readers tolerate a slightly stale view, so no lock is taken. The publisher reports cumulative counts while Prometheus counters take deltas, so the logger remembers the last value per engine and clamps negative deltas, which keeps the counters correct across a publisher restart.

Impact on core components is kept small: 4 added lines in `vllm/v1/core/sched/scheduler.py` and 3 in `vllm/v1/metrics/stats.py`, with the logic living in `kv_events.py` and `loggers.py`.
