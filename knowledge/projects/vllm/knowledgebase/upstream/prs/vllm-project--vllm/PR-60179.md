# [Bugfix][Weight Cache] Key non-MoE DP daemons as DP=1 like the engine

[Upstream PR](https://github.com/vllm-project/vllm/pull/60179) · state: closed · merged: True

## Original PR description

## Overview

Fixes #60178 . A dense (non-MoE) engine with `--data-parallel-size N` sends `dp_size=1, dp_rank=0` to the `vllm preload` daemon, which keys each rank as `dp_size=N, dp_rank=r`, so `--load-format ipc_cache` never maps the cached weights. The daemon now keys dense DP ranks as `(1, 0)` like the engine; MoE daemons are unchanged (follow-up to #57386).

## Claims

- A dense model with `--data-parallel-size N` and `--load-format ipc_cache` now maps its weights from the daemon on every rank.
- MoE daemons, daemons started without DP, and the per-GPU workaround from the issue are unchanged.
- No open PR touches the daemon's key. #59648 (`protocol.py`) and #59813 (`ipc_loader.py`) each add tests to `test_weight_cache.py`, a trivial rebase either way. #60006 rewrites `docs/features/preload.md` and keeps listing data parallelism as supported, which this fix makes true for dense models too.

## Validation

Unit test, no GPU needed:

```bash
.venv/bin/python -m pytest tests/model_executor/model_loader/test_weight_cache.py -k "daemon or key or copy_mode" -q
```

`5 passed`. The new `test_daemon_keys_dense_dp_ranks_like_the_engine` checks that the daemon's key for a dense DP rank equals `ParallelConfig` after `reconfigure_for_independent_dp_rank()`, and that a MoE rank keeps `(dp_size, dp_rank)`.

End-to-end on 2x RTX A6000 with `Qwen/Qwen3-0.6B`, `main` at 5f30fc7031 vs this branch. Each scenario runs `vllm preload`, then `vllm serve --load-format ipc_cache`, then one greedy completion. "Map" means the worker logs `Mapped 339 tensors from the weight cache daemon`.

| | daemon | engine | before | after |
|---|---|---|---|---|
| A | `-dp 2` | `-dp 2`, `fallback=false` | fails to start, `WeightCacheKey mismatch on fields: ['dp_size']` | 2/2 ranks map |
| B | `-dp 2` | `-dp 2`, default | 0/2 map, both ranks fall back to disk | 2/2 map |
| C | no DP | no DP | 1/1 map | 1/1 map |
| D | one no-DP daemon per GPU | `-dp 2` | 2/2 map | 2/2 map |

Every run that starts returns the same text before and after. `pre-commit` passes.

The unit test runs in the existing Model Executor CI step (`pytest model_executor`). The DP scenarios need two GPUs and a server, so they are not added to CI.

Not validated: TP > 1 with DP, multi-node DP, MoE with DP end to end, the Ray DP path, and draft daemons with DP.

## Details

Root cause:

1. For a non-MoE model, `run_engine_core` calls `reconfigure_for_independent_dp_rank()` on every DP rank, which sets `data_parallel_size = 1` and `data_parallel_rank = 0` ([`core.py` L1388-L1397](https://github.com/vllm-project/vllm/blob/5f30fc7031cae49bf51073fc953d419b08f8887c/vllm/v1/engine/core.py#L1388-L1397)).
2. `IpcModelLoader` builds the key from `get_dp_group()`, so a dense engine sends `dp_size=1, dp_rank=0` on every GPU ([`ipc_loader.py` L345-L357](https://github.com/vllm-project/vllm/blob/5f30fc7031cae49bf51073fc953d419b08f8887c/vllm/model_executor/model_loader/weight_cache/ipc_loader.py#L345-L357)).
3. `WeightCacheDaemon` used the launcher's `data_parallel_size` and its own `dp_rank` regardless of the model.

Fix: a new `get_engine_dp_placement(vllm_config, dp_rank)` in `daemon.py` returns `(1, 0)` when the target model is not MoE and `(dp_size, dp_rank)` otherwise. The daemon passes that to `WeightCacheKey.from_model_config`. It keys on the target model's `is_moe`, like `core.py`, so a draft daemon follows its target. It has one call site but stays a function so the test can compare it with `ParallelConfig.reconfigure_for_independent_dp_rank()` without constructing a daemon. Only the key changes; daemon placement and the world group are untouched.

All dense DP ranks now share one key. That is correct because they hold identical weights, and the per-GPU socket plus `_check_gpu_uuid` already bind each engine worker to the daemon on its own GPU.

Same class of bug as #56949 (RL weight transfer), where dense DP ranks also reset `data_parallel_rank` to 0.

- he-yufeng · comment · 2026-10-06T17:46:14Z · [source](https://github.com/vllm-project/vllm/pull/60179#issuecomment-6022059122)

Independently walked the same path before noticing this PR, confirming the mechanism on main e82b8009: the engine's key comes from get_dp_group() after run_engine_core rescopes dense ranks to DP=1, the daemon fingerprints with the launcher's dp_size/dp_rank, so every dense DP rank mismatches on dp_size (and dp_rank past rank 0). The daemon-side collapse is the right layer since the key is only a compatibility token.

One edge I checked that is easy to get wrong and this gets right: the predicate has to read the TARGET model's is_moe even for draft daemons, because the engine rescopes on the target. The call site passes the target's vllm_config before the draft ModelConfig swap, so a dense draft under a MoE target still advertises the real placement. The test comparing against a real reconfigure_for_independent_dp_rank() output instead of a hardcoded (1, 0) is a nice touch, it pins both ends of the contract.
