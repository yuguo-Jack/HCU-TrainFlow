# [Fast Start] Fix weight cache daemon GPU memory and warm-cache warmup hang

[Upstream PR](https://github.com/vllm-project/vllm/pull/62583) · state: closed · merged: True

## Original PR description

## Purpose

Fixes three issues with the weight cache daemon (`vllm preload`) that made fast start differ from a disk load, plus one logging issue.

1. **The KV cache was smaller than with a disk load.** `get_memory` reported `torch.accelerator.memory_allocated()`. That number also counts memory the engine never maps: communication buffers, warmup workspaces, and tensors outside parameters/buffers, which the engine rebuilds itself and so pays for twice. The engine subtracts the reported number from its `gpu_memory_utilization` budget. The daemon now reports the bytes of the distinct CUDA storages it exports.
2. **The daemon held its process groups for its whole lifetime.** Serving only exports CUDA IPC handles, but the NCCL / custom all-reduce / symm-mem communicators and the FlashInfer all-reduce workspace kept about 2.5 GiB per GPU pinned outside the engine's budget. The daemon now tears them down after warmup.
3. **Warmup deadlocked with a warm compile cache (TP > 1).** The daemon never set `parallel_config.rank`, so every daemon used `torch_aot_compile/<hash>/rank_0_0`. With a warm cache, all ranks loaded rank 0's artifact, whose Inductor code hard-codes `set_device(0)`. Warmup lazily creates the FlashInfer MNNVL workspace inside that graph, so on ranks 1..N it used `torch.cuda.current_device() == 0`:
   - On those ranks, `cuMulticastAddDevice` failed with `CUDA_ERROR_UNKNOWN` and they fell back to the trtllm workspace.
   - Rank 0 kept waiting in `cuMemMap` for the other ranks to add their devices.

   The daemon now sets `parallel_config.rank` the way engine workers do (`worker_base.py`).

   Caches written before this fix may still contain such an artifact under `rank_0_0`. Clear the daemon's `torch_aot_compile` cache once after upgrading.
4. **Logs were dropped in the daemon processes.** The spawned daemons never called `configure_logging`, so their vLLM logs were lost.

## Test Plan

- Unit tests: `pytest tests/model_executor/model_loader/test_weight_cache.py -k "not cold_start and not rope_matching"`, including two new tests:
  - `test_daemon_reports_exported_weight_bytes`
  - `test_daemon_sets_its_rank_like_engine_workers`
- End to end on 4x B300: Qwen3-30B-A3B-NVFP4, TP4, `--gpu-memory-utilization 0.6`, `--max-model-len 8192`, `--load-format ipc_cache` in zero_copy mode.
  - Ran the daemon with both a cold and a warm compile cache.
  - Compared the KV cache, the daemon's GPU memory, and a greedy completion against a disk load.

## Test Result

- Unit tests: 9 passed. `test_ipc_rope_matching` fails the same way on `main`, so it is unrelated to this change.
