# [Test] Allow one fp8 step on K bytes in the kpool decode fuzz test

[Upstream PR](https://github.com/vllm-project/vllm/pull/60725) · state: closed · merged: True

## Original PR description



## Overview

Makes `test_batched_matches_reference_fuzz` tolerate a one-step fp8 rounding difference on K bytes. Seed 9 fails on the ROCm 10.0 (TheRock) stack (#58761) and in main's scheduled ROCm 10 AMD CI lane.

## Claims

- `_assert_eq` takes `k_byte_tol`, and only the random fuzz test passes `1`.
- Scale bytes, the tail cache, and all fixed-input cases stay exact.

## Validation

`pytest tests/kernels/test_kpool_decode_update_batched.py` on MI300X (reproduces there):

| | ROCm 10 image | ROCm 7.2 image |
|---|---|---|
| before | 1 failed (`fuzz[9]`), 33 passed | 34 passed |
| after | 34 passed | 34 passed |

## Details

TheRock's torch GPU `randn` differs from the 7.2 build by one ULP for about 16% of values. For seed 9, one pooled value then lands about 4e-5 of a step from a bf16 rounding midpoint before the Hadamard and fp8 quantization, so the GPU kernel and the CPU reference round apart and two K bytes differ by 1. Swapping saved inputs between the images confirmed that the kernel and the reference behave the same on both stacks; only the inputs differ. Any seed can hit this on another torch or ROCm build, so I bounded the difference instead of skipping the seed.

Not a duplicate: no open PR touches this test.
