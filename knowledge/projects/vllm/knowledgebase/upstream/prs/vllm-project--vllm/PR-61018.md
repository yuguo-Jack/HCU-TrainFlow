# [Model] Qwen4Exp: support batch-sharded sampling (compute_logits_local)

[Upstream PR](https://github.com/vllm-project/vllm/pull/61018) · state: closed · merged: False

## Original PR description

## Overview

Let Qwen4Exp take the batch-sharded sampling path (#50465). `Qwen4ExpForConditionalGeneration` inherits `compute_logits_local` from `Qwen3_5ForConditionalGeneration`, which calls `language_model.compute_logits_local`, but `Qwen4ExpForCausalLM` does not define it. This PR adds the method on the NVIDIA and AMD `Qwen4ExpForCausalLM`, the same 3-line pattern as Qwen3.5 and MiniMax M3.

**Draft:** the end-to-end serving validation below is still running. I will mark the PR ready only after it is filled in.

The first serving run reached "Batch-sharded sampling enabled." on all 8 ranks. It then failed in warm-up, with NCCL out of memory at the first all-to-all. That failure is not specific to Qwen4Exp: the profile run never executes the sharded all-to-all. The fix is #61025, and the serving retry runs with both PRs.

**Retry with #61025 (measured):** start-up passes. All 8 ranks log "Batch-sharded sampling enabled.", warm-up is clean, and the server answers requests. The NCCL all-to-all buffers now take about 2.9 GiB per GPU (non-torch memory 17.75 → 20.62 GiB), so the KV cache falls from 2,128,699 to 1,742,619 tokens (−18 %) on 40 GB A100s. That is a real trade-off for capacity-bound serving; the 3 × 60 min result will show whether the sampling saving outweighs it.

**Serving result (measured, MLPerf agentic full set, 20 concurrent sessions, 3 × 60 min per arm, same node type, strict per-request SLO TTFT ≤ 2.93 s and TPOT ≤ 21.74 ms):**

| Arm | Joint SLO pass r1/r2/r3 | Goodput (req/s) | TTFT p50 / p95 (s) | TPOT p50 / p95 (ms) | Accuracy score |
|---|---|---|---|---|---|
| Flag off | 90.0 / 89.2 / 89.5 % | 1.83–1.89 | 0.93–0.98 / 2.22–2.35 | 14.1–14.3 / 23.9–24.5 | 0.540–0.542 |
| Flag on (this PR + #61025) | 75.2 / 77.4 / 75.3 % | 1.35–1.38 | 1.35–1.41 / 3.22–3.35 | 15.8–16.1 / 27.3–29.2 | 0.536–0.543 |

On this memory-tight, KV-capacity-bound workload, the 18 % smaller KV cache costs far more than sampling saves; nsys on the flag-off run puts redundant sampling at about 1.5–2 % of step time. So **I do not claim a speed-up**. This PR only makes the existing option work for Qwen4Exp (today `Qwen4ExpForConditionalGeneration` advertises `compute_logits_local` but the language model lacks it). It should pay off where the KV cache is not the limit, for example GPUs with more memory, or after limiting NCCL point-to-point channels; I have not measured those. If reviewers prefer, I will close this PR rather than add an option that does not help on the hardware I can test.

## Claims

- `--enable-batch-sharded-sampling` works for Qwen4Exp. Each TP rank computes its vocabulary shard of the logits (`skip_gather=True`), and the existing `BatchSharder` all-to-all gives each rank the full vocabulary for its share of the requests.
- No change when the flag is off: the new method is reached only from the sharded path.
- (Pending) Serving result on Qwen3.8-Flash-Next-FP8, TP8 + EP, 8 × A100-SXM4-40GB.

## Validation

- `Qwen4ExpForCausalLM.compute_logits_local` calls the logits processor with `skip_gather=True`.
- The VL wrapper `Qwen4ExpForConditionalGeneration.compute_logits_local` reaches it.
- It follows the existing `test_rocm_compute_logits_local_skips_gather` pattern in `tests/models/test_deepseek_v4_vl_rocm.py`.

## Details

- **Root cause:** models opt in to batch-sharded sampling by implementing `compute_logits_local` (`ParallelConfig.enable_batch_sharded_sampling` docstring). The Qwen3.5 VL base class delegates the call to its language model. `Qwen4ExpForConditionalGeneration` reuses that base class, but its language model class did not implement the method.
- **Expected effect (estimate from an nsys trace of this model at 16 concurrent sessions):** top-k/top-p and the logits all-gather run redundantly on all 8 ranks, about 0.6–0.8 ms of a 42 ms average step (1.5–2 %). That trace also counted the Triton top-k/top-p kernel at 6.8 % of the eager kernel time.
- **Size:** +14 lines of model code; +57 lines of test.
- **Limitations:**
  - I have not checked whether the MTP drafter's logits take the sharded path; the drafter code is unchanged.
  - LoRA is rejected by the flag itself (#56074).
