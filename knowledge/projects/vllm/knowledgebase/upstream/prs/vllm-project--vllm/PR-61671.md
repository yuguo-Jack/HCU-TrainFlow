# [Bugfix][Quantization] Gate QuTLASS to SM10x and keep transformed linears on unquantized input

[Upstream PR](https://github.com/vllm-project/vllm/pull/61671) · state: open · merged: False

## Original PR description

## Overview

`CompressedTensorsLinearTransformMethod.from_schemes` and `FPQuantLinearMethod` pick the QuTLASS kernels when `has_device_capability(100)` is true. QuTLASS is compiled for one SM family (`cmake/external_projects/qutlass.cmake` selects SM100 whenever both SM100 and SM120 are in the arch list, which is the case for the wheels: `_qutlass_C.abi3.so` in `vllm/vllm-openai:nightly` contains only `sm_100` cubins and no PTX). On consumer Blackwell (SM120 / SM121: RTX 50 series, RTX PRO Blackwell, DGX Spark) the check passes and the first forward fails inside the kernel:

```
RuntimeError: run, .../qutlass/csrc/fused_quantize_nv.cu:101, Error Internal
```

Once SM12x falls through to the generic transform method, a second problem shows up: `CompressedTensorsW4A4Fp4` exposes the kernel's `input_quant_key`, so the MLP producer hands `down_proj` a pre-quantized `QuantizedActivation`, and the Hadamard input transform fails with `AttributeError: 'QuantizedActivation' object has no attribute 'unflatten'`. The input transform has to run on the original activation. By inspection the same applies to `QutlassNvFP4LinearMethod` on SM100, whose `apply` quantizes the activation itself (`fusedQuantizeNv`) and also expects a plain tensor; it inherits the fix through `super().create_weights`.

This was already flagged in the #43229 review (https://github.com/vllm-project/vllm/pull/43229#discussion_r3670554315) but never addressed

This PR:

- selects QuTLASS only on `is_device_capability_family(100)` (transform scheme) and raises a clear `ValueError` in FPQuant on other CUDA devices instead of the runtime `Error Internal`;
- sets `layer.requires_unquantized_input = True` when a linear layer has an input transform, so `get_input_quant_key` hides the wrapped kernel's key from fused activation-quant producers;
- aligns the module-level skip of `test_nvfp4_qutlass.py` / `test_mxfp4_qutlass.py` with the gate (they currently run and fail 234/234 on SM12x with the wheel);
- adds a CPU-only test for the selection and the input-key behaviour.

## Claims

- `nm-testing/Llama-3.2-1B-Instruct-quipv16-nvfp4` (compressed-tensors NVFP4 W4A4 + Hadamard input transforms, the model used by `test_compressed_tensors_transforms_perplexity`) now loads and generates on DGX Spark (GB10, SM121) through `FlashInferCutlassNvFp4LinearKernel`; perplexity on the test prompt is 79.3 (test threshold 150). On main it fails at engine start with the QuTLASS error.
- No behaviour change on SM10x other than `requires_unquantized_input` for layers with input transforms, which restores the pre-#44260 behaviour of the transform path receiving a plain tensor. No change for W4A16 transform models (their kernels expose no input key).

## Validation

All measurements on NVIDIA DGX Spark (GB10, SM121, driver 580.178.04), image `vllm/vllm-openai:nightly-5555a2d8f7116b2b4877f66516f4128176cf722a` (vLLM 0.31.1rc1.dev376), with the changed files overlaid; both files are byte-identical between the image and main.

- `cuobjdump --list-elf vllm/_qutlass_C.abi3.so`: 6 x `sm_100`, no other ELF, no PTX.
- Main: `python -c "LLM('nm-testing/Llama-3.2-1B-Instruct-quipv16-nvfp4', enforce_eager=True)"` -> `fused_quantize_nv.cu:101, Error Internal` from `QutlassNvFP4LinearMethod.apply` during `profile_run`.
- Gate only (`is_device_capability_family(100)`): `AttributeError: 'QuantizedActivation' object has no attribute 'unflatten'` in `HadamardTransform.forward` from `down_proj`.
- Gate + `requires_unquantized_input`: loads, `Using FlashInferCutlassNvFp4LinearKernel for NVFP4 GEMM`, greedy "The capital of France is" -> " Paris. The capital of France is Paris. ...", prompt perplexity 79.30 on "Flat is better than nested.\nSparse is better than dense." (upstream threshold 150.0).
- `pytest tests/kernels/quantization/test_transform_linear_selection.py tests/kernels/quantization/test_nvfp4_qutlass.py tests/kernels/quantization/test_mxfp4_qutlass.py`: 7 passed, 2 skipped (the two QuTLASS modules now skip on SM121; on main they collect and fail 234/234 with `Error Internal`). The new test's SM12x cases and the input-key case fail against main.
- FPQuant on SM121 now raises `ValueError: FPQuant requires the QuTLASS kernels, which are only built for SM 10.x ...` from `create_weights`.
- `ruff check` / `ruff format --check` clean on the changed files.

I do not have an SM100 device; the SM10x behaviour is unchanged by inspection and covered by the existing H200/B200 CI only where those kernels are selected.

## Details

- `cmake/external_projects/qutlass.cmake` warns "Both SM100 and SM120 archs were requested; selecting SM100 because TARGET_CUDA_ARCH is a single compile-time selector". A source build with an SM120-only arch list would get working SM12x kernels and is now also gated off; exposing the compiled target at runtime (for example a `QUTLASS_TARGET_CC` define surfaced through `_qutlass_C`) would be the precise fix and could be a follow-up.
- `requires_unquantized_input` is the mechanism `get_input_quant_key` already provides (used by the LoRA linear layers); the transform wrapper is the second consumer that needs the original activation.
- The transform perplexity test runs on H200 in CI, where the NVFP4 W4A4 scheme falls back to Marlin (W4A16, no input key), so neither problem is visible there.

Not a duplicate: searched issues/PRs for "qutlass sm120", "Error Internal", "quipv16", "fp_quant sm120" (2026-10-14); #45260 tracks SM12x coverage generally but does not list QuTLASS. #38957 (open, stale) touches the qutlass cmake arch list for a different reason. #61073 (open) extends the QuantizedActivation contract and also honours `requires_unquantized_input`, so the two are compatible; it would additionally pre-quantize `qkv_proj` / `gate_up_proj`, which makes this fix more necessary, not less.
