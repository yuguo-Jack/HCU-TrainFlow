# [KV Offload] Reject out-of-range block ids instead of computing a wild pointer

[Upstream PR](https://github.com/vllm-project/vllm/pull/60061) · state: open · merged: False

## Original PR description

## Purpose

`compute_sub_block_ptrs()` in `vllm/v1/kv_offload/cpu/gpu_worker.py` turns a block id into `base_ptr + id * row_stride` and hands the result to the copy engine. Nothing downstream re-checks the address. An id at or past `tensor.shape[0]` therefore becomes a host address outside the CPU tier's allocation, and a negative id wraps through the `uint64` cast to one far beyond it.

Because that address is outside the `cudaHostRegister`ed range, the driver treats it as pageable memory and takes the staged D2H path, and the deferred staging-to-destination `memcpy` faults on a driver thread. What the user sees is

```
ERROR [multiproc_executor.py:314] Worker proc VllmWorker-13 died unexpectedly (exit code: None), shutting down executor.
```

with no Python frames, no Xid and nothing in `dmesg`, long after the bad id was produced. In the case reported in #50821 the fault landed 6.88 GiB past the end of the region, 10 to 24 minutes into sustained load, on all TP ranks of the last pipeline stage at once.

This PR checks the ids against the tensor's row count before the pointer arithmetic and raises a `ValueError` naming the offending id and the valid range. It raises rather than asserts so the guard survives `-O`. On the `blocks_per_chunk == 1` path only the ids that are actually turned into pointers are checked, matching what that path uses. With the guard in place the same failure reads

```
ValueError: Block id 25600 is out of range for a 25600-block cpu KV tensor (valid ids: 0..25599).
```

raised from `submit_store -> transfer_async -> _fill_direct_ops -> compute_sub_block_ptrs`, which is what turned the investigation in #50821 from a core dump into a capacity-mismatch diagnosis.

### Relationship to #50653 / #50821

#50653 fixes the capacity mismatch that produced the out-of-range ids in that report (different `num_chunks` across pipeline stages). It does not add a bounds check, so any future id error stays a silent out-of-bounds host write. This PR is the defensive half and is independent of #50653; both can land in either order. Opening it separately was discussed in #50821.

## Test Plan

New unit tests in `tests/v1/kv_offload/cpu/test_gpu_worker.py`, CPU only:

- `test_compute_sub_block_ptrs_accepts_boundary_ids[1|3]`: ids `0` and `num_blocks - 1` are accepted and map to the expected addresses, with and without sub-block expansion.
- `test_compute_sub_block_ptrs_rejects_out_of_range_ids[-1|8|25600 x 1|3]`: a negative id, the first id past the end, and a far out-of-range id raise, on both the 1:1 path and the sub-block expansion path.
- `test_compute_sub_block_ptrs_checks_only_used_ids_on_fast_path`: documents that the 1:1 path only checks the ids it turns into pointers.

Regression suites, run on a GPU node with and without the fix (`vllm/` reverted, tests kept):

```bash
pytest -q tests/v1/kv_offload tests/v1/kv_connector/unit/offloading_connector
```

## Test Result

- With the fix: 1144 passed, 2 skipped. Without the fix: 1138 passed, 6 failed, 2 skipped. The 6 failures are exactly the `rejects_out_of_range_ids` cases; everything else is identical between the two runs.

Reviewed the pointer-generation path and tests. The guard runs before the unsigned conversion, uses the tensor’s native row count, and correctly limits validation to consumed IDs on the 1:1 path while validating all chunk IDs on the expansion path.
