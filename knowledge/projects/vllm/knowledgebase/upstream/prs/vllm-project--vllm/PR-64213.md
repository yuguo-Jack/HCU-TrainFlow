# [KV Offload][KVCR] Demote the CPU-tier copies of chunks served to a peer

[Upstream PR](https://github.com/vllm-project/vllm/pull/64213) · state: open · merged: False

## Original PR description

## Overview

This PR adds an opt-in `demote_served_chunks` option to the KVCR secondary tier.

When a peer fetches chunks from this instance through KVCR, the peer stores its own copy. The local CPU-tier copy keeps its place in the eviction order, because the serve path pins it without recording an access. With the option on, the tier demotes those local copies right after pinning them, so they are evicted first once the transfer releases them. They are demoted, not dropped: a later local reuse restores their rank.

To support it:
- `CachePolicy` gains an optional `demote(keys)` hint. It is a no-op by default, and `lru` implements it.
- `CPUOffloadingManager` gains `demote(keys, pins_held)`.
- Secondary tiers reach it through a new optional `ParentManager.demote(keys)`.

## Claims

- **New option:** the KVCR tier option `demote_served_chunks`, default `false`. Nothing changes unless it is set.
- **Behavior with `lru`:** served chunks move to the evict-first end, tail first and oldest demotion first.
  - A chunk that another local request is reading keeps its place.
  - A later local request-scoped access restores normal recency.
- **Compatibility:** `arc` and existing out-of-tree policies ignore the hint. Other secondary tiers are unaffected, because `ParentManager.demote()` demotes nothing by default.
- **Outputs cannot change:** the option only reorders CPU-tier evictions.
- **Performance:** in a disaggregated deployment of a hybrid model (4 prefill and 4 decode instances with KVCR, under agentic traffic), compared with the option off:
  - at 320 concurrent sessions: 10.3% more requests and TTFT p50 −36%;
  - at 256: prefill tokens computed per request −23.6% and TTFT p90 −51%.

## Details

### Motivation

A worked example with two prefill instances, A and B, whose KVCR tiers link their CPU tiers (as in the runs above; the decode instances receive KV over NIXL and have no CPU tier):

1. Turn 1 of session S is prefilled on A. A's CPU tier holds S's prefix P, among older prefixes such as T that exist only on A.
2. The router sends turn 2 to B. B's KVCR tier finds P on A and fetches it: A pins P with `prepare_read()`, which records no access, transfers it, and releases it. B stores its own copy, and S's later turns are likely to land on B.
3. Both CPU tiers now hold P, and A's copy keeps the rank of its last local use. When A needs room, it evicts T, the only copy in the cluster, while P stays.

With `demote_served_chunks`, A demotes P's chunks in step 2, so A evicts P instead of T, and B still holds P. If S returns to A before then, the reuse restores P's rank. In the runs above, second copies took 25–31% of the CPU tiers' contents before the change, and 15–16% after.

### Design

- **`CachePolicy.demote(keys)`:** an optional hint that cached chunks are unlikely to be reused locally. The default ignores it.
- **`LRUCachePolicy.demote`:**
  - Demoted chunks rank below every recency rank, tail first and oldest demotion first.
  - A pinned chunk takes its demoted place once it becomes evictable, through LRU's lazy heap.
  - A later `touch`, `on_request_access` or `on_request_finished` gives the chunk a normal rank again.
- **`CPUOffloadingManager.demote(keys, pins_held)`:** demotes only ready chunks whose `ref_cnt` does not exceed the caller's own pins.
- **`ParentManager.demote(keys)`:** reaches `TieringOffloadingManager.demote_served(keys)`, which demotes on the CPU tier and counts the serve job's own pin.
- **KVCR:** `_FrameworkPinAdapter._resolve_pin()` calls `parent.demote()` right after `create_store_job()`. This runs inside `serve_external_requests()`, under the tiering manager's lock. The KVCR tier is served once per step (`tolerates_off_thread_polling = False`).
- **Cost:** one pass over a serve job's keys, plus one heap push per evictable chunk. It runs on the scheduler side, with no GPU work.

### Related work

- **#63824 (open):** Guard-only KVCR sources serve Guard-owned memory without the framework pin path, so this option has no effect for them. It applies to framework-backed sources: no Guard configured, or `guard_only_sources: false`.
- **#60469 (merged):** aligns KVCR's own cache recency with request prefixes, through KVCR's `align_sequence()`. It does not change the order of vLLM's CPU tier.
- **#61050 (merged):** request-scoped provisional ranks in `lru`. Demoted ranks sit below them, and a request access restores a normal rank.
- **#63578 (open):** `mamba_aware_lru` subclasses `lru`, so it inherits `demote()`. It keeps its own, lower band for superseded Mamba states, so those still go first. Whichever lands second can move both onto `demote()`.
- **RFCs #53421, #59708 and #57103** (KV hint envelopes, composable policies): a per-fetch hint, such as KVCR's planned `mode=move`, could later drive the same `ParentManager.demote()` per fetch instead of per tier.

### Tradeoffs and limitations

- **Re-fetch or recompute:** if this instance needs a served prefix again after its own copy is evicted, it fetches it back from the peer or recomputes it. In the runs above, about 1% of demoted chunks were reused locally before eviction.
- **Policies:** only `lru` honors the hint for now; `arc` ignores it.
- **Granularity:** the option is per tier. It cannot tell a peer that keeps the copy briefly from one that keeps it for long.
- **Sources:** it covers framework-backed KVCR sources only (see #63824).
