# [Bugfix][ROCm] Qwen4Exp QSA: accept Octave KV caches again

[Upstream PR](https://github.com/vllm-project/vllm/pull/63849) · state: closed · merged: False

## Original PR description

## Purpose

Qwen4Exp (Qwen3.8-Flash-Next) with an Octave KV cache fails at startup on `main`:

```
NotImplementedError: FlashAttention does not support octave_k3v3 kv-cache on this device.
```

#59774 added Octave support to the Qwen4Exp QSA layer, and in the same change `get_kv_quant_mode()` maps `octave_*` to an Octave `KVQuantMode`, so `is_quantized_kv_cache()` returns `True` for it. `Qwen4ExpQSAFlashAttentionImpl` subclasses `FlashAttentionImpl`, whose `__init__` raises for any quantized cache FlashAttention cannot read (added in #42569). QSA never hands the Octave cache to FlashAttention: it reads it with its own kernel. So every `--kv-cache-dtype octave_*` run of this model now fails while building the layers.

The fix passes `"auto"` to the parent for Octave dtypes and restores the real dtype right after. The parent uses `kv_cache_dtype` only to store it and for that check, and QSA has its own `forward`.

Not a duplicate: I searched open PRs and issues for "qwen4_exp octave", "QSA octave FlashAttention" and the error message, and found nothing. I authored #59774, so this regression is mine.

## Test Plan

- `tests/models/qwen4_exp/test_qsa_amd.py::test_qsa_impl_accepts_octave_kv_cache` (new, parametrized over the three Octave dtypes) builds the QSA impl and checks that it keeps the Octave dtype and its `OctaveFormat`. It replaces only the global config QSA reads (`model_config.dtype`), so it needs no model.
- End to end: `vllm serve` Qwen3.8-Flash-Next (TP4, `--kv-cache-dtype octave_k3v3`) on 4x RX 7900 XTX (gfx1100).

## Test Result

New test, on `main` without the fix:
```
NotImplementedError: FlashAttention does not support octave_k3v3 kv-cache on this device.
3 failed, 16 deselected
```
With the fix, the whole file:
```
19 passed
```
End to end, with the fix: the server starts and serves 100K and 200K-token prompts and a 128K-token `prompt_logprobs` request. Without it, it stops at layer construction with the error above.

This change does not affect model output: it only lets the layer be built with the cache it already supports.

AI assistance (Claude) was used. I reviewed every changed line and ran the tests and the end-to-end check above.
