# [Bugfix] Scope the nested-RoPE validator patch to the allowlisted model types

[Upstream PR](https://github.com/vllm-project/vllm/pull/57624) · state: open · merged: False

## Original PR description

Closes #57623

## Purpose

#57289 made the nested-RoPE validator patch reach transformers' automatic validation and, per review, kept it "surgical" by installing it only for the model types in `_PATCH_HF_NESTED_ROPE_VALIDATION` (`laguna`, `gemma4_text`). The installed wrapper, though, replaces `PretrainedConfig.validate_rope` for the rest of the process and drops shared `rope_parameters` entries for any config it validates. So once a `laguna` or `gemma4_text` config has been parsed, a later config of any other model type with the same malformed shape is accepted with a warning instead of failing validation. This PR makes the wrapper check the model type as well, so only the allowlisted types get the accommodation.

Reproduction on `main` (config loading only, no GPU): a `gemma3_text` config with a shared `rope_theta` beside its per-layer dicts raises `AttributeError: 'float' object has no attribute 'get'` when built; after `get_config("poolside/Laguna-XS-2.1-NVFP4", trust_remote_code=True)` in the same process, the identical config builds with `Dropping ['rope_theta'] from rope_parameters` logged. Same through `vllm.config.ModelConfig`. Issue linked above has the snippet.

This is the nested-map sibling of #57188 (the same wrapper mutating later flat `rope_parameters`), which #57189 fixed with the layer-type gate.

## Changes

- `vllm/transformers_utils/config.py`: in `_patch_hf_transformers_nested_rope_validation`'s wrapper, an early return to the original `validate_rope` when `getattr(self, "model_type", None)` is not in `_PATCH_HF_NESTED_ROPE_VALIDATION`. Five added lines, nothing removed. The install gate, the allowlist, the `__class_validators__` walk and the `sarvam_mla` shim are unchanged.
- `tests/test_config.py`: the #57189 test's nested namespace gets `model_type="laguna"` (the contract it now depends on); new `test_nested_rope_validation_patch_is_scoped_to_allowlisted_model_types`, same `monkeypatch` style, asserts a nested mapping on `model_type="llama"` keeps its shared key and reaches the original validator once. Fails on `main`, passes here.

## Not in this PR

- wentian-byte · comment · 2026-10-22T16:50:31Z · [source](https://github.com/vllm-project/vllm/pull/57624#issuecomment-6346244479)

+1, we hit this in a downstream fork's CI and can confirm the fix.

**What we saw:** under `pytest -n 16`, a test that loads a nested `rope_parameters` config with shared top-level entries (`mrope_section`, `mrope_interleaved`) failed only when xdist scheduled it on the same worker that had earlier run `test_gemma4_dspark_rope_config_preserves_parameters`. That `gemma4_text` load installs the wrapper for the whole worker process, the later config gets its shared keys dropped, and the failure survives `--reruns` because the reruns stay in the same process. On a different worker it passes, so it shows up as an order-dependent flake.

**Minimal repro on current `main`** (`c723f6d3ee`, transformers 5.20.2, config only, no GPU):

```python
from transformers import Gemma3TextConfig
import vllm.transformers_utils.config as c

def mk():
    return Gemma3TextConfig(
        num_hidden_layers=2,
        layer_types=["full_attention", "sliding_attention"],
        rope_parameters={
            "full_attention": {"rope_type": "default", "rope_theta": 1e6},
            "sliding_attention": {"rope_type": "default", "rope_theta": 1e4},
            "mrope_section": [1, 2, 3],
        },
    )

print(mk().rope_parameters)  # mrope_section kept
c._patch_hf_transformers_nested_rope_validation()  # what a gemma4_text/laguna load does
print(mk().rope_parameters)  # mrope_section silently dropped
```

**With this PR applied:**
- `mrope_section` is kept after the patch is installed.
- `pytest tests/test_config.py -k nested_rope_validation`: 2 passed. The new test fails on `main` without the code change.
- The branch still merges cleanly into current `main`.
