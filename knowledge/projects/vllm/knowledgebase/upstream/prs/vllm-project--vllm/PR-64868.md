# [Bugfix][Responses API] Leave unset item and tool fields out of responses

[Upstream PR](https://github.com/vllm-project/vllm/pull/64868) · state: closed · merged: False

## Original PR description



## Overview

Fixes #47200. `/v1/responses` no longer returns `null` for output item and tool fields that nothing set, so clients that validate the response strictly can parse it.

## Claims

- Output items no longer carry unset fields such as `namespace`, `caller`, `async`, `phase`, or a reasoning item's `status` and `encrypted_content`, in the JSON response or in SSE events.
- Echoed tools contain what the client sent, plus `parameters` and `strict`, which the schema requires but allows to be null. Unset `defer_loading`, `allowed_callers`, `async` and `output_schema` are gone.
- Values that were set are unchanged, including explicit nulls from the client and nulls inside a tool's JSON schema.

## Validation

- Added a regression test through `RemoteOpenAIServer`, streaming and non-streaming, that reads the raw wire format because the SDK hides these nulls. It fails on `main` and passes with this fix, as does a new unit test.
- Compared every JSON path from a live server before and after, across plain, named-tool and auto-tool requests, streaming and non-streaming. No path that ever held a value was removed, and none was added.
- Real-server suites with `Qwen/Qwen3-1.7B`: `test_function_call.py` and `test_namespace_tool_separator.py`, 18 passed, including namespaced tools keeping `namespace`.
- Responses unit suites: 298 passed, 1 xfailed on openai 3.42.0. On openai 2.44.0, which CI pins, the regression tests pass plus `test_responses_utils.py`, `test_streaming_events.py` and `test_serving_responses.py`: 155 passed, 1 xfailed. `pre-commit` passed.
- Local testing was on macOS CPU. CI covers GPU, the Harmony path end to end (`test_harmony.py`) and `test_simple.py`, which needs `Qwen/Qwen3-8B`. I read SMG's parser but did not run SMG against this change.
- No model eval: this only changes how responses are serialized, not generated tokens.

## Details

The SDK types default every optional field to `None`, and the response was dumped with those defaults. The report in #47200 has two parts on current `main`:

- The `status: null` on `function_call` items that caused `invalid type: null, expected a string` was fixed by #59324.
- Echoed tools can still fail. [SMG's `FunctionTool`](https://github.com/smg-project/smg/blob/873e49226cdc40f2d0c939350b9b2686fdf1badb/crates/protocols/src/responses.rs#L540) rejects any key outside `name`, `description`, `parameters` and `strict`, so `defer_loading: null` should fail with an unknown-field error. New SDK versions add more such fields.

This uses `exclude_unset` rather than `exclude_none` because some nulls are meaningful: `ResponseCodeInterpreterToolCall.outputs` is set to `None` on purpose, and a client's explicit `null` should round-trip. So call sites that passed `namespace=None` or `status=None` now leave those fields unset. `ResponsesResponse` keeps its defaults, such as `object`, because only its `output` and `tools` are filtered, and `model_dump()` in Python mode is unchanged.

Not changed, to keep this small:

- Top-level `user`, `text` and `usage` can still be `null`. The OpenAI spec's own response examples return `"user": null` and `"usage": null`, and SMG accepts all three.
- `content[*].logprobs` can still be `null`, because call sites set it explicitly and SMG accepts it. Sending `[]` as streaming does at the start of a part would change a value, so it should be a separate change.
- vLLM-only fields such as `kv_transfer_params` stay as they are, since SDK users may read them as attributes.

Tradeoff: a non-SDK client that reads `item["namespace"]` without a default would now see a missing key. The schema marks these fields optional, and SDK clients still get `None`. The Rust frontend has no Responses API on `main` yet, so nothing needs to change there.

Not a duplicate: no open PR references #47200 or changes this serialization. This replaces #47184, which the stale bot closed on 2026-10-31 without a review. That PR removed `status`, which SMG now requires on `function_call`, and added position-specific cleanup (+340 lines, this is +44 in source). I searched open PRs by the issue number and by `namespace`, `exclude_unset`, `defer_loading`, `allowed_callers`, `output item status null` and `tools echo responses`. #54297 and #35508 handle nulls on request input, not responses.
