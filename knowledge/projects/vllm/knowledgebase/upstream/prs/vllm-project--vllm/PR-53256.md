# [Bugfix][Frontend] Do not report finish_reason="tool_calls" when no tool call was made

[Upstream PR](https://github.com/vllm-project/vllm/pull/53256) · state: closed · merged: False

## Original PR description

## Purpose

Fixes #53255.

With `tool_choice="required"`, the non-streaming chat handler translates the
engine's `"stop"` into `finish_reason="tool_calls"`. That translation assumes a
tool call was produced, but it never checks. When the parse yields no calls —
for example when no tool parser is configured, so `parser` is None and
`tool_calls` is `[]` — the response goes out with `finish_reason="tool_calls"`
next to an empty `tool_calls`.

`finish_reason` is the documented way to detect a tool call, so a client takes
the tool-execution branch and finds nothing to execute.

The streaming path in the same file already gets this right — it requires
`tools_streamed[i]`, set only when a tool-call delta was actually emitted,
before reporting `"tool_calls"`. So today the same request answers differently
depending only on `stream`. This makes the non-streaming path agree:

```python
 is_finish_reason_tool_calls = auto_tools_called or (
     request.tool_choice
     and request.tool_choice == "required"
     and output.finish_reason == "stop"
+    and bool(tool_calls)
 )
```

Scope is deliberately narrow:

- `auto` is unaffected — `auto_tools_called` already implies non-empty tool calls.
- `required` **with** a real tool call still reports `"tool_calls"`.
- Named `tool_choice` is untouched; it continues to report `"stop"`, which is the
  existing intended behaviour documented in the comment above this expression.

  of the two needs reviewing.

## Test Plan

Unit test added: `test_required_tool_choice_does_not_claim_a_tool_call_it_did_not_make`
in `tests/entrypoints/openai/chat_completion/test_serving_chat.py`, extending the
existing suite and reusing its `_build_minimal_metrics_serving_chat` helper (which
already configures no tool parser — the exact condition that triggers this).

```
.venv/bin/python -m pytest \
  tests/entrypoints/openai/chat_completion/test_serving_chat.py \
  -k required_tool_choice_does_not_claim -v
```

I could not run the suite locally — no CUDA/GPU on the machine used to prepare
this — so the unit test is offered for CI. The behavioural claims below come from
running a real server.

End-to-end: the server was exercised over HTTP with the request from the issue,
on the same host and image with the patch as the only variable, in two arms —
tool parser off (the broken case) and tool parser on (the case this change could
regress).

## Test Result

End-to-end, `tool_choice="required"`:

| Arm | `tool_calls` | `finish_reason` | |
|---|---|---|---|
| unpatched, no tool parser | 0 | `"tool_calls"` | contradicts the empty array |
| **patched**, no tool parser | 0 | `"stop"` | fixed |
| **patched**, tool parser enabled | 1 | `"tool_calls"` | unchanged — no regression |

The third row is the one that matters most: the working path is untouched, and
the returned call is still well formed (`get_weather({"city": "San Francisco"})`).

Named `tool_choice` was checked in the same runs and is unchanged by this patch,
still returning its call with `finish_reason="stop"` as before.

No model evaluation is included: this changes only the `finish_reason` field
selected by the serving layer. Token generation, sampling and model output are
untouched.
