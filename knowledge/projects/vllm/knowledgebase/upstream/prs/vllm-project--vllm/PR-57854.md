# [Bugfix][RL] Fail a weight update without taking the engine down

[Upstream PR](https://github.com/vllm-project/vllm/pull/57854) · state: open · merged: False

## Original PR description


## Purpose

A weight-update session (`start_weight_update` → `update_weights` × N → `finish_weight_update`) has two ways to end without completing, and today both leave the engine dead rather than just failing the request. They are fixed together here because they meet at the same point in the worker: the code that drops a session that will not finish.

### 1. The weights are asleep

Sleep mode unmaps the weight allocations (level 1 offloads them to host memory, level 2 discards them), and nothing checked that they were mapped again before a weight update wrote into them. A CUDA IPC update issued after `sleep()` and before `wake_up()` segfaults the EngineCore inside the device copy, the API server keeps running with a dead engine, and the trainer only sees its HTTP call time out:

```
POST /sleep?level=1        -> 200
POST /start_weight_update  -> 200
POST /update_weights       -> (no reply)
!!!!!!! Segfault encountered !!!!!!!
  File "<unknown>", line 0, in cuMemcpyDtoDAsync_v2
  File "<unknown>", line 0, in at::native::copy_device_to_device(at::TensorIterator&, bool, bool)
  ...
(APIServer) WARNING [core_client.py:803] [shutdown] MPClient: engine core exited unexpectedly
```

Reported in #57853. The RL transaction in #48310 is pause → sleep → wake(weights) → update, and a client that gets the order wrong (or whose wake failed) should get an error, not a dead engine.

### 2. A chunk fails

The IPC and NCCL engines call `initialize_layerwise_reload` at `start_weight_update`, which saves each layer's tensors and re-creates the parameters on the meta device so the new weights can stream in layer by layer. Only `finalize_layerwise_reload`, run from finish, puts real tensors back.

If an `update_weights` call raises, the worker clears the session flag and resets the target pointer, and nothing restores the tensors. Every layer that had not finished loading stays on the meta device, `finish_weight_update` is then refused because the session is gone, and the next forward runs on meta tensors and takes the EngineCore down. Three HTTP calls against a plain server reproduce it, with no trainer process involved:

```bash
curl -X POST localhost:8802/start_weight_update
# {"message":"Weight update started"}

curl -X POST localhost:8802/update_weights -H 'Content-Type: application/json' -d '{
  "update_info": {"names": ["model.embed_tokens.weight"], "dtype_names": ["torch.bfloat16"],
                  "shapes": [[151936, 1024]],
                  "ipc_handles": [{"GPU-00000000-0000-0000-0000-000000000000": []}]}}'
# 500  "IPC handle not found for GPU UUID <this GPU>. Available UUIDs: ['GPU-0000…']"

curl -X POST localhost:8802/v1/completions -d '{"model": "…", "prompt": "The capital of France is", "max_tokens": 16}'
# 500  "EngineCore encountered an issue"
```

`/health` then returns 503 and the server process exits. A worker extension that hashes every parameter shows 0 of 339 tensors on the meta device before the sequence and 340 of 340 after the failed update, and the EngineCore's fatal traceback ends in:

```
NotImplementedError: _C_cache_ops::reshape_and_cache_flash: attempted to run this operator
with Meta tensors, but there was no fake impl or Meta kernel registered.
```

The mismatched GPU UUID is just the shortest way to make a chunk raise; a parameter name the model does not have, a dtype or shape mismatch, or an OOM while loading all land on the same path (checked separately with a real IPC trainer engine and an unknown parameter name). `sharded_rdt_engine.py` already carries a note that the layerwise API should expose an `abort_layerwise_reload`.

Both cases are the fail-closed behaviour #48312 asks for on every transfer transaction: a session that does not reach `finish` should leave the model serviceable.

## Changes

**The guard.** The worker mirrors the executor's sleeping tags and refuses `start_weight_update`, `update_weights`, `finish_weight_update` and `reload_weights` with a `RuntimeError` that names the fix while `weights` is asleep; a partial `wake_up(tags=["kv_cache"])` keeps the guard in place. `finish_weight_update` is included because the layerwise-reload finalize step still writes into the weights. The check lives in the worker because every weight RPC is dispatched as a bare `collective_rpc` from `AsyncLLM` and `LLM`, so the worker is the one point they all pass through, above the transfer backend: NCCL, NCCL M2N, sparse NCCL and sharded RDT updates are covered as well as IPC. #44483 took the same approach for the sibling case of a forward during a partial wake, and `release_kv_cache_memory()` already refuses in the same way when executor memory is not resident.

**The rollback.** `abort_layerwise_reload(model)` sits next to `finalize_layerwise_reload`: for every layer whose reload is still open it puts the saved kernel tensors back, drops the buffered partial weights and resets the layer's reload info, then restores the torchao flag and clears `LOADING_LAYERS` the way finalize does. `WeightTransferEngine.abort_weight_update()` exposes it to the worker — a no-op by default, so in-place and custom engines are unaffected, implemented by IPC, NCCL and NCCL M2N (#51520, which landed after this PR was opened), whose abort is a plain restore. M2N only parks on meta when its plan has fallback entries, so its abort is gated the same way; directly-resharded parameters were written in place and stay as they are. Sharded RDT also parks on meta at start, but its abort has to quiesce a background pull/process pipeline first; that is left as a follow-up and it keeps the base no-op for now.

**Where they meet.** `Worker._abort_weight_update_session()` is what both use: it lets the engine put back whatever it moved aside while the engine still points at the session's target model, then resets the target and ends the session. A failure inside the engine's abort is logged, not raised, so the error that ended the update stays the one the caller sees. The asleep refusals reach it from `update_weights` and `finish_weight_update`; the failure paths reach it from all three of `start_weight_update`, `update_weights` and `finish_weight_update`. Placing the restore here is also what makes the guard complete: an update refused between chunks had already parked the weights on meta at `start`, so without the rollback that refusal would leave exactly the model the second bug produces. For a draft-model session the helper also puts the draft's quantized lm_head back (`restore_quantized_lm_heads(..., refresh=False)`), which main's start and update failure paths do since #59973; the asleep refusals and a failing finish now do it too.

Two things worth calling out:

- The restore is not a clean rollback. A layer whose chunks all arrived before the failure was already processed and copied back as it completed, so it keeps the new weights; only layers still mid-reload revert, and tied weights follow whichever side completed. The model can therefore hold a mix of the old and new versions until the trainer resends the whole update — `abort_layerwise_reload` logs a warning saying so, and the docstring and the docs spell it out. A session is dropped rather than resumed for the same reason, and after a level-2 sleep the chunks already received are gone regardless. `reset_lora_state()` is intentionally skipped on an aborted finish, since the base weights are no longer on one version.
- `finish_weight_update` used to leave the session active when `finalize_layerwise_reload` raised. On engines that roll back (`rolls_back_failed_updates`: IPC, NCCL, NCCL M2N) it now aborts the session too, so the model is usable and the trainer can start over. Engines with nothing to roll back keep the session open as before, so ModelExpress (#58399) can still retry a failed `finish_weight_update`, as its worker test expects.

One edge this does not try to fix: if `Worker.sleep` raises after the allocator has already unmapped the memory (the `freed_bytes >= 0` assertion), the executor never records the sleep and later `wake_up` calls return early, so the worker stays asleep and keeps refusing updates until restart. Refusing is still the right answer there, because the memory really is unmapped; the executor/worker disagreement is a pre-existing problem.

#51378 (draft RFC) proposes replacing layerwise reload with model-wide transactions and includes an engine-level `abort_weight_update` as part of that redesign; this PR adds only the hook and the rollback for the layerwise path that ships today, under the same name so the two compose.

## Test Plan

- `tests/v1/worker/test_gpu_worker_weight_transfer.py`: the sleep cases (start refused while asleep; update and finish refused with the session dropped; update allowed once `weights` is woken while `kv_cache` is still asleep; reload refused; tag bookkeeping across `sleep` / partial `wake_up` / `discard`), plus the failure cases (the engine is asked to abort before the target is reset on a failing start, update and finish; a failing finish on an engine without a rollback keeps the session and can be retried; an abort that itself raises does not hide the update error; a successful session never aborts).
- `tests/v1/worker/test_gpu_draft_lm_head.py`: a failed draft update ends the session with the quantized lm_head copy back in place, and the engine's abort runs while the drafter still shares the source head.
- `tests/model_executor/model_loader/test_reload.py`: abort with one layer half loaded, one fully loaded and one untouched — the half load is dropped, the completed layer keeps its new weights, nothing is left on meta, and a full reload works afterwards; abort with no reload open is a no-op.
- `tests/distributed/test_weight_transfer.py`: the IPC engine's `abort_weight_update` puts a CPU model back after `start_weight_update`, twice.
- `tests/distributed/test_weight_transfer_m2n.py`: the M2N engine runs `abort_layerwise_reload` only when its plan uses fallback entries.
- `tests/entrypoints/rl/weight_transfer/test_offline.py` (moved there from `tests/entrypoints/weight_transfer/test_weight_transfer_llm.py` by #59948): the sleep test (levels 1 and 2, partial wake, interrupted session, normal flow after a full wake) and a new failure test on the real IPC engine — a chunk with a wrong GPU UUID raises, greedy output before and after is identical, the dead session cannot be finished, and a fresh start/finish works. Without the rollback the generate after the failure raises `EngineDeadError`.
- Against a real server (IPC backend, `VLLM_SERVER_DEV_MODE=1`): the sleep sequences above, the three-call reproduction, and a trainer-driven variant that sends a chunk whose parameter name the model does not have and then resyncs.
- Docs: `docs/features/sleep_mode.md`, `docs/training/weight_transfer/README.md` (including the failed-update warning #62267 added, which now describes the rollback), the layerwise lifecycle table in `docs/training/layerwise.md`, and the engine API list in `docs/training/weight_transfer/base.md`.
