# [Kernel][DSv4.1] Bump FlashMLA to the 2026.09.30 release and its interleaved V4.1 KV cache

[Upstream PR](https://github.com/vllm-project/vllm/pull/61371) · state: closed · merged: True

## Original PR description

# Overview

Bump FlashMLA to vllm-project/FlashMLA@5dceadb (vllm-project/FlashMLA#30), which syncs upstream's 2026.09.30 release (deepseek-ai/FlashMLA#229). Upstream changed the DeepSeek-V4.1 KV cache records to an interleaved layout, so this moves vLLM's V4.1 cache writers and readers to it and aligns the packed DSv4.1 block to the new decode kernels.

## Claims

- vLLM builds against FlashMLA 5dceadb. V4.1 records (528 B MXFP8, 288 B NVFP4) written by vLLM now use the interleaved layout, and FlashMLA's V4.1 decode kernels and vLLM's own gathers read back exactly what the writers stored.
- DeepSeek-V4.1 serves end to end on SM100 with both FlashMLA backends; GSM8K is in the table below.
- KV capacity: a packed DSv4.1 block now has to hold whole rows of both V4.1 records. Relaxing the indexer's DeepGEMM alignment to 256 B (possible since #61149) keeps the loss at 9.5% instead of 24.6% on DSv4.1-Flash with MegaAttention.
- V3.2, V4.0, NVFP4 (V3.2 geometry) and SM90 keep FlashMLA's legacy kernels; their layouts and code paths are unchanged.

## Details

**Layout.** Upstream's V4.1 records used to put a page's data rows first and all its scale rows after. They are now interleaved, so token `i` sits at `i * 528` (512 fp8 values, then 16 UE8M0 scales) or `i * 288` (256 Bof e2m1 pairs, then 32 e4m3 scales). The writers (`fused_deepseek_v4_qnorm_rope_kv_insert`, `rope_quant_insert`, the MXFP8 quantize-and-insert in `cache_utils.py`) and readers (the Triton MXFP8 / NVFP4 gathers and the CuTeDSL dequant gather) only change their offsets. The V4.0 record (584 B, separate scale region) is untouched.

**Block stride.** The new decode kernels gather tokens with TMA as rows of a 2D view over the whole cache, so they require `k_cache.stride(0) % bytes_per_token == 0`. DSv4.1 packs every layer's page (SWA, compressed, indexer, compressor state) into one physical block, so each view's `stride(0)` is the whole block. `DeepseekV4SWACache` therefore takes `packed_block_stride_alignment`, and V4.1 sets it to `lcm(528, compressed record)`: 528 with `fp8_ds_mla`, 3168 with `nvfp4_ds_mla`. The KV cache planner already rounds the block up to the lcm of every spec's `block_stride_alignment`.

**Indexer alignment.** DeepGEMM's paged sparse MQA logits address pages as `base + page * stride` with 16 B loads; since #61149 (vllm-project/DeepGEMM#33) its guard is 256 B instead of 512 B. main still aligned the indexer to 512 B, which with V4.1 records would round the block up to `lcm(512, 528, 288) = 50,688` B (152,064 B, -24.6%). With 256 B it is `lcm(256, 528, 288) = 25,344` B (126,720 B, -9.5%). With V4.1 records the indexer leaves its page alignment out of that lcm, since the SWA spec now carries the record stride; with the V4 record it keeps the 576 B TMA stride in it.

**Compatibility.** The V4.1 KV cache bytes change layout, so V4.1 KV caches transferred or offloaded between builds before and after this PR are not interchangeable. Decode kernel speed is not claimed here; the V4.1 kernels are upstream's.

**Not a duplicate.** I searched open PRs for `bump FlashMLA`, `FlashMLA pin`, `flashmla.cmake`, `interleaved KV FlashMLA` and `FlashMLA 5dceadb`; none bumps the FlashMLA pin or changes the V4.1 record layout.
