# [Bugfix][KV Offload] Report only written blocks from fs tier store jobs

[Upstream PR](https://github.com/vllm-project/vllm/pull/63524) · state: open · merged: False

## Original PR description

## Overview

Block files in the `fs` tier are named by content hash, so when a prefix that is already on disk gets stored again, `_store_block` skips the write. The job still reported the full batch in `transfer_bytes`, and it completed in microseconds, so the back-pressure detector saw a big, instant write every time this happened. This PR makes the tier report only the blocks it actually wrote.

## Claims

- `transfer_bytes` now counts written blocks only, and is `0` when every block was already on disk. `BackpressureDetector.update` already ignores `num_bytes <= 0`, so these jobs stop feeding the EMA.
- Nothing else changes: same bytes on disk, same job success, same lookup verdicts and KV events. The C extension path and the pure Python path report the same counts.

## Validation

- `test_store_reports_only_newly_written_blocks` stores `[1, 2]`, then `[2, 3]`, then `[1, 2]` again, and checks the reported bytes are 2, 1 and 0 blocks and that block 2's file was never rewritten. Runs on both store paths. On `main` it reports 2 blocks every time.
- `test_update_ignores_jobs_that_wrote_nothing` pins the detector behaviour the fix depends on.
- `test_store_skips_block_published_after_filter` covers a block another writer publishes between the filter and the write, on both store paths. `test_store_accepts_block_published_by_another_writer` (#61390) now also asserts `transfer_bytes == 0`.
- `pytest tests/v1/kv_offload/tiering`: 588 passed, 1 skipped. `pre-commit` is clean.
- #61390 and #61780 have since merged; this is rebased on both.

## Details

This is the normal flow of tiering, not an edge case. The CPU tier is smaller than the filesystem tier, so it evicts a prefix, the next request recomputes it, stores it to CPU, and the completion cascades to `fs` again. There is no existence check before the cascade, so on a warm filesystem most of what the detector sees are these skipped writes. They drag the EMA down and keep the fast path engaged right when the filesystem might actually be slow.

The count comes from the writers themselves: Python `_store_block` returns whether it published the block, and `fs_io_C.batch_store_block` returns the number written instead of `None`. A block another writer publishes after the existence filter, or that wins the rename (EEXIST, #61390), is skipped and not counted; the store still succeeds. The Prometheus `WRITE_BYTES` and `WRITE_TIME` counters in `metrics.py` are computed from key count and are left alone here.
