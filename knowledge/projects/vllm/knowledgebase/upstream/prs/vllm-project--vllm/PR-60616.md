# [Docs][KV Events] Document the KV cache events contract

[Upstream PR](https://github.com/vllm-project/vllm/pull/60616) · state: open · merged: False

## Original PR description



## Overview

Documents the KV cache events wire contract in `docs/features/kv_events.md` and pins it with a CPU test. Follows up #20492, where a published schema, documentation and a conformance test were requested.

KVEvents are critical in production pipelines, yet their contract has never been formalized. Different module implementors have historically broken/abused the API, causing production pain.

## Claims

- `docs/features/kv_events.md` specifies the transport, encoding, event semantics, block hashing and compatibility rules for KV event consumers.
- `BlockRemoved` is defined per physical copy. Consumers count references per hash and scope (`medium`, `group_idx`, `locality`, `ownership`).
- `tests/v1/core/test_kv_events_contract.py` (`cpu_test`) checks four things:
  - the required fields are frozen;
  - new fields must default to `None`;
  - a canonical batch keeps its wire shape;
  - each stored copy of a hash gets exactly one removal.
- `BlockStored`/`BlockRemoved` field docstrings move below their fields, where they attach. `KVEventsConfig` docstrings state that `buffer_steps`, `hwm` and `max_queue_size` count batches.

No runtime behavior changes.

Each of these changes, applied alone, fails the new test:
- adding a required field;
- adding an unlisted optional field;
- `array_like=True` on events;
- emitting `BlockRemoved` only for the last copy, as in #58508.

## Details

- **Scope.** The page states current behavior. Where emitters differ, it lists what each one does.
- **Effect on open PRs.** Under the per-copy definition, #58508 changes semantics; #48933's additive `remaining_copy_counts` is compatible.
- **`AllBlocksCleared`.** It carries no scope, and pools differ in whether they emit it. Consumers therefore drop everything that publisher and DP rank reported.
- **No duplicate.** No open PR documents or tests this contract. #57789 adds a snapshots page at the same path and will rebase onto this one.
- **Follow-ups found while writing the page:**
  - `MooncakeStoreConnector` publishes `medium="cpu"`.
  - The LoRA path is hashed but not published.
  - `AllBlocksCleared` has no `medium`.
  - The example subscriber replays through a REQ socket, which receives only the first replayed batch.

Thanks for writing this down! One suggestion for the `BlockRemoved` section: it might help to state that the grouping of hashes into events is unspecified. Consumers should depend only on the per-hash sequence, not on how many events a set of removals arrives in. Something like:

> How removals are grouped into events is not part of the contract. Consumers must apply each listed hash in order and must not assume one event per block.

Context: #63390 coalesces consecutive same-group removals (74% fewer `BlockRemoved` events in serving; per-hash sequence identical to main), and it relies on exactly this. If the contract should instead guarantee one hash per event, I'd rather know now and drop the coalescing.
