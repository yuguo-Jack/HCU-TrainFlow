File: `vllm/v1/attention/backends/flashinfer.py` · line 1875

🟡 **Severity: MEDIUM**

`unbind(1)` on the interleaved `[blocks, 2, page_size, heads, dim]` cache produces **non-contiguous** views (stride[0] = 2×page_size×heads×dim). The CUDA kernel uses `data_ptr()` with contiguous offset arithmetic, so for any physical page p > 0 it reads from approximately page p/2 in the raw buffer. In a multi-tenant server those wrong pages may belong to other users' requests, leaking their KV cache data into the current user's attention output.
Helpful? Add 👍 / 👎

<details>
<summary>💡 Fix Suggestion</summary>

**Suggestion:** After calling `kv_cache_permute.unbind(1)`, both `key_cache` and `value_cache` become non-contiguous views with stride[0] = 2×page_size×heads×dim instead of the expected contiguous page_size×heads×dim. The CUDA kernel `paged_decode_partial_kernel` uses `data_ptr()` and assumes contiguous layout for its offset arithmetic, so for any physical page p > 0 it reads from the wrong location. Fix this by calling `.contiguous()` on each tensor after unbinding to force a contiguous copy before passing them to the CUDA kernel.

File: `csrc/attention/l20_paged_decode.cu` · line 295

⚪ **Severity: LOW**

The shared-memory array `corrections[64]` is indexed by `split` which iterates up to `num_splits`. The exposed `l20_paged_decode_split_out` torch op computes `num_splits = ceil(max_seq_len / split_size)` with no upper-bound check against 64, so a caller can trigger a shared-memory buffer overflow by supplying a large `max_seq_len` relative to `split_size`.
Helpful? Add 👍 / 👎

<details>
<summary>💡 Fix Suggestion</summary>

**Suggestion:** Add a `TORCH_CHECK` in the host-side wrapper functions to validate that `num_splits` does not exceed 64 (the size of the `corrections` shared-memory array in the kernel). Specifically, after the line `const int num_splits = (max_seq_len + split_size - 1) / split_size;` in both `l20_paged_decode` (around line 375) and `l20_paged_decode_split_out_cuda` (around line 413), insert:

```cpp
TORCH_CHECK(num_splits <= 64,
    "num_splits (", num_splits, ") exceeds the kernel shared-memory array size of 64; "
    "reduce max_seq_len or increase split_size");
```

This ensures any caller that supplies a `max_seq_len` / `split_size` combination that would produce more than 64 splits gets a clear error instead of triggering an out-of-bounds write into the `__shared__ float corrections[64]` array.
