# [Perf][MoE] Grouped W8A16 skinny GEMM for block-FP8 routed experts at small token counts (SM90)

[Upstream PR](https://github.com/vllm-project/vllm/pull/64983) · state: open · merged: False

## Original PR description



## Overview

Builds on #64980 (W8A16 skinny GEMM for the dense block-FP8 linear layers). At 1-4 tokens the Triton fused MoE on SM90 is far from memory bound: on `Qwen/Qwen3.6-35B-A3B-FP8` (256 experts, top-8, 128x128 block FP8) the first expert GEMM reads 16 MB of weights in 10.7 us (1.5 TB/s) and the second 8 MB in 5.8 us, and the layer quantizes its activations twice (before each GEMM). Whole expert path per layer at one token, measured in isolation: 27.7 us.

This PR adds a grouped variant of the shape-dynamic W8A16 skinny GEMM for the routed experts: one CTA per (token, expert) pair and output block, BF16 activations, FP8 weights with their 128x128 scales, FP32 accumulation, routing weight folded into the second GEMM's epilogue. `TritonExperts` takes it for 128x128 block-FP8 layers that have a plan for their expert shapes, at the planned token counts (1-4), without EP all2all or LoRA; on that path there is no activation quantization. Above the planned token counts and everywhere else, nothing changes. The layer reports `expects_unquantized_inputs` so that the prepare step hands it BF16 activations; for other token counts it quantizes them itself, with the same kernel as before.

## Claims

- **Expert path per layer, isolated (H200, cold weights, disjoint expert sets):** 1 token 27.7 -> 17.8 us (-36%), 2 tokens 34.0 -> 25.6 us (-25%), 4 tokens 49.6 -> 42.4 us (-15%). 8 tokens measure -8% in isolation but +4% TPOT in the model (see Details), so the plans stop at 4.
- **E2E, `Qwen/Qwen3.6-35B-A3B-FP8`, H200 TP=1, on top of #64980:** median TPOT -10.2% at one request (3.574 -> 3.208 ms), -8.3% at 2, -4.5% at 4, unchanged at 8 (Triton path).
- **E2E, `Qwen/Qwen3-30B-A3B-FP8` (128 experts, plans for 1-2 tokens):** median TPOT -9.9% at one request (4.166 -> 3.755 ms), -6.3% at 2; 4 and 8 requests take the Triton path (a plan for 4 tokens made that model 2% slower, see Details).
- **Accuracy:** W8A16 is closer to the dequantized reference than the W8A8 Triton path (max relative error 3.6e-3 vs 4.0e-2 on random experts); GSM8K 0.7354 / 0.7369 vs 0.7430 for the base (run-to-run spread of this model is 0.728-0.741).
- **Applies to** any 128x128 block-FP8 MoE layer on SM90 whose expert shapes have a plan; this PR ships plans for the Qwen3.5/3.6-35B-A3B experts (`(1024, 2048)` gate_up, `(2048, 512)` down) and the Qwen3-30B-A3B experts (`(1536, 2048)`, `(2048, 768)`). Other shapes keep the Triton path until measured.

## Details

- **Why 4 tokens and not 8.** The kernel reads an expert's weights once per (token, expert) pair; the Triton path groups pairs by expert and reads each expert once. With 8 tokens of real traffic enough pairs share experts that this costs more than the kernel saves: a run with plans up to 8 tokens gave 6.005 / 6.010 ms at 8 requests against 5.764 ms without (+4%), although the isolated measurement with disjoint expert sets was 8% faster. At 4 tokens Qwen3.6 (256 experts) still gains 4.5%, while Qwen3-30B (128 experts, so more sharing) loses 2%, which is why its plans stop at 2 tokens. A per-expert grouping of the pairs (read each expert once, as the Triton path does) would lift both limits and is the natural follow-up.
- **Padded pairs.** vLLM's warmup and profiling runs route padded tokens to expert `-1`; the kernel skips those pairs and writes zero rows, so the top-k sum stays finite.
- **Why `expects_unquantized_inputs`.** The prepare step quantizes activations before `apply`; the kernel needs them in BF16. When the layer has a plan it asks for unquantized activations and quantizes them in `apply` for token counts that take the Triton path, with the same `moe_kernel_quantize_input` call, so those counts see the same kernels as before. DP, EP all2all, LoRA and `expert_map` layers never take the path.
- **Eligibility is decided before the path is taken.** `TritonExperts` checks both expert stacks (contiguity, scale shapes, the configs' divisibility) and the routing weights per call and otherwise runs the Triton path; the kernel wrapper only re-validates. Ids outside `[0, E)` produce zero rows like padding.
- **Two kernels, one loop.** The grouped kernel repeats the dense skinny kernel's tile loop and reduction (about 60 lines) rather than threading an expert index through the dense kernel, so the dense path stays untouched and both can be tuned separately; folding them into one kernel once both have settled is a reasonable follow-up.
- **Workspace.** The grouped kernel writes into the same `workspace2` / `workspace13` buffers the Triton path uses (`(tokens * top_k, N)` and `(tokens * top_k, N / 2)`), so no extra memory.
- **Plans** live next to the dense FP8 plans in `skinny_gemm_plans.py`, keyed by one expert's `(N, K)` and the token count, under capability `(9, 0)`.
