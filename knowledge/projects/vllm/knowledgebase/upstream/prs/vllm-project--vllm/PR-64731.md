# [Perf][Kernel] Faster full-warp MoE top-k selection with redux.sync

[Upstream PR](https://github.com/vllm-project/vllm/pull/64731) · state: open · merged: False

## Original PR description

> **Status:** folded into #62912 together with its author (co-authored). This PR stays open for reference until that lands.

## Overview

Speed up `topkGating` (`csrc/moe/topk_softmax_kernels.cu`) for rows that one full warp owns (128-576 experts, depending on the logits dtype) without a correction bias. Each top-k round is two `redux.sync` (max score, then min expert among the lanes holding it) instead of the shuffle butterfly. Lane `i` keeps the `i`-th selection in registers, the row is written once, and only the lane that owned the winner rescans. Output is bitwise identical to `main`.

Any model whose router goes through `topk_softmax` takes the new path, e.g. Qwen3.8-Flash-Next on DeepGEMM MegaMoE (#64315) and the Triton/DeepGEMM MoE backends. The default Blackwell path for Qwen3.8-Flash-Next (FlashInfer TRTLLM) routes inside its own kernel and is unaffected.

Related:
- #62912 (@kimseunghyun-kr) introduced the same `redux.sync` selection with a per-round store; this PR adds the register-resident output path. The two are now combined in #62912, which is a further 4-9% faster than this PR on B300 (bitwise equal; numbers in #62912).

## Claims

- **1.6-2.5× faster than `main`** for E=512 top-10 at every M from 1 to 8192 (bf16 and fp32 logits), and **1.3-2.2× faster than #62912's first revision**, on B300.
- **Bitwise identical** to `main`: weights, expert ids and token-expert indices, in 252/252 microbenchmark case-runs and 11,520 wider cases.
- **E2E within noise**: the kernel saves 0.2-0.3 ms per decode step (0.6-1.5% of the step). Serving Qwen3.8-Flash-Next shows no measurable change at c16/c64 and about +1% at c464, against a 0.5-1.9% base-vs-base noise floor.
- **Unchanged accuracy**: full GSM8K within noise of `main`; 200/200 identical greedy outputs.
- Sub-warp rows (E=128 with 16-bit logits), biased routing and k > 32 keep the existing loop with unchanged code generation (1.00×).

**Method.**
- GPU and stack: B300 SXM6, driver 595.112.07, torch 2.14.0+cu130, FlashInfer 0.7.2.post1, CUDA 13.1 toolchain.
- Each arm is a separate `_moe_C_stable_libtorch` build of `csrc/moe/topk_softmax_kernels.cu`, loaded with `torch.ops.load_library` in its own process. Inputs are seeded identically.
- Inputs and outputs are preallocated outside the timed region, and 25 warm-up calls run before timing.
- Each round runs main → #62912 → PR, rotated by one each round.
- Bitwise check: weights compared as int32 bits, plus expert ids and token-expert indices, for every case and run.
- GB/s = (tokens × E × logit bytes + tokens × k × 12) / time.
- The kernel has no tunable knobs; the launch config is the same as on `main`.
- Biased routing keeps the existing instantiation, with code generation identical to `main` (0.99-1.01x).
- Latency is the meaningful metric: ideal traffic (logits read once, plus weights, ids and indices written) reaches only 123 GB/s at 464 tokens and 471-869 GB/s at 8192 tokens, so the kernel is latency-bound at decode sizes.

```bash
# Build each arm (same build dir and flags), keeping one library per arm:
#   cmake --build <build-dir> --target _moe_C_stable_libtorch && cp <build-dir>/_moe_C_stable_libtorch.abi3.so libs/moe_<arm>.so
arms=(main pr62912 pr)
for r in 0 1 2; do for i in 0 1 2; do
  v=${arms[$(( (i + r) % 3 ))]}
  CUDA_VISIBLE_DEVICES=0 python topk_cupti_bench.py libs/moe_$v.so out/${v}_r$r.json out/${v}_r$r.pt
done; done
```

```python
# topk_cupti_bench.py <_moe_C .so> <out.json> <outputs.pt>
import json, statistics, sys
import torch
from flashinfer.testing import bench_gpu_time_with_cupti

torch.ops.load_library(sys.argv[1])
TOKENS = (1, 4, 16, 64, 128, 256, 464, 1024, 2048, 4096, 8192)
CASES = [(dt, 512, 10, t) for dt in (torch.bfloat16, torch.float32) for t in TOKENS]
CASES += [(torch.float32, 256, 8, t) for t in (1, 64, 4096)]
CASES += [(torch.bfloat16, 128, 8, t) for t in (1, 64, 4096)]
res, outs = {}, {}
for dt, e, k, t in CASES:
    key = f"{str(dt)[6:]}/E{e}/k{k}/t{t}"
    x = torch.randn(t, e, device="cuda", generator=torch.Generator(device="cuda").manual_seed(t * e + k)).to(dt)
    w = torch.empty(t, k, device="cuda")
    ids = torch.empty(t, k, dtype=torch.int32, device="cuda")
    tei = torch.empty_like(ids)
    run = lambda: torch.ops._moe_C.topk_softmax(w, ids, tei, x, True, None, None)
    run(); torch.cuda.synchronize()
    outs[key] = [w.view(torch.int32).cpu(), ids.cpu(), tei.cpu()]
    for _ in range(25):
        run()
    torch.cuda.synchronize()
    us = statistics.median(bench_gpu_time_with_cupti(run, use_cuda_graph=True, cold_l2_cache=True)) * 1e3
    res[key] = {"us": us, "gbps": (t * e * x.element_size() + t * k * 12) / (us * 1e3)}
json.dump(res, open(sys.argv[2], "w"))
torch.save(outs, sys.argv[3])
```

## Details

Dispatch logic
- The launcher selects the new instantiation (`FULL_WARP_SELECT`) only when one full warp owns a row (128-576 experts, depending on the logits dtype), there is no correction bias, and k ≤ 32. It is compiled for SM80+ CUDA (`redux.sync`); ROCm and older archs keep the existing loop.
- Everything else (biased routing, sub-warp rows, k > 32) takes the existing loop through a separate instantiation, so its code generation is identical to `main`.

Tests
- `tests/kernels/moe/test_fused_topk.py`: 1080 passed on B300. The new `test_topk_without_bias_matches_zero_bias` compares the no-bias launch (new path) bit for bit with an all-zero-bias launch (old loop): E ∈ {128, 384, 512}, top-k ∈ {1, 10, 32}, softmax/sigmoid, bf16/fp32, random and tie-heavy (NaN/±Inf) logits. A variant with a wrong tie rule fails 120 of those cases. The L4 MoE kernel CI job runs this file.
- Outside CI: 11,520 cases (E 128-576, top-k 1-40, fp32/bf16/fp16, softmax/sigmoid, padding, CUDA graph) bitwise equal to `main` and #62912.
- `benchmark_fused_topk.py` gains `--dtype` (default bf16, as before) for fp32 router logits. `pre-commit run --files` passes.

Limitations
- Measured on B300 (SM100) only; A100 numbers for the combined kernel are in #62912.
- An ablation (this selection with #62912's per-round store) runs at #62912's speed, so the gain over #62912 comes from the output path.
- An earlier run on Qwen3-Next-80B (bf16, Triton MoE, TP1) gave 400/400 identical greedy outputs and GSM8K 0.864 vs 0.869; e2e within noise there too.
