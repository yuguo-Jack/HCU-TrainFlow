# [HiSparse] Bound prefill staging temporaries by chunk, not prompt length

[Upstream PR](https://github.com/vllm-project/vllm/pull/60706) · state: closed · merged: False

## Original PR description

## Purpose

Part of #60420. When a HiSparse prefill stages history that has spilled to host, two temporaries grow with prompt length:

- `HiSparsePrefillStagingPlan.ensure_gpu_sources` built a `num_unique_blocks × max_blocks_per_req` int64 table (about 2.1 GiB at 1M tokens). It now indexes the entries it needs directly.
- The resident-row copy gathered a second staged-size tensor before copying. It now copies in 64K-row chunks.

Same results, smaller temporaries.

## Test Result

1×B200, GLM-5.3-NVFP4 cut to 4 layers with dummy weights, fp8 KV, 1.04M-token prompt with 2 requests decoding:
- Greedy token ids and logprobs are bit-identical to main (FlashInfer fp8), including spilled prompts up to 524K with decodes running.
- In this workload the peak isn't set by these temporaries, so it doesn't change on its own: #60424 + this PR measured the same as #60424 alone (+1.50 GiB over profile at 1.04M). These temporaries set the peak once the larger allocations are gone. An earlier version of #60424 that preallocated the attention output before staging ran out of memory in `ensure_gpu_sources` at about 640K tokens, and these two changes fixed that.
- `pytest tests/v1/attention/test_sparse_mla_backends.py tests/v1/kv_connector/unit/test_hisparse_connector.py` on B200: 412 passed, including the new `test_hisparse_gather_prefill_cache_prefers_resident_rows[3]`, which splits the copy into several chunks and fails if the chunk offset is wrong.
