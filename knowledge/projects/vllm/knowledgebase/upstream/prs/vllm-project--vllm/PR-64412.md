# [Bugfix][Frontend] Pool HF fast tokenizers in all renderers

[Upstream PR](https://github.com/vllm-project/vllm/pull/64412) · state: closed · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Fixes #64034.

Only `HfRenderer` wrapped its HF fast tokenizer with `maybe_make_thread_pool`. Renderers that inherit `BaseRenderer` directly (`CohereRenderer`, `DeepseekV4Renderer`, `DeepseekV32Renderer`, `InklingRenderer`, `KimiK3Renderer`) shared one tokenizer across `--renderer-num-workers` threads, which can raise Transformers'
`RuntimeError: Already borrowed`.

Duplicate check: issue #64034 is open, unassigned, has no comments, and `gh pr list --search "64034 in:body"` returns 0. A keyword search for renderer tokenizer thread-safety found only unrelated #63463.

## Claims

- Make every renderer wrap `TokenizersBackend` tokenizers in the existing per-worker pool, not just `HfRenderer`.
- Leave non-HF tokenizers (e.g. `MistralTokenizer`) and `skip_tokenizer_init=True` untouched.
- Preserve tokenization output; only the concurrency behavior changes.

Caveat: this environment has no DeepSeek-V4-Flash checkpoint/GPU, so the original `Already borrowed` crash was not reproduced. The regression test pins the invariant that `HfRenderer` already relied on; verification of the original scenario by the reporter is requested.

## Details

Root cause: `BaseRenderer.__init__` builds an executor with `renderer_num_workers` threads and every thread calls `self.get_tokenizer()`. `HfRenderer` called `maybe_make_thread_pool` after `super().__init__`; the other renderers never did. HF fast tokenizers are backed by one Rust tokenizer whose mutable borrow state is not thread-safe, hence
`Already borrowed` under concurrent rendering.

Implementation: copy the tokenizer and call `maybe_make_thread_pool` in `BaseRenderer.__init__`, after multimodal processor creation so the previous ordering for `HfRenderer` is preserved. The copy keeps the cached/shared tokenizer unmodified, and already-pooled tokenizers are left alone. The redundant call in `HfRenderer` is removed.

Tradeoff: each renderer now creates `renderer_num_workers + 1` deep copies of a fast tokenizer at startup. This is the same allocation `HfRenderer` already performed, and it does not apply to non-HF or Python-backed tokenizers.
