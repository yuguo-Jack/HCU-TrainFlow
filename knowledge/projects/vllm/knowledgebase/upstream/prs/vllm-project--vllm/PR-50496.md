- tomas-polach · COMMENTED · 2026-08-07T19:05:43Z · [source](https://github.com/vllm-project/vllm/pull/50496#pullrequestreview-4885822121)

we were testing today with @loleg: text and visual works like a charm but we spotted a streaming-only bug with direct tool calls (no thinking block). In LibreChat this showed up as raw `<|tools_prefix|>[...]` JSON leaking into the visible assistant message instead of triggering the tool call, so MCPs stop working.

`ApertusReasoningParser.extract_reasoning()` already handles the "no thinking block at all" case correctly for non-streaming (returns the whole output as content), but there's no `is_reasoning_end_streaming()` override. `BaseThinkingReasoningParser`'s default only flips `is_reasoning_end` once it sees the *end* token. If the model commits to a direct tool call and never emits the start token either, the end token never arrives, so `DelegatingParser.parse_delta()` never leaves "reasoning phase" for the rest of that stream, and the tool parser never runs; the raw `<|tools_prefix|>[...]` text leaks into `content` instead of populating `tool_calls`.

Suggestions inline below, mirroring the same assumption `extract_reasoning()` already makes, just applied per-delta, including a streaming test case since the existing `test_output_without_deliberation_is_all_content` only covers non-streaming.

- AryanAhadinia · comment · 2026-08-13T18:56:23Z · [source](https://github.com/vllm-project/vllm/pull/50496#issuecomment-5285087552)

@tomas-polach, Thank you for this, it is a good catch, and it sent me down a useful path. I wanted to measure everything properly before replying, so this took a while. Your reading of the code is exactly right: the base parser only ends the reasoning phase when it sees the end token, so a turn with no thinking block never leaves that phase. I committed your test as well, and it does what you intended, failing without your change and passing with it.

**Why the patch does not help us, and where it hurts.** By design, Apertus 1.5 is served with either a reasoning parser or a tool-call parser, never both on one endpoint. Users pick the mode they want. The switch your patch repairs has exactly one job: stop feeding the stream to the reasoning parser and start feeding it to the tool parser. On a reasoning-only endpoint there is nothing to switch to, and the text goes out as ordinary content whether the phase ends or not, so nothing about the response changes. The one caller that does react to the switch is structured output, where vLLM asks the reasoning parser at every decode step whether reasoning is over and only then applies the JSON grammar. There the patch makes things worse. Two endpoints identical apart from it, strict json_schema, thinking off, temperature 0, six runs each: without the patch the answer came back as `{"city": "Zurich", "celsius": 14}`, and with it as `{"{"city": "Zurich", "celsius": 14}`, which is not valid JSON. The doubled opening token is the tell. The patch ends the reasoning phase on the first generated token, so vLLM treats that token as the end marker and skips it when advancing the grammar, the grammar then starts from its initial state and emits its own `{` on top of the one the model already wrote. The signal you identified is right, but a per-step answer arrives one token too late, because the bitmask for a token is chosen before that token is sampled.

**What does fix it.** The question has to be answered before generation starts, and vLLM already asks it there, in `should_fill_bitmask` and when building the engine flag in `chat_completion/serving.py`. A turn rendered with "Deliberation: disabled" is past reasoning before its first token, so the parser can simply say so, the same way `qwen3.py` and `glm47_moe.py` already do with their `thinking_enabled` flag. Ten lines in our own parser, no changes anywhere else in vLLM, and the grammar then applies from the first token and the JSON comes back clean. There is a neat confirmation that this is the right place: sending `include_reasoning=false` on an unpatched server already produces correct JSON, because the frontend then marks reasoning as finished before generation. Same server, same model, same prompt, no parser change at all.

**Why we are not applying it either.** Once we measured how the bug is reached, it turned out to need a client to explicitly send `enable_thinking: false` together with `response_format` on a reasoning endpoint. Default traffic is unaffected, thinking-enabled requests are unaffected, and anyone who wants structured output without deliberation can use the non-thinking deployment, where no reasoning parser gates the grammar at all. The fix also carries a small behaviour trade: with thinking off it treats reasoning as finished from the start, so a block the model emits anyway would stream into content instead of reasoning_content. For a path that needs a deliberate opt-out to reach, we would rather keep the parser as it is and document the combination than take a behaviour change into the release. If a user does hit it, the diagnosis and the ten lines are written up and ready.

One last thing: since neither patch is landing, your test comes out with them, purely because it only passes with your change. That is not a verdict on the test. It is what proved the mechanism was real and pushed us to measure the structured output path, which is where the actual bug turned out to be. Thanks again for the careful review.
