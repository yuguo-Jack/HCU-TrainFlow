# [Bugfix][Realtime] Ignore a final commit when no transcription is running

[Upstream PR](https://github.com/vllm-project/vllm/pull/65426) · state: open · merged: False

## Original PR description

## Overview

On `/v1/realtime`, an `input_audio_buffer.commit` with `final: true` sent while no transcription is running still queues the end-of-audio marker. The next transcription reads that marker first and ends at once. This change only queues the marker while a generation task is running.

## Claims

- A spare or repeated final commit no longer empties the next turn.
- The session no longer drifts one turn behind afterwards.
- Behaviour is unchanged when commits follow the documented order (commit starts a run, final ends it).

## Validation

New test `test_final_commit_without_generation_is_ignored` in `tests/entrypoints/speech_to_text/realtime/test_realtime_validation.py`: transcribe a turn, send one extra final commit, then transcribe a second turn.

```
pytest tests/entrypoints/speech_to_text/realtime/test_realtime_validation.py -v
```

- main 01b6a05b7: the new test fails with `assert 'Mary had a little lamb' in ''`; the other 5 tests pass.
- This branch: all 6 pass.
- The CI step `entrypoints-integration-speech_to_text` selects this file.

End to end with Voxtral-Mini-4B-Realtime-2602, on 0.30.0 and on main: turn 1 returns the full JFK sentence and turn 2 returns `''`. With the fix, both turns return their text, and so do three turns after a double final.

`ruff check` and `ruff format --check` pass. I didn't run mypy or the full `tests/entrypoints` suite.

## Details

Root cause, in `connection.py`:
- A final commit always calls `audio_queue.put_nowait(None)`.
- `audio_stream_generator` stops at the first `None`.
- `_run_generation` clears the queue only after it has sent `transcription.done`.

So a `None` that arrives after that stays in the queue, and the next run reads it before any audio. That run returns empty text. The queue is then cleared while the client is still sending that turn's audio, so every later turn starts with stale audio.

Alternatives considered:
- Sending an `error` event: this adds a new error code, and clients that send a defensive final would see errors.
- Dropping stale markers when a run starts: this touches the queue internals and still lets stale audio through.

Trade-off: a client that sends `final` before the starting commit now gets a run that ends only at the length limit. The docs and both example clients send final after the starting commit.

Not a duplicate: I searched open issues and PRs for realtime final/commit/empty-transcription and read the 11 open PRs that touch `realtime/connection.py`; none guards the final commit. #48130 rewrites the same `put_nowait(None)` line, so whichever lands second has a one-line conflict.

AI assistance was used: Claude Code found the bug through a protocol probe and drafted the fix and test. I reviewed every changed line and reran the test.
