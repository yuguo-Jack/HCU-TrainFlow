# [CI][Bugfix] Ignore soft-failed jobs in `/ci retry` on a new commit

[Upstream PR](https://github.com/vllm-project/vllm/pull/62548) · state: open · merged: False

## Original PR description



## Overview

`/ci retry` on a new commit refuses to run when a previous build's failed jobs include a soft-failed `image-build-*` step, even though a soft fail never blocks the PR. This ignores soft-failed jobs for that command.

## Claims

- A soft-failed `image-build-*` (or setup-step) job no longer triggers the "failed during CI setup" refusal; the real failures are re-run.
- Soft-failed jobs are not added to the set of step keys re-run on the new commit.
- A hard-failed `image-build-*` job still refuses, as before.

## Validation

- Motivating case: Buildkite `ci` build 95468 had three failed jobs: `image-build-xpu` (soft_failed=true) and two `lora-tp-distributed` L4 jobs (soft_failed=false). The bot refused instead of re-running the two LoRA jobs. The Buildkite jobs endpoint the bot calls returns `soft_failed` on each job item.
- `python -m pytest .github/workflows/scripts/test_run_ci_command.py -q`: 66 passed. Four new tests cover soft-failed image build, soft-failed non-image job, only-soft-failures, and a hard-failed image build regression guard.
- Removing the `soft_failed` condition makes three of the new tests fail. A scoped mutmut run on the changed lines killed 7 of 7 mutants.
- Not run against live Buildkite or a real PR comment.

## Details

- One filter in `handle_retry_failed`, applied before both the missing-step-key check and the setup check, so all later uses see only hard failures.
- The same-commit path uses Buildkite's `retry_failed_jobs` endpoint, which does not go through this list, so it is unchanged.
