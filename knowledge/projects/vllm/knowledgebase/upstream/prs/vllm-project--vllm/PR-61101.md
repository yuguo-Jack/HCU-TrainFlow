# [Bugfix][Spec Decode] Support dynamic speculative decoding in ngram_gpu (#60981)

[Upstream PR](https://github.com/vllm-project/vllm/pull/61101) · state: open · merged: False

## Original PR description

Fixes #60981

## Purpose

In `vllm/v1/spec_decode/ngram_proposer_gpu.py:340`, `NgramProposerGPU.propose` hardcodes `assert num_speculative_tokens == self.k`. When dynamic speculative decoding is configured (e.g. via `num_speculative_tokens_per_batch_size`), the scheduler dynamically requests fewer speculative tokens under load (including K=0 or sub-step K < k). This caused an immediate `AssertionError` and killed the worker process (`EngineDeadError`).

This PR:
1. Relaxes the assertion to `assert 0 <= num_speculative_tokens <= self.k` (matching the CPU implementation in `ngram_proposer.py:38`).
2. Safely handles `num_speculative_tokens == 0`: scatters newly sampled tokens to `token_ids_gpu` to maintain historical context, then returns empty tensors `[batch_size, 0]` without running the kernel.
3. When `num_speculative_tokens < self.k`, slices proposed draft tokens to `num_speculative_tokens` and clamps `num_valid_draft_tokens`.
4. Adds unit tests covering full-step K, sub-step K, K=0 context preservation, and multi-tier dynamic schedules.

- **Hardware**: 1× NVIDIA L20 (48GB)
- **Model**: `Qwen/Qwen3-0.6B` (`Qwen3ForCausalLM`, bf16)
- **Speculative Configuration**:
  ```python

      "method": "ngram_gpu",
      "prompt_lookup_min": 2,
      "prompt_lookup_max": 5,
      "num_speculative_tokens": 4,
      "num_speculative_tokens_per_batch_size": [[1, 16, 4], [17, 256, 0]],
  }
  ```

**Before Fix:**
Sending 24 concurrent requests triggered scheduler K=0, crashing immediately with:
```text
(EngineCore pid=3260083) ERROR [core.py:1507]   File "vllm/v1/spec_decode/ngram_proposer_gpu.py", line 340, in propose
(EngineCore pid=3260083) ERROR [core.py:1507]     assert num_speculative_tokens == self.k
(EngineCore pid=3260083) ERROR [core.py:1507] AssertionError
vllm.v1.engine.exceptions.EngineDeadError: Engine core process died.
```

**After Fix:**
- Batch size 1 (K=4): Completed in 0.12s with expected draft speedup.
- Batch size 24 (K=0 -> K=4 transition): All 24 requests completed successfully in 0.48s with valid token generation (0 failures).
- Multi-tier Schedule (`[[1, 8, 4], [9, 16, 2], [17, 256, 0]]`): 20 concurrent requests completed seamlessly across all tiers (K=0 -> K=2 -> K=4).
