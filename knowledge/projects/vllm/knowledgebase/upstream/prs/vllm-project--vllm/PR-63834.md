# [Bugfix][Model] Nemotron VL: keep the video placeholder when it directly follows text

[Upstream PR](https://github.com/vllm-project/vllm/pull/63834) · state: open · merged: False

## Original PR description

## Overview

Nemotron VL (`nano_nemotron_vl.py`, e.g. Nemotron 3.5 Super VL / Nemotron 3 Nano Omni) rejects a valid video request with HTTP 500 whenever the `<video>` placeholder directly follows non-whitespace text. This PR makes the model's multimodal processor re-encode text segments separately in the prompt-update fallback, as `minicpmv.py` already does for the same reason.

## Claims

- Fixes `Expected there to be 1 prompt placeholders corresponding to 1 video items, but instead found 0 prompt placeholders!` for prompts such as `"Describe this clip.<video>"` (text part followed by a video part with no separator, or a user-supplied placeholder inside the text).
- No behaviour change for prompts whose placeholder is already delimited (`"...\n<video>"`): they still take the token-level path.
- Model-local change only (one method override on `NanoNemotronVLMultiModalProcessor`, +56 lines); no change to the shared processor.

## Validation

Root cause reproduced with the real Nemotron 3.5 Super VL tokenizer (`<video>` is not a vocabulary token):

| prompt | token-level match | text fallback, joined re-encode | text fallback, segments encoded separately |
| --- | --- | --- | --- |
| `Describe this clip.<video>` | no (`.<`, `video`, `>`) | replacement not found (`.Frame` merge) | found |
| `<video>\nDescribe this clip.` | no (`>\n`) | found | found |
| `Describe this clip.\n<video>` | yes | n/a | n/a |

New GPU-free tests in `tests/models/multimodal/test_nano_nemotron_vl.py` use a small tokenizer that reproduces both merges:

- `test_video_placeholder_adjacent_to_text_is_replaced` (3 prompts): **fails without the fix** on the two adjacent prompts (`2 failed, 2 passed`) and passes with it (`4 passed`), run against an installed vLLM v0.32.0.
- `test_video_placeholder_adjacent_to_text_needs_segment_encoding`: documents that `BaseMultiModalProcessor._apply_prompt_updates` alone loses the placeholder for this model.
- Existing `test_nano_nemotron_vl.py`: `17 passed`.

`ruff format` / `ruff check` clean on both files.

## Details

The video `PromptReplacement` target is `cached_encode(tokenizer, "<video>")`, which yields `<`, `video`, `>` because `<video>` is not in the vocabulary (unlike `<image>`, `<img>`, `</img>`, which are added tokens). When text precedes the placeholder, BPE merges across the boundary (`.<`) and `apply_token_matches` finds nothing. The base class then falls back to `_apply_prompt_updates_via_text`, which joins `prompt_prefix + decoded_replacement + suffix` and re-encodes it in one pass; the video replacement begins with ordinary text (`Frame 1 sampled at 0.00 seconds: `), so the same kind of merge now happens at the new boundary (`.Frame`) and `find_mm_placeholders` cannot locate the replacement sequence.

`_apply_prompt_updates_via_text(..., encode_segments_separately=True)` exists for exactly this situation and is used by MiniCPM-V. The override here mirrors that implementation. The alternative of normalising the prompt text (inserting `\n` before an adjacent `<video>`) would change the prompt the model sees and only covers the leading boundary, so it was not taken.

The chat template shipped with the current public checkpoints inserts a newline between a text part and a following video part, so the OpenAI chat endpoint usually avoids this today; raw prompts, user-supplied placeholders in text, and older or custom templates still hit it.
