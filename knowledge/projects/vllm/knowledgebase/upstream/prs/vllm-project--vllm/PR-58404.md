# [FS-Offloading] Batching for FS threadpool

[Upstream PR](https://github.com/vllm-project/vllm/pull/58404) · state: open · merged: False

## Original PR description

## Purpose
Implement RFC https://github.com/vllm-project/vllm/issues/57106 

### Design: 
New file (dispatch.py) and new class (WorkDispatcher) that is responsible for, 
    - Batching policy.
    - What to batch and how
    - What job to execute and when - The PR no longer respects FCFS for reasons in the RFC. 
 
### Changes:
 - Failed Keys reporting: On `main`, a single job is processed by 1 threads. The threads stops on first failure. With Batching, a Job is processed by multiple threads. This requires failed_keys reporting by the thread-pool. 
 - Optimization: Introduce a separate _idle_condition variable in thread_pool.py so we don't not wake up rw threads. 
 - WorkDispatcher: Follows RFC closely. 
 
 
## Performance: 
bench script: 
[bench.sh](https://github.com/user-attachments/files/32569929/bench.sh)
```
MODEL="openai/gpt-oss-120b"
TP_SIZE=2       
CPU_BYTES=25GB
KV offload block-sizes : {1024, 16}
```
```
Workloads: Prefill (output-tokens=1) / Decode (output-tokens=512)
```
```
Guidellm: 
BENCH_MAX_SECONDS=700
BENCH_RANDOM_SEED=889
BENCH_TURNS=5
BENCH_PROMPT_TOKENS=4096
BENCH_PREFIX_TOKENS=20000
CONCURRENCY=64
```

Note : Benchmarking multi-turn conversations with Offloading has considerable variance. The root cause of the variance is the CPU KV cache space. A momentary unavailability of CPU cache space, has lasting effects. (When a conversations first turn, with 20K tokens) isn't offloaded, vLLM simply has to recompute in the next turn).
