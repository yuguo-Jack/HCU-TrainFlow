# [Bugfix] Fix ZeroDivisionError when Dynamic SD schedule includes K=0 for DSpark draft cudagraph capture

[Upstream PR](https://github.com/vllm-project/vllm/pull/47737) · state: closed · merged: False

## Original PR description

## Purpose

Dynamic Speculative Decoding (DSD) allows `num_speculative_tokens_per_batch_size` entries with `K=0`, meaning no draft tokens at high concurrency. When initializing CUDA graph candidates, `CudaGraphManager._init_candidates()` expands each schedule entry into a decode query length via:

`decode_query_len = K + (manager.decode_query_len - config.num_speculative_tokens)`

For **DSpark with anchor-as-first** (DeepSeek V4 default), the draft `DFlashCudaGraphManager` passes `decode_query_len = num_query_per_req = K_max`, so the recovered bonus term is **0**. A schedule entry with `K=0` therefore yields **`decode_query_len = 0`**, and `round_up(num_tokens, 0)` raises `ZeroDivisionError` during worker startup (e.g. `DFlashCudaGraphManager` init for DSpark).

This does not affect DFlash / 1+N layouts, where the bonus term is 1 and `K=0` maps to `qlen=1`.

**Fix:** Skip DSD schedule entries whose computed decode query length is `<= 0`. `K=0` disables drafting, so no draft FULL decode graph is needed for that shape. Target-model capture is unchanged (`K=0` still maps to `qlen=1` there).

**Test:** Add `test_dynamic_sd_skips_zero_draft_tokens_in_cudagraph_schedule` covering the DSpark anchor-as-first case with a schedule containing `[97, 128, 0]`.

This config passes schedule validation:

```text
--speculative-config '{"method":"dspark","num_speculative_tokens":5,"draft_sample_method":"greedy","num_speculative_tokens_per_batch_size":[[1,3,5],[4,256,0]]}'
```

```text
cudagraph_utils.py:234 in _init_candidates
  rounded_num_tokens = round_up(num_tokens, decode_query_len)
math_utils.py:22 in round_up
  return ((x + y - 1) // y) * y
ZeroDivisionError: integer division or modulo by zero
```
