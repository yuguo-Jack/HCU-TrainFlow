# [Bugfix][Weight Transfer] Re-apply composed-loader transforms in sharded_rdt replay

[Upstream PR](https://github.com/vllm-project/vllm/pull/63831) · state: closed · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

`sharded_rdt` weight transfer silently corrupts every Mamba2 layer: the baked replay lands raw `A_log` in `MambaMixer2.A` instead of `-exp(A_log)`. This makes the replay re-apply `composed_weight_loader` post-load transforms. Ported from the same fix in SkyRL's copy of this engine (NovaSky-AI/SkyRL#2336).

## Claims

- After a `sharded_rdt` sync, Mamba2's `A` matches what `load_weights` produces. The same path covers every `composed_weight_loader` user (plamo3, LongCat-Flash, DeepSeek-V4.1 fused layout), but only Mamba2 is validated here.
- Re-initializing the engine applies each transform once, not once per bake, and `shutdown()` releases the modules it captured.
- No change for models without composed loaders: `_post_load_fns` stays empty and the replay path is unchanged.

## Validation

`TestBakeOnARealModel` replays the baked plan against a synthesized checkpoint and asserts the result equals `load_weights`. I added a tiny Mamba2 model to it (`yujiepan/mamba2-codestral-v0.1-tiny-random`):

| | `mamba2` |
|---|---|
| `main` | **fail**: `replay differs from load_weights for: ['backbone.layers.0.mixer.A', 'backbone.layers.1.mixer.A']` |
| this PR | pass |

Results on 1x B200 with this PR:
- `pytest -v -s tests/distributed/test_sharded_rdt_plan.py`: 132 passed. That is 128 CPU tests, including the 4 new `TestComposedPostLoadTransform` tests, plus 4 `TestBakeOnARealModel` cases (`gqa-dense`, `moe`, `mla-moe`, `mamba2`).
- `pre-commit` passes on the changed files.

The new case runs in the existing `Sharded RDT Weight Transfer` Buildkite step, so no CI wiring changes are needed.

The end-to-end symptom (from the SkyRL port, vLLM 0.30.0, 8xH100) appears with `Nemotron-H-4B-Base-8K` started with dummy weights and given one `sharded_rdt` sync. Greedy output before the fix is `'\x17\x17\x17…'`. After the fix it is `' Answer: Paris…'`, which matches a real-weights load. On a 120B hybrid Mamba2 MoE, rollouts stopped hitting the length cap, and the sampler-vs-trainer logprob mean abs diff was 0.052 (NCCL sync: 0.054).

AI assistance: Claude Code was used to port this fix from SkyRL, write the tests and run the validation. I reviewed the full diff and the results above.

No duplicate work: I found no open issue or PR about `sharded_rdt` with composed loaders. #44814 fixed a different composed-loader bug in layerwise reload (the over-count that dropped `mixer.D`). RFC #60931 lists Mamba's `-exp(A_log)` as a `weight_loader` transform but does not address the RDT replay.

## Details

**Root cause.** `composed_weight_loader(loader, fn)` runs `loader(param, w)` and then `param.data.copy_(fn(param))`. The bake drives the loaders with `FakeRDTTensor` sources and meta `param`s. The inner copy has a fake source, so it is recorded. `fn(param)` only reads the meta destination, so it records nothing. Replay copies checkpoint bytes and never runs the loader, so `fn` never runs. `A` ends up positive, the SSM state grows instead of decaying, and generations never terminate. Nothing raises.

**Fix.**
- `composed_weight_loader` now exposes `inner_loader` and `post_load_fn` on the loader it returns.
- During the bake, `_install_recording_stamps` collects each param's post-load fns per leaf module. Nested compositions are applied innermost first. It unwraps any `_rdt_stamp_inner` first, because reload metadata can retain the previous bake's stamp, and without the unwrap the transform would be lost or stacked.
- `_run_quant` re-applies the fns once the module's last scatter has landed and before `process_weights_after_loading`. That is the same point at which `composed_loader` runs `fn`.
- The collection is cleared on each bake and on `shutdown()`.

**Tradeoffs / limitations.**
- The cost is one elementwise op per composed param per sync, on the quant stream, so it is negligible.
- Only `composed_weight_loader` is covered. Any other loader that writes into `param` from `param` would have the same blind spot. None exist today besides these composed ones.
