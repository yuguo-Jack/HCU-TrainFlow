# [Bugfix][Hardware][AMD] Handle AITER unified-attention LDS overflow with Triton fallback

[Upstream PR](https://github.com/vllm-project/vllm/pull/49264) · state: open · merged: False

## Original PR description

## Purpose
 
On ROCm, AITER's `kernel_unified_attention_3d` can request more LDS than the GPU provides. On affected Wave32 archs, `select_3d_config` chooses a tile size and pipeline depth **without checking the LDS budget**, so once Triton double-buffers the K/V tiles, the kernel asks for **65792** bytes against the 65536-byte (64 KB) limit. Triton raises an `OutOfResources` error in its pre-launch shared-memory check at the first 3D-kernel launch (during CUDA-graph capture in the default path) which aborts server startup.

Since the root-cause is with AITER's select_3d_config call, this bugfix adds a one-shot, defensive fallback in the ROCm AITER unified-attention backend. It catches the first LDS-overflow error from the causal AITER launch, logs a warning once, latches a per-instance flag, and routes that and every later causal forward to the in-tree `triton_unified_attention` kernel for the rest of the process. The error is then recognized by a typed check against `triton.runtime.errors.OutOfResources` with a message-text fallback, so it survives Triton refactors. The non-causal path already used the in-tree kernel; that call site is extracted into a shared `_forward_triton_unified` helper so no attention logic is duplicated. Triton's `OutOfResources` is a pure pre-launch Python check, so no GPU work is enqueued. The fallback is safe inside CUDA-graph capture (verified bit-identical to eager). This is a vLLM-side stopgap; the underlying tile/LDS budgeting belongs in AITER's `select_3d_config` I have tracked it upstream at ROCm/aiter#4329. 

Not a duplicate: #48723 is open and unassigned, and the AGENTS.md duplicate-work checks (`gh issue view 48723`, `gh pr list --search "48723 in:body"`, `gh pr list --search "aiter unified attention LDS"`) returned no PR addressing this, which I verified immediately before opening. 

Catching `OutOfResources` from a Triton launch and rerouting at runtime is an established in-tree idiom: `vllm/triton_utils/force_first_config.py` (imports it at line 31, catches at line 67) and `vllm/model_executor/layers/fused_moe/fused_moe.py` (at line 1257) both do it. The only difference here is that those pick a different config of the same kernel; this picks a different kernel.

Fixes #48723

### Hardware Methods

Hardware-verified on **gfx1151** (Radeon 8060S / Ryzen AI MAX+ 395 "Strix Halo", RDNA3.5, Wave32, 64 KB LDS), torch 2.11.0+rocm7.2 / triton 3.6.0, by forcing aiter's `select_3d_config` to request the reporter's exact 65792 B, then running a real `vllm serve` + `vllm bench throughput` with `--attention-backend ROCM_AITER_UNIFIED_ATTN`.

## Test Result

- **CPU**: 10 passed. `pre-commit` + `mypy-3.12` clean; the "Prevent new `torch.cuda` APIs" guard passed. `triton.runtime.errors.OutOfResources` resolves on triton 3.6.0 (typed branch is live).
- **gfx1151 hardware**:
  - _Catch-in-capture, byte-exact_: the `OutOfResources` is caught inside a live `torch.cuda.graph`; replay is bit-identical to eager (`max|Δ| = 0`).
  - _Real serve, forced overflow_: the warning fires once; JIT trace shows aiter `kernel_unified_attention_3d` overflow → in-tree `kernel_unified_attention` fallback; **all greedy tokens match** the aiter-3D reference, **max first-token logprob Δ = 0.0090** (< `atol=1.5e-2`; byte-equality not claimed, that's for different kernels).
  - _cudagraph-ON_ startup capture (the reporter's exact scenario): overflow caught **inside** FULL capture, capture completes **35/35 with no `hipErrorStreamCaptureUnsupported`**, engine serves coherently: where the reporter's process aborts, this finishes clean.
- **Fallback-path throughput** (Qwen2.5-0.5B, 1024/512, 64 prompts, cudagraph ON, 2 runs each):

| path                    | output tok/s (mean) |
|-------------------------|---------------------|
| baseline aiter-3D       | 3504.3              |
| fallback in-tree Triton | 3508.5              |

- **Δ +0.1%**, inside the ±3.6% run-to-run spread → yielded **no measurable regression**. The real win here is that this cost is paid **_only_** on GPUs that would otherwise fail to start. The latch is process-sticky and deliberately coarse, once any shape overflows, **all** later causal forwards take the fallback, including large-batch shapes that aiter's own 2D path would have served.
