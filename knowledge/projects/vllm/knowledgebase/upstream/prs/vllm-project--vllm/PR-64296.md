# [Perf][P/D] Skip prompt block hashing for KV connectors that don't use it

[Upstream PR](https://github.com/vllm-project/vllm/pull/64296) · state: closed · merged: False

## Original PR description



## Overview

With prefix caching off, `EngineCore` still builds the request block hasher whenever any KV connector is configured, so a NIXL (or DecodeBench) decode instance hashes every admitted prompt in the EngineCore input thread (contending for the GIL with the busy loop) even though nothing reads `Request.block_hashes`. This adds `KVConnectorBase_V1.requires_block_hashes` (default `True`) and opts out NIXL (pull and push) and DecodeBench. It also trims `BlockPool.get_new_blocks` when caching is off.

## Claims

- P/D decode instances with `--no-enable-prefix-caching` + NIXL/DecodeBench no longer hash prompts: admitting a 135K-token prompt takes 3.8 ms of EngineCore CPU instead of 8.9 ms (sha256) / 31 ms (sha256_cbor).
- `get_new_blocks` without caching or metrics: 253 → 168 us per 4000 blocks.
- No behavior change for connectors that read `block_hashes` (offloading, LMCache, Mooncake store, hf3fs, UMBP, Example, ...): they keep the default `True`. `MultiConnector` hashes if any child needs it.

## Details

- The property lives on the connector instance (like `requires_kv_delivery`) because `MultiConnector` needs its children to aggregate.
- Only the "prefix caching off" case changes; with caching on the hasher is always built.
- `get_new_blocks`: blocks popped from the free queue always have `ref_cnt == 0`, so assign `1` directly and only loop again when a metrics collector is set.
- Related, complementary work: #63454 (`sha256_int32`) and #63842 (frontend hashing) make hashing cheaper or move it off the engine thread; this PR avoids it entirely where it is unused. #64096 adds a different capability (`supports_lookahead_block_hashes`) and does not change when the hasher is built.
