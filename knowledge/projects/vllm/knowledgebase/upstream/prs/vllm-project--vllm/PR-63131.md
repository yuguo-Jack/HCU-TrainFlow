# [Bugfix][ROCm][Kimi-K3] Validate gfx942's int4 expert requant as int4

[Upstream PR](https://github.com/vllm-project/vllm/pull/63131) · state: closed · merged: True

## Original PR description

## Overview

Since #59042, Kimi-K3 with `--quantization-config '{"moe": {"weight": "int4_per_group_32"}}'` fails at startup on gfx942. This PR changes the fail-closed MoE experts check so it validates gfx942's load-time int4 requant as int4.

## Claims

- Kimi-K3 with the int4 expert requant starts and serves on gfx942 again.
- MXFP4 backend selection is unchanged for every other model and GPU.

## Validation

All runs on 8x MI325X (gfx942).

- **Before:** `upstream/main` (`87b804f09d`) fails in `Mxfp4MoEMethod._setup_kernel_k3_situ_gfx942`. I reproduced it by calling `_validate_mxfp4_experts_config(AiterMxfp4Experts, <K3 SiTU MoE config>, AITER_MXFP4_BF16)` on the device:
  ```
  ValueError: AiterMxfp4Experts does not support this MoE deployment since kernel does not support quantization scheme QuantKey(u8,scale(u8,static,GroupShape(row=1, col=32)),symmetric)xNone.
  ```
  With this change the same call passes.
- **Serving:** `vllm serve moonshotai/Kimi-K3 -tp 8 --quantization-config '{"moe":{"weight":"int4_per_group_32"}}'`, with DSpark (k=7) and stock decode.
  - The server starts, requantizes the experts, logs `Using AiterMxfp4Experts`, and runs AITER's `flydsl_moe*_abf16_wint4` kernels.
  - GSM8K (5-shot, 1319 questions, concurrency 1) scores 0.9575 ± 0.0056 on both strict and flexible extract.
- **Tests:** two new tests in `tests/kernels/moe/test_rocm_aiter_moe.py`. Both fake the arch, so any ROCm CI machine covers every arch.
  - `test_aiter_mxfp4_experts_quant_scheme_support_by_arch`: `AiterMxfp4Experts` accepts MXFP4 on gfx950 only and int4 on gfx942 only.
  - `test_mxfp4_experts_check_accepts_aiter_deployments`: the fail-closed check accepts every AITER MXFP4 backend on each arch it is deployed on, plus the gfx942 Kimi-K3 int4 requant.
  - `pytest tests/kernels/moe/test_rocm_aiter_moe.py -k "quant_scheme_support or check_accepts_aiter"` gives 13 passed. On `upstream/main`, exactly the two gfx942 int4 cases fail (2 failed, 11 passed), one with the `ValueError` above.
  - `pytest tests/models/kimi_k3/test_gfx942_int4.py` gives 7 passed.

## Details

- **Root cause:** #51274 requantizes K3's MXFP4 experts to packed int4 (`kInt4Static32`, bf16 activations) on gfx942. It builds the kernel with `make_mxfp4_moe_kernel(experts_cls=AiterMxfp4Experts)`.
  - #59042, a CUTLASS FP4 expert-parallel fix, added `_validate_mxfp4_experts_config` at the top of that shared function. The check validates an experts class with the first of `_MXFP4_SCHEME_CANDIDATES` the class supports. If none match, it falls back to the MXFP4 keys.
  - The AITER experts accept MXFP4 keys on gfx950 only. #60322 kept that rule when it split `AiterExperts` into per-quant classes.
  - So on gfx942 no candidate matched, and the check rejected the int4 experts.
- **Fix:** `AiterMxfp4Experts` accepts `(kInt4Static32, None)` on gfx942 only, and that pair is appended as the last candidate.
  - The oracle's backend selection passes `kMxfp4Static` explicitly, so it is unaffected.
  - Classes that support an MXFP4 key still pick that key first, so gfx950 is unchanged.

AI assistance (Claude) was used to develop this change. I reviewed every changed line and ran the tests above.
