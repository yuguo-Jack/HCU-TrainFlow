# [Hardware] Use accelerator APIs in weight transfer

[Upstream PR](https://github.com/vllm-project/vllm/pull/63457) · state: closed · merged: True

## Original PR description



## Overview

Use the unified PyTorch accelerator APIs for backend-independent operations in `vllm/distributed/weight_transfer`, following #30679 and existing vLLM usage.

## Claims

- Replace availability checks, device selection, synchronization, and current-stream lookups that do not pass streams to CUDA-specific communication APIs.
- Use `torch.Event` for sharded-RDT slot and quantization dependencies.
- Preserve stream-level synchronization boundaries, NCCL stream interfaces, and CUDA IPC behavior.

### Compatibility and scope

Generic streams do not expose the `.cuda_stream` field consumed by the current NCCL wrappers. Communication stream lookups and stream constructors/contexts are retained, including sharded-RDT contexts that update vLLM's cached current-stream tracking. Device UUID lookup and CUDA IPC collection also remain unchanged.

The earlier global event migration was reverted in #47668 because `torch.Event` ignored the `blocking` parameter ([upstream explanation](https://github.com/vllm-project/vllm/pull/47081#issuecomment-4874967250)). This patch only replaces default, nonblocking events.

Duplicate-work checks covered #30679 and its comments, open PRs mentioning it, and `weight_transfer accelerator`. #57374 overlaps the NCCL post-send availability check and changes that stream lookup through vLLM's helper as part of a new transport. This patch additionally covers IPC, packed-buffer stream tracking, sparse NCCL synchronization, and sharded-RDT device/event handling. #57022, #33225, and #37134 address stream/platform or communicator migrations; their interfaces are retained here. This patch does not add a transport or change rendezvous behavior.

### Runtime API equivalence on H20 (7/7 pass)

`torch.accelerator.current_stream()` returns a generic `torch.Stream` on torch 2.13, so these are behaviour checks of each substituted call against its `torch.cuda.*` counterpart:

| check | result |
| --- | --- |
| `current_stream()` is the default stream (drains already-enqueued default-stream work) | pass |
| `current_stream(torch.device)` targets that device and does not change the current device | pass |
| `device_index(int)` context manager sets and restores the current device, including tensor placement | pass |
| `set_device_index(int)` inside a worker thread (engine proc/quant-thread pattern) | pass |
| `torch.Event()` `record`/`synchronize`/`wait` on `torch.cuda.Stream`s, with cross-stream ordering | pass |
| `torch.Event()` built on one thread, recorded on the proc stream, waited on the quant stream (engine pattern) | pass |
| `accelerator.synchronize()` drains default-stream work (4.7 ms vs 4.5 ms for `cuda.synchronize()` over the same matmul) | pass |

Compatibility observation that backs the PR's design note: on torch 2.13 the generic wrappers do **not** carry the CUDA-only attributes — `torch.Stream` has no `.cuda_stream` (it has `synchronize`/`query`/`record_event`/`wait_stream`/`device`), and `torch.Event` has no `enable_timing`/`blocking`/`interprocess` (it has `record`/`query`/`synchronize`/`wait`). Nothing in `vllm/distributed/weight_transfer` reads `.cuda_stream` after this patch, and the sites that need CUDA-specific objects (NCCL `stream=` arguments, `torch.cuda.Stream(...)` constructors, `get_device_properties`, `ipc_collect`) correctly stay `torch.cuda.*`.

### CI: `amd-mi355-dpx-benchmarks-cli` is a pre-existing failure, not caused by this PR

The only red job in build #97033 fails in
`tests/benchmarks/test_responses_request_func.py::test_request_payload_is_accepted_by_the_server_schema`
with `KeyError: 'x-request-id'` (the rest of that job is 224 passed, 1 skipped). This PR
only touches `vllm/distributed/weight_transfer`; the same test fails identically when run
against the pristine **merge-base** wheel (`7a64fb8fc9`, none of this PR's files), so it is
red on main, not here.

**Root cause:** aiohttp 3.14.5 / multidict 7.1.0 / yarl 1.25.1 (bumped by #62835)
canonicalize outgoing header names, so the test's server receives `X-Request-ID` instead of
`x-request-id`. The test copies `request.headers` — a case-insensitive `CIMultiDictProxy` —
into a plain `dict` and then looks the key up case-sensitively. Reproduced directly:
with aiohttp 3.14.5 the handler captures `{"X-Request-ID": "bench-7", "Content-Type": ...}`.

**A fix is already open:** #63462 replaces `dict(request.headers)` with
`request.headers.copy()`. I re-ran the test file with that one-line change on the same
aiohttp 3.14.5: `1 failed` before, `24 passed` after — on both this PR's tree and the
merge-base tree. Nothing to change here; the job should go green once #63462 lands.
