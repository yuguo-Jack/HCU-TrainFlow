# [Bugfix][Kimi-K3] Reserve KDA prefill workspace before profiling

[Upstream PR](https://github.com/vllm-project/vllm/pull/63989) · state: closed · merged: True

## Original PR description

## Overview

Earlier Kimi K3 NVFP4 serving OOMs exposed approximately 0.93 GiB/rank of KDA prefill workspace growth after KV cache sizing. Although the latest tested stack now completes the workload without this patch, reserve that workspace before profiling so KV sizing accounts for the memory actually needed.

## Claims

- Reserve the configured FlashKDA layout or FlashInfer output layout before attention warmup.
- Reuse the shared, grow-only workspace across layers and subsequent requests within its capacity.
- Preserve construction without an initialized workspace manager and avoid reservations for the Triton prefill backend.

## Validation

The earlier OOM no longer reproduces in the latest matched GPU comparison on GB200 NVL with Kimi K3 NVFP4, TP16, default/profile-derived KV sizing, and `gpu_memory_utilization=0.95`:

| Measurement | Without reservation | With reservation |
| --- | ---: | ---: |
| KV cache per rank | 21.42 GiB | 20.49 GiB |
| Lowest sampled GPU-0 free memory | 0.53 GiB | 1.69 GiB |
| Both configured serving sweeps, all request counts | Passed | Passed |

Both arms completed all configured requests in both sweeps without OOM or request errors. The reservation moves 0.93 GiB/rank into the budget before KV sizing and improves runtime headroom; throughput differed by at most approximately 1.6%. This supports correcting the accounting gap, without claiming the patch was required for these runs to pass.

This campaign used an exact-content port of commit `2e3f235a2197dfb95288a9b98266900ab9767ae4` to a pinned vLLM v0.30.0 stack. The FlashInfer workspace backport, MoE workspace caller port, and separate V2 graph-accounting fix were held constant in both arms. GPU results apply to this combination; the assessment of current upstream main is based on source inspection.

The focused regression suite at commit `796d49e802fb0adacb1b94466013b2d5f912d7cb` also passed on GB200 with this installed stack: **10 passed, zero skips or errors**. It uses real layer constructors and a two-layer dummy-weight model through `LLM`, including two-token generation with both FlashKDA and FlashInfer prefill. Removing only the reservation block in the disposable installed package caused all **six reservation/engine cases to fail**: four found no reserved storage and both engine cases rejected workspace growth before memory profiling. The original source was then restored.

## Details

Upstream main inspected at [`eca54bd1`](https://github.com/vllm-project/vllm/commit/eca54bd1d937e778a939c240a2ed966fbcb12f85) still skips attention during V2 memory profiling and first requests KDA's prefill workspace during attention execution. That workspace can therefore grow during kernel warmup, after KV cache sizing. The passing control shows that the tested configuration has enough headroom despite this ordering; it does not mean the late allocation was included in the budget.

The worker initializes the workspace manager before model loading. Reserving immediately after the backend's layout is known brings the allocation into the model-loading memory measurement, reducing dependence on spare runtime headroom.

The reservation uses the same ordered specs and `get_simultaneous` call as runtime. Returned views are discarded; storage stays with the shared manager rather than each layer. FlashInfer's output scratch is reserved conservatively even when a particular request can write directly to the output. KV sizing settings and CUDA graph accounting are unchanged.

Duplicate-work check: searched open upstream PRs for `KDA workspace` and `workspace prefill in:title`; no matching KDA constructor-reservation fix was found. Related [#61250](https://github.com/vllm-project/vllm/pull/61250) changes prefill backend selection rather than adding this early reservation.
