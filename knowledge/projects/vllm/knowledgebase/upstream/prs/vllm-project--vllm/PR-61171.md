# [Bugfix][ROCm] Stop forcing legacy HSA IPC in ROCm images

[Upstream PR](https://github.com/vllm-project/vllm/pull/61171) · state: open · merged: False

## Original PR description

## Summary
- Stop setting `HSA_ENABLE_IPC_MODE_LEGACY=1` in the ROCm, ROCK, and gfx1250 images.
- Legacy IPC export uses an ioctl that only the DKMS driver implements. On in-tree `amdgpu`, `hipIpcGetMemHandle` fails and RCCL P2P breaks.
- The UCX pin-leak workaround stays available as an explicit opt-in for Instinct hosts on DKMS. Fixes #61055.

## Test plan
- [x] On MI355X with the DKMS `amdgpu` driver, `hipIpcGetMemHandle` succeeds with the variable unset, `0`, and `1`.
- [ ] On an in-tree `amdgpu` host (Radeon / stock Ubuntu kernel), confirm the same call fails when the variable is `1` and succeeds when it is unset.
- [ ] Rebuild a ROCm image from this branch and confirm `HSA_ENABLE_IPC_MODE_LEGACY` is unset.
- [ ] On an Instinct + DKMS host that still hits the UCX `rocm_ipc` pin leak, confirm `-e HSA_ENABLE_IPC_MODE_LEGACY=1` restores the previous workaround.

Independently worked the same fix for #61055 and arrived at an identical diff — dropping our PR in favor of this one. Two things that may help it land:

**1. Supporting validation on the DKMS side.** On MI300X (gfx942, DKMS `amdgpu` 6.19.14 on kernel 6.8.0-134, ROCm 7.14), a minimal probe (`hipMalloc` 1 MiB + `hipIpcGetMemHandle`) succeeds with `HSA_ENABLE_IPC_MODE_LEGACY` set to `1`, `0`, and unset:

```diff
     When using UCX as the transport backend, NCCL environment variables (like `NCCL_IB_HCA`, `NCCL_SOCKET_IFNAME`) are not applicable to NixlConnector, so configure UCX-specific environment variables instead of NCCL variables.
 
+#### ROCm: optional `HSA_ENABLE_IPC_MODE_LEGACY=1` workaround
+
+On ROCm hosts running the DKMS `amdgpu` driver, setting `HSA_ENABLE_IPC_MODE_LEGACY=1` (e.g. `docker run -e HSA_ENABLE_IPC_MODE_LEGACY=1 ...`) works around a UCX `rocm_ipc` issue where GPU memory stays permanently pinned after buffers are freed ([rocm-libraries#6266](https://github.com/ROCm/rocm-libraries/issues/6266)).
+
+Do not set it on hosts running the in-tree (stock kernel) `amdgpu` driver: the legacy IPC path relies on the `AMDKFD_IOC_IPC_EXPORT_HANDLE` ioctl, which only the DKMS driver implements. With it enabled there, every `hipIpcGetMemHandle` call fails, breaking RCCL P2P, vLLM's custom all-reduce, and CUDA-IPC tensor sharing ([vllm#61055](https://github.com/vllm-project/vllm/issues/61055)). The vLLM ROCm images therefore do not set it by default.
+
 #### Selecting a NIXL transport backend (plugin)
 
 NixlConnector can use different NIXL transport backends (plugins). By default, NixlConnector uses UCX as the transport backend.
```

- zoroyihan7 · comment · 2026-10-14T16:22:12Z · [source](https://github.com/vllm-project/vllm/pull/61171#issuecomment-6173016356)

An additional data point for the runtime-image change, from a setting the existing tests do not cover: an **unprivileged** container on a **DKMS** host.

**Environment:** 8x MI355X (gfx950), DKMS `amdgpu` 6.14.14, kernel 6.8, ROCm 7.2.3, `vllm/vllm-openai-rocm` nightly image. Kubernetes pod with default capabilities (no `SYS_PTRACE` / `SYS_ADMIN`), `NoNewPrivs=1`, seccomp RuntimeDefault, no `hostIPC`.

**Result:** with the image's `HSA_ENABLE_IPC_MODE_LEGACY=1`, the export side succeeds, but the import side's `ioctl(AMDKFD_IOC_IPC_IMPORT_HANDLE)` returns `-1 EPERM` (strace). `hipIpcOpenMemHandle` then fails with `invalid device pointer`, so any TP >= 2 start fails in the custom all-reduce / RCCL init. Reversing parent and child (the parent imports the child's handle) fails the same way, so it is not a ptrace-ancestry restriction. The non-legacy (DMA-BUF) path works under the same restrictions.

Single-variable runs in one container. Only this variable changed; the other image ROCm variables stayed as shipped:

| `HSA_ENABLE_IPC_MODE_LEGACY` | 2-GPU `all_reduce` (torchrun) | torch CUDA tensor IPC | `vllm serve`, TP=4 |
|---|---|---|---|
| `1` (image default) | fails, `invalid device pointer` | fails | fails within ~70 s on all ranks |
| unset | passes | passes | ready in ~166 s, completions OK |
| `0` | passes | passes | ready, completions OK |

Unsetting other image variables one at a time (`ROCPROFILER_QUEUE_INTERPOSITION`, `LD_LIBRARY_PATH`, `HSA_NO_SCRATCH_RECLAIM`, `HIP_FORCE_DEV_KERNARG`) did not change the failure. Leaving only `HSA_ENABLE_IPC_MODE_LEGACY=1` reproduced it.

So in addition to the in-tree kernel case in #61055, the legacy setting also breaks multi-GPU serving in any unprivileged container on DKMS hosts. Keeping it only in `ci_base`, as this PR now does, fixes that for the published images. I have not checked whether a privileged or `hostIPC` container behaves differently.
