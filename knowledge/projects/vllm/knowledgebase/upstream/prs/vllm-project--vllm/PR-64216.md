# [KV Offload] Keep a running request's resumable prefix in the CPU tier

[Upstream PR](https://github.com/vllm-project/vllm/pull/64216) · state: open · merged: False

## Original PR description

## Overview

Under load, CPU KV offloading evicts a long-running turn's prefix before the turn ends, so the conversation's next turn recomputes it. This PR adds the opt-in `retain_running_prefixes` option, which keeps that prefix available to the next turn on hybrid (Mamba) models.

Related: #57813 takes a different approach to the same problem (see [Related work](#related-work)).

## Claims

- **New option:** `retain_running_prefixes` (default `false`) for `CPUOffloadingSpec` and `TieringOffloadingSpec`. Nothing changes unless it is set.
- **The option has two parts.** A hybrid model resumes only where both the attention chunks and the Mamba state are cached.
  - **(a) Retained state:** while a request runs, the CPU tier does not evict the Mamba state that its next turn resumes from. This is the deepest state saved within the prompt. Finish, abort and cache reset release it.
  - **(b) Store again at finish:** when a request finishes, it offers its stored full-attention chunks again. The chunks evicted while it ran are stored again from its GPU blocks. This does not happen after an abort or while a load is pending.
- **Metrics:** three `vllm:kv_offload_retention_*` counters report retained states, finished requests by how much state they retained, and chunks stored again. A refused store counts in the existing `vllm:kv_offload_allocation_failure`.
- **Outputs cannot change:** the option changes only which chunks stay cached and which are stored.
- **Performance:** at 384 concurrent sessions of agentic multi-turn traffic on `nvidia/NVIDIA-Nemotron-3.5-Super-VL-120B-A12B-NVFP4`:
  - 6.5% more requests per hour than a same-day baseline, or about +5% to +12% given baseline variation;
  - 6.2% fewer prompt tokens computed per request.

## Details

### Why retain the state but store attention again

- **Attention chunks:** a request keeps its attention blocks on the GPU until it finishes. So at finish, the connector can store again the chunks that the CPU tier evicted.
- **The prompt's Mamba state:** vLLM hands this state to the connector at the prompt boundary. Then the request releases its GPU copy. If the CPU tier evicts the state, nothing can store it again, so the request retains it while it runs.
- **Both are needed:** without the state, the attention chunks below it are useless to the next turn, and the reverse.
- **Root cause:** a running request's chunks keep the LRU rank they got when the request started (#61050). So a long turn ages behind newer requests, and LRU evicts its chunks first.
- **The request-level offload policy does not cover this:** `OffloadPolicy.REQUEST_LEVEL` offers each chunk once, when the request first has it, and not again at finish.

### Design

- Retention reuses the CPU tier's load pin, with no transfer. So a retained chunk cannot be evicted, and it counts as used by the request.
- Storing again reuses `prepare_store()`. At finish, the full-attention store cursor restarts at chunk 0, so only the missing chunks are copied.
- **Cost:** scheduler bookkeeping only, with no GPU synchronization. At most (running requests) × (Mamba groups) chunks are retained.

### Related work

- **#57813 (open draft):** `pin_in_flight_chunks` soft-pins every chunk that an unfinished request has touched, with an eviction fallback. It targets paused colocated RL rollouts, where frozen requests touch nothing.
  - This PR retains only the one state per Mamba group that a request resumes from. It also stores evicted attention chunks again at finish.
  - In our trace replay at 384 sessions, pinning every chunk of the running requests lost 40% more prefix tokens. This PR's two parts lost 39% fewer.
  - If #57813 lands, (a) could build on its lifetime signal.
- **#61050 (merged):** a running request's chunks share one provisional LRU rank, set when the request starts. So a long turn still ages behind newer requests. It also does not cover a state that the request no longer holds.
- **#61282 (open):** keeps the prompt's Mamba state alive in the GPU prefix cache until the request ends. Complementary.
- **#62479 (draft):** restores Mamba boundary hand-offs that sparse GPU retention can suppress. It makes sure a state reaches the CPU tier; this PR keeps it there while the request runs.
- **#63566 (merged):** pins a shared-prefix junction when a sparse group cuts the offload hit. Its trigger differs: requests that diverge before the stored state.
- **#47235 (draft):** the same idea as (b) for `SimpleCPUOffloadConnector`, by scanning during the request. This PR stores again once, at finish, in `OffloadingConnector`.

### Trade-offs and limitations

- **Capacity:** retained states take room from idle sessions (see the cost line in the GPU runs).
- **Store cost at finish:** GPU→CPU copies. In the runs, 5% of the offered chunks were missing and were stored again.
- **Scope:** only hybrids in Mamba `align` cache mode get (a). Part (b) applies to the full-attention groups of any model, with the option on.
