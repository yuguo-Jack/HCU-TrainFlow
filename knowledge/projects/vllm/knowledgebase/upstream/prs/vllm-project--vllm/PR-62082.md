# [Feature][Elastic EP] Correlate external scaling operations

[Upstream PR](https://github.com/vllm-project/vllm/pull/62082) · state: open · merged: False

## Original PR description



## Overview

After an external Elastic EP request loses its HTTP response, a controller cannot reliably associate the observed resize with its request or tell whether a failed commit left the topology known. Add optional operation correlation and explicit topology evidence to the existing coordinator.

Follow-up to vllm-project/vllm#43202; ports the remaining scope of fangyuchu/vllm#292. Related to #42515 and [Dynamo DEP #13121](https://github.com/ai-dynamo/dynamo/issues/13121).

## Claims

- Accept optional `operation_id` and per-rank `expected_instance_id`; replay the latest operation without repeating it and reject conflicting or stale requests with HTTP 409.
- Expose requested/effective DP sizes and `topology_known`; prevent a new resize when the previous topology is unknown.
- Publish topology evidence before completion and keep correlated observation available while admission is closed, including on retired API processes.

## Details

Reuse the existing epoch-scoped TCPStore metadata and state machine. Preserve #43202's failure propagation, commit-readiness barrier, control-store lifetime, and off-thread status reads. Commit-failure admission closure is already upstream and is not duplicated.

An instance token identifies an individual API process. Only the latest actual resize is retained; a target already equal to the current DP size remains a no-op. This adds neither historical-operation persistence nor engine recovery.

Duplicate check: searched open PRs for `42515 in:body`, `"elastic" "operation"`, and `"elastic" "topology_known"`. No duplicate was found. #50778 concerns failure-flag handling rather than correlated external operations.
