# [Bugfix][Spec Decode] Muse Spark DSpark: initialize _context_kv_proj so the draft loads

[Upstream PR](https://github.com/vllm-project/vllm/pull/65125) · state: closed · merged: True

## Overview

Muse Spark with DSpark fails at startup on main: loading the draft raises `AttributeError: 'MuseSparkDSparkModel' object has no attribute '_context_kv_proj'`. Regressed by #64357. This PR initializes the attribute in `MuseSparkDSparkModel.__init__`.

## Claims

- Muse Spark + DSpark (`--speculative-config '{"method":"dspark",...}'`, the recipe's DSpark profiles) starts again. The failing code path is shared by CUDA and ROCm.
- DSpark acceptance is unchanged from before the regression.
- A unit test builds the real draft model and loads weights; it fails without the fix and passes with it.

## Details

Root cause: #64357 moved the creation of the MXFP8 context K/V projection from `_build_fused_kv_buffers` (run at the end of `load_weights`) into `DFlashQwen3Model.__init__`, and `DFlashQwen3Model.load_weights` now reads `self._context_kv_proj`. `MuseSparkDSparkModel` inherits `load_weights` but calls `nn.Module.__init__` instead of the parent's `__init__`, so the attribute never exists. `AutoWeightsLoader` reaches the inherited `load_weights` through `MuseSparkDSparkForCausalLM.load_weights` and fails.

Fix: set `self._context_kv_proj = None`. Muse projects its context K/V in `_project_muse_context_kv` (from the weights `_build_fused_kv_buffers` stacks) and never uses the parent's MXFP8 projection, so `None` keeps the pre-#64357 behavior. Of the other `DFlashQwen3Model` subclasses, the two that also skip the parent `__init__` never reach the inherited `load_weights`: Laguna DFlash overrides it, and Gemma4 DSpark loads parameters directly from its `ForCausalLM`.

Why CI missed it: the Muse DSpark registry entry is `is_available_online=False` and the model initialization test loads dummy weights, so no CI job runs the draft's `load_weights`. The new test does; `tests/transformers_utils` is currently not run by any Buildkite step (the step is commented out in `.buildkite/test_areas/misc.yaml`), so it is covered only by local runs until that step is re-enabled.

Not a duplicate: no open issue or PR mentions `_context_kv_proj` or this failure; #64692 and #64690 touch weight loading but not this attribute. #65080, the other Muse fix today, merged the duplicate `process_weights_after_loading` from #64357 and #63440 in `amd/model.py` and does not touch the draft.
