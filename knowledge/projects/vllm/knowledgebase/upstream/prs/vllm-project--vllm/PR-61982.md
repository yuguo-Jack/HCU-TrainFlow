# [Bugfix] Fix decoded logprob tokens that continue a split UTF-8 character

[Upstream PR](https://github.com/vllm-project/vllm/pull/61982) · state: open · merged: False

## Overview

Decoded logprob tokens can contain U+FFFD even though the generated text is valid. With Qwen3, the logprob tokens of `🍰이 맛있다` join to `��이 맛�다`. This fixes the correction in `LogprobsProcessor` for tokens that start with the rest of a split UTF-8 character and then contain more text, and the copy of that correction in `OnlineDerenderer`, which the `/derender` endpoints use.

## Claims

- Sample logprobs (streaming and non-streaming) and prompt logprobs of such tokens now decode to the right text in `/v1/completions`, `/v1/chat/completions` (including `top_logprobs`), `/inference/v1/generate` with `output_mode="text"`, and `/v1/chat/completions/derender` and `/v1/completions/derender`: for Qwen3 and `🍰이 맛있다`, the logprob tokens join to the same string as the output text.
- Tokens whose decoded text ends with U+FFFD are corrected as before.

## Details

Qwen3 tokenizes `🍰이 맛있다` into tokens that decode individually as `['�', '��이', ' �', '�', '�', '�다']`: `��이` holds the last bytes of 🍰 followed by 이. `_verify_tokens` only corrected tokens whose decoded text ends with U+FFFD, so `��이` and `�다` were returned as is. In `_correct_decoded_token`, the context search stopped at the first context whose decoded text no longer ended with U+FFFD, which can still contain an incomplete character earlier in the string. Both checks now look for U+FFFD anywhere in the text. The rest of the correction, including the four-token context limit, is unchanged.

`OnlineDerenderer` (`vllm/renderers/online_derenderer.py`) has its own copy of `_correct_decoded_token` and the same trailing-only checks in `_resolve_logprobs`, so the second commit makes the same change there.

A literal U+FFFD in the text is dropped from the logprob tokens both before and after this change, since it can't be told apart from an incomplete byte sequence this way.

Duplicate check: I searched open and closed PRs and issues for `LogprobsProcessor`, `_correct_decoded_token`, `decoded_token`, the file path, and "logprobs" with "utf-8", "unicode", "replacement character" and "emoji". The earlier UTF-8 fixes for #27300 (#28874, #34875) are merged and this case fails with them. Open PRs that touch `vllm/v1/engine/logprobs.py` or its tests (#60542, #60915, #60918, #57442, #35961) change logprob storage, rendering and fast paths, not this correction. #60437 changes the parsed streaming path in `online_derenderer.py`, but not `_correct_decoded_token` or the checks in `_resolve_logprobs`.
