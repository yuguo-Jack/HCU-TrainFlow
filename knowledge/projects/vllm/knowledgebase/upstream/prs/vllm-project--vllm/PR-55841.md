# [Core][Perf] Prefer contiguous KV block runs for disaggregated transfer

[Upstream PR](https://github.com/vllm-project/vllm/pull/55841) · state: open · merged: False

## Original PR description

## Overview

Prefer physically contiguous KV block-ID runs for large allocations so disaggregated KV transfers can coalesce more NIXL descriptors. The policy is opt-in with `VLLM_KV_CONTIG_ALLOC=1`; the default allocator remains unchanged.

The motivating workload is MiniMax-M3-NVFP4 with 128-token KV blocks, one TP2 prefill replica, three TP2 decode replicas, and 60 concurrent long-context agentic sessions.

## Claims

- For allocations of at least eight blocks, the opt-in policy searches a bounded `4 * num_blocks` prefix of the free queue, takes the longest queue-adjacent physical-ID runs in ascending order, then fills any remainder in normal eviction order.
- It changes only which already-free physical block IDs are returned. Reference counts, prefix-cache eviction, hashes, metrics, and allocation size retain their existing paths.
- The default-off path and allocations below eight blocks continue to use `popleft_n` directly.
- Blocks released by the current `unpin_blocks` API remain last-resort candidates and are excluded from contiguous-run selection; they are reused only by the ordinary fallback when necessary.

Author-provided end-to-end measurements against the same source base and serving configuration showed:

| Run | p90 output tok/s/user | Total tok/s/GPU | Delta |
| --- | ---: | ---: | ---: |
| Control | 123.591 | 47,289.91 | -- |
| Contiguous allocation A | 129.297 | 49,698.86 | +4.62% / +5.09% |
| Contiguous allocation B | 127.553 | 48,828.00 | +3.21% / +3.25% |

A representative per-rank READ reduced native descriptors from 23,252 to 8,926-10,222, descriptor posting time from 79.6 ms to about 32 ms, and transfer time from 117 ms to about 53 ms. Results were workload-dependent: at 48 sessions the change was +1.58% / +0.43%, and a heterogeneous TP2-prefill/TP4-decode point was within run-to-run variation at +1.22% / +0.29%. This variability and the bounded scan/LRU tradeoff are why the policy is not the default.

## Details

### Implementation and tradeoffs

The bounded window preserves approximate eviction age rather than globally optimizing packing. Within that window, selecting longer runs can bypass older free blocks; if useful runs do not satisfy the request, allocation resumes from the queue head. Descending runs are normalized because transfer coalescing requires matching address direction at both endpoints.

The implementation adds 52 non-test lines to the core allocator and isolates the selection logic in one helper. The environment variable is registered in `vllm.envs` and excluded from torch.compile factors because it changes allocator policy rather than generated code.

### Duplicate-work check

Open-PR searches for contiguous KV allocation, physical block-ID runs, NIXL descriptor merging, and BlockPool changes found no overlapping allocator optimization. Draft PR #32290 deliberately emulates strict contiguous-allocation fragmentation by delaying work when a contiguous range is unavailable; this PR instead performs a best-effort bounded preference with ordinary fallback. Connector packing/range-loading PRs operate at the transfer or layout layer rather than changing `BlockPool.get_new_blocks()`.

Transfer-time data for `VLLM_KV_CONTIG_ALLOC=1` on a GQA model with homogeneous TP, over cuda_ipc/NVLink.

Setup: Qwen3-235B-A22B FP8 (94 layers, 1 KV head per rank), 1P TP4+EP4 : 1D TP4+EP4 on one 8x H100 SXM node, vLLM v0.32.0 + this PR's `block_pool.py`/`envs.py` at head `0f79acb` (applied cleanly), env on both P and D, NixlConnector pull, FP8 KV, toy proxy. One launch per arm, points in order: multi-turn c64, 16k-token prompts c16 (S2), multi-turn c256. Arm A was repeated last as a drift control (A2: transfer time within 0-7% of A, S2 TTFT/ITL identical).

Transport caveat: P and D ran in separate containers. Without a shared PID namespace (`--pid=host` on both; `--cap-add SYS_PTRACE` alone did not help and is not needed), UCX silently left cuda_ipc and transfers were ~16x slower with 0 failures reported. All numbers below are with the shared namespace; NVLink counters on the prefill GPUs match NIXL's byte count to within 0.1 GB per point.

Consumer-side means per rank-transfer:

| Point | Arm | descriptors | post ms | xfer ms |
|---|---|---|---|---|
| S2 c16 | control b64 (A / A2) | 16,260 / 16,239 | 60.3 / 60.3 | 78.3 / 78.3 |
| S2 c16 | this PR, b64 | 3,815 | 11.0 | 23.7 |
| S2 c16 | control b128 | 8,679 | 33.3 | 41.4 |
| c256 | control b64 (A / A2) | 4,780 / 4,715 | 17.1 / 16.7 | 37.0 / 34.4 |
| c256 | this PR, b64 | 2,737 | 9.0 | 26.4 |
| c256 | control b128 | 2,560 | 7.5 | 26.6 |

- Post time is linear in descriptors across all 12 pull points: ~3.7 µs per descriptor (R^2 0.996). The PR cuts S2 descriptors 77%, post 82%, transfer 70%; at c256, -43% / -47% / -23..-29%. Multi-turn c64 is unchanged (~150-180 descriptors, already contiguous).
- End to end, honestly: no measurable gain on this node. S2 TTFT is ~8 s and prefill-bound, so the ~55 ms saved per transfer is <1%; request latency p50 12.19 s (control) vs 12.25 s (PR), req/s equal. S2 ITL p50 fell 17.1 -> 15.5 ms with the PR, but TTFT p50 rose ~5%, so we do not claim it.
- Earlier run (broken transport, same allocator behaviour): the descriptor gain falls from -79% on a fresh pool to -33% on the same 16k workload after one c256 phase; the bounded scan window is a plausible cause, untested.
- Not tested: #45211 (READ submission on a reader thread). It does not apply to v0.32.0 (3 of 5 hunks rejected; v0.32.0 rewrote the handshake/failure paths it touches), so no result either way.
