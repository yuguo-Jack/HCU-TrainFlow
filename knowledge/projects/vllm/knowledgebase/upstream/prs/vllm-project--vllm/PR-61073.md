# [Fusion][Perf] Extend QuantizedActivation contract with get_input_quant_scale and maybe_fused_norm_quant

[Upstream PR](https://github.com/vllm-project/vllm/pull/61073) · state: open · merged: False

## Original PR description



## Overview

Extends the `QuantizedActivation` linear-kernel contract (`#44260`, `#51415`, `#53793`, `#55643`, `#59612`) with `get_input_quant_scale(layer)` (resolving `TODO(mgoin)` in `quant_activation.py` and `fused_act_quant.py`) and introduces `maybe_fused_norm_quant` (`vllm/model_executor/layers/fusion/fused_norm_quant.py`) to fuse `RMSNorm` / `FusedAddRMSNorm` + input quantization across `input_layernorm -> qkv_proj` and `post_attention_layernorm -> gate_up_proj`.

## Claims

- **Resolves `TODO(mgoin)` via `get_input_quant_scale(layer)`:** Producers (`fused_act_quant.py`, `relu2_fp8_quant.py`, `fused_norm_quant.py`) retrieve static FP8 (`input_scale`) and dynamic NVFP4 (`input_global_scale_inv`) scales through the contract rather than reaching into kernel-specific attributes on `LinearBase`. Automatically returns `None` when `requires_unquantized_input=True` (e.g., active LoRA adapters).
- **Introduces `maybe_fused_norm_quant` with Asymmetric Residual Preservation:** Updates `residual` in-place in full precision (`BF16`/`FP16`) while returning a pre-quantized `QuantizedActivation` (`kFp8StaticTensorSym`, `kFp8DynamicTokenSym`, `kFp8Dynamic128Sym`, `kFp8Dynamic64Sym`, `kNvfp4Dynamic`) to the consumer linear layer with **zero consumer-side changes**.
- **1.68x–2.97x Boundary Speedup on NVIDIA H100:** Eliminates the intermediate `BF16` HBM write + read between `RMSNorm` and quantization (saving up to 64 MB of HBM traffic per call at `M=4096, d=4096`), working in both eager mode and across `torch.compile` graph breaks for arbitrary `rms_norm_eps`.

## Details

1. **Asymmetric Residual Stream vs. Quantized Branch (`maybe_fused_norm_quant`):**
   At `post_attention_layernorm` (and `input_layernorm` for layers `l >= 1`), the normalization kernel computes `residual = x + residual` in `BF16`/`FP16` and writes that unquantized sum back to `residual` in-place, while quantizing the normalized activation in registers directly to `FP8` / packed `NVFP4` (`QuantizedActivation`). Because `QKVParallelLinear` and `MergedColumnParallelLinear` inherit from `ColumnParallelLinear` and dispatch through `FP8ScaledMMLinearKernel` / `NvFp4LinearKernel` (which already unwrap `QuantizedActivation` via `as_quantized_activation`), no consumer changes are needed.
2. **Eager Mode, Graph Breaks, & Arbitrary `rms_norm_eps`:**
   Unlike `RMSNormQuantFusionPass` (`rms_quant_fusion.py`), which registers 76 separate FX pattern-matcher rules hardcoded to `for epsilon in [1e-5, 1e-6]`, `maybe_fused_norm_quant` passes `norm_fn.variance_epsilon` directly and works in eager mode, across graph breaks, and for any model epsilon (e.g. `1e-4`).
3. **Tradeoffs & Cooperation with LoRA and `AllReduceRMSNormFusionPass`:**
   - **LoRA:** When LoRA wraps `qkv_proj` or `gate_up_proj`, `requires_unquantized_input=True` causes `get_input_quant_key(linear)` to return `None`, falling back cleanly to unfused `norm_fn(x, residual)` so the LoRA branch receives `BF16`/`FP16` activations.
   - **Multi-GPU Tensor Parallelism (`TP > 1`):** When `residual is not None`, `TP > 1`, and compiler `fuse_allreduce_rms=True` is enabled, `_should_defer_to_allreduce_rms_fusion` yields to `AllReduceRMSNormFusionPass` so 3-way FlashInfer collective fusion (`AllReduce + Add + RMSNorm + Quant`) is not preempted.
   - **Zero Host-Device Sync:** No CPU/GPU synchronization or host tensor reads are introduced on the forward path.

I re-measured norm+quant fusion for Qwen3-8B-FP8 on current main (`e8e1e961`, FlashInfer 0.7.1, DeepGEMM 2.8.1 vendored, 1× H100 SXM5, torch profiler). Today the only way to get `rms_norm_per_block_quant` on sm90 is the compile pass with the default kernel disabled:
- **A**: default `FlashInferFp8DeepGEMMDynamicBlockScaledKernel`. It takes BF16 and quantizes internally, so the pass has nothing to match.
- **B**: A disabled + `fuse_norm_quant` → `DeepGemmFp8BlockScaledMMKernel` + `rms_norm_per_block_quant`.

**GPU time per decode step** (decoder-layer kernels, µs)

| bs | A | B | Δ | Δ GEMM | Δ norm/quant |
|---|---|---|---|---|---|
| 1 | 3839 | 4397 | +558 (+14.5%) | +285 | +262 |
| 32 | 4504 | 4656 | +151 (+3.4%) | +21 | +129 |
| 256 | 8540 | 8707 | +167 (+2.0%) | +1 | +134 |

**Wall clock** (`vllm bench latency`, in 128 / out 256, median of 3 runs): +11.5% at bs=1, −0.5% to +7.2% at bs 8–256. Without the one run that had host contention: +1.2% to +9.3%, positive at every bs.

**Where the cost comes from**
- **bs=1:** losing FlashInfer swapAB costs +285 µs (DeepGEMM `1d2d` is 6–15% slower per launch at M=1). About 55 µs more is unrelated to fusion: o_proj/down inputs go through `per_token_group_quant` (2.4 µs) instead of `scale_1x128` (1.6 µs).
- **bs ≥ 32:** same GEMM kernel (±1%). The delta is the fused kernel (≈ +71 / +51 µs at bs 32 / 256) plus an Inductor copy of the residual before the in-place op (+56 / +80 µs). #60481 removes the copy.
- **The fused kernel itself:** 5.8 / 5.6 / 7.2 µs per launch in-model, vs 3.6 / 4.6 / 6.5 µs for the Triton rmsnorm + quant pair it replaces (bs 1 / 32 / 256). #54111 was a race fix; the structure is unchanged (3 passes, `VEC_SIZE=4`, no `__launch_bounds__`).

**What this means for 1×128 here**
- **swapAB is not lost by design.** `fp8_blockscale_gemm_sm90(x_fp8, w, x_scale, w_scale)` takes FP8 input and still reaches `runGemmSwapAB` for M < 32.
- **Scale layout.** Both sm90 consumers, swapAB (M < 32) and DeepGEMM `fp8_gemm_nt` (M ≥ 32), take fp32 scales column-major with M padded to 4. Two producers already write that layout, and the kernel lists show no transform kernel before the GEMM:
  - `rms_norm_per_block_quant(..., is_scale_transposed=True)` into a TMA-aligned buffer
  - flashinfer-ai/flashinfer#4480

  With `is_scale_transposed=False`, as allocated here, every consumer needs a transpose. Could the 1×128/1×64 producers allocate column-major + TMA-aligned (same for `_silu_and_mul_fp8_dynamic_block`), or encode the layout in the contract per the TODO in `quant_activation.py`?
- **Numerics.** Rel. Frobenius error vs a BF16 reference is 2.5–2.7e-2 on all paths. The fused paths are slightly lower at M ≥ 32, because today's path rounds scales to UE8M0. The fused op has no UE8M0 option.
- **Still a loss with today's C++ producer.** Even keeping swapAB, it is +3.4% (gate_up) to +8.5% (qkv) per norm+GEMM at M=1, and within ±4% at M=8–256. Upper bound with a producer no slower than today's rmsnorm alone: −3.1% / −4.0% / −2.6% GPU time per step at bs 1 / 32 / 256.
- **No consumer yet.** `Fp8BlockScaledMMLinearKernel` has no `input_quant_key()`, and `fp8.py` never calls `expose_input_quant_key`. So 1×128 producers (this one and `_silu_and_mul_fp8_dynamic_128` on main) never fire for `fp8` block checkpoints.

**Proposal:** I'd take the consumer side as a follow-up to this PR:
- `input_quant_key()` / `QuantizedActivation` handling in the block-FP8 kernels
- `expose_input_quant_key` in `fp8.py`
- an FP8-in branch in `FlashInferFp8DeepGEMMDynamicBlockScaledKernel` (swapAB below 32, DeepGEMM above)
- the column-major / TMA-aligned convention

On sm90 it stays off until a producer beats today's path. I'm benchmarking C++ vs flashinfer-ai/flashinfer#4480 vs Helion #36895 at decode sizes. Does that split work for you, and do you have a preferred 1×128 producer? cc @HumphreySun98, who planned the 1×128 follow-up in #45364.
