# [Bugfix][Model Runner V2] Embed randomized dummy input ids for inputs_embeds models

[Upstream PR](https://github.com/vllm-project/vllm/pull/64530) · state: open · merged: False

## Original PR description

## Overview

With `randomize_inputs`, the MRV2 dummy run randomizes `input_ids` (#58411), but models that take `inputs_embeds` are given the pre-allocated, zero-filled embeddings buffer instead. This PR fills that buffer with the embeddings of the random ids, so these models see random tokens, as V1 does since #30472.

## Claims

- On MRV2, multimodal-registered models (served without `--language-model-only`) and prompt-embeds models now get the embeddings of the randomized ids in dummy runs that set `randomize_inputs`: FlashInfer autotune, `VLLM_RANDOMIZE_DP_DUMMY_INPUTS` profile/DP dummy batches, elastic EP and SSM replay warmup. Before this PR they got all-zero embeddings.
- Effect on MoE: with zero embeddings, every token of the autotune dummy run routes to the same experts in every MoE layer (GLM-5.3-Flash: 1 unique top-8 row out of 65536). FlashInfer's trtllm-gen MoE tuner replays the caller's `topk_ids` under DP+EP, so all decode-sized buckets are tuned on that load and pick large tiles. With this PR the dummy routing is diverse and the tuner picks smaller tiles at decode sizes.
- No change for text-only models, PP ranks other than the first, or dummy runs without `randomize_inputs` (e.g. CUDA graph capture).

## Details

**Root cause.**
- MRV2 feeds `inputs_embeds` instead of `input_ids` when `uses_inputs_embeds` is set (multimodal models, prompt embeds); `input_ids` is passed as well only for `requires_raw_input_tokens` models.
- In dummy runs, `execute_model` takes `model_state.dummy_inputs_embeds(n)`, a slice of `encoder_runner.inputs_embeds` / `DefaultModelState.inputs_embeds`. Both are allocated with `torch.zeros`, and only the real-request path (`prepare_inputs_embeds`) writes them, so they are still zero during startup dummy runs.
- #58411 randomizes `input_ids` only. V1 hit the same gap and #30472 fixed it there by randomizing `inputs_embeds` when `input_ids` is `None`; the MRV2 port did not carry that over.

**Fix.**
- `DefaultModelState.dummy_inputs_embeds(num_tokens, input_ids=None)` writes `model.embed_input_ids(input_ids)` into the buffer when ids are given. The runner passes the randomized ids only when `randomize_inputs` is set. The `ModelState` interface signature is updated to match.
- Embedding the random ids (rather than V1's `randn`) gives real token embeddings at the model's own scale, and keeps `inputs_embeds` consistent with `input_ids` for `requires_raw_input_tokens` models.
- The write is in place, so the buffer address stays the same for compiled models.

**Tradeoffs and limitations.**
- One embedding lookup per randomized dummy run; nothing on the steady-state path. With `VLLM_RANDOMIZE_DP_DUMMY_INPUTS=1` (opt-in, DP > 1), idle DP ranks also do this for their 1-token dummy batches.
- During `profile_run` with randomized inputs, the lookup allocates the same temporary as the real `prepare_inputs_embeds` path.
- The dummy run embeds token ids only, not multimodal features. Random-token routing is prefill-like rather than decode-like. FlashInfer MoE tuning on representative routing is addressed separately (FlashInfer #3537, #3573).

**Related, not duplicates.**
- #49540 (open) exercises the multimodal embedding merge during V1/MRV2 memory profiling. It does not randomize the ids, so its embeddings would be identical for every token.
- #63733 (open) changes which `input_ids` MRV2 CUDA graph capture uses; it does not touch dummy embeddings.
- Searched open PRs and issues for `dummy_inputs_embeds`, `randomize dummy`, `MRV2 randomize`, `VLLM_RANDOMIZE_DP_DUMMY_INPUTS` and `inputs_embeds dummy run`; none addresses this.
