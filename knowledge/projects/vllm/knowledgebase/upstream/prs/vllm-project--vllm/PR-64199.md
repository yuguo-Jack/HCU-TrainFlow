# [Qwen4Exp] NVFP4 main KV for QSA via FlashInfer

[Upstream PR](https://github.com/vllm-project/vllm/pull/64199) · state: open · merged: False

## Original PR description

Lets Qwen4Exp's QSA layers run with `--kv-cache-dtype nvfp4`. Their main KV cache uses FlashInfer's NVFP4 pages and is read by `flashinfer.sparse.qsa_sparse_paged_attention`, which comes from [FlashInfer #6804](https://github.com/flashinfer-ai/flashinfer/pull/6804). That PR is merged and ships in the next FlashInfer release; this becomes usable once vLLM's FlashInfer pin moves to that release. On the current 0.7.2.post1 pin, BF16 and FP8 caches run as before and `nvfp4` fails at startup, since the pinned FlashInfer doesn't have the function.

## Claims

- Qwen4Exp QSA accepts an NVFP4 main KV cache. FlashInfer picks the kernel from the compute capability and rejects GPUs it has none for, so vLLM keeps no architecture list of its own.
- The same KV memory holds 593,398 tokens with NVFP4 against 390,645 with FP8, and long-context passphrase retrieval matches FP8 (9/9 vs 9/9).
- A QSA layer forward takes 0.63-0.87 of the FP8 time with CUDA graphs and 0.52-0.59 in eager mode.
- BF16 and FP8 caches keep their current path.

## Validation

sm_80, main (`6376fda7a9`) plus this PR, FlashInfer from main (`3bfacde7d`), which picks its Cake kernel here:

- `tests/models/qwen4_exp/test_qsa_prepare.py` and `test_qsa_reference.py`: 69 passed and 21 failed, the same tests as on main. The 21 are FP8 cases that pass `float8_e4m3fn` tensors to the Triton kernels, which Triton can't compile below sm_89 (`type fp8e4nv not supported in this architecture`); the serving path hands those kernels the raw `uint8` cache there.
- Qwen4Exp checkpoint with NVFP4 weights and its real KV scales, TP=2, 3.3 GB of KV cache per GPU. A passphrase at 10, 50 and 90% depth of 15.7K, 47.1K and 98.0K-token prompts: 9/9 with NVFP4, 9/9 with FP8. The same reservation holds 593,398 NVFP4 tokens against 390,645 FP8 tokens.
- 8-layer dummy model end to end with `nvfp4`: the bytes each QSA layer writes match FlashInfer's writer run separately on the same K/V and scales, and all rows of the four checked attention calls are within 2^-6 normalized error of an FP64 reference over the dequantized cache.
- One QSA layer forward (prepare, cache write, attention, gate and projections) of that model, decoding at 8K context, NVFP4 time over FP8 time, two runs each in ABBA order. The two FP8 runs differ by up to 20% with CUDA graphs while the two NVFP4 runs agree, so each cell gives the ratio against both FP8 runs:

  | rows | 1 | 8 | 16 | 64 |
  | --- | --- | --- | --- | --- |
  | CUDA graphs | 0.76-0.87 | 0.64-0.76 | 0.63-0.75 | 0.64-0.78 |
  | eager | 0.57-0.58 | 0.53-0.55 | 0.54-0.57 | 0.52-0.53 |

- That model also completes end to end with `VLLM_GPU_SYNC_CHECK=error` for both `fp8` and `nvfp4`.

CI can't run the NVFP4 path until the FlashInfer pin carries the function, so this PR adds no test that would only be skipped there. The kernel's tests are FlashInfer's (`tests/experimental/test_qsa_nvfp4.py`, `test_cake_qsa_nvfp4.py` and `test_cake_qsa_nvfp4_api.py`).

## Details

- The cache spec and the data/scale views are the FlashInfer backend's (`customize_spec`, `_nvfp4_kv_views`), and the cache is written by `nvfp4_quantize_append_paged_kv_cache_with_slot_mapping`, the writer the FlashInfer backend already uses for its fa2 NVFP4 path. The QSA layer writes and reads its own cache with that pair on every GPU, so the FlashInfer backend's trtllm-gen NVFP4 layout on SM100 doesn't come into it.
- The fused prepare still runs for NVFP4. Its cache store handles BF16 and FP8 rows only, so under NVFP4 it writes BF16 K|V rows to a workspace staging buffer, which FlashInfer then quantizes into the cache. The staging buffer is reserved during the profiling run next to the indexer scratch.
- `flashinfer.sparse` is imported when the attention impl is built, so a FlashInfer without the function fails at model construction rather than on the first request.
- With `backend="auto"`, FlashInfer runs its reference kernel on 8.x and 9.0 and its Cake kernel on 10.0, 10.3, 10.7 and 12.0. Cake's results agree with the reference kernel within FlashInfer's test tolerances but are not bit-identical to it.
- The Triton main-attention warmup is skipped for NVFP4, since that kernel never runs over an NVFP4 cache.
