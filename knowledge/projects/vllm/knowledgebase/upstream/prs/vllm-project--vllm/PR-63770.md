# [Bugfix][ROCm] Keep ROCM_AITER_FA rows without query tokens out of the kernels

[Upstream PR](https://github.com/vllm-project/vllm/pull/63770) · state: open · merged: False

## Original PR description


_Requested by **Tun Jian**_



## Overview

Stacked on #63675 (the ROCM_AITER_FA test suite). Only the last commit is new; please review it after #63675 lands. Part of the attention backend test standard RFC (https://github.com/vllm-project/vllm/issues/63640), rule B8.

**Before:** ROCM_AITER_FA ran rows with no query tokens as if they were real rows. Those rows come from FULL CUDA graph request padding (seq_len 0) and from requests whose KV an async connector is still loading (seq_len > 0, #51486).
- In a decode-only batch, the decode kernels computed each such row at the Q/output row its `query_start_loc` points at, which is past the real tokens. With unpadded buffers that is an out-of-bounds read and write; the suite caught it as a GPU abort, and deterministically as writes into padded output rows.
- The extend chunk planner gave such rows context chunks for their whole computed length, and the sliding-window extend gathered a full window for them. Nothing reads that context, but it adds chunks no real row needs: 22 chunks instead of 2 in the suite's case. #55695 and #51489 ask chunk planners never to do this.

**After:** trailing zero-query rows of a decode-only batch are left out of the decodes, and zero-query extend rows get no context chunks and no sliding-window gather.

This deletes the `zero-query-rows` entry from `known_defects.py`. Its 8 unit tests were strict xfails on #63675 and now pass.

## Details

- `AiterFlashAttentionMetadataBuilder.build`: when the batch has no extends or prefills, `num_decodes` stops at the last row with query tokens. This is computed from `query_start_loc_cpu`, so decode-only builds still do not sync the GPU.
- Extend rows with no query tokens get `computed_kv_lens = 0` and a sliding-window gather length of 0.

## Related upstream PRs

#55695 and #51489 fix the same class of bug in the DeepSeek-V4 sparse prefill paths (zero-query chunks); #51486 is the original report.
