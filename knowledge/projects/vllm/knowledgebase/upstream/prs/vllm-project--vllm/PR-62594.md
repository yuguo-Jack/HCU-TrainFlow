# [Perf][Sampler] Split the full-vocab passes of the Triton top-k/top-p kernel over several programs per row

[Upstream PR](https://github.com/vllm-project/vllm/pull/62594) · state: closed · merged: False

## Original PR description



## Overview

With an active top-k, `_topk_topp_kernel` runs **one program per row**, and that program sweeps the whole vocab twice: once to gather outliers and once to apply the final mask. On A100 with a 248K vocab, one row takes about 360 µs of GPU time, and most of it is spent in those two sweeps. This PR splits the two sweeps over several programs per row. The pivot search and the top-p search stay as they are, and the output is **bitwise equal** to the current kernel.

Related:
- #61996 / #54651 add the split pipeline for top-p-only rows; this PR covers rows with an active top-k.
- #59540 also touches the scratch buffer.

## Claims

- **Faster:** on A100-SXM4-40GB, `apply_top_k_top_p_triton` GPU time is 1.14–4.1× lower at `top_k` 20 (with and without `top_p` 0.95), up to 512 rows at a 248K vocab. Outside the gate it is never slower (1.00×).
- **Same output:** bitwise equal to `main` on 96 + 42 test inputs, which include ties, `-inf` regions, mixed per-row k/p and chunked batches.
- **Small scratch cost:** the existing per-program buffer is reused, padded by at most one gather tile per split (≤ 128 KiB per row). There is no new host sync and no new CPU work per call; 3 extra kernel launches.
- **Where it applies:** this is the MTP/EAGLE verify path of MRV2. It runs `apply_top_k_top_p` on every step for `(1 + num_spec) × num_reqs` rows. For example, Qwen3.8-Flash with MTP 3 at 32 requests gives 128 rows × 248K vocab: 928 µs → 634 µs per step.

## Details

- **Why one program per row is slow here:** each pass loads 8192-wide tiles and runs a `tl.cumsum` per tile to compact the outliers. A single program moves 3–6 GB/s, so the row is latency-bound. Measured stage times for 1 row:
  - pass 1 alone: about 220 µs GPU time;
  - the top-k + top-p searches: about 50 µs;
  - the final mask: about 40 µs.

  Replacing the searches (cached tiles, a `tl.sort` fast path) did not help, so the sweeps are the target.
- **Exactness:**
  - `_topk_split_pivot_kernel` computes the block-0 Gaussian pivot with the same `BLOCK_SIZE` and `num_warps` as the monolithic kernel, so every split selects the same outliers.
  - The monolithic kernel (`NUM_SPLITS > 0`) merges the per-split max, min and counts, which is order-free. It moves each split's outliers down in vocab order, so the buffer is byte-identical to the one-program sweep, and the unchanged searches compute the same float sums. Destinations never pass sources, and barriers order each tile's loads before its stores.
  - Rows with ties at the pivot (`num_keep < num_duplicate_logit`) keep the sequential mask, which needs vocab order. All other rows get `logit > pivot` in `_topk_split_mask_kernel`.
- **Memory:** rows run in chunks of `num_sm`, one row per program, so the existing `(num_programs, row_len)` buffer holds every split. `row_len` grows from `vocab` to `splits × ceil(tiles / splits) × gather_block`, which is at most 16 × 2048 extra floats. A small per-device workspace holds the split stats.
- **Warm-up:** like the existing top-k/top-p kernels on CUDA, the new kernels JIT on first use. MRV2 registers these warm-ups only on ROCm.
- **Complexity:** about 200 new lines (three kernels, `_apply_topk_split`, the gate). The rest of the +429 is re-indentation of the existing first pass and mask loop under the new `NUM_SPLITS` branches. The one-program path compiles to the same code (`NUM_SPLITS = 0`).
