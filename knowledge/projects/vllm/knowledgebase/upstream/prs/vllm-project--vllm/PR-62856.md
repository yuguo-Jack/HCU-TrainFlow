# [Bugfix][Frontend] Accept and echo prompt-cache and safety_identifier fields in the Responses API

[Upstream PR](https://github.com/vllm-project/vllm/pull/62856) · state: closed · merged: True

## Original PR description

## Overview

Fixes #62855. `/v1/responses` now accepts `safety_identifier`, `prompt_cache_retention` and `prompt_cache_options` as typed fields and echoes them, together with `prompt_cache_key` (#32824), on the response object, as OpenAI does.

## Claims

- The three fields are declared on `ResponsesRequest`, so they are validated. Before this change they were untyped extras
- `ResponsesResponse` echoes all four through `from_request`, which covers non-streaming, streaming (`response.created` …) and background responses
- `prompt_cache_retention` accepts `"in-memory"` (older `openai` SDKs), `"in_memory"` (current SDKs) and `"24h"`. Any other value returns 400
- No change for requests that don't send these fields; they echo as `null`

## Validation

New tests in `tests/entrypoints/openai/responses/test_serving_responses.py`: each field is echoed, an omitted field is `None`, invalid retention or `ttl` is rejected, and `response.created` carries the fields. They fail on `main` and pass with this change.

## Details

- Root cause: #32824 declared `prompt_cache_key` on the request but not on the response; the other three fields were never declared
- `PromptCacheOptions` is defined locally because the minimum supported `openai` (2.25) doesn't have it
- No length limit on `safety_identifier`. vLLM doesn't use the value, and a limit would turn requests that succeed today into 400s
- vLLM still doesn't act on these fields; the field descriptions say so

Upstream has two different shapes here. Can we add `prewarm` on the request and echo only the three response fields?
