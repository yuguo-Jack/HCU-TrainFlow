# [Model][ROCm] qwen4_exp: 4-bit NF4 n-gram embedding table

[Upstream PR](https://github.com/vllm-project/vllm/pull/60670) · state: open · merged: False

## Original PR description



## Overview

**Draft: waiting for #56273.** Add a 4-bit NF4 storage format for the qwen4_exp (Qwen3.8-Flash-Next) n-gram embedding table on the AMD path, selected with `ple_embedding_dtype: "nf4"`.

The n-gram table is 51 GB in FP8 and lives in pinned host memory, which does not fit hosts with 64 GB of RAM. In NF4 it is 24 GB. Each 160-wide row is stored as 16 Lloyd-Max levels of a unit Gaussian times one FP16 row scale: 80 bytes of codes, the scale and two bytes of padding, 84 bytes per row, so a row is still one contiguous read for the pinned UVA lookup. The rows are close to Gaussian (kurtosis 3.1), so the Gaussian levels beat a uniform int4 grid at the same size (relative squared error 0.81% vs 1.04% on the real table).

## Relation to #56273 (why this is a draft)

#56273 adds a packed NVFP4 PLE table through the same embedding-method interface and touches the same files (`common/ngram_embedding.py`, `amd/ple_layer.py`, `test_ple.py`). It explicitly rejects NVFP4 on the AMD path (`test_amd_rejects_nvfp4_ple`), so today AMD has no 4-bit table at all; that is the gap this PR fills. It is not a duplicate, but the two will conflict. I will rebase this onto #56273 once it lands and plug NF4 in as one more method of its interface, so the diff here should shrink.

Other related PRs checked: #55040 (FP8 PLE on AMD, a different format), #59958 (NVFP4 for `host_file_gather`, NVIDIA path), #58439 (checkpoint-mapped PLE for unified-memory GPUs), #58856 (FP8 lookup on SM86). None adds a 4-bit table on AMD.

## Checkpoint

There is no published NF4 checkpoint yet. The table is produced offline from the published FP8 or BF16 table with `quantize_ple_nf4` (in this PR, the same packer the tests use): per row, the scale is searched around the row RMS for the lowest squared error. I can publish the converted table or the conversion script, whichever reviewers prefer.

## Changes

- `common/ngram_embedding.py`: `Qwen4ExpPLENf4EmbeddingMethod` (allocation as `uint8` rows of `dim // 2 + 4` bytes, dequantize after lookup), `quantize_ple_nf4`. The pinned-host embedding copies the stored row width instead of the embedding dim, and reduces packed rows across ranks as raw bytes, like FP8.
- `amd/ple_layer.py`: the lookup buffers and the shard shape check use the stored row width.
- Known gap: on the NVIDIA path `ple_embedding_dtype: "nf4"` fails at load with a shard shape mismatch. I will turn that into an explicit rejection when rebasing onto #56273, mirroring its AMD rejection of NVFP4.

## Validation

**Unit tests** (gfx1100, this branch on `upstream/main` `f4dde3132c`): selection of the NF4 method, a quantize/dequantize round trip, the raw-byte cross-rank reduce, and a pinned-host lookup of packed rows.

```
pytest tests/models/qwen4_exp/test_ple.py
# 96 passed
```

**Full model**: Qwen3.8-Flash-Next, GPTQ W4A16 g32 checkpoint, fp16, TP4 on 4x RX 7900 XTX, NF4 vs FP8 table, same launch, paired per text:

| metric | NF4 − FP8 |
| --- | --- |
| NLL, 12 long texts, positions ≥ 2048 | +0.005 ± 0.003 |
| NLL, same texts, positions < 2048 | +0.032 ± 0.008 |
| NLL, 24 short texts | +0.010 ± 0.006 |
| GSM8K (chat, no thinking, 200 q) | 99.0% vs 99.0% |
| decode tok/s, 1 user, median of 6×512 | 65.6 vs 58.5 |

That run uses RDNA3 changes that are not in `main` yet (fp16 serving, #60650; asymmetric W4A16 MoE), so it shows the NF4 table is sound end to end rather than that `main` + this PR serves that checkpoint.
