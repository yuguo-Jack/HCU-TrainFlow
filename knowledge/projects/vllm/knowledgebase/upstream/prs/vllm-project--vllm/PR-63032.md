# [ROCm][Perf] Qwen3.8-Flash-Next specialized decode on MI355X (--monokernel)

[Upstream PR](https://github.com/vllm-project/vllm/pull/63032) · state: closed · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Opt-in `--monokernel` decode for Qwen3.8-Flash-Next (`amd/Qwen3.8-Flash-Next-Quark-MXFP4`) at TP2 on MI355X. Laid out per the specialized-decode RFC #60904 under `vllm/models/qwen4_exp/amd/specialized_decode/`. A decode step of 1–16 rows runs four persistent FlyDSL launches a layer; everything else runs vLLM's forward. No core changes beyond the `--monokernel` docstring.

## Claims

- 23–37% lower median TPOT than stock vLLM at 1–8 concurrent requests and 9–12% at 12 and 16 (1k/1k and 8k/1k), on the same image and flags. Past 16 rows `plan()` hands the step to vLLM's decode, and the two are level (within 1%).
- Accuracy parity: GSM8K 0.967 vs 0.966 stock; GPQA 0.902 vs 0.902 over three repeats each; NIAH 1.000 for both at 64k and 128k, every needle answered alike.
- Follows RFC #60904: `--monokernel` switch, default-deny refusals in three stages (each listing every reason, TP ranks agreeing), one `plan()` per step, MRV2 only, model-owned code, weights and caches read in place.
- A rank whose cross-rank wait gives up (10 s) marks itself failed; the TP ranks raise together within 16 steps, so the engine stops rather than hangs (tested with a stalled rank).
- Kernel numerics tests (TP2, MI355X) and CPU refusal/routing tests, with a Buildkite MI355 step.

## Validation

All numbers: MI355X, TP2, image `vllm/vllm-openai-rocm:nightly-df3bd094aeea829f27baa0a5282830464f601d9f` with this branch's `vllm/models/qwen4_exp/amd/` overlaid, default FULL_AND_PIECEWISE graphs, empty vLLM and AITER caches per run. Stock and `--monokernel` differ only in the flag. The TPOT table, GSM8K and the tests are at this PR's head; GPQA (`b595b0e37f`) and NIAH (`910ca119ca`) ran on earlier revisions of this branch, before the batched GDN polls and the MXFP4 MoE intermediate.

## Details

**Launches.** Per layer: (1) the attention hyper-connection front (grouped Gemma norm, down + inject GEMM, hc_silu, up GEMM, gate-mix); (2) the GDN block (in_proj_qkvz MXFP4 + in_proj_ba, conv update, gated delta rule, RMSNormGated), with vLLM's QSA attention on the QSA layers; (3) the o_proj block (out_proj MXFP4 / gated o_proj BF16, TP all-reduce, attention HC combine); (4) the MLP front and the MoE block (softmax top-10 router, MXFP4 experts with the fused shared expert, TP all-reduce, MLP HC combine). Blocks 3 and 4 fold the HC combine into the all-reduce epilogue and hand the next front its sums of squares, so the multi-stream state is written once a block. Embeddings, final mix, head and sampling stay vLLM's. This is the RFC's step mode; no launch spans more than two layers.

**MXFP4 layouts.** Since #61278, `AiterMxfp4LinearKernel` uses the ASM FP4 GEMM only for tuned shapes; FN's TP2 in_proj_qkvz and out_proj have no tuned ASM config, so on main they are row-major with transposed scales and run Triton `gemm_afp4wfp4`. The kernels read whichever layout vLLM picked (`runtime/guards.py`, `mxfp4_shuffled`) in place and quantize the activations with the matching rounding (Triton's floor rule vs ASM's RCEIL). Both layouts are covered by `test_kernels.py`. No weights are duplicated.

**Refusals.** Config (model `__init__`): TP≠2, PP, DP, EP, EPLB, DCP, PCP, DBO, sequence parallelism, LoRA, KV connectors, routed-expert capture, speculative decoding, sleep mode, CPU offload, weight updates, GDN prefix caching, GDN state dtypes other than BF16 conv / FP32 recurrent, QSA KV cache dtypes other than BF16, unfused shared expert, MRV1, `STOCK_TORCH_COMPILE`, other shapes, non-gfx950 or partitioned GPUs. Model (after load): every layer's modules, quant methods, weight layouts and shapes. Caches (every bind): GDN state dtypes, shapes and slot layout. Without `--monokernel` none of this runs.

**Steps.** `plan()` returns a `Step` for a pure decode of 1–16 rows with int32 GDN state indices, else None (stock forward). Every width is compiled when the executor is built (FlyDSL `COMPILE_ONLY`), so no JIT on the first step of a width. PIECEWISE steps run stock; the warmup forward before each PIECEWISE capture runs the specialized kernels eagerly, as intended.

**Shared helpers.** The launch ABI and health words (`mono/abi.py`), the device primitives, tagged mailbox and build keys (`mono/common/`), the GEMV stage (`mono/stages/gemv.py`), peer memory (`runtime/peer.py`) and `FailStop` (`runtime/guards.py`) are adapted from the Kimi-K3 decode (#60683, by @hyukjlee, after ROCm/ATOM) and trimmed to what these kernels use. The package imports nothing from other models, as RFC #60904's "the model owns it" asks; the kernel cache key covers every source under its `mono/`, and the Buildkite step triggers only on this model's directories.

**Limitations / follow-ups.**
- Failure: every cross-rank wait is bounded (10 s). A rank that gives up records the wait, flags the output rank and sets its sticky failed word; `FailStop` copies that word to the host without blocking after each step (from `compute_logits`) and the TP ranks vote over the CPU group every 16 steps, then raise together. There is no fallback to the stock forward after a failure; without `--monokernel` vLLM's decode runs.
- Size: ~6.8k lines, about 1.1k of them the shared helpers, almost all in the model-owned package (outside it: 16 lines in `model.py`, 29 in `model_state.py`, the `--monokernel` docstring naming this model, the Buildkite step).
- The QSA layers run vLLM's QSA ops between the GDN block's stages (~13% of a c4 8k step), so faster QSA kernels, such as #62589's one-row decode path or #59437's FlyDSL kernels, apply to both routes; a fused QSA block is not in this PR.
- Speculative decoding is refused here; #63124 (stacked on this PR) adds MTP verify steps.
- Startup does not check the FlyDSL version; serving was measured with FlyDSL 0.3.4.1 (AITER v0.1.25), the tests run with FlyDSL 0.4.0 (AITER v0.1.26, which main pins).
