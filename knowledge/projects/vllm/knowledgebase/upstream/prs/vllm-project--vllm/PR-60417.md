# [HiSparse] Read GPU-resident KV directly for mixed and BF16 prefills

[Upstream PR](https://github.com/vllm-project/vllm/pull/60417) · state: closed · merged: True

## Original PR description

Fixes #60420.

**Problem on main:** with HiSparse, a prefill batched with any decode copies its entire KV history into a temporary GPU buffer on every layer of every chunk, then joins the decode and prefill outputs with `torch.cat`. This happens even when all of its KV is already on GPU, which is the common case in aggregated serving. FlashMLA BF16 does the copy on every prefill. Startup profiling sees neither allocation. Two results:
- **Crash:** a long prompt arriving while other requests decode kills EngineCore with CUDA OOM, and the running requests die with it.
- **Slowdown:** the per-layer copy grows with context. A 1M-token prefill on FlashMLA BF16 takes 3.3x longer than without HiSparse.

**Now:** when all KV is on GPU, decode and prefill rows run in one kernel against the GPU pages, with no copy and no `torch.cat`. Covers FlashInfer, FlashAttn, FlashInfer SM120 and FlashMLA BF16 sparse MLA.

**Evidence:** 1×B200, GLM-5.3-NVFP4 cut to 4 layers with dummy weights, 2 requests decoding, then one 1.04M-token prompt. Peak is the largest per-step peak above the step's starting allocation.

```bash
vllm serve <GLM-5.3-NVFP4> --load-format dummy --hf-overrides '{"num_hidden_layers": 4}' \
  --kv-cache-dtype fp8 --block-size 64 --max-model-len 1048576 --gpu-memory-utilization 0.97 \
  --scheduler-reserve-full-isl \
  --kv-transfer-config '{"kv_connector":"HiSparseConnector","kv_role":"kv_both","kv_connector_extra_config":{"host_pool_gib":24}}'
```

| Path | main | this PR | no HiSparse |
|---|---|---|---|
| FlashInfer fp8, util 0.97 | **OOM at 934K** in `torch.cat`; peak 6.30 GiB | 58.6 s; peak 4.91 GiB | 53.7 s; peak 4.91 GiB |
| FlashMLA BF16, util 0.95 | 184 s; peak 6.58 GiB | 56.0 s; peak 4.48 GiB | 55.2 s; peak 4.48 GiB |

With debug logging, no host-staging calls happen with this PR.

**Tests**
- `pytest tests/v1/attention/test_sparse_mla_backends.py` (B200): 509 passed. The resident-mixed routing cases in `test_sparse_mqa_hisparse_lanes` fail on main.
- GSM8K, GLM-5.3-NVFP4 TP4 with HiSparse, 4×B200 (1319 questions, 5-shot, FlashInfer sparse MLA), two runs each: 0.896 / 0.914 vs main 0.914 / 0.909.
- After merging #55866 (shared HiSparse forward), the 4-layer repro at util 0.97 still OOMs on main (12b005eefa, in `torch.cat`) and completes with this PR.
