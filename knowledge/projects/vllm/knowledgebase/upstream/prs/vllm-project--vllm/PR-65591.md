# [Model][CUDA] Gemma 4 native vision tower on H100: bound eager tower memory, fix Triton test

[Upstream PR](https://github.com/vllm-project/vllm/pull/65591) · state: open · merged: False

## Original PR description



## Overview

Fixes for Gemma 4's native vision tower (#65431) on NVIDIA H100: bound the eager tower's peak memory, fix the Triton tower test on NVIDIA, and document the validated backends.

**Stacked on #65431.** Only the last 3 commits are new. Draft until #65431 merges, then I'll rebase.

## Claims

- **KV cache:** #65431 packs every image of an encoder batch into one eager tower call. On `google/gemma-4-31B-it` this raises the profile's peak activations and shrinks the KV cache by enough that the model no longer starts with `max_model_len=8192` at `gpu_memory_utilization=0.9`: peak activations grow from 2.78 to 3.83 GiB. Capping eager calls at 4 × 1120 soft tokens brings peak activations back to 2.81 GiB and the KV cache to within 2% of main (8,479 vs 8,642 tokens).
- **Test fix on NVIDIA:** `test_gemma4_vision.py` fails its Triton case on NVIDIA because Triton's fp32 `tl.dot` uses TF32 there. Triton now gets 3e-2 on CUDA; SDPA keeps 1e-3.
- **Validated on H100:** `FLASH_ATTN` (auto-selected for head_dim 72 on SM90), `FLASHINFER` and `TRITON_ATTN`, both eager and with `cudagraph_mm_encoder`. `TORCH_SDPA` works eager, and with graphs it stops at startup with a clear error.

Divergences start at tokens 5 to 62 of 64. The native tower on FA and on SDPA differs from itself by the same amount (3/6 exact, the rest within top-5), so this is bf16 noise in the vision embeddings rather than a backend issue. In fp32 the tower matches transformers to <= 1e-5 relative error (31B head_dim 72 and E2B clipped linears).

Encoder graphs on **MRV2** OOM during capture for 31B at util 0.95, **on main as well**. MRV2 reserves about 6 GiB less graph memory than MRV1 does for the same config (11.96 vs 5.6 GiB available KV). That is unrelated to this PR, and I'll report it separately.

```python
"""Gemma 4 e2e: greedy outputs + top-5 logprobs for fixed image prompts.

Usage: python e2e_gemma4.py --out o.json [--backend FLASH_ATTN] [--graph]
"""

import argparse
import json
import time

from vllm import LLM, SamplingParams
from vllm.assets.image import ImageAsset

QUESTIONS = [
    "Describe this image in detail.",
    "What text, if any, appears in the image?",
    "List the main colors in the image.",
]


def main():
    p = argparse.ArgumentParser()
    p.add_argument("--model", default="google/gemma-4-31B-it")
    p.add_argument("--backend", default=None)
    p.add_argument("--graph", action="store_true")
    p.add_argument("--compile-mm", action="store_true")
    p.add_argument("--gpu-util", type=float, default=0.9)
    p.add_argument("--max-model-len", type=int, default=8192)
    p.add_argument("--out", required=True)
    a = p.parse_args()

    comp = {}
    if a.graph:
        comp["cudagraph_mm_encoder"] = True
    if a.compile_mm:
        comp["compile_mm_encoder"] = True
    t0 = time.perf_counter()
    llm = LLM(
        a.model,
        max_model_len=a.max_model_len,
        gpu_memory_utilization=a.gpu_util,
        limit_mm_per_prompt={"image": 2},
        mm_encoder_attn_backend=a.backend,
        compilation_config=comp or None,
        seed=0,
    )
    startup = time.perf_counter() - t0

    images = [ImageAsset(n).pil_image for n in ("stop_sign", "cherry_blossom")]
    prompts = []
    for img in images:
        for q in QUESTIONS:
            msgs = [
                {
                    "role": "user",
                    "content": [
                        {"type": "image_pil", "image_pil": img},
                        {"type": "text", "text": q},
                    ],
                }
            ]
            prompts.append(msgs)
    sp = SamplingParams(temperature=0, max_tokens=64, logprobs=5)
    llm.chat(prompts[:1], sp)  # warmup
    t1 = time.perf_counter()
    outs = llm.chat(prompts, sp)
    gen = time.perf_counter() - t1

    res = {
        "startup_s": startup,
        "gen_s": gen,
        "outputs": [
            {
                "text": o.outputs[0].text,
                "token_ids": list(o.outputs[0].token_ids),
                "logprobs": [
                    {str(k): v.logprob for k, v in lp.items()}
                    for lp in o.outputs[0].logprobs
                ],
            }
            for o in outs
        ],
    }
    json.dump(res, open(a.out, "w"))
    print(f"RESULT startup={startup:.1f}s gen={gen:.2f}s -> {a.out}")


if __name__ == "__main__":
    main()
```

## Details

- Without the cap, the tower's activations grow with the whole encoder batch (the profile batch is up to the encoder cache budget, 16384 tokens here), and that peak is reserved away from the KV cache. The cap splits a batch into calls of at most 4 × 1120 soft tokens, the largest single image times 4, and keeps the outputs in input order (covered by `test_eager_vision_calls_are_bounded`).
- With tower LoRA (`enable_tower_connector_lora`), the batch stays one call, because the LoRA mapping is built over the whole encoder batch.
- Encoder CUDA graphs are unaffected: they already pack by token budget.

**Not a duplicate:** this PR builds on #65431 and adds only the H100 fixes above. I have commented the findings on #65431.
