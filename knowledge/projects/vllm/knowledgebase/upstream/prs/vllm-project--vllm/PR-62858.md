# [Bugfix] Make LOG2E a constexpr in the DeepEncoder attention kernel

[Upstream PR](https://github.com/vllm-project/vllm/pull/62858) · state: open · merged: False

## Original PR description

## Overview

Fixes #62848. DeepSeek-OCR and Unlimited-OCR fail to start on v0.32.0 because the DeepEncoder rel-pos attention kernel added in #55629 reads `LOG2E`, a plain Python float, from inside `@triton.jit`, and Triton 3.7 rejects non-constexpr globals.

## Claims

- DeepSeek-OCR starts and serves again on v0.32.0 / main (Triton 3.7.1).
- Adds the first test for `deepencoder_rel_pos_attention`, which compares it with the non-Triton path.

## Validation

New test, `pytest tests/kernels/attention/test_deepencoder_rel_pos_attention.py` (float16 and bfloat16, 8x8, 14x14 and 16x12 grids), on an RTX 5060 Ti (SM120) with torch 2.13.0+cu130 and Triton 3.7.1:
- v0.32.0: 6 failed, each with the `CompilationError` from the issue
- this PR: 6 passed

End to end, `LLM("deepseek-ai/DeepSeek-OCR", enable_prefix_caching=False, mm_processor_cache_gb=0, enforce_eager=True)` with a rendered image and the prompt `<image>\nFree OCR.` at temperature 0:
- v0.32.0: `Engine core initialization failed`, with the `NameError("Cannot access global variable LOG2E from within @jit'ed function ...")` from the issue
- this PR: `'Invoice 2026-10-21\n\nTotal due: 1,234.56 EUR\n\nThank you for your order'`, which matches the image

`ruff check` and `ruff format --check` pass on the changed files.

## Details

The fix wraps the same value in `tl.constexpr` next to the kernel, as `gumbel.py` does for `_TL_RAND_MIN`. `vllm.triton_utils.LOG2E` stays a float, because `xpu_mla_sparse.py` uses it in host code (`sm_scale *= LOG2E`). This kernel is the only `@triton.jit` code that reads it. The `TritonLanguagePlaceholder` maps `tl.constexpr` to the identity, so importing the model without Triton still works.

Not a duplicate: no open PR mentions #62848, DeepEncoder or this constant. The issue's side note about `NGramPerReqLogitsProcessor` and the V2 model runner is a separate problem and isn't changed here.

AI assistance was used: I used Claude Code to reproduce the failure, write the fix and test, and run the validation above. I reviewed every changed line.

I checked the other kernels on main, and this is the only one that reads `triton_utils.LOG2E` as a global inside `@triton.jit`. `rocm_aiter_mla_merge.py` and `xpu_mla_sparse.py` pass `LOGE2` in as a `tl.constexpr` kernel argument (`LOGE2=LOGE2` at launch), so Triton 3.7 accepts them. `fast_exp` in mamba's `triton_helpers.py` defines its own `tl.constexpr` inside the function. `xpu_mla_sparse.py` also uses `LOG2E` in host code (`sm_scale *= LOG2E`), which is why I left the shared value as a plain float.

If you'd rather match the other kernels, I can pass `LOG2E` in as a `tl.constexpr` argument here instead of the module-level `_LOG2E`.
