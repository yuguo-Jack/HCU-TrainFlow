# [Bugfix][KV Offload][P2P] Support IPv6 literals in the ZMQ control channel

[Upstream PR](https://github.com/vllm-project/vllm/pull/64006) · state: open · merged: False

## Original PR description

## Overview

The P2P KV-offload tier's ZMQ control channel could not bind or dial IPv6 addresses.
This fixes the endpoint construction, enables `ZMQ_IPV6` on the control sockets, and
normalizes bracketed IPv6 literals, so `VLLM_P2P_SIDE_CHANNEL_HOST=::1` (or `[::1]`)
works.

## Claims

- `ZmqTransport` now builds ZMQ endpoints via `make_zmq_path()`, which brackets IPv6
  literals (`tcp://[::1]:5710`), replacing the ambiguous `tcp://::1:5710` the old
  f-string produced.
- The ROUTER and DEALER sockets set `ZMQ_IPV6=1` when the configured host is an IPv6
  literal. Without it libzmq rejects IPv6 endpoints regardless of the URL form.
- Bracketed literals (`[::1]`) are accepted and normalized to the bare form, both for
  the configured host and for a host parsed back out of a peer id. Previously a
  bracketed host was not recognized as IPv6 at all, so `ZMQ_IPV6` stayed off and the
  bind failed with an unrelated error.
- `test_bidirectional_messaging` is parametrized over IPv4/IPv6 on both sides, covering
  the mixed-family pair (IPv4 <-> IPv6), and now asserts the DEALER identity and the
  first message the ROUTER sees.
- Docs note that IPv6 literals are accepted in either form, with the port separate.

| With `make_zmq_path` + `ZMQ_IPV6` only | `24 passed` |

The test file is already wired into Buildkite CI (`check-test-tethering` passes). No GPU
is required. This is a control-plane change: it does not touch the data path, model
execution, or output, so no model evaluation applies.

## Details

Root cause: `_tcp_addr()` interpolated `f"tcp://{host}:{port}"`. An IPv6 literal makes
that string ambiguous (`tcp://::1:5710`), and libzmq additionally requires `ZMQ_IPV6` to
be enabled to use IPv6 transports at all. Both had to be fixed; fixing only the URL form
still fails to bind. A third case is a bracketed literal: `is_valid_ipv6_address()` only
recognizes the bare form, so `[::1]` silently took the IPv4 path. The approach mirrors
the existing mooncake control channel
(`vllm/distributed/ec_transfer/ec_connector/mooncake/control.py`), which uses the same
`make_zmq_path` + `ZMQ_IPV6` pairing.

Normalization happens at both entry points — the configured `host` in `__init__` and the
host parsed out of a `peer_id` in `_open_connection` — so a bracketed value cannot reach
`is_valid_ipv6_address()` from either direction.

The peer identity format is unchanged: `P2POffloadingTier` builds `_local_id` and
`_peer_id_from_params` as bare `host:port`, and `_open_connection` parses it back with
`rsplit(":", 1)`. For IPv6 that yields the correct host and port, so no identity
migration is needed and IPv4 behavior is untouched.

Tradeoffs and limitations:

- Hostnames that resolve to IPv6 (rather than IPv6 literals) still take the IPv4 socket
  path, matching existing vLLM behavior.
- Only the control channel is covered here; the data plane address handling is
  unchanged.
