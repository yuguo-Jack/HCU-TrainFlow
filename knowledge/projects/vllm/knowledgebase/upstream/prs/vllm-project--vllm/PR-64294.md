# [Bugfix][Rust Frontend][ZMQ] Run ZMQ transport I/O on the dedicated runtime

[Upstream PR](https://github.com/vllm-project/vllm/pull/64294) · state: closed · merged: True

## Original PR description



## Overview

Create and connect Rust frontend ZMQ sockets on the dedicated runtime so
socket readiness and background transport tasks use the same Tokio I/O
driver. Caller-runtime load or shutdown can no longer delay or terminate
engine communication.



## Claims

- Registers HandshakeOwner and Bootstrapped transport I/O with the dedicated
  ZMQ runtime instead of the runtime that calls `EngineCoreClient::connect`.
- Keeps engine communication functional after the connecting runtime is shut
  down.
- Preserves the existing transport protocol, configuration, and public API.
- Retains cancellation safety while connection setup runs on the dedicated
  runtime.



## Validation

```
cargo nextest run --locked -p vllm-engine-core-client \
  client_transport_outlives_connecting_runtime
```


A Linux epoll probe with a mock engine confirmed the runtime ownership change:

| Measurement | Before | After |
|---|---:|---:|
| ZMQ TCP descriptors on the connecting runtime | 4 | 0 |
| ZMQ TCP descriptors on the dedicated runtime | 0 | 4 |
| Output delay while the connecting runtime was blocked | ~4.70 s | 0.43–0.75 ms |




## Details

Tokio associates TCP resources with the I/O driver of the runtime active when
those resources are created. Transport setup previously ran on the caller
runtime, while `build_zmq_runtime()` was called only after the sockets had
already been bound or connected. Background transport tasks ran on the
dedicated runtime, but socket readiness was still driven by the caller
runtime.

The dedicated runtime is now created before transport setup. The complete
connection path runs on that runtime, and the same runtime is passed into
`from_connected` for background task execution and lifetime ownership.
