# [Attention][DCP] Support DCP on the FlashMLA sparse bf16 KV path

[Upstream PR](https://github.com/vllm-project/vllm/pull/61609) · state: open · merged: False

## Original PR description



## Overview

Enables decode context parallelism (DCP) for `FLASHMLA_SPARSE` with a bf16 KV cache. Until now the bf16 path raised `NotImplementedError` under DCP.

Related: #46514 (DCP for the `fp8_ds_mla` mixed-batch path, which added the bf16 guard), #61285 (`a2a` comm backend for the same backend).

## Claims

- `--kv-cache-dtype bfloat16` with `--decode-context-parallel-size > 1` now runs on `FLASHMLA_SPARSE`. On Hopper, no other sparse MLA backend supports DCP.
- GSM8K accuracy matches DCP1: 0.904 at DCP4 vs 0.894 at DCP1 on GLM-5.3-Flash.
- bf16 is not bound by the fp8 DCP limits (mixed-batch only, head envelope). For example, 32 local heads at DCP4 and 16 at DCP8 are accepted.
- On GLM-5.3-Flash, DCP4 holds 1.40× the KV tokens of DCP1.

## Validation

**Setup.** One GH200 node, 4× GPUs (96 GB, SM90). `zai-org/GLM-5.3-Flash`, TP4, `--quantization fp8` (weights only; the KV cache stays bf16).

**Unit tests.** `pytest tests/v1/attention/test_sparse_mla_backends.py -k dcp`: 10 passed, 3 of them new.

**GSM8K.** `tests/evals/gsm8k/gsm8k_eval.py`, 500 questions, 5-shot, greedy, seed 42, CUDA graphs on. Both runs set `sparse_mla_force_mqa`, so prefill rows also take the changed path; otherwise GSM8K prompts (shorter than `index_topk`) would go to dense MHA and only decode would be tested.

| DCP | Accuracy | Invalid | Output tok/s |
|---|---:|---:|---:|
| 1 | 0.894 | 0.000 | 833 |
| 4 (`ag_rs`) | 0.904 | 0.000 | 726 |

The difference is within the ~1.3-point standard error at n=500.

**KV-cache capacity.** Same per-rank KV memory budget in each row.

| Mode | DCP1 tokens | DCP4 tokens | Ratio |
|---|---:|---:|---:|
| eager | 225,475 | 315,665 | 1.40× |
| CUDA graphs | 216,892 | 302,557 | 1.39× |

```bash
  --num-questions 500 --num-shots 5 --max-concurrency 64 --seed 42
```

- `--cp-kv-cache-interleave-size 4`: required by GLM-5.3-Flash's indexer KV compression (`compress_ratio=4`) under DCP.
- `--max-num-seqs 128`: keeps the per-request state blocks within memory for CUDA graph capture.

## Details

- **Root cause.** Under DCP each rank holds a shard of the KV cache, but the indexer emits global token ids. The bf16 path converted them with `triton_convert_req_index_to_global_index`, which treats every index as local, so it would read slots owned by other ranks. #46514 enabled DCP for fp8 only and added a guard rejecting bf16.
- **Fix.** `_forward_bf16_kv` converts top-k with `triton_filter_and_convert_dcp_index`, as the fp8 path and the sparse MLA base already do. Its compacted output and valid counts map directly onto `flash_mla_sparse_fwd`'s `topk_length`.
- **Empty rows.** For a row where this rank owns none of the selected tokens, `flash_mla_sparse_fwd` returns `lse=+inf` (FlashMLA `tests/ref.py`). Those rows are set to `-inf`, the identity of the cross-rank merge, as the fp8 path does. The output is made contiguous for the combine.
- **Guards.** The bf16 kernel returns the LSE for every token and pads the gathered heads itself, so the builder's mixed-batch and head-envelope checks now apply to fp8 caches only. PCP+DCP with bf16 and HiSparse+DCP are still rejected.
- **Cost.** bf16 KV is ~1.75× the size of `fp8_ds_mla`, so fp8 stays preferable where its DCP path applies. This PR covers the configs it rejects and deployments that need a bf16 cache.
- **Not a duplicate.** Searched open PRs and issues for "DCP FlashMLA sparse bf16" and "DCP sparse bf16 fp8_ds_mla". #54541 touches the same conversion but backports to v0.28.0, which predates #46514's guard.
- **Tests.** `test_bf16_dcp_skips_fp8_guards` covers the builder and `test_bf16_dcp_filters_topk_and_neutralizes_empty_rows` covers the forward path, both in `test_sparse_mla_backends.py`.
