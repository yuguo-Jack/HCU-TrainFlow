# [ROCm][Perf] Fuse the GDN gated RMSNorm into out_proj at decode

[Upstream PR](https://github.com/vllm-project/vllm/pull/58802) · state: open · merged: False

## Original PR description

## Summary

On ROCm, run the Gated DeltaNet output norm (`RMSNormGated`) and the unquantized `out_proj` GEMM as one AITER FlyDSL kernel at decode. On `amd/Qwen3.8-2.4T-A95B-Quark-MXFP4` at TP8 on MI355X, median TPOT drops by 3.5% at 1 concurrent request (14.84 to 14.31 ms) and by 1.3% at 8 (21.43 to 21.14 ms). gsm8k does not change.

This needs ROCm/aiter#5881, which adds `flydsl_gdn_gated_rmsnorm_out_proj`. With an AITER build that does not have it, `is_gdn_norm_out_proj_enabled()` returns False and the layer runs `_output_projection` as before.

## Background

In the decode CUDA graph of this model, a GDN layer at 1 token runs the gated norm as one Inductor kernel, then an Inductor copy of its output into the input of `rocm_unquantized_gemm`, then `wvSplitK` for `out_proj`. On rank 0 with the torch profiler, these take 5.16, 4.72, and 9.56 µs per layer, and the model has 69 GDN layers. The fused kernel replaces all three and takes 8.08 µs. At 8 tokens the op runs the Triton gated norm and then the GEMM on a view of its output, so the copy is gone there too.

The profiler makes every kernel in the graph longer, so these times are larger than without it. Without the profiler, TPOT at 1 concurrent request drops by 0.53 ms, which is 7.7 µs per GDN layer.

## What this PR does

- `qwen_gdn_linear_attn.py`: `forward_hip` calls `_fused_output_projection`, which runs the new custom op `vllm::qwen_gdn_gated_rmsnorm_out_proj` and then the TP all-reduce. The all-reduce stays outside the op, so the all-reduce + RMSNorm fusion still applies.
- The op runs the AITER kernel for the batches that `flydsl_gdn_gated_rmsnorm_out_proj_supported` accepts, which is 1 to 5 tokens at this model's K = 2048. All other batches, including prefill, run the Triton gated norm and then `rocm_unquantized_gemm_impl`.
- The op takes the norm weight, the out_proj weight, and eps instead of a layer name. It is not a splitting op, so it is part of the compiled graph, and a layer name would make the graph of every GDN layer different. With a layer name, torch.compile took 157 s instead of 54 s.
- The layer uses the op only when AITER is enabled and has the kernel, `_supported` accepts the out_proj shape of the layer at 1 token, the norm uses SiLU, and out_proj is unquantized bf16. `forward_hip` also checks that out_proj is not wrapped for LoRA. In all other cases the layer runs `_output_projection` as before.
- `VLLM_ROCM_USE_AITER_GDN_NORM_OUT_PROJ` (default on) turns it off. `_aiter_ops.is_gdn_norm_out_proj_enabled()` checks the flag and whether AITER has the kernel.
- `tests/kernels/mamba/test_gdn_output_projection.py` compares the op with `RMSNormGated.forward_static` + `F.linear` for 1, 3, and 5 tokens (AITER kernel) and 6 and 64 tokens (fallback).

## Validation

Setup: MI355X, TP8, ROCm 7.2.4, torch 2.10.0, FlyDSL 0.3.4.1, AITER main with ROCm/aiter#5881. The test image has vLLM from the `releases/v0.28.0` branch (2cf0a6915). The numbers are from this change applied there, and the changed lines are the same as in this PR.

```
vllm serve amd/Qwen3.8-2.4T-A95B-Quark-MXFP4 --tensor-parallel-size 8 --kv-cache-dtype fp8 \
  --max-model-len 32768 --max-num-batched-tokens 32768 --max-num-seqs 256 \
  --gpu-memory-utilization 0.9 --attention-backend ROCM_AITER_FA --async-scheduling \
  --no-enable-prefix-caching --generation-config vllm --trust-remote-code \
  --compilation-config '{"pass_config": {"enable_qk_norm_rope_fusion": true, "fuse_allreduce_rms": true}}'
```

with `VLLM_ROCM_USE_AITER=1`, `VLLM_ROCM_USE_AITER_MHA=1`, `VLLM_ROCM_USE_AITER_FUSION_SHARED_EXPERTS=1`, `AITER_USE_FLYDSL_MOE_SORTING=1`, `VLLM_ROCM_QUICK_REDUCE_QUANTIZATION=INT4`, `VLLM_ROCM_QUICK_REDUCE_MAX_SIZE_BYTES_MB=512`, `HSA_NO_SCRATCH_RECLAIM=1`, and `VLLM_PLUGINS=` so that no plugin is loaded. The cudagraph mode is the default `FULL_AND_PIECEWISE`. The only difference between the two arms is `VLLM_ROCM_USE_AITER_GDN_NORM_OUT_PROJ`. Every server start compiled into an empty cache.

Decode: `vllm bench serve --dataset-name random --random-input-len 1024 --random-output-len 256 --ignore-eos --num-prompts 12*c --max-concurrency c`, median TPOT in ms, mean ± std over 3 server starts without this PR and 4 with it:

| Concurrency | Without this PR | With this PR | Change |
|---|---|---|---|
| 1 | 14.84 ± 0.04 | 14.31 ± 0.03 | -3.5% |
| 2 | 15.81 ± 0.03 | 15.37 ± 0.02 | -2.8% |
| 4 | 17.67 ± 0.02 | 17.03 ± 0.20 | -3.6% |
| 8 | 21.43 ± 0.01 | 21.14 ± 0.03 | -1.3% |

Two of the four runs with this PR used an earlier version of the op that took a layer name and ran the same kernels. At concurrency 4, one run with this PR gave 17.32 ms and the other three gave 16.89 to 16.98 ms.

A decode batch runs as the next CUDA graph size, 1, 2, 4, or 8. So batches of 1, 2, and 4 tokens use the AITER kernel, and a batch of 8 uses the fallback path of the op. The fallback path is still faster than before because the copy is gone. With the profiler, the kernels between the GDN core and the all-reduce take 21.32 µs per layer at 8 tokens with this PR and 27.04 µs without it.

TTFT: at concurrency 1 the median TTFT is 185.4 ± 5.3 ms without this PR and 188.4 ± 2.2 ms with it. 16 prompts of 4096 tokens with 1 output token, one at a time, give a median TTFT of 283.6 ± 0.8 ms without this PR (2 runs) and 283.2 ± 1.9 ms with it (4 runs). At concurrency 2 to 8 the median TTFT changed by up to 120 ms between server starts of the same arm, so it is not compared here.

Accuracy: `lm_eval --model local-completions --tasks gsm8k --num_fewshot 5 --gen_kwargs "max_gen_toks=512,temperature=0.0,top_p=1.0"` with `num_concurrent=64`, on the first 400 questions or on all 1319:

| Run | Questions | strict-match | flexible-extract |
|---|---|---|---|
| Without this PR | 400 | 0.9575 ± 0.0101 | 0.9575 ± 0.0101 |
| With this PR, earlier op | 400 | 0.9625 ± 0.0095 | 0.9625 ± 0.0095 |
| With this PR | 400 | 0.9450 ± 0.0114 | 0.9475 ± 0.0112 |
| Without this PR | 1319 | 0.9477 ± 0.0061 | 0.9484 ± 0.0061 |
| With this PR | 1319 | 0.9439 ± 0.0063 | 0.9439 ± 0.0063 |

The two 400-question runs with this PR run the same kernels and differ by up to 0.0175, so differences of this size are run-to-run noise from the batching of the concurrent requests.

Startup: torch.compile takes 53.0 and 54.1 s without this PR and 31.4 and 30.9 s with it. Without this PR, vLLM compiles 50 graph pieces per compile range. The two GDN pieces that I compared have the same Inductor code and differ only in their cache key. With this PR, vLLM compiles 5 pieces per range.

Sanity: "The capital of France is", "Q: What is 17 * 23? A:", and "Write hello world in C." give coherent answers in both arms.
