# [Bugfix][XPU] Apply attn_sink in the DeepSeek-V4 sparse MLA Triton kernel

[Upstream PR](https://github.com/vllm-project/vllm/pull/64252) · state: open · merged: False

## Original PR description

- **Problem:** On XPU the DeepSeek-V4 sparse-MLA path never applied the per-head `attn_sink` (the prefill call site did not pass it and `xpu_sparse_decode_fp8()` accepted it but dropped it), unlike the NVIDIA, ROCm and CPU backends, so the softmax was silently wrong, by 105–118 % of the output for a row with 1 valid key and 0.2–0.8 % for 512–2048 keys (fp32 reference, sinks from the released V4-Flash range [-2.20, +2.49], Intel Arc Pro B70, bf16).
- **Fix:** Adds an optional `attn_sink` to `_bf16_mla_sparse_kernel` and `triton_bf16_mla_sparse_interface` (`HAS_ATTN_SINK` constexpr; the sink joins the softmax denominator and `lse` stays over the selected keys) and passes it from the V4 prefill (`xpu_sparse.py`) and decode (`xpu_sparse_decode_fp8.py`) call sites, while callers that omit it (V3.2 / GLM-5) are bitwise unchanged.
- **Validation:** On an Intel Arc Pro B60, `pytest tests/kernels/attention/test_xpu_mla_sparse.py` gives 29 passed (25 new) against 25 failed on the unpatched kernel, and deliberately breaking the kernel (missing log2(e), sink off by 0.1 nat, sink ignored) or dropping `attn_sink` at either call site makes the new tests fail, while the no-sink path is bitwise equal to `main` and kernel time is unchanged without a sink and +0.7 % to +3.7 % with one.
- **Not a duplicate:** No open PR changes the kernel or the lines this PR adds; other open PRs edit `xpu_sparse.py` in other hunks, among the sparse-MLA sources vllm-project/vllm#64065 (my own PR, which also adds a test and a CI step) and vllm-project/vllm#59019 (23 files) only change the backend file `vllm/v1/attention/backends/mla/xpu_mla_sparse.py`, and vllm-project/vllm#60666 renames `self.attn_sink` to `self.sinks`, so whichever lands second has to update the new prefill line.
