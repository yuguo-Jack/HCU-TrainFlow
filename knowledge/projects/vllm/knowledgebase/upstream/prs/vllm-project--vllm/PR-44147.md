# [Kernel] Use FlashInfer CUDA BGMV MoE Kernel for Multi-LoRA MoE dispatch

[Upstream PR](https://github.com/vllm-project/vllm/pull/44147) · state: open · merged: False

## Original PR description

Co-authored-by: Claude

## Purpose
This PR connects vLLM's MoE LoRA dispatch path to FlashInfer's BGMV MoE CUDA kernel (merged in https://github.com/flashinfer-ai/flashinfer/pull/3249). When FlashInfer with BGMV MoE support is installed, vLLM uses it via the `flashinfer.fused_moe` API. The Triton SGMV kernel remains as a fallback, selectable via environment variables.

This is the recommended integration path: kernel lives in FlashInfer, vLLM consumes it through the existing FlashInfer interface.

## Changes
* **flashinfer.py**: Add `has_flashinfer_bgmv_moe()` detection and lazy wrappers for `bgmv_moe_shrink` / `bgmv_moe_expand`
* **punica_gpu.py**:
  * Add CUDA/Triton backend selection via `VLLM_MOE_LORA_BACKEND` env vars (default: CUDA)
  * Add pre-allocated GPU buffer infrastructure (`_init_moe_bgmv_buffers`) for zero-allocation kernel calls
  * Add `add_lora_fused_moe_cuda` method that dispatches to FlashInfer's `bgmv_moe_shrink` / `bgmv_moe_expand`
  * Add cudagraph capture skip (MoE LoRA ops are not capture-safe)
  * Route `add_lora_fused_moe` between CUDA (FlashInfer) and Triton paths based on backend config
  * Add FP8->bf16 input cast in `add_lora_fused_moe` for FP8 quantized models (neither CUDA BGMV nor Triton MoE LoRA kernels support FP8 activations directly)
  * Add stream synchronization after expand to prevent race condition with shared buffer reuse across layers

## Related PRs
* https://github.com/vllm-project/vllm/pull/40670 - Original PR with kernel implementation directly in vLLM (superseded by this approach)
* https://github.com/flashinfer-ai/flashinfer/pull/3249 - FlashInfer PR with the CUDA kernel (merged)

Hi @jeejeelee and @linitra24, our CUDA BGMV MoE Kernel for Multi-LoRa MoE is targeting dispatch at small batch size (bs <= 8), so Triton's better OTPS results are expected in the shared results by @linitra24. But the problem is that when I ran E2E tests with the updated vLLM at small batch sizes, Triton's performance now exceeds that of our BGMV CUDA kernel. It is not expected and did not match the e2e test when we compared ours with Triton in the April 22nd version of vLLM. It means that our CUDA BGMV MoE kernel has lost competitiveness compared to the Triton on the updated vLLM. I have changed the VLLM_MOE_LORA_PREFILL_BACKEND and VLLM_MOE_LORA_DECODE_BACKEND default in punica_gpu.py as triton.

We need to identify the specific changes in vLLM and the Triton code that led to this shift; if the findings are significant, we should also explore whether modifying our BGMV kernel and/or code changes on the vLLM side could yield further performance improvements. I'll share the updated results if the updated code revision can achieve better results when using our CUDA BGMV kernel. (cf. There are some updates like https://github.com/flashinfer-ai/flashinfer/pull/3542 and https://github.com/flashinfer-ai/flashinfer/pull/3535 to improve our BGMV kernels.)
