# [Bugfix][MiniMax-M3] Don't emit MXFP8 from the input norm under sequence parallelism

[Upstream PR](https://github.com/vllm-project/vllm/pull/65496) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

MiniMax-M3 on NVIDIA fails at startup when MegaMoE, TP > 1 and EP are combined and `qkv_proj` takes MXFP8 input (e.g. `MiniMaxAI/MiniMax-M3.1-Flash`). With sequence parallelism (SP, #64659), the input norm output is all-gathered before attention; since #64852 that output is a `QuantizedActivation`, which the all-gather cannot take. This PR keeps the norm output in BF16 under SP and lets `qkv_proj` quantize after the gather.

## Claims

- Fixes `AttributeError: 'QuantizedActivation' object has no attribute 'contiguous'` in the profile run for TP > 1 + EP + `--moe-backend deep_gemm_mega_moe` (SP is enabled automatically in that setup).
- No change when SP is off.
- With the fix, GSM8K is 0.958 (0.964 with `VLLM_ENABLE_GEMM_RS=1`), in line with the 95.5–96.1% that #64659 reports for TP4 with and without SP.

## Validation

`MiniMaxAI/MiniMax-M3.1-Flash` on 4× B300, main at `39dbf51839`. GSM8K is the full 1319 questions, 5-shot, chat mode with thinking off.

| Setup | Code | Result | GSM8K |
|---|---|---|---:|
| TP4 + EP + MegaMoE (SP on) | main | crashes in the profile run | – |
| TP4 + EP + MegaMoE (SP on) | this PR | starts | 0.958 |
| TP4 + EP + MegaMoE (SP on), `VLLM_ENABLE_GEMM_RS=1` | this PR | starts | 0.964 |

## Details

**Root cause.** `forward_input_norm` asks the norm for MXFP8 output whenever `qkv_proj` can consume it, assuming the activation goes straight from the norm to `qkv_proj`. Under SP, `forward_after_input_norm` all-gathers it first, and `sp_all_gather` only handles tensors. `QuantizedActivation` is a dataclass holding the E4M3 data and UE8M0 scales, so the custom all-gather fails on `.contiguous()`.

**Scope.** Only the plain norm branch is reachable under SP: MegaMoE never defers its finalize (no `MoEOutput` input), and SP layers never defer the FFN all-reduce, so `fuse_input_allreduce` stays off. With SP off, the condition evaluates exactly as before. The dense MLP already handles SP this way: it all-gathers BF16 and quantizes after the gather.

**Tradeoff.** Under SP the fused norm+quant is not used. The data flow is the same as when #64659 measured SP (before #64852), with the BF16 norm now on #64852's Triton kernel. Gathering the MXFP8 data and scales instead would halve the all-gather bytes, but the 128x4 swizzled scales cannot be concatenated by rows: it needs unswizzled scales from the norm kernel and a swizzle after the gather. That is left as a follow-up.

**Duplicate check.** Searched open and closed PRs and issues for the error message, `QuantizedActivation` + all-gather, and MiniMax SP + MXFP8; no existing fix.
