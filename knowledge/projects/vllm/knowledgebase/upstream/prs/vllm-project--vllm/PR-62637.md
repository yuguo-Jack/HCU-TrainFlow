# [Bugfix][KV Connector] Drain sub-connector KV cache events in MultiConnector (fixes worker memory leak)

[Upstream PR](https://github.com/vllm-project/vllm/pull/62637) · state: open · merged: False

## Original PR description



## Overview

`MultiConnector` never forwarded `get_kv_connector_kv_cache_events()` to its sub-connectors. Worker-side KV events from `MooncakeStoreConnector` (and LMCache) were therefore never drained when it ran inside a `MultiConnector`. With KV events enabled, the Mooncake store's per-block `BlockStored` buffer grew for the life of the worker process. This PR implements the method, aggregates events per sub-connector across workers, and routes each sub-connector its own events on the scheduler side.

This resolves the TODO left in `multi_connector.py` after #31811 and #34522, both closed unmerged.

## Claims

- Fixes an unbounded host-memory leak in GPU worker processes. It triggers when `MultiConnector` contains `MooncakeStoreConnector` and `--kv-events-config '{"enable_kv_cache_events": true, ...}'` is set. For example, the common P/D setup `MultiConnector(NixlConnector, MooncakeStoreConnector)` with KV-aware routing.
- KV cache events from sub-connectors inside a `MultiConnector` now reach the scheduler and are published, the same as when those connectors run standalone.
- No change for `MultiConnector` setups whose sub-connectors do not produce KV events (all return `None`), or for single connectors.

## Validation

**Production evidence (before the fix).** Read-only heap analysis of a live prefill `Worker_DP` process (`/proc/<pid>/mem`, nothing paused):
- Setup: DeepSeek-V4.1-Flash, DP2/EP, `MultiConnector(NixlConnector, MooncakeStoreConnector)`, KV events on, block size 128.
- After 12 h of traffic, the process held:
  - one Python list of 1,377,539 `BlockStored` objects;
  - 1,377,544 lists of exactly 128 ints, which are the events' `token_ids`;
  - about 7 GiB in total.
- The worker grew with prompt tokens, about 30 GiB per pod per day. It eventually ran an 8×B300 node out of host memory, and the node hung for about 3 h.

## Details

**Root cause.** The model runner calls `kv_connector.get_kv_connector_kv_cache_events()` once per step (`kv_connector_model_runner_mixin.py` for MRV1, `gpu/kv_connector.py` for MRV2). With `MultiConnector` as the top-level connector, this hit the base-class default and returned `None`.

`MooncakeStoreConnector`'s send thread appends one `BlockStored` (with the block's `token_ids`) per stored block to `KVTransferThread.kv_events`. The only code that clears that list is `MooncakeStoreConnector.get_kv_connector_kv_cache_events()`, via `get_kv_events()`, which was therefore never called. The scheduler side (`take_events`) was already forwarded, but never received any events.

**Flow with this PR:**
1. Worker step: `MultiConnector.get_kv_connector_kv_cache_events()` calls every sub-connector, which drains its buffer. It returns `MultiKVConnectorKVEvents(events=[per-connector container or None, ...])`, or `None` if all are `None`.
2. `KVOutputAggregator.aggregate` folds workers together through a new `KVConnectorKVEvents.aggregate_worker(other)` hook. The default is the previous `add_events(other.get_all_events()); increment_workers(1)`, so existing containers behave identically. `MultiKVConnectorKVEvents` overrides it to merge per index.
3. Scheduler: `MultiConnector.update_connector_output` sets `connector_output.kv_cache_events = events[i]` for each sub-connector, exactly as it already does for `kv_connector_worker_meta`, and restores the field afterwards. Each sub-connector keeps receiving the container type it produced, so the existing `isinstance` checks in Mooncake and LMCache are unchanged.
4. `MultiConnector.take_events()` (unchanged) yields each sub-connector's events for publishing.

**Notes and tradeoffs:**
- Deployments that use `MultiConnector` with Mooncake or LMCache and KV events enabled will now publish those connectors' events (e.g. Mooncake `BlockStored` with `medium="cpu"`). Previously they were silently dropped while leaking. This matches standalone behaviour, but KV-event consumers will see new events.
- `MultiKVConnectorKVEvents.add_events` raises, because untyped events cannot be routed to a connector. Nothing calls it: the aggregator uses `aggregate_worker`.
- The per-step cost is one extra method call per sub-connector. There is no CPU/GPU sync.
