# [Bugfix][KV Offload][P2P] Fail a timed-out load at once, defer releasing its slots

## Overview

Part of #63602 (gap 2, consumer half). A timed-out P2P load now fails at the load timeout. Its destination chunks stay held until the peer confirms its WRITEs ended (AbortAck/TransferDone), or until the session ends.

This is the P2P side of the deferred-release API from **#63779** (merged). It replaces the consumer slot quarantine proposed in #61667 and supersedes #63715, whose disconnect-on-missed-AbortAck is folded in.

Three commits on main: #63715's disconnect on a missed AbortAck (`ac5c9806e6`) with its test constant fix (`0262efcc3a`), then the deferred release (`f00e9c6710`).

## Claims

- **The request falls back 5 s sooner.** A load that times out is reported failed at once, instead of after a further `_ABORT_ACK_TIMEOUT_S`: 10 s instead of 15 s for symmetric P2P, 30 s instead of 35 s for PD. The same applies to `finish()` of an in-flight load.
- **No early slot reuse.** The failed load's chunks stay out of the free pool until AbortAck, a late TransferDone, or session close. Before, the abort-ack timeout and `close()` freed them through `complete_write(False)` while the peer's WRITE might still land in them.
- **Every hold is bounded.** A missed AbortAck disconnects the peer (the folded-in #63715), and `close()` sets every held load's release.

## Details

**Root cause.** `JobResult` used to carry both the outcome and the memory release, so P2P had to pick one of two problems:
- Report late: on a load timeout, keep the job until AbortAck or `_ABORT_ACK_TIMEOUT_S`.
- Free too early: an abort-ack timeout, or `close()` on peer death, reported `success=False`. The TieringManager then freed the chunks through `complete_write(False)` with the peer's WRITE possibly still landing.

#63779 splits the two. This PR uses it.

**Lifecycle of a load in `ClientRole`:**

| event | before | after |
|---|---|---|
| load timeout / `finish()` | send AbortFetch, keep job | send AbortFetch, **report failed now** with `deferred_release=Event()`, keep load |
| AbortAck | report failed | `event.set()`, no second result |
| late TransferDone | report its result | `event.set()`, no second result (request already fell back) |
| AbortAck timeout | report failed (chunks freed) | no result; record `expired_abort_ack`, which makes the session disconnect |
| `close()` | fail every in-flight load (chunks freed) | set every held load's event; in-flight loads not yet reported fail as before |

**The release point is ack or disconnect**, as agreed in #61667 ([comment](https://github.com/vllm-project/vllm/pull/61667#issuecomment-6418290229)). Two cases remain:
- **A WRITE that is stalled but still alive when the session ends.** On the source side this is covered by #64250, which keeps unconfirmed WRITEs across teardown, and #64251, which faults a peer whose WRITE stalls. Whether NIXL teardown fences a stalled WRITE stays open on #63602.
- **Loads never sent** (still queued before ConnectAck) also fail through `close()`, without a deferred release. Nothing was posted for them.

**`drain_jobs()`** keeps polling while any held load remains. Each hold is bounded by the abort-ack timeout and then the disconnect, which meets #63779's rule that every event is set before `drain_jobs()` returns.

**Why not #61667 as is:** it re-reports the same `job_id` with `memory_safe=True`, which needs parallel quarantine tables. It also rejects `reset_cache()` with `UnsafeTransferError` and a retry loop. #63779's alternatives section covers this. Here each job has exactly one outcome, and the release carries none.

Complexity: about 110 non-test lines in `p2p/` (client 154+/−, manager +10), plus #63715's 44.
