# [Bugfix][Model] Preserve Dynamic NTK base below the trained context length

[Upstream PR](https://github.com/vllm-project/vllm/pull/62372) · state: open · merged: False

## Original PR description



## Overview

Keep the original RoPE base when Dynamic NTK is configured with a served maximum at or below the trained context length, avoiding complex caches and NaN embeddings.

Fixes #52665.

## Claims

- Clamp the length used by the Dynamic NTK base formula to `max_trained_positions`.
- Preserve the existing formula when the configured maximum exceeds the trained length.
- Add cache regressions at 512, 2048, and 4096 positions for a model trained at 2048 positions.

## Validation

The added tests compare caches at 512 and 2048 positions against ordinary RoPE and check that the 4096-position cache remains finite, bounded, and scaled.

The regression suite and lint checks have not been rerun during this PR submission session. End-to-end Nomic serving and model evaluation have not been performed in this session. Relevant command:

```bash
.venv/bin/python -m pytest tests/model_executor/layers/test_dynamic_ntk_rope.py -v
```

The new test file falls under the existing Model Executor Buildkite job (`pytest -v -s model_executor -m '(not slow_test)'`). Full CI is not triggered automatically for new PRs.

## Details

For the issue's configuration (`served=512`, `trained=2048`, `factor=2`), the current base formula raises `-0.5` to a fractional power. That creates a complex-valued cache before its real-dtype cast. Clamping the formula's length to the trained context gives the original base at and below that boundary while leaving larger lengths unchanged.

Related work: #52675 proposed the same behavior and was closed without merging. #55910 changes NTK cache allocation bounds rather than this base calculation. Open #60369 implements per-document Nomic scaling and already covers short served maxima; this patch instead changes the existing generic `DynamicNTKScalingRotaryEmbedding` class and does not implement per-document scaling. Its overlap with #60369 requires maintainer coordination before treating this as an independent fix.
