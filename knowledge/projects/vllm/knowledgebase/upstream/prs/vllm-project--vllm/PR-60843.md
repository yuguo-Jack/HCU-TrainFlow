# [Core] Add --kv-cache-host-pinned: host-pinned KV cache on integrated GPUs (GB10, Thor)

[Upstream PR](https://github.com/vllm-project/vllm/pull/60843) · state: open · merged: False

## Original PR description

## Overview

Related: #60844.

Add `--kv-cache-host-pinned` (`CacheConfig.kv_cache_host_pinned`): 

on integrated (unified-memory) GPUs such as GB10 / DGX Spark it is not possible to register buffers for zero-copy RDMA.

The switch adds the capability to back the KV cache with host-pinned memory (`cudaHostAlloc`, mapped and write-combined), so the NIXL connector can register it for RDMA (`ibv_reg_mr`) and UCX moves it zero-copy.

On 2× DGX Spark this makes the prefill→decode KV transfer **33× faster** at batch 1 (553 → 16.8 ms for 255.9 MB) and cuts TTFT by **39% / 43% / 83%** at batch 1 / 8 / 32. Gated on `current_platform.is_integrated_gpu()`, refused everywhere else.

## Claims

- On GB10 the KV cache in device memory **cannot be registered for RDMA**: no `nvidia-peermem`, `cuMemGetHandleForAddressRange(DMA_BUF)` returns `CUDA_ERROR_INVALID_VALUE` (`DMA_BUF_SUPPORTED=0`, `GPU_DIRECT_RDMA_SUPPORTED=0`), `ibv_reg_mr` fails with `EFAULT`, and ODP registers lazily but the first transfer hangs. UCX therefore stages every transfer through `cuda_copy`.
- Host-pinned memory registers with `ibv_reg_mr`, the NIC writes it at the link ceiling in a standalone probe (**109 Gbit/s**, same as stock `ib_write_bw` host-to-host), and with `cudaHostAllocWriteCombined | cudaHostAllocMapped` the GPU reads it at the **same bandwidth as `cudaMalloc`** (the default flags read 7–11% slower).
- **End to end, 2× DGX Spark, disaggregated prefill/decode with `NixlConnector`** (table below): UCX selects `rc_mlx5` **zero-copy from host memory to host memory, split 50/50 across both RoCE ports**; the KV transfer runs at ~15 GB/s (16.8 ms for 255.9 MB). TTFT drops 39% at batch 1 and 83% at batch 32, request latency drops 3% / 8% / 27% at batch 1 / 8 / 32.
- **GPU-side cost.** Reading the KV cache costs nothing (XQA decode attention 39.4 vs 39.3 µs per call in Nsight Systems), but kernels that re-read the same blocks or read-modify-write state every step are slower on host-pinned memory: on the decode worker `gdn_decode_post_conv_mtp_kernel` 37.9 → 74.6 µs and `_causal_conv1d_update` 5.7 → 8.5 µs (about +1.9 ms on a 107 ms step, +1.8%), on the prefill worker `BatchPrefillWithPagedKVCacheKernel` 1104 → 2556 µs (about +25 ms per 2048-token prefill). End to end this is the +1.5% ITL at batch 1 in the table, against ~550 ms of staging removed per request. At batch 32 ITL rises further (101.6 vs 87.0 ms) because decode runs bigger batches once prefill→decode stops being the bottleneck: 27.9 vs 17.7 requests running on the decoder on average, and decode output throughput rises from 207 to 280 tok/s (+35%).
- **Why `cudaHostAlloc` and not `cuMemCreate(HOST_NUMA)`.** An earlier revision of this PR placed the KV cache with `cuMemCreate` on the host NUMA node through the cumem pool. It registers fine, but UCX (1.23, as vendored by NIXL) classifies any VMM allocation located on the host as CUDA memory (`uct_cuda_copy_detect_vmm()` marks `HOST` / `HOST_NUMA` locations as `UCS_MEMORY_TYPE_CUDA`, hardcoded), so transfers kept going through `cuda_copy` at ~2.6 GB/s (99 ms for the same 255.9 MB). `cudaHostAlloc` memory is classified as host. NIXL also rejects any `UCX_TLS` without `cuda_copy` when GPUs are present, so there was no configuration-only way around it.
- **Not supported with sleep mode** (`ValueError` at startup): `cudaFreeHost` cannot release the memory while keeping the virtual address that the KV views and the captured CUDA graphs point to, so `wake_up` could not restore it in place.

## A race specific to zero-copy, and its fix

On the consumer, the scheduler hands the blocks of a request that just finished to the next incoming request within the same step. With the KV cache in device memory the pull is staged by UCX `cuda_copy` in 8 KB chunks (~600 ms per 256 MB), so by the time the data lands in the blocks the kernels of the step that finished the previous request (the MTP drafter runs after sampling) are long done. With a host-pinned KV cache the NIC writes the blocks within milliseconds, while those kernels are still in flight. On a hybrid model (GDN/Mamba state + MTP, QSA indexer deriving indices from KV data) this crashed the decode with an illegal memory access at concurrency 4; on the 27B it only cost a wasted draft (outputs byte-identical to the device path, see below). The scheduler-side block log shows request A finishing and releasing blocks 1-8 at 05:36:39 and request B's pull aimed at those same blocks in the same second. Commit 3caa1251bb fixes it without blocking: with `kv_cache_host_pinned` the consumer keeps a finished request's blocks (`request_finished` returns `delay_free_blocks`), hands the request id to the worker in the connector metadata, and the worker reports it in `finished_sending` once a CUDA event recorded two `start_load_kv()` calls later has completed (`Event.query()`, no waits); blocks stay allocated for about two extra steps. Validated on the hybrid model: 30/30 requests at concurrency 4 with 85 block reuses logged, versus a crash within the first 1-7 requests before. Unit test: `tests/v1/kv_connector/unit/test_nixl_deferred_release.py`.

## Details

**What changes.** A new op, `_C.alloc_host_pinned_tensor(nbytes)` (`csrc/cuda_view.cu`, next to `get_cuda_view_from_cpu_tensor`): `cudaHostAlloc(Mapped | WriteCombined)`, zeroed on the device, returned as an int8 CUDA tensor on the current device that frees itself with `cudaFreeHost`. `allocate_kv_cache(..., host_pinned=True)` uses it for the single backing allocation of the KV cache, so every layer view lives there; the V2 model runner passes `cache_config.kv_cache_host_pinned` from `init_kv_cache()` (`vllm/v1/worker/gpu/attn_utils.py`); the deprecated V1 runner is not touched, and the worker rejects the flag at startup with the V1 runner and with HiSparse (whose `init_hisparse_kv_cache()` allocates its own KV cache). Nothing else leaves device memory: only the KV cache crosses the NIC. Write-combined is safe because the CPU never reads the KV cache; the NIC reads it by DMA.

**NIXL.** With the flag on and `kv_buffer_device="cuda"`, the connector registers the KV regions as `DRAM`, which is what lets `ibv_reg_mr` succeed. `kv_buffer_device="cpu"` (host staging buffers) is a different mechanism and is left untouched.

**Scope.** `current_platform.is_integrated_gpu()` gates the flag with a `ValueError`: on parts with their own GPU memory, moving the KV cache to host memory is a regression, not a generalization. GH200/GB200 are not integrated and stay excluded. `ibv_reg_mr` of a large KV cache needs `ulimit -l unlimited` in the container.

Prefill+decode with the KV cache in device memory and prefill+decode with `--kv-cache-host-pinned` then produce identical outputs on all 6 deterministic 2k-token prompts (6/6), and the host-pinned pair repeats 6/6 across a decode restart; the pull runs zero-copy at 16.6 ms per 255.9 MB. Without that flag every placement combination diverges from every other one (0/6), including changing only the prefill's placement: the autotuner picks different FP4 GEMM tactics depending on where the KV cache lives (`cutlass 128x32x256` vs `128x64x256` in Nsight), and the resulting ~1e-3 logit differences flip greedy ties. So token-level differences between the two placements are kernel selection, not data corruption.

**A real race, now fixed in 3caa1251bb.** On a hybrid model (GDN/Mamba state + MTP, with a QSA indexer that derives indices from the KV data) the decode worker crashed with `CUDA error: an illegal memory access` on the first request after a zero-copy transfer at concurrency 4; never at concurrency 1, never with the KV cache in device memory, never on the 27B. A scheduler-side block log shows the mechanism: request A received into logical blocks 1–8, finished at 05:36:39 releasing them, and in the same second request B's pull was aimed at blocks 8, 5, 20, 19, 18, 4, 17, 16, i.e. A's blocks; the decode died right after. The NIC writes B's KV into those blocks within milliseconds while kernels of the step that finished A (the MTP drafter runs after sampling) are still in flight. With device memory the same transfer is staged by UCX `cuda_copy` in 8 KB chunks (~600 ms per 256 MB, 97k stream syncs in Nsight), which hid the race. Ruled out along the way: KV block zeroing (`new_block_ids_to_zero` is empty here), async scheduling (`--no-async-scheduling` still crashes), premature completion (the received bytes are stable 100 ms after NIXL reports done). The fix is the last form, without blocking: on the consumer with `kv_cache_host_pinned`, `request_finished` keeps the blocks and hands the request id to the worker in the connector metadata; the worker records a CUDA event two `start_load_kv()` calls later (so a drafter launched at the start of the following step is covered as well) and reports the request in `finished_sending` once `Event.query()` says the guard has completed; the scheduler frees the blocks on that output. Update since the last round:

**Rebased onto main, which now has the extensible KV cache (#56492).** The V2 model runner passes `alloc_host_pinned_tensor` to `init_kv_cache()` through the same `allocate` hook the extensible cache uses. `kv_cache_host_pinned` now resolves the extensible cache to off, and requesting both explicitly is an error, because the extensible cache reserves device memory.

**Block-lifetime fixes from review** (390c6bbb1c, 54f81e1e16):
- A request aborted while its pull was still in flight was also queued for deferred release. That gave it two completions, and either order hit `assert req_id in self.requests`; if the guard event came first, the blocks went back to the pool while the NIC was still writing. The connector scheduler now tracks D-side pulls in flight: a pull is added when the request is parked in `WAITING_FOR_REMOTE_KVS`, and removed on `finished_recving` / `failed_recving` or when the request ends. A request still receiving keeps the upstream path and is freed once, on `finished_recving`. Every other request is deferred, including an abort during decode, which can race the drafter just like a normal finish.
- With `kv_buffer_device="cpu"`, the scheduler deferred the release but the worker never reported it. The scheduler no longer defers when it uses a host buffer, and `kv_cache_host_pinned` with a CPU buffer is rejected at startup.
- New scheduler-level tests (`tests/v1/kv_connector/unit/test_nixl_deferred_release.py`) cover five cases: an abort during the pull, an abort after the pull but before scheduling, an abort during decode, a normal finish, and the CPU buffer. Each checks that the request is freed exactly once and that the scheduler ends empty. The abort and CPU-buffer tests fail before these commits. 27/27 pass together with `test_remote_prefill_lifecycle.py` and `test_remote_decode_lifecycle.py`.
- The scheduler's own `defer_block_free` is not a substitute. It was already active in the Flash-Next runs that crashed: async scheduling plus MRV2 gives `max_concurrent_batches=2` on the consumer. Those runs still hit illegal memory accesses, 10 of 30 requests completing; the guard two steps later is what closed the race (30/30).
