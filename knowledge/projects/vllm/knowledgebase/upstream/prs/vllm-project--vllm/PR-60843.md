# [Core] Add --kv-cache-host-pinned: host-pinned KV cache on integrated GPUs (GB10, Thor)

[Upstream PR](https://github.com/vllm-project/vllm/pull/60843) · state: open · merged: False

## Original PR description

## Overview

Related: #60844.

Add `--kv-cache-host-pinned` (`CacheConfig.kv_cache_host_pinned`): on integrated (unified-memory) GPUs such as GB10 / DGX Spark, allocate the KV cache in host-pinned memory through the cumem pool, so the NIXL connector can register it for RDMA (`ibv_reg_mr`), which device memory on these parts does not allow. On 2× DGX Spark this makes the prefill→decode KV transfer 6.4× faster and cuts TTFT by 35% at batch 1. Gated on `current_platform.is_integrated_gpu()`, refused everywhere else.

## Claims

- On GB10 the KV cache in device memory **cannot be registered for RDMA**: no `nvidia-peermem`, `cuMemGetHandleForAddressRange(DMA_BUF)` returns `CUDA_ERROR_INVALID_VALUE` (`DMA_BUF_SUPPORTED=0`, `GPU_DIRECT_RDMA_SUPPORTED=0`), `ibv_reg_mr` fails with `EFAULT`, and ODP registers lazily but the first transfer hangs. UCX therefore stages every transfer through `cuda_copy`.
- Host-pinned memory allocated with `cuMemCreate(CU_MEM_LOCATION_TYPE_HOST_NUMA)` registers with `ibv_reg_mr`, the NIC writes it at the link ceiling in a standalone probe (**109 Gbit/s**, same as stock `ib_write_bw` host-to-host), and the GPU reads it at the **same bandwidth as `cudaMalloc`** (166/235/235/258 vs 166/234/234/258 GB/s on 4 Sparks).
- **End to end, 2× DGX Spark, disaggregated prefill/decode with `NixlConnector`** (table below): the per-request KV transfer (255.9 MB) drops from 630 ms to 99 ms at batch 1, TTFT drops 35% (1410 → 911 ms), and output throughput rises 5–7% at batch 8/32. Same image, same nodes type, only the flag differs.
- **Not yet wire-speed zero-copy.** The transfer runs at ~2.6 GB/s, well below the 13.6 GB/s the link sustains; as reported in review, UCX's protocol selection still classifies the buffer as `cuda` and uses its emulated/staged path even though NIXL registers it as `DRAM`. Disabling UCX's memtype cache (`UCX_MEMTYPE_CACHE=n`) does not change that and is slower (154 ms). The win today is a cheaper staging path; getting UCX to treat the region as host memory is the follow-up.
- Scoped to the `kv_cache` pool: weights, activations and CUDA-graph pools keep the regular allocator. Works with sleep mode: the placement is recorded per allocation and `wake_up` recreates the memory host-pinned at the same address.

## Validation

End-to-end PD, 2× DGX Spark (GB10, driver 580.78, CUDA 13.0, ConnectX-7 RoCEv2), image built from this branch, `nvidia/Qwen3.8-27B-NVFP4`, FP8 KV cache, MTP k=3, ISL 2048 / OSL 256, aiperf closed loop (concurrency = batch), Dynamo frontend; KV transfer time from the decoder's NIXL metrics (`Avg xfer time`, mean over all requests of the point):

| 1 | device (no flag) | 630 | 1410 | 44.9 | 19.9 |
| 1 | **host-pinned** | **99** | **911** | 44.8 | **20.8** |
| 8 | device (no flag) | 995 | 2497 | 58.3 | 117.0 |
| 8 | **host-pinned** | **438** | **2081** | 56.8 | **122.6** |
| 32 | device (no flag) | 14537 | 18137 | 90.5 | 197.3 |

No request errors in any point (50/400/1600 requests). At batch 8/32 the transfer time includes queueing behind other transfers, so it is not a bandwidth figure.

Unit-level, on GB10 inside the same image:
- `tests/basic_correctness/memory/cumem/test_cumem.py::test_host_pinned_pool`: host-pinned pool → `CU_POINTER_ATTRIBUTE_MEMORY_TYPE=1` (host), device pool → `2`, GPU writes/reads and direct CPU reads correct, sleep/wake keeps the allocation host memory at the same address with its contents, pools released → 0 mapped. PASSED.
- `vllm serve <model> --kv-cache-host-pinned` with the `is_integrated_gpu()` gate: `is_integrated_gpu()` is True on GB10 (cc 12.1), the server starts (46.19 GiB of KV cache), greedy completion correct.
- The patched `cumem_allocator` extension standalone (no torch): with the switch off the allocation is device memory and `ibv_reg_mr` → `EFAULT`; with it on, host memory and `ibv_reg_mr` succeeds.
- `pre-commit` (ruff, clang-format, mypy, typos) passes.

Not validated: Thor. The gate covers it (`is_integrated_gpu()` is a property of the part, not a part number), but CUDA cannot be initialised from user jobs on the Thor nodes available to me (`cuInit` → `CUDA_ERROR_NOT_SUPPORTED`, a node-configuration issue), so nothing here is measured on Thor.

Measurement details for the registration and bandwidth claims are in #60844.

## Details

**Why not a global switch.** Only the KV cache crosses the NIC; everything else has no reason to leave device memory. The cumem pool already gives per-tag scoping (sleep mode uses it), so the change rides on that: a process-wide placement switch in `csrc/cumem_allocator.cpp` (`set_host_numa_node(device, enable)`) that makes `cuMemCreate` use `CU_MEM_LOCATION_TYPE_HOST_NUMA` on the device's host NUMA node (`CU_DEVICE_ATTRIBUTE_HOST_NUMA_ID`), with read/write access for both the device and the host and without the GPUDirect-RDMA/fabric allocation flags that only apply to device memory. `CuMemAllocator.use_memory_pool(tag, host_pinned=True)` toggles it around the pool context and records the placement on each `AllocationData`, which `wake_up` honours; `gpu_worker._host_pinned_kv_cache_pool_context` routes only the `kv_cache` tag through it when the flag is on.

**NIXL.** With the flag on and `kv_buffer_device="cuda"`, the connector registers the KV regions as `DRAM`, which is what lets `ibv_reg_mr` succeed. `kv_buffer_device="cpu"` (host staging buffers) is a different mechanism and is left untouched.

**Scope.** `current_platform.is_integrated_gpu()` gates the flag with a `ValueError`: on parts with their own GPU memory, moving the KV cache to host memory is a regression, not a generalization. GH200/GB200 are not integrated and stay excluded. `cudaHostAlloc(Default)` was measured too and reads 7–11% slower than `cudaMalloc` on GB10, which is why the cuMem/VMM path is used rather than a `cudaHostAlloc` allocator.

**Memory accounting.** On integrated GPUs `gpu_memory_utilization` already sizes from `psutil` (`mem_utils.py`), so a host-pinned KV cache is counted; the KV budget is the same with and without the flag (67.61 vs 67.80 GiB on the prefill worker, 67.05 vs 67.18 GiB on the decode worker in the runs above). `ibv_reg_mr` of a large KV cache needs `ulimit -l unlimited` in the container.

Two-node P/D (NixlConnector, `kv_buffer_device=cuda`, prefill → decode): with the flag NIXL registers the 34 GiB KV cache as DRAM (`ibv_reg_mr` succeeds, which it cannot on device memory) and transfers succeed: 329 MB for a 3004-token prompt over the RoCE port in 115 ms (2.86 GB/s); without the flag the same transfer is 177 ms (1.1 GB/s avg over 5). Outputs identical between the two modes.

One thing the trace shows, though: `UCX_PROTO_INFO=y` on the decoder prints the same protocol with and without the flag — `remote memory read by ucp_get*(multi) into cuda/GPU0 from cuda | 0..inf | software emulation | rc_mlx5/rocep1s0f0:1`. So UCX 1.22 (bundled with nixl 1.4.1) still reports the buffer as `cuda` and takes the emulated/staged path even with the DRAM registration; I did not trace why (UCX memtype detection vs. what NIXL passes), and the speed-up is plausibly cheaper staging rather than zero-copy. Until that is resolved it would be worth describing the observed protocol in the PR text, since the zero-copy path is the stated goal.

Issues:
1. `test_host_pinned_pool` fails as written on my base (ac68c3087 + the patched extension): `mapped_usage(allocator) == x.untyped_storage().nbytes()` gives 20971520 != 4194304. The caching allocator rounds the 4 MiB request to a 20 MiB segment, exactly as for a device pool; the neighbouring tests use ≥16 MiB tensors for that reason.
2. Sleep/wake drops the placement: `wake_up` re-creates allocations through `create_and_map`, which reads `g_host_numa_node` (−1 outside the pool context), so a host-pinned KV cache comes back as device memory at the same address while NIXL still holds its DRAM registration. Record the placement per allocation (handle / `AllocationData`) and honour it in `create_and_map`, or reject the flag together with sleep mode. The docstring's "independent of sleep mode" could be read as sleep-compatible; it is not yet, for this reason.
3. Gate: `is_device_capability(121)` names one part. The property that matters is "integrated GPU without GDR/dma-buf", which `current_platform.is_integrated_gpu()` already expresses and which also covers Thor-class parts; GH200 stays excluded because its GPU is not integrated. Suggest gating on that and naming GB10 in the error text as the known case.

Not run: the pytest on a full PR-base build (the final `mapped_usage == 0` assertion could not be adjudicated on my base), the ODP first-WRITE hang, and why UCX reports the HOST_NUMA allocation as cuda (not traced into UCX's memtype detection).

@gitbisector thanks, this was a very useful review: independent reproduction on a second pair, and three real issues. All three are addressed in the latest push (`9d8f7a8d77`), and the PR text now reports what the transfer actually does.

**UCX protocol / zero-copy.** You are right, and I have rewritten the claim. End to end on 2× Spark (Qwen3.8-27B-NVFP4, ISL 2048, NixlConnector, same image both arms, numbers in the PR description) the 255.9 MB KV transfer goes from 630 ms to 99 ms at batch 1 and TTFT from 1410 to 911 ms. But 99 ms is ~2.6 GB/s against a 13.6 GB/s link, consistent with your 2.86 GB/s and with UCX still taking the emulated path for a buffer it classifies as `cuda`. My first guess was UCX's memtype cache marking every `cuMemMap` range as cuda; I ran a third arm with `UCX_MEMTYPE_CACHE=n` and it is not that: same behaviour, slower (154 ms). So the PR now claims what is measured (a much cheaper transfer) and lists getting UCX to treat the region as host memory as the open follow-up, rather than claiming zero-copy.

**1. Test bookkeeping.** Fixed: the assertion is now `mapped_usage >= nbytes` (the caching allocator maps a 20 MiB segment for the 4 MiB tensor, as you found), and the pools are released with `allocator._trim` before the final `== 0`, since `empty_cache()` does not release pluggable-allocator segments (pytorch/pytorch#145168). The test passes on GB10 inside a full build of this branch.

**2. Sleep/wake.** Good catch, and a real bug. The placement is now recorded per allocation (`AllocationData.host_pinned`) and `wake_up` recreates the memory with it, so a host-pinned KV cache comes back as host memory at the same address. The test now does a `sleep(offload_tags=("kv_cache",))` + `wake_up()` round trip and checks memory type and contents; it passes on GB10.

**3. Gate.** Changed to `current_platform.is_integrated_gpu()`, as you suggested, with GB10 and Thor named in the error text. Verified on GB10 (`is_integrated_gpu()` True, `vllm serve --kv-cache-host-pinned` starts and generates correctly). I could not validate Thor: on the Thor nodes I have access to, CUDA does not initialise from user jobs at all (`cuInit` → `CUDA_ERROR_NOT_SUPPORTED`, a node-configuration issue on my side), so the PR says explicitly that Thor is covered by the gate but untested. If you have a Thor at hand, a run of `test_host_pinned_pool` there would close that.
