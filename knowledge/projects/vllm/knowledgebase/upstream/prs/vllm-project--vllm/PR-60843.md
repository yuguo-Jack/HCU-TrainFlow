# [Core] Add --kv-cache-host-pinned: host-pinned KV cache on GB10 (sm_121)

[Upstream PR](https://github.com/vllm-project/vllm/pull/60843) · state: open · merged: False

## Original PR description

## Overview

Related: #60844.

Add `--kv-cache-host-pinned` (`CacheConfig.kv_cache_host_pinned`): on GB10 / DGX Spark (sm_121, unified memory) allocate the KV cache in host-pinned memory through the cumem pool, so the NIXL connector can register it for RDMA and transfer it zero-copy instead of staging every transfer through a host bounce buffer. Accepted on sm_121 only, refused everywhere else.

## Claims

- On GB10 the KV cache in device memory **cannot be registered for RDMA**: no `nvidia-peermem`, `cuMemGetHandleForAddressRange(DMA_BUF)` returns `CUDA_ERROR_INVALID_VALUE` (`DMA_BUF_SUPPORTED=0`, `GPU_DIRECT_RDMA_SUPPORTED=0`), `ibv_reg_mr` fails with `EFAULT`, and ODP registers lazily but the first transfer hangs. UCX therefore falls back to `cuda_copy` staging, an extra pass through the same LPDDR5x that the GPU and the ConnectX-7 already share.
- Host-pinned memory has none of these problems: `ibv_reg_mr` accepts it and the NIC writes it at the link ceiling (**109 Gbit/s** between two Sparks, same as stock `ib_write_bw` host-to-host, payload verified by a GPU kernel on the receiver).
- On GB10 the GPU reads host-pinned memory allocated with `cuMemCreate(CU_MEM_LOCATION_TYPE_HOST_NUMA)` at the **same bandwidth as `cudaMalloc`** (1 GiB streaming kernels, 4 nodes: 166/235/235/258 GB/s vs 166/234/234/258 read; write 8-11% faster), so the KV cache pays nothing for living there.
- The change is scoped to the `kv_cache` pool: weights, activations and CUDA-graph pools keep the regular allocator, and it works independently of sleep mode.

## Validation

Done:
- The patched `cumem_allocator` extension built standalone on a GB10 node (driver 580.78, CUDA 13.0) and driven through `my_malloc` without torch: with the switch off the allocation is device memory (`cuPointerGetAttribute(MEMORY_TYPE)=2`, `ibv_reg_mr` → `EFAULT`); with it on it is host memory (`MEMORY_TYPE=1`), the GPU writes/reads it (`cudaMemset`/`cudaMemcpy`), the CPU dereferences it directly, and **`ibv_reg_mr` succeeds**; the switch resets after the context and the allocator bookkeeping returns to zero.
- `pre-commit` (ruff, clang-format, mypy, typos) passes.
- New unit test `tests/basic_correctness/memory/cumem/test_cumem.py::test_host_pinned_pool` (allocation through `use_memory_pool(tag="kv_cache", host_pinned=True)`, GPU compute, direct CPU read, bookkeeping).

Not done yet, which is why this is a draft:
- Running the new pytest on a GB10 with a full build.
- An end-to-end prefill/decode run over two Sparks with `NixlConnector`, comparing transfer time and confirming no staging copies with and without the flag.

Measurement details for the RDMA/bandwidth claims (registration probe, two-node RDMA WRITE with GPU-side verification, GPU bandwidth per allocation type) are in #60844.

## Details

**Why not a global switch.** Only the KV cache crosses the NIC; everything else has no reason to leave device memory. The cumem pool already gives per-tag scoping (sleep mode uses it), so the change rides on that: a process-wide placement switch in `csrc/cumem_allocator.cpp` (`set_host_numa_node(device, enable)`) that makes `cuMemCreate` use `CU_MEM_LOCATION_TYPE_HOST_NUMA` on the device's host NUMA node (`CU_DEVICE_ATTRIBUTE_HOST_NUMA_ID`), with read/write access for both the device and the host and without the GPUDirect-RDMA/fabric allocation flags that only apply to device memory. `CuMemAllocator.use_memory_pool(tag, host_pinned=True)` toggles it around the pool context; `gpu_worker._host_pinned_kv_cache_pool_context` routes only the `kv_cache` tag through it when the flag is on.

**NIXL.** With the flag on and `kv_buffer_device="cuda"`, the connector registers the KV regions as `DRAM`, so UCX takes the plain `ibv_reg_mr` path instead of looking for GPUDirect RDMA. `kv_buffer_device="cpu"` (host staging buffers) is a different mechanism and is left untouched.

**Scope.** `is_device_capability(121)` gates the flag with a `ValueError`: on parts with their own GPU memory, moving the KV cache to host memory is a regression, not a generalization, and on GB10 the memory is the same LPDDR5x either way. `cudaHostAlloc(Default)` was measured too and reads 7-11% slower than `cudaMalloc` on GB10, which is why the cuMem/VMM path is used rather than a `cudaHostAlloc` allocator.

**Limitations / open points.** The GPU-side bandwidth parity is measured, not derived; `gpu_memory_utilization` on UMA already sizes from `psutil` (`mem_utils.py`), but a host-pinned KV cache does not show up in `cudaMemGetInfo`, so that interaction deserves a look in the end-to-end run. `ibv_reg_mr` of a large KV cache needs `ulimit -l unlimited` in the container.

Thanks for this — the registration table and the P/D gain are real and reproduce on our pair. Validated on 2× DGX Spark (GB10 sm_121, driver 580.178.04, CUDA 13.0, ConnectX-7 RoCEv2 200G, nixl 1.4.1 / UCX 1.22), base ac68c3087 + this PR's Python changes and a standalone build of the patched `cumem_allocator` extension.

Confirms the registration table: `ibv_reg_mr` on `cudaMalloc` / `cuMemCreate(DEVICE)` / managed → EFAULT (ODP registers), `cudaHostAlloc` / `cuMemCreate(HOST_NUMA)` → OK with `MEMORY_TYPE=HOST`, GPU write → CPU read coherent; `ib_write_bw` host-to-host 109.25 Gb/s. Device attrs: INTEGRATED=1, GDR=0, DMA_BUF=0.

Single node (Qwen3-0.6B): KV budget identical with and without the flag (33.32 GiB) — the UMA sizing in `mem_utils.py` is psutil-based, so host-pinned memory is already counted and the `cudaMemGetInfo` concern does not apply; greedy output identical; the engine RSS shows the KV cache host-resident.

Two-node P/D (NixlConnector, `kv_buffer_device=cuda`, prefill → decode): with the flag NIXL registers the 34 GiB KV cache as DRAM (`ibv_reg_mr` succeeds, which it cannot on device memory) and transfers succeed: 329 MB for a 3004-token prompt over the RoCE port in 115 ms (2.86 GB/s); without the flag the same transfer is 177 ms (1.1 GB/s avg over 5). Outputs identical between the two modes.

One thing the trace shows, though: `UCX_PROTO_INFO=y` on the decoder prints the same protocol with and without the flag — `remote memory read by ucp_get*(multi) into cuda/GPU0 from cuda | 0..inf | software emulation | rc_mlx5/rocep1s0f0:1`. So UCX 1.22 (bundled with nixl 1.4.1) still reports the buffer as `cuda` and takes the emulated/staged path even with the DRAM registration; I did not trace why (UCX memtype detection vs. what NIXL passes), and the speed-up is plausibly cheaper staging rather than zero-copy. Until that is resolved it would be worth describing the observed protocol in the PR text, since the zero-copy path is the stated goal.

Issues:
1. `test_host_pinned_pool` fails as written on my base (ac68c3087 + the patched extension): `mapped_usage(allocator) == x.untyped_storage().nbytes()` gives 20971520 != 4194304. The caching allocator rounds the 4 MiB request to a 20 MiB segment, exactly as for a device pool; the neighbouring tests use ≥16 MiB tensors for that reason.
2. Sleep/wake drops the placement: `wake_up` re-creates allocations through `create_and_map`, which reads `g_host_numa_node` (−1 outside the pool context), so a host-pinned KV cache comes back as device memory at the same address while NIXL still holds its DRAM registration. Record the placement per allocation (handle / `AllocationData`) and honour it in `create_and_map`, or reject the flag together with sleep mode. The docstring's "independent of sleep mode" could be read as sleep-compatible; it is not yet, for this reason.
3. Gate: `is_device_capability(121)` names one part. The property that matters is "integrated GPU without GDR/dma-buf", which `current_platform.is_integrated_gpu()` already expresses and which also covers Thor-class parts; GH200 stays excluded because its GPU is not integrated. Suggest gating on that and naming GB10 in the error text as the known case.

Not run: the pytest on a full PR-base build (the final `mapped_usage == 0` assertion could not be adjudicated on my base), the ODP first-WRITE hang, and why UCX reports the HOST_NUMA allocation as cuda (not traced into UCX's memtype detection).
