# [Reload] Keep captured-graph tensors valid across reload_weights after level-2 sleep (NVFP4 MoE + MLA)

[Upstream PR](https://github.com/vllm-project/vllm/pull/61304) · state: open · merged: False

## Original PR description

## Overview

Stacked on https://github.com/vllm-project/vllm/pull/61303 (its commit is the first of the two here; review the second commit).

After `sleep(level=2)` discards the weights pool, `reload_weights` on a ModelOpt NVFP4 MoE model (GLM-5.2-NVFP4, FlashInfer TRT-LLM backend, MLA) brings the server back healthy and serving garbage: well-formed completions, wrong content. Two independent causes, fixed behind env flags so the default path is unchanged:

- `VLLM_RELOAD_KEEP_MOE_KERNEL=1`: on reload, keep the ModelOpt NVFP4 MoE kernel the CUDA graphs were captured with and copy the freshly derived quant-config tensors into the ones it references, instead of building a new kernel.
- `VLLM_LAYERWISE_RELOAD_MEASURED_TOTALS=1`: trigger a layer's layerwise processing from the element count its loaders reported during the first load, not from the declared parameter sizes, and process a ready layer only once a load for another layer arrives.

## Claims

- With both flags, after `wake_up` + `reload_weights` every parameter, buffer and derived tensor hashes identical to a fresh load. Measured on vLLM **0.20.2** (this PR is the port to `main`): 10 rounds out of 10 on 4x TP=2 GLM-5.2-NVFP4 on an 8xB300, content-verified completions; without the fixes, 0 of 10.
- Reload through the pinned Run:ai path (https://github.com/vllm-project/vllm/pull/61303): 113 s → 55 s per TP=2 pair.
- This is what makes a GPU-state snapshot (CRIU + cuda-checkpoint) of a *sleeping* server usable: a 17 GB image per TP=2 pair instead of 491 GB, with the weights refilled from one page-cached copy of the checkpoint.

## Validation

- New CPU unit test `test_layerwise_reload_measured_first_load_totals` in `tests/model_executor/model_loader/test_reload.py`: a layer whose scale loader is called twice per expert (so its loaders report 8 elements where the layer declares 6), streamed with the over-counted parameter last. With the stock trigger the layer is processed two loads early and a tensor derived in `process_weights_after_loading` stays stale (`[222, 0]`); with the measured total it is correct (`[222, 242]`). Both variants run and pass; the rest of `test_reload.py` that runs on CPU still passes (38 passed, the remaining cases need the GPU fixtures).
- `pre-commit` `ruff-check`, `ruff-format`, `typos` pass on the changed files.
- **Not yet re-run on hardware against `main`.** The 10/10 result is from the same two fixes applied to 0.20.2. Parts of the 0.20.2 patch are already upstream and were dropped from this port: #48251 (MLA `W_UV`/`W_UK_T` refreshed in place), #49489 (shared NVFP4 MoE scales writable, which also removes the need for an overlap-tolerant copy), #40390 (`replace_parameter(prefer_copy=True)`), #59158 (KV-init runtime state offloaded on sleep). I will re-run the wake+reload checksum drill on `main` as soon as I have the node again and post here; draft until then.

## Details

**Cause 1, stale derived tensors.** `ModelOptNvFp4FusedMoE._build_moe_kernel` runs on every `process_weights_after_loading`, so a reload builds a new `FusedMoEQuantConfig` and kernel. The activation gscales (`a1`/`a2`) in that config are derived at load time and are not layer parameters, so the layerwise reload's copy into kernel tensors does not cover them: the captured graphs keep pointers to the old tensors, whose memory the level-2 sleep discarded. Eager steps use the new tensors, graph replays the stale ones. The fix keeps the kernel on reload and refreshes its quant-config tensors in place (`_refresh_moe_quant_config_inplace`, per-descriptor, same shape/dtype/device required, otherwise rebind with a warning). The new kernel's `fused_experts.process_weights_after_loading(layer)` still runs so the layer's parameters are converted; the layerwise machinery then copies them back into their original storage as before.

**Cause 2, early trigger.** The layerwise reload processes a layer once `load_numel >= get_layer_size(layer)`. NVFP4 MoE scale loaders are called more than once per parameter (one call per expert per projection), and the Run:ai streamer yields tensors out of file order, so the count reaches the declared size before the last scale tensors have arrived; the layer is quantized early and the trailing loads are dropped as "Excessive loading" (the `Limitations(4)` case in `layerwise.py`). The per-call cap in `get_numel_loaded` cannot see repeated calls. `record_first_load_numel(model)` wraps every weight loader during the first `load_weights` (only when the flag is set), records the per-layer total in `LayerReloadingInfo.first_load_numel` (kept across `reset()`), and `initialize_online_processing` uses it as `load_numel_total` when reloading. As a second line of defence a ready layer is processed only when a load for another layer arrives (`PENDING_LAYERS`), flushed in `finalize_layerwise_processing`.

Both are opt-in because they have been validated on one model family and one backend; if maintainers would rather have the measured-total trigger on by default, I am happy to drop the flag.
