# [Perf][Kimi-K3] Make GEMM-AR SM margin configurable

[Upstream PR](https://github.com/vllm-project/vllm/pull/56510) · state: closed · merged: False

## Original PR description

## Purpose

Kimi-K3 fused GEMM-AR can be faster in isolation but slower during TP8 + PP2 serving. Add `VLLM_KIMI_K3_GEMM_AR_SM_MARGIN` to reduce its persistent CTA budget so concurrent kernels have room to run. The default is 0; setting it to 8 on B200 caps the grid at 140 CTAs instead of 148. Existing 2-CTA cluster rounding is preserved, invalid margins are rejected before workspace allocation, and GEMM-RS is unchanged. This limits the grid; it does not reserve specific physical SMs.

Related to #55261, but independent of its Lamport backend and crossover work. Searches found no open PR providing this SM-margin control. This PR does not change the crossover or claim that PP contention is the only source of latency. The environment-variable documentation includes the new setting through its existing `envs.py` inclusion.

## Test Result

Two nodes, 8 × B200 each; TP8, PP2, DCP1; full Kimi-K3 with DSpark 8, synthetic acceptance length 4, snapshot state recovery. Each row summarizes two 960-request runs at concurrency 96 with fixed 8192-token input and 1024-token output. Every request succeeded and produced the requested token count. These are controlled performance measurements, not a quality or real-acceptance evaluation.

| Configuration | Output tokens/s, run 1 / run 2 | Mean output tokens/s | vs. AR off | Mean TTFT (ms) | Mean TPOT (ms) |
|---|---:|---:|---:|---:|---:|
| AR off | 2266.8 / 2282.5 | 2274.7 | baseline | 6573.2 | 35.00 |
| AR on, margin 0 | 1776.1 / 1783.6 | 1779.8 | -21.8% | 9339.5 | 44.04 |
| AR on, margin 8 | 2320.3 / 2337.5 | 2328.9 | +2.4% | 6488.4 | 34.11 |

Margin 8 recovers the large regression versus margin 0 (+30.8%), but the incremental gain over disabling fusion is only +2.4%. The two AR-on configurations had identical KV cache capacity; AR off had about 0.32% more. A later two-run AR-off recheck measured 2268.6 / 2283.6 output tokens/s (mean 2276.1, +0.06% versus the initial baseline), supporting the stability of this small gain.

Isolated BF16 GEMM-AR sweeps on both nodes covered M=128 through 16000, K=1536/4224, N=7168, margins 0/8, with numerical checks against GEMM + all-reduce. Most shapes changed little; the large dense shape (M=16000, K=4224) regressed by about 4–5% with margin 8. This is why the setting remains opt-in rather than selecting a hardware-wide default.

These checks reused the test function bodies directly; the full pytest command on the complete PR checkout remains pending.

# GEMM-AR on B200 TP8 + PP2

## Scope and recommendation

Nodes 30 and 26, eight B200 GPUs per node, TP8 + PP2, DCP1. Serving uses random 8192-token input and 1024-token output, concurrency 96, 960 requests per run, two runs per configuration. DSpark uses eight speculative tokens with synthetic acceptance length four and snapshot state recovery. These are performance measurements, not model-quality or real-acceptance results.

The best completed serving configuration is GEMM-AR enabled with crossover 128 and SM margin 8. Its gain over fusion disabled is small (about 2.4%), but repeatable across the two measured runs and consistent with a later off recheck. Increasing the lower crossover to 1536 makes this workload slower. The split-exit-wait prototype recovers 26.19% throughput relative to original fusion, but is -1.26% versus fusion disabled and -3.56% versus SM margin 8. The controlled PP experiment supports the residency/wait-dependency explanation, while the complete serving comparison still favors SM margin 8 among tested configurations. A higher lower crossover, shallower operand pipeline, and fused-copy prototypes did not improve this workload.

## Completed serving comparison

| Configuration | Run 1 (output tok/s) | Run 2 (output tok/s) | Mean (output tok/s) | vs. initial AR off |
|---|---:|---:|---:|---:|
| AR off | 2266.85 | 2282.46 | 2274.66 | baseline |
| Original AR, crossover 128, margin 0 | 1776.06 | 1783.58 | 1779.82 | -21.75% |
| Original AR, crossover 128, margin 8 | 2320.25 | 2337.46 | 2328.86 | +2.38% |
| Original AR, crossover 1536, margin 0 | 1726.33 | 1731.17 | 1728.75 | -24.00% |
| AR off, later recheck | 2268.63 | 2283.61 | 2276.12 | +0.06% |

All requests succeeded with exact requested token counts. Original-kernel AR-on configurations have identical KV capacity; AR off has about 0.32% more. Loading and warmup are excluded. The pooled mean of all four off runs is approximately 2275.39 output tok/s; margin 8 is approximately 2.35% faster against that reference.

## What explains the regression?

The isolated GEMM-AR crossover is insufficient to predict serving performance. A persistent fused kernel performs computation and communication, then keeps its compute CTAs resident while waiting for cross-rank completion. With concurrent PP communication, a delayed rank can amplify waiting across the TP group. Large prefill shapes are particularly exposed: the static tile-dependency model predicts that blocked producer CTAs can prevent all resident clusters from finishing when the final cross-rank wait stays inside the compute kernel.

This is supported by a controlled experiment that leaves TP8 + PP2 unchanged and delays one PP sender by 5 ms. CUDA events verify actual overlap. The following are 50-sample median maximum-TP-rank latencies for M=16000, K=1536, N=7168; they are operator timings, not serving throughput.

| Variant | SM margin | No PP traffic (us) | Delayed PP traffic (us) |
|---|---:|---:|---:|
| Original kernel | 0 | 585.76 | 4712.06 |
| Original kernel | 8 | 585.76 | 585.76 |
| Move final wait to a lightweight kernel | 0 | 585.82 | 649.22 |
| Move final wait to a lightweight kernel | 8 | 585.76 | 585.76 |
| Wider fused wait-and-copy kernel | 0 | 612.38 | 673.79 |
| Operand pipeline capped at 2 stages | 0 | 690.24 | 5009.42 |
| Operand pipeline capped at 5 stages | 0 | 587.09 | 4701.78 |

Moving the final wait removes most of the stall without reducing the GEMM CTA cap. This is stronger evidence for a residency/wait-dependency problem than a throughput gain from changing SM margin alone. It does not prove the exact register/shared-memory/cluster admission constraint, nor is it a hardware scheduler trace. The observed effect is transient waiting, not a demonstrated permanent deadlock.

Raising the lower crossover retains the large shapes susceptible to this contention and removes fusion from smaller shapes that can benefit from it. This explains why a higher threshold can make the complete workload worse even if an isolated crossover suggests it should help.

## Three operator directions tested

| Direction | Implementation | Finding | Decision |
|---|---|---|---|
| Reduce GEMM operand pipeline depth | Caps 2, 3, 4, 5, 6, 8; PP size unchanged | Lower shared-memory use did not eliminate delayed-PP stalls; several shapes regressed in isolation | Do not select for serving |
| Release compute CTAs before final cross-rank wait | Separate 128-thread completion kernel; independent output clone preserved | Large reduction in controlled PP stall, little isolated latency change | Two serving runs complete; slower than AR off and margin 8 |
| Fuse output copy | Copy in original communication warps, separate wait+copy, and wider wait+copy grid | Initial copies were slower; wider copy reduced overhead but did not consistently beat baseline across shapes/nodes | Keep experimental |

The isolated sweep contains 352 measurements across both nodes, two SM margins, four M values, two K values, and eleven variant/stage configurations. Every prototype and pipeline cap passed numerical, output-lifetime, CUDA Graph, rank-skew and mixed-shape workspace-reuse checks. These focused checks are not the complete pytest suite or a formal memory-ordering proof.

## What can and cannot be attributed

- PP overlap is a demonstrated trigger in a controlled experiment with the same TP8 + PP2 layout. This does not establish that every PP workload regresses.
- DCP is not necessary: the regression and improvement both occur at DCP1.
- B200 is the tested hardware. There is no matched experiment on another GPU, so a B200-exclusive cause is not established.
- There is no full-model TP8 + PP1 comparison: this model does not fit in the tested single-node layout. The controlled PP probe provides the PP/no-PP comparison at operator level.
- Shared expert does not independently invoke GEMM-AR in this model path; its output joins the MoE tail reduction. Optimizing a hypothetical separate shared-expert AR would not address the serving path.
