# [Bugfix] Pin torchcodec to the CUDA-variant build matching the Docker image

[Upstream PR](https://github.com/vllm-project/vllm/pull/63133) · state: open · merged: False

## Original PR description

## Overview

Fixes #63121. `requirements/cuda.txt` left `torchcodec` unpinned (`>= 0.14`), so which CUDA-variant wheel got installed depended on the resolver's index strategy. Under pip semantics the newest release wins across indexes, so CUDA 12.x image builds could install the CUDA 13 build from PyPI, and `vllm serve` then died at import time with `OSError: libnvrtc.so.13`. This PR pins torchcodec and makes the Dockerfile's existing CUDA 12 fixup select the matching variant build.

Note: @MuonChaser mentioned in #63121 that they are investigating the Docker dependency paths. This PR is scoped to the torchcodec selection only, happy to coordinate or defer to a broader change if one is preferred.

## Claims

- CUDA 13 (default) builds resolve `torchcodec==0.17.0`, served as the `+cu130` build from the PyTorch index.
- CUDA 12 builds resolve `torchcodec==0.16.0+cu<major><minor>` (for example `+cu129`), the matching CUDA-variant build, instead of the PyPI CUDA 13 wheel.

## Validation

Resolver checks run locally against the live PyPI and PyTorch indexes (Python 3.12, x86_64):

- Old spec, pip: `pip download "torchcodec>=0.14" --extra-index-url https://download.pytorch.org/whl/cu129` selects `torchcodec-0.17.0` from PyPI. This is the reported bug.
- New CUDA 12 path, pip: `pip download "torchcodec==0.16.0+cu129" --extra-index-url https://download.pytorch.org/whl/cu129` selects `torchcodec-0.16.0+cu129-cp312-cp312-manylinux_2_27_x86_64.manylinux_2_28_x86_64.whl`.
- New CUDA 13 path, pip: `pip download "torchcodec==0.17.0" --extra-index-url https://download.pytorch.org/whl/cu130` selects `torchcodec-0.17.0+cu130`.
- The Dockerfile rewrite was simulated with `CUDA_VERSION=12.9.1` and produces exactly `torchcodec==0.16.0+cu129` in the requirements file.
- Index listings checked directly: the cu129 index tops out at torchcodec `0.16.0+cu129` (no 0.17 build exists for cu129), and the cu130 index carries `0.17.0+cu130`.

No GPU image build was run locally; the validation is at the resolver level, which is where the wrong wheel was selected. The reporter's hardware verification in #63121 already confirms `0.16.0+cu129` serves correctly in the cu129 image.

## Details

- `requirements/cuda.txt`: `torchcodec >= 0.14` becomes `torchcodec==0.17.0`, alongside the existing exact pins for torch, torchvision, and torchaudio. torchcodec declares no torch or CUDA constraint in its own metadata, so the pin is the only thing keeping the CUDA 13 line deterministic.
- `docker/Dockerfile`: both CUDA 12 fixup blocks (build stage and final stage) gain one `sed` line next to the existing `nvidia-cutlass-dsl[cu13]` and `humming-kernels[cu13]` rewrites, substituting `torchcodec==0.16.0+cu$(echo $CUDA_VERSION | cut -d. -f1,2 | tr -d '.')`. The `+cuXXX` local build only exists on the matching PyTorch index, which the install commands already pass as `--extra-index-url`, so resolution is forced to the variant build under both pip and uv semantics.
- The fault-tolerant audio import from #61090 already covers the secondary issue in #63121 (a broken optional decoder no longer takes down the server); this PR is only the packaging root cause.
- Tradeoff: the CUDA 12 branch hardcodes 0.16.0, the newest torchcodec published for CUDA 12 indexes. When a newer CUDA 12 build appears, that line needs the same bump the torch pin gets. If a future CUDA 12.x index has no 0.16.0 build, resolution fails loudly at build time rather than silently installing a CUDA 13 wheel.
