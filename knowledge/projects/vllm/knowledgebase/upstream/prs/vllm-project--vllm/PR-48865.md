# reasoning: treat no-think-block output as content, not reasoning

[Upstream PR](https://github.com/vllm-project/vllm/pull/48865) · state: open · merged: False

## Original PR description

Fixes #48863

## Problem

When `include_reasoning=False` is combined with a `json_schema` response format, `content` is `null` in the response. Introduced in v0.23.1 (#44301).

`serving.py` sets `reasoning_ended = True` when `include_reasoning=False`, which causes the structured-output grammar to enforce valid JSON from token 1 — so the model never generates a `<think>` block. That part is correct.

The bug is in `basic_parsers.py::extract_reasoning`: when neither `start_token` nor `end_token` is found in the output, the entire output is returned as **reasoning** and content as `None`:

```python
if self.end_token not in model_output:
    return model_output, None  # entire output → reasoning (wrong when no think block)
```

The caller then nulls the reasoning because `include_reasoning=False` → both fields are `None`.

## Fix

Distinguish between two no-end-token cases:

| Case | `start_token` found? | Correct classification |
|------|----------------------|------------------------|
| Grammar prevented think block entirely | No | **content** |
| Think block started but was truncated (max_tokens) | Yes | **reasoning** (existing behavior) |

```python
model_output_parts = model_output.partition(self.start_token)
start_found = bool(model_output_parts[1])
model_output = model_output_parts[2] if start_found else model_output_parts[0]

if self.end_token not in model_output:
    if not start_found:
        return None, model_output or None  # no think block → content
    return model_output, None             # incomplete think → reasoning
```

## Tests

- Updated `test_extract_reasoning_no_end_token`: no start or end token → `(None, content)`
- Added `test_extract_reasoning_start_no_end`: start token present, end absent → `(reasoning, None)` (truncated think)
- Updated `test_extract_reasoning_empty_output`: empty output with no think block → `(None, None)`
- Updated `test_malformed_tokens`: unrecognized tokens → treated as content
- Added `test_no_think_block_json_output`: regression test for the exact bug scenario

Thanks for finding this — the root cause write-up in #48863 is accurate and the `content: null` symptom reproduces exactly as described on current `main` (`3f1d409`, CPU-only, no GPU needed).

I think the condition needs to be narrower than "no start token", though, and I have measurements that I hope are useful.

### The flipped assertions are not stale

The comment this diff removes was documenting deliberate behaviour:

```python
# For models that may not generate start token,
# assume the reasoning content is always at the start.
```

That covers models whose **chat template emits the opening think token into the prompt** rather than into the generated output — most notably DeepSeek-R1. #49743 independently documents the same prompt-opened behaviour on the `count_reasoning_tokens` path.

### What breaks beyond the three edited tests

### The production failure mode

DeepSeek-R1 truncated mid-thought (`max_tokens` reached before `</think>`) emits output with neither token. Today that is reasoning; with this change it becomes `content`. When the client sent `include_reasoning=False`, the chain-of-thought is then returned **as content** — leaked to a client that explicitly opted out of it.

### Why the ambiguity can't be resolved from the string alone

"No start token and no end token" genuinely means *content* for a grammar-suppressed request and *reasoning* for a prompt-opened block. Two existing parsers show both answers are legitimate per model:

- `MiniMaxM3ReasoningParser` disambiguates by tracking `_initial_in_reasoning` (did the template open the block).
- `MistralReasoningParser` case 3.b returns content unconditionally, which is correct there because its grammar carries an optional `think?` rule.

The base class has neither signal today. What does hold in every case is request state: `include_reasoning=False` **together with** a structured-output constraint is precisely the combination that makes `OpenAIServingChat` mark reasoning as ended before generation (`serving.py`, `reasoning_ended = True`) and lets the grammar constrain the very first token, so no think block is possible.

### Alternative gating

```python
def _reasoning_suppressed(self, request) -> bool:
    if request.include_reasoning:
        return False
    return request.extract_structured_outputs() is not None

...
if self.end_token not in model_output:
    if not start_token_found and self._reasoning_suppressed(request):
        return None, model_output or None
    return model_output, None
```

Measured on the same machine: `tests/reasoning/` → **454 passed**, **zero existing assertions modified** (the pre-existing `test_cohere_command_reasoning_parser.py` collection error from the missing `cohere_melody` package is unrelated and present on `main` too). `tests/parser/` shows the same 4 pre-existing `test_harmony.py` failures with and without the change. Verified scenarios:

| scenario | reasoning | content |
|---|---|---|
| `include_reasoning=False` + `json_schema`, output `{"answer": 42}` | – | `{"answer": 42}` ✅ the reported bug |
| same via Responses API `text.format` | – | `{"answer": 42}` ✅ |
| `include_reasoning=False`, no grammar, truncated CoT | dropped | – ✅ no CoT leak |
| `include_reasoning=True` + grammar, truncated CoT | CoT | – ✅ unchanged |
| complete `<think>…</think>{json}`, reasoning suppressed | dropped | `{json}` ✅ |

It also brings the non-streaming path closer to `extract_reasoning_streaming`, which already treats output with no start token as content.
