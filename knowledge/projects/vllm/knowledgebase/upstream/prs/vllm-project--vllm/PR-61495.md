# [Bugfix] Size YaRN cos/sin cache to cover max_position

[Upstream PR](https://github.com/vllm-project/vllm/pull/61495) · state: closed · merged: False

## Original PR description



## Overview

Generic YaRN (`rope_type: "yarn"`) precomputes only `original_max_position_embeddings × factor` cos/sin rows. A model whose `max_position_embeddings` is larger than that reads past the end of the cache for positions beyond it. This PR sizes the cache to at least `max_position`.

## Claims

- Fixes out-of-bounds cos/sin cache reads for YaRN configs where `max_position_embeddings > original_max_position_embeddings × factor`.
- Leaves every existing row bit-identical and the cache size unchanged for configs where `max_position ≤ original_max_position_embeddings × factor`.

## Validation

- **New unit test** `test_yarn_cos_sin_cache_covers_max_position` in `tests/kernels/core/test_pos_encoding.py` (factor 2, original 16384, max_position 131072):
  - It **fails on main**, on the row-count assertion (32,768 rows instead of 131,072).
  - It **passes with this change**. The test also checks that the first 32,768 rows match the short cache exactly, and that the new rows follow the same YaRN frequencies.
  - The existing `test_rope_module_cache` still passes.
  - Run: `pytest tests/kernels/core/test_pos_encoding.py -k "yarn_cos_sin or module_cache"`.
- **End-to-end:** we served a Kimi-K3 DSpark draft (qwen3 layers, trained at 16k, served with YaRN factor 2 / original 16384 / `max_position_embeddings` 1,048,576) as the speculative draft for Kimi-K3 on 8×B300. The run used a vLLM 0.17.2rc1-based build carrying this patch (same two-file change).
  - 500 real requests with prompts up to 842k tokens completed with no errors.
  - Acceptance on 64k+ prompts was in line with shorter prompts (3.27 tokens/step on 64k+ vs 3.14 pooled over all 500).
  - Every rank logged a 1,048,576-row cache.
  - The draft's cache also matched the Transformers YaRN reference (`ROPE_INIT_FUNCTIONS["yarn"]`) up to position 841k, within fp32 rounding.
  - We did not run upstream `main` end-to-end with this model.

## Details

**Root cause.** `get_rope(..., max_position, ...)` passes `original_max_position_embeddings` as the class's `max_position_embeddings`, which is needed for the YaRN correction range. `_compute_cos_sin_cache` then builds `max_position_embeddings × scaling_factor` rows. Two things make this a problem:
- Since #56446, `max_model_len` is `max_position_embeddings` for YaRN, matching Transformers. Nothing ties that value to `original × factor`.
- The rotary kernels index the cache by absolute position without bounds checks.

So any config with `max_position_embeddings > original_max_position_embeddings × factor` gets out-of-bounds reads past position `original × factor`. That means garbage rotations, or an illegal memory access. A concrete case is a draft model trained at 16k that rides along with a 1M-context target: it serves with YaRN ×2 (32k rows) but sees target positions up to 1M.

**Fix.** `get_rope` passes `cache_max_position=max_position` to `YaRNScalingRotaryEmbedding`, and the cache uses `max(original × factor, cache_max_position)` rows.
- The frequencies (`_compute_inv_freq`) still depend only on `original_max_position_embeddings` and `factor`, so the extra rows are the same YaRN rotation evaluated at larger positions, which is what Transformers computes on the fly.
- `MRotaryEmbedding` borrows `_compute_cos_sin_cache`, hence the `getattr` default. Its sizing is unchanged.

**Tradeoff.** Affected configs need more cache memory: `max_position × rotary_dim × dtype bytes`, e.g. 256 MiB for 1M × 64 in fp32. The cache is shared through `get_rope`'s module cache. Configs that were already in bounds are unaffected. The DeepSeek YaRN path is out of scope; it has its own cache class.
