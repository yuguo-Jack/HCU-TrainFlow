# [Perf] Fuse the mamba align block-table gather into one Triton kernel, 7 kernels -> 1, 6x speedup on all shapes for this kernel

[Upstream PR](https://github.com/vllm-project/vllm/pull/58737) · state: closed · merged: True

## Original PR description

> [!IMPORTANT]
> **Scope: this is a kernel-level microbenchmark, not an end-to-end throughput claim.**
> The numbers below are measured on the isolated kernel, both versions in the same process. Against a multi-millisecond decode step a
> change of this size sits inside run-to-run variation (~1% on a conc=1 arm), so
> **no measurable serving throughput improvement is claimed, and none should be
> inferred.** The value is removing six of seven kernel launches on a path that is
> on the critical path at low concurrency.

## Purpose

`mamba_get_block_table_tensor`'s `"align"` branch takes the last `1 + num_speculative_blocks` block-table entries of each request:

```python
start_indices = (seq_lens - 1) // kv_cache_spec.block_size
start_indices.clamp_(min=0)
offsets = torch.arange(1 + kv_cache_spec.num_speculative_blocks, ...)
indices_to_gather = (start_indices.unsqueeze(1) + offsets).to(torch.int64)
return torch.gather(block_table, 1, indices_to_gather)
```

The arithmetic is trivial, but as PyTorch ops it is **seven kernel launches** over a `(num_reqs,)` tensor — which holds a **single element** in a one-request decode. Almost all of the cost is launch overhead rather than work.

This is a **shared utility**: `gdn_attn`, `mamba_attn`, `short_conv_attn` and `linear_attn` all call it, so the change is not specific to one model.

## Measured

On MI355X, both versions in the same process so it is like-for-like:

| num_reqs | spec blocks | kernels | us | speedup |
|---|---|---|---|---|
| **1** | **7** | **7 -> 1** | **10.81 -> 1.78** | **6.06x** |
| 1 | 3 | 7 -> 1 | 10.91 -> 1.79 | 6.11x |
| 8 | 7 | 7 -> 1 | 10.73 -> 1.82 | 5.90x |
| 64 | 7 | 7 -> 1 | 12.02 -> 1.95 | 6.16x |

The gain is **flat in batch size**, because the cost is per-launch rather than per-element.

For context on why this site was picked: in a Kimi-K3 concurrency-1 decode trace, attributing every GPU kernel back to its Python call site ranks this the **highest kernels-per-invocation** of any non-model-math site in that model — 7.0 kernels and 19.6 us per invocation. Every other call site in that model is already at or near one kernel per call.

To be explicit about scope: this is a **kernel-level claim**. Against a multi-millisecond decode step it is a fraction of a percent end-to-end, and I am not claiming a measurable throughput change.

## Correctness

**Update after review ([@ChuanLi1101](https://github.com/ChuanLi1101)):** the first version of this kernel indexed the block table as `base + req * stride(0) + start + offs`, which silently assumes a **column stride of 1**. The `torch.gather(block_table, 1, ...)` it replaces honours any layout, and since this is a shared utility a caller holding a non-contiguous view would have read the wrong blocks. The kernel now takes `block_table.stride(0)`, `block_table.stride(1)` and `seq_lens.stride(0)` explicitly, matching the existing `kimi_k3/nvidia/kda_metadata.py` helper.

Worth stating plainly: the original 48-shape sweep below **did not catch this**, because every block table it generated was contiguous. The test added in this PR closes that gap.

Verification now lives in-tree at `tests/v1/attention/test_mamba_align_block_table.py`, so CI runs it rather than it being an out-of-tree script. It pins the kernel to the pre-fusion expression over:

- **48 shape combinations** — `num_reqs` 1/2/8/64 x `block_size` 16/64/256 x `num_speculative_blocks` 0/1/3/7, bit-identical (`atol=0, rtol=0`)
- **a non-contiguous block table** (`stride(1) == 2`) — the regression test for the bug above
- **`seq_len == 0`**, the CUDA-graph padding row the previous `clamp_(min=0)` guarded, which must clamp to row 0
- **`num_reqs == 0`**, which must not launch a `(0,)` grid
- the **`"all"` / `"none"`** passthrough modes, which still return the input tensor itself rather than a copy

55 tests pass against the fixed kernel. The three non-contiguous cases **fail against the previous kernel**, so the suite catches the defect rather than merely covering the line.

The kernel keeps the same in-range assumption the existing `torch.gather` already relies on: `start + num_speculative_blocks` must lie inside the block-table row.

- #60008, GB200, Nemotron-3.5-Lightning: 4 Mamba KV-cache groups x 7 torch ops
  = **28 extra eager launches per decode step**, in a decode loop that is
  host-bound (3.7-3.8 ms of GPU work in a 5.3 ms step).

The second one is useful independent confirmation of the mechanism rather than
just the effect: that 7 is the same per-call op count this PR fuses, measured on
a different vendor and a different model from ours.

**On the relationship to #58851.** These compose rather than compete, and I want
to state that plainly in case the two land in either order:

- **#58851 reduces how many times the call happens** - it shares GDN/Mamba/KDA
  batch metadata across KV-cache groups, so the per-group duplication goes away
  (73 -> 10 CUDA API calls per `build_attn_metadata` on Mamba2 x 9 groups).
- **This PR reduces what each call costs** - the align branch of
  `mamba_get_block_table_tensor` goes from 7 launches to 1 per call.

With both, a 4-group model pays 1 group x 1 launch instead of 4 groups x 7.
Neither subsumes the other: #58851 does not change the op count inside a single
call, and this PR does not remove the per-group repetition. If #58851 merges
first I am happy to rebase on it and re-measure.

Also noting #59726 was closed in favour of this PR, so the opt-in-flag variant
of the same fusion is no longer an alternative to weigh.

This PR still covers only the first of the three causes in #60008; the
outside-CUDA-graph align kernels and the block-boundary prefill split are
untouched here.
