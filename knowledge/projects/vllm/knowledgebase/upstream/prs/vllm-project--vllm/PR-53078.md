# [Bugfix][KV Connector] Mooncake: heterogeneous-TP support for hybrid GDN/Mamba models

[Upstream PR](https://github.com/vllm-project/vllm/pull/53078) · state: open · merged: False

## Original PR description

### What

Fix `MooncakeConnector` for **heterogeneous-TP** disaggregated prefill/decode (e.g. PP2TP2 prefill → TP4 decode) on **hybrid GDN/Mamba + full-attention** models (Qwen3.5 / Qwen3-Next family).

Without these changes, het-TP transfer on hybrid models either fails region validation or silently corrupts the mamba/GDN state on the consumer side.

### Changes

1. **Register every mamba state with its real, unpadded byte length** (`register_kv_caches`). The block page packs conv + ssm states contiguously before padding; registering the padded page length lets the TP-ratio slice cut across padding and misalign states. Each state now registers as its own region with its true payload size.

2. **Split the GDN conv state into per-sub-projection regions** (Q/K/V), reusing `derive_mamba_conv_split` from the NIXL path. Under the DS (dim, state_len) layout each sub-projection is contiguous and shards across TP independently; treating the conv page as one region lets the het-TP byte-split cut across the Q/K/V boundary and scrambles the state (consumer ranks receive Q-segment bytes in K position, etc.). Because the conv state only influences the first `kernel-1` decoded tokens, the corruption shows up as a moderate accuracy drop with occasional empty generations rather than a hard failure. Falls back to a single conv region under the SD layout (homogeneous-TP whole-region copies are unaffected by layout).

3. **Whole-region copy when the consumer TP exceeds the KV-head count** (`consumer_kv_replicated`). With 2 KV heads and consumer TP4, each consumer rank replicates its head group's region rather than slicing the producer's region; the generic ratio slicing would otherwise deliver only half the heads to each consumer rank.

4. **Tolerate peer-PP-stage layers** in `_get_transfer_regions`: remote layers from another PP stage are absent from the local spec table, so use `.get()` (their split flag is unused — region alignment only matches locally registered layers).

5. **Group-aware per-region length validation** in `_validate_asymmetric_region_lengths`: attention regions follow the replicated-consumer rule while mamba/GDN regions keep the TP-ratio rule.

6. **Scope producer-side KV replication per KV group** (reported by @z-zanez on
   Falcon-H1 P TP4 → D TP2). Producer replication used to be a single
   engine-wide flag derived from the attention KV-head count, so on a hybrid
   model whose mamba head count still exceeds the producer TP size (Falcon-H1:
   2 attention KV heads, 24 mamba heads) only producer ranks 0/2 sent their
   whole mamba regions and the consumer silently lost half the mamba state.
   Replication is now computed per region's group: attention groups replicate
   when TP > KV-head count; mamba/GDN groups always shard by head count.

### Tests

- `test_register_kv_caches_splits_gdn_conv_sub_projections`: DS layout registers Q/K/V/ssm as separate regions with correct offsets and real byte lengths.
- `test_gdn_conv_sub_projection_regions_align_across_het_tp`: P TP2 → D TP4 per-region transfer plan keeps every slice inside its sub-projection.
- Existing hybrid-mamba cases updated (per-state registration, replicated consumer KV, PP peer layers) — the module's 12 tests pass.

### Notes

- Homogeneous-TP paths (e.g. TP4→TP4) need change 1 too when the Mamba page sits inside a larger packed block, as in Qwen3.8-Flash-Next, which packs every layer of a block id into one row. On `main` such a view registers as one region whose copy length is the whole row stride, so a copy that starts at the page's offset runs into the next block id, which another request may own. Otherwise per-region copies degenerate to whole-region copies.
- Heterogeneous-TP GDN requires `VLLM_SSM_CONV_STATE_LAYOUT=DS`, the same requirement as the NIXL connector.

- lucifer1004 · comment · 2026-10-01T08:25:58Z · [source](https://github.com/vllm-project/vllm/pull/53078#issuecomment-5927659446)

Thanks for the review. I've reworked the PR in this direction (54b451fbf6, plus follow-ups from end-to-end runs):

- **Attention follows the plain-model rules in hybrid models too.** Each region now takes its layer's `(producer_cache_replicated, total_num_kv_heads)` rule, and attention regions get the same one plain models use. `main`'s head mapping (#52516) therefore covers replicated consumers, and the separate `consumer_kv_replicated` path is gone. `_compute_sender_transfer_plan` and `_validate_asymmetric_region_lengths` are back to `main`'s versions, and the handshake validates each rule's regions separately.
- **Mamba/GDN sharding stays separate.** States shard by the TP ratio, or are copied whole when the spec is `tp_replicated`. Region construction keeps NIXL's conv sub-projection split (`derive_mamba_conv_split`).
- **DS layout requirement, as in NIXL.** Heterogeneous TP with sharded Mamba/GDN state is now rejected at handshake unless `VLLM_SSM_CONV_STATE_LAYOUT=DS`, instead of silently falling back to one conv region. Homogeneous TP copies whole states and still accepts SD.
- **Two fixes that came up while merging #57952.**
  - Packed rows shared by several groups carry `group_index == -1`, and the old `group_specs[group_index]` lookup read the last group for them. They now follow the attention rule.
  - Adjacent regions coalesce only when every region's rule copies it whole. Otherwise a layer's conv and ssm regions merge whenever the attention KV is replicated, and the ratio split then cuts across their boundary.

- **Fixes that came up in end-to-end runs.**
  - The rule is read from each layer's own spec (c27a59d93a). A group's spec can wrap its layers in `UniformTypeKVCacheSpecs`, as every group of Qwen3.8 does, so a group-level `MambaSpec` check matched nothing.
  - Under DS, only sharded conv states split into sub-projections (0fe09d16ad). A TP-replicated short conv, such as Qwen3.8's per-layer embedding cache, stays one region; the split helper does not support it.
  - In hybrid models, an MLA cache, or an attention cache whose head count does not follow the KV-head sharding (e.g. a single-head indexer key ring), is copied whole (aea531b1cf). Plain models keep `main`'s rule.

Validation:
- All Mooncake connector unit tests pass (484), including new ones for the per-layer rule, the DS requirement, the coalescing guard and the replicated conv state.
- Qwen3.8-27B-FP8 (GDN + full attention, 4 KV heads), P TP1 -> D TP2 over Mooncake/RDMA, DS layout, on RTX PRO 6000: 200-question 5-shot chat GSM8K at 32 concurrent requests scores 0.980, with no degenerate outputs; the same questions sent directly to the decode engine score 0.975.
- Qwen3.8-Flash-Next, P TP2 -> D TP2: 0.985 on the same check.
- Not covered: Qwen3.8-Flash-Next at P TP1 -> D TP2. Its attention registers as packed rows (#57952), and the TP1 and TP2 rows have different layouts. The handshake rejects the pair, and NIXL rejects the same case in `_validate_csa_linear_tp_layout`.

Independent reproduction on the released v0.30.0, plus a note on how quietly it fails.

I hit this on `v0.30.0` (PyPI wheel, unmodified) while benchmarking PD-disaggregation and want to add a data point from the user side, since #53078 is still open and the fix is not in any release yet.

**TL;DR**: on a released vLLM, heterogeneous-TP PD on a hybrid GDN model does not merely lose accuracy — it returns a single token repeated, identically for every prompt, with a *normal* HTTP status, *normal* token counts, and *better* latency than the correct configuration. 408/408 requests in one benchmark cell were degenerate and every automated check we had passed them.

| P | D | direct to P | direct to D | through PD proxy |

## What the degenerate output looks like

Every response is the token `duct` repeated to the length limit — byte-identical across Chinese, English and arithmetic prompts, i.e. the prompt contributes nothing:

```
'ductductductductductductductduct...'   # len 2048, identical for all 408 requests
```

## Why this is worse than an accuracy drop

This is the part I think is worth adding to the discussion. The failure is invisible to everything except reading the text. From our benchmark records, comparing the corrupted cell against two healthy cells **in the same run, same prompts, same client**:

| | `replica5` (healthy) | `pd4p1d` (healthy) | `pd1p1d-tp4` (**100% degenerate**) |
|---|---|---|---|
| `http_status` | 200 | 200 | 200 |
| `finish_reason` | `length` ×10 | `length` ×10 | `length` ×10 |
| `prompt_tokens` | {2057, 2058, 2060} | {2057, 2058, 2060} | {2057, 2058, 2060} |
| `completion_tokens` | **512** (all) | **512** (all) | **512** (all) |
| TTFT p50, 2K prompt | 804.8 ms | 853.9 ms | **298.4 ms** |
| TTFT p50, 32K prompt | 13308.7 ms | 13514.3 ms | **3869.5 ms** |
| output tok/s, 32K | 8.10 | 8.00 | **20.35** |

The token accounting is byte-identical to the healthy cells. The connector reports no problem at all:

```
KV Transfer metrics: Num successful transfers=16, Avg xfer time (ms)=54.58,
  ..., Num failed transfers=0, Num failed recvs=0, Num KV expired reqs=0
External prefix cache hit rate: 100.0%
```

No warning or error is emitted on the transfer path for the whole run. (The one `ERROR` in our log is `EngineDeadError` during SIGTERM teardown after the run finished, not a runtime failure.)

Note also that the connector **announces het-TP safety** while doing this:

```
[mooncake_connector.py:523] MooncakeConnector setting KV cache layout to LBHNC
  for heterogeneous TP-safe KV transfer.
```

The practical consequence: the corrupted configuration looks like the **best** result in the benchmark — 65–71% lower TTFT, 2.5× the output throughput. We published exactly that as a headline finding before noticing the text was garbage. Anyone doing PD capacity planning on a hybrid model with a released vLLM can silently produce numbers that are not just wrong but *attractively* wrong.

## Code path on 0.30.0

For completeness, on `v0.30.0` three sites disable het-TP head handling whenever the model has Mamba/GDN layers, which for this model is always true:

- `mooncake_connector.py:2146` — `_validate_head_resharding_layout` returns `None` (i.e. "no error") immediately for `use_mla or has_mamba_layers`, so the layout guard never runs.
- `mooncake_connector.py:1280` and `:2207` — `total_num_kv_heads` is passed as `None` under the same condition, into `_validate_asymmetric_region_lengths` and the sender transfer plan respectively, so `_compute_sender_transfer_plan` skips its head-aware branch and falls back to plain `tp_ratio` byte-offset arithmetic.

None of #53078's markers (`derive_mamba_conv_split`, `consumer_kv_replicated`, `region_shared_groups`, `region_row_offsets`) are present in 0.30.0's Mooncake connector, though `derive_mamba_conv_split` does exist and is used on the NIXL path (`nixl/base_worker.py:506`).

## Suggestion, independent of this PR

Whatever the final shape of the fix, it would help a lot if an unsupported het-TP + hybrid combination **refused to start** (or at minimum logged a loud warning) instead of transferring silently. Right now `_validate_head_resharding_layout` returns "no error" for precisely the model class that cannot be re-sharded correctly, so the one guard that could have caught this is disabled exactly where it is needed. A startup-time rejection would have saved us a day of benchmarking and a wrong published result, and it does not depend on the re-sharding work landing first.

Happy to re-run any of the above on this branch if it would help unblock the PR — we have the hardware and the harness set up. Just say which topologies you want covered.
