# [Bugfix] Honor code_revision in config-based tokenizer loading

[Upstream PR](https://github.com/vllm-project/vllm/pull/61611) · state: closed · merged: True

## Original PR description

## Overview

Honor `ModelConfig.code_revision` in both config-based tokenizer helpers when the model and tokenizer share a repository. Complements #61272, which fixed snapshot resolution for direct tokenizer loading.

## Claims

- Config-based loading no longer silently ignores an independently pinned tokenizer code revision.
- A separately configured tokenizer does not inherit an unrelated model commit.
- Explicit caller overrides, including `code_revision=None`, remain authoritative.

## Details

Both `tokenizer_args_from_config` and `cached_tokenizer_from_config` omitted the model's code revision. They now use `setdefault` and the same model/tokenizer repository equality guard already used by the processor chat-template path. This avoids applying a model commit to an independently configured tokenizer repository. The skip-tokenizer-init early return is unchanged.

- `vllm/tokenizers/registry.py`: guarded code-revision propagation in both wrappers.
- `tests/tokenizers_/test_basic.py`: real remote-code loading regressions for both helpers, separate repositories and explicit overrides; real Mistral config-loading regressions; accept equivalent offline errors in the existing negative test.
- `tests/tokenizers_/test_registry.py`: complete the existing config fixture and regress Mistral argument filtering, minimal configs, HF-backed aliases and explicit overrides.

File: `vllm/tokenizers/registry.py` · line None

🔴 Mistral-format models (`tokenizer_mode` "mistral" or auto-detected) may now fail to load their tokenizer at startup with a ValueError. On the base branch they load. `setdefault` always adds a `code_revision` key, even when its value is None. That key reaches `MistralTokenizer.from_pretrained`, which forwards `**kwargs` unchanged to `MistralCommonBackend.from_pretrained`, and that function rejects kwargs it does not recognize. Fix: forward `code_revision` only to HF-backed tokenizer classes. One way is to drop the key in `resolve_tokenizer_args` when the resolved mode is not "hf", which covers both helpers (registry.py:183 and :294).

<details>
<summary>Why this was flagged</summary>

Trigger: any model served with `tokenizer_mode="mistral"`, or with "auto" where `is_mistral_model_repo` detects tekken.json. It enters through `renderer_from_config` (vllm/renderers/registry.py:86), which calls `cached_tokenizer_from_config`. At registry.py:294-299 kwargs now always gets `code_revision` (None in the default case). `resolve_tokenizer_args` only reads that key in the hf branch (registry.py:168) and leaves it in kwargs for the mistral mode. `get_tokenizer` then calls `MistralTokenizer.from_pretrained(..., code_revision=None)`, and vllm/tokenizers/mistral.py:219-226 passes `**kwargs` straight into `MistralCommonBackend.from_pretrained`. tests/models/multimodal/processing/test_transformers_audio.py:66 already records that this function "rejects the kwargs vLLM passes". The result is a ValueError during tokenizer init, so Mistral model startup can fail. On the base branch the key was never added and these models loaded. User-registered plugin tokenizers whose `from_pretrained` lacks `**kwargs` are exposed the same way.

**Verification:** At registry.py:294-299 the new code always runs `kwargs.setdefault("code_revision", ...)`, so the key is in kwargs even when its value is None. `MistralTokenizer.from_pretrained` (vllm/tokenizers/mistral.py:210-226) passes `**kwargs` straight to `MistralCommonBackend.from_pretrained`, which raises ValueError for kwargs not on its allow-list, and `code_revision` is not on it. On the base branch this works.

</details>
