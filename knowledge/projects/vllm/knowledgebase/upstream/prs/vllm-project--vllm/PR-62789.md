# [Bugfix][Frontend] Mark background Responses failed when generation raises

[Upstream PR](https://github.com/vllm-project/vllm/pull/62789) · state: open · merged: False

## Original PR description

## Overview

A non-streaming background `/v1/responses` request whose generation raises stays `"queued"` forever. `_run_background_request` only marks the stored response `"failed"` when `responses_full_generator` returns an `ErrorResponse`. Exceptions from the engine generator propagate instead, for example `VLLMValidationError` for `top_logprobs` above `--max-logprobs`, or `GenerationError` for `finish_reason="error"`. Nothing awaits the background task, so the error is dropped, and clients polling `GET /v1/responses/{id}` never see a terminal status. This catches the exception, logs it, and marks the response `"failed"`.

## Claims

- A background request whose generation raises now ends with `status="failed"` instead of `"queued"`.
- The exception is logged with its traceback rather than lost in an unawaited task.
- No change for successful requests, `ErrorResponse` returns, or cancelled responses (`"completed"`/`"cancelled"` are still preserved).

## Validation

Real server on `34ac4f96a3` (Qwen3-0.6B, RTX 4090, `--enforce-eager`, `VLLM_ENABLE_RESPONSES_API_STORE=1`, default `--max-logprobs 20`). Request: `{"input": "Say hi.", "max_output_tokens": 8, "top_logprobs": 50, "include": ["message.output_text.logprobs"]}`.

| Build | Foreground | Background `POST` | Background `GET` after 5s |
|---|---|---|---|
| `main` | HTTP 400 `Requested sample logprobs of 50, which is greater than max allowed: 20` | 200 `queued` | 200 `queued` (never changes) |
| this PR | same | 200 `queued` | 200 `failed` |

Tests:

- New `tests/entrypoints/openai/responses/test_serving_responses.py::test_background_request_fails_when_generation_raises`. It fails on `main` with the escaped `VLLMValidationError` and passes with this PR.
- `pytest tests/entrypoints/openai/responses/test_serving_responses.py`: 67 passed, 1 xfailed.
- `pre-commit run --files <changed files>`: all hooks pass.

## Details

This PR only touches the non-streaming background path. The streaming background path (`_run_background_request_stream`) has a related hang on producer errors, which #49721 addresses, so I left it alone to avoid conflicts.

Not a duplicate: I found no issue or PR for this (searched "responses background", "background response failed", "_run_background_request"). #49721 changes the streaming background consumer. #38190 (draft) wraps `create_responses` to return a `response.failed` event, but does not touch the background task. #62549 is about streaming retrieval with no stored events.
