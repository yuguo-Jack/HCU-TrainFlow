# [Bugfix][Tool Parser] Don't stream numbers in pythonic tool calls before they're complete

[Upstream PR](https://github.com/vllm-project/vllm/pull/61394) · state: open · merged: False

## Original PR description

## Overview

Fixes #61393

The pythonic tool parsers could stream a number before it was done, like sending `37.` as `37.0`, and then tack the rest on, so `37.7749` came out as `37.0749`. Now `make_valid_python` waits while the text ends in a number, so numbers go out once they're complete.

## Claims

- streamed args in `pythonic`, `llama4_pythonic`, `olmo3` and `lfm2` now match non-streaming for decimals, negatives and exponents
- non-streaming doesn't change, and strings and other arg types stream the same as before

## Validation

I added a case to each of the four parser test files: a call with a URL, then one with `lat=37.7749, lon=-122.4194, scale=1.5e3, eps=5e-3`, streaming and non-streaming. On main the 4 streaming cases fail. With this PR all 8 pass, along with the rest of those files, `test_utils.py` and the olmo3 reasoning tests (302 total). pre-commit is clean.

```
pytest -n 2 tests/tool_parsers/test_pythonic_tool_parser.py tests/tool_parsers/test_llama4_pythonic_tool_parser.py tests/tool_parsers/test_olmo3_tool_parser.py tests/tool_parsers/test_lfm2_tool_parser.py tests/tool_parsers/test_utils.py tests/reasoning/test_olmo3_reasoning_parser.py
```

I also ran a real server (Llama-3.2-1B-Instruct, `--tool-call-parser pythonic`) with prompts that fetch a URL and then look up coordinates. On main, streaming gave `{"lat": 37.0749, "lon": -122.0194}` and `{"lat": 40.0128, ...}`. With this PR both modes match.

Outside the tests I checked a bunch more number shapes (`0.5`, `.5`, `10.`, `1e5`, `2.5e-3`, `1.5E+10`, `-3.0e2`, `0x1F`, `1_000`, ints, floats in lists and dicts), split by real tokens and one char at a time. All match now.

## Details

A number that's still coming in can parse as a different value: `37.` is `37.0`, and `1.5` becomes `1500.0` once `e3` shows up. Once something's sent it can't be taken back, since `compute_tool_delta` only appends. So the fix just holds the number until whatever comes after it arrives (`,`, `)` and so on). Numbers inside strings aren't touched.

#56846, #51649 and #44777 also change these parsers, but none of them fix this. I merged #56846 onto main and it still reproduced.
