# [Bugfix] Fix illegal memory access when MTP/DFlash/DSpark drafts run past their max_position_embeddings

[Upstream PR](https://github.com/vllm-project/vllm/pull/63432) · state: open · merged: False

## Original PR description

## Overview

With an MTP draft whose config nests the text model under `text_config` (Qwen4Exp, Qwen3.5), and a target served past the checkpoint's `max_position_embeddings`, the engine dies with `CUDA error: an illegal memory access` once a request passes that position. In the issue the target is extended with YaRN through `--hf-overrides` (1,048,576 vs 262,144). The drafter's RoPE cache is sized from the draft config, which keeps 262,144, but the drafter is fed the target's positions.

#63251 already raises a draft's `max_position_embeddings` to the target's `max_model_len` for every method except `draft_model`. When it can't do that safely, it lowers `max_model_len` to the draft's on the V2 model runner. Both checks read the draft's top-level `hf_config`, though. For nested configs, `max_position_embeddings` and `rope_parameters` live in `hf_text_config`, so neither check fires. This PR points both at `hf_text_config`.

Fixes #62383

Compared with #62409, this fix:

- Leaves the target's YaRN RoPE unchanged. That PR feeds its larger size into YaRN, so in the issue's setup 9 of the target's 32 `inv_freq` values move away from the transformers reference. Its cache also grows 4x, to 4,194,304 rows, and the KV cache drops from 11,668,007 to 11,617,509 tokens.
- Reuses the existing draft override from #48894 and #63251 instead of adding a separate M-RoPE path.
- Adds a test that fails on the old code and passes with the fix. That PR adds no test.

## Claims

- No more engine crash when an MTP draft with a nested `text_config` gets positions past its checkpoint's `max_position_embeddings` and the target serves a longer window.
- For nested drafts whose RoPE type can't be resized safely, the V2 model runner now limits `max_model_len` to the draft's, as #63251 already does for flat configs.
- Drafts with text-only configs (EAGLE/EAGLE3, DFlash, DSpark, flat MTP) behave as on `main`: for them `hf_text_config` is the same object as `hf_config`.
- One new CPU config test covers the nested MTP path.

### Current `main` (after #63251), config level

With `Qwen/Qwen3.5-0.8B` as the target, `--hf-overrides '{"text_config": {"max_position_embeddings": 524288}}'` and `method="mtp"`, the MTP draft on `main` ends up with:

- top-level `hf_config.max_position_embeddings`: `None`, so the override returns early;
- `hf_text_config.max_position_embeddings`: still `262144`;
- `draft_shares_target_positions()`: `True`, because the top-level config has no `rope_parameters`, so `VllmConfig` does not lower `max_model_len` either.

The target keeps `max_model_len` 524,288 while the drafter's rotary cache has 262,144 rows, which is the crash above.

## Details

Root cause:

- The MTP draft `ModelConfig` is built from the checkpoint. Dict `--hf-overrides` are not applied to drafts, by design (`compose_draft_hf_overrides`). So the target gets YaRN x4 with a 1,048,576-row cache, and the drafter keeps plain M-RoPE with `max_position_embeddings` 262,144 and a 262,144-row cache.
- The speculator clamps draft positions only to the target's `max_model_len - 1`. Past position 262,143, the drafter's `cos_sin_cache` gather goes out of bounds. The error shows up later, at `copy_event.synchronize()`.
- To find it, we added syncs around the draft prefill. The sync before it passed and the sync after it failed, with draft positions up to 262,427 and 262,144 draft RoPE rows. When only the draft's size was raised, both requests passed.
- `_maybe_override_draft_max_position_embeddings` (#48894, extended to every method except `draft_model` in #63251) and `draft_shares_target_positions()` (#63251) both get `draft_model_config.hf_config`. For nested configs (Qwen4Exp, Qwen3.5), the values the RoPE reads are in `hf_text_config`.
- Before #59853, every M-RoPE cache had 4x headroom, which hid this. We read this from that diff and did not run the older code.

Change (`vllm/config/speculative.py`, two lines):

- `_maybe_override_draft_max_position_embeddings` now gets `hf_text_config`.
- `draft_shares_target_positions()` checks the RoPE types of `hf_text_config`. Without this, a nested draft with a RoPE type that can't be resized (e.g. YaRN) would be reported as sharing the target's positions and would skip the `max_model_len` limit.
- For text-only configs `hf_text_config` is the same object as `hf_config`, so those drafts see no change.

Limitations:

- The draft keeps plain M-RoPE while the target uses YaRN, because dict overrides are not forwarded to drafts. This affects acceptance rate, not memory safety. See the numbers above.
- Independent `draft_model` drafts are not touched by this PR.
- With `VLLM_ALLOW_LONG_MAX_MODEL_LEN=1` and no RoPE scaling, the target's own RoPE cache is still too short. We saw this by reading the code only, and it is not the reported bug.
