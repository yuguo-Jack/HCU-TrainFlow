# [Bugfix] Flush DeepSeek V3.1 tool arguments that do not end in a string

[Upstream PR](https://github.com/vllm-project/vllm/pull/58806) · state: open · merged: False

## Original PR description

Related: #48342

## Purpose

When the tail of the tool arguments arrives in the same streamed delta as `<｜tool▁call▁end｜>`, the close branch of `DeepSeekV31ToolParser.extract_tool_calls_streaming` rebuilds the unstreamed tail from `delta_text` and assumes the arguments end in `"}`:

```python
if '"}' not in delta_text:
    return None
end_loc = delta_text.rindex('"}')
diff = delta_text[:end_loc] + '"}'
```

Tails such as `2}`, `2]}` and `1}}` contain no `"}`, so the branch returns None and the client never receives them, and the same happens to a lone `}` whose closing quote arrived one delta earlier. A `"}}` tail is cut at the inner `"}`, which drops the outer brace. Streaming then disagrees with `extract_tool_calls` on the same text:

| Argument deltas (the last one shares a delta with the end token) | Streamed before | Streamed after |
| --- | --- | --- |
| `{"city": "Tok` / `yo"}` | `{"city": "Tokyo"}` | `{"city": "Tokyo"}` |
| `{"city": "NYC` / `"` / `}` | `{"city": "NYC"` | `{"city": "NYC"}` |
| `{"count": 4` / `2}` | `{"count": 4` | `{"count": 42}` |
| `{"xs": [1,` / `2]}` | `{"xs": [1,` | `{"xs": [1,2]}` |
| `{"o": {"b":` / `1}}` | `{"o": {"b":` | `{"o": {"b":1}}` |
| `{"o": {"b": "x` / `"}}` | `{"o": {"b": "x"}` | `{"o": {"b": "x"}}` |

The fix reads the finished arguments out of the tool call text with the existing `stream_tool_call_portion_regex` and sends only what is not yet in `streamed_args_for_tool`. The incremental branch above already keeps that record, so the flush no longer has to guess the closing characters. #48343 makes the same change to the DeepSeek V3 parser, and this PR keeps the V3.1 close branch in line with it. The dead `diff is str` comparison in the same block goes away too: it compared a string with the `str` type, so it was always False.

## Why this is not duplicating an existing PR

- #48342 / #48343 report and fix this bug in the DeepSeek V3 parser (`deepseekv3_tool_parser.py`). #48343 says it left V3.1 alone because #38866 was reworking that parser.
- #38866 (by @pascal9585) found the quote-apart case for V3.1. It moved the cut in `delta_text` from the last `"}` to the last `}`, and used the whole delta minus trailing newlines and backticks when there was no `}`. The gemini-code-assist review on it suggested replacing that manual cut with the regex the parser already uses elsewhere, which is what this PR does. The stale bot closed it on 2026-08-02 without a human review. This PR supersedes it: the quote-apart case is one of the test cases here, and the flush no longer reads the tail from `delta_text` at all. Credit to @pascal9585 for the quote-apart case.
- Other open PRs that touch this file do not change the flush: #48636 (a whole tool call in one delta), #55565 (incremental delimiter counting), #55473 (regex timeouts).
- The parser engine PRs, such as #53739 and the #51577 migration, do not cover V3.1. On main, `deepseek_v31` still maps to the legacy parser class.

## Test Plan

The test goes into the existing `tests/tool_parsers/test_deepseekv31_tool_parser.py` and reuses `run_tool_extraction_streaming` / `run_tool_extraction_nonstreaming` from `tests/tool_parsers/utils.py`. One parametrized test feeds six argument shapes through the streaming parser with the tail and `<｜tool▁call▁end｜>` in one delta, then compares the streamed name and arguments with `extract_tool_calls` on the joined text. The string case is the control that already passes on main.

```

```
