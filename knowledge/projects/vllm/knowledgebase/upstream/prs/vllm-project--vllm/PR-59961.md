# [Bugfix][DSv3.2] Carry the shared indexer top-k across pipeline stages

[Upstream PR](https://github.com/vllm-project/vllm/pull/59961) · state: closed · merged: True

## Original PR description



## Overview

Fix a GSM8K accuracy loss on GLM-5.x / DeepSeek-V3.2-style models under pipeline parallelism. These models reuse the previous layer's indexer top-k, and when a PP stage starts on a reusing layer, that stage read a stale top-k. This PR sends the top-k along with the intermediate tensors, using shared helpers that also fix HY-V4 and reject the unsupported MiniMax-M3 AMD case.

## Claims

- GLM-5.3-NVFP4 PP2 × TP2 on main: GSM8K 0.879 → 0.908. Before the fix, stage 1's first three layers attend with the previous step's top-k.
- With gather-based DCP (#59916), where it was more visible: 0.820 → 0.908.
- When any later stage starts on a top-k-reusing layer, every stage boundary also sends `(num_tokens, index_topk)` int32 per step. Other models and partitions are unchanged.

## Validation

GSM8K (5-shot, all 1319 q) on 4x B300, MRV2, GLM-5.3-NVFP4, `--kv-cache-dtype fp8_ds_mla -cc.cudagraph_mode=NONE`:

| config | main | this PR |
|---|---:|---:|
| `-pp 2 -tp 2` | 0.879 | 0.908 |
| `-pp 2 -tp 2 -dcp 2` with gather DCP (#59916) | 0.820 | 0.908 |
| same, `VLLM_PP_LAYER_PARTITION=38,40` (boundary aligned to a top-k group), no fix | 0.882 | - |

GSM8K (5-shot, all 1319 q, greedy) on 8x MI350X (ROCm 7.2), GLM-5.3-BF16, `--kv-cache-dtype fp8`, default cudagraph mode (`FULL_AND_PIECEWISE`):

| config | code | strict-match |
|---|---|---:|
| `-tp 8` (reference) | this PR | 0.932 |
| `-pp 2 -tp 4` | first commit (NVIDIA-only fix) | 0.886 |
| `-pp 2 -tp 4` | this PR (8 runs, two revisions) | 0.916–0.931 |

Both PP configs on ROCm also include the AMD part of #60477, so the top-k fix is the only difference between them. Repeated runs of the same code vary by about 1.3 points on this setup; interleaved runs of the two revisions overlap.

## Details

**Root cause.** GLM-5.3 sets `index_topk_freq=4` with offset 3, so groups of layers reuse the top-k computed by the group's first layer.
- The default PP2 split puts the stage boundary at layer 39, which is inside a group.
- Stage 1's first layers (39-41) therefore skip the indexer and read `topk_indices_buffer`. On that stage the buffer holds the top-k of the previous step's last indexer layer, for the previous batch.
- Aligning the partition (38/40) restored accuracy, which confirms the cause.

**Fix.** Shared helpers in `model_executor/models/utils.py`:
- `compute_skip_topk_layers` moves there from HY-V4 and replaces the copy in the DSA attention init.
- `pp_splits_layer_sharing` checks whether a later stage's first top-k layer reuses the top-k. `pp_topk_buffers` returns the buffer to send in that case.
- `make_empty_intermediate_tensors_factory` takes those buffers, and `copy_pp_buffers` copies them into place on the receiving stage.

Models:
- DSA (NVIDIA, AMD, dots3) and HY-V4 (NVIDIA, AMD) send the top-k, which is TP-replicated and token-major. `Dots3NoteModel` inherits `forward` but has its own `__init__`, so it calls the helpers too.
- MiniMax-M3 AMD with `use_index_cache` raises instead, since its top-k is sharded over TP index heads. Setting `VLLM_PP_LAYER_PARTITION` avoids the split.
- DeepSeek-V4.1 needs nothing: its index-sharing groups sit inside kv-sharing groups, which already reject PP splits.

`tests/models/deepseek_v32/test_pp_topk.py` covers the stage-boundary check, the empty tensors, and a middle stage receiving and forwarding the top-k.

**Duplicate check.** No open PR fixes top-k across PP stages (searched "pp topk_indices", "pipeline topk").
