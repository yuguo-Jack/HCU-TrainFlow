# [Bugfix][ROCm][Kimi-K3] Refresh derived weight copies after in-place weight writes

[Upstream PR](https://github.com/vllm-project/vllm/pull/64886) · state: open · merged: False

## Original PR description

## Overview

This adds an opt-in module hook, `refresh_derived_weights()`, plus a walker in `weight_utils.py`. The walker is called from three shared paths that overwrite `state_dict()` tensors in place without the per-layer post-load hook:
- `SparseNCCLWeightTransferEngine.finish_weight_update`;
- the kernel-format branch of `reload_weights`;
- `ElasticEPScalingExecutor.prepare_new_worker`.

It does nothing unless a module defines the hook. Today only the Kimi-K3 ROCm KDA layer and MLA wrapper do, and the elastic-EP call has no model that reaches it yet. The PR also makes the Kimi-K3 ROCm `_w_fold` rebuild write in place.

Kimi-K3 on ROCm derives three tensors from its weights and keeps them outside `state_dict()`:
- `decode_conv1d_weight`, read by the AITER Gluon and HIP fused decode kernels;
- `decode_norm_weight`, read by the HIP kernel only;
- `_w_fold`, a plain attribute read by the fused decode-query GEMM.

The KDA copies (the first two) go stale on all three paths. `_w_fold` goes stale on the kernel-format reload and on elastic EP. On sparse NCCL it is rebuilt, but as a new tensor that CUDA graphs captured earlier do not read.

Related (all merged):
- #60110 added `_w_fold`.
- #61207 stages the KDA copies at load.
- #64158 builds `_w_fold` from the root model's hook.
- #64357 runs the model-level hook after every load, checkpoint-format reload and sparse NCCL update, but not after a kernel-format reload.

## Claims

The kernel-format reload claim is covered by the updated unit test. The sparse NCCL, elastic-EP and `_w_fold` claims come from reading the code (see Validation).

- **Kernel-format `reload_weights(..., is_checkpoint_format=False)`:** the Kimi-K3 ROCm KDA decode copies are re-staged from the reloaded weights, at the same addresses. On main they keep the values staged at load, while prefill reads the reloaded weights.
- **Sparse NCCL weight updates:** the same holds for an update that writes `conv1d.weight` or `o_norm.weight`.
- **Elastic-EP scale-up:** new ranks re-derive these tensors from the weights received from their peer, instead of keeping values computed from the dummy load. This is defensive for Kimi-K3. It does not set `num_moe_layers`, so EPLB never registers it and an elastic-EP scale-up cannot complete on it today (it fails at the `model.expert_weights` and `model_states` lookups).
- **`_w_fold`:** rebuilt in place. On main, layerwise reload and sparse NCCL assign a new `_w_fold`, so CUDA graphs captured before the rebuild keep the old, freed tensor's address.
- **Other models:** no change. Only modules that define `refresh_derived_weights()` are called.

## Details

**How it was found.** By reading the code while reviewing #63612. It was not observed in a serving or RL run.

**Root cause.**
- The KDA copies are staged only in the layer's `process_weights_after_loading`. `_w_fold` is built only from the Kimi-K3 model-level hook.
- The kernel-format branch of `reload_weights` copies parameters and runs neither hook.
- Sparse NCCL ends with `finalize_model_weights`, which reaches the MLA wrappers through the model hook but not the KDA layers.
- Elastic EP builds new ranks with `load_dummy_weights=True` (`elastic_execute.py:273`), so both hooks derive these tensors from dummy weights. `batch_transfer_weights` then receives only `model.state_dict()` from a peer (`:97`) and runs no post-load pass.

**Change.**
- **The walker:** `weight_utils.refresh_derived_weights(model)` calls `refresh_derived_weights()` on every module that defines it, under `no_grad`.
- **The hook contract** (in the docstring): idempotent; reads only non-expert `state_dict()` tensors, since elastic EP moves routed experts later; no collectives; writes in place.
- **Callers:**
  - `prepare_new_worker`, after the transfer and `torch.accelerator.synchronize()`, under the worker's vLLM config;
  - `finish_weight_update`, after `finalize_model_weights`;
  - the kernel-format branch of `reload_weights`, after the copy loop.
- **`KimiK3DeltaAttention`:** the existing copy body moves into `refresh_derived_weights()`. `process_weights_after_loading` keeps the IPC weight-cache guard and calls it.
- **`KimiK3MultiHeadLatentAttentionWrapper`:** `process_weights_after_loading()` and `refresh_derived_weights()` both rebuild `_w_fold`, which is copied in place once it exists.
- **Precedent:** `refresh_quantized_lm_heads` (`layers/quantization/online/lm_head.py:157`) re-derives copies in place after a weight reload, for the same CUDA-graph reason.

**Alternatives considered.**
- **Re-stage the KDA copies from the Kimi-K3 model hook (`amd/linear.py:1174`).** Sparse NCCL already runs that hook, so this fixes sparse NCCL with no core change. But the kernel-format reload runs no hook, and the elastic-EP receiver runs none, so a core call is needed anyway.
- **Refresh from the weight loader, as #63612 does for its GLM layer.** This covers writes that go through `load_weights`, such as sparse NCCL. It misses the kernel-format `param.copy_` and the elastic-EP `state_dict()` copy. #61207 also moved Kimi-K3's staging out of the loaders because dummy loads skip them.
- **Register the buffers as persistent, so `state_dict()` carries them.** This covers elastic EP only. It changes the key set of every saved Kimi-K3 `sharded_state` checkpoint ("Missing keys" on load), makes that key set depend on the decode backend picked at runtime, and does not cover `_w_fold`.
- **Re-run `finalize_model_weights` or the per-layer hooks on new elastic ranks.** Model-level hooks are not idempotent on already-processed weights in general: DeepSeek-V4 AMD preshuffles in its hook.

**Trade-offs and limits.**
- On sparse NCCL, `_w_fold` is now built twice per update (model hook, then the walker). That is one extra `_w_fold` build per MLA layer: `kv_b_proj` dequant, an einsum and a concat, then an in-place copy.
- The same pattern is left for follow-ups:
  - the Kimi-K3 NVIDIA KDA buffers, which only the weight loaders fill, so they are uninitialized after a dummy load;
  - `GateLinear._bf16x3_weight` for fp32-router models on gfx950;
  - #63612's GLM-5.3-Flash decode copy, a model that does reach elastic EP. Its layer could implement this hook.

**Duplicate check.**
- I searched open and closed PRs for `refresh_derived_weights`, `decode_conv1d_weight`, `_w_fold` and elastic-EP buffer staleness, and found the PRs listed above.
- #63612 refreshes its own layer's copy from its weight loader. No PR covers kernel-format reloads or elastic EP, or adds a hook that every in-place path calls.
