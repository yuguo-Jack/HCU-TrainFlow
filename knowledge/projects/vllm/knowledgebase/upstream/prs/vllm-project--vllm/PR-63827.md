# [Bugfix][Core] Defer async KV loads on HiSparse decoders until in-flight steps finish

[Upstream PR](https://github.com/vllm-project/vllm/pull/63827) · state: closed · merged: True

## Original PR description

> **Edited by @MatthewBonanni:** per @LucasWilkinson's suggestion (vMaroon/vllm#2), every async load on a HiSparse decoder is now deferred until the in-flight step is processed; the reuse detection is gone. Overview, Claims, unit tests and Details are updated. The GLM-5.3 results were measured on the earlier revision, which deferred only loads into reused pages.

## Overview

Fixes KV corruption on HiSparse P/D decoders: a NIXL load can overwrite a GPU page while the previous step is still reading it. The request that was reading it emits garbage for the rest of its output. The fix makes the scheduler start every async load on a HiSparse decoder one step later, once the in-flight step is done.

Fixes #63811.

## When it happens

All four hold at once:

1. **HiSparse is on.** It returns a running request's clean resident pages to the GPU pool early; the request keeps reading them until the pool hands them out again.
2. **Async scheduling** (`max_concurrent_batches > 1`): step N is still on the GPU while step N+1 starts.
3. **KV arrives by an async load**: a P/D decoder with `NixlConnector` as consumer. NIXL posts its reads from the CPU, so nothing orders them after step N.
4. **In step N+1, the pool hands one of those returned pages to a new request whose KV comes through that load.**

NIXL then writes the new request's KV into the page while step N still reads it as the owner's KV. The owner's tokens from step N get wrong KV, later steps attend to them, and the output never recovers.

Unaffected: pages filled by a forward or a host restore (ordered on the CUDA stream), and engines without HiSparse or without an async KV load.

## Claims

- Fixes the symptom: output cuts mid-sentence into one repeated token (`locklocklock...` on GLM-5.3) until `max_tokens`, with MTP acceptance at 0.
- With HiSparse enabled, every async load is registered with the connector once the step in flight at its allocation is processed, normally on the next step. Other requests and steps run as before.
- Cost: each async-loaded request on a HiSparse decoder starts its load about one step later. No device sync, and no check for which pages were reused.
- Active only with HiSparse and `defer_block_free` (overlapping steps and a KV consumer); otherwise nothing is deferred.

## Validation

GLM-5.3 on H100, P/D. Decoder TP8 x DP2, MTP 3, MRV2, async scheduling, `MultiConnector` (`NixlConnector` + `HiSparseConnector`), 20,000-block GPU pool. Traffic from `benchmarks/multi_turn`: 46-77K token prompts, 2-4K token answers. Counts are answers with at least 1,024 tokens. The rig runs the production image, a vLLM fork at `110cf9dc12`; "this PR" is this change applied to that fork's scheduler, block pool and KV cache manager (it applies cleanly).

| Free-queue order | Engine | Answers | Page handed to a NIXL load while read | Collapsed |
| --- | --- | --- | --- | --- |
| default | base | 133 | 0 | 0 |
| released pages first | base | 162 | 90 | 81 |
| released pages first | this PR | 173 | 106 (load held) | 0 |

- "Released pages first" is the one-line test change in step 1 below. It makes condition 4 frequent. Any free-block order is valid for the allocator, so a correct engine keeps its output quality under it.
- Collapsed: under 1.3 tokens per step (MTP drafts stop matching) from some point to the end of the answer, for at least 512 tokens. On base, collapse starts a median 35 tokens after the overwrite.
- Holds with this PR: 151 loads, each registered in the pass where step N had been processed, none earlier.
- TTFT of later turns (prompt mostly cached on the decoder) in the stress run: p50 1.98 s base, 2.07 s this PR. First-turn TTFT is not comparable across these runs because the prefill pods' prefix cache state differed.
- Default order with long answers (12-16K tokens, KV pool up to 88% full, base engine): 0 of 5,215 reuses of returned pages went to a NIXL-filled group, so the hold would not have triggered.
- Unit tests in `tests/v1/core/test_deferred_block_free.py`: a deferred load is registered after the in-flight step, it records its prefix cache stats (with `hits_by_source`) when it starts, a load without deferral registers at once, and an abort while deferred frees the blocks after the in-flight step.

**How to reproduce**

1. In `BlockPool.unpin_blocks`, replace `self.free_block_queue.append_n(released)` with `self.free_block_queue.prepend_n(released)`.
2. Serve GLM-5.3 P/D with a decoder as above. Run `benchmarks/multi_turn/benchmark_serving_multi_turn.py --num-clients 4 --max-active-conversations 8` on a generated config: 20 conversations, 10-12 turns, 15K common plus 30-50K prefix tokens, 1-2.5K token user turns, 2-4K token answers. The tool rejects reasoning-only streams, so accept `reasoning` deltas.
3. On base, within minutes, answers end in a repeated token and the `SpecDecoding metrics` per-position acceptance falls toward 0. With this PR, no degenerate answers.

## Details

- `defer_async_loads` is set at init when `defer_block_free` is on and the KV cache config has a HiSparse host pool.
- With a step in flight, the scheduler puts an async load in `deferred_loads` with the fence `sched_step_seq` at allocation instead of calling `update_state_after_alloc`. `_drain_deferred_loads` starts it in `update_from_output`, next to `_drain_deferred_frees`, once `processed_step_seq` reaches the fence. The request stays in `WAITING_FOR_REMOTE_KVS` meanwhile.
- Connector prefix-cache stats for a deferred load are recorded in `_drain_deferred_loads` after `update_state_after_alloc`, so it keeps `hits_by_source` (the connector attributes tiers only after the load plan exists). The allocation-site stats code is unchanged from main apart from skipping deferred loads.
- Abort while deferred: no load was posted, so the scheduler frees the blocks itself, deferred to the same fence through `last_sched_seq`, which is set when the load is deferred. `NixlConnector.request_finished` already releases the remote blocks of a request it never registered.
- The scheduler already fences block reuse against async connector writes (`defer_block_free`), but only for freed requests' blocks; these pages still belong to a running request. Deferring the registration needs no device sync; the only HiSparse-specific line in the scheduler is the init flag.
- CI does not cover the GPU path (needs NIXL P/D on GPUs).

- robertgshaw2-redhat · comment · 2026-10-26T21:02:08Z · [source](https://github.com/vllm-project/vllm/pull/63827#issuecomment-6427240641)

Independent confirmation from #63811, plus a CPU-only test that may be useful here.

Condition 4 happens with the **default** free-queue order, without the `prepend_n` change from the PR's repro step 1. With prefix caching on (as on production decoders), `unpin_blocks` appends released pages to the tail of the free queue, and `free_blocks` also appends freed cached blocks to the tail. Released pages therefore sit in plain LRU order among cached blocks, and ordinary request churn brings them to the head while the owner is still decoding. A NIXL-imported request owns a hot buffer from admission, so every page it writes during decode is released right after its host copy, at any pool usage. This fits production decode pods hitting the collapse while their GPU KV usage peaks around 50%.

The test is in the #63811 comment: https://github.com/vllm-project/vllm/issues/63811. It drives the real `KVCacheManager`, `HiSparseCoordinator` and `NixlPullConnectorScheduler` with no GPU.

- **Setup:** request A, which arrived by import, decodes and has pages released. Short requests then run and finish, with the pool more than half free throughout.
- **Result:** in the next step, NIXL import B's `reqs_to_recv` plan targets two blocks A read as resident in the previous step.
- **Base:** it fails on `main`.
- **This branch:** the same blocks still go to B, as expected since this fences rather than prevents. `coordinator.reused_readable_blocks` contains both blocks, and B is allocated but not scheduled, so `fence_async_loads` is set for that step.

If useful, it could become a regression test here by asserting `fence_async_loads` on that step instead of "no overlap".
