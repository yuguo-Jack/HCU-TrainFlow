# [Bugfix][KV Offload][P2P] Fail never-sent fetches locally

[Upstream PR](https://github.com/vllm-project/vllm/pull/64298) · state: open · merged: False

## Original PR description

## Overview

Queued P2P Fetch messages can outlive a cancelled or timed-out load and be flushed after a delayed handshake. Retire never-sent loads locally and release the producer's parked storage without closing newer work using the same request ID.

Extracts **A** from #61667 as requested in review. Refs #61532. B (#64299) and C (#64300) have merged; this PR addresses the separate unsent-fetch lifecycle.

## Claims

- Retired, cancelled or expired Fetch messages never reach transport handoff.
- Never-sent loads fail locally without abort/deferred-release work. Producer terminal release cannot close a newer live round.
- Post-disconnect AbortAck semantics and finished-request failure bookkeeping are preserved.

The retained manager regression verifies that a never-sent fetch fails locally and releases parked producer blocks. Session regressions cover cancellation/expiry, both handshake orderings, finished-request propagation, subsequent ID reuse, expiry logging and dead-connection/send-failure handling.

Earlier real-entry validation used real HuggingFaceTB/SmolLM2-135M weights at `93efa2f097d58c2a74874c7e644dbc9b0cee75a2`, RTX 4060 Ti/CUDA 13.0, FP16/eager/greedy/batch-invariant inference and NIXL UCX TCP localhost. A delayed-handshake request timed out and recomputed; the peer then received a fresh fetch and never the retired one. The equivalent control observed `['retired', 'live']` and failed. That model test and its dedicated fixture were removed from CI per [review](https://github.com/vllm-project/vllm/pull/64298#issuecomment-6630803920), because the smaller manager/session suite covers the same flow. Their source remains in `e388466c`; the production code is unchanged by this test-only trimming. No task-accuracy or performance claim is made.

## Details

Track a queued Fetch by object identity until transport handoff. Timeout or cancellation retires it locally. Empty terminal Fetch messages release producer supply, subject to the existing-request guard so they cannot close newer work. The manager handles terminal-only fetches without replaying stale stores. Finished loads keep #64300's `request_finished` marker, and the liveness check applies only to data Fetch messages so #64251's abort acknowledgements remain sendable after disconnect.

Duplicate-work check: this is the requested split from the original PR. Merged #64256 handles timed-out sent loads and deferred slot release; merged B handles buffered terminals, and merged C handles finished-request failures. This PR covers the separate never-sent path.

Rendered behavior documentation is in `docs/features/kv_offloading_usage.md`. The existing `v1-kv-offload` CI step selects the retained tests and covers the changed sources.

- liranschour · comment · 2026-10-29T13:16:19Z · [source](https://github.com/vllm-project/vllm/pull/64298#discussion_r4412766023)

File: `vllm/v1/kv_offload/tiering/p2p/session/client.py` · line 567

When a never-sent fetch is retired, the producer never hears about it. No fetch goes out, and `finish()` skips the terminal empty fetch because `peer_lookup_open` is already False. So the prefiller holds this request's blocks until `unbound_store_timeout_s` (60 s by default).

Could you queue the terminal empty `FetchMsg` when retiring the load? It goes out after the handshake, and the producer frees the blocks right away.

One catch: the empty fetch closes the whole `kv_request_id` on the producer. If the same ID is reused before the handshake completes, as in `test_unsent_fetch_retires_without_abort`, it would also close the new round. Only send it when no newer load for that ID is queued.
