# [Bugfix] Keep TRTLLM attention when FlashInfer cubins are local

[Upstream PR](https://github.com/vllm-project/vllm/pull/57644) · state: open · merged: False

## Original PR description

## Problem

`has_nvidia_artifactory()` gates TRTLLM attention for the whole process. When the connectivity probe fails at startup (no egress, a transient DNS failure), vLLM silently falls back to FlashInfer's native attention kernels even when every cubin the server needs is already on disk. On Blackwell that fallback is significantly slower, and the only trace is a one-line "Failed to connect to NVIDIA artifactory" warning that does not say what changed.

## Fix

- `has_flashinfer_cubin()` now also returns true when `FLASHINFER_CUBIN_DIR` points at an existing directory. FlashInfer reads cubins from that directory before it ever contacts the artifactory, so the probe is unnecessary in that configuration, the same as with `VLLM_HAS_FLASHINFER_CUBIN=1` or the `flashinfer-cubin` package.
- The probe's warnings now state the consequence (TRTLLM attention disabled for the process, slower fallback) and the remedy.

## Tests

`tests/utils_/test_flashinfer_cubin.py`: env flag, local dir, missing dir, no cubins; probe skipped when cubins are local; unreachable and non-200 responses warn with the consequence; reachable path unchanged. All run on CPU with the network patched. `pre-commit` (ruff) and the mypy hook are clean for the touched files.

AI assistance was used in preparing this change; the author reviewed all changes and ran the tests.

- zzw4257 · comment · 2026-10-13T04:07:58Z · [source](https://github.com/vllm-project/vllm/pull/57644#issuecomment-6138019858)

Live GPU data for this, since the PR only has CPU tests so far. We hit the bug in practice.

**How often.** We run many short-lived servers on a shared B200 host. Of ~100 server starts that used FlashInfer decode, 3 logged `Failed to connect to NVIDIA artifactory ... Temporary failure in name resolution` and `decode_backend=flashinfer-native`; all others logged `decode_backend=trtllm-gen`. The two we could measure cleanly stayed ~10% slower in decode until restart. Released wheels don't ship `flashinfer-cubin` (see the comment in `requirements/cuda.txt`), so every `pip install vllm` goes through this probe.

**Cost** (vLLM 0.29.0, Qwen2.5-7B-Instruct, 1x B200; one 512-token request, median of 10; artifactory made unreachable with `FLASHINFER_CUBINS_REPOSITORY=http://127.0.0.1:9/`):

| server | `decode_backend` | ms/token |
|---|---|---|
| normal | trtllm-gen | 3.51 |
| artifactory unreachable | flashinfer-native | 3.82 (+8.8%) |
| unreachable + `VLLM_HAS_FLASHINFER_CUBIN=1` | trtllm-gen | 3.51 |

On agent workloads (vLLM 0.28.0, `--max-num-seqs 2`, 12 tree-of-thought and map-reduce programs, 2 servers per row), the unreachable servers had 1.089x per-request decode time (1.080–1.091 across programs) and 1.072x program makespan; `VLLM_HAS_FLASHINFER_CUBIN=1` gave 0.998x on both.

**One gap.** The new check fires only when `FLASHINFER_CUBIN_DIR` is set. In our case it was not: FlashInfer had downloaded the cubins on first use into its default directory (`FLASHINFER_CACHE_DIR / "cubins"`: `~/.cache/flashinfer/cubins`, or under `FLASHINFER_WORKSPACE_BASE` as in our setup). That is the common pip-install setup, and it still loses TRT-LLM on a DNS hiccup (with the clearer warning from this PR). Checking the resolved `flashinfer.jit.env.FLASHINFER_CUBIN_DIR` instead of only the env var would cover it. In our normal runs FlashInfer's loader fetched cubins missing from that directory on first use (`cubin_loader.py: Fetching ...`), so a partly filled directory is handled either way; we have not tested what happens when such a fetch fails.

AI assistance was used to run these measurements and draft this comment; I reviewed the data.
