# [Bugfix][Reasoning] Hunyuan A13B: detect reasoning end from token ids so structured output applies

[Upstream PR](https://github.com/vllm-project/vllm/pull/63632) · state: open · merged: False

## Original PR description



## Overview

With `--reasoning-parser hunyuan_a13b`, structured output (`response_format` json_schema / json / regex) is never applied: the reasoning-end gate in the structured-output manager always reads "not ended", so the whole response is unconstrained and can be invalid JSON with no error. This fixes `HunyuanA13BReasoningParser.is_reasoning_end` / `is_reasoning_end_streaming` to detect the end from token ids.

## Claims

- Structured output now activates after `</think>\n<answer>\n` for Hunyuan A13B (both the normal and "fast think" forms).
- Earlier turns' `<think>…</answer>` in a multi-turn prompt don't start the grammar early.
- Frontend streaming extraction is unchanged: the new check fires on the same token where the parser's state machine switches to the answer (asserted by a test).

Through the real `StructuredOutputManager` (xgrammar and guidance backends; uncommitted harness reusing `_build_harness` from `tests/v1/structured_output/test_structured_output_manager.py`, with `reasoner_cls = HunyuanA13BReasoningParser`): after feeding `<think>\n … </think>\n<answer>\n` through `accept_tokens`, `reasoning_ended` latches and `validate_tokens` rejects a non-JSON token. Before the fix `reasoning_ended` never becomes `True` (2 failed → 2 passed).

Regression: `pytest tests/reasoning tests/v1/structured_output/test_structured_output_manager.py` → 550 passed, 1 xfailed; `tests/tool_parsers/test_hunyuan_a13b_tool_parser.py` → 10 passed, 1 xfailed. `pre-commit` clean.

**Not validated end-to-end:** I don't have hardware for Hunyuan-A13B (80B MoE), so there is no `vllm serve` run with real weights; validation is at the parser and structured-output-manager level on CPU.

## Details

**Root cause.** `is_reasoning_end` returned `self.current_state == "response"`. `current_state` is only advanced by `extract_reasoning_streaming`. The structured-output manager (`vllm/v1/structured_output/__init__.py`, `_get_reasoner`) builds a separate per-request parser and only calls `is_reasoning_end` / `is_reasoning_end_streaming`, so on that instance the state stays `"idle"`. `_get_constraint_bounds` therefore always places the constraint past the accepted tokens, `accept_tokens` never latches `reasoning_ended`, and the bitmask is never applied. The frontend's `resolve_reasoning_ended` on the prompt also always returned `False`.

**Fix.**
- `is_reasoning_end` (called on prompts): scan backward to the newest marker; `</think>\n<answer>\n` → ended, `<think` or `</answer` → not ended. Prompts keep earlier assistant turns verbatim (checked with the model's chat template), so a plain "contains" check would constrain the current turn's reasoning.
- `is_reasoning_end_streaming` (every decode step): only checks whether the end marker completes within `delta_ids` plus the preceding `len(marker) - 1` tokens, per `vllm/reasoning/AGENTS.md`.
- The marker used is `response_start_ids_fast` (`</think>\n<answer>\n`), the suffix of every think-end variant. With the real tokenizer, text like `"think.\n</think>"` merges `.\n` into one token, so the 7-token `response_start_ids` (leading `\n`) often never appears.

**Cost.** `is_reasoning_end` is O(prompt) once per request in the worst case (no markers): ~6.6 ms for a 128k-token prompt; it exits at the newest marker otherwise. The streaming check is O(delta).

**Related.** #58412 (multi-token streaming deltas) and #58127 (`</answer>` leak) touch the same parser but not `is_reasoning_end`.
