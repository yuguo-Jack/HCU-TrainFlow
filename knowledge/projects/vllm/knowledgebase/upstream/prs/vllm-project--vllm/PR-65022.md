# [ROCm][Bugfix] Keep AITER MLA split metadata alive for CUDA graph replay

[Upstream PR](https://github.com/vllm-project/vllm/pull/65022) · state: open · merged: False

## Original PR description



## Overview

On ROCm, `aiter.mla.get_meta_param` is a `functools.lru_cache` (default 128 entries) that returns a device tensor, `num_kv_splits_indptr`. A CUDA graph captured around `mla_decode_fwd` keeps only that tensor's address, and the cache entry is its only owner. Once enough new batch shapes evict the entry, the memory is reused and every replay of that graph reads garbage split offsets: decode output silently turns to gibberish while prefill stays correct. This PR holds a reference to every tensor handed out while a graph is being captured.

This is a stopgap for ROCm/aiter#5193. The proper fix is ROCm/aiter#5194 (open); vLLM pins AITER v0.1.27, which still has the cache. The workaround switches itself off once AITER stops caching the tensor.

## Claims

- Fixes silent decode corruption on long-running ROCm servers whenever AITER MLA decode runs inside CUDA graphs and `mla_decode_fwd` derives its own split metadata: the sparse MLA backend (`ROCM_AITER_MLA_SPARSE`) always, and by code reading the dense backend when it runs without persistent metadata.
- GSM8K on `tencent/Hy4-preview-FP8` (8x MI355X, TP8) scores 93.5–93.7% in both compiled and no-compile graph modes with the fix. Without it, runs scored 75–94% because the corruption started at a random point 25–37 minutes in.
- Memory stays bounded: only tensors handed out during capture are kept, about one per captured batch size.

## Details

**How it was found.** Every bad run had one synchronized event: all in-flight requests degenerated within seconds, with no log message, NaN or KV pressure. Weights and KV cache were unchanged, prompt log-probs (prefill) stayed correct, and decode with graph replay disabled was correct. Sampling AITER's caches showed `get_meta_param` reaching 128/128 entries shortly before the event. The key is effectively the batch token count; mixed prefill/decode steps run attention eagerly and add a key per new batch size, while graph replays never touch the entries their graphs captured, so those are evicted first.

**Fix.** On the first MLA decode call (always before graph capture), wrap `aiter.mla.get_meta_param` and keep a reference to each tensor returned while `torch.cuda.is_current_stream_capturing()`. AITER's cache and results are unchanged. Graph replays run no Python, so steady-state decode has no added cost.

**Why not an unbounded cache.** The dense non-persistent path keys on `total_kv = kv_indices.shape[0]`, which changes almost every step, so an unbounded cache would grow for the life of the server.

**Known gap.** The dense backend's decode-context-parallel path calls AITER's `mla_decode_fwd` directly. The wrapper is installed by the first call through either vLLM decode op, so a server that only takes that path is not covered.
