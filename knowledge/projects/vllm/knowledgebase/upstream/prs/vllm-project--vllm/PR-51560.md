# [Bugfix][Model] Serve Inkling on SM12x via the Triton attention fallback

[Upstream PR](https://github.com/vllm-project/vllm/pull/51560) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Purpose

Fixes #51405: Inkling now **serves** on SM120/SM121 (RTX PRO 6000 Blackwell, GeForce Blackwell, DGX Spark) instead of crashing during startup profiling with

```
AssertionError: Paged KV not supported on SM 12.0 in this PR
```

**Change of scope.** Earlier revisions of this PR rejected SM12x up front, because no in-tree path could serve it. @TheVerdman's #55078 has since added a Triton relative-attention fallback for SM8x (reusing Inkling's ROCm kernels). SM12x hits the identical `page_table is None` limitation in FA4, so the same fallback applies, and the fail-fast guard no longer has anything to reject. This PR now makes SM12x work, and fixes the further problems that showed up once it did.

**Stacked on #55078.** This branch contains #55078's commits; until it merges, the diff here includes them. Please review only the commits listed below. @TheVerdman offered in #55078 to either fold the SM12x change in or keep it as a follow-up; keeping it here keeps #55078 focused on SM8x.

## Changes

1. **Route SM12x to the Triton fallback** (`vllm/models/inkling/nvidia/attention.py`). `_TRITON_ATTENTION_MAJORS = (8, 12)`; the SM8x/SM12x comparison tests in `test_fa4_rel_attention.py` run on both.
2. **Remove the fail-fast guard** added by earlier revisions (`verify_model_arch`, `_CAPABILITY_RESTRICTED_MODELS`, `check_inkling_fa4_support`, the `ModelConfig` hook and their tests). With SM12x served, every entry in those tables would be dead. `docs/models/supported_models.md` keeps the new Inkling rows; the note now says SM8x/SM12x use the Triton fallback.
3. **Skip the fused Lamport collective unless the TP GPUs are fully NVLink-connected** (`vllm/models/inkling/nvidia/ops/lamport.py`). Lamport polls peer stores; over PCIe P2P it hangs on its barrier. That was reproduced here at TP=2 on 2× RTX PRO 6000 Workstation, and at TP=4 on 4× RTX PRO 6000 Server (PCIe-only), where `LAMPORT_RS_SCONV=0` was required. Init now checks `current_platform.is_fully_connected` (same NVML query as the custom all-reduce) and falls back to NCCL with a warning. Unlike the custom all-reduce, there is no two-GPU exemption, because the TP=2 hang is exactly the reported case.
4. **FP8 KV cache on the Triton fallback** (`common/ops/triton_rel_attention*.py`). With `--kv-cache-dtype fp8*`, the prefill kernel dotted bf16 `q` against fp8 `K`, and both kernels cast softmax probabilities to the fp8 `V` dtype before P·V. K/V are now upcast to the query dtype, as the decode kernel already did for K.
5. **Compile split-KV decode once** (`common/ops/triton_rel_attention_decode.py`). `max_kv_splits` was a `constexpr` derived from the live `max_seq_len`, so every 2048-token step of context (up to 32 splits) JIT-compiled a new kernel variant mid-serving, and again after every restart without a persisted Triton cache. It is now an unspecialized runtime argument.
6. **Port #60502 to the shared kernel.** #60502 migrated the ROCm Inkling kernel off `tl.make_block_ptr`; #55078 moved that kernel to `common/ops/triton_rel_attention.py`, so the same migration is applied there (resolved while merging `main`).

## Not duplicating existing work

- #55078 covers SM8x only and does not claim SM12x; this PR builds on it rather than re-implementing it.
- #54705 / vllm-project/tml-fa4#4 add FP8 KV on the SM100 FA4 sheared path only; item 4 here is the Triton fallback, a different kernel.
- No open PR addresses the Lamport PCIe hang or the decode recompiles.

- m4xkushnir · comment · 2026-09-13T19:38:19Z · [source](https://github.com/vllm-project/vllm/pull/51560#issuecomment-5655617484)

@RocketRider — yes, this is fail-fast only. DGX Spark is GB10, which is family-120 Blackwell (sm_121), so the `major == 12` entry here catches it. It doesn't make Inkling run; it makes it stop in ~7s naming your device instead of after loading the full checkpoint and sizing the KV cache.

The underlying blocker is that the FA4 relative-attention forward has no paged-KV path on SM12x, and vLLM always attends over the paged KV cache. That kernel is fetched at build time from `vllm-project/tml-fa4` (pinned in `cmake/external_projects/tml_fa4.cmake`), so the fix can't be written from this repo.

On work in progress:

- #55078 routes around FA4 entirely on SM8x, using FlexAttention with Inkling's relative bias carried through `score_mod`. It explicitly does not claim SM12x, but it is the closest thing to a template — if it lands, extending the same path to major 12 is the plausible in-tree route, and the guard here comes out as one row in `_CAPABILITY_RESTRICTED_MODELS` plus one entry in `_NO_PAGED_KV_MAJORS`.
- @IgnacyPawlak's workaround in #51405 materialises the paged cache and calls with `page_table=None`, `seqused_k` and `num_splits=1`. It gets Inkling serving short prompts on sm_120, but long multi-page contexts hit an invalid global read that needs `aux_tensors` plus batch > 1 — which Inkling's relative bias always triggers. It also needs a source patch to the installed tree, reachable from no released build or flag. I wouldn't run it for anything real; an IMA on a long context is worse than a refusal to start.

One thing specific to a multi-Spark setup even if attention gets solved: Inkling's fused collective `rs_sconv_ag_add_norm` (`vllm/models/inkling/nvidia/ops/lamport.py`) hangs on its Lamport barrier over CUDA IPC without NVLink. `LAMPORT_RS_SCONV=0` switches to the NCCL fallback; `NCCL_P2P_DISABLE=1` does not cover it. #52708 is also relevant if you're building rather than using a published wheel.

If you can test patches on 4× Spark, saying so on #55078 is probably the highest-leverage place for it.
