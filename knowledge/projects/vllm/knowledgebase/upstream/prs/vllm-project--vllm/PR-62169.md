# [Bugfix][Attention] Chunk sparse indexer decode logits by request

[Upstream PR](https://github.com/vllm-project/vllm/pull/62169) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

The CUDA sparse-indexer decode path scores the whole batch into one fp32 `[batch * next_n, max_model_len]` logits tensor. Full CUDA graphs keep that tensor in their pool, while the profiling run reserves only `VLLM_SPARSE_INDEXER_MAX_LOGITS_MB` for it. This PR scores whole requests in chunks bounded by that budget, as the prefill path already does. At long context with many sequences, this frees several GiB per GPU for KV cache.

## Claims

- Decode logits never exceed `VLLM_SPARSE_INDEXER_MAX_LOGITS_MB` (default 512 MiB) per chunk on SM90/SM120. At least one whole request goes into each chunk.
- DeepSeek-V4.1-Flash, 8x RTX PRO 6000, TP8, 1M context, 1,024 sequences: the CUDA graph pool drops from 12.45 to 3.09 GiB per GPU, and KV cache capacity grows 2.12x (6.31M to 13.39M tokens).
- Accuracy is unchanged (GSM8K 0.901 before, 0.904 after, with 1,024 concurrent requests so the chunked path runs).
- Nothing changes when the batch fits in one chunk. Varlen decode (SM100), DCP and XPU keep the single full-batch call.

## Details

**Root cause.** The decode branch calls `fp8_fp4_paged_mqa_logits` once for the whole batch. For V4.1 at 1M context, each row has 262,144 compressed columns (1 MiB of fp32). During FULL-graph capture, that allocation is made at the captured batch size and stays in the graph pool. The profiling run's dummy allocation reserves only `VLLM_SPARSE_INDEXER_MAX_LOGITS_MB`, and prefill is already chunked to that budget, but decode was not. The measured pool shrinks by 9.36 GiB per GPU. That is more than one 1 GiB logits tensor; I have not broken it down per captured size.

**Change.**

- `chunk_size = max(1, budget // (next_n * max_model_len * 4))` requests.
- Each chunk slices Q, Q scales, weights, block-table rows, candidate rows and top-k rows.
- Each chunk rebuilds its DeepGEMM schedule metadata from its own context lengths. It uses `get_num_sms()`, DeepGEMM's current SM count, which dual-batch overlap lowers. That is the count the kernel checks the metadata against (the full-batch case of this is #60732).
- Each chunk's logits are freed before the next chunk is allocated.
- The chunk size depends only on shapes, so it adds no host sync, and graph capture stays deterministic. The test captures the chunked path in a graph.
- The extra cost is one small metadata kernel per chunk per indexer layer, paid only when the batch is larger than one chunk.
- GSM8K throughput was the same in both arms: 2,339–2,541 output tok/s patched, against 2,313–2,556 unpatched, over 3 runs each. This is not a performance claim.

**Scope.**

- SM100 decode is varlen (`indices`, with bf16 logits). Chunking it would need varlen-aware schedule metadata that I cannot test, so that path keeps one call.
- DCP keeps one call, because `_merge_dcp_topk_global` runs over the full rows.

**Not a duplicate.**

- #58068 fixes the prefill logits width (#55569), not decode.
- #56686 and #42856 size decode logits by `max_seq_len` for eager steps. Under graph capture, `max_seq_len` is `max_model_len`, so captured graphs keep the full width.
- Searches for open PRs on decode-logits chunking, `VLLM_SPARSE_INDEXER_MAX_LOGITS_MB` and `sparse_attn_indexer` decode memory found nothing else.
- #58536 (TP-sharded decode rows) and #60732 touch the same decode branch but solve different problems. I will rebase onto whichever lands first.
