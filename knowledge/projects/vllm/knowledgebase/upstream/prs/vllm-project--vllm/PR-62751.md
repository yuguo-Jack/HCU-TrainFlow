# [Quantization] Honor MoE activation override for Humming MXFP4

[Upstream PR](https://github.com/vllm-project/vllm/pull/62751) · state: closed · merged: True

## Original PR description



## Overview

`--moe-backend humming --quantization-config.moe.activation <name>` was silently ignored for gpt-oss: the Humming conversion for `GptOssMxfp4MoEMethod` never received an input schema, so experts always ran with BF16 activations, and vLLM logged a misleading "Falling back to 'HUMMING' with BF16 activations". This PR passes the user's MoE activation override to Humming (gpt-oss, plus the shared MXFP4 converter).

Depends on vllm-project/humming#157 being released and the `humming-kernels` pin being bumped separately. Without that fix, Humming's MX group-scaled activations produce NaN rows whenever K is padded, which includes gpt-oss (hidden 2880, padded to 2944).

## Claims

- On gpt-oss, `--moe-backend humming --quantization-config.moe.activation {mxfp8,mxfp4,fp8_per_token}` now runs Humming with that activation format instead of BF16. Unsupported requests fail at load ("No compatible Humming input schema") instead of silently running BF16.
- The BF16-fallback warning no longer fires when Humming applies the user's override itself. It still fires when Humming really does run BF16, e.g. online MXFP4, whose W4A4 preference Humming does not apply.
- Adds GPQA coverage for Humming + MXFP8 on gpt-oss-20b to the optional B200 GPT-OSS eval job.

## Validation

GPT-OSS-20B on B300 (SM103). `humming` here is humming `main` plus vllm-project/humming#157.

GPQA (`tests/evals/gpt_oss/test_gpqa_correctness.py`, reasoning effort low, TP=2, threshold 0.568), using a local copy of the configs pointing at the `RedHatAI/gpt-oss-20b` mirror:

| Config | GPQA | Runs |
|---|---|---|
| `--moe-backend humming --quantization-config.moe.activation mxfp8` (new config) | 0.5764, 0.5720 | 2 |
| `--quantization-config.moe.activation mxfp8` (auto, FlashInfer TRT-LLM MXFP8, existing config) | 0.5663 | 1 |

Both pass (the harness uses threshold 0.568 with tolerance 0.05). In one of the two Humming runs, the harness's post-test GPU-memory wait (120 s) timed out after the score passed. The server and workers had exited cleanly, and a dedicated teardown check on the same config (serve, load, SIGTERM) released all GPU memory within 10 s, so I attribute it to the shared machine rather than this change.

GSM8K sanity check (first 200 test questions, reasoning low, TP=1), with the MoE path the engine actually selected, read back from the layer:

| Config | Before (main, humming 0.1.17) | After (this PR + humming#157) |
|---|---|---|
| `--moe-backend humming` | Humming, BF16 act: 0.475 | Humming, BF16 act: 0.535 |
| `... --quantization-config.moe.activation mxfp8` | Humming, **BF16 act** (override ignored): 0.480 | Humming, MXFP8 act: 0.535 |
| `... --quantization-config.moe.activation mxfp4` | Humming, **BF16 act** (not scored) | Humming, MXFP4 act: 0.415 |
| `... --quantization-config.moe.activation fp8_per_token` | Humming, **BF16 act** (not scored) | Humming, FP8 per-token act: 0.530 (per-token scales are unaffected by humming#157; measured on 0.1.17) |
| `--quantization-config.moe.activation mxfp8` (auto) | FlashInfer TRT-LLM MXFP8: 0.535 | unchanged |

With this PR but humming 0.1.17 (without #157), the MXFP8 and MXFP4 rows score 0/200 because of the humming padded-K bug described above.

Reproduce:

```bash
pytest -s -v tests/evals/gpt_oss/test_gpqa_correctness.py --config-list-file=configs/models-b200.txt
vllm serve openai/gpt-oss-20b --moe-backend humming --quantization-config.moe.activation mxfp8
```

## Details

- **Root cause:** `select_mxfp4_moe_backend` resolves the override, but `convert_gpt_oss_weight_to_mxfp4_moe_kernel_format` called `convert_to_humming_moe_kernel_format` without an input schema, so Humming used its default (BF16, or `VLLM_HUMMING_INPUT_QUANT_CONFIG`). The Humming branch now builds the input schema from `_resolve_activation_key(None)`, mirroring the existing checkpoint-key handling in `convert_weight_to_mxfp4_moe_kernel_format`. The env var still takes precedence, and input-schema fallback is off, so an explicit request is either honored or fails loudly.
- **Both converters share one helper:** `_humming_input_schema()` resolves the checkpoint key together with the override, replacing the checkpoint-only logic in `convert_weight_to_mxfp4_moe_kernel_format`. Humming therefore applies exactly the user's override on every MXFP4 path, which is what makes the narrowed warning exemption correct. On online MXFP4, selection asks for W4A4 but Humming runs BF16 unless the user overrides, so the warning still fires there.
- **Relation to #59488:** that PR also changes the generic converter's Humming branch and additionally changes backend *selection* for `Mxfp4MoEMethod` models (DeepSeek V4/V4.1, Kimi-K3), which this PR does not touch. The two will conflict in that one hunk; whichever lands second can drop its version. This PR is needed independently because #59488 does not cover the gpt-oss path.
- **Override resolution timing:** the override is resolved from the current vLLM config during `process_weights_after_loading`. Both initial load and `reload_weights` run inside `set_current_vllm_config`.
- **CI:** the new config runs in the optional `(B200) GPQA Eval (GPT-OSS)` job and will fail there until the humming pin includes #157.
