# [Perf][Step5] Overlap the shared expert with routing at small batch

[Upstream PR](https://github.com/vllm-project/vllm/pull/62771) · state: open · merged: False

## Original PR description



## Overview

`Step5MoE.forward` runs the shared expert, then the router, then the routed experts, all on one stream. At decode batch sizes these are small, latency-bound kernels. This PR runs the shared expert on the aux stream beside the router and routed experts for up to 64 tokens, through the existing `maybe_execute_in_parallel`, as Inkling does for its sink experts. Follow-up to #61727.

## Claims

- Step-5 decode on a one-GPU proxy (1xH200, all 92 layers, dummy weights, TP8 expert widths): a decode step takes 4.6-6.7% less time at 1-32 requests, and 4.1-5.4% less with MTP (3 speculative tokens) at 1-8 requests. A mixed prefill/decode run is 2.5% shorter.
- Outputs are unchanged: same kernels on the same inputs, only the stream differs. Greedy tokens match main exactly.
- No change above 64 tokens per step, with MegaMoE, sequence parallelism, EPLB or fully-sharded LoRA, when the shared expert would reduce on its own (TP > 1 with DP > 1), with `VLLM_DISABLE_SHARED_EXPERTS_STREAM=1`, and during breakable CUDA graph capture (`maybe_execute_in_parallel` falls back to serial there).

## Validation

One GPU stands in for one TP8 rank's MoE: all 92 layers, dummy weights, 64 experts of the per-rank width (`moe_intermediate_size` and `share_expert_dim` 192, dense `intermediate_size` 1728), attention at TP1. 1xH200, nightly `df3bd094ae`, `VLLM_USE_BREAKABLE_CUDAGRAPH=1`, default CUDA graph mode (decode runs in FULL graphs).

```python
LLM(model="stepfun-ai/Step-5-Preview", load_format="dummy",
    hf_overrides={"text_config": {"moe_num_experts": 64, "moe_intermediate_size": 192,
                                  "share_expert_dim": 192, "intermediate_size": 1728}},
    max_model_len=8192, enable_prefix_caching=False, seed=0)
```

Prompts are 512-1536 random tokens, greedy, `ignore_eos`. ms per decode step = (time for 129 tokens - time for 1 token) / 128. main and this PR alternate in one container (main, PR, PR, main), 2 runs each, median of 4:

| | main | this PR | change |
|---|---|---|---|
| decode, 1 request | 13.42 | 12.52 | -6.7% |
| decode, 8 requests | 17.36 | 16.39 | -5.6% |
| decode, 32 requests | 20.94 | 19.99 | -4.6% |
| MTP3 decode, 1 request | 5.34 | 5.05 | -5.4% |
| MTP3 decode, 8 requests | 7.82 | 7.50 | -4.1% |
| 128 requests through 32 slots, 64 tokens each (s) | 15.91 | 15.50 | -2.5% |

MTP uses `rejection_sample_method="synthetic"` with acceptance rates 0.8/0.6/0.45. In one main run at 1 request the 1-token pass took 0.83 s instead of 0.17 s, so its decode figure is too low; the median is not affected.

As a bound, a third arm drops the shared expert entirely (`shared_output = None`), which is the most any overlap can save. Same proxy, plain decode, 2 runs per arm in the order main, bound, PR, PR, bound, main, median of 4 (separate container from the table above):

| | main | PR | no shared expert | PR saves, of the bound |
|---|---|---|---|---|
| decode, 1 request | 13.47 | 12.46 | 12.31 | 1.01 of 1.16 ms (87%) |
| decode, 8 requests | 17.27 | 16.37 | 16.11 | 0.90 of 1.16 ms (78%) |
| decode, 32 requests | 20.83 | 20.03 | 19.67 | 0.79 of 1.16 ms (68%) |

Greedy tokens (8 requests, 64 tokens) are identical between main and this PR, and between two main runs. With synthetic MTP rejection, two main runs already differ, so that comparison is not meaningful.

No new test: the change only moves the shared expert to another stream, and Step-5 has no MoE-level test to extend. `tests/models/step5/test_strided_summary_cache.py` does not reach this code.

## Details

- Collectives: the shared expert must not issue one on the aux stream. With TP > 1 and DP = 1, Step-5 already defers both MoE branches' reduction to one fused all-reduce after the combine (`_step5_moe_reduce_policy`), so the shared expert has none and can overlap. When it reduces on its own, the overlap stays off.
- The 64-token cap: on the same proxy, overlap at 96 tokens per step gave -1.0% (plain) and -1.8% (MTP), inside the run-to-run spread, and +1.0% / -0.3% at 128. It is capped at 64 rather than following `VLLM_SHARED_EXPERTS_STREAM_TOKEN_THRESHOLD` (default 256); the env var can still lower it.
- With the overlap off, the routed branch now runs before the shared expert instead of after. The two are independent, so the result is the same.
- LoRA: fully-sharded LoRA layers all-gather / all-reduce across TP on their own, so with `fully_sharded_loras` the overlap stays off, as #61284 does for `SharedExperts`. Plain LoRA keeps the overlap; its shrink/expand buffers are allocated per call on the current stream.
  Checked on the same 1xH200 proxy at TP1, nightly `8e2beaa3bf` plus this branch: the overlap is on in all 88 MoE layers without LoRA and with `enable_lora`, off in all 88 with `fully_sharded_loras`, and greedy tokens (8 requests, 32 tokens) match across the three. The TP > 1 hang itself was not reproduced here.
- Not measured: TP > 1 and the full model. I only ran the one-GPU proxy; 8xH200 TP8 or 4xB300 runs are not available to me. With TP > 1 and DP = 1 the overlap is on and the shared expert issues no collective (without fully-sharded LoRA), but that path is not run here. The proxy keeps TP1 attention heads and has no all-reduce, so the real TP8 step is shorter and the shared expert is a larger part of it.

Not a duplicate: no open PR changes `Step5MoE.forward`. #62577 and #62550 touch Step-5 but not the MoE forward.
