# [ROCm][Perf] Fix Kimi-K2.6 int4 MoE prefill regression on Triton 3.8 (gfx950 tuned config)

[Upstream PR](https://github.com/vllm-project/vllm/pull/62565) · state: closed · merged: True

## Original PR description

## Purpose

Kimi-K2.6 (int4 W4A16, TP8) prefill regressed between v0.29 and v0.31 on MI350/MI355: c32 TTFT went up ~150%. The cause is a Triton 3.7.1 → 3.8.0 codegen regression in `fused_moe_kernel_gptq_awq` for one tile, which the tuned config uses for its `"8192"` entry (every batch from ~6k tokens up): BLOCK 256×256×32, 8 warps, 2 stages, `matrix_instr_nonkdim=32`. On Triton 3.8 that tile is 3–8x slower; the same tile with 1 stage, or with BLOCK_N 128, is fine.

This PR changes that entry to BLOCK_N 128 and `num_stages=1` in the four identical `E=384,N=256,device_name=AMD_Instinct_MI35*,dtype=int4_w4a16.json` files. Nothing else changes: only Kimi-K2-family int4 checkpoints at TP8 on MI350/MI355 load these files, and only batches of ~6k+ tokens use this entry.

## Test Result

Kernel (Kimi-K2.6 TP8 shapes, w13 + w2 summed over M=8192 and 16384, Triton 3.8.0):

| `"8192"` entry | µs |
| --- | ---: |
| current (256×256×32, 8 warps, 2 stages) | 44180 |
| 256×256×32, 8 warps, **1 stage** | 7677 |
| 256×**128**×32, 8 warps, 2 stages | 7631 |
| **this PR** (256×128×32, 8 warps, 1 stage) | 6129 |

Serving (change vs. current table):

| conc | TTFT (before → after) | TPOT | E2EL | tok/s |
| ---: | --- | --- | --- | --- |
| 1 | 118 → 117 ms (−0.9%) | +1.8% | +1.8% | −1.7% |
| 32 | 1981 → 829 ms (−58%) | −1.5% | −5.8% | +6.2% |

c1 doesn't reach the `"8192"` entry; its TPOT difference comes from one restart (20.93 vs 21.92 ms) and is run-to-run noise.
