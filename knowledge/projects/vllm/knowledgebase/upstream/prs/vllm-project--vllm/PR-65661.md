# [Bugfix][CPU] Support Mamba2 internal prefill checkpoints on CPU

[Upstream PR](https://github.com/vllm-project/vllm/pull/65661) · state: open · merged: False

## Original PR description

## Overview

Fixes #62153. With prefix caching on (the default), Mamba2 hybrid models crash on the CPU backend once a prefill crosses a Mamba block boundary. This is a regression from #57329. This PR makes the internal prefill checkpoints from #57329 work on CPU instead of turning them off there.

## Claims

- Mamba2 hybrid models no longer crash on CPU with prefix caching on: `granite-4.0-h-350m`, cold 1300-token prompt, `IndexError` on main.
- Checkpoints stored inside a CPU prefill are reused correctly. A prompt that shares 1024 tokens with an earlier one gets `cached=1024`, and every prompt produces the same greedy tokens as a run with prefix caching off.
- CPU only. The CUDA/ROCm path is unchanged except for one `current_platform.is_cpu()` branch in `MambaPrefillCheckpointExporter.export()`.
- `tests/kernels/mamba/test_mamba2_checkpoint_state.py` now runs in the CPU CI. On main, most of it fails on CPU.

## Validation

**End to end.** macOS 26.6.2, Apple M1 Pro, CPU backend, built from source on `790be385c8`. Model `ibm-granite/granite-4.0-h-350m`, fp32, greedy, 16 output tokens, `VLLM_CPU_KVCACHE_SPACE=1`. Prompts run one at a time, in this order:

| Prompt | main (`790be385c8`) | This PR, prefix caching on | This PR, prefix caching off |
|---|---|---|---|
| 1300 tokens (cold) | `IndexError: index 5 is out of bounds for dimension 0 with size 1` | cached 0 | cached 0, same tokens |
| 512 tokens | – | cached 0 | cached 0, same tokens |
| 513 tokens | – | cached 0 | cached 0, same tokens |
| first 1024 tokens of the 1300 prompt + 276 new | – | cached 1024 | cached 0, same tokens |

The cold 1300-token prefill runs in one step, crosses the 512 and 1024 block boundaries, and stores the 1024 checkpoint from inside that step. The last prompt resumes from that checkpoint. In a second ordering (513 tokens, then 1300), the 1300-token prompt resumed from the 512 checkpoint stored inside the 513-token prefill (`cached=512`), and again matched the prefix-caching-off tokens. On main, that ordering crashes at the 1300-token prompt with index 3.

## Details

**Root cause.** #57329 lets `MambaMixer2` store a block-boundary checkpoint from inside a prefill (`num_prefill_checkpoint_blocks=1`), so the scheduler no longer splits long prefills at block boundaries. Two pieces of that path had no CPU implementation:

1. `_mamba_chunk_scan_combined_fwd_cpu` accepts `return_intermediate_states` but ignores it, and always returns one final state per sequence. `conv_ssm_forward` then reads `varlen_states[last_chunk_indices_p]` with per-chunk indices, which raises the `IndexError` (index 5 = last of the six chunks of a cold 1300-token prefill split at 256-token chunks and the 1024 checkpoint).
2. The store of the checkpoint into the paged cache is Triton-only. It used to be `store_prefill_checkpoint` in `ops/ssd_checkpoint.py`. Since #63742 it is `MambaPrefillCheckpointExporter.export()`, which always launches `store_cache_checkpoints_kernel`. Getting past 1 alone therefore fails at the kernel launch.

**Fix.**

- *CPU chunk scan.* When intermediate states are requested, run the existing C++ `mamba_chunk_scan_fwd_cpu` one chunk at a time, carrying each sequence's state across its chunks, and return the state at every chunk end, `(num_chunks, nheads, headdim, dstate)`, as the Triton scan does. The path without checkpoints is unchanged.
- *CPU export.* `export()` dispatches to `store_cache_checkpoints_cpu` on CPU. It is a vectorized torch version of the kernel with the same rules: it skips rows with a null destination or no offset, skips the conv window (but still stores the recurrent state) when the offset is shorter than it, maps tokens through `token_indices`, picks recurrent rows through `recurrent_rows`, and copies each recurrent row flat from the block start, so page padding is left alone. It lives next to the other CPU Mamba ops in `ops/cpu/mamba_ssm.py`, and is chosen with `current_platform.is_cpu()`, the same check `ssd_combined.py` uses to pick the CPU chunk scan.
- *Tests.* `test_mamba2_checkpoint_state.py` is added to the x86 and Arm CPU CI. A new test covers a batch of two prefills with different chunk counts: each row's final state matches a solo run, and a checkpoint in one row matches a run over that row's prefix. The existing store test now gives its declining row an offset with a null destination, so the null-block skip (a non-final chunk under sparse retention, #59175) is covered on GPU and CPU.

**Alternative considered.** The smaller fix leaves `num_prefill_checkpoint_blocks` at 0 on CPU, as GDN does through `_exports_checkpoints`, so the scheduler splits CPU prefills at block boundaries as before #57329. It also fixes the crash and gives the same cache hits, but a 1300-token prompt then runs as 1024 + 276 tokens in two steps instead of one, and CPU stays on a different scheduling path than GPU. This PR keeps CPU on the #57329 path.

**Tradeoff.** With checkpoints, the CPU chunk scan launches the C++ kernel once per chunk (`chunk_size` 256 for this model) instead of once per batch. Only steps that store a checkpoint take this path. I did not measure the throughput impact.

**Relation to #62232.** #62232 by @deep1blue targets the same issue and builds on the chunk-scan change from my branch. Its branch predates #63742, so on that branch Mamba2 still calls the Triton-only `store_prefill_checkpoint`. It also adds `MambaMixer2.get_prefill_checkpoint_alignment()`, which changes the prefill checkpoint alignment on GPU too and overlaps #61466. This PR stays CPU-only, is on current main, and was validated end to end. I asked @tomeras91 on Slack about opening a separate PR, and he said it was fine. Thanks to @deep1blue for the work on #62232.
