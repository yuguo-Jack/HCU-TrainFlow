# [ROCm][Bugfix][Perf] Route AutoAWQ checkpoints to the RDNA W4A16 kernel and retune gfx12 small-M tiles

[Upstream PR](https://github.com/vllm-project/vllm/pull/63562) · state: open · merged: False

## Original PR description

## Overview

Route AutoAWQ linear layers on RDNA through the mixed-precision W4A16 selector, paired with the gfx12 small-M tile retune needed to avoid large batched regressions. Preserve legacy AWQ fallback when automatic selection exhausts eligible kernels, and deduplicate its warning.

Related: #63455; fallback contribution merged from [daibenzhe/vllm#1](https://github.com/daibenzhe/vllm/pull/1). Duplicate checks on 2026-10-30 found only this PR for `63455 in:body`; the area searches and earlier issue discussion identified no other PR implementing this combined gfx12 tile/routing change. This PR is **ready for review**; the CDNA test expectation and performance tradeoffs below still need resolution before merge.

## Claims

- Retune gfx12 tiles for `M <= 32`: use `BLOCK_N=64`, with `BLOCK_M=16` for `N > K and M <= 16`, otherwise 32. `BLOCK_K=128` and four warps are unchanged. Historical Qwen3 compressed-tensors measurements improved batch-8 whole-generation throughput by 78.4%.
- Make AutoAWQ use the existing mixed-precision selector on RDNA (`gfx1x`). On the measured R9700, normal selection uses `RDNAHybridW4A16LinearKernel`; CDNA retains the legacy method.
- In automatic RDNA selection, catch only `NoCompatibleMPLinearKernelError` and install the legacy method before weight registration/repacking. Explicit backend preferences disable this legacy fallback; weight-loading and execution errors are not caught.
- Pass `str(exc)` to `warning_once`, so identical fallback reasons share a cache entry instead of logging once per layer and retaining exception tracebacks. The real Qwen fallback test emitted one warning after this fix, versus 96 previously.

Kernel ablation (simplified: the four Qwen shapes. The logged run used all eight shapes, one timing
order, and a single `do_bench` median per cell):

```python
import torch
from vllm.model_executor.kernels.linear.mixed_precision import rdna_hybrid_w4a16 as hybrid
from vllm.model_executor.layers.quantization.awq_triton import awq_gemm_triton
from vllm.triton_utils import triton

G = 128
KERNEL = hybrid._triton_w4a16_skinny_fmt_kernel

def build(N, K, seed=0):
    g = torch.Generator(device="cuda").manual_seed(seed)
    w = torch.randint(0, 16, (N, K), dtype=torch.int32, device="cuda", generator=g)
    s = torch.randn(K // G, N, dtype=torch.float16, device="cuda", generator=g) * 0.02
    zp = torch.randint(0, 16, (K // G, N), dtype=torch.int32, device="cuda", generator=g)
    order = torch.tensor([0, 4, 1, 5, 2, 6, 3, 7], device="cuda") * 4
    zp_t = zp.t().contiguous().view(N // 8, 8, K // G)
    shifts = (torch.arange(8, device="cuda", dtype=torch.int32) * 4).view(1, 8, 1)
    return dict(w_q=hybrid.pack_skinny_int4(w), s=s.t().contiguous(),
                zp=torch.sum((zp_t & 0xF) << shifts, dim=1, dtype=torch.int32).contiguous(),
                awq_q=torch.sum((w.t().contiguous().view(K, N // 8, 8) & 0xF) << order[None, :],
                                dim=2, dtype=torch.int32).contiguous(),
                awq_s=s,
                awq_z=torch.sum((zp.view(K // G, N // 8, 8) & 0xF) << order[None, :],
                                dim=2, dtype=torch.int32).contiguous())

def run(a, w, M, K, N, bm, bn):
    b_q = w["w_q"].view(torch.int32)
    c = torch.empty((M, N), dtype=a.dtype, device=a.device)
    KERNEL[(triton.cdiv(M, bm), triton.cdiv(N, bn))](
        a, b_q, w["s"], w["zp"], c, M, N, K, K // 8, K // G,
        w["s"].stride(0), b_q.stride(0), a.stride(0),
        group_size=G, ZP_BIAS=8, HAS_ZP=True, PACKED_DEQUANT=False,
        BLOCK_M=bm, BLOCK_N=bn, BLOCK_K=128, num_warps=4)
    return c

bench = lambda f: float(triton.testing.do_bench(f, quantiles=[0.5, 0.5, 0.5], return_mode="median")[0])
for (N, K) in ((37888, 3584), (4608, 3584), (3584, 3584), (3584, 18944)):
    w = build(N, K)
    for M in (3, 4, 5, 6, 8, 16, 32):
        a = torch.randn(M, K, device="cuda", dtype=torch.float16)
        bm_new = 16 if (N > K and M <= 16) else 32
        t_cur = bench(lambda: run(a, w, M, K, N, 16, 16))
        t_new = bench(lambda: run(a, w, M, K, N, bm_new, 64))
        t_awq = bench(lambda: awq_gemm_triton(a, w["awq_q"], w["awq_s"], w["awq_z"], 8))
        same = torch.equal(run(a, w, M, K, N, 16, 16), run(a, w, M, K, N, bm_new, 64))
        print(f"N={N} K={K} M={M} cur={t_cur*1e3:.1f}us new={t_new*1e3:.1f}us "
              f"awq={t_awq*1e3:.1f}us equal={same}")
```

End-to-end script that produced the historical Qwen3 compressed-tensors table. It is invoked once per (configuration, batch); the
four processes per batch ran interleaved (current, retuned, retuned, current):

```python
# usage: .venv/bin/python bench.py RedHatAI/Qwen3-8B-quantized.w4a16 128 <batch> 3
import os, sys, time
os.environ["VLLM_ROCM_USE_AITER"] = "0"
from vllm import LLM, SamplingParams

model, max_tokens, batch, reps = sys.argv[1], int(sys.argv[2]), int(sys.argv[3]), int(sys.argv[4])
llm = LLM(model=model, max_model_len=2048, enforce_eager=True,
          gpu_memory_utilization=0.85, disable_log_stats=True)
prompts = ["Explain how a paged KV cache works in three sentences."] * batch
params = SamplingParams(max_tokens=max_tokens, temperature=0.0, ignore_eos=True)
for _ in range(2):                       # warm-up at the measured shape
    llm.generate(prompts, params)
rates = []
for _ in range(reps):                    # timed repetitions
    t0 = time.time()
    outs = llm.generate(prompts, params)
    rates.append(sum(len(o.outputs[0].token_ids) for o in outs) / (time.time() - t0))
rates.sort(); med = rates[len(rates) // 2]
print(f"RESULT model={os.path.basename(model.rstrip('/'))} batch={batch} reps={reps} "
      f"tok/s_total_median={med:.2f} min={rates[0]:.2f} max={rates[-1]:.2f} "
      f"tok/s_per_stream={med / batch:.2f}")
```

Those `RESULT ...` lines are what the logs in the table contain; nothing else in the harness was
changed between configurations apart from the tile row under test.

<details>
<summary>Tile-selection rationale, boundary tests and limitations</summary>

**Historical tile implementation and rationale**

**Change**

```python
if M <= 32:
    if N > K and M <= 16:
        BLOCK_M, BLOCK_N, BLOCK_K, num_warps = 16, 64, 128, 4
    else:
        BLOCK_M, BLOCK_N, BLOCK_K, num_warps = 32, 64, 128, 4
```

`BLOCK_K` and the warp count are unchanged from the previous row; the outputs were observed to be
exactly equal for the two tile choices in the measured fp16 cells. That equality is an observation
for this configuration (one device, Triton 3.5.1), not a guarantee that other tile shapes, dtypes or
compiler versions lower identically.

**Why the old row was slow (hypothesis, consistent with the measurements):** with `BLOCK_M=16` and
`BLOCK_N=16` the small-M path issues very narrow N tiles, and for `M > 16` it also launches two M
tiles; the M=32 latency being roughly twice the M=16 latency points at that M-tiling step. No
profiler counters were collected, so the underlying mechanism (occupancy vs. memory-level
parallelism) is not established.

**Tests and CI**

- The two added cases, `(16, 256, 512, 32)` (N>K) and `(16, 512, 256, 64)` (N<K), extend a table that
  previously started at M=17. They pass with and without part 1, so they add boundary coverage
  for both arms of the new condition rather than acting as a failing-before/passing-after gate, and
  no test asserts the selected tile tuple.
- vLLM's ROCm CI runs on CDNA (`gfx942`-class) hardware, which never enters `_on_gfx12x()`. All
  performance evidence here is local to `gfx1201`; independent human confirmation remains pending; marking this PR ready for review does not establish that validation.

**Limitations**

- `_on_gfx12x()` also matches `gfx1200`, which is untested; only `gfx1201` was measured.
- Offline whole-`generate()` throughput on one device with `enforce_eager=True`; not a serving
  benchmark. Part 1 reports batches 1 and 8, part 2 reports batches 1/8/16/32.
- Part 2 is measured on `gfx1201` only. `gfx1151` (the chip in the original report), other `gfx11`
  parts, tensor parallelism, fp8 KV cache, CUDA-graph mode and AWQ checkpoints with a group size
  other than 128 are untested; `gfx1151` batch 6-32 in particular is unknown.
- AWQ MoE (`RoutedExperts`) still uses `AutoAWQMoEMethod`; part 2 does not change it.
- Part 1: kernel tables use synthetic int4 weights with fp16 activations/scales; its end-to-end and
  gsm8k runs use the bf16 checkpoint. Part 2 was measured in fp16, the dtype AutoAWQ checkpoints
  resolve to; bf16 is covered only by `test_awq_bfloat16_on_rocm` and was not benchmarked.
- `down_proj` (tall K) and all measured Llama-3.1 shapes remain slower than `awq_gemm_triton`; this
  narrows the gap, it does not close it.

## Details

The original AutoAWQ routing bypassed the mixed-precision selector on ROCm. The new route reuses `AutoAWQMarlinLinearMethod`; despite its name, non-CUDA platforms select their own kernels. Marlin capability verification runs only on CUDA. Legacy fallback swaps the method before weight creation, so subsequent loading and application use the legacy lifecycle. CUDA, CPU and XPU retain their prior selection paths; AWQ MoE is unchanged. User-facing behavior is documented in `docs/features/quantization/auto_awq.md`.

**Open review findings and limitations:**

- `test_auto_awq_explicit_backend_does_not_fallback` currently expects an MP-selection exception on every platform. Source tracing shows CDNA instead selects the legacy method and does not raise. MI300/MI355 quantization CI includes this test, so its platform expectations need correction. No CDNA run was available; this is a predicted CI failure, not a measured one. The existing model-selection test is not universally skipped on CDNA.
- Explicit non-auto backend preferences suppress legacy fallback, including when the shared selector falls back to its candidate list because no candidate matches the preference. This compatibility edge and the docs' “retain their existing selection behavior” wording need review.
- Single GPU, gfx1201 only. gfx1200, gfx11 (including the issue's gfx1151), tensor parallelism, CUDA graphs and other AWQ group sizes were not validated. BF16 coverage exercises normal RDNA execution; forced legacy was validated in FP16 and retains its own dtype/shape restrictions.
- RDNA is outside the documented hardware support for batch invariance; no batch-invariance guarantee is made here.
- Independent Gemini Argon and Claude Opus reviews preceded this refresh. Their repeated-warning finding is fixed; the CDNA test finding remains open. Current CI is not green: the pre-update checks include failed pre-run-check and Read the Docs, with pre-commit skipped upstream; local formatting checks passed.

AI assistance was used for implementation, testing, analysis and this description. Human review and validation remain required before merge; ready-for-review status does not imply these checks are complete.
