# [Bugfix] Use per-token FP8 MoE activation scales under batch invariance

[Upstream PR](https://github.com/vllm-project/vllm/pull/62369) · state: open · merged: False

## Original PR description

## Purpose

A dynamic per-tensor FP8 activation scale is an amax over every row of the batch, so the quantized value of a token's row, and with it the expert output, changes with the other requests in the batch. The dense FP8 linear path already recognises this under `VLLM_BATCH_INVARIANT=1` (`fp8_scaled_mm_is_batch_invariant` in `vllm/model_executor/kernels/linear/__init__.py`, with the BF16 fallback in `Fp8LinearMethod.apply`). The FP8 MoE methods did not: `Fp8MoEMethod` (`--quantization fp8` on a BF16 checkpoint, or an FP8 checkpoint with `activation_scheme: dynamic` and no block scales) and `Fp8PerTensorOnlineMoEMethod` (`--quantization fp8_per_tensor`) quantize both expert-GEMM inputs with one scale per batch, and `TritonExperts` advertises batch-invariance support for that configuration. The online bs1-vs-bsN check fails for every such deployment.

This PR selects per-token activation scales for those two methods in batch-invariant mode (`kFp8DynamicTokenSym` instead of `kFp8DynamicTensorSym`, `per_act_token_quant=True`), leaving the per-expert weight scales as they are. The Triton kernel's per-channel branch indexes the weight scale by expert and output channel, so the per-expert scalar scale is handed to it as a broadcast `[E, N]` view (its expert stride was 0 before, which would have read expert 0's scale for every expert). Nothing changes when the flag is off: the keys, flags and launcher strides are the ones used today.

The oracle still refuses backends that do not support `(kFp8StaticTensorSym, kFp8DynamicTokenSym)` under batch invariance (the CUTLASS FP8 experts), as it does for other unsupported pairs.

## Test Plan

One NVIDIA GB300 node, `main` at `ce49c47cbb` vs `main` + this PR, `ibm-granite/granite-3.1-1b-a400m-instruct`, TP=1, `VLLM_BATCH_INVARIANT=1`:

- Online bitwise check (32 prompts, `temperature=0.6`, fixed seed, `max_tokens=8`, each prompt alone vs all 32 in one batched request, per-step top logprobs compared; "standard" and "ragged" prompt sets), `main` on GPU 0 and this PR on GPU 1, for three deployments: `--quantization fp8_per_tensor --moe-backend triton`, `--quantization fp8 --moe-backend triton`, `--quantization fp8` (backend chosen by the oracle), plus a repeat of the first.
- The same online check on a real-size MoE model: `Qwen/Qwen3-30B-A3B` (BF16 checkpoint) with `--quantization fp8`, `main` on GPU 2 vs this PR on GPU 3.
- Cost under `VLLM_BATCH_INVARIANT=1`: `vllm bench throughput` (random dataset, 2000 prompts, seed 0), `main` vs this PR alternating, six runs per side, `--quantization fp8_per_tensor --moe-backend triton`. The second command of each pair passed `--input-len 64 --output-len 256`, but the random dataset's defaults take precedence over those legacy flags (the bench warns about it), so all twelve runs sampled 1024-token prompts with 128 output tokens; the sampled lengths and token totals from each log are included below.
