# [Perf][MRV2] Upload batch indices with one UVA kernel

[Upstream PR](https://github.com/vllm-project/vllm/pull/63211) · state: open · merged: False

## Original PR description



## Overview

Each Model Runner V2 step, `prepare_inputs()` uploads `idx_mapping` and `query_start_loc` (and `cu_num_logits` with drafts) with separate `async_tensor_h2d` calls, each through a new pinned tensor, and with `VLLM_MOE_SKIP_PADDING` fills `is_padding` with extra kernels. The small copies add copy-engine latency that the next kernel waits on. This replaces the copies of `idx_mapping` and `query_start_loc` (and `cu_num_logits` with drafts), plus the padding fills, with a single Triton kernel that reads a pinned staging slot through UVA.

## Claims

- `BatchIndexUploader` stages the host arrays in a pinned slot; a single kernel writes `idx_mapping`, `cu_num_logits`, the whole `query_start_loc` buffer and, when requested, `is_padding`.
- Slots rotate, and an event recorded after each launch retires a slot before the host rewrites it, so async scheduling with any number of steps in flight is safe.
- Outputs, dtypes and values are unchanged. On platforms other than CUDA/ROCm, or without UVA, the existing copies run as before. No new option.

## Validation

Not run yet. Planned:

```bash
pytest -v tests/v1/worker/test_gpu_input_batch_v2.py
```

plus a token-equality check against main and an Nsight trace of a spec-decode step.

## Details

The tests check that the uploader leaves the same device state as the separate uploads, including `query_start_loc` and `is_padding` entries past the padded range, and that wrapping the slot ring waits for a kernel still reading the slot. #62748 removes the per-call pinned allocation for these same three copies with `UvaBufferPool`s; this change removes the copies and fills themselves, so the two touch the same lines and the pinned-staging part of #62748 would no longer be needed.
