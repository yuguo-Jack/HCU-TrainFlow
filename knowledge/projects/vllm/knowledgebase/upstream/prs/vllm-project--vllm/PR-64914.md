# [MRV2] Cap torch.topk rows in chunked prompt logprobs

[Upstream PR](https://github.com/vllm-project/vllm/pull/64914) · state: closed · merged: True

## Original PR description



## Overview

Bound the `torch.topk` workspace in Model Runner V2's chunked prompt-logprobs computation by ranking each logits chunk in row blocks of at most 64M elements. Follow-up to #64841, whose preallocated outputs raised the peak for full-vocab prompt logprobs on short multi-chunk prompts.

## Claims

- Full-vocab prompt logprobs (152k vocab, fp16 logits) peak at **4.98 GiB** for a 2048-row prompt, down from 7.54 GiB before #64841 and 8.12 GiB with it; **11.94 GiB** at 8192 rows, down from 28.12 / 15.07 GiB.
- ~3.5% added latency, for full-vocab prompt logprobs only.
- No change for `k` below ~65k (e.g. the default `max_logprobs=20`): each chunk is still ranked in one `topk` call, with identical latency and peak.

## Validation

GB200, `compute_prompt_logprobs_with_chunking` on a 151936-vocab, 1536-hidden fp16 head, median of 20 runs (5 at full vocab); all variants return identical results:

| rows | k | before #64841 | #64841 (+ early frees) | this PR |
|---|---|---|---|---|
| 2048 | 5 / 20 / 100 / 1000 | — | 3.50 / 3.51 / 3.52 / 3.59 ms | 3.50 / 3.50 / 3.52 / 3.57 ms |
| 2048 | 151936 | 7.54 GiB, 21.7 ms | 8.12 GiB, 21.45 ms | **4.98 GiB, 22.19 ms** |
| 8192 | 5 / 20 / 100 / 1000 | — | 13.76 / 13.77 / 13.81 / 14.06 ms | 13.75 / 13.78 / 13.81 / 14.07 ms |
| 8192 | 151936 | 28.12 GiB, 86.3 ms | 15.07 GiB, 85.56 ms | **11.94 GiB, 88.54 ms** |

Peak memory for k ≤ 1000 is 0.30–0.37 GiB in every variant.

## Details

- `torch.topk` with k near the vocab size sorts each row; its workspace grows with rows × k, ~5.5 GiB for a 1024-row chunk of a 152k vocab, and was the step's peak. #64841 preallocates the whole prompt's outputs after the first chunk, so for a 2-chunk prompt they (plus the previous chunk's still-referenced results) sat on top of the second chunk's `topk`. The per-block results and per-chunk logits are now freed before the next block / chunk.
- Motivation: with measured KV cache sizing (#56492), the sizing warmup's largest prefill requests `max_logprobs` prompt logprobs, and `tests/entrypoints/openai/chat_completion/test_chat_echo.py` (`--max-logprobs 151936`) reserved ~7.5 GiB for this on an 18 GB H200 MIG slice, leaving no KV cache.
- Cap choice: 32M elements gives 3.80 GiB at 2048 rows but +20% latency; 128M would leave the 2048-row peak near 7.3 GiB.
- The Triton top-k/top-p sampler kernel isn't a substitute: it masks below a pivot rather than returning sorted ids, and logprob ranks are assigned by position, so full-vocab requests still need a full sort.
