# [Quantization] Load ModelOpt NVFP4 W4A16 token embeddings in mixed-precision checkpoints

[Upstream PR](https://github.com/vllm-project/vllm/pull/64767) · state: open · merged: False

## Original PR description

## Overview

ModelOpt mixed-precision checkpoints can mark the token embedding `W4A16_NVFP4` in `quantized_layers`, but today only Q8_0 embeddings load (through b12x). This PR adds `ModelOptNvFp4EmbeddingMethod`, which keeps the packed table and dequantizes only the looked-up rows.

## Claims

- **NVFP4 embeddings load and serve.** On `nvidia/NVIDIA-Nemotron-3.5-Bolt-74B-A9B-24GB` with its BF16 embedding re-quantized to NVFP4, weights drop from 23.05 to 22.33 GiB and the KV cache grows 1.5%.
- **No accuracy or speed change:** MMLU-Pro 57.71 vs 57.67 (2,100 questions), and 164.2 / 1134 vs 163.9 / 1140 tok/s at C=1 / C=16.
- **Tied embeddings are rejected**, since the LM head would read packed bytes.
- **Weight reloads keep the lookup table in place**, so captured CUDA graphs stay valid.
- Documented in the ModelOpt quantization page.

## Validation

**Unit test:** `pytest tests/quantization/test_modelopt_nvfp4_embedding.py` gives 2 passed, and it runs in the CPU quantization CI job. It builds a real `VocabParallelEmbedding` through `ModelOptMixedPrecisionConfig`, loads it through `weight_loader`, and compares with `break_fp4_bytes` dequantization at zero tolerance. It also checks the tied-embedding rejection, and that rerunning post-processing (as a weight reload does) keeps the lookup table's address. On `main`:

```
E   ImportError: cannot import name 'ModelOptNvFp4EmbeddingMethod' from 'vllm.model_executor.layers.quantization.modelopt'
```

**End to end:** one RTX PRO 6000, both with #64766 applied. Weights, KV cache and MMLU-Pro on nightly `335dd77b`, reasoning off; throughput on nightly `77154ca6` with genai-perf, 1024 input / 1024 output tokens, mean of 2 runs.

| | BF16 embedding | NVFP4 embedding |
|---|---|---|
| weights | 23.05 GiB | 22.33 GiB |
| KV cache | 7,282,057 tokens | 7,392,964 tokens |
| MMLU-Pro (2,100 q) | 57.67 | 57.71 |
| C=1 tok/s/user, C=16 tok/s | 163.9, 1140 | 164.2, 1134 |

```bash
vllm serve <checkpoint> --trust-remote-code \
  --max-model-len 32768 --max-num-seqs 16 --gpu-memory-utilization 0.80 --enable-chunked-prefill \
  --kv-cache-dtype fp8 --linear-backend b12x --moe-backend b12x --attention-backend FLASHINFER \
  --mamba-backend flashinfer --mamba-ssm-cache-dtype bfloat16 --mamba-cache-dtype bfloat16 \
  --mamba-cache-mode align --limit-mm-per-prompt '{"video":0,"image":0}'
```

The weights, KV cache and MMLU-Pro runs also passed `--no-enable-prefix-caching`.

Not run: TP > 1 on GPU (a two-rank CPU run matched the reference exactly).

## Details

- **Root cause:** `ModelOptMixedPrecisionConfig.get_quant_method` returns an embedding method only for the b12x block codecs, and that method accepts only Q8_0 embeddings, so a `W4A16_NVFP4` embedding fails to load.
- **Relation to #42791:** it also adds NVFP4 weight-only embeddings, but on current main its path fails at startup on this model under torch.compile (`Constraints violated (L['input_ids'].size()[0])`). On CUDA, `dequantize_to_dtype(..., swizzle=False)` goes to `_triton_dequantize_nvfp4`, whose launch config branches on the row count, so Dynamo specializes `input_ids.size(0)`. This PR dequantizes the gathered rows directly and compiles.
