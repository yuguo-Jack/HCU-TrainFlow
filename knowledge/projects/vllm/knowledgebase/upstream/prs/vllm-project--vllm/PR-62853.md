## Original PR description

# [RL] Support partitioned trainer source groups for NCCL M2N

## Summary

This PR builds directly on `main`, which includes merged [#60934](https://github.com/vllm-project/vllm/pull/60934), and addresses [#59840](https://github.com/vllm-project/vllm/issues/59840). It lets a trainer-side producer partition the parameter manifest across disjoint source rank groups while preserving the per-parameter mesh and placement contract. [#60949](https://github.com/vllm-project/vllm/pull/60949) is now stacked above this PR; it is not a prerequisite.

This supports pipeline-parallel and other partitioned trainers where different
trainer ranks own different parameters. It removes the requirement for a
producer to gather or replicate pipeline-owned parameters across one common
trainer group before calling NCCL M2N. A parameter's declared layout may still
require collectives within its owning source group. Each parameter selects one
canonical source group, and vLLM creates one NCCL M2N transfer communicator for
that source group plus all inference workers.

Before this PR, every parameter had to use the same participating trainer-rank
set, even though each parameter could describe a different mesh factorization
over those ranks:

```text
all trainers + all inference workers -> one M2N communicator
```

After this PR, the source declares ordered, disjoint trainer groups and assigns
each parameter to exactly one group:

```text
all trainers + all inference workers -> one metadata/control group

source group 0 + all inference workers -> transfer route 0
source group 1 + all inference workers -> transfer route 1
...
```

Each parameter can still declare its own source mesh and placements over its
assigned group's ordered ranks. vLLM does not infer trainer ownership from
parameter names or from the inference pipeline topology.

The runtime flow is:

```text
source declares groups and parameter ownership
  -> all ranks agree on the source and destination plans
  -> vLLM creates one transfer communicator per source group
  -> each route transfers only its group's parameters
  -> workers load through main's direct or full-fallback destinations
  -> all trainer ranks receive the same round outcome
```

## Stack

The merge order is now:

1. [#60934](https://github.com/vllm-project/vllm/pull/60934) (merged) adds
   general per-parameter source meshes and placements over one common
   participating trainer-rank set.
2. This PR builds directly on main and adds partitioned trainer source groups
   and multi-communicator execution.
3. [#60949](https://github.com/vllm-project/vllm/pull/60949) builds on this PR
   and adds rank-local destination targets, bounded semantic staging, and
   model-native loading callbacks.

This PR retains main's existing destination resolver and does not include the
rank-local target interfaces or `RoutedExperts` integration from #60949.

## Problem

A pipeline-parallel trainer does not hold every parameter on every trainer
rank. For example, one ordered rank group may own the first set of layers while
another group owns the remaining layers.

The previous source contract could express different TP, DP, or EP mesh
factorizations only when every parameter used the same participating trainer
ranks. A partitioned trainer therefore had to normalize ownership first, such
as by gathering or replicating pipeline-owned parameters across one common
group, before calling NCCL M2N.

That normalization adds memory, synchronization, and communication that NCCL
M2N does not otherwise require.

## Design

### Explicit source topology

`M2NWeightSource.source_topology()` returns an `M2NSourceTopology` containing:

- `groups`: ordered trainer-rank groups in the global metadata-group namespace;
  and
- `param_groups`: one canonical source-group index for every parameter in the
  ordered manifest.

The contract requires:

- source groups are non-empty and pairwise disjoint;
- a trainer rank belongs to at most one source group;
- every parameter selects exactly one canonical source group;
- every declared source group owns at least one parameter; and
- each parameter's source mesh covers exactly its assigned group's ordered
  ranks.

Ranks that hold a tied or replicated copy outside the canonical source group do
not transfer that copy. A rank may belong to no source group when it owns no
transferable parameter.

`M2NWeightSource.iter_group(group_index)` yields only that group's local
parameters in their subsequence of global manifest order. Returning `None`
from `source_topology()` preserves the existing single-source-group behavior,
and `iter_group(0)` delegates to the source's normal iterator.

### Transfer routes and collective agreement

For every source group, vLLM derives one ordered transfer route containing:

```text
ordered source-group ranks + all inference-worker ranks
```

All trainers and inference workers still join one metadata/control group. They
collectively agree on the complete source manifest, source topology,
destination placements and direct/full-fallback loading choices,
parameter-to-route mapping, and route membership before constructing any NCCL
M2N communicator. Every rank then independently derives the same deterministic
bounded transfer schedule.

The direct/full-fallback choice must agree as well as placements: a replicated
direct destination and a full fallback can have identical placements but
different loader-order dependencies.

Each transfer route receives its own NCCL unique ID, communicator, and CUDA
stream. Nonmembers process the fixed UID bootstrap and initialization outcome
for every route but do not initialize or enter a communicator they do not
belong to. A single post-initialization agreement reports the outcome of the
complete communicator set.

The wire schema advances from main's version 2 to version 3. Mixed versions fail during metadata
initialization rather than entering an incompatible collective sequence.

Multiple NCCL communicators can have independent host launch order. When a plan
contains more than one transfer route, every process must set:

```bash
NCCL_LAUNCH_ORDER_IMPLICIT=1
```

vLLM validates that requirement collectively before communicator
initialization. The legacy one-route configuration does not require it.

### Bounded transfer schedule

Trainer and inference ranks derive the same deterministic transfer schedule
from the agreed plan. Within each route, parameters retain their manifest
order. Independent routes use separate CUDA streams, and one launch wave can
submit the next ready parameter from multiple routes before waiting.

The scheduler preserves the ordering required by model loading:

- exact in-place destinations need no model-loader ordering dependency; and
- full-fallback destinations retain global manifest loading order.

This permits independent source groups to make progress together without
allocating one receive buffer per parameter. At most one full-fallback receive
buffer remains pending per route. Its transfer stream completes before the
loader reads it, and all route streams drain at the end of the transfer.
Semantic staging and model-consumer ordering are added by #60949.

One parameter still belongs to one canonical source group. This PR does not
split one logical parameter across multiple pipeline source groups.

### Trainer round coordination

Trainer rank zero coordinates `start_weight_update`, `update_weights`, and
`finish_weight_update` with the inference workers. Every trainer rank receives
the same round dispatch and outcome before entering or leaving its local
transfer work.

Each trainer rank participates only in the route for its source group. It
materializes local buffers lazily from `iter_group()`, validates name, order,
dtype, and layout-derived local shape, and retains source-buffer ownership
until its route stream completes.

The trainer control path also fixes `StatelessProcessGroup` object keys to
include both source and destination rank. This prevents simultaneous replies
from multiple trainer ranks to one coordinator from overwriting each other in
the shared store.

### Failure handling

The failure policy distinguishes update-local loader state from M2N transport:

| Failure point | Behavior |
|---|---|
| Worker setup or update validation before its first M2N launch, or a trainer failure known before worker dispatch | Reset update-local layerwise-loader state; preserve communicators; report the original error |
| Failure after worker dispatch, or after an M2N launch may be in flight | Abort every joined transfer communicator without waiting on CUDA streams; require transport reinitialization |
| Loader/finalizer failure after transfer completion | Preserve transport, reset update-local state, and replay the complete update once from `start_weight_update()` |
| Healthy shutdown | Synchronize pending work, destroy the M2N handle, and abort every route communicator |

The replay is coordinated across all trainer ranks. It does not retry a failed
collective or malformed metadata request.

## Compatibility and scope

- Existing sources that do not implement `source_topology()` continue to use
  one group containing every trainer rank.
- Per-parameter source meshes and placements remain model-independent and are
  interpreted over the parameter's assigned source group.
- The current destination remains one configured inference-worker mesh shared
  by all parameters. The contracts preserve room for future per-parameter
  destination meshes over the same worker subset, but that selection is not
  implemented here.
- Destination selection retains main's exact live-tensor and full-fallback
  paths. Fused checkpoint tensors still use full fallback when main cannot
  resolve an exact live target. #60949 adds rank-local destinations and the
  first `RoutedExperts` consumer as a stacked follow-up.
- This PR does not infer Megatron pipeline stages, trainer ownership, or tied
  parameter ownership. A trainer integration supplies that information through
  `M2NSourceTopology`.
- Multiple joined route communicators can increase NCCL M2N runtime staging;
  the exact allocation behavior belongs to the NCCL M2N runtime rather than
  this vLLM contract.

## Performance

These are the original, pre-restack measurements, collected with #60949's
rank-local destination support enabled as well as trainer source groups. They
have not been rerun on this standalone branch. Both M2N methods use the same
rank-local destination support, so their comparison measures grouped versus
sequential execution on that combined stack, not this branch's full-fallback
performance.

This synthetic microbenchmark compares sequential and grouped execution of
partitioned-source weight transfers. It uses the production vLLM trainer and generator
transfer engines and data plane with Qwen-shaped BF16 fused-expert tensors. The
Qwen configurations provide tensor shapes and scale only; the source-group
design is model-independent.

### Setup

| Profile | Trainer topology | Inter-role transport | Generator topology | Logical payload |
| --- | --- | --- | --- | ---: |
| Qwen3-30B-A3B-shaped | 1 node / 4 GB200, PP2 with two 2-rank source groups, one NVLink domain | InfiniBand | 1 node / 4 GB200, EP4, separate NVLink domain | 54 GiB |
| Qwen3-235B-A22B-shaped | 4 nodes / 16 GB200, PP2 with two 8-rank source groups, one NVLink domain | InfiniBand | 4 nodes / 16 GB200, EP16, separate NVLink domain | 423 GiB |

Topology probes confirmed NVLink/MNNVL communication within each role and
InfiniBand/GDRDMA between trainer and generator roles.

Three transfer paths were compared:

- **NCCL all-gather + broadcast:** each PP group performs its required trainer
  all-gather, uses the production packed NCCL broadcast, and the synthetic
  model's `load_weights` path selects the local EP shard.
- **Sequential M2N:** two preinitialized single-group engines are reused. Each
  measured update runs two sequential `start_weight_update` → `update_weights`
  → `finish_weight_update` lifecycles with required synchronization after each.
- **Grouped M2N (this PR):** one preinitialized two-group plan and its two
  transfer communicators are reused. Each measured update uses one shared
  reload lifecycle and the grouped transfer schedule.

![Synthetic expert-transfer latency](https://raw.githubusercontent.com/pkousha/vllm/569c200370715260e00df0111b6a64d13298af85/pr-assets/nccl-m2n-pp-grouped-summary.png)

Each value is the mean ± sample standard deviation of 10 warm updates; the first
cold update is excluded.

| Profile | NCCL all-gather + broadcast | Sequential M2N | Grouped M2N | Grouped speedup vs. sequential |
| --- | ---: | ---: | ---: | ---: |
| 2 nodes / 54 GiB | 0.6085 ± 0.0026 s | 0.6461 ± 0.0008 s | **0.3360 ± 0.0004 s** | **1.92×** |
| 8 nodes / 423 GiB | 4.6593 ± 0.0045 s | 1.2785 ± 0.0015 s | **0.6741 ± 0.0034 s** | **1.90×** |

The direct comparison for this PR is grouped M2N versus sequential M2N:
**1.92×** faster on the 2-node profile and **1.90×** faster on the 8-node
profile. This combines coordinated source-group scheduling with eliminating one
reload lifecycle and its required synchronization; the benchmark does not
independently isolate transfer overlap.

Grouped M2N was also **1.81×** faster than NCCL on the 2-node profile and
**6.91×** faster on the 8-node profile. That broader comparison includes
M2N's owner-local transfer instead of NCCL's trainer all-gather, full broadcast,
and generator-local slicing, so it is not solely the effect of this PR.

![Sequential versus grouped M2N schedule](https://raw.githubusercontent.com/pkousha/vllm/569c200370715260e00df0111b6a64d13298af85/pr-assets/nccl-m2n-pp-grouped-schedule.png)

The schedule widths are normalized to each method's end-to-end time; phase
measurements were collected independently and are explanatory rather than an
additive decomposition.

<details>
<summary>Timing boundary and benchmark scope</summary>

The timed boundary includes the required trainer all-gathers for NCCL, transfer,
destination loading or callbacks, CUDA completion, reload lifecycle calls, and
required synchronization. One-time setup and communicator initialization are
excluded.

The M2N paths use a synthetic `ShardedWeightTarget` callback. The NCCL path
uses the benchmark's synthetic model `load_weights` implementation to select
the local EP slice after the production packed broadcast. The benchmark uses a
Gloo control plane and production NCCL/M2N GPU data paths.

The benchmark excludes source-buffer fill, correctness validation, checkpoint
loading, optimizer work, generation, and RL execution. It exercises
Qwen-shaped tensors, not an instantiated Qwen or `RoutedExperts` model.

Each profile was measured in one job using the fixed order NCCL → sequential
M2N → grouped M2N. The reported standard deviation describes within-job
variation across the 10 warm updates, not variation across independent jobs.

### Real SkyRL workload

The production path was also measured with Qwen3-235B-A22B in a real GSM8K
GRPO workload: no LoRA, full fine-tuning, 16 GB200 trainers with
TP4/PP2/EP8 and two 8-rank parameter-owner groups, and 16 GB200 generators
with DP16/EP16. The trainer and generator roles occupied separate NVLink
domains connected by InfiniBand. SkyRL's NCCL rank-zero broadcast and grouped
M2N ran back-to-back in the same allocation with otherwise identical software,
model, optimizer, and runtime configuration.

![Real M2N comparison with PP support](https://raw.githubusercontent.com/pkousha/vllm/bf4fc740be7de8e7790715985619fac7d2dd2115/pr-assets/nccl-m2n-real-pp-performance.png)

Each reported mean retains all 10 warm synchronizations after excluding one
cold synchronization; every warm synchronization followed an optimizer update.
Mean weight-sync E2E fell from **29.345 s to 3.716 s (7.90x)**, and mean total
generator-unavailable time fell from **29.400 s to 3.772 s (7.79x)**.
Weight-sync E2E includes trainer extraction/conversion and required collectives,
trainer-to-generator transfer, receiver update, and finish. Total unavailable
also includes generator pause/resume and the outer wrapper.

### Real SkyRL workload with trainer PP4

A separate Qwen3-235B-A22B GSM8K GRPO experiment used no LoRA and
full-parameter BF16 fine-tuning. NCCL broadcast and grouped M2N ran back-to-back
in the same eight-node allocation with identical software and workload
settings; only the weight-sync backend changed.

| Configuration | Value |
|---|---|
| Hardware | 8 nodes, 4 GB200 GPUs per node; 16 trainer and 16 generator GPUs |
| Trainer | TP4 / PP4 / CP1 / EP4 / ETP1 / EDP1; four disjoint 4-rank source groups |
| Generator | TP1 / PP1 / DP16 / EP16 / EDP1 |
| Topology | NVLink/MNNVL within each role; InfiniBand/GDRDMA between roles |
| Sampling per backend | 21 records: one initial synchronization excluded and 20 measured synchronizations after optimizer updates |

All optimizer-progress, memory, generator-backend, topology, and comparison
gates passed. All 20 measured samples are retained; the mean is the primary
statistic.

| Timing boundary | NCCL broadcast | Grouped M2N | Improvement |
|---|---:|---:|---:|
| Mean weight-sync E2E | 48.987 s | 5.115 s | 9.58×; 89.6% lower |
| Mean total generator-unavailable time | 49.041 s | 5.170 s | 9.49×; 89.5% lower |

![Real Qwen3-235B-A22B PP4 weight-sync comparison and timing boundaries](https://raw.githubusercontent.com/pkousha/vllm/efd704ca72fa3d6075392f159ff05f263b143137/pr-assets/nccl-m2n-real-pp4-performance.png)

The timing boundaries are the same as in the PP2 experiment above. Extraction,
required collectives, M2N transfer, and receiver loading overlap inside
`update_weights`; the figure's overlapping lanes are not independent phase
measurements.

Like the PP2 results, this run measured the pre-restack combined stack,
including #60949's rank-local destination support. It does not measure the
standalone main-based #62853 full-fallback path. PP2 and PP4 are separate
experiments; each reported speedup compares backends within its own experiment.
