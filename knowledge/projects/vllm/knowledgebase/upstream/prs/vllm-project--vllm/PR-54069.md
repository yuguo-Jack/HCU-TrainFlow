# [Model] Migrate Gemma4DSpark to AutoWeightsLoader

[Upstream PR](https://github.com/vllm-project/vllm/pull/54069) · state: open · merged: False

## Original PR description

Part of the ongoing effort tracked in #15697 to standardize weight loading
across all model backbones onto `AutoWeightsLoader`.

`Gemma4DSparkForCausalLM.load_weights` hand-rolled its own weight-name
matching and manually stacked `gate_proj`/`up_proj` into `gate_up_proj` by
iterating `named_parameters()` / `named_buffers()` directly. This replaces
that with `AutoWeightsLoader`:

- `Gemma4DSparkModel` gets its own `hf_to_vllm_mapper` that stacks only
  `gate_proj`/`up_proj` into `gate_up_proj`. `AutoWeightsLoader` delegates
  the `model.*` subtree to the inherited `DFlashQwen3Model.load_weights`,
  whose mapper also fuses `q_proj`/`k_proj`/`v_proj` into `qkv_proj`.
  Gemma4 DSpark attention keeps `q_proj`/`k_proj` separate, so that mapper
  can't be inherited as-is.
- The flat checkpoint layout is adapted by a small generator that adds a
  `model.` prefix to everything except `lm_head`.
- The confidence-head handling added in #57263 is preserved: its weights
  load when the config enables the head, are dropped when the config
  disables it, and the head is set to `None` when the config enables it but
  the checkpoint does not ship it.
- `load_weights` still calls `self.model._build_fused_kv_buffers()`
  afterward.

**One intentional behavior difference:** the old loop silently ignored
checkpoint keys that matched no parameter; `AutoWeightsLoader` raises on
them. I checked the reference checkpoint `deepseek-ai/dspark_gemma4_12b_block7`
(from `tests/models/registry.py`): all 74 tensors map to a parameter or a
persistent buffer (`layer_scalar`), including `confidence_head.proj.*`, so it
is unaffected.

Rebased onto current `main`, including #57263 (confidence head) and #57797
(which removed `DFlashQwen3Model._preprocess` but kept the inherited mapper).

## Testing

On CPU, with a throwaway harness (not included in this PR):

- Built `Gemma4DSparkForCausalLM` from the real
  `dspark_gemma4_12b_block7` `config.json`, shrunk to toy dimensions with 2
  real decoder layers, and loaded random tensors under the checkpoint's real
  key names. Every tensor, including each half of `gate_up_proj`, lands in
  the right parameter with the right values. The same harness passes
  against the current `main` loader. A mutation (swapped `gate`/`up` shard
  ids) makes it fail as expected.
- An earlier revision of this PR put the mapper on
  `Gemma4DSparkForCausalLM`. This harness showed it failing with
  `There is no module or parameter named 'layers.0.self_attn.qkv_proj'`,
  which is what led to the fix above.
- The four confidence-head cases from
  `test_gemma4_dspark_loads_confidence_head` pass, including
  `compute_confidence`. The upstream test itself also passes its loading
  assertions on CPU. Its `compute_confidence` step fails on CPU with
  `'ReplicatedLinear' object has no attribute 'cpu_linear'`, identically
  on `main`, because the test doesn't run the post-load weight processing
  the CPU GEMM path needs. My harness swaps in `F.linear` for that step.
- `ruff check` / `ruff format` (0.14.0), `typos`, `check-spdx-header`,
  `check-forbidden-imports`, `check-torch-cuda-call`,
  `check-boolean-context-manager`, and `mypy` via
  `tools/pre_commit/mypy.py` (in an environment matching the hook's
  dependencies) pass on the changed file.
- Not yet run end-to-end on a GPU. The gemma4 case of
  `tests/v1/e2e/spec_decode/acceptance_rates/dspark/test_dspark.py` would be
  the definitive check.
