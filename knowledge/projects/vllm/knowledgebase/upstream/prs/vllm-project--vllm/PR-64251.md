# [Bugfix][KV Offload][P2P] Fault a peer whose source WRITE stalls

[Upstream PR](https://github.com/vllm-project/vllm/pull/64251) · state: closed · merged: True

## Original PR description



## Overview

Part of #63602 (gap 2, source half). Builds on #64250 (merged), which retains the stalled transfer across the teardown this fault triggers. One commit on main (`ffaa825b33`).

A source WRITE that NIXL keeps reporting as `PROC`/`PEND` past `VLLM_P2P_TRANSFER_STALL_TIMEOUT_S` (default 20 s) now faults its peer. The fault releases nothing.

## Claims

- A stalled source transfer faults its peer and ends the session. Before this change, nothing ever faulted it, and `write_blocks()` kept posting new WRITEs to the wedged peer.
- The fault releases nothing. The stalled transfer and its pins are retained across teardown (#64250) until the transport reports it stopped.
- A stall fault skips the 10 s peer-fault drain, since a stalled transfer would never drain.

## Validation

## Details

**Root cause.**
- `NixlTransport.poll()` treats `PROC`/`PEND` as "wait" forever.
- `_drain_abort` holds a stuck transfer and its AbortAck forever, and only logs after 10 s.
- Nothing records when a transfer was submitted, so nothing faults the peer.
- `write_blocks` is gated only on `peer_fault`, so the source keeps feeding the wedged peer.

In the GPU run in #63602, 36 WRITEs never completed, and pulls from a *healthy* peer dropped (679/847).

**Change.**
- `_InflightXfer.submitted_at` is set on submit.
- `ServerRole.collect_results()` checks for stalls when the transport reports no fault. Once the oldest in-flight transfer is past the timeout, it sets `peer_fault = "transfer stalled for Ns"` and `transfer_stalled`.
- Everything after that is the existing #60374 path: no new WRITEs, `_escalate_peer_fault` then `DisconnectMsg` (the consumer fails its loads), reap, and the data-plane reconnect backoff.
- `_escalate_peer_fault` skips its drain wait when `transfer_stalled` is set.

Detection lives in `ServerRole`, not `NixlTransport`. It sits next to the `_STORE_TIMEOUT_S` logic it mirrors, it doesn't depend on which transport is used, and the session reproducers exercise it directly.

**Why it depends on #64250.** Without retention, the teardown this fault triggers would run `cancel(mode="immediate")` and unpin the stalled transfer's blocks. That is the very release the deadline must not cause.

**New env var** `VLLM_P2P_TRANSFER_STALL_TIMEOUT_S` is a float, default 20, and 0 disables it. It is documented in `vllm/envs.py` and in the P2P table in `docs/usage/security.md`, next to the other `VLLM_P2P_*` limits.

Complexity: about 40 non-test lines.

File: `vllm/v1/kv_offload/tiering/p2p/session/server.py` · line 1259

Thanks. I think measuring age since submit is the right call. The reorder for comment 1 (e260881df9) takes care of most of the scheduler-stall case, and the rest is safe.

**What the reorder covers.** The stall check now runs after the `done`/`failed` drain. Say the scheduler doesn't poll for longer than the timeout. Every WRITE that finished during the gap comes back in that next `poll()` and is drained as done before `_check_stalled_transfers` looks at the oldest in-flight transfer. Missed polls don't hold transfers up either: UCX runs its own progress threads, so WRITEs keep going while nobody polls. So a scheduler stall no longer faults sessions whose WRITEs actually finished. The fault fires only if a WRITE is still PROC/PEND, by a fresh state read, more than 20s after submit. On a healthy lane that's milliseconds of work, so we treat it as a real stall wherever the time went.

**Why per-poll progress doesn't help.** NIXL only gives us a transfer's state, not how many bytes have moved. Between two polls a pending WRITE looks the same whether it is moving or wedged. "Progress between polls" would just mean "still PROC/PEND". That's what the check already tests, and it uses fresh state.

**Why the fault is safe.** The stall check never releases anything on a timer; it only marks the peer faulted. Every release after that goes through a fresh state read:
- **Teardown:** `close()` cancels with `mode="wait"`. That checks `check_xfer_state` per transfer and releases only DONE/ERR. A WRITE still PROC/PEND is retained, with its source pins, not freed.
- **Hold cap:** `_poll_retained` calls `poll_retired()` (another state read) before its 30s cap force-releases anything. Only transfers still running after that read are released.
- **Abort drain and store timeout:** both cancel with `mode="wait"` too.

The only release that skips the state check is the shutdown drain's `mode="immediate"` fallback, and it runs only after its own wait-and-poll loop has timed out.

So even a fault after a long gap can't release a WRITE that might still be landing. At worst, a session whose WRITE is still pending after the gap gets torn down. That's what the stall timeout is for.


- liranschour · comment · 2026-10-29T11:19:17Z · [source](https://github.com/vllm-project/vllm/pull/64251#discussion_r4411670325)

File: `vllm/v1/kv_offload/tiering/p2p/session/server.py` · line 1259

I'd rather keep the age-since-submit measure. There are two kinds of polling gap:

1. **The scheduler thread is busy but the process runs.** NIXL's progress thread and the UCX worker threads (`num_threads=4`) keep the WRITE moving without us polling. After the reorder in e260881df9, anything that completed during the gap is drained before the stall check. A transfer still PROC/PEND 20s after submit had 20s of real progress time, so faulting it is correct.
2. **The whole process is frozen (SIGSTOP, VM pause).** We can't tell this apart from a stall, and we don't need to: the session is lost either way. The peer's ZMQ heartbeat (10s) drops us and the consumer's load timeout aborts the fetch. Clamping the gap would keep a session alive that the peer has already reaped, and only delay our own teardown.

In both cases the fault releases nothing. Teardown and the hold cap re-read transfer state before releasing anything, so there's no correctness risk in calling the transfer stalled.
