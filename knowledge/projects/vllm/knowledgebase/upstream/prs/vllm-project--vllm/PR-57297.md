# [XPU] limit FA kernel block size to multipleOf 64

[Upstream PR](https://github.com/vllm-project/vllm/pull/57297) · state: closed · merged: True

## Original PR description




## Purpose
On XPU platform, `flash_attn_varlen_func` prefers `block_size` multipleOf 64 from performance perspective and we originally respect it by adding path in [`get_preferred_block_size`](https://github.com/vllm-project/vllm/blob/main/vllm/v1/attention/backends/flash_attn.py#L323). But as introduction of [`prepare_kernel_block_size`](https://github.com/vllm-project/vllm/blob/main/vllm/v1/worker/utils.py#L458), the final kernel block size changes to small numbers such as 16, 32 which are not actually preferred ones on XPU platform. This PR enforces the preference and adds warning if final kernel block size is not as expected.

Take `Microsoft/Phi-3.5-mini-instruct` for example, #53007 caused final kernel_block_size changed to `16` from previous `64`, as it picks primary block size for SWA layers which changes KV cache Spec info. XPU will follow the `prepare_kernel_block_size` flow but inject specific logic like [update_block_size_for_backend](https://github.com/vllm-project/vllm/blob/main/vllm/platforms/xpu.py#L425), [get_preferred_block_size](https://github.com/vllm-project/vllm/blob/main/vllm/v1/attention/backends/flash_attn.py#L373), and here `get_preferred_kernel_block_size`.

## Test Plan
```
python3 examples/basic/offline_inference/generate.py --model Microsoft/Phi-3.5-mini-instruct  --enforce-eager --max-model-len 4096 --trust_remote_code 
```

## Test Result
previous without `multipleOf[64]` limitation, it will use kernel block-size `16`:
```
(EngineCore pid=14829) WARNING 09-17 03:28:59 [attn_utils.py:259] On XPU platform, current selected kernel block size is not fully optimized: kernel_block_size=16, backend=<class 'vllm.v1.attention.backends.flash_attn.FlashAttentionBackend'>, kv_cache_spec=SlidingWindowSpec(block_size=16, num_kv_heads=32, head_size=96, dtype=torch.bfloat16, head_size_v=96, kv_quant_mode=<KVQuantMode.NONE: 0>, page_size_padded=None, num_head_slots=None, state_content_bytes=None, tokens_per_state=1, sliding_window=262144, extra_retained_tokens=0)
```
after:
No warning happens indicating that block size `64` is used.
**Note that if user explicitly sets block size using `--block-size 16`, it will be respected and warning will be printed.**

- yma11 · comment · 2026-09-29T08:04:59Z · [source](https://github.com/vllm-project/vllm/pull/57297#issuecomment-5886197535)

> I know this patch can resolve issue. but I am not much clear the cause and impact scope of why/what block size will be due to previous code change. hope you can investigate more to make thing clear.

Final `kernel_block_size` is determined involving steps like 1) decide logical KV cache manager block size, differs by platform and attention backend 2) build KV cache groups, varies by model layer types and num of layers 3)Select `kernel_block_size` per group 3) Virtual splitting if needed. **Any logic change in these steps may cause final `kernel_block_size` change.** XPU follows this workflow and specify its support by adding path in [update_block_size_for_backend](https://github.com/vllm-project/vllm/blob/main/vllm/platforms/xpu.py#L425), [get_preferred_block_size](https://github.com/vllm-project/vllm/blob/main/vllm/v1/attention/backends/flash_attn.py#L373), and here get_preferred_kernel_block_size.

This PR limits the kernel block size to `multipleOf[64]` which is perf friendly to kernel and can avoid unexpecting config missing in kernel side. This is also a practice that XPU follows before but just `prepare_kernel_sizes` breaks it.
