# [Bugfix][CPU] Resolve the process cgroup when reading the memory limit

[Upstream PR](https://github.com/vllm-project/vllm/pull/64104) · state: open · merged: False

## Original PR description

## Issue

`get_cgroup_memory_limit()` and `get_cgroup_memory_usage()` read `/sys/fs/cgroup` only. They miss a limit on the process cgroup or on a parent. The CPU backend then sizes the KV cache and the SHM buffers from host RAM. Fixes #64103.

## Fix

- Read `/proc/self/cgroup`. Walk from the process cgroup up to the root.
- `get_cgroup_memory_limit()` returns the smallest limit on that path.
- `get_cgroup_memory_usage()` returns usage such that `limit - usage` is the smallest free headroom of all limited cgroups. A parent limit also counts its other children. The callers do not change.
- Find the cgroup mount in `/proc/self/mountinfo`. Of the mounts that contain the process cgroup, use the one with the shortest root, so every parent limit is visible.
- Off by default. `RESOLVE_PROCESS_CGROUP_BY_DEFAULT = False` sets the default in one line. `VLLM_RESOLVE_PROCESS_CGROUP=1` or `=0` overrides it. Its comment in `vllm/envs.py` generates the docs.

## Effect

Three callers read these two functions. With `VLLM_RESOLVE_PROCESS_CGROUP=1` they see the limit of the process cgroup instead of the root:

- `get_memory_node_info()`: the CPU worker's KV-cache budget (`total_memory × gpu_memory_utilization`) and its available-memory check; also `CpuPlatform.get_device_total_memory()` and the CPU `mem_get_info` stand-in.
- `_get_available_ram_bytes()` in `weight_utils.py`: whether the checkpoint fits in 90% of available RAM, which decides safetensors prefetch on a network filesystem.
- `check_cgroup_memory_available()`: the SHM preflight log.

With the variable unset, every caller gets the values of `main`. With no cgroup limit, both functions return `None` as before and the callers use host RAM (rows 1 and 2 below).

```sh
#!/bin/sh
# Needs rootful Docker. Row 10 also needs systemd, sudo and python3 on the host.
set -eu
REF=${1:?git ref, e.g. main or refs/pull/64104/head}
IMG=python:3.12-slim
W=$(mktemp -d)
trap 'rm -rf "$W"' EXIT
for f in utils/cpu_resource_utils envs; do
  curl -fsSL --create-dirs -o "$W/src/vllm/$f.py" \
    "https://raw.githubusercontent.com/vllm-project/vllm/$REF/vllm/$f.py"
done
# vllm/__init__.py and vllm/logger.py are stubs, so no torch install is needed.
: > "$W/src/vllm/__init__.py"
: > "$W/src/vllm/utils/__init__.py"
echo 'import logging; init_logger = logging.getLogger' > "$W/src/vllm/logger.py"

cat > "$W/probe.py" <<'EOF'
import vllm.utils.cpu_resource_utils as c
limit, usage = c.get_cgroup_memory_limit(), c.get_cgroup_memory_usage()
free = None if limit is None or usage is None else limit - usage
f = lambda v: "None" if v is None else f"{v >> 20} MiB"
print(f"limit {f(limit):>8}   free {f(free):>8}")
EOF

cat > "$W/case.sh" <<'EOF'
set -e
C=/sys/fs/cgroup
P="env PYTHONPATH=/w/site:/w/src VLLM_RESOLVE_PROCESS_CGROUP=1 python3 /w/probe.py"
V=1; [ -f $C/cgroup.controllers ] && V=2
mk() {
  if [ $V = 1 ]; then
    mkdir -p $C/memory/pod/app; echo $$ > $C/memory/pod/app/cgroup.procs
  else
    grep -qx '0::/' /proc/self/cgroup
    mkdir -p $C/pod/app; echo $$ > $C/pod/app/cgroup.procs
    echo "+memory" > $C/cgroup.subtree_control; echo "+memory" > $C/pod/cgroup.subtree_control
  fi
}
mem() {
  if [ $V = 1 ]; then echo $(($2 << 20)) > $C/memory/$1/memory.limit_in_bytes
  else echo $(($2 << 20)) > $C/$1/memory.max; fi
}
hide() {
  exec unshare -C -m sh -ec "if [ $V = 2 ]; then umount -l $C; mount -t cgroup2 none $C
    else umount -l $C/memory; mount -t cgroup -o memory none $C/memory; fi
    exec $P"
}
case $1 in
  nocgroup) mount -t tmpfs none $C ;;
  self)   mk; mem pod/app 256 ;;
  parent) mk; mem pod 512 ;;
  both)   mk; mem pod 512; mem pod/app 768 ;;
  hidden) mk; mem pod 512; hide ;;
esac
exec $P
EOF

docker pull -q $IMG >/dev/null
docker run --rm --user "$(id -u):$(id -g)" -v "$W:/w" $IMG \
  pip install -q --no-cache-dir --disable-pip-version-check --root-user-action=ignore --target /w/site psutil regex

row() {
  l=$1; c=$2; shift 2
  printf '%-58s %s\n' "$l" "$(docker run --rm --privileged -v "$W:/w:ro" "$@" $IMG sh /w/case.sh "$c")"
}
echo "$REF, cgroup v$(docker info -f '{{.CgroupVersion}}')"
row "1. no cgroup mounted"                                   nocgroup
row "2. no limit (node)"                                     -
row "3. container 1 GiB (Kubernetes container limit)"        - --memory=1g
row "4. container 1 GiB; process 256 MiB"                    self --memory=1g
row "5. container 1 GiB; parent 512 MiB"                     parent --memory=1g
row "6. container 1 GiB; parent 512 MiB; process 768 MiB"    both --memory=1g
row "7. parent 512 MiB, hidden (Kubernetes pod limit)"       hidden
row "8. as 3, host cgroupns"                                 - --memory=1g --cgroupns=host
row "9. as 4, private cgroupns"                              self --memory=1g --cgroupns=private
if command -v systemd-run >/dev/null; then
  printf '%-58s %s\n' "10. systemd unit, MemoryMax=256M, no Docker" \
    "$(sudo systemd-run -q --scope -p MemoryMax=256M \
       env PYTHONPATH="$W/site:$W/src" VLLM_RESOLVE_PROCESS_CGROUP=1 python3 "$W/probe.py")"
fi
```

```sh
#!/bin/sh
# Before/after check of vLLM's cgroup memory readers inside cgroups. Needs Docker with cgroup v2.
#   sh check_cgroup_memory.sh <before git ref spec> <after git ref spec>
# Example:
#   sh check_cgroup_memory.sh "git+https://github.com/vllm-project/vllm@main" \
#                             "git+https://github.com/prabhkodes/vllm@fix/cgroup-memory-limit-hierarchy"
set -eu
docker run --rm -i --privileged --cgroupns=private --memory=3g ${EXTRA_DOCKER_ARGS:-} \
  -e BEFORE="${1:?before spec}" -e AFTER="${2:?after spec}" python:3.12-slim sh -s <<'INNER'
set -e
export DEBIAN_FRONTEND=noninteractive VLLM_USE_PRECOMPILED=1 VLLM_TARGET_DEVICE=cpu
apt-get -qq update >/dev/null 2>&1 && apt-get -qq install -y git >/dev/null 2>&1
pip install -q uv >/dev/null 2>&1
cat > /tmp/probe.py <<'PY'
import vllm.utils.cpu_resource_utils as c
limit, usage = c.get_cgroup_memory_limit(), c.get_cgroup_memory_usage()
fmt = lambda v: "None" if v is None else f"{v >> 20} MiB"
free = None if limit is None or usage is None else limit - usage
print(f"{fmt(limit):>10} {fmt(free):>10}")
PY
cat > /tmp/hold.py <<'PY'
import time
b = b"\x01" * (1024 << 20)
time.sleep(3600)
PY
C=/sys/fs/cgroup
mkdir -p $C/init; for p in $(cat $C/cgroup.procs); do echo $p > $C/init/cgroup.procs 2>/dev/null || true; done
echo "+memory" > $C/cgroup.subtree_control
mkdir -p $C/nested; echo $((1024 << 20)) > $C/nested/memory.max
mkdir -p $C/shared; echo $((1536 << 20)) > $C/shared/memory.max; echo 0 > $C/shared/memory.swap.max
echo "+memory" > $C/shared/cgroup.subtree_control
mkdir -p $C/shared/sibling $C/shared/me; echo $((1280 << 20)) > $C/shared/me/memory.max
run() {
  printf "%-7s %-52s" "$1" "$2"
  sh -c "echo \$\$ > $C/$3/cgroup.procs; VLLM_RESOLVE_PROCESS_CGROUP=1 exec python /tmp/probe.py 2>/dev/null"
}
for v in before after; do
  if [ $v = before ]; then spec=$BEFORE; else spec=$AFTER; fi
  uv pip install -q --system --torch-backend=cpu "vllm @ $spec" >/dev/null 2>&1
  # The install leaves gigabytes of page cache, which memory.current counts as used.
  sync; echo 1 > /proc/sys/vm/drop_caches
  if [ $v = before ]; then
    sh -c "echo \$\$ > $C/shared/sibling/cgroup.procs; echo -1000 > /proc/self/oom_score_adj; exec python /tmp/hold.py" &
    sleep 3
    printf "%-7s %-52s %10s %10s\n" "" "process cgroup (container limit 3 GiB)" "limit" "limit-usage"
  fi
  run $v "A. container root" init
  run $v "B. child cgroup, limit 1 GiB" nested
  run $v "C. child 1280 MiB; parent 1.5 GiB, sibling 1 GiB" shared/me
done
INNER
```

Supplementary AI-assisted check of `f9562474`: the ordinary nested-limit and sibling-headroom cases pass, but I found a remaining multiple-mount case.

When both the full hierarchy and a bind-mounted child subtree are readable, `_cgroup_mount()` chooses the most specific root. Walking only that mount then misses a tighter parent available through the full hierarchy. A child limit does not override its ancestor's limit ([kernel hierarchy semantics](https://docs.kernel.org/admin-guide/cgroup-v2.html#what-is-cgroup)).

Appending this case to your existing test file reproduces it in both mount orders:

```python

    mounts = [
        "40 25 0:30 / /mnt/main rw - cgroup2 cgroup2 rw\n",
        "41 25 0:30 /pod/ctr /mnt/ctr rw - cgroup2 cgroup2 rw\n",
    ]
    _stub_files(monkeypatch, {
        _PROC_SELF_CGROUP: "0::/pod/ctr\n",
        _PROC_SELF_MOUNTINFO: "".join(mounts[::-1] if reverse else mounts),
        "/mnt/main/memory.max": "max\n",
        "/mnt/main/pod/memory.max": str(512 << 20),
        "/mnt/main/pod/memory.current": str(256 << 20),
        "/mnt/main/pod/ctr/memory.max": str(1024 << 20),
        "/mnt/main/pod/ctr/memory.current": "0\n",
        "/mnt/ctr/memory.max": str(1024 << 20),
        "/mnt/ctr/memory.current": "0\n",
    })
    limit = cru.get_cgroup_memory_limit()
    assert limit == 512 << 20
    assert limit - cru.get_cgroup_memory_usage() == 256 << 20
```

Both fail with `1073741824 != 536870912`. An independent temporary-file fixture with an actual symlink alias gives the same result; without the alias, the nested and sibling controls pass. Could ancestor discovery retain the readable full-hierarchy view rather than stopping at the selected subtree?

Separately, running the unchanged `-k cgroup` selection gave **24 passed, 1 failed, 6 deselected** in a cgroup-v2-limited container. The v1 co-mount fixture doesn't stub `_V2_LIMIT_PATH`, so `_stub_files()` falls through to the container's real `memory.max` (2 GiB), which wins before the simulated v1 limit (1 GiB). This looks like fixture leakage, separate from the multiple-mount case.
