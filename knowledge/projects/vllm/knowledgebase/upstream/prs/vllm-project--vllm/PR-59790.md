# [Bugfix][KV Offload][P2P] Keep store pins until inflight transfers settle

[Upstream PR](https://github.com/vllm-project/vllm/pull/59790) · state: open · merged: False

## Original PR description

## Overview

Keep P2P store slots pinned until a timed-out transfer has stopped, and actively request cancellation instead of merely skipping inflight jobs. Addresses #59569 and the review on #59790.

## Claims

- Expired store rounds request `cancel(mode="wait")`; only confirmed cancellations or terminal transport results release their jobs.
- Late completions fail the expired round exactly once. Remaining transfers retain pins, and new supply cannot restart that round.
- Consumer aborts cannot force-release a timed-out round's unconfirmed transfers through the existing immediate-cancel fallback.

## Details

The original `continue` prevents freeing memory under a running write but leaves a stuck `PROC` transfer without an active cancellation attempt. This follow-up marks the round expired, cancels all its transfers, and keeps retrying cancellation even after the originally expired job has settled. A job shared by multiple transfers remains pinned until none still reference it.

`cancel(mode="wait")` can return IDs whose cancellation is still pending. Calling it is not proof that the writes stopped. Consequently, this change does not claim an unconditional lifetime bound: if NIXL never confirms cancellation and never reports a terminal state, preserving memory safety still requires retaining pins. A hard deadline would require a stronger transport guarantee.

The two originally removed late-completion/late-failure tests represented releasing active slots before a subsequent transport result. Their replacements cover cancellation requested, pins retained, then cancellation confirmation or late terminal completion/failure, with no duplicate result. Additional regressions cover a never-completing transfer, multiple transfers in one round, late supply, and consumer abort during pending cancellation.

This is distinct from #59329, which withdraws timed-out parked supply before Fetch. Its withdrawal set must be derived from actual emitted results (`{r.job_id for r in results}`), so unconfirmed inflight jobs are not removed from the round's pending jobs. This PR does not duplicate that withdrawal implementation; whichever PR merges second needs that integration adjustment.

- sohom-cs · COMMENTED · 2026-10-03T22:56:59Z · [source](https://github.com/vllm-project/vllm/pull/59790#pullrequestreview-5403289472)

Thanks for picking this up. I hit the neighbouring case in #59329, and I checked this against `server.py` on main.

1. **Liveness of a stuck transfer.** Before this change, the 30 s store timeout was an (unsafe) backstop: it eventually released the pins even if the transfer never finished. With the `continue`, an inflight job is only settled by `transport.poll()` reporting it done or failed. `NixlTransport.poll` reports failure only when `check_xfer_state` returns something other than `DONE`/`PROC`/`PEND`. If a transfer stays in `PROC` (a peer that died mid-write, or a hung RDMA path), nothing ever settles the job: the primary slots stay pinned and the round never finalizes. Could the timeout cancel the transfer instead of skipping it? For example, `self._transport.cancel([tid], mode="wait")` and then fail the round, the first option in #59569. With `mode="wait"` the handle is released only after NIXL confirms the abort, so the slots still aren't freed under a running write, and the job gets a bounded lifetime. If you'd rather rely on a transport-level deadline, a test showing what bounds a stuck `PROC` transfer would help.

2. **Interaction with #59329.** #59329 adds a pass right after this loop that withdraws the timed-out jobs from each round's `available` and `pending_job_ids`, using `set(timed_out)`. With your `continue`, `timed_out` would also contain the skipped inflight jobs, and withdrawing those from `pending_job_ids` while their transfer is still running would be wrong. Whichever lands second should build that set from the jobs that actually produced a `StoreResult` (`{r.job_id for r in results}`). I'm happy to adjust #59329 if this one merges first.

3. **Tests.** The two removed tests (`..._late_completion_no_duplicate` / `..._late_failure_no_duplicate`) covered "timed out, then the transport reports". That sequence can't happen for an inflight job anymore, so dropping them makes sense. A short note in the description saying so would help reviewers. The new parametrized test reads well. One more case worth adding is "inflight job past the deadline and the transfer never completes", which pins down the behaviour in point 1.
