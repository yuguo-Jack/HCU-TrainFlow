# [Bugfix][Scheduler] Do not schedule ahead of an uncapped lone prefill chunk

[Upstream PR](https://github.com/vllm-project/vllm/pull/60485) · state: open · merged: False

## Original PR description



## Overview

Fixes #60476. Since #57951 a lone long prefill runs uncapped chunks of `max_num_batched_tokens`, and with async scheduling (or `max_concurrent_batches > 1`) the next chunk is scheduled while the current one is still executing. A request that arrives mid-prefill therefore sits through up to two full uncapped steps before `long_prefill_token_threshold` can engage again. This change stops the batch queue from scheduling ahead of a chunk that ran uncapped under the lone-request exemption, so the cap re-engages right behind the in-flight chunk.

## Claims

- A request arriving during a lone uncapped long prefill is now seen by the scheduler before any further chunk is committed: worst-case head-of-line wait drops from about two uncapped steps to the remainder of the in-flight one.
- The #57951 exemption is unchanged: a request that stays alone still prefills at full `max_num_batched_tokens`.
- No effect when `long_prefill_token_threshold` is 0 (default), when the exemption does not fire (more than one eligible request), or for steps within the configured threshold (e.g. decode), so single-stream decoding keeps schedule-ahead pipelining.

## Validation

Scheduler level, run locally on CPU:

```
pytest tests/v1/core/test_scheduler.py -k long_prefill
```

Four tests pass: flag set for an uncapped lone chunk, flag clear for a within-threshold step, flag clear with multiple eligible requests, flag clear when the adaptive floor binds without the exemption. Red/green was checked by stashing the source changes (all four fail without them) and restoring.

Engine level: new `test_engine_core_no_schedule_ahead_of_uncapped_lone_prefill` in `tests/v1/engine/test_engine_core.py` drives a real EngineCore with a 2-deep batch queue, a 12-token prompt, `max_num_batched_tokens=10`, threshold 5:

- the first chunk is scheduled uncapped (10 > 5) and flagged;
- the next `step_with_batch_queue` call pops that batch instead of scheduling a second chunk behind it (before this change it scheduled ahead and the queue reached depth 2);
- after a second request is added, the very next schedule caps it to 5 tokens and co-schedules the first request.

This machine has no CUDA and that module is CUDA-only, so the engine test was not run locally; it is expected to run in CI. The gate was verified locally by driving `EngineCore.step_with_batch_queue` with a mocked engine: with a flagged batch queued, `schedule()` is not called; with an unflagged batch it is; on unpatched code `schedule()` is called in both cases.

`DummyExecutor` and `make_request_with_max_tokens` move from `test_engine_core_concurrent_batches` to module scope so both engine tests share them; that test's body is unchanged.

## Details

Root cause: #57951 zeroes the effective threshold when `running + waiting <= 1`. The predicate is evaluated at schedule time, but with a batch queue the schedule for step N+1 runs while step N still executes. A newcomer that lands between the two schedules is invisible to both, so two uncapped chunks of `max_num_batched_tokens` each get committed before the threshold can re-engage. At deep context one such chunk takes seconds (the issue logs show about 10 s of extra wait at a 65536-token budget), which is exactly the head-of-line blocking the flag exists to prevent.

The queued chunk is already launched, so it cannot be re-capped. The only place to restore the #57951 contract ("as soon as any other request is present, the threshold applies") is to never schedule ahead of an uncapped lone chunk. When `Scheduler.schedule()` sees the exemption actually let a chunk exceed the configured threshold, it marks the batch via the new `SchedulerOutput.has_uncapped_lone_prefill`; `EngineCore.step_with_batch_queue` then skips scheduling a new batch and blocks on the queued one first, so the next schedule observes any arrival that drained in the meantime.

Tradeoff: behind an uncapped lone chunk the GPU idles for one schedule + launch (milliseconds per multi-second chunk) instead of having the next chunk ready. Only configurations that set `long_prefill_token_threshold` pay this, and only while a lone long prefill is actually running uncapped.

Alternatives considered: re-capping the queued chunk (impossible, it is launched at schedule time); bounding the exempted chunk size or making the exemption opt-in (both weaken the lone-TTFT benefit of #57951, which this keeps intact). The remaining wait of up to one in-flight uncapped chunk is inherent to the exemption and matches its documented intent.

Not a duplicate: no open PR addresses the exemption / schedule-ahead interaction (checked #60476 comments, plus open PRs for "long prefill threshold", "lone prefill", and "60476 in:body"). #57427 (partial-prefill concurrency limit) and #58420 (SRPF) are separate mechanisms.

- he-yufeng · comment · 2026-10-08T18:29:33Z · [source](https://github.com/vllm-project/vllm/pull/60485#issuecomment-6066456787)

You're right, and thanks for checking the assertion before spending GPU time on it.

On the discard: in the synchronous `GPUModelRunner` path, `optimistic_seq_lens_cpu[i] = num_computed + num_scheduled` (`gpu_model_runner.py`, around L2065-2070), and `discard_request_mask[i] = optimistic_seq_lens_cpu[i] < num_tokens_np[i]` (L2082-2085). For req0 here that is 0 + 10 = 10 < 12, so its sampled ids get cleared (`.clear()` around L3705-3710 in the sync path). The scheduler contract matches: `_update_request_with_output` in `scheduler.py` notes that if a request is still being prefilled, the runner is expected to return empty token ids. So after the first chunk, req0 has zero accepted sampled tokens, and the next step schedules only the 2 remaining prompt tokens. The assertion was wrong.

One honesty note on how it slipped through: this file is skipped without CUDA, and the vllm PR pipeline doesn't run the unit-test legs, so the wrong `== 3` was never actually executed in CI on this PR. I had reasoned "one sampled token gets picked up" from the schedule side without tracing the runner discard. Fixed now: 84d4578 changes it to `== 2` with a comment explaining why.

On your coverage point: agreed, the current test only exercises the batch-queue path with both requests already queued before the first step. A new request arriving through the input queue between steps, while the uncapped chunk is still in flight, is a distinct path (the flag is recomputed per step from `batch_queue`, so the arrival timing matters). I'd rather add that case in a follow-up than grow this PR further, but if you'd like to write it as part of your validation pass, that's very welcome.
