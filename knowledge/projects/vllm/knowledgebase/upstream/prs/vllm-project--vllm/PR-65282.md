# [Core] Priority scheduling: preempt lower-priority requests for KV cache space

[Upstream PR](https://github.com/vllm-project/vllm/pull/65282) · state: open · merged: False

## Original PR description

## Overview

With `--scheduling-policy priority`, a waiting request never preempts running requests for KV cache space, so a high-priority request that finds the KV cache full waits behind lower-priority ones: the KV cache case of #40004. This PR adds `--max-priority-preemptions-per-step N` (default `0`, off): at the start of a step, the highest-priority waiting request may preempt up to `N` lower-priority running requests, but only if that makes room for it. #65283 builds on it.

## Claims

- With `N > 0`, the highest-priority waiting request preempts up to `N` running requests of a strictly lower priority when the KV cache lacks room for its whole sequence: in the running loop's order (lowest priority, then latest arrival), as few as make room, and none if `N` would not.
- The room is net of the request's prefix cache hit, bounded as the waiting loop bounds it. It counts a shared block as freed only once all its holders are preempted, and it counts the blocks the running decodes take until the victims' blocks are freed.
- In the step room is made, neither a victim nor a lower-priority request that holds KV blocks without a reservation, such as a streaming session's next chunk, takes the room.
- A request waiting to start an async KV load (#65319's queue, with `--max-num-inflight-kv-loads`) counts as a waiting request: room is made for it as for any other.
- Off by default, and off it changes no schedule: 832 traced configurations schedule as main does, step for step.
- A counter, `vllm:num_priority_preemptions`, registered only when `N > 0`; `vllm:num_preemptions` counts these preemptions too.
- On an RTX 5060 Ti with the KV cache held by two lower-priority requests, a priority 0 request's TTFT falls from 4,976 to 284 ms.

## Details

- **Where.** In `scheduler.py`, beside the queues, `_preempt_request` and the in-flight prefill state it reads. Off, a step pays only a few attribute checks: the traces and the cost table above show main's schedules and main's cost.
- **At the start of `schedule()`.** A victim has nothing scheduled in the step yet, so there is no budget, block, encoder or prefix-cache state to roll back (the class of bugs in #59907).
- **Which request.** The highest-priority request in either waiting queue that is ready to run: not one waiting on a KV load, a grammar or streaming input, on its output from before a preemption, or on a LoRA slot under `max_loras`. A blocked request does not stop room being made for the ones behind it. Encoder cache space is not checked, since its checks change state; a request the waiting loop then skips for it costs its victims one preemption, as no room is made for it again until the loop has tried it.
- **The room.** The request's whole remaining sequence, as `scheduler_reserve_full_isl` (the default) admits it, with an encoder-decoder model's cross-attention blocks, beside what in-flight prefills still need and, while requests run, the watermark. Its prefix cache hit is bounded as the waiting loop bounds it: prompt scoring's limit and the aux-output connector's.
- **No second round.** Once room is made for a request, none is made for it again until the waiting loop has tried it, so a request the loop then skips cannot cost a victim every other step.
- **The room stays the request's.** A victim is not resumed in the step that preempted it. In that step a lower-priority request that holds KV blocks but no reservation for the rest, such as a streaming session's next chunk, waits too: the waiting loop drains such requests first, and it would take the room. With prefix caching a victim's freed blocks stay cached, and it would be resumed into them between the chunks of the request it made room for. So while a higher-priority prefill is in flight, a lower-priority request that holds no KV blocks, preempted or new, is admitted only if its whole sequence fits beside the blocks in-flight prefills still need.
- **Costs.** Victims recompute their prefill unless prefix caching or a KV offloading connector keeps their KV. No room is made while scheduling is paused, in a step that defers prefills, or while the KV connector has pending block frees.
- **Related.** #54530 and #45561 preempt at `max_num_seqs` only. #40087 and #45558 preempt in the waiting loop when `allocate_slots` fails, one victim at a time, so they can preempt without making room.
- **Open question.** If #58037 lands, should `vllm:num_priority_preemptions` become a reason of its `vllm:num_preemptions_by_reason`?
