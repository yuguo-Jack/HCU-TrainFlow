# [RFC] feat(scheduler): implement Shortest Remaining Prefill First (SRPF) policy with starvation aging

[Upstream PR](https://github.com/vllm-project/vllm/pull/58420) · state: open · merged: False

## Original PR description

This RFC introduces the `srpf` scheduling policy, prioritizing requests with the Shortest Remaining Prefill First. This is designed for mixed-workload clusters where massive prompt ingestion (e.g., 100k+ tokens) unfairly stalls short interactive requests.

### Motivation

Currently, V1's scheduling queue is susceptible to Head-of-Line (HoL) blocking. When a long prefill (e.g., 100k tokens) is being chunked, shorter requests that arrive later are forced to wait for many scheduling iterations until the large prefill finishes. While `long_prefill_token_threshold` partially mitigates this, it arbitrarily limits throughput when the queue is empty.

SRPF solves this dynamically at the queue level by prioritizing requests that have the shortest remaining token demand, maximizing interactive responsiveness (TTFT) without wasting batch capacity.

### Proposed Architecture

1. **SRPF Policy**: Introduces `srpf` to `SchedulerConfig`.
2. **Dynamic Preemption**: Automatically preempts running requests if a waiting request has a significantly shorter prefill requirement.
3. **Starvation Aging**: Tracks `consecutive_starvation_ticks`. If a heavy request gets skipped repeatedly by shorter ones, it temporarily jumps the queue to guarantee its chunk, preventing complete starvation.

### Done when
- [ ] SRPF and Aging logic implemented and gated by `SchedulerConfig`.
- [ ] Unit tests added for priority queuing and aging threshold behavior.
- [ ] Benchmark results collected showing TTFT improvements under high-contention mixed workloads.

### Alternatives Considered
- **Dynamic `long_prefill_token_threshold`**: We prototyped dynamically disabling the chunking threshold when the queue is empty. However, this required forecasting cache hits for WAITING requests to accurately judge "demand", which proved fragile. SRPF naturally avoids HoL blocking without complex demand forecasting.
- **Strict SJF (Shortest Job First)**: Rejected because it does not account for partial prefill progress and can completely starve long requests.

### Additional context
- Originally prototyped to address the exact agentic serving bottlenecks discussed in #57413 and #57427.
