# [Build] Let the NIXL source build take a Git ref and build the LIBFABRIC plugin

[Upstream PR](https://github.com/vllm-project/vllm/pull/63188) · state: open · merged: False

## Original PR description

## Overview

`BUILD_NIXL=true` builds NIXL from source, but only the release tag pinned in `requirements/kv_connectors.txt` and only the UCX plugin. This adds a Git-ref override and LIBFABRIC plugin support to that path, so an image can carry a NIXL build that is not yet released and talk to libfabric fabrics such as EFA.

## Claims

- `NIXL_REF` (build arg and env) builds any NIXL branch, tag or commit; the wheel version is read from the checkout's `pyproject.toml` instead of the pin.
- `NIXL_PLUGINS` (default `UCX`) selects the plugins. With `LIBFABRIC`, the script builds libfabric `LIBFABRIC_REF` (default `v2.7.0`, tcp provider only) and hwloc `HWLOC_VERSION` (default 2.12.2) from source for the headers and the link, the same way NIXL's own manylinux wheel build does: the plugin compiles its dmabuf registration path only against headers that define `FI_MR_DMABUF` (libfabric 1.20+), and it needs the hwloc 2.5+ API, which the manylinux 2.28 base's hwloc 2.2 lacks. The wheel keeps excluding `libfabric*` and `libhwloc*`, so at runtime the plugin loads the host's libfabric and providers, as the released `nixl-cu*` wheels do.
- Building the plugin in the image links it against the image's CUDA runtime. The released `nixl-cu13` 1.5.0 LIBFABRIC plugin links `libcudart.so.12`, which a CUDA 13 image does not ship.
- With LIBFABRIC requested, `extensions-build` installs `numactl-devel` (libnuma is linked and bundled into the wheel by auditwheel) and `vllm-openai-base` installs `libhwloc15`, the one runtime library the plugin needs from the image; libfabric stays host-provided. Defaults are unchanged, so existing `BUILD_NIXL` builds are unaffected.

## Validation

- `pre-commit run` on the five files passes (ruff, forbidden imports, Dockerfile/versions.json consistency, markdownlint).
- Script, final code, on an x86_64 host with CUDA 13.2 (`--skip-system-deps --no-build-nixl-ep --build-only`):
  - Default path, no `NIXL_REF`, `NIXL_PLUGINS=UCX`: builds `nixl_cu13-1.5.0` from the pinned tag with `libplugin_UCX.so` only, as before this change.
  - `NIXL_REF=main NIXL_PLUGINS=UCX,LIBFABRIC`: builds UCX v1.23.x, libfabric v2.7.0 (tcp only) and NIXL main as `nixl_cu13-1.6.0-cp312-cp312-manylinux_2_39_x86_64.whl` plus the `nixl-1.6.0` meta wheel, with `libplugin_UCX.so` and `libplugin_LIBFABRIC.so`. `ldd` on the LIBFABRIC plugin resolves `libcudart.so.13` and `libhwloc.so.15` and leaves `libfabric.so.1` to the host; the plugin's strings include the `FI_MR_DMABUF` registration path, so it was compiled against libfabric 1.20+ headers.
- Dockerfile package installs: `numactl-devel` installs on `quay.io/pypa/manylinux_2_28_x86_64`; `libhwloc15` installs on `ubuntu:24.04`.
- The Dockerfile's `extensions-build` NIXL block, run verbatim under `quay.io/pypa/manylinux_2_28_x86_64` (the build base's distribution, no CUDA) with `NIXL_REF=main NIXL_PLUGINS=UCX,LIBFABRIC`: the dnf installs, the env passthrough and the script succeed, building libfabric v2.7.0, hwloc 2.12.2 and NIXL main into a `manylinux_2_28` wheel with both plugins. The LIBFABRIC plugin needs `libfabric.so.1` and `libhwloc.so.15` from outside the wheel, links the bundled libnuma, and contains the `FI_MR_DMABUF` path and the hwloc 2.5+ `hwloc_get_local_numanode_objs` call. The same block with the EL8 `hwloc-devel` (2.2) failed to compile, which is why hwloc is built from source.
- No full `docker build` was run (the build base alone is 7.3 GB compressed); the Dockerfile change threads the three ARGs into the existing `BUILD_NIXL` step and adds the two conditional installs above.

## Details

The ref override keeps the existing tag resolution for the pinned-version path and adds `checkout_nixl_ref`, which tries the ref and `origin/<ref>` and then reads `project.version` with `tomllib`. A ref build skips the installed-package and wheel-cache reuse, since its version is only known after checkout, so it never picks up a cached release by accident.

libfabric and hwloc are built rather than taken from the build base's package manager because the manylinux 2.28 base is AlmaLinux 8: its libfabric predates `FI_MR_DMABUF`, and building against such headers silently drops the dmabuf registration path from the plugin, while its hwloc 2.2 lacks `hwloc_get_local_numanode_objs` and fails the compile outright. Only libfabric's tcp provider is enabled, which keeps the build free of rdma-core and EFA dependencies; the provider set that matters is the host's.

This does not install libfabric into the runtime image and takes no position on which libfabric a host should run; it only makes the plugin buildable and correctly linked. Fabric-specific images (for example an EFA variant) can set `BUILD_NIXL=true NIXL_PLUGINS=UCX,LIBFABRIC` and supply the runtime libfabric themselves.
