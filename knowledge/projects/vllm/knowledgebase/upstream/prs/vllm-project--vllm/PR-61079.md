# [Bugfix][GLM-5.3-Flash] Restore MTP index sharing across draft iterations

[Upstream PR](https://github.com/vllm-project/vllm/pull/61079) · state: closed · merged: True

## Original PR description

## Overview

GLM-5.3-Flash's checkpoint sets `index_share_for_mtp_iteration: true`: the MTP head computes the sparse indexer top-k on draft step 0 and reuses it on the later steps. Since #57387 the flag is no longer visible on the draft config, so sharing has been silently off. This restores it.

Not a duplicate: I searched open PRs for `index_share_for_mtp_iteration`, `share_mtp_topk_indices`, `glm5_next_mtp` and GLM-5.3-Flash MTP and found nothing covering this.

## Claims

- With MTP on GLM-5.3-Flash, draft steps 1+ reuse step 0's top-k again, as before #57387.
- Accepted tokens per draft step go from 3.28 to 3.42 on GSM8K (MTP 5), and decode throughput is +2.7% at a fixed acceptance length.

## Validation

4x B200, nightly `8cbd5d03`, TP1 x DP4 with expert parallel and #60895's MegaMoE path, MTP 5, one run each.

| | sharing off (main) | sharing on |
|---|---:|---:|
| GSM8K (lm-eval, 5-shot, 1,319 questions) | 0.9704 ± 0.0047 | 0.9750 ± 0.0043 |
| draft steps for that GSM8K run | 58,471 | 56,072 |
| accepted tokens per draft step | 3.28 | 3.42 |
| random 1024 in / 1024 out, concurrency 128, output tok/s | 11,639 | 11,952 |
| mean TPOT | 10.13 ms | 9.90 ms |

The GSM8K rows use real acceptance; the throughput rows fix it with `synthetic_acceptance_length` 3.61.

The GPU runs switched the same proposer flag (`share_mtp_topk_indices`) through a local patch that read it from `text_config`. With this PR's code I ran:

- `tests/config/test_speculative_draft_hf_overrides.py`: 17 passed; the new test fails without the change. Run against nightly `8cbd5d03`, whose `speculative.py` is identical to `main`'s.
- `SpeculativeConfig.hf_config_override` on the real checkpoint config: `index_share_for_mtp_iteration` is `True` (missing before).
- pre-commit on the changed files.

## Details

- Root cause: the MTP proposers read the flag from the draft config (`mtp/speculator.py`, `llm_base_proposer.py`). The in-tree `Glm5NextConfig` forwarded `text_config` attributes to the top level; the upstream Transformers config that #57387 switched to does not. That PR moved `num_nextn_predict_layers` to `get_text_config()` but not this flag.
- Fix: promote the flag onto the draft config in the `glm5_next` override, as the Qwen4-Exp override already does. An explicit `index_share_for_mtp_iteration` in `--speculative-config` still takes precedence.
- The GSM8K difference is within one standard error; I read it as no regression, not as an accuracy gain.
- Limitations: validated on NVIDIA SM100 only, not on ROCm. Acceptance was measured on GSM8K only.

## Summary

This pull restores MTP index sharing for GLM-5.3-Flash. The draft config override now reads the index_share_for_mtp_iteration flag from the text config and copies it onto the draft config, which is where both MTP proposers look for it. We found no serious problems and three smaller ones. The most useful one is a small hardening of how the flag gets copied: right now the copy can overwrite a value that is already on the draft config.

## Serious findings

None.

## Smaller findings

**1. The copied flag can overwrite a value already on the draft config [vllm/config/speculative.py]**
The glm5_next branch reads the flag from the text config, falling back to False, and always writes the result onto the top-level draft config. If a checkpoint carried the flag at the top level but not in its text config, the override would now reset it to False. That matters because the proposers in llm_base_proposer.py and the MTP speculator read only the top-level value. The qwen4_exp branch in the same function copies this flag the same way, and a user's explicit index_share_for_mtp_iteration setting is still applied afterwards. So this is a hardening suggestion, not a regression for the GLM-5.3-Flash checkpoint as shipped.
*Change:* Copy the flag only when the text config actually has it, or when the top-level config doesn't have it yet.

**2. The new test only covers the case where the flag is True [tests/config/test_speculative_draft_hf_overrides.py]**
test_glm5_next_mtp_override_promotes_index_share builds one config, with the flag set to True inside the text config, and checks for True. Nothing tests the False fallback when the key is missing, or whether a user's explicit setting still wins for glm5_next. The existing tests for that precedence in this file are built on a qwen4_exp_mtp mock, not a GLM-5 config.
*Change:* Parametrize the new test over flag absent, False and True, and add one case where the explicit SpeculativeConfig setting overrides the checkpoint value.

**3. A module-level import puts all 17 tests in this file at risk [tests/config/test_speculative_draft_hf_overrides.py]**
The file now imports Glm5NextConfig from transformers at the top of the module. vLLM already imports Glm5NextTextConfig from transformers in several places, but this is the first in-tree use of the outer Glm5NextConfig class. If a supported transformers version doesn't export it, the whole file fails collection and all 17 tests stop running, not just the new one.
*Change:* Import Glm5NextConfig inside the new test, or skip that test when transformers doesn't provide the class.
