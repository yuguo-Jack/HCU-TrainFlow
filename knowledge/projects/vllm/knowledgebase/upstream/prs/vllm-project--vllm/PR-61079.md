# [Bugfix][GLM-5.3-Flash] Restore MTP index sharing across draft iterations

[Upstream PR](https://github.com/vllm-project/vllm/pull/61079) · state: closed · merged: True

## Original PR description

## Overview

GLM-5.3-Flash's checkpoint sets `index_share_for_mtp_iteration: true`: the MTP head computes the sparse indexer top-k on draft step 0 and reuses it on the later steps. Since #57387 the flag is no longer visible on the draft config, so sharing has been silently off. This restores it.

Not a duplicate: I searched open PRs for `index_share_for_mtp_iteration`, `share_mtp_topk_indices`, `glm5_next_mtp` and GLM-5.3-Flash MTP and found nothing covering this.

## Claims

- With MTP on GLM-5.3-Flash, draft steps 1+ reuse step 0's top-k again, as before #57387.
- Accepted tokens per draft step go from 3.28 to 3.42 on GSM8K (MTP 5), and decode throughput is +2.7% at a fixed acceptance length.

## Validation

4x B200, nightly `8cbd5d03`, TP1 x DP4 with expert parallel and #60895's MegaMoE path, MTP 5, one run each.

| | sharing off (main) | sharing on |
|---|---:|---:|
| GSM8K (lm-eval, 5-shot, 1,319 questions) | 0.9704 ± 0.0047 | 0.9750 ± 0.0043 |
| draft steps for that GSM8K run | 58,471 | 56,072 |
| accepted tokens per draft step | 3.28 | 3.42 |
| random 1024 in / 1024 out, concurrency 128, output tok/s | 11,639 | 11,952 |
| mean TPOT | 10.13 ms | 9.90 ms |

The GSM8K rows use real acceptance; the throughput rows fix it with `synthetic_acceptance_length` 3.61.

The GPU runs switched the same proposer flag (`share_mtp_topk_indices`) through a local patch that read it from `text_config`. With this PR's code I ran:

- `tests/config/test_speculative_draft_hf_overrides.py`: 17 passed; the new test fails without the change. Run against nightly `8cbd5d03`, whose `speculative.py` is identical to `main`'s.
- `SpeculativeConfig.hf_config_override` on the real checkpoint config: `index_share_for_mtp_iteration` is `True` (missing before).
- pre-commit on the changed files.

## Details

- Root cause: the MTP proposers read the flag from the draft config (`mtp/speculator.py`, `llm_base_proposer.py`). The in-tree `Glm5NextConfig` forwarded `text_config` attributes to the top level; the upstream Transformers config that #57387 switched to does not. That PR moved `num_nextn_predict_layers` to `get_text_config()` but not this flag.
- Fix: promote the flag onto the draft config in the `glm5_next` override, as the Qwen4-Exp override already does. An explicit `index_share_for_mtp_iteration` in `--speculative-config` still takes precedence.
- The GSM8K difference is within one standard error; I read it as no regression, not as an accuracy gain.
- Limitations: validated on NVIDIA SM100 only, not on ROCm. Acceptance was measured on GSM8K only.
