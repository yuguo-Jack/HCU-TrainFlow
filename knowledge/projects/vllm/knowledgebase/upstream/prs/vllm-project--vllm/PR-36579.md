# [Quantization] Diagnose CUDA driver too old for Marlin PTX JIT across all Marlin users

[Upstream PR](https://github.com/vllm-project/vllm/pull/36579) · state: open · merged: False

## Original PR description

## Summary

Detect a CUDA driver that is too old to JIT-compile Marlin's PTX once, at the shared Marlin op layer, and log a single actionable warning that tells the user how to keep using Marlin. This replaces the earlier AWQ-only fallback. Kernel selection is unchanged for every quantization method.

Fixes #36235

## Root cause

Several Marlin kernels (dense GEMM, repack, MoE) are built as `8.0+PTX` (see `MARLIN_ARCHS` / `MARLIN_OTHER_ARCHS` / `MARLIN_MOE_*` in `CMakeLists.txt`). On GPUs with no native SASS in the wheel (e.g. sm_90 H100/H20, sm_100), the driver JIT-compiles that PTX at load time. CUDA minor-version compatibility covers SASS but not PTX JIT, so a driver older than the toolkit the wheel was built with fails with `cudaErrorUnsupportedPtxVersion` ("the provided PTX was compiled with an unsupported toolchain"). In #36235 that was torch/vLLM cu129 on an H20 with a 12.8 driver. This hits every method that uses Marlin, not only AWQ.

## Design

Per review feedback, the fix should cover all Marlin usage and keep users on the kernel:

- **One place for every Marlin user.** Every Marlin path (AWQ, GPTQ, compressed-tensors WNA16, FP8, NVFP4/MXFP4, MXFP8, MoE) prepares its weights through the Marlin repack/preprocess ops in `vllm/_custom_ops.py` before the first Marlin GEMM. The check is wired into those ops (`gptq_marlin_repack`, `awq_marlin_repack`, their MoE variants, `marlin_int4_fp8_preprocess`), so no quantization method needs its own code. It fires only when Marlin is actually used, not when a selector merely probes `can_implement`. It runs at load time, never in the forward path.
- **Keep Marlin and say how to fix the environment.** Nothing switches kernels. The warning names the driver and toolkit versions and lists the three ways to keep using Marlin: upgrade the driver, install a build for the driver's CUDA version, or (datacenter/professional GPUs) set `VLLM_ENABLE_CUDA_COMPATIBILITY=1`. It links the existing troubleshooting section. It is logged once per process.
- **Accurate version source.** The driver version comes from `cuDriverGetVersion` on the loaded `libcuda`, not NVML. When forward-compat libs are active, that reports the compat version, so no special case for `VLLM_ENABLE_CUDA_COMPATIBILITY` is needed. No CUDA context is created.
- **Warning, not an error, and not arch-gated.** Whether a GPU needs PTX JIT depends on how the wheel was built (`TORCH_CUDA_ARCH_LIST`, the CMake arch lists), so Python cannot know for sure that the kernel will fail. On GPUs with native Marlin SASS (sm_8x, sm_12x) a mismatch still works, so a hard error would break working setups.

Changes from the previous revision of this PR:
- Removed the automatic `LD_LIBRARY_PATH` compat-lib injection from `env_override.py`. The official image ships `/usr/local/cuda-*/compat`, and loading those libs on consumer GPUs fails with Error 803. That is why `VLLM_ENABLE_CUDA_COMPATIBILITY` is opt-in, so auto-enabling it would regress those users.
- Removed the hooks in `check_marlin_supported` / `check_*_supports_layer`, which are probes and could warn even when another kernel is selected.

Related: #38669 (adds `9.0+PTX` to the Marlin arch lists so sm_90 gets native SASS) removes the JIT dependency on Hopper. This PR is complementary: it covers the remaining PTX-only archs and source builds, and gives users a clear next step either way.

## Changes

- `vllm/utils/platform_utils.py`: `parse_cuda_version()`, `get_cuda_driver_version()` (cached `cuDriverGetVersion`), `warn_if_cuda_driver_cannot_jit_ptx(kernel_name)` (cached per kernel family, returns whether a mismatch was found).
- `vllm/_custom_ops.py`: `_check_marlin_cuda_driver()` called from the five Marlin weight-prep ops (CUDA only).
- Tests: `tests/utils_/test_platform_utils.py`, `tests/quantization/test_marlin_cuda_driver_check.py`.

### Tested on RTX PRO 4000 Blackwell (sm_120), driver 610.57

**Setup.** The vLLM nightly wheel for `1a86733c7` (the parent of this PR's base commit; the only difference between them is in `structured_output/backend_xgrammar.py`), with torch 2.13.0+cu132. This branch's `vllm/_custom_ops.py` and `vllm/utils/platform_utils.py` were copied over the installed package, and their sha256 matches the files at `d13075241c`. The driver reports CUDA 13.3 through `cuDriverGetVersion`.

**What each run does.** The script below loads a Marlin-quantized model with `gpu_memory_utilization=0.2`, `max_model_len=2048`, enforce-eager, then generates 24 tokens greedily. It prints the driver and toolkit versions, the generated text, and `warn_if_cuda_driver_cannot_jit_ptx.cache_info()`. That last value counts how many times the Marlin ops invoked the check. V1 multiprocessing is turned off so the weights load in the same process. That way the `sim` mode can patch `vllm.utils.platform_utils.get_cuda_driver_version` to report CUDA 13.1. The real driver is newer than any toolkit, so this is the only way to exercise the mismatch path on this machine.

```
python check_marlin_driver.py real Qwen/Qwen2.5-0.5B-Instruct-AWQ
python check_marlin_driver.py sim  Qwen/Qwen2.5-0.5B-Instruct-AWQ
python check_marlin_driver.py real Qwen/Qwen2.5-0.5B-Instruct-GPTQ-Int4
python check_marlin_driver.py sim  Qwen/Qwen2.5-0.5B-Instruct-GPTQ-Int4
```

<details><summary><code>check_marlin_driver.py</code></summary>

```python
"""Load a Marlin-quantized model and report whether the CUDA driver check fires.

usage: python check_marlin_driver.py {real|sim} <model>
  real: use the driver version reported by cuDriverGetVersion
  sim:  report CUDA 13.1, older than the toolkit, to exercise the warning
"""
import os
import sys

os.environ["VLLM_ENABLE_V1_MULTIPROCESSING"] = "0"  # load weights in this process

import torch
import vllm.utils.platform_utils as pu

mode, model = sys.argv[1], sys.argv[2]
print(f"TORCH_CUDA={torch.version.cuda} DRIVER_CUDA_REAL={pu.get_cuda_driver_version()}")
if mode == "sim":
    pu.get_cuda_driver_version = lambda: (13, 1)
    print("DRIVER_CUDA_SIMULATED=(13, 1)")

from vllm import LLM, SamplingParams

llm = LLM(model=model, gpu_memory_utilization=0.2, max_model_len=2048,
          enforce_eager=True, seed=0)
out = llm.generate(["The capital of France is"],
                   SamplingParams(temperature=0, max_tokens=24))
print(f"OUTPUT={out[0].outputs[0].text!r}")
print(f"CHECK_CALLS={pu.warn_if_cuda_driver_cannot_jit_ptx.cache_info()}")
```

</details>

**Results.** All four runs exited 0.

| Model | Driver CUDA | Kernel selected | Check calls | Warnings logged | Generation |
|---|---|---|---|---|---|
| AWQ | 13.3 (real) | `Using MarlinLinearKernel for AutoAWQMarlinLinearMethod` | 96 (1 miss, 95 cached) | 0 | ` Paris. The capital of the United States is Washington, D. C. ...` |
| AWQ | 13.1 (simulated) | `Using MarlinLinearKernel for AutoAWQMarlinLinearMethod` | 96 (1 miss, 95 cached) | 1 | identical |
| GPTQ | 13.3 (real) | `Using MarlinLinearKernel for AutoGPTQLinearMethod` | 96 (1 miss, 95 cached) | 0 | ` Paris. It is the largest city in Europe ...` |
| GPTQ | 13.1 (simulated) | `Using MarlinLinearKernel for AutoGPTQLinearMethod` | 96 (1 miss, 95 cached) | 1 | identical |

"Check calls" is the number of times a Marlin repack op ran the check during model load, one per quantized linear layer. Only the first call does any work; the rest hit the cache, so the check adds nothing per layer and nothing in the forward path. Peak GPU memory across the runs, sampled with `nvidia-smi` every 500 ms, was 4802 MiB.

The warning as emitted in the simulated runs:

```
WARNING [platform_utils.py:137] The CUDA driver supports CUDA 13.1, but vLLM/PyTorch were built with CUDA 13.2. Marlin kernels that are compiled to PTX for this GPU must be JIT-compiled by the driver, which needs CUDA >= 13.2, and will fail with 'the provided PTX was compiled with an unsupported toolchain'. To keep using Marlin, do one of: upgrade the NVIDIA driver to one that supports CUDA >= 13.2; install a vLLM/PyTorch build for CUDA 13.1; or, on datacenter/professional GPUs, enable CUDA forward compatibility with VLLM_ENABLE_CUDA_COMPATIBILITY=1. See https://docs.vllm.ai/en/latest/usage/troubleshooting.html#cuda-error-the-provided-ptx-was-compiled-with-an-unsupported-toolchain
```

**What this does and does not show.** It shows that, with a matching driver, the check does not misfire. With an older driver it warns exactly once per process. In both cases Marlin stays selected and the output is unchanged. It does not reproduce the real `cudaErrorUnsupportedPtxVersion`: sm_120 has native Marlin SASS in the wheel, so this card never JIT-compiles Marlin PTX. Reproducing that needs a PTX-only arch (e.g. sm_90 with the current arch lists) on a driver older than the build toolkit, as in #36235.

All 5 Marlin weight-prep ops call `_check_marlin_cuda_driver()`, so every Marlin user (AWQ, GPTQ, compressed-tensors, FP8, FP4, MoE) gets the diagnostic before any GEMM.

**Tests are thorough**

- Edge cases: None, empty string, malformed version strings, missing `libcuda`, failed CUDA call
- Warning content verified: driver version, toolkit version, kernel name, troubleshooting links
- Idempotency: 5 calls → 1 warning logged
- All 5 Marlin ops verified to call the check; non-CUDA platforms verified to skip it

If the driver (`cuDriverGetVersion`) is older than the build toolkit, vLLM logs one warning naming both versions and the ways to keep using Marlin (upgrade the driver, use a build for that CUDA version, or `VLLM_ENABLE_CUDA_COMPATIBILITY=1` on datacenter GPUs).
- I dropped the earlier automatic compat-lib injection. Auto-loading the compat libs the image ships would break consumer GPUs with Error 803.

I verified it on an sm_120 card with AWQ and GPTQ: Marlin is selected and generates correct text, there is no warning when versions match, and with a simulated older driver the warning fires exactly once. Details are in the description. #38669 (native sm_90 SASS) is complementary.
