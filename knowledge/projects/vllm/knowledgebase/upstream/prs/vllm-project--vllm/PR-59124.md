# [ROCm][Perf][MLA] Add opt-in FlyDSL FP8 prefill attention for AITER MLA

[Upstream PR](https://github.com/vllm-project/vllm/pull/59124) · state: open · merged: False

## Original PR description

## Purpose

This PR adds an opt-in FlyDSL FP8 path for MLA prefill attention on ROCm, following the approach of [ROCm/ATOM#2191](https://github.com/ROCm/ATOM/pull/2191). The target is Kimi-K3 on MI355X (gfx950).

It adds a new, opt-in MLA prefill backend, `ROCM_AITER_FLYDSL_FP8`, which subclasses `ROCM_AITER_FA`. Select it with `--attention-config '{"mla_prefill_backend":"ROCM_AITER_FLYDSL_FP8"}'`; it is not in the ROCm auto-selection priorities. The backend:

- quantizes Q/K/V to FP8 with dynamic per-tensor scales and runs AITER's `flydsl_flash_attn_fp8_func` for the new tokens;
- keeps the new-token FP8 Q for the context chunks. Each chunk quantizes only its own K/V and calls the kernel non-causally with `return_lse=True`. The LSE layout (`[H, T]`, natural log) is unchanged, so `merge_attn_states` works as-is. The layer's softmax scale is passed directly.
- takes over context-free prefills too, in place of the ASM FP8 prefill (`mla_prefill_ps_asm_fwd`). The metadata builder stops building ASM PS metadata when this backend is selected, and `AiterMLAImpl.forward_mha` then falls back to the common path.

Support is checked through the standard prefill-backend hooks. vLLM does not hard-code any shape or model:
- `supported_dtypes = [bf16]`, because the kernel writes BF16 output;
- `supports_compute_capability` requires gfx950;
- `is_available` requires AITER and the FlyDSL FP8 API;
- `validate_configuration` defers to AITER's `flydsl_flash_attn_fp8_supported` for the head dims.

An explicit selection that fails these checks raises at startup. At runtime, inputs the kernel cannot take (empty, or ≥2³¹ elements) use the parent's BF16 path.

`vllm/v1/attention/ops/triton_per_tensor_fp8_quant.py` is a small Triton kernel adapted from ATOM#2191's fused QKV quantizer (MIT). It quantizes up to three strided `[tokens, heads, dim]` tensors in two launches, each with its own amax/descale. V is quantized directly from its strided view of the `kv_b_proj` output. Compile-time specialization does not depend on token counts (only the grid size does), so varying batch shapes do not recompile, and no atomics are used. Unlike ATOM's KV quantizer, element counts are runtime arguments.

**Why not reuse `ops.scaled_fp8_quant`.** vLLM's dynamic per-tensor quantizer (`dynamic_scaled_fp8_quant`, also behind `QuantFP8`) gives the same result: descales within 1e-6 relative, values within 1 e4m3 ulp. It is too slow for this path, for three reasons:
- It takes one 2D tensor per call, so Q/K/V need three calls (memset, amax, quant each).
- The strided V (row stride 256) takes its per-row path: one 256-thread block and one `atomicMax` per 128-element row, i.e. T×H rows.
- An all-zero input gets descale 0. ATOM uses a positive descale in that case to avoid FMHA NaNs, and this kernel does the same.

`rocm_aiter_ops.per_tensor_quant` returns wrong results for the strided V. GPU time on MI355X, 12 heads, q/k 192 and v 128 (v a strided view):

| Tokens | This kernel (Q/K/V, one call) | `scaled_fp8_quant` ×3 | `scaled_fp8_quant` ×3, V made contiguous first |
|---:|---:|---:|---:|
| 1,024 | 50 µs | 189 µs | 59 µs |
| 8,192 | 50 µs | 1,318 µs | 237 µs |
| 65,536 | 352 µs | 10,165 µs | 1,306 µs |

At 65,536 tokens, V alone takes 9,284 µs with `scaled_fp8_quant` and 110 µs here. The existing op is faster only for a single small contiguous tensor (Q alone at 1,024 tokens: 21 µs vs 44 µs), which this path never quantizes.

**AITER requirement.** This needs an AITER build containing:
- ROCm/aiter#5718 (`flydsl_flash_attn_fp8_supported`)
- ROCm/aiter#5508 (short-query split-K)
- ROCm/aiter#5405 (`softmax_scale` in `flydsl_flash_attn_fp8_func`)

All three are already on AITER main. #5718 is the newest of them, so a build that has the capability check also has the other two. #5508 only affects performance. The current `vllm/vllm-openai-rocm` nightly (AITER 0.1.22.post1) predates them, so there this backend reports itself unavailable.

**AOT build.** ROCm/aiter#5796 and #5901 pre-compile the FlyDSL FP8 FMHA for Kimi-K3 TP8 (`12:12:192:128`, `varlen_cross` layout, 92 kernels) during AITER source builds, so serving no longer JIT-compiles them. The new-token call therefore passes `cross_seqlen=True`, as ATOM does.
- With `cross_seqlen=False`, the new-token call would use the `varlen` layout, which is not pre-compiled.
- For equal q/kv lengths, the two layouts give bit-identical output and LSE. Checked 8 batch shapes.
- Kernel time with `cross_seqlen=True` is within ±2% for most shapes and 7% faster for 1×8192. Batches of several equal-length sequences are slower: 4×2048 +15 µs, 8×1024 +4 µs.

Coverage check: the 92 AOT kernels (built with `aiter.aot.flydsl.fmha_fp8` from AITER main) were put into an empty `FLYDSL_RUNTIME_CACHE_DIR`, and `FLYDSL_RUNTIME_RUN_ONLY=1` was set, which makes any cache miss raise.
- Through this backend, all 12 new-token and context-chunk calls were served from the AOT cache, and the cache did not grow. The calls covered 1–32 sequences, 17–8192 new tokens and contexts of 0–131072 tokens.
- With `cross_seqlen=False`, all 20 new-token calls missed.

**Not a duplicate.** I searched open PRs for FlyDSL/FP8 MLA prefill:
- #51551 (draft) adds a gfx942-only FP8 context-prefill path for 12-head Kimi-K3. It uses AITER's Gluon kernel (ROCm/aiter#4645) with static, offline-calibrated per-head scales. This PR targets gfx950 through FlyDSL, uses dynamic per-tensor scales with no calibration artifact, and also covers new tokens and context-free prefills.
- #53335 is a non-MLA FlyDSL BF16 attention backend.
- #58887 fixes an ASM PS-metadata race. It is orthogonal: that path is skipped while this backend is selected. Both PRs touch the `_fp8_prefill_enabled` gate in `AiterMLAMetadataBuilder.__init__`, so whichever lands second needs a small rebase.

AI assistance (Claude Code) was used to implement this change and to run the tests and benchmarks below.

- gbyu-amd · comment · 2026-09-30T07:13:50Z · [source](https://github.com/vllm-project/vllm/pull/59124#issuecomment-5906132267)

@ChuanLi1101 Thanks for the careful read — points 1 and 3 are fixed in 19a77e3, and I have numbers for point 2.

**1. Out-of-range pointers in the shared quant grid**

You're right that the grid is sized for the largest input, so programs can land past the end of a smaller one. Every load and store was already masked and the offset math is int64, so nothing was dereferenced or wrapped — but those programs still computed addresses they had no business computing. Both kernels now stop before that:

- `_partial_amax` derives its trip count per program, `tl.cdiv(N - start, PARTS * BLOCK)`, which is 0 once the program's stripe starts past the end of this input. It still stores its (zero) partial, which the reduce needs.
- `_quant` guards the body with `if start < N or start == 0`. Program 0 stays alive unconditionally so an empty input still gets its descale written.

I added `test_fused_per_tensor_fp8_quant_covers_every_element` to the kernel test: it plants the global max at `{0, BLOCK-1, BLOCK, STRIPE-1, STRIPE, numel-1}` for sizes straddling the 4096-element block and 1048576-element stripe boundaries, up to 3,145,735 elements. It fails if a single element is dropped (verified by shrinking the amax loop to one stripe). The change is perf-neutral: host 46.3–46.8 µs, e2e 349.2 µs at 65K tokens, same as before.

**2. Per-call temporary buffers**

I measured this on MI355X before changing it, since the buffers are tiny (`partial` is 3×256 f32, `scales` is 3 f32). Host cost of `fused_per_tensor_fp8_quant(q, k, v)`:

| Variant | Host | Δ |
|---|---:|---:|
| current (5 allocations) | 46.6 µs | — |
| reuse `partial` only | 44.2 µs | −2.4 µs |
| reuse `partial` + `scales` | 42.7 µs | −3.9 µs |
| one merged scratch allocation | 46.7 µs | +0.1 µs |

Where the 46.6 µs goes: 28 µs is the two Triton launches (an empty kernel with the same signature already costs 15.2 µs), 10.2 µs is `torch.empty` ×5, and the rest is the Python wrapper. So the ceiling on reuse is ~8% of host cost and ~1% of the 349 µs e2e at 65K tokens. The three FP8 outputs can't be reused at all — they are returned and stay live for the whole attention call.

Reusing `scales` specifically has a correctness trap: the backend keeps `self._q_fp8 = (q, q_fp8, q_descale)` across the forward, where `q_descale` is a view into that call's `scales`, and each context chunk then calls the quantizer again for its own K/V. A shared per-instance `scales` would be overwritten under the still-live `q_descale` unless keyed by tensor count — exactly the kind of implicit invariant that breaks later.

Given ~2 µs for the only unambiguously safe part (`partial`, which never escapes the function) against making a pure function stateful, I left it as is. Happy to add the `partial` cache if you'd still prefer it — it's a five-line change.

**3. Disabling the ASM FP8 prefill directly**

Agreed, keying off absent PS metadata was too indirect. There's now a single predicate in `rocm_aiter_mla.py`:

```python
def _asm_fp8_prefill_superseded(prefill_backend: object) -> bool:
    return isinstance(prefill_backend, AiterFlyDSLFP8PrefillBackend)
```

used in both places so they can't drift:

- `AiterMLAMetadataBuilder.__init__` folds it into `_fp8_prefill_enabled`, so the PS workspace buffers aren't allocated either.
- `AiterMLAImpl.forward_mha` checks the actual `prefill_metadata.prefill_backend` instance and defers to the parent, instead of inferring it from `fp8_prefill_qo_indptr is None`.

`test_mla_backends.py::test_chunked_context_backend_correctness` covers this through the `context_free_prefill` spec.

**4. Opt-in**

Agreed — it stays out of the ROCm auto-selection priorities and is only reachable via `--attention-config '{"mla_prefill_backend":"ROCM_AITER_FLYDSL_FP8"}'`.

- gbyu-amd · comment · 2026-09-29T13:28:58Z · [source](https://github.com/vllm-project/vllm/pull/59124#discussion_r4134014128)

I compared against the existing kernels first. On MI355X, with 12 heads, q/k 192 and v 128, and V a strided view of the `kv_b_proj` output:
- `rocm_aiter_ops.per_tensor_quant` returns wrong results for the strided V.
- `ops.scaled_fp8_quant` matches this kernel: descales within 1e-6, values within 1 e4m3 ulp. It is much slower here, though:

| Tokens | This kernel (Q/K/V, one call) | `scaled_fp8_quant` ×3 | ×3, V made contiguous first |
|---:|---:|---:|---:|
| 1,024 | 50 µs | 189 µs | 59 µs |
| 8,192 | 50 µs | 1,318 µs | 237 µs |
| 65,536 | 352 µs | 10,165 µs | 1,306 µs |

Why it is slower:
- It takes one 2D tensor per call, so Q/K/V need 3 × (memset + amax + quant).
- V's row stride sends it down the per-row path: one 256-thread block and one `atomicMax` per 128-element row, and there are T×H rows. At 65K tokens, V alone takes 9.3 ms there versus 110 µs here.
- An all-zero input gets descale 0.

This kernel is adapted from ATOM's fused QKV quantizer. The one change is that token counts are runtime args, so varying batch shapes don't recompile.

I'd be happy to move it somewhere more general, or to fix the strided path of `dynamic_scaled_fp8_quant` in a follow-up, if you prefer.

Yes. `forward_mha` passes `out` only together with `output_scale`, i.e. fused quantized output. That requires `supports_quant_output()`, which this backend doesn't claim (neither does `ROCM_AITER_FA`), so `out` is always `None` here and FlyDSL allocates the output itself.

If a caller did pass `out`, FlyDSL would write into it: it validates a contiguous BF16 `[T, H, Dv]` buffer.

I kept `supports_out()` False because nothing on the ROCm MLA path consumes it yet; only the Kimi-K3 NVIDIA module does. The context-chunk path asserts `out is None`.

Saving the extra `output.copy_` for context-free prefills could be a follow-up with numbers.
