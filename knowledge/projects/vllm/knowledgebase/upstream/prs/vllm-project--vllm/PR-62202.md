# [ROCm] Enable RDNA3 MXFP4 kernels on gfx1151 and for DeepSeek-V4

[Upstream PR](https://github.com/vllm-project/vllm/pull/62202) · state: open · merged: False

## Original PR description

> **Stacked on #46676.** The first commit is #46676 squashed and rebased onto main (authored by @JartX, unchanged apart from one enum conflict). **Only the second commit is new in this PR.** I'll rebase onto main once #46676 merges.

## Purpose

#46676 adds native MXFP4 kernels for gfx1100. gfx1151 (Strix Halo / Radeon 8060S) has the same WMMA and dot instructions, and the kernels compile to identical code on both, but #46676 gates them to gfx1100 only. On top of #46676, this PR:

- Opens the gfx1100 gates to gfx1151: the two kernel files, the CMake source gate, and the dense + MoE support checks.
- On gfx1151, uses the scalar `bsm=4` tile instead of WMMA-16 for steps of 16+ rows. WMMA-16 is 1.5–57× slower there at every shape I tried (table below). gfx1100 keeps #46676's rule.
- Makes the backend reachable from DeepSeek-V4, which loads its experts through `Mxfp4MoEMethod`: `RDNA3_MXFP4` goes before `TRITON_UNFUSED` in its ROCm priority, and the repack uses `gate_up_interleaved=False`, because DeepSeek-V4 stores `gate_proj`/`up_proj` contiguously.

Tests: a new dispatch test for the gfx1151 tile rule.

## Duplicate-work check

Searched open PRs for MXFP4 on gfx1151 / gfx11 / Strix Halo and for `RDNA3_MXFP4`. No duplicate.

- #46676 is the base. This PR depends on it.
- #52970 (AITER on RDNA) does not touch the MXFP4 MoE path. The DeepSeek-V4 numbers below include it.
- #62197 fixes an unrelated gfx11 decode bug that makes DeepSeek-V4 decode garbage with either MoE backend. Both DeepSeek-V4 arms below include it.

## Test Result

All on gfx1151, with `_rocm_C` built from the branch. Unit tests ran on this branch; end-to-end runs used the ROCm nightly wheel (main @ 49cb2bbf7) + #46676 + the new commit, `--enforce-eager`.

```
pytest tests/kernels/quantization/test_mxfp4_rdna3.py           24 passed (all skipped before)
       tests/kernels/quantization/test_mxfp4_rdna3_dispatch.py  223 passed
       tests/kernels/quantization/test_mxfp4_kernel_selection.py 27 passed
```

The MoE kernel matches a dequantized fp32 reference for every tile at DeepSeek-V4 shapes: 80/80 within the `eps·Σ|x||w|` bound from `test_mxfp4_rdna3.py`.

**Tile choice on gfx1151**: MoE gate_up + down in ms, DeepSeek-V4 TP=2 shapes (E=256, H=4096, I=1024, top-6). Expert sets rotate so weights stream from DRAM:

| rows (M) | WMMA-16 | bsm=4 | speedup |
|---|---|---|---|
| 16   | 11.43 | 2.52  | 4.5× |
| 64   | 315.9 | 6.60  | 47.9× |
| 256  | 620.9 | 10.82 | 57.4× |
| 2048 | 1217  | 131.2 | 9.3× |

**`openai/gpt-oss-20b` (1× gfx1151)**: `vllm bench serve`, random 2048-in / 128-out, concurrency 1, native MXFP4 vs the Triton path it replaces:

| | TRITON | RDNA3_MXFP4 | speedup |
|---|---|---|---|
| mean TPOT (ms)      | 73.8  | 19.3  | 3.8× |
| output tok/s        | 12.6  | 25.7  | 2.03× |
| mean TTFT (ms)      | 751   | 2542  | 0.30× |
| GSM8K (first 25)    | 25/25 | 25/25 | |

**`deepseek-ai/DeepSeek-V4-Flash-0731` (TP2 over 2× gfx1151, both arms with #52970 and `VLLM_ROCM_USE_AITER=1`)**: `llama-benchy --pp 2048 --tg 128 --runs 6`, concurrency 1:
