# [ROCm][DSv4.1] MXFP4 compressed KV cache (mxfp4_ds_mla) on gfx950

[Upstream PR](https://github.com/vllm-project/vllm/pull/64120) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Adds `--kv-cache-dtype mxfp4_ds_mla` for DeepSeek-V4.1 on ROCm gfx950 (MI350/MI355). It is the CDNA4 counterpart of NVIDIA's `nvfp4_ds_mla`: the sliding-window cache keeps its fp8 record, and the compressed cache stores 272 B MXFP4 records. It is meant to be used with the existing MXFP4 indexer (`--attention-config '{"indexer_kv_dtype": "mxfp4"}'`).

**Draft, and stacked on other PRs.** The first two commits are [#57523](https://github.com/vllm-project/vllm/pull/57523) (which includes [#57463](https://github.com/vllm-project/vllm/pull/57463)), rebased onto main by me with the authors' commits and authorship kept. Only the last two commits are new:
1. `Read the interleaved V4.1 records in the gfx950 decode tile`: a fix #57523 needs after the rebase (details below).
2. `Add the mxfp4_ds_mla compressed KV cache on gfx950`: this PR.
3. `Native scaled-MFMA QK and PxV for the MXFP4 MLA record` (`1a240688c`, after a merge of main): the decode reads the record with `tl.dot_scaled` instead of dequantizing it.
4. `Optional dequant fallback for small decode batches` (`3ef079e21`): `VLLM_ROCM_DSV41_MXFP4_DEQUANT_BELOW_ROWS=N` sends decode batches with fewer than N query rows through the bf16 dequant tile. It defaults to 0, which keeps the native tile at every batch size.
5. `Faster native decode tile at small batches` (`c953998b1`): optimized with AMD GEAK. The native tile is now within 0.5–0.6 µs of the stock FP8 tile at 1–16 rows and 17–27% faster from 64 rows up (see "Native decode" below).
6. `Packed KV planner: pick the block width that reserves the fewest bytes` (`df07ea7f3`): a generic planner fix that lets the smaller records turn into capacity (see "KV capacity" below). It is split out as [#64381](https://github.com/vllm-project/vllm/pull/64381), which this one stacks on: `66256d9f7` merges #64381's branch (and with it main `ce775739e`) into this one, so this PR's planner files match #64381's exactly. The merge's one conflict was the NVFP4 K gather in `deepseek_v41/common/ops/cache_utils.py`: main tiled it, and the resolution adds this PR's UE8M0 scales to the tiled kernel. The MXFP4 gather and record tests pass on MI355X after the merge (`test_rocm_dsv41_mxfp4_kv_cache.py`, `test_rocm_sparse_mla_v41_records.py`, `test_compressor_kv_cache.py`: 174 passed, the rest skipped as not applicable).

The MXFP4 half of [#57489](https://github.com/vllm-project/vllm/pull/57489) (stale draft, @LiuYinfeng01, credited as co-author) is revived here. It is rewritten on top of #57523's width-keyed decode tile and uses the quantizer from [#60321](https://github.com/vllm-project/vllm/pull/60321). Monokernel support is a separate follow-up; until then `--monokernel` keeps its documented FFN-launch fallback for this dtype.

## Claims

- New cache dtype `mxfp4_ds_mla`, gfx950 only. Each compressed token is 512 post-RoPE dims as E2M1 pairs (even dim in the low nibble), followed by 16 UE8M0 scales of 32 dims. The scales are interleaved after each token's data, as in the other V4.1 records. That is 272 B per token, against 528 B (MXFP8) or 584 B (V4) for the compressed cache today.
- The writer is bit-exact with the `mxfp4_mla` quantizer from #60321: the scale is `ceil_pow2(amax/6)`, taken on the fp32 bit pattern so it is exact at powers of two; the code is clamped to [1, 254]; all-zero groups get code 127; E2M1 rounds half to even.
- Prefill gathers and decode reads the record in place. The gfx950 split-K tile feeds it straight to the block-scaled MFMA (`v_mfma_scale_f32_16x16x128_f8f6f4`) for both QK and P×V, without dequantizing. The record layout is unchanged (see "Native decode" below).
- Accuracy is unchanged: GSM8K 96.66% (mean of 3) against 96.79% for the FP8 baseline.
- **Throughput is unchanged** on this model (see the table below). In DSv4.1-Flash only 4 layers own a compressed cache and sparse decode reads a fixed top-512 set, so the compressed record is a small part of decode traffic.
- **Capacity:** without commit 6, the packer turns the smaller pages into more groups rather than more blocks (18 groups against 9), and MXFP4 holds about 9% fewer tokens than FP8. With commit 6 it holds 2.6% more (offline planner replay; a measured boot is pending, see "KV capacity" below).

## Details

**Why the extra fix commit.** [#61371](https://github.com/vllm-project/vllm/pull/61371) (Sep 30) moved the V4.1 MXFP8 (528 B) and NVFP4 (288 B) records to FlashMLA's interleaved layout. The writers and the prefill gathers on main use it. #57523 was written a day earlier and addresses those records page-segregated in the gfx950 decode tile, so after the rebase its decode would read the wrong bytes. The fix commit addresses both V4.1 records per token and leaves the V4 (584 B) page segregated. It also builds that test's pages the same way.

**Design notes:**
- Width-keyed like the other records. The writer, the gather and the decode tile all dispatch on `k_cache.shape[-1] == 272`. The spec plumbing adds the 272 B compressed width, `mxfp4_ds_mla` at the three packed-page sites (compressed, indexer, SWA), `KVQuantMode.MXFP4_DS_MLA` and a `reads_mxfp4_compressed_cache` gate, which is true only for the ROCm attention on gfx950.
- `VLLM_ROCM_USE_AITER_TRITON_SPARSE_MLA` is ignored, with a warning, for FP4 compressed caches, because the aiter kernel reads fp8 only.
- The extra-cache NaN trust covers `mxfp4_ds_mla`. E2M1 has no NaN encoding and the writer caps the scale code at 254, so a canonically written record cannot decode to NaN. KV connectors still disable the trust.
- The quantizer helpers sit in a small shared module, `vllm/v1/attention/ops/mxfp4_e2m1.py`, so #60321's `mxfp4_mla` cache can import them rather than keep a second copy. Whichever PR lands second will switch to it.

**Native decode (commits 3 and 5).**
- QK reduces over dims, and the record's scale is per (token, 32 dims). That matches the MFMA's B-operand scale, so K is used as stored. Q is MXFP8-quantized once per program.
- P×V reduces over tokens, and the MFMA wants V scales per (dim, 32 tokens), which the record doesn't have. Changing the record was rejected: a 32×32 block scale, or a second scale copy indexed by token blocks, can't be finalized when one compressed token is written alone. Instead each token's power-of-two scale is folded into P for each 32-dim group: `P_q = P · 2^(code_t − c_blk)`, with `c_blk = max(code over the 32-token block) − 8`, which keeps `P_q ≤ 256` within e4m3. `c_blk` becomes P's E8M0 scale, and V is used with a unit scale (`rhs_k_pack=False`). Commit 3 did that as 16 dots of N = 32 per 128-token tile. Commit 5 folds the same power of two into V instead (exact for shifts ≥ −8, and below that it flushes like the P fold), so P is converted once and P×V is 4 accumulating scaled MFMAs. The scaled MFMA's K is 128, so the compressed segment runs 128-token tiles; the SWA segment is unchanged.
- Commit 5 also transposes the native QK (tokens on M), which removes warp-redundant MFMAs and brings the tile from 368 to 248 VGPRs, so two 4-warp CTAs fit per CU. It uses split counts that give each split one 128-token tile, 4 warps while the grid fits in two CTAs per CU (2 beyond that), and it prefetches the next tile's slots.
- Batching the 16 groups into one 3D `dot_scaled` crashes `TritonAMDGPUAccelerateMatmul` on Triton 3.8.0.

Kernel time in µs: 16 heads per rank (TP4), top-512 compressed plus 128 SWA tokens, ragged indices precomputed as the model does, CUDA-graph replay, `triton.testing.do_bench`:

| decode rows | 1 | 4 | 16 | 64 | 128 | 256 |
|---|---|---|---|---|---|---|
| FP8, V4 584 + 584 (stock) | 23.6 | 24.0 | 24.7 | 33.7 | 40.5 | 62.1 |
| MXFP4 528 + 272, dequant to bf16 (before) | 23.2 | 23.8 | 24.3 | 44.1 | 57.4 | 92.5 |
| MXFP4 528 + 272, native, commit 3 | 42.8 | 43.4 | 44.0 | 50.9 | 51.4 | 78.6 |
| MXFP4 528 + 272, native, commit 5 | 24.1 | 24.5 | 25.3 | 28.1 | 33.5 | 45.2 |

All rows except commit 3 come from one session at `c953998b1` (`kbench_decode.py`); the commit 3 row is from its own session. With commit 5 the native tile is 0.5–0.6 µs slower than stock FP8 at 1–16 rows and 17–27% faster from 64 rows up. Attention is about 10–15% of a decode step on this model. The end-to-end table above was measured on the dequant tile (`fb22b513e`) and will be re-measured.

**Small-batch fallback (commit 4).** End to end, the commit 3 native tile was slower than FP8 at small batches: the median TPOT at TP4 is 10.02 vs 9.17 ms at c16 (+9.3%), 16.37 vs 15.52 ms at 8K c64 (+5.5%), and 24.55 vs 24.13 ms at c256 (+1.7%). `VLLM_ROCM_DSV41_MXFP4_DEQUANT_BELOW_ROWS` lets small batches use the dequant tile instead. It is off by default. Commit 5 closes most of that kernel gap, and the end-to-end numbers will be re-measured on it. Unit tests run the 272 B record with the flag at 0 and at 1024: 95 passed, 32 skipped (the skips are the non-MXFP4 records, for which the flag has no effect).

**KV capacity (commit 6).** `_get_packed_kv_cache_groups` capped sliding-window and state buckets at the widest group (the anchor). Each group then reserves its own blocks per request, and on this model the sliding-window reservation dominates: at 64K context with 32K tokens in flight, each SWA group reserves 1029 blocks per request against 1024 for the compressed cache. Smaller compressed and indexer records shrink the anchor, so the 40 SWA layers split into more, narrower groups and the reserved bytes per request grow. Commit 6 also tries the widths at which a state bucket fits in one group, and keeps the grouping that reserves the fewest bytes per request. The anchor is still a candidate, so the fix never reserves more than before.

The numbers come from replaying the planner on CPU with the layer specs rebuilt from the checkpoint's `config.json`. The rebuilt specs match a real boot's planner dump field for field, and the replay reproduces that boot's logged count exactly (12,205,275 tokens). KV tokens at 166.55 GiB per rank, 64K context, 32K tokens in flight, and #57523's 528 B SWA record in both arms:

| | `fp8_ds_mla` | `mxfp4_ds_mla` | MXFP4 vs FP8 |
|---|---|---|---|
| Before commit 6 | 13,289,240 | 12,086,294 | −9.1% |
| With commit 6 | 14,052,872 (+5.7%) | 14,423,097 (+19.3%) | +2.6% |

The gain depends on how much the SWA reservation dominates. With the fix, MXFP4 against FP8 is +9.7% at 16K tokens in flight, +17.1% at 8K, +9.7% at 128K context and −1.4% at 16K context. Unit tests: a new case in `test_contiguous_kv_packing.py` covers the widened block. Two existing cases encoded the old cap at `max_model_len=16` and now run at 64K, and the mock configs gained `max_in_flight_tokens`. `tests/v1/core/` on MI355X: 203 passed.

**Limitations:**
- gfx950 only; other archs are refused at layer construction.
- The record is not readable by the monokernel yet (follow-up PR).
- No user-facing doc page lists the `_ds_mla` dtypes. The `CacheConfig` docstring, which feeds the CLI reference, documents the new one.
