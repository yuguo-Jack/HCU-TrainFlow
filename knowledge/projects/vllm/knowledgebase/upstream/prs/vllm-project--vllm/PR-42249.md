# Add recompute partial rollout sleep mode

[Upstream PR](https://github.com/vllm-project/vllm/pull/42249) · state: open · merged: False

## Original PR description

 ## Purpose

  This PR adds a `recompute` pause/sleep mode for hybrid partial rollout.

  The existing partial rollout sleep path can pause requests and offload weights while keeping KV
  cache resident on GPU. That is fast to resume, but it still consumes GPU memory during colocated
  training.

  This PR introduces a new mode:

  ```python
  llm.sleep(mode="recompute")

  With mode="recompute", vLLM preserves in-flight request/token state, releases KV cache memory
  during sleep, and recomputes KV from prompt + generated tokens after wake/resume before continuing
   generation.

  Main changes:

  - Add recompute pause mode.
  - Preserve request state while forcing KV/prefix cache invalidation.
  - Mark paused running requests for recomputation on resume.
  - Ensure staged wake-up does not resume scheduling too early:
    - wake_up(tags=["weights"]) wakes weights only.
    - scheduler remains paused while KV cache is still sleeping.
    - scheduler resumes only after required resources, including kv_cache, are awake.
  - Update sleep mode docs.
  - Add a partial rollout pause/resume example.

  This is useful for colocated RL partial rollout where training needs to reclaim KV cache GPU
  memory between rollout chunks.

  Notes for upper-level frameworks such as OpenRLHF

  Frameworks that integrate vLLM for colocated RL partial rollout need to choose the correct sleep
  mode depending on their memory/resume tradeoff.

  For the existing fast-resume behavior, frameworks may continue using:

  llm.sleep(mode="keep", offload_tags=["weights"])

  This keeps request state and KV cache alive, and only offloads selected memory such as weights.

  For memory-constrained colocated training, frameworks should use:

  llm.sleep(mode="recompute")

  or the corresponding async/API path with recompute pause mode.

  Important integration details:

  - mode="recompute" is intended for partial rollout where in-flight generation should continue
  after training.
  - The upper-level framework should not abort or recreate in-flight rollout requests during this
  sleep window.
  - The request/generator should remain alive so vLLM can resume it after recomputing KV.
  - mode="recompute" releases KV cache memory during sleep, but resume is slower than mode="keep"
  because prompt + generated tokens need to be recomputed.
  - If the framework performs staged wake-up, it must not resume generation after waking weights
  only:
    - wake_up(tags=["weights"]) is useful before loading/syncing updated weights.
    - generation should resume only after KV cache resources are also awake.
    - use full wake-up, or explicitly wake the remaining tags such as kv_cache, before continuing
  rollout.
  - Framework wrappers should expose the sleep mode instead of hardcoding the old behavior.
  - mode="abort" should not be used for partial rollout continuation, because it drops in-flight
  requests instead of preserving them.

  For OpenRLHF-style colocated training, the expected flow is:

  1. generate rollout chunk with vLLM
  2. pause vLLM with recompute mode
  3. release KV cache and offload model memory
  4. run trainer/update step
  5. wake weights and synchronize updated weights if needed
  6. wake remaining vLLM resources, including KV cache
  7. resume rollout; vLLM recomputes KV and continues generation

  This allows OpenRLHF-like frameworks to trade additional recompute time for lower peak GPU memory
  during training.

## Code Review

This pull request introduces tag-wise selective sleep to support hybrid co-location with partial rollouts, allowing specific GPU memory pools to be offloaded while others remain mapped. It also adds a recompute pause mode that releases KV cache while preserving request state. Feedback identifies a logical inconsistency where recompute mode might fail to reclaim memory if used with empty offload tags or level 0 sleep. Additionally, a potential crash was noted during staged wake-ups from level 2 sleep if model buffers are restored before the corresponding memory pool is remapped.

File: `vllm/v1/engine/core.py` · line 756

![high](https://www.gstatic.com/codereviewagent/high-priority.svg)

If `mode="recompute"` is used with `offload_tags=[]` or `level=0`, the scheduler state will be cleared (invalidating KV cache logically), but the GPU memory for the KV cache will not be released because the executor sleep path is skipped. This contradicts the intended behavior of the `recompute` mode which is to reclaim GPU memory. Consider enforcing that `recompute` mode always triggers a memory release for the KV cache tag.

- gemini-code-assist[bot] · comment · 2026-05-10T21:31:05Z · [source](https://github.com/vllm-project/vllm/pull/42249#discussion_r3215558912)

File: `vllm/v1/worker/gpu_worker.py` · line 250

![high](https://www.gstatic.com/codereviewagent/high-priority.svg)

In a staged wake-up scenario following a `level=2` sleep, if `wake_up(tags=["kv_cache"])` is called before weights are restored, `buffer.data.copy_` will attempt to copy data into tensors whose underlying memory (on the weights pool) is still unmapped. This will likely result in a CUDA error or a crash. Although this is an existing issue for legacy sleep levels, the introduction of fine-grained tag-wise wake-up makes this failure path more accessible.
