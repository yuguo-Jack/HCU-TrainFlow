# [Bugfix][Frontend] Set `completed_at` on completed Responses API responses

[Upstream PR](https://github.com/vllm-project/vllm/pull/63234) · state: closed · merged: False

## Original PR description

## Overview

`/v1/responses` never returns `completed_at`, even when `status` is `"completed"`, so OpenAI SDK clients always read `response.completed_at` as `None`. This PR sets it on completed responses. Fixes #63183.

## Claims

- Completed responses carry `completed_at` (Unix seconds, `>= created_at`) on all three paths: the non-streaming response, the `response.completed` stream event, and background responses retrieved later.
- `completed_at` is `null` for `queued`, `in_progress`, `incomplete`, `failed` and `cancelled` responses. This matches the OpenAI Response object, where it is "only present when the status is `completed`".

## Details

**Root cause:** `ResponsesResponse` declared `created_at` but no `completed_at`, and `ResponsesResponse.from_request` had no way to set it.

**Fix:** I added `completed_at: int | None = None` and set it in `from_request` when `status == "completed"`. Every response object on this route is built by `from_request`, so this one change covers all three paths:

- non-streaming responses from `responses_full_generator`
- the stream's terminal event, which reuses the result of that generator
- the background store

A background response is first stored as `queued` with `completed_at=None`. When it finishes, the completed object replaces it, so `GET /v1/responses/{id}` returns the timestamp. Cancel and failure only change `status` on the stored object, so `completed_at` stays `null`.

**Type:** I used `int` to match vLLM's existing `created_at: int`. The SDK field is `Optional[float]` and accepts integers.

**Not a duplicate:** No open PR references this issue or `completed_at`. #38616 made a similar change but was closed as stale on 2026-07-31 without being merged. #62856 echoes other Response fields and does not touch `completed_at`.
