# [Metrics] Add vllm:kv_load_failed_tokens counter

[Upstream PR](https://github.com/vllm-project/vllm/pull/64026) · state: open · merged: False

## Original PR description

Adds a per-engine Prometheus counter, `vllm:kv_load_failed_tokens`, for the computed tokens lost when a KV connector's load fails. The scheduler already computes this number and logs it, but no metric exposes it.
## Overview
When a KV connector reports a failed load, the scheduler rolls back the affected requests' computed tokens and, per `kv_load_failure_policy`, either recomputes them (`recompute`) or fails the requests (`fail`). Today the only record is a log line:
```
Failing N request(s) due to KV load failure (failure_policy=fail, M tokens affected). Request IDs: ...
Recovered from KV load failure: N request(s) rescheduled (M tokens affected).
```
Operators running P/D disaggregation or KV offloading can't graph or alert on how much prefill work failed loads cost. This PR exports that number as `vllm:kv_load_failed_tokens` (`vllm:kv_load_failed_tokens_total`, labels `model_name`, `engine`). It counts in the scheduler, so it works with every KV connector without connector changes.
## Claims
- `vllm:kv_load_failed_tokens_total` increases by the same "tokens affected" total the scheduler logs for block-level failures (`invalid_block_ids`), under both policies.
- For whole-request failures (`failed_recving`), it increases by the request's computed tokens, which are discarded (`recompute`) or lost with the request (`fail`). Today no log line reports this.
- Each failure is reported once under both policies, including when a connector reports both `failed_recving` and `invalid_block_ids` in the same step (`_handle_invalid_blocks` skips requests already handled in `_handle_failed_recving`). The count drains into `SchedulerStats` every step.
- Registered only when `kv_transfer_config is not None` (`self.kv_load_failure_metrics_enabled`), matching #64023 (`vllm:kv_load_failed_requests`) and `vllm:num_requests_kv_fetch_by_stage`.

End-to-end on GKE, run on the previous revision of this PR (before the review changes). Neither change affects that run: the TPU connector never reports `failed_recving`, and `kv_transfer_config` is set in P/D. I cherry-picked it onto `v0.32.0` with stock `vllm-torchtpu` `main`, which has no plugin copy of this counter: TPU v5e, Qwen2.5-7B-Instruct, P/D via llm-d with `TPUConnector` + Raiden, `block_size=128`, `kv_load_failure_policy=fail`. ## Details
- **Where it counts:**
  - `_handle_invalid_blocks()` adds the `total_failed_tokens` it already computes for its log line (excluding any `already_failed_req_ids` already counted by `_handle_failed_recving()`);
  - `_handle_failed_recving()` adds `request.num_computed_tokens` before resetting it;
  - `make_stats()` moves the total into the new `SchedulerStats.num_kv_load_failed_tokens` and resets it;
  - `PrometheusStatLogger.record()` increments `vllm:kv_load_failed_tokens` when `kv_load_failure_metrics_enabled` is true.
- **Registration policy:** gated on `kv_transfer_config is not None` (`self.kv_load_failure_metrics_enabled = kv_transfer_config is not None`), matching #64023 (`vllm:kv_load_failed_requests`) and `vllm:num_requests_kv_fetch_by_stage`. Documented automatically in the generated metrics list (`gen:metrics-general`) on the [metrics page](https://docs.vllm.ai/en/latest/usage/metrics.html).
- **Small scheduler change:** under `fail`, `_handle_invalid_blocks` now skips async requests that `_handle_failed_recving` has already failed in the same step. Those requests finish with an error regardless. The only visible difference is that the "Failing N request(s)" log line no longer counts them twice. Under `recompute`, `_handle_failed_recving` returns an empty set and zeroes `num_computed_tokens`, so nothing changes there.
- **Limitations:**
  - For a `failed_recving` request, the count includes any local prefix-cache hit tokens, because the scheduler rolls those back too.
- **Rust frontend:** its `SchedulerStats` decoder ignores unknown fields, so it is unaffected. It doesn't export this counter yet; that can be a follow-up.
- Pairs with #64023 (`vllm:kv_load_failed_requests`) as part of a broader HBM KV cache observability effort.

Note on the `policy="fail"` interaction between `_handle_failed_recving` and `_handle_invalid_blocks` and the PR description:

In `update_from_output` (lines 2267–2280), `_handle_failed_recving` runs before `_handle_invalid_blocks`. Under `recompute`, line 3650 resets `request.num_computed_tokens = 0`, which prevents `_handle_invalid_blocks` from recounting the request if its blocks also appear in `invalid_block_ids`. Under `fail` (`self.recompute_kv_load_failures == False`), `request.num_computed_tokens` stays non-zero and `request.status` stays `WAITING_FOR_REMOTE_KVS` until `finish_requests` at line 2540, so `_handle_invalid_blocks` will scan the request a second time and double-count its failed tokens (as noted in the **Limitations** section of the PR description).

However, the **Validation** section of the PR description currently states the opposite for the `kv_load_failure_policy=fail` GKE run:
> *"The worker reports every failed request id twice, as `failed_recving` and as invalid blocks; the counter still matches the log total exactly, so no request was counted twice."*

(On vLLM `v0.32.0`, `vllm-torchtpu`'s `tpu_runner.py` `_build_kv_connector_output` calls `get_finished()` and never sets `failed_recving`, which is why `_handle_failed_recving` was not triggered in that run.) We should either update that sentence in the PR description to match **Limitations**, or filter out `failed_kv_load_req_ids` when building `async_load_reqs` in `_handle_invalid_blocks` so `policy="fail"` also avoids double-counting.
