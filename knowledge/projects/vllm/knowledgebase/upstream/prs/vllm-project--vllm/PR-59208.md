# [Bugfix][Distributed] Guard cross-node symmetric-memory rendezvous

[Upstream PR](https://github.com/vllm-project/vllm/pull/59208) · state: open · merged: False

## Original PR description



## Purpose

Cross-node symmetric-memory rendezvous is safe only when every rank belongs to
the same NVLink fabric. Without a topology check, unsupported groups can hang
or fail during CUDA memory import. This affects generic symmetric-memory
all-reduce as well as Direct DCP, custom all-reduce, Async TP, GEMM RS/AR, and
the Kimi K3 latent-MoE tail fusion.

This change:

- classifies groups as `INTRA_NODE`, `CROSS_NODE_NVLINK`, or `UNSUPPORTED`;
- reads the fabric UUID and clique ID through vLLM's vendored NVML V2 API
  (`c_nvmlGpuFabricInfoV_t` and `nvmlDeviceGetGpuFabricInfoV`), without spawning
  `nvidia-smi`;
- fails closed when fabric metadata is absent, invalid, or differs across
  ranks;
- applies the topology guard before entering symmetric-memory rendezvous; and
- prevents forced Direct DCP settings from bypassing topology safety.

The legacy `nvmlDeviceGetGpuFabricInfo` structure is not compatible with the
GB300 driver used for validation: it exposed zero clique/state fields. The versioned
V2 call returns correct UUID and clique.

AI assistance was used.

## Test Plan

- Run `git diff --check` and pre-commit on both changed files.
- Run `tests/distributed/test_nvlink_fabric.py` in the GB300 validation image.
- On H100, B200, and GB300 clusters, allocate two nodes, then
  launch eight ranks (four GPUs per node) against exact baseline and patched
  source snapshots using PyTorch `2.13.0+cu130`.
- For each topology, inspect raw NVLink fabric metadata, exercise Direct CP in
  forced and automatic modes, initialize `SymmMemCommunicator`, and validate a
  BF16 all-reduce. Each potentially unsafe stage has a 180-second timeout.
- On GB300, test both two nodes within one NVL72 group and two nodes from
  different NVL72 groups.

No model evaluation was run: the change affects collective selection rather
than model numerics. Collective correctness was checked on all eight ranks;
the expected and observed BF16 sum was 36.

Validated an adaptation of this PR against the real workload from #59185 on two B200 nodes without a multi-node NVLink fabric, using two GPUs per node, TP=4, the Ray executor, and default communicator settings.

| Workload | Stock | With the adapted patch |
| --- | --- | --- |
| Qwen3.6-35B-A3B FP8, TP4 | Startup failed after 1,940 s | Startup and GSM8K 10% evaluation passed in 574 s; accuracy 0.432 |
| Qwen3.6-35B-A3B NVFP4, TP4 | Startup failed after 1,990 s | Evaluation passed in 483 s; accuracy 0.114 |
| TP2 regression control, one GPU per node | Passed; accuracy 0.939 | Passed; accuracy 0.947 |

Both stock TP4 runs reproduced the 1,800 s Gloo timeout in `_node_count` → `in_the_same_node_as`, followed by `Application timeout caused pair closure`. With the patch, every rank logged that the multi-node group does not share an NVLink fabric and skipped symmetric memory and custom collectives. The NVFP4 score is within the observed 0.09–0.13 range for this checkpoint; this validates startup completion, not an accuracy improvement.

Environment: vLLM `0.31.1rc1.dev253+g7d0b4e57a`, PyTorch `2.13.0+cu130`, CUDA 13.0.2, NVIDIA driver 580.82.07, FlashInfer `0.7.0.post1`, Ray `2.59.0`, Python 3.12.3, Ubuntu 24.04. Both arms used the same pinned image base:
`vllm/vllm-openai:nightly@sha256:2b3b0fe155011cbca03828e35fe1a483c1b5c9cf44c807cdee6ab51db734d553`.
Build assertions checked patch absence in stock and the expected patched file hashes in treatment.

Revision caveat: this tested the runtime changes from PR head `54da1d9ba3cb67a54e4384e710580c2b005c1fea` adapted onto `7d0b4e57a`, **not the exact PR head or current main**. The adaptation dropped the AsyncTP hunks because #60517 removed that code, and resolved the custom-all-reduce docstring conflict using the PR text.
