## Original PR description

This PR is split from the original full PR: https://github.com/vllm-project/vllm/pull/58568

Add compact whole-block load and store plans, plus transfer cancellation.
Coordinate asynchronous lookup with hybrid and Mamba groups. Full-attention hits stay prefix-closed, and Mamba or sparse groups restore their own state.
Add partial hash hits, KV events, eviction reporting, and transfer metrics.

- tjtanaa · comment · 2026-10-22T00:49:46Z · [source](https://github.com/vllm-project/vllm/pull/61791#discussion_r4343472785)

Slicing off `local_tokens` changes the coordinate system used by the core cache managers. This is unsafe for chunked-local attention, whose active chunk depends on the absolute token position.
For example, with block size 16, attention chunk size 64, a 16-token local prefix, and an 81-token prompt, the external candidate is 64 tokens. The sliced lookup treats that as a chunk boundary and can return all-null chunked-local blocks, even though the resulting absolute hit is 80 and KV for tokens 64–79 is required. `_load_plans_for_external_tokens()` then skips those null entries.
Please preserve absolute positions when coordinating external hits, or explicitly reject the unsupported case until it is handled. Add a regression with a nonzero local prefix that is block-aligned but not attention-chunk-aligned.

- tjtanaa · comment · 2026-10-22T00:51:03Z · [source](https://github.com/vllm-project/vllm/pull/61791#discussion_r4343479086)

File: `vllm/distributed/kv_transfer/kv_connector/v1/umbp/scheduler.py` · line 1133

Please derive these boundaries using core’s `replay_boundaries(..., use_eagle=self.use_eagle)` rather than always using `num_prompt_tokens - 1`.
With EAGLE and sparse retention, this can discard the tail needed for the next lookup. For a 65-token prompt, block size `16`, sliding window `32`, and retention interval `0`, the current boundary stores SWA block indices `[2, 3]`; the EAGLE-adjusted boundary retains `[1, 2, 3]`, which is required to match and drop back to 48 tokens.
Please add a regression using the real sliding-window mask and hit finder. The existing mocked-mask test verifies forwarding of arguments, but cannot catch disagreement with core’s EAGLE replay semantics.

- tjtanaa · comment · 2026-10-22T00:52:09Z · [source](https://github.com/vllm-project/vllm/pull/61791#discussion_r4343484639)

File: `vllm/distributed/kv_transfer/kv_connector/v1/umbp/scheduler.py` · line None

A successful store quorum does not guarantee the object is still resident on the ranks that completed earlier.
Consider TP2: rank 0 completes, then evicts the object and emits `BlockRemoved` in an earlier step; rank 1 completes later. This code then emits `BlockStored`, leaving consumers with a stored event for an object that is no longer present on every rank.
Please reconcile evictions with pending publication attempts—for example, with attempt-scoped invalidation or an authoritative residency check before publication. Keep block-pin release separate from whether a `BlockStored` event is emitted. Please add a cross-step regression for “rank 0 complete → rank 0 eviction → rank 1 complete.”
