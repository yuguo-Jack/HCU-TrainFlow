# [Kernel] Separate what the GDN prefill selector can run from what it prefers

[Upstream PR](https://github.com/vllm-project/vllm/pull/63284) · state: open · merged: False

## Original PR description



## Overview

`--gdn-prefill-backend` uses one capability list both to resolve `auto` and to veto an explicit choice, so asking for `flashinfer` on a device the list doesn't name logs a warning and runs Triton anyway. This splits "can it run here" from "should `auto` pick it", and passes FlashInfer the prefill lengths it needs once it does run. The SM8x path comes from [FlashInfer #5109](https://github.com/flashinfer-ai/flashinfer/pull/5109), which is merged and ships in the next FlashInfer release; it becomes usable once vLLM's FlashInfer pin moves to that release. On the current 0.7.2.post1 pin, `auto` picks what it picked before, and an explicit `flashinfer` on SM8x fails at startup with FlashInfer's own error.

## Claims

- A named backend runs where it can and fails at startup where it can't, instead of quietly running something else. When the selector refuses it, the message names the device, `head_k_dim` and the alternative.
- `auto` makes the same choice as before on every platform.
- SM8x with `head_k_dim == 128` is allowed by the selector, but not preferred. Running it needs a FlashInfer build with the SM8x GDN prefill.
- The prefill gets the longest prefill length and a host copy of the prefill `cu_seqlens` without a device-to-host sync. With that FlashInfer PR on sm_80 (2048 tokens, 48 value heads), passing the length takes peak prefill memory from 159.0 MiB to 132.0 MiB.

## Validation

sm_80, main (`32551991b9`) plus this PR, with FlashInfer built from the [FlashInfer #5109](https://github.com/flashinfer-ai/flashinfer/pull/5109) branch:

```text
pytest tests/kernels/mamba/test_gdn_prefill_backend_selection.py   # 13 passed
pytest tests/kernels/mamba/ -k gdn                                 # 36 passed, 21 skipped
pytest tests/v1/attention -k gdn                                   # 78 passed, 10 skipped
```

`test_gdn_prefill_backend_selection.py` is new. It covers SM8x being runnable but not the default, refusal instead of substitution on an unsupported device, the `head_k_dim` gate, unchanged SM90, SM100 and non-CUDA choices, and which keywords the adapter passes to builds with and without `max_seqlen` and `cu_seqlens_cpu`.

## Details

The selector allows a backend from the device capability; actually running it also needs an installed FlashInfer build that has the kernel. Whether `auto` should pick it depends on having measured it against the fallback. New architecture support is runnable before it has been measured, which is why SM8x goes into the first set and not the second. SM8x is allowed from the device capability like SM90, SM100 and SM120, and only the public `chunk_gated_delta_rule` is called. `max_seqlen` and `cu_seqlens_cpu` are only passed to builds whose signature takes them; 0.7.2 has the first and not the second.

`GDNAttentionMetadata` gains `prefill_max_seq_len` and `prefill_query_start_loc_cpu`, taken from the host prefix the builder already holds. When FlashInfer is active, the long-prefill warmup passes them as well and also runs the width of a full prefill batch, which is where FlashInfer switches kernels. A warmup failure for a backend the user named is raised instead of being logged as a slow first request.

`test_gdn_fused_mtp.py` asked for `cutedsl` and only passed off SM100 because the selector substituted Triton. It now asks for `auto` on CUDA and keeps `triton` on ROCm.
