# [ROCm][Attention] Accelerate ROCm Prefill Attention with FP8 Triton Kernels

[Upstream PR](https://github.com/vllm-project/vllm/pull/62913) · state: open · merged: False

## Original PR description

## Overview

`ROCM_AITER_FA` runs prefill and extend attention through CK in bf16/fp16, even with an FP8 KV cache. This PR runs eligible head-dim-256 calls on gfx942 through aiter's Triton MHA on per-tensor FP8 Q/K/V. It is enabled by an FP8 KV cache plus `--attention-config '{"use_prefill_query_quantization": true}'`, the switch MLA already uses (#31195). Without the switch, every call still goes to CK.

## Claims

- No new env var; `envs.py` and `_aiter_ops.py` are untouched. With the switch off, the layer calls CK directly, and the existing `tests/kernels/attention/test_rocm_aiter_fa.py` gives the same result with and without this PR.
- Qwen3.8-27B-FP8, 131072 input tokens, TP1, measured on this head: median TTFT −14.2%, output throughput +12.3%, median TPOT −7.6% on MI325X; −11.5% / +11.3% / −8.6% on MI300X. Gains shrink with input length and are neutral at 4096.
- The fresh-server first pass is no longer slower than base. At 16384 it was +11% slower on revision `209d4e9c37`; on this head it is +0.2% (MI325X) and −2.2% (MI300X).
- Long-context accuracy is unchanged. NIAH at 133k tokens scores 5/5 on both base and this PR at every needle depth, which exercises the extend/context-chunk path that gsm8k does not reach. The worst per-head relative error against CK in the unit tests is 0.059 on the output and 2.5e-3 on the LSE.
- Fewer request-time Triton compiles: with `max_seqlen_q/k` rounded up to a multiple of 16, 42 mixed calls compile 6 `_attn_fwd` variants instead of 17, with bitwise-identical outputs.
- Ineligible bf16/fp16 calls and calls with unknown kwargs run the CK call unchanged. An aiter whose `_flash_attn_forward` lacks the needed kwargs keeps the layer on CK from load time. Kernel errors, including OOM, raise; there is no per-call fallback.
- The FP8 Q/K/V buffers come from vLLM's workspace manager and are reserved during the profile run, so the memory profiler accounts for them. The FP8 path adds no GPU-to-CPU sync.
- Untouched: decode, other head dims, other architectures including gfx950, CUDA, and `VLLM_BATCH_INVARIANT`.

## Why `_TUNED_CONFIG` is here

aiter's gfx942 MHA config has no FP8 head-dim-256 entry, so `_get_config` falls through to `fwd["default"]` (`PRELOAD_V` false, `num_warps` 4, `num_stages` 1). On that config the Triton FP8 path is **slower than the CK path this PR replaces**, so the local override is load-bearing rather than a convenience.

MI325X, head dim 256, 24 query heads, 4 KV heads, aiter 0.1.26, median of 5 after 3 warmups. A second pass agreed within 1% on every cell, and MI300X shows the same pattern.

| case (q × k) | CK bf16 | Triton FP8, aiter default | Triton FP8, tuned |
|---|---|---|---|
| 4096 × 4096, causal | 0.731 ms | 1.907 ms | 0.559 ms |
| 16384 × 16384, causal | 8.795 ms | 23.189 ms | 6.116 ms |
| 30720 × 30720, causal | 30.149 ms | 79.473 ms | 20.720 ms |
| 30720 × 16384, context chunk | 32.014 ms | 75.123 ms | 19.768 ms |
| 30720 × 32768, context chunk | 63.642 ms | 151.799 ms | 39.151 ms |

The tuned config is 24–38% faster than CK; aiter's default is 2.3–2.6× slower. This resembles the pipelining pathology aiter documents one branch higher in `_get_config` for `16 < head_dim_v <= 64` ("a num_stages=1 software-pipelining pathology on this backend (e.g. ~3x slower at d64)"), fixed there by adding a `small_head` entry. I will send a gfx942 FP8 head-dim-256 entry to aiter the same way; once it lands and the pin moves, `_TUNED_CONFIG` here is a one-line deletion.

## Validation

MI325X (gfx942) and MI300X (gfx942), TP1, `vllm/vllm-openai-rocm:nightly-rocm72-5d35ce3934a7804b298559d2d99eec33792e1eb9` (AITER 0.1.26, torch 2.13.0, Triton 3.8.0). "This PR" is that image with the diff applied in place.

All serving and accuracy numbers below were re-measured on this head. The earlier tables from revision `209d4e9c37` are not reused: the extend and context-chunk path changed numerically in this round, since the gathered FP8 context is now read with the cache's own scales instead of being dequantised to bf16 and requantised with a fresh per-call scale. Both arms were run with the identical script on the same host, base first.

```bash
VLLM_ROCM_USE_AITER=1 VLLM_ROCM_USE_AITER_LINEAR=1 VLLM_ROCM_USE_AITER_RMSNORM=1 \
VLLM_ROCM_USE_AITER_CUSTOM_AR=1 VLLM_ROCM_USE_AITER_MHA=0 \
vllm serve Qwen/Qwen3.8-27B-FP8 --attention-backend ROCM_AITER_FA --kv-cache-dtype fp8 \
  --attention-config '{"use_prefill_query_quantization": true}' \
  --max-model-len 133120 --max-num-seqs 8 --max-num-batched-tokens 30720 \
  --gpu-memory-utilization 0.9 --no-enable-prefix-caching

vllm bench serve --model Qwen/Qwen3.8-27B-FP8 --dataset-name random \
  --random-input-len $ISL --random-output-len 1024 --num-prompts 24 \
  --max-concurrency 8 --num-warmups 0 --seed 1234 --ignore-eos
```

## Details

- `enabled()` decides at layer init whether the FP8 Triton path is used; `prefill_attn()` then builds the varlen callable. The three call sites in `rocm_aiter_fa.py` call `self._prefill_attn(...)`.
- `triton_fp8_prefill_attn()` quantises Q with `ops.scaled_fp8_quant` into a workspace buffer (one scale per tensor per call) and calls aiter's `_flash_attn_forward`. K and V are quantised the same way when they arrive in `q`'s dtype, and passed through untouched when the caller supplies `descale_k`/`descale_v`, which the module broadcasts to `[batch, num_kv_heads]`.
- One scale per tensor per call, so results are not batch invariant.
- Causal calls must pass one tensor for both `cu_seqlens`, because aiter writes LSE 0 for causal rows with no key (ROCm/aiter#6180).
- On the NHD cache layout, the gathered context chunk and a KV-sharing layer's K/V are read from the cache as FP8 with the cache's own scales as `descale_k`/`descale_v`, with no dequantise-then-requantise round trip. The shuffle layout still dequantises and requantises; that path is unchanged and not validated for the direct read.
- `max_seqlen_q/k` are rounded up to a multiple of 16. With varlen inputs the kernel reads real lengths from `cu_seqlens`, so only Triton's specialisation changes.
- The FP8 Q/K/V buffers are reserved from the workspace manager during the profile run, together with a one-off allocation of aiter's float32 output and its cast, so the memory profiler counts them. At the configuration measured above this did not change the reported KV cache size. ROCm/aiter#7232 (draft) adds `out_dtype` to `_flash_attn_forward`; once vLLM's aiter pin has it the kernel can write bf16 directly instead of a float32 buffer that is then converted. This PR does not depend on it.
- Scope: gfx942, head dim 256, FP8 E4M3 KV cache, prefill and extend only, and only layers without ALiBi, attention sinks or a sliding window. Other layers stay on CK and log why. Only TP1 was measured.
- Not a duplicate: #53823 (gfx950) and #63679 touch the same call sites, and #58713 (draft) touches `extend_forward`. #53823 adds the same direct FP8 context gather for its prequantised path; whichever lands second will reuse the other's switch. None adds FP8 prefill for gfx942. If they land first, I will rebase.

Done. Summary of the three gather sites:

| call site | cache layout | before | now |
|---|---|---|---|
| extend context chunk | NHD (default) | dequant to bf16, requant with a fresh scale | read as FP8, cache scales as `descale_k`/`descale_v` |
| KV-sharing layer | NHD (default) | dequant to bf16, requant with a fresh scale | read as FP8, cache scales as `descale_k`/`descale_v` |
| both | SHUFFLE (`VLLM_ROCM_SHUFFLE_KV_CACHE_LAYOUT=1`, off by default) | dequant to bf16, requant with a fresh scale | unchanged |

The chunk is gathered with `dequant=False` into the extend workspace viewed as FP8, and the
module broadcasts the per-tensor cache scale to `[batch, num_kv_heads]`, which is the layout
the kernel indexes. The second row is the call site your comment implies but doesn't name: a
KV-sharing layer projects only Q and reads K/V back from the target layer's cache, and that
gather had the identical round trip.

I left SHUFFLE alone because it's a separate gather kernel I haven't validated; it's off by
default, so the default path no longer quantises twice. At the kernel level the round trip was
~1% of a 30720x32768 context-chunk call (0.43 ms of 45 ms), so the value is correctness rather
than speed.

Covered by `test_extend_with_context_matches_ck[nhd|shuffle]` and
`test_kv_sharing_prefill_reads_fp8_cache[nhd|shuffle]`, which assert the `dequant` flag and the
descales the kernel receives, and compare per-head error against CK reading the same cache.
