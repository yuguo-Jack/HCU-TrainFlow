# [Rust Frontend] Coerce replayed tool-call arguments that are not an object

[Upstream PR](https://github.com/vllm-project/vllm/pull/65371) · state: closed · merged: True

## Original PR description



## Overview

In the Rust frontend, coerce replayed assistant tool-call `arguments` that are not a JSON object to `{}`, as Python does since vllm-project/vllm#48922. Today a malformed `arguments` string in the history (for example a call cut off at `max_tokens`) makes `/v1/chat/completions` return 500 on every later turn of the conversation.

## Claims

- The HF, DeepSeek V3.2, Inkling and `glm5_next` renderers coerce malformed and non-object `arguments` to `{}` with a warning (size only, never the content); `null` coerces without a warning, as in Python.
- A conversation whose history holds a malformed call keeps working instead of failing with 500 (400 on the render route).
- DeepSeek V4/V4.1, Kimi K3 and Harmony keep their reference-encoding behavior.

## Details

**Root cause.** A client replays assistant tool calls with `function.arguments` as the string the model produced. The Rust HF renderer decodes it and fails with `Error::ChatTemplate` when it is malformed, which is not a request-validation error, so chat returns 500. The string stays in the history, so every later turn fails the same way. DeepSeek V3.2 and Inkling fail the same way and also reject valid non-object JSON; the HF renderer passed non-object JSON through, so `42` reached the template as a number and a template calling `.items()` failed on it. Python's `_postprocess_messages` (`vllm/renderers/chat_utils/chat_message.py`) coerces these to `{}` with a warning because a failure in the history makes the conversation unrecoverable.

**Design.** A shared default, `tool_call_arguments_or_empty` in the `renderer` module, decodes `arguments` to a JSON object and coerces anything else to `{}`. Each renderer opts in, because the handling differs by reference encoding:

- DeepSeek V4/V4.1 keep wrapping malformed text as `{"arguments": raw}`, as deepseek-recipe does.
- Kimi K3 keeps its raw-text block for malformed text and its error for non-object JSON.
- Harmony already renders the string verbatim.

HF's `to_template_tool_calls` can no longer fail, so it returns an `Option`.

**`glm5_next` (second commit).** Python serves `glm5_next` through the HF renderer, so these strings are coerced there too. The native Rust renderer passed the string into its template messages and its encoder rejected it with 400. The coercion now happens where the request is turned into template messages (the counterpart of Python's `parse_chat_messages`), as on the HF renderer; the encoder keeps the template's own rejection of non-object input, which `fixtures/test_cases.json` pins (`bad_arguments_*`).

**Why `{}` rather than the raw text.** HF templates need a mapping for `arguments` (`.items()`, `tojson` re-encodes a string); DeepSeek V3.2 writes DSML parameters, which a JSON string does not contain; only Inkling could carry the raw payload. The cost is one prefix-cache miss from the coerced arguments onward on the first turn that replays the call (block hashes chain); `{}` renders deterministically, so later turns hit.

**Not covered.** Warning text and counts are not asserted. Python's dict passthrough case does not apply, because the Rust request DTO carries `arguments` as a string; the empty and missing cases are already covered at the DTO by `prepare_chat_request_lowers_empty_tool_call_arguments_as_absent`.

Not a duplicate: no open PR changes tool-call argument handling in the Rust renderers (searched open PRs for `tool call arguments`, `malformed`, `coerce`, `glm5_next`). AI assistance (Claude Code) was used to prepare this change; the human submitter reviewed every changed line.
