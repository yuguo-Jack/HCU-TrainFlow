# [Bugfix][ROCm] Run ROCM_AITER_FA prefill/extend with soft cap, sinks or ALiBi through unified_attention

[Upstream PR](https://github.com/vllm-project/vllm/pull/63677) · state: open · merged: False

## Original PR description


_Requested by **Tun Jian**_



## Overview

Stacked on #63675 (the ROCM_AITER_FA test suite). Only the last commit is new; please review it after #63675 lands. Part of the attention backend test standard RFC (https://github.com/vllm-project/vllm/issues/63640).

**Before:** With a logits soft cap, attention sinks or ALiBi, ROCM_AITER_FA prefill and extend returned wrong outputs. The soft cap was never applied, the head-128 asm kernel dropped sinks (and extend counted them twice across context chunks), and ALiBi positions restarted in every context chunk. Decode was correct.

**After:** Every declared feature gives the float32-reference output in every phase, at head sizes 64, 128 and 256 and with bf16 and fp8 KV.

This deletes the `prefill-features` entry from `known_defects.py`. Its 59 unit tests were strict xfails on the tests-only PR and now pass.

## Validation

MI350X (gfx950), `vllm/vllm-openai-rocm:nightly` (AITER 0.1.26), full unit suite including the nightly matrix:

- Unit: 3847 passed, 19 xfailed, 0 unexpected, with the AITER defect below registered.
- All 59 `prefill-features` tests pass, covering every declared feature × phase × head size 64/128/256 × KV dtype.

### Known AITER defect this PR exposes (kept on AITER's kernel, registered as `aiter-gluon-buffer-offset`)

**What fails.** This PR routes prefill/extend with sinks, soft cap or ALiBi through AITER's `unified_attention`. On gfx950 that op picks its Gluon kernel by default. Two nightly-matrix cases (GPT-OSS full attention, 8192-token context × 128 requests, block sizes 16 and 32) get a few outputs wrong, with a max abs error of 0.03.

**Why.** The Gluon launcher (`aiter/ops/triton/attention/unified_attention.py`, `_unified_attention_gfx950`) switches on 32-bit buffer loads when `k.nelement() * k.element_size() <= 2**31 - 1`. vLLM's paged cache stores K and V interleaved in one tensor per layer, so the K view has `stride(0)` equal to twice a block. Its address span is about twice its element count. When the K view is 1-2 GiB, the check passes, but blocks beyond the 2 GiB byte offset overflow the 32-bit offset and are read from the wrong place. Confirmations:
- The same calls with `k.contiguous()` / `v.contiguous()` are correct.
- AITER's own Triton variant (`backend="triton"`) matches vLLM's Triton kernel at every shape tried.
- Decode (1 query token) did not reproduce.

**Is it about context length (16384 and beyond)?** Not directly. What matters is the size of the per-layer K view and whether the request's blocks sit beyond 2 GiB. Measured with GPT-OSS head 64, 8 KV heads, bf16, against the float32 reference (wrong outputs / max abs error):

| Context × requests | K view | Gluon (default) | AITER Triton | vLLM Triton |
| --- | --- | --- | --- | --- |
| 4096 × 128 | 0.5 GiB | 0 / 0.0015 | – | – |
| 8192 × 64 | 0.5 GiB | 0 / 0.0012 | – | – |
| 8192 × 128 | 1.0 GiB | 5-12 / 0.03 | 0 / 0.0005 | 0 / 0.0005 |
| 10240 × 128 | 1.25 GiB | 547k / 0.16 | – | – |
| 12288 × 64 | 0.75 GiB | 0 / 0.0012 | – | – |
| 12288 × 96 | 1.13 GiB | 17k / 0.08 | – | – |
| 12288 × 128 | 1.5 GiB | 1.6M / 0.11 | 0 / 0.0003 | 0 / 0.0003 |
| 16384 × 128 | 2.0 GiB (buffer loads off) | 0 / 0.0007 | – | – |
| 20480 × 64 | 1.25 GiB | 12k / 0.08 | – | – |
| 24576 × 64 | 1.5 GiB | 65k / 0.05 | – | – |
| 32768 × 64, 65536 × 32 | 2.0 GiB (off) | 0 / 0.0004 | – | – |

Head 128 (Qwen3 shape) behaves the same, for example 3.1M wrong outputs at 12288 × 128. In serving, the per-layer KV pool is sized from GPU memory, not from one request, so a K view of 1-2 GiB per layer is common on MI355. Long requests are more likely to land on blocks beyond 2 GiB. So contexts of 16384 and longer are affected whenever the pool falls in that range. Only the test harness's tightly sized cache made 16384 look clean.

**Impact of keeping AITER's kernel.** Models with sinks, soft cap or ALiBi (GPT-OSS sinks among them) can get wrong prefill/extend attention on gfx950 when the per-layer K view is 1-2 GiB. The fix belongs in AITER: base the buffer-op check on the view's address span (or the underlying storage) instead of `nelement()`. A vLLM-side mitigation that still uses AITER is to pass `backend="triton"` in `_forward_unified`. The registry entry should be deleted once AITER ships the fix.

## Details

AITER's varlen kernels cannot serve these features on every path. Causal batches with prefill or extend rows and one of these features now run through `unified_attention` over the paged cache, which already holds this step's K/V. The soft cap is also passed through to the varlen calls (for the non-causal path).


## Related upstream PRs

- #60487 (engint-cerebras) fixes one part of this PR: sinks counted once per context chunk in `extend_forward`, by passing `sink_ptr=None` to the cached-context chunk calls. This PR covers that case too, and also the soft cap, ALiBi and the head-128 asm kernel dropping sinks. #60487 adds its regression test to `tests/kernels/attention/test_rocm_aiter_fa.py`, which #63675 replaces with the backend suite, so the two will need to be reconciled whichever lands first.
