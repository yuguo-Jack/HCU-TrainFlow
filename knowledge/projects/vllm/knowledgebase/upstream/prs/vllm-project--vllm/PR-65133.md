# [Bugfix] shm_broadcast: unblock writer in acquire_write when shutdown

[Upstream PR](https://github.com/vllm-project/vllm/pull/65133) · state: open · merged: False

## Original PR description



## Overview

Fix #65135 . When a writer is blocked in `acquire_write` (e.g., due to a dead reader), `shutdown` won't help because `acquire_write` never check `self.shutting_down`. This pr add this check, so allowing `shutdown` to unblock writers symmetrically with readers.

`shutdown` is already invoked on writer-side queues in serveral places, such as "MultiprocExecutor.shutdown", " WorkerProc.shutdown", "WorkerProc.monitor_death_pipe". The docstring limitation to idle readers is updated accordingly.

## Claims

- Fix a bug where `MessageQueue.shutdown()` had no effect on writers blocked in `acquire_write`.
- Add a unit test to verify `shutdown()` cancels a blocked writer.

## Validation

 - Added `test_acquire_write_respects_shutdown`.
 - `pytest tests/distributed/test_shm_broadcast.py::test_acquire_write_respects_shutdown` passes.
 - Existing shutdown tests still pass

## Details

**Root Cause**

 `acquire_write()` never checks `self.shutting_down`, and `SpinCondition.cancel()` is a no-op for writers. Thus `shutdown()` cannot unblock a writer.

 **Motivation**

  `shutdown()` is already called on writer-side queues (e.g. `rpc_broadcast_mq`, `worker_response_mq`) in `MultiprocExecutor.shutdown`, `WorkerProc.shutdown`, and `WorkerProc.monitor_death_pipe`, but these calls are currently ineffective for blocked writers.

**Design Decisions**

  - Check `shutting_down` only in the blocking path of `acquire_write`.
  - Raise `RuntimeError("cancelled")` symmetrically with reader cancellation.
  - Update the `shutdown()` docstring.

**Limitations**
This change relies on callers invoking `shutdown()`. It does not implement automatic reader-death detection.
