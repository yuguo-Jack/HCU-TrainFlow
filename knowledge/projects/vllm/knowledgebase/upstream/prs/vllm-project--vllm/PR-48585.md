# [Bugfix][Frontend] Handle None/NaN/Inf logprob values when using FP8 quantization

[Upstream PR](https://github.com/vllm-project/vllm/pull/48585) · state: open · merged: False

## Original PR description

## Purpose

When using FP8 quantization (`--quantization fp8`), token logprobs can be `None`, `NaN`, or `±inf` due to numerical underflow or instability in the quantized computation path. The existing code used `max(step_token.logprob, -9999.0)` which raises `TypeError` when `logprob` is `None`, and silently propagates `NaN`/`inf` to the JSON response, causing a serialization failure:

```
ValueError: Out of range float values are not JSON compliant
```

This issue is not universally reproducible — it was observed on a fine-tuned model under specific request conditions. However, the root cause (non-finite logprob values leaking into the serving layer) is a latent risk for any FP8-quantized model, so this fix is intentionally **defensive**.

This PR introduces a `clamp_logprob()` helper in `vllm/logprobs.py` that safely handles all three cases (`None`, `NaN`, `±inf`) by clamping them to `-9999.0` — the sentinel value already used by vLLM for zero-probability tokens — and applies it at both call sites in `_create_completion_logprobs`.

Fixes: logprob JSON serialization error when using FP8 quantization with `logprobs` enabled.


- DemisEom · comment · 2026-11-03T13:43:14Z · [source](https://github.com/vllm-project/vllm/pull/48585#issuecomment-6605405463)

We hit this in an internal deployment, so adding a data point in case it helps this PR move forward.

When logits contained NaN (KV cache corruption, Gemma-4-31B NVFP4 + MTP on B300), chat completion requests with `logprobs: true` came back as HTTP 400 `Out of range float values are not JSON compliant: nan`. We saw it on v0.25.1 in production and reproduced it on v0.28.0: after filling 5% of KV blocks with NaN, 17 of 20 such requests returned that 400. A 400 tells clients and gateways the request was bad, so they do not retry and nobody looks at the server, while the real fault is on the server side.

On current main the same `max(logprob, -9999.0)` pattern is still in the chat and responses paths, not only completions: `chat_completion/serving.py` (2 places), `responses/serving.py` (2 places), `completion/serving.py` (2 places). `scale_out/token_in_token_out/serving.py` already handles NaN explicitly. Since the case we hit was chat completions, would you be open to applying `clamp_logprob` to those call sites as well? Happy to help test, or to send a follow-up for the chat/responses paths if you prefer to keep this PR small.
