# [Bugfix][KV Offload] Size CPU cache slots for one KV group

[Upstream PR](https://github.com/vllm-project/vllm/pull/56953) · state: open · merged: False

## Original PR description

Fixes #56871.

An offload key identifies one KV cache group, but CPU slots can reserve the combined footprint of all groups. For eight equally sized, disjoint groups, a budget that should hold 16 group keys holds only two.

This change carries each selected group's byte size into the offloading config and sizes the shared slot pool for the largest group. Worker views start at the beginning of each slot for each group, preserving GPU strides, aliases, unpadded payload sizes, and partial chunks. Packed GPU layouts use group-specific transfer regions instead of copying the whole multi-group block. The layout applies to CPU offloading and the CPU primary tier of tiered offloading.

Slots remain fixed-size for secondary-tier transfers. Unequal groups can still leave unused space inside a slot. A storage-format identifier including row size separates compact rows from previously persisted rows; existing files remain on disk but are not reused. Single-group and external backends retain their existing layout by default.

## Duplicate-work check

The issue is claimed at https://github.com/vllm-project/vllm/issues/56871#issuecomment-5674698213. Issue discussion and open/closed PR searches were rechecked on 2026-09-15. Production validation on **DeepSeek-V4.1, TP=8 on SM90 (Hopper)** with the CPU offloading path — the case the PR description lists as not yet covered.

**Setup**
- Base: `vllm/vllm-openai:nightly-dc36fcce` (v0.29.1rc1.dev47+gdc36fcce9). The 9 runtime files from this PR were applied on top (they apply cleanly on that base; tests/docs not applied).
- One extra local change so a non-HiSparse model only offloads prefix-cacheable groups: `get_offloading_group_ids()` returns `kv_cache_config.prefix_cacheable_group_ids` (same idea as #54743). Without it the DSpark draft group (`block_size=8`) fails the `tokens_per_block % tokens_per_hash` check in `build_offloading_config` at startup.
- Flags: `--kv-offloading-size 500 --kv-offloading-backend native --enable-cumem-allocator --gpu-memory-utilization 0.95 --max-model-len 1048576`, DSpark speculative decoding on (k=5). GPU KV pool: 5,289,827 tokens.

**Before this PR** (same base, see #56871): 500 GiB of host memory held only ~3.3M tokens — less than the GPU pool — and an evicted prefix was never served back from host.

**With this PR**
- Read-back works. A 139,200-token prompt was sent once; the engine then served ~22 minutes of live traffic (GPU KV usage dropped to 0–4% several times, so its blocks were gone from GPU). Re-sending the identical prompt: `cached_tokens` = 139,136 / 139,200, TTFT 0.5 s, `vllm:external_prefix_cache_hits_total` +139,136, `vllm:kv_offload_size_sum{transfer_type="CPU_to_GPU"}` +1.9 GiB; the needle answer was correct.
- 20/20 fresh ~90k-token sessions hit on their second turn (same as without offloading).
- Throughput with all other traffic paused, vs. the identical config without offloading: single-stream decode 214 vs 140 tok/s, 8-way decode 313 vs 307 tok/s, cold prefill 12.6k vs 12.6k tok/s, 8-way decode while two 374k-token cold prefills run 25.1 vs 24.5 tok/s. No regression.
- ~112 GB written to host in the first 10 minutes of traffic, ~160 GB after 22 minutes; startup took ~9 min vs ~5 min without offloading (first run of the offload path).
- Has been serving production traffic since, no engine errors so far.

One side observation, probably unrelated to this PR: `vllm:kv_offload_cpu_cache_usage_perc` reads `0.0` on `/metrics` while the periodic "KV Transfer metrics" log line reports a non-zero value for the same gauge.
