# [Perf][GLM-5.3-Flash] Update FlashKDA pin, consume row-strided QKV directly

[Upstream PR](https://github.com/vllm-project/vllm/pull/61614) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

GLM-5.3-Flash prefill hands FlashKDA packed Q/K/V views (`3 * H * D` token stride, contiguous H/D rows), and `_flashkda_prefill` copied them into three contiguous buffers because the kernel required dense inputs. FlashKDA #15 (vllm-project/FlashKDA#15) accepts row-strided Q/K/V, so this PR pins that revision and passes the views directly. This is the consumer-side alternative to producing dense QKV in the convolution itself.

## Claims

- Removes the three per-layer Q/K/V copies from GLM-5.3-Flash prefill; profiles show 4 -> 1 copy kernels (the remaining one is the beta transpose).
- Serial A/B/A on H200, ISL2048/OSL1: saturated prefill throughput **21.37 -> 21.78 req/s (+1.9%)**, median TTFT **-2.1%**.
- GSM8K is unchanged within sampling noise: 0.9163 (A1) / 0.9125 (candidate) / 0.9170 (A2), i.e. 1204 / 1199 / 1205 of 1314 questions.

## Validation

Environment: 4 x H200, GLM-5.3-Flash FP8 checkpoint, BF16 KDA projections, serial A/B/A on the same host.

## Details

- The change is two lines: pin FlashKDA `17a037d` -> `47fc9fec` in `cmake/external_projects/flashkda.cmake`, and drop `q/k/v.contiguous()` in `vllm/models/glm5next/common/kda.py`. `g`, `beta`, states, workspace and output handling are unchanged, as is the tensor operator schema.
- FlashKDA #15 accepts any aligned token stride as long as the H/D rows are contiguous, the base pointer and row starts are 16-byte aligned, rows do not overlap and the B*T flattening is uniform. The merged convolution output satisfies all of these, including the 16-byte alignment (`3 * H * 128 * 2` bytes is always a multiple of 16).
- Beta still needs the transpose inside FlashKDA; that is unchanged and is the single remaining copy kernel in the profile.
- The pin also brings FlashKDA #15's standalone `launch_prepare` / `launch_recurrence` signature change. Nothing in vLLM `main` calls those launchers today (main pinned `17a037d`, which predates them), but the in-flight KCP work (vllm#59304) should pass `0` / its strides when it rebases.
