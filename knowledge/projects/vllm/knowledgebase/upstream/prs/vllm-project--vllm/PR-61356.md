# [Frontend] Send ping keepalives while an Anthropic /v1/messages stream waits for its first token

[Upstream PR](https://github.com/vllm-project/vllm/pull/61356) · state: open · merged: False

## Original PR description

## Overview

Emit Anthropic `ping` events on `/v1/messages` streams while the engine has not yet produced a chunk, so proxy and client idle timeouts (commonly 300s) do not cut off requests with long prefills. Addresses item 14 ("No `ping` or early `message_start` during long prefills") of RFC #58647.

## Claims

- A streaming `/v1/messages` request whose first token takes longer than the keepalive interval now receives `event: ping` / `data: {"type": "ping"}` every `VLLM_ANTHROPIC_STREAM_KEEPALIVE_INTERVAL_S` seconds (default 15) until the first chunk, then the unchanged event sequence.
- Requests whose first chunk arrives promptly are byte-for-byte unchanged.
- `VLLM_ANTHROPIC_STREAM_KEEPALIVE=comment` sends an SSE comment line instead (invisible to SSE parsers, for clients whose SDK streaming helper rejects events before `message_start`); `off` disables the feature.
- Closing the response while a keepalive wait is pending cancels the in-flight read on the OpenAI stream.

End-to-end on vLLM 0.31.0 (this change applied as a file overlay) serving `deepseek-ai/DeepSeek-V4.1-Flash` (DP=3, TP=2, max-model-len 1M) behind kgateway (Envoy) and the production-stack router, requested from inside the cluster with `curl -N`:

| Request | First token | Events observed |
|---|---|---|
| `max_tokens: 8`, short prompt | < 1s | `message_start` first, no `ping` |
| 1.3 MB prompt, `max_tokens: 1` | 53s | `ping` at 15s, 30s, 45s, then `message_start` … `message_stop`, HTTP 200 |
| 1.7 MB prompt through Envoy and the router | 66s | `ping` at 16s, 31s, 46s, 61s, then a full response, HTTP 200 |

Before the change, the same deployment lost requests at exactly 300s whenever a cold 200k to 1M token prefill ran (Claude Code reports "Request timed out"; Envoy's `downstream_rq_idle_timeout` counter incremented).

Client compatibility: Claude Code 2.1.296 was run against a mock Messages server that sends a `ping` before `message_start`; the response, `stop_reason` and `usage` were reported correctly. The TypeScript and Python SDK `MessageStream` helpers (`client.messages.stream()`) throw on any event before `message_start`, which is why the `comment` mode exists; raw `create(stream=True)` iteration in both SDKs ignores `ping`.

## Details

- Root cause: `message_stream_converter` emits its first bytes (`message_start`) only on the first `ChatCompletionStreamResponse` chunk, which the engine produces after prefill. For 100k+ token prompts with no prefix cache hit that is minutes of silence on the wire.
- Implementation: `_iter_with_keepalive` wraps the OpenAI stream and yields `None` when `asyncio.wait` on the pending `__anext__` times out; the converter turns `None` into the keepalive payload. The pending future is kept across timeouts (cancelling `__anext__` of an async generator corrupts it) and is cancelled in a `finally` via `items.aclose()` so a client disconnect mid-wait does not leave the read running.
- Keepalives are also emitted mid-stream if the engine stalls longer than the interval; after `message_start` a `ping` is unconditionally legal in the Anthropic protocol.
- Configuration lives in `vllm/envs.py` (`VLLM_ANTHROPIC_STREAM_KEEPALIVE`, `VLLM_ANTHROPIC_STREAM_KEEPALIVE_INTERVAL_S`) so it is documented automatically on the environment-variables page; the online-serving README gets a one-line note.
- Tradeoff: the default sends a `ping` before `message_start`, which the real Anthropic API does not do. It is accepted by Claude Code, the primary consumer of this endpoint, and by raw SDK iteration; SDK `.stream()` helper users can select `comment`. An early `message_start` with placeholder usage was considered and rejected because `usage.input_tokens` is only known once the first chunk arrives.
- Not a duplicate: open PRs mentioning the Anthropic converter are #46162 (forwarding engine error chunks, a different code path; this PR deliberately does not touch error handling), #59616 (context-window errors) and #52519 (tool JSON). No open PR or issue proposes keepalives; RFC #58647 lists it as item 14 with "none found".
- AI assistance was used for this PR (Claude Code). The submitting human reviewed every line, ran the tests above, and deployed and validated the change on the serving cluster described in Validation.
