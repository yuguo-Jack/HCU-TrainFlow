# [Model] Add Alpamayo 2 Super (reasoning model)

[Upstream PR](https://github.com/vllm-project/vllm/pull/62957) · state: closed · merged: True

## Original PR description



## Overview

Add `nvidia/Alpamayo2-Super`. vLLM serves its Qwen3-VL reasoning model, which produces all of the model's text outputs: VQA, grounding, chain-of-causation reasoning with meta-actions, and auto-labeling. The trajectory expert stored in the same checkpoint is not loaded. This follows `Cosmos3ForConditionalGeneration`. The full policy (reasoning + trajectory) will be served by vLLM-Omni (vllm-project/vllm-omni#9133).

## Claims

- `vllm serve nvidia/Alpamayo2-Super` works on the released checkpoint as-is: no conversion and no extra flags. The checkpoint's architecture `Alpamayo2Super` resolves to `Alpamayo2SuperForConditionalGeneration`.
- Matches the reference implementation ([NVlabs/alpamayo2](https://github.com/NVlabs/alpamayo2) @ `9596749e`):
  - token-identical prompts;
  - LingoQA 80.8% vs the reference's 81.0% (Lingo-Judge, 500 questions; model card: 79.2);
  - no throughput or latency cost against the same weights served as plain Qwen3-VL.
- Prompts can carry the model's ego-trajectory and special tokens as text. The new `alpamayo2_super` tokenizer mode is selected automatically and adds them with the reference ids.

## Validation

Environment: 1x H200 NVL, using `vllm/vllm-openai:nightly` built from `8e2beaa3b` with this branch's `vllm/` diff applied.

**Serving the released checkpoint**

```bash
vllm serve nvidia/Alpamayo2-Super --max-model-len 16384 --limit-mm-per-prompt '{"image": 24}'
```

The log shows `Resolved architecture: Alpamayo2Super` and `Defaulting to tokenizer_mode='alpamayo2_super'`. The model takes 62.5 GiB (bf16, expert skipped).

**Parity with the reference implementation**

The test set is 3 validation samples × 5 requests: 2 VQA questions, grounding, meta-action, and auto-labeling. All requests are greedy with 6 cameras × 4 frames, about 4.5k prompt tokens each, and the server runs with `--no-enable-prefix-caching` so its greedy output is reproducible. Prompts are built as in the reference `text_tasks.build_text_task_messages` and sent through `/v1/chat/completions`. The reference ran 4 times, once with float and once with uint8 image inputs each time.

| check | result |
|---|---|
| prompt token ids identical to the reference (incl. history/future trajectory tokens) | 15/15 |
| vLLM greedy output equals one of the reference's greedy outputs | 15/15 |
| reference greedy output stable across its own 4 runs | 8/15 (7 cases flip on near-tie tokens) |
| trajectory tokens generated | 0/15 |

Where outputs differ between runs, the alternatives say the same thing: for example "roadwork" vs "road work", grounding box corners 1–3 units apart, or reworded reasoning with the same meta-actions. A run with `VLLM_GPU_SYNC_CHECK=error` (5 of these requests) completed with no sync errors.

**LingoQA**

The official evaluation protocol: 500 questions, front camera, 5 frames each, greedy, up to 256 tokens. Each answer is scored with `wayveai/Lingo-Judge` as the maximum over all references, with a `> 0` threshold.

| | Lingo-Judge accuracy |
|---|---|
| reference implementation (transformers, SDPA, bf16) | 81.0% (405/500) |
| this PR | 80.8% (404/500) |

476/500 answers are identical; the other 24 are near-tie wording variants. The model card reports 79.2.

**Performance**

The same weights served as plain Qwen3-VL, i.e. the converted `vlm.` weights on the unmodified build, were compared with this PR on the released checkpoint. The workload was 20 single requests plus 10 × 6 concurrent requests, each with 24 images and about 4.6k prompt tokens.

|---|---|---|
| TTFT | 0.661 s | 0.661 s |
| decode | 20.52 ms/token | 20.52 ms/token |
| request latency | 0.909 s | 0.915 s |
| 6 concurrent requests, wall time | 0.982 s | 0.983 s |

## Details

- **Weights.** The checkpoint stores Qwen3-VL under `vlm.` and the trajectory expert under `expert.`. The `WeightsMapper` rewrites `vlm.` onto the Qwen3-VL layout and drops `expert.`.
- **Config.** `model_type: alpamayo2_super` is not in transformers. `Alpamayo2SuperConfig` exposes the nested `vlm_config` as a `Qwen3VLConfig` and keeps the trajectory fields. It matches vLLM-Omni's config class field for field, so vLLM-Omni can use this one once its vLLM pin includes it.
- **Tokenizer.** The checkpoint ships the base Qwen3-VL tokenizer, and the reference appends 4,000 `<iN>` trajectory tokens and 29 special tokens in code. The model's embeddings and `traj_ids` assume those ids. The `alpamayo2_super` tokenizer mode appends them the same way and checks them against `traj_ids`. It is auto-selected for the architecture, uses `HfRenderer`, and needs no `--tokenizer-mode`. Without it, prompts with trajectory tokens would tokenize as plain text.
- **Trajectory-token mask.** Like the reference (`MaskDiscreteTrajectoryLogitsProcessor`), `compute_logits` never samples the discrete trajectory tokens, because they only appear in prompts. Clients cannot do this themselves: `logit_bias` is capped at 1,024 entries. The mask is a single slice assignment on the logits, with no host sync.
- **Pixel budget.** The model config sets `min_pixels=163840` and `max_pixels=196608`, and the reference implementation passes them to the processor for every task (`helper.get_processor`). The limit applies to each image separately, so it is the same whether a request has one camera or six. The checkpoint's preprocessor config doesn't carry it, so it is set on `image_processor.size` as in `d3.py`; `mm_processor_kwargs` can still override it.
- **Image-only.** The reference implementation passes camera frames as images and never uses video, so `get_supported_mm_limits` lists only `image`; a video input is rejected with a 400 (`At most 0 video(s) may be provided in one prompt`). Qwen3-VL's `get_supported_mm_processor_kwargs` assumes video is supported, so the base implementation is used instead.
- **Relation to vLLM-Omni.** vllm-project/vllm-omni#9133 registers its trajectory reasoning stage as `Alpamayo2SuperPolicy`, so with vLLM-Omni installed, `Alpamayo2Super` still resolves to this class. A follow-up there can subclass this class.
- **Limitations.**
  - No trajectories (that needs the expert) and will be covered in vLLM-Omni
  - Pipeline parallelism and LoRA are inherited from Qwen3-VL but were not tested.
  - CI does not run the full checkpoint (72 GB, 62.5 GiB in bf16), so the end-to-end parity above was run locally.
