# [Kernel] Add VLLM_FLASHINFER_MOE_FUSED_FINALIZE to disable the nondeterministic MoE finalize

[Upstream PR](https://github.com/vllm-project/vllm/pull/54948) · state: open · merged: False

## Original PR description


## Purpose

Fixes #54945. `flashinfer.fused_moe.cutlass_fused_moe` has a `use_fused_finalize` argument whose default (fused epilogue, atomics) is documented as nondeterministic. vLLM's `flashinfer_cutlass_moe.py` never passed it, so identical requests at temperature 0 could return different logits on this backend with no switch to turn it off. This adds `VLLM_FLASHINFER_MOE_FUSED_FINALIZE` (default `1`, behaviour unchanged) and passes it through.

## Test Plan

- Qwen3.8-Flash-Next NVFP4 on a GB10 (sm_121), FlashInfer 0.6.17: one fixed prompt three times, `temperature=0`, `max_tokens=4`, `top_logprobs=20`, hashing every token's top-20 (script in #54945).
- Three serving shapes: prefix cache off + eager; prefix cache on (chunked prefill); prefix cache on + MTP n=5.

## Test Result

| shape | default | `VLLM_FLASHINFER_MOE_FUSED_FINALIZE=0` |
| --- | --- | --- |
| cache off, eager | token 2 differs, 3 distinct of 3 | 1 distinct of 3 |
| cache on | token 1 differs, 3 distinct of 3 | 1 distinct of 3 |
| cache on + MTP n=5 | not probed | 1 distinct of 3 |

Decode cost of the unfused finalize: +3.6 % in one 8-turn agent-loop measurement (43.92 → 45.50 ms/tok; run-to-run band for this config 42.8–47.7), i.e. indicative. `ruff check` / `ruff format --check` clean.

Note for FlashInfer ≤ 0.6.17: with a populated `VLLM_FLASHINFER_AUTOTUNE_CACHE_DIR`, switching the finalize fails at init with `Invalid gemm2 profile id` because the autotune cache key did not distinguish the two runners; fixed in FlashInfer from v0.6.18rc2 (`MoERunner.get_cache_key_extras`). Use a fresh cache dir on older versions.

- Col-5555 · comment · 2026-10-06T09:09:44Z · [source](https://github.com/vllm-project/vllm/pull/54948#issuecomment-6013064876)

Support for this PR from a 2× GB10 (sm_121) TP=2 deployment over RoCE: `RedHatAI/GLM-5.3-Flash-NVFP4` (288 experts, top-8), vLLM `4be061c5` built from source, FlashInfer 0.7.0, CUDA graphs on. We carry a patch with the same env var name, default and meaning as this PR, so our launcher setting will carry over if it merges.

**A tactic-level answer to the open guess in #54945.** @YasuhikoOse suggested that the token-count pattern comes from whether the tuned GEMM2 tactic has the FINALIZE epilogue. We tested each tactic directly. We called `flashinfer.fused_moe.cutlass_fused_moe` on synthetic NVFP4 inputs with our layer's shapes (hidden 4096, per-rank intermediate 1024, bf16 out), forced each autotuner candidate through `profile_ids`, and made 20 calls on identical inputs at M = 1, 24 and 256. GEMM2 offered 32 candidates: 16 plain (IDs in 20–29 and 40–49 on our build) and 16 with the FINALIZE epilogue (30–39 and 50–59). Every plain tactic, and all 16 GEMM1 tactics, gave one output in 20 calls at every M. Of the FINALIZE tactics, two (32 and 33) fail to initialise on sm_121 with "Failed to initialize cutlass TMA WS grouped gemm". The other 14 were all non-deterministic at M = 24 and 256, typically with 20 distinct outputs in 20 calls, and 13 of the 14 were at M = 1. So it is a property of the tactic: whether a deployment is reproducible at a given token count depends on what the autotuner happened to pick for that bucket. On our server, replacing only the GEMM2 cache entries for buckets 16 and 32 with the plain tactics another run had chosen made the output bit-identical, with no other change.

**With `use_fused_finalize=False`** the GEMM2 candidate list drops to the 16 plain tactics. All of them are deterministic, and at a given M all 16 give the same bits. Taking the fastest plain tactic against the fastest of all candidates, the whole MoE call costs +1.0 % at M = 1, +0.15 % at M = 24 and +0.03 % at M = 256. End to end, single-stream decode was 15.51–15.59 tok/s with the switch, against 15.54–15.62 on our previous image without it (5 cold boots each). With the switch, each of 5 cold boots gave the same first token 20 times and the same full answer 5 times at temperature 0, and all five boots gave the same answer.

**A note for reviewers.** On FlashInfer 0.7.0, `use_fused_finalize` is part of the autotune cache key, so flipping the switch re-tunes the MoE once. Our per-rank cache went from 32 to 64 entries on the first boot and then loaded without tuning. That may be worth a line in the docs for anyone with a persisted cache, because the first boot after the change takes longer.

**On where the switch lives,** we agree with keeping it standalone as here. It would also make sense for `VLLM_BATCH_INVARIANT=1` to imply it, since batch invariance cannot hold if identical calls differ.

Separately, the candidate filter still offers the two FINALIZE tactics that fail to initialise on sm_121, and the autotuner survives them. We can open a FlashInfer issue if that is useful.
