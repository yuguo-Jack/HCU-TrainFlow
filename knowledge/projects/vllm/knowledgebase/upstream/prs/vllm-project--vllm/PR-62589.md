# [ROCm][Perf][Qwen4Exp] Tile QSA indexer scoring and skip invisible columns

[Upstream PR](https://github.com/vllm-project/vllm/pull/62589) · state: open · merged: False

## Overview

`_qsa_mqa_paged_kernel` scores every row against the full page-table width (max_model_len / 4 = 65,600 columns), regardless of how many are visible. In a 32K prefill profile on MI325X it takes 43% of GPU time. This PR skips columns past each request's visible range and scores 16 rows x 64 keys per program with `tl.dot`.

For decode with one query row per request (no MTP, no prefill) the 16-row tile is mostly padding. At 262K context with one row it took 9.4 us against 6.3 us for the old one-row kernel (scoring kernel only). On gfx942, batches of at most 32 such rows now use the old one-row kernel plus the same skip of invisible column blocks.

## Dispatch

`qsa_mqa_paged(..., single_row_decode=True)` uses the one-row kernel when all of these hold:

- the caller sets `single_row_decode`. `QSAIndexer._select` sets it from `QSAForwardMetadata`: `num_prefills == 0 and decode_query_len == 1`. Both are host values, so there is no device sync, and the choice is fixed when a CUDA graph is captured.
- at most 32 rows. The crossover against the tiled kernel on MI325X is about 32 rows at 32K to 98K context.
- the platform is gfx942.

Prefill, mixed prefill/decode, MTP decode (4 rows per request) and other architectures use the tiled kernel. The one-row kernel is correct for any row-to-request mapping, so a wrong flag costs speed only.

## Trade-offs

- 262K context, 64 requests x 1 row, no MTP: full selection 353.3 -> 367.7 us (+14.4 us, +4%); scoring kernel alone 317.9 -> 346.4 us (+28.5 us, +9%). More than 32 rows use the tiled kernel, so this matches the first revision (367.6 us full selection, 335.8 us scoring). Run-to-run spread is about 10 to 15 us. These are microbenchmarks; no end-to-end run covers this shape.
- The TP2 tests never reach 64 x 262K: the KV cache holds about 9.35M tokens per replica and 64 x 262K = 16.8M. Deployments with more KV can.
- The 32-row limit is where the one-row and tiled kernels break even on MI325X at 32K and 98K context (32 x 1 scoring: 43.5 vs 48.9 us at 32K, 65.2 vs 64.2 us at 98K). At 262K the one-row path is level with the old kernel below 32 rows rather than faster than the tiled one.

## Details

- Rows are request-major, so a 16-row block usually shares one page table and loads the key tile once for all rows and heads. A block that spans requests loops over them; each request skips column blocks past its own visible range.
- The one-row kernel is the pre-PR kernel body (`.to(tl.float32)` on keys and queries) with an early return for column blocks at or past the row's visible count.
- The dot runs in fp16 for fp16 inputs (#60650) and bf16 otherwise, which is exact for the fp8 cache in #61529. fp32 inputs, which no caller passes, would also use bf16.
- Logits past `visible_blocks[row]` are not written. The only consumer, `top_k_per_row_decode`, reads `[0, visible_blocks[row])`.
- The NVIDIA indexer in `nvidia/ops/qsa_indexer.py` is not reusable here: it needs split prefill/decode metadata and the CUDA-only top-k.
- Local benchmarks are on gfx942 (MI325X). On gfx950 (MI355X), the tiled kernel delivered 1.61× geometric-mean output throughput across 12 end-to-end cases in [@mjkvaak-amd's tests](https://github.com/vllm-project/vllm/pull/62589#issuecomment-6322558699), with no observed accuracy regression. MI300X (gfx942) kernel numbers are in [this comment](https://github.com/vllm-project/vllm/pull/62589#issuecomment-6599007249).

Related work: #59437 (draft) adds an opt-in AITER FlyDSL backend for QSA scoring and top-k (`VLLM_ROCM_QSA_FLYDSL=1`). This PR optimizes the existing Triton scoring path on gfx942, which that backend replaces when the flag is set and falls back to. The two are independent, but both edit `QSAIndexer._select`.
