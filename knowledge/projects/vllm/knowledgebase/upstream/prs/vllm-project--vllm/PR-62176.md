# [Core] Bound prefix-cache reuse for target-token prefill scoring

[Upstream PR](https://github.com/vllm-project/vllm/pull/62176) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable MD041 -->

## Overview

When a target-token scoring request opts into prefix-cache reads, a cache hit can skip rows whose scores are required. This PR bounds reuse at `prompt_logprob_start` so every requested score is returned. Implements the initial full-attention path in [bounded-reuse RFC #60366](https://github.com/vllm-project/vllm/issues/60366) and [teacher-serving roadmap #62175](https://github.com/vllm-project/vllm/issues/62175).

Related work on prefix-cache reuse for prompt scoring: #60960. This PR resolves unsupported configurations before connector admission, checks the worker-resolved KV format, and adds complete-score regressions.

## Claims

- In supported configurations, `skip_reading_prefix_cache=False` reuses KV before the first scored row and returns the complete score matrix.
- Defaults and ordinary generation are unchanged. Unsupported configurations, and requests that also ask for ordinary prompt logprobs, recompute the full prompt and log a one-time warning.
- With Qwen3-32B at TP=4, teacher scoring is 3.7x to 3.8x faster for long shared documents and about 1.1x faster for short prompts.

### Teacher-stage performance

Qwen3-32B, 4×A100 80GB with NVLink, TP=4, BF16, FlashAttention 2, compilation and CUDA graphs, synchronous scheduling. Batch-invariant mode is off. Each prompt group has four responses and starts with an empty cache. Each case alternates six repetitions per path after warmup.

The table uses grouped arrivals. Each row covers 16 responses across four groups; times sum the four group medians. The token budget is `max_num_batched_tokens`.

| Token budget | Workload | Uncached | Bounded reuse | Speedup |
| --- | --- | --- | --- | --- |
| 512 | Short math prompts | 1.88 s | 1.66 s | 1.13x |
| 512 | Long documents | 6.13 s | 1.60 s | 3.84x |
| 2048 | Short math prompts | 1.61 s | 1.42 s | 1.14x |
| 2048 | Long documents | 5.16 s | 1.39 s | 3.71x |

Short prompts have 142 to 209 context tokens and 437 to 1024 response tokens. Documents have 2933 to 3944 context tokens and 13 to 58 response tokens. Staggered arrivals, targeting 20 ms gaps with admission at engine-step boundaries, gave similar results: 1.11x to 1.13x for short prompts and 3.71x to 3.83x for documents. Across all six repetitions, aggregate speedups ranged from 1.11x to 1.14x for short prompts and 3.66x to 3.87x for documents. These are offline scoring times, including the existing one-token generation step; model loading, compilation and warmup are excluded.

BF16 scores vary with execution shape. The largest absolute logprob difference from uncached scoring on the 32B runs was 0.50, compared with 0.37 between single and batched uncached scoring. A separate Qwen3-0.6B synthetic probe reached 0.14 for actual tokens and 1.17 for extra candidates. Batch-invariant Qwen3-0.6B checks matched exactly across uncached, bounded and preempted paths. Training loss and gradient equivalence has not been validated.

Scripts, raw results and pinned source/model versions: [reproduction materials in my fork](https://github.com/LinzeShi/vllm/blob/db215c5db9eec0decd891b802b2928f90fe16d46/benchmarks/opd_prefix_reuse_tp4/README.md).

## Details

KV holds attention state, not the logits for skipped rows. The cache hit is capped at `min(prompt_logprob_start or 0, num_tokens - 1)` with the usual block alignment, and the cap applies again after preemption. Admission decides the fallback before connector hooks run, on a copy of the caller's sampling params.

The first version uses MRV2 and supports text token inputs, one causal full-attention KV group, unquantized KV, `max_tokens=1`, and single-GPU or tensor-parallel execution. It adds no response fields and no score storage. Connector, adapter and other configuration exclusions are documented in `docs/training/prompt_token_id_logprobs.md`.

### Design choices and relation to score reuse

For a prompt of length `L` and first scored row `S`, the request needs rows `S` through `L - 2`. KV alone cannot supply those scores. The chosen boundary reuses only earlier blocks and recomputes the scored suffix. For example, with `L=1000`, `S=768` and 32-token blocks, a cache hit can reuse at most 768 tokens; rows 768 through 998 are still computed. An unaligned boundary rounds down through normal block matching.

| Choice | Tradeoff |
| --- | --- |
| Always recompute the prompt | Simple and safe, but repeats shared-context work |
| Bound KV reuse at the first scored row | Reuses unscored context without storing scores or changing the response contract; used here |
| Reuse stored scores as well | Can skip previously scored rows, but needs artifact identity, lifetime and eviction handling; the roadmap's stored-score reuse work |

The initial guard admits one full-attention KV group so its cache hit has a single validated boundary. Quantized KV and mixed groups can add representation or replay constraints; they need their own validation. These guards are based on the worker-resolved cache format, not the weight dtype alone. Unsupported requests fall back before connector admission, without mutating the caller's parameters.

Stored-score reuse adds publication and retrieval to the execution path. Before extending a hit into scored rows, it must acquire matching scores and KV together. When scores are unavailable, it uses this boundary where supported, otherwise recomputes the prompt. This extends the admission/boundary implementation and retains bounded recomputation as a fallback. AuxOutput is excluded here, so the connector-compatible fallback is part of that later work.

### Prefill work and measured latency

For a cold group of `m` responses sharing `P` context tokens, with response lengths `R_i`, uncached prefill processes `mP + sum(R_i)` tokens. With block size `b` and scoring starting at row `P - 1`, the reusable prefix is `H = b * floor((P - 1) / b)`. If the remaining responses hit that prefix, bounded prefill processes `mP + sum(R_i) - (m - 1)H` tokens.

The saved workload uses four responses per group and 16-token blocks. Recorded cache-hit counters match this calculation across both token budgets and arrival modes:

| Workload, four groups | Uncached prefill tokens | Bounded prefill tokens | Token-count ratio | Measured grouped speedup |
| --- | --- | --- | --- | --- |
| Long documents | 54,867 | 14,163 | 3.87x | 3.71x to 3.84x |
| Short math prompts | 16,743 | 14,727 | 1.14x | 1.13x to 1.14x |

The counts explain why long shared contexts benefit more. They are prefill-work ratios, not latency bounds: attention cost, kernel efficiency and scheduling also affect elapsed time. The timings above include the existing one-token generation step.

DeepSeek-V4.1's multi-group cache layout needs a separate reuse extension and validation. A [DeepSeek scoring bug #62651](https://github.com/vllm-project/vllm/issues/62651) is tracked separately. The measurements in this PR cover the Qwen configurations listed above.
