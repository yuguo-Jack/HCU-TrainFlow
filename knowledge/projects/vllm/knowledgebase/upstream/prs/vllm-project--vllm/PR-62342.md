# [Frontend] Build and serialize logprob responses in pydantic-core

[Upstream PR](https://github.com/vllm-project/vllm/pull/62342) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Cut the CPU an API server spends turning a finished request's logprobs into the HTTP response: validate the generate endpoint's logprob tree in one pydantic-core pass, serialize the non-streaming generate, chat and completions responses with `model_dump_json()`, and take the chat logprob models off the request-side extra-field validator. Same wire format, no new options. Follows #58181, which did the equivalent for the generate endpoint's models, and the `Response` shape suggested in #33548.

## Claims

- With the default single API server and `logprobs=8`, generation throughput rises 21–23% on `/inference/v1/generate` and 9–11% on `/v1/chat/completions` (`top_logprobs=8`), on R1-Distill-Qwen-1.5B, Qwen3-4B and Qwen2.5-7B-Instruct, one H100, two trials each with no overlap.
- With `--api-server-count 8` throughput is unchanged (±2%) and API-server CPU per generated token falls 12–23% at `logprobs=8`.
- The synchronous block per finished 620-token response shrinks 1.7x on generate (20.4 to 12.1 µs per token at k=8) and 1.6x on chat (35.4 to 21.6 µs), build and serialization included. Response bytes are identical; the only behavioral difference is that a NaN float in a response would serialize as `null` instead of failing the request, and the logprob fields are already clamped.

## Details

With `logprobs=k`, finishing a request makes the API server build `k + 1` pydantic objects per generated token, dump them to dicts and encode the dicts with the stdlib encoder, in one synchronous block on the event loop (12.6 ms for a 620-token response at k=8 on main). py-spy on a single API server at k=8 puts 40% of its active time in that block, which is why `logprobs=8` costs 50–60% of throughput there while eight API servers hide it.

- `_create_tokens_logprobs` builds plain dicts and calls `GenerateLogProbs.model_validate` once: pydantic-core validates the whole tree without a Python-level `__init__` per candidate. `model_construct` is slower (it is Python), and `TypedDict` entries would be faster still but change the Python-side types derender and the tests use.
- `_clamp_logprob` is one comparison instead of `math.isnan` plus `max`; NaN compares False, so NaN and `-inf` still map to `-9999.0`. It was the top self-time frame of the profile (15%) because it runs once per candidate.
- The three non-streaming routes return `Response(content=generator.model_dump_json(), media_type="application/json")`: no intermediate dict tree, no stdlib encoder. `model_dump_json` was 2.5x faster than `model_dump` + `json.dumps` and faster than `orjson.dumps(model_dump())`, which still builds the tree. Error responses and streaming are untouched.
- `ChatCompletionLogProb*` were `OpenAIBaseModel`, whose `__log_extra_fields__` wrap validator checks a request dict for unknown fields; on these response-only objects it only cost time, and it is what required the `field_names` cache workaround from #13925, now removed. `extra="allow"` is kept.

Not changed here: candidate detokenization in tokens mode (`LogprobsProcessor` decodes text the generate endpoint never sends, about 8% of the same profile) and the per-step `Logprob` objects; both are engine-output-path changes.
