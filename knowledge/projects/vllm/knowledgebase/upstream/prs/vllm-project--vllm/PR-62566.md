# [KV Offload] Warn when secondary-tier KV is tied to the parallel config

[Upstream PR](https://github.com/vllm-project/vllm/pull/62566) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Log a startup warning when `TieringOffloadingSpec`'s secondary-tier KV can't be shared across tensor-parallel sizes, i.e. unless `canonical_layout` is on **and** the model's KV cache layers (and the parallel configuration) are certified parallelism-agnostic. This is the first follow-up listed in #62283.

Related: #62283, #55191 (core fix: direct caches keep TP in their namespace), #61822 (`canonical_layout` docs).

## Claims

- One warning per engine at startup when there is at least one secondary tier and either:
  - `canonical_layout` is off (direct layout), or
  - `canonical_layout` is on, but the layers can't all be certified as parallelism-agnostic (for example Mamba/GDN hybrids, which fall back to the opaque mapping), or PP, DCP or PCP is > 1. Today, this case starts up normally with nothing in the log saying sharing is off.
- No warning when canonical KV is portable, and none without secondary tiers.
- No behavior change: it doesn't raise, and lookups and namespaces are unchanged.

## Details

- **Why:** without `canonical_layout`, the direct layout's bytes depend on the engine's parallel configuration. Engines with different TP sizes sharing a tier get silently wrong KV today (#62283), or always miss once #55191 lands. Nothing at startup tells the user why. With `canonical_layout` on, a model with layers that can't be certified (for example Mamba/GDN layers, which fall back to the opaque mapping) keeps TP in the namespace and never shares across TP sizes, and only an `all_layers_portable=False` info line hints at it.
- **Where:** `TieringOffloadingSpec.get_manager()`, next to the existing "Created TieringOffloadingManager" log. It runs once per engine on the scheduler side, whereas `__init__` also runs in the workers.
- **Condition:** `secondary_tiers and not (canonical_layout and is_parallelism_agnostic)`. It requires the user's `canonical_layout` flag, not just `is_parallelism_agnostic`: before #55191, that flag is True in exactly the direct-layout case that corrupts, so gating on it alone would hide the warning where it matters most. After #55191, `is_parallelism_agnostic` is False whenever `canonical_layout` is off, so the same condition stays correct. With `canonical_layout` on, the static `is_parallelism_agnostic` check decides whether the tier's namespace drops TP. It is also False for DCP > 1 or `world_size != tp_size` (PP or PCP > 1), so the message names "no PP, DCP or PCP" alongside the layer requirement.
- **Wording:** the warning says KV is "only valid for" engines with the same parallel configuration, not "only reusable by". Until #55191 lands, a cross-TP read on the V1 runner loads wrong KV instead of missing, and "only valid for" is accurate before and after #55191.
- **Known false positives:** the advice is harmless in each case. Excluding them would mean hardcoding tier names or more namespace rules in the spec.
  - Replicated MLA without `canonical_layout`: it can already be shared between engines with TP > 1, but still gets the warning.
  - The `example` tier (in-process memory) and the `kvcr` tier: they don't share KV across engines through the `FileMapper` namespace, but still get the warning.
- **Level:** `warning`, as the issue asks. Happy to switch to `info` if it's too noisy for single-topology deployments.
- **Docs:** no changes here. #61822 documents `canonical_layout` in the KV offloading usage guide.
- **Not a duplicate:** no open PR references #62283 or adds this check. #55191 changes the namespace gate in `offloading/config.py`, and this PR doesn't touch that file.
