# [Bugfix][P/D] Reject P/D kv_transfer_params with several prompts

[Upstream PR](https://github.com/vllm-project/vllm/pull/65063) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

A P/D leg (`kv_transfer_params` with `do_remote_prefill` or `do_remote_decode`) describes the KV transfer of one prompt. `/v1/completions` with a prompt list and `/v1/chat/completions/batch` with several conversations accept such a leg today and return HTTP 200 with every later prompt decoded from the first prompt's KV. This PR rejects those requests with HTTP 400. `n > 1` has the same shape and is left to #38900.

## Claims

- `/v1/completions` with more than one prompt and `/v1/chat/completions/batch` with more than one conversation fail with HTTP 400 (`param: kv_transfer_params`) when `kv_transfer_params` sets `do_remote_prefill` or `do_remote_decode`.
- Both rules are `model_validator`s on the request models, so a rejected request is answered in body validation; a rejected decode leg's prefill blocks are freed at lease expiry, as for every other validation error on these requests.
- Single-prompt requests, and `kv_transfer_params` without the P/D keys (offloading hints such as `max_offload_tokens`), are unchanged.

Each P/D request follows the router steps in Details: the prefill leg is the client body with `kv_transfer_params: {"do_remote_decode": true}` and `max_tokens: 1`, the decode leg is the client body with the prefill response's `kv_transfer_params`. The `/v1/completions` 400:

```json
{"message": "Completions with P/D `kv_transfer_params` take a single prompt: one KV transfer cannot serve 2 prompts. (parameter=kv_transfer_params)", "type": "BadRequestError", "param": "kv_transfer_params", "code": 400}
```

Rejection cleanup. Both 400s come from body validation, before `_with_kv_transfer_rejection_cleanup`, so a rejected decode leg leaves the prefill's blocks to the lease: on a decode that had already completed one P/D round trip, the rejected 2-prompt decode leg's prefill request expired unread (`Releasing expired KV blocks ... retrieved by 0 remote worker(s)`), where the same check placed in `_create_completion` inside the wrapper freed it in 2 of 2 runs. Every other `model_validator` on these requests behaves the same way, and with the prefill leg rejected first, as a router sends it, there is no decode leg.

## Details

Flow on main, NIXL pull mode, a router that forwards the client body to both legs (llm-d's P/D sidecar does this):

1. Router sends `/v1/completions` with `prompt: [A, B]`, `max_tokens: 1` and `kv_transfer_params.do_remote_decode` to the prefill.
2. Prefill runs `cmpl-X-0` (A) and `cmpl-X-1` (B), holds both under the KV lease, and returns one `kv_transfer_params`: `final_res_batch[0]`'s, for A.
3. Router sends `prompt: [A, B]` with those params to the decode.
4. Decode creates `cmpl-Y-0` and `cmpl-Y-1`; `to_sampling_params` gives both A's `remote_request_id` and `remote_block_ids`. Both read A's blocks, and B's request decodes from A's KV.
5. Prefill frees A after the first read. The second read is for a request it no longer tracks (`Potentially invalid KV blocks for unrecognized request`); B's blocks expire unread after the lease.

`/v1/chat/completions/batch` is the same at the decode (each conversation's `ChatCompletionRequest` copies the batch's `kv_transfer_params`), and its prefill response carries no `kv_transfer_params` at all.

Design:

- Reject, not support. `kv_transfer_params` is one dict per request and per response, so several prompts would need per-choice params in the response and a router that splits the decode leg; no router does that today. #38900 proposes that shape for `n > 1`.
- Only the P/D keys. Other connectors put request-agnostic hints in `kv_transfer_params` (`max_offload_tokens`, `max_load_tokens`, `include_output_tokens`) that are valid on every prompt.
- Both checks are `model_validator`s: the completions one on `CompletionRequest` next to `validate_prompt_list_length`, counting prompts as `prompt_to_seq` does (a string, a flat token list or one embedding is one prompt; `prompt_embeds` add to `prompt`), the batch one next to #55771's `prompt_token_ids` rule in `BatchChatCompletionRequest.check_batch_mode`. They run in body validation, before `_with_kv_transfer_rejection_cleanup`, like the other validators on these requests (14 on `CompletionRequest` and 19 on `ChatCompletionRequest` raise 400 there), so a rejected decode leg's prefill blocks wait for the lease; the Validation section measures this.
- Not gated on a configured connector, matching the batch `prompt_token_ids` rule: the request is malformed either way.

A production P/D deployment (NIXL pull mode behind llm-d's sidecar) shows the step 5 pair 4 times in 30 h of prefill logs: a read for an unrecognized `cmpl-...-0`, then 30 s later an unread expiry of `cmpl-...-1` from the same request.

- vMaroon · comment · 2026-11-02T19:52:16Z · [source](https://github.com/vllm-project/vllm/pull/65063#discussion_r4447020052)

File: `vllm/entrypoints/openai/completion/serving.py` · line None

Because of the rejection cleanup. The route parses `CompletionRequest` before `create_completion` is called, so a 400 from a pydantic validator never goes through `_with_kv_transfer_rejection_cleanup`. For a `do_remote_prefill` leg that means the prefill keeps the blocks pinned until the lease runs out. Doing the check after `render_completion_request` keeps the 400 inside the wrapper, so the connector gets notified and the prefill frees the blocks.

Same reason #55771 put the `prompt_token_ids` check at render time and only used a validator on the batch endpoint, which isn't wrapped. That's also why the batch check in this PR is in the model.

Smaller point: after rendering I can just use `len(engine_inputs)`. In the model I'd have to work the count out again from the raw body (`prompt_to_seq` treats a flat `list[int]` as one prompt, and `prompt_embeds` add to it).

I can move it next to `validate_prompt_list_length` if you'd rather have it there. The trade-off is that a rejected decode leg then holds the prefill KV for the length of the lease.
