# [Kimi-K3][ROCm] AttnRes: runtime strides, packed D loads, and per-phase launch tuning

[Upstream PR](https://github.com/vllm-project/vllm/pull/58861) · state: open · merged: False

## Original PR description

## Purpose

Speed up the AMD AttnRes kernel in `vllm/models/kimi_k3/amd/ops/attn_res.py`, which runs 187 times per Kimi-K3 decode step (93 layers, `attn_res_block_size` 12, two calls per layer plus the final one).

**Addressing (first commit).** 

- Apply the Triton kernel optmization.
    - remove nonnecessary tl.constexpr to reduce number of kernels
    - provide compiler hints to improve vectorization
    - pipeline loop
    - add heuristics based on the tuned configs 
    - use exp2 fast intrinsics.

**Auxiliary prefix store (third commit).** The five DSpark target layers each launched a bf16 add of `prefix + mlp_output` (about 4.1 us, 0.02 ms/step) and then the next AttnRes added that same pair. AttnRes already rounds that sum to bf16 for the in-place prefix update. This commit stores that packed value into the auxiliary buffer from the same store, and `KimiLinearModel` passes the buffer in instead of adding. The snapshot stride is a runtime pitch, like the other row strides. A non-final pipeline-parallel rank whose last layer is an auxiliary layer still uses one `torch.add` into that buffer, because no following AttnRes runs on that rank.

## Test Plan

- First commit: bit-compare against the previous kernel on MI355X (gfx950), Triton 3.8:
  - decode, hidden 7168, with delta and output norm
  - padded rows (prefix/delta/block pitches not divisible by 16)
  - prefill, 320 tokens
  - `num_blocks == 0` with a block write and output norm
- First commit: confirm the generated AMDGCN still uses `buffer_load_dwordx4` / `buffer_store_dwordx4` on those launches.
- Second commit: the same ISA check on every new launch config (decode single-tile `BLOCK_L` of 1, 2, 4, 8, and 16 with 8 warps; prefill `BLOCK_L = 1`, 4 warps, 2 stages), including a padded-row launch.
- Second commit: sweep `BLOCK_L` x `num_warps` x loop stages per block count (0-8) at decode (8 tokens) and prefill (512 tokens), graph-replayed on MI355X with no profiler.
- Both commits: `tests/models/kimi_k3/test_amd_attn_res.py` from the full checkout.
- Timing of the final kernel over the K3 decode call mix, and prefill at 320 tokens.
- Third commit: `tests/models/kimi_k3/test_amd_attn_res.py` checks the auxiliary snapshot equals the bf16 prefix update, including padded rows and the no-delta path.
- Fifth commit: `test_amd_attn_res.py` adds 255 and 256 tokens, where the launch changes from the decode tile to the prefill tile. The FP8 test also passes the auxiliary snapshot, because the DSpark target path uses both in one launch. `test_eagle3.py` checks that `KimiDecoderLayer` gives its snapshot to the pre-attention AttnRes.

## Test Result

**Correctness.** The first commit matched the previous kernel bit-for-bit on the four shapes above, including the in-place prefix update and the optional block write, and its compiled AMDGCN still contains `buffer_load_dwordx4` and `buffer_store_dwordx4` (8–20 loads and 4–8 stores, depending on the constexpr variant).

The second commit keeps that packing. On MI355X, every launch config above compiles to `buffer_load_dwordx4` and `buffer_store_dwordx4`:

| launch | loads x4 | stores x4 |
|---|---:|---:|
| decode, 0 blocks, write + output norm, `BLOCK_L=1`, 8 warps | 4 | 4 |
| decode, 1 block, delta + output norm, `BLOCK_L=2`, 8 warps | 12 | 4 |
| decode, 2 blocks, delta + output norm, `BLOCK_L=4`, 8 warps | 15 | 4 |
| decode, 4 blocks, delta + output norm, `BLOCK_L=8`, 8 warps | 19 | 4 |
| decode, 8 blocks, delta + output norm, `BLOCK_L=16`, 8 warps | 27 | 4 |
| decode, 5 blocks, padded rows, write, `BLOCK_L=8`, 8 warps | 6 | 2 |
| prefill, 4 blocks, delta, `BLOCK_L=1`, 4 warps, 2 stages | 24 | 8 |
| prefill, 8 blocks, delta + output norm, `BLOCK_L=1`, 4 warps, 2 stages | 28 | 8 |

Aligned rows use only those packed accesses (no `dwordx2`, scalar `dword`, or 16-bit load/store). The padded-row launch still has a 16-bit fallback where the pitch is not divisible by 16 (103 loads, 32 stores), the same path as the first commit. No scratch traffic and no VGPR spills on any of these launches.

The second commit is no longer bit-identical to the previous kernel: the single-tile reduction order, the pipelined loop and `exp2` move outputs by at most one bf16 ulp. The in-place prefix update and the block write are unchanged. `tests/models/kimi_k3/test_amd_attn_res.py` from the full checkout at `985e9792` (`PYTHONPATH` on `xguo/attn-res-triton-hints`, not a copied kernel file): 9 passed on MI355X in 9.55s.

**Performance.** MI355X, hidden 7168, graph-replayed, no profiler. Decode is weighted by the K3 call mix (187 calls per step):

| | before | after |
|---|---|---|
| decode, 8 tokens | 6.65 us/call, 1.24 ms/step | **5.59 us/call, 1.05 ms/step** |
| prefill, 320 tokens, 4 blocks | 13.6 us | **11.9 us** |
| prefill, 320 tokens, 8 blocks | 20.6 us | **17.2 us** |

Per block count at decode, the single-tile config was the fastest at every block count from 1 to 8. The largest win is 8 blocks (9.52 -> 7.46 us), where the previous `BLOCK_L = 4` needed three loop trips. Pipelining helps configs that actually loop (e.g. 1-source tiles at 8 blocks, 13.5 -> 11.0 us), but at decode it did not beat the single tile. At prefill, 2 stages were consistently faster (7–11%) and 3 stages were often slower.

**Third to fifth commits.** MI355X (gfx950), rebased on `main`, latest ROCm nightly:

```bash
pytest tests/models/kimi_k3/test_amd_attn_res.py tests/models/kimi_k3/test_eagle3.py
```

30 passed. The full `tests/models/kimi_k3` folder: 319 passed, 83 skipped. `test_latent_moe_tail.py` did not collect, because the image has no `ray` module. When the decoder layer does not pass the snapshot, the new wiring test fails.
