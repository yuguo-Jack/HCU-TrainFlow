# [KVConnector][Mooncake] Add optional KV compression for P/D transfer

[Upstream PR](https://github.com/vllm-project/vllm/pull/61085) · state: open · merged: False

## Original PR description



## Overview

This PR adds **optional KV compression to Mooncake P/D transfer** through a versioned interface to [KVServe](https://github.com/hpdps-group/KVServe) (SIGCOMM 2026), implementing the fixed-profile foundation of [RFC #59538](https://github.com/vllm-project/vllm/issues/59538).

vLLM retains KV-cache adaptation, workspace reservation, Mooncake transport, and request/session lifetime. KVServe owns compression layouts, algorithms, and Python/CUDA backends. The change is rebased onto upstream main `aa3564ceef`.

## Claims

- **Compression interface:** a small adapter translates vLLM cache geometry into KVServe's versioned planning/encode/decode API. The runtime is optional and imported only when compression is enabled.
- **Mooncake integration:** prefill encode → Mooncake TransferEngine write → decode restore into the destination KV cache, while preserving cache registration, region mapping, and transfer completion semantics.
- **Memory and lifecycle:** compression workspace is reserved before automatic KV-cache sizing. Bounded GPU slots, CUDA completion events, helper liveness, cancellation drains, and slot credits prevent buffers from being reused while work is in flight.
- **Compatibility:** the disabled path does not import KVServe or create compression buffers/helper state. Dense BF16 FullAttention is supported, including FullAttention regions in hybrid models; unsupported layouts and topologies fail explicitly.

The runtime is maintained on KVServe's `v1` branch. Native Mooncake users install nothing additional. Compression users can install the pinned runtime as a normal wheel from its immutable source archive without cloning KVServe or changing `PYTHONPATH`.

## Validation

The representative benchmark below was recorded before the current rebase. GPU validation used two RTX 5090 hosts, TP2 per P/D instance, Llama-3.1-8B-Instruct, Mooncake TCP over a 25 Gb/s link, HotpotQA, concurrency 8, and `max_tokens=32`. The representative fixed-profile benchmark ran each mode twice:

| KV compression | Batch time (s) | Mean TTFT (s) | Completed |
| --- | ---: | ---: | ---: |
| Off | 42.25 ± 9.40 | 9.11 ± 2.39 | 32/32 |
| On (KVServe) | 29.19 ± 0.14 | 6.38 ± 0.03 | 32/32 |

In this configuration, KVServe achieved:

- **30.9% lower batch completion time** and **30.0% lower mean TTFT**.
- **5.84× payload compression**, or 82.9% fewer transferred payload bytes.
- A **2.66-point HotpotQA F1 reduction** with the tested lossy profile.

These measurements characterize this hardware, transport, model, profile, and workload rather than a universal speedup.

After rebasing onto main `aa3564ceef`, the targeted Mooncake, session/helper, compression-adapter, and MultiConnector regression suites passed **216 cases** (two model-dependent cases deselected). A same-host RTX 5090 TP1 P/D smoke test completed **2/2 HotpotQA requests in each of Off and On (KVServe)**, concurrency 2 and `max_tokens=32`, with `VLLM_GPU_SYNC_CHECK=error`; the compressed path reported zero failed sends/receives. This is a correctness check, not a new performance comparison. Pre-commit, including mypy, passed.

- The retained vLLM integration/lifecycle tests plus independent KVServe runtime suites account for **296 passing cases per backend**, Python and CUDA, with no failures, errors, or skips in the recorded runs.
- Cross-host requests completed all SSE streams; transfer metrics reported no failed sends or receives with `VLLM_GPU_SYNC_CHECK=error` enabled.
- The installed wheel and both remote source trees were checked against committed sources. The wheel includes CUDA JIT sources, and importing the runtime does not import vLLM.
- Pre-commit, Python 3.11 mypy, DCO, and direct installation from the immutable GitHub source archive passed. Upstream test CI remains gated by the repository's pre-run check.

## Details

The request path is:

1. vLLM converts its cache specs into KVServe `CacheSpec` objects and reserves the planned workspace before KV-cache sizing.
2. The prefiller encodes selected KV blocks into bounded slots, waits for the encode event, and submits the payload through the existing Mooncake TransferEngine.
3. The decoder waits for received bytes, restores KV directly into its cache, and returns the slot credit only after the decode event completes.

Existing native RDMA batching remains in place. Compressed payloads use the same TransferEngine and its configured transport; the reported GPU validation used TCP, and RDMA remains unvalidated. The helper owns session/credit control, while GPU runtime and TransferEngine operations remain in the engine process.

Algorithm, numerical, kernel, workspace, partial-tail, and cross-backend tests live in KVServe. The external 3,298-line runtime is not part of this vLLM diff.

This PR provides one complete fixed-profile integration. Generic provider registration, dynamic selection, additional algorithms, and Mooncake Store support remain future work. Both peers require the same runtime and wire-profile version; missing or incompatible optional dependencies fail explicitly when compression is enabled. Native Mooncake retains main's layout caching and RDMA sleep hooks; sleep mode is explicitly rejected when compression or raw aggregation is enabled.
