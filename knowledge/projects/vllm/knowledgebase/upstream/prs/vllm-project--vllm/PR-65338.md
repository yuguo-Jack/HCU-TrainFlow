# [Bugfix][Kernel] Align packed GDN decode with speculative recurrence

[Upstream PR](https://github.com/vllm-project/vllm/pull/65338) · state: open · merged: False

## Original PR description

## Overview

Give the packed recurrent GDN decode path and the speculative-verification path
one kernel, one implementation of the recurrence math, one launch
configuration, and one default routing decision on CUDA. This addresses the
packed-vs-verification and batch-dependent-configuration parts of #62851, and
targets the residual few-ULP mismatch on sm_110/Jetson Thor reported in
#65338, without relaxing the bitwise regression.

## Claims

- **One decode kernel.** `fused_recurrent_gated_delta_rule_packed_decode` and
  `fused_sigmoid_gating_delta_rule_update` are thin wrappers around
  `gated_delta_rule_decode_kernel`. The packed path passes q/k/v as views of
  `mixed_qkv` with explicit token strides instead of gathering them.
- **One default routing on CUDA.** Speculative decode now defaults to that
  shared kernel. The CUDA post-conv MTP op
  (`torch.ops._C.fused_gdn_decode_post_conv_mtp`) is reachable only with an
  explicit `VLLM_GDN_DECODE_KERNEL=cuda`. It uses `__expf`/`rsqrtf` fast-math
  intrinsics and warp reductions that the Triton kernel cannot reproduce, so
  leaving it in the default path would keep a request's state dependent on
  whether it ran alone or inside a verification batch.
- **Shared math.** `l2norm_qk`, `sigmoid_gating` and `recurrent_step` live in
  `recurrent_common.py`, and are also used by the FLA prefill recurrence, the
  fused prefill post-conv and the MTP post-conv update (including the ROCm
  Triton port).
- **Shared, batch-independent config.** `(BK, BV, num_warps, num_stages)` is a
  function of `(K, V, state dtype, platform)` only: no batch size and no device
  id. The removed SM100 table keyed `BV` on `B * HV <= 64`; a request can move
  between a one-request verification batch and a large decode batch, so a
  batch-keyed tile reintroduces the divergence by construction. Hardware-keyed
  tuning is not itself the problem and can be restored once it is re-measured
  against the new four-warp kernel; the old numbers were tuned for the previous
  one-warp packed kernel and do not transfer.
- `T` is a constexpr and is pinned to 1 for varlen launches (a runtime `T` cost
  1.3-1.6x in local measurements).
- The grid split for `num_seqs * HV > 65535` is retained. Padded state slots now
  write zeros to `out` instead of leaving it uninitialized.

## Token and state alignment

Packed decode and speculative verification intentionally use different input
layouts. Packed decode has one row per request (`mixed_qkv[B, ...]`, `T = 1`)
and a 1-D state index `ssm_state_indices[n]`. Verification has one row per
token (`q[1, total_tokens, ...]`) grouped by `cu_seqlens`, and a 2-D state index
`ssm_state_indices[n, t]`; its initial state is the checkpoint at
`num_accepted_tokens[n] - 1`. They align on `(request, timestep)`, not on a raw
row index. Under varlen, `T` is pinned to 1 only as a specialization constant;
the loop bound is `cu_seqlens[n + 1] - cu_seqlens[n]`.

For fp32 state, one multi-token verification launch is bitwise equal to the
same number of per-token packed launches. For a reduced-precision state cache
with `T > 1`, the verification kernel keeps `b_h` in fp32 registers across
tokens while per-token packed decode round-trips it through the cache, so
bitwise equality is not expected. Qwen3.8's HF config sets
`text_config.mamba_ssm_dtype = "float32"`, so the fp32 comparison covers the
production configuration for this model.

## End-to-end validation

Qwen3.8-27B-FP8 + DFlash2, TP=4 on four H100 MIG slices, `enforce_eager=True`,
greedy, one prompt, 128 generated tokens. The reference is the same engine
without speculative decoding; `exact` compares the two token sequences.

| build | spec-decode kernel | result |
|---|---|---|
| pre-fix `ddbe9beb75` | CUDA fused MTP (default) | differs at token 37: `5614` vs `6007` |
| pre-fix `ddbe9beb75` | shared Triton | differs at token 37: `5614` vs `6007` |
| this PR | CUDA fused MTP, packed on | differs at token 10: `8046` vs `623` |
| this PR | CUDA fused MTP, packed off | differs at token 10: `8046` vs `623` |
| this PR | shared Triton (now the default) | **exact, 128/128** |

The last row is deterministic: two target-only runs and three speculative runs
are byte-identical, and both sequences hash to
`e48d57d287f9f58eef807feab6c4a79090864796fa23a622d54a7e2e38383e7d`. Disabling
packed decode leaves the mismatch unchanged, which rules out the packed kernel
as the cause of the remaining CUDA-MTP divergence.

Token 37 of the reference is a bitwise tie (`5614` and `6007` both
`-1.4804171323776245`), so the sequence change relative to the pre-fix build is
a tie-break, not a quality change: unifying on one reduction order has to move
one side, and the packed kernel now uses the normalization form the
verification path already used.

## Performance

Kernel level, H100, CUDA-graph replay, 50 launches per graph, new/old time:

| path | state | B=1 | B=4 | B=16 | B=64 |
|---|---|---|---|---|---|
| packed | fp32 | 0.895 | 0.723 | 0.883 | 0.869 |
| packed | bf16 | 0.981 | 0.933 | 0.955 | 1.000 |
| verification | fp32 | 0.837 | 1.139 | 0.973 | 0.989 |
| verification | bf16 | 1.136 | 0.799 | 0.962 | 0.980 |

CPU enqueue: 31.0 -> 37.7 us/call (+6 us). Geomean over the four sizes is
0.84-0.97x for packed and 0.96-0.98x for verification. The packed fast path
keeps its performance; verification is mostly neutral or faster, with two ~14%
points.

Model level, the end-to-end setup above, three speculative runs after a warmup
run, seconds for 128 tokens:

| spec-decode kernel | warm runs |
|---|---|
| CUDA fused MTP | 3.11, 3.24 |
| shared Triton | 2.40, 2.38 (default routing: 2.40) |

The shared kernel is ~1.3x faster for this batch shape on this host, so moving
the default does not trade speed for parity. Single-host numbers with eager
execution; they are not a serving benchmark.

## Validation

Kernel tests, `tests/kernels/fla/test_fused_recurrent_packed_decode.py`:
25 passed.

- Bitwise packed vs single-token verification comparison, fp32 and bf16 state,
  1/2/7 tokens (`test_packed_decode_matches_serial_speculative_recurrence`).
- One 4-token varlen verification launch vs four per-token packed launches,
  bitwise, fp32 state (`test_packed_decode_matches_batched_speculative_verification`).
  A bf16 cache cannot match by construction: the multi-token launch keeps the
  state in registers across tokens while per-token launches round-trip it.
- Batch invariance: the same sequence is bitwise identical alone and in an
  8-request launch (`test_packed_decode_is_batch_size_invariant`).
- Both entry points resolve the same config
  (`test_decode_paths_share_one_kernel_config`).

Routing tests, `tests/kernels/mamba/test_gdn_fused_mtp.py`: 24 passed, including
`test_spec_decode_kernel_routing`, which pins the four cases (CUDA spec defaults
to the shared kernel, explicit `cuda` opts in, no spec leaves CUDA alone, non-CUDA
unchanged).

Full suites before the routing change: `tests/kernels/fla tests/kernels/mamba`
-> `2689 passed, 41 skipped` (16:09). The routing change touches no kernel code;
`tests/kernels/fla/test_fused_recurrent_packed_decode.py` and
`tests/kernels/mamba/test_gdn_fused_mtp.py` were re-run together afterwards:
49 passed.

Cross-arch codegen, no sm_110 hardware; Triton compiled for `(11, 0)`:

- Single-token packed vs verification specializations: identical ordered TTGIR
  FP op sequence (41 ops) and identical PTX (336 ops). The whole normalized
  TTGIR differs by one address constant.
- Multi-token varlen verification vs packed: identical ordered TTGIR FP op
  sequence (41 vs 41). PTX differs only because ptxas pairs independent f32 ops
  into `*.f32x2` in the dynamic loop; each `f32x2` is two independent IEEE f32
  operations in one instruction.

The sm_110 codegen is verified; an on-device Thor re-run is still pending.

## Details

The root cause is that the packed path and the verification path were
independently written kernels. #65338 aligned the normalization form and the
warp count, but the two paths still (a) compiled separate programs and (b) used
different `BV` (4 vs 32). On H100 that happened to be bitwise identical; on
sm_110 it was not. Sharing the kernel body and the tile removes the degrees of
freedom instead of matching one configuration on one architecture. The same
argument applies to the CUDA MTP op: it is a third, separately written
recurrence, so it cannot be part of a bitwise-parity claim.

For fp32 state with `K = V = 128` on CUDA the shared config uses `BV = 16`.
Measured on H100 with four warps: at `B=128` packed it is 79.1 us vs 78.5 us for
`BV=32` and 104.9 us for the old `BV=4`; for nine-token verification at
`B=64` it is 189 us vs 187 us for `BV=32` and 282 us for `BV=4`. The old
`BV=4` was tuned for the one-warp kernel and costs 1.3-1.5x here. bf16/fp16
state keeps `BV = 32`.

Duplicate work: `gh pr list --search "62851 in:body"` returns only this PR.
#59414 touches the same grid dimension but not the kernel body or config.
#60400 tunes the packed kernel per ROCm arch/batch; a batch-dependent config
cannot coexist with this parity guarantee, so that table needs to be re-derived
against the unified kernel. I have no ROCm hardware to re-measure it here.

Scope: this unifies the FLA Triton recurrent kernels used by CUDA, ROCm and
XPU, and routes CUDA speculative decode to them by default. The ROCm AITER
path, the FlashInfer GDN backends and the CPU C++ kernels are separate
implementations and are not changed here.

**TL;DR: the parity bug reproduces on sm_110 (larger than on H100), the fix improves the mismatch ~256×, but the new regression's bitwise expectation does not hold on this architecture.**

A/B, same test, only `fused_recurrent.py` switched (parent/main version vs this PR):

| kernel | result of `test_packed_decode_matches_serial_speculative_recurrence` |
|---|---|
| main (pre-fix) | FAIL — final-state compare: **max abs diff 7.63e-06**, max rel diff **0.167** at (0, 6, 44, 65) |
| this PR | FAIL — outputs pass; final-state compare: **max abs diff 2.98e-08**, max rel diff **1.59e-04** at (16, 30, 114) |
| this PR, other 16 tests in the file | all pass on sm_110 |

Notes:

- The pre-fix relative difference (16.7%) is far larger than the 9.54e-7 absolute error recorded on H100, consistent with a normalization defect hitting small-magnitude state entries hardest — and the fix's rsqrt alignment clearly addresses the same defect here.
- The residual after the fix (a few ULPs: 2.98e-8 ≈ 2^-25) is likely reduction-order/tiling divergence in the arch-specific configuration sm_110 compiles to — the kernel's history (`#63864` SM90 tuning, `#61355` SM100-family tuning) suggests per-arch paths, and the packed and speculative kernels presumably still reduce in a different order on this target.

Suggestion, if bitwise equality is only achievable on some architectures: a tolerance such as `atol=1e-6, rtol=1e-3` on the final-state compare still discriminates cleanly (pre-fix rel 0.167 and abs 7.6e-6 both fail it with wide margin; post-fix 3e-8 / 1.59e-4 pass it) and would make the regression portable beyond H100. Alternatively, keeping `rtol=0, atol=0` documents an H100-only guarantee and will likely fail on other archs.

Happy to dig into which shape/index drives the sm_110 residual (or run the packed-decode probe at other batch shapes) if useful. Full disclosure: run was AI-assisted (opencode); I executed and reviewed the A/B locally, swapping only `fused_recurrent.py` between runs.
