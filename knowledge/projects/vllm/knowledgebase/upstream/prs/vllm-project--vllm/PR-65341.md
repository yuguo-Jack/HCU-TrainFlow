# [ROCm][Perf][Qwen4Exp] Use one warp for QSA sparse paged attention prefill on gfx950

[Upstream PR](https://github.com/vllm-project/vllm/pull/65341) · state: closed · merged: False

## Original PR description

## Purpose

On gfx950, use one warp per program instead of two in the `base_programs > 512` profile (prefill and mixed steps) of `qsa_sparse_paged_attention`, for every query-head group size. Other architectures keep the current profile.

In a profile of an 8,192-token prefill/mixed step on MI355X TP2 (a downstream build of this kernel) the kernel is about 26 ms of a 180 ms step.

Related: #62590 (gfx942 `BLOCK_N`, same branch, independent through the arch gate), #64405 (draft, mxfp4 profile for `base_programs <= 512`), #59437 (opt-in FlyDSL backend; this PR changes the default Triton path).

## Changes

- `qsa.py`: `partial_warps = 1` when `on_gfx950()` (previously also required `block_m == 16`, which was dropped after the sweep below).
- `test_qsa_amd.py`: two prefill cases that reach the profile, `tp2_split1_prefill` (513 rows, 12 q / 1 KV heads) and `tp1_split1_prefill` (257 rows, 24 q / 2 KV heads).

## Results

Upstream main's kernel, one MI355X, median ms per call (eager, CUDA events, 20 warm-up + 100 timed, three interleaved rounds, round-to-round spread at most 0.8 %):

| q heads per KV head | BLOCK_M | 2 warps (main) | 4 warps | 1 warp (this PR) | 2 w / 1 w at 8,192 rows | 2 w / 1 w over 640 to 16,384 rows | 1-warp VGPR / spills |
|---:|---:|---:|---:|---:|---:|---:|---|
| 24 | 32 | 4.489 ms | 3.869 ms | 1.956 ms | 2.30x | 2.07 to 2.35x | 512 / 25 |
| 12 | 16 | 2.395 ms | 1.854 ms | 1.331 ms | 1.80x | 1.58 to 1.83x | 403 / 0 |
| 6 | 8 | 2.210 ms | 2.916 ms | 1.596 ms | 1.39x | 1.23 to 1.51x | 348 / 0 |
| 3 | 4 | 1.909 ms | 2.659 ms | 1.612 ms | 1.18x | 1.11 to 1.22x | 310 / 0 |

- One warp is fastest in all 24 group x row-count cells (rows 640, 1,024, 2,048, 4,096, 8,192, 16,384).
- Output is bitwise equal across 1, 2 and 4 warps in every cell. Against an fp64 reference on 132 boundary and random rows at 8,192 rows, rel_l2 is 1.73e-3 to 1.76e-3 for every variant.
- This branch's launcher selects one warp at all four group sizes: time within 0.4 % of the one-warp substitution, output bitwise equal to it.
- For Qwen3.8-Flash-Next (24 q / 2 KV heads) the group size is 12 at TP1 and TP2, 6 at TP4 and 3 at TP8. 24 q heads per KV head is not a shape of that model; it is included because the kernel is generic.
- End to end: not measured yet (see Remaining).

## Method

- **Image:** `vllm/vllm-openai-rocm:nightly-40941f2c4ba96fba0a7e282a5355e89cd74d9ac5`, the same image as Docker Hub's `nightly` (built 2026-11-03 06:07 UTC; no newer one at 09:48 UTC): vLLM 0.33.0rc1.dev573+g40941f2c4, torch 2.13.0+rocm10.0.0, HIP 7.15.26333, Triton 3.8.0, one AMD Instinct MI355X (`gfx950:sramecc+:xnack-`). The commit is 17 commits behind this PR's base (`ddbe9beb75`), but its `qsa.py` and `test_qsa_amd.py` are byte-identical to the base's (same git blob ids), so the numbers are for upstream main's kernel and tests.
- **Inputs:** Qwen3.8-Flash-Next paged K/V layout (1,568-token pages, 1 KV head, head_dim 256, bf16), random q / K / V N(0,1), 2,051-wide top-k indices from a captured 8,192-token prefill step.
- **Cross-check:** the same sweep on an older image (vLLM 0.32.1rc1.dev276, torch 2.13.0, HIP 7.2, Triton 3.8.0) agrees within 3 % at 8,192 rows.

## Notes

- Only the `base_programs > 512` branch changes; the decode and small-batch profiles are untouched and unmeasured here.
- TP1 has two KV heads (grid `(rows, 2, 1)`); the sweep used one, so TP1 timing is not measured, only its numerics (`tp1_split1_prefill`).
- Four warps beat two at 12 and 24 heads per KV head and lose at 6 and 3; one warp is fastest everywhere. Why is not established.
- No open or merged PR touching `qsa.py` changes this profile (searched 2026-11-03). Whichever of the adjacent PRs above lands second needs a trivial rebase around the `else:` branch.
