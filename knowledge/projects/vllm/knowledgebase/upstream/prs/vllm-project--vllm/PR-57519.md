# [Bugfix][Benchmark] Fail streams that end in a server error event

[Upstream PR](https://github.com/vllm-project/vllm/pull/57519) · state: open · merged: False

## Original PR description

## Purpose

`vllm bench serve` records a request as successful whenever any token chunk arrived, even when the stream ends in a
server error event. A generation that fails after the response has started cannot change the HTTP 200 already sent, so
the stream generators report the failure in-band:

```text
data: {"error": {"message": "EngineCore encountered an issue. ...", "type": "InternalServerError", "param": null, "code": 500}}
data: [DONE]
```

(That payload is copied from a real run below; the unit tests use a cause-neutral message, because the client has to
fail on any `error` object whatever produced it.)

Both benchmark clients read only `choices` and `usage`, so the truncated request joins `completed`, its partial tokens
join `total_output` and `output_throughput`, and its short end-to-end time joins `mean_e2el_ms` and
`percentiles_e2el_ms`. The report is biased in the optimistic direction exactly when the server is failing.

The same envelope is emitted for a dead engine, a failed tool parser and a generation error (five files under
`vllm/entrypoints/` call `create_streaming_error_response`), so the fix keys on the `error` object rather than on any
one cause.

This change:
- tracks the error object in `async_request_openai_completions`, `async_request_openai_chat_completions` and
  `async_request_openai_audio`, in both `vllm/benchmarks/lib/endpoint_request_func.py` and the standalone
  `benchmarks/backend_request_func.py`;
- fails the request and puts the server's error object in `output.error`;
- keeps the partial `generated_text` for `--save-detailed`;
- gives the error precedence over the existing "Never received a valid chunk to calculate TTFT" message, which names a
  symptom rather than the server's own reason.

## Why this is not a duplicate

Before opening this, I searched the open and merged PRs touching these files on 2026-09-18. The closest ones:
- **#54708** (merged) fails streams that carry *no* token chunk. A stream that produces tokens and then fails is still
  counted as a success.
- **#55508** (merged) fixed TTFT/E2E latency accounting in the same functions; it does not look at error events.
- **#54628** (open) adds error-event handling for the new Responses backend only, in a new function. This change brings
  the existing completions/chat/audio backends to the same behaviour and follows its `stream_error` shape, so the two
  should not conflict beyond a trivial rebase.

## Test Plan

Unit (no GPU), extending the existing fake-session suite:

```bash
pytest tests/benchmarks/test_endpoint_request_func_timing.py -v
```

`test_error_event_stream_is_not_reported_as_success` and its legacy counterpart stream two token chunks, then the
error envelope, then `[DONE]`, over all three streaming endpoints. Two tokens, not zero: that is the case #54708 does
not cover.

End-to-end on one RTX 3060 (clocks locked), Qwen2.5-0.5B-Instruct, `vllm bench serve --save-detailed`, random
512-token prompts, 128 output tokens, `--ignore-eos`; `kill -9` on the EngineCore process 20 s into the run, at
concurrency 16 and 64.

## Test Result

Unit: **24 passed** (18 before this change, plus the 6 new parametrizations). Reverting only the two source files puts
the 6 new tests back to failing. `pre-commit run --files <changed>` and `mypy-3.12` pass.

End-to-end at concurrency 64, classifying one unpatched run's own requests by token count:

| reported by the benchmark | reported | counting only complete requests | error |
|---|---:|---:|---|
| completed | 274 | 225 | **+22%** |
| mean E2EL | 2,566 ms | 2,790 ms | 8% too fast |
| output tokens | 32,684 | 28,800 | +3,884 partial tokens |
| output throughput | 2,745 tok/s | 2,418 tok/s | **+14%** |

49 of the 274 "successful" requests (18%) never produced their 128 tokens; their counts run 1–127, **median 121**, so
they do not stand out by eye. With the fix, the same fault reports **221 completed, all complete**, and each failed
request carries the server's error object.

Scope note: only a request that has already streamed a token and then receives the error event is miscounted, so the
size of the effect is the number of in-flight streams at the instant of the fault — 49 at concurrency 64, but only 1–4
at concurrency 16.

**Model evaluation:** not applicable. This only changes how the benchmark client classifies a response; no model,
kernel or serving path is touched.

## How this was found

While measuring failure modes of a vLLM server (deliberately `SIGKILL`ing EngineCore under load and watching what each
observer reports), the requests in flight at the fault ended with HTTP 200 after 1–116 of their 128 tokens. My own load
generator counted them as successes until I classified requests by token count; that raised the question of what
`vllm bench serve` does with the same streams, which is this bug.

## Follow-up

The Rust bench client (`rust/src/bench/src/backends/openai_completions.rs`, `openai_chat.rs`) fails a request only on
transport errors and has the same gap. I kept it out so this change stays in one language and one test suite, and will
send it separately — happy to fold it in here instead if you would rather have both at once.
