# [Bugfix][Benchmark] Fail streams that end in a server error event

[Upstream PR](https://github.com/vllm-project/vllm/pull/57519) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

`vllm bench serve` counts a request as successful when any token arrived, even if the stream then ends in a server error event. This fails those requests in the completions, chat and audio backends, in both `vllm/benchmarks/lib/endpoint_request_func.py` and the standalone `benchmarks/backend_request_func.py`.

Benchmark client only: no model, kernel or serving path is touched.

## Claims

- A stream that delivers tokens and then an `error` event is reported as failed, with the server's error object in `output.error`. Partial `generated_text` is kept for `--save-detailed`.
- The server's error takes precedence over "Never received a valid chunk to calculate TTFT", which names a symptom rather than the cause.
- Under a mid-run EngineCore kill at concurrency 64, the unpatched report overstates completed requests by 22% and output throughput by 14%, and understates mean E2EL by 8%.

## Validation

Unit (no GPU), at the rebased head `4a4eb4257`, on base `76c6f3f2a`. `test_error_event_stream_is_not_reported_as_success` and its legacy counterpart stream two tokens, then the error envelope, then `[DONE]`, over all three streaming endpoints.

```bash
pytest tests/benchmarks/test_endpoint_request_func_timing.py -k error_event
```

| Sources | Result |
|---|---|
| Base `76c6f3f2a` (new tests only) | 6 failed, each `AssertionError: assert not True` on `output.success` |
| This PR | 6 passed |
| This PR, full `test_endpoint_request_func_timing.py` + `test_responses_request_func.py` | 74 passed |

Those pytest runs used `--noconftest` in a CPU-only environment. `pre-commit run --hook-stage manual --files <changed>` passes, including mypy.

End-to-end on one RTX 3060 (clocks locked), Qwen2.5-0.5B-Instruct, `vllm bench serve --save-detailed`, random 512-token prompts, 128 output tokens, `--ignore-eos`; `kill -9` on EngineCore 20 s into the run. Measured at the original commit, before the rebase. Classifying one unpatched run's own requests by token count, at concurrency 64:

| Reported by the benchmark | Reported | Complete requests only | Error |
|---|---:|---:|---|
| completed | 274 | 225 | **+22%** |
| mean E2EL | 2,566 ms | 2,790 ms | 8% too fast |
| output tokens | 32,684 | 28,800 | +3,884 partial tokens |
| output throughput | 2,745 tok/s | 2,418 tok/s | **+14%** |

49 of the 274 "successful" requests (18%) never produced their 128 tokens; their counts run 1-127, median 121, so they do not stand out by eye. With the fix, the same fault reports 221 completed, all complete, and each failed request carries the server's error object.

Only a request that has already streamed a token and then receives the error event is miscounted, so the effect scales with in-flight streams at the fault: 49 at concurrency 64, 1-4 at concurrency 16.

Independent validation at the earlier commit `1e74a69c7`: [regression corpus](https://github.com/k21993/benchmark-stream-audit) from a comment on this PR.

No `RemoteOpenAIServer` regression test is added: a real server cannot deterministically emit this event mid-stream without fault injection, so the tests drive the real request functions over the existing fake session, and the end-to-end run above covers the real failure.

**Model evaluation:** not applicable; this only changes how the benchmark client classifies a response.

## Details

**Root cause.** A generation that fails after the response has started cannot change the HTTP 200 already sent, so the stream generators report the failure in-band:

```text
data: {"error": {"message": "EngineCore encountered an issue. ...", "type": "InternalServerError", "param": null, "code": 500}}
data: [DONE]
```

The clients read only `choices` and `usage`, so the truncated request joins `completed`, its partial tokens join `total_output` and `output_throughput`, and its short end-to-end time joins the E2EL statistics. The report is biased in the optimistic direction exactly when the server is failing.

**Design.** The same envelope is emitted for a dead engine, a failed tool parser and a generation error, so the fix keys on the `error` object rather than on one cause. It uses the same `stream_error` shape as the Responses backend.

**Not a duplicate.** Searched the PRs touching these files:
- #54708 (merged) fails streams with no token chunk; a stream that produces tokens and then fails still counted as a success.
- #55508 (merged) fixed TTFT/E2E latency accounting; it does not look at error events.
- #54628 (merged) handles error events for the Responses backend only.
- #62341 (merged) filters content-free chat chunks; this PR is rebased on it and keeps `_choice_has_streamed_output`.
- #64143 (open) changes SSE data-field parsing, not failure classification; it touches the same file, so whichever lands second needs a small rebase.

**Follow-up.** The Rust bench client (`rust/src/bench/src/backends/openai_completions.rs`, `openai_chat.rs`) has the same gap and is left out to keep this change in one language. #59736 covers token-less streams there, not this case. I can send it separately or fold it in here.

**How this was found.** While `SIGKILL`ing EngineCore under load to compare what each observer reports, requests in flight at the fault ended with HTTP 200 after 1-116 of their 128 tokens.
