# [Model] Nemotron-3.5-Transcribe: pack the audio tower's valid frames for MMEncoderAttention

[Upstream PR](https://github.com/vllm-project/vllm/pull/64944) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

Follow-up to #64282, from @Isotr0py's review there ("Can we use MMEncoderAttention with cu_seqlens for FA?"). Both
encoders of the Nemotron-3.5-Transcribe audio tower, the ASR encoder and the Sortformer speaker encoder, now run only
each row's valid frames, packed row after row, and attend through `MMEncoderAttention` with `cu_seqlens` instead of
padded, masked SDPA. The PR changes the model file, its tests and its docs note only.

## Claims

- The tower attends through vLLM's multimodal encoder attention: vLLM selects the platform's variable-length kernel
  (FlashAttention on the tested GPUs), and `--mm-encoder-attn-backend` applies to the tower.
- The tower is faster on batches of many clips (BF16, tower only): 3.1× and 2.5× on 32 and 64 clips on an RTX PRO
  6000, 1.51× and 2.15× on H100. On H100 it is slower on 8 clips and on 4 long clips (0.85× and 0.84×). Offline
  end-to-end RTFx on the RTX PRO 6000 quick sets does not change.
- Quick-set WER changes are small. On the long sets, AMI-IHM cpWER rises by 1.73 points, all from one meeting whose
  speaker attribution the packed tower changes in every run (six runs per arm, with GPUs swapped and request order
  shuffled); Earnings22 WER rises by 0.32 points from a few looping recordings whose link to the tower change is not
  known.
- `mm_encoder_attn_dtype='fp8'` is refused with a clear error. The FP8 and NVFP4 checkpoints quantize the linear
  layers of the tower's ASR encoder without this setting and are not affected.

The new tests fail without their code: the empty-batch test with the guard removed (vLLM's SDPA wrapper raises
`torch.cat(): expected a non-empty list of Tensors`), and the FP8 test with the refusal removed (vLLM's generic FP8
check raises a different message). The tiny tower is float32 and selects TORCH_SDPA, so the tests do not cover
FlashAttention; the real-tower measurements below do. CI runs the file in the CPU Multimodal Processor step.

**Exactness and accuracy** (each clip encoded alone; 64 short and 4 long clips; the released checkpoint). With
float32 and vLLM's TORCH_SDPA backend, the packed tower is bit-identical to main's padded tower for 68 of 68 clips at
the ASR states, speaker probabilities and embeddings, on both the RTX PRO 6000 and H100. In BF16, against that
float32 reference, both towers have the same typical error (ASR relative L2 median about 7e-3 on short clips on both
GPUs). On the four long clips, FlashAttention 2 (RTX PRO 6000) matches main's error (788 against 843 flipped speaker
frames of 4,314), while FlashAttention 3 (H100) has somewhat larger worst-case errors (ASR maximum 0.043 against
0.036; 358 against 316 flipped frames).

**Tower speed** (BF16, tower only, median of 10 alternating runs):

| Batch | Padded, RTX PRO 6000 (ms) | Packed, RTX PRO 6000 (ms) | Packed speedup, H100 |
|---|---|---|---|
| 8 clips | 15.7 | 13.8 | 0.85× |
| 32 clips | 107.2 | 34.1 | 1.51× |
| 64 clips | 148.7 | 60.0 | 2.15× |
| 4 clips of 55–115 s | 91.8 | 73.6 | 0.84× |

Offline end-to-end RTFx does not change (RTX PRO 6000, quick sets, English / multilingual: 386 / 428 packed, 390 /
426 padded): the tower does not limit serving throughput.

**Accuracy, quick sets** (offline; Open ASR leaderboard English, 18,341 rows scored as 18,006 entries; multilingual,
15,486 clips):

| Checkpoint | Padded WER (%) English / multilingual | Packed WER (%) English / multilingual |
|---|---|---|
| BF16 | 3.89 / 4.96 | 3.90 / 4.94 |

**Accuracy, long sets** (multi-speaker SOT, 164 sessions, cpWER; long-form, 451 recordings, WER with the loop
guardrail; padded and packed served side by side, each run twice):

| Set | Padded (%), run 1 / run 2 | Packed (%), run 1 / run 2 | Packed − padded (points) |
|---|---|---|---|
| SOT headline | 13.01 / 13.04 | 13.25 / 13.28 | +0.24 |
| SOT AMI-IHM | 10.27 / 10.50 | 12.04 / 12.20 | +1.73 |
| SOT AMI-SDM | 17.65 / 17.53 | 17.31 / 17.22 | −0.32 |
| SOT CHAES | 11.52 / 11.51 | 11.46 / 11.48 | −0.04 |
| SOT Mixer6 | 15.01 / 15.07 | 14.92 / 14.94 | −0.11 |
| Long-form CORAAL average | 14.78 / 13.59 | 13.61 / 14.84 | +0.04 |
| Long-form Earnings21 | 8.25 / 8.25 | 8.17 / 8.20 | −0.07 |
| Long-form Earnings22 | 12.36 / 12.55 | 12.81 / 12.74 | +0.32 |

CORAAL's mean moves by +0.04 points, against repeat differences of 1.19 (padded) and 1.23 (packed); Earnings21 moves
by −0.07. AMI-IHM's +1.73 comes from one of its 16 meetings (EN2002c): in both packed runs, about 800 words of one
speaker go to an extra speaker tag. The words are unchanged (WER without speaker tags moves by +0.07), so this is
speaker attribution, not recognition; an earlier H100 comparison with different weights moved the same meeting the
other way. Earnings22's +0.32 comes from nine recordings where generation loops or reaches the token limit, mostly as
deleted text; the other 116 recordings improve slightly. On H100 (one run per arm, an earlier checkpoint and chat
template), AMI-IHM and Earnings22 improved instead, while Mixer6 and three CORAAL locations got worse. A crossover on
SOT (four more runs per arm, with GPUs swapped and request order shuffled) reproduced the EN2002c split in all six
packed runs (about 915 words under the extra tag) and in none of the six padded runs (about 115 words), so it follows
the tower, not the GPU or the batch order. The other 15 AMI-IHM meetings are equal or slightly better with the packed
tower in every pair. Earnings22 was not part of the crossover. TED-LIUM (11 recordings) varies too much between runs
of the same code to compare (up to 5.9 points).

**Batch dependence (BF16).** A clip's tower output can depend on the other clips in its batch, before and after this
PR: rounding changes with the batch, the speaker encoder's probabilities move, and the thresholded speaker features
flip on some frames. Batched against alone:

| Tower | H100: identical clips, 64 short / 4 long | H100: flipped speaker frames, long clips (of 4,314) | RTX PRO 6000: flipped speaker frames, long clips (of 4,314) |
|---|---|---|---|
| Padded (SDPA) | 32 / 4 | 0 | 170 |
| Packed, FlashAttention | 32 / 2 | 44 | 216 |
| Packed, TORCH_SDPA forced | 32 / 4 | 0 | 316 |

On the four long clips on H100, forcing SDPA removed the additional speaker-feature variation of FlashAttention 3,
and the ASR encoder's output stayed identical with FlashAttention 3. Forcing SDPA does not make the tower
batch-invariant: on H100, half of the short clips change with the batch in all three towers (embeddings up to 0.033
relative L2 apart, no speaker flips), and on the RTX PRO 6000 all three towers flip speaker frames on three of the
four long clips. FlashAttention therefore stays the default. Forced SDPA on the RTX PRO 6000 takes 23.4, 63.8, 113.0
and 100.3 ms on the four batches of the speed table.

## Details

- **Packing.** `TransformerEncoder.pack` indexes each row's valid frames from host lengths and builds `cu_seqlens`
  with `MMEncoderAttention`'s helpers for the selected backend. Rotary embeddings use each frame's position in its
  row. Rows without valid frames are left out, and a batch without any valid frame skips the layers, because vLLM's
  SDPA wrapper cannot split an empty `cu_seqlens`. The padded positions of the output are zero. The Sortformer step
  adds its speaker-cache and FIFO context to the host lengths as to the device lengths.
- **Host lengths.** The tower already has the clip lengths on the host, so packing adds no device-to-host copy. With
  `TORCH_SDPA`, vLLM's SDPA wrapper still copies the cumulative lengths to the host once per layer
  (`vllm/v1/attention/ops/vit_attn_wrappers.py`).
- **FP8 encoder attention.** vLLM's encoder attention accepts `mm_encoder_attn_dtype='fp8'` only on the FlashInfer
  cuDNN backend and on ROCm AITER. There, the tower's attention layers would add FP8 scale buffers that no checkpoint
  has, so loading fails, and the FlashInfer path expects a different `cu_seqlens` layout. The tower therefore refuses
  the setting on every backend when it is built. The padded SDPA path ignored it.
- **Docs.** The model's note in `docs/models/supported_models.md` states the refusal and that the encoder attention
  backend and the other clips in a batch can change the tower's BF16 output.
- **Tradeoffs and limits.** On H100 the packed tower is slower than the padded one on 8 clips and on long clips, and
  serving throughput does not change. `MMEncoderAttention` has no per-layer backend option, so SDPA in the speaker
  encoder alone would need a model-specific override. Measured on RTX PRO 6000 and H100 only, not on ROCm or other
  GPUs.
- **Duplicate check.** No open PR mentions Nemotron-3.5-Transcribe (GitHub search, 2026-10-31).
