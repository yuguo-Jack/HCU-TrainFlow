# [Bugfix][HiSparse] Carry adopted prefix pages in the new request's row

[Upstream PR](https://github.com/vllm-project/vllm/pull/60117) · state: closed · merged: False

## Original PR description

## Purpose

Fixes #60109: HiSparse servers crash with an illegal memory access when a new request hits a prefix whose published host pages still have GPU copies.

The coordinator adopts those copies after the scheduler has already built the request's `NewRequestData`, so the adopted row went out as a `block_table_updates` entry. For a new request, model runner V2 then stages two full-row writes for the same row in one step (`add_requests`, then `update_requests`), and the staged-write kernel applies them in parallel with no ordering. A rank that kept the pre-adoption row saw null resident pages, while the scheduler reported every context page resident. The resident-prefill shortcut then sent the prefill rows through the decode residency resolver, whose host union overflowed `max_union_rows` and faulted.

The fix puts the adopted row in the new request's `block_ids`; `block_table_updates` stays for running requests. HiSparse-only (`hisparse/connector.py`).

Note: MRv2's staged block-table writer doesn't order overlapping writes to the same row. This PR stops HiSparse from producing them; changing that in core is a separate discussion.

## Reproduction on main

GLM-5.3-NVFP4 on B200, either TP8 or TP4 (`host_pool_gib` 128 or 64):

```bash
vllm serve RedHatAI/GLM-5.3-NVFP4 -tp 4 --kv-cache-dtype fp8 --block-size 64 \
  --max-model-len 22528 --max-num-seqs 256 \
  --kv-transfer-config '{"kv_connector":"HiSparseConnector","kv_role":"kv_both","kv_connector_extra_config":{"host_pool_gib":64}}'
vllm bench serve --model RedHatAI/GLM-5.3-NVFP4 --dataset-name random --random-input-len 20480 \
  --random-output-len 1024 --ignore-eos --seed 42 --max-concurrency 1 --num-prompts 4
vllm bench serve --model RedHatAI/GLM-5.3-NVFP4 --dataset-name random --random-input-len 20480 \
  --random-output-len 1024 --ignore-eos --seed 42 --max-concurrency 4 --num-prompts 8
```

Because of the fixed seed, the second wave repeats the first wave's prompts, so its requests hit the published prefix and adopt the GPU copies on admission.

| | c=1 (4 prompts) | c=4 (8 prompts) |
|---|---|---|
| main `528772a4bf` (TP4 3/3 runs, TP8 4/4 runs) | 4/4 | 0/8: illegal memory access, engine dead |
| this PR (TP4, 3 servers × 3 c=4 waves) | 4/4 | 8/8 in every wave, no CUDA errors (9/9 waves) |

## Performance

No change expected: one dict pop per newly scheduled request per step, and one fewer row write on the GPU for adopted requests.
