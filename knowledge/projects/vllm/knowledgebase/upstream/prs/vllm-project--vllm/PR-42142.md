# Fix: Prevent RuntimeError in DeepGEMM warmup by deferring alignment check for non-FP8 modules

[Upstream PR](https://github.com/vllm-project/vllm/pull/42142) · state: open · merged: False

## Original PR description

**Description:**
In `vllm/model_executor/warmup/deep_gemm_warmup.py`, the function `_fp8_linear_may_use_deep_gemm()` was unconditionally calling `get_mk_alignment_for_contiguous_layout()` before verifying if the module was actually an FP8 module. 

Since `get_mk_alignment_for_contiguous_layout()` throws a `RuntimeError` when the DeepGEMM backend is missing or outdated (e.g., on non-Hopper hardware), this caused vLLM to instantly crash during model warmup for **all** models (including standard `bfloat16` models like Qwen2.5-VL), even though they never intended to use DeepGEMM.

**Fix:**
Moved the `block_size = get_mk_alignment_for_contiguous_layout()[0]` execution strictly below the module type-checking guard. This ensures the alignment check (and potential `RuntimeError`) is only ever evaluated if the module is definitively confirmed to be an FP8 linear module.

The addition of `getattr(module, "quant_method", None) is not None` is redundant because the preceding `isinstance(module, LinearBase)` check already guarantees that the `quant_method` attribute exists on the module.

More importantly, to fully resolve the risk of a `RuntimeError` on unsupported hardware (e.g., NVIDIA GPUs older than Hopper) for FP8 models, the guard should explicitly verify if DeepGEMM is enabled and supported for this specific module. By checking `getattr(module.quant_method, "use_deep_gemm", False)`, you ensure that `get_mk_alignment_for_contiguous_layout()` is only invoked when the DeepGEMM backend is actually available and intended for use. This makes the fix robust for FP8 models running on non-Hopper hardware.

```suggestion
        and isinstance(module.quant_method, Fp8LinearMethod)
        and getattr(module.quant_method, "use_deep_gemm", False)
```
