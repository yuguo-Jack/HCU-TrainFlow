# [hw-agnostic] Linear layers for the Transformers backend

[Upstream PR](https://github.com/vllm-project/vllm/pull/65454) · state: open · merged: False

## Original PR description

## Overview

Adds hw-agnostic linear layers, and has the Transformers backend build every linear layer through `hw_agnostic.resolve`, the opt-in mechanism from #60218. With `VLLM_USE_HW_AGNOSTIC=1`, the attention and MLP GEMMs of a dense model now run on hw-agnostic layers.

Supersedes https://github.com/bohnstingl/vllm/pull/6, which predates #60218. That version stacked on the embedding PR, used per-layer getter functions instead of `resolve`, and also contained a portable FP8 kernel subtree that no model could reach; see Details.

## Claims

- `vllm.model_executor.hw_agnostic.layers.linear` provides `ReplicatedLinear`, `ColumnParallelLinear`, `RowParallelLinear`, `MergedColumnParallelLinear`, `QKVParallelLinear` and the rest of the in-tree module. It is a copy of the current in-tree `layers/linear.py` without its hardware-specific GEMM selection.
- Every site where the backend builds a linear layer goes through `hw_agnostic.resolve`: `replace_linear_class` and the QKV, packed-QKV, merged-column and MLA fusers. Out-of-tree plugins therefore override these layers the way #60218 documents.
- Accuracy is unchanged: Granite-4.2-8B gsm8k is within one stderr of the in-tree baseline, and a TP=2 run gives bit-identical greedy logprobs.
- LoRA together with `VLLM_USE_HW_AGNOSTIC=1` is rejected with a clear error at startup. Previously an adapter on the linear layers failed to load with `expected target modules in {'embed_tokens'}`.
- No behavior change when `VLLM_USE_HW_AGNOSTIC` is unset: `resolve` returns the in-tree classes.

## Details

- **Size.** About 1850 non-test lines are added, but about 1810 of them are the copy of `linear.py`. The new logic is the 24-line `utils.py` (also covered in https://github.com/vllm-project/vllm/pull/52355), the 7-line LoRA check and about 16 lines of `resolve` calls.
- **A copy, not a rewrite.** `hw_agnostic/layers/linear.py` keeps the in-tree weight loaders, TP sharding and quant-method resolution verbatim, so the fusers' weight mappers and checkpoints load unchanged. It differs from `layers/linear.py` in about 35 lines, so the diff against in-tree can be reviewed directly:
  - `PluggableLayer` comes from `hw_agnostic.custom_op`, the separate registry.
  - `UnquantizedLinearMethod` dispatches through `hw_agnostic.layers.utils.dispatch_unquantized_gemm`. It drops the `linear_backend`/FlashInfer selection, the ROCm cache-aliasing padding, the XPU N-contiguous weight copy and the CUDA skinny GEMM.
  - `VLLM_BATCH_INVARIANT` is kept, as in-tree.

  The copy has to be kept in sync with in-tree `linear.py`. A follow-up could check this in CI against the list of expected differences.
- **GEMM dispatch.** The new `hw_agnostic/layers/utils.py` returns `cpu_unquantized_gemm` on CPU, whose weight prepacking removes `layer.weight`, and `torch.nn.functional.linear` everywhere else. The kernel is then chosen by the device's ATen backend, not by vLLM. Platform-specific GEMMs belong in an out-of-tree plugin that overrides the layer.
- **Resolved per construction.** Each site calls `hw_agnostic.resolve` when it builds the layer, not at import, so the class follows the worker's environment.
- **LoRA check.** LoRA finds and wraps the in-tree linear classes by type, e.g. in `get_supported_lora_modules` and the `vllm/lora/layers` wrappers, and the hw-agnostic classes don't derive from them. `LoRAConfig.verify_with_model_config` therefore rejects LoRA when `VLLM_USE_HW_AGNOSTIC` is set and the model uses the Transformers backend. The check sits next to the existing per-model LoRA checks there, and runs in the front-end process, so the message reaches the user instead of a generic engine-startup failure.
- **Test change.** `test_head_counts_come_from_the_module_not_the_model` used to patch the fuser module's `QKVParallelLinear` name; it now patches `hw_agnostic.resolve`, since that name no longer exists in the module.
- **Trade-offs.** With the variable set, the dropped GEMM selection may cost speed: the CUDA skinny GEMM and FlashInfer for small batches, and on ROCm the wvSplitK/skinny kernels and cache-aliasing padding. This has not been measured. The variable is off by default.
- **Limitations:**
  - LoRA is not supported on the hw-agnostic path and is rejected, see above.
  - Quantized checkpoints are not supported on the hw-agnostic path. Quantization configs pick their method with `isinstance(layer, LinearBase)` against the in-tree class, which the hw-agnostic layers don't derive from. A quantized model either raises "All linear layers should support quant method." or gets the wrong method. Supporting this needs a quantization design of its own.
  - The MoE router `GateLinear`, an in-tree `ReplicatedLinear` subclass, and the shared-expert gate in `fusers/moe.py` stay in-tree. They belong with the MoE port.
  - Attention, embedding, LM head and logits are not covered here. The embedding, LM head and logits are in #52355.

File: `vllm/model_executor/models/transformers/utils.py` · line 132

This helper is shared: `gemma4_mm.py`, `diffusion_gemma.py` and `embedding_gemma2.py` reach it via `recursive_replace_linear`, and `deepseek_vl2.py` calls it directly. With `VLLM_USE_HW_AGNOSTIC=1` those native models get hw-agnostic tower linears, which contradicts the `resolve` docstring and `custom_op.md`. Quantized towers fail with "All linear layers should support quant method.", and the LoRA check doesn't cover them.

Native models shouldn't depend on Transformers backend utils anyway, so can we fix that here? `recursive_replace_linear` has no backend callers, so it can move to `models/utils.py` and build `ReplicatedLinear` from `layers/linear.py` directly. `deepseek_vl2.py` can build its `ColumnParallelLinear` and `RowParallelLinear` directly (with `return_bias=False`, as this helper does). `replace_linear_class` is then backend-only and `resolve` is safe here.

While you're here, please resolve only the class for `style`: three `resolve` calls per linear also logs classes the model never builds, and the return annotation is wrong when the flag is set.
