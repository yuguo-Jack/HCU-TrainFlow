# [Bugfix][Quantization] Forward a2_scale in OCP MX MoE emulation

[Upstream PR](https://github.com/vllm-project/vllm/pull/52868) · state: open · merged: False

## Original PR description

## Purpose

`OCP_MXQuantizationEmulationTritonExperts.apply()` hardcoded `a2_scale=None` in its `super().apply(...)` call, so the checkpoint's static second-GEMM activation scale never reached the quantizer. The emulated MoE silently fake-quantized the second GEMM against a **dynamic per-tensor amax** instead of the static scale the checkpoint declares.

### Affected scheme/model

- Exactly one scheme: **Quark `w_mxfp4_a_fp8` on the `EMULATION` backend.**
- Example model: https://huggingface.co/amd/gpt-oss-120b-w-mxfp4-a-fp8

## Test Plan

### New regression test

`test_ocp_mx_emulation_forwards_a2_scale` is added to `tests/kernels/moe/test_ocp_mx_moe.py`

### End-to-end test
- `amd/gpt-oss-120b-w-mxfp4-a-fp8`
- on MI325X (gfx942), ROCm, torch 2.10.0.

```bash
# On gfx942 emulation is the auto-selected backend; --moe-backend emulation pins it.
vllm serve amd/gpt-oss-120b-w-mxfp4-a-fp8 \
  --moe-backend emulation --tensor-parallel-size 4 \
  --reasoning-parser openai_gptoss --trust-remote-code

lm_eval --model local-chat-completions \
  --model_args base_url=http://127.0.0.1:8000/v1/chat/completions,num_concurrent=64 \
  --tasks gsm8k_platinum --num_fewshot 5 \
  --gen_kwargs max_gen_toks=2048 --apply_chat_template --fewshot_as_multiturn
```
