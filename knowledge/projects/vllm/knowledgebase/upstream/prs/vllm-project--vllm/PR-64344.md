## Original PR description

# RFC: Packed KV block stride (one slot holds all groups' pages)

## Summary

vLLM prices every shared block id at `max_g(per_group_bytes)` and gives each KV
cache group its own id per position. For hybrid models whose groups share one
block index space (equal `block_size`, every group consumes a block per
position) with no sliding-window, no indexer-role cache, and no per-group
alignment, this wastes `max/mean` of the budget. Packing the stride to
`sum_g(per_group_bytes)` makes one id hold every group's page for a position,
recovering that ratio.

The MLA + indexer + fp4 class (the one with the 1.737 ratio) is NOT eligible
under the current predicate: it needs the two extensions in `inference-ytt`
(alignment handling for indexer caches, and a separate pool for sliding-window
groups). This RFC describes the base mechanism, which realizes 1.325 on a
(p, 2p) config today.

This is a **planner + view-creation** change, not a kernel rewrite. Measured
runtime concurrency ratio on a (p, 2p) 2-group config: **1.325** (bound 1.333).

## Waste (current code)

`vllm/v1/core/kv_cache_planning.py`:

- `bytes_per_block = max_g(per_group_bytes)` in `_get_kv_cache_bytes_per_block`
  (`_get_kv_cache_bytes_per_block` at line 574; the `max(...)` at lines 584-589 on `7c713621f3`).
- `interleaved_block_stride = bytes_per_block` for block-outer layouts (the
  assignment near the top of `get_kv_cache_config_from_groups`).
- Each group's tensor is a view with the **same** `block_stride` and a per-group
  `byte_offset` that accumulates inside the block (`offset=byte_offset` at
  `offset=byte_offset` at ~line 722, `byte_offset += ...` at ~line 726).

So every slot is max-width and a request spends one id per group per position.
Per-group quotas (size-classed block counts) cannot pay because the id itself is
max-priced — which is why they measure exactly 1.0x.

## Mechanism

Set, when eligible:

- `interleaved_block_stride = sum_g(per_group_bytes[g])`
- `num_blocks = B // sum_g(page_g)` (one slot per block of total page size)
- per-group `byte_offset` accumulates across groups unchanged, so group `g`'s page
  for block `i` lands at the expected offset inside slot `i`.

ids become shared across groups: slots needed = `bpr` instead of `G*bpr`,
bytes = `bpr * sum_g(page_g)`, and the ratio is exactly `max_page / mean_g(page_g)`
in the planner model (dd0).

## Exact predicate (guard)

Packing applies **only** when all groups share one block index space:

- block-outer layout (`layout.is_block_outermost`);
- every group has the same `block_size`;
- no `SlidingWindowSpec` / `ChunkedLocalAttentionSpec`;
- no `MambaSpec` with `tokens_per_state not in (1, -1)`;
- no spec with `block_stride_alignment` set;
- no indexer cache role (`cache_role` containing `INDEXER`).

If any fails, fall back to today's max-priced layout with a `logger.warning`
("Packed block stride disabled; falling back to max-priced layout"). No silent
degradation.

## Ratio identity

With `b_g` = blocks a request needs from group `g` (from the scheduler, not
layer counts), `n_g` = layers in group `g`, `page_g` = that layer's padded page,
and `T_g = n_g * page_g` (group's per-block bytes):

```
ratio = (Σ_g b_g) * max_g(T_g) / Σ_g (b_g * T_g)
```

i.e. max group total over the `b_g`-weighted mean of group totals. The weights
are load-bearing: with equal `b_g`, deepseek computes to 1.496; the real 1.737
comes from SWA reserving 64 blocks against 512 for the other groups. For qwen3 the
max is the recurrent group (42 × 16384 = 688128 > 10 × 65536), which is why
skewed layer counts do not inherit the payoff.

Verified against committed 49m architecture tables + `blocks_to_reserve` at 8k:

| config | ratio |
|---|---|
| deepseek-v4.1-style (equal layers, MLA + indexer + fp4) | **1.737** (planner 1.734, sim 1.736) — *planner only, not eligible today* (guard excludes indexer cache role and SWA; see inference-ytt) |
| gpt-oss-20b (equal page sizes per group) | 1.000 |
| Llama-3.1-8B (dense, single group) | 1.000 |
| qwen3-next-hybrid (skewed layer counts) | 1.050 (planner 1.056) |

## Worked example (hand-checkable)

Two groups, page sizes 32768 and 65536 (p, 2p), block_size 16, BLHNC layout,
B = 80 × 65536 = 5242880.

- Legacy: `bytes_per_block = 65536`, `num_blocks = 80`, bpr = 2 → concurrency 40.0.
- Packed: `bytes_per_block = 98304`, `num_blocks = 53`, bpr = 1 → concurrency 53.0.
- Ratio = 53.0 / 40.0 = **1.325** (bound `max/mean = 65536 / 49152 = 1.333`,
  integer rounding).

## Guard / fallback

- `use_packed_stride` field on `KVCacheConfig` records the decision.
- Ineligible configs log `logger.warning` and use max-priced layout.
- All groups' `block_size` equality is asserted in code, not assumed.

## Test plan

1. Stride test: group `g`'s page for block `i` lands at the expected offset inside
   slot `i` (static stride test; views already treat `block_stride` as per-tensor data).
2. Invariant: `sum of allocation bytes == num_blocks * sum_g(page_g) <= B`.
3. Concurrency: `kv_cache_max_concurrency` packed vs unpatched planner == the config's
   own planner ratio (1.333 ± rounding for (p, 2p); 1.0 for equal pages).
4. Greedy-token equality: same greedy tokens as the unpacked layout on a small model,
   2 prompts × ≤64 tokens (proves kernel views still see the right bytes). Not run in
   this lab's CPU job; requires a GPU (`torch.cuda.device_count()`). The static stride
   test is the CPU-side substitute.

## Scope (honest)

- Does nothing for dense single-group models (ratio 1.0).
- Does nothing for sliding-window / Mamba hybrid groups (excluded by guard).
- Pays only for equal-layer-count, unequal-padded-page hybrids: the DeepSeek-V4 /
  Latent-MLA family (MLA + indexer + fp4 caches).
- Requires block-outer layout.

## What this does not cover (yet)

- **Indexer cache-role packing** (`block_stride_alignment` on
  `SparseCacheRole.INDEXER`) and **SWA split pool**: handled in
  `inference-ytt` (alignment + separate SWA pool; packed SWA-split ratio
  1.736 vs pack-everything 1.169, alignment overhead 0.03%). The RFC above
  describes the base (p, 2p) mechanism only.
- End-to-end greedy-token equality (GPU required) — still open.
- ~~Virtual-block-splitting cost (utils.py:668)~~ — **not applicable**: for block-outermost
  layouts `block_stride` already exceeds `layer_stride` before packing (it is the max
  group's bytes, not one layer's page), so the fallback to `kv_manager_block_size` is the
  status quo, not a consequence of this change.

### Evidence (four pieces)

1. **1.325x measured runtime** (inference-8qn): packed 53.0 vs legacy 40.0
   concurrency on a (p, 2p) 2-group config; bound 1.333. Source: vllm-runtime.
2. **1.7366x planner on the V4.1-shaped config = 0.9998 of ideal** (inference-ytt):
   packed SWA-split 233.5 MB/req → 131.6 concurrent vs legacy 75.8;
   pack-everything 1.1686. Source: vllm-planner (49m tables).
3. **Fallback-path determinism on a 5090** (inference-0vs): Qwen3-0.6B is a
   dense single-group model, so packed_eligible=False and both arms used the
   max-priced fallback. The run establishes fallback determinism (byte-identical
   greedy tokens, 64 tok, 2 prompts, batch 1 and 4), not packed addressing.
   Packing correctness rests on the static stride test + 8qn harness.
   Source: vllm-runtime (5090).
4. **Split-cost not applicable** (inference-r09): virtual-block splitting is
   effectively unavailable in packed mode because block_stride (sum of pages)
   differs from the dense page size, which makes the ratio>1 split path raise in
   create_kv_cache_views. The measured throughput (218.6 vs 225.8 tok/s, ~3%
   noise) is the real evidence; no regression. Source: vllm-runtime (5090).

### Who benefits today (inference-ey7)

Config-only engine-planner sweep over 8 hybrid candidates (no GPU, no weights):
padded (unified) pages are equal by construction for all 6 resolved models
(engine pads smaller pages to the max), so ratio = 1.0 by construction; verdict
null. 5 of 6 have unequal RAW pages (e.g. Nemotron-H: 4,255,744 mamba vs
65,536 attention raw, padded to 4,255,744) but packing sums pages (worse, not
better), so no shipped hybrid reaches ratio >= 1.05. 2 candidates unresolved
(Qwen3-Next-80B, Kimi-Linear-48B require CUDA for model init). Nemotron-H
calibration: 7 groups x 4,255,744 (engine 4,259,840; 4,096 B platform
alignment). tiny-granite: 2 groups x 2,147,840 (engine 2,148,352; 512 B).
The actual gain is a runtime block-sharing effect, not a bytes_per_block
difference. The 1.325 and 1.7366 headline numbers are unchanged.

### Shipped beneficiary: DeepSeek-V3.2 (DSA) (inference-azo, inference-55e)

DeepSeek-V3.2 is a shipped frontier model whose DSA layout has two cache groups
that cannot be page-equal: the MLA latent (kv_lora_rank 512 + qk_rope_head_dim 64
= 576 B/token at fp8; page 10,496 B at block_size 16) and the sparse indexer keys
(index_head_dim 128 = 132 B/token incl. scale; page 2,112 B). Legacy prices both
ids at the max, so per token 1312 B vs 788 B packed = 1.665x more in-flight
requests at 30 GiB / 8k (2997 -> 4990). block_stride_alignment == 1 on both
groups, so no alignment padding is needed.

Caveats:
- hisparse opt-out: when attention_config.hisparse_config is set, the indexer gets
  its own host/device pool and the waste disappears; the win is on the default
  path only.
- DeepGEMM block-major risk: the indexer read path is stride-aware
  (sparse_attn_indexer.kv_cache_as_quant_view uses kv_cache.stride(0);
  flat_kv_row_view handles interleaved rows), so the packed stride is compatible
  in principle. MLA is routed to Triton MLA on sm_120 (triton_mla.py:140 declares
  sm_120 support; FlashMLA/FlashInfer MLA/FlashAttn MLA are sm_90/sm_100-only).
  Our runtime attempt on this box was blocked by a build mismatch
  (concat_and_cache_mla compiled-extension arg count), which is an infra/build-
  configuration issue, not a capability wall. A packed DSA run on hardware with a
  working MLA stack (build fixed) remains the outstanding check.
- Shipped mamba hybrids are 1.0x by construction (inference-ey7, inference-206),
  so this PR cannot regress them.

### If this lands: interaction with per-group block counts

KVCacheConfig.num_blocks becomes the shared id count for the packed slot.
Per-group block counts (num_blocks_per_group) are removed by this patch;
consumers already take per-tensor block_stride. No kernel rewrite needed.
