# [Bugfix][Rust Frontend] Composite transparent images over white like Python

[Upstream PR](https://github.com/vllm-project/vllm/pull/63912) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

On the Rust frontend, an image with transparent pixels reaches the vision encoder with those pixels in their stored colour, which is usually black. The Python frontend composites them over white first, so a black-on-transparent screenshot or logo that Python reads correctly comes through Rust as an all-black image.

## Claims

- Request images are decoded with `TransparencyPolicy::CompositeOverWhite`, matching Python's image loader (`convert_image_mode` composites any image with an alpha channel or a `transparency` entry over `ImageMediaIO`'s `rgba_background_color`, white by default).
- An image processor that handles the alpha channel itself (`VisionPreProcessor::keeps_alpha`, today Kimi-K3) still gets the image as decoded, as Python's K3 renderer keeps the alpha channel (`image_mode: None`).
- The decoded pixels of opaque images, and video frames, are unchanged.

## Validation

Qwen/Qwen3-VL-2B-Instruct on one RTX 6000 Ada, main 50a184f43. Each image is black "HELLO 42" text, 448x160, on a transparent background whose stored colour is black unless noted, asked "What text is written in the image? Answer with the text only." (greedy):

| Image | Python | Rust, main | Rust, this PR |
|---|---|---|---|
| RGB on white (control) | hello42 | hello42 | hello42 |
| RGBA | hello42 | 100% | hello42 |
| RGBA, transparent pixels stored as white | hello42 | HELLO 42 | hello42 |
| LA | hello42 | 100% | hello42 |
| Palette with `tRNS` | HELLO 42 | 100% | HELLO 42 |
| WebP with alpha | hello42 | 100% | hello42 |
| CMYK JPEG, 16-bit grey PNG (opaque) | Hello42, HELLO 42 | same | same |

Asked "What text is in each image?" about the control image and the RGBA one together, main answers "The first image contains the text "HELLO 42". The second image is completely black and does not contain any text." and this PR answers "The text in each image is "HELLO 42".", as Python does. Prompt token counts are equal in every case. Four videos (30 fps 10 s, 24 fps 20 s, 3 frames, 2 fps 8 s) give the same prompt tokens and answers on all three.

The binaries were built from 50a184f43 without and with the first version of this change (before the Kimi-K3 exception, which does not touch Qwen3-VL) and selected with `VLLM_RUST_FRONTEND_PATH`; the image files are generated with Pillow and can be attached.

Tests:

- `transparent_pixels_reach_the_encoder_as_white` (`vllm-chat`): on Qwen3-VL, a fully transparent image gives the same encoder input as an opaque white one and a different one from an opaque black one. It fails on main.
- `image_transparency_follows_the_processor` (`vllm-chat`): images are decoded over white for Qwen3-VL and as decoded for Kimi-K3. It fails if every image is composited.
- `cargo fmt --all -- --check` and `cargo clippy --workspace --all-targets --all-features --locked -- -D warnings` pass; `cargo test -p vllm-chat -p vllm-server --lib` passes, apart from `audio_pipeline_attributes_stage_timings_to_request`, which also fails on main when it shares a process with the other `vllm-chat` tests and passes on its own.

## Details

`llm-multimodal` decodes images under a per-tracker `TransparencyPolicy` and leaves it to the caller to choose the one its engine's Python loader uses. The default is `KeepAlpha`, which hands the processor the image as decoded. The Qwen-VL processors, and others built on `rgb_bytes`, then call `to_rgb8()`, which drops the alpha channel. vLLM's Rust frontend never set a policy, so it got that default. This sets the policy on the tracker in `MultimodalModelInfo::fetch_media`, the one place request images are decoded (chat completions, `/tokenize`, `/inference/v1/generate` and gRPC media all go through it); preprocessed features are not decoded and are not affected. The crate documents that a frame for a `keeps_alpha` processor is decoded under `KeepAlpha` whatever the engine's rule, hence the exception.

The crate folds any policy other than `KeepAlpha` into each image's hash (`hash_image_with_transparency`), so every image's `mm_hash` changes once with this change, opaque ones included (Kimi-K3 images keep theirs). That only matters to caches that outlive the process.

One difference from Python remains, in the crate: for a truecolour PNG with a `tRNS` colour key, `CompositeOverWhite` keeps the stored colour (`apply_transparency` in `llm-multimodal`'s `media.rs` assumes the reference loader does), while vLLM's `convert_image_mode` turns the keyed colour transparent and composites it (since #61986), so a keyed black pixel becomes white (checked with Pillow 12.2). That is a change for the crate, not for this frontend.

No open or closed PR or issue covers this; I searched for transparency, alpha and RGBA in Rust frontend issues and PRs.
