# [Perf] Avoid quadratic output text copies in the incremental detokenizer

[Upstream PR](https://github.com/vllm-project/vllm/pull/62262) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

`BaseIncrementalDetokenizer.update` does `self.output_text += piece` per token. CPython can only append to a string in place when nothing else references it; here the attribute does, so every token copies the whole output text and per-step frontend CPU grows linearly with output length (quadratic per request). This appends to a local after dropping the attribute's reference, so the string is resized in place — a ~10-line change. Same goal as the draft #36023, whose author [doesn't plan to finish it](https://github.com/vllm-project/vllm/pull/36023#issuecomment-6246472478); the Rust frontend avoids the problem, but it is opt-in (`VLLM_USE_RUST_FRONTEND=0` by default).

## Claims

- `OutputProcessor.process_outputs` per-step cost no longer grows with output length: 2.88 → 0.38 ms/step at 128 requests × 64k generated tokens on macOS; the copy being removed costs ~3× less on Linux/glibc, so expect a smaller but still length-independent gain there (see below).
- No change for short outputs, and output text / deltas / stop strings / `include_stop_str_in_output` / `min_tokens` are byte-for-byte identical.

## Validation

**`OutputProcessor` benchmark** (real `OutputProcessor`, Qwen3-0.6B tokenizer, 128 requests, DELTA output with stop strings, 1 token/step, 500 timed steps after `warm` tokens already generated; macOS / Apple M-series, Python 3.12, single run each):

| tokens already generated | main (ms/step) | this PR (ms/step) |
|---|---|---|
| 0 | 0.435 | 0.434 |
| 32k | 2.06 | 0.39 |
| 64k | 2.88 | 0.38 |

**Append cost alone, Linux vs macOS** (synthetic: 128 interleaved strings, one 4-char piece per string per step with interleaved allocations; ms/step):

| tokens already generated | Linux aarch64, glibc 2.39, Py 3.12: main → PR | macOS, Py 3.12: main → PR |
|---|---|---|
| 1k | 0.019 → 0.007 | 0.022 → 0.008 |
| 8k | 0.084 → 0.009 | 0.097 → 0.009 |
| 32k | 0.310 → 0.008 | 0.695 → 0.009 |
| 64k | 0.622 → 0.010 | 1.861 → 0.010 |

On Linux the result was the same after first raising glibc's dynamic mmap threshold (allocating and freeing 30 MB blocks), i.e. with the strings on the heap as in a long-running server. The in-place append also holds on Python 3.10, 3.11, 3.13 and 3.14 (same synthetic, macOS).

**Correctness**
- Byte-equivalence matrix against main on the benchmark driver (hash of all emitted text, finish/stop reasons, token counts): DELTA / CUMULATIVE / FINAL_ONLY × `include_stop_str_in_output` × `min_tokens` 0/300 × 1 or 7 tokens per step, with stop strings that fire → 24/24 identical.
- `pytest tests/detokenizer tests/v1/engine/test_output_processor.py tests/v1/engine/test_fast_incdec_prefix_err.py` → 103 passed; the remaining 3 failures + 1 error need a running engine / gated meta-llama repo and fail identically on main on this machine. The new `test_decode_error_keeps_output_text` checks that an exception from `decode_next` keeps the text decoded so far (passes on main, fails without the `finally`).
- `pre-commit run` on the changed file passes.

**Not included:** an end-to-end serving benchmark — I have no GPU. The saving scales with the total output text in flight across requests (per step, ~0.3–0.4 ns per in-flight token on macOS and ~0.07 ns on Linux in the numbers above), so it is visible when one frontend streams many long outputs at once (e.g. long reasoning traces, or DP with a single API server), not on short-output workloads. The work runs on the AsyncLLM frontend's event loop, not in EngineCore, so it shows up as streaming latency/HTTP responsiveness rather than GPU step time. Happy to add `vllm bench serve` numbers if someone can run them.

## Details

- Root cause: `self.output_text += piece` loads the attribute (refcount ≥ 2), so `PyUnicode_Append` must allocate a new string and copy. With the attribute temporarily set to `""`, the local is the only reference and CPython's in-place unicode append resizes it via `realloc`, which grows the block in place in the common case.
- The attribute is restored in a `finally`, so an exception from `decode_next` keeps the text decoded so far, as on main; this matters for the offline `LLM`, which keeps the request alive after a failed step (thanks @liulanze). `try` is zero-cost on Python ≥ 3.11 and the benchmark is unchanged (0.41 / 0.36 / 0.37 ms/step at 0 / 32k / 64k).
- If something else holds a reference to the text (non-delta output kinds return it to the caller), the next append copies once, exactly as today — never worse than main.
- vs #36023: that PR keeps a list of per-token pieces, re-joins on every CUMULATIVE step and predates the current `token_offsets`/`bisect` stop truncation; this change leaves that logic untouched. Credit to @amirkl94 for identifying the hotspot.
- The same pattern exists in `responses/context.py` (`SimpleContext.append_output`) and `responses/streaming_events.py`; left for a follow-up. The chat-completions one is handled by #61379.
- #55483 also edits `update()`; the changes are independent but one of us will need a small rebase.
