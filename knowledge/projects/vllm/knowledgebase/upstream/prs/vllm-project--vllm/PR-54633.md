# [Bugfix][MiniCPM-V] Route video_embeds to the shared vision parser

[Upstream PR](https://github.com/vllm-project/vllm/pull/54633) · state: closed · merged: True

## Original PR description

## Purpose

MiniCPM-V routes video inputs through the image vision parser, stripping the `video_`
prefix off its multi-modal kwargs on the way:

```python
self._parse_and_validate_vision_input(
    "videos", **{k.removeprefix("video_"): v for k, v in kwargs.items()}
)
```

That works for `video_pixel_values` and `video_tgt_sizes`. It does not work for
`video_embeds`, because the image field is named `image_embeds`, not `embeds`. The
parser pops `image_embeds`, never sees the renamed key, and behaves as if no video
were passed.

`video_embeds` is a declared multi-modal field on both models, in
`_minicpmv_field_config` and `_minicpmv4_6_field_config`. It can be passed offline
through `multi_modal_data`, and #54242 added the chat frontend path for
`video_embeds` content parts, both under `--enable-mm-embeds`. Users hit this in
two ways. On 2.6 the parser returns `None`, which is stored as
`modalities["videos"]` and then subscripted by `_process_vision_input`, raising
`TypeError: 'NoneType' object is not subscriptable`. On 4.6 the guard reads
`video_kwargs.get("image_embeds")`, which is absent after the rename, so the video
branch is skipped and the video is dropped with no error at all.

Other VLMs give video its own `_parse_and_validate_video_input` that pops
`video_embeds` by name, Qwen2.5-VL and GLM-4.1V among them. MiniCPM-V shares the
image parser on purpose, since its videos run the same vision pipeline, so this
keeps that structure and replaces the prefix strip with an explicit video-to-image
kwarg mapping used by both models.

Restricting the mapping to video keys also stops image kwargs reaching the video
parser. The old comprehension rewrote every kwarg, so an `image_embeds` sent in the
same request was passed through to the video call untouched.

### Duplicate-work check

No open PR or issue covers this. Searched open and closed PRs for `minicpm`,
`minicpm video embeds` and `video_embeds`, and issues for `minicpm video_embeds`.
The nearest open PR, #43760, moves resampler tensors between devices and does not
touch input routing.

InternVL looks related, since its `_parse_and_validate_video_input` also pops
`image_embeds`, but it is left out here: `video_embeds` is not in its
`_get_video_fields_config`, so supporting it is a feature rather than a fix.

Verified on head 0a533a4 (diff vs PR base f5c3cc2, plus direct logic probes).

**Bug confirmed in both models:**
- 2.6 (minicpmv.py:1279 on base): `{k.removeprefix("video_"): v for k, v in kwargs.items()}` turns `video_embeds` into `embeds` — but `_parse_and_validate_vision_input` pops `image_embeds`/`pixel_values` (minicpmv.py:1252-1253), so `embeds` is invisible -> parser returns None -> TypeError in `_process_vision_input`. Confirmed by reading the parser body.
- 4.6: same rename bug; the guard reads `image_embeds` from the renamed kwargs, video branch never fires -> video silently dropped (minicpmv4_6.py:1069-1077 pattern).
- **Bonus defect fixed:** the old 2.6 code passed ALL kwargs through, so a genuine `image_embeds` (image input) also leaked into the video parser unmodified (removeprefix is a no-op there). The new `_image_kwargs_from_video` filters to the 4 video keys only - both leaks closed.

**Fix verified by probe:** `_VIDEO_TO_IMAGE_KWARGS` maps video_embeds->image_embeds, video_pixel_values->pixel_values, video_tgt_sizes->tgt_sizes, video_image_sizes->image_sizes; non-video keys (image_embeds, embeds, pixel_values) are filtered out. New helper is shared by 2.6 and 4.6 (single source of truth), 4.6's inline duplicate removed.

**Tests:** new file uses `object.__new__` + lambda stubs - no model download, no GPU, runs as pure unit tests. Structurally: test_video_embeds_reach_the_vision_parser asserts type=="image_embeds" + tensor equality (would fail on base: parser gets `embeds` -> None); test_image_and_video_embeds_stay_in_their_own_modality pins the leak fix; test_video_embeds_are_embedded_by_4_6 covers the 4.6 path.

**Env note (not a PR issue):** could not execute the test file locally - the sandbox's torch 2.13.0+cpu has no matching torchvision binary (operator torchvision::nms ABI mismatch at import, fails for ANY model module, identical on base). Logic fully verified by code reading + mapping probe instead. `pytestmark = skip_global_cleanup` matches repo convention.

Clean minimal fix, correct both halves, good unit coverage.
