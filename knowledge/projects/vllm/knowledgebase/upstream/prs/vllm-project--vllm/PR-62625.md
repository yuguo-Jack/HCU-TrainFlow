# [Spec Decode][Qwen GDN] Keep RecoverSSM replay records out of the Mamba page

[Upstream PR](https://github.com/vllm-project/vllm/pull/62625) · state: open · merged: False

## Original PR description



## Overview

Second follow-up to #58863, as discussed there (stacked on #61309, which is stacked on #58863; only the last commit is new).

The replay record only lives from a step's verify to the same step's commit, but #58863 keeps it in every Mamba page. That makes the page bigger, and on hybrid models the attention block grows with it (Qwen3.5-4B, K=5: 288 → 352 tokens), so prefix hits get rounded down to a bigger block. This PR moves the records into a per-layer buffer with one row per request slot, so the page and block are the stock size again.

## Claims

- With `--use-replayssm`, the Mamba page and attention block are the stock size again (Qwen3.5-4B, K=5: 352 → 288 tokens).
- Shared-prefix reuse matches stock kernels exactly: per-request hits are identical to stock on a 40-pair probe. With the record in the page (#61309), the same probe reuses 36 fewer tokens per request on average (hit rate 0.717 → 0.700).
- **Same arithmetic as the in-page version:** the kernel test checks that moving the record leaves verify and commit bit-identical.
- **Greedy outputs end to end:** they still differ from #61309 at near-ties. The attention block size changes, and with it the attention kernel's float order. Every first divergence, against stock and against #61309, is at a top1 − top2 gap ≤ 0.125.
- Throughput, acceptance and GSM8K are unchanged versus #61309 (within noise), and the KV cache holds slightly more tokens.

## Change

<details>
<summary>Record buffer, indexing, memory</summary>

- **Record buffer.** `QwenGatedDeltaNetAttention` registers `recoverssm_replay` `[max_num_seqs, HV, K+1, V+K+1]` fp32 as a non-persistent buffer. It is allocated at model init, so the memory profiler accounts for it before sizing the KV cache.
  - The layer and the model-level Mamba state specs (Qwen3.5, Qwen3-Next, Qwen4Exp) no longer add the record; they are the stock GDN states again.
- **Indexing by request slot.** `gdn_recoverssm_verify` and `GDNRecoverSSMCommitContext.commit` take `record_indices`, the buffer row for each window. The GDN RecoverSSM builder fills it from `CommonAttentionMetadata.req_idx` (the request's persistent slot, `idx_mapping`) for the spec rows.
  - The indices are staged in a persistent `CpuGpuBuffer`, so FULL CUDA graphs replay the verify with the current step's rows. Graph-padding windows get row 0; the kernels skip them because their state index is null.
  - Two requests never share a record row. In my prototype the row was the spec-batch position instead, which would not be safe once several batches are in flight (#59983).
- `record_indices=None` keeps the old addressing by state index, so the kernel API still accepts in-page records. The existing kernel tests use it unchanged.
- **Memory.** The buffer is `max_num_seqs × HV × (K+1) × (V+K+1) × 4` bytes per GDN layer. For Qwen3.5-4B (24 GDN layers, TP 1) at K=5 and `--max-num-seqs 100`, that is 452 MiB. The in-page record grows every Mamba block instead, so the KV cache still ends up slightly larger than with #61309 (815,377 vs. 813,301 tokens).

</details>

<details>
<summary>New / changed tests</summary>

- **Out-of-page vs. in-page records:** `test_records_outside_the_page_match_in_page_records` checks non-contiguous spec rows, with and without align mode. It gives the verify a separate NaN-filled record buffer and permuted record rows. Verify output and committed states must be bit-identical to in-page records, and a NaN would show any read of an unwritten row.
- **Index staging:** `test_builder_stages_request_slots_as_record_indices` checks that the builder stages `req_idx` of the spec rows and pads with row 0.
- **Stock Mamba page:** `test_qwen_gdn_recoverssm_keeps_the_stock_mamba_page` replaces #61309's "state carries the replay record" test. With RecoverSSM on, the model-level Mamba state equals the stock one for Qwen3.5, Qwen3-Next and Qwen4Exp at TP 1/2 and K 0/3/5.

</details>

`ruff` and `mypy` report no new findings.

**End-to-end:** `Qwen/Qwen3.5-4B` with its native MTP head, K=5, BF16, 1× L40S, MRV2. The flags are the same as in #61309: `--mamba-cache-mode align --enable-prefix-caching --prefix-match-unit 16 --mamba-backend triton --attention-backend TRITON_ATTN --max-num-seqs 100`.

**Prefix reuse.** 40 pairs share a prefix of L tokens, with L uniform in [1000, 3000] (mean 2116); see the probe below.

| | Attention block | Mean hit tokens (2nd request) | Hit rate |
|---|---|---|---|
| Stock kernels | 288 | 1540.8 | 0.717 |
| RecoverSSM, record in the page (#61309) | 352 | 1504.8 | 0.700 |
| RecoverSSM, record buffer (this PR) | **288** | **1540.8** (identical per pair to stock) | **0.717** |

<details>
<summary>Per-pair details</summary>

- **Per pair:** this PR hits more than #61309 in 25 pairs and fewer in 9. In the other 6 pairs one of the two runs had no hit at all; stock shows the same zero-hit pairs as this PR, so these are not caused by RecoverSSM.
- **Lost tokens per pair:** on the 34 pairs that hit in both runs, the mean unreused part of the shared prefix is 418 tokens for this PR and 494 for #61309. That is about 1.5 blocks in each case: one block for the MTP-dropped checkpoint plus half a block of rounding.
- **Larger blocks:** the gap grows with the block size. On an FP8 Qwen3.5-4B finetune with FP8 KV, the record grew the block from 576 to 656. On a workload sharing a ~1.9k-token system prompt, every request then reused 1,312 instead of 1,728 tokens.

</details>
