# [ROCm][Perf] Support Hy4 clamped SwiGLU in MXFP8 MoE backend

[Upstream PR](https://github.com/vllm-project/vllm/pull/58056) · state: closed · merged: False

## Original PR description

## Motivation

Hy4's MoE quietly falls back to Triton even with `VLLM_ROCM_USE_AITER=1`. Booting it on an MI355X shows the same thing as 57960 reports:

```text
INFO [mxfp8.py:137] Using 'TRITON_MXFP8' MxFp8 MoE backend.
```

We already ship `AiterMxfp8Experts` for this exact case, but `is_supported_config` turns Hy4 away. It insists on SwiGLU-OAI
(`alpha=1.702`, `beta=1.0`), and Hy4 uses a clamped SwiGLU:

```text
gate = clamp(gate, max=limit)
up   = clamp(up, -limit, limit)
out  = silu(gate) * up          # Hy4 ships swiglu_limit=10.0
```

## The Fix

 AITER already does Hy4's activation, it just calls it something else:

| AITER `ActivationType` | what it computes | who uses it |
|---|---|---|
| `Swiglu` | `gate*sigmoid(1.702*gate)*(up+1)` | gpt-oss, MiniMax-M3 |
| `Silu` + `swiglu_limit` | `silu(clamp(gate)) * clamp(up)` | Hy4 |

Hy4 leaves `swiglu_alpha`/`swiglu_beta` unset because `HYV4MoEFused` only passes `swiglu_limit`, and unset means the `SiluAndMulWithClamp` defaults (1.0 / 0.0). So the change is:

- swap the two hardcoded checks for one   `activation -> (alpha, beta, requires_limit)` table
- accept `MoEActivation.SILU` too, and send the `ActivationType` that matches
- still reject a SwiGLU-OAI config that never set alpha/beta, instead of quietly treating it as clamped SiLU
- reject clamped SiLU with no limit, rather than dropping the clamp

## Testing

Same Hy4 boot before and after (`--load-format dummy`, 4 layers, gfx950):

```text
before: Using 'TRITON_MXFP8' MxFp8 MoE backend.
after:  Using 'AITER_MXFP8' MxFp8 MoE backend.
```

The patched server starts up fine and serves requests (`200 OK`).

For numerics I ran `aiter.fused_moe` through our own weight prep and compared against dequantized BF16, with the clamp actually firing:

| what we send | vs Hy4 ref | vs OAI ref |
|---|---|---|
| `Silu` + limit (after) | **5.3%** | 20.9% |
| `Swiglu` (before) | 19.7% | **4.4%** |

Each one matches its own reference. The ~5% floor is just MXFP8 quantization noise and shows up in both, so what matters is which side each row lands on.

Unit tests: `18 passed` in `test_mxfp8_aiter_backend_selection.py` (9 that were already there, plus 9 new ones covering Hy4, the rejections, and both activation/parameter mismatches).

## End-to-end validation take 2 — BF16 KV cache

The previous comparison use fp8 kv cache, which I discovered has some problems see the issue I just filed https://github.com/vllm-project/vllm/issues/58487. I redid the e2e benchmark, this time with accuracy too. I used GSM8k here because it's fast compared to other evals and we just need to show that the accuracy remains the same before and after the changes.
