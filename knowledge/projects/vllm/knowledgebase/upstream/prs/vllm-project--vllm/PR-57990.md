# [Bugfix] [Frontend] Preserve prompt_logprobs in /v1/completions/derender

[Upstream PR](https://github.com/vllm-project/vllm/pull/57990) · state: open · merged: False

## Original PR description

Fixes #57929

**What/Why:** Non-streaming `/v1/completions/derender` returned `prompt_logprobs: null` — `OnlineDerenderer._derender_completion` built each choice without the field, discarding data the engine had already computed. The chat derender path and direct `/v1/completions` already pass it through.

**How:** One line in `vllm/renderers/online_derenderer.py` — attach `gen.prompt_logprobs` to every choice of that response (per-prompt semantics identical to the direct endpoint), plus regression test 

**Updated:** Chat fills `prompt_logprobs` inside `_derender_chat`, in the same background call that decodes the text 

`test_derender_completion_prompt_logprobs_passthrough` in `tests/entrypoints/scale_out/derender/test_derender.py` (fails on unfixed code, passes after).


**Tests:** `pytest tests/entrypoints/scale_out/derender/test_derender.py` → 37/37 passed locally; pre-commit clean; GPU parity suite left to CI. Not model-affecting (frontend response assembly only).

🟡 (optional) Derender requests whose prompt_logprobs contain a token id with no vocab entry, or a negative one, now fail with a 500; the base branch passed them through. `_resolve_prompt_logprobs` hands every key with `decoded_token=None` to `convert_ids_list_to_tokens`, and nothing validates those keys. Fix: before decoding, check every prompt_logprobs key the same way `choice.token_ids` is checked (non-negative, inside the vocab), returning a 400. Otherwise map an id with no vocab entry to "", as `resolve_token_id_placeholder` already does.

<details>
<summary>Why this was flagged</summary>

A client POSTs to /v1/chat/completions/derender or /v1/completions/derender. Its generate_response.prompt_logprobs has a dict key that is out of vocab or negative, with decoded_token null. protocol.py:443 types the field as `list[dict[int, Logprob] | None]` with no key validation. At online_derenderer.py:1025, `convert_ids_list_to_tokens` calls `tokenizer.convert_ids_to_tokens`, which returns None for unknown ids. `_restore_leading_spaces` then runs `for ch in None` and raises TypeError on SentencePiece-marker tokenizers. HF fast `decode([-1])` raises OverflowError. The chat handler at serving.py:173 catches only ValueError, and the completion call at serving.py:235 has no handler at all, so the client gets a 500. On the base branch prompt_logprobs went through untouched and these requests succeeded.

**Verification:** `_resolve_prompt_logprobs` (online_derenderer.py ~1015-1025) collects every key whose `decoded_token is None` and calls `convert_ids_list_to_tokens(tokenizer, missing)`. Nothing validates those keys first. The chat path catches only `ValueError` (serving.py:172). Before this change, either request got a 200. Now the request fails with an unhandled exception, which surfaces as a 500.

</details>

🟡 (optional) Derender callers whose router re-serializes `prompt_logprobs` with sorted or unordered map keys can get wrong `decoded_token` text for multi-byte (U+FFFD) prompt tokens. On base those fields stayed null. `_resolve_prompt_logprobs` takes the correction context from `next(iter(entry))`, the first JSON key of each position. That is only the prompt token if JSON object key order survives every hop. Fix: take the context from the real prompt ids, such as `gen.prompt_token_ids[i]` or a full-length caller `prompt_token_ids`, when their length matches `prompt_logprobs`. Fall back to key order only when neither is available.

<details>
<summary>Why this was flagged</summary>

The trigger is a caller of /v1/chat/completions/derender or /v1/completions/derender whose generate_response passed through a component that does not keep JSON object key order. The generate server (token_in_token_out/serving.py:469) emits the prompt token first, but JSON objects are unordered by spec and the derender request is caller-supplied. In `_resolve_prompt_logprobs` (online_derenderer.py:1043), `context_token_ids.append(next(iter(entry)))` then records an arbitrary top-k id, such as the smallest id, as the earlier prompt token. For any missing decoded_token that ends in U+FFFD, `_correct_decoded_token` (line 1038) decodes it against these wrong ids. That returns garbage or "" rather than what `vllm serve` returns. On base, decoded_token stayed null, so callers could tell it was missing; now it is wrong without any warning.

**Verification:** The field is client-supplied data: `GenerateResponseBase.prompt_logprobs` (token_in_token_out/protocol.py:443) arrives in the derender request body, and pydantic accepts any key order. Nothing checks that the first key is the prompt token. The base branch returned null for these fields, so the result changes from missing to silently wrong.

</details>
