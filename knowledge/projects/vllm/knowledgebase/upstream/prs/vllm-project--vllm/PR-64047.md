# [Bugfix][MoE] Avoid double router weighting in TRTLLM NVFP4 experts

[Upstream PR](https://github.com/vllm-project/vllm/pull/64047) · state: open · merged: False

## Original PR description



## Overview

Avoid applying the router weight twice in TRTLLM NVFP4 modular experts when `apply_router_weight_on_input=True`, as used by Llama4 top-1 routing. Give fused output finalization unit weights after prepare has weighted the input.

## Claims

- Fix the input-weighted path for both static and per-token activation quantization; leave default output weighting and monolithic experts unchanged.
- Extend the existing kernel suite with six nonzero SiLU/top-1 regressions and document the routing contract.

## Validation

On B300, Torch 2.14.0+cu130 / FlashInfer 0.7.2.post1, with matched baseline/candidate module overlays:

| Check | Before | After |
| --- | --- | --- |
| Complete modified `test_trtllm_nvfp4_moe.py` | 23 passed, **6 failed**, 2 skipped | **29 passed**, 2 skipped |
| Actual offline LLM, online NVFP4, DP2/EP2: routed-layer checks | 6/6 failed, relative L2 0.418–0.475 | 6/6 passed, relative L2 0.154–0.174 |

Kernel command (run with the PR test file on both arms, changing only the expert implementation):

```bash
.venv/bin/python -m pytest -v -s tests/kernels/moe/test_trtllm_nvfp4_moe.py
```

The six new cases fail before the fix at the exact input-weighting comparison; existing cases and the two unsupported RELU2-tile skips are retained. The existing `kernels-b200` Buildkite step selects this file and the changed implementation.

For the supplementary LLM regression, I used the public nonzero weights from `ngxson/TEST-Tiny-Llama4@24071fa7c15a663c545dff8fdfc58b500db05be9`, `quantization="nvfp4_per_token"`, `moe_backend="flashinfer_trtllm"`, and `all2all_backend="flashinfer_nvlink_one_sided"`, with expert parallelism enabled and eager text generation. Both arms loaded the actual `Nvfp4OnlineMoEMethod` → `TrtLlmNvFp4ExpertsModular` path and generated six one-token responses per rank. Passive layer captures were compared with an independent Torch routed-expert reference using the original weights quantized/dequantized by the native NVFP4 helper. The predeclared relative-L2 limit was 0.2 because the reference does not emulate activation/intermediate FP4 rounding.

This is a routed-layer correctness evaluation, **not trained-model accuracy, graph-mode, or performance evidence**. The tiny checkpoint's attention-temperature `int4` config was explicitly normalized to `true` for Transformers compatibility. The runtime used precompiled artifacts plus the matching source/test overlays, not a full current-main rebuild. Scoped Linux pre-commit hooks all passed without changing the reviewed files:

```bash
.venv/bin/python -m pre_commit run --files \
  vllm/model_executor/layers/fused_moe/experts/trtllm_nvfp4_moe.py \
  tests/kernels/moe/test_trtllm_nvfp4_moe.py \
  docs/design/moe_kernel_features.md
```

## Details

Prepare weights the activations before quantization, but the modular expert still forwards the original weights to fused output finalization. Replacing them with ones when input weighting is enabled preserves the existing reduction/chunking path without weighting again. The regression compares this path with explicitly preweighted input and unit output weights, requires a nonzero reference, and uses exact equality.

This is separate from #63700 (BF16 experts) and #62019/#63024 (LoRA paths). I rechecked open PRs and the latter's NVFP4 implementation; they do not fix this base modular-expert path. The three touched upstream files remain unchanged on current main `e7fa26d5c8d` relative to the validated base.
