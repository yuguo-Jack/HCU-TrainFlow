# [Core] Release the CUDA graph pool on sleep instead of backing it up

[Upstream PR](https://github.com/vllm-project/vllm/pull/59909) · state: open · merged: False

## Original PR description

## Purpose

Follow-up to #59160. With `sleep_mode_offload_cudagraph=True`, sleep copied the CUDA graph pool to pinned host memory and copied it back on wake. The copy is unnecessary: after capture, no tensor is allocated in the pool. It only holds scratch (activations, kernel workspaces, indexer logits, MoE scratch) that every replay writes before it reads.

This PR:
- Releases the `cudagraph` tag on sleep without a CPU backup. Any wake still maps it back at the same addresses, so graphs replay without recapture.
- Refuses to release the pool if a tensor is still allocated in it (`Cannot release the CUDA graph pool: tensors are live`). The check runs before anything is unmapped, so a future buffer kept alive inside the pool fails loudly instead of waking up as garbage.
- Updates the config docstring and the sleep mode docs.

Effect: no pinned host memory for the pool, and less copying on sleep and wake. On DeepSeek-V4.1 (TP8, GB300) the pool is 7.43 GiB per GPU.

## Test Plan

- `test_cudagraph_pool_sleep` (levels 1 and 2), reworked:
  - sleep releases every `cudagraph` allocation with no backup;
  - sleep refuses, and unmaps nothing, while a tensor is alive in the pool;
  - any wake maps the pool back at the same addresses;
  - a replay is correct after wake.
- `test_sleep_cudagraph_pool` (FULL, PIECEWISE, breakable, TP2 with custom allreduce, off by default): outputs are exact after level 1 and level 2 sleeps.
- Liveness, measured before this change on the #59160 code: at the end of capture, the graph pool's allocated bytes, for
  - DeepSeek-V4.1 (TP8);
  - DeepSeek-V4-Flash with MTP;
  - 16 configs on H200: Qwen3 0.6B/4B/8B (FULL, PIECEWISE, breakable), V1 runner, TP2 with custom allreduce, draft model, DeepSeek MTP, MiMo MTP, DFlash, Qwen3-VL-2B encoder graphs, LoRA.
- Garbage fill, also measured before this change: after sleep and wake, fill the pool with 0xFF, then compare outputs with the awake run.

## Test Result

- CI image `5e56e9af2a` (main with #59160) plus this patch, run the CI way (`cd tests`, `VLLM_WORKER_MULTIPROC_METHOD=spawn`), on H200:
  - `test_cumem.py`: 21 passed.
  - `test_sleep_cudagraph_pool`: 5/5 passed in each of 3 runs.
  - `test_sleep_mode_backend.py`: 9 passed.
- Liveness: 0 allocated bytes in the graph pool after capture, and still 0 after generation, in every config above. Everything reserved is cached-free.
- Garbage fill: outputs token-exact in every config. Zero-filling the `weights` tag changes them, so the check can fail.
- Negative control: a 256 MiB tensor allocated during capture, kept alive, written once outside the graph and read by every replay, shows up as allocated in the pool. With this PR, sleep refuses it.

- AlanFokCo · comment · 2026-10-05T06:09:24Z · [source](https://github.com/vllm-project/vllm/pull/59909#issuecomment-5989071022)

Independent H20 validation of this patch at `4d8abead353b6c6bf3dc0196cb91e9671f20b7a9`, applied to main `6f75cc7d5d1b5adfb399cbf79a8231ae66844fcf` (driver 580.126.09, PyTorch 2.13.0+cu130).

The normal path worked for Qwen3-32B TP=1/2/4 and Qwen3-30B-A3B-Instruct-2507 TP=4: 20 cycles per sleep level (1 and 2). In another 20 cycles per configuration, we overwrote every tagged graph-pool region with alternating `0xA5`/`0x5A` after wake (and after weight reload for level 2). Retained graphs replayed without recapture, worker PIDs and addresses stayed stable, communication checks passed, and generated tokens matched each run's reference. This is limited-input validation: 32B returned logprobs varied under ordinary scheduling, and 30B had pre-sleep warm-up token differences in the normal level-2 run and the fill level-1 run; formal cycles matched their references.

There is a separate rejection-path issue. With Qwen3-0.6B TP=2, we kept a tensor allocated during capture alive **only on rank 0**. For both sleep levels, with `enable_nccl_comm_suspend` off and on, the recorded states after the backend calls were:

| Component | Observed result |
|---|---|
| Rank 0 | `Cannot release the CUDA graph pool: tensors are live`; allocations still mapped; backend `SUSPENDED` |
| Rank 1 | Allocations already asleep; backend `SUSPENDED` |
| Executor | `sleeping_tags=[]`, `is_sleeping=False` |

At level 2, rank 1 had also discarded its weights. The per-worker snapshots were collected in `finally` around `CuMemBackend.suspend`; we did not issue inference, another worker RPC, or public wake after the exception. The communication option was recorded, but these snapshots do not establish completion of communicator suspension.

The local guard correctly rejects before unmapping **on that rank**, but this does not make the multi-worker sleep atomic. Restoring only the rejecting backend's state would leave rank 1 asleep. It would be useful to define the failure contract and add an asymmetric two-rank regression: coordinate validation before mutation, and handle failures after mutation separately. This does not contradict the normal-path results above or establish a failure in the GB300 configurations in the PR description.

Allocator-level regression reproducer: [af8dd21067](https://github.com/AlanFokCo/vllm/commit/af8dd210670f34206fd4a275c37e6e4eb94ad67e). With this PR's patch applied to the pinned main, its four level/tensor-view cases fail at the final `backend.state() == "RUNNING"` assertion after the mapping, backup and replay checks pass. This is a tests-only, **expected-failing single-backend reproducer**, not a production fix or a replacement for the TP2 diagnostic above. It is provided for reproducing the issue or adopting alongside a fix, not for merging unchanged as a passing regression.
