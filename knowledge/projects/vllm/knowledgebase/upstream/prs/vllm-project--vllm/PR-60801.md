# [Kernel][XPU] Mamba2 SSD: tensor-descriptor path for _chunk_scan_fwd_kernel and _chunk_state_fwd_kernel

[Upstream PR](https://github.com/vllm-project/vllm/pull/60801) · state: open · merged: False

## Original PR description

### Purpose

Mamba2 SSD prefill spends most of its SSD time in `_chunk_scan_fwd_kernel` and `_chunk_state_fwd_kernel`. Both load and store 2D tiles with masked pointer arithmetic. This PR adds a tensor-descriptor (TD) path to both behind a `USE_TD` constexpr: on Intel XPU the descriptors lower to 2D block IO, and the path is on by default there. Elsewhere it is opt-in with `VLLM_TRITON_USE_TD=1` (TMA on sm90+). With TD off the generated code is unchanged.

Co-author: @mfylcek; work initiated by Marceli.

No open PR adds a tensor-descriptor path to these kernels (searched open and merged PRs for SSD and tensor descriptor); earlier single-kernel attempts #47084 and #45816 were closed.

### Changes

- **Kernels:** tiles go through `tl.make_tensor_descriptor` (zero padding replaces the load masks, outputs are stored through descriptors). When a sequence has no initial state, the TD branch skips the `prev_states` dot. `USE_TD` is part of both autotune keys.
- **Guard:** `vllm.triton_utils.tensor_descriptor_compatible` sends a launch down the pointer path when an operand cannot back a descriptor: non-unit inner stride, base not 16 B aligned, last-dim width under 64 B or not a 16 B multiple, outer pitch under max(64 B, width) or not a 16 B multiple. The 64 B rule is the Intel 2D block IO minimum; narrower operands (for example `head_dim=8`) abort under `TRITON_INTEL_2DBLOCK_ASSERT=1`.
- **Tests / CI:** TD tests are added to `tests/kernels/mamba/test_mamba_ssm_ssd.py` (`-k ssd_td`, 37 tests): TD vs pointer path with identical pinned tiles, guard fallbacks, TD vs the torch reference, and a launch spy that asserts which path ran. An Intel step runs them; the CUDA mamba step also depends on the TD helper files.

### Results

> **Reproducing these results requires #60800** (SSD autotune warmup on up to 32 chunks instead of one). The kernels are autotuned on the first call and the tile picked there is reused for every later prefill; with the one-chunk warmup a start can lock in a slow tile, so numbers vary from start to start (main's most of all). That PR has the evidence.

**Kernel level**, time per call with the best tile of each side (all tiles timed, median of 3 reps), Arc Pro B60 and B70:

| kernel | Nano-4B 4x2048, B60 | Nano-4B cases, B70 | geomean over 20 realistic cases, B60 | geomean over 20 realistic cases, B70 |
| --- | --- | --- | --- | --- |
| `_chunk_scan_fwd_kernel` | 7186 -> 3467 us (**2.07x**) | **2.26x** | **2.10x** | **1.78x** |
| `_chunk_state_fwd_kernel` | 1993 -> 1092 us (**1.82x**) | **1.57x** | 1.25x | 1.15x |

The 20 cases are 4 model shapes (Nemotron-3-Nano-4B, Falcon-H1-0.5B, Nemotron-3-Ultra TP=8 per-card shape, a synthetic dstate=256 shape) x 5 batch shapes.

Nemotron-3-Nano-4B-BF16, TP=1, seed 42, prefix caching off, Triton 3.8.0, `vllm bench latency --output-len 1` (prefill). Every sample is a separate process (B70: one container per sample) with its own autotune results, which are cached on disk; main and PR interleaved, warm-up discarded. On B70 compiled Triton binaries were reused between samples, autotune results never.

| platform | input x batch | main | PR | delta | samples |
| --- | --- | --- | --- | --- | --- |
| Arc Pro B60 | 2048 x 4 | 905 ms (902-910) | 828 ms (821-832) | -8.5% (-7.9 ... -9.6%) | 9, all faster |
| Arc Pro B60 | 8192 x 1 | 935 ms | 862 ms | -7.8% (-7.6 ... -8.1%) | 3, all faster |
| Arc Pro B60 | 128 x 1 | 38.2 ms | 36.2 ms | -5.3% | 2, all faster |
| Arc Pro B70 | 2048 x 4 | 658-835 ms | 587-590 ms | -18.7% (-10.4 ... -29.6%) | 7, all faster |
| Arc Pro B70 | 8192 x 1 | 708-738 ms | 607-611 ms | -15.7% (-13.7 ... -17.7%) | 2, all faster |
| Arc Pro B70 | 128 x 1 | 32-34 ms | 33-34 ms | -1.5%, +4.8% | 2, mixed |

On B70 main's own time varies between samples (658-835 ms at 4x2048) because of the first-call tile choice (see Notes). Against main with the same warmup change the gain of this PR is -8.3 ... -9.4% at 4x2048 (7 samples) and -8.4 ... -8.9% at 1x8192 (2 samples). At 128 tokens the PR is not a win on B70: 3-8% (1-3 ms) slower than main with that change.

`vllm bench serve` (random 2048/128, 200 prompts, concurrency 16), main vs PR with the warmup change:

| platform | mean TTFT | p99 TTFT | TPOT | output tok/s |
| --- | --- | --- | --- | --- |
| Arc Pro B60 | -12.1% | -11.9% | -4.9% | +6.0% |
| Arc Pro B70 (3 reps) | -23.6% | -22.8% | -11.0% | +14.6% |

On B70 main's throughput varies by 8% between server starts (331-359 tok/s) because of the first-call tile choice (see Notes), the PR's by 1%; the per-rep gain is +9.8% to +18.7%. In the B70 serve runs the warmup sequence is 8 chunks (`max_num_batched_tokens` 2048).

gsm8k 5-shot (full set, 1319), `lm_eval --model vllm`, Nemotron-3-Nano-4B, main vs PR:

| platform | flexible-extract | strict-match |
| --- | --- | --- |
| Arc Pro B60 | 0.8476 vs 0.8476 (stderr 0.0099) | 0.8453 vs 0.8461 |
| Arc Pro B70 | 0.8484 vs 0.8476 (stderr 0.0099) | 0.8461 vs 0.8431 |

The kernel speedups above are larger than the end-to-end ones because the SSD kernels are only part of the prefill. Most of the scan gain is the skipped `prev_states` dot (TD without the skip: 1.18x). State is shape dependent: on Falcon-H1-0.5B the best state tile with TD is 1.04-1.13x slower than main's best, so the end-to-end numbers are the claim.

A launch spy confirmed `USE_TD=True` for every launch of both kernels on the PR and `False` on main. With TD off (CUDA default), TTGIR and PTX of every autotune config of both kernels (69 scan / 28 state variants) are identical to main on H200 NVL and B200, and the autotune config lists are unchanged.

### Notes

- Part of the tensor-descriptor work under RFC #42545, gated by the shared `VLLM_TRITON_USE_TD` (auto on for XPU, opt-in elsewhere).
- Earlier single-kernel SSD TD attempts were closed for flat end-to-end results: #47084 (`_bmm_chunk_fwd`) and #45816 (`_chunk_cumsum_fwd`).
- Depends on #60800 for stable, reproducible autotune picks (see the note at the top of Results). Without it a start can pick a slow tile, with or without TD.
- On CUDA and ROCm the opt-in path is validated by unit tests only (CUDA sm90/sm100); there is no accuracy or end-to-end measurement there, and ROCm is untested.
- Overlaps #58592, which splits the CUDA mamba kernel CI step and moves `test_mamba_ssm_ssd.py`; whichever lands second rebases.
- AI assistance (Claude) was used for parts of this change, the tests and the measurements. All results come from runs on the hardware listed above.
