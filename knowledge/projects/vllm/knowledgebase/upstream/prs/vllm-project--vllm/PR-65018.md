# [Feature][Frontend] Add metadata value to mm_payload on render requests

[Upstream PR](https://github.com/vllm-project/vllm/pull/65018) · state: open · merged: False

## Original PR description

## Overview

Adds `mm_payload: "metadata"` to render requests: `kwargs_data` is null and `mm_metadata` stays. Prefill can then load embeddings through the EC connector without render serializing the processed tensors. Closes #64997, part of #46722.

## Claims

- A `metadata` render returns the same token IDs, hashes, placeholders and `mm_metadata` as a `tensors` render, without the tensors.
- Prefill from a `metadata` render matches single-instance output end to end.
- `none` and the `tensors` default are unchanged, except for the fix below.
- Fixes a 400 on `tensors` when one modality in a request has no metadata, such as image + video on LLaVA-OneVision and Gemma 4.

## Details

- **New value, not a changed `none`.** #62152 and #64685 rely on `none` being layout only.
- **`RenderedGenerateRequest`.** Render returns `GenerateRequest`, whose EC check rejects metadata-only items, and render output has no EC params until encode runs. Without this subclass every `metadata` render with metadata returns 400, and keeping metadata under `none` would too. `/inference/v1/generate` still validates its input as `GenerateRequest`, so metadata-only items without `ec_transfer_params` are still rejected.
- **Null when incomplete.** The encoder used to drop a modality without metadata, and `MultiModalFeatures` then rejected the mismatch. `mm_metadata` is now null if any modality has none, which keeps it complete when present (see #56069). Callers see null and fall back to sending the media, as `renderer.md` now says.
- **Limits.** Prefill was not run on Gemma 4 or on real audio. Image + audio is covered by unit tests only. In the EC e2e test, encode takes `kwargs_data` from a `tensors` render. I did not run encode from `content_parts` on a GPU. On CPU, that path gives the same hashes as render (Qwen2-VL-2B and LLaVA-OneVision, 3 requests each), but it expands rendered `token_ids` again (87 to 150 tokens for one image on Qwen2-VL-2B). That is existing behavior and this PR doesn't change it. A `metadata` response with null `mm_metadata` must not go to generate, same as `none`; #62152 turns that into a 400. I did not measure serving latency: #64997 reports the prefill cost of the current fallback.
- **Overlaps.** #60526 moves `MMPayload`, so whichever lands second needs a small rebase. #64685 will need the same value in its Rust render.
