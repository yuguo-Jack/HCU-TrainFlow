# [Perf] Watermarking: skip greedy-fallback argmax when no request is greedy

[Upstream PR](https://github.com/vllm-project/vllm/pull/62654) · state: closed · merged: True

## Original PR description

## Overview

`GPUWatermarkSampler._sample_random` ran a full-vocabulary argmax on every watermarked step to give greedy (temperature 0) rows their token, even when the batch had no greedy row. This PR checks the host-side temperatures first and skips the argmax and the `torch.where` when no row is greedy.

## Claims

- The watermarked sampler step is 13 to 41 µs faster under CUDA graphs on H200 (B = 1 to 128, vocab 151,936), for both `gumbel` and `dual_key_gumbel`. That is 15 to 22% of the step, and 17 to 41% of the watermark's overhead over the plain sampler.
- Serving Qwen3-0.6B with Gumbel watermarking at concurrency 32: mean TPOT drops by 21.5 ± 11.5 µs (6 paired replicates), which matches the 20 µs saved per step at B = 32. The no-watermark arm does not change.
- Speculative decoding (`dual_key_gumbel` + DFlash): the verify step uses the rejection sampler, which handles greedy rows inside its kernel and never reaches the changed code. Verify-step time and serving throughput are unchanged. Only steps where no request in the batch has drafts go through `_sample_random`; those get the same saving.
- Sampled tokens are unchanged. When any row is greedy, the old code runs as before.

## Details

**Root cause.** The greedy fallback was unconditional:

```python
sampled = torch.where(temperatures == 0, processed_logits.argmax(dim=-1), sampled)
```

The argmax reads the whole `[B, V]` fp32 logits tensor again after the watermark kernel has already read it. At B = 32 and V = 151,936 that is 19.4 MB per step, plus a second kernel launch for `torch.where`. Most watermarked traffic has no greedy rows, because a greedy request cannot be watermarked, so the result was usually discarded.

**Change.** Run the fallback only if `self.sampling_states.any_greedy(idx_mapping_np)` is true. This existing helper reads the host-side temperature array, the same one `_sample_random` already reads to decide whether watermarking is on for the batch. The branch is decided on the host, like the existing watermarking-enabled check above it, so there is no GPU sync. Expanded (speculative) rows repeat `idx_mapping` rows, so the host check covers them too.

**Speculative decoding.** When the batch has drafts, the V2 model runner calls `RejectionSampler`. It applies sampling params and runs the watermarked `rejection_sample` kernels, which handle temperature-0 rows in-kernel (accept if the draft matches the target argmax). It does not call `_sample_random`. The draft side (`DraftWatermarker.sample`) has no greedy-fallback argmax either. So this PR only affects spec-decode steps where no request in the batch has drafts. In the DFlash serving run above, 13 of the first 5,000 sampling steps (0.3%, startup warm-up included) went through `_sample_random`, counted with a diagnostic hook; the rest used the rejection sampler.

**Behaviour.** Tokens are unchanged for every batch. One internal difference: padding rows (`expanded_idx_mapping == -1`) used to read slot −1's temperature on the GPU and could receive an argmax token. They now keep the sampled token when no real row is greedy. Padding rows are discarded, so this is not observable.

**Tests.** Three existing tests stub `sampler.sampling_states` with a `SimpleNamespace`; they get an `any_greedy` stub that returns `False`, since all their rows use temperature 1.
