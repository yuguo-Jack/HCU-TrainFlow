# [Bugfix][Spec Decode] Fall back from InstantTensor for PP-local draft models

[Upstream PR](https://github.com/vllm-project/vllm/pull/65572) · state: open · merged: False

## Original PR description



## Overview

With pipeline parallelism, a speculative-decoding draft model that lives only on the last PP stage deadlocks at load time when the target uses `--load-format instanttensor`. This extends the existing `fastsafetensors` fallback in `get_pp_safe_draft_load_config` (vllm-project/vllm#54416) to `instanttensor`.

## Claims

- Fixes a startup deadlock for PP > 1 + any drafter loaded through `get_pp_safe_draft_load_config` (EAGLE/EAGLE3/MTP, DFlash, DSpark, draft_model, extract_hidden_states) + `load_format="instanttensor"`.
- Only the draft falls back to the standard safetensors loader; the target model still loads with InstantTensor.
- PP = 1 and other load formats are unchanged.
- The fallback warning is now actually emitted. Only last-stage ranks reach it, so the default `local` scope of `warning_once` hid it on a single node; this also applied to the existing `fastsafetensors` message.

**Where we hit it:** DeepSeek-V4.1-Flash, TP4 × PP2 + DSpark, InstantTensor, 8 × RTX 6000D, on a downstream build carrying the same `get_pp_safe_draft_load_config` and `instanttensor_weights_iterator` logic. Startup stalled with the same two stacks (`load_dspark_model` instead of `load_eagle_model`); with this fallback the server starts and serves (mean DSpark acceptance length 3.20, 32K-token single-request TTFT 1.82 s).

## Details

**Root cause.** `instanttensor_weights_iterator` passes the world group's device group as `process_group` (unless a tensor filter is active), and InstantTensor runs an `all_reduce` on it while planning I/O. The draft model is instantiated only on the last PP stage, so ranks on earlier stages never join that collective and the last stage blocks until the NCCL timeout. `get_pp_safe_draft_load_config` already handles the same problem for `fastsafetensors`; `instanttensor` was missing.

**Choice.** Reuse the existing fallback instead of passing a stage-local group to InstantTensor: it is the smallest change, matches the `fastsafetensors` behavior, and draft checkpoints are small, so the slower loader costs little. Making InstantTensor collective over the stage-local group could be a follow-up.

**Scope.** Model Runner V2 only, like the existing `fastsafetensors` fallback; the deprecated MRV1 draft path (`vllm/v1/spec_decode/`) is left unchanged.

**Test placement.** The test is a new `pp2_instanttensor` config of the existing `test_deepseek_mtp_load_inline`, which already checks drafter loading under TP/EP/EPLB/PP. The standalone `draft_model` method hits the same deadlock, but on `main` it fails under PP for an unrelated reason once loading succeeds (the draft is built with the global PP group, so `Qwen2Model.forward` asserts `intermediate_tensors is not None` during profiling), so it cannot host a passing test.

**Not a duplicate.**
- vllm-project/vllm#63321 and vllm-project/vllm#63619 enable DSpark + PP for DeepSeek-V4.1 in the model code; neither touches draft loading.
- vllm-project/vllm#61449 makes InstantTensor drop the collective only when a tensor filter is used (`is_unused_checkpoint_weight`); drafts that do not define it (e.g. the DeepSeek-V4.1 DSpark head, standalone draft models) still use the world group.
- vllm-project/vllm#61835 (closed) applied the same helper to RunAI's distributed mode; it does not cover InstantTensor.

**CI.** The `[Nightly] Spec Decode DeepSeek MTP Parallel Load` step (2 × B200) already runs this test file; `vllm/v1/worker/gpu/spec_decode/utils.py` is added to its source dependencies. The new case is skipped on non-CUDA platforms (e.g. the AMD mirror) because InstantTensor requires NVIDIA GPUs.
