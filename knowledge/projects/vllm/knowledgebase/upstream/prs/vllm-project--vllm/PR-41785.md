# [LoRA][Perf] Overlap LoRA weight H2D copies with compute via side CUDA stream

[Upstream PR](https://github.com/vllm-project/vllm/pull/41785) · state: open · merged: False

## Original PR description

## Purpose

LoRA adapter H2D copies in `activate_adapter` sit on the default stream behind whatever compute is still in flight. PCIe DMA and SMs are independent so there's no reason they can't run in parallel.

This adds `--enable-lora-overlap-loading` (off by default). Copies go on a dedicated side stream; the default stream waits on a CUDA event before the next forward pass. Flag off = `nullcontext()`, zero cost.

7 files changed, +275/−13. Core logic is a ~33-line `LoRAOverlapLoader` class (+56/−10 across 5 source files; the remainder is tests).

## Relationship to PR #31941

PR #31941 ("LoRA Per Request Loading Pipelining Support") targets the same general idea but is a different design:

| | This PR | PR #31941 |
|---|---|---|
| **Granularity** | Coarse: entire `activate_adapter` on one side stream, single sync point before next forward | Fine: layer-by-layer pipelining within prefill forward pass, per-layer sync points |
| **Scope** | +56/−10, 5 source files, no forward pass changes | +597/−191, modifies forward pass |
| **When it helps** | Every adapter swap (decode, speculative, any sequence length) | Per-request loading with long inputs (>1000 tokens) |
| **Risk** | Low — flag off is a strict no-op | Higher — invasive changes to forward path |

The two approaches are complementary. This PR is a low-risk, always-on-eligible primitive; #31941 is a more aggressive pipeline for TTFT-critical workloads.

## Not a Duplicate

Searched open PRs for `lora overlap`, `lora stream`, and `activate_adapter stream`. PR #31941 is the closest match but uses a materially different approach (per-layer forward-pass pipelining vs. coarse side-stream with single event). No other open PR addresses the coarse-grained overlap approach implemented here.

File: `vllm/lora/lora_overlap_loader.py` · line 21

![critical](https://www.gstatic.com/codereviewagent/critical.svg)

The current implementation is susceptible to a critical race condition. When LoRA slots are reused across iterations, the side stream may start overwriting GPU buffers while the default stream is still executing kernels from the previous iteration that are reading from those same buffers. To ensure correctness, the side stream must synchronize with the default stream before starting the copies. Additionally, creating a new `torch.cuda.Event` on every call is inefficient; using `enable_timing=False` is recommended for synchronization-only events to reduce overhead.

```python
    @contextmanager
    def load_context(self):
        current_stream = torch.cuda.current_stream()
        with torch.cuda.stream(self._stream):
            # Ensure we don't overwrite buffers currently in use by the default stream
            self._stream.wait_stream(current_stream)
            yield
        event = torch.cuda.Event(enable_timing=False)
        event.record(self._stream)
        self._pending = event
```

🟡 **Severity: MEDIUM**

The side CUDA stream begins H2D copies without first waiting for the default stream's in-flight work. When a LoRA slot is evicted and reused between consecutive `execute_model` iterations, the side stream can overwrite GPU weight buffers (`lora_a_stacked`/`lora_b_stacked`) while the previous forward pass on the default stream is still reading them, causing a data race on shared GPU memory. A `self._stream.wait_event(default_stream_event)` is needed before entering the side stream context.

<summary>💡 Fix Suggestion</summary>

**Suggestion:** Before entering the side CUDA stream context, record an event on the current (default) stream and make the side stream wait on it. This ensures the side stream's H2D copies won't begin until the default stream has finished any in-flight forward-pass kernels that may still be reading the weight buffers.

Add the following before the `with torch.cuda.stream(self._stream):` block:
```python
default_event = torch.cuda.Event()
default_event.record(torch.cuda.current_stream())
self._stream.wait_event(default_event)
```
