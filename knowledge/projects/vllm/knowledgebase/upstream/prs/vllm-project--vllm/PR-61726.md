# [Bugfix][ROCm][MoRIIO] Support heterogeneous TP in WRITE mode for all attention and mamba layers

[Upstream PR](https://github.com/vllm-project/vllm/pull/61726) · state: closed · merged: True

## Original PR description

Fixes #60101. This PR fixes a hang in MoRIIO WRITE-mode disaggregated serving when using MLA models with a smaller tensor-parallel size on prefill than on decode.

For example, with prefill TP2 and decode TP4, the expected mapping is:

- Prefill rank 0 → decode ranks 0 and 1
- Prefill rank 1 → decode ranks 2 and 3

Previously, each prefill rank wrote the KV cache to only the first mapped decode rank. The other decode ranks did not receive their KV cache or completion notification and continued waiting indefinitely.

## Root cause

MoRIIO already calculated the first corresponding remote TP rank, but the WRITE data path treated this as a one-to-one mapping.

That behavior is sufficient for equal TP sizes and mappings that do not require replication. However, the MLA KV cache must be fanned out when the decode TP size is a multiple of and larger than the prefill TP size.

The existing heterogeneous-TP acknowledgement logic expects completion from all corresponding decode ranks, while the WRITE path previously reached only one of them.

## Changes

This PR introduces a small helper, `get_moriio_write_target_tp_ranks`, which extends the existing remote-rank mapping for MLA WRITE fan-out.

When MLA is used and decode TP is larger than prefill TP:

1. Determine the first decode rank using the existing MoRIIO TP-rank mapping.
2. Calculate the required fan-out from the prefill and decode TP sizes.
3. Establish sessions with every corresponding decode rank.
4. Write the KV cache through every target session.
5. Wait for all resulting transfer statuses before completing the request.
6. Send `write_done` to every target decode rank.
7. Send `write_failed` to every affected target if a deferred write times out.

## Scope and compatibility

The fan-out behavior is restricted to:

- MoRIIO WRITE mode
- MLA models
- Prefill TP smaller than decode TP

This change is contained within the vLLM MoRIIO connector and does not require changes to the MoRI library.

Routing is based on TP/DP ranks and the existing endpoint-resolution logic rather than physical node placement. Runtime validation was performed on a single node.

- chunfangamd · comment · 2026-10-16T05:29:16Z · [source](https://github.com/vllm-project/vllm/pull/61726#issuecomment-6208789010)

This fixes #60101 on the setup where we first saw it. Thanks!

**Setup:** two MI355X nodes, `deepseek-ai/DeepSeek-R1-0528` (FP8, with an fp8 KV cache), and MoRI-IO in WRITE mode over RDMA. The prefill ran at TP4 (with `--enforce-eager`) on one node, and the decode at TP8 on the other. Both runs below used the same image, the ROCm nightly at `3f1bcfd8`, whose MoRI-IO files are identical to this PR's base. For the second run, we mounted this PR's three files (at `53a33311`) over them.

**Without the PR,** the request hung, as in #60101. The prefill connected to only 4 of the 8 decode ranks (0, 2, 4 and 6). With MLA, every decode rank needs its own full copy of the latent, but only 4 of the 8 copies arrived.

**With the PR,** the prefill connected to all 8 decode ranks, and every request completed, through vllm-router and through SMG: 6 single requests and 32 at concurrency 8 in all. Each time, the decode node received all 8 copies (100.0 to 100.5% of the expected bytes). The single requests' answers matched what the prefill alone produces, and each concurrent request got the answer to its own prompt.

Two things the PR leaves out, which could be follow-ups:

1. The handshake still accepts topologies the fan-out doesn't handle. These are non-MLA models with different TP sizes, TP sizes that aren't multiples of each other, and a prefill TP larger than the decode TP. Rejecting them at handshake would turn a hang into a clear error.
2. The decode still sends its "blocks ready" and release notifications to one prefill port per decode rank, that is, to as many ports as the decode's TP size. With a TP4 prefill and a TP8 decode, half of them go to ports nobody listens on, and they stay queued in the decode's sockets, which have no send limit. With a prefill TP larger than the decode TP, some prefill ranks would never be notified.
