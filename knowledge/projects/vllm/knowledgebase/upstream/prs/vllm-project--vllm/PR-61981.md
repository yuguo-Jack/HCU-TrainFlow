# [XPU] Use per-token dynamic FP8 activation quantization on XPU

[Upstream PR](https://github.com/vllm-project/vllm/pull/61981) · state: closed · merged: False

## Original PR description

## Purpose

With `activation_scheme="dynamic"`, FP8 linear layers pick per-token activation scales only when `cutlass_fp8_supported()` is true. That helper is CUDA-only, so XPU always falls back to **per-tensor** dynamic quantization. Per-tensor dynamic quant needs a separate global max-reduction pass before quantizing, which is noticeably slower on XPU.

`XPUW8A8FP8LinearKernel` already lists `kFp8DynamicTokenSym` as supported, and `torch.ops._xpu_C.fp8_gemm` already accepts `[M, 1]` activation scales, so only the selection logic needs to change.

## Changes

- Add `dynamic_per_token_fp8_supported()` in `w8a8_utils.py`, returning `current_platform.is_xpu() or cutlass_fp8_supported()`. `cutlass_fp8_supported()` keeps its CUTLASS-only meaning.
- Use it in `Fp8LinearMethod` and `Fp8PerTensorOnlineLinearMethod`.

No behavior change on CUDA, ROCm, or CPU.

Note: on XPU this affects the W8A8 path (`XPUW8A8FP8LinearKernel`, e.g. `--kernel-config '{"linear_backend": "xpu"}'`). With `linear_backend=auto`, XPU currently selects the weight-only `XPUW8A16FP8LinearKernel`, where activations are not quantized.

## Test Plan

Intel Arc Pro B70, single GPU, Llama-3.2-1B-Instruct, `quantization="fp8"` (online), `linear_backend="xpu"`:

- Check the selected activation quant key and the scale shape passed to `fp8_gemm`
- Greedy generation, baseline vs patched
- Op-level timing of dynamic quant + `fp8_gemm`, per-tensor vs per-token

## Test Result

**Selection**: baseline `QuantKey(f8e4m3fn, scale(f32, dynamic, per_tensor))` -> patched `QuantKey(f8e4m3fn, scale(f32, dynamic, per_token))`.

**Generation**: 3 of 4 greedy prompts produce identical output. The fourth diverges after about 40 tokens with an equivalent continuation (normal numerical drift).

**Op-level (ms, dynamic quant + fp8_gemm, bf16 input, per-tensor FP8 weight)**:

| m, n, k | quant T -> K | gemm T -> K | total T -> K | speedup |
|---|---|---|---|---|
| 4096, 256, 8192 | 0.729 -> 0.215 | 0.233 -> 0.237 | 0.736 -> 0.486 | 1.51x |
| 4096, 1024, 8192 | 0.463 -> 0.217 | 0.908 -> 0.921 | 1.461 -> 1.233 | 1.18x |
| 4096, 2048, 8192 | 0.467 -> 0.221 | 1.857 -> 2.057 | 2.604 -> 2.362 | 1.10x |
| 4096, 4096, 4096 | 0.295 -> 0.137 | 1.935 -> 2.091 | 2.429 -> 2.283 | 1.06x |
| 8192, 8192, 8192 | 0.977 -> 0.450 | 17.204 -> 17.357 | 18.195 -> 17.651 | 1.03x |
| 32, 4096, 4096 | 0.053 -> 0.030 | 0.054 -> 0.054 | 0.091 -> 0.068 | 1.34x |
| 512, 4096, 4096 | 0.053 -> 0.030 | 0.229 -> 0.229 | 0.271 -> 0.263 | 1.03x |

Relative error vs fp32 reference is the same for both (about 0.037).

`ruff check` / `ruff format --check` pass.
