# [Model][Frontend] Add native VibeVoice-ASR with transcription API support

[Upstream PR](https://github.com/vllm-project/vllm/pull/62398) · state: open · merged: False

## Original PR description



## Overview

Adds a native VibeVoice-ASR implementation (`microsoft/VibeVoice-ASR-HF`) with `/v1/audio/transcriptions` support, including `diarized_json` (#48543). Previously the model only ran through the Transformers backend, which has no transcription endpoint. `--model-impl transformers` still selects that path. No open PR covers VibeVoice.

## Claims

- `json`, `text` and `diarized_json` responses; `prompt`/`hotwords` map to the model's context slot.
- Single-pass long-form audio (no server-side chunking), clean up to 40 min (see the 60 min row).
- Deterministic: no VAE sampling noise, unlike HF (see Details).
- Matches HF with its noise disabled: identical transcripts on 500/500 LibriSpeech, 300/300 VoxPopuli-de and 19/20 multi-speaker clips.

## Details

- **Determinism:** HF samples VAE noise at inference; here the latent mean is used. vLLM's processor, encoder and prefix caches assume deterministic embeddings, and the noise changes 3–20 % of transcripts with no accuracy gain. Reviewers, please confirm this divergence.
- **Serving change:** `parse_diarized_transcript` now receives the raw output, not the `post_process_output` result, mirroring `verbose_json`. VibeVoice needs plain text for `json` and structure for `diarized_json`. MOSS parses identically either way.
- **Transformers backend:** it caps audio at ~60 s (via the config's `max_position_embeddings=450`), OOMs on 24 GB with default settings, and crashes when batching audio of different lengths. This PR doesn't fix those issues; it avoids that path.

**Limitations**
- No native LoRA, which the fallback had. Most of the ~10 Hub adapters target the original checkpoint format; they can be merged offline. Decoder LoRA can follow (`glmasr.py` pattern).
- Validated in fp16 only. **Could a reviewer with an Ampere+ GPU please run the generation test in bf16, ideally plus a ~60 min request?**
- Beyond ~40 min, split recordings client-side. The default output cap (32,768 tokens, from `generation_config.json`) is also tight for an hour.
- Long-form serving needs the `VLLM_MAX_AUDIO_*` limits and `--max-model-len` raised (documented).
- Streaming returns raw JSON.
- Speaker labels are passed through as generated (`"0"`, `"1"`, ...).
- Chat prompts don't get `<|AUDIO_DURATION|>` filled in (pre-existing).
- Startup profiling adds ~1.5 min.

- sebfelix · comment · 2026-10-19T08:07:00Z · [source](https://github.com/vllm-project/vllm/pull/62398#issuecomment-6262630962)

Thanks for taking a look! There is currently no meaningful inference-speed gain over the Transformers backend. Both run the same HF encoder modules and vLLM's kernels for the Qwen2 decoder, which dominates compute:

| 500 LibriSpeech test-clean utts, offline, 1× RTX 6000 (fp16), `max_num_batched_tokens=2048` | Wall time (2 runs) | WER |
|---|---|---|
| Transformers backend¹ | 187 s / 201 s | 2.18 % |
| Native (this PR) | 193 s / 179 s | 2.14 % |

¹ With a local workaround for the batching crash described below (will probably open a separate PR for this later, since it may affect other models too).

Single stream (100 utts, no workaround needed): 201 s vs. 198 s.

The main motivation for this PR is functionality:

- The backend doesn't implement `SupportsTranscription`, so VibeVoice has no `/v1/audio/transcriptions` (including no `diarized_json`). The model-specific parts (prompt with the audio duration, JSON segment parsing, no server-side chunking) need a model class.
- The backend sizes audio items from `max_position_embeddings`, which VibeVoice's config sets to 450 (= 60 s), so longer audio is rejected. The model targets up to 60 min according to its model card (validated up to 40 min here).
- Startup with default settings: the backend's encoder profiling OOMs on a 24 GB GPU.
- Batching: the backend currently crashes when two audios of different lengths are encoded in the same step (`padding_mask` reaches HF's `get_audio_features` as a list). This brings performance gains.
- HF samples VAE noise in the acoustic latents at inference. The native class uses the latent mean, which keeps the encoder and prefix caches consistent.

If you'd rather keep the Transformers backend for the modelling, an alternative would be a thin VibeVoice class on top of `TransformersMultiModalForCausalLM` that only adds `SupportsTranscription` and sizes audio correctly. I didn't find a precedent for that pattern, so I went native, but I'm happy to switch if it fits better.
