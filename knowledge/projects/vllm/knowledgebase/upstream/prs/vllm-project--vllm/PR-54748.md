# [Spec Decode] Make the dynamic SD schedule observable

[Upstream PR](https://github.com/vllm-project/vllm/pull/54748) · state: open · merged: False

## Original PR description

Dynamic SD (`num_speculative_tokens_per_batch_size`) is hard to observe in two places.

**The resolved schedule is not printed.** `SpeculativeConfig.__repr__` omits it, so the startup banner cannot show whether the table survived config resolution (#48494). Under data parallelism `_maybe_disable_dynamic_sd_for_data_parallel` clears it after parsing. The banner now prints the resolved schedule and is unchanged when none is set.

**The K=0 decision is not observable.** Spec-decode stats count, per request, the drafts a step verifies. A step that selects K=0 can still verify drafts proposed in the previous step; what it changes is that it requests none for the next. The existing stats therefore do not show that a step selected K=0, and a deliberate K=0 tier appears only later, as verification that stops, which looks the same as speculative decoding not running.

## Behavior

`vllm:spec_decode_scheduled_steps_total{num_spec_tokens="K"}` counts scheduler steps by the K the schedule selected, including 0. K is the draft length requested from the drafter in that step; the next step verifies those drafts. A step is counted only when a dynamic schedule is set and the step scheduled request work, since an empty step never consults the schedule. Existing counters are unchanged. The counter is exported by the Python frontend only; the Rust frontend (`VLLM_USE_RUST_FRONTEND=1`) does not report it.

## Relation to #64099 / #64156

The RFC's drafted, verified and accepted counts are per request and per verification step. This counter records the scheduler's K decision per step, which those counts do not represent; a step that selects K=0 can still verify earlier drafts and appear in them. The two do not reconcile. The branches merge with one conflict: two adjacent declarations in `SpecDecodingProm.__init__`.

#56278 was opened yesterday, and its description places this PR as the scheduled-budget piece alongside #43310 and #44487, extending #48915 which you both approved. So a third party is now building against the shape of this one.

They compose rather than collide. #56278 extends `RequestSpecDecodeMetrics` — per request, keyed by proposed draft length. This one adds a per-step field to `SchedulerStats` and a new `vllm:spec_decode_scheduled_steps` counter, labelled by the K the schedule selected and incremented including `K = 0`. Different classes in `stats.py`, no overlapping lines.

The gap they approach from opposite ends is that a step the dynamic schedule sends to `K = 0` currently leaves no trace at all. `RequestSpecDecodeMetrics.observe` is reached only through the guard at `scheduler.py:1970`, which requires a non-empty entry in `scheduled_spec_decode_tokens`, and no entry is written when nothing was proposed. The aggregate counters have the same shape. The practical consequence is that a policy drafting on every step and one drafting on a fifth of them are today indistinguishable in the metrics, which is awkward now that the budget is allowed to vary per step.

+165/−1, reusing the `num_spec_tokens_to_schedule` the scheduler already computes rather than adding a new path to carry it, and the config banner output is byte-identical when no schedule is configured. Happy to split it, narrow it, or drop the logging half if you would rather it lived elsewhere.
