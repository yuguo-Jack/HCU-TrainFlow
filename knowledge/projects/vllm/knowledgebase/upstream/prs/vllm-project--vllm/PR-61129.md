# [Perf][Attention] Cache FlashAttention KV cache transpose+split views

[Upstream PR](https://github.com/vllm-project/vllm/pull/61129) · state: open · merged: False

## Original PR description

## Overview

Cache the `kv_cache.transpose(1, 2).split(head_size, dim=-1)` result in `FlashAttentionImpl` keyed on `data_ptr()`, avoiding redundant view operations on every `forward()` and `do_kv_cache_update()` call.

## Claims

- Eliminates redundant `transpose(1, 2).split(head_size, dim=-1)` calls in the FlashAttention hot path
- Applies to both `FlashAttentionImpl` and `FlashAttentionDiffKVImpl`
- Clears cached views during profiling cleanup to avoid stale references

## Validation

- GPU correctness test on RTX 5090 (CUDA 13.0): verified cache hit returns same views, rebind triggers recompute, cached views match fresh computation, writes to kv_cache reflected in cached views
- `ruff check` and `ruff format --check`: all passed
- Existing `test_kv_head_stride_canonicalization.py` tests: 10 CPU tests passed

## Details

The KV cache tensor is bound once via `bind_kv_cache()` and never reallocated during serving, making its `data_ptr()` stable. This allows caching the transpose+split views and reusing them across calls.

`_get_kv_cache_views()` checks `data_ptr()` on each call. On the first call (or after a rebind with a new tensor), it computes and stores the views. Subsequent calls return the cached views directly.

`FlashAttentionDiffKVImpl` inherits this method. Its `forward()` uses the same `split(self.head_size)` pattern, so the cached views work correctly. Its `do_kv_cache_update()` uses only `transpose(1, 2)` without split (passes to `triton_reshape_and_cache_flash_diffkv`), so it does not use the cached views.

Also added cleanup of `_kv_cache_view_cache` in `_cleanup_profiling_kv_cache()` alongside the existing `_k_scale_cache`/`_v_scale_cache` cleanup, to release old KV cache storage promptly after profiling.
