# [Bugfix] Treat an empty label encoding as a ValueError in decisions init

[Upstream PR](https://github.com/vllm-project/vllm/pull/63515) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Fixes #63474. If the tokenizer encodes every label to `[]`, `reply_label_ids` now raises the `ValueError` it already documents instead of an `IndexError`. `init_decisions_state` catches that `ValueError` and disables the decisions endpoints, so the API server no longer crashes at startup.

## Claims

- A checkpoint whose tokenizer encodes everything to nothing (e.g. tokenizer files missing after an interrupted download) no longer crashes the API server in `init_decisions_state`. It falls back to the existing "no decisions strategy" path.
- Label ids are unchanged for every tokenizer that produces a non-empty encoding: the new check only fires when `extended == []`.

## Validation

New CPU test `test_empty_encoding_is_not_a_label` in `tests/entrypoints/generate/structured_decisions/test_strategies.py`. It uses a stub tokenizer that encodes to `[]`, with a prompt made only of an added token, so the tail is empty too.

- On current main (`e7473bf68`), without the fix, the test fails with the error from the issue:
  ```
  >           if extended[:-1] != tail or extended[-1] in ids:
  E           IndexError: list index out of range
  vllm/entrypoints/openai/decisions/strategies.py:232: IndexError
  ```
- With the fix: `pytest tests/entrypoints/generate/structured_decisions/test_strategies.py` → 82 passed. Run on CPU (`CUDA_VISIBLE_DEVICES=""`).
- `pre-commit run --files <changed files>`: all hooks passed, including ruff and mypy.

**Startup path with a real broken checkpoint (CPU).** I took `Qwen/Qwen3-0.6B`'s `config.json`, deleted tokenizer files, loaded the tokenizer with vLLM's `get_tokenizer`, and ran `init_decisions_state` as the API server does once the engine is up. Only the engine client is a stub, since the crash happens after the engine has loaded. transformers 5.20.2, tokenizers 0.23.3:

| Tokenizer files kept | Tokenizer load | main | this PR |
|---|---|---|---|
| `tokenizer_config.json` only | loads, `encode("A") == []` | **`IndexError`, startup crashes** | `init_decisions_state` returns `None`, startup continues |
| `merges.txt` only (the issue's case) | `ValueError` at tokenizer init | fails before decisions init | same |
| `merges.txt` + `vocab.json` + `tokenizer_config.json` | normal | `NextTokenStrategy` | `NextTokenStrategy` (unchanged) |

The reporter's transformers version may build a tokenizer from `merges.txt` alone, which would explain the difference.

- main: weights load, CUDA graphs are captured, `init engine ... took 27.96 s`, then the API server exits with code 1:

## Details

Root cause: `extended[:-1] != tail or extended[-1] in ids`. When `tail` is non-empty, an empty `extended` already makes the first comparison true and the `ValueError` is raised. When `tail` is also empty (the prompt ends in an added token, and the broken tokenizer still knows its added tokens), `[] != []` is false, so `extended[-1]` is evaluated and raises `IndexError`. `init_decisions_state` only catches `ValueError`.

I kept the fix to the guard rather than broadening the `except` in `init_decisions_state`, so unrelated `IndexError`s are not silently swallowed. The reporter's suggestion of a tokenizer-files sanity check at startup would catch this earlier, before weights load, but it is a broader change to tokenizer loading and is left out of this PR. If maintainers think it is worth doing, I can open a separate PR that checks for an empty encoding right after the tokenizer is loaded.
