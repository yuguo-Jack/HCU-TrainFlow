# [Bugfix][HiSparse] Resolve MTP verification rows with a union residency kernel

[Upstream PR](https://github.com/vllm-project/vllm/pull/59235) · state: closed · merged: True

## Original PR description

## Purpose

Resolve all of a request's MTP verification rows with one union residency kernel, on every sparse MLA backend, and drop the fragile routing that worked around the old kernel.

The old `hisparse_resolve_residency_kernel` ran one block per row, but `device_global_indices` and the LRU are per request, so two rows of one request in one launch could claim the same free slot and read each other's KV. Callers avoided that by resolving verification one step per launch (FlashMLA, FlashInfer TRTLLM) or by treating it as prefill (backends without `hisparse_supports_multi_token_decode`). On FlashAttn sparse MLA a FULL CUDA graph froze that prefill path's residency check at capture, so replays with spilled pages still hit the race. Found via #59036's CI failure (`test_hisparse_spill_and_prefix_restore`).

## Changes

- **Union kernel.** Each request's first-row block resolves all its rows: one hash-table union of host misses, one LRU walk, eviction slots in deterministic (row, top-k) order, one LRU rewrite. Each host row is copied once per request; a reused slot counts as a hit. The table is sized from `max_decode_query_len * index_topk` (~90 KB for GLM-5.3 + MTP3, MTP ≤ 9 at `index_topk=2048`), checked at startup; a union past that bound traps.
- **One routing path.** Verification resolves in one `swap_in` per layer, and `hisparse_supports_multi_token_decode` is removed, so every backend keeps verification as decode. Request ids (with CUDA-graph padding rows masked) live in a group-owned buffer, since the resolver reads them on the copy stream.

## Test Plan

- New `test_hisparse_speculative_rows_resolve_host_misses_consistently` (disjoint, overlapping, and multi-pass rows) plus unit tests for hit counting, union-bound sizing, the startup check, spec-as-decode, and padding/request-id handling.
- HiSparse kernel, sparse MLA backend, and e2e tests; #59036 applied on top.
- GLM-5.3-NVFP4 + MTP3 on B200 (FlashInfer TRTLLM, HiSparse under spill pressure), and a layer-level benchmark on H100.

## Test Result

- Race test fails 30/30 on main's kernel and passes with this PR; HiSparse tests pass (H100, H200, B200); `test_hisparse.py` passes, also with #59036.

File: `csrc/libtorch_stable/hisparse_kernels.cu` · line None

The union hash table gets `hot_size + 1` entries, so its shared memory scales with `device_buffer_size` (~10 B per slot) rather than with how many rows a request actually resolves. With the 227 KB per-block limit, any `device_buffer_size` above ~22k now errors on the first forward, even with spec decode off.

Example: `index_topk=2048`, `device_buffer_size=32768` (allowed by the config) used ~104 KB on main and needs ~340 KB here.

A request's union can never exceed `max_decode_query_len * top_k`. Could we size the table from that bound (passed in from Python) instead of `hot_size`, and check the shared-memory requirement in `ResolvedHiSparseConfig` so an oversized config fails at startup?

File: `csrc/libtorch_stable/hisparse_kernels.cu` · line 447

Defensive nit: this probe loop only terminates if the union fits in `hot_size`. That holds on the decode path (`hot_size >= Q * top_k` is enforced), but multi-row callers also include the resident-prefill path, and nothing in the kernel checks the bound. If it's ever violated, this spins forever and hangs the GPU, and `s_lru_out[hot_size - 1 - m]` goes out of bounds. Could we cap the probe count, or check the union size, and fall back to invalid or `__trap()`?
