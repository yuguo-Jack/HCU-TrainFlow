# [Bugfix] Gate the FA4 masked-MHA sparse prefill on prefill-query quantization, not KV cache dtype

[Upstream PR](https://github.com/vllm-project/vllm/pull/60806) · state: open · merged: False

## Original PR description

## Description

`_is_masked_mha_available` rejects the FA4 masked-MHA sparse prefill whenever the KV cache is quantized: `fa_version == 4 and not is_quantized_kv_cache(kv_cache_dtype)`. That conflates the KV cache dtype with the prefill query dtype. The masked path never reads FP8 KV as FP8: context rows go through the same `gather_and_maybe_dequant_cache` the dense path already uses, and the suffix K/V are the current step's bf16 projections. An FP8 prefill query is what the kernel cannot consume, and for NoPE-dims models like GLM-5.3-Flash it is unreachable anyway: no prefill backend supports the `(256, 0, 256)` dims for prefill query quantization, so the query is always bf16. As the gate stood, every prefill token past 2048 context rode per-token sparse MQA with topk random KV gathers, inside the regime where the measured threshold table already routes masked MHA ahead of MQA.

This gates on the actual prefill-query quantization state instead. `fp8_ds_mla` / `nvfp4_ds_mla` and the other packed byte formats stay excluded via an explicit dtype allow-list, the HiSparse routing is untouched, and with no config present the gate stays conservative-off for quantized dtypes, preserving current behavior.

| config | before | after |
|---|---|---|
| GLM-5.3-Flash: fp8 KV, FA4, prefill q bf16 | masked-MHA vetoed, per-token sparse MQA for all prefill past 2048 ctx | masked-MHA eligible |
| fp8 KV, prefill query quantization on + backend supports it | vetoed | vetoed (unchanged) |
| fp8_ds_mla / nvfp4_ds_mla / e5m2 / per-token-head / nvfp4 KV | vetoed | vetoed (dtype allow-list) |
| auto / f16 / bf16 KV | unchanged | unchanged |
| fa3 / non-SM100 | unavailable | unavailable |

Draft until the unlocked path is run end-to-end with an FP8 KV cache; the table above is code-verified but not yet executed.
