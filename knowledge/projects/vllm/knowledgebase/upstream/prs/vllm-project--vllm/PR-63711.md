# [CPU][Zen] Enable Laguna MoE on Zen CPU via grouped W8A16 (DA8W8)

[Upstream PR](https://github.com/vllm-project/vllm/pull/63711) · state: open · merged: False

## Original PR description

## Overview

Enables quantized **Laguna** (`LagunaForCausalLM`) MoE inference on the Zen CPU backend. Laguna INT4 checkpoints mix grouped int4 and grouped int8 experts across their layers and route with ungrouped sigmoid scoring, neither of which the Zen CPU WNA16 path added in #54024 could handle, so the model previously could not load on it. This extends that path to grouped **W8A16** (DA8W8).


## Test Plan
```bash
lm_eval --model vllm \
  --model_args pretrained=$CKPT,dtype=bfloat16,max_model_len=4096 \
  --tasks gsm8k --num_fewshot 5 --batch_size auto \
  --apply_chat_template --gen_kwargs max_gen_toks=2048
```

```bash
vllm bench throughput --model $CKPT --dtype bfloat16 \
  --random-input-len 1024 --random-output-len 1024 \
  --num-prompts 256 --max-num-seqs <8|32> --max-model-len 2176 \
  --no-enable-prefix-caching --seed 0
```

Unit tests. tests/kernels/quantization/test_zen_da8w4.py and tests/kernels/moe/test_cpu_fused_moe.py

## Test Result

**Accuracy.** Laguna INT4 on AMD EPYC 9005 (Turin), 32 cores, bf16 activations, `VLLM_CPU_INT4_W4A8=1`. The checkpoint carries two compressed-tensors groups — `num_bits=4` over layers 1-30 and `num_bits=8` over layers 31-39, both `group_size=128`, symmetric, `strategy=group`.

| gsm8k | 5 | flexible-extract | exact_match | 0.9022 ± 0.0082 |
| gsm8k | 5 | strict-match | exact_match | 0.8916 ± 0.0086 |

**Throughput.** Same pod and build, 1024 in / 1024 out, 256 prompts.

Admitting MiniMax2 routing relies on process_weights_after_loading copying scoring_func and renormalize off the layer, but only the compressed-tensors method calls that hook. AutoGPTQMoEMethod._setup_kernel (auto_gptq.py:691) never does, and a sym GPTQ int4/int8 checkpoint maps to kInt4Static/kInt8Static, so it picks ZEN_CPU first. For a GPTQ checkpoint of Laguna or MiniMax-M2 on Zen with the default VLLM_CPU_INT4_W4A8=1, apply() then routes with softmax and renormalize=False, and the correction bias is ignored. On main this config failed at load because neither Zen nor CPUExpertsInt4 accepted MiniMax2; now it silently serves wrong output. I ran select_experts with these defaults against the layer's real config (64 random tokens, 128 experts, top-8): no token got the same expert set, and the weights summed to 0.30 instead of 1. Could you add the compressed-tensors hook call to AutoGPTQMoEMethod._setup_kernel, or derive these defaults from moe_config.routing_method so a missed hook can't fall back to softmax?
