# [Bugfix][Model] Bailing MoE: keep fp32 router logits for expert selection

[Upstream PR](https://github.com/vllm-project/vllm/pull/63836) · state: open · merged: False

## Original PR description



## Overview

With `router_dtype: "fp32"` (every Ling/Ring 2.0 and 2.5 config), `BailingMoE` and `BailingMoeV25` compute the router GEMM in fp32 and then cast the logits to bf16 before sigmoid, `expert_bias` and grouped top-k. This PR removes that cast, as #56034 did for Sarvam.

## Claims

- With `router_dtype: "fp32"`, `FusedMoE` now receives fp32 router logits. Its routing was already configured for them (`router_logits_dtype=self.router_dtype`).
- On `inclusionAI/Ling-mini-2.0`, vLLM's expert selection matches the reference router for all tokens. On main, 2.0–4.1% of tokens per MoE layer get a different expert set.
- With `router_dtype` bf16 or unset, nothing changes: the cast was a no-op there.
- No new kernels; one cast op fewer.

## Validation

**Unit test**, `tests/models/test_bailing_moe_router_dtype.py` (CPU, no checkpoint):

```

```

It was run against a vLLM build at 74340c7, whose `bailing_moe.py` and `bailing_moe_linear.py` are identical to this PR's base (3e75ccb). For "with this PR", the same build had the two cast lines removed.

**Routing compared with the reference router.** The first 4 layers of `inclusionAI/Ling-mini-2.0` (256 experts, 8 groups, 4 kept, top-8) ran in vLLM (bf16, eager) on 8192 tokens: 4 x 1024 of wikitext-2 and 4 x 1024 of Python source. At each MoE layer, the gate input and the experts vLLM selected were recorded and compared with the reference router (`modeling_bailing_moe_v2.py`: fp32 GEMM, fp32 sigmoid + `expert_bias`, grouped top-k) on the same inputs.

| MoE layer | max abs logit error from the cast | tokens with a different expert set, main | with this PR |
|---|---|---|---|
| 1 | 0.031 | 4.14% | 0.00% |
| 2 | 0.016 | 2.04% | 0.00% |
| 3 | 0.031 | 2.72% | 0.00% |

Most affected tokens have one of their 8 experts swapped. On main, re-running the same vLLM router on fp32 logits (`F.linear(x.float(), W)`) also gives 0.00%. The grouped top-k kernel already works in fp32, so the cast is the only source of the difference.

Environment: vLLM 74340c7 (0.32.1rc1.dev534), torch 2.14.0+cu130, RTX 5070 Ti (sm_120).

## Details

**Root cause.** `router_logits, _ = self.gate(hidden_states)` returns logits in `router_dtype`, and `FusedMoE` is built with `router_logits_dtype=self.router_dtype`. The next line, `router_logits = router_logits.to(hidden_states.dtype)`, rounds them to bf16 before routing. vLLM pays for the fp32 GEMM and then discards its precision.

**Impact.**
- Ling/Ring 2.0 and 2.5 route 2–4% of tokens per MoE layer differently from the reference. The difference grows in later layers, because they see changed hidden states.
- RL pipelines that train with the HF reference (fp32 router) and sample with vLLM get those tokens routed off-policy.

**Tradeoffs.**
- Performance: the GEMM was already fp32, one cast kernel goes away, and top-k reads fp32 logits.
- The MoE backend is already selected for fp32 logits through `router_logits_dtype`, so no kernel sees a dtype it does not support.

**Not a duplicate.** I found no open or closed vLLM PR or issue about the Bailing router cast. Searched: "bailing", "bailing router", "bailing fp32", "Ling router logits", "bailing router_dtype". #56034 made the same change for Sarvam only. SGLang has the same cast in its Bailing gates; there, sgl-project/sglang#38719 addresses it.

**Limitations.**
- No model accuracy eval (lm_eval / GSM8K) was run: the full Ling-mini-2.0 (16B) does not fit on the 16 GB GPU used here. The routing comparison above covers the first 4 layers.
- The unit test stands in for `GateLinear` and the `FusedMoE` factory, and patches the TP helpers. `tests/AGENTS.md` asks for real objects and a `vllm_runner` regression test.
- CI: the test is added to the CPU step `basic-models-test-other-cpu` in `.buildkite/test_areas/models_basic.yaml`, next to the other block-level model tests.
