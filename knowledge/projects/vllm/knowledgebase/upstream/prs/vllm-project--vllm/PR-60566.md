# [MRV2][Perf] Screened lm_head

[Upstream PR](https://github.com/vllm-project/vllm/pull/60566) · state: open · merged: False

## Original PR description

## Purpose

Opt-in `--screened-lm-head`: when sampling only reads the top-k logits (greedy, or temperature with top-k <= 32 and optional top-p, e.g. Qwen's default `temperature=1.0, top_k=20, top_p=0.95`), compute them from an FP8 screen of the lm_head plus exact logits for the few rows the screen cannot rule out. Same tokens for the same seed, about half the lm_head bytes. Qwen3.8-Flash-Next on DGX Spark: +7.7% decode greedy, +6.2% at Qwen's default sampling (c=1, no speculative decoding).

- An FP8 copy of the lm_head scores every row, with a rigorous per-row error bound (FP8 error plus fp32 accumulation error of both GEMMs, computed in fp64 at load).
- A row more than one output ulp below the k-th best lower bound can neither enter nor tie the full head's top k. The rest (greedy: 15 rows per token on Flash-Next, top-20: about 1,200) get exact BF16 logits, the others `-inf`.
- Three Triton kernels, no host sync. Other batches (logprobs, penalties, logit bias, min-p, structured outputs, top-k > 32) use the full head. Unsupported setups (quantized or TP-sharded lm_head, LoRA, custom samplers, `VLLM_BATCH_INVARIANT`, pre-SM89) raise at load.

**Scope:** the gain needs the lm_head to be a large share of the step (DGX Spark, Jetson Thor, RTX). On GB200/GB300 it is neutral to slightly negative, so it is opt-in.

Exactness (both heads on the same hidden states):
- Offline, 10,572 real Flash-Next rows at batch widths 1 to 64 plus 1,024 adversarial near-ties: 0 argmax mismatches; for top-20, 0 true top-20 rows screened out.
- Live, 1.36M greedy and 353k sampled rows: 0 true top-k rows screened out. 12 greedy argmax flips, all sub-ulp ties on a BF16 rounding midpoint where the screened value was the correctly rounded one.
- Kept logits differ from cuBLAS in 0.047% of entries, 99% of those by one BF16 ulp (summation order), as with any GEMM change.
- `pytest tests/v1/worker/test_gpu_screened_head.py`: 21 passed on GB10 and GB200.

## Details

- Not the platform W8A16 kernels: the bound needs the screen's own arithmetic (fp32 accumulation of the stored FP8 values) fused with per-block maxima. A rank-256 SVD bound rules out almost nothing (flat spectrum); a fused select+exact kernel was 2% to 9% slower.
- Weight updates (`reload_weights`, weight transfer including draft updates) rebuild the FP8 copy; it lives in the weights memory pool for sleep mode.
- Memory: an FP8 copy of the lm_head (+0.64 GB on Flash-Next) plus `min(max_num_seqs * (k + 1), 64) x vocab x 8` bytes, allocated at load.
- Stock Flash-Next is not deterministic run to run on this stack (32/352 identical texts between two stock runs), hence exactness on shared hidden states rather than output texts.

Not a duplicate: #55494 packs the BF16 lm_head losslessly (0.77x bytes) for single-token decode and any sampling; this reads about 0.5x for greedy and top-k sampling and covers spec-decode verify widths.

AI assistance (Claude) was used to write and test this change; I reviewed every line and ran the tests and benchmarks above.

Its median TTFT is also about 10% higher at c=1 (46.0 to 50.5 ms, greedy and sampled alike, every screened boot above every stock boot) and 2% higher at c=4, while the 35B's TTFT moves by under 2% either way, less than its stock boots vary. The bench prompts are random token ids, and I haven't profiled any of this.

Greedy output: on 8 fixed text prompts (one at a time, temperature 0, 256 tokens with `ignore_eos`), the screened head's texts matched stock's on both models once both arms ran the same compiled backbone. My first run showed the 35B's screened texts differing from stock in 6 of 8 prompts, but that came from my setup: each arm compiled into its own compile cache (`VLLM_CACHE_ROOT`), and Inductor's autotuner picked different block sizes for three fused add+RMSNorm reductions in the 35B's two caches (1024, 1024 and 256 screened, 512 each stock), so the arms summed those norms in a different order.

In a rerun, every boot got a fresh copy of one arm's cache, and each arm (stock, screened) ran twice on each cache. On the screened arm's cache, both stock boots and both screened boots produced the first run's screened texts; on the stock arm's cache, both screened boots and one stock boot produced the texts of the first run's stock boots 1 and 2. The other stock boot there differed in one prompt from character 794 of 1122 on, run-to-run variation like the first run's stock boot 3 (one prompt, from character 1222). Both of those variations were on stock boots; all seven screened boots (three in the first run, four in the rerun) matched their cache's texts. On the 8B both caches made the same picks for every reduction (only one elementwise kernel's differs), and all its texts match.

The speed numbers in this review are from that first run, so each arm there ran its own cache's picks (8 of the 35B graph's 18 autotuned kernels differ, 1 of 8 on the 8B), and I didn't rerun the bench cells on shared caches. Each rerun boot's warm-up, 4 greedy requests at c=4 with the same random 512 in / 256 out, gives the same median ITL per arm on both caches (stock 6.24 to 6.26 ms, screened 5.94 to 5.99 ms), so the picks don't explain the c=4 greedy gap; c=1 and the sampled cells weren't rechecked.
