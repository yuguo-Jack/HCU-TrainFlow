# [Bugfix][Build] Keep the plain CUDA arch when the source list has its suffixed variant

[Upstream PR](https://github.com/vllm-project/vllm/pull/64332) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

`cuda_archs_loose_intersection()` in `cmake/utils.cmake` dropped a plain source architecture when the same base was also present in the source list as an arch-specific (`a`) or family (`f`) variant, so an explicitly requested plain arch was narrowed to the exact minor version of the suffixed target. This keeps the plain arch, consistent with the symmetric pass fixed in #56549, and emits the result in ascending order.

Related: #56548 (a dropped plain arch left vLLM with `sm_100a`-only cubins, which do not run on a CC 10.3 device), #56549 (the symmetric pass of this function), #45260 (open item: add CMake unit coverage for the `10.0f` / `12.0f` / `12.1a` / `+PTX` cases), and the test-only #56582.

## Claims

- A plain arch that the source list provides is no longer dropped in favour of its suffixed variant: `cuda_archs_loose_intersection("7.5;8.0;8.6;9.0;9.0a" "8.0;8.9;9.0")` now returns `8.0;8.6;9.0;9.0a`, i.e. the function's own documented example, instead of `9.0a;8.0;8.6`.
- The exact-base pass now behaves like the symmetric pass fixed in #56549: the plain arch is preserved whenever the source list can provide it.
- The result is emitted in ascending order, so it is deterministic and matches the documented example.
- Adds CMake regression tests for the plain-arch case and for the family (`12.0f`), arch-specific (`12.1a`) and `+PTX` cases requested in #45260.

## Validation

Reproducer, run directly against the function:

```console
$ cat repro.cmake
cmake_minimum_required(VERSION 3.26)
include("cmake/utils.cmake")
cuda_archs_loose_intersection(actual "7.5;8.0;8.6;9.0;9.0a" "8.0;8.9;9.0")
message(STATUS "OUT=${actual}")
```

| | output |
|---|---|
| base commit | `OUT=9.0a;8.0;8.6` (plain `9.0` dropped) |
| this PR | `OUT=8.0;8.6;9.0;9.0a` |

New test fails on the base commit and passes with the fix:

```console
$ pytest -q tests/test_cmake_utils.py -k plain_arch          # base commit
E   CMake Error ... Expected '8.0;8.6;9.0;9.0a', got '9.0a;8.0;8.6'
1 failed, 4 passed
$ pytest -q tests/test_cmake_utils.py                         # with the fix
6 passed
```

Differential check of the selection result before and after this change, over every arch list currently used in the tree (25 component lists plus the 2 top-level supported lists in `CMakeLists.txt` and `cmake/external_projects/*.cmake`) crossed with 34 realistic target lists (plain, arch-specific, family and `+PTX` variants of the supported architectures), 918 combinations in total:

```text
identical: 761, order-only changed: 157, content changed: 0
```

No combination selects a different set of architectures; only the emission order changes (which does not affect the generated `-gencode` flags).

CI coverage: the existing CPU Buildkite job in `.buildkite/test_areas/misc.yaml` runs `pytest -v -s test_cmake_utils.py` and already lists `cmake/utils.cmake` in its `source_file_dependencies`, so the new tests run in CI. No GPU is required; the tests shell out to `cmake -P`.

Limitations: validation was done on CPU with CMake 4.4.4. No CUDA wheel was rebuilt and no GPU run was performed, since the change only affects the CMake architecture selection, and the selected architectures for all arch lists currently used by vLLM are unchanged.

## Details

Root cause: the exact-base pass removed the plain target (`${_base}`) from the target list as soon as a suffixed source entry matched it, even when the source list could also provide the plain arch. The plain source entry was then left unmatched and silently disappeared from the result, so the build narrowed from the plain architecture to the exact minor version of the suffixed target (for example `sm_100a` instead of `sm_100`, which does not run on a CC 10.3 device). This is the same failure mode as #56548, which was fixed for the symmetric pass in #56549 but not for the exact-base pass.

The fix mirrors #56549: the plain target is only dropped when the source list cannot provide the plain arch. The result is additionally sorted so that it is deterministic and reproduces the documented example of the function.

```cmake
-        list(REMOVE_ITEM _TGT_CUDA_ARCHS "${_base}")
+        if (NOT "${_base}" IN_LIST _SRC_CUDA_ARCHS)
+          list(REMOVE_ITEM _TGT_CUDA_ARCHS "${_base}")
+        endif()
```
