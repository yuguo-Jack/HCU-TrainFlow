# [Model] Enable torch.compile and CUDA graphs for EmbeddingGemma2

[Upstream PR](https://github.com/vllm-project/vllm/pull/61572) · state: closed · merged: True

## Original PR description



## Overview

Enable `torch.compile` and CUDA graphs for EmbeddingGemma2 by adding `@support_torch_compile` to `EmbeddingGemma2TextModel`, the same way `Gemma3Model`, `Gemma4Model` and `BertModel` are compiled. This compiles the text backbone only; the multimodal encoders are untouched, and the encoder `TODO(lucianomartins)` from #60254 stays.

## Claims

- EmbeddingGemma2 now runs with piecewise compilation and CUDA graphs instead of eagerly.
- Single-query latency drops from 49.8 ms to 10.6 ms on A100-80GB (4.7x) and from 48.8 ms to 15.5 ms on L40S (3.1x); batch throughput rises 61% and 21%.
- Embeddings are unchanged: cosine similarity to sentence-transformers is 0.9998 at minimum before and after.

## Validation

Same vLLM build on both sides: nightly image `cu134-nightly-5555a2d` (its `embedding_gemma2.py` is identical to main), with and without this file. Model `google/embeddinggemma-2`, bf16, `--runner pooling`, `max_model_len=8192`, multimodal limits set to 0. Offline `LLM.embed`, 86 real queries (~20 tokens) and 1,495 document chunks from a RAG corpus, after 20 warm-up calls.

| GPU | | one query p50 / p95 (ms) | throughput (chunks/s) | cos vs sentence-transformers (min / mean) | engine startup (s) |
|---|---|---|---|---|---|
| A100-80GB | before | 49.75 / 52.50 | 333.8 | 0.99959 / 0.99993 | 57.9 |
| A100-80GB | **after** | **10.57 / 12.85** | **537.6** | 0.99982 / 0.99993 | 138.4 |
| L40S* | before | 48.77 / 56.24 | 382.5 | 0.99970 / 0.99993 | 48.7 |
| L40S* | **after** | **15.54 / 17.75** | **464.7** | 0.99978 / 0.99993 | 159.9 |

\* L40S has 99 KiB of opt-in shared memory per block, so EmbeddingGemma2 cannot start on it today (#60847). Both L40S rows include the tile fix from #60848, which is independent of this change.

Existing tests, A100-80GB, before and after:

```
EG2_MODEL_PATH=google/embeddinggemma-2 pytest -v tests/models/multimodal/pooling/test_embedding_gemma2.py
```

On the unmodified build (A100-80GB): 18 passed, 3 skipped (media assets not in the repo), 2 failed: `test_instance_attribute_access` and `test_video_loader_real_video`. Both fail without this change, so they are pre-existing in that environment. A run on the patched build was started and stopped early to save GPU time; text parity on the patched build is covered by the table above (cosine >= 0.9998 against sentence-transformers, above the test's 0.999 threshold). These tests need `EG2_MODEL_PATH` and are skipped in CI.

## Details

Root cause: `EmbeddingGemma2TextModel` was never decorated, so the model provides no compiled submodule and vLLM logs `Cudagraph mode PIECEWISE requires piecewise capture, but the loaded model provides neither a compiled submodule nor breakable CUDA graphs. Overriding to NONE.` A torch.profiler trace of one ~20-token query (transformers, L40S) shows why that matters for this model: 2,453 CUDA kernels per forward (24 layers with per-layer embeddings, q/k/v norms and two attention head sizes), with the GPU busy for 4.8 ms of a 49 ms forward. The same forward captured as a CUDA graph takes 5.6 ms. The model is launch-bound, not compute-bound.

The text backbone's `forward(input_ids, positions, inputs_embeds)` takes only model-runner tensors and has no data-dependent control flow, so the default decorator applies as is. The vision, audio and video towers stay eager and outside the compiled region. Compiling them or capturing them as encoder CUDA graphs (`compile_mm_encoder` / `SupportsEncoderCudaGraph`, as `gemma4_mm.py` does) is the separate encoder TODO, not part of this change.

Tradeoffs: engine startup grows by about 80-110 s for compilation and graph capture (first start; the compile cache shortens later starts), plus the memory for captured graphs. `--enforce-eager` restores the previous behaviour.

Not a duplicate: no open PR adds compilation for this model (searched `EmbeddingGemma2` and `embedding_gemma2` in PRs). #60848 and #60942 fix the separate shared-memory crash on 99 KiB GPUs.
