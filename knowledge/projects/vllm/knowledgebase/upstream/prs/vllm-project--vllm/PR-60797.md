# [Bugfix][Mamba] Store conv_kernel - 1 inputs in Mamba2 prefill checkpoints

[Upstream PR](https://github.com/vllm-project/vllm/pull/60797) · state: closed · merged: True

## Original PR description



## Overview

With speculative decoding, the Mamba2 prefill checkpoint (added in #57329) stored conv inputs that were `num_spec` tokens too old. After a prefix-cache restore from that checkpoint, the model read stale conv inputs for its first new tokens and could give a wrong answer. This PR stores only the `conv_kernel_size - 1` inputs that the conv readers use.

## Claims

- Fixes wrong outputs after a prefix-cache hit that restores from a Mamba2 internal prefill checkpoint when MTP or another speculative method is on.
- No change without speculative decoding: then `conv_state.size(-1)` already equals `conv_kernel_size - 1`.
- No change to cache layout, KV capacity or speed.

## Validation

**Unit test.** `test_store_selects_the_checkpoint_from_all_chunk_states` now runs with `spec_slots` 0 and 3. It checks that the first `state_len` slots hold the newest inputs and that the spec slots stay untouched. All 8 tests in the file pass on GPU with the fix. With the old `store_prefill_checkpoint`, both `spec_slots=3` cases fail and both `spec_slots=0` cases pass.

**End to end.** A Mamba2 hybrid model with one MTP layer, `--enable-prefix-caching --mamba-cache-mode align --prefix-match-unit 16 --enable-mamba-shared-prefix-checkpoint`, FP8 KV cache, temperature 0, thinking off. These three files are identical at the tested commit and at current `main`.

- **Resend test:** a ~71k-token prompt (a record table; the task copies records 100-160) sent 3 times. Sends 2 and 3 restore 16-31 tokens before the end, on the question.
- **Block-boundary test:** a ~11.6k-token prompt whose key digits sit right before a 4,544-token (4,416 with 5 draft tokens) block boundary, so the restore lands at that boundary.
- **Wrong** = a copied record differs from the source table.

| Setup | Test | Wrong before | Wrong after |
|---|---|---|---|
| 7 draft tokens | resend, 24 resends | 8 / 24 | 0 / 24 |
| 7 draft tokens, default `--prefix-match-unit` | block boundary, 12 resends | 10 / 12 | 0 / 12 |
| 5 draft tokens, probabilistic drafting | resend, 24 resends | 6 / 24 | 0 / 24 |
| 5 draft tokens, default `--prefix-match-unit` | block boundary, 12 resends | 12 / 12 | 0 / 12 |
| P/D disaggregated (NIXL), 7 draft tokens | resend, 24 resends | 13 / 24 | 0 / 24 |

- First sends (no cache hit) were wrong 0 times before and after, and gave the same text before and after.
- All 270 sends restored at the predicted token count, so the tests went through the restore path.
- Controls before the fix: prefix caching off gave 0 / 24 wrong; speculative decoding off gave 0 / 24 wrong.
- KV cache size and resend latency did not change.

## Details

**Root cause.** With speculative decoding the paged conv state has `conv_kernel_size - 1 + num_spec` slots (`mamba_utils.py`). `store_prefill_checkpoint` set `state_len = conv_state.size(-1)` and wrote inputs `[ckpt - state_len, ckpt)` into slots `0..state_len-1`, oldest first. Every reader takes slots `0..conv_kernel_size-2` as the newest inputs:

- `causal_conv1d_fn` uses `state_len = KERNEL_WIDTH - 1`.
- `causal_conv1d_update` reads from slot `num_accepted_tokens - 1`, which is 0 for a restored request.

So slots `0..2` (conv kernel 4) held inputs that were `num_spec` tokens too old. `--prefix-match-unit 16` makes such restores frequent: the restore point lands 16-31 tokens before the prompt end. The default unit restores at block boundaries, which the same export also writes.

**Fix.** `store_prefill_checkpoint` takes a required keyword `state_len`, and its only caller passes `self.conv_kernel_size - 1`. `FlashKDAPrefillCheckpointExporter` already takes an explicit `state_len` for the same reason. The kernel keeps the physical strides, so both conv layouts (dim-first and the transposed view) work. The spec slots of the checkpoint block are not written. Nothing reads them before the next update rewrites all slots, and before this change they held no useful data either.

**Other paths checked.** The align-mode copies, the shared-prefix checkpoint, NIXL transfer and CPU offload copy whole conv rows or already use `conv_kernel_size - 1`. They need no change.

**Limitation.** This covers Mamba2 only. When `state_len` is unset, `FlashKDAPrefillCheckpointExporter` still falls back to the full conv width.
