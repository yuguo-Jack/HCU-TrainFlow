# [Spec Decode][Qwen3.5] RecoverSSM for Qwen3.5 / Qwen3-Next GDN

[Upstream PR](https://github.com/vllm-project/vllm/pull/61309) · state: open · merged: False

## Original PR description



## Overview

Follow-up to #58863 (stacked on it, only the last commit is new). #58863 adds RecoverSSM to the Qwen GDN layer but only turns it on for Qwen4Exp. Qwen3.5 and Qwen3-Next use the same layer, so this PR is mostly wiring the model classes + tests.

We serve a Qwen3.5-4B finetune with MTP, which is why I looked at this. On the public 4B checkpoint it's about +8.6% throughput at K=5 / c=32, with the same accept length and GSM8K.

## Claims

- Qwen3.5 (dense / MoE, CausalLM / ConditionalGeneration), Qwen3-Next, and their MTP drafters accept `--use-replayssm` with MTP and run the RecoverSSM verify/commit path.
- On `Qwen/Qwen3.5-4B` + its native MTP head (1× L40S, c=32): **+8.6% output throughput at K=5** (3 runs). Acceptance, GSM8K accuracy and greedy outputs are unchanged (details below).
- No change when `--use-replayssm` is off.

`ruff check` / `ruff format` are clean. `tools/pre_commit/mypy.py 3.11` on the changed files plus `qwen4_exp/nvidia/model.py` reports no new errors versus the #58863 head. It also clears one existing `[override]` error: Qwen4Exp's `get_mamba_state_dtype_from_config` is now compatible with the Qwen3.5 parent.

**End-to-end setup:**
- `Qwen/Qwen3.5-4B` with its native MTP head, BF16, 1× L40S.
- MRV2, `--mamba-cache-mode align --enable-prefix-caching --prefix-match-unit 16 --mamba-backend triton --attention-backend TRITON_ATTN`.
- Stock spec-decode kernels vs `--use-replayssm`; everything else identical.

Throughput, `vllm bench serve --dataset-name spec_bench` (480 prompts, 256 output tokens, temperature 0, c=32). Each run uses a fresh server after a 64-prompt warmup. Output tok/s:

| MTP K | Stock (3 runs) | RecoverSSM (3 runs) | Δ (mean) | Accept len (stock / RecoverSSM) |
|---|---|---|---|---|
| 5 | 2596 / 2561 / 2593 (mean 2583) | 2764 / 2844 / 2806 (mean 2805) | **+8.6%** | 3.931–3.940 / 3.933–3.938 |
| 3 | 2733 / 2494 / 2508 (mean 2578) | 2499 / 2791 / 2708 (mean 2666) | +3.4% (noisy) | 3.177–3.181 / 3.175–3.177 |

On v0.31.0 with a port of the same protocol we saw the same picture: +7.6% at K=5 and +10.1% at K=3 (3 runs each), no gain at c=1, and −3% at K=1. The gain comes from dropping the per-draft-position state write-back, so it grows with K and batch size. This matches the K=2 / c=1 note in #58863.

Accuracy, `tests/evals/gsm8k/gsm8k_eval.py` (1319 questions, 5-shot, temperature 0), MTP K=5:

| | GSM8K accuracy | Accept len |
|---|---|---|
| Stock | 0.773 | 4.193 |
| RecoverSSM | 0.771 | 4.193 |

The RecoverSSM GSM8K server ran with `VLLM_GPU_SYNC_CHECK=error` and completed without a sync error. That run's throughput is not comparable because of the debug mode.

<details>
<summary>Duplicate check, subclass opt-outs, state, what's not tested</summary>

- **Duplicate check:**
  - #58863 enables RecoverSSM only for Qwen4Exp.
  - The other follow-ups do not touch model enablement: #59982 (XPU), #59983 (PP) and #61017 (grouped commit).
  - Searching open PRs for "RecoverSSM" and "ReplaySSM Qwen3.5" found no other Qwen3.5 / Qwen3-Next work.
- **Model wiring** mirrors Qwen4Exp:
  - `SupportsReplaySSM` on the target classes and on the MTP drafters. The drafter's config shares the target's `cache_config`, so it must pass the support check too.
  - The architectures join the RecoverSSM list in `validate_mamba_cached_kernel`. As for Qwen4Exp, `--use-replayssm` on them requires speculative decoding, because the Qwen GDN layer has no plain ReplaySSM path.
- **Subclasses opt out:** `supports_replayssm` is a class attribute, so subclasses of the Qwen3.5 classes would inherit it. Three subclasses are outside the RecoverSSM list and now set `supports_replayssm = False` explicitly, so they keep rejecting `--use-replayssm` as before:
  - `InternS2PreviewForConditionalGeneration`
  - `InternS2MobiusMTP`
  - the AMD `Qwen4ExpForConditionalGeneration` (same architecture name as the NVIDIA one, which is on the list)

  `Qwen3_5ForCausalLMBase` itself does not declare support; its two Qwen3.5 leaves do, so `InternS2MobiusForCausalLM` is unaffected. A test pins the opt-outs.
- **State shape and dtype:** the model-level Mamba state gains the fp32 replay record `[HV, K+1, V+K+1]` exactly when the GDN layer does, which the new test checks for TP 1/2 and K 0/3/5.
  - `qwen3_next.py` and `qwen3_5.py` held three identical copies of the GDN state shape/dtype code; they now share one helper. Main code: +124 / −85 lines; tests: +119 / −10.
- **Not run end-to-end:**
  - Qwen3-Next and the Qwen3.5 MoE checkpoints, which need more GPU memory than we have. They share the same layer and helper and are covered by the unit tests.
  - TP > 1.
- **Observation for follow-up (not changed here):** with RecoverSSM, the replay record grows the Mamba page and therefore the attention block. On Qwen3.5-4B the block grows from 288 to 320 tokens at K=3 and to 352 at K=5. Prefix hits land on block multiples, so this can cost prefix reuse; see the discussion in #58863.

## Results: DSpark k=7 serves 17.5% more requests/s at concurrency 18 and 31% more at 27

Setup:

- **Model and drafter:** Qwen3.5-35B-A3B fine-tune, FP8, with a 5-layer DSpark head (sliding window 4096), `num_speculative_tokens=7`, no adaptive verification.
- **Hardware and parallelism:** 1x H100 80GB, TP1 with expert parallel.
- **Runner and caching:** MRV2, Triton mamba backend, prefix caching (align mode).
- **Limits:** `max_model_len=262144`, `max_num_seqs=160`.
- **Workload:** agentic computer-use trajectories replayed with aiperf, closed loop at fixed concurrency: 150 trajectories, 5,843 requests, 3 screenshots per request, turns back to back.

| Setup | req/s, c=18 | prefix-cache reads, c=18 | p50 latency, c=18 | req/s, c=27 | prefix-cache reads, c=27 | p50 latency, c=27 |
|---|---|---|---|---|---|---|
| No speculation | 1.646 | 81.6% | 5.86 s | 1.604 | 71.9% | 8.48 s |
| MTP k=3 (stock kernels) | 2.038 | 76.3% | 4.58 s | 1.445 | 42.5% | 9.76 s |
| DSpark k=7 (stock kernels) | 1.800 | 63.9% | 5.02 s | 1.328 | 29.4% | 11.53 s |
| DSpark k=7 + `--use-replayssm` | 2.115 | 76.9% | 4.24 s | 1.744 | 56.2% | 7.46 s |

All runs completed every request with 0% errors. Each point is a single run; repeated runs of the same configuration varied by about 2% in our setup.

Most of the gain comes from KV capacity. With stock kernels in align mode, each GDN layer keeps `2 + num_speculative_tokens + 1` state blocks per running request, so k=7 holds 10 states per layer where no speculation holds 3. On this model a state block is 2.25 MiB and there are 30 GDN layers, so each running request holds about 470 MiB more than without speculation. At concurrency 27 that is about 12.5 GiB of a 30.4 GiB pool, and the prefix-cache read rate falls from 72% (no speculation) to 29%.

With `--use-replayssm`, per-request GDN blocks drop from 10 to 3 per layer, while the replay buffer takes 1.2 GiB of KV memory at startup (32.57 → 31.34 GiB, sized by `max_num_seqs=160`):

| | DSpark k=7, stock kernels | DSpark k=7, `--use-replayssm` |
|---|---|---|
| KV memory available | 32.57 GiB | 31.34 GiB |
| Blocks per 262,144-token request | ~572 | ~535 |
| Logged GPU KV cache size | 1,355,308 tokens | 1,398,455 tokens |

The logged capacity spreads the per-request state over a single 262k-token request, so it shows only 3% of the change. The cache-read rates in the table above show the rest.

Acceptance: over the first 36 SpecDecoding log intervals, the two `--use-replayssm` servers accepted 3.59 and 3.49 tokens per step, against 3.48 for stock kernels. We have no full-run log for the stock run, so this is not a like-for-like comparison over the whole replay, and we did not compare outputs token by token.

Not included in this build:

- the prefix-cache fix for the first re-send of a prefix from #58863's comments, since main's checkpoint-position code has changed since that diff;
- the fix from #58863's comments for decode rows without drafts (K=0), which this PR routes through the RecoverSSM verify path; DSpark proposes drafts for every decode row in our workload, so we did not apply it.
