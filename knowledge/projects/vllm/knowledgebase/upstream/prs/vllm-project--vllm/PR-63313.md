# [Rust Frontend] Report every invalid logit_bias key like Python

[Upstream PR](https://github.com/vllm-project/vllm/pull/63313) · state: closed · merged: True

## Original PR description

## Overview

When several `logit_bias` keys are not token IDs, Python returns one 400 naming all of them. The Rust frontend stops at the first key that fails to parse, and since the request map is a `HashMap`, which key it reports is arbitrary. This PR reports every invalid key, and enables the Python test that pins it in the Rust frontend CI.

## Claims

- `logit_bias: {"bad1": 50.0, "bad2": 20.0}` on chat or completions returns one 400 with `param = "logit_bias"` naming both keys, in sorted order: `logit_bias contains key(s) that are not valid token IDs: ["bad1", "bad2"]. Token IDs must be non-negative integers.`
- `test_chat_logit_bias_validation.py::test_chat_logit_bias_multiple_non_integer_keys` now passes under the Rust frontend and runs in the Rust OpenAI Coverage step.

- Unit test `utils::tests::convert_logit_bias_reports_all_invalid_keys` uses keys `bad2`, `7`, `bad1` and `-1` and snapshots the error, which names `-1`, `bad1` and `bad2` in sorted order. With the old function it fails, naming only the first key the map yields. `convert_logit_bias_converts_valid_keys` covers the success path.
- E2E on one GB200 GPU, `vllm-rs` built from this branch, `VLLM_USE_RUST_FRONTEND=1`: `pytest entrypoints/openai/chat_completion/test_chat_logit_bias_validation.py`: 4 passed.

## Details

Python's `SamplingParams.from_optional` converts each key with `int()`, collects every failure, and raises one `VLLMValidationError` (`param="logit_bias"`). In Rust, string keys exist only in the OpenAI JSON wire format: gRPC carries a `map<uint32, float>` and `vllm-text` takes `HashMap<u32, f32>`. So the HTTP DTO lowering (`convert_logit_bias` in `rust/src/server/src/utils.rs`, shared by chat and completions) is the only consumer of string keys, and the existing function now collects errors instead of returning on the first.

Difference kept: a negative key such as `"-1"` passes Python's `int()` and is then rejected by the vocabulary check with a different message; Rust token IDs are `u32`, so Rust reports `"-1"` with the other invalid keys. Both are a 400 with `param = "logit_bias"`.

The second commit drops `-k "not multiple"` from the Rust OpenAI Coverage step in `.buildkite/test_areas/rust_frontend.yaml`.

Not a duplicate: no open PR changes Rust `logit_bias` validation.
