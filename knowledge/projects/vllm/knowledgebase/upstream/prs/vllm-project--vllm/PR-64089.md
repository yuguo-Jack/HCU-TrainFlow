# [ROCm][Kernel] Add AITER Triton MXFP8 linear kernel for CDNA4

[Upstream PR](https://github.com/vllm-project/vllm/pull/64089) · state: open · merged: False

## Original PR description

## Purpose

Add `AiterTritonMxfp8LinearKernel`, an MXFP8 (OCP MX, 1x32 E8M0 scales) dense linear
backend for gfx950 that calls AITER's Triton `gemm_afp8wfp8`. It is first in the
ROCm MXFP8 kernel list and claims only the `(N, K)` shapes AITER ships tuned
configs for; every other shape falls through to `RocmDotScaledMxfp8LinearKernel`
unchanged. Requires `VLLM_ROCM_USE_AITER=1`. With `--linear-backend aiter` it
takes every MXFP8 shape, untuned ones on AITER's default tile (slower than
`RocmDotScaledMxfp8LinearKernel`).

Depends on ROCm/aiter#7038 (tuned `GEMM-AFP8WFP8_A32_W1X32` configs). With
an AITER that lacks those configs, `can_implement()` returns False for every
shape and behaviour is identical to today.

## Changes

- `kernels/linear/mxfp8/aiter.py`: new kernel, gated on
  `rocm_aiter_ops.is_linear_enabled()`.
- `_aiter_ops.py`: `rocm_aiter_triton_mxfp8_gemm_dynamic_quant` custom op (dynamic
  activation quant via `mxfp8_e4m3_quantize`, then `gemm_afp8wfp8`) with a fake
  impl for torch.compile, the `rocm_aiter_ops.triton_mxfp8_gemm_dynamic_quant` wrapper,
  and `rocm_aiter_ops.is_triton_gemm_afp8wfp8_tuned(n, k)` (cached; returns False
  when AITER or the config family is missing).
- `kernels/linear/__init__.py`: register first for ROCm, and under
  `--linear-backend aiter` (which also takes untuned shapes).
- Disabled under `VLLM_BATCH_INVARIANT` (the tuned decode configs use split-K).

## Test Plan

- `pytest tests/kernels/quantization/test_mxfp8_kernel_selection.py` (CPU): ROCm
  selection prefers AITER only for tuned shapes, and takes every shape under
  `--linear-backend aiter`; rejects unaligned K / BMM; off under batch invariance.
- `pytest tests/kernels/quantization/test_rocm_mxfp8_linear.py` (gfx950): the
  dequant-reference test is now parametrized over `rocm_native` and `aiter`
  (DeepSeek V4.1 TP4 attention and MiniMax-M3.1 TP4 shapes, all tuned in AITER;
  M = 1 to 1024), plus
  a 3D input + bias test for AITER, and forced untuned shapes on AITER's default
  tile (M = 1 to 8193).
- Kernel microbenchmark vs `rocm_native` (CUDA-graph timing, activation quant
  included on both sides).
- End to end: MiniMax-M3-MXFP8, TP8 and TP4, MI350X, `vllm bench serve` random dataset;
  baseline = `VLLM_DISABLED_KERNELS=AiterTritonMxfp8LinearKernel`. Same A/B on
  DeepSeek-V4.1-Flash, TP4.
- Accuracy: gsm8k 5-shot via `lm_eval` local-completions, and GPQA-Diamond
  0-shot CoT via local-chat-completions, real weights, same A/B.

Known trade-off: TTFT for short prompts at high concurrency is higher on
MiniMax-M3 (TP8: up to +21% at 1024 tokens, conc 64; TP4: +14% at 1024
tokens, conc 1). Cause: prefill
batches above the CUDA-graph capture sizes run eagerly, and at M around 1024
these GEMMs are host-launch bound. Host time per call is about 72 us for
AITER (vLLM quant 18.5 + `gemm_afp8wfp8` 42) versus 41 us for `rocm_native`.
