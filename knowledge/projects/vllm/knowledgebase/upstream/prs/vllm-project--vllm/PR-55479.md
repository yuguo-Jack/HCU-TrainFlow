# [Bugfix][Frontend] Preserve Harmony refusal content parts

[Upstream PR](https://github.com/vllm-project/vllm/pull/55479) · state: open · merged: False

## Original PR description

## Purpose

Harmony parsers currently ignore OpenAI `type: refusal` content parts and only read `text`. A part like `{"type": "refusal", "refusal": "I can't help with that"}` is therefore converted to empty `TextContent`, so the model never sees the refusal string.

This maps refusal parts to Harmony `TextContent` using `refusal` with a fallback to `text`, matching Chat Completions / `chat_utils` / Cohere conventions. No new Harmony channel is introduced. Other non-text types are left unchanged.

Fixed sites:
- `parse_chat_input_to_harmony_message` in `vllm/entrypoints/openai/parser/harmony_utils.py`
- `_parse_harmony_format_message` and `_parse_chat_format_message` in `vllm/entrypoints/openai/responses/harmony.py`

## Why this is not a duplicate

Checked open PRs for "harmony refusal" / "refusal content". Nearby work is different:

- #49130 / #48237 reconstruct Responses *output* items and crash on empty/refusal `ResponseOutputRefusal` blocks in `responses/utils.py`.
- #28303 (closed) recovered malformed gpt-oss *model output* with newer `openai-harmony`.

None of those map inbound OpenAI refusal content parts onto Harmony `TextContent`.

APPROVE — verified locally against head 8e1b7c29 and base 28e605fb.

**Bug is real.** OpenAI refusal content parts (`{"type": "refusal", "refusal": "..."}`) were flattened with `c.get("text", "")` in the Harmony parsing paths, silently dropping the refusal string into an empty TextContent — the model never saw it (and an all-refusal message could collapse to an empty assistant turn).

**Fix verified.** New `text_from_content_part()` helper: refusal parts read `refusal` first, then fall back to `text` (the variant some producers emit), else `""`; non-refusal parts unchanged (`text` or `""`). Applied at all three content-list flattening sites: `parse_chat_input_to_harmony_message` (parser/harmony_utils.py), `_parse_harmony_format_message` and `_parse_chat_format_message` (responses/harmony.py). Ordering preserved — a mixed text+refusal array keeps both parts in sequence (asserted).

**Regression-proven:** 7/7 new tests FAIL on base 28e605fb (refusal dropped to empty text; mixed arrays lose the refusal part) / all PASS at head. The one new test that passes on both (`test_refusal_content_falls_back_to_text_field`) is a behavior-preservation lock — a refusal carrying `text` instead of `refusal` already worked pre-fix, and the helper keeps that working — correct to keep. Full touched test files: 193 passed at head vs 186 on base — the +7 are exactly the new tests; zero collateral.

**Non-blocking observation (sibling site):** `response_input_to_harmony` (responses/harmony.py:171) still flattens list content with `c.get("text", "")` for non-system/developer `type: message` input items. In practice that path serves Responses `input` items whose validated content parts are text/image/audio (`refusal` is an output-only construct per the OpenAI schema), so it is likely unreachable for refusals today — but for defense-in-depth and consistency, routing it through `text_from_content_part` too would close the class entirely. Not a blocker; worth a follow-up commit.

Otherwise clean, minimal, well-tested.
