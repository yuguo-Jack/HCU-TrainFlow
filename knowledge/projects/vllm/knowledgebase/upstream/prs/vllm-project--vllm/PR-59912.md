# [Bugfix] flashinfer_moe_ep_cutedsl: reject it without nvshmem4py and install nvshmem4py

[Upstream PR](https://github.com/vllm-project/vllm/pull/59912) · state: open · merged: False

## Original PR description

## Overview

Fixes #59903. `--moe-backend flashinfer_moe_ep_cutedsl` loaded the whole checkpoint and then failed with `ModuleNotFoundError: No module named 'nvshmem'`, because `nvshmem4py` isn't installed. This PR rejects the backend at selection when `nvshmem.core` isn't usable, and installs `nvshmem4py` on Linux: `nvshmem4py-cu13` on CUDA 13 builds, `nvshmem4py-cu12` on CUDA 12 builds. The CuTeDSL path on FlashInfer 0.7.0.post1 also needs #59900 (the #59887 fix), a separate PR that merges cleanly with this one; the test images below contain both.

## Claims

- **Selection check:** without a usable `nvshmem4py` (`nvshmem.core`), an explicit `--moe-backend flashinfer_moe_ep_cutedsl` is rejected when the backend is selected, before any checkpoint shard loads, with a reason naming the package. `flashinfer_moe_ep_mega_deep_gemm` doesn't need NVSHMEM and isn't affected by the check.
- **Dependency:** wheels and images depend on `nvshmem4py-cu13` (unpinned; Linux, Python < 3.14, since there are no cp314 wheels), so the resolver takes the newest release (0.4.0 as of 2026-10-10). CUDA 12 builds swap in `nvshmem4py-cu12` at the same three sites (`setup.py` and both Dockerfile blocks) that already rewrite `humming-kernels[cu13]`.
- **CUDA 12.9 resolution:** `nvshmem4py-cu12` caps `cuda-python` at 12.9, so the `cuda-python` metapackage resolves to 12.9.0. `cuda-bindings` (12.9.9, within torch cu129's `>=12.9.4,<13`), torch and `nvidia-nvshmem-cu12` (3.4.5, torch's pin) are unchanged.
- **Together with #59900:** in images built from this PR merged with #59900, the CuTeDSL backend needs no runtime install of `nvshmem4py`: kernel e2e tests and DEP serving pass on GB200 and GB300 (CUDA 13, including DEP=16 WideEP across 4 GB300 nodes) and 8× B200 (CUDA 12.9). The current-head serving runs also needed in-container workarounds for two unrelated `main` bugs (see Validation).

## Details

**Root cause.**
- **Where it's needed:** FlashInfer's CuTeDSL megakernel declares the runtime requirements `{TORCH_DIST, NVSHMEM}` (`cutedsl_runtime_requirements`). `MoEEpMegaLayer.__init__` → `bootstrap_moe_ep_runtime` → `_ensure_nvshmem` → `_init_nvshmem_after_dist` then does `import nvshmem.core`, and the kernel's comm shim also allocates its symmetric buffers through `nvshmem.core`.
- **Nobody declares it:** FlashInfer 0.7.0.post1 doesn't list `nvshmem4py`. 0.7.1 lists `nvshmem4py-cu13>=0.3.1` only in its `sm107` extra.
- **Nobody checks for it:** vLLM's `flashinfer_moe_ep_unsupported_reasons` didn't check for the package, so the oracle accepted the backend and the failure surfaced only in `process_weights_after_loading`.

**Fix.**
1. `has_nvshmem4py()` in `vllm/utils/import_utils.py`. A spec check keeps an absent package silent, and a trial import catches a broken native install.
2. A CuTeDSL-only unsupported reason in `flashinfer_moe_ep_unsupported_reasons`. The NVFP4/MXFP4 oracles turn it into a `ValueError` when the quant method is built.
3. The requirement in `requirements/cuda.txt`, which feeds both the wheel and the Docker image. The CUDA 12 paths rename it to `nvshmem4py-cu12`.

**Tradeoffs.**
- The requirement adds `nvshmem4py` (about 5 MB) plus `cython` to every Linux CUDA install on Python < 3.14, for an opt-in backend. If the build owners prefer a Docker-only install (like DeepEP) or an extra, it can be reduced to that, and the selection check stands on its own.
- It is unpinned, so new `nvshmem4py` releases (and any change to their `cuda-python`/`cuda.core` bounds) flow in automatically; `has_nvshmem4py()` checks that `nvshmem.core` imports, not its version. A release whose `nvshmem.core` fails to import makes the backend fail selection with the reason above; a release with conflicting bounds resolves to an older `nvshmem4py`. An API break would only show up when CuTeDSL runs on SM100, which CI does not exercise (the CPU test stubs `has_nvshmem4py()`, and the kernel e2e tests are skipped without SM100).
- `nvshmem4py` leaves `nvidia-nvshmem-cu1x` unpinned. torch 2.13 pins 3.4.5 for both CUDA majors, which is what was tested.
- On CUDA 12 the `cuda-python<=12.9` cap is harmless with torch cu129. Without the documented cu129 index, PyPI's default (CUDA 13) `torch==2.13.0` with `nvshmem4py-cu12` still resolves, but to `cuda-python==12.6.2.post1` plus an extra `nvidia-nvshmem-cu12` 3.8.0. A cu129 vLLM wheel on CUDA 13 torch is already a mismatched environment.
- FlashInfer documents `moe_ep` as CUDA 13 only, but its CuTeDSL MegaMoE path has no CUDA-version gate in 0.7.0.post1; the B200 runs above are the CUDA 12.9 evidence.
- CuTeDSL loads the newest toolkit flavor the driver supports. `nvidia-cudnn-frontend` (via FlashInfer) already pulls `nvidia-cutlass-dsl[cu13]` into CUDA 12.9 images, so on R580+ drivers CuTeDSL runs its `cu13` flavor there. At the current head the B200 runs used the `cu13` flavor; in the earlier B200 validation, the kernel e2e tests (8/8) and DEP=8 serving (GSM8K 0.894) also passed with only the `cu12` flavor present.
- The requirement can be dropped once FlashInfer declares the dependency for the backends vLLM uses.

**CI.**
- `requirements/cuda.txt`, `docker/Dockerfile` and `setup.py` trigger the full CI run. PR CI builds only CUDA 13 images; the CUDA 12 rename is exercised by the release CUDA 12.9 builds.
- `tests/models/test_deepseek_v4_fi_moe_ep.py`, including the new test, runs in `basic-models-test-other-cpu` (`.buildkite/test_areas/models_basic.yaml`). The kernel e2e tests need SM100 GPUs and are skipped in CI.
