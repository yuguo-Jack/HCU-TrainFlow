# [XPU] Work around Battlemage oneCCL IPC handle cache device-loss failures

[Upstream PR](https://github.com/vllm-project/vllm/pull/50887) · state: open · merged: False

## Original PR description

## Summary

Investigation for #50850.

This PR was originally intended to add a targeted XPU workaround for Intel Battlemage / Xe2 multi-GPU systems by automatically setting `CCL_ZE_CACHE_OPEN_IPC_HANDLES=0`.

Based on review feedback and additional testing, that approach is currently **blocked**. The setting appears to avoid one failure mode in some cases, but it may also introduce or expose a worker startup race when resources are constrained. Because of that, this PR should not be treated as a safe automatic fix in its current form.

It also does **not** explain or fix every failure reported in `#50850`, especially potential single-card failures such as `openai/whisper-large-v3-turbo`, which likely require separate investigation.

## Current status

This PR is now in **investigation / blocked** state rather than merge-ready.

The current evidence suggests there are at least two distinct problem paths that need to be separated:

- the original `UR_RESULT_ERROR_DEVICE_LOST` / startup failure path
- a constrained-resource worker startup race that appears when `CCL_ZE_CACHE_OPEN_IPC_HANDLES=0`

Until those are reproduced independently and understood clearly, automatically forcing `CCL_ZE_CACHE_OPEN_IPC_HANDLES=0` is not justified.

## What changed in this branch

- Added a small XPU utility helper that detects multi-GPU Battlemage/Xe2 device sets from the visible `torch.xpu` device names.
- Wired that helper into XPU platform config initialization so the branch can test automatic application of `CCL_ZE_CACHE_OPEN_IPC_HANDLES=0`.
- Added focused tests for:
  - Battlemage name detection
  - multi-GPU gating
  - preserving explicit user overrides
  - skipping non-Battlemage devices

These changes are useful for investigation, but they are not sufficient evidence that the automatic env-var change is correct to merge.

## Why this does not duplicate an existing PR

I checked for open upstream PRs tied to `#50850` and for open PRs covering this Battlemage/XPU IPC-handle behavior. I did not find an existing open PR addressing this specific line of investigation.

## Limitations

I do not have access in this environment to the original Linux Intel XPU Battlemage multi-GPU hardware stack, so I could not rerun the full model-level repro on actual B70 devices.

The validation above only covers the config seam and regression tests for the detection logic. It does **not** establish that automatically setting `CCL_ZE_CACHE_OPEN_IPC_HANDLES=0` is the correct production behavior.

## Next investigation steps

- Reproduce the original failure with default `CCL_ZE_CACHE_OPEN_IPC_HANDLES=1`
- Reproduce the constrained-resource startup race with forced `CCL_ZE_CACHE_OPEN_IPC_HANDLES=0`
- Hold model, TP configuration, and memory limits constant across both runs
- Determine whether the underlying issue is:
  - worker startup concurrency
  - compile/warmup-time resource contention
  - host memory pressure
  - XPU memory allocation ordering

When XPU serving uses `distributed_executor_backend="ray"` with `VLLM_USE_RAY_V2_EXECUTOR_BACKEND=0`, this assignment only changes the driver's environment. `RayDistributedExecutor` copies variables selected by `get_env_vars_to_copy()`, whose prefixes exclude `CCL_`, and `XPUPlatform.additional_env_vars` does not register this variable. Consequently, remote Ray workers initialize XCCL without the workaround and remain vulnerable to the Battlemage device-loss failure; register `CCL_ZE_CACHE_OPEN_IPC_HANDLES` for worker propagation.
