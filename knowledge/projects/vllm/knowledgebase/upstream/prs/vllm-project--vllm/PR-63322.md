# [ROCm][Perf] Muse Spark: column-shard the MoE pooler/unpooler over TP

[Upstream PR](https://github.com/vllm-project/vllm/pull/63322) · state: open · merged: False

## Original PR description



## Overview

On ROCm, the Muse Spark MoE pooler (8192 → 4096) and unpooler (4096 → 8192) are `ReplicatedLinear`, so at TP8 every rank reads both full BF16 weights on every step: 134 MB per layer, about 8.3 GB per forward over the 62 layers. This PR makes both projections `ColumnParallelLinear` and all-gathers their output columns over TP. Each output column is still computed from the full reduction on one rank; the gather only moves data. Each rank holds `1 / TP` of the weights, which frees 6.8 GiB per GPU for the KV cache.

## Claims

- **Recipe default (TP8 + EP8 + DSpark), 8×MI355X, random 8k in / 1k out:** output throughput is +2.6% to +4.6% at every concurrency (c4: +20%, mostly from the acceptance length), mean TPOT is −1.7% to −9.3%, and mean TTFT is −0.6% to −8.2%.
- **Memory:** model weights 82.36 → 75.58 GiB per GPU, KV cache +4.8% (6,271,180 → 6,573,865 tokens).
- **Trade-off:** a lone short prompt on an idle server is about 4 ms slower (2k tokens: 104.2 → 108.2 ms); 8k and longer are 1–2% faster. See Details.
- **Accuracy:** GSM8K unchanged (paired exact McNemar p = 0.86). Outputs are not bit-identical, because the GEMM summation order changes.
- **Default on** when every TP rank sees the same tokens (TP > 1, no sequence-parallel MoE, DP = 1, not `VLLM_BATCH_INVARIANT`), with the same config switches as the CUDA path. To turn it off: `--hf-overrides '{"text_config": {"muse_spark_tep_shard_pooler": false, "muse_spark_tep_shard_unpooler": false}}'`.
- No change to core files: everything is in `vllm/models/muse_spark/amd/`, plus the two new tests in the Buildkite yaml.

**Accuracy**

- GSM8K 5-shot (`lm_eval --model local-completions --tasks gsm8k --num_fewshot 5`, 1319 questions, 32 concurrent requests), TP8 + EP8 + DSpark: strict 0.9492 -> 0.9477, flexible 0.9484 -> 0.9469. Paired on strict: 16 questions are correct only on the baseline and 14 only with this PR, exact McNemar p = 0.86.
- Greedy outputs on 5 fixed prompts (45 to 8192 tokens) are not bit-identical: the first-token logprob differs by 0.03–0.34 and 3 of 5 completions diverge. The pooled activations differ by up to 1 BF16 ulp because the GEMM summation order changes, and the experts' MXFP4 activation quantization can turn 1 ulp into a different quantization step.

## Details

**How.**

- `MuseSpark1xMoE` builds the pooler and unpooler with `ColumnParallelLinear` when sharding is on, so each rank loads its `[N / TP, K]` block of the checkpoint weight. `_gathered_column_proj` runs the projection and all-gathers the output columns.
- **All-gather.** AITER's custom all-gather (`dim=-1`, no transpose) when available. Prefill outputs larger than its IPC buffer are gathered in token chunks, which is faster than RCCL (single layer at TP8, 2048 tokens: 128 µs vs 248 µs for the two gathers). Otherwise `tensor_model_parallel_all_gather`.
- **Decode GEMM.** After sharding, N is only 512 (pooler) or 1024 (unpooler), too narrow for hipBLASLt to fill the GPU at decode sizes. Up to 128 tokens on gfx950, `ops/skinny_gemm.py` runs a two-pass split-K Triton GEMM: each split accumulates in fp32, and a second kernel adds the splits in a fixed order in fp32 and rounds to BF16 once. No partial sum is rounded to BF16, so the error is that of an fp32-accumulating GEMM such as `F.linear`. AITER's tuned GEMMs are not used here because their split-K accumulates the partials in BF16. Single MI355X, graph replay: pooler shard 17.4 µs (full `F.linear`) → 4.9 µs at 1 token, unpooler shard 16.0 → 4.8 µs.

**Trade-off: a lone short prompt on an idle server is about 4–11 ms slower.**

- Below about 2.5k tokens, an eager single-request prefill of this model is bound by host-side kernel launches: baseline TTFT stops falling (about 95–100 ms at both 512 and 1024 tokens) while the GPU work keeps shrinking. The two extra all-gathers per layer add about 49 µs of host launch time per layer (about 3 ms per forward) and two cross-rank synchronization points.
- The GPU time of the sharded segment is lower at every prefill size from 256 tokens up (11 to 92 µs per layer), so prefills of 3k tokens and more are faster, and under concurrent traffic prefill chunks are batched with decodes and are GPU-bound.
- The full weights no longer exist on each rank, so a token-count threshold cannot fall back to the replicated GEMMs. Keeping the full weights and sharding only at decode sizes (as the CUDA path does) would avoid this cost but give up the 6.8 GiB per GPU. Users who care most about idle short-prompt TTFT can turn the feature off with the `hf-overrides` above.

**Complexity.** The PR adds 294 non-test lines: `model.py` (+127/−16: the sharded projections, the all-gather and the switches) and `ops/skinny_gemm.py` (167: the split-K kernel and its per-shape configs).
