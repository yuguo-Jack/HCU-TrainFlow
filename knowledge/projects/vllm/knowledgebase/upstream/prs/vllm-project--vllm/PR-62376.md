# [Bugfix][Attention] Accept split KV blocks in the b12x backend

[Upstream PR](https://github.com/vllm-project/vllm/pull/62376) · state: open · merged: False

## Original PR description

## Overview

Hybrid attention/mamba models cannot use `--attention-backend b12x`: hybrid page alignment raises the KV block size above 128 (2176 in #62320), and b12x only accepted exactly 64 or 128. The worker already splits large manager blocks into the kernel page sizes a backend declares, and b12x declares 64 and 128, so this drops b12x's exact-size override and lets the standard split apply. Fixes #62320.

## Claims

- Hybrid models now start with `--attention-backend b12x`: the manager block is aligned to the mamba page (a multiple of 128) and the worker hands b12x 128-token kernel pages. `ValueError: Aligned KV cache block size ... is not supported by attention backend(s): B12X` is gone.
- Non-hybrid models are unaffected: with `--block-size` unset or 64/128 nothing changes; block sizes that are not a multiple of 64 are still rejected at selection.
- One override removed, one unit test added. No kernel or runner changes.

## Validation

DGX Spark (GB10, sm_121, aarch64), CUDA 13.0, torch 2.14.0+cu132, flashinfer-python 0.7.2 (provides the `b12x` module), vLLM main @ f98ae6a9f.

Reproducer close to #62320 (same Qwen3.5 GDN + full-attention layout, head_dim 256, 2 KV heads, under 1B parameters):

```python
from vllm import LLM
LLM("Qwen/Qwen3.5-0.8B", attention_config={"backend": "B12X"}, block_size=128, dtype="bfloat16")
```

| | before | after |
|---|---|---|
| startup | `Setting attention block size to 640 tokens ...` then `ValueError: Aligned KV cache block size 640 is not supported by attention backend(s): B12X.` | starts; manager block 640, b12x runs on 128-token kernel pages (`planned_page_sizes=(64, 128)`); generates |

Greedy outputs, b12x vs FLASH_ATTN on the same model: identical on 11 of 12 outputs (4 short prompts, a 300-token prompt, a 3k-token prompt spanning several aligned blocks, and a mixed batch of all six). The one that differs is a prompt whose greedy continuation also flips between two identical FLASH_ATTN runs on this model, i.e. a near-tie, not a kernel difference. Repeated b12x batches are identical.

Also tried `tiiuae/Falcon-H1-0.5B-Instruct` (Mamba2 hybrid, head_dim 64): with this change the aligned block of 896 is accepted and the engine proceeds to CUDA-graph capture, where the b12x kernel planner raises `no valid NUM_MMA_KV typed shared-memory allocation fits the device`. That is a head_dim 64 limitation of the b12x package (a non-hybrid head_dim 64 model, Qwen2.5-0.5B-Instruct, fails identically with `block_size=128`), independent of this PR; I will file it separately.

```
$ pytest tests/v1/attention/test_b12x.py
41 passed in 34.60s   # DGX Spark, GB10; includes the new test
```

The new test fails on main (`supports_block_size(2176)` is False there) and passes with this change. `pre-commit run --files ...` is clean.

## Details

`Platform._align_hybrid_block_size()` sets the manager block so one attention page is at least one mamba state page, rounded to the backend's kernel block alignment. For b12x that is a multiple of 128. `_check_aligned_block_size()` (#58457) then asks every backend `supports_block_size(aligned)`, and b12x's override answered False for anything but exactly 64 or 128.

The base `AttentionBackend.supports_block_size()` accepts any multiple of a declared kernel size for exactly this case ("the framework-level block size only needs to be a multiple of the kernel's requirement"). At runtime `prepare_kernel_block_sizes()` / `select_common_block_size()` pick the largest declared size that divides the manager block (128 for 2176), the KV cache is allocated in kernel pages, and `AttentionGroup.map_to_kernel_block_table()` expands the block table. b12x already reads the page size from the cache tensors (`_kv_page_size`), prepares plans for both page sizes, and sizes its page table for the hybrid expansion (`_max_page_table_width(..., is_hybrid)` adds the trailing capacity for exactly this split). So the only thing standing between hybrid models and b12x was the override.

`get_preferred_block_size()` is kept, so a non-hybrid model with no `--block-size` still gets 128 rather than the base class's minimum of 64 (with #62265).

Related: #62265 removes the same backend's constructor-time block-size check; this PR is independent of it when `--block-size` is passed explicitly (as in the report), and together they make `--attention-backend b12x` work for hybrid models with no `--block-size` at all.

Not a duplicate: no PR references #62320; the open b12x PRs (#54976, #54669, #54719, #55405) are about MoE/MLA selection.

I found this via #62320, which mentions my earlier b12x fix. I used Claude Code to Understand the split mechanism, traced it, and run the validation; I reviewed every changed line and ran the tests myself.
