# [ROCm] Warm up Triton GEMM and MiniMax-M3 sparse-PA decode variants that otherwise compile inside the first requests

[Upstream PR](https://github.com/vllm-project/vllm/pull/65308) · state: closed · merged: False

## Original PR description

## Purpose

On ROCm, a few Triton/Gluon kernels still JIT-compile inside the first user requests after startup, adding 0.5–2.6 s to those requests:

1. `VLLM_ROCM_GEMM_JIT_WARMUP`: warms up the Triton GEMM variants used by the ROCm unquantized GEMM path and the bf16x3 router GEMM for the configured batch sizes (MiniMax-M3: `_reduce_terms_kernel`, 864 warm-up calls over 16 shapes, 2.65 s at startup instead of during serving).
2. MiniMax-M3 on ROCm: warms up the sparse paged-attention decode variants (`ONE_SHOT` × context-lengths pointer alignment) that otherwise compile while serving. Alignment variants arise only where KV heads per rank are not a multiple of 4 (TP2/4/8). 4 calls, ~0.9 s per rank at startup.

Default behaviour is unchanged unless the env / model path enables it. Main has a JIT warm-up registry (`kernel_config.enable_jit_warmup`) and a Blackwell-only `_warmup_bf16x3_router_gemm`; happy to hang (1) off that registry and extend the router warm-up to ROCm if preferred.

## Test Result

MiniMax-M3 VL on MI355X, TP4: with both, no GEMM or sparse-PA compile while serving in any of 8 full benchmark passes (before: a compile inside a measured row in every pass, costing that row up to ~14%). Throughput effect is within pass-to-pass noise; the claim is the removed in-request compile, shown by the server logs. MMMU 0.636–0.678.
Known gap: the LM head's AITER `_gemm_a16_w16_kernel` variants still compile on first use; not covered here.
