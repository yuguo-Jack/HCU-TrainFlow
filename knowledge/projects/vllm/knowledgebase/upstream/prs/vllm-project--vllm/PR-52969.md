# [Bugfix][V1] Don't crash the engine on an aborted request

[Upstream PR](https://github.com/vllm-project/vllm/pull/52969) · state: closed · merged: False

## Original PR description

## Purpose

I think there is a narrow race condition allowing for an uncaught RuntimeError affecting requests aborted before they've started running.

A request can be aborted (e.g. when a client disconnect) via `finish_requests` while still sitting in the scheduler's waiting queue. If it lands between `schedule` popping the request and checking its status, the status is no longer WAITING or PREEMPTED, and `schedule` raises an uncaught RuntimeError. This crashes the entire engine-core process. For vllm-omni the single stage dying dying takes the orchestrator and all other stages down with it (which was how I originally found the issue).

I'm not 100% certain this is the correct fix but I tried to split the problem into two pieces

* An early check right after `peek_request` drops an already finished request but before any KV cache allocation happens for it. 
* A second at the original crash site handling the narrower window between the (second) pop_request() and the status check

For the second in particular I'm not confident the clean up code is entirely correct and would greatly appreciate some feedback. @njhill 


## Test Plan

- New regression test, test_schedule_drops_request_aborted_while_waiting in tests/v1/core/test_scheduler.pt that simulating the conditions triggering the trash.
- Verified the test fails with the original RuntimeError: Invalid request status: FINISHED_ABORTED traceback against unpatched scheduler.py, and passes with the fix.

When `load_kv_async` is true and `finish_requests()` lands during `pop_request()`, control enters the async-load branch before this new finished-status check. Move the finished check ahead of the `load_kv_async` branch and perform the appropriate rollback there.

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Evict uncomputed blocks when rolling back an aborted admission**

With prefix caching enabled and a prompt containing at least one full block, `allocate_slots()` hashes and caches the newly allocated prompt blocks before `pop_request()`. **<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Release pending CoW retentions during abort rollback**

With async scheduling and a hybrid-model partial prefix-cache hit, `allocate_slots()` creates a pending CoW pair whose source and destination carry extra retention references. If the request is aborted inside `pop_request()`, freeing its block table here does not remove that pending pair; the end of `schedule()` drains it behind the next nonempty-step fence, but this abort-only iteration has zero scheduled tokens and advances neither fence counter. The rollback needs to cancel and release CoW work belonging to the aborted admission rather than leave it pending.
