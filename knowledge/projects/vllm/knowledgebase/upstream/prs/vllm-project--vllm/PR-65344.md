# [Perf][Kernel] Add opt-in BF16 gated projection fusion for SM89 prefills

[Upstream PR](https://github.com/vllm-project/vllm/pull/65344) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Adds an opt-in Triton kernel that fuses the MLP gate/up GEMM with SiLU-and-mul for BF16 dense prefill on SM89 (RTX 4090), wired into `Qwen2MoeMLP`, the dense MLP of Qwen3.5-4B. Defaults are unchanged.

Related: [RFC #52776](https://github.com/vllm-project/vllm/issues/52776) proposes a general epilogue interface; this PR is one narrow, measured instance and does not implement that interface. An open-PR search on 2026-11-03 (`swiglu gemm`, `silu fusion`, `dense MLP`, `52776`) found no equivalent dense BF16 gate/up + SiLU fusion for SM89; [#60846](https://github.com/vllm-project/vllm/pull/60846) targets SM120 tiny-batch decode (shared-expert scalar gate and reduction), not the gate/up GEMM.

## Claims

- **End to end:** Qwen3.5-4B on one RTX 4090, 16K-token prompt, `vllm serve` default `max_num_batched_tokens=2048`: TTFT **−3.0%** (mean per-pair change, 95% CI −3.3% to −2.8%; median 1,143.5 → 1,108.2 ms over 12 request pairs, all 12 faster).
- **Per MLP call (isolated op):** gate/up GEMM + SiLU-and-mul takes **10–11% less time** for 768–4,096 rows (1,090.1 → 966.2 µs, −11.4%, at 1,584 rows).
- **Opt-in and contained:** nothing changes unless `+gated_linear_silu` is set. When it is set, steps outside 768–4,096 rows run the same cuBLAS GEMM and `silu_and_mul` kernels as before (bit-exact in the fallback tests), and no weight copy is made. GSM8K: 1,019 → 1,022 of 1,319 correct, difference not significant.

## Validation

**Why this kernel.** In a 16K-token prefill before this PR, GEMMs take 73% of GPU kernel time and the MLP gate/up GEMM alone takes 30.5%. Its 18,432-wide BF16 output is written to memory only to be read back by SiLU-and-mul. The fused kernel keeps that intermediate in registers and writes the 9,216-wide activation once:

```text
Before: X → gate/up GEMM → [G, U] in memory (M × 18,432, BF16) → SiLU(G) · U → A (M × 9,216) → down GEMM
After:  X → one kernel: gate/up GEMM with SiLU(G) · U in its epilogue       → A (M × 9,216) → down GEMM
```

At 1,584 rows the skipped intermediate is about 58 MB per layer per step, written once and read once on the old path.

**End to end.** One `vllm serve` at `b2a9480` with `--dtype bfloat16 --language-model-only --max-model-len 16576 --gpu-memory-utilization 0.85` and the opt-in flag; everything else default (`max_num_batched_tokens` 2,048, FULL_AND_PIECEWISE CUDA graphs up to 512 tokens, prefix caching on). One request at a time, one output token, zero prefix-cache hits on every request. For the paired A/B, a test-only worker extension switches each MLP's `gate_up_silu` between the fused op and `None` while the server is drained, so both arms share KV allocation and the CUDA graphs captured at startup.

The kernel-level gain is enough to explain the end-to-end gain. A 16K prompt runs 10 steps of 1,584 rows through 32 layers, so 320 fused calls × 123.9 µs ≈ 39.6 ms would be expected from the isolated benchmark; the measured paired mean saving is 34.7 ms (95% CI 31.6–38.0 ms), about 87% of that.

**Model quality.** GSM8K from the vLLM CI assets, 1,319 questions, 5-shot, greedy, concurrency 64:

| | Native | Fused |
|---|---:|---:|
| Correct | 1,019 (77.26%) | 1,022 (77.48%) |

Paired difference +0.23 pp, 95% CI −0.76 to +1.21 pp. The fused kernel processed 542,217 rows (counted at one representative layer). Because decode rows can share a step with prefill chunks, that covers 35–56% of the 972,038 prompt tokens: 56% if every row was a prompt row, 35% after subtracting all 203,366 generated tokens. Scheduling alone moves results at this concurrency: a native re-run of 64 questions changed 6 outcomes, while native and fused differ on 45 of 1,319. The kernel accumulates in a different order than cuBLAS, so outputs are not bitwise identical and greedy tokens can diverge (an earlier 4K-prompt probe diverged at token 58).

**GPU sync check.** A real-server run with `VLLM_GPU_SYNC_CHECK=error` (guard confirmed active) served 528- and 16,384-token requests on both paths without error; the fused 16K request ran all ten 1,584-row steps through the kernel.

- **Off by default.** Without `+gated_linear_silu`, or when any eligibility check fails, `gate_up_silu` is `None` and `Qwen2MoeMLP.forward` runs the original code.
- **Eligibility (checked once when the model is built):** SM89; BF16; unquantized, bias-free linears on the automatic linear backend; TP=1; hidden size 2560 and intermediate size 9216; `silu_and_mul` custom op enabled; no LoRA, batch invariance, expert gate or weight offload. At runtime, steps outside 768–4,096 rows and non-contiguous inputs fall back to the native GEMM and `silu_and_mul`.
- **Untouched:** scheduler, model runner, KV cache, weight loading and configs. Reverting deletes the five new files and the hook in `qwen2_moe.py`; no config field, weight layout or saved state is added.

</details>

<details>
<summary>Design, trade-offs and limitations</summary>

- The kernel reads the original `[gate; up]` weight rows in interleaved order, so there is no transformed copy and in-place weight updates are seen. It accumulates in FP32 and keeps the native BF16 cast points after the projection, the SiLU and the product.
- One fixed configuration: 64-row × 64-output-column tiles (128 interleaved gate/up weight rows), K step 32, 4 warps, 3 stages. M is a runtime argument, so one binary serves every eligible token count.
- The gain depends on the batch budget. With prefix caching on (the default), Qwen3.5's hybrid cache ends each non-final prefill chunk on its 528-token block. With the `vllm serve` default of 2,048, a 16K prompt therefore runs as 10 × 1,584 rows (fused) plus 528- and 16-row tails (native). With the offline `LLM` default of 8,192 on the same GPU, non-final chunks are 7,920 rows, above the 4,096-row limit, so the same 16K prompt never reaches the kernel.
- The kernel is a plain `@triton.jit` function, not registered with vLLM's JIT warmup (`docs/contributing/jit_kernel_warmup.md`), so it compiles on its first eligible call. With `max_num_batched_tokens=2048` that call is the 2,048-row startup profile run. If no startup step has 768–4,096 rows, the first eligible step compiles it while serving, and vLLM's JIT monitor logs a warning (or raises with `--jit-monitor-mode error`). A `VllmJitKernel` wrapper can be added if reviewers prefer.
- Compilation mode: vLLM auto-enables breakable CUDA graphs for Qwen3.5 on NVIDIA, which selects compilation mode 0, whose default custom-op set is `all`. The flag keeps `all` because the fusion also needs the `silu_and_mul` custom op. With `VLLM_USE_BREAKABLE_CUDAGRAPH=0` the model is torch-compiled instead and `all` would also switch every other custom op to its CUDA kernel; that configuration was not measured.
- Measured on one RTX 4090 only. Other SM89 parts (L4, L20, L40S) differ in SM count and memory bandwidth, which is why the path is opt-in. Not measured: decode throughput, speculative decoding, image/video inputs (runs were text-only) and torch.compile mode. The shape check is deliberately specific to Qwen3.5-4B's 2560/9216 MLP; other shapes would need their own tile choice and measurements.

</details>
