# [Bugfix][Core] Opt-in capture of attention ops in breakable CUDA graph segments (fixes glm5_next capture-time IMA on SM120)

[Upstream PR](https://github.com/vllm-project/vllm/pull/64266) · state: open · merged: False

## Original PR description

## Background

GLM-5.3-Flash (`Glm5NextForConditionalGeneration`, hybrid KDA linear-attention + NoPE sparse-MLA) **cannot start on SM120 (RTX PRO 6000 / 6000D, CUDA 13 stack) with default settings**: vLLM auto-enables breakable CUDA graphs for hybrid models, and the boot dies during CUDA graph capture with an illegal memory access.

This reproduces deterministically at engine start (no traffic needed), on both `0.32.1rc1.dev463` and the current `0.33.0rc1.dev174` nightly.

## Root cause

With breakable CUDA graphs, attention-family ops wrapped by `eager_break_during_capture` are **executed for real between capture segments** (`add_eager` runs `fn()` after `_end_segment()`). On SM120 + CUDA 13 cuBLAS, the MLA absorption `torch.bmm` inside that eager window dispatches to an **nvJet TMA GEMM kernel that faults when executed mid-capture-sequence**:

- Non-blocking mode: async IMA surfaces at the next `capture_end`/`instantiate` (`cudaGraphInstantiateWithFlags` returns 700, `Failed to instantiate EVENT_RECORD node`).
- `CUDA_LAUNCH_BLOCKING=1`: `CUBLAS_STATUS_INTERNAL_ERROR` raised at `cublasGemmStridedBatchedEx` (`mla_attention.py`, the NoPE `torch.bmm(mqa_q_nope, W_UK_T, out=...)`).
- GPU coredump (`CUDA_ENABLE_COREDUMP_ON_EXCEPTION=1` + cuda-gdb) names the faulting kernel:
  `nvjet_sm120_tst_mma_64x24x64_8_16x24x64_tmaAB_alignCD4_bz_NNNN` — "Device Unknown Exception".

The kernel itself is healthy: the **same GEMM captured inside FULL-mode CUDA graphs records and replays correctly** (51 FULL graphs capture cleanly and serve correct output with `VLLM_USE_BREAKABLE_CUDAGRAPH=0 + cudagraph_mode=FULL`). Only the *eager execution between capture segments* faults. FULL mode already bypasses the eager break for the attention op (`mode == CUDAGraphMode.FULL` → straight `fn()`), which is why it works.

## The fix

Add an opt-in env, `VLLM_BREAKABLE_CAPTURE_ATTN=1`, that makes the wrapper let attention-family ops (`"mla" in fn.__name__`) run inside the captured segment — the same treatment FULL mode already gives them — instead of executing them as eager breaks. KDA/GDN eager breaks are unaffected by the name filter (their recurrent-state ops cannot be captured yet; #61952 tracks that).

Why opt-in rather than default:
- The eager break for the unified attention op also carries PD-disaggregation KV-transfer side effects (`maybe_transfer_kv_layer`), which must stay eager. Users running PD disagg should not enable this.

## Validation

8x RTX PRO 6000 Blackwell 96G (SM120), TP8, `zai-org/GLM-5.3-Flash` FP8 checkpoint, FlashInfer 0.7.2.post1.

| stack | default (stock) | with this patch + env |
|---|---|---|
| v0.32.1rc1.dev463, torch 2.14.0+cu132 | capture-time IMA, engine dead | READY; PIECEWISE 106 + FULL 57 graphs all captured; 4/4 correctness probes; c1 **92.0** tok/s, c32 **1295.2** tok/s (1.8K in x 1K out, ignore_eos) |
| v0.33.0rc1.dev174, torch 2.14.1+cu130 | capture-time IMA, engine dead (unchanged) | READY; PIECEWISE 106 + FULL 51 graphs; 4/4 probes; c1 **87.8**, c32 **1155.5** |

Correctness gate on the 0.33 stack: final answers (temperature=0: arithmetic / Chinese QA / fact recall / code generation) are identical between the patched-graph engine and a stock `--enforce-eager` engine on the same stack.

For reference, the workaround before this patch was `VLLM_USE_BREAKABLE_CUDAGRAPH=0 + cudagraph_mode=FULL` (79.4 / 1179.5 tok/s on the same box) — this patch is ~10-16% faster because piecewise mixed batching is recovered.

## Notes

- Zero changes to the default path; env-gated opt-in only.
- Not stack-specific in principle: any platform where cuBLAS's TMA GEMM kernels misbehave when executed between breakable capture segments can use this; SM120/CUDA-13 is where we have hardware to prove it.
- Related: #61952 (captures the GDN core itself — complementary), #54317 / #53963 (other GLM-5.3-Flash Blackwell failure modes, different layers of the stack).

## Update (review feedback, 581b3aea): scoped to sparse MLA, fail-fast elsewhere

`VLLM_BREAKABLE_CAPTURE_ATTN` now only allows the **sparse MLA** path to be
recorded into breakable PIECEWISE segments:

- Sparse forwards derive their decode/prefill split from `q.size(0)` (traced),
  so replays stay correct for any batch composition — verified on GLM-5.3-Flash
  (hybrid KDA + sparse NoPE MLA, SM120) with forced mixed batches in both
  directions (long chunked prefill overlapping an active decode, and
  short-prefill-during-decode).
- The dense unified MLA forward reads `attn_metadata.num_decode_tokens`
  (a Python int from a `for_capture=False` dummy batch under PIECEWISE) and
  would freeze that split into the graph — it (and anything not positively
  identified as sparse) now **raises at capture time** with a clear message.

The sparse allowance is empirical (GLM-5.3-Flash NoPE MLA); the per-layer-impl
gate can be tightened further if other sparse backends turn out unsafe.

Good catch, and the mechanism is exactly as you describe — I verified it in code: the breakable graph cache keys on `BatchDescriptor` (num_tokens/num_reqs only, no decode/prefill split), so under PIECEWISE a mixed batch hits a segment captured with the decode-only dummy batch, and the dense path would replay `attn_metadata.num_decode_tokens` (a Python int built with for_capture=False) as a frozen split.

Two data points from the model I validated this on (GLM-5.3-Flash, hybrid KDA + sparse NoPE MLA, SM120):
- The sparse path is composition-independent at replay: with a decode-only dummy its forward takes the `is_sparse and num_mha_tokens == 0` branch and derives the split from `q.size(0)` (traced), so I forced mixed batches — a ~24K-token chunked prefill overlapping an active multi-second decode, plus the short-prefill-during-decode direction — and outputs stayed correct in both directions.
- The dense unified path bakes the Python-int split exactly as you predicted, so rather than guessing, the gate now refuses it.

Pushed in 581b3aea: the opt-in now resolves the backing layer via `get_attention_context` and only allows `impl.is_sparse` paths; dense unified MLA (or anything it cannot positively identify as sparse) raises at capture time with a clear message, so it fails at startup as you suggested instead of corrupting silently. Refusal branch unit-checked; re-validated the sparse boot + mixed-batch probes + throughput parity after the change.

One limitation kept as documented in the PR description: the sparse allowance is empirical (GLM-5.3-Flash NoPE MLA on SM120), not a claim about every sparse backend — the gate is per-layer-impl so it can be tightened further if other sparse backends turn out unsafe.
