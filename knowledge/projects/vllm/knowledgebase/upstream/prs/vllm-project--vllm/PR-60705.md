# [Bugfix][CPU] Avoid Triton JIT stall in _ranks_kernel on CPU

[Upstream PR](https://github.com/vllm-project/vllm/pull/60705) · state: open · merged: False

## Original PR description

## Overview

On the Triton CPU backend, the first `logprobs=-1` request on the V2 runner stalls for ~55 minutes because `_ranks_kernel` takes extremely long to compile. This keeps the full-vocab blocks unmasked and masks only a small tail, which removes the stall. Related: #60357. Same file as #60095 / #60097 (different kernel), no dependency.

## Claims

- First-request compile of `_ranks_kernel` on the Triton CPU backend goes from ~55 min to seconds.
- Rank results are unchanged: the new test matches `(logits >= logits.gather(...)).sum(-1)` across batches, fp32/fp16, ties, `-inf` rows, strided inputs and vocab sizes around `BLOCK_SIZE`.
- On non-CPU platforms the launch parameters give the same structure as before (full blocks, then one masked tail iteration). GPU timing was not run.

## Details

The old kernel loaded every `BLOCK_SIZE=8192` tile with a mask. On the Triton CPU backend, compile time for a masked tile grows sharply with tile size. In a standalone copy of the kernel, with a masked tile as wide as the main block, cold compile took ~30 s at 1024 and ~600 s at 4096. I did not isolate the mechanism, and I did not time 8192 directly.

The fix runs the full blocks without a mask and handles the remainder in a separate masked loop of `TAIL_BLOCK_SIZE` elements. On CPU the tail is 64, which compiled in about a second in my tests. On other platforms it stays at 8192, so the leftover is a single masked iteration, close to the previous behavior. A smaller tail on GPU would add many serial iterations, so I left GPU as-is rather than guess.

The semantics are unchanged. `_ranks_kernel` has a single call site, which is updated.
