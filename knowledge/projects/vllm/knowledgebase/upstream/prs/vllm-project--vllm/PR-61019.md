# [Bugfix][KV Connector] Serve and store OffloadingConnector partial tails with EAGLE/MTP groups

[Upstream PR](https://github.com/vllm-project/vllm/pull/61019) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

**Problem.** With an EAGLE/MTP draft model and `mamba_cache_mode="align"`, the native CPU `OffloadingConnector` never serves a partial tail. So every hit from the CPU tier stops at a scheduler-block boundary, and the tokens after it are computed again.

**Fix, in three parts:**
1. **Lookup:** look up the tail at the EAGLE proof position, as Mooncake does since #60695.
2. **Store:** fix the store gate. Before, it always skipped the one step that can store the tail.
3. **Store policy:** store an EAGLE tail only for a request that loaded from the CPU tier. Without this, parts 1 and 2 double the GPU → CPU traffic, and serving gets slower (P95 TTFT 13 % higher without it in a same-day control, see Validation).

**Result** (8 × A100, MLPerf agentic, 3 × 60 min per arm): no serving regression; SLO pass 92.42 % against 91.70 % without this PR. The CPU-tier hits now end at partial tails, as designed.

Related: #60533 (core proof), #52832 (producer partial tails), #54165 (a different bug in the same file).

## Claims

- With an EAGLE group and align Mamba, a CPU-tier hit can now end at `prefix_match_unit` granularity, as a GPU prefix-cache hit already does. Before, it ended at a whole scheduler block, minus one more block for the EAGLE pop.
- The EAGLE group's tail is keyed at `boundary + eagle_proof_margin`, the same proof that core uses since #60533. Mamba groups and non-EAGLE groups stay keyed at the boundary.
- The tail is stored on the step that computes the proof.
- With an EAGLE group, only a request that loaded from the CPU tier stores its partial tail.
- No change without an EAGLE group, or where partial tails are not supported (DCP > 1, `blocks_per_chunk > 1`, mixed block sizes, sliding-window groups). No new config option.

## Details

**Root cause 1: lookup.** `SchedulerOffloadConfig.from_spec` set `supports_partial_tail = False` when any group was an EAGLE group. For an EAGLE group, the complete-chunk lookup asks for one extra chunk and then drops it. So the hit ended one scheduler block before the last stored chunk, and no partial tail was tried.

**Root cause 2: store gate.**
1. With EAGLE block drop, core stops the prefill at the Mamba checkpoint T = floor(P/h)·h − h.
2. On the next step (tokens T..P), the state is copied (CoW), and the manager hands `(group, cow_block, T)` to the connector one time.
3. The scheduler builds the connector metadata before `_update_after_schedule`, so `num_computed_tokens == T` at that point.
4. So the gate `boundary + margin > num_computed_tokens` reads `T + h > T`. This is always true, so the store is always skipped, and the hand-off does not come again.

**Changes.**
- Remove the EAGLE exclusion from `supports_partial_tail`.
- Key the EAGLE non-recurrent groups at `boundary + margin` in store, lookup and load.
- Margin rule as in core: one hash unit if `cache_hit_alignment_tokens` < block and the group manager supports fine-grained lookup; else one block.
- Widen the partial search by one block, with bridge keys for the dropped chunk. That chunk is looked up once per lookup; a miss skips that block.
- Check the proof against `min(num_computed_tokens + num_scheduled_tokens[req_id], num_prompt_tokens)`. The cap keeps the proof out of speculative tokens.
- With an EAGLE group, store a partial tail only if `update_state_after_alloc` scheduled a CPU-tier load for this request (`RequestOffloadState.loaded_from_offload`). Complete chunks and aligned boundary states are stored as before.

**Why the proof-step store is safe.** Stores are only queued in `wait_for_save` and are sent at the start of the next step. The CPU transfer stream waits on the compute stream at that point, so the copy runs after this step's forward wrote the proof block.

**Difference from #60695.** Mooncake stores one key per hash unit. The native connector stores whole chunks and keeps its chunk-level EAGLE drop for complete chunks. So only the partial-tail key of EAGLE groups changes.

**Limitations.**
- If the hand-off step stops before `T + h`, the tail is not stored. I ran core's chunk-split code on 20,000 prompts (1k–200k tokens) per configuration. No hand-off was lost when block ≤ `max_num_batched_tokens` with EAGLE or single-module MTP. Losses occur only with multi-module MTP (0.2–0.45 %) or with a block larger than the token budget (≤ 1.7 %). A fix would need core to keep the CoW block across steps; not done.
- The store policy is a heuristic. A request served only from the GPU prefix cache stores no EAGLE tail. If the GPU later evicts that prefix, the next turn's CPU-tier hit ends at the last complete chunk. That turn then loads from the CPU tier and stores its tail, so the turn after it can get a partial hit. Measured on one workload only.
- When the dropped chunk is present, the search covers two blocks. This applies only with an EAGLE group.
- Existing CPU caches hold no EAGLE tails, so no migration is needed.

**Size:** `offloading/scheduler.py` +170 / −34 (no core files changed); tests +348 / −1.

## Summary

This pull lets the CPU offloading connector store and serve partial tails when a model has an EAGLE or MTP draft group. The pull is marked as a draft. We found two serious and two smaller findings. The most important problem is that a hand-off skipped because the proof is not yet computed is never offered again, so that tail is never stored.

## Serious findings

**1. A skipped hand-off is lost for good [offloading/scheduler.py]**
When the EAGLE proof has not been computed by the end of the step, the code skips the copy-on-write hand-off for that step. The hand-off is created once and cleared the next time pending hand-offs are drained, so nothing retries it and that tail is never stored.
*Change:* Defer the hand-off until the proof is computed instead of dropping it.

**2. EAGLE configs double the partial-tail lookups on every request [offloading/scheduler.py]**
With an EAGLE proof margin the search covers two blocks instead of one, which doubles the boundary iterations. Each boundary also probes extra bridge keys before the per-group lookups, which adds lookups and host-to-GPU bridge loads on a path that runs for every request.
*Change:* Avoid paying the extra lookup cost on every request, for example by only probing the second block or the bridge keys when they can change the result.
