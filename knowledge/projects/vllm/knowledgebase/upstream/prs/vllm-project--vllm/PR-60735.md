# [Bugfix][MoE] Keep DeepEP high-throughput buffers alive across DBO streams

[Upstream PR](https://github.com/vllm-project/vllm/pull/60735) · state: closed · merged: True

## Original PR description



## Overview

Under DBO, `DeepEPHTPrepareAndFinalize` has DeepEP allocate its dispatch outputs on the DBO comm stream, then reads them on the compute stream; the combine input crosses the other way. The caching allocator is never told about these cross-stream reads, so the other microbatch's next DeepEP call can reuse a block and overwrite it before it is read. With the DeepGEMM FP8 MoE this crashes the engine at startup with an illegal memory access in `ep_scatter`. This PR calls `record_stream` on every tensor that crosses between the two streams.

A GitHub search found no existing issue or PR for this. Related: #46990 added a ROCm-only host sync after HT dispatch/combine under DBO, possibly for the same hazard (see Details). #27666 and #38451 fixed other DBO + DeepEP HT problems.

## Claims

- Fixes the startup crash with DBO + DeepEP high-throughput + the DeepGEMM FP8 MoE (`VLLM_USE_DEEP_GEMM=1 VLLM_MOE_USE_DEEP_GEMM=1`, the defaults). For GLM-5.3 FP8 on main, 2 of 2 runs crashed in the first microbatched step without the fix. On 0.29.0, so did all 7 runs that had neither the fix nor a serializing workaround (`CUDA_LAUNCH_BLOCKING`, no caching allocator, host sync). With the fix, full GSM8K scores 0.927 with CUTLASS linears and 0.912 with DeepGEMM linears (DBO off: 0.923).
- Covers both directions for every experts backend behind DeepEP HT: DeepEP's outputs (comm stream to compute stream) and the reduced expert output passed to combine (compute stream to comm stream; defensive on main, see Details). With `--enable-dbo`, main runs Model Runner V1 unless `VLLM_USE_V2_MODEL_RUNNER=1` is set. MRV2's opt-in DBO uses the same microbatch contexts and streams, so it gets the same fix. Only Model Runner V1 was run.
- No change when DBO is off. With DBO on, there are no host syncs and no extra kernels. The cost is at most 9 `record_stream` calls per MoE layer per microbatch, plus one CUDA event per recorded block when it is freed; the allocator reuses that block only after the event completes. The throughput cost was not measured.
- DeepEP low-latency, NIXL-EP and DeepEP v2 are not affected, because on main they do not switch streams under DBO. `deepep_ll.py` is unchanged. The open #52177 adds the same comm-stream switching to DeepEP v2, so it may need the same treatment.

## Details

**Root cause** (main @ 240785b8, before this PR):
- **Shared streams.** `UBatchWrapper` creates one comm stream (`gpu_ubatch_wrapper.py:76`) and gives both microbatches that comm stream and the same compute stream (`:288-291`). MRV2's `UBatchRunner` does the same (`gpu/ubatch_utils.py:327,458-462`).
- **Where DeepEP allocates.** `_do_dispatch` switches to the comm stream (`deepep_ht.py:126`). It then calls `get_dispatch_layout` and `dispatch` with `allocate_on_comm_stream=False` (`:139,168`) and, under DBO, `async_finish=False` (`:138,167`). DeepEP therefore allocates recv x, scales, topk ids and topk weights on the current stream, which is the DBO comm stream's allocator pool. It runs its kernels on its own internal stream, which waits only on `previous_event`. With `async_finish=False` it then makes the calling stream wait for that internal stream, and it records no other stream on its tensors: its HT dispatch and combine call `record_stream` only when `async_finish=True` (`csrc/deep_ep.cpp`).
- **Where they are read and freed.** `dbo_switch_to_compute_sync()` (`:177`) orders the compute stream after the dispatch, and `_receiver` reads the outputs there: first the `torch.where` over the topk ids (`:225`), then the experts. Once those kernels are enqueued the Python references are dropped; for example, `expert_topk_ids` is rebound by the `torch.where`. The blocks go back to the comm pool, free for any later comm-stream work.
- **How they get overwritten.** The other microbatch's next DeepEP call allocates from the same comm-stream pool. Its kernels wait only on its own `previous_event`, captured on the compute stream before it yielded (#38451). The DBO comm stream itself waits only on that microbatch's compute-done event (`ubatching.py:86-87`, recorded in `yield_and_switch_from_compute_to_comm` before the yield). Both events were recorded before this microbatch enqueued its reads. So that call's outputs can land in the freed blocks and be written before the reads run. The DeepGEMM contiguous path then loads `expert_map[expert_id]` for whatever id it finds (`deep_gemm_utils.py:107-110`, called from `_fwd_kernel_ep_scatter_2` at `:244-247`), which is the faulting load in the core dump.
- **Reverse direction.** For experts that leave the weight-and-reduce to the prepare/finalize (`TopKWeightAndReduceDelegate`), `_finalize` reduces into a new compute-stream tensor (`apply(output=None)`, `:365`), and combine reads it on the comm stream (`:376`). `dbo_switch_to_compute()` (`:389`) does not order the compute stream after the combine. The tensor is freed when `_finalize` returns, so later compute-stream work, such as shared experts or the other microbatch, can reuse the block while combine is still reading it. On main, though, no experts class that can run behind DeepEP HT delegates: the delegating classes all use the batched activation format, DeepEP HT uses the standard one, and the standard CUTLASS FP8 and Marlin experts return `TopKWeightAndReduceNoOP`. Every experts class that can run behind DeepEP HT reduces itself (DeepGEMM, Triton, FlashInfer CUTLASS, ...), so the combine input is the per-microbatch workspace (or the caller's output tensor when the shapes match), which is not freed there. The `_finalize` call (1 of the 9) is therefore defensive on main, for a future delegating experts class. We did not observe this direction.
- **Dispatch inputs.** Tokens, scales, topk ids and topk weights are already safe today, because they are freed only after `dbo_switch_to_compute_sync()` makes the compute stream wait on the comm stream. They are recorded anyway (4 of the 9 calls), so their safety does not depend on that ordering; this is also the version validated on 0.29.

**Fix:** `_dbo_record_stream()` calls `t.record_stream(current_stream())` on each non-`None` tensor when `dbo_enabled()`. It is called in three places:
- in `_do_dispatch`, after switching to comm, on the dispatch inputs (compute to comm);
- in `_receiver`, before the `torch.where`, on DeepEP's outputs (comm to compute);
- in `_finalize`, after switching to comm, on the reduced expert output (compute to comm).

When a recorded tensor is freed, the allocator records an event on the consuming stream and does not reuse the block until that event has completed. For the two compute-to-comm sites the actual reader is DeepEP's internal stream. Recording the DBO comm stream still covers it, because with `async_finish=False` the DBO comm stream waits for DeepEP's kernels before dispatch or combine returns, and the tensors are freed after that. DeepEP's handle and layout tensors and `combined_x` are used only on the DBO comm stream and DeepEP's internal stream, so they are not recorded (but see "Not covered").

CUDA graphs: DeepEP HT is never captured. vLLM forces `cudagraph_mode` NONE for HT with DP > 1, and DBO needs DP > 1. PyTorch also supports `record_stream` during capture.

**Why FLASHINFER_CUTLASS does not crash, but may still race.** The hazard is in the prepare/finalize, so it does not depend on the experts backend; what differs is what a corrupted id does. FlashInfer's CUTLASS MoE receives `ep_rank`/`ep_size` and keeps only ids in this rank's range (`expert >= start_expert && expert < end_expert`, `cutlass_fused_moe_kernels.cuh:223,449` in FlashInfer 0.7.0.post1). A garbage id is therefore dropped instead of dereferenced, and garbage activations or weights would only produce wrong numbers. With FLASHINFER_CUTLASS, DBO matches DBO off on GSM8K: 0.922–0.927 on main in #60734, and 0.924 at EP32 above. So we have no evidence that the race fires there in practice. We also do not know why the window opens reliably for GLM-5.3 with DeepGEMM but not for DeepSeek-V2-Lite with DeepGEMM. #60734 notes an illegal memory access with DeepSeek-V3.2 and DBO that also uses FLASHINFER_CUTLASS and also disappears with `CUDA_LAUNCH_BLOCKING=1`. We have not tested whether this PR fixes it.

**Why ROCm already host-syncs.** #46990 added `_sync_dbo_comm_if_needed` (`deepep_ht.py:61,71-76`), a host `synchronize()` of the current stream after HT dispatch and combine under DBO, on ROCm only. Its comment cites reuse of "Buffer-owned communication workspace". Forcing the same sync on CUDA also removed the crash (0.29 table). We suspect ROCm hit the same allocator hazard, but we have no ROCm hardware to check, so this PR leaves the ROCm sync in place; on ROCm, `record_stream` only adds bookkeeping.

<details>
<summary>Alternatives considered</summary>

1. Use the host sync on CUDA as well. It works (0.29 table), but it blocks the CPU after every HT dispatch and combine of every microbatch: 300 times per step for GLM-5.3's 75 MoE layers. That gives up the CPU run-ahead DBO needs for overlap. Not benchmarked.
2. `allocate_on_comm_stream=True`. This moves the outputs to DeepEP's internal stream, but the compute stream still reads them, so on its own it does not order reuse. DeepEP also accepts it only together with `previous_event` and `async_finish=True`, and vLLM disables `async_finish` under DBO. Not tried.
3. `record_stream` (this PR). It marks exactly the tensors that cross streams, adds no syncs or kernels, and keeps the fix inside the one prepare/finalize that switches streams under DBO.
</details>

**Not covered:** blocks freed on the comm stream itself, for example `combined_x` after `output.copy_` in the finalize receiver, are reused by later comm-stream allocations. DeepEP's kernels for that later call wait on `previous_event`, a compute-stream event, rather than on the comm stream, so in principle they could run before the earlier comm-stream copy finishes. We inferred this from DeepEP's source (its internal stream waits on `previous_event` when one is given, otherwise on the calling stream) and have not observed it. `record_stream` cannot express this ordering. Passing `previous_event=None` under DBO would make DeepEP wait on the comm stream instead. That is left for a follow-up because it changes the ordering #38451 tuned.
