# [Multimodal] Cache PyNvVideoCodec decoder caps

[Upstream PR](https://github.com/vllm-project/vllm/pull/64618) · state: closed · merged: True

## Original PR description



## Overview

The PyNvVideoCodec (NVDEC) video backend calls `nvc.GetDecoderCaps` on every request, from `PyNvVideoCodecVideoBackendMixin._validate_decoder_caps`. Each call takes ~180 ms and holds the GIL, so it freezes the whole API server process for that long. The result only depends on the device, codec, chroma format and bit depth, so this PR caches it in a bounded LRU (64 entries).

## Claims

- **Removes ~185 ms of fixed cost from every NVDEC video request.** The caps check drops from 183–190 ms to 0.3–1.6 ms. It also removes the ~180 ms freeze of the API server's event loop per request.
- **Serving:** Nemotron-3-Nano-Omni NVFP4 on 1× GB300 with the default config: TTFT −19 to −45% and throughput 1.37–1.90× for clips up to ~30 s. Longer videos see −2 to −7% TTFT, because decoding dominates.
- **No regressions:**
  - Decoded frames are byte-identical, and unsupported videos are still rejected.
  - In the worst case, every lookup misses, and loading performs the same as main: latency within ±1%, throughput 1.00–1.02×.
- **Bounded:** at most 64 entries per API server process, 27 KiB when full. Real deployments use a handful.

## Details

### Why a bounded LRU

- **Caps never change while the server runs.** `GetDecoderCaps` reports what the GPU and driver can decode for a given (device, codec, chroma format, bit depth). Nothing in a request changes that, so the cache needs no invalidation. vLLM only reads `supported`, the width and height limits and `mb_num_max` from the result.
- **The cache must be bounded.** The key is read from the uploaded file's stream headers, so an unbounded cache (`functools.cache`) would grow with every new format a client sends. `functools.lru_cache(maxsize=64)` caps memory with one decorator and keeps the formats in use resident.
- **Why not per decoder slot.** Caps depend on the device and stream format, not on a slot:
  - One slot serves every format the traffic contains. On GB300, a single slot decoded H.264 → VP9 → H.264 → MPEG-4 → VP9 through `reconfigure_decoder`, without a rebuild.
  - Caps are needed before a slot is borrowed: they reject unsupported streams and set the maximum dimensions the slot's decoder is configured with.
  - A per-slot copy would miss on every format switch and after every slot recovery, and a client can trigger slot recoveries by sending corrupt videos.

### Why 64

- **Far above real use.** A deployment sees a handful of keys per device, for example H.264, HEVC, VP9 and AV1 at 4:2:0, 8- or 10-bit. With 64 entries, steady-state traffic always hits.
- **Deliberately below the full key space.** PyNvVideoCodec has 12 compressed codecs × 4 chroma formats × 8, 10 or 12 bits, about 144 combinations per device. Most of those match no real video. The bound only needs to stop unbounded growth, not hold every possible key.
- **Overflow is no worse than main.** If traffic cycles through more than 64 formats, lookups miss and each request calls `GetDecoderCaps`, as main does today. The benchmark's "worst case" column misses on every lookup and matches main within ±1%.
- **Cheap when full.** Each entry is a 10-key dict. A full cache measured 26.9 KiB with `tracemalloc`, 431 B per entry.
- **Not a tuning knob.** Any size between the number of formats in use and a few hundred performs the same. 64 is a round number with an order of magnitude of headroom.

### Other details

- **`nvc` is part of the key.** Production always passes the PyNvVideoCodec module, so this costs nothing. It stops the existing tests' fake `nvc` classes, which return different caps for the same codec, from sharing entries.
- **Threads.** `lru_cache` is safe to call from the media thread pool. Two requests racing on a cold key may each call `GetDecoderCaps` once, which is harmless.
- **Failures.** A `supported == 0` result is cached, and the existing checks still reject the video. If `GetDecoderCaps` raises, nothing is cached.
- **Shared result.** Callers get the same dict object. `_validate_decoder_caps` only reads it, and the docstring says not to mutate it.
- **CI.** The new test uses a fake `nvc`, like the neighboring decoder-caps tests, so it needs no GPU. The existing `pytest -m 'not cpu_test' multimodal` Buildkite step picks it up.
- **Not a duplicate.** I searched open PRs for `GetDecoderCaps`, "pynvvideocodec caps" and "decoder caps" and found none. #52605 also edits these two files (pool lease accounting), but in different hunks, and it merges cleanly with this PR.
- **Out of scope.** `GetDecoderCaps` itself is slow and doesn't release the GIL. That is worth raising with the PyNvVideoCodec maintainers separately.
