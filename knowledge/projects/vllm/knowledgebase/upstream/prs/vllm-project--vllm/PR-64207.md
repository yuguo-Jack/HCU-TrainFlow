# [ROCm][Perf][GLM-5.3-Flash] MonoKernel: take the mHC Sinkhorn off the gate's critical path (on #61662)

[Upstream PR](https://github.com/vllm-project/vllm/pull/64207) · state: open · merged: False

## Original PR description

## Overview

Takes the mHC Sinkhorn off the critical path of the GLM-5.3-Flash MonoKernel's gate. Median decode ITL drops 6.7% at concurrency 1 and 6.9% at concurrency 4 (TP2, MI355X, real-text prompts), with bit-identical outputs.

**Stacked on #61662**, which has not landed, so the diff against main includes it. This PR's own change is the last commit, `bcba53a68f` (+72 / −66, one file: `mono/ffn/kernel.py`, `run_gate`). I'll rebase when #61662 lands.

**Independent of the KV cache dtype.** The gate runs before attention in every MonoKernel launch (the attention gate before qkv, the FFN gate before the router) and touches no KV state, so the gain carries over unchanged to the e4m3 KV path, bf16 KV, and the `mxfp4_mla` KV of #64121.

## The change

Each gate computes `pre`, `post`, and a 4×4 `comb` matrix normalised by 20 Sinkhorn iterations. Before this PR, thread 0 did all of it serially and only then wrote the layer input row, which the rest of the launch waits on. Traced at TP2 (S=2, 2,048 context), the Sinkhorn alone took 5.0–6.9 µs per gate, twice per launch.

- **16 lanes.** The Sinkhorn now runs on 16 lanes of wave 0, with lane `4i + j` holding `comb[i][j]`. Row and column sums come from lane shuffles, added in the sequential loop's order, so every `comb` value is bit-identical to before.
- **After the row.** Only a later seam reads `comb`, so the layer row is written first and the Sinkhorn runs after it, off the critical path.
- **Smaller moves.** `pre` and `post` move to 8 lanes, and the scale and base loads are issued before the mailbox wait.

## Performance

A/B on this exact branch: #61662 at `0ea31fadbd` against this PR's `bcba53a68f`. ## Accuracy

The float operations and their order are unchanged, so outputs are bit-identical. No paired GSM8K/GPQA runs were done, since there's nothing for them to measure.

**Kernel outputs, bit for bit.** #61662's head and this branch each ran one FFN launch and one KDA launch (the attention gate, then the FFN gate) at TP2, widths 2 and 4, on the same seeded weights and inputs. Every output (`x`, residual, `post`, `comb`) and the KDA conv and recurrent states are bit-identical on both ranks at both widths.

**Served greedy outputs aren't a usable check here.** Both trees served the same 8 prompts at temperature 0 (256 tokens each, one at a time, and four concurrently). The outputs differ, but several differ at the first generated token, which comes from prefill and never runs the MonoKernel. So this server config isn't deterministic from one run to the next. A control confirms it: #61662's head served twice against itself diverges on all 12 comparisons too, 4 of them at the first token.
