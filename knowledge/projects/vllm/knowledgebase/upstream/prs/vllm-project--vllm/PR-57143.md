# [Misc] Removing unreachable condition

[Upstream PR](https://github.com/vllm-project/vllm/pull/57143) · state: open · merged: False

## Original PR description

## Purpose

With caching disabled, block hashes are `None`, which makes the 2nd part of this condition redundant / unreachable code:
`if block.block_hash is None or not self.enable_caching:`
Consider removing to avoid confusion and simplify code:
`if block.block_hash is None:`

## Test Plan
I've asked Claude to verify if this is unreachable.

## Test Result
Response:

### It's provably redundant

For a block in this pool to have `block.block_hash is not None`, some path must call `set_block_hash` (only reachable via `BlockPool._insert_block_hash` at [block_pool.py:624](vllm/v1/core/block_pool.py#L624)). All callers require the pool's `enable_caching=True`:

- [`cache_full_blocks`](vllm/v1/core/block_pool.py#L231) / [`cache_partial_block`](vllm/v1/core/block_pool.py#L452) → called from `SingleTypeKVCacheManager.cache_blocks`, gated by [`if not manager.enable_caching: continue`](vllm/v1/core/kv_cache_coordinator.py#L347) in the coordinator; the manager's flag is the same one the pool got.
- [`move_block_hashes`](vllm/v1/core/block_pool.py#L646) → only fires when the source already has a hash (so caching was on).
- [`simple_kv_offload/manager.py:1026`](vllm/v1/simple_kv_offload/manager.py#L1026) → operates on a `cpu_block_pool` that is hard-coded [`enable_caching=True`](vllm/v1/simple_kv_offload/manager.py#L194).

So on any pool with `enable_caching=False`, no block ever gets a hash → `block.block_hash is None` alone would already send every block down the LIFO branch. The `or not self.enable_caching` extends it to be a global short-circuit for the whole pool (arguably a hair cheaper — skips the per-block attribute read), and it documents intent, but it is not a case that the first clause misses.
