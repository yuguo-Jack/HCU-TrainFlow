# [ROCm][Perf][MoE] Trim MoRI dispatch output to rows that can hold a token

[Upstream PR](https://github.com/vllm-project/vllm/pull/63412) · state: open · merged: False

## Original PR description



## Overview

MoRI's `dispatch()` returns its whole preallocated receive buffer, so the expert GEMMs run over `num_dispatchers * max_num_tokens` rows on every step, including one-token decode steps. This slices the dispatch output to the rows that can hold a token, using a host-side bound from `DPMetadata`. Related: #53108 trims the same output for an AITER correctness issue using `dispatch_recv_token_num.item()`; see Details for how the two differ.

## Claims

- DeepSeek-V4-Flash PD decode on MI300X with MoRI EP: **TPOT 855 ms → 30 ms** at concurrency 1 (EP16).
- No GPU→host synchronization: the bound comes from `num_tokens_across_dp_cpu`, which is already on the host, so it is the same under eager execution and CUDA-graph capture.
- No-op whenever the bound covers the whole buffer (prefill, `profile_run`) or DP metadata is absent.

## Validation

**End to end**, disaggregated prefill/decode (MoRIIO KV connector, vllm-router), `-tp 1` + DP8 + MoRI EP per role, MI300X (gfx942), ROCm 7.2, `max_num_batched_tokens=1024`, `vllm bench serve` random 1024 in / 1024 out, median TPOT (ms):

| V4-Flash 2P/2D EP16 | **with** | **29.6** | **30.8** | **33.9** | **42.4** |

## Details

**Root cause.** `MoriPrepareAndFinalize.prepare` hands the modular kernel the tensors returned by `mori_op.dispatch`, which are views of MoRI's full receive buffer, `(num_dispatchers * max_num_tokens, hidden)`. The experts size their GEMMs from that row count, so a decode step with one token per rank runs the experts over the prefill-sized buffer (8192 rows at EP8 with `max_num_batched_tokens=1024`), and decode cost is set by the buffer rather than the batch.

**Bound.** Each source rank sends a destination at most one copy of each of its tokens, and received tokens are packed from row 0, so at most `num_dispatchers * max(tokens on any DP rank)` rows are live. `max(...)` comes from `DPMetadata.num_tokens_across_dp_cpu` (and the local token count), so the slice is computed on the host from data the forward context already holds, and it is fixed for a given padded batch, which keeps it valid under CUDA-graph capture.

**vs #53108.** #53108 reads `dispatch_recv_token_num[0].item()` outside capture (one device→host sync per MoE layer per step) and falls back to `input_tokens * topk * ep_size` under capture. This PR's bound is looser than the exact received count but needs no sync and is the same in both modes. The two would conflict on the same lines in `prepare()`; happy to consolidate with @amd-weisun on whichever shape maintainers prefer.

**Limitations.** The bound is an upper limit, not the exact count, so a skewed step still runs some empty rows. Only the MoRI prepare/finalize is changed; other all2all backends are untouched. CI has no multi-node MoRI EP hardware, so end-to-end validation was done outside CI as above.
