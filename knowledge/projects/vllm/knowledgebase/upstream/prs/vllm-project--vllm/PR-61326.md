# [Bugfix][Spec Decode] Serialize batch queue for spec decode + PP

[Upstream PR](https://github.com/vllm-project/vllm/pull/61326) · state: open · merged: False

## Original PR description

## Overview

With speculative decoding + pipeline parallelism + async scheduling disabled, the PP batch queue schedules step N+1 before step N's output is processed; the plain scheduler lacks the overlap compensation AsyncScheduler has, so the worker asserts (`num_scheduled_tokens_np >= num_logits`, `model_runner.py:1403`) and the PP0 worker dies mid-step (PP1+ hang in NCCL irecv). This change serializes the batch queue for that configuration.

Delivers the e2e repro against current main requested by @njhill in #60902, plus the fix for the root cause it exposed. Related: #54437 documents the async-path staleness of the same draft hand-off (different failure mode); #54442 (merged) makes stale drafts fail closed; #56802 (closed) proposed snapshot identity for the async path.

**Not a duplicate:** searched upstream for the assert and the batch-queue race — no existing issue or PR reports the non-async count under-count:
- `gh search issues --repo vllm-project/vllm "num_scheduled_tokens num_logits"` → 0 hits
- `gh search issues --repo vllm-project/vllm "MTP pipeline parallelism"` / `"spec decode pipeline parallel hang"` → 0 hits
- #54437 / #54442 / #56802 all address the async-scheduling staleness path, not this.

## Claims

- Bug fix: spec decode + PP>1 + async scheduling disabled crashes the worker on the first overlapped spec decode steps (assert in `prepare_inputs`); after this change the same configuration serves correctly.
- The bug is spec-method-agnostic and model-agnostic: the vanilla-main before/after repro pair is OLMoE-1B-7B + ngram (PP=2); an earlier independent repro (GLM-5.3 + MTP, PP=3/TP=2, on a nightly tree) hit the same assert with the same root cause.
- The async V2 path (`pp_size + 1`) is unchanged: the new branch sits after the async early-returns and is unreachable there (unit-tested).

## Validation

**Unit tests** (hermetic, no GPU):

```bash
pytest tests/test_config.py -k max_concurrent_batches -q
# 3 passed: spec+PP+async-off -> 1; no-spec+PP -> pp_size; spec+PP+async+V2 -> pp_size+1
```

**E2E reproducer** (any 2 GPUs; also validated on 2×96GB Ampere):

```bash
vllm serve <OLMoE-1B-7B-0125-Instruct> --pipeline-parallel-size 2 \
  --max-model-len 4096 --no-async-scheduling \
  --speculative-config '{"method":"ngram","num_speculative_tokens":2}'
# then 4 concurrent chat requests with a repetitive prompt (ngram proposes every step)
```

- Before (vanilla main `c077dc663d`): `AssertionError` at `model_runner.py:1403` within seconds; PP0 dead, PP1 hung in irecv.
- After (this change): identical config and workload → 4/4 clean completions, zero asserts. Async variant (`ngram_gpu` + `--async-scheduling`) also serves cleanly, zero asserts.

**Throughput micro-bench** (OLMoE-1B, PP=2, 8 concurrent × 256 max_tokens, 2 runs each):

| Config | Spec method | Aggregate tok/s |
|---|---|---|
| non-async (serialized by this change) | ngram | 1137 / 1166 |
| non-async (serialized by this change) | ngram_gpu | 1150 / 1094 |
| async | ngram_gpu | 657 / 666 |

On this micro-bench the serialized configuration shows no throughput cliff (the 1B model's async per-step overhead dominates; cost on deeper pipelines/larger models is a tradeoff — see Details).

## Details

**Root cause** (all cites at base `c077dc663d`):

- The engine-core batch queue exists to fill the PP pipeline and deliberately schedules ahead: "fulfilling the batch queue has a higher priority than getting model outputs" (`vllm/v1/engine/core.py:700-790`). `schedule()` for step N+1 runs before `update_from_output(N)`.
- `AsyncScheduler` compensates for that overlap on both sides: `num_output_placeholders += num_sampled_tokens_per_step + cur_num_spec_tokens` (`async_scheduler.py:45-47`) and `-1` draft placeholders that the worker fills from GPU-resident drafts (`:50`).
- The plain `Scheduler` — used when async scheduling is disabled — never increments `num_output_placeholders` (only resets it on preemption/session reset, `scheduler.py:1607/:2478`), so step N+1's `num_new_tokens = num_tokens_with_spec + num_output_placeholders - num_computed_tokens` (`scheduler.py:703-707`) under-counts by step N's in-flight sampled + spec tokens.
- The worker still builds bonus + draft logits rows for the scheduled spec slots, so `num_scheduled_tokens_np < num_logits` trips the assert (`model_runner.py:1403`). Per the comment above it, a shortfall would otherwise *silently select the preceding request's hidden states* — a correctness hazard, not just a crash.

**Fix:** `max_concurrent_batches` returns 1 when `pp_size > 1` and speculative decoding is configured, after the async early-returns — serializing the queue so each step settles before the next is scheduled. Validated e2e on the vanilla-main repro pair; the earlier GLM-5.3 + MTP PP3/TP2 validation (nightly tree) served with 422/531 draft acceptance under the same serialization.

**Tradeoffs and limitations:**

- Serialization gives up PP overlap for spec decode on the non-async path (prefill overlap included). The deeper fix — porting the placeholder compensation to the plain scheduler — would restore overlap, but it interacts with preemption and stale-output handling (`num_output_placeholders` resets, stale-delivery guards) and needs its own validation matrix; offered as follow-up work rather than bundled here.
- V1 runner + async + spec + PP now serializes too (falls through to the new branch): conservative, on a deprecated path already flagged as not fully supporting async scheduling with PP.
- With `max_concurrent_batches == 1`, `defer_block_free` stays off for KV-consumer configs — correct at size 1 (a single in-flight batch has no free/write ordering hazard); UVA pool depth and `max_in_flight_tokens` shrink consistently with the queue.
- The e2e reproducer is GPU-marked and not part of CI (multi-GPU + spec-decode CI coverage gap); the unit tests guard the config contract and the commands above reproduce the e2e behavior.
