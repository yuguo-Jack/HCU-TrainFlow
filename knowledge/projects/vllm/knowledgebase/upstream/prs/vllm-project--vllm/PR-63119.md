# [Perf][GLM-5.x] DeepGEMM FP8 MegaMoE for DeepseekV2MoE (DSA models, PCP)

[Upstream PR](https://github.com/vllm-project/vllm/pull/63119) · state: open · merged: False

## Original PR description

## Overview

Follow-up to #60895: run the routed experts of `DeepseekV2MoE` through #60895's block-FP8 DeepGEMM MegaMoE experts, for the DSA models (GLM-5.x, DeepSeek-V3.2: `GlmMoeDsaForCausalLM` / `DeepseekV32ForCausalLM` and their MTP). Enabled with `--moe-backend deep_gemm_mega_moe` (`--tensor-parallel-size 1 --enable-expert-parallel`, data parallel or prefill context parallel).

**Stacked on #60895**: only the last commit (`[Perf][GLM-5.x] DeepGEMM FP8 MegaMoE for DeepseekV2MoE (DSA models)`) is new here. Draft until #60895 lands; I'll rebase then.

## Changes

- `DeepseekV2MoE`: when the backend is `deep_gemm_mega_moe` and the caller allows it (`allow_mega_moe=True`, set by the DSA decoder layer), build `Glm5NextMegaMoEExperts` instead of `FusedMoE`:
  - routing (`scoring_func` + `e_score_correction_bias`, renormalized, times `routed_scaling_factor`) with `fused_topk_bias` before the kernel;
  - the shared expert stays a separate MLP (no shared-expert fusion yet);
  - requires EP, TP=1, one expert group, `noaux_tc` routing and a block-FP8 checkpoint; other configurations raise `NotImplementedError`.
- DSA model and MTP: expert weights load into the kernel layout (`routed_experts_prefix=""`), `process_weights_after_loading` requantizes them (UE8M0 1x32), and layerwise reload is refused until #57733, as in #60895.
- Other backends and other `DeepseekV2MoE` users are unchanged; DeepSeek-V2/V3 with this backend get a clear error.

**Prefill context parallelism** needs no extra handling: MegaMoE is a collective over the EP group, and with PCP every EP rank runs each MoE layer once per step on the same padded token count, so the kernel calls stay matched.

## Validation

Measured with a prototype of the same integration on vLLM v0.31.0 (same routing, same requantization rounding as #60895, shared expert outside the kernel), GLM-5.3 FP8, one 8x B300 node, PCP8 x EP8, MTP 1. Same pod and identical prompts; only the MoE differs:

| | FlashInfer TRT-LLM | MegaMoE |
|---|---:|---:|
| GSM8K, 1,319, greedy, chat | 96.36% | 96.59% |
| Long-context retrieval, 5 depths, 32k / 64k / 128k / 187k tokens | 20/20 | 20/20 |
| Cold prefill, 16k prompts, 8 / 24 in flight | 54.0k / 55.9k tok/s | 85.8k / 90.8k tok/s (+59% / +62%) |

GSM8K: 7 questions right only with TRT-LLM, 10 only with MegaMoE (McNemar p = 0.63).

Not yet run on this branch itself (main + #60895 + this commit): I'll repeat the same checks on B300 and post them here before marking it ready. `tests/models/deepseek_v32/test_mega_moe_wiring.py` covers the loader helpers on CPU.
