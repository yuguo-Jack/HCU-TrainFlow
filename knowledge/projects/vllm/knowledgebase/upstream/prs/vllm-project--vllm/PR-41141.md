# [EPLB] Add offline expert mapping support (aka "offline EPLB")

[Upstream PR](https://github.com/vllm-project/vllm/pull/41141) · state: open · merged: False

## Original PR description

## Purpose

Adds offline EPLB support: collect expert-load stats during a representative run, save them to a file, then reload them at startup of a different server to apply a static physical-to-logical mapping before warmup.

## Test Result

### Performance

Hardware: 8xB200, model `nvidia/Qwen3.5-397B-A17B-NVFP4` (DP=8 EP).

For each dataset the corpus is split 50/50 into two parts. Schedule is recorded on `part1` and perf is measured on `part2` — independent data.

| Dataset (size after 50/50 split) | Baseline | Online EPLB | Offline EPLB | Δ Total token throughput (tok/s) |
| --- | --- | --- | --- | --- |
| [AI4Chem/ChemData700K](https://huggingface.co/datasets/AI4Chem/ChemData700K) (~324k/half) | 6745.20 | 6873.39 | 6981.33 | +3.5% |
| [nvidia/OpenMathInstruct-2](https://huggingface.co/datasets/nvidia/OpenMathInstruct-2) (~303k/half) | 6473.46 | — | 6717.14 | +3.8% |
| [ise-uiuc/Magicoder-Evol-Instruct-110K](https://huggingface.co/datasets/ise-uiuc/Magicoder-Evol-Instruct-110K) (~55k/half) | 6381.60 | — | 6598.05 | +3.4% |

<summary>Bench commands</summary>

Shared server flags: `-tp 1 -pp 1 -dp 8 --enable-expert-parallel --language-model-only --reasoning-parser qwen3 --stream-interval 100 --enable-eplb`. Only the `--eplb-config` and the per-dataset bench arguments differ.

```
# Step 1: collect stats on part1 (also doubles as the baseline reference
# for math / code, since `save_path` records stats but does not apply any
# rearrangement)
vllm serve nvidia/Qwen3.5-397B-A17B-NVFP4 --port 8000 [shared flags] \
    --eplb-config '{"save_path":"./cumulative.safetensors","step_interval":256,"communicator":"torch_gloo"}'

# Step 1 (chemistry only): separate no-schedule baseline server on part2
vllm serve nvidia/Qwen3.5-397B-A17B-NVFP4 --port 8000 [shared flags] \
    --eplb-config '{"step_interval":100000,"communicator":"torch_gloo"}'

# Step 2: offline EPLB server (schedule loaded, online rearrange pinned off)
vllm serve nvidia/Qwen3.5-397B-A17B-NVFP4 --port 8000 [shared flags] \
    --eplb-config '{"load_path":"./cumulative.safetensors","step_interval":100000,"communicator":"torch_gloo"}'

# Client (3 runs each phase, paired --seed across baseline/offline)
vllm bench serve --backend vllm --model nvidia/Qwen3.5-397B-A17B-NVFP4 \
    --port 8000 --endpoint /v1/completions --temperature 0.0 \
    --dataset-name custom --dataset-path ./<dataset>/part<N>.jsonl \
    --custom-output-len 2048 --skip-chat-template \
    --num-prompt <NUM_PROMPT> --max-concurrency 128 \
    --seed <random per iter, same value in baseline and offline>

# Per-dataset bench params:
#   chemistry: num-prompt 1024
#   math:      num-prompt 1024
#   code:      num-prompt 512  (sized down so a single run finishes in ~2 min)
```

- SageMoore · COMMENTED · 2026-05-19T15:09:25Z · [source](https://github.com/vllm-project/vllm/pull/41141#pullrequestreview-4319547534)

Hi, @arpera. Thanks for the contribution. I have two high level pieces of feedback for this PR.

First, just to give some more context, we've been working on making Async EPLP the most performant and low-overhead way to run EPLB for a while now. With the NIXL backend, we've been able to get rid of the numerous hangs and overlapping the expert transfers with the forward pass has gone a long way towards making EPLB cheaper to run. Frankly there's a bit more work to do here, but the main benefit of a more performant EPLB is that you can run it more frequently increasing the balancedness, which increases the overall throughput.

It's not clear to me that the approach here is the best way forward. The idea of an informed initial placement makes sense, and the benchmarks you posted do show a decent performance improvement. However, if we ran EPLB after some small number of initial steps I suspect that we could probably get similar results with lower user friction. EPLB is primarily a Wide EP feature, meaning pushing/pulling files is a bit more cumbersome. Not impossible obviously, and definitely automatable, but still there's friction. I'm interested to hear your thoughts on this.

Second, given that this is a somewhat niche feature, let's try to sequester the code for it as much as possible. I've left some comments on how I think that could be done.

- arpera · comment · 2026-05-19T19:43:29Z · [source](https://github.com/vllm-project/vllm/pull/41141#issuecomment-4491412859)

Thank you @SageMoore for a detailed review!

I agree that on practice the difference between offline and online EPLB is likely to be small, and that online EPLB requires fewer intermediate steps. My motivation for offline EPLB is based on the following.

First, offline and online EPLB modes are orthogonal to each other, which means they can be used either independently or together. In other words, offline EPLB is not a replacement for online EPLB. Offline EPLB complements online EPLB and can be used by users who understand their inference workload pattern well enough.

Second, offline EPLB has one important advantage over online EPLB: it does not require additional communications between ranks during inference. This is beneficial because it improves the overall robustness of the system, since hard bugs to detect and debug usually happen during all2all communications. In case of distributed serving, robustness becomes even more important, because in such systems anything can go wrong, and that is normal. In this case reducing amount of communications in inference makes sense for me.
