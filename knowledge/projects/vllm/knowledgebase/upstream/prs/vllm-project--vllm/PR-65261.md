# [MoE][Model Loader] Fused-expert fast path in RoutedExperts.load_weights for every MoE model that loads through it; HY-V3 moves to it

[Upstream PR](https://github.com/vllm-project/vllm/pull/65261) · state: open · merged: False

## Original PR description

## Purpose

Part of #64418 (L1, the first of several PRs; replaces #54477 F1).

RL trainers send routed experts in either form of #64418 §2: per expert
(`experts.E.{gate,up,down}_proj.weight`, as Hub checkpoints store them) or the transformers v5 fused
form (`experts.gate_up_proj` `[E, 2I, H]`, gate rows then up rows; `experts.down_proj` `[E, H, I]`).
`RoutedExperts.load_weights` on main accepts both, but loads a fused tensor with one
`weight_loader` call per expert. 54 model files don't use it for loading at all: they hand-roll a
`make_expert_params_mapping` loop that only matches per-expert names.

This PR:

1. Loads a fused tensor already on the parameter's device with one `narrow` + `copy_` per shard and
   run of local slots (one run per shard for linear EP), expert TP included. This is the direct-reload
   / direct `load_weights` case; cold start and layerwise reload keep the per-expert path.
2. Fills EPLB redundant replica slots from fused tensors, which main never did (only per-expert
   names filled them).
3. Adds `load_routed_experts_weight(model, name, tensor)` for hand-rolled loaders whose name
   rewriting doesn't fit `AutoWeightsLoader` + `WeightsMapper` (most MTP/draft loaders); family PRs
   may move simple loaders to `AutoWeightsLoader` instead.
4. Moves HY-V3 and HY-V3 MTP to it, as the first family.

Not duplicating: no open PR changes fused loading in `RoutedExperts.load_weights` or the HY-V3
loaders. #64352 changes `_load_model_weight_or_group_weight_scale` (`is_scale` becomes `param`);
whichever lands second rebases with a one-line change at the fast-path call site.

## Models covered

- **Fast path (v5 fused expert names on a device-tensor reload):** every MoE model whose routed experts load through
  `RoutedExperts.load_weights`, i.e. through `AutoWeightsLoader` with no hand-rolled expert mapping loop. By grep of
  `vllm/model_executor/models/`, that is AfMoE, Alice-AI, Aria, Bailing-MoE, Nomic BERT MoE (`bert_with_rope`),
  Cohere2-MoE, Ernie 4.5 MoE, EXAONE-MoE, Gemma 4, GLM-4 MoE, GraniteMoE, InternS1-Pro, InternS2-Mobius, Jamba,
  Laguna, LFM2-MoE, MiniMax-M2, Mixtral, Nemotron-H, OpenPangu, Param2-MoE, PhiMoE, Qwen2-MoE, Qwen3-MoE, Qwen3-Next and Sarvam,
  plus models built on them (Qwen3-VL-MoE, Qwen3-Omni-MoE thinker).
- **Moved to the shared helper in this PR:** HY-V3 and HY-V3 MTP. They gain the fused form, and EPLB replicas are
  now loaded.
- **Shared per-expert code:** the per-expert `weight_loader` path (refactored, same bytes) is used by every MoE model,
  including the hand-rolled loaders below. Cold start keeps the per-expert path (cross-device copies are excluded),
  and so does layerwise reload.
- **Unchanged here (hand-rolled `expert_params_mapping` loops; follow-up family PRs, see "L1 split"):** DeepSeek-V2
  family and MTP/Eagle, gpt-oss, Llama 4 / mLlama 4, GLM-4 MoE Lite (+ MTP), GLM-4 MoE MTP, LongCat-Flash
  (+ MTP, n-gram), MiMo-V2, Step3 / Step3.5 (+ MTP), Nemotron-H MTP, Bailing-MoE linear / v3 (+ MTP),
  Ernie 4.5 VL MoE, MiniCPM (+ Eagle), K2-Horizon, AXK1, OpenPangu MTP, GraniteMoE hybrid. gpt-oss (`[E, H, 2I]`
  interleaved) and Llama 4 (transposed) keep their own loaders.
- **Delegates but keeps the per-expert path:** DBRX (its own `weight_loader`, which the fast path skips).
- **Bypassed:** subclasses that override `RoutedExperts.load_weights` (Muse Spark, the Transformers backend).

## Changes

- `RoutedExperts._covers_fused_load` / `_load_fused_experts` (new). The predicate accepts only the
  `weight_loader` branches that narrow and copy: model weights and GROUP/BLOCK scales (FP8 block
  `gate_up_proj_scale_inv` / `down_proj_scale_inv` map to `w13_/w2_weight_scale_inv`); a comment in
  `weight_loader` points back to it. Each run calls the same `_load_model_weight_or_group_weight_scale`
  as the per-expert path with the expert dim kept, local ids come from the same
  `_map_global_expert_id_to_local_expert_id`, and the FP8 block-scale upsample is one shared
  `_refine_block_scale`, so the bytes are the same. Everything else loads per expert as on main:
  copies across devices (cold start from CPU safetensors, where one strided multi-expert copy would
  need full-size temporaries, so cold start is unchanged; reloads from device tensors take the fast
  path under `VLLM_RELOAD_MODE=direct` or a direct `load_weights` call, while the default layerwise
  reload wraps the loaders and stays per expert, now including replicas), loaders other than the layer's own `RoutedExperts.weight_loader` (Dbrx, gpt-oss,
  layerwise/online wrappers, ...), the online shared-expert loader, `is_transposed`
  (GPTQ/AWQ/CT WNA16), ModelOpt, `gpt_oss_mxfp4`, biases, input scales, `weight_shape`, and
  per-tensor / per-channel scales (no v5 fused checkpoint form that I know of).
- `RoutedExperts._fused_expert_slots`: (physical id, tensor index) of every slot a fused tensor
  fills, from the initial physical→logical map; used by the fast path and the per-expert fallback.
- `RoutedExperts.load_expert_weight` (new, public): the per-tensor body of `load_weights`. Returns
  the names written, or None when the name matches no mapping entry; `load_weights` logs
  `warning_once` per name pattern for those (AutoWeightsLoader models keep loading as before).
- `RoutedExperts._indexed_expert_mapping`: caches the mapping and its index, keyed on the LoRA
  prefix and expert counts. Uncached they cost ~430 µs per call at E=192 (~15 s per load of a
  60-layer model when called per tensor); cached, a per-tensor call costs ~31 µs, the same as the old
  mapping scan.
- `RoutedExperts._loading_quant_method`: the online-requantization unwrap, shared with `weight_loader`.
- `load_routed_experts_weight` (`fused_moe/layer.py`): finds the MoE layer at the name's
  `...experts` prefix, unwraps a LoRA wrapper (names under `base_layer.`, as on main), and calls
  `load_expert_weight`. Returns the set of names written (empty when no expert of the tensor is on
  this rank), or None when the name is not under a MoE layer (e.g. PP-missing) or matches no mapping
  entry, so the caller falls through and an unknown name raises `KeyError` as on main. Note: it
  calls `RoutedExperts.load_expert_weight` directly, so a subclass that overrides `load_weights`
  (Muse Spark, Transformers backend) would be bypassed; no L1 family uses one.
- HY-V3 and HY-V3 MTP: the mapping loop is replaced by the helper; both now also take the v5 fused
  form. With EPLB redundant experts, replicas are now loaded (the old mapping left out
  `num_redundant_experts` and the loop stopped at the first local replica).
- Tests: `tests/kernels/moe/test_routed_experts_fused_load.py`,
  `tests/models/test_hy_v3_expert_loading.py` (added to Basic Models (Other)); shared builders
  `routed_expert_checkpoint` / `fake_moe_layer` in `tests/kernels/moe/utils.py` for the family PRs.

gpt-oss (`[E, H, 2I]` interleaved) and Llama4 (transposed) keep their own loaders.

How the fused sync was run (Qwen3 row): the server cold starts from the checkpoint. A trainer on a third GPU then
sends two NCCL updates (packed). The first is the checkpoint with every tensor's elements rolled by one, under the
same names, shapes and dtypes (per-expert names). The second is the real weights, with the routed experts sent in
the transformers v5 fused form: `mlp.experts.gate_up_proj` [128, 1536, 2048] (gate rows, then up rows) and
`mlp.experts.down_proj` [128, 2048, 768]. Everything else keeps its checkpoint name, for 531 tensors and 61.1 GB in
total. The trainer holds the weights on its GPU before the sync starts. The time reported is the wall time of
`send_weights()`: the transfer plus loading on the server, through `finish_weight_update` (post-load processing
rerun included).

The audit extension compares tensor digests after each sync:
- After the scrambled sync, 870 of the 1256 registered tensors per run differ from cold start, including every
  expert weight. The 386 unchanged tensors are the attention q/k/v/prob scales and the rotary cache, which no
  checkpoint tensor writes. So the real sync starts from wrong weights.
- After the real sync, all 1256 tensors are byte-identical to cold start, in both arms and in every round.

Notes:
- **Fused-sync speed:** the real sync takes 0.86–0.93 s on B and 1.42–1.59 s on A, over 6 samples per arm in two
  orders. That is about 40% less time (0.57 s less) for a 61 GB update. The scrambled sync uses per-expert names, so
  the fast path does not apply to it, and it takes the same time in both arms (1.83–2.22 s), as expected.
- Noise: GSM8K moves by up to 0.7 pt between runs of the same arm (Hy3 B 0.9538 / 0.9469; DSV4 B 0.9462 / 0.9500).
  Throughput follows run order, not the arm. The first arm of a job also runs the 192-prompt calibration bench, and
  the second reuses its prompt count without a warm-up. Hy3: 1111 / 1006 tok/s for A, 1002 / 989 for B; the gap is
  −9.8% in the first order and −1.7% swapped. DSV4: −12% first, +9% swapped. Qwen3: +0.9% first, −1.6% swapped.
  MTP acceptance and KV cache are unchanged. No regression.
- The DSV4 bench ran about 70 s, not about 2.5 min: the calibration ran on a cold server, so it underestimated the
  throughput and too few prompts were sent.
- DSV4 setup: the serve args follow `tests/evals/gsm8k/configs/DeepSeek-V4-Flash-EPLB-TEP4.yaml` without EP/EPLB:
  `--tokenizer-mode deepseek_v4 --max-model-len 8192 --block-size 256 --kv-cache-dtype fp8
  --attention_config.indexer_kv_dtype=mxfp4 --max-num-batched-tokens 16384 --max-num-seqs 128`. They also add
  `--compilation-config.cudagraph_mode FULL_DECODE_ONLY`. On main (arm A) the default `FULL_AND_PIECEWISE` crashes in
  piecewise cudagraph capture: `sparse_attn_indexer` calls `max()` on an empty `prefill_metadata.chunks`. This is not
  related to this PR.
- Hy3 setup: GSM8K uses chat completions, with the template default `reasoning_effort=no_think`. The server runs
  `--reasoning-parser hy_v3` with MTP (2 speculative tokens), so the HY-V3 MTP loader is exercised too.
- What each row covers. Hy3 covers the migrated HY-V3 / HY-V3 MTP loaders on per-expert checkpoint names at cold
  start; it does not use the fast path. DSV4 covers the shared `RoutedExperts.weight_loader` / `load_weights` code at
  cold start. Qwen3 covers the fast path itself, against main's per-expert loop over the same fused tensors.
- Not run: FP8 block-scale fused tensors through the fast path (`*_scale_inv`), EP / EPLB replicas on GPU, and a
  layerwise-mode (default) reload of fused names.

## L1 split

Follow-up family PRs move 47 files in 14 groups plus the four Step files to the helper. The helper
maps names with the layer's `ckpt_names`, so DeepSeek-V4 amd/xpu/cpu, Kimi-K3 and MiniMax-M3 must
first declare `ckpt_names=("w1", "w2", "w3")`; otherwise the helper returns None and the loader
raises `KeyError`. MegaMoE experts, gpt-oss, Llama4, mllama4 and Ernie-4.5-VL keep their loaders.
