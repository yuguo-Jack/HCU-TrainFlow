# [ROCm][Kimi-K3] Keep one persistent AttnRes block bank

[Upstream PR](https://github.com/vllm-project/vllm/pull/63838) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Kimi-K3 on ROCm (8x MI355X, TP8) crashes mid-serving with `HSA_STATUS_ERROR_OUT_OF_RESOURCES`. Each prefill step allocates two ~1.8 GB buffers sized by the step's token count, and the caching allocator piles up slightly-too-small free copies until the headroom outside vLLM's budget is gone. This PR fixes one of the two buffers: the AttnRes block bank in `KimiLinearModel` now comes from the workspace manager as one persistent buffer, sized for `max_num_batched_tokens`, instead of a fresh allocation per forward.

Companion fix for the other buffer, in AITER: ROCm/aiter#6965. Both are needed; they can merge independently, in any order (see [Merge order](#merge-order)).

## Claims

- Fixes the Kimi-K3 serving crash on MI355X. perf-eval's `kimi_k3-mi355x` nightly has failed since Oct 3 (e.g. [build 717](https://buildkite.com/vllm/perf-eval/builds/717)); see [History](#history).
- No KV-cache loss and no accuracy change without DBO. Under DBO the workspace manager keeps one bank per micro-batch slot, one extra bank of KV cache (measured below).
- No throughput change on the perf-eval benchmarks (8k in: 1280.3 ± 1.8 vs 1281.1 ± 2.7 tok/s over 4 samples per arm).

## Details

**Failure.** A ROCr queue callback aborts with `HSA_STATUS_ERROR_OUT_OF_RESOURCES ... Available Free mem : 0 MB`. Every rank first logs a torch OOM-and-retry for a 1,860,173,824-byte request with under 1 GB free. The `too many resources requested for launch` tracebacks that follow land at whatever HIP call runs next, so they differ between runs and are not the cause.

**Root cause.** Two per-step buffers are each num_tokens x 114,688 B, about 1.8 GB for a 16k-token chunk at TP8:
- this model's AttnRes bank, `[num_tokens, num_blocks, hidden]` bf16;
- AITER's FlyDSL MoE stage-2 reduce target, `[num_tokens, topk, model_dim]` bf16.

The caching allocator never serves a request from a smaller free segment and never merges segments. So every step slightly larger than the last allocates new ~1.8 GB segments and keeps the old ones. A snapshot just before the crash had 14.5 GiB in fully free segments. Seven of them were 1766–1772 MiB, just under the failing 1774 MiB request, and their recorded stacks point at exactly these two call sites. Torch recovers its own allocations by emptying the cache and retrying. ROCr cannot, so the next scratch acquisition fails. rocprofv3 shows no kernel needing large scratch; the cache growth is what consumes the headroom.

**Change.** `_new_block_residual` takes a `(max_num_batched_tokens, num_blocks, hidden)` buffer from `current_workspace_manager().get_persistent()` and slices it per step. The profiling run allocates it before the workspace locks, so it is inside the measured peak. The runner sizes its own input buffers to `max_num_batched_tokens`, so no forward can need more rows; an assert guards it.
- **PP:** every rank uses the bank, including non-last ranks that send it. `gpu_worker.execute_model` waits for the previous step's sends before the next forward. TP4 x PP2: gsm8k on 250 questions 0.988 ± 0.007, KV cache 75.15 GiB.
- **No workspace manager** (e.g. unit tests): falls back to the per-step allocation.
- **DBO:** the workspace manager keeps persistent buffers per micro-batch slot by design ([`get_persistent_resource`](https://github.com/vllm-project/vllm/blob/e8570ef757b67805797b005b59fcd6600d939421/vllm/v1/worker/workspace.py#L146): "Each ubatch/lane pair has a separate cache"), so each slot gets its own bank: one extra bank under DBO, 1.75 GiB at 16k tokens (0.44 GiB at the recipe's 4096). Both slots get their bank during warmup, before the workspace locks. Measured with DP2 x TP4 + EP + `--enable-dbo`, `--max-num-seqs 128` (the recipe's value): KV cache on rank 0 is 52.03 GiB stock vs 50.64 GiB with this PR, and startup completes with no workspace-lock error for the bank. End-to-end serving under DBO could not be measured for any version: on stock vLLM the first benchmark batch fails with `AssertionError: Workspace is locked but allocation from 'modular_kernel.py:1207:_allocate_buffers' requires 213.50 MB, current size is 112.00 MB` (the MoE workspace isn't sized for the DP-gathered token count before the lock), and with the default `max_num_seqs` startup runs out of memory during graph capture. Both reproduce without this PR (#65106, #65105).
- **Speculative decoding (DSpark, measured on `c4696ae1ae`, same path without DBO):** TP8 with the speculative config from vLLM's Kimi-K3 DSpark CI eval and `--max-num-seqs 128`: gsm8k 0.9674 ± 0.0049 stock vs 0.9629 ± 0.0052 fixed, mean acceptance length 5.30–5.48 vs 5.34–5.40, KV cache 60.64 vs 60.74 GiB.
- **Multimodal (measured on `c4696ae1ae`):** 16 image+text prompts at temperature 0 are answered correctly by both; outputs vary between runs of the same version (stock vs stock 6/16 identical), so exact-match comparison doesn't separate the versions.

### History

The nightly started crashing on Oct 3: a `git bisect` between builds 628 and 631 found #58344 (Kimi-K3 prefill checkpoints on ROCm), which makes the same two buffers fill the headroom within the first 8k benchmark. Since #57392 made the gluon prefill backend (checkpoints off) the default, the crash moved to the 1k conc 128 benchmark, and [build 249](https://buildkite.com/vllm/perf-eval/builds/249) survived the same code by luck. With both fixes, the fused backend with checkpoints on also completes everything (free cached flat at 6.0–6.3 GiB, gsm8k 0.9591 ± 0.0055); restoring from a checkpoint is untested.

### Why both PRs

| phase | vLLM fix only: free cached | vLLM fix only: min free | both: free cached | both: min free |
|---|---|---|---|---|
| 8k in, conc 128 | 6.3 GiB | 7.2 GiB | 6.3 GiB | 7.4 GiB |
| 1k in, conc 64 | 7.8 GiB | 5.5 GiB | 6.2 GiB | 7.3 GiB |
| 1k in, conc 128 | 11.5 GiB | **0.12 GiB** | 6.3 GiB | 7.3 GiB |

With only this PR, the run finishes but bottoms out at 0.12 GiB free, and free cached segments still grow by 5 GiB. Those leftover 1766–1772 MiB segments come from AITER's `_flydsl_v2_stage2_wrapper`; this model's bank shows as one fully used 1792 MiB segment. Finishing alone is not evidence: the same stock nightly passed in build 249 after logging the OOM on all 8 ranks and crashed in build 724 the same night. The reverse also holds: this model's bank piles up on its own. Stock snapshots show free 1742 MiB segments created at `linear.py:894`, the allocation this PR replaces.

### Merge order

Merge order: on current vLLM (with the extensible KV cache, vllm#56492), this change must land together with or after an AITER fix for the stage-2 target ([ROCm/aiter#7363](https://github.com/ROCm/aiter/issues/7363)) in vLLM's AITER pin. Alone, it fails every request: the persistent bank lowers the warmup transient reserve, and AITER's per-call 1.70 GiB stage-2 allocation then OOMs under the allocator cap (fused_moe.py:3178).

### Revisions

- **`86ed9fb065`..`8bed270c99`** (initial): the bank comes from the workspace manager (`get_persistent`), sized for `max_num_batched_tokens`, on every PP rank.
- **`c4696ae1ae`**: a model-owned bank shared by the DBO micro-batches at their token offsets, to avoid the extra bank under DBO.
- **`ebb611c61a`** (review): back to the workspace bank, identical to `8bed270c99`. One bank per micro-batch slot is the workspace manager's design, and the extra bank under DBO is acceptable. Adds the forward-level regression tests to `test_amd_attn_res.py` (replacing `test_amd_attn_res_bank.py`).
