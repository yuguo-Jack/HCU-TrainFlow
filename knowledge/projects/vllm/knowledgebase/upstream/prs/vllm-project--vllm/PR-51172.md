# [Bugfix][Benchmark] Preserve SSE output across transport chunk boundaries

[Upstream PR](https://github.com/vllm-project/vllm/pull/51172) · state: closed · merged: True

## Original PR description



## Purpose
Fix SSE parsing in the Python `vllm bench serve` clients so results do not depend on how the HTTP response is split into transport chunks.

The OpenAI completions, chat completions, and audio clients iterate streaming responses with `response.content.iter_any()` and call `bytes.strip()` on every returned chunk before passing it to `StreamedResponseHandler`. 

`iter_any()` returns arbitrary available transport data, not complete SSE records, so stripping each fragment mutates the stream before reassembly.

For example, a valid event may arrive as:

>     b"data:"
>     b' {"choices": ...}\n\ndata: [DONE]\n\n'

Stripping both fragments removes the required space after `data:`. The reassembled message becomes `data:{...}`, so `removeprefix("data: ")` no longer matches and JSON parsing fails. The request is marked failed.

A split immediately before whitespace inside a JSON string is worse: the request succeeds, but valid model-output whitespace is silently removed. When the backend omits streaming usage info, the benchmark tokenizes `generated_text` itself, so this can also shift measured output length and derived throughput/TPOT numbers.

The fix passes chunks returned by `iter_any()` unchanged to `StreamedResponseHandler` (three deleted lines). The message-level `.strip()` inside `StreamedResponseHandler` is unchanged: it runs only after a complete SSE boundary (`\n\n`) has been identified. The legacy `benchmarks/backend_request_func.py` loops are untouched; they iterate
`response.content` line-by-line, where per-line stripping is safe.

The per-chunk `.strip()` predates #24373, which switched these loops from line-based iteration (where stripping a complete line is harmless) to `iter_any()`. #50868 recently fixed the same invariant: transport boundaries must not alter output, in the Rust client; this is the Python-side equivalent.


## Test Plan
```
pytest tests/benchmarks/test_endpoint_request_func.py -v
pytest tests/benchmarks/test_audio_dataset.py -v
```

The new test invokes the real completion and chat request functions against a fake session and enumerates every possible two-piece split of an SSE stream containing the `data: ` prefix, leading/internal/trailing generated-text whitespace, a multibyte UTF-8 character, and the `[DONE]` event. For every split position, the request must succeed and return the exact original text.

## Test Result

Before the fix, 10 split positions fail per endpoint:

- splits inside `data: `: request fails with `json.decoder.JSONDecodeError: Expecting value: line 1 column 1`
- 8 splits adjacent to whitespace inside the JSON string: request succeeds but whitespace is silently deleted from the generated text, e.g. `' leading 中 trailing '` → `'leading 中 trailing '`

After the fix:
- tests/benchmarks/test_endpoint_request_func.py ..                  [100%] 2 passed
- tests/benchmarks/test_audio_dataset.py ........                    [100%] 8 passed

I tried this against current main, since the branch is a few weeks behind. The three `chunk_bytes = chunk_bytes.strip()` lines (completions, chat, audio) are still there on main, so the change carries over as is.

I loaded `endpoint_request_func.py` with a fake aiohttp session and fed `async_request_openai_completions` a three-event stream (`"Hello"`, `" world"`, `" foo"`, then `[DONE]`), split into two reads at every byte offset:

Splitting right after `data:` or `data: ` in any of the three events fails the whole request with `JSONDecodeError`, and splitting on either side of the leading space in `" world"` or `" foo"` passes but returns `Helloworld foo` / `Hello worldfoo`, so the lost whitespace goes unnoticed.
- main with the three strips removed: 133 of 133.

So the fix does what the description says, including the silent-whitespace case.

A separate thing I noticed while testing, not caused by this PR: `StreamedResponseHandler` only splits on `\n\n`, so a server that ends events with `\r\n\r\n` (allowed by the SSE spec, and the default separator in sse-starlette) only parses when each event arrives in its own read. With CRLF, the same stream fails at all 141 two-way split points on both main and this branch, and also fails when all events come in a single read. It might be worth a follow-up to normalize CRLF/CR before splitting, but I'd keep it out of this PR.

- esmeetu · COMMENTED · 2026-10-13T12:33:33Z · [source](https://github.com/vllm-project/vllm/pull/51172#pullrequestreview-5503552756)

Thanks for the fix, and sorry for the slow response. The bug is real and the fix is correct.

`iter_any()` yields whatever bytes happen to be available, not whole SSE records, so stripping each fragment before reassembly corrupts the stream. Depending on where the split lands, the request either fails with `JSONDecodeError` (split inside `data: `) or silently loses whitespace in the generated text. The second case is worse: when the backend doesn't return usage, the benchmark tokenizes `generated_text` itself, so output length and throughput/TPOT end up skewed with no error. Stripping after `StreamedResponseHandler` has found the `\n\n` boundary, which stays in place, is the right place for it.

**Verified**
- The three per-chunk `.strip()` calls (completions, chat, audio) are still on current main, and the branch merges cleanly.
- Without the strip, standalone `"\n"`/`"\n\n"` fragments go into the buffer and `split("\n\n")` turns them into empty messages, which are skipped. That's correct SSE handling. The existing streams in `test_endpoint_request_func_timing.py` all end events with `\n\n`, so they're unaffected.
- The newer `async_request_openai_responses` loop already passes `iter_any()` chunks through unstripped, which supports the view that the strip is a leftover from the line-based loop before #24373.
- No duplicate open PR found.

**Requested change**
- Please move the test into `tests/benchmarks/test_endpoint_request_func_timing.py` and reuse its `_FakeContent` / `_FakeResponse` / `_FakeSession` / `_sse` helpers, instead of adding a new file with a parallel set of mocks. That file was added in #55508 after this PR was opened. The split-enumeration test itself is cheap and a good invariant to keep.

**Optional**
- `StreamedResponseHandler`'s early-emit path only fires when the buffer starts with `data: `. If a `\n\n` separator is split across reads, a leading `\n` can be left in the buffer, and the next event then waits for its own `\n\n` instead of being emitted early. That only affects timestamp precision, and in practice the separator usually arrives with its JSON. Checking `self.buffer.lstrip("\n")` there would make it fully robust. Fine as a follow-up.
- The CRLF separator issue raised above is a separate bug. vLLM's own server emits `\n\n`, so it only affects third-party servers. Agreed it should stay out of this PR.

LGTM once the test is consolidated.
