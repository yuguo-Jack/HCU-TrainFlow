# [Perf][Frontend] Build run-batch TypeAdapters once instead of per request

[Upstream PR](https://github.com/vllm-project/vllm/pull/63005) · state: closed · merged: True

## Original PR description



## Overview

`vllm run-batch` builds a new pydantic `TypeAdapter` for each `/v1/embeddings`, `/score` and fallback input line, and for each `JSONResponse` it converts back. Each build regenerates the core schema, which costs about 0.5 ms. This PR builds the four adapters once at module level.

## Claims

- In the current run-batch flow, the per-line frontend cost for an embeddings batch drops from 1,952 µs to 178 µs (~11×, median of 3 runs). For a 1.45M-line batch, single-threaded frontend CPU time drops from about 47 min to about 4.3 min.
- The event-loop ceiling of `run_one_request` rises from about 800 to about 6,600 req/s.
- Behavior does not change. Parsed bodies, validation errors (type, loc and msg), and converted responses are identical before and after.

**Equivalence.** I compared the original and patched modules side by side on 13 input lines and 4 responses. Inputs: embeddings str/list/tokens/chat, extra field, missing input, bad type, score text/queries-documents/invalid, chat, fallback valid/invalid. Responses: embedding, error, unparseable body, handler exception. All 17 results are identical.

**Microbenchmark.** Apple M1 Pro, CPU only. 20k `/v1/embeddings` lines (`dimensions=128`) and a stub handler that returns an `EmbeddingResponse` as a `JSONResponse`. No model or engine is involved. The table shows the median of 3 alternating runs, with the range in brackets.

| step | before | after |
|---|---|---|
| pass 1: `validate_batch` | 689 µs [678–718] | 26 µs [25–27] |
| pass 2: `run_one_request` (parse + handler + response conversion) | 1,254 µs [1,233–1,441] | 151 µs [144–154] |
| **total per line** | **1,952 µs [1,932–2,130]** | **178 µs [169–179]** |
| 1.45M lines (scaled) | 47.2 min | 4.3 min |

**End to end.** I have not run an end-to-end comparison on main. In our deployment on v0.31.0, which has the same per-request `TypeAdapter` code, a 1.45M-line embeddings batch spent 25.5 min just reading input (~950 lines/s). Processing was capped at 1,150–1,600 req/s, which matches the ~0.63 ms per response conversion on the event loop. With this change applied as a patch, the end-to-end batch time went from about 60 min to about 20 min.

```python
"""Per-line cost of the run-batch flow: validate_batch pass + run_one_request.

Usage: python bench_run_batch.py <path to run_batch.py>
"""

import asyncio
import hashlib
import importlib.util
import io
import json
import random
import sys
import time

from fastapi.responses import JSONResponse

from vllm.entrypoints.pooling.embed.protocol import (
    EmbeddingResponse,
    EmbeddingResponseData,
)

import vllm.entrypoints.launchers  # noqa: F401  (parent package for relative imports)

spec = importlib.util.spec_from_file_location(
    "vllm.entrypoints.launchers.rb_bench", sys.argv[1]
)
rb = importlib.util.module_from_spec(spec)
spec.loader.exec_module(rb)

N_IN, N_REQ, PROD = 20000, 5000, 1_451_852
print("module:", sys.argv[1])

base = "Recent interests: camping gear, hiking boots, outdoor clothing, travel, coffee. "
lines = [
    json.dumps(
        {
            "custom_id": "_" + hashlib.md5(str(i).encode()).hexdigest(),
            "method": "POST",
            "url": "/v1/embeddings",
            "body": {
                "model": "vllm",
                "input": (base * (1 + i % 4)) + f"#{i}",
                "dimensions": 128,
            },
        },
        ensure_ascii=False,
    )
    for i in range(N_IN)
]
for ln in lines[:200]:
    rb.BatchRequestInput.model_validate_json(ln)


def report(label, per_us):
    print(f"{label:<34} per={per_us:8.1f}us -> {per_us * PROD / 1e6 / 60:5.1f} min")


t0 = time.perf_counter()
for ln in lines:
    rb.BatchRequestInput.model_validate_json(ln)
report("parse  model_validate_json", (time.perf_counter() - t0) / N_IN * 1e6)

t0 = time.perf_counter()
n = rb.validate_batch(io.StringIO("\n".join(lines) + "\n"))
assert n == N_IN
validate_per = (time.perf_counter() - t0) / N_IN * 1e6
report("pass1  validate_batch", validate_per)

usage = EmbeddingResponse.model_fields["usage"].annotation(prompt_tokens=30, total_tokens=30)
rnd = random.Random(0)
payloads = [
    EmbeddingResponse(
        id="embd-x",
        created=0,
        model="vllm",
        data=[
            EmbeddingResponseData(
                index=0, embedding=[rnd.uniform(-0.2, 0.2) for _ in range(128)]
            )
        ],
        usage=usage,
    ).model_dump()
    for _ in range(N_REQ)
]


async def run_all():
    it = iter(payloads)

    async def handler(_body):
        return JSONResponse(content=next(it))

    registry = {
        "embeddings": {
            "url": "/v1/embeddings",
            "handler_getter": lambda: handler,
            "wrapper_fn": None,
        }
    }
    t0 = time.perf_counter()
    outs = [await rb.run_one_request(lines[i], registry) for i in range(N_REQ)]
    return outs, time.perf_counter() - t0


outs, el = asyncio.run(run_all())
bad = sum(
    1
    for o in outs
    if o.error is not None or not isinstance(o.response.body, EmbeddingResponse)
)
run_per = el / N_REQ * 1e6
report("pass2  run_one_request (loop)", run_per)
print(f"       bad={bad}, event-loop cap ~{1e6 / run_per:,.0f} req/s")
report("total  pass1 + pass2", validate_per + run_per)
```

## Details

**Root cause.**
- Input side: `TypeAdapter(...)` inside `BatchRequestInput.check_type_for_url`, added in #12420.
- Response side: `TypeAdapter(AllResponse | ErrorResponse)` in `run_request`, added in #28631. It also builds a new `Union` object on every call, so caching by type identity would not help. A module constant is the simplest fix.
- Since #52505, each line is parsed twice: once in `validate_batch` before the engine starts, and again in `run_one_request` on the event loop. That doubles the input-side cost.

**Import cost.** Building the four adapters adds about 2–3 ms at import. `vllm.entrypoints.cli.run_batch.subparser_init` imports this module for every `vllm` CLI invocation, including `vllm serve`, so the cost applies there too. It is negligible against the module's ~9 s import.

**Safety.** `TypeAdapter.validate_python` does not keep per-call state, so sharing one adapter across concurrent requests is safe. vLLM never calls `model_rebuild` on these models at runtime, so a cached adapter cannot hold a stale schema.

**Scope.** I checked the other per-call `TypeAdapter(...)` sites under `vllm/entrypoints`. They run only on rare paths: a dict `structural_tag` `response_format`, and the Responses API streaming error path. `sagemaker` already caches its adapters. This PR leaves them alone.

**Duplicate check.** As of 2026-10-22, searching vllm-project/vllm issues and PRs for `TypeAdapter run_batch` / `run_batch TypeAdapter` returns nothing. None of the open PRs that touch `run_batch` (#51859, #57825, #59716) change this code.
