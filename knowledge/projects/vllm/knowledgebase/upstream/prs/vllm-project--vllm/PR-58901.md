# [Bugfix][Core] Count the external claim's state block in MambaManager admission

[Upstream PR](https://github.com/vllm-project/vllm/pull/58901) · state: open · merged: False

## Original PR description

## Purpose

Fix the wrong `num_new_blocks` calculation in `MambaManager.get_num_blocks_to_allocate` (align mode) when a KV connector cache hit is loaded synchronously on a hybrid model with Mamba/GDN layers (`--mamba-cache-mode align`). The estimate is one block short per Mamba group, so the request is admitted with `free == estimate` and the pool raises inside the allocation, killing the EngineCore:

```
File "vllm/v1/core/kv_cache_coordinator.py", line 299, in allocate_new_blocks
File "vllm/v1/core/single_type_kv_cache_manager.py", line 1882, in allocate_new_blocks
    new_blocks = self.block_pool.get_new_blocks(num_new_blocks)
File "vllm/v1/core/block_pool.py", line 681, in get_new_blocks
ValueError: Cannot get 1 free blocks from the pool
```

Cause: the align-mode estimate caps `num_new_blocks` at what `allocate_new_blocks` pulls, but when external computed tokens and new tokens are allocated in the same `allocate_slots` call, the inherited `allocate_external_computed_blocks` pulls the boundary state block first, and that block is not counted. Async loads are unaffected (the external span is allocated with no new tokens) and #57050 only fixed the over-estimate in the same function, so this is still present on `main`.

Fix: count the blocks `allocate_external_computed_blocks` will pull (`cdiv(total_computed, block_size) - max(skipped, held)`) and size the `allocate_new_blocks` share from the blocks held after it. The estimate then equals the allocation for sync loads and stays exact for async loads and cold prefills.

### Supersedes #46892

#46892 (thanks @zqs164) found the same bug and was approved by @MengqingCao and @ivanium in June, but pre-commit failed, it has needed a rebase since #57050 rewrote the cap in July, and there has been no activity on it since — the bug is still live on `main` three months later and kills the engine whenever a KV connector loads a cache hit synchronously on a Mamba/GDN hybrid in align mode, which is why we are opening a new PR rather than waiting on it. It also takes a different approach rather than rebasing #46892:

- #46892 adds a constant `+1` inside the cap. That is exact only when the claim ends on a block boundary; for a mid-block claim (e.g. 133 external + 11 new tokens with block size 16) it reserves a block that is never pulled, one per Mamba group, which can refuse a request that fits near the pool ceiling. This change counts the actual pull, so admission equals allocation in both cases (the invariant `test_mamba_checkpoint_admission_matches_allocation` asserts).
- The external block is counted outside `physical_block_cap`, which only describes `allocate_new_blocks`, so the fix does not depend on the cap's formula (the coupling that made #46892 conflict with #57050).
- "External tokens present" is tested with `total_computed_tokens > num_local_computed_tokens` instead of `len(new_computed_blocks) * block_size`, which also holds under partial local hits.

The `request_id not in self.num_cached_block` gate suggested in #46892's review is kept.

## Test Plan

```
pytest tests/v1/core/test_single_type_kv_cache_manager.py -k mamba
pytest tests/v1/core/test_prefix_caching.py -k "external_claim or mamba_align"
```

- `test_mamba_external_claim_admission_matches_allocation` replays the coordinator's order (`add_local_computed_blocks` -> `allocate_external_computed_blocks` -> `allocate_new_blocks`) for a cold prefill and aligned, non-aligned and async claims, each followed by the next chunk, asserting `estimate == allocated`.
- `test_mamba_align_external_claim_admission_matches_allocation` does the same through `KVCacheManager.allocate_slots` on a `full + mamba_align` layout.

Without the fix the sync-claim cases fail (`assert 1 == 2`).

End-to-end: Qwen3.8-27B-FP8 (3 GDN groups) TP1 on H100 with a KV connector doing synchronous loads, `--num-gpu-blocks-override 28 --max-model-len 32768 --max-num-seqs 8`; two 14,012-token prompts whose first 12,544 tokens are served by the connector: prefill cold, `/reset_prefix_cache`, re-send both.

## Test Result

- Without the fix: both warm requests fail, EngineCore exits with the trace above.
- With the fix: both served, 25,088 external tokens loaded per round, repeated twice, no restarts.
- `tests/v1/core/test_single_type_kv_cache_manager.py` + `tests/v1/core/test_prefix_caching.py`: 201 passed on `main` (`a9eafde59c`).

Scheduler admission accounting only; no model outputs affected, no evals run.
