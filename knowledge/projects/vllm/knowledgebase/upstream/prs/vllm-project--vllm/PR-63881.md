# [Doc] CPU release wheels are manylinux_2_39 since v0.30.0

[Upstream PR](https://github.com/vllm-project/vllm/pull/63881) · state: open · merged: False

## Original PR description



## Overview

Since v0.30.0 the CPU release wheels are `manylinux_2_39` builds, but the pre-built wheel commands in the CPU install docs still name the `manylinux_2_34` file. Every current release (v0.30.0 to v0.32.0) returns 404 for that name, on both x86_64 and aarch64. This PR changes the file names and says what glibc the wheels need.

It also fixes the Qwen3.5-35B-A3B recipe guide, whose CPU block names a `manylinux_2_35` wheel that no release has shipped.

## Claims

- **`cpu.x86.inc.md` / `cpu.arm.inc.md`:**
  - The uv and pip commands use `manylinux_2_39`.
  - The intro says these wheels need glibc 2.39+ (e.g. Ubuntu 24.04), and that for 0.29.0 and earlier the name is `manylinux_2_34`.
- **`recipes/models/Qwen/Qwen3.5-35B-A3B.yaml`:** the guide's CPU code block is replaced with a pointer to the command builder (Xeon 6), whose Install block renders the CPU release-wheel command (vllm-project/recipes#1189). The docs link stays. The broken copy was a duplicate of that command.

## Validation

- Reproducer: `curl -sIL -o /dev/null -w '%{http_code}' https://github.com/vllm-project/vllm/releases/download/v0.32.0/vllm-0.32.0+cpu-cp38-abi3-manylinux_2_34_x86_64.whl` prints 404 (also for `aarch64`). With `manylinux_2_39` it prints 200 for both.
- Release assets: v0.29.0 ships `+cpu-cp38-abi3-manylinux_2_34_{x86_64,aarch64}`. v0.30.0, v0.31.0 and v0.32.0 ship `manylinux_2_39_{x86_64,aarch64}`.
- `uv pip compile` of the v0.32.0 x86_64 wheel URL for an `x86_64-manylinux_2_39` target resolves (torch 2.13.0+cpu and the triton-cpu wheel).
- `node scripts/validate-source.mjs --source vllm --dir recipes` (vllm-project/recipes) passes.

## Details

- **Not in this PR: index installs on x86_64.** The `--extra-index-url https://wheels.vllm.ai/{nightly,<version>,<commit>}/cpu` commands in the same docs fail with uv on x86_64 from v0.31.0: `Package triton was included as a URL dependency`. Since #58140, `requirements/cpu.txt` pins triton-cpu by URL, and uv doesn't accept a URL dependency from a package it found on an index. It does accept one from a package installed by URL, which is why the release-wheel commands above work. The fix belongs in packaging, not the docs, so I'll file it as an issue.

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Derive the wheel tag for post-v0.32 releases**

When `releases/latest` moves past v0.32.0, this URL will again select a nonexistent asset. The current CPU release jobs in `.buildkite/release-pipeline.yaml` build both architectures from `docker/Dockerfile.cpu`, which now starts from Ubuntu 22.04, and `.buildkite/scripts/upload-nightly-wheels.sh` runs the auditwheel-based tag detector (which documents Ubuntu 22.04 builds as `manylinux_2_35`) rather than forcing `manylinux_2_39`. Consequently the next release asset will not retain this suffix while `VLLM_VERSION` automatically advances; the Arm snippet has the same problem. Resolve the actual asset/tag dynamically or restrict this suffix to v0.30–v0.32.
