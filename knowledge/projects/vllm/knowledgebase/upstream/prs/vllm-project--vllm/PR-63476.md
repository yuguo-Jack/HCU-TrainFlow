# [Bugfix][MRV2] Report the first failed DBO microbatch

[Upstream PR](https://github.com/vllm-project/vllm/pull/63476) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

When two DBO microbatches fail, the MRV2 `UBatchRunner` reports the one with the lowest index instead of the one that failed first, which hides the root cause. Related: #61487 (the hidden microbatch-1 error), follow-up to #63372 (also a DBO microbatch fix in `UBatchRunner`).

## Claims

- `finish()` reports the first recorded microbatch failure, not the lowest microbatch index (`min(errors)` → `next(iter(errors))`).
- The behavior is unchanged when one microbatch fails or none fail.

## Validation

`test_ubatch_runner_names_the_microbatch_that_failed` is now parametrized. The new `[1]` case makes microbatch 1 fail first, then microbatch 0 registers a recv hook on the exited peer, which raises the follow-on error.

```bash
VLLM_USE_V2_MODEL_RUNNER=1 pytest -q \
  "tests/v1/worker/test_gpu_ubatch_slicing.py::test_ubatch_runner_names_the_microbatch_that_failed"
```

1x H200, on base `7822663cb4`:

| | Result |
| --- | --- |
| Before (base + new test) | 1 failed, 1 passed: `assert 'Microbatch 1' in 'Microbatch 0 of 2 failed'` |
| After | 2 passed |

`pre-commit run` passes on the changed files. CI runs the test through the existing `v1/worker` step.

## Details

Root cause: as reproduced in #61487, microbatch 1 fails and exits, and its `UBatchContext.__exit__` clears `_CURRENT_CONTEXTS[1]`. Microbatch 0 then calls `dbo_register_recv_hook()` on that cleared slot and raises an `AttributeError`. `min(errors)` picks microbatch 0, so the original error is lost.

Each worker thread writes `errors` at most once, under its own key. `finish()` reads `errors` only after joining all threads, and dicts keep insertion order, so the first key is the first recorded failure. No locking or new state is needed.

Limitations: "first recorded" is the first failure raised in Python, which can be later than the GPU fault because CUDA errors are asynchronous. This change does not fix the hang when a peer exits mid-handoff, or the HiSparse + DBO issues in #61487.

Not a duplicate: no open PR changes this selection. Searched for `61487 in:body`, "ubatch failed microbatch error", "DBO microbatch exception", and "UBatchRunner error".
