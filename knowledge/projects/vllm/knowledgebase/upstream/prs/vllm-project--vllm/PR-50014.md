# [Bugfix][KV Offload] Protect unread promotions from eviction by other speculative promotions

[Upstream PR](https://github.com/vllm-project/vllm/pull/50014) · state: open · merged: False

## Original PR description

## Purpose

Fixes #49902. `TieringOffloadingManager` promotes secondary-tier blocks to
the primary CPU tier on every `lookup()`, including probes for waiting
requests the scheduler ends up skipping that step (a request that defers is
`continue`d past, not `break`ed on, so one `schedule()` pass can walk the
whole waiting queue and issue a promotion per secondary-tier hit). Under
many concurrent, disjoint-working-set requests, one promotion's
landed-but-not-yet-GPU-read block could be evicted by another promotion
before ever being consumed — `complete_write()` marks it evictable the
moment the async load finishes, and `evict()`'s `protected` set only ever
covered the *current* call's own keys, so a landed-but-unconsumed block from
a different promotion was a normal eviction candidate. The evicted data gets
re-promoted (and re-evicted) on a later step, burning secondary-tier I/O on
data that never gets used.

## Fix

Track landed-but-unread promotions (`block -> owning req_id`) in
`TieringOffloadingManager` and pass them as `extra_protected` (new optional
param on `CPUOffloadingManager.prepare_store`) so a promotion can never evict
another promotion's not-yet-consumed data. Protection is contention-driven,
not a static quota — it's a single dict tracked against the actual promotion
lifecycle, not a fraction of primary capacity:

- Added when a promotion job completes (`_process_finished_jobs`), unless the
  owning request is already known-finished.
- Removed the moment the block is actually read (`prepare_load` — the real
  consumption event, regardless of which request originally promoted it).
- Removed when the owning request finishes without ever reading it
  (`on_request_finished`), so an abandoned promotion doesn't pin capacity
  forever.
- Cleared on `reset_cache()`.

Real GPU-driven stores are intentionally **not** gated by this — they
represent confirmed demand and can still evict an unread promotion freely;
only *other speculative promotions* are blocked from evicting it.

## Not a duplicate

#49952 is open against the same issue and touches the same three files, but
fixes a materially different mechanism. Its own PR description identifies
both: promotions can starve *real GPU-driven stores* of primary-tier
capacity (no headroom was reserved for stores), **and**, separately, a
landed promotion can be evicted by another promotion before its owner reads
it. #49952's fix (`_store_headroom_blocks` + `_num_inflight_promotion_blocks`)
targets only the first: its promotion budget is in-flight-only and
decrements the moment a promotion *completes* (lands), so a landed-but-unread
block is invisible to that accounting and remains an eviction candidate for
the next promotion — the exact gap this PR closes. This PR does not touch
store-headroom reservation at all; real stores are explicitly left free to
evict unread promotions. The two are complementary, not competing:
#49952 stops promotions from starving stores, this PR stops promotions from
starving each other.

Thank you @AlejandroParedesLT  . I left a round of comments. 

One high level question: 
- Do we care about releasing keys in lock-step when CPU -> GPU transfer is triggered?

AFAIU,  The CPU -> GPU transfer is the ultimate resolution/verdict from the prefix-matching logic. When that happens, we can sure that all the CPU -> GPU load job submissions will happen in that scheduler step. The "key" level granularity might be unnecessary. 
Further, at the moment, all the FS lookups result in a disk -> CPU load (I am making an issue for this). But CPU -> GPU loads are selective (in the case of Sliding window attention). I think we will end up locking the unloaded CPU blocks for the entire request duration unnecessarily. 

IMHO, it is better to unlock all the CPU blocks that are associated with a request, when we detect a CPU -> GPU load for a request. 

wdyt ?
