# [Metrics][KV Connector] Count KV load failures in the scheduler

[Upstream PR](https://github.com/vllm-project/vllm/pull/64023) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Add a Prometheus counter, `vllm:kv_load_failed_requests`, that counts requests affected by failed external KV cache loads. The v1 Scheduler counts them where it already handles these failures (`_handle_invalid_blocks` and `_handle_failed_recving`), so connectors and platform plugins no longer need to work this out themselves.

## Claims

- New per-engine counter (labels `model_name`, `engine`), registered when a `kv_transfer_config` is set:
  - `vllm:kv_load_failed_requests_total`: requests affected by a failed external KV cache load, including requests that share an invalid prefix block.
- Counted under both `kv_load_failure_policy` values (`recompute`: the requests are rescheduled; `fail`: they finish with an error), and for both failure reports: block-level `invalid_block_ids` (sync and async loads) and request-level `failed_recving` (the path hybrid and multi-group models must use), without double-counting when a connector reports both for the same load.
- The numbers match the scheduler's existing KV load failure log lines ("Failing N request(s) ..." / "Recovered from KV load failure: N request(s) rescheduled ..."). The counter reuses the request total behind those lines and adds no new accounting.
- Docs: the metrics table in `docs/usage/metrics.md` is generated from `loggers.py`, so it picks up the counter. The KV Load Failure Policy section in `docs/features/nixl_connector_usage.md` now points to it.

## Details

**Why in the scheduler.** The scheduler already decides which requests a failed load affects: it truncates `num_computed_tokens`, applies the failure policy, and logs totals. A connector or platform plugin that wants this metric has to rebuild that decision from outside, for example by tracking block claims per request and retiring them across async-scheduling steps, and it still gets shared-prefix and policy cases wrong. Counting at the decision point gives one definition for every connector.

**Accounting.**
- `_handle_invalid_blocks`: adds `sync_failed_req_ids` plus `async_failed_req_ids` not already failed by `_handle_failed_recving` in the same step (so connectors like `NixlConnector` that report both `failed_recving` and `invalid_block_ids` on non-HMA models count the request once under `policy=fail`).
- `_handle_failed_recving`: adds affected `WAITING_FOR_REMOTE_KVS` requests not already in `failed_recving_kv_req_ids` (so under `KVOutputAggregator` with TP > 1, where `invalid_block_ids` can arrive a step before `failed_recving`, the request is counted once under `policy=recompute`).
- A request is counted each time a distinct failure report affects it. A progressive async load that reports invalid blocks in several steps can therefore count the same request more than once, just as it produces more than one log line today.
- The count is kept on the scheduler and moved into `SchedulerStats` (then reset) in `make_stats`, the same way `connector_prefix_cache_stats` works. `make_stats` runs at the end of every `update_from_output` when stats are enabled, so nothing is lost between steps. With `log_stats=False` the integer is never read.

**Registration.** The counter is created only when `kv_transfer_config` is set. Load failures need a connector, and this follows how other optional metrics are handled: `vllm:num_requests_kv_fetch_by_stage` (KV consumers only), `vllm:watermark_requests`, and `vllm:corrupted_requests`. For the same reason it is not added to `EXPECTED_METRICS_V1` in `tests/entrypoints/serve/instrumentator/test_metrics.py`.

**No `connector` or `policy` label.** `kv_load_failure_policy` is a single engine-wide setting. Under `MultiConnector`, the scheduler only receives the merged `invalid_block_ids` and `failed_recving`, so it cannot say which child connector failed. Per-child attribution belongs in connector stats (`KVConnectorStats` / `build_prom_metrics`) and can be added later.

**Not covered here.**
- Rust frontend: `SchedulerStats` decoding in `rust/src/engine-core-client/src/protocol/stats.rs` ignores unknown fields, so the new field does not break it, but the Rust `/metrics` endpoint does not export this counter yet. It also does not export `vllm:num_requests_kv_fetch_by_stage`. This can be added in a follow-up.
- `LoggingStatLogger`: the scheduler already logs each failure at warning level (`recompute`) or error level (`fail`), so the periodic stats line is unchanged.

**Why this is not a duplicate.** Open PRs and issues searched on 2026-10-27:
- PR searches with `gh pr list --repo vllm-project/vllm --state open --search ...`: "kv load failure metric", "invalid_block_ids metric", "kv_load_failure", "failed_recving metric", "kv load failed requests", "kv load failure", "kv_load_failed", "invalid blocks metric", "kv connector metrics prometheus".
- Issue searches with `gh issue list`: "kv load failure metric", "kv load failure", "invalid_block_ids", "failed_recving", "kv_load_failure_policy metric", "kv transfer failure prometheus".

None of the results adds a failed-request counter. The closest are:
