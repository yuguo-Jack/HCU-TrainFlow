# [Bugfix][Frontend] Normalize beam search scores by generated length

[Upstream PR](https://github.com/vllm-project/vllm/pull/62928) · state: closed · merged: True

## Original PR description



## Overview

Beam search divides each beam's cumulative log-prob (a sum over the *generated* tokens) by `(prompt + generated length) ** length_penalty`. It should divide by the generated length only, as Transformers does. With any non-trivial prompt, the prompt length dominates the denominator, so `length_penalty` stops having an effect and beams that hit EOS early win, often with an empty completion. This affects `LLM.beam_search` and `use_beam_search` on `/v1/completions`, `/v1/chat/completions` and speech-to-text, which all share `create_sort_beams_key_function`.

Fixes #2606, which was auto-closed as stale. The earlier fix in #7007 targeted the old V0 `sequence.py` and was never merged, and the bug carried over into the current frontend implementation.

## Claims

- Beams are ranked by `cum_logprob / num_generated_tokens ** length_penalty`, counting a terminating EOS token, as in Transformers' [`_update_finished_beams`](https://github.com/huggingface/transformers/blob/09a71e5b32a747dbc7805599457e67c956ef212f/src/transformers/generation/utils.py#L3531): `topk_log_probs / ((cur_len + 1 - decoder_prompt_len) ** length_penalty)`. Transformers fixed the same bug in huggingface/transformers#27351.
- Beam search no longer prefers empty completions. On `tests/prompts/example.txt` without trailing newlines, the top beam on `main` is EOS-only for 8 of 8 prompts (HF: 1 of 8). With this PR it is 1 of 8.
- HF parity improves. On the exact prompts `tests/samplers/test_beam_search.py` uses, the top beam matches HF on 8/8 prompts instead of 6/8.
- `length_penalty` changes the result again for long prompts. On `main`, the same beam wins for every value from 0 to 2.
- `BeamSearchParams.length_penalty` now has a docstring describing these semantics.

## Details

**Root cause.** `get_beam_search_score` divided by `len(tokens)`. `tokens` starts as the prompt (`BeamSearchInstance` and the online path's `tokens=prompt_token_ids`), but `cum_logprob` only sums generated tokens. The helper was adapted from an old Transformers `BeamHypotheses.add` that had the same bug. huggingface/transformers#27351 (v4.36) fixed it there, noting it "would cause an unexpected bias towards generating shorter sequences".

**Why `len(x.logprobs)`.** Every path that extends or completes a beam appends exactly one logprobs entry and adds that token's log-prob to `cum_logprob`. That covers offline steps, online running beams, EOS beams and aborted beams. `tokens` can't be used, because the online path drops the EOS from `tokens` unless `include_stop_str_in_output` is set. The `max(..., 1)` guard still covers a beam aborted before generating anything.

**Behavior change.** Final rankings change only when the compared beams have different generated lengths, which is the intent. Pruning of running beams is unchanged, since every running beam has the same length at each step.

**Not changed.** Two differences from Transformers remain:
- vLLM finalizes every EOS candidate among each beam's top `2 * beam_width` logprobs; Transformers only finalizes those in the global top `num_beams`.
- vLLM has no early-stopping heuristic.

**Related.**
- #59506 adds overflow handling to the same function. It is orthogonal, but it needs a rebase onto the new `(num_generated_tokens, cumulative_logprob, length_penalty)` signature.
- The Rust-frontend beam search in #47705 ports the old formula, including unit tests that encode it. The same `logprobs.len()` change applies there.
- RFC #61880 plans to reuse `get_beam_search_score` for HF-parity scoring.

**Not a duplicate.** I searched open and closed issues and PRs for `beam search length penalty`, `length_penalty`, `get_beam_search_score`, `beam search normalization` and `beam search shorter`. The only related hits are #2606, the stale V0 PR #7007, and #59506 (overflow only). I also checked every open PR touching `vllm/entrypoints/generate/beam_search/` (#59506, #60327, #60550, #52621, #36285, #60787, #49541, #47705): none changes the normalization.
