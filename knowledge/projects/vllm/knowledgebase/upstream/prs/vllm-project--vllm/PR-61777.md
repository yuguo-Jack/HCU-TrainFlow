# [Bugfix][Bench] Aggregate DP running requests for profiling

[Upstream PR](https://github.com/vllm-project/vllm/pull/61777) · state: closed · merged: True

## Original PR description

## Overview

Fix Rust bench's deferred profiling on data-parallel servers by summing `vllm:num_requests_running` across the engine series exposed by `/metrics`.

## Claims

- DP8 with 16 running requests per engine now reports 128 to `--profile-batch-threshold`, instead of 16. A threshold of 120 can therefore be reached.
- Match the exact gauge name and read its sample value before an optional timestamp. Preserve zero versus missing metrics and clarify the aggregate threshold in CLI help.

## Validation

Linux x86_64, Ubuntu 24.04, Rust 1.95.0. From `rust/`:

```bash
cargo test --offline --locked -p vllm-bench
cargo clippy --offline --locked -p vllm-bench --all-targets -- -D warnings
```

Raw test summaries (unit tests, then CLI parity tests):

```text
test result: ok. 190 passed; 0 failed; 12 ignored; 0 measured; 0 filtered out; finished in 2.60s
test result: ok. 3 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.01s
```

Four synchronous parser tests cover DP sum, exact-name matching, zero versus missing metrics, and timestamps. The original parser fails the DP sum, exact-name, and timestamp cases; all four pass after the fix. Clippy and pre-commit pass.

## Details

The previous parser returned the first matching series. vLLM exports this gauge per engine, so the profiling threshold could remain unreachable despite sufficient total concurrency. Aggregate valid samples while excluding metric names that merely share the prefix. Client-side metric parsing and help text only; no new dependencies.

The total matches the aggregate scope of `--max-concurrency`, rather than requiring a minimum batch size on each engine. With uneven DP load, profiling may start while some engines still have small batches. Only engines exposed by the target `/metrics` endpoint are counted.

Duplicate check: no matching open PR found for `fetch_num_requests_running`, `profile_batch_threshold`, or Rust DP profiling.

- esmeetu · comment · 2026-10-29T09:00:24Z · [source](https://github.com/vllm-project/vllm/pull/61777#issuecomment-6492406625)

lgtm, A few non-blocking suggestions:

1. Split the text parsing into a pure `parse_num_requests_running(&str) -> Option<usize>` and test it directly. Each test currently spins up a TCP server, which makes the test code bigger than the fix. The case table could also be trimmed to the cases that matter: DP sum, exact-name match, `0` vs missing, and the timestamp.
2. Please add a sentence to the PR description on why the threshold uses the total across engines rather than a per-engine value such as the min. With uneven DP load, profiling can start while some ranks still have small batches. I think the total is the right choice because it matches `--max-concurrency`, but it is a semantic change.
3. One possible note for the help text: with multi-node DP, `/metrics` only covers the engines local to the `--base-url` node.
