# [Bugfix][Bench] Aggregate DP running requests for profiling

[Upstream PR](https://github.com/vllm-project/vllm/pull/61777) · state: open · merged: False

## Original PR description

## Overview

Fix Rust bench's deferred profiling on data-parallel servers by summing `vllm:num_requests_running` across the engine series exposed by `/metrics`.

## Claims

- DP8 with 16 running requests per engine now reports 128 to `--profile-batch-threshold`, instead of 16. A threshold of 120 can therefore be reached.
- Match the exact gauge name and read its sample value before an optional timestamp. Preserve zero versus missing metrics and clarify the aggregate threshold in CLI help.

## Validation

Linux x86_64, Ubuntu 24.04, Rust 1.95.0. From `rust/`:

```bash
cargo test --offline --locked -p vllm-bench
cargo clippy --offline --locked -p vllm-bench --all-targets -- -D warnings
```

Raw test summaries (unit tests, then CLI parity tests):

```text
test result: ok. 189 passed; 0 failed; 12 ignored; 0 measured; 0 filtered out; finished in 2.33s
test result: ok. 3 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.01s
```

The three new tests exercise the real HTTP fetch path against a local metrics endpoint. All three fail with the original implementation, including `Some(16)` versus `Some(128)` for DP8, and pass after the fix. Clippy and pre-commit pass.

## Details

The previous parser returned the first matching series. vLLM exports this gauge per engine, so the profiling threshold could remain unreachable despite sufficient total concurrency. Aggregate valid samples while excluding metric names that merely share the prefix. Client-side metric parsing and help text only; no new dependencies.

Duplicate check: no matching open PR found for `fetch_num_requests_running`, `profile_batch_threshold`, or Rust DP profiling.
