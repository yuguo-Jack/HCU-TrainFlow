# [Bugfix][Model] Fix GLM non-mHC sequence-parallel decoder layout

[Upstream PR](https://github.com/vllm-project/vllm/pull/58834) · state: open · merged: False

## Original PR description

## Purpose

Fix the sequence-parallel layout in the non-mHC branch of `Glm5NextDecoderLayer.forward()`.

`Glm5NextModel` shards tokens before entering decoder layers. The non-mHC branch passes that shard directly to attention without gathering the full sequence or reduce-scattering its output. MoE then shards the input a second time. This produces incorrect dense-layer outputs and can cause a token-count mismatch in expert dispatch.

Follow the existing mHC layout: gather and trim padding before attention, reduce-scatter afterward, and tell MoE that its input is already sequence-parallel. MTP receives full-sequence inputs, so it skips these outer collectives and retains MoE's internal chunk/gather pair. The mHC branch is unchanged.

Searches for GLM sequence-parallel fixes found no open PR addressing this non-mHC decoder layout.

## Test Plan

Run a four-process numerical regression with TP=2, DP=2 and expert parallelism, alongside the existing sequence-parallel tests. Compare sequence-sharded execution against a replicated-token reference using randomly initialized GLM decoder layers, the real dense/MoE implementations, weight post-processing and NCCL collectives. Attention uses a small causal SDPA fixture with the real TP output projection.

Cover dense and sparse layers, 1/5/8 tokens, padding, and MTP's full-sequence inputs. BF16 comparisons use `rtol=atol=0.02`.

```bash
python -m pytest tests/models/glm5next/test_sequence_parallel.py -v --tb=short
```
