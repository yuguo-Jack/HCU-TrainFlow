# [Bugfix][Core] Copy every overlaid KV view in copy_kv_cache_blocks_inplace

[Upstream PR](https://github.com/vllm-project/vllm/pull/55112) · state: closed · merged: True

## Original PR description

## Purpose

`copy_kv_cache_blocks_inplace` (the CoW copy for partial prefix-cache hits) skips a KV cache view when another view with the same `data_ptr` has already been copied. That is right for cross-layer KV sharing (identical aliased views) but wrong for hybrid models: the KV cache config puts one layer of each KV cache group on the same tensor, so a Mamba state view and an attention view share a base address while spanning different bytes per block, and whichever view comes first in layer order decides how many bytes of a block get copied.

For Kimi-K3 (3 KDA groups + 1 MLA group, block_size 5760, kernel page 64) the KDA view `(num_blocks, 1, 1, 814080)` int8 comes first, so the MLA view `(num_blocks*90, 1, 64, 576)` bf16 of the same tensor is skipped and an MLA block copy moves only 814080 of its 6635520 bytes, i.e. the first 706 of 5760 token slots. The whole-storage fast path would hide this, but it is not taken when several tensors live in one allocation.

Observed effect (het-TP PD, TP8 prefill -> TP1 decode, `--prefix-match-unit 128`, GSM8K 5-shot): every prompt's prefill stops at its last 128-token boundary `B` (Mamba align mode caches the state there); on the small-KV prefill engine the request is then preempted and resumes with a local partial prefix-cache hit on its own boundary entry, which redirects every group's block through this CoW copy (any new request with a partial hit takes the same path). The block the request continues in and ships to decode reads `slots [0,707) valid | [707,B) zero | [B,N-1) valid`. Accuracy dropped to 0.72 with a 128-token sawtooth (about 0.2 right after a boundary, 0.95 late in a chunk), only for `B >= 768`, deterministic per prompt and independent of the KDA kernel. Decode-local prefill on TP1 was unaffected because its per-block Mamba state is 8x larger (5653 slots), which is why the problem only showed up with a high-TP prefill engine.

## Fix

Key the dedup on `(device, data_ptr, shape, stride, element_size)`, so only identical aliased views are skipped and every overlaid geometry is copied. Overlaid views copy the same source block, so the extra narrow copy is redundant but harmless.

### Why the deduplication key includes view geometry

The key answers: "Has this view's block copy already been performed?" The same starting address does not imply the same copy coverage.

Consider the layout used by the regression test: four scheduler blocks per tensor region, 64 bytes per block, and two 256-byte tensor regions in one 512-byte storage. Within each region, a narrow Mamba view and a wider attention view start at the same address:

```text
One scheduler block:
byte offset     0              24                         64
                |--------------|--------------------------|
Mamba view      |  state data  |
Attention view  |              full KV data               |
```

The two views have these properties:

| Property | Mamba view | Attention view |
|---|---|---|
| Device | CPU | CPU |
| Starting address | A | A |
| Shape | (4, 1, 1, 24) | (8, 1, 8, 2) |
| Stride, in elements | (64, 1, 1, 1) | (16, 16, 2, 1) |
| Element size | 1 byte (int8) | 2 bytes (int16) |
| Bytes covered per scheduler block | 24 | 64 |

The attention view splits each scheduler block into two kernel pages: each page contains `1 * 8 * 2 = 16` int16 elements, so the two pages cover `2 * 16 * 2 = 64` bytes.

When copying block 0 to block 2, with the Mamba view visited first:

1. **Before the fix:** both views have the key `(device, A)`. The Mamba view copies the first 24 bytes and records the key. The attention view is then skipped, leaving the remaining 40 destination bytes unchanged.
2. **After the fix:** the views have different geometry keys. The Mamba view copies the first 24 bytes, and the attention view subsequently copies all 64 bytes. The overlapping 24 bytes are copied from the same source block to the same destination block, so the extra copy is redundant but harmless.

This example deliberately uses two tensor regions in one storage. The whole-storage fast path requires `storage.nbytes() == num_blocks * scheduler_block_stride`; here that is `512 == 4 * 64`, which is false. The fallback copies the current view's logical elements, so the narrow view cannot cover the full attention block. With a single 256-byte region, the whole-storage fast path would copy the full block and hide the bug.

The new key describes both the starting location and the layout:

```python
key = (
    cache.device,
    cache.data_ptr(),
    tuple(cache.shape),
    tuple(cache.stride()),
    cache.element_size(),
)
```

- `device` and `data_ptr()` identify where the view starts.
- `shape` describes its logical extent.
- `stride()` describes where its elements lie. For example, two views starting at `a` with shape `(3,)` can select `[a, b, c]` with stride 1 or `[a, c, e]` with stride 2.
- `element_size()` converts element-based strides to byte distances: stride 2 means 2 bytes for int8 but 4 bytes for int16.

Matching these fields lets identical aliased views retain the existing deduplication optimization without skipping overlaid views that cover different bytes.
