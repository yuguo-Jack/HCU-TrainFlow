# [Bugfix][MoE] Preserve invalid expert IDs in NIXL round-robin mapping

[Upstream PR](https://github.com/vllm-project/vllm/pull/64086) · state: open · merged: False

## Original PR description


## Overview

**Production change: one line. The remaining 80 added lines are regression tests.**

Preserve invalid expert IDs in NIXL round-robin remapping. When the adapter receives `-1` together with a global-to-physical table, the current lookup selects the table's last real expert.

This is the same fix and regression test originally submitted as [LucasWilkinson/vllm#5](https://github.com/LucasWilkinson/vllm/pull/5), moved to the upstream repository. It is related to @LucasWilkinson's [#63823](https://github.com/vllm-project/vllm/pull/63823), but independently targets `main` and does not include that PR's padding-only replay change.

## Claims

- Keep `-1` invalid in the helper shared by dispatch and combine.
- Preserve the existing mapping for valid IDs and the no-map path.
- Add adapter contract regressions for mixed inputs (including valid IDs), all-padding and linear placement.

## Details

The test-only follow-up reduces the regression from 93 to 80 lines: valid IDs are covered in the mixed case; input-purity assertions were removed; and the expert-output fixture shrank from 2 MiB to 64 KiB. Both dispatch and combine checks, all-padding coverage, the no-map control and module-cache cleanup remain.

Python/PyTorch negative indexing means `mapping[-1]` selects the last entry. The fix uses `torch.where(topk_ids >= 0, mapping[topk_ids], -1)`: valid IDs retain their mapped value, while invalid IDs remain invalid. The shared helper covers both dispatch and combine without changing collective ordering. It adds mask/selection work on the mapped path; its GPU cost is unmeasured.

Triggering this requires **both a non-None mapping table and incoming invalid IDs**. Default linear placement does not use that table. Placement eligibility alone does not establish a model-level reproducer: the standard grouped router's padding filtering is currently gated to DeepEP-v2 in the factory. No default DeepSeek failure, incorrect model output or GPU overflow is claimed.

@LucasWilkinson cc @bnellnm — clarifying the relationship with #63823:

`-1` is an invalid/padding route sentinel, not a valid expert ID. If padding-only replay in #63823 sends `-1` routes into NIXL while a global-to-physical mapping table is active, the existing `mapping[-1]` lookup turns them into the last real expert in that table. This PR preserves `-1` through the helper shared by dispatch and combine, keeping those routes marked invalid.

The changes are complementary: #63823 changes microbatch graph replay, while this PR fixes existing adapter behavior on `main` and can be reviewed independently. The adapter-level failure and fix are covered by the CPU regressions. I have not verified that #63823 actually reaches this mapped-invalid-ID combination in an end-to-end model run, so I am not claiming that #63823 requires this fix.

The corresponding explanation is also in https://github.com/vllm-project/vllm/pull/63823#issuecomment-6445271363.
