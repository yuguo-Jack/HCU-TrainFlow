# [ROCm][Muse Spark] Quark MXFP4 support on gfx942

[Upstream PR](https://github.com/vllm-project/vllm/pull/64084) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

`amd/Muse-Spark-Open-816B-A42B-Quark-MXFP4` fails to start on gfx942 (MI300X/MI325X). This PR runs its routed experts there on the existing AITER Triton W4A16 kernels, keeping the MXFP4 weights and using BF16 activations. Changes are confined to the Muse Spark AMD MoE runner, its tests, and the Muse Spark recipe.

## Claims

- The Quark MXFP4 checkpoint now serves on gfx942 with TP: GSM8K 96.97% on 4x MI325X (TP4), where it previously failed at model construction.
- DFlash2 speculative decoding works on top of it unchanged (acceptance length 4.96 on GSM8K with `RadixArk/Muse-Spark-Open-DFlash2`).
- gfx950 behaviour is unchanged: the CK W4A4 experts are still selected whenever the oracle picks `AITER_MXFP4_MXFP4`.

  --max-num-seqs 64 --max-num-batched-tokens 8192 --reasoning-parser muse
```

```

These end-to-end runs predate the rebase; the runner is unchanged by it, and the rebase only adapted the test to main's `triton_weight()` storage (#62407). CUDA graphs on (the engine resolves to `FULL_DECODE_ONLY`), greedy, max 4096 output tokens, concurrency 64, `--speculative-config '{"method": "dflash", "model": <draft>, "num_speculative_tokens": 7}'`:

**Unit tests**, MI325X, rebased on main (`5689c2790c`), run in `vllm/vllm-openai-rocm:nightly` `0.33.0rc1.dev484+g76c6f3f2a` with this PR's files and main's `amd/model.py` mounted, `pytest tests/kernels/moe/test_muse_spark_rocm_bf16_moe.py`: 32 passed, 3 skipped (gfx950-only).

- `test_rocm_aiter_w4a16_mxfp4_moe_matches_dequantized_reference` (gfx942) builds a real `RoutedExperts` and `MuseSparkQuarkOCPMXFusedMoE`, loads MXFP4 weights through `process_weights_after_loading`, and runs the resulting kernel against an explicit reference on the dequantized weights, including the post-expert norm and router weighting. It covers 16 routes (aiter's fused sort), 64 routes, and 65,544 routes (int32 indices), and checks that CUDA graph replay matches eager exactly. With the gate/up interleave removed, all three cases fail (~97% of elements mismatched).
- `test_muse_mxfp4_method_requires_w4a4_aiter` also covers the gfx942 selection and checks that an explicit `--moe-backend` is not replaced.

`pre-commit run` on the changed files passes, and the recipe validates with `node scripts/validate-source.mjs --source vllm` from vllm-project/recipes.

**CI.** The `(MI300) MoE Kernels` step runs `tests/kernels/moe` on gfx942, so the new test runs there. The gfx942 end-to-end run needs the 509 GB checkpoint and is not in CI; it was run locally as above.

## Details

**Root cause.** The Muse Spark ROCm MoE accepts only the CK W4A4 experts (`AITER_MXFP4_MXFP4`), which need gfx950's FP4 matrix cores. On gfx942 the Quark W4A4 oracle falls back to `EMULATION`, which the model rejects.

**Fix.**

- On gfx942 with AITER enabled and `--moe-backend` `auto`/`aiter`/`aiter_triton_mxfp4_bf16`, `MuseSparkQuarkOCPMXFusedMoE` switches to `AITER_TRITON_MXFP4_BF16` with the new `MuseSparkAiterW4A16Experts`. Other cases raise as before.
- `MuseSparkAiterW4A16Experts` keeps the route-preserving contract of the CK experts. Each expanded (token, route) row is routed top-1 by a one-hot logit, so the softmax gate is exactly 1 and GEMM2 writes one unweighted output per route. That output goes to the existing `MuseSparkTopKWeightAndReduce` (post-expert norm, router weights, TP reduction). The stock `aiter_triton_kernel_w4a16_moe_forward` does the work; no new kernels.
- The Triton SwiGLU epilogue reads gate/up as interleaved row pairs while Muse loads `w13` as `[gate | up]`, so `process_weights_after_loading` interleaves the `w13` rows and scales before Quark's Triton swizzle.
- `AITER_TRITON_USE_HERD` changes aiter's top-k selection and could drop the one-hot expert, so the new experts reject it.

**Limitations.**

- TP only; expert parallelism is rejected on this path.
- Numerics differ from gfx950 because activations stay BF16 instead of dynamic MXFP4.
- The BF16 -> MXFP4 online path (`VLLM_ROCM_MUSE_MOE_ONLINE_QUANT=mxfp4`) goes through the same code but was not run end to end on gfx942.
- The recipe's AMD flags (`ROCM_AITER_FA`, breakable `FULL_AND_PIECEWISE` graphs, TP8) were not validated on gfx942, so the recipe documents gfx942 support in its guide without adding MI300X/MI325X to `supported_hardware`.
- No throughput comparison against the BF16 checkpoint or FP8 requantization.

**Not a duplicate.** Open Muse Spark AMD PRs either speed up the gfx950 MXFP4 path (#63290, #63263, #63298, #63254) or target the separate PTPC-FP8 checkpoint on MI300X (#63721–#63725, #63727, #63729). None enables the MXFP4 checkpoint on gfx942. Several touch `muse_moe_runner.py`, but not the backend selection.
