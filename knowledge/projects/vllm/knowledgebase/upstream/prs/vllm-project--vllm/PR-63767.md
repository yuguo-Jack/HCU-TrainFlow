# [Rust Frontend] Export request metric series at startup like Python

[Upstream PR](https://github.com/vllm-project/vllm/pull/63767) · state: closed · merged: True

## Original PR description

## Overview

Python's `PrometheusStatLogger` creates every per-engine request series when the frontend starts, including one `vllm:request_success` child per `FinishReason`, so a fresh server exports them with value 0. The Rust frontend creates each series on first use, so a series appears only when a request first records into it. This PR creates them at startup.

## Claims

- Right after startup, the Rust frontend exports zero-valued request series per engine: `vllm:request_success` for all five finish reasons, plus the request token counters and histograms.
- `increase()`/`rate()` no longer lose the first increment of a series that previously appeared with value 1. For example, the shipped Grafana dashboard's `sum by(finished_reason) (increase(vllm:request_success_total[...]))` missed the first abort after startup.

- `connecting_exports_zero_valued_request_metrics_before_any_request` (`rust/src/llm/tests/generate.rs`) connects to a mock engine, sends no request, and snapshots the zero-valued series; it fails on `main`, where no series is rendered.
- The existing request-metrics tests (`generate_records_request_metrics_in_prometheus_output`, `generate_without_engine_stats_exports_only_frontend_observed_metrics`, `dropping_stream_records_abort_terminal_request_metrics`, the server's `metric_delta` checks) pass unchanged.

## Details

Python: `create_metric_per_engine(...)` in `PrometheusStatLogger.__init__` (`vllm/v1/metrics/loggers.py`), and `for reason in FinishReason:` for `vllm:request_success` (`loggers.py:807-819`).

Rust before: `RequestMetricsTracker::new` (`rust/src/llm/src/request_metrics.rs`) resolved the handles with `get_or_create` on every request, and `record_request_success` created a `finished_reason` child only on first use. Another consumer that saw the difference is `label_values(vllm:request_success_total, model_name)`, which stayed empty until the first request finished.

Change: `Llm::new` resolves the request metric handles once per connected engine (the engine set is fixed at connect), and each request's tracker shares them through an `Arc`. `vllm:request_success` gets one counter per finish reason, chosen by an exhaustive `match` on `FinishReason`, so a new reason cannot go unexported. The per-request `get_or_create` lookups go away. The labels (served model name, engine index) and the engine-stats gate are fixed when `Llm` is built, so the handles are construction-time state of `Llm`; this mirrors how the engine-core client already pre-creates its scheduler and iteration series per engine in `ClientInner::new`.

`EngineCoreClient::engine_indices` now derives each index the way `call` stamps it on the request stream (`engine_index().unwrap_or(0)`) instead of panicking on an identity that encodes no index, so the handle map is keyed exactly like the streams that look it up. Production identities always encode an index; only test engines do not.

Known difference, unchanged: Python registers `vllm:corrupted_requests` only with `VLLM_COMPUTE_NANS_IN_LOGITS`; Rust always registers it, and now exports it from startup.

Not a duplicate: no open PR pre-creates the Rust request series.
