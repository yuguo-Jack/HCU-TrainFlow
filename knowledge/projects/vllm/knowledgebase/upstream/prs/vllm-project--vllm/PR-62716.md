# [ROCm][Build][1/5] Speed up ROCm build: generate the paged attention instantiations from one variant list

[Upstream PR](https://github.com/vllm-project/vllm/pull/62716) · state: closed · merged: True

## Disclosure

AI assistance was used. The changes were reviewed and tested manually.

## Overview

**Splits each paged attention translation unit on one more item: `block_size`.** `main` (#62475) splits the kernels per (query dtype, kv-cache dtype, head size), giving 12 units, and each of those units still instantiates *both* block sizes and picks one at runtime. **Thus, we now have 24 kernels instead of 12.**

We introduce a generator for these 24 units instead of hand-writting each file: https://github.com/vllm-project/vllm/blob/f4edf9f0f078ae67392510aafd1871288948a3c3/csrc/rocm/generate_paged_attn.py

This PR is part of a 5-PRs series with #62717 (topk softplus-sqrt), #62718 (skinny GEMMs), #63364 (int4 skinny GEMM) and #63365 (fused MUSE-Spark op). All PRs are required for build time gain, see details below.

The single-arch rows are `pip install -e .` on MI350 (gfx950); the 9-arch row is the `setup.py bdist_wheel` described under *Validation*. All cold builds:

| build | `main` | this PR | All 5 PRs (#62921) |
|---|---|---|---|
| `MAX_JOBS=16`, gfx950 only | 107 s | 92 s | 87 s |
| `MAX_JOBS=64`, gfx950 only | 85 s | 86 s | 50 s |
| `MAX_JOBS=64`, 9 archs | 1263 s | 1261 s | 472 s |

## Claims

- Splits each unit on one more item, `block_size`: the runtime `switch (block_size)` inside `paged_attention_*` becomes an entry point per block size (introduced as a kernel dimension by #8310, kept as a runtime branch by #62475), so 12 units become 24 and each instantiates half the kernels.
- 14 % off the single-arch build at `MAX_JOBS=16`; neutral at `MAX_JOBS=64`, where another unit is the tail.
- ~190 lines of hand-written duplication removed: 12 units, 12 prototypes and a 50-line configure-time regex guard collapse into one variant list, so an instantiation can no longer exist without a dispatch arm - which is what the guard used to check.
- Navi-less builds instantiate 11 % fewer device kernels per unit; Navi (gfx11/gfx12) builds are unaffected.
- Nothing about what runs changes: same kernels, same dispatch order, same numerics.

### Why five PRs

The two builds are bound by different things, so no single change moves both.

**Why the three single-arch PRs are all needed.** At 1 arch (`gfx950`, `MAX_JOBS=64`, `main` = 85 s) three groups take turns setting the wall, in this order:

1. topk softplus-sqrt (#62717) - 74.5 s, a single unit
2. paged attention (#62716) - 71.6 s, the slowest of 12 units
3. other skinny GEMMs (#62718) - 40.9 s, a single unit

#62717 takes (1) to 7.4 s, #62716 takes (2) to 31.1 s and #62718 stops (3) from becoming the next tail; with all three the tail moves to `selective_scan_fwd` (37.7 s) and the build goes from 85 s to 49 s. Drop any one of them and a ~70 s unit is back at the top, so the single-arch win needs all three.

**Why that is not enough at 9 archs.** A 9-arch build multiplies every unit's time by ~9, and the tail becomes two files that none of the first three touch: `csrc/rocm/skinny_gemms_int4.cu` at 1232 s and `csrc/fused_muse_spark_qknorm_rope_kv_insert_kernel.cu` at 478 s. All three merged take the 9-arch build from 1263 s to only 1253 s. #63364 splits the first (its tail drops to 448 s) and #63365 the second (to 171 s), which is what reaches 472 s.

The `skinny_gemms_int4.cu` tail is invisible in a `gfx950` build because that file **only emits its kernels for RDNA (that is part of the 9-arch build)**:

https://github.com/vllm-project/vllm/blob/f4edf9f0f078ae67392510aafd1871288948a3c3/csrc/rocm/skinny_gemms_int4.cu#L17-L19
https://github.com/vllm-project/vllm/blob/f4edf9f0f078ae67392510aafd1871288948a3c3/csrc/rocm/skinny_gemms_int4.cu#L568-L579

`csrc/fused_muse_spark_qknorm_rope_kv_insert_kernel.cu` fails differently: it has no arch guard, so a `gfx950` build compiles it for real - it is just 25 s there against 478 s across nine archs, which is why a single-arch profile ranks it as irrelevant (#63365).

## Details

Device code generation for one instantiation set is ~95 s of AMDGPU backend time, so a single file holding every (dtype, kv-cache dtype, head size) combination made the wall clock of the whole build that file. #62475 split it by hand, which left three things to keep in sync: the files, the prototypes in `attention_dispatch.cu` and the dispatch arms (hence the `file(READ)` + regex guard). Generating all three from one `VARIANTS` list removes that coupling:

- one translation unit per (variant, block size) - `block_size` moves from a runtime switch inside the entry point into the entry point name, which is what lets a unit instantiate a single block size;
- `attention_paged_attn_entries.inc`, the `ATTN_ENTRY()` prototypes, included at file scope;
- `attention_paged_attn_dispatch.inc`, the kv-cache-dtype / query-dtype / mfma-type / block-size / head-size dispatch of `paged_attention()`, included in its body.

The generated units do not depend on the arch list: whether the Navi (gfx11/gfx12) kernel set is instantiated is a `VLLM_ROCM_ATTN_NO_NAVI` compile definition that CMake derives from `VLLM_GPU_ARCHES` and sets on the `_rocm_C` target, so every build directory and arch list uses the same files (two builds can no longer overwrite each other's units). What is on disk is recorded in a stamp next to the outputs (`csrc/rocm/.paged_attn_generated`: the script hash plus the exact list of files written, gitignored) rather than in the CMake cache, and CMake takes the source list from that list instead of a glob: a stray or scratch `attention_paged_attn_*.cu` in `csrc/rocm/` is no longer compiled into `_rocm_C`, and a partially deleted set (any `.cu` **or** `.inc`, not just "all of them") triggers regeneration. The script is also in `CMAKE_CONFIGURE_DEPENDS`, so editing it re-runs configure instead of leaving stale units behind. Separately, `-ftime-trace` attributed 6.9 s of the 11.5 s host frontend of a unit to `<torch/all.h>`, which pulls autograd, nn and jit into code that only needs `at::Tensor`, the CUDA stream/guard helpers and `TORCH_CHECK`; the header now includes the ATen/c10 surface only, which cuts both the host and the device parse by ~2/3.

**Change in behaviour.** Only one, and it is narrow: a build whose arch list has no `gfx11`/`gfx12` code objects now raises `TORCH_CHECK(!is_navi, ...)` instead of running a Navi launcher that no code object backs. The `mfma_type` handling keeps the previous semantics (the last arm is a plain `else`, so an unrecognised value still selects the f16 MFMA kernels rather than failing). Numerics are unchanged.

**How the matrix got this big.** The instantiation space this PR splits was grown one axis at a time:

| PR | landed | what it added to the instantiation space |
|---|---|---|
| #8310 | 2024-09-13 | initial ROCm paged attention: 4 kernels over `{fp16, bf16}` x head `{64, 128}` x block `{16, 32}` x alibi `{on, off}` |
| #8577 | 2024-09-19 | fp8 KV cache: the `KV_DTYPE` / `cache_t` axis |
| #12348 | 2025-03-04 | partition/reduce rewrite: 4 -> 6 kernels (`mfma16`, `mfma4`, `reduce`) |
| #17139 | 2025-05-07 | fp8 output fusion: `OUTT` becomes `uint8_t` when `fp8_out_scale` is set = x2 |
| #17004 | 2025-05-21 | RDNA/Navi: the whole set duplicated for gfx11/gfx12, 6 -> 12 `__global__` |
| #22222 | 2025-09-15 | fp8 attention update: adds `MFMAType` (`Fp8` vs `F16`) = x2 on the fp8 path |
| #42755 | 2026-10-15 | `USE_INTERLEAVED_V_CACHE` added to all 12 kernels = +50 % |

So the matrix this PR splits is a product of six axes. This PR adds none of them; it cuts the product into 24 units.

### Left to do

Follow-ups identified while doing this, deliberately out of scope:

- [ ] Split the units further along `alibi` / `fp8_out_scale`: measured a loss while each unit paid ~20 s just to parse `attention_kernels.cuh`, which is ~6 s now.
- [ ] Cheaper debug info for HIP kernels: dropping `-g` saves ~18 % of a unit's compile time at 1 arch and more at 9 (`RelWithDebInfo` applies `-g` to every unit).
- [ ] `csrc/mamba/selective_scan_fwd` is the next tail once the two per-unit splits are in (296 s at 9 archs, 37.7 s at 1): split or prune its instantiations.
- [ ] `<torch/all.h>` still comes in transitively via `rocm/dispatch_utils.h`, which ~50 TUs include; trimming it there needs a CUDA build check.
- [ ] `hipify_all` is a single serial command (1.9 s) that every compile waits on - worth parallelising once the wall clock is ~10 s.
- [ ] Not done here on purpose: folding the 12 `VARIANTS` dicts into a product of three tables and dropping the redundant `clang-format off/on` pair around the generated include - refactor churn that does not change the build outcome.
- [ ] Not done here on purpose: `MANIFEST.in` has `recursive-include csrc *`, so an sdist built from an already-configured tree would ship the generated units (harmless, they are regenerated; CI sdists come from a clean clone), and the ROCm build docs do not yet mention that changing `PYTORCH_ROCM_ARCH` regenerates these units.

Nit (non-blocking) (for dev convenience):

Only the generator script is in CMAKE_CONFIGURE_DEPENDS. If a generated unit or the stamp is deleted, for example by git clean -X on the source tree with an out-of-tree build dir, plain ninja / cmake --build fails instead of regenerating:
  

>    ninja: error: '.../csrc/rocm/attention_paged_attn_h64_f16_auto_bs16.cu', needed by '.../csrc/rocm/quickreduce/custom_quickreduce.hip', missing and no known rule
>    to make it

  
   pip install isn't affected because it always re-runs configure, but the preset/ninja flow in docs/contributing/incremental_build.md is. Adding the stamp and the outputs as configure dependencies fixes it, after the endif() that closes the generation block (~L1631):
  
     list(TRANSFORM VLLM_ATTENTION_PAGED_ATTN_SRC PREPEND ${CMAKE_CURRENT_SOURCE_DIR}/
       OUTPUT_VARIABLE _attn_gen_abs)
     set_property(DIRECTORY APPEND PROPERTY CMAKE_CONFIGURE_DEPENDS
       ${ROCM_ATTN_GEN_STAMP} ${_attn_gen_abs})
  
   With this, ninja prints "Re-running CMake...", regenerates the missing file and builds.
