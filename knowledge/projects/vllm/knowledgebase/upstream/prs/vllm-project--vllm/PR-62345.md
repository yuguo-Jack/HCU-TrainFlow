# [Bugfix][Security] muse_glimmer: fix quadratic attribute scans in tool-call extraction

## Purpose

`muse_glimmer`'s tool-call extraction finds the `name="..."` attribute of an ATEM tag by skipping the rest of the tag with `[^>]*?`. That class crosses `<`, so when model output opens tags without closing one, the attribute search restarts at every `<atem:invoke` / `<atem:parameter` position and each attempt scans to the end of the block — the cost grows with the **square** of the output length.

Model output is the input, so a long generation that repeats an opening tag stalls the event loop inside `extract_tool_calls`.

Found by a dynamic scan: every regex literal in `vllm/` was compiled with the engine its own module imports (`regex` here, not `re` — they behave very differently on these shapes) and run against inputs built by pumping the pattern's own repeated atoms, with the growth measured from 200 to 800 units. 207 patterns, measured, not inferred.

## Fix

`[^<>]` instead of `[^>]` for the two attribute runs. A tag's attributes cannot contain either bracket, so no well-formed markup changes meaning; a failed attempt now stops at the next `<` instead of running to the end of the text, which makes the total work linear.

## Test Plan

New case in `tests/tool_use/test_muse_glimmer.py` (the file that already drives this parser): one complete invoke block of 52 KB on the tool channel, with the same channel header as the existing `test_single_tool_call_after_reasoning`, asserting the parse stays under 1 s. The repaired cost is ~2 ms, the old one 7.5 s, so the bound does not depend on runner speed.

## Test Result

Driving the compiled patterns exactly as `_parse_tool_calls` does (`_INVOKE_RE.findall` → `_NAME_RE.search` → `_PARAM_RE.finditer`), on `"<atem:invoke " * n` closed by one `</atem:invoke>`:

| bytes | before | after |
|------:|-------:|------:|
| 6,514 | 121.4 ms | 0.21 ms |
| 13,014 | 468.6 ms | 0.38 ms |
| 26,014 | 1871.9 ms | 0.77 ms |
| 52,014 | **7495.4 ms** | **1.52 ms** |

4x per doubling before, 2x after — quadratic becoming linear.

Equivalence, same driver, old vs new patterns:

```
well-formed  : [('get_weather', {'city': 'Paris'})]   identical
extra attrs  : name parsed identically ('g'), parameters identical
multi invoke : [('a', {'k': '1', 'j': '2'}), ('b', {})]   identical
```

**What I could not do:** vLLM is not installed in this environment and its maturin/Rust build does not complete here, so I could not run pytest. The numbers above come from the patterns themselves with the engine the module imports; the new test is written to match the existing tests in that file but has not been executed. Please treat the test as needing a CI pass.

## Not fixed here

`_INVOKE_RE` (`<atem:invoke\b.*?</atem:invoke>`) is quadratic in the same way but much milder — 32 ms at 52 KB — because its `.*?` has to cross `<` to span a block. Fixing it needs a different structure rather than a character class, so I left it alone instead of guessing.
