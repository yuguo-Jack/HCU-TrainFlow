# [Bugfix][Kernel] Fix reshape & cache dropping KV heads past 512 chunks

[Upstream PR](https://github.com/vllm-project/vllm/pull/64087) · state: open · merged: False

## Original PR description



## Overview

`reshape_and_cache` leaves KV heads unwritten when a token has more than 512 16-byte chunks, so `ROCM_ATTN` silently reads stale KV cache data for shapes such as 32 KV heads × head size 192/256 in bf16. This restores a thread-stride loop in the kernel and adds a regression test. It fixes Pattern B of #62697. Pattern A (decode reads at block size 528 on gfx1201) is a separate problem and isn't addressed here.

## Claims

- `reshape_and_cache` now writes every KV head for any `num_kv_heads * head_size`. Before, chunks past the 512th per token were skipped whenever `num_kv_heads * head_size * cache_element_size > 8192` bytes.
- With the reporter's script, the three failing Pattern B cases of #62697 now match `TRITON_ATTN` (max error ≤ 0.0006, previously 0.097–0.196).
- No other test outcome changes, and no performance change for shapes that fit within 512 chunks per token (see Validation).

## Details

**Root cause.** #25955 replaced the kernel's thread-stride loop over all elements with one thread per (KV head, 16-byte chunk) pair, but kept the launch cap of `dim3 block(std::min(num_heads * head_div_x, 512))`. When `num_heads * head_size / x > 512` (`x = 16 / cache element size`, so 8 for fp16/bf16 and 16 for fp8), the extra chunks get no thread. For example, with bf16 and 32 KV heads, head size 256 means 1024 chunks, so heads 16–31 are never written. Head size 192 means 768 chunks, so head 21 is partly written and heads 22–31 not at all. The unwritten slots keep whatever the cache block held before, so the outputs are silently wrong rather than crashing. `test_reshape_and_cache` only uses `NUM_HEADS = [8]` (at most 256 chunks), so CI never hit the limit.

**Fix.** The per-chunk body is wrapped in `for (h_block_idx = threadIdx.x; h_block_idx < num_heads * h_block_count; h_block_idx += blockDim.x)`, and the scale setup moves above the loop. `reshape_and_cache_flash_kernel` already strides by `blockDim.x` in the same way. The launch configuration is unchanged. Most of the diff is re-indentation, so view it with whitespace hidden (10 lines changed).

This keeps one block per token, preserving the current launch behavior and avoiding repeated token metadata and scale loads. A 2D launch with multiple blocks per token could expose more parallelism for over-limit shapes, but would add scheduling overhead and needs tuning across token counts and GPU architectures. The strided loop is the minimal correctness fix; a multi-block layout can be evaluated separately as a performance optimization.

AI assistance (Cursor) was used for the root-cause analysis, the patch, the test and the validation scripts. I reviewed every changed line and ran the validation above.
