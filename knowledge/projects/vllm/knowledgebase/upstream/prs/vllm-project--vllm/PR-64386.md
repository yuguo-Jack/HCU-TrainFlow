# [ROCm][Bugfix] Route padded MoE rows to expert 0 with zero weight on the AITER a4w4 path

[Upstream PR](https://github.com/vllm-project/vllm/pull/64386) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

With `VLLM_MOE_SKIP_PADDING=1` (the default), the grouped top-k router marks padded rows with `topk_ids = -1` and weight 0. On ROCm, AITER's a4w4 MoE path (`VLLM_ROCM_USE_AITER_MOE_A4W4_DSV4=1`, DeepSeek-V4 MXFP4 w4a4) can raise `hipErrorIllegalAddress` on those ids. A cudagraph warmup batch is all padding, so a graph-mode boot dies right after memory profiling, and padded decode batches hit the same input. This PR sends padded rows to expert 0 with weight 0 on that path only.

## Claims

- On the AITER a4w4 path, `rocm_aiter_fused_experts` no longer passes -1 ids to AITER. Padded rows go to expert 0 with weight 0, so their output is still zero.
- The remap uses out-of-place `masked_fill`, so it is cudagraph-capture safe and leaves the caller's tensors untouched.
- Other AITER paths are unchanged. They keep -1, which their sorts skip.

**Cost.** Against `VLLM_MOE_SKIP_PADDING=0`, median TPOT is 18.75–18.93 ms with this PR and 18.88–18.93 ms without, so there's no measurable decode cost.

**Valid rows.** A kernel check at a TP4 rank's shape (E 384, top-k 6, hidden 5120) compares 65 valid rows padded to 80, with 16 of them on expert 0, against the 65 rows alone, 20 runs each. The a4w4 kernel isn't run-to-run deterministic even without padding, so bitwise equality can't be asserted. The padded runs stay within the unpadded runs' own spread, and padded rows' contents don't affect valid rows. Padded rows' output is exactly 0.

- **Setup:** TP1 with `moe_intermediate_size` set to a TP4 rank's 576, so every MoE call has a TP4 rank's shape. For expert 0's rows it is 99.79% against 99.85%. With different padded-row activations it is 99.73%. The small gap fits the 80-row launch rounding slightly differently from the 65-row one.

## Details

**Root cause.** At the first cudagraph warmup (80 tokens), every MoE call gets all-`-1` ids and zero weights. With -1 ids, `mxfp4_moe_sort` returns `num_valid_ids = [0, M]` and leaves `sorted_expert_ids` unwritten, and the next `aiter.fused_moe` call faults. The fault is intermittent and depends on memory layout. The root fix belongs in AITER, and the remap can be removed once AITER handles -1 ids on this path. AITER issue: _to be filed; link pending_.

**Tradeoffs.**
- Padded rows now count toward expert 0's token count, at weight 0, so the output is unchanged.
- Expert parallelism was considered but not booted. With EP, AITER gets global ids plus `expert_mask`. Remapped rows point at global expert 0, so only the rank that holds it computes them, at weight 0, and the other ranks drop them. Either way the output is unchanged.
- `VLLM_MOE_SKIP_PADDING=0` also avoids the crash, but only for users who know to set it.
