# fix(gguf): Auto-select compatible dtype for GGUF models on Blackwell

[Upstream PR](https://github.com/vllm-project/vllm/pull/30410) · state: open · merged: False

## Original PR description

## Summary

Adds `_resolve_dtype_conflict()` to automatically select float32 when both bfloat16 (GGUF/Blackwell) and float16 (Gemma2/Gemma3) are disallowed.

## Changes

- Add dtype conflict resolution logic in model config
- Auto-select float32 as compatible dtype when no other option works
- Log informative message about automatic dtype selection

## Root Cause

Gemma2/Gemma3 models disallow float16 (numerical instability), while GGUF on Blackwell disallows bfloat16 (precision issues). Only float32 works for both.

## Testing

Tested with Gemma2 GGUF on RTX 5090 - model loads and runs correctly with auto-selected float32.

- ErenAta16 · comment · 2026-07-13T13:46:14Z · [source](https://github.com/vllm-project/vllm/pull/30410#issuecomment-4958617191)

Checked this against current `main`, the target functions (`_get_quantization_config`, `_is_valid_dtype`) still exist in the same shape, so this still applies. The core scenario checks out: `_FLOAT16_NOT_SUPPORTED_MODELS` blocks float16 for Gemma3 (numerical instability), and GGUF's `get_supported_act_dtypes()` blocks bfloat16 on Blackwell, so Gemma3 + GGUF + Blackwell currently has zero valid dtypes and hits the hard `ValueError` unconditionally. The preference-ordered fallback (try fp16, then bf16, then fp32, filtered by what's actually valid for the model type) correctly resolves to float32 for that case.

Two things worth getting a maintainer's read on before merge though:

1. `has_device_capability(100)` -> `has_device_capability(120)` narrows the bf16-precision-issue check from "SM 10.0+" to "SM 12.0+ only". Per `has_device_capability`'s own semantics (`current_capability.to_int() >= capability`, where the int is `<major><minor>`), that excludes datacenter Blackwell (B100/B200, SM 10.0) from the restriction going forward, only consumer Blackwell (RTX 50-series, SM 12.0) keeps it. The original comment said "bfloat16 has precision issues on Blackwell devices" with no such distinction. Is the SM 12.0-only claim based on actual testing showing B100/B200 doesn't have this issue, or did the 100->120 change happen incidentally while chasing the RTX 5090 case specifically? If the latter, this silently re-enables bf16 on datacenter Blackwell without that having been verified.

2. The new fallback in `vllm/config/vllm.py` applies broadly, any `model_config.dtype not in supported_dtypes` now gets silently auto-corrected with a warning instead of raising, not just the Gemma3-on-Blackwell-GGUF case. If a user explicitly sets a dtype that happens to conflict with their quantization method for an unrelated reason, they'll now get their choice silently overridden rather than an error telling them why. Is that the intended scope, or should this be gated more narrowly to the specific known-conflicting-restrictions case this PR targets?

### Missing fallback when no preferred dtype matches compatible list

**Low Severity**

<!-- DESCRIPTION START -->
If `compatible_dtypes` is non-empty but contains no dtypes from `dtype_preference` (float16, bfloat16, float32), the for loop completes without `break`, leaving `model_config.dtype` unchanged at its original unsupported value. The code then continues to `quant_config.maybe_update_config()` and returns without raising an error, silently using an invalid dtype. For GGUF this cannot occur since all its supported dtypes are in the preference list, but it's a latent risk for future quantization methods.
<!-- DESCRIPTION END -->

### LoRA dtype set before model dtype auto-correction

**Medium Severity**

<!-- DESCRIPTION START -->
In `VllmConfig.__post_init__`, `lora_config.verify_with_model_config()` is called before `_get_quantization_config()`. When `lora_dtype` is "auto", it copies `model_config.dtype` (e.g., bfloat16). Then `_get_quantization_config()` may change `model_config.dtype` to float32. This leaves `lora_config.lora_dtype` with the stale bfloat16 value, creating a dtype mismatch between LoRA weights and the model when using LoRA with GGUF on Blackwell.
<!-- DESCRIPTION END -->
