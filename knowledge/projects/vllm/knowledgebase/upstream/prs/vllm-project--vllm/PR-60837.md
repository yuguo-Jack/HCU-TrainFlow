# [Bugfix][Scheduler] Fail requests whose encoder input can never be scheduled

[Upstream PR](https://github.com/vllm-project/vllm/pull/60837) · state: closed · merged: False

## Original PR description

## Summary

Fixes #60819.

A multimodal encoder input that is larger than the whole per-step encoder budget or the whole encoder cache capacity can never be admitted by `EncoderCacheManager.can_allocate()`. `_try_schedule_encoder_inputs()` handled this case like any other budget/capacity shortage: it trimmed `num_new_tokens` to 0 and deferred the request. Since the condition cannot change between scheduling steps, the request was re-queued forever — no failure path, no timeout, and no log line; the client simply never received a response (see the linked issue for a reproduced case where a single image above the effective budget wedged the instance with `Waiting: 1` indefinitely).

This PR distinguishes two cases in the `can_allocate()` failure branch:

- **Structural** — the input alone exceeds the *full* per-step encoder budget (`max_num_encoder_input_tokens`) or the *total* encoder cache capacity (`cache_size`), so no future step can ever admit it. The request is now terminated with `FINISHED_ERROR` in the same engine step, reusing the existing `encoder_cache_mismatch_reqs` drain pattern in `update_from_output()`, plus a `logger.error` spelling out the input size vs. budget/cache numbers and the knobs to tune.
- **Transient** — the input fits the full limits but this step's budget is consumed or the cache is temporarily full. Behavior is unchanged: the request is deferred and retried as before.

The comparison is deliberately against the *whole* budget/capacity rather than the amounts remaining in the current step, so transient contention (e.g. items that only fit once the earlier items of the same step have been encoded and cached) never produces a false failure.

## Tests

- `test_oversized_encoder_input_fails_request_instead_of_waiting_forever`: a 2000-embedding item vs. a 1024-token budget is not scheduled, and `update_from_output()` finishes it with `FINISHED_ERROR` and removes it from the waiting queue in the same step.
- `test_encoder_input_fitting_budget_is_not_failed`: a 900-embedding item against the same budget keeps the existing scheduling behavior and survives the step.

## Known limitations

- The `FINISHED_ERROR` output carries no error text today (same as the existing encoder-cache-mismatch and grammar-compile-error paths); the detailed numbers are only in the engine log.
