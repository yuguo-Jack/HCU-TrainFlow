# [Bugfix][Flint] Fix silu_and_mul crash on TP-sharded MLP widths

[Upstream PR](https://github.com/vllm-project/vllm/pull/63986) · state: open · merged: False

## Original PR description


## Overview

Flint's dense-MLP `silu_and_mul` crashes whenever the MLP width is TP-sharded: with `--tensor-parallel-size 4` the 6144 intermediate shards to 1536, which fails `assert d % bd == 0` at engine startup; with TP8 it shards to 768, which passes the assert but is not a power of two, so `tl.arange(0, BD)` fails Triton compilation. Select the block width as the largest power-of-two divisor of `d`, capped at 1024.

Fixes #63984

## Claims

- Flint serves with `--tensor-parallel-size 4` and `8` (previously: startup crash on both).
- Every previously working width keeps an identical launch configuration (6144 -> BD 1024, 3072 -> BD 1024, 2048 -> BD 1024, 512 -> 512, 256 -> 256); the newly reachable widths resolve to 1536 -> BD 512, 768 -> BD 256.
- Kernel math is unchanged; op output is bit-exact vs the fp32 reference on all tested widths.

## Validation

- New regression test `test_silu_and_mul_tp_sharded_widths` (d = 3072/1536/768) in `tests/models/flint/test_flint_ops.py`, asserting exact-fraction > 0.999 and `assert_close(rtol=2**-7)` against the existing `_silu_and_mul_ref` helper.
- pytest red/green on SM120 (8x RTX 5090), run through a scratch copy of the test file with the module's SM100-only skip gate removed (the gate currently keeps this suite from running on SM120):
  - pre-fix: `2 failed, 1 passed` — 1536 -> `AssertionError`, 768 -> `triton.compiler.errors.CompilationError: arange's range must be a power of 2`
  - post-fix: `3 passed`
- Serve smoke, NVFP4 GGUF checkpoint, `--max-model-len 8192`:
  - pre-fix TP4: engine init crash with the assert traceback (see issue)
  - post-fix TP4: `/health` 200 in ~195s, coherent chat completion (`system_fingerprint ...-tp4-...`)
  - post-fix TP8: `/health` 200 in ~165s, coherent chat completion (`system_fingerprint ...-tp8-...`)
- Full pre-commit suite passes.
- No model evals: the change only alters block-width selection for widths that previously crashed; all previously working widths launch identically and op-level output is bit-exact vs the fp32 reference.

## Details

**Root cause:** `vllm/models/flint/ops/norm.py` used `bd = min(d, 1024)` with `assert d % bd == 0`. `FlintMLP.forward` calls the custom op unconditionally whenever the fused GEMV path is not eligible (always at engine init, during the profiling forward), and TP shards the 6144 dense intermediate to non-1024-divisible (TP4) or non-pow2 (TP8) widths.

**Fix:** `bd = min(d & -d, 1024)` — the lowest set bit of `d` is its largest power-of-two divisor, so `bd` divides `d` by construction (unmasked loads stay in bounds, grid stays `(m, d // bd)`) and is a power of two (`tl.arange` requirement). The kernel itself is untouched.

**Non-duplication:** searched open issues and PRs (`flint tensor parallel`, `flint silu`) and merged PRs mentioning flint (only #62938 model-add and #63609 CI-disable); no prior fix for this.

**CI note:** the flint step in `.buildkite/test_areas/models_basic.yaml` is currently commented out (disabled in #63609 pending a pinned gguf install), so the new test runs once that suite is restored; validation was done outside CI as above. The TP "not validated" note in `recipes/models/RecursiveSI/flint.yaml` is deliberately left untouched — a full TP validation pass would be a separate follow-up.
