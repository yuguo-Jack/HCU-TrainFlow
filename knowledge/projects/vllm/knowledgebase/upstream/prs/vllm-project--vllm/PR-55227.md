# [Bugfix][Core] Skip cascade prefixes during deferred KV frees

[Upstream PR](https://github.com/vllm-project/vllm/pull/55227) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->
## Overview

Suppress cascade common-prefix detection while deferred KV frees retain references from finished requests. Resume normal detection once those references drain.

## Claims

- Retained references can make unrelated surviving requests appear to share a prefix.
- A native scheduler reproduction reports 16 common blocks for eight survivors with distinct first blocks.
- The guard preserves allocation, freeing, and fence behavior; its fallback is ordinary attention over each request's own block table.

## Validation

Validated on 2026-10-10 at published head `67fd6b642f` and in a temporary merge with upstream `276fbcff2717bd934cfa37c8a2e4c391f3e7237b`. The published branch was not rebased.

```sh
VLLM_TARGET_DEVICE=cpu CUDA_VISIBLE_DEVICES='' .venv/bin/python -m pytest tests/v1/core/test_deferred_block_free.py tests/v1/core/prefix_cache/test_partial_prefix_cache_hits.py tests/v1/core/test_single_type_kv_cache_manager.py -q
.venv/bin/pre-commit run --hook-stage manual --files vllm/v1/core/sched/scheduler.py tests/v1/core/test_deferred_block_free.py
```

The three suites pass **73 tests at the PR head** and **240 on current upstream plus the fix**; all applicable scoped hooks pass. Removing the guard produces **1 failure and 1 pass**, reporting 16 common blocks for unrelated survivors.

**GPU output check:** published Python source, real `facebook/opt-125m` weights (`27dcfa74d334bc871f3234de431e71c6eeba5dd6`), RTX 5070 Ti, FP16, MRV1, FlashAttention 2, eager async scheduling, 257-token prompts, 32-token survivors, existing precompiled extensions. A probe scheduler enables the existing deferred-free gate; scheduling, references, fences, and attention execute natively. This does not test a deployed KV connector.

Two scenarios ran three times each: eight distinct survivor prefixes, and eight genuinely shared prefixes with seven retired requests using another prefix. Every held step had seven deferred frees, eight scheduled survivors, candidate prefix 16 blocks, and guarded prefix zero. Normal FA2 cascade resumed with a 256-token prefix after the fence drained.

All **1,578 output token IDs** matched cascade-disabled references. Distinct-prefix logprobs and the guarded steps matched exactly. Later normal-cascade shared-prefix logprobs differed by at most **0.008461**; token IDs stayed equal.

Tiny-model throughput is not a production benchmark. Excluding each scenario's first cold run leaves two warmed runs per mode:

| Scenario | Cascade disabled, tokens/s | Guarded cascade enabled, tokens/s |
| --- | ---: | ---: |
| Distinct | 3409–3521 (median 3465) | 2854–3192 (median 3023) |
| Shared | 3409–3414 (median 3412) | 2810–2855 (median 2832) |

Enabled-mode timing is slower and variable even when both modes use ordinary attention. These runs do not isolate the guard's throughput cost.

## Details

Common-prefix detection compares block reference counts with the number of tracked requests. Finished requests leave the request tables before their in-flight blocks release references, making that equality insufficient.

The guard disables cascade for all groups while any deferred free remains, including blocks unrelated to the candidate prefix. This can reduce optimization opportunities under sustained completions; Production throughput impact remains unmeasured.

Fresh overlap review found no replacement. Related #49675 has merged and #49674 is closed; they concern zero-progress preemption retries rather than common-prefix correctness.

Upstream CI is blocked at contributor authorization. AI assistance was used for investigation, implementation, tests, and review.
