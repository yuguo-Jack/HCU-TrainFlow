# [Bugfix][RL] Fix cross-stream reuse of packed NCCL receive buffers

[Upstream PR](https://github.com/vllm-project/vllm/pull/62555) · state: closed · merged: True

## Original PR description

## Overview

Fixes #62554. `packed_nccl_broadcast_consumer` lets the caching allocator hand a receive buffer to the next receive while a layerwise-reload replay on another slot stream still reads it. This corrupts MoE weights after packed NCCL weight updates.

## Claims

- Fixes silent weight corruption with packed NCCL weight transfer plus layerwise reload when a layer spans several packs (reproducer: 10/10 corrupted reloads on `main`, 0/10 with this PR).
- Orders every `post_unpack_func` after all earlier receives, instead of relying on NCCL's in-order completion.
- No measurable change in sync time; two-stream overlap is preserved.
- Same or lower peak memory than `main`, except layerwise reload over a slow transport, which reserves one to a few packs more because buffers with pending reads can no longer be reused early.

## Validation

All on this PR's head, 4x H100, torch 2.14.

- **New tests** (`pytest tests/distributed/test_packed_tensor.py -k DeferredConsumer`): 4 fail on `main` (20/20 runs), 4 pass here. The allocator test asserts the reuse directly via `data_ptr`s, so it fails on `main` regardless of GPU timing.
- **Upstream suites** (`test_packed_tensor.py`, `test_weight_transfer.py`, `test_weight_transfer_nccl_uid.py`, `test_gpu_worker_weight_transfer.py`, `test_reload.py`): 250 passed, 36 skipped, 2 xpassed, 0 failed.
- **Reproducer** (in the issue; real NCCL over NET, real `RoutedExperts`, real layerwise reload): 10/10 corrupted on `main`, 0/10 here.
- **Served** (`rlhf_http_nccl.py` layout, TP=2 OLMoE, NET): `/weight_checker` matched after every sync with per-expert, grouped per-expert and fused senders; greedy outputs identical to `main`.

**Latency** (`examples/rl/rlhf_http_nccl.py`, median of 10–12 syncs):

| config | main | this PR |
|---|---|---|
| opt-125m (example as written) | 61.9 ms | 61.7 ms |
| Qwen3-0.6B, 32 MB packs | 122.5 ms | 123.0 ms |
| OLMoE-1B-7B, 104 packs, NET | 4,886 ms | 4,929 ms |
| OLMoE-1B-7B, 13 packs (1 GB default), NET | 4,945 ms | 4,928 ms |

Overlap with 2 buffers is unchanged (NVLink 10.7 vs 10.8 ms; NET ~105 ms vs 189 ms serial, all builds within ±1.5%).

**Memory** (consumer peak reserved over baseline; `max_memory_allocated` doesn't count blocks held back by `record_stream`):

| scenario | main | this PR |
|---|---|---|
| Immediate load, k buffers | 2k packs | k packs |
| Served OLMoE, NET, 1 GB packs, first sync / later syncs | 4,554 / +0 MB | 4,276 / +0 MB |
| Served OLMoE, NET, per-expert, 128 MB packs | 2,270 MB | 2,404 MB |
| Reproducer (layerwise), NET, 106 MB packs, 2 / 3 buffers | 2,400 / 3,276 MB | 2,764 / 3,384 MB |

Over NVLink the layerwise numbers match `main`.

## Details

- **`record_stream`** on each receive buffer, for every slot stream and the caller's stream, fixes the corruption: the allocator won't reissue a freed block until those streams pass the free. It also covers the buffer's own pending broadcast, so the consumer no longer keeps the previous pack of each slot alive.
- **Event chain** (one event per pack): each pack's callback waits on the previous pack's receive, so callbacks are ordered after all earlier receives. Receives are never delayed, and no callback waits on another callback.
- Each half alone passes only its own test.
- Larger `num_buffers` doesn't avoid the bug: with k buffers, a layer spanning at least k + 2 packs is exposed. The allocator test covers `num_buffers=3`.
- **Alternatives considered:** copying out in the callback (an extra copy of every weight); a host sync per replay (serializes the streams).
- `test_unpack_produces_independent_copies` is replaced by `test_unpack_returns_views`; the old test passed only because the packed buffer aliased the reference tensor.

Good catch, this did show up with the first version. max_memory_allocated looked unchanged, but that metric doesn’t include blocks held back by record_stream, so I measured max_memory_reserved and allocator retries instead.

In the served 1 GB-buffer case, the first version caused 6 allocator retries per sync and made the receive about 3–5% slower. Dropping the slot array fixed that: the current version peaks at 4276 MB reserved vs 4554 MB on main, with no retries after the first sync. 

Layerwise reload over slower transport like NET still uses some extra reserved memory: +364 MB with 2 buffers and +108 MB with 3 in the repro, and +134 MB in the served per-expert run.
