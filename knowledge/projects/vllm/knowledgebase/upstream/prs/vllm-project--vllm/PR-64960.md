# [Perf][Kernel][Attention] Drop reduction in token/request mapping

[Upstream PR](https://github.com/vllm-project/vllm/pull/64960) · state: closed · merged: False

## Original PR description

## Overview

The token-to-request mapping kernel in `vllm/v1/attention/ops/metadata.py` runs a 256-lane binary search. Every loop iteration ends with a cross-warp `tl.sum((lo < hi))` reduction and a barrier to decide whether to continue. This PR replaces the loop condition with a fixed iteration count and unrolls the search. The output is bit-identical.

The kernel builds per-token request indices for sparse MLA (DeepSeek V3.2/V4) and sparse SWA metadata, so it runs on the per-step path.

## Claims

- Kernel time drops **1.37-1.55x** for 32-1024 requests and **1.24-1.32x** for 8 requests on an RTX PRO 4500 Blackwell.
- Output is bit-exact against `torch.searchsorted` in 24 shapes and 85 tests.
- No new host/device synchronization: the iteration count comes from `query_start_loc.shape[0]`.
- The indexer metadata kernel that still uses `_token_request` is unchanged.

## Validation

Hardware: RTX PRO 4500 Blackwell (24 GB, sm_120), driver 595.91.07, torch 2.9.1+cu128, Triton 3.8.0, CUDA 12.8.

Method: 3 s burn-in; CUDA graph with 100 kernel launches per replay, so the reported number is per-kernel time and not host launch overhead; `triton.testing.do_bench` with L2 flush, 100 ms warmup and 300 ms measurement; 3 independent rounds, median of medians. ## Details

Root cause: the loop condition `tl.sum((lo < hi).to(tl.int32), 0) > 0` reduces across all warps on every iteration, which needs shared memory and a barrier. The search needs at most `ceil(log2(num_reqs + 1))` iterations, so the
condition can be replaced by a fixed count.

Fix: compute `ITERS = max(1, num_reqs.bit_length())` on the host and unroll the search with `tl.static_range(ITERS)`. Each lane keeps its own `lo`/`hi` and the `active` guard preserves the original convergence behavior. `num_reqs` stays `do_not_specialize`; only `ITERS` is a compile-time constant, so the kernel has one variant per binary-search depth (at most about 12).

Tradeoff: the old loop could exit before the full depth when all lanes converged early. The new loop always runs the full depth, but removes the per-iteration reduction. The measured result is a win for 8 or more requests; one request is within measurement noise (0.92 vs 0.98 us).

Duplicate check: `token_to_req` and `_token_request` have zero matches in the title or body of 1,500 open vLLM PRs (2026-11-01). No open PR targets this kernel.
