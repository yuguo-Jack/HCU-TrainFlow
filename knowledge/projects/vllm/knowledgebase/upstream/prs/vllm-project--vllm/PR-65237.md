# [Bugfix][KV Offload] Keep lazy SimpleCPUOffload stores at the GPU eviction end

[Upstream PR](https://github.com/vllm-project/vllm/pull/65237) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Lazy SimpleCPUOffload should offload the blocks the allocator will evict next, but two behaviors move it away from them. This PR fixes both: stored blocks go back to the front of the GPU free queue, and every walk starts from the head of the queue instead of a saved cursor.

Includes the two commits of #59383 by @obendidi, rebased onto main with authorship kept, plus the walk change. Builds on #64229.

## Claims

- Lazy stores return GPU blocks to the eviction end (from #59383).
- The lazy walk starts at the head of the free queue on every step, so it no longer offloads blocks far from eviction.
- With sliding-window groups that are not prefix-cacheable (DeepSeek-V4.1) and a contended CPU tier, the walk change is what lowers recomputed blocks; #59383 alone does not help there. The simulation below went from 67.5% to 59.7% recomputed blocks with 32 such blocks per cached block.
- No change to eager mode. Net -3 lines outside tests (+17/-20).

## Validation

Tests, on CPU:

```bash
pytest tests/v1/simple_kv_offload/test_scheduler.py tests/v1/simple_kv_offload/test_kv_events.py tests/v1/kv_connector/unit/test_simple_cpu_offload_connector.py tests/v1/kv_connector/unit/test_simple_cpu_offload_metrics.py
```

Result: 152 passed. `pre-commit` passes on the changed files.

`test_lazy_walk_does_not_offload_past_eviction_window` fails before the walk change: the second walk offloads the blocks past `target_free`. `test_lazy_store_returns_blocks_to_eviction_end` comes from #59383.

Simulation: the real `SimpleCPUOffloadScheduler` and `BlockPool` replaying one multi-turn session trace per row, with only the requests and store completions simulated. Each cell is the share of prompt blocks recomputed, averaged over 2 seeds (lower is better). The CPU tier is 2x the GPU pool and the working set is about 2.7x the CPU tier. SWA blocks are taken from the same free queue and freed on the next step. The 32 row uses twice the pool and half the per-step budget of the others, so that the SWA blocks fit, and runs long enough to reach steady state.

| Uncached SWA blocks per cached block | main | #59383 only | walk from head only | this PR |
|---|---|---|---|---|
| 0 | 74.8% | 55.8% | 74.5% | 55.7% |
| 8 | 64.7% | 66.5% | 60.0% | 57.6% |
| 32 | 67.5% | 70.5% | 62.6% | 59.7% |

Per request, #59383 alone also writes 1.8x (8 SWA) to 2.1x (32 SWA) as many blocks to the CPU tier as this PR. When the CPU tier holds the whole working set (8 SWA), all four variants recompute 4.0%.

Not validated:

- No E2E serving run was done for this PR, so these are block-level hit rates and not a throughput measurement. The pool sizes and session shape are assumptions.
- `tests/v1/simple_kv_offload/test_integration.py` has no passing result: its 2 non-optional tests need a GPU. They failed at engine startup on a GPU without enough free memory, and also fail without a GPU, as `test_chunked_local_partial_gpu_hit` does on main. They need a run in CI or on a free GPU.

## Details

Root cause: the cursor is only reset when its block leaves the free queue. Uncached SWA blocks are freed to the front of the queue and reused there, so the block under the cursor is often neither stored nor reallocated, and the walk resumes past it. In the simulation with SWA groups, about 99% of walks with only #59383 applied resumed from the cursor, against 72% without SWA. The walk then misses the blocks #59383 returned to the front and keeps offloading fresher blocks, which turns over the CPU tier.

Why not just #59383: it is sufficient without such groups (first row), but on DeepSeek-V4.1-style configurations it needs the walk change. The two are combined here so they can be reviewed and merged together. If #59383 merges first, this PR reduces to the walk commit.

Tradeoffs: a walk now revisits blocks already on CPU near the head, but it is still bounded by `target_free`, the same bound as before. One simulated case favors #59383 alone: without SWA groups and with an 8-step store latency, it recomputes 67.2% against 70.8% here. With 8 SWA blocks and the same latency, this PR is better (65.6% against 58.7%).
