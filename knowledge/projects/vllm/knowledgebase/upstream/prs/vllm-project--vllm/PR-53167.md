# [Bugfix] hadacore: issue cp.async.wait_group on the partial-chunk warp

[Upstream PR](https://github.com/vllm-project/vllm/pull/53167) · state: open · merged: False

## Original PR description

## Fixes #53086, fixes #57014

The nibble ordering and zero-point packing named in the issue are both fine. The defect is a layer down, in `hadacore_transform`, which `single_rht` calls on the INT4 write path.

### The bug

`hadamard_transform_kernel` hands each warp two 256-element chunks. When the chunk count is odd the last warp gets one, and takes a separate code path:

```cpp
int64_t diff_num_chunks = real_num_chunks - num_chunks;   // 1 - 2 = -1
```

Used as `switch(k + diff_num_chunks)` over cases `0..31`, with no `default:`. Nothing matches, so no `cp.async.wait_group` runs and the warp reads shared memory before its copy arrives. A full warp gets `2 - 2 = 0` and lands on the right case regardless, which is why this survived until a warp came up short.

The prefetch loop always issues `num_chunks` copies, so the same warp also fetches 512 bytes past the end of the tensor. Stores were already guarded, so nothing was written out of bounds.

### The fix

- `llabs` on the delta, so the index is never negative. Not `abs`, which binds to the `int` overload and truncates an `int64_t`.
- A `default:` arm issuing `wait_group 0`. An unmatched index must not silently skip a barrier.
- The `k >= real_num_chunks` guard the consumer loop already uses, applied to the prefetch loop.

### Why these shapes

`reshape_and_cache_int4` runs the RHT over `[num_tokens, num_kv_heads, head_size]`. An odd `num_tokens * num_kv_heads * head_size / 256` is what reaches the broken path, and that picks out exactly the three failing cases of the 18 (INT8 and FP8 skip the RHT).

### Tests

I ran the file on an sm_89 card and got 25 passed. To exercise the kernel on its own I compiled it standalone with a `default:` arm that records whether the switch matched anything. Before the fix it matched nothing on every odd chunk count; afterwards it matches every time. memcheck on 28x64 went from 33 errors to zero.

### What CI needs to check

The added case does not discriminate on sm_89: the old kernel returns correct results here even at 4097 blocks with dense input, so it passes with and without the fix on my hardware. Requesting an sm_90 run to confirm the wrong-value path.

### Housekeeping

Not a duplicate. #43462 (merged 22 Sep) fixed the wrapper at line 796, and #33589 (still open) is the ABI migration. This fix is inside the kernel, at lines 121, 136 and 358.

Upstream `meta-pytorch/applied-ai` has both defects, so a resync reintroduces them. Happy to send the fix there.

- he-yufeng · comment · 2026-09-15T21:25:53Z · [source](https://github.com/vllm-project/vllm/pull/53167#issuecomment-5688311554)

Independent mechanism check of this fix against current main, since it has sat for a month and #57014 just reported the same race end to end with a kernel-level repro.

The `llabs` form is correct under both commit models. With the new prefetch guard, the tail warp commits exactly `real_num_chunks` groups; at read `k`, `case (k + num_chunks - real)` then issues `wait_group(num_chunks - (k + num_chunks - real) - 1) = wait_group(real - k - 1)`, which is precisely "groups 0..k landed" for a real-only commit. For a full warp (`diff = 0`) it collapses back to the original `wait_group(num_chunks - k - 1)`. The `default: wait_group 0` makes any residual index shape fail safe rather than skip the barrier, so the negative-index path from the original report is unreachable in either direction.

Worth calling out separately: the prefetch guard (`k >= real_num_chunks: break`) is not just hygiene. The old loop committed `cp.async` for `num_chunks` groups unconditionally, so the tail warp's dummy groups read past the end of the input tensor on the global side, independent of the shared-memory race. That is a second real bug fixed in the same diff.

And the coverage check against #57014's exact report: the race fires for `rows % 8 in 1..4` with `rows > 8192`, which is exactly the partial-chunk-warp shape this PR's new parametrized test exercises (odd 256-element chunk count, one case per hadamard size). If the maintainers want the end-to-end evidence, #57014 has a standalone kernel repro and int4 KV-cache logprobs showing 3 distinct outputs at those row counts; the fix here addresses all of them. This is complete and correct as far as I can verify statically; it deserves a review.

So the wrong-value path is confirmed on sm_90, and the fix holds on both architectures with no measurable latency change.

**About the new test.** The four odd-chunk shapes in `test_hadacore_partial_chunk` are 2 to 6 blocks, so the copy almost always lands before the tail warp reads. Driven harder than the test does (random input, NaN-poisoned smem, 200 launches) they never fail on sm_89, and on sm_90 only 42x64 fails, about once in 200. As written the test is flaky-on-Hopper rather than a regression test. One more case with enough blocks in flight does discriminate: `(8193, 64)` (1 MB, 1025 blocks) fails on `main` 200/200 on the 4090 and 198/200 on the H100, and passes with the fix. `eye()[:num_rows]` cannot produce that many rows, so the case needs random input and a tolerance:

```python
def test_hadacore_partial_chunk_large(dtype=torch.bfloat16, device="cuda"):
    """Odd chunk count with enough blocks in flight that the tail warp's
    skipped wait actually loses the race (#57014); the small shapes above
    rarely do."""
    num_rows, hidden_dim = 8193, 64
    torch.manual_seed(0)
    x = torch.randn(num_rows, hidden_dim, dtype=dtype, device=device)
    hadamard = deterministic_hadamard_matrix(
        hidden_dim, dtype=torch.float64, device=device
    ) / math.sqrt(hidden_dim)

    y = ops.hadacore_transform(x.clone())
    y_true = (x.to(hadamard.dtype) @ hadamard.T).to(dtype)
    torch.testing.assert_close(y, y_true, atol=0.1, rtol=0.02)
```

The tolerance has margin on purpose: the failure mode is NaN or errors above 1 in the last `rows % 8` rows, not rounding drift. Two caveats. My harness poisons shared memory before each run; I did not measure the failure rate without that, but the stale rows then hold the previous launch's bytes, as in #57014, so the reference comparison should still catch them. And the other instantiations fail less reliably per launch on `main` here (`(4097, 256)` 140/200 and 142/200; `(16385, 32)` 51/200 and 162/200; `(8193, 128)` 133/200 and 26/200, 4090 and H100 respectively), so covering them would take a few repeated launches per shape. Happy to push this as a commit on your branch if you prefer.

**Side note, not this PR's problem:** the 620 hazards used as the baseline above come from the *unmasked* kernel instantiation as well, identically on `main` and this PR and on both cards: a lane reads smem that another lane's `cp.async` wrote, after `wait_group` but with no `__syncwarp`. Warp-synchronous execution makes it benign in practice. I have not chased it further and mention it only so the 748 vs 620 comparison is readable.
