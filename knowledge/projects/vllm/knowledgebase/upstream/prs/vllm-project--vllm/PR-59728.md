# [MoE] Overlap the runner-held gate with the routed input transform on the aux stream

[Upstream PR](https://github.com/vllm-project/vllm/pull/59728) · state: closed · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

When `MoERunner` holds the gate and has a `routed_input_transform` (e.g. the latent projection of latent MoE), apply the transform inside the MoE op and run the gate on the aux stream the runner already uses for shared experts, so the two overlap. Nemotron-H passes its gate to the runner. Reworked after review: no model-specific custom op, hook or env var. Related: #46077.

## Claims

- For any model whose runner holds the gate and has a routed input transform, the gate GEMM runs concurrently with the transform instead of before it; the gate reads the pre-transform input.
- Nemotron-H (latent MoE): MoE layer output and router logits bitwise identical to the current compiled path at 1-256 tokens, eagerly and under CUDA graph replay (unit-tested against a `torch.compile`d stock prologue).
- End to end on Nemotron-H with MTP, TP4 on 4x B200: about -2.3 % time per verify iteration (mean of 2 interleaved pairs, -1.5 % to -3.0 %) (see Validation).
- Same gating as the shared-experts stream: on by default on CUDA-alike platforms, off with `VLLM_DISABLE_SHARED_EXPERTS_STREAM=1`, inline above `VLLM_SHARED_EXPERTS_STREAM_TOKEN_THRESHOLD` tokens.

## Details

- **Runner:** with a held gate and an input transform, `forward()` passes the pre-transform hidden states into the MoE op and derives the truncation sizes from shapes (the transform's output width is the experts' hidden size); the routed output width is passed to the fake. In `_forward_impl` the gate is launched on the aux stream first (record an event on the current stream, aux waits, gate, record), then the shared experts as before, then the transform and padding on the current stream; the current stream waits on the gate's event before dispatch / routing reads the logits. Events are per DBO micro-batch, as for the shared experts. Callers that pre-apply the transform (passing `shared_experts_input`) keep the old order.
- **Gate input:** the gate reads `shared_experts_input` when set (the pre-transform input), else `hidden_states`. This is the fix from #46077; for models without a transform both are the same tensor.
- **Race-free:** event record / wait only, like the shared experts (graph edges under CUDA graph capture). The logits are allocated on the aux stream and consumed on the current stream after the wait; any later aux-stream work starts by waiting on an event recorded on the current stream after those consumers. The gate's input is an input of the MoE op, so it stays alive until after the join.
- **Exactness (Nemotron-H):** inside the opaque op `GateLinear` picks its GEMM tier per call, so batches of 16 tokens or fewer would use the low-latency bf16 tier. In the compiled model forward the tier branch was traced once at a large batch, so the cuBLAS tier ran at every batch size. Nemotron-H disables the low-latency tier on its gate to keep that GEMM; other models with a runner-held gate already chose the tier at run time and are unchanged.
- **Nemotron-H wiring:** `gate=self.gate` to the runner, placeholder logits as for other runner-held gates; LoRA skips the gate's alias under the runner as it already skips `mixer.gate`.
- **Limitations:** the transform no longer runs in the compiled region when the runner holds the gate, so it cannot be fused by compile passes (it is a separate GEMM either way).

Thanks for the review. Agreed: I've reworked this locally so `MoERunner` owns the gate. When the runner holds the gate and has a `routed_input_transform`, the transform runs inside the MoE op, and the gate is launched first on the shared-experts aux stream on the pre-transform input (the input change you mentioned, similar to #46077). The current stream waits on its event before dispatch/routing; events, per-ubatch handling and gating mirror the shared experts. NemotronH just passes `gate=self.gate`, and the custom op, hook and env vars are gone.

One thing found while doing this: inside the opaque op, `GateLinear` picks its kernel at run time, so at <=16 tokens it uses `ll_bf16_gemm`, while the compiled model forward always used cuBLAS. Router logits therefore differ from before in the last bits at small batch (and the original version of this PR had the same issue, so its "bitwise identical" claim was wrong). I'll decide between keeping the cuBLAS path for exact parity or documenting the difference before pushing. End to end it's about -3 % time per verify iteration (2 interleaved pairs). Updated branch and description coming shortly.
