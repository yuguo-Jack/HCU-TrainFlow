# [Recipe] Kimi-K3.1-Pro: pin Docker images, drop pip, add Rubin VR200

[Upstream PR](https://github.com/vllm-project/vllm/pull/65688) · state: closed · merged: True

## Original PR description



## Overview

Follow-up to #65684. The Kimi-K3.1-Pro recipe named its day-0 images only in an install note, so the builder's commands used `vllm/vllm-openai:nightly` on NVIDIA. This pins the images, hides the pip tab, and adds Vera Rubin (VR200) with its CUDA 13.4 image.

## Claims

| Hardware | Image before | Image after |
|---|---|---|
| GB300, B300 | `vllm/vllm-openai:nightly` | `vllm/vllm-openai:kimi-k31` |
| VR200 (new, `supported`) | not offered | `vllm/vllm-openai:kimi-k31-cu134` |
| MI355X | `vllm/vllm-openai-rocm:kimi-k31` | unchanged, now from `model.docker_image.amd` |
| 810E, M890 | PPU image | unchanged |

- The pip tab is gone on all hardware, because K3.1 isn't in a wheel until #65685 lands.
- The builder no longer offers a CUDA 12.9 toggle for a `kimi-k31-cu129` tag that doesn't exist.

## Validation

Recipe metadata only; no serving-engine code changes, so there are no model evaluation results. **Nothing was run on VR200**, which is why it is `supported` rather than `verified`. CI has no Rubin hardware either.

Run from vllm-project/recipes at `main` (f382387), which has the `vr200` profile:

```bash
node scripts/validate-source.mjs --source vllm --dir <vllm>/recipes
# ✓ vllm recipes from <vllm>/recipes are valid against the renderer
```

- **Before/after diff:** I built the JSON API from `origin/main` and from this branch, then compared every Kimi-K3.1-Pro rendering. On existing hardware the only rendering differences are the image tags above. VR200 adds its own new files.
- **VR200 rendering:** it opens on `multi_node_tp` (TP8 over 2 trays). PD uses 2 prefill and 4 decode trays, the same as GB300.
- **Markdown form:** the `.md` rendering shows no `uv pip` command on GB300, VR200 or MI355X.
- **Docker Hub:** `vllm-openai:kimi-k31` and `kimi-k31-cu134` both publish amd64 and arm64; `vllm-openai-rocm:kimi-k31` publishes amd64.

## Details

- **`min_vllm_version: "0.34.0"`:** this replaces `"nightly"`, which `cu129DockerImage` scores as 0.0.0, so it would derive a `-cu129` tag. 0.34.0 assumes K3.1 ships in the first release after v0.33.0, and `nightly_required` stays set until then.
- **`install: { pip: false }` on `vr200`:** pip is already off for the whole recipe. This override is there to replace the profile's note, which says its own `cu134-nightly` image is the only one that runs on Rubin.
- **Rubin flags:** `rubin` shares the `blackwell` block (`--load-format fastsafetensors` and the 3600 s ready timeout), following #65400. Without it, loading ~1.56 TB could hit the default timeout. It has not been tuned on Rubin, and there is no DCP row on VR200 because DCP sizes list only the GPUs it ran on.
- **Conflict with #65685:** that PR still adds its own older copy of this file. Its rebase should keep the version on `main`, or it will undo this fix.
- **Not a duplicate:** the open-PR searches for `Kimi-K3.1-Pro` and `kimi-k31` find only #65685, which doesn't contain these changes.
