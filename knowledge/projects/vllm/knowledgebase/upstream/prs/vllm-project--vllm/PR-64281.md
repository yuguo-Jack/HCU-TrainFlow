# [Bugfix][Core] Reject negative block counts in FreeKVCacheBlockQueue.popleft_n and BlockPool.get_new_blocks

[Upstream PR](https://github.com/vllm-project/vllm/pull/64281) · state: open · merged: False

## Original PR description



## Overview

Defense-in-depth follow-up to #52707. Reject negative block counts in `FreeKVCacheBlockQueue.popleft_n()` and `BlockPool.get_new_blocks()` before they can corrupt the free-block queue.

## Claims

- A negative count raises `ValueError` before changing queue state.
- Previously, `popleft_n(-1)` increased `num_free_blocks` without removing any blocks. A later allocation could return the fake tail sentinel (`block_id=-1`).
- Valid counts behave as before. The added checks have not been benchmarked.

## Validation

**CPU unit tests (reported from local validation):**

- Without the fix, the three new test cases fail with `DID NOT RAISE ValueError`.
- With the fix, all three pass.
- `test_kv_cache_utils.py` and `test_prefix_caching.py`: **337 passed**.
- `test_single_type_kv_cache_manager.py`: **49 passed**.
- Other applicable CPU unit tests under `tests/v1/core/` passed, except the scheduler case below.
- `test_scheduler.py`: 277 passed, 1 failure (`test_async_scheduling_pp_allows_rescheduling_with_output_placeholders`), reproduced on the unmodified base on this CPU setup.
- Ruff check and format check passed. `git diff --check` passed.

Reproduce the new tests on CPU:

```bash
VLLM_TARGET_DEVICE=cpu .venv/bin/python -m pytest -v \
  tests/v1/core/test_kv_cache_utils.py::test_negative_block_count \
  tests/v1/core/test_prefix_caching.py::test_get_new_blocks_rejects_negative_count
```

**End-to-end validation limitation:** No end-to-end serving reproducer was run. The previously known production call path was fixed in #52707, and no currently known normal caller passes a negative block count. Therefore, this defensive guard is validated with a direct unit-level reproducer rather than a serving workload. GPU-only CI was not run locally (CPU-only setup). The existing Buildkite CPU job selects both changed test files through the `cpu_test` marker.

## Details

In the old implementation, the upper-bound check accepts negative counts. `popleft_n()` then applies `num_free_blocks -= n`, but `range(n)` performs zero iterations for a negative `n`. This makes the free-block count larger than the linked list, which can eventually allocate the fake tail.

#52707 fixed the known speculative over-allocation caller with `max(0, ...)`. This PR adds guards at the two underlying APIs so future callers fail immediately rather than silently corrupting the queue.

**Tradeoffs:** One additional integer check in each function, including a standalone check for direct calls to `popleft_n()`. Performance impact has not been benchmarked.
