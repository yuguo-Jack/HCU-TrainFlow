# [Spec Decode] Batch invariance: build the drafter without batch-invariant kernel selection

[Upstream PR](https://github.com/vllm-project/vllm/pull/62193) · state: open · merged: False

## Original PR description



## Overview

Under `VLLM_BATCH_INVARIANT=1`, builds the EAGLE/MTP drafter without the batch-invariant restriction on MoE kernel selection. Its tokens are only proposals: the target's batch-invariant verification decides every output token and logprob.

This is one self-contained part of #62017 by @aoshen02, split out unchanged for separate review. The commit keeps his authorship.

## Claims

- New `vllm/model_executor/determinism/scope.py`:
  - `batch_invariance_exempt()` is a context manager for building modules that need not be batch invariant.
  - `requires_batch_invariant_kernels()` returns `VLLM_BATCH_INVARIANT and not exempt`.
- `load_eagle_model` builds the drafter inside `batch_invariance_exempt()`.
- The modular MoE experts check (`FusedMoEExperts`) uses `requires_batch_invariant_kernels()` instead of reading `VLLM_BATCH_INVARIANT` directly. A drafter can therefore select MoE experts that are not batch invariant, such as `flashinfer_cutlass`, while the target cannot.
- Nothing changes without BI, and the target model is unaffected. Other BI kernel selections (linear, attention, norms) still read `VLLM_BATCH_INVARIANT` directly, so for them the drafter keeps its current behavior.

## Validation

This PR has no dedicated unit test; #62017 did not include one. The evidence is engine-level:
- B300 (SM103), on the earlier revision aoshen02/vllm#85 `7a0244d0dc`, whose `scope.py`, `load_eagle_model` and modular-kernel changes are the same as here.
- Nemotron-H Lightning NVFP4, `VLLM_BATCH_INVARIANT=1`, MTP with `num_speculative_tokens=3`, and drafter `moe_backend=flashinfer_cutlass`. That backend is not batch invariant, so it is selectable for the drafter only through this exemption.
- Acceptance was 57.9%, by position 77.7 / 54.6 / 41.5%.
- Target tokens and FP32 logprobs are bitwise equal to the non-speculative run in all six phases (alone, batched, reversed order, grouped, and two prefill/decode splits), across two runs.

On this branch, CPU-only:
- every changed module imports;
- `tests/v1/worker/test_spec_decode_embed_sharing_pp.py` and `tests/v1/spec_decode/test_mtp.py` give the same results as on base `fa75d3456d`;
- `pre-commit` mypy (Python 3.11) and ruff pass.

A unit test for the exemption is easy to add if reviewers want one: check `requires_batch_invariant_kernels()` inside and outside the context, and that a non-BI experts class is accepted only inside it.

## Details

- **Scope.** This affects every model that runs BI together with an EAGLE/MTP drafter, not only Nemotron-H. The drafter's MoE layers may now use faster experts that are not batch invariant. Output determinism is unaffected, because verification is batch invariant and decides every accepted token. The acceptance rate can still depend on the batch.
- **Why a context variable instead of a config flag.** The same `get_model` path builds the target and the drafter, and kernel selection happens deep inside layer construction. A context variable scopes the exemption to the drafter build without threading a flag through every layer constructor.

Related open PR: #52522 extends batch invariance to stochastic speculative decoding (RNG streams and scheduling). It does not touch drafter kernel selection.
