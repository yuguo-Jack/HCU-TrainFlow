# [Bugfix][Model] Enable pipeline parallelism for GLM-5.3-Flash (materialize deferred mHC state; load MTP drafter embedding)

[Upstream PR](https://github.com/vllm-project/vllm/pull/57171) · state: closed · merged: False

## Original PR description

## Purpose

Two independent bugs kept GLM-5.3-Flash from running usefully under pipeline parallelism. Both fixes are hardware-agnostic (pure Python model/loader code, no kernels touched).

### 1. Pipeline parallelism was gated off (`vllm/models/glm5next/common/model.py`)

`Glm5NextModel` shipped without `make_empty_intermediate_tensors`, so `supports_pp()` was `False` for `Glm5NextForCausalLM` and `Glm5NextForConditionalGeneration` and `--pipeline-parallel-size > 1` was rejected. The in-tree comments spelled out why: *"PP is gated off for GLM-5.3-Flash (no make_empty_intermediate_tensors)"*.

The obstacle is mHC (manifold-constrained hyper-connections). Each token carries `config.mhc_num_residual_streams` (4) residual streams, and every decoder layer **defers** its `hc_post` mix into the *next* layer's fused post+pre kernel, returning `(x, residual, post, comb)` (`Glm5NextDecoderLayer.forward`). At a stage boundary there is no next layer to fuse with, so the deferred `post`/`comb` had nowhere to go and were simply dropped.

This PR resolves the deferred state at the boundary rather than propagating it:

* `Glm5NextModel.__init__` now installs `make_empty_intermediate_tensors`. For mHC it is the new `_make_empty_mhc_intermediate_tensors`: a single `"hidden_states"` key of shape `(batch, mhc_num_residual_streams, hidden_size)` — the residual streams themselves, token dim leading so the runner's per-batch slicing works. For non-mHC configs it is the standard `make_empty_intermediate_tensors_factory(["hidden_states", "residual"], hidden_size)`.
* `Glm5NextModel.forward` materializes the pending `hc_post` on the **sending** rank, through the last active layer's `hc_post()`, before constructing the `IntermediateTensors`. Only the residual streams cross the boundary. Under sequence parallelism the streams are flattened, all-gathered and reshaped (collectives expect 2-D), mirroring what the last rank already does before its final norm.
* On the **receiving** rank `residual`/`post`/`comb` start as `None`, so its first layer takes the standalone `hc_pre` path — which is exactly the layer-0 path minus `hc_expand` (`layer_idx != 0` there, so no re-expansion).
* `Glm5NextForCausalLM` and `Glm5NextForConditionalGeneration` alias `make_empty_intermediate_tensors` so `supports_pp()` is satisfied. `Glm4vForConditionalGeneration.forward`, which the multimodal class inherits, already passes `intermediate_tensors` through to `language_model.model` and returns them unchanged on non-last ranks.

**Why this is equivalent:** `MHCFusedPostPreOp` is defined as `hc_post` followed by `hc_pre` on the updated streams. Splitting the two halves across a stage boundary computes the same two operations with the same parameters; only the kernel fusion is lost, for one layer per stage.

### 2. MTP drafter ran with an uninitialised embedding under PP (`vllm/models/glm5next/common/mtp.py`)

With PP enabled, MTP accepted **exactly zero** draft tokens. Outputs remained correct (verification is untouched), so MTP was pure overhead. Three things lined up:

* The checkpoint has no `layers.45.embed_tokens`; the MTP input embedding is the target's `model.embed_tokens.weight`.
* `Glm5NextMTP.load_weights` dropped that weight — the name arrives with the `model.language_model.` prefix already stripped, and `get_spec_layer_idx_from_weight_name` returns `None` for it.
* `maybe_share_target_embed` (`vllm/v1/worker/gpu/spec_decode/eagle/utils.py`) early-returns when `pp_world_size > 1` and the drafter does not declare `has_own_embed_tokens`; and on the last PP stage the target's `embed_tokens` is a `PPMissingLayer` anyway, so there is nothing to alias.

`Glm5NextMTP.__init__` now sets `self.has_own_embed_tokens = not get_pp_group().is_first_rank`, and `load_weights` loads `model.embed_tokens.weight` into the drafter's own `VocabParallelEmbedding` when that flag is set. With PP=1 the flag is `False`, the weight is skipped as before, and the target's embedding is aliased — no second copy, no behaviour change.

## Test Plan

* New CPU-only unit test `tests/models/glm5next/test_pp_intermediate_tensors.py` (no GPU, no process group, no weights): `make_empty_intermediate_tensors` keys/shapes/dtypes for mHC and non-mHC, and the `Glm5NextModel.forward` PP branch wiring on first/middle/last ranks with a patched `get_pp_group` and stand-in layers — including that exactly the last active layer's `hc_post` is called at a send, and that `supports_pp()` holds for both model classes.

  ```bash
  pytest tests/models/glm5next/test_pp_intermediate_tensors.py -q
  ```

* Standalone kernel-level comparison of `MHCPreOp` / `MHCPostOp` / `MHCFusedPostPreOp`: fused path vs. the split (post-then-pre) path used at a stage boundary.

* End-to-end serving on 4x NVIDIA CMP 170HX (GA100, sm_80, 64 GB) with `--pipeline-parallel-size 4`, checkpoint `canada-quant/GLM-5.3-Flash-W4A16-MTP`, vLLM `a31ec3a68`:
    * greedy free-form generation, coherence check;
    * GSM8K, first 50 test problems, greedy, chat template, with and without MTP;
    * `SpecDecoding` metrics with `num_speculative_tokens` 1 and 2, eager and CUDA-graph;
    * single-stream 256-token latency with and without MTP.

## Test Result

Unit test: `9 passed`. `ruff format` and `ruff check` clean on the three changed files, along with the `check-spdx-header`, `check-forbidden-imports`, `check-torch-cuda-call`, `check-root-lazy-imports` and `check-boolean-context-manager` pre-commit hooks.

Kernel-level fused-vs-split comparison: **bit-identical** residual streams for token counts > 32 (where the fused op already runs unfused internally); for <= 32 tokens, where the TileLang fused kernel keeps fp32 state, <= 1 bf16 ulp on `x` (max absolute difference 3.1e-2 at |x| ~ 4.7) and ~1e-3 on the mixes.

End-to-end at PP=4:

| | before | after |
|---|---|---|
| PP=4 serving | refused (`supports_pp()` False) | works end to end, coherent greedy output |
| GSM8K (50 problems, greedy, chat) | n/a | **0.98** with MTP and without |
| SpecDecoding, N=1 and N=2, eager and CUDA-graph | `Accepted: 0 tokens, Drafted: 604+` | mean acceptance length **2.45–2.81** |
| per-position acceptance | 0 | **0.85 / 0.60** free-form, **0.95 / 0.86** GSM8K |
| single-stream 256-token generation | ~5.7 s (no MTP) | ~3.3 s (MTP) |

GSM8K accuracy is identical with and without MTP, as expected since speculative verification is unchanged.

**Hardware note:** the end-to-end numbers were measured on sm_80 (CMP 170HX) with an out-of-tree sparse-attention backend for that architecture. **That backend is not part of this PR** and neither fix depends on it — both changes are plain Python in the model definition and the MTP weight loader, with no architecture-specific code, so they apply to any accelerator that can run GLM-5.3-Flash. The PP=4 end-to-end evidence is what the author had hardware for; reviewers with Hopper/Blackwell nodes may want to confirm the same acceptance rates there.
