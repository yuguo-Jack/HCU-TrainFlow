# [Perf][Structured Output] View the token history instead of copying it in the reasoning fallback

[Upstream PR](https://github.com/vllm-project/vllm/pull/60134) · state: open · merged: False

## Original PR description

## Overview

Resolves the TODO in `StructuredOutputManager._get_constraint_start` (added in #48200): the reasoning fallback path copied `request.all_token_ids` on every call just to append draft tokens and pop them off again. It now passes `TokenIdsView`, a read-only `Sequence[int]` over the history plus the drafts, so the per-step cost no longer grows with the length of the reasoning.

## Claims

- For parsers whose `is_reasoning_end_streaming` only looks at the new tokens (the `BaseThinkingReasoningParser` family, e.g. `deepseek_r1`), per-step cost on this path is flat in history length: 160 µs → 4.5 µs at 64k tokens.
- Parsers see the same `input_ids` / `delta_ids` as before on both the draft (`validate_tokens`) and committed paths.

## Validation

Microbenchmark (CPU, Python 3.12): one decode step during reasoning, i.e. the committed check on the 3 tokens just accepted plus `validate_tokens` on 3 new drafts, timed through `StructuredOutputManager` with the real parser classes. History starts with the think-start marker and has no end marker yet. Same script on both branches.

| Parser | History tokens | `main` | this PR |
|---|---|---|---|
| deepseek_r1 | 2,000 | 8.7 µs | **4.5 µs** |
| deepseek_r1 | 16,000 | 35.2 µs | **4.5 µs** |
| deepseek_r1 | 64,000 | 160.5 µs | **4.5 µs** |
| minimax_m3 | 64,000 | 53.6 ms | 88.1 ms |
| minimax_m3 + #56498 | 64,000 | 1.79 ms | **1.38 ms** |

Tests:
```
pytest tests/v1/structured_output/test_structured_output_manager.py tests/v1/structured_output/test_token_ids_view.py tests/v1/structured_output/test_backend_xgrammar.py
# 118 passed, 1 xfailed (with test_backend_xgrammar.py)
```
- `test_fallback_probes_see_history_and_draft_prefixes` records every `(input_ids, delta_ids)` the parser receives and checks them against the copy-and-pop sequence, for the draft and committed paths and two marker positions. It passes on `main` and on this branch.
- `test_token_ids_view_matches_list` checks `len`, indexing (incl. negative), every slice/step combination, iteration, `in` and `index` against the equivalent list.
- `ruff` clean; `mypy` reports no new errors in the touched files.

Not measured end to end: I don't have GPU access for a serving benchmark. The path runs once per structured-output request per decode step while reasoning is in progress, with spec decode enabled, so at 32 concurrent requests and 64k reasoning tokens the copies cost about 5 ms of scheduler time per step on `main`.

## Details

- `TokenIdsView` lives next to `strip_speculative_padding` in `structured_output/utils.py`. Slices inside the history return a list slice of the underlying list, `in` and `index` delegate to the list, and iteration uses `itertools`, so parsers that only read the tail or call `in` stay at C speed.
- It wraps `request._all_token_ids` rather than `request.all_token_ids`: the `ConstantList` wrapper adds a Python frame per access on exactly this path, and the scheduler already reads `_all_token_ids` directly. The committed-path pre-check now gets the raw list too.
- Tradeoff: `minimax_m3` without `thinking_mode` (with it, the parser returns before scanning) scans the whole history by slicing at every position, and each slice now goes through `TokenIdsView.__getitem__`, about 1.6× slower per step. That scan is already O(history) per step; #56498 replaces it with `marker_id in token_ids`, and with #56498 applied this PR is faster for MiniMax as well (table above). Happy to wait for #56498 if you'd rather land them in that order.
- Duplicate check: no open PR touches `_get_constraint_start` or this TODO (searched `_get_constraint_start`, `is_reasoning_end_streaming`, and the structured-output copy).

AI assistance (Claude Code) was used to write the change, tests and benchmark; I reviewed every changed line and ran the tests and benchmarks above.
