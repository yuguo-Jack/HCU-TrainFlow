# [Frontend] Serve Gemma 4 on /v1/systemone and /v1/decisions

[Upstream PR](https://github.com/vllm-project/vllm/pull/62303) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

Serve the Gemma 4 family on `/v1/systemone` and `/v1/decisions` by mapping its architectures to the existing `NextTokenStrategy`. This addresses #62096 with the alternative the issue suggests, adding Gemma 4 to the supported list. A default for every generation model is left to RFC #59365.

```bash
vllm serve google/gemma-4-12B-it
```

## Claims

- `Gemma4ForConditionalGeneration` (E2B, E4B, 26B-A4B, 31B), `Gemma4UnifiedForConditionalGeneration` (12B) and `Gemma4ForCausalLM` (text-only exports) now serve both endpoints. Before this change, both returned 501.
- With thinking off, each Gemma 4 chat template ends where the label is the reply's first token. All 38 labels (A–Z, yes/no, 0–9) are one token there. A CPU test pins both template variants.
- Other generation models stay unsupported. This widens the allowlist and adds no default.

## Validation

**Templates and labels (CPU).** `test_gemma4_labels_start_the_reply` builds `NextTokenStrategy` from the `google/gemma-4-E2B-it` and `google/gemma-4-12B-it` tokenizers. Construction fails unless every label is one distinct token at the start of the reply. The E2B/E4B prompt ends at `<|turn>model\n`. The 12B/26B/31B prompt ends with a closed empty thought, `<|turn>model\n<|channel>thought\n<channel|>`.

**End to end.** I ran main at `3c13653738` with this patch, installed with `VLLM_USE_PRECOMPILED=1`. Each model ran the existing `/v1/systemone` e2e suite (`test_structured_decisions_e2e.py`) with `MODEL_NAME` swapped and `--max-model-len 4096`. Each model also answered the first 200 AG News test rows as a 4-way `choice`, with the article as the state; that sample has about ±6% error at 95%. Before the patch, `vllm serve google/gemma-4-E2B-it` returns 501 on both endpoints.

**Tests.**

```bash
pytest tests/entrypoints/generate/structured_decisions/test_strategies.py
# 55 passed (macOS CPU and L4)
pytest tests/entrypoints/generate/structured_decisions/test_decisions.py tests/entrypoints/generate/structured_decisions/test_question_types.py
# 49 passed
```

Without the `strategies.py` change, `test_strategy_selection` fails with "does not support Gemma4ForCausalLM". A template that leaves `<|channel>thought\n` open still constructs `NextTokenStrategy`, so the test's prompt-ending assertion is what catches that.

**Not covered in CI.** No Gemma 4 checkpoint runs in CI, as in #60676 and #61064. The CPU test downloads two Gemma 4 tokenizers (31 MB each).

## Details

- **Why not a default for every generation model.** Review on #59299 asked that models opt in once their read is known to work, after a DeepSeek-V4.1-Flash read came back wrong. At startup the server only checks that each label is one token after the generation prompt. It cannot tell whether the reply starts with the answer, so a template that opens a thought or a channel returns 200 with noise. RFC #59365 proposes a next-token fallback behind a strategy registry, and this PR leaves that open.
- **Why no new strategy.** Each checkpoint's own template already ends where the answer starts, and it should not be swapped. Serving E2B with the 12B template, whose only difference is the empty thought, drops `argmax_is_label` from 0.77 to 0.00 and AG News accuracy from 0.79 to 0.30.
- **E2B.** Its misses are a preamble, not a thought: in 45 of the 46 non-label reads the top token is `The`. `label_mass` reports this. E4B uses the same template and lands every read on a label.
- **`Gemma4ForCausalLM`.** No Google checkpoint declares it, but text-only exports do. For example, `LilaRest/gemma-4-31B-it-NVFP4-turbo` has 147k downloads, and its template also closes an empty thought. I also checked this architecture by serving E2B with `--hf-overrides '{"architectures": ["Gemma4ForCausalLM"]}'`.
- **Startup.** A Gemma 4 checkpoint without a chat template, such as the base `google/gemma-4-E2B`, fails `NextTokenStrategy` with a `ValueError`. The server still starts, and both endpoints return 501 as before.
- **Speculative decoding.** With MTP, `logprob_token_ids` reads can return 500 when they share a batch with draft requests, until #42592 is fixed (#44727 and #61219 are open). This affects every next-token model, and Gemma 4 is often served with MTP.
- **Media.** `NextTokenStrategy` takes no media yet, so Gemma 4 reads are text-only until #62181.
- **Not a duplicate.** No open PR adds Gemma 4 to `NextTokenStrategy`. I searched for 62096 and for keywords such as `READ_STRATEGIES`, `NextTokenStrategy`, systemone, decisions and gemma. Related PRs:
  - #60713 (Winnow) picks its own strategy from an explicit `decision_read_strategy` override before this lookup, so it still works. Its test asserts that a plain `Gemma4ForCausalLM` is unsupported, so whichever PR lands second updates that line.
  - #61251's splice test would need Gemma 4 entries in `SPLICE_MODELS`.
