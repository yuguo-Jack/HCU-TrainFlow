# [Rust Frontend] Export Mooncake connector transfer metrics like Python

[Upstream PR](https://github.com/vllm-project/vllm/pull/63317) · state: closed · merged: True

## Original PR description

## Overview

vllm-project/vllm#56939 added Prometheus metrics for the P2P `MooncakeConnector`. Under the Rust frontend these stats are dropped: the payload matches no typed `KvConnectorStats` variant, decodes as an unknown-child `Multi`, and records nothing. This PR decodes the payload and exports the six `vllm:mooncake_*` families with Python's names, labels, and buckets.

## Claims

- With a `MooncakeConnector` (bare or as a MultiConnector child), `/metrics` reports `vllm:mooncake_xfer_time_seconds`, `vllm:mooncake_bytes_transferred`, `vllm:mooncake_num_descriptors` (histograms) and `vllm:mooncake_num_failed_transfers`, `vllm:mooncake_num_failed_recvs`, `vllm:mooncake_num_kv_expired_reqs` (counters), labeled `model_name` and `engine`, as Python's `MooncakePromMetrics` does.
- NIXL and Mooncake store metrics are unchanged.

## Validation

- `metrics::tests::mooncake_transfer_stats_are_recorded_into_mooncake_metrics`: a Python-shaped `MooncakeConnector` payload goes through decode and recording; the exposition is snapshotted.
- `metrics::tests::kv_connector_stats_are_recorded_into_mooncake_and_nixl_metrics` (extended): a MultiConnector payload with a `MooncakeConnector` child records into the same families.
- `tests::client::python_msgpack_fixtures_match_rust_encoding`: the Python fixture script now msgpack-encodes a `MooncakeConnector` payload, bare and as a MultiConnector child, and Rust decodes both into the new types.
- With the variant placed after `Multi` (the old decode behavior), the bare-payload and fixture tests fail; without the MultiConnector recording branch, the extended test fails.

## Details

- **Decode** (`engine-core-client` `protocol/stats.rs`): `MooncakeTransferStats` mirrors `MooncakeKVConnectorStats.data` with `deny_unknown_fields`. It is its own `KvConnectorStats` variant, placed before `Multi` (which accepts any map; the enum now documents this order contract), and the `MooncakeConnector` child of `MultiConnectorStats`.
- **Register** (`vllm-metrics` `SchedulerMetrics`): the six families, reusing the NIXL bucket constructors, which match Python's buckets.
- **Record** (`engine-core-client` `metrics.rs`): per engine, next to `record_nixl_stats`.

This is the NIXL path with Mooncake's field set (no `post_duration`; `num_failed_recvs` instead of `num_failed_notifications`), with no new abstraction.

Difference kept: like the existing NIXL families in Rust, the Mooncake series are created for every engine at startup and report `0` when no Mooncake connector is configured; Python registers connector families only for the configured connector.

Not a duplicate: no open PR adds these families to Rust. vllm-project/vllm#60856 (inactive since 2026-10-09) decodes NIXL connector stats in the same files and does not touch Mooncake.
