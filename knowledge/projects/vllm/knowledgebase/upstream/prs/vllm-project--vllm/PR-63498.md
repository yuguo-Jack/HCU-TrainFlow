# [Bugfix][KV Offload][P2P] Exclude rc_gda lanes from the P2P NIXL agent

[Upstream PR](https://github.com/vllm-project/vllm/pull/63498) · state: closed · merged: True

## Original PR description

## Overview

The P2P KV offload tier creates its NIXL UCX backend with UCX's default transports, which include the `rc_gda` GPU device lanes. After a P2P peer stalls or is replaced, connecting those lanes fails, so the peer was not usable again during the observation window (90 s): registering it fails, or its WRITEs stall, and every pull from it falls back to local prefill. This creates the tier's UCX backend with `engine_config="TLS=^rc_gda"`; the tier only moves host memory.

Fixes #63499.

Related: #63207 (the control-plane freeze in the same fault cases; without it the replacement cases freeze before reaching this bug), ai-dynamo/nixl#2437 / ai-dynamo/nixl#2337 (the `NIXL_ERR_INVALID_PARAM` loop that follows the first failed registration).

## Claims

- After a pause, the peer is pulled from again: the first pull succeeded 9-12 s after SIGCONT, and every probe from 40 s after SIGCONT on was pulled. After a replacement, the first pull came 0.3-0.7 s after the switch, and every probe from 10 s after the switch was pulled. Without the change, no pull from that peer completed during the observation window (90 s).
- No change for a healthy fleet, and none when `UCX_TLS` is set: UCX env vars take precedence over `engine_config`.

## Validation

Three single-GPU engines (Qwen3-0.6B, `--enforce-eager -O0`) on 8xH200 nodes with mlx5 InfiniBand: consumer A, source B that the fault hits, healthy source C. `OffloadingConnector` + `TieringOffloadingSpec`, 8 GiB CPU tier, P2P tier over RDMA, NIXL 1.5.0. Both arms run nightly `8e2beaa3b` + #63207 (`478d86b21`); the change is the only difference. A probe seeds a fresh ~2K-token prefix on B or C every 200 ms and asks A to pull it (`kv_transfer_params.remote_kv_source`); "recovered" means A's requests to B (or B2) after recovery were pulled (A logged `request_blocks ... blocks>0` for them).

| fault on B | without this change | with this change |
|---|---|---|
| none | pass 1/1 | pass 1/1 |
| SIGSTOP 60 s, then SIGCONT | no pull in 90 s, 0/3 | recovers, 2/2: first pull 9-12 s after SIGCONT; every probe pulled from SIGCONT + 40 s (p50 0.051-0.057 s) |
| pod deleted gracefully, replacement B2 | no completed pull from B2 in 90 s, 0/3 (35-36 requested per run, none completed) | recovers, 2/2: first pull 0.7 s after the switch; 400/400 from switch + 10 s (p50 0.056-0.057 s) |
| pod force-deleted, replacement B2 | recovers 1/3 (no pull from B2 in 90 s in the other two) | recovers, 2/2: first pull 0.6-0.7 s after the switch; 400/400 from switch + 10 s (p50 0.053-0.058 s) |
| SIGSTOP, B on another node | no pull in 90 s, 0/1 | recovers, 1/1: first pull 10.6 s after SIGCONT; 242/242 from SIGCONT + 40 s |
| graceful replacement, B2 on another node | no pull from B2 in 90 s, 0/2 | recovers, 1/1: first pull 0.3 s after the switch; 400/400 from switch + 10 s |

Across nodes, the graceful replacement fails through registration (`REMOTE_DISCONNECT`, then `INVALID_PARAM`) rather than the WRITE stall seen on one node. With NIXL main + ai-dynamo/nixl#2337 (and UCX v1.23.x) the `INVALID_PARAM` loop is gone, but recovery still fails: registration retries fail with `REMOTE_DISCONNECT` in the pause and force-delete cases, and 35-39 WRITEs stall in the graceful-replacement case. With `UCX_TLS=tcp,self,cuda_copy` all three recover (5/5); with `UCX_TLS=^rc_gda` set in the environment all three recover (3/3), matching this change.

Unit tests (`tests/v1/kv_offload/tiering/p2p`, CPU):

```

311 passed

```

CI cannot reproduce the failure: it needs RDMA NICs, GPUs and a peer fault between two engines. The updated tests only pin the backend configuration.

## Details

With UCX's GPU device API (NIXL sets `UCP_FEATURE_DEVICE`), every UCX endpoint gets `rc_gda` lanes next to its `rc_mlx5` lanes, whether or not GPU memory is ever transferred. UCX debug logs on the consumer for the SIGSTOP case:

1. At t+31 s (B stopped at t+21 s) the P2P session drops B and NIXL closes the endpoint; UCX destroys it after the UD keepalive times out at t+62 s.
2. B resumes at t+81 s and the session re-registers it at t+91 s: the new endpoint connects all eight `rc_mlx5` lanes, then the next lane connect fails:
   ```
   ib_mlx5_dv.c:446  UCX  ERROR   mlx5dv_devx_obj_modify(opcode=0x503) failed, syndrome 0x5d668c: Remote I/O error
   ucp_ep.c:1621 UCX  DEBUG ep 0x...: set_ep_failed status Input/output error
   nixl_agent.cpp:1679] loadRemoteMD: error loading remote metadata for agent '<B>' with status NIXL_ERR_REMOTE_DISCONNECT
   P2PSession <B>: peer registration failed, rejecting peer: NIXL_ERR_REMOTE_DISCONNECT
   ```
3. On NIXL 1.5.0 every later registration of B then fails with `NIXL_ERR_INVALID_PARAM` (ai-dynamo/nixl#2437). With NIXL main + #2337 the retries fail with `REMOTE_DISCONNECT` instead.

In the graceful-replacement case on one node, registration succeeds, but B2's WRITEs to A do not complete during the run and report no error; the stalled transfers pin CPU-tier chunks on both sides until both report `cannot store chunks`, which also drops some pulls from the healthy C (679/847 pulled). Excluding `rc_gda` removes that form as well.

The tier registers and transfers DRAM only, so it never uses the device lanes; dropping them also removes four lanes per endpoint. The change follows the `engine_config` mechanism the NIXL connector uses for its sleep-mode agent. On UCX versions without `rc_gda`, an unknown name in a negated `TLS` list is ignored without a warning. The underlying UCX failure (an `rc_gda` connect rejected after a peer fault) is not addressed here.
