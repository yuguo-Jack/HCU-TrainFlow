# [Bugfix][Elastic EP] Release a prepared reconfiguration when scaling fails

[Upstream PR](https://github.com/vllm-project/vllm/pull/53947) · state: open · merged: False

## Original PR description

A failed prepare or drain leaves `eep_scaling_state` active, so subsequent scales are rejected until the engine restarts.

Release the prepared engine state and standby groups when prepare or drain fails, including external-LB peers waiting for drain completion. Preserve failure handling once the topology commit starts.

## Tests

- Revision `37ce4eae3f`: seven CPU control-path regressions with injected failures passed. The same tests with the current main implementation failed all seven cases. Coverage includes prepare/drain failures, external peer failure, and preserving a committing state.
- `pytest tests/v1/engine/test_async_llm.py::test_elastic_ep_releases_prepared_state_before_commit tests/v1/engine/test_engine_core.py::test_abort_prepared_elastic_ep_preserves_committing_state tests/v1/distributed/test_external_lb_dp.py::test_external_elastic_ep_releases_state_when_peer_drain_fails -q`
- Pre-commit hooks, including mypy, passed for all changed files.

Historical GPU validation, before the current main merge: **2× H200**, DeepSeek-V2-Lite, externally launched DP/EP ranks, TP=1, EPLB enabled. A single-rank scale request reproduced the stuck state; the fix released it and accepted a new reconfiguration. DP2 → DP3 still committed in about 33 seconds. This GPU scenario was not rerun on the current revision.

A failed scale-up still requires recreating the joining rank before retrying because abort tears down its handshake.
