# [CI] Split (H200 MIG 35GB) Mamba Kernels into SSD / Ops / GDN whole-unit jobs

[Upstream PR](https://github.com/vllm-project/vllm/pull/58592) · state: closed · merged: False

## Original PR description

## What

`(H200 MIG 35GB) Mamba Kernels` runs all 943 cases of `tests/kernels/mamba` in one pytest process and measures 36.6–48.7m wall (40.1m median) across 14 recent main builds. This replaces it with four content-named jobs — SSD Single Example, SSD Continuous Batch, Ops, and GDN — each running whole files or whole folders, so the timeline says what ran and every file's per-process setup is paid exactly once per lane. The `(MI250)` mirror splits the same way.

This is the third design iteration, each measured on a scoped build: case-level hash sharding ([90995](https://buildkite.com/vllm/ci/builds/90995)) failed both budgets — per-process kernel setup repeats per shard (summed pytest 67.0m vs 35.9m unsharded). Three file-level jobs ([91011](https://buildkite.com/vllm/ci/builds/91011)) fixed cost (+5.5 worker-minutes) and reconciled coverage exactly, but the single-file SSD job measured 22.8m pytest against the 20m target. This revision extracts that file's parametrized groups into two flat wrappers over a shared helper, splitting SSD into two ~11m units. Both validations are documented in the comments.

## Old

```
kernels-mamba-test   "(H200 MIG 35GB) Mamba Kernels"   35.9m pytest / 36.9m wall (build 90947)
└── pytest -v -s kernels/mamba        tests/kernels/mamba/  (17 test files + cpu/, flat)
mirror: amd-kernels-mamba-test   "(MI250) Mamba Kernels"   23.9m pytest / 25.4m wall
```

## New

```

├── ssd/
│   ├── _mamba_ssm_ssd.py                                   (new: shared helpers, never collected)
│   ├── single_example/test_mamba_ssm_ssd_single_example.py (test_mamba_chunk_scan_single_example, 48 cases)
│   └── cont_batch/test_mamba_ssm_ssd_cont_batch.py         (both continuous-batch tests, 46 cases)
├── gdn/        (new folder: 6 GDN test files, mirrors vllm/.../mamba/gdn/)
├── ops/        (new folder: 10 files, mirrors vllm/.../mamba/ops/)
├── cpu/        (unchanged, CPU lane)
└── utils.py    (unchanged helper, imported by absolute path)

kernels-mamba-ssd-single-example   "(H200 MIG 35GB) Mamba SSD Single Example"     pytest kernels/mamba/ssd/single_example
kernels-mamba-ssd-cont-batch       "(H200 MIG 35GB) Mamba SSD Continuous Batch"   pytest kernels/mamba/ssd/cont_batch
kernels-mamba-ops-test             "(H200 MIG 35GB) Mamba Ops Kernels"            pytest kernels/mamba/ops
kernels-mamba-gdn-test             "(H200 MIG 35GB) Mamba GDN Kernels"            pytest kernels/mamba/gdn

each with its own mirror:  amd-<key>  "(MI250) Mamba ..."
```

Original file → wrappers: `test_mamba_ssm_ssd.py::test_mamba_chunk_scan_single_example` → `ssd/single_example/test_mamba_ssm_ssd_single_example.py`; `::test_mamba_chunk_scan_cont_batch` and `::test_mamba_chunk_scan_cont_batch_prefill_chunking` → `ssd/cont_batch/test_mamba_ssm_ssd_cont_batch.py`; `segsum` / `ssd_minimal_discrete` / `generate_random_inputs` / `generate_continuous_batched_examples` → `ssd/_mamba_ssm_ssd.py`. Bodies are verbatim; a static diff confirms every non-import line is unchanged, and 48 + 42 + 4 = 94 matches the measured case count.

Old → new keys: `kernels-mamba-test` → the four keys above (union of their coverage equals the old job's; the retired key has no other consumers). The legacy optional `:amd: (MI300) Mamba Kernels` step in `.buildkite/test-amd.yaml` is a separately rendered pipeline, untouched — its whole-directory command still collects everything.

## Expected runtime and overhead

Predictions from measured per-function timings in the build 91011 SSD job log (single-example span 7.7m over a partial capture, ~11–12m with all 48 cases; cont-batch ~10–11m) and measured per-file timings from builds 90947/90995:

| job | pytest (est.) | running wall (est.) | non-pytest overhead (est.) | main overhead cause |
| --- | ---: | ---: | ---: | --- |
| Mamba SSD Single Example | ~11–12m | ~13.5m | ~1.5m | container setup |
| Mamba SSD Continuous Batch | ~10–11m | ~12.5m | ~1.5m | container setup |
| Mamba Ops Kernels | ~14.1m (measured, build 91011) | ~15.2m (measured) | ~1.1m | container setup |
| Mamba GDN Kernels | ~1.8m (measured) | ~2.9m (measured) | ~1.1m | container setup |
| MI250 SSD x2 / Ops / GDN | ~8m each / 6.6m / 1.5m | ~9.5m each / 8.3m / 3.3m | ~1.7m each | container setup |

- **Slowest job ~14.1m pytest (Ops, measured); SSD halves estimate to ~11–12m.** All well inside the 20m target.
- **Aggregate:** base lane ~44.6 worker-minutes vs 36.9 before (**~+7.7 vs the ≤20 budget**); mirror ~30.1 vs 25.4 (**~+4.7**). The increase over the v2 estimates is one more repeated container setup for the second SSD job.
- Coverage equivalence: moved files are `git mv` (path-prefix-only node ID changes); the SSD split is body-verbatim extraction (static diff-checked). Every previously-run case is under exactly one new command.

## Notes

- **Why not hash-shard:** measured, not hypothetical — per-file fleet-cold vs warm inflation (SSD 94 cases: ~18m → 33m across 3 shards; `test_memcpy_u64_tiled.py` 120 cases: 1.8m → 13.9m). Details in the first validation comment.
- **Grouping is by content, not duration:** `gdn/` and `ops/` mirror `vllm/model_executor/layers/mamba/{gdn,ops}`; the SSD wrappers split along the file's own test-function boundary (single-example vs continuous-batch), each in its own `ssd/` subdirectory so every job runs a directory. The GDN job's root sweep runs any test file added at the `kernels/mamba` root.
- **Other path updates:** `.buildkite/hardware_tests/cpu.yaml`, `run-cpu-test-arm.sh` and the `(B200) Kernels` job point at the moved `ops/` and `gdn/` files.
- The Ops job is now the slowest at a measured 14.1m; if it grows past target it hash-shards cleanly as a directory (`ops/` has 10 files, ~800 cases) without the per-file setup penalty this directory showed at case level — that was the failed experiment, noted only to explain why Ops stays one job today.

## Validation — build [90995](https://buildkite.com/vllm/ci/builds/90995) @ 99187ac (fails both budgets; rework planned)

Scoped build with `kernels-mamba-test` + `amd-kernels-mamba-test`. All 5 replicas passed, and coverage reconciles exactly against the unsharded baseline (908 = 301+308+299 passed on the base lane; 707 = 368+339 on the mirror). Checkout confirmed at the PR head on every replica. But the measurements falsify the PR's predictions:

| job | pytest | running wall | non-pytest overhead | main overhead cause |
| --- | ---: | ---: | ---: | --- |
| Base lane shard 1 | 21.4m | 22.6m | 1.2m | checkout + container setup |
| Base lane shard 2 | 22.4m | 24.0m | 1.6m | checkout + container setup |
| Base lane shard 3 | 23.2m | 24.5m | 1.3m | checkout + container setup |
| Mirror shard 1 | 20.2m | 21.7m | 1.5m | checkout + container setup |
| Mirror shard 2 | 21.3m | 23.2m | 1.9m | checkout + container setup |

**Runtime verdict: FAIL.** Slowest shard 23.2m pytest (predicted ~12m) vs the 20m target; the mirror's slowest is 21.3m.

**Cost verdict: FAIL on the base lane.** The shards sum to 67.0m pytest against a 35.9m unsharded baseline: 71.1 worker-minutes vs 36.9 before → **+34.2, over the ≤20 budget** (mirror: 44.9 vs 25.4 → +19.5, barely inside). I predicted "pytest total is unchanged" and that was wrong.

**Cause.** Hash-sharding by case scatters each file's cases across three pytest processes, and this directory has large per-process/per-file warm-up that the unsharded single process pays once. Measured per-file, warm (baseline) → fleet-cold (sum across the 3 shards):

| file | cases | warm | fleet-cold (3 shards) |
| --- | ---: | ---: | ---: |
| test_mamba_ssm_ssd.py | 94 | ~17–19m | 33.0m |
| test_memcpy_u64_tiled.py | 120 | ~1.8m | 13.9m |
| test_replayssm_standard_decode_mamba2.py | 117 | ~3.1m | 6.0m |
| (all others) | ~600 | ~13m | ~13.5m |

So the inflation is not container overhead (stays ~1–2m per replica) — it is repeated kernel setup/compile and lost in-process cache reuse inside pytest. No shard count fixes this: at N=2 the slowest shard gets slower (~28m), at N=4 the aggregate cost roughly doubles again.

**Rework.** I'm converting this PR from case-level hash sharding to file-level named jobs, so every file's setup is paid exactly once per lane: the dominant `test_mamba_ssm_ssd.py` (~17–19m warm, under target as a singleton) becomes its own named job, and the remaining 13 files move into `gdn/` and `ops/` folders mirroring `vllm/model_executor/layers/mamba/{gdn,ops}` behind two more named jobs. Predicted aggregate stays within a few worker-minutes of the 36.9m baseline; a fresh validation build will follow on the new head.
