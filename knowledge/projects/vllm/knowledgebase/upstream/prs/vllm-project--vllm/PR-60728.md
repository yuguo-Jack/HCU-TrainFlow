# [Frontend] Add return_mm_kwargs to render requests

[Upstream PR](https://github.com/vllm-project/vllm/pull/60728) · state: closed · merged: True

## Original PR description



## Overview

Add `return_mm_kwargs` to render requests. When false, the render response leaves out the processed multimodal tensors (`kwargs_data`) and `mm_metadata`, for callers that need only token ids, item hashes and placeholder ranges, such as cache-aware routers. Part of #46722.

## Claims

- `return_mm_kwargs: false` on the chat, completions, Messages and Responses render endpoints returns `kwargs_data` and `mm_metadata` as null. Token ids, `mm_hashes` and `mm_placeholders` are unchanged. The default (`true`) keeps current behavior.
- For four 1080p images the response drops from 66.91 MB to 0.058 MB, and render time from 166-189 ms to 38 ms with a warm processor cache, or from 194 to 74 ms cold.
- Tensor serialization no longer holds the API server's event loop: `/health` p99 during back-to-back renders goes from 114.5 to 2.0 ms.

## Validation

`pytest tests/entrypoints/scale_out/token_in_token_out/test_mm_serde.py tests/entrypoints/scale_out/token_in_token_out/test_protocol.py`: 45 passed, including the new `test_extract_without_kwargs_keeps_layout`.

End to end on this head: `vllm launch render Qwen/Qwen3-VL-8B-Instruct` on CPU (M4 Pro, `OMP_NUM_THREADS=1`), four 1920x1080 PNGs by URL, median of 3 after a warm-up:

| Endpoint | Default | `return_mm_kwargs: false` | Token ids, hashes, placeholders equal |
| --- | --- | --- | --- |
| chat | 166.0 ms, 66.91 MB | 37.9 ms, 0.058 MB | yes |
| Messages | 172.2 ms, 66.91 MB | 38.1 ms, 0.058 MB | yes |
| Responses | 188.9 ms, 66.91 MB | 37.5 ms, 0.058 MB | yes |

Measured with the same change on main `1afb029839`, processor cache off (`--mm-processor-cache-gb 0`): render 193.9 to 73.6 ms. The time removed is `json.dumps` of the response (102 ms) and msgpack plus base64 (4.8 ms), both on the event loop, plus 14 ms of transfer. With renders back to back, `/health` p99 goes from 114.5 to 2.0 ms and max from 117.4 to 4.1 ms.

On GPUs: 2 x H100 serving Qwen3-VL-8B (nightly `81198e97` with this change laid over the installed package) behind llm-d-router with llm-d/llm-d-router#3273, closed loop, four 1080p images by URL per request, 60 s per step, flag off, on, off. At 16 concurrent clients throughput went from 2.6 to 8.3 req/s, client p95 from 15.2 to 3.0 s, and engine `/health` p99 from 1,177 to 11 ms. With the flag on, the router's predicted cached tokens equal the engine's cached tokens (6 of 6 repeats, chat and Messages).

Not run: the GPU `vllm serve` render tests (`tests/entrypoints/scale_out/render/test_render_multimodal.py`). No model eval: the change affects only render responses.

## Details

- Not a duplicate of #53169: its `skip_pixel_values` replaces the tensors with the original image bytes so `/inference/v1/generate` can rebuild them. A router discards those bytes as well (about 33 MB of base64 for the images above). If both land, they could share one field with three values: tensors, source bytes, none.
- Independent of #58660, which makes serialization cheaper for callers that need the tensors.
- A response rendered with the flag must not be sent to `/inference/v1/generate`, which reads a null `kwargs_data` as every item being cached. The field description and `renderer.md` say so.
- Render still runs the multimodal processor; moving it out is the open question in #46722 and out of scope here.
- Messages render converts the request to a chat request, so the handler copies the field across.
