# [ROCm][Qwen3.8-Flash-Next] mxfp4_qsa main KV cache for the AMD QSA path: format, writer and portable reader

## Purpose

This PR adds `--kv-cache-dtype mxfp4_qsa` for Qwen3.8-Flash-Next QSA main attention on ROCm gfx950 (MI355X). Main K and V are stored as OCP MXFP4: E2M1 codes and E8M0 scales, with a group size of 32. For head_dim 256 a (token, KV head) record takes 272 bytes, versus 512 for FP8, so each GPU holds about 1.9x more main-attention tokens. The indexer cache is unchanged and stays BF16 or FP8 as in #61529.

### Format and layout

- **Quantization:** scale = `ceil_pow2(absmax / 6)`, E8M0-clamped to [1, 254]; an all-zero group gets 127. E2M1 rounds to nearest-even. Rows are packed low nibble first, as in #60321. The quantizer duplicates #60321's `mxfp4_mla` helpers (same scale rule and rounding); once #60321 merges, this PR will import them instead.
- **Block-split layout:** inside each KV block of R = tokens x heads records, the regions are K data `[R, 128]`, V data `[R, 128]`, K scales `[R, 8]` and V scales `[R, 8]`. Every K or V row is therefore one aligned 128-byte line for the split-K gather. Both token-major and head-major blocks are supported, as are padded block strides. vLLM sees an opaque uint8 view `[blocks, tokens, heads, 272]`, sized through `AttentionSpec.state_content_bytes`.
- `mxfp4_qsa` reports `KVQuantMode.NONE`: the QSA backend owns every read and write of this cache, so no generic quantized-KV path (query quantization, quantized cache views, per-mode workspaces) applies, and no per-tensor scales are used.

### Changes

- `vllm/models/<model-pkg>/amd/ops/mxfp4_kv.py` (new): the layout helpers, Triton quantize/dequantize helpers, and the standalone cache writer used by `do_kv_cache_update`.
- `ops/qsa_prepare.py`: the fused prepare kernel writes MXFP4 main K (after QK-norm and RoPE) and V directly.
- `ops/qsa.py`: the split-K sparse reader loads packed K/V plus scales and decodes them to BF16 with a portable Triton decoder; QK and PV run in BF16. The gfx950 fast path is in #64405.
  - Both kernels take an explicit `is_mxfp4` flag from the layer's `kv_cache_dtype` rather than inferring MXFP4 from a uint8 cache, since other KV dtypes use uint8 storage too.
- `amd/qsa.py`: accepts `mxfp4_qsa`, sizes the spec, and routes the cache update and forward.
- `vllm/platforms/rocm_kv_cache_dtypes.py` (new): registers `mxfp4_qsa` through `register_kv_cache_dtype` / `KVCacheDTypeHandler` (uint8 storage, `KVQuantMode.NONE`). No core dtype tables change. `RocmPlatform.pre_register_and_update` imports it before `CacheConfig` validates the dtype, so the platform never imports model code; the QSA module imports it too, so every worker registers it.
- The hybrid block-size alignment gets the MXFP4 page from the QSA backend's `customize_spec`, which keys on the configured cache dtype string (and a uint8 layer spec), not on the quant mode. `platforms/interface.py` is unchanged.

`<model-pkg>` is the model's package directory on vLLM main.

## Test Plan

Run on MI355X (gfx950) in `dlimpus/vllm-openai-rocm:main-af4db2a67` (main `af4db2a67`, no QSA-relevant `csrc/` change since), with this branch's Python sources overlaid.

```
pytest tests/models/<model-pkg>/test_qsa_mxfp4_amd.py \
       tests/models/<model-pkg>/test_qsa_prepare_amd.py \
       tests/models/<model-pkg>/test_qsa_amd.py
pytest tests/models/<model-pkg>
```

- `test_qsa_mxfp4_amd.py` (new):
  - The writer is checked **bitwise** against a torch reference, for 1 and 2 heads and for token- and head-major blocks. The check covers outliers, zero groups, tiny negatives, exact 6.0, skipped slots, and untouched inter-block padding.
  - The split-K reader is compared with an fp32 attention over the dequantized cache, for TP1/TP2 decode, split and prefill shapes, and ragged `-1` selections.
  - The ROCm platform hook registers the dtype (torch dtype, quant mode `NONE`, `CacheConfig` validation).
  - `customize_spec` gives `mxfp4_qsa` layers the 272-byte record, while `mxfp4_qsa` configs' model-dtype layers, `fp8` and `auto` keep their own record sizes.
  - The platform's padded hybrid page equals the page the layer publishes, for `mxfp4_qsa`, `fp8` and `auto`.
  - Wired into both AMD Buildkite steps (MI355 mirror and MI300).
- `test_qsa_prepare_amd.py`: the fused-prepare test gains an `mxfp4_qsa` main-KV arm.
  - V must match the standalone writer bitwise.
  - K may differ from the unfused path by at most 1 bf16 ulp from RoPE, so it is checked by code-agreement rate and by an error bound of peak x (1/5 + 2^-7) against the reference.

## Capacity and speed

**KV capacity:** 14.36M tokens for FP8 versus 21.74M for MXFP4 (+51%), which is 110 versus 166 concurrent 128K-token requests.

This PR is the capacity step. Its portable reader is slower than FP8 in the split-K kernel (309 µs against 138 µs at 256 rows, TP2 decode shape); the gfx950 fast path in #64405 makes MXFP4 1.18x–1.45x faster than FP8 from 16 rows up, and carries the kernel table and the serving A/B.

## MXFP4 routed experts (not part of this PR)

Quantizing the routed experts to MXFP4 online is a separate serving recommendation with its own A/B; it is kept out of this description. Its paired McNemar results (FP8 KV in both arms) are the **experts** gate, not a KV gate. The KV-format accuracy gate is still pending (below).
