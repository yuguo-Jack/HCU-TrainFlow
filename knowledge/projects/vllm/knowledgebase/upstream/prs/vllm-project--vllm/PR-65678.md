# [CPU] Support heterogeneous memory (DDR + HBM) NUMA nodes via hwloc

[Upstream PR](https://github.com/vllm-project/vllm/pull/65678) · state: open · merged: False

## Original PR description

## Purpose
Follow up to #65677,  On CPUs with heterogeneous memory, vLLM currently recognizes only one NUMA node per CPU core, which can be selected with `VLLM_CPU_OMP_THREADS_BIND`. On CPUs configured with SNC4 (sub-NUMA clustering) and containing two memory tiers DDR and HBM (Intel Xeon Max, SiPearl's Rhea1), the DDR nodes are attached to CPU cores, while the HBM nodes are CPU-less and have no cores assigned. `lscpu` does not report this layout, so it is only visible through `lstopo`/`hwloc-ls`. As a result, vLLM CPU workers cannot be placed on HBM memory nodes, and users cannot benefit from the higher memory bandwidth of HBM.

This PR adds an hwloc-based topology path that:

- parses `hwloc-ls --of xml` and maps each core to every NUMA node attached to it, including CPU-less HBM nodes, instead of a single node per core
- lets users assign their own memory nodes to each vLLM CPU worker via `<CPU_VISIBLE_MEMORY_NODE>`, including HBM nodes
- falls back to the existing `lscpu` path, which stays the default. hwloc is used only when the env var is set and `hwloc-ls` is installed, so there is no behavior change otherwise
- works with `VLLM_CPU_OMP_THREADS_BIND` set to either `auto` or explicit core lists
- picks an alternative memory node for a core when its default node is not in the allowed set, and stores the chosen node on the worker. Memory availability checks, error messages and KV cache sizing now use the node actually selected rather than the core's default node

`hwloc-ls` becomes an optional dependency, needed only for this feature.

## Test Plan

- Manual runs on <CPU model> with <SNC mode>, DDR + HBM, covering:
  - `VLLM_CPU_OMP_THREADS_BIND=auto` with HBM nodes selected
  - Explicit core binding with HBM nodes selected
  - Default behavior without the env var, and without `hwloc-ls` installed
