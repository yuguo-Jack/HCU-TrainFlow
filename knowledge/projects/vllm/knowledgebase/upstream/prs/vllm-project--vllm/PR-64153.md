# [ROCm][Perf][DSv4.1] Mono: batch TP8 K2's X8 copies, load its push's peer bases late

[Upstream PR](https://github.com/vllm-project/vllm/pull/64153) · state: open · merged: False

## Original PR description

### Purpose

#63892 changes the gfx950 TP4 K2 build (target and DSpark draft) in two ways:

- `moe.load_x8_rows_all`: the one-tile X8 / X8R row copies issue every load before the first LDS store.
- `run_ffn(peer_load=...)`: the MoE all-reduce push loads its peer bases right before the down stage's barrier. Before, it held them from the start of the kernel.

#63892 gates both on `tp == 4 and not GFX942`. With TP8 mono decode (#64101), the TP8 K2 build goes through the same code, so this PR widens the gate to TP4 and TP8:

```python
late_peers = tp in (4, 8) and not GFX942
```

It also updates the comment and runs the no-scratch test at TP8. Nothing else changes. gfx942 and TP2 builds are not affected.

**Stacking.** This PR depends on two open PRs, and both must land first:

### Test Plan

1. CPU compile for gfx950 (FlyDSL `COMPILE_ONLY`, image `rocm/mlperf-inference:custom_vllm_custom_2026-10-23-17-30-29`, no devices). I built the `mono/` tree at `6b7a45b73b` (base = #63892 + #64101) and at this PR. That is 72 configurations, each built at both, for 144 builds:
   - K2 at TP2, TP4 and TP8, with 7, 14, 16 and 28 rows, for 5 cases: compress ratio 0, 1 or 2 (no key index), ratio 2 with the key index, and the DSpark draft (128 experts, top-3, SWA 192)
   - K1 at 7 and 28 rows (ratio 2), and draft K1 at 14 rows, at each TP
   - FFN at 7 rows, at each TP

   For each build I recorded VGPRs, spills, LDS and private segment. I hashed the `gpu.binary` blob to compare base and PR, and checked the disassembly for `scratch_` instructions and for load -> `s_waitcnt vmcnt(0)` -> `ds_write` sequences.
2. `test_mono_decode_k2_no_scratch[tp=4,8][tokens=14,16]` (renamed from `test_mono_decode_k2_tp4_no_scratch`). I ran the test body in the same image on CPU with `ray` stubbed, because the `_on_cdna4()` skip needs a GPU.
3. On GPU, run `test_mono_decode_layer_matches_vllm[tp=8]` on MI355X. #64101 adds the TP8 cases and #63892 adds the 14-row ratio-2 step. In CI this runs in #64101's optional mi355_8 step. `test_mono_decode_k2_no_scratch` only compiles, so the existing 4-GPU "Mono Decode Numerics" step also runs its TP8 cases.
4. End to end: the DSv4.1 CI conc-1 recipe at TP8, measuring ms/step, GSM8K and acceptance length.

### Test Result

**1. CPU compile, gfx950.** All 144 builds succeed. No build has spills or scratch, and LDS is unchanged in every build.

- **TP2 and TP4: byte-identical to the base** (48 of 48 configurations: K1, K2, FFN, target and draft).
- **TP8 K1 and FFN: byte-identical** (4 of 4).
- **TP8 K2** (only these 20 configurations change):

| TP8 K2 | rows | VGPRs base -> PR | load->vmcnt(0)->LDS-store sequences base -> PR |
|---|---|---|---|
| target, ratio 0/1/2, with or without index | 7 | 250 -> 237 | 13 -> 2 |
|  | 14 | 242 -> 240 | 13 -> 2 |
|  | 16 | 248-249 -> 240 | 10-12 -> 1 |
|  | 28 | 232 -> 231-232 | 13 -> 11-13 (past 16 rows only the peer-base loads move, as at TP4) |
| draft | 7 / 14 / 16 / 28 | 199 / 167 / 165 / 174 -> 160 / 169 / 175 / 173 | 13 -> 2 / 13 -> 2 / 12 -> 1 / 13 -> 13 |

Unlike TP4 before #63892, the base TP8 K2 does not spill, even though it holds 8 peer bases. So at TP8, any gain from this PR has to come from the batched X8 copies and the late base loads, because there is no spill reload to remove. This PR's gain at TP8 has not been measured on its own. The draft's VGPR count rises by up to 10 at 14 and 16 rows, but stays at 175 or below with no spill. Occupancy does not change: K2 runs 8 waves per CTA (2 per SIMD) and one CTA per CU, because its LDS limits it to one.

As an independent check, I rebuilt three pairs from fresh `git archive` trees: TP4 K2 at 16 rows ratio 2, the TP4 draft at 14 rows, and TP8 K2 at 16 rows ratio 2. The binary hashes match the sweep: the two TP4 pairs are identical, and the TP8 pair differs. TP8 K2 at 16 rows ratio 2 goes from 249 to 240 VGPRs, and its load->vmcnt(0)->store sequences drop from 12 to 1.

**2. No-scratch test:** passes for TP4 and TP8 at 14 and 16 rows. At TP8 it is a guard: the base passes too.

**3. GPU tests:** not run. The GPUs were busy.

**4. Performance.** Measured on 8x MI355X with the local stack (not this branch). Setup: conc-1 microbench, 32k context, synthetic AL 3.87, CI recipe. Nightly `83c078d955` + #63182 #63027 #63367 #63181 #63355 + the local stack.

| TP8 mono | ms/step |
|---|---|
| generic | 4.970 |
| + #63885 #63888 #63890 #63891 + main #63576 | 4.795 |
| + tuned K1 at TP8 + X8R at TP8 (this PR) + seam poll batch | **4.534** |

- conc 2: 5.234 ms/step.
- conc 4, one TP8 server: 7.156 ms/step, TPOT 2.35 ms.
- GSM8K 0.919, AL 3.570. The base gives 0.917-0.923 and 3.565-3.585.
- For reference, TP4 with tuned K1 runs at 4.77 ms/step.

**Not measured:** the TP8 effect of this PR alone. In the measured run, X8R was turned on at TP8 together with tuned K1 at TP8 (#63893 widened) and the seam poll batch. At TP4, X8R alone measured -1.1% at conc 1 and -3.9% at conc 2.

The measured run used the local stack's version of X8R: an env-switched `MonoBuild.x8r` on non-tuned K2 builds, with the same `load_x8_rows_all` and late peer-base loads. It did not use this branch's gate. At TP8 no K2 build is tuned, so both turn on the same builds.
