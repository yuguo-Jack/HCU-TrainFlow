# [Kernel][Attention] Segment sliding windows in split-K; split-K for non-causal speculative rows

[Upstream PR](https://github.com/vllm-project/vllm/pull/61760) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Changes to the split-K (3D) path of the Triton `unified_attention`:

1. **With a pruned sliding window, the segments split the window instead of the whole sequence.**
   - Before, segment `i` covered tiles `[i * tiles_per_segment, (i + 1) * tiles_per_segment)` of `[0, seq_len)`.
   - At long context, most segments therefore fall before the window and return immediately, so the whole window was walked by one or two programs.
   - This applies to every sliding-window model on `TRITON_ATTN` (decode and spec verify).
2. **Non-causal speculative rows take the 3D launch.**
   - Multi-query rows of up to `MAX_3D_QUERY_LEN` tokens already use split-K when causal (#56148). Non-causal rows, i.e. the DFlash drafter's query block, were excluded.
   - The softmax reduction does not depend on the mask, so `reduce_segments` applies unchanged.
3. **Non-causal rows use fewer, fuller segments when the batch is larger.**
   - Each non-causal program carries a whole query block, so at short context a one-tile segment is mostly fixed cost (Q load, partial store, reduction).
   - Non-causal 3D launches therefore require at least `min(next_power_of_2(num_seqs), 8)` tiles per segment.
   - The kernel and `reduce_segments` take this as the same constexpr, so they agree on the segment count.

## Claims

- **Gemma-4-26B-A4B on one MI355X, end to end.** 25 of its 30 layers are sliding window (1024). On ROCm, Gemma-4 is forced to `TRITON_ATTN`, so this is its default path.
  - Output throughput with 16k-token prompts: **+35% at concurrency 1, +28% at c=4, +5% at c=16**.
  - With 4k-token prompts: +11% at c=1.
  - ShareGPT is within the host's noise (−2.9% median; the kernel accounts for at most 0.4%, see below).
  - GSM8K: 0.711 → 0.713.
- **Kernel time, causal sliding-window decode and verify at long context:** 2–9.4× faster for the batches that take split-K, i.e. up to `seq_threshold_3D` (8–16 sequences for these head counts). With the Gemma-4 sliding layer shape, this is 5.2× at B=1 and 2.1× at B=16 with 16k context.
- **DFlash2 drafter attention** (non-causal, window 2048): 4.6× faster at B=1 and 1.55× at B=16 once the context exceeds the window. Every point measured is at least as fast as main.
  - End to end for Qwen3.8-27B + `z-lab/Qwen3.8-27B-DFlash2` (with #61433, which makes ROCm pick `TRITON_ATTN` for the drafter) this is small: the decode step is 1.2–1.5% shorter with 8k prompts, because only the 5 drafter layers use this kernel (measured on nightly 0cbac6cd; not rerun on the current base). An earlier revision of this PR reported +17%/+16% for this setup; that was a single run with `--attention-backend TRITON_ATTN` and is superseded.
- Outputs match the reference (new tests below). Batches above `seq_threshold_3D` stay on the 2D launch and are bit-identical.

Known regression: **causal, context ≤ window: 0.95–0.98×** (up to 1.3 µs; B=2–4 for these shapes, B=4–16 for the Gemma-4 shape above). Here the window covers the whole sequence, and the per-segment tile bounds are identical to main's; I checked this through the bounds helper. The difference is codegen, from two sources:
- **Decode (1 query token), 0.97–0.98× for the Gemma-3-like shape:** the two extra integer divisions of the window split, about 0.3 µs. With the divisions removed (diagnostic build), these points are at 0.99×. I have not root-caused the Gemma-4-shape points (head size 256, 0.95–0.98× at B=8–16).
- **Verify (4 query tokens), 0.95–0.98×:** scheduling of the tile loop. The loop body has the same instructions, but the compiler now allocates 80 VGPRs instead of 88. In the QK^T step it waits for each LDS read before the MFMA that uses it, where main issues four reads first. At B=2–4 there is about one program per CU, so the lost overlap shows. At B=16 the higher occupancy is what makes this PR 1.07–1.10× faster.

What I tried for the verify points:
- Writing the window split in main's `max`/`min` form brings B=2–4 to 0.99–1.00×. It also gives up the B=16 gain (1.07× → 1.00× at ctx 4096) and makes the drafter at B=16, ctx 512 0.97×.
- `waves_per_eu` 4, 5 or 6 on the 3D launch is slower almost everywhere, and spills at head size 256.
- Falling back to main's bounds at run time when the window prunes nothing (`if tile_start > 0`) gave 0.92× at B=16, ctx 4096.

So I left it as is.

"""Sliding-window attention: main (ua_base/) vs rocm-noncausal-swa-3d (ua_src/).

Default config is the DFlash2 drafter (non-causal 8-token block, SWA 2048).
Env: CAUSAL=1 QLEN=1 H=32 KVH=16 D=128 SW=1024 BS=16 for causal SWA decode.
Kernel time is from a HIP graph of 20 calls (Triton's ~20 us Python launch
would otherwise hide these small kernels).
"""
import importlib.util
import math
import os
import sys

import torch
from triton.testing import do_bench

HERE = os.path.dirname(os.path.abspath(__file__))
E = lambda k, d: int(os.environ.get(k, d))  # noqa: E731
H, KVH, D, QLEN, SW = E("H", 32), E("KVH", 8), E("D", 128), E("QLEN", 8), E("SW", 2048)
BS, CAUSAL, NSEG = E("BS", 832), bool(E("CAUSAL", 0)), E("NSEG", 16)

def load(name, path):
    spec = importlib.util.spec_from_loader(name, loader=None)
    mod = importlib.util.module_from_spec(spec)
    mod.__file__ = path  # triton needs a real file for inspect
    sys.modules[name] = mod
    exec(compile(open(path).read(), path, "exec"), mod.__dict__)
    return mod

def load_ua(tag, src):
    # the unified attention module binds the helpers at import time
    load("vllm.v1.attention.ops.triton_attention_helpers",
         f"{src}/triton_attention_helpers.py")
    return load(f"ua_{tag}", f"{src}/triton_unified_attention.py").unified_attention

ua_base = load_ua("base", f"{HERE}/ua_base")
ua_pr = load_ua("pr", f"{HERE}/ua_src")

def make(B, ctx):
    g = torch.Generator(device="cuda").manual_seed(0)
    nper = math.ceil(ctx / BS)
    nb = B * nper + 1
    kc = torch.randn(nb, BS, KVH, D, device="cuda", dtype=torch.bfloat16,
                     generator=g)
    vc = torch.randn_like(kc)
    bt = (torch.randperm(nb - 1, device="cuda", generator=g)[: B * nper] + 1)
    q = torch.randn(B * QLEN, H, D, device="cuda", dtype=torch.bfloat16,
                    generator=g)
    cu = torch.arange(B + 1, device="cuda", dtype=torch.int32) * QLEN
    sk = torch.full((B,), ctx, device="cuda", dtype=torch.int32)
    return q, kc, vc, bt.view(B, nper).int(), cu, sk

def run(fn, q, kc, vc, bt, cu, sk, ctx, window):
    out = torch.empty_like(q)
    n = q.shape[0]
    segs = dict(
        seq_threshold_3D=E("THRESH", 128 // KVH),
        num_par_softmax_segments=NSEG,
        softmax_segm_output=torch.empty(n, H, NSEG, D, device="cuda"),
        softmax_segm_max=torch.empty(n, H, NSEG, device="cuda"),
        softmax_segm_expsum=torch.empty(n, H, NSEG, device="cuda"),
    )
    f = lambda: fn(q, kc, vc, out, cu, QLEN, sk, ctx, D**-0.5, CAUSAL,  # noqa
                   window, bt, 0, None, None, None, **segs)
    f()
    N = 20
    g = torch.cuda.CUDAGraph()
    with torch.cuda.graph(g):
        for _ in range(N):
            f()
    us = do_bench(g.replay, warmup=10, rep=200) * 1e3 / N
    return us, out.clone()

print(f"H={H} KVH={KVH} D={D} qlen={QLEN} SW={SW} causal={CAUSAL} block={BS} "
      f"nseg={NSEG} seq_threshold_3D={E('THRESH', 128 // KVH)}")
print(f"{'B':>3} {'ctx':>6} {'main_us':>8} {'pr_us':>8} {'speedup':>7} {'maxerr':>7}")
w = (SW - 1, 0 if CAUSAL else SW - 1)
for B in (1, 2, 4, 8, 16, 64):
    for ctx in (512, 2048, 4096, 8192, 32768, 131072):
        if B * ctx > 64 * 8192:
            continue
        args = make(B, ctx)
        tb, ob = run(ua_base, *args, ctx, w)
        tp, op = run(ua_pr, *args, ctx, w)
        err = (op.float() - ob.float()).abs().max().item()
        print(f"{B:>3} {ctx:>6} {tb:8.1f} {tp:8.1f} {tb / tp:6.2f}x {err:7.1e}",
              flush=True)

## Details

**Window segmentation.** In `compute_tile_loop_bounds` (`triton_attention_helpers.py`), when `IS_3D` and the sliding window can be pruned:
```python
num_segments = cdiv(seq_len, tiles_per_segment * TILE_SIZE)
window_tiles_per_segment = cdiv(max(tile_end - tile_start, 0), num_segments)
loop_lo = tile_start + segm_idx * window_tiles_per_segment
loop_hi = min(loop_lo + window_tiles_per_segment, tile_end)
```
- `num_segments` is the count `reduce_segments` derives from `seq_len`, so the reduction reads exactly the segments that were written. Segments past the window stay empty, and the reduction already ignores empty segments (#56148).
- The kernel's existing early exit (`segm_idx * tiles_per_segment * TILE_SIZE >= seq_len`) is unchanged.
- Without a sliding window, the bounds are the same as before.

**Non-causal 3D.** This removes `or not use_causal` from the `use_3d` condition.
- The existing scratch-size guard still falls back to 2D when the scratch has fewer rows than query tokens.
- `TritonAttentionMetadataBuilder` sizes the scratch for `1 + num_speculative_tokens` tokens per sequence, which covers the DFlash block.

**Minimum segment size.** For non-causal 3D launches, `unified_attention` passes `MIN_TILES_PER_SEGMENT = min(next_power_of_2(num_seqs), 8)` (otherwise 1) as a constexpr to both kernels:
```python
tiles_per_segment = cdiv(seq_len, NUM_SEGMENTS_PER_SEQ * TILE_SIZE)
if MIN_TILES_PER_SEGMENT > 1:
    tiles_per_segment = max(tiles_per_segment, MIN_TILES_PER_SEGMENT)
```
- The kernel's early exit, the window segmentation, and `reduce_segments` all derive the segment count from `tiles_per_segment`, so they stay consistent. Unused segments are left empty, as at short context today.
- The value depends only on `num_seqs`, not on sequence lengths, so a captured CUDA graph keeps its choice across replays.
- It compiles at most 4 more kernel variants (1, 2, 4, 8). Causal launches and the other `reduce_segments` callers keep the default of 1, and their code is unchanged.

**Relation to #57409.** That PR also routes non-causal DFlash draft rows to the 3D kernel, and it sizes the scratch for them. It excludes sliding windows (`sliding_window_val == 0`), and the DFlash2 drafter uses one, so the drafter case above is not covered there. The two PRs overlap on the `use_causal` condition. If #57409 lands first, this PR reduces to the window segmentation plus the drafter-with-window case.

No host synchronization or new kernel launches are added.
