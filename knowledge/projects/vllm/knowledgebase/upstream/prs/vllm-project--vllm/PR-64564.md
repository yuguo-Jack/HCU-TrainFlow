# [Bugfix] Fix EVS M-RoPE recompute when a prefill chunk ends after a vision start token

[Upstream PR](https://github.com/vllm-project/vllm/pull/64564) · state: open · merged: False

## Original PR description



## Overview

Fix `recompute_mrope_positions` (EVS / `--video-pruning-rate`) when the previous prefill chunk ends right after a media's `<|vision_start|>` token. It crashed the engine with `IndexError` or silently produced wrong M-RoPE positions.

## Claims

- Fixes `IndexError: index 0 is out of bounds for dimension 0 with size 0` at `evs.py:297`, which raises in a worker and kills the engine (`EngineDeadError`). We hit this in production serving a Qwen3-VL-based model with `--video-pruning-rate 0.01`, chunked prefill, and multi-image requests.
- Fixes wrong M-RoPE positions in the same situation when a later media exists in the prompt. That case doesn't raise; generation just diverges.

```python
import sys
from PIL import Image
from transformers import AutoProcessor
from vllm import LLM, SamplingParams

MODEL = "Qwen/Qwen3-VL-2B-Instruct"
num_images = int(sys.argv[1]) if len(sys.argv) > 1 else 2

processor = AutoProcessor.from_pretrained(MODEL)
images = [Image.new("RGB", (224, 224), c) for c in ["red", "blue", "green"][:num_images]]
content = [{"type": "text", "text": "Describe these images."}]
for _ in images:
    content += [{"type": "image"}, {"type": "text", "text": "Next."}]
prompt = processor.apply_chat_template(
    [{"role": "user", "content": content}], add_generation_prompt=True, tokenize=False
)
ids = processor(text=[prompt], images=images, return_tensors="pt")["input_ids"][0].tolist()
vs_id = processor.tokenizer.convert_tokens_to_ids("<|vision_start|>")
vision_starts = [i for i, t in enumerate(ids) if t == vs_id]
chunk = 4096 if len(sys.argv) > 2 else vision_starts[1] + 1

llm = LLM(
    model=MODEL,
    max_model_len=4096,
    max_num_batched_tokens=chunk,
    max_num_seqs=1,
    enable_prefix_caching=False,
    video_pruning_rate=0.5,
    limit_mm_per_prompt={"image": num_images, "video": 0},
    gpu_memory_utilization=0.5,
    enforce_eager=True,
)
out = llm.generate(
    {"prompt": prompt, "multi_modal_data": {"image": images}},
    SamplingParams(temperature=0, max_tokens=40),
)
print(out[0].outputs[0].text)
```

## Details

**Root cause.** For each media in the current chunk, `recompute_mrope_positions` decides whether the chunk continues a media started in an earlier chunk (`in_the_middle_of_media`) or starts a new one at the next `<|vision_start|>` at or after `num_computed_tokens`. When the previous chunk ended exactly after a media's `<|vision_start|>`, neither applied. No embedding of that media had been seen, so it wasn't treated as "in the middle", and its vision start is behind `num_computed_tokens`, so the next-start lookup skips it:
- if no later media exists, the lookup indexes an empty tensor and the worker raises `IndexError`;
- otherwise the media is anchored at the *next* media's vision start, which gives wrong positions.

Chunk boundaries land there in normal serving with chunked prefill. With pruning enabled, images go through this path too, so multi-image requests hit it regularly.

**Fix.** Treat a chunk that starts one token after the last seen vision start, on a media token, as the start of that media (`in_the_middle_of_media` with 0 embeddings seen). This extends the existing Qwen3-VL timestamp special case right above it. The `media_mask` check keeps it from firing for frames whose tokens were all pruned, which still go through the next-vision-start path.

**Notes.**
- The new condition reads a GPU tensor on the host. This function already syncs heavily (`.item()`, `nonzero`, `count_nonzero`), and its Qwen3-VL caller runs it under `gpu_sync_allowed()`, so it adds no new kind of sync. It only runs when multimodal pruning is enabled.
- **CI:** the only active step that runs `tests/model_executor` is AMD MI300 Model Executor; the NVIDIA step is currently disabled in `.buildkite/test_areas/model_executor.yaml`. The new test is CPU-only.
- There is no `vllm_runner` regression test, because forcing the chunk boundary needs a model-specific prompt layout. The unit test exercises the exact branch against ground-truth positions, and the end-to-end run above covers the real engine path.
