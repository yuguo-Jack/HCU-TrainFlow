# [Perf][HiSparse] Drop the per-call pinned check from the residency resolver

[Upstream PR](https://github.com/vllm-project/vllm/pull/64732) · state: closed · merged: False

## Original PR description

Related to #60072.

`hisparse_resolve_residency` checked that `host_cache` is pinned, which costs a `cudaPointerGetAttributes` driver call on every eager launch (every layer of every step outside CUDA graphs). The resolver never reads host memory; it only uses `host_cache` for its row count. This PR keeps the CPU-device and shape checks and drops the pinned check. The `hisparse_gather_*` ops read host memory and keep theirs.

This is a host-only change. The SASS of every kernel in `hisparse_kernels.cu` is identical to `main`.

## Performance (neutral)

**Hardware and model:** 4× B200 (pirate2 `dell-b200-02`), TP4, GLM-5.3-NVFP4. Base and PR ran back to back on the same node, three runs each, with the server restarted for every run. Both variants used `_C_stable_libtorch` built locally for SM100 with the same toolchain.

**Workload:** random dataset, 16,384-token inputs and 1,024-token outputs, c=64, 128 prompts.

**KV regime:** the startup log reports full-residency capacity of 40.76 requests at 18,432 tokens, but 64 requests were running. Every run therefore read from host: about 300M hot-buffer misses and about 600 GB H2D per run, in both variants.

| | output tok/s (r1 / r2 / r3) | mean | mean TPOT (ms) | mean TTFT (ms) |
|---|---|---|---|---|
| main | 1017.4 / 1022.5 / 1021.6 | 1020.5 | 50.87 | 11892 |
| PR | 1018.2 / 1019.4 / 1018.5 | 1018.7 (-0.17%) | 50.96 | 11913 |

The difference is within main's run-to-run spread of 0.5%. The saving is about 0.1 µs per eager resolver call, too small to show on a server.

## Correctness

These runs also used 4× B200 at TP4, with `--max-model-len 4096` and `--num-gpu-blocks-override 8000`, which gives a full-residency capacity of 3.05 requests. Most of the time six requests were running, so the host tier was exercised. The HiSparse stats show about 34M hot-buffer misses and about 73 GB H2D per 2,000-step readback interval, in both variants.

- **GSM8K** (1,319 questions, c=16): main 0.903, PR 0.901.
- **Greedy:** 48 prompts of about 3.3k tokens each (retrieval over a code registry), 96 output tokens, c=16. Both variants retrieve the queried code 48/48 and list the next five codes in 46/48 (main) and 47/48 (PR). Exact text matched 0/48. Two back-to-back main runs (main wheel, `dell-b200-01`) also matched 0/48 exactly, while retrieving 48/48 and 47/48. Greedy text is not reproducible in this regime, so the PR's divergence is at main's noise floor.
