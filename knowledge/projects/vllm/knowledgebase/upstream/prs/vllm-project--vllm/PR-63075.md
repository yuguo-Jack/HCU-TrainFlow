# [Bugfix][EPLB] Give EPLB each expert-weight region once

[Upstream PR](https://github.com/vllm-project/vllm/pull/63075) · state: open · merged: False

## Original PR description



## Overview

With the Humming FP8 MoE backend and a block-quantized FP8 checkpoint, `RoutedExperts.get_expert_weights()` gives EPLB the same scale tensor twice. EPLB with the default NIXL communicator then fails at start-up. This PR makes `get_expert_weights()` return each memory region once.

## Claims

- **Bug fix:** `--moe-backend humming` + block FP8 (`weight_scale_inv`) + `--enable-eplb` no longer fails in `NixlEplbCommunicator` init with `NIXL_ERR_NOT_ALLOWED`.
- With a non-NIXL communicator (`torch_gloo`, `pynccl`), EPLB no longer moves the aliased scale rows twice during a rearrangement (from the code; not measured).
- No change for layers without aliased parameters: the returned list is the same as before.

## Validation

Measured on 8 x A100, Qwen3.8-Flash-Next-FP8 (block FP8), `--moe-backend humming --enable-eplb`, default NIXL EPLB communicator (NIXL 1.4.1):

- **Before (vLLM 5555a2d8f):** start-up fails.
  ```
  loadRemoteMD: error loading remote metadata ... NIXL_ERR_NOT_ALLOWED
  RuntimeError: Failed to initialize NixlEplbCommunicator (NIXL EPLB init failed: agents)
  ```
- **Alias check (1 GPU):** after weight processing, the Humming layer has `[w13_weight, w13_weight_scale, w2_weight, w2_weight_scale, w13_weight_scale_inv, w2_weight_scale_inv]`. `w13_weight_scale` and `w13_weight_scale_inv` share one memory region (the same for `w2`). The Marlin backend has no alias.
- **After (same setup, with this change):** the 8 NIXL agents initialize and there is no `NIXL_ERR_NOT_ALLOWED`. At our first KV cache setting the engine then ran out of memory in CUDA graph capture (EPLB needs about 1.1 GiB more per GPU here; not related to this change). With 1.25 GiB less KV cache it starts and serves: 2 runs of 60 min each, MLPerf agentic workload, 32 sessions, 8 redundant experts, rearrangement every 3,000 steps, 0 failed requests. EPLB logs balancedness (mean / max tokens per EP rank) of 0.79-0.87 during serving, and the runs started 28 and 29 asynchronous rearrangements after the start-up one (11,814 and 11,918 samples, 0 failed). The task score stays inside the run-to-run spread of the same server without EPLB (0.5380 and 0.5399 vs 0.5387 and 0.5337).
- **Unit test (CPU):** `tests/kernels/moe/test_fp8_tp_loading.py::test_fp8_block_expert_weights_give_each_region_once` builds a real block-FP8 `RoutedExperts` on CPU and adds a second `*_weight_scale` Parameter over each `*_weight_scale_inv` storage, as Humming does.
  ```
  pytest -q tests/kernels/moe/test_fp8_tp_loading.py::test_fp8_block_expert_weights_give_each_region_once
  ```
  - On `main` without the fix: fails, `Left contains 2 more items` (both scales are returned twice).
  - With the fix: `1 passed`.
  - This test runs in the existing "MoE Kernels" CI step (`tests/kernels/moe`, triggered by `vllm/model_executor/layers/fused_moe/`).
- `ruff check` and `ruff format --check` (ruff 0.14.0) pass on the changed files. The full `pre-commit` suite was not run.

**Not measured:**
- No dedicated accuracy benchmark (only the task score of the serving runs above).
- No rearrangement run with `torch_gloo` or `pynccl`; the double-move claim follows from the code, not from a measurement.
- No performance claim.

## Details

**Root cause.**
1. `convert_to_fp8_moe_kernel_format` (HUMMING branch, `fused_moe/oracle/fp8.py`) calls `convert_to_humming_moe_kernel_format`. It deletes the `w13_*`/`w2_*` parameters, registers Humming's own (`w13_weight_scale`, ...), and returns `layer.w13_weight_scale`.
2. `Fp8MoEMethod` then calls `replace_parameter(layer, "w13_weight_scale_inv", w13_scale)`. The old parameter was deleted in step 1, so `replace_parameter` registers a new Parameter over the same storage.
3. `get_expert_weights()` returns every named parameter except a few non-expert names. `named_parameters()` merges only identical Parameter objects, so both names reach EPLB.
4. NIXL registers the same region twice. In `nixlRemoteSection::addDescList`, a descriptor that is already present with different metaInfo gives `NIXL_ERR_NOT_ALLOWED`.

**Fix.** `get_expert_weights()` keeps the first parameter for each `(data_ptr, nbytes)` region, in `named_parameters()` order. The existing filters, the contiguity assert and the scale-transpose view are unchanged. The transpose view keeps `data_ptr` and `nbytes`, so it does not change the key.

**Tensor count.** EPLB code assumes the same tensor list for each layer and rank:
- `EplbState` sizes `expert_buffer` from `model.expert_weights[0]` and zips it with the tensors of every layer.
- `NixlEplbCommunicator` exchanges metadata keyed by `(layer_idx, tensor_idx)` between ranks.

The dedup is deterministic and depends only on the layer's parameter layout. All MoE layers of a model use the same quant method and backend, and all ranks run the same code. So each layer and rank keeps the same count, order and shapes. The 1-byte `uint8` view in `MixtureOfExperts.set_eplb_state` comes after this function and does not change it.

**Limitations.**
- The key is the exact region (same address and size). Partial overlaps (a view of part of another parameter) are not merged; no backend registers these today.
- `DeepGemmMegaMoE.get_expert_weights()` is a separate implementation and is not changed.
- #62407 (open) plans to alias renamed params as one Parameter object under two names. `named_parameters()` already merges that case; this change covers the case of two Parameter objects over one storage, which is what `main` does now.

**Related:** #61786 (merged, 1-byte EPLB tensors as `uint8` views), #47588 (open, Quark MXFP4 weights missing from `get_expert_weights`), #62326 (merged, `replace_parameter` keeps the parameter object), #62407 (open). No open PR or issue found for this failure.
