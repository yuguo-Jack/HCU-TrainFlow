# [Perf][MiniMax-M3] Quantize the routed MoE input while the router GEMM runs

## Overview

In MiniMax-M3's decode, the routed experts (TRTLLM-Gen NVFP4, per-token activation scales) are on the step's critical path. Each MoE layer runs, back to back on that path:

1. the fp32 router GEMM (`GateLinear`);
2. inside the MoE call, the per-token NVFP4 quantization of the experts' input (`quantize_nvfp4_per_token_input`);
3. routing and the expert GEMMs.

Steps 1 and 2 both read only the hidden states, so the quantization does not need to wait for the router.

This PR quantizes on the aux stream while the router GEMM runs, then hands the result to the experts:

- Each TRTLLM-Gen NVFP4 experts instance owns an `NvFp4PerTokenInputHandoff` (`fused_experts.input_handoff`). Its `quantize(x)` is the experts' input quantization. `provide(x, quantized)` scopes a precomputed result to one MoE call and restores the previous entry on exit.
- The experts use the provided result only if their input is that very tensor: same storage, shape, strides and dtype. Anything else is quantized as before.
- `MiniMaxM3MoE._route` is one context manager:
  - record a fork event on the main stream;
  - on `aux_stream()`, wait for the fork, call `handoff.quantize`, and record a join;
  - run the router GEMM on the main stream;
  - wait for the join;
  - `record_stream` the outputs on the main stream, so the allocator cannot reuse their blocks before the MoE call that reads them;
  - yield the router logits with the handoff open.
- It runs only while the call is being captured into a CUDA graph (`torch.cuda.is_current_stream_capturing()`), at any captured size. There the fork and join are recorded once and replay for free. An eager forward does not use it, and the experts quantize on the current stream as before. Eager forwards are steps above the largest captured size, e.g. steps carrying a prefill chunk, or runs without CUDA graphs. They are host-bound, and the per-layer fork and join (57 MoE layers) cost more host time than the overlap saves on the GPU (see Validation).
  - The model is not `torch.compile`d. Breakable CUDA graphs run this Python at capture time and replay only the graphs, so the check is evaluated on every call; it is not traced once into a compiled graph.
- It applies only when the routed experts are TRTLLM-Gen NVFP4 with per-token activation and receive the hidden states unchanged:
  - no all-to-all, naive DP/SP dispatch, PCP or padding;
  - no routed input transform;
  - no DBO;
  - not MegaMoE;
  - bf16 input.

  This is checked per call against the built kernel, so a weight reload is picked up.

The kernels and their inputs are unchanged, so outputs are bit-identical.

## Claims

- **Bit-identical outputs:** same kernel on the same input, only overlapped with the router GEMM.
- **Eager steps unchanged:** steps that run eagerly take the previous path.
- **End to end:** the per-layer latency from the post-attention all-reduce to the first routed GEMM drops by 1.7–4.1 µs, which is −1.2% to −1.5% of a decode step at concurrency 1–32 (see Validation).

## Validation

GB300 (SM103), driver 580.178.04, image `vllm/vllm-openai:minimax-m31-flash-arm64-cu134@sha256:5d763476…` with this PR's two source files. The measurements below were taken before the rebase onto `main` a900ac810e. The rebase had one import-level conflict in each source file (`main` added a `SWIGLUSTEP` check next to the new handoff, and the model's import block moved); the logic is unchanged.

**On a `main` build** (the nightly wheel for a900ac810e on the same image, with this PR's files; GB300, 4 ranks): the two test files gave 28 passed / 2 failed / 2 skipped. The 2 failures (`test_trtllm_fp4_moe_deferred_finalize[1-None]` and `[16-None]`, 1 of 1024 elements off by 3e-5 at zero tolerance) and the 2 skips (a FlashInfer tile-config skip) are the same on `main`. A 12-request smoke serve completed 12/12, and a probe saw the handoff quantize and provide during graph capture on every rank.

**Tests** (GPU, SM100):

- `tests/kernels/moe/test_trtllm_nvfp4_moe.py`:
  - The handoff is used only for its own input. A view counts; a clone, a slice, a dtype view or another stride over the same storage does not.
  - Per-token TRTLLM-Gen experts given a side-stream quantization return output `torch.equal` to the self-quantizing call. Given another input's quantization, they return that input's output.
- `tests/models/minimax_m3/test_moe_input_quant_overlap.py`: a `MiniMaxM3MoE` block on TRTLLM-Gen experts, at 1/16/200 tokens, against the router and MoE call run in sequence:
  - Eager `moe(x)` is `torch.equal` to the reference and does not use the handoff.
  - `moe(x)` captured in a CUDA graph uses the handoff once. Replays with new inputs are `torch.equal` to the reference for each input.
- On GB300 before the rebase: 13 passed, 1 pre-existing skip / 3 passed. After the rebase (the rebased source merged onto the image's files): 13 passed, 1 skipped / 3 passed. One of the 13, a trivial test of the handoff's nesting and restore-on-error, has since been removed.

**Router + quantization alone** (graph-timed, GB300): router GEMM (fp32, 6144 → 128) plus per-token input quantization, serial vs overlapped, in µs:

| tokens | serial | overlapped | change |
|---|---|---|---|
| 1 | 4.19 | 3.59 | −14% |
| 32 | 8.47 | 5.20 | −39% |
| 256 | 12.12 | 8.83 | −27% |
| 512 | 15.95 | 12.05 | −25% |
| 1024 | 18.83 | 17.24 | −8% |
| 2048 | 24.88 | 21.96 | −12% |
| 4096 | 39.01 | 33.94 | −13% |
| 8192 | 75.84 | 61.61 | −19% |

On the GPU the overlap never loses up to the 8192-token prefill chunk. So the gate is CUDA graph capture, not a token count: captured steps take the overlap at any size, and only eager steps skip it, because of their host cost (see "Eager big steps" below).

**Serving** (InferenceX GB300 recipe: TP4, DSpark K=7, NVFP4 KV, FULL_AND_PIECEWISE; agentic-like code prompts of about 22k tokens; nsys; arms alternated base / PR / base / PR on one node).

Whole-step periods move by up to ±4% between server restarts on this setup, because each restart decodes different text. So the comparison uses the per-layer MoE head latency: the post-attention all-reduce + norm kernel's end to the first routed GEMM's start. Each value is the median over about 2,500 layer instances of one server run (µs):

| concurrency | base | this PR | MoE tail, base → this PR |
|---|---|---|---|
| 1 | 10.11 / 10.05 | 8.03 / 8.00 | 3.97 / 3.90 → 3.94 / 3.94 |
| 8 | 18.14 / 18.18 | 15.04 / 15.10 | 15.30 / 15.17 → 15.94 / 15.52 |
| 16 | 17.82 / 17.86 | 14.50 / 14.50 | 17.95 / 17.82 → 17.73 / 17.79 |
| 32 | 23.87 / 22.62 | 18.21 / 18.21 | 23.30 / 23.07 → 23.04 / 23.04 |

At 57 MoE layers that is about −100 / −200 / −190 / −230 µs per decode step at concurrency 1 / 8 / 16 / 32 (−1.2% to −1.5%). The MoE tail (the last routed GEMM's end to the next layer's QKV GEMM) is unchanged. An earlier prototype with the same logic gave the same picture on another node; at concurrency 1 its target CUDA graph span went from 5858 / 5862 to 5768 / 5767 µs.

With the handoff owned by the experts (ABAB on one node per concurrency; previous revision → this one, MoE head µs/layer): 8.19 / 8.19 → 8.13 / 8.06 at c1, 18.18 / 18.30 → 18.30 / 18.72 at c32. In the decode graphs, every per-token quant kernel runs concurrently with another stream (6840 / 6840 at c1 and c32), on one stream per graph instead of 26 pooled ones, and CUDA-graph memory went down: 0.34 → 0.31 GiB at c1, 5.12 / 4.17 → 4.66 / 3.58 GiB at c32.

**Eager big steps.** Setup: the GB300 recipe at concurrency 32 (max-num-seqs 64), with this PR stacked on other pending MiniMax-M3 changes. Load: 32 streaming decodes plus sequential 3.5k / 7.5k-token prompts with 1 output token. Each prompt adds 1–2 steps above the largest captured size (1024 tokens), and those steps run eagerly. Step period is the host time from one `execute_model` to the next, on rank 0.

Taking the overlap in eager steps too made them 4–5% slower on Grace: +7 to +8 ms per step from 57 forks and joins. That is why this PR takes it only under capture. Paired within one server, a file toggle switches the eager path every two prompts and leaves the decode graphs unchanged (120 prompts per server, mean ms per eager step):

| server | overlap in eager steps | this PR (capture only) | change |
|---|---|---|---|
| 1 | 182.1 | 175.1 | −3.8% |
| 2 | 176.4 | 168.2 | −4.6% |

Unmodified builds, alternated on one node (40 prompts each):

| build | eager step, mean ms | decode step, median ms |
|---|---|---|
| overlap in eager steps | 175.7 / 171.9 | 16.74 / 16.83 |
| this PR | 162.0 / 160.9 | 16.98 / 16.84 |

Decode steps replay the same graphs in both builds. In the toggle build, a counter saw 4845 side-path MoE calls during capture on every rank: 85 graphs (83 piecewise, 2 full) × 57 MoE layers. The decode medians differ by less than the ±1% seen between server restarts.

**Accuracy** (GSM8K chat, 320 questions, concurrency 32, together with two other pending changes): greedy 0.9781 → 0.9750, temperature 1 / top-p 0.95 0.9750 → 0.9719 (one question each); DSpark acceptance unchanged. Outputs are bit-identical by construction, which the block test asserts.

## Details

- `vllm/model_executor/layers/fused_moe/experts/trtllm_nvfp4_moe.py`: `NvFp4PerTokenInputHandoff` and its use in the per-token experts' input quantization.
- `vllm/models/minimax_m3/nvidia/model.py`: `MiniMaxM3MoE._route` and the per-call applicability check.
- CI: the `(B200) Kernels` step runs the kernel tests; the `(B200) MiniMax-M3 Model Tests` step, which runs the block test, now also triggers on `trtllm_nvfp4_moe.py`.
- The overlap uses the existing `aux_stream()`; no new stream or config option.
- **Related:** #43592 fuses MiniMax-M2's top-k and activation quantization into a prepared-input fast path. This PR does not fuse kernels; it only moves the existing quantization off the critical path.
