# [Core][Frontend] Process checkpoint lifecycle with HTTP prepare/status/resume

[Upstream PR](https://github.com/vllm-project/vllm/pull/62570) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

Make process checkpoint/restore (CRIU plus `cuda-checkpoint`, run by an external orchestrator such as [ai-dynamo/snapshot](https://github.com/ai-dynamo/snapshot)) a first-class engine lifecycle with a production HTTP surface: `POST /checkpoint/prepare`, `GET /checkpoint/status`, `POST /checkpoint/restore`, and `--checkpoint-prepare-on-startup`, in the Python and Rust frontends. Implements the minimal API from RFC #60422 ([summary](https://github.com/vllm-project/vllm/issues/60422#issuecomment-6187366614)), building on the communicator hooks from #46877 and the paused-request rejection from #51488.

## Claims

- The engine owns a repeatable lifecycle: `running → preparing → prepared → restoring → running`, or `failed`. `AsyncLLM.checkpoint_prepare(mode)` and `checkpoint_restore()` each run as one engine call, so repeated and concurrent calls (several API servers, DP) are no-ops. `checkpoint_state()` reports the state; DP engines merge as failed if any failed, otherwise the shared state.
- `POST /checkpoint/prepare?mode=wait|abort|keep` drains with the pause mode, discards the KV cache and runs the workers' `checkpoint_prepare` hooks. It returns 200 once started (poll status), or 400 with the reason if the engine cannot prepare now, like the other admin routes (for example asleep or mid-cycle).
- `GET /checkpoint/status` returns 200 when prepared, 503 until then and 500 after a failure. `POST /checkpoint/restore` returns 200 when restoring or done (orchestrators redeliver), 400 while preparing or failed. Both work after a restore or in place.
- While an engine does not serve, new requests get the retryable `engine_paused` error from #51488, and `sleep`, `wake_up` and `resume_scheduler` are refused. `/health` keeps its upstream meaning and returns 200, as for a sleeping engine.
- `--checkpoint-prepare-on-startup` prepares each engine once it starts, for capture-at-startup orchestrators.
- The routes exist only with `--enable-sleep-mode`, which preparing requires, as the fault-tolerance and profiler routes exist only with their flags. They document their status codes in the OpenAPI schema.
- The Rust frontend serves the same three routes with the same status codes, bodies and sleep-mode gating.

## Details

**Why this shape.** The pieces exist upstream, but an external orchestrator cannot use them safely: `/pause`, `/sleep` and `/wake_up` are dev-mode routes, `checkpoint_prepare/restore` (#46877) only run the worker hooks and leave sequencing to the caller, nothing reports where the engine is, and other calls can interleave. Moving each step into one engine call gives an idempotent, observable contract that any orchestrator (Snapshot, scripts, future live migration) can drive over HTTP, and that the Rust frontend can call without copying the sequence.

`AsyncLLM.checkpoint_prepare()` and `checkpoint_restore()` previously only ran the worker communicator hooks, and callers paused and slept first. They now run the whole step and refuse an engine that is already asleep. The worker-level hooks are unchanged.

**Not duplicate.** #51360 (`vllm snapshot`), #52132, #35934, #37921, #58183 and #61544 implement checkpointing inside vLLM (CRIU and/or `cuda-checkpoint`). This PR adds no checkpointing code; it is the boundary an external orchestrator needs, and those paths could reuse the same lifecycle later. #48311 owns pause/drain/sleep for RL; this PR reuses `pause_generation` and adds no new pause semantics.

**Tradeoffs and limitations.**
- `/health` stays a liveness check, which the multi-port DP supervisor, elastic EP and the documented Kubernetes probes rely on. A prepared engine therefore stays in rotation, and new requests get the retryable `engine_paused` error until it resumes. A readiness signal that stays false until the engine serves can be added later without changing `/health`.
- With `--enable-sleep-mode`, the routes need no API key, like `/scale_elastic_ep` and the dev-mode `/sleep` and `/pause`. They are listed in `docs/usage/security.md`. A deployment that does not want them can block the paths at the proxy.
- `EngineCoreProc.resume_scheduler` now clears `reject_new_requests` after the base class's checks, so a refused resume keeps rejecting requests.
- With data parallelism, the Rust frontend reports a prepare refusal from any engine, and Python reports engine 0's. Engines that accepted keep preparing. Refusal causes are normally the same on every engine.
- Follow-ups, already prototyped: a checkpoint resource registry for CPU offload and HiSparse host memory (galletas1712/vllm#5), and independent P/D restore over NIXL (galletas1712/vllm#3). No gRPC `Control` methods yet.
