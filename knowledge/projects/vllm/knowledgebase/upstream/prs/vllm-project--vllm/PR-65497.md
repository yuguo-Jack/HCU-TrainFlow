# [Perf][Kernel] Fuse RMSNorm + block FP8 quant for fp32 (Gemma-style) norm weights

[Upstream PR](https://github.com/vllm-project/vllm/pull/65497) · state: open · merged: False

## Original PR description



## Overview

Let `rms_norm_per_block_quant` take an fp32 norm weight with a bf16/fp16 input, and let the RMSNorm + group-quant fusion patterns fuse that case. `GemmaRMSNorm` passes an fp32 `1 + weight`, so since #44694 the pass skips it and block-FP8 models with Gemma norms run the norm and `per_token_group_fp8_quant` as separate kernels.

## Claims

- Block-FP8 models that use `GemmaRMSNorm` and go through torch.compile on CUDA (e.g. `Qwen/Qwen3-Next-80B-A3B-*-FP8`) get the RMSNorm + per-block FP8 quant fusion again, plain and fused-add.
- Numerics match the unfused path: the kernel rounds `normed.to(weight.dtype) * weight` to the input dtype before quantizing, exactly like `rms_norm`'s native implementation. Same-dtype weights compile to the same expression as before.
- Qwen3.5 on NVIDIA is not affected: since #51012 it no longer uses torch.compile there.

## Validation

Built `_C_stable_libtorch` from this branch on top of the precompiled wheel for c1d8fade; torch 2.14.0+cu130, CUDA 13.0.

The new kernel test fails on main at the dtype check (`fused_layernorm_dynamic_per_token_quant.cu:295`, `weight.scalar_type() == input.scalar_type()`) and passes with this change. The new `test_fusion_gemma_rmsnorm_block_quant` ran on Triton (both GPUs) and Cutlass block FP8 (H200); the DeepGEMM cases are skipped by the existing packed-UE8M0 rule.

Not included: an end-to-end Qwen3-Next-80B-FP8 accuracy and throughput comparison (stopped before completion), and kernel-level timing of the fp32-weight path. A proxy microbenchmark on an RTX 4050 (existing fused kernel with a bf16 weight vs. Inductor native Gemma norm + `per_token_group_fp8_quant`, CUDA graph replay, dynamic token dim) showed 19-54% less time for the norm+quant step at hidden 4096/5120; that is not a measurement of this change.

## Details

- `layernorm_utils.cuh`: the vectorized scale and norm+quant helpers take a `weight_t` template parameter (default `scalar_t`), and the weight multiply goes through one helper, `apply_norm_weight`.
- `fused_layernorm_dynamic_per_token_quant.cu`: `rms_norm_per_block_quant` dispatches on an fp32 weight and accepts it in the host check. The extra dispatch level re-indents the launch block; the change is easier to read with whitespace hidden.
- `rms_quant_fusion.py`: the two group-quant patterns use a check that allows an fp32 weight. Static and per-token patterns keep the strict dtype check (their kernels are unchanged).
- Kernel instantiations: one extra weight type for bf16/fp16 inputs in the per-block kernel only.

## Overall assessment

The core insight is clean: `GemmaRMSNorm.forward_native` already materializes an
fp32 `1 + weight` and feeds it to `rms_norm`, so the `+1` offset never needs to
touch the kernel — the kernel just has to tolerate an fp32 weight alongside a
bf16/fp16 input. Templating `weight_t` (default `scalar_t`) through
`compute_dynamic_per_token_scales` / `norm_and_quant` and routing the multiply
through a single `apply_norm_weight` helper is the minimal way there, and the
same-dtype case provably compiles down to the previous expression.

## Blocking
None.

## What I checked and found safe

- **Numeric equivalence to the unfused reference.** `apply_norm_weight<scalar_t>`
  is `static_cast<scalar_t>(static_cast<weight_t>(normed) * weight)`. With
  `weight_t=float` this is exactly `(bf16)((fp32)normed * weight_fp32)` — a
  faithful match for the Gemma path; with `weight_t=scalar_t` it reduces to the
  old expression. Both the absmax pass and the quant pass go through the helper,
  so the scale and the quantized value use identical arithmetic.
- **The `(1 + weight)` Gemma variant** is handled entirely in `layernorm.py`
  (`weight = self.weight.float() + 1.0`); the fusion pattern matches
  `rms_norm(x, weight_fp32, eps)` and passes it through unchanged — the kernel
  stays Gemma-agnostic.
- **Residual add ordering** unchanged (folded in fp32, written back as
  `scalar_t` before any weight application); the new test asserts bit-exact
  residual (atol=0,rtol=0).
- **Fallback / scoping to the block path only:** the `extra_check` swaps to
  `_rms_weight_dtype_supported_by_block_quant` are only on the block/group-quant
  patterns whose FUSED_OP is `rms_norm_per_block_quant`; static and per-token
  keep `_rms_input_weight_dtype_match`, matching the host check.
- **Non-block callers untouched:** `rms_norm_dynamic_per_token_quant_kernel`
  calls the helpers without the `weight_t` arg → defaults to `scalar_t`,
  byte-identical.
- **Host check** still rejects any weight dtype that is neither input dtype nor
  fp32, with a clear message.

## Questions

1. **fp16 input + fp32 weight coverage.** Both new tests pin bf16. The path
   supports fp16 (`weight_t=float`, `scalar_in_t=half`) and the
   round-through-fp16 in `apply_norm_weight` is where a surprise would surface —
   could you add an fp16 case so that combination has an assertion behind it?
2. **`scale_ub` interaction** — the kernel test always passes `None`. Is the
   fp32-weight path reachable with non-null `scale_ub` in any Gemma block-FP8
   config? If yes, one case; if not, a note that it's out of scope.
3. **DeepGEMM / packed-UE8M0 skip** — confirming the pass *declines to fuse* on
   those configs (runs norm+quant separately, correct but unoptimized) rather
   than fusing and mismatching; a one-line comment near the skip would help.
4. **Validation gaps you flagged** — the e2e accuracy run was stopped early and
   the perf numbers are a proxy microbench on a different GPU. Honestly
   disclosed, appreciated; but the "[Perf]" / "19-54%" framing isn't
   substantiated for this change on a real model. A short lm-eval accuracy delta
   (fusion on vs off) on one Gemma-norm block-FP8 model before merge would close
   it. Not blocking given the correctness argument.

## Nits
- `apply_norm_weight`'s doc comment is precise — consider citing
  `ir/ops/layernorm.py` so the invariant is anchored to what it must stay in
  sync with.
- The re-indent (extra `VLLM_STABLE_DISPATCH_BOOL` level) makes the diff noisy;
  I verified the launch args are identical except `weight.const_data_ptr<weight_t>()`.
- The ULP test's `+ 8` floor could use a one-line comment on its origin.

Nice work overall — "keep the kernel Gemma-unaware, just let the weight be fp32"
is the right call, and the same-dtype no-op proof is the key thing that makes
this safe to land.
