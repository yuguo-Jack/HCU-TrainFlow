# [Bugfix][Core] Do not double-count CUDAGraph memory in --kv-cache-memory suggestion

[Upstream PR](https://github.com/vllm-project/vllm/pull/57983) · state: open · merged: False

## Original PR description

## Purpose

Fixes #57936

`--kv-cache-memory` suggestions double-count CUDAGraph memory whenever `VLLM_MEMORY_PROFILER_ESTIMATE_CUDAGRAPHS=1` (the default). `peak_activation_memory` included the graph estimate from `determine_available_memory`, and `compile_or_warm_up_model` then added the actual captured pool. For large graph pools both suggested values go negative, so they cannot be copied back and the startup-plan guard rejects them.

This is a regression of #37426, reintroduced by the accounting rewrite in #49208.

The allocation path is unchanged: it already subtracts the graph estimate once. This PR restores `peak_activation_memory` to transient activation headroom only, matching #37426, and extracts the suggestion arithmetic so a CPU test can pin the invariant.

`VLLM_ENABLE_STARTUP_PLAN=1` was saving that printed suggestion. The suggestion also subtracts the captured CUDAGraph pool and a 150 MiB buffer, so the next boot allocated fewer KV tokens than the profiled boot (reported by @GodRishUniverse). The plan now persists `available_kv_cache_memory_bytes`, the budget this boot allocated. The printed suggestion is unchanged.

On current main, extensible KV warmup reads `peak_activation_memory` as reserved activation headroom. Leaving the graph estimate out of that field matches that use. The captured pool is still subtracted once in the KV budget and once in the printed suggestion.

## Test Result

`ruff check` and `ruff format` are clean on the two files. The suggestion test encodes the #57936 numbers: suggestions stay positive when CUDAGraph is counted once, and go negative if the estimate is folded into peak activation. The startup-plan test checks that a later boot would replay the allocated budget rather than the tighter printed hint. Full GPU startup was not re-run on this machine.

@rajfirke With VLLM_ENABLE_STARTUP_PLAN=1, the plan still saves the printed `--kv-cache-memory suggestion`. The save call is unchanged by this PR. After this fix, the suggestion subtracts the capture free-memory delta plus 150 MB, whereas the first boot’s KV budget subtracts the graph estimate. Those different calculations can therefore change the KV capacity when the plan is reused.

In my Llama-3.1-8B-Instruct run on ROCm 10.1, the current estimate and capture delta are close: 3.83 GB versus 3.62 GB. Testing #59368 (+ my ROCm change) together with this PR reduces the estimate to about 0.68 GB, while the capture delta remains 3.62 GB. The first boot gets 81,360 KV tokens, but the saved suggestion gives the second boot only 56,112.

Saving `int(self.available_kv_cache_memory_bytes)` instead preserves 81,360 tokens on the second boot in that experiment. Would you be open to collaborating on the startup-plan part here rather than in a separate PR? Thanks!
