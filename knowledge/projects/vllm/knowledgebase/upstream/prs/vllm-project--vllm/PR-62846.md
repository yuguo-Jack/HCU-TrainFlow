# [ROCm][Perf] Fix wvSplitK tile choice for N>=5 on gfx950 and add N=6

[Upstream PR](https://github.com/vllm-project/vllm/pull/62846) · state: closed · merged: False

## Original PR description

## Purpose

On gfx950, `wvSplitK` picks YTILE 3 or 4 for wide outputs. Once N >= 5 those tiles are up to 4x slower than YTILE 2, so N=5 fell behind hipBLASLt on shapes like an LM head shard (e.g. the draft/target LM head under EAGLE with K=3 and 5 rows).

This PR:
- uses YTILE 2 for N >= 5 on gfx950 (N <= 4 and other GPUs are unchanged);
- lets gfx950 run N=6 through `wvSplitK` where it beats hipBLASLt (M > 1024, 2048 <= K <= 8192).

## Kernel results (MI355X, bf16, µs per call, CUDA graph over rotating weights)

LM head shard M=50016, K=6144:

| N | hipBLASLt | wvSplitK before | wvSplitK after |
|---|---:|---:|---:|
| 4 | 129.9 | 103.0 | 103.0 |
| 5 | 129.4 | 385.8 | 95.1 |
| 6 | 123.7 | — (hipBLASLt) | 98.1 |

Over a 630-shape grid (M 16–100032, K 512–16384, N 1–6):
- N=5: 35% faster than before on average (geomean), 42/105 shapes more than 20% faster, none slower beyond noise.
- N=6 in the enabled range: 13% faster than hipBLASLt on average (geomean), worst case +7% at M=100032 where both are bandwidth bound.
- N <= 4: unchanged.
- N=7/8 beat hipBLASLt on only part of the grid and stay on hipBLASLt.

Max relative error vs an fp32 reference: 0.4%.
