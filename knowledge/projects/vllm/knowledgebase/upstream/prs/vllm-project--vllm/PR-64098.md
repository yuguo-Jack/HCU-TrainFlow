# [ROCm] Bound DeepSeek V4 steady-state memory on gfx1151

[Upstream PR](https://github.com/vllm-project/vllm/pull/64098) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Fix a gfx1151 ROCm memory failure where long-running DeepSeek V4 DSpark `FULL_AND_PIECEWISE` serving can grow Linux page-table memory until a global OOM kills a Ray worker.

This keeps the original DeepSeek V4 DSpark runtime configuration intact and applies the validated low-overhead fix: bound paged-MQA decode workspace sizing through the active forward config, disable PyTorch expandable segments after ROCm gfx1151 warmup/capture, and keep a conservative post-collective completion guard.

## Claims

- Prevents the observed gfx1151 page-table OOM in the original DeepSeek V4 DSpark `FULL_AND_PIECEWISE` configuration.
- Keeps PyTorch expandable segments available during startup, memory profiling, and graph capture, then disables them once for steady-state gfx1151 ROCm serving when they were initially enabled.
- Preserves the existing paged-MQA live-row allocation behavior on current upstream, and fixes the remaining profiling/forward-context fallback so decode workspace reservation can use the scheduler/speculative config instead of falling back to `max_num_batched_tokens`.
- Removes the temporary allocator re-enable used by the previous validated workaround around collectives. The retained collective guard only synchronizes after selected generic device collectives when the steady-state allocator transition was applied.
- Does not change model weights, quantization, DSpark acceptance logic, RoPE, CUDA graph mode, TP behavior, or GEMM kernels.

## Details

The failure signature was not a normal tensor leak. The failing `FULL_AND_PIECEWISE` runs showed a Linux global OOM with Ray worker page tables growing into multi-GiB territory. EAGER and PIECEWISE controls with the workspace-sizing-only changes stayed bounded for 300 requests, which implicates FULL graph behavior or the additional `FULL_AND_PIECEWISE` allocation footprint rather than EAGER execution.

The fix has three parts:

- Carry `vllm_config` in `ForwardContext`, so ROCm paged-MQA helpers can still derive `max_num_seqs` and speculative token count when `get_current_vllm_config()` is unavailable.
- Keep startup/profile/capture allocation behavior unchanged, then disable PyTorch expandable segments once after ROCm gfx1151 warmup when an expandable-segments allocator env was initially enabled.
- Add a conservative post-collective synchronization guard after generic device collectives only when the steady-state allocator transition has been applied.

On current upstream, the paged-MQA runtime path already requests live decode rows, but the profiling/capture path can still lose config visibility and reserve for `max_num_batched_tokens`. In the baseline comparison this was visible as:

```text
baseline: PAGED_MQA_RESERVE shape=[9216,25000], storage_nbytes=921600000
this PR / previous workaround: PAGED_MQA_RESERVE shape=[6,25000]
```

The collective guard is intentionally conservative. It is retained from the validated workaround as an RCCL/collective completion safety guard after the allocator transition. It no longer temporarily re-enables expandable segments around collectives.
