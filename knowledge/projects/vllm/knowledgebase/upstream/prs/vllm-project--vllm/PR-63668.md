# [Bugfix][Frontend] Bound incremental detokenization cost on malformed UTF-8 output

[Upstream PR](https://github.com/vllm-project/vllm/pull/63668) · state: open · merged: False

## Original PR description



## Overview

Both incremental detokenizers hold tokens back while the decoded text ends in an incomplete UTF-8 sequence and re-decode the whole held-back run on every step. A model emitting byte tokens that never complete a code point (garbage output) therefore costs O(n²) per request and blocks the API-server event loop (`/health` hangs, every stream stalls). Cap the held-back run at `MAX_PENDING_TOKENS = 16` tokens and flush it as replacement characters. Fixes #63667.

## Claims

- Per-token detokenization cost no longer grows with the length of a malformed run: 8 000 garbage tokens take 0.02 s (fast) / 0.09 s (slow) instead of 5.7 s, and 20 000 take 0.06 s / 0.23 s instead of 35.7 s / 35.2 s.
- Replacement characters are streamed while the run is in progress instead of being withheld until a valid character arrives; the final text equals a full `decode()` of the same ids, including the whitespace of the text that follows the run.
- Well-formed output is unaffected: a code point spans at most 4 byte tokens, so the cap is never reached by valid text.

## Details

**Root cause.** `tokenizers.DecodeStream.step()` keeps every token since the last emitted text and re-decodes that slice each step while the result ends with `�` (`step_decode_stream`, `tokenizers/src/tokenizer/mod.rs`). `detokenize_incrementally()` does the same with its `prefix_offset`/`read_offset` window (`if ... new_text.endswith("�"): return ... prefix_offset, read_offset`). Neither bounds the window, and `OutputProcessor.process_outputs` runs on the event loop.

**Fix.**
- `MAX_PENDING_TOKENS = 16` in `vllm/tokenizers/detokenizer_utils.py` (a UTF-8 code point is at most 4 byte tokens; the margin covers runs of skipped special tokens).
- Slow path: when the window reaches the cap, fall through to the normal advance branch, which emits the `�` text and moves the offsets. Spacing context is preserved by the existing prefix window.
- Fast path: `FastIncrementalDetokenizer` counts held-back ids (`step()` returned `None`). At the cap it decodes them once, emits the text, and restarts `DecodeStream` primed with the ≤4 tokens behind the last rendered text (`_context_ids`, initially the prompt tail) so the next token decodes in the same context as an unbroken stream (SentencePiece strips a leading space only at the start of a decode). A primed prefix that itself ends in `�` is ignored by `DecodeStream` and would be re-emitted, so such a context is dropped (covered by the second test). The existing invalid-prefix reset (#17448) is left as is, only clearing the counter.

**Trade-offs / limitations.**
- With no prompt and no previously rendered text, the restarted fast stream has no context, so a space directly after a malformed run can be lost (`"world"` instead of `" world"`); that is the same behaviour as the existing #17448 reset. Real requests have a prompt, which the first test exercises.
- Text emitted for a flushed run is `tokenizer.decode(run)`, i.e. the replacement characters a full decode produces; nothing else changes for well-formed output.
- Not touched: the prompt-priming cost of `DecodeStream` (#51281, #57330) and prompts ending mid-UTF-8 (#48854). All three are orthogonal and touch the same constructor lines, so expect trivial rebases.

**Not a duplicate.** Searched issues/PRs for "detokenizer quadratic", "DecodeStream", "replacement character stall", "detokenize_incrementally", "byte fallback slow": #51281 and #57330 cap prompt-priming work (per-request O(prompt), not per-token growth); #48854 routes prompts ending mid-UTF-8 to the slow path; #46723 is the Rust frontend. None bounds the held-back run.
