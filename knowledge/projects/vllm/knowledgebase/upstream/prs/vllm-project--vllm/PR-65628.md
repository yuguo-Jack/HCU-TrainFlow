# [ROCm][Perf][Qwen4Exp] Opt-in INT4 QuickReduce for the --enable-hc-sp collectives

[Upstream PR](https://github.com/vllm-project/vllm/pull/65628) · state: open · merged: False

## Original PR description

## Overview

Opt-in `--enable-hc-sp-quick-reduce` (ROCm, default off) runs the four sequence-parallel collectives of the Qwen4Exp decoder layer under `--enable-hc-sp` through AITER's FlyDSL INT4 QuickReduce (`QuickAllReduceInt4.reduce_scatter` / `all_gather`) instead of RCCL bf16. Depends on ROCm/aiter#7444 (adds those methods) and on #65407, without which `--enable-hc-sp` does not compile on the AMD path; MTP serving also needs #65475.

## Claims

- On this branch: 34 CPU unit tests (in `test_quick_all_reduce.py`) and 16 config / argument-parser tests (9 of them new) pass; on 2 GPUs `test_sp_quick_reduce.py` passes 7 of 7.
- Experiment, not this branch (internal vLLM build, `amd/Qwen3.8-Flash-Next-Quark-MXFP4`, TP2, 2x MI355X): `--enable-hc-sp` with RCCL bf16 collectives loses 13.2 / 13.6 / 14.7 % output throughput at c16 / c32 / c64 against the same server without it; with INT4 reduce-scatter and all-gather (HIP kernels outside AITER) it gains 2.2 / 2.7 / 3.0 %. GSM8K (n = 1 per arm; the INT4 all-reduce, `VLLM_ROCM_QUICK_REDUCE_QUANTIZATION=INT4`, is on in the control, layout-only and HIP-hook arms): 95.38 / 95.53 % strict / flexible with the HIP hook against 94.84 % without it; 94.996 / 95.15 % with the FlyDSL kernels of the AITER PR, 0.38 points below the HIP hook (paired SE 0.5).
- Not measured on this branch: end-to-end throughput and accuracy (it needs #65407 to start at all).

Normalized MSE of the INT4 collectives, printed by a script that wraps the test's `_nmse` (an earlier run: flydsl 0.4.0, AITER files before their review edits): reduce-scatter against the exact fp32 all-reduce 6.0e-3 at 1,024 / 1,030 / 1,032 rows per rank, all-gather against the exact gather 6.0e-3. With the min-size gate forced to 1 GB both INT4 cases fail on the floor (3.2e-6 and 0.0), so an exact fallback cannot pass them. One run per case, not on the CI image. The test also bounds each row's error (0.1): two mutants that lose one row of the padded path pass the all-rows band and fail this bound (a lost row gives 1.0). A layer test lowers the size gate and counts the FlyDSL launches at the four sites (2 reduce-scatter, 2 all-gather); with the gate lowered, a second check runs full tensors of 5, 15 and 25 tiles, and the main checks include blocks of an odd number of half tiles (2,080 rows: 325 tiles), which aiter's own op test does not cover.

CI: the 2-GPU file joins `:amd: (MI355) Qwen4 Exp SP` (runs on PRs); the CPU tests extend `tests/distributed/test_quick_all_reduce.py`, which `:amd: (MI355) Distributed Features` runs (optional: nightly or manual), in `test_areas/` and in the legacy `test-amd.yaml`; `check_test_tethering.py --all` reports neither as untethered. The 2-GPU test skips on an AITER without the three methods, so on PRs it exercises the path only once the image's AITER has them.

## Details

- The methods live on `QuickAllReduce`, which already owns the FlyDSL INT4 object, its inbox and its JIT warm-up. The flag is `ParallelConfig.enable_hc_sp_quick_reduce`; config validation rejects it off ROCm, without HC sequence parallelism (`--enable-hc-sp`, or MoE SP, which also turns HC SP on and is untested here), at TP other than 2 (TP=1 ignores it, like `--enable-hc-sp`), with DBO, and without `VLLM_ROCM_QUICK_REDUCE_QUANTIZATION=INT4`. With INT4 set, the TP all-reduces were already INT4-compressed; `--enable-hc-sp` removes them, and this flag restores compressed collectives. The new lossy stage is the all-gather of post-norm activations. What config cannot know (gfx950 via `get_cdna_version()`, `VLLM_ROCM_USE_AITER=1`, custom all-reduce, an AITER with `reduce_scatter`, `all_gather` and `compile_sp`) is checked when the decoder layer is built: one warning per process, and the collectives stay exact. `compile_sp` runs on every rank at init, keeping the JIT out of the first prefill and of CUDA graph capture.
- Eligibility is decided from shapes and dtype only, so all ranks agree: bf16, 2-D, contiguous, the full tensor inside the QuickReduce size gates (built-in minimum 8 MB for bf16 TP2 INT4; decode-sized steps stay on RCCL). A misaligned view (the kernels need 16-byte alignment) is copied, not declined: a pointer-dependent decision could differ between ranks and hang the launch. Blocks are zero-padded to the fewest rows that make the full tensor a whole number of the kernels' 32 KiB tiles (a multiple of 16 rows at hidden 2560) and unpadded again: an extra copy, not measured.
- The pair is registered as opaque custom ops, because the launch is a Python call into AITER and the decision depends on the token count. The embedding shard, LM-head gather and PLE sites stay exact. Scope: with MoE sequence parallelism the MLP pair is skipped, so two sites switch; the MTP draft builds the same decoder layer, so it switches too (draft acceptance with the flag on is not measured).
- About 272 added non-test lines; nothing changes when the flag is off.

Limits: validated on TP2 and gfx950 only (the code gates gfx950; gfx942 stays exact). The INT4 codec is lossy: AITER restores values up to +-480 (divisor 1 in these collectives), the accuracy evidence is GSM8K on one model, and the INT4 all-gather of post-norm activations is a new lossy stage.

Duplicates (searched 2026-11-03): no open PR changes the two SP helper files. #64428 (the same opt-in pattern for another collective, the DP MoE combine, `VLLM_ROCM_DP_MOE_QUICK_REDUCE`), #57547 and #61021 (fused add-RMSNorm), #63226 and the 58-file draft #64243 touch the same files.
