# [Perf] Cache get_sm_version_num() in cutlass dispatch

[Upstream PR](https://github.com/vllm-project/vllm/pull/40163) · state: closed · merged: False

## Original PR description

## Summary

Cache the result of `get_sm_version_num()` instead of querying
`cudaDeviceGetAttribute(..., 0)` on every call.

## Motivation

The previous implementation queried the compute capability of device 0
on every invocation. This function sits on the hot path of several
quantized CUTLASS entry points, including `cutlass_scaled_mm`.

Since the prior implementation already hard-coded device 0, this PR
preserves existing semantics by caching that same device-0 result once,
rather than introducing new per-device behavior.

## Expected impact

This is a small perf cleanup that removes repeated device-attribute
queries from the dispatch hot path. It is not intended to fully resolve
small-M decode regressions by itself, but it should reduce a small amount
of fixed per-call CPU overhead across all call sites that use
`get_sm_version_num()`.

## Validation

I spot-checked the same small-M decode-side benchmark shapes I had been
using for the original investigation.

The results are somewhat noisy run-to-run, but the qualitative pattern is
unchanged. This is expected because this PR only removes one small repeated
dispatch-side cost (`get_sm_version_num()`), rather than addressing the
larger structural overhead in the generic small-M `scaled_mm` path.

semantic change and should be handled independently.

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Validate attribute queries before caching SM version**

The new static cache makes the first `cudaDeviceGetAttribute` result permanent, but these calls still ignore their return status. If the first invocation happens while CUDA is in an error state (for example after an earlier async launch failure), `major_capability`/`minor_capability` may be left unset and that bogus SM value is then cached for the lifetime of the process, causing all later CUTLASS dispatch decisions to use the wrong architecture. Before storing `cached`, check both return codes (or use the project’s CUDA error-check macro) and fail/retry instead of caching unchecked data.

- gemini-code-assist[bot] · comment · 2026-04-17T16:13:34Z · [source](https://github.com/vllm-project/vllm/pull/40163#discussion_r3101702773)

File: `csrc/cutlass_extensions/common.cpp` · line None

![high](https://www.gstatic.com/codereviewagent/high-priority.svg)

The variables `major_capability` and `minor_capability` are declared but not initialized. If `cudaDeviceGetAttribute` fails for any reason (e.g., if device 0 is inaccessible or the driver is in an error state), these variables will retain indeterminate values. The subsequent calculation `major_capability * 10 + minor_capability` would then result in undefined behavior. Since this value is stored in a `static` variable, the corrupted SM version would be cached for the entire lifetime of the process, potentially causing incorrect kernel dispatching or crashes. Initializing these to 0 ensures that a failure results in a safe SM version of 0, which is correctly handled as an unsupported architecture by the callers.

```suggestion
    int32_t major_capability = 0, minor_capability = 0;
```
