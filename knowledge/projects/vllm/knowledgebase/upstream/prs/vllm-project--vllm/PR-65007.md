# [Perf][Spec Decode] Vocab-parallel DSpark Markov sampling and vocab-sharded verification over TP

[Upstream PR](https://github.com/vllm-project/vllm/pull/65007) · state: open · merged: False

## Original PR description

## Overview

With tensor parallelism, DSpark speculative decoding repeats full-vocabulary work on every TP rank, twice per decode step: the drafter's sequential Markov sampling loop, and the target's verification (an all-gather of the target logits, then temperature, top-p and the rejection sampler over the whole vocabulary). This PR splits both by vocabulary across the TP ranks. It has two parts, each behind its own opt-in flag (both off by default):

1. **Vocab-parallel DSpark Markov sampling** (`speculative_config.dspark_tp_markov_sampling`, experimental): each rank runs the Markov loop on its share of the vocabulary and the ranks exchange per-block maxima.
2. **Vocab-sharded verification** (`speculative_config.vocab_sharded_verification`): each rank verifies on its own vocabulary blocks, without gathering the target logits, and with part 1 on, the drafter also works only on those blocks.

They ship together because they share the exchange machinery: symmetric-memory tagged words with never-zero tags that the reader clears, a bounded spin with a timeout flag in pinned host memory, and a setup fallback that all ranks agree on. Also, the draft side of part 2 is part 1's Markov loop restricted to the ranks' owned columns.

### Part 1: vocab-parallel DSpark Markov sampling

DSpark drafts a block of `num_speculative_tokens` tokens with a parallel backbone pass, then runs a sequential Markov loop. Each of the loop's steps adds a Markov bias, from the previously sampled token, to the base draft logits and Gumbel-samples the next token. With tensor parallelism the loop runs **replicated** on every TP rank. Each step:

- reads the whole `markov_w2` projection (`[draft_vocab, markov_rank]` bf16, 102 MB for a 200k vocabulary) to compute a few rows of bias;
- Gumbel-samples the full vocabulary.

Both are memory bound, and every rank does the full work. For MiniMax-M3.1 Flash (K=7) the loop is 150–570 µs per decode step at concurrency 1–32 on GB300, on the draft's critical path.

With `dspark_tp_markov_sampling`, each TP rank owns a contiguous range of the sampler's 1024-column blocks and, per step:

1. computes the bias of its columns only, from a row slice of `markov_w2` (1/TP of the weight traffic);
2. Gumbel-samples its blocks, with the noise keys the replicated loop uses (`gumbel_noised_argmax`, `spec_step_seed`);
3. publishes one 8-byte word per block, `[block max (fp32) | 22-bit tag | 10-bit index in the block]`, to every rank through torch symmetric memory. Each word carries its own tag, so no fence or flag is needed (NCCL's LL protocol). Tags are never 0, and the reader clears each word it consumes, so a slot holds either nothing or the current step's word and a stale word can never be taken for a fresh one. A sys-scope release/acquire flag variant and an NCCL all-gather were both slower than the replicated loop.
4. Every rank picks the winner as the replicated loop does: the first NaN block, otherwise the first maximum.

The block maxima are the values the replicated loop computes, so the drafted tokens are the same.

The rejection sampler reads the draft-logits cache at full vocabulary on every rank (unless part 2 is on, see below). Each rank writes its own columns while sampling, and the rest is completed in one of two ways:

- **≤ 4 requests:** while sampling, ranks also push their biased logits to their peers' staging buffers, two bf16 per tagged 8-byte word, and one kernel unpacks them after the loop.
- **More requests:** every rank recomputes the peers' columns for all steps at once, from the sampled tokens, projecting only the peers' rows of `markov_w2` (left and right of its own). This reads them once per draft step instead of once per Markov step. Pushing a whole cache would cost more NVLink time than it saves.

**Exactness guard.** The sliced and batched projections must equal the replicated loop's projection bitwise. cuBLAS gives that for 64-aligned vocabularies, but not for odd ones (e.g. 50017), where it picks different kernels. So at load time the speculator checks it on the real weight against the real `model.markov_bias` (logits processor and GEMM dispatch included), for every batch size up to 128, and all TP ranks agree on the result (0.42 s and a 367 MiB transient peak per rank for M3.1 Flash at TP4). If any size differs, or the configuration is unsupported, the replicated loop runs. Unsupported configurations are:

- greedy drafting, top-k drafting, a reduced draft vocabulary, batch-sharded draft logits;
- watermarking, adaptive verification, fp64 Gumbel, a model-specific `sample_sequential`;
- a scaled or soft-capped logits processor, a quantized or skinny-GEMM `markov_w2`, TP = 1, non-CUDA.

Batches above 128 requests also run the replicated loop.

### Part 2: vocab-sharded verification

With a vocab-parallel LM head, verification all-gathers the target logits, so every TP rank holds `[num_logits, vocab]` and applies temperature, top-p and the rejection sampler over the whole vocabulary: the same work on every rank. With probabilistic drafting the drafter does the same with its own logits: an all-gather per draft step, and a full-vocabulary draft-logits cache on every rank.

With `vocab_sharded_verification`, each TP rank owns whole 8192-column blocks of the vocabulary (the rejection sampler's statistics blocks, split as evenly as possible) and works on those only:

- **Target logits:** the rank's own lm_head shard, plus the few columns of its owned range that sit in the right neighbour's shard, which that neighbour pushes. Nothing is all-gathered.
- **Temperature and top-p:** on the owned columns. Top-p is an exact select run jointly by all ranks: the smallest prefix (by logit, then token id) whose probability mass reaches `p`, plus the row max. Masses are summed in 64-bit fixed point, so every rank, and every run, gets the same kept set. Greedy rows do not trigger it.
- **Rejection sampling:** the rejection sampler's per-block kernels run on the owned blocks only (they now take a block offset and a column offset); the per-block partials are exchanged and the per-request kernels combine all blocks in the stock order. The drafted tokens' target and draft logits come from their owners. Given the same processed logits, the result is bitwise the stock one.
- **Drafting (DSpark with `dspark_tp_markov_sampling`):** the draft logits are computed the same way (own shard + right neighbour's columns), part 1's Markov loop runs on the same owned ranges, and only the owned columns of the draft-logits cache are written, since verification reads only those.

All exchanges are small (per-block partials, per-row histograms, the boundary columns) and use part 1's tagged-word scheme. Each verification step uses its own tag epoch and alternates between two buffer halves. The sharded verification kernels are compiled at load, collectively on every rank, so that no rank compiles while its peers wait on an exchange. The warmup runs one step per kernel variant that serving can launch: for each top-p tie-split count, a row count that is a multiple of 16 and one that is not (`warmup_num_logits`, commit 946ffe554e). Verified: no vocab-shard Triton compiles after load in a c32 serving smoke, and the unit tests pass.

Steps with requests that need the full vocabulary (logprobs, top-k, min_p, logits processors or a thinking budget, structured output) take the stock path. Before such a step, the cached draft logits of its requests are completed with an all-gather, bounded to 64 MiB per chunk.

### Opt-in, flags and fallbacks

Both options are off by default and change nothing unless set.

| flag | falls back (logged on every rank alike) to | when |
|---|---|---|
| `dspark_tp_markov_sampling` | the replicated Markov loop | the exactness guard fails; a configuration listed under part 1; batches above 128 requests; symmetric memory unavailable |
| `vocab_sharded_verification` | gathered verification, as today | no probabilistic drafting; watermarking, FLy, adaptive verification, batch-sharded sampling, prefill context parallelism, a custom rejection sampler, `VLLM_COMPUTE_NANS_IN_LOGITS`, sampling masks or trace replay; a target model without `compute_logits_local`; a draft-logits cache narrower than the target vocabulary; symmetric memory unavailable |
| `vocab_sharded_verification`, per step | gathered verification for that step | a request in the batch needs the full vocabulary (above) |
| both, draft side | part 1's loop on full-vocabulary columns | the draft model or vocabulary does not support owned columns |

**Failure handling** (both parts):
- If symmetric memory cannot be allocated or rendezvoused on any rank (no P2P, multi-node TP, a torch build without it), every rank logs the reason and falls back. Each setup step is agreed across ranks first, so no rank waits in a collective for a peer that failed.
- An exchange that waits more than about 2 s for a peer stops spinning and sets a flag in pinned host memory. The next step reads the flag without a sync and raises, instead of producing tokens from incomplete data.

## Claims

**Part 1 (vocab-parallel Markov sampling)**

- **Same tokens and the same draft-logits cache, bitwise.** On MiniMax-M3.1 Flash's real draft model (TP4, GB300), the replicated loop and this loop were run from identical draft metadata. The metadata includes a padding request, a greedy request and a temperature-0.7 request. The drafted tokens and the entire draft-logits cache match on all 4 ranks at B = 1, 2, 4, 8, 16, 32, 64, 96 and 128, in both completion modes, with 0 exchange timeouts.

  | 32 | 705 | 600 |
  | 64 | 1156 | 995 |

  The review changes do not cost loop time. Against the first revision on the same node, run ABAB: B1 232 → 233, B32 601 → 600, B64 998 → 995, B128 1759 → 1759.
- **Draft CUDA graph per decode step in serving:** −61 µs at concurrency 1, −35 to −42 µs at 8, −128 to −133 µs at 32 (Validation).
- **Memory:** about 43 MiB of symmetric memory per rank, allocated and zeroed once at load: push staging for 4 requests, `2 · TP · 4 · K · ⌈blocks/TP⌉ · 512 · 8 B` (42.9 MiB at TP2/TP4, 43.8 MiB at TP8 for V = 200064, K = 7), plus 0.4 MiB of block words for 128 requests.

**Part 2 (vocab-sharded verification)**

- **Same tokens:** for the same processed logits, the sampled tokens and counts equal the full-vocabulary rejection sampler's (block, standard and synthetic modes). Drafting on owned columns draws the same tokens as part 1's loop.
- **Exact, deterministic top-p:** the kept set is the float64-exact one except within fp32 rounding of `p` at the boundary (on real logits: 4 of 3611 rows, one tied token each); never a superset.
- **Faster from 8 requests up** (MiniMax-M3.1 Flash, TP4, DSpark K=7, GB300; base = the same build with part 1 on and gathered verification). On the final revision, step period **−6.3% at concurrency 16** (15.62 → 14.63 ms) and **−6.7% at concurrency 32** (18.82 → 17.56 ms). Time per decode step outside the target model's CUDA graph (step period − target graph span; the target graph itself is unchanged):

  | concurrency | base | this PR | change |
  |---|---|---|---|
  | 1 | 964 µs | 985 µs | +21 µs |
  | 8 | 1523 µs | 1243 µs | −280 µs |
  | 16 | 2297 µs | 1398 µs | −900 µs |
  | 32 | 2955 µs | 1695 µs | −1260 µs |

  c16 / c32: final revision, two runs per arm. c1 / c8: first revision (the review changes kept the c16 / c32 gain within noise of the first revision's −882 / −1210 µs).
- At concurrency 1 the exchanges' latency outweighs the work saved (verification 325 → 377 µs, drafting 591 → 565 µs).
- **Memory:** one symmetric buffer per rank, allocated at load (before the KV cache is sized), proportional to `max_num_seqs`: 253 MiB at TP4, K = 7, V = 200064, `max_num_seqs` 256, plus 50 MiB on the draft side (sized for the Markov sampler's 128-request limit).

**Accuracy:** GSM8K unchanged within noise with both options on (Validation).

## Details

- **Integration with `main` (8530a778f7):**
  - `dspark_tp_markov_sampling` is a method-specific option: it is listed in `_METHOD_SPECIFIC_OPTIONS` and in `DSparkSpeculatorConfig.supported_options`. Its type is `bool | None` (unset means off), so the generic option check rejects it for other methods only when it is set.
  - `vocab_sharded_verification` is a plain `SpeculativeConfig` field; it is a property of verification, not of a drafting method.
  - `DSparkSpeculator.load_model` calls `_try_enable_tp_markov_sampling` when only part 1 is on. With part 2 also on, the runner decides verification first and then calls `enable_vocab_sharded_drafting(shard_or_None)`, which builds exactly one Markov sampler (owned-columns or plain).
- **Commits:**
  - f8d461a2ad: part 1;
  - eddf09a8ac, db489e9491, f2ffea69db: part 1 review changes (agreed symmetric-memory fallback, surfaced timeouts, never-zero 22-bit tags with consume-and-clear, the guard against `model.markov_bias`, the skinny-GEMM exclusion, peers-only recompute; tests on the real sampling path and the CI step; the timeout flag in pinned host memory);
  - 0ae150c7e0: part 2;
  - 41a2302734, 54030bb072, 9741123d3b: part 2 review changes (agreed fallback via `VocabShard.create`, load-time eligibility and collective warmup, `do_not_specialize` on per-step scalars, never-zero tags with consume-and-clear, bounded completion chunks, tighter buffer sizing, CI step and tests; the timeout flag in pinned host memory).
  - 946ffe554e: the load-time warmup covers every kernel variant serving can launch (the top-p tie kernels' split count and the exchange strides' divisibility by 16), with a test that every step size is covered.
- **Code map (part 2):**
  - `vllm/v1/worker/gpu/spec_decode/vocab_shard.py` (new): ownership, the exchanges, the owned-logits assembly and the sharded top-p.
  - `rejection_sampler_utils.py`: `rejection_sample(..., vocab_shard=...)`; the stats, residual-mass and resample kernels take `block_start` / `target_col_start`, and the logprob helper optionally reads the drafted token's logits from a small array. Stock calls pass 0 / None.
  - `RejectionSampler.supports_vocab_sharding` / `vocab_sharding_unsupported_reason` / `warmup_vocab_sharded` / `verify_vocab_sharded`; `Sampler.needs_full_vocab` (per request); `GPUModelRunner.sample` takes the sharded path when eligible.
  - DSpark: `TPMarkovSampler.create(speculator, owned_ranges)`, `DSparkSpeculator.enable_vocab_sharded_drafting` / `complete_draft_logits`.
- **Validation scope:** the measurements ran on the MiniMax-M3.1 Flash day-0 image with this PR's files, adapted to that image's API where `main` differs. The A/B serving runs of each part had the same unrelated MiniMax-M3 model changes in both arms; the final GSM8K run above compares the stock image with only this PR's files. The option wiring for `main`'s per-method speculator config has not run end to end on `main`, which has no MiniMax-M3.1 NVIDIA model path.
- **Related:** batch-sharded sampling (`enable_batch_sharded_sampling`) splits the batch across ranks instead of the vocabulary. It is exclusive with both options here: part 1 is ignored when batch-sharded draft logits are in use, part 2 when batch-sharded sampling is on. Part 2's verification side works with any probabilistic drafter whose draft-logits cache is replicated; only its draft side is DSpark-specific.

**14-bit tag aliasing.** Freshness is `tag == e & 0x3FFF`. A (row, block) word is refreshed only while that row is active, so a slot not written for a multiple of 16384 epochs (about 2340 draft steps at K=7, i.e. seconds at serving rates) and then read again has the expected tag and is accepted without waiting.

- The zero-initialised buffer: at epoch 16384 the tag is 0, so any never-written word passes immediately ("Tags never match a zeroed word: the first epoch is 1" holds only for the first 16383 epochs).
- Concurrency drops below row r, stays there for exactly 16384*k epochs (same parity slot), then rises: row r's old words (tag from epoch e-16384k) are read as fresh before the peers' writes land, so a token and max from a past draw are used.

The combine kernel (L192) has the same check. The push path avoids this with the full 32-bit epoch.

The word is full (32 value + 14 tag + 18 token), but the block index is implied by the word's position, so only the 10-bit in-block index needs storing. That frees 8 bits for a 22-bit tag, and removes the 2^18 vocabulary limit.

Fair question. Here are the numbers, so maintainers can weigh it.

**Scope.** The option is opt-in, default off, and now marked *Experimental* in its docstring. With it off, nothing changes on the shared decode path: `_sample_sequential` gains one `is not None` check, and `propose` one more. With it on, unsupported configurations and inexact GEMMs fall back to the replicated loop on every rank alike, a failed symmetric-memory setup falls back, and a peer timeout raises instead of drifting. The other comments' failure modes (aliasing, silent timeouts, dispatch drift) are fixed and tested in this revision (eddf09a8ac, db489e9491, f2ffea69db).

**What it saves (MiniMax-M3.1 Flash, TP4, K=7, GB300).**

- Markov loop, graph-timed on the real draft model (replicated → vocab-parallel, µs): B1 291 → 233, B4 371 → 315, B8 440 → 389, B16 563 → 509, B32 705 → 600, B64 1156 → 995, B128 2010 → 1759. That saves 51–251 µs, or 10–20% of the loop. The absolute saving grows with batch size, because the replicated loop's cost scales with B at full vocabulary on every rank.
- Serving (seeded, same node, nsys; draft CUDA graph p50 per step, µs): concurrency 1: 646 → 586, concurrency 8: 917 → 875–882, concurrency 32: 1368 → 1235–1240. That saves 61, 35–42 and 128–133 µs per step. The whole step is 6.8, 13.4 and 19.7 ms, so this is 0.3–0.9% of the step, as in the original table.

**Why this design.** A plain NCCL all-gather of the per-block maxima, and a sys-scope flag variant, were both slower than the replicated loop at these sizes (the exchange is about 1.5 KB per row per step, so latency is everything). That is why the exchange uses tagged LL words over symmetric memory. The exchange and sampler are also meant as the base of a planned follow-up (vocab-sharded verification), which would reuse `TPMarkovSampler` to draft on each rank's owned columns.

If the maintainers prefer not to carry an LL protocol in `spec_decode/dspark/` for a sub-1% step gain on its own, I'm fine keeping it out of tree until the follow-up shows the larger combined effect. Let me know which you prefer.
