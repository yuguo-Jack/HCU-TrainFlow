# [ROCm][Perf] Support all-reduce + RMSNorm above the custom-all-reduce pool

[Upstream PR](https://github.com/vllm-project/vllm/pull/57547) · state: open · merged: False

## Original PR description


<!-- markdownlint-disable -->

## Overview

Fuse all-reduce + RMSNorm with AITER's QuickReduce kernel up to the QuickReduce workspace (2 GiB) instead of the 64 MiB custom-all-reduce pool, and repair the QuickReduce handshake that has been failing silently since AITER 0.1.19.post1 (the pin is 0.1.24.post1). Follows #48249 and #58547. Only applies when `VLLM_ROCM_QUICK_REDUCE_QUANTIZATION` is not `NONE` (the default is `NONE`).

Not a duplicate: searched open PRs for "allreduce rmsnorm ceiling quickreduce" and "AITER AR+RMSNorm fusion max_token_num". #55347 changes `effective_max_size()` for `AITER_CUSTOM_AR_MAX_SIZE`; this PR builds on that function and the two compose.

## Claims

- At hidden 4096 in bf16 the default 16384-token prefill chunk (128 MiB) now fuses AR + RMSNorm. Before, fusion stopped at 8192 tokens (the pool).
- The fused QuickReduce + RMSNorm kernel now actually runs on current AITER. On main its communicator never comes up, so it never ran, inside or above the pool.
- Qwen3.5-397B-A17B MXFP4, TP2, MI355X: output throughput +0.7% to +5.8% in 12 of 12 cases, mean TTFT lower in 11 of 12 (one run per case).
- Cost: GSM8K -2.1 to -3.0 pp with QuickReduce at INT4. In-pool all-reduces move from an exact bf16 all-reduce to the INT4 codec. With QuickReduce off nothing changes.

## Details

**Before.** `RocmAiterAllReduceFusionPass` gated on the custom-all-reduce IPC pool (`effective_max_size()`, 64 MiB). The fused QuickReduce + RMSNorm kernel stages through the QuickReduce workspace instead. So a 16384-token chunk at hidden 4096 (128 MiB) ran a separate QuickReduce all-reduce and RMSNorm. Separately, `_get_or_create_aiter_qr_rmsnorm_comm` called `aiter.qr_get_handle(ptr)`. Since ROCm/aiter#4421 that function takes an output pointer, so the call raised, the `except` swallowed it, and the fused kernel was never reachable.

**After.**

1. `AiterCustomAllreduce.fused_rms_max_size()` returns `max(pool, qr_comm.qr_max_size)` where the fused kernel can run (QuickReduce up, bf16/fp16, a row that divides the 32 KiB tile), and the pool otherwise. `qr_rmsnorm_supports_row()` is the one predicate behind that and the runtime dispatch gate, so the compile ceiling cannot promise a kernel that dispatch then declines. The vLLM and AITER communicators are sized from the same `VLLM_ROCM_QUICK_REDUCE_MAX_SIZE_BYTES_MB`.
2. The per-group-FP8-quant variants lower to custom-AR kernels with no QuickReduce path, so they move to their own `PatternMatcherPass`, applied only for compile ranges within the pool. `VllmConfig` already puts a compile-range boundary at the pool, so a range is either fully inside or fully above it. The quant matcher runs first, as before, so the AR+RMS-only patterns cannot consume the `all_reduce` it needs.
3. The handshake goes through AITER's `qr_exchange_handles`, imported unconditionally (every release since 0.1.19.post1 has it). A failure to create the communicator now logs once instead of passing silently.

The unfused fallback and the Gemma gate this PR originally carried are now on main from #58547, and were dropped in the rebase.

**Why the accuracy drops.** Inside the pool, main's fused AR+RMSNorm falls back to AITER's custom-AR kernel, an exact bf16 all-reduce. With the handshake fixed, the same sites go through QuickReduce INT4. So the drop is the cost of the INT4 codec at those sites. The A/B does not separate the handshake fix from the ceiling lift, and both add INT4 sites. Measured against an fp32 reference at TP2, the fused kernel's error (8.150e-2 at INT4) matches the same codec unfused (8.152e-2), is flat from 256 to 32768 tokens, and compares with 2.96e-3 for an exact bf16 all-reduce. A user who sets `VLLM_ROCM_QUICK_REDUCE_QUANTIZATION=INT4` already gets this codec on every all-reduce above its minimum size when the fusion pass is off.

**Shared code.** `VllmFusionPatternMatcherPass.register` gains an optional `pm_pass` argument; the default is the old behaviour. Nothing changes on CUDA. Net non-test change is about 100 added lines.

**Limitations and CI gaps.**

- Accuracy was measured at INT4 only. A GSM8K arm at `FP` or `INT8`, and an arm with the fusion pass off at INT4, would separate the codec from the fusion. Neither has been run.
- TP2 only, gfx950 only. QuickReduce also supports gfx942 and TP4/8, which are not exercised.
- No NIAH, although the change targets prefill all-reduce.
- One run per case in the sweep.
- Kernel counts and the sweep were measured before the rebase, on older nightlies. The code they exercise is unchanged by the rebase, but the numbers are not re-measured on a current nightly.
- On gfx950 QuickReduce's bf16 to fp16 cast does not guard against overflow, so an activation above 65504 zeroes its token's row. This is shared with the unfused QuickReduce path and is not changed here.
- The 2-GPU pass test is covered by CI only through the MI355 mirror of "Fusion and Compile FP8".
