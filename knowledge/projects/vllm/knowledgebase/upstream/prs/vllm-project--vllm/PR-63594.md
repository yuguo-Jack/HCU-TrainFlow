# [Bugfix][Frontend] Probe non-jinja renderers for inline system message support (Anthropic API)

[Upstream PR](https://github.com/vllm-project/vllm/pull/63594) · state: closed · merged: True

## Original PR description



## Overview

`/v1/messages` merges inline system messages into the leading system prompt for every renderer without a jinja template, so Claude Code's per-turn reminders invalidate the prefix cache on DeepSeek V4.1, Kimi K3 and Inkling. Probe the renderer instead of assuming. Fixes #60537.

Overlaps #58772 (draft, superset: same probe plus a fold mode), #56520 and #60555 (per-tokenizer flags). This is the probe on its own as a small fix that can land first; I'm coordinating with @bbrowning on #58772.

## Claims

- Non-jinja renderers keep inline system messages in place only when the renderer emits them as distinct system turns in order and a trailing one is still followed by the generation prompt; anything else merges as before.
- DeepSeek V4.1, Kimi K3, Inkling: now kept in place. DeepSeek V4 (appends system text to the user turn, #46710), V3.2 (trailing system lands after the generation prompt, #53737), Mistral (moves it into the user turn): still merged.
- No per-tokenizer registration. HF/jinja path unchanged.

## Validation

E2E: Claude Code-style tool loop (system reminder after each tool result) via `/v1/messages`, Inkling with dummy weights (2 layers, H100). `cache_read_input_tokens` per turn:

| turn | prompt | main | this PR |
|---|---|---|---|
| 1 | 1716 | 0 | 672 |
| 2 | 2756 | 640 | 1696 |
| 3 | 3796 | 640 | 2752 |
| 4 | 4836 | 672 | 3776 |

Main logs the "merged into the leading system prompt" warning at startup; this PR doesn't. A dummy 2-layer DeepSeek V4.1 didn't report prefix hits on either side (cross-layer KV sharing breaks under the layer override), so V4.1 is covered at the render level: each turn's prompt tokens are an exact extension of the previous turn's (371/371 ... 663/663 tokens reused).

New test fails on main, passes here:

```
pytest tests/entrypoints/anthropic/test_anthropic_messages_conversion.py -k test_probes_non_jinja_renderer
main:  FAILED [deepseek-ai/DeepSeek-V4.1-Flash-False] - assert True is False
here:  3 passed
```

Probe result through real renderers (`renderer_from_config`): V4-Flash merge, V4.1-Flash keep, V3.2-Exp merge, Kimi-K3 keep, Inkling keep, Pixtral (mistral) merge.

`tests/entrypoints/anthropic/`: 125 + 7 passed. pre-commit clean.

No model evals: prompt text for DeepSeek V4.1, Kimi K3 and Inkling changes (reminders render as system turns where the client sent them instead of in the leading system prompt).

## Details

`_should_merge_inline_system` previously only probed jinja templates; non-HF renderers had no template to probe and always merged. The probe renders `[sys, user, sys, user]`, the same with the inline system as user, and `[sys, user, sys]` through `renderer.render_messages`, once at startup. "Didn't raise" is not enough: V4 and V3.2 render without error but misplace the text.

- bbrowning · comment · 2026-10-28T12:39:42Z · [source](https://github.com/vllm-project/vllm/pull/63594#issuecomment-6469212497)

This looks like a reasonable win for the models that don't typically use chat templates. But, some of the models (like Cohere) can be run with a custom template. If we want this to work and not break that type of usage, we'd need to build the ChatParams more like something like the OnlineRenderer does to include the chat template and kwargs: https://github.com/vllm-project/vllm/blob/ab0e5ef7954190de2a74a6715d1382b08f5accc4/vllm/renderers/online_renderer.py#L214-L218

Otherwise I checked that DeepSeek v4.1, Kimi K3, Inkling, and Cohere all choose to keep inline system with this and render correctly (with the caveat about only correct when using no custom chat template with Cohere). And I checked that DeepSeek v4, DeepSeek v3.2, and Mistral models merge the inline system messages vs keep it separate.

One other small nit, that may or may not be worth fixing, is some models like DeepSeek v4.1 will attach tools to the first system, wherever that is. For typical usage with a harness like Claude Code that's not a problem as there is always an initial system message. But if someone is using their own client with tools but no custom system message, this could potentially end up with the tools attaching to a later mid conversation system message. That seems rare to me in practice, and something we could deal with later if it comes up in real usage.
