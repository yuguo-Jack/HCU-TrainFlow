# improve OOM error messages for low-VRAM scenarios

[Upstream PR](https://github.com/vllm-project/vllm/pull/50985) · state: open · merged: False

## Original PR description

## What this PR does
Improves two error messages that users encounter when running vLLM on
low-VRAM GPUs (e.g. 6GB laptop GPUs, WSL2 environments).

**Change 1: `vllm/v1/worker/utils.py`**
When `gpu_memory_utilization` is set too high, the error now includes
the computed maximum safe value based on actual free memory, so users
know exactly what value to use instead of guessing.

Before:
  "Decrease GPU memory utilization or reduce GPU memory used by other processes."

After:
  "The maximum safe value for your current free memory is 0.83
   (e.g. --gpu-memory-utilization 0.81). Decrease GPU memory
   utilization or reduce GPU memory used by other processes."

**Change 2: `vllm/v1/core/kv_cache_utils.py`**
When there is zero memory left for KV cache after loading model weights,
the previous message said "Try increasing gpu_memory_utilization" — which
is misleading because the model itself is too large and increasing
utilization would just trigger the error above. The new message explains
the real cause and suggests actionable alternatives.

## Why this is not a duplicate
Searched open issues and PRs. Related issues (#47292, #50261) address
the UVA/pinned-memory error on WSL2, not the error message quality for
these two OOM scenarios.

## Test
Verified both error messages manually on WSL2 with RTX 1000 Ada (6GB):
- Change 1: `--gpu-memory-utilization 0.95` on a 6GB GPU → new message
  shows suggested value 0.83
- Change 2: `Qwen2.5-3B` + `--gpu-memory-utilization 0.75` on 6GB GPU
  → new message shows actionable alternatives

- cadamcat · comment · 2026-08-30T20:58:37Z · [source](https://github.com/vllm-project/vllm/pull/50985#issuecomment-5471218129)

@YifanLi3 A data point for change 2, from a case where the new text's stated cause is not the cause.

One NVIDIA L4 (23034 MiB), vLLM 0.28.0, `--gpu-memory-utilization 0.95 --max-num-seqs 1`, two 4-bit models on the same card the same day:

```
gemma-4-31B  w4a16   Model loading took 18.7 GiB    Available KV cache memory: -0.8 GiB
        + --enforce-eager                           Available KV cache memory:  1.71 GiB  (2,020 tokens)

Qwen3.8-27B  int4    Model loading took 19.24 GiB   Available KV cache memory: -0.39 GiB
        + --enforce-eager                           Available KV cache memory: -0.34 GiB
```

For the first, **the model is not too large** — it serves, at 2,020 tokens of context. What put the budget below zero was the CUDA graphs, worth **2.51 GiB** here. None of the three suggestions reaches that: it is already a quantized checkpoint, so (1) is met, and (3) is already at 0.95. The lever that worked is `--enforce-eager`, and it is not on the list.

For the second the new text is right, and that is the difficulty — the same flag on the same card buys **0.05 GiB**, and 19.24 GiB of weights really do leave too little. Two cases one log line apart, wanting opposite advice.

So: a fourth item naming `--enforce-eager` (or a smaller capture set) would cover the first case. And the message may be able to tell them apart rather than guessing, since the profiler already estimates the graph footprint — #51590 is about making that estimate right — so it could say whether giving graphs up would cover the deficit.

Four serve logs, two per model: https://github.com/cadamcat/dual-radeon-vllm/tree/main/benchmarks/cuda-l4/campaign-2026-08-30c/logs
