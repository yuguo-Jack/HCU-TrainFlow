# [Rust Frontend] Report vllm-proto schema version in ServerInfo

[Upstream PR](https://github.com/vllm-project/vllm/pull/61533) · state: closed · merged: True

## Original PR description



## Overview

Report the gRPC schema version in `ServerInfo.proto_version` so clients can tell which request fields a server reads. Bump `vllm-proto` to 0.6.0 for the new field.

## Claims

- `Control.GetServerInfo` returns `proto_version`, set from the new `vllm_proto::VERSION` constant (the crate's `CARGO_PKG_VERSION`), so it cannot drift from the schema the server was built with.
- Servers that predate the field return an empty string (the proto3 default), so clients can treat empty as "older than 0.6.0" without probing.
- Wire-compatible addition. Rust callers that build `ServerInfo` with struct literals must add the field, hence 0.5.0 → 0.6.0.

## Validation

From `rust/`:

```sh
cargo test --locked -p vllm-server --lib -- --quiet
cargo clippy --locked -p vllm-proto -p vllm-server --all-targets
cargo publish --manifest-path proto/Cargo.toml --locked --dry-run
```

468 tests passed, clippy reported no warnings, and the dry run packaged `vllm-proto` 0.6.0. Scoped pre-commit checks passed for all changed files.

The existing `control_reports_server_and_model_info` test now checks the field over a real Tonic client/server pair. No real-model/GPU validation; the change is metadata only.

## Details

Proto3 drops unknown fields silently, and `api_version` is the constant `"vllm"`, so a client cannot tell whether a server honored a field it sent. Dynamo hit this while adopting 0.5.0 ([ai-dynamo/dynamo#15550](https://github.com/ai-dynamo/dynamo/pull/15550)): v0.31.x servers ignore `engine_reasoning_gate` and `thinking_token_budget`, and the client cannot detect that. `engine_version` is not a reliable substitute: the crate is versioned independently of vLLM releases, so clients would need a release-to-schema table, which cannot cover nightlies or backports (for example, v0.31.0 ships the 0.4 inference schema and `main` ships 0.5.0).

- **Why a new field instead of `api_version`:** existing clients compare `api_version` exactly against `"vllm"` and refuse to start otherwise; Dynamo's sidecar does this.
- **Field number 12:** the lowest unused number. Open PRs #56364, #56337, #52723 and #56421 also propose 12 or 13; whichever merges later renumbers.
- **Version vs capabilities:** the version tells clients which fields the server knows. Behavior that depends on server configuration, or that may be deprecated without a schema change, is better served by `supports_*` capability flags like those proposed in #56421. The two are complementary.
