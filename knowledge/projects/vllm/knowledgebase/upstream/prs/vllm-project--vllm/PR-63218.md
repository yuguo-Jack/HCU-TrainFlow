# [Bugfix] Default Nemotron Omni mamba_ssm_cache_dtype to float32

[Upstream PR](https://github.com/vllm-project/vllm/pull/63218) · state: closed · merged: True

## Original PR description



## Overview

Maps the three Nemotron Omni architecture aliases to the existing `NemotronHNanoVLV2Config` in `MODELS_CONFIG_MAP`. With this mapping, the NemotronH Mamba SSM-cache default from #39032 (float32, or the checkpoint's own value) applies to them instead of silently falling back to bf16.

Related PRs:
- #39032: NemotronH float32 default and the `NemotronH_Nano_VL_V2` hook.
- #52929: added the `NemotronH_Omni_Reasoning_V3` registry alias only.
- #55026: temporarily removed the Omni aliases.

No existing issue or open PR covers this. I searched open and closed vLLM issues and PRs for these architecture names, `mamba_ssm_cache_dtype` with Omni, and `NemotronHNanoVLV2Config`.

## Claims

- **Default cache dtype:** for `NemotronH_Nano_Omni_Reasoning_V3`, `NemotronH_Super_Omni_Reasoning_V3` and `NemotronH_Omni_Reasoning_V3`, `mamba_ssm_cache_dtype=auto` now resolves through the NemotronH hook. That means float32, or the value in the checkpoint config, instead of the model dtype (bf16).
- **Nemotron 3 Nano Omni:** this fixes a large accuracy loss. GPQA Diamond goes from 51.9 to 68.4 with no flags, the share of generations that run to the token cap drops from 23% to 0.25%, and requests/s rises 2.55×.
- **Nemotron 3.5 Super VL:** the checkpoint's own `mamba_ssm_cache_dtype: float32` is now honored. Accuracy was within noise, but bf16 had a 4% runaway tail and about 30% lower throughput.
- **No change for explicit settings:** an explicit `--mamba-ssm-cache-dtype` still takes precedence, and other architectures are unaffected.

## Details

**Root cause.**
- `registry.py` maps the three Omni aliases to `("nano_nemotron_vl", "NemotronH_Nano_VL_V2")`.
- `MODELS_CONFIG_MAP` is looked up by the HF architecture string and only contains `NemotronH_Nano_VL_V2`.
- So `NemotronHNanoVLV2Config.verify_and_update_config` never runs for the Omni aliases. `mamba_ssm_cache_dtype` stays `auto`, which resolves to the model dtype.
- That hook is also the only place the checkpoint's `mamba_ssm_cache_dtype` is read.
- The bug is present on v0.31.0, v0.32.0 and current nightly.

**Why float32.**
- Nano Omni: NVIDIA's report, [arXiv 2604.24954](https://arxiv.org/abs/2604.24954) §4.7, says "the Mamba SSM state cache is kept at FP32 at serving time". NeMo-Skills' Nemotron 3 Nano recipe, for the same LLM backbone, serves with `--mamba_ssm_cache_dtype float32`.
- Super VL: its checkpoint sets `llm_config.mamba_ssm_cache_dtype: float32` ([config.json](https://huggingface.co/nvidia/NVIDIA-Nemotron-3.5-Super-VL-120B-A12B-BF16/blob/main/config.json)).
- #39032 made float32 the NemotronH default because "Only `float32` is known to have no accuracy issues by default".

**Why it matters.** bf16 rounding of the recurrent state shows up as runaway generations. Models served with MTP speculative decoding, such as Super VL here, are affected much less than Nano Omni.

**Tradeoff.** A float32 SSM state doubles SSM-cache memory and costs a few percent of decode throughput. On these models the net throughput still rises, because the runaway generations go away.

**Limitations.**
- `NemotronH_Super_Omni_Reasoning_V3` is included because it is registered to the same class. It has no public checkpoint to test.
- The mapping also applies `NemotronHNanoVLV2Config.verify_and_update_model_config`, which defaults the video backend to `nemotron_vl` via `setdefault`. Omni already uses the `NemotronH_Nano_VL_V2` model class, so this aligns it with that class.

**AI assistance.** AI assistance (Claude) was used for the investigation, the patch, the test and this description. I reviewed every changed line and ran the tests above.
