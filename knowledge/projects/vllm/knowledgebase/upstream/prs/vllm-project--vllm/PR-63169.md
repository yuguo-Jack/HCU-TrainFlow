# [Attention] Allow an NVFP4 KV cache at head_size 64 on fa2

[Upstream PR](https://github.com/vllm-project/vllm/pull/63169) · state: open · merged: False

## Original PR description

## Overview

The fa2 NVFP4 KV path refuses head_size 64 because FlashInfer's fa2 prefill misreads the cache at that size. [FlashInfer #6024](https://github.com/flashinfer-ai/flashinfer/pull/6024) fixes the kernel; this drops the two refusals and runs the existing NVFP4 decode test at head_size 64 as well. That PR is merged and ships in the next FlashInfer release. On the current 0.7.2.post1 pin, head_size 64 models would still get wrong attention and the new test cases fail, so this should land with or after the bump to that release.

## Claims

- With FlashInfer PR 6024, fa2 reads an NVFP4 cache at head_size 64 as accurately as at 128 and 256: its prefill output matches SDPA over the dequantized cache to 0.002–0.003 relative error, on random inputs and on q/k/v captured from two head_size 64 models.
- `test_flashinfer_nvfp4_decode_correctness` at head_size 64 fails on FlashInfer 0.7.2 and passes with PR 6024.
- Other head sizes and KV cache dtypes are unchanged.

## Validation

sm_80, main (`c723f6d3ee`) plus this commit. "0.7.2" is the pinned FlashInfer release; "0.7.2 + 6024" is the same release with PR 6024's `prefill.cuh` change applied.

```text
pytest tests/v1/attention/test_attention_backends.py -k test_flashinfer_nvfp4_decode_correctness
    # 0.7.2: 2 failed (head_size 64, q_len 4), 6 passed; 0.7.2 + 6024: 8 passed
pytest tests/kernels/attention/test_flashinfer.py -k nvfp4    # 4 passed (both)
pytest tests/kernels/attention/test_attention_selector.py    # 87 passed, 22 skipped, 2 failed
```

The two selector failures (`test_hopper_mm_prefix_selects_triton_flash_attn[None-True]` and `[4-True]`) fail the same way on main.

fa2 NVFP4 prefill output against SDPA over the cache read back with `nvfp4_kv_dequantize_paged` (relative L2 error, random inputs, sequence lengths 40, 300 and 1027; a local script, not added here):

| q / kv heads, head_size | 0.7.2 | 0.7.2 + 6024 |
|---|---|---|
| 32 / 8, 64 | 0.0746 | 0.0034 |
| 14 / 2, 64 | 0.0741 | 0.0033 |
| 16 / 8, 128 | 0.0033 | 0.0033 |
| 24 / 4, 256 | 0.0033 | 0.0033 |

The same check on q/k/v captured from the first GSM8K 5-shot prompt gives, over all layers, at most 0.2636 on 0.7.2 and 0.0019 with PR 6024 for Llama-3.2-1B-Instruct (641 tokens, 16 layers), and 0.1971 and 0.0018 for Qwen2-0.5B-Instruct (726 tokens, 24 layers).

GSM8K (1319 questions, 5-shot, greedy; prompts and scoring from `tests/evals/gsm8k`; offline `LLM` with the FLASHINFER backend):

| Model (head_size) | BF16 KV | NVFP4 KV, 0.7.2 | NVFP4 KV, 0.7.2 + 6024 |
|---|---|---|---|
| Llama-3.2-1B-Instruct (64) | 0.319 | 0.127 | 0.249 |
| Qwen2-0.5B-Instruct (64) | 0.372 | 0.016 | 0.016 |
| Qwen3-0.6B (128) | 0.399 | 0.177 | 0.180 |

The NVFP4 cache costs these small models a lot of accuracy at head_size 128 too. On Qwen2-0.5B it costs nearly everything with or without the fix: on the captured inputs the kernel matches the dequantized reference in every layer, while quantization alone moves the first layer's attention output by 0.999 relative to BF16.

## Details

At head_size 64, fa2 prefill pairs a 128-row query tile with a 64-row KV tile. The zero-fill `cp.async` that loads the V scale factors writes zeros even when its predicate is off, so the lanes past the scale-factor bytes overwrite the first two rows of the query tile in shared memory. PR 6024 stops those lanes; head_size 128 and 256 give the same results with and without it.

On the vLLM side, `FlashInferBackend.supports_combination` rejected NVFP4 at head_size 64 on SM8x, SM90 and SM12x, and the metadata builder raised for it; both go, and the sink refusal stays. SM12x decodes NVFP4 with XQA, which vLLM already routes for head sizes 16–256 in multiples of 16. Only sm_80 was run here; the SM90 fa2 path and SM12x were not.
