# [Model] Use FlashInfer for Gemma 4 with an NVFP4 KV cache when FA4 is unavailable

[Upstream PR](https://github.com/vllm-project/vllm/pull/47547) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Without FA4, `Gemma4Config` pins `TRITON_ATTN` for Gemma 4's heterogeneous head dimensions. Triton cannot read an NVFP4 KV cache, so `--kv-cache-dtype nvfp4` on these GPUs fails at backend selection unless `--attention-backend FLASHINFER` is passed by hand, as in the SM121 run on [#46963](https://github.com/vllm-project/vllm/pull/46963). Since #46963, FlashInfer reads that cache on SM8x and SM12x. This pins `FLASHINFER` instead for a plain Gemma 4 architecture with an `nvfp4` cache.

## Claims

- On SM8x and SM12x, which have no FA4 and where FlashInfer reads an NVFP4 cache, a plain Gemma 4 model that does not need multimodal-prefix attention (text-only, or a checkpoint that is not a multimodal-prefix LM) starts on FlashInfer with `--kv-cache-dtype nvfp4` when no backend is set.
- In that same branch, every other cache dtype, including `nvfp4_4over6`, still gets `TRITON_ATTN`, and so do DiffusionGemma and EmbeddingGemma2, which call `Gemma4Config`. An explicitly set backend is left as is.
- No change where FA4 is available.

## Validation

```
pytest tests/kernels/attention/test_attention_selector.py
```

The new `test_gemma4_without_fa4_backend` covers the FA4-less branch for the three plain Gemma 4 cases and both models that reuse it. Its `nvfp4` case fails on `main`. The five cases pass with stock FlashInfer 0.7.0.post1 and 0.7.1rc5.

End to end on SM80 with stock `flashinfer-python==0.7.1rc5` and `google/gemma-4-E4B-it` (heads 256 + 512), four fixed prompts, greedy, 64 tokens:

| | `main` | `main` + `--attention-backend FLASHINFER` | this PR |
| --- | --- | --- | --- |
| `--kv-cache-dtype nvfp4` | fails: `TRITON_ATTN ... kv_cache_dtype not supported` | runs | runs on FlashInfer |

With stock FlashInfer 0.7.1rc5, the PR default and explicit FlashInfer matched token IDs on all four raw and four chat prompts when reusing the same torch.compile artifacts. A fresh-compilation main run differed on two chat prompts from a cached main run; the cause was not isolated. The same routing change was also validated on October 8 with stock FlashInfer 0.7.0.post1, the current main pin: four raw and four chat prompts matched the explicit FlashInfer baseline.

## Details

`#46329` also routes Gemma 4 with an NVFP4 cache to FlashInfer, as part of a two-pass V split, calibration support and image masking behind new environment variables. This change is only the routing: it uses the existing FlashInfer path, adds no environment variable or backend code, and is limited to plain Gemma 4 with an `nvfp4` cache so the policies of the models that reuse `Gemma4Config` stay as they are.

A Gemma 4 checkpoint that runs as a multimodal-prefix LM, such as `gemma-4-31B-it` with images enabled, still needs FlashInfer mm-prefix support ([#46558](https://github.com/vllm-project/vllm/pull/46558)); text-only launches are covered here.

- cadamcat · comment · 2026-08-26T16:40:54Z · [source](https://github.com/vllm-project/vllm/pull/47547#issuecomment-5428183066)

Tested this PR's exact behavior on an A100 80G (Ampere, FA4 unavailable), vllm 0.28.0 as released, gemma-4-31B w4a16 with the official MTP assistant, text-only serving. Three results that may help it along.

**The FlashInfer release blocker is gone.** flashinfer-ai/flashinfer#3739 merged 2026-07-03 and is in every release from v0.6.16 (2026-07-31) onward — including 0.6.16.post3, the exact pin in `requirements/cuda.txt`. A stock install already carries the Ampere large-head kernel, and the backend validator on 0.28.0 accepts the 512-head group (head size never appears among its rejection reasons on this model).

**The selector path works, and it is fast.** With the forced fallback removed as in this diff, the selector lands on FLASH_ATTN for the sliding groups (head 256) and FLASHINFER for the full-attention group (head 512), and the mixed engine runs correctly, speculation included. 30K-token prompt, decode rate by 64-vs-8 differencing:

| routing (30K, text-only serving) | MTP | no spec |
|---|---:|---:|
| TRITON_ATTN (current forced default) | 31.50 | 43.85 |
| this PR's selector path (FA2+FlashInfer) | 66.09 | 48.95 |
| explicit all-FLASHINFER, for reference | 62.43 | 47.42 |

The MTP rows are the end-user story: this PR turns speculative decoding at long context from a 28% loss into a 35% gain, and at 50K the forced default collapses to 15.75 tok/s while FlashInfer holds 41.35 — that is #52049. So this PR repairs that issue's default routing for text-only deployments (`limit_mm_per_prompt` all zero); multimodal-enabled deployments still exclude FlashInfer at validation until #46558, so the two PRs pair up.

One hazard for anyone testing this: #50891. The AOT compile cache key ignores `limit_mm_per_prompt`, and flipping it also flips what the selector picks here — a stale artifact from a TRITON/mm-enabled run crashes the FlashInfer configuration at engine init (`AttributeError: 'NoneType' object has no attribute 'size'`). Clear `~/.cache/vllm/torch_compile_cache` when switching configs.

Numbers are single-run probes on Colab (two sessions, same stack; the 50K pair and both selector-path rows are from one session). Full logs, the probe script and the matrix as JSON: https://github.com/cadamcat/dual-radeon-vllm/tree/main/benchmarks/cuda-a100
