# [Quantization][Quark] Support MXFP8 (W8A8) routed experts

[Upstream PR](https://github.com/vllm-project/vllm/pull/63125) · state: closed · merged: True

## Original PR description



## Disclosure

AI assistance was used. The changes were reviewed and tested manually.

## Overview

Support AMD Quark checkpoints whose routed experts are OCP MX MXFP8 (W8A8) instead of MXFP4/MXFP6, by adding a `QuarkW8A8Mxfp8MoEMethod`.

This also makes per-layer mixed checkpoints (some MoE layers MXFP8, others MXFP4) loadable, since Quark already resolves the scheme per layer.

## Claims

- A Quark checkpoint with MXFP8 (W8A8) routed experts now loads and serves instead of failing at model construction with `ValueError: Unsupported OCP MX dtype combination for MoE: input_dtype=mxfp8_e4m3, weight_dtype=mxfp8_e4m3`.
- MXFP8 experts use the existing MXFP8 MoE stack (`select_mxfp8_moe_backend`, `convert_to_fp8_moe_kernel_format`, `make_fp8_moe_kernel`), i.e. `AITER_MXFP8` on gfx950, with dynamic MXFP8 activations — no new kernel, no new weight layout.
- Per-layer mixed MXFP4/MXFP8 routed experts work with no change to Quark's config resolution: `layer_quant_config` entries matching `<layer>.experts*` select MXFP8 for that layer, everything else falls back to `global_quant_config`.
- Unsupported spellings fail early with an actionable error: only the 1-D `per_group`/`group_size=32`/`e8m0` weight spelling is accepted for MXFP8 experts (the 2-D `per_block` spelling is Linear-only), and biases are rejected.
- No change for existing MXFP4/MXFP6/INT8/FP8/NVFP4 Quark checkpoints.

End-to-end accuracy of a Quark MXFP8 MoE checkpoint was not measured here; the numerics are those of the shared MXFP8 MoE path.

## Details

Quark resolves MoE schemes per layer (`global_quant_config` plus `layer_quant_config` globs), but `quark_moe.py` had no MXFP8 MoE method: `fp8_e4m3`/`per_group`/`group_size=32`/`e8m0` routed experts were dispatched to `QuarkOCP_MX_MoEMethod`, which only implements MXFP4/MXFP6, and failed at model construction.

`QuarkW8A8Mxfp8MoEMethod` mirrors `CompressedTensorsW8A8Mxfp8MoEMethod` (https://github.com/vllm-project/vllm/blob/main/vllm/model_executor/layers/quantization/compressed_tensors/compressed_tensors_moe/compressed_tensors_moe_w8a8_mxfp8.py#L35).

Behavior changes:
- `QuarkOCP_MX_MoEMethod` no longer declares MXFP8 in its `supported_*_quant_keys`, so MXFP8 experts are rejected by the shared `QuarkMoEMethod` validation instead of the later `OCP_MX_Scheme` check (its `ValueError` keeps upstream's wording),
- Quark checkpoints that previously failed to load now serve

Limitations:
- `hidden_size`/`intermediate_size_per_partition` must be divisible by 32,
- no bias,
- dynamic MXFP8 activations only, and the kernel comes from `select_mxfp8_moe_backend` (`AITER_MXFP8` on gfx950)

No new flag, config field or env var, so no docs change.

No duplicate work: `gh pr list --repo vllm-project/vllm --state open --search "quark mxfp8"` and `--search "mxfp8 MoE quark in:body"` return no PR adding a Quark MXFP8 MoE method; #61457 (per-layer fused shared expert) and #56523 (MXFP4 oracle) are distinct.
