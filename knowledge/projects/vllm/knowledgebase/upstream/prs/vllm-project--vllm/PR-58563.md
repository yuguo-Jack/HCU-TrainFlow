# [Metrics][Frontend] Pluggable KV connector metrics on the Rust frontend via connector metrics descriptor

[Upstream PR](https://github.com/vllm-project/vllm/pull/58563) · state: open · merged: False

## Original PR description



## Purpose

Today the Rust frontend's `/metrics` can only export KV connector metrics for Nixl and Mooncake, because each of them has dedicated Rust code. Stats from every other connector (Offloading, HF3FS, HiSparse, and out-of-tree connectors) do reach the Rust process, but are silently dropped, so these metrics disappear as soon as `VLLM_USE_RUST_FRONTEND=1` is set.

This PR lets a connector describe its own metrics, so the Rust frontend can export them without any per-connector Rust code. Design discussion: RFC: #58562.

## Changes

How it works:

1. On the Rust frontend, the first time a connector reports stats, it also sends a short description of its metrics: name, type, help text, histogram buckets, and where each value sits in its stats. The description rides the existing scheduler stats message; there is no new RPC.
2. When the Rust frontend sees a description, it registers those metrics. After that, every stats tick carries values only, and Rust updates the metrics from them.
3. On the Python frontend nothing changes: no description is sent, and the existing Prometheus metrics stay as they are.
4. With MultiConnector, each child sends its own description and is exported separately.

Nixl and Mooncake keep their existing Rust code paths.

Key pieces:

- **`maybe_attach_metrics_descriptor()`** (Python): attaches the description once, and only when the Rust frontend is on. A connector calls it from its stats `to_dict()`.
- **Built-in connectors** (Python): Offloading, HF3FS, and HiSparse build their description from the same definitions their Prometheus metrics use; a unit test keeps the two in sync.
- **`DescriptorDrivenAdapter`** (Rust): registers metrics from a description and applies later values to them.
- **Routing in `metrics.rs`** (Rust): stats from connectors without dedicated Rust code go to the adapter, whose metrics are rendered on `/metrics` after the built-in ones.

- **Rust frontend zero-series pre-create:** once a connector metrics descriptor arrives, the Rust frontend pre-creates zero-valued series for every engine × model_name × const labels.
- **Rust HELP trailing-period strip:** when registering from a descriptor, the Rust frontend strips a single trailing `.` from HELP text before Prometheus adds its own, so HELP lines end with one period (matching the Python frontend).
- **List-valued gauge samples:** when a gauge's stats value is a list (HiSparse reports per-step lists), the Rust frontend sets the gauge to the last element, matching the Python Prometheus logger's last-value behavior.

An out-of-tree connector adopts this the same way: attach a description in its stats `to_dict()`.

> **NOTE:** On the Rust frontend, connector series are registered from the metrics descriptor carried on the first `SchedulerStats` that includes KV connector stats. Engine cores emit no stats while idle, so connector series appear after the connector first reports stats (then pre-created at 0 for all DP engines), rather than immediately at startup as on the Python frontend. The engine core was left untouched; a startup-only stats message from the core would close this gap but is not required for correct values after the first report.


## Known field differences (Rust vs Python)

These are field-level (name / HELP / TYPE / labels / suffixes), not value mismatches:

- **(a) Inherent encoder format:** Python's Prometheus client emits `_created` timestamps and names counters with a `_total` suffix in HELP/TYPE; the Rust encoder does not. Rust also pre-creates zero series after the first descriptor, so some families appear as samples earlier than on Python (where samples appear lazily after the first increment).
- **(b) Legacy / deprecated Python-only:** a few older Offloading families remain on the Python frontend only and are not part of the descriptor surface.
- **(c) Config-gated:** `stores_skipped` is always present in the Offloading descriptor (and therefore on Rust); the Python Prometheus path registers it only when `store_threshold >= 2`.
- **Nixl / Mooncake HELP punctuation:** on the Rust frontend, Nixl and Mooncake HELP strings still end with `..` because those connectors use the pre-existing typed Rust registration path, which is outside this PR; the trailing-period strip applies only to descriptor-registered metrics. The Python frontend's Nixl HELP lines end with a single `.`.
- **(d) Real adapter bugs:** none found in the paired field comparison across Offloading, HF3FS, HiSparse, OOT, and Multi.
