# [ROCm][Perf][DSV4] Keep one decoder-replay row on unfinished prefills on gfx942

[Upstream PR](https://github.com/vllm-project/vllm/pull/61682) · state: open · merged: False

## Original PR description

## Overview

On ROCm, an unfinished DeepSeek-V4.1-Flash prefill chunk keeps one decoder-replay row instead of `min(query_len, 128)`. The finishing chunk, decode, and prompt-logprobs stay on the window. CUDA is unchanged. #59039 is the 128-row path this trims.

## Claims

- An unfinished chunk is `num_computed_prefill_tokens + query_len < prefill_len`. On ROCm its kept length is 1. Prompt-logprobs still keep every row.
- An empty `decoder_replay_cudagraph_capture_sizes` on ROCm also captures `[1, 2, 4, 6, 8, 12, 16, 24, 32, 48, 64, 96]` below the window. An explicit list that omits 1 is rejected. CUDA still starts at the window.
- 8k prompts are one chunk, so both arms replay 128 rows. At 256k the unfinished chunks are shorter.

## Validation

4× MI325X (gfx942), TP4, DeepSeek-V4.1-Flash, ROCm 7.2.3, nightly. `vllm bench serve`, random data, 20 prompts, one warmup, output length 1024. The one-row arm passed the capture list explicitly because the empty list started at 128.

- ischencheng · comment · 2026-10-20T23:24:24Z · [source](https://github.com/vllm-project/vllm/pull/61682#discussion_r4331395707)

File: `vllm/models/deepseek_v41/nvidia/model_state.py` · line 475

This drops rows that a later step still reads.

```python
# L133, _gather_replay_batch_kernel
if kept_end - kept_begin < end - begin:
    kv_start = tl.maximum(kv_start, tl.load(seq_lens_ptr + req) - window)
```

The finishing chunk only gets this floor when it is trimmed. Otherwise its first row attends 127 rows back into the previous chunk, and with one row kept those replay-layer KV slots were never written. Two ways to hit it:

- The finish is <= 128 rows. Your new test is one: 250 = 200 + 50, row 200 reads 73-198 after chunk 1 kept only row 199.
- The finish runs in a FULL graph, or a PIECEWISE graph below `decoder_replay_trim_threshold`. `_prepare_replay_batch` returns at L462 there, and the replay layers run on every row with the batch's SWA metadata. E.g. 8192 + 300: the 300-token finish plus a few decodes takes a small PIECEWISE graph and reads rows 8065-8191.

Could we keep one row only when the rest of the prompt is out of the finish's reach? Something like:

```python
remaining = prefill_len - computed - query_lens
# The finish may run untrimmed up to the trim threshold and reads window - 1 rows back.
reach = (layers.trim_threshold or self.max_num_tokens) + int(layers.window)
row_limit = np.where(unfinished & (remaining >= reach), 1, int(layers.window))
```

That keeps the 128-row tail on the last chunk or two, so a 256K prompt still skips almost all of them.

Checked on an L4 with this PR's own fixtures (`_input_batch` / `_prepare`): for 250 = 200 + 50 and for 1024 + 300 (finish padded to 320 in PIECEWISE), chunk 1 writes only its last row and the finish needs 126 rows nobody wrote. With the snippet above chunk 1 writes 128 rows, nothing is missing, and a 1024-token chunk of a 100K prompt still keeps one row.
