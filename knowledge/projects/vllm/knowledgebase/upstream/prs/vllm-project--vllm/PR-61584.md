# [Bugfix] Reserve construction-time scratch across workspace slots

[Upstream PR](https://github.com/vllm-project/vllm/pull/61584) · state: open · merged: False

## Original PR description

## Overview

Reserve attention scratch across every configured microbatch/lane slot before execution, preventing locked-workspace growth when a slot was not exercised during warmup. Addresses the workspace-reservation portion of #61487, not the complete HiSparse + DBO serving issue.

## Claims

- Construction reservations size every execution slot with runtime-equivalent alignment.
- Runtime allocation remains slot-local, preserving peer storage and the existing lock contract.
- Reservations retain no tensor views and reuse the existing allocation context.

Full-model HiSparse/DBO serving and ROCm kernel validation remain unperformed locally. The 8 GiB NVIDIA setup does not cover the original large-model deployment; these focused results do not establish that all of #61487 is fixed.

## Details

Construction reservations previously used `get_simultaneous`, which sizes only the current slot. `WorkspaceManager.reserve` applies the same per-tensor alignment to every slot. Forward calls continue using `get_simultaneous` so growth cannot replace another microbatch's live storage.

The API is intended for initialization before execution or graph capture, while no slot holds scratch views. Required scratch is accounted for even when warmup misses a slot; single-slot capacity is unchanged. Updated callers cover FlashMLA sparse, Triton MLA, AITER MLA, TurboQuant, FlashInfer/TRTLLM prefill, B12x, and Dots3Note. HiSparse is present in this merged base, but its full serving/state-isolation behavior is outside this PR's validation.

An open-PR workspace search found no other all-slot construction-reservation fix. Related #48179 presizes MoE scratch for worst-case shapes rather than reserving all execution slots.
