## Overview

A simpler version of #62817 (DeepSeek-V4.1: replay one row for prefill chunks far from the prompt end). It keeps the original author's commits and adds three commits on top. They drop the model runner hook, the `ModelState` interface method and the MoE finalize change. A config-derived bound replaces them, so the change stays inside `vllm/models/deepseek_v41/`. This is a proposal for #62817, not a competing optimization. If the author prefers, the last three commits can be cherry-picked there and this PR closed.

## Claims

- Same optimization as #62817. A prefill chunk that ends far enough before its prompt's end replays one row, and later chunks never read the rows it skipped.
- No changes to `vllm/v1/worker/gpu/model_runner.py`, `model_states/interface.py`, `deepseek_v41/nvidia/model.py` or `decoder_replay_layers.py`.
- Non-test diff vs main: +94/-31 in 3 files (#62817: +172/-38 in 7 files). Tests: +62 (#62817: +136/-2).
- With default settings the same chunks skip their tails as in #62817: 7 of 8 for a 124K prompt in 16K chunks, and 3 of 4 for 64K.

## Details

**Why #62817 needs the eager hook.** After a one-row chunk, its skipped rows hold no replay-layer KV. A later chunk whose SWA window reaches back to them must read nothing below them. Only the replay batch's own metadata can apply that floor. In a CUDA graph step that runs the replay layers on the whole batch, they share SWA metadata with the encoder-side layers, so #62817 forces such steps eager from the model runner.

**Why the hook isn't needed.** Such a step can only be a CUDA graph step if it holds at most `max_cudagraph_capture_size` tokens. Neither kind of chunk that can follow a one-row chunk fits in one:

- A chunk whose window reaches back past the replayed tail (`K = max_cudagraph_capture_size + 2 * window` tokens) starts within `window - 1` of it, so if it is the prompt's last chunk it holds more than `max_cudagraph_capture_size + window` tokens.
- A chunk the scheduler cuts short shares its step with at least the smallest prefill cap. That cap is `max_num_scheduled_tokens`, `max_num_batched_tokens - max_num_seqs * draft_slots` (the scheduler takes `draft_slots` off the input budget per request) or `long_prefill_token_threshold`. With adaptive verification, `max_num_seqs * num_speculative_tokens` comes off too, because the runner may drop every draft before it picks a graph. The rule is enabled only when the result exceeds `max_cudagraph_capture_size + window`. That holds by default, because the capture size is at most 1024 and never exceeds `max_num_batched_tokens`.
- The runner sizes graph dispatch from the scheduled token count, which is shrunk only by adaptive verification and PCP (the rule is off under PCP). DP sync only raises it, and ubatching only applies to an already-chosen FULL graph. A future runner feature that shrinks a step before dispatch would have to be added to this bound.
- The second window covers the few tokens that the MTP lookahead or `max_model_len` can shave off a chunk.
- Encoder inputs can cut a chunk anywhere, so the rule is off when the model accepts multimodal inputs. With `--language-model-only` it stays on.

**Other simplifications.**

- Replay batch steps keep holding more than a window of tokens, so the MoE finalize change is not needed.
- The single-use `needs_eager_forward` / `_skipped_tails` helpers are gone.
- The kernel's host-side `kv_floor` (which also drops `_pcp_replay_start`) and the 1..64 replay graph sizes from #62817 are kept.

**What comes from DeepInfer.** The rule follows DeepInfer's [`clip_prefix`](https://github.com/deepseek-ai/DeepInfer/blob/a679bb86ce36e883a98a97733492b686e5b9a08e/csrc/engine/input_metadata/prepare_tensor_input_v4.cpp#L203-L231), reimplemented here (no code is copied). A prefill keeps only its rows in the prompt's last K tokens, and always its last row. Those rows read nothing before the last K tokens. Both follow from the prompt length alone, so the model state doesn't track where the last one-row chunk ended.

**What differs from DeepInfer.**

- K is `max_cudagraph_capture_size + 2 * window`, not DeepInfer's 140 (window + backtracking). vLLM can run a small prefill chunk in a whole-batch graph, where no floor applies, so a chunk that reads back past the tail must be too large for a graph. Chunks ending within K of the prompt's end keep their full window, which costs one extra replay tail on some prompts.
- A one-row chunk reads itself and writes its KV, which nothing reads. DeepInfer's placeholder row reads nothing and doesn't write.
- The first replay layer still reads its full window, and the last window's floor stays `seq_len - window` as on main. So outputs are not meant to match DeepInfer bit for bit.
- The rule is off under PCP. DeepInfer's CP boundary redistribution isn't ported.
- Prompt-logprob requests keep every row. DeepInfer turns prompt logprobs off instead.

**Tradeoff.** Unlike #62817, the rule is off when `long_prefill_token_threshold` or another prefill cap is at most the capture size plus a window, when multimodal inputs are enabled, or when the scheduling policy is priority, where preemption can return a step's budget after a chunk was cut short. Those deployments keep today's behavior.
