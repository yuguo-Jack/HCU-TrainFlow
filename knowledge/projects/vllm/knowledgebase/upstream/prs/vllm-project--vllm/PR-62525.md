# [MoE][Model] Gemma 4: skip CUDA-graph padding rows in the routing kernel

[Upstream PR](https://github.com/vllm-project/vllm/pull/62525) · state: closed · merged: True

## Original PR description



## Overview

Gemma 4's MoE routing kernel ignores `forward_context.is_padding`, so the rows that pad a decode batch up to a captured CUDA graph size are routed to 8 real experts each and the expert GEMMs do their work for nothing. This passes the padding mask into the Gemma 4 kernel, as #48979 did for the fused top-k kernels, and shares the mask lookup that two routers each defined.

## Claims

- `google/gemma-4-26B-A4B-it`, default `vllm serve`, 1x H200 (80 GB cap): **+19% output tok/s at 9 concurrent users, +12% at 17, +6% at 33**; unchanged at 1 user and at CUDA graph sizes (no padding there).
- Real tokens are unchanged: greedy outputs and logprobs are bit-identical to `main` for 9- and 17-request batches.
- No behaviour change for other models: `fused_topk_router` and `fused_topk_bias_router` call the same helper they inlined before.

## Validation

**End to end.** `main@852989f`, 1x H200 NVL with `--gpu-memory-utilization 0.5219` (80 GB, as an H100), BF16, default backend (`TRITON_FLASH_ATTN`), V2 model runner. `vllm bench serve --dataset-name random --random-input-len 1024 --random-prefix-len 512 --random-output-len 256 --ignore-eos --num-prompts 8*users`, 2 runs per arm, alternating `main` / PR in the same session:

| Users | `main` tok/s (run 1 / 2) | PR tok/s (run 1 / 2) | Change | TPOT p50, `main` → PR |
|---:|---:|---:|---:|---:|
| 1 | 189.5 / 190.3 | 189.9 / 190.0 | 0% | 4.98 → 4.95 ms |
| 9 | 840.3 / 841.6 | 1001.7 / 1004.3 | +19.3% | 9.83 → 8.05 ms |
| 17 | 1346.2 / 1338.1 | 1505.0 / 1513.9 | +12.5% | 11.50 → 9.87 ms |
| 33 | 2118.5 / 2128.3 | 2258.7 / 2259.5 | +6.4% | 13.72 → 12.67 ms |

9, 17 and 33 users run as 16-, 24- and 40-row graphs (7, 7 and 7 padding rows).

**Accuracy.** GSM8K (1,319 questions, 5-shot chat, greedy) at 9 concurrent users: `main` 95.9%, PR 96.1%.

**Bit-identity.** Offline `LLM.chat`, greedy, 256 tokens with `ignore_eos`, all requests starting in the same step: 9 requests (16-row graphs) and 17 requests (24-row graphs) give the same token ids and the same logprobs as `main`; `VLLM_MOE_SKIP_PADDING=0` on this branch also matches `main`.

**Tests.** `tests/kernels/moe/test_gemma4router.py` adds a padding case: real rows bit-identical to the unmasked call, padding rows id -1 and weight 0. `tests/kernels/moe/test_topk_softplus_sqrt.py` patches the renamed helper. `VLLM_GPU_SYNC_CHECK=error` serving GSM8K: no syncs flagged (same as `main`). V1 model runner (`VLLM_USE_V2_MODEL_RUNNER=0`, 1 run): 823.5 → 989.5 tok/s at 9 users (+20%), 1312.0 → 1477.6 at 17 (+12.6%), GSM8K (300 q) 98.0% on both.

## Details

#46428 introduced `VLLM_MOE_SKIP_PADDING` as a `torch.where` in the modular kernel, which every router went through. #48979 moved the mask into the fused top-k kernels and removed that step, so routers that do not use those kernels lost it. Gemma 4 routes with its own Triton kernel through `CustomRoutingRouter`; with a 9-request decode batch replayed as a 16-row graph, each of the 7 padding rows selected 8 experts, so the expert GEMMs loaded weights for up to 56 extra (token, expert) pairs per layer.

The kernel now takes an optional `is_padding` tensor (a `HAS_PADDING` constexpr, so the unmasked path compiles as before) and writes id -1 / weight 0 for padding rows, which `moe_align_block_size` already drops. The mask costs nothing extra: it is applied in the kernel's existing stores.

Other users of `CustomRoutingRouter` (Llama 4, Cohere2-MoE, Phi-MoE, InternS1-Pro, the Transformers MoE backend) route with Python functions and have the same gap; a generic mask there would add two small kernels per MoE layer, so it is left for a separate change with its own measurements.
