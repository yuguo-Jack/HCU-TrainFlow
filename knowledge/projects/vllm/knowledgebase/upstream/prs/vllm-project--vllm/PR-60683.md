# [ROCm][Perf][Kimi-K3] Mono decode layer for Kimi-K3 on MI355X

[Upstream PR](https://github.com/vllm-project/vllm/pull/60683) · state: open · merged: False

## Original PR description

## Purpose

Opt-in (`VLLM_ROCM_MONO_DECODE=1`) Kimi-K3 decode path for MI355X (gfx950), TP8. A spec-verify step of at most 8 rows runs each decoder layer as two persistent FlyDSL launches, with the TP all-reduces in-kernel over peer memory:

- **K1** (KDA layers): AttnRes, in_proj, f_b, spec conv, KDA recurrence, gated RMSNorm.
- **K2** (MoE layers): o_proj + all-reduce, MLP AttnRes, the latent MoE (router, top-16 MXFP4 experts, shared experts, latent all-reduce + RMSNorm, up_proj, final all-reduce). MLA layers run vLLM's attention up to o_proj (`forward_core`), then K2.

Every other step (prefill, mixed, > 8 rows, other TP/GPUs) takes the existing path; the switch off changes nothing. The path is also off with a KV connector (its copy kernels on another stream can hold CUs while the mono CTAs spin-wait).

```text
amd/mono_decode.py   eligibility per layer / per step, vLLM tensors -> kernel inputs
amd/mono/
    runner.py        scratch, step epoch, peer memory
    layer.py         K2
    attention/       kda.py (K1), back.py (o_proj + AR + MLP AttnRes)
    stages/          moe.py, gemv.py
    common/          ops, sync, ranks, mx, plan, peer_memory, debug
```

`mono/common/` is adapted from ROCm/ATOM `atom/mono` (MIT, a526f0d) with AMD's notice kept. Layout follows #60397.

Not a duplicate of #60397 (DeepSeek-V4.1 mono decode): different model, attention, residual and MoE.

## Test Plan

- `pytest tests/models/kimi_k3/test_amd_mono.py` (8x MI355X): K1 vs vLLM's KDA op chain incl. state updates and block-write layers; K2 and the MoE launch vs o_proj + all-reduce + attn_res + KimiMoE (aiter `fused_moe`), ranks bit-identical.
- gsm8k 5-shot at conc 1 (every decode step fused).
- `vllm bench serve` 8k/1k, conc 1, 3 seeds; InferenceX agentic-coding c1 3600 s.

Kimi-K3, TP8, DCP8, MTP k=7, `--stream-interval 10`, MI355X.

## Kimi-K3 mono decode (`VLLM_ROCM_MONO_K3=1`): C=1 accuracy on MI355X

**Setup**
- Image `vllm/vllm-openai-rocm:nightly-rocm100-81198e97ba7eee2a22540caaa756b7fdddcb4d93`, with `vllm/models/kimi_k3/amd/` and the `envs.py` hunk from this PR at `e2e886c37`. `git apply` did not apply cleanly to the image's older base, so I copied the directory over instead.
- MI355X, TP8. Serving flags from InferenceX recipe `kimik3-fp4-mi355x-vllm-agentic-mtp`: fp8 KV cache, DSpark MTP with `num_speculative_tokens=7` and block rejection, `max-num-seqs 2`.
- `VLLM_ROCM_MONO_DECODE=1` and `VLLM_USE_BREAKABLE_CUDAGRAPH=1`. py-spy on the workers shows the decode step running in `_forward_mono_kda` and `_mono_k2.forward`.
- Concurrency 1: one request at a time, at most 8 rows per decode step, so every decode step stays within the mono limit.

**Results (C=1, mono on)**
