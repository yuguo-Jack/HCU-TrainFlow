# [Rust Frontend] Accept empty stream_options without streaming

[Upstream PR](https://github.com/vllm-project/vllm/pull/62643) · state: closed · merged: True

## Original PR description

## Overview

Python chat and completions reject `stream_options` without `stream=true` only when the object is non-empty (`if data.get("stream_options") and not data.get("stream")` in each `validate_stream_options`), and `/inference/v1/generate` has no such check. The Rust frontend rejects any `stream_options` with `stream=false` on all three routes, including `{}`. This PR aligns the Rust checks with Python.

## Claims

- Chat and completions accept `"stream_options": {}` without streaming and still reject a `stream_options` object that sets an option.
- Non-streaming `/inference/v1/generate` accepts `stream_options`, as in Python; the non-streaming handler already ignores `include_usage` and `continuous_usage_stats`.

| Request with `stream=false` | Python | Rust before | Rust after |
|---|---|---|---|
| chat or completions, `stream_options: {}` | 200 | 400 | 200 |
| chat or completions, `stream_options: {"include_usage": false}` | 400 | 400 | 400 |
| generate, any `stream_options` | 200 | 400 | 200 |

- Chat and completions `validate_request_compat_accepts_empty_stream_options_without_streaming` (`{}`, through both chat layers) fail when the checks go back to `stream_options.is_some()`.
- Chat and completions `validate_request_compat_rejects_stream_options_without_streaming` cover `{"include_usage": false}` and `{"continuous_usage_stats": true}`.
- Generate `validate_request_compat_accepts_stream_options_without_streaming` replaces the test that pinned the rejection.

## Details

`StreamOptions::is_empty` sits on the shared DTO (`routes/openai/utils/types.rs`) and destructures every field, so a new option has to be considered there. Chat has two overlapping checks (the `validate_chat_cross_parameters` schema validator and `validate_request_compat`), and both change together; completions changes `validate_request_compat`. The generate check came from mirroring chat in vllm-project/vllm#43779; Python's generate never had it, so it is removed rather than kept as a Rust-only rejection.

One edge case stays different: Python checks the raw JSON, so it rejects `{"include_usage": null}`; Rust sees the deserialized options and accepts it like `{}`.

Not a duplicate: the only open upstream PR touching `stream_options` and the Rust frontend area, vllm-project/vllm#61275, adds a new Python option and does not change this validation.
