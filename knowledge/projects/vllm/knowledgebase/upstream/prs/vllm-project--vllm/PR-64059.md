# [Bugfix] Fix DFlash draft acceptance of 0 with FULL CUDA graphs

[Upstream PR](https://github.com/vllm-project/vllm/pull/64059) · state: closed · merged: True

## Original PR description

## Overview

Fixes #63587. With the default `FULL_AND_PIECEWISE` CUDA graphs, the DFlash draft reads a stale kernel block table, so none of its tokens are accepted. This PR maps the draft kernel block tables before the FULL graph replay, the same way `TargetDependentARSpeculator` already does (#57169).

## Claims

- DFlash-family drafts work again under FULL draft CUDA graphs when the KV cache block is split into smaller kernel blocks. Tested with hybrid `Qwen/Qwen3.5-4B` and a DFlash2 draft on B200: acceptance goes from 0.0000 to about 0.185, the same as the PIECEWISE control (0.1863).
- The FULL draft path from #60692 stays on. Throughput is 20.56–21.21 requests/s, against 6.59–6.67 before the fix and 11.57 with PIECEWISE.
- Adds one row to `test_dflash_correctness`. It fails without the fix and passes with it.
- The code change is 8 lines in `vllm/v1/worker/gpu/spec_decode/dflash/speculator.py`.

## Details

**Root cause.** Qwen3.5 is a hybrid model (attention plus GDN layers). To make the attention page match the mamba page, the KV cache manager uses 640-token blocks. The draft's FlashAttention 4 backend uses 128-token kernel blocks. So the draft attention group reads its block table from the persistent `AttentionGroup.kernel_block_table` buffer (`vllm/v1/worker/utils.py`), and the captured FULL graph reads that buffer. Only `map_to_kernel_block_table` fills it, and only the eager metadata build calls that (`_with_kernel_block_table`).

Since #60692, `DFlashSpeculator.propose` skips `_build_uniform_attn_metadata` when it replays a FULL graph and every draft backend supports `update_draft_decode_metadata`. The in-graph `_update_draft_decode_metadata` only asks each builder to refresh its own data. It does not map the block table. So after capture, the buffer keeps the rows from the dummy all-zero block table: kernel pages 0..4, which belong to the null block. On every replay the draft reads the null block's K/V instead of the request's. The drafts are unrelated to the context, and the target rejects all of them. The output stays correct because the target checks every token.

A debug print before `run_fullgraph` (not part of this PR) confirmed this. Request 0 owned manager block 83, so its kernel row should be `[415, 416, 417, 418, 419]`, but the buffer held `[0, 1, 2, 3, 4]`. With the fix, it held `[415, 416, 417, 418, 419]`.

**Fix.** In the branch where the build is skipped, call `group.map_to_kernel_block_table(self.block_tables.input_block_tables[group.kv_cache_group_id])` for every draft attention group before the replay. This is the same step `TargetDependentARSpeculator._fused_multi_step_decode` takes before its FULL replay. `map_to_kernel_block_table` already handles the kernel block size, the packed stride and the backend, and it returns at once for groups with no split. When the build does run, it maps the table itself, so that path is unchanged. DFlash, DFlash2, DSpark, LiLiCorr and XPress all use this `propose`.

**Other FULL draft replays checked.** `TargetDependentARSpeculator` (MTP, EAGLE, Gemma4) already maps the table before its fused FULL replay. `MultiModuleMTPSpeculator` builds the metadata before `run_fullgraph`. `StandaloneARSpeculator` does not use FULL replay.

**Not chosen.** Mapping inside `_update_draft_decode_metadata` would also map again on every `TargetDependentAR` step, which already maps. Reporting `supports_decode_metadata_update = False` for split groups would turn #60692 off for these models.

**Limitations and notes for reviewers.**

- The issue does not name its checkpoints (a 9B FP8 target and an NVFP4 target, served through Dynamo). I validated with the 4B BF16 pair above and plain `vllm serve`. The issue saw acceptance of 0.004 and 0.0005; here it was exactly 0. The issue's `no KV cache group could be identified as the draft model's` warning did not appear here, and I did not look into it.
- The test row uses a community draft checkpoint, `nchapman/Qwen3.5-4B-DFlash2`, the one used in the issue thread. If CI should use only official checkpoints, the row can point at another hybrid target/draft pair with the same block split.
- CI: the row id contains `dflash2`, so the nightly `spec-decode-dflash2-nightly-b200` step (`-k "dflash2"`) selects it. `-k dflash2` also selects it in non-B200 steps (H100, MI355), and the thresholds were measured only on B200.
