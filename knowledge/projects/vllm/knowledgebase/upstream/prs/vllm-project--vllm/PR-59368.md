# [Bugfix][MRV2] Measure the CUDA graph pool for the memory estimate, not the capture's free-memory delta

[Upstream PR](https://github.com/vllm-project/vllm/pull/59368) · state: open · merged: False

## Original PR description

## Purpose

Fixes #59318.

`profile_cudagraph_memory()` (model runner V2, #53306) sizes the KV cache budget with two numbers that are not graph memory:

1. `measured` is the free-memory delta of `capture_model(profile_only=True)`. It also counts the first-use allocations the pass makes outside the graph pool (on GLM-5.3 TP4/DCP4 about 1.0 GiB of non-torch memory per rank: NCCL, JIT modules) and the transients the caching allocator keeps. The real capture later pays neither, because the profiling pass already made them.
2. The FULL extrapolation `first + (N - 1) * mem_samples[1]` samples per-graph free-memory deltas, and those deltas are negative: `torch.cuda.graph.__enter__` calls `empty_cache()` before every capture, so each sample is "pool growth minus the cache released from the previous warmup". `per_graph` is then floored to 1 MiB, and `measured - sum(mem_samples)` adds back the absolute value of the second sample (0.37 GiB here). The 0.40 GiB gap in the issue is that sign artifact, not a slope problem; the instrumented run below shows the 16 smaller FULL graphs add 0 bytes to the pool after the first one.

The issue's decomposition of the 0.97 GiB was right on part 1 and wrong on the mechanism of part 2; the numbers are in the test results.

This PR:

- captures every descriptor in the profiling pass (FULL graphs are cheap: 4 s for 17 here) and drops the sampling and extrapolation;
- measures the throwaway pool through the allocator snapshot (`segment_pool_id`) instead of the free-memory delta, with the delta kept as a fallback where there is no snapshot;
- reserves, on top of the pool, what the pass still holds after teardown (`free before - free after teardown`), and stores it as `runner.cudagraph_profiling_retained_bytes`. That memory is real process footprint the profile run never saw; before this PR it was charged by accident as part of the delta. It is logged as its own line item so it can be argued about separately;
- makes the "CUDA graph pool memory: actual vs estimated" line in `compile_or_warm_up_model` compare the pool with the pool (`graph_pool_bytes(global pool)`), and name the retained part.

Related: #59317 is the DCP top-k merge transient that this over-reservation happened to cover on our host; it is fixed in #59367. Without that fix, a tight estimate returns the OOM described there.

Not a duplicate: #51590 profiles every descriptor for the V1 runner (`gpu_model_runner.py`) and adds its own retained-memory term; this PR is the V2 runner (`vllm/v1/worker/gpu/cudagraph_utils.py`), which has its own `profile_cudagraph_memory` and is the default runner. The two share the shape of the answer, not the code. #50780 (the first FULL sample's mnbt-linear transient on hybrid GDN models) is the same class of pollution of the free-memory delta and is addressed by measuring the pool. #57936 (`--kv-cache-memory` suggestion double-counts the estimate) is the suggestion line in the worker and is untouched here.

## Test Plan

CPU unit tests (no GPU), on `vllm-openai:nightly` af7f9488c with the PR's `cudagraph_utils.py` mounted over the package:

```
python3 -m pytest -o addopts= tests/v1/worker/test_gpu_model_runner_v2_cudagraph_profiling.py -q
```

Serving: GLM-5.3-NVFP4 (`Inferact/GLM-5.3-NVFP4`), 4x H200 NVL, TP4 DCP4 EP, MTP 3, `fp8_ds_mla`, `max-model-len 786432`, `max-num-batched-tokens 8192`, `max-num-seqs 32`, `gpu-memory-utilization 0.945`, `FULL_AND_PIECEWISE` (35 PIECEWISE, 17 FULL, 17 + 7 speculator graphs). The PR was ported onto nightly af7f9488c together with the fix for #59317 and an instrumented log (per-FULL-graph free and pool deltas, allocator stats at each stage), then booted and run through 8x32k and 2x128k fresh prefills, the throughput bench and a 3x600k stress.

## Test Result

Unit tests: 4 failed / 9 passed on the base image (the new tests: pool + retained estimate, every FULL graph captured, free-memory fallback, `graph_pool_bytes`), 13 passed / 1 skipped (CUDA-only) with the PR.

Instrumented profiling pass, identical on all four ranks (bytes per rank):

| quantity | value |
|---|---|
| free-memory delta of the profiling capture (old `measured`, all 17 FULL captured) | 1.95 GiB |
| throwaway pool after the capture (`graph_pool_bytes`) | 0.91 GiB |
| non-torch memory grown during the capture | 0.92 GiB |
| torch memory reserved outside the pool during the capture | 0.12 GiB |
| per-FULL-graph free-memory deltas (old `mem_samples`, MiB) | -698, -374, -350, ..., -12, -10 |
| per-FULL-graph pool deltas (MiB) | 384, then 0 for the other 16 |
| old formula recomputed from the same samples | 2.33 GiB |
| retained after teardown (free before - free after) | 1.18 GiB (0.18 torch, 1.00 non-torch) |
| new estimate = pool + retained | 2.09 GiB |

Real capture: free-memory delta 1.02 GiB, global pool 0.91 GiB. Log line:

```
CUDA graph pool memory: 0.91 GiB (actual), 0.91 GiB (estimated), difference: 0.0 GiB (0.0%); 1.18 GiB retained by the profiling pass was reserved on top of the estimate.
```

Before (same host, stock nightly): `CUDA graph pool memory: 1.19 GiB (actual), 2.16 GiB (estimated), difference: 0.97 GiB (82.5%)`.

KV cache: 13.25 GiB / 1,039,616 tokens with this PR plus the #59317 fix, against 13.32 GiB / 1,045,248 tokens before. The budget did not grow: the old over-reservation was of the same size as the memory the profiling pass really retains, which this PR now reserves on purpose. What changed is that the estimate is the pool it claims to be and the retained part is visible.

Serving with both fixes: fresh prefill 8x32768 in 65.7 s (5092 tok/s; 5129 tok/s on the unpatched production image the same night), 2x131072 in 69.7 s (4941 tok/s; 4988 before), decode N=1 110.7, N=8 329.8, N=32 761.1 tok/s. The decode figures are single samples; across seven boots of the unpatched image that night N=8 ranged 263 to 317 tok/s and N=32 701 to 838 tok/s, so no decode change is claimed either way, stress 3x600k cold 3/3 in 373.8 s (370.8 s before) and replay from CPU offload 3/3, needle 200k at depth 0.1 retrieved. The needle ran concurrently with the stress, so the replay wall time (47.3 s against 2.4 s before) is contention with the needle prefill, not a measurement of the fix.

Second boot with `VLLM_MEMORY_PROFILER_ESTIMATE_CUDAGRAPHS=0` and only the #59317 fix (the combination that OOMed on the first 8x32k prefill before): KV cache 15.34 GiB / 1,203,712 tokens, fresh prefill 8x32768 in 63.0 s (5103 tok/s), 2x131072 in 72.6 s, decode N=1 119.1, N=8 279.2, N=32 823.9 tok/s, no errors; 0.8 GiB free per GPU while serving, so that configuration is not a recommendation.

### Before / after

| | v0.32.0 | with this PR |
|---|---|---|
| profiling capture free-memory delta | 0.62 GiB | 0.62 GiB |
| graph pool (estimated / actual) | 0.62 / 0.03 GiB (2150%) | 0.03 / 0.03 GiB (0.0%) |

The +400 tokens (≈22 MiB) match the transient I measured in the profiling capture (freed blocks still held by the caching allocator), which the PR no longer charges. The process footprint grows by the same amount, so nothing that stays resident is dropped.

### What the retained memory is here
Before trying the PR, I measured the same split by hand on v0.32.0, with `get_memory_info`, `memory_reserved` and `memory_allocated` around `capture_model(profile_only=True)`, and again after `profile_cudagraph_memory()` returned. Values are relative to just before the profiling capture:

| | MiB |
|---|---|
| profiling capture, free-memory delta | 630 |
| left after teardown + `empty_cache()` | 582 (396 torch, 186 non-torch) |
| real capture, free-memory delta | 28 |

582 MiB matches the PR's 0.57 GiB retained. An allocation trace of the profiling capture shows 394 MiB of the torch part is FlashInfer's global trtllm workspace, allocated on first use inside the capture:

```
vllm/v1/attention/backends/flashinfer.py:142  _get_trtllm_workspace_buffer
vllm/v1/attention/backends/flashinfer.py:2474  forward
...
vllm/v1/worker/gpu/cudagraph_utils.py:462  capture
```

With `--attention-backend TRITON_ATTN` on unpatched v0.32.0, the profiling delta drops from 0.62 to 0.21 GiB while the real capture stays at 0.03 GiB, consistent with that workspace being part of the retained memory.

Note: v0.32.0 does not include #61044 (cuBLAS handles created before memory profiling), so on newer builds part of the 186 MiB non-torch retained memory may move into the profile run's consumed memory instead.
