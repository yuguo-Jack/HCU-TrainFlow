# [Feature][KVEvents] Add state snapshots support

[Upstream PR](https://github.com/vllm-project/vllm/pull/57789) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Adds an opt-in snapshot endpoint to the ZMQ KV event publisher. A cache-aware router that starts late, restarts or misses events loads a rank's current cache state from it, then follows the live stream with no gap.

Related: #50134 solves the same problem differently (compared under Details). llm-d/llm-d-router#2946 is the router side. #59599 makes offload stores carry `extra_keys`.

## Claims

- Off by default; set `KVEventsConfig.snapshot_endpoint` to turn it on. With it off, live and replay messages are byte-identical to `main`.
- With it on, every batch gets one extra trailing field, `publisher_id`. msgspec decoders ignore it. Decoders that need the exact field count reject it, so consumers like llm-d-router need #2946 first.
- Each data-parallel rank serves its own snapshot: event batches that rebuild its cache state, plus the sequence of the last live batch they cover.
- A separate recorder thread builds snapshots. It shares the GIL, so the engine slows down while a snapshot is built. Engine cost on one H100 is under Validation.
- Memory is capped by `snapshot_max_blocks` (1M records) and `snapshot_max_response_bytes` (256 MiB).
- Covers GPU and offload tiers, KV cache groups that share a block size, LoRA, extra keys, locality and ownership. Blocks the recorder cannot rebuild are left out.
- `/kv_event_sources` and the Rust gRPC `GetKvEventSources` report the snapshot address (`vllm-proto` 0.7.0).
- Docs in `docs/features/kv_events.md`; example client in `examples/features/kv_events/kv_events_snapshot_subscriber.py`.

## Details

**Why.** Replay keeps only the last `buffer_steps` batches. A router that joins later misses every block stored before that, so it treats those prefixes as cold.

**How.** The recorder folds the event stream into one record per block hash: parent, tokens, hash inputs, and a reference count per scope (medium, KV cache group, locality, ownership). A snapshot replays those records as events. Dead records stay for 64 event batches, because an offload store can land after the GPU copy is gone. The docs have the full procedure.

**Cost.** The recorder runs on its own thread in the EngineCore process and shares the GIL, so building a snapshot takes engine time. Pausing the recorder often to hand back the GIL made it worse on the H100 (0.76x throughput, ITL p99 3.8x): the engine loses the same GIL time, spread over more steps. A recorder outside the engine process would remove the cost; that is left for a follow-up.

**Failure.** A queue that stays full for 1 s, an unsupported event, or an exceeded limit stops the recorder. It logs, frees its state and answers `-2` until the engine restarts. Live publishing continues. Snapshots only speed up router warm-up, so the engine keeps serving.

**Limitations.**
- KV cache groups with different block sizes restate one hash for different token spans, so snapshots leave those blocks out.
- Per-request `full` KV event reporting re-announces blocks as new stores. Use incremental reporting.

**Compared with #50134** (at c6f3328). #50134 builds each snapshot on the publisher thread and serves it on the replay socket, so live publishing waits while a snapshot is built. It tracks state whenever `replay_endpoint` is set. This PR uses a separate endpoint and thread, bounded memory, a publisher identity and heartbeats.

Addressed in 375020f:

- Wire format: the publisher identity is now a trailing `publisher_id` element of the batch (`IdentifiedKVEventBatch`). Sequence frames stay 8 bytes, and `KVEventBatch` decoders read these batches unchanged. With snapshots off, payloads are byte-identical to `main`.
- Taint is gone. The in-process stream is complete, but some events do not carry what is needed to rebuild a block: an offload store without tokens whose record already aged out, stores that skip blocks (sliding window, Mamba), and a hash restated with other inputs when KV cache groups have different block sizes. The export now leaves those blocks out, and a router learns them when they are stored again. Snapshots are best effort, which fits their job of warming a router.
- Failed state: it now covers only the bounded resources (input queue, `snapshot_max_blocks`, reply size) and unsupported events, in one path: log, free the recorder's memory, answer `-2`. I think restarting vLLM is too strong for an optional warm-up feature, since serving and live events are unaffected.
- `kv_events_snapshot` is simpler: bind in `__init__`, `queue.Queue`, batch objects in place of encoded bytes, one request per loop iteration, a strict REQ envelope. The module is 57 lines shorter.
- Overhead: the work runs on the publisher thread and a recorder thread, off the engine loop, and both take the GIL. Folding costs about 5 us per block and an export of 1M records about 1 s on my Mac (table in the description). The recorder no longer decodes batches. Engine-level latency under load is not measured yet.

@robertgshaw2-redhat I measured the engine cost on one H100, using a small model as the worst case:

- Recording alone costs about 2% throughput.
- Each snapshot costs the engine about as long as it takes to build, about 1 s for a full 375K-block cache, because the recorder holds the GIL while it builds. In an unrealistic stress test with a request every 5 s, throughput was 0.82x and TTFT p99 3x. Real use is about 2 snapshots per rank per day.
- Pausing the recorder to hand back the GIL made it worse (0.76x), so it is not in the PR.
- If the cost ever matters, the fix is a recorder outside the engine process, as a follow-up.
- Consumers that loaded a snapshot mid-run matched the full stream in every run.

The docs now say that decoders needing an exact field count, such as llm-d-router before llm-d/llm-d-router#2946, must upgrade before `snapshot_endpoint` is set.

**Non-blocking (AI-assisted): identity renewal makes healthy consumers drop exact state.**

`_served_unavailable` is set when any requester gets `-2`, and the identity renews here once the taint clears. Step 6 of the install procedure tells every consumer to clear its state on an identity change. That has two costs:

Clients that got `-2` already retry, so it might be simpler not to signal availability through the stream identity.

**Non-blocking (AI-assisted): GC-tracked records vs. `gc.freeze()`.**

`_Record` is a slotted Python class, so every instance is GC-tracked. Up to 1M of them accumulate after `freeze_gc_heap()` in `EngineCore.__init__`, which is there to shorten full-collection pauses. Full collections then walk every record under the GIL. `export()` also allocates one `children` list per parent, which makes a full collection during an export likely. Rough estimate, not measured: about 500 B per record and tens of ms per full collection near the cap.

The records hold no cycles, so `msgspec.Struct(gc=False)` (as the event structs use) should avoid this. The RSS and p99 numbers in the description are from an earlier revision; a current-revision measurement at a high block-event rate with offload would be useful.
