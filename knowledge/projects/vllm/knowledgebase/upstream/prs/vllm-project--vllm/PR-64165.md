# [Bugfix] Fix FlashInfer plan buffer race causing illegal memory access with PP

[Upstream PR](https://github.com/vllm-project/vllm/pull/64165) · state: open · merged: False

## Original PR description

## Overview

Fixes #63505. `FlashInferMetadataBuilder` could call FlashInfer `plan()` again before the GPU had copied the previous plan out of the wrapper's page-locked buffer. The earlier step's attention kernel then ran with the later step's plan and read out of bounds. This PR makes the builder wait for that copy before it plans again. The race became reachable with #57214.

## Claims

- Fixes the `illegal memory access` that kills the engine on the first long cold prefill with Qwen3.8-27B-FP8, `--pipeline-parallel-size=3`, chunked prefill and prefix caching.
- The wait covers every `plan()` call in `FlashInferMetadataBuilder.build()`: prefill, DCP prefill and decode (`fast_plan_decode`, which also plans the CUDA-graph decode wrappers). The TRTLLM/XQA paths do not call `plan()`, so they neither wait nor record.
- The host waits only when it is more than one plan ahead of the GPU. On one GPU with async scheduling it never blocked (0 of 2000 builds).
- New test `test_flashinfer_plan_waits_for_previous_plan_copy` (prefill and decode cases) fails without the fix and passes with it.

## Details

**Root cause.** FlashInfer's `plan()` writes its plan (request, tile and merge indices) into a page-locked host buffer owned by the wrapper. Then it copies that buffer to the GPU with `cudaMemcpyAsync` and does not wait. `FlashInferMetadataBuilder` reuses the same wrappers every step. If the host calls `plan()` again before the GPU has run the previous copy, the previous step's kernel reads the next step's plan. It reads page indices out of range and faults. This matches the Xid 31 `FAULT_PDE ACCESS_TYPE_VIRT_READ` in the issue thread.

**How it was found.**

- A CUDA core dump (`CUDA_ENABLE_COREDUMP_ON_EXCEPTION=1`) names the faulting kernel: `CUDBG_EXCEPTION_WARP_MMU_FAULT` in `flashinfer::BatchPrefillWithPagedKVCacheKernel` (bf16 query, fp8 KV) on PP rank 0. The GDN frames in the issue are only where the asynchronous error was reported.
- A debug print before each prefill `plan()` checked, without blocking, whether an event recorded after the previous `plan()` had completed. The 27,423-token prompt is cut into chunks of 4704 (five times), 3136 and 767 tokens. The plan for the last 767-token chunk was written while the copy of the 3136-token plan was still pending. That was the only such case in the log, and the illegal memory access came right after it.
- With PP=3 the scheduler keeps up to three steps in flight, so a stage gets the next chunk before its GPU has finished the earlier ones. That is why PP with chunked prefill hits this. The race needs the host to be at least two plans ahead, so changes in timing (eager mode, `CUDA_LAUNCH_BLOCKING=1`) hide it.

**Why it is a regression.** Before #57214 (in v0.31.0, not in v0.30.0), `build()` called `common_attn_metadata.seq_lens.cpu()` on every step of the native FlashInfer paths. That blocking copy drained the stream, so the previous plan's copy had always run before the next `plan()`. #57214 replaced it with the CPU upper bound when there is no speculative decoding. This matches the report: v0.28.0 good, v0.31.0 bad.

**The fix** (6 lines in `flashinfer.py`). The builder records a CUDA event after its `plan()` calls and synchronizes on it before the next ones. Both happen only when `needs_paged_kv_indices` is true, which is exactly when `build()` calls a wrapper's `plan()`. This follows `synchronize_input_prep` in `gpu_model_runner.py`, which does the same for vLLM's own reused CPU buffers. The event is created with `blocking=True`, so the host sleeps during the wait instead of spinning. Each builder has its own wrappers and its own event. `synchronize()` on an event that was never recorded returns at once.

**Cost.** The host blocks only when it is more than one plan ahead of the GPU, which is exactly when the race can happen. One GPU with async scheduling: 0 of 2000 builds blocked. PP=2 with Qwen2.5-0.5B: 69 of 1000 builds blocked, up to 8.5 ms each. A wait never lasts more than one plan step, which is less than the full stream drain of `seq_lens.cpu()` before #57214. In that PP=2 setup the base commit also crashed in 1 of 3 runs, and this PR in 0 of 3.

<details>
<summary>Alternatives considered</summary>

- Bring back `seq_lens.cpu()` in `build()` (revert #57214 for this path). It fixes the race only as a side effect, and it drains the stream on every step for every FlashInfer user.
- Use two or more wrappers in turn. This only lowers the chance: with PP the host can be `pp_size` or more steps ahead, so it still needs events, and each wrapper costs its own buffers.
- Give the wrapper a fresh pinned buffer before each `plan()`. PyTorch's caching host allocator does not see FlashInfer's `cudaMemcpyAsync`, so it can hand the freed buffer out again while the copy is pending.
- Fix it in FlashInfer, so that `plan()` guards its own buffer. Worth raising upstream, but vLLM has to work with the FlashInfer version it uses.

</details>

**Limitations.**

- Not changed: the MLA FlashInfer prefill wrappers (`vllm/v1/attention/backends/mla/prefill/flashinfer.py`), the sparse SM90 MLA backend and the step5 sparse ops. They also call `plan()` on reused objects, but they have their own builders and were not tested here. The MLA prefill path is safe today only because it passes GPU indptrs to `plan()`, and FlashInfer copies them to the CPU with a blocking copy. #52657 plans to remove that copy, which would expose this path to the same race.
- The issue also reports gibberish output with `--no-enable-prefix-caching`. On 3 x A10 that config runs out of GPU memory on the cold prompt, with and without this PR, so I could not check it. This PR makes no claim about it.

**Why one GPU sees it here.** This card has one copy engine per direction. A 64 KiB pinned host-to-GPU copy took 0.05 ms alone, 0.10 ms beside 1 GiB moving GPU-to-host, and 158.8 ms beside 1 GiB moving host-to-GPU on another stream, the whole of the big copy (158.9 ms). The connector's loads go by DMA (`cuMemcpyBatchAsync`: its Triton copy kernel takes only pages under 28 KiB, and FP8 pages here are 32 KiB), so a plan's small copy can queue behind a resumed session's prefix, up to about 1.8 GB, for a couple of hundred milliseconds while the host plans the next step into the same buffer. Without the CPU tier the same counter found the copy pending in 0 of 10,000 builds. That would explain why your single-GPU run saw 0 of 2,000 builds wait and this one about one in 80.

A CUDA core dump of a stock crash (`CUDA_ENABLE_COREDUMP_ON_EXCEPTION=1`, `CUDA_COREDUMP_GENERATION_FLAGS` with `skip_abort`, read with cuda-gdb) names the faulting kernel: `flashinfer::PersistentVariableLengthMergeStatesKernel<8u, 16u, 8u, 4u, __nv_bfloat16, __nv_bfloat16, int>`, a warp illegal address, the kernel cpuchip's dumps named in #61239. It merges at indices the plan gives, which fits a plan built for another step.

Every run's logs are in [this record](https://github.com/StevenWang-CY/flatshare/tree/v1.14/benchmarks/results/2026-10-31-fp8-crash), and the harness that ran them is in [`benchmarks/fp8`](https://github.com/StevenWang-CY/flatshare/tree/v1.14/benchmarks/fp8).
