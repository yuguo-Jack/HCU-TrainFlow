# tracing: propagate active server span via headers

[Upstream PR](https://github.com/vllm-project/vllm/pull/43005) · state: closed · merged: False

## Original PR description

## Purpose

This PR fixes parent/child relationships for tracing spans in the OpenAI serving path when OpenTelemetry tracing is enabled.

Today, `_get_trace_headers()` forwards tracing information by extracting the raw incoming request headers. That preserves the upstream trace context, but it misses an important detail when OTel auto-instrumentation is active in the API server: by the time `_get_trace_headers()` runs, there is already an active FastAPI/server span in the current request context.

Later in the request lifecycle, tracing work happens in a different async context/task. At that point, the code reconstructs trace context from the forwarded headers and creates the downstream `llm_request` span. Because the forwarded headers came from the original request rather than the currently active server span, the downstream `llm_request` span ends up attached to the original upstream parent instead of the active FastAPI/server span.

In practice, this means:

- the FastAPI/server span and the downstream vLLM `llm_request` span become siblings
- the trace tree does not accurately reflect request handling inside the API server

This PR fixes that by capturing the **current active span context** at request time and serializing it into W3C trace headers. Those headers are then propagated through the engine pipeline and later re-extracted when the downstream span is created, allowing `llm_request` to become a child of the active server span instead of a sibling.

Concretely, this PR:

- adds `inject_current_trace_headers()` to `vllm/tracing/otel.py`
- exports the helper from `vllm.tracing`
- updates `OpenAIServing._get_trace_headers()` to prefer injecting the current active span context and to fall back to the existing raw-header extraction behavior when no active span is available
- adds a focused tracing test that verifies injected current-span headers can be extracted and used to create a child span with the expected parent relationship

This keeps the change low-risk because environments without OTel auto-instrumentation still preserve the old behavior via fallback.

This change ensures that downstream spans are correctly nested as children of the current span (e.g., a FastAPI server span) rather than being treated as siblings.
