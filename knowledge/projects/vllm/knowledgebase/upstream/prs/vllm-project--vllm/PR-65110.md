# [Perf][HY4] Speed up the iHC pre reduction with M-blocked and split-K paths

[Upstream PR](https://github.com/vllm-project/vllm/pull/65110) · state: open · merged: False

## Original PR description

## Overview

Reworks the HY V4 iHC Triton kernels: `triton_ihc_pre` gets an M-blocked
K-reduction with a split-K path for small token counts, and `triton_ihc_post`
tiles the whole hc dimension at once. No change in numerical output.

## Claims

- **`triton_ihc_pre` is 1.4-2.7x faster from 64 tokens up** — 2.22x at 1024,
  2.33x at 4096, 2.38x at 16384, 2.67x at 32768 (H100, `hidden_size=6144`,
  `hc_mult=4`, bf16).
- **`triton_ihc_post` is 1.04-1.12x from 64 tokens up** — effective bandwidth
  2878 → 3018 GB/s at 16384 tokens, ~90% of H100 HBM3 peak.
- **No accuracy loss** — both kernels match the current ones across 18 token
  counts from 1 to 32768 at `hidden_size` 4096 and 6144; post stays bitwise
  equal to the torch reference.
- **End-to-end +9.4% request throughput and -8.5% median TTFT** for
  1024-token prefill at concurrency 64 on 8×H100, and -2.6% single-request
  TPOT across all four workload shapes tested.
- No regression at any measured shape or workload. Shared memory unchanged
  (12288 B), no register spills.

## Details

**pre** — stage1 previously re-read the `x` tile once per projection row. It
now blocks over tokens (`_BLOCK_M`) and loads each tile once to feed all
`2*hc_mult` rows. Below `_MBLOCK_MIN_TOKENS` that path starves, so a split-K
variant takes over: one program per `(token, K-chunk)`, all projection rows
read as a single tile.

**post** — pure streaming (`out = post * x + residual`), so only the access
pattern was left. Handling the whole hc dimension as one `[hc, BLOCK_D]` tile
turns the residual loads and stores into single 2D accesses, and a D-major
grid keeps consecutive programs contiguous.

<details>
<summary>Design decisions and tradeoffs</summary>

**Why two pre paths rather than one.** The split-K and M-blocked variants
duplicate the gating math (sigmoid, rsqrt, channel reduction). Merging them
would need a branch inside the kernel, which Triton compiles as both paths
with the union of their register pressure. Measured at the crossover: forcing
both paths at 384 tokens, split-K is 1.17x faster; at 512 M-blocked wins by
1.03x. Keeping them separate costs ~60 lines and keeps each specialization
tight.

**Why fp32 accumulation, not `tl.dot`.** `tl.dot` in bf16 exceeds the gate
tolerance at `K = hc_mult * hidden_size` (24576 for HY V4). Both variants
accumulate in fp32 throughout.

**Why stage2 reduces in index order.** Both variants write per-split private
slots; stage2 sums them by index, so the result does not depend on which block
finishes first. This keeps pre at two launches without a third reduction
kernel, and makes the output reproducible run to run.

**Block sizes**, from a sweep on H100 at `hidden_size=6144`, `hc_mult=4`:

| constant | value | rationale |
| --- | --- | --- |
| `_BLOCK_M` | 32 | with `_BLOCK_K=64`, beats 8/128 by 13-17% between 384 and 32768 tokens |
| `_BLOCK_K` | 64 | shared memory stays at 12288 B (same as 8/128), no spills |
| `_MBLOCK_MIN_TOKENS` | 512 | measured crossover, see above |
| `_POST_BLOCK_D` | 512 | swept 256/512/1024/2048 × 2/4/8 warps; 512/4 optimal at every shape above 32 tokens |

`_BLOCK_M=32` was checked for occupancy before adopting: shared memory is
12288 B (5.3% of H100's 227 KB per-block limit) and the PTX shows zero
register spills, identical to `_BLOCK_M=8` — `BLOCK_M` rising 4x while
`BLOCK_K` halves keeps the `x` tile the same size.

**No host-device sync added.** The dispatch logic is Python integer
arithmetic on shapes; no `.item()`, `.cpu()`, or `.tolist()` on the execution
path.

</details>

<details>
<summary>Pre-existing limitation found while benchmarking</summary>

`_ihc_post_kernel` launches with
`grid = (cdiv(hidden_size, _POST_BLOCK_D), num_tokens)`, placing the token
count on the grid's Y dimension, which CUDA caps at 65535. A single post call
with `num_tokens >= 65536` fails with `CUDA Error: invalid argument`.

**This is unchanged from the current kernel** — both versions share the grid
layout — and is not reachable with the default `max-num-batched-tokens`. pre
is unaffected: its token count is on the X dimension (capped at 2³¹).

Swapping the two dimensions would fix it but inverts the D-major traversal
that this PR's post optimization relies on, so it needs either a blocked
token dimension or a re-measurement of the bandwidth gain. Happy to address
it here or in a follow-up, whichever reviewers prefer.

</details>
