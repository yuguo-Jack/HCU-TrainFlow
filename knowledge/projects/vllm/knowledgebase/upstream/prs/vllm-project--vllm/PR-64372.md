# [Bugfix] Fix thinking_token_budget for Mistral control tokens

[Upstream PR](https://github.com/vllm-project/vllm/pull/64372) · state: open · merged: False

## Original PR description

## Motivation

`tokenizer.encode()` treats control tokens like Mistral's `[THINK]` and `[/THINK]` as literal text, splitting them into multiple sub-word token IDs (4 IDs instead of 1). This causes `thinking_token_budget` to over-count reasoning tokens and cut off thinking prematurely for Mistral Magistral models.

Reported in #64309.

## Root cause

`ReasoningConfig.initialize_token_ids()` calls `tokenizer.encode(marker_str, add_special_tokens=False)` for all reasoning markers. For control tokens registered in the tokenizer vocabulary as single entries (like `[THINK]`), `encode()` treats the brackets and text as separate subwords. The resulting multi-ID sequence then fails to match the single token the model actually emits, breaking budget tracking.

## Fix

Add `_resolve_token_ids(tokenizer, marker)` helper that:
1. First tries `convert_tokens_to_ids(marker)` -- returns the correct single ID for registered control tokens
2. Falls back to `tokenizer.encode()` for multi-token markers like `<think>` that aren't single vocab entries

Applied at all three marker resolution sites in `initialize_token_ids()`.

## Tests

Added `tests/config/test_resolve_token_ids.py` with 4 test cases:
- Control token resolves to single ID via `convert_tokens_to_ids`
- Unknown marker falls back to `encode`
- `unk_token_id` return triggers fallback
- `None` return triggers fallback

Fixes #64309
