# [ROCm][Perf] Skip the AITER packed GDN path under speculative decoding

[Upstream PR](https://github.com/vllm-project/vllm/pull/62381) · state: open · merged: False

## Original PR description



## Overview

With `VLLM_ROCM_USE_AITER=1` and speculative decoding, `QwenGatedDeltaNetAttention.forward_hip` now uses the generic `forward_cuda` path instead of the AITER packed qkvz/ba path. With spec tokens, the AITER path never reaches its decode kernel and only adds unpacking copies before the same `_forward_core`.

Part of the DFlash2-on-ROCm plan in #61761.

## Claims

- Qwen3.8-27B + `z-lab/Qwen3.8-27B-DFlash2` (7 draft tokens), one MI355X, `VLLM_ROCM_USE_AITER=1`: output throughput +1.6% / +1.5% / +1.7% at concurrency 1 / 16 / 64 (mean of 2 runs).
- Per target step, GPU kernel time drops by 400–600 µs at 1 and 8 requests. The fix removes the extra elementwise and copy kernels, so the GDN layers run the same kernels as without AITER.
- No accuracy change: acceptance length is the same, and GSM8K (5-shot, 1319 questions) is 0.785 → 0.783, which is 3 questions.
- Nothing changes without speculative decoding or without AITER.

## Details

**Root cause.** `GDN_AITER_TRITON_AVAILABLE` is true whenever `VLLM_ROCM_USE_AITER=1` and the aiter GDN Triton kernels can be imported. There is no separate switch for it. `forward_hip` then:
1. computes the packed qkvz/ba projections;
2. calls `qwen_gdn_attention_core(..., use_aiter=True)`, i.e. `_forward_core_rocm`.

`_forward_core_rocm` uses `_forward_core_decode_aiter` only when `spec_sequence_masks is None and num_prefills == 0`. With speculative decoding, every decode step has spec tokens, so it always takes the fallback:
- `core_attn_out.zero_()`;
- `prepare_gdn_attention_core_inputs` to unpack qkvz/ba;
- `z_out[:] = z`;
- `_forward_core`.

`forward_cuda` reaches the same `_forward_core` without these copies.

**Change.** `forward_hip` takes the AITER path only when `self.num_spec == 0`.

**Tradeoff.** With speculative decoding on, a batch with no spec tokens, such as a plain decode step after the drafter proposed nothing, also uses the generic path instead of the AITER decode kernel. Such batches are rare.

**Overlap with #61855.** #61855 changes the same line to `not self.enable_fused_gdn_spec_decode`, so that ROCm uses its fused MTP kernel through `forward_cuda`. Its flag is true only when `speculative_config` is set, so `not self.num_spec` covers it. This PR also covers the cases #61855's kernel does not take, for example:
- `VLLM_GDN_DECODE_KERNEL=triton`;
- the interleaved layout (Qwen3-Next);
- more than 8 tokens per request.

Whichever PR lands second keeps `not self.num_spec`.

**Benchmark.** Run this against each server. Acceptance length is `1 + accepted / drafts`, computed from the deltas of the spec decode counters in `/metrics`.

```bash
DS=/path/to/ShareGPT_V3_unfiltered_cleaned_split.json
counts() {
  curl -s localhost:8000/metrics | awk '/^vllm:spec_decode_num_drafts_total/{d=$2}
    /^vllm:spec_decode_num_accepted_tokens_total/{a=$2} END{print d+0, a+0}'
}
for C in 1 16 64; do
  N=$(( C * 8 < 64 ? 64 : C * 8 ))
  read D0 A0 <<< "$(counts)"
  vllm bench serve --backend vllm --port 8000 --model qwen --tokenizer /models/Qwen3.8-27B \
    --dataset-name sharegpt --dataset-path $DS --sharegpt-output-len 512 \
    --num-prompts $N --max-concurrency $C --seed 0 --temperature 0 | grep -E "Output token throughput|Mean TPOT"
  read D1 A1 <<< "$(counts)"
  python3 -c "d = $D1 - $D0; print('C=$C acceptance length', 1 + ($A1 - $A0) / d if d else 'n/a')"
done
python3 /work/vllm/tests/evals/gsm8k/gsm8k_eval.py --port 8000 --max-concurrency 64
```
