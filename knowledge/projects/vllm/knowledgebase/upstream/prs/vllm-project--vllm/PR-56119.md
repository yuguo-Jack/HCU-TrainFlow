# [Bugfix][Quantization] Dequantize directly-consumed block-FP8 weights before Marlin repacks them

[Upstream PR](https://github.com/vllm-project/vllm/pull/56119) · state: open · merged: False

## Original PR description

## What this fixes

On devices without FP8 hardware (SM 8.x / A100 / A800) the FP8 quant method selects Marlin. Marlin's
`process_weights_after_loading` repacks `layer.weight` into an opaque layout and rewrites the block scales
(folding an exponent bias into them). That is fine for layers that go through `apply_weights()`, but some
layers are consumed **directly**: DeepSeek-V4's `o_proj` sets `layer.is_bmm = True` and reads `layer.weight`
together with its block scales in a fused FP8 einsum. With Marlin selected it reads packed integers as FP8
and the model emits garbage. Checked against `main` today: `is_bmm` appears nowhere in
`quantization/fp8.py`, so nothing currently prevents this.

## The fix

In `Fp8LinearMethod.process_weights_after_loading`, before the `if self.use_marlin:` branch, when
`use_marlin and block_quant and getattr(layer, "is_bmm", False)` the weight is dequantized to bf16 using the
**original** block scales and the method returns early, skipping kernel processing entirely. Such a layer
never calls `apply_weights()`, and the model's existing bf16 fallback then handles it (the model's `use_fp8`
check keys off `wo_a.weight.dtype`). A small helper `dequantize_fp8_block_weight_to_bf16` does the
dequantization in fp32 with a single rounding, accepts fp32 or e8m0 scales, and raises on anything it cannot
interpret.

## Scope

- No behaviour change for any other layer: the branch is gated on `is_bmm`.
- The SM90+ DeepGEMM path is untouched: the gate is `use_marlin`, not `is_deep_gemm_supported()`, because that
  path already handles `is_bmm` itself.
- This is a **correctness** fix, not a performance one. It does not preserve FP8 compute for these layers on
  SM 8.x; they run the bf16 path instead. The earlier draft of this PR also carried a ~320-line portable
  Triton FP8 einsum kernel; it is **dropped**, because the existing bf16 fallback is sufficient for
  correctness and a bespoke kernel for one model on one architecture is not something we can maintain.

## Testing

- Nine unit cases for the helper: expansion against a manual reference for `(128,128)`, `(128,64)` and
  `(1,32)` blocks, e8m0 scales, "the scale is a multiplier, its `_inv` name is legacy", and four rejection
  cases (non-FP8 weight, wrong scale grid, non-divisible shape, unsupported scale container).
- Two integration tests that drive `Fp8LinearMethod.process_weights_after_loading` on a block-quantized
  `is_bmm` layer with a Marlin kernel, asserting the weight ends up bf16, `input_scale` is cleared and
  Marlin's repack is **not** called; plus a regression case that a non-`is_bmm` layer still goes to Marlin.
- All of the above pass against a built tree (11 passed).
- Not yet exercised end to end on real DeepSeek-V4 hardware; we would welcome guidance on the shape of an
  SM 8.x end-to-end test.
