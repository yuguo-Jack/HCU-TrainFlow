# [Bugfix] Size the HiSparse hot buffer from the rounded sparse top-k width

[Upstream PR](https://github.com/vllm-project/vllm/pull/60805) · state: closed · merged: True

## Original PR description

## Overview

HiSparse sized its scheduler hot-cache allocation from `index_topk`, while GLM-5.3-Flash allocates a wider, padded top-k buffer. This updates the existing fix in #60805 following review; related GLM support is tracked in #61243 and #60072.

## Claims

- Keep GLM's width calculation in its model definition, shared with MTP. Pass the actual allocated width through `MLAAttentionSpec` so HiSparse does not need to import GPU model code in the scheduler.
- Allow custom `device_buffer_size` values whose physical allocation includes block padding, by removing the startup equality assertion.

## Validation

All applicable pre-commit hooks pass, including Ruff, mypy, test tethering, and forbidden-import checks. No new tests are included; existing MLA test fixtures only gain the metadata field required by the code change.

The normal focused pytest run cannot collect on this macOS ARM checkout due to missing vLLM dependencies. The documented precompiled editable install also fails because no macOS ARM wheel is available. CUDA startup, model evaluation, and full pytest remain to be run in a supported environment.

## Details

For `index_topk=2048` and `index_kpool=4`, the model reserves the incomplete pool tail and rounds the buffer width to 2176. With seven speculative tokens, HiSparse therefore needs `9 * 2176 = 19584` default hot rows per request, rather than `9 * 2048 = 18432`. The scheduler now receives this width from the model's cache specification, preserving the model's own sizing rules.

A user-selected capacity can differ from the physical allocation: 129 logical rows occupy three 64-row blocks. Registration must accept that padding.

AI assistance was used to implement and review these changes. The existing PR is updated rather than opening a duplicate; no broader GLM enablement is included.
