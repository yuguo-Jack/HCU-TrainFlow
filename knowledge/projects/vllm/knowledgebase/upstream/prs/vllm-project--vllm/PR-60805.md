# [Bugfix] Size the HiSparse hot buffer from the rounded sparse top-k width

[Upstream PR](https://github.com/vllm-project/vllm/pull/60805) · state: open · merged: False

## Original PR description

## Description

HiSparse sizes the per-request hot buffer twice, from two different values. The scheduler builds `ResolvedHiSparseConfig` from `hf_config.index_topk`; the model allocates the top-k buffer at `round_up(index_topk + kpool - 1, 128)` wide and derives `region_stride` from that width. For any `index_kpool > 1` model the stride is strictly larger than the scheduler-sized table, so the CUDA resolver's `hot_block_table` column check fails at the first host-backed decode ("hot_block_table has too few columns"), and with a larger explicit `device_buffer_size` the hot set silently mispredicts rows instead. Existing A/Bs never hit it because the validated models are kpool == 1.

This makes both sides read one shared `get_sparse_topk_buffer_width()` and asserts `blocks_per_request * block_size == region_stride` in `HiSparseConnectorWorker.register_kv_caches`, so a future mismatch fails at startup instead of mid-decode. DeepSeek-style kpool == 1 configs resolve to exactly `index_topk` and keep their sizing.

| model | scheduler rows (before) | worker rows | before | after |
|---|---|---|---|---|
| GLM-5.3-Flash (topk 2048, kpool 4) | 9 * 2048 = 18432 | 9 * round_up(2047, 128) = 19584 | column check fails / hot set off by 1152 rows | 19584 == 19584, boots clean |
| DeepSeek-style (kpool 1) | 9 * 2048 | 9 * 2048 | unchanged | unchanged |

Verified at block sizes 32/64/128 with the GLM-5.3-Flash MTP k=7 shape (19584 == 306 * 64).
