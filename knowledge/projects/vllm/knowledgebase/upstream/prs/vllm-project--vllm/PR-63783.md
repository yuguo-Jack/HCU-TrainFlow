# [Bugfix][Responses API] Add completed_at to ResponsesResponse

[Upstream PR](https://github.com/vllm-project/vllm/pull/63783) · state: open · merged: False

## Original PR description

## Overview

Fixes #63183

`/v1/responses` responses with `"status": "completed"` never carried `completed_at`, so OpenAI-SDK clients reading `response.completed_at` always got `None`. The OpenAI Response object defines `completed_at` as the Unix timestamp (seconds) of completion, present when `status` is `completed`.

## Claims

- `ResponsesResponse` gains `completed_at: int | None` (default `None`).
- `ResponsesResponse.from_request()` sets `completed_at=int(time.time())` when `status == "completed"`, else `None`.
- `from_request` is the single construction point for completed responses, so all paths are covered: non-streaming final responses (`serving.py` ~L929) and background completion flows build their final objects through it, while background initial (`"queued"`, ~L546) and streaming initial (`"in_progress"`, ~L1381) constructions keep `None` automatically. The only in-place status mutation on stored responses is the `"failed"` transition (`serving.py` L1120), where `completed_at` correctly stays `None`.
- Invariant: `completed_at >= created_at` always holds — `from_request` is invoked when the response finishes, so the current time is the completion time while `created_time` was captured at creation.

## Validation

Unit tests (`tests/entrypoints/openai/responses/test_responses_completed_at.py`, CPU-only, no model weights or GPU needed):

- `status="completed"` → `completed_at` is not `None` and `>= created_at`
- `status in {queued, in_progress, failed, cancelled}` → `completed_at` is `None`

Repro from the issue against a served model now behaves as expected:

```sh
curl -s http://localhost:8000/v1/responses -H 'Content-Type: application/json' \
  -d '{"model":"<model>","input":"Reply with the single word: ok","store":false}' \
  | jq -c '{status, created_at, has_completed_at: has("completed_at")}'
# {"status":"completed","created_at":<t>,"has_completed_at":true}
```

## Details

Root cause: `ResponsesResponse` (protocol.py) carried `created_at` and `status` but never defined `completed_at`, and the single `from_request` constructor had no completion timestamp to set. The fix adds the field and populates it at that single point rather than threading timestamps through three call sites, keeping background/streaming initial states correct by construction.
