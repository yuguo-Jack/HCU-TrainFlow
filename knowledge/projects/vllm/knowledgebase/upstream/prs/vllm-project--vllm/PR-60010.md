# [Bugfix][Benchmark] Clean up sweep workers after the server exits

[Upstream PR](https://github.com/vllm-project/vllm/pull/60010) · state: open · merged: False

## Overview

Fix benchmark sweep cleanup when a server exits before its workers: terminate the surviving process group and reap the directly owned server process.

## Claims

- `ServerProcess.stop()` terminates workers that remain in the original process group after its leader has exited and been reaped.
- Cleanup reaps the direct child and remains safe to call again after successful cleanup.

## Details

`start_new_session=True` makes the server PID the process group ID. Previously, cleanup depended on `poll() is None`, so a reaped leader prevented cleanup of surviving workers. Looking up its PGID also requires the leader to exist. Signal the known group ID directly, retain the existing SIGKILL behavior, then wait for the direct child. A per-start completion flag prevents subsequent calls from signalling the old group again. Only a missing process group is suppressed; other errors still propagate.

The scope is workers that remain in the server's group. This does not wait for every grandchild, cover detached sessions, or guarantee GPU-memory release. Waiting for the direct child adds synchronous shutdown waiting. Numeric PGID reuse remains a consideration if the whole group disappears long before the first cleanup call.

File: `tests/benchmarks/sweep/test_server_process.py` · line 67

🟡 nit (optional): On every passing run, the test's cleanup sends SIGKILL to a process group whose leader was already reaped. If the PID is reused, an unrelated process group could be killed. The `finally` block calls `os.killpg(server._server_process.pid, signal.SIGKILL)` unconditionally, even after `server.stop()` has already killed the group and reaped the leader. Fix: in the finally block, run the killpg/wait only when the process has not been reaped yet, for example `if server._server_process.returncode is None:`. That still covers the leaked-worker case on a failing assertion before `stop()`.

<details>
<summary>Why this was flagged</summary>

In the passing path, `server.stop()` (vllm/benchmarks/sweep/server.py:63-65) SIGKILLs the group and reaps the leader. For parent_exits=True, `process.wait(timeout=10)` had already reaped it. After that the PID and PGID are free for reuse. The finally block at tests/benchmarks/sweep/test_server_process.py:64-67 still calls `os.killpg(server._server_process.pid, signal.SIGKILL)`. On a busy CI host (for example under pytest-xdist), a new session or group leader could have received that PID. It would then get SIGKILLed, and ProcessLookupError only suppresses the case where nobody holds it. This is the same reuse hazard the PR description mentions for production, but here it is hit unconditionally on every successful test run, not only when a group dies before cleanup.

**Verification:** The `finally` block at tests/benchmarks/sweep/test_server_process.py:64-67 runs `os.killpg(server._server_process.pid, signal.SIGKILL)` with no check, guarded only by `contextlib.suppress(ProcessLookupError)`. If another process had become a group leader with that PID, it would be SIGKILLed. The risk is limited to the test (no production code path does this).
