# [ROCm] Enable tuned AITER per-token FP8 linear on RDNA4  (a8w8 on RDNA3 WIP) 

[Upstream PR](https://github.com/vllm-project/vllm/pull/60672) · state: open · merged: False

## Original PR description

## Purpose

Enable the existing unshuffled AITER per-token FP8 scaled-MM linear kernel on RDNA4 when AITER linear operations are enabled and the installed AITER package has a tuned configuration for the layer shape. This provides an opt-in AITER path for the regression discussed in #57838. Related: #57861.

The change routes W8A8 GEMM through AITER's architecture-aware `gemm_a8w8` dispatcher. RDNA4 checks AITER's `GEMM-A8W8` Triton tuning entries; other ROCm architectures (`gfx9x`, `gfx1250`) retain the CK tuning check. Shapes without an accepted tuning entry fall through to the existing kernels during automatic selection.

Tuning configurations belong to the AITER repository and are supplied by the installed AITER package. The companion gfx1201 GEMM A8W8 tuned configurations are in [ROCm/aiter#6245](https://github.com/ROCm/aiter/pull/6245). This PR changes only `vllm/_aiter_ops.py` and the existing AITER scaled-MM kernel support gate.

Enable with `VLLM_ROCM_USE_AITER=1` and `VLLM_ROCM_USE_AITER_LINEAR=1`. 

## Validation

Test environment: Radeon AI PRO R9700 / gfx1201 (one GPU for TP1, two for TP2), Torch 2.13.0+rocm10, and Triton 3.8. Model: `RedHatAI/gemma-4-12B-it-FP8-Dynamic`.

**Serving smoke tests passed for all four configurations:** TP1/TP2 with AITER linear disabled/enabled. Each completed 18 successful chat requests, including eight concurrent two-turn conversations and a 512-token completion (72 requests total). Full decode graph capture covered batch sizes 1/2/4/8. Logs confirmed Torch RowWise when AITER linear was off and `AiterPerTokenFp8ScaledMMLinearKernel` when on.

@amd-xavierwang following up on the RDNA3 enablement discussion: we benchmarked the individual AITER Triton kernels on **two RX 7900 XTX / gfx1100 GPUs**. The results suggest **A16W8 is a more suitable candidate for the RDNA3 extension** than software-emulated A8W8. @hyjuunn is helping work on the A16W8 path to enable RDNA3.

The comparison uses **per-channel FP8 weight scales**, matching the weight-scale layout relevant to this PR:

- **A8W8:** `gemm_a8w8`, FP8 E4M3FN activations with dynamic per-token scales and FP8 E4M3FN weights with per-channel scales.
- **A16W8:** `gemm_a16w8_blockscale(prequant=False)`, original BF16 activations and the **same FP8 weights**, with weight scales passed as `(N, 1)`. No weight requantization or preshuffle.

**A16W8 was faster in all 50 cases: 4.11–7.80× faster than A8W8, with a median speedup of 5.44×.** These are GEMM-only timings, excluding activation quantization. Including AITER per-token activation quantization in the A8W8 path gave a separately measured median speedup of **5.62×** for A16W8.

| M | Median A16W8 speedup over A8W8 | Range across five shapes and two GPUs |
|---:|---:|---:|
| 1 | 5.65× | 4.26–7.70× |
| 4 | 5.65× | 4.11–7.65× |
| 32 | 5.62× | 4.44–6.49× |
| 128 | 5.26× | 4.76–6.34× |
| 1024 | 5.25× | 4.22–7.80× |

**Accuracy:** median relative L2 error against an FP32 reference computed from the original BF16 inputs was **2.6456% for A16W8 vs 3.7384% for A8W8**. Relative L2 is `||output - reference||₂ / ||reference||₂`. Against each path's dequantized-input FP32 reference, arithmetic-only error was approximately **0.166% for both**, and all correctness checks passed. A16W8 avoids the activation quantization error. These are random-input operator checks, not downstream model-quality results.

**Compiled ISA:** disassembled code objects show `v_wmma_f32_16x16x16_f16` for A8W8 and `v_wmma_f32_16x16x16_bf16` for A16W8, both with FP32 accumulation. On gfx1100, A8W8 software-converts both FP8 operands; A16W8 converts only the FP8 weight tiles and keeps activations in BF16. Neither uses native FP8 matrix instructions. A16W8 keeps the weights in FP8 VRAM storage without materializing a full BF16 weight matrix.

**Configuration limitation:** neither operator has a gfx1100 default configuration in the installed AITER revision. We explicitly borrowed the corresponding gfx1100 **blockscale A8W8** shape configurations and reused them for both operators. **Neither operator was independently tuned in this comparison.** The gains apply to these measured configurations; they do not establish peak performance or end-to-end serving gains. This per-token/per-channel study is separate from our earlier 128×128 block-scaled comparison.

For vLLM integration, A16W8 needs a **separate path that preserves the original BF16 activation**: `input_quant_key()` should return `None`, and `apply_weights` should bypass activation FP8 quantization. Swapping the GEMM after activations have already been quantized would lose that benefit. An explicitly forced experimental adapter passed **32 compatibility cases across both GPUs** (24 nonempty, 8 empty), covering channel/tensor weight scales, optional bias, 2D/3D inputs, fullgraph dynamic `torch.compile`, and HIP graph replay. The adapter adds bias after GEMM rather than fusing it; it is not registered for automatic selection.

The suggested direction is to add/tune the A16W8 backend for gfx1100/RDNA3 while keeping RDNA4's native-FP8 A8W8 path separate. Accepted gfx1100 tuning belongs in AITER. **Full-model A16W8 serving throughput, TP2, and downstream quality are still untested.**

However, I noticed one potential issue with the new dispatch. `AiterInt8ScaledMMLinearKernel` also uses `rocm_aiter_ops.w8a8_gemm()` and supports per-tensor INT8 scales, while triton's `gemm_a8w8` expects per-token/per-channel scales.

I tested this on gfx1201 and confirmed that single element INT8 scales produce incorrect outputs across all 6 tested GEMM shapes, including NaNs/Infs in some cases, while equivalent per-token/per-channel scales pass. I also reproduced the issue through this PR's registered `rocm_aiter_ops.w8a8_gemm()` op.

The INT8 aiter kernel isn't selected on RDNA4, but with `AITER_TRITON_ONLY=1` on CDNA, the new dispatch could route per-tensor INT8 scales through this Triton kernel. (I haven't tested that configuration on CDNA)

We could keep the triton dispatch architecture-specific for now by restricting `_aiter_w8a8_uses_triton()` to `on_rdna4()`. This would also be consistent with the architecture-aware backend selection in `AiterFp8BlockScaledMMKernel`, while preserving the existing CDNA CK routing.
Alternatively, we could separate the triton and CK paths at the linear kernel level, similar to the blockscale implementation.
