# [Core] Default prefix_cache_retention_interval to a block multiple for hybrid + EAGLE

[Upstream PR](https://github.com/vllm-project/vllm/pull/58549) · state: open · merged: False

## Original PR description

## Purpose

Related to #58303 and #53595 (not claiming to close either until maintainers agree).

On current `main`, an unset `prefix_cache_retention_interval` falls through to the `CacheConfig` default of `0`. For hybrid (Mamba) models with EAGLE speculative decoding, sparse retention keeps only the replay-boundary checkpoint, and EAGLE's tail-block drop makes that checkpoint unreachable — so prefix-cache hits go to 0% (#53595). The release-branch dense default (`None`) from #55760 / #55861 is capacity-worst under interleaved long conversations and also regresses to 0% hits (#58303).

This PR tracks unset vs explicit values and, when unset **and** hybrid **and** `use_eagle()`, resolves the interval to **`6 * scheduler_block_size`** (named `HYBRID_EAGLE_PREFIX_CACHE_RETENTION_BLOCKS`). Explicit `0` / `None` / `N` are untouched; non-hybrid and non-EAGLE defaults stay `0`.

### Why k=6

Thanks to @cch-zuzuche, who measured the multiplier-to-capacity curve in review (the paragraph below is adapted from their suggestion):

Retaining one checkpoint in `k` blocks buys capacity and coarsens hits. Measured largest alternating pair that still reuses, versus `k`: `1` (dense) ~50K, `2` ~60–100K, `6` ~170K, `8` ~190K per conversation. The default picks the smallest value that covers the range reported in #58303; deployments that run short conversations can lower it (the cost is bounded by one interval per turn), and deployments that run longer ones can raise it.

Caveat from the same measurements: they come from one card and one pool size (~542K tokens). The shape should generalise, but the absolute pair sizes will not; the knee moves with `--kv-cache-memory`.

Hit granularity is `hit = floor(prompt_tokens / interval) * interval`.

`k` must be at least 2, because `reachable_block_mask` treats `interval // block_size <= 1` as dense. The constant is asserted `>= 2`, and if the resolved interval would be at or below one block, the default clamps `k` to 2 with a warning, so it never falls back to dense (or to `0`).

### Where block size is resolved

1. **First apply** in `EngineArgs.create_engine_config` after `create_speculative_config` (what unit tests observe; typically `6 * 16` or `6 * --block-size`).
2. **Re-apply** at the end of every `Platform.update_block_size_for_backend` implementation (CUDA / CPU / XPU) so hybrid-aligned sizes (e.g. `6 * 2176 = 13056`) are used before KV-cache config copies the interval.

An info log states the chosen interval and that dense is capacity-worst while `0` never hits under EAGLE.

Thanks for taking this on, and no apology needed — a concrete PR is easier to react to than a plan. Two things from the report side, one of which is a sharp edge in the new constant.

## 1. `HYBRID_EAGLE_PREFIX_CACHE_RETENTION_BLOCKS = 1` is dense, not "minimum sparsity"

Worth a guard or a comment. `reachable_block_mask` (`v1/core/single_type_kv_cache_manager.py`, the Mamba sparse-retention path):

```python
segment_tokens = None if retention_interval == 0 else retention_interval
if segment_tokens is not None:
    per_segment = segment_tokens // block_size
    if per_segment <= 1:
        # Interval at/below the block size: every block is a boundary.
        return None
```

`return None` is **dense** — the function's own contract is "`None` → cache every block". So an interval of exactly `1 * block_size` resolves back to the arm this issue is about, silently, through the helper that exists to avoid it. With the constant parked at a class attribute it is an easy place for a later tuning PR to land on 1 thinking "least sparsity wins".

Suggest either:

- validate `HYBRID_EAGLE_PREFIX_CACHE_RETENTION_BLOCKS >= 2` where it is declared, or
- have `maybe_apply_hybrid_eagle_retention_default` refuse to write an interval ≤ `block_size` (and log why), so the invariant lives next to the code that depends on it.

## 2. The right multiplier is different for `main` than for a v0.29 backport

Your PR description says a v0.29.x backport can follow. **I would not carry `k = 6` over to that one** — the two branches are replacing different baselines, and the cost lands in different places.

| | what unset means today | what a fix to `k * block` changes |
|---|---|---|
| **`main`** | `CacheConfig` default `0` → under EAGLE, *never hits* (#53595) | any `k >= 2` is a **strict improvement**; `k = 6` costs nothing relative to today |
| **`releases/v0.29.0`** | `None` (dense) via #55760/#55861 | `k = 6` **regresses short conversations** relative to the default it replaces |

The second row is the part that is easy to miss, and it is measured on this repo's reference 3090 (7 drafts, block 2176) — the table in `docs/gotchas.md` 60:

| workload | dense (v0.29's current default) | 4352 (k=2) | 13056 (k=6) |
|---|---|---|---|
| ~8K chat, turns 2-3 | 81% (1.7 s) | 54% (3.6 s) | **0% (7.3 s)** |
| ~20K chat, turn 2 | 98% (0.8 s) | 87% (3.0 s) | 65% (7.2 s) |
| two ~32.6K chats alternating | **0% (31.8 s)** | 93% (2.7 s) | 93-99.5% |

On a backport, `k = 6` would turn an 8K conversation's turns 2-3 from 81% into **0%** — a regression below the default it replaced, for workloads that never had the problem being fixed. `k = 2` fixes the alternating failure (93%) with the least collateral damage there.

So: **`k = 6` reads as a defensible default for `main`** (it only has to beat `0`), and **`k = 2` is the value I would pick if the dense default is being replaced**. Same knob, opposite conclusion, because the baseline differs — worth a sentence in the PR body either way, since the next person will read `6` as a recommendation.

## 3. Capacity does not come for free at small k, which is the other half of the trade

For completeness, since `6` came from the report's long-conversation numbers: on our box (one 5090 D, 542,206-token pool, block 2176, two conversations advancing alternately) the largest symmetric pair that still reuses is

| interval | largest pair that holds |
|---|---|
| dense | ~50K |
| 13056 (k=6) | ~170K |
| 17408 (k=8) | ~190K |
| — | 230K fails at k=8 too |

and the knee moves with the pool (`--kv-cache-memory` halved halves the largest surviving pair). So a deployment keeping two long documents live will raise it above the default no matter what the default is — which is the argument for choosing the default at the small end and letting those deployments tune up. It is in gotchas 60 already; flagging it only so the default's rationale is not read as "6 is the good value".

## 4. On the implementation

Your handling of the block-size timing is the part I would have got wrong. I raised in #58303 that the interval must be a multiple of `scheduler_block_size` and that the block is not known when `EngineArgs` resolves the default — it moves with the draft count (2176 at 7 drafts, 2432 at 15, 2048 at 3 or fewer on this stack), and a wrong value refuses to boot rather than degrading:

```
ValueError: prefix_cache_retention_interval (13056) must be non-negative
            and a multiple of scheduler_block_size (2048).
```

Re-applying at the end of `Platform.update_block_size_for_backend` is the right shape for that — the first application covers the unit tests, the second covers the hybrid-aligned size that only exists later. Resolving the multiple rather than a token constant also means it cannot go stale when the geometry moves, which is what we had to hand-patch on our fork.

## 5. Offer

If it helps, I can run arms on the box here (dedicated to this model, restartable) for whichever value you settle on — the default against a long-conversation pair, a hit-granularity sweep at `k = 2` vs `k = 6`, or the two-block variant against the alternating failure. The harness is in `bench/` (`prefix_alternation.py`, `interleave_dose.py`, `needle_reuse.py`), so arms are cheap, and I will post raw records with the numbers.

One caveat to keep on the capacity numbers: one card, one pool size. The *shape* — capacity grows with the multiplier, and the knee moves with `--kv-cache-memory` — should generalise; the absolute pair sizes should not be quoted as a rule.

`HYBRID_EAGLE_PREFIX_CACHE_RETENTION_BLOCKS >= 2` implies `interval = k * block_size > block_size`, so this cannot fire as written. That is the value `EngineArgs` passes when the interval is unset:

```python

    0 if retention_interval_unset else self.prefix_cache_retention_interval
)
...
```

Cheap fixes, either is fine:

- clamp instead of refusing: `interval = max(2, k) * block_size`, which keeps the default doing something useful, or
- if refusing is preferred, say what it refuses *into* and make it dense deliberately — `cache_config.prefix_cache_retention_interval = None` — so the outcome matches the sentence.

I would only mention it because the symmetry is the whole point of this issue: `0` and `None` are the two ends of the same axis and both fail under EAGLE, on opposite sides. A guard against the dense end that falls back to the sparse end is still on the axis.
