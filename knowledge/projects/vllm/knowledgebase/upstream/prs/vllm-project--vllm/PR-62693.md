# [Core][KV Connector] Evict HF3FS pages under reader leases

[Upstream PR](https://github.com/vllm-project/vllm/pull/62693) · state: open · merged: False

## Original PR description

## Purpose

A full HF3FS page pool makes every save fail permanently: once
`allocate_pages_for_keys` runs out of pages there is no way to get one back and
the metadata server has to be restarted (issue #62389).

#62393 stops cache hits and duplicate keys from consuming *new* pages, but it
deliberately does not add eviction, so the failure above remains.

Naively evicting the least-recently-used key is unsafe here: the scheduler calls
`batch_key_exists` (via `get_num_new_matched_tokens`) before the worker loads the
block (`get_key_locations`), so a key can be a "hit" while its page is still
about to be read. Recycling that page turns a hit into a load failure or into
another request's data.

## Stacked on #62393

This branch is based on #62393 (`84f00fa`) because the two changes touch the same
allocation path. The first commit in the diff is #62393 itself; **only the second
commit is new here**. I will rebase onto `main` once #62393 lands.

## What this does

- **Reader leases.** `POST /keys/acquire` returns page locations *and* pins the
  keys; `POST /keys/release` drops the pin. The load path
  (`AsyncOperationManager._handle_load_task`) acquires before reading and
  releases as soon as the blocks are in host buffers: on success, on a missing
  key, on read failure, and on exceptions.
- **LRU eviction of safe keys only.** When allocation needs more pages than the
  free list has, the server reclaims complete, unleased keys that are not part of
  the allocating request (`exclude=cached_pages`), oldest first, returning one
  page per rank to the free list and deleting the key.
- **Lease expiry.** Leases carry a monotonic deadline (default 120 s,
  `--lease-ttl-s`) so a crashed reader cannot pin pages forever. The TTL is a
  safety parameter, not a tuning knob: it has to exceed the slowest block load.
  Reported figures in #62389: a 28k-token prompt loads in about 1.1 s and a 60k
  one in about 1.9 s, but a failed 3FS storage pod stalled loads for 16-18 s, so
  the 120 s default leaves roughly 7x headroom over the observed stall. Renewal
  for loads longer than the TTL is not implemented; a reader that stalls longer
  than the TTL is treated as dead.
- **Backward compatible.** `Hf3fsMetadataInterface.acquire_keys/release_keys`
  have non-abstract defaults (plain lookup / no-op), so the mock and single-node
  clients are unaffected. The HTTP client falls back to `get_key_locations` on
  404/405, which is safe against an older server because it never evicts.

## Correctness argument

- A page is only handed out after it is back in the free list; eviction releases
  it there first.
- Only complete keys are tracked for eviction; partial keys stay owned by their
  writer (the boundary with #61247).
- A key with a live lease is never evicted; its owner releases it or it expires.
- Eviction cannot target the allocating request's own hits, so a batch that has
  already decided to read a page cannot recycle it underneath itself.

## Testing

- `tests/v1/kv_connector/unit/test_hf3fs_metadata_server.py` gains 7 cases:
  eviction makes room, leases protect, expired leases are reclaimed, partial keys
  are skipped, same-request hits are not evicted, LRU order respects acquires,
  and eviction returns one page per rank.
- Isolated harness (full source plus upstream tests, only the import path
  rewritten, `--noconftest`): **25 passed**, then a real localhost HTTP probe
  that leases every complete key, asserts allocation fails, releases one key,
  and asserts the eviction landed on that key.

1. The lease deadline is the latest deadline of all leases on a key. - kerry0520 · comment · 2026-10-21T04:45:24Z · [source](https://github.com/vllm-project/vllm/pull/62693#issuecomment-6308261679)

Thanks - the log timeline closes it. "Scheduler logged 0 matched blocks while the saves were still queued, no save failures, and `Evicted key` kept appearing until 12:24:48" is exactly the case the design skips: a key that is not complete yet is never an eviction candidate, so the reader sees "not present" rather than "evicted". Nothing to add on our side, and c9b2b40 stays as is; no debug line.

On the side fact (reader computing and saving the same three prompts while the writer's saves were queued): the metadata server has no writer lease, so what happened is the documented cache-hit path, not a bug. `allocate_pages_for_keys` returns the existing page for a complete key (`cached_pages`), so the second writer gets the same page and writes into it instead of allocating a new one - which is why you saw no leaked page, no allocation failure and no error. `confirm_write_for_keys` is idempotent per (key, rank), so the second confirmation just re-records the same page.

What that does not give you is serialization: two writers can have those bytes in flight at the same time. For the same key the KV content should be identical (the key hashes model, tokens and block), so the outcome should be correct even if the writes interleave, but I cannot claim protection against a real content mismatch. If that ever shows up, the fix is a write lease like the read lease - deliberately out of scope here so the diff stays at one mechanism.

I updated the PR description-level notes in my own record; nothing in the code changed. Thanks again for spending two H100s on this - the leased-key and expired-lease rows are the ones I could not produce here.
