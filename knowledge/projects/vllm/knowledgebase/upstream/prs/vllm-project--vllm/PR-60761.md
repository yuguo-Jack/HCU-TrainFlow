# [Bugfix][EC Connector] Fail Mooncake requests on abandoned pushes immediately

[Upstream PR](https://github.com/vllm-project/vllm/pull/60761) · state: open · merged: False

## Original PR description



## Overview

Mooncake EC: when a producer abandons a push, fail the consumer requests waiting on it right away instead of after `push_wait_timeout_s`. That includes requests whose own encoder is healthy but whose reservation follows the abandoned one. Supersedes #58123.

## Claims

- A request no longer waits out `push_wait_timeout_s` for a push that no producer will write. It now fails immediately with the existing retryable error, so the proxy re-encodes it straight away.
- Only `mooncake/` changes. The new event goes from the consumer worker to its own scheduler, so there is no cross-instance protocol change.

## Validation

1 node: Qwen3-VL-4B, Mooncake TCP, enc0 + enc1 → 1 PD through two proxies, `push_wait_timeout_s=20`. enc0 carries a local patch (not in this PR) that raises in `_push_batch` after 6s. A goes through enc0, then B goes through enc1 1.5s later.

| | main | main + #58123 | this PR |
|---|---|---|---|
| same image: B (healthy encoder) | 500 after 20s, OK on proxy retry (20.5s) | same (20.5s) | fails on abandon, OK on retry (**7.3s**) |
| different images: A (faulty encoder) final 500 | 40.2s | 40.2s | **12.1s** |
| PD `never arrived` warnings | 3 | 3 | 0 |
| control: B alone / B with a different image | 200 | 200 | 200 |

B's remaining 7.3s is the injected 6s delay plus encode time.

.venv/bin/python -m pytest tests/v1/ec_connector/unit                                   # 420 passed

## Details

Root cause, using two requests that share an image:
1. A's producer reserves the image on the consumer and becomes the writer.
2. B's producer reserves the same `mm_hash` while A is still writing. The consumer makes B a follower of A and replies `write=False`, so B's producer finishes without writing.
3. A's push batch fails, for example on a Mooncake write error, a validation error, or any other exception in `_push_batch`. A's producer abandons its reservation.
4. `ConsumerReservationManager._release` cancels B together with A. Nobody tells B's waiting request, so it waits for `push_wait_timeout_s` and then fails.

Fix:
- `ConsumerReservationManager` records the reservations a producer abandoned, plus the followers cancelled along with them.
- After each `cancel`, the control server publishes them as `abandoned` events.
- The scheduler marks a waiting transfer unavailable when its event arrives. An event that arrives before the request leaves a tombstone, and an event for a transfer that already landed is ignored.
- A consumer's own cancels and refresh re-reservations are not reported.

#58123 doesn't fix this. A producer never completes a follower, because it is told `write=False`. A consumer also doesn't reject the completion of a writer it cancelled, because the cancel is deferred until the writer completes. The table above shows the same timings with #58123 applied.

Limitation: B's first attempt still fails and relies on a retry. Re-pushing from the follower's producer would avoid that, but it needs producer-side changes. Left for a follow-up.

Not a duplicate: open-PR searches ("mooncake follower", "mooncake abandoned", "mooncake EC reservation", "push_wait_timeout", "EC mooncake push") found only #57904 (shape sizing) and #57275 (proxy fallback identity). Neither touches this path.
