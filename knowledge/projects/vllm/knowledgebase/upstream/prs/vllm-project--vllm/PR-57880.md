# [ROCm][DSv4][DSV4.1][Perf] Fill decode wave counts and fuse the reduce at one split

[Upstream PR](https://github.com/vllm-project/vllm/pull/57880) · state: open · merged: False

## Original PR description

## Summary

Two related fixes to the ROCm DSv4 sparse MLA decode split-K path on gfx950.

**1. Fill wave counts with fewer split iterations.** The split heuristic sized
splits to hit a workgroup target, which could leave a wave partly idle while
each workgroup still walked more `BLOCK_K` iterations than necessary. Among all
split counts that land in the *same* wave count, pick the one with the fewest
per-workgroup iterations; never trade an extra wave for fewer iterations.

**2. Fuse the reduce into the partial kernel when there is one split.** At one
split the split-K machinery is pure overhead: the partial kernel writes fp32
running state (`part_m`, `part_l`, `part_acc`) that the reduce immediately reads
back, divides, and stores as bf16 — a full round trip through memory plus a
second launch to finish work the partial kernel already had in registers.
Normalize in the partial epilogue and store bf16 straight to `out`, skipping both
the staging buffers and the reduce launch. Attention sinks fold into the same
epilogue. Shapes taking more than one split are untouched.

Single-split is not a corner case: it is what the heuristic picks once rows fill
the device, i.e. the high-concurrency and long-spec-decode points that set decode
throughput.

## Results

MI355X (gfx950), decode partial+reduce under CUDA-graph replay, 192 shapes:
2 profiles (DSv4.1-Flash topk=512, V4-Pro topk=1024) x {16, 32} heads/rank x
concurrency 1-128 x spec-decode length 1-6.

Both arms of each comparison are timed **back-to-back inside one process**,
alternating order and taking medians. Re-measuring identical code in a fresh

## Where the kernel now sits against its roofline

Measured machine limits: 3.4 TB/s for random 576 B gathers (the KV access
pattern), 4.63 TB/s streaming, 232 TFLOP/s at the decode's own MFMA tile shape,
and a graph-replay launch floor of 10.8 us (one kernel) / 12.5 us (two).

Taking `launch + max(memory, compute)` as the floor, with memory counting the KV
gather alone, for 32 heads/rank:

- **Rows <= ~48**: 89-117% of floor — at the ceiling, launch- and gather-bound.
- **Rows 96-192**: 74-89% of floor.
- **Rows 384-768**: 55-60% of floor, and here `actual ~= gather + dot + launch`
  almost exactly (Flash at 768 rows: 111 + 139 + 11 = 261 us modelled vs 255 us
  measured; Pro at 768 rows: 173 + 250 + 11 = 434 vs 438). The kernel gets
  essentially **no overlap** between the KV gather and the MFMA work at large
  rows.

That serialization is the remaining headroom, and it is not reachable from the
launcher: `num_stages` 1/2/3, `num_warps` 4/8, and `waves_per_eu` 0/1/2 are all
flat to within 1% at 128/384/768 rows, because the accumulators (4 x [16,128]
fp32) plus the staged Q tile leave no register budget for the compiler to
prefetch a KV tile. Closing it needs a kernel restructure, not tuning, so it is
left out of this PR.

### At the TP=4 serving config

The figures above are 32 heads/rank. The end-to-end section below serves
DSv4.1-Flash at TP=4, which is 16 heads/rank — half the MFMA work per row
against the same KV traffic — so those shapes are reported separately here.

The floor is `launch + max(gather + stream, compute)` over the bytes the kernel
is *obliged* to move at that shape:

- gather: `rows x 640 x 576 B` of fp8_ds_mla KV at 3.4 TB/s. MLA shares one
  latent entry across all heads, so this does not scale with head count.
- stream at 4.63 TB/s: Q in, `out` back, and — only when there is more than one
  split — the fp32 `part_m`/`part_l`/`part_acc` buffers, which the partial
  kernel writes and the reduce reads straight back,
  `rows x splits x heads x (576 x 4 + 8) B` each way.
- compute: `rows x heads x 640 x 2 x (576 + 512)` FLOP at 232 TFLOP/s.

Counting the split staging matters: at 192 rows and 4 splits it is 13.8 us of
required traffic against 20.8 us of KV gather. A KV-only floor omits it and
makes the kernel look considerably worse than it is.

The heuristic changes its choice at 6, 12, 96 and 192 rows and leaves 24, 48,
384 and 768 alone, and the timings track that exactly: every shape it touches
gains (1.08x to 1.32x) and every shape it does not is flat to within 0.5%.

Across 96-384 rows the kernel runs at 83-90% of what the model allows, so there
is little left on the table in the range that sets decode throughput. The two
soft spots are at opposite ends. At 48 rows and below it sits at 65-72%, but
there the floor is mostly the 12.5 us two-kernel replay launch and the kernel
moves under 20% of the gather bound — the device is idle, so that gap is fixed
overhead rather than inefficiency. At 768 rows it falls to 73%, a 37 us
absolute gap, and that is where the gather/MFMA serialization described above is
least well hidden.

At 192 rows this PR is the difference between 64% and 90% of floor, and it gets
there while moving *more* staging traffic than base (4 splits against 3): the
win is iteration count, not bytes.

Percent-of-floor is only comparable within an arm. At 768 rows the fusion drops
the floor from 112.5 us to 100.2 us by removing the staging round trip
altogether, so this PR reads as a lower percentage (73% against base's 74%)
while being 13.4 us faster in absolute terms. Across arms, compare microseconds.

## End-to-end serving

Full server A/B on MI355X: DeepSeek-V4.1-Flash, TP=4, `--moe-backend aiter`,
DSpark MTP with 5 draft tokens, `--max-num-batched-tokens 16384`,
`--max-cudagraph-capture-size 1024`, Rust frontend, torch profiler off.
Steady-state decode step time is read from `vllm:iteration_tokens_total_count`
and `vllm:generation_tokens_total` on `/metrics`.

The two arms are this branch and **its own merge parent**
(`382970ee6c`), so they differ by this PR alone. Both are served concurrently on
disjoint 4-GPU halves of one node and sampled at the same wall-clock instant, so
host and PCIe drift is common-mode and cancels in the ratio. Six paired reps per
point, then the arms are **swapped across the two GPU halves** and the six reps
repeated, so a systematic difference between the halves cannot produce the
result. Speedup is the median of the paired per-rep ratios.

| conc | rows | base ms/step | PR ms/step | base tok/s | PR tok/s | speedup | 95% CI | n |
|---:|---:|---:|---:|---:|---:|---:|---|---:|
| 1 | 6 | 10.26 | 10.21 | 342.8 | 344.4 | 1.0049x | 1.0045-1.0057 | 10 |
| 4 | 24 | 11.66 | 11.66 | 1204.0 | 1203.2 | 0.9991x | 0.9981-1.0010 | 11 |
| 16 | 96 | 16.12 | 15.99 | 3482.0 | 3511.6 | 1.0075x | 1.0060-1.0114 | 12 |
| 32 | 192 | 20.56 | 19.88 | 5464.3 | **5651.5** | **1.0344x** | 1.0269-1.0363 | 12 |
| 64 | 384 | 29.97 | 29.95 | 7498.4 | 7501.1 | 1.0010x | 0.9992-1.0026 | 12 |

Geomean across all points is 1.0094x. The gain concentrates at concurrency 32,
which is 192 decode rows once DSpark's 1+5 verify shape is applied — the range
the split heuristic targets. Concurrency 4 (24 rows) and 64 (384 rows) are flat
because the heuristic picks the same split count there as before; neither is a
regression, and both straddle 1.0x. The c32 result reproduces across the GPU-half
swap: 1.0337x on one assignment and 1.0347x on the other.

The serving result and the kernel table agree. Feeding each measured kernel
speedup through Amdahl with sparse MLA attention's share of the decode step
(6.7% at c1 rising to 12.6% at c32) predicts +0.58 / +0.00 / +0.75 / +3.18% at
c1 / c4 / c16 / c32, against +0.49 / -0.09 / +0.75 / +3.44% measured — within
0.26 points at every point.

Note on methodology, in case this harness is reused: the sampling window must be
short enough that every stream is still generating when it closes. If the streams
hit their token limit mid-window the engine idles for the remainder, the step
counter stops advancing, and `ms_per_step` collapses to `window / steps_at_limit`
— an identical number at every concurrency, which looks like a perfectly flat
step time rather than a broken measurement.

## Accuracy

The split change reorders float accumulation across splits; the fusion performs
the same arithmetic without the fp32 round trip, so results differ only in where
the final bf16 rounding lands. Measured max deviation vs. the staged path is
1.2e-4 (one bf16 ulp) across both profiles, 16 and 32 heads/rank, with and
without attention sinks.

GSM8K on the served model, full 1319 questions, TP=4, DSpark MTP with block
rejection (not the synthetic-acceptance perf setting, whose generations are not
meaningful):

| arm | strict-match | flexible-extract |
|---|---|---|
| base | 0.9765 +/- 0.0042 | 0.9757 +/- 0.0042 |
| this branch | 0.9765 +/- 0.0042 | 0.9757 +/- 0.0042 |

Identical to four decimal places on both extractors.
