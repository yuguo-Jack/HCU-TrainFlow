# [Bugfix] Fix Gemma 4 vision crash with online FP8 quantization

[Upstream PR](https://github.com/vllm-project/vllm/pull/64168) · state: open · merged: False

## Original PR description

## Overview

Fixes #63732. With `--quantization fp8`, an image request to Gemma 4 returns HTTP 500 and kills the engine core. The transformers patch embedder casts the pixel values to `input_proj.weight.dtype`. Once vLLM quantizes that layer, this dtype is `float8_e4m3fn`, so the FP8 linear gets an FP8 input. This PR runs the patch embedder steps in `gemma4_mm.py` with the pixel values cast to `self.model_dtype`. It makes the same change for the pooled states before `embedding_projection` in the encoder CUDA graph path.

Compared with #63911, this fix:

- Also fixes `DiffusionGemmaForConditionalGeneration` and `EmbeddingGemma2Model`. They borrow Gemma 4's `_process_image_input` and `_process_video_input` and build their own FP8-quantized tower. [#63911](https://github.com/vllm-project/vllm/pull/63911) swaps the embedder only in `Gemma4ForConditionalGeneration.__init__`, so their image and video paths still crash with the reported error (checked with a probe that loads E4B with FP8 and builds each model's own tower, since no checkpoint of either model was at hand).
- Adds tests that fail on the old code for video and for the encoder CUDA graph path, including the `embedding_projection` cast. The compiled and encoder-graph cases in [#63911](https://github.com/vllm-project/vllm/pull/63911) pass on the old code, so they guard neither path.

## Claims

- Gemma 4 image requests with online FP8 no longer crash the engine. `input_proj` stays FP8 and still uses the same FP8 kernel.
- The same fix covers video inputs. On the old code, `--quantization fp8 --enforce-eager` with video enabled crashed at engine start, because the encoder profile run sends dummy video through the same patch embedder.
- The same fix covers the encoder CUDA graph path (the patch embedder call and the `embedding_projection` cast).
- Online `fp8_per_block`, `fp8_per_channel` and `mxfp8` (eager, custom ops off) crashed at engine start on the old code. With this fix, all three answer `The sign in the image is a **STOP** sign.`
- `DiffusionGemmaForConditionalGeneration` and `EmbeddingGemma2Model` get the same fix through the borrowed methods.

## Details

Root cause: vLLM builds the Gemma 4 vision tower with `AutoModel.from_config`. It then replaces each `nn.Linear` with a `ReplicatedLinear` that carries the tower quant config. With online FP8, `input_proj.weight` becomes `float8_e4m3fn` after loading. The transformers `Gemma4VisionPatchEmbedder.forward` does:

```python
pixel_values = 2 * (pixel_values - 0.5)
if (target_dtype := self.input_proj.weight.dtype).is_floating_point:
    pixel_values = pixel_values.to(target_dtype)
hidden_states = self.input_proj(pixel_values)
```

This is right for a plain `nn.Linear`. For a quantized layer, though, the weight dtype is the storage dtype. FP8 is a floating type, so the guard lets the cast through. The bf16 pixel values are rounded to FP8 without a scale, and the FP8 linear's activation quant gets an FP8 input. `dynamic_per_token_scaled_fp8_quant` only accepts fp16, bf16 or fp32. A debug run confirmed the chain: the pixel values enter the patch embedder as bf16, and only `vision_tower.patch_embedder.input_proj` receives an FP8 input. `encoder_cudagraph_forward` had the same mistake in vLLM code: it cast the pooled states to `embedding_projection.weight.dtype`, which is also FP8 under the tower quant config.

The CUDA kernel runs when the `quant_fp8` custom op is on: with `--enforce-eager`, with `+quant_fp8`, and by vLLM's default for block-scaled FP8 checkpoints and ROCm AITER FP8 linear. With the op off, eager `forward_native` also fails (`"abs_cuda" not implemented for 'Float8_e4m3fn'`). Only the default compile mode passes without an error, and there the pixel values are still rounded to FP8 without a scale.

Fix: a module-level `_embed_patches(patch_embedder, pixel_values, pixel_position_ids, padding_positions, dtype)` repeats the steps of the transformers forward (`2 * (x - 0.5)`, `input_proj`, `_position_embeddings`, sum), but casts to the given dtype. The image, video and encoder CUDA graph paths call it with `self.model_dtype`. The CUDA graph path also casts the pooled states to `self.model_dtype`, as the eager paths already do before `embed_vision`. The quant config is not touched, so the layers stay FP8. For an unquantized layer nothing changes, because then the weight dtype is the model dtype. The helper is a module-level function, not a method, because the two borrowing models copy `_process_image_input` and `_process_video_input` without inheriting from Gemma 4. A method would be missing on those classes.

Alternatives not taken:

- Building `input_proj` without quantization: this changes which layers the user's quantization covers. It can also break loading of pre-quantized checkpoints that quantize this layer, and it leaves the `embedding_projection` cast as it is.
- Making the FP8 linear accept an FP8 input: this treats the crash site, and by then the input has already been rounded to FP8.

Tradeoffs and limitations:

- `_embed_patches` uses the private `_position_embeddings` of the transformers embedder. This file already splits `Gemma4VisionModel.forward` into its parts, so this goes one level deeper in the same style.
- With online FP8 in the default compile mode, which did not crash before, image outputs may change a little because the pixel values are no longer rounded to FP8 first. On `input_proj` against the bf16 weight, the relative error went from 4.50% to 3.68%. I did not run a vision eval.
- The tests use `google/gemma-4-E4B-it`, which CI already uses. E2B has the same vision tower and would be cheaper, but I could not confirm the answer checks (`stop`, `book`) on E2B.
- CI: `gemma4_mm.py` is added to `source_file_dependencies` of `quantized-models-test` and its AMD mirror, so the eager test runs when this file changes. This adds an estimated 14% more runs of that step. The `gemma4_fp8` row (`core_model`) runs in the existing multimodal step.
- Not run on AMD.
- Out of scope: online `mxfp4` on SM 12.x fails at engine start in `input_proj` with `ValueError: SM12x cute-dsl requires NVFP4 with 128x4 scales`, the same before and after this patch, with a bf16 input.
