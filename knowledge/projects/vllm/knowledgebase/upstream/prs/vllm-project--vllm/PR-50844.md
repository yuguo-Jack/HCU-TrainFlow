# [Bugfix][DSv4] Bound token_id before the tid2eid gather in hash-MoE routing

[Upstream PR](https://github.com/vllm-project/vllm/pull/50844) · state: open · merged: False

## Original PR description

## Summary

DeepSeek-V4's hash-MoE routing kernels read a token's expert ids straight out of
the lookup table:

```cpp
const int64_t token_id = load_index_as_int64(input_ids, warp);
...
expert = static_cast<int>(tid2eid[token_id * 6 + lane]);
const float x = input[warp * num_experts + expert];
```

`token_id` is data, not a loop bound, and `tid2eid` is `[vocab_size, topk]`.
There is no bound on it. An out-of-range token id gathers outside the table,
yields a garbage expert id, and that id is then used to index the gating logits
and is stored into `topk_ids` for the downstream MoE kernels — an illegal access
that takes down every TP rank.

## Evidence

Hit in production on DeepSeek-V4-Flash (TP2 + `--enable-expert-parallel`).
CUDA core dump, both ranks:

```
CUDA Exception: Warp MMU Fault
errorpc  vllm::moe::dsv4HashTopkSoftplusSqrt<int,int>
```

SASS at `errorpc` shows the chain explicitly:

```
LDG.E R7,[R10.64]        ; R7 = tid2eid[token_id*6 + lane]  -> "expert"
IMAD  R13,R2,UR6,R7      ; R13 = warp*num_experts + expert
IMAD.WIDE R8,R13,0x4,R8  ; addr = input + R13*4
*> LDG.E R8,[R8.64]      ; <-- FAULT

R7 = 0xD9E366E0 = 3655558880
```

`R7` is the value that came *out of* `tid2eid` — i.e. the table was read out of
bounds, and the "expert" is the bit pattern of a neighbouring tensor.

The out-of-range `token_id` came from the sampler emitting an id equal to
`vocab_size`, fixed separately in the sampler by bounding the tile-local argmax (#50843).

## Fix

Bound `token_id` against the table's row count, threaded from `tid2eid.size(0)`,
in both kernels that perform the gather (`dsv4HashTopkSoftplusSqrt` and the
generic `topkGatingSoftplusSqrt` `USE_HASH` path). **Updated after review on #50845:** a
non-padding row whose id cannot index `tid2eid` now stops the kernel with a
clear message (`printf` + trap) instead of being treated as padding. Rows
flagged in `is_padding` may hold any id and still never read outside the
table.

This is worth keeping independently of the sampler fix. The kernel trusts whatever
lands in `input_ids`, and the sampler is not the only producer: prompt ids are
range-checked by `validate_token_ids` only when a tokenizer is initialized (it
returns early under `skip_tokenizer_init`), and padded or stale rows can also
reach the kernel. An out-of-range id should never become an out-of-bounds read.

## Test

`tests/kernels/moe/test_topk_softplus_sqrt.py::test_hash_routing_traps_on_token_id_outside_table`
covers both kernels (the DSv4 fast path and the generic `USE_HASH` path):
in-process, a flagged padding row with an out-of-range id is harmless and real
rows route to their `tid2eid` experts; in a subprocess, the same id on an
unflagged row traps. The file passes (1675 tests) on SM120, and DeepSeek-V4-Flash
(TP2 + EP) served a 20-minute randomized-concurrency stress run with no trap.
