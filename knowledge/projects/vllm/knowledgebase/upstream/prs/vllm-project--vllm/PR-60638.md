# [MoRIIO] Require pending remote prefill for READ cache hits

[Upstream PR](https://github.com/vllm-project/vllm/pull/60638) · state: closed · merged: True

## Original PR description

## Overview

MoRIIO READ can claim external cache hits for a request with no pending remote prefill, even though allocation will not schedule a READ. Require `do_remote_prefill` before reporting a READ hit.

Rebased onto main `bfa7e5b7afe40ebe48288801a2baf5c1135cd881`. This remains an independent child of closed #58968.

## Claims

```diff
D receives a request without pending remote prefill
- MoRIIO reports an external hit; no matching READ is scheduled
+ MoRIIO reports zero; local computation or another connector can serve it
```

The eligible READ path retains N−1 accounting and synchronous loading. Producer and WRITE behavior are unchanged.

The eight independent PRs compose on this same main. The combined CPU suite passes **344 tests**, with **33 skips** (32 ROCm/aiter-gated connector cases and one GPU LLM case) and **one model-loading deselection**. Counts overlap with the independent suites.

## Details

`get_num_new_matched_tokens` shares one remote-prefill guard across READ and WRITE, matching the eligibility flag used by `update_state_after_alloc`. Existing READ fixtures explicitly set that flag; the regression reuses the scheduler suite's fixture.

Duplicate checks: #53250 and #60544 add eligibility in WRITE, #54301 changes READ to an asynchronous lifecycle, and #48471 adjusts block-list matching. None supplies this READ-only eligibility guard. The matching implementation in #58968 was superseded by the split PRs.

**Merge danger:** two-way door; blast radius: MoRIIO READ admission. No base connector API or KV transfer clipping change.

Merged #53250 supplies WRITE eligibility; this extends its existing guard to READ. #60867 changes group routing and speculation gates, not this admission check.

AI assistance was used for implementation, rebase, regression checks and this description. Human line-by-line review and the runtime acceptance items above remain pending. No performance improvement is claimed.

Could we add a lifecycle regression alongside this parameterized test? Start with a valid READ request, call `update_state_after_alloc()`, and verify that it queues the receive and clears `do_remote_prefill`. Then verify that `build_connector_meta()` still emits the original queued transfer, while a subsequent `get_num_new_matched_tokens(request, 0)` returns `(0, False)`.
That would protect the recovery/rescheduling case directly: clearing the flag must prevent another external hit without suppressing the transfer that was already queued. The current table test checks the flag values correctly; this would additionally lock down the contract between matching, allocation, and metadata construction.
