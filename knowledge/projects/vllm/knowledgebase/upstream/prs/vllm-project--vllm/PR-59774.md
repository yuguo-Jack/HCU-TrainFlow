# [ROCm] Octave KV (`ROCM_OCTAVE`): native 3-bit KV cache backend for AMD GPUs

[Upstream PR](https://github.com/vllm-project/vllm/pull/59774) · state: open · merged: False

## Original PR description

RFC: https://github.com/vllm-project/vllm/issues/59773

## Purpose

This adds `ROCM_OCTAVE`, an attention backend that keeps the KV cache of
full-attention layers at 3-4 bits per value, with all kernels in HIP. You
select it with `--kv-cache-dtype octave_k3v3`, `octave_k3v4` or
`octave_k3v3_compact` (216, 248 and 196 bytes per slot at head size 256,
against 1024 for fp16). The RFC explains why we built it and what we would
like it to become; `docs/design/rocm_octave.md` describes the format and the
per-architecture contract.

The short version: on 4× RX 7900 XTX with Qwen3.8-27B it holds 4.6× more
tokens than fp16 and GSM8K does not move. Against TurboQuant at the same size
it holds as many tokens or more, loses 2.5× less NLL, and runs decode 4.6×
and MTP verification 11× faster per layer at 380k, because the kernels are
written for the hardware (codebook through `v_perm_b32`, WMMA straight from
the packed cache, no host syncs). It works with MTP and CUDA graphs, and we
have served it in production since October 2, 2026.

The aim is to give ROCm a native compressed KV cache across the whole AMD
line. The capacity gain is a ratio of bytes, so it carries over to any card,
from a 24 GB Radeon to a 192 GB MI300X; the speed we have only measured on
RDNA3. There, attention stops being what grows with the context: from 128k
to 512k decode only goes from 153 to 127 tok/s, because most of the step is
the rest of the model again. This PR brings that first architecture, and the
RFC lists what the others need.

## What changes

Most of the PR is new files:

- `vllm/v1/attention/ops/rocm_octave.py`: the format and its PyTorch
  reference, which defines the byte layout.
- `vllm/v1/attention/backends/rocm_octave_attn.py`: the backend and its
  metadata builder.
- `csrc/attention/octave_*`: the kernels. Store, reduce, rotation and a
  portable decode build for every AMD target; the WMMA decode and prefill are
  for RDNA3 (gfx1100-1103).
- `tests/kernels/attention/test_rocm_octave.py`, and `--model` plus the new
  cache dtypes in `benchmarks/attention_benchmarks`.
- `docs/design/rocm_octave.md`.

The changes to existing files are small: the three cache dtypes in
`vllm/config/cache.py`, `vllm/utils/torch_utils.py` and
`vllm/v1/kv_cache_interface.py`; the backend in the registry and in the ROCm
platform's selection; the ops in `csrc/ops.h`, `csrc/torch_bindings.cpp` and
`CMakeLists.txt`. `customize_spec` now runs under the current vLLM config,
because the backend needs the model's rotary dims to size the slot. Nothing
changes for other backends or cache dtypes.

A few design choices a reviewer may want to know about:

- There is no Triton fallback. On an architecture without a native prefill
  kernel the backend refuses to start and names the missing kernel. Today
  that is everything except RDNA3; the RFC lists what each one needs.
- The metadata builder is the backend's own. It builds the per-query maps on
  the device without host syncs, supports `UNIFORM_BATCH` CUDA graphs, and
  refreshes the maps between fused MTP draft steps, so the fused draft path
  stays on.
- Supported models today: head size 256 with 64 RoPE dims, i.e. Qwen3-Next
  and Qwen3.5 / 3.6 / 3.8. The decode handles up to 8 query heads per KV head
  on each GPU, so Qwen3.5-122B and 397B need TP 4 or more. Head size 128 is
  the next step.

## Not a duplicate

I searched open PRs and issues for `splitq`, `octave`, `turboquant rocm`,
`kv cache 3-bit`, `kv cache quantization hip` and `lloyd-max kv`. The closest
are UltraQuant (#57057: FP4 with FlyDSL for gfx950, built on TurboQuant),
KVarN (#46613 / #46812: Triton, CUDA-first), #43835 (HIP int8/int4 for CDNA),
#40396 (a Triton TurboQuant decode for MI300X), #53231 (TurboQuant for Gemma 4
on ROCm) and #59132 (Triton attention for RDNA without KV quantization). None
targets RDNA with native kernels, and none runs below 8 bits with MTP on ROCm.

## Evaluation

4× RX 7900 XTX (gfx1100), Qwen3.8-27B GPTQ W4A16, TP4, 8 GB of KV cache per
GPU, same image and flags for every row. GSM8K: `tests/evals/gsm8k/gsm8k_eval.py`,
chat, thinking off, 500 questions, temperature 0.6, no MTP so that TurboQuant
is correct. NLL: one 380k-token document.

| KV cache | Bytes | GSM8K | NLL over fp16 |
|---|---|---|---|
| fp16 | 1024 | 91.8 | — |
| `turboquant_k3v4_nc` | 230 | 89.8 | +0.00155 |
| `octave_k3v4` | 248 | 91.4 | +0.00086 |
| `octave_k3v3` | 216 | 92.4 | +0.00125 |
| `octave_k3v3_compact` | 196 | 91.8 | +0.00150 |

Attention per layer at 380k (`benchmarks/attention_benchmarks`, one TP4
shard):

| | fp16 | `turboquant_k3v4_nc` | `octave_k3v3_compact` | `octave_k3v3` |
|---|---|---|---|---|
| decode, 1 token | 2370 µs | 2565 µs | 563 µs | 614 µs |
| MTP verify, 4 tokens | 48.8 ms | 6.65 ms | 0.58 ms | 0.62 ms |
| prefill, 2048-token chunk | 125.6 ms | 86.6 ms | 60.8 ms | 63.9 ms |

Time to first token, end to end with MTP and a cold prefix: 297 s at 380k
with `octave_k3v3_compact`, against 371 s with fp16 and 621 s with
TurboQuant. At 100k all three are within 8%, because the model's GEMMs and
all-reduce dominate.

When I replaced the Triton metadata builder the backend inherited at first
with its own, I checked that nothing moved (TP4, MTP, GSM8K 500 at
concurrency 6, which mixes prefill, decode and verification): GSM8K
92.2 → 91.8, MTP acceptance 83.33% → 83.39%, output 216.1 → 216.8 tok/s.

A side note on the GSM8K script: with `--max-concurrency`, its per-request
timeout also counts the time a request waits for a free connection, so queued
questions can time out and count as invalid. Our runs put a semaphore around
the request; I can send that fix separately.

## Update: sparse attention (qwen4_exp QSA)

The new commits make Octave the main KV cache of `qwen4_exp`'s sparse
attention (QSA), where each token attends to the 2048 positions its indexer
picks:

- `octave_decode_sparse`: the WMMA decode reads K/V through per-token
  top-k indices (logical positions, `-1` holes skipped) instead of a
  contiguous range. Same split-KV partials and reduce as the dense path.
- `--kv-cache-dtype octave_k3v3` / `octave_k3v4` on a QSA model sizes the
  main KV pages through `RocmOctaveAttentionBackend.customize_spec`; the QSA
  indexer pages are unchanged.
- An exact sink and recent window, a first, scoped answer to question 4 of
  the RFC (#59773). The first 4 and the last 64 tokens are also kept in fp16,
  in small direct-mapped tables keyed by cache slot and tagged, so an evicted
  entry falls back to the quantized copy. The sparse decode masks window hits
  and an exact kernel adds them as one more split before the reduce. Cost:
  ~18 MB per layer, no change in KV capacity. It lives in the QSA path only;
  the dense backend is unchanged.

Why this model needed the window: its attention is much sharper than
Qwen3.8-27B's. Q·K logits have a spread of 6-9 nats between median and p99,
the last 64 tokens take 35-80% of the attention mass in most layers, and the
first 4 take 15-40% in a few. When a few tokens carry most of the mass,
their quantization error is not averaged out over many others. Both halves
contribute: quantizing only V costs more than quantizing only K.

Evaluation: 4x RX 7900 XTX, Qwen3.8-Flash-Next GPTQ W4A16 (asymmetric, g32),
TP4, fp16, `--max-num-batched-tokens 512`, no prefix caching, same image and
flags for every row. NLL from `prompt_logprobs` over 12 code/text documents of
~8k tokens (105,910 tokens), split at position 2048 (where top-k starts to
drop tokens), and over 24 short documents (16,427 tokens). Differences are in
nats over fp16.

| KV cache | KV tokens | NLL pos >= 2048 | NLL pos < 2048 | NLL short |
|---|---|---|---|---|
| fp16 | 47,409 | 1.0856 | 1.6707 | 1.1788 |
| `octave_k3v3`, no window | 155,930 | +0.0395 | +0.0851 | +0.0708 |
| `octave_k3v3` | 155,930 | +0.0163 | -0.0221 | +0.0085 |

fp16 per-token logprobs on this model vary by ~0.1 between runs (MoE and
split-K atomics); mean NLL repeats to about +-0.2% (+-0.003 nats at
pos >= 2048), so the window's pos < 2048 value is noise. These are short documents with
a different protocol from the 380k NLL above, so the two are not directly
comparable, but this model clearly costs more: the remaining +0.016 nats at
pos >= 2048 is what we are working on next. A generation eval (GSM8K) will
follow.

Note on that run: it used our fork, because the fp16 port of QSA and the RDNA3
W4A16 MoE fixes for compressed-tensors checkpoints are separate PRs (to
follow). On this branch alone the QSA path is bf16, like upstream.
