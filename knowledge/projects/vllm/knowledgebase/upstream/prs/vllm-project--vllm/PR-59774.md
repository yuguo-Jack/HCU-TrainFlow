# [ROCm] Octave KV (`ROCM_OCTAVE`): native 3-bit KV cache backend for AMD GPUs

[Upstream PR](https://github.com/vllm-project/vllm/pull/59774) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

Adds `ROCM_OCTAVE`, an attention backend that keeps the KV cache of
full-attention layers at 3-4 bits per value, with native HIP kernels for
RDNA3 (gfx1100) and MI300X (gfx942). Select it with
`--kv-cache-dtype octave_k3v3`, `octave_k3v4` or `octave_k3v3_compact`
(216, 248 and 196 bytes per slot at head size 256, against 1024 for fp16).

RFC: #59773. `docs/design/rocm_octave.md` describes the format and the
per-architecture contract.

## Claims

- **Capacity:**
  - On 4× RX 7900 XTX with Qwen3.8-27B, 4.6× the KV tokens of fp16.
  - On one MI300X, 1.95× the tokens of AITER's fp8 cache (7.0M vs 3.6M, i.e.
    53 vs 27 concurrent 128k requests).
- **Quality:** GSM8K and a 126k needle-in-a-haystack test match fp16 and fp8
  on both architectures. Next-token NLL at 380k is +0.0009 to +0.0015 nats
  over fp16.
- **Speed:**
  - On MI300X, decode for one request matches AITER fp8. Per layer it is
    faster from 32k on (65 vs 103 µs at 128k).
  - On RDNA3 at 380k, per layer, decode is 4.6× faster than TurboQuant and
    MTP verification 11× faster.
- **Works with MTP and CUDA graphs.** No host syncs in the metadata builder.
  We have served it in production on RDNA3 since October 2, 2026.
- **Guarded to the validated architectures**, gfx1100 and gfx942:
  - CMake builds the sources and registers the ops only for them.
  - `supports_compute_capability` rejects other devices.
  - The tests skip elsewhere.

The haystack is vLLM's own Python source, cut to 126k tokens. 16 keys are
inserted every ~7.7k tokens, each a line such as

## Details

What changes. Most of the PR is new files:
- `vllm/v1/attention/ops/rocm_octave.py`: the format and its PyTorch
  reference, which defines the byte layout.
- `vllm/v1/attention/backends/rocm_octave_attn.py`: the backend and its
  metadata builder.
- `csrc/attention/octave_*`, the kernels:
  - store, reduce, rotation and a portable decode, shared by both
    architectures;
  - WMMA decode and prefill for gfx1100;
  - MFMA decode and prefill for gfx942;
  - the op registration in `octave_torch_bindings.cpp`.
- Tests, docs, and `--model` plus the new cache dtypes in
  `benchmarks/attention_benchmarks`.

Changes to existing files are small:
- the three cache dtypes in `vllm/config/cache.py`,
  `vllm/utils/torch_utils.py` and `vllm/v1/kv_cache_interface.py`;
- the backend in the registry and in the ROCm platform's selection;
- the sources in `CMakeLists.txt`;
- `customize_spec` now runs under the current vLLM config, because the
  backend needs the model's rotary dims to size the slot;
- in `qwen4_exp` (QSA), Octave as the main cache through a sparse decode,
  with the new fused QSA prepare turned off for an Octave cache, since it
  writes raw BF16 K/V.

Nothing changes for other backends or cache dtypes.

Design choices a reviewer may want to know about:
- **Native kernels only.** There is no Triton fallback; an architecture is
  added once it has its own kernels and passes the tests and an end-to-end
  run. The RFC lists what each one needs.
- **The metadata builder is the backend's own.** It builds the per-query
  maps on the device without host syncs, supports `UNIFORM_BATCH` CUDA
  graphs, and refreshes the maps between fused MTP draft steps.
- **On gfx942**:
  - QK runs on `v_mfma_i32_16x16x32_i8`, with the query split into high and
    low int8 halves.
  - V is widened to fp16 by one `v_perm`: each codebook byte becomes an exact
    fp16 denormal, which the MI300 MFMA keeps.
  - The decode file is built with `-amdgpu-mfma-vgpr-form`, so the
    accumulators do not halve the occupancy.
- **Supported models.** Head size 256 with 64 RoPE dims, i.e. Qwen3-Next and
  Qwen3.5 / 3.6 / 3.8.
  - The decode handles up to 8 query heads per KV head on each GPU.
  - The sparse decode and the exact sink/recent window are QSA-only and
    gfx1100-only for now.
  - Head size 128 is the next step.
- **Size.** This is a large PR: about 1.4k lines of gfx942 kernels on top of
  the RDNA3 ones. Each architecture lives in its own file behind the same
  `octave_prefill` / `octave_decode` entry points, so it can be reviewed and
  later removed on its own.

**Not a duplicate.** I searched open PRs and issues for `octave`,
`turboquant rocm`, `kv cache 3-bit`, `kv cache quantization hip` and
`lloyd-max kv`. The closest are:
- UltraQuant (#57057): FP4 with FlyDSL for gfx950, built on TurboQuant.
- KVarN (#46613 / #46812): Triton, CUDA-first.
- #43835: HIP int8/int4 for CDNA.
- #40396: a Triton TurboQuant decode for MI300X.
- #53231: TurboQuant for Gemma 4 on ROCm.
- #59132: Triton attention for RDNA without KV quantization.

None targets RDNA with native kernels, and none runs below 8 bits with MTP on
ROCm.

# Qwen3.8-27B on Dual RX 7900 XTX: Benchmarking KV Cache Quantization in vLLM

I wanted to see how well Qwen3.8-27B would run on two AMD Radeon RX 7900 XTX GPUs (24 GB each), especially during long conversations. The goal was straightforward: reduce GPU memory usage by quantizing the KV cache, while keeping generation speed and answer quality as close as possible to the unquantized setup.

I compared five KV-cache configurations in vLLM, all using `float16` and tensor parallelism across both GPUs. Three packing variants—`k3v3`, `k3v4`, and `k3v3_compact`—use our RDNA3 backend, **Octave** ([vLLM PR #59774](https://github.com/vllm-project/vllm/pull/59774)). `int8_per_token_head` uses a separate quantized kernel implementation, while `auto` leaves the KV cache unquantized. The model was [`cyankiwi/Qwen3.8-27B-AWQ-INT4`](https://huggingface.co/cyankiwi/Qwen3.8-27B-AWQ-INT4).

## Main results

| KV-cache mode | Generation speed at ~180K context tokens | KV-cache capacity (tokens) | GSM8K accuracy |
|---|---:|---:|---:|
| **`k3v3_compact`** | **44.8 tokens/s** | **1,385,454** | **75%** |
| `k3v3` | 44.4 tokens/s | 1,143,333 | 74% |
| `k3v4` | 43.8 tokens/s | 1,005,882 | 75% |
| `int8_per_token_head` | 31.8 tokens/s | 505,185 | 72% |
| `auto` (unquantized) | Test not completed | 252,671 | 73% |

The three Octave variants sustained roughly **44–45 tokens/s even with ~180K tokens of context**. `k3v3_compact` also provided the highest KV-cache capacity. The separate INT8 implementation slowed down more at long context lengths, while unquantized `auto` performed substantially worse.

The capacity figures above describe the **aggregate KV-cache token capacity reported by vLLM**, not the maximum length of a single conversation. For these tests, `--max-model-len` was set to **200,000 tokens**.

One important correction came out of the testing. Our first measurements made long-context generation look extremely slow, but the issue was in our benchmark script rather than the quantized cache. We estimated how long prompt processing (*prefill*) would take and accidentally counted much of that time as generation. We fixed the measurement by using streaming and timing the interval between the first and last received output tokens.

That revealed the real bottleneck: **processing a very long prompt before generation begins**. At around 180K context tokens, the quantized modes took roughly **two minutes to produce the first token**. Once generation started, however, they still ran at around 44 tokens/s. This distinction matters when judging how responsive the model feels in everyday use.

## Did quantization affect quality?

We did not observe a clear quality difference in these tests. All five configurations answered our 10 reasoning questions correctly and passed the *needle-in-a-haystack* retrieval checks at the tested context lengths. We then used vLLM's GSM8K evaluation (`gsm8k_eval.py --num-shots 5 --max-tokens 256`, same command for all five variants) and obtained accuracy scores between **72% and 75%**. That sample is too small to establish a statistically significant difference between the modes, but the results suggest that KV-cache quantization did **not cause a noticeable loss of accuracy** in these tests.

We also measured server throughput using the official `vllm bench serve` tool (`vllm bench serve --dataset-name random --random-input-len 2000 --random-output-len 500 --num-prompts 60 --max-concurrency 4`, same command for all five variants, just pointed at each server):

| KV-cache mode | Aggregate generation throughput |
|---|---:|
| `k3v3` | 100.4 tokens/s |
| `k3v4` | 99.9 tokens/s |
| `k3v3_compact` | 99.3 tokens/s |
| `int8_per_token_head` | 99.6 tokens/s |
| `auto` | 68.1 tokens/s |

## Which one would I use?

**For this setup, I would choose `k3v3_compact`.** It offers the largest KV-cache capacity, maintains strong generation speed with long contexts, and showed no noticeable accuracy loss in our tests. `k3v3` is a very close alternative; based on these results, it is difficult to justify using unquantized `auto`.

These findings apply to **two RX 7900 XTX GPUs and this particular vLLM build**. Other hardware or software configurations may produce a different ranking.

*Tests carried out October 10–13, 2026. Backend: [Octave, vLLM PR #59774](https://github.com/vllm-project/vllm/pull/59774).*

# Benchmarks — Qwen3.8-27B-AWQ-INT4 on 2x AMD RX 7900 XTX

A report with the real numbers from putting this model through its paces on the ROCm stack we have set up. It includes three methodology corrections we made along the way — the last two after review feedback — because each one changed what the numbers actually mean.

## Read this first: each KV-cache mode also changes the attention backend

This is the single most important caveat in the document, and it was missing from earlier revisions. On this stack, choosing `--kv-cache-dtype` does not only change how the KV cache is stored — **it also changes which attention backend vLLM selects**, because each backend only accepts certain cache layouts. Confirmed from the startup logs of every configuration:

| KV-cache mode | Cache storage | Attention backend selected |
|---|---|---|
| `k3v3`, `k3v4`, `k3v3_compact` | 3-bit quantized | `ROCM_OCTAVE` (the Octave backend) |
| `int8_per_token_head` | int8 | `TRITON_ATTN` |
| `auto` | fp16, unquantized | `ROCM_ATTN` |

The log line for `auto`, for example, reads:

```
Found incompatible backend(s) [TURBOQUANT, …] with AttentionType.DECODER.
Overriding with ROCM_ATTN out of potential backends: ['ROCM_ATTN', 'TRITON_ATTN']
```

(The elided entry is the Octave backend, which the stock image still reports under its older internal enum name.)

**What this means for every number below:**

- Comparisons **within** the Octave family (`k3v3` vs `k3v4` vs `k3v3_compact`) are clean: identical backend, only the packing variant differs. These are the only strictly apples-to-apples comparisons in this report.
- Comparisons **across** families (Octave vs `int8_per_token_head` vs `auto`) measure **backend and cache format together**, not quantization in isolation. A figure like "Octave is 3.8x faster than unquantized" is really "Octave-on-`ROCM_OCTAVE` is 3.8x faster than fp16-on-`ROCM_ATTN`" — a legitimate end-to-end result for this stack, but not evidence about quantization on its own.
- This is **structural, not a misconfiguration.** Octave's kernels require the quantized cache layout, so a "Octave with an unquantized cache" configuration does not exist and cannot be constructed. There is no way to isolate the quantization variable on this hardware with these backends. We checked whether `int8_per_token_head` and `auto` at least shared a backend (which would have given one matched pair) — they don't: `TRITON_ATTN` vs `ROCM_ATTN`.
- We verified this is not an eager-mode artifact: every configuration ran with `enforce_eager=False`, `cudagraph_mode=FULL_AND_PIECEWISE`, and CUDA graphs captured successfully at startup (both PIECEWISE and FULL passes present in the logs).

## Methodology correction #1: decode speed vs. prefill

The first version of this report measured "long-context decode speed" with a broken formula: it estimated prefill time as `prompt_tokens / 3000` and subtracted that from the total request time to get "decode time." From ~80K tokens of context onward, that prefill estimate was far lower than real prefill (which takes tens of seconds, not a fraction), so almost all of the request time got wrongly attributed to decode — making generation speed look like it collapsed to ~1 tok/s at long context, when in reality **it stays at 40-50 tok/s for a single in-flight request**.

The fix: use streaming (`stream: true`) and measure the time between the first and last token received to get real decode speed, isolated from prefill. Time to first token (TTFT) does include the full prefill and is reported separately.

## Methodology correction #2: GSM8K was underreporting

The GSM8K numbers in the first version (72-75% accuracy) were measured through the plain `/v1/completions` endpoint with `--max-tokens 256`. For a chat-tuned model that truncates a meaningful fraction of answers before they reach the final number, depressing the measured accuracy without reflecting any real quality difference.

The fix: run the same evaluation through `/v1/chat/completions` (`--use-chat-completions`), with thinking disabled (`--chat-template-kwargs '{"enable_thinking": false}'`) and `--max-tokens 2048`. Corrected scores land in the **97-98%** range for every variant. The relative ranking is unchanged; only the absolute numbers were wrong.

## Methodology correction #3: the long-context concurrent numbers were misread

Our first write-up of the 4-concurrent × 150K test claimed decode speed "converges to ~0.7-0.9 tok/s across all five variants," and concluded the packing variant stops mattering at long context. **That reading was wrong, and the conclusion was backwards.**

- `Output token throughput` (0.77-0.81 tok/s) divides 512 generated tokens by the full ~650s benchmark duration — and **~415s of that is prefill** (the mean TTFT). It is not a decode-rate measurement at all.
- `Mean TPOT` (~1.2s) isn't pure decode either: while one request generates, the other three are still chunked-prefilling 150K tokens each, so every decode step queues behind those prefill chunks. It measures scheduling contention, not generation speed.
- **Real decode throughput shows up in the peak**, once prefill has drained: see the corrected table below.

The corrected conclusion is the opposite of what we first wrote: at long context the choice of KV-cache mode matters **more**, not less.

## Speed at long context, real concurrency (150,000 in / 128 out, 4 concurrent) — corrected

4 requests in flight, 150K tokens each, 600K tokens of aggregate context:

| Variant | TTFT (mean) | Peak decode throughput | Prefill-dominated avg. (not a decode rate) |
|---|---:|---:|---:|
| `k3v3_compact` | 429.2s | **80 tok/s** | 0.79 tok/s |
| `k3v3` | 417.7s | **76 tok/s** | 0.78 tok/s |
| `k3v4` | 416.1s | **67 tok/s** | 0.81 tok/s |
| `int8_per_token_head` | 412.8s | **50 tok/s** | 0.77 tok/s |
| `auto` (unquantized) | **1226.5s** | **1 tok/s** | 0.23 tok/s |

Two things to read from this:

**1. Generation speed does not converge — it separates sharply.** Once prefill drains, the Octave variants sustain 67-80 tok/s, `int8_per_token_head` 50 tok/s, and `auto` just 1 tok/s. The ~0.7-0.9 tok/s figures in the last column are the average over the whole run including ~415s of prefill, which is why they look flat across variants; they are a measure of total job duration, not of generation speed. Our earlier revision quoted that column as if it were decode speed, and wrongly concluded the variant choice stops mattering at long context. It is the opposite: this is where the gap is widest.

**2. `auto`'s TTFT penalty at this length is partly a capacity cliff.** At 150K tokens per request, four concurrent requests need 600K tokens of KV cache — far past `auto`'s 252,671-token ceiling. The four cannot be admitted together, so they serialize, and the last waits behind three full prefill+decode cycles. That inflates its TTFT to ~3x worse (1226.5s vs ~413-429s) while the quantized variants, which hold all four, only pay the normal interleaved-prefill contention. The follow-up test in the next section removes the serialization and shows how much of the gap survives without it — most of it does.

**Relevance to our workload**: production here is 4 concurrent requests up to 32K tokens each (~128K aggregate), comfortably inside what any of these modes can admit. This 600K-aggregate scenario is a stress test well beyond it, run specifically to answer "what happens at real concurrency *and* long context" — it is not our operating point.

## Isolating the capacity cliff: 4 concurrent × 60K (240K aggregate)

The 150K test above left one variable tangled: `auto`'s 3x TTFT penalty could be its small cache forcing serialization, or a genuine throughput deficit, or both. To separate them we re-ran at **60,000 tokens per request** — 240,000 aggregate, deliberately just under `auto`'s 252,671-token ceiling, so all four requests are admitted concurrently in every mode and nothing serializes.

Both configurations reported `Peak concurrent requests: 4.00`, confirming no serialization on either side:

| Metric | `k3v3_compact` | `auto` | Ratio |
|---|---:|---:|---:|
| Peak concurrent requests | 4.00 | 4.00 | — (both admitted all four) |
| Benchmark duration | 222.3s | 522.8s | 2.4x |
| Mean TTFT | 146.8s | 278.5s | 1.9x |
| **Median ITL (clean decode)** | **32.1 ms** | **531.1 ms** | **16.5x** |
| Peak decode throughput | 114 tok/s | 8 tok/s | 14x |

**The capacity cliff was not the whole story.** With serialization eliminated, `auto` is still 1.9x slower on prefill and roughly 15x slower on decode. So the 150K result's 3x TTFT gap had a capacity component, but removing it does not rescue `auto` — the underlying deficit is real and large at matched admission.

Two incidental findings worth noting:

- **Median ITL is the cleanest decode metric in these runs.** For `k3v3_compact` the mean ITL is 585 ms but the median is 32.1 ms — the mean is dragged up by the prefill contention of the other three requests, while the median reflects steps where decode actually ran unimpeded. 32.1 ms is ~31 tok/s, consistent with the short-context measurements. Where earlier revisions of this report quoted mean TPOT/ITL at long context as "decode speed", the median is the number that answers that question.
- **Prefill overhead in `auto` appears only under load.** At 8K single-request, TTFT was essentially identical between modes (6.3s vs 5.9s) — Octave adds no prefill overhead. But at 4×60K, `auto`'s prefill is 1.9x slower. Consistent with the cost of writing a much larger unquantized cache once bandwidth is contended.

As with every cross-family comparison in this report, this still bundles the attention backend with the cache format and cannot be decomposed into "how much is quantization" (see the opening section).

## What the numbers say

### 1. Within the Octave family, `k3v3_compact` is the best choice

This is the one fully controlled comparison in the report — same backend, same everything, only the packing variant differs:

- `k3v3` and `k3v4` are equal on speed (44.4 vs 43.8 tok/s at 180K single-request; 76 vs 67 tok/s peak under long-context concurrency). `k3v4` spends more bytes per token on the value cache, so it fits less context for no speed gain.
- `k3v3_compact` is as fast or faster than `k3v3` and holds the most context of any mode — measured at ~7,070 B/token, against ~8,770 for `k3v4` (a 1.24x advantage at equal memory; see the capacity note above for why the raw token counts overstate this). It achieves that with an extra Hadamard rotation over the keys, which costs a little compute per token — but the cost does not show up as a measurable speed penalty in any of our tests.
- No meaningful quality difference was observed among the three in these evaluations.

### 2. `auto` is clearly the worst option on this stack — but attribute it correctly

`auto` is worse on every speed and capacity axis: 20.6 vs ~30 tok/s at short context, 1 vs 67-80 tok/s peak decode at 150K under concurrency, 286s TTFT at 150K single-request, 1226.5s TTFT under concurrency, and a ~252,671-token cache ceiling (roughly a quarter of the Octave variants', and the one capacity figure we re-verified directly). Critically, the matched 4×60K test shows this is **not** merely an artifact of its small cache forcing serialization: with all four requests admitted in both modes, `auto` is still 1.9x slower on prefill and ~15x slower on decode. For a long-context workload on this hardware, don't use it.

But the *reason* is a package deal: unquantized fp16 cache forces the `ROCM_ATTN` backend, and the measured gap reflects both together. We cannot report a clean "quantization gives Nx" figure from this data, and we aren't claiming one.

### 3. `int8_per_token_head` brings nothing here

It matches the Octave variants at short context (31.6 tok/s on `TRITON_ATTN`), but degrades more with context single-request (50.6 → 31.8 tok/s, -37%, vs ~-14% for Octave), peaks lower under long-context concurrency (50 vs 67-80 tok/s), and holds roughly half the cache of the Octave variants. No axis on which it wins.

### 4. TTFT is the real long-context cost, and concurrency multiplies it

Single-request TTFT grows roughly linearly with context for the quantized modes: ~6.4s at 8K, ~22s at 30K, ~60s at 80K, ~120s at 180K. Under 4-concurrent load at 150K each it rises to ~413-429s from interleaved prefill contention, and for `auto` to 1226.5s because its capacity ceiling adds forced serialization on top. In day-to-day use this — not decode speed — is what reads as "slow" in a long conversation.

## Conclusion

1. **Use a quantized KV-cache mode for long contexts.** On this stack `auto` is worse on speed and capacity at every context length we measured. Its small cache adds a serialization cliff under concurrency, but that is not the root cause: in a matched test where all four concurrent requests fit in both modes, `auto` is still 1.9x slower on prefill and ~15x slower on decode.
2. **Among the Octave variants, `k3v3_compact` is the best**: same speed as `k3v3`, more capacity than anything else. This is our recommendation, and it rests on the report's one fully controlled comparison. `k3v3` is a close, slightly simpler alternative, and the extra capacity of `k3v3_compact` is not needed at our production load — so either is defensible.
3. **`k3v4` and `int8_per_token_head` offer no advantage** over `k3v3_compact`.
4. **No meaningful quality difference was observed across the five modes** (97-98% GSM8K, NIAH pass at every reached length). These tests do not establish absolute equivalence or cover complex reasoning over long contexts.
5. **Cross-family speed comparisons in this report bundle the attention backend with the cache format**, and cannot be decomposed on this hardware. Only the within-Octave comparisons isolate the packing variant.
6. **At long context under real concurrency, the gap between modes is at its widest** (67-80 vs 50 vs 1 tok/s peak decode) — the opposite of what our previous revision concluded from a prefill-contaminated average.
