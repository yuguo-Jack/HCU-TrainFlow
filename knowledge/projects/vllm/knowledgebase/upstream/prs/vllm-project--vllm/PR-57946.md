# [Bugfix] Handle MoE padding sentinel in FlashInfer b12x experts

[Upstream PR](https://github.com/vllm-project/vllm/pull/57946) · state: open · merged: False

## Original PR description

## Purpose

`VLLM_MOE_SKIP_PADDING` (on by default) makes the topk kernels write `-1` into `topk_ids` for
cudagraph padding rows, so downstream MoE kernels can skip work for them. `FlashInferB12xExperts`
never handled that sentinel and passed `topk_ids` straight into `B12xMoEWrapper.run()`, where the
b12x kernels index the expert state with the raw id. A value of `-1` writes outside the workspace
and trips an MMU fault:

```
NVRM: Xid (PCI:000f:01:00): 31, pid=..., name=python3, MMU Fault: ENGINE GRAPHICS GPC1
      FAULT_PDE ACCESS_TYPE_VIRT_WRITE
RuntimeError: Triton Error [CUDA]: an illegal memory access was encountered
```

Chronology, since the base has moved: on the build this was isolated on (`5db652225`) the
profiling run marked every row as padding, so all 40960 routing indices were `-1` and the engine
faulted in `determine_available_memory()` before the server could start. Current `main` no longer
does that — `is_padding=not is_profile` in the V2 runner (#57270) deliberately routes profiling
tokens to experts so MoE memory is measured — so the startup repro no longer applies as written.
The bug itself is unchanged: cudagraph padding, idle-DP dummy batches and trailing padded rows on
real batches all still emit the same sentinel, so b12x remains unsafe on current `main`.

Note the reported traceback is misleading. Without `CUDA_LAUNCH_BLOCKING=1` the fault surfaces at
the *next* Triton `load_binary`, which for this model is `_hc_combine_kernel` in layer 0's
attention — before any MoE has run. With blocking launches the faulting call is
`flashinfer_b12x_moe.py:288`, `wrapper.run(...)`.

Neutralize the sentinel where the other routing fixups happen: route padding rows to expert 0 with
zero weight, contributing nothing to the output. The router's mask is per row (`is_padding[:num_tokens]`), so a marked
row is `-1` in every slot, and no live row loses a single expert. Unguarded, b12x never gets as far as producing
discardable output for those rows: it indexes expert state with the `-1`, an out-of-bounds access that kills
the CUDA context. The guard
runs only when `VLLM_MOE_SKIP_PADDING` is on: every sentinel writer is gated on that flag and b12x takes no
expert map, so with the flag off no `-1` can arrive (a static read, resolved while the graph is traced). The rewrite is branchless so it remains
cudagraph-capturable. This mirrors the AITER fix in #57036 and the XPU gating in #55231.

Fixes #50189.

## Test Plan

- New regression test `test_flashinfer_b12x_moe_tolerates_padding_sentinel` in
  `tests/kernels/moe/test_flashinfer_b12x_moe.py`, three cases: `(32, 2, half)` -> 64 routed rows,
  the static b12x path; `(384, 2, all)` -> 768 routed rows, every row padded, crossing the 640-row
  static/dynamic cutover; `(32, 2, nan)` -> padded activations poisoned with NaN, since cudagraph
  padding rows may carry NaN/Inf. Asserts padding rows are exactly zero and finite, and that real
  rows match a run without padding. The test is skipped when `VLLM_MOE_SKIP_PADDING` is off, since no
  sentinel is written and the guard is skipped then.
- Hot-path cost of the guard, measured with CUDA events at the model's real shapes
  (E=512, k=2560, n=640, topk=10), eager and inside a CUDA graph.
- End-to-end: serve Qwen3.8-Flash-Next NVFP4 with `--moe-backend flashinfer_b12x` on GB10 and
  confirm the engine starts and generates.
- Isolated repro against FlashInfer directly (no vLLM), varying only the routing table.

Whole file with this patch: 51 passed with the flag on; 48 passed, 3 skipped with

End-to-end, same checkpoint and flags:

| --- | --- |
| before | engine dies in `determine_available_memory()`, Xid 31 |
| after  | serves in 660 s; `"Name the four seasons"` -> `"spring, summer, autumn, winter"` |

Isolated FlashInfer repro, same process, same shapes (E=512, k=2560, n=640, topk=10, 40960 routed
rows) — only the routing table differs:

| `topk_ids` | result |
| --- | --- |
| all `-1` | illegal memory access |
| padding masked to expert 0, weight 0 | clean, finite output |

Hot-path cost of the guard (E=512, k=2560, n=640, topk=10), CUDA events, vs the b12x MoE call
at the same shape:

| M | sentinel eager us | sentinel graphed us | MoE graphed us | guard, % of graphed MoE |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 22.25 | 6.33 | 117.92 | 5.4% |
| 2 | 21.68 | 6.86 | 284.53 | 2.4% |
| 4 | 22.05 | 6.74 | 482.11 | 1.4% |
| 8 | 21.09 | 6.34 | 1045.32 | 0.6% |

The eager cost is flat at ~21 us across every M, i.e. it is kernel-launch overhead on a `[M, topk]`
tensor rather than work. Decode runs under CUDA graphs, where the three ops replay in ~6.3 us --
5.4% of the MoE call at M=1 and under 1.5% from M=4 up. Both sides are captured here; the MoE call
is only ~11% faster graphed than eager, so it is GPU-bound rather than launch-bound. At ~2 us per replayed kernel this is near the
floor for elementwise ops on this device; going lower means handling `topk_id < 0` inside the
FlashInfer b12x kernel, which would also avoid computing expert 0 for padded routes at all.

Note there is no b12x "before" number for end-to-end decode: without this patch the backend faults,
so the unpatched configuration cannot be benchmarked. `VLLM_MOE_SKIP_PADDING=0` is the way to
isolate the guard's end-to-end cost, and I can add that measurement if it would help.

On NaN: padded rows whose activations were set to NaN still produce exactly zero, finite output
(0 NaN of 40960 elements), so the zero route weight is not defeated by `0 * NaN` here.

Routing measured at the router's return: the 4096-token profiling batch is 40960/40960 negative,
while the 32-token warmup a few calls later routes normally (ids 1..504), with finite inputs in
both cases — i.e. legitimate sentinel values, not corrupted memory. `FLASHINFER_CUTLASS` tolerates
them on the same checkpoint, which is why only the b12x path faulted.

- hclsys · comment · 2026-09-23T15:27:59Z · [source](https://github.com/vllm-project/vllm/pull/57946#issuecomment-5797663608)

Can't give you SM120 numbers — I'm on a GB10 too, so mine would be the same favourable case you already flagged. Two things from reading it instead.

**The thing a reviewer would stop on, and it's fine.** Zeroing `topk_weights` where `topk_ids < 0` is only safe if the sentinel is written per *row*, not per slot — otherwise you'd be dropping one expert from a live row and silently changing the remaining weights' normalization. It is per row: `_get_padding_mask()` in `router/fused_topk_router.py` returns `is_padding[:num_tokens]`, a `[num_tokens]` mask, and that's what `ops.topk_softmax` takes. So a marked row is fully `-1` and the whole row's output is zero and discarded. Worth stating explicitly in the PR body, since the guard itself is written elementwise and reads as if per-slot sentinels were possible.

**One way to make the cost you're worried about disappear where it doesn't apply.** The guard runs unconditionally, but with `VLLM_MOE_SKIP_PADDING=0` no `-1` can ever reach here — the routers only mark padding under that flag. Gating it:

```python
if envs.VLLM_MOE_SKIP_PADDING:
    topk_ids = topk_ids.to(torch.int32)
    ...
else:
    topk_ids = topk_ids.to(torch.int32)
```

is a Python-level read of a static env, resolved while the graph is being traced, so it doesn't cost you capturability. That doesn't help the default path, which is the one your table measures — but it does mean the 6.3 us is only ever paid by configurations that can actually produce the sentinel, which seems worth having given the SM120 share you're raising yourself.

The `torch.where` pair itself looks right to me: both operate on `[M, topk]`, the scalar `0.0` stays weakly typed so `topk_weights` keeps its dtype, and routing to expert 0 with zero weight is a no-op in an accumulate-style MoE.

**One thing I went looking for and did not find**, in case anyone else wonders: `torch.where(is_padding, 0.0, topk_weights)` with a Python `0.0` does **not** promote — bf16 in, bf16 out, and bitwise identity when the mask is all-False. Python scalars are weak-typed in the promotion rules, so the kernel still receives its original dtype. I expected an fp32 upcast and was wrong.

`if envs.VLLM_MOE_SKIP_PADDING:` reading a module-level env value also does what your comment claims under tracing — it's a Python-level constant at trace time, so the flag-off path has no branch in the captured graph rather than a predicated one.

The cause is just that **nothing deselects it for you**. `test_flashinfer_b12x_moe_tolerates_padding_sentinel` is one function (3 params) with no flag guard; the two `pytest.skip` calls at the top of the file are the CUDA/family gates. `vllm.envs` does pick the shell variable up correctly (`VLLM_MOE_SKIP_PADDING = False`), so with the flag off the test feeds `-1`, the guard is skipped by design, and b12x indexes expert state with it. Your 48 must have come from deselecting by hand rather than from the file doing it — worth a `skipif` so the next person doesn't get an illegal access instead of a skip:

```python
@pytest.mark.skipif(
    not envs.VLLM_MOE_SKIP_PADDING,
    reason="the sentinel is only written when VLLM_MOE_SKIP_PADDING is on",
)
```

Incidentally this makes the PR's case stronger than the description does. The body reads as if an unguarded `-1` gives wrong-but-finite output that the router discards; on sm_121 it's an out-of-bounds access that kills the context. "Its whole output is discarded" is true of the *router's* mask, but the kernel never gets that far.
