## Overview

Add nonblocking GPU duration to existing per-iteration logging. This is the timing layer split from #52061, not another implementation of #61424's scheduler counters (dependency head `650d50d154d0f7ada81a3783b1408c8a7d0193db`) or an additional workload/export API. ## Claims

- `--enable-logging-iteration-details` automatically collects timing when log statistics and runtime support permit it. Timing defaults off; `iteration_timing_enabled` is derived before worker initialization, not a constructor or CLI option. Unsupported logging configurations retain counts-only logs with a warning.
- Only the output worker of each DP replica owns pooled `torch.Event` pairs. Scheduler snapshots and asynchronously completed durations are joined by iteration ID in `SchedulerStats.iteration_records`. GPU-duration samples use milliseconds throughout; the later FPM exporter converts to its existing seconds-based wire format.
- The recorded `model_step_cuda` interval covers execution, sampling and speculative drafting on the recorded stream, including host-submission gaps. With PP, only the last stage's output worker is timed; this may include waiting for earlier stages. It is neither kernel-busy time, whole-pipeline/request latency, nor a sum of independent streams.
- Actual execute/sample/dummy calls stay visible in `gpu_worker.py`. A same-file guard starts scheduled iterations and cancels on error; sampling continues the interval. Conditional finish remains explicit. Dummy has its own complete-lifecycle context. MRV2 is primary; MRV1 shares the instrumentation for existing Dynamo deployments during migration.
- Normal outputs carry ready samples. Tail collection permits one outstanding RPC and checks readiness/FIFO before consuming it; active execution also reaps a previously submitted query. Future completion now uses the existing `result()` path. The poll contract distinguishes an unavailable response from an empty completed response. No timing-specific CUDA synchronization or blocking flush is added.
- Per-iteration logs no longer attach current KV-cache usage to historical records; periodic KV reporting remains. This PR does not add workload/context statistics, idle heartbeats, Prometheus instruments or a publisher.

## Details

Support is generative CUDA models with `uni`/`mp` executors and out-of-process EngineCore. Non-CUDA, pooling, Ray/external-launcher and in-process logging retain counts only. The later workload/FPM layers require timing and reject unsupported configurations. With no active logging consumer, this layer creates no timer pool, collector or timing polls.

Collection still adds event, CPU and IPC overhead. Shutdown's bounded best-effort drain can lose tails. Prior native-MTP PP2 qualification covers MRV2 async eager only; other attempted combinations failed on the timing-off baseline. Prior DP output checks passed, but teardown needed worker force-kill. Neither broad PP2-MTP support nor graceful DP shutdown is claimed.
