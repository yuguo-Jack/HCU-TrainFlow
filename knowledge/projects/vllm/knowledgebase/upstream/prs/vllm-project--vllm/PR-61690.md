## Original PR description

## Overview

Add nonblocking GPU duration to existing per-iteration logging. This is the timing layer split from #52061; it does not change scheduler counters or add a workload/export API.

Dependency order: **#61690 (timing)** → #61691 (workload) → #52061 (FPM exporter). This stack is independent of, and complementary to, #61424; that PR is not a prerequisite. [Next layer](https://github.com/vllm-project/vllm/pull/61691) · [Review only this layer](https://github.com/tedzhouhk/vllm/compare/190df0b90007eead441d97d3abf6270f84f2c63e...f2a63a8ffb766a2c7444156953afda2a710f3ee6).

The existing PR numbers and review history are retained. All three target `main`, so downstream upstream-facing diffs are cumulative; use the layer-only comparisons and merge/rebase in order. Related proposals: #61423, #39979, #38760.

This main-merge update applies to #61690 only; #61691 and #52061 are intentionally not restacked or updated.

## Claims

- `--enable-logging-iteration-details` enables timing when log statistics and runtime support permit it. Timing remains default-off; `iteration_timing_enabled` is derived before worker initialization, not exposed as another CLI or constructor option. Unsupported logging configurations keep counts-only logs with a warning.
- Existing `compute_iteration_details` supplies the logging snapshot before worker execution. This PR does not change `scheduler.py`, `vllm/v1/utils.py`, or the profiler's counter algorithm. Workload counts and phase snapshots belong to #61691.
- Only the output worker of each DP replica owns pooled `torch.Event` pairs. Completed durations join their own snapshots by iteration ID in `SchedulerStats.iteration_records`. Records are delivered only after both timing and model-output processing complete; internal durations stay in milliseconds.
- Timing covers execute, sampling and speculative drafting, including the complete DP dummy call. Function-level decorators in `iteration_timing.py` keep execution, sampling and dummy control flow out of the worker method bodies while preserving their timing boundaries and cancelling failed iterations. MRV2 is primary; MRV1 is retained for existing deployments during migration.
- Existing scheduler statistics stay on their original frontend, preserving request-local LoRA enrichment; completed records are attached once. Frontend zero is only the fallback when no stats owner exists. The producer only appends to the timing deque; one nonblocking drain lock serializes removal, without a second pending-deque lock.
- Normal outputs carry ready samples. Tail collection allows one outstanding RPC and checks readiness/FIFO before consuming it through the existing `result()` path. Unavailable and completed-empty responses remain distinct. Delayed associations survive until the complete record can be joined; no timing-specific CUDA synchronization or blocking flush is added.
- Historical iteration records no longer include current KV-cache usage; periodic KV reporting remains. This layer adds no workload/context statistics, idle heartbeats, Prometheus instruments or publisher.

## Details

Support remains generative CUDA models with `uni`/`mp` executors and out-of-process EngineCore. Non-CUDA, pooling, Ray/external-launcher and in-process logging retain counts only. Without a logging consumer, PR1 creates no timer pool, collector or timing polls.

The `model_step_cuda` interval includes host-submission gaps on the recorded stream. PP measures only the last-stage output worker and may include upstream-input waits—not whole-pipeline/request latency, kernel-busy time or independent-stream totals. Collection adds event, CPU and IPC overhead; bounded best-effort shutdown may lose tails.

Historical native-MTP PP2 qualification covers MRV2 async eager only; other attempted combinations failed on the timing-off baseline. Historical DP output checks passed but teardown needed force-kill, so graceful DP shutdown is not established.
