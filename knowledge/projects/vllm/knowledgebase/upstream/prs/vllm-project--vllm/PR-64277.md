# [Bugfix][Kernel] DSv4 router: compute sqrt(softplus) with log1p

[Upstream PR](https://github.com/vllm-project/vllm/pull/64277) · state: open · merged: False

## Original PR description



## Overview

The DeepSeek-V4 `sqrtsoftplus` routers compute softplus(x) as log(1 + exp(x)) in fp32. For x below about -16.64, 1 + exp(x) rounds to 1, so the expert's score is exactly 0. Up to about x = -10 the score is off by more than 1e-3 relative (77% at x = -16.6 in the CUDA kernels). This PR computes log1p(exp(x)) instead, in the Triton `dsv4_topk` kernel and in the CUDA `topk_softplus_sqrt` kernels. It makes the same change in the GB300 CuTe DSL MoE front, which must match `dsv4_topk` bit for bit. Related: #49927.

## Claims

- Max relative error of sqrt(softplus(x)) for x in [-30, -5], main vs this PR:
  - Triton `dsv4_topk`: 1.0 -> 9.15e-7
  - CUDA hash kernel: 1.0 -> 2.18e-7
  - CUDA generic kernel: 1.0 -> 1.43e-7
- On main, a token whose selected experts all have logits <= -16.64 gets all-zero routing weights (sum 0.0 instead of `routed_scaling_factor`), so it gets no routed expert output. With this PR its weights match the `F.softplus(x).sqrt()` reference.
- The GB300 specialized-decode front still matches `dsv4_topk` bit for bit. Its top-k ids and weights were compared on an sm_120 GPU: 192/192 launches identical on main and with this PR. Patching only the Triton side makes 105/192 differ.
- Cost per router call:
  - Triton: +0.07 to +0.09 us (+4% to +5%) up to 512 tokens, +0.25 to +0.28 us (+4%) at 4096 tokens.
  - CUDA hash kernel: +0.04 us at 1 token, within run-to-run noise (-7% to +5%) at 8-512 tokens, +0.60 to +0.74 us (+25% to +32%) at 4096 tokens.
  - CUDA generic kernel: +1% to +14%.

## Details

**Root cause.** In fp32, 1 + exp(x) keeps only the bits of exp(x) that fit next to the leading 1. For x < -16.636 (exp(x) < 2^-24) nothing survives, and the log returns 0. Above that, the rounding error of the sum is up to 2^-24 in absolute terms, which is large relative to softplus(x) ~ exp(x). The CUDA kernels add `__logf`, whose absolute error near 1 is larger still. `log1p(exp(x))` never forms 1 + exp(x) and keeps full relative precision.

**The change.**
- Triton: `tldevice.log1p(tl.exp(logits))`, which is libdevice `__nv_log1pf`. `tl.exp` and the x > 20 branch are unchanged.
- CUDA hash kernel: `sqrtf(fmaxf(x, 0.f) + log1pf(expf(-fabsf(x))))`, at both sites.
- CUDA generic kernel: `log1pf(expf(val_b)) / beta`, at both sites.
- `expf` replaces `__expf`: keeping `__expf` gave no consistent speedup (table above) and a 4x larger maximum error.
- GB300 CuTe front: the inline PTX now produces exp(x) (the `add.f32 ..., 1.0` is gone), and the log is `cute.math.log1p(..., fastmath=False)` (libdevice `log1pf`) instead of `cute.math.log`. The module docstring is updated to match.

**Impact.** In the hash-routed layers the experts come from the token id, not from the logits, so a token's six weights are the scores of whatever logits those experts get. If they are all very negative, main renormalizes scores with up to 77% error, or returns all-zero weights. In bias-routed layers, experts whose scores underflow are ranked by their bias alone. I have not measured how often DeepSeek-V4 router logits fall below -9.6. On GSM8K (above) the change is within run-to-run noise. Ordinary logits also change in the last bits: in the front check's negative control, 11 of 48 launches with randn logits differ between the patched `dsv4_topk` and main. So outputs shift slightly, as #49927 describes for an earlier softplus change.

**Still 0 below x = -87.3.** There exp(x) is no longer a normal fp32 number. With this PR, Triton and the CuTe front still return a score of 0 there (with logits in [-110, -80], 50 of 224 rows got all-zero weights in both). I measured the CUDA kernels only down to x = -30.

**Other implementations of the same formula, not changed here.**
- AMD mono decode stages, `_score` in `vllm/models/deepseek_v4/amd/mono/stages/moe.py` and `vllm/models/deepseek_v41/amd/mono/stages/moe.py`: `log2(1 + exp2(x log2e)) ln2` with `llvm.amdgcn.log.f32`. They are written to match aiter's `topk_gating_kernel_opt` (sqrtsoftplus), which is outside vLLM, so changing them alone would break that match. Not run (no AMD GPU).
- CPU, `csrc/cpu/sgl-kernels/topk.cpp` `sqrtsoftplus`: below x = -15 it uses exp(x/2), so it never returns 0. Above that it computes `(1 + exp(x)).log()`. A numpy fp32 emulation of that formula gives 8.1% relative error at x = -15 and more than 1e-3 up to x = -10.4. Not run: the test host has no AVX-512.
- The ROCm build of `topk_softplus_sqrt_kernels.cu` gets this fix too, but was not built or run.
- #57478 (open, ROCm fused router gate) adds a compensation term to the log (`tl.log(rounded_sum) + correction / rounded_sum`). Not measured here.

- No ROCm run. The only model eval is the GSM8K run above, on V4-Flash at TP1; V4-Pro and V4.1 were not evaluated.
