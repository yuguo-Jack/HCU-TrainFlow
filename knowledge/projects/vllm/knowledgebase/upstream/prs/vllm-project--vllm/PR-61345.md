# [ROCm][DSv4] Require explicit MXFP4 opt-in for MegaMoE shared-expert fusion

[Upstream PR](https://github.com/vllm-project/vllm/pull/61345) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

Follow-up to #61004. Fusing DeepSeek-V4's shared expert into AITER MegaMoE requantizes it from FP8 to MXFP4. With this PR, that requires an explicit opt-in through the online quantization API instead of a dedicated env var, and it goes through the shared fused-shared-expert (FSE) helpers.

## Claims

- Removes `VLLM_ROCM_AITER_MEGA_MOE_FUSE_SHARED_EXPERTS`. Under `--moe-backend aiter_mega_moe`, the existing `VLLM_ROCM_USE_AITER_FUSION_SHARED_EXPERTS` requests the fusion.
- The shared expert is fused only when it is explicitly requantized to MXFP4:
  ```bash
  VLLM_ROCM_USE_AITER_FUSION_SHARED_EXPERTS=1 vllm serve deepseek-ai/DeepSeek-V4-Pro --moe-backend aiter_mega_moe ... \
      --quantization-config.targets '{"*shared_experts*": "mxfp4"}'
  ```
  Without that target, a warning is logged and the shared expert stays unfused in checkpoint precision (FP8).
- No model-specific logic:
  - The decision goes through `resolve_layer_fused_shared_expert` / `is_shared_expert_quant_fse_compatible`, which now take a `moe_backend` argument.
  - The requantization reuses `get_and_maybe_dequant_weights` and the `ONLINE_SHARED_EXPERT_QUANTIZERS` from #55686.
- Kernel, routing and performance are unchanged from #61004.

## Validation

DeepSeek-V4-Pro, MI355X, DEP4, `--moe-backend aiter_mega_moe`. GSM8K: lm-eval, 5-shot.

| `--quantization-config.targets` | Shared expert | GSM8K (strict) |
|---|---|--:|
| `{"*shared_experts*": "mxfp4"}` | fused, MXFP4 | 0.9469 ± 0.006 |
| none | unfused, FP8 + warning | 0.9545 ± 0.006 |

```
INFO  Quantizing 122 layers of types: ffn.shared_experts.down_proj: 61 (from targets: *shared_experts*, mxfp4); ffn.shared_experts.gate_up_proj: 61 (...)
WARNING  VLLM_ROCM_USE_AITER_FUSION_SHARED_EXPERTS is enabled but cannot be enabled - skipping for this layer: AITER MegaMoE fuses the shared experts only when --quantization-config.targets requantizes them to MXFP4.
```

Unit tests:
- `tests/models/test_deepseek_v4_aiter_mega_moe.py` covers `is_shared_expert_quant_fse_compatible` with the MegaMoE backend.
- `tests/model_executor/layers/test_fused_shared_expert.py::test_online_mxfp4_shared_expert_rejects_quark_weight_only_mxfp4_fse` keeps Quark weight-only routed experts incompatible with an `mxfp4` shared-expert target.

## Details

- **Activation key.** MegaMoE (a8w4) quantizes every slot's activations to MXFP8 itself. A `"mxfp4"` target cannot express "MXFP4 weights, MXFP8 activations", so for MegaMoE only the weight key is compared. Other backends still compare both keys: Quark weight-only routed experts have no activation key (BF16 activations), which an `mxfp4` target does not match.
- **Why the shared expert is not built with `Mxfp4OnlineLinearMethod`:**
  - `Fp8LinearMethod` has no `dequantize_weight`, so it can't serve as the source for requantization.
  - `AiterMxfp4LinearKernel` pre-shuffles the weights into a layout MegaMoEV2 can't use.

  Instead, the fused shared expert keeps the checkpoint quant config, minus online quantization. MegaMoE then dequantizes it with `get_and_maybe_dequant_weights` and quantizes it with the registered quantizer.
- **Config class.** On CUDA and ROCm, `deepseek_v4_fp8` resolves to the v4.1 `DeepseekV4FP8Config`, so the check accepts both the v4 and v4.1 classes.
- **Breaking:** `VLLM_ROCM_AITER_MEGA_MOE_FUSE_SHARED_EXPERTS`, added in #61004 and present in v0.32.0rc0–rc2, is removed without a deprecation period. Setting it afterwards triggers vLLM's "Unknown vLLM environment variable" warning (an error with `--fail-on-environ-validation`), and the shared expert stays unfused in FP8. If preferred, I can keep it as a deprecated no-op with a warning for one release instead.
- **Out of scope:** making MegaMoE a generic MoE backend in the oracle.
