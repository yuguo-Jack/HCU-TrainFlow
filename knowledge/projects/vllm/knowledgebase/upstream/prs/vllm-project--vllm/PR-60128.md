# [Tiered-Offloading][Performance] : Lazy CPU block allocation for FS tier 

[Upstream PR](https://github.com/vllm-project/vllm/pull/60128) · state: open · merged: False

## Original PR description

## Overview

In Tiered Offloading, the CPU block allocation for Secondary -> Primary transfer happens in tiering/manager.py. Under load, this leads to, reserving / locking the CPU cache space for long periods of time unnecessarily. For example, when the FS tier has only N threads, we'd only need to allocate space for N jobs for active use. 
This behavior on `main` makes "Promotion Allocation Failure" a function of input requests load. 

## Claims

This PR adds a Lazy CPU block allocation technique, by which the FS tier allocates CPU blocks only when it needs it. With this "Promotion Allocation Failure" becomes a function of the number of FS read/write threads. Users can tune their FS read/write threads value based on their CPU KV cache size. 

Note : With Thread Pool batching https://github.com/vllm-project/vllm/pull/58404 "Promotion Allocation Failure" will further be decoupled from RW thread count. With batching, there is only a small constant number of jobs that are actively promoting at any given time.

## Details

Changes: 
- LazyTransferJob : subclass TransferJob to introduce LazyTransferJob. A dataclass that inputs a  "allocation function" and materializes the CPU cache blocks only when requested. 
- Lock Primary Tier accesses: In the PR, the FS tier threads are responsible for making the actual allocation calls. This interferes with the Scheduler thread launched GPU <-> CPU transfer allocations. As a result, the primary tier accesses from the TieringManager is always guarded by a lock. 
- TieringManager::_scheduler_hit_threads : The allocation by the FS threads should not evict an on-going lookup for a request. _scheduler_hit_threads records the current request lookups and protects them from a FS evict due to allocation. 
- Metrics : Due to the fact that the allocation is lazy, `PROMOTION_ALLOCATION_FAILURE` and `primary_write_chunk_count` are updated during the allocation for the LazyTransferJobs. For Eager jobs (i.e. eagerly allocated) the behavior remains the same as on `main`. 
- Note that the changes only affect the FS tier. Although, the framework for other Secondary tiers to follow suite is established with this PR.

Claude's suggestion for simplifying tiering/manager.py:

**1. `manager.py` — drop `safe_prepare_write` / `_RequestFinalized`**
Add in-flight promotions to the `_maybe_finalize_request` gate (it checks
`is_finished` / `pending_primary_stores` / `pending_cascade_keys` but not
promotions); then a promotion can never allocate post-finalization and the
sentinel has nothing to signal.

**2. `cpu/manager.py` — drop `_is_request_cache_access_finished`**
Its only caller is `safe_prepare_write`; goes with (1), taking the file to +0.

**3. `manager.py:680` — drop the `req_id in self._req_state` check**
Same root cause; unconditional once (1) lands.

**4. `manager.py:673` — move `requested_keys` onto `JobMetadata`**
Drops the `isinstance(transfer_job, PromotionTransferJob)` and the metrics reads
of `transfer_job.keys`/`chunk_ids` — the last non-owner touching a job.

**5. `manager.py` — is `_promotion_failed_requests` still needed?**
`_initiate_promotion` already returns `False` on allocation failure and a full
primary is transient, so banning the request for its lifetime is stronger than
the comment claims; if `_inflight_promotion_keys` plus the natural `MISS` covers
it, drop the set and its three call sites.

**6. `manager.py:684-700` — fold the key partition**
`failed = set(transfer_job.keys) - set(successful_keys)` replaces the
three-branch split.

## Ban requests from promotions for life
I spoke too soon in reverting the ban. 

### `main` vs `This PR` : 

The current state of this PR is "retry until the promotion succeeds". This is bad because, 
 - `initiate_promotion` always returns True in this PR. This is problematic as, a request that fails `materialize()` will re-initiate promotions for the exactly the same set the failed promotion ran with. 
 
We don't have this problem on main, 
 `main` detects capacity issues in `initiate_promotion` and returns a lookup MISS early. As a result we get the following 2 properties, 
    - A request naturally shrinks until it fits or just recomputes on the GPU. 
    - A request whose promotion set is larger than the CPU capacity is automatically denied. " added a test https://github.com/neuralmagic/vllm/blob/0b0bb2fd0602b52d26b1619ec5cfe29c44860b5f/tests/v1/kv_offload/tiering/test_tiering_offloading.py#L647 for this. 
    
Caveat with PR: for FS tier, at high concurrencies, the time between `submit_load` and `materialize()` could be multiple scheduler steps. So the request is already paying considerable time before it knows that the `materialization` failed. 

### What is needed: 
 - Until the bugeting fixes discussed in https://github.com/vllm-project/vllm/pull/62932 lands, we need a way for initiate_promotion to return False, triggering a Lookup MISS.
 
### Fixes considered:  
1. Estimate CPU space in initiate_promotion: This is a bad idea. The drift in CPU cache availability between `initate_promotion` and `materialize()` is too much. Ideally, with FS thread pool batching (transfer one job at a time), the number of promotion blocks pinned at any given time will be much smaller than what is in `main` or this PR. For example consider, 
 15 requests each with 100 promotion blocks, and a CPU KV Cache of 1000 blocks.
 - on `main` - All 15 requests try CPU cache allocation in the same scheduler step. This results in 10 requests passing `initiate_promotion` and 5 requests downgraded to a GPU recompute. 
 - on this `PR` : 
    - with 32 r/w threads, each thread gets one job and similar to `main` only 10 requests pass and 5 requests fail materialization. 
    - with 4 r/w threads, all requests should pass the promotion. 
  - with FS thread pool batching: regardless of the number of r/w threads, all requests should pass. 
  
Estimating CPU space in `initiate_promotion` will preclude Tier level optimizations and downgrade requests prematurely. 
  
2. In the TieringManager::RequestState, record the keys that failed promotions and report a MISS on those keys the next time `initiate_promotion` is requested on that pair. 
  - This will work for pure sliding-window models where the request's promotion set shrinks. 
  - For models with Full-Attention, this will just degenerate to "recompute on the GPU"
  
  Caveat: Even with this, we should consider the time a request waits between `submit_load` and `materialize()` and factor it in the number of retries. 
  
3. Bound retries: 
   Keep it simple and bound the retries. Retry N times, and simply downgrade to GPU recompute. 
   
Suggestion:
 1. The "budgeting and admission" discussion in  https://github.com/vllm-project/vllm/pull/62932 is the ultimate holistic solution. For now, re-introduce the ban for life policy in this PR. and maybe follow up with a retry policy in a separate PR.

Hi @orozery 

I assume the suggestion is to, 
 - Defer CPU block allocation to _flush_pending_promotions, and
 - Submit only as many load jobs as dictated by the tier's max_inflight_promotion_jobs

I think it'd be better to not add another optimization parameter vertical with `max_inflight_promotion_jobs`. 

A `max_inflight_promotion_jobs` requires tuning the parameter for 
 1. CPU KV cache size : We want to use CPU tier judiciously so we dont drop promotions / cascades unnecessarily. A max_inflight_promotion_jobs for a small CPU KV cache is not optimal for a bigger CPU KV cache. For a bigger CPU KV cache, we could allow a more inflight promotions.
 2. Secondary Tier medium (nvme, remote-disks, object-tier etc.) : We want to Exercise the Secondary tier for maximum bandwidth. The max_inflight_promotion_jobs parameter should be such that the submitted jobs keep the Tier active between forward passes.  
 3. Model (model forward pass time) - This dictates the frequency with which we call the flush.
 4. Workload (big vs small requests)

For this instance, I believe we may avoid tuning by letting the runtime workload drive the pressure. 

The crux of the issue really is the over-reservation of CPU blocks. Allocating the blocks only when necessary, lets the Engine (Model) / Workload drive the CPU KV cache space required and the Tiers are not artificially throttled. 

Further, there is a FS threadpool batching argument to this (Planned as a followup). On the PR, each FS thread picks up a job. This is sub-optimal. With batching,  where each promotion job is split across multiple threads, we'd only need to allocate CPU KV cache space for a few jobs at a time. This will drive down the CPU space requirements further, tying a Job's CPU KV cache pinning duration to model forward pass time.

I think there are benefits in letting the tiers handle CPU allocation as they see fit and in letting the system drive the requirements naturally. Pre-allocating, is simpler, but I think with that, we will always need to fight the Promotion / Cascade Allocation Failure performance issues. 

I realize the complexity the PR introduces. I am happy to discuss / re-work implementation. Thanks 🙌
