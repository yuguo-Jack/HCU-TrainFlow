# [Tiered-Offloading][Performance] : Lazy CPU block allocation for FS tier 

[Upstream PR](https://github.com/vllm-project/vllm/pull/60128) · state: open · merged: False

## Original PR description

## Overview

In Tiered Offloading, the CPU block allocation for Secondary -> Primary transfer happens in tiering/manager.py. Under load, this leads to, reserving / locking the CPU cache space for long periods of time unnecessarily. For example, when the FS tier has only N threads, we'd only need to allocate space for N jobs for active use. 
This behavior on `main` makes "Promotion Allocation Failure" a function of input requests load. 

## Claims

This PR adds a Lazy CPU block allocation technique, by which the FS tier allocates CPU blocks only when it needs it. With this "Promotion Allocation Failure" becomes a function of the number of FS read/write threads. Users can tune their FS read/write threads value based on their CPU KV cache size. 

Note : With Thread Pool batching https://github.com/vllm-project/vllm/pull/58404 "Promotion Allocation Failure" will further be decoupled from RW thread count. With batching, there is only a small constant number of jobs that are actively promoting at any given time.

## Details

Changes: 
- LazyTransferJob : subclass TransferJob to introduce LazyTransferJob. A dataclass that inputs a  "allocation function" and materializes the CPU cache blocks only when requested. 
- Lock Primary Tier accesses: In the PR, the FS tier threads are responsible for making the actual allocation calls. This interferes with the Scheduler thread launched GPU <-> CPU transfer allocations. As a result, the primary tier accesses from the TieringManager is always guarded by a lock. 
- TieringManager::_scheduler_hit_threads : The allocation by the FS threads should not evict an on-going lookup for a request. _scheduler_hit_threads records the current request lookups and protects them from a FS evict due to allocation. 
- Metrics : Due to the fact that the allocation is lazy, `PROMOTION_ALLOCATION_FAILURE` and `primary_write_chunk_count` are updated during the allocation for the LazyTransferJobs. For Eager jobs (i.e. eagerly allocated) the behavior remains the same as on `main`. 
- Note that the changes only affect the FS tier. Although, the framework for other Secondary tiers to follow suite is established with this PR.

 - Defer CPU block allocation to _flush_pending_promotions, and
 - Submit only as many load jobs as dictated by the tier's max_inflight_promotion_jobs

I think it'd be better to not add another optimization parameter vertical with `max_inflight_promotion_jobs`. 

A `max_inflight_promotion_jobs` requires tuning the parameter for 
 1. CPU KV cache size : We want to use CPU tier judiciously so we dont drop promotions / cascades unnecessarily. A max_inflight_promotion_jobs for a small CPU KV cache is not optimal for a bigger CPU KV cache. For a bigger CPU KV cache, we could allow a more inflight promotions.
 2. Secondary Tier medium (nvme, remote-disks, object-tier etc.) : We want to Exercise the Secondary tier for maximum bandwidth. The max_inflight_promotion_jobs parameter should be such that the submitted jobs keep the Tier active between forward passes.  
 3. Model (model forward pass time) - This dictates the frequency with which we call the flush.
 4. Workload (big vs small requests)

For this instance, I believe we may avoid tuning by letting the runtime workload drive the pressure. 

The crux of the issue really is the over-reservation of CPU blocks. Allocating the blocks only when necessary, lets the Engine (Model) / Workload drive the CPU KV cache space required and the Tiers are not artificially throttled. 

Further, there is a FS threadpool batching argument to this (Planned as a followup). On the PR, each FS thread picks up a job. This is sub-optimal. With batching,  where each promotion job is split across multiple threads, we'd only need to allocate CPU KV cache space for a few jobs at a time. This will drive down the CPU space requirements further, tying a Job's CPU KV cache pinning duration to model forward pass time.

I think there are benefits in letting the tiers handle CPU allocation as they see fit and in letting the system drive the requirements naturally. Pre-allocating, is simpler, but I think with that, we will always need to fight the Promotion / Cascade Allocation Failure performance issues. 

I realize the complexity the PR introduces. I am happy to discuss / re-work implementation. Thanks 🙌

```
# base.py

class TransferJob(ABC):
    """Handle to an async transfer whose primary-tier resources are unacquired.

    A job holds no primary-tier claim until get() is called. The executing tier
    calls it exactly once, on whichever thread will perform the transfer.
    """

    job_id: JobId
    req_context: ReqContext

    @abstractmethod
    def get(self) -> tuple[Collection[OffloadKey], np.ndarray] | None:
        """Acquire primary-tier resources and return what to transfer.

        Idempotent. For a promotion this reserves primary chunks; for a cascade
        it pins resident chunks against eviction. Either may yield fewer keys
        than were requested.

        Returns:
            The keys to transfer and their primary chunk ids, or None if
            nothing could be acquired.
        """
```
