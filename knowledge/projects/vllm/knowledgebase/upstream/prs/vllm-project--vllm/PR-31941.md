# LoRA Per Request Loading Pipelining Support

[Upstream PR](https://github.com/vllm-project/vllm/pull/31941) · state: open · merged: False

## Original PR description

## Purpose
Currently LoRA Loading for Per Request needs to first sequentially **load all the LoRA layers** before **beginning Pre-Fill**. This adds significant overhead in TTFT. 
<img width="1522" height="545" alt="Screenshot 2026-01-07 at 6 54 53 PM" src="https://github.com/user-attachments/assets/75932a7d-c8d2-47b2-a121-ab40d5435665" />

However, **Pre-Fill** is a layer by layer process and for large enough input tokens(**> 1000 tokens**) it is **longer than LoRA Loading time**. If we run **LoRA loading and Compute in separate streams(CUDA or otherwise)** we can hid significant part of the LoRA loading  time with **Sync points** in each LoRA layer of the forward pass to make sure the LoRA layer is loaded.

<img width="1313" height="467" alt="Screenshot 2026-01-07 at 6 59 12 PM" src="https://github.com/user-attachments/assets/36cb10d8-cbab-4292-b5f7-c622c8b82ede" />

The above process allows for **E2E TTFT to be nearly ~28% lower**

## Code Review

This pull request introduces a significant performance improvement for LoRA loading by pipelining it with the pre-fill computation. By using separate CUDA streams for LoRA weight loading and the forward pass, and synchronizing with a custom Triton kernel, you've managed to hide a substantial portion of the loading latency, resulting in a commendable ~35% reduction in TTFT. The refactoring of `set_lora` methods to use pre-padded contiguous copies is also a clean and efficient change. I've found a critical issue in the padding logic for `FusedMoEWithLoRA` that needs to be addressed.

This will lead to a shape mismatch if the hidden size and intermediate size are different, which is usually the case. A similar issue exists for `lora_b` where `w3` incorrectly uses the buffer for `w1`.

### Flag initialized to 0 causes deadlock on first forward

**High Severity**

<!-- DESCRIPTION START -->

### Registered-but-not-active adapters never get activated on retry

**Medium Severity**

<!-- DESCRIPTION START -->
In `WorkerLoRAManager.add_adapters`, adapters in `list_adapters()` (registered adapters) are skipped, and only newly-loaded adapter IDs are added to `ids_to_activate`. If loading fails mid-batch, some adapters become registered but not activated. On retry, these adapters are skipped because they're registered, but they're never activated because they're not in `ids_to_activate`. The fix is to include all requested adapter IDs in `ids_to_activate` (as `LRUCacheWorkerLoRAManager` does), not just newly-loaded ones.
<!-- DESCRIPTION END -->
