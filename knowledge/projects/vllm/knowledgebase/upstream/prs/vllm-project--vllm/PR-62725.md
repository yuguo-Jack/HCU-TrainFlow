# [ROCm][Bugfix] Serve gfx942 MLA verify past 4 tokens with a Triton kernel

[Upstream PR](https://github.com/vllm-project/vllm/pull/62725) · state: open · merged: False

## Original PR description

- Route causal verify longer than 4 tokens on CDNA3 (no DCP) to a new Triton verify kernel in `rocm_aiter_mla.py`; shorter verify, decode, prefill, DCP and gfx950 keep their current paths.
- Add `decode_attention_fwd_verify` to `triton_decode_attention.py`: one program reads each KV tile once for a block of a request's (token, head) rows, with a per-row causal limit, int64 page offsets and FP8 dequant. Its variants are compiled before serving, so ngram drafts of any length never JIT mid-request.
- Undo the FP8 V-scale drop of AITER's qlen 2-4 FP8 decode kernel (ROCm/aiter#6732), found by a one-time probe, so a fixed AITER turns the correction off by itself.
- Apply the per-TP head override of `test_mla_backends.py` on ROCm as well (it was XPU only), so ROCm CI tests real per-rank head counts instead of 128 heads at every TP.
- Below page size 8 with bf16, read the block table one tile ahead instead of two: above 2 GiB of KV, Triton's global-load variant of the kernel otherwise spills VGPRs (2.1-3.1x slower at `--block-size 1`).
- Add an op test for the new kernel (bf16 and FP8, pages 1 and 16, ragged, padded and varlen rows).

On MI300X, MTP or ngram with 4 or more draft tokens fails at startup: AITER's persistent bf16 MLA decode only has kernels up to 4 query tokens, and its non-persistent kernels are not a safe fallback. They return wrong results at 32 heads, ignore the causal mask at 64/128 heads, and at 16 heads (what padded ranks such as TP2 of a 16-head model use today) read the wrong KV pages once the cache passes 4 GiB (ROCm/aiter#6733). That last case is silent: DeepSeek-V2-Lite at TP2 with k=7 drops to GSM8K 0.004 once serving fills the cache past 4 GiB, and goes back to 0.605 with this PR. Raising an error instead (as #57642 does) would leave MTP 4+ unusable on MI300 and break the gfx942 DCP verify routes that work today. This fixes item 1 of #55609 and needs no AITER change to be correct.

**Still open on the AITER side (not blocking this PR, but blocking a fully green `test_mla_backends.py` on MI300):**
- ROCm/aiter#6731: the persistent `_ps` decode kernel returns wrong output in about 1 of 1000 calls (a race). ROCm/aiter#6277 (open) brings it to 6 bad calls in 250k but not to zero. In 30 runs of the whole file on this branch it shows up as an occasional `ROCM_AITER_MLA` mismatch on unchanged decode paths.
- ROCm/aiter#6735, fixed by ROCm/aiter#6748 (rounds CK forward attention to nearest): `test_chunked_context_backend_correctness[...glm...]` fails on main and on this branch because CK's FMHA forward truncates bf16; it passes 100/100 seeds with that change.
- ROCm/aiter#6732, ROCm/aiter#6733: the FP8 V-scale and the non-persistent kernel bugs worked around here.

**Results** (MI300X, AITER v0.1.25, DeepSeek-V2-Lite-Chat, `VLLM_ROCM_USE_AITER=1`, ngram drafts; `vllm bench serve`, mean of 2 runs, output tok/s):

The c32 differences without spec decode are within this host's run-to-run noise (the same path runs on both). GSM8K 5-shot (lm_eval, 1319) is 0.647-0.663 for every config on both branches, and the TP2 k=7 0.004 above is the >4 GiB case.

**Against the per-token row-view** (what gfx942 DCP verify uses: one row per draft token through the generic split-KV kernel). MI300X, AITER v0.1.27, DeepSeek-V2-Lite-Chat, ngram k=7, TP1, one server at a time on the same GPU, output tok/s:

Per layer, with both kernels in HIP graphs on identical inputs and a production-size KV pool, row-view is 1.8-4.6x slower as it ships and 1.44x slower on geomean when tuned (0.96-2.4x across 16-128 heads and batch 1-64). The c1 gap over tuned row-view (6-8%) is outside this host's noise; at c32 this PR is ahead in every round run, but by less than the c32 run-to-run spread. TP2 and k=5 show the same ordering, and GSM8K is 0.648-0.668 on every arm.

Tests: `pytest tests/kernels/attention/test_triton_decode_attention.py -k verify` (48 passed; 10/10 runs with the page-size fix), `tests/v1/attention/test_rocm_aiter_mla_mtp_split.py`, and `VLLM_ROCM_USE_AITER=1 pytest tests/v1/attention/test_mla_backends.py` 30 times: every run passes all spec-decode and verify cases (634 passed). The two remaining failures are both AITER-side and listed above: `test_chunked_context_backend_correctness[...auto-glm...]` fails in all 30 runs (max diff 0.031, identical on `TRITON_MLA`, the CK prefill), and 8 of 30 runs have one FP8 `large_decode` (qlen 1, unchanged decode path) `ROCM_AITER_MLA` mismatch of 0.16-0.39 from the persistent-kernel race. On main the 16 `spec_decode_medium` cases fail every run with `cannot get heuristic kernel ... qseqlen:8`.

Where the tolerance comes from: the kernel rounds to bf16 twice, so the bound has two terms.

- P (the softmax weights, in [0, 1]) is rounded to bf16 before the PV dot. That is at most 2^-9 relative per weight, and the weights sum to 1, so the error is at most 2^-9 · max|V|. I budget 2^-8 · max|V| as `atol` to leave room for exp2 and accumulation-order differences against the fp32 reference.
- The output is rounded to bf16 once more, which is at most 2^-9 relative, so `rtol` is 2^-8.
- FP8 compares against the dequantized cache, so the same bound applies with V already scaled (k_scale 3).

Measured over 30 seeds of all 48 cases (2880 comparisons): the worst case uses 48% of the bound for bf16 (max abs error 0.0078) and 52% for FP8 (0.0235). The old `atol=3e-2, rtol=2e-2` was 4-9x looser than anything measured. The new bound is not too tight either: with `rtol=0`, the worst error is 0.89 · 2^-8 · max|V|, so halving `atol` would start failing. Every bug I injected fails by a wide margin: dropping the V scale (170x the bound), a causal off-by-one (394x), the wrong exp base (30x), and P rounded to FP8 (4.8x). 30/30 seeded runs of the test pass.

The check asks for both sides (close to the unscaled reference and far from the scaled one), so any other failure, such as NaN or garbage, returns False and leaves the output alone. > The P-rounding half of this bound is right, but the fp8 path has a larger error source that isn't in it: the kernel rounds the dequantized K to bf16 before the QK dot (k = (k.to(f32) * ks).to(q.dtype)) while _verify_reference stays in fp32.
