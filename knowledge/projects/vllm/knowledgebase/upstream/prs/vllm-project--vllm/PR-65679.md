# [Bugfix] Require fastokens >= 0.3.5 for VLLM_USE_FASTOKENS

[Upstream PR](https://github.com/vllm-project/vllm/pull/65679) · state: open · merged: False

## Original PR description



## Overview

Raises the minimum `fastokens` version for `VLLM_USE_FASTOKENS=1` from 0.2.0 to 0.3.5, in `vllm/tokenizers/fastokens.py`, the `VLLM_USE_FASTOKENS` comment in `vllm/envs.py`, the docs and the Nemotron 3.5 Lightning recipe. This is the Python-frontend part of #63467; #63707 already moved the Rust frontend to 0.3.5.

## Claims

- With `VLLM_USE_FASTOKENS=1`, vLLM now refuses a fastokens release older than 0.3.5 when it loads the tokenizer, with an `ImportError` that names 0.3.5.
- This is a hard error at startup for anyone who installed fastokens 0.2.0 to 0.3.4 themselves and sets `VLLM_USE_FASTOKENS=1`: the wheels and the Docker image don't bundle fastokens, so the fix for them is `pip install -U "fastokens>=0.3.5"`. A warning would let the wrong ids through without a sign, since they decode to the same text.
- The releases it now refuses have two bugs:
  - Before 0.3.4, a text that shares a prefix of 4 KB or more with the text the same thread encoded just before it can get different token ids than Hugging Face, which decode to the same text (#63467; fixed in 0.3.4 by crusoecloud/fastokens#78).
  - 0.3.3 and 0.3.4 can deadlock in `encode_batch` while another thread changes the tokenizer's padding or truncation (crusoecloud/fastokens#84, fixed in 0.3.5 by crusoecloud/fastokens#85).

## Validation

- `pytest tests/tokenizers_/test_fastokens.py`: 4 passed. The new test checks that the guard rejects 0.2.0 and 0.3.4 with a message naming 0.3.5 and the installed version, that `get_tokenizer` itself refuses 0.3.4, and that 0.3.5 is applied; on main the three rejection cases fail.
- vLLM's `get_tokenizer("Qwen/Qwen3-8B")` with `VLLM_USE_FASTOKENS=1` and the new floor: with fastokens 0.3.4 it raises `ImportError: fastokens >= 0.3.5 is required when VLLM_USE_FASTOKENS=1 (found 0.3.4).`, and with 0.3.5 it loads.
- The spaces pair from #63467 through vLLM's tokenizer loader (5,000 spaces then `x`, then 5,000 spaces then a newline, counted on the second text):

  | Tokenizer | Ids for the second text |
  | --- | --- |
  | fastokens 0.2.0, the current minimum | 41 |
  | fastokens 0.3.4 | 40 |
  | fastokens 0.3.5 | 40 |
  | Hugging Face (`transformers` 5.19.0, `tokenizers` 0.23.3) | 40 |

- fastokens' own `python/tests/test_batch_thread_safety.py` from the 0.3.5 sdist: all 8 concurrent encode-while-changing-settings cases hang on 0.3.4 (the test's 15 s watchdog fires in each) and pass on 0.3.5.
- `pre-commit` on the changed files passes.

The two tokenizer-loader checks ran on vLLM `153a17166e`, whose `vllm/tokenizers/fastokens.py` matches this branch apart from the floor. I compared ids only with Qwen3-8B's tokenizer, on the pair above. 0.3.4 and later also apply a `tokenizer.json`'s truncation and padding blocks on encode and load some tokenizers 0.2.x rejected (#63707 has the Rust-side details); I haven't compared those cases through the Python frontend.

## Details

- 0.3.5 is on [PyPI](https://pypi.org/project/fastokens/0.3.5/). The fastokens repository has no tag or release for it, so PyPI is the reference for that version.
- #84 shows the deadlock is reachable through transformers: `PreTrainedTokenizerFast` changes padding before each batch encode, so one thread encoding plain text while another tokenizes with `padding=True` is enough. It was reported from SGLang; I haven't reproduced it through vLLM.
- Open #47863 adds `fastokens>=0.2.0` to `docker/Dockerfile` and the `setup.py` extras. Those entries are not on main, so this PR cannot change them; #47863 would need `>=0.3.5` there as well.
- I checked the open PRs that mention fastokens; none changes the Python floor.
- The new test runs in the CPU Multimodal + Config job, which already covers `vllm/tokenizers/` and `tests/tokenizers_`.
