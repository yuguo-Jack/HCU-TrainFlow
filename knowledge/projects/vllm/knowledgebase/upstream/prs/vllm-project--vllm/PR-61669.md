# [Bugfix][Model] DiffusionGemma: stop sampler recompiles during serving

[Upstream PR](https://github.com/vllm-project/vllm/pull/61669) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

DiffusionGemma's sampler ran its post-sample step, softcap and two small helpers through `@torch.compile(dynamic=True)` outside vLLM's compile pipeline. No startup path compiled them, so each new request shape compiled during serving and stalled every request on the replica. Following review, this revision drops `torch.compile` from the sampler. The step and softcap become Triton kernels that register their warmup inputs with vLLM's JIT warmup registry, so every variant serving reaches compiles at startup.

## Claims

- **No first-request stalls.** On current `main`, the first narrow-canvas, single-step and constrained requests stall 6–9 s while graphs compile. With this PR none of them do, and none of the sampler's kernels compile during serving. That holds at concurrency 128, where tiles exceed 2 GiB.
- **Faster startup:** 172 s vs 212 s (TP=1, cold caches).
- **Same steady-state speed and accuracy.** Request latency, time per denoising step, throughput and GSM8K all match `main` within noise (tables below).
- **Small footprint:** the diff only touches the DiffusionGemma model, its sampler kernels and their test. The previous revision's `ModelState.warmup_compiled()` hook, the `kernel_warmup` call and the sampler warmup are gone.

## Validation

All runs use 8× MI350X, ROCm 7.0.2, torch 2.14.0+rocm7.2 and transformers 5.19.0, with vLLM built from source at upstream `main` (`db7f2d7c44`) and at this PR rebased on it. They serve `RedHatAI/diffusiongemma-26B-A4B-it-FP8-dynamic` with `--attention-backend TRITON_ATTN`.

**Serving** ran in vLLM's default mode (torch.compile, CUDA graphs and JIT warmup on) with cold caches, `--jit-monitor-mode warn --jit-monitor-verbose`, and TP=1 so that constrained reads are allowed.

| TP=1 | `main` | This PR |
|---|---|---|
| Startup to healthy | 212 s | 172 s |
| First narrow-canvas request (width 4) | 9.25 s | 1.28 s (= steady) |
| First single-step read (width 1) | 5.88 s | 0.02 s |
| First constrained read, K=1 / 7 / 16, 3 steps | 6.04 / 1.23 / 0.28 s | 0.02 / 0.03 / 0.03 s |
| Sampler kernels compiled during serving | 10 (`_row_stats_kernel`) | 0 |
| `vllm bench serve` (random 512 in / 256 out, 1024 prompts, concurrency 128) | 2437 tok/s, 0 failed | 2425 tok/s, 0 failed |

Both builds also compile `fused_moe_kernel` during serving. That comes from the MoE layers and is unrelated to this PR. These runs used `VLLM_GPU_SYNC_CHECK=warn`, because a pre-existing synchronous copy in `DiffusionGemmaRequestStates.allowed_tensor` trips `error` mode on constrained reads in both builds. This PR also passes a TP=2 run under `VLLM_GPU_SYNC_CHECK=error` (no constrained reads): 256/256 requests, 0 sampler compiles during serving, 0 errors.

**Steady state:** 60 sequential requests per build. Steps come from `vllm:diffusion_num_denoising_steps`.

| TP=1, steady | `main` | This PR |
|---|---|---|

| Full canvas: median latency / time per denoising step | 72.9 ms / 14.50 ms | 72.3 ms / 14.53 ms |

Narrow-canvas latency is dominated by how many denoising steps a request takes, which varies with sampling: `main`'s own median ranged from 1142 to 1317 ms across runs. Time per step is the stable comparison.

**GSM8K** uses the repo's CI config `tests/evals/gsm8k/configs/DiffusionGemma-26B-A4B-it-FP8-dynamic.yaml` (TP=2, 1319 questions, 5-shot, threshold 0.84). It samples at temperature 1.0 with no seed, so each build ran twice.

**Tests:** `pytest tests/v1/sample/test_diffusion_gemma_reads.py tests/v1/sample/test_diffusion_sampler_stats.py tests/v1/worker/test_gpu_diffusion_sampler.py` passes all 41 tests.
- `test_sample_step_kernel_matches_reference` checks the kernel against the PyTorch reference with exact equality on every state tensor. It uses one request per outcome (converge, read-only emit, stable but uncertain, unstable, commit, step cap), across widths {CL, 3, 1} and stability thresholds {1, 3}, with tied and NaN entropies.
- `test_jit_warmup_covers_every_serving_variant` runs the registered warmup, then a battery of serving shapes, and asserts that no kernel compiles a new variant.
- `test_single_step_decode_does_not_sync` runs the single-step decode path under `torch.cuda.set_sync_debug_mode("error")`.
- `test_softcap_kernel_matches_reference` checks the softcap kernel against the plain formula.

I also broke the code deliberately 17 ways: pins, read-only handling, tie order, cumsum, ring slot, stability, keep mask, converged argmax, valid length, mean width, missing warmup classes and dtypes, and NaN ordering. Every break failed the tests. Separately, on ROCm, launching the kernels with 2–4 GiB tensors after warmup compiled no new variants.

## Details

- **`sample_step`** is a Triton kernel with one program per decode request. It covers confidence, entropy-bound accept/renoise, the history ring and stability check, convergence and emit. The entropy sort uses packed (order-preserving entropy bits, position) int64 keys, the same trick as `gemma4.py`'s routing kernel, so ties break by position and NaN sorts last, as in `torch.sort`. `BLOCK` comes from the full canvas length and `W` is not specialized, so every tile width shares one compiled kernel. The launcher asserts the layout it relies on.
- **`sample_step_reference`** keeps the PyTorch form for tests and non-CUDA runs, mirroring `sample_row_stats_reference`.
- **Self-conditioning** (matmul, TP all-reduce, masked store) stays in PyTorch in `_store_self_conditioning`. The single-step path zeroes with `index_fill_`, which avoids a GPU→CPU sync.
- **JIT warmup:** `sample_row_stats`, `sample_step` and `softcap_logits` use `triton_kernel_dispatcher_with_warmup`, and `DiffusionGemmaForConditionalGeneration.__init__` registers them while the runner's registry is active. Their warmup inputs cover:
  - the full vocabulary and the constrained allowed-set size classes (1, divisible by 16, other);
  - on ROCm, tiles whose logits, probabilities or softcap output exceed 2 GiB. With the tiled logits projection from #51953 a tile can reach that size, and Triton specializes pointers on whether their storage fits 32-bit offsets. These cases are added only when `max_num_seqs × canvas_length` rows can reach them.

  Warmup builds output buffers as metadata only, so it allocates nothing. Nothing outside DiffusionGemma changes.
- **`softcap_logits`** is one Triton pass with no vocab or stride specialization. `_compute_num_rejected` and `_denoise_temperature` run eager; they are a few ops on `[num_reqs]` tensors.
- **`_row_stats_kernel`** no longer specializes on its seed or the canvas width. Its vocab and stride specialization stays, because removing it costs 7–9% on the full-vocab path; warmup covers those variants instead.
- **Behaviour changes:**
  - Renoise tokens come from `torch.randint` before the kernel rather than Inductor's RNG, so outputs are not bit-identical to before.
  - Entropy ties now break by position.
- **Limitations:** validated on ROCm only. CUDA is covered by the unit tests and the GSM8K config in CI.
- **Pre-existing issues found while testing, not addressed here:**
  - A `diffusion_constrained` request on a TP>1 server raises in the worker and kills the engine instead of being rejected at admission.
  - `allowed_tensor` performs a synchronous host-to-device copy on the step path.
