# [Bugfix][Spec Decode] DFlash2: map reduced-vocabulary candidates to target ids

[Upstream PR](https://github.com/vllm-project/vllm/pull/60365) · state: open · merged: False

## Original PR description

## Overview

DFlash2 drafters with a reduced draft vocabulary (`draft_vocab_size` smaller than `vocab_size`, with a `d2t` table) propose the wrong tokens. `compute_candidates` returns the top-k row numbers of the reduced head, and the speculator uses them as target token ids. It writes them into the draft tokens and looks up the selector codebooks with them.

Only rows where `d2t` is non-zero come out wrong. Pruned vocabularies usually keep the most frequent (lowest) ids, so `d2t` is the identity over a prefix and it's the rarer tokens past that prefix that break. You get lower acceptance rather than garbage drafts, and if the vocabulary happens to be a pure prefix of the id space you don't see it at all. That's how I missed it the first time I tested.

This hits any reduced-vocab DFlash2 drafter on any model or backend. The fix is in model code and nothing in it is ROCm specific.

## Claims

- Candidates from a reduced-vocab DFlash2 drafter go through `draft_id_to_target_id` before they reach the candidate selector, with the same `target = row + d2t[row]` mapping `compute_logits` already uses.
- Drafters with the full vocabulary (no `d2t`) are unchanged.
- No new host sync. The mapping is a gather on tensors that are already on the device.

## Validation

I added a test to `tests/v1/spec_decode/test_dflash2.py`, which already runs in the CPU and the GPU spec decode CI steps. It fails on main for the reduced-vocab case and passes with the fix:

```
pytest tests/v1/spec_decode/test_dflash2.py
# CUDA (RTX A2000 Laptop, sm_86), torch 2.13.0+cu132:
#   main:        test_compute_candidates_returns_target_ids[True] FAILED (1 failed, 22 passed)
#   this branch: 23 passed
# CPU only: 13 passed, 10 skipped (the skipped ones need CUDA)
```

`pre-commit run` passes on the changed files.

I also ran an end-to-end acceptance A/B with stock checkpoints: target `RedHatAI/Qwen3.8-27B-INT4`, drafter `z-lab/Qwen3.8-27B-DFlash2`, vLLM v0.31.1rc0 built for ROCm, one Radeon AI PRO R9700 (gfx1201). My only NVIDIA card is an 8 GB laptop GPU, so I couldn't repeat this part on CUDA. Settings were `num_speculative_tokens=4`, eager, prefix caching off, c=1, 8 prompts (6 code, 2 prose), greedy, 256 tokens each, thinking off. Acceptance comes from the engine's `vllm:spec_decode_*` counters.

For the pruned drafter I cut the z-lab drafter down to 32,768 rows (head rows copied from the target's `lm_head`, `d2t` = kept id minus row). I picked the vocabulary by token frequency over the CPython 3.12 stdlib source so anyone can rebuild it. Its `d2t` is the identity for rows 0 to 12,637 and non-zero for 20,130 of the 32,768 rows.

| drafter | code | mean acceptance length | draft acceptance | per position (0 / 1 / 2 / 3) |
|---|---|---|---|---|
| full | main | 3.693 | 67.3 % | .880 / .738 / .596 / .479 |
| full | this PR | 3.672 | 66.8 % | .866 / .724 / .600 / .482 |
| pruned 32k | main | 2.916 | 47.9 % | .720 / .524 / .395 / .277 |
| pruned 32k | this PR | 3.449 | 61.2 % | .827 / .669 / .538 / .415 |

- With the fix the pruned drafter's mean acceptance length goes from 2.916 to 3.449 (+18.3 %). The gap that's left to the full drafter comes from the smaller vocabulary itself.
- With the full drafter, main and this branch give bit-identical output when I run them back to back in one session (558 drafts, 1,491 accepted, same text). The 3.693 vs 3.672 in the table is boot-to-boot variation on main, which lands on one of those two results each time the engine starts.
- The same drafter pruned to a pure prefix (ids 0 to 32,734 plus the 33 special/EOS ids, so only 33 rows with a non-zero `d2t`) shows no cost from the bug on main. So a quick test with that kind of vocabulary looks fine.

## Details

`DFlashQwen3ForCausalLM` already sizes `lm_head` to `draft_vocab_size`, loads `d2t` and maps through it in `compute_logits`. DFlash2's `compute_candidates` skips that step, but the selector codebooks, the proposal cache and the verifier all index the target vocabulary.

I went through the other drafters on main that allow a reduced vocab. Eagle3 (llama, qwen3, deepseek), DFlash and DSpark all map draft ids, and LiLiCorr refuses a reduced vocab, so DFlash2 looks like the only one missing it. This is MRV2 only, since that's the only place the DFlash2 speculator exists.

Related PRs I checked, none of them a duplicate:

- #59740 moves the `d2t` handling of Eagle3, DFlash and DSpark into a shared `DraftVocab` but leaves DFlash2's `compute_candidates` alone. It keeps `draft_id_to_target_id` on the model, so this applies on top of it as is. If it lands first I'm happy to switch this to `self.draft_vocab.map_draft_to_target(ids)`.
- #52883 also edits `compute_candidates` (unquantized heads in the selector) without touching the mapping, so whichever lands second just needs to keep these lines.
- #55961 packs the top-k all-gather and doesn't change the mapping.
