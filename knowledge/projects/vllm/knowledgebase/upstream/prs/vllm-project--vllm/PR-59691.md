# [CI] Build the torch-nightly lane against CUDA 13.2

[Upstream PR](https://github.com/vllm-project/vllm/pull/59691) · state: closed · merged: False

## Original PR description

## Purpose

Make the `TORCH_NIGHTLY=1` lane build against **CUDA 13.2** instead of 13.0. Nothing outside that lane changes.

CUDA 13.0 was removed from PyTorch's binary build matrix on 2026-09-28
([pytorch/pytorch#198913](https://github.com/pytorch/pytorch/pull/198913), announced on
[dev-discuss](https://dev-discuss.pytorch.org/t/removing-cuda-13-0-builds-from-pytorch-ci-cd-starting-the-week-of-sept-28/3447)).
The `cu130` **nightly** index has published nothing since, so this lane has been re-testing a
frozen wheel for three days:

```
whl/nightly/cu130/torch/   last: 2.15.0.dev20260928
whl/nightly/cu132/torch/   dev20260928, dev20260929, dev20260930, dev20261001
```

Concretely, [build 92398](https://buildkite.com/vllm/ci/builds/92398) (Oct 1) still installed
`torch==2.15.0.dev20260928+cu130`, so fixes that landed upstream after Sep 28 cannot reach CI —
including [pytorch/pytorch#198865](https://github.com/pytorch/pytorch/pull/198865), which restores
`ProcessGroupNCCL._comm_ptr` and should clear the `(B200) Distributed` and `(B200) FusedMoE Layer
Kernels` failures.

## Changes

All four are gated on the nightly lane:

- `image_build_torch_nightly.sh` — `NIGHTLY_CUDA_VERSION` `13.0.2` → `13.2.1`, builder image →
  `manylinux2_28-builder:cuda13.2`. This script only ever runs for the nightly lane.
- `image_build_arm64.sh` — the builder image becomes a variable, overridden to the cuda13.2 build
  **only under `TORCH_NIGHTLY=1`**, and `CUDA_VERSION=13.2.1` is passed explicitly. Without the
  latter the lane inherits `ARG CUDA_VERSION=13.0.3` from `docker/Dockerfile` and keeps resolving
  `cu130`. Regular arm64 CI is untouched.
- `check-ray-compatibility.sh` — the `TORCH_NIGHTLY=1` branch moves to `nightly/cu132`. The release
  branch stays on `cu130`.
- `image_build.sh` — comment only; it documents the dispatch as "CUDA 13.0".
- `tests/standalone_tests/pytorch_nightly_dependency.sh` — `cu128` → `cu132`. This test installs a nightly torch and asserts that `requirements/test/nightly-torch.txt` does not downgrade it, but `whl/nightly/cu128` has published nothing since `2.15.0.dev20260408`, so it was asserting against a six-month-old wheel. CUDA 12.8 is long gone from PyTorch's matrix.

### Why the builder tag is unpinned

Both nightly builder references track the floating `cuda13.2` tag rather than a commit-pinned
`cuda13.2-<sha>`. This lane exists to test against a moving upstream, so tracking the current
toolchain is in character — and a commit pin is precisely what let the old `cuda13.0-78e737ad…`
reference outlive the CUDA version it named, with nothing to flag it.

Pinning on `main` is not uniform today, so this is not a new precedent:

| Reference | Form |
| --- | --- |
| `release-pipeline.yaml` cuda13.4 (x86 + aarch64) | floating |
| `docker/Dockerfile` (one of two refs) | floating |
| `release-pipeline.yaml` cuda12.9 / cuda13.0, `run-gh200-test.sh`, `versions.json` | pinned |

The non-nightly arm64 pin in `image_build_arm64.sh` is deliberately left pinned; only the
`TORCH_NIGHTLY=1` override floats. If you would rather the nightly lane stay pinned, it is a
two-line change back — the tradeoff is reproducing a specific nightly failure versus this
class of silent staleness.

### Why 13.2.1 and not PyTorch's 13.2.2

`docker/Dockerfile` derives the wheel index from major.minor only (`13.2` → `cu132`), but
`FINAL_BASE_IMAGE` resolves to `nvidia/cuda:${CUDA_VERSION}-base-ubuntu24.04`, and no
`13.2.2-base-ubuntu24.04` tag is published (404). `13.2.1` exists and yields the same index.

## Other index locations audited

Searched for every place the lane can pick a torch index (`TORCH_INDEX_URL`,
`PYTORCH_CUDA_INDEX_BASE_URL`, `--torch-backend`, `download.pytorch.org`), to be sure one
`CUDA_VERSION` change is actually sufficient:

| Location | Status |
| --- | --- |
| `check-ray-compatibility.sh` — only `TORCH_INDEX_URL` in the repo | changed here (nightly branch only) |
| `docker/Dockerfile` — `PYTORCH_CUDA_INDEX_BASE_URL` | derives from `CUDA_VERSION`; no change needed |
| `requirements/test/cuda.txt` — commits `+cu130` pins | **recompiled at image-build time** under `PYTORCH_NIGHTLY=1` against the derived index; no change needed |
| `requirements/test/nightly-torch.txt` | carries no index directives |
| `image_build.sh` | `exec`s the nightly script; comment corrected here |
| `tests/standalone_tests/pytorch_nightly_dependency.sh` | hardcoded a *different*, stale index (`cu128`, last publish `dev20260408`) — changed here |
| `.buildkite/test_areas/quantization.yaml` | hardcodes `torchao==0.17.0 --index-url .../whl/cu130`. **Deliberately not changed**: it is not gated on `TORCH_NIGHTLY`, so it affects the default lane too, and `--index-url` replaces rather than extends the index. Belongs with #55387. |

The last row is the one known inconsistency this PR introduces: a cu132 image installing torchao
from a cu130 index. It is pinned to an exact version and the L4 quantization shards pass today, so
it should be inert, but it is worth a reviewer's eye.

## Relationship to #55387

[#55387](https://github.com/vllm-project/vllm/pull/55387) moves the **default** build to 13.2 across
15 files and is the better end state, but it is currently conflicted and its requirements
regeneration predates the 2.14 pin. This is deliberately the narrow subset — nightly lane only — so
it can land now and unfreeze that lane. It should be dropped in favour of #55387 once that lands;
the overlapping hunks are compatible in intent.

| `nvidia/cuda:13.2.2-base-ubuntu24.04` | **404** — hence 13.2.1 |
| `whl/nightly/cu132` publishing daily | yes, through dev20261001 |

## Test plan

`bash -n` / `sh -n` pass on all five scripts. The lane is exercised by the next `Full CI run torch nightly`:
the image build should log `Building torch nightly image (CUDA 13.2.1)` and the installed wheel
should be `2.15.0.dev2026100x+cu132` rather than `dev20260928+cu130`.

The nightly-dependency test should additionally install a current `dev2026100x+cu132` wheel instead of `dev20260408+cu128`.
