# [Feature][Core] Add opt-in multi-worker CUDA checkpoint sleep

[Upstream PR](https://github.com/vllm-project/vllm/pull/64186) · state: closed · merged: True

## Original PR description

## Overview

Add a default-off `CUDACheckpointExecutor` that checkpoints CUDA workers after level-1 sleep and restores their original CUDA state before waking allocator tags. This follows the six-file feature split in https://github.com/aoshen02/vllm/pull/186, extracted from #58183.

This PR now contains only the six-file CUDA checkpoint feature, against main `b71c1d5f14e593b6c5af9a689c6f6afead33f7e1`, following @aoshen02's request to review this part first. #64183, #64184 and #64185 remain separate follow-ups; their client cleanup, resume guard and general control-ordering changes are not included in the final diff or required to land first. The earlier stacked commits and maintainer main merge remain in history; a follow-up commit removes the prerequisites from the final diff.

The experimental documentation states the supported serial call sequence directly: fully wake all tags before explicitly resuming, and restart after checkpoint failure. Without #64183, an EngineCore exit can leave a management call waiting even after workers terminate; callers need an external timeout. This PR does not claim to fix that separate client failure-notification issue.

## Claims

- Preserve captured graph executables across worker checkpoint/restore, without recapture.
- Run driver operations concurrently within each stage, with all-rank stage barriers and failure/timeout cleanup.
- Keep the feature opt-in and preserve documented driver, communication and configuration restrictions.

### Historical GPU and model validation carried over from #58183

These are measurements of the original combined PR at the revisions stated below, **not reruns of this split**. They supplement the checkpoint-only validation above. The historical suite had more parametrized cases and an alias test; its 129-pass count is not the current suite count.

The historical measurements below correspond to `c9171d7ad9eedd77d7633d5cdb0355018ff9b29a`, based on `9514aef85`. Four H20 GPUs, driver 580.126.09, PyTorch 2.14.0/CUDA 13, NCCL 2.30.7, FlashInfer 0.7.2, V2 model runner. The tested Python sources matched the files published at that original revision. Existing native components were used; this is not a clean rebuild of all optional extensions or a substitute for upstream CI.

- Helper/executor unit tests: **129 passed**. Coverage includes complete stage responses, arbitrary rank counts, failure/timeout cleanup, configuration rejection and old/new executor names in that revision (the never-upstreamed alias is omitted from this split).
- Opt-in GPU regression: **5 passed** — TP1/2/4 peer-to-peer and TP2/4 forced shared memory, three cycles each with Qwen3-0.6B and batch invariance. Checks cover exact output, both partial-wake orders, repeated sleep, original worker/graph identities, increased **post-wake** replay counts and zero new captures. `/dev/shm` entries were unchanged after the suite.
- Qwen3.8-27B BF16: TP2 peer-to-peer and TP4 shared memory each completed **20 cycles**, preserving original graphs and actually replaying them after wake. All four diagnostic prompts matched their immediately preceding outputs in 13/20 and 16/20 cycles respectively. TP4 ordinary sleep also matched in 16/20, but in different cycles; equal counts do not establish equal causes or exclude restoration-induced perturbation.
- Real TP2 restore OOM: one rank restored while the other failed under external GPU memory pressure; the call failed and both workers were reaped. A helper test combines a failed rank with a blocked peer and verifies bounded helper termination.

Qwen3.8-27B BF16, TP2, forced shared-memory transport; fixed first 128 GSM8K questions, five examples per question, at most 512 output tokens:

| Execution path | Before sleep | Repeat without sleep | After sleep |
|---|---:|---:|---:|
| Ordinary sleep | 124/128 | 124/128 | 124/128 |
| CUDA checkpoint | 124/128 | 125/128 | 124/128 |
| Corresponding full token sequences equal across paths | 128/128 | 113/128 | 128/128 |

This is a paired 128-question subset, not the full benchmark or a general determinism guarantee. Batch invariance is unsupported for this model's gated delta network attention.

A matched TP4 timing sample used Qwen3.8-27B BF16, forced legacy shared memory, four prompts × 64 output tokens, and a fixed 4 GB KV cache per GPU (1 GB = 2^30 bytes). Only the driver helper differed (serial versus concurrent stages). Both summaries use the first five cycles; steady values are medians and observed ranges from cycles 2–5, in seconds.

| Driver helper | First sleep / wake | Steady sleep (range) | Steady wake (range) |
|---|---:|---:|---:|
| Serial | 9.601 / 4.127 | 3.396 (3.359–3.440) | 4.173 (4.110–4.298) |
| Concurrent stages | 8.282 / 1.952 | 2.132 (2.117–2.148) | 1.960 (1.948–2.063) |

These are end-to-end sleep and complete wake-sequence latencies; each wake sequence uses either one full wake call or both partial-tag calls, with the same order in both runs. They are not a breakdown of driver Restore or allocator operations. The sample supports a reduction in this configuration's wake latency; it does not establish TP8 scaling, statistical significance or unchanged inference performance. No internal time-attribution claim is made.

### Earlier capacity measurement

At `a2472393067b4e04e83cdb7bc3f93aa52c8a67fa`, Qwen3.8-27B BF16 TP2 allowed a separate process to allocate and write **1.3203125 GB more per GPU** after checkpoint than after ordinary sleep (two cycles on both devices; 1 GB = 2^30 bytes). This measures whole-process additional physical capacity, not exclusively graph-executable memory. This capacity measurement was not rerun for this split.

Source: [#58183 validation](https://github.com/vllm-project/vllm/pull/58183). The extended model, capacity, timing and failure measurements used local harnesses rather than additional committed CI tests.

## Details

The feature commit contains only the helper, executor, their tests, GPU integration test and experimental documentation. Following the maintainer split, it removes the never-upstreamed `ProcessCheckpointExecutor` alias, names the executor test `test_cuda_checkpoint_executor.py`, and adds no functional change to `EngineCore.sleep()`.

Related to #48311's performance work. #62570 provides an external-orchestrator lifecycle; this executor calls the CUDA driver directly and does not add CRIU/container migration or another public checkpoint API. #56373 is another overlapping offload integration to coordinate with maintainers.

Tradeoff: lower sleeping GPU residency requires host memory and extra sleep/wake latency. NVLS and other documented unsupported resources remain restricted. TP8 and full native-extension rebuilding are not established by this split.
