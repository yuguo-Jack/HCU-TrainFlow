# [Kernel] ReplaySSM: cache SSM inputs instead of state for faster standard and speculative decode (Mamba2 + GDN)

[Upstream PR](https://github.com/vllm-project/vllm/pull/47576) · state: closed · merged: False

## Original PR description

## Background
- **RFC:** [vllm-project/vllm#47572](https://github.com/vllm-project/vllm/issues/47572).
- **Project:** ReplaySSM, caching recent SSM inputs instead of writing the recurrent state back to HBM every step.
- **Collaboration:** [Dao AI Lab](https://dao-lab.ai) × NVIDIA.
 - **Blog (full derivation + figures):** [ReplaySSM](https://dao-lab.ai/blog/2026/replayssm/)
- **Fork / branch:** [`Johnny-Liou/ReplaySSM`](https://github.com/Johnny-Liou/ReplaySSM)
- **Concurrent cross-framework work:** [TensorRT-LLM PR](https://github.com/NVIDIA/TensorRT-LLM/pull/14203)
- **AI assistance:** AI assistance was used for parts of this work. The human authors have reviewed the kernel design and most of the code; since this is a draft PR, we will finish reviewing every changed line and run the tests before marking it ready.

## Core concept
- SSM decode is memory-bound: each step loads and stores a `(nheads, d, n)` recurrent state; the state store dominates traffic.
- ReplaySSM keeps a small ring buffer of recent inputs and a periodic checkpoint state; it reconstructs the state (or reads the output directly) from the checkpoint + buffer, and writes the full state back only on periodic flushes.
- Three benefits from one change:
  - **Less memory traffic:** halves the dominant state traffic in standard decode (state store replaced by a small input append most steps).
  - **Cheap rollback:** vLLM's current spec path stores a per-draft state snapshot to undo rejected tokens; ReplaySSM makes rollback a ring-buffer pointer move, so no per-step state snapshots are kept or restored.
  - **Parallel verification:** most steps only need the output, not the state: the output-only form computes all `T` draft outputs from one checkpoint + buffer in a single GEMM (removing the length-`T` serial recurrence), and materializes the full state only at a flush.
- **Additional benefit (numerical precision):** reconstruction runs in FP32 and the state is written back only on flushes, so storing the checkpoint in low precision (e.g. FP16) re-quantizes it at most ~`L`× less often than the baseline, which re-quantizes on every per-step state store to HBM. Reference: [NVIDIA Nemotron-3-Ultra Technical Report](https://research.nvidia.com/labs/nemotron/files/NVIDIA-Nemotron-3-Ultra-Technical-Report.pdf), Section 4.5.
- **Regime (hybrid models):** the win is largest at short-to-medium output lengths (where the SSM layers dominate the step) and at large batch size (at small batch the MLP layers dominate). ReplaySSM shows largest kernel-level speedup at large batch size, where the SSM kernel is purely memory-bound.

## Design notes (the non-obvious parts)
- **What the baseline stores (for contrast):**
  - Standard decode: the baseline advances the recurrent state and writes the full `(nheads, d, n)` state back to HBM every step.
  - Speculative decode: vLLM stores a separate state snapshot for every draft token (to enable rollback of rejected tokens); even the improved prior works still advance the state and write at least one full state back to HBM per step.
- **What ReplaySSM caches instead (per step):** a small input append, no state store.
  - Mamba2: the per-step SSM inputs `(v, Δ, k)` (i.e. `x`, `dt`, `B`).
  - GDN: `(u, k, g)`, where `u = β(v - Sk)` is the corrected update vector (cached instead of `v`) because it depends on the state; caching the already-corrected `u` keeps replay free of the serial dependency.
- **What ReplaySSM keeps in HBM (the state):**
  - A single checkpoint state `S₀`, loaded every step and written back only on flushes (see below), replacing the baseline's per-step state store.
  - Conv state reuses vLLM's `causal_conv1d_update` unchanged; in spec decode the window is `conv_kernel-1+num_spec` and rollback is a shift keyed on `num_accepted_tokens`. ReplaySSM never touches the conv path.
- **When we flush (write the checkpoint):** `B` (`--replayssm-buffer-len`, default 16) is the maximum number of history tokens (past SSM inputs) the buffer holds. A flush reconstructs the recurrent state from the cached history tokens and writes it back as the new checkpoint `S₀` in HBM; the history window then restarts.
  - Standard: each step appends one input to the size-`B` buffer, so we flush every `B` steps.
  - Speculative: a verify step consumes a window of `T = num_spec_tokens + 1` tokens at once, so we flush whenever `history_tokens + T > B` (the next window would not fit). This guarantees every verify step has room for a full `T`-draft window, preventing window collapse / truncation.
- **Ring-buffer sizing (spec):** the ring holds `L = B + T` slots. A flush step carries at most `B` history tokens (from the flush rule above) and appends the current window of up to `T`, so `L = B + T` always has room for a full `T`-draft window on top of the history, so the window never collapses or truncates.
  - **Physical size:** we currently round the logical size up to `next_pow2(L)` so wraparound indexing is a cheap bit-mask (`& (N-1)`) instead of a `% L`. Sizing the ring to exactly `L = B + T` (dropping the pow2 slack to save cache memory) is future work.
- **Why a ring buffer (spec):** the number of accepted tokens is only known after the whole step, so rejected drafts must be discarded cheaply. Rather than relocate accepted tokens to the front of the buffer every layer/step, the kernel indexes the cache circularly and moves cursors instead of data.
  - **Circular indexing (in-kernel):** every cache access maps to physical slot `(post_origin + write_pos + offs) & (buf - 1)`, driven by two block-keyed cursors: `post_origin` (the window's circular base) and `write_pos` (committed-history offset).
  - **Commit / rollback (device-side, no data movement):** a normal step does `write_pos += num_accepted` (rejected drafts are never committed, which is the rollback); a flush advances `post_origin` past the committed history and resets `write_pos`.
- **Full decode step (end-to-end integration):**
  - Standard: `write_pos` is just `decode_step mod B`, derived on the host each build from scheduler token counts (a deterministic +1 per step) and pushed to the kernel with a small async host→device copy. Because it needs no GPU result, there is no device→host sync. The main decode kernel then appends the input at `write_pos` and flushes when `write_pos == B-1` (every `B` steps). No device cursor kernel is needed, unlike spec, where variable acceptance (`num_accepted` is a GPU value) would otherwise force a per-step device→host sync, so the cursor is advanced on-device instead.
  - Speculative: one device kernel at metadata-build time (`commit_replayssm_spec`) does two jobs at once: it commits the previous step's accepted tokens (`write_pos += num_accepted`, or advances `post_origin` on a flush) and decides `is_flush` for the current step (the `history + T > B` rule above). The forward then runs conv (`causal_conv1d_update`) → scatter the fresh spec tokens into the ring → verify + flush launches gated by `is_flush` (see the CUDA-graph note below).
  - The commit targets the previous step because a step's acceptance is only known after its forward + sampling; folding it into the next build (rather than a separate post-forward launch) keeps every cursor update on-device.
- **CUDA-graph + continuous batching:**
  - The constraint: a captured graph is a fixed sequence of kernel launches, so any per-step decision must live inside a kernel, never in a host branch that changes which kernels launch.
  - The problem: whether a row flushes (`is_flush`) is per-row runtime data that varies across the batch (continuous batching) and across steps (variable acceptance), so the host cannot pick the launch set.
  - The solution: the launch sequence stays fixed. Every step issues both a verify launch and a flush launch; each kernel is compiled for its single role (`is_flush` is a compile-time constant per launch), and every row early-exits from the launch that does not apply to it. Which rows flush is routed on-device by the `is_flush` flags, not by host slicing.
  - The result: since the commit and flush-decision also run on-device (no host sync on `num_accepted`), the launch sequence is identical every step, so one captured graph per batch size covers the whole decode path.
- **Paged cache layout:** all ReplaySSM caches live inside the paged KV block, not in registers or a private per-request buffer, for two reasons. First, they are live across decode steps: the checkpoint persists until the next flush and the input ring accumulates history over many steps, so they must sit in HBM between kernel launches. Second, vLLM addresses every per-request recurrent state through paged blocks and a block table (continuous batching, variable active-request sets, prefix caching); we append our caches as extra tensors on the baseline `(conv, ssm)` state so they reuse that machinery, indexed per request by physical block id and allocated/freed with the request. Only the small per-block cursors (`write_pos`, `post_origin`, `is_flush`) for spec live in the metadata builder rather than the page.
  - **What we page (never the read/query vector):** the output's read vector (Mamba2 `C`, GDN `q`) is never cached in any mode; it comes from the current step's activations. Only the state-building inputs are paged:
    - Mamba2: `x`, `B`, `dt`. Standard uses separate size-`B` caches; spec packs `x|B` plus `dt` in a circular `next_pow2(B+T)` ring. `C` is read fresh from `conv_out`.
    - GDN: `(d, k, g)`, where `d` is the corrected update `u`. Standard uses size-`B` caches; spec uses a circular `next_pow2(B+T)` ring. `q` is read fresh.
  - The only structural difference across families and modes is the buffer geometry: size-`B` for standard, a circular `next_pow2(B+T)` ring for spec (room for the `T`-window).
- **Cache dtypes:** the checkpoint state follows the configured SSM dtype (`mamba_ssm_cache_dtype`; fp32 by default for the evaluated NVFP4 models, but FP16/BF16 supported); the input-vector caches (Mamba2 `x`/`B`, GDN `d`/`k`) follow the activation dtype (bf16); the per-step scalars that drive cumulative decay (Mamba2 `dt`, GDN `g`) are always fp32, for numerically-stable decay replay (and they are tiny, no `d`/`n` dim).

## Correctness / test coverage

Three levels, each with its command. Precision IDs are `(state, activation)`, each fp32/bf16/fp16 (e.g. `s32_a16` = fp32 state, bf16 activation).

### Kernel-level (vs reference)
Each cached kernel is checked per step over multi-flush sequences against the baseline decode and an exact reference.
- **Mamba2 standard** (`tests/kernels/mamba/test_replayssm_standard_decode_mamba2.py`): both routes vs the exact fp32 recurrence and baseline; also checks the `x`/`dt`/`B` caches and flushed state. 6 precisions `{s32_a32, s32_a16, s16_a16, s32_afp16, sfp16_afp16, sfp16_a16}`; geometries `{small, tiny, Nano-4B, Super-120B, Ultra-550B}`; buffer len `{1, 4, 16}`; `has_z`; per-row write positions and NULL-padded slots (continuous batching).
- **Mamba2 spec** (`tests/kernels/mamba/test_replayssm_spec_decode_mamba2.py`): a `T`-window verify step vs decoding the same window one token at a time; the non-flush checkpoint is checked bit-exact. 3 precisions `{s32_a32, s32_a16, s16_a16}`; same geometries; `B ∈ {16, 32}`; `T = 1 + num_spec ∈ {2, 4, 6, 8}`; rollback across flushes; continuous batching; a "teeth" test (a corrupted history slot must change the output).
- **GDN standard / spec** (`tests/kernels/test_replayssm_standard_decode_gdn.py`, `..._spec_decode_gdn.py`): the GDN analogs (standard has one route; spec mirrors Mamba2's `B`/`T` sweep and rollback / continuous-batching checks). Geometries `{small, Qwen-4B, Qwen-122B}`; standard also sweeps the paged strided layout.
- **Tolerances:** fp32 activations near-exact (rtol 1e-4, atol 1e-3), tight enough to catch a TF32-vs-`tf32x3` regression; bf16/fp16 loose (bf16 rounding dominates). Non-flush spec checkpoints are bit-exact.
```
pytest tests/kernels/mamba/test_replayssm_standard_decode_mamba2.py \
       tests/kernels/mamba/test_replayssm_spec_decode_mamba2.py \
       tests/kernels/test_replayssm_standard_decode_gdn.py \
       tests/kernels/test_replayssm_spec_decode_gdn.py -q
```

### Prefill/decode equivalence (full sequence)
The SSM recurrence is path-independent, so parallel chunked prefill (the model's prefill path) and step-by-step decode must give identical per-position outputs and final state on the same inputs.
- **Mamba2** (`..._prefill_decode_equivalence_mamba2.py`): anchors prefill, baseline, and both routes on the exact fp32 recurrence, then checks decode equals prefill. 6 precisions, `{small, Nano-4B}`.
- **GDN** (`..._teacher_decode_equivalence_gdn.py`): chunked prefill is the reference ("teacher", bf16-activation only); decode must reproduce its outputs and final state. 3 bf16-activation precisions, `{small, Qwen-4B}`.
- **Tolerances:** chunked-scan regime (parallel scan vs step recurrence): 1e-2/3e-2 (fp32-act), 6e-2/1e-1 (bf16).
```
pytest tests/kernels/mamba/test_replayssm_prefill_decode_equivalence_mamba2.py \
       tests/kernels/test_replayssm_teacher_decode_equivalence_gdn.py -q
```

## Performance — standard decode
Benchmark (runs the standard kernel and ReplaySSM in separate processes, reports the per-step speedup):

Setting: fp32 SSM state, `replayssm_buffer_len = 16`, output-only route for Mamba2 (single cached route for GDN), CUDA graphs on, greedy decode.

### End-to-end results
Whole-model per-step speedup (baseline ms/step / ReplaySSM ms/step; equivalently the tok/s ratio):

| Model (SSM, HW) | bs 1 | bs 8 | bs 32 | bs 64 | bs 128 | bs 256 | bs 512 |
|---|---|---|---|---|---|---|---|
| Nano-4B (Mamba2, H100) | 0.99 | 1.06 | 1.17 | 1.28 | 1.40 | 1.49 | 1.55 |
| Qwen3.5-4B (GDN, H100) | 0.99 | 1.04 | 1.08 | 1.14 | 1.21 | 1.27 | 1.31 |

- ReplaySSM is best at large batch and roughly break-even (~1.0×) at small batch.

### Max concurrency (16,4)
Baseline spec keeps state per draft token (`1 + num_spec = 4×` state) for rollback; ReplaySSM holds ~1× state plus the small input ring, so it fits far more concurrent requests under a fixed HBM budget (max decode concurrency at mml=2048, B300):

| Model | native-spec cap | ReplaySSM cap | cache/std |
|---|---|---|---|
| Super-120B (Mamba2) | 213 | 694 | 3.25× |
| Qwen-122B (GDN) | 233 | 702 | 3.01× |

These are serving-capacity caps (worst case, at the full 2048-token request length). Once the requested batch exceeds the cap, throughput saturates rather than failing: vLLM splits the batch into sub-batches under the cap and runs them sequentially.

### Kernel-level results
Isolated verify-step (non-flush) kernel latency on Super-120B (Mamba2, B300), fp32 state, best config (`bsm64/nw2/dt64`), cold L2, measured with `ncu` at base clock.

## Notes for reproducibility of benchmarks 
- **Blackwell / FlashInfer workarounds (orthogonal to ReplaySSM).** On the pre-release Blackwell FP4 path these present as a long silent hang after `torch.compile` (not a crash), so do not mistake them for the cached kernels:
  - `gdn_prefill_backend=triton` (GDN models; the scripts default to it): FlashInfer's GDN-prefill kernel JIT-compiles (cutlass-DSL) on first use and stalls; the Triton prefill starts instantly and leaves decode speed (and the measured speedup) unchanged.
  - draft `moe_backend=triton` (pass for GDN spec, as in the command above): the draft model's bf16 MoE hangs on the `flashinfer_trtllm` backend; the main-model MoE stays on `auto`.
  - FP4-MoE autotuner disabled under CUDA-graph capture (script default; pass `--no-disable-flashinfer-autotune` for non-FP4 models).
- **Memory profiler:** set `VLLM_MEMORY_PROFILER_ESTIMATE_CUDAGRAPHS=0` to keep the benchmark scripts' default `gpu-memory-utilization`; otherwise lower `gpu-memory-utilization` to fit large batch sizes.

## Work in progress (Follow-up)
- **Low-precision state (FP16/BF16):** on B300, FP16/BF16 state is currently ~parity with baseline latency (high register pressure → low bandwidth utilization); the planned fix is dstate-tiling (as already done in the spec kernel). Only fp32 state has been evaluated so far.
- **Tensor parallelism (TP>1):** add TP-correctness tests (e.g. TP1 == TP2) and evaluate large models (Ultra-550B, Qwen3.5-397B) on both standard and speculative decode.
- **Precision study:** covers the re-quantization benefit of a low-precision checkpoint (FP32 reconstruction plus flush-only writeback re-quantizes the state at most ~`L`× less often than the per-step baseline; see Core concept) and the per-step output arithmetic (`output_only` vs `state_and_output`). Both Mamba2 routes are retained for it; `state_and_output` and `--replayssm-route` will be removed in the final version.
