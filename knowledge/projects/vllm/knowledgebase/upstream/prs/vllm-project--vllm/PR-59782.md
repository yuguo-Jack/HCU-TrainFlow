# [ROCm][DSv4.1][Perf] Quantize the activation inside the MXFP8 block32 GEMM at small M

[Upstream PR](https://github.com/vllm-project/vllm/pull/59782) · state: open · merged: False

## Original PR description

## Overview

On ROCm, every MXFP8 linear with 32x32 block scales (all DeepSeek V4.1 attention and shared-expert linears) ran `mxfp8_e4m3_quantize` and then the block32 GEMM from [#58510](https://github.com/vllm-project/vllm/pull/58510), which is two launches per linear. At decode sizes the GEMM now quantizes the bf16 activation in registers, bit-identically, so each linear is one launch. That removes about 210 graph nodes per DSv4.1 decode step at TP4. No existing PR does this; see Details for [#56674](https://github.com/vllm-project/vllm/pull/56674) and [#57857](https://github.com/vllm-project/vllm/pull/57857), which touch the same activations.

## Claims

- At 1–8 tokens, the DSv4.1 block32 linears are 1.14× to 1.61× faster per call on MI355X. Some shapes keep gaining up to 64 tokens. Above each shape's tuned limit (8 to 64 tokens), routing falls back to the old two-launch path and timing is unchanged.
- Activation quantization is bit-identical to `mxfp8_e4m3_quantize`. The only numeric change is accumulation order, where the small-M tile config differs from the existing table.

## Details

**Motivation.** A DSv4.1 decode profile on MI355X (TP4, 2 requests) showed about 1,335 graph nodes per step and host-side graph submission as the bottleneck, at about 8 µs per node. The MXFP8 quantization (`_kernel`) and the block32 GEMM (`_block32_packed_kernel`) each ran 210 times per step at about 5 µs, a third of all nodes.

**Kernel.** `_block32_tiled_kernel` and `_block32_packed_kernel` take a `QUANT_X` constexpr. When it is set, they load the bf16 tile and quantize it per 32 columns with `_quant_mxfp8`, using the same fp32 operations as `_mxfp8_quant_triton_kernel`:

- the amax is clamped to the smallest normal fp32;
- the E8M0 scale is `ceil(log2(amax / 448)) + 127`, clamped to [0, 254];
- values are multiplied by the reciprocal power of two, then cast to e4m3.

This makes the result bit-identical. The packed kernel's K panels start on 32-column boundaries, so each row's groups are exactly the activation's MX blocks. The kernels also take an activation row stride, so a sliced input doesn't need a copy.

**Routing.** `rocm_mxfp8_block32_linear` is an opaque custom op, like the existing GEMM op, because the choice depends on the token count. It takes the fused path when `_TUNED_QUANT_X` (or `_DEFAULT_QUANT_X` for untuned shapes) has a tier for M. Otherwise it quantizes separately and uses the existing `_TUNED` table. The pre-quantized `rocm_mxfp8_block32_gemm` op is unchanged for callers that already hold MXFP8 activations.

**Tuning.** I swept packed and tiled configs at 1–64 tokens for each DSv4.1 TP2/TP4 shape, under the same HIP-graph, cold-LLC timing as `_TUNED`. Each shape stops at the largest M where the fused config beat the separate path by at least 5%. A separate table is needed because the in-kernel quantization only pays off with different configs. With the existing `_TUNED` configs, it lost on most shapes and token counts, by 0.22× to 0.99×:

- **Large tiles:** `fused_wqa_wkv`'s 16×1024 packed tile ran at 0.72× even at 1–8 tokens.
- **Tiled configs at 24–32 tokens:** `indexer_wq_b` dropped to 0.33×.
- **48 tokens and up:** every shape lost, falling to about 0.5× at 1024 tokens and 0.22× for `wq_b` at 8192. Every N-tile program re-quantizes the same activation rows, so the kernel becomes bound on vector ALU work.

With small packed tiles (4–8 rows, K tiles of 128–256), the per-32 reduce is cheap. GPU kernel time drops as well as the launch count: for example, 6.38 → 4.46 µs for shared down TP4 at M=1 in profiler time.

**Relation to #56674's prologue result.** #56674 reports that it tried quantizing in the GEMM prologue and rejected it at 0.28–0.89×, with the reshape+reduce adding about 26 µs to a 12 µs GEMM. That attempt predates the block32 GEMM ([#58510](https://github.com/vllm-project/vllm/pull/58510)) and targeted `_mxfp8_dot_scaled_linear` with its existing tiles. The 0.22× to 0.99× above, from this kernel with the existing `_TUNED` configs, reproduces that result. The difference here is small-M configs tuned for in-kernel quantization, plus routing that only takes the fused path where it measured faster.

**Complexity.** +210 / −7 lines in `rocm_block32_gemm.py`, of which about 95 are the tuned table, and +3 / −4 in `rocm_native.py`. No core components are touched, and no CPU/GPU synchronization is added (the op reads only shapes and strides on the host).

**Limitations.**

- Tuned on gfx950 (MI355X) only, like `_TUNED`.
- DeepSeek-V4 (not V4.1) also uses this kernel through the default tier, but was not run end to end.
- Bit-exactness relies on both Triton kernels compiling the same fp32 math. The new tests check this on every CI run.



### Existing PRs and interaction

I searched vllm-project/vllm PRs (open and closed) for MXFP8 / block32 / dot_scaled together with quant fusion and ROCm. No PR fuses the activation quantization into the block32 GEMM.

- [#56674](https://github.com/vllm-project/vllm/pull/56674) (open, draft) fuses RMSNorm into the MXFP8 quantization by pattern-matching `rms_norm` followed by `torch.ops.vllm.mxfp8_quantize` in the compiled graph. It rejected prologue quantization for the pre-block32 kernel; see Details for why this result differs. This PR moves the quantization inside the opaque `rocm_mxfp8_block32_linear` op, so for block32 linears #56674's pattern would no longer match at any M, prefill included.
  - At decode both PRs remove one launch per linear. This PR also covers linears that don't follow an RMSNorm, and it stays bit-identical to `mxfp8_e4m3_quantize`. #56674's AITER quantizer rounds a few blocks per thousand to a scale one power of two apart.
  - At prefill, #56674 would remove a launch that this PR doesn't.
  - If both are wanted, a follow-up could let the block32 linear accept a pre-quantized input above the fused threshold. Reviewer input welcome.
- [#57857](https://github.com/vllm-project/vllm/pull/57857) (open, needs rebase) lets the ROCm MXFP8 linear take a pre-quantized activation, so `wq_b` and `indexer.wq_b` can share one quantization. This is complementary. At decode, each GEMM now quantizes in-kernel at almost no cost. Above the fused threshold, sharing would still save a launch.
- [#58510](https://github.com/vllm-project/vllm/pull/58510) (merged) added the block32 GEMM and `_TUNED` that this PR extends.
