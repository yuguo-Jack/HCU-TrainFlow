# [Bugfix][Rust Frontend] Drop a DeepSeek DSML tool-call opener cut after its DSML token

[Upstream PR](https://github.com/vllm-project/vllm/pull/62290) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Follow-up to #65375. Since #65375, a DeepSeek V3.2 / V4 / V4.1 output that ends inside a DSML tool-call block is dropped at finish instead of being returned as `content`. An output that ends inside the tool-call opener, after its `｜DSML｜` token, still leaks: a V4.1 output `Checking.\n\n<｜DSML｜ calls` (cut before `>`) returns `content: "Checking.\n\n<｜DSML｜ calls"`. This PR reports that tail as `IncompleteToolCall` too, so `UnifiedParserState::finish` drops it like any other unfinished tool call.

This PR is now rebased onto #65375 and reduced to that one case. Its earlier revision added its own `IncompleteToolCall` and dropped the buffer only at `max_tokens`; #65375 does that in general (every parser family, every finish reason), so that part is gone, and the title and description are rewritten.

## Claims

- An output that ends inside a DSML opener after its `｜DSML｜` token (` calls>` for V4.1, `tool_calls>` for V4, `function_calls>` for V3.2) no longer returns the half-written opener as `content`. The text before it is kept (the `\n\n` that frames the opener is dropped with it, as it is for a complete tool call). As in #65375, this holds for every finish reason. It is the rule the Python parser engine pins for a cut inside a tool-call opener (`TestTruncatedToolOpenerStreamParity`, with `qwen3_coder`); I did not check the Python DeepSeek parser for this case.
- Trailing text is still returned as text: a partial `<｜DS` spelling, an opener spelled with ordinary tokens, and a held-back tail without `<｜`.
- Code change: `deepseek_dsml/mod.rs` only (22 lines). The rest is tests.

## Validation

**Real trigger.** `｜DSML｜` is a single added token in the DeepSeek-V4.1 tokenizer, and the rest of the opener is ordinary tokens. `"Checking.\n\n<｜DSML｜ calls>\n"` encodes (DeepSeek-V4.1-Flash `tokenizer.json`, `add_special_tokens=False`) as:

```
'Checking' '.ĊĊ' '<' '｜DSML｜' 'Ġcalls' '>Ċ'
```

so `max_tokens` can end the output right after `｜DSML｜` or after ` calls`. For the V4 opener the pieces are `'<' '｜DSML｜' 'tool' '_c' 'alls' '>Ċ'` (V3.2: `'function' '_c' 'alls'`, checked with the same vocabulary). The tests cut at these boundaries.

New tests:
- V4.1: cut right after the `｜DSML｜` token and after ` calls`, each at every two-chunk split. The earlier text is emitted, `finish()` returns `IncompleteToolCall`, and `reset()` holds only the unfinished markup. The input is attributed as the frontend decodes it, so `｜DSML｜` is the added token.
- V3.2 and V4: a half-written opener (`<｜DSML｜function_c`, `<｜DSML｜tool_c`) returns `IncompleteToolCall`.

The reasoning `plan` and the text `Checking.` are kept, the half opener is dropped, and no tool call is emitted.

## Details

- **Root cause:** in text mode the DSML parser holds back a tail that may still become an opener (`safe_text_len_mul`). If the output ends there, the parser never enters `ToolBlock`, and `finish()` returns the held-back tail as text (`DsmlMode::Text => output.push_text(...)`). So the `IncompleteToolCall` that #65375 drops is never raised.
- **The check** (`is_unfinished_opener`): the held-back tail contains `<｜` and is a proper prefix of `framed_tool_calls_start` or `tool_calls_start`. Openers match only on the dedicated `｜DSML｜` token (#62875), so an opener spelled with ordinary tokens has already been emitted as text before `finish()`. A held-back tail without `<｜`, such as a trailing `\n\n` or `<`, is text.
- **Scope:** only the DSML parser changes, so only DeepSeek V3.2 / V4 / V4.1 are affected.
