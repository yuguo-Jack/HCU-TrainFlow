# [Bugfix][Rust Frontend] Drop an incomplete DeepSeek DSML tool call at max_tokens instead of leaking it into content

[Upstream PR](https://github.com/vllm-project/vllm/pull/62290) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

When a DeepSeek V3.2 / V4 / V4.1 response is cut by `max_tokens` inside a DSML tool call, the Rust frontend returns the half-written markup as `content`, for example `…\n<｜DSML｜ invoke name="get_weather"` with `finish_reason=length`. This PR adds `ToolParserError::IncompleteToolCall` and drops the buffered text only for that error at `max_tokens`. Related: #62051 (Python parser, same class of problem), #62259.

## Claims

- A tool call cut by `max_tokens` no longer appears in `content`: DSML in content goes from 22/88 to 0/88 on DeepSeek-V4.1-Flash. Earlier text and completed calls are kept.
- For every other finish reason (stop, EOS, a stop string), and for any other parser error, the buffered text still falls back to content, as before. The existing Gemma4 EOS-recovery test passes unchanged.
- With thinking on, reasoning that was emitted before the cut is kept, and only the unfinished markup is dropped: DSML in content goes from 32 and 35 / 154 on two base runs to 0 / 154.

## Details

- **Root cause:**
  - `DeepSeekDsmlToolParser::finish()` fails while a tool-call block is open (`deepseek_dsml/mod.rs`).
  - The unified output path (`rust/src/chat/src/output/default/unified.rs`) handles a failed `finish()` by emitting `parser.reset()` as text, so the unconsumed DSML ends up in `content`.
  - The `calls` opener was already consumed, which is why the leaked text starts at `<｜DSML｜ invoke`.
  - A cut inside the opener itself (`\n\n<｜DSML｜ ca`) was emitted as text directly.
- **Why only `IncompleteToolCall` at `length`:**
  - `finish()` knows that a call is unfinished, not why. At `max_tokens` the buffer holds a call that was cut off, so dropping it is safe: there is no tool call, `finish_reason` stays `length`, and the client can retry with a larger `max_tokens`.
  - On any other finish reason, the buffer may hold malformed output (for example a missing `</｜DSML｜ invoke>`), and falling back keeps it visible. The same holds for other parser errors.
  - The drop is logged with `warn!` and the dropped length.
- **Scope:**
  - Only the DSML parser returns the new variant, so only DeepSeek V3.2 / V4 / V4.1 change.
  - Other parsers that report `incomplete … tool call` with `ParsingFailed` keep their current behaviour. They can switch to `IncompleteToolCall` in follow-ups, for example Gemma4, GLM, Kimi or MiniMax.
  - The error message text is unchanged, so the existing V3.2 tests that check it pass unmodified.
- **Known, unchanged:** on `main`, `CombinedParser::finish` discards output produced earlier in the same `finish()` call when the tool parser fails. This PR does not change that, and it does not trigger for DeepSeek: its reasoning parser flushes only reasoning or only content at finish. The combined test above covers this path.
- **Other open PRs:** the Rust DSML PRs #56302, #56334 and #58057 keep the `finish()` error for an open block, so they do not overlap with this change. #58057 composes with it.
