# [Bugfix][Core] Keep resumable sessions that stop while preempted

[Upstream PR](https://github.com/vllm-project/vllm/pull/58778) · state: closed · merged: True

## Original PR description

## Purpose

Fixes #58776.

With async scheduling, a resumable (streaming-input) request can be preempted while a step is still in flight. That step's output is delivered as stale output, and if it hits a stop condition the request stops in `PREEMPTED` state. Two things then go wrong:

1. **The session drops out of every queue.** `_handle_stopped_request` re-enqueues the resumable request, but the stopped-while-preempted cleanup in `update_from_output` removes it from `waiting`, `kv_holding_waiting` and `deferred_waiting`, including that new entry. The session is then in no queue and is never scheduled again. (Still the case after the queue rework in #58947 and the handoff fix in #58259.)
2. **The fold deletes the prompt.** `_update_request_as_session` keeps `all_token_ids[num_prompt_tokens:num_computed_tokens]` and deletes the rest. After preemption `num_computed_tokens == 0`, so it deletes the whole list, while `prompt_token_ids` (a separate list) is only extended; `num_prompt_tokens` then no longer matches `all_token_ids`, and the previous turn's output is lost.

Changes:

- After the stopped-while-preempted cleanup, re-enqueue requests that did not finish, so each ends up in exactly one queue.
- In the fold, keep up to `max(num_computed_tokens, num_tokens - 1)`. On a normal stop `num_computed_tokens == num_tokens - 1`, so nothing changes; after preemption the session keeps all but the final sampled token, and `num_computed_tokens` stays 0 so everything is recomputed.

## Not a duplicate

Searched open and closed issues and PRs for this path (`stopped_preempted_reqs`, streaming/resumable + preempt, `_update_request_as_session`, session hang symptoms); none found. #58668 fixes a different case where `num_computed_tokens` is wrong at the fold (a speculative step stopping on an accepted draft). Both PRs append a test to `tests/v1/streaming_input/test_scheduler_streaming.py`, so whichever lands second needs a trivial rebase.

## Impact (update)

Besides the client-visible hang, the parked variant leaks scheduler capacity. When the session stops while preempted with no continuation queued, it is parked as `WAITING_FOR_STREAMING_REQ` and `num_waiting_for_streaming_input` is incremented — and the queue cleanup then drops the session from every queue. If no continuation ever arrives, the counter is never decremented: each occurrence permanently consumes one `max_num_active_reqs` admission slot (the `num_running = len(self.running) + self.num_waiting_for_streaming_input` accounting in `schedule()`), so repeated occurrences silently shrink admission capacity. Verified locally on main: after the preempted stop, the parked case leaves `num_waiting_for_streaming_input == 1` with the session in no queue; if a continuation later arrives the counter rebalances in `_update_request_as_session`, but the session itself is already lost.

- yzong-rh · APPROVED · 2026-09-30T21:59:31Z · [source](https://github.com/vllm-project/vllm/pull/58778#pullrequestreview-5372460458)

> The session drops out of every queue.

LGTM. The stopped-while-preempted cleanup in `update_from_output` is run on all requests that stopped **in the current step**. It removes the request from all queues, which is correct for normal requests but is incorrect for resumsable requests. For them, reaching stop in the current step doesn't mean the request has finished, so removing from all schedulings leave them orphaned.

The current fix re-enqueues any request that hasn't finished. This is correct, but a cleaner fix may be to centralize queue ownership updates: don't `_enqueue_waiting_request` in `_handle_stopped_request`, enqueue them once in `update_from_output`. This has a nice side-benefit of not allowing a request to be on two queues at once, even temporarily.


> The fold deletes the prompt.

LGTM. Using `num_computed_tokens` and `num_output_placeholders` to compute the prompt handoff always felt like a codesmell since they can be reset by preemption. I think instead of `max(num_computed_tokens, num_tokens - 1)`, it's safe to just use `num_tokens - 1`. IIUC, `num_computed_tokens` and `num_tokens - 1` would not differ in the normal autoreggressive case after https://github.com/vllm-project/vllm/pull/58668 assuming no preemption. Pooling, encoder-only, and diffusion may break this invariant, but they don't really make sense with resumable requests. We already reject resumable + pooling. We should reject resumable + encoder-only or diffusion.

#59501 demonstrates one way to implement the above suggestions and NITS. Feel free to copy and commandeer it.
