# [Misc] Add trace context to JSON logs

[Upstream PR](https://github.com/vllm-project/vllm/pull/54769) · state: closed · merged: False

## Original PR description

## Overview

Add `trace_id` and `span_id` to vLLM's existing JSON log format when an OpenTelemetry span is current. The built-in vLLM and Uvicorn JSON configurations use the same formatter.

## Claims

- Logs emitted under a valid active span include its trace and span IDs as JSON fields.
- JSON logs without active trace context keep their existing fields. Text logging is unchanged.

## Validation

- `.venv/bin/python -m pytest tests/test_logger.py tests/test_uvicorn_logging.py -q --disable-warnings` — 42 passed.
- `.venv/bin/pre-commit run --files examples/features/logging_configuration.md tests/test_logger.py vllm/logger.py vllm/logging_utils/formatter.py vllm/logging_utils/uvicorn_logging.py` — passed.
- A local Uvicorn JSON access-log probe matched both IDs to the active span.
- A broader `test_abort_requests` run could not load its `meta-llama/Llama-3.2-1B` fixture because Hugging Face was unreachable. The final PR diff does not change engine code.
- Model evaluation is not applicable: this changes logging output, not model output or serving behavior.

## Details

The formatter extends the existing JSON output; it does not define a separate OpenTelemetry flat JSON schema. This work is distinct from #57957 (valid JSON lines) and #58739 (built-in JSON selection).

The invasive early `llm_request` span lifecycle changes were removed in response to review.
this PR makes trace fields available on records with active context but does not solve stuck-request correlation.

# RFC: logging configuration and structured logging

## 1. Motivation

- Reduce logging-specific environment-variable proliferation ([#25700]).
- Provide a coherent CLI and serve-config model.
- Support structured logs and request correlation without requiring every user  to author a Python logging configuration.

## 2. Current state

- [`--log-config-file`] loads a Python `dictConfig`; its default comes from  `VLLM_LOGGING_CONFIG_PATH`.
- Custom configuration covers both vLLM and Uvicorn since [#18403].
- JSON stdout is already possible with the bundled `python-json-logger`; see  [Example 1 in the logging-configuration documentation].
- Additional requests include file output ([#31863]) and control of process  prefixes ([#28582]).

## 3. Goals

- Make CLI/serve configuration canonical while retaining existing environment  variables as compatibility aliases.
- Provide simple built-in text and JSON profiles.
- Optionally provide an OpenTelemetry Logs Data Model-aligned JSON profile.
- Expose `request_id`, `trace_id`, and `span_id` as structured log attributes.
- Configure vLLM, Uvicorn, and subprocess logging consistently.

## 4. Non-goals

- Native OTLP log export.
- Logging prompts or generated content by default.
- Treating formatting as a substitute for missing events or context  propagation.

## 5. Proposed configuration model

Candidate settings:

- `--log-config-file PATH`
- `--log-format {text,json,otel-json}`
- `--log-level LEVEL`
- output/stream/file configuration
- process-prefix configuration

Define precedence:

```text
CLI > --config YAML > environment compatibility aliases > defaults
```

Specify how built-in profiles interact with a custom `dictConfig`.

## 6. Structured-log profiles

### JSON

Machine-readable representation of normal `LogRecord` fields.

### OTel-aligned JSON

Define mappings for:

- timestamp
- severity text/number
- body
- logger/instrumentation scope
- service/resource attributes
- exception attributes
- `trace_id` and `span_id`

Clarify that this is an application stdout profile, not OTLP/JSON.

## 7. Correlation attributes

- Add `request_id` independently of formatting ([#28933], [#35864]).
- Add trace/span IDs only when valid context exists.
- Ensure production-safe lifecycle and error records receive correlation  attributes without enabling prompt/output logging.
- Define behavior across API and engine processes.

## 8. Compatibility and security

- Preserve existing environment-variable behavior during migration.
- Keep text output as the initial default.
- Avoid prompt/output disclosure.
- Address volume, exceptions, third-party loggers, and multiprocessing.

## 9. Alternatives

- Continue requiring user-supplied `dictConfig`.
- Perform normalization in an external collector.
- Add another environment-variable-only switch, as proposed by [#54769].

## 10. Validation

- Configuration-precedence tests.
- Text/JSON schema tests.
- vLLM and Uvicorn coverage.
- Exception and subprocess coverage.
- End-to-end request test proving `request_id`, `trace_id`, and `span_id`  correlation with production-safe settings.
