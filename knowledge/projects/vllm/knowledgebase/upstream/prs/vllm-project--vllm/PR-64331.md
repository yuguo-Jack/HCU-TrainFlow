# [ROCm][RDNA][Perf] Bump triton_kernels to ROCm 3.8.x with the RDNA MXFP4 configs

[Upstream PR](https://github.com/vllm-project/vllm/pull/64331) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Bump the ROCm triton_kernels pin from `669b31acc1` to `3ef5021860`, the head of ROCm/triton `release/internal/3.8.x`. The new commit is ROCm/triton#952, the 3.8.x backport of triton-lang/triton#10810. It adds RDNA3/4 tile configs for bf16 × MXFP4 `matmul`, the gpt-oss MoE GEMMs.

## Claims

- gpt-oss-20b on Radeon AI PRO R9700 (gfx1201): **+11.6% throughput** over main (10.59 → 11.82 req/s). MoE GEMM time drops 18.7%.
- Only triton_kernels changes. The Triton compiler pin (`Dockerfile.rocm_base`, 3.8.0+git669b31ac) stays.
- No change outside RDNA:
  - The only triton_kernels file that differs between the two pins is `matmul_details/opt_flags.py` (+30/−13).
  - The CDNA4 bf16 × MXFP4 block is only re-indented under the shared dtype check.
  - The new block is gated on `get_rdna_version() in (3, 4)`.
  - The other files that differ between the two commits are compiler/setup files, which vLLM's triton_kernels fetch does not use.

## Validation

**Throughput.** `vllm bench throughput --model openai/gpt-oss-20b --max_model_len 4096 --dataset-name sharegpt --num_prompts 1000 --tensor_parallel_size 1 --gpu-memory-utilization 0.8`, single R9700.
- Same build and session for both arms. Only the vendored `opt_flags.py` differs.
- One cold run and two warm runs per arm. The table shows warm-best, with the individual runs in brackets.

| | req/s | vs main |
|---|---:|---:|
| main | 10.59 (10.29, 10.59) | — |
| **this PR** | **11.82** (11.50, 11.82) | **+11.6%** |

Stack: ROCm 10.2.0a20261020, torch 2.14, Triton 3.8.0+git669b31ac, main c0a41721c7.

**rocprofv3, one warm run of the same benchmark (s):**

| MoE GEMM tiles (GEMM1 + GEMM2) | main | this PR |
|---|---:|---:|
| small steps: `32x256x128` → `16x64x512` | 16.51 | 9.68 |
| mid + large steps: `64x256x64` + `128x256x128` → `64x128x128` | 36.33 + 7.12 = 43.45 | 39.10 |
| **MoE GEMMs total** | **59.96** | **48.77** |
| total GPU kernel time | 103.02 | 91.83 |

On main, the 192 large-step calls use `128x256x128` and average 24.7 ms (GEMM1) and 12.3 ms (GEMM2). With this PR they run on `64x128x128`, so the middle row compares the same calls.

On main, the 2-warp `32x256x128` variants (steps of up to 4 tokens) run at 256 VGPRs with about 1,200 spills each. None of the new tiles spill (151–180 VGPRs).

**GSM8K** (`lm_eval --model vllm --tasks gsm8k --num_fewshot 5`, all 1319 problems, R9700). The new tiles change the fp32 accumulation order, so MoE output is not bitwise equal to main. Each arm was run twice, because identical reruns are not reproducible here.

| | run 1 | run 2 | mean |
|---|---:|---:|---:|
| main, flexible / strict | 0.3647 / 0.2540 | 0.3700 / 0.2722 | 0.3673 / 0.2631 |
| this PR, flexible / strict | 0.3639 / 0.2494 | 0.3723 / 0.2691 | 0.3681 / 0.2593 |

- The mean differences (+0.0008 / −0.0038) are well inside the per-run stderr (0.013).
- Scored outcomes flip on 386–397 problems between main and this PR, vs 389–399 between identical reruns of the same version.

**Tests:** `pytest tests/kernels/moe/test_gpt_oss_triton_kernels.py` on gfx1201 gives the same result with either pin: 19 passed, and 4 `test_equiv` failures. Those failures exist on main too: ROCm reports capability 12.0, so the test applies the NVIDIA SM12x `is_persistent` constraint (`InapplicableConstraint`).

**gfx1100:** the new block also covers RDNA3, but this PR was not measured on gfx1100.

## Details

triton-lang/triton#10810 landed on main on 2026-07-12, after the 3.8 branch cut (2026-06-23). So no 3.8 release branch had it, and vLLM's ROCm build, which pins `release/internal/3.8.x` to match the Triton compiler in its images, never shipped it. ROCm/triton#952 backports it to `release/internal/3.8.x`. The 3.9 branches already contain it.

The pin is set in three places, all updated:
- `cmake/external_projects/triton_kernels.cmake` (non-Docker builds);
- `ROCM_TRITON_KERNELS_COMMIT` in `docker/Dockerfile.rocm`;
- the same ARG in `docker/Dockerfile.rocm_72`.

`Dockerfile.rocm_72` fails the build when its ARG does not match the cmake tag.
