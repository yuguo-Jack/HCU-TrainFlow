# [Rust Frontend] Support VLLM_LOG_STATS_INTERVAL and VLLM_DISABLE_REQUEST_ID_RANDOMIZATION

[Upstream PR](https://github.com/vllm-project/vllm/pull/62825) · state: closed · merged: True

## Original PR description

## Overview

The Python frontend reads two settings only from the environment: `VLLM_LOG_STATS_INTERVAL` paces the periodic stats log, and the deprecated `VLLM_DISABLE_REQUEST_ID_RANDOMIZATION` keeps external request IDs as engine-core request IDs. The Rust frontend ignores both. This PR honors them on both launch paths.

## Claims

- `VLLM_LOG_STATS_INTERVAL` (float seconds, `vllm/envs.py`) sets the Rust stats log interval, like Python's `asyncio.sleep(envs.VLLM_LOG_STATS_INTERVAL)` (`launchers/utils/server_utils.py`). Before, Rust always logged every 10s.
- `VLLM_DISABLE_REQUEST_ID_RANDOMIZATION=1` keeps the external request ID without the 8 random characters (`InputProcessor.assign_request_id`). Before, Rust always randomized.
- Both work under `vllm-rs serve` and under `vllm serve` with `VLLM_USE_RUST_FRONTEND=1`, with no Python change.

## Details

Environment handling stays in the CLI layer (`rust/src/cmd/src/cli.rs`), where `VLLM_API_KEY`, `VLLM_ENGINE_READY_TIMEOUT_S`, and `VLLM_HTTP_TIMEOUT_KEEP_ALIVE` are already read; the server and `vllm-llm` only see typed config.

- `vllm-rs serve`: clap binds each variable to a hidden flag (`env = ...`), as `--debug-cli` does with `VLLM_RS_DEBUG_CLI`. clap needs a long name to bind an env var; hiding it keeps the help aligned with Python, which has no such flag.
- `vllm serve` with the Rust frontend: `--args-json` is parsed with serde, so `apply_env_fallbacks` (formerly `apply_env_api_key_fallback`) reads both from the environment the Rust process inherits, like `VLLM_API_KEY`. It takes the environment lookup as a parameter so tests do not mutate process env.
- The values reach their existing consumers: `Llm::with_log_stats` takes the interval (`None` when stats logging is disabled or the interval never elapses) and passes it to `StatsLogger`; the server calls the existing `Llm::with_request_id_randomization`.

Parsing follows Python: `VLLM_LOG_STATS_INTERVAL` ≤ 0 or NaN gives 10s; an interval too long for a `Duration` (`inf`, `1e30`) never logs, as Python's `asyncio.sleep(inf)` never wakes; `VLLM_DISABLE_REQUEST_ID_RANDOMIZATION` is `int(value) != 0`. Two differences: the stats logger rounds a zero interval (such as `1e-10`) up to 1ns, because tokio panics on a zero period; and a malformed value fails startup, while in Python it only kills the background logging task when that task first runs.

Not a duplicate: no open upstream PR touches these variables in Rust. Python's open vllm-project/vllm#45688 (inactive since 2026-07-29) proposes removing `VLLM_DISABLE_REQUEST_ID_RANDOMIZATION`; if it lands, the Rust side is one field and one builder call to drop.
