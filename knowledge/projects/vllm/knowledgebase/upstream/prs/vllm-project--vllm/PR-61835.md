# [Bugfix][Spec Decode] Avoid distributed RunAI draft loading with PP

[Upstream PR](https://github.com/vllm-project/vllm/pull/61835) · state: closed · merged: False

## Original PR description



## Overview

Avoid distributed RunAI loading for speculative draft models instantiated only on the last pipeline stage. Reuse the existing MRV2 pipeline-safe draft loader helper and preserve distributed target loading.

**Dependency before merge:** [model-streamer #252](https://github.com/dsx-ai-factory/model-streamer/pull/252) must ship in the required RunAI version. Released 0.16.1 still performs a global collective during non-distributed safetensors header reads; this vLLM guard alone is insufficient with that release.

## Claims

- With PP>1, copy the RunAI draft extra config and disable its distributed mode, preserving S3 access and other loader options.
- Preserve PP1 behavior, the target configuration, and the existing fastsafetensors fallback.
- Resolve the reproduced PP2 draft-loading deadlock when paired with the RunAI fix.

## Validation

Six parametrized configuration regressions passed against the candidate helper in the deployed Linux vLLM 0.30.0 image, with GPUs hidden. Relevant pre-commit hooks passed, including Ruff, formatting, typos, mypy, and test tethering; `git diff --check` passed.

```bash
.venv/bin/python -m pytest tests/v1/worker/test_dspark_utils.py -q \
  -k 'runai_draft_loading_preserves_target_configuration or pp_draft_preserves_loader_without_distributed_streaming'
```

A real two-process Gloo reproducer loads a local safetensors target on both ranks through `RunaiModelStreamerLoader.load_weights`, then loads the draft on rank 1 while rank 0 waits at the final barrier. It verifies exact loaded tensors. Runtime: Python 3.12.3, PyTorch 2.13.0+cu130, RunAI 0.16.1, safetensors 0.8.0; target streaming remained distributed.

| Configuration | Result |
| --- | --- |
| Baseline | Collective timeout |
| vLLM guard only | Hidden header-discovery collective timeout |
| RunAI #252 only | Distributed draft-payload collective timeout |
| Both fixes | Target and draft load; exact tensors |

Full Kimi-K3 verification used two eight-B200 nodes, TP8/DCP8/PP2, InfiniBand RDMA, MRV2, and DSpark with three speculative tokens and block rejection sampling. Both patches were applied before startup inside isolated containers using pinned vLLM 0.30.0. All 16 ranks finished model loading, including the last-stage draft. A nonempty 512-token SSE response ended with `[DONE]`; arithmetic, cached prompt logprobs, images, ordered images, tool calls, and all 80 concurrent requests passed. Acceptance was **6,799 / 12,123 draft tokens (56.08%)**.

These are short synthetic correctness checks, not a broad quality evaluation or controlled throughput comparison. The full-model run used the exact helper backported to v0.30.0, rather than a complete build of this main-based branch. Kimi's existing CPU-offload count fix was present with one explicit test block per rank; production speculative offload sizing was outside this loading validation.

The unit cases are covered by the existing `v1-executor-worker` Buildkite job (`pytest v1/worker`). Full-model CI additionally requires the Kimi checkpoint and 16 B200 GPUs; the canary supplied that validation outside CI.

## Details

PP0 finishes target loading and never instantiates the draft. A draft inheriting distributed RunAI loading enters collectives requiring those absent PP0 participants. The existing shared helper already avoids this topology mismatch for fastsafetensors; extend it for RunAI while retaining its S3 loader. DSpark, EAGLE, and DFlash already call this helper. The change runs only during loading and adds no steady-state inference synchronization.

Independent draft reads can increase startup I/O compared with distributed draft streaming. A future process-group-aware RunAI API could support distributed reads scoped to the draft ranks. The target's large checkpoint retains its configured distributed loading mode.

Duplicate checks reviewed related work: #53901 addresses ROCm Kimi/fastsafetensors loading, #61699 applies the existing helper to standalone drafts, and #61715 integrates DeepSeek mixed CPU/GPU loading. None implements this RunAI PP draft guard. The loader deadlock is also described in comments on #44697; this change does not implement that RFC's broader PP token-accounting work. The existing RunAI #252 is reused rather than duplicated or vendored here.
