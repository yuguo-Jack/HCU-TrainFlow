# [Core] Route by exact in-flight count when a single client owns the DP engines

[Upstream PR](https://github.com/vllm-project/vllm/pull/62900) · state: open · merged: False

## Original PR description



## Overview

With one API server, `DPLBAsyncMPClient` routes by `max(inflight, waiting + running)`, where the second term is the coordinator's step-boundary snapshot. The snapshot lags the client's exact in-flight count, so the engine that just freed a slot ties with the full engines, and the rotating tie-break sends the replacement to a full engine (DP-1)/DP of the time. Under closed-loop load one engine then runs one request over and one engine one under for a whole round, and lockstep DP+EP decode waits for the fuller one. Related: #43279 (power-of-two choices, open), #59017 (session affinity, merged), #49204 (exact in-flight counts). #58070 (open, with #61386 as its plumbing stage) changes the same score with result-metric penalties and a superlinear in-flight term behind an env flag; whichever lands second will need a rebase, and this PR changes only the single-client case.

## Claims

- When `client_count == 1`, engines are scored by `inflight` plus the unchanged KV-pressure waiting penalty; the snapshot's `waiting + running` only breaks ties between equal in-flight counts, and the rotating scan start stays the final tie-break.
- With several API servers the score is unchanged. Explicit `data_parallel_rank`, late-interaction stickiness and session affinity are untouched.
- On DP8/EP8 MI355X with uniform 8k/1k requests: +2.2% throughput at c256 on main, neutral at c1024. Not a win on every workload (chat-like prompts are flat, see below).

## Validation

Imbalance before the change, DP8/EP8, 8k/1k random, closed loop: share of steps with some rank above ceil(c/8) was 56% at c128, 38% at c160, 19% at c256 and 41% at c384. A 20-seed offline simulation of the routing rule gives 46-56% (c64-c384) with the current rule and 0% with this one.

## Details

**Why only for one client.** With several API servers each client sees only its own in-flight requests, so the snapshot is the only view of the others' load and the `max` stays. With one, `inflight` is exact (decremented on `finished_requests`), and the snapshot is a stale copy of it: published at step boundaries, which are about 1.5 s apart during mixed prefill steps on this setup, and still counting finished requests.

**Tie-break.** Using the snapshot as a secondary key keeps it useful when in-flight counts are equal (e.g. at start-up) and does not change which engine has the minimum in-flight count.
