# [Bugfix][Multimodal] Budget encoder compute before video token pruning

[Upstream PR](https://github.com/vllm-project/vllm/pull/63291) · state: open · merged: False

## Original PR description



## Overview

Budget Qwen video encoding by its token count before pruning, while keeping encoder-cache accounting based on retained embeddings. Fixes #63187.

## Claims

- Pruned videos can no longer overfill a step's encoder compute budget by charging only their retained embeddings.
- Duplicate inputs reuse the encoder cache, and priority preemption refunds the original compute cost. Inputs without pruning retain the existing accounting.

## Details

Pruning happens after the vision encoder. Placeholder rewriting previously discarded the original size, so both compute admission and cache allocation used the reduced embedding count. The patch carries an optional `num_encoder_tokens` through prompt updates and placeholder metadata. It uses the same merged output-token units as encoder profiling; absent metadata falls back to the retained embedding count. Cache allocation still uses retained embeddings. No scheduler model-specific branch or GPU synchronization is added.

The intended tradeoff is smaller encoder batches when pruning is enabled; pruning still reduces decoder work and cache occupancy. The user documentation explains this distinction.

Duplicate-work checks on 2026-10-23 found no open PR referencing #63187 or implementing this fix. Searches included `63187 in:body` and `encoder budget pruning`; the related Cosmos3 encoder-CUDA-graph PR #52229 handles graph capture policies, not pre-pruning scheduler accounting.

- vadiklyutiy · COMMENTED · 2026-10-29T12:29:10Z · [source](https://github.com/vllm-project/vllm/pull/63291#pullrequestreview-5697687220)

Thanks for working on this — charging the encoder compute budget with the unpruned count is the right unit, and the budget part does what the issue asks: on the issue's Qwen3-VL recipe every vision-tower call stays within the profiled budget (max 0.938x of the profile, one video per call).

I ran the PR's diff on top of 5d35ce3934a7 and found two inputs that worked before the change and break with it, both on Qwen2.5-VL with `--video-pruning-rate`:

**1. An item whose unpruned count exceeds the whole compute budget is never scheduled.**
The charge is the full unpruned count with no cap, and `can_allocate` now refuses any item above the budget. The input processor still validates only the pruned count, so the request is accepted and then waits forever. Example: one 34-frame 720p video, 20,332 unpruned embeddings against a budget of 16,384. On the base commit it is answered; with this PR the request stays at the placeholder offset (`num_computed_tokens=15`) with no encoder call at all. This hits any long Qwen2.5-VL video, since that processor caps pixels per frame rather than per video, and a Qwen3-VL request with a large per-request `size` too. Charging `min(num_unpruned, encoder_compute_budget)` lets such an item run alone in its step, which is what happened before.

**2. Two concurrent pruned videos now crash in `recompute_mrope_positions`.**
With the higher charge the second video no longer fits in the same step, so its chunk starts right at the placeholder. `recompute_mrope_positions` in `vllm/multimodal/evs.py` does not expect a chunk to start there for media without timestamp tokens and raises `IndexError: index 0 is out of bounds` (line 297 on that commit). Example: two distinct 16-frame videos sent at once. This works on the base commit. The fix is to accept a chunk that starts right after the vision-start token of the chunk's first media.

Separately, the issue's recipe still ends with `RuntimeError: The expanded size of the tensor (0) must match the existing size (3014)` on this PR, but that comes from vllm-project/vllm#62937 (outer `<|vision_start|>` from newer transformers), which vllm-project/vllm#62959 addresses, so it is not this PR's to fix.

On the tests: the end-to-end check that no vision-tower call exceeds the budget, the preemption-restore test and the duplicate-input test are great. I'd add two cases for the paths the new charge creates: an item larger than the budget being scheduled alone, and a chunk that starts at a media placeholder in `recompute_mrope_positions`.
