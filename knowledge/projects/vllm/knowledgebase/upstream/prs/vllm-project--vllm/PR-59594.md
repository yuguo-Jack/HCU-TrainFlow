# [Core][KV Connector] Keep the connector's head order when its KV layout is unsupported

[Upstream PR](https://github.com/vllm-project/vllm/pull/59594) · state: open · merged: False

## Original PR description



## Overview

When the KV connector's requested layout is not supported by every backend, `resolve_kv_cache_layout` now falls back to the first candidate that keeps the requested head/token order, instead of the backends' first choice.

## Claims

- Mooncake (and NIXL) request `LBHNC` so heterogeneous-TP transfers can slice pages by KV head. On a hybrid model whose backends only accept block-outer layouts, the fallback now picks `BLHNC` (head-major) instead of `BLNHC`, so a page can still be cut by head.
- With that layout, prefill TP1 → decode TP2 over Mooncake works for Qwen3.8-Flash-Next. With `BLNHC` the handshake fails.
- No throughput or latency cost on that model at equal TP (tables below).
- Connectors whose requested layout is supported, and runs with `VLLM_KV_CACHE_LAYOUT` set, are unchanged.

The first case fails without the change.

## Details

Mooncake and NIXL request `LBHNC` because a heterogeneous-TP transfer splits each page by KV head, which needs each head's tokens to be contiguous. QSA declares `(BLNHC, BLHNC)`, so `LBHNC` is not a candidate, and the fallback took `BLNHC`, where heads are interleaved per token. At TP2 a page holds one head, so it is still contiguous and equal-TP transfers work. At TP1 it holds two, cannot be sliced, and registers as one row the size of the whole block.

The fallback now picks the first candidate whose head/token order (`KVCacheLayout.is_head_major`, H outside N) matches the request, and otherwise the backends' first choice as before. The other layout requests follow the same rule: offloading and HiSparse ask for head-major layouts, and the example hidden-states connector asks for `LBNHC` to keep each token's data together, so an unsupported request now falls back to a token-major candidate.

Related: #53078 (Mooncake heterogeneous TP for hybrid GDN models) and #59592 (Mooncake block-size handshake), from the same TP1/TP2/TP4 testing. #58380 changes the layout order the worker reports for mixed page sizes and keeps connector requests taking precedence; it does not touch this fallback.

No, I believe `index()` is right here. Each member's value lists the logical dims in physical order, so a dim's physical position is `value.index(dim)`, not `value[dim]`. For example, `BHLNC = (1, 2, 0, 3, 4)` is physically `[B, H, L, N, C]`. The neighboring properties read `value` the same way: `is_block_outermost` is `value[0] == _DIM_B`, `is_block_contiguous` compares `value[-3:]`, and `layer_view_order` iterates over `value`.

`value[_DIM_H]` is the logical dim stored at physical position 2. For the six layouts defined today, the two expressions happen to agree: five of the permutations are their own inverse, and BHLNC gives the same answer either way. They diverge for a layout like `LHNBC = (0, 2, 3, 1, 4)`, physically `[L, H, N, B, C]`. Each head's tokens are contiguous there, and `value.index(2) = 1 < value.index(3) = 2` says so, but `value[2] = 3 > value[3] = 1` would report it as not head-major. Happy to add a comment on the convention next to `_DIM_*` if that would help.
