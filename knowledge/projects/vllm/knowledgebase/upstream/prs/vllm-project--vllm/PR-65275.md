# [Bugfix][MRV2] Use promised max_query_len for encoder-only FULL CUDA graphs

[Upstream PR](https://github.com/vllm-project/vllm/pull/65275) · state: open · merged: False

## Original PR description

## Overview

With the V2 model runner, models whose attention is encoder-only (non-causal, no KV cache) produce wrong outputs when they
are served with `cudagraph_mode=FULL`.

A FULL CUDA graph for mixed batches is captured on a dummy batch that spreads its tokens over many requests (down to one
token each), but it may later replay a batch with one long prompt. `DefaultModelState` already builds the captured
attention metadata from the batch's promised `max_query_len` for this reason. `EncoderOnlyModelState` instead used the
dummy batch's actual largest query length, so the encoder attention kernels in the graph kept a very short
`max_seqlen_q` / `max_seqlen_k`. Prompts that replay such a graph are then computed incorrectly. There is no error.

The fix applies the same rule as `DefaultModelState`: use `input_batch.max_query_len` when the batch sets it, and fall
back to the largest scheduled query length otherwise.

```python
max_query_len = input_batch.max_query_len
if max_query_len is None:
    max_query_len = int(input_batch.num_scheduled_tokens.max())
```

One file changed (`vllm/v1/worker/gpu/model_states/encoder_only.py`), plus a regression test.

## Claims

- Encoder-only models served with `cudagraph_mode=FULL` give the same outputs as eager execution.
- No change for `PIECEWISE` or `NONE`, for decoder models, or for batches without FULL graphs.
- With the fix, FULL graphs are a correct option for these models: slightly faster single-request reads than PIECEWISE,
  about equal under load (table below).

## Benchmark

NVIDIA GB200 (one GPU), 8B non-causal decoder fine-tune, FP8, `max_cudagraph_capture_size=8192`, one exclusive node,
each configuration measured alone.

| | FULL, this PR | PIECEWISE |
|---|---|---|
| 512-token read, concurrency 1, p50 / p95 | 13.4 / 14.8 ms | 14.0 / 16.5 ms |
| mixed prompts (~1.7k tokens), concurrency 1, requests/s | 35.3 | 32.7 |
| same, concurrency 16, requests/s | 41.8 | 42.8 |
| same, concurrency 64, requests/s | 41.1 | 42.3 |

The main point of the PR is correctness: on main, FULL looks faster (12.6 ms for the same 512-token read) only because
it computes the wrong attention.
