# [Feature][CUDAGraph] Add opt-in device-launch instantiation for CUDA graphs

[Upstream PR](https://github.com/vllm-project/vllm/pull/63869) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Adds an opt-in `CompilationConfig.cudagraph_launch_mode` (`"host"` by default, or `"device"`). With `"device"`, the CUDA graphs vLLM captures for the model forward pass are instantiated with `CUDA_GRAPH_INSTANTIATE_FLAG_DEVICE_LAUNCH` and uploaded at capture time; replays are still issued from the host. It is a workaround to try when host-launched graph replays stop making progress, as in pytorch/pytorch#196133.

## Claims

- Opt-in (`-cc.cudagraph_launch_mode=device`); the default `"host"` path is unchanged.
- Wired into vLLM's forward-pass capture sites: `CUDAGraphWrapper` (FULL and PIECEWISE, both model runners), the MRV2 `CudaGraphManager` (including drafters and DBO), breakable piecewise capture, and the MRV1 `UBatchWrapper` (DBO).
- A graph the driver cannot instantiate this way keeps PyTorch's instantiation, with a warning that gives the driver's reason; after capture, each rank logs how many graphs were device-launched and how many fell back.
- Executable graphs are allocated at capture time, so CUDA graph memory profiling accounts for them.
- `"device"` is rejected off CUDA, without `cuda-bindings`, and with features that draw random numbers inside captured graphs (`--enable-mamba-cache-stochastic-rounding`, `VLLM_MOE_ROUTING_SIMULATION_STRATEGY`).

## Validation

Only the graph builder's instantiation differs between the arms (patch and commands below).

| default (`flags=0`) | 12 | 12 |
| `CUDA_GRAPH_INSTANTIATE_FLAG_DEVICE_LAUNCH` + `cuGraphUpload` | 12 | 0 |

## Details

**Why.** pytorch/pytorch#196133 reports CUDA graph replays on B300 that stop completing without an error; the thread reproduces it with a driver-API-only program, so the cause is below PyTorch. Reports differ on driver updates: some say r595/r610 drivers fix it ([1](https://github.com/pytorch/pytorch/issues/196133#issuecomment-6332203748), [2](https://github.com/pytorch/pytorch/issues/196133#issuecomment-6333661312)), others still reproduce it on 595, 610 and 615 drivers ([3](https://github.com/pytorch/pytorch/issues/196133#issuecomment-6333948151), [4](https://github.com/pytorch/pytorch/issues/196133#issuecomment-6335366813)). Where a driver update helps, that is the better fix; the docs say so. This option makes device-launch instantiation, which avoided the freeze in the reproducer above, available without patching PyTorch or vLLM. It does not fix the root cause, and this PR does not include an A/B on a vLLM workload that stalls. The current alternative, patching `torch._C._CUDAGraph` at runtime, affects every graph in the process and depends on torch internals.

**How.** `vllm/compilation/cudagraph_launch.py` adds `DeviceLaunchCUDAGraph`, a `torch.cuda.CUDAGraph` subclass that overrides `instantiate()`, `replay()` and `reset()`. PyTorch 2.14's `capture_end()` calls `instantiate()` while the captured graph is live; the override instantiates it with `cuGraphInstantiateWithParams` (`DEVICE_LAUNCH | USE_NODE_PRIORITY | UPLOAD`) through cuda-bindings, `replay()` calls `cuGraphLaunch` on the current stream, and `reset()` or garbage collection destroys the executable graph. Capture raises if a future PyTorch stops calling `instantiate()` there. Capture sites call `new_cuda_graph(cudagraph_launch_mode)` instead of `torch.cuda.CUDAGraph()`, and both model runners log the per-rank summary at the end of `capture_model()`.

**Limitations.**

- Performance changes in either direction depending on the model (table above). In a microbenchmark, each device-launched replay took a few microseconds longer, independent of graph size, programmatic dependent launch and concurrent branches; the larger end-to-end differences were not investigated further.
- RNG: replays bypass PyTorch's per-replay RNG setup, so random numbers drawn from PyTorch's CUDA generator inside a graph use an undefined seed and offset and repeat on every replay. vLLM's sampling is unaffected (the sampler runs outside the graphs; MRV2 draft sampling uses Triton RNG seeded per request); the two features above that draw random numbers in graphs are rejected.
- NCCL: captured NCCL collectives can contain event nodes, which device launch does not support; such graphs keep PyTorch's instantiation. vLLM does not set `NCCL_GRAPH_MIXING_SUPPORT=0`, which removes them, because with that setting NCCL does not support a non-captured collective during an outstanding graph launch on the same communicator.
- Scope: encoder, model-specific helper and third-party graphs keep PyTorch's instantiation. DBO with device launch was validated manually (above), not in CI.

**Naming.** `"device"` mirrors `CUDA_GRAPH_INSTANTIATE_FLAG_DEVICE_LAUNCH`; launches stay on the host. Happy to rename the field (for example `cudagraph_instantiate_mode`) before merge.

**Follow-up.** An instantiate-mode switch on `torch.cuda.CUDAGraph` (for example `CUDAGraph(device_launch=True)`) would keep PyTorch's RNG setup and replay hooks; `DeviceLaunchCUDAGraph` would then reduce to that argument, with no direct driver calls.

- mispa-ms · comment · 2026-11-04T19:02:34Z · [source](https://github.com/vllm-project/vllm/pull/63869#issuecomment-6639446057)

Thanks @galv . Agreed: this doesn't fix the root cause in https://github.com/pytorch/pytorch/issues/196133, the platform-level coherence problem you described there. It's an opt-in workaround, and here is why it helps:
- The hang is a lost completion between consecutive host-launched graphs on one stream: graph N runs all its kernels, but the next graph never starts.
- Our understanding is that a host-launched graph's completion is signalled through host memory, which is what the coherence bug can corrupt under heavy GPU-to-host writes. A graph instantiated for device launch is scheduled by the GPU and doesn't depend on that signal, so it sidesteps the problem rather than fixing it.
- Evidence (PR Validation): with only the instantiate flag changed, the #196133 reproducer froze in 12/12 host-launch runs and in none of 12 device-launch runs on an affected B300. In our Kimi-K3 serving runs on the same platform, device launch ran clean where host launch stalled.

If a platform fix is on the way, I'm fine closing this. I've also been working on this with the NVIDIA teams internally  in [this NVBug](https://nvbugspro.nvidia.com/bug/6979381); happy to sync offline.
