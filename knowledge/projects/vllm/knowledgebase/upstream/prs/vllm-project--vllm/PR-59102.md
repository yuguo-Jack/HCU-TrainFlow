# [Bugfix][NIXL] Re-save the block that straddles a chunked-prefill boundary in host-buffer mode

[Upstream PR](https://github.com/vllm-project/vllm/pull/59102) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

In NIXL host-buffer mode (TPU, or `kv_buffer_device="cpu"`), a chunked prefill that ends inside a block leaves that block for the next chunk to finish, but the block is never copied to the host buffer again. The decode instance (D) then reads stale KV for up to `block_size - 1` tokens per chunk boundary, with no error. This PR makes `_build_save_meta` (`nixl/base_scheduler.py`) select blocks by token position, so the straddling block is copied again once it is complete.

## Claims

- Each chunk copies the blocks covering `[saved, num_computed + num_scheduled)`. A block that straddles a chunk boundary falls in both ranges, so it is copied again once complete. Example (block size 16, budget 24, 40-token prompt): on main, step 1 copies b0 and b1 with b1 half written, and step 2 copies only b2, so tokens 24-31 never reach the host buffer; with this PR, step 2 copies b1 and b2.
- Spec-decode lookahead blocks are copied only once written (ovidiusm's review).
- A first chunk after a local prefix-cache hit still copies the cached blocks.
- A preempted request starts over when it comes back. It arrives with its whole block table (`is_full_table`, from #60810), so the saved count resets.
- Chunked local attention groups are saved by position too (xuechendi's review). A `UniformTypeKVCacheSpecs` group needs nothing extra: `generate_scheduler_kv_cache_config` gives the scheduler one of its layer specs, which already takes this path.
- SSM state with `mamba_cache_mode="none"`: each chunk rewrites the state block in place, but main copied it only when allocated, so D got the state after chunk 1. The last chunk now copies the slot that `request_finished` hands to D. The hybrid test from snadampal's review found this, and since it is the same bug I fixed it here; I can split it out if you prefer.

## Details

`_build_save_meta` keeps, per partially prefilled request, its block table per KV cache group and the number of tokens already saved (`_reqs_save_state`), and drops them when the last chunk is scheduled or the request is aborted. `saved` starts at 0, which is why a prefix-cache hit's blocks are copied with the first chunk.

Not covered here, and unchanged from main (they keep main's per-step copy):

- SSM groups with `mamba_cache_mode="align"` (prefix caching on). Their block table is not append-only, as `single_type_kv_cache_manager.py` notes, so the state slot can't be found by position.
- `CircularBufferSpec` groups: one ring block per request, rewritten in place, so not positional. If D needs the ring as of the last chunk, it wants the same last-chunk copy as the SSM state; I'd do that as a follow-up with a DSv4.1 test.

Not a duplicate: no open PR changes `_build_save_meta` (#60181 changes the receive path).
