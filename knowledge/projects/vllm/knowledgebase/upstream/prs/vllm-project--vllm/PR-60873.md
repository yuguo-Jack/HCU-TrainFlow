# [Bugfix] Fix depyf incompatibility with Inductor's set_sys_modules

[Upstream PR](https://github.com/vllm-project/vllm/pull/60873) · state: open · merged: False

## Original PR description



## Overview

Any `torch.compile` run with `debug_dump_path` set fails once compilation reaches an autotune code block, because depyf's `load_by_key_path` hook does not accept Inductor's `set_sys_modules` argument. A compatibility shim gives the hook `**kwargs` and forwards them.

Seen on the `PyTorch Fullgraph` step in [Buildkite #93716](https://buildkite.com/vllm/ci/builds/93716/list?jid=01a11edf-b64d-4af0-91f8-60f8f72d7308&tab=output).

## Claims

- Fixes `InductorError: RuntimeError: Failed to run autotuning code block: patched_load_by_key_path() got an unexpected keyword argument 'set_sys_modules'`.
- Not platform-specific. The failing step is a ROCm mirror, but nothing in the cause or the fix is vendor-dependent; it needs only a cold compile cache.
- The shim is conditional on depyf's hook signature, so it disables itself if depyf ever ships a fix.
- The existing depyf test could not catch this. It was one parametrization of `test_custom_compile_config`, which reuses vLLM's on-disk compile cache, so on a persistent agent it usually verified nothing. It is now a separate test that disables the cache.
- Adds a CPU-only unit test that reproduces the incompatibility in 2.3 s, instead of only through a GPU end-to-end run.
- Costs 27 s on `PyTorch Fullgraph` and 11 s on `PyTorch Compilation`, both against budgets of 90 and 30 minutes. The other six parametrizations keep using the cache.
- Not fixed: depyf's other two hooks are unchanged. Both were audited and are already compatible.

## Validation

1× AMD MI355X (gfx950), ROCm 7.2, PyTorch `2.13.0+git733fca1`, depyf 0.20.0, vLLM `19c0bed584`.

| Check | Result |
|---|---|
| New unit tests, CPU only | 6 passed, 2.3 s |
| End-to-end depyf test, cold cache, after the fix | passed, 50.6 s |
| Same, before the fix | failed, 25.8 s |
| Same, before the fix, warm cache | passed, 23.3 s |
| Unit tests with the shim forcibly disabled | 4 of 6 failed |

The last two rows are the ones that matter. The warm pass is why this reached `main`: with a populated cache nothing is compiled, depyf's hook is never called, and the test is green. The forced-disable run confirms the new tests measure the fix rather than the environment.

## Details

`depyf.prepare_debug` replaces `PyCodeCache.load_by_key_path` with a hook that dumps each generated kernel before loading it. The hook's signature is frozen at `(key, path, linemap, attrs)`, and `generate_and_run_autotune_block` now also passes `set_sys_modules`. The resulting `TypeError` is raised inside the `exec` of the tuning block, so it surfaces as an `InductorError` about the autotune block rather than as anything mentioning depyf.

Bumping the pin is not available: 0.20.0 is the last release upstream published, its repository has had no commits since that release, and four pull requests have been open without review. The hook is therefore patched in vLLM, in the way depyf already handles this for `lazy_format_graph_code`: accept `**kwargs` and forward them.

The shim forwards the keyword rather than dropping it. Dropping it would also make the call succeed, while quietly reintroducing the `sys.modules` exhaustion that pytorch#184285 fixed; one of the unit tests pins exactly that. Both vLLM entry points into depyf go through the shim, so neither can miss the patch.
