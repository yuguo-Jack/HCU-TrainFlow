# [Bugfix][Frontend] Accept web_search_call values in Responses include

[Upstream PR](https://github.com/vllm-project/vllm/pull/63230) · state: open · merged: False

## Original PR description

## Overview

Fixes #63185

`/v1/responses` returned 400 for `include: ["web_search_call.results", "web_search_call.action.sources"]`, although the `web_search` tool is accepted. Thanks to the reporter for the clear write-up.

## Claims

- Both values are now accepted. They are ignored, like the other `include` values for built-in tools vLLM does not run.

## Validation

- Before: `ResponsesRequest(input="hi", include=["web_search_call.results", "web_search_call.action.sources"])` raised a `literal_error` for `include.0` and `include.1`.
- New test `test_web_search_include_values_accepted` fails without the fix and passes with it.
- `tests/entrypoints/openai/responses/test_protocol.py`, `test_sampling_params.py`, `test_serving_responses.py`, `test_responses_utils.py`: 134 passed, 1 xfailed. `ruff check` and `ruff format --check` clean.
- Run on an A40 node, but only the pydantic request model was exercised. I did not start a server or run a model, so no end-to-end `curl` check.

## Details

Root cause: `ResponsesRequest.include` in `vllm/entrypoints/openai/responses/protocol.py` is a closed `Literal` list missing these two values from the OpenAI SDK's `ResponseIncludable`. The fix adds them to the list. I did not switch the field to the SDK type, to keep the diff minimal.
