# [Bugfix][Frontend] Pull RunAI model+tokenizer files in a single pass when URIs match

[Upstream PR](https://github.com/vllm-project/vllm/pull/64052) · state: open · merged: False

## Original PR description

## Overview

Fixes #63863

When `model` and `tokenizer` are the **same** object-storage URI (RunAI/S3/GCS), `ModelConfig.maybe_pull_model_tokenizer_for_runai` issues **two** `pull_files` passes over the same bucket:

1. `allow_pattern=["*.model", "*.py", "*.json"]` — a config-only pull
2. `ignore_pattern=["*.pt", 〔该信息已删除，我不再记得〕, "*.bin", "*.tensors", "*.pth"]` — an everything-except-weights pull

The ignore-pattern pass downloads a **superset** of the config-only pass, so every `config.json` / `tokenizer.json` / `*.model` / `*.py` object is listed (`ListObjects`) and fetched (`GetObject`) twice on every engine startup. On large tokenizers with sentencepiece models this doubles cold-start object-store traffic and latency.

## Claims

- On the same-URI path, the config-only pull is skipped and a **single** ignore-pattern pull covers both model-config and tokenizer needs. Object storage round-trips for the duplicated pass are eliminated.
- The different-URI path (`model != tokenizer`) is unchanged: config-only pull for the model, ignore-pattern pull for the tokenizer (still asserted by the existing `test_s3_url_different_model_and_tokenizer`).
- No behavior change when neither URI is an object-storage URI, or when weights were already pulled (`model_weights` guard).

## Validation

- New test `test_s3_url_same_uri_pulls_files_once` asserts exactly one `pull_files` call with `ignore_pattern` for identical URIs, and that `model`/`tokenizer` resolve to the same local directory.
- The patched method was additionally executed against a stubbed `ObjectStorageModel` across all four paths: same URI (1 pull, ignore-pattern), different URIs (2 pulls, allow-then-ignore), non-object-storage URIs (no pull), and the already-pulled guard.
