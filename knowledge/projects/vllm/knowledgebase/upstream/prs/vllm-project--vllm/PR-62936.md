- simon-veitner-redhat · comment · 2026-10-22T13:09:28Z · [source](https://github.com/vllm-project/vllm/pull/62936#issuecomment-6341561325)

Thanks Roberto, this looks good. The persistent and filtered paths are now exact where main is not, and most shapes got faster. I tested on B200 and found two bugs. Three small commits are on [simon-veitner-redhat:persistent-topk-exact-fixes](https://github.com/LopezCastroRoberto/vllm/compare/fix/persistent_exact_topk...simon-veitner-redhat:vllm:persistent-topk-exact-fixes) if you want to cherry-pick them.

**1. Shared-memory race after `radix_topk`** (persistent_topk.cuh, end of `radix_topk`). The tie loop at the end reads `shared_ordered`, and there is no barrier after it. When the CTA's next row takes the medium path, it zeroes the same shared memory before its first barrier, so warps still in the tie loop can read the overwritten values. Under `compute-sanitizer --tool racecheck` at k=2048, a radix row followed by a 16K row gives 2221 hazards on this PR and 0 on main. A radix row followed by a 4K row already races on main (1857 hazards). One `__syncthreads()` after the loop gives 0 hazards in both cases, and its cost was within noise (0-1.8% on 24 long-row configs). At full speed I saw no wrong outputs in 2000 iterations, so racecheck is the way to see it.

**2. Misaligned vector loads on offset views** (topk.cu, `vec_size` selection). `vec_size` is picked from the stride alone. A view `x = base[:, off:off+L]` keeps `stride % 4 == 0` but moves the base pointer by 4 or 8 bytes. With that, 1x4096 k=512 (4-byte offset) and 4x16384 k=2048 (8-byte offset) fail with `CUDA error: misaligned address` on the PR head, while main returns correct results. The commit also checks the base pointer and falls back to narrower vector loads. The filtered path at 64 rows and the radix case at 40000 already fault on main with these views; `FilteredTopKRaggedTransform` needs the same check.

The branch also ports the four #59645 overflow tests (special bins, -inf ties, mixed lengths, staging fallback) to run over `WORKSPACE_TOPK_BACKENDS`, so persistent and filtered get them too.

Some notes and questions:
- `OverflowRecovery::kDisabled` is unused but is still the default template argument, so a new caller would silently get the inexact path. Could it be dropped? (In my build, also switching the fallback to `exact_topk_rescan_cold` made 4K-8K rows at k=2048 7-16% slower through code layout, so I left that alone.)
- The description says the non-overflow path is unchanged, but it was rewritten. It is faster (8-34% on short rows, persistent 1-32 rows at 1K-32K), so please mention it in the description.
- Narrow or all-equal scores on the filtered path (64 and 256 rows at 8K and 32K) are 10-72% slower than main, for example 64x32K k=512 goes from 13.1 to 22.1 us. Main is inexact there. A min==max fast path would cover it: if the threshold bin's min equals its max, any of its elements are correct and the rescan can be skipped.
- Can `try_sampled_exact_topk` be reached? As far as I can tell, topk.cu sends every shape that would need it to `sampled_topk_kernel`.

End to end on DeepSeek-V4-Flash TP2 with `--sparse-indexer-topk-backend persistent`: gsm8k 20-shot 0.9553 vs 0.9560 on main, serve 8192/512 at concurrency 128 2451 vs 2449 tok/s.
Overflow recovery never fired on real data, so the new recovery paths are covered only by the synthetic tests.
