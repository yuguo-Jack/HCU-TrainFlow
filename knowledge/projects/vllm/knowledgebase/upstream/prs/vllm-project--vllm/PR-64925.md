# [XPU][Qwen4Exp] Run the QSA side-cache ops and indexer prepare on XPU

[Upstream PR](https://github.com/vllm-project/vllm/pull/64925) · state: open · merged: False

## Original PR description



## Overview

Part of #54595 (item 5). Needed by the QSA follow-up to #61607.

The Qwen4Exp QSA kernels under `qwen4_exp/nvidia/` are Triton and run on Intel XPU, but CUDA-only checks keep them off it, and since #60992 an FP8 main KV cache cannot build on XPU at all. This lets the side-cache store and compression kernels accept XPU tensors, enables the fused QK-norm/RoPE/gate and fused `qsa_prepare` on XPU, makes the unfused indexer path use the platform's Gemma RMSNorm and RoPE instead of flashinfer and `vllm_flash_attn`, and gives the FP8 KV cache its e4m3 view on XPU. CUDA and ROCm behaviour is unchanged.

Nothing on main calls these ops on XPU yet: `qwen4_exp/__init__.py` refuses XPU, and #61607's XPU model is dense-only. This PR makes the shared ops and their existing tests run on XPU, so the follow-up that wires QSA into the XPU model is a model-only change.

## Claims

- `qsa_store_cache_rows` and `qsa_compress_groups_with_ratio` run on XPU tensors; CPU tensors are still rejected.
- On XPU, `use_fused_qk_norm_rope_gate` is True under the same conditions as on CUDA, which also enables the fused `qsa_prepare`.
- The unfused path needs neither flashinfer nor `vllm_flash_attn` off CUDA; on CUDA it makes the same calls as before.
- With an FP8 KV cache on XPU, the attention impl, the fused-prepare gate and the sparse-attention warmup use the `float8_e4m3fn` view instead of the uint8 bytes, so the kernel no longer reaches the PTX byte decode added in #60992 (which fails to build on XPU).
- The QSA kernel tests in `test_qsa_reference.py` and `test_qsa_prepare.py` run on XPU, except block selection (CUDA-only top-k; follow-up stacked on this PR).

## Validation

CPU (x86, torch 2.14.0+cpu, `VLLM_TARGET_DEVICE=cpu`):

```
pytest tests/models/qwen4_exp/test_qsa_reference.py tests/models/qwen4_exp/test_qsa_prepare.py
main:     18 passed, 72 skipped
this PR:  18 passed, 72 skipped   (kernel tests skip without CUDA/XPU)
```

XPU (1 × Intel Arc Pro B70, torch 2.14.0+xpu, triton 3.8.0+xpu, vllm-xpu-kernels 0.1.16), same command:

| tree | result |
|---|---|
| this PR's tests on main's code | 18 failed, 49 passed, 23 skipped (QSA cache stores refuse non-CUDA tensors; flashinfer missing in the unfused path; every `test_qsa_fused_prepare_matches_unfused` case) |
| this PR | 67 passed, 23 skipped (the 23 are block selection, CUDA-only until the follow-up) |

FP8 KV view: on main, the four `test_qsa_sparse_paged_attention_correctness[*_fp8]` cases pass when the test hands the kernel `float8_e4m3fn` caches, and all four fail with `ZE_RESULT_ERROR_MODULE_BUILD_FAILURE` / `Constraints for inline assembly cannot be validated (in file: qsa.py:37)` when the caches are handed over as the uint8 view the XPU impl used before this change. Main's sparse-attention warmup compiles either way (the failure appears at module build on launch), so it does not show the bug. The impl path itself needs the QSA XPU model (follow-up to #61607) to run end to end, so no CI-reachable test fails without this commit.

FP8 indexer tolerance: `test_qsa_fused_prepare_matches_unfused` is unseeded, and in its `indexer_dtype1` (FP8) cases the fused and unfused paths on XPU occasionally differ by more than one code step. Over 30 seeds × 24 comparisons, 14 comparisons had exactly one element out of range, at most 4 code steps and 2^-7 absolute, near the bottom of the e4m3 range (for example fused 0.0 vs unfused 2^-7). The XPU tolerance is 2^-7; CUDA keeps 2^-8.

CUDA: not run. Every changed line keeps the CUDA branch identical or is behind `current_platform.is_cuda()` / `is_xpu()`; `fp8_kv_view_is_native()` is `has_device_capability(89)` on CUDA and ROCm, as before. The CUDA step in `test_areas/models_basic.yaml` runs both test files.

`pre-commit run --from-ref upstream/main --to-ref HEAD`: all hooks pass.

## Details

1. `nvidia/ops/qsa.py`: the two `not tensor.is_cuda` guards become `tensor.device.type not in ("cuda", "xpu")`; new `fp8_kv_view_is_native()` (XPU or sm_89+).
2. `nvidia/qsa.py`: `use_fused_qk_norm_rope_gate` accepts `current_platform.is_xpu()`, as `Qwen3NextAttention` already does for the same `fused_qk_rmsnorm_rope_gate` kernel; the FP8 view and the fused-prepare FP8 gate use `fp8_kv_view_is_native()`.
3. `nvidia/qsa_indexer.py`: `apply_qsa_rope` calls `apply_rotary_emb.forward_cuda` on CUDA and the `ApplyRotaryEmb` module (CustomOp dispatch, `forward_xpu` on XPU) elsewhere; `_gemma_rmsnorm` calls flashinfer on CUDA and the `GemmaRMSNorm` module elsewhere.
4. Tests: the device comes from `current_platform.device_type`; `requires_qsa_kernels` covers CUDA and XPU; the four block-selection tests stay CUDA-only until the top-k dispatch lands; `test_qsa_unfused_cache_update_ignores_padded_qk` uses a real `GemmaRMSNorm`; the prepare test's Gemma RMSNorm reference is flashinfer on CUDA and a torch reference elsewhere; the FP8 compare tolerance is 2^-7 on XPU.

Two commits: the portability change with its tests, and the FP8 view.

CI: no Intel CI step runs `tests/models/qwen4_exp/`; the XPU results above were run locally.

Why this is not a duplicate: searched open and merged PRs on 2026-10-31 for "QSA XPU", "Qwen4Exp XPU", "qwen4_exp is_cuda", "qsa_store_cache_rows", "qsa fp8 inline asm". #61607 adds a dense XPU model and leaves the QSA ops alone; #57294 adds a separate CPU backend; #62298 and #62589 are ROCm. #54595 reports the problem without a PR.

AI assistance (Claude) was used to port the change from our B70 tree, write the tests and draft this text. I reviewed every changed line and ran the tests above.
