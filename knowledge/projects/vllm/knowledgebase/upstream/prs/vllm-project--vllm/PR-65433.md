# [Perf][MiniMax-M3] Raise the fused MoE finalize + all-reduce cap from 32 to 128 tokens

[Upstream PR](https://github.com/vllm-project/vllm/pull/65433) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

This extends MiniMax-M3's existing fused MoE finalize (`FUSED_MOE_FINALIZE_MAX_TOKENS = 32` on `main`) to decode steps of up to 128 tokens.

On NVIDIA (SM100 family, TP without EP, NVLink multicast), MiniMax-M3 leaves a decode step's MoE top-k finalize to the next layer's input norm. A fused kernel there does the finalize + shared-expert add + TP all-reduce (one-shot multicast Lamport) + Gemma RMSNorm + MXFP8 quantization of the `qkv_proj` input. On `main` this applies only up to 32 tokens.

Above 32 tokens, each MoE layer runs a slower tail:

- the MoE's own finalize;
- a separate shared + routed add;
- FlashInfer's two-shot all-reduce + RMSNorm;
- a separate MXFP8 quantization.

This PR raises the cap to 128 tokens at TP ≤ 4 (64 at TP8, see Details). That covers decode steps of up to 16 requests with 7 speculative tokens (MiniMax-M3.1 Flash's DSpark recipe), or 32 requests with 3. The kernel and its numerics are unchanged; only the cap, its scaling with TP, a batch-invariance guard and the test move.

## Claims

- **Cheaper per-layer MoE tail on GB300, TP4.** The whole tail was measured in situ: from the end of the routed fc2 to the start of the next `qkv_proj` GEMM, covering finalize, shared add, all-reduce + norm and MXFP8 quantization. Values are the median per layer over about 2500 layers, nsys, base → fused (cap 512), three nodes:

  | tokens | base (µs) | fused (µs) |
  |---|---|---|
  | 64 | 15.6 / 15.7 / 15.5 | 7.1 / 7.9 / 7.6 |
  | 128 | 18.3 / 18.0 / 17.3 | 11.0 / 11.7 / 11.8 |
  | 256 | 23.0 / 22.9 / 23.3 | 22.3 / 22.2 / 22.1 |

  One-shot traffic grows with the batch, so the gain shrinks from about 6.5 µs per layer at 128 tokens to about 0.8 µs at 256, where the step period does not improve. The cap therefore stops at 128. The microbenchmark below shows the same trend for the fused kernel alone.
- **End to end** (MiniMax-M3.1 Flash, TP4, DSpark K=7, GB300, decode step period, three nodes; base → cap raised):

  | concurrency | tokens / step | node 1 | node 2 | node 3 |
  |---|---|---|---|---|
  | 8 | 64 | −3.3% | −3.5% | −3.0% |
  | 16 | 128 | −3.2% | −1.8% | −5.1% |
  | 32 | 256 | (unchanged path with a 128 cap) | | |

  Concurrency 1 (8 tokens) already took the fused path.
- **Numerics** are the same as the existing ≤ 32-token path. The test compares each output with the unfused all-reduce + norm + MXFP8 reference: bitwise residual, and ≥ 99% of codes and of the real rows' scales equal. The fused path rounds differently from the regular path above the cap, so it is off under `VLLM_BATCH_INVARIANT`.
- **Memory:** the Lamport mailbox grows from 3 × TP × 32 to 3 × TP × 128 rows: 18.9 MB of symmetric memory per GPU for hidden 6144 at TP4.

The fused output equals the unfused all-reduce + norm path bitwise (BF16 residual, MXFP8 codes and scales) at every size up to the cap. A 12-request smoke serve completed 12/12 and the log reported "… for up to 128 tokens (56 layers)". Full GSM8K (1,319 questions, concurrency 64, two runs per arm, one node): greedy `main` 0.9689 / 0.9689, this PR 0.9682 / 0.9697; temperature 1, top-p 0.95: `main` 0.9636 / 0.9689, this PR 0.9666 / 0.9606. The standard error per run is about 0.005.

**Tests:** `tests/distributed/test_custom_all_reduce.py::test_finalize_all_reduce_gemma_norm_mxfp8_matches_unfused_path` builds the op with the model's TP4 cap (`fused_moe_finalize_max_tokens(4)` = 128). It runs batches 1, 6, 3, 17, cap/2, 2, cap, cap − 1, 1 through one mailbox, eagerly and under CUDA-graph replay, and checks that cap + 1 is rejected. It passes on 4 GB300 ranks (run through torchrun, since the image has no Ray), both before and after the rebase (after: the rebased source merged onto the image's files). A new optional (nightly) `(4xB200) MiniMax-M3 Fused MoE Finalize` CI step runs it; no step ran it before.

**Serving:** the InferenceX GB300 recipe (TP4, DSpark K=7, NVFP4 KV, FULL_AND_PIECEWISE), agentic-like code prompts of about 22k tokens, nsys decode step period. Three nodes, base then patched on each, with the cap at 512 (identical to 128 for these batch sizes):

## Details

- `FUSED_MOE_FINALIZE_MAX_TOKENS`: 32 → 128, measured at TP4.
  - Each rank reduces `tp_size` rows per token, so `fused_moe_finalize_max_tokens(tp_size)` scales the cap by 4 / `tp_size` above TP4. That gives 64 at TP8, the same rows reduced per rank as TP4 at 128. TP8 and B200 were not measured.
  - The model passes that one value to both the experts and the op.
  - Calls above the cap, and experts that split a call across launches (which lower the cap themselves), keep finalizing in the MoE as before.
- `supports_fused_moe_finalize` returns False under `VLLM_BATCH_INVARIANT`, as DeepSeek-V4.1's fused tail does.
- **Follow-up:** steps of 256 tokens (32 requests × 8) need a two-shot variant of the fused kernel (reduce-scatter + all-gather, with the finalize and MXFP8 output fused); a follow-up PR adds it. The post-attention all-reduce stays on FlashInfer's two-shot + separate RMSNorm above 32 tokens. Forcing FlashInfer's one-shot MNNVL path there was slower at 64–256 tokens.
- **Related:** NVIDIA's InferenceX MiniMax-M3.1 work also tried raising this cap, to 64 tokens; the measurements above put the crossover at TP4 between 128 and 256. #64957 adds a general compile-time MoE finalize + all-reduce + RMSNorm fusion pass; this PR only changes MiniMax-M3's existing model-level fusion.
