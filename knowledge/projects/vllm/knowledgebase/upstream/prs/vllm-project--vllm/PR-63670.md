# [Core][Mamba] Drop the align-mode prefill chunk split

[Upstream PR](https://github.com/vllm-project/vllm/pull/63670) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Exploratory draft. It removes the Mamba "align" prefill chunk split, so every prefix-cached Mamba state comes from the backend's internal prefill checkpoint (Kimi-K3 KDA, GLM-5.3-Flash, Mamba2) or from a running slot that ends exactly on a block boundary. The goal is to see how much core simplification this buys.

Not every backend or case supports internal checkpoints yet. This PR does not cover them; see Limitations.

## Claims

- **Core shrinks by 328 net lines** (`vllm/v1/core`: +109 / −437). The whole change is +582 / −2696.
  - Removed: `Scheduler._mamba_block_aligned_split` and its five flags.
  - Removed: the Mamba producer partial tail (owner CoW-on-continue, `BlockPool.move_block_hashes`, `finalize_partial_tail_offload(s)`).
  - Removed: `--enable-mamba-shared-prefix-checkpoint`.
  - Removed end-to-end: the connector API `register_finished_partial_tail`.
- **Prefix-cached Mamba states stay correct without the split.** The new `MambaManager.published_block_mask` never publishes a running slot left at a mid-block state. Without it, removing the split poisons the cache (#43559) even under the default `prefix_cache_retention_interval=0`. This shows up both in a unit test and end-to-end on three real models (see Validation).
- **Store connectors never see a stale slot.** Mooncake store, UMBP, offloading and SimpleCPU all store Mamba state from `take_boundary_state_offloads` or block hashes, so the mask covers them.
  - UMBP now adds the full-attention tail page for sub-block boundaries in `_add_boundary_state_plans`. This used to happen only in the removed `register_finished_partial_tail`.

The new test drives `KVCacheManager.allocate_slots` with raw token budgets. It uses the worker's `compute_mamba_prefill_checkpoints` to model where states land, and asserts that every hashed Mamba slot holds the state its hash claims.

It covers several configurations:
- Mamba blocks of 1600, 1536 and 12288.
- With and without EAGLE.
- Dense and `0` retention.
- Partial hash hits off.
- Multi-module MTP. Here the cacheable token count stops short of the chunk end, so the chunk end is now recorded at allocation.

**End-to-end poisoning repro** (GB200, offline `LLM`, greedy, `mamba_ssm_cache_dtype=float32`):
1. Each of 8 distinct text slices is a prompt of `P = 2·bs + 50` tokens.
2. With `max_num_batched_tokens = 1.5·bs`, the first chunk leaves the running state at `1.5·bs` in column 1, and the second chunk crosses `2·bs`.
3. Each prompt is sent twice, and the resend is compared with a no-cache run.

`--no-mask` monkeypatches `published_block_mask` to a no-op, i.e. the split is removed with nothing in its place.

| Model (backend) | `bs` | resend hit, mask | resend hit, `--no-mask` | resends diverging within 8 tokens, mask / `--no-mask` |
| --- | --- | --- | --- | --- |
| Jamba-tiny-dev (Mamba1, no checkpoint) | 144 | 0 | 288 (= 2·bs) | 0/8 / 3/8 |
| Qwen3.5-0.8B (GDN) | 576 | 0 | 1152 | 1/8 / 4/8 |
| granite-4.0-h-tiny (Mamba2) | 784 | 0 | 1568 | 2/8 / 8/8 |

Without the mask, every resend restores the `1.5·bs` state as if it were the `2·bs` state. With the mask nothing stale is published, so the resend misses. The few divergences with the mask happen with no cache hit at all; they come from the different chunking versus the no-cache reference. The miss itself is the unaligned-chunk-start limitation below.

Model evals were not run. This is a draft for design review.

## Details

**Root cause the split guarded against.** The worker writes the running state into column `(seq_len - 1) // block_size` at every chunk end. `MambaManager.cache_blocks` hashes full blocks by position. A chunk that ends mid-block followed by one that crosses the boundary therefore publishes a truncated state. The new mask restricts what a prefill step publishes:
- the internal-checkpoint column;
- the running column, only when the chunk ended exactly on its block boundary.

Decode is unchanged: the slot advances in place, and spec-decode postprocess fills boundary slots.

**`test_mamba_prefix_cache.py` step tables.** They encoded the split: a 2B prompt ran as `[0,B)+[B,2B)`, and an over-budget chunk was cut back to 5B. They now expect whole chunks: `[0,2B)`, and `[0,3072)+[3072,10B)` for a 10B prompt. The identical-prompt hit check now expects a hit only from a backend with internal checkpoints. Triton GDN exports no state at the replay boundary B of a 2B prompt, and retention `0` does not keep the 2B state.

**Breaking change.** `--enable-mamba-shared-prefix-checkpoint` is removed outright, and `docs/features/automatic_prefix_caching.md` is updated. If this direction lands, it should go through a deprecation cycle instead.

**Limitations (intentionally not handled here):**
- **Short prompts.** The checkpoint column is fixed at `cdiv(seq_len, bs) - 2` and must exceed the initial-state column. A prompt shorter than about two Mamba blocks therefore exports no reusable sub-block state. The prompt-129 case of `test_dcp_fine_hit_retention_uses_hash_alignment` (expected hit 128, got 0) is dropped for now. Fixing it needs a non-positional checkpoint slot, which should restore the case.
- **Unaligned chunk starts.** A chunk whose start is not hash-aligned (and, for FlashInfer GDN, not on the checkpoint grid) gets no checkpoint. So the final chunk of a prompt longer than `max_num_batched_tokens` loses its replay-boundary state unless the budget is a multiple of the hash block; `--prefix-match-unit` works around it. This lowers the hit rate but does not affect correctness.
- **Shared-prefix junctions** are no longer checkpointed.
- **Backends without internal checkpoints** (`num_prefill_checkpoint_blocks == 0`, e.g. Triton GDN, Mamba1) cache only states at block-aligned chunk ends. Under the default retention `0`, a prompt prefilled in one chunk keeps nothing reusable.
- **NIXL host buffer** (`kv_buffer_device=cpu`) saves only each step's newly allocated blocks.
  1. P prefills `[0,20)` then `[20,30)` with `bs=16`.
  2. Step 1 saves the Mamba running block (state@20) and attention block 1.
  3. Step 2 allocates no new block, so neither is saved again.
  4. D receives state@20.

  Pure attention already has the attention half of this problem under unaligned chunked prefill. This needs a NIXL-side re-save at the final prefill step.

**Not a duplicate.** `gh pr list --search "mamba_block_aligned_split"` returns nothing. Related open PRs (#62479, #63610, #60659) build on the split or on boundary hand-offs rather than removing the split.
