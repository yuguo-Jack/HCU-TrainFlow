# [Bugfix][Benchmark] Parse SSE data fields across streaming backends

[Upstream PR](https://github.com/vllm-project/vllm/pull/64143) · state: open · merged: False

## Overview

Reuse the existing SSE data-field extractor in the Python completions, chat-completions, and audio benchmark clients, so valid event metadata and comments do not turn successful responses into failed benchmark requests.

## Claims

- Accept metadata/comment lines, `data:` without an optional space, and multiline JSON data within each message emitted by the existing stream handler, in all three streaming clients.
- Ignore events without a nonempty data payload while continuing to fail on malformed JSON in the extracted payload. See the existing framing limitation below.
- Preserve generated text (including Unicode line separators), token accounting, and existing timing behavior; no model or kernel changes.

## Validation

Validated on macOS / Apple M4 CPU with Python 3.12.13 and Torch 2.14.0. Baseline: `405276b8f0354ddf8686aa5da2f905e76427f1a8`, with the new tests present and the production module unchanged.

## Details

The three clients previously stripped only a leading literal `data: ` prefix. Other SSE fields therefore reached `json.loads`, while skipping whole messages starting with `:` could discard valid data following a comment. This change reuses `_extract_sse_data`, already used by the Responses client, without changing its implementation or the shared stream-framing handler. Documentation is updated under Online Benchmark.

Duplicate checks found no matching open Python payload-extraction fix. Related work is distinct: #61534 and #61576 modify stream framing; #57519 detects error objects inside JSON payloads; #60177 changes the Rust benchmark client. This patch does not modify any of those mechanisms.

Known framing limitation, raised in [this review comment](https://github.com/vllm-project/vllm/pull/64143#issuecomment-6456047182): the existing handler can emit a complete JSON value before the event's blank-line delimiter. A single event containing two separate JSON values on two `data:` lines fails JSON parsing when delivered together, but can be processed as two messages if an HTTP chunk ends immediately after the first value. This was reproduced locally at the real handler/extractor level, and the handler's AST is identical between the tested baseline and `78b9199`. Strict multiline-event validation across arbitrary chunk boundaries is not claimed or fixed here. The benchmark documentation now records this limitation; framing remains outside this patch's scope.

- adenzhou1350 · comment · 2026-10-27T23:22:37Z · [source](https://github.com/vllm-project/vllm/pull/64143#issuecomment-6456047182)

Independently checked `78b9199` on Linux: the metadata fix works for completions and chat. One pre-existing framing caveat to the malformed-JSON claim:

```text
data: {"choices":[{"text":"A"}]}
data: {"choices":[{"text":"B"}]}

```

This is one SSE event; joining its data fields with a newline does not produce a single valid JSON value. Sending it in one HTTP write correctly produces `JSONDecodeError`. Sending the exact same bytes in two writes, split immediately after the first `}` and before the single newline, returns `success=True` and text `AB` instead. A normal usage event and `[DONE]` follow in both cases.

I reproduced both outcomes through the actual completions/chat request functions and an aiohttp loopback server. Observing the real handler calls confirms that the first JSON is emitted before the event delimiter arrives. Independently delimited events and a split UTF-8 character are healthy controls.

The same behavior exists at base `4d95f222`, so this is **not a regression from this PR**. Since #61534/#61576 already cover framing work, this may be best recorded there or kept as an explicit limitation rather than expanding this payload-extraction patch.

Scope: exact complete request module, Python 3.12.10, aiohttp 3.14.5; not a full vLLM build, audio/model test or official CI.
