# [Bugfix][LoRA] Keep failed activations retryable

[Upstream PR](https://github.com/vllm-project/vllm/pull/61618) · state: closed · merged: True

## Original PR description



## Overview

Commit LoRA activation metadata after all layer-loading calls return successfully. A synchronous loading exception currently leaves the adapter marked active, so a retry can skip loading and serve partially copied weights.

## Claims

- Failed activation propagates its exception without marking the adapter active or assigning its GPU slot.
- Retrying a cached adapter executes loading again. An unchanged malformed adapter keeps failing instead of falsely succeeding.
- Successful loading, capacity checks and LRU eviction retain their existing behavior.

## Validation

The CPU regression and real GPU-engine validation below were run on `de8828bf36545fdd414cfd84b1d1480e0c627b7a`. After removing the submitted test and the maintainer's subsequent merge of `main`, the production `vllm/lora/model_manager.py` remains byte-identical at `73be6d45dcc0a15e93edb882ad272d2478f5399a`. The runtime results below predate that merge.

The added regression has been removed from the PR at the maintainer's request. The recorded local regression used the existing manager fixtures and real layer buffers: an incompatible second-layer A tensor made `set_lora` raise; after restoring it, activation had to succeed and copy the restored weights. Both manager implementations were covered. The test file now matches the base exactly.

The local regression failed on the original source for both managers. On the patch, it and the existing selected lifecycle checks passed. After removing the submitted test, all applicable affected-file pre-commit hooks, including type checking and CI test tethering, passed again.

Real multiprocess GPU-engine validation used NVIDIA L20, TP=1, default Model Runner V2, FP16, eager mode, rank 8, two GPU/CPU adapter slots, prefix caching off, and eight prompts with eight greedy output tokens each. The checkpoint is a deterministic, locally generated OPT model with two layers, hidden size 64 and FFN size 128.

The isolated harness runs the original and patched manager sequentially:

```bash
.venv/bin/python run_engine_validation.py
```

| Engine check | Original | Patched |
| --- | --- | --- |
| One-time exception at the second LoRA layer | Failed adapter remains active; slot assigned | Failed adapter inactive; slot unassigned |
| Same-ID retry compared with a normally loaded reference | 0/8 matching token sequences; maximum selected-logprob difference 0.2615957 | 8/8 matching token sequences; logprob difference 0 |
| Actual malformed checkpoint loaded twice through worker `add_lora` | First call raises; second falsely succeeds | Both calls raise the shape error |
| Replacing the malformed adapter with valid weights | Matches normal reference | Matches normal reference |

Worker extension methods carry primitive RPC arguments and construct `LoRARequest` inside the worker; pickle-based RPC serialization stays disabled. The one-time failure is controlled fault injection, not a hardware-OOM experiment. The malformed-checkpoint check uses an actual tensor-copy shape error.

The engine validation used commit `de8828bf36545fdd414cfd84b1d1480e0c627b7a`, based on `8a8e2baa02cdd3d98ee99dbead0a8c9943a97410`; native components come from the official `be4ce2e50545c6c1bf13f224022aeb2bcf0c0070` nightly wheel. Compiled sources and the affected LoRA files are unchanged between that wheel commit and the base. GPU runtime: Torch 2.14.1+cu130, Transformers 5.19.0 and Triton 3.8.0. Multi-GPU serving was not tested. These checks establish loading/retry correctness; no accuracy or throughput improvement is claimed.

## Details

Only the two metadata writes move. The submitted test was removed in `6e8d27da` following review; the effective PR diff now contains only this production file. The existing copy/reset loop and return contract are unchanged, with no additional allocation or synchronization. Physical buffers may still contain partial data after an exception, but no adapter ID is assigned to that slot; the next activation executes the existing loading/reset loop.

Open-PR searches and relevant diffs were checked. #60039 validates module-name matching, #60222 compensates failed loads in the Rust frontend, and #59819 exposes slot read/update operations. They do not defer the worker manager's activation commit after a synchronous layer-loading exception. Related overlap-loading and cache-observability PRs were also checked.
