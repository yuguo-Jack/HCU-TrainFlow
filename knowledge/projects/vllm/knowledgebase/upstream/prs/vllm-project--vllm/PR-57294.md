# [CPU] Add Qwen3.8-Flash-Next CPU backend

[Upstream PR](https://github.com/vllm-project/vllm/pull/57294) · state: open · merged: False

## Original PR description


## Purpose

This PR adds a native x86 CPU backend for Qwen3.8-Flash-Next (`Qwen4ExpForCausalLM` and `Qwen4ExpForConditionalGeneration`) using Model Runner V2.

The CPU backend:

- implements the Qwen4Exp model, model state, HyperConnection, QSA, PLE, and N-gram embedding paths under the CPU-owned model package;
- uses Triton-CPU kernels for QSA scoring, index expansion, side-cache compression and storage, sparse attention, PLE N-gram hashing, PLE gating, PLE short convolution, and HyperConnection operations, while shared QSA metadata, top-k selection, and main KV-cache updates use PyTorch CPU tensor operations;
- supports block-FP8 checkpoints with BF16 activations and BF16 QSA KV cache;
- pads serialized block-FP8 MoE experts when needed so valid tensor-parallel partitions remain block-aligned;
- supports tensor parallelism, compiled and eager execution, and prefix caching, with TP1 and TP2 validated; and
- extends the dedicated CPU Buildkite shard with focused CPU configuration,
  HyperConnection, PLE, and QSA tests.

### Implementation provenance

This backend is a CPU port of the existing Qwen4Exp implementation rather than an independent model implementation. The model, QSA/indexer, PLE, HyperConnection, model-state, and N-gram embedding structure was copied and adapted from the existing NVIDIA and AMD backends. The CPU Triton kernels also reuse and adapt the corresponding kernel math: HyperConnection and sparse QSA attention draw from both vendor implementations; QSA scoring, expansion, cache-store, and compression kernels are adapted primarily from the AMD implementation; and PLE gating, N-gram hashing, and short-convolution kernels are adapted primarily from the NVIDIA implementation.

The CPU copies replace backend-specific launch and runtime behavior with Triton-CPU thread configuration, CPU cache layouts and buffer shapes, CPU-resident PLE weights, and PyTorch CPU tensor operations for metadata and top-k selection. They intentionally omit CUDA/ROCm-only behavior such as PDL, UVA, asynchronous prefetch, and GPU-specific top-k paths. The duplicated host-side orchestration and kernel math are marked with scoped follow-up comments where common extraction may become practical.

The CPU model path is kept separate from the AMD and NVIDIA implementations. The shared QSA metadata entry point retains the Triton path for CUDA/ROCm tensors and selects the PyTorch implementation for CPU tensors.

Current CPU support is intentionally limited to:

- x86-64 with an active Triton-CPU backend;
- Model Runner V2;
- text-only execution with `--language-model-only`;
- pipeline parallel size 1; and
- BF16 activations and BF16 QSA KV cache.

Speculative decoding, LoRA, multimodal/MRoPE execution, dual-batch overlap, microbatching, and pipeline parallelism are not supported by this initial CPU backend and fail with explicit errors.

The unquantized/BF16 path is covered at the configuration and PLE embedding unit level, but this PR does not claim end-to-end validation of a BF16 checkpoint.

This work does not duplicate an existing PR. #53896 added the original Qwen3.8-Flash-Next accelerator support for NVIDIA and AMD. #53899 and #54431 concern CPU offload for accelerator execution rather than a native CPU model backend. The optimization tracker #55922 also lists CPU offload as a separate TODO; it does not track native CPU execution.

## Compiled mode silently skips the PLE short conv

### Cause

- `Qwen4ExpPLELayer._short_conv` in `vllm/models/qwen4_exp/cpu/ple_layer.py`
  (line 309) is plain Python. It reads
  `get_forward_context().attn_metadata` and returns early when it is `None`
  (line 311). `forward` calls it directly (line 383), inside the
  `@support_torch_compile` model (`cpu/model.py:513`).
- On CPU, compilation runs in `CompilationMode.DYNAMO_TRACE_ONCE`
  (`vllm/platforms/cpu.py:340`), and all guards are dropped
  (`guard_filter_fn = torch.compiler.skip_all_guards_unsafe`,
  `vllm/compilation/wrapper.py:121`). So the branch taken on the first trace
  stays in the graph for good. The first trace happens during warmup, when
  there is no attention metadata, so the `return` gets baked in.
- `@eager_break_during_capture` does not protect this path on CPU. This PR
  disables breakable cudagraphs on CPU (`vllm/config/vllm.py:112`), and in
  that case the decorator returns the function unchanged
  (`vllm/compilation/breakable_cudagraph.py:97`).
- The AMD backend avoids the problem by running `_short_conv` through a custom
  op (`amd/ple_layer.py:1059`, `qwen4_exp_ple_short_conv`).

With this bug the dilated short conv never runs and its conv state is never
written. The model still produces fluent text, so nothing looks broken unless
you compare against eager.

### Minimal reproduction of the mechanism

We compiled a function that calls the layer, with `fullgraph` and
`skip_all_guards_unsafe`. The first call ran with `attn_metadata=None`, and
later calls ran with metadata that makes the conv add `inputs * scale` to the
residual:

| Call path | Results for None, scale=100, scale=1 | Expected |
|---|---|---|
| `layer._short_conv(...)` (current) | `[1.0, 1.0, 1.0]` | `[1.0, 101.0, 2.0]` |
| custom op (patch below) | `[1.0, 101.0, 2.0]` | `[1.0, 101.0, 2.0]` |

## Long context: QSA selection cost and a proposed fix

Same setup, compiled mode with the PLE fix, `--max-model-len 262144`, one
streamed greedy request per length (a list of `Room N code: XXXX.` lines and
a question about the middle room). All answers were correct at every length,
up to about 258K tokens.

| Prompt tokens | TTFT, PR + PLE fix | TTFT, plus QSA change | Decode tok/s, before / after |
|---|---|---|---|
| ~33K | 109.8 s | 56.5 s | 6.06 / 8.83 |
| ~66K | 198.3 s | 114.1 s | 9.53 / 9.60 |
| ~138K | 412.8 s | 277.6 s | 9.49 / 9.58 |
| ~258K | 769.1 s | 593.5 s | 9.44 / 9.40 |

(The 6.06 tok/s decode at ~33K in the first column comes from the first long
request after startup and is probably a warmup effect. We did not verify this.)

The change to `cpu/ops/qsa.py` does three things:

- `qsa_select_paged_tokens` bounds the scoring width by the longest visible
  compressed prefix (rounded up to 32) instead of the full block table width.
  With a large `max_model_len`, logits and `torch.topk` otherwise scale with
  the table width, not with the context.
- When every visible block fits the budget (`max visible <= token_topk / R`),
  it skips scoring and top-k and selects all visible blocks.
- `_qsa_sparse_paged_gqa_splitk_kernel` takes the tile count as a runtime
  argument (`do_not_specialize`). The host derives it from the longest compact
  selection, so the kernel is compiled once and no longer walks tiles that
  only hold `-1`.

We checked it against the original implementation on 24 configurations
(contexts from 1 to 9000 tokens, 1 to 3 rows, one or two requests, and a row
with `token_to_req = -1`). Selected sets match except where the top-k
boundary falls on exact zero scores (ReLU ties), where `torch.topk` picks
arbitrarily in both versions. Attention outputs agree within 0.004 on
identical inputs. The PR CPU tests still give `54 passed, 29 skipped`.

## Decode: thread partitioning and Triton launch overhead

Same machine and setup (FP8, TP=2, compiled, tcmalloc plus libiomp5), with
the PLE and QSA changes above. Each configuration is one server start and
three greedy requests with a 3428-token prompt and 129 generated tokens
(the first request is warmup and is dropped), then one with 33431 tokens.

### Why rank 1 is slower

We profiled both ranks of one decode run. The clocks agree (the ends of
matching `shm_allreduce` calls line up within about 1.5 us). Rank 0 reaches
the all-reduce first in 88% of calls and waits a median of about 60 us. Rank 1
is not slower everywhere. Only these ops differ:

| Op (shape) | Rank 0, us | Rank 1, us |
|---|---|---|
| `fused_experts_cpu` FP8, 1 token, top-10 of 512 | 186.7 | 217.5 |
| `onednn_mm` HC, 320 -> 10240 | 40.0 | 62.5 |
| `onednn_mm` HC, 10240 -> 336 | 51.6 | 64.8 |
| `onednn_mm` 2560 -> 8192 and `lm_head` | about equal | about equal |

Summed over 41 steps this comes to about 5.4 ms per step. Memory placement

### Patch 1: balanced split for the FP8 MoE

`parallel_2d_balanced` picks the `nth_m x nth_n` split (odd thread counts
allowed) with the smallest maximum number of blocks per thread. It keeps the
`parallel_2d` split unless the new one is strictly better and is used only by
the four `parallel_2d` calls in `moe_fp8.cpp`. Each block is still computed by
one thread in the same way, so the output is bit-identical. We checked this
against the old kernel with `torch.equal` for 1, 9 and 512 tokens at 15, 16
and 32 threads. `tests/kernels/moe/test_cpu_quant_fused_moe.py` and
`test_cpu_fused_moe.py` gave 401 passed and 288 skipped with the first
version (see the next paragraph); the final version is part of the kernel
run in the patches 4 and 5 section of the next comment (539 passed).

The first version launched the region with only `nth_m * nth_n` threads. On
32 threads that made the kernel about twice as slow, because OpenMP resizes
the team between the MoE stages. The final version keeps the full team, and
the threads stride over the tiles. Extra threads find no tile, and a team
smaller than planned (nested region, `OMP_DYNAMIC`) still covers every tile.
Empty `m` or `n` returns early instead of dividing by zero. (The existing
`parallel_2d` does the same resize whenever the thread count is odd.)

### Patch 2: small grids, K/V store and launch overhead (Python only)

A decode step launches several hundred small Triton kernels. Three changes,
all with bit-identical results:

- Grids of at most 8 programs run with `num_cpu_threads=1`. With
  `num_cpu_threads=0` Triton-CPU opens an OpenMP region over the whole team for
  4-5 programs. In a sweep on `hc_gate_mix` and `hc_combine_norm`, one thread
  was 1.2-2.4x faster up to 8 programs and slower from 12 programs on. No CPU
  kernel here uses atomics, so the thread count cannot change the result.
- `do_kv_cache_update` in `cpu/qsa.py` writes K/V with a small kernel
  (`_store_qsa_kv_kernel`). It replaces `any`, boolean indexing and two
  `index_put` calls, and slots below zero are still skipped.
- `ops/launch.py` adds `launch(kernel, grid, ...)`. It still calls the
  kernel's own Triton binder, so specialization (dtype, alignment,
  `==1` and `%16`) is Triton's. The compiled kernel is cached per specialization
  and started with `CompiledKernel.run`, which skips the device-key lookup,
  cache-key hashing and launch metadata. When launch hooks are installed it
  falls back to `kernel[grid]`. (In this Triton the hooks are an empty
  `HookChain` rather than `None`, so the check looks at `.calls`.)

We checked every HC op and the K/V store against the old path with
`torch.equal` for 1 to 512 tokens, 1 to 4 KV heads, strided views,
misaligned pointers and negative slots. The Qwen4Exp CPU tests give 70 passed

## Decode: MTP speculative decoding on CPU (patch 3)

At batch 1 the decode step here is dominated by per-step overhead, not by
weight reads. One rank reads about 6.6 GB of weights per token, which takes
about 30 ms at the 223 GB/s we measured for `lm_head` (124160x2560 BF16 in
2.846 ms), out of about 87 ms per step. Extra tokens in a step are therefore
cheap. Step time with M concurrent 3.4K-token requests (`bench/mbatch.py`,
same server as above):

| M | 1 | 2 | 3 | 4 |
|---|---|---|---|---|
| step, ms | 87.84 | 100.40 | 105.17 | 115.12 |

This makes the checkpoint's MTP layer worth using, but the CPU path rejects
it in `cpu/runtime.py` and `qwen4_exp/__init__.py`. The generic V2 runner
already runs MTP on CPU (`tests/v1/e2e/test_cpu_spec_decode.py` with
Qwen3.5), and the CPU GDN, PLE short conv and QSA side caches already handle
`num_speculative_tokens`. Three pieces were missing:
- a CPU drafter. `cpu/mtp.py` is `amd/mtp.py` without the low-latency GEMM,
  and the routed experts go through `_pad_moe_checkpoint_weights` with the
  draft quant config, as in the target (640 to 768 at TP=2 with 128x128
  blocks; patch 10 removes this padding);
- the target hook. The CPU model keeps the pre-final-mixer multi-stream state
  in `_mtp_hidden_buffer` and exposes `get_mtp_target_hidden_states`, as the
  NVIDIA model does. Without it the speculator feeds `[T, H]` instead of
  `[T, hc_count*H]`;
- config. `mtp` is allowed on CPU and other methods are still rejected.
  `Qwen4ExpMTPConfig` strips MRoPE on CPU even when `vision_config` is
  present, because the CPU QSA indexer supports 1D RoPE only
  (`cpu/indexer_qsa.py:80-81`).

One trap when porting from the NVIDIA file. The CPU decoder layer applies
`prev_block_output` only together with `prev_injection`, so the NVIDIA-style
`prev_block_output=inputs_embeds, prev_injection=None` would silently drop the
embedding residual. The AMD file adds the embedding to every branch
explicitly, the CPU file keeps that, and a unit test covers it.

## Decode: HC glue as plain torch ops, and two numeric fixes (patches 4, 5)

Patch 4 (`hc-torch.patch`, Python only). `hc_silu`, `hc_gate_mix` and
`hc_combine_norm` run once or twice per HC module on a few KiB per token, 97
HC modules per decode step. As Triton ops each call is an opaque launch. In
our Y01 profile their self time was 20.4, 35.7 and 57.9 us per call, 10.9 ms
per step. As plain torch ops Inductor fuses them into the graph. On a
compiled chain of 48 HC modules with the GEMMs stubbed out (VM, 30 threads)
the HC glue drops from 88 to 24 us per module. The patch removes the Triton
kernels of these three ops and keeps `hc_combine` and
`grouped_gemma_rmsnorm`. Numerics against the Triton kernels: `silu` and
`gate_mix` are bit-identical at 1 and 7 tokens, the combined residual is
bit-identical at 1 token, and the normalized output under `torch.compile`
differs by one bf16 ulp in 0.1-0.6% of the elements (reduction order).

Patch 5 (`cpu-numeric-fixes.patch`):
- `_softmax_topk` in `fused_moe/router/cpu_router.py` applies the top-k
  softmax in the logits dtype and casts to fp32 afterwards, while
  `_grouped_topk` in the same file calls `.float()` first. With bf16 logits
  (4096x512 `randn * 2`, top-10) this changes the routing weights by up to
  0.39% (mean 0.14%) against fp32. The patch normalizes in fp32.
- `CVT_FP8_TO_BF16_EXT` in `sgl-kernels/vec.h` sets the `0x4000` exponent bit
  unconditionally. FP8 zero therefore decodes to 2^-7 times the block scale
  (after the `kFP8_BIAS` rescale), and a subnormal with mantissa m to
  2^-7 * (1 + m/8) instead of 2^-6 * m/8. The FP8 MoE uses it for decode
  (`gemm_fp8.cpp:321`) and for the brgemm unpack (`gemm_fp8.cpp:117`). An
  expert with all up-projection weights at FP8 zero returns 7.84 instead of
  0. The patch clears the zero lanes (two instructions). Subnormals stay
  approximate, as the comment in `store_cache.cpp` already notes. In 12
  sampled expert tensors of the FP8 checkpoint 0.0009% of the weights are
  zero and 0.012% are subnormal, so the effect on this model is small. The

## Decode: router and shared-expert input projections as one GEMM (patch 7)

The router (512 rows), the shared expert's `gate_up_proj` (640 rows per rank
at TP=2) and `shared_expert_gate` (1 row) all read the same input. In our Y01
profile they took 26.4, 27.8 and 12.4 us per layer at one token, mostly
launch overhead. On the VM a single oneDNN GEMM over the 1153 concatenated
rows takes 56.6 us at M=1 and 58.4 us at M=4, against about 91 and 88 us for
the three separate calls. `moe-fused-input.patch` (Python only, CPU model
only):
- `Qwen4ExpSparseMoeBlock` gets a `fused_in_proj` (`ReplicatedLinear`) when
  all three layers are unquantized and the shared expert is TP-sharded, not
  replicated, fused or sequence-parallel;
- `fuse_input_projections()` fills it at the end of `load_weights`, before
  the CPU GEMM packing, and turns the three source weights into meta tensors
  with `_cpu_skip_gemm_dispatch`, so no copy is kept;
- the runner gets `gate=None` and no shared experts, with
  `moe_config.skip_final_all_reduce = True` as in the Inkling MoE. The block
  computes the shared expert from the fused output, adds `shared + routed` in
  the runner's order and does the one TP all-reduce itself. The MTP layer
  uses the same block.

The fused oneDNN primitive accumulates in a different order, so outputs move
at bf16 rounding level (reduced checkpoint: max |delta logprob| 0.0157 on the
common prefix, divergences only at ties).

## Decode and memory: GDN glue, sharded PLE table, FP8 MoE without padding (patches 8 to 10)

`gdn-glue.patch` (Python only). With MTP (4 tokens per step) the eager glue
inside `cpu_gdn_attention_core` was larger than the conv kernel. In a VM
profile of the reduced checkpoint (k=3) each call ran 8 `aten::copy_`
(63-87 us) plus `aten::cat` and `aten::clone` from `rearrange_mixed_qkv`,
next to about 170 us of the recurrent kernel and 45 us of the conv kernel.
- `forward_cpu` passes `mixed_qkv.contiguous()`, `b.contiguous()` and
  `a.contiguous()`, so these copies run in the compiled graph and the
  `.contiguous()` calls inside the op become no-ops;
- q/k/v are per-head views of `mixed_qkv` (`_qkv_views`), because the CPU
  recurrent kernels take row and head strides; `rearrange_mixed_qkv` is no
  longer called on CPU;
- the int32 indices, `cu_seqlens` and the uniform-length check of a spec
  step are computed by the first GDN layer and cached on the metadata object
  that all GDN layers of the step share (`_spec_step_inputs`).

The op median at 4 tokens goes from 649-743 us in four earlier VM profiles
to 484 us, with 1.7 copies per call (13.8 us) left.

A latent issue we noticed on the way:
`fused_sigmoid_gating_delta_rule_update_spec_cpu` checks `a` and `b` with
`CHECK_INPUT_SHAPE_DTYPE<true>` (`csrc/cpu/sgl-kernels/fla.cpp:2503-2504`),
which only requires the last dimension to be contiguous, but the kernel
indexes them as dense `[T, HV]` rows (`a_ptr[token * v_num_heads + ni]`,
`fla.cpp:1882` and `1885`). Every caller makes them contiguous today, so it
does not trigger. A row-strided view such as the `ba.chunk(2, dim=-1)`
halves built in `forward_cpu` would be read wrong without an error. Checking
full contiguity or passing the row stride would close it.

`ple-shard.patch` (Python only). `Qwen4ExpPLEEmbedding` drops
`disable_tp=True`. With TP > 1 each rank keeps its vocab shard of the N-gram
table, looks up the masked ids, dequantizes the rows to the model dtype,
zeroes the rows it does not own and all-reduces. Every row has exactly one
owner, so the sum is exact: on the reduced checkpoint at TP=2 the tokens and
top-2 logprobs matched the run without the patch exactly, on all prompts and
in both passes (including the prefix-cache pass). The TP=1 path is
unchanged. For the FP8 checkpoint this saves 23.84 GiB per rank at TP=2
(the table is 47.68 GiB); for BF16, where the table is about 95 GiB, the
saving is about half of that per rank.

`moe-refined-blocks.patch` (C++ and Python). The experts' intermediate size
640 splits into 320 rows per rank at TP=2, which is not a multiple of the
128 x 128 checkpoint blocks, so `_get_padded_moe_intermediate_size` padded it
with zeros to 768 (67.5 instead of 56.25 GiB of experts per rank). vLLM
already refines block scales for such shards (`refine_fp8_moe_block_shape`,
128 -> 64 here), but the CPU FP8 MoE kernel only accepted 128-wide K blocks.
- `brgemm::apply` and the small-M `tinygemm_kernel_nn` in `gemm_fp8.cpp`
  take `block_size_K` at runtime for the scale index and the unpack loop,
  instead of the compile-time `BLOCK_K` (and `k >> 7`);
- `CHECK_MOE_SCALES_FP8` in `moe.cpp` requires `block_size_N` to be a
  multiple of `block_size_n()` and `block_size_K >= 32` to divide `BLOCK_K`;
- `CPUExpertsFp8._supports_quant_scheme` accepts static 32 x 32 and 64 x 64
  block quant keys;
- `_get_padded_moe_intermediate_size` does not pad when
  `gcd(block_n, block_k, per_partition, hidden_size) >= 32`, so refinement
  is possible, and pads as before otherwise.

On Y01 the log shows `FP8 MoE block scales refined from [128, 128] to
[64, 64] to fit the TP-sharded intermediate size 320`. A new kernel test
compares refined 64 x 64 and 32 x 32 blocks against the dequantized
reference for M = 1, 4 and 64 (small-M and brgemm paths); the MoE, Qwen4Exp
config and GDN CPU test files give 335 passed. In a VM microbenchmark (one
token, 512 experts, top-10) the kernel time with refined blocks stayed
within run-to-run noise (medians 237-283 us against 259-305 us padded).
The rounding order changes, so outputs move at bf16 level; see the GSM8K
row below.

## Decode: FP8 MoE bookkeeping on the calling thread (patch 12)

At decode a `fused_experts_cpu` call routes 1 to 4 tokens to 10 experts,
yet it opens seven OpenMP regions, five of them over a few KB of work: the
`sorted_ids`/`expert_ids` padding fill and the counter zeroing in
`fused_experts_cpu`, the count and scatter loops of `moe_align_block_size`
(grain 0, so 10 elements still fork the team) and the `silu_and_mul` loop
in `moe_fp8.cpp`. `moe-decode-serial.patch` (C++ only) gives them grain
sizes so that small problems stay on the calling thread: the fills below
64K elements, the count and scatter loops below `GRAIN_SIZE` routed tokens
(both loops keep the same grain, so each thread still scatters the ids it
counted), and the activation below about 16K elements. Prefill sizes keep
the parallel path.

On the VM (30 threads, `KMP_BLOCKTIME=5` and explicit affinity as vLLM
sets them, tcmalloc and libiomp5 preloaded, E=512, N=320 per rank, K=2560,
top-10, 64 x 64 blocks, a different random expert set on every call so the
weights come from memory) the call takes 163.9-170.5 us instead of
182.9-190.7 us at M=1 (minimum over 9 series, two processes each), and
559.8-560.1 us instead of 564.8-572.5 us at M=4. The output is
bit-identical at M = 1, 4 and 64. With 48 MoE layers that is about 0.9 ms
per step at M=1. The CPU MoE kernel test files (`test_cpu_fused_moe.py`,
`test_cpu_int4_moe.py`, `test_cpu_quant_fused_moe.py` and the two Zen
files) give 423 passed and 290 skipped. The 25 MB `at::empty` per call did
not matter with tcmalloc: with `TCMALLOC_RELEASE_RATE=0` the M=1 time
stayed within the same range, so we left `B_tmp` alone.

On Y01 (patches 1 to 12) the gain is within run-to-run noise: the no-MTP
step is 67.2-68.1 ms at 3.4K and 69.3 ms at 33K against 67.7 and 69.9 ms
before, and the natural prompts average 14.61 tok/s without MTP (14.82
before) and 26.88 tok/s with k=3 (26.79). The output did not change: the
k=3 run diverges from the no-MTP run at the same tokens as before and has
the same mean acceptance length (3.183). The patch is bit-identical and
removes five fork/joins per MoE call, but on this machine it does not show
up end to end.
