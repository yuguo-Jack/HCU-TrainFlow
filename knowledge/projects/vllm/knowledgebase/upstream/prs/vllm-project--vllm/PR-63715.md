# [Bugfix][KV Offload][P2P] Disconnect a peer whose AbortAck times out

[Upstream PR](https://github.com/vllm-project/vllm/pull/63715) · state: closed · merged: False

## Original PR description

> **Depends on #61667.** Draft until the consumer slot quarantine lands; see "Merge order" below.

## Purpose

Part of #63602 (gap 2).

When a P2P load times out (`_P2P_LOAD_TIMEOUT_S` 10 s for a symmetric-P2P fetch, `_PD_LOAD_TIMEOUT_S` 30 s for a PD fetch), the consumer sends `AbortFetchMsg`. If no `AbortAck` arrives within `_ABORT_ACK_TIMEOUT_S` (5 s), `ClientRole.collect_results()` fails that one load, but the session stays up. Every later fetch routed to the same stuck peer then waits out both timeouts again: 15 s per P2P request, 35 s per PD request. The GPU run in #63602 (before the per-mode split in #63781) showed exactly this: loads to the replacement peer took 40.1–40.2 s and 0/400 pulls succeeded.

A missed `AbortAck` means the peer has stopped confirming that its WRITEs ended, and this side can't tell whether they stopped. This PR treats it as a data-plane fault:

- `ClientRole` records the first load whose `AbortAck` timed out (`expired_abort_ack`). The load still fails exactly as before.
- `P2PSession.poll()` checks it right after `_escalate_peer_fault()` and calls `_disconnect("abort ack timed out")`. It sends a best-effort `DisconnectMsg` and marks the connection dead, the same path the lookup-response timeout already uses. Like `_escalate_peer_fault()`, it does nothing if the session already died earlier in the same poll (for example, the peer's `DisconnectMsg`), so a clean disconnect is not reported as a data-plane fault.
- `data_plane_fault` also reports this cause, so the manager's reap applies the existing data-plane reconnect backoff (1 s doubling up to 60 s) instead of immediately reconnecting to the stuck peer. The reap already fails the peer's other in-flight loads and unresolved probes, so they prefill locally.

There are no manager changes.

This is the consumer-side bound. It works even when the source's control path is broken, which is exactly when the source-side stall deadline proposed in #63602 can't help.

## Trade-off: a slow but healthy peer is also disconnected

The source holds the `AbortAck` until NIXL reports every aborted WRITE terminal (`_pending_aborts` / `_slow_aborts` in the server role); it never force-releases one, and only logs past `_CANCEL_DRAIN_TIMEOUT_S` (10 s). So a large WRITE that is still progressing more than 5 s after the abort now ends the whole session: the peer's other loads fail and prefill locally, and the reconnect backoff starts.

This is deliberate. On `main` that load already fails at the same moment; this PR adds the collateral failures and the backoff. The consumer can't tell a slow WRITE from a stuck one, and a peer that can't finish a single transfer within the load timeout plus 5 s is not worth routing more fetches to. Keeping the session is exactly what made every later request wait out both timeouts again.

I have not measured the largest single transfer under load against the 5 s bound. On links where one WRITE can legitimately exceed it, `_ABORT_ACK_TIMEOUT_S` (shared with the existing per-load failure) is the knob; this PR doesn't change it.

## Merge order

Without #61667, a failed load hands its destination slots back through `complete_write(..., False)` while the source's WRITE may still land in them. On `main` that already happens for the one load whose `AbortAck` timed out. This PR's disconnect fails *every* in-flight load to that peer, so it widens the same window, and the source's abort drain has no deadline (gap 2 in #63602). With #61667, those slots stay quarantined until `TransferDone`/`AbortAck`, or a fencing guarantee, makes them safe, and this PR only changes when requests fail, not when memory is reclaimed. It must merge after #61667, and I'll rebase onto it then.

Not a duplicate: the only open PRs referencing #63602 are #63628 (gap 4), #63664 (gap 5) and #63708 (gap 1). #61667 changes what happens to slots on timeout and close, but not whether the session survives a missed `AbortAck`.
