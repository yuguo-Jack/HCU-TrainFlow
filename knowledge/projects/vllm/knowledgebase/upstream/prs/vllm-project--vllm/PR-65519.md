# [Perf][KV Offload] Bound copy descriptors submitted per step for CPU->GPU loads

[Upstream PR](https://github.com/vllm-project/vllm/pull/65519) · state: open · merged: False

## Original PR description



## Overview

A large CPU->GPU KV offload load submits all of its copy descriptors in one `cuMemcpyBatchAsync` call. When the call has more descriptors than the GPU command queue holds, it blocks the worker thread for most of the copy, and the next step's kernels are not launched. This PR caps the descriptors a regular async load submits per step and submits the rest in later steps.

Fixes #65515

## Claims

- Regular async loads no longer block the worker thread for the length of the copy.
- GLM-5.2-NVFP4, TP=8, 8x B200, CPU tier on, AgentX c=32: 859 vs 706 output tok/s, TTFT avg 17.4 s vs 23.8 s.
- Stores and expedited loads are unchanged. `VLLM_KV_OFFLOAD_MAX_LOAD_SUBMIT_DESCRIPTORS=0` restores the old behavior.

## Validation

**Root cause.** One B200, 6.6 GB per load, same bytes in each row (GLM-5.2 TP=8 uses 40 KB descriptors):

| Descriptors per call | CPU time inside the call | DMA time |
| --- | --- | --- |
| 161k (40 KB) | 110 ms | 123 ms |
| 40k (160 KB) | 52 ms | ~123 ms |
| 10k (640 KB) | 3.1 ms | ~123 ms |

In a torch profiler trace of the TP=8 server, all 8 ranks enter the call in the same step and the compute stream launches nothing during it.

**End to end.** `nvidia/GLM-5.2-NVFP4`, TP=8 on 8x B200, `OffloadingConnector` with an 880 GB CPU tier, AgentX (`aiperf --scenario agentx`), concurrency 32, KV tiers emptied before each run. `vllm/vllm-openai:v0.31.0` with and without this change backported to `gpu_worker.py`.

| Run (30 min) | Engine steps | Output tok/s | TTFT avg / p50 / p90 (s) | ITL avg / p50 (ms) |
| --- | --- | --- | --- | --- |
| Baseline | 62,253 | 706 | 23.8 / 22.1 / 42.5 | 18.4 / 9.0 |
| This PR | 86,776 | 859 | 17.4 / 16.7 / 35.5 | 9.1 / 7.3 |

A torch profiler capture ran for ~7 min of the baseline run. A 1 h baseline run without the profiler gave 762 tok/s and 19.5 s TTFT avg.

## Details

- `transfer_async()` queues the job and submits up to the cap. `get_finished()` submits the next slice. The connector calls it once per engine step, also on steps without a forward pass, so a pending load always makes progress. Loads still run in submission order.
- A job is reported only after its last slice completes, and the request stays in `WAITING_FOR_REMOTE_KVS` until then. Its transfer time is the sum of its slice times.
- `wait()` and `shutdown()` submit all remaining slices at once, so the flush fence and the shutdown drain keep their meaning.
- Trade-off: 8192 descriptors is about 6 ms of DMA at 40 KB, so a 6.6 GB load spreads over ~20 steps and that request waits longer for its KV. The default keeps each call below the ~16k-23k descriptors where the blocking starts.
- `VLLM_KV_OFFLOAD_MAX_BATCH_DESCRIPTORS` (#43018) splits a job into several calls, but all in the same step, so the thread still blocks. #64236 moves async-load submission after the forward pass in mixed sync/async steps but still submits each load in one call. No open PR caps the descriptors per step.
- Not covered by CI: the end-to-end effect needs GB-scale loads. The unit tests check slicing, ordering, the `wait()` flush, the shutdown drain, and transfer accounting on a real GPU.

We ran into a similar stall with CPU-tier KV restores, so thanks for putting this up.

One thought on the default: the right per-step cap likely depends on the GPU and the PCIe link, so a fixed 8192 may be too small on one setup and too large on another.

In #57569 I'm adding a startup calibration that measures the DMA/SM boundary per machine. Happy to wire that up once this lands, or coordinate here if you prefer.

- zetxqx · comment · 2026-11-04T01:07:22Z · [source](https://github.com/vllm-project/vllm/pull/65519#issuecomment-6619711459)

Thanks @hyunnnchoi, agreed that one fixed number will not fit every setup.

Two separate things set the cap. The point where `cuMemcpyBatchAsync` starts to block depends on how many descriptors the driver queue holds, not on bytes. On B200 that was about 16k-23k descriptors, and I have not measured other GPUs or drivers. The link speed sets how much DMA one step carries: 8192 × 40 KB is about 6 ms on B200, which is well within a step.

I would like to keep this PR to the fixed default plus the env var, so it stays small and independent of #57569. Deriving the cap from your calibration as a follow-up sounds good to me.

- zetxqx · comment · 2026-11-04T01:50:01Z · [source](https://github.com/vllm-project/vllm/pull/65519#discussion_r4462643413)

File: `vllm/v1/kv_offload/cpu/gpu_worker.py` · line 651

Thanks for the review. I tested this on one B200 GPU. This is a small test of the worker only. It has no model, no TP, and no other GPU work.

Setup: 40 KB per descriptor (same as GLM-5.2 TP=8), 10 runs for each case. I measured the CPU time inside the batch copy calls.

| Case | Descriptors | CPU time (median / max) |
| --- | --- | --- |
| One call, no cap | 8k / 16k / 24k / 32k / 48k | 2.6 / 5.2 / 7.8 / 17.9 / 27.0 ms |
| K loads start in one step, cap 8192 | K = 1 / 2 / 3 / 4 | 2.6 / 6.3 / 7.9 / 10.6 ms (max 14.4) |
| One load in flight, then `get_finished()`, then K new loads | K = 1 / 2 / 3 | 5.3 / 8.0 / 10.6 ms |

What I see:

- Each descriptor costs about 0.32 µs of CPU time. This cost grows in a straight line.
- One big call starts to block between 24k and 32k descriptors.
- Many small calls of 8192 do not block, even at 32k in total. The copy engine empties the queue fast enough between the calls.
- So K loads in one step add about K × 2.6 ms. Before this PR, one big load blocked for about 110 ms.

A shared budget for the whole step can remove this extra time. But then a burst of loads gets only about 6 ms of copy per step, so these loads finish later. I prefer to keep the per-call cap. If you think a hard per-step limit is needed, I can add it.
