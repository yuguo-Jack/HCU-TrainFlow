# [ROCm][Perf] Keep wvSplitK at YTILE 2 for N=5 on wave64 to avoid VGPR spills

[Upstream PR](https://github.com/vllm-project/vllm/pull/63015) · state: open · merged: False

## Original PR description



## Overview

On wave64 (MI300/MI355), `wvSplitK` with N=5 picks YTILE 3/4 for wide M. These tiles exceed the VGPR budget and spill, so a 5-row BF16 GEMM is ~4x slower than a 4-row one. This PR keeps N=5 at YTILE 2 on wave64.

## Claims

- 5-row BF16 GEMM on wide M is ~4x faster on MI355X (e.g. 32B lm_head 930 → 235 us).
- Speculative decoding with 5 rows per verify step (conc=1, `num_speculative_tokens=4`) gets 2.07x output throughput (Qwen3.8-27B MTP).
- No change for other N or for wave32 (gfx11/gfx12).

## Validation

MI355X (gfx950), same build. Only `_rocm_C.abi3.so` is swapped between before and after.

**Kernel** (`rocm_unquantized_gemm_impl`, BF16, us, 2 runs each):

| Shape (M x K) | n=4 | n=5 before | n=5 after |
| --- | --- | --- | --- |
| 10240 x 5120 (32B qkv) | 22.8 | 47 | 16.4 |
| 51200 x 5120 (32B gate_up) | 77.0 | 328 | 80.3 |
| 34816 x 5120 (14B gate_up) | 52.3 | 230 | 53.8 |
| 151936 x 5120 (32B lm_head) | 231 | 930 | 235 |
| 248320 x 5120 (27B lm_head) | 380 | 1548 | 385 |

**E2E**: Qwen3.8-27B MTP, `num_speculative_tokens=4`, conc=1, 200 ShareGPT prompts, `--attention-backend ROCM_AITER_UNIFIED_ATTN`. Before and after runs alternate, 3 runs each, spread < 0.5%:

| | Output tok/s | Median ITL | Acceptance length |
| --- | --- | --- | --- |
| Before | 92.4 | 33.3 ms | 3.17 |
| After | 191.3 | 15.8 ms | 3.17 |

**Tests**: `tests/kernels/quantization/test_rocm_skinny_gemms.py` and `tests/model_executor/layers/test_rocm_unquantized_gemm.py`: 2444 passed, 0 failed. This PR adds N=5 cases (wide M, odd M, large K). Before this PR there were none.

## Details

- **Root cause**: `wvSplitK` launches 16 waves of 64 threads, so each thread has at most 128 VGPRs. With N=5, the compiler reports spills for all YTILE 3/4 variants (`-Rpass-analysis=kernel-resource-usage`, bf16):

  | N | YTILE / UNRL | VGPR spill (`wvSplitK_hf_`) |
  | --- | --- | --- |
  | 4 | 4 / 1 | 0 |
  | 5 | 2 / 2 | 0 |
  | 5 | 3 / 2 | 45 |
  | 5 | 4 / 2 | 111 |

  N=4 already uses UNRL 1 to avoid this. N=5 was not handled.
- **Fix**: add one branch to `WVSPLIT_TILE_CFG` so wave64 N=5 uses YTILE 2 / UNRL 2. It is a separate branch so the macro is not reformatted.
- **Limitations**: performance is measured only on gfx950. gfx942 has the same wave64 VGPR budget and should benefit. CI (MI300 and MI355 Quantization Kernels) covers correctness.
