# [Core] Add --release-weight-page-cache to drop checkpoint pages after load

[Upstream PR](https://github.com/vllm-project/vllm/pull/58625) · state: open · merged: False

## Original PR description

## Problem

A DEP32 GLM-5.3 prefill group (4 pods x 8 DP ranks, DeepEP) dies as a unit: one rank stops between steps, the other 31 wait for it in `internode_dispatch`, hit the 100 s DeepEP timeout and trap (Xid 43); the stalled rank never traps. Captured on a production group right after its first real requests:

- The stalled worker's main thread was in kernel state `D` inside `__vm_munmap` for 73 s, ran for 1 s, then in a 16 KiB anonymous `mmap` (`vm_mmap_pgoff`) for 88 s. `py-spy` could not attach for exactly that window, since it needs `mmap_lock` as well.
- `perf` on the same workers under load: 1,000-3,400 `mmap` + `munmap` calls per second per worker, all 16 KiB. CPython 3.12 allocates a new frame data-stack chunk with `mmap` when a call crosses the end of the current chunk and frees it on return (python/cpython#142183, fixed in 3.13.13); the MoE forward crosses that boundary in every layer.
- The node sat at its free-memory floor for the whole stall: MemFree 16 GiB against MemAvailable 896 GiB (about 700 GiB of clean checkpoint pages plus a 761 GiB CPU KV tier in shm), with direct-reclaim bursts (`pgscan_direct` 7k-20k per 5 s), `compact_stall` 23-56 per 5 s and hundreds of `thp_fault_fallback`. MemFree jumped from 17 to 344 GiB the moment the group died.

`mmap` and `munmap` take the process `mmap_lock` for write; a page fault takes it for read and, with no free pages, holds it through direct reclaim and compaction. One faulting thread in reclaim blocks the main thread's chunk `munmap`, and the queued writer then blocks every later fault in the process, so the whole worker stops. The condition exists whenever a pod starts on a node whose previous pod left the checkpoint in the page cache (any in-place restart or rollout) and is worst on a rank's first real requests, when the KV tier faults in new pages at scale.

## Purpose

Adds `--release-weight-page-cache` (`LoadConfig.release_weight_page_cache`, default off). After `load_weights` returns, each worker calls `posix_fadvise(POSIX_FADV_DONTNEED)` on the checkpoint files it read. The pages are clean and no longer mapped at that point, so they are freed immediately and the node leaves the memory edge; the reclaim that held `mmap_lock` has nothing left to scan. The interpreter-side `mmap` churn is untouched (a CPython fix or upgrade), but without the edge it costs microseconds, not seconds.

Cost: the next start on that node re-reads the checkpoint from disk. Opt-in because a rank still reading a file that another rank already released re-reads it as well.

## Test Plan

GLM-5.3 prefill, DEP32 (4 pods x 8 workers), 0.29-based image, production pod templates, nodes started at the memory edge (previous pod's cache kept): release after load, in-place restart of the group, then cache-churn soaks (160 sessions x 2 rounds, 32 concurrent, 66K-token prompts) and 16 x 157K-token prompts at concurrency 8, with per-second sampling of every worker main thread's kernel state.

## Test Result

- Without the release, at the edge: worker main threads seen in `D` inside `vm_mmap_pgoff` / `__vm_munmap` under the same traffic.
- With the release: 703 GiB freed per node in 13-16 s; MemFree 550-650 -> 770-855 GiB; shm tier untouched; 0 `D` waits over the whole run.
- No latency cost: cache-churn soak TTFT p50 32.2 s cold and 5.4 s with prefix hits, 16 x 157K-token prompts p50 50.6 s and 50.4 s across two bursts, all equal to the same runs without the release; 0 errors.
- Cold and warm loads both 200-260 s.
- After the restart, nodes came up with 547-652 GiB free instead of 6-33 GiB.
