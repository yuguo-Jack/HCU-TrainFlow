# [Bugfix][EPLB] Share one NIXL agent per worker across elastic EP reconfigurations, enable MI355 scaling test

[Upstream PR](https://github.com/vllm-project/vllm/pull/63134) · state: open · merged: False

## Original PR description

## Overview

`NixlEplbCommunicator` created its own NIXL agent and registered the expert weights with it. A
reconfiguration builds the replacement communicator while the old one is still alive, so a worker ended up
holding several agents with the same expert pages registered. On MI355 the extra IPC export is refused and
the test fails. This hands the replacement communicator the agent it is replacing, so the pages are
registered once, and adds the Elastic EP Scaling step on MI355.

## Claims

- A worker holds one NIXL agent over its expert weights instead of one per communicator ever built.
- `tests/distributed/test_elastic_ep.py` passes on MI355, which it did not before.
- Nothing here is platform specific and nothing is gated on a platform. The extra registration happens on
  every backend; it is only fatal on some.

## Validation

**Agent count per worker process**, counted from `Initialized NIXL agent` lines in CI logs of
`tests/distributed/test_elastic_ep.py`, which runs four scale cycles:

| | processes | agents | processes holding more than one |
| --- | --- | --- | --- |
| MI355X, unmodified, build 92231 | 12 | 18 | 5, one of them three |
| MI300X, unmodified | 16 | 31 | 8 |
| MI355X, with this change | 16 | 16 | 0 |
| H100, with this change | 20 | 20 | 0 |

Build 92231 ran this step on #56679, which adds Buildkite yaml and nothing else, so that is unmodified code. There MI355 reports `hipIpcGetMemHandle failed : invalid argument` 6 and 8 times and the test fails, while H100 passes in the same builds. The counts are lower than 16 because those runs failed part way through, so fewer workers reached the point of creating an agent.

The MI300X row is an unmodified run on hardware that tolerates the extra registrations. It shows the extra
registration is not specific to the platform where it breaks.

**The test.** The MI355 step failed on every attempt before this change. With it, the two most recent runs
were 4 passed, 1 skipped, in 857 s and 853 s, with zero `hipIpc* failed`, and the H100 step green in the same
builds. The fifth case skips on ROCm because NIXL EP is not installed in that image. Accuracy stays in the
H100 band: the largest deviation from the pre-scaling GSM8K score was 0.036 on MI355 and 0.035 on H100,
against a tolerance of 0.080.

## Details

**Root cause.** A NIXL registration belongs to the agent that made it, and `num_local_experts` is fixed, so
the expert weights and the receive buffers keep their storage across a reconfiguration. Building a fresh
agent for the replacement communicator therefore exports IPC handles for memory that is already exported,
and leaves the worker holding two and then three agents over the same pages.

**The fix.** `EplbState.create_communicator` already holds the communicator being replaced, so it passes it
down and the NIXL backend reuses its agent, registering memory only when it creates a fresh one. The agent
is dropped when the last communicator referencing it is collected, and NIXL deregisters the memory and
disconnects the peers from its destructor. `add_remote_agent` for a peer the shared agent already knows is a
no op, since `loadRemoteMD` merges into the existing entry and the connection info is unchanged.

This is @NickLucche's implementation, from a branch he wrote against this one. My first version kept a module
level registry keyed by the expert address range, which was more machinery for the same result.

**The `__del__` guard.** Separate and small, in the same teardown path. `__del__` can run during interpreter
shutdown, when module globals are already being set to `None`, including the `contextlib` that the teardown
body itself uses. The cleanup then raises and every worker prints a traceback on exit. The body is now
wrapped in a plain `try` that depends on no module.

**On the ROCm side.** A probe in the worker showed that at the moment a 6 MiB export is refused a 2 MiB one
from the same process still succeeds, and that shortly before the refusal the same process had completed 64
consecutive 6 MiB exports. So the refusal is narrower than the duplicate export alone would suggest, and
that part is being looked at separately in ROCm/rocm-systems#11892. This PR does not depend on that issue and
does not work around it: it removes the duplicate registration, which was worth removing on the vLLM side
regardless of how any runtime responds to it.

**CI steps.** The upstream step is the `mirror.amd` override of the existing H100 nightly step, so it
inherits `optional: true` and runs nightly on `mi355_4`. It overrides `commands` because ROCm installs the
KV connector requirements differently, and adds a pytest thread timeout so a hung scale cycle prints a
Python stack instead of being killed by the agent with an empty log. A matching MI355 step is added next to
the existing MI300 one in the AMD pipeline.

- stefankoncarevic · comment · 2026-11-03T12:18:48Z · [source](https://github.com/vllm-project/vllm/pull/63134#issuecomment-6603596642)

> Adding remote agents concurrently with submitting xfers may be unsafe with `NIXL_THREAD_SYNC_NONE`, and other modes might affect performance (not necessarily, just saying that it is something we need to investigate)

You're right, and the window is specific to this PR. The agent runs with NIXL_THREAD_SYNC_NONE (no listener thread, so that's the default), and add_remote_agent is called from _prepare_eplb_communicator during preparation, while the server is still serving and EPLB is only drained later at commit. Before this change each communicator built its own agent, so peers were added to an agent with nothing in flight; now a replacement communicator adds them to an agent the outgoing one may still be using.

On the cost of the stricter modes, I couldn't measure one. Under sustained load with step_interval=10, so 164 and 166 EPLB rearranges in two minutes, NONE gave 8.39 req/s at p50 2.207 s and STRICT gave 8.63 req/s at p50 2.144 s, with STRICT coming out marginally ahead, which puts the difference inside run-to-run noise.

So I've switched the EPLB agent to NIXL_THREAD_SYNC_STRICT. It only applies to the agent I create, so nothing else using NIXL is affected. Full suite on MI355 with the change is 4 passed, 1 skipped in 762 s, with scale and downtime numbers unchanged.
