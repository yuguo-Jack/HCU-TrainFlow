# [Bugfix][Kernel] Hoist tensor-descriptor construction out of unified-attention TD loop

[Upstream PR](https://github.com/vllm-project/vllm/pull/51506) · state: open · merged: False

## Original PR description

## Summary

Part of the TD adoption strategy proposed in #42545. `USE_TD`'s K/V tile
loader rebuilt the tensor descriptor every tile iteration, since the
descriptor base baked in the per-tile physical block index. This forced a
`tensormap_create` per iteration, which the pipeliner could not predicate.

- With Triton 3.8.0, the loop-local path failed to compile with a
  `tensormap_create` pipeliner error on all tested CUDA architectures (SM90,
  SM100, SM103, and SM120).

## Fix

The loop-invariant `kv_head_idx` is now part of the descriptor base. One
descriptor is built per K/V cache before the tile loop, and the per-tile
physical block is supplied through the `load()` coordinate. This makes the
descriptor loop-invariant and restores pipelined compilation.

The hoisted 3D descriptor also requires a registered scratch allocator on the
tested CUDA architectures. The PR wires up `set_triton_allocator()`, cached
per device to avoid repeated registration on every forward pass.

Q/output TD remains disabled for CUDA query lengths up to
`MAX_3D_QUERY_LEN`; K/V TD remains enabled. TD remains opt-in, and the
raw-pointer default is unchanged.

## Final validation

Across the tested workloads, this PR's TD path is never slower than vLLM
main's TD path. The default path passes the same `1,627` tests before and
after the change.

With the Triton 3.8.0 version currently installed by vLLM, vLLM main's TD
path fails to compile on all four tested architectures. With Triton's current
main, vLLM main's TD path reaches launch but fails without allocator
registration. This PR's TD path runs and is faster than vLLM main's TD path
across all tested architectures.

## Validation

Correctness summary: `1,162 passed` for the TD suite across SM90, SM100,
SM103, and SM120; the default non-TD path passes the same `1,627` tests
before and after the change.

<details>
<summary>Benchmark methodology</summary>

### Method

The PR TD and raw-pointer arms used the same PR head with
`VLLM_TRITON_USE_TD=1` and `VLLM_TRITON_USE_TD=0`, respectively. The main TD
arm used the vLLM main kernel with allocator registration added so it could
launch on Triton main. Benchmarks used `vllm bench throughput` with BF16
activations, `TRITON_ATTN`, 20 warmup prompts, 200 measured prompts, and
three interleaved repetitions per arm on one pinned GPU. The benchmark used
Triton main `19a5c66d`, PyTorch `2.14.0+cu130`, and Qwen3-4B, gpt-oss-20b,
and Qwen3.6-35B-A3B-FP8. Every ratio compares arms within one job on one
Triton build.
