# [Multimodal] Point KV cache memory errors at encoder profiling knobs

[Upstream PR](https://github.com/vllm-project/vllm/pull/63362) · state: open · merged: False

## Original PR description



## Overview

On small GPUs, multimodal encoder profiling at the maximum input size can take most of the KV cache budget. Startup then fails with a KV cache memory error whose only advice is to raise `gpu_memory_utilization` or lower `max_model_len`. This PR adds the multimodal settings that shrink the profiled encoder footprint to both KV cache memory errors. Related: #27706 (Qwen3-VL-2B runs out of memory at startup; the user found the multimodal limits by trial and error).

## Claims

- For multimodal models whose encoder is profiled, both KV-cache-too-small errors now name `limit_mm_per_prompt` size hints, `mm_processor_kwargs` (e.g. `max_pixels`) and `skip_mm_profiling`.
- Text-only models, `skip_mm_profiling=True` and `language_model_only=True` keep the existing messages.
- No behavior change apart from the error text.

## Validation

RTX 4070 Laptop 8 GB, Qwen/Qwen3-VL-2B-Instruct (BF16), GPU otherwise idle, base `47c091b`, `VLLM_LOGGING_LEVEL=DEBUG`:

```bash
vllm serve Qwen/Qwen3-VL-2B-Instruct --max-model-len 8192 --gpu-memory-utilization 0.9 [extra flags]
```

| Extra flags | Encoder profiled with | Torch peak increase | Available KV cache | Result |
|---|---|---|---|---|
| none | 1 image, 16384 tokens | 1.79 GiB | 0.36 GiB | fails: needs 0.88 GiB for `max_model_len` 8192 |
| `--skip-mm-profiling` | not profiled | 0.09 GiB | 2.06 GiB | starts |
| `--mm-processor-kwargs '{"max_pixels": 802816}'` | 2 images, 2048 tokens total | 0.18 GiB | 1.98 GiB | starts; serves image requests |

Weights (4.08 GiB) and memory consumed at rest (4.36 GiB) are identical across the three runs. The only difference is the profiled encoder input. Its activation peak becomes the transient peak headroom subtracted from the KV budget (`vllm/utils/mem_utils.py`), costing ~1.7 GiB here. Raising `gpu_memory_utilization` can't recover that when it is already 0.9. Reducing the profiled input size does. With another process holding ~0.5 GB of the GPU, the default run leaves -0.62 GiB instead and hits the other error ("No available memory for the cache blocks"), which this PR also covers.

## Details

- Root cause: `profile_run` runs the encoder on a dummy batch at the model's maximum feature size (Qwen3-VL: 16384 tokens for one image). Profiling completes without raising, but its activation peak is reserved out of the KV budget. The KV memory check is the first user-facing signal, and it named only `gpu_memory_utilization` and `max_model_len`.
- The hint lives in `_check_enough_kv_cache_memory`, the single place both KV memory errors are raised, so it covers MRV1 and MRV2 without touching either model runner. Its `max_model_len` parameter became `vllm_config` (both callers already had it).
- Limitation: if every modality is explicitly set to `0` in `limit_mm_per_prompt` (rather than `language_model_only`), the hint still appears. Detecting that needs the model's supported modalities, which this function doesn't have; it didn't seem worth the extra complexity.
- Why this is not a duplicate: open PRs on profiling and KV sizing (#49540, #58243, #60228, #59893, #62806, #57656, #62139) change what is profiled or how memory is measured. None changes these error messages or `kv_cache_planning.py`.
- Motivation: I first hit this while serving Cosmos-Reason2-2B (Qwen3-VL-2B) W4A16 on a Jetson Orin Nano 8 GB, where vLLM only started after capping `max_pixels` and setting `limit_mm_per_prompt`. The validation above is from an RTX 4070, not the Jetson. On Tegra, encoder profiling can instead fail inside the allocator (NvMap contiguous-allocation limit) before this check runs, and this PR does not change that path.
