# [KV Connector][NIXL] Batch host-buffer KV block copies on CUDA

[Upstream PR](https://github.com/vllm-project/vllm/pull/61056) · state: open · merged: False

## Original PR description



## Overview

With `kv_buffer_device="cpu"` on CUDA, NIXL P/D stages KV through a host buffer, and both host-buffer copies go through `copy_kv_blocks`. In a serving process these copies run at 1.2–2.4 GB/s and account for most of the extra latency P/D adds. This PR pins the host transfer buffer on CUDA (falling back to pageable memory if pinning fails) and copies all (layer, block) pairs with one `ops.swap_blocks_batch` call, the primitive the CPU offloading connector already uses. Follows #54483; related to #60181.

## Claims

- Host-buffer D2H/H2D copies in a serving process: 1.2–2.4 GB/s → 8.7–16.3 GB/s.
- P/D `max_tokens=1` request latency (1P1D, Qwen3-0.6B, single request): 1.7–3.6x lower, e.g. 7000-token prompt 1222.5 → 340.1 ms.
- No correctness regression observed.

## Validation

**Tests**
- New `tests/v1/kv_connector/unit/test_copy_kv_blocks.py` (13 tests, CUDA only; picked up by the existing `v1/kv_connector/unit` GPU job): both directions on the default stream and on an explicit side stream; pinned (batched) vs pageable (fallback); exact `torch.equal` results, with the stream stalled before the copy so an early return would be caught; non-contiguous and mixed block-size fallbacks; pinned-allocation fallback, and other allocation errors still propagate. Breaking the fast path's destination pointers, or removing its stream sync, makes the 4 pinned cases fail.
- `pytest tests/v1/kv_connector/unit/test_nixl_connector.py`: 178 passed.
- `VLLM_GPU_SYNC_CHECK=error`: the P/D serving run below completes without errors. As a control, calling the fast path inside a `with_gpu_sync_check` region raises without `gpu_sync_allowed()` and passes with it, which is how both NIXL call sites already wrap these copies.

**End-to-end** (main `187a0eb`, 4x RTX 4090 without P2P, NIXL 1.5.0/UCX, 1P1D on two GPUs, Qwen3-0.6B, `--gpu-memory-utilization 0.4 --max-model-len 8192`, `kv_buffer_device="cpu"` on both sides). `max_tokens=1` request latency through the toy proxy, single request, random token prompts, 5 runs per length after warmup; same environment, only this change toggled:

Per-copy throughput was measured on an earlier base (`f0c44cc7d5`) by timing `save_kv_to_host` / `sync_recved_kv_to_device` with a stream sync on both sides: e.g. 128 blocks (224 MiB) D2H 123.5 → 14.5 ms, 438 blocks (766 MiB) H2D 333.7 → 58.4 ms.

**Correctness**: greedy outputs through P/D match prefill-node-only generation token for token in eager mode (4/4 prompts, up to 2694 prompt tokens). With CUDA graphs, 2/4 prompts diverge at near-ties (top-1/top-2 logprob gap 0.0625 and 0.0); the divergence positions and logprob gaps are the same with and without this change.

## Details

**Flow touched** (P/D with `kv_buffer_device="cpu"`):
1. P runs a prefill step; `NixlConnector.wait_for_save()` → `save_kv_to_host()` → `copy_kv_blocks(device → host, "d2h")`. **Changed.**
2. D admits the request and NIXL READs the blocks from P's host buffer into D's host buffer.
3. When the read completes, D's `get_transfer_results()` → `sync_recved_kv_to_device()` → `copy_kv_blocks(host → device, "h2d")`; the request then decodes. **Changed.**

**Root cause.** `CudaPlatform.swap_out_blocks_to_host` / `insert_blocks_to_device` do `dst[idx] = src[idx].cpu()` / `.to(device)` per layer, so the host side is an advanced-indexing gather/scatter on the CPU. By default serving sets Torch to one thread (`set_torch_threads_for_runtime`), which caps that at ~2.5 GB/s: for 128 blocks the CPU scatter takes 71 ms of 87 ms, while the PCIe copy itself is 15 ms. Pinning the buffer alone does not help; the copy has to skip CPU-side indexing.

**Change.** `copy_kv_blocks` first tries `_try_copy_kv_blocks_batched`: on CUDA, when the host side is pinned and every layer's tensors are contiguous with the same per-block size, it builds one pointer per (layer, block) and submits a single `swap_blocks_batch` (batched on a non-default stream such as serving's, per-copy on the legacy default stream), then synchronizes the current stream to keep the existing synchronous contract. Otherwise it falls back to the per-layer path, so TPU/XPU and non-contiguous layouts are unchanged. The NIXL host buffer comes from `alloc_host_xfer_buffer`, which pins on CUDA when available and falls back to pageable memory with a one-time warning if the pinned allocation fails.

**Trade-offs and limitations.**
- The host buffer matches the GPU KV pool in size, so pinning it locks that much host memory; in our setup (7.5 GiB buffer, measured on `f0c44cc7d5`) it added ~2.5–3 s to engine startup.
- The copies stay synchronous; making them asynchronous (events instead of a stream sync) is left for a follow-up.
- Validated on a single KV-cache-group model only. #60181 fixes which layers `sync_recved_kv_to_device` copies for multi-group models; it changes the callers, not `copy_kv_blocks`, so the two compose.
- Measured single-node, single-request; not measured under concurrency.

**Not a duplicate.** Searched issues/PRs for `save_kv_to_host`, `sync_recved_kv_to_device`, `copy_kv_blocks`, `swap_out_blocks_to_host`, `insert_blocks_to_device`, `use_host_buffer` and pinned host buffers. The closest is #54483, which coalesces calls across cache groups but keeps the per-layer copy. #53263 stages the NIXL READ itself (step 2) through device memory when the destination is host memory; it does not touch the host↔device copies in steps 1 and 3, so the two are complementary.
