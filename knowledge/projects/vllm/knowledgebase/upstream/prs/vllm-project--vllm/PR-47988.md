# [Bugfix][Quantization] Upcast E8M0 scales for CUTLASS block FP8 and skip unaligned N on SM12x

[Upstream PR](https://github.com/vllm-project/vllm/pull/47988) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Fixes #47818. With DeepGEMM disabled (`VLLM_USE_DEEP_GEMM=0`), or for a layer DeepGEMM declines, block-FP8 linears with E8M0 weight scales stop on the CUTLASS block kernel's fp32 scale check. That check runs before any arch dispatch, so this affects every arch the kernel supports (SM90 and newer), not only SM12x. On SM12x, block-FP8 layers whose output dimension is not a multiple of 128 stop in the same kernel (DeepSeek `kv_a_proj_with_mqa`, N=576, #47990). Related: #56214 (fixed the Triton half), #48588 (pads N for CUTLASS), #53278 (declines E8M0 in CUTLASS instead; see Details).

## Claims

- `CutlassFp8BlockScaledMMKernel` converts E8M0 weight scales to fp32 once at load time, as the DeepGEMM and B12x paths already do, so these layers no longer stop on CUTLASS's fp32 scale check. It finds the scale through `FP8BlockParams.block_scale` and `block_scale_attr`, so `weight_scale` and `weight_scale_inv` are both covered.
- `_upcast_e8m0_to_fp32` uses PyTorch's native `float8_e8m0fnu` conversion: code 0 decodes to 2^-127 instead of 0.0 and code 255 to NaN instead of inf. Codes 1 to 254 decode as before.
- On SM12x, `CutlassFp8BlockScaledMMKernel.can_implement` declines block-FP8 layers with N % 128 != 0, so selection moves on to the next kernel (Marlin W8A16 on current main) instead of the server dying with `Invalid status` in `profile_run`.

## Details

- Root cause: quant configs that set `is_scale_e8m0` (DeepSeek-V4 and V4.1 with FP4 experts, Bailing-MoE-V3 with `"scale_fmt": "ue8m0"`, and HY-V4 MTP layers quantized as FP8 with `"scale_fmt": "ue8m0"`) make `Fp8LinearMethod` create `weight_scale_inv` as `float8_e8m0fnu`. DeepGEMM decodes that dtype in its own weight post-processing, but with DeepGEMM disabled or when it declines the layer, the layer goes to the CUTLASS block kernel, and `dispatch_scaled_mm` stops on `STD_TORCH_CHECK(b_scales.scalar_type() == torch::headeronly::ScalarType::Float)` in `scaled_mm_helper.hpp`, before any arch dispatch. The SM120 blockwise kernel itself is correct for 128-aligned N, so the issue's guess of a missing SM120 dispatch entry is not the cause.
- Decoding: the old helper shifted the exponent byte into the fp32 exponent field, which turns code 0 (2^-127) into 0.0 and code 255 (NaN) into inf. The native conversion is how main already decodes E8M0 elsewhere (Marlin's `scales.view(torch.float8_e8m0fnu).to(param_dtype)`, and the uint8 branch of `_decode_e8m0_scales`, `exp2(code - 127)`). The helper is shared with the Triton, DeepGEMM, AITER, B12x and CPU linear paths, DeepSeek-V4 CPU sparse attention, the DeepSeek-V4/V4.1 ROCm paths and ROCm sparse MLA; for codes 1 to 254 nothing changes for them.
- Unaligned N: the SM12x blockwise CUTLASS kernel rejects every N % 128 != 0 shape (`Invalid status` from `can_implement` in `cutlass_gemm_caller.cuh`, on all three tile configs, #47990). The guard keeps those layers off CUTLASS. B12x has the same N % 128 requirement, and FP8 Marlin has accepted every shape on SM89+ since #52182, so on current main they run as Marlin W8A16, with activations kept in BF16. @adi-suresh01 measured the tradeoff on N=576, K=2048: Marlin takes 16.0 to 34.3 us at M <= 64 against 8.3 to 11.7 us for padded CUTLASS (#48588), and is the faster of the two at M = 256 to 1024; GSM8K was 0.646 with Marlin and 0.635 with padded CUTLASS. #48588 keeps these layers on CUTLASS by padding N, and once it lands this guard can be dropped.
- Overlap with #53278 (open, labeled `ready` and `needs-rebase`): it takes the other route for CUTLASS. It marks E8M0 weight scales in the weight quant key and makes `CutlassFp8BlockScaledMMKernel.can_implement` decline them, so those layers move to another kernel. Both PRs edit `can_implement`. If #53278 lands as it is, CUTLASS is no longer selected for E8M0 layers and the upcast here stops running for them; the decoding fix and the SM12x N guard still apply. Upcasting at load keeps these layers on CUTLASS W8A8.
- Not a duplicate. Open PRs on 2026-10-17: `gh pr list -R vllm-project/vllm --state open --search "47818 in:body"` returns only this PR (#54435 was closed by its author as a duplicate of this one); `--search "CUTLASS E8M0"` and `--search "e8m0 cutlass block fp8"` add #53278 (above), #48588 (pads N, complementary), #57512 (DeepGEMM selection with fp32 scales on SM12x), #41834 and unrelated MoE, ROCm, DeepGEMM and DeepSeek-V4 work. #41834 (DeepSeek-V4 SM12x enablement, 221 changed files) also upcasts E8M0 for CUTLASS, but it disables the CUTLASS block kernel on SM12x entirely, while the kernel is correct for 128-aligned N.
- Limits:
  - A real-weight evaluation of an E8M0 checkpoint is not possible here (DeepSeek-V4-Flash is about 160 GB of weights against 96 GB of VRAM). The E8M0 path is checked at the layer level above, through the same `Fp8LinearMethod` selection and loading a checkpoint goes through.
  - SM90 and SM100 were not run; the claim that they hit the same scale check rests on the shared `dispatch_scaled_mm` source.
  - The native conversion was checked on CPU and CUDA only. The shared helper also runs on ROCm and XPU paths, which I could not test.
