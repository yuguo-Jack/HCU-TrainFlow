# [Spec Decode] Generic reduced-vocabulary get_top_tokens() for DraftModelSpeculator

[Upstream PR](https://github.com/vllm-project/vllm/pull/60387) · state: open · merged: False

## Original PR description



## Overview

Generic, opt-in `VLLM_SPEC_DRAFT_VOCAB` env var that attaches a reduced-vocabulary `get_top_tokens()` to any `DraftModelSpeculator`-based drafter whose model doesn't already have its own restriction mechanism — covers plain EAGLE and EXAONE 4.5's native MTP head, which #59740 (addressing #58578) doesn't reach. Posting on behalf of VENETA (I'm BRANTD-veta) — full writeup and the Korean draft-vocabulary files we built this against: https://github.com/veneta-ai/mtp-draft-vocab-ko.

## Claims

- +13.4% decode (15.83 → 17.95 tok/s median) on `yuhuili/EAGLE-LLaMA3.1-Instruct-8B` drafting for Llama 3.1 8B, acceptance unchanged, zero output difference between arms.
- +7.0% decode (5.57 → 5.96 tok/s median) on `LGAI-EXAONE/EXAONE-4.5-33B-FP8`'s native MTP head (`Exaone4_5_MTP`), acceptance unchanged, zero output difference between arms — a second confirmation on a different dispatch shape (native MTP head, not an auxiliary drafter).
- No new `speculative_config` keys, no changes to verification — a single env var read once at `load_model()` time, opt-in, no-op when unset.
- Generalizes across every speculator built on `DraftModelSpeculator` (EAGLE, MTP, dflash, dspark) by attaching at that shared layer instead of per-model-class, while still correctly leaving alone any model that overrides `LocalArgmaxMixin.get_top_tokens()` with its own mechanism (detected by identity comparison, not just `hasattr`).

## Validation

Measured on one DGX Spark (GB10), 10 Korean prompts, greedy decoding, k=3:

| drafter | vocab | decode tok/s (median) | accepted/draft | output diff |
|---|---|---:|---:|---:|
| EAGLE-LLaMA3.1-Instruct-8B / Llama-3.1-8B-Instruct | full (128,256) | 15.83 | 1.55 | — |
| same | reduced (65,536, Korean-biased) | **17.95 (+13.4%)** | 1.57 | 0 replacement/garbled chars |
| EXAONE-4.5-33B-FP8 (native MTP head, `Exaone4_5_MTP`) | full (153,600) | 5.57 | 1.07 | — |
| same | reduced (65,536, Korean-biased) | **5.96 (+7.0%)** | 1.07 | 0 replacement/garbled chars |

The EXAONE gain is smaller for two reasons, not just noise: this model keeps 42.7% of its vocabulary (65,536 of 153,600) against the EAGLE case's 51.1% of a much larger 128,256-token vocabulary in absolute rows cut, so there's proportionally less matmul being saved; and EXAONE 4.5 runs in reasoning mode by default (a long CoT before any answer token), with acceptance pinned at 1.07/3 in both arms regardless of vocab size — the target rejects most drafts either way, so the draft step is a smaller share of total decode time here than in the EAGLE case. Boot log for this one: `spec draft vocab: 65536 of 153600 tokens (42.7%) kept; get_top_tokens() attached to this Exaone4_5_MTP instance (lm_head 1500.0 -> 640.0 MiB per draft step)`.

A first attempt at this (not in this PR) masked `compute_logits()`'s already-full-vocabulary output after the fact instead of reducing the matmul — correct, but measured **zero speedup**, because the full matmul still ran before the mask was applied. That's the reason this PR attaches a real `get_top_tokens()` (a smaller matmul) rather than post-hoc masking logits — mentioning it since "we tried the obvious thing first and it didn't work, here's why" seemed worth keeping rather than silently landing only the working version.

Confirmed from the boot log that the mechanism is actually engaging, not a no-op: `lm_head` read shrank from 1002.0 MiB to 512.0 MiB per draft step (51.1%), matching the kept-vocabulary fraction almost exactly.

New unit tests (`tests/v1/worker/test_gpu_reduced_draft_vocab.py`, CPU-only, no GPU needed): no-op when the env var is unset; no-op when the model already overrides `get_top_tokens()` with its own mechanism (mirrors Gemma4's centroid head); no-op when `tp_size != 1` or the model has no plain top-level `lm_head`; correct id-remapping when ids are kept out of order and a non-kept row would otherwise win the argmax; and an explicit check that the reduced weight tensor never aliases the original `lm_head.weight` (the property that matters when an EAGLE drafter shares that exact weight object with its target via `load_eagle_model`).

I don't have a working current-`main` vLLM install on this machine to run these through the real CUDA path tonight (the model-class landscape has moved since the image we had locally), so I verified the committed function body by extracting it verbatim into a standalone harness against plain torch + a stub `LocalArgmaxMixin`/`logger` and running all six scenarios there — all pass. Would appreciate a CI run catching anything that harness couldn't.

## Details

**Motivation.** #58578 measured this general idea (+25–29%) and #59740 implements a considerably more sophisticated context-aware version of it (static list + per-token dynamic rows via a rank-256 SVD scorer, quantized rows, +15.2–22.6% on `Qwen3.8-Flash-Next-NVFP4` + MTP k=3 — also on one DGX Spark, for what it's worth our own measurement of the *existing* MiaAI-Lab kit's mechanism on that exact model/hardware was +54%, a gap we can't explain and aren't asserting a cause for). That PR's changed-files list (`qwen3_5_mtp.py`, `qwen3_eagle3.py`, `qwen3_dflash.py`, `qwen3_dspark.py`, `llama_eagle3.py`, `deepseek_eagle3.py`, `gemma4_dspark.py`, `qwen4_exp/{nvidia,amd}/mtp.py`) doesn't touch plain `eagle/speculator.py`-dispatched models or `exaone4_5_mtp.py` — this PR is specifically the static-list-only piece for those classes, not a competing design for the ones #59740 already covers well.

**Why attach at `DraftModelSpeculator.load_model()` instead of per model file.** `MTPSpeculator`, `EagleSpeculator` and `AutoRegressiveSpeculator` all resolve to the same `_greedy_sample_draft`/`sample_draft` dispatch on the shared base class, and neither overrides it. A hook there, right after `self.model = self.load_draft_model(...)` and before `self._validate_local_argmax_reduction()` (which already requires `hasattr(self.model, "get_top_tokens")` whenever `use_local_argmax_reduction=True`), covers every method built on that class at once rather than needing one patch per model file.

**Why `LocalArgmaxMixin.get_top_tokens` identity comparison, not `hasattr`.** `hasattr(model, "get_top_tokens")` is true for almost every model already, via `LocalArgmaxMixin`'s own generic default — which is itself just a full-vocabulary matmul plus a TP-communication optimization, not a vocabulary restriction. A naive `hasattr` check would silently skip attaching to EAGLE/Llama models entirely (they already have *a* `get_top_tokens`, just not a reduced one), while still correctly skipping Gemma4's centroid-projection head, which overrides the mixin with something real. Identity-comparing the unbound function against `LocalArgmaxMixin.get_top_tokens` distinguishes "has the generic default" from "has its own mechanism" correctly in both directions.

**Safety.** `index_select` always allocates a new tensor, so the reduced weight is never a view onto the original `lm_head.weight` — this matters because `load_eagle_model` (in `eagle/utils.py`) commonly points a draft model's `lm_head` at the literal same object as the target's. `get_top_tokens()` is only ever called from this speculator's own `_greedy_sample_draft`/`sample_draft`, never from the target's own `compute_logits()`/rejection-sampler verification path, so there is no path by which this change can reach target verification regardless.

**Limitations, stated rather than glossed over.** Static list only — no context-aware dynamic rows, no quantization, no `tp_size > 1` support (explicit, logged no-op rather than silently wrong). `use_local_argmax_reduction` also requires `draft_sample_method != "probabilistic"` (pre-existing constraint, unrelated to this PR) so this only applies to greedy drafting. Models whose head is nested rather than a plain top-level `lm_head` (GLM-4 MoE's `shared_head.head`, DeepSeek's equivalent) aren't covered yet either — a straightforward extension, just not done here since I don't have a measurement for it.

Measured results for the four-arm attribution I promised when I withdrew the earlier numbers.

**Why four arms.** `get_top_tokens()` is only reached from `sample_draft()` when `use_local_argmax_reduction=True`, so attaching a reduced vocabulary without that flag cannot affect decode. Two conditions cannot separate "the reduced vocabulary does the work" from "the flag's own path does the work", so I ran all four combinations of (vocabulary attached) × (flag set).

### Setup

| | |
|---|---|
| hardware | 1 × NVIDIA GB10 (DGX Spark), compute capability 12.1, aarch64, 121.7 GiB unified memory, driver 580.173.02, CUDA toolkit 13.0, torch 2.13.0 |
| build | this PR's branch at `8674c1f9`, editable install, reports `0.28.0.dev999+veneta` |
| target | `meta-llama/Llama-3.1-8B-Instruct`, TP=1 |
| draft | `yuhuili/EAGLE-LLaMA3.1-Instruct-8B`, `method: eagle`, `num_speculative_tokens: 3` |
| server | `--gpu-memory-utilization 0.6 --max-model-len 16384`; one server per arm, torn down between arms |
| vocabulary | 65,536 of 128,256 target ids kept (51.1 %); the engine logs the `lm_head` slice as 1002.0 → 512.0 MiB per draft step |
| workload | 20 fixed Korean prompts (10 general, 10 domain), `temperature: 0`, `max_tokens: 400`, 3 repeats → n = 60 per arm |
| decode metric | streamed tokens / wall time per request, median over the 60 |
| acceptance metric | `1 + Δspec_decode_num_accepted_tokens_total / Δspec_decode_num_drafts_total` from `/metrics` — mean accepted tokens per draft step, max k+1 = 4 |

### Results

| arm | `VLLM_SPEC_DRAFT_VOCAB` | `use_local_argmax_reduction` | median decode | vs baseline | acceptance | IQR |
|---|---|---|---|---|---|---|
| a | unset | false | 18.13 tok/s | — | 1.71 | 17.6–20.0 |
| b | set | false | 18.19 tok/s | +0.3 % | 1.71 | 17.7–20.1 |
| c | set | **true** | **20.48 tok/s** | **+12.9 %** | 1.70 | 19.8–22.6 |
| d | unset | true | 18.17 tok/s | +0.2 % | 1.71 | 17.7–19.9 |

U+FFFD count across all 240 generations: 0.

### What this says

- Arm b is the important one: attaching the reduced vocabulary with the flag off is a no-op (+0.3 %, inside run-to-run spread). The branch now logs a warning in exactly this case, naming the flag.
- Arm d shows the flag alone is also a no-op on this configuration (+0.2 %).
- Only both together move decode, by +12.9 % here.
- Acceptance is flat across all four arms (1.70–1.71), so the gain is not better drafts. It is the cheaper per-draft-step projection and argmax over 65k instead of 128k ids — the same drafts for less work.

### Limits

- One hardware target, one target/draft pair, one `k`, one prompt language, one session, n = 60 per arm with no repeated sessions. I would not read +12.9 % as more precise than "roughly ten percent on this configuration".
- EXAONE 4.5 (native MTP head) is not measured yet; I will post it when the GPU frees up again.
- Nothing here checks output quality beyond the U+FFFD count. Restricting the draft vocabulary changes which tokens the draft can propose; flat acceptance is consistent with unchanged outputs but is not proof of it.
- Per-request run files and the server boot logs (which carry the attach/warning lines and the acceptance counters) are available if they would be useful.
