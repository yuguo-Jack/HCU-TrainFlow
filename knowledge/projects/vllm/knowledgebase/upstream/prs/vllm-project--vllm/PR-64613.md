# [Bugfix] Keep metadata of a delayed BlockStored when an OffloadKey is reused

[Upstream PR](https://github.com/vllm-project/vllm/pull/64613) · state: open · merged: False

## Original PR description

## Overview

This fixes vllm-project/vllm issue 63037. The bug needs `enable_kv_cache_events` and `self_describing_kv_events` to be on. In that mode, `OffloadingEventsTracker` loses the payload of a delayed `BlockStored` when an `OffloadKey` is stored again before the `BlockRemoved` of its old allocation is translated. The event is then sent as a placeholder (`token_ids=[]`, `block_size=0`). With this fix the tracker counts, per key, the old primary removals that a new recorded store has replaced. The old `BlockRemoved` then no longer drops the metadata that the new store still needs.

Compared with #52103 and #63129, this fix:

- Is much smaller. It is about 30 lines in `events.py` and keeps the existing metadata map and the `record_*` hooks. [#52103](https://github.com/vllm-project/vllm/pull/52103) touches 11 source files and removes the map and the hooks. [#63129](https://github.com/vllm-project/vllm/pull/63129) replaces the map with a dict subclass that overrides `__setitem__`, `pop` and `clear`, and adds a deque of generations per key.

Compared with #52103, this fix:

- Also fixes resumable requests. With the reported order on [#52103](https://github.com/vllm-project/vllm/pull/52103)'s head, the delayed `BlockStored` of a resumable request is still `block_hashes=[49] token_ids=[] block_size=0`. Its first store is also a placeholder, and that store has full metadata on the current code.
- Keeps the current event output. [#52103](https://github.com/vllm-project/vllm/pull/52103) changes `BlockRemoved` to carry only the chunk key (`[49]` instead of `[48, 49]` for a two-block chunk). It also turns kvcr inventory `BlockStored` events into `block_size=0` placeholders.
- Adds a test that runs the reported order (store again before the old `BlockRemoved` is translated) and fails without the fix. No test in [#52103](https://github.com/vllm-project/vllm/pull/52103) runs that order.

Compared with #63129, this fix:

- Still releases a key after a failed store. On a port of [#63129](https://github.com/vllm-project/vllm/pull/63129) to the base commit, the generation of a failed store is never retired. So the key's entry stays held after its final eviction, and `test_dropped_promotion_cleanup_does_not_hold_restored_key` fails.
- Passes the existing tests. On that port, `test_pending_promotion_captures_payload_before_inventory[False-evicted]` and `[False-retained]` fail.

## Claims

- With `enable_kv_cache_events` and `self_describing_kv_events` on, the delayed `BlockStored` of a reused `OffloadKey` keeps its block hashes, token ids and block size, as the `events.py` docstring promises.
- `record_partial_store` is fixed too. Its `_record_partial_tail` had a copy of the same merge code and failed the same way.
- Keys are still released at their final eviction. This includes the case where the manager drops the cleanup of a failed promotion. No existing test or expected value changes.

## Validation

Reproducer: the script below drives vLLM's real `OffloadingEventsTracker`, `GroupOffloadConfig` and `OffloadingEvent` through the order from the issue: store K, `BlockStored(K)`, store K again, the old `BlockRemoved(K)`, then the delayed `BlockStored(K)`. Only the `Request` is a mock. There is no model and no server. The `control` mode translates the delayed store before the old removal.

```python
"""Reused OffloadKey: drives vLLM's real OffloadingEventsTracker through the ordering in the report."""
import sys
from unittest.mock import MagicMock
import torch
from vllm.distributed.kv_transfer.kv_connector.v1.offloading.events import OffloadingEventGroupSpec, OffloadingEventsTracker
from vllm.distributed.kv_transfer.kv_connector.v1.offloading.scheduler import GroupOffloadConfig
from vllm.v1.core.kv_cache_utils import BlockHash
from vllm.v1.kv_cache_interface import FullAttentionSpec, KVCacheSpecKind
from vllm.v1.kv_cache_spec_registry import KVCacheSpecRegistry
from vllm.v1.kv_offload.base import Medium, OffloadingEvent, OffloadingKVEventsConfig, make_offload_key

mode = sys.argv[1]  # "bug" = report ordering; "control" = delayed store arrives before the old removal
H = lambda i: BlockHash(str(i).encode())
def req():
    r = MagicMock(); r.request_id = "r"; r.block_hashes = [H(0), H(1)]
    r.all_token_ids = list(range(1, 9)); r.lora_request = None; return r
def ev(keys, removed):
    return OffloadingEvent(keys=keys, medium=Medium.CPU, removed=removed, locality=None, ownership=None, removal_expected=False)
spec = FullAttentionSpec(block_size=4, num_kv_heads=1, head_size=1, dtype=torch.float32)
gc = GroupOffloadConfig(group_idx=0, tokens_per_block=4, tokens_per_chunk=8, hashes_per_chunk=2,
    sliding_window_size_in_chunks=None, kv_cache_spec=spec, manager_cls=KVCacheSpecRegistry.get_manager_class(spec),
    kv_event_group_spec=OffloadingEventGroupSpec(KVCacheSpecKind.FULL_ATTENTION.value, None))
t = OffloadingEventsTracker(OffloadingKVEventsConfig(enable_kv_cache_events=True, self_describing_kv_events=True))
key = make_offload_key(H(1), 0)
t.record_store(req(), gc, 0, key)                  # 1. K resident
[old_stored] = t.take_events([ev([key], False)])
t.record_store(req(), gc, 0, key)                  # 3. K stored again, async store not complete
if mode == "bug":
    [old_removed] = t.take_events([ev([key], True)])   # 4. old BlockRemoved(K)
    [new_stored] = t.take_events([ev([key], False)])   # 5. delayed BlockStored(K)
else:
    [new_stored] = t.take_events([ev([key], False)])
    [old_removed] = t.take_events([ev([key], True)])
print("old_stored:", old_stored.block_hashes, old_stored.token_ids, old_stored.block_size)
print("new_stored: block_hashes=%s token_ids=%s block_size=%s" % (new_stored.block_hashes, new_stored.token_ids, new_stored.block_size))
ok = new_stored.token_ids == list(range(1, 9)) and new_stored.block_size == 4 and len(new_stored.block_hashes) == 2
print("RESULT:", "complete metadata" if ok else "placeholder metadata lost")
```

## Details

Root cause: the tracker keeps one `_OffloadEventMetadata` per `OffloadKey`. It records which tiers hold the key in `active_residencies`, a set of `(medium, ownership)` pairs. The CPU tier is the single pair `(CPU, None)`. The scheduler calls `record_store` right after `prepare_store` allocates a key. But the eviction of the key's previous allocation is queued in the manager at eviction time and is translated only at the next drain. For a reused key the order is:

1. K is evicted. Its `BlockRemoved` is queued.
2. `prepare_store` allocates K again. `record_store(K)` merges the new claim into the same `(CPU, None)` entry, because a set cannot hold it twice.
3. The old `BlockRemoved(K)` is translated. It discards the only entry, and `take_events` pops K's metadata at the end of the batch.
4. The delayed `BlockStored(K)` of the new store finds no metadata and is sent as a placeholder.

Fix:

- `prepare_store` only returns absent keys in `keys_to_store`, and the scheduler only records those keys. So a recorded store on an entry that still holds `(CPU, None)` is a new allocation, and the removal of the old allocation is still queued. `record_store` and `record_partial_store` now share `_replace_event_metadata`, which counts this case in `_superseded_primary_removals`.
- A `(CPU, None)` removal (an eviction or a metadata-only cleanup) first uses up a count, and only then discards the residency.
- The counts are cleared at the end of each `take_events` batch and on `reset`. The scheduler drains the whole manager queue each time, so every superseded removal is in the next batch. A count left over belongs to a failed-promotion cleanup that `CPUOffloadingManager.take_events` dropped because the key was allocated again. If it were kept, it would hold the key until reset.
- `active_residencies` stays a set of residency kinds, so `test_reoffload_preserves_secondary_residency` and other readers see no change.

Limitation: a promotion can allocate a key again after a queued eviction and be seen only through `record_lookup`. That case still sends a placeholder, as before. A lookup cannot tell a new allocation from a second lookup of the same allocation, so this case needs information from the manager. It is left for a separate change.
