# [Bugfix][Multimodal] Honour explicit num_frames in Qwen-VL video loaders

[Upstream PR](https://github.com/vllm-project/vllm/pull/64899) · state: open · merged: False

## Original PR description



## Overview

Fixes #64882. Setting `num_frames` for video (via `--media-io-kwargs` or per request) had no effect on Qwen2-VL, Qwen2.5-VL and Qwen3-VL: their loaders always sampled by fps. This makes those loaders use an explicit `num_frames`, the same way HF's `sample_frames` does.

## Claims

- An explicit `num_frames` now applies to the `qwen2_vl` (Qwen2-VL, Qwen2.5-VL) and `qwen3_vl` (Qwen3-VL, Cosmos3-Edge) loaders.
- When `num_frames` isn't set, nothing changes for any loader: the generic loader still takes 32 frames and the Qwen loaders still sample at 2 fps.
- Docs: a short "Video Frame Sampling" section in `docs/features/multimodal_inputs.md`, and the `--media-io-kwargs` help text no longer implies every loader honours `num_frames`.

## Validation

Qwen2-VL-2B, the `baby_reading` test clip (243 frames at 25 fps), `--mm-processor-kwargs '{"min_pixels": 784, "max_pixels": 151200}'`. Video tokens returned by `/tokenize`:

| Setting | main | this PR |
|---|---:|---:|
| `num_frames` not set | 1620 (18 frames) | 1620 (unchanged) |
| server `--media-io-kwargs '{"video": {"num_frames": 4}}'` | 1620 | 360 (4 frames) |
| request `media_io_kwargs`, `num_frames=4` | 1620 | 360 |
| request `media_io_kwargs`, `num_frames=8` | 1620 | 720 (8 frames) |

Request rows used `--trust-request-mm-kwargs`.

Tests:

```bash
pytest tests/multimodal/test_video.py -k qwen_vl
pytest tests/multimodal/media/test_video.py -k "num_frames_default or jpeg_frames_default"
pytest tests/entrypoints/serve/tokenize/test_tokenization_video_num_frames.py
```

- The new tests fail on main (the end-to-end one with `assert 1620 == 360`) and pass with this change.
- Running all of `tests/multimodal/test_video.py` and `tests/multimodal/media/test_video.py` on my machine: 147 passed, 15 failed. The same 15 fail on main too (torchcodec can't load without FFmpeg on macOS, plus some glm5next/clef_omni decoder tests), so they're unrelated.
- Loading the clip through every CPU video loader with `num_frames=8`: only `qwen2_vl` (18 → 8) and `qwen3_vl` (19 → 8) change.
- Qwen2.5-VL video timing follows the frames actually sampled: `second_per_grid_ts` goes from 1.08 s (unset, 18 frames) to 2.43 s (`num_frames=8`), since HF computes it from `frames_indices`.
- Tested on macOS (Apple M4, CPU backend), torch 2.14.0, transformers 5.22.1. I haven't run the GPU tests locally. I ran the last one with `VLLM_CPU_KVCACHE_SPACE=1`, since vLLM otherwise tries to reserve 92% of RAM for the KV cache there.

## Details

**Root cause.** `VideoMediaIO` defaulted `num_frames` to 32 and always passed it to the loader, so the fps-based loaders couldn't tell a value the user set from the default. #45555 dealt with that by having the Qwen2-VL loader ignore `num_frames` completely, and the Qwen3-VL loader works the same way. As pointed out in the issue, fixing it needs both sides: `VideoMediaIO` has to tell "unset" apart, and the Qwen loaders have to actually read `target.num_frames`.

**Change.** `VideoMediaIO` now defaults `num_frames` to `None` and only resolves it when loading, to the loader's new `default_num_frames` class attribute: 32 on `VideoLoader`, and -1 (sample by fps) on the two Qwen loaders. This follows HF's `BaseVideoProcessor.sample_frames`, which treats `num_frames=None` as unset and falls back to the processor's default. Simply passing nothing when unset wouldn't work, because the generic loader would then decode every frame. The `video/jpeg` path keeps its 32-frame cap.

**Behaviour changes worth knowing:**
- Anyone already setting `num_frames` for a Qwen model now gets that many frames. Before, it was silently ignored.
- For the Qwen loaders, if both `num_frames` and `fps` are set, `num_frames` wins. HF raises in that case; the generic loader still takes whichever gives fewer frames.
- Qwen2-VL rounds `num_frames` to an even number like HF does, and explicit values are clamped to 768 frames and the clip length instead of raising.
- Qwen2-VL with an unknown source fps now works when `num_frames` is set, since fps isn't needed then.

**Checked:** the processor cache key already includes per-modality `media_io_kwargs` (#54918), so requests with different `num_frames` don't collide. The other `VideoMediaIO` callers in `entrypoints/openai/decisions/strategies.py` pass `num_frames=-1` explicitly and are unaffected. The Rust frontend rejects `--media-io-kwargs`, so it isn't affected either.

**Not in this PR:** GLM-4V and GLM-4.6V ignore `num_frames` too, but their HF `sample_frames` only takes `fps`, so that matches HF; a warning there could be a follow-up. Molmo2 is handled in #56207, and #57717 / #55727 are already changing the `opencv_dynamic` and glm5next loaders. One-frame clips can still divide by zero in the Qwen2-VL loader (#58353), unchanged here. `VideoMediaIO.num_frames` can now be `None`; nothing in the repo reads it.
