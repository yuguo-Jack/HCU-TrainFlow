# [Kimi-K3][ROCm] Reuse one attention metadata build across the KV cache groups

[Upstream PR](https://github.com/vllm-project/vllm/pull/60426) · state: open · merged: False

## Original PR description



## Overview

Kimi-K3's 93 layers are split by the hybrid allocator into 14 KDA and 5 MLA KV cache groups. Every group holds the same requests and differs only in which blocks they live in, yet `build_attn_metadata` runs a full metadata build for each one on every decode step. This builds once per group type and points the rest at it, which is what the V1 model runner already does.

## Claims

- MRV2 reuses metadata for any group whose builder opts into `update_block_table`. It was restricted to `MambaSpec`, while the V1 runner (`gpu_model_runner.py`) has long gated on the capability flag alone; this aligns the two.
- `AiterMLAMetadataBuilder` opts in and grows an `update_block_table` that rebuilds only what it reads off the block table: the per-token page indices, the segmented DCP verify row view, the prefill backend's prepared metadata and the slot mapping.
- The KDA builder's opt-in moves from an exact-type check to a `reuses_group_metadata` class flag, so the K3 subclass participates instead of being excluded along with it.
- Measured on MI355X at concurrency 1, ISL 100k: full-decode ITL p50 5.640 ms to 5.431 ms, **-209 us/step (-3.71%)**.

## Validation

Hardware: MI355X (gfx950), TP8, DCP1, fp8 KV cache, `FULL_DECODE_ONLY` cudagraphs.

```
pytest tests/v1/attention/test_rocm_aiter_mla_mtp_split.py \
       tests/kernels/attention/test_rocm_aiter_mla_decode_metadata.py \
       tests/models/kimi_k3/test_amd_kda_checkpoint.py
```

`94 passed, 14 warnings in 13.43s`

The two added cases build group 1, derive group 2 through `update_block_table` against a shifted block table, and compare against the build that group 2 would otherwise have done. They assert both halves: that the block-table-dependent tensors differ correctly, and that the batch-level tensors are the *same objects*, which is what makes the reuse worth doing. The MLA case was checked against a negative control — replacing `update_block_table` with a stub that only swaps the block table makes it fail — so it is not vacuous.

End-to-end, three arms on one node in one sitting, ISL 100000, OSL 512, 12 requests, concurrency 1, seeds 7 and 11:

| arm | frITL p50 (ms), seed 7 / seed 11 |
|---|---|
| baseline | 5.623 / 5.655 |
| reuse | 5.417 / 5.445 |
| baseline, repeated | 5.622 / 5.660 |

Mean p50 5.640 to 5.431 ms, **-3.71%**; p90 **-3.56%**; interactivity 177.3 to 184.1 tok/s.

The repeated baseline lands within 0.005 ms of the first, which rules out drift over the session, and the arms do not overlap (worst reuse 5.445 against best baseline 5.622). Both arms reported zero errors and exactly one engine init, and each server self-reported which arm it was running from inside the process.

Host-side cost of the MLA metadata builds alone, 5 groups: 651.6 to 239.8 us/step at qlen 1, and 523.8 to 216.4 us/step at qlen 8.

## Details

Everything `build()` derives from the batch — sequence lengths, the indptrs, the decode schedule, the fp8 prefill work maps — is identical across groups holding the same requests, so `update_block_table` recomputes only the block-table-dependent fields and shares the rest by object identity.

`_expand_page_indices` is factored out of `_build_decode` so the build path and the reuse path cannot drift apart; both now expand page indices through the same code.

Widening the MRV2 gate also turns reuse on for the other builders that already set `supports_update_block_table` (FlashAttention, b12x, Mamba). That is deliberate: those builders declare the capability, and the V1 runner has been exercising it for them without the `MambaSpec` restriction, so this removes an inconsistency rather than extending a contract. The flag stays opt-in, so a builder holding per-group state beyond the block table keeps per-group builds by leaving it unset — which is what `reuses_group_metadata` gives the KDA subclass hierarchy.

The reuse is ordering-dependent only in that a derived group's metadata must come from a group already built. That holds structurally: `_get_kv_cache_groups_uniform_page_size` assigns `layers[i::num_groups]`, so groups interleave in execution order and group 0 holds the first layer of the pattern.

Not included here: AITER MLA's in-graph decode schedule recording is a separate local change, and composing the two needs the recorded schedule split into a batch-level half and a per-group page-index expand. That is a follow-up; nothing in this PR depends on it.
