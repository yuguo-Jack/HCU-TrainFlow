# [Perf][DSv4.1] Specialized decode at TP8 on GB300

[Upstream PR](https://github.com/vllm-project/vllm/pull/64146) · state: open · merged: False

## Original PR description



## Overview

Allow tensor parallel size 8 for the DeepSeek-V4.1 `latency_specialized` decode (#61868): two GB300 trays of an NVL72 NVLink domain. **Stacked on #64144** (its commit is included here; please review only the last commit, "Specialized decode at TP8 on GB300").

## Claims

- The specialized decode and its fused all-reduce + mHC accept TP 4 or 8 (was 4 only).
- At TP8, single request on DeepSeek-V4.1-Flash with DSpark: **746 → 942 tok/s** (+26 %) against the stock decode, on vLLM main.
- The routed-expert GEMMs are bitwise equal to FlashInfer's TRT-LLM-gen MoE at the TP8 slice.

## Validation

vLLM nightly `5d35ce39` (FlashInfer 0.7.2.post1, with #63914's version gate applied locally), two GB300 trays (TP8 over MNNVL):

| Test | Result |
|---|---|
| `test_kernels.py` (1 GPU) | all TP8 (`padded384`) cases pass bitwise. One TP4 case, `routed_experts_match_flashinfer[padded640-5-graph]`, fails by 6 bf16 ULPs in the finalize comparison; unchanged `main` fails it identically on FlashInfer 0.7.2.post1 (the finalize order changed, see #63921) |
| `test_layers.py` (4 GPUs, TP4) | passed |
| TP8 serve | "specialized decode on", correct answers and tool calls |

Single request, Tetris prompt (~6.7k output tokens), 8 runs each (4 at temperature 0, 4 at the default), DSpark 7 draft tokens, `--async-scheduling-depth 6` (#64145):

| TP8, vLLM main | tok/s (mean) | tokens per step |
|---|---:|---:|
| stock decode | 746 | 5.92 |
| specialized decode (this PR) | 942 | 6.00 |

With #61869 (DSpark draft on the specialized decode) and #64145, the same two trays run one request at about 1,560 tok/s, against about 1,160 for TP4 on one tray.

## Details

- At TP8 each rank holds a 288-column slice of the routed experts' 2304-wide intermediate. The TRT-LLM-gen weight conversion pads it to 384.
- The routed-expert GEMMs now derive the slice from the weights' padded width: 576/640 at TP4, 288/384 at TP8.
  - GEMM1 uses ceil(2 × slice / 128) M tiles, so 5 at TP8. The last 32 H columns of the fifth tile come from zero weights.
  - It zeroes the remaining padding columns from where the tiles end.
- The routed-expert test is parametrized over both slices.
- Without NVLink multicast between the two trays (the usual case when the partition's groups are in use), the fused all-reduce uses #64144's unicast path.
- CI cannot run TP8: it needs two GB300 trays in one NVLink domain. The TP8 slice is covered on one GPU by `test_kernels.py`, which runs in the nightly B200 DeepSeek-V4.1 step.
- This overlaps in files with #63921 (TP4 only); whichever lands second rebases.
