# [Bugfix] Warm up FlashInfer kernels on an autotune cache hit

[Upstream PR](https://github.com/vllm-project/vllm/pull/65148) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

> Draft for discussion: the fix is not settled.

## Problem

The FlashInfer autotune cache is not a compile cache: it stores tactics, not compiled kernels. On an autotune cache hit, startup does not execute the kernels serving will use, so FlashInfer's MXFP8 CuTe DSL kernels JIT-compile on live requests. #63088 made this worse by skipping the one forward that still ran on an autotune cache hit.

| Autotune cache at startup | p50 TTFT (s) | p90 TTFT (s) | Completed in rate |
| --- | --- | --- | --- |
| empty (tunes at startup) | 2.15, 2.16 | 3.01, 3.12 | 98% |
| warm | 5.51, 5.58 | 7.68, 7.70 | 92% |

MiniMax-M3.1-Flash, PP2 on 2x GB300, prefill-only Poisson load at 6.5 req/s. The tactics are identical, since every FlashInfer tuned op hits the loaded autotune cache. On a warm start both GPUs idle for 12 s at the start of serving while kernels compile.

## Root cause

Which warmup compiles each kernel class (PP2, logged per CuTe DSL / Triton compile from process start):

| Kernel class | Cold start: compiled by | Autotune cache hit (main) | Autotune cache hit, dummy runs restored |
| --- | --- | --- | --- |
| FlashInfer MXFP8 GEMM (`mm_mxfp8` CuTe DSL, one kernel per tactic) | autotune profiling, all token buckets | 44-51 compile during serving (20-24 s) | the dummy run's bucket only; 38-39 still compile during serving (19 s) |
| FlashInfer MXFP8 activation quantize (`mxfp8_quantize`, called by vLLM's MXFP8 linear; variants by K and size flags) | profile run, CUDA graph capture, autotune dummy run | prefill-size variants compile during serving (~0.5 s) | covered |
| vLLM CuTe DSL kernels (fused RMSNorm+MXFP8, dense MXFP8 GEMM, router GEMM, fused QKV epilogue) | profile run, JIT warmup registry, CUDA graph capture | covered | covered |
| MiniMax-M3 sparse attention | MSA warmup (prebuilt kernels + 16-token mixed batch) | covered | covered |
| vLLM Triton kernels (incl. the indexer gather, warmed only by the dummy run) | various | first use is a disk-cache load (~0 s) | same |

- #63088's skip uncovers FlashInfer MXFP8 kernels only: the GEMM tactics for the dummy run's token bucket, plus the activation quantize variants used at prefill size. On this model, other kernel classes are warmed by other mechanisms.
- The larger part is pre-existing: the autotune cache stores tactics, not kernels, so a hit leaves the other buckets' GEMM tactics uncompiled, with or without #63088.
- Affected: the #63088 skip, v0.33.0 and main with the per-rank autotune cache (PP > 1, multi-rank, multi-node, elastic EP). The uncompiled tactics, also v0.32.x and single-rank (v2 autotune cache).

## Measured (warm autotune cache)

| Change | p50 TTFT (s) | Engine init (s) | CuTe DSL compiles during serving |
| --- | --- | --- | --- |
| main | 5.27-5.58 (4 runs) | 45 | GEMM + quantize, 20-24 s |
| restore the dummy runs on an autotune cache hit (pre-#63088) | 4.36-4.55 (3 runs) | 48 | GEMM, 19 s |
| + dummy forward at both ends of every token bucket (probe) | 2.15, 2.19 | 56 | none |

The probe shows that full coverage fixes the stall, but it is not a fix: about 40 forwards to reach about 50 kernels, and it depends on model dispatch (MiniMax-M3 takes a fused QKV path at M >= 512, so the 512 bucket's GEMM tactic runs only for M in 257..511).

## Scope

- **This PR:** restore the dummy runs on an autotune cache hit (fixes the #63088 regression).
- **FlashInfer (follow-up):** on an autotune cache hit, compile each cached tactic once (e.g. via the runner's `precompile_tactics`). A persistent compile cache for `mm_mxfp8` / `mxfp8_quantize` (`build_and_load_cute_dsl_kernel`, as `mm_fp4` uses) would make restarts cheaper, but it can miss.
