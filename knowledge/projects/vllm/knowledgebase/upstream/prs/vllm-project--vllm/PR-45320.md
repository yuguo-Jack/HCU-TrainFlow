# [Bugfix] Reject NVFP4 MoE checkpoints with missing per-expert scales

[Upstream PR](https://github.com/vllm-project/vllm/pull/45320) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Fixes #45212; #51525 reports the same failure on another checkpoint. ModelOpt can omit per-expert `input_scale` keys when calibration never routes tokens through an expert, and a missing `input_scale` or `weight_scale_2` key leaves `torch.empty` storage in the MoE layer. The garbage can look finite, so the model loads and later produces invalid activations and empty completions. `ModelOptNvFp4FusedMoE` now fills those scales with NaN at creation and rejects the checkpoint at load if any expert row is still NaN, zero or infinite.

## Claims

- A ModelOpt NVFP4 MoE checkpoint with missing or zero per-expert scales fails in `process_weights_after_loading`, before any scale inversion or kernel-format conversion, with a `ValueError` naming the layer, the parameter and the expert ids.
- Weight scales (`w13_weight_scale_2`, `w2_weight_scale_2`) are always required. Activation scales are required only by backends that read them; HUMMING (with its default input schema), MARLIN, FLASHINFER_B12X (quantizes the FC1 input itself and sets `a2_gscale` to 1.0), FLASHINFER_MOE_EP_CUTEDSL (drops them) and B12X in A16 mode (decided by the oracle's `_use_a16`) do not, so the check skips them.
- With the per-token activation override (#56740) both activation scales are set to 1.0 before the check, so per-token mode loads without them and still rejects missing weight scales.
- Fail-fast only: no missing calibration value is guessed.

- The four new tests (24 cases): 24 passed. With `modelopt.py` reverted to main, 15 failed and 9 passed: every case that expects a rejection fails with `DID NOT RAISE`, and the cases that expect a checkpoint to load pass on both, so they guard against false rejections.
- `ruff check`, `ruff format --check` (v0.14.0) and the mypy pre-commit hook pass on both changed files.

The tests:

2. `test_modelopt_nvfp4_moe_process_validates_before_conversion`: a missing scale raises before kernel-format conversion and kernel construction.

4. `test_modelopt_nvfp4_moe_ep_validates_only_local_experts`: EP rank 1 of 2 (8 global experts) loads scales through `RoutedExperts.weight_loader`; scales missing for the other rank's experts are accepted, and a missing scale on a local expert raises with its local id.

Model runs on one RTX PRO 6000 with `nvidia/Qwen3-30B-A3B-NVFP4` (FLASHINFER_CUTLASS backend), from an earlier head. The check has not changed for FLASHINFER_CUTLASS since then; later commits narrowed the activation-scale check for the backends listed above and reuse `_use_a16`:

- The unmodified checkpoint loads and generates on this branch and on main.
- A copy missing `input_scale` and `weight_scale_2` for experts 0 and 1 of layer 0: main loads and generates without error; this branch stops at load with `ValueError: ... layer 'model.layers.0.mlp.experts': 'w13_weight_scale_2' has zero or non-finite values for expert ids [0, 1].`
- With only `input_scale` removed for the same experts, main again loads silently and this branch names `'w13_input_scale'` for expert ids `[0, 1]`.

@AubinGil also confirmed the rejection on the #51525 checkpoint (SM120) in [this comment](https://github.com/vllm-project/vllm/pull/45320#issuecomment-5663066947).

## Details

- Root cause: `create_weights` allocated the four per-expert scale tensors with `torch.empty`, and nothing checked that the checkpoint filled every expert row. The NaN sentinel makes an unloaded row detectable; main's NVFP4 linear path already initializes its block weight scale to NaN for the same reason.
- Zero is rejected on every backend that reads activation scales, including the FlashInfer backends with global scale factors, where the max over experts would hide one zero row. A zero row only breaks scaling on backends that invert each expert's scale, but it marks the same incomplete calibration everywhere, so the load fails the same way on every backend.
- Not a duplicate. Open PRs on 2026-10-17: `gh pr list -R vllm-project/vllm --state open --search "45212 in:body"` and `--search "51525 in:body"` return only this PR; `--search "NVFP4 MoE missing scales"` adds #54444, which checks linear layers, not MoE experts, plus unrelated work; `--search "input_scale experts nvfp4"` adds #62036 (W4A16 layerwise reload that ignores a legacy `input_scale`), #55073, which reconciles mismatched w13 global scales in the same `process_weights_after_loading` and does not check for missing scales, and other unrelated work.
- Limits:
  - Expert parallelism is covered only by the simulated single-process test. No multi-GPU EP run.
  - On FlashInfer backends with global activation scale factors, the activation scales span all global experts on every rank and are checked across all of them; the EP test does not cover that case.
  - Expert ids in the error are row indices of the checked tensor: rank-local for weight scales, global for activation scales on backends with global scale factors.
  - The pre-processed weights path returns before the check and is not covered.
  - Only zero and non-finite scales are rejected. A tiny positive scale whose reciprocal overflows still loads, as on main: `txn545/Qwen3.5-122B-A10B-NVFP4` (#42601) has `down_proj.input_scale` (`w2_input_scale`) = 1.3803e-41 for expert 82 of layer 8, which becomes an infinite scale factor on backends that invert each expert's scale.
  - Online re-quantization from a ModelOpt NVFP4 checkpoint (#60276) dequantizes through `dequantize_weight` and does not run this check; a missing `weight_scale_2` there now reads NaN instead of uninitialized memory.

- taking-lying-flat · comment · 2026-08-09T02:13:27Z · [source](https://github.com/vllm-project/vllm/pull/45320#issuecomment-5229319743)

@AubinGil I reproduced the failure from #51525 on Linux and traced it to the same missing per-expert activation scales addressed by this PR.

Environment: vLLM 0.24.0, PyTorch 2.11.0+cu130, RTX 5090 (SM120), and `bg-digitalservices/Gemma-4-26B-A4B-it-NVFP4`. With `VLLM_CUTLASS`, the system+user reproducer returned 48 pad tokens and stopped at `max_tokens`; changing only the MoE backend to Marlin returned `The capital of France is Paris.`

Checkpoint inspection found 25 experts across 12 layers with missing `input_scale` entries. Layer 0 is missing experts `[40, 42, 82, 98]`, exactly the set reported in #45212. Filling only those missing activation-scale slots with the per-projection median of the loaded finite scales recovered the CUTLASS reproducer 3/3. This establishes that the failure is not a general CUTLASS kernel problem: uncalibrated experts leave holes in the ModelOpt checkpoint, and the CUTLASS activation-quantized path consumes those holes.

There is one reliability issue with the current validation approach in this PR: current `main` allocates `w13_input_scale`, `w2_input_scale`, and the per-expert secondary weight scales with `torch.empty`. A missing checkpoint key is therefore not guaranteed to leave a zero or non-finite value; it can leave an arbitrary finite nonzero value, so `(scale == 0) | ~scale.isfinite()` can miss the incomplete load.

I suggest initializing scale slots that must be loaded from the checkpoint with a NaN sentinel, then validating before `convert_to_nvfp4_moe_kernel_format`. The existing Marlin gate is important because Marlin drops activation scales.

The preferred policy should remain fail-fast:

1. By default, raise a `ValueError` naming the missing parameter and expert/slot ids, explaining that calibration did not route through every expert.
2. As an explicitly enabled best-effort fallback only, fill missing **activation** scales with the median of the loaded finite values for the corresponding projection/shard and emit a prominent warning listing the repaired slots. This should not be silent or the default, because no imputation can recover the absent expert calibration statistics. Missing weight scales should still be a hard error.

The full Linux model test confirms that fail-fast prevents the HTTP 200/pad-token corruption, while the Marlin path remains unaffected.

Three things from reading the diff:

1. **The `is_weights_pre_processed()` branch returns before the validation call.** That path requires `FLASHINFER_TRTLLM`, which falls into the `else` arm of `_validate_loaded_expert_scales` and therefore does consume both activation scales — so a pre-processed checkpoint with the same holes would still load silently. Deliberate?

2. **The message does not say which layer.** This checkpoint has 25 affected experts across 12 layers, and `[40, 42, 82, 98]` alone does not tell you it came from layer 0. `RoutedExperts` already carries `self.layer_name` (`fused_moe/routed_experts.py:86`), so including it is a one-line change that makes the error directly actionable.

3. **`(per_expert == 0)` is broader than the sentinel requires.** With NaN initialization a missing slot is deterministically non-finite, so `~isfinite` alone identifies it. Is a legitimately calibrated zero activation scale possible? If so this would turn a valid checkpoint into a hard startup failure.

Unrelated to this PR but worth flagging for anyone reproducing: when EngineCore raised, the `APIServer` frontend did not exit — it stayed alive until I killed it.
