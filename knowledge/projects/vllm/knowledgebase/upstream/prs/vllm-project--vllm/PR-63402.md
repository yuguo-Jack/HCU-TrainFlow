# [ROCm][Quantization] Add int8 lm_head quantization (per-channel and per-group-32) for RDNA (gfx11/gfx12)

[Upstream PR](https://github.com/vllm-project/vllm/pull/63402) · state: open · merged: False

## Original PR description

Builds on #62708 and should merge after it; only the last commit is new here. It adds two values to `KernelConfig.lm_head_quantization`:

- `int8_per_channel`: symmetric int8 with one scale per output channel.
- `int8_per_group_32`: symmetric int8 with one scale per 32 input channels.

At load time, an unquantized fp16/bf16 lm_head is quantized and then run on a new RDNA W8A16 op. Both schemes share the op, the quantizer and the method class; the group size is a class attribute.

Many 4-bit checkpoints leave the lm_head in fp16/bf16. Decode reads the whole head on every step, so on bandwidth-bound RDNA it is often one of the largest per-token costs. Int8 halves that read. Int4 (#62708) cuts it further, but int8 keeps accuracy at the bf16 level, which lets users trade speed against accuracy. `int8_per_group_32` gives up about 1 % of TPOT against `int8_per_channel` for a third fewer flipped top-1 tokens.

```bash
vllm serve <model> --kernel-config.lm_head_quantization int8_per_channel
vllm serve <model> --kernel-config.lm_head_quantization int8_per_group_32
```

**Hardware:** all testing, benchmarks and evals below were run on gfx1151 (Strix Halo) only. The op is enabled for gfx11/gfx12 like #62708's int4 path, but has not been validated on other RDNA GPUs.

## Design

- **One op for both schemes.** `rdna_w8a16_apply` takes scales `[N]` (per channel) or `[N, K // group_size]` (per group); the group size is implied by the scale shape, as in `cutlass_scaled_mm`. No op signature changes between the two schemes.
- **HIP decode kernel (`wvSplitK_int8`, M ≤ 5):** a `GROUP_SIZE` template parameter (0 = per channel). With groups, each thread's 16-weight chunk lies in one group, so its partial dot is scaled once in fp32. Scales are loaded non-temporally next to the weights; cached loads measured ~6 % slower.
- **Triton kernel (everything else):** the per-group path scales each group's fp32 partial dot instead of dequantizing the weight. Dequantizing would round every `q * scale` to bf16, which costs about as much accuracy as the int8 quantization itself. It has its own tile table: with the per-channel tiles it ran up to 5x slower from M = 32 on.
- **Adding group sizes:** a new size (e.g. 128) is a `Literal` value, a three-line `Int8LMHeadMethod` subclass (`scheme`, `group_size`, `k_align`) and one `case` in the HIP dispatch. The quantizer and the Triton kernel are already generic.

- **TPOT:** the int8 saving tracks the head size: half of vocab × hidden × 2 bytes at ~230 GB/s, i.e. 1.5–6 ms per token. The relative gain is largest where the head is a big share of decode reads: small models and large vocabularies. `int8_per_group_32` reads 1/16 more bytes for its scales and costs 0.3–1.5 % TPOT against `int8_per_channel`.
- **TTFT:** prefill still computes logits for the last position, so TTFT moves by about one decode step's head saving (2–4 ms). That is only visible at short prompts; at 1920 input tokens it is within noise.
- **Weights:** untied heads (Llama-3.1, Qwen3.6) shrink by half the head. Tied heads (Qwen3-4B, Gemma-4) grow by the int8 copy, because the embedding stays fp16/bf16.

## Accuracy

Teacher-forced next-token scoring of the lm_head alone, on AIME problem and solution text (203,813 tokens), Qwen3.6-35B-A3B W4A16 (compressed-tensors) on gfx1151, measured at this PR's head. Each row is compared against the unquantized head:

| lm_head | Perplexity Δ | Top-1 agreement | Mean \|Δlogprob\| |
|---|---|---|---|
| `int4_per_group_32` (#62708) | +0.40 % | 97.56 % | 0.0491 |
| `int8_per_channel` | +0.00 % | 99.66 % | 0.0071 |
| `int8_per_group_32` | +0.00 % | 99.77 % | 0.0047 |

Int8 changes the top-1 token 7–11x less often than int4. `int8_per_group_32` flips a third fewer top-1 tokens than `int8_per_channel` and has a 34 % lower logprob error. The real kernels give exactly the same predictions as an exact fp32 simulation of the `int8_per_group_32` weights (100.00 % top-1, mean |Δlogprob| 0.0000).

## Tests

- `tests/kernels/quantization/test_rdna_lm_head.py` (shared with #62708): each scheme is a `Scheme`, so config dispatch, the setup checks, shape and dtype errors, tied and untied weight handling, and output against a dequantized reference (M ∈ {1, 4, 5, 6, 32, 256}, both dtypes) run for all three. Error against the full-precision head is bounded at 0.015 for `int8_per_channel` (measured 8.4e-3) and 0.0075 for `int8_per_group_32` (measured 5.5e-3, so per-channel scales would fail it). The int8 quantizer tests (error at most half a scale step, codes within ±127, chunked equals unchunked) run per channel and per group.
- `tests/kernels/quantization/test_rdna_w8a16.py`, per channel and per group where scales matter:
  - The op, `wvSplitK_int8` (M = 1–5) and the Triton kernel against an fp32 reference, both dtypes, including a ragged N and K.
  - Input validation, including an unsupported group size.
  - Both dispatch paths and the boundaries between them, including a K that the HIP kernel cannot take.
  - Padded weight rows.
  - Weight offsets past 2^31.
- **316 tests pass** on gfx1151. The GPU tests need a gfx11/gfx12 GPU, so CI (CDNA) runs only the CPU tests. `pre-commit run --files <changed files>` is clean.

## Notes for reviewers
