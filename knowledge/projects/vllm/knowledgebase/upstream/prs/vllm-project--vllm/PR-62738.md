# [Frontend] Use VLLMValidationError for client input errors in renderers base

[Upstream PR](https://github.com/vllm-project/vllm/pull/62738) · state: closed · merged: True

## Original PR description



## Overview

Part of #48227 (Step 5). Switches the remaining client-input `ValueError`s in `vllm/renderers/base.py` to `VLLMValidationError` with `parameter` set. The file already raises `VLLMValidationError` for out-of-vocabulary token ids and `truncate_prompt_tokens`; these seven sites were the leftovers.

## Claims

- Seven raise sites in `BaseRenderer` now raise `VLLMValidationError` with `parameter` set. The message strings are unchanged.
- HTTP: these were already 400 through the raw-`ValueError` fallback in `create_error_response`. They now go through the `VLLMValidationError` branch, so `param` is filled instead of `null`. Like every `VLLMValidationError`, the message gets a ` (parameter=...)` suffix.
- The deprecated raw-prompt path of `AsyncLLM.generate()` (`InputProcessor.process_inputs` -> `render_cmpl`) only re-raises `VLLMClientError` since Step 3. These checks used to be wrapped into `EngineGenerateError` there. Now they surface as validation errors.

## Validation

Tests (CPU only, no model weights). No new tests. The existing checks that expected `ValueError` now expect `VLLMValidationError`:

- `tests/renderers/test_completions.py`: `test_empty_input`.
- `tests/renderers/test_process_multi_modal_uuids.py`: `test_multi_modal_uuids_length_mismatch_raises` (both cases) and `test_multi_modal_uuids_missing_modal
ity_raises`.

Commands (WSL Ubuntu 22.04, Python 3.12, CPU torch, `VLLM_TARGET_DEVICE=cpu`):

```bash
pytest -q tests/renderers/test_completions.py                # 43 passed
pytest -q tests/renderers/test_process_multi_modal_uuids.py  # 13 passed
pytest -q tests/renderers                                    # 642 passed, 3 failed (all environmental: 2 gated HF repos, 1 model-weight download blocked loc
ally; the same 3 fail on main)
pre-commit run --files tests/renderers/test_completions.py tests/renderers/test_process_multi_modal_uuids.py  # all hooks passed
```

Error body for `POST /v1/completions` with `{"prompt": []}`, as built by `create_error_response` from the exception each version raises:

```json
// before
{"error": {"message": "You must pass at least one prompt", "type": "BadRequestError", "param": null, "code": 400}}
// after
{"error": {"message": "You must pass at least one prompt (parameter=prompt)", "type": "BadRequestError", "param": "prompt", "code": 400}}
```


## Details

**Not a duplicate.** No open PR touches these sites, and no comment on #48227 claims `vllm/renderers/`. The latest claim there (TylerMa-debugg, 2026-10-04) is the pooling entrypoints only. Searched open PRs for `VLLMValidationError renderers`, `multi_modal_uuids VLLMValidationError`, `prompt_embeds VLLMValidationError` and `48227`, and found nothing.

**Sites changed:**

| Site | Check | `parameter` | Reached from |
|---|---|---|---|
| `render_prompts`, `render_prompts_async` | empty prompt list | `prompt` | `/v1/completions` with `"prompt": []` (the `CompletionRequest` validator only treats `None`/`""` as empty); `LLM.generate([])` |
| `_validate_mm_uuids` (3 raises) | uuid missing for an empty modality or item; uuid list length differs from data | `multi_modal_uuids` | Per-item case: a chat `image_embeds: null` part with no `uuid` (with `--enable-mm-embeds`), or `/inference/v1/generate` `content_parts` with neither `url` nor `uuid`. All three: prompts passing `multi_modal_data`/`multi_modal_uuids` (`LLM.generate`, raw `AsyncLLM` prompts) |
| `_process_embeds` (2 raises) | `--enable-prompt-embeds` not set; tensor not 2D | `prompt_embeds` | Raw-tensor `EmbedsPrompt` from `LLM.generate` or `AsyncLLM`. HTTP `prompt_embeds` already fails the same checks earlier in `safe_load_prompt_embeds`, which uses `parameter="prompt_embeds"`, so both paths now match |

`multi_modal_uuids` names the field the message already refers to. Chat clients set `uuid` per content part, but `BaseRenderer` doesn't know which endpoint it is serving, so it uses the prompt-level name.

**Left unchanged:**

- `get_tokenizer` ("Tokenizer not available when `skip_tokenizer_init=True`") and `get_mm_processor` ("Multi-modal processor not available for text-only models"): these are server-configuration checks, so they need their own classification and are not request validation.
- The `TypeError`s in `_tokenize_singleton_prompt{,_async}`: these are prompt-type invariants that run after parsing.
- The `RuntimeError`s (no decoder start token, detokenizing embeddings): these are internal.

**Compatibility.** `VLLMValidationError` no longer subclasses `ValueError` (Step 1). Offline code that catches `ValueError` around these errors needs `VLLMValidationError` instead. This is the same trade-off #53432 made for `LLM.generate` input checks. I found no `except ValueError` in `vllm/` that wraps these call paths. Online, they reach the global `VLLMError` handler.
