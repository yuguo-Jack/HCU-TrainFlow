# [Bugfix][Kernel] Fit Triton prefill attention tiles for 256-wide heads in shared memory (EmbeddingGemma 2 support)

[Upstream PR](https://github.com/vllm-project/vllm/pull/60631) · state: open · merged: False

## Original PR description



## Overview

`context_attention_fwd` (Triton prefill attention, used for encoder/bidirectional attention) uses 128-row tiles on
compute capability >= 8.0. For 256-wide heads those need 160KB of shared memory per block, more than RTX 30/40/50,
RTX PRO 6000 and GB10 have (~99KB), so e.g. EmbeddingGemma 2 (#60254) fails to start with `OutOfResources`.
This uses 64-row tiles (72KB) for 256-wide heads on CUDA devices with < 160KB per block.

## Claims

- Encoder attention with 256-wide heads runs on ~99KB-shared-memory NVIDIA GPUs (sm_86/89/120/121) instead of
  failing with `OutOfResources: Required: 163840, Hardware limit: 101376`; e.g. `google/embeddinggemma-2` now
  serves on an RTX PRO 6000.
- No change on GPUs with >= 160KB per block (A100/H100/B200 keep 128-row tiles), for heads < 256 wide, or on ROCm.

## Validation

RTX PRO 6000 Blackwell (sm_120, 99KB/block), vLLM @ e161a07 (`VLLM_USE_PRECOMPILED=1 uv pip install -e .`),
transformers 5.19.0.

`pytest tests/kernels/attention/test_triton_prefill_attention.py` (this PR adds `D=256` to `test_context_attention`
and `test_wide_head_tile_fits_shared_memory`):

| | Result |
|---|---|
| main + new tests | the 4 bf16 `D=256` cases fail with `OutOfResources: Required: 163840, Hardware limit: 101376` |
| this PR | 36 passed |

`google/embeddinggemma-2` end to end (`runner="pooling"`), vs SentenceTransformers bf16 on 53 queries, 53 passages,
32 page images:

| | Result |
|---|---|
| main | engine fails to start (same `OutOfResources`) |
| this PR | cosine to ST: mean 1.000, min 0.996; same top-1 query→passage for 98%; 40 ms/query, 657 passages/s |

Shared memory of `_fwd_kernel` measured on sm_120 (bf16): head 256 at 128×128 tiles: 160KB; at 64×64: 72KB;
head 512 at 32×32 (existing cap): 66KB.

## Details

- Root cause: `get_block_size()` returns 128 for 16-bit dtypes on capability >= 8.0; #60254 capped 512-wide heads
  to 32 rows but 256-wide heads still get 128. CI's L4 (Ada, ~99KB) should hit the new `D=256` cases without the fix.
- CUDA only, following #39018 (same pattern for `triton_unified_attention` / FlexAttention with 512-wide heads on
  Turing; different kernel, not a duplicate). ROCm has its own tiling (`_prefer_narrow_kv_tile`) and is untested
  here: the new `D=256` test cases also run in the MI300 mirror.
- `get_max_shared_memory_bytes()` is cached, so the check costs nothing per call.
- Motivation: EmbeddingGemma 2 (740M) is a natural fit for workstation and consumer GPUs, but on Blackwell RTX-class
  parts (RTX 50-series, RTX PRO Blackwell, DGX Spark) it can't start in vLLM: FlashAttention rejects its 256-wide
  heads there, so encoder attention falls to this kernel, which needs more shared memory than they have.
- AI assistance (Claude) was used to investigate, write and validate this change. The changes were reasonably concise and simple. I reviewed all of the code changes and corresponding test cases.

Verified on GB10 (sm_121, 101376 B, triton 3.7.1): head-256 bf16 goes from `Required: 163840` to passing at BLOCK=64, and A100 keeps 128. One gap: fp32 at head 512 still overflows (`Required: 135168` at the capped BLOCK=32; 16 fits). The measured allocation is `(2 * BLOCK_DMODEL + BLOCK) * BLOCK * element_size` (exact across D 64–512, bf16/fp32, BLOCK 16–128), so fitting against that instead of the fixed threshold covers both cases.
