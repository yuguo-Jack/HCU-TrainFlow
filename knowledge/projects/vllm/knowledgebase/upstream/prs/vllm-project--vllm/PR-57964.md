# [Bugfix][Spec Decode] Raise a DFlash or DSpark draft's max_position_embeddings to the target's max_model_len

[Upstream PR](https://github.com/vllm-project/vllm/pull/57964) · state: closed · merged: False

## Original PR description


## Purpose

A DFlash draft checkpoint ships `max_position_embeddings` equal to its target's native context. When the target is served with a longer context (`--hf-overrides`, YaRN), the draft's rotary `cos_sin_cache` is still sized from the draft's own value while the drafter is handed the target's absolute positions for its context KV, so the first request longer than the draft's value reads past the end of that cache and takes the engine down with a CUDA illegal memory access. The access is asynchronous, so the traceback usually lands in the target model's next GEMM rather than in the drafter.

Reported in #57941 (target extended to 393216 with `--hf-overrides`, draft `z-lab/Muse-Glimmer-30B-DFlash2` at 131072; a 150k-token request kills the engine) and independently in a comment on #55279 (target at 1M through YaRN, draft `incoai/Qwen3.8-27B-DFlash2` at 262144; the first request over 512k kills it).

This is a V2 model runner failure, which is the default runner since 0.29.0. The V1 runner keys `effective_drafter_max_model_len` on the draft's own `max_model_len` (the smaller of the draft config's value and the target's) and `_input_fits_in_drafter` stops drafting for a batch that exceeds it, so on V1 the same request just runs without speculation. The V2 speculator has no such gate: it works from the target's `max_model_len` and drafts at every length the target accepts.

`SpeculativeConfig._maybe_override_draft_max_position_embeddings` already handles this for EAGLE drafts (#49343, for #48894) by raising the draft's `max_position_embeddings` to the target's `max_model_len` so the cache is sized for every position the drafter can see, but it only runs for `eagle` and `eagle3`. DFlash drafts share the target's positional space in the same way (`qwen3_dflash.py`, `qwen3_dflash2.py` and `laguna_dflash.py` all size their rope from the draft config's `max_position_embeddings`), and the issue's workaround, editing that value in a local copy of the draft's config, is exactly what the override does.

DSpark drafts are built the same way: `Qwen3DSparkModel` and `Gemma4DSparkModel` subclass the DFlash model and size their rope from the same value, and a speculators-format DSpark config is flattened from `transformer_layer_config`. A comment below reports the same crash past 262,144 tokens with `RedHatAI/Qwen3.8-27B-speculator.dspark`, fixed by raising that value by hand.

## Changes

`vllm/config/speculative.py`: apply the existing override to `dflash` and `dspark` as well, and say so in the comment, the docstring and the log line. No new code path; DFlash and DSpark drafts now get the same treatment as an EAGLE draft.

`tests/config/test_speculative_draft_max_position_embeddings.py`: a CPU-only case, run for a DFlash draft (`z-lab/Qwen3-4B-DFlash-b16` on `Qwen/Qwen3-4B`) and a DSpark draft (`deepseek-ai/dspark_qwen3_8b_block7` on `Qwen/Qwen3-8B`), both at 40960, with the target served at 65536 through `hf_overrides`; the draft's `max_position_embeddings` must come out as 65536 with the override logged. The existing `draft_model` case still checks that an independent draft keeps its own limit.

Two things this does not change:

- `draft_model_config.max_model_len` is computed before the override and stays at the draft's original value, so the V1 runner keeps skipping speculation past it while V2 now drafts there. That is how EAGLE behaves today; making the two runners agree means refreshing that value after the override, which touches EAGLE on V1 too and is better done separately.
- V2 has no drafter-capacity gate at all, so an independent `draft_model` drafter with a shorter context than the target hits the same illegal access on V2, and for it the answer is to skip rather than resize. That is a separate change.

The cache grows with the target's context: about 6 MB for 40960 to 65536 here, about 270 MB for the 262144 to 1M case in #55279. A draft whose own config uses YaRN sizes its cache from `original_max_position_embeddings` and is not affected by this value; neither shipped DFlash draft does.

## Test Plan

- `tests/config/test_speculative_draft_max_position_embeddings.py` on main 6ad2e06c4, on the previous head of this PR (DFlash only) and on this PR; the new cases must fail where the method is not covered.
- Real server, vLLM v0.29.0 wheel with only this change overlaid, RTX 6000 Ada, `--enforce-eager`: `Qwen/Qwen3-4B` with `--max-model-len 65536 --hf-overrides '{"max_position_embeddings": 65536}'` and `--speculative-config '{"method": "dflash", "model": "z-lab/Qwen3-4B-DFlash-b16", "num_speculative_tokens": 8}'`. Send a 30k-token completion (inside the draft's 40960), then a 50k-token one, then a short one, checking `/health`, the server process and the spec-decode counters in `/metrics` after each. Run on the V2 runner (default) and on V1 (`VLLM_USE_V2_MODEL_RUNNER=0`).

The config-edit equivalent of this PR fixes the >262K crash for DFlash2 on our setup, and dspark needs the same treatment.

Could the check include `dspark`? `Qwen3DSparkModel` subclasses `DFlashQwen3Model` and sizes its rotary cache the same way, but the override is gated on the method name. With RedHatAI/Qwen3.8-27B-speculator.dspark's `transformer_layer_config.max_position_embeddings` raised to 1,010,000 by hand, DSpark K=8 also completed 979K-token prompts at 3.51 tokens/step.
