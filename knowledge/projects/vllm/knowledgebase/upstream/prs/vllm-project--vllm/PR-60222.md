# [Bugfix][Rust Frontend] Clean up failed LoRA loads and handle already-absent unloads

[Upstream PR](https://github.com/vllm-project/vllm/pull/60222) · state: open · merged: False

## Original PR description

## Overview

Fix Rust frontend LoRA lifecycle handling: compensate failed fresh loads
and accept already-absent adapters during unload.

## Claims

- Failed fresh loads remove the allocated adapter ID from every engine
  before returning an error.
- Failed in-place refreshes preserve the existing registration and avoid
  deleting its adapter ID.
- Cleanup failures report the adapter ID and both failure causes.
- Unload succeeds when an engine has already evicted the adapter.
- Genuine unload errors preserve registration so removal can be retried.

## Validation

From `rust/`:

- `cargo nextest run -p vllm-server --no-fail-fast`: **441 passed**, including LoRA failure, refresh, and unload regressions.
- `cargo clippy -p vllm-server --all-targets -- -D warnings`, `cargo fmt --all --check`, and `git diff --check`: passed.

LoRA regressions use mock engines; real-model serving evaluation remains pending.

## Details

A failed load can leave an adapter installed on engines that succeeded,
despite having no frontend registration. Compensation removes its fresh
ID using the existing update lock and utility fan-out, which waits for
every engine outcome before returning.

Removal returning false means the adapter was already absent. It should
not prevent deregistration after all engines complete without an error.

Compensation applies only to fresh IDs. Removing an existing ID after
a failed refresh could delete the previously served adapter. Atomic
in-place replacement and cancellation protection are outside this change.
Cleanup remains best effort when an engine returns a removal error.
