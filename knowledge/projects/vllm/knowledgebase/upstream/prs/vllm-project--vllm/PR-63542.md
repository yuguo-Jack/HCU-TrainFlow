# [ROCm][Bugfix] Fix ROCM_AITER_FA extend/prefill split bug

[Upstream PR](https://github.com/vllm-project/vllm/pull/63542) · state: open · merged: False

## Original PR description

## Overview

split_decodes_prefills_and_extends assumed extends precede new prompts (MRV1's behavior), which MRV2 does not guarantee (it only puts decodes first). An extend that followed a new prompt was classified as a prefill and attended without its KV cache context. This will silently downgrade the output quality. In some of my tests, the PPL could increase 8%+. 

Only the leading decodes and the trailing run of requests without context are now separated; everything in between goes through the extend path, which handles zero-context rows correctly. The extend context workspace is split only among requests that actually have context, so interleaved new prompts do not inflate the number of context chunks.

This fix is compatible with MRV1.

- whx-sjtu · comment · 2026-10-26T07:34:32Z · [source](https://github.com/vllm-project/vllm/pull/63542#discussion_r4374886609)

File: `vllm/v1/attention/backends/utils.py` · line 776

This might not hold when the model has attention sinks (e.g. GPT-OSS full-attention layers). `extend_forward` in `rocm_aiter_fa.py` passes `sink_ptr=self.sinks` to the new-token call and to every context-chunk call, then merges the results, so the sink lands in the softmax denominator more than once. Rows that used to take the prefill path (one call, sink counted once) now pick up that error.

Fix: drop `sink_ptr=self.sinks` from the chunk-loop `flash_attn_varlen_func` call in `extend_forward`. Every row has at least one new token, so the new-token call always carries the sink exactly once. This also fixes the smaller, already existing error on rows with context.
