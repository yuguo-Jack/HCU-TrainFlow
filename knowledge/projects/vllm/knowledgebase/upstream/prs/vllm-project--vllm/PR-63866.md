# [Bugfix][HiSparse] Start async KV loads into still-read blocks after in-flight steps

[Upstream PR](https://github.com/vllm-project/vllm/pull/63866) · state: closed · merged: False

## Original PR description



## Overview

Alternative fix for the HiSparse P/D KV corruption diagnosed in #63827 (and #63811). It avoids #63827's host GPU sync and keeps HiSparse's readable-until-reused GPU cache, which #63858 turns off in P/D.

## Claims

- An async KV load (e.g. a NIXL read) into a block that HiSparse released but an in-flight step may still read now starts only after that step's output is processed.
- No CPU-GPU synchronization. Only the import that reuses such a block is delayed, by about one step; the rest of the batch is unaffected.
- No change for engines without HiSparse: only `unpin_blocks` creates such blocks, and only HiSparse calls it.

## Validation

- New CPU unit test in `tests/v1/core/test_deferred_block_free.py`, covering the held-back load and an abort while it is held back.
- **Pending:** cluster runs of the unit suites, and the P/D small-model repro from #63811 comparing base, #63858 and this PR on correctness (NaN logits rows) and decode throughput.

## Details

**Root cause** (see #63827): HiSparse releases clean resident pages with `BlockPool.unpin_blocks`. They count as free, but their owner keeps reading them until the pool hands them out. With overlapping batches, step N can still be reading such a block when step N+1's scheduling pass allocates it for an async load. The load is posted from the CPU and is not ordered after step N.

**Why `defer_block_free` doesn't cover it:** that mechanism keeps a block out of the free queue until the last step touching it is processed. These blocks are already in the free queue, and their owner reads them until the moment they are reused, so there is no earlier point to defer to. The only safe point is after the handout.

**Fix:**
1. `BlockPool` counts handouts of still-readable blocks.
2. If an async-load allocation reused one while steps are in flight (`processed_step_seq < sched_step_seq`, which is only possible when `defer_block_free` is on), the scheduler holds back `connector.update_state_after_alloc` (which starts the load) in `deferred_load_starts`. It is fenced on `sched_step_seq` and drained next to `_drain_deferred_frees()`.
3. The held request also gets `last_sched_seq`, so if it is aborted while held back, its blocks go through the fenced free path. It doesn't wait for a load completion that will never come; NIXL already handles finishing a request it was never told about.

**Tradeoffs / limitations:**
- Prefix-cache hit-source stats for a held-back request skip the per-tier breakdown (`hits_by_source=None`). The hit counts are still recorded. Some connectors (e.g. offloading) can only attribute tiers after `update_state_after_alloc`.
- The fence is conservative: it waits for all in-flight steps, not just those that scheduled the old owner.
