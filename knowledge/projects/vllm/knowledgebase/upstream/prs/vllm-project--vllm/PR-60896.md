# [Bugfix][Build] Build fused GDN MTP decode for SM80-SM90 with CUDA < 13

[Upstream PR](https://github.com/vllm-project/vllm/pull/60896) · state: closed · merged: True

## Original PR description

## Overview

`FUSED_GDN_DECODE_ARCHS` is set only inside the `CUDA >= 13.0` block of `CMakeLists.txt`. So every CUDA 12.x build, including the published cu129 images, ships without `fused_gdn_decode_post_conv_mtp` on all architectures, and GDN models fall back to the Triton spec-decode path. This PR builds the kernel for `8.0;8.6;8.9;9.0a` when CUDA < 13.0. The family targets (`10.0f;11.0f;12.0f`) still need CUDA 13.

Builds on #51674 (kernel, "only needs cp.async and BF16 math"), #52743 (Ampere declaration guard) and #53835 (SM110 target).

## Claims

- CUDA 12.9 builds include the fused GDN MTP decode kernel for SM80–SM90.
- No change for CUDA ≥ 13.0 builds.

## Validation

On A100-SXM4-40GB, with nvcc 12.9 and torch 2.13.0+cu129 from the `cu129-nightly` image (vLLM 81198e97 + this patch, `TORCH_CUDA_ARCH_LIST=8.0`):

| | `tests/kernels/fla/test_fused_gdn_post_conv.py` + `tests/kernels/mamba/test_gdn_fused_mtp.py` |
|---|---|
| Without patch | 71 passed, 29 skipped ("fused GDN decode MTP op is not built"), 2 failed (`test_fused_model_path_matches_reference[pure-mtp]`: the fused path is not called) |
| With patch | 102 passed |

- Configure prints `Building fused GDN decode for archs: 8.0`.
- End to end: serving Qwen3.8-Flash-Next-FP8 (TP8) logs `GDN spec decode kernel: cuda` instead of `Falling back to the Triton GDN spec decode path: ... is not built`.
- Kernel time at CUDA-graph replay, per-rank shape H=2, HV=6, K=V=128, 4 MTP tokens per request: 0.48–0.76× of the Triton path at 1–32 requests.

## Details

- Not tested here: SM86/SM89/SM90 on CUDA 12.x (same source and gate; only SM80 was built).
- Related open PRs #53807 and #54034 change only the `ops.h` guard, which #52743 already fixed.
