# [DARFT][Core][DP] Add an opt-in cross-DP prefill delayer (--dp-prefill-delayer)

[Upstream PR](https://github.com/vllm-project/vllm/pull/61834) · state: open · merged: False

## Original PR description



## Overview

The DP ranks of a MoE engine step in lockstep. When any rank has prefill, the step becomes a long mixed (and, on some backends, eager) step for every rank. Agentic multi-turn traffic makes prefill frequent, so decode keeps getting interrupted. `--dp-prefill-delayer` (opt-in, default off) aligns prefill across the ranks and protects the decode steps after a prefill. It follows ATOM's PrefillDelayer.

## Claims

Measured on a development branch with an earlier version of this change: DeepSeek-V4-Pro on 8x MI355X, DP8 attention + EP8, AgentX agentic workload, 1200 s runs, metrics over 300-1200 s, single runs per configuration.

| Concurrency | Configuration | P90 interactivity (tok/s/user) | P50 interactivity (tok/s/user) | Total tok/s/GPU | TTFT p50 (s) | Node |
|---|---|---:|---:|---:|---:|---|
| 64 | no delayer (`--prefill-schedule-interval 32`), mean of 2 runs | 16.65 | 31.03 | 22.0K | 3.76 | A, B |
| 64 | + prefill delayer (10 protected steps) | **45.54** | **56.89** | 22.2K | 8.63 | A |
| 128 | no delayer (`--prefill-schedule-interval 32`) | 7.29 | 11.96 | 23.8K | 7.47 | D |
| 128 | prefill delayer, 10 protected steps | 22.82 | 26.97 | 39.7K | 5.41 | C |
| 128 | prefill delayer, 20 protected steps | **26.36** | **28.92** | 38.6K | 10.03 | C |

- The c128 rows use a later recipe with other changes; they differ only in the prefill policy. The no-delayer c128 row ran on a different node of the same type.
- The trade-off is TTFT: prefill waits for the other ranks, and long prompts wait for alignment chunk by chunk.

Validation on this upstream branch is still to be added.

## Details

- **Protocol.** Once per engine step, each rank reports 6 ints in one CPU SUM all-reduce on the DP group: prefillable, pending prefill tokens (capped at `max_num_batched_tokens`), running decodes, KV usage >= 0.9, chunk in progress, prefill ran. Every rank then takes the same FIRE / HOLD decision for its next schedule.
- **Placement.** The all-reduce sits next to `_has_global_unfinished_reqs()`. Every rank reaches that point on every non-idle step (real, dummy and pause steps alike), which the existing DP state sync already relies on, so the extra collective cannot be skipped by one rank. The state resets at each DP wave boundary.
- **Rules (ATOM's), in order:**
  1. A step that ran prefill arms `--dp-prefill-delayer-protected-steps` (default 10) steps that HOLD while decodes run.
  2. FIRE if no rank has prefill, no rank decodes, or KV usage is high.
  3. FIRE after 200 held steps, or after 100 with a chunk in progress.
  4. HOLD until all ranks have prefill.
  5. FIRE when the pending tokens reach 0.9 x prefillable ranks x `max_num_batched_tokens`, or when the backlog stops growing for 10 steps.
- **HOLD scope.** HOLD defers all prefill compute, new requests and in-progress chunks, on every rank that has a decode to run. A rank with only prefill work still runs it: a rank that schedules nothing while its DP peers step hangs the engine (V2 model runner with speculative decoding; benenzhu/vllm#6).
- **Interaction with `--prefill-schedule-interval`.** The delayer replaces it; setting both is an error.
- **Cost.** Off: none. On: one 6-int `cpu_all_reduce_` per step on the DP group (114 us p50 on 8 ranks, vs 695 us for `dist.all_reduce`), with the configured CPU distributed timeout.
- **Not supported:** elastic EP, fault tolerance (both can change the DP size at runtime) and custom scheduler classes.
- **Relation to #51199** (cc @kjiang249). That PR coordinates releases through the DP coordinator (asynchronous, with acks and a 2-step lead); this one uses a synchronous per-step all-reduce in the engine loop and adds protected decode steps and a token fill target. We drove both decision functions in a CPU simulation of 8 lockstep ranks with agentic traffic:
  - #51199's all-ranks release rarely triggered; most of its releases came from its capacity and 30-pass fail-open bounds.
  - This delayer had 2-4x fewer mixed steps and about half the mean decode latency.
  - #51199 had about 3x lower TTFT.

  The two are complementary, and I am happy to merge efforts.

**Why `--prefill-schedule-interval` does not solve it here**

The interval coordinates *when* the DP ranks may prefill: they share the step counter, so on off-cadence steps every rank defers prefill. It does not coordinate *whether* they prefill: each rank decides from its own queue and sees nothing of the other ranks. Under agentic load this still lets prefill reach most steps:

1. After a release step, a rank whose waiting queue did not fit the token budget (`prefill_capacity_bound`) stops throttling and prefills on every step until the queue drains. The check is local to the rank, but one prefilling rank makes the step mixed for all 8 ranks. With 90-130K-token prompts at c128, some rank is often in this state. This is our reading of the c128 result; we have not counted the mixed steps yet.
2. A cadence step runs whatever prefill each rank has, even one small chunk on one rank, and the other ranks pay a full mixed step for it.

The delayer adds the missing state exchange. Once per step the ranks all-reduce a few counters (pending prefill tokens, running decodes, KV pressure), and every rank takes the same decision. It fires when the pending tokens across the ranks reach about 90% of their budget, then keeps the next N steps decode-only.


**Next steps**

This PR is at an early stage. Our next goal is to lower TTFT, or at least bound it so that a TTFT SLA can be met:

1. A time-based bound: release when the oldest waiting prefill has waited longer than a configured budget in ms.
2. A sweep against interval 8 / 16 (with and without the long-prefill threshold) across concurrency, reported as throughput vs E2E-normalized interactivity and throughput vs TTFT.
3. A looser alignment is a first candidate. We tried releasing with 6-7 of 8 ranks ready and a shorter partial-chunk hold, on the current recipe and against the same-node default. At about the same throughput (-1.8% to +1.3%), TTFT went down 28-39% and the E2E-normalized p90 went up 29-42%, while the ITL-only p90 went down 15-24%.

Also related: #54627 (just merged) has the same basic idea, holding prefill so that decode runs in longer stretches, but it applies only when data_parallel_size == 1. On MoE DP ranks it is a no-op. There, the existing cadence aligns when the ranks may prefill, but no rank sees the other ranks' queues. This PR adds that cross-rank state: one small all-reduce per step, so every rank takes the same prefill decision.
