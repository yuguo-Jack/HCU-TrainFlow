# [Bugfix] Flatten object-composition allOf in xgrammar validation to avoid silent AnySpec fallback

[Upstream PR](https://github.com/vllm-project/vllm/pull/60952) · state: open · merged: False

## Original PR description

## Overview

Multi-branch `allOf` JSON schemas silently degrade to `AnySpec` ("accept anything") under the xgrammar backend (mlc-ai/xgrammar#937). The existing mitigation (flag `allOf` as unsupported in `has_xgrammar_unsupported_json_features`, auto-fall back to guidance) does not hold in mixed traffic on V1: `StructuredOutputManager` locks one backend per engine, so a guidance-resolved `allOf` request arriving on an engine that already locked xgrammar is still compiled by xgrammar and silently degrades to `AnySpec` (observed on a live deployment; see isolation data in vllm-project/vllm-ascend#18173).

This PR flattens **object-composition** `allOf` (all branches object-typed -- the common property-mixin pattern) into a plain object schema in `validate_xgrammar_grammar`, so those schemas are compiled by xgrammar directly: no backend switch, no reliance on the fallback.

Refs: #56556

## Claims

- Object-composition `allOf` schemas now compile and constrain correctly with the xgrammar backend.
- Mixed scalar/object `allOf` branches (e.g. `allOf: [{"type": "string"}, {"enum": ["yes", "no"]}]`) are intentionally left untouched and keep the existing fallback behavior -- no behavior change there.
- Single-branch and empty `allOf` are untouched.

## Validation

- New unit tests in `tests/v1/structured_output/test_backend_xgrammar.py` (`TestMergeAllof`):
  - flattening correctness: union of `properties`, deduplicated union of `required`, `allOf` dropped, `type: object` defaulted, nested `allOf` flattened bottom-up, input schema not mutated;
  - mixed-branch nodes are left unchanged;
  - flattened schemas pass `has_xgrammar_unsupported_json_features`;
  - `validate_xgrammar_grammar` rewrites `so_params.json` to the flattened schema;
  - grammar semantics via `grammar_accepts`: the merged schema accepts the compliant object and rejects bare strings, missing-required and wrong-typed values (the pre-fix failure mode was accepting everything).
- Runtime-verified on a live Ascend P/D deployment (V1 + xgrammar 0.2.7): an `allOf` violation probe returned forced compliant objects 3/3 post-patch (was bare `true` pre-patch, i.e. AnySpec full-accept); flat-schema control unchanged; no 400s. Full isolation data (same prompt: 20/20 clean without `json_schema`, garbled with multi-branch `allOf`) in vllm-project/vllm-ascend#18173.

## Details

- `_merge_allof` only flattens when **every** `allOf` branch is object-typed (`type == "object"` or has `properties`): union of `properties`, deduplicated union of `required`, first-wins copy of other non-structural fields, drop `allOf`, default `type: object`. Anything else (scalar branches, non-list or empty `allOf`) is left unchanged.
- The merged schema is written back to `so_params.json` so the engine compiles the flattened schema too; `structured_output_key` re-serializes dict schemas, so the dict write-back is safe.
- If a flattened schema still contains other unsupported features (e.g. `multipleOf`), the existing unsupported-features fallback proceeds unchanged.
- Known limitation: overlapping scalar constraints inside object branches (two branches constraining the same property) merge first-wins, not by intersection.
