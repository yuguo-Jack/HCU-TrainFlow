# [Kernel] Add portable Triton FP8 E4M3 conversions

[Upstream PR](https://github.com/vllm-project/vllm/pull/55173) · state: open · merged: False

## Original PR description



## Purpose

Triton kernels that cast `tl.float8e4nv` directly cannot compile those conversions for SM80 and SM86, which blocks otherwise portable attention and DeepSeek V4 kernels with `ValueError: type fp8e4nv not supported in this architecture`.

Provide one reusable pair of dtype-dispatched Triton helpers backed by always-inline CUDA conversion routines linked from portable SM75 LLVM bitcode. This keeps conversion semantics in one implementation, supports FP16, BF16, and FP32 inputs, preserves direct FP32 rounding, and lets consumers retain native conversion paths where the architecture supports them.

The alternatives were to duplicate conversion code in every consumer or wait for every supported Triton version to lower these casts on pre-SM89 GPUs. A shared helper is smaller across the full call graph, gives every consumer identical saturating round-to-nearest-even behavior, and can be removed cleanly when native lowering covers the supported architectures.

This extracts the conversion layer from Michael's existing #49077 so attention and DeepSeek V4 changes can consume one prerequisite rather than carry private copies.

## Test Plan

The end-to-end consumer check uses this helper together with the co-pending DeepSeek V4 sparse-MLA and output-projection changes on four eight-GPU A100 nodes. The helper branch itself contains no model-specific dispatch; this Slurm job validates the production consumers that call it:

```bash
#!/bin/bash
#SBATCH --nodes=4
#SBATCH --ntasks=4
#SBATCH --ntasks-per-node=1
#SBATCH --gpus-per-node=8
#SBATCH --time=02:00:00

set -euo pipefail

export MODEL=nvidia/DeepSeek-V4-Pro-0813-NVFP4
export REVISION=2ff4ec53ee664e54571f670276d2c89d0fcc7b82
export MASTER_ADDR
MASTER_ADDR=$(scontrol show hostnames "$SLURM_JOB_NODELIST" | head -n1)
export MASTER_PORT=29501
export COMPILATION_CONFIG='{"cudagraph_capture_sizes":[1,2,4,8,16,32,64],"inductor_compile_config":{"enable_auto_functionalized_v2":true}}'

srun --nodes=4 --ntasks=4 --ntasks-per-node=1 bash -lc '
  headless=()
  if (( SLURM_NODEID > 0 )); then
    headless=(--headless)
  fi

  exec vllm serve "$MODEL" \
    --revision "$REVISION" \
    --served-model-name deepseek-v4-pro \
    --host 0.0.0.0 \
    --port 8000 \
    --trust-remote-code \
    --tokenizer-mode deepseek_v4 \
    --load-format fastsafetensors \
    --safetensors-load-strategy lazy \
    --distributed-executor-backend mp \
    --master-addr "$MASTER_ADDR" \
    --master-port "$MASTER_PORT" \
    --nnodes "$SLURM_NNODES" \
    --node-rank "$SLURM_NODEID" \
    --tensor-parallel-size 16 \
    --pipeline-parallel-size 2 \
    --enable-expert-parallel \
    --kv-cache-dtype fp8 \
    --block-size 256 \
    --max-model-len 10240 \
    --max-num-seqs 64 \
    --max-num-batched-tokens 16384 \
    --gpu-memory-utilization 0.9 \
    --linear-backend auto \
    --moe-backend auto \
    --no-enable-prefix-caching \
    --distributed-timeout-seconds 7200 \
    --cpu-distributed-timeout-seconds 7200 \
    --compilation-config "$COMPILATION_CONFIG" \
    "${headless[@]}"
'
```

After the A100 head process becomes ready, run the evaluation from that node:

## Test Result

Before the helper is used, an SM75, SM80, or SM86 consumer that directly casts `tl.float8e4nv` fails during Triton compilation:

```text
ValueError: type fp8e4nv not supported in this architecture
```

After the helper is used, each RTX 4090 target run reports:

```text
SM75 target: 10 passed
SM80 target: 10 passed
SM86 target: 10 passed
native SM89: 10 passed
```

The tests exhaust every finite FP8 byte for decode, cover encode edge cases and FP32 double-rounding, and cross-check every FP16/BF16 bit pattern against native SM89 conversion.

Without portable conversion, the A100 server fails before generation with the `fp8e4nv` compilation error above. Together with the co-pending DeepSeek V4 sparse-MLA and output-projection PRs, the helper lets the compiled A100 server capture CUDA graphs and the full evaluation reports:

```text
questions: 1319
completed: 1319
flexible_accuracy: 0.965125
strict_accuracy: 0.953753
invalid: 0
output_tokens: 121802
```

All applicable pre-commit hooks passed.
