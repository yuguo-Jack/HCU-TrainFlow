# [Perf][DSv4.1] Improve the TP4 concurrency-1 specialized decode

## Overview

Lowers the step time of the DeepSeek-V4.1-Flash `latency_specialized` decode at TP4, concurrency 1, with DSpark on GB300. All changes are unconditional: no new env vars or config options.

Stacked on #61869. The branch is main (7663a8c524, which now has #63921), a merge of #61869's head (12a509d84c) into it (f074aad7b6; its message lists the conflict resolutions and the fixes needed against current main), and this PR's commit, 4a8a438518. Review the last commit; the merge goes away once #61869 lands. The two Model Runner V2 changes that apply beyond this executor (the FULL graph's sliced output copy and the skipped draft-token gather) moved to #64701. This PR no longer changes the shared runner or speculators: #61869 removed the post-forward CUDA graphs on review, and the changes here that extended them went with them.

## Claims

- Numbers below are from the previous stack (#63921 + #61869 with its post-forward graphs, which this PR also extended), and are being re-measured on this base: AgentX P90 interactivity 907.5 → 986.5 tok/s (+8.7%), median 936.0 → 1017.0 (+8.7%), ITL p50 1.068 → 0.983 ms, on the same GB300 tray; a second run of this PR in the same job gave 986.1 / 1017.4.
- The vendored DeepSelect cluster top-k, which an earlier revision of this PR carried, was worth about 1.5% P90 / 1.2% median of that (1001.3 / 1029.4 in the same job).
- The new top-k kernel (`topk_bf16_small`) is not bitwise equal to the code it replaces (the same set up to ties at the k-th value, in another order); GSM8K is unchanged within noise. The other changes that touch a kernel's arithmetic are bitwise equal to the code they replace; the rest moves work between streams or changes launch timing.

## Details

**Where the time went.** An nsys trace of the base at 3.73 ms per step showed most kernels close to their floor. The time was elsewhere:

- Lamport all-reduce + mHC time exposed between sublayers: 365 µs/step.
- Idle gaps in the PDL chain, where a kernel waited for its predecessor's tail.
- The indexer top-k chain: 98.9 µs/step.
- The MLA launch chain on plain layers: KV insert, query RoPE and quantization between `wq_b` and the attention.
- Host and graph gaps outside the target layers.

Per-layer medians after the change:

| Per-layer median | Base (µs) | This PR (µs) |
|---|---|---|
| Plain-layer attention half | 31.4 | 27.4 |
| Indexer-layer attention half | 63.0 | 55.5 |

Layers 2, 8 and 14 keep the stock indexer's top-k (62–76 µs each), so the indexer-layer gain is on layers 20–36. The MoE half varies with the number of experts the trace window hits, so whole-step trace times are not compared.

**Third-party code.** `topk_bf16_small` is adapted from SGLang (Apache-2.0), whose kernel adapts DeepSelect's init-window select (MIT); the file carries both notices. It is JIT-built with `torch.utils.cpp_extension` at warm-up (on the first start, then cached), like `vllm/models/deepseek_v41/amd/ops/topk.py`, so the executor needs nvcc and a host compiler at runtime (documented in its `AGENTS.md`). An earlier revision of this PR also vendored DeepSelect's bf16 cluster kernel in SGLang's rewrite for the dense indexers' token top-k; it is out, to keep the vendored tree out of this PR, and those layers stay on `decode_topk` or the stock indexer as in the base. The ahead-of-time DeepSelect build vLLM pins does not fit as is: its cluster kernel lacks the rewrite, its gather signals completion barriers in the wrong CTA (deepseek-ai/DeepSelect#16), and a row holding a NaN gets a marker the sparse-index table build does not mask. Landing the rewrite in `vllm-project/DeepSelect` and bumping the pin would bring back the ~1.2–1.5% above.

**Limitations**

- The fused query RoPE and the norm's KV write match nvcc's FMA contraction of the CUDA kernels they replace; `test_sparse_mla_cute.py` catches a compiler change that breaks that.
- #61869 conflicts with current main; the merge in this branch resolves that, and is replaced when #61869 lands or rebases.

**Not a duplicate.** A related open PR changes other parts: #64146 (TP8 specialized decode on GB300). Searches for `latency_specialized`, "specialized decode", "DSv4.1 TP4" and "DSv4.1 top-k DeepSelect" found no open PR with these changes.

We've been looking at the same draft-token gather overhead and found that this change in `model_runner.py` is generic: it lives in the shared MRV2 runner and benefits every spec-decode model, not just specialized decode. We'd like to avoid duplicate PRs, so would you mind splitting this part into its own small PR? It'd be easier to review and could land independently of this one.

When you rebase it, note that #64458 changed `broadcast_drafts` to take a pre-gathered tensor. PP still needs its own full-width, batch-ordered copy, because the broadcast runs on a side stream and the next step can overwrite the source before it's sent. So the slice shouldn't go to PP:

```python
broadcast = self.pp_handler is not None and num_spec_tokens > 0
if broadcast or input_batch.has_structured_output_reqs:
    draft_tokens = self.req_states.draft_tokens[input_batch.idx_mapping]
else:
    draft_tokens = self.req_states.draft_tokens[: input_batch.num_reqs]  # width only
self.draft_tokens_handler.set_draft_tokens(input_batch, draft_tokens[:, :num_spec_tokens])
if broadcast:
    self.pp_handler.broadcast_drafts(draft_tokens)
```

A couple of tests would help: check that the placeholder width matches K (0, partial, max), and that PP still sends the full width when K < max.
