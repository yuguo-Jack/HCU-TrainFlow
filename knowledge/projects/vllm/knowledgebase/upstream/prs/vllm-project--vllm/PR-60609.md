# [XPU][MoE] Let XpuFusedMoe own the MoE weight/scale layout

[Upstream PR](https://github.com/vllm-project/vllm/pull/60609) · state: open · merged: False

## Original PR description

## Overview

This change aligns the interface between upstream vLLM and [vllm-xpu-kernels PR #583](https://github.com/vllm-project/vllm-xpu-kernels/pull/583) (XE3P grouped GEMM)..

The interface changes are also aligned with the already-merged Innersource `pull/249`.

## Changes

Removed the pre-transpose and relayout logic for XPU MoE weights and scales from vLLM:

- Deleted `prepare_fp8_moe_layer_for_xpu()`, which transposed the last two dimensions of `w13`/`w2` and their 3-D scales before passing them to the XPU kernel.
- Removed the `Fp8MoeBackend.XPU` branch in `convert_to_fp8_moe_kernel_format()` that called `prepare_fp8_moe_layer_for_xpu()`.
- Removed the `UnquantizedMoeBackend.XPU` branch that performed an in-place transpose of raw BF16/FP16 weights before kernel setup.

Two places relaid out MoE weights for XPU at load time, and between them they only got part of it right:

prepare_fp8_moe_layer_for_xpu() transposed the fp8 weights and any 3-D scale. That is correct for mxfp8, whose [E, N, K/32] scales the XE3 kernel reads dense along N, but wrong for block fp8, whose scales are already in the [E, ceil(N/128), ceil(K/128)] layout the kernel wants -- transposing them dequantizes every 128x128 tile with another tile's scale.
UnquantizedFusedMoEMethod transposed the bf16/fp16 weights.
Nothing at all was done for mxfp4, so its scales never reached the XE3 kernel in the N-dense layout it needs.

vllm-xpu-kernels now relayouts weights and scales inside XpuFusedMoe.init, per device family, so hand them over exactly as they were loaded and drop both sites. The WNA16 int4 repack stays: it decodes the GPTQ int32 nibble format into the [E, N, K // 2] weights and [E, N, K // group_size] scales that are the expected input.

### End-to-end accuracy on Xe2 (BMG): Qwen3-30B-A3B BF16, TP=4

`Qwen/Qwen3-30B-A3B` (BF16, unquantized MoE), 4x Intel Arc Pro B60 (Xe2/BMG), TP=4, `max_model_len=4096`, `gpu_memory_utilization=0.85`, seed 1234. The log confirms the changed path is exercised: `Using XPU Unquantized MoE backend`.

- **Baseline**: vLLM 0.32.0+xpu without this PR + `vllm-xpu-kernels==0.1.15.4`
- **This PR**: this PR's vLLM changes + `vllm-xpu-kernels` built from [#583](https://github.com/vllm-project/vllm-xpu-kernels/pull/583) (head `35c61cd`, built with oneAPI DPC++ 2026.1.1; one local line added to `xe_moe_gemm_greedy.hpp` so it compiles: `#include <sycl/ext/intel/experimental/grf_size_properties.hpp>`)

| Baseline (repeat, noise floor) | 0.8939 ± 0.0085 | 0.8453 ± 0.0100 |
| **This PR** | **0.8916 ± 0.0086** | **0.8476 ± 0.0099** |

| Pair | filter | only first correct | only second correct | p |

Scores are within one standard error of both baseline runs and the discordant pairs are symmetric, so no accuracy regression is observed. Note that generation is not bit-reproducible between runs of the same code (only 47.1% of responses are textually identical between the two baseline runs, vs 48.7% between baseline and this PR), so the repeated baseline is used as the noise floor.

**Fixed-prompt greedy decoding** (8 prompts, 64 new tokens, logprobs):

|---|---|---|
| baseline vs baseline (repeat) | 4/8 | 0.22 / 1.12 |

Differences from this PR are within the run-to-run noise of the baseline.

**Memory**: weights take 14.25 GiB per rank in both runs; actual usage after profiling is 15.11 GiB (baseline) vs 14.97 GiB (this PR), so the in-kernel relayout does not keep an extra copy of the weights on this path.

**Kernel unit tests** re-run on Xe2 (2x B60) at `35c61cd`: `test_fused_moe_xe2.py`, `test_grouped_gemm_xe2.py`, `test_moe_quant_scale_layout.py`, `test_remap_hidden_states.py`, `test_reorder_mxfp_scales.py`: 699 passed, 16 skipped (Xe3P-only), 0 failed.

Scope: only the BF16 (unquantized) MoE path was validated end to end here. FP8 (block / per-tensor), MXFP8, MXFP4 and WNA16 paths are not covered by this run.
