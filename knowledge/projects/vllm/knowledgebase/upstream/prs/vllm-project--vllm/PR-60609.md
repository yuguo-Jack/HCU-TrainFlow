# [XPU][MoE] Let XpuFusedMoe own the MoE weight/scale layout

[Upstream PR](https://github.com/vllm-project/vllm/pull/60609) · state: open · merged: False

## Original PR description

## Overview

This change aligns the interface between upstream vLLM and [vllm-xpu-kernels PR #583](https://github.com/vllm-project/vllm-xpu-kernels/pull/583) (XE3P grouped GEMM)..

The interface changes are also aligned with the already-merged Innersource `pull/249`.

## Changes

Removed the pre-transpose and relayout logic for XPU MoE weights and scales from vLLM:

- Deleted `prepare_fp8_moe_layer_for_xpu()`, which transposed the last two dimensions of `w13`/`w2` and their 3-D scales before passing them to the XPU kernel.
- Removed the `Fp8MoeBackend.XPU` branch in `convert_to_fp8_moe_kernel_format()` that called `prepare_fp8_moe_layer_for_xpu()`.
- Removed the `UnquantizedMoeBackend.XPU` branch that performed an in-place transpose of raw BF16/FP16 weights before kernel setup.

Two places relaid out MoE weights for XPU at load time, and between them they only got part of it right:

prepare_fp8_moe_layer_for_xpu() transposed the fp8 weights and any 3-D scale. That is correct for mxfp8, whose [E, N, K/32] scales the XE3 kernel reads dense along N, but wrong for block fp8, whose scales are already in the [E, ceil(N/128), ceil(K/128)] layout the kernel wants -- transposing them dequantizes every 128x128 tile with another tile's scale.
UnquantizedFusedMoEMethod transposed the bf16/fp16 weights.
Nothing at all was done for mxfp4, so its scales never reached the XE3 kernel in the N-dense layout it needs.

vllm-xpu-kernels now relayouts weights and scales inside XpuFusedMoe.init, per device family, so hand them over exactly as they were loaded and drop both sites. The WNA16 int4 repack stays: it decodes the GPTQ int32 nibble format into the [E, N, K // 2] weights and [E, N, K // group_size] scales that are the expected input.

## Validation

### Kernel unit tests (vllm-xpu-kernels PR583, Xe2/BMG, commit 733f769)
Run on 4x Intel Arc Pro B60 (Xe2):
- tests/fused_moe/test_fused_moe_xe2.py: 290 passed
- tests/fused_moe/test_grouped_gemm_xe2.py + test_moe_quant_scale_layout.py + test_remap_hidden_states.py: 287 passed, 16 skipped
- tests/fused_moe/test_reorder_mxfp_scales.py: 15 passed
- Total: 592 passed, 16 skipped (Xe3P-only cases, no Xe3P hardware available), 0 failed

End-to-end accuracy xe2 (ported xpu_moe.py / oracle/fp8.py / unquantized_fused_moe_method.py)
`nm-testing/OLMoE-1B-7B-0924-Instruct-FP8` (FP8 static-per-tensor-symmetric, matches `kFp8StaticTensorSym`), TP=1:
- Full GSM8K (5-shot, 1319 examples, lm_eval 0.4.12):
  - flexible-extract: exact_match = 0.3548 ± 0.0132
  - strict-match: exact_match = 0.3419 ± 0.0131

Additionally verified weight loading, FP8 oracle conversion, and `XpuFusedMoe` kernel calls across all 48 layers on `Qwen/Qwen3-30B-A3B` (bf16) and `nm-testing/Qwen3-30B-A3B-Fp8` with no type/assertion errors (eventual OOM is a single-GPU 24GB capacity limitation, unrelated to this PR's code).

### End-to-end accuracy xe3: GSM8K (lm_eval 0.4.13)
- Model: `nm-testing/OLMoE-1B-7B-0924-Instruct-FP8` (FP8 static per-tensor symmetric), TP=1, 5-shot, full test set (1319 examples).
- Backend selected: `XPU` FP8 MoE backend (confirms this PR's code path is exercised).

| Metric | Xe2/BMG (baseline, this PR's description) | Xe3P|
|---|---|---|
| flexible-extract `exact_match` | 0.3548 ± 0.0132 | **0.3669 ± 0.0133** |
| strict-match `exact_match` | 0.3419 ± 0.0131 | **0.3487 ± 0.0131** |

Both metrics on Xe3P are within ~1 standard error of the Xe2/BMG baseline — **no accuracy regression observed** on Xe3P for this model/quantization configuration.
