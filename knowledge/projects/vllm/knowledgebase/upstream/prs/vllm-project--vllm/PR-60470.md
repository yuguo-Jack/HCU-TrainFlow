# [Kernel] Let FlashInfer select the Kimi-K3 fused KDA decode kernel (backend="auto")

[Upstream PR](https://github.com/vllm-project/vllm/pull/60470) · state: open · merged: False

## Original PR description

## Overview

Let FlashInfer select the Kimi-K3 fused KDA T=1 decode kernel: with `kda_decode_backend="flashinfer"` and a FlashInfer whose `fused_kda_decode` accepts them, pass `backend="auto"` and `state_indices_mode="unique_or_null"`; on the pinned `flashinfer-python==0.7.0.post1` FlashInfer receives the same arguments as before. No new environment variable, module or Cake-specific logic in vLLM. Related tracker: #59725; FlashInfer side: flashinfer-ai/flashinfer#4967.

## Claims

* With `kda_decode_backend="flashinfer"` and a FlashInfer whose `fused_kda_decode` accepts `backend` / `state_indices_mode` (FlashInfer >= 0.7.1rc1, added by flashinfer-ai/flashinfer#4967), the Kimi-K3 KDA T=1 decode call passes `backend="auto"` and `state_indices_mode="unique_or_null"`, and FlashInfer selects the kernel (on SM100 / SM103 its generated Cake variants where a route matches, the CuTe DSL kernel otherwise). vLLM carries no Cake-specific logic, switch or module.
* On FlashInfer builds without the two parameters (the pinned `0.7.0.post1`) FlashInfer receives the same arguments as before (the call site now goes through a helper that forwards an empty kwargs dict); the other KDA decode backends are untouched.
* Validation: 12 CPU dispatch tests, the existing GPU correctness test (13 passed / 7 test-own skips) and a kernel-selection probe on one B200; end to end on Kimi-K3 NVFP4 TP8 (two GB300 nodes): GSM8K 0.945 (native) vs 0.943 (`auto`), serving throughput and medians within ±1.5 % of native, one run per arm.

## Details

This PR started as an opt-in `VLLM_CAKE_ROUTES` change (its first commit) and was reworked after maintainer feedback that vLLM should carry no awareness of Cake-generated kernels (Cake: the generated kernel family inside FlashInfer that `backend="auto"` can select for these Kimi-K3 shapes). On the current head the `VLLM_CAKE_ROUTES` switch, the host-side admission predicates and the Kimi-K3 MLA decode route are gone; the net diff against `main` is the four files below. Kernel selection is FlashInfer's job.

### What changes

* `vllm/models/kimi_k3/nvidia/kda.py`
  * `_flashinfer_kda_decode_kwargs(backend)` decides once, at layer init, which extra kwargs the FlashInfer call gets: `{"backend": "auto", "state_indices_mode": "unique_or_null"}` when `backend == "flashinfer"` and the probe below is true, `{}` otherwise. The result is stored as `self.flashinfer_kda_decode_kwargs`; when non-empty, `_announce_flashinfer_kda_decode` logs it once (INFO) after `_format_kda_decode_kwargs` has rendered it to a `k=v, ...` string.
  * The FlashInfer decode call moves into `KimiK3DeltaAttention._flashinfer_fused_kda_decode(...)`, which forwards `**self.flashinfer_kda_decode_kwargs`. The branch condition in `_forward` (the FlashInfer path is taken exactly when it was before, only for `kda_decode_backend == "flashinfer"`), the `auto` / `native` / `triton` / `flashinfer` resolution and the `@eager_break_during_capture` decorator are unchanged; the call itself now goes through the helper and gains the two kwargs.
  * Module constant `_FLASHINFER_KDA_STATE_INDICES_MODE = "unique_or_null"` with the rationale below.
* `vllm/utils/flashinfer.py`
  * `flashinfer_fused_kda_decode_selects_backend()` (cached): true when FlashInfer's `fused_kda_decode` is available and its signature accepts `backend` and `state_indices_mode`. `_fused_kda_decode_accepts_backend(fn)` is the signature check.
* Tests: `tests/models/kimi_k3/test_kda_flashinfer_decode_dispatch.py` (new, CPU) and a two-line change in `tests/models/kimi_k3/test_kda.py`. The earlier form's `tests/v1/attention/test_cake_routes_kimi_k3.py` no longer exists on this branch (not part of the net diff).

### FlashInfer semantics relied on

In FlashInfer `main` (`flashinfer/kda_decode.py`), `fused_kda_decode(..., backend="auto", state_indices_mode=...)`:

* `backend="auto"` selects FlashInfer's Cake-generated program only when `state_indices_mode` is supplied and one of its routes matches the call (SM100a / SM103a, a matching layout); otherwise it runs the CuTe DSL kernel, i.e. the same kernel the call ran before this PR.
* `state_indices_mode` is consumed only by that selector; it is a host-side statement about the `state_indices` tensor, never verified on the device.

**Version note.** The two parameters exist in FlashInfer >= 0.7.1rc1 (every 0.7.1 pre-release; added by flashinfer-ai/flashinfer#4967). The pinned `0.7.0.post1` does not have them, the probe returns false and FlashInfer receives the same arguments as before; when the pin moves to a release with them, every `kda_decode_backend="flashinfer"` deployment switches to the `auto` form without further vLLM changes. That backend stays opt-in (vLLM's own decode is the default); inside it there is no vLLM knob to keep the CuTe DSL kernel, and FlashInfer has no environment switch for this call either, so the way back is another `kda_decode_backend`.

**Why `unique_or_null`.** vLLM's KDA metadata fills CUDA-graph padding rows with `NULL_BLOCK_ID` (0), the reserved null block owned by no request, and every live T=1 decode row owns its own block, so the state indices are non-positive or unique. FlashInfer treats non-positive rows as the null path (zero output, no state update). `positive_unique` would be a false assertion under padding. Because FlashInfer does not verify the mode on the device, it has to hold for every caller path that reaches the FlashInfer decode; the single call site in `_forward` is that path and it only runs for pure T=1 decode batches (`num_prefills == 0`, no speculative tokens).
