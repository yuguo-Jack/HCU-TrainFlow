# [Perf][Attention] Reuse KV loads across DiffKV prefill query positions

[Upstream PR](https://github.com/vllm-project/vllm/pull/58177) · state: open · merged: False

## Original PR description

## Purpose

On GPUs without FA3/FA4 (e.g. DGX Spark / GB10), MiMo-V2.6-Flash runs `TRITON_ATTN_DIFFKV`. Its global layers have 16 query heads per KV head, so a 16-row block covers a single query position and every position reloads its KV prefix. For prefills with `max_seqlen_q >= 64`, this uses `BLOCK_M=32` so two positions share each KV tile load. Outputs were bitwise identical to `BLOCK_M=16` in the tested comparisons.

Like `tuned_large_head` in `triton_unified_attention.py`, this is a `BLOCK_M` override gated on shape and device family (CUDA SM12x; `is_cuda()` because ROCm gfx12 also reports 12.x). The threshold is 64 following independent GB10 and RTX PRO 6000 measurements. [GB10 results](https://github.com/vllm-project/vllm/pull/58177#issuecomment-5842644689) show 1.80–1.87x at 64 tokens. [RTX PRO 6000 results](https://github.com/vllm-project/vllm/pull/58177#issuecomment-5842511004) show 1.54–1.70x at 192 tokens, while 64–128 is mixed (0.92–1.10x), so this is a trade-off rather than a universal improvement at 64. Both reviewers confirmed bitwise agreement on their tested batches.

The SM12x gate is retained as the measured performance scope, not a correctness requirement. B300/GB300 are SM10.3 and are unaffected, including when Triton DiffKV is forced. Generalizing the tile choice needs separate measurements of the Triton path on those devices; SM count alone does not determine occupancy or the crossover.

No open PR changes DiffKV prefill tiling. #53804 (XPU tile overrides) touches the same launcher with a different mechanism.

Bitwise: `torch.equal` between BM16 and BM32 on 8 batches ([1, 257]/[1344, 294], [512]/[8192], [1, 3, 300, 7]/[2048, 900, 16384, 64], [256]/[4096], [257]/[4096], [300, 301]/[8192, 7000], [64]/[8192], [96, 1, 130]/[4096, 50000, 2000]): all exact.

So on 188 SMs the win starts between 128 and 192, not at 64: 64-128 is flat (within about +-8%, sign flips between warm and cold), and 192-255 gets 1.54-1.77x that the current 256 gate leaves out. Below 64 BM32 is 6-13% slower, same as your GB10 data.

The crossover seems to track the SM count rather than being a fixed token count: the 2D grid is `(num_q_tokens / BLOCK_Q) x num_kv_heads`, i.e. 2*qlen CTAs at BM16 vs qlen at BM32 here, and the steps line up with BM16 spilling into an extra wave at roughly 2 resident CTAs per SM (qlen ~ 188 on this card, ~48 on GB10, which matches your crossover at 64 there). The dip at 384 (BM32 itself goes just over one wave) fits the same picture.

For the gate, that makes **64 safe on both parts**: it costs nothing measurable on a 188-SM card (64-128 is neutral here) and picks up 64-192 on GB10 and 192-255 here. A gate derived from the SM count would be tighter, but since the grid depends on the batch's total query tokens while the gate sees `max_seqlen_q`, I don't think the extra precision would survive mixed batches; a constant 64 seems like the better trade.

BM128 beats BM32 by 1.13-1.48x from qlen 128 up, and loses to it at 64. I'd predicted the opposite from the wave argument in my last comment — `BLOCK_Q = BLOCK_M // 16`, so BM128 gives a quarter of BM32's CTAs and should empty a 48-SM machine four times sooner. It doesn't; the KV-load reuse wins well before occupancy becomes the binding constraint. BM64 being consistently worse than BM32 says the tile shape matters more than the CTA count here too.

So on this part the shape looks like a two-step ladder rather than one tile: BM32 over 64-127, BM128 at >= 128.

**The catch.** BM128 is not bitwise identical to BM16, and BM32 is:

```
torch.equal against the BM16 leg, 6 batches x block_size 16/32:
  BM32    12 of 12 identical,  max|d| 0
  BM128    0 of 12 identical,  max|d| up to 9.766e-04
```

That matters more than it looks, because the gate reads `max_seqlen_q` — the batch's longest query — so once the tile choice changes the numerics, a given request's output depends on what else got batched with it, in the default non-batch-invariant path. BM32 was safe precisely because the output didn't move; I checked that two comments ago and it's why I didn't flag the gate's batch dependence as a problem then.

@lucamotz so if the ladder is worth having, BM128 needs its own answer on that rather than inheriting BM32's. The honest options look like: keep BM32 only and take the smaller win, or take BM128 and drop the bitwise claim from the description and say output may differ from the untuned path.

I didn't test 8 warps separately — my sweep varied only `BLOCK_M`, so the 1.13-1.48x above is tile-only and your deployment's number bundles more than that.
