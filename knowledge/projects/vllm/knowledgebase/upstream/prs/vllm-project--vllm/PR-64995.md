# [Docs] Add drain shutdown section to Kubernetes deployment guide

[Upstream PR](https://github.com/vllm-project/vllm/pull/64995) · state: open · merged: False

## Original PR description



## Overview

Revives #43208 by @markmc, which @robertgshaw2-redhat approved before it was closed for inactivity: a "Drain Shutdown" section in the Kubernetes deployment guide covering `--shutdown-timeout`, a `preStop` hook and `terminationGracePeriodSeconds`. It applies the two review suggestions on that PR and corrects what I found to differ from the server's behavior while testing drains with `vllm/vllm-openai:nightly` on Kubernetes-style `SIGTERM` (sent to PID 1 with `docker kill`).

## Changes from #43208

| #43208 | This PR | Why |
|---|---|---|
| Example runs `/bin/sh -c "vllm serve ..."` | Passes the model and flags as `args` to the image's `vllm serve` entrypoint, and explains why | The shell becomes PID 1 and does not forward `SIGTERM`, so vLLM never starts draining and the pod is killed at the grace period (the `exec` suggestion in review) |
| "A second SIGTERM will skip the drain timeout" | Removed | `serve_http` ignores further signals once shutdown has started (`if shutdown_event.is_set(): return`); skipping the drain on a second signal is the gRPC server's behavior (#62967) |
| New requests during the drain "return 503" | "The server stops taking new requests", without a status code | On a single API server they currently fail with 500 (`cannot schedule new futures after shutdown`); with #61562 they are refused at the socket |
| `/health` and `/metrics` "remain accessible during drain" | Replaced by a note not to rely on the readiness probe during the drain | `/health` reports engine liveness, not drain state; documenting it as available suggests the readiness probe takes the pod out of rotation, which is what the `preStop` sleep is for |
| `terminationGracePeriodSeconds >= preStop + --shutdown-timeout` (60 = 15 + 45 in the example) | Adds a teardown margin; example uses 15 + 40 + 15 = 70 | The engine and the server need time to exit after the drain (the margin suggestion in review); #64991 gives EngineCore 5 s past the timeout |
| Timeout sized from token throughput | Keeps that, and points to the p99 of `vllm:e2e_request_latency_seconds` | Lets operators size it from their own traffic |
| | Notes that aborted requests end with `finish_reason="abort"` when the abort reaches the client, and that clients should treat it as incomplete | Observed with `--shutdown-timeout 0`; the drain-deadline case is left until #64991 lands |

## Validation

- Behaviors above checked on `vllm/vllm-openai:nightly` (0.33.0rc1.dev421+g2b009fc6d), RTX 5060 Ti, `Qwen/Qwen3-0.6B`, `--shutdown-timeout 0` and `20`, `SIGTERM` to PID 1 via `docker kill`; the signal-handling claim against `serve_http` in `vllm/entrypoints/launchers/launcher.py`.
- `pre-commit` (markdownlint) passes on `docs/deployment/k8s.md`.
