# [Rust Frontend] Support beam search (use_beam_search, length_penalty)

## Overview

Implements beam search in the Rust frontend for `/v1/completions` and `/v1/chat/completions` (`use_beam_search`, beam width `n`, `length_penalty`), mirroring Python's online beam search. Part of the Rust frontend parity roadmap #44280 ("Beam search via the existing `use_beam_search` request parameter, including `length_penalty`").

- Scoring follows Python after #62928 (normalize by generated length).
- Related: #58914 (general OpenAI `n` choices). This PR does not depend on it; beam output assembles its own choices, so it can be rebased onto #58914's merging later.
- Prior work: #47705 by @yangyang-cs95 implements the same Python algorithm. It predates #62928 (score by generated length) and #62072 (generation-config EOS), and builds requests outside the text pipeline. This PR is written on current `main`; I'm happy to close it if @yangyang-cs95 prefers to continue there.

## Claims

- `use_beam_search=true` with `n` ≥ 1 and `length_penalty` now works on both endpoints, replacing the previous `use_beam_search is not supported.` / `length_penalty is not supported.` 400s.
- Non-streaming output matches the Python frontend (beam texts, order, `finish_reason`, `stop_reason`, usage) on Qwen2.5-0.5B-Instruct.
- Requests that Python accepts but silently ignores under beam search are rejected with a 400 that names the parameter (see Details).
- Dropping the client connection aborts in-flight step requests.

## Details

**Design.** Same algorithm as `vllm/entrypoints/generate/beam_search/online.py`:
- Each step sends one engine request per live beam, with `max_tokens=1` and `logprobs=2·n`.
- EOS candidates move to the completed set with `stop_reason=<eos id>`.
- Live candidates are sorted by `cum_logprob / max(len,1)**length_penalty` and the top `n` kept. `len` counts generated tokens, including EOS (#62928).
- At the end, completed and live beams are sorted by score and the top `n` returned.

Ownership by crate:
- `vllm-text`: `TextLlm::beam_search` runs the steps and builds one synthetic terminal output per beam. That output goes through the existing `decoded_text_event_stream`, so detokenization, stop handling and logprobs reuse the normal path.
- `vllm-chat`: `ChatLlm::beam_search` pairs each beam with its own chat output processor, so reasoning and tool parsing run per choice. Commit 1 is a mechanical refactor that lets `prepare` create several processors.
- `vllm-server`: validation, and assembling the multi-choice response with merged usage.

**Deviations from Python** (per `rust/AGENTS.md`, unimplemented behavior is rejected instead of silently ignored):
- **Ignored sampling params are rejected.** Under beam search, Python silently drops `top_p`, `top_k`, `min_p`, `seed`, `min_tokens`, the penalties, `stop`, `stop_token_ids`, `logit_bias`, `bad_words`, `structured_outputs`, prompt logprobs, `kv_transfer_params`, `ec_transfer_params` and similar fields. Rust returns 400 for any non-default value. This is the main behavior change to review.
- **Chat streaming is rejected** (`param: stream`). Python finishes the search and then streams every beam at once as SSE chunks; no tokens stream during the search. The Rust chat SSE path currently writes a single choice (`index: 0`), so this needs multi-choice streaming. A possible follow-up builds on #58914's `n > 1` streaming: `ChatLlm::beam_search` already returns one finished `ChatEventStream` per beam, which can feed that writer, and then the 400 can be removed. Completions streaming is rejected in both frontends.
- **`allowed_token_ids` is rejected (TODO).** Python scores allowlisted beams with exact-ID logprobs, which needs Model Runner V2 support.
- **Tool calling that implies an output grammar is rejected:** `tool_choice` `required` or a named function, strict tools or `--tool-strict-level`, or a tool parser that always constrains output. Python's online beam search ignores the grammar. Its offline `LLM.beam_search` does enforce it per beam, by running a structured output backend in the frontend process and replaying each beam's tokens. The engine only advances a grammar over tokens it generates itself, so Rust would need its own grammar matcher or an engine protocol change. `auto` and `none` work unless strict tools or the model's tool parser impose a grammar.
- **Completions with `max_tokens=0` is rejected (TODO).** Python returns the bare prompt as a single choice.
- **Logprobs.** Each position reports the chosen token, then the top `k` candidates, deduplicated, as Rust's non-beam responses do. Python's beam search reports the first entries of the step's `2·n` candidate dict instead. So Python can return `k+1` alternatives, can leave out the chosen token, and lists the candidates in rank order rather than chosen-first. The token and logprob of each position are identical.
- **Ties** are broken deterministically: candidates keep engine order and the sort is stable.
- **Child request IDs** follow Python (`<parent>-<uuid>-beam-<i>`), so `/abort_requests` with the parent ID does not reach in-flight steps. Client disconnect does abort them.
- **`metrics`** on the response is `null`, because there's no single engine request to report.

**Shared limit:** `n > 10` needs `--max-logprobs` ≥ `2·n`, because each step asks for `2·n` logprobs. Both frontends reject it with the default of 20.

**Not validated locally:**
- **GPU:** I only had CPU. The new end-to-end tests cover it in CI.
- **Chat with a reasoning or tool parser on a real model:** covered by route tests.
- **Multimodal prompts:** features are forwarded to every step request, but this wasn't run on a multimodal model.

`rust_frontend.yaml` also updates a comment that said the Rust frontend has no beam search. `test_batch_completions` stays excluded, because Rust still rejects batched prompts.

**Docs:** the rendered docs have no Rust frontend parameter page, and recent `[Rust Frontend]` parity PRs haven't touched `docs/`. I'm happy to add a short note under "Extra Parameters" in `docs/serving/online_serving/openai_compatible_server.md` if reviewers want one.

**Size:** about 800 implementation lines and 870 test lines across 20 files. Most of the implementation is in `rust/src/text/src/beam_search.rs`.

**Updates after review:**
- An EOS-only beam with `logprobs` no longer returns 500 on chat; it returns empty logprobs, like Python.
- Grammar rejections from strict tools or `--tool-strict-level` now name those causes instead of `tool_choice`.
- `kv_transfer_params`/`ec_transfer_params` are rejected under their own names instead of `vllm_xargs`.
