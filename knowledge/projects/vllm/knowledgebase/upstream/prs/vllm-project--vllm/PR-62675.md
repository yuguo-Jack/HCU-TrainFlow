# [Bugfix][ROCm] Pad Qwen4Exp PLE n-gram inputs for piecewise CUDA graph replays

[Upstream PR](https://github.com/vllm-project/vllm/pull/62675) · state: open · merged: False

## Original PR description

## Overview

Fixes #61486

The Qwen4Exp AMD backend computes PLE n-gram ids inside PIECEWISE CUDA graph pieces, where the request search keeps the count the piece was captured with, but `Qwen4ExpModelState` only refreshed the live batch's rows of `query_start_loc` and
`ngram_context`. Replays read a stale tail, hashed the wrong n-gram and made the answer depend on what the server had served before. This pads both buffers.

## Claims

- PLE n-gram inputs no longer depend on server history: 0/300 short prompts change their answer after a 16-way burst, versus 77/300 before.
- Bit-identical replays: the max first-token logprob delta after the burst is 0.0000, versus 0.72 before.
- Eager and FULL-graph steps are unaffected: there `num_reqs_padded == num_reqs`, so the refreshed range already covers what the graph reads.


## Validation

vllm serving command:

```
vllm serve Qwen/Qwen3.8-Flash-Next-FP8 --max-num-seqs 256 --gpu-memory-utilization 0.90 \
  --max-model-len 32768 --enable-prefix-caching --reasoning-parser qwen3 \
  --speculative-config '{"method": "mtp", "num_speculative_tokens": 3}'
```

Using the reproducible script provided, 300 prompts served sequentially and greedily, the same prompts again as a control, a 16-way concurrent burst, then the same prompts again. Only the server state accumulated in between differs.

```python
"""300-prompt history test for issue 61486.

Run against the server above. Each prompt is generated three times, and the first
16 are reused as the burst; only the server state accumulated in between differs.
Expected: the control reports 0 changed prompts, and the effect reports 0 with
the fix (about 25-30% without it).
"""
import json
import urllib.request
from concurrent.futures import ThreadPoolExecutor

from datasets import load_dataset

BASE = "http://127.0.0.1:8000"
MODEL = "Qwen/Qwen3.8-Flash-Next-FP8"


def post(path, payload):
    req = urllib.request.Request(
        BASE + path,
        data=json.dumps(payload).encode(),
        headers={"Content-Type": "application/json"},
    )
    return json.loads(urllib.request.urlopen(req, timeout=600).read())


def gen(ids, max_tokens=8):
    out = post(
        "/v1/completions",
        {"model": MODEL, "prompt": ids, "max_tokens": max_tokens,
         "temperature": 0.0, "logprobs": 1},
    )
    lp = out["choices"][0]["logprobs"]
    return {"tokens": lp["tokens"], "logprob0": lp["token_logprobs"][0]}


def run_set(prompts):
    return [gen(ids) for ids in prompts]  # sequential, fixed order


questions = load_dataset("openai/gsm8k", "main", split="test")["question"][:300]
prompts = [
    post("/tokenize", {"model": MODEL, "prompt": q})["tokens"] for q in questions
]

first = run_set(prompts)
again = run_set(prompts)  # control: nothing changed in between
with ThreadPoolExecutor(16) as ex:  # concurrent traffic, then repeat
    list(ex.map(lambda ids: gen(ids, 24), prompts[:16]))
after = run_set(prompts)

for name, a, b in (("control", first, again), ("effect ", first, after)):
    changed = sum(x["tokens"] != y["tokens"] for x, y in zip(a, b))
    delta = max(abs(x["logprob0"] - y["logprob0"]) for x, y in zip(a, b))
    print(f"{name}: {changed}/{len(a)} prompts changed, max |dlogprob0| = {delta:.4f}")
```

## Details

PIECEWISE descriptors carry `num_reqs=None`, so the runner does not pad the request axis, while the captured piece uses `num_reqs = min(piece_tokens, max_num_seqs)`. `qwen4_exp_amd_ple_ngram_ids` is not a splitting op and sizes its search from
`query_start_loc.numel() - 1`, so it keeps the capture-time count and reads rows this step never wrote. For a 24-token batch, `prepare_inputs` refreshed `query_start_loc[0:2]` while the piece reads `query_start_loc[0:25]`.

* Added a new test, covering both NVIDIA and AMD platform: buffers are non-decreasing, unused capacity cannot capture real tokens, a search over the captured request range resolves every real token to its own request (request-padded and unpadded cases), rows the batch does not own are sentinels, and the capture-time dummy inputs follow the same convention.

Each buffer is handed over as the smallest view the kernel needs: `query_start_loc` as the live prefix, because the kernel derives its request count from the view length, and `ngram_context` as the whole buffer, because it indexes rows by request, so every
reachable row must be valid. Passing the full buffers, as the NVIDIA copy does, also fixes this, but makes every eager and FULL step search `max_num_reqs + 1` boundaries instead of the live count. Therefore preferring this over the NVIDIA fixes.

Additional info: steps whose padded token count exceeds the largest captured piece (512 here) run eager and were never affected, so long and few-shot prompts show no difference; short prompts, chunked prefill and prefix-cache continuations are the exposed cases. The two model states remain separate per-backend copies; I can unify them in a follow-up PR if preferred.
