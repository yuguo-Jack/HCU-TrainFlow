# [Bugfix] Warm GLM DeepGEMM mHC pre-norm specializations

[Upstream PR](https://github.com/vllm-project/vllm/pull/60567) · state: open · merged: False

## Original PR description

## Overview

GLM-5.3-Flash can finish startup and still pause to compile an mHC kernel when a new prompt length arrives. This PR moves those missing compilations to startup without changing the kernel math or split-K heuristic.

Addresses #60536. Depends on https://github.com/vllm-project/DeepGEMM/pull/29 for the compile-only entry point used by this implementation.

## Claims

- Register every reachable DeepGEMM mHC pre-norm specialization for GLM's configured token range, deduplicated by `(N, K, num_splits)`.
- Compile them through the existing startup warmup registry, without allocating input tensors or launching dummy kernels.
- Keep runtime split selection, kernel math, and backend selection unchanged.

## Details

### Why startup misses these kernels

The mHC pre-norm path contains a matrix multiplication implemented by DeepGEMM. It selects a split-K count (how many pieces to divide the reduction into) based on the number of tokens in the current engine step. Each distinct split count requires a separately compiled kernel. The row count `M` itself is dynamic, so there is no need to compile once per prompt length.

The existing selection is:

```python
num_splits = max(1, min(num_sms // ceil(M / 64), ceil(K / 64) // 4))
```

Here `M` is the step's token count, `K` is the input width, and `N` is the output width. For example, with 78 SMs and `K=16384`, `M=64`, `192`, and `16384` select 64, 26, and 1 splits respectively. Compiling the first and last does not compile the middle one. The number of required specializations depends on the GPU and configured token range; the issue's count of missing variants is not a universal constant.

The startup profile run and CUDA-graph capture exercise only some split counts. GLM does not register the remaining DeepGEMM variants for explicit warmup. The first real request that reaches a missing split therefore compiles it while serving, delaying that engine step and potentially other in-flight requests. This is a JIT coverage gap, not evidence of incorrect model arithmetic.

```text
Before: startup warms some splits -> request reaches a new split -> compile -> run
After:  startup warms all reachable splits -> request -> reuse compiled kernel
```

### What this changes

When GLM selects the DeepGEMM path, register its projection dimensions with a small kernel wrapper. The wrapper enumerates token counts up to `max_num_batched_tokens` at the heuristic's 64-token boundaries, maps them to `(N, K, num_splits)`, and deduplicates the keys. Startup compiles those keys; requests continue to call the same DeepGEMM runtime kernel.

### Why a companion DeepGEMM change?

The first proposal in #60536 is to warm each reachable split by executing one dummy row through the existing API. That can trigger compilation **without changing DeepGEMM**. This PR uses the same coverage strategy, but chooses compile-only warmup to follow the [current warmup contract](https://github.com/vllm-project/vllm/blob/main/docs/contributing/jit_kernel_warmup.md), which excludes real tensor allocation and dummy kernel launches.

The companion PR exposes `compile_tf32_hc_prenorm_gemm(n, k, num_splits)`, reusing the runtime JIT source and cache keys but stopping before launch. The trade-off is a cross-repository dependency and additional cold-start compilation time, rather than pauses during requests. This dependency is a choice of implementation, not a requirement inherent to fixing the issue.

### Relationship to earlier work

This builds on existing warmup work; the idea of warming mHC or DeepGEMM specializations is not new. The remaining gap is **GLM's DeepGEMM pre-norm GEMM with its existing token-dependent split heuristic**.

### Scope and alternatives

- The issue's dummy-row proposal is a valid way to trigger compilation through the existing DeepGEMM API. The compile-only choice and its dependency are explained above; the dependency is not necessary for every possible solution.
- The issue also suggests bucketing splits into `1/4/16`. That changes runtime tuning and needs prefill/decode performance evaluation. This PR deliberately leaves that heuristic unchanged.
- #49905 tracks broader DeepGEMM warmup gaps. This PR only covers this GLM mHC entry point, not all DeepGEMM kernels, module-loading costs, or a general JIT-monitor extension. It does not promise zero runtime compilation across the whole model.
