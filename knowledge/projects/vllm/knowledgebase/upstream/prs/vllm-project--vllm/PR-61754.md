# [Bugfix][KV Offload] Make in-flight mark_miss generation-aware

[Upstream PR](https://github.com/vllm-project/vllm/pull/61754) · state: closed · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Make failed promotion results generation-aware for filesystem and object-store tier lookups. A load job now carries the lookup token for the request that initiated it, so `mark_miss` cannot update a newer probe for the same `OffloadKey`.

## Claims

- Keep unresolved probes isolated from failed-load corrections; only the resolved generation that initiated a promotion can be marked missing.
- Ignore stale load completions whose lookup generation no longer matches the current request.
- Keep the existing failed-load livelock prevention without poisoning newer requests.

### The failure case

A promotion is submitted in one step and reported in a later one, by which time
its request may already be gone:

```text
Step N    A probes K -> RESOLVED HIT (generation g); K is queued for promotion
Step N    on_schedule_end() -> _flush_pending_promotions() -> submit_load(A)
          -> lookup_token(K, "A") captures LookupToken(K, "A", g)
Step N+1  A is aborted -> on_request_finished(A) -> cleanup() releases A's reference
          the already submitted load is deliberately not cancelled
Step N+k  get_finished_jobs() reports the promotion failed -> mark_miss(A's token)
```

The two calls inside step N are ordered load-then-release on purpose.
`build_connector_meta()` signals `on_request_finished()` before
`on_schedule_end()` (`offloading/scheduler.py`), but `finished_req_ids` only
holds requests that finished *between* steps, and those are not scheduled
again -- so a request cannot both queue a promotion in step N and be cleaned up
in step N. A promotion queued in step N is therefore always submitted while its
request still holds a lookup reference, and that reference is released strictly
later.

That ordering is also a documented framework guarantee: `submit_store()`,
`submit_load()`, and `touch()` are all issued before the request's
`on_request_finished()` (`tiering/base.py`), which is what releases the
reference.

A request parked on an unresolved promotion cannot complete on its own: an
external hit makes `get_num_new_matched_tokens()` return `load_kv_async=True`,
the request moves to `WAITING_FOR_REMOTE_KVS`, and
`_handle_blocked_waiting_request()` keeps skipping it until the transfer is
reported. It leaves that state in one of two ways -- the transfer is reported
and the request resumes, or the request is aborted first (client cancellation,
explicit abort, error, engine shutdown). The case below is the second one: the
abort releases the lookup reference, the in-flight transfer is deliberately not
cancelled, and its failure is only observed afterwards.

That interval is what makes the key alone insufficient: another request B can
probe the same `K` between step N and `mark_miss`.

Before (key only):

1. B probes `K` in a step after N and owns a newer generation `g'`.
2. A's failure arrives and calls `mark_miss(K)`.
3. The call cannot tell A's probe from B's, so it overwrites B's state.
4. B is now corrected by A's failed promotion instead of by its own probe.

After (token):

1. The promotion carries `LookupToken(K, "A", g)`, captured at `submit_load()`.
2. `mark_miss([token])` compares the token's generation with the live state.
3. `g != g'`, so the token is ignored and B's probe decides on its own.
4. If B still shares generation `g`, the correction does apply.

`MARKED_MISS` is what makes that last point safe to keep: it records that A's
promotion could not use the lookup result, not that `K` is absent from the tier.

#59096 guards the same call site, but only against probes that are still
`PENDING`/`IN_FLIGHT`. Once B's probe has resolved, the verdict is served from
cache without re-probing, so a key-only `mark_miss` still overwrites B's `HIT`
with a miss for a key the tier holds. Generation comparison closes that window;
`test_mark_miss_ignores_newer_resolved_probe` pins it.

## Details

`LookupToken` combines the offload key, request ID, and lookup generation. `LookupStatus` combines the lookup lifecycle (`PENDING`, `IN_FLIGHT`) with resolved outcomes (`HIT`, `MISS`, and `MARKED_MISS`). Successful, failed, and partial load completions remove their per-job token metadata.

A token is only minted for a request that still holds a resolved verdict for the key: `lookup_token()` asserts that precondition instead of returning an unresolved placeholder, so `LookupToken.generation` is a plain `int` and `mark_miss()` has no `None` special case. The only corrections it drops are a key entry that is already gone and a generation that has been superseded. `test_lookup_token_requires_resolved_verdict` pins the minting contract; tier tests that drove `submit_load()` directly now establish a verdict first, the way the scheduler does.

This is distinct from the existing skip-unresolved and stale-miss fixes in #59096 and #61717: it preserves in-flight state while associating the correction with the generation that initiated the promotion.
