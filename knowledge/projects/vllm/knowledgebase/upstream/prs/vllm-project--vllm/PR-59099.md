# [Bugfix][KV Offload] Make reset_cache re-entrant

[Upstream PR](https://github.com/vllm-project/vllm/pull/59099) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

A second `reset_cache()` on the offloading connector before the engine steps again fails on `assert not self._current_batch_jobs_to_flush`. The engine keeps running, but the call that made the second reset gets the error. It happens when two `reset_prefix_cache(reset_connector=True)` calls arrive with no step in between while store jobs are in flight: the first reset moves those jobs into the flush set, which stays set until the next step sends it. In the multiprocess engine, pause and sleep clear caches only once the engine is idle, so they don't hit this; in the in-process engine (`VLLM_ENABLE_V1_MULTIPROCESSING=0`), pause clears at once, so a pause or sleep can be one of the two resets. This lets the second reset add to the pending flush set instead of asserting.

The first version of this PR also kept an idle engine stepping until the flush set reached the workers. #62929 now does that (the engine keeps stepping until the flushed jobs are reported), so that part is gone after merging main.

## Claims

- Two `reset_prefix_cache(reset_connector=True)` calls with no step in between no longer raise. The first reset's flush set still goes out on the next step, and the engine goes idle once the workers report those jobs.
- A single reset is unchanged, and the other three "not in the middle of a step" asserts stay.

`test_cache_reset_twice_before_a_step_still_flushes` uses the real-scheduler helpers from #62929: it finishes a request with its store jobs in flight, resets twice, then checks that the next `schedule()` carries exactly those jobs in `jobs_to_flush` and that the engine goes idle once they are reported.

On main (8321d1119bc2, Linux CPU) the second reset fails:

```
>       assert not self._current_batch_jobs_to_flush
E       AssertionError
vllm/distributed/kv_transfer/kv_connector/v1/offloading/scheduler.py:2463: AssertionError
```

With the fix it passes, and so does the rest of the file (446 passed, Linux CPU); pre-commit is clean on both files. These tests build the CPU offload region in `/dev/shm`, so they don't run on macOS. No CI step runs this file today: the GPU "V1 KV Connectors" step is disabled, and the CPU step selects only `cpu_test`-marked tests. No GPU run: the reproducer is scheduler-level. Model outputs are unaffected, so no evals.

## Details

`_reset_cache()` moves every in-flight job id into `_current_batch_jobs_to_flush` and leaves it set on purpose: the workers must wait on those jobs before a later store reuses their CPU chunks, and the set goes out in the next step's metadata. A second reset before that step finds it non-empty. Merging into it is safe: the first reset already moved and cleared every in-flight job, so the second adds no ids, leaves #62929's fence as it is, and does not call `on_reset_flushed()` while the fence is held.

The reset is reached from `pause_generation(clear_cache=True)` and sleep (`EngineCore._reset_caches`, the RL weight-update path), from the dev-mode `POST /reset_prefix_cache?reset_external=true` and from `LLM.reset_prefix_cache(reset_connector=True)`.

Not a duplicate: #62929 leaves this assert in place, and none of the open offload PRs that touch this file removes it.
