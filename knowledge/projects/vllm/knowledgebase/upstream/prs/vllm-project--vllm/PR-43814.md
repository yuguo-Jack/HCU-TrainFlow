# [Bugfix][SM120] Enable CUTLASS grouped GEMM (MoE) for SM_120/SM_121 consumer Blackwell

[Upstream PR](https://github.com/vllm-project/vllm/pull/43814) · state: open · merged: False

## Original PR description

## Summary

Fixes two bugs that silently disabled the CUTLASS FP8 grouped GEMM path for all SM_120/SM_121 hardware (RTX 5090/5080/5070, DGX Spark GB10), causing every MoE expert dispatch to fall back to the Triton backend.

Fixes #43507.

---

## What changed

### Bug 1 — Python gate (`vllm/_custom_ops.py`)

\`\`\`python
# Before (wrong):
if cuda_device_capability < 90 or cuda_device_capability >= 110:
    return False

# After (correct):
if cuda_device_capability < 90 or cuda_device_capability >= 130:
    return False
\`\`\`

\`cuda_device_capability\` is an integer: \`121 >= 110\` is \`True\`, so this gate always returned \`False\` for SM121, routing every call through Triton. \`>= 130\` is correct — it reserves the exit clause for genuinely unsupported future architectures beyond SM12x.

### Bug 2 — Missing SM120 grouped GEMM kernel

Added \`csrc/libtorch_stable/quantization/w8a8/cutlass/moe/grouped_mm_c3x_sm120.cu\`, the SM120 analog of \`grouped_mm_c3x_sm100.cu\`. Configuration:

- **Schedule**: \`KernelPtrArrayTmaWarpSpecializedCooperativeSm120<2>\` (cooperative, 4×2 UMMA atom layout)
- **Tile shape**: \`128×128×128\` (same as SM100 default)
- **Cluster shape**: \`1×1×1\` (no programmatic multicast on consumer Blackwell)
- **Epilogue**: \`EpilogueScheduleAuto\` (auto-selects per-tensor/per-token scaling in the epilogue, matching the FP8-Dynamic quantization scheme)
- **Arch tag**: \`Sm120\` (runs on SM_121 as well per CUDA arch compatibility)

Added dispatch block in \`scaled_mm_entry.cu\` for \`version_num >= 120 && version_num < 130\`.
Added the \`.cu\` file to the existing SM12x build block in \`CMakeLists.txt\` (under \`FP4_ARCHS\`, which already sets \`ENABLE_CUTLASS_MOE_SM120=1\`).

---

## CUTLASS dependency

\`KernelPtrArrayTmaWarpSpecializedCooperativeSm120<2>\` requires the \`MainloopSm120ArrayTmaWarpSpecialized\` collective specialization, which is **not yet in CUTLASS 4.5**. It has been contributed upstream via [NVIDIA/cutlass#3280](https://github.com/NVIDIA/cutlass/pull/3280) (currently in review). This vLLM PR will compile correctly once vLLM's pinned CUTLASS revision includes that change.

## Hardware validation

Validated on **SM_121 hardware** (NVIDIA DGX Spark, GB10, 128 GB LPDDR5X unified memory):

- **Container**: vLLM source build, CUDA 13.0.2, \`TORCH_CUDA_ARCH_LIST=12.0a;12.1a;12.1+PTX\`, patched CUTLASS (includes NVIDIA/cutlass#3280 changes)
- **Model**: \`RedHatAI/gemma-4-26B-A4B-it-FP8-Dynamic\` (Gemma 4 MoE, 26B total / 4B active, FP8-Dynamic quantization)

**Result**: SM120 CUTLASS grouped GEMM collective activates and produces correct outputs. Previously fell back to Triton for every MoE dispatch.

### Throughput comparison (wall-clock, single-stream, MTP speculative decoding, 3 iterations)

| Prompt size | Baseline (Triton fallback) | This fix (SM120 CUTLASS) | Delta |
|---|---|---|---|
| Short (128 tok output) | 76.3 tok/s | 81.9 tok/s | **+7.3%** |
| Medium (512 tok output) | 89.8 tok/s | 89.8 tok/s | ≈0% (within noise) |
| Long (1024 tok output) | 87.6 tok/s | 85.5 tok/s | -2.4% (within noise) |

Short-sequence improvement is the clearest signal (decode-dominated, grouped GEMM runs every forward pass). Medium/long variance is dominated by speculative decoding accept-rate noise over 3 iterations.

- toan-tq · comment · 2026-09-26T14:54:29Z · [source](https://github.com/vllm-project/vllm/pull/43814#issuecomment-5847239056)

Hi @tgmerritt, @Harry-Chen — now that #54190 (CUTLASS v4.7.1) has landed, I built and tested this PR on an **RTX 5090 (sm_120)**. It compiles. I ran into two problems that need attention before the SM120 grouped path can be enabled. Details below. This is a report only; I have not proposed any changes.

**Environment:** RTX 5090 32 GB, driver 580.105.08, CUDA 13.0, torch 2.13.0+cu130, vLLM `main` @ `a4eb3f25d6` + this PR (`9d221b31` cherry-picks cleanly). CUTLASS v4.7.1, source build with `TORCH_CUDA_ARCH_LIST=12.0`. `grouped_mm_c3x_sm120.cu` compiles in ~27 s.

### 1. The kernel is compiled in but never selected on sm_120

With this PR applied, the extension contains `cutlass_moe_mm_sm120` (checked with `nm`). But all three of these still return `False` on the 5090:
- `torch.ops._C.cutlass_group_gemm_supported(120)`
- `ops.cutlass_group_gemm_supported(120)`
- `CutlassExpertsFp8._supports_current_device()`

Why:
- The PR relaxes the Python check in `vllm/_custom_ops.py` (`>= 110` → `>= 130`).
- The C++ `cutlass_group_gemm_supported()` in `scaled_mm_entry.cu` only reports the 90–99 and 100–119 ranges. It was narrowed to "archs with an actual dispatch" in #45277 (2026-06-14), after this PR was written.

So `VLLM_CUTLASS` is filtered out for sm_120 even though the kernel exists.

### 2. Wrong results when `a1q.size(0) <= 64`

To exercise the kernel, I made the C++ check return `True` for 120 in my local build. (That was only to run the tests; it is not a suggestion.)

**Kernel level.** `pytest tests/kernels/moe/test_cutlass_moe.py::test_cutlass_moe_8_bit_no_graph`, 20 cases, each run 3 times, each run in a fresh process:

| `a1q` rows (M·topk) | result |
|---|---|
| 12, 16, 42, 56 (M = 2, 7; topk 6 / 8) | **fail 3/3**: `illegal instruction` or `illegal memory access`. `compute-sanitizer` reports OOB global reads inside `cutlass_3x_group_gemm<float_e4m3_t, …, Sm120, ScaledEpilogueArray, 128x128x128>` |
| 384, 512, 1344, 1792 (M = 64, 224) | pass 3/3 |

All four scale combinations (per-token/per-tensor × per-channel/per-tensor) fail the same way.

**Diagnosis:**
- `run_cutlass_moe_fp8` sets `swap_ab = a1q.size(0) <= 64` (`experts/cutlass_moe.py:211`), and the problem sizes are then written as `(2N, M, K)`.
- The SM90 and SM100 dispatchers pick a `swap_ab=true` config under the same condition (`grouped_mm_c3x_sm90.cu:145-154`, `grouped_mm_c3x_sm100.cu:98`).
- The SM120 file has a single `swap_ab=false` config.

A standalone `ops.cutlass_moe_mm` call with identical data crashes 3/3 when the problem sizes are written swapped, and passes 3/3 when they are not.

**Serving level.** In serving this shows up as **silent wrong output**, not as a crash, and only inside a narrow window:
- `--moe-backend cutlass` goes through `TritonOrCutlassExperts`. Its small-batch fallback is gated on `has_device_capability(100)`, which is a `>=` check, so on sm_120 batches with ≤ 8 tokens go to Triton.
- CUDA graphs pad the batch size up to a capture size.

The kernel is therefore reached with swapped sizes only when **8 < M and M·topk ≤ 64, with M taken after padding**.

Measurements on `nm-testing/DeepSeek-Coder-V2-Lite-Instruct-FP8-dynamic` (topk 6, so M ∈ {9, 10}):

| run | Triton (same build) | this PR, `--moe-backend cutlass` |
|---|---|---|
| `--enforce-eager`, prefill of exactly 9 tokens, 4 greedy tokens | `[565, 291, 459, 207]` | `[1023, 330, 330, 330]` (2/2) |
| `--enforce-eager`, prefill of exactly 10 tokens | `[291, 459, 207, 17]` | `[1023, 543, 330, 543]` (2/2) |
| `--enforce-eager`, GSM8K 200 questions, 5-shot, `--max-concurrency 10` | 0.795 | **0.000** (2/2): every answer runs to `max_tokens`, and no error is logged |
| default CUDA graphs, GSM8K 200 questions, 5-shot | 0.79 (precompiled wheel, same settings) | 0.77 / 0.785: the window is unreachable, since 9–10 tokens pad to 16 (96 rows) |

The controls outside the window give the same tokens as the non-swapped path: eager with 11 tokens (66 rows), and CUDA graphs with 9 tokens.

Which models this affects:
- With default CUDA graphs, models with topk ≥ 5 never hit the window.
- That is consistent with the GB10 deployment mentioned earlier in this thread: Gemma-4-26B-A4B has topk 8, so its window is empty.
- **Prediction, not tested:** models with topk ≤ 4 would hit it even with CUDA graphs (16·4 = 64). The eager/graph prefill test above on a topk ≤ 4 FP8 MoE should show it.
