# [Bugfix][Frontend] Decode each streaming-input chunk after its own prompt

[Upstream PR](https://github.com/vllm-project/vllm/pull/65269) · state: open · merged: False

## Original PR description



## Overview

With streaming input, the frontend detokenizer only ever sees the first chunk's prompt. Each later chunk's output gets decoded straight after the previous chunk's output, so when a chunk stops partway through a character (max_tokens landing on a byte token), the next chunk's text starts with U+FFFD. This PR feeds each new chunk's prompt to the detokenizer as context, the same way the scheduler builds the model's context.

## Claims

- After a chunk that ends partway through a multi-byte character, the next chunk's text no longer starts with U+FFFD. That holds for DELTA and CUMULATIVE output, and for both the fast and the slow detokenizer.
- Voxtral realtime is unchanged. It re-sends each chunk's last token as the next prompt, and a character split across two chunks still comes out once, whole.
- Chunk boundaries that don't cut a character give the same text as before.

## Details

**Root cause.** `RequestState.apply_streaming_update` extends the prompt but never tells the detokenizer, which was primed once with the first chunk's prompt in `FastIncrementalDetokenizer.__init__` / `SlowIncrementalDetokenizer.__init__`. The scheduler builds the next chunk's context as the previous output minus its last sampled token, then the new prompt (`Scheduler._update_request_as_session`). When that dropped token is the first byte of a character, the detokenizer is still holding it as an unfinished character and prepends it to the next output. Qwen3-ASR realtime starts every segment with a fresh prompt and caps it at 64 tokens, so a segment that hits the cap mid-character shows this; so does any streaming-input session that stops on max_tokens.

**Fix.** At each chunk boundary, `apply_streaming_update` steps the new prompt's tokens through the detokenizer (`add_prompt_tokens`) and throws away their text. If the prompt starts with the token the scheduler just dropped (Voxtral realtime re-sends it, `all_outputs[-1:]`), that token is skipped: the detokenizer has already decoded it, and what it holds is then exactly the model's context. Without the skip, the Voxtral case breaks (`'�😀'` with gpt2).

**Why step the tokens instead of priming a fresh `DecodeStream(ids=...)`.** A primed prefix that ends mid-character never gets established (see #48854), and that's exactly the Voxtral re-send case. Stepping lets the next output complete the character.

**Slow path.** `SlowIncrementalDetokenizer.decode_next` now decodes the id it's given instead of reading `self.token_ids[-1]`. `detokenize_incrementally` only reads the last id once `prev_tokens` is set, so nothing changes for `update()`, and prompt tokens can go through without being added to the output.

**Cost.** One decode step per prompt token of each later chunk. Realtime chunks are a few tokens, and Voxtral's single re-sent token is skipped.

**Limitation.** When the prompt doesn't re-send the dropped token, the detokenizer keeps it just ahead of the new prompt. That only affects how the prompt's own first token decodes, and that text is thrown away.
