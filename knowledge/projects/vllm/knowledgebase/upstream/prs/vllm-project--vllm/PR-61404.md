# [Kernel] Scale elementwise kernel launches with the device, not just batch size

[Upstream PR](https://github.com/vllm-project/vllm/pull/61404) · state: open · merged: False

## Original PR description

## Overview

`silu_and_mul` and the other `act_and_mul` variants, the scalar activations,
`swigluoai_and_mul`, `situ_and_mul` and `rotary_embedding` all launch `grid(num_tokens)`
with one block per token, so the grid is only as wide as the batch however much work a
token carries. At decode that leaves most of the device idle. This splits a token's work
across `gridDim.y` when the batch alone cannot fill the device.

## Claims

- **+1.1% to +3.1% end-to-end output throughput** on Llama-3.1-8B and Qwen3-30B-A3B at
  low-to-moderate concurrency, with the custom ops enabled.
- Kernel level: up to 3.42x on `silu_and_mul` and 1.91x on `rotary_embedding`; medians
  1.31x over 288 shapes and 1.58x over 108 gated-activation shapes.
- Unchanged where the batch already fills the device: 0.994x-1.004x by construction.
- Bit-identical output on every tested shape; NIAH accuracy unchanged.
- One shared helper, no API change, no new kernel entry point.

## Validation

**Bitwise.** 288 shapes (`silu_and_mul`, `rotary_embedding`, bf16 and fp16, 1-2048 tokens,
neox and non-neox, several head counts) and 108 gated-activation shapes compared against
the unpatched build — `torch.equal` and SHA-256 of raw output bytes, not a tolerance.

**End-to-end**, MI355X, `VLLM_PLUGINS=` (upstream vLLM, no out-of-tree plugin), compiled
path with the custom ops enabled via
`-cc '{"custom_ops":["+silu_and_mul","+rotary_embedding",...]}'`. Output throughput,
mean of 4 reps, with arms rotated across GPUs and benchmark positions so GPU and ordering
bias cancel (measured GPU-to-GPU bias on identical builds: 0.21%):

| workload | Llama-3.1-8B | Qwen3-30B-A3B |
|---|---|---|
| in=128 out=256 conc=1 | **1.031x** | **1.012x** |
| in=128 out=256 conc=8 | **1.026x** | **1.028x** |
| in=1024 out=256 conc=32 | 1.017x | — |
| in=1024 out=128 conc=64 | 1.007x | 1.011x |
| in=200 out=64 conc=64 | 1.005x | **1.019x** |
| in=4096 out=128 conc=8 | **1.023x** | 1.013x |
| in=8192 out=64 conc=8 | 0.984x | 1.013x |
| in=32768 out=32 conc=4 | 1.000x | — |

TPOT moves with it — Llama at conc=1 goes 3.50 -> 3.40 ms (1.031x), and Qwen3-30B-A3B
gains 1-4% across its points. TTFT is unchanged within noise, as expected: the launch only
changes when `num_tokens < sm_count`, so prefill, where the grid is already full, is
untouched. That is also why the result is neutral at 8k/32k; the single 0.984x is ~0.5
sigma against that point's run-to-run spread.

**Models exercised, including those that showed nothing.** Reach was verified by loading
each model and reading vLLM's own `Op '<x>' not present in model` log plus worker profiler
kernel counts, not by inspecting configs:

| model | config | result |
|---|---|---|
| Llama-3.1-8B | TP1, custom ops on | table above, +0.5% to +3.1% |
| Qwen3-30B-A3B | TP1, custom ops on | table above, +1.1% to +2.8% |
| Kimi-K3 | TP8, aiter on (needed for the MLA backend) | throughput 0.999-1.004x, TTFT 0.997-1.019x, TPOT 1.000-1.005x |
| MiniMax-M3 | TP2 | no valid measurement — see below |
| DeepSeek-V4-Flash | TP8 | reaches none of these ops; not benchmarked |

Kimi-K3 is the only model in a 64-checkpoint survey that reaches `situ_and_mul`, and it
is flat: the kernel does run there (profiler confirms 279 calls), but it is 0.79% of
device time because aiter's fused MoE absorbs the expert activations, so a 7x kernel win
caps out below measurement resolution. MiniMax-M3 has no configuration that is both
usable and exercises the patched kernels — without aiter it runs at 5.5 tok/s, and with
aiter its rope is absorbed into `fused_minimax_m3_qknorm_rope_kv_insert` and
`rotary_embedding_kernel` executes zero times.

**Kernel level**, HIP-graph replay, minimum of several runs:

| kernel | shape | before | after | |
|---|---|---|---|---|
| `situ_and_mul` | d=28672, 1-2 tokens | 14.9-15.3us | 2.1-2.2us | 7.0x |
| `swigluoai_and_mul` | d=28672, 1 token | 9.0us | 2.1us | 4.4x |
| `silu_and_mul` | d=28672, 1-16 tokens | 7.2-8.0us | 2.2-2.5us | up to 3.4x |
| `silu_and_mul` | d=14336, 64 tokens | 4.52us | 2.82us | 1.60x |
| `rotary_embedding` | 32 heads, 8-32 tokens | 4.3-4.4us | 2.3us | up to 1.91x |

**Accuracy.** lm_eval RULER NIAH (`niah_single_2`, `niah_multikey_1`) at 8192 and 32768
tokens, 100 docs per cell, both models, both modes: 1.0 in all 16 cells, patched identical
to base. Generated text is not bit-identical across runs, but a null control — two
identical base builds — reproduces the same 62-92% range, so that is vLLM's batching
nondeterminism rather than this patch.

## Details

**Root cause.** `grid(num_tokens)` is as wide as the batch, not as wide as the device. At
one token these kernels put a single block on 256 CUs.

**Change.** `vllm_elementwise_launch_config()` in `csrc/launch_bounds_utils.h`, used by
every call site in `activation_kernels.cu` and `pos_encoding_kernels.cu`. Once
`num_tokens >= sm_count` it returns the existing configuration, so large-batch launches
are untouched; below that it uses smaller blocks and splits a token's work over `chunks`
blocks in `gridDim.y`. Every element is still handled by exactly one thread reading the
same inputs, which is why results do not move.

**Where this helper fits.** It suits kernels whose loop strides over the hidden dim, so
any `(threads, chunks)` split is valid. It does *not* suit kernels that give each
`blockIdx.y` a contiguous chunk and vectorize inside it — there a small chunk leaves too
few elements per thread to form a wide load. All the kernels here are the first kind.

**Scope — please read before judging the numbers.** These ops are `CustomOp`s, and
`CustomOp.default_on()` is false when Inductor is in use, so **in the default compiled
configuration they are replaced by Inductor-generated Triton kernels and this patch does
not run**. A decode profile confirms it: the activation work appears as
`triton_poi_fused_mul_silu_slice_*` with zero `vllm::act_and_mul_kernel`. The end-to-end
numbers above are from the explicit-custom-ops configuration; the default-configuration
gain is zero.

**Model reach of the gated activations.** Over 64 checkpoints, `situ_and_mul` is reached
by one architecture (Kimi-K3) and `swigluoai_and_mul` by none — MiniMax-M3's AMD path
deliberately uses an fp32 Triton `swiglu_oai_split`, for accuracy. Given the Kimi-K3
result above, **the 7.05x and 4.36x figures should be read as microbenchmark-only**; the
end-to-end case rests on `silu_and_mul` and `rotary_embedding`.
