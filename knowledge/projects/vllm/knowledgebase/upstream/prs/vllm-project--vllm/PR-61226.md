# [Security] Bound decoded and downloaded media per request

[Upstream PR](https://github.com/vllm-project/vllm/pull/61226) · state: closed · merged: True

## Original PR description



## Overview

Bound the total downloaded and decoded media in one multimodal request. The same patch was reviewed and approved in the private security fork before public submission.

## Claims

- Enforce one decoded-byte budget across images, audio, and video frames, including direct PIL chat inputs.
- Enforce one streamed HTTP download-byte budget across all media URLs in a request, while retaining the per-response limit.
- Reject requests that exceed either budget and document both configuration controls.

## Details

Previously, a request could pass every per-item media check while still scheduling and retaining many compressed media items before prompt-length admission. The change shares request-scoped budgets across the synchronous and asynchronous chat media paths. HTTP responses are charged as bytes stream in; decoded images are charged before raster allocation, audio decoders reserve capacity before decoding and settle their actual decoded bytes afterward, and video frames are charged during extraction or before JPEG decoding as appropriate. In-flight audio reservations count against the budget for other media. The existing per-item limits remain in effect.

The default decoded budget is 715827880 bytes and the default aggregate HTTP download budget is 256 MB. Operators can configure either limit through the documented environment variables. Requests above a limit now fail rather than consume unbounded frontend resources.

Coverage includes chat completions, messages, and responses that use the Python multimodal tracker; HTTP URLs, `data:` URLs, allowed local files, direct PIL inputs, and video frames. The opt-in Rust frontend and offline user-code helpers are outside this Python parser change.

File: `vllm/connections.py` · line 145

🔴 A transient network blip during a media download can now make an otherwise-small request spuriously fail the new per-request download budget. `_append_chunk` (connections.py:144) calls `request_budget.charge(len(chunk))` as bytes stream in, but on a retryable error (ConnectionError, ServerDisconnectedError, timeout, 5xx) `@ _sync_retry`/`@ _async_retry` (connections.py:449,469) re-invoke get_bytes/async_get_bytes from scratch, re-downloading the whole file and charging it to the same MediaRequestDownloadBudget.used again, since nothing rolls back the bytes already charged in the aborted attempt. Fix: charge only the bytes kept in the final successful response — reset the request_budget's partial charge on a retryable abort, or charge once after the full body is assembled, for both get_bytes and async_get_bytes.

<details>
<summary>Why this was flagged</summary>

Trigger: a chat request fetches a remote media URL whose download hits a transient mid-stream failure (connection reset, server timeout, 5xx) after partial bytes were already read, via MediaConnector.load_from_url/load_from_url_async (connector.py:403,462) passing the shared `self.download_budget` into HTTPConnection.get_bytes/async_get_bytes. `_append_chunk` already called `request_budget.charge()` for the partial bytes of the failed attempt; `MediaRequestDownloadBudget.used` is never decremented. The retry decorator (connections.py:279,325) restarts the download from byte 0 and charges the full file size again on top of the stale partial charge. On the base branch there was no per-request budget, so retries never over-counted; now a request whose real total downloaded bytes is under the 256MB default can be rejected with MediaRequestDownloadSizeExceededError purely because of a retried fetch, an operational failure with no user-visible cause (the client sees 'Request media downloads exceed VLLM_MAX_MEDIA_REQUEST_DOWNLOAD_SIZE_MB').

**Verification:** Retry double-counts the per-request download budget, causing spurious rejection of legitimate large requests under transient network failures. `_append_chunk` (vllm/connections.py:144) calls `request_budget.charge(len(chunk))` per chunk; `MediaRequestDownloadBudget.charge` only increments `self.used`, with no decrement or reset. `@ _sync_retry`/`@ _async_retry` re-invoke `get_bytes`/`async_get_bytes` from scratch on a retryable error, re-charging the full response.

</details>

🟡 (optional) Multi-audio chat requests now decode audio clips one at a time instead of in parallel, adding latency the base branch did not have. `_load_with_budget` holds `budget.decoded_budget.lock` for the full `load_audio(...)` call (lines 583-610), not just the quick charge. Since `global_thread_pool` dispatches concurrent `media_io.load_bytes` calls per request, and all audio items in a request share the same `MediaDecodedBudget` lock, concurrent audio decodes serialize to one thread. Image/video budgeting only call the quick `charge()`, not holding the lock across decode, so audio is inconsistent. Fix: compute/reserve the budget briefly under the lock, release it before calling `load_audio`, and charge the actual result afterward, restoring decode parallelism across audio items.

<details>
<summary>Why this was flagged</summary>

Trigger: a chat request with several audio clips, routed through MediaConnector.load_from_url_async -> connector.py:483 `loop.run_in_executor(global_thread_pool, media_io.load_bytes, data)`, with up to VLLM_MEDIA_LOADING_THREAD_COUNT=8 workers (vllm/envs.py:83). Bug: AudioMediaIO._load_with_budget (audio.py:572-612) wraps the entire load_audio() decode inside `with budget.lock:` (line 583), not just the charge step. On base, these decodes ran concurrently across threads; after this change they execute strictly one-at-a-time per request because decoded_budget is shared per BaseMultiModalItemTracker (chat_utils.py:614-615). No safeguard limits lock hold time; image.py:97-98 and video.py:131 only hold the lock for the cheap charge() call, showing audio's pattern is an outlier, not intended design.

**Verification:** nit. Real but non-breaking performance regression. In vllm/multimodal/media/audio.py:583-612, `_load_with_budget` opens `with budget.lock:` (line 583) and holds that lock across the entire `load_audio(...)` decode (lines 593-599); only `remaining()` and `budget.charge(audio[0].nbytes)` (611) need it. The lock is shared across every audio item in a request via connector.py:514-515, dispatched concurrently to `global_thread_pool`.
