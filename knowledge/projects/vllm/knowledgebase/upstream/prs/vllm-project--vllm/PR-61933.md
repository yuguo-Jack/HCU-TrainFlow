# [Rust Frontend] Validate bad_words limits during request lowering

[Upstream PR](https://github.com/vllm-project/vllm/pull/61933) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

A Rust-frontend request with more than `VLLM_MAX_NUM_BAD_WORDS` (128) bad-word sequences or `VLLM_MAX_BAD_WORDS_TOTAL_TOKENS` (1024) bad-word tokens reaches Model Runner V2, which raises uncaught inside the engine step and kills EngineCore. This rejects such requests during lowering with HTTP 400 / gRPC `INVALID_ARGUMENT`.

## Claims

- Lowering checks the combined `bad_words_token_ids` (raw IDs plus tokenized `bad_words`) against both limits, with the same env vars, defaults and messages as [MRv2](https://github.com/vllm-project/vllm/blob/a956a8126e6bd184cb0a6b8f7318fe4717675c2f/vllm/v1/worker/gpu/sample/bad_words.py#L40-L66).
- Requests within the limits lower as before. No proto change.

## Validation

`cargo clippy -p vllm-text -p vllm-server --all-targets -- -D warnings` is clean and `cargo test -p vllm-text -p vllm-server` passes. The new `lower_sampling_params_enforces_bad_words_limits` fails without the fix.

End-to-end with `Qwen/Qwen2.5-0.5B-Instruct` on MRv2 (RTX 6000 Ada), vllm-rs built from this PR and from its parent `a956a8126e`:

| Request | Before | After |
|---|---|---|
| HTTP chat, 65 `bad_words` (130 sequences) | 500, EngineCore dies | 400 `Too many bad words: 130. The max number is 128.` |
| gRPC, 129 one-token `bad_words_token_ids` | `INTERNAL`, EngineCore dies | `INVALID_ARGUMENT` `Too many bad words: 129. The max number is 128.` |
| gRPC, one 1025-token sequence | `INTERNAL`, EngineCore dies | `INVALID_ARGUMENT` `Too many total bad word tokens: 1025. The max is 1024.` |
| At the limits (128 sequences; 128 × 8 tokens) | — | 200 / OK |

Before the fix, EngineCore logs "EngineCore encountered a fatal error" from `BadWordsState.add_request` and `vllm serve` exits. After it, `/health` and later requests succeed. No eval, since accepted requests are unchanged.

## Details

vllm-rs sends `EngineCoreRequest` straight to EngineCore, skipping [`update_from_tokenizer`](https://github.com/vllm-project/vllm/blob/a956a8126e6bd184cb0a6b8f7318fe4717675c2f/vllm/sampling_params.py#L802-L845), the Python frontend's bad-words check. MRv2 enforces both limits in `BadWordsState.add_request` during `execute_model`. Nothing catches the `ValueError`, so [`run_engine_core`](https://github.com/vllm-project/vllm/blob/a956a8126e6bd184cb0a6b8f7318fe4717675c2f/vllm/v1/engine/core.py#L1508-L1513) logs "EngineCore encountered a fatal error" and exits.

- Limits are read from the environment per request, like `VLLM_MAX_STOP_STRINGS`. The managed engine inherits the same environment.
- The Python frontend checks only the count; #54721 adds the total-token check there.
- #51891 adds similar Rust limits inside `tokenize_bad_words`, which misses raw gRPC `bad_words_token_ids` on current `main`. I'll close this if it is rebased to cover them.
- Lets Dynamo's gRPC sidecar drop its copy of this cap ([ai-dynamo/dynamo#15550](https://github.com/ai-dynamo/dynamo/pull/15550)).
