# [Bugfix] Keep the AOT load-or-compile decision uniform across ranks

[Upstream PR](https://github.com/vllm-project/vllm/pull/60463) · state: open · merged: False

## Original PR description



## Overview

Fixes #60391. When one rank has a usable AOT artifact and another does not, each rank currently makes its own load-or-compile decision, so the ranks split: loaded ranks run a model whose collectives the compiling ranks never join, and under `VLLM_FORCE_AOT_LOAD` the failing rank dies while its peers hang in a later collective. This PR makes the decision collective: every rank loads iff every rank has a usable artifact.

## Claims

- The AOT load-or-compile decision is now uniform across all ranks of a multi-rank run: any rank missing its artifact, or failing to load it, sends every rank down the compile path.
- Under `VLLM_FORCE_AOT_LOAD`, a load failure now raises on every rank instead of killing one rank and hanging the rest.
- Single-rank runs and runs without an initialized process group keep the exact previous behavior.

## Validation

New tests in `tests/compile/test_aot_compile.py` spawn two gloo ranks sharing one cache root; rank 1 deletes its artifact between phases, and each rank records its load attempts and outcomes for the parent to assert on:

- `test_aot_load_decision_is_uniform_across_ranks`: phase B (rank 1 lost its artifact) makes **zero** load attempts on either rank, where the old code let rank 0 attempt (and here fail) its own load; phase C (artifacts re-saved) has both ranks attempt the load together with a uniform outcome.
- `test_force_aot_load_fails_uniformly_across_ranks`: with `VLLM_FORCE_AOT_LOAD=1`, the missing artifact raises `RuntimeError` on **both** ranks instead of one.

Commands and results (macOS, torch 2.13.0, Python 3.14, CPU):

```
python -m pytest tests/compile/test_aot_compile.py::test_aot_load_decision_is_uniform_across_ranks \
                 tests/compile/test_aot_compile.py::test_force_aot_load_fails_uniformly_across_ranks -q
# 2 passed in 14.38s
```

Red-green check: with `vllm/compilation/decorators.py` stashed, `test_aot_load_decision_is_uniform_across_ranks` fails on the load-attempt assertions; with the change it passes.

Full file: `python -m pytest tests/compile/test_aot_compile.py` gives 5 failed, 21 passed, 2 skipped, 1 error. The 5 failures and the error reproduce identically on unmodified upstream/main in this environment (`test_save_and_load` and siblings fail here on a torch-side `'function' object has no attribute 'finalize_loading'` load error, plus one WorkerProc startup issue); they are macOS/torch-2.13 environment limitations, not regressions from this change. The two new tests are part of the 21 passed.

## Details

Root cause: the load decision at the `@support_torch_compile` call site was purely local (`_try_load_aot_compiled_fn` per rank). The issue reporter hit this on the TPU plugin path, where a healthy rank loaded its artifact while an unhealthy rank compiled, and the two model variants diverged on collective usage.

Design: `_load_aot_fn_uniform` wraps the existing loader with two `all_gather_object` checkpoints when `world_size > 1`:

1. Artifact presence (file exists and is non-empty). Any rank without one sends every rank to compile.
2. Load success. A rank whose load raised reports the failure to the gather instead of raising past it, so no peer blocks in the collective; any disagreement sends every rank to compile, and `VLLM_FORCE_AOT_LOAD` re-raises uniformly on all ranks.

Both checkpoints are unconditional and in the same order on every rank, so the gather itself cannot introduce a new split. Tradeoff: multi-rank runs now compile on all ranks when previously the healthy ranks could have loaded, which is strictly the safe direction (compile is always correct) and matches how the rest of the compilation cache already treats rank divergence.

Limitations: validated on 2-process gloo/CPU; I do not have TPU or multi-GPU hardware here, so the CUDA and TPU plugin paths were not run. The collective used is plain `all_gather_object` on the default process group, the same mechanism vLLM already relies on elsewhere for cross-rank coordination.

Duplicate check: no open PR references #60391; the only issue comment is my own claim. AI assistance was used in the preparation of this PR; every changed line was reviewed and the tests above were run by the human submitter.

- gddezero · comment · 2026-10-10T09:58:39Z · [source](https://github.com/vllm-project/vllm/pull/60463#issuecomment-6096346297)

Thanks for picking this up. The two gathers cover the missing, truncated and failed-to-load cases from #60391.

It looks like a rank can still end up waiting alone when not every rank in the default process group runs the same compiled modules. The gathers are on the default group, so every rank in it has to call `_load_aot_fn_uniform` the same number of times. With pipeline parallelism plus speculative decoding, the drafter is only built on the last PP rank (`vllm/v1/worker/gpu_model_runner.py` line 604, `if self.speculative_config and get_pp_group().is_last_rank:`; and `if self.is_last_pp_rank:` at line 290 of `vllm/v1/worker/gpu/model_runner.py`; line numbers at the PR head), and drafter models such as `llama_eagle3.LlamaModel` are `@support_torch_compile`. So with PP=2 + EAGLE3 and AOT compile on (the default on torch >= 2.10), the last PP rank would enter the first `all_gather_object` for the drafter, PP rank 0 never would, and the last rank would wait until the process-group timeout and then raise. The first gather runs whether or not an artifact exists, so this would happen on every start, cold cache included.

I have not run PP + EAGLE on this branch; the above is from reading the code. I did check the gather on its own: `_load_aot_fn_uniform` copied verbatim, two gloo ranks, the loader stubbed to succeed, both ranks call it once for the target, then only rank 1 calls it again for a drafter while rank 0 keeps running. Rank 1 blocks for the full timeout (15 s in the test) and raises `RuntimeError: ... Timed out waiting 15000ms`.

# _load_aot_fn_uniform copied from vllm/compilation/decorators.py at 746e5facc9 into uniform_fn.py
import datetime, logging, os, tempfile, time, types
import torch, torch.distributed as dist, torch.multiprocessing as mp

def worker(rank, port, d):
    dist.init_process_group("gloo", init_method=f"tcp://127.0.0.1:{port}", rank=rank,
                            world_size=2, timeout=datetime.timedelta(seconds=15))
    g = {"torch": torch, "os": os, "Any": object, "logger": logging.getLogger("x"),
         "envs": types.SimpleNamespace(VLLM_FORCE_AOT_LOAD=False),
         "_try_load_aot_compiled_fn": lambda m, p: object()}
    exec(open("uniform_fn.py").read(), g)
    for name in ["target"] + (["drafter"] if rank == 1 else []):  # drafter only on the last PP rank
        p = os.path.join(d, f"{name}_rank{rank}"); open(p, "wb").write(b"x")
        try:
            g["_load_aot_fn_uniform"](None, p); print(f"rank{rank} {name}: ok", flush=True)
        except Exception as e:
            print(f"rank{rank} {name}: {type(e).__name__}: {e}", flush=True)
    if rank == 0:
        time.sleep(40)  # rank 0 keeps serving and never reaches the drafter gather

if __name__ == "__main__":
    mp.spawn(worker, args=(29571, tempfile.mkdtemp()), nprocs=2, join=True)

One way out would be to gather over the ranks that actually build and run the module, for example the TP group of the current PP stage, rather than the whole world.


- he-yufeng · comment · 2026-10-12T17:37:26Z · [source](https://github.com/vllm-project/vllm/pull/60463#issuecomment-6129402570)

Confirmed, and thanks for the worked repro. The gathers ran on the default group, so a module built on only one pipeline stage (the drafter on the last PP rank) entered an all_gather_object its peers never reach, and your two-rank gloo run is exactly the failure shape.

Fixed in 4e8ed7d9 by scoping the coordination to the caller's TP group (new `_aot_decision_group()`), your suggested direction. The ranks that run the same compiled graph are the ones that must agree, and the module set is uniform within a TP group even under PP, since the drafter is built on every TP rank of the last stage. The world group is kept only as a fallback where TP state is not initialized (minimal drivers, and the two existing uniform tests run that path).

With TP=1 per stage the decision now degrades to the plain per-rank load, which is safe there: pipeline stages never share a compiled graph, so there is no collective to split.

Coverage: new `test_aot_load_decision_scoped_to_own_stage_group` spawns two gloo ranks, gives each its own singleton decision group, and has only rank 1 make the drafter call; scoped, it returns immediately instead of waiting out the process-group timeout. The two existing uniform tests still pin the multi-rank agreement. One environment note: locally those two heavy tests could not get through inductor's code hashing on this machine (iCloud-evicted files in the torch package stall reads with Errno 60, both with and without this change), so I verified the fallback gather logic with a direct two-rank gloo run of `_load_aot_fn_uniform` instead: missing artifact gates with zero load attempts on both ranks, bogus artifact produces one attempt and a uniform compile fallback on both.
