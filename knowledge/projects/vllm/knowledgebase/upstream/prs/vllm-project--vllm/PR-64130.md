# [Perf][ROCm] Split the top-k mask across programs for small batches

[Upstream PR](https://github.com/vllm-project/vllm/pull/64130) · state: open · merged: False

## Original PR description

## Overview

At decode, `batch_size` is the number of concurrent requests, so `_topk_topp_kernel`'s grid of `min(num_sm, batch_size)` programs puts a single-stream step on one compute unit, each program sweeping a whole vocabulary row serially. `topk_topp_triton.py` already splits rows across programs for top-p, but all three split stages begin with `if HAS_K and tl.load(K + row) < VOCAB_SIZE: return`, so rows with an active top-k keep the one-program-per-row grid. This adds a split pipeline that covers them. Its kernels are compiled at startup, and it only runs for batch shapes where it was measured to be faster than the existing kernel.

## Claims

- **End to end, Qwen3.8-27B-FP8 with its own sampling defaults** (`top_k=20, top_p=0.95`; one MI325X, TP1): median TPOT 1.1–1.9% lower at concurrency 1–16 and 0.9–1.0% lower at 32, in each of three rounds; output throughput 0.6–1.6% higher. At 64 the change is 0.3–1.8%. At 128, outside the gate, nothing changes.
- **The mask per decode step, measured inside the server:** 186.5 → 50.2 µs at 1 row, 222.4 → 63.3 µs at 8, 298.4 → 111.5 µs at 32.
- **Nothing compiles while serving.** The extraction loops run to a runtime bound, so 12 warmup variants cover every `k` up to 64. The first requests after startup see the same TTFT as main; engine startup takes about 7 s longer.
- **Accuracy unchanged.** gsm8k, sampled with the model's defaults, is 0.663 strict-match over 10 runs, against 0.662 for main built the same way and 0.668 for the official image, inside a run-to-run spread of up to 1.3 points. Inside the server, the masks from this path and from the existing kernel were identical on all 419,364 sampler rows after warm-up (same logits through both).
- **No slower shape is dispatched.** A row cap per bound on `k` and a vocabulary floor of 150,000, measured on real decode logits, keep every dispatched shape faster than the existing kernel. Other shapes, other platforms and callers that pass no bound run the existing kernel unchanged.
- **Correction to the first version of this description:** its gains at small vocabularies were measured against the existing kernel called with `has_topp_only_rows=True`, which also launches the no-op top-p split. MRv2 passes `False` for batches where every row has a top-k, and against that the split barely gains below 150,000 (see Which batches take it). All numbers here use `False`.

## Details

### Root cause

`_build_dispatch` launches one program per row, capped at one per SM:

```python
num_programs = min(num_sm, batch_size)
```

Each program then sweeps its row in `BLOCK_SIZE` tiles, and the comment above the launch already names the consequence — "per-tile latency bounds kernel latency". The existing "Split-row pipeline for small batches" solves exactly this by giving a row to several programs, but it is a top-p machine: `K` reaches its three stage kernels only so that rows with an active top-k can `return` immediately. So there is no top-k capability in it to widen a gate into.

### Design

Top-k makes the row easier to split rather than harder, because top-k is applied before top-p: at `k=20` at most twenty logits survive, so the result is a scatter over known indices rather than a threshold comparison across the row. Four kernels:

1. **Per-chunk top-k** (`_topk_split_chunk_kernel`, grid `(rows, chunks)`) — each program extracts its own chunk's top-`k` by repeated max from registers. Exact, not approximate: an element of the global top-k is at least as large as every element of its own chunk bar at most k−1 of them, so it cannot hide from its chunk's top-k.
2. **Merge and cut** (`_topk_split_combine_kernel`, grid `(rows,)`) — merges the chunk candidates, cuts at that row's own `k`, applies top-p to the survivors.
3. **Scatter** — `fill_` then `scatter_` over the survivors.

Candidates are retired by index rather than by value, which keeps duplicate logits emitted once each, and is why tied rows match the reference.

**Compilation.** The bound on `k` is a runtime argument in `do_not_specialize`, and the only compile-time choices are the candidate tile (16, 32 or 64) and whether top-p is on, so each kernel has 6 variants. Both go through `triton_kernel_dispatcher_with_warmup` and are registered in `register_top_k_top_p_warmups` on ROCm. The chunk kernel loops to the bound; the merge is unrolled over the tile with a runtime guard, because a plain loop is slower there.

<details>
<summary>One non-obvious choice: the top-p cut is written on the suffix mass</summary>

```python
suffix = tl.flip(tl.cumsum(tl.flip(e, 0), 0), 0)
kept = head & (suffix > (1.0 - p) * total)
```

The direct prefix form saturates. A peaked row's running exclusive prefix mass reaches exactly 1.0 in float32 after about seventeen terms, so `prefix < p` is false for `p = 1.0` and silently truncates a row that asked for no top-p filtering at all. `get_top_k_top_p` only drops the `p` tensor when *every* row is 1.0, so a mixed batch carries such rows in. The suffix form compares against `(1 - p) * total`, which is exactly 0 at `p = 1.0`, and keeps the row whole. `test_matches_reference_across_p` covers `p = 1.0` for this reason.

</details>

### Which batches take it

| bound on `k` | most rows |
|---|---|
| ≤ 24 | 64 |
| ≤ 32 | 32 |
| ≤ 40 | 16 |
| ≤ 48 | 8 |
| ≤ 64 | 4 |

Measured on 768 decode rows of Qwen3-0.6B (vocabulary 151936) with each bound as every row's `k`; on Gemma 3 decode rows (262144) and at 248320 every capped shape wins with more margin. Past a row's cap the merge and the extra launches cost more than the split saves.

The split also needs a vocabulary of at least 150,000. Below that the monolithic kernel is cheap enough that the split loses at some capped shapes, for example 0.72x at vocabulary 32064 with `k=20` at 64 rows, and 0.57x with `k=64` at 4 rows. Every model I found that ships a `top_k` default (Qwen3, Qwen3.5 and Qwen3.8 with 20, MiniMax-M2 with 40, Gemma 3 and 4 with 64) has a vocabulary above that. The warmup is skipped for smaller vocabularies.

### Where the bound on k comes from

The candidate tile is a compile-time constant, so the pipeline needs an upper bound on every row's `k`. Taking it from the `k` tensor would be a device sync on the execution thread. `get_top_k_top_p` already reads a host mirror, `top_k_np`, and already derives `has_topp_only_rows` from it, so `max_top_k` follows the same route and costs nothing. It is threaded through the same call chain as `has_topp_only_rows`, and defaults to `None`, which selects the existing behaviour.

### Complexity

283 lines in `topk_topp_triton.py` and 54 across `topk_topp_sampler.py` and the four callers that pass the bound, tests excluded. The 283 are the two kernels, their warmup-registered dispatchers, the launch helper and the row cap. The split costs four launches where the monolithic kernel needs one, which is why it is limited to the shapes in the table above.

### Overlapping work

- #62594 also split the sweeps of rows with an active top-k across programs, on CUDA, by adding split branches to the monolithic kernel itself; its author closed it after measuring 0.5% lower TPOT at 128 rows per step. This PR leaves the monolithic kernel unchanged, adds a separate pipeline for ROCm only, and caps it at 64 rows.
- #62596 changes the monolithic kernel's top-k pivot (#61998). It does not touch this path; the main column above will move when it lands, and I will measure again.
- #54651 and #61996 are the top-p split pipeline this mirrors.

### Limitations

- **A batch with any greedy or top-p-only row falls through entirely.** `max_top_k` is the max over all rows, and such a row carries `k = vocab_size`. Leaving greedy rows out of the bound would keep mixed traffic on this path; it is a follow-up.
- **The two paths can disagree at the top-p boundary**, because the existing kernel's pivot search is approximate. In the cases found, this path matched an exact sort-based cut and the existing kernel did not. On a row with no variance at all the existing kernel masks nothing, while this path keeps `k`; `test_a_zero_variance_row_diverges_from_the_reference` records it.
- **Gated to ROCm and measured on gfx942 (MI325X) only**, and the row cap was measured on that GPU.
- **Not wired into the V1 runner** (`TopKTopPSampler`) or the V1 rejection sampler, which call `apply_top_k_top_p` without the bound.
- **This is a second implementation beside the existing split pipeline**, which the contribution guide discourages. Teaching that pipeline to apply top-k would be the unified design; it is a substantially larger change.
