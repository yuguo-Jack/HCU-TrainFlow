# [Perf] Fuse admission-time staged writes into fewer kernel calls

[Upstream PR](https://github.com/vllm-project/vllm/pull/62018) · state: open · merged: False

## Original PR description

## Overview

A 3-commit series that extends the existing `FusedStagedWriter` (introduced in #44944 for `BlockTables`) to three more places that still apply correlated `StagedWriteTensor` writes with multiple separate calls, each paying its own CPU-side dispatch and kernel-launch overhead:

1. `RequestState` (`states.py`): `total_len` + `all_token_ids` + `num_computed_tokens` -- always staged together in `add_request()`. 3 calls -> 1.
2. `BadWordsState` (`bad_words.py`): `bad_word_token_ids` + `bad_word_offsets` -- always staged together. 2 calls -> 1.
3. `LogitBiasState` (`logit_bias.py`): `allowed_token_ids` + `logit_bias_token_ids` + `stop_token_ids` -- all int32, fused into 1. `logit_bias` itself is float32 and `FusedStagedWriter`'s content buffer is hardcoded to int32, so it keeps its own separate call (4 calls -> 2).

## How this was found

`py-spy` profiling (30 Hz, raw collapsed-stack format) of a running EngineCore process under decode-heavy concurrent load (128 concurrent requests, varied prompts, `vllm serve` on 2x RTX 5090) showed `UvaBufferPool.copy_to_uva` as a real, measurable chunk of self time, spread across many independent small call sites in `vllm/v1/worker/gpu/`. Grepping for `.apply_write()` call sites found 12+ places invoking it, only one of which (`BlockTables`) already uses the fused path.

## Duplicate-work check

Searched `gh pr list`/`gh issue list` for `FusedStagedWriter`, `StagedWriteTensor`, `copy_to_uva`. Found:
- #44944 (merged): introduced `FusedStagedWriter` for `BlockTables` -- the mechanism this series extends, not a duplicate.
- #51334 (open): optimizes the *data representation* of staged writes (NumPy chunks instead of Python list boxing) in `rope.py`/`buffer_utils.py` -- a different, complementary layer (makes each call cheaper; this series reduces the *number* of calls). No file overlap with this series' commits.
- #60206 (open): CPU-backend-only override files (`vllm/v1/worker/cpu/*`) -- does not touch any file this series changes.
- #58403 (open): skips the block-table H2D copy entirely when unchanged -- different file, different mechanism.

No open PR does what this series does.

## Performance

Each commit's message has its own isolated-benchmark numbers (CUDA events, fresh state object per trial so there's no cross-trial pollution, old vs new order alternated per iteration, correctness checked bit-exact against the pre-patch implementation before timing). Summary:

| Commit | Calls before -> after | Speedup | Saving per admission batch |
|---|---|---|---|
| `RequestState` | 3 -> 1 | 1.33x-2.16x | 65-109us |
| `BadWordsState` | 2 -> 1 | 1.34x-1.46x | 43-46us |
| `LogitBiasState` | 4 -> 2 | 1.18x-1.27x | 34-45us |

In all three, the saving shrinks as the number of requests admitted in the same step grows -- expected, since this removes fixed per-call Python/kernel-launch overhead that's amortized over more real work at larger batch sizes. It's largest (and most representative of real traffic, where admission is usually 1-a-few requests per step, not dozens at once) at the small end.

This is admission-time overhead (triggered by `add_request()`, not every decode step), so its share of total engine time scales with how often new requests enter the running batch relative to total steps -- larger for high-QPS/short-completion workloads (high admission churn) than for long-generation workloads where each request is admitted once and then decodes for a long time.
