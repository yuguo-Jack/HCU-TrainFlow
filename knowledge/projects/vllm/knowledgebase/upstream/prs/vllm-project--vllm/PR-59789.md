# [Bugfix][Spec Decode] Size the YaRN rotary cache to cover max_position

[Upstream PR](https://github.com/vllm-project/vllm/pull/59789) · state: open · merged: False

## Original PR description



## Overview

Follow-up to #49343: YaRN sizes its cache from `original_max_position_embeddings * factor` and ignores `max_position`, so an EAGLE draft crashes once a request goes past that length under a target with a longer `max_model_len`.

## Claims

- `get_rope` now passes `max_position` to `YaRNScalingRotaryEmbedding`, so the YaRN cache is built large enough to cover every position the model can receive.
- Existing cache rows are unchanged.

## Validation

- The new test `test_yarn_draft_rope_covers_target_max_model_len` fails on `main` and passes with this change.
- On one H200 with the nightly (`0.30.1rc1.dev575+gfa212b8dc`), I served an 8B `LlamaForCausalLM` target with `--max-model-len 65536` and an EAGLE-3 draft with YaRN (`factor: 2` over 8192), and sent one 18K-token request. Without this change the engine crashes at position 16384 with `index out of bounds ... < 16384`. With this change the request completes and the server stays up.

## Details

- `_compute_cos_sin_cache` uses `math.ceil(original * factor)` for the old row count, because `torch.arange` on a float end gives `ceil(end)` rows and `int` would drop a row when the product is not an integer.
- It reads `max_position` with `getattr(self, "max_position", None)`, because `MRotaryEmbedding` reuses this method without setting it, so its cache stays as before.
- `deepseek_scaling_rope.py` sizes its cache the same way and is left unchanged here.
- This fixes the crash, not draft quality. Positions past `original * factor` are extrapolated, so acceptance there may drop.
