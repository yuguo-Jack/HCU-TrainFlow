# [CI] Move Attention, Quantization and MoE kernel tests and their AMD mirrors from fixed to automatic shards

[Upstream PR](https://github.com/vllm-project/vllm/pull/62077) · state: closed · merged: True

## Original PR description

## Overview

Moves two kernel test steps and their two AMD mirrors from fixed pytest shards to `automatic_shard`, the way #61200 and #61477 moved other steps. For each: `parallelism` is dropped, `--shard-id`/`--num-shards` come off the commands, `Shard %N` comes out of the label (the generator adds `shard N/M`), and `automatic_shard: true` is set. No tests change.

## Claims

- Each step runs as parallel jobs planned from main's per-file timings, with each job running only its share of the tests:

| Step | Was | Shards in `/ci run` |
|---|---:|---:|
| `kernels-attention-test` | 7 fixed | 4 |
| `amd-kernels-attention-test` | 6 fixed | 6 |
| `kernels-moe-test` | 5 fixed | 4 |
| `amd-kernels-moe-test` | 5 fixed (inherited) | 3 |

- Fixed pytest shards split by test count, so some shards finish in a few minutes while others take much longer, and every shard pays the job startup again. The plan balances by measured time, so these steps use fewer jobs and finish sooner than main's fixed split.
- Every test runs exactly once across the shards, with the same environment as before.

## Validation

- Planned each step and mirror with ci-infra main's `runtime_shard.plan_step` against main's timings on the step's own queue.
- Rendered each step and mirror with the pipeline generator and ran every shard's commands against a mock test tree, as a PR build and with main's `pytest -p ci_otel` wrapper: every test of every command ran in exactly one shard, with the same env.
- Build on the current head (scoped to the four steps): every shard passed with no retries; the slowest took under 18 minutes. Machine time is 21-38% below main's fixed split. Passed counts match main exactly. Skipped counts are lower only because main's fixed shards each collect every file, so files skipped at module level count once per shard there and once here.
- MI300 Attention: in two earlier builds its slowest shard ran 21-23 minutes. Nearly all of that is `test_swap_blocks` in `test_cache.py`, whose CPU-GPU copy cases vary several-fold between hosts; main's fixed split has the same problem, with its slowest shards running longer.

## Details

- **Left out.** `kernels-quantization-test` (NVIDIA) stays on its fixed split: one automatic shard ran past the 22-minute bar in three builds, because some tests cost more when they share a process than their per-file timings show. Its AMD mirror stays fixed with it, since a mirror shards only when its base step is enrolled. `kernels-b200` stays fixed too: its command is a hand-written `case "$$BUILDKITE_PARALLEL_JOB"` per shard, which needs rewriting as plain pytest commands first. Helion is out because main has disabled it.
- **Untimed files.** Each plan lists some files with no timing on main, mostly tests for other hardware that skip on these queues. The plan places them in the first shard.
- **`caplog`.** `tests/kernels/moe/test_moe_weight_loading_padded.py` asserts on log text through `caplog_vllm`, but in a unit test that starts no engine, so test order within a shard doesn't affect it.
- **Timeouts unchanged (human).** `timeout_in_minutes` is per job and stays sized for one shard, as in #61200 and #61477. If planning fails, or the `VLLM_CI_RUNTIME_SHARD` rollback switch turns sharding off, these steps run as one job and the L4 steps and the Attention and MoE mirrors would hit their timeouts. Making the timeout follow the shard count belongs in a central timeout setting rather than in per-step values.
- **Where to look.** `.buildkite/test_areas/kernels.yaml`: the two steps and their `mirror.amd` blocks.
