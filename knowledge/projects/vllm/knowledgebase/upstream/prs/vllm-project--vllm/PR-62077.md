# [CI] Move Attention, Quantization, MoE and Helion kernel tests and their AMD mirrors from fixed to automatic shards

[Upstream PR](https://github.com/vllm-project/vllm/pull/62077) · state: open · merged: False

## Original PR description



## Overview

Moves four kernel test steps, and their AMD mirrors, from fixed pytest shards to `automatic_shard`, the way #61200 and #61477 moved other steps. For each: `parallelism` is dropped, `--shard-id`/`--num-shards` come off the commands, `Shard %N` comes out of the label (the generator adds `shard N/M`), and `automatic_shard: true` is set on the step and on `mirror.amd`. No tests change.

## Claims

- Each step runs as parallel jobs planned from main's per-file timings, with each job running only its share of the tests:

| Step | Was | Planned shards |
|---|---:|---:|
| `kernels-attention-test` | 7 fixed | 3 |
| `amd-kernels-attention-test` | 6 fixed | 6 |
| `kernels-quantization-test` | 6 fixed | 3 |
| `amd-kernels-quantization-test` | 6 fixed (inherited) | 3 |
| `kernels-moe-test` | 5 fixed | 4 |
| `amd-kernels-moe-test` | 5 fixed (inherited) | 3 |
| `kernels-helion-test` | 5 fixed | 3 |
| `amd-kernels-helion-test` | 2 fixed | 1 (one job) |

- Fixed pytest shards split by test count, so some shards finish in a few minutes while others take much longer, and every shard pays the job startup again. The plan balances by measured time, so these steps use fewer jobs and less machine time, with each shard staying under the 20-minute target.
- Every test runs exactly once across the shards, with the same environment as before.

## Validation

- Planned each step and mirror with ci-infra main's `runtime_shard.plan_step` against this branch and main's timings on the step's own queue.
- Rendered each step and mirror with the pipeline generator and ran every shard's commands against a mock test tree, as a PR build and with main's `pytest -p ci_otel` wrapper: every test of every command ran in exactly one shard, with the same env. The AMD Helion mirror was confirmed to stay one job.
- `/ci run` exercises all eight; none is optional.

## Details

- **Left out.** `kernels-b200` (and its NVFP4 Dense Emulation mirror) stays on fixed shards: its command is a hand-written `case "$$BUILDKITE_PARALLEL_JOB"` per shard, which needs rewriting as plain pytest commands first. `kernels-core-operation-test`'s mirror is in #61862.
- **Untimed files.** Each plan lists some files with no timing on main, mostly tests for other hardware that skip on these queues. The plan places them in the first shard.
- **`caplog`.** `tests/kernels/moe/test_moe_weight_loading_padded.py` asserts on log text through `caplog_vllm`, but in a unit test that starts no engine, so test order within a shard doesn't affect it.
- **Timeouts unchanged (human).** `timeout_in_minutes` is per job and stays sized for one shard, as in #61200 and #61477. If planning fails, or the `VLLM_CI_RUNTIME_SHARD` rollback switch turns sharding off, these steps run as one job, and the L4 Attention, Quantization and MoE steps and the Attention and MoE mirrors would hit their timeouts. Making the timeout follow the shard count belongs in a central timeout setting rather than in per-step values.
- **Where to look.** `.buildkite/test_areas/kernels.yaml`: the four steps and their `mirror.amd` blocks.
