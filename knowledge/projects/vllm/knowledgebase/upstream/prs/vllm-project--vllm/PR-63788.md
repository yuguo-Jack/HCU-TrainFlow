# [Bugfix][KV Offload][OBJ] Don't lose a completed transfer when telemetry is unavailable

[Upstream PR](https://github.com/vllm-project/vllm/pull/63788) · state: closed · merged: True

## Original PR description

## Problem

In `obj/manager.py`, `_poll_active_transfers` calls `get_xfer_telemetry()` after the transfer completed, and the call sits outside any `try`. Builds compiled without telemetry raise there. The exception escapes the tier, so a finished job is lost.

This is the same defect as #63787 at a different call site. In the connector an enclosing `except Exception` catches the raise and reports a false failure. Here nothing catches it.

## Change

Guard the call. On a raise, log once and leave `transfer_time` as `None`. The job still reports success and the handle is still released. Only the timing is lost. Nothing changes when telemetry works.

## Tests

`test_telemetry_failure_does_not_lose_successful_transfer`: a raising `get_xfer_telemetry` must still give `JobResult(success=True)` with `transfer_time is None`. Without the guard this test does not pass, so it pins the bug. It sits next to `test_post_transfer_cleanup_failure_does_not_lose_result` and `test_release_xfer_failure_retries_without_losing_result`, which cover the same shape for the other cleanup calls.

It passes on the `vllm/vllm-openai:nightly` image with this branch on `main` at `4f140a2`. `ruff check` and `ruff format` pass on both files.

## Scope

I did not reproduce this one in a live deployment, because we do not run the OBJ tier. It is the same bug shape at a call site with less protection. I found it while I fixed the connector.

## Relationship to #62650

#62650 covers a failed NIXL submission in the same file. This covers a telemetry raise after the transfer completed. Different functions, no shared code.

I applied both to current `main` in both orders. There is no conflict in `obj/manager.py` or `test_obj_tier.py`. Whichever lands first, the other needs no change. I can rebase on #62650 if that is easier to review.

I also ran the tiering tests with #62650 applied on top of this branch. The result is the same as with #62650 alone, so the two changes do not interfere.
