# [Perf][torch.compile] Pre-create FlashInfer AR+RMSNorm workspaces at backend init

[Upstream PR](https://github.com/vllm-project/vllm/pull/61268) · state: open · merged: False

## Original PR description



## Overview

Pre-create the FlashInfer AR+RMSNorm workspaces in `VllmBackend.__init__` so their allocation is no longer charged to `torch.compile` time. Related to #34635. This is a narrower alternative to #35216 (reverted in #37733 after #37732), which moved the whole pass.

AI assistance was used (Claude Code) to investigate, draft, and run tests.

Not a duplicate: I found no open PR addressing #34635. The only prior attempt, #35216, was merged and reverted.

## Claims

- The workspace allocation (a cross-rank collective, plus any first-time FlashInfer JIT build) moves out of the `torch.compile` window and into model construction.
- Outputs are unchanged.
- No measurable `torch.compile` speed-up on the configuration tested. This is an accounting change, not a startup speed-up on this setup (see Validation).

## Validation

**Setup:** 2x H100 80GB SXM (NV18), Qwen3-0.6B, TP=2, `fuse_allreduce_rms` on, fresh `VLLM_CACHE_ROOT` per run, warm FlashInfer JIT cache, 3 alternating baseline/patched runs, baseline = `f26d9f432c`.

| | run 1 | run 2 | run 3 | mean |
|---|---|---|---|---|
| `torch.compile` time, baseline (s) | 23.71 | 25.71 | 27.29 | 25.57 |
| `torch.compile` time, patched (s) | 25.27 | 23.71 | 31.51 | 26.83 |

- Run-to-run spread is about ±4 s, so there is no measurable compile-time difference.
- Workspace creation relative to `Starting torch.compile` (rank 0): baseline +6 s, +7 s, +9 s (inside the compile window); patched -4 s in all 3 runs (before it).
- Creating the workspace, timed directly (2 ranks, bf16, hidden 1024, max_token_num 16384, warm JIT): about 0.13 to 0.19 s. The base workspace dominates; the quant workspace reuses it.
- Greedy outputs identical across all 6 runs, for a short prompt and a ~2,500-token prompt (the length that regressed under #35216).

**Tests**

```bash
# unit tests (GB10, aarch64): 13 passed
pytest tests/compile/passes/distributed/test_fusion_all_reduce.py -k "preinit or workspace_hidden or oneshot"

# CI selection of the TP2 AR+RMS e2e test (2x H100): 10 passed, 30 skipped, 1 failed
pytest tests/compile/fusions_e2e/test_tp2_ar_rms.py -k "inductor_partition and not +rms_norm and (not +quant_fp8 or +quant_fp8 and (qwen3 or deepseek)) and not Scout"
```

- The 1 failure is `meta-llama/Llama-3.1-8B-Instruct` returning a gated-repo 401 (no HF token on the box). `nvidia/Llama-4-Scout` was deselected for the same reason. The skips are Blackwell-only, fp4 and AMD cases.
- `tests/compile/test_config.py::test_use_cudagraphs[*]` (4 tests) fail on the GB10 with and without this change (`facebook/opt-125m` Hub fetch warnings); unrelated.
- ruff check and format pass.

**Not covered:** speculative decoding with a draft model wider than the target, Blackwell / MNNVL backends, models larger than 0.6B, cold-JIT startup timing.

## Details

`AllReduceFusionPass.__init__` computed the support checks (`tp_size <= 1`, missing `model_config`, FlashInfer unavailable, unsupported world size) and `max_token_num` inline. That logic now lives in `_fused_ar_workspace_kwargs` in the same file. Both the pass and the new `preinit_fused_ar_workspaces` call it, so they cannot disagree on workspace size.

The pass is still constructed at the same point in `VllmBackend.__call__`, so no other pass state is initialised earlier (unlike #35216). It now finds the cached workspace singletons.

Side effects:
- Two `logger.warning` calls became `warning_once` so the shared helper does not print twice.
- `AllReduceFusionPass.group` and `.workspace_hidden_dim` are no longer stored (no users in the repo).
- Memory profiling is unchanged (identical "Available KV cache memory" in baseline and patched runs).
- `VllmBackend` construction now touches the TP group when `fuse_allreduce_rms` is on. This is auto-enabled only for TP>1, so distributed state exists; an explicit `fuse_allreduce_rms=True` without distributed init would now fail at construction instead of at compile.

Limitation: the workspace is sized for the widest hidden size at first creation. With a pre-init this happens when the target model's backend is built, which should precede any draft model's backend, but I did not test a wider draft model.
