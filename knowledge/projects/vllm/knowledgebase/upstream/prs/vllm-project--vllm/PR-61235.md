# [Bugfix][LoRA] Slice expert LoRA by the unpadded per-rank size under TP

[Upstream PR](https://github.com/vllm-project/vllm/pull/61235) · state: closed · merged: True

## Original PR description

## Overview

Expert LoRA factors are sliced at the wrong offset under TP > 1 when the MoE backend pads the expert intermediate dimension (e.g. Marlin / FlashInfer TRTLLM MXFP4). Every rank except rank 0 silently applies the wrong LoRA rows.

## Claims

- `FusedMoEWithLoRA` and `FusedMoE3DWithLoRA` shard an adapter along the intermediate dim by the unpadded per-rank size, matching how the base expert weights are sharded.
- No behavior change when the backend does not pad.
- No dependency on a FlashInfer version.

## Details

Root cause: `_slice_w13_b` / `_slice_w2_a` use `moe_config.intermediate_size_per_partition` as the per-rank stride. `RoutedExperts.__init__` overwrites that field with the result of `maybe_roundup_sizes()`, so it is the padded size (MXFP4 rounds up to 128 for Marlin / TRTLLM / DeepGEMM / CUTLASS and to 64 for Triton). The base weights are sharded by `loaded_weight.shape[shard_dim] // tp_size` in `RoutedExperts._load_w13` / `_load_w2`. With 576 padded to 640, the base weight of rank `r` holds rows `[576 r, 576 (r + 1))` while the adapter slice is `[640 r, 640 (r + 1))`. Nothing raises because the slice is copied into the head of a zero buffer. We first observed this on DeepSeek V4.1 (TP 4, padded MoE backends).

Fix: use `moe_config.intermediate_size_per_partition_unpadded` as the stride. Buffers keep the padded size with a zero tail. For the concatenated `(gate, up)` layout of the 3D class, the up half is placed at the allocated per-rank size, where the base `w13` has it.

Not addressed: GPT-OSS MXFP4 uses a block-aligned shard stride in its own loader (`cdiv(intermediate_size / 32, tp_size) * 32`), which differs from `intermediate_size // tp_size` at TP 4 / 8.

Not a duplicate: searched open PRs and issues for `_slice_w13_b`, `intermediate_size_per_partition LoRA padded`, `fused_moe LoRA TP slice`; nothing addresses this. #61164 and #61165 touch other parts of the MoE LoRA path and do not overlap.
