# PR Description: Mooncake EC Connector for Distributed Encoder-Cache Transfer

## Purpose

This PR extends the existing `example` EC connector path to use `Mooncake` as the transport backend, enabling distributed storage and transfer for encoder-cache data in EPD-style disaggregation.

Compared to the issue [#39766](https://github.com/vllm-project/vllm/issues/39766), this implementation takes a minimal-surface-area approach to adding Mooncake transport support while limiting changes to encoder-cache internals and keeping integration patterns in a production-friendly shape.

cc @herotai214 @knlnguyen1802 @khuonglm 

## Summary

The change introduces a Mooncake-backed encoder-cache connector flow for:

- decoupling encoder and decoder execution nodes,
- moving encoder cache material through a remote transfer channel,
- and avoiding fragile dependency on local/shared storage backends.

Key design choice: use Mooncake `TransferEngine` as the transport backend, and maintain the transfer staging area as pinned CPU memory. This better isolates Mooncake transfer memory from CUDA memory pressure on decode/prefill nodes and reduces interference with KV cache residency.

## High-level Design

### 1. Storage and transfer model

After an encoder run finishes on an encoder node, multimodal cache data is written into a Mooncake staging region and associated transfer metadata is returned in `ec_transfer_params`. On the consumer side, the scheduler uses this metadata to request remote encoder caches and populate local execution state before model forward.

`TransferEngine` is used as the actual bulk data path. The control channel remains lightweight, carrying only metadata and handshake messages.

### 2. CPU pinned transfer buffer strategy

This PR uses a dedicated pinned CPU buffer for encoder-cache transfer staging:

- avoids competing with CUDA KV cache memory for allocation and lifetime,
- keeps transfer registration and reuse deterministic,
- aligns with multi-node deployment expectations where RDMA-like transfer semantics are required.

### 3. Transfer buffer lifecycle management

The transfer buffer now follows explicit ownership rules:

- Ring-based allocation with bounded capacity tracking.
- Slot pinning/refcount support for in-flight data.
- Safe eviction behavior:
  - in-flight/pinned slots are protected from eviction/reuse,
  - completed/failed paths release resources in a controlled way.
- Callback-based synchronization keeps internal ownership maps coherent.

In short, the transfer buffer has a defined lifecycle (`allocate -> use -> complete/timeout -> release`) instead of uncontrolled overwrite.

### 4. Failure and recovery behavior

Remote transfer misses are treated as recoverable cache misses:

- failure is surfaced as failed hash sets,
- scheduler disables remote-cache attempt for affected hashes and can reschedule locally,
- connector completion and cleanup paths are designed to avoid hard aborts in normal transient-miss scenarios.

## Compatibility and scope

This PR intentionally remains conservative for this stage:

- Mooncake EC is aligned to single-role deployment (`ec_producer` or `ec_consumer`), while full dual-role(`ec_both`) handling is deferred.
- Base behavior without Mooncake remains unaffected through existing connector abstractions.

![critical](https://www.gstatic.com/codereviewagent/critical.svg)

There is a critical race condition in `store_tensor`. The `allocate` method (line 241) returns an address for a slot that is not yet pinned. If another thread calls `allocate` and the ring buffer wraps around, it could evict this newly allocated slot before the `copy_` operation (line 253) finishes, as the copy happens outside the lock and without an active pin. This will lead to silent data corruption or crashes. You must pin the slot immediately after allocation and unpin it only after the copy is complete.

![critical](https://www.gstatic.com/codereviewagent/critical.svg)

The use of `ctypes.from_address` and `torch.frombuffer` is only valid for host (CPU) memory. If `EncoderCacheTransferBuffer` is initialized with `device="cuda"` (as supported by the constructor at line 66), this code will attempt to access GPU memory addresses via the host-side buffer protocol, which will result in a segmentation fault or undefined behavior. If GPU support is intended, you should use tensor slicing and views instead of `ctypes` for the copy operation.

- gemini-code-assist[bot] · comment · 2026-04-23T09:25:36Z · [source](https://github.com/vllm-project/vllm/pull/40695#discussion_r3129734981)

File: `vllm/distributed/ec_transfer/ec_connector/mooncake_connector.py` · line 1111

![high](https://www.gstatic.com/codereviewagent/high-priority.svg)

In `zmq.asyncio`, `sock.recv()` does not always respect the `RCVTIMEO` socket option when used as an awaitable. If the producer becomes unresponsive or a network partition occurs, this `await` could hang indefinitely, blocking the entire `receiver_loop` thread and preventing any further transfers. It is highly recommended to use `asyncio.wait_for(sock.recv(), timeout=...)` to ensure the timeout is strictly enforced at the event loop level.
