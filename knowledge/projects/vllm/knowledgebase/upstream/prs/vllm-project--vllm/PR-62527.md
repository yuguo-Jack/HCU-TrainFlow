# [ROCm][Bugfix] Skip AITER unquantized MoE for hidden sizes not divisible

[Upstream PR](https://github.com/vllm-project/vllm/pull/62527) · state: open · merged: False

## Original PR description

## Overview

Fall back from AITER to Triton for unquantized MoE, instead of crashing at weight load or at runtime. Fixes the two MI355 "Language Models (Hybrid)" failures in AITER-ON build https://buildkite.com/vllm/amd-ci/builds/13642 (`tiny-random/qwen3-next-moe`, hidden size 8). The MI300 torchrun failure in that build (`240 % 32`) is already fixed on main by #55368.

## Claims

- `tiny-random/qwen3-next-moe` runs with `VLLM_ROCM_USE_AITER=1`. Before, weight loading failed with `AssertionError: 8 % 32 == 8` in `aiter.ops.shuffle.shuffle_weight`.
- Hidden sizes that are multiples of 64 but not 128 (e.g. 2880) no longer hit CK's `device_gemm ... does not support this GEMM problem` at some batch sizes.
- No change for hidden sizes divisible by 128: AITER is still selected.

## Validation

MI300X (gfx942), AITER 0.1.25, torch 2.12.0+rocm10.0.0:

|---|---|
| `VLLM_ROCM_USE_AITER=1 pytest tests/models/language/generation/test_gdn_sleep_wake.py` | main: `8 % 32` assert; this PR: pass |
| `VLLM_ROCM_USE_AITER=1 pytest tests/models/language/generation/test_hybrid.py -m hybrid_model -k qwen3-next-moe` | pass (logprobs vs HF) |
| `pytest tests/kernels/moe/test_rocm_aiter_moe.py -k hidden_rule_matches_kernel` | 4 passed; `[192]` and `[2880]` fail without the fix |
| `pytest tests/kernels/moe/test_unquantized_backend_selection.py tests/kernels/moe/test_rocm_aiter_moe.py tests/rocm/test_moe_padding.py tests/rocm/test_moe_weight_replay.py` | 114 passed, 5 skipped |
| `VLLM_ROCM_USE_AITER=1 VLLM_ROCM_USE_AITER_MOE=1 pytest tests/kernels/moe/test_modular_kernel_combinations.py tests/kernels/moe/test_moe_layer.py -k aiter` | 44 passed, 10 skipped |
| `VLLM_ROCM_USE_AITER=1 TP_SIZE=4 torchrun --nproc-per-node=4 tests/distributed/test_torchrun_example_moe.py`, plus the PP2/TP2, DP4/EP and TP2/DP2/EP variants | pass, still on `AiterUnquantizedExperts` |

No model eval: the selected backend is unchanged when the hidden size is divisible by 128, and the affected shapes failed to run before.

## Details

- Root cause: `AiterUnquantizedExperts` had no shape check, so the oracle chose it for any hidden size. The weight pre-shuffle needs hidden % 32, and the CK 2-stage kernels tile the hidden dim up to 128 wide depending on `inter_dim` and `block_m`. All 487 bf16 rows in AITER's tuned and untuned MoE configs have hidden % 128 == 0.
- Fix: override `_supports_shape`. The oracle then falls back to Triton, with a warning when AITER is enabled via env; `--moe-backend aiter` raises at init instead. FP8 and MXFP4 AITER experts are unchanged.
- Tests: the new kernel test checks the rule against the real CK kernel for intermediate sizes 64 and 256 at 1024/2560/5120 tokens. `test_select_rocm_aiter_backend` now covers hidden 128 (AITER) and 8 (Triton); it previously relied on the default hidden size of 1.
- Limitation: validated on gfx942 only. gfx950's CK dispatch also uses 128-wide hidden tiles, but this hasn't been run on MI355.
- Not a duplicate: no open PR gates unquantized AITER MoE on hidden size, and #55368 pads only the intermediate size. #62092 adds a similar gate for `AiterFp8BlockExperts` and also edits `test_select_rocm_aiter_backend`, so whichever merges second needs a small rebase.
