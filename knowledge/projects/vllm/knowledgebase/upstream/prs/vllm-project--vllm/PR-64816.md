# [Perf][DSv4.1] Vectorize first-layer HC expansion copy

[Upstream PR](https://github.com/vllm-project/vllm/pull/64816) · state: closed · merged: True

## Original PR description

## Purpose

DeepSeek-V4.1's first decoder layer builds its `hc_mult` residual streams with `x.unsqueeze(1).expand(-1, hc_mult, -1).contiguous()`. This replaces it with `hc_expand`, a small Triton copy that reads each input element once and stores it to every stream. The output is the same contiguous `[M, hc_mult, H]` tensor, bit for bit.

The kernel lives in the DeepSeek-V4.1 mHC ops (`vllm/models/deepseek_v41/nvidia/ops/mhc.py`) and is called directly; DSv4.1 does not run under `torch.compile`, so no custom op is registered. Shared mHC kernels are unchanged.

## Results

GB300, DeepSeek-V4.1-Flash, TP1 / DP2 / EP2, DSpark K=5, FlashInfer autotune on. Full model-forward latency (target + DSpark), FI → HC → FI per shape, 3 samples × 5 iterations, 5 s warmup.

| Tokens / rank | Main | This PR | Reduction | Main drift |
| --- | ---: | ---: | ---: | ---: |
| 8192 | 84.755 ms | 84.214 ms | 0.638% | +0.188% |
| 32768 | 292.447 ms | 291.563 ms | 0.302% | +0.276% |

- Hidden states and draft tokens are bitwise identical to main on both ranks.
- A single sequence; earlier prototype rounds gave 0.38% / 0.32% at 32K and no gain at 8K, so only the 32K gain is claimed.
- This revision moves the kernel into DeepSeek-V4.1 with the same indexing and launch. Re-checked against the measured commit (`be1a44dee6`) on 6 decode/prefill shapes, old → new → old in fresh processes: outputs bitwise identical, latency equal or up to 0.3% faster (within run-to-run drift).
- Copy alone at `[32768, 5120]`, `hc_mult=4`, BF16: 1321 → 241 µs (CUPTI, cold L2). PTX uses `ld.global.v4.b32` / `st.global.v4.b32`.

GSM8K (1319 questions, 5-shot, greedy, max 1024 tokens, same FI tactics):

| Concurrency | Main | This PR |
| --- | ---: | ---: |
| 1 | 1192 (90.372%) | 1192 (90.372%), all responses and token counts identical |
| 32 | 1205 (91.357%) | 1198 (90.826%) |

C32 batches are dynamic and main itself is not output-stable there (two main runs flip 31 questions each way), so equal C32 accuracy is not claimed. 60 passkey cases at 8K/16K/32K match main's full responses and token counts.
