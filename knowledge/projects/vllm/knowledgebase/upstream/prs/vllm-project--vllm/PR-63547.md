# [ROCm][MiniMax] Add MiniMax-M3.1 AMD compatibility via MXFP4 experts and FP8 KV

[Upstream PR](https://github.com/vllm-project/vllm/pull/63547) · state: open · merged: False

## Original PR description

## Summary
- Add an AMD MiniMax-M3.1 compatibility path modeled on SGLang: consume the official `MiniMaxAI/MiniMax-M3.1-Flash` NVFP4 checkpoint, requantize routed experts NVFP4→MXFP4 at load (`--quantization-config.moe mxfp4`), and keep the supported ROCm FP8 MSA/indexer caches.
- Wire nested DSpark from `{model}/dspark` (`DSparkMiniMaxDraftModel`), skip draft tensors on the target load, route all 60 MSA layers, and fail early with a precise recipe if NVFP4 KV/indexer is requested on ROCm.
- Update the public MI355 recipe so it no longer claims native NVFP4 KV + MXFP8 experts. Default AMD serving is MXFP4 experts + FP8 KV/indexer; monokernel and DBO stay off until proven on the all-sparse M3.1 layout.

**Served precision to claim:** official NVFP4 checkpoint requantized to MXFP4 routed experts with FP8 main KV and FP8 indexer. This is not native NVFP4 serving.

## Reproducibility
```bash
# image: vllm/vllm-openai-rocm:nightly (or the branch built from this PR)
# checkpoint: MiniMaxAI/MiniMax-M3.1-Flash
bash examples/online_serving/minimax_m31_flash_rocm.sh
```

TP4 MI350/MI355 AgentX sweep wrapper:
```bash
ACCOUNT=amd-agentx QOS=amd-agentx-4-qos PARTITION=amd-spur \
  bash examples/online_serving/minimax_m31_flash_rocm_qos.sh submit
```

## Tests
- CPU: `tests/models/test_minimax_m31_amd_compat.py` — all-sparse MSA config, nested DSpark path/architecture, weight mapper, NVFP4→MXFP4 layout (scales, packing, AITER padding, gate/up split), NVFP4 recipe guards.
- ROCm dispatch (Unix/vLLM env): `tests/kernels/attention/test_minimax_m31_rocm_dispatch.py` — reject NVFP4 KV/indexer; FP8 is not treated as NVFP4.

Local result from this change: 16 CPU tests passed. The ROCm dispatch module is skipped on Windows (`uvloop`). AgentX TP4 QOS (c1/c4/c8/c16/c32/c64), accuracy vs a non-requantized reference, long-context, and memory sweeps were not run from this workstation (no MI350X/MI355X allocation / `srun`). The scripts above are the exact commands for that QOS job.
