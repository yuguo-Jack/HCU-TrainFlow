# [CPU] Add GELU-tanh MoE, FP8 checkpoint support and Gemma-4 INT8 TP=4 padding

[Upstream PR](https://github.com/vllm-project/vllm/pull/62016) · state: closed · merged: True

## Original PR description

## Summary
Two independent CPU-backend changes:

- **GELU-tanh MoE activation:** `amd/gemma-4-26B-A4B-it-w8a8-llmcompressor` uses `gelu_pytorch_tanh` in its MoE blocks, but every SGL-kernel-backed CPU MoE path (INT8/INT4/FP8 W8A8, FP8/MXFP4 W8A16) only supported SiLU. Partially syncs the vendored SGLang CPU kernels to get the generic `CPUActMethod` dispatch (4 files with unrelated upstream changes are left unsynced, noted in `common.h`), adds an AVX512 `gelu_tanh_and_mul` primitive, and threads it through all 5 `CPUQuantMethod` kernels, the `fused_experts_cpu` op schema, and each `CPUExperts*` class. `_supports_activation` of each class now matches what its kernel implements (`CPUExpertsFp8`/`CPUExpertsMxfp4` also declare exact GELU), and the activation is passed to `fused_experts_cpu` as a `CPUActMethod` IntEnum (mapped explicitly from `MoEActivation`) instead of a string, so clamped swiglu (`SWIGLUOAI`) is selected explicitly rather than inferred from alpha/limit. DeepSeek-style shared-expert kernels are untouched. Also makes this model work at TP=4: the MoE intermediate size 704 shards to 176 per rank, which the INT8 kernel rejected (it needs a multiple of 32), so `CPUExpertsInt8` now zero-pads the intermediate dim (weights and w13 scale) before prepacking, reusing the padding the unquantized CPU experts already do.
- **FP8 checkpoints on CPU:** `static_scaled_fp8_quant` and `dynamic_per_token_scaled_fp8_quant` were placeholders that raised on CPU, so any path calling `ops.scaled_fp8_quant` failed (load-time requantization of fused modules, online FP8 quantization, Torch FP8 linear fallbacks). Implements both with AVX-512 (e4m3fn/e5m2, 0D/1D/2D static scales, per-token dynamic scales with `scale_ub`), and adds `CPUFp8ChannelWiseScaledMMLinearKernel` so per-channel FP8 weights (e.g. `*-FP8-dynamic` checkpoints) run through the SGL W8A16 kernel.

## Changes
- GELU-tanh MoE: `csrc/cpu/sgl-kernels/{common,gemm,moe,moe_fp8,moe_fp8_w8a8,moe_int4,moe_int8,vec}.*`, `csrc/cpu/torch_bindings.cpp`, `vllm/_custom_ops.py`, `vllm/model_executor/layers/fused_moe/experts/cpu_moe.py`, `tests/kernels/moe/test_cpu_quant_fused_moe.py`, `tests/kernels/moe/test_cpu_fused_moe.py` (TP=4 padding test).
- FP8 on CPU: `csrc/cpu/fp8_quant.cpp`, `cmake/cpu_extension.cmake`, `csrc/cpu/torch_bindings.cpp`, `vllm/model_executor/kernels/linear/{__init__,scaled_mm/cpu}.py`, `tests/kernels/quantization/test_cpu_fp8_{quant,scaled_mm}.py`, `.buildkite/hardware_tests/cpu.yaml` (runs the new FP8 quant tests in the CPU kernel job).

## Test plan
- [x] Rebuilt at the PR head and ran `tests/kernels/moe/test_cpu_fused_moe.py`, `tests/kernels/moe/test_cpu_quant_fused_moe.py`, `tests/kernels/quantization/test_cpu_fp8_quant.py` and `tests/kernels/quantization/test_cpu_fp8_scaled_mm.py`: 666 passed, 318 skipped, 0 failed.
- [x] GELU-tanh: new tests for all 5 quant configs against a plain-PyTorch reference. End-to-end on `amd/gemma-4-26B-A4B-it-w8a8-llmcompressor`: the INT8 CPU MoE backend is selected and a `temperature=0.0` chat prompt answers correctly ("The capital of France is Paris."). At TP=4 (previously `No Int8 MoE backend supports the deployment configuration`) the same model selects the CPU INT8 MoE backend and answers chat prompts correctly (`The capital of France is Paris.`, `42`); the new padding test compares against the unpadded reference for an intermediate size of 176 and fails (`invalid weight input features 176`) with the padding disabled.
- [x] FP8 on CPU: full GSM8K (1319 questions) on RedHatAI `Meta-Llama-3.1-8B-Instruct-FP8`, `Meta-Llama-3.1-8B-Instruct-FP8-dynamic` and `Qwen3-4B-FP8-dynamic`. AVX-512 quant ops vs. the scalar loops on a Xeon 6972P (32 threads), 2048x4096 bf16: static 433 -> 123 us, per-token 772 -> 177 us. The e4m3fn conversion is bit-identical to `c10::Float8_e4m3fn` over every bf16/fp16 bit pattern and 4M random fp32 values.
