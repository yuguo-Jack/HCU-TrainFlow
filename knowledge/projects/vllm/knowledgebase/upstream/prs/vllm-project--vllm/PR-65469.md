# fixing up the MCP Tool discovery

[Upstream PR](https://github.com/vllm-project/vllm/pull/65469) · state: open · merged: False

## Original PR description



## Overview

Fixes [[#65074](https://github.com/vllm-project/vllm/issues/65074)](https://github.com/vllm-project/vllm/issues/65074).

`MCPToolServer` previously retrieved only the first page of tools from an MCP server, ignoring the `next_cursor` returned by the server. This change adds cursor-based pagination to ensure all available MCP tools are discovered and advertised correctly.

## Claims

* **Complete tool discovery:** Fetches all pages of tools exposed by an MCP server instead of stopping after the first response.
* **Cursor-based pagination:** Continues requesting subsequent pages using the `next_cursor` provided by the MCP server.
* **Backward compatibility:** Preserves existing single-page discovery behavior and tool filtering.
* **Improved reliability:** Handles multi-page tool discovery while preventing incomplete tool registration.
* **Regression coverage:** Adds tests for single-page, multi-page, empty responses, filtering, and pagination edge cases.

## Validation

The issue was reproduced using a real local MCP SSE server exposing two tools across two pages.

**Before the fix:**

```text
advertised: ['first_page']
```

The second tool was available through the MCP session but was not advertised by `MCPToolServer`.

Manually following the returned cursor successfully retrieved and executed `second_page`.

**Expected behavior after the fix:**

```text
advertised: ['first_page', 'second_page']
```

## Details

### Root Cause

The `list_server_and_tools()` function in `vllm/entrypoints/mcp/tool_server.py` called `session.list_tools()` only once.

MCP supports cursor-based pagination through the `next_cursor` field in `ListToolsResult`. When a server exposes tools across multiple pages, clients must continue requesting subsequent pages until no cursor is returned.

Because vLLM did not follow this cursor, tools on subsequent pages were silently omitted from the advertised tool namespace.

### Implementation

The tool discovery logic now needs to:

1. Request the initial page of tools.
2. Collect the returned tools.
3. Check the `next_cursor` field.
4. Request subsequent pages using `PaginatedRequestParams`.
5. Continue until the server returns no further cursor.
6. Return the complete collection while preserving existing filtering and registration behavior.

This keeps the change focused on MCP tool discovery without modifying the underlying MCP protocol or unrelated functionality.

### Impact

MCP servers exposing tools across multiple pages can now have their complete tool namespace discovered by vLLM.

Previously, tools beyond the first page were unavailable to the model despite being registered and callable on the MCP server.

This fix ensures that tool discovery correctly handles both single-page and multi-page MCP responses.
