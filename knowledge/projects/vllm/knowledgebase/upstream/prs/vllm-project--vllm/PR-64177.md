# [Bugfix] Omit null `annotations` and `usage.prompt_tokens_details` in chat completions

[Upstream PR](https://github.com/vllm-project/vllm/pull/64177) · state: closed · merged: True

## Original PR description

## Overview

On a default server, a non-streaming chat completion returns `"annotations": null` in each message and `"prompt_tokens_details": null` in `usage`. The OpenAI spec makes both fields optional but not nullable, so strict schema validators reject the reply. This PR leaves both keys out when they are `None`. It also types `annotations` as a list, as the spec and the OpenAI SDK do. Fixes vllm-project/vllm issue 61425.

Another PR, #61431, which fixes the same issue, has had no activity for two weeks.

## Claims

- Non-streaming chat completions no longer send `annotations: null` or `usage.prompt_tokens_details: null`. A field that has a value is still sent.
- `ChatMessage.annotations` is now `list[OpenAIAnnotation] | None`, the same as the OpenAI spec and SDK. Before, a real value could not be sent in the right shape.
- `/v1/completions`, and any other response that uses `UsageInfo`, also stops sending `prompt_tokens_details: null`.

## Details

Root cause: the non-streaming chat route returns `JSONResponse(content=result.model_dump())` (`chat_completion/api_router.py`). A plain `model_dump()` writes every `None` field as `null`.

- `ChatMessage.annotations` defaults to `None`, and nothing in chat completions sets it. It was also typed as one `Annotation`, but the spec and the SDK use a list.
- `UsageInfo.prompt_tokens_details` is `None` whenever `--enable-prompt-tokens-details` is off.

`ChatMessage._serialize` drops an empty `tool_calls`, but nothing dropped these two fields. `exclude_unset=True` would not help either. `serving.py` assigns `usage.prompt_tokens_details` after it builds `UsageInfo`, so the field counts as set even when it is `None`.

Spec (openai-openapi `openapi.yaml` 2.3.0): `ChatCompletionResponseMessage.annotations` is `type: array`, and `CompletionUsage.prompt_tokens_details` is `type: object`. Both are optional and not nullable. `refusal`, `audio` and `function_call` are nullable, so they stay as they are.

Fix: `Field(default=None, exclude_if=lambda value: value is None)` on the two fields. vLLM already uses this pattern for `ResponsesResponse.metrics` (`responses/protocol.py`). It applies to both `model_dump()` and `model_dump_json()`, so every route that dumps these models gets the fix. `exclude_if` needs pydantic 2.11 or later, and vLLM requires 2.12 or later. The fields stay on the models, so code that reads `usage.prompt_tokens_details` as an attribute (the Anthropic and Cohere layers) does not change.

Options I did not choose:

- `model_dump(exclude_none=True)` in the router. It also drops `content: null` and `logprobs: null`, and the spec requires those keys. It would also fix only one router.
- `[]` and `{}` as defaults. `PromptTokenUsageInfo()` dumps `cached_tokens: null`, which the spec does not allow either. An empty details object would also claim details that `--enable-prompt-tokens-details` is meant to turn on.

Points for review:

- `usage.completion_tokens_details` is still `null`, and the spec has the same rule for it. I left it out because the issue does not ask for it. Also, `test_streaming_reasoning_usage_counts_across_deltas` in `test_serving_chat.py` asserts `model_dump()["completion_tokens_details"] == expected_details`, where `expected_details` is `None` when reasoning details are off. The same change on that field makes this test fail with `KeyError`. A maintainer should decide whether that test should change.
- Typing `annotations` as a list is a small break for outside Python code that passes one `Annotation` object to `ChatMessage`. Nothing in `vllm/` sets this field, and that input never gave a reply that the spec or the SDK accepts.
- The `UsageInfo` change also removes `prompt_tokens_details: null` from completions, pooling, scoring and transcription responses.
- Sample outputs in `docs/models/pooling_models/classify.md`, `docs/models/pooling_models/embed.md` and `examples/features/openai_batch/README.md` still show `"prompt_tokens_details": null`. They are old captured outputs, and I left them unchanged.
- The served `/openapi.json` still marks both fields as nullable, because pydantic does not put `exclude_if` into the schema.
- With `--enable-prompt-tokens-details`, the details object still has vLLM-only keys set to `null` (for example `multimodal_tokens`). That is outside this fix.
