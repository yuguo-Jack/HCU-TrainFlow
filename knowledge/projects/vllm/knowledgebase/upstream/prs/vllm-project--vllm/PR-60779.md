# [Perf][MoE] Avoid GPU synchronization in expert ID lookups

[Upstream PR](https://github.com/vllm-project/vllm/pull/60779) · state: open · merged: False

## Original PR description



## Overview

Part of #60778 (bottleneck 1: GPU scalar reads during expert ID mapping).

During layerwise weight reloading (`load_weights`, e.g. RL weight updates for DeepSeek V4 Flash), the host-side expert ID queries in `ExpertMapManager` (`map_global_to_local`, `is_local_expert`, `get_local_expert_ids`, `get_compressed_map_string`) read scalars from the GPU-resident `_expert_map` tensor via `expert_map[global_id].item()`. Each lookup issues a D2H copy and a CUDA stream synchronization. In the profiled `load_weights` invocation this amounts to 3,048 D2H transfers and 3,048 stream synchronizations, costing 959.661 ms of CPU time (~50% of the window), of which 870.633 ms is host waiting in stream synchronization — while the corresponding D2H transfers take only 7.177 ms of GPU time.

This PR caches a host-side copy of the expert map (`_expert_map_cpu`, a Python list) and serves all host-side lookups from it:

- `_expert_map_cpu` is rebuilt alongside `_expert_map` in `_calculate_expert_maps()`, the single place where the map is created or recalculated (including EPLB-driven `update()`), so the two always stay in sync.
- GPU-side consumers of `_expert_map` are untouched.
- The cost is one extra `.cpu().tolist()` per map (re)computation, amortized across all subsequent lookups.

## Claims

Measured on the profiled second `load_weights` call reported in #60778 (DeepSeek V4 Flash, NVIDIA H200, world size 4, TP/EP = 4/4, MXFP4 → Marlin):

- Expert ID mapping CPU duration: **959.661 ms → 0.287 ms**
- D2H transfers inside expert ID lookups: **3,048 → 0**
- CUDA stream synchronizations inside expert ID lookups: **3,048 → 0**
- Lookup count is unchanged (3,048) and returned IDs are unchanged (same underlying map) — no functional change.

## Validation

- Added `tests/distributed/test_expert_placement.py::test_expert_map_manager_lookups_follow_ep_updates`, which verifies that `map_global_to_local`, `is_local_expert`, `get_local_expert_ids`, and `get_compressed_map_string` return the expected IDs/locality/map-string on the initial EP configuration, and remain in sync after `ExpertMapManager.update()` reconfigures placement (EP rank change, then EP disabled): `pytest tests/distributed/test_expert_placement.py::test_expert_map_manager_lookups_follow_ep_updates`.
- The performance numbers above come from the profiling experiment in #60778 (repeated weight updates for DeepSeek V4 Flash on H200). Lookup behavior is otherwise unchanged, so existing MoE/EPLB test coverage continues to apply.

## Details

- `_expert_map_cpu` is `None` iff `_expert_map` is `None`, preserving the existing identity-mapping behavior when EP is disabled.
- `map_global_to_local` still returns a plain Python `int` (previously via `.item()`); `is_local_expert` now returns a Python `bool` instead of a 0-dim tensor, which is equivalent in boolean contexts.
- Combined with the other optimizations tracked in #60778, the profiled `load_weights` window drops from 1,923.691 ms to 276.823 ms; this PR contributes the expert-ID-mapping portion.
