# [Test] Let simulate_tool_streaming stream explicit per-chunk token ids

[Upstream PR](https://github.com/vllm-project/vllm/pull/65362) · state: open · merged: False

## Original PR description

## Overview

Test-only change. `simulate_tool_streaming()` gains an opt-in
`delta_token_ids_per_chunk` parameter, so tests can stream explicit per-chunk
token ids through the shared helper. `test_granite.py` and `test_inkling.py`
migrate their `_stream()` loops to it. Fixes #65328.

## Claims

- `simulate_tool_streaming(parser, request, chunks,
  delta_token_ids_per_chunk=...)` streams explicit per-chunk delta ids, one
  entry per chunk. Example: the full per-token ids serving sends. This mirrors
  the existing escape hatch of `simulate_reasoning_streaming()`.
- Default behavior is unchanged. Without the parameter, the helper synthesizes
  marker-only ids from the chunk text exactly as before. None of the eight
  existing callers change.
- `test_granite.py` and `test_inkling.py` now stream through the helper with
  explicit ids. Their old `_stream()` loops already built token-batched ids
  plus a final `finish_streaming()`, so the call sequence is unchanged.

## Details

The synthesized ids are marker-only, deduplicated, and carry no ids for
ordinary text. When a delta mixes a marker with ordinary text, its ids are
not a tokenization of the delta text, and serving never sends ids like that.

The production bridge (`ParserEngineToolAdapter.extract_tool_calls_streaming`)
passes `delta_token_ids` through unchanged. With `--stream-interval N > 1`,
each delta carries a batch of N full per-token ids. #45256 is the bug class
that only shows up under that batching.

Serving keeps one rule: `delta_token_ids` is a tokenization of `delta_text`.
The helper cannot keep that rule from text alone. Once any ids arrive, the
engine trusts the token ids and stops matching their text.

On the #64012 input family, 134/296 chunk layouts fail under the synthesized
ids. Full per-token ids parse all 296.

The text-only interface also cannot feed token batches, so the suite works
around it by hand:

- test_granite.py, test_inkling.py, and llama_json build their own
  `delta_token_ids` and call `extract_tool_calls_streaming` in a loop. The
  first two migrate here.
- gemma4's token-batched tests (including the detokenizer-holdback ones) and
  `replay_harness.py` go through `parse_delta()` instead, which already takes
  ids.
- The same marker-only id construction is also copy-pasted into two `_stream*`
  helpers in `test_parser_engine.py` (both call `parse_delta()`).

Design:

- The parameter mirrors the reasoning-side hatch. When explicit ids are
  given, the helper skips the token-id map, so the two helpers stay symmetric.
- Encoding the chunks inside the helper does not work for current callers.
  Many pass Mock tokenizers whose `encode()` returns a constant, so the
  per-chunk ids have to come from the caller.
- The default synthesis stays unchanged, because the eight existing test
  files that call the helper rely on the current token-id coverage. The new
  tests do not encode the default mode's divergence into assertions: they
  assert the explicit mode's correctness, and mode agreement on green layouts
  only.

granite and inkling migrate here. llama_json's `_stream()` is the same kind
of loop, so it can follow the same way. The `parse_delta()`-based feeders use
a different API and stay as they are.
