# [Bugfix][MoE] Use the prepared b12x API for compact N64 W4A8 MXFP4 experts

[Upstream PR](https://github.com/vllm-project/vllm/pull/65233) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

With `--moe-backend b12x`, W4A8 MXFP4 MoE layers with a per-rank intermediate size of 64 modulo 128 stop during b12x warmup:

```
RuntimeError: compact W4A8 execution requires its prepared native launchers
```

This PR uses the prepared execution API of FlashInfer for these layers. Other layers keep the current path.

## Claims

- W4A8 MXFP4 layers with an intermediate size of 64 modulo 128 (for example 192) run with the b12x backend.
- Other layers do not change. This includes W4A8 MXFP4 layers with an intermediate size that is a multiple of 128, NVFP4, W4A16 and the block codecs.
- No new configuration is necessary. The fix uses `flashinfer-python==0.7.2.post1`, which vLLM pins.

## Validation

New GPU test: `test_b12x_mxfp4_w4a8_compact_n64_runs` in `tests/kernels/moe/test_b12x.py`. It runs a W4A8 MXFP4 layer with an intermediate size of 192 through `B12xExperts`, warmup and execution. It compares the output with the torch reference.

```
pytest tests/kernels/moe/test_b12x.py -k compact_n64
```

Results on DGX Spark (GB10, SM121), `flashinfer-python==0.7.2.post1`:

| Run | Result |
| --- | --- |
| New test on `main` | Fails with `RuntimeError: compact W4A8 execution requires its prepared native launchers` |
| New test on this branch | Passes. Cosine similarity with the torch reference is above 0.99, before and after a weight reload |
| All of `tests/kernels/moe/test_b12x.py` | No other test changes status between `main` and this branch |

The test runs warmup for 1, 16 and 64 tokens and then `apply`. It also does a weight reload from new copies of the weights, because the first load repacks the weights in place.

`pre-commit` passes on the changed files.

## Details

Root cause: FlashInfer repacks W4A8 MXFP4 weights with an intermediate size of 64 modulo 128 to compact N64 tiles. For small batches, FlashInfer runs these tiles with compact micro kernels. Only the prepared execution API (`fused_moe.plan_execution` with `b12x.preparation.PreparationSession`) makes the launchers for these kernels. The current `plan_weights(quant_modes=...)` and `plan`/`bind` path cannot make them, so `b12x_moe_fp4` raises the error.

Change:
- `B12xExperts._prepare_experts` prepares these layers with `plan_weights(PackedSource, ActivationSpec, MoEGeometry)` and `PackedWeights`.
- `_plan` makes prepared execution plans for power-of-two token capacities up to `max_num_tokens`. It makes them once, before CUDA graph capture.
- `vllm/utils/b12x.py` gets `get_b12x_preparation()`, next to the other b12x accessors.

Limitations:
- The code reads `representation.value.n64_repack` from the prepared experts. This attribute is not part of the public FlashInfer API. If the layer is not repacked, the code keeps the current path.
- If data parallelism is used without expert parallelism, the experts can get more tokens than `max_num_tokens`. For each such token count, the code makes one exact plan. The current path also makes one plan for each token count.
- A possible follow-up: use the exact warmup sizes of FlashInfer (`warmup_token_counts`) in one plan, instead of power-of-two capacities.
- #64765 also changes `vllm/utils/b12x.py` and `docs/features/quantization/b12x.md`. The two changes do not conflict in function. The merge conflict, if any, is small.
