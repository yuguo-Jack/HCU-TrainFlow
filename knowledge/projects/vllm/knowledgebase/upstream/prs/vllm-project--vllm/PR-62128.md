# [Kernel] Use 16-row tiles for SM89 int8 CUTLASS GEMM at M in (16, 64] for small N

[Upstream PR](https://github.com/vllm-project/vllm/pull/62128) · state: open · merged: False

## Original PR description



## Overview

Fixes #56924. On SM89 (Ada), the int8 W8A8 CUTLASS GEMM gets ~1.5x slower when M goes from 16 to 17, and again from 32 to 33. The dispatch moves from 16-row tiles (`sm89_int8_config_M16`) to 32-row tiles at M=17 and 64-row tiles at M=33. For the small-N layers of models like Qwen3-1.7B (N=2048, K=2048) that halves or quarters the number of CTAs (32 CTAs with 32x64 tiles on a 128-SM RTX 4090), so most of the GPU sits idle and each CTA does more work.

This PR keeps the existing `sm89_int8_config_M16` config for M in (16, 32] when N <= 4096 and for M in (32, 64] when N <= 2048. No new kernel configs, no new template instantiations beyond what M <= 16 already uses.

## Claims

- On an RTX 4090, the six Qwen3-1.7B int8 shapes from the issue take ~13% less total GEMM time over M = 17–64 (409.5 µs → 355.3 µs summed over 6 shapes x 6 M values). Per layer: q/o_proj 1.32–1.44x (1.09x at M=64), k/v_proj 1.56–1.84x, qkv_proj 1.19–1.23x for M in (16, 32], down_proj 1.25–1.31x for M = 17–48.
- The M=16 → 17 jump is mostly gone: q/o_proj 4.90 → 5.53 µs (was 4.92 → 7.81).
- Results are identical: same max relative error vs an fp64 reference on every shape and M.
- M <= 16, M > 64, and N > 4096 (or N > 2048 for M in (32, 64]) keep the current configs. Only the SM89 int8 path changes.
- One row is slightly slower: down_proj (N=2048, K=6144) at M=64, 16.65 → 17.01 µs (0.98x). I kept a single N rule rather than a special case for one shape.

## Details

- Why these N limits: I also tried the M16 config for every N with M <= 64. It won on the small-N layers but lost badly once the grid needs more than one wave of CTAs (gate_up_proj N=12288: 0.37–0.55x; gate/up_proj N=6144 at M > 32: 0.74–0.80x; qkv_proj N=4096 at M > 32: 0.80–0.93x). The N <= 4096 / N <= 2048 limits keep only the cases that won.
- I also tried new 32-row configs for (32, 64] picked from a standalone CUTLASS sweep (32x64x128, 5 stages). They were faster in the standalone sweep but mostly slower inside vLLM, so they are not in this PR.
- An SM-count rule (use 16-row tiles while ceil(M/16) * ceil(N/64) <= number of SMs) picks exactly the same configs on a 4090 for these shapes. I went with the plain N rule: no device query in the dispatch, and it matches how the other configs in this file branch on `next_pow_2(N)`.
- Measured only on an RTX 4090 (128 SMs). On smaller Ada parts (L4, 58 SMs) the N limits may be too generous; I have not measured that. @AshrithaG, could you time this on your setup?
- No split-K: the c2x scale epilogue does not support it, and the issue asks for a config fix.

I used an AI assistant to help analyze the benchmark sweeps. I wrote the dispatch change and ran all builds, tests, and benchmarks above on an RTX 4090 myself.
