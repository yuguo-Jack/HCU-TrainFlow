# [Kernel] Use 16-row tiles for SM89 int8 CUTLASS GEMM at M in (16, 64] when they don't add waves

[Upstream PR](https://github.com/vllm-project/vllm/pull/62128) · state: open · merged: False

## Original PR description

## Overview

Fixes #56924. On SM89 (Ada), the int8 W8A8 CUTLASS GEMM gets ~1.5x slower when M goes from 16 to 17, and again from 32 to 33. The dispatch moves from 16-row tiles (`sm89_int8_config_M16`) to 32-row tiles at M=17 and 64-row tiles at M=33. For the small-N layers of models like Qwen3-1.7B (N=2048, K=2048) that halves or quarters the number of CTAs (32 CTAs with 32x64 tiles on a 128-SM RTX 4090), so most of the GPU sits idle and each CTA does more work.

This PR uses the existing `sm89_int8_config_M16` config for M in (16, 64] when its 16-row tiles fit in the same number of waves as the current config, or when the current config already needs two or more waves and the 16-row grid adds at most half again as many. The rule reads the SM count once per device. No new kernel configs, no new template instantiations beyond what M <= 16 already uses.

The first version used fixed N limits (N <= 4096 for M in (16, 32], N <= 2048 for M in (32, 64]). @ShikhaPallavi123's run on an RTX 4500 Ada (60 SMs) showed those limits are too generous for smaller Ada parts: down_proj got 35–81% slower. An L4 (58 SMs) shows the same thing (below). The wave rule picks the same configs as before on a 4090 and keeps the current configs where the 16-row tiles would spill into extra waves.

## Claims

- On an RTX 4090 the wave rule makes the same choices as the first version for all six shapes, so these numbers stand. The six Qwen3-1.7B int8 shapes from the issue take ~13% less total GEMM time over M = 17–64 (409.5 µs → 355.3 µs summed over 6 shapes x 6 M values). Per layer: q/o_proj 1.32–1.44x (1.09x at M=64), k/v_proj 1.56–1.84x, qkv_proj 1.19–1.23x for M in (16, 32], down_proj 1.25–1.31x for M = 17–48.
- The M=16 → 17 jump is mostly gone: q/o_proj 4.90 → 5.53 µs (was 4.92 → 7.81).
- Results are identical: same max relative error vs an fp64 reference on every shape and M.
- On an L4 (58 SMs): 836.0 µs → 801.4 µs over M = 17–64, six shapes (4.1% less). Every cell the rule changes is faster (0.59–0.82x of stock); the rest run the stock kernel. The first version on the same L4: 857.8 µs (2.6% more than stock), with down_proj up to 1.75x slower (M = 64).
- On an RTX 4500 Ada (60 SMs), measured by @ShikhaPallavi123 on 8c897b5: total over M = 17–64, six shapes, 626.2 → 602.4 µs (3.8% less; two repeats gave 3.1% and 3.5%). The rule changes only k/v_proj at M 17–48 (0.63–0.72x of stock) and qkv_proj at M 17–32 (~0.80x); o_proj and down_proj stay within 0.98–1.01x of stock. int8 tests: 400 passed, 54 skipped.
- M <= 16, M > 64, and any shape where the 16-row tiles would add waves keep the current configs. Only the SM89 int8 path changes.
- One row on the 4090 is slightly slower: down_proj (N=2048, K=6144) at M=64, 16.65 → 17.01 µs (0.98x). It stays in one wave either way on 128 SMs, so the wave rule keeps it; I didn't add a special case for one shape.

## Details

- Why waves: these M16/M32/M64 configs all run one CTA per SM (61 KB / 51 KB / 80 KB of shared memory against Ada's 100 KB per SM), so time goes roughly with waves × per-CTA time. On 128 SMs, small-N layers stay in one wave with either tile, and the smaller tiles finish sooner. On 58–60 SMs, down_proj at M=17 goes from 1 wave (32 CTAs) to 2 (64 CTAs), which is what showed up as +47% on the 4500 and +41% on the L4. On the 4090 the M16 config for every N also lost exactly where it added waves (gate_up_proj N=12288: 0.37–0.55x; gate/up_proj N=6144 at M > 32: 0.74–0.80x; qkv_proj N=4096 at M > 32: 0.80–0.93x).
- The 1.5x allowance comes from the qkv_proj case (2 → 3 waves on 58–60 SMs, still faster: 0.72–0.82x on the L4 across two runs). It's the one part of the rule fitted to data; the L4 numbers above are the check.
- I also tried new 32-row configs for (32, 64] picked from a standalone CUTLASS sweep (32x64x128, 5 stages). They were faster in the standalone sweep but mostly slower inside vLLM, so they are not in this PR.
- The SM count is cached per device in the dispatch file rather than read through `get_device_attribute()`, which caches only the first attribute it is ever asked for.
- Measured on an RTX 4090 (128 SMs), an L4 (58 SMs) and, by @ShikhaPallavi123, an RTX 4500 Ada (60 SMs). @AshrithaG, a timing run on your setup would still help.
- No split-K: the c2x scale epilogue does not support it, and the issue asks for a config fix.

I used an AI assistant to help analyze the benchmark sweeps. I wrote the dispatch change and ran all builds, tests, and benchmarks above on RTX 4090 and L4 myself.
