# [ROCm][CI] Cache a PR's ROCm base image before it merges with `/amd-ci cache`

[Upstream PR](https://github.com/vllm-project/vllm/pull/65276) · state: open · merged: False

## Original PR description

- `run_ci_command.py`: `/amd-ci cache`, for maintainers with write access, starts a main build of AMD CI that caches the PR's ROCm base image from the stack images its CI built; commenting it again once that passes retries CI's `ROCm base image cache` job, and `/ci run` and `/amd-ci run` replies on such PRs say so
- `build.sh`: `prebuild` copies those images when their key is this merge's and the PR used main's build.sh and bake file, refuses deleted or chmod-ed stack inputs, keeps its own cache ref, and accepts later commits such as merges of main
- `test_run_ci_command.py`, `test_rocm_build.py`, contributing docs

When a PR changes the ROCm stack, main cold-builds it after merge (about 162 minutes for the AITER bump in https://github.com/vllm-project/vllm/pull/63774), and PRs started in that window rebuild the same image or wait for it. With https://github.com/vllm-project/ci-infra/pull/886, the required `ci` pipeline fails such a PR in a `ROCm base image cache` job until `rocm/vllm-ci` has the stack image main will need, and this adds the way to get it there: once the rest of CI is green, a maintainer comments `/amd-ci cache`, which copies the stack the PR's CI already built in minutes, then comments it again to retry that job. Main and other PRs then reuse the image from the first build after merge, nothing new is needed in secrets or settings, and ci-infra#886 has to merge first. The copied images come from PR CI, whose `rocm/vllm-dev` tags and caches every PR can write, so the maintainer's comment is what vouches for them; a bad cached image is undone by bumping `ARG REFRESH` in `Dockerfile.rocm_base`. No open PR does this; the `run_ci_command.py` (67) and `test_rocm_build.py` (22) tests pass, and the prebuild merge was run against real git merges, where it computes the same key as main after the merge.

Rright, that fake was too opaque. It stands in for `GitHubClient.get_file_sha`, which `/amd-ci cache` only calls for `main`: it records main's version of `Dockerfile.rocm_base` and `therock_wheels.py` with each cache build, so if main changes those files later, an earlier cache build no longer counts. The tests didn't need real file IDs, so it returned a constant. In 320854c70 it reads main's IDs from a per-test table and asserts it's only asked about `main`, and `test_a_stack_change_on_main_needs_a_new_cache_build` covers a change on main starting a new cache build.
