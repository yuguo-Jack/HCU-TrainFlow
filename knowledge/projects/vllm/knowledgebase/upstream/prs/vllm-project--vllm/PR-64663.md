# [Doc] Named and required tool_choice need a tool parser

[Upstream PR](https://github.com/vllm-project/vllm/pull/64663) · state: open · merged: False

## Original PR description



## Overview

`docs/features/tool_calling.md` says named function calling works "by default", and that `tool_choice="required"` "is enabled by default and will work with any supported model". Since #30613 (first released in v0.14.0), both return HTTP 400 unless the server has loaded a tool parser, and the server loads one only when `--enable-auto-tool-choice` and `--tool-call-parser` are both set. This PR updates the Named and Required Function Calling sections and the `--enable-auto-tool-choice` entry to match. Related: #55754, #55762.

## Claims

- Named and Required Function Calling state that both flags are needed and that a request without a loaded parser returns HTTP 400. They also note that this check does not reject requests to models in the official Mistral format or to gpt-oss models.
- Both sections now point to [Constrained Decoding Behavior](https://github.com/vllm-project/vllm/blob/6d018934838a0c8c6beed244aa1ca327e1ed7182/docs/features/tool_calling.md#L112-L125) for how far the arguments follow the tool's schema, instead of saying the output strictly matches it. That later section enforces a tool's schema under a structural tag only when the tool sets `strict: true` or the server uses `--tool-strict-level parameter`.
- The `--enable-auto-tool-choice` entry under Automatic Function Calling says that named and required function calling also need it.
- The sentence that alternative decoding backends are on the V1 roadmap is removed; [`docs/usage/v1_guide.md`](https://github.com/vllm-project/vllm/blob/6d018934838a0c8c6beed244aa1ca327e1ed7182/docs/usage/v1_guide.md#L157) lists them as functional.

## Validation

The behaviour described comes from the code at the base commit `6d01893`:

- [`OnlineRenderer.render_chat()`](https://github.com/vllm-project/vllm/blob/6d018934838a0c8c6beed244aa1ca327e1ed7182/vllm/renderers/online_renderer.py#L263-L290): with no tool parser, and neither a Mistral tokenizer nor gpt-oss, `"auto"` fails with `"auto" tool choice requires --enable-auto-tool-choice and --tool-call-parser to be set`, and `"required"` or a named choice fails with `tool_choice=... requires --tool-call-parser to be set`. Both are 400 `BadRequestError`.
- [`ParserManager.get_tool_parser()`](https://github.com/vllm-project/vllm/blob/6d018934838a0c8c6beed244aa1ca327e1ed7182/vllm/parser/parser_manager.py#L33-L35) returns `None` when `enable_auto_tools` is false, so `--tool-call-parser` alone loads no parser. #55754 reproduces this over HTTP with `--tool-call-parser hermes`.
- [`test_tool_choice_validation_without_parser`](https://github.com/vllm-project/vllm/blob/6d018934838a0c8c6beed244aa1ca327e1ed7182/tests/entrypoints/openai/chat_completion/test_serving_chat.py#L2866) covers the case with no parser.

Driving `OnlineRenderer.render_chat()` from the v0.32.0 wheel on CPU, with the Qwen2.5-3B-Instruct tokenizer and no engine, gives the same result. With no tool flags, and with `--tool-call-parser hermes` alone, a request with tools returns 400 for `tool_choice` omitted, `"auto"`, `"required"` and named; with both flags all four are accepted. The check and `get_tool_parser()` are the same in v0.32.0 and at the base commit.

`pre-commit run --files docs/features/tool_calling.md` passes, including `markdownlint-cli2` and `typos`. A local `mkdocs build` did not get past `docs/mkdocs/gen_files/generate_argparse.py`, which imports modules that need the compiled CUDA extensions, so the Read the Docs preview is the render check.

## Details

The 400 is intended. #30613 added it because, without the two flags, these requests "would silently degrade instead of returning a clear error". The docs predate it. Up to v0.11.0 the JSON schema for a named or required call was built in `ChatCompletionRequest.to_sampling_params()` without a parser; #27383 (v0.11.1) moved that into the tool parser.

#55762 proposes loading the configured parser without `--enable-auto-tool-choice` for named and required choices. If it lands, the sentences that name both flags should say that `--tool-call-parser` is enough; that PR does not change the docs. No open PR edits these sections. #60585 adds an Allowed Tools section right after Required Function Calling, next to a line this PR changes, so the second of the two to merge may need a rebase.

This PR leaves out two related points. The error message names only `--tool-call-parser`, but it sits in the validation block that #55762 rewrites. The Responses API does not apply this check (#39221), and the new sentences describe the chat completion API.
