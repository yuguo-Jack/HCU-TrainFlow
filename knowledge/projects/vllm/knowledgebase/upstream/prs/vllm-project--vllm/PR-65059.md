# [Bugfix][Kernel] Only set PDL launch attr for MoE top-k gating on SM90+

[Upstream PR](https://github.com/vllm-project/vllm/pull/65059) · state: closed · merged: True

## Original PR description

## Overview

Fixes #65055. Since #59737, `topkGating` is launched with the PDL attribute on every CUDA arch. Pre-SM90 GPUs cannot use PDL, but stream capture still records the attribute as a programmatic edge in the CUDA graph, and replaying those graphs is slower. This PR sets the attribute only when the device is SM90+. SM90+ keeps the #59737 behaviour; older GPUs launch without the attribute, which measured the same as the v0.32 `<<<>>>` launch. The standalone effect was measured on sm80, sm86 and sm89; end-to-end numbers are A100 only.

## Claims

- 4× A100, TP4 + EP + MTP (our deployment config, private NVFP4 checkpoint of Qwen3.8-Flash-Next; setup below): per-request decode is 6.5–13.6% faster in 17 of 18 prompt × concurrency (1–16) cells, and 2.1% in the 18th. At concurrency 16: prose 74.3 → 80.1 and code 88.7 → 94.8 tok/s, close to the last commit before #59737 (3b05805d4: 81.5 and 95.3, one run).
- Standalone CUDA (no vLLM): the attribute adds one programmatic edge per launch and 0.6–1.1 µs of graph replay per edge on A100 (sm80), RTX A4000 (sm86) and RTX 4090 (sm89), in every round; without the attribute `cudaLaunchKernelEx` matches `<<<>>>`.
- 1× A100, CUDA graph replay of a router GEMM → `topk_softmax` chain: 6.9–9.0% faster for Qwen3.8-Flash-Next, Qwen3-30B-A3B and OLMoE shapes at 1/16/48 tokens, in every round against a no-change rebuild.
- 1× A100 end to end, `vllm bench latency`: batch 1 is 0.7% faster for OLMoE-1B-7B (every round vs a no-change rebuild, 2 of 3 rounds vs the shipped build) and 1.2% faster for Qwen3-30B-A3B-GPTQ-Int4 (every round). Batch 16 is within noise for both.
- No accuracy change: GSM8K 5-shot on Qwen3-30B-A3B-GPTQ-Int4 is 85.90% (base) vs 86.13% (fix). The kernel body is identical.
- SM90+ is unchanged by construction (the same attribute is set as before); not measured.

## Details

- Root cause: on pre-SM90 the attribute does nothing for eager launches, but stream capture records it as a programmatic edge (`cudaGraphGetEdges` counts one per launch on sm80). Each edge adds about 1.1 µs of GPU time per graph replay on A100.
- #59737 first had this host check (uncached); review asked to drop it for consistency with `topk_softplus_sqrt` / `per_token_group_quant` and to avoid `cudaGetDevice` + `call_once` per eager launch. The measurements above are the reason to bring it back. It is cached in a function-local static as in `fused_deepseek_v4_qnorm_rope_kv_insert_kernel.cu` (`numAttrs = (sm_version >= 90) ? 1 : 0`), so eager launches pay nothing per call. This also matches the scope in #59737's own description ("Enable PDL for the consumer on SM90+"). Python launch sites already gate PDL on `current_platform.is_arch_support_pdl()`.
- The static is initialized once per template instantiation, on the device the caller's `DeviceGuard` selects. It assumes all GPUs in a process share the major arch, which holds for vLLM workers (one GPU each); a mismatch would only affect speed, not results.
- The 1-GPU gain (about 1%) matches the GPU-side edge cost. The TP4 + EP + MTP gain does not: at concurrency 16 a decode step goes from about 29.5 to 27.3 ms, while 48 edges × 1.1 µs is about 0.05 ms per forward; we have not located the rest. The TP4 A/B swaps only `_moe_C` (shipped → this diff built from the same source); on one GPU a no-change rebuild is within 0.8% (median) of the shipped build, so we attribute the gain to this diff.
- Other C++ launchers still set the attribute on all archs, for example `topk_softplus_sqrt_kernels.cu` and `per_token_group_quant.cu` (the latter can run on sm89 for FP8). They are left out to keep this fix small enough to cherry-pick; a shared helper can follow if maintainers prefer.
- Not a duplicate: no open issue or PR changes this launch attribute (searched `topkGating PDL`, `topk_softmax PDL`, `59737`). #62912 (open) changes top-k selection in the same file and keeps `config.numAttrs = 1` as context next to this change, so whichever lands second needs a small rebase; it does not touch the attribute.
- Not covered: Hopper/Blackwell (unchanged code path, not measured), sm75 and older, end to end on GPUs other than A100, and a full main build (only `_moe_C` was rebuilt and overlaid on v0.33.0).
- This is a performance regression against v0.32.0; we'd like it cherry-picked into a v0.33.x patch release if one is planned.
- I used AI assistance (Claude) for the investigation, the code and the tests. I reviewed every changed line and ran the tests and GPU checks above.

**Two questions while I had the tree open.**

1. *Coverage.* `cudaLaunchAttributeProgrammaticStreamSerialization` is set at 28 sites in `csrc/`; ten are still unconditional on pre-Hopper, and several of those run per layer on common models: `fused_qknorm_rope_kernel.cu:594`, `quantization/w8a8/fp8/per_token_group_quant.cu:411,456,819`, `dsv3_fused_a_gemm.cu:694`, `moe/topk_softplus_sqrt_kernels.cu:212,692`, `fp32_router_gemm.cu:188`, `kimi_k3/fused_kda_decode_kernel.cu:759`, `kimi_k3/attn_res_kernel.cu:915`, `custom_all_gather_reduce_scatter.cu:63,155`, `beam/allreduce_norm.cu:450`. At ~0.6 µs per edge per replay, each of those still costs what this PR removes for one kernel. Would it be better to land a shared helper (mirroring `enable_pdl` in `moe/grouped_topk_kernels.cu:1303`) and convert the hot per-layer ones in the same PR, or is a follow-up the plan?

2. *`static const bool use_pdl`.* The cache is per template instantiation and captures the device active on first call. `get_device_prop()` is already cached per device, so dropping the `static` only costs a `cudaGetDevice()`, and it avoids the mixed-device footgun.

Happy to rerun this harness on any follow-up patch — the two builds and the script are reproducible here.
