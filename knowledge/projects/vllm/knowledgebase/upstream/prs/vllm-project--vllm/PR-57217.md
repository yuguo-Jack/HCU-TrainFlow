# feat(mla-prefill): let FlashInfer serve (256,256) MLA prefill via backend="auto"

[Upstream PR](https://github.com/vllm-project/vllm/pull/57217) · state: open · merged: False

## Original PR description

## Purpose

Let the FlashInfer MLA prefill backend serve `(head_dim_qk=256, head_dim_vo=256)` by widening
its dimension whitelist and asking FlashInfer for `backend="auto"` instead of pinning
`"cutlass"`.

Today that shape cannot reach this backend at all, and the two reasons are coupled:

1. **`supported_mla_dimensions` lists exactly one entry**, DeepSeek-V3's
   `(qk_nope 128, qk_rope 64, v_head 128)`. `MLAPrefillBackend.supports_mla_dimensions()`
   rejects anything outside a non-empty list, so `FlashInferPrefillBackend` is filtered out
   before backend priority — or an explicit `mla_prefill_backend` override — is consulted.

2. **Both `BatchPrefillWithRaggedKVCacheWrapper` constructions pin `backend="cutlass"`.**
   CUTLASS FMHA's dispatch (`DISPATCH_head_dim` in FlashInfer's `csrc/fmha_cutlass_sm100.cu`)
   accepts exactly `(192,128)`, `(128,128)` and `(64,64)`; `(256,256)` falls through to
   `return false`. Measured on GB300:

   ```
   RuntimeError: Check failed: (dispatched) is false:
   Unsupported head dimensions: head_dim_qk=256, head_dim_vo=256
   ```

   So selecting this backend for a `(256,256)` model today **crashes** rather than running
   slowly.

The two are consistent — the whitelist was drawn around what the pinned CUTLASS backend can
serve — so widening one without unpinning the other just moves the failure later.

`backend="auto"` resolves per shape inside FlashInfer: cuDNN for `(256,256)`, and still CUTLASS
where CUTLASS fits.

### Which models this affects, and how much

Two different `(256,256)` models route very differently, and the distinction decides whether
this is a perf change or purely a correctness/coverage one:

| model | MLA dims | wrapper shape | prefill backend stock vLLM picks |
|---|---|---|---|
| GLM-5.3 (`GlmMoeDsaForCausalLM`) | `(192, 64, 256)` | (256,256) | **TRTLLM_RAGGED** — the selector special-cases exactly this triple, and `TrtllmRaggedPrefillBackend` lists it |
| GLM-5.3-Flash / `Glm5Next` | `(256, 0, 256)` | (256,256) | **FLASH_ATTN** — not special-cased, and TRTLLM_RAGGED's whitelist does not contain it |

So:

- For **`Glm5Next` (256,0,256)** the baseline is FlashAttention, and cuDNN is **~3–4× faster**
  (table below). This is where the PR is a real perf win.
- For **GLM-5.3 (192,64,256)** the baseline is already FlashInfer's trtllm-gen ragged kernel,
  and cuDNN is **roughly at parity** — 0.73–1.16×, winning only at long sequence lengths. For
  this model the PR is a **correctness/coverage fix, not a speedup**.

### Dependency

Requires a FlashInfer carrying <https://github.com/flashinfer-ai/flashinfer/pull/5133>, which
lets `backend="auto"` reach cuDNN on Blackwell. That PR also normalises the cuDNN prefill
wrapper's `qo_indptr` to **token units**, which matters here: this backend passes
`prefill_metadata.query_start_loc`, and the pre-normalisation cuDNN path expected element-unit
offsets. Without that FlashInfer version, `auto` resolves to FA2 — this PR becomes a no-op
rather than a regression.

cuDNN library **≥ 9.24** / frontend **≥ 1.25** is required for bf16; below that FlashInfer's
`_cudnn_supports_direct_seqlens()` is False and `auto` quietly falls back.

## Test Plan

Kernel-level, at the `(256,256)` MLA prefill shape. No end-to-end serving run: GLM-5.3 is
704 GB and the measurement cluster has no vLLM build new enough to contain this file.

- **Hardware:** GB300, cc (10,3), single GPU.
- **Stack:** torch 2.13.0a0, CUDA 13.4, cuDNN frontend 1.29.0 / backend 92600, FlashInfer at the
  PR #5133 branch.
- **Workload:** `head_dim_qk=256`, `head_dim_vo=256`, `num_kv_heads == num_qo_heads`, bf16,
  causal, ragged. Byte-identical q/k/v across routes. Median of 20 iterations after 5 warmup,
  CUDA events. Head counts are per-GPU (GLM-5.3's 64 heads / TP degree).

Routes: `trtllm_ragged` (called exactly as `trtllm_ragged.py` does), `fa2`
(`flash_attn_varlen_func`), `fi_fa2` and `fi_auto` (FlashInfer ragged wrapper).

## Test Result

Times in ms, GB300, bf16. Two independent allocations; every figure below reproduced within
~2%, and the `vs trtllm` column within 0.02–0.07×.

| case | trtllm_ragged | fa2 | fi_fa2 | fi_auto | picks | **vs trtllm** | vs fa2 |
|---|---|---|---|---|---|---|---|
| b1 s4096 h64 | 0.397 | 1.442 | 1.540 | 0.438 | cudnn | **0.91×** | 3.30× |
| b4 s4096 h64 | 1.415 | 5.251 | 5.772 | 1.400 | cudnn | **1.01×** | 3.75× |
| b8 s2048 h64 | 0.832 | 2.772 | 3.033 | 0.846 | cudnn | **0.98×** | 3.27× |
| b1 s16384 h64 | 5.389 | 20.110 | 22.194 | 5.009 | cudnn | **1.08×** | 4.01× |
| b4 s4096 h8 | 0.257 | 0.979 | 0.840 | 0.282 | cudnn | **0.91×** | 3.47× |
| b8 s2048 h8 | 0.142 | 0.448 | 0.455 | 0.195 | cudnn | **0.73×** | 2.30× |
| chunked 1k→8k | 1.259 | 4.851 | 5.251 | 1.215 | cudnn | **1.04×** | 3.99× |
| chunked 2k→16k | 5.157 | 18.651 | 20.580 | 4.545 | cudnn | **1.13×** | 4.10× |

With `backend="cutlass"` (current code) every one of these rows raises the
`Unsupported head dimensions` error quoted above.

Reading:

- Against **FlashAttention**, cuDNN is 2.3–4.1× — this is the gain for `(256,0,256)` models,
  where FA is the baseline.
- Against **trtllm-gen ragged**, cuDNN is 0.73–1.16×, i.e. broadly at parity, ahead only at the
  longest sequences (1.08× at s16384, 1.13× chunked 2k→16k) and behind at small shapes
  (0.73× at b8/s2048/h8). For GLM-5.3, which routes to trtllm-gen, this PR should **not** be
  expected to improve throughput.
- `auto` picks cuDNN on every row; `fa2` and `fi_fa2` agree within ~7%, a control on the FA
  baseline being fair.

### What this does not establish

- **Per-op attention, not end-to-end TTFT.** No serving benchmark was run.
- **The FA baseline is upstream flash-attn 2.7.4, not `vllm-flash-attn`.** The measurement
  environment had no vLLM install and no compiled `vllm_flash_attn`.
- **The chunked `trtllm_ragged` rows are approximate**: `run_prefill_context_chunk` passes
  different `max_kv_len`/`seq_lens` than the single-shot path benchmarked here. The square rows
  are the trustworthy trtllm comparison.
- **Not runtime-validated inside vLLM** — no available container has this file (the MLA prefill
  sub-backend package postdates every vLLM image on the measurement cluster). This is a source
  change justified by kernel-level measurement plus reading the selector. Reviewers with a
  working deployment can validate via `mla_prefill_backend=FLASHINFER`.

### Deliberately not included

The Blackwell MLA prefill priority list is unchanged, so this PR makes FlashInfer *selectable*
for these dims without altering any default. Given the parity result against trtllm-gen,
promoting FlashInfer in that list is **not** justified for GLM-5.3 on this evidence; the
`(256,0,256)` case would be the candidate, and that deserves its own measurement against
`vllm-flash-attn` rather than a proxy.

Correcting the perf claim in the description above — the original version compared against the
wrong baseline, and the corrected numbers weaken the case for GLM-5.3 specifically.

I had taken GLM-5.3's MLA dims from `Glm5NextConfig` defaults (`qk_nope 256, qk_rope 0`). The
actual released GLM-5.3 checkpoint is `GlmMoeDsaForCausalLM` with `qk_nope 192, qk_rope 64,
v_head 256`. The wrapper shape is `(256,256)` either way, so the crash this PR fixes is
unaffected — but the **baseline backend is not**:

`(192, 64, 256)` is exactly the triple the prefill selector special-cases, and
`TrtllmRaggedPrefillBackend.supported_mla_dimensions` lists it — so stock vLLM runs GLM-5.3
prefill on **TRTLLM_RAGGED** (`flashinfer.prefill.trtllm_ragged_attention_deepseek`), not
FlashAttention. vLLM is already using FlashInfer here, via the trtllm-gen kernel.

Measured against that baseline on GB300, cuDNN is **0.73–1.16×** — at parity, ahead only at
long sequences and behind at small shapes. The 3–4× figure I first quoted is real but is
against FlashAttention, which is the baseline for `(256, 0, 256)` models (`Glm5Next`) where
TRTLLM_RAGGED's whitelist does not apply — not for GLM-5.3.

Net: for GLM-5.3 this PR is a **correctness/coverage fix rather than a speedup**; the perf win
applies to the `(256,0,256)` variant. The description has been updated with both baselines and
the full table.
