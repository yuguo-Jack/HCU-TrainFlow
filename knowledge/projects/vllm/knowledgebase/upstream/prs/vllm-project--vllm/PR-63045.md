# [Kimi K3] KDA RecoverSSM: CuTe verify and commit kernels, records outside the KV cache

[Upstream PR](https://github.com/vllm-project/vllm/pull/63045) · state: closed · merged: True

## Original PR description

## Purpose

Make Kimi-K3 KDA RecoverSSM fast on Blackwell and usable with KV connectors.

RecoverSSM (`--use-replayssm` with speculative decoding) verifies a speculative window from one KDA state slot per request and, after sampling, folds the accepted tokens into the state, instead of storing the state after every draft token. With its Triton kernels it was slower per decode step than speculative decoding without it.

**CuTe DSL kernels for SM10x** (`vllm/models/kimi_k3/nvidia/recoverssm/`), used automatically wherever they apply (bfloat16 SSM state and activations, the bounded KDA gate, head_dim 128, at most 7 speculative tokens):

- a tcgen05 verify with the short convolution fused in: warp specialized (bulk-copied activations, TMA state) for the dim-first conv state, and a plain variant for the token-major layout and unaligned rows;
- a state commit that folds every KDA layer in one launch, streaming each head's state through shared memory with bulk copies, including the block-boundary state that prefix caching (align mode) stores.

**Verify records out of the KV cache.** The per-token records (FP32 corrections, keys and raw gates) are scratch space for one step: each verify writes them and the commit after it reads them. They used to be appended to every Mamba page, which grew the page and the attention block size and made KV connectors copy them. Each KDA layer now keeps them in a buffer with one row per schedulable request (`max_num_seqs`), indexed by the request's row in the speculative batch. The Mamba page is the stock conv + SSM state again, so:

- the page and attention block shrink (Kimi-K3 at TP8: 1024 -> 896 tokens, the same as without RecoverSSM);
- KV connectors (P/D disaggregation, KV offloading) transfer a RecoverSSM request's state as usual, and RecoverSSM no longer rejects them;
- the record shape helpers in `mamba_utils.py` are removed.

Also:

- RecoverSSM requires Model Runner V2 with or without prefix caching (only V2 commits the accepted tokens; V1 without prefix caching silently skipped the commit), and rejects `--enable-dbo` (micro-batches would share a layer's record rows);
- the commit context is rebuilt when the KV cache is re-bound.

## Test Plan

```
pytest tests/models/kimi_k3/test_recoverssm_kernels.py   # SM10x
pytest tests/models/kimi_k3/test_kda.py -k recoverssm
pytest tests/models/kimi_k3/test_kda_metadata.py
pytest tests/models/kimi_k3/test_recoverssm_preemption.py   # SM10x, dummy 8-layer Kimi-K3
pytest tests/test_config.py -k "recoverssm or replayssm"
python benchmarks/kernels/benchmark_kimi_k3_kda_recoverssm.py
```

`test_recoverssm_kernels.py` checks the CuTe verify and commit against the Triton ones on padded Mamba page views: windows 2/5/8, 96 and 12 heads, both conv layouts, FP32 and BF16 conv weights, null-slot and `PAD_SLOT_ID` padding, empty requests, misaligned rows and token offsets (plain-kernel and Triton fallbacks), rejected tensors, record rows past the batch left untouched, CUDA graph replay, the commit at 96/12/3 heads, the align-mode commit with block-boundary crossings, and several verify -> sample -> commit steps against stock speculative decoding over 1 + k state slots. `test_recoverssm_preemption.py` runs decode preemption and aborts on the dummy 8-layer Kimi-K3 with RecoverSSM off / Triton / CuTe.

Accuracy, end to end: Kimi-K3 MXFP4 on GB300, DSpark with 4 speculative tokens (probabilistic drafts, real rejection sampling), prefix caching, gsm8k 5-shot: aggregated TP8 + DCP8, and 1P1D disaggregated (NIXL, TP8 + DCP8 on both sides, RecoverSSM on the decode worker only).

Performance, end to end: disaggregated serving with RecoverSSM on the decode worker only, against the same deployment without it (below).

## Test Result

All tests above pass on GB300 (kernels 141, metadata 41, `test_kda.py -k recoverssm` 13, config 7, preemption 3).

The verify kernel of the warp-specialized path dropped the betas at window 8 (7 speculative tokens): fixed, and window 8 is now tested (it fails without the fix).

Accuracy (gsm8k 5-shot, 1319 questions, strict-match):

| | Speculative decoding | RecoverSSM (CuTe) |
|---|---|---|
| gsm8k strict-match | 0.9621 | 0.9613 |
| Mean acceptance length | 3.70 | 3.68 |

1P1D disaggregated (NIXL), RecoverSSM on the decode worker only: gsm8k strict-match 0.9666 ± 0.0049, mean acceptance length 3.6. The prefill worker runs without RecoverSSM and hands its requests' KDA state to the RecoverSSM decode worker through the connector.

The RecoverSSM server uses an 896-token attention block, as the speculative decoding one does (1024 with the records in the Mamba page).

End to end (GB300, Kimi-K3 MXFP4). Disaggregated: 2 prefill workers (TP8, expert parallel) and 1 decode worker (DP16 + EP16), DSpark with 4 speculative tokens. Both runs use synthetic acceptance (mean acceptance length 3.36), so they accept the same number of tokens. The workload is multi-turn agentic trace replay at concurrency 240 for 1 hour. RecoverSSM runs on the decode worker only; everything else is identical.

Decode is far from its KV limit here, so the KV saving does not show up in throughput; it allows more concurrent requests per decode GPU before the cache fills.
