# [Tests][MRV2] Test padded tokens get PAD slots

[Upstream PR](https://github.com/vllm-project/vllm/pull/64726) · state: open · merged: False

## Original PR description



## Overview

Adds a regression test for #36580, which fixed MRV2 slot mapping under CUDA-graph padding but added no test. No open PR adds one.

## Claims

- After a longer batch, the padded slots of a shorter batch must be `PAD_SLOT_ID`. Before #36580 they kept the longer batch's slots, so padding tokens wrote into KV cache in use.
- The new test fails without the fix and passes with it.

## Validation

`pytest tests/v1/worker/test_gpu_block_table.py` on an RTX 3050 Ti Laptop GPU:

| Build | Result |
|---|---|
| main (4b47db92) | 20 passed |
| main with #36580 reverted | 1 failed (the new test), 19 passed |

The revert restores the pre-fix padding start, `positions.shape[0]`. The failure:

```
assert [20, 21, 22, 23, 24, 25, ...] == [20, 21, 22, -1, -1, -1, ...]
At index 3 diff: 23 != -1
```

I also ran the same steps as a script against the actual builds on an A40: 156e3355 (before #36580) gives `[20, ..., 27]`, and 9efc3bdc (#36580) gives `[20, 21, 22, -1, -1, -1, -1, -1]`.

CI runs it in the existing `pytest -v -s v1/worker` step in `.buildkite/test_areas/misc.yaml`.

## Details

- No existing test pads past the real tokens: each sets `num_tokens_padded` to the token count.
- The bug raises no error; it only corrupts KV. On main, the last program of the `num_reqs + 1` grid pads from the real token count, so shrinking the grid or moving that start offset silently brings the bug back.
- `block_table.py` has changed 22 times since #36580, including three fixes for stale block-table rows (#49757, #56734, #61174).
