# [Bugfix][Attention] Avoid runtime JIT in Triton unified attention when num_seqs changes

[Upstream PR](https://github.com/vllm-project/vllm/pull/62357) · state: open · merged: False

## Original PR description



## Overview

Add `num_seqs` to `do_not_specialize` for `kernel_unified_attention` and `reduce_segments`. Triton specializes these kernels on whether `num_seqs` is 1 or a multiple of 16, and warmup does not run every launch shape with every such value, so some steps compile a new variant while serving.

Related: #49349 (zero JIT compilation during runtime), #47047 (the same two kernels among the Triton JIT warnings in a log on RTX PRO 6000).

## Claims

- Without `--attention-backend`, `vllm serve openai/gpt-oss-20b` on A100 selects TRITON_ATTN and compiles `kernel_unified_attention` twice while serving, at the first single 200-token prompt. With this change the JIT monitor reports no compilation after startup in that run.
- With `--jit-monitor-mode error`, `main` fails at the first step that prefills two requests together (Qwen3-8B, A100 and RTX PRO 6000). Triton's disk cache does not avoid this: with a filled cache the same launches are still reported. With this change every request is served.
- Outputs are bit-identical to `main`, and kernel time is unchanged.

## Validation

`main` and this PR were run on the same nightly, `0.32.0rc1.dev190+g3f1bcfd82` (Triton 3.8.0), whose `triton_unified_attention.py` is identical to current `main`, with the patch applied for this PR. A100 80GB (bf16 KV) and RTX PRO 6000 Blackwell (`--kv-cache-dtype fp8`), empty Triton cache per start unless noted:

```
VLLM_SERVER_DEV_MODE=1 vllm serve Qwen/Qwen3-8B --attention-backend TRITON_ATTN \
  --kv-cache-dtype auto --gpu-memory-utilization 0.85 --max-model-len 40960 \
  --max-num-seqs 16 --max-num-batched-tokens 8192 --enable-chunked-prefill \
  --async-scheduling --enable-prefix-caching --jit-monitor-mode warn --jit-monitor-verbose
```

gpt-oss-20b ran with `--load-format dummy --max-model-len 8192 --gpu-memory-utilization 0.85 --jit-monitor-verbose` and no `--attention-backend`. Requests are greedy with 8 output tokens. Qwen3-8B: 2, then 5, then 15 concurrent 100-token prompts, then single prompts of 9 and 200 tokens. gpt-oss-20b: a single 200-token prompt, then 2 concurrent. A concurrent group is sent while the scheduler is paused, so it is prefilled together:

```
curl -X POST "localhost:8000/pause?mode=keep"
# send the group's /v1/completions requests
curl -X POST localhost:8000/resume
```

| Run | `main`: attention compiles while serving | this PR |
|---|---|---|
| gpt-oss-20b, A100 | 2D, `num_seqs == 1`, at the 200-token prompt: two (sliding-window and full layers) | none |
| Qwen3-8B, A100 and RTX PRO 6000 | 2D at the 2-request group, 2D at the 9-token prompt | none |
| Qwen3-8B, RTX PRO 6000, single 4/5/8/9-token prompts | 3D and `reduce_segments` at 5 tokens, 2D at 9 tokens | none |
| Qwen3-8B, A100, filled Triton cache | the same two, loaded from cache (0.001 s) and still reported | none |
| Qwen3-8B, `--jit-monitor-mode error`, A100 and RTX PRO 6000 | the 2-request group returns 500 and the engine stops (`EngineDeadError`) | all requests return 200 |

Each attention compile stalls its step for 0.35–0.42 s. In the warn-mode runs, greedy outputs match `main` on all 79 requests.

Kernel time (attention + reduce per forward, CUDA graph replay, Qwen3-8B shapes, 600 step shapes replayed from Mooncake traces plus 26 synthetic ones): the ratio of this PR to `main`, weighted by how often each step shape occurs, is 1.000–1.001 on both GPUs, and the maximum absolute output difference is 0.0 on all 626 shapes. `pytest tests/kernels/attention/test_triton_unified_attention.py` gives the same outcome for each of the 1917 tests on `main` and this PR: 1627 passed on RTX PRO 6000 and 711 on A100. The remaining tests fail the same way on `main`: `test_triton_unified_attn_use_td*` on RTX PRO 6000, and the FP8 cases on A100, where SM 8.0 has no fp8e4nv. Since outputs are bit-identical, no accuracy eval was run.

Full server logs, summaries, per-shape kernel times and per-test outcomes: https://gist.github.com/yuy-blip/d3b9c98e002fe2ba1f676765a7e4ae0d

## Details

- **Root cause.** Triton specializes non-constexpr integer arguments on `== 1` and `% 16 == 0`, and `num_seqs` can change every step. With `--max-num-seqs 16`, startup (dummy runs and CUDA graph capture) runs the 2D kernel only at 16 requests, and the 3D kernel at 16, 2 and 1. On SM 12.0 the one-request decode uses 64 segments, so 3D with 16 segments at one request is not warmed either. A prefill step on the 2D kernel with one request, or with a count that is neither 1 nor a multiple of 16, therefore compiles while serving. A larger `--max-num-seqs` captures more counts, but not `num_seqs == 1` on the 2D kernel.
- **Why `do_not_specialize` rather than more warmup.** In `kernel_unified_attention`, `num_seqs` only bounds the binary search for a program's sequence (`find_seq_idx`). With this change each attention launch shape compiles once at startup, to the same binary (same Triton cache hash) that `main` compiles for `num_seqs == 1`. In `reduce_segments`, which also uses `num_seqs` for its padding guard, the `num_seqs == 1` specialization lets Triton fold that search; without it, the search runs one iteration per program, which is included in the kernel times above. This matches the guidance in vLLM's Triton guide (`.agents/skills/triton-kernel-writing/SKILL.md`): "Put unimportant runtime integer scalars in `do_not_specialize`".
- **Scope.**
  - Other per-step choices (2D or 3D, segment count, tile size) are constexprs and still rely on warmup. For example, Model Runner V1 does not launch the 2D kernel during startup, so it still compiles once there.
  - The attention kernels of DiffKV, INT4 per-token-head, TurboQuant and UltraQuant are unchanged. The last three also call `reduce_segments`, so they get this change there. They were not tested, and neither were ROCm and XPU.
  - The JIT monitor e2e test is currently skipped in CI, so this was checked manually (see Validation).
- I found no open or recently merged PR or issue that changes these decorators or adds `do_not_specialize` to these kernels.
- AI assistance (Claude Code) was used in preparing this PR. I ran all measurements and tests myself.
