# [Bugfix][Attention] Avoid runtime JIT in Triton unified attention when num_seqs changes

[Upstream PR](https://github.com/vllm-project/vllm/pull/62357) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Triton unified attention (`TRITON_ATTN`) JIT-compiles `kernel_unified_attention` and `reduce_segments` during serving. Triton specializes `num_seqs` on `== 1` and divisibility by 16, and warmup covers only some of these cases. This PR marks `num_seqs` as `do_not_specialize` on both kernels. Related: #49349.

## Claims

- No runtime JIT of either kernel when `num_seqs` changes between steps.
- No output change: `num_seqs` only bounds the sequence lookup and the padding guard.

## Validation

End to end, `--jit-monitor-verbose`, A100 and RTX PRO 6000, nightly `3f1bcfd82` (its `triton_unified_attention.py` equals this PR's base):

| | Runtime JIT of these kernels |
|---|---|
| `main`, gpt-oss-20b on A100, default backend | 2, at the first single prompt |
| `main`, Qwen3-8B with `TRITON_ATTN` | at new request counts (2D, 3D, `reduce_segments`); with `--jit-monitor-mode error` the engine stops |
| This PR | 0 |

Kernel time over 626 step shapes: ratio to `main` 1.000–1.001, max abs output difference 0.0.

```
pytest tests/kernels/attention/test_triton_unified_attention.py
# same outcome as main for each of the 1917 tests
```

Logs: https://gist.github.com/yuy-blip/d3b9c98e002fe2ba1f676765a7e4ae0d

## Details

No new unit test: the change only drops a compile-cache specialization (as in 0d6f92ae), and the end-to-end JIT monitor runs above cover it.

Not run on ROCm or XPU. TurboQuant, UltraQuant and INT4 per-token-head also call `reduce_segments` and were not tested.

Not a duplicate: no open or merged PR changes these decorators.

AI assistance (Claude Code) was used in preparing this PR. I ran all measurements and tests myself.
