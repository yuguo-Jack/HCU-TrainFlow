# [Model Loader] Decode CSF-compressed NVFP4 block scales at load

[Upstream PR](https://github.com/vllm-project/vllm/pull/60646) · state: closed · merged: False

## Original PR description

## Overview

Lets the default loader read checkpoints whose NVFP4 block scales are stored with CSF compression (`weight_scale_encoding: "csf"`), such as [`local-inference-lab/Qwen3.8-Flash-Next-NVFP4-MXFP8-CSF-QAD`](https://huggingface.co/local-inference-lab/Qwen3.8-Flash-Next-NVFP4-MXFP8-CSF-QAD). Each `<name>.nvfp4_csf_fixed` / `<name>.nvfp4_csf_exceptions` stream pair is decoded back to the `<name>` E4M3 scale tensor before weight loading, so every existing NVFP4 MoE backend (FlashInfer CUTLASS / cuTile / sm12x, Marlin, ...) loads the checkpoint unchanged. Today these checkpoints only load through a b12x-specific path in a downstream fork; stock vLLM fails on the unknown tensors.

The codec is lossless (`byte-window4-fixed-stream-u24-exceptions/1`): per 16-row slab, one base byte per row plus 4-bit codes, and a sorted list of 24-bit positions with replacement bytes for out-of-window values.

## Claims

- **Lossless:** decoded scales are byte-identical to the uncompressed release of the same weights (`Qwen3.8-Flash-Next-NVFP4@6909a5bed0` vs `...-CSF-QAD@dc5b8ab2fa`), checked on `layers.0.mlp.experts.0.gate_proj` [640, 160] and `layers.17.mlp.experts.311.down_proj` [2560, 40] via ranged safetensors reads.
- **Backend-neutral:** decoding happens in the weights iterator, before TP slicing and kernel-specific layout, so no quantization method or kernel changes.
- **Layout:** the loader also finds shards that the index places in a subdirectory (`tensors/`), which this checkpoint uses.

Disclaimers:
- Draft: end-to-end serving (server start, GSM8K, decode throughput vs the uncompressed checkpoint on RTX PRO 6000 and DGX Spark) is running; results will be added here before this is marked ready.
- This PR does not keep the scales compressed in GPU memory. The runtime VRAM saving of CSF (about 3.3 GiB of expert scales for Qwen3.8-Flash-Next) needs kernels that read compressed scales; that is a separate change.

## Details

- Stream layout follows local-inference-lab/vllm `integration/karmic-kraken-beta` @ `13b13ad54b` (`nvfp4_csf_utils.py`); the decoder here is a standalone torch implementation with no b12x dependency.
- Unpaired streams raise; row bases above 240 and out-of-range exception positions raise.
- Decoding runs on CPU at load.

Not a duplicate: no open or closed vLLM PR handles `weight_scale_encoding` or CSF streams (searched "CSF scale", "weight_scale_encoding", "nvfp4_csf").

AI assistance (Claude) was used to write and test this change; I reviewed every line and ran the tests above.

@stecasta Hey, thanks for putting this together. We're running GLM-5.3-Flash on two DGX Sparks and hit the same wall with stock vLLM.

One thing I noticed: the GLM checkpoints (`nvidia/GLM-5.3-Flash-FP4-Local` and the XSFP4 requant built on it) use a different CSF layout. They declare `weight_scale_encoding: "csf_32x2_v1"` and store each scale matrix as five tensors (`csf32_bases`, `csf32_codes`, `csf32_page_bases`, `csf32_offsets`, `csf32_exceptions`), with 32x2 blocks instead of 16-row slabs. So they still won't load with this PR.

Would you be open to picking the decoder based on `weight_scale_encoding` from the quant config, instead of the tensor suffixes? Then `csf` and `csf_32x2_v1` can sit side by side, and a checkpoint whose config and tensors don't match fails with a clear error. I already have a 32x2 decoder working against TensorFold's reference implementation. I can push it as a follow-up on top of this, or into your branch if you prefer.
