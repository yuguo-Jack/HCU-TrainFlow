# [XPU][Attention] Enable tuned large-head prefill config on XPU

[Upstream PR](https://github.com/vllm-project/vllm/pull/61630) · state: open · merged: False

## Original PR description



## Overview

Enable the head_size 256 `tuned_large_head` prefill launch config of the Triton unified-attention kernel on Intel XPU (Arc Pro B70). Currently it is SM100-only. On XPU, short multi-query batches (speculative-decode verify) keep the 3D split-K path. Related: #59466 (configurable launch params, CUDA SM120 head 512), #58177 (same `BLOCK_M` override for the DiffKV kernel on SM12x).

## Claims

- 1.5–1.8× faster head-256 sliding-window prefill attention on Arc Pro B70 (Gemma-4-26B-A4B sliding-layer shape). Outputs are bit-identical to the current config.
- +4.6% end-to-end throughput for Gemma-4-26B-A4B at TP=4 on 4× B70 (random 1024-token prompts, 128 output tokens).
- No change for decode or speculative-verify batches (`max_seqlen_q <= 8`). Without the split-K gate, low-batch verify would regress 0.32–0.65×.
- CUDA behaviour is unchanged.

**Output check:** I ran greedy decoding on 10 prompts (128 tokens) before and after. The kernel output is bit-identical. Because the attention output is bit-identical, I did not run a separate accuracy eval.

**CI:** the changed path is XPU-only. The existing kernel test above exercises it on XPU runners. No new test is added.

## Details

**Root cause of the gap.** The `tuned_large_head` config (`BLOCK_M=32`, `num_stages=2`) is gated on `is_device_capability_family(100)`. On XPU, head-256 prefill batches therefore run the decode-oriented defaults (`BLOCK_M=16`), which under-tile them.

**Change.** Enable the config on XPU:
- **4 warps instead of 8.** XPU warps are 16 lanes, and 8 warps cancels the gain.
- **The 128-wide KV tile stays CUDA-only.** With tensor descriptors on XPU, the tile is clamped to the KV block size; without them it is slower.

**Split-K gate.** The XPU branch requires `max_seqlen_q > MAX_3D_QUERY_LEN`. `tuned_large_head` also feeds the `use_3d` predicate, so enabling it for every `max_seqlen_q > 1` moved q_len 2..8 verify batches from the 3D split-K kernel to the 2D kernel. At low batch sizes the 2D grid cannot fill the GPU. Measured without the gate:

| verify batch, kv 4096 | before µs | without gate µs | speedup |
|---|---|---|---|
| 1 × q_len 4 | 125 | 389 | 0.32× |
| 4 × q_len 4 | 250 | 383 | 0.65× |
| 16 × q_len 4 | 231 | 513 | 0.45× |

**Tradeoffs and limitations:**
- The XPU gate uses query length as a proxy for "this batch takes the 2D path". q_len 2..8 batches that go 2D anyway get the untuned config, as before this PR. Examples are batches above the split-K threshold or batches without spec-decode scratch. Without the gate, 64-sequence verify batches were 1.1–1.2× faster on 2D, so a finer gate could win a little more.
- I only benchmarked bf16 with tensor descriptors on. Other dtypes and KV-quant modes are covered for correctness by the kernel tests, but not benchmarked.
- SM100 may have the same short-verify interaction. It is not measured here and the CUDA condition is not changed.

**Duplicate check.** I searched open, merged and closed PRs and issues in vllm-project/vllm and vllm-project/vllm-xpu-kernels for `tuned_large_head`, `unified_attention xpu`, `triton_unified_attention xpu`, and Gemma-4 sliding-window XPU. No PR enables this config on XPU; the related items are linked above.
