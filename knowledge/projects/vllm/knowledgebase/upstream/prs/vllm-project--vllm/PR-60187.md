# [Bugfix][Model] K-EXAONE: restore loading of pre-2.0 configs and apply RoPE to the MTP layer

[Upstream PR](https://github.com/vllm-project/vllm/pull/60187) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

Fixes two K-EXAONE-236B-A23B (K-EXAONE 1.0) problems introduced with #50524 (K-EXAONE 2.0 support, 2026-08-03):

1. Checkpoints whose `config.json` predates that change fail to load.
2. With the current official config, the MTP drafter runs its attention without RoPE, which lowers MTP acceptance by 3–5 pp.

## Claims

- **Legacy configs load again.**
  - `"architectures": ["ExaoneMoEForCausalLM"]` resolves through a registry alias, in the same way as `LLaMAForCausalLM`.
  - When `sliding_windows`, `mtp_layer_types` and `mtp_sliding_windows` are missing, `ExaoneMoeAttention` falls back to the scalar `sliding_window`. The MTP layer then takes the settings of the main layer with the same index, which is what vLLM did before #50524.
- **The MTP layer always applies RoPE.** Main-model full-attention layers stay NoPE.
  - With the current official 1.0 config, MTP acceptance goes from 85.0% to 88.3% on GSM8K and from 67.9% to 73.1% on MT-Bench.
  - K-EXAONE 2.0 and legacy 1.0 configs already ran their MTP layer with RoPE (sliding window), so they are unchanged.
- Main-model layers are unchanged for every config. Output quality is unaffected, since spec decoding is lossless.

## Validation

**Setup.** 16× A100-SXM4-40GB. Model: K-EXAONE-236B-A23B FP8 (compressed-tensors), TP=8. Flags: `--speculative-config '{"method":"mtp","num_speculative_tokens":1}'`, temperature 0, no prefix caching. Two config variants of the same weights: the current official HF config, and a legacy copy predating 2026-08-03.

**Metric.** MTP acceptance comes from the `vllm:spec_decode_num_{draft,accepted}_tokens` counters. Prompts: 200 GSM8K test questions and the 80 MT-Bench prompts. Reruns of the same configuration varied by ≤0.2 pp.

## Details

**Root cause: loading.** #50524 renamed the registry key `ExaoneMoEForCausalLM` to `ExaoneMoeForCausalLM` without keeping an alias. It also replaced `Exaone4Attention`, which reads the scalar `sliding_window`, with code that reads `sliding_windows`, `mtp_layer_types` and `mtp_sliding_windows` directly.

`transformers`' `ExaoneMoeConfig` does not define these fields. The official HF repo added them on the same day ([61e6d57](https://huggingface.co/LGAI-EXAONE/K-EXAONE-236B-A23B/commit/61e6d578eb102b578e5704e2916ac841df9eca0a)), but existing copies kept the old config. Public examples still on it include:
- `furiosa-ai/K-EXAONE-236B-A23B-NVFP4A16`
- `Hyun9junn/K-EXAONE-236B-A23B-W4A16-G128`
- `haanjack/K-EXAONE-236B-A23B-MXFP4`
- `tazza26/K-EXAONE-236B-SFT-full`

**Root cause: MTP RoPE.** `ExaoneMoeAttention` applied RoPE only to sliding layers. That matches the main model, whose global layers are NoPE in both HF and vLLM. vLLM applied the same rule to the MTP layer, which `transformers` does not implement at all.

- Before #50524, the 1.0 MTP layer inherited layer 0's settings (sliding 128), so it ran with RoPE.
- After #50524 it reads `mtp_layer_types: ["full_attention"]` from the new config, and so loses RoPE.

Measured on v0.30.0, with only the MTP layer's attention changed:

| MTP layer attention | GSM8K | MT-Bench |
|---|---|---|
| full, NoPE (current) | 85.05% | 68.32% |
| full, RoPE (this PR) | 88.24% | 73.61% |
| sliding 128, RoPE (pre-#50524) | 88.96% | 74.63% |

RoPE accounts for most of the gap, so the MTP layer was trained with RoPE. This PR keeps the configured attention type and only fixes the positional encoding.

**Duplicate check.** No open issue or PR covers this.
- #50865 (closed) only renamed the test registry key after the HF change.
- #51558 (K-EXAONE-2.0 DSpark) edits `exaone_moe.py` class bases and Eagle hooks, not the attention init.
