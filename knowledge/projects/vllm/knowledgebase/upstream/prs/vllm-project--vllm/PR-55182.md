# [Security] Validate kv_transfer_params role sub-dicts are dicts

[Upstream PR](https://github.com/vllm-project/vllm/pull/55182) · state: open · merged: False

## Original PR description

## Summary

The P2P secondary tier manager assumes that the nested role sub-dicts
(`remote_prefiller`, `remote_decoder`, `remote_kv_source`) inside
`kv_transfer_params` are always dicts. When a client sends a non-dict value
(e.g. a string), the subsequent `.get()` call on the result raises
`AttributeError`, which escapes request handling and terminates EngineCore.

This adds `isinstance(val, dict)` checks in the three role accessor
functions so non-dict values are treated as absent (return `None`),
making the malformed input a request-local no-op instead of a fatal crash.

## Changes

- `vllm/v1/kv_offload/tiering/p2p/manager.py`: Added type validation in
  `_remote_prefiller_params`, `_remote_decoder_params`, and
  `_remote_kv_source_params` — return `None` when the extracted value is
  not a `dict`.
- `tests/v1/kv_offload/tiering/p2p/test_manager.py`: Added
  `TestNonDictRoleParamsRejected` with regression and completeness tests
  for string, int, list, and bool values across all three role keys, plus
  full manager-flow tests for `on_new_request`, `lookup`, and
  `submit_store`.

## Codepath coverage

All entry-point-to-sink paths verified as fixed:
- `/v1/completions` (and all protected endpoints) → EngineCore → Scheduler
  → P2P `on_new_request` → `_annotate_req_context` → `_parse_source` /
  `_parse_dest` → accessor functions (now guarded)
- `/invocations` (unauthenticated SageMaker) → same chain → same guard

- Manny7717 · APPROVED · 2026-09-03T18:13:46Z · [source](https://github.com/vllm-project/vllm/pull/55182#pullrequestreview-5105297712)

Independent APPROVE — fully locally verified on head `ce1fdc90` (CPU env, repo's own venv); no rubber stamp.

**Vulnerability confirmed real:** `kv_transfer_params` arrives from the client as free-form JSON (`dict[str, Any]` in the token-in-token-out protocol — no recursive shape validation). On base, a truthy non-dict value for any role, or a non-dict `kv_transfer_params` itself, reached `_peer_id_from_params`/`role.get` and crashed EngineCore with `AttributeError: 'str' object has no attribute 'get'` (reproduced: `kv_params={"remote_prefiller": "not-a-dict"}` → AttributeError at manager.py:100 on base; clean local-degradation on head). That is a remote availability hole on the serving path — the hardening is justified.

**Fix semantics verified coherent across the whole surface** (executed 11-case matrix on head):
- consumer roles (`remote_prefiller`, `remote_kv_source`) with non-dict values → treated as absent → request handled locally (`OffloadPolicy.BLOCK_LEVEL`, `lookup → MISS`), never a crash;
- producer role (`remote_decoder`) with a non-dict value → coerced to `{}` (present-but-empty) so `submit_store` fails closed (`JobResult(success=False)`) instead of silently storing locally a block a remote decoder is expecting — the correct asymmetry, since storing locally would be silent data loss for the decode side;
- empty-dict role values and empty `kv_params` behave exactly as on base (no behavior change); only the previously-crashing non-dict inputs change.
- `isinstance(kv_params, dict)` guards also cover the outer-params-non-dict case (string/int/None) that base mishandled for truthy values.

**Regression-proven:** all 19 new parametrized tests FAIL on base manager.py (crash) and PASS on head; full `tests/v1/kv_offload/tiering/p2p/test_manager.py` = 91/91 passed on head (72 pre-existing + 19 new). No call-site drift: `_parse_source`/`_parse_dest`/`submit_store` consumers all handle the new `None`/`{}` outputs correctly per the tests.

Nit (non-blocking): the fail-closed `{}` coercion for `remote_decoder` relies on the docstring to explain the asymmetry vs. the consumer roles returning `None` — a one-line comment at each call site would make the intent self-documenting, but the class docstrings and tests already carry it.

Matches maintainer russellb's approved direction; no remaining issues found.

- liranschour · CHANGES_REQUESTED · 2026-10-01T11:49:06Z · [source](https://github.com/vllm-project/vllm/pull/55182#pullrequestreview-5378815121)

Thanks for this — the underlying bug is real and worth fixing. I confirmed against current `main` that `{"remote_prefiller": "x"}` reaches `_peer_id_from_params("x")` and raises `AttributeError: 'str' object has no attribute 'get'` out of `on_new_request` on the scheduler thread. Since `kv_transfer_params` is typed `dict[str, Any] | None` in the pydantic models, the *nested* values are genuinely unvalidated client JSON, so the entry point you describe is correct.

Two things need to change before this lands.

## 1. Three of the six new tests fail on this branch

`OffloadPolicy.BLOCK_LEVEL` does not exist. It was renamed to `CHUNK_LEVEL` in #52615 (`[Refactor][kv_offload]: rename block→chunk`), and the only three references to `BLOCK_LEVEL` anywhere in the tree are the ones this PR adds. Running the file on this PR's head:

```
3 failed, 88 passed

TestNonDictRoleParamsRejected::test_manager_survives_malformed_prefiller_role
TestNonDictRoleParamsRejected::test_malformed_decoder_role_fails_store
TestNonDictRoleParamsRejected::test_manager_survives_malformed_kv_source_role

AttributeError: type object 'OffloadPolicy' has no attribute 'BLOCK_LEVEL'
```

It's a one-word fix — `CHUNK_LEVEL` is also what `on_new_request` actually returns for a role-less request (bare `RequestOffloadingContext()`). With `s/BLOCK_LEVEL/CHUNK_LEVEL/` applied, all 19 tests in the new class pass. `ruff` can't catch this because it's a runtime attribute lookup, and the unit-test job didn't run on this PR, so it slipped through green CI.

## 2. The guard doesn't close the crash class it targets

`kv_request_id` is equally `Any`, and it is used as a `set`/`dict` key. With this PR applied, a perfectly dict-shaped role still terminates EngineCore:

| `kv_transfer_params` | sink | result |
|---|---|---|
| `{"remote_prefiller": {"remote_host": "h", "remote_port": 1, "kv_request_id": ["x"]}}` | `lookup()` → `_failed_req_ids` | `TypeError: unhashable type: 'list'` |
| same, `kv_request_id: {"a": 1}` | `lookup()` → `_failed_req_ids` | `TypeError: unhashable type: 'dict'` |
| `{"remote_decoder": {"kv_request_id": ["x"]}}` | `submit_store()` → `_reaped_stores` | `TypeError: unhashable type: 'list'` |
| same, `kv_request_id: {"a": 1}` | `submit_store()` → `_reaped_stores` | `TypeError: unhashable type: 'dict'` |

Same endpoint, same fatal outcome, both reachable from plain JSON — so the PR's goal of making malformed input "a request-local no-op instead of a fatal crash" isn't met yet.

A per-key `isinstance` in the three accessors treats the symptom. The funnel is `_parse_source` / `_parse_dest`, which already validate shape:

```python
if peer_id is None or not kv_request_id:
    return None
```

Tightening that to require `isinstance(kv_request_id, str)` (and the same for `remote_host` / `remote_port` in `_peer_id_from_params`) covers both classes in one place, and lets the three accessors stay as they are. Could you move the validation there instead?

Related, lower severity: `remote_host` / `remote_port` are unvalidated too, so `peer_id` becomes arbitrary attacker-controlled text — e.g. `"{'a': 1}:8000"` — which is then used as a session-map key and a ZMQ endpoint. Not a parse-time crash, but it belongs in the same validation pass.

## 3. Behavior change on `{"remote_decoder": null}`

Commit 2 swaps `.get()` for an `in` check plus an `{}` fallback, so an explicit JSON `null` now takes the fail-closed path: `JobResult(success=False)`, where before it was `success=True`. A JSON `null` most naturally reads as "absent", and an external router templating `"remote_decoder": null` would start failing stores. Suggest an explicit `if val is None: return None` before the `{}` fallback.

## What's right

The fail-closed asymmetry is the correct call and I'd keep it: consumer roles (`remote_prefiller` / `remote_kv_source`) degrade to local compute, while a present-but-malformed `remote_decoder` fails the store. That matches the existing `P2PDestInfo` docstring and the behavior already in tree for `{"remote_decoder": {}}`, so commit 2 makes the non-dict case consistent with the empty-dict case rather than introducing a new rule. The top-level `isinstance(kv_params, dict)` guard is unreachable via the HTTP endpoints (pydantic validates the container) but it's harmless defense-in-depth and doesn't regress the `{}` case.
