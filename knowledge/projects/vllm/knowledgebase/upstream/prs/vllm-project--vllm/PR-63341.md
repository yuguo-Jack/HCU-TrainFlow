## Original PR description

# [ROCm][Perf][DSv4.1] Mono decode: architecture-selected tiling + MI350P enablement path

## Summary

The mono decode kernels hardcoded the grid width `BLOCKS=256` (the compute-unit
count of MI355X / MI350X / gfx942), one resident CTA per CU. This PR makes the
tiling **architecture- and compute-unit-selected** via `common/arch.py`'s
`resolve_tiling(arch, cus)`, threads the chosen width to the traced device
modules through `VLLM_DSV41_MONO_BLOCKS`, and keys the JIT cache on it so builds
for different compute-unit counts never collide.

It also lays the **MI350P (gfx950, 128 CUs, 4 XCDs) enablement path**: MI350P is
detected and refused with the exact remaining work (tracked in #63340), rather
than silently building a grid that fails a compile-time assert.

## What changed / what did NOT

- **Unchanged on 256-CU parts (MI355X / MI350X / gfx942):** the resolver returns
  `BLOCKS=256` there, every `BLOCKS`/`THREADS`/`WAVES` use is the same value, and
  the only new cache-key entry (`("blocks", 256)`) is constant — so the compiled
  kernels and numerics are identical.
- **New:** `resolve_tiling(arch, cus)`, `tiling()`, `MONO_BLOCKS_ENV`; the gate
  resolves+exports the grid width before importing the runner; `key_tuple` keys
  the cache on the grid width (fixes a latent cache-collision risk where the arch
  / CU count never reached the key).

## MI350P: why not fully enabled in this PR

A bare `BLOCKS=128` does **not compile**. The MoE down stage and the attention
`wo_b`/`wo_a` stages fix their task counts from the model width
(`DOWN_TASKS = HIDDEN // ROWS = 5120 // 16 = 320`, and `d.wob_tasks` likewise),
and the device loops emit one task per CTA plus an optional second
(`BLOCKS < tasks <= 2*BLOCKS`). At 128 CTAs a 320-task stage needs three passes
per CTA, which the traced loops do not emit, so the build asserts fire
(`moe.py: assert BLOCKS < DOWN_TASKS <= 2*BLOCKS` → `128 < 320 <= 256` is false;
`back.py: assert BLOCKS < d.wob_tasks <= 2*BLOCKS` likewise).

Enabling 128 CTAs is a task-decomposition rewrite that must be validated on the
hardware — tracked in **#63340**. `resolve_tiling` refuses a gfx950/128
deployment with a message naming that work, so the switch flips on in a follow-up
once the loops are written and validated.

## Tests run (CI, no GPU)

The tiling resolver and gate are plain Python, exercised by the extended
`tests/models/test_dsv41_mono_decode.py` via the monkeypatched `_deployment`
(no FlyDSL/GPU), which now reuses the real `resolve_tiling`:
- `test_opt_in_takes_the_256_cu_gfx950` — gfx950/256 builds the whole-layer kernels.
- `test_opt_in_on_mi350p_names_the_retune` — gfx950/128 refused, message names the work.
- `test_opt_in_outside_the_kernels_moe_raises[cus]` — an unvalidated count (64) raises.
