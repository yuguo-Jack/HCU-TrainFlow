# [Perf][KV Events] Batch BlockRemoved events per allocation

[Upstream PR](https://github.com/vllm-project/vllm/pull/63441) · state: open · merged: False

## Original PR description



## Overview

Emit one `BlockRemoved` per KV cache group per allocation instead of one per evicted block. When most of a prompt comes from an external KV store (P/D prefill with Mooncake), every allocated block evicts a cached one, and building these events costs the scheduler a few percent of its time.

## Claims

- `BlockPool.get_new_blocks` with KV events on, every allocated block evicting a cached one: 1,613 -> 717 ns per evicted block; events off unchanged (468 ns).
- `BlockRemoved` events for 10,240 evictions in 40 allocations over 4 KV cache groups: 10,240 -> 160. Same hashes, same order within each allocation.
- Context: on a DeepSeek-V4.1-Flash 2P1D deployment (B200, Mooncake store, ~96% of prompt tokens loaded from the store), py-spy put 5-7% of each prefill EngineCore's main thread in this path.

## Validation

Micro-benchmark on main `ae06591864` vs this PR (CPU): `BlockPool(num_gpu_blocks=10241, enable_caching=True)`, every block cached under one of 4 group ids and freed, then `get_new_blocks(256)` x 40; `envs.enable_envs_cache()` as in EngineCore; best of 7.

```bash
pytest tests/v1/core/test_prefix_caching.py tests/v1/simple_kv_offload/test_kv_events.py \
  tests/v1/kv_connector/unit/offloading_connector/test_events.py tests/distributed/test_kv_cache_events.py
```

234 passed on this PR, 230 on main (the 4 new tests: one event per group for a multi-group eviction with bytes and int hashes, `evict_blocks` batching, `maybe_convert_block_hash` equal to the old formula). The same 26 tests fail on both (environment of the offline image). End-to-end A/B on the P/D deployment is pending.

## Details

- `get_new_blocks` and `evict_blocks` collect the hashes they evict and emit one `BlockRemoved` per group per call. `BlockRemoved.block_hashes` is already a list; consumers that read `block_hashes[0]` per event must iterate (two tests updated).
- `group_external_block_hashes` converts the packed `BlockHashWithGroupId` keys directly, and `maybe_convert_block_hash` reads the low 64 bits from the last 8 bytes (same value).
- #63390 also coalesces `BlockRemoved` (consecutive same-group events in the queue) and trims event construction; it reports no end-to-end change on Qwen3-0.6B. This PR batches at the source, per allocation, and targets the eviction-heavy case above. #58508 and #55092 change which hashes are reported; whichever lands second needs a small rebase.
