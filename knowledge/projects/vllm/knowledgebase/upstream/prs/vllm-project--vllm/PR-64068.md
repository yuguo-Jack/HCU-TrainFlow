# [Bugfix][Worker] Honor fixed KV-cache sizing at GPU startup

[Upstream PR](https://github.com/vllm-project/vllm/pull/64068) · state: open · merged: False

## Original PR description

## Overview

Honor explicit `--kv-cache-memory-bytes` independently of `gpu_memory_utilization` at GPU startup.
The utilization check could reject a fitting fixed cache before loading weights.

Revisits closed [#39852](https://github.com/vllm-project/vllm/pull/39852), with zero-value handling and
real-LLM regression coverage.

## Claims

- A nonzero fixed cache bypasses the utilization-fraction startup check; `None` and `0` retain automatic sizing and its guard.
- The worker budget remains initialized, and the generated configuration reference documents the behavior.

## Validation

RTX 5070 Laptop, sm_120, 8 GB, WSL2, driver 596.13, torch 2.14.0+cu130. The session power-limit probe
reported 78.50 W; the limit varies. No throughput or latency improvement is claimed.

| Check | Result |
| --- | --- |
| New cases without the fix | 1 failed at the reported startup guard; 2 passed (`None`, `0`) |
| New cases with the fix | 3 passed |
| Entire `test_gpu_utilization.py` before latest-main rebase | 4 passed, twice |
| Latest-main rebase (`939ff73503` base) | 3 new cases passed; existing multi-instance test hit CUDA OOM |
| Original full test file with all changed files restored to latest main | Same CUDA OOM allocating 1.88 GiB KV cache |
| Qwen3-1.7B, fixed 1 GiB KV, utilization 0.8 vs 1.0, O2 and CUDA graphs, separate fresh processes | Both start; 16 greedy tokens identical; selected-token logprob max difference 0.0 |
| Pre-commit on all changed files, including mypy and CI test tethering | Passed; commit hooks also passed |

The full-file passes were on base `9e0bc7a651`. After rebasing the unchanged patch onto `939ff73503`,
the three new cases still passed, but the existing multi-instance test failed allocating a 1.88 GiB
KV buffer. Restoring all three changed files to main and running the original full test file reproduced
the same CUDA OOM. The current WSL full-file run is therefore **not reported as passing**. No tests,
assertions, tolerances or environment settings were changed to hide the failure.

The latest same-process Qwen control also ran out of memory while loading the second model. Both
configurations were then validated in separate fresh processes with the same model revision,
batch shape, O2/CUDA-graph settings and output/logprob comparison; both passed. The earlier
same-process controls had passed before the rebase. These results do not establish the cause of
the latest-main/WSL memory-allocation behavior.

Reproduce with OPT-125M cached when offline:

```bash
HF_HUB_OFFLINE=1 VLLM_WSL2_ENABLE_PIN_MEMORY=0 OMP_NUM_THREADS=1 \
  .venv/bin/python -m pytest tests/entrypoints/llm/test_gpu_utilization.py -vv -s

.venv/bin/pre-commit run --files \
  vllm/v1/worker/gpu_worker.py vllm/config/cache.py \
  tests/entrypoints/llm/test_gpu_utilization.py
```

The fixed-cache regression compares eight greedy token IDs at utilization 1.0 and 0.5 with the same
64 MiB cache and batch shape. Without the fix, the 1.0 case fails before loading weights:

```text
ValueError: Free memory on device cuda:0 (6.77/7.96 GiB) on startup is less than
 desired GPU memory utilization (1.0, 7.96 GiB).
```

CI already selects this suite in Entrypoints Integration (LLM). Local validation is CUDA-only; ROCm
execution is left to its existing CI mirror. Startup bookkeeping does not change model math or kernel
selection, so greedy output/logprob comparison was used instead of a numerical model evaluation.

## Details

`Worker.init_device()` called `request_memory()` before the fixed-cache branch in
`determine_available_memory()`. Initialize the budget from the free-memory snapshot for nonzero fixed
KV bytes, keeping the existing call for `None` and `0`. This matches the later branch's truthiness check
and avoids the unset-budget zero-value bug identified in the closed proposal. XPU is unchanged.
Explicit allocations must still fit; this does not add pinned-cache fit profiling.

Open/closed duplicate searches covered `kv_cache_memory_bytes gpu_memory_utilization`,
`kv-cache-memory-bytes startup utilization`, `Skip gpu_memory_utilization validation`, and
`39852 in:body`; prior comments and inline reviews were read. Open
[#56698](https://github.com/vllm-project/vllm/pull/56698) changes later pinned-cache profiling/validation
but leaves this earlier guard unchanged.

AI assistance was used to investigate, implement, test, and prepare this change.
