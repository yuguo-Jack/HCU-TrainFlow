# [Rust Frontend] Support hybrid and external DP LB in `vllm-rs serve`

[Upstream PR](https://github.com/vllm-project/vllm/pull/64451) · state: closed · merged: True

## Original PR description

## Overview

Support hybrid and external data parallel load balancing in standalone `vllm-rs serve`, with the same flags as `vllm serve`: one Rust frontend per node or per DP rank, each serving only its own ranks.

Top of a stack: vllm-project/vllm#64449 → vllm-project/vllm#64450 → this PR.

## Claims

- `vllm-rs serve` accepts `--data-parallel-hybrid-lb`, `--data-parallel-external-lb`, `--data-parallel-rank` (or `VLLM_DP_RANK`), and `--data-parallel-start-rank` outside `--headless`. Until now the first three were rejected as unsupported.
- A hybrid-LB frontend serves its node's ranks, and an external-LB frontend serves its single rank. `X-data-parallel-rank` takes the global rank.
- For MoE models, the rank-0 frontend runs the DP coordinator and the other frontends follow its waves.

## Validation

GB200 node, DP 4 with one GPU per rank, `--enforce-eager`, `--max-model-len 2048`, `--gpu-memory-utilization 0.3`:

| Scenario | Result |
| --- | --- |
| MoE (`TitanML/tiny-mixtral`), internal LB, two launchers: rank 0 plus `--headless --data-parallel-start-rank 2` | Requests pinned to ranks 0–3 and an unpinned request return 200; 32/32 concurrent requests succeed |
| MoE, hybrid LB: frontend 8100 with ranks 0–1 (`--data-parallel-hybrid-lb`), frontend 8101 with ranks 2–3 (`--data-parallel-start-rank 2`) | Own ranks and unpinned requests return 200 on both; rank 0 pinned on 8101 returns 400; bursts of 32 sent to 8101 only, then 8100 only, then 8101 again all return 200 |
| MoE, external LB: four frontends with `--data-parallel-rank 0..3` | Each returns 200; 32 concurrent requests to rank 3's frontend only all return 200, which needs the other ranks' engines to follow its waves |
| Dense (`Qwen/Qwen3-0.6B`), hybrid LB: same layout as the MoE hybrid run | Own ranks and unpinned requests return 200 on both frontends, with the same greedy output on every rank; bursts of 32 sent to 8100 only and to 8101 only all return 200 |

All rows are from the current heads of this stack.

## Details

Flag resolution follows `vllm serve`'s `EngineArgs.create_engine_config`:

- A start rank outside `--headless` implies hybrid LB, and hybrid LB with every rank on the node is internal LB.
- `--data-parallel-rank` selects external LB with one local rank.
- Without `--data-parallel-size-local`, the start rank is ignored.
- Rejected: hybrid together with external LB, hybrid LB with `--headless`, a rank together with a start rank, external LB without a rank or with a local size other than 1, hybrid LB without a local size, and a rank range beyond the DP size.

Launch: the rank-0 frontend binds the shared handshake on `--data-parallel-address:--data-parallel-rpc-port`, as before. Any other frontend binds a local IPC handshake and starts its managed Python engines as a headless node with its start rank and local size, passing that endpoint as the new hidden `--headless-client-handshake-address`. `run_headless` hands it to `CoreEngineProcManager` as `client_handshake_address` with `local_client=True`, so the engines handshake with rank 0 for the coordinator and rendezvous and with their own frontend for input/output. The README gains a section on these modes.

Differences from `vllm serve`:

- `--data-parallel-rpc-port` has no default in hybrid and external LB, because every node must agree on it.
- Ranks are not inferred from `--nnodes`/`--node-rank`.
- Dense models are not rejected for external LB. `vllm serve` rejects them and points to independent instances instead.

A pre-existing issue, also present with Python-supervised hybrid LB on `main`: a request pinned to a rank the frontend does not own returns 400, but the body says only `engine-core error`. The detailed message ("rank 0 is not connected to this frontend; connected ranks: [2, 3]") is lost when the error is wrapped.
