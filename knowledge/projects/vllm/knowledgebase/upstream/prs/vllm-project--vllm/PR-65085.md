# [Bugfix][Benchmark] Derive forward benchmark batch budget from cases

[Upstream PR](https://github.com/vllm-project/vllm/pull/65085) · state: open · merged: False

## Original PR description

## Overview

`vllm bench forward` defaulted `max_num_batched_tokens` to at least 8192 even when no case used a prefix-cache hit. The engine uses that value as the memory-profiling batch, so small decode/verify-only case sets profiled a much larger batch than they run, which can make KV-cache planning fail at high `--gpu-memory-utilization`.

This derives the default from the cases while keeping an explicit `--max-num-batched-tokens` unchanged.

## Claims

- The default budget is now the largest case's query tokens plus draft tokens plus 1024 tokens per prefix-cache hit, with `1` for an empty case list.
- An explicit `--max-num-batched-tokens` still wins.
- A six-case decode/verify set that previously profiled 8192 tokens now profiles 792 instead of 432/792 query tokens plus drafts.

## Details

### Root cause

`_make_engine_args` applied `max(8192, ...)` when `--max-num-batched-tokens` was unset. `max_num_batched_tokens` sizes the memory-profiling dummy batch (`profile_run -> _dummy_run(self.max_num_tokens, is_profile=True)`). A six-case decode/verify set with 432 query tokens and 360 draft tokens therefore profiled 8192 tokens instead of 432/792, increasing non-KV memory. At high `gpu_memory_utilization`, the KV budget can then go negative and startup fails with `No available memory for the cache blocks`.

### Behavior and tradeoffs

- The 1024-per-prefix-hit term preserves the existing bounded-replay approximation. A model whose replay window is larger than 1024 tokens may still need an explicit budget.
- Draft tokens are counted conservatively: verify queries already include them, so the derived value can be slightly larger than the executed batch. The error is in the safe direction and far below the old floor.
- There is no behavior change when the flag is explicit, and no change to the scheduler or model runner.
