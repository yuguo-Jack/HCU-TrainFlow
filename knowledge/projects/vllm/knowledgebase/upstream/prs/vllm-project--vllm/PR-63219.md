## Overview

Revert https://github.com/vllm-project/vllm/pull/54442, which introduces a performance regression under PP + spec decode with structured outputs, and re-fix https://github.com/vllm-project/vllm/issues/54437 by addressing the root cause in `DraftTokensHandler`.

Rework of https://github.com/vllm-project/vllm/pull/61348, rebased, with remaining comments addressed, pre-commit fixed, and simplified implementation + tests.

## Claims

#54442 patched the issue in #54437 by masking out the draft tokens after a handoff race in `DraftTokensHandler`. This fixes #61348 but effectively shortens the draft sequence, causing an acceptance-length (and performance) regression under PP + spec decode with structured outputs.

This PR addresses the `DraftTokensHandler` handoff race directly, fixing the original issue #54437 while maintaining acceptance length.

This PR also adds an E2E repro for #54437 and acceptance length regression.

## Details

### Background

`DraftTokensHandler` allows workers to asynchronously send draft tokens back to the scheduler / structured output manager for processing.

With async scheduling, it works roughly like:
```
Scheduler-side                          Worker-side
--------------------------------------------------
schedule step N
sample step N
                                        execute step N
schedule step N+1
wait for step N
                                        sample step N
                                        DraftTokensHandler.set_draft_tokens
                                        execute step N+1
DraftTokensHandler.get_draft_tokens
generate sampling bitmasks
sample step N+1
                                        sample step N+1
...
```

On main, `DraftTokensHandler` holds the latest batch set by the worker. This works fine for PP=1, but when PP>=2, this can occur:
```
Scheduler-side          Worker-side
----------------------------------
                        set_draft_tokens(micro-batch A)
                        set_draft_tokens(micro-batch B)
get_draft_tokens
```

Micro-batch B replaces micro-batch A in the handler. Scheduler-side cannot recover A's drafts and generates incorrect grammar bitmasks, leading to #54437.

#54442 fixes this by effectively truncating the worker-side draft sequence, reducing acceptance length.

This PR fixes this by making `DraftTokensHandler` track draft tokens by request ID. So micro-batch B cannot override micro-batch A.

- michael-gpu · comment · 2026-10-27T22:15:55Z · [source](https://github.com/vllm-project/vllm/pull/63219#issuecomment-6454950013)


@yzong-rh — one residual path I want to close the loop on before this
merges. This is not a re-litigation of the revert: @ArcheyChen's
fail-closed rationale and the handoff fix being the right fix for the race
are both settled in this thread, and I agree with both.

The handoff fix restores trust in drafts that the **race** corrupted. But
#54442 was fail-closed against a second source of untrusted drafts behind
a bitmask: **grammar-invalid proposals**. That path is independent of the
handoff and still exists on this branch:

1. The drafter proposes a token the grammar rejects → the scheduler's
   `validate_tokens` drops it and pads the window with `-1`
   (`spec_token_ids.extend([-1] * num_invalid_tokens)` in
   `update_draft_token_ids`).

2. `StructuredOutputManager`'s bitmask fill treats the first `-1` as
   `seen_padding`, and every later row is filled with
   `apply_bitmask=False` — all-permissive. The `failed_index` reuse only
   fires when a *real* token is rejected during the fill, which cannot
   happen once padding starts (`vllm/v1/structured_output/__init__.py`,
   the serial fill loop: `if token == -1: seen_padding = True`).

3. The worker then verifies its device-side proposals at those positions
   (`gpu_model_runner.py` draft-verify path + `rejection_sampler.py`), so
   the model samples from an unmasked row at a position it really does
   sample — the exact failure #54437 reported.

#54442's guard (`grammar_invalid_drafts`, deleted by this PR) was the
fail-closed mechanism for precisely this path; its deleted test
(`tests/v1/worker/test_grammar_invalid_drafts.py`) states the contract in
the docstring:

> `StructuredOutputManager.grammar_bitmask` fills row i before it inspects
> `req_tokens[i]`, so with the first -1 placeholder at index j rows 0..j
> carry a real mask and rows j+1.. carry the all-permissive `_full_mask`.
> Drafts j..K-1 must therefore be rejected, or the request samples with no
> grammar constraint at a position the model really does sample.

The E2E here is real but stochastic coverage: it passes because the DFlash
drafter's proposals in the test happen to be grammar-valid at the asserted
positions, not because the padded path is closed. A drafter that proposes
a grammar-invalid token under a constrained request would walk straight
through it.

Three ways to close it, in increasing invasiveness:

1. **Re-add `grammar_invalid_drafts`** scoped to the grammar-invalid path
   (the deleted test is CPU-only and passes on main — it can come back
   verbatim).
2. **Constrain the rows CPU-side**: when padding originates from
   `validate_tokens` invalidation, fill later rows from the last valid
   grammar state (the `failed_index` reuse already does this for
   fill-time rejections — the padding path just never sets it).
3. **Extend the E2E** with a drafter that deterministically proposes a
   grammar-invalid token, so the padded path is exercised on every run
   rather than by race timing.

Happy to put up (1) or (3) as a follow-up commit on this PR if you'd
rather not rework the handler — the deleted test is a working starting
point either way.
