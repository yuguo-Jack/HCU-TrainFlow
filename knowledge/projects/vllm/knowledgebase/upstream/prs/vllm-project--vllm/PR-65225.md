# [Bugfix] Pad extensible KV cache segments instead of rounding the block count

[Upstream PR](https://github.com/vllm-project/vllm/pull/65225) · state: closed · merged: True

## Original PR description



## Overview

Fixes #65204. Supersedes #65210 (carries over its connector gating, with Vegetog as co-author).

With the extensible KV cache (#56492), any KV connector made the engine round the KV block count down to a multiple of `granule / gcd(granule, block_stride)`. For awkward strides that multiple is huge, so engines with `--kv-offloading-size` could fail to start. This PR pads segment placement instead, and applies it (and the defragmenting commit) only for connectors that register the KV cache for RDMA.

## Claims

- `--kv-offloading-size` (and any connector that doesn't register the device KV cache) keeps its measured block count: no rounding, no padding, no defragmenting commit.
- NIXL / Mooncake / MoRIIO / UMBP keep one physical chunk per committed segment for RDMA registration at **any** block count, instead of losing up to one alignment unit (2048 blocks, ~11.6 GB, for the stride in #65204) or failing to start below it.
- `UMBPStoreConnector` is added to `registers_kv_cache_memory()`: it registers GPU KV storage through MORI. This also turns the extensible cache off for it on ROCm, as for MoRIIO.

## Details

**Root cause.** A connector that registers each committed segment for RDMA needs that segment backed by one physical chunk. Segments were placed at multiples of `capacity × block_stride`, so they only started on commit granules when the block count was a granule multiple; the engine forced that by rounding the reserved capacity and the post-warmup count for *every* connector. CPU offloading only copies blocks and needs none of it.

**Fix.**
- When `registers_kv_cache_memory()`, each worker pads its own copy of the KV cache config in `initialize_from_config` (`pad_kv_cache_segments`): each layer region of a block-compact layer-outermost layout starts on that device's commit granule. This costs address space only; commits already map whole granules per segment (`physical_bytes_for`), so a defragmenting commit of any count backs each segment with exactly one chunk. Block-outermost layouts have one segment at offset 0 and are untouched. KV connectors with the extensible cache are already restricted to block-compact layouts.
- Padding is worker-local so the engine/scheduler configs keep unpadded placements: `shrink_kv_cache_configs` scales `size` by block count and scheduler-side connectors read `size // num_blocks`.
- `ExtensibleKVCache` takes the layout to derive one segment per layer region (gaps allowed) rather than inferring segments from a single stride, which can't tell padding from LHBNC head groups for small caches.
- Removed: engine-side `align_extensible_kv_cache_capacity` / `granule_aligned_kv_cache_blocks`, the `kv_cache_commit_granule` RPC, `granule_aligned_blocks` / `granule_block_alignment`, `blocks_within(aligned=)`.
- The defragmenting commit is gated on `registers_kv_cache_memory()` (#65210).

**Tradeoff/limitation.** `registers_kv_cache_memory()` is a name-based allowlist, so out-of-tree connectors loaded via `kv_connector_module_path` that register device memory no longer get one-chunk segments by default (previously any connector did). Unpadded configs (no registering connector) behave as before.
