# [Rust Frontend] Keep developer messages in place for templates without the role

[Upstream PR](https://github.com/vllm-project/vllm/pull/65294) · state: open · merged: False

## Original PR description



## Overview

When a chat template does not name the `developer` role, the Rust HF renderer (since vllm-project/vllm#63901, a port of Python's fallback from vllm-project/vllm#43590) renames developer messages to `system` and then merges every system message, developer or not, into one at the front. Codex sends its base prompt as a leading developer message and adds developer context updates mid-conversation (time reminders, model or permission changes, an image notice after tool output). Each update is moved ahead of all earlier turns, so:

- the prompt prefix changes every time an update is added, and prefix caching misses from the system message onward;
- the caller's own mid-conversation system messages move too, even when the template would render them in place;
- media in a moved message would no longer match the media order, so vllm-project/vllm#63901 rejects it with a 400.

This PR keeps developer messages where the caller put them, choosing the lowering once per compiled template.

Stacked on vllm-project/vllm#65293, whose probe harness it reuses (special tokens and default template kwargs reach the probe; a template that renders only with tools is retried with one).

## Claims

- A template that names `developer` (string check, as in Python) gets developer messages unchanged.
- Otherwise, developer messages in the leading run of system messages are merged with it into one `system` message. Nothing moves, and templates that read the system message from `messages[0]` and then require alternating turns (Llama 2, Gemma-style) accept it.
- A later developer message becomes a `system` message in place when the template renders `[system, user, assistant, system, user]` with every text (Qwen3, Qwen3-Coder).
- Otherwise it joins the adjacent user turn, the following one if any, else the previous one (Qwen3.5 raises "System message must be at the beginning.", Ministral 3 raises "Unexpected role 'system' after role 'assistant'", Mistral 7B requires alternating turns).
- The caller's own system messages are left to the template, so its own error still surfaces.
- The 400 for media in a moved developer or system message is removed; placeholders stay in media order.
- Developer messages are lowered on the chat messages, before the content format is chosen, so a request with a developer message gets the format its lowered roles call for. With Qwen3.5, a leading developer message no longer switches a user image from the template's own `<|vision_start|><|image_pad|><|vision_end|>` to string content.
- Merged content uses the new `ChatContent::append`: parts keep their order and text on both sides of the boundary is joined with a blank line, as Python merges system messages. This replaces the `TemplateContent` merge from vllm-project/vllm#63901, which merged after the format was chosen and needed a branch per format.

Codex-shaped request `[system, developer, user, assistant, developer, user]` with the real Qwen3.5 template:

| | prompt |
|---|---|
| `main` | `system: instructions\n\nbase\n\nupdate`, `user: question`, `assistant: answer`, `user: follow-up` |
| this PR | `system: instructions\n\nbase`, `user: question`, `assistant: answer`, `user: update\n\nfollow-up` |

|---|---:|---:|---:|---:|

No template that renders on the base branch fails. The 12 errors are templates that reject `system` or `developer` outright, or hit MiniJinja's `undefined|length` (Apriel). Two non-chat templates (Qwen3-Reranker, Qwen3-ASR) keep one text fewer than on the base branch, because the update now lands in a user turn they do not render; seven templates keep more. During development, this corpus caught two flaws in the first design: SGLang's probe shape `[system, user, system, user]` misses the Mistral 3 family, and relabelling a developer message as a standalone `user` message (Dynamo's approach) breaks templates that require alternating turns.

## Details

**Probe.** Runs when the template is compiled and only when the source does not name `developer`: one render, two for a template that needs tools. Per-request `chat_template` overrides are compiled and probed per request, as for vllm-project/vllm#65293.

**Python parity.** Python still consolidates every system message to the front (`vllm/renderers/hf.py`). Prompts differ from Python only for requests with developer messages on templates without the role. Porting the same lowering to Python is a follow-up.

**Cost.** Lowering clones the request's messages when the template does not name `developer` and the request has a developer message; otherwise the messages are borrowed.

**Model evaluation.** None run: the change only alters the prompt for requests with developer messages on templates that do not name the role, and the tests and corpus check those prompts directly.

Not a duplicate: open PRs on `developer` handling target the Python frontend or specific renderers (vllm-project/vllm#56391, vllm-project/vllm#64934); none changes the Rust HF renderer's fallback.
