# [Bugfix][CPU] DeepSeek-V4: return all layer types from the CPU tile scheduler

[Upstream PR](https://github.com/vllm-project/vllm/pull/65365) · state: open · merged: False

## Original PR description



## Overview

On CPUs, DeepSeek-V4 raises `KeyError: 'c1a'` at the first decode step, since #56228. Every release from v0.30.0 to v0.33.0 is affected. The CPU `build_tile_scheduler` override omits the `c1a` and `c2a` keys that the shared sparse-SWA metadata builder reads. This PR returns them with the sentinel `None`, as the base builder does, and adds a regression test. Fixes #65364.

## Claims

- DeepSeek-V4 on CPU decodes again: a decode step through `DeepseekV4CPUSparseSWAMetadataBuilder.build()` no longer raises `KeyError: 'c1a'`.
- The new test fails on main with exactly that error and passes with this change.
- The CPU kernel CI step now also triggers on `vllm/models/deepseek_v4/cpu/` and `vllm/v1/attention/backends/mla/sparse_swa.py`, so a future change on either side runs the test.

## Details

**Root cause.**
- #55355 added the CPU backend, whose `build_tile_scheduler` returns `None` for `swaonly`, `c4a` and `c128a`.
- A few hours later, #56228 (DeepSeek-V4.1) made `DeepseekSparseSWAMetadataBuilder.build()` also read `tile_sched[c1a]` and `tile_sched[c2a]` (`sparse_swa.py:790-791`), and extended the base `build_tile_scheduler` to all five types. The CPU override was not updated.
- GPUs use the base method, so only CPU fails.

**Why CI missed it.** The CPU kernel step runs `test_deepseek_v4_cpu_kernels.py`, but no existing test drives a decode step through the metadata builder. The step also did not trigger on the files involved. This PR fixes both.

**Alternative.** The override could return `super().build_tile_scheduler(0)`, which yields the base's all-`None` sentinel and would track future layer types automatically. I kept explicit keys to match the existing code; happy to switch if preferred.

**Not a duplicate.** No open issue or PR reports this (searched: DeepSeek-V4 CPU, `KeyError 'c1a'`, `build_tile_scheduler`).
