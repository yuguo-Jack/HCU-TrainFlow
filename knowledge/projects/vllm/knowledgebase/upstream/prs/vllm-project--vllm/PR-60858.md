# [CI] Enroll a fourth batch of five steps in automatic sharding

[Upstream PR](https://github.com/vllm-project/vllm/pull/60858) · state: closed · merged: True

## Original PR description

## Purpose

Fourth batch of automatic sharding (vllm-project/ci-infra#700), following #60492, #60662 and #60757. The earlier batches enrolled steps whose commands are plain pytest. Four of the five steps here have the command shapes those batches left out:

| Step | Command shape | Planned shards |
|---|---|---|
| `replayssm-e2e` | one file, 2 GPUs per shard | 3 |
| `batch-invariance-h100` | `export` and `pip install` setup, `VLLM_TEST_MODEL=...` prefixes, test IDs with `-k` | 2 |
| `distributed-dp-tests-2-gpus` | `export` setup, `TP_SIZE=... DP_SIZE=...` prefixes, 2 GPUs per shard | 2 |
| `distributed-dp-tests-4-gpus` | the same, plus a test-ID command, 4 GPUs per shard | 2 |
| `rayexecutorv2-4-gpus` | `export` setup, `-k "ray"`, a `TARGET_TEST_SUITE=...` prefix, 4 GPUs per shard | 2 |

As before, each shard runs the step's commands as written. Setup commands run in every shard, and a pytest plugin keeps only that shard's tests in each pytest command. If timings are missing or planning fails, the step runs as its usual single job. AMD mirrors inherit the flag, but the generator doesn't shard AMD steps.

Notes:
- `replayssm-e2e` is one file split by test function. The planner can cut it into only 3 parts, and one part is slightly over the 18-minute budget, so its plan annotation carries the over-budget warning. Each shard is still far shorter than the single job.
- `batch-invariance-h100` runs `test_batch_invariance.py` in three commands: the whole file, plus two test IDs under different `VLLM_TEST_MODEL` values. The plan keeps each command separate. A shard that holds none of a command's tests runs that command, deselects everything and passes.

## Test Plan

- Ran ci-infra's `runtime_shard.plan_step` against this checkout. All five steps produce the plans above, and main has timings for every file.
- Rendered each step with the pipeline generator and ran every shard's commands in `sh` against a mock test tree. Every test of every pytest command ran in exactly one shard, with the env from the step's `export` lines and command prefixes. This held both as a PR build runs the commands and with main's tracing wrapper (`pytest -p ci_otel ...`, the case fixed by vllm-project/ci-infra#754).
- This PR's CI build should show each step as parallel shard jobs with a planning annotation, and each step's test counts should match main.
