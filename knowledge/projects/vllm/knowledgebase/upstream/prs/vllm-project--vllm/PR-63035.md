# [Core][Scheduler] Bound the context a prefill step attends over

[Upstream PR](https://github.com/vllm-project/vllm/pull/63035) · state: open · merged: False

## Original PR description



## Overview

Adds `--max-num-batched-context-tokens`, an opt-in bound on the context that one step's prefill chunks attend over. Each chunk counts its request's already-computed tokens plus the tokens it prefills, summed over the step. `max_num_batched_tokens` bounds only the new tokens, so it does not bound the step time of long-context prefill.

## Claims

- New `SchedulerConfig.max_num_batched_context_tokens` (default `None`: no change in behavior).
- When set, a prefill chunk that does not fit is shortened, or left for a later step. The step's first prefill chunk is always scheduled, so every prefill keeps making progress. Decode tokens do not count.
- This bounds the cost of a prefill step when several chunks deep into long prompts land in it. With data-parallel MoE, it also bounds how long the other ranks wait for that step.

## Validation

- New tests in `tests/v1/core/test_scheduler.py`:
  - chunks deep into long prompts are shortened, then deferred, while the first chunk of each step still runs;
  - decodes do not use the budget.
- `pytest tests/v1/core/test_scheduler.py tests/engine/test_arg_utils.py` (CPU, offline): 272 passed on this branch and 270 on main, the difference being the 2 new tests. The same 81 tests fail on both, because their Hugging Face models are not cached on the test node.
- `pre-commit run` passes on the changed files.
- End-to-end benchmark: **pending**. The plan is DeepSeek-V4.1-Flash prefill instances (DEP4, B200) under the AgentX trace, comparing step-time distribution and TTFT p50/p99 with and without the bound. Results will be added here before this leaves draft.

## Details

**Motivation (measured).** We run DeepSeek-V4.1-Flash prefill instances behind Dynamo for disaggregated serving, each with DEP4 on B200. The AgentX trace has ISL p50 ~90K and p99 ~650K tokens, with ~95% prefix hits. Settings: `--max-num-batched-tokens 32768 --long-prefill-token-threshold 8192`.

The engine stats line paused for 16-18 s. py-spy during one pause:
- EngineCore was in `step_with_batch_queue`, waiting for workers.
- DP rank 0 was in `cpu_all_reduce_` (`sync_cudagraph_and_dp_padding`), waiting for the other ranks.

So one rank's prefill step took over 10 s while the others idled. The step held up to 32,768 new tokens, but each token attended over hundreds of thousands of cached tokens.

**Prior art.** DeepInfer's prefill scheduler caps each step by `max_num_batched_tokens` and also by `prefill_max_sum_seqlen_k`, the sum of the scheduled sequences' full lengths ([scheduler.hpp#L358-L447](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/csrc/engine/scheduler.hpp#L358-L447)). This PR is the same idea in the V1 scheduler. DeepInfer's production scheduler goes further: it solves chunk sizes from a per-step time budget with a fitted cost model, and takes the minimum budget across each DP group ([inference_deployment_qa.md](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/doc/inference_deployment_qa.md)).

**Relation to open PRs.**
- **#61741** shrinks one request's chunk as that request's own context grows, so its chunks cost about the same. It does not bound how many such chunks share a step: smaller chunks let `max_num_batched_tokens` pack more of them, so the step's total context is still unbounded. This PR bounds that total. The two are complementary and touch different lines.
- **#61080** (defer mode) and **#58420** (SRPF) change which prefill runs, not how much context a step carries.

**Design.**
- `_fit_prefill_context` caps `num_new_tokens` in both the running and the waiting loop. It runs after the existing token-budget and long-prefill caps, and before the Mamba-alignment, encoder and MTP-lookahead adjustments, which may shorten the chunk further.
- The step's summed context is accumulated only for scheduled prefill chunks, using their final `num_new_tokens`.
- A waiting request that does not fit stops admission (`break`, FCFS), like the token budget does.
- Padded spec-decode admissions and async KV loads are not counted.
- Enabling the bound without chunked prefill raises an error. Encoder-decoder models disable it, as they do `long_prefill_token_threshold`.
- The logic is plain integer bookkeeping, with no new CPU/GPU sync.

**Limitations.**
- The sum of context lengths is a proxy for attention cost, not a time model.
- The bound is applied per rank, without a DP-wide agreement. It still caps the worst step on every rank.
- The right value depends on the model and the attention backend.
