# [Perf] Avoid redundant tensor operations during serialization

[Upstream PR](https://github.com/vllm-project/vllm/pull/62464) · state: closed · merged: True

## Original PR description



## Overview
Reduce GIL contention in EngineCore's output thread by avoiding redundant PyTorch operations when exporting contiguous CPU tensors for serialization. This is a follow-up of sorts to #61640, has a similar motivation, and addresses a similar problem, this time in the EngineCore output thread.


## Claims
- Improve embedding throughput on short inputs by **7.5% at concurrency 128** and **2.6% at concurrency 64** on the GH200 workload below, with no request errors.
- Reduce contiguous CPU FP32 export latency from **4.61 µs to 1.10 µs** and GIL releases from **7 to 1** per call.
- Reuse `TORCH_DTYPE_TO_NUMPY_DTYPE` to export NumPy-native dtypes directly and view other dtypes as uint8, avoiding exception overhead for BF16, FP8 and packed FP4.



## Validation

Existing serialization, buffer-lifetime, and prompt-embedding hashing tests:

```bash
  tests/v1/test_serial_utils.py \
  tests/v1/core/test_kv_cache_utils.py \
  -k 'serial or prompt_embeds' -q
```


**Review-fix validation:** 84 passed, 88 deselected with the command above. Coverage includes exact dtype, shape and byte round trips for 19 tensor dtypes as scalars and matrices. All pre-commit hooks passed.

A local CPU comparison against commit `22b25cb319` (2048 elements, minimum of 5 repeats of 5000 calls) reduced export time for `float8_e4m3fnuz`, `float8_e5m2fnuz`, `float8_e8m0fnu` and `float4_e2m1fn_x2` from 14.6–14.9 µs to 2.24–2.26 µs. ## Details
The original chain releases and reacquires the GIL repeatedly even when the tensor is already contiguous and on CPU. This overhead adds contention when the output thread serializes many small tensors during concurrent serving.

The fast path exports a NumPy-backed byte memoryview directly. Membership in the existing `TORCH_DTYPE_TO_NUMPY_DTYPE` mapping identifies NumPy-native dtypes; other dtypes are viewed as uint8 before export. The mapping includes native real floating-point, integer and boolean dtypes. This preserves raw bytes without another dtype registry or unnecessary `.view()` calls for the listed native types. Noncontiguous or non-CPU tensors, and failed exports (including BF16 scalars), use the original conversion chain.
