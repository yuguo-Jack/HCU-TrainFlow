# [Perf] Avoid redundant tensor operations during serialization

[Upstream PR](https://github.com/vllm-project/vllm/pull/62464) · state: open · merged: False

## Original PR description



## Overview
Reduce GIL contention in EngineCore's output thread by avoiding redundant PyTorch operations when exporting contiguous CPU tensors for serialization. This is a follow-up of sorts to #61640, has a similar motivation, and addresses a similar problem, this time in the EngineCore output thread.


## Claims
- Improve embedding throughput on short inputs by **7.5% at concurrency 128** and **2.6% at concurrency 64** on the GH200 workload below, with no request errors.
- Reduce contiguous CPU FP32 export latency from **4.61 µs to 1.10 µs** and GIL releases from **7 to 1** per call.
- Reuse existing `EMBED_DTYPES` metadata for BF16/FP8 views and preserve the original conversion path for other inputs.



## Validation

Existing serialization, buffer-lifetime, and prompt-embedding hashing tests:

```bash
.venv/bin/python -m pytest \
  tests/utils_/test_serial_utils.py \
  tests/v1/test_serial_utils.py \
  tests/v1/core/test_kv_cache_utils.py \
  -k 'serial or prompt_embeds' -q
```


**End-to-end performance**: `nvidia/Nemotron-3-Embed-1B-BF16` (`--quantization fp8_per_tensor`,
  `--api-server-count 16`), `/v1/embeddings`, ViDoRe v3 finance-en queries (~30 tokens each),
  closed-loop client on the other NUMA node, 1× GH200, `orjson` in use. Mean of 3 × 30 s runs.

  | 64 | Throughput (req/s) | 4,482 | 4,600 | **+2.6%** |
  | 64 | p50 latency (ms) | 14.26 | 13.87 | −2.7% |
  | 64 | p99 latency (ms) | 14.97 | 15.04 | +0.5% |
  | 128 | Throughput (req/s) | 6,601 | 7,093 | **+7.5%** |
  | 128 | p50 latency (ms) | 19.37 | 18.04 | −6.9% |

  **Per call** (`tensor_data()` on a contiguous 2048-element CPU tensor):

  | float8_e4m3fn | 4.53 µs | 3.84 µs | 1.18× | — |
## Details
The original chain releases and reacquires the GIL repeatedly even when the tensor is already contiguous and on CPU. This overhead adds contention when the output thread serializes many small tensors during concurrent serving.

The fast path exports a NumPy-backed byte memoryview directly. A precomputed `torch.dtype` lookup derives only non-identity views from `EMBED_DTYPES`: BF16 is viewed as FP16, and the two supported FP8 formats as uint8. This preserves the raw bytes without maintaining another dtype list or adding unnecessary `.view()` calls for NumPy-supported formats. If NumPy export fails, serialization falls back to the original chain.
