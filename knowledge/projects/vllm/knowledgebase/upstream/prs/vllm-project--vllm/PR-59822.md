# perf: route GLM-5.2 fused-QKV-A GEMM through dsv3_fused_a_gemm on SM10x

[Upstream PR](https://github.com/vllm-project/vllm/pull/59822) · state: open · merged: False

## Original PR description

## Summary

This PR routes the GLM-5.2 (GlmMoeDsaForCausalLM) fused QKV-A projection
through the existing `min_latency_fused_qkv_a_proj` custom op backed by
`dsv3_fused_a_gemm`, eliminating the cuBLASLt split-K + splitKreduce kernel pair
at decode batch size 1. The `dsv3_fused_a_gemm` C++ kernel already supports the
GLM-5.2 fused-QKV-A shape with a warp-specialized fused-A kernel that folds the
split-K reduction inside the CTA -- the same kernel SGLang uses for this projection.
The custom op has a registered `fake_impl`, making it torch.compile-safe and CUDA-graph
capture-safe.

The core change widens `_can_use_min_latency_fused_qkv_a_gemm` to accept the
GLM-5.2 fused-QKV-A weight shape alongside the existing DeepSeek-V3 shape. This
collapses two kernel launches per layer (splitK GEMM + splitKreduce) into a single
`fused_a_gemm_kernel` launch. PDL (Programmatic Dependent Launch) is also enabled on
SM90+ for additional latency reduction at low token counts.

Because the fused-QKV-A custom-op path is frozen into the CUDA graph at capture time,
the GLM-5.2 branch is gated on the `VLLM_DISABLE_GLM52_LOW_LATENCY_GEMM`
kill switch so the feature-toggle A/B comparison captures the full benefit of this path
(the DeepSeek-V3 shape stays always-on). Without this gate the toggle only disabled the
secondary CuTe-DSL projections and the A/B delta collapsed to noise.

The GLM-5.2 low-latency GEMM module is also updated: the device capability gate is
widened from SM103-only to the full SM10x family (covering B200/SM100), the dead
`GLM52_Q_B_PROJECTION` spec is replaced with `GLM52_DENSE_GATE_UP_PROJECTION`
for the dense MLP layers, and an environment variable kill-switch is added for safe A/B
testing.

## Performance Results

## Feature Toggle

- **Environment variable**: `VLLM_DISABLE_GLM52_LOW_LATENCY_GEMM`
  - Set to `1` to disable the feature (falls back to stock `UnquantizedLinearMethod`
    -> `F.linear` -> cuBLASLt)
  - Not set or any other value: feature runs by default
- **Startup log messages**:
  - `GLM-5.2 low-latency GEMM plan is ENABLED (81 projection(s) switched)`
  - `GLM-5.2 low-latency GEMM plan is DISABLED (env override)`
  - `GLM-5.2 low-latency GEMM plan is ENABLED but no projection matched (0 switched)`
    (warning)
- The fused-qkv-a custom-op path is always-on for qualifying shapes, consistent with how
  DeepSeek-V3 already behaves in production.

File: `vllm/models/deepseek_v32/nvidia/glm52_low_latency_gemm.py` · line 42

🔴 Toggling VLLM_DISABLE_GLM52_LOW_LATENCY_GEMM between runs (the PR's own A/B workflow) can silently reuse a stale compiled graph from the prior toggle value. It is read via raw os.getenv() (glm52_low_latency_gemm.py:43, deepseek_v2.py:991) instead of being registered in vllm/envs.py, so envs.compile_factors() (vllm/compilation/caching.py:576) never hashes it into the on-disk torch.compile cache key, unlike VLLM_DISABLE_SHARED_EXPERTS_STREAM. The cache is on by default, so a graph built with the fused path on can be served after flipping the var off, or vice versa. Fix: register it in vllm/envs.py so compile_factors() hashes it.

<details>
<summary>Why this was flagged</summary>

Entry point: model init reads VLLM_DISABLE_GLM52_LOW_LATENCY_GEMM via os.getenv at glm52_low_latency_gemm.py:43 and deepseek_v2.py:991 to decide, once, whether to install the GLM-5.2 low-latency plan / fused-QKV-A path; that decision is then frozen into the torch.compile graph as described in the PR itself. vllm/compilation/caching.py:576 hashes envs.compile_factors() into the on-disk AOT compile cache key, but compile_factors() (vllm/envs.py:2311) only iterates vllm/envs.py's registered environment_variables dict. Since this new var is never added there (unlike VLLM_DISABLE_SHARED_EXPERTS_STREAM, VLLM_DISABLE_DSV4_MEGAMOE_SHARED_EXPERT_FUSION), two runs differing only in this env var hash to the same cache key, so the second run can load the first run's compiled artifact with the opposite toggle baked in. The compile cache is on by default (disabled only via VLLM_DISABLE_COMPILE_CACHE=1), so this is the default execution path.

**Verification:** VLLM_DISABLE_GLM52_LOW_LATENCY_GEMM is read via raw os.getenv at deepseek_v2.py:991 and glm52_low_latency_gemm.py:43, and is not registered in vllm/envs.py's environment_variables dict. compile_factors() (envs.py:2311) only iterates environment_variables, so the var is never hashed into the compile cache key (caching.py:576), and the compile cache is on by default.

</details>

<details>
<summary>Why this was flagged</summary>

Trigger: GLM-5.2 model loads on SM10x with VLLM_DISABLE_GLM52_LOW_LATENCY_GEMM unset (default), entry point DeepseekV32ForCausalLM.__init__ -> enable_glm52_low_latency_gemm(self, dtype) (model.py:438). But DeepSeekV2FusedQkvAProjLinear.forward() (deepseek_v2.py:1027-1038) only calls self.quant_method when self._use_min_latency_gemm is False; when True (the normal case per this PR's own _can_use_min_latency_fused_qkv_a_gemm gate at deepseek_v2.py:960-991) it instead calls torch.ops.vllm.min_latency_fused_qkv_a_proj directly, never touching quant_method. So the swap at line 253 has no runtime effect, yet is counted as 'switched' and validated by test_glm52_low_latency_wiring.py's test_enable_logs_and_installs_on_sm10x, which only checks the attribute was set on a bare mock, not that it is ever called.

**Verification:** Severity: nit; impact is cosmetic. forward() at deepseek_v2.py:1031-1036 calls torch.ops.vllm.min_latency_fused_qkv_a_proj and returns, bypassing self.quant_method, since _use_min_latency_gemm is True for shape (2624,6144) by default.
