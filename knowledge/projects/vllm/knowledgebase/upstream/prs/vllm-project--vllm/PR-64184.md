# [Core] Reject resume while executor memory is asleep

[Upstream PR](https://github.com/vllm-project/vllm/pull/64184) · state: open · merged: False

## Original PR description

## Overview

Reject explicit resume while any executor memory remains asleep, before changing scheduler or request-admission state. This is the standalone split requested by @aoshen02 in https://github.com/aoshen02/vllm/pull/184, extracted from #58183.

## Claims

- Keep scheduling paused and preserve request rejection when resume is refused.
- Retain the existing checkpoint-lifecycle guard and ordinary wake behavior.

## Validation

Main `06e172b5cf8845c80c40a6eaaecbcbde3e38e8df` versus this standalone change:

- **Before the fix — expected reproduction of the bug:** the new regression fails on unmodified main because resume does not raise while executor memory is asleep.
- **After the fix:** all **23 selected engine regressions passed**, including the new resume-while-asleep regression. There is no remaining failure in this selected suite.
- Real H20 / Qwen3-0.6B / single GPU / eager mode: after level-1 sleep, main accepted `AsyncLLM.resume_generation()` and unpaused scheduling; the fix raised the sleeping-memory error and kept scheduling paused. After ordinary wake, all 16 generated token IDs matched the pre-sleep output in both runs.
- Applicable pre-commit checks, including mypy, passed.

`.venv/bin/python -m pytest tests/v1/engine/test_engine_core.py -k "checkpoint or pause or sleep or kv_cache_release or wake_up or reject" -q -rs`

The GPU check reused existing compiled extensions and their generated FlashMLA interface; it was not a full native rebuild or a stress test. No inference was issued against sleeping memory.

### Earlier integration evidence from #58183

At `c9171d7ad9eedd77d7633d5cdb0355018ff9b29a`, the combined implementation passed all **5 opt-in GPU regression configurations** on H20: tensor parallelism (TP) 1/2/4 with peer-to-peer transport and TP2/4 with forced shared-memory transport, three cycles per configuration using Qwen3-0.6B and batch invariance. The checks covered exact output, both partial-wake orders, repeated sleep, original worker/graph identities, increased post-wake replay counts and zero new captures.

At the earlier `a2472393067b4e04e83cdb7bc3f93aa52c8a67fa` revision, real HTTP tests also covered request draining, partial wake and matching post-wake output with insecure serialization disabled.

These results from [#58183](https://github.com/vllm-project/vllm/pull/58183) provide historical sleep/wake integration coverage for the combined implementation. They were not rerun on this standalone branch and do not replace the explicit-resume regression above. This PR's current real-GPU check specifically verifies that refusing resume leaves scheduling paused and that ordinary wake still permits correct generation.

## Details

`wake_up()` already resumes only when fully awake, but explicit `resume_scheduler()` lacked the same memory check. The guard runs before scheduler state and `reject_new_requests` can change. This keeps the split to the maintainer's two files; CUDA checkpointing is separate.

Related to #48311. Broader sleep/lifecycle redesigns such as #53082 have a different scope.
