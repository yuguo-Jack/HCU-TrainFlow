# [Bugfix][Kernel] Honor batch invariance in WNA16 MoE dispatch

[Upstream PR](https://github.com/vllm-project/vllm/pull/57778) · state: closed · merged: False

## Original PR description

## Purpose

**Performance trade-off:** under `VLLM_BATCH_INVARIANT=1`, routing this WNA16
MoE shape to Triton increases median kernel latency by 8.5% for FP16 and 5.8%
for BF16 at the issue shape. In a K sweep, the slowdown grows to approximately
5.22x at K=16384. The default, non-batch-invariant path is unchanged.

Fixes #56887.

The CUDA `moe_wna16_gemm` path uses split-K atomic additions into a 16-bit
output, so its accumulation order is not deterministic. Small W4A16 MoE shapes
currently select this path even when `VLLM_BATCH_INVARIANT=1`.

This change makes `should_moe_wna16_use_cuda` honor
`VLLM_BATCH_INVARIANT`. Batch-invariant execution therefore uses the existing
Triton path, which stores each fully accumulated output element once. It also
adds:

- a focused dispatch regression test for both values of the flag; and
- a standalone H100 reproduction and benchmark script under
  `benchmarks/kernels/`.

### Duplicate-work check

No open PR references #56887. The related open PRs #46639 and #48032 address
the Marlin WNA16 MoE path (`moe_wna16_marlin_gemm` and Marlin route alignment,
respectively). This PR addresses the separate non-Marlin
`moe_wna16_gemm` split-K kernel selected by `should_moe_wna16_use_cuda`; the
fixes do not overlap.

## Test Plan

```bash
VLLM_TARGET_DEVICE=cuda .venv/bin/python -m pytest --noconftest \
  tests/kernels/moe/test_moe.py::test_wna16_cuda_respects_batch_invariance -q

pre-commit run --files \
  benchmarks/kernels/benchmark_moe_wna16_determinism.py \
  tests/kernels/moe/test_moe.py \
  vllm/model_executor/layers/fused_moe/fused_moe.py
```

On an NVIDIA H100 80GB HBM3, run the benchmark in fresh processes for CUDA and
Triton, for FP16 and BF16, with 20 warmups and 100 measured calls. Save the
first CUDA and Triton outputs and compare a second process against each saved
output. Repeat the in-process test for K in `{1024, 2048, 4096, 8192, 16384}`.

## Test Result

Environment: NVIDIA H100 80GB HBM3 (SM90), CUDA 13.0,
`torch 2.13.0+cu130`, base commit `e378275a8f20`.

- Targeted dispatch test: `2 passed`.
- Pre-commit hooks on all three changed files: passed.
- `git diff --check`: passed.

At the issue shape (`M=16`, `E=8`, `top_k=2`, `K=1024`, `N=512`,
`group_size=128`):

| dtype | CUDA, 100 calls | CUDA across processes | Triton, 100 calls | Triton across processes | max CUDA-to-CUDA diff | max Triton-to-CUDA diff | Triton/CUDA latency |
| --- | ---: | --- | ---: | --- | ---: | ---: | ---: |
| FP16 | 100 hashes, 99/99 changed | not bitwise equal | 1 hash, 0/99 changed | bitwise equal | 3.66e-4 | 2.90e-4 | 1.085x |
| BF16 | 100 hashes, 99/99 changed | not bitwise equal | 1 hash, 0/99 changed | bitwise equal | 2.93e-3 | 1.95e-3 | 1.058x |

The K sweep reproduced CUDA non-determinism at every point (100 hashes from
100 calls) and Triton determinism at every point (one hash):

| K | dtype | max CUDA-to-CUDA diff | max Triton-to-CUDA diff | diff ratio | allclose | Triton/CUDA latency |
| ---: | --- | ---: | ---: | ---: | --- | ---: |
| 1024 | FP16 | 3.66e-4 | 2.75e-4 | 0.750 | true | 1.094x |
| 1024 | BF16 | 2.93e-3 | 2.01e-3 | 0.688 | true | 1.071x |
| 2048 | FP16 | 1.22e-3 | 8.54e-4 | 0.700 | true | 1.451x |
| 2048 | BF16 | 7.81e-3 | 5.86e-3 | 0.750 | true | 1.463x |
| 4096 | FP16 | 4.88e-3 | 2.93e-3 | 0.600 | true | 2.707x |
| 4096 | BF16 | 4.69e-2 | 3.13e-2 | 0.667 | false | 2.688x |
| 8192 | FP16 | 1.56e-2 | 1.17e-2 | 0.750 | true | 4.302x |
| 8192 | BF16 | 1.25e-1 | 9.38e-2 | 0.750 | false | 4.255x |
| 16384 | FP16 | 4.69e-2 | 3.71e-2 | 0.792 | false | 5.229x |
| 16384 | BF16 | 3.75e-1 | 3.75e-1 | 1.000 | false | 5.217x |

For every tested K, the Triton-to-CUDA maximum difference is no larger than
the CUDA-to-CUDA variation measured against the same first CUDA output. Absolute
`allclose` becomes false for the larger shapes because CUDA itself moves beyond
the fixed tolerance; it is therefore reported as a diagnostic rather than used
as the acceptance criterion.

### Output evaluation

No end-to-end model evaluation was run. The affected WNA16 MoE operator was
evaluated directly at the exact issue shape and across the K sweep above. At
the issue shape, the Triton-to-CUDA maximum difference stays within the
observed CUDA run-to-run variation envelope, and the Triton result is bitwise
stable across processes.
