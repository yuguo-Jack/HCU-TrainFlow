# [Metrics][Core] Add vllm:kv_cache_blocks_by_state gauge

[Upstream PR](https://github.com/vllm-project/vllm/pull/64024) · state: open · merged: False

## Original PR description



## Overview

Add `vllm:kv_cache_blocks_by_state`, an opt-in per-engine gauge that splits the usable KV cache blocks (`num_gpu_blocks - 1`) into 9 exclusive states. `vllm:kv_cache_usage_perc` shows how full the cache is; this gauge shows what fills it: live work, stalled KV transfers, deferred frees, reclaimable prefix cache, or blocks with no owner.

## Claims

- New gauge `vllm:kv_cache_blocks_by_state{model_name, engine, state}` with states `active_shared`, `active_private`, `loading_kv`, `held_for_send`, `waiting_hold`, `pending_free`, `unattributed`, `cached_evictable`, `empty_free`. For one engine the series always sum to `num_gpu_blocks - 1`.
- Enabled by the existing `--kv-cache-metrics` flag (no new CLI flag or config field). With the flag off nothing changes: no count runs and the metric is not registered.
- Counted at most every 10 seconds while the engine is busy. When the engine goes idle after a busy count, it counts once more, and again only if the idle pool state changes (for example deferred frees drain). This stops the gauge from freezing at a busy value once `EngineCore.step` stops producing stats.
- Each count is one Python pass on the engine-core thread. Measured cost with real `KVCacheManager` objects: about 1 ms at 10k blocks, 5 ms at 50k blocks, and 17 to 21 ms at 200k blocks (see Validation).

### Cost of one count

Measured with `count_kv_cache_blocks_by_state` on real `KVCacheManager` / `BlockPool` / `Request` objects: one full-attention group, prefix caching on, block size 16, 64 blocks per request, some requests sharing an 8-block prefix. The free pool was warmed so free blocks carry a hash. Median of 15 runs on a shared 64-core host (load average 5 to 9 during the run). Absolute numbers depend on the host.

| Blocks | Idle (all free, hashed) | Half (50% owned by running requests) | Full (about 100% owned) |
| --- | --- | --- | --- |
| 10,000 | 1.0 ms | 1.2 ms | 1.3 ms |
| 50,000 | 4.4 ms | 5.1 ms | 5.6 ms |
| 200,000 | 17.3 ms | 19.6 ms | 20.5 ms |

Counts per engine: at most one every 10 seconds while busy, plus at most one each time the engine goes idle after a busy count (and one more if deferred frees drain while idle). With bursty traffic this means at most about two counts per 10 seconds, so for typical GPU pools (10k to 60k blocks) the average overhead is well under 0.1% of engine-loop time. The step that runs the count is still delayed by the amount above.

**Not run: GPU serving benchmark.** No GPU was available on the local CPU-only development machine to run `vllm bench serve` with and without `--kv-cache-metrics`; the classifier cost and end-to-end `Scheduler` -> `SchedulerStats` -> `PrometheusStatLogger.record()` -> `/metrics` pipeline were validated on CPU above.

## Details

### Where the count comes from

`Scheduler.make_stats` calls `_maybe_count_kv_cache_blocks_by_state()`, which calls the pure function `count_kv_cache_blocks_by_state()` in `vllm/v1/core/kv_cache_metrics.py`. All inputs are state the scheduler already keeps for its own correctness: `self.requests`, each single-type manager's `req_to_blocks`, `finished_recving_kv_req_ids`, `deferred_frees`, and the block pool. No new bookkeeping is added on any hot path.

Classification for each block (null block excluded):

1. Blocks in `req_to_blocks` of a request in `self.requests`, by request status:
   - `RUNNING`: `active_shared` if `ref_cnt > 1`, else `active_private`.
   - `WAITING_FOR_REMOTE_KVS` and the load has not finished: `loading_kv`.
   - Finished (the request stays in `self.requests` only while its free is delayed by a KV or EC connector): `held_for_send`.
   - Any other unfinished status (waiting or preempted while holding blocks, or the load finished but the request is not scheduled yet): `waiting_hold`.
2. Blocks in `deferred_frees` that are not already marked: `pending_free`.
3. A block with several owners takes the first matching state in the order above.
4. `unattributed` = in-use blocks minus marked blocks. `cached_evictable` = free blocks with a hash. `empty_free` = the other free blocks.

The marks go into a `bytearray` indexed by block id, so a block shared by several requests is counted once. The marked counts use `bytearray.count`, which runs in C. The only full pass over all blocks is the count of free blocks that have a hash. `BlockPool` keeps no O(1) count of those.

### Design decisions

- **9 states, not 8.** `pending_free` covers blocks in `deferred_frees` (KV consumer with async scheduling or pipeline parallelism). Their request is already deleted from `self.requests`, so without this state those blocks would show up as `unattributed` on every such P/D decode node.
- **`unattributed`, not "leak".** Copy-on-write, HiSparse, and some connectors (Mooncake store, UMBP) hold block references outside any request on purpose. The metric documentation says `unattributed` is not necessarily a leak. A value that stays non-zero on an idle engine without those features does point to leaked blocks.
- **Aborted async loads count as `held_for_send`.** After an abort, the status `WAITING_FOR_REMOTE_KVS` is overwritten with `FINISHED_ABORTED`, and nothing else separates "aborted load" from "send in flight". The docs for `held_for_send` therefore say "free waits for a connector transfer (a KV send or store, an aborted async KV load, or an EC connector transfer)". If reviewers want them split, tracking the aborted request IDs in a set costs about 4 lines in `finish_requests` and `_free_blocks`.
- **Idle sample.** `EngineCore.step` returns no stats once `has_requests()` is false, so a periodic gauge would freeze at its last busy value. When the scheduler is idle it counts whenever `(num_free_blocks, len(deferred_frees))` differs from the last idle count. That check is O(1). A one-sample-per-idle-period flag would not be enough: under async scheduling a queued batch can drain `deferred_frees` after the engine goes idle. The idle key is cleared only when a busy count is published, so the gauge never stays at a busy value once idle, and idle counts are not repeated per request at low concurrency. Idle counts do not advance the 10 s busy timer, so a burst that starts soon after an idle count still gets its busy count on time. Trade-off: if the engine goes idle again in the same `(num_free_blocks, len(deferred_frees))` state with no busy count in between, it is not recounted, so the `cached_evictable` / `empty_free` split can lag; the in-use states are still right.
- **Why a snapshot, not O(1) counters.** Counters in `BlockPool` would need updates in `allocate_slots`, `free_blocks`, `touch`, eviction, `unpin_blocks`, deferred frees, and every request status change. That touches the hot path for every user to serve an opt-in metric, and any missed transition would drift silently. The snapshot reads existing state only, costs nothing when the flag is off, and is right by construction (the sum check is built in).
- **Opt-in.** The count is O(blocks) Python on the engine-core thread, so it is gated on `--kv-cache-metrics`, the existing opt-in flag for KV cache residency metrics (HiSparse host-pool histograms also use it). The 10 s interval is a module constant (`KV_CACHE_BLOCK_STATES_INTERVAL_S`). I did not add a config field without a demonstrated need.
- **Transport.** New field `SchedulerStats.kv_cache_blocks_by_state: dict[str, int] | None = None`. `None` means "no new sample", so the bare `SchedulerStats` objects published for DP load balancing do not overwrite the gauge. The frontend sets the children only when the field is not `None`. The gauge uses `multiprocess_mode="mostrecent"` like the other scheduler gauges.
- **Scope.** Only the main device pool is counted. HiSparse host-pool blocks are skipped; host occupancy already has HiSparse metrics. Hybrid models share one pool, so all KV cache groups merge into one count. DP engines are separated by the `engine` label.
- **Name.** `vllm:kv_cache_blocks_by_state`. Some upstream count gauges use the `num_*_by_*` form (`vllm:num_requests_kv_fetch_by_stage`). I can rename to `vllm:num_kv_cache_blocks_by_state` if reviewers prefer.

### Known limitations

- Before the first request, all series read 0.
- `reset_prefix_cache` or sleep-mode calls on an idle engine produce no stats, so `cached_evictable` stays stale until the next step.
- The full-pass cost grows with pool size (about 20 ms at 200k blocks on this host). If that matters for large pools, the hashed-free count can walk the free queue instead of all blocks.
