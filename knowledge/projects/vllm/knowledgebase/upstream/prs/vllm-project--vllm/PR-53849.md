# [Feature][LoRA] Support per-module MM mappings for Granite Speech

[Upstream PR](https://github.com/vllm-project/vllm/pull/53849) · state: closed · merged: False

## Original PR description

## Purpose

Related to #31479.

This PR enables LoRA on the Granite Speech multimodal tower and connector, including the audio encoder input/attention projections, QFormer projections, and the final projector.

Granite Speech also exposed a framework limitation: different multimodal modules consume sequences with different lengths, and batched audio items can require mapping updates one item at a time. To support that without special-casing the runtime for one model, this change:

- adds optional target prefixes to `LoRAMapping`;
- lets multimodal models report per-prefix token counts;
- creates and dispatches independent Punica wrappers per multimodal prefix; and
- supports deferred, per-item multimodal LoRA mapping updates during encoder execution.

The Granite Speech implementation supplies the exact mapping lengths used by its audio encoder, QFormer self/cross attention, and projector. Existing multimodal LoRA models retain the default single-mapping behavior.

I checked the open and closed PRs linked from #31479 and searched for Granite Speech LoRA work. I did not find an existing PR for Granite Speech tower/connector LoRA; #31479 explicitly allows separate contributors to cover different models.

## Test Plan

- Focused CPU/unit coverage for the new mapping, manager dispatch, Granite Speech token accounting and native linear wrapping, per-item encoder updates, and deferred activation behavior.
- A CUDA kernel test for independent mapping lengths on replicated linear layers.
- End-to-end Granite Speech generation using Model Runner V2, two different audio durations in one batch, and a deterministic non-zero rank-8 adapter targeting the encoder, attention, QFormer cross-attention, and projector. This was exercised with both the multiprocessing executor on an RTX 3090 and the Ray V2 executor on an RTX 4090.
- A separate single-GPU Ray V2 smoke test with `distributed_executor_backend="ray"`.
- Ruff, format, `git diff --check`, and a normalized mypy comparison against the exact unmodified base commit.

## Test Result

- Focused relevant pytest suite with the repository-pinned `ray==2.56.1` installed: `20 passed, 14 warnings in 13.24s`. This includes `test_linear_replicated_supports_independent_mapping_lengths[cuda:0]`; the complete run and teardown finished cleanly.
- Granite Speech model/processing rerun: `13 passed, 14 warnings in 4.33s` (these tests overlap the focused suite above).
- Generic Ray V2 GPU E2E on an RTX 4090: passed with Ray `2.56.1`, `distributed_executor_backend="ray"`, and `Using V2 Model Runner`; Qwen2.5-0.5B loaded and generated successfully.
- Granite Speech MM LoRA E2E on an RTX 4090 with Ray `2.56.1`: passed with `distributed_executor_backend="ray"`, `Using V2 Model Runner`, and both audio items completing successfully. This exercised the actual LoRA Triton shrink/expand kernels through a Ray worker.
- Ruff check: passed on all 18 changed files.
- Ruff format check: all 18 changed files formatted.
- `git diff --check`: passed.
- The repository mypy hook remains non-zero on this base because of existing errors. A normalized comparison against the exact base found no new Granite Speech errors after the typing fix: `9` baseline errors vs. `9` patch errors, with no additions or removals.

The Granite Speech E2E runs used `ibm-granite/granite-4.0-1b-speech` at revision `bd87ab862416353633ea431fe49b1614003623c5`, BF16/eager mode, Model Runner V2, and 1.0-second plus 3.0-second audio items in the same request batch. Both the multiprocessing run on the RTX 3090 and the Ray V2 run on the RTX 4090 completed successfully. The Ray V2 result was:

```text
GRANITE_MM_LORA_E2E_OK=[{"duration_seconds": 1.0, "completion_token_ids": [2000, 6935, 29671, 100257], "text": "for timothy", "finish_reason": "stop"}, {"duration_seconds": 3.0, "completion_token_ids": [2000, 6935, 29671, 574], "text": "for timothy was", "finish_reason": "length"}]
```

The adapter is synthetic and intentionally non-zero, so these runs validate execution, mapping lengths, per-item updates, executor integration, and kernel integration rather than transcription quality. Ray validation on the RTX 4090 used a single GPU (`TP=1`); multi-GPU Ray tensor parallelism was not run on that node.
