# [MoE] Use the sorted fused-MoE path for host-resident expert weights

[Upstream PR](https://github.com/vllm-project/vllm/pull/62054) · state: open · merged: False

## Original PR description



## Overview

At small batch (`num_tokens * top_k * 4 <= num_experts`, e.g. up to 4 tokens for Qwen3 MoE) the Triton fused-MoE path skips `moe_align_block_size` and gives every (token, expert) pair its own block (#29354, #39016). That saves the alignment kernel when weights are in device memory. With UVA weight offloading (`--offload-backend uva --cpu-offload-params experts`) the expert weights are read from host memory in place, and an expert routed to several tokens is then read over PCIe once per token. This PR takes the sorted path when the expert weights carry the UVA offload marker, so each routed expert is read once per step. Device-resident weights keep the naive path.

## Claims

On RTX 4090 (PCIe 4.0 x16), natural-text chat requests, 128 output tokens:

- Qwen3-30B-A3B-Instruct-2507-FP8, one GPU, 16 GiB of experts offloaded: **+7% / +10% / +15–19% output throughput at 2 / 3 / 4 requests in flight**; unchanged at 1, 8 and 16.
- Qwen3-235B-A22B-Instruct-2507-FP8, TP8, 16 GiB per GPU offloaded: **+7% / +10% / +18% at 2 / 3 / 4**; unchanged at 1.
- Base is the vLLM 0.31.0 wheel, whose two touched files are byte-identical to the base commit. Measured on CUDA only; ROCm's Triton path takes the same branch.
- No change without offloading: the code path is the same; measured on the 30B at TP2 with weights in VRAM (one start per build).
- Quality: GSM8K (lm-eval 0.4.13, 5-shot, greedy, first 250 questions, 4 requests in flight so decode steps take the changed path), 30B with 16 GiB offloaded: 0.888 flexible / 0.880 strict exact match for both builds, and all 250 responses byte-identical.
- Output: greedy completions identical to unpatched on the 30B (all starts). On the 235B at TP8 greedy output varies from start to start *without* the patch (three unpatched starts gave three different completions and three patched starts two, with one completion common to both builds), so it cannot distinguish the builds there.

## Details

**Why.** With experts in host memory, a decode step's cost is dominated by the bytes it reads over PCIe, and on the naive path an expert routed to several of the step's tokens is read once per token. The sorted path reads each routed expert once per step. How much that saves depends on how often a step's tokens share experts: on natural-text prompts the gain is in the Validation table; on random-token prompts with greedy decoding, whose routing is far more repetitive, the same change doubles throughput at 4 requests in flight. We report natural text.

**Implementation.**

- `_prepare_expert_assignment` takes `weights_host_resident` (default `False`), which disables the naive block assignment.
- `TritonExperts.apply` and the legacy `fused_experts_impl` pass `_weights_host_resident(w1, w2)`: true when either weight has `_vllm_is_uva_offloaded`, which the UVA offloader sets (and `device_loading_context` re-sets after `process_weights_after_loading`). `w1`/`w2` are the layer's own parameters on this path, so it is a getattr per forward inside the `moe_forward` custom op; the result depends only on the parameters, so CUDA-graph capture per size is unaffected. "Either", because UVA offloads per parameter and a budget cut-off can leave w13 on the host and w2 on the device.
- Other MoE paths are unaffected: Marlin and `TritonWNA16Experts` always align; the prefetch offloader copies weights to the device before compute and never sets the marker. Two model-specific callers of `_prepare_expert_assignment` (`models/k2_horizon.py`, `models/dots3_note/nvidia/vision_moe.py`) do not pass the flag and keep today's behaviour; they can opt in separately.
- Why a per-forward check rather than a decision when the kernel is built: `replace_parameter` in `process_weights_after_loading` installs a new Parameter without the marker, and `device_loading_context` re-marks it only afterwards, so a setup-time check would read False.

**Related.** No open or merged PR makes this change (searched 2026-10-07, rechecked 2026-10-16). The naive path came from #29354 and #39016; #34920 (closed, stale) proposed making it tunable from configs; #55268 (open) warms up Triton MoE variants per batch size, and this PR changes which variant host-resident weights use at ≤ 4 tokens. #57215 (open) keeps MoE experts offloaded during weight post-processing on XPU, the marker lifecycle this PR relies on; #56177 (open) is a shared GPU expert pool. RFC #38256 discusses expert caches for offloaded MoE, where a comment reports the same effect with a GPU-side slot buffer (the naive path stops sharing an expert's weight tile between tokens at batch ≥ 2). #37190, #57794 and #57943 decide which experts stay in VRAM; this PR is independent of that and helps whichever experts remain on the host.

> Do you have any benchmarks for nvidia hardware?

Yes, all the numbers above are on RTX 4090s (Ada, PCIe 4.0 x16) with CUDA, on a 2-socket EPYC host: 30B on
one GPU and 235B at TP8, both with experts offloaded via `--offload-backend uva`.

If you meant datacenter GPUs, I don't currently have access to any. The change only affects host-resident
expert weights at 2–4 tokens per step, and how many bytes it saves depends on routing overlap rather than
on the hardware. So I'd expect PCIe hardware (H/B) to see a similar relative speedup while GB's speedup would be much lower considering how much C2C speeds up host reads relative to each step, although I haven't measured either of these.

The motivation is VRAM-limited setups like mine (consumer/workstation cards, or fewer GPUs than the model
needs), where expert offload is what allows inference to be done at all on larger MoE models; on datacenter-grade clusters I'd imagine it's mostly not relevant.
