# [Perf][Frontend] Validate plain embedding inputs before the full union

[Upstream PR](https://github.com/vllm-project/vllm/pull/65166) · state: closed · merged: True

## Original PR description



## Overview

`EmbeddingRequest` is a five-member pydantic union with no discriminator, so every `/v1/embeddings` body is validated against all five. The chat-input members (#45173) check each input item against every chat message type, so a 256×64 token-id batch spends ~66 ms in validation on the API server's event loop. This tries `EmbeddingCompletionRequest` first when `input` is not chat-shaped and the body has no chat-only field, and otherwise (or on any error) falls back to the original union.

## Claims

- Validation of plain inputs: 256×64 token ids ~66 ms → 0.28 ms, 256 strings 818 → 44 µs, 1 string 20 → 4.8 µs.
- Parsed requests, `errors()` and HTTP 400 bodies are unchanged; chat bodies take the original path (+~0.4 µs for the check).
- Reach: `/v1/embeddings` (and `run_batch`) with string or token-id input. The Rust frontend has no embeddings route.

## Validation

A/B, 15 alternated rounds, fresh process per run, validation through the route's FastAPI body field; macOS arm64, Python 3.12.7, pydantic 2.14.1:

| body | main | PR |
|---|---|---|
| 256×64 token ids | 65.6 ms | 0.28 ms |
| 32×512 token ids | 64.9 ms | 0.15 ms |
| 256 strings | 818 µs | 44 µs |
| 1 chat conversation | 32.3 µs | 32.7 µs |
| ScoreRequest (control) | 15.6 µs | 15.7 µs |

<summary>Reproduce</summary>

```python
import time
from pydantic import TypeAdapter
from vllm.entrypoints.pooling.embed.protocol import EmbeddingRequest

ta = TypeAdapter(EmbeddingRequest)
body = {"model": "m", "input": [list(range(64)) for _ in range(256)]}
ta.validate_python(body)
t = time.perf_counter()
for _ in range(20):
    ta.validate_python(body)
print(f"{(time.perf_counter() - t) / 20 * 1e3:.2f} ms")  # main 68.3, PR 0.26
```

## Details

Only the completion member can accept a non-chat `input` without `messages`, so when it validates, the result matches the union. Bodies with a chat-only field (`_CHAT_ONLY_FIELDS`, derived from `EmbeddingChatRequest.model_fields`) skip the fast path, because chat-member validators can reject them with a non-`ValidationError` (e.g. `continue_final_message` + `add_generation_prompt`). A `WrapValidator` is used instead of a `Discriminator`, which would change error `loc`s and the OpenAPI schema (`anyOf` → `oneOf`). Only cosmetic difference: `ValidationError.title` names the wrapper, visible in the first line of `run_batch` error strings.

AI assistance (Claude Opus 5.5) was used to find this target, draft the patch, and build the benchmark and identity check. I reviewed every line, re-ran the tests, and benchmarks above myself, and can answer for the change and where the perf wins come from.
