# [Rust][Benchmark] Add openai-responses backend to vllm-bench

[Upstream PR](https://github.com/vllm-project/vllm/pull/59489) · state: open · merged: False

## Original PR description

## Purpose

`vllm-bench` has no Responses API backend, so this fails on main:

```text
$ VLLM_USE_RUST_BENCH=1 vllm bench serve --backend openai-responses --endpoint /v1/responses ...
error: invalid value 'openai-responses' for '--backend <BACKEND>'
```

This ports the Python `openai-responses` backend from #54628. Reasoning deltas count toward TTFT and ITL, latency ends at the last token event, and a stream that ends without `response.completed` or `response.incomplete` fails the request. `--min-p` is rejected, matching Python. Without `--endpoint` it uses `/v1/responses`, the way the other Rust backends pick their endpoint.

Chunks are not trimmed like in the chat and completions backends, because a chunk can end between an event's `event:` and `data:` lines.

## Test Plan

```bash
cargo fmt --manifest-path rust/Cargo.toml --all -- --check
cargo clippy --manifest-path rust/Cargo.toml --workspace --all-targets --all-features --locked -- -D warnings
cargo test --manifest-path rust/Cargo.toml -p vllm-bench --locked
```

RTX 3070, `vllm serve Qwen/Qwen3-0.6B --reasoning-parser qwen3`. Python `vllm bench serve` and Rust `vllm-bench`, both with `--backend openai-responses`, alternating after one warmup, three runs each: random dataset, 512 in, 128 out, 200 prompts, concurrency 16, temperature 0, seed 42.

## Test Result

fmt and clippy are clean on macOS. Tests pass on macOS and Linux.

| | Rust | Python |
| --- | --- | --- |
| Successful requests | 200/200 | 200/200 |
| Output tokens | 25600 | 25600 |
| Output throughput (tok/s) | 1676-1680 | 1671-1673 |
| Mean TTFT (ms) | 217-222 | 219 |
| Mean TPOT (ms) | 7.60-7.63 | 7.65-7.66 |
| Median ITL (ms) | 7.32-7.34 | 7.34-7.35 |

With this branch, the `VLLM_USE_RUST_BENCH=1` command above completes 200/200 at 1676 tok/s, 219 ms mean TTFT, 7.64 ms TPOT and 7.33 ms median ITL.

A separate request at 128 output tokens streamed 127 `response.reasoning_text.delta` events and no output text, so this setup exercises the reasoning path.

The GPU runs used an earlier revision of this branch. The later changes don't affect the numbers above, and a rerun against a mock server still matches Python on success, output tokens, TPOT and ITL.

Total input tokens differ (102180 vs 104000). Like the chat and completions backends, Rust sums the dataset's prompt lengths, while Python sums the server's count, which includes the chat template. I'll fix that for all three backends in a separate PR.

**The `--min-p` check for `openai-responses` is out of date and should be removed**

After this PR's last commit, #48084 (`2ddde19e8e`, merged 2026-10-09) added `min_p` support to the Responses API:

- `ResponsesRequest` now has a `min_p` field (`vllm/entrypoints/openai/responses/protocol.py:270`), and it is passed to `SamplingParams` (`:567`).
- The same commit removed the matching `--min-p` check from the Python `vllm bench serve` (`vllm/benchmarks/serve.py`).

So the Rust check no longer matches Python. `vllm-bench --backend openai-responses --min-p 0.1` now fails at config time, even though the server would apply `min_p` and the Python bench accepts the flag.

Could you rebase onto main and:
- remove the `OpenaiResponses` + `min_p` check in `BenchConfig::from_args`,
- remove `test_responses_backend_rejects_min_p`,
- remove "`--min-p` is rejected, matching Python" from the PR description?
