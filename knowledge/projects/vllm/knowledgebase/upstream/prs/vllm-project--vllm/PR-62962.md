# [Spec Decode] Add a registry for out-of-tree speculative methods and a linear-attention verify extension

[Upstream PR](https://github.com/vllm-project/vllm/pull/62962) · state: closed · merged: False

## Original PR description

## Overview

This PR lets a plugin add a speculative decoding method to vLLM without a fork. A package registers the method from a `vllm.general_plugins` entry point, users select it by name in `--speculative-config`, and Model Runner V2 builds its speculator. On hybrid models, a registered method can also verify drafts that are not a chain (a tree, for example) in the GDN and Mamba2 layers, through a data-only `LinearAttnVerifyExtension`. **With no method registered, no new code path runs.**

```python
from vllm.v1.spec_decode.registry import SpeculativeMethodSpec, register_speculative_method

def register():  # a vllm.general_plugins entry point
    register_speculative_method(
        "my_method", SpeculativeMethodSpec(speculator_cls="my_pkg.spec:MySpeculator")
    )
```

```bash
vllm serve <target> --speculative-config '{"method": "my_method", "model": "<draft>", "method_config": {"depth": 4}}'
```

A method vLLM does not ship needs a fork today, because `SpeculativeConfig.method` is a closed `Literal`, `SpeculativeConfig` forbids extra fields, and Model Runner V2 picks the speculator in a closed if/elif chain. On hybrid models the GDN and Mamba2 layers verify speculative rows as a chain, so a tree method cannot verify there either.

This PR applies to `main` on its own. #62963 builds on it and adds the Model Runner V2 calls that a non-chain verifier also needs (a custom rejection sampler, verify-input and accepted-path hooks).

## Claims

- `register_speculative_method(name, SpeculativeMethodSpec)` makes `method=<name>` valid. Other unknown names are still rejected, and the error lists the registered ones. `method_config` is passed to the method uninterpreted and is part of `compute_hash()`. The spec's `configure` hook runs at the end of `__post_init__`, and its traits (target hidden states, auxiliary hidden states, lookahead slots) feed the places that key on the method name today.
- `init_speculator` builds the registered speculator. Registered methods select Model Runner V2, as watermarking does, and `VLLM_USE_V2_MODEL_RUNNER=0` with one raises a clear error.
- The autoregressive drafter combines auxiliary hidden states for any method whose draft model has `combine_hidden_states`, in addition to `eagle3`.
- GDN and Mamba2 layers hand their spec-decode rows to a `LinearAttnVerifyExtension` as typed zero-copy views (projections, states, gate parameters, indices, accepted counts and the output buffer). The extension replaces only the in-tree spec kernels, and the prefill and plain decode rows of mixed batches keep the in-tree path.
- `SharedExperts.disable_aux_stream()` lets a caller opt one MoE layer out of the auxiliary-stream fork and join before graph capture. It is a separate `[MoE]` commit and can move to its own PR if reviewers prefer.

Each extension point has a caller in an out-of-tree tree speculator. Its entry point registers the method, its `configure` reads `method_config` to set `num_speculative_tokens`, `num_speculative_tokens_per_batch_size` and the draft model config, and Model Runner V2 builds its `BaseSpeculator` subclass at start-up. Its EAGLE-3-style draft head reads the target's intermediate-layer hidden states as `eagle3` does. Its tree verifier runs the conv and the recurrence over the tree rows through the extension, on Qwen3.5-architecture GDN targets and on Nemotron-H-style Mamba2 hybrids, and stores each row's state for #62963's `post_accept` to commit. `disable_aux_stream()` serves speculators that capture conditional verify graphs on MoE targets with shared experts, because a conditional graph body cannot join an auxiliary stream captured outside it.

## Not a duplicate

I ran the duplicate-work searches from `AGENTS.md` §1 (open PRs, with keywords for a speculative method registry or plugin, out-of-tree speculators on Model Runner V2, tree verification on GDN and Mamba2, and the shared-experts aux stream). No open PR adds a plugin registry for speculative methods or a linear-attention verify extension. These are related, and this PR uses no code from them:

- #42910 (DDTree) adds a tree method in-tree on the V1 runner. This PR serves methods that live outside vLLM, and the two are independent.
- #60339 (suffix decoding on MRV2) and #55947 (Uno) add built-in MRV2 speculators, which keep their own selection branch.

## Details

- Registered methods run only on Model Runner V2. The V1 `custom_class` path replaces only a proposer and cannot express non-chain verification.
- The extension gets data, not the layer object. The state layout is the in-tree one (row `i` at `spec_state_indices_tensor[b, i]`, resuming from `num_accepted_tokens - 1`). An extension without Mamba2 support raises at the first Mamba2 forward instead of verifying chains, and ReplaySSM is refused with an extension because it keeps no per-row states.
- `_forward_core` copies `b` and `a` after the extension branch, and the fused-norm entry passes them in uncopied, so the extension reads the projections as strided views. #62961 moves the same copy for the other entry. The two PRs merge without conflicts, and whichever lands second drops the resulting second pair of `.contiguous()` calls.
- The extension covers Qwen GDN and Mamba2 layers. Kimi and Olmo GDN layers, and prefix caching with a registered method, are outside this PR.
