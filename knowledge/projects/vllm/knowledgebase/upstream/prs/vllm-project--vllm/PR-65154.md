# [Bugfix][XPU] Make layer_norm batch invariant under VLLM_BATCH_INVARIANT

[Upstream PR](https://github.com/vllm-project/vllm/pull/65154) · state: open · merged: False

## Original PR description

## Purpose

With `VLLM_BATCH_INVARIANT=1`, `test_batch_invariance_vlm.py` (Qwen3-VL-2B) fails on XPU: 3 of 4 requests give different logprobs at batch 1 vs batch N.

Root cause: on XPU (torch 2.14.0+xpu), native `layer_norm` uses a different reduction once a call has >= 256 rows. Rows then differ from the same rows normalized in a small batch (hidden 1024-4096, bf16/fp16/fp32, max diff 3e-5 to 1e-3). The vision encoder calls it on all patches of the batch. `enable_batch_invariant_mode()` overrides GEMMs on XPU but not `layer_norm`.

This PR registers a per-row Triton `aten::native_layer_norm` for XPU in `batch_invariant.py`, next to the existing XPU GEMM overrides, and enables the VLM test on XPU (`skip_if_not_cuda_alike` -> `skip_unsupported`). CUDA and ROCm are not affected.

The code was co-developed with Claude Code.

## Test Plan

On Arc Pro B60, torch 2.14.0+xpu:

```
cd tests/v1/determinism
VLLM_BATCH_INVARIANT=1 pytest -v test_batch_invariance_vlm.py
```

## Test Result

- main: 5 failed. This PR: 5 passed (A-B-A: override on / off / on = 5 passed / 5 failed / 5 passed).
- `test_rms_norm_batch_invariant.py`: 4 passed, 471 skipped, same as main.
- Override vs native `F.layer_norm` (4096 rows, hidden 64-8192, bf16/fp16/fp32): bitwise identical rows at batch 1 vs 8-4096; max difference to native about 1 ulp.
- Correctness: kernel vs fp64 reference: bf16/fp16 0.5 ulp (same as native XPU), fp32 <= 5.5 ulp (native 5.9). End-to-end vs an fp32 run of Qwen3-VL-2B (20 sequences x 32 greedy tokens): 552/640 tokens on the fp32 path with this PR vs 504/640 on main; max logprob difference 0.20 vs 0.31.
