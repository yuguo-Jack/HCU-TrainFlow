# [Bugfix][Parser] Keep streamed tool-call indices contiguous when a call is rejected

[Upstream PR](https://github.com/vllm-project/vllm/pull/63582) · state: open · merged: False

## Original PR description

## Overview

When the Parser Engine rejects a tool call, streaming kept emitting later calls at their raw slot index. The first valid call then streams as `index: 1`, which crashes the OpenAI SDK's stream helper and, with `parallel_tool_calls=False`, drops the call entirely. This PR streams each call at its position in the non-streaming result.

Two cases trigger the rejection: an undeclared tool name with `validate_tool_names`, and a malformed Kimi call id.

Fixes #63581.

## Claims

- Streamed `tool_calls[].index` now matches the call's position in the non-streaming result when an earlier call is rejected. In production that affects `glm47` and `minimax_m2` (undeclared tool names) and `kimi_k2` (malformed call ids). With `validate_tool_names` forced on, every engine parser in the replay suite shows the same gap: 13 parsers, including Qwen3 (see #50986). The new cross-parser test covers parsers that enable validation later.
- The OpenAI Python SDK stream helper (`ChatCompletionStreamState`) no longer raises `IndexError` on these streams.
- With `parallel_tool_calls=False`, the streamed response now contains the valid call instead of no tool call.
- No change when no call is rejected: the remap is the identity.

`TestRejectedToolCallIndex` (suggested in review by @smiyamoto3) takes each replay parser's two-call sample and declares only the second tool. It forces `validate_tool_names=True` and checks that the streamed indices are `{0}` and match `parse()`. It asserts the indices directly because `collect_output` groups calls by index and drops the index itself. That is why the existing replay tests missed the gap. `deepseek_v32` has no two-call sample, so it is not covered. The Kimi case covers the malformed-id path, which runs with validation off.

## Details

**Root cause.** The engine opens one `ToolCallSlot` per call the model starts. The delta builders (`_emit_name_delta`, `_handle_arg_chunk`, `_handle_tool_end`, and Kimi's `_handle_arg_chunk` override) all stream `index=<slot index>`. A slot whose name is rejected never sets `name_sent`, and `_build_extracted_result` skips it, so non-streaming compacts while streaming leaves a gap.

**Fix.** In `_events_to_delta`, every streamed tool-call delta passes through one place before coalescing. There, set each delta's index to the number of earlier slots with `name_sent`. This is safe because calls stream in order: when slot `i` emits, each earlier slot is already final, either sent or rejected. Internal state stays keyed by slot index; only the outgoing delta changes. `_coalesce_tool_call_deltas` merges by index, and the mapping is one-to-one on sent slots.

**Other consumers of the index** keep working: Responses API grouping (`streaming_events.py`), the Anthropic and Cohere index-to-id maps, and `maybe_filter_parallel_tool_calls`, which this fixes. All of them either key by index or expect 0-based positions.

**Interaction with #50986.** That open PR enables `validate_tool_names` for Qwen3 and adds `test_invalid_name_is_filtered_and_valid_call_keeps_raw_index`, asserting the gapped `index == 1`. With this change, that assertion would become `{0}`. I think 0 is correct, because it matches non-streaming and OpenAI clients, but I'm flagging it for whoever reviews both. cc @c5566b

**Not a duplicate.** I searched open issues and PRs for "tool call index", "validate_tool_names", "undeclared tool streaming", "kimi_k2 invalid", "rejected tool call index" and "non-contiguous index". The only related item is #50986 above, which pins the current behaviour rather than changing it.

**Limitation.** There is no `RemoteOpenAIServer` test. The affected checkpoints (GLM-4.7, MiniMax-M2, Kimi-K2) are far too large for CI or local hardware, and no small model uses a name-validating engine parser. Validation instead goes through the same `Parser.parse_delta` path the server calls, plus the real OpenAI SDK, as shown above.
