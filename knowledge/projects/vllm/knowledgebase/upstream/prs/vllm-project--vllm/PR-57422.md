# [Bugfix][KV Offload] Unlink shared mmap by inode after all ranks map

[Upstream PR](https://github.com/vllm-project/vllm/pull/57422) · state: open · merged: False

## Original PR description


Fixes a /dev/shm region leak in TieringOffloadingSpec, and a stale-generation unlink that could delete a live engine's file.

## Purpose

`/dev/shm/vllm_offload_{engine_id}.mmap` is unlinked once every process has mapped it, so a hard kill can't leak the region. Two gaps:

1. **`TieringOffloadingSpec` never dropped the name.** It maps the region in the workers *and* the scheduler, and the scheduler maps last, so nothing was positioned to unlink. The file survived every restart.
2. **Unlink targeted the path, not the file.** A stale generation shutting down late could delete the file belonging to the engine that replaced it.

Fix: `SharedOffloadRegion.unlink()` records `(st_dev, st_ino)` at map time and removes the pathname only if it still names that inode. All four unlink sites route through it. `get_manager()` calls `scheduler_mmap.unlink()` once the scheduler-side mapping exists — EngineCore builds it only after the synchronous worker `initialize_from_config` RPCs return, so every TP worker has already mapped.

Single-generation behavior is unchanged; the guard only turns a wrong unlink into a no-op.


```bash
.venv/bin/python -m pytest tests/v1/kv_offload/cpu/test_shared_offload_region.py \
                          tests/v1/kv_offload/test_factory.py -v
```

Two existing tests extended, both of which fail on `main`:

- `test_joiner_flag_not_set` — a joiner (the scheduler mapping) can drop the pathname; all mappings stay valid and coherent.
- `test_backing_file_unlinked_after_barrier` — a stale generation's `unlink()` returns `False` and leaves the replacement's inode at the path.

File: `vllm/v1/kv_offload/tiering/spec.py` · line 377

You can, where the last opener is known at construction time, which is the CPU spec's worker case. The tiering scheduler mapping is different: it has to assert it joined rather than created the region before dropping the name, and the name has to outlive the whole get_manager mapping phase so a startup failure can still abort_startup_cleanup() by path. Unlinking inside the constructor would defeat both. That's why #53073 itself passes unlink_owner=False for the scheduler mapping and keeps an explicit scheduler_mmap.unlink() in spec.py, which is the same shape as here. Since #53073 now carries the barrier and inode guard too, I'll close this PR once it lands.
