# [Quantization] Support w4afp8 checkpoints on the W4A8 FP8 MoE path

[Upstream PR](https://github.com/vllm-project/vllm/pull/64410) · state: open · merged: False

## Original PR description

## Overview

Add a `w4afp8` quantization method so SGLang-style W4AFP8 MoE checkpoints (`PhalaCloud/GLM-5.3-W4AFP8`) can be served by reusing the compressed-tensors W4A8 FP8 MoE path from #58427. Load-time layout translation only: no kernel, C++, or build changes.

## Claims

- `PhalaCloud/GLM-5.3-W4AFP8` loads and serves end-to-end on 8x H20 (TP=8 + EP=8) driven by the checkpoint's own `quant_method`, scoring GSM8K 0.9113 against the 0.911 reported for `gpustack/GLM-5.3-W4A8` in #58427.
- Routed experts reuse the Humming / CUTLASS W4A8 oracle; the on-disk differences are translated at load time (signed INT4 -> `uint4b8`, `int8` pack=2 -> `int32` pack=8, `*_scale_inv` -> `*_scale`, static `w{1,2,3}.input_scale` dropped), while dense `Linear` layers use the native `Fp8Config` block-128 path, which already expects `weight_scale_inv`.
- Core impact is `+24` additive lines in `routed_experts.py` behind a flag defaulting to `False`; no existing quantization path changes behavior.

## Validation

```bash
pytest tests/quantization/test_w4afp8.py -v      # 7 passed, CPU only

vllm serve PhalaCloud/GLM-5.3-W4AFP8 --tensor-parallel-size 8 --enable-expert-parallel --trust-remote-code --max-model-len 2048 --enforce-eager --kv-cache-dtype fp8_ds_mla --gpu-memory-utilization 0.80 --moe-backend humming

python tests/evals/gsm8k/gsm8k_eval.py --port 8000 --num-questions 1319 --num-shots 5 --max-tokens 256 --temperature 0.0 --seed 42 --max-concurrency 128
```

GSM8K, 1,319 questions, 5-shot, `temperature=0`, `seed=42`, single run per backend:

| Config | Accuracy | QPS | Output tokens/s | Baseline (#58427) |
| --- | --- | --- | --- | --- |
| `--moe-backend humming` | **0.9113** (1202/1319) | 5.07 | 489.6 | 0.911 |
| `--moe-backend cutlass` | 0.9113 (1202/1319) | 5.33 | 515.0 | n/a |

Both backends produce coherent output on English, arithmetic and Chinese prompts, every checkpoint tensor loads with no `KeyError`, and pre-commit (ruff, pyright, isort) passes on the touched files.

## Details

**Why an adapter.** Only the serialization differs, so the change is a `CompressedTensorsW4A8Fp8MoEMethod` subclass plus a `CompressedTensorsConfig` subclass. Parameters are created under the checkpoint's own names and widths so the stock expert-parameter mapping loader fills them; `process_weights_after_loading` repacks and defers to the parent, which runs the kernel-format conversion, backend selection and kernel construction unchanged. Editing the shared parent instead would put the `gpustack/GLM-5.3-W4A8` path at risk of regressions.

**Format translation.** The checkpoint stores two's-complement signed INT4, two nibbles per `int8` byte, while the kernels consume `uint4b8`; XOR-ing each byte with `0x88` adds 8 to both nibbles at once, then `view(torch.int32)` folds four bytes into one word. The repack is a pure tensor function, so it is unit-tested without a GPU.

**Static activation scales.** The W4A8 kernels recompute activation scales per token, so `w{1,2,3}.input_scale` is loaded (a parameter has to exist for the loader) and then retired via `retire_parameter`, which keeps it registered for weight reloading while hiding it from the kernels. Because it is never consumed, the fused parameter holds one scalar per expert (`[E]`) instead of ModelOpt's `[E, 2]`, which is what keeps the `routed_experts.py` change purely additive. Renamed and retired parameters follow the convention introduced in #62407 (`move_parameter` / `retire_parameter`). Layers whose expert naming does not match the config regex would silently stay unquantized, so `get_quant_method` warns in that case.

**Scope.** Group size 128 with symmetric INT4; hidden size and per-partition intermediate size must be multiples of 256; on-disk static scales are ignored by design; validated on H20 (SM90) only.

**Prior art.** #53848 (closed) attempted the same checkpoint support by integrating the conversion into the Humming fused-MoE experts; it was abandoned with unresolved merge conflicts. This PR keeps the conversion out of the kernel path and reuses the compressed-tensors W4A8 oracle instead. #49979 (closed) proposed a dedicated SM90 grouped-MoE kernel and was directed to this oracle path as well. No other open PR targets this quant method.
