# [ROCm][Perf][DSv4.1] Build the SWA decode metadata in one launch 

[Upstream PR](https://github.com/vllm-project/vllm/pull/63885) · state: closed · merged: True

## Original PR description

## Overview

With `--monokernel` on gfx950 (MI355X), DeepSeek-V4.1 decode batches of up to 32 rows now build their SWA metadata with `swa_decode_meta`'s single Triton launch (#60731). Before, they took vLLM's 8 launches per SWA group. #60731 enabled the kernel only on gfx942, but the kernel has no arch-specific code. This PR converges with #63994: it takes #63994's gate, `swa_decode_meta_enabled()` (`on_gfx942() or on_gfx950()`), and adds the gate test, the MI355 CI step and the GPU validation below.

## Claims

- **49 fewer launches per decode step at c1: 114 to 65.** That is 7 SWA groups (4 target, 3 DSpark draft), each going from 8 launches to 1. Counted in a torch-profiler trace of each arm.
- **Decode step (ITL p50): c1 -100 us (-1.75%), c2 -80 us (-1.16%).**
  - Setup: DeepSeek-V4.1-Flash, MI355X TP4, `--monokernel`, DSpark k=6 (synthetic AL 3.87, AV off), 32k in / 1k out, on `main` nightly 5d35ce3934.
  - Runs: 2 rounds with the arms' GPU halves swapped. The per-round deltas are -1.85% and -1.66% at c1, and -1.70% and -0.61% at c2.
- **Same metadata, same accuracy.**
  - On MI355X, the kernel test matches vLLM's ops.
  - With AV off, GSM8K matches base at 4 parallel requests, where every decode-only step takes the new path (6 runs per arm), and at 8 parallel (10 runs per arm).
  - Acceptance length (AL) on first passes and on passes with a per-request `cache_salt` is 3.577 in both arms.
  - With AV on (1 server per arm), GSM8K and AL match as well.
- **Unchanged:** gfx942, runs without `--monokernel`, other arches, and prefill, mixed or >32-row batches. The gate test covers arch x flag; the row and prefill guards are #60731's and untouched. There is no new flag.

## Details

**Change.** `ops.swa_decode_meta_enabled()`, the gate from #63994, returns true with `--monokernel` on ROCm when `on_gfx942()` or `on_gfx950()` holds. Only `swa_decode_meta.build` uses it. The other gfx942 helpers keep `ops.enabled()`. On gfx942 the two gates agree.

**Limits.**
- The kernel takes at most 32 rows; gfx950 mono takes up to 48.
  - With AV off at k=6, steps with 5 or more requests keep vLLM's build: the target at 35 or more rows, and the draft, which is padded to the 36-row graph. gfx942 behaves the same.
  - With AV on, the cutoff is 32 rows, not a request count.
- AV-on `--monokernel` deployments now take this path. The AV-on round served without errors and matched base on accuracy and AL.

<details>
<summary>Why the metadata is the same, and who reads it</summary>

- **What the kernel writes.** `_decode_swa_meta_kernel` is integer Triton with no arch intrinsics.
  - For rows `[0, n)` it writes `is_valid_token` and the dense window indices and lengths. It sets the lengths from row `n` to the end of the buffer to 0. It writes `indptr[:n+1]` and the ragged indices up to `indptr[n]`.
  - These are the same values that `torch.ge`, the length fill, `_compute_swa_indices_and_lens_kernel` (or `ComputeDSparkNoncausalSWAIndicesKernel` for the draft block), `build_ragged_indices_from_dense` and `_copy_ragged_to_graph_buffers` produce.
  - `build()` returns views of the same persistent buffers, with the same lengths: ragged `[:max(n*width, 1)]` and `indptr[:n+1]`.
- **Who reads it.**
  - **Mono:** with `--monokernel`, every target and DSpark-draft layer runs mono on decode-only steps of 48 rows or fewer that replay a FULL graph or run eagerly. Mono reads only the dense indices and lengths, `slot_mapping` and `token_to_req`.
  - **aiter sparse MLA:** on steps that mono declines, such as PIECEWISE steps, it (`VLLM_ROCM_USE_AITER_TRITON_SPARSE_MLA`) reads the ragged indices between `indptr[t]` and `indptr[t+1]`. It sizes its splits from the ragged view's `numel()`, which is `n*width` on both paths.
  - **Top-k build:** it reads `is_valid_token` on compressed layers.
  - Draft and target builders do not share buffers.
- **The only bytes that differ** are the ragged entries past `indptr[n]`. vLLM's build copies them from a `torch.empty` tensor; the kernel leaves the previous contents. No reader reads past `indptr`.
- **#60154** is on `main` but not in the measured image. It fuses inverse RoPE and the MXFP8 quant into the aiter sparse-MLA output, and does not change the index views that call reads. So this argument holds on current `main`.

</details>
