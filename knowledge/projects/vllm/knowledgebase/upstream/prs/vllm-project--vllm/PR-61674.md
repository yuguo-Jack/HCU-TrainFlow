# [Bugfix][KV Offload] Allow explicit SimpleCPUOffload block counts

[Upstream PR](https://github.com/vllm-project/vllm/pull/61674) · state: closed · merged: True

## Original PR description



## Overview

Allow `SimpleCPUOffloadConnector` users to set a shared `num_cpu_blocks` so uneven pipeline stages use the same offload pool size. This implements the explicit-count alternative [suggested in the review of #52921](https://github.com/vllm-project/vllm/pull/52921#pullrequestreview-5449639086).

## Claims

- The scheduler and workers honor the configured count for CPU or disk offload.
- Startup rejects nonpositive/noninteger counts and counts exceeding the local byte-derived capacity, before allocating offload buffers.
- Omitting the option retains automatic sizing. No engine-core changes, collectives, or runtime synchronization are added.

## Validation

- **116 scheduler/worker tests passed**, including 15 added regression cases. Tested current-main Python sources on a B200 using the deployed v0.30.0 compiled extensions; this was not a full current-main native build.
- **All pre-commit hooks passed**, including mypy, formatting, and CI test tethering.
- **End-to-end A/B serving:** Kimi K3, two nodes with 8 B200 GPUs each, TP8/DCP8/PP2, fp8 KV, TOKENSPEED MLA, MRV2, RDMA, no speculative decoding, 128 MiB CPU budget per rank. The same connector change was backported to the deployed v0.30.0 image for serving validation.

| Observation | Automatic sizing | Explicit `num_cpu_blocks: 23` |
|---|---:|---:|
| Scheduler / PP0 / PP1 block counts | 25 / 25 / 23 | 23 / 23 / 23 |
| Highest CPU destination ID | 24 | 22 |
| Out-of-bounds native copy calls | 40, across all 8 PP1 ranks | 0 across 1,088 copy calls |
| Nonempty streaming responses with `[DONE]` | 34/34 | 35/35 |
| Forced CPU reload after GPU prefix-cache reset | Not requested | All 16 ranks; identical 16 output tokens |

The baseline reproduced invalid copy IDs and completed its responses without a model segfault. These results establish the sizing/copy defect; they do not attribute every historical crash to it. No throughput or broad model-accuracy improvement is claimed.

## Details

Automatic sizing divides the byte budget by each stage's cache geometry independently. With uneven PP stages, the scheduler can assign IDs beyond a heavier worker's allocation; the DMA implementation forms pointers from those IDs without a bounds check. An explicit shared count limits both the scheduler's pool and each worker's allocation, with worker validation based on live tensor strides. For the disk backend, the bound is `disk_capacity_bytes`.

This is materially different from the open #52921: that PR automatically aligns counts using worker collectives and engine RPC. This PR provides the reviewer's smaller configuration-based alternative and leaves engine core untouched. It requires operators to choose a count that fits every worker and configure it identically on every rank. Recalculate it when model layout, parallelism, or speculative decoding changes; unspecified automatic sizing is not repaired by this option.
