# [Perf][Distributed] Skip movedim+reshape for dim=0 in DeviceCommunicatorBase reduce_scatter

[Upstream PR](https://github.com/vllm-project/vllm/pull/61140) · state: open · merged: False

## Original PR description

## Overview

Skip redundant `movedim` + `reshape` tensor view operations when `dim=0` in `base_device_communicator.py`'s `reduce_scatter`.

## Duplicate-work check

Sibling PRs #61136, #61138, #61139 each touch a different function in a different communicator class (`CudaCommunicator.all_gather`, `CudaCommunicator.reduce_scatter`, `DeviceCommunicatorBase.all_gather`); none overlaps with this diff. `gh pr list --search "movedim"` and `--search "base_device_communicator reduce_scatter"` turned up no other open PR touching this function.

## Performance

**Isolated microbenchmark** (the exact removed chain -- `movedim(0,0)` + `.contiguous()` on both input and output -- timed with no distributed call in the region, 2000 reps, warm-started): median delta ~2.2us/call total (~1.08us input side + ~1.13us output side), measured identically on CPU and CUDA tensors -- this is pure Python/ATen dispatch overhead, independent of device.

**Platform reachability**: `CudaCommunicator` and `XpuCommunicator` both override `reduce_scatter`, so on CUDA and XPU this base-class method is **not** reached in production. `CpuCommunicator` does **not** override `reduce_scatter`, so this fix is exercised by the CPU backend, which I do have available on this host.

**End-to-end CPU validation** (2-process gloo `reduce_scatter_tensor`, 100 trials/condition, old/new order alternated, both ranks reduced with MAX): this host is under heavy, shared load (384 cores, load average consistently 7+), and the gloo end-to-end call showed enormous call-to-call spread (e.g. the (512, 4096) shape: old median 15023us with p10-p90 of 10706-18980us; new median 14824us with p10-p90 of 9894-18860us) -- an order of magnitude larger than the ~2.2us the isolated test shows this PR saves. I could not demonstrate a clean above-noise end-to-end win on the CPU backend on this machine; the isolated-operation number is the only evidence I can stand behind for the actual saved cost.

**Applicability**: this only saves time in eager execution (the CPU backend has no graph-capture equivalent, so this applies on every call for CPU-backend users).

## Claims

- Eliminates 2 redundant `movedim` + `contiguous` calls per `reduce_scatter(dim=0)` call on the CPU backend, measured at ~2.2us/call in isolation (see Performance)

## Validation

- `ruff check` and `ruff format --check`: all passed
- When `dim=0`, `movedim(0, 0)` returns the same tensor — skipping is behavior-preserving
- Isolated microbenchmark: see Performance section above
- End-to-end CPU (gloo) run: did not show a clean signal above this host's own noise floor; reported above rather than omitted

## Details

`reduce_scatter` in `base_device_communicator.py` calls `movedim(0, dim)` and `.contiguous()` on both input and output. When `dim=0`, `movedim(0, 0)` is a no-op. Call `.contiguous()` directly and return the output without `movedim` when `dim=0`.
