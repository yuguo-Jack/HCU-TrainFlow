# [Bugfix] Tolerate NVML device query failures in startup diagnostics

[Upstream PR](https://github.com/vllm-project/vllm/pull/65020) · state: open · merged: False

## Original PR description

## Overview

Addresses #64972: an NVML error while collecting device names for the startup diagnostic can abort initialization even when the affected device is excluded by `CUDA_VISIBLE_DEVICES`.

## Claims

- Continue the diagnostic when an individual physical device's handle or name cannot be queried, and emit a deduplicated warning identifying that device.
- Preserve the mixed-device ordering warning for successfully queried devices and propagate non-NVML exceptions.

## Validation

AI-run validation on Runpod, November 2, 2026, at head `618133d2f0f564db31a80df46652ab3008e53d4a`:

- Hardware: one NVIDIA A100-SXM4-80GB, driver 595.91.07. Python 3.12.3, PyTorch 2.14.0+cu132, Transformers 5.22.0.
- Installed the PR source editable using the precompiled wheel from its exact main parent `b8c04dd3b455affd8d91f0ab436b815491c9af38`; vLLM imported from the PR checkout. No C++/CUDA source changed.
- With the current regression tests and the parent's `vllm/platforms/cuda.py`, the healthy generation case passed and the injected NVML handle-error case failed during `LLM` construction with `NVMLError_Unknown`: **1 passed, 1 failed (51.98 s)**.
- Restoring the unmodified PR file, both healthy and fault-injected real-GPU generation cases passed: **2 passed (43.81 s)**. Each loads `distilbert/distilgpt2` and requires four generated tokens; the fault case also verifies the warning and that injection occurred.
- The full related CUDA-context/NVML file passed on the same GPU: **18 passed (5.41 s)**.
- Changed-file pre-commit passed locally, including ruff, mypy and Buildkite test tethering; no files were modified by the checks.


## Details

The diagnostic enumerates physical GPUs independently of CUDA visibility. The change catches only `pynvml.NVMLError` around each device query; NVML initialization, shutdown, and unexpected exceptions retain their existing behavior.

A search for open PRs referencing #64972 and NVML `log_warnings` did not find an open PR addressing this specific diagnostic. #55481 concerns GPU memory reporting in the scheduler.
