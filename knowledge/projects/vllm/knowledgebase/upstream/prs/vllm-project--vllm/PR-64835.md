# [Perf][DSv4] Add opt-in locality placement for MegaMoE weights

[Upstream PR](https://github.com/vllm-project/vllm/pull/64835) · state: closed · merged: False

## Original PR description

## Purpose

Opt-in placement of DeepSeek-V4/V4.1 MegaMoE expert weights in the GPU memory locality domain of the SMs that read them, using DeepGEMM's existing locality allocator (`deep_gemm.locality_domain.empty_per_domain`).

```bash
vllm serve <model> --kernel-config '{"moe_backend":"deep_gemm_mega_moe"}' \
  --additional-config '{"dsv4_megamoe_localize_weights": true}'
```

- Off by default. The change is confined to DeepSeek-V4: a new `DeepseekV4LocalizedMegaMoEExperts` subclass (`vllm/models/deepseek_v4/nvidia/mega_moe.py`) that `DeepseekV4MoE` selects when `dsv4_megamoe_localize_weights` is set in `additional_config`. V4.1, DSpark and MTP draft layers share that path. The shared `DeepGemmMegaMoEExperts`, `KernelConfig` and DeepGEMM are unchanged.
- Weights are allocated directly in the `deep_gemm.localize(w, dim=-2)` layout and checkpoint shards load into it, so one copy is resident. Quantization and scales are unchanged; the forward path and kernel call are unchanged.
- The results below were measured with an earlier env-var switch. Only how the option is read changed since; allocation, loading and the kernel call are the same, so they were not rerun.
- Rejected at startup: NVFP4 experts, an unavailable allocator, sleep mode, CPU weight offloading, meta-device loading.

## Results

GB300, DeepSeek-V4.1-Flash, TP1 / DP2 / EP2, DSpark K=5, FlashInfer autotune off. Full model-forward latency (target + DSpark), not serving E2E.

| Workload | Query tokens / rank | Shapes | Mean reduction | Median | Range |
| --- | --- | ---: | ---: | ---: | ---: |
| Decode | 120–1200 | 50 | **0.544%** | 0.645% | −0.036% to +0.885% |
| Prefill | 2048–32768 | 50 | **0.869%** | 0.712% | +0.369% to +1.725% |

- All 100 shapes (600 arms) are bitwise identical to main in hidden states and draft tokens on both ranks.
- This revision moves the code into a DeepSeek-V4 subclass with the same allocation, loading and kernel call. Re-checked against the measured commit (`f1282f70c5`) on 6 decode/prefill shapes in fresh processes, three old runs per GPU pair: outputs bitwise identical, latency −0.12% to +0.18% across two GPU pairs, comparable to the old runs' own spread (up to 0.14%).
- The one negative shape, D-U02 (168 × 1 @ 1024), is −0.076% / +0.004% across the two rounds (~6 µs of 16.3 ms).

GSM8K (1319 questions, 5-shot, greedy, max 1024 tokens, prefix caching off):

| Concurrency | Main | This PR |
| --- | ---: | ---: |
| 1 | 1187 (89.992%) | 1187 (89.992%), all responses and token counts identical |
| 32 | 1202 (91.130%) | 1197 (90.751%), −0.379 pp; 371 responses identical |

C32 batches are dynamic, so outputs diverge; equal C32 accuracy is not claimed.

def partition(total, count):
    cuts = sorted(rng.sample(range(1, total), count - 1))
    return [b - a for a, b in zip([0] + cuts, cuts + [total])]

def irregular_decode(total):
    qs = []

        q = min(total, rng.choice([1, 1, 2, 3, 4, 6, 6]))
        qs.append(q)

                 chunked=bool(index % 2)) for q in partition(total, 2 + index % 7)]
