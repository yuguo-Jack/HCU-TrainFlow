# [Rust Frontend] Warn at startup when the auto tool parser cannot resolve for the model

[Upstream PR](https://github.com/vllm-project/vllm/pull/64069) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

With `vllm-rs serve`, `--tool-call-parser` defaults to `auto`. When `auto` finds no tool parser for the served model, startup is silent and every request with `tools` fails (500 today, 400 once #63843 lands). Operators only learn about it from client errors, and 400s usually don't trigger alerts. This PR logs a warning at startup in that case.

Part of #63584.

## Claims

- `vllm-rs serve` logs one warning at startup when `--tool-call-parser auto` resolves to no tool parser for the served model. The message says requests with `tools` will be rejected and how to fix it (`--tool-call-parser <name>`, or `none` to disable tool parsing explicitly).
- No warning when `auto` resolves a parser, with `--tool-call-parser none`, with an explicit parser name (already validated at startup by `validate_parser_overrides`), or for `gpt_oss` models (tool calls go through Harmony, not a tool parser).
- Request handling is unchanged.

## Validation

**Unit tests** (`rust/src/chat/src/backend/hf.rs`). Each one fails when the condition it guards is removed from `HfChatBackend::auto_tool_parser_unresolved`:

| Test | Case | Fails when |

| `auto_tool_parser_unresolved_when_auto_finds_no_parser` | `auto`, model `test-model` | the override is removed (trait default `false`) |
| `auto_tool_parser_unresolved_is_false_when_auto_finds_a_parser` | `auto`, model `Qwen/Qwen3-0.6B` | the `resolve_tool_name(..).is_none()` check is removed |
| `auto_tool_parser_unresolved_is_false_for_harmony_models` | `auto`, `model_type: gpt_oss` | the `uses_harmony()` check is removed |
| `auto_tool_parser_unresolved_is_false_when_disabled` | `none` | the `ParserSelection::Auto` check is removed |

## Details

**Where the check lives.** A new `ChatBackend::auto_tool_parser_unresolved` method has a default of `false`, like `multimodal_model_info`, so the test backends are unchanged. `HfChatBackend` answers it with the same inputs request-time resolution uses: its `model_id`, the Harmony check, and `ParserSelection::resolve_tool_name`. That keeps the startup prediction in step with what requests actually do. `build_state` only decides how to report it.

**Shared Harmony check.** `HfChatBackend::uses_harmony()` replaces the inline `model_type == "gpt_oss"` comparison, so `new_chat_output_processor` and the new check can't drift apart.

**Placement.** The check runs right after the backends load in `build_state`, before connecting to the engine, so the warning shows up early in startup logs.

**`warn!` rather than `info!`.** With this configuration, every tool request fails. Deployments that don't use tools can silence the warning with `--tool-call-parser none`.

**Out of scope.**
- Reasoning parser: an unresolvable `auto` reasoning parser disables reasoning parsing without failing requests, so it's left for a separate change.
- Suggesting `--tool-call-parser hf` at startup: the existing request-time hint from #59005 already covers models that ship a `response_template`.

**Not a duplicate.** I found no open PR adding a startup warning for this (searched for Rust frontend tool parser `auto` startup warning and PRs referencing #63584). #63843 handles the request-time 400 and doesn't overlap with this change.
