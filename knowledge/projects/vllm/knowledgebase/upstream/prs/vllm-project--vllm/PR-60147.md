# [Metrics][Frontend] Count requests that fail mid-stream

[Upstream PR](https://github.com/vllm-project/vllm/pull/60147) · state: open · merged: False

## Overview

Counts requests that fail after a streaming response has started, which are reported as HTTP 200 today, in `vllm:request_failure_total{stage="streaming"}`.

**Stacked on #60145** — only the last commit is new; the first commit is that PR. Draft until it merges.

## Claims

- An error chunk sent on a stream (tool call parser failure, engine `finish_reason=error`, late admission rejection, ...) is counted with `stage="streaming"` and the error's status code.
- A stream generator that raises after the response started is counted with `stage="streaming", code="500"`.
- Client disconnects are not counted as failures.

## Validation

Real server (`vllm serve Qwen/Qwen3-0.6B --max-num-queued-reqs 1`, one H100), three concurrent streaming requests. Two are rejected by admission control after the `200` was sent:

```
vllm:request_failure_total{code="503",model_name="Qwen/Qwen3-0.6B",stage="streaming"} 2.0
http_requests_total{handler="/v1/completions",method="POST",status="2xx"} 5.0
```

```
.venv/bin/python -m pytest tests/entrypoints/serve/middleware/test_request_failure_metrics.py tests/entrypoints/openai/chat_completion/test_chat_error.py -q
35 passed
```

New tests: a chat stream whose generator fails after the first chunk records one `streaming`/500 failure; a `StreamingResponse` whose generator raises is counted by the middleware.

## Details

**Root cause.** Once the status line is sent, a failure can only be delivered as an SSE `data:` error chunk, so `http_requests_total` sees `2xx`. Frontend-origin failures were visible only through `logger.exception`.

**Change.** `GenerateBaseServing.create_streaming_error_response` is the single helper every streaming endpoint uses to build the error chunk (chat, completions, responses, tokens-in-tokens-out, speech-to-text), so the counter is incremented there. The middleware additionally counts exceptions that escape after the response started, and excludes Starlette's `ClientDisconnect`.

**Scope note.** The stage counts every failure delivered in-stream, including engine errors that are also counted in `vllm:request_success{finished_reason="error"}`. The two counters answer different questions (what the client saw vs. how the engine finished the request).

**Not a duplicate.** Searched open PRs for `streaming error metric counter`, `frontend error metrics`; nothing overlapping.
