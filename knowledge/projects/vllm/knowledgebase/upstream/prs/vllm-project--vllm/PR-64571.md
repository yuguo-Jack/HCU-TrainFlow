# [Perf][Attention] Cache FlashAttention K/V cache views per tensor

[Upstream PR](https://github.com/vllm-project/vllm/pull/64571) · state: open · merged: False

## Original PR description

## Overview

Since #44455 (KV-cache layout refactor, v0.26), `FlashAttentionImpl` re-derives
the K/V cache views on **every** attention call: in `forward` it runs
`kv_cache.transpose(1, 2).split(head_size, dim=-1)` and then
`canonicalize_singleton_dim_strides` on both views, and in `do_kv_cache_update`
it runs the same `transpose(1, 2).split(...)`. Before #44455 this was a single
`kv_cache.unbind(1)`.

These views depend only on the per-layer `kv_cache` tensor's storage, shape and
strides, all of which are fixed once the KV cache is allocated. Under the
default `FULL_AND_PIECEWISE`, attention for prefill / mixed batches runs
eagerly, so this derivation is host time on the critical path for short
prefills. The issue (#59534) measures ~+21 µs per `unified_attention_with_output`
call on H100 (K/V view ops 11.6 µs → 17.0 µs), ~+1.35 ms per prefill step for a
64-layer model, and a 1–3.5 ms TTFT p50 regression on 8×H100 (TP=8) with short
prompts and `max_tokens=1`. Only the FA backend is affected; FlashInfer is not.

Fixes #59534.

## Claims

- The derived K/V views are now computed once per `kv_cache` tensor and reused
  on subsequent calls, removing the per-call `transpose`/`split`/canonicalize
  host work from the FA critical path.
- Output is unchanged: the cached views are byte-identical to the derivation
  they replace (same shape, strides and values).
- The cache is keyed on the `kv_cache` tensor **identity**, so it is rebuilt
  when the tensor is replaced — in particular the profiling path that binds a
  minimal KV cache, runs attention, frees it, then allocates the real cache
  never sees stale views pointing at freed memory.

## Implementation

A single `FlashAttentionImpl._get_kv_views(kv_cache, canonicalize)` helper
derives and caches the views. It caches both variants from one derivation:
`forward` needs the canonicalized views (TMA requires ≥16-byte strides on
size-1 dims), while `do_kv_cache_update` writes with a scatter op that needs no
canonicalization. The cache (`self._kv_view_cache`) is a per-impl tuple
`(kv_cache, key_raw, value_raw, key_canon, value_canon)`; the `is` identity
check rebuilds it on tensor replacement.

This mirrors existing precedent: `TritonAttentionImpl` already caches its KV
scale views in `_k_scale_cache` / `_v_scale_cache`.

Profiling memory: `_cleanup_profiling_kv_cache` frees the minimal profiling KV
cache, and holding cached views of it would keep its storage alive. The cleanup
already clears the Triton scale caches for exactly this reason, so this PR
clears `_kv_view_cache` in the same place; the identity check covers any
remaining replacement path.

## Validation

`main @ 4e0ad5720` with `VLLM_USE_PRECOMPILED=1` editable install,
torch 2.14.0+cu132, Ubuntu 24.04.

**Microbench** — host time per call (N=2000 iters after warmup, bf16 cache,

## Follow-up

The same per-call derivation exists in other eager-path backends
(line numbers @ `65ff14056`): `triton_attn.py` (L655/744/828/863, where the
FP8-KV path additionally re-runs two `view(fp8_dtype)` retypes per call —
measured 6.97–7.23 µs/call on the same box), `flex_attention.py` (L1233/1346),
`hpc_attn.py` (L443), `rocm_aiter_fa.py` (L1666), `flash_attn_diffkv.py`
(L111/193), and the trtllm path in `flashinfer.py` (L2839/2844).
`TritonAttentionImpl` already caches its KV *scale* views the same way. If this
approach lands, I'm happy to extend the caching to those backends in follow-up
PRs.

## Why this is not a duplicate

No open PR addresses the per-call K/V view derivation in `FlashAttentionImpl`.
Searched open PRs for `59534`, `_get_kv_views`, and FA `transpose(1, 2).split`
view caching — none found. The related view-caching precedent in
`TritonAttentionImpl` is existing code, not an open PR.

File: `vllm/v1/worker/gpu_model_runner.py` · line 6227

This only clears `_kv_view_cache` in V1's `_cleanup_profiling_kv_cache`. Model Runner V2 is the default, and its profiling teardown and `shutdown()` both go through `clear_layer_kv_caches` in `vllm/v1/worker/utils.py`, which only resets the scale caches. So on MRV2 each FlashAttentionImpl keeps the profiling KV tensor alive in `_kv_view_cache[0]` until the first real forward, and after shutdown it pins the real KV cache whenever the model outlives the runner. Moving the reset into `clear_layer_kv_caches` next to the scale caches would cover both paths.

Good catch, thank you — confirmed and fixed in e86d17be5.

You're right on all three points: `use_v2_model_runner` defaults to true, MRV2's teardown paths go through `clear_layer_kv_caches` (`gpu/model_runner.py` profiling teardown + `shutdown()`, and `gpu/cudagraph_utils.py`), and that helper only reset the scale caches — so the cached views kept the detached `kv_cache` tensor alive exactly as you describe.

The fix resets `_kv_view_cache` in `clear_layer_kv_caches` next to the scale caches. I kept the V1 inline reset in `_cleanup_profiling_kv_cache` as well, since V1 doesn't call the shared helper — it inlines the same pattern (the scale-cache resets are already duplicated the same way in both places), so the two stay symmetric. Also added a regression test that exercises the shared helper against a real `FlashAttentionImpl` with a populated view cache.
