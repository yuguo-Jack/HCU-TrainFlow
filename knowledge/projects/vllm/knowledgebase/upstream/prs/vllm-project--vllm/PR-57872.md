# [Feature][KVConnector][DSv4.1] Encoder-only prefill with Mooncake P/D

[Upstream PR](https://github.com/vllm-project/vllm/pull/57872) · state: open · merged: False

## Original PR description

## Purpose

Implement encoder-only Prefill for DeepSeek-V4.1-Flash P/D serving with the direct `MooncakeConnector`, following the asymmetric P/D design in RFC #57383 and the full-prompt cache-hit replay design in RFC #57738.

P executes through the L20 pre-mix boundary and produces the transferable Main KV and Indexer K. D receives those regions, replays the bounded tail through the full target, and samples the first token.

## Implementation

This PR is intentionally split into two commits:

1. `13d89a71d0` - feature implementation and streamlined tests
   - Adds `KVTransferConfig.dsv41_encoder_only_prefill` for dedicated Mooncake producer and consumer roles.
   - Adds the V4.1 execution boundary, explicit transfer profile, cache-only zero-token P completion, GPU completion event, request validation, and proxy `cache_only` handoff.
   - P runs L0-L19 plus the L20 pre-mix and canonical Main-KV/Indexer-K writes, then skips L20 attention/FFN, L21-L39, final norm, LM head, sampling, and DSpark.
   - D keeps bounded-replay state and DSpark state local. The validated D path supports DSpark K5 adaptive verification and `FULL_DECODE_ONLY` CUDA graphs.

2. `8d5b2b21c9` - Mooncake release-only pull fix
   - Bounded replay can discard a short remote hit while Mooncake still needs to release the producer blocks.
   - An empty pull has no local blocks and the consumer never enters `WAITING_FOR_REMOTE_KVS`. This commit releases the producer blocks without reporting a receive completion to the scheduler.

The current boundary is direct `MooncakeConnector`, NVIDIA, model runner V2, PP=1, no PCP or microbatching, SWA bounded replay with a 128-token window, the 40-layer V4.1-Flash topology, text-only requests, and no prompt logprobs. P requires `--no-async-scheduling` and must not configure a speculator.

Thanks for this work, @wangyicong52. I tested a small extension on two H20 nodes (TP4 + EP on each side): **physically omit the unused decoder-layer weights on the encoder-only P**, rather than only skip their forward execution.

### What I changed

- Keep L0-L19 and the full L20 boundary layer. L20 is needed for the canonical Main-KV/Indexer-K writes.
- Replace L21-L39 with `PPMissingLayer` and skip only those layers' checkpoint tensors during loading. Preserve the original 40-layer model configuration and layer names. The full D is unchanged.
- This first experiment keeps the final norm and LM head allocated; it is not an attempt to prune every unused parameter. No checkpoint files were modified.

### Memory observations

The pruned P logs **38.14 GiB of model-loading GPU memory per TP rank**, compared with **73.55 GiB** for our previous full P. Available KV-cache memory per rank increased from **41.74 to 78.05 GiB** at the same GPU-memory-utilization setting.

Important qualification: that previous P also used DSpark K5 and a different source revision. The 35.41 GiB/rank reduction therefore **must not be attributed entirely to layer pruning**. Independently, the omitted L21-L39 tensors account for **130.779 GiB of checkpoint tensor payload in total**; that is checkpoint size, not a measured CUDA allocation reduction. A same-revision, unpruned encoder-only P control is still needed for an isolated savings claim.

### Correctness and one handoff issue

On PR head `a35de2b6530349600ca040620df2b68fc81f31c7`, I also encountered a block-alignment issue during the full P-to-D handoff: an 1815-token prompt leaves 29 blocks on P, but bounded replay imports 28 full 64-token blocks on D. The existing suffix selection then chooses P blocks 1-28 instead of 0-27. Transport succeeds, but a deterministic retrieval answer was incorrect. This suffix-selection assumption is already present in the PR's base; pruning does not change it.

A local, encoder-only-scoped fix clips P's transfer metadata to the scheduler-aligned import end before applying the existing suffix selection for D-local prefix hits. The CPU descriptor regression changes from 8/12 to 12/12 passing. With that fix, **12 short, sequential PD answer checks pass**, including cold/repeated hits, streaming, aligned/unaligned lengths, partial-prefix prewarm, and a shorter-than-one-block input. These checks use separate cache salts for local-D controls and cold PD requests. They are not a long-context, concurrency, or full quality evaluation.

Would you consider producer-only weight pruning as a follow-up to this PR? It looks useful for freeing additional KV capacity on P. I can share the small pruning/alignment diffs and focused regressions if helpful.

### 1. Transfer-end alignment (correctness)

- P computes 29 blocks, including a partial tail.
- D's bounded replay imports 1792 tokens / 28 blocks.

The suffix selection itself predates this PR. I am reporting a concrete failure in this PR's new encoder-only path, **not claiming the PR introduced that line** or that every existing Mooncake request is affected. Simply replacing suffix selection with prefix selection would break partial local hits.

I observed a similar trend in separate H20 tests. These results show substantial P-side savings, but also noticeable decode regressions. They support the concern you raised, although they do not isolate cross-rank interference or quantify individual inter-token stalls.

The original motivation came partly from an issue in vLLM’s initial implementation: it replayed the SWA window on both P and D, even when P had already produced and transferred the required SWA state. Removing the P-side decoder computation therefore seemed like a natural optimization. #59197 subsequently fixed the redundant D-side replay for transfers carrying that state, leaving replay on the prefill side in that path. The tradeoff is now quite different: encoder-only prefill still needs D to reconstruct the missing state, so its additional impact on ongoing decode requests becomes much more important. I have not yet found a good way to reduce that replay overhead.

I think encoder-only prefill still has value. First, it could reduce the weights loaded on P by omitting unused decoder layers. More importantly, combining it with PP would allow more balanced pipeline partitions, and our internal tests showed larger prefill performance gains with a balanced PP2 partition. These are follow-up opportunities, though, and are outside the scope of this PR.

For the upstream version, I think we should first find a way to reduce the decode-side overhead and validate its effect on ongoing requests before moving this PR forward. If anyone has ideas for making replay less disruptive, I would be happy to discuss them.
