# [ROCm][MiniMax-M3] Keep Q and P in BF16 in the AITER sparse paged attention

[Upstream PR](https://github.com/vllm-project/vllm/pull/64172) · state: open · merged: False

## Original PR description

- sparse_pa.py: call AITER's Gluon paged attention with `compute_type=q.dtype` on an FP8 KV cache, so Q and the softmax weights stay in BF16 and only K/V are upcast from FP8.
- test_minimax_m3.py: first numerical test of the AITER sparse attention path on an FP8 cache, against fp32 attention on the dequantized cache with an error bound derived from the BF16 roundings.

With an FP8 KV cache the MiniMax-M3 ROCm sparse attention asked AITER for FP8 compute without a query scale, so the kernel rounded the BF16 query and the softmax weights to e4m3. Q's range is not the problem (on gsm8k traffic |q| stays under 14, far below 448, and a per-token query scale changes nothing); e4m3's 3-bit mantissa is. Rounding Q alone moves the attention output by 2% (median head) to 7% (median worst head per token) against an fp32 reference on the same cache. With BF16 compute the error drops to 0.2-0.3%. The kernel is 2-7% slower below about 4K rows and as fast above, which does not show end to end, and gsm8k does not move, so this improves precision and does not fix an accuracy regression.

MI355X, MiniMax-M3 at TP4 (16 query heads and 1 KV head per rank), FP8 KV cache. Before forces `compute_type` back to FP8; after is this PR. Both arms run on identical inputs.

- AndreasKaratzas · comment · 2026-11-02T20:02:38Z · [source](https://github.com/vllm-project/vllm/pull/64172#issuecomment-6587155071)

There was no issue with any test group. FP8 compute here was never a measured tradeoff. It came in with the initial AITER sparse PA (#47287), which benchmarked the whole path against Triton (BF16 Q/P) and never compared FP8 vs BF16 compute. It also passes query_scale=None, while AITER documents a query scale as required for FP8 compute. Measured now, against fp32 attention on the same FP8 cache:  
- FP8 compute: 5-6% median head error, up to 20% worst head (I did add a new test fail that demonstrates 100/100 failure)
- BF16 compute: ≤0.33% (same test has 100/100 pass rate)
- Cost: +0.8% TPOT at c=1 (~50 µs/step), flat at higher concurrency, GSM8K unchanged
 
So MiniMax-M3's own Triton sparse kernel keeps Q/P in BF16, so this path was the outlier within the model, and nobody had ever priced the trade. The new test now guards it in CI. So my gut tells me that maybe there was some aggressive optimization on perf and this setting was hardcoded, to squeeze that .8% perf boost.

- AndreasKaratzas · comment · 2026-11-03T23:15:52Z · [source](https://github.com/vllm-project/vllm/pull/64172#issuecomment-6617925456)

Ran it properly. Short version: not a bug, but fp8 Q/P does cost a bit of fidelity, consistently.

Setup: MXFP4 M3, TP4, fp8 KV, mono off. Old (fp8 Q/P) vs this PR (bf16 Q/P), plus a bf16-KV reference and repeat servers.

- Teacher-forced PG19 (24 books, prompt logprobs up to 64K, so this is the prefill call, same kernel/setting as decode): fp8 Q/P raises NLL by 0.003 nats/token at 64K (+0.3% ppl, 95% CI 0.0016-0.0046, 22/24 books), and KL to the bf16-KV reference by 0.0034 (24/24 books). For scale, fp8 KV by itself adds ~0.0017, so the fp8 cast costs roughly 2-3x what fp8 KV does. Same numbers on a second pair of fresh servers with the GPUs swapped.
- It's small next to run-to-run noise (identical runs differ at KL ~0.07 even with bf16 KV). It shows up because it goes the same way on every book, not because it's big.
- Doesn't grow with context, which makes sense since every sparse layer attends a fixed 2048 keys.
- No task-level hit: RULER NIAH at 32K+64K is ~100% on both (3 misses out of 1600, 2 of them on the bf16 side, p=1), and gsm8k was flat.

So I'd call it a precision fix, not a bug fix: closer to the reference for ~50us/step at c=1 when mono is off, no measurable accuracy change on tasks..
