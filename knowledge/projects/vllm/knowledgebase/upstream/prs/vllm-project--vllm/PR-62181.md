# [Frontend] Accept images on /v1/systemone for multimodal next-token models

[Upstream PR](https://github.com/vllm-project/vllm/pull/62181) · state: open · merged: False

## Original PR description



## Overview

`/v1/systemone` rejects `images` for models read through `NextTokenStrategy`, such as Qwen3.5, with `this model does not take image inputs`, although `NextTokenStrategy.read()` already places images ahead of the state since #60676. The strategy declares no media, so `ServingStructuredDecisions._media()` refuses the request before the read. This makes `NextTokenStrategy` accept images when the loaded model takes multimodal inputs.

No open PR changes the media `NextTokenStrategy` accepts: #60745 adds image inputs to `/v1/decisions`, and #61192, #61216 and #61251 change other parts of `strategies.py`.

## Claims

- Multimodal models on `NextTokenStrategy` (`Qwen3_5ForConditionalGeneration`, `Qwen3_5MoeForConditionalGeneration`) accept `images` on `/v1/systemone`.
- Text-only models, and multimodal models served with `--language-model-only` or zero media limits, keep rejecting images with a 400.
- `LiquidStrategy` inherits the check instead of declaring `image` itself.
- The `images` row of `docs/models/structured_decisions_models.md` lists these models.

## Validation

Served Qwen3.8-27B (`Qwen3_5ForConditionalGeneration`, TP=2) from a build carrying this commit on a slightly earlier main, whose `/v1/systemone` read path matches this branch, and sent a red 96×96 PNG with a question and its opposite:

```bash
curl -sS http://127.0.0.1:31252/v1/systemone \
  -H "Authorization: Bearer ${VLLM_API_KEY}" \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "qwen3.8-27b",
    "state": "Use the attached image as the only evidence for both questions.",
    "images": ["data:image/png;base64,<96x96 RGB (230,20,20) PNG>"],
    "questions": {
      "image_is_red": {"type": "noul", "instructions": "Is the attached square red?"},
      "image_is_blue": {"type": "noul", "instructions": "Is the attached square blue?"}
    },
    "chat_template_kwargs": {"enable_thinking": false}
  }'
```

| request | status | result |
|---|---|---|
| one red image | 200 | `image_is_red` yes 0.998, `image_is_blue` no 0.9996 |
| red then blue image, `choice` per image | 200 | first red 0.99993, second blue 0.9992 |
| text-only `state` | 200 | unchanged behavior |

The new test constructs `NextTokenStrategy` for a Qwen3.5 model config with and without multimodal input support and checks the accepted modalities.

This change and its tests were written with AI assistance; I reviewed every changed line and the validation results above.

## Details

`NextTokenStrategy` decides the media it accepts per instance, from the loaded model.

### Alternatives considered

A `MultimodalNextTokenStrategy` subclass declaring `modalities = {"image"}`, selected for multimodal models in `select_read_strategy`, would keep `modalities` a class-level declaration. It ties the accepted media to the class rather than to the loaded model, though: once `NextTokenStrategy` reads a second modality such as audio, each combination a model supports would need its own subclass. Deciding at construction from what the model accepts keeps a single strategy, and also rejects images when a multimodal model runs with `--language-model-only` or zero image limits.

- Vigilans · comment · 2026-10-19T09:37:02Z · [source](https://github.com/vllm-project/vllm/pull/62181#discussion_r4312307572)

File: `vllm/entrypoints/openai/decisions/strategies.py` · line 238

Thanks for your review! I started with exactly that `MultimodalNextTokenStrategy` subclass, then moved the check into `NextTokenStrategy` for two reasons:

- Models on `NextTokenStrategy` differ in what they take: Qwen3.5 also takes video, Gemma 4 Unified also takes audio. Once `read()` supports these modalities, the accepted set depends on the loaded model, so the subclass `modalities` can no longer be a static `ClassVar`. This PR already turns `modalities` from a `ClassVar` into an instance attribute decided at construction, though it is only empty or `{"image"}` for now.
- The image path is already in `NextTokenStrategy.read()`, which places images ahead of the text for any model; only the empty `modalities` keeps them out. Deciding the accepted media in the same class keeps the declaration next to the code that renders it.

Happy to switch to the subclass if you'd still prefer it (if you consider the tradeoff above premature).
