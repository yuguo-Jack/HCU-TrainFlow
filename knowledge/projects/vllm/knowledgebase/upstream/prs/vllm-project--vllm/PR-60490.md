# [Bugfix][Qwen4Exp] Reserve QSA indexer prefill workspace during memory profiling

[Upstream PR](https://github.com/vllm-project/vllm/pull/60490) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Reserve the Qwen4Exp QSA indexer's selection scratch (prefill logits workspace, or the worst-case decode logits,
whichever is larger) during the memory-profiling run, so the KV pool is not sized past what the indexer needs at
runtime. Fixes #60489.

## Claims

- Qwen3.8-Flash-Next (`Qwen4Exp`) no longer OOMs inside `qsa_select_paged_prefill` on the first long prefill
  when `--max-model-len` and `--gpu-memory-utilization` are high: the profiler now accounts for the indexer
  logits workspace (`VLLM_SPARSE_INDEXER_MAX_LOGITS_MB`, 512 MiB by default) plus the 1 MiB top-k workspace.
- Configurations that genuinely do not fit are rejected at startup with the existing actionable
  "estimated maximum model length" error instead of failing at request time.
- The decode path is covered too: `qsa_select_paged_decode` allocates `[decode tokens, compressed columns]` fp32
  logits on demand, which exceeds the 512 MiB prefill budget above 2048 decode tokens per step at 262K (e.g.
  `max_num_seqs` 1024 with MTP K=3). The reservation is `max(prefill budget, worst-case decode logits)` plus the
  top-k workspace, like `sparse_attn_indexer`.
- ~25 lines in the QSA profiling branch (`vllm/models/qwen4_exp/nvidia/qsa.py`); no core/runner changes.

## Validation

`Intel/Qwen3.8-Flash-Next-W4A16-AutoRound`, 4× RTX 3090 (SM86), TP=4 + EP, nightly `0.30.1rc1.dev702`
(this file set is unchanged on current `main`):

```bash
vllm serve Intel/Qwen3.8-Flash-Next-W4A16-AutoRound --tensor-parallel-size 4 --enable-expert-parallel \
  --max-model-len 262144 --gpu-memory-utilization 0.96 --max-num-batched-tokens 2048 \
  --kv-cache-dtype bfloat16 --max-num-seqs 32 --cpu-offload-gb 2 --cpu-offload-params visual
# then one ~250K-token chat request
```

| default 512 MiB indexer budget | before | after |
|---|---|---|
| Available KV memory / GPU | 3.32 GiB | 2.93 GiB (workspace accounted) |
| Startup | succeeds | fails fast: "estimated maximum model length is 236400. Try increasing `gpu_memory_utilization` …" |
| First long prefill | OOM in `qsa_select_paged_prefill` (512 MiB requested, 168 MiB free)¹ | n/a (rejected up front) |

¹ Reproduced with `--language-model-only` in place of the two offload flags (3.49 GiB KV/GPU), same OOM site.

With `VLLM_SPARSE_INDEXER_MAX_LOGITS_MB=128` the fixed build starts at 262K and the profiler's numbers hold at
runtime: a c=1/8/32 decode sweep and a 300-question GSM8K/MMLU-Pro eval run with no OOM; in a build that also
carried #60491 (fp8_e5m2 KV) and the #53981 rebase, two 250K-token passkey requests (depth 0.5 and 0.1) pass. Output is unaffected (the change only runs in the profiling branch).

Decode worst case (eager decode, no CUDA graphs, `--language-model-only`, `--max-num-seqs 128`,
`VLLM_SPARSE_INDEXER_MAX_LOGITS_MB=16` so decode dominates), instrumented with a test-only log line:

| | first commit (prefill only) | this PR |
|---|---|---|
| Reserved during profiling | 16 MiB + 1 MiB | **33,587,200 B** + 1 MiB (formula) |
| Real decode logits at runtime (128 concurrent requests) | up to 31,225,600 B (119 rows × 65,600 cols), **not reserved** | ≤ 33,587,200 B (128 × 65,600), covered |
| KV pool / c=128 load / 250K passkey | 283,825 tokens / pass | 283,825 tokens / pass (×2 runs) / pass |

The formula's worst-case width (`cdiv(max_model_len, block_size) × cdiv(block_size, compress_ratio)` = 65,600 at
262K, block size 1600) matched the runtime decode logits exactly. The old version did not OOM here (the 16 MB
shortfall fit in allocator slack); at larger `max_num_seqs` × speculative tokens the shortfall grows into
hundreds of MB. The final inlined code was re-run in the same config: identical KV pool, c=128 ×2, c=1/8/32 sweep
and a 250K passkey all pass with no OOM.

`pre-commit run --from-ref origin/main --to-ref HEAD`: all hooks pass.

No unit test added: the behaviour is the profiler's view of peak GPU memory during the dummy run, which a CPU
unit test cannot observe; CI has no Qwen3.8-Flash-Next long-context job. Validation above was done outside CI.

## Details

Root cause: the profiling dummy run carries no attention metadata, so `Qwen4ExpQSA.forward` takes the
`not isinstance(metadata, dict)` branch and returns before the indexer runs. `qsa_select_paged_prefill`
allocates its logits workspace on demand ("always allocate the worst case"), so the profiler never sees it.
The generic `sparse_attn_indexer` already handles the same situation with a dummy allocation of
`max(decode logits, prefill cap)` in its own no-metadata branch; this mirrors that inline in the QSA profiling
branch (review feedback: inlined rather than a single-use helper). QSA attention runs eagerly outside CUDA-graph
capture (`@eager_break_during_capture`), so the reservation never lands in a graph pool.

Tradeoff, by design: the KV pool shrinks by the memory the indexer really needs (~0.4 GiB/GPU here at the
default budget). Users can trade that back by lowering `VLLM_SPARSE_INDEXER_MAX_LOGITS_MB`; the indexer chunks
rows to fit. The reservation is freed immediately and only runs during profiling, so there is no steady-state
cost and no added host/device synchronization.

Duplicate check: searched open issues/PRs for the QSA indexer/profiling area (`qsa indexer`,
`VLLM_SPARSE_INDEXER_MAX_LOGITS_MB`, `qsa_select_paged_prefill`); no existing report or fix.

- nkuhn-vmw · comment · 2026-10-08T10:15:28Z · [source](https://github.com/vllm-project/vllm/pull/60490#issuecomment-6057665561)

Yes, sorry, I should have called that out when pushing. While inlining I found a second case the original reservation misses. It only covered the **prefill** logits workspace, but `qsa_select_paged_decode` also allocates on demand: `[decode tokens, compressed columns]` fp32 logits, with no chunking. At 262K with compress ratio 4 that's 256 KiB per decode token, so above 2048 decode tokens per step (e.g. `max_num_seqs` 1024 with MTP K=3) it exceeds the 512 MiB prefill reservation, and the profiler never sees it.

The reservation is now `max(prefill budget, worst-case decode logits)`, the same thing `sparse_attn_indexer`'s profiling branch does. The extra lines only compute that worst case from the scheduler/spec/cache config.

Checked on 4× RTX 3090: the computed width (65,600 columns at 262K) matched the runtime decode logits exactly, and with decode dominating, the first commit's reservation (16.8 MB) under-counted real decode allocations of 31.2 MB. Numbers are in the description.

If you'd rather keep this PR minimal, I can split the decode part into a follow-up PR. Just say which you prefer.
