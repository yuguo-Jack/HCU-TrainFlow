# [DPLB] Token-aware internal DP load balancing (DualPath)

[Upstream PR](https://github.com/vllm-project/vllm/pull/62696) · state: closed · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

This PR adds `--data-parallel-lb-policy` to the internal DP load balancer.
- `requests` is the default and keeps today's routing.
- `tokens` and `dualpath` also count each engine's tokens, not just its requests.
- `dualpath` follows the decode-engine scheduler of [DualPath](https://arxiv.org/abs/2602.21548) and balances tokens and requests together.

**Status: closed.** On the two models tested on 8x H200, neither token-aware policy gives a consistent end-to-end gain. See Results.

## Claims

- With DP attention + EP, the ranks step in lockstep, so the slowest rank sets every step. A rank's request count sets its batch size, and its tokens set its attention cost (full attention, MLA, DSA indexer/top-k, compressed attention). When request lengths vary widely, balancing request counts alone can leave some ranks with much more attention work than others. `dualpath` balances both.
- `--data-parallel-lb-policy requests` (the default) keeps today's routing. Unless a token-aware policy is selected, engines skip the token sum and the front-end skips the token bookkeeping.
- End-to-end effect on 8x H200: no consistent gain.
  - `dualpath` stays within run-to-run noise of `requests`, except +2-3% throughput at C=64/128 on DeepSeek-V4.1-Flash-1017.
  - `tokens` alone loses up to 9%.

## Results

**Setup.**
- 8x H200, DP8 + EP8, `DecodeBenchConnector`, `vllm-rs bench serve` with prompt token IDs.
- Workload: ISL ~ U[1.3K, 261K], OSL 512, N = 4 x C.
- All three policies run on one server with the same request sequence in each pass. The policy order rotates per pass, and there are 3 passes.
- KV cache is not full, except where noted.

|---|---|---|---|
| DeepSeek-V4.1-Flash-1017 (DSpark, 3 draft tokens, synthetic acceptance) | 64 | 0.967 [0.966, 1.028] | 1.028 [1.001, 1.035] |
| | 128 | 0.935 [0.932, 0.967] | 1.020 [1.015, 1.032] |
| | 256 | 1.011 [1.003, 1.059] | 1.062 [0.979, 1.067] |
| | 384 | 0.962 [0.949, 0.985] | 0.971 [0.933, 1.038] |
| | 512 | 0.913 [0.896, 0.952] | 0.989 [0.971, 1.008] |
| GLM-5.3-Flash (MTP, 3 draft tokens, synthetic acceptance) | 64 | 0.927 [0.883, 0.946] | 1.006 [0.973, 1.020] |
| | 128 | 0.999 [0.970, 1.001] | 0.999 [0.955, 1.060] |
| | 192 | 0.998 [0.941, 1.007] | 0.973 [0.956, 1.001] |

GLM-5.3-Flash at C >= 224 hits KV capacity (waiting requests, preemptions). There, every policy varies by up to +/-50% from run to run, so those rows are left out.

**Why the gain is small.**
- `dualpath` does even out per-rank context tokens. On V4.1 at C=64, the coordinator snapshots show max/mean per-rank tokens drop from 1.41 to 1.27 (median).
- But both models' decode step depends little on context length.
  - On DeepSeek-V4.1-Flash-1017 with equal per-rank load (fixed ISL, C=256, `requests`), TPOT p50 is 24.5 / 23.8 / 24.4 / 28.4 ms at 4K / 64K / 128K / 256K.
  - GLM-5.3-Flash is mostly linear attention.
- So balancing context tokens can only recover a few percent of the slowest rank's step.

**`tokens` alone is worse than `requests`.**
- It skews request counts across ranks, and with them batch sizes. On V4.1 at C=64, per-rank running max/mean is 1.40, against 1.16 for `requests`.
- At the `--max-num-seqs` limit (V4.1, C=512, 64 per rank), it also queues requests on full ranks: mean waiting is 17.6 vs 9.6, and p99 TTFT is +21%.
- `dualpath` avoids both.

## Details

**Policy (`dualpath`).** For a request with `n` prompt tokens, let `tok_e` and `req_e` be engine `e`'s token and request loads.
- Engines with a KV-bound waiting queue are skipped unless every engine has one. A KV-bound queue means waiting requests at >= 50% KV usage, the same signal the default policy already penalizes.
- With `Z = 1.05 * (sum_e tok_e + n) / E`:
  - if some engines satisfy `tok_e + n <= Z`, choose the one among them with the fewest requests;
  - otherwise, choose the engine with the fewest tokens.

Short requests therefore fill request-count gaps on token-heavy engines, and long requests go to token-light engines. DualPath additionally checks free HBM per engine; here the KV-bound-queue check stands in for it.

**Load estimate.** As for request counts today, each engine's load is the larger of the coordinator's latest snapshot and this client's in-flight load times `client_count`. The client also counts each routed request locally until the next snapshot.

**Plumbing.** `SchedulerStats.num_kv_tokens` (tokens of waiting + running requests) is published with the existing DP LB stats.
- It is computed only when a token-aware policy is selected, and only when request counts change, so the publish cadence is unchanged.
- The coordinator snapshot grows from 3 to 4 fields per engine.

**Why this is not a duplicate.**
- #40795 (token-level LB for prefill-heavy load, closed for inactivity) scored `waiting_tokens * 4 + running_tokens`. That is close to `tokens` here. `tokens` alone balances tokens but can skew request counts, and with them batch sizes; `dualpath` balances both.
- #58070 / #61386 add result-metric signals (queue time, preemptions), #43279 adds power-of-two-choices sampling, and #43483 / #52464 route for prefix-cache hits. These are orthogonal. #61386 also widens the coordinator snapshot, so the two changes would need a rebase against each other.
- SGLang has `--load-balance-method total_tokens` (fewest tokens). There is no DualPath-style two-dimensional policy in SGLang or vLLM.

**Limitations.**
- The Rust front-end (`VLLM_USE_RUST_FRONTEND=1`) keeps request-count routing; a port would be a follow-up.
- External LB mode is unaffected, since vLLM does not route between ranks there.
- Token growth during decode is reflected at the next request-count change, not every step.
