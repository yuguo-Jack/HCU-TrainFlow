# [Bugfix] Close the early-PDL completion race for small FlashInfer one-shot all-reduce calls

[Upstream PR](https://github.com/vllm-project/vllm/pull/64420) · state: open · merged: False

## Original PR description

## Overview

Correctness hardening of the FlashInfer all-reduce integration: calls with
`num_tokens <= PDL_ADVANCE_LAUNCH_TOKENS` that are dispatched to the
one-shot Lamport kernel via FlashInfer's AUTO strategy currently run with
`trigger_completion_at_end=False` — the early-PDL completion mode vLLM's own
code comment documents as a NaN race window. Related:
flashinfer-ai/flashinfer#1223.

## Claims

- Removes a documented race window: the existing comment in
  `allreduce_rms_fusion.py` states — "The one-shot Lamport all-reduce
  signals PDL completion before its output buffer is committed when
  trigger_completion_at_end is False, so the next PDL-launched kernel can
  read the uninitialized Lamport buffer and produce NaN." Today the guard
  `(use_oneshot is True) or num_tokens > PDL_ADVANCE_LAUNCH_TOKENS` closes
  it only when the ENGINE forces one-shot; when the strategy is deferred to
  FlashInfer AUTO (`use_oneshot is None` — the MNNVL path of the fused pass,
  and always in the standalone `FlashInferAllReduce` communicator), AUTO
  also selects one-shot at those sizes and the call still runs in the
  race-prone mode.
- Two-line behavior change, both call sites:
  `vllm/compilation/passes/fusion/allreduce_rms_fusion.py` →
  `(use_oneshot is not False) or num_tokens > PDL_ADVANCE_LAUNCH_TOKENS`
  (forced two-shot keeps early completion);
  `vllm/distributed/device_communicators/flashinfer_all_reduce.py` →
  `trigger_completion_at_end=True` (its above-threshold calls already
  completed at the end, so only the hazardous small-call case changes).
- Measured e2e perf-neutral, and removes multi-millisecond mid-kernel stalls
  of the affected kernel family in profiled decode windows.

## Validation

- End-to-end A/B on GB300 NVL (SM103) serves — 6 models x vLLM across 6
  concurrencies (agentic replay, 900 s windows, fixed seed), metric = p90
  normalized per-user interactivity: deltas are sign-mixed and inside the
  measured run-to-run noise band (repeated identical baselines reproduced
  p90 to +0.6% on single-node and +5.4% on 2-node topologies; an
  identical-arm control pair differed by -4.2%). An isolated split arm
  carrying ONLY this change on one serve measured -2.9% (c8) / +3.3% (c20)
  p90 vs stock — in-band, sign-mixed.
- Kernel-window evidence for the mechanism: in an Nsight Systems capture of
  a 550B-class MoE decode window on the same hardware, the quantized fused
  one-shot family ran at 2.3 ms average / 15.1% of the window under early
  completion, and 155 us average / 1.0% of the window once moved to
  completion-at-end — same kernel, same traffic, the stall is the early-PDL
  wait.
- Accuracy, stated honestly: no NaN was observed in our runs (zero request
  errors across all cells; matching output-length distributions). The hazard
  citation is vLLM's own in-tree comment — this PR removes a documented race
  window rather than fixing an observed corruption.
- Patched modules compile; behavior change is confined to the
  `trigger_completion_at_end` argument at the two call sites.

## Details

- Root cause: `_select_flashinfer_allreduce_use_oneshot` intentionally
  returns `None` for MNNVL workspaces (deferring strategy to FlashInfer
  AUTO), and the standalone communicator never sets a strategy at all. AUTO
  selects one-shot for every payload under its internal threshold — which
  includes all `num_tokens <= PDL_ADVANCE_LAUNCH_TOKENS` calls — so the
  "one-shot => complete at the end" intent of the existing guard is silently
  not honored on exactly the paths that always take one-shot.
- Trade-off: completion-at-end serializes the PDL handoff for small calls,
  foregoing the early-launch overlap. The e2e grid above shows this is not
  measurable at serve level, while the profiled stall/race mode is removed.
  Forced two-shot (`use_oneshot is False`) keeps early completion since the
  two-shot kernel is synchronized (per the existing comment).
- Limitations: measured on Blackwell-family NVL hardware with bf16/NVFP4/
  MXFP8 serves; the change is topology-agnostic by construction (it only
  tightens the completion mode for calls that can dispatch one-shot).

No — we did not observe a NaN or an accuracy failure attributable to this
window in any of our serves (6 models x 6 concurrencies, 900 s replays,
request errors 0.0% throughout). The PR is hardening, not a fix for a
failure we hit.

What we have is:

1. **The hazard is documented by vLLM's own code**: the comment in
   `allreduce_rms_fusion.py` states the one-shot Lamport kernel signals PDL
   completion before its output buffer is committed when
   `trigger_completion_at_end=False`, and the guard was written to avoid
   exactly that — it just doesn't cover the AUTO-strategy path
   (`use_oneshot is None`), which selects one-shot at the same small sizes
   and still runs in the early-completion mode. flashinfer-ai/flashinfer#1223
   is the upstream history of the same race.
2. **The race-prone configuration actually executes in production shapes**:
   profiled decode windows show the affected kernel family running under
   early completion at <=16-token calls (the Nsight capture in the
   description).
3. **Closing it is measured perf-neutral** end-to-end (in-band, sign-mixed
   deltas across all serves, including an isolated arm carrying only this
   change).

Whether the race fires depends on timing between the Lamport commit and the
next PDL-launched kernel's first read, so "we never saw it" is the expected
observation on a healthy part and not evidence of safety — the same reasoning
that led to the existing guard for the engine-forced one-shot case. If you'd
prefer this gated differently (e.g. keeping early completion behind an
explicit opt-in env), happy to rework.
