# [ROCm][MiniMax-M3] MXFP4 mode for the fused norm / RoPE / KV insert

[Upstream PR](https://github.com/vllm-project/vllm/pull/65194) · state: open · merged: False

## Original PR description

Replaces #64359, which GitHub closed when its base branch `minimax-m31-flash` was deleted after #64111 merged into main.

## Overview

Adds an MXFP4 mode to MiniMax-M3's fused FlyDSL norm / RoPE / KV insert on ROCm (gfx950). The same launch that writes NVFP4 pages can write K, V and index-K as MXFP4 pages: E2M1 data with one E8M0 scale per 32 dims and no global scale. That takes 68 B per token and head, against NVFP4's 72.

**Stacked on #64358** (the `mxfp4` KV dtype; its two commits come first here). Review the writer commit, `425d35ac5`; the rest is #64358 and merges of main.

## Changes

- `norm_rope_nvfp4_insert/kernel.py`: `compile_norm_rope_insert(..., mx=True)` swaps the scale step and the scale addresses. Norm, RoPE, the E2M1 data layout, V's octet runs and the index-q output are unchanged.
  - The scale is 2^ceil(log2(amax / 6)) from the fp32 quotient's exponent bits, clamped at 2^-126, and 2^0 for an all-zero group. It reduces over 8 lanes (32 dims) instead of 4.
  - Elements are scaled by the exact power of two, then converted with the RNE `cvt_scalef32_pk_fp4_f32` the NVFP4 path already uses.
  - Scale layout: K and index-K `[token][4]`, V `[group][token]`; per head and page, 8192 B of data plus 512 B of scales.
- `host.py`: `mxfp4=` keyword. The slot width comes from `mxfp4_kv_cache_full_dim` / `nvfp4_kv_cache_full_dim`, and `k_scale` / `v_scale` are ignored in MXFP4 mode.
- The NVFP4 path compiles to the same code as before (`mx=False`).

The readers (sparse decode / prefill and the index kernels on scaled MFMA) and the backend's `customize_spec` follow in later PRs. Nothing calls `mxfp4=True` yet.

## Validation

`tests/kernels/attention/test_minimax_m3_norm_rope_nvfp4_insert.py` runs on MI355X: **45 passed**. That's the existing 31 NVFP4 cases, plus the MXFP4 cases for the two-kernel comparison, the all-padding batch and graph replay. Every output byte is compared, stale page bytes included. The cases cover a single decode token, octet- and page-crossing runs, DSpark decode rows, unaligned prefill chunks and 4K-token prefill, at TP4 and TP1 head counts.

The reference (`minimax_m3_nvfp4_ref.py`) gains an MXFP4 quantizer written with `torch.frexp`, independent of the kernel's bit arithmetic. On CPU it matches a brute-force OCP MXFP4 quantizer on random data at three magnitudes, exact ties, all-zero groups and the 2^-126 clamp.

## Accuracy of MXFP4 KV for M3.1

The same values were emulated by rounding K, V and index-K to MXFP4 before the FP8 KV insert. Against the NVFP4-KV baseline (Quark MXFP4 experts, seed 42, paired exact McNemar): GSM8K 94.31% vs 94.31% (p = 1.0), GPQA-Diamond 83.33% vs 80.30% (p = 0.39), RULER NIAH multikey-2 32k 100% vs 100% (p = 1.0).
