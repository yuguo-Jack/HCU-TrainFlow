# [Perf][Spec Decode] Give the DFlash padding loops their own block width, 2048 -> 16 iterations

[Upstream PR](https://github.com/vllm-project/vllm/pull/58633) · state: closed · merged: False

## Original PR description

> [!IMPORTANT]
> **Scope: this is a kernel-level microbenchmark, not an end-to-end throughput claim.**
> Against a multi-millisecond decode step a change of this size sits inside
> run-to-run variation (~1% on a conc=1 arm), so **no measurable serving
> throughput improvement is claimed, and none should be inferred.** The value is
> removing work from a path that is on the critical path at low concurrency.

> [!NOTE]
> **This PR changed approach after review.** It originally split the padding into
> a second kernel to parallelise it across the grid. @okorzh-amd measured that
> the split cost more host time than it saved on device, and identified the real
> cause of the original slowness. The implementation below is her one-launch
> variant. The earlier description, and its 35.8 us figure derived from a kernel
> that no longer exists, have been replaced.

## Purpose

`_prepare_dflash_inputs_kernel` pads the unused tail of the draft-input buffers so CUDA-graph replay at a larger captured size never reads stale state or writes KV. That padding runs inside the main kernel, guarded on `req_idx == num_reqs - 1`, as serial loops whose trip counts come from the **buffer capacities**, not from the batch:

```python
for i in range(q_pad_start, max_num_tokens, BLOCK_SIZE):
    block = i + tl.arange(0, BLOCK_SIZE)
    tl.store(out_query_slot_mapping_ptr + block, PAD_SLOT_ID, mask=block < max_num_tokens)
```

`num_reqs * num_query_per_req` stays small, so that span is essentially `max_num_tokens` at **any** concurrency, and it scales the wrong way: doubling `max_num_batched_tokens` doubles the work for identical real input.

## The actual cause: block width, not serialisation

The loops reuse the **main kernel's** `BLOCK_SIZE`, which is

```python
BLOCK_SIZE = min(256, triton.next_power_of_2(max(1, max_tokens_per_req)))
```

At decode `max_tokens_per_req` is `k+1`, so **8** at spec 7. Walking a 16384-token span 8 elements at a time is **2048 iterations**:

| `max_num_batched_tokens` | BLOCK_SIZE 8 | PAD_BLOCK_SIZE 1024 |
|---|---|---|
| 8192 | 1024 iterations | 8 |
| 16384 | **2048 iterations** | **16** |
| 32768 | 4096 iterations | 32 |

A single program running 16 iterations is not a problem; one running 2048 is. That is where the time went — not from the work being confined to one workgroup.

## The change

Give the padding loops their own `PAD_BLOCK_SIZE` constexpr, sized from the padded span and capped at 1024, instead of inheriting the main kernel's decode-sized width. The padding stays in `_prepare_dflash_inputs_kernel`, now under `req_idx == num_reqs - 1 and block_idx == 0` (the main grid is 2-D, so without the second term every block of the last request would redo the padding).

No extra launch. That matters here because `prepare_dflash_inputs` is called from the per-draft-KV-group loop in `propose()`, so any added launch repeats per group per step, and K3 decode at conc 1 is sync-bound on host dispatch (#58381).

## Measurement

In situ, Kimi-K3 decode, conc 1, MI355X, `max_num_batched_tokens=16384`, PyTorch profiler trace — the baseline this PR targets:

| | |
|---|---|
| `_prepare_dflash_inputs_kernel` | **38.0 us/step** |
| samples | 48 (6 per step x 8 ranks) |
| min / max | 37.2 / 38.9 us |

**Measurements of the implemented variant are @okorzh-amd's**, on MI355X at spec 7 / 16384 tokens, per call (device / host us):

| | device | host | total |
|---|---|---|---|
| base | 65 | 31.8 | 96.8 |
| second-kernel split (earlier revision, **not** this PR) | 4.4 | 45.3 | 49.7 |
| **this PR — wide block, one launch** | **6.0** | **31.4** | **37.4** |

The split bought 1.6 us of device time for ~13.5 us of host time. The wide block recovers ~97% of the device win with host time unchanged, and is ~12 us better in total. It also avoids the prefill device regression the split caused (5.2 -> 7.7 us).

I have not re-measured the reworked version myself; the numbers above for it are hers.

## Correctness

The padding exists for CUDA-graph safety, so this was checked by simulating both versions' writes and comparing buffers elementwise rather than by arguing from the code.

- Earlier split revision: 900 configurations, 0 mismatches.
- **This revision**: the span-sized width against the original main-`BLOCK_SIZE` form, **468 shapes x 4 block widths x 9 buffers, elementwise, 0 mismatches**. Width changes how many iterations run, not what lands.
- The store set — buffer and value for all 9 buffers — diffs clean against the pre-PR block. The buffer count is 9 rather than the original 6 because this branch carries the merge with #59166, which added `input_ids`, `query_positions` and `is_padding` to the padded set.

@okorzh-amd Both correct — reproduced each one. Thanks.

### `pad_span > 0` is always true (`:835`)

Confirmed. `num_reqs <= max_num_reqs` holds throughout this path, so the first term `max_num_reqs + 1 - num_reqs` is ≥ 1, which makes `pad_span` ≥ 1 unconditionally. The `if` never guards anything and `max(1, pad_span)` at `:841` can never clamp. Both are going.

Worth noting the dead `max(1, ...)` is a leftover from the earlier `PAD_BLOCK_SIZE = 1024` version you asked about — when the size became `next_power_of_2(pad_span)` I added a guard against `pad_span == 0` without checking whether that case could occur. It can't.

### The test reimplements the launch (`test_dflash_pad_buffers.py:63`)
