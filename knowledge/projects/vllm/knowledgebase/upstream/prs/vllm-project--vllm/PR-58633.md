# [Perf][Spec Decode] Parallelise DFlash draft-input padding, saving up to 35.8us/step from one workgroup

[Upstream PR](https://github.com/vllm-project/vllm/pull/58633) · state: open · merged: False

## Original PR description

> [!IMPORTANT]
> **Scope: this is a kernel-level microbenchmark, not an end-to-end throughput claim.**
> The numbers below are measured on the isolated kernel, in the same process for both versions. Against a multi-millisecond decode step a
> change of this size sits inside run-to-run variation (~1% on a conc=1 arm), so
> **no measurable serving throughput improvement is claimed, and none should be
> inferred.** The value is removing serialized work from a single workgroup on a path that is
> on the critical path at low concurrency. Details under "Scope".

## Purpose

`_prepare_dflash_inputs_kernel` pads the unused tail of six draft-input buffers so CUDA graph replay at a larger captured size never reads stale state or writes KV. That padding ran **inside the main kernel**, guarded on `req_idx == num_reqs - 1`, as four serial loops whose trip counts come from the **buffer capacities**, not from the batch:

```python
q_pad_start = num_reqs * num_query_per_req
for i in range(q_pad_start, max_num_tokens, BLOCK_SIZE):
    block = i + tl.arange(0, BLOCK_SIZE)
    tl.store(out_query_slot_mapping_ptr + block, PAD_SLOT_ID, mask=block < max_num_tokens)
```

`num_reqs * num_query_per_req` stays small, so that span is essentially `max_num_tokens` at **any** concurrency, and a single program walks all of it. It also scales the wrong way: doubling `max_num_batched_tokens` doubles the work for identical real input.

## Measurement, and what this is expected to save

Kimi-K3 decode, concurrency 1, MI355X, `max_num_batched_tokens=16384`, from a PyTorch profiler trace:

| | |
|---|---|
| `_prepare_dflash_inputs_kernel` | **38.0 us/step** |
| samples | 48 (6 per step x 8 ranks) |
| min / max | 37.2 / 38.9 us |
| grid at this shape | **(1, 1)** |

The spread is under 5%, so this is steady state rather than a first-call artifact. At `max_num_tokens=32768` the loop is **2047 iterations in one program**.

### Serial work removed — exact, verified without a GPU

The loop bound is arithmetic, so the reduction can be stated exactly rather than
estimated. One program before; one block per program after:

| `max_num_batched_tokens` | serial iterations, 1 program | programs after | iterations per program |
|---|---|---|---|
| 8192 | 512 | 8 | 1 |
| 16384 | **1024** | 16 | **1** |
| 32768 | **2048** | 32 | **1** |

That is the concrete benefit and it does not depend on the pending GPU run: the
per-program serial work drops by the full `max_num_tokens / BLOCK_SIZE` factor,
and grows with `max_num_batched_tokens` today rather than staying flat.

### Wall-clock — measured

Isolating the padding work on one MI355X (both implementations run in the same
process, so this is a like-for-like comparison of exactly what changed), at the
production shape `num_reqs=1, num_query_per_req=6, max_num_tokens=16384`:

| | |
|---|---|
| serial padding, 1 program, 1024 iterations | **39.84 us** |
| parallel padding, 16 programs, 1 iteration each | **2.17 us** |
| **delta** | **-37.67 us (18.4x)** |

Note that the serial padding measured standalone (39.84 us) reproduces the
fused kernel measured in situ (38.0 us) to within 5%. The padding was
essentially the whole cost of that kernel, which is what the grid shape
predicted: everything else it does is for `num_reqs * num_query_per_req` = 6
tokens.

So `_prepare_dflash_inputs_kernel` should fall to a few microseconds and the new
`_pad_dflash_buffers_kernel` costs 2.17 us. Against the 38.0 us the fused kernel
cost in situ, that puts the recovery at **up to 35.8 us/step** (38.0 - 2.17),
with the true figure a little under that since the main kernel still does its
own per-token work -- call it **~34 us/step** on this configuration.

To be explicit about scope: this is a **kernel-level claim**. Against a
multi-millisecond decode step it is a fraction of a percent end-to-end, and I am
not claiming a measurable throughput change.

## The change

The padded writes are independent of each other, and disjoint from everything the main kernel stores — the main kernel writes only the `[0, num_reqs)` prefixes of these buffers, while the padding covers `[num_reqs, capacity)`. So they move to their own launch whose grid spans the padded range: **32 programs at 32768 tokens instead of one**, with a wider block since these are plain contiguous fills.

`max_num_reqs` and `max_num_tokens` were used *only* by that block, so the main kernel no longer takes them — it no longer needs to know buffer capacities at all.

## Correctness

The padding exists for CUDA-graph safety, so this was checked by simulating **both versions' writes** and comparing the buffers elementwise, rather than by arguing from the code:

```
  900 configurations, 0 mismatches
```

covering `max_num_reqs` ∈ {1, 2, 8, 64, 128}, `num_speculative_tokens` ∈ {1, 3, 6, 8}, `num_query_per_req` ∈ {1, 6, 7, 13}, `max_num_tokens` ∈ {64, 1024, 16384, 32768}, and `num_reqs` from 1 to `max_num_reqs`. Buffers start sentinel-filled so any position left unwritten would show up as a mismatch.

The grid is computed from host-side values at capture time exactly as the existing one is, so replay behaviour is unchanged.

@dllehr-amd On `PAD_BLOCK_SIZE = 1024` — you were right to ask, and there wasn't a good
answer. It was a bare constant, and inconsistent with the rule the main kernel

BLOCK_SIZE = min(256, triton.next_power_of_2(max(1, max_tokens_per_req)))

### `pad_span > 0` is always true (`:835`)

Confirmed. `num_reqs <= max_num_reqs` holds throughout this path, so the first term `max_num_reqs + 1 - num_reqs` is ≥ 1, which makes `pad_span` ≥ 1 unconditionally. The `if` never guards anything and `max(1, pad_span)` at `:841` can never clamp. Both are going.

Worth noting the dead `max(1, ...)` is a leftover from the earlier `PAD_BLOCK_SIZE = 1024` version you asked about — when the size became `next_power_of_2(pad_span)` I added a guard against `pad_span == 0` without checking whether that case could occur. It can't.

### The test reimplements the launch (`test_dflash_pad_buffers.py:63`)

You're right, and this is the more important of the two. `_launch()` carries its own copy of the `pad_span` formula, the grid and the block size, and the module imports `_pad_dflash_buffers_kernel` but never `prepare_dflash_inputs`. The fix is the one your comment implies: `test_dflash_prepare_inputs.py` already drives the real `prepare_dflash_inputs`, it just stops at `[:3]` / `[:4]` — the head of each buffer. The tail assertions belong there, against the real launcher, rather than in a separate file that re-derives the arithmetic. I'll move them and drop the reimplementing helper, keeping the sentinel-prefill idea since that part is what makes an unwritten tail visible.
