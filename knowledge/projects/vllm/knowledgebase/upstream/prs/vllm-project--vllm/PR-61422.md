# [Perf] Share Triton JIT warmup compilation pool across registered kernels

[Upstream PR](https://github.com/vllm-project/vllm/pull/61422) · state: closed · merged: True

## Original PR description

## Overview

Follow-up to #58582. Eligible Triton kernels now share one `AsyncCompileMode` pool during startup warmup, instead of each kernel draining its own pool in turn.

## Claims

- Compilation now overlaps across kernels, not just within one kernel. Single-key kernels previously always compiled serially.
- 9–12% faster cold JIT warmup at default threads, 23–28% at 16 threads, when several Triton warmup kernels are registered (MRV1 sampler/spec-decode kernels, DSv4, GLM-5 Next).
- No change for ROCm, autotuned kernels, non-Triton owners, or configs with a single registered kernel.

## Validation

`pytest tests/model_executor/test_jit_warmup_triton_launcher.py`: 15 passed. The updated test (two single-key kernels must compile concurrently) fails on the base commit.

Cold-cache `JIT kernel warmup finished in …s` on H100, `VLLM_USE_V2_MODEL_RUNNER=0`, mean of 3 runs per arm:

| Config | Threads | Before | After |
|---|---|---|---|
| Gemma 4 31B + EAGLE3, TP=8 (12 kernels) | 4 | 20.72s | 18.86s (−9%) |
| | 16 | 15.25s | 11.69s (−23%) |
| Qwen3-0.6B-FP8 + ngram (9 kernels) | 4 | 17.99s | 15.89s (−12%) |
| | 16 | 11.55s | 8.37s (−28%) |

Gemma 4 on default MRV2 registers only the FA4 kernel, so there's nothing to overlap: 5.74s → 5.73s. No model evals: only compile scheduling changes, not the compiled kernels.

## Details

`JitWarmupRegistry.warmup()` runs all kernels with `supports_parallel_compile` inside one `compile_triton_warmup()` pool, then the rest serially. A ContextVar stops `compile_many` from nesting pools; called directly, it still creates its own pool. Dispatch stays on the calling thread, as in #58582.

Limitations:
- The tqdm bar advances on dispatch, so it jumps ahead and then waits for the pool to drain.
- Compile errors surface when the shared pool exits, not inside the failing kernel's `compile_many`.

Not a duplicate: no open PR shares a pool across kernels. #56154 (compile-key derivation) and #56761 (TileLang) are the closest.
