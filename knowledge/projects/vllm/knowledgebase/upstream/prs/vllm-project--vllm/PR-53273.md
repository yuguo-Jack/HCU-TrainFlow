# [Model][Gemma4] Fuse post-attention residual add into pre-FFN RMSNorm

[Upstream PR](https://github.com/vllm-project/vllm/pull/53273) · state: open · merged: False

## Original PR description

### Purpose

The Gemma4 decoder layer wrote the post-attention residual as a standalone add:

```python
hidden_states = self.post_attention_layernorm(hidden_states)
hidden_states = hidden_states + residual        # separate elementwise add kernel
residual = hidden_states
hidden_states = self.pre_feedforward_layernorm(hidden_states)
```

That add lowers to its own kernel every layer (`triton_poi_fused_add_*` in a torch-compile trace; a standalone elementwise pass otherwise). This PR folds it into the following norm using `RMSNorm`'s two-argument add-then-norm form:

```python
hidden_states = self.post_attention_layernorm(hidden_states)
hidden_states, residual = self.pre_feedforward_layernorm(hidden_states, residual)
```

`RMSNorm.forward(x, residual)` dispatches to `fused_add_rms_norm`, which performs the residual add and the normalization in one op. This is the exact residual-threading pattern `gemma3` and `llama` already use. On ROCm (CK-tile / aiter RMSNorm) this removes one standalone add kernel per decoder layer; on other backends it removes the separate add node from the graph.

Primarily this is a redundant-kernel cleanup that aligns Gemma4 with the gemma3/llama residual-threading pattern. The measurable upside is concentrated in short-input decode — the long tail of chat interactions, where inputs start as very short sentences and the fixed per-pass kernel overhead is a larger fraction of each step; at large ISL the saved time is negligible against the prefill GEMMs (see Serving benchmark).

### Why this is numerically equivalent (not an approximation)

`fused_add_rms_norm` (`vllm/ir/ops/layernorm.py`) computes:

```
residual = x + residual
out      = rms_norm(residual, weight, eps)
return out, residual
```

Mapping to the old code: `x = post_attention_layernorm(attn_out)`, `residual = old_residual`. The returned `residual` is `post_attn_norm_out + old_residual` — identical to the previous `residual = hidden_states` after the explicit add — and the returned `hidden_states` is `pre_feedforward_layernorm(that sum)`. The two MoE-branch reads of `residual` (`pre_feedforward_layernorm_2(residual)`, `router(residual)`) and the post-FFN add therefore see the same value as before.

### Scope / what is intentionally not changed

- Only the **post-attention** residual add is fused. The **post-feedforward** residual add (`hidden_states = hidden_states + residual` after `post_feedforward_layernorm`) is left as-is: the per-layer-embedding (PLE) contribution and the `layer_scalar` multiply sit between it and the next layer's `input_layernorm`, so there is no adjacent norm to fold it into without restructuring the cross-layer residual flow.
- `q_norm` / `k_norm` / `v_norm` / RoPE, the attention path, the MoE branch, and all non-Gemma models are untouched.
- The **Gemma4 MTP (multi-token prediction) draft** decoder layer (`gemma4_mtp.py`) carried the identical unfused post-attention add and is fused the same way; its post-feedforward add is likewise left unchanged. Non-MTP and non-Gemma paths are untouched.

### Relation to existing PRs (not a duplicate)

Checked open `vllm-project/vllm` PRs (`gemma4 residual`, `gemma4 rms norm`, `fused_add_rms_norm gemma`, `gemma4 fused`). No PR fuses the **post-attention** residual add. Closest, and why this is distinct/complementary:

- **#42144** *[Kernel] Fuse dual RMSNorm + residual + scalar in Gemma4 MoE layers* — a bespoke Triton kernel for the **post-FFN tail** `(rmsnorm(rmsnorm+rmsnorm)+residual)*scalar`, gated to **MoE layers, CUDA, no PLE**. That fuses the *other* residual add (`triton_residual_add_mul`, which this PR deliberately leaves alone), on a path this dense FP8 model never executes. The two are **complementary**: #42144 handles the post-FFN tail, this PR handles the post-attention add.
- **#43953** *[ROCm][Perf] Enable AR+RMS fusion for GemmaRMSNorm models* — a compile-pass `allreduce+residual_add+rmsnorm` fusion at **TP>1** for `GemmaRMSNorm`. Different mechanism and scope; this PR is TP=1, plain `RMSNorm`, no allreduce.
- **#53115** *enable FUSED_QK_NORM_ROPE for 512 head dim (Gemma4)* — separate QK-norm+RoPE kernel work, unrelated to residual-add fusion.

### Test Result

**Accuracy — gsm8k, 1000 samples, 5-shot.** No regression: both metrics move within one standard error (≈ ±0.014), i.e. statistically unchanged (marginally higher).

| gsm8k metric | baseline | this PR (fused add) |
|--|--|--|
| flexible-extract exact_match | 0.734 ± 0.0140 | 0.740 ± 0.0139 |
| strict-match exact_match | 0.727 ± 0.0141 | 0.730 ± 0.0140 |

**Kernel confirmation (A/B GPU-lane traces).** Diff of GPU-lane traces before vs after this change (16 forward passes over 60 layers, so a per-layer per-pass kernel appears 60 × 16 = 960 times):

| kernel | baseline | this PR | note |
|--|--|--|--|
| `triton_poi_fused_add_0` (post-attention add) | 960 | **0** | removed — folded into pre-FFN `fused_add_rms_norm` |
| `triton_poi_fused_add_mul_*` (post-FFN add + `layer_scalar`) | 960 | 960 | kept (not fusable); suffix renumbered `_2`→`_1` |
| total GPU kernels | 22,306 | 21,346 | net **−960** = exactly one add/layer removed |

- The net kernel-count change is **precisely** the 960 removed post-attention adds; every other difference is inductor renumbering with identical counts (`gelu_mul_slice_1`→`_0`, `rms_norm_4`→`_3`).
- The add is **fused, not dropped**: the ck_tile RMSNorm still carries `Rmsnorm2dFusedAddEnumE0` (fused-add disabled), so the add folded into the fp8-group-quant norm path via `fused_add_rms_norm`, and the residual still feeds the surviving post-FFN add.
- Measured removed-kernel time: **~5.1 ms across the trace ≈ 0.32 ms/forward-pass**.

**Serving benchmark — `vllm bench serve`** (random dataset, input 4096 / output 140, mean of 3 seeds; `RedHatAI/gemma-4-31B-it-FP8-block`, TP=1, `--kv-cache-dtype fp8`, `--max-model-len 32768`, AITER (`VLLM_ROCM_USE_AITER=1`) with the `ROCM_AITER_UNIFIED_ATTN` backend; baseline = same build with the post-attention add unfused). This exercises the dense base Gemma4 decoder path; the MTP draft layer carries the identical change and is covered by the equivalence argument above. Deltas are within run-to-run noise — removing ~0.32 ms/step is a small fraction at these batch sizes — so no regression:

Expected: TTFT is prefill-dominated (GEMMs/attention over 4096 input tokens), so removing ~0.32 ms of residual-add kernels per pass is negligible at these batch sizes — but more impactful in the long tail of chat interactions, where inputs start as very short sentences and the fixed per-pass kernel cost is a larger fraction of each decode step.

### On adding a dedicated unit test

Not added, by design. The change is an equivalence-preserving refactor to a call already covered by `fused_add_rms_norm`'s own tests and by the registry-driven Gemma4 generation tests; a bespoke `Gemma4DecoderLayer` numerical-equivalence test would need a full config + weights + GPU and would largely duplicate framework coverage. Per AGENTS.md, validation for a model-output-affecting change is a model eval (gsm8k above), which is the guard here. If a reviewer prefers an explicit equivalence unit test, it can be added.
