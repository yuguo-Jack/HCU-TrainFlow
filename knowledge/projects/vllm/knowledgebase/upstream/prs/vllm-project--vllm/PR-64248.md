# [KV Offload] Add an external evictor to bound the FS tier's root_dir ( #64239 )

[Upstream PR](https://github.com/vllm-project/vllm/pull/64248) · state: open · merged: False

## Original PR description

## Overview

The filesystem (FS) KV offload tier has no size limit: every stored block stays on disk forever, so `root_dir` grows until the disk or shared volume fills up. This PR adds a small standalone evictor that keeps `root_dir` under a byte budget, for a single engine or many engines sharing one directory.

Refs RFC #64237, which asks for a cluster-wide quota and coherent eviction for an FS tier shared by many engines. This PR is the smallest useful piece of that: a working size bound with no engine changes.

**Not a duplicate:** #52784 (an in-engine capacity bound) was closed unmerged, and no open PR bounds the FS tier. This PR takes a different, out-of-engine approach.

## Claims

- `python -m vllm.v1.kv_offload.tiering.fs.evict <root_dir> --max-bytes 500G` keeps the FS tier's disk usage under the budget, whether one engine or many write to the directory.
- Cleans up `.tmp` files left behind by writers that crashed mid-store, which today are never removed.
- No changes to the engine, the FS tier, or any config. Users who don't run the evictor see no difference.

## Validation

- New test `test_evict_removes_oldest_blocks_and_stale_tmp` checks that the oldest blocks are evicted down to the low watermark, a stale `.tmp` is removed, a live `.tmp` is kept, and a second pass deletes nothing. I confirmed the test fails if the eviction order is reversed.

## Details

### The problem

The FS tier writes each KV block as one file under `root_dir`, named by its content hash. Several engines can share one `root_dir` (for example on a shared PVC or distributed filesystem) and reuse each other's blocks. Nothing ever deletes these files. A long-running deployment eventually fills the volume, and once writes start failing, offloading stops being useful.

### Why an external process instead of changes inside the engine

With many engines writing to one directory, an in-engine limit needs every engine to agree on how much space is used, which means locks or a central service. A single evictor per `root_dir` avoids that:

- The filesystem is the only source of truth: no counters to persist, sync, or rebuild after a crash.
- It works the same for one engine or many, on a local disk or a shared volume.
- It needs no change to `SecondaryTierManager`, so other tiers are unaffected.
- It ships as an opt-in tool, so the default behavior doesn't change.

### How it works

Each pass:

1. Walks `root_dir` and stats every file.
2. Records each `.bin` block file's size and mtime.
3. Deletes any `.tmp` file older than `--tmp-grace-s` (default 1 hour). These are left by writers that crashed between writing and renaming.
4. If total block size is over `--max-bytes`, sorts blocks oldest first and deletes them until usage reaches `--low-watermark` (default 90%) of the budget. Stopping below the limit gives headroom, so it doesn't evict on every pass.

It repeats every `--interval-s` seconds (default 60). `--interval-s 0` runs one pass and exits, for cron or Kubernetes CronJob use.

### Why it is safe to delete files while engines are running

- **No partial reads:** the FS tier writes each block to a temporary file and renames it into place, so a `.bin` file is always complete. The evictor never touches in-flight writes, and only removes `.tmp` files after the grace period.
- **A block deleted after an engine found it costs a recompute, not an error.** The load fails, the tier's existing failure handling marks the block as a miss, and the engine recomputes it. `test_failed_load_missing_file` already covers this.
- **Reads already in progress keep working:** on POSIX filesystems a file that is already open stays readable after it is deleted.
- **Two evictors racing:** a file that is already gone is skipped and counted as freed, so the process doesn't crash.

### Eviction policy: oldest first

The FS tier never rewrites a block that already exists, so a file's mtime is when it was first stored, and eviction is first-in, first-out rather than least-recently-used. True LRU would need a recency signal. atime is usually disabled (`noatime`/`relatime`), and updating mtime on every cache hit would add a metadata round trip per hit, which is expensive on a distributed filesystem. FIFO is the cheap baseline. If its hit rate proves too low, in-engine `touch()` support can be added later.

### Usage

```bash
# Keep /mnt/kv under 500 GiB, checking every minute
python -m vllm.v1.kv_offload.tiering.fs.evict /mnt/kv --max-bytes 500G

# One pass, e.g. from cron
python -m vllm.v1.kv_offload.tiering.fs.evict /mnt/kv --max-bytes 500G --interval-s 0
```

Sizes accept `K`, `M`, `G` and `T` suffixes. Documented in `docs/features/kv_offloading_usage.md` under "Capacity and Eviction".

### Limitations

- Each pass scans the whole tree, so time and memory grow with the number of blocks. That is fine at a one-minute interval for millions of blocks. Beyond that, usage would need to be tracked incrementally.
- Run one evictor per `root_dir`. Two are safe but may evict more than needed.
- The budget is checked between passes, so usage can briefly exceed it by up to one interval's worth of writes.
