# [Bugfix] Use one warp for resampled token insertion

[Upstream PR](https://github.com/vllm-project/vllm/pull/64990) · state: open · merged: False

## Original PR description

## Overview

Run `_insert_resampled_kernel` with `num_warps=1` to avoid a race when reading and updating `num_sampled` in place. The race can cause an out-of-range lookup during speculative decoding and a fatal CUDA exception.

## Claims

- Removes the cross-warp read/write race in `_insert_resampled_kernel` by restricting its execution to one warp.
- Changes only this kernel's launch configuration.
- Makes no performance or model-quality claims.

## Validation

Two CUDA core dumps from separate crashes on an NVIDIA RTX PRO 6000 Blackwell show the same failure mechanism:

| Incident | Threads reading `num_sampled = 4` | Threads reading `num_sampled = 5` |
|---|---|---|
| First | 0, 32 | 64, 96 |
| Second | 0, 32, 64 | 96 |

The listed threads represent different warps within the same block. Disassembly maps these values to the load of `num_sampled`; the corresponding resampling indices are 4 and 5, with an exclusive end index of 5.

Both dumps report `Warp Out of range Address` at `_insert_resampled_kernel+384`, corresponding to:

    temp = tl.load(temp_ptr + req_state_idx).to(tl.float32)

The failing environment used vLLM 0.32.0, PyTorch 2.13.0+cu130, Triton 3.7.1, and Gemma 4 MTP with four speculative tokens. The same read/update pattern remains in the main-branch code patched here.

Local validation:
- Applicable pre-commit hooks passed, including Ruff, mypy, typos, and repository Python checks.
- Python syntax validation and `git diff --check` passed.

The dumps establish the original failure mechanism.

## Details

The kernel loads `num_sampled`, uses it to compute a resampling index, and increments the same counter in global memory. In the captured machine code, there is no inter-warp barrier between the load and the store.

A delayed warp can therefore read the incremented value after another warp has performed the update. In both incidents, this changes the resampling index from 4 to 5, outside the request's logits range. The subsequent mapping lookup supplies an invalid request-state index, causing the temperature load to fault.

Using one warp removes this inter-warp dependency without changing the sampling algorithm or introducing another kernel launch.

This failure occurs before the NaN/argmax handling addressed by #50183.
