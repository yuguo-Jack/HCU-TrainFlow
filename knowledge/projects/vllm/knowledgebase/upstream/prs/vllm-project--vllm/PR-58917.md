# [Bugfix] shm_broadcast: never drop a write notification

[Upstream PR](https://github.com/vllm-project/vllm/pull/58917) · state: open · merged: False

## Original PR description

## Purpose

`SpinCondition`'s writer notify socket is a zmq PUB with `SNDHWM=1`. zmq refreshes a PUB pipe's "full" state only when the socket processes the subscriber's activation command. A send does that at most once per ~3M CPU-counter ticks: ~1 ms on x86, **~3 ms on aarch64**. So a notification sent that soon after the previous one is dropped, even though the reader already consumed the previous one. A reader that parked in between sleeps until `SHM_READER_RECHECK_INTERVAL_MS`, which is 5 s.

With the default `busy_loop_s=1` this stays latent, because a reader never parks within 3 ms of a read. Any shorter window exposes it.

We hit it on 4x DGX Spark (GB10, aarch64) at TP=4. There we lower the window to 2 ms, because the busy-wait otherwise spins a core for the whole generation on a package where CPU and GPU share one power budget. EngineCore then missed TP0's response to the step that ends a request. About a third of warm prefix-cache hits took 1.2–10.8 s instead of 0.1–0.4 s, with 0 s queue time and a 0.03 s prefill. py-spy showed EngineCore in `get_response` while every worker sat in `dequeue`.

**Fix:** keep the default high water mark. The readers' `CONFLATE` already collapses a burst of pings into one, and the subscriber drains its pipe continuously, so the writer's queue cannot grow.

## Test Plan

- Standalone PUB/SUB reproduction on GB10: two pings `gap` apart, after the reader has consumed the first. 200 trials per gap.
- New unit test `test_back_to_back_writes_wake_a_parked_reader`. It sets the reader's busy window to 0 so it parks after every read, writes a second message 1 ms after the first, and asserts the reader wakes within 0.5 s. It uses 50 iterations with the recheck interval patched to 2 s.
- End to end on the GB10 cluster: back-to-back warm exact resends.

## Test Result

- Standalone repro, pyzmq with libzmq 4.3.5:

  | gap | `SNDHWM=1` | default high water mark |
  |---|---|---|
  | 0.2 ms | 200/200 lost | 102/200 merged by CONFLATE (harmless: the reader finds both messages) |
  | 1 ms | 200/200 lost | 0/200 |
  | 2 ms | 200/200 lost | 0/200 |
  | ≥ 3 ms | 0/200 lost | 0/200 |

- Unit test: **fails on the old code**, where every one of its 50 wake-ups waits out the recheck (105 s total), and passes on the new code. I ran it against the same `shm_broadcast.py` in our fork, which is identical in this area.
- End to end: 14/14 back-to-back 8K warm exact resends at 0.09–0.11 s, down from about half at 1.2–10.8 s. Engine TTFT now equals prefill.
