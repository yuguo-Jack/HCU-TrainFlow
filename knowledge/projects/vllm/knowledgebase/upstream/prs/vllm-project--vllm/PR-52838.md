# [Bugfix][AMD] A GPU-CPU KV transfer fault in OffloadingConnector takes the engine down instead of degrading the cache.

[Upstream PR](https://github.com/vllm-project/vllm/pull/52838) · state: closed · merged: True

## Original PR description

## Purpose

A GPU<->CPU KV transfer fault in `OffloadingConnector` takes the engine down, although the connector
declares itself a best-effort cache (`requires_kv_delivery` is False, `offloading_connector.py:74`:
*"a dropped save is just a future cache miss"*).

On main (f47792af7f):
- `swap_blocks_batch` raises through `STD_TORCH_CHECK` when the batch copy fails
  (`csrc/cache_kernels.cu:229` on ROCm, `:187` on CUDA). A device error latched by earlier work on
  the transfer stream surfaces at `end_event.query()`.
- No caller catches it. The V1 mixin starts async loads and submits deferred stores inside a bare
  `try/finally` (`kv_connector_model_runner_mixin.py:86-90`); the V2 `pre_forward` / `post_forward`
  (`v1/worker/gpu/kv_connector.py:70`, `:131`) and `gpu_model_runner.handle_preemptions` have no
  handler at all.
- The failure channel is dead code: `offloading/worker.py:286-288` asserts `transfer_result.success`,
  and its only producer hardcodes `success=True` (`cpu/gpu_worker.py:715`).

## What this changes

Faults are reported, not raised.

- **Submit fault** (`transfer_async`). The `RuntimeError` is caught, and the error the failed copy
  left pending on the thread is cleared. On ROCm the batch call does not read it, so without the
  clear the next kernel launch raised `hipErrorInvalidValue` and killed the engine anyway (measured
  on MI355X). `end_event` is still recorded on the failing stream and the job is queued as a failed
  transfer, so `wait()` and the next job's stream ordering still fence it. It is reported as failed
  only once that event completes, because copies enqueued before the failing one may still be
  running. Its stream, events and descriptor buffers are not returned to the pools.
- **Poll / wait faults.** `get_finished` reports a `RuntimeError` from `end_event.query()` as
  `TransferResult(success=False)`; `wait()` no longer raises and leaves reporting to the next poll.
  Only `RuntimeError` is downgraded (device faults raise it); anything else still propagates.
- **Failed store.** The worker marks the job failed in `OffloadingWorkerMetadata.failed_jobs` (kept
  across ranks by `aggregate`), and the scheduler calls `complete_store(success=False)`, so the
  chunks are never published as cache, and drops the KV event metadata recorded for them. Serving
  is unaffected: the chunk is simply not cached.
- **Failed load.** Its destination blocks hold undefined KV, so the request is reported through
  `KVConnectorTransferResults.failed_recving`, which the scheduler handles for any number of KV
  cache groups (block-level reports are rejected for more than one group since #56855). The outcome
  follows `kv_load_failure_policy`:
  - `fail` (the default): the request finishes with an error; other requests keep being served.
  - `recompute`: the request is rerun from scratch. It is marked `load_failed`, so its later lookups
    skip the offloaded cache and a persistent fault cannot reload the same chunks forever. Other
    requests still read those chunks, since the CPU copy itself is intact.

Scope: this covers the batch-copy path (ROCm 7.1+, CUDA 12.8+ drivers). The per-copy fallback in
`csrc/cache_kernels.cu:237-247` ignores `cudaMemcpyAsync` return codes and behaves as on main.

## Not a duplicate

- #50984 (merged) and #56855 did this for Mooncake; this PR follows the same `failed_recving` design
  for `OffloadingConnector`.
- #56032 (open) handles disk I/O failures in `SimpleCPUOffloadConnector`; no file overlap.
- #42461 (open, dormant) would remove the per-block API; this PR no longer uses it.

API update. My 09-09 reply is out of date. The PR no longer uses get_block_ids_with_load_errors. Failed loads go through the request-level KVConnectorTransferResults.failed_recving (#53781). That also covers hybrid models, where #56855 makes block-level load errors raise. With the default kv_load_failure_policy="fail", a failed load ends only that request. With "recompute", the request is rerun and does not read the offloaded copy again, so a persistent fault cannot loop.

Setup. MI355X (gfx950), image vllm/vllm-openai-rocm:nightly-rocm100-e68efc685 (ROCm 10.0, torch 2.12). The PR's 8 commits applied cleanly onto e68efc685. Main (e68efc685) vs main + PR, same image, same args.

Fault injection. I wrap gpu_worker._select_swap_blocks_fn and set one descriptor size to 0 in the first store or load batch. HIP then really fails the copy: hipMemcpyBatchAsync failed at index N with error 1.
```
orig = gpu_worker._select_swap_blocks_fn
def patched(refs, gpu_to_cpu, host_memory_is_pinned=True):
    fn = orig(refs, gpu_to_cpu, host_memory_is_pinned)
    def faulty(src, dst, sizes, **kw):
        sizes[len(sizes) // 2] = 0          # first matching batch only
        return fn(src, dst, sizes, **kw)
    return faulty
gpu_worker._select_swap_blocks_fn = patched
```

🟡 **Severity: MEDIUM**

When a store transfer fails, `mark_completed(job_id)` reports it to the scheduler as a successful completion (the metadata carries no failure flag). The scheduler then calls `manager.complete_store(keys, req_context)` with default `success=True`, marking corrupt/undefined CPU cache blocks as "loadable". A subsequent load from these blocks delivers stale data (potentially from another user's request) to the GPU. The manager already supports `success=False` to remove invalid entries, but this path never invokes it.
Helpful? Add 👍 / 👎

<details>
<summary>💡 Fix Suggestion</summary>

**Suggestion:** The fix requires propagating a failure flag from the worker through the metadata protocol to the scheduler, so the scheduler can call `manager.complete_store(keys, req_context, success=False)` for failed stores. This involves changes across three files:

1. **`common.py` (`OffloadingWorkerMetadata`)**: Add a `failed_jobs: set[int]` field (default empty set). Update `mark_completed` to accept a `success: bool = True` parameter; when `success=False`, add the `job_id` to `failed_jobs` as well. Update `aggregate()` to merge `failed_jobs` sets via union.

2. **`worker.py` (line 380)**: When a failed transfer is not a load (i.e., a failed store), call `self._connector_worker_meta.mark_completed(job_id, success=False)` instead of the current `mark_completed(job_id)`. For failed loads, also pass `success=False`.

3. **`scheduler.py` (`_process_worker_metadata`, around line 1566)**: When processing a completed store job, check if `job_id` is in the aggregated metadata's `failed_jobs` set. If so, pass `success=False` to `self.manager.complete_store(job_status.keys, req_status.req_context, success=False)`. This causes the manager to remove and free the invalid blocks instead of marking them as ready/evictable.

The manager already implements the `complete_store(success=False)` path (cpu/manager.py:256-262) which properly removes write-pending blocks and frees them, so no changes are needed in the manager itself.
