# [Bugfix][Sampler] Carry the boundary tie count across blocks in the split top-p mask kernel

[Upstream PR](https://github.com/vllm-project/vllm/pull/62046) · state: closed · merged: True

## Original PR description



## Overview

Fixes #61997. The split top-p mask kernel (`_topp_sb_mask_kernel`) restarts its count of tied boundary tokens at every 8192-entry block. Slices longer than one block therefore keep too many copies of the boundary value. This PR carries the count across blocks, as the monolithic kernel already does.

## Claims

- In the split top-p pipeline (top-p-only rows, batch ≤ 64, CUDA/ROCm), the number of copies of a tied boundary value that are kept now matches the sort-based reference. The kept copies are the first ones in index order, as the cross-slice logic intends.
- Rows without an exact tie at the boundary, and rows whose ties fit in one block, are unchanged.

## Validation

All runs on an NVIDIA L4 (58 SMs, so S=1 at B=64; torch 2.14.0+cu132), branch at `bc6de71192`, `VLLM_USE_PRECOMPILED=1`.

**New test, unfixed kernel (`main` version of `topk_topp_triton.py`):** fails as expected.

```
pytest tests/v1/sample/test_topk_topp_sampler.py -k test_topp_ties_across_blocks
E   AssertionError: kept [4160], expected [2300]
1 failed, 133 deselected
```

**Fixed kernel, the whole Triton class:**

```
pytest tests/v1/sample/test_topk_topp_sampler.py -k TestTritonTopkTopp -v
95 passed, 39 deselected in 210.12s
```

**Issue's repro script** (4096 tied tokens at the boundary, B=64, p=0.7, run against the `main` kernel file; the script patches its own copy with the same line as this PR):

| kernel | ties over 8 blocks | ties in 1 block |
|---|---|---|
| float64 reference | 1913 (mass 0.700) | 1913 (mass 0.700) |
| `main` | 4160 (mass 0.994) | 1913 (mass 0.700) |
| this PR | 1913 (mass 0.700) | 1913 (mass 0.700) |

**End to end:** `VLLM_USE_FLASHINFER_SAMPLER=0` routes top-p through these Triton kernels. With it set, `LLM("Qwen/Qwen3-0.6B")` generated 16 prompts with `SamplingParams(temperature=1.0, top_p=0.95, max_tokens=48)`, which uses the split path at batch ≤ 16. All 16 completions came back with no errors, and the text reads normally.

## Details

**Root cause.** A copy of the boundary value `dup` gets rank `num_preceding + cumsum(dmask)`, and only copies with rank ≤ `numkeep` are kept. Here `num_preceding` is the number of copies in lower-indexed slices. The block loop never advanced `num_preceding`, so every block of a slice ranked its copies starting from the same base. Each block could keep up to `numkeep - num_preceding` copies of its own. Only slices longer than `BLOCK=8192` are affected, i.e. `S < V / 8192`. On current GPUs, S is 1 or 2 at batch 64, so every current vocab hits this.

**Fix.** Add `num_preceding += tl.sum(dmask.to(tl.float32))` after each block. It counts every copy, kept or not, which matches how the cross-slice `num_preceding` is built from `nmin`. The monolithic kernel counts kept copies (`num_kept += tl.sum(duplicate_keep_mask)`), which is equivalent here. The added work is one block reduction per block, and it runs only when the row has a tie at the boundary.

**Test.** `test_topp_ties_across_blocks` spreads 4096 tied tokens over every block of the row, at stride 37 in a 151936-entry vocab. It adds 64 higher tokens and a `-8.0` tail, and sets `p=0.75`, so the boundary falls mid-copy inside the tie group. That keeps the fp32 reference from landing one copy off. The tail matters: if the tied value were the row's minimum, the ladder search could not place a pivot below it, and the row would take the keep-everything fallback before reaching the mask loop. The test asserts that the kept count equals `apply_top_k_top_p_pytorch`, and that the kept copies are an index-ordered prefix. The existing `test_topp_tie_break_deterministic` puts all its ties in one block, so it can't catch this. B=64 gives multi-block slices on any GPU with fewer than 256 SMs. That includes the H200 MIG slice used by the "V1 Sample" CI step. The test also still covers this after #61996, which shrinks slices to about 9.5K entries (two blocks) at this vocab.

**Not duplicating:** the issue has no comments or assignee, and searches for the issue number, `num_preceding`, `topp_sb_mask` and "split top-p tie" turned up no PR. #61996, also by the reporter, changes `_topp_split_count` but not the mask loop.

**Model evals:** the `tests/evals/gsm8k` configs either decode greedily or sample without `top_p`, so none of them reaches the split top-p path. They can't measure this change. The kernel-level comparison against a float64 reference is above.
