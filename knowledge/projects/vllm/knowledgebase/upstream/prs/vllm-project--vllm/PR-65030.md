# [Perf][Model] DeepSeek V4/V4.1 Vision: encode a call's images in packed passes

[Upstream PR](https://github.com/vllm-project/vllm/pull/65030) · state: closed · merged: True

## Original PR description

## Overview

DeepSeek V4 and V4.1 Vision run the ViT and aligner once per image, even when a call carries several images. This PR encodes a call's images in one packed pass through `forward_packed`, the path V4.1's encoder CUDA graphs already use. No new flag.

## Claims

- Across 54 multi-image encoder calls, encoding is 2.0–2.6× faster on V4 and 1.6–2.1× faster on V4.1, on two H100 machines. No call got more than 2% slower.
- With the real V4 checkpoint on 2× B200, median TTFT drops from 367–378 ms to 271 ms for 4-image requests at concurrency 1, and from 914–959 ms to 548 ms on VisionArena at concurrency 16.
- MMMU-Pro scores match main within run-to-run noise (862 correct vs 861 / 860 on main; multi-image 75 vs 74 / 75) on a direct-answer setup described below. Startup KV-cache capacity is effectively unchanged in the tested configuration.
- Cost: peak encoder memory per call grows with the number of images, up to about 1.7 GB more on V4 and 2.0 GB on V4.1 for a 32-image call. Output is not bit-identical to the per-image path, and the PR disagrees with main on more answers than main does with itself (200 vs 96 of 1730), in both directions.

On one H100, the per-image path of the two main wheels (`2abde627d9`, `190df0b900`) differs by about 4%, close to the 2.6% between two runs of the same wheel, so the gap is mostly the machine.

## Details

`_process_image_input` loops over images, so each one pays for its own kernel launches through 32 blocks. `forward_packed` runs them together, with per-image attention through `cu_seqlens`.

- **Scope.** Packing applies only to FlashAttention with two or more images. One image gains nothing from it, and I didn't measure other backends, so both keep the per-image path. `run_dp_sharded_vision_tower` and the graph manager's eager fallback are unchanged.
- **Memory.** Peak encoder memory grows with the images in a call. The startup profile run encodes the maximum items per batch, and the KV-cache size above did not change.
- **Rounding.** Each matmul sees more rows, so packed output rounds differently. Together with batching, that can change generated answers; the evaluation above shows more disagreements with no net change in scores, but does not separate the two causes.
- **Not tested.** V4.1 serving and MMMU-Pro (encoder results only), AMD (it shares the helper), thinking mode, DSpark speculative decoding, and MMMU-Pro with a larger output budget.
- **Overlaps.** #62802 has since merged and this branch still merges cleanly with main. #57985 touches some of these files and merges cleanly too. It removes the patch dtype cast, which is why `merge_mask` takes its dtype from the aligner weights. #58782 conflicts in `amd/vl_model.py`. #64435 and #57872 also target V4.1 but don't touch these files.
