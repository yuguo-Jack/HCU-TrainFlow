# [MORI] Add MORI EP V2 support

[Upstream PR](https://github.com/vllm-project/vllm/pull/61361) · state: closed · merged: True

## Original PR description

## Overview

Adds `--all2all-backend mori`, an expert-parallel all2all backend that runs MoRI EPv2 (`mori.ops.dispatch_combine_v2`) where it is supported and MoRI EPv1 otherwise. EPv2 dispatches and combines tokens through a MoRI CCO symmetric-memory window, so all EP ranks must sit in one load/store-accessible (LSA) team, e.g. one node.

`VLLM_MORI_EP_V2` selects the version. When it is unset, `mori` prefers EPv2 and falls back to EPv1 with a warning in any of these cases:

- the EP size exceeds 8 (except on gfx1250, whose UALink team can span hosts);
- `MORI_ENABLE_SDMA=1` is set (except on gfx1250);
- `--moe-backend aiter_mega_moe` is used;
- the model is not BF16.

Setting it to `1` forces EPv2, and `0` selects EPv1. The choice is made once in the ROCm platform's config hook. On EPv1 across nodes, `mori` uses InterNodeV1LL when the per-rank token budget is at most `VLLM_MORI_DISPATCH_INTER_KERNEL_SWITCH_THRESHOLD` (default 256), and InterNodeV1 otherwise.

The existing MoRI backends (`mori_high_throughput`, `mori_low_latency`) are unchanged and always run EPv1. `docs/serving/expert_parallel_deployment.md` explains how to choose among them.

The MoRI EPv1 flag `use_mori_kernels` is renamed to `use_mori_epv1_kernels`, next to `use_mori_epv2_kernels`. This touches its existing users in `rocm_aiter_moe.py`, `deepseek_v32` and the MiniMax-M3 test.

No other open PR adds a MoRI EPv2 backend.

## Claims

- On DeepSeek-V4-Pro with DP8+EP8 on 8× MI355X, `mori` on EPv2 matches TP8 and the existing MoRI EP backend on GSM8K.
- Under the InferenceX MI355X serving recipe (8k/1k), `mori` on EPv2 gives about 13% more output throughput and about 11% lower TPOT than `mori_high_throughput`.

## Validation

DeepSeek-V4-Pro, 8× MI355X, `--moe-backend aiter`, CUDA graphs, MoRI main.

**Accuracy**

| Backend | Parallelism | GSM8K (lm-eval, 1319 q, 5-shot, strict) |
|---|---|---|
| default | TP8 | 0.950 |
| `mori_high_throughput` | DP8+EP8 | 0.958 |
| `mori` (EPv2) | DP8+EP8 | 0.955 |

GSM8K ran with 4096 max new tokens, so about 33 answers per backend were cut off before the final answer. The absolute scores are lower than with a longer budget, but the backends can be compared with each other.

**Throughput.** InferenceX vLLM MI355X recipe: DP8+EP8, `--max-num-batched-tokens 8192`, prefix caching, DSpark speculative decoding (6 tokens), and model runner V2. The load is random input/output of 8k/1k, with 640 requests at concurrency 64 and 1280 requests at concurrency 128. Both runs used the same image, on an earlier revision of this branch where the backend was still named `mori_epv2`.

| Backend | c64 output tok/s (TPOT ms) | c128 output tok/s (TPOT ms) | GSM8K (200 q) |
|---|---|---|---|
| `mori_high_throughput` | 1835 (30.3) | 2339 (47.0) | 0.965 |
| `mori` (EPv2) | 2073 (26.9) | 2644 (41.8) | 0.960 |

The eager mode (`--enforce-eager`) start-up also passed. Unit tests: `pytest tests/kernels/moe/test_mori_epv2_prepare_finalize.py`.

## Follow-ups

- Make mori the single MoRI backend: fold mori_high_throughput and mori_low_latency into it (deprecate first, then remove). VLLM_MORI_EP_V2 stays as the EPv2/EPv1 override.
- Add EPv2 across nodes (RDMA), so multi-node EP no longer falls back to EPv1.
- Use quantized (FP8/FP4) dispatch on EPv2. MoRI supports it, but this backend does not use it yet.

Additional validation, part 2: accuracy on the same two models and the same DP8 + EP8 setup as part 1, with EPv2 (default `mori`) and EPv1 (`VLLM_MORI_EP_V2=0`) side by side.

**Setup.**
- **GPQA-Diamond.** 198 questions x 4 samples, simple-evals prompt and answer extraction. The question set is the public simple-evals CSV.
- **AIME25.** 30 problems x 8 samples. The answer is read from `\boxed{}`.
- **Shared settings for both.** Run through lm-eval over chat completions with thinking on. `max_tokens` is 65536. Each request is sampled independently, with no fixed seed. Sampling follows the model cards: DeepSeek-V4-Pro uses `temperature=1.0, top_p=1.0`, and Qwen3.5 uses `temperature=1.0, top_p=0.95, top_k=20, presence_penalty=1.5`.
- **NIAH.** The 8 RULER NIAH subtasks (single 1-3, multikey 1-3, multivalue, multiquery), with 100 samples each at 4k, 16k, 64k and 128k. Prompts are tokenized with each model's own tokenizer. Generation is greedy with thinking off and a 128-token limit, scored with RULER `string_match_all`.

Each cell is avg@N ± stderr, followed by pass@N and the share of samples with no extractable answer in parentheses. A sample with no extractable answer counts as wrong. In 140 of the 143 such samples the reasoning was still running when it hit the 64k limit, so no final answer was produced. The absolute scores are therefore conservative, but both backends run under the same limit.
