# [Bugfix] Fuse GLM-5.3 KDA q|k|v convs into one conv1d parameter

[Upstream PR](https://github.com/vllm-project/vllm/pull/60991) · state: closed · merged: True

## Original PR description

## Overview

`Glm5NextLinearAttention` cached the merged q|k|v conv weight on the first forward, so an RL refit left the conv kernels reading stale values (#55087). This PR replaces the three `q/k/v_conv1d` modules with a single `conv1d` parameter of shape `[3 * C_local, 1, K]`, which the kernels read directly. Checkpoint `q_conv1d` / `k_conv1d` / `v_conv1d` weights load into it as shards 0/1/2 through `stacked_params_mapping`, using the `_make_fused_conv1d_weight_loader` already used by Kimi-Linear KDA and OLMo-Hybrid GDN. There is no second tensor to keep in sync, so every write path lands in the tensor the kernels read, at a fixed address.

Alternative fixes for the same issue: #56298 and #57638 (see Details; their authors are co-authors on the commit). The fused-parameter design was suggested by hao-aaron in review and replaces this PR's first approach (parameter views into a merged buffer), which broke under weight offloading and `ipc_cache` copy mode.

## Claims

- After `load_weights` / `reload_weights` (checkpoint or kernel format), GLM-5.3 KDA decode uses the refitted conv weights, in eager mode **and** with the default `FULL_AND_PIECEWISE` cudagraphs.
- The conv weight keeps its address across refits, so FULL decode graphs captured before a refit stay valid.
- Works with `--cpu-offload-gb` (with and without refit) and with `--load-format ipc_cache` in both `copy` and `zero_copy` modes.
- No numerical change: the per-rank layout is `[q_r | k_r | v_r]`, the same as the old `torch.cat`. Direct-load outputs are identical to `main`. One copy of the conv weights is dropped.

Checkpoint-format refits are not supported on an `ipc_cache`-loaded model on `main` either, so they're not compared here. `_apply_entries` re-registers every parameter as a plain `nn.Parameter` (399/399 lose `weight_loader`), so `load_weights` of any stacked weight raises `AttributeError` (verified on `main` with `self_attn.q_proj`), and the layerwise `reload_weights` fails with `Cannot copy out of meta tensor`. On `main` the three conv weights happened to fall through to `default_weight_loader`; with this PR they're stacked like the other projections. Making checkpoint-format refit work after `ipc_cache` is a separate issue.

## Details

**Root cause.** The KDA layer runs one causal conv over the concatenated q|k|v channels. The merged weight was built lazily on the first forward with `torch.cat` and cached, so later writes to `q/k/v_conv1d.weight` (RL refit through the weight-transfer engines, `reload_weights`, or kernel-format `copy_`) never reached it.

**Why not invalidate the cache (#56298, #57638).** Both PRs drop the cached tensor on refit and rebuild it on the next forward. That works with `enforce_eager=True`, but with the default `FULL_AND_PIECEWISE` cudagraphs the KDA forward is captured inside the FULL decode graphs, which keep the old tensor's address, so decode replays never see the rebuilt weight.

**Why one parameter instead of views into a merged buffer.** Views only hold while nothing replaces a parameter's storage. The UVA and prefetch CPU offloaders set each parameter's `.data` right after the layer is built, and the `ipc_cache` loader in copy mode clones every entry separately; either way the three weights stop aliasing the tensor the kernels read. With a single parameter, those paths, the layerwise reload, and kernel-format `copy_` all write the tensor the kernels use. This matches how Kimi-Linear and OLMo-Hybrid already store their fused short convs.

**Trade-offs.**
- The vLLM parameter name changes from `q/k/v_conv1d.weight` to `conv1d.weight`. Checkpoint-format updates keep the HF names and go through the stacked mapping. Kernel-format writers need the fused name, and GLM-5.3 artifacts saved with vLLM parameter names (`sharded_state`, vLLM-serialized tensorizer) before this change will not load.
- Open PRs #59304 (KCP) and #57496 (CPU KDA backend) reference `q_conv1d` / `_merged_conv_weight` and will need a small rebase.

**Not covered here.** The TP2 cudagraph reload drift from the FlashInfer TRT-LLM FP8 MoE `gemm1_clamp_limit` tensor and the DSA indexer's lazily cached `_wp_fp32` are separate issues, left for follow-ups.

For the record, the same bug pattern exists in the GLM-5.3 indexer: `Indexer._wp_fp32` (`vllm/models/glm5next/common/attention.py`) is an fp32 copy of the `weights_proj` rows of the fused `wk_weights_proj`, built lazily on the first forward and never refreshed, so after a refit the head gate keeps using the old weights (and FULL cudagraphs hold its address). - hao-aaron · comment · 2026-10-10T18:24:15Z · [source](https://github.com/vllm-project/vllm/pull/60991#issuecomment-6100756519)

Nice find on the FULL-graph address problem. Making the merged weight live at a fixed address is the right goal. I think the aliasing approach can still go stale, though, in two load paths where the q/k/v params stop sharing storage with `_merged_conv_weight`:

1. **Weight offloading** (`--cpu-offload-gb`, UVA or the prefetch offloader).
   - `make_layers` runs the offloader right after each layer's `__init__`. It moves each param's `.data` to new CPU/UVA memory (`offloader/uva.py` `_maybe_offload_to_cpu`, `offloader/prefetch.py:677`). Buffers aren't offloaded.
   - The checkpoint then loads into the offloaded params, while `_merged_conv_weight` keeps its `torch.empty` contents from the first request.
   - On main this case works today, because the lazy `torch.cat` reads the loaded params.
2. **`--load-format ipc_cache` with `mode: copy`.**
   - `_apply_entries` clones each exported tensor separately, so the params and the buffer come back as independent copies.
   - Outputs are correct at startup and go stale after the next refit.

**Suggestion:** fuse the three convs into one param, the way Kimi-Linear's KDA (`kimi_gdn_linear_attn.py`) and OLMo-Hybrid's GDN (`olmo_gdn_linear_attn.py`) already do. Then there's no second tensor to keep in sync:

```python
# kda.py __init__: replaces q/k/v_conv1d, the unsqueezes, and the cached merge
self.conv1d = ColumnParallelLinear(
    input_size=self.conv_size,
    output_size=3 * projection_size,
    bias=False,
    params_dtype=torch.float32,
    prefix=f"{prefix}.conv1d",
)
self.conv1d.weight.data = self.conv1d.weight.data.unsqueeze(1)
delattr(self.conv1d.weight, "weight_loader")
set_weight_attrs(
    self.conv1d.weight,
    {"weight_loader": _make_fused_conv1d_weight_loader(
        [projection_size] * 3, self.tp_size, self.tp_rank)},
)

# _forward
conv_weights = self.conv1d.weight.view(
    self.conv1d.weight.size(0), self.conv1d.weight.size(-1)
)
conv_bias = self.conv1d.bias

# model.py stacked_params_mapping
(".conv1d", ".q_conv1d", 0),
(".conv1d", ".k_conv1d", 1),
(".conv1d", ".v_conv1d", 2),
```

`_make_fused_conv1d_weight_loader` can be imported from `kimi_gdn_linear_attn`, as `kimi_k3/amd/kda.py` already does. It accepts both 2D and 3D checkpoint conv tensors.

From reading the code, this should:
- **keep outputs identical:** the per-rank layout is `[q_r | k_r | v_r]`, the same as today's `torch.cat`;
- **cover every conv call:** the spec-decode, prefill and decode paths already all read the one merged weight;
- **keep a fixed address** for FULL cudagraphs, and make every write path land in the tensor the kernel reads: layerwise reload, kernel-format `copy_`, offloading, and `ipc_cache` copy mode;
- **drop one copy** of the conv weights.

Trade-offs:
- **The param is renamed to `conv1d.weight`.**
  - Kernel-format writers would need the fused name.
  - GLM-5.3 artifacts saved with vLLM param names (`sharded_state`, vLLM-serialized tensorizer) wouldn't load.
  - Checkpoint-format updates keep the HF names and go through the stacked mapping.
- **Tests and other PRs reference the old names:** `tests/models/glm5next/test_kda_recurrent.py` mocks `q_conv1d` / `_merged_conv_weight`, and #59304 and #57496 reference them too.

Your refit test should carry over, with `conv1d.weight` for the kernel-format step. A `--cpu-offload-gb` run would cover case 1.

Caveat: I haven't tested any of this. It's from reading the code, so please treat it as a suggestion, not a verified fix.

The fused param change looks good to me. One concern about the new e2e test: `test_refit_reaches_cudagraph_decode` is quite heavy for `glm5next-unit-tests`. Two lighter alternatives:

**1. A `_forward`-level guard, no engine.** `test_prefill_checkpoint_resumes_suffix` in `test_kda_recurrent.py` already drives `layer._forward` on a mocked layer. A sibling test could stub the conv kernel to record the `weight` it receives and assert it shares storage with `layer.conv1d.weight`, before and after an in-place refit. That targets the actual regression (a cached copy of the merged weight) and runs in milliseconds. Together with your CPU tests for the fused loader and the layerwise reload, I think that covers the change.

**2. Keep the e2e shape, but with dummy weights.** `test_initialization` already builds GLM-5.3 with `load_format="dummy"` + `dummy_hf_overrides`, so only the config (and the tokenizer, or use `skip_tokenizer_init` with token IDs) gets downloaded. For the checkpoint-format step, refit only the three `q/k/v_conv1d` tensors (split the current fused weight and scale it). `finalize_layerwise_processing` puts back the original tensors for layers that receive no weights. Since greedy tokens from random weights may not move, compare logprobs: they should differ after ×2 and match exactly after restoring. The address-stability check stays as is. I haven't verified that a shrunk dummy GLM-5.3 generates cleanly with cudagraphs, so this needs a quick try.

If you'd rather keep the pruned-checkpoint e2e, I'd move it into the `glm5next-pruned-e2e` step from #57537 instead of the unit step.
