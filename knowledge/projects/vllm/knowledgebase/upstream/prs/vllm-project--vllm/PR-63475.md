# [Bugfix][Kernel] persistent_topk: sync the CTA around radix barrier arrivals

[Upstream PR](https://github.com/vllm-project/vllm/pull/63475) · state: closed · merged: True

## Original PR description

- Sync the CTA before thread 0 arrives at the per-round inter-CTA barrier in `radix_topk`.
- Sync the CTA at the end of each radix row, before it moves on to its next row.

`radix_topk` uses thread 0 alone to signal the inter-CTA barrier. In each radix round it arrives while the other threads of its CTA may still be adding their local histogram into the group's global histogram, or (on CTA 0) zeroing the next round's buffer, so peers can read an incomplete histogram, pick a different pivot and emit duplicate or missing indices. Separately, a CTA that owns several rows moves on to the next one while slower threads are still scanning `shared_ordered` for pivot ties, and the next radix row's vectorized load, or CTA 0's short-row path, overwrites that dynamic shared memory. The cost is one CTA barrier per radix round, next to the grid-wide spin barrier that round already waits on, plus one per radix row. I found both races while porting the kernel to ROCm (stacked on #62298), and I am sending the fix on its own because the code is shared with CUDA. No CUDA GPU was available to me, so the reproduction below is on MI355X and CUDA CI has to confirm the CUDA build and the existing `persistent_topk` tests.

<summary>Reproduction, tests and duplicate check</summary>

**Reproduction (MI355X, gfx950).** A standalone HIP build of `persistent_topk_kernel` from my ROCm port, launched with the same grid sizing as `topk.cu`. Its `radix_topk` matches main except for the warp-shuffle macro, and the barrier's acquire load is a device-scope HIP atomic instead of PTX. Each run executes 150 random cases (k ∈ {512, 1024, 2048}; widths 32K-256K; randn, near-constant, 4-value ties, mostly `-inf`, all-equal; ragged and negative lengths; 1-32 rows, so CTAs own several rows) and checks every row against a CPU top-k by value set.

| variant | runs | rows checked | wrong rows |
|---|---|---|---|
| neither barrier (main) | 169 | 882,700 | 146 (57 runs) |
| end-of-row barrier only | 169 | 882,700 | 152 (59 runs) |
| pre-arrival barrier only | 169 | 882,700 | 0 |
| both (this PR) | 169 | 882,700 | 0 |

The end-of-row race did not show up on its own in these runs, so I checked it by making odd waves sleep (`s_sleep`) before the tie scan:

| variant (odd waves delayed) | runs | rows checked | wrong rows |
|---|---|---|---|
| pre-arrival barrier only | 32 | 29,820 | 712 (32 runs) |
| both (this PR) | 32 | 29,820 | 0 |

**Tests.** The kernel builds only for CUDA on main, so `tests/kernels/test_top_k_per_row.py -k persistent` could not run here; CUDA CI covers it.

No new test: the races depend on scheduling and do not reproduce deterministically, so a unit test would be flaky.

**Duplicate check.** Searched open PRs for `persistent_topk`, `persistent topk`, `radix_topk`, `topk race` and `persistent_topk.cuh`, and read the `persistent_topk.cuh` diffs of #62936, #55122, #41748, #41105, #58785, #55314 and #52149. None adds a sync before the per-round arrival. #55122 rewrites the tie-collection stage and ends it with a grid barrier plus `__syncthreads()`, which would also close the end-of-row race, so whichever lands second drops that hunk. #41105 adds a trailing grid barrier only for its fused page-table variant.

File: `csrc/persistent_topk.cuh` · line 502

What this fixes: without the pre-arrival barrier, thread 0 can signal the inter-CTA barrier while its CTA is still adding into the group histogram (or CTA 0 is still zeroing the next round's buffer), so peers can pick a pivot from an incomplete histogram. With a pivot that is too low, the stage-3 `> pivot` store (which has no `pos < TopK` bound) lets the CTAs write more than k indices: the row loses part of its real top-k, and the extra indices spill into the next row or, for the last row, past the end of the output. The end-of-row barrier stops a CTA from overwriting `shared_ordered` with its next row while slow threads are still scanning it for ties.

End to end, on MI355X with my ROCm port of this kernel (same `radix_topk`; LDS capped to 64 KiB so the multi-CTA path runs), GLM-5.3-Flash MXFP4, TP2, `--sparse-indexer-topk-backend persistent`, 135K-190K token prompts so every decode indexer row goes through `radix_topk`. A = without the two barriers, B = this PR; the ISA differs only by the two `s_barrier`s.

| | A (no barriers) | B (this PR) |
|---|---|---|
| wrong rows vs `per_row` on the same logits, eager | 107 / 2.64M | 0 / 2.64M |
| same, CUDA graphs | 137 / 2.64M | 0 / 2.64M |
| `vllm bench serve` (141K in, 1K out, c8/c16) | 7/7 servers died with `Memory access fault by GPU` within their 2nd-6th run | 0 faults in 37 runs |
