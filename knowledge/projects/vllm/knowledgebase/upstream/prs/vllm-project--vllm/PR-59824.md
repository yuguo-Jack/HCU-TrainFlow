# [ROCm][Kimi-K3] Support DSpark adaptive verification on MI355X

[Upstream PR](https://github.com/vllm-project/vllm/pull/59824) · state: closed · merged: True

## Original PR description

 **Requires #55504 and #56831.** Both are open, and this branch carries them as separate commits until they merge.
> - **#55504** "Preserve GDN recurrent state on zero-draft speculative decode steps". Without it, the 1-token-per-request varlen capture dummies record the non-spec KDA path, which trimmed verify batches then replay. This PR also contains the fix I'm proposing for #55504: a row is a spec-decode row only if it is no wider than k+1.
> - **#56831** "Synchronize adaptive DSpark decisions across TP ranks". Without it, rank-local confidences can choose different draft budgets or request boundaries on different TP ranks, which leaves the collectives mismatched and can hang. Kimi-K3 runs at TP8, and trimming happens on ~97% of steps at conc ≥ 8.

### Purpose

`speculative_config.enable_adaptive_verification` (#47808) trims each verify request to 1..k+1 tokens on the device, using the DSpark confidence head. #52988 enabled it for Kimi-K3 on NVIDIA only. On ROCm, Kimi-K3 is refused at engine start:

1. `KimiK3ROCmKDABackend` inherits GDN's `is_ssm()`, so `supports_device_cpu_query_lens_mismatch()` returns `False`.
2. The ROCm KDA builder is `UNIFORM_BATCH` and declares no varlen bound.
3. `AiterMLAMetadataBuilder` is `UNIFORM_BATCH` and declares no varlen bound.

This PR removes those three gates. It also fixes two bugs that showed up once adaptive verification actually ran on a hybrid model.

### Changes

**ROCm KDA** (`models/kimi_k3/amd/kda_metadata.py`)
- The backend accepts a CPU/device query-length mismatch. The spec path plans from `spec_query_start_loc` and `num_accepted_tokens` on the device.
- `get_varlen_cudagraph_max_query_len` returns k+1 under adaptive verification. The builder keeps `UNIFORM_BATCH`, because FULL capture is decode-only.
- Under adaptive verification, the builder drops the host-derived `uniform_spec_sequence_length`. The fixed-length recurrent kernel places sequence *i* at `i * L` and bakes `L` in at graph capture. Varlen graphs are captured with an even split (e.g. 2×4) and replayed with ragged batches (e.g. 1×8), so keeping it corrupts KDA state: acceptance length fell from about 3.8 to 2.0 when we kept it.

**AITER MLA** (`v1/attention/backends/mla/rocm_aiter_mla.py`)

These changes apply under adaptive verification only, with DCP=1 and causal batches:
- Every decode batch runs as uniform k+1 blocks. That is the width the FULL graph's ASM kernel variant was captured at.
- Real tokens are left-aligned in their block, and the kernel's KV length is extended by the pad. Each real token keeps its exact causal window, and no row gets an empty window. Right-alignment faulted the ASM kernel (`HSA_STATUS_ERROR_MEMORY_APERTURE_VIOLATION`) on contexts shorter than k+1.
- The appended page-list entries repeat the request's first page (`CLAMP_TAIL` in `_expand_page_indices_kernel`), so they stay in bounds.
- q is gathered into the blocks and the output is gathered back using index maps built on the device from `query_start_loc`. This adds no host sync.
- `query_len_support` becomes `VARLEN`, and `get_varlen_cudagraph_max_query_len` returns k+1.
- Causality is decided per batch, not from the group spec. Kimi-K3 DSpark draft layers share the target's MLA group, and `MLAAttentionSpec.merge` sets `non_causal_multi_token_decode` on the whole group. Non-causal draft batches keep the existing path.
- No aiter change is needed: the kernels only ever see uniform blocks.

**Adaptive-verification cost profiling** (`v1/worker/gpu/input_batch.py`, `v1/worker/gpu/model_runner.py`, `v1/worker/gpu/model_states/mamba_hybrid.py`)

With the default `VLLM_ADAPTIVE_VERIFICATION_PROFILE_CONTEXT_LEN=8192`, profiling faulted on the second prefill-shaped dummy batch ("Write access to a read-only page"). Two causes:
- `compute_num_decode_draft_tokens` (from #55504) made every non-prefilling row without drafts a spec row, including the dummy run's 12-token rows. Those rows carry no prefill flag. The recurrent kernel then walked 12 tokens through an 8-wide state-index row. Now only rows no wider than k+1 are decode rows. Before this fix, running without the fabricated context avoided the crash but silently corrupted memory: acceptance dropped about 10% at conc 1, and recovered fully once the bug was fixed.
- `set_dummy_context` gave every KV cache group the same `arange` block ids, including the recurrent-state groups. Hybrid models back all groups with the same tensors, so KDA wrote fp32 state over blocks the MLA layers read as fp8 KV. Context blocks now count up from the first block past the null block, and state slots count down from the top of the pool.

### Dependencies

Both are required for adaptive verification to run correctly on Kimi-K3. Until they merge, this branch carries them as separate commits, and they will be dropped on rebase.

| PR | Status | Commit here | Why it is required |
|---|---|---|---|
| #55504 | open | `83f1d05dd4` (unchanged backport, original author) | Zero-draft decode rows, including the 1-token varlen capture dummies, must take the GDN/KDA spec path that applies `num_accepted_tokens`. Without it, the FULL varlen graphs record the plain decode kernel. |
| #56831 | open | `2a4a548fd6` (cherry-pick) + `7777ad03c3` (test adapted to this base's `async_tensor_h2d`) | Rank 0's draft budget and per-request capacities are broadcast, so all TP ranks build the same verify layout. |

The width check in `compute_num_decode_draft_tokens` (commit `843d1663e8`) fixes #55504 itself. I've also proposed it on #55504; if it lands there, it will drop from this PR.

### Test Plan

One new test per fix, plus the updates existing tests need:
- `tests/v1/attention/test_mla_backends.py::test_adaptive_varlen_decode_correctness` (GPU, 2 cases at 16 heads). Ragged device query lengths (1..k+1) are run against an even host split and checked against an SDPA reference. The two cases are fp8 KV, and bf16 with contexts shorter than k+1 (the left-alignment case).
- `tests/v1/attention/test_rocm_aiter_mla_mtp_split.py`: `test_varlen_cudagraph_bound_follows_adaptive_verification` (on/off, DCP, and a draft group that shares the target's spec) and `test_varlen_rows_left_align_each_request_in_its_block`.
- `tests/models/kimi_k3/test_amd_kda_adaptive_verification.py`: the backend/builder opt-in, and dropping the uniform length under adaptive verification (with a control case without it).
- `tests/v1/worker/test_mamba_hybrid_model_state.py::test_rows_wider_than_a_verify_block_keep_the_sentinel`.
- `tests/v1/worker/test_gpu_pcp_manager.py::test_dummy_context_keeps_state_slots_apart_from_context_blocks`.
- End to end: Kimi-K3 FP4, TP8, MI355X (vLLM nightly 36768d1b plus this branch). DSpark K=7 with block (real) acceptance, adaptive verification on vs off, measured on fresh servers.

### Test Result

- All of the new tests above pass on MI355X.
- The touched files pass in full: AITER MLA mtp_split 67/67, the new KDA file, pcp manager, and mamba_hybrid model state.

**Not covered yet**
- No accuracy eval (e.g. GSM8K) with adaptive verification on.
- No long-context (>16k) runs at conc ≥ 8.
- conc 4 / FULL_AND_PIECEWISE mixed batches and async scheduling are untested.
- DCP>1 is gated off.
- The gains above are against static K=7. They have not been measured against the best static K for each concurrency.

### Notes

- Related, not required: #57942 (AMD DSpark MLA module) currently maps `confidence_head` to `None`. Once ROCm routes K3 DSpark to that module, enabling adaptive verification would fail at load with `AttributeError` on `model.model.confidence_head`, so the head needs to be kept there. Today ROCm uses the NVIDIA module, which keeps it.
- `vllm:spec_decode_num_draft_tokens` counts proposed drafts, so it reads K even when adaptive verification trims on the device. The "verified" figures above come from instrumentation in the adaptive-verification manager. The scheduler metric still needs fixing
