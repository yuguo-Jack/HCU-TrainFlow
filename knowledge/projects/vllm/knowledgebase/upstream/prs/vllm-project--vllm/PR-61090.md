# Fix torchcodec lazy-import startup crash when native lib raises OSError

[Upstream PR](https://github.com/vllm-project/vllm/pull/61090) · state: closed · merged: True

## Original PR description



## Overview

Widens the module-scope torchcodec import guard in `vllm/multimodal/media/audio.py` to also catch `OSError`, so `vllm serve` starts cleanly even when torchcodec's bundled native library fails to load (e.g. built against a CUDA runtime that is not installed). Fixes #60406.

## Claims

- `vllm serve` no longer dies at import time when `torch.ops.load_library` inside torchcodec raises `OSError`.
- With torchcodec unavailable, `AudioDecoder` is `None` and `load_audio(backend='auto')` falls back to soundfile/PyAV instead of crashing.
- The original `OSError` is preserved in `_torchcodec_import_exc` and chained into the deferred `ImportError`, so the real cause is not hidden.

## Validation

The full vLLM test suite is not runnable in this environment (needs CUDA + full install). I verified with a harness driving the real fixed `audio.py` with heavy deps stubbed and a fake torchcodec whose `decoders/__init__.py` raises `OSError` at import (faithful to the issue): 9/9 checks passed — fixed module imports cleanly, `AudioDecoder` is `None`, the `OSError` is preserved and chained into the deferred `ImportError`, the healthy-torchcodec control is unaffected, and the pre-fix file demonstrably crashes with `OSError` on import.

## Details

Root cause: torchcodec 0.17.0's bundled native lib (built against CUDA 13) fails inside `torch.ops.load_library`, which raises `OSError` (torch/_ops.py). The existing guard caught only `(ImportError, RuntimeError)`, so the `OSError` propagated and killed the whole `vllm serve` startup path even for text-only serving. The fix is a one-line widening of the except clause plus a comment citing the issue. No new third-party APIs are called; `requirements/cuda.txt` already pins `torchcodec >= 0.14` unbounded, matching the issue's analysis.
