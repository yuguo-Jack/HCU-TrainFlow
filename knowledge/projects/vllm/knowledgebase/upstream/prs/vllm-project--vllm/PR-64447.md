# [Perf][DSA] Share the prefill indexer's logits schedule across layers on SM100

[Upstream PR](https://github.com/vllm-project/vllm/pull/64447) · state: open · merged: False

## Original PR description



## Overview

On SM100, the sparse indexer's prefill builds DeepGEMM's per-SM `mqa_logits` schedule once per prefill chunk and passes it to `fp8_fp4_mqa_logits` in every indexer layer that scores the chunk. Without a schedule, DeepGEMM runs its unbalanced kernel variant, which is slow when rows' KV ranges differ a lot, as in prefix-cache hits on long contexts. The MX weight cast also runs once per layer instead of once per chunk.

## Claims

- DeepSeek-V4.1-Flash prefill on a 128K-token prefix-cache hit: the dense indexer logits are 17–26% faster (GB200).
- Whole-model forward (`vllm bench forward`, real weights, DSpark, DEP2 on GB300) over 52 prefill shapes: 0.8% faster on average at 128K–160K cached tokens (up to 1.2%), 0.3–0.4% at 64K–96K, unchanged (within ±0.1%) for cold prefills and short prefix hits.
- Logits are bit-identical; GSM8K, passkey and DSpark acceptance unchanged.

## Details

- `get_mqa_logits_metadata()` wraps DeepGEMM's schedule builder and returns None off SM100 or where the installed DeepGEMM lacks it; `fp8_fp4_mqa_logits()` passes an optional `schedule_meta` through.
- The schedule depends only on the rows' bounds, KV length and head count, all fixed for a chunk within a step. `DeepseekV32IndexerPrefillChunkMetadata.logits_schedule()` builds it in the first indexer layer that scores a row window and returns it to the rest. It is keyed by the row window, so TP row-sharded ranks share theirs too, and by capture state, so a captured graph never reads a schedule built eagerly.
- Decode already passes `schedule_metadata` to the paged kernel; this does the same for prefill.
- Not a duplicate: no open PR passes a schedule to the prefill logits; #63038 changes how prefill chunks are budgeted, which this does not touch.
