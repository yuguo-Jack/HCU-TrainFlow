# [Bugfix][KV Offload] Make batch lookup resolution atomic

[Upstream PR](https://github.com/vllm-project/vllm/pull/62611) · state: closed · merged: False

## Original PR description



## Overview

Make batch lookup resolution atomic: probe every key without side effects, pin all primary HITs in one all-or-nothing call, then start promotions. Four commits: atomic `_prepare_load`, the new `ParentManager` batch contract, the KVCR migration, and per-lookup failure containment.

Related: #60729 names this race and defers the fix to a separate PR; #50014 protects landed-but-unread promotions from other promotions; #58168 adds manager locking.

## Claims

- `CPUOffloadingManager._prepare_load()` validates every key before pinning any of them. A failed load no longer leaves earlier keys of the batch with `ref_cnt > 0` and `_num_evictable_cache_chunks` permanently short.
- `ParentManager` gains `LookupProbe` plus `probe_batch()` / `promote_batch()`. Probing inspects and promotes nothing; promotion runs only after the caller pinned the batch's primary HITs. `lookup()` keeps its exact single-key semantics, implemented on top of the same probe.
- The P2P server resolves one `LookupMsg` as: probe the whole batch -> one `create_store_job()` for all primary HITs -> `promote_batch()`. Still exactly one batched transfer per LookupMsg; no per-key pin.
- Capacity-1 reproduction: A is a primary HIT, B a secondary HIT. Probing A also promoted B, evicted A, and the following `create_store_job([A])` hit `assert chunk is not None`. With the new order A stays pinned and B is reported MISS because primary is full.
- KVCR's framework pin path uses the same order, preserving its old "secondary HIT starts a promotion" side effect.
- A failure while probing, pinning, or promoting no longer escapes `serve_external_requests()`: unsettled keys become MISS, exactly one `LookupRespMsg` is sent, and `on_request_finished` fires exactly once (`_finalize_lookup` is idempotent). Because failures are now contained, the atomicity in the first commit is what keeps a contained failure from leaking primary capacity.

## Details

**Root cause.** `_poll_lookup_keys()` called `parent.lookup()` per key and pinned only after the loop. `lookup()` promotes a secondary-tier HIT inline. That promotion calls `primary.prepare_write([B])`, whose eviction pass only protects `{B}`; an earlier HIT A of the same LookupMsg, not yet pinned, is a normal eviction candidate. Whether A survives depends on the eviction policy. When it does not, `create_store_job([A])` reaches `_prepare_load()` and asserts, so a lookup that answered HIT turns into a failed request. KVCR's `_resolve_pin()` had the same shape.

**Two halves of one invariant.** Fixing only the ordering is not enough, and fixing only the pin is not enough:

- Ordering: probing must not promote, otherwise the batch can evict itself.
- Atomicity: `_prepare_load()` must validate before pinning, otherwise a pin that fails halfway leaves chunks pinned with no job to release them.

The atomicity commit is deliberately not split out as its own PR. On `main`, the `prepare_load()` assertion propagates through `OffloadingConnectorScheduler.update_state_after_alloc` into the scheduler and EngineCore with no handler in between, so the engine goes down and the leaked capacity goes with it. The leak only becomes observable once this PR contains those failures and keeps serving, which is exactly what the last commit does. Split out, the first commit would be dead weight; together, it is the primitive the containment relies on.

**Fix.** Split "query" from "mutate". `TieringOffloadingManager._probe()` runs the primary and secondary queries and reports a secondary HIT as `LookupProbe(result=None, promotion_tier=i)`. `probe_batch()` does this for every key and never calls `_initiate_promotion()`; `promote_batch()` is the only batch entry point that does. The contract is documented on `ParentManager`: all primary HITs of a probe batch must be pinned before promotion. `_prepare_load()` validates the whole key list first, then pins.

**Why not pin per key.** Pinning as each HIT is found would fix the race but split one LookupMsg into one `add_stored_blocks` / NIXL write per block, which is the batching the P2P path deliberately maintains. Pinning the batch in one call keeps both properties.

**Failure containment.** Pinning and promotion can fail on a key the probe just reported as HIT (a full primary tier, a tier error). Those failures are per-lookup: they mark only the unsettled keys MISS and close the lookup through the same single-response path. Keys already pinned before a promotion failure keep their HIT. `_finalize_lookup()` is guarded by `_ActiveLookup.finalized`, so the failure path and a later re-poll cannot both answer. `parent.on_new_request()` stays outside the `try` because it owes no cleanup if it fails.

**Commit layout.** Four commits, reviewable in order: (1) atomic `_prepare_load`, (2) `LookupProbe` / `probe_batch` / `promote_batch` and the P2P migration, (3) the KVCR migration, (4) failure containment and the docstring corrections that claimed the manager lock prevents eviction between lookup and pin.

**Not a duplicate.** #50014 protects a promotion that already landed from being evicted by a *different* promotion; it does not order pinning against promotion inside one batch. #58168 adds a manager lock, which excludes other threads but not a promotion this same call issues. #60729 only enriches the assertion message and states that this fix belongs in a separate PR. #56836 bounds unanswered lookups and tears down the session; it does not fix the eviction.

**Limitations.** The probe/pin window is still protected only by the manager lock; a tier that mutated primary state outside that lock, or a promotion issued from a tier-poll round, is out of scope. The primary tier can still fail a pin for a genuine coverage mismatch, which is now reported as MISS rather than retried.
