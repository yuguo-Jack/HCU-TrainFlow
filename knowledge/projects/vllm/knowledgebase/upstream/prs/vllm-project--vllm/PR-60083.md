# [Perf][HiSparse] Cache per-request residency instead of rescanning every page each step

[Upstream PR](https://github.com/vllm-project/vllm/pull/60083) · state: closed · merged: True

## Original PR description

## Purpose

HiSparse decode is CPU-bound on main because of one scheduler-side scan. Every step, `HiSparseCoordinator.all_context_pages_resident` walks every page of every scheduled request in every resident group (one group per layer), only to decide whether prefill can skip host staging. That is O(requests × context pages × layers) Python per step, even for pure-decode batches.

The scan arrived in c4b9b7deac ("bypass host resolution for resident decode"), after the GLM-5.3 results in #53781 were measured, and shipped with 3/N. This PR caches the requests whose resident pages are all non-null. A request is scanned once. Pages become null only at admission or host import, before the first scan, or when the pool reuses an unpinned page (`_lose_page`), so those paths plus `free` drop the cache entry. The per-step check is O(requests).

HiSparse-only change (`vllm/v1/hisparse/coordinator.py`). Not a duplicate: no open PR touches this scan.

## Results

GLM-5.3-NVFP4 on B200, fp8 KV, block 64, random prompts, 1k output tokens. Each point is one run, main vs. this PR back to back on the same node and config. The gain tracks how much resident context the scan walks per step relative to GPU step time: it's largest when every page is GPU-resident and contexts are long. It disappears at low concurrency, and in the host-offload regime, where the old scan already exited at the first host page.

| TP | input | concurrency | peak KV | main tok/s | this PR tok/s | Δ | mean TPOT main → PR |
|---|---|---|---|---|---|---|---|
| 8 | 16k | 64 | 61% | 764 | 1209 | **+58%** | 73.3 → 42.0 ms |
| 4 | 16k | 40 | 76% | 809 | 906 | **+12.0%** | 40.9 → 35.7 ms |
| 4 | 4k | 160 | 89% | 2470 | 2583 | +4.6% | 57.7 → 54.8 ms |
| 4 | 4k | 128 | 70% | 2777 | 2882 | +3.8% | 40.1 → 38.3 ms |
| 4 | 8k | 64 | 64% | 1510 | 1551 | +2.7% | 35.8 → 34.7 ms |
| 4 | 16k | 24 | 46% | 744 | 760 | +2.2% | 26.5 → 25.8 ms |

For reference, the TP8 16k c=64 config without HiSparse gives 1302 tok/s and 39.2 ms TPOT. Single-run differences under ~3% are within noise.

```bash
# TP8: host_pool_gib 128; TP4: -tp 4 and host_pool_gib 64 (the host pool lives in /dev/shm)
vllm serve RedHatAI/GLM-5.3-NVFP4 -tp 8 --kv-cache-dtype fp8 --block-size 64 \
  --max-model-len <input+2048> --max-num-seqs 256 \
  --kv-transfer-config '{"kv_connector":"HiSparseConnector","kv_role":"kv_both","kv_connector_extra_config":{"host_pool_gib":128}}'
vllm bench serve --model RedHatAI/GLM-5.3-NVFP4 --dataset-name random \
  --random-input-len <input> --random-output-len 1024 --num-prompts <2×concurrency> \
  --max-concurrency <concurrency> --ignore-eos --seed 42
```

Notes:
- The TP4 runs restarted the server per point and included the #60109 crash fix (#60117, cherry-picked) on both sides. Without it, reusing a server across points crashes.
- The TP8 row is a single fresh-server run of 128 prompts on main and on this PR; it has no prefix hits, so it doesn't trigger #60109.
