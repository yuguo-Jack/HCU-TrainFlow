# [Bugfix][Frontend] Parse DeepSeek-V3 tool calls with multi-line JSON args

[Upstream PR](https://github.com/vllm-project/vllm/pull/60361) · state: closed · merged: False

## Original PR description

## Overview

`DeepSeekV3ToolParser` loses a tool call when the model pretty-prints the JSON
arguments over more than one line. Fixes #60342.

## Claims

- Non-streaming: `extract_tool_calls` returns the call, instead of
  `tools_called=True` with an empty `tool_calls` list.
- Streaming: the argument delta accumulates the whole object, instead of stopping
  at the first newline.
- Parallel tool calls stay separate calls, single-line or indented.

## Validation

Both regexes live in `__init__`, so I drove the reproducer from #60342 through the
patterns themselves against a `get_weather` block whose body is
`json.dumps({"city": "Tokyo", "unit": "celsius"}, indent=2)`:

| | before | after |
| --- | --- | --- |
| `tool_call_regex.findall` | `0` matches | `1` match, args `{"city": "Tokyo", "unit": "celsius"}` |
| `stream_tool_call_portion_regex` arguments group | `'{'` | `'{\n  "city": "Tokyo",\n  "unit": "celsius"\n}'` |

Single-line arguments are unchanged before and after. For the two-call output, the
non-streaming regex yields two matches with their own arguments both indented and
not, which is the case a plain `re.DOTALL` would break.

That case is now pinned by `test_pretty_printed_arguments` in
`tests/tool_parsers/test_deepseekv3_tool_parser.py`. It goes through the shared
`ToolParserTests` harness, so the existing `streaming` fixture runs it on both the
streaming and the non-streaming path:

```bash
pytest tests/tool_parsers/test_deepseekv3_tool_parser.py
```

## Details

Root cause: both regexes capture the fenced JSON body with `.` and neither is
compiled with `re.DOTALL`, so the argument group cannot cross a newline. The
non-streaming pattern then fails to match at all, and `extract_tool_calls` still
reports `tools_called=True` because it only checked for the start token. The
streaming pattern does match, but its argument group ends at the first line break,
so only `{` is ever streamed.

I scoped `[\s\S]` to the two argument groups rather than compiling the patterns
with `re.DOTALL`, because `type` and `function_name` are greedy `.*`: under
`DOTALL` they run past the end of one tool call, and a response containing two
calls collapses into one match with the first call's markup swallowed into the
name. Keeping those two groups line-bound is what preserves parallel calls, and
it is also true to the format — neither the type nor the function name ever
contains a newline.

The non-streaming argument group is lazy (`[\s\S]*?`) so it stops at its own
closing fence; the streaming one stays greedy, since it is matched against a
partial tool call and should carry as much of the argument text as has arrived.

Not a duplicate: searching open PRs for the issue number and for `deepseekv3`
/ tool-parser keywords turned up nothing touching this parser, and the issue has
no linked PR.

No model eval: the change is confined to string handling inside the tool parser
and does not touch generation, sampling or any model code path, so there is no
accuracy surface to measure. The behaviour is covered by the unit test above.

One thing I deliberately left out of scope: `deepseekv31_tool_parser.py` has the
same shape of defect in its own `tool_call_regex` and
`stream_tool_call_portion_regex` (lazy/greedy `.*` for the arguments, no
`DOTALL`), for its sep-token format rather than a fenced block. I kept this PR to
the parser the issue reports. Happy to fold V3.1 in here or send it separately,
whichever you prefer.
