# [Bugfix][Tokenizer] Handle trailing system messages in DeepSeek V3.2 rendering

[Upstream PR](https://github.com/vllm-project/vllm/pull/53768) · state: closed · merged: False

## Original PR description

## Purpose

Fixes #53737.

The DeepSeek V3.2 encoder writes a system turn that follows a user turn on the wrong side of the `<｜Assistant｜>` transition. The text lands inside the assistant reply, and when the system turn is last the prompt ends there with no generation prompt.

`user_msg_template` is `<｜User｜>{content}<｜Assistant｜>`, so the transition is already written by the time the system turn renders. `system_msg_template` is a bare `{content}`, which then appends past it.

On current main:

| Messages | Rendered |
| --- | --- |
| `system, user, system` | `<｜User｜>Hi<｜Assistant｜><think>Be brief.` |
| `system, user, system, assistant, user` | `<｜Assistant｜></think>Note.Hello!` |

The model reads the system text as its own output. V4 keeps the same text on the user side, after #51262.

This folds a qualifying system turn into the preceding user or developer turn, so the text is written before the transition. A system turn qualifies when it follows a user or developer turn and is either last or followed by an assistant turn. Python and Rust both change, matching how #51262 handled V4.

### Scope

#51262 used a trailing-only guard for V4 and said why: moving the transition out of the user template changes existing golden fixtures, which is what #43937 does and why it is still open. This change keeps the template and folds the content instead, so no fixture moves.

`user, system, user` still differs from V4, which drops the transition entirely when the next entry is neither an assistant turn nor the end. Reproducing that in V3.2 means moving `<｜Assistant｜>` out of `user_msg_template`, so I left it alone.

Thanks to @wuhangxian for reproducing the bug on the issue.

**<sub><sub>![P2 Badge](https://img.shields.io/badge/P2-yellow?style=flat)</sub></sub>  Keep context-boundary system messages in the output**

When `encode_messages` receives a context ending in a user/developer turn and the new `messages` begin with a trailing system turn, this predicate sees the preceding context entry and classifies the system message as folded. The earlier user turn is not rendered by the loop, however, so nothing consumes `_folded_system_content`; the system branch returns an empty string and the newly supplied instruction disappears entirely. Restrict folding to cases where the preceding user-like turn belongs to the currently rendered message slice.

**<sub><sub>![P2 Badge](https://img.shields.io/badge/P2-yellow?style=flat)</sub></sub>  Preserve metadata from folded system messages**

For a qualifying system message that carries `tools` or `response_format`, the fold transfers only `content`, after which the system branch returns before rendering either supported field. Such requests therefore silently lose their tool schemas or response-format constraint; the complete rendered system payload, not just its content, needs to be moved ahead of the assistant transition.
