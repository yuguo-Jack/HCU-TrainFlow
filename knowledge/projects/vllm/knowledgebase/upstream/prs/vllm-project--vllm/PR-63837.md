# [Perf][DSV4.1] Make the fused all-reduce + mHC token cap configurable

[Upstream PR](https://github.com/vllm-project/vllm/pull/63837) · state: open · merged: False

## Original PR description

## Purpose

Make the DeepSeek-V4.1 fused all-reduce + mHC token cap configurable through `--kernel-config '{"mhc_overlap_max_tokens": N}'`. **The default stays 16, so behaviour is unchanged unless the knob is set.**

`MHC_OVERLAP_MAX_TOKENS` (#57603, #57643, #58586) was tuned on GB200 and hardcoded at 16. With DSpark k=5 every sequence verifies 6 tokens, so 16 covers only two sequences, and anything larger runs the unfused path. The same cap sizes the Lamport buffer, gates the overlap path, and drives the MoE top-k finalize deferral, so it is one engine-config property. It is read per engine from `KernelConfig`, validated (`> 0`), and hashed with the rest of the kernel config, instead of being an import-time constant.

I am **not** proposing a new default. #57643 reports that extending fusion to 24-128 tokens regressed model-forward time on GB200, and I could not reproduce that on B300. The numbers below are meant to show the knob is useful on at least one platform and to ask whether a per-platform or per-spec-decode default is wanted.

## Test Plan

Kernel correctness above 16 tokens, on 4x B300 (TP4), CuTe DSL fused all-reduce + mHC and the finalize path against the unfused torch reference, eager, CUDA-graph replay and replay after in-place input changes:

`tests/distributed/test_custom_all_reduce.py::test_all_reduce_mhc_matches_unfused_path` is now parametrized over cap 16 (existing sizes) and cap 128 (sizes 1, 6, 12, 16, 17, 20, 24, 32, 48, 64, 96, 128, 33, 5, 128, 1).

## Test Result

Correctness (B300 x4): cap 16: 264 checks, 0 failures. Cap 128: 528 checks, 0 failures at every size including 17 and 20, where #57643 reported failures in its baseline's native top-k check. The parametrized test passes under pytest on 4x B300 (`2 passed`, cap16 and cap128); a standalone harness running the same checks gave the counts above.

Decode speed, B300 TP4, DeepSeek-V4.1-Flash, ~50k-token real source-code prefix (prefix-cached), closed-loop streams, p50 decode tok/s/user, two alternating runs per arm, 0 request errors. Noise between repeated arms is about +/-3-5%.

No speculative decoding (tokens per step = concurrency), cap 128 vs 16:

| Concurrency | 8k context | 51k context |
|---|---|---|
| 16 (fused in both) | -1.8% | +1.5% |
| 24 | +8.1% | +11.8% |
| 48 | +5.6% | +8.8% |
| 96 | inconclusive (one stalled run) | -1.3% |

DSpark k=5, adaptive verification off (6 tokens per sequence), 51k context:

| Sequences | 2 (12 tok) | 4 (24) | 8 (48) | 10 (60) | 16 (96) |
|---|---|---|---|---|---|
| cap 128 vs 16 | +0.4% | +12.6% | +7.5% | +13.2% | +13.6% |

DSpark k=5, adaptive verification on (the serving default), 51k context:

| Sequences | 2 | 4 | 8 | 10 | 16 |
|---|---|---|---|---|---|
| cap 128 vs 16 | -2.8% | -1.6% | +2.0% | +2.7% | +6.5% |

With adaptive verification on, the optimizer avoids the larger shapes, so the realized gain is smaller than the raw step-time gain.

Not measured here: GB200/GB300 (the platform #57643 measured), accuracy evals above 16 tokens (the kernel check is bitwise against the unfused path, but I did not run GSM8K/GPQA with the cap raised), and any model other than DeepSeek-V4.1-Flash.
