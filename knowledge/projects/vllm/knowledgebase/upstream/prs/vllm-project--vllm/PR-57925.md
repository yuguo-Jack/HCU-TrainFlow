## What this is

**Draft, do not merge.** This is my long-running `perf/rdna3_full_stack` branch: the
complete inference stack I run on 4× RX 7900 XTX (gfx1100, RDNA3, PCIe P2P — no XGMI). It
stays open as a single tracking PR so ROCm maintainers can see the whole picture and tell
me **which pieces are worth landing and in what order**. Each piece goes out as a small,
self-contained PR against a fresh `main`; nothing here is proposed for merge as-is.

The branch last merged `main` at `df417f780a` (2026-10-07). Measured against that
merge-base, the branch adds ~28k lines in 160 files; part of the commit list is merge
drift of work of mine that already landed (#41394, #44075, #40835, #39931, #55522,
#60388).

## What is in the branch

Grouped by what I think a landable PR would look like. Marked **generic** where the
change is platform-independent.

1. **HIP INT8/INT4 per-token-head attention kernels for gfx1100** — paged prefill
   (`csrc/attention/paged_prefill_attn_rdna3_v2*.cu`, INT8 with WMMA QK), split-KV decode
   (`pth_decode_int{4,8}_rdna3.cu`), a GQA-grouped decode, an INT8 decode on WMMA with
   independent waves, and a GQA-packed WMMA prefix attention for head size 256. A previous
   attempt was #41455 (closed). Related, different target: #43835 (CDNA). Largest block
   without a PR; I would split it into decode and prefill.
2. **Octave KV** — #59774. Pending for that PR: a per-layer exact window (the qwen4_exp
   MTP draft layer needs exact keys up to ~1000 positions back; with the default 64 it
   accepts ~15% fewer tokens per step) and `--kv-cache-dtype-skip-layers` support in the
   AMD QSA, both in this branch.
3. **qwen4_exp on AMD** — fp16 (#60650), fused HyperConnection (#60657), a 4-bit NF4
   n-gram embedding table (#60670, draft until #56273 lands: that PR adds NVFP4 through the
   same interface and rejects it on AMD), and the Octave main KV cache for the QSA (part of
   #59774). Related: #59442 (HyperConnection on CDNA through AITER), #55040 (FP8 n-gram
   table).
4. **RDNA3 W4A16 GEMM beyond #41394** — decode kernels for the 5..128-row GEMMs of
   speculative-decode verification (WMMA), a `v_dot2` kernel for fp16 at 1..10 rows, a
   128×128 WMMA prefill tile, an exact fp16 dequant and a deterministic split-K. No PR yet.
5. **RDNA3 W4A16 MoE** — asymmetric (zero-point) checkpoints, the next PR now that #60388
   is merged; cold-expert offload (#49321); an optional shared expert-LoRA.
6. **Triton prefill launch tuning for wave32** — BLOCK_M / num_warps by sequence length.
   Overlaps #52684 and #56232 (both open, by others).
7. **Hybrid KV page-size unification by LCM** (`70d00a2a23`) — **generic**. Needed when
   a Mamba/GDN state page and a quantized attention page disagree on block size.
8. **gfx11 custom all-reduce over PCIe P2P** — custom all-reduce and QuickReduce enabled
   on gfx11, plus my own all-reduce kernel (low-latency protocols, fused with the
   following RMSNorm). On a Z790 chipset host peer reads returned zeros while writes
   worked; on a PCIe switch host all P2P works. **Overlaps #57767** (open, by another
   author); if that lands, this block should be reconciled with it or dropped.
9. **Model Runner V2** — a prefill lane that runs long prefills concurrently with decode,
   sampling from gathered top-k logits under TP, and a restricted vocabulary for the MTP
   draft head (+6.3% tok/s, no acceptance loss). The prefill lane touches core
   scheduling and would need a design discussion first.
10. **ROCm correctness fixes** — blocking H2D for GDN chunk metadata and conv1d program
    indices, stale CUDA-graph `mid_o` pointer on the int8 decode path, unbounded split-K
    `mid_o` allocation, per-token-head KV metadata not refreshed on the spec-decode
    verify step, GDN readout buffer dtype, GDN reads/writes in place in spec decode.
    Several are **generic** or Mamba-generic, and are the ones I would send first.
11. **Unconditional zero-temperature guard in the sampler** (`0aa0085946`) —
    **generic**. The guard only ran when the batch already contained a greedy request,
    so a single `temperature=0` probe could poison a batch.
12. **Qwen3 tool parser: terminate a parameter at the surrounding structure**
    (`053a5b773d`) — **generic**. Overlaps #50955 (open, by another author).

## Measured results

Kernel microbenchmark, ctx=8000 ql=512, 2× RX 7900 XTX TP2, Qwen3.6-27B W4A16:

| Kernel | Time | vs Triton baseline |
|---|---|---|
| Triton INT8 per-token-head | ~25 ms | — |
| HIP INT8 | **3.03 ms** | **8.3×** |
| HIP INT4 | **3.05 ms** | **8.2×** |
| Triton FP16, default M16w4 | 11.2 ms | — |
| Triton FP16, tuned M64w4 | **3.0 ms** | **3.7×** |

End-to-end TTFT, same setup (attention is ~20% of runtime here, GEMM dominates, so an
8× kernel win yields ~10% e2e and grows with context):

| Prompt | Baseline FP16 | INT8 full stack | INT4 full stack |
|---|---|---|---|
| ~2K | 2.81 s | 2.74 s (−2.5%) | 2.78 s (−1%) |
| ~8K | 11.15 s | 10.99 s (−1.4%) | 11.25 s (+1%) |
| ~16K | 23.74 s | 22.52 s (−5.1%) | 22.96 s (−3.3%) |
| ~24K | 38.44 s | **34.84 s (−9.4%)** | **35.49 s (−7.7%)** |

KV cache capacity at a fixed 33.3 GB budget — the metric that actually decides what the
card can serve:

| KV dtype | Max context | Concurrent @8K | Concurrent @32K |
|---|---|---|---|
| FP16 | 136K | 17 | 4 |
| INT8 | 273K | **34** | **8** |
| INT4 | **545K** | **68** | **17** |

Qwen3.8-27B W4A16 G32, TP4, INT8 per-token-head KV, MTP k=3: sustained **113–119 tok/s
decode** at both short and 167K context, mean speculative acceptance 3.13/4 on real code
traffic.

Qwen3.8-Flash-Next pruned to 256 experts, GPTQ W4A16, TP4, 512K context, MTP k=3:

| | value |
|---|---|
| KV cache, fp16 → `octave_k3v3` | 398K → **1.98M tokens** |
| decode, one user | 105–114 tok/s (peaks ~149) |
| fused HyperConnection, fp16 KV, no MTP | 72.5 → **76.6 tok/s (+5.8%)** |
| MTP layer exact window 64 → 1020 | tokens per step +11–27% on code, JSON, tables and refactors, +3% on prose; 4.00/4 on a counting task |
| GSM8K (chat, no thinking, 200 q) | 96.0% |

Quality: INT8 per-token-head is cosine 1.000000 against the FP16 reference (symmetric,
no precision loss); INT4 is 0.999995.

## Why this is not mergeable as it stands

- 94 commits behind `main` today; every piece is rebased onto a fresh `main` when it
  goes out on its own.
- **No CI covers gfx1100.** The kernels are guarded to gfx1100 and compile out elsewhere
  (there are compile-guard tests for exactly that), but nobody in CI executes them. This
  is the main thing I want maintainers' opinion on.
- Blocks 6, 8 and 12 may be superseded by other people's open PRs listed above.

## What I am asking for

1. Are gfx1100 HIP attention kernels wanted in-tree at all, given no CI runs them? If
   yes, in what shape — alongside the CDNA ones of #43835, or separate?
2. Should the generic fixes (items 7, 10, 11) go out as small standalone PRs? I think yes.
3. For items 6, 8 and 12, tell me to stand down if the existing PRs cover it — I would
   rather review theirs than compete.
4. Is the Model Runner V2 prefill lane (item 9) something you would want as an RFC?
