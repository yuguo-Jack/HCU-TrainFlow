# [Bugfix] Don't assert on already-freed request in _update_from_kv_xfer_finished

[Upstream PR](https://github.com/vllm-project/vllm/pull/58200) · state: closed · merged: False

## Original PR description

## Purpose

Fixes #57938

For models with multiple KV cache groups (e.g. heterogeneous-attention models like Gemma-4, which mix sliding-window and global attention), `_update_from_kv_xfer_finished` could crash the entire `EngineCore` process with `AssertionError: assert req_id in self.requests`.

Each KV cache group can report transfer completion/failure independently and asynchronously across different scheduler steps, but they all share the same `req_id`. Sequence that triggers the crash:

1. Step N: one group's `finished_recving` succeeds for `req_id` → added to `finished_recving_kv_req_ids`.
2. Step N+1: a different group fails for the same `req_id` → `finish_requests()` sees `req_id` already in `finished_recving_kv_req_ids`, skips the delay-free guard, and deletes the request from `self.requests` immediately.
3. Same step N+1: a trailing/duplicate `finished_recving` signal for that same `req_id`, processed later in the same `update_from_output()` call, hits the assert and crashes.

This replaces the two `assert req_id in self.requests` checks in `_update_from_kv_xfer_finished` (for `finished_recving` and `finished_sending`) with a guard that logs and skips an already-freed `req_id` instead of crashing — since the request being gone is a real, reachable state for multi-group requests, not an invariant violation.

## Test Plan

Added `test_failure_after_partial_finished_recving_crashes` to `tests/v1/kv_connector/unit/test_kv_load_failure_recovery.py`, using a mocked HMA-capable connector (`MockHMAConnector`) with a 2-group scheduler (`swa_enabled=True`) to reproduce the same race condition without requiring LMCache or GPU hardware.

```bash
pytest tests/v1/kv_connector/unit/test_kv_load_failure_recovery.py -v
```

## Test Result

After the fix: all 15 tests in `test_kv_load_failure_recovery.py` pass, including the new regression test and the existing single-group / multi-group failure-policy tests (no change in behavior for the previously-passing cases).
