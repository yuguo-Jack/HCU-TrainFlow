# [Spec Decode] Adaptive verification: wait for stale confidences only when ranking drafts

[Upstream PR](https://github.com/vllm-project/vllm/pull/63355) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

`record_confidences` blocked the CPU on the previous step's confidence copy at every step, adding 3-5 ms prefill latency to DSpark adaptive verification (AV). Wait in `get_num_tokens` instead, only when drafts are scheduled.

## Claims

- Removes AV's prefill overhead vs. fixed K, with unchanged acceptance.
- Full-model (DeepSeek-V4.1-Flash) results to follow.

## Validation

Small [DeepSeek-V4-Flash-DSpark](https://huggingface.co/inference-optimization/DeepSeek-V4-Flash-DSpark-2.1B-A1.9B-small) (dummy weights), 1×H100, 8K random prompts, 16 output tokens, c=1, 3 trials. Server prefill time (`vllm:request_prefill_time_seconds`):

| branch | variant | prefill (ms) | AL |
|---|---|---|---|
| main | K=5 | 47.7 ✅ | 5.76 |
| main | K=5 + AV | 51.2 🐌 | 5.74 |
| this PR | K=5 + AV | 46.6 ✅ | 5.76 |

## Details

- **Root cause:** the previous step's copy is ordered after all its GPU work, so syncing on it right after launching the next step stalled the CPU (profile: extra `cudaEventSynchronize` after prefill, identical GPU work).
- **Fix:** wait one step later, when the budget reads the copy. By then it has landed, so the wait is free.
- **Pending-reset list → step counters:** a row is used only if its copy is newer than its request, otherwise 1.0. Same behavior, but no CPU writes into buffers with in-flight copies.
