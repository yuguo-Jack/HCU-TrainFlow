## Original PR description

  # [XPU] Add Qwen4Exp (Qwen3.8-Flash-Next) model architecture support

  Adds the `xpu/` sibling to the existing `amd/` and `nvidia/` implementations under
  `vllm/models/qwen4_exp/`, routed through the existing platform dispatch. It reuses
  `Qwen3NextAttention`, `QwenGatedDeltaNetAttention` and `Qwen3NextSparseMoeBlock`, so
  it is much smaller than the other two backends.

  **Changes outside the model package**

  - `speculator.py` / `llm_base_proposer.py` - the MTP hidden buffer was widened via
    `hc_mult` (the DeepSeek-V4 spelling). Qwen4Exp calls it `hc_count`, so the `getattr`
    fell back to 1 and the MTP head got an un-widened buffer. Both names now accepted.
  - `inc_wna16_linear.py` - guard the `qzeros` copy, which can be empty or mismatched
    under symmetric group quantization and crashed weight load on the 512 routed experts.

  **`layer_types`** - Transformers v5.18 renames `full_attention` to `indexed_attention`;
  all three spellings map to the dense GQA block here. This does not branch on
  `indexer_n_heads` like `amd/`/`nvidia/` do: on `Qwen3.8-Flash-Next-W4A16` that field is
  set (`4`) but the checkpoint ships no indexer tensors, so keying off it would pick a QSA
  path the weights cannot feed.

  **Known limitations** - no QSA/indexer path on XPU (such checkpoints fail at weight load
  rather than silently running dense attention); TP=4 needs `--enable-expert-parallel`
  (`moe_intermediate_size=640 / 4 = 160` is not divisible by `group_size=128` - checkpoint
  arithmetic, not an XPU limit); requires `transformers >= 5.16.1`, same as the other
  backends; TP=4 validated with `--enforce-eager` only.
  
**model** - https://huggingface.co/devan-carlin/Qwen3.8-Flash-Next-W4A16

1. **INT8 row-scale table:** 160 × int8 plus one fp32 scale per row. Relative L2 error 0.66 %, against 2.65 % for FP8 with one global scale, at 48.9 GiB of pinned host RAM against 95.4 GiB for BF16. File: `vllm/v1/worker/gpu/spec_decode/speculator.py` · line 136

  Not XPU-specific - it's model-specific, so CUDA/ROCm hit the same path.

  The attribute name comes from the HF config (`Qwen4ExpTextConfig`), not from the
  platform. On `Qwen3.8-Flash-Next` it is `hc_count = 4` and `hc_mult` is absent, so
  `getattr(hf_config, "hc_mult", 1)` silently returns 1 and the HC-widened buffer is
  left at `hidden_size` instead of `hc * hidden_size`.

  Nothing gates that branch on the platform: `_target_feeds_hc_residual()` keys on
  `hasattr(target_cls, "get_mtp_target_hidden_states")`, and both
  `qwen4_exp/nvidia/model.py` and `qwen4_exp/amd/model.py` define that method, so a
  CUDA or ROCm run of Qwen4Exp + MTP goes through the same code. 

  Caveat on what I actually measured: I reproduced and verified the fix on XPU only
  (no CUDA/ROCm hardware on hand). The CUDA/ROCm claim above is from reading the
  shared code path, not from a run. If you can try Qwen4Exp + MTP on CUDA, I'd expect
  the same un-widened buffer; happy to be corrected if the draft path differs there.
