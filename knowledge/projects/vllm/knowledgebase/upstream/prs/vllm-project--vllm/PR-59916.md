# [Feature][DCP] --dcp-gather: gather-based DCP for MLA attention without native DCP (+ DSv4)

[Upstream PR](https://github.com/vllm-project/vllm/pull/59916) · state: open · merged: False

## Overview

`--dcp-gather` runs decode context parallelism (DCP) for MLA models whose attention backends can't run DCP natively.
- The KV cache keeps native DCP's block-sharded layout, so capacity scales with the DCP size as usual.
- Before each layer's attention, every rank pulls the batch's pages from the other ranks into a scratch cache, and attention runs as if DCP were off. Attention backends are unmodified.
- The pull runs on a side stream through symmetric memory, overlapped with the previous layer's output projection and MoE.
- DeepSeek-V4, which has no native DCP, always uses it.

It is an alternative to layer-sharded KV (KVPP, #59059).

Related fixes, split out:
- #59951: native DCP group rank order when the group spans TP × PCP (needed for the native-DCP baseline below).
- #59961: DSv3.2 top-k across PP stages (needed for correct PP results).

## Results

All numbers are from 2026-10-06 on 4x B300, Inferact/GLM-5.3-NVFP4, 32 GiB/GPU KV budget.

- **KV capacity.** Gather-DCP holds 2.40M tokens at TP1×PCP4 and TP4. Native DCP holds 2.54M, KVPP 2.18M, and no DCP 637K.
- **Working set fits (TP1×PCP4, 24 prefixes).**
  - Gather-DCP runs at 146.0K tok/s, against 144.1K for native DCP and 142.7K for KVPP.
  - That is 2.85x no DCP (51.5K), whose 637K-token cache can't hold the 1.44M-token working set.
- **Working set near capacity (36 prefixes, 2.16M tokens).** Gather-DCP runs at 122.3K tok/s, against 127.6K for native DCP and 98.3K for KVPP.
- **Where native DCP is slow or missing.**
  - TP4: 62.2K tok/s, 1.57x native DCP (39.7K) and level with KVPP (62.2K).
  - PP2×TP2: 102.0K tok/s, 1.73x no DCP (59.0K) and level with KVPP (102.1K).
  - DeepSeek-V4 gets DCP with no attention-backend changes.
- **Overhead.** On a working set that even the replicated cache holds, gather-DCP is about 1% slower than no DCP. On an interleaved A/B it is about 2% faster than KVPP.
- **Accuracy.** GSM8K matches the baselines on GLM-5.3, DeepSeek-V4-Flash and DeepSeek-V2-Lite.

## How it works

- **KV layout.** The engine plans the KV cache exactly as for native DCP: a block spans `N` pages, and rank `r` stores page `r`. Scheduler, prefix caching and block IDs are unchanged; there are no engine or scheduler changes.
- **Worker.** Gather mode sets the worker's DCP size to 1 before distributed init, so attention runs unsharded. The KV cache is allocated from torch's symmetric-memory pool so that peers can read it directly. Every layer with the same cache shape shares one scratch cache with `N`x the blocks; kernel block `b*N + r` is page `r` of block `b`.
- **Per forward,** on one side stream, in layer order:
  1. Pull layer 0's pages of the batch's blocks from every rank.
  2. When layer `l` releases its cache (after its attention), copy this rank's pages of the blocks the forward wrote back to its own cache, then pull layer `l+1`.
  3. Layer `l` acquires its cache (waits for its pull) before its first KV access, then writes its new KV into the scratch cache as usual.
  4. One symmetric-memory barrier per forward orders peers' reads of the write-backs against block reuse.
- **Data movement.** New tokens need no communication: every rank computes all of them (the MLA latent is replicated under TP, and PCP gathers KV before the insert). Each rank pulls the other `(N−1)/N` of the old tokens, which is the minimum. Blocks shared by several requests are copied once.
- **Hooks.** Layers call `acquire`/`release` around their KV accesses in the generic MLA cache-update and attention ops, the sparse indexer, DSv3.2's attention and DSv4's attention. The model runner builds the runtime with the KV cache and calls it once per step.
- **Capacity.** One scratch cache per cache shape comes out of the KV budget. For GLM-5.3 at `N=4` that leaves 2.40M tokens, versus KVPP's 2.18M and native DCP's 2.54M.

**Size.** About 480 lines including the unit test; about 280 of them in the new `generic_kvp.py`. No engine, scheduler, `vllm/distributed` or attention-backend changes.

## Limitations

- **Single NVLink domain only** (symmetric memory).
- **MRV2 and MLA caches only.** FULL CUDA graphs are downgraded to PIECEWISE.
- **Rejected at startup:** spec decode, DBO/microbatching, elastic EP, in-process executors and sleep mode.
- **Not yet supported:** layerwise KV connectors, HiSparse, and DSv4 with PCP (main has no DSv4 PCP; see #59857).
- **Decode** pulls the full history every step. The target is prefill (e.g. P/D prefill nodes); use native DCP for decode where it is supported.

**Duplicate check.** No open PR implements generic gather-based DCP. #59059 (KVPP) is the layer-sharded alternative compared here. #57239, #44573 and #56738 add native DeepSeek-V4 DCP through backend or kernel changes.
