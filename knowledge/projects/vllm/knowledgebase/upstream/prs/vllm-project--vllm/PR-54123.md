# [Bugfix] Reject incompatible mamba_ssm_cache_dtype before it crashes EngineCore

[Upstream PR](https://github.com/vllm-project/vllm/pull/54123) · state: open · merged: False

## Original PR description

[Bugfix] Reject incompatible mamba_ssm_cache_dtype before it crashes EngineCore

The Mamba1 selective_scan CUDA kernel (csrc/libtorch_stable/mamba/ selective_scan_fwd.cu) only supports an SSM state dtype that is either float32 or exactly equal to the model's activation dtype -- its dispatch macro instantiates state_t from ssm_states.scalar_type() while u (the activation input) drives input_t, and the kernel asserts state_type == input_type || state_type == float32 before it will run.

MambaStateDtypeCalculator.mamba1_state_dtype() resolved mamba_ssm_cache_dtype independently of the model's compute dtype whenever it was set to an explicit value, so a config like --dtype float16 --mamba-ssm-cache-dtype bfloat16 passed straight through config validation and model loading, and only failed once the first request hit selective_scan_fwd inside EngineCore, killing the engine with a bare STD_TORCH_CHECK failure at line 791.

Validate the combination in mamba1_state_dtype() itself, where both the model's activation dtype and the requested cache dtype are already available, and raise a clear ValueError naming the incompatible dtypes and how to fix the config. This runs during KV-cache-spec construction at engine init, well before any request reaches EngineCore.

Mamba2 and GatedDeltaNet layers never call selective_scan_fn -- they use mamba_chunk_scan_combined_varlen / selective_state_update instead, which don't share this constraint -- so the check is scoped to mamba1_state_dtype() only and mamba2_state_dtype()/gated_delta_net_state_dtype() are left untouched.

Fixes #53239

## Purpose

`mamba_ssm_cache_dtype` currently accepts a dtype independent of the model's activation dtype, but the Mamba1 `selective_scan_fwd` CUDA kernel only supports an SSM state dtype that is `float32` or exactly equal to the model's activation dtype. Any other explicit combination passes config validation and model loading today, then crashes EngineCore on the very first request with `RuntimeError: selective_scan_fwd, .../selective_scan_fwd.cu:791`.

This PR moves that validation into `MambaStateDtypeCalculator.mamba1_state_dtype()`, so the incompatible combination is rejected with a clear `ValueError` during KV-cache-spec construction at engine startup, instead of killing EngineCore mid-request. Mamba2 and GatedDeltaNet don't go through `selective_scan_fn`, so the check is intentionally scoped to `mamba1_state_dtype()` only.

No open PR addresses this issue as of this writing (checked via issue comments and a PR search on #53239).
