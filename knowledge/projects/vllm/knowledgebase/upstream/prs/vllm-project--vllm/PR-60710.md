# [ROCm][Perf] W4A16: opt-in dense weight cache for RDNA hybrid prefill

[Upstream PR](https://github.com/vllm-project/vllm/pull/60710) · state: closed · merged: True

## Original PR description

## Overview

Adds opt-in `KernelConfig.rdna_hybrid_w4a16_prefill_dequant` (`"enable"`/`"disable"`, case-insensitive, default `"disable"`). When it is `"enable"`, `RDNAHybridW4A16LinearKernel` caches a dense fp16/bf16 copy of each weight at load time and runs GEMMs with `M >= 256` on it, so prefill no longer dequantizes int4.

## Claims

- TTFT −22% to −26% on Qwen3-4B/8B w4a16 and −21% on Gemma-4-31B AWQ with MTP-3, on Strix
  Halo (gfx1151). TPOT is unchanged at concurrency 1.
- No accuracy change: GSM8K is within ±0.6 pp.
- Decode, small batches and spec-decode verify stay on the int4 path.
- Disabled by default, which leaves current behaviour unchanged.

## Validation

Usage: `--kernel-config '{"rdna_hybrid_w4a16_prefill_dequant": "enable"}'`. `vllm bench serve` with random 2048 in, concurrency 1, `disable` vs `enable` on the same build, interleaved (3 pairs per Qwen model, 2 for Gemma); values are the mean of per-run medians. Measured only on gfx1151; the kernel also runs on other gfx11/gfx12 parts, where the `M >= 256` threshold may need tuning.

| Model | TTFT disable → enable | TPOT disable → enable |
| --- | --- | --- |
| RedHatAI Qwen3-8B w4a16, fp16 (asym) | 1328 → 1033 ms (**−22.2%**) | 27.7 → 27.7 ms |
| RedHatAI Qwen3-8B w4a16, bf16 (asym) | 1341 → 1023 ms (**−23.7%**) | 28.2 → 28.2 ms |
| RedHatAI Qwen3-4B w4a16, fp16 (sym) | 782 → 578 ms (**−26.1%**) | 16.4 → 16.5 ms |
| cyankiwi Gemma-4-31B AWQ, MTP-3, 128 out | 8.75 → 6.88 s (**−21.4%**) | 68.0 → 67.2 ms |

Disabled matches current main (554340f3d3) within 1% TTFT on all four models.

At concurrency 16 (Qwen3-8B fp16, 512 in / 256 out, 64 prompts, 2 pairs): TTFT 3069 → 2252 ms (−26.6%), TPOT 85.2 → 83.1 ms.

GSM8K (in-tree `tests/evals/gsm8k`, 5-shot, 500 questions, concurrency 16), Qwen3-8B: fp16 0.886 → 0.880, bf16 0.872 → 0.878.

`pytest tests/kernels/quantization/test_rdna_hybrid_w4a16.py`: All 293 passed on gfx1151.

## Details

- **Why opt-in:** the copy is 4x the int4 layer weight and is taken from the `gpu_memory_utilization` budget, so it comes out of KV cache. Qwen3-8B: +13.5 GiB weights, −13.5 GiB KV. Gemma-4-31B: weights 20.2 → 75.1 GiB, KV 71.6 → 16.6 GiB. The trade targets unified-memory parts like Strix Halo, where TTFT matters more than KV capacity. Enabling it caches every layer or none: if the copies do not fit while leaving 4 GiB of activation headroom plus KV cache for one `max_model_len` request, startup fails with an error naming the option. It is a mode string rather than a bool so further modes can be added without renaming it.
- **Why `M >= 256`:** below it the dense GEMM is still memory bound and reads 4x the bytes. Per-GEMM on gfx1151 it is up to 2.3x slower than int4 on Gemma-4-31B MLP shapes. At 256 and above it is no slower on any Qwen3-8B or Gemma-4-31B shape measured.
- **Limitation:** the dense copy is built once at load time, so in-place weight reloads (`reload_weights`, RL weight sync through the weight-transfer engines) are not supported with `"enable"`. The option is intended for pure inference; keep it `"disable"` when weights are updated at runtime.

### Related Work
- no open PR caches a dense copy of W4A16 weights for this kernel.
- #55711 makes the int4 prefill dequant cheaper, and this PR skips it, so the two stack. On top of #55711 this PR still cut TTFT by 6.7% (Qwen3-8B fp16), 12.8% (Qwen3-4B fp16) and 23.0% (Qwen3-8B bf16, since #55711 is fp16 only)
- #52637 (int4 repack in `process_weights_after_loading`) and #55742 (profiler labels) touch the same file, so whichever lands second needs a small rebase.
- #53709 applies the same idea (opt-in load-time dequant for prefill) to DeepSeek-V4 MXFP4 experts on another GPU family. It's a different kernel with no shared code path.
