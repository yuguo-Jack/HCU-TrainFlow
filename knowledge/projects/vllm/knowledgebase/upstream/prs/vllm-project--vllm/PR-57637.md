# [Frontend] Notify systemd (READY=1) once the HTTP server is serving

[Upstream PR](https://github.com/vllm-project/vllm/pull/57637) · state: open · merged: False

## Original PR description

## Purpose

Running `vllm serve` as a `Type=notify` systemd unit does not work today: nothing ever sends
`READY=1`, so the unit stays `activating` until `TimeoutStartSec` even though the server answers.
Users fall back to `Type=simple`/`Type=exec` — the unit is "started" the moment the process is
spawned, tens of seconds to minutes before the model can be queried — and poll `/health` from the
outside, or wrap `vllm serve` in a script that does.

This PR makes the launcher send `READY=1` on the socket systemd passes in `NOTIFY_SOCKET`, once
uvicorn reports `started` (sockets bound, startup hooks run). With that, `systemctl start` blocks
until the server is usable, `After=`/`Requires=` dependencies mean what they say, and
`systemd-run --property=Type=notify … vllm serve …` returns exactly when the model can be queried.

- `vllm/entrypoints/launchers/utils/sd_notify.py`: a minimal sd_notify(3) client, standard
  library only (`AF_UNIX`/`SOCK_DGRAM`, abstract namespace handled). A no-op when `NOTIFY_SOCKET`
  is unset (not under systemd, or `NotifyAccess` forbids it); an unreachable socket is logged,
  never fatal.
- `vllm/entrypoints/launchers/launcher.py`: `serve_http` schedules a small task that waits for
  `server.started`, then notifies and logs `Notified systemd that the server is ready`. It gives
  up if the server task ends first and is cancelled with the other tasks.
- `tests/entrypoints/launchers/test_sd_notify.py`: unit tests for the notifier (no socket,
  filesystem socket, abstract socket, unreachable socket) and one for `serve_http` — the datagram
  arrives only when the server already answers HTTP.
- `docs/deployment/systemd.md`: a unit file example (`Type=notify`, `NotifyAccess=all`,
  `TimeoutStartSec`) and the transient-unit form.

No new dependency, no behaviour change outside a notify unit.

This PR includes AI-generated code (Claude, `Co-Authored-By` trailer on the commit); every line
was reviewed by me and the change was validated end-to-end as described below.

## Test Plan

```sh
pytest -q tests/entrypoints/launchers/test_sd_notify.py
pre-commit run --files vllm/entrypoints/launchers/launcher.py \
  vllm/entrypoints/launchers/utils/sd_notify.py tests/entrypoints/launchers/test_sd_notify.py

# end to end, as a transient notify unit:
systemd-run --user --property=Type=notify --property=NotifyAccess=all \
  --property=TimeoutStartSec=3600 --unit=vllm-notify-test -- \
  vllm serve OpenLLM-France/Luciole-1B-Base --port 8011 --enforce-eager --max-model-len 2048
# blocks until the server serves, then:
curl -s localhost:8011/health -o /dev/null -w '%{http_code}\n'
journalctl --user -u vllm-notify-test -o short-precise \
  | grep -E 'Starting vLLM server|Application startup|Notified systemd|Started vllm'
```

Without the patch the same command sits in `activating` (`systemctl --user is-active
vllm-notify-test`) until the timeout, while `/health` already answers 200.

## Test Result

- `5 passed` (`test_sd_notify.py`, Python 3.12); ruff check/format clean.
- End to end on a single RTX 3060, `OpenLLM-France/Luciole-1B-Base`, `--enforce-eager`:

```
21:54:35.907 vllm:    [entry.py:139] Starting vLLM server on http://0.0.0.0:8011
21:54:35.936 vllm:    INFO:     Waiting for application startup.
21:54:36.329 vllm:    INFO:     Application startup complete.
21:54:36.329 vllm:    [launcher.py:118] Notified systemd that the server is ready
21:54:36.329 systemd: Started vllm-notify-test.service      ← READY=1 received
```

`systemd-run` returned ~60 s after spawn, 0.3 ms after uvicorn's "Application startup
complete"; `/health` answered 200 on the first request. The same unit run outside systemd
(no `NOTIFY_SOCKET`) starts as before, without the log line.
