# [ROCm][Model] Muse Spark: share one RoPE cache sized by max_model_len

[Upstream PR](https://github.com/vllm-project/vllm/pull/62757) · state: closed · merged: True

## Original PR description

## Overview

The ROCm Muse Spark model builds a separate fp32 RoPE cache in each of its 46 sliding-window attention layers. Each cache is sized for 1,048,576 positions, whatever `max_model_len` is, for about 11.5 GiB per GPU. This PR shares one cache across those layers and sizes it by `max_model_len`. Follow-up to #62622.

## Claims

- About 11.5 GiB per GPU is freed for the KV cache pool: from 46 caches of `[1048576, 64]` fp32 to one `[max_model_len, 64]` cache. That is 8 MiB at `max_model_len` 32768 and 192 MiB at 786432. This is an estimate from tensor sizes and has not been measured on a GPU. With `VLLM_ROCM_USE_AITER_TRITON_ROPE=1`, the per-layer bf16 copies, about 5.75 GiB more, are shared too.
- Numerics are unchanged. Every row of the cos/sin table is computed the same way regardless of its length, and positions never reach `max_model_len`.
- The DSpark draft is unchanged: it keeps its own cache at its current size.

## Validation

The new test builds two target attention layers. It requires them to hold the same `RotaryEmbedding` instance and that instance's cache to be fp32. It fails on the base commit and passes with this PR:

These runs were CPU-only, in the ROCm image with no GPU attached. Because of that, the ROCm architecture query and device detection were stubbed locally. **Not yet done:** a GPU run comparing the KV cache size reported at startup before and after, and an accuracy check such as GSM8K with greedy output compared against the base. Both are needed before this PR leaves draft.

## Details

**Root cause.**
- Each target `MuseSpark1xAttention` constructs its own `RotaryEmbedding` (`vllm/models/muse_spark/amd/model.py:491`).
- The decoder layer passes it `max(config.max_position_embeddings, max_model_len)` (`amd/model.py:707`), and the checkpoint sets `max_position_embeddings` to 1,048,576.

**Changes.**
- **Size.** Target layers use `max_model_len`. The target RoPE is unscaled, and the scheduler keeps input positions below `max_model_len`, including padded speculative-decoding verify slots (`vllm/v1/core/sched/scheduler.py:770`).
- **Sharing.** Target layers get their RoPE from `get_rope`, which returns one instance per configuration (`vllm/model_executor/layers/rotary_embedding/__init__.py:84`). All sliding-window layers use theta 500000, so there is one cache.
- **Draft.** DSpark draft layers keep their own instance and the larger size, because draft blocks can run past `max_model_len`. Keeping them separate also means the draft's unfused RoPE path cannot recast the target's shared table.
- **Guard.** The fused QK-norm/RoPE/KV-insert path asserts that the shared table is still fp32. The kernel accepts either fp32 or the qkv dtype, so a recast table would otherwise silently switch it to bf16 RoPE.

**Related PRs.**
- #63078 stops the unfused attention path and the DSpark context-key precompute from replacing the fp32 table with a bf16 copy. It complements this PR: that PR keeps tables fp32, and this one makes the target share a single, smaller table. The two edit different hunks of `amd/model.py`. Both add `vllm/models/muse_spark/` to the MI355 step's dependencies, so whichever merges second needs a trivial rebase.
- No other open PR shares or resizes the Muse target RoPE cache, so this is not a duplicate. #62064 resized the cache for the NVIDIA path of the superseded #61879, and main has no NVIDIA Muse path.

**Test limitation.** The test replaces the TP linears and the attention backend with `nn.Identity`, and passes a `SimpleNamespace` config. That keeps the test CPU-only and free of a checkpoint, but conflicts with `tests/AGENTS.md`'s preference for real constructors, and is noted for reviewers.

## KV cache and GSM8K: main vs this PR

**Setup.** 8x MI355X, TP8, `amd/Muse-Spark-Open-816B-A42B-Quark-MXFP4`, no speculative decoding. Image `vllm/vllm-openai-rocm:nightly-rocm100-df6603f05` (aiter 0.1.26, torch 2.13.0+rocm10.0.0), with each tree's Python overlaid; base is main 2de0531d81. Server flags are the AMD MXFP4 recipe's:

```bash
VLLM_ROCM_USE_AITER=1 VLLM_ROCM_MUSE_MOE_REDUCE_DTYPE=bf16 VLLM_USE_BREAKABLE_CUDAGRAPH=1 \
vllm serve amd/Muse-Spark-Open-816B-A42B-Quark-MXFP4 \
  --tensor-parallel-size 8 --dtype bfloat16 --distributed-executor-backend mp \
  --language-model-only --compilation-config '{"cudagraph_mode":"FULL_AND_PIECEWISE"}' \
  --no-enable-prefix-caching --enable-chunked-prefill --attention-backend ROCM_AITER_FA \
  --max-model-len 32768 --max-num-seqs 128 --max-num-batched-tokens 8192 \
  --gpu-memory-utilization 0.90

# 5-shot, all 1,319 questions, max 256 tokens, 64 concurrent requests
python tests/evals/gsm8k/gsm8k_eval.py --port 8000 --num-shots 5 --max-tokens 256 --max-concurrency 64 --temperature 0
python tests/evals/gsm8k/gsm8k_eval.py --port 8000 --num-shots 5 --max-tokens 256 --max-concurrency 64 --temperature 1.0 --seed 42
```

Accuracy is shown ± one binomial standard error (n = 1,319). Sampled runs also use the model's default `top_k` 64 from its generation config.

**KV cache at startup**, from the server log:

| Code | Available KV cache memory | GPU KV cache size | Max concurrency at 32,768 tokens |
|---|---|---|---|
| main 2de0531d81 | 167.67 GiB | 8,173,209 tokens | 249.43x |
| this PR | **179.17 GiB** | **8,733,353 tokens** | **266.52x** |
| difference | **+11.50 GiB** | **+560,144 tokens (+6.9%)** | **+17.09x** |

The measured +11.50 GiB per GPU matches the 46 x [1048576, 64] fp32 tables this PR removes (11.5 GiB).

**GSM8K**, batch-sharded sampling off:

| Code | Greedy accuracy | Sampled accuracy, T=1.0 | Invalid answers, greedy / sampled |
|---|---|---|---|
| main 2de0531d81 | 0.9507 ± 0.0060 | 0.8196 ± 0.0106 | 0.000 / 0.007 |
| this PR | 0.9500 ± 0.0060 | 0.8264 ± 0.0104 | 0.000 / 0.006 |

Accuracy is unchanged within one standard error for both greedy and sampled decoding. Throughput is also unchanged: greedy took 122.3 s on main and 121.3 s with this PR, at 10.8 questions/s.
