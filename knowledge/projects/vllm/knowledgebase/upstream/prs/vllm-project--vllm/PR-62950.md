# [Bugfix][Model] Size RoPE cos/sin cache to max_model_len for unscaled RoPE

[Upstream PR](https://github.com/vllm-project/vllm/pull/62950) · state: open · merged: False

## Original PR description

## Purpose

When `VLLM_ALLOW_LONG_MAX_MODEL_LEN` sets `max_model_len` above the model's native `max_position_embeddings`, the RoPE cos/sin cache is still sized from the native limit. Positions at or beyond that limit index out of bounds: in graph/compile mode the compiled `index_select` hits a Triton bounds assertion and crashes; in eager mode the C++ kernel does an unchecked pointer read and silently returns garbage cos/sin values.

The defect is platform-independent — the cache is undersized on every backend. It was observed on XPU (Llama-3-70B-Instruct FP8 TP4, graph mode, `--max-model-len 9472` with native `max_position_embeddings=8192`), but the same compiled `index_select` crashes on CUDA without RoPE fusion, and the eager/fused path silently corrupts RoPE output on CUDA/ROCm/XPU alike.

### Crash reproduction

```
Assertion `index out of bounds: 0 <= tl.broadcast_to(tmp30, [XBLOCK]) < 8192` failed.
RuntimeError: cancelled  →  HTTP 500 on all in-flight requests
```

The crash fires at the first decode step (position 8192) after an 8192-token prefill. KV cache usage was 5.4% — not an OOM issue. Raising `--max-num-batched-tokens` to 9472 did not help, confirming the bound originates in `config.json`, not in that flag.

### Root cause

`LlamaDecoderLayer.__init__` reads `max_position_embeddings` from the HF config (`llama.py:266`) and passes it to `get_rope(max_position=...)`. `RotaryEmbeddingBase._compute_cos_sin_cache` (`base.py:97`) builds the cache with exactly that many rows:

```python
t = torch.arange(self.max_position_embeddings, dtype=torch.float)
```

`forward_static` (`base.py:173`) indexes it directly:

```python
cos_sin = cos_sin_cache.index_select(0, positions)
```

Nothing in the RoPE layer consults `max_model_len`, so the cache has `max_position_embeddings` rows regardless of the serving context length.

### Why it crashes in graph mode but not eager

In graph/compile mode (inductor + non-NONE), vLLM disables all custom ops (`custom_ops.append("none")`, `vllm.py:1791-1793`). `CustomOp.dispatch_forward` then returns the compiled `forward_native` (`custom_op.py:189-192`), which calls `forward_static` → `index_select`. Inductor lowers `index_select` to a Triton kernel with a bounds assertion.

In eager mode (`CompilationMode.NONE`), custom ops are enabled (`custom_ops.append("all")`, `vllm.py:1795`), and `dispatch_forward` returns `forward_cuda`/`forward_xpu` → `ops.rotary_embedding()`, a C++ kernel that indexes the cache with raw pointer arithmetic and no bounds check (`pos_encoding_kernels.cu:92-93`). This avoids the crash but performs a genuine out-of-bounds read, returning undefined cos/sin values for every position ≥ 8192.

On XPU, the RoPE fusion passes that would re-enable the custom op in graph mode (`fuse_rope_kvcache`, `fuse_rope_kvcache_cat_mla`) are force-disabled (`platforms/xpu.py:358-360`), so the compiled `forward_native` path is unavoidable. On CUDA without RoPE fusion (optimization level 0/1) the same compiled `index_select` crashes; with fusion or in eager mode the unchecked OOB read produces silent data corruption.

### Fix

In `LlamaDecoderLayer.__init__`, raise the local `max_position_embeddings` to `max(max_position_embeddings, max_model_len)` before it flows into `get_rope()`, so the cache covers every position up to `max_model_len - 1`:

```python
max_model_len = vllm_config.model_config.max_model_len
_rope_params = getattr(config, "rope_parameters", None)
_rope_type = (_rope_params or {}).get("rope_type", "default")
if max_model_len is not None and _rope_type == "default":
    max_position_embeddings = max(max_position_embeddings, max_model_len)
```

### Why the `rope_type == "default"` gate

Gated on `rope_type == "default"` (unscaled RoPE) because scaled variants derive `inv_freq`, `mscale`, or cache stride from `max_position_embeddings` — inflating it there would change RoPE values at every position, not just beyond the native limit. The gate expression matches `get_rope()`'s dispatch (`rotary_embedding/__init__.py:62-64`), so the cache is enlarged **only when** `get_rope()` selects the unscaled `"default"` branch.

| `rope_type` | What inflation would break |
|---|---|
| `linear` | cache becomes `mpe × factor` rows (`linear_scaling_rope.py:90`) — already-sufficient buffer inflated again |
| `dynamic` | NTK base recomputed from a ratio (`dynamic_ntk_scaling_rope.py:61`) |
| `longrope` | `short_mscale` / `long_mscale` (`phi3_long_rope_scaled_rope.py`) multiply cos/sin at every position |
| `yarn` / `deepseek_yarn` / `deepseek_llama_scaling` | pass `original_max_position`, not `max_position` — harmless, but gated anyway |

`rope_parameters` is guaranteed normalized (`patch_legacy_rope_type` runs during config loading via `get_config()`, before model construction), so legacy `type` → `rope_type`, `su` → `longrope`, and `mrope` → `default` conversions are handled before this code runs.

### Safety

No-op when `max_model_len <= max_position_embeddings` (the `max()` returns the native value). Does not mutate `config`, so `derived_max_model_len` and the `VLLM_ALLOW_LONG_MAX_MODEL_LEN` guard are unaffected — the explicit opt-in is preserved.

`get_rope()` memoizes instances in `_ROPE_DICT` (keyed by `max_position`), so one cache is shared by all layers. For Llama-3-70B (`rotary_dim=128`, bf16) the cache grows from ~2.0 MiB to ~2.3 MiB — a one-time +0.3 MiB.

```bash
docker run -d --name vllm-server \
  --privileged --device=/dev/dri --network=host --ipc=host \
  -e HF_TOKEN=$HF_TOKEN -e PYTHONUNBUFFERED=1 \
  -e VLLM_ALLOW_LONG_MAX_MODEL_LEN=1 -e VLLM_WORKER_MULTIPROC_METHOD=spawn \
  vllm/vllm-openai-xpu:v0.31.0 \
  meta-llama/Meta-Llama-3-70B-Instruct \
  --tensor-parallel-size 4 --quantization fp8 --kv-cache-dtype fp8 \
  --max-model-len 9472 --max-num-batched-tokens 8192 \
  --block-size 64 --no-enable-prefix-caching --gpu-memory-util 0.9 --trust-remote-code
```

Send a request with ISL=8192, OSL=1024 (total context 9216 > 8192):

```bash
aiperf profile --model meta-llama/Meta-Llama-3-70B-Instruct \
  --url http://localhost:8010 --endpoint-type chat --streaming \
  --isl 8192 --isl-stddev 0 --osl 1024 --osl-stddev 0 \
  --concurrency 4 --request-count 40
```
