# [ROCm][Perf][DSv4.1] Tune MoRI decode dispatch grid and MXFP8 block32 packed cutoff on MI355X

[Upstream PR](https://github.com/vllm-project/vllm/pull/62335) · state: closed · merged: False

## Original PR description

## Purpose

Two small, self-contained decode-path tunings for **DeepSeek-V4.1-Flash on MI355X (gfx950)** under the DEP8 MoRI expert-parallel recipe with DSpark speculative decode. Both are driven by the observation that DSpark verifies `num_speculative_tokens + 1` rows per sequence each step, so the *effective* decode width is ~7x larger than a single-token decode and the stock decode-regime heuristics are mis-sized for it.

1. **MoRI decode dispatch/combine launch grid.** MoRI's intra-node dispatch/combine has a grid-wide barrier (every block waits for the last to arrive), so the launch grid sets the dispatch tail. The handle's fixed `80x16` launch leaves CUs idle at this decode width. Launching the dispatch and combine with a `128x16` grid (block count capped at the CU count so the barrier stays resident) is **~4% better TPOT** across concurrency 64–256; going wider (`192`) regresses.

2. **MXFP8 32x32-block GEMM packed-kernel cutoff.** The packed kernel fills the MFMA rows with K panels instead of tokens and beats the tiled kernel while there are only a handful of real rows. The per-shape `_TUNED` table switches to the tiled kernel above small M; the decode GEMMs (incl. the indexer projection) land in that tiled range once DSpark inflates M, and those tiled launches dominated the attention stream. Keeping the packed kernel through `M <= 64` recovers that time without fighting the table above it.

Both knobs are env-overridable (`VLLM_MORI_DECODE_BLOCKS` / `VLLM_MORI_DECODE_WARPS`, `VLLM_PACKED_DECODE_MAX_M`) so they can be re-tuned per platform; the defaults are the MI355X-tuned values. With the defaults nothing else changes.

### Files changed

* `vllm/model_executor/layers/fused_moe/prepare_finalize/mori.py` — `_mori_launch_config(num_tokens)` returns `(block_num, warp_per_block)`; `prepare()`/`finalize()` pass them to `dispatch()`/`combine()`.
* `vllm/model_executor/kernels/linear/mxfp8/rocm_block32_gemm.py` — `_PACKED_DECODE_MAX_M` keeps the shape's largest packed tier through small decode M in `_config`/`_default_config`.

## Test Plan

DeepSeek-V4.1-Flash, MI355X 8x (gfx950, ROCm 7 nightly), vLLM `0.32.0rc1.dev369`, DEP8 (data-parallel 8) + `--enable-expert-parallel --all2all-backend mori_high_throughput`, aiter MoE, MXFP4 sparse indexer, block size 128, V2 Model Runner, DSpark MTP `num_speculative_tokens=6` with adaptive block verification, FULL CUDA graphs. "Baseline" = the same image, branch and server flags with the stock image kernels; "tuned" = with this change.

* **Accuracy:** GSM8K 5-shot, 1319 questions, temperature 0, parallel.
* **Serving:** `ISL 8192 / OSL 1024`, streaming `/v1/completions`, `ignore_eos`, closed-loop at fixed concurrency 4 / 64 / 128 / 256; TTFT p50, TPOT p50, total tok/s.
* **Tuning sweep** (ISL 8192 / OSL 256 decode-TPOT probe, conc 64 and 128) to justify the chosen values: MoRI decode grid `{80x16, 128x16, 192x16}` and packed cutoff `{0, 32, 64}`.

## Test Result

### Accuracy (GSM8K 5-shot, 1319 q)

| build                         | accuracy |
| ----------------------------- | -------- |
| baseline (stock kernels)      | 90.07%   |
| as-ported (untuned: 64x4 grid, packed M<=384) | 90.52% |
| **tuned (128x16 grid, packed M<=64)** | **90.75%** |

### Performance (ISL 8192 / OSL 1024)

TPOT p50 (ms, lower is better):

| conc | baseline | as-ported | **tuned**   | tuned vs baseline |
| ---- | -------- | --------- | ----------- | ----------------- |
| 4    | 23.45    | 28.32     | 27.80       | +18.5% (wide grid overhead at a ~28-row batch) |
| 64   | 55.38    | 59.65     | **53.39**   | **-3.6%**         |
| 128  | 55.46    | 59.75     | **53.50**   | **-3.5%**         |
| 256  | 55.45    | 59.68     | **53.53**   | **-3.5%**         |

Total throughput (tok/s, higher is better) and TTFT p50 (ms):

| conc | baseline tok/s | **tuned tok/s** | baseline TTFT | **tuned TTFT**   |
| ---- | -------------- | --------------- | ------------- | ---------------- |
| 64   | 22432          | **22700** (+1.2%) | 11099       | 11857            |
| 128  | 24599          | **27285** (+10.9%) | 27179      | **23059** (-15.2%) |
| 256  | 27082          | **28701** (+6.0%) | 56207       | **50009** (-11.0%) |

The untuned ATOM-direction port (narrow `64x4` grid + packed through `M<=384`) was 7–8% *worse* than baseline on TPOT everywhere; re-tuning on MI355X reverses that into a win from conc 64 up. The only soft spot is conc 4, where a ~28-row decode batch cannot fill the wide grid; this is the opposite end of the same mechanism and could be removed later with a token-count-scaled decode grid.

### Tuning sweep (TPOT p50 ms, ISL 8192 / OSL 256 probe)

| config                         | TPOT@64 | TPOT@128 |
| ------------------------------ | ------- | -------- |
| baseline (stock)               | 55.38   | 55.46    |
| MoRI 80x16 + trust-table       | 55.37   | 55.34    |
| **MoRI 128x16 + trust-table**  | 53.15   | 53.18    |
| MoRI 192x16 + trust-table      | 54.04   | 54.04    |
| MoRI 128x16 + packed M<=32     | 53.19   | 53.30    |
| **MoRI 128x16 + packed M<=64** | **52.97** | **53.03** |

- karverma-amd · comment · 2026-10-18T21:15:07Z · [source](https://github.com/vllm-project/vllm/pull/62335#issuecomment-6255232139)

Closing this. On production agentic traffic (131k-token, rank-imbalanced contexts) the wide MoRI decode grid regressed end-to-end ~15% TPS: MoRI dispatch/combine use a grid-wide barrier that waits on the slowest rank, and a wider grid parks more CUs in that wait, starving the attention/expert kernels. The win only appeared on a uniform 8k/1k synthetic sweep where ranks are balanced. The real decode-path headroom is the exposed combine all2all (dispatch+combine ~47% of device time), which a launch-grid knob cannot remove -- that will be addressed by a fused-combine MoE path in a separate PR with agentic numbers.
