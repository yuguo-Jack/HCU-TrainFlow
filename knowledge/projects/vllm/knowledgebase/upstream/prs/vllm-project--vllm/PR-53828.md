# [Pooling] Optimize MRV2 chunked pooling output handling

[Upstream PR](https://github.com/vllm-project/vllm/pull/53828) · state: closed · merged: False

## Original PR description

## Purpose

MRV2 pooling can avoid per-step overhead when decoder prompts are split across prefill chunks. Intermediate chunks with no finished requests still creates a blocking CUDA event, entering the output copy stream, and synchronized
when the empty output was consumed. Token-wise `ALL` pooling also cloned every partial hidden-state chunk into a Python list and concatenated the chunks when the request finished. 

This PR adds a no-output fast path that returns the known `None` results without copy-stream/event work, and replaces the `ALL` chunk list with one prompt-sized buffer populated in place. The result is **1.1-1.6%** higher request throughput and 1.1-1.4% lower median E2E latency in the tested MRV2 chunked-pooling workloads, without changing model outputs.

The `ALL` path retains its single-chunk fast path: requests that finish in one step still return the original hidden-state view, cloning only when async scheduling requires owned storage. Multi-chunk requests allocate once, copy each chunk once, and return the populated view without a final `torch.concat`.

## Reproducer

Hardware: NVIDIA H100 80GB. Model runner V2 was forced for every server with `VLLM_USE_V2_MODEL_RUNNER=1`. Each result is the median of three runs after 16 warmup requests, using 256 measured requests at an infinite request rate.

- taneem-ibrahim · comment · 2026-08-26T16:12:45Z · [source](https://github.com/vllm-project/vllm/pull/53828#discussion_r3864602211)

All credit to Codex Sol for back of the napkin calculations below: 

The allocation is exactly:

```text
prompt_len × hidden_size × element_size
In the ALL reproducer, that is 1024 × 1024 × 2 = 2 MiB per active partial request. With four 256-token chunks, a deterministic H100 allocation probe measured:
- main: 4.0 MiB peak—the final 2 MiB concat coexists with cached chunks
- branch: 2.5 MiB peak—the 2 MiB buffer coexists with the current 0.5 MiB chunk
Thus the pooling-state peak is 1.5 MiB lower for this workload, although the branch allocates the full 2 MiB earlier.
```
More generally, live buffer memory is Σ(prompt_len × hidden_size × element_size) across concurrent partial ALL requests. Therefore, very long or concurrently capped prefills could increase steady-state memory even though the final-concat peak is removed. I’ll document this tradeoff; alternatively, we can grow the buffer incrementally if we want to avoid the up-front allocation.

The model’s hidden size is 1024 and it runs BF16, confirming the 2 MiB calculation ([configuration](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B/blob/main/config.json)).
