# [Bugfix][KV Offload] Do not store sliding-window chunks with null blocks

[Upstream PR](https://github.com/vllm-project/vllm/pull/63652) · state: closed · merged: True

## Original PR description


## Overview

Fixes #63653.

With offloaded chunks of several GPU blocks, `OffloadingConnector` could store a sliding-window chunk that contained a null block. A later CPU hit then loaded the never-written slot as KV, and the request's output changed with no error.

## Claims

- A sliding-window chunk is stored only when every block that the store mask marks reachable is present, so a CPU hit no longer loads a slot that no store wrote.
- One-block chunks and full-attention groups behave as before. A one-block chunk with a null block was already skipped, and full-attention block tables hold no null blocks.

- `test_sliding_window_chunk_with_null_block_is_not_stored` in `tests/v1/kv_connector/unit/offloading_connector/test_scheduler.py`: scheduler level, sync and async scheduling.

## Details

Root cause, with lines at `24324ef0`:
- A GPU prefix-cache hit leaves sliding-window blocks before the window null (`vllm/v1/core/single_type_kv_cache_manager.py:1004-1037`). A sliding-window free also zeroes pending store positions (`offloading/scheduler.py:1503-1522`).
- With the default `prefix_cache_retention_interval=0`, a GPU hit lands on an earlier prompt's replay boundary. That boundary is block-aligned but not necessarily chunk-aligned, so the null run can end mid-chunk.
- `_build_store_jobs` selected chunks by their last block only (`offloading/scheduler.py:1880-1891`, `1917`), then dropped null blocks from the store spec (`1995`).
- The worker wrote part of the chunk (`vllm/v1/kv_offload/cpu/gpu_worker.py:635-654`), while `complete_store` marked all of it ready (`vllm/v1/kv_offload/cpu/manager.py:370-387`).

The fix adds one check to key selection. After the existing reachability test, a chunk is skipped if any block the store mask marks reachable is null. With no mask, any null block skips it. No GPU block exists to copy for that position, so the chunk can't be completed. A later request that would have hit this chunk computes it instead: it loses a partial CPU hit and avoids loading stale KV. Null blocks that the mask marks unreachable are still allowed. A request whose window excludes them holds null blocks there too, and its load skips those slots.

Test changes:
- `RequestRunner` rejected `blocks_per_chunk > 1` whenever custom KV cache groups were passed. It now accepts them when every group uses the runner's block size.
- `_wait_for_prefix_cache_reset` takes `reset_connector`, so the LLM-level test can clear the CPU tier before its cold run.

Not a duplicate: as of 2026-10-26, no open or closed issue or PR reports this bug. I ran 20 keyword searches over issues and PRs and checked the 171 open PRs that touch the offloading connector or `kv_offload/`. The closest are these two:
- #57216 guards the end-of-request partial-chunk store against null blocks. This PR covers full chunks.
- Draft #61426 moves this loop into `store_triggers/on_compute.py` and keeps the last-block check. If it lands first, this check goes there.
