# [Core][Spec Decode] Lookahead block hashes for EAGLE prefix caching

[Upstream PR](https://github.com/vllm-project/vllm/pull/61589) · state: open · merged: False

## Original PR description



## Overview

Part 1 of 2 split from vllm-project/vllm#50897 (implements vllm-project/vllm#50438): **lookahead block hashes** for the local prefix cache. EAGLE-family drafters write the draft KV at a block's last position from the token after the block, so `main` drops the last matched block on every hit. This PR puts that token into the block hash and removes the drop when no KV connector is configured. KV connector support is in the stacked PR (part 2).

## Claims

- Local prefix-cache hits with EAGLE, EAGLE3, MTP, DFlash and DSpark reach `floor((N - 1) / B) * B`, the same as without speculative decoding, instead of one cache unit less (544–1600 tokens on hybrid attention + Mamba/GDN models).
- A block is reused only when its lookahead token matches, so a hit reads the same draft KV as a cold run.
- New `SpeculativeConfig.disable_lookahead_block_hashes` restores `main`'s behavior. With any KV connector configured, this PR keeps the legacy hashes.
- Model runners are unchanged; no new CPU/GPU synchronization.

## Details

**Enablement.** `is_lookahead_block_hashing_enabled` (`v1/core/kv_cache_utils.py`) requires `use_eagle_block_drop()`, `not disable_lookahead_block_hashes`, `num_prefill_lookahead_tokens == 1`, no HiSparse, prefix caching on, and no KV transfer config. Part 2 replaces the last condition with a per-connector capability.

**Hashing.** `get_request_block_hasher(..., use_lookahead_block_hashes=True)` hashes a block ending at `e` only once token `e` is in `all_token_ids`, with `(block_keys, token_e, token_e_keys)` as extra keys. All KV cache groups share these hashes. KV events carry the same extra keys.

**Caching.** Blocks are cached at allocation, as without lookahead hashes; `SingleTypeKVCacheManager.cache_blocks` stops at the last hashed block. At request finish, `update_from_output` caches the block whose lookahead token is the last sampled one.

**Drop removal.** The scheduler clears `use_eagle_block_drop`. `KVCacheCoordinator.drop_eagle_group_ids` is empty in this mode and drives the per-group drop and `replay_boundaries`, so the last-block drop, the Mamba checkpoint back-off and the replay-boundary shift are all skipped from one place. `eagle_group_ids` stays, since `mamba_shared_prefix_checkpoint` still applies.

**Why it is correct.** The drafter writes the draft KV at `e - 1` (input `(h_{e-1}, token e)`) in the step that prefills or samples token `e`. The hash exists only once token `e` is in `all_token_ids`, which never holds draft or in-flight tokens, so a cached block's draft KV is written by the end of that step.

**Limitations**

- Multi-module MTP (`num_nextn_predict_layers > 1`) keeps the block drop: module j at position p reads token p + j.
- HiSparse keeps the block drop; it is not validated with lookahead hashes yet.
- Hybrid models lose the hit when a prompt diverges exactly at the producer's last retained Mamba boundary (0 vs one unit on `main`); see vllm-project/vllm#50897 for the reproducer.
- KV event extra keys become `(block_keys, lookahead_token_id, lookahead_keys)` in this mode, with no field marking the scheme.

**<sub><sub>![P2 Badge](https://img.shields.io/badge/P2-yellow?style=flat)</sub></sub>  Invalidate cached hashes when replacing the lookahead token**

When a resumable streaming turn finishes exactly on a hash-block boundary, the finish-time caching path has published the preceding block using the sampled token that this method now discards. Deleting only the request's hash leaves each manager's `num_cached_block` at the old count and the block pool mapping the old hash to the live block; the continuation then recomputes a replacement hash and overwrites the EAGLE KV at that boundary, but caching short-circuits as already cached. Consequently, a later request can hit the old hash and read KV written for the replacement token, while the replacement hash is never installed, so this path needs to detach/COW or invalidate and re-key the affected cached boundary block as well as truncating `session.block_hashes`.
