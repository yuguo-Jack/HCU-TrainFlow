# [Bugfix][Structured Output] Drain compilation tasks before releasing the backend

[Upstream PR](https://github.com/vllm-project/vllm/pull/61047) · state: closed · merged: True

## Original PR description

## Overview

Fixes #61043. Stop structured-output thread pools before destroying the backend, so an in-flight grammar compilation cannot access a released xgrammar compiler.

## Claims

- Cancel queued compilation tasks and wait for running tasks before releasing the backend.
- Close the optional mask-filling executor and make repeated cleanup safe.
- Preserve normal structured-output generation; no request handling or backend API changes.

## Validation

```bash
VLLM_TARGET_DEVICE=cpu CUDA_VISIBLE_DEVICES='' .venv/bin/python -m pytest -q tests/v1/structured_output
.venv/bin/pre-commit run --files vllm/v1/structured_output/__init__.py tests/v1/structured_output/test_structured_output_manager.py
```

- Official structured-output suite: 237 passed, 1 existing xfail. The new tests use the real manager, thread pools and xgrammar compiler. The shutdown regression also passed in five independent runs.
- With the original `clear_backend()` restored through a local test plugin, the new regression fails with the reported `AttributeError: 'XgrammarBackend' object has no attribute 'compiler'`.
- Actual HTTP serving on H100 with `facebook/opt-125m`, BF16, TP=1, eager execution and Model Runner V2: both versions returned the expected JSON for three normal requests. With a cold compilation paused at the compiler entry point, SIGTERM caused the original method to release the backend first and reproduce the compiler error. The fix let compilation finish before backend destruction, without that error.
- All applicable project hooks pass. The existing Buildkite structured-output step includes the regression file.

The serving comparison used a local timing-control wrapper and existing native extensions, not a new clean build. It validates the shutdown ordering deterministically, not the frequency of an uncontrolled race. The in-flight HTTP request is aborted during shutdown; its response is not counted as a successful structured-output result.

## Details

`EngineCore.shutdown()` calls `clear_backend()` while grammar futures can still be running or queued. `XgrammarBackend.destroy()` deletes the compiler, leaving those tasks able to access a destroyed backend.

Drain the initialized executors with `shutdown(wait=True, cancel_futures=True)`, then destroy the backend and clear its reference. The initialization guards match the constructor. This keeps the repair in the manager's existing cleanup method and does not reorder engine shutdown.

Shutdown now waits for already-running compilation; Python cannot cancel a running thread. No timeout, runtime dependency or steady-state synchronization is added.

No open PR addressing #61043 was found. Related closed, unmerged #34690 also explored executor cleanup as part of a broader leak fix; this change is limited to backend teardown and its regression tests.
