# [Core] Add max_async_kv_loads_per_step to cap new async KV loads per step

[Upstream PR](https://github.com/vllm-project/vllm/pull/61725) · state: open · merged: False

## Original PR description

## Purpose

On a P/D decode instance, a request that starts an async KV load moves to `WAITING_FOR_REMOTE_KVS` and does not take a running slot. At very high concurrency the waiting queue is long and the decode batch is full. Then each time one running slot frees, a single `schedule()` call starts a load for every waiting request whose blocks fit and allocates KV blocks for each of them. On DeepSeek-V4.1-Flash with ~130K-token prompts that is 90-140 requests per engine and about 1.6 ms of Python each, so one step stalls for 150-290 ms. With data parallelism every DP rank waits for that step.

- New `SchedulerConfig.max_async_kv_loads_per_step` (`--max-async-kv-loads-per-step`). Once N async KV loads have started in a step, the scheduler stops taking requests from the waiting queue until the next step. Requests that already hold KV blocks are still drained first, as before.
- The default `None` keeps the current behavior. The limit only matters at very high concurrency, when the waiting queue is much longer than the number of slots that free per step. At low or moderate concurrency, few requests start loading per step anyway.

Not a duplicate: I searched open PRs for `async kv load per step`, `WAITING_FOR_REMOTE_KVS admission`, `limit async KV loads scheduler` and `max async kv`. #42568 lets completed async loads be promoted under saturation; it does not limit how many loads start per step.

## Test Result

238 passed on CPU. The 2 failures (`test_async_scheduling_pp_allows_rescheduling_with_output_placeholders`, `test_diffusion_read_deferral_keeps_a_longer_pp_wait`) need GPUs for pipeline parallelism and fail the same way without this change. Pre-commit (ruff, format, typos, mypy, config docstrings) passes.

## E2E (P/D, very high concurrency)

DeepSeek-V4.1-Flash on GB300, 7 prefill instances (DEP2) and 1 decode instance (DEP16), NIXL, AgentX multi-turn agentic trace at concurrency 4800, with the decode batch full:

| | tok/s/GPU | P90 interactivity (tok/s/user) |
|---|---:|---:|
| no limit | 460K | 109 |
| limit 4 | 516K | 153 |

The decode step time returned to the decode-only level (22.4 ms). These runs used a development tree and also included two smaller CPU fixes on the same admission path, which will be sent separately: the in-flight prefill reservation is summed once per scheduling pass instead of once per admitted request, and the block-id walk reads `_block_hash` directly. A limit of 4 beat 10-12. With a full decode batch, a higher limit let 40-80 requests that already hold KV blocks pile up per engine, and each 10 of them added 0.12-0.15 ms per step.
