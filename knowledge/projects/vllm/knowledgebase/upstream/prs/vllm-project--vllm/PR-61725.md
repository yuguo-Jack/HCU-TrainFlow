# [Core] Add max_async_kv_loads_per_step to cap new async KV loads per step

[Upstream PR](https://github.com/vllm-project/vllm/pull/61725) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Adds `--max-async-kv-loads-per-step` (default `None`), which limits how many async KV loads one `schedule()` may start. #65319 (merged) bounds how many loads are held at once; this bounds how fast they start. The two solve different problems on a DP decode instance, where every rank waits for the slowest rank's step.

Merged with main and tested at `8d2b491533` (main at `226104db52`, 2026-11-04). The limit now shares its gate with the in-flight cap.

## Claims

- **Hard bound per step.** With the cap alone, one step can start up to `cap - held` loads. On one real `schedule()` with 140K-token requests, that is 42.7 ms at cap 16 and 174.3 ms at cap 64, against 5.8 ms at cap 64 with a limit of 2.
- **No cap value does both jobs.** The cap must exceed rate x load time or requests fall behind. At the highest load tested, caps 16 and 32 wait 20 s and 8 s, while caps of 64 and above keep up and still start 32 loads in one step.
- **The limit fixes that without falling behind.** In the same high-load case, the slowest rank's `schedule()` goes from 28.7 / 48.2 ms (mean / p99) at cap 64 to 14.6 / 14.6 ms at limit 4 and 9.0 / 9.0 ms at limit 2, while the wait before a load starts goes from 0.05 s to 0.07 s and 0.17 s.
- **The limit has its own range.** It must stay above the arrival rate and at or below the typical burst. Limit 1 falls behind at 1.43 req/step. At the reference load with bursts of 2, limit 4 gains almost nothing and limits 1-2 help.
- **The cap does not need to be large.** Beyond keeping up, a larger cap only moves the queue behind the transfer. Peak finished loads waiting for a slot reaches 231 per rank at cap 256 under overload, against 14 at cap 16. These hold KV blocks and add to every step.
- **Not shown yet:** GPU idle time or throughput for the combination. There is no E2E run of cap + per-step limit.

## Details

**How a burst becomes a GPU stall:**

1. Prefill finishes and the request reaches a decode rank's waiting queue.
2. `schedule()` starts its async KV load: it allocates KV blocks for the whole prompt and moves it to `WAITING_FOR_REMOTE_KVS`. It takes no running slot, so nothing but the cap limits how many start in one step.
3. Each load costs ~2.8 ms of Python on that rank.
4. The next `execute_model` does a DP all-reduce, so all 16 ranks wait for the rank that started the most.
5. The KV arrives, and the request waits for a running slot.

**Why the cap alone leaves this open.** The cap only binds once `held` nears `cap`, and `cap` has to stay above rate x load time to keep up. In the reference run about 2/3 of the time was spent below `max-num-seqs`, with ~10.6 loads in progress, so a cap large enough to keep up leaves room for a burst. When the batch is full and the cap is reached, #65319 already paces loads to one per admission, and the limit adds little there. #65319's description also notes that a per-step limit could be layered on.

**Implementation.** With a cap set, remote-prefill requests wait in `async_kv_waiting`, so the limit moved from a `self.waiting` check before the head is peeked to the gate shared with `_admits_inflight_kv_load()`. A head stopped by the limit behaves like one stopped by the cap: an `async_kv_waiting` head stops only that queue for the step, and a `self.waiting` head ends admission for the step. Each limited step still evaluates one head request up to that gate, as the cap already does.

**Suggested settings, from this repro only:** cap around 1.5x rate x load time (16 at the reference load), and a per-step limit above the arrival rate and no larger than the typical burst. This depends on load, so the limit is a setting and not a fixed default.

**Limitations:**

- The repro models `schedule()` on the slowest rank, not GPU idle, and leaves out `update_from_output()`. Its numbers are not a predicted bubble reduction, and async overlap absorbs part of a late rank.
- Step time does not feed back into arrivals. Load time is fixed at 30 steps, and the arrival process is synthetic.
- Raising concurrency alone does not reach the high-load case. Once prefill is saturated, decode's arrival rate stops growing; it takes more prefill capacity and a larger `max-num-seqs`.
- Even at limit 1, some rank starts a load on most steps, so the slowest rank stays near 6.2 ms. Lowering that needs a lower cost per load.
- #64379 and #65285 (both open) remove the repeated reservation sum. Part 1 is already linear at this size (~2.7 ms per load), so they would not remove this per-load cost.

**Not a duplicate:** searched open PRs for `per-step async kv` and `max_num_inflight_kv_loads`. #65319 caps loads held, and its description lists this change as an alternative and a possible layer on top. #64379 and #65285 lower the cost of an admission, not how many start in a step.

```python
#!/usr/bin/env python
"""Why --max-num-inflight-kv-loads (#65319) still needs a per-step limit (#61725).

CPU only. Drives the real Scheduler and NIXL scheduler-side connector; only the
GPU and the transfer are faked (a load finishes `--load-steps` later).

Usage, from a checkout of #61725:
    PYTHONPATH=. python repro_per_step_vs_inflight.py 2>/dev/null

Part 1 times a real schedule() call: one step can start `cap` loads.
Part 2 replays 16 DP ranks. A rank that parks N loads delays every rank, because
each step's DP all-reduce waits for the slowest one.
"""

import argparse
import logging
import multiprocessing as mp
import os
import random
import time

os.environ.setdefault("HF_HUB_DISABLE_PROGRESS_BARS", "1")

import numpy as np

from tests.v1.kv_connector.unit.utils import (
    create_model_runner_output,
    create_request,
    create_scheduler,
    create_vllm_config,
)
from vllm.v1.metrics.stats import (
    KV_FETCH_COMPLETED_WAITING,
    KV_FETCH_IN_PROGRESS,
)

# Reference: DSv4.1 8P1D DEP16 AgentX c6600, mns 128, per-step 6, 1 h CPU hooks.
# Used only to set the load and to turn parked loads into milliseconds.
DP_RANKS = 16
MAX_NUM_SEQS = 128
STEP_MS = 23.1
ARRIVALS_PER_STEP = 0.358  # 15.5 req/s per rank
LOAD_STEPS = 30  # 0.69 s
MEAN_OUTPUT_TOKENS = 320  # 116 running / 0.358 per step
SCHEDULE_BASE_MS = 3.4
SCHEDULE_MS_PER_PARK = 2.8

REAL_RUN = "real run, per-step 6: slowest rank's schedule() averages 10.9 ms"



def make_configs(scale):
    """(label, --max-num-inflight-kv-loads, per-step limit); caps scale with load."""
    caps = {c: c * scale for c in (4, 8, 12, 16, 64, 256)}
    return [
        ("main default (no limits)", None, None),
        ("#61725 per-step 6, as run", None, 6),
        *((f"#65319 cap {caps[c]}", caps[c], None) for c in (4, 8, 12, 16, 64)),
        *(
            (f"both: cap {caps[16]}, per-step {k}", caps[16], k)
            for k in (4, 3, 2, 1)
        ),
        (f"both: cap {caps[64]}, per-step 2", caps[64], 2),
        (f"both: cap {caps[256]}, per-step 2", caps[256], 2),
    ]


def make_rank(
    cap, per_step, scale=1, block_size=16, num_blocks=60_000, max_len=200_000
):
    config = create_vllm_config(
        max_num_seqs=MAX_NUM_SEQS * scale,
        max_num_batched_tokens=10 * MAX_NUM_SEQS * scale,
        block_size=block_size,
        max_model_len=max_len,
    )
    config.scheduler_config.max_num_inflight_kv_loads = cap
    config.scheduler_config.max_async_kv_loads_per_step = per_step
    rank = create_scheduler(config, num_blocks=num_blocks)
    rank.started = []
    set_stage = rank._set_kv_fetch_stage

    def recording_set_stage(request, stage):
        if stage == KV_FETCH_IN_PROGRESS:
            rank.started.append(request)
        set_stage(request, stage)

    rank._set_kv_fetch_stage = recording_set_stage
    return rank


def remote_request(num_tokens, max_tokens, block_size=16):
    return create_request(
        block_size=block_size,
        num_tokens=num_tokens,
        max_tokens=max_tokens,
        do_remote_prefill=True,
        num_remote_blocks=num_tokens // block_size,
    )


def part1_real_schedule_time(num_requests=64, prompt_tokens=140_000):
    """One real schedule() with a queue of 140K-token requests on an idle rank."""
    print(f"\n[Part 1] {num_requests} queued {prompt_tokens // 1000}K-token requests")
    print(f"{'config':<28}{'loads started':>15}{'schedule() ms':>15}")
    blocks = (num_requests + 2) * prompt_tokens // 16
    for label, cap, per_step in (
        ("#65319 cap 16", 16, None),
        ("#65319 cap 64", 64, None),
        ("both: cap 64, per-step 2", 64, 2),
    ):
        rank = make_rank(cap, per_step, num_blocks=blocks)
        for _ in range(num_requests):
            rank.add_request(remote_request(prompt_tokens, 16))
        start = time.perf_counter()
        rank.schedule()
        elapsed_ms = (time.perf_counter() - start) * 1e3
        print(f"{label:<28}{len(rank.started):>15}{elapsed_ms:>15.1f}")


def arrival_stream(seed, steps, burst, rate):
    """Poisson arrivals of fixed-size bursts, the same stream for every config."""
    rng = random.Random(seed)
    arrivals = np.random.default_rng(seed).poisson(rate / burst, steps) * burst
    return [
        [1 + int(rng.expovariate(1 / MEAN_OUTPUT_TOKENS)) for _ in range(n)]
        for n in arrivals
    ]


def replay(args_tuple):
    """Replay one config on DP_RANKS ranks. Returns one row of the Part 2 table."""
    (label, cap, per_step), args = args_tuple
    parks = np.zeros((args.steps, DP_RANKS), dtype=int)
    holding_finished = np.zeros((args.steps, DP_RANKS), dtype=int)
    waits, backlog = [], 0

    for r in range(DP_RANKS):
        rank = make_rank(cap, per_step, args.scale)
        arrived_at, finishes_at = {}, {}
        stream = arrival_stream(r, args.steps, args.burst, args.rate)
        for step, output_lens in enumerate(stream):
            for max_tokens in output_lens:
                request = remote_request(160, max_tokens)
                arrived_at[request.request_id] = step
                rank.add_request(request)

            rank.started = []
            output = rank.schedule()
            parks[step, r] = len(rank.started)
            for request in rank.started:
                if step >= args.warmup:
                    waits.append(step - arrived_at[request.request_id])
                due = step + args.load_steps
                finishes_at.setdefault(due, set()).add(request.request_id)
            holding_finished[step, r] = rank._kv_fetch_counts[
                KV_FETCH_COMPLETED_WAITING
            ]
            rank.update_from_output(
                output,
                create_model_runner_output(
                    list(rank.running),
                    finished_recving=finishes_at.pop(step + 1, None),
                ),
            )
        backlog += len(rank.waiting) + len(rank.async_kv_waiting)

    slowest = parks[args.warmup :].max(axis=1)
    slowest_ms = SCHEDULE_BASE_MS + SCHEDULE_MS_PER_PARK * slowest
    return (
        label,
        int(slowest.max()),
        100 * float((slowest >= 3).mean()),
        float(slowest_ms.mean()),
        float(np.percentile(slowest_ms, 99)),
        STEP_MS / 1e3 * float(np.mean(waits)) if waits else 0.0,
        backlog / DP_RANKS,
        int(holding_finished[args.warmup :].max()),
    )


def part2_dp_replay(args):
    needed = args.rate * args.load_steps
    print(
        f"\n[Part 2] {DP_RANKS} ranks, mns {MAX_NUM_SEQS * args.scale}, "
        f"{args.rate:.3f} req/step/rank in bursts of "
        f"{args.burst}, load {args.load_steps} steps, {args.steps} steps"
        f"\nCap must exceed rate x load time = {needed:.1f} to keep up."
        f"\nSlowest rank's schedule() = {SCHEDULE_BASE_MS} + "
        f"{SCHEDULE_MS_PER_PARK} ms x parks ({REAL_RUN})."
    )
    print(
        f"{'config':<28}{'max parks':>10}{'steps >=3':>11}{'mean ms':>9}"
        f"{'p99 ms':>8}{'wait s':>8}{'backlog':>9}{'finished':>10}"
    )
    print(
        f"{'':<28}{'in a step':>10}{'parks':>11}{'slowest':>9}{'slowest':>8}"
        f"{'to load':>8}{'/rank':>9}{'waiting':>10}"
    )
    jobs = [(config, args) for config in make_configs(args.scale)]
    with mp.get_context("fork").Pool(min(args.jobs, len(jobs))) as pool:
        for row in pool.imap(replay, jobs):
            print(
                f"{row[0]:<28}{row[1]:>10}{row[2]:>10.1f}%{row[3]:>9.1f}"
                f"{row[4]:>8.1f}{row[5]:>8.2f}{row[6]:>9.1f}{row[7]:>10}",
                flush=True,
            )


if __name__ == "__main__":
    parser = argparse.ArgumentParser(description=__doc__.splitlines()[0])
    parser.add_argument("--steps", type=int, default=3000)
    parser.add_argument("--warmup", type=int, default=1000)
    parser.add_argument("--rate", type=float)
    parser.add_argument(
        "--scale",
        type=int,
        default=1,
        help="Multiply max-num-seqs, arrival rate and caps: same D utilization.",
    )
    parser.add_argument("--burst", type=int, default=2)
    parser.add_argument("--load-steps", type=int, default=LOAD_STEPS)
    parser.add_argument("--jobs", type=int, default=10)
    parser.add_argument("--skip-part1", action="store_true")
    cli_args = parser.parse_args()
    cli_args.rate = cli_args.rate or ARRIVALS_PER_STEP * cli_args.scale
    logging.disable(logging.WARNING)
    if not cli_args.skip_part1:
        part1_real_schedule_time()
    part2_dp_replay(cli_args)
```
