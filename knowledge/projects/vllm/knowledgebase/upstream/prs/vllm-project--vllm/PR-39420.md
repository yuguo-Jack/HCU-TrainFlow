## Original PR description

## Purpose

This PR adds support for a new attention backend, "HPC_ATTN", by integrating [hpc-ops](https://github.com/Tencent/hpc-ops) into vLLM.

**Specifically:**
- Defines a new backend HPC_ATTN under the v1 attention interface
- Wraps HPC-provided CUDA kernels for both decode and prefill stages:
   - hpc.attention_decode_bf16 
   - hpc.attention_with_kvcache_prefill_bf16
- Targets improved performance in HPC-oriented deployments with bf16 support

**Usage:**
```bash
python3 -m vllm.entrypoints.openai.api_server \
  --model /workspace/models/Qwen3-14B \
  --host 0.0.0.0 \
  --port 8000 \
  --attention-backend HPC_ATTN \
  --block-size 32
```

The attention scaling factor `self.scale` is not applied to the query. Standard attention requires scaling the query (usually by `1/sqrt(head_dim)`) before computing attention scores. Unless the HPC kernels are specifically designed to handle this scaling internally (which is uncommon and would limit flexibility for models with custom scales), the query should be scaled here.

```suggestion
            decode_q = (query[:num_decode_tokens] * self.scale).contiguous()
```

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Thread configured block size into HpcAttentionImpl**

The implementation reshapes KV cache pages using `self.block_size`, but this class defaults to `32` and the normal attention construction path never passes `cache_config.block_size` into `HpcAttentionImpl`. As a result, running with `--block-size 64` silently reinterprets each cache block as two 32-token pages while `block_table`/`seq_lens` still describe 64-token blocks, so decode/prefill kernels read incorrect cache regions and produce wrong outputs.
