# [XPU] Fix Dockerfile.xpu: add /opt/venv/lib to LD_LIBRARY_PATH

[Upstream PR](https://github.com/vllm-project/vllm/pull/48634) · state: open · merged: False

## Original PR description

intel-sycl-rt / intel-cmplr-lib-ur install libsycl.so and the UR adapter libs into /opt/venv/lib, but LD_LIBRARY_PATH never pointed there, so torch.xpu.device_count() came back 0 even though Level-Zero saw the GPU fine.

Fixes #48625 

Co-authored-by: Claude

## Purpose

docker/Dockerfile.xpu builds an image where torch.xpu.device_count() returns 0 even though Level-Zero sees the GPU fine (zeInit/zeDriverGet work). Turns out LD_LIBRARY_PATH (line 139) never includes /opt/venv/lib, which is where the intel-sycl-rt / intel-cmplr-lib-ur pip wheels drop libsycl.so and the UR adapter libs. Without it on the path, SYCL/UR enumeration silently finds 0 devices.

## Test Plan

docker build -f docker/Dockerfile.xpu -t vllm-xpu-test .
docker run --rm --device /dev/dri -it vllm-xpu-test \
  python -c "import torch; print(torch.xpu.device_count())"
then a normal vllm serve boot on XPU hardware.

- marcorigodanzo · comment · 2026-07-22T12:58:43Z · [source](https://github.com/vllm-project/vllm/pull/48634#issuecomment-5046044225)

@yma11 Your instinct is right that there are two candidate sets of libs here — but I think the data shows the `/opt/venv/lib` ones are exactly the intended ones. Here is what I measured inside a running stock `0.25.1` XPU container (2× Arc Pro B70, serving in production for 8 days with `/opt/venv/lib` prepended to `LD_LIBRARY_PATH`).

### The image ships two *different builds* of the same SYCL/UR sonames

Both `/opt/venv/lib` and `/opt/intel/oneapi/compiler/2025.3/lib` provide `libsycl.so.8`, `libur_loader.so.0.12.0` and `libur_adapter_level_zero.so.0.12.0` — same sonames, same version numbers, **different files**:

| library | `/opt/venv/lib` | `/opt/intel/oneapi/compiler/2025.3/lib` |
|---|---|---|
| `libsycl.so.8.0.0` | `0336997fdfed9b2e…`  11812104 B | `18fa367fb7be21f0…`  11812104 B |
| `libur_loader.so.0.12.0` | `68e273791752638d…`  24405248 B | `32d668526c7e76ed…`  24405**632** B |
| `libur_adapter_level_zero.so.0.12.0` | `ceecac1cb3124f15…`  4082872 B | `790057ec30cbac2f…`  4082**936** B |

The cause is a patch-level mismatch: the pip wheels are `intel-sycl-rt==2025.3.2` and `intel-cmplr-lib-ur==2025.3.2`, while the oneAPI install in the image is `2025.3`. Same soname, different build.

### What a working engine actually loads

From `/proc/<engine-pid>/maps` of the running server:

```
/opt/venv/lib/libsycl.so.8
/opt/venv/lib/libur_loader.so.0
/opt/venv/lib/libur_adapter_level_zero.so.0
/opt/venv/lib/libur_adapter_level_zero_v2.so.0
/opt/venv/lib/libur_adapter_opencl.so.0
/usr/lib/x86_64-linux-gnu/libze_loader.so.1.28.2
/usr/lib/x86_64-linux-gnu/libze_intel_gpu.so.1.15.38308
```

So the working configuration is **pip-wheel SYCL/UR + system Level Zero**, and `torch 2.12.0+xpu` is the wheel built against the `2025.3.2` runtime.

### Why the fix is needed at all

`/opt/intel/oneapi/compiler/2025.3/lib` is *already* on the baked `LD_LIBRARY_PATH` (line 139). So without this PR the loader resolves the **other** build first, and torch reports 0 XPU devices — which is the reported symptom. The libs under `/opt/venv/lib` aren't stray leftovers; they're the ones the torch XPU wheel depends on, and the ones a working container demonstrably resolves.

### Suggestion

The PR fixes the symptom correctly and matches what works in the field. If you want to address the root cause rather than the ordering, the options would be to stop shipping two overlapping SYCL runtimes in the same image, or to pin the oneAPI install and the pip wheels to the same patch level — because as it stands, which runtime wins is decided purely by `LD_LIBRARY_PATH` ordering, which is fragile regardless of what this PR sets it to.

Happy to run further checks inside the container if any would help.
