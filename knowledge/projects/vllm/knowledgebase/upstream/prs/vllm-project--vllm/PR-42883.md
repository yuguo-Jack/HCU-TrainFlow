# [Frontend] Add optional llm_sign integration for OpenAI-compatible APIs

[Upstream PR](https://github.com/vllm-project/vllm/pull/42883) · state: closed · merged: False

## Original PR description



## Purpose

Adds an **opt-in, end-to-end-verifiable signing layer** on top of vLLM's `/v1/chat/completions` and `/v1/responses` endpoints. The provider signs every `(request, response)` turn with its TLS private key and embeds the certificate chain in the response envelope. Clients ([`llm-sign`](https://pypi.org/project/llm-sign/) on PyPI) authenticate the chain under standard X.509 server-certificate validation and verify the transcript under the validated leaf public key.

This defends against tampering by intermediate relays / API gateways that the client's own HTTPS session cannot see past — a common scenario where the client's TLS only authenticates the nearest hop, not the actual provider serving the request.

**Configuration** — three new env vars, all default to disabled / unset:

| Env var | Type | Default |
|---|---|---|
| `VLLM_LLM_SIGN_ENABLED` | bool | `0` |
| `VLLM_LLM_SIGN_CERTFILE` | path | `None` |
| `VLLM_LLM_SIGN_KEYFILE` | path | `None` |

**Zero-impact when disabled:**
- Both call sites (`OpenAIServingChat.create_chat_completion`, `OpenAIServingResponses.responses_full_generator`) gate every llm_sign action behind `if envs.VLLM_LLM_SIGN_ENABLED:`. When disabled, the response code path is **byte-for-byte identical to upstream**.
- The `llm_sign` field is dynamically attached via pydantic's `extra="allow"`; never declared in any schema, so disabled responses do not even emit `"llm_sign": null`.
- The external `llm-sign` PyPI package is imported lazily inside `_OpenAILLMSigner.__init__`; `import vllm` works without it installed.
- Inference function signatures (`responses_full_generator`, `responses_stream_generator`, `_run_background_request{,_stream}`, `create_responses`) are kept byte-for-byte identical to upstream — no llm_sign-only kwargs in the inference path.

**Files** (6 files, +889 / -1):

- `vllm/envs.py` — three new env vars.
- `vllm/entrypoints/openai/llm_sign.py` — **new**, the hook module + lazy-imported TLS-credential wrapper.
- `vllm/entrypoints/openai/chat_completion/serving.py` — 1 import + 4-line gated hook call.
- `vllm/entrypoints/openai/responses/serving.py` — 1 import + 1 self-contained `if envs.VLLM_LLM_SIGN_ENABLED:` block.
- `tests/entrypoints/openai/test_llm_sign.py` — **new**, unit tests.
- `docs/serving/openai_compatible_server.md` — user-facing docs.

Companion library: [`llm-sign==0.2.0`](https://pypi.org/project/llm-sign/0.2.0/) on PyPI, maintained in lockstep with this integration.

**Out of scope:** streaming responses (SSE), batch endpoints, `/v1/completions`. These require an artifact-over-SSE protocol extension and are tracked separately.

Oh, I may not have explained it clearly. Here, the “gateway” generally refers to third-party platforms similar to OpenRouter.

This threat is not hypothetical.

Recent work measures, in the wild, exactly the relay-layer misbehavior that llm_sign is designed to defend against:

* “Real Money, Fake Models: Deceptive Model Claims in Shadow APIs” (arXiv:2603.01919,https://arxiv.org/abs/2603.01919) documents third-party “shadow API” resellers that charge for a premium model while silently routing traffic to a cheaper or different model. This is the model-substitution attack listed above, observed on real commercial endpoints.

* “Your Agent Is Mine: Measuring Malicious Intermediary Attacks on the LLM Supply Chain” (arXiv:2604.08407,https://arxiv.org/abs/2604.08407) measures malicious intermediaries across the LLM supply chain that modify, redirect, or hijack agent traffic between the client and the true provider. This corresponds to the relay-tampering / response-forgery attack class.

Both papers establish that a plain client ──HTTPS──▶ relay ──HTTPS──▶ provider topology provides the client with no cryptographic evidence about which model actually answered, or whether the answer was modified in transit. llm_sign provides exactly that missing evidence.

- arian-gogani · comment · 2026-05-24T23:32:13Z · [source](https://github.com/vllm-project/vllm/pull/42883#issuecomment-4530507815)

signing the `(request, response)` pair at the model layer is the right primitive for output provenance. the complementary layer is signing at the agent layer — what the agent *did* with that output.

a model signs "I generated this response." an agent receipt signs "I took this action based on that response." the two compose: the model signature proves the output wasn't tampered with between model and agent, the agent receipt proves what the agent decided to do with it.

we built the agent-layer receipt format at nobulex — Ed25519 signed over JCS-canonical JSON (RFC 8785), independently verifiable. if vllm's `llm_sign` covers the model-to-agent channel and nobulex covers the agent-to-world channel, you get end-to-end provenance from model output to real-world action.

The `_get_signer` function is not thread-safe. Use a lock to ensure singleton initialization, especially if signing is offloaded to a thread pool in the future.

```suggestion
_signer: _OpenAILLMSigner | None = None
_signer_lock = threading.Lock()


def _get_signer() -> _OpenAILLMSigner:
    global _signer
    if _signer is None:
        with _signer_lock:
            if _signer is None:
                _signer = _OpenAILLMSigner()
    return _signer
```

File: `vllm/entrypoints/openai/responses/serving.py` · line 953

![high](https://www.gstatic.com/codereviewagent/high-priority.svg)

The response is stored in `self.response_store` (lines 920-925) before it is signed. This creates a race condition where a concurrent request using `previous_response_id` might retrieve an unsigned parent response from the store, breaking the cryptographic chain for multi-turn verification. Additionally, if signing fails after storage, the store is left with an unsigned response. The signing logic should be moved before the storage block to ensure that only fully signed responses are persisted.
