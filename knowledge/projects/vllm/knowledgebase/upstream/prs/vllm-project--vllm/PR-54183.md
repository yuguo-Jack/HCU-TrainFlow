# [Metrics] Export KV cache capacity in bytes

[Upstream PR](https://github.com/vllm-project/vllm/pull/54183) · state: open · merged: False

## Original PR description

## Review summary

- Adds startup-time `vllm:kv_cache_capacity_bytes`, preserving capacity per global DP rank.
- Counts device KV backing only; excludes HiSparse host pools and avoids counting aliased device descriptors twice.
- Rebased onto main `852989f580`; 111 CPU checks and changed-file pre-commit passed.

## Overview

Expose a KV-cache byte-capacity Gauge for device-memory dashboards and capacity
alerts, using post-profiling `KVCacheConfig` backing sizes summed across workers
in each DP engine.

This complements #42206's group-aware token capacity and maximum concurrency
in `vllm:cache_config_info`, rather than duplicating that work. The original
duplicate-work searches found no equivalent open byte-capacity PR.

## Claims

- Counts device backing allocations per worker, without double-counting
  aliased cache-group descriptors. Custom builders with multiple allocations
  use their declared total bytes per block. Host-resident pools are excluded.
- Initializes each `engine` Gauge from its matching global-DP-rank ready
  response, independent of response arrival order.
- Computes capacity at startup with no steady-state GPU work; the Gauge uses
  the existing model/engine labels.

## Details

Ready responses carry each EngineCore's capacity; the frontend stores it by
global DP rank and initializes the matching `engine` Gauge once.

HiSparse uses separate host and device backings. The old assertion incorrectly
required all descriptors to have the same size and could fail during EngineCore
initialization. Accounting now filters host-resident descriptors first, matching
the device allocator's input. Default layouts retain the device single-backing
invariant; an empty device descriptor list reports zero. Custom builders that
declare multiple allocations store their declared bytes per block times the
final worker block count, after cross-worker replanning. This does not change
allocation or model execution. Shared host memory is outside the metric's scope.

The value excludes allocator tail padding, including ROCm's 4096-byte rounding;
it is not total process/device memory usage. The configuration documentation,
Prometheus HELP, and `docs/design/metrics.md` use the same device-only definition.

**[P2] Preserve capacity per DP engine.** Each EngineCore computes and reports its own capacity, and the ready response already carries `data_parallel_rank`. However, `_apply_ready_response()` keeps only the first non-`None` capacity in the shared `CacheConfig`, so this loop writes the first response's value to every `engine` label. DP cores profile memory independently, so their allocations can legitimately differ. Please retain capacity keyed by rank and initialize each gauge from its matching value. A two-ready-response test with ranks 0/1 and capacities 111/222 (including reversed arrival order) would catch this.
