# [ROCm] Fuse tiny-M MXFP8 quant into the block32 GEMM; guard lm_head skinny-GEMM by weight size

[Upstream PR](https://github.com/vllm-project/vllm/pull/63179) · state: closed · merged: True

## Original PR description

## Overview

Two decode-time fastpaths for DeepSeek-V4.x block32 MXFP8 linears on MI355X (gfx950): fuse the tiny-M activation quant into the block32 GEMM (one launch instead of two), and guard the lm_head skinny-GEMM dispatch by weight size (weights far larger than L2 stay on the generic GEMM fall-through).

Part of the DSV4.1-Flash MI355X serving fastpath series — four **independent** PRs on `main`@90c4a1a73e, each reviewable and mergeable separately, in any order. Siblings: #63180 (fused shared experts), #63181 (fused draft sampling), #63182 (draft-prepare fastpaths). The four series PRs all register kill switches in `vllm/envs.py` at the same anchor and therefore conflict textually with each other there; the resolution is to keep both sides. This branch trial-merges cleanly into current `main`.

## Claims

- **Fused quant+GEMM** (`rocm_block32_gemm.py`): at M ≤ 8 (decode shapes) the block32 linear path launched `_mxfp8_quant_triton_kernel` solely to produce the e4m3 tiles + E8M0 scales the packed GEMM immediately re-reads. The fused kernel computes that quant inside the GEMM's K loop, in registers, with the same arithmetic — one launch instead of two, no activation round trip. Bit-exact against the stock two-launch path at all eligible shapes (tuned tiers, masked K tail, in-launch split-K); ineligible inputs (non-contiguous x, fp32 x, M > 8) fall back bit-identically. Kill switch `VLLM_DEBUG_DISABLE_FUSED_MXFP8_QUANT_GEMM`.
- **lm_head skinny-GEMM guard** (`layers/utils.py`): `wvSplitK_hf_sml` re-reads the weight matrix once per K-shard, so its effective bandwidth collapses on weights far larger than L2 — at TP=4 the DSpark draft vocab-parallel lm_head shard ([32320, 5120] bf16, ~315 MiB, one call per decode step) hit this collapse. Weights above `VLLM_SKINNY_GEMM_MAX_WEIGHT_BYTES` (default 256 MiB) stay on the generic hipBLASLt fall-through at 1 < n ≤ 5; n = 1 (no pathology) is unchanged. Kill switch `VLLM_DEBUG_DISABLE_LMHEAD_SKINNY_GEMM_GUARD`.
- **−117 µs median decode ITL (−2.1%) on the current base** (`main`@`717cf84342`) — official DSV4.1-Flash serving command at TP=4 on MI355X, every paired run faster (rebase re-check under Validation). The submission-base study measured **−2.45% (−177/−188 µs)** over 12 position-balanced A/B cycles, and the win holds at the same magnitude across bases and images (−127 µs on the nightly ROCm-10 re-verification, −117 µs on the rebased tip). TTFT unchanged within noise.

## Details

**Fused quant+GEMM.** At M ≤ 8 the block32 linear path pays a full `_mxfp8_quant_triton_kernel` launch just to produce the e4m3 tiles + E8M0 scales the packed GEMM immediately re-reads; the fused kernel computes that quant inside the GEMM's K loop, in registers, with the exact same arithmetic. Eligibility is a shape-table hit (serving shapes at TP=4 covering the K-structure variety: multi-band K=5120 with the in-launch split-K tier, the masked-K-tail K=1280, a small-K tile, and the default-config tier); degenerate activation blocks (all-zero, denormal, huge, negative-mirror) quantize identically, and CUDA-graph capture/replay is bit-exact in both counter states. The per-row-scale dispatch branch of the linear kernel is unaffected.

**lm_head skinny-GEMM guard.** The guard is a byte-size predicate on the weight at the skinny dispatch site: above the cap, at 1 < n ≤ 5, the call goes to the generic hipBLASLt GEMM (the same kernel class the n=6 path uses); below the cap, or at n=1, or with the kill switch, dispatch is stock. The swap is not bit-exact (different GEMM kernel, different accumulation order) — numerics are checked within bf16 GEMM tolerance, and the decision table, dispatch selection, env behavior and one-shot-per-site census warning are pinned by tests.

Both paths log their engagement as WARNINGs (one line per site/state), so ON/OFF arms can be asserted from the server log before benchmarking.

<details><summary>MI355X measurements behind the skinny-GEMM guard</summary>

Measured on MI355X (gfx950), DeepSeek-V4.1-Flash at TP=4, vocab-parallel `[32320, K]` bf16 lm_head shards, from serving traces and isolated microbenches:

- The DSpark draft lm_head `[32320, 5120]` (315.5 MiB, n=5, once per decode step) ran `wvSplitK_hf_sml<..., 2, 5>` at **1.55 TB/s** (213.8 µs/call in-graph), while the generic fall-through class runs the same GEMM at **~6.5 TB/s** (~51–73 µs).
- The n=6 target-verify lm_head `[32320, 7168]` (442 MiB) already dispatches to hipBLASLt `Cijk MT64x16x512` (56.2 µs/call in-graph, 7.9 TB/s), i.e. the fall-through kernel is fast and CUDA-graph-capture-safe in this exact serving configuration.
- Isolated microbench on the target-shape shard at n=5: wvSplitK 313.3 µs vs `torch.linear` 71.2 µs (4.4×).
- The n=1 variant (`wvSplitK_hf_sml<..., 2, 1>`) shows no pathology on large weights (6.9 TB/s on the 442 MiB shard); its fall-through (LLMM1) would be a numerics change with no speed win, so n=1 keeps stock dispatch.

The mechanism is weight re-reads: `wvSplitK_hf_sml` streams the weight once per K-shard, so above L2-sized weights the effective bandwidth collapses. This is orthogonal to VGPR-spill fixes in the skinny kernel itself (#63015, #62846) — see the related-PRs note below.

</details>

**Related PRs.**

- #63015 / #62846 (skinny-GEMM tile/spill fixes): the guard here addresses a different mechanism — weight re-reads vs L2 bandwidth on very large weights — not VGPR spills, so the two are orthogonal and compose. The spill fixes should recover `wvSplitK` throughput on shapes that spill; the re-read cost on weights far above L2 remains. Once either lands we can re-measure the `[32320, 5120]` n=5 shard on top of it and revisit the guard's byte cap / n-window if the fixed `wvSplitK` wins there.
- #59782 (fused MXFP8 quant, draft): same fused-quant idea, per-shape cutoffs and keeps the fusion past M=8 on some shapes, where this PR caps every shape at M=8 with a bit-exactness contract against the stock path. In our measurements the fusion works well at M ≤ 8; we have not measured beyond that and are happy to coordinate on which approach to keep.

Done in fb0e39d997: **the default now equals the L3 (memory-side) cache size**, read once per process at first use via AMD's `amdsmi` library — 256 MiB on MI355X, 128 MiB on MI300X-class parts.

The portable device-properties API can't be used: it exposes only the 4 MiB L2 (`L2_cache_size`), the wrong level. amdsmi reports the level-3 DATA_CACHE directly.

L3 is the boundary because the kernel's measured cost at `n` activation rows scales as ~`n` passes over the weight (442 MiB shard: 67.5 µs at n=1, 313 µs at n=5) — past the last-level cache those passes are HBM round trips, which is the collapse the guard redirects. The measured site (`[32320, 5120]` bf16, ~315 MiB, once per decode step) sits just above the 256 MiB MALL, and a serving-model census shows no other n≤5 weight at or above the cap.

If the query fails (no amdsmi, no GPU access, API change) the cap falls back to the documented 256 MiB; an explicit env value still overrides. On MI355X the derived value is exactly the old default (268435456), so behavior there is unchanged. Tests pin the L3 selection, the env > hardware > fallback precedence, and the no-L3 cases.
