# [ROCm][Perf] MiniMax-M3: fp8 FMHA v3 for long extend-prefill rows, fp8 copy of a drafter's own lm_head

[Upstream PR](https://github.com/vllm-project/vllm/pull/63477) · state: closed · merged: False

## Original PR description

## Purpose

Two independent changes that cut MiniMax-M3 decode time on MI355X under agentic (long-context, EAGLE3) load:

1. **Long extend-prefill rows on AITER fp8 FMHA v3** (`ROCM_AITER_UNIFIED_ATTN`, gfx950, fp8 KV cache, opt-in via `VLLM_ROCM_UNIFIED_ATTN_FMHA_EXTEND_MIN_Q`, default 0 = off). Unified attention runs every row through AITER's triton `unified_attention`, which is built for decode; on a long extend-prefill chunk over a long context it reaches ~0.7–0.8 PFLOP/s, while AITER's FMHA v3 fp8 kernel runs chunks of 4K+ new tokens 1.7–2.7x faster.
   - The metadata builder splits the batch on the host: requests whose query has at least `MIN_Q` tokens (prefill chunks; decode / spec-decode rows never qualify) become "long" rows.
   - For the long rows, the layer gathers their fp8 K/V (context + new tokens, already in the paged cache) into contiguous tensors and calls the fp8 FMHA v3 varlen kernel (bottom-right causal) with the layer's statically quantized fp8 query — the same query unified attention reads.
   - The remaining rows run `unified_attention` as a compact batch. Unsupported configurations (sinks, ALiBi, soft cap, sliding window, shuffled KV layout, head size other than 64/128, fused output quant) keep the current path, and CUDA graph capture never takes the split.
   - In MiniMax-M3 this backend serves the 3 dense full-attention layers and the EAGLE3 draft layer (the 57 sparse layers use their own kernels).

2. **`draft_lm_head_quantization` for a drafter's own lm_head.** The option only applied when the drafter shares the target's `lm_head`; a drafter that ships its own head (e.g. `Inferact/MiniMax-M3-EAGLE3-GQA`, whose head differs from the target's) was rejected with a `ValueError`, so its bf16 head (614 MB per rank at TP4) is read in full three times per step. This PR quantizes that head instead, with the same online methods (`fp8`: per-row weight / per-token activation scales; `nvfp4`: weight-only W4A16). The shared-head path is unchanged and moves into `resolve_draft_lm_head`. As in the shared case, the bf16 source head stays resident for `refresh_quantized_lm_heads` / draft weight updates, so the copy adds memory (307 MB per rank here).

## E2E (MI355X, MiniMax-M3-MXFP4, TP4, EAGLE3-GQA K=3)

This PR = `VLLM_ROCM_UNIFIED_ATTN_FMHA_EXTEND_MIN_Q=3072` + `draft_lm_head_quantization: fp8`. Base: vLLM nightly `8e2beaa3` with the MiniMax-M3 model code from main `4643f41` + #62509 + #62614 + #62846, FFN monokernel on (`--monokernel`, plus two local commits that let it take #62509's FP8 projections); the baseline is the same image without this PR. AgenticX: InferenceX recipe `minimaxm3/vllm/mi355x-fp4-mtp/agentic.yaml`, 3600 s, synthetic acceptance (AL 2.78); in each row the baseline and the change ran concurrently on the two GPU halves of one node (start times up to 25 minutes apart), one run each. Single-request TTFT on a cached 160K prefix (FMHA only, averaged over runs on both GPU halves of one node): 8,192 new tokens 322 → 297 ms, 16,384 new tokens 492 → 462 ms (the halves alone differ by up to ~25 ms, so read these as ±10 ms).

## Test plan

- `tests/v1/attention/test_rocm_aiter_unified_attn_fmha_extend.py`: host row split (long / short rows, KV row indices, spec-decode rows excluded); on gfx950, the backend output with the FMHA path matches the unified-attention path for mixed batches (1 and 2 KV heads). 3 passed on MI355X.
- `tests/v1/worker/test_gpu_draft_lm_head.py`: an own-head drafter gets a quantized copy of its own head (not the target's); without quantization it keeps its head; quantization without any head raises. 7 passed, 4 skipped (nvfp4 cases) on MI355X.
