# [Kernel][MoE] Add FlashInfer CuTe-DSL W4A16 NVFP4 experts

[Upstream PR](https://github.com/vllm-project/vllm/pull/62191) · state: open · merged: False

## Original PR description



## Overview

Adds `FlashInferCuteDSLW4A16Experts`, a routed-expert backend for W4A16 NVFP4 checkpoints on the `flashinfer_cutedsl` MoE backend, together with its NVFP4 oracle branch. Under `VLLM_BATCH_INVARIANT=1`, a token's expert output is bitwise independent of the batch.

This is one self-contained part of #62017 by @aoshen02, split out unchanged for separate review. The commit keeps his authorship. An earlier revision was reviewed as aoshen02/vllm#91.

## Claims

- W4A16 NVFP4 experts with BF16 activations run on FlashInfer's CuTe-DSL W4A16 runner. The results match a dequantized-weight reference.
- Under batch invariance, every token count uses one pinned tile tactic. Each output element is one CTA's FP32 accumulation over the full K, with no split-K, and the top-k combine is an FP32 sum in slot order. A token's output is therefore the same alone or in any batch, and EP1 gives the EP4 bits.
- No existing path changes for other configurations. `backend_to_kernel_cls(FLASHINFER_CUTEDSL)` lists the W4A4 experts first and then this class, and `is_supported_config` picks between them by quant scheme; the oracle has no special case for it. The class accepts only an explicit `moe_backend=flashinfer_cutedsl` in the scope below, so auto-selection never picks it. When an explicit request fails, the error now lists every candidate's reason instead of only the last one's.

## Details

Scope. Anything else is rejected by `is_supported_config`, with a reason:
- `moe_backend == "flashinfer_cutedsl"`, set explicitly. The class no longer reads the model type from the global config, so any model with exactly this geometry qualifies;
- BF16 activations;
- non-gated ReLU2 (`RELU2_NO_MUL`);
- the Nemotron-H Lightning geometry: hidden 2688, intermediate 1856, 128 experts, top-6;
- TP1 with EP1 or EP4;
- no EPLB or batched-expert layouts;
- contiguous, uniform expert ownership;
- an installed FlashInfer that has the W4A16 runner.

The geometry gate is deliberately narrow: these are the shapes the pinned tactic and the EP4 combine were validated on. Widening it needs the same bitwise checks on other shapes.

Weight conversion takes the checkpoint's fresh, unswizzled E4M3 block scales and converts them to FlashInfer's interleaved layout (`prepare_w4a16_scales`, with rows padded to a multiple of 128 and columns to a multiple of 4). The padded storage stays registered, because the runner consumes its raw pointer. Activation scales are rejected after conversion.
