# [Perf] Warm up DeepGEMM MegaMoE kernels before serving

## Overview

The DeepGEMM warmup covers `fp8_gemm_nt` and the grouped MoE GEMM. It does not cover `fp8_fp4_mega_moe` or the `bf16_mega_gate` that routes into it. With `--moe-backend deep_gemm_mega_moe`, DeepSeek-V4 and Kimi K3 therefore JIT-compile these kernels on the first request at each new prefill size. This PR adds them to `deep_gemm_warmup.py`, following the structure of the two existing DeepGEMM warmups there.

## Claims

- No serving-time compiles of the MegaMoE kernels: `fp8_fp4_mega_moe`, `bf16_mega_gate` and the Triton input-staging kernel. Before: 60 DeepGEMM compiles in one DeepSeek-V4 benchmark run. For Kimi K3, the 2 SiTU `fp8_fp4_mega_moe` compiles during serving that cost 2.6-2.9 s of TTFT each go to 0, at about +10 s of startup.
- MTP speculative decoding needs nothing extra. The DeepSeek-V4 MTP drafter's MegaMoE layer uses the same kernels as the target's, and there were 0 DeepGEMM compiles during serving with MTP on.
- DeepSeek-V4: the first request at a new prefill size no longer stalls for 3.5 to 6 s. It now takes about the same time as a repeat. The exception is a one-time 60-85 ms communication-buffer setup on the server's first large prefill, which is not a compile (see Details).
- Cost: for DeepSeek-V4, the first startup on a cold DeepGEMM cache takes about 4 to 5 min longer (+247 to +299 s on fully empty caches). A warm restart takes the same time as before. For Kimi K3, it is about +10 s.

## Validation

**Setup (DeepSeek-V4).** DeepSeek-V4-Flash on 2x B300, TP2 + EP2, `--moe-backend deep_gemm_mega_moe`, `max_num_batched_tokens` 16384, `--max-model-len 16384`, prefix caching off, Model Runner V2. vLLM precompiled wheel `3ca00a82` (cu130) with its bundled DeepGEMM.

Each run used a fresh `DG_JIT_CACHE_DIR` seeded with every non-mega DeepGEMM kernel, so only the mega kernels start cold.

**Workload.** One request at a time: token-ID prompts to `/v1/completions`, `max_tokens` 4, streamed time to first token (TTFT).
1. Six fixed lengths (100 to 8000 tokens). Each gets a first request, then 3 repeats with new random tokens.
2. 40 seeded random lengths from 51 to 15504 tokens. The warmup did not pick these.
3. 32 concurrent requests.

**JIT compiles during serving.** Counted as new entries in the DeepGEMM cache dir between "Application startup complete" and the end of the workload, across all kernel families. Triton, CuTeDSL and TileLang compiles were counted with `--jit-monitor-verbose`.

<summary>bench.py</summary>

```python
"""First-hit benchmark. Phase 1 (fixed): for each prompt length, one request
at a time: a first hit, then REPEATS more with fresh random tokens. Phase 2
(sweep, optional): random lengths the warmup did not pick, then a concurrent
burst (mixed prefill + decode). Records TTFT and every DeepGEMM JIT cache
entry created during serving, per kernel family."""
import collections, concurrent.futures as cf, json, os, random, re, sys, time
import requests

port, dgdir, out = sys.argv[1], sys.argv[2], sys.argv[3]
LENGTHS = [int(x) for x in os.environ.get("LENGTHS", "100,400,1000,2000,4000,8000").split(",")]
REPEATS = int(os.environ.get("REPEATS", "3"))
SWEEP = int(os.environ.get("SWEEP", "0"))
URL = f"http://localhost:{port}/v1/completions"
MODEL = "deepseek-ai/DeepSeek-V4-Flash"
cache = os.path.join(dgdir, "cache")

def entries():
    return set(os.listdir(cache))

def family(e):
    m = re.match(r"(?:kernel\.)?(.+?)\.[0-9a-f]{32}$", e)
    return m.group(1) if m else e

def fam_count(es):
    return dict(collections.Counter(family(e) for e in es))

def ttft(prompt_ids, max_tokens=4):
    t0 = time.perf_counter()
    r = requests.post(URL, json=dict(model=MODEL, prompt=prompt_ids, max_tokens=max_tokens,
                                     temperature=0, stream=True, ignore_eos=True),
                      stream=True, timeout=3600)
    first = None
    for line in r.iter_lines():
        if line and line.startswith(b"data: ") and line != b"data: [DONE]" and first is None:
            first = time.perf_counter() - t0
    return first, time.perf_counter() - t0

rng = random.Random(0)
def prompt(L):
    return [rng.randrange(1000, 100000) for _ in range(L)]

start = entries()
print(f"entries at ready: {len(start)} {fam_count(start)}", flush=True)
rows = []
ttft(prompt(8))  # HTTP/tokenizer warm; 4 per-rank tokens -> no mega gate
for L in LENGTHS:
    for i in range(1 + REPEATS):
        before = entries()
        t, e2e = ttft(prompt(L))
        new = entries() - before
        rows.append(dict(phase="fixed", prompt_len=L, rep="first" if i == 0 else f"repeat{i}",
                         ttft_s=t, e2e_s=e2e, new=fam_count(new)))
        print(json.dumps(rows[-1]), flush=True)
after_fixed = entries()
sweep_lengths = []
if SWEEP:
    srng = random.Random(1)
    sweep_lengths = sorted(srng.randrange(17, 16380) for _ in range(SWEEP))
    for L in sweep_lengths:
        before = entries()
        t, e2e = ttft(prompt(L))
        rows.append(dict(phase="sweep", prompt_len=L, rep="first", ttft_s=t, e2e_s=e2e,
                         new=fam_count(entries() - before)))
        print(json.dumps(rows[-1]), flush=True)
    # concurrent burst: 32 requests, mixed lengths, 64 output tokens -> prefill + decode mix
    burst = [prompt(srng.randrange(17, 6000)) for _ in range(32)]
    before = entries(); t0 = time.perf_counter()
    with cf.ThreadPoolExecutor(32) as ex:
        res = list(ex.map(lambda p: ttft(p, 64), burst))
    rows.append(dict(phase="burst", prompt_len=-1, rep="32 concurrent", ttft_s=max(r[0] for r in res),
                     e2e_s=time.perf_counter() - t0, new=fam_count(entries() - before)))
    print(json.dumps(rows[-1]), flush=True)
end = entries()
summary = dict(rows=rows, entries_at_ready=fam_count(start), new_during_fixed=fam_count(after_fixed - start),
               new_during_serving=fam_count(end - start), new_entries=sorted(end - start),
               sweep_lengths=sweep_lengths)
json.dump(summary, open(out, "w"), indent=1)
print("new during serving:", summary["new_during_serving"])
```

## Details

**Root cause.** Both kernels choose a JIT config from the per-rank token count:
- `bf16_mega_gate`: block tokens, MMA CTAs, split-K, expert groups and stages (`heuristics/mega_gate.hpp`). That is 87 configs for per-rank sizes 17 to 8192.
- `fp8_fp4_mega_moe`: `block_m` in {16, 32, 64, 128, 192, 240}.

Startup only compiles the sizes that the profile run and CUDA graph capture hit, here 512 or fewer tokens per rank. Every other prefill size compiles on first use, about 1.7 s per kernel. DeepSeek-V4 needs two gate kernels per size, because hash-routed and bias-routed layers pass different optional inputs.

**Design.** The warmup lives in `deep_gemm_warmup.py`, with the same parts as the existing DeepGEMM warmups:
- A layer predicate that matches DeepSeek-V4's `DeepseekV4MoE` and Kimi K3's `KimiMoE` when they use the native MegaMoE backend.
- A cache constant.
- `_get_fp8_fp4_mega_moe_m_values`: for every per-rank size, it asks DeepGEMM for the `block_m` and, for DeepSeek-V4, the gate config. It keeps the largest size of each distinct config (95 sizes for DeepSeek-V4 here), because DeepSeek-V4 only calls `bf16_mega_gate` above a small token threshold and a config's largest size is always above it. The configs come from DeepGEMM's own getters, so the dedup is exact and `VLLM_DEEP_GEMM_WARMUP=full` would add nothing.
  - Kimi K3 routes with its `GateLinear`, which the bf16x3 router warmup already covers, so for Kimi only `block_m` matters.
  - Kimi's experts call the SiTU variant of `fp8_fp4_mega_moe`, which picks `block_m` with the same heuristic.
- A private worker and a public loop, an `elif` branch in `_count_warmup_iterations`, and calls in `deep_gemm_warmup`.

The worker runs the whole MoE layer at each size, not the raw kernels:
- The gate gets the same optional inputs it gets in serving.
- Every EP rank runs the same sizes in the same order, which the collective MegaMoE kernel needs.
- It runs under a minimal forward context with a padding mask, because the layer reads `is_padding` from the forward context. This makes the Triton input-staging kernel compile the variants serving uses.
- Under sequence parallelism with `VLLM_MOE_SKIP_PADDING` on (the default), ranks above 0 get mask slices at any alignment, so each size runs once with an aligned slice and once with an unaligned one.

The predicate looks the model modules up in `sys.modules`, as other model-specific warmups in this package do (`kimi_k3_triton_warmup.py`, `qwen4_exp_qsa_warmup.py`), so other models import neither model. The cache key reads two DeepSeek-V4-only attributes (`tid2eid`, `image_sentinel_lo`) with `getattr`, because they do not exist on Kimi K3. The two config getters are reached through `_import_deep_gemm`, as in the model code.

`models/kimi_k3/nvidia/model.py` gains one line, which stores `use_sequence_parallel` on `KimiMoE` as `DeepseekV4MoE` already does. The warmup needs it to compute the per-rank token count.

<details>
<summary>Startup trade-off: where the cold warmup time goes</summary>

- About 84% of the cold warmup is serial `nvcc` time for 136 gate kernels (1.7 s each).
- About 14% is about 24 Triton staging variants.
- About 3% is 3 MegaMoE kernels.
- The layer forwards and the size search take under 1 s.

Compiling in parallel threads crashed inside DeepGEMM's JIT, which has no locking and no compile-only API. Parallel compilation would need DeepGEMM changes. vLLM keeps the DeepGEMM cache in `~/.cache/vllm/deep_gemm`, so the cold cost is paid once per machine and DeepGEMM version.
</details>

<details>
<summary>Remaining one-time first-request cost</summary>

The first eager prefill whose reduce-scatter falls in the MNNVL multimem size range sets up a symmetric-memory buffer (`_init_mnnvl_multimem_reduce_scatter_buffer`). This adds 60-85 ms to that one request (+61, +66 and +83 ms in three runs). CUDA graph capture skips this setup. It is paid once per server and is not a compile. A torch profile and a request-order test confirm both points.
</details>

**Limitations.** DeepSeek-V4 was validated only on 2x B300 with TP2 + EP2 and Model Runner V2, with and without MTP. Kimi K3 was validated only with a pruned checkpoint on 4x B300, TP4 + EP4, Model Runner V2.
- Not run: Model Runner V1, DP > 1, other EP sizes, EPLB, and routed-experts capture. With EPLB or routed-experts capture on, the warmup forwards would pass dummy tokens to the load recording and the capture hook.

My agent flagged a potential issue. Could you double-check whether it’s actually valid? It seems plausible to me, which is exactly why I’m not a fan of these token-based warmups... :))

> DeepSeek-V4 only calls bf16_mega_gate above a hardcoded threshold, at model.py:1043-1044:

```python
gate_threshold = 1 if self.gate.weight.shape[0] == 128 else 16
if hidden_states.shape[0] <= gate_threshold:
    router_logits, _ = self.gate(hidden_states)      # GateLinear + fused_topk_bias
    ...
else:
    ... bf16_mega_gate(...)
```

> The warmup side. It picks the smallest token count for each config key, at deep_gemm_warmup.py:367-383:

```python
for num_tokens in range(1, max_tokens + 1):
    gate_config = (dg.get_bf16_mega_gate_config(num_tokens, ...) if uses_mega_gate else {})
    block_m = dg.get_block_m_for_mega_moe(...)
    m_values.setdefault((tuple(gate_config.items()), block_m), num_tokens)
```

> How the gap happens. Suppose a (gate_config, block_m) key spans token counts 1..N with N > 16. Its representative is then 1. The forward at deep_gemm_warmup.py:433 takes the GateLinear branch, so bf16_mega_gate is never compiled for that config. On DSv4-Flash with EP2 (256 experts, top-6), block_m=16 covers about 1–181 tokens. Any gate config that is constant across 16→17 would be missed. CUDA-graph capture probably compiles most of those sizes, so the leftover gap is eager sizes above the capture limit.

> Fix. Make “mega-gate is actually reached” part of the key, and stop hardcoding the threshold in two places:

```python
# model.py — expose it
def mega_gate_threshold(self) -> int:
    return 1 if self.gate.weight.shape[0] == 128 else 16

# deep_gemm_warmup.py
threshold = module.mega_gate_threshold() if uses_mega_gate else 0
for num_tokens in range(1, max_tokens + 1):
    uses_gate_kernel = uses_mega_gate and num_tokens > threshold
    gate_config = dg.get_bf16_mega_gate_config(...) if uses_gate_kernel else {}
    ...
    m_values.setdefault((uses_gate_kernel, tuple(gate_config.items()), block_m), num_tokens)
```
