# [Bugfix][Attention] Keep FlashInfer's plan() staging buffer pageable

[Upstream PR](https://github.com/vllm-project/vllm/pull/59493) · state: open · merged: False

## Original PR description

## Purpose

Fixes a race where FlashInfer can overwrite a CPU planning buffer before the GPU has finished reading the previous plan. With MTP speculative decoding, the GPU can then use the wrong scheduling data and crash or hang. This addresses the staging-buffer race reported in #40756.

The change replaces FlashInfer's pinned CPU staging buffer with ordinary, pageable CPU memory when vLLM creates an attention wrapper. This lets CUDA stage the source data before the next plan reuses the buffer. It covers decode, prefill and DCP child wrappers (cascade attention, which this originally also covered, was removed upstream in #61126), and adds a regression test for both eager and CUDA graph decode.

### Why it is needed

Repeated draft steps can plan the same wrapper before its previous GPU copy runs. A `seq_lens.cpu()` wait masks that overlap in the recorded main baseline, but the performance change in #57352 removes the wait for drafting. This fix protects the planning buffer independently of that wait. The fused drafting path in #58371 does not cover the native FlashInfer path that re-plans each step.

### Why this is not a duplicate

Rechecked #40756 and open PR searches for the issue, `_pin_memory_int_workspace_buffer` and FlashInfer planning. No other matching vLLM staging-buffer fix was found. #42603 used an explicit stream wait; #57352 removes a wait. The other PRs referencing #40756 (#45005, #51508, #53450) address different failure mechanisms.

## Validation

Previously recorded local results on an RTX 4080 Laptop under WSL2:

- New queued-plan regression: **2 failed without the fix, 2 passed with it** on FlashInfer 0.7.0.post1.
- FlashInfer backend, DCP reorder and new regression tests: **31 passed, 5 skipped**. The backend run used an ungated Llama config; changed-file pre-commit checks passed.
- Standalone reproductions on FlashInfer 0.6.16.post3 and 0.7.0 showed stale plans and kernel hangs without the fix, and correct plans with pageable staging.
- Qwen3.5-0.8B with MTP and fp8 KV cache: outputs and draft acceptance matched the local #57352 comparison build across all three workloads. No consistent throughput regression was observed on the tested hardware. The real-model crash itself was not reproduced on this laptop.

Re-run on 2026-10-16 after merging current main (same hardware): the queued-plan regression passes 2/2, and fails 2/2 with the unpin turned into a no-op; `test_attention_backends.py -k flashinfer`: 28 passed, 9 skipped; `test_flashinfer_dcp_spec_reorder.py`: 1 passed; changed-file pre-commit checks pass. Hosted pre-commit is currently skipped because the repository's contributor eligibility check fails.

### Limits

The patch adds no explicit stream synchronization. Pageable copies may still block or synchronize inside the CUDA driver, so the measurements below are not a guarantee for every device or driver ([CUDA synchronization behavior](https://docs.nvidia.com/cuda/cuda-runtime-api/api-sync-behavior.html)). FlashInfer MLA wrappers are outside this change and have not been validated on Hopper.

## Test Plan

1. New regression test, `tests/v1/attention/test_flashinfer_plan_staging.py`: builds a `FlashInferMetadataBuilder`, holds the GPU with `torch.cuda._sleep`, plans its decode wrapper twice through `fast_plan_decode`, and compares the workspace the first launch reads against a clean first plan. It also asserts the second plan was issued while the first copy was still queued, so it cannot pass vacuously. Covers the eager and CUDA graph decode wrappers.

3. `plan()` host time with a pinned vs pageable staging buffer while the GPU is held busy.
4. Existing FlashInfer backend tests and `pre-commit`.
5. End to end: Qwen3.5-0.8B with MTP, FlashInfer, fp8 KV cache, on main, main + #57352, and main + #57352 + this PR, with a local-only probe counting plans issued while the wrapper's previous copy was still queued.

All runs on an RTX 4080 Laptop (sm_89) under WSL2.

@benchislett on #42603 you said forcing a synchronization was an unacceptable fix until a root cause was identified. This PR has one for the staging-buffer race reported in #40756: FlashInfer's `plan()` writes its metadata into a single pinned host buffer per wrapper and copies it to the GPU asynchronously, so when the drafter re-plans the same wrapper before that copy executes, the earlier launch reads the later plan. The fix makes that staging buffer pageable, so the copy captures its source when it is issued, and adds no explicit sync. The new regression test reproduces the stale read deterministically (fails without the fix, passes with it). On main the overlap is currently masked by the `seq_lens.cpu()` wait that #57352 removes.
