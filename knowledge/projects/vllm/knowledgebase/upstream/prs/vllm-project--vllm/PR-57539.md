## Purpose

First half of #55627, split out on request. Mamba2 runs the chunked scan (SSD) for prefill and the single-token update (SSU) for decode, and the two do not round the same way, so under `VLLM_BATCH_INVARIANT=1` a token's logprob depends on how the scheduler split the sequence. The fix in #55524 is to replay: every SSD call starts from the fp32 state at the sequence's last chunk boundary and re-feeds the buffered inputs of the partial chunk in front of the new tokens, so the kernels always see the chunk grid of a single-shot prefill.

This PR adds only the pieces that do not touch the model or the backend:

- `exact_replay_ssd`: one replayed SSD step for a batch of sequences (prefill rows and decode rows alike), on top of the existing varlen chunked-scan kernel. It updates the fp32 boundary state and the partial-chunk buffers in place.
- `ExactReplayMetadata` and `build_exact_replay_metadata`: the host-side layout of such a step (augmented sequence lengths, chunk offsets, which rows complete a chunk, which tokens are stored back). The metadata refers to batch rows, never to state slots, so one instance serves every KV cache group of a hybrid model.
- `ExactReplayBuffers`: the per-slot buffer views the step reads and writes.

Nothing runs this code yet; the state layout, the backend metadata builder and the mixer wiring come in #55627, and the row-gated decode kernels in #55905 build on the same step.

## Test Plan

```bash
pytest tests/kernels/mamba/test_mamba2_exact_replay.py
```

One kernel-level test drives two layers with different state slots through a schedule of unaligned prefill splits, resumed prefill and shrinking decode batches, and checks every output row and final state bitwise against a single-shot prefill. Two host-side tests pin down the metadata for decode rows and for prefill rows at several chunk offsets.
