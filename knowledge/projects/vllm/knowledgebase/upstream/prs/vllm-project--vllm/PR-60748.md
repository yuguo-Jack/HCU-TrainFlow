# [Bugfix][Structured Output] Decode choice specs as JSON in outlines and LMFE

[Upstream PR](https://github.com/vllm-project/vllm/pull/60748) · state: closed · merged: True

## Original PR description



## Overview

Choice constraints that contain characters outside the Basic Multilingual Plane, such as emoji, break the outlines and lm-format-enforcer backends. The choice list is stored with `json.dumps`, which writes such characters as surrogate pairs, and both backends read it back with `ast.literal_eval`, which turns them into lone surrogates. This reads the spec with `json.loads` instead.

## Claims

- outlines: a choice like `["😀 yes", "no"]` now compiles and can be generated. Before, grammar compilation failed with `UnicodeEncodeError: surrogates not allowed` and the request errored.
- lm-format-enforcer: the emoji choice is no longer silently unreachable.
- The default xgrammar backend was not affected and is unchanged.

## Validation

Unit test `test_outlines_choice_with_non_bmp_characters` in `tests/v1/structured_output/test_structured_output_manager.py` builds the spec with `get_structured_output_key` and compiles it with the outlines backend. It fails on main with `UnicodeEncodeError` and passes with this change.

```bash
pytest tests/v1/structured_output/test_structured_output_manager.py
# 49 passed, 1 xfailed
```

End to end, `vllm serve Qwen/Qwen2.5-0.5B-Instruct --structured-outputs-config.backend outlines` with `"structured_outputs": {"choice": ["😀 yes", "no"]}`:

| | main | this PR |
|---|---|---|
| result | FILL IN | FILL IN |

## Details

- Root cause: `json.dumps` and `ast.literal_eval` disagree on `\uXXXX` surrogate pairs. Characters inside the BMP, such as "é", round trip correctly, which is why this went unnoticed.
- The lm-format-enforcer line has no test. On main that backend cannot be imported, because its vLLM integration needs a module that was removed. Open PR #52661 restores it. The fix there is the same one line.
- `choice` is typed `list[str]`, and request validation enforces that for the server. `get_structured_output_key` still passes a raw string through for direct Python callers. A JSON string keeps working; a Python repr string such as `"['a', 'b']"` would now fail to parse.
- Not a duplicate: PR searches for "literal_eval", "outlines choice", "backend_outlines" and "format enforcer", and issue searches for emoji, surrogate and unicode choice reports found nothing that changes this parsing.
- AI assistance was used to find the bug, write the fix and the test, and draft this description. I reviewed every changed line and ran the tests above.
