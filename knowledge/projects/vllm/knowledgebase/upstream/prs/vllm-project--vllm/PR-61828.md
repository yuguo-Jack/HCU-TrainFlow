# [CPU] Match the slot-mapping fallback to the Triton kernel signature

[Upstream PR](https://github.com/vllm-project/vllm/pull/61828) · state: open · merged: False

## Original PR description



## Overview

The CPU override was called positionally, so block_size received the slot-mapping tensor and the block-size assert failed.

## Claims

- Fixes `RuntimeError: Boolean value of Tensor with more than one value is ambiguous` in `_compute_slot_mapping_kernel_impl` during `execute_model` on CPU when Triton is unavailable.
- The override now uses the same parameter names and order as `ComputeSlotMappingKernel.kernel`, so the dispatcher forwards launch kwargs by name.
- `KV_CACHE_BLOCK_SIZE` is passed to the C++ op, and slots past `num_tokens` are filled with `PAD_ID`. Context parallelism is still rejected on CPU.


## Validation

- Compared the parameter lists of `_compute_slot_mapping_kernel_impl` and `ComputeSlotMappingKernel.kernel`. They match in name and order.
- No new test was added. This path runs only when Triton is unavailable, and the failure was observed on an s390x CPU serve of `ibm-granite/granite-4.1-3b`.
- After this change, rebuild and serve on that CPU. One chat request should get past `compute_slot_mapping` without the boolean-tensor assert.

## Details

`KernelOverride` forwards by keyword only when the replacement function's parameter names equal the Triton kernel's `arg_names`. The CPU function used `query_start_loc`, `block_size`, and `BLOCKS_PER_KV_BLOCK`, while the kernel uses `query_start_loc_ptr`, `slot_mapping_ptr`, and `KV_CACHE_BLOCK_SIZE`. The mismatch sent the slot-mapping tensor into `block_size`, and `assert block_size * BLOCKS_PER_KV_BLOCK == KV_CACHE_BLOCK_SIZE` could not reduce a multi-element boolean tensor.
The fix stays in the CPU fallback. The Triton kernel and the C++ slot-mapping op are unchanged. The C++ op still does not implement context parallelism; `TOTAL_CP_WORLD_SIZE != 1` continues to raise.
