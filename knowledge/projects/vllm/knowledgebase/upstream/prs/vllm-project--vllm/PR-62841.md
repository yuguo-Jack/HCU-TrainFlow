# [Bugfix][Mamba] Avoid re-marking committed prompt-tail boundaries as cached this step

[Upstream PR](https://github.com/vllm-project/vllm/pull/62841) · state: closed · merged: True

## Original PR description

## Overview

On hybrid models with `mamba_cache_mode="align"` (e.g. Qwen3.5), requests whose prompts share their last hash-aligned boundary are admitted one per engine step once that boundary is committed. This hits reads fanned out over one prompt and the children of a parallel-sampling request (`n > 1`). This PR skips re-caching that boundary in `MambaManager._cache_partial_tail_block` when the block already carries its hash, so these requests are admitted together. Related: #29387 (the same-step guard this interacts with), #61192 (`/v1/systemone` reads over one state, which take this path).

## Claims

- Bug fix: requests that hit an already committed prompt-tail boundary are no longer deferred, so a fan-out over a shared prefix is admitted together instead of one request per step. Which blocks are cached and hit does not change.
- `vllm bench serve` on Qwen3.5-4B: 5.0x request throughput for a fan-out over shared prefixes with 1-token outputs, 3.0x with 64-token outputs, and 4.7x for parallel sampling with `n=16`. Median TTFT drops 5–15x.
- No accuracy change: on `/v1/systemone` decisions, flips against a serial reference stay at noise level (1/458 vs. 2/458, same max |Δp|), and accuracy is 0.891 with and without the fix.

## Details

**Root cause.** `MambaManager._cache_partial_tail_block` re-caches the prompt's last hash-aligned boundary whenever a request whose prompt passes that boundary is scheduled. The request's block at that boundary may already carry exactly that hash, either because it is a prefix-cache hit or because the request committed it in an earlier step. Nothing new is written in that step, but the function still returns the hash. `cache_blocks` then adds it to `cached_blocks_this_step`, and `get_num_blocks_to_allocate` defers every other request whose hit ends on that block (the guard from #29387). This repeats whenever the producer's next chunk or a sibling is scheduled, so siblings are admitted one per step. Because the deferral is reported as insufficient blocks, the scheduler also stops scanning the waiting queue for that step. We found it by logging each deferral with the step that had added the hash: every one pointed at a re-cache of a block already keyed at that boundary.

**Fix.** In the non-checkpoint branch, return early when `source_block.block_hash_num_tokens == num_tokens`. The checkpoint branch above already uses the same condition.

**Why this is safe.** The skip applies only when the block already carries the hash for exactly this boundary, so its state was written in an earlier step or arrived as a hit. A sibling scheduled in this step reads it after that write, since forwards run in order. A step that does write the state still marks the hash, either through the first `cache_partial_block` call for a mid-block boundary or through the full-block loop in `cache_blocks`, so the #29387 guard still applies where it is needed.

**Not a duplicate.** The open PRs that touch `_cache_partial_tail_block` or `cached_blocks_this_step` fix other problems:

- #52972 and #53158 add a similar check to the full-attention manager's `_cache_partial_tail_block`, for stale partial hashes after full-block promotion.
- #56525 replaces the same-step set with a commit fence. The re-mark would still re-publish the hash there and fence siblings until the step commits, so the two changes compose.
- #61282 keeps the boundary state alive until the request ends.
- #55142, #52244 and #53802 change when or where the boundary is registered (connector loads, MTP, EAGLE).

None of them skips the re-cache in `MambaManager`'s non-checkpoint path. RFC #55697 and #55873/#55875/#55876 add application-declared checkpoints with producer/consumer scheduling; this fix is for the default path, with no markers.

**Scope.** The gain depends on siblings arriving together. With many unrelated prefixes interleaved, the bug still admits about one sibling per prefix in each step before the first deferral, so the gap shrinks. In a shuffled `prefix_repetition` run (24 prefixes of 1200 tokens with 64-token suffixes, otherwise as above), main and the fix were within noise: 105.6 ± 6.5 vs. 108.4 ± 5.2 req/s with 1-token outputs, and 35.4 ± 0.2 vs. 36.4 ± 0.9 req/s with 128-token outputs. That run is also close to compute-bound, since each sibling recomputes 112 tokens.

A sibling that arrives in the same step as the producer's first write is still deferred by the #29387 guard, as intended. We also tried letting the scheduler skip a deferred request instead of stopping the scan; with this fix in place it gave no further gain, so it is not included.
