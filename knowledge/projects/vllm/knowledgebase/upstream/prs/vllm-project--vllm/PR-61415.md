# [CI] Release the previous checkpoint's page cache between LM Eval models

[Upstream PR](https://github.com/vllm-project/vllm/pull/61415) · state: open · merged: False

## Original PR description

## Overview

An LM Eval config list walks several multi-GiB checkpoints through a single container. Page cache is charged to the container's memory cgroup, which is what `_get_available_ram_bytes()` measures, so the models evaluated so far consume the RAM budget of the ones still to come. The safetensors prefetch is then skipped partway down the list and the loader falls back to serial mmap reads over NFS, roughly an order of magnitude slower.

I free each checkpoint's page cache when the next model is about to load, reusing the existing `drop_checkpoint_cache()`. The harness change is CI only and the release is gated on ROCm. `drop_checkpoint_cache()` itself gains a cache lookup fallback and a log line, which its one existing caller also benefits from.

## Claims

Two AMD steps lose their prefetch today and both should be fixed. The last model's cache is left in place, since nothing in the job needs it again but the next job on the node may. Every other step on this harness is unaffected, because its checkpoints are small enough or it loads a single model, so the gate never trips.

This is **gated on ROCm**, following `_shutdown_lm` in the same file. `:nvidia: (H100) LM Eval Large Models` runs the same config list but reads over VIRTIOFS rather than NFS, so `is_net_fs` is false and auto-prefetch never turns on there. Its available RAM also sits at 1.58 TiB and does not fall between the two models, measured over the last four nightlies, so upstream has nothing to gain.

The FP8 numbers below are **measured in CI**. The Large Models Harness numbers are **estimates derived from nightly timings**.

In build 94479 this step ran 16.1m with loading down from 452s to 260s, and the log showed why it is not yet at its floor: the release worked for three checkpoints and reported `No local checkpoint found` for `meta-llama/Meta-Llama-3-70B-Instruct` and `mistralai/Mixtral-8x7B-Instruct-v0.1`. Offline, `snapshot_download()` resolves a revision only through `refs/<revision>`, which the cache on that node does not have for those two repos, so 218.41 GiB stayed charged and one prefetch was still skipped. `drop_checkpoint_cache()` now falls back to the cache layout, which should take the step the rest of the way.

|---|---:|---:|---|

No model name repeats within a list, and none of these checkpoints appears in another config list, so no eval re-reads a checkpoint this releases.

## Details

`drop_checkpoint_cache()` already existed and is already tested by `test_drop_checkpoint_cache_releases_local_weight_files`, but its only caller is `vllm/models/deepseek_v41/nvidia/model.py`, which uses it to make room for Engram host tables. The generic loader never releases the cache its prefetch warms.

Releasing the previous model's cache at the start of the next load, rather than the current model's cache at the end of its own, keeps the last model cached without having to know which model is last. Skipped evals never reach `launch_lm_eval`, so they do not disturb the tracking.

The harness logger is named after the test module, not `vllm.*`, so it has no handler and its INFO records are dropped. The release notice is therefore a `print`, and `drop_checkpoint_cache()` reports which directory it resolved and how much it evicted, so a step that frees nothing can be told apart from one that frees the wrong files.

The lookup fallback cannot tell which revision was loaded, so it evicts every cached snapshot of the repo. Nothing is deleted and `posix_fadvise` leaves dirty pages alone, so the worst case is that a later job re-reads a snapshot from NFS.
