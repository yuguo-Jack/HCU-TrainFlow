# [Bugfix][KV Connector] Handle load failures after preemption

[Upstream PR](https://github.com/vllm-project/vllm/pull/62287) · state: open · merged: False

## Original PR description

## Overview

Fixes #61912. Retain the KV blocks of preempted requests until their in-flight load reports arrive, so failure handling can invalidate the cache and apply the requested failure policy.

Depends on #61769, whose aborted-owner fix is kept as a prerequisite commit. This adds the preempted-owner handling requested in #61912; running-owner recovery remains in #53298. [Incremental diff above #61769](https://github.com/Lewis-panda/vllm/compare/7238ccdf6d3ae8166bb8d16e8fc14a3f507bdd1f...53aa9dd3965860e455dafd87eda29afd59a23316). I'll rebase after #61769 merges.

## Claims

- Evict the rejected prefix and dependent suffix even after preemption.
- Discard samples from affected outstanding steps; terminate the owner under `fail`.
- Drain retained outputs before readmission, including after a failed prefix-cache reset.

## Validation

At `2dcb854d`, the CPU selection passed **501 tests**; unchanged `7238ccdf` production code with that revision's tests gave **476 passes and 25 intended regression failures**. The current head also passes **501 CPU tests**. Python 3.12, PyTorch 2.13 CPU; mocked connector and worker outputs. Applicable pre-commit checks passed.

The invalid-block suite has 63 cases. The 16 tests added by `2dcb854d` cover public producer-role scheduling pressure, reset followed by `schedule(N+1)`, and a longer prompt reaching the failed load's last block. At that revision, seven failed without the fix; successful-load controls passed.

[Guanxin independently validated the implementation at `89a93299`](https://github.com/vllm-project/vllm/issues/61912#issuecomment-6220454763) on GB200/Qwen3-0.6B, greedy, two trials per cell, standalone and combined with #53298 at `1eca68f4`. Under `fail`, the owner terminates and a subsequent request matches full recomputation; under `recompute`, both requests match that baseline. Successful-load controls are unchanged. Those GPU tests inject preemption directly. Since `89a93299`, changes are limited to tests, comments and diagnostic log wording; recovery logic is unchanged.

## Details

While load N is in flight, pressure or reset can preempt its owner and release its blocks. When report N arrives, scanning running requests misses that owner. Retaining its block IDs before release lets failure handling evict the dependent suffix, discard stale samples and apply `fail` before readmission.

The conservative admission guard can delay requests, including no-load connector requests; latency is unmeasured. Physical block-ID reuse by another request before the report remains the separate #61905 allocation-identity problem. Public-pressure tests use a producer-role mock; they do not establish reachability through a production synchronous-loading producer connector.

Thanks @guanxingithub for the preemption report and GPU validation, and @ArijitDeb for #61769 and the public-scheduler, reset-ordering and longer-prefix probes behind these regressions.

- ArijitDeb · comment · 2026-10-18T15:47:44Z · [source](https://github.com/vllm-project/vllm/pull/62287#issuecomment-6251879991)

Thanks @Lewis-panda. I ran the CPU selection from the description on `2dcb854d` and on `7238ccdf` with this PR's test file: 501 passed, and 476 passed with 25 failed, matching your numbers. The scheduler code is the same as `89a93299`, which I reviewed in #61912; only tests have been added since.

Of the 16 new tests, the 7 that fail on `7238ccdf` are all failed-load cases: the four producer-role pressure cases, reset-then-`schedule(N+1)` under `recompute`, and both longer-prompt cases. Every load-ok control passes on both trees. Reset-then-`schedule(N+1)` under `fail` also passes on `7238ccdf`, consistent with my probes: the next `schedule()` readmits the owner before the report, and the report then fails it while it is running. With only the admission gate removed (the `gate-ablation.patch` from my follow-up probes), exactly one of the 16 fails: reset-then-`schedule(N+1)` under `recompute`, where the step N+1 token is delivered. So the gate has its own regression test here.

The new tests cover the public-scheduler pressure, reset-ordering, and longer-prefix cases I raised in #61912.

Three small, non-blocking suggestions:
- In `test_reset_then_schedule_discards_rejected_next_frame`, consider also asserting `owner.request_id not in second.num_scheduled_tokens`. That would make the gate's intended readmission behavior explicit alongside the output assertions; the ablation already shows this is a valid regression test.
- The comment in `reset_prefix_cache()` about forcing "preemption + resumption in the same step" could mention that requests with retained in-flight records now wait for those records to drain.
- The new retained-record branch in `_handle_invalid_blocks()` adds preempted owners to `total_failed_requests` without adding their affected tokens to `total_failed_tokens`. Could the "tokens affected" log account for those owners, or make that exclusion explicit?
