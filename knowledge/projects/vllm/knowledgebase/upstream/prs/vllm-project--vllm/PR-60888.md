# [Perf][Core][Mamba] Export prefill checkpoints at or before the initial-state column

[Upstream PR](https://github.com/vllm-project/vllm/pull/60888) · state: open · merged: False

## Original PR description



## Overview

With a fine-grained prefix match unit (e.g. `--prefix-match-unit 128` on GLM-5.3-Flash, KDA linear attention + sparse MLA), many partial-hit prefills pay one extra fixed-cost prefill step. The scheduler rejects the in-pass prefill checkpoint whenever its column is at or before the column holding the initial state, then splits the prefill at the checkpoint boundary. This PR lets a request's first chunk export that checkpoint in the same pass, so those prefills run as a single step. It also fixes a related cache-publishing bug in `MambaManager`. Follow-up to #56960; related to #59146, #59175, #59759 and #58021.

## Claims

- Partial-hit prefills whose checkpoint column is at or before the initial-state column (`checkpoint_col <= (start - 1) // block_size`) no longer split at the tail boundary. On GLM-5.3-Flash TP8 with pmu128, a hit of 2944/3300 tokens now prefills in one step. Median TTFT at c=1 goes from 58.8 ms to 41.4 ms. At c=16 it goes from 404 ms to 286 ms.
- No accuracy change: GSM8K and a multi-turn GSM8K that feeds the model's own answers back (every turn after the first is a prefix hit) match the unpatched image and the baseline. Prefix hit rates are unchanged.
- Fix: when a chunk resumed mid-block and ran past the block boundary, `MambaManager.cache_blocks` published that slot under its full-block hash, although the slot holds the initial (or checkpoint) state. A later request could then match it.

## Validation

Geometry: mamba block 1152, hash block 128, checkpoint alignment 16. Both arms use the same image, with this PR overlaid on top; the PR is backported 1:1 to the image's vLLM version.

## Details

**Root cause.**
- In "align" mode with prefill-checkpoint blocks, the state at the prompt's last hash-block boundary `P` is written into column `cdiv(end, bs) - 2` of the request's Mamba block row in the same forward pass.
- `is_mamba_prefill_checkpoint_valid` required that column to be strictly after the initial-state column `(start - 1) // bs`. With a 128-token unit, a hit followed by a short tail often lands at or before it. For example, a hit of 2944 and a prompt of 3300 give checkpoint column 1 and initial-state column 2.
- The scheduler then fell back to stopping the chunk at `P`. The extra step costs about 20-35 ms for small chunks and about 120 ms for chunks above 512 tokens.

**Change.**
- `vllm/v1/kv_cache_interface.py`: `is_mamba_prefill_checkpoint_valid` accepts `checkpoint_col <= initial_state_col`, except for a block-aligned start where the two columns coincide (that column is the shared hit block). New helper `mamba_prefill_checkpoint_needs_fresh_row`.
- `vllm/v1/core/sched/scheduler.py`: these geometries are allowed only for a request's first chunk (`num_computed_tokens == 0`), whose worker block-table row is sent whole. A running request's row is append-only and may still hold a stale id at that column, so it keeps splitting.
- `vllm/v1/core/single_type_kv_cache_manager.py` (`MambaManager`):
  - For `checkpoint_col < initial_state_col`, reserve one extra block and put it in the skipped (null) slot.
  - For `==` with a mid-block start, the checkpoint overwrites the request's private copy-on-write block, which only fed the initial state.
  - `cache_blocks` skips past a slot whose content is not its full-block state. This is also the publishing bug fix listed under Claims.
- The worker side is unchanged. `vllm/model_executor/layers/mamba/checkpoint.py` already writes to whatever block id is in that column, for any backend (KDA, Mamba2, etc.).

**Related.** #59826 also changes how Mamba prefill checkpoint boundaries are computed (resend-safe boundary, EAGLE, Mooncake), but it does not touch the initial-state-column rule. The two PRs touch some of the same functions, so whichever merges second needs a rebase.

**Not addressed (separate issue).** With DCP8 on a KV-capacity-bound multi-session workload, pmu128 was much worse than the default unit, which is already partial at 1152 there. Prefix hit rate was 27% vs 66% and TTFT p50 4.5 s vs 0.67 s. A CPU replay of that session trace through the KV cache manager reproduces it from cache footprint and eviction, not from prefill splits: at 2415 blocks the hit rate is 0.22 with pmu128 vs 0.67 with the default. This PR moves it only slightly (0.22 -> 0.30), so it needs its own follow-up.

Thanks for this PR. We found one case where the worker writes a Mamba checkpoint into a block that is still in the prefix cache.

**Path:** a running request starts a chunk in the middle of Mamba block k, for example after a block-aligned hit and the shared-prefix junction. The scheduler and the manager allow the relaxed checkpoint shape only on a first chunk, so the manager reserves no block for column k-1. The worker still computes a checkpoint for column k-1 with the relaxed `is_mamba_prefill_checkpoint_valid`. Its append-only row holds the freed block there, and that block keeps its cache key. `store_prefill_checkpoint` writes into it, and a later hit restores the wrong state.

**Repro:** `test_running_row_declines_checkpoint_at_or_before_initial_state` (Mamba block 64, unit 16, attention block 16, junction on) fails with `assert None == (112, 0)`.

**Suggested fix (diff below):** a per-row flag, `CommonAttentionMetadata.fresh_block_table_rows`, marks the first scheduled step of a new or resumed request. The V1 and V2 runners set it. `compute_mamba_prefill_checkpoints` declines the relaxed shapes on a row that is not fresh. The fix only declines exports: the scheduler, the manager, the steps and the hits do not change.

**Results:** the PR tests and 3 new tests pass on CPU. A CPU ledger of random request chains goes from 56 wrong restores to 0. A GPU probe of a backport of this PR plus the fix (hybrid Mamba model, MTP, prefill and decode over NIXL, unit 16) gives 0 wrong outputs.
