# [KV Offload] Give each rank its own CPU region outside the replicated layout

[Upstream PR](https://github.com/vllm-project/vllm/pull/59547) · state: open · merged: False

## Original PR description

Outside the replicated layout, ranks never read each other's slots, but they still share one region whose rows interleave all ranks. Every rank pre-faults and pins its strided slots in the same shm file, contending with the others.

Give each rank its own region holding only its slots, in its own shm file. No other process maps that file, so the rank no longer waits on the cross-worker barrier before unlinking it. The replicated layout keeps the shared region.

## Tests

4× H200, measured on `16d4ac4ba3` with this change (the touched files are unchanged on current main):

- GLM-5.3 W4A8, TP4 + EP, 256 GiB native CPU offload: the offload startup step fell from 63.6 to 22.6 s (22.8 and 22.4 s in two runs), and pinning from 20.8 to 3.3 s. A 20k-token retrieval prompt answered 8/8 lookups cold and 8/8 after `/reset_prefix_cache`, with 3.9 GB reloaded from CPU.
- `pytest tests/v1/kv_offload tests/v1/kv_connector/unit/offloading_connector tests/v1/kv_connector/unit/test_offloading_connector.py tests/v1/worker/test_utils.py`: 1182 passed. The 7 failing tests need a gated model and fail the same way on main.
- pre-commit, including mypy, passed.

File: `vllm/v1/kv_offload/cpu/spec.py` · line 192

Claude:
    the /dev/shm and cgroup capacity check now
    under-detects by a factor of world_size. `SharedOffloadRegion` calls
    `check_shm_free_space(self.total_size_bytes)` on the creator path
    (shared_offload_region.py:137). Before, exactly one creator checked the full
    `cpu_bytes_to_use`. Now all world_size ranks are creators and each checks
    `cpu_bytes_to_use / world_size`.
    Concrete: `--shm-size=128g`, `cpu_bytes_to_use=256GiB`, TP4. Before: the creator sees
    256 GiB required > 128 GiB free and raises the intended RuntimeError
    ("Increase /dev/shm…") at startup. After: each rank sees 64 GiB ≤ 128 GiB free — all
    four pass, because they race on the same free-space snapshot and tmpfs `ftruncate` is
    sparse so nothing is charged yet — and the failure resurfaces as ENOSPC or SIGBUS
    inside `MADV_POPULATE_WRITE`/the fallback page-touch loop, mid-startup, with no
    actionable message. `check_cgroup_memory_available` degrades the same way.
    Fix: check the aggregate once — pass a `creator_memory_check` validating
    `total_size_bytes * world_size`, or keep one designated rank checking the full budget.

- orozery · comment · 2026-10-14T10:30:57Z · [source](https://github.com/vllm-project/vllm/pull/59547#discussion_r4269645292)

File: `vllm/v1/kv_offload/cpu/spec.py` · line 194

Claude:
    aggregate /dev/shm can exceed
    `cpu_bytes_to_use`. `num_chunks` is still derived (spec.py:116-119) from
    `round_up(world_size * p, PAGESIZE)`, but each rank now reserves
    `num_chunks * round_up(p, PAGESIZE)`. Padding moved from once per chunk row to once per
    rank per row, so the aggregate is `num_chunks * world_size * round_up(p)` and overshoots
    by up to `num_chunks * (world_size - 1) * PAGESIZE`.
    Concrete: MLA-shaped per-worker pages are routinely not page-aligned (e.g. 576 latent
    dims × 2 B × block_size 16 = 18432 B per layer, ×61 layers = 1,124,352 B = 274.5 pages).
    At 256 GiB with ~4 MiB chunks (~65k chunks) and TP4 that is ~0.8 GiB over budget — small
    in absolute terms, but it silently breaks the "`cpu_bytes_to_use` is a budget" contract
    and grows with world_size.
    Fix: recompute `num_chunks` from the per-rank row size,
    `cpu_bytes_to_use // (world_size * round_up(p, PAGESIZE))`, when not replicated.
