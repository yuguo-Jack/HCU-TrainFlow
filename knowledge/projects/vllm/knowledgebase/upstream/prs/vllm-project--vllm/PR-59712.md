# [Feature][Spec Decode] ngram_hint: draft tool calls from the chat template's rendered call syntax

[Upstream PR](https://github.com/vllm-project/vllm/pull/59712) · state: open · merged: False

## Original PR description

## Purpose

The n-gram speculative methods work by finding the recent context earlier in that same context and reusing what came after it.

For a tool call, though, there is nothing to find.

The prompt has the tool schema as JSON, while the model outputs the actual tool call syntax from its chat template, for example `<tool_call>\n{"name": ...` for Qwen and Hermes. Those are different token sequences. So on the first tool call of a conversation, the model still decodes that structure one token at a time, even with `ngram` or `suffix` on. Plain `ngram` does find the tool *name*, because it is in the schema, and then diverges right after it at the schema's `"description"` vs the call's `"arguments"`.

Agentic use is a pretty large share of how these models are served now, and agent loops are dominated by tool calls. A harness might expose tens of tools and most of them only get called once per session, so almost every tool call is this cold-call case. I've been getting deep into speculative decoding at work and this is the gap I kept running into.

The idea is pretty simple:

Render the conversation normally, then render it again with an example assistant tool call appended. The difference between those two renders is the assistant turn the model is about to generate, already in that model's own chat template and its own tokens. Then hand those tokens to the drafter.

Now instead of decoding the structural part of the tool call one token at a time, the model verifies a bunch of it in one batch. The actual argument values are still generated by the model, this only drafts the syntax around them.

Nothing is forced. If a hint is wrong it just fails verification and costs one speculative step, so the output is identical whether the method is on or off, right!

What this PR adds, in three commits:

1. **`ngram_hint`**, a lookup proposer that drafts from token sequences supplied per request on `SamplingParams.extra_args["spec_hints"]`. It takes `input_batch` like `SuffixDecodingProposer` does, plus the runner's request states so it can read `extra_args` per request, following the `kv_transfer_params` precedent. It is registered as V1-runner-only in `config/vllm.py` next to `suffix`, since the V1 runner is where the CPU lookup drafters live. The new V2 ngram speculator (#40704) is a GPU kernel over the token history, and a V2 version of `ngram_hint` would be a GPU matcher over per-request hint tensors. That is a separate change I am happy to follow up with once this one is reviewed.
2. **`vllm/renderers/tool_call_hints.py`**, `render_tool_call_hints()`, which does the two renders and returns the token ids of the difference, one sequence per tool.
3. **The chat completion server** attaches those hints when the engine is running `ngram_hint`, so an unmodified OpenAI-compatible client with `tools` gets the drafts. The check is one flag computed at startup (mirrors `has_kv_connector`), requests without tools or with `tool_choice="none"` are skipped, and a `spec_hints` the client sent through `vllm_xargs` is kept as is.

The verification path is untouched.

Limits I know about:

- All the hints share the same prefix up to `{"name": "`, and the drafter takes the first match there, so the first draft of a call to the second tool comes from the wrong hint and gets rejected at the name. At two tools that only cost one step in my runs (numbers below), but with many tools the shared prefix matters more. Stopping the draft where the hints disagree should fix this. I would leave that as follow-up work.
- With thinking enabled the rendered hint carries an empty think block, so the draft fails early and has to re-enter at `</think>`. Not measured yet.
- Rendering is one template pass per tool, once per request, on the CPU, and only when `ngram_hint` is the configured method.

This is the vLLM version of the idea I posted for llama.cpp in https://github.com/ggml-org/llama.cpp/discussions/29405.

## Test Plan

Unit tests, no GPU:

```
pytest tests/v1/spec_decode/test_ngram_hint.py tests/v1/spec_decode/test_ngram_hint_propose.py tests/renderers/test_tool_call_hints.py
pytest tests/entrypoints/openai/chat_completion/test_serving_chat.py -k spec_hints
```

End to end with `Qwen/Qwen3-0.6B`, greedy, two tools (`get_weather`, `get_time`), thinking off, `num_speculative_tokens=8`, one config per process (`none`, `ngram`, `ngram_hint`), once for a request that calls the first tool and once for one that calls the second.

Then the same two requests through `vllm serve` over HTTP with `--enable-auto-tool-choice --tool-call-parser hermes`, reading the `vllm:spec_decode_*` counters from `/metrics` before and after each request.

## Test Result

23 unit tests pass, and the 38 other tests in `test_serving_chat.py` still pass. `ruff` at the pre-commit pin is clean. `mypy` reports nothing on the lines this PR adds (the errors it reports in `gpu_model_runner.py` and `serving.py` are already there on `v0.30.0`).

`LLM.generate`, same output text across all three methods in both runs:

| request calls | method | drafts | draft tokens | accepted | acceptance |
|---|---|---:|---:|---:|---:|
| `get_weather` (1st tool) | `ngram` | 4 | 32 | 7 | 22% |
| `get_weather` (1st tool) | `ngram_hint` | 3 | 18 | 16 | 89% |
| `get_time` (2nd tool) | `ngram` | 5 | 40 | 6 | 15% |
| `get_time` (2nd tool) | `ngram_hint` | 3 | 18 | 16 | 89% |

So the 20-token call goes from 20 decode steps to about 4.

Through `vllm serve`, plain chat requests with `tools` and nothing else special:

| request calls | parsed tool call | completion tokens | drafts | draft tokens | accepted |
|---|---|---:|---:|---:|---:|
| `get_weather` | `{"city": "Paris"}` | 20 | 3 | 18 | 16 |
| `get_time` | `{"tz": "Asia/Tokyo"}` | 23 | 3 | 18 | 16 |

Happy to adjust anything about where this sits in the config or the runner :)
