# [Perf][MRV2] Skip empty draft-token resets on request admission

[Upstream PR](https://github.com/vllm-project/vllm/pull/61640) · state: closed · merged: True

## Original PR description



## Overview
On GH200, short-input embedding inference at high concurrency is **CPU-bottlenecked by the EngineCore main thread**, with GPU SM utilization only **~9–18%**. Skip unnecessary per-request draft-buffer indexing and zeroing when Model Runner V2 has zero speculative steps, improving throughput by **~11–28%** in the measured workload while preserving the stale-slot reset from [#39833](https://github.com/vllm-project/vllm/pull/39833) for nonempty buffers. The improvement is largely due to reduced GIL contention.



## Claims
- Remove unnecessary PyTorch operations from request admission for pooling and ordinary non-speculative generation.
- Preserve draft-token clearing on slot reuse whenever the buffer has columns, including speculative decoding and diffusion models.
- The PyTorch operation releases the GIL, leading to the main thread being unnecessarily preempted by other threads that could do their work while the main thread waits for the GPU instead.
- Existing pinned GH200 embedding benchmarks report +10.6% request throughput for short inputs at concurrency 512 and +25.0–28.2% at concurrency 2048 for this guard alone.


## Validation
Checks run for this change:

```bash

pre-commit run --files vllm/v1/worker/gpu/states.py tests/v1/worker/test_gpu_model_runner_v2.py

```

With short inputs on GH200, throughput plateaus at roughly **5–6k requests/s (~85–100k tokens/s)** while the EngineCore main thread is CPU-saturated and GPU SM utilization remains **~9–18%**. For comparison, 1024-token inputs reach roughly **400k tokens/s** on the same server. These observations identify per-request work on the engine's main thread as the short-input throughput bottleneck.

| Concurrency | Stock throughput | With guard, pass 1 / pass 2 (estimated) | Gain, pass 1 / pass 2 |
|---|---|---|---|
| 512 | ~4.66k req/s | ~5.15k / ~5.15k req/s | +10.6% / +10.6% |
| 2048 | ~5.57k req/s | ~6.96k / ~7.14k req/s | +25.0% / +28.2% |

Configuration: `nvidia/Nemotron-3-Embed-1B-BF16`, FP8 quantization, v0.31.0 aarch64 container, one GH200, MRV2 with synchronous scheduling, 16 API servers, and unique random short text inputs. Two reverse-order benchmark passes used six runs per configuration. Engine cores 4–5, API-server cores 8–39, and client cores 40–71 were pinned on GPU 0's NUMA node. Stock pinning-validation repeats spanned 4741–4965 req/s; per-patch raw variability is unavailable here.

```text
--max-cudagraph-capture-size 32768

```



## Details
`RequestState` allocates `draft_tokens` with shape `[max_num_reqs, num_speculative_steps]`. Admission previously evaluated `self.draft_tokens[req_idx].zero_()` even when the row had zero elements. The guard tests the configured width before indexing.

**Why such a large improvement:** The reason seems to be GIL contention. The pytorch op releases the GIL and then the main thread spends time waiting in pthread_cond_timedwait to reacquire it. If GIL is not released at that point, other threads will acquire it when the main thread waits for the GPU instead, leading to better overlapping GPU and CPU work.

**Why short inputs matter for embedding models:** semantic search commonly embeds a short question or a few keywords to retrieve much longer passages. Short-query embedding is therefore a core online serving workload, even when the indexed documents are long.
