# [Feature][KV Connector] Add UMBP standalone mode

[Upstream PR](https://github.com/vllm-project/vllm/pull/59275) · state: open · merged: False

## Original PR description

## Purpose

Adds `UMBPStoreConnector`, a KV connector that offloads full prefix-cached KV blocks to a UMBP host-DRAM pool (MORI) and restores them on a later prefix hit, after vLLM has evicted them from GPU memory (RFC #57187). Two deployments are supported:

- **Embedded**: each worker owns a private pool in its own process. No extra process to run.
- **Standalone**: one node-local `umbp_standalone_server`, started outside vLLM, owns the pool. Every engine, DP rank and worker on the node attaches to it, so engines share stored prefixes and the pool outlives an engine restart.

The branch is self-contained on `main` and includes the core and embedded mode also proposed in #58568, so the stack builds and tests on its own.

## Design

vLLM keeps scheduling, GPU block ownership and block hashes; a runtime owns the pool and the transfers.

- **Lookup**: the scheduler looks up the blocks after the local prefix hit and reports whole-block hits. Keys encode the model, KV layout, cache group, parallel rank (TP/DCP/PP) and draft model, so incompatible engines never share objects, and a hit requires every rank's object. The last block is dropped for EAGLE-style drafters, as core does.
- **Load**: loads target the blocks core allocated and run asynchronously by default, so the forward pass never waits on a transfer. A failed load reports its blocks and core recomputes them (`kv_load_failure_policy=recompute`).
- **Store**: newly completed blocks are stored after the forward pass. A store holds its GPU blocks until every rank has finished, and a preempted request's transfers finish or are cancelled before core can reuse its blocks.
- **Embedded runtime**: a MORI client per worker; scheduler lookups reach each rank over per-engine local sockets.
- **Standalone runtime**: workers register their GPU KV with the server over HIP IPC and the server copies between those allocations and its pool, so no KV bytes cross the socket. vLLM never starts or sizes the server: pool-sizing and auto-start options are rejected, as with Mooncake store and LMCache MP.
- **Hybrid models**: models with several KV cache groups (Mamba-style layers, sparse-attention indexers, draft-model groups) coordinate hits across groups with core's KV cache coordinator, store Mamba align states from core's boundary hand-offs, and always load asynchronously.
- **Observability**: `BlockStored`/`BlockRemoved` KV cache events and transfer counters through `KVConnectorStats` and Prometheus.

## Commit structure

The PR is split into seven commits, each self-contained with its own tests, meant to be reviewed in order:

1. Core connector and embedded mode, with docs, unit tests, GPU integration tests and an AMD CI step.
2. Bulk whole-block transfers, and skipping restored blocks that are still in the pool.
3. Transfer timeouts, cancelling queued transfers on preemption, and retrying puts while the pool evicts.
4. Optional asynchronous lookup off the scheduler thread.
5. Hybrid KV cache groups.
6. KV cache events and transfer metrics.
7. Standalone mode.

## Configuration

```json
{"kv_connector": "UMBPStoreConnector", "kv_role": "kv_both", "kv_load_failure_policy": "recompute", "kv_connector_extra_config": {"mode": "embedded", "total_capacity_bytes": 10737418240}}
```

Standalone: start `umbp_standalone_server` on the node, then use `{"mode": "standalone", "endpoint": "/path/to/server.sock"}`. See `docs/features/umbp_embedded_dram.md` and `docs/features/umbp_standalone.md`.

## Test Plan

- Unit tests: `tests/v1/kv_connector/unit/test_umbp_*.py` (core, embedded, async lookup, hybrid, events, standalone). Each commit passes its own suite and pre-commit.
- GPU integration tests: `tests/v1/kv_connector/umbp_integration/`, including a token-level end-to-end test that evicts a prompt from GPU memory, restores it from the pool and checks the generated tokens.
- Serving benchmarks against Mooncake Store (embedded and standalone) on GPT-OSS-20B and Llama-3.1-8B, one GPU per engine, 10 GiB pool: `vllm bench serve` with 256 requests of 8192 input / 1024 output tokens at 2 req/s, and 10 forced-restore trials of a 10,001-token prompt (cold run, GPU-only cache reset, replay that can only restore from the pool).
- Cross-engine restore through one standalone server: engine A computes a prompt, engine B restores it.
- Kimi-K3 with a DSpark drafter (TP=8, one node): restore of a long prompt with draft-acceptance comparison, plus a negative control that skips restoring the drafter's cache group.

## Test Result

- Unit tests: 101 to 213 passed across the seven commits; GPU integration: all passed (14 at the top of the stack). Pre-commit clean.
- Every restore trial was verified by external-hit and native-load metrics (10,000 of 10,000 tokens restored, no GPU hit, no transfer errors), and restored output matched the cold output.

Restore latency of a 10,001-token prompt (median of 10 trials, ms):

| Model | Recompute | UMBP embedded | UMBP standalone | Mooncake embedded | Mooncake standalone |
|---|---:|---:|---:|---:|---:|
| Llama-3.1-8B | 144.7 | **45.8** | 53.6 | 67.4 | 51.7 |
| GPT-OSS-20B | 92.9 | **25.7** | 27.9 | 34.0 | 27.1 |

Embedded restore copies from the worker's own DRAM straight into GPU KV at about 45 GiB/s, which makes it the fastest restore path measured, 32% faster than Mooncake embedded on Llama-3.1-8B. Standalone restore is on par with Mooncake standalone.

Serving overhead (mean TTFT ms / TPOT ms, first measured run):

| Model | UMBP embedded | UMBP standalone | Mooncake embedded | Mooncake standalone |
|---|---|---|---|---|
| GPT-OSS-20B | 102.5 / 4.14 | 103.5 / 4.15 | 99.8 / 4.13 | 100.6 / 4.12 |
| Llama-3.1-8B | 179.1 / 11.70 | 184.0 / 11.83 | 178.9 / 11.65 | 178.3 / 11.71 |

TPOT is within 1% of Mooncake Store; storing runs off the forward pass without contending with it.

Cross-engine restore through one standalone server (median ms): GPT-OSS-20B 91.6 recompute on engine A versus 30.6 restore on engine B; Llama-3.1-8B 153.8 versus 70.0. When both engines serve the same prefix traffic, engine B serves 99.8% of the shared prefix tokens from the pool (GPT-OSS-20B).

Kimi-K3 with DSpark (42,932-token prompt, 4 trials per run, embedded and standalone):

| Metric | Cold | Restored |
|---|---:|---:|
| Tokens restored from the pool | 0 | 39,936 |
| TTFT | 5.4 to 6.1 s | 3.0 to 3.6 s |
| Draft acceptance (median over 10 runs) | 0.585 | 0.581 |

Skipping the restore of the drafter's cache group drops acceptance to 0, so the hybrid path restores every group the drafter reads.

Kimi-Linear-48B-A3B-Instruct GSM8K through one standalone server (earlier revision of this branch, same hybrid design): cold 88.3 / 89.5, with pool hits 89.1 / 89.2, replay 89.5 / 88.7.
