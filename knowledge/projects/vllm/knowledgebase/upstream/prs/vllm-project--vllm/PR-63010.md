# [Bugfix][KV Offload] Reset the store cursor when a request restarts from token 0

[Upstream PR](https://github.com/vllm-project/vllm/pull/63010) · state: closed · merged: True

## Original PR description

## Overview

A request resumed from preemption kept `next_stored_chunk_idx` from before the preemption. If the CPU tier had evicted its chunks meanwhile, the chunks below the cursor were never offered again and everything stored afterwards sat behind a chunk-0 miss. Reset the cursor in `get_num_new_matched_tokens`, which only runs when a request starts from `num_computed_tokens == 0`.

## Claims

- A resumed request offers its chunks from chunk 0 again; `prepare_store` drops the ones still resident, so nothing is stored twice.
- A CPU prefix hit on resume is unchanged: `update_state_after_alloc` still raises the cursor afterwards.

## Validation

- `test_request_preemption` gains a `cpu_hit=False` case that fails on `main` and passes here, both scheduling modes.
- `pytest tests/v1/kv_connector/unit/offloading_connector`: 609 passed, 2 skipped. `pre-commit` clean.
- No open PR or issue covers this (searched `next_stored_chunk_idx`, `preempt offload`); #57813, #61375, #60574, #60810 and #62929 touch nearby code and compose with it.

## Details

`_reset_cache` already resets the cursor for the same reason. The reset cannot live in `_update_req_states` under `if preempted:`, which runs after `update_state_after_alloc` in the same step and would clobber the hit-derived cursor.

AI assistance (Claude) was used; I reviewed every line and ran the tests above.
