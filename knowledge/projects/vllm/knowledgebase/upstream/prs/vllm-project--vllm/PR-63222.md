# [Doc] Kimi-K3: document the GB300 disaggregated specialized-decode points in the guide and command builder

[Upstream PR](https://github.com/vllm-project/vllm/pull/63222) · state: closed · merged: True

## Original PR description

## Overview

Document the settings that the GB300 Dynamo + vLLM AgentX lane of [SemiAnalysisAI/InferenceX#4373](https://github.com/SemiAnalysisAI/InferenceX/pull/4373) (head `6417f957`) uses but `recipes/models/moonshotai/Kimi-K3.yaml` lacked, in both the guide and the command builder: the `latency_specialized` decode backend for disaggregated serving, plus the two roles' settings that go with it. The recipe already covers the aggregated `latency_specialized` path (Low latency serving) and the #4047 xPyD profile.

## Claims

- **Guide** (under **GB300: InferenceX AgentX disaggregated**): the worker table now lists the #4373 points: 1P3D c16 and 1P2D c24-c32 with specialized decode (decode `--max-num-seqs 12`), 1P2D c48-c64, 2P3D c240 and 3P4D c240 with the regular uncapped decode (128). Each worker spans two 4-GPU GB300 trays (TP8 + DCP8). A new **Specialized decode (low concurrency)** section gives the changes to the Workers commands:
  - Decode: `--additional-config '{"decode_backend":"latency_specialized"}'`, attention config without `tokenspeed_mla_min_split_kv`, `--max-num-seqs 12` (= `64 // (K + 1)` with the K4 draft), `--max-cudagraph-capture-size 64`, capture sizes 1..64 with `FULL_AND_PIECEWISE`.
  - Both roles: `--mamba-ssm-cache-dtype float32` (the backend needs FP32 recurrent state), `--cp-kv-cache-interleave-size 1`, no FlashInfer autotune. The interleave is pinned because NIXL P/D otherwise raises it to the KV block size after the specialized decode has read it, so its spec-verify causal mask uses the stale value.
  - The prefill workers do not set `--additional-config` (the backend rejects expert parallelism), and the K8 draft that the builder's Spec decoding toggle selects is rejected by the backend (at most 7 draft tokens).
- **Command builder** (GB300 `pd_cluster` only): the Dynamo/vLLM-router PD pools now render the specialized 1P2D c24-c32 worker commands; the previous decode `--max-num-seqs 8` was the 1P2D point that #4373 removes. The regular points use the Workers commands.

## Validation

- `node scripts/validate-source.mjs --source vllm --dir <this checkout>/recipes` passes (vllm-project/recipes @ `86540ba`).
- Rendered every variant x hardware x strategy x feature set x KV-offload option x PD router (none, Dynamo, SMG) x pool-node preset x frontend (19,800 renders) before and after: only the 360 GB300 `pd_cluster` renders change; no other hardware or strategy changes and none errors.
- GB300 + Dynamo prefill/decode render vs the #4373 `override_1p2d_specdecode` effective args (`disagg-variants.yaml` at the PR head): `--mamba-ssm-cache-dtype`, `--cp-kv-cache-interleave-size`, `--additional-config`, `--attention-config`, `--max-num-seqs`, `--max-cudagraph-capture-size` and the 1..64 capture sizes match per role. The builder also sets `cudagraph_mode` to `FULL_AND_PIECEWISE` explicitly (the lane relies on the default).
- Checked against vLLM main: `specialized_decode/runtime/__init__.py` (requirements, at most 7 draft tokens, rejects expert parallelism), `providers.py` (the DCP box reads `cp_kv_cache_interleave_size`) and `adjust_dcp_kv_cache_interleave_size` (NIXL only auto-resolves an unset interleave).

## Details

Per-concurrency worker counts stay in the guide because the builder renders one prefill and one decode pool per selection. The guide's old 1P4D/1P3D/2P5D capped rows are replaced because #4373 removes those points. Not verified here: the guide's reasoning that `--max-num-seqs 12` (12 x 5 = 60 tokens) fits the 64-token graph cap comes from the InferenceX PR's recipe comment, not from the kernel code. Excluded as InferenceX harness only: concurrency lists, synthetic acceptance and AIPerf/trace-replay settings, Slurm and telemetry.
