# [DSpark] Support PP prefill with KV transfer (disaggregated serving)

[Upstream PR](https://github.com/vllm-project/vllm/pull/56957) · state: open · merged: False

## Original PR description

## What

DSpark pipeline-parallel support, end to end: **aggregated (in-flight-batching) serving with PP targets** and **prefill on a pipeline-parallel producer with KV transfer** (PD-disaggregated serving).

This PR is self-contained: it re-applies #56956 (reverted in #58484 for further streamlining) and builds the PD producer path on top. Happy to iterate on the streamlining with you, @njhill.

Aggregated IFB PP (re-applied #56956):

- `PPHandler` broadcasts the last rank's sampled tokens (and draft tokens, for spec decode) to earlier stages on a side stream; earlier stages apply them `pp_size` steps later in a deferred post-update.
- The deferred post-update Triton kernel is pre-compiled during warmup with the exact serving specialization (int32 `idx_mapping`, 16-byte-aligned `num_sampled`/`num_rejected` via a padded combined buffer) — a mid-serving compile there would deadlock on the in-flight broadcast NCCL kernel.
- DSv4 router: pad the top-k buffer so non-last stages can drop EAGLE read-ahead rows.

PD prefill-only producer (this PR on top):

- `SpeculativeConfig.target_kv_transfer_config` + `is_dspark_prefill_only()`; NIXL is rejected for this mode (it cannot describe packed per-layer KV regions; Mooncake works).
- The scheduler narrows `use_eagle` (and eagle block-drop) for the prefill-only producer so it never does the EAGLE-style read-ahead.
- `DFlashSpeculator.materialize_context_kv()`: precompute and store draft context KV without drafting. `propose()` delegates to it when `is_dspark_prefill_only()` and returns `None`, so the model runner keeps its single call site unchanged and only skips the draft-side subsystems on the producer (rejection sampler, drafter graph capture, EPLB registration, draft-token handler) via one `dspark_prefill_only` flag. The preparation half is shared with `propose()` via `_prepare_draft_inputs()`; on the aggregated path the context-K/V store stays graph-aware as introduced by #57632 (merged here), while the producer stores eagerly (it captures no draft graph).
- The DSv4 draft in this mode builds only the attention submodule needed for prefill (`context_kv_only`) — avoiding transient MoE expert allocation — and loads just the context-KV weights (the merged `context_wkv_proj` plus per-layer `kv_norm`).

Kimi-K3 DSpark additionally relies on the TritonMLA causal multi-token fix from #51065 (merged; included in this branch's base; verified on SM120).

Split from #53577 (reviewer request).

## Model evaluation

Validated end-to-end on the pre-split stack (#53577 lineage): DeepSeek-V4-Flash-0731 DSpark PD disaggregation with PP on both sides — prefill PP2×TP2 (prefill-only DSpark producer) + decode PP2×TP2 with DSpark, Mooncake KV transfer (TCP transport): GSM8K strict-match **0.9447** (1319 samples, stderr 0.0063). This is exactly the P-PP + D-PP DSpark combination previously reported to produce garbled output.

This rebuild rebases that stack onto current main (including the #57632 context-K/V graph-capture refactor and the #58484 revert of #56956, which this PR re-applies); the rebase keeps the aggregated-path behavior and changes no model numerics.

Re-validated on this exact tree (SM120, same both-PP PD configuration, Mooncake TCP): GSM8K strict-match **0.9462** (1319 samples, threshold 0.8) — consistent with the pre-split stack's 0.9447. The re-validation caught one integration bug from the #57632 merge: the graph-captured context-K/V staging buffer was sized by the hc-widened `hidden_size` (that widening exists for MTP-style drafters whose forward eats the target's pre-hc_head residual), while DFlash only ever stores `combine_hidden_states` output there — fixed in `103ffe9e9e` by sizing it from the draft's own hidden size, with a regression test.

After the review-driven streamlining (model_runner.py diff down from 197 to 66 changed lines: the producer branch moved behind `propose()`, and `warmup_pp_decode_update` moved to warmup.py), re-validated again on HEAD `b2952d32d0` (SM120):

- Aggregated IFB PP2×TP2: GSM8K strict-match **0.9545** (1319 samples).
- Both-PP PD, Mooncake TCP: GSM8K strict-match **0.9431** (1319 samples). (Run on a host whose GPU P2P is disabled at the NCCL level for an unrelated IOMMU issue — transport-level only, no effect on the correctness paths under test.)

Infrastructure flakes observed during validation are unrelated to this PR: the known Mooncake bootstrap 5s HTTP timeout (#58543) on cold-start/high-load attempts, and a harness abort-mode teardown racing its GPU-memory cleanup check on one passing run.

AI assistance was used in preparing this PR.

@njhill Thanks for the review — I've done a refactoring pass on the current head (`b2952d32d0`):

1. **model_runner.py: 197 → 66 changed lines.** The producer branch no longer lives in the runner: `DFlashSpeculator.propose()` now delegates to the context-KV materialization itself when `is_dspark_prefill_only()` and returns `None`, so both the dummy-run and the execute call sites are back to the unchanged upstream calls. What remains in the runner is one `dspark_prefill_only` flag, five one-line gates (EPLB registration, rejection sampler, adaptive verification, draft-graph capture, draft-token handler), and a `None` check around the draft-table update.
2. **`warmup_pp_decode_update` moved to warmup.py** — it is warmup-only logic.
3. **`broadcast_drafts` moved back** to its original position (the apparent move was a re-apply artifact — see the inline reply).

On `PPHandler.disabled`: it mirrors the existing `KVConnector.set_disabled()` warmup pattern (same motivation — synthetic warmup steps must not post side-stream NCCL ops that can overlap the next step's activation p2p and deadlock the pipeline). Happy to experiment with an alternative (e.g. stream-ordered broadcast during warmup instead of skipping) if you'd rather see the flag go.

Re-validated after the refactor on SM120 (DeepSeek-V4-Flash-0731 DSpark): aggregated IFB PP2×TP2 GSM8K strict-match **0.9545**; both-PP PD (Mooncake TCP) GSM8K strict-match **0.9431** — details in the Model evaluation section.
