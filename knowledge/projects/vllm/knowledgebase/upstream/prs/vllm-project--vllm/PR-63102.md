# [Perf][GLM-5.3-Flash] Specialized decode for GB300 TP4

[Upstream PR](https://github.com/vllm-project/vllm/pull/63102) · state: open · merged: False

## Original PR description

## Overview

Adds an opt-in specialized decode path for GLM-5.3-Flash on GB300 at TP4, built the same way as the Kimi K3 (#61867) and DSV4.1 (#61868) specialized decode: CuTe DSL kernels for every sublayer, fused all-reduce + mHC boundaries, and one policy table that picks an implementation per token count. Decode and uniform MTP verify steps of up to 64 tokens run it; everything else runs stock.

Enable with `--additional-config '{"decode_backend": "latency_specialized"}'`, the same switch as Kimi K3.

## Claims

- Median served ITL on 4x GB300 drops by 1.76x at concurrency 1 (5.15 -> 2.93 ms) and by 1.16x at concurrency 64 (13.92 -> 12.00 ms); with MTP 3 by 1.33x at concurrency 1 and 1.23x at 16.
- Accuracy stays within stock's range: GSM8K 0.918 (stock 0.914), 0.915 with MTP 3 (stock 0.912). Every kernel's error against an FP64 reference is no larger than the stock kernel's.
- Other deployments are not affected. The path refuses at startup with the list of unmet requirements (GB300 family, TP4 without PP/DP/EP/DCP, MRV2 with FULL decode graphs, FP8 KV cache), and steps it does not plan run the stock forward.

## Validation

GB300 x4, TP4, FP8 KV cache, `FLASHINFER_MLA_SPARSE`, MRV2, no prefix caching, `--numa-bind` for both builds. `vllm bench serve`, random 8k-token prompts, 512 output tokens with `ignore_eos`, one wave of C requests. Median ITL is the decode step as a client sees it.

|---|---|---|---|
| 1 | 5.15 ms | 2.93 ms | 1.76x |
| 8 | 7.23 ms | 5.53 ms | 1.31x |
| 32 | 11.11 ms | 9.04 ms | 1.23x |
| 64 | 13.92 ms | 12.00 ms | 1.16x |
| MTP 3, 1 | 6.64 ms | 4.98 ms | 1.33x |
| MTP 3, 8 | 11.61 ms | 9.28 ms | 1.25x |
| MTP 3, 16 | 14.72 ms | 12.00 ms | 1.23x |

With MTP each ITL is one verify step of 4 tokens per request. TPOT is not compared there, because on random prompts it follows the acceptance rate, which moves between runs.

The CUDA graph replay span of one decode step was measured with nsys and is the minimum over the TP ranks. Repeated runs vary by about ±0.25 ms at 32 requests.

|---|---|---|---|---|---|
| stock | 4.99 | 5.89 | 6.49 | 9.59 | 11.86 ms |
| this PR | 2.70 | 4.24 | 4.77 | 7.57 | 9.82 ms |

| GSM8K (1319, `vllm serve`) | stock | this PR |
|---|---|---|
| no MTP | 0.914 (c16) | 0.918 (c32), 0.921 (c2, c8) |

Serial greedy outputs differ from stock only at near-ties: every divergence is at a top-1/top-2 logprob margin of 0.125–0.25. Stock shows drift of the same size when only the batch composition changes.

Tests: `pytest tests/models/glm5next/`. Each kernel is compared against FP64 or naive PyTorch references and against the stock kernel's error:

- the fused boundary against all-gather + PyTorch mHC, eager and under CUDA graph replay, 1–64 tokens;
- the indexer and kpool kernels, which are bit-exact with the stock Triton kernels and the Hadamard quant;
- per-route and grouped MoE, including the shared expert, on TRTLLM-prepared weights;
- the GLM copy of `KdaSplit` at the new head count, with and without the folded gate;
- the split-K projections of the DSA layers and the MTP draft, on strided inputs;
- the DSA attention kernels, the dense MLP, the draft all-reduce + norm, and the logits gather.

The tests cover each kernel at the ends of its token range rather than every token count. They skip off SM100, and the 4-GPU ones also skip with fewer than 4 GPUs. No CI agent has GB300, so a new optional nightly step runs them on 4xB200, the same way as DeepSeek-V4.1's specialized decode tests; they have not been run on B200 yet. The tests and the evals above were run locally on GB300. The numbers above were measured on this change's previous base; on the rebased branch, pre-commit and the unit tests have been rerun. Moving the two generic pieces out keeps serial greedy outputs identical to the previous revision. With MTP, the draft prefill again computes every row, so draft tokens can flip at near-ties and later verify steps drift at near-ties; applying #64072 on top gives identical outputs again. The replay span is unchanged within noise except at 32 requests, where it is about 0.16 ms longer until #60070 lands.

## Details

**Structure.** `Glm5NextModelState` builds a `SpecializedDecode` after weight loading. At FULL graph capture, `plan()` accepts pure decode or uniform MTP verify steps of at most 64 tokens. A planned step walks the 45 layers itself and swaps in these stages, all in CuTe DSL:

- **`kda`:** a copy of Kimi K3's `KdaSplit` (`kda_split.py`) replaces four kernels per KDA layer. The copy adds schedule rows for GLM's 16 heads per rank and, at 32–64 tokens, folds the output gate GEMV into the kernel. K3's own kernel is not changed.
- **`gemm`, `dsa_gemm`, `kda_gate`:** a skinny GEMM at 1–4 tokens, then K3's split-K GEMM, which issues its weight TMA before the PDL wait. Each weight shape has its own tactics.
- **`dsa_attn`:** the q/kv a-norm becomes one kernel. Another kernel does the W_UK absorb, the FP8 query quant and the FP8 KV cache write.
- **`dsa_indexer`, `dsa_kpool`:** the indexer goes from 11 kernels to 1–2. The kpool path is bit-identical to stock.
- **`ar_mhc`:** every sublayer leaves its output TP-partial. One publish kernel and one cluster kernel then replace the all-reduce and the two mHC kernels at each of the 90 boundaries:
  - The publish kernel multicasts the partial into a Lamport mailbox.
  - The cluster kernel post-mixes the residual streams, runs the prenorm GEMV and RMS-normalizes.
  - The Sinkhorn mix only feeds the next boundary, so it runs on a side stream.
  - MoE layers stop before the finalize, and the boundary does the top-k reduction and the shared-expert add.

  At 64 tokens the boundary takes 15 µs against about 25 µs for stock.
- **`mega_moe`:** at 1–4 tokens, one 16-CTA cluster runs per routed expert, reading the TRTLLM-Gen FP8 weights in place. At 8–64 tokens, a persistent kernel walks packed units of (expert, up to 16 tokens), and routing, token quant and split-K GEMM1 all run inside it. The MoE layer at 64 tokens takes about 160 µs against 183 µs for TRTLLM-Gen.
- **`dense_mlp`:** two FP8 `mma.sync` kernels on the DeepGEMM-prepared weights.
- **LM head and MTP draft:**
  - a split-K head GEMM, and an NVLink all-gather of vocab shards in eager steps;
  - CuTe all-reduce + norm at the draft's boundaries;
  - a vocab-parallel greedy draft argmax that picks the same token as the stock argmax, ties included.

Which implementation runs at a given token count is set by one table in `policy.py`, using Kimi K3's `batch_table` specs. `additional_config["policy"]` can override entries for sweeps; an empty entry (for example `{"policy": {"boundary": ""}}`) runs that stage stock.

`specialized_decode/AGENTS.md` records the package's invariants (rank-uniform dispatch, TP-partial sublayer outputs, weight loads before the PDL wait, cluster limits) and how to validate a change to it.

**Outside `vllm/models/glm5next/`** the only change is the model config hook that turns on the vocab-parallel draft argmax for greedy MTP. Two generic pieces that earlier revisions of this PR carried are left to separate PRs, since they also help the stock path:

- FlashInfer sparse MLA: reuse a persistent multi-CTA KV counter buffer instead of allocating and zeroing one per call. #60070 already does this; this path picks it up once it lands.
- MRV2 MTP: skip draft decode metadata for indexer caches that draft steps do not read when the top-k is shared, and pass the last-token rows to the draft model so its prefill computes only those rows (#64072). Until it lands, `set_prefill_rows` in this PR is never called and the draft prefill computes every row, as stock does.

**Tradeoffs and limitations:**

- Kernels shared with Kimi K3 and DSV4.1 (CuTe DSL primitives, split-K GEMM, Lamport all-reduce primitives) are imported unchanged from those model directories for now; `KdaSplit` is copied because GLM needs a variant of it. Where they should live is left to the interface discussion in #60904 / #61311, and this PR will move to the common `--specialized-decode` interface if #61311 lands first.
- The change is large (about 11K lines, most of it kernels and their tests). It is opened as one draft so the whole path can be reviewed together. It can be split by stage if reviewers prefer.
- Not yet covered: AIME, GPQA, long-context evals, DFlash, and an in-situ comparison of the logits gather against `custom_all_gather`.

**Not a duplicate:** no other PR implements a GLM-5.3-Flash NVIDIA specialized decode. #61662 is the MI355X mono decode layer.
