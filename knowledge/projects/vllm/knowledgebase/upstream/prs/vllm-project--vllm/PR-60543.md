# [Bugfix][DSv4.1] Autotune the sparse indexer's wq_b GEMM

[Upstream PR](https://github.com/vllm-project/vllm/pull/60543) · state: open · merged: False

## Original PR description

## Overview

Make FlashInfer autotune cover the DeepSeek-V4.1 sparse indexer's `wq_b` GEMM. In the autotune dummy run the indexer took its short-context path, which returns before `wq_b`, so that MXFP8 GEMM was never tuned. The autotune pass now tunes `wq_b` directly; the indexer forward is unchanged.

## Claims

- With `enable_flashinfer_autotune`, the indexer `wq_b` GEMM (K=1280, N=4096 on DSV4.1-Flash) is now tuned for every token bucket.
- Serving no longer hits untuned `mxfp8_gemm` shapes for it, so it no longer falls back to `CuteDSLMxfp8GemmRunner` and JIT-compiles mid-step.

## Validation

DeepSeek-V4.1-Flash, MRV2, MegaMoE + MegaAttention, DSpark K=5, `FULL_AND_PIECEWISE` graphs to 8190, `--max-num-batched-tokens 16384`, `--kernel-config '{"enable_flashinfer_autotune":true,"moe_backend":"deep_gemm_mega_moe"}'`. Both runs tuned from an empty `VLLM_FLASHINFER_AUTOTUNE_CACHE_DIR` with the same 22 token buckets (1 to 16384), so the entry counts are comparable.

| | main | this PR |
|---|---:|---:|
| `mxfp8_gemm` entries in the saved autotune cache (per rank) | 110 | 132 |
| ... of which `(1280, 4096)` (indexer `wq_b`) | 0 | 22 |
| `No tuned config covers mxfp8_gemm` warnings in the server log | 35 | 0 |
| ... after the server was ready (during serving) | 3 | 0 |

- main: GB300, DEP2 (TP1 × DP2 + EP2), prefill-only AgentX replay at concurrency 256.
- this PR: GB200, DEP4 (DEP2 does not fit: 150.8 GiB of weights per GPU), `--max-num-seqs 256`, `vllm bench serve` with 256 random prompts (6.2K input tokens on average), all succeeded. Every rank saved the same counts.

The other GEMMs got the same entries in both runs (22 buckets each).

`wq_b` is tuned with a bf16 input, while the forward passes a pre-quantized `QuantizedActivation`. Both reach the same `mm_mxfp8` call with the same shapes, and the forward hit the tuned entries: there was no warning during CUDA graph capture (M from 6 to 8190) or serving.

To reproduce: start the server with FlashInfer autotune on and grep the log for `No tuned config covers mxfp8_gemm input_shapes=((..., 1280), (1280, 4096)`, or check the saved `autotune_configs_*.json` for `(1280, 4096)` entries.

`pre-commit` passes on the changed files. CI does not run this path: it needs SM100 and the DSV4.1 checkpoint. I did not add a unit test, because it needs an MXFP8 `wq_b` on SM100 with FlashInfer.

## Details

The autotune dummy run spreads `max_num_batched_tokens` over up to `max_num_seqs` requests, so each one has only tens of tokens. The indexer then takes its short-context path (`max_seq_len // compress_ratio <= index_topk`) and returns before `wq_b`. CUDA graph capture does run `wq_b` (it skips that path), but capture only reads the autotune cache.

On main, a step that hits an untuned M falls back to `CuteDSLMxfp8GemmRunner` and compiles a kernel for that shape inside `execute_model`. In one run, while another server on the same node was compiling, that step went past `VLLM_EXECUTE_MODEL_TIMEOUT_SECONDS` (300 s). The engine died with a `TimeoutError` in the shm broadcast dequeue, right after logging the `(16376, 1280) x (1280, 4096)` fallback.

`_run_flashinfer_autotune_dummy_runs` now calls `autotune_indexer_wq_b` inside the same `autotune(tuning_buckets=..., round_up=True)` context as the dummy run. It runs every indexer's `wq_b` at the max tuning M with a random bf16 input. FlashInfer keys each config on the op, runner, input shapes and runner extras (output dtype and PDL for `CuteDSLMxfp8GemmRunner`), and skips profiling on a cache hit. So indexers that share a key are tuned once, and any indexer with a different dtype, quantization or backend gets its own entries. On DSV4.1-Flash the 8 indexers share one key, and the autotune pass did not get slower.

Alternatives considered:

- Skip the short-context path in the indexer forward while FlashInfer is tuning (the first version of this PR). It works, but it makes the forward read FlashInfer's global tuner state on every step.
- Give the autotune dummy run a long context (`_dummy_run(context_len=...)`). This changes the autotune pass for every model, exists only in MRV2, and gives every dummy request about `max_model_len` of context, far more than the KV pool can hold.

No other open PR tunes this GEMM.
