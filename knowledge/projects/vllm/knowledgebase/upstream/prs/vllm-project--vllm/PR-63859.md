# [ROCm][DCP] Support decode context parallelism on ROCM_AITER_MLA_SPARSE

[Upstream PR](https://github.com/vllm-project/vllm/pull/63859) · state: open · merged: False

## Original PR description

## Summary

Enable decode context parallelism (DCP) for `ROCM_AITER_MLA_SPARSE`, the backend that GLM-5.x and DeepSeek-V3.2 (DSA sparse MLA) use on ROCm. At TP8 on 8x MI355X with an FP8 KV cache, DCP8 holds 27.9M KV tokens instead of 3.57M, so 26 requests of 1M tokens fit instead of 3. GSM8K is unchanged (0.9212 at both DCP8 and DCP1, stderr 0.0074).

## Background

Today `ROCMAiterMLASparseImpl` declares `supports_dcp = False`, so `--decode-context-parallel-size` fails at backend selection. Dense `ROCM_AITER_MLA` got DCP in #51705. The sparse path needs three more things that the dense path does not have.

1. The DSA indexer has to pick the global top-k while every rank holds only 1/N of the indexer keys. The CUDA path does this with a CuteDSL merge, which does not run on ROCm.
2. Each rank has to attend over only the selected tokens that it owns, and return the LSE of that partial attention.
3. The fused ROCm DSA path in `deepseek_v32/amd/rocm.py` calls `forward_mqa` directly and skips the query gather and the LSE combine of the generic MLA path.

## What this PR does

- **Indexer top-k merge.** `dcp_topk_torch.py` adds a merge with plain torch ops. Each rank packs its local top-k into int64 keys (score, then the lower global token id on a tie, which is the tie rule of the single-rank top-k), all-gathers them over the DCP group, and takes the top-k. A token in the global top-k is in the local top-k of its owning rank, so this is exact. The ROCm sparse indexer gathers only the keys this rank owns in prefill, uses the local lengths that the indexer metadata already builds under DCP, and runs the merge after its prefill and decode top-k.
- **Attention backend.** The index conversion keeps only the tokens this rank owns and maps them to local slots, then `compact_dcp_kv_indptr` shortens each row of the ragged index stream to them on the device. Under DCP the decode uses the nonpersistent AITER kernel with `return_lse=True`, on the query heads of the whole DCP group. Rows where the rank owns no selected token return `(0, -inf)`, so they drop out of the merge. Persistent metadata is not built under DCP. FP8 queries skip the 16-head kernel bucket and pad to 128 heads, because the 16-head FP8 split-KV kernel gave wrong outputs in my tests on gfx950.
- **Fused ROCm path.** Under DCP the fused path gathers the query heads with the DCP manager, calls `forward_mqa`, and merges the partial outputs with `dcp_manager.combine`. GLM-5.x no longer defaults to DCP query replication on ROCm, because this path does not use the replicated weights.
- **`mla_decode_fwd_lse`.** With one KV split, the AITER BF16 kernels with 64 and 128 heads write the output but not the LSE, so the returned LSE was uninitialized memory. The wrapper already forced two splits for FP8. It now does that for every dtype. It also builds the split offsets itself instead of using the tensor that `get_meta_param` returns from its `lru_cache`. That tensor can be freed and reused after a FULL CUDA graph captured its address (ROCm/aiter#5193), and with it GSM8K under DCP8 with CUDA graphs fell to 0.0015. The AITER side of the single-split LSE is fixed in ROCm/aiter#6971.
- **Guards.** DCP with attention sinks is rejected at backend selection, and DCP with speculative decoding is rejected at startup with a clear error. Both are follow-ups. DCP with indexer KV compression or candidate blocks raises in the ROCm indexer.

## Validation

`zai-org/GLM-5.3` (FP8 weights), TP8, 8x MI355X, `vllm/vllm-openai-rocm:nightly-00b6c4c565a8732c131e1f452d4a17803bb0842b` with this PR applied (AITER 0.1.26), `--max-num-batched-tokens 8192`, FULL_AND_PIECEWISE CUDA graphs unless noted.

GSM8K, `lm_eval --model local-completions`, 5-shot, full set (1,319), greedy:

| Config | KV cache | KV tokens | strict-match |
| --- | --- | --- | --- |
| DCP1 (baseline) | fp8 | 3,571,600 | 0.9212 ± 0.0074 |
| DCP8 | fp8 | 27,897,856 | 0.9212 ± 0.0074 |
| DCP8, eager | fp8 | 28,663,552 | 0.9212 ± 0.0074 |
| DCP8, prefix caching on | fp8 | | 0.9227 ± 0.0074 |
| DCP8 | bf16 | 14,089,600 | 0.9287 ± 0.0071 |
| DCP4, `--cp-kv-cache-interleave-size 16` | fp8 | 14,025,792 | 0.9234 ± 0.0073 |

Passkey retrieval (key at 10%, 50% and 90% depth): 9/9 at 3.5K, 34K and 114K tokens for every row above, and 6/6 at 571K and 1.03M tokens with DCP8, FP8 KV and `--max-model-len 1048576`. At that length vLLM reports a maximum concurrency of 26.03x for 1M-token requests.

Seven concurrent requests of about 1M tokens each with DCP8 and FP8 KV all ran to completion, and the steady decode of all seven was about 240 tok/s in total. I did not measure performance beyond that, and this PR does not claim a speedup. DCP adds collectives to every decode step, so it pays off when the KV cache, not the compute, limits concurrency.

Unit tests on MI355X: `tests/v1/attention/test_rocm_aiter_mla_sparse_dcp.py` (new: the top-k merge against a global top-k with ties and empty ranks, the index conversion and compaction against a reference for DCP 2 and 8 and interleave 1 and 16, `mla_decode_fwd_lse` against a reference for BF16 and FP8 at 1 to 1,024 tokens, and sharded decode merged by LSE against full attention), plus the existing ROCm sparse MLA, sink, indexer and backend selection tests: 303 passed, 26 skipped.

## Not a duplicate

There is no open PR or issue for DCP on `ROCM_AITER_MLA_SPARSE` (searched for `supports_dcp`, `ROCMAiterMLASparseImpl`, `mla_decode_fwd_lse` and "DCP sparse ROCm"). #57239 is DeepSeek-V4 only. #59916 (`--dcp-gather`) gathers the KV instead of sharding the attention, and is a draft tested on NVIDIA. #54541 is a backport for the NVIDIA FlashMLA sparse backend.

## Notes

- Not covered yet: DCP with speculative decoding (MTP or DSpark), DCP with attention sinks, DCP with PCP on this backend, and the Triton sparse decode fallbacks, which do not return an LSE and raise under DCP.
- The torch top-k merge is simple and not tuned. AITER has a fused FlyDSL DCP top-k merge (ROCm/aiter#5123) that could replace it in a follow-up.
- Related: #57239 adds DCP for DeepSeek-V4 on ROCm. That model has a different cache layout, so the two PRs touch different code.

AI assistance (Claude) was used to write this change. I reviewed every changed line and ran the tests and evaluations above.
