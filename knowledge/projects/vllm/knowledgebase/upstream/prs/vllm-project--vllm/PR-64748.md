# [Perf][LoRA][MoE] Remove the small-batch fused MoE-LoRA kernel

[Upstream PR](https://github.com/vllm-project/vllm/pull/64748) · state: open · merged: False

## Original PR description

Stacked on #64747; review only the last commit ("Remove the small-batch fused MoE-LoRA kernel"). Diff of that commit: 2 files, +0 / -367.

## Purpose

Remove `_fused_moe_lora_small_batch_kernel`, `_run_fused_moe_lora_small_batch` and `_pick_small_batch_chunk`.

Before this stack, the small-batch kernel handled naive block assignment with `max_lora_rank <= 64` and `num_tokens * top_k * max_lora_rank <= 1024`. With batches of up to 256 tokens now going to shrink/expand (#64746), it is reachable only above 256 tokens with `top_k * max_lora_rank <= 3`, i.e. in practice only with `max_lora_rank=1`. Those batches now take the one-shot kernel, like every other batch above 256 tokens.

I measured the range the small-batch kernel covered on main (naive assignment, rank 4/8, top_k 1-2, E 64-256, max_loras 4-16, 65-256 tokens, 90 cases per GPU). Time relative to the small-batch kernel, same harness as #64746 (CUDA graph over layers with distinct weights, bf16):

| GPU | shrink/expand (this stack), geomean | shrink/expand, worst | one-shot, geomean | one-shot, worst |
|---|---:|---:|---:|---:|
| GB200 | 0.51x | 0.84x | 0.73x | 1.59x |
| H200 | 0.58x | 0.95x | 0.86x | 1.62x |

So in the range it covered, shrink/expand with the #64746 configs is always faster than the small-batch kernel.
