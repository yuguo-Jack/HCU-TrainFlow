# [CI] Shard (H200 MIG 35GB / MI300) Entrypoints Integration (LLM) into whole coverage units

[Upstream PR](https://github.com/vllm-project/vllm/pull/58000) · state: closed · merged: False

## Original PR description

## What

Splits the `Entrypoints Integration (LLM)` CI job (H200 MIG 35GB lane, with its MI355 DPX mirror) into three named jobs whose commands are whole coverage units with no `--ignore`/`-k` selection filters. Each job runs a directory: `test_chat.py`, `test_gpu_utilization.py` and `test_prompt_validation.py` move into `core/`, `test_accuracy.py` into `accuracy/`, `test_generate.py` into `generate/`, and `test_struct_output_generate.py` into `structured_output/` as two wrapper files over a non-collected helper, so a new test file added to one of these folders runs without a YAML edit.

## Old

One job, 36–50 min wall on recent `main` builds, with the bulk of the suite hidden behind `--ignore` flags:

```yaml
- pytest -v -s entrypoints/llm --ignore=entrypoints/llm/test_generate.py --ignore=entrypoints/llm/test_collective_rpc.py --ignore=entrypoints/llm/offline_mode
- pytest -v -s entrypoints/llm/test_generate.py   # needs a clean process
- pytest -v -s entrypoints/llm/offline_mode       # needs to avoid interference
```

```
tests/entrypoints/llm/
  test_accuracy.py  test_chat.py  test_collective_rpc.py  test_generate.py
  test_gpu_utilization.py  test_prompt_validation.py  test_struct_output_generate.py
  offline_mode/
```

## New

```
tests/entrypoints/llm/
  core/
    test_chat.py  test_gpu_utilization.py  test_prompt_validation.py
  accuracy/
    test_accuracy.py
  structured_output/
    _structured_output.py                  # shared constants/params (never collected)
    test_structured_output.py              # core backend matrix (rename of the old file)
    test_structured_output_features.py     # reasoning matrices, auto mode, guidance, batched, structural tag
  generate/
    test_generate.py                       # moved, still its own pytest process
  test_collective_rpc.py                   # unchanged, distributed job
  offline_mode/                            # unchanged, own process
```

| Job | Key | Coverage | Replicas |
|---|---|---|---|
| Entrypoints Integration (LLM) | `entrypoints-integration-llm` (unchanged) | `entrypoints/llm/core/`, plus `generate/` and `offline_mode/` (own commands, process isolation preserved) | 1 |
| Entrypoints Integration (LLM Accuracy) | `entrypoints-integration-llm-accuracy` | `entrypoints/llm/accuracy/` | 1 |
| Entrypoints Integration (LLM Structured Output) `%N` | `entrypoints-integration-llm-structured-output` | `entrypoints/llm/structured_output/` hash-sharded | 2 |

Old file → wrappers: `test_struct_output_generate.py::test_structured_output` → `structured_output/test_structured_output.py`; the other five test functions (`..._with_reasoning_matrices`, `..._auto_mode`, `test_guidance_no_additional_properties`, `..._batched_with_non_structured_outputs_requests`, `..._with_structural_tag`) → `structured_output/test_structured_output_features.py`. No test body, parameter, or marker changed.

`test_collective_rpc.py` is unchanged and remains covered by the distributed job on both lanes. Each mirror (MI355 DPX since #57599) inherits its base job's commands; the structured-output mirror intentionally inherits `parallelism: 2`, sized from that lane's own per-file timings. All three jobs share the original `source_file_dependencies` through one YAML anchor, so an edit anywhere under `tests/entrypoints/llm` still triggers each of them. Other references now point at the new paths: the Intel and legacy `test-amd.yaml` copies of `test_generate.py`, the TPU v1 scripts (`accuracy/test_accuracy.py::test_lm_eval_accuracy_v1_engine`, and the structured-output folder with its existing `-k` selection unchanged), `CODEOWNERS`, and the mergify auto-label rule.

## Expected runtime and overhead

Estimates from per-file timings in two recent passed `main` builds (fast/slow pair); non-pytest overhead on this job measures ~2 min per worker (prebuilt image, checkout only):

| Job | pytest (est) | running wall (est) | non-pytest overhead (est) | main overhead cause |
|---|---|---|---|---|
| LLM (residual) | 10.5–13.7m | 12.5–16m | ~2m | checkout/setup |
| LLM Accuracy | 7.0–8.4m | 9–10.5m | ~2m | checkout/setup |
| LLM Structured Output, per shard | 8.4–12.8m | 10.5–15m | ~2m | checkout/setup |

- Before: 1 worker, 34–48 min pytest, 36–50 min wall.
- After: 4 workers, ~43–56 worker-min aggregate → **+6–9 extra worker-min** (budget: ≤20). Slowest replica pytest ~13.7m (budget: ≤20m). Shard count 2 against 20 collectible structured-output cases, no empty-shard risk; the mirror lane's per-file timings are similar, so the same split holds there.
- Measured in validation build [#91265](https://buildkite.com/vllm/ci/builds/91265) (see its comment). [#91391](https://buildkite.com/vllm/ci/builds/91391) on the current head, which includes the `generate/` move and the DPX mirrors, passed all 8 jobs.

## Notes

- Process-order behavior: `generate/` and `offline_mode/` keep their own pytest processes; the remaining shared-process files keep their previous relative order. The structured-output tests previously ran last in the shared process and contain no env monkeypatching, so hash-sharding them into fresh processes is safe.
- Not a duplicate: no open PR restructures this job (#42219 only narrows `source_file_dependencies` textually and is stale since May).
- Pre-existing issue spotted but left out of scope: in the legacy `.buildkite/test-amd.yaml` copy of this job, the first command's `--ignore` list is mangled (`--ignore=...test_collective_rpc.pyentrypoints/llm/offline_mode`), so that legacy-pipeline job currently runs the whole directory and then re-runs `test_generate.py`/`offline_mode`. Coverage there is unaffected by this PR; happy to fix in a follow-up.
- Local verification: `py_compile` on all new files, `yaml.safe_load` on edited YAML, full `pre-commit run` (ruff, mypy, mergify auto-label check, Buildkite key check) all pass. GPU test bodies were not run locally; a scoped validation build on this PR head will confirm collection counts and per-shard runtimes.
- This change was prepared with AI assistance (Kimi Code); the diff was reviewed line-by-line by the human submitter.
