# [Core][Metrics] Tag deferred waiting requests with the reason they were deferred

[Upstream PR](https://github.com/vllm-project/vllm/pull/62348) · state: open · merged: False

## Original PR description



## Overview

The scheduler defers a waiting request for six materially different reasons and reports all of them as one integer, so an operator watching a backlog cannot tell which constraint is holding it. This tags each deferral with its reason and reports the breakdown on `SchedulerStats`. Collection only; no Prometheus metric is added or changed. Related: #38435, which built the labeled waiting metric, and #61423, which defers the export contract for scheduler queue statistics to a separate design.

## Claims

- Every site that defers a waiting request now records why, instead of only that it happened.
- `SchedulerStats.num_deferred_reqs_by_reason` splits the existing `num_skipped_waiting_reqs` population across `blocked`, `stale_output`, `lora`, `kv_connector`, `kv_transfer` and `encoder_transfer`.
- The existing `Deferred: N reqs` console line carries the breakdown.
- No metric name, label, or value changes, so nothing downstream moves.

## Validation

Two tests pass, the new one and the pre-existing `test_scheduler_stats_waiting_queues` from #38435 that reads the same fields:

```
PASS test_scheduler_stats_waiting_queues
PASS test_scheduler_stats_deferred_by_reason
by_reason = {'blocked': 1, 'stale_output': 1, 'lora': 0, 'kv_connector': 0,
             'kv_transfer': 0, 'encoder_transfer': 0}
```

I could not run these under pytest on this host, and I want to be exact about why rather than imply a clean suite run. `tests/conftest.py` imports `fresh_cache` from `torch._inductor.utils`, which needs a recent torch; this host is glibc 2.26 and every torch wheel from 2.10.0 on is built for `manylinux_2_28`, so it cannot import. The newest torch that imports here is 2.6.0, which has no `fresh_cache`, so pytest dies at conftest collection before reaching any test. What I ran instead is both test functions imported directly from `tests/v1/core/test_scheduler.py` and called, under torch 2.6.0 with `CpuPlatform` forced, bypassing conftest. That exercises the real `create_scheduler`, the real `schedule()` scan and the real `make_stats()`; the output above is from that run. CI runs them normally.

The new test is discriminating rather than a presence check: one request is blocked before the scan reaches it and another is deferred inside the scan for stale output, and the assertion pins each to its own label, so tagging everything with a single reason fails it. Before this change the labels do not exist, so it cannot compile against main.

No performance measurement, and I am not claiming the overhead is zero. Reasons are module-level interned constants, so a deferral costs a dict insert where it previously cost a set insert, with no formatting during scheduling. `make_stats` gains one six-key dict per step, alongside the `num_kv_fetch_reqs_by_stage` copy already there, and only when `log_stats` is on. No new host-device synchronization and nothing on the model execution thread. If a reviewer wants this behind the same opt-in that #61424 is benchmarking, say so and I will move it.

Lint: `ruff-check`, `ruff-format`, `typos`, `mypy`, `check-spdx-header`, `check-root-lazy-imports` and `check-test-tethering` all pass on the four changed files. I could not run the full `pre-commit` here because the `clang-format` hook builds LLVM from source and this host's GCC is 7.3.1, below the 7.4 minimum. That hook does not apply to a Python-only diff.

## Details

`deferred_waiting` was a `set[Request]`, so `make_stats` could only take its length. Eight sites put requests into that set: seven `skip_request()` calls in the waiting scan and `_enqueue_waiting_request` for a request that arrives already blocked. The reasons behind them are not variations on one theme. A `lora` deferral clears when a LoRA slot frees, a `kv_transfer` deferral clears when an async load lands, and `blocked` clears when grammar compilation finishes. Collapsed into one integer they are indistinguishable, and `vllm:num_requests_waiting` is the single scalar most routers read.

The change makes `deferred_waiting` a `dict[Request, str]` and gives `skip_request` a `reason` argument, so the funnel that already existed now carries the reason through it. The two bulk removals that relied on `set.difference_update` move to a small `_drop_deferred` helper. The field shape follows `num_kv_fetch_reqs_by_stage`: a dense `dict[str, int]` beside the integer, summed across engines in `AggregatedLoggingStatLogger` the same way.

On scope, deliberately: #38435 shipped `vllm:num_requests_waiting_by_reason{reason="capacity"|"deferred"}` and named splitting `deferred` into `lora`, `kv_transfer` and `blocked` as what its schema was built for, so the export is already designed. I have not done it here, because #61423 puts scheduler queue statistics in follow-on work needing their own design for populations, observation boundaries and export contracts, and because #61424 stages collection ahead of exposure for the iteration counters. Adding label values to a live gauge is the part that needs that design, and tagging is useful on its own through the console line. @markmc, this is the piece your RFC defers, so if you would rather it wait for your design or land under a different field name, I will follow that.

Two compatibility notes. `deferred_waiting` is a private scheduler attribute; the existing tests that touch it use `len`, `in` and truthiness, all of which behave the same on a dict, and none needed changing. The Rust `SchedulerStats` in `rust/src/engine-core-client/src/protocol/stats.rs` does not set `deny_unknown_fields` and already omits `num_kv_fetch_reqs_by_stage`, so the new field needs no Rust-side change.

I checked for duplicate work before writing any of this. No open or merged PR tags deferral reasons per request: #38435 and #58947 are the merged predecessors this builds on, #61424 touches `schedule()` for per-iteration prefill/decode counts and does not go near the skip funnel, and #49628 touches the scheduler for a stall watchdog. #61423 defers this area but does not claim it, and there is no open issue or PR for the deferred design.
