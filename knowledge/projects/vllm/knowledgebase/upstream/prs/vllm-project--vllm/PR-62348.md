# [Core][Metrics] Export deferred waiting requests by the reason they were deferred

[Upstream PR](https://github.com/vllm-project/vllm/pull/62348) · state: open · merged: False

## Original PR description

## Overview

The scheduler defers a waiting request for seven different reasons. Prometheus reports all of them as one series, `vllm:num_requests_waiting_by_reason{reason="deferred"}`. An operator watching that series climb cannot tell which constraint is holding the queue. This PR tags each deferral with its reason and exports the breakdown as a new gauge, `vllm:num_requests_deferred_by_reason`. Related: #38435 built the `capacity`/`deferred` split and named this finer split as its intended next step.

## What changes

- Every site that defers a waiting request now records why. There are nine such sites.
- `SchedulerStats.num_deferred_reqs_by_reason` splits the `num_skipped_waiting_reqs` population into `blocked`, `stale_output`, `lora`, `kv_connector`, `kv_transfer`, `encoder_transfer` and `no_schedulable_tokens`.
- `vllm:num_requests_deferred_by_reason{reason=...}` exports one series per reason. Its series sum to `vllm:num_requests_waiting_by_reason{reason="deferred"}`.
- The existing gauge keeps its name and labels. Splitting its `deferred` label in place would break every query on `reason="deferred"`, so the breakdown is a separate gauge. That follows the pattern of `vllm:num_requests_kv_fetch_by_stage` from #58874.
- The `Deferred: N reqs` console line carries the breakdown too.

## Validation

Three tests pass:

```
PASS test_deferred_by_reason_gauge_records_breakdown
PASS test_scheduler_stats_waiting_queues
PASS test_scheduler_stats_deferred_by_reason
```

`test_scheduler_stats_deferred_by_reason` blocks one request before the scan reaches it. It defers a second inside the scan for stale output. The assertion pins each request to its own label, so a change that tagged everything with one reason would fail it. `test_deferred_by_reason_gauge_records_breakdown` records a `SchedulerStats` through `PrometheusStatLogger` and reads every series back from the registry. I checked that it fails when the gauge is set to zero instead of the recorded count. `vllm:num_requests_deferred_by_reason` is also added to `EXPECTED_METRICS_V1`.

These did not run under pytest on this host. `tests/conftest.py` imports `fresh_cache` from `torch._inductor.utils`. This host has glibc 2.26. Every torch wheel from 2.10.0 on needs `manylinux_2_28`. Torch 2.6.0 imports here but has no `fresh_cache`. So I imported the test functions from their modules and called them directly under torch 2.6.0 with the CPU platform forced. That runs the real `create_scheduler`, `schedule()`, `make_stats()` and `PrometheusStatLogger.record()`. CI runs them normally.

Lint: `ruff-check`, `ruff-format`, `typos`, `mypy`, `check-spdx-header`, `check-root-lazy-imports` and `check-test-tethering` pass on the changed files. The `clang-format` hook could not run because it builds LLVM and this host's GCC 7.3.1 is below the 7.4 minimum. The diff is Python only.

No performance measurement. A deferral now costs a dict insert where it cost a set insert. The reasons are interned module constants, so nothing is formatted during scheduling. `make_stats` builds one seven-key dict per step, only when `log_stats` is on.

## Details

`deferred_waiting` becomes a `dict[Request, str]`. `skip_request` takes a `reason` argument. The two bulk removals that used `set.difference_update` go through a small `_drop_deferred` helper. The stats field follows `num_kv_fetch_reqs_by_stage` and is summed across engines in `AggregatedLoggingStatLogger` the same way.

The Rust frontend decodes `SchedulerStats` by field name without `deny_unknown_fields`. The new field passes through it unread. Its `/metrics` will not show the new gauge until a Rust change mirrors it, as happened for the KV-fetch gauge. I can add that here or in a follow-up.
