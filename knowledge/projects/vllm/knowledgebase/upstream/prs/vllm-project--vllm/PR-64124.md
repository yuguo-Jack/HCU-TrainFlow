# [Quantization] Stop importing DeepSeek V4 model packages from generic quant code

[Upstream PR](https://github.com/vllm-project/vllm/pull/64124) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Generic quantization code imports the DeepSeek V4/V4.1 model packages to reach their `DeepseekV4FP8Config`. This removes those imports from the two hot paths, a small step toward the model isolation in #42770 (models own their code; the engine does not import concrete models).

## Claims

- `get_quantization_config(method)` no longer imports `vllm.models.deepseek_v41` (whole package, model code included) unless `method == "deepseek_v4_fp8"`. Before, any call did, e.g. `get_quantization_config("fp8")` loaded 130 extra modules, 59 of them under `vllm.models` (measured on GB10, image built from 237d2ffd08).
- `is_shared_expert_quant_fse_compatible()`, called for every MoE layer through `fused_moe/utils.py`, no longer imports both `vllm.models.deepseek_v4` and `vllm.models.deepseek_v41`: it recognizes the DeepSeek config by its method name, which both classes share.
- No behavior change: same classes are returned and the same FSE branches are taken.

## Validation

All on GB10 (sm_121), image built from this branch (`ab0e623`, merged with main at `892cb19816`); "main" = the same image with the two changed files and the FSE test reverted to `892cb19816`.

## Details

- `get_quantization_config()`: the DeepSeek entry is dropped from the eager `method_to_config` table and resolved after the table lookup, only when requested, from the `quant_config` submodule. Custom registrations still take precedence. `deepseek_v4_fp8` is the only declared method absent from the table, hence the assert.
- FSE check: `quant_config.get_name() == "deepseek_v4_fp8"` plus `expert_dtype == "fp4"` replaces the two `isinstance` checks. A DeepSeek config with fp8 experts still falls through to the `Fp8Config` branch, since it subclasses `Fp8Config`. The class is imported under `TYPE_CHECKING` only, to keep mypy on `_is_quark_mxfp4_ocp`.
- Limitation: the checkpoint-detection loop in `ModelConfig` (`config/model.py`) still asks every method's `override_quantization_method`, so the frontend process of a quantized checkpoint still imports the DeepSeek package. The gain is in the worker processes, which only resolve the selected method. Closing that gap needs `vllm.models.deepseek_v4{,1}/__init__.py` to export lazily (PEP 562) so that importing `quant_config` does not load the model; I left it out to avoid touching files under the in-progress DeepSeek V4 hardware separation, and can follow up.
