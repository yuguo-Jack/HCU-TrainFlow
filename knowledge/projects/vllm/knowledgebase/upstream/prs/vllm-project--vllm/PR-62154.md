# [Spec Decode] Fix adaptive verification startup on FA2 GPUs

[Upstream PR](https://github.com/vllm-project/vllm/pull/62154) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Fixes #62094. With `enable_adaptive_verification` and no `--attention-backend`, the selector picks FLASH_ATTN on GPUs where it runs FA2 (SM8x, SM12x), and the worker then rejects it after the weights load, because FA2's decode cudagraphs cannot replay variable per-request query lengths. Automatic selection now skips such backends for the target model's layers, as it already skips backends that plan from CPU query lengths. No other open PR addresses #62094 (searches under Details).

## Claims

- The issue's command starts and serves: the target model's attention layers run TRITON_ATTN, the EAGLE-3 drafter stays on FLASH_ATTN, and selection logs one INFO line, `Adaptive verification precluded higher-priority attention backend(s) FLASH_ATTN, FLASHINFER. Using TRITON_ATTN instead.`
- An explicit `--attention-backend FLASH_ATTN` on FA2 is rejected at backend selection, before the weights load, instead of after.
- Nothing changes with adaptive verification off, or where FLASH_ATTN runs FA3 or FA4 (FA3 builders declare `ALWAYS`, and FA4 builders do since #60908).

## Validation

The touched files are identical there and at the branch base. Against main with `--attention-backend TRITON_ATTN`, the configuration that works there today, measured earlier on a tree whose code equals this branch (only a comment differs), applied to the same main, two runs per latency cell, main against this PR: mean TPOT 4.041 against 4.005 ms at c=1 (16 prompts) and 5.83 against 5.90 ms at c=32 (80 prompts), with overlapping run ranges; mean acceptance length 2.00 against 2.01 at c=1; chat GSM8K (one run per arm, 250 questions, flexible match) 0.936 against 0.940.

Tests on SM120:

- `test_attention_selector.py` and `test_adaptive_verification.py`: 113 passed with this PR, 107 on main (22 skipped each).
- The six new selector cases alone, with this branch's test file on main's code: 5 failed, 1 passed. Four fail with `TypeError` because `AttentionSelectorConfig` has no `use_varlen_decode_cudagraphs` field on main, and the target-layer case selects FLASH_ATTN where it expects TRITON_ATTN. The one that passes checks that `eagle_head` drafters keep FLASH_ATTN, which main also does. All six pass with this PR.

CI runs these cases in the L4 Attention Kernels shards; they mock the SM120 backend order and FA2's declaration, so they do not need SM12x hardware.

## Details

- Root cause: FA2's metadata builder declares `UNIFORM_BATCH`, which the worker's `get_varlen_cudagraph_unsupported_backend` rejects for target layers, but the selector's only adaptive-verification check was `supports_device_cpu_query_lens_mismatch()`, which FA2 passes. A backend hook `supports_varlen_decode_cudagraphs()` (default True) is now checked in `validate_configuration()`.
- FlashAttention's hook reads the builder's declared `_cudagraph_support` instead of calling `get_cudagraph_support()`. That method takes the layer's KV cache spec, and `Attention.get_kv_cache_spec()` builds the spec from the backend being selected, so the selector has none to pass. `FlashAttentionMetadataBuilder.get_cudagraph_support()` returns the declaration unchanged, so the selector and the worker read the same value. Open #58591 adds a branch there that returns `ALWAYS` for FA4 with adaptive verification, which FA4 already declares since #60908, so the two would still agree.
- Scope: the requirement applies to target layers only, through `AttentionSelectorConfig.use_varlen_decode_cudagraphs`, set like `use_adaptive_verification` but off under the `eagle_head` tag, following the tag check from #47808's review: drafters built under that tag replay FULL graphs only for untrimmed batches of uniform length, so they can keep FA2. It is a field because selections are cached per config.
- Placement: @he-yufeng suggested in #62094 failing in `_validate_adaptive_verification`, or reusing the worker's `get_varlen_cudagraph_unsupported_backend`, rather than falling back. Neither has the backends at config time: they are resolved per layer during model construction, and the worker predicate walks attention groups and their KV cache specs, which exist only after that. So automatic selection skips FA2 and logs what it skipped at INFO, not WARNING: adaptive verification is opt-in and this fallback is how it runs on these GPUs, so there is nothing for the user to fix. An explicit FLASH_ATTN still fails, now at selection. The worker check stays as the per-layer backstop.
- Not a duplicate. Open PRs on 2026-10-17: `gh pr list -R vllm-project/vllm --state open --search "62094 in:body"` returns only this PR; `--search "adaptive verification FlashAttention"` adds #58591 (FA4 cudagraphs for adaptive verification, no FA2 selection change) and unrelated work; `--search "adaptive verification FA2"` adds only unrelated work.
- Limits:
  - Drafters built under other tags (for example `draft_model`, `dflash_head`, `extract_hidden_states`) keep the requirement, while the worker checks target layers only. For them the selector is stricter than the worker: with a target that does not use FLASH_ATTN (an MLA model, say) and a `draft_model` drafter on SM12x, the drafter moves from FA2 to TRITON_ATTN. I have not measured that case.
  - Other backends that declare `UNIFORM_BATCH` without a varlen bound (TRITON_MLA, FLASHMLA, ROCM_AITER_FA) still fail at the worker as on main; they can follow the same pattern if wanted.
  - Only SM120 was run. FA3 (SM90) keeps FLASH_ATTN through its `ALWAYS` declaration, which this PR does not change.
