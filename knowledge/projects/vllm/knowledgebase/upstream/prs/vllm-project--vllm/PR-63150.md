## Overview

Dory is a looped model: a shared block runs `n_recurrent_loops` times per token, and more loops trade latency for reasoning depth. Today the count is fixed per engine. This PR lets each request pick its count:

```python
SamplingParams(..., extra_args={"loops": 3})                                  # offline
client.chat.completions.create(..., extra_body={"vllm_xargs": {"loops": 3}})  # OpenAI server
```

with the engine started as `--hf-overrides '{"n_recurrent_loops": 2, "max_recurrent_loops": 3}'`. `n_recurrent_loops` stays the default.

## Claims

- A request with `loops=N` produces the same tokens and logprobs as an engine started with `n_recurrent_loops=N`, alone and inside a batch that mixes counts (batch-invariant mode).
- A step costs the largest count in its batch: a mixed {1,2,3} batch runs at the speed of a pure 3-loop batch.
- Without `max_recurrent_loops` nothing changes for other models, and Dory's speed is unchanged within 0.5%.
- Requests with different counts never share prefix-cache blocks. Out-of-range values return a 400 error.

## Details

**Model** (`dory.py`). There is one compiled unit for each largest count m = 1..`max_recurrent_loops`. Unit m runs m loops. Loop i's state update is a custom op, `vllm::dory_loop_state`, that keeps the state of tokens whose count is ≤ i. The op is opaque to torch.compile on purpose. With the select inlined, Inductor fused it into the neighbouring nGPT norm reductions, so a mixed batch rounded differently from a fixed-count engine and greedy outputs diverged after about 40 tokens. With the op, the code around it compiles identically in every unit, and every token is bit-identical to its fixed-count engine. Each unit has its own forward qualname, which the AOT compile cache is keyed on. All units are compiled during the profiling run, so they get the same Inductor size hints as a fixed-count engine.

**Per-request state** (`DoryModelState`, via the existing `get_model_state_cls` hook) reads `extra_args["loops"]` in `add_request`. In `prepare_inputs` it fills a persistent per-token count buffer and selects the unit for the batch's largest count.

**Core changes** (about 45 lines, opt-in):
- `ModelState.cudagraph_variants()` / `ModelState.cudagraph_variant`. FULL CUDA graphs are baked to one unit, so `ModelCudaGraphManager` captures them once per variant and replays the current batch's variant. The default is a single variant (`None`), which takes the unchanged path, and `model_runner.py` is not touched. Dory has `max_recurrent_loops` variants (3 here). The FULL-graph memory estimate in `profile_cudagraph_memory` is multiplied by the variant count. Batch-dependent depth with FULL graphs needs one graph per depth; a single max-depth graph would make `loops=1` cost as much as the max.
- `InputProcessor`: an optional `hf_config.request_cache_salt(extra_args, cache_salt)` hook. Prefix-cache hashes do not cover `extra_args`, and loop-k KV is only written up to the batch's largest count, so a block written at one count is not valid at another. The hook appends `dory-loops=N` to the request's salt for non-default counts and validates the value at admission (400). Relying on clients to set `cache_salt` themselves would silently corrupt outputs when they forget.

**Limitations**
- With `per_loop` KV, the per-loop caches are allocated for `max_recurrent_loops` for every request. KV capacity therefore scales with the max, not the default. `last_loop` KV mode is rejected together with per-request counts.
- Engine start compiles one unit per count and captures FULL graphs per count. Startup and CUDA graph memory grow linearly with `max_recurrent_loops`.
- Model Runner V2 only. On V1 the field is validated, but every request runs the default count.
- Tensor parallel size 1 only, as in #60149.
