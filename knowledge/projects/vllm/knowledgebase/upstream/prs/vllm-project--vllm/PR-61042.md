# [Frontend] Explain disabled scale-out endpoints with opt-in hints

[Upstream PR](https://github.com/vllm-project/vllm/pull/61042) · state: closed · merged: True

## Original PR description

## Purpose

After #54579 and #55176, existing callers of `/inference/v1/generate` receive an unexplained 404 unless the server is started with `--enable-scale-out`. This makes a deliberate configuration gate look like a missing or removed API.

Keep the existing opt-in default and dedicated render/tokens-only behavior. Disabled Python scale-out POST routes and Rust `/inference/v1/generate` instead return HTTP 403 with an OpenAI-style error explaining that the server must be restarted with `--enable-scale-out`. The handlers have no request-body parameters and never invoke rendering, generation, or multimodal deserialization. Configured API-key authentication remains in front of them; Python diagnostic routes stay out of OpenAPI. Unknown paths still return 404.

Keep startup diagnostics at INFO in both frontends: an unused optional feature being disabled is normal, not a warning condition. Callers that actually use a disabled endpoint receive the actionable HTTP error. This is not a rollback of the security gate and does not change pickle settings, model execution, or successful generation responses.

The Python diagnostic paths and HTTP methods are derived from the existing routers instead of maintaining a second endpoint list. Error construction reuses the existing `create_error_response` helper; no new global error framework or middleware is introduced.

## Duplicate check

Checked open PRs and issues for scale-out disabled-endpoint errors, `--enable-scale-out`, and 404/403 diagnostics. No existing PR implementing this diagnostic change was found. #56124 concerns Rust render-endpoint support, not this disabled-generation response. This is a follow-up to #54579/#55176, not a duplicate or replacement.

@aoshen02 The RL point is fair. Needing both `VLLM_SERVER_DEV_MODE` and `--enable-scale-out` to do RL is clunky and I get why a clear error looked like an easy win.

I agree with @chaunceyjiang, @DarkLight1337 and @franciscojavierarceo on the stubs though. When #54579 added the gate, the rule was that these routes aren't registered at all when the feature is off. #55176 kept that and only swapped the env var for a flag. It's the same pattern as `VLLM_SERVER_DEV_MODE` and we had a test for it (`test_scale_out_routes_are_disabled_by_default`). With the 403 handlers, the routes show up under "Available routes" right after the log line saying they're disabled and a probe can now tell the feature exists. The 403 is also a bit off because nothing is forbidden here. The feature just isn't turned on.

Could we revert the stubs and put the old test back? I'm happy to help with a docs change so anyone who hits the 404 can find `--enable-scale-out` quickly.

For the bigger RL question, I think RFC #56993 is the right place. We're raised there about components owning their endpoints and an RL or generation component that brings` /inference/v1/generate` and `/derender` with it would fix the two flag problem properly. It would also remove the need for adding back the extra endpoints on a plain `vllm serve`. Would be great to have your input there.
