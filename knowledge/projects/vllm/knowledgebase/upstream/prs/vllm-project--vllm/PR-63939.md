# [Bugfix][Multimodal] Reject audio chunk sizes smaller than one sample

[Upstream PR](https://github.com/vllm-project/vllm/pull/63939) · state: closed · merged: False

## Original PR description



## Overview

`split_audio` can loop without advancing when `int(sample_rate * max_clip_duration_s)` is zero or negative. Reject these chunk sizes before entering the splitting loop.

## Claims

- Raise `ValueError` for computed chunk sizes below one sample, including positive durations that truncate to zero.
- Preserve valid one-sample chunks and ordinary chunked transcription behavior.
- Add 12 utility regression cases, one real Whisper compatibility test, and document the input contract.

## Validation

Source baseline: `3d81a510f9ebc802a7864ced38832182295f4cad`.

Linux aarch64 / NVIDIA GB10, Python 3.12, PyTorch `2.14.0+cu130`. Runtime: official ARM64 main wheel `0.32.1rc1.dev532+g2f1cb151f`. Its original `audio.py` is byte-identical to the source baseline. Tested independent complete package copies, replacing only `audio.py` in the candidate; current changed tests and root pytest fixtures were used with normal imports and pytest configuration.

## Details

**Follow-up scope verification:** [Real HF, HTTP and complete offline reproduction results](https://github.com/vllm-project/vllm/pull/63939#issuecomment-6435565853). HF rejects invalid sampling rates, and no hang was reproduced through the stock Whisper transcription endpoint with a valid model configuration. The demonstrated failure is a caller-supplied zero/sub-sample duration in the documented public offline chunking helper, including after a successful explicit HF waveform precheck.

`chunk_size` is calculated before the loop. For a zero chunk size, `end_i == i`; the helper appends an empty slice and assigns the same position back to `i`. Checking the computed integer size also covers a positive duration shorter than one sample. The check runs before the empty-input early exit so malformed parameters behave consistently.

The validation does not change the split-point search, overlap defaults, sampling, model weights or valid chunk boundaries. Empty audio with a valid chunk size still returns an empty list.

Duplicate-work checks on 2026-10-27 searched open PRs for `split_audio`, `chunk_size audio`, and zero-sized audio chunks. No matching fix was found. [#52927](https://github.com/vllm-project/vllm/pull/52927) changes the final energy-search window; [#62995](https://github.com/vllm-project/vllm/pull/62995) changes the default search region. Neither validates the computed chunk size. The earlier NaN progress fix [#46463](https://github.com/vllm-project/vllm/pull/46463) also leaves this zero-size case.

@DarkLight1337 I checked the HF boundary and ran a real HTTP server as well as the documented offline chunking workflow. **I could not reproduce this through the stock Whisper `/v1/audio/transcriptions` endpoint with a valid model configuration. The reproducer is narrower: a caller-supplied invalid chunk duration in the public offline `split_audio` helper.**

HF does reject `sampling_rate=0` and `-16000`, as you suspected. With the valid 16 kHz waveform used here, the real HF `WhisperProcessor` accepts the audio and returns `[1, 80, 3000]` features. It does not see the separate `max_clip_duration_s` argument passed to `split_audio`. Even after an explicit HF precheck succeeds, `max_clip_duration_s=0` or `0.5 / 16000` still hangs in the original helper. In the documented offline workflow, splitting normally happens before `LLM.generate` invokes HF processing.

Observed results:

| Actual path | Result |
| --- | --- |
| Original helper, valid decoded audio + successful HF precheck, duration `0` or `3.125e-5` | Did not return; stopped by a 2-second alarm, exit 124 |
| Same inputs with this patch | Immediate `ValueError: sample_rate * max_clip_duration_s must yield at least one sample`, exit 2 |
| Fixed helper, duration `10` -> real Whisper `LLM.generate` | Two chunks `[160000, 95168]`; both produced nonempty transcription, exit 0 |

| Original HTTP server, WAV header with sample rate zero | HTTP 400 during decoding |
| Original HTTP server, valid 8 kHz input | HTTP 200 after resampling |

The server uses the model processor's 16 kHz / 30-second settings ([Whisper config](https://github.com/vllm-project/vllm/blob/3d81a510f9ebc802a7864ced38832182295f4cad/vllm/model_executor/models/whisper.py#L937-L945)), rather than a request-supplied chunk limit. [Decode/chunk preprocessing](https://github.com/vllm-project/vllm/blob/3d81a510f9ebc802a7864ced38832182295f4cad/vllm/entrypoints/speech_to_text/base/serving.py#L173-L204) also precedes the renderer/HF processing. I am therefore treating this as defensive validation of the public offline helper, not a demonstrated malformed-request bug in the default server. The existing Whisper regression checks valid-input compatibility; it is not an end-to-end invalid-request regression.

<summary>Full offline reproduction script (Linux): repro_offline_chunking.py</summary>

```python
import argparse
import json
import signal
import time
from transformers import AutoProcessor
from vllm import LLM, SamplingParams
from vllm.multimodal.audio import split_audio
from vllm.multimodal.media.audio import load_audio


def main():
    p = argparse.ArgumentParser()
    p.add_argument("--audio", default="mary.wav")
    p.add_argument("--model", default="openai/whisper-tiny")
    p.add_argument("--max-clip", type=float, required=True)
    p.add_argument("--split-timeout", type=float, default=2)
    a = p.parse_args()
    events = []

    def record(event, **kwargs):
        item = dict(event=event, **kwargs)
        events.append(item)
        print(json.dumps(item), flush=True)

    audio, sr = load_audio(a.audio, sr=16000)
    record("audio_decoded", sample_rate=sr, samples=len(audio))
    processor = AutoProcessor.from_pretrained(a.model)
    f = processor(audio=audio, sampling_rate=sr, return_tensors="np")
    record("real_hf_precheck_accepted", shape=list(f["input_features"].shape))
    record(
        "calling_split_audio",
        max_clip_duration_s=a.max_clip,
        computed_chunk_size=int(sr * a.max_clip),
    )

    def expired(signum, frame):
        raise TimeoutError("split_audio did not return before the bounded deadline")

    old = signal.signal(signal.SIGALRM, expired)
    started = time.monotonic()
    try:
        signal.setitimer(signal.ITIMER_REAL, a.split_timeout)
        chunks = split_audio(
            audio,
            sr,
            max_clip_duration_s=a.max_clip,
            overlap_duration_s=0,
            min_energy_window_size=1,
        )
    except Exception as e:
        record(
            "split_failed",
            type=type(e).__name__,
            message=str(e),
            seconds=round(time.monotonic() - started, 3),
        )
        raise SystemExit(124 if isinstance(e, TimeoutError) else 2)
    finally:
        signal.setitimer(signal.ITIMER_REAL, 0)
        signal.signal(signal.SIGALRM, old)
    record("split_returned", lengths=[len(x) for x in chunks])
    llm = LLM(
        model=a.model,
        dtype="half",
        max_model_len=448,
        max_num_seqs=2,
        max_num_batched_tokens=4096,
        enforce_eager=True,
        gpu_memory_utilization=0.03,
        kv_cache_memory_bytes=67108864,
        enable_prefix_caching=False,
        attention_config={"backend": "TRITON_ATTN"},
    )
    requests = [
        {
            "prompt": "<|startoftranscript|><|en|><|transcribe|><|notimestamps|>",
            "multi_modal_data": {"audio": (x, sr)},
        }
        for x in chunks
    ]
    outputs = llm.generate(requests, SamplingParams(temperature=0, max_tokens=64))
    texts = [o.outputs[0].text for o in outputs]
    assert len(texts) == len(chunks) and all(t.strip() for t in texts)
    record("llm_transcription_completed", texts=texts)


if __name__ == "__main__":
    main()
```
