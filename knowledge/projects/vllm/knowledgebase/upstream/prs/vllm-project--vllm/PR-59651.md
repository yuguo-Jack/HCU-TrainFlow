# [HiSparse] Suggestion for #59450: keep spec expansion out of core KV cache sizing

[Upstream PR](https://github.com/vllm-project/vllm/pull/59651) · state: closed · merged: True

## Original PR description

Suggestion PR into #59450 (`hisparse-admission-fit`). It shrinks the core diff against main without changing behavior.

## Changes

- **Expansion moves to the worker.** `resolve_hisparse_block_size` is renamed to `resolve_hisparse_specs`. It now also adds the derived resident/hot specs, and returns the specs instead of mutating them. `get_kv_cache_spec` calls it only when `hisparse_config is not None`. Workers report every cache they allocate, so `get_kv_cache_configs` needs no HiSparse step, and `expand_hisparse_kv_cache_specs` is inlined and removed.
- **`_max_memory_usage_bytes_from_groups` matches main again.** The `host_resident` filter moves to its one HiSparse call site, the "max seq len" check in `get_kv_cache_configs`.
- **Smaller HiSparse-local diffs.** In `get_hisparse_kv_cache_groups`, the `mla_specs` check is back where it is on main. In `create_hisparse_layout`, `min_host_blocks` is back to its one-line form. The `max_admission_blocks_per_request` docstring is one line.

The `host_resident` filter in `_pool_bytes_per_block` stays: the override conversion, the null-block reserve and the re-plan to the smallest rank all rely on it. The projection early return also stays.

Net diff vs main for #59450: 121 → 116 lines changed. `core/kv_cache_utils.py` goes from +18/−9 to +11/−10.

## Testing

- `tests/v1/core/test_kv_cache_utils.py`: same results as #59450's head. Locally, 8 tests fail on both because of the environment. One is `test_hisparse_pool_must_fit_max_model_len[32768-657-True]`; see the notes.
- Not run: `tests/v1/worker/test_attn_utils.py`. Its collection needs the flash-attn extensions, which the local env lacks. It needs CI.
- Not run: end-to-end HiSparse. Workers now report the derived specs to the engine core, so a TP=2 smoke run on this branch is still needed.

## Other review notes on #59450 (not addressed here)

1. **The new test depends on `async_scheduling`.** `test_hisparse_pool_must_fit_max_model_len[32768-657-True]` fails when `async_scheduling` resolves to True: `max_in_flight_tokens` becomes 4096, so a request needs 784 blocks instead of 656. Pin `async_scheduling = False`, or derive the expected values from `max_in_flight_tokens`.
2. **Auto-fit is off by one with `num_gpu_blocks_override`.** The HiSparse branch of `_estimate_max_model_len_from_groups` sizes against the full override and ignores the null block. Auto-fit then picks a length that needs exactly `override` blocks, which the "max seq len" check rejects. Probe at 32768 / 2048 batched tokens: an override of 656 or 657 makes auto-fit pick 24576 or 24640, and startup then fails.
