# [Step5] Allow MegaMoE with pipeline parallelism

[Upstream PR](https://github.com/vllm-project/vllm/pull/65504) · state: closed · merged: True

## Original PR description

## Overview

Step5 rejects `--moe-backend deep_gemm_mega_moe` with TP>1 and PP>1 at startup (`Step5 MegaMoE with TP requires sequence parallelism and PP=1`), because its model-level sequence parallelism (SP) is gated on PP=1. Step5 already handles the PP boundary under SP:
- it all-gathers its token shards before returning `IntermediateTensors` from a non-last stage;
- it re-shards them on entry to the next stage.

The default PP transport therefore sees full, TP-identical tensors, and the gate is unnecessary. This PR removes the PP=1 condition from the SP gate and the startup check.

## Claims

- Step5 with MegaMoE, TP>1 and PP>1 starts and matches PP=1 accuracy.
- At PP2×TP2 on B300, output throughput is +13.5% compared with the default MoE backend, which was the only option under PP before.
- PP=1 behavior is unchanged. No other model is affected.

## Validation

Hardware: 8× B300 (SM100) per node, NVLink, MRV2. GSM8K uses the full 1319 questions, 5-shot.

| Step5 config (EP on) | MoE backend | main | This PR |
|---|---|---|---|
| PP1×TP4 (reference, SP on) | MegaMoE | 0.934 | — (path unchanged) |
| PP2×TP2 | default | 0.936 | — |
| PP2×TP2 | MegaMoE | fails at startup | 0.934 |
| PP2×TP4 | MegaMoE | fails at startup | 0.926 |

Throughput, PP2×TP2. Two runs per arm, no other jobs on the node. Each cell lists the two runs' output tok/s, then their mean TPOT in ms:

| Workload (in/out, concurrency) | Default MoE | MegaMoE + SP | Throughput |
|---|---|---|---|
| decode 512/512, c64 | 934.1, 935.6 / 66.5, 66.4 | 1058.6, 1064.5 / 59.0, 58.2 | +13.6% |
| mixed 2048/256, c64 | 814.4, 809.0 / 72.2, 72.6 | 920.5, 921.6 / 63.0, 62.9 | +13.5% |
| prefill 8192/16, c8 | 43.1, 42.9 / 85.9, 85.4 | 43.1, 42.2 / 95.3, 95.3 | −1% |

At PP2×TP4 (EP4) the trade-off differs: prefill throughput is +19% (TTFT −26%) and decode is −15%. The backend choice stays with the user.

## Details

With TP>1 the PP transport sends 1/t of each `IntermediateTensors` entry from every TP rank and all-gathers it on the receiver. This is correct only when the tensor covers all tokens and is identical on every TP rank. `Step5Model.forward` meets that:
- it calls `sp_all_gather(hidden_states)[: positions.shape[0]]` before the non-last-rank return;
- it calls `sp_shard` on the received `hidden_states` on entry.

That code was already on main but never ran with PP, because SP was off whenever PP>1.

The gather at the boundary adds two TP all-gathers per stage boundary per step. On NVLink this cost is not measurable: an interleaved A/B against a prototype that sends the shards rank-to-rank instead showed no throughput difference beyond run-to-run spread at PP2×TP2 and PP2×TP4.

**CI.** This path needs MegaMoE, which runs only on SM100. The SM100 CI steps use at most 4×B200, which cannot hold the ~650 GB Step5 checkpoint plus KV cache; the 8-GPU H200 steps can hold it but cannot run MegaMoE. Validation was done outside CI as listed above.
