# [Perf] Bound block-hash slicing to the current prefill chunk

[Upstream PR](https://github.com/vllm-project/vllm/pull/55749) · state: closed · merged: False

## Original PR description

## Purpose

`BlockPool.cache_full_blocks` slices all remaining request hashes on every prefill chunk, although its loop only consumes the hashes for the newly full blocks. Long prompts therefore repeatedly copy hashes for future chunks. When the group block size differs from the hash block size, the slice also repeatedly materializes the `BlockHashListWithBlockSize` view in Python.

Bound the slice by `num_full_blocks`, matching the existing block slice. This reduces cumulative hash materialization from quadratic to linear in prompt blocks for a fixed chunk size. Hash computation, cache insertion, and event semantics are unchanged.

The regression test counts hash elements read while registering two consecutive chunks and verifies the stored hashes. It covers equal/different block sizes and KV events enabled/disabled without timing assertions.

- zupengwang · comment · 2026-09-08T08:13:19Z · [source](https://github.com/vllm-project/vllm/pull/55749#issuecomment-5581606232)

@ivanium Thanks for the feedback. I followed up with CPU profiling and actual HTTP serving measurements to check whether the reduced work translates into an end-to-end benefit.

The motivation is that `cache_full_blocks` only consumes hashes through `num_full_blocks`, but the original `block_hashes[num_cached_blocks:]` slice also materializes hashes for future prefill chunks. Bounding the slice avoids repeatedly constructing those unused list entries. It does not avoid recomputing hash digests or change cache semantics.

In a separate CPU profile of one 128K-token request, cumulative `cache_full_blocks` CPU time decreased from **2.148 to 1.410 ms** with default matching, and from **7.459 to 2.403 ms** with 16-token matching. These are function-level CPU measurements, not serving speedups.

For the end-to-end test, I used an RTX 3090 / Xeon Gold 6226R and Qwen3.5-0.8B BF16, with the normal multiprocessing engine, compilation and CUDA graphs, a 2,048-token scheduling budget, and max sequences 8. Default matching and explicit 16-token matching each had four independently started servers in **original / patched / patched / original** order. The tested commits were `7cc89a7ddabd6be3ff64535139bea20548062ca6` and `f43ca2ac8beec871a441a2399ffa99db601a219e`.

Startup/warmup were excluded. The upstream streaming HTTP benchmark client sent fixed pre-tokenized code prompts with 32 output tokens and cold prefix caches. C8/C2 below are client concurrency limits. Throughput values are means of two runs per implementation; the last column shows the two order-balanced pair comparisons.

| Matching | Workload | Original → patched req/s | AB / BA throughput change |
|---|---|---:|---:|
| Default | 32K, C8 | 0.68954 → 0.68576 | -1.096% / +0.006% |
| Default | 128K, C2 | 0.07958 → 0.07944 | -0.470% / +0.114% |
| 16-token | 32K, C8 | 0.68403 → 0.68478 | +0.097% / +0.121% |
| 16-token | 128K, C2 | 0.07958 → 0.07968 | +0.050% / +0.205% |

I also tested 32K prompts with seeded Poisson arrivals at 0.5 req/s. The mean of per-run TTFT p95 changed from **4,777 to 4,779 ms** with default matching and **4,792 to 4,815 ms** with 16-token matching. Thus, the small throughput increases with 16-token matching did not come with a consistent latency improvement across workloads.

All **512 measured requests and 40 warmup requests** completed with the expected token counts, zero failures, zero preemptions, and zero prefix-cache hit tokens. Some text outputs varied, including in repeated runs of the unchanged original version; all samples were retained, and this online test is not a bitwise-correctness claim. The environment reused existing vLLM 0.28 native extensions rather than rebuilding all native components at the PR SHA. There were only two independent server lifetimes per implementation/configuration, so individual requests should not be treated as independent performance trials.

The measurements support reduced CPU metadata work, especially with finer-grained matching, but **do not establish a stable, practically meaningful end-to-end gain on this setup**. If a demonstrated serving improvement is needed to justify this change, the current evidence does not meet that bar.
