# [Feature][Attention] Partition mixed batches and gate cudagraphs in Triton DiffKV

[Upstream PR](https://github.com/vllm-project/vllm/pull/59052) · state: open · merged: False

## Original PR description

## Purpose

This PR upstreams work from the patch set of the MiMo recipe we deploy — Diffbot's MiMo-V2.6-Flash-RL FP8KV/W4A8 recipe (Hugging Face: diffbot/MiMo-V2.6-Flash-RL-FP8KV-W4A8-2x-RTX-PRO-6000, built by Mike Tung), itself porting parts from the local-inference-lab/vllm fork: the idea and the original implementation belong to the recipe's authors, not to us. Their version of this change is tracked in local-inference-lab/vllm#848; we re-derived the diff against upstream main, wrote or extended the tests, and ran the checks.

### Motivation

The Triton DiffKV backend handles mixed batches poorly in two ways:

1. **Cudagraphs.** The DiffKV metadata builder inherited `AttentionCGSupport.ALWAYS` from `TritonAttentionMetadataBuilder`, so cudagraphs were captured and replayed for mixed batches too — a graph may only replay for batches whose call structure matches the one it was traced on. This PR pins the builder to `AttentionCGSupport.UNIFORM_BATCH` and initializes the decode reorder threshold the runner needs before it orders decodes first.

2. **Split-KV is lost on mixed batches.** A mixed batch runs as a single 2D call today, so its decode rows never take the split-KV path. The builder now produces a `TritonAttentionDiffKVMetadata` carrying `partitions`: when the actual token count exceeds the softmax-segment buffer capacity, the batch splits into a decode partition and a prefill partition, each with its own `query_start_loc` / `seq_lens` / `block_table` / `slot_mapping` slices, and the impl runs `unified_attention_diffkv` once per partition over its own token range of `q` and `out`. The split only engages when it can pay: a shared predicate (`can_use_split_kv`, the launcher's own gate exported as one function) keeps the batch unpartitioned whenever the decode side's max query length exceeds 1 or `VLLM_BATCH_INVARIANT` disables the 3D path, and `build()` bails out unless the batch has a decode side that fits the scratch buffers and a prefill side to split off.

## Test Result

Results, stated exactly, re-run against the PR head:

- ruff format/check clean on all three touched files (run directly with ruff 0.16.10; `pre-commit run` with the repo-pinned ruff 0.14.0 cannot execute in this NixOS environment, its hook environments fail with the `stub-ld` dynamic-linker error);
- **unit coverage** in `tests/v1/attention/test_triton_diffkv_metadata_partitioning.py` (**10 passed**) for: the DiffKV builder's V-shaped softmax scratch vs the parent builder, `build()`'s partition threshold and buffer wiring, the cudagraph capture-size threshold snap, the forward KV-split and partition-buffer handoff (kernel stubbed), the forward guards (no-metadata zeros, `output_scale` `NotImplementedError`), and the launcher's 3D/2D partition dispatch including the per-segment reduce launch (both Triton kernels stubbed, so no kernel executes in these tests);
- the two existing test files this PR edits, `test_triton_attn_metadata_builder.py` and `test_triton_attn_segments.py`, pass in full (**44 passed**); their `parallel_config` fixture change is required because the new `_init_reorder_batch_threshold` reads `decode_context_parallel_size`;
- the kernel-facing suites: **189 passed, 118 skipped, 0 failed**, identical to the same two files run on this PR's upstream base `2365177d`; the 118 skips are the 96-case DiffKV kernel suite (`FA DiffKV needs FA3/FA4`, not installed here) plus 22 skips in `test_attention_selector.py`. Executing the kernels in this NixOS environment needed two workarounds: a `/sbin/ldconfig` shim for Triton's `libcuda_dirs()` and `TRITON_PTXAS` / `TRITON_PTXAS_BLACKWELL` pointed at a system `ptxas`, since the vendored one does not run here;
- `tests/v1/attention` was attempted again and still cannot be completed here: 5996 tests collect, a 15-minute run reaches only ~18% and fails in unrelated suites before reaching this PR's test files, so nothing is claimed for that suite;
- **no model eval was run.** The partition moves oversized mixed-batch decode rows onto the 3D split-KV kernel — a different reduction order — and AGENTS.md asks for eval numbers on output-affecting changes; running one needs a model and free GPUs that were unavailable here. Stated plainly rather than argued away.
