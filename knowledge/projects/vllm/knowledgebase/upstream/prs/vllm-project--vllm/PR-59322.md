# [Perf][KV Offload] Avoid repeated hash-prefix scans

[Upstream PR](https://github.com/vllm-project/vllm/pull/59322) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Avoid repeated scans of previously processed request hashes when `OffloadingConnector` updates offload keys. Preserve key order, chunk boundaries, and recorded token positions.

## Claims

- Each update reads only the newly selected hashes, instead of traversing the existing prefix again for each cache group.
- Updates with no complete new chunk avoid scanning old hashes.
- The regression test checks incremental updates, incomplete chunks, repeated calls, multiple chunk sizes, key order, and token positions.

## Validation

These are CPU tests with mocked scheduler inputs. `--noconftest` excludes unrelated GPU fixtures. Buildkite already includes this test file in the V1 KV Connectors suite.

The regression uses a hash list that rejects iteration but permits indexed access. Restoring the method from main (`8fb16ea5a66f0ef362e728f0ff025f2845927fd5`) in memory makes the test fail. The rebased method passes. This establishes the traversal change without a timing threshold.

End-to-end serving and model evaluation remain pending for this rebased commit. No model, GPU, workload, or serving speedup is claimed. Human review of every changed line and the required serving validation remain pending.

## Details

Without this change, `RequestOffloadState.update_offload_keys()` uses `islice` to skip hashes that already have offload keys. Skipping still consumes the iterator from the beginning. Every call therefore traverses the hash list again, even when the request has no new complete chunk.

This method runs during offload lookup, scheduler updates, and request completion. The repeated CPU work grows with the request hash count and affected requests. It adds work to the scheduler path. The effect on serving latency and throughput is not measured here.

`Request.block_hashes` is a list. Indexed slicing starts at the next unprocessed chunk boundary and selects each chunk's final hash. Key construction and position updates remain unchanged. The temporary list contains only newly selected hashes, at the cost of one short-lived list per group per update.

Open-PR searches for `update_offload_keys` and `offload hash` found no duplicate of this traversal fix. Related #54743 changes which cache groups support offloading. It does not remove this repeated hash-prefix traversal.

We hit the same `islice` prefix walk in production and can add evidence for this PR.

**Profile (8 × A100, Qwen3.8-Flash-Next, native CPU offload 256 GiB, MLPerf agentic set).** py-spy of the EngineCore process: `update_offload_keys` was in 804 of ~17,800 leaf samples at concurrency 32 (~4.5 %) and in 667 of ~22,200 at concurrency 20 (~3 %).

**CPU microbenchmark** (Apple M3 Max, Python 3.12.13, one KV group, steady state, mean of 20,000 calls, median of 5 repeats). It copies the loop body before and after the change. One step = 32 running requests × 1 call:

| History (tokens) | Block hashes | New chunks per call | `islice` (µs/call) | Indexed (µs/call) | `islice` (µs/step, 32 req) | Indexed (µs/step) |
|---:|---:|---:|---:|---:|---:|---:|
| 8,192 | 512 | 0 / 1 | 1.1–1.5 | 0.12–0.31 | 35–49 | 4–10 |
| 32,768 | 2,048 | 0 / 1 | 4.0–4.5 | 0.11–0.31 | 128–142 | 4–10 |
| 77,824 | 4,864 | 0 / 1 | 9.3–9.8 | 0.11–0.31 | 297–312 | 4–10 |
| 200,704 | 12,544 | 0 / 1 | 23.7–24.3 | 0.11–0.32 | 759–778 | 4–10 |

Ranges cover `hashes_per_chunk` 1, 30 and 120; the `islice` cost does not depend on it. The cost is per KV group, so a hybrid model with several groups pays it several times per request per step.

**Serving A/B (honest result):** with the same change backported, a 1 × 60 min run at concurrency 32 on the same node gave a strict SLO pass of 63.36 % vs 64.30 % without it, and 1.743 vs 1.746 qualified req/s. That is no measurable end-to-end change, within run-to-run noise. In our setup the GPU step (~35–110 ms) dominates, and this host work overlaps it on the EngineCore. The fix removes O(history) work per call, so it should matter more with longer histories, more KV groups or a busier scheduler. It does no harm, and the keys are identical (randomized check against the `islice` version over appends, no-op calls and truncation).

The benchmark script is about 80 lines; happy to share it. Prepared with Claude Code; I reviewed the results.
