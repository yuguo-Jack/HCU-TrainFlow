# [Perf][HiSparse] Preserve THP alignment in shared host pools

[Upstream PR](https://github.com/vllm-project/vllm/pull/63970) · state: open · merged: False

## Original PR description

## Overview

Keep segmented shared host pools aligned for a THP-enabled `/dev/shm`, and document the deployment mount settings. This replaces the original broad implementation with one small allocator change and 22 lines of documentation.

Related: #61859, #58852, #63289. This PR no longer stacks on #58852 or adds `host_pool_dir`, hugetlbfs handling, a private file allocator, THP advice helpers, or new configuration.

## Claims

- Use the existing shared-pool path with `/dev/shm` mounted `huge=always,mpol=interleave`; the mount requests THP without application `MADV_HUGEPAGE` calls.
- Reserve the segmented mapping through an unlinked file on the backing tmpfs. A `memfd` uses the internal shmem policy instead and can choose a non-PMD-aligned address. On the test host, the small change restores PMD coverage from 0% to 100% in a four-segment probe.
- Final diff: two files, 27 insertions and 6 deletions; production code alone is 5 insertions and 6 deletions.

## Validation

Four H100 80GB GPUs; GLM-5.3 native dimensions with eight layers and dummy weights; TP4, MRV2 eager, NIXL + HiSparse, 1 TiB shared pool. All arms used NUMA interleave and a 300s worker grace to measure graceful shutdown through all workers exiting. A 128 GiB warmup was excluded.

The controlled comparison uses PR base `a20280f30e` and original PR `f0f265e3bf`:

| Configuration | LLM startup | Graceful shutdown | Pool PMD coverage |
| --- | ---: | ---: | ---: |
| Unchanged base, ordinary pages (1 run) | 398.0s | 139.5s | 0% |
| Unchanged base, THP `/dev/shm` (2 runs) | 109.9–116.8s | 44.2–53.5s | 99.9998% |
| Original PR, dedicated THP tmpfs (1 run) | 112.3s | 41.1s | 99.9998% |
| Current allocator + minimal fix, THP `/dev/shm` (1 run)* | 109.1s | 43.9s | 99.9998% |

*The last row keeps the same base engine and matching binary wheel, taking only `hisparse/runtime.py` and `shared_offload_region.py` from current-main `ffdf26702a` plus the reservation fix. It exercises the retained production change through the real `LLM()` entry point at 1 TiB. Its timing also includes upstream segmentation improvements, so it is not a before/after measurement of the reservation fix alone. The other rows isolate the removed PR changes from mount policy.

All runs exercised host-tier reads and matched greedy token IDs, with no remaining workers. The dummy model's existing 0.001 log-probability guard remains unsatisfied (about 0.00196 maximum common-candidate difference); this is not claimed as resolved or a full-weight accuracy evaluation. The earlier investigation also observed this guard fail between ordinary-page runs.

Additional checks:

- Current-main allocator from `ffdf26702a`, four-segment 4 GiB real-mapping probe on the same THP mount: PMD coverage assertion fails before the reservation change (0%) and passes after it (100%); mapping and file cleanup pass.
- Existing `tests/v1/kv_offload/cpu/test_shared_offload_region.py`: 69 passed on Linux with the current allocator and reservation fix. Tests were run against the controlled base's dependencies and matching binary wheel.
- Pre-commit and `git diff --check`: passed.

## Details

```bash
# Configure inside the deployment's mount namespace before starting vLLM.
mount -o remount,size=1100G,huge=always,mpol=interleave /dev/shm
```

The mount applies to all `/dev/shm` allocations. THP remains best effort; private per-rank pools do not use this mount, and reserved hugetlb pages are a separate feature. The default five-second worker grace can still be too short. This does not remove per-rank CUDA registration or close #61859's shutdown issue.

The old base already maps one file on `/dev/shm`, so it needs no allocator changes to benefit. Current main uses segmented files and a `memfd` address reservation; the retained small change lets that reservation follow the backing mount's THP policy. It preserves the mapping flags, segment layout, sparse reservation, and cleanup, with no persistent temporary file.

This is a reduction of the existing PR, not another competing implementation of #58852 or #63289. AI assistance (Codex) was used for the reduction and validation.
