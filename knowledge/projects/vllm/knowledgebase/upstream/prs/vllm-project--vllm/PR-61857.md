# [Bugfix][Parser] Honor a prompt-closed reasoning block in non-streaming parse and reasoning token counts

[Upstream PR](https://github.com/vllm-project/vllm/pull/61857) · state: closed · merged: True

## Original PR description

## Overview

With GLM-5.3 and `continue_final_message`, non-streaming Chat Completions return the continued answer as `reasoning` with `content: null`, and both streaming and non-streaming count every generated token as a reasoning token. This PR makes non-streaming parsing and `count_reasoning_tokens()` honor a prompt that already closes reasoning, as streaming `parse_delta()` already does.

## Design

Thanks to @bbrowning for catching that an earlier version leaked multi-turn reasoning into `content` for legacy parsers like `deepseek_r1`, and for suggesting moving the fix onto `ParserEngine`. This version follows his outline:

- `ParserEngine.set_prompt_token_ids()` uses the engine's turn-aware `is_reasoning_end` to start the parse in `CONTENT` when the prompt already closes reasoning. The engine's reasoning token count uses the same starting state.
- `ReasoningParser` gets a no-op `set_prompt_token_ids()`, so legacy reasoning parsers behave exactly as on `main`. `ParserEngineReasoningAdapter` and `DelegatingParser` pass the prompt through.
- The engine only uses the prompt when its config starts in `REASONING` and declares `turn_boundary_tokens`; without turn boundaries, a previous turn's `</think>` would count as closing reasoning in the new turn.

## Claims

- Non-streaming returns the continuation as `content` instead of `reasoning` when the prompt already closes reasoning.
- `reasoning_tokens` is 0 in that case, on both streaming and non-streaming. Before, it was the whole output (17 tokens in the example below).
- Normal reasoning turns are unchanged, and a previous turn's `</think>` doesn't count as closing reasoning in the new turn.

## Validation

**Dummy Reproduction** (CPU only) parser level:

```python
from vllm.entrypoints.openai.chat_completion.protocol import ChatCompletionRequest
from vllm.parser.parser_manager import ParserManager
from vllm.tokenizers import get_tokenizer

tok = get_tokenizer("zai-org/GLM-5.3")
msgs = [{"role": "user", "content": "Count from 1 to 10 separated by commas."},
        {"role": "assistant", "content": "1, 2, 3, 4,"}]
prompt = tok.apply_chat_template(msgs, tokenize=False, add_generation_prompt=False,
                                 continue_final_message=True)
prompt_ids = tok.encode(prompt, add_special_tokens=False)
out = " 5, 6, 7, 8, 9, 10"
out_ids = tok.encode(out, add_special_tokens=False)
req = ChatCompletionRequest(model="m", messages=msgs, add_generation_prompt=False,
                            continue_final_message=True)
parser_cls = ParserManager.get_parser(tool_parser_name="glm47", reasoning_parser_name="glm45",
                                      enable_auto_tools=True, tokenizer=tok)
print("prompt tail :", repr(prompt[-44:]))
print("model output:", repr(out))

# non-streaming, as chat_completion/serving.py does it
p = parser_cls(tok, None, chat_template_kwargs={}, model_config=None)
p.set_prompt_token_ids(prompt_ids)
reasoning, content, _ = p.parse(out, req, enable_auto_tools=True, model_output_token_ids=out_ids)
print(f"non-stream  reasoning={reasoning!r}  content={content!r}  "
      f"reasoning_tokens={p.count_reasoning_tokens(out_ids)}")

# streaming, one token at a time
p = parser_cls(tok, None, chat_template_kwargs={}, model_config=None)
r = c = ""
for i, t in enumerate(out_ids):
    d = p.parse_delta(tok.decode([t]), [t], req, prompt_token_ids=prompt_ids,
                      finished=i == len(out_ids) - 1)
    if d:
        r += d.reasoning or ""
        c += d.content or ""
print(f"stream      reasoning={(r or None)!r}  content={(c or None)!r}  "
      f"reasoning_tokens={p.count_reasoning_tokens(out_ids)}")
```

**Before** (`main` at `3dcfaeb4e8`, this branch's base):

```
prompt tail : 'mmas.<|assistant|><think></think>1, 2, 3, 4,'
model output: ' 5, 6, 7, 8, 9, 10'
non-stream  reasoning=' 5, 6, 7, 8, 9, 10'  content=None  reasoning_tokens=17
stream      reasoning=None  content=' 5, 6, 7, 8, 9, 10'  reasoning_tokens=17
```

**After** (this PR):

```
prompt tail : 'mmas.<|assistant|><think></think>1, 2, 3, 4,'
model output: ' 5, 6, 7, 8, 9, 10'
non-stream  reasoning=None  content=' 5, 6, 7, 8, 9, 10'  reasoning_tokens=0
stream      reasoning=None  content=' 5, 6, 7, 8, 9, 10'  reasoning_tokens=0
```

The "before" output matches what we saw in production on GLM-5.3: the API returned the continuation in `reasoning_content` with `content: null` and `reasoning_tokens: 17`.

- bbrowning · comment · 2026-10-16T13:08:51Z · [source](https://github.com/vllm-project/vllm/pull/61857#issuecomment-6216195757)

After a round of code review iterations with my coding assistant, it looks like this may cause some unintended consequences for older reasoning parsers that use `BastThinkingReasoningParser` because now we'll be feeding the entire prompt to their `is_reasoning_end` when we did not before and a lot of those have no multi-turn boundary awareness meaning we'll end up marking reasoning as ended prematurely. It was able to verify with the deepseek_r1 parser this change can cause multi-turn reasoning to leak out into the content field.

From an altitude point-of-view, I wonder if this should live somewhere on ParserEngine so that we get this right for all the engine based parsers but don't run into unintended consequences with the older reasoning parsers.

- bbrowning · comment · 2026-10-16T13:46:05Z · [source](https://github.com/vllm-project/vllm/pull/61857#issuecomment-6216874291)

I prototyped this a bit myself and agree the bug is real and that we need to fix it. But, I think the state needs to live somewhere else. Gating `DelegatingParser.parse()` on the reasoning parser's `is_reasoning_end` pulls every legacy `ReasoningParser` into the decision, and most of those scan for the nearest `</think>` without any notion of a turn boundary. The `ParserEngine` behind the engine adapters already has a turn-aware `is_reasoning_end`, and `_single_pass_parse` already takes an `initial_state`, so I think the fix belongs on `ParserEngine` and reaches the delegating path through `ParserEngineReasoningAdapter`.

Here's the rough outline of how I think we need to fix this to scope the fix to just the newer parsers without unintended side-effects in the old reasoning parsers:

1. Give `ParserEngine` a `set_prompt_token_ids()` that derives a `_prompt_initial_state` of `CONTENT` when `self._has_reasoning and self.is_reasoning_end(prompt_token_ids)`, else `None`. Because the engine's check stops at turn boundaries, a prior turn's `</think>` does not count.

2. `_reset(initial_state=None)` falls back to `_prompt_initial_state`. That makes `extract_reasoning()` start in the right state, and `count_reasoning_tokens()` is correct for free because it reads the same pass. No separate flag to keep in sync, and no bypass of `extract_reasoning()`, so whatever the engine config does with a re-opened `<think>` applies here too, the same as when `enable_thinking=False` is passed through `chat_template_kwargs` today.

3. `ReasoningParser` gets a no-op `set_prompt_token_ids()`. `ParserEngineReasoningAdapter` forwards it to its engine and to the counting engine, so the count's `_single_pass_parse` starts in the same state. `DelegatingParser.set_prompt_token_ids()` forwards to the reasoning parser, and `parse_delta` calls it inside the `prompt_reasoning_checked` block regardless of which branch is taken, so the streaming and non-streaming counts agree. The existing `adjust_initial_state_from_prompt` hook can't do this job: it only runs on the streaming path, and only when reasoning is still open. Legacy parsers see a no-op, so deepseek_r1 and friends are unchanged.

On tests, add a quick mock-tokenizer case in `tests/parser/engine/test_qwen3_reasoning.py` with a prompt like `[</think>, <|im_end|>, <|im_start|>, text]` to show a prior turn's close does not flip the new turn to content.

I could be wrong, so if you consider and believe the original version here is the right way to fix that I'm happy to listen to feedback.

- albertoperdomo2 · comment · 2026-10-16T14:21:49Z · [source](https://github.com/vllm-project/vllm/pull/61857#issuecomment-6217552107)

Thanks @bbrowning, I pushed some changes that followed your outline. One difference is that the engine only uses the prompt when its config starts in `REASONING` and declares `turn_boundary_tokens`. Several engine configs (Kimi K2 and DeepSeek V4.1, among others) don't declare turn boundaries. For those, `ParserEngine.is_reasoning_end` doesn't stop at the current turn; it scans back into earlier turns just like `BaseThinkingReasoningParser`. So `_has_reasoning and is_reasoning_end(prompt)` on its own can bring the multi-turn problem back.
