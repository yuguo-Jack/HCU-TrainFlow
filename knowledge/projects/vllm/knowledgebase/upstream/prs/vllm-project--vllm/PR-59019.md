# [Feature][Profiler] Meta-device operator capture

[Upstream PR](https://github.com/vllm-project/vllm/pull/59019) · state: open · merged: False

## Original PR description

## Purpose

Implements RFC #59018 (full design, flow diagram and results there).

`capture_model_ops(model, device="meta")` returns the operators a model would
execute on the **current platform**: order, shapes, dtypes and owning module.
It needs no weights, allocates no accelerator memory and runs no kernels. The
real `current_platform` still chooses the attention, KV-cache, MoE and
quantization backends; only the device is fake.

Changes, in logical commits:

- **Core hooks (small):**
  - `load_format="meta"`: `vllm/model_executor/model_loader/meta_loader.py`
    and its registration
  - the `DIRECT_REGISTERED_OPS` registry in `vllm/utils/torch_utils.py`
  - public `min_kv_cache_memory_bytes` in `vllm/v1/core/kv_cache_utils.py`,
    with a test
  - `_torch_cuda_wrapper` → `torch_cuda_wrapper` in the XPU runner, so the
    capture can reuse it
- **`vllm/profiler/op_capture/`:**
  - `capture` (`ForwardHarness`, `BatchSpec`)
  - `recorder` (`OpRecorder` TorchDispatchMode; runs glue-op bodies)
  - `meta_ops` (schema-derived meta kernels, `OVERRIDES`, Triton launch
    recording)
  - `report` (selection metadata, platform gaps, module tree, files)
  - `trace` (Chakra ET, `compare_devices`)
  - `parallel` (TP ranks)
- **Coverage:**
  - decoder, MLA/sparse MLA, fp8 KV cache, encoder-only/pooling, Mamba/hybrid,
    multimodal encoder inputs, TP>1
  - `keep_going` partial captures
  - several batches per run
- **Supporting files:**
  - tests: `tests/profiler/test_op_capture.py`
  - docs: `docs/design/meta_op_capture.md`
  - example CLI: `examples/features/profiling/capture_model_ops.py`
  - CI: `op-capture` (L4) and its MI300 mirror in
    `.buildkite/test_areas/misc.yaml`, and `op-capture-intel` in
    `.buildkite/intel_jobs/misc_intel.yaml`
- **Three small fixes the capture found:**
  - `XPUMLASparseImpl.record_logical_topk_ready`: a no-op, mirroring ROCm.
    `MLAAttention.forward` calls it on every sparse layer, so without it GLM-5
    fails on XPU with `AttributeError` on its first forward.
  - `gather_initial_states` also accepts meta tensors, so the KDA and Kimi GDN
    prefill paths can be captured. Real-device calls are unchanged.
  - `requantize_with_max_scale` skips its value check on meta weights, so
    static per-tensor FP8 checkpoints such as Mistral-Medium-3.5-128B load
    with `load_format="meta"`. Real-device loading is unchanged.

Apart from the XPU `record_logical_topk_ready` fix, serving behavior does not
change: everything else is opt-in or only taken on meta tensors.

## Not a duplicate

I searched open issues and PRs for "meta device operator capture", "op capture
meta", "load_format meta" and "operator list profiler". Nothing overlaps.
#45069 (CUDA-graph capture tracing) is complementary. The RFC for this work is
#59018.

The fixes have no open PR: searches for `record_logical_topk_ready`,
`xpu_mla_sparse`, `gather_initial_states` and `requantize_with_max_scale`
found none. #56604 was closed as
superseded by #57252, which added the hook for ROCm only; its closing note says
the XPU case is not covered. Kimi-K3's other XPU gaps (the unconditional
cutlass import in `kimi_k3/nvidia/`, KDA on XPU) are left to #49598, which adds
an XPU Kimi-K3 implementation.

## Test Plan

```bash
pytest tests/profiler/test_op_capture.py tests/v1/worker/test_xpu_model_runner.py \
    tests/v1/core/test_kv_cache_utils.py -q
pre-commit run --files $(git diff --name-only origin/main...HEAD)
python examples/features/profiling/capture_model_ops.py \
    --model <model> --max-model-len 2048 --batch 2,16 --keep-going --output-dir out/
```

Parity is checked with `compare_devices(model, "xpu")`, which captures on meta
and on the device in separate processes and diffs the normalized Chakra
execution traces.

  `0074fae5dc`:
  - pytest: **186 passed**
  - pre-commit on the changed files passed, including mypy and
    check-test-tethering
- **Parity, meta vs XPU: exact match** for:
  - Qwen2.5-0.5B
  - bge-small
  - bge-reranker
  - Qwen3-Embedding
  - mamba-130m (prefill and decode)
  - granite-4.0-h-tiny
  - Qwen2.5-VL-3B: text 1350/1350 ops; image batch 2952/2952 ops
- **Full-size configs, meta only.** Eleven frontier models, 2 × 16 tokens. Nine
  capture fully:
  - DeepSeek-V4-Pro: 11,577 ops
  - GLM-5.3: 11,921 (needs the XPU `record_logical_topk_ready` fix above)
  - DeepSeek-V4-Flash: 8,146
  - Ring-2.5-1T: 7,230, one `.item()` body_error
  - Qwen3.8: 6,202
  - MiMo-Pro: 4,698
  - MiMo-Flash: 3,224
  - Qwen3-Coder-Next: 3,243
  - gpt-oss-120b: 2,751, also run at TP=2

  Two stop at real XPU platform gaps, which the report names: GLM-5.3-NVFP4 and
  Kimi-K3. See the RFC table. Without quantization, Kimi-K3's KDA layers need
  the aligned Mamba state indices that Model Runner V2 computes with a
  CUDA-only kernel. The capture computes them on CUDA/ROCm and refuses
  elsewhere, naming the kernel. Past that point a CUDA capture would reach
  `gather_initial_states`, which now accepts meta. That is not run yet; on XPU
  a unit test covers it, since the capture stops earlier.
- **The open-weights models on artificialanalysis.ai**, 13 of them, same
  batch. Eight capture fully: GLM-5.3, K2-Horizon-375B, Muse-Glimmer-30B,
  Nemotron-3-Ultra-550B, MiMo-V2.6-Pro, Mistral-Medium-3.5-128B (3,801 ops,
  needs the `requantize_with_max_scale` fix above), gpt-oss-120b and
  Qwen3.8-27B. The other five have no XPU implementation yet: MiniMax-M3 and
  Inkling capture partially and the report names where they stop (FlashInfer,
  `vllm_flash_attn`); GLM-5.3-Flash, DeepSeek-V4.1-Flash and Kimi-K3 fail to
  build.
- **Report metadata, corrected against the eleven models.** The selection
  metadata describes one representative attention layer, and hybrid models broke
  both of its counts:
  - Head counts came off whichever `AttentionLayerBase` came first, which on a
    hybrid model is a Mamba mixer or an indexer's KV cache. GLM-5.3, Qwen3.8,
    Qwen3-Coder-Next and both DeepSeek-V4 models reported `0 query, 0 kv, head
    size 0`, and Ring-2.5-1T reported `64 query, 0 kv, head size 0`. They now
    report what their configs give: GLM-5.3 and Ring `64 query, 1 kv, head size
    576` (MLA, `kv_lora_rank` 512 + `qk_rope_head_dim` 64), Qwen3.8 `64/4/256`
    without picking up its Gated DeltaNet's 16/128. A model whose attention
    class reports no counts now reads `unknown`, not a fabricated zero.
  - The attention layer count included layers that own a KV cache but run no
    attention, so DeepSeek-V4-Pro reported 243 layers over its 61 decoder layers
    and GLM-5.3 reported 99 over 78. That count was also the denominator of the
    summary's per-layer column, so an operator issued once per decoder layer read
    `0.25` and `0.79` instead of `1.00`. Per-layer counts now divide by decoder
    layers, and the total names the kinds it is made of:
    `99 (78 MLAAttention, 21 DeepseekV32IndexerCache)`.

  Both are metadata only: `ops.txt` is byte-identical across all nine captures
  before and after, and the three non-hybrid models' reports are unchanged too.
- **Not run on CUDA or ROCm yet.** The CI jobs above would be the first run;
  help from CUDA/ROCm owners is welcome.
- **Model evals:** not applicable. The op capture does not affect serving,
  output or accuracy: nothing runs unless `load_format="meta"` or the op-capture
  API is used. The `record_logical_topk_ready` fix is a no-op method that
  replaces an `AttributeError`. I could not serve GLM-5.3 on one B60 to show
  that end to end.
