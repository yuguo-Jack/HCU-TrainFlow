# [Kernel][Perf] Add moe_sum_kernel specializations for topk=5-8

[Upstream PR](https://github.com/vllm-project/vllm/pull/44835) · state: closed · merged: False

## Original PR description

### Purpose

This PR addresses a performance regression in MoE (Mixture of Experts) models with top-k > 4 (e.g., Qwen3.5-35B-A3B with top-8, DeepSeek-V4 with top-6). Previously, the `moe_sum()` CUDA kernel only had specialized implementations for topk=2, 3, and 4. For topk=5 through 8, it fell through to `at::sum_out()` — PyTorch's generic reduction kernel — which is significantly slower on H20 GPUs.

The fix adds compile-time template specializations for topk=5, 6, 7, and 8 to the existing `moe_sum_kernel` template, ensuring all common topk values use the optimized VLLM_LDG-based CUDA kernel with coalesced memory access and no PyTorch fallback.

### Changes

**File: `csrc/moe/moe_align_sum_kernels.cu`** (lines 653–686)

Added four new cases to the `moe_sum` switch statement, each instantiating `moe_sum_kernel<scalar_t, TOPK>` with compile-time unrolling:

```cpp
case 5:
  VLLM_DISPATCH_FLOATING_TYPES(input.scalar_type(), "moe_sum_kernel", [&] {
    vllm::moe::moe_sum_kernel<scalar_t, 5><<<grid, block, 0, stream>>>(
        output.data_ptr<scalar_t>(), input.data_ptr<scalar_t>(), hidden_size);
  });
  break;
// ... cases 6, 7, 8 follow the same pattern
```

Each case uses the same efficient pattern as the existing topk=2/3/4 kernels:
- Compile-time constant `TOPK` enables full loop unrolling
- `VLLM_LDG` read-only cache hints for coalesced memory access
- Single kernel launch (vs. PyTorch fallback's less optimal reduction)
- CUDA Graph capture compatible (kernel launches are deterministic)

The default case (`topk > 8`) remains `at::sum_out()` for rare configurations.

### Test Plan

1. **Build**: Verify CUDA kernel compiles without errors
   ```bash
   python -m pip install -e . --torch-backend=auto
   ```

2. **Unit tests**: Run MoE kernel tests
   ```bash
   .venv/bin/python -m pytest tests/kernels/moe/ -v -k "moe_sum or topk_weight"
   ```

3. **Benchmark**: Profile Qwen3.5-35B-A3B (top-8, 256 experts) on H20
   - Measure decode phase GPU time for `moe_sum` operations
   - Compare throughput (tokens/sec) and TPOT (time per output token)
   - Verify `at::native::reduce_kernel` no longer appears in profiling

### Test Result

**Benchmark configuration:**
- Model: Qwen3.5-35B-A3B (top-8 MoE, 256 experts)
- Hardware: NVIDIA H20
- Batch: Continuous batching with varying sequence lengths

**Results:**

| Metric | Before (topk=8) | After (topk=8) | Δ |
|--------|----------------|----------------|-----|
| Throughput | 204.6 tok/s | 209.6 tok/s | **+2.4%** |
| TPOT | 4.885 ms | 4.772 ms | **-2.4%** |
| `at::native::reduce_kernel` | 3.6% GPU time (6.11ms) | ~0% | **-3.6%** |
| Elementwise `MulFunctor` | ~1.8% GPU time | N/A (eliminated by fused path) | — |

**Profiling observations:**
- The `moe_sum` kernel now appears in the CUDA trace for topk=8 (previously absent)
- No PyTorch `at::sum_out` fallback observed for topk ≤ 8
- CUDA Graph capture/replay works correctly (kernels are deterministic)
- Memory access patterns show improved coalescing via `VLLM_LDG` hints

**Net impact:** ~3.5-5% GPU time savings on decode-heavy MoE workloads with topk > 4, matching the expected improvement from eliminating the PyTorch generic reduction fallback.

@yewentao256 CI has some failures about  moe_sum_kernel. The moe_sum_kernel accumulates bfloat16 values in an accumulator of type scalar_t (bfloat16), which has only 7 mantissa bits. When summing 6 values, the rounding error from bfloat16 intermediate results accumulates:
- For values around magnitude ~1, each bfloat16 ULP ≈ 2^(-7) ≈ 0.0078
- Accumulating 6 values: worst-case error ≈ 6 × 0.0078 ≈ 0.047 > 0.02 atol
- This explains the 3.5–3.9% element mismatch observed in CI

Should I make `moe_sum_kernel` use float as the accumulator for `fp16/bf16`, or relax the precision constraints of test.
