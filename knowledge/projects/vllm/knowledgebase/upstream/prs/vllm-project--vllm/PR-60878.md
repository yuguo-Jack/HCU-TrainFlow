# [Bugfix][MiniMax-M3] Keep video timestamps with the processor cache

[Upstream PR](https://github.com/vllm-project/vllm/pull/60878) · state: open · merged: False

## Original PR description

## Overview

With the multimodal processor cache on, which is the default, MiniMax-M3 video prompts contain no per-frame timestamps. The reference HF processor puts `]<]X.X seconds[>[` before every frame pair. This PR parses videos with `video_needs_metadata=True`, as #45381 intended, so the cached path keeps the frame metadata.

Without timestamps the model gets sampled frames but no time scale, so it cannot say when something happens or how long a video is. Tested on the same vLLM commit with and without this PR: 30 synthetic videos (60-1200 s, a red square appearing at a known time, no on-screen time cues), 32 frames, greedy decoding, thinking off:

| | Without | With |
|---|---|---|
| "When does the square first appear?" median error | 100 s, 0/30 within one frame pair | 0 s, 30/30 (as precise as 32 frames allow) |
| "How long is the video?" median error | 95% of the length (answers ~15 s for every video) | 2.5% |

All 30 videos improve on both questions (sign test p = 2⁻³⁰). Without the fix the model does find the right frame, but reads time as if frames were 0.5 s apart. VideoMMMU accuracy is unchanged (below), as its questions rarely need absolute times.

## Claims

- Served prompts now carry the reference processor's timestamps, one per frame pair, and the prompt is identical with and without the processor cache.
- No detectable accuracy change on a 225-question VideoMMMU subset: 0.462 → 0.444, paired McNemar p = 0.63.
- Videos without metadata (bare frame arrays, the profiling dummy) are unchanged.

## Validation

- Processor level on `main` (CPU, real processor and tokenizer, 60 s and 1 h videos, 32 frames): before, 0 timestamps with the cache on and 16 with it off; after, 16 in both, with identical prompts.
- Served on a ROCm nightly at `8cbd5d03` plus this commit (MiniMax-M3 FP8, TP4, MI325X): 16 timestamps per 32-frame video, against 0 on the stock nightly. The prompt token IDs match those of the A/B below, with and without the fix.
- Served from an image built on the official `vllm/vllm-openai-rocm` nightly for `8cbd5d03`, with vLLM rebuilt from source at `8cbd5d03` plus this PR and #60879 (same hardware): on the same 32-frame probe video as the run above, 16 timestamps and identical prompt token IDs (11,847 tokens); 250 timestamps on a 500-frame 1-hour video; and a 225-question VideoMMMU subset with 0 failures.
- Negative control on the official `vllm/vllm-openai-rocm` nightly image for `8cbd5d03`, with #60879's loader file but without this PR: the same 1-hour video at 500 frames gives 180,500 video prompt tokens, exactly 250 frame pairs × 722 tokens, i.e. no timestamps.
- On an image built from that nightly with this PR and #60879, server-wide `max_frames` 32 and thinking on by default (`--default-chat-template-kwargs '{"thinking_mode":"enabled"}'`):
  - a 225-question VideoMMMU subset with 0 failures;
  - a 1-hour video at 32 frames has 11,691 video prompt tokens, 139 more than its 16 frame pairs (16 × 722), consistent with 16 timestamps.
- Served A/B on vLLM 0.26.1rc1 with the equivalent patch, 225 questions, 32 frames:
  - +128 prompt tokens per request, 0 failures;
  - accuracy as above; this subset can resolve changes of about 5-7 points;
  - answers 14% longer.
- `pytest tests/models/multimodal/processing/test_minimax_m3.py`: 11 passed. The 2 new tests fail on `main`. `pre-commit` passes.

## Details

- **Cause:**
  - Parsed video items held bare frames.
  - On the cache path, `_get_cache_missing_items` re-parses the cache-miss items, and the prompt updates are built from them, so fps and `frames_indices` were gone.
  - #45381 set `video_needs_metadata=True` through `_get_data_parser`, a hook that #33260 and #33757 had already removed. #50285 later deleted it as dead code.
- **Fix:** `MiniMaxM3VLProcessingInfo.get_data_parser` returns `video_needs_metadata=True`. A small parser subclass gives metadata-less videos `{}` instead of raising, as GLM-4.1V and Molmo2 do, so offline frame arrays and the profiling dummy keep working.
