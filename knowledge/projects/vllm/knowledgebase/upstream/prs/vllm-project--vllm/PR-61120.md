# [Bugfix] Don't force a second </think> after a natural end in V1 spec decode

[Upstream PR](https://github.com/vllm-project/vllm/pull/61120) · state: open · merged: False

## Original PR description



## Overview

Fixes #61116. With speculative decoding on Model Runner V1, if the model emits `</think>` itself inside the draft window and `thinking_token_budget` runs out in that same window, a second `</think>` was forced. This PR skips forcing for that step when the in-budget drafts already contain the end sequence.

## Claims

- Spec-decode output with `thinking_token_budget` on MRV1 matches non-spec output when the natural end falls inside accepted drafts (no duplicate `</think>`).
- Budget enforcement is unchanged otherwise: the forced position is computed exactly as before.
- MRV2 is not affected and not touched.

## Validation

Reproducer from #61116 (Qwen3-0.6B, fp32, greedy, ngram k=3, `thinking_token_budget=91`, `VLLM_USE_V2_MODEL_RUNNER=0`), RTX 5070 Laptop 8 GB:

| Runner | Build | `</think>` count (3 prompts) | ngram == no-spec |
|---|---|---|---|
| MRV1 | `main` (f26d9f432) | 2 / 2 / 2 | no |
| MRV1 | this PR | 1 / 1 / 1 | yes, token-identical |
| MRV2 (default) | this PR | 1 / 1 / 1 | yes |

The reporter re-ran their sweeps with this PR on the 0.31.0 x86 CPU wheel ([comment](https://github.com/vllm-project/vllm/pull/61120#issuecomment-6116595362)): duplicate `</think>` went from 8/200 to 0/200 (fixed budget 91) and from 92/131 to 0/131 (budget just above the natural reasoning length), with all 131 outputs token-identical to non-spec. That run used commit 1881726. The later committed-output change does not affect single-token ends.

Tests:

```bash

# main: 4 failed, 4 passed; this PR: 8 passed
pytest tests/v1/sample/test_thinking_budget_state.py tests/v1/logits_processors/test_correctness.py
# this PR: 51 passed
pre-commit run --files vllm/v1/sample/thinking_budget_state.py tests/v1/sample/test_thinking_budget_state.py
# all hooks pass
```

The new test drives `ThinkingBudgetStateHolder` in the V1 call order (`update_state`, the bonus-row `apply_to_logits` in `Sampler`, then the target-row call in `RejectionSampler`) with greedy verification on CPU. It covers two bug cases plus two controls (a natural end well within budget, and the budget reached first), and a 2-token end whose first token is already committed when the rest arrives in the drafts. It runs in CI via `pytest v1/sample` (`.buildkite/test_areas/misc.yaml`).

Not run: the reporter's 200-prompt sweep, or spec methods other than ngram end to end. The change only reads `spec_token_ids`, so it does not depend on the proposer.

## Details

**Root cause.** Natural-end detection in `_update_think_state` only scans committed output. When `think_count + len(spec_token_ids) + 1 > budget`, the transition to end mode picks `force_index` from `remaining_budget` and the draft length alone. If an earlier draft is `</think>` and is accepted, the target row at `force_index` is still one-hot `</think>`. The draft there differs, so it is rejected and the recovered token is a second `</think>`.

**Fix.** Compute the forced position first. If the end sequence is in the last `len(end) - 1` committed tokens plus `spec_token_ids[:force_index]`, return without entering end mode. The committed tail covers a multi-token end that started in the previous step; for single-token ends it is empty. This is safe because all rows before `force_index` are within budget:
- If the drafts through `</think>` are accepted, it's a natural end, handled next step by the existing committed-output path.
- If an earlier draft is rejected, no token past the budget is emitted, and the next step re-evaluates.

When the end token is exactly at `force_index`, forcing agrees with the draft, so that case is unchanged.

**MRV1.** MRV1 is still used with `VLLM_USE_V2_MODEL_RUNNER=0`, on builds without Triton (CPU/macOS), and for spec methods MRV2 doesn't support (suffix, medusa, mlp_speculator, …). This fix is in V1-only code.

**Relation to #61005.** That open PR rewrites the same branch for a different bug: a corrupted multi-token forced end. It does not fix this one; I checked that its head fails the new test. The two changes compose. Applied on top of #61005, the conflict is trivial (the guard goes right before `_force_end_window`), and both test files pass (11 passed). I'm happy to rebase onto whichever lands first.

**Alternatives considered.** I didn't include drafts in natural-end detection, because drafts can be rejected and that would need rollback state. I also didn't mask `</think>` at the forced row, because that alters the model's own choices.

AI assistance (Claude) was used to investigate, write, and test this change. I reviewed every changed line and ran the validation above.
