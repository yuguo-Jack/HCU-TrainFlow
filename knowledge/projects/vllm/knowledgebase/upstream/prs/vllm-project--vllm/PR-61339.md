# [Benchmark] Add vllm bench forward: exact-shape forward timing

[Upstream PR](https://github.com/vllm-project/vllm/pull/61339) · state: closed · merged: True

## Original PR description



> Commits: *[Benchmark] Add vllm bench forward*, the *model-microbenchmark* agent skill, and *Support DCP*. No changes to the model runner or model code.

## Overview

Add `vllm bench forward`: time the model forward of an **exact** batch (prefill, chunked prefill, prefix hit, decode, spec-decode verify, or any mix), built without the scheduler and run through the real `execute_model`, captured as a one-shot CUDA graph. Works single-GPU and with DP/TP/EP/DCP across nodes via `torchrun`.

```bash
vllm bench forward --model deepseek-ai/DeepSeek-V4-Flash \
  --case decode=64*1@8192 --case prefill=8192 --case mix=4096,32*1@8192
torchrun --nproc-per-node=4 -m vllm.entrypoints.cli.main bench forward \
  --model ... -dp 4 --enable-expert-parallel --shapes shapes.json
```

## Claims

- Exact shapes: requests are `[N*]Q[@K][c][:D]` (query length, KV length including the query, draft tokens). A prefill's prefix is a prefix-cache hit (SWA bounded replay on DeepSeek-V4.1) unless `c` marks a chunked prefill. Every run checks that the runner built exactly that batch.
- Accurate GPU time: one-shot FULL graph even for prefill (host-side plans are correct by construction, since the graph only replays the batch it captured). Rendezvous and timing events live inside the graph, so rank skew and launch gaps are excluded; each replay is reduced with MAX over ranks; per-replay jitter is reported (sample spread) and flagged above 0.5%.
- Realistic defaults for dummy weights: KV lengths vary +-50% (same on every DP rank, `--kv-len-jitter`); MoE routing is balanced per EP rank (`--routing auto`), replacing the degenerate routing of dummy gates.
- Matches independent references (below).

DCP: Kimi-K3 (9 layers, MLA) TP4 with DCP1 vs DCP4 on decode, chunked prefill and prefix hit: the runner builds the expected batches, DCP4 allocates the scheduler's block count (`block_size * dcp` tokens per block for DCP-sharded specs), and replays are deterministic.

Also run: DeepSeek-V4/V4.1 DEP4 (1 node) and DEP8 (2 nodes, MNNVL), TEP4, prefix hits, verify. Median run-to-run reproducibility within ~0.3%; sample spread mostly 0.01-0.4% (higher on V4.1 DEP prefill, from MegaMoE cross-rank sync and host engram reads).

## Details

- **Flow per case:** build `SchedulerOutput` (disjoint block IDs across KV groups) -> zero the case's KV blocks -> `execute_model` twice: eager warmup (JIT, autotune), then capture/validate/time. For those two steps the bench shadows `runner.prepare_inputs` (to check the batch the runner built) and `model.forward` (to take over the eager model call) with instance attributes, then deletes them; the runner itself is unchanged. Requests are re-added on the second call; `sample_tokens` is never called, so the pending step state is dropped.
- **State restore:** the KV blocks a step writes are snapshotted and restored inside the graph before each replay, so in-place state (e.g. DeepSeek-V4.1's compressor) is identical across replays.
- **KV init:** zeros only for now (`--kv-init zeros`). Random KV was measured within 3% on DeepSeek-V4.1 at ~100K context, so its per-layout model code isn't worth it yet.
- **Routing:** forward hooks on `GateLinear` replace gate logits with a balanced fixture; this covers backends that route from logits, including monolithic FlashInfer TRTLLM (verified on Kimi-K3) and modular (verified on DeepSeek-V4: router top-k equals the fixture). Models that compute top-k themselves (e.g. MegaMoE's fused gate on DeepSeek-V4/V4.1 and Kimi-K3) instead get the fixture's `topk_ids` through a forward pre-hook on any experts module whose `forward` takes `topk_ids`; on DeepSeek-V4.1 DEP4 this matches the earlier model-local override within run-to-run noise (+0.05% to +0.8%). Grouped top-k is rejected; layers the fixture can't reach fail loudly.
- **Model code:** none.
- **Dependencies / limitations:**
  - Dummy-loaded DeepSeek-V4.1 loses MegaMoE shared-expert fusion (fixed by #60096); the bench's dummy loader finalizes early as a temporary workaround (TODO to remove).
  - Data-dependent kernels need realistic activations: #61323 keeps dummy norms neutral (e.g. V4.1 sparse top-k 27.8 ms -> 10.7 ms, real weights 10.6 ms).
  - The batch builder mirrors scheduler semantics (block counts, prefix-hit replay); the unit test and the per-run layout check guard against drift.
  - Model branches on `is_current_stream_capturing()` (e.g. DeepSeek-V4 short-context top-k, V4.1 mHC overlap) make small batches' graph output differ slightly from eager; reported, not asserted.
- **Agent skill:** `.agents/skills/model-microbenchmark` documents usage and pitfalls (dummy-weight artifacts, torch.compile models, timing spread) for agents.
- **Size:** ~1,050 non-test lines, isolated under `vllm/benchmarks/forward/` plus the CLI entry, docs and agent skill.
