# [Bugfix] Accept the renamed unlimited_ocr model type

[Upstream PR](https://github.com/vllm-project/vllm/pull/61594) · state: closed · merged: False

## Original PR description

## Overview

The `baidu/Unlimited-OCR` checkpoint renamed its `model_type`, which breaks two AMD CI steps on current main. This registers both the old and the new spelling.

## Claims

- Fixes `(MI355 DPX) Basic Models (Extra Initialization) Shard 1` and `(MI355 DPX) Multimodal Processor Shard 4`, failing in [build 94688](https://buildkite.com/vllm/ci/builds/94688/list) and every build since.
- Keeps checkpoints pinned to a revision from before the rename working.
- No behaviour change for any other model: four registry entries, no new logic.

## Validation

Five tests across `test_initialization.py`, `test_tensor_schema.py` and `test_common.py` fail on current main and pass with this change, verified on gfx950:

```
pytest tests/models/test_initialization.py \
       tests/models/multimodal/processing/test_tensor_schema.py \
       tests/models/multimodal/processing/test_common.py \
       -k Unlimited -q
```

Before: `4 failed, 662 deselected` and `1 failed, 401 deselected`. After: all pass.

## Details

The failure looks like this:

```
pydantic_core._pydantic_core.ValidationError: 1 validation error for ModelConfig
  Value error, The repository baidu/Unlimited-OCR contains custom code which must
  be executed to correctly load the model.
Please pass the argument `trust_remote_code=True` to allow custom code to be run.
```

No vLLM commit caused it. The hub checkpoint changed: commit [`8249d20b`](https://huggingface.co/baidu/Unlimited-OCR/commit/8249d20b2822a7d8a4c22c8d8c9069b5ac36bda3), "Update files for compatibility with transformers (#13)", renamed `model_type` from `unlimited-ocr` to `unlimited_ocr`. Every commit on that repository since June had only touched the README.

vLLM ties this model to four registries, all keyed on `model_type` by exact string match. `_maybe_register_hf_config` therefore no longer finds `UnlimitedOCRConfig`, so it is never registered with `AutoConfig`, and transformers falls back to the repository's `auto_map`. That `auto_map` has always been present; it only started to matter once the lookup began to miss.

Both spellings are registered rather than just renamed, because `_register_config_class` assigns `model_type` from whichever key matched, so a revision pinned before the rename keeps resolving.

One limitation worth naming: the same hub commit also added `chat_template.jinja`, so the new chat template fallback entry is inert for current revisions. I added it anyway so that all four registries agree on the model type rather than leaving one keyed only on the old name.
