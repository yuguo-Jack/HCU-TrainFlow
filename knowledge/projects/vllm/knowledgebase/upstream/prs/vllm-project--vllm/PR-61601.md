# [Perf][Qwen4Exp] Internal prefill checkpoints for the PLE short conv

[Upstream PR](https://github.com/vllm-project/vllm/pull/61601) · state: open · merged: False

## Original PR description



## Overview

Follow-up to #60050. Qwen4Exp (Qwen3.8-Flash-Next) has a second Mamba layer, the PLE short conv, that could not export internal prefill checkpoints. Since the scheduler takes them only when every Mamba layer can, Qwen4Exp prefills kept splitting at the prompt's last cacheable block boundary. The PLE layer now exports its conv window at the checkpoint, so a Qwen4Exp prefill that crosses that boundary runs in one step, like Qwen3.5 does since #60050.

## Claims

- Qwen3.8-Flash-Next FP8, TP4 + EP, MTP (3 tokens), 1x GB200 node, 8000-token prompts, against main `ec317a4`: mean TTFT −17% / −17% / −23% at concurrency 1 / 4 / 16, median −18% / −20% / −21%. TPOT drops 2–9%; GSM8K is unchanged.
- Only active where #60050's checkpoints are (FlashInfer GDN prefill, prefix caching on). Elsewhere every spec, block size and kernel is unchanged; ROCm's PLE layer is a separate class and is untouched.

## Validation

Setup: Qwen3.8-Flash-Next-FP8, `-tp 4 -ep --enable-prefix-caching --speculative-config '{"method": "mtp", "num_speculative_tokens": 3}'`, MRV2, every arm on the same GB200 node.

- Main splits an 8000-token prompt at 7200 + 800 tokens (block 800). This PR runs it in one step: a torch profile shows a single `execute_context_1(8000)` step (126 ms), and `store_cache_checkpoints_kernel` runs 37 times per prefill (36 GDN layers + the PLE layer).
- TPOT drops at concurrency 4 and 16, not 1: decoding requests share a step with each new prompt's prefill and wait for it. Main makes them wait for two steps per prompt (the 800-token one is ~45 ms), this PR for one. At 16, each request sees about 16 prefills while decoding 1000 tokens, so ~45 ms × 16 / 1000 ≈ 0.7 ms per token, close to the measured 0.71 ms.
- The 64-token checkpoint grid moves the block from 800 to 832 tokens (KV cache memory 124.01 vs 124.03 GiB), as it does for Qwen3.5 since #60050.

**GSM8K** (`tests/evals/gsm8k/gsm8k_eval.py --use-chat-completions --chat-template-kwargs '{"enable_thinking": false}' --max-tokens 1024`, 20-shot, 1319 questions):

| main `ec317a4` | this PR |
|---|---|
| 0.9651 | 0.9606 |

Other main runs of this eval on the same node scored 0.9629 and 0.9583, so the difference is within run-to-run noise.

- The shared 20-shot prefix makes 60% of prompt tokens prefix hits (main: 77%), so requests resume from the exported checkpoints. MTP mean acceptance length is 3.49 on both arms.
- The hit rates differ because of the block size, not the export: these prompts are 4122–4287 tokens with a 4087-token shared prefix, just under 5 × 832, so with MTP's dropped block they hit at 3 × 832 − 832 = 2496 here and at 5 × 800 − 800 = 3200 on main.
- Raw-completion GSM8K is not used: this model ends few-shot completions immediately on every arm.
- Under `VLLM_GPU_SYNC_CHECK=error`, 300 GSM8K questions (0.9833) and 64 8000-token prompts at concurrency 4 completed without a sync violation.

- `test_prefill_exports_conv_window_at_checkpoint` runs the PLE layer's dispatch on a batch of decodes and two prefills that checkpoint mid-query, alone and mixed with spec-decode rows (whose prefill tokens the kernels reach through the non-spec token map), in both conv-state layouts. - `test_checkpoint_exporter.py` calls the shared exporter the way each of its callers does (GDN with FlashInfer's row map into an FP32 SSM cache as on Qwen3.5 and Qwen4Exp, or a BF16 one as on Qwen3-Next; Kimi-K3 and GLM-5.3-Flash FlashKDA; Kimi-K3 ROCm conv-only; Qwen4Exp PLE with a token map), in both conv-state layouts, against a PyTorch reference, and checks that nothing else in either cache changes. ## Details

- **PLE layer.** `get_prefill_checkpoint_alignment()` returns 1 in align mode: the conv window ending at any offset of at least `(kernel - 1) * dilation` (9 tokens here) is a copy of the inputs before it. When every Mamba layer can checkpoint, the PLE spec reserves a checkpoint block on the same grid as GDN, and the prefill path exports each window with `MambaPrefillCheckpointExporter(state_len=(kernel - 1) * dilation)`. Under sequence parallelism the conv input is all-gathered before the conv, so the export sees every token.
- **PLE metadata builder.** Builds `MambaPrefillCheckpointMetadata` over the non-spec rows in both of its paths (decodes then prefills, or the non-spec rows of a mixed spec batch).
- **One grid for every Mamba spec.** The scheduler checks offsets against one alignment (the first Mamba group's), so GDN's checkpoint grid moves to `get_mamba_prefill_checkpoint_grid` in `layers/mamba/abstract.py` and both specs use it: the prefix-cache grid made a multiple of the model's checkpoint alignment.
- **Exporter.** The recurrent half of `MambaPrefillCheckpointExporter.export` is now optional, and an optional `token_indices` maps the rows' tokens to their rows of the input. Existing callers pass the same keyword arguments as before.

**Tradeoffs.**

- The block is 4% coarser (800 → 832), so prefix hits land on a coarser grid. How much that costs depends on where prompts end relative to block boundaries; the GSM8K run above is an unlucky case (60% vs 77% hit rate) that still keeps its accuracy.
- Validated on SM100 (GB200) only, like #60050.
- The exporter's new conv-only and token-map variants compile on the first checkpointed step, like the GDN one does since #60050: its strides depend on the allocated KV cache.

**Related / not a duplicate.** No open PR adds internal checkpoints for the PLE short conv (searched 2026-10-14).

- #60050 (merged) added internal checkpoints for the FlashInfer GDN prefill and aligns blocks only when every Mamba layer can checkpoint.
