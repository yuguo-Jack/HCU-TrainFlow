# [ROCm][CI] Make ROCm 10.0 the default image; keep ROCm 7.2 as -rocm72

[Upstream PR](https://github.com/vllm-project/vllm/pull/58761) · state: closed · merged: True

## Original PR description

## Purpose

Make ROCm 10.0 (TheRock) the default ROCm image and wheel, keeping ROCm 7.2 available for a transition period.

- Rename `Dockerfile.rocm{,_base}` → `Dockerfile.rocm_72{,_base}` and `Dockerfile.rock{,_base}` → `Dockerfile.rocm{,_base}`, so all CI now builds ROCm 10.0.
- Images: `:nightly` / `:latest` are ROCm 10.0 (also tagged `-rocm100`); ROCm 7.2 is published as `-rocm72`.
- Wheels: `wheels.vllm.ai/rocm/` now serves ROCm 10.0 (`rocm100`); ROCm 7.2 stays at `rocm/<ver>/rocm723`. Install:
  ```bash
  uv pip install "vllm[device-gfx942]" --extra-index-url https://wheels.vllm.ai/rocm/
  ```
  The index hosts vLLM, triton, FA, aiter, amdsmi and a torch repacked to require our triton, and links the ROCm SDK and GPU kernels from AMD's whl-next index.

- Both stacks go through the same scripts and pipeline steps: each ROCm script takes the stack's base Dockerfile, and `.buildkite/scripts/rocm/stack.sh` derives the version, variant, cache keys and image tags from it.
- Internal ECR tags are renamed to the variant (e.g. `<commit>-rocm100`), so the first run rebuilds each base image once.

Known gaps: wheel installs miss the image's build-time ROCm patches, and the amdsmi wheel still needs a hardware check.

AI assistance (Claude Code) was used; reviewed and owned by me. No duplicate PR exists.

## Test Plan

YAML/shellcheck/ruff, `tests/tools/test_docker_build_metadata_args.py`, dry runs of the publish/upload scripts against a fake S3, and `uv pip compile "vllm[device-gfx942]"` against a locally generated index.

## Test Result

All pass; the one-liner resolves to our torch/triton plus AMD's SDK and gfx942 kernels. Full builds and the AMD test suite still need to run.
