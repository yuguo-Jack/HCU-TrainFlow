# [Bugfix][Frontend] fix Anthropic inline-system probe crashing startup

[Upstream PR](https://github.com/vllm-project/vllm/pull/64020) · state: closed · merged: True

## Original PR description

## Overview

Fixes #61919: `vllm serve` crashes at startup for `allenai/Olmo-3-7B-Instruct`. When the Anthropic `/v1/messages` endpoint is set up, vLLM renders the model's chat template once to check how it handles system messages, and that render raised an uncaught `TypeError`. This PR  stops the server from going down if the render fails.

## Claims

- `vllm serve allenai/Olmo-3-7B-Instruct` now starts. Before this change, it stopped with `TypeError: Object of type Undefined is not JSON serializable`.
- OLMo 3 is correctly detected as accepting non-leading system messages, so inline system messages are **not** merged into the leading system prompt, and the prefix cache keeps working.
- If the startup check fails for any reason other than a template error, vLLM falls back to merging instead of stopping the server.

## Validation

- ran `vllm serve allenai/Olmo-3-7B-Instruct --dtype bfloat16` on a local GPU. It crashed at startup before the fix and reached `Application startup complete.` with it.

```bash
pytest tests/entrypoints/anthropic/test_anthropic_messages_conversion.py -k TestDetectMergeInlineSystem -q
```

| | Result |
|---|---|
| Without fix | 2 failed, 5 passed |
| With fix | 8 passed |

`ruff check` and `ruff format --check` pass on the changed files.

**Model output:** the change only affects the one-time startup check, not how prompts are rendered for requests, so model output is unchanged and no accuracy evaluation was needed.

## Details

**Root cause:** `AnthropicServingMessages.__init__` calls `_should_merge_inline_system`, which calls `_detect_merge_inline_system`. That function renders the chat template with a `[system, user, system, user]` conversation to find out whether the template accepts non-leading system messages. Since #58727, this check renders the model's own template.

The render did not pass `tools`, so in Jinja it was `Undefined`, not `None`. OLMo 3's template branches on `tools is none`. That is false for `Undefined`, so the template ran `tools | tojson`, and `json.dumps` raised `TypeError`. `_detect_merge_inline_system` only caught `jinja2.TemplateError`, so the error reached the top and stopped the server. Real requests to both `/v1/chat/completions` and `/v1/messages` pass `tools=None` and were never affected; only this startup check was.

**Fix:**

Widen `except jinja2.TemplateError` to `except Exception`, falling back to merging (`True`). This is a safety net so that a template the check can't render for some other reason causes at worst unnecessary merging, not a failed startup.

**Tradeoff:** catching `Exception` alone would also stop the crash. But for OLMo 3 it would wrongly decide that merging is needed, which moves inline system messages into the leading system prompt and breaks prefix caching. That's why (1) is included and not only (2).

**Not a duplicate:** I searched open PRs for `61919` and for `merge_inline_system`. None address this crash. The related open PRs #63368 (fold inline system messages in place) and #53501 (preserve prefix cache for inline system turns) change different behavior.

Thanks for working on this. The `except Exception` fallback fixes the crash, but I think `tools=None` makes things worse, so could we drop it?

Hermes-3's `tool_use` template iterates `tools`, so with `tools=None` the probe raises and Hermes-3 now merges, where main keeps inline system messages. For OLMo 3, merging looks like the better result: its [chat template](https://huggingface.co/allenai/Olmo-3-7B-Instruct/blob/6e5971d9eba42665f5bd5a0fcf047f299ce1dccc/chat_template.jinja) appends the whole tool list to every system message, so keeping inline ones resends all tool schemas with each Claude Code reminder (about 2,450 tokens per reminder with 20 tools). It also merged before #58754.

Without `tools=None`, every model in my HF cache matches main except OLMo 3, which merges. I haven't run a live server.

nit: OLMo 3 would then merge only because the probe render fails. A check that renders a dummy tool and merges when the tool list repeats per system message would make it explicit, though it adds code for one model. I think that's worth discussing with the maintainers.

```suggestion
    def test_tools_none_check_template_merges(self):
        """OLMo 3-style ``tools | tojson`` on undefined tools falls back to merge."""
        template = (
            "{% if tools is none %}{% else %}{{ tools | tojson }}{% endif %}"
            "{% for m in messages %}{{ m.content }}{% endfor %}"
        )
        assert AnthropicServingMessages._detect_merge_inline_system(template) is True

    def test_tools_loop_template_no_merge(self):
        """Hermes-style ``for tool in tools`` must not raise in the probe."""
        template = (
            "{% for tool in tools %}{{ tool | tojson }}{% endfor %}"
            "{% for m in messages %}{{ m.content }}{% endfor %}"
        )
        assert AnthropicServingMessages._detect_merge_inline_system(template) is False
```
