# [Bugfix] Fix out-of-bounds attrIdxs in C++ batch memcpy path

[Upstream PR](https://github.com/vllm-project/vllm/pull/53971) · state: open · merged: False

## Original PR description

Fixes #53863

## Summary

`swap_blocks_batch()` in `csrc/cache_kernels.cu` (moved there from `csrc/libtorch_stable/` by #60721) passes a **single** `size_t` as the `attrIdxs` array to `cuMemcpyBatchAsync` / `hipMemcpyBatchAsync`, regardless of the descriptor count — the same contract violation fixed for the Python path in #53860.

The CUDA Driver API documentation for `cuMemcpyBatchAsync` specifies `attrIdxs` as an array of `count` elements (indices into `attrs`, each `< numAttrs`). Passing `&attrs_idx` where `attrs_idx` is one stack scalar while `count` is large (typically thousands of 64 KiB KV blocks per offload) leaves the driver reading past the end of that scalar — an out-of-bounds read / undefined behavior that currently happens to work only because adjacent stack bytes happen to read as tolerable values.

Still present at upstream `main` (`f47792af7`): `csrc/cache_kernels.cu` lines 174-185 (CUDA) / 201-227 (ROCm). First confirmed by @curvedinf at `241e9391e`; between that commit and current `main` the only changes to this file are the #60721 move plus include reshuffles and a compile-warning guard elsewhere in the file — `swap_blocks_batch()` itself is byte-identical, and the line numbers above reflect current `main`. This branch is rebased onto `f47792af7`.

## Why this is not a duplicate

- #53991 was the only other PR touching this file. It was **closed on 2026-09-07** when its author deleted the head repository, so this is currently the only open fix for the C++ path.
- #53860 is the separate **Python** path (`vllm/v1/simple_kv_offload/cuda_mem_ops.py`). It is deliberately kept as its own PR so this one has no Python-side blast radius and that one has no compile-matrix impact.

## Fix

Allocate a per-descriptor index array. All-zero indices preserve the existing semantics exactly (every descriptor uses `attrs[0]`):

```cpp
std::vector<size_t> attr_idxs;
...
attr_idxs.assign(static_cast<size_t>(cnt), 0);
CUresult result = batch_fn(..., &attr, attr_idxs.data(), 1, &fail_idx, ...);
```

Both the CUDA and ROCm paths are fixed. The entire change is **1 file, +12/-5**, confined to `swap_blocks_batch()` plus one `#include <vector>`. On ROCm runtimes where `num_attrs = 0` is passed, `attrIdxs` is ignored and the array is simply unused.

## The read is live on ROCm 7.13+, not merely permitted

On ROCm 7.13+ the code sets `num_attrs = 1` (see `runtime_accepts_attrs`, lines 205-214 at current `main`), so `attrIdxs` is *consumed* — the driver really does read `count` entries from a one-element stack object. @curvedinf hit this on a ROCm 7.14 runtime downstream and independently ported the same fix to both batch paths (commit in `curvedinf/int8-vllm`, 2026-09-13, "Rebuilt + import smoke OK"), which is the confirmation that motivated the sanitizer harness below.

## Deterministic sanitizer reproducer (no GPU, no driver required)

Harness by @curvedinf (`oob_demo.cpp`, attached to [#53863 (comment)](https://github.com/vllm-project/vllm/issues/53863#issuecomment-5686772976)). It replicates the exact upstream call pattern against a stub driver-side consumer that implements the documented contract (one index read per descriptor), and contrasts it with the fixed pattern in the same binary:

```bash
g++ -std=c++17 -O1 -g -fsanitize=address -o oob_demo oob_demo.cpp
./oob_demo   # exit 1
```

```
ERROR: AddressSanitizer: stack-buffer-overflow ... READ of size 8
    #0 stub_batch_memcpy ... oob_demo.cpp:42
    #1 upstream_pattern  ... oob_demo.cpp:60
This frame has 3 object(s):
    [64, 72) 'attrs_idx' (line 58) <== Memory access at offset 72 overflows this variable
```

Note *where* it lands: `attrs_idx` occupies 8 bytes at frame offset `[64, 72)`, and the faulting access is at offset `72` — exactly one element past the scalar, i.e. `attrIdxs[1]`. The harness trips on the **second** descriptor, not on some extreme corner: with `numAttrs > 0 && count > 1` the read goes out of bounds immediately.

The fixed-pattern branch (`attrIdxs` sized to `count`, all zeros) runs clean in the same binary. Per @curvedinf's suggestion this is kept out of `tests/` — it validates the *call pattern*, not vLLM behavior, so it belongs in the PR rather than the test tree. Reviewer shortcut: **the bug is fixed when the upstream-shaped branch of the harness is the clean one.**

That declaration is a leftover from before #43717 deleted `csrc/cache_kernels.cu`; `torch.ops._C_cache_ops.swap_blocks_batch` is registered from `csrc/libtorch_stable/torch_bindings.cpp` (`STABLE_TORCH_LIBRARY_FRAGMENT(_C_cache_ops, ops)`), i.e. the implementation in this diff. So #53971 + #53860 close the whole surface; they are complementary, not redundant.

Unlike #53860, this change is signature- and ABI-neutral, so no test updates are needed on the C++ side.

### 3. Reachability: three gates, which is why nobody has hit this deterministically

The over-read happens only when all three hold:

1. **the C++ op is selected** — `swap_blocks_triton.py` handles small CPU→GPU batches, so it is the larger transfers that fall through to `ops.swap_blocks_batch`;
2. **the call is on a non-default stream** — since #46379 the op falls back to per-copy transfers on the legacy default stream, so the batch path (and this bug) is skipped entirely there;
3. **`cnt > 1`** — with `cnt == 1` a scalar *is* a valid one-element array.

The offload copy backend satisfies (1) and (2) in normal configurations, and (3) whenever more than one block moves per call — thousands, in a typical offload step. Note that the over-read length scales with `cnt`, so the regime that reaches this code is also the regime that reads furthest out of bounds.

### 4. Failure modes: crash or spurious error, but no silently-wrong copy

With `numAttrs == 1` the only valid element value is `0`, so the over-read has three outcomes:

- trailing bytes happen to be zero → the call behaves exactly as intended (why this has survived CI, and why #40259 has no reproducer);
- they hold a non-zero value → invalid attribute index → the driver returns an error and the op raises `cuMemcpyBatchAsync failed at index N`;
- the read crosses into an unmapped page → SIGSEGV.

I don't want to overstate this: if a driver build does not validate `attrIdxs[i] < numAttrs`, it would instead index `attrs` out of bounds, which is a second-order over-read whose visible effect depends on neighbouring memory. Either way the caller hands the driver a pointer to an object `cnt` times too small, and that is the part this PR fixes.

### 5. Blast radius: two independent consumers

`swap_blocks_batch()` is a public op (`vllm/_custom_ops.py` → `torch.ops._C_cache_ops.swap_blocks_batch`) with two callers:

- `vllm/v1/kv_offload/cpu/gpu_worker.py` — KV block offload/restore;
- `vllm/distributed/ec_transfer/ec_connector/cpu/worker/__init__.py` — the erasure-coding transfer connector, which accumulates descriptors via `descriptor_buffers.py` and flushes them in one call (`flush_saves()` → `swap_blocks_batch(src_ptrs[:n], ...)`), where `n` is the number of EC blocks saved in that step. Its `cnt` is unbounded by design, and `is_src_access_order_any=True` at the other call site means it is specifically asking for the batch API's ordering hints.

### 6. Why the existing suite can't regress this, and what I can offer

- `tests/v1/kv_offload/cpu/test_swap_blocks_batch.py::test_swap_blocks_batch_dedicated_stream` **does** reach `cuMemcpyBatchAsync`, with `cnt == 3`, and passes — the over-read of two extra `size_t` slots is currently tolerated by luck of stack layout. Its default-stream sibling never reaches the batch path at all (§3, gate 2).
- On the Python side, `tests/v1/simple_kv_offload/test_hip_mem_ops.py` monkeypatches `_batch_memcpy`, so even its `(0, 61, 135) -> [8235]` case validates descriptor bookkeeping only and never asserts anything about `attrIdxs`. (I'm adding exactly that assertion in #53860, where the existing monkeypatch makes it cheap and deterministic.)

Being straight about the C++ side: a deterministic in-CI regression test is awkward here. The over-read is performed inside `libcuda`, not in instrumented vLLM code, so ASan/valgrind on our side won't see it, and a `PROT_NONE` guard page can't be injected around an array allocated inside the op. What I can offer, if maintainers want it:

- (a) a large-`cnt` dedicated-stream case (e.g. 1024–4096 descriptors × 64 KiB) so the offload regime is at least covered functionally — this is the configuration I verified locally: `mismatched bytes: 0`, byte-for-byte;
- (b) the standalone `cuGetProcAddress` harness I used (single `size_t` placed immediately before a `PROT_NONE` page, `count = 2`) as a `tools/` script, runnable manually rather than in CI. On this driver build (595.71.05) the read was not performed, so the probe demonstrates the contract violation rather than producing a fault — I'd label it as such rather than overselling it;
- (c) if someone knows a way to make this deterministic in CI, I'll implement it.

Happy to add (a) and/or (b) as a **second commit** — no force-push, no rewriting the existing one.
