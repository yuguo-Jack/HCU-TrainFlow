# [DSv4][Kernel] Add DSpark confidence-head fused TileLang kernel

[Upstream PR](https://github.com/vllm-project/vllm/pull/62840) · state: open · merged: False

## Original PR description

> **RFC**: https://github.com/vllm-project/vllm/issues/62839
> Draft implementation. Hold merge until the RFC discussion converges.

## Purpose

Add a fused TileLang kernel for the **DSpark confidence head** used by adaptive speculative decoding. The shape:

```
p_accept = sigmoid( ( [hidden_state ; markov_embed] @ W ) / temperature )
```

In main, per draft step, this is four CUDA launches — `cat`, `.float()` cast, cuBLAS GEMV, then `sigmoid` — plus an `(n, H + r)` fp32 temporary which defeats activation-checkpoint reuse and forces a re-allocation inside the CUDA-graph hot path on every decode step.

This PR introduces a single kernel that performs all four ops with a shared fp32 accumulator and emits the post-sigmoid result. It is the same fusion pattern DeepInfer uses in [`dflash.py`](https://github.com/deepseek-ai/DeepInfer/blob/main/deepinfer/model_executor/layers/tilelang_ops/cuda/dflash.py#L12-L72), kept at FP32 weights (unlike DeepInfer's bf16 cast) to preserve vLLM's numerical semantics.

- Kernel: `vllm/model_executor/kernels/dspark/` (TileLang + pure-PyTorch fallback)
- Dispatcher: `class DsparkConfidenceTileLangKernel(VllmJitKernel[CompileKey])`, pre-compiled at engine JIT warmup
- Custom op: `torch.ops.vllm.dspark_confidence_tilelang` exposed via `direct_register_custom_op` so CUDA-Graph capture sees a single opaque node
- Integration: `compute_confidence()` in [`vllm/model_executor/models/qwen3_dspark.py`](vllm/model_executor/models/qwen3_dspark.py) and [`vllm/models/deepseek_v4/nvidia/dspark.py`](vllm/models/deepseek_v4/nvidia/dspark.py) — falls back to the existing PyTorch path unchanged when the kernel declines (wrong dtype, stride, batch outside `[32, 2048]`, non-V4-Flash shape, no CUDA, no TileLang, etc.)

Platform gate: **NVIDIA Hopper (SM90) and later**. Earlier NVIDIA, ROCm and XPU keep the PyTorch fallback path since TileLang PDL is SM90+ and TileLang ROCm/XPU support is unstable on vLLM 0.32. Scope is DSpark-deepseekV4/Qwen3-DSpark (NVIDIA path); Gemma4-DSpark and K3-DSpark do not instantiate a confidence head and are unaffected.

**Dispatch gate (shape + batch floor)**. The fused path is *only* admitted when `(n_embed, markov_rank) == (7168, 32)` — the DeepSeek-V4-Flash production shape — and batch `32 ≤ n ≤ 2048`. Smaller DSpark variants (e.g. Qwen3-4B-DSpark at H=2560, r=256) see parity fused vs PyTorch across all measured batch configurations on consumer GPUs and a ~42 % regression on H200 sequential, so they now fall back to PyTorch (see RFC § "Batch + shape gate rationale"). This is a hardening of the gate from the initial draft.

**RFC discussion lives at [#62839](https://github.com/vllm-project/vllm/issues/62839)**. This PR ships the implementation, tests, and microbenchmarks.

### Micro-benchmark

Runs on vLLM 0.32.0, PyTorch 2.13.0+cu130, TileLang 0.1.12. Two GPUs covered:

- **RTX 5090** (Blackwell SM120, CUDA 13.0, driver 575): sweep covers `n ∈ {1, 32, 128, 512, 2048, 8192} × H ∈ {2048, 7168} × r ∈ {0, 8, 32}`, 200 iters each, 36 shapes.
- **NVIDIA H200** (Hopper SM90, 143 GB HBM3e, CUDA 13.1, driver 590.44.01): `n ∈ {32, 128, 512, 2048, 8192} × H ∈ {2048, 7168} × r ∈ {8, 32}`, 200 iters each, 20 shapes.

The live dispatch gate caps fused calls at `n ≤ 2048` — see RFC [#62839 "Dispatch gate"](https://github.com/vllm-project/vllm/issues/62839) for the conditions.

| Metric | RTX 5090 (SM120) | NVIDIA H200 (SM90) |
|---|---:|---:|
| Median latency speedup vs `compiled` | **1.92×** | **1.90×** |
| Min / max | 0.72× / 3.56× | 0.39× / 5.15× |
| Production dispatch range (n ≤ 2048) | 1.72× – 2.77× | 0.39× – 2.97× |
| Peak-memory delta (fused per call) | **0 B** | **0 B** |
| Median err_ratio vs `compiled` | **0.610** | **0.695** |

H200's wider min-max range reflects Hopper's launch overhead at small shapes (`n=32` sits at 0.39×); above `n=128` H200 pulls ahead of 5090 and reaches **5.15×** at `n=8192, H=7168, r=32`, where HBM3e bandwidth favors the fused kernel more than 5090's smaller cache.

### End-to-end batched sweep (5090, 4B shape — negative result that motivated the gate)

`Qwen/Qwen3-4B-FP8` target + `deepseek-ai/dspark_qwen3_4b_block7` drafter, greedy (T=0, seed=42), 64 tokens, on one RTX 5090. Single `llm.generate(list_of_B_prompts)` so vLLM batches inside the engine.

| Concurrent B | fused (s) | baseline (s) | fused / baseline |
|---:|---:|---:|---:|
| 32  | 0.414 | 0.422 | **0.98×** |
| 128 | 0.817 | 0.839 | **0.97×** |
| 256 | 1.445 | 1.467 | **0.99×** |

The fused path shows **parity** with PyTorch at every production-realistic batch on this shape — the kernel contributes ≤0.1 % of decode kernel time and the TileLang dispatch overhead cancels the GEMV savings. That parity combined with the observed H200 regression at the same shape is what motivated the shape-floor gate.

### E2E serving

**End-to-end smoke:** ran the branch under `vllm.LLM` with target `Qwen/Qwen3-4B-FP8` and draft `deepseek-ai/dspark_qwen3_4b_block7` on one RTX 5090, adaptive verification enabled, `load_format="dummy"`. Profiled with `llm.start_profile()` / `stop_profile()` (the vLLM-supported pattern — plain `torch.profiler` in the main process sees nothing because v1 runs inference in a separate EngineCore subprocess).

The trace shows the fused kernel invoked **64 times** across a 64-token decode (one per draft step, grid `[7,1,1]` matching `num_speculative_tokens=7`), **captured inside CUDA graphs** (`graph id` field present), at **1.70 µs median per launch**. Total 0.109 ms against 375 ms of kernel time across the trace — about **0.03 %**, which is why we're not claiming a TPOT-level win at production scale.

**Real-checkpoint behavioral A/B** on the same target/draft (real weights, not dummy): 30 diverse prompts × 64 tokens × greedy sampling (temperature=0, seed=42). Fused vs PyTorch fallback produces **0/30 divergent outputs on both RTX 5090 and H200** (bitwise-identical output text and token counts). Run logs land in the local evidence bundle; reproduce script available as `benchmarks/kernels/dspark/real_weight_ab.py` on request.

No serving benchmark table is included: the real DSpark production shapes (V4.1-Flash ≈ 300 GB packed, V4-Pro ≈ 880 GB at FP4/FP8 mix) need multi-GPU H200 per-replica. At ~0.03 % of decode kernel time this kernel is below `bench_serving` noise at that scale. Multi-H200 TPOT numbers would land as a follow-up comment — see "What's not here".

## What's not here

- **Multi-GPU production-shape TPOT (H200 × 8, V4.1-Flash)**: not covered. Kernel-side correctness on a single H200 SM90 is verified (sweep + unit tests + real-checkpoint A/B above); TPOT at production shape would land as a follow-up comment.
- **Systematic single-request wall-clock regression on H200 at the 4B shape** (~50 % slow): **no longer reachable**. The new dispatch gate rejects `(n_embed, markov_rank) = (2560, 256)` (see above), so the Qwen3-4B-DSpark configuration that triggered this regression now falls back to PyTorch. The root cause (per-call TileLang dispatch overhead on Hopper) is not eliminated in general; whether it stays within budget at the V4-Flash shape × batch ≥ 32 is a follow-up question. Reviewers may want a `vllm bench serve` repro at the V4-Flash shape before merge.
- **ROCm / XPU dispatch**: out of scope (`DSparkDeepseekV4Model` on those platforms loads but does not wire the head into inference yet).
- **Autotune** of `tile_n`/`split_k`: not implemented. Microbench shows the hand-picked `tile_n=256` is comfortably within noise of best across the sweep; welcome maintainer preference here.
- **Adaptive GEMV batch**: `_FUSED_MAX_BATCH = 2048` is conservative; H200 sweep shows a consistent win up to `n=8192` (5.15×) so a higher cap is feasible, but keeping it at 2048 matches realistic DSpark workload.
