# [Kimi-K3] Route the fp8 chunked-context K/V pack through FlashInfer where it has a fused kernel

[Upstream PR](https://github.com/vllm-project/vllm/pull/61527) · state: closed · merged: True

## Original PR description

## Purpose

Follow-up to #56881. FlashInfer now ships `concat_mla_kv_quant_fp8` (flashinfer-ai/flashinfer#5667, #6163, #6373): the same fused bf16 -> FP8 MLA context K/V pack that vLLM's private `fused_kimi_k3_mla_kv_concat_quant_fp8` does, byte-identical, behind one public library function so vLLM, SGLang and other FlashInfer consumers share it. Behind that API FlashInfer routes by head count: a hand-written kernel for 12 local heads (Kimi-K3's 96 heads over TP8) and generated Cake programs for every other head count.

This PR makes Kimi-K3's fp8 chunked-context pack call the FlashInfer API where it has a fused kernel, and keeps vLLM's kernel everywhere else.

## What changes

- `vllm/utils/flashinfer.py`: `has_flashinfer_concat_mla_kv_quant_fp8()`, the usual cached feature probe.
- `vllm/models/kimi_k3/nvidia/ops/fused_mla_key_concat_kv_cache.py`: `fused_mla_kv_pack_quant_fp8(kv_nope, k_pe, *, nope_dim)`. It calls FlashInfer when all of these hold: FlashInfer exposes the API, the inputs are bf16, `kv_nope` is contiguous (it is the `kv_b_proj` output), and the device is compute capability 10.x (where FlashInfer's fused backends are built). Otherwise it runs vLLM's `fused_mla_kv_concat_quant_fp8`: fp16 inputs, an fp8 `k_pe` gathered from a plain fp8 cache, pre-Blackwell GPUs, or a FlashInfer without the API.
- `vllm/models/kimi_k3/nvidia/mla.py`: both chunked-context paths (the layer's own loop and the DCP hook from #56881) call it for the fp8-query case. The bf16-query path and everything else are unchanged.

No new environment variables. FlashInfer's own `FLASHINFER_SPECIALIZED_KERNEL_DISABLE=1` forces its composable path if anyone needs to A/B inside FlashInfer.

## Performance

Kernel-level on GB300 in the Kimi-K3 deployment container (cold L2, median of 100, the same head-by-token grid as #56881's tables), FlashInfer's API vs vLLM's `fused_kimi_k3_mla_kv_concat_quant_fp8`:

| local heads | chunk tokens | FlashInfer vs vLLM kernel |
|---|---|---|
| 12 (TP8) | 16 to 131072 | 1.11x to 1.29x faster (hand-written kernel) |
| 1 to 128, not 12 | 1536 to 131072 | 1.06x to 1.26x faster (Cake programs; flashinfer-ai/flashinfer#6163 tables, B200 and B300) |

At 12 heads and the 66k-token serving chunk: 120 us -> 101 us. Byte-identical on every row (55 rows checked in the GB300 run, plus FlashInfer's own 65536-pattern cast test). End to end this is about 1 ms of a 93 ms engine step at 70 concurrent sessions, which is inside run-to-run noise on that route; the value is one shared kernel path rather than a per-framework copy.

New in `test_kimi_k3_mla_fused_epilogue.py`:
- `test_context_kv_pack_routes_to_flashinfer_only_where_it_serves`: with a stubbed FlashInfer, bf16 inputs on a served device go to FlashInfer with the nope split and the same bytes as vLLM's kernel; an fp8 `k_pe` or an unserved device run vLLM's kernel without touching FlashInfer.
- `test_context_kv_pack_flashinfer_route_is_byte_exact`: with a real FlashInfer that has the API, on compute capability 10.x, the two implementations produce identical bytes for the real prefill-context layouts (strided `k_pe`, 3 / 12 / 24 heads, 1 / 257 / 2048 tokens). Skipped elsewhere.

## Test Result

H100 (vLLM 0.31.0 wheel with this PR's four files overlaid, torch 2.13 + CUDA 13.0): `test_kimi_k3_mla_fused_epilogue.py` + `test_mla_prefill_context.py`: 46 passed, 9 skipped (the real-FlashInfer rows; that FlashInfer predates the API and the GPU is SM90). `ruff check` / `ruff format --check` clean.

## Scope

- Until vLLM picks up a FlashInfer release that includes the API (it is on FlashInfer `main` as of 2026-10-12), the probe is false and this PR changes nothing at runtime. Once it does, Blackwell deployments switch to the FlashInfer kernels automatically.
- Hopper and earlier always keep vLLM's kernel, which is built for SM90+.

AI assistance was used to prepare this change.
