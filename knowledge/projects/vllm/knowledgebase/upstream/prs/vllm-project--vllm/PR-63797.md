# [Frontend][Mistral] Pass response_format to mistral-common chat templating

[Upstream PR](https://github.com/vllm-project/vllm/pull/63797) · state: closed · merged: False

## Original PR description

## Overview

Passes the OpenAI `response_format` through the Mistral renderer into mistral-common chat templating: mistral-common 1.13 renders the requested output format into the v15 `[MODEL_SETTINGS]` block alongside `reasoning_effort`. Also accepts `response_format` on `/tokenize` so the rendered prompt can be inspected.

Not a duplicate: searched open PRs/issues for `response_format` + Mistral; the open items are structured-output bugs on other backends (e.g. #62483, #49095) and none forward `response_format` into the Mistral tokenizer's chat template.

## Claims

- The OpenAI `response_format` is converted to its mistral-common equivalent in the Mistral renderer and forwarded to the tokenizer.
- Only applied for v15+ tokenizers, so requests without it and older tokenizers render exactly as before.
- `response_format` is accepted on `/tokenize` for rendered-prompt inspection.

## Validation

- `python -m pytest tests/renderers/test_mistral.py tests/tokenizers_/test_mistral.py tests/entrypoints/serve/tokenize/test_serving_tokenization.py -v` — extended by this change and wired into CI.
- Requires mistral-common >= 1.13 for the format to reach the template; the forwarding is inert with older versions (same rendering as before).

## Details

- The conversion happens in the renderer (not the protocol layer) so the OpenAI-facing surface stays unchanged; the tokenizer only sees the mistral-common format.
- The `/tokenize` extension uses the same conversion, which makes the exact rendered prompt verifiable without a chat completion.

- sfeng33 · comment · 2026-10-26T18:12:34Z · [source](https://github.com/vllm-project/vllm/pull/63797#discussion_r4380817063)

File: `vllm/tokenizers/mistral.py` · line 72

`MistralResponseFormats.json` is the 1.11/1.12 name. On mistral-common main the enum is `text`, `json_object`, `json_schema`. So on the only version where line 14 imports, a `json_object` request hits AttributeError here and returns a 500. The tests use the same name. `MistralResponseFormats("json_object")` works on both.

- sfeng33 · comment · 2026-10-26T18:12:35Z · [source](https://github.com/vllm-project/vllm/pull/63797#discussion_r4380817307)

File: `vllm/renderers/mistral.py` · line 54

This runs the `MistralJsonSchema` validator (Draft-7 `check_schema`) outside the try in `safe_apply_chat_template` and, in the async path, on the event loop. A bad schema like `{"type": 123}` comes back as a raw pydantic error instead of the normalized mistral-common one, and a large schema blocks the loop. Can this move inside the executor call so it runs with the rest of the rendering?

- sfeng33 · comment · 2026-10-26T18:12:36Z · [source](https://github.com/vllm-project/vllm/pull/63797#discussion_r4380817493)

File: `vllm/entrypoints/serve/tokenize/protocol.py` · line 104

Chat runs `validate_response_format` on this field, tokenize does not. So `{"type": "json_schema"}` with no schema is a 400 on chat but a 200 here with no `[MODEL_SETTINGS]` block. That makes /tokenize show a different prompt than chat would send. Can we reuse the chat validator here?

- sfeng33 · comment · 2026-10-26T18:13:55Z · [source](https://github.com/vllm-project/vllm/pull/63797#discussion_r4380830740)

File: `vllm/tokenizers/mistral.py` · line 14

`JsonSchema` and `ResponseFormats.json_schema` only exist on mistral-common main. The latest release is 1.12.0 and does not have them, so with our `>= 1.11.6` pin this module fails to import and every Mistral, Pixtral and Voxtral model stops loading. Is the plan to wait for a mistral-common release and bump the pin in this PR first?
