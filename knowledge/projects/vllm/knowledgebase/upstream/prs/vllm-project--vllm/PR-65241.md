# [Bugfix][Kernel] Add __syncwarp before the lane-0 stores in the fused KDA decode block reductions

[Upstream PR](https://github.com/vllm-project/vllm/pull/65241) · state: open · merged: False

## Original PR description

## Overview

In `csrc/kimi_k3/fused_kda_decode_kernel.cu`, the two pairwise block reductions let lane 0 of warp 0 overwrite `scratch[0]` and `scratch[1]` right after the warp reads the per-warp partials from the same buffer. Lane 1 reads `scratch[1]`, and nothing orders that read before lane 0's store. This PR adds one `__syncwarp()` before the stores in each function. TensorRT-LLM made the same change to the same two functions in its copy of this kernel ([NVIDIA/TensorRT-LLM#19830](https://github.com/NVIDIA/TensorRT-LLM/pull/19830)).

## Claims

- Removes an intra-warp shared-memory race in `block_reduce_sum2_for` and `block_reduce_sum2_active_for`. compute-sanitizer racecheck reports it on main and reports no hazards with this change.
- Outputs do not change: they are bitwise identical before and after on B200.
- No measurable latency change. The fix adds one `WARPSYNC` instruction per kernel.

## Validation

Setup: one B200, driver 580.173.02, CUDA 13.0, compute-sanitizer 2025.3.1. vLLM at 3d81a51 with `_C_stable_libtorch` built from source (`TORCH_CUDA_ARCH_LIST=10.0`, Release), without and with this patch. The other extensions come from the precompiled wheel.

Commands, from the repo root:

```bash
# Test, both builds: 10 passed
python -m pytest -q tests/models/kimi_k3/test_kda.py::test_fused_kda_decode_correctness -k native
# Reproducer: 2400 racecheck warnings on main, 0 with this PR
compute-sanitizer --tool racecheck --racecheck-report hazard \
  python -m pytest -q tests/models/kimi_k3/test_kda.py::test_fused_kda_decode_correctness -k native
# Latency, three runs per build in alternating order
python benchmarks/kernels/benchmark_kimi_k3_kda_decode.py --graph --heads 12 24 48 96 --tokens 1 8 32 128
```

The output comparison is a short script that builds the test's inputs, calls `ops.fused_kda_decode` with each build, and compares the saved tensors byte by byte.

- **racecheck.** All 2400 warnings on main are `(Warp Level Programming) Potential WAR hazard` records in `kda_decode_fusion_many_heads_kernel`: read by thread (1,0,0), written by thread (0,0,0), at the 4 bytes of `scratch[1]` (`__shared__ 0x8e04`–`0x8e07`). That is one record per byte for each of the 600 CTAs in the 10 test cases. vLLM builds this file without `-lineinfo`. A standalone `-lineinfo` build of the same file attributes the pair to `block_reduce_sum2_for<8>`: the read of `scratch[lane]` at [L185](https://github.com/vllm-project/vllm/blob/3d81a510f9ebc802a7864ced38832182295f4cad/csrc/kimi_k3/fused_kda_decode_kernel.cu#L185) and the store `scratch[1] = block_y` at [L191](https://github.com/vllm-project/vllm/blob/3d81a510f9ebc802a7864ced38832182295f4cad/csrc/kimi_k3/fused_kda_decode_kernel.cu#L191).
- **SASS.** In that standalone build, this PR adds exactly 128 instructions over the 128 kernel instantiations, all `WARPSYNC`. The `BAR.SYNC` count is unchanged.
- **Latency.** The largest difference is +0.02 µs (for example 96 heads, 1 token: 5.27 → 5.29 µs). Per-configuration numbers are in the table below.
- **Verifier.** We found the race with a PTX-level synchronization and race verifier we are developing ([gpu-verifier/sentryward](https://github.com/gpu-verifier/sentryward)). On `kda_decode_fusion_many_heads_kernel` (12 heads, `sm_100f`, CUDA 13.2), it reports the same pair: `ld.shared.b32` by thread 1 and `st.shared.b32` by thread 0 on `scratch[1]`, with no happens-before order. With `bar.warp.sync -1` inserted before the stores, the result is `race_free`.
- **Tests.** No new test. The race does not change outputs, so a unit test cannot tell main from this PR; the racecheck run above is the reproducer, as in NVIDIA/TensorRT-LLM#19830. The existing test runs in the `(B200) Kimi K3` CI step, which changes under `csrc/kimi_k3/` trigger.
- **Not run.** End-to-end serving and model evaluation: we have one B200. The kernel outputs are bitwise identical, so model outputs do not change.

## Details

`block_reduce_sum2_for` ([L168–L196](https://github.com/vllm-project/vllm/blob/3d81a510f9ebc802a7864ced38832182295f4cad/csrc/kimi_k3/fused_kda_decode_kernel.cu#L168-L196)) on main (3d81a51):

```
if (warp == 0) {
  block_x = lane < kReduceWarps ? scratch[lane] : 0.0f;                 // lane 1 reads scratch[1]
  block_y = lane < kReduceWarps ? scratch[kReduceWarps + lane] : 0.0f;
  block_x = warp_reduce_sum(block_x);                                   // __shfl_xor_sync only
  block_y = warp_reduce_sum(block_y);
  if (lane == 0) {
    scratch[0] = block_x;
    scratch[1] = block_y;                                               // lane 0 writes scratch[1]
  }
}
```

- Root cause: the `__syncthreads()` before this block orders the per-warp writes before these reads, and the one after orders the final stores before every thread reads the result. Nothing orders lane 1's read of `scratch[1]` before lane 0's store to it. Shuffles do not order shared-memory accesses.
- Why outputs are correct today: lane 0's totals depend on lane 1's loaded value through the shuffles, so in practice the load returns before the store. That is a data dependency, not an order the CUDA memory model guarantees; `__syncwarp()` provides the order.
- `block_reduce_sum2_active_for` ([L230–L262](https://github.com/vllm-project/vllm/blob/3d81a510f9ebc802a7864ced38832182295f4cad/csrc/kimi_k3/fused_kda_decode_kernel.cu#L230-L262)) has the same sequence. The current launcher instantiates only `block_reduce_sum2_for`. The patch fixes both, so the active variant stays correct if it is enabled.
- The single-value reductions (`block_reduce_sum`, `block_reduce_sum_active_for`) do not have this problem: lane 0 writes only `scratch[0]`, which only lane 0 reads. The ROCm copy (`fused_kda_decode_kernel_rocm.cu`) does not have this pattern either: its `block_reduce_sum3` stores the totals at `scratch[3 * kGroups]` and after, past the partials that the lanes read.
- Base: the branch is rebased onto main 28dd9c3 (2026-11-02). `csrc/kimi_k3/` is unchanged between 3d81a51, where we ran the validation above, and 28dd9c3.
- Duplicate check: no open PR touches this file. We searched open PRs and issues for `fused_kda_decode`, `syncwarp` and `kda race`.
