# [ROCm][Perf] W4A16: speed up skinny GEMM decode, including speculative batches

[Upstream PR](https://github.com/vllm-project/vllm/pull/57199) · state: closed · merged: True

## Original PR description

## Summary

Tunes the W4A16 skinny GEMM decode path on gfx115x, and stops routing deep-K decode shapes away from it.

The kernel compiles for gfx11 and gfx12, and everything here was measured on gfx1151, so **every commit gates itself to gfx115x** -- the tuning and the routing alike. Off gfx115x the kernel runs exactly as it does today: the K * N bound stays at 1.2x LDS, the chunked path never launches, every tuple takes the checked K loop, the zero point keeps its own pass over the unpacked values, and the dispatch keeps its current tuples. The Python side gets an `on_gfx115x()` platform helper so the layer routes to match the C++ host check.

Eight commits, each measured against its parent on gfx1151 / ROCm 10.2, median of 3 passes:

| commit | what | effect |
|---|---|---|
| test coverage | asymmetric path and batch 4/5 at the op level | — |
| K loop | instantiate the whole-block loop without the bound check | mean **+18.9%**, 44 of 46 cells |
| zero point | fold it into the fp16 dequant constants | up to **+28.8%** at batch 1, asymmetric |
| group stride | scale and zero-point rows get their own row stride, HIP and Triton | — |
| LDS bound | stop rejecting K * N past the LDS budget | **+67% / +90%** on the shape that crosses it |
| chunked K | walk K in LDS-sized chunks so every activation row stays in LDS | **+30.5% / +51.7%** at batch 4, deep K |
| dispatch rules | avoid trimming wave slots, widen loads for deep-K batch 1 | **+9.4% to +16.3%** |
| LDS band | store the chunked activation band piece-major, conflict-free | **+1.9%** mean on chunked shapes |

## Results

The speculative-decode rows carry the routing change: today any shape with K * batch past the LDS budget goes to the Triton prefill kernel, which at N=3 and K=16384 runs at 30% of bandwidth. Run-to-run spread is under 4% on every cell except that one, where it is 7.6%; the effect there is an order larger.

⁽¹⁾ Above 100% because the denominator charges scales and zero points to DRAM; for this shape that working set is 18 MB and fits the 32 MB MALL. The weight stream alone is 115.6 MB in 499.2 µs, 232 GB/s, which is the board's practical ceiling.

## Accuracy

GSM8K, full 1319 questions, 5-shot, greedy, seed 42, on `Qwen/Qwen3-8B-AWQ` with `max_num_seqs=4`:

| | main | this branch |
| :--- | :--- | :--- |
| strict-match | 0.8582259287338894 | 0.8582259287338894 |
| flexible-extract | 0.8612585291887794 | 0.8612585291887794 |

Identical to the last digit, so every one of the 1319 answers matches. `max_num_seqs=4` is load-bearing: Qwen3-8B has K = 4096 and K = 12288, so at batch 1 nothing crosses the LDS budget and none of the routing changes engage. At batch 4 the down projection gives K * N = 49152, which goes to Triton today and stays on the chunked path here -- the eval runs straight through the largest behavioural change in the series and produces the same output.

The deep-K tuple is not covered by this eval, and cannot be by any Qwen3-8B: it needs K divisible by 8192, and this model has neither. It is covered at the op level instead, by test cases at K = 8192 and K = 16384.

## End to end

`cyankiwi/gemma-4-31B-it-AWQ-4bit` served on gfx1151, 328 in / 256 out, 10 prompts each carrying one 640×480 image, batch 1:

| | main | this branch | |
| :--- | :--- | :--- | :--- |
| **TPOT** | 120.7 ms | **107.4 ms** | **−11.0%** |
| **Decode throughput** | 7.65 tok/s | **8.49 tok/s** | **+11.0%** |
| End-to-end latency | 33.47 s | 30.15 s | −9.9% |
| TTFT | 2691 ms | 2762 ms | +2.6% |

TTFT is prefill. Routing there is unchanged, and the Triton kernel's arithmetic is too, but its scale and zero-point addressing now goes through a row stride instead of assuming K / group_size; for a contiguous tensor that stride is the same value and the generated code is unchanged.

This understates the series: at batch 1 on an AWQ checkpoint the chunked path, the wave-packing rule and the deep-K tuple all stay inactive, so the number above comes from the first four commits alone. The last three target speculative decoding and deep-K projections, which this configuration does not exercise.
