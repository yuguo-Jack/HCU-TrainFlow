# [Rust Frontend] Choose chat content format by probing the template

[Upstream PR](https://github.com/vllm-project/vllm/pull/64042) · state: closed · merged: False

## Original PR description



## Overview

With `--chat-template-content-format auto` (the default), the Rust HF renderer decides from the template's Jinja AST whether `message.content` reaches the template as a string or as OpenAI content parts: any loop over message content selects parts for every message. Many templates loop over parts only for user messages and print system, assistant, or tool content directly, so the part list leaks into the prompt. This PR replaces the AST walk with a render probe: each template is rendered with small probe conversations, and each request gets parts only if the template renders parts for every message in it.

## Claims

- Multi-turn tool calling no longer prints tool results as a part list for templates that render tool content directly. On `main`, GLM-4.5/4.7/5 render `<tool_response>{"type": "text", "text": ...}</tool_response>`, and Ministral 3 and Devstral 2 render `[TOOL_RESULTS][{"type": "text", ...}][/TOOL_RESULTS]`.
- Templates that take parts only for user messages (InternVL2.5, GLM-4.1V, Gemma 4, cogito, and others) get strings for requests with system or assistant messages, instead of a printed part list or dropped content.
- Media parts a template ignores (audio in Nemotron-Nano-12B-v2-VL) fall back to strings, so the model's media placeholder still reaches the prompt.
- On 375 distinct public chat templates rendered through the Rust renderer, `auto` picks a working format for 99.9% of (template, request shape) pairs, up from 97.0% on the base branch.

New tests in `vllm-chat` `renderer::hf`:

- `format::tests::content_format_per_capabilities_and_request` is a table of the chosen format for 7 hand-written capability sets × 11 request shapes (each role, each media modality, developer messages), covering every branch of the per-request choice.
- `format::tests::probes_chat_template_constructs` probes 15 short templates, each distilled from a public model's template down to the construct that decides the format: printed tool, system, or assistant content; skipped audio parts; parts without a string branch (LLaVA-1.5); an audio-only template (Qwen3-ASR); a template that renders only with tools; `bos_token` concatenation (Llama 3); a macro bound to `message.content` (MiMo-V2.5); and a template that accepts only its own input format (TranslateGemma). It replaces the snapshot over vLLM's example templates, which were copied into `rust/src/chat/tests/templates/vllm_examples/` only for the AST detection and are removed.
- `tests::chat_template_renders_roles_without_part_support_as_strings` checks the final prompt for a template that takes parts only in user messages; it fails on the base branch. `tests::chat_template_probes_render_with_special_tokens` fails if the renderer does not pass its special tokens to the probe.
- Mutation checks: making tool messages always accept parts, removing the retry with a tool, or removing the parts-only fallback each fails at least one of the two tables.

Offline corpus (outside the repo): 375 distinct chat templates from the public checkpoints of first-party Hub organizations, each rendered through this branch's Rust renderer under `auto`, forced `string`, and forced `openai` for 9 request shapes (user, system + user, multi-turn, multi-part text, tool round trip, image, audio, system + image, multi-turn with image). A forced render is acceptable when it keeps every text marker in order, prints no part list, and, for media, places the media. 97 templates were added after the probe was last changed and serve as a held-out set.

| `auto` | acceptable (all) | templates with a failure | acceptable (held-out 97) |
|---|---:|---:|---:|
| base (#63963, AST detection) | 97.0% | 40 | 96.2% |
| this PR | 99.9% | 2 | 100% |

Nine of the base failures are image-only models scored on the audio shape (their architectures do not declare modalities); the other 31 are the cases in Claims. The two remaining failures are Apriel-1.5/1.6, which fail every conversation with an assistant message in either format: MiniJinja raises on `undefined|length`, where Jinja2 returns 0. That is a separate MiniJinja compatibility issue.

No model evaluation was run: the change only alters which format a template receives, and the corpus checks the rendered prompts directly.

## Details

**Probe.** `ContentCapabilities` renders the template with the renderer's special tokens and default template kwargs:

- a plain-string user message;
- text parts in a user, system, assistant, and tool message;
- image, video, and audio parts, each compared with the same message without the part.

A probe passes when the render succeeds, contains every probe text, and prints no part list. If nothing renders without tools (a `tool_use` template, or a tool-only template used as the default), the template is probed again with one tool.

**Per-request choice.**

- Parts when every message's role passed its text-part probe and every media part's modality passed its probe. For a user message with media, only the media probes count, so an ASR template that drops text still receives its audio parts.
- Otherwise strings, unless the template renders parts and not strings.
- A template that renders none of the probes gets strings, with a warning at startup.
- Developer and custom roles are not probed, so a request with them uses strings when the template accepts strings.
- An explicit `--chat-template-content-format` is unchanged.

**When it runs.** Each template is probed once when it is compiled. `HfChatRenderer::new` now takes the special tokens, since a template like Llama 3's (`bos_token + content`) fails to render without them: across the corpus, probing without tokens changes the result for 14 templates. A per-request `chat_template` override is compiled per request, as before, and is now also probed per request under the request-template fuel limit. Release-build micro-benchmark over the 375 templates (median of 31 runs, 4-message text request):

| | p50 | p90 | max |
|---|---:|---:|---:|
| compile | 63 µs | 190 µs | 362 µs |
| probe | 59 µs | 161 µs | 404 µs |
| render, model template | 10 µs | 25 µs | 61 µs |
| override request, `string` (compile + render) | 73 µs | 213 µs | 410 µs |
| override request, `auto` (compile + probe + render) | 136 µs | 421 µs | 849 µs |

Python caches the compiled template and the detected format (`lru_cache`); Rust caches neither for overrides. A small cache of compiled override templates would remove both costs, since the capabilities live on the compiled template; that is left for a follow-up.

**Scope.** Rust frontend only; the Python frontend's detection is unchanged. The user docs describe `auto` as best-effort detection, which still holds.

**Related PRs.** #63974 (merged) changes how Rust joins text parts under the string format; it is independent of which format is chosen. #63901 (merged) maps developer messages to system messages for templates without a developer role; the probe still treats developer messages as unprobed. #39630 special-cases GLM tool results in Python's detection; this PR covers that case for Rust without model-specific rules.

**Diff size.** Most of the deleted lines are the 33 removed example-template copies. Non-test code: about +375/−230 lines across `format.rs`, `template.rs`, and `mod.rs`, mostly the probe replacing the AST walk.

Not a duplicate: no open PR changes the Rust frontend's content-format detection.
