# [ROCm][Perf] Build AITER MLA full-graph decode metadata in one kernel

[Upstream PR](https://github.com/vllm-project/vllm/pull/65132) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Under full CUDA graphs, `AiterMLAMetadataBuilder._build_decode` fills the persistent decode metadata buffers (`graph_seq_lens`, `paged_kv_indptr`, `qo_indptr`, and for adaptive verification the varlen q/o row maps) with 10-25 small eager ops per build. This PR does it in a single Triton kernel, `_build_decode_indptr_kernel`, on the non-DCP full-graph decode path.

No open PR covers this: #65022 (split metadata lifetime) and #64560 (decode q absorb/quant fusion) touch the same backend but not this metadata build; #61504 / #58352 target the sparse MLA backend.

## Claims

Kimi-K3 official recipe (TP8, DSpark MTP 7 tokens, fp8 KV, `FULL_AND_PIECEWISE`), MI355X, per decode metadata build:

| Mode | Kernels | GPU time | Host time (p50) |
|---|---|---|---|
| uniform MTP (recipe default) | 11 → 4 | 60.2 → 40.6 µs (-33%) | 211 → 158 µs (-25%) |
| adaptive verification (varlen) | 24.5 → 4.7 | 134.7 → 48.4 µs (-64%) | 342 → 163 µs (-52%) |

- Outputs are bit-identical to the eager build (the only difference is the never-read dump slot of the varlen o-row map).
- No new host/device synchronization.
- DCP (`dcp_world_size > 1`) keeps the existing eager path unchanged.
- Faster than the eager ops at every `max_num_seqs` up to 1024 and every batch size (microbenchmark below); end to end, decode steps are 0.2-0.56% faster at concurrency 1-8 and unchanged within noise at 16-64.

They also assert that DCP batches never launch the fused kernel and that an oversized batch is rejected.

**Kernel cost vs `max_num_seqs`** (MI355X, one GPU, 8 query tokens per request, GPU time = sum of kernel durations per build from torch profiler):

| Mode | `max_num_seqs` | batch 1: eager → fused | half: eager → fused | full: eager → fused |
|---|---|---|---|---|
| uniform | 8 / 64 / 256 / 512 | 25 → 2.0 µs | 25 → 2.0 µs | 21-23 → 2.0 µs |
| uniform | 1024 | 26 → 2.3 µs | 27 → 2.5 µs | 24 → 2.8 µs |
| adaptive | 8 / 64 | 61 → 2.0 µs | 59 → 2.1 µs | 56 → 2.1 µs |
| adaptive | 256 | 63 → 3.6 µs | 64 → 3.6 µs | 67 → 3.7 µs |
| adaptive | 512 | 64 → 5.0 µs | 70 → 5.1 µs | 71 → 5.2 µs |
| adaptive | 1024 | 66 → 8.1 µs | 76 → 8.2 µs | 78 → 8.5 µs |

The single program is sized by `max_num_seqs`, so its cost grows with the buffer rather than the live batch, but it stays 8-30x cheaper than the eager ops everywhere. Host launch time is ~17 µs fused vs 77-213 µs eager, independent of `max_num_seqs`. (The eager reference here rebuilds its row ids each call, so its varlen kernel count is slightly higher than in the builder.)

**Serving correctness** (Kimi-K3 recipe, gsm8k 5-shot, full 1319 questions, greedy). A shadow check also re-verified after every build that all page indices past the live pages are -1 (uniform/adaptive: thousands to 16k builds per rank, 0 mismatches).

|---|---|---|
| uniform | 94.92% | 95.38% |
| adaptive | 94.92% | 95.83% |
| DCP=8 / DCP=8 + adaptive (first 400 questions) | - | 98.5% / 98.25% (fused path not taken, as expected) |

**End-to-end** (decode step period p50, main vs this PR, ABBA interleaved, server restarted per leg, 512 output tokens per request, 8 × concurrency requests per window). The step period is used instead of TPOT because DSpark acceptance length varies by ±8% across runs, which swamps TPOT and throughput at this effect size.

| Config | Concurrency | Step period | Change | Pairs | Paired t |
|---|---|---|---|---|---|
| recipe (`--max-num-seqs 8`) | 1 | ~18.0 ms | -0.20% | 4 | -1.4 |
| | 4 | ~23.8 ms | -0.44% | 4 | -2.7 |
| | 8 | ~28.6 ms | -0.56% | 4 | -2.3 |
| `--max-num-seqs 64`, graph sizes to 512 | 16 | ~39.2 ms | -0.12% | 4 | -0.6 |
| | 32 | ~53.0 ms | +0.14% | 8 | +1.9 (n.s.) |
| | 64 | ~78.2 ms | 0.00% | 4 | 0.0 |

At concurrency 32 the first 4 pairs read +0.24% (t = 3.3); a rerun of 4 more pairs read +0.03% (t = 0.3), so the pooled 8 pairs are within noise. As expected, the ~20-100 µs saved per step is a shrinking share of the step at high concurrency. The concurrency 8-64 runs load weights with `SAFETENSORS_FAST_GPU=0` (same for both arms) so server restarts reuse the page cache.

An earlier revision (which additionally replaced the full `paged_kv_indices.fill_(-1)` with a tail reset) measured -0.46% at concurrency 1 over 6 pairs (t = -4.7). That part was dropped to keep this PR small: the remaining `fill_` costs 7.8 µs per build.

Kernel and host numbers come from torch profiler traces of the serving run (decode builds inside the graph-replay window), with host time measured around `_build_decode` before profiling starts.

## Details

- The fused path is gated on full CUDA graphs, `self.dcp_world_size == 1` and no DCP total lengths; everything else keeps the existing code. A batch larger than the graph buffers is rejected by an assert (the eager ops rejected it too).
- `num_reqs` is excluded from Triton specialization (`do_not_specialize`) so new batch sizes do not trigger a JIT compile while serving.
- The kernel runs as a single program sized `next_power_of_2(max_num_reqs + 1)`: it writes kernel KV lengths and their zero-prefixed cumsum, the query indptr (uniform when padded), the tails up to the buffer length, and for varlen the q/o row maps.
- In the varlen case the row maps are left-aligned, which is always the case without DCP after #62990.
- `_expand_page_indices_kernel` now reads `kv_indptr` from the persistent buffer, which holds the same values as the old temporary.
- Gains are per decode step, so they matter most at low concurrency and with adaptive verification. The remaining biggest cost per build is AITER's own `get_mla_metadata_v1` (~28 µs), which this PR does not touch.
