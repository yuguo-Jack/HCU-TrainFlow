[Upstream PR](https://github.com/vllm-project/vllm/pull/63631) · state: open · merged: False

## Original PR description

# Match GPTQ dynamic patterns against all module-name forms

Fixes #63630

## Why

For multimodal-wrapped checkpoints (Qwen3.5-VL family), one module has three names across vLLM: the on-disk checkpoint form (`model.language_model.layers.0...`, the GPTQModel convention used to author `dynamic` patterns), the `hf_to_vllm_mapper`-mapped form (`model.layers.0...`), and the constructed module-tree form (`language_model.model.layers.0...`). `get_dynamic_override` matched patterns against the module-tree form only, so `-:`/`+:` entries authored in either other form silently never matched — the module stayed quantized and boot failed later with an unrelated-looking loader error (tracebacks in the linked issue).

## What

- `gptq_utils._dynamic_name_variants(name)`: for a name starting with one of the known wrapper prefixes, produce the other two forms; otherwise return the name unchanged.
- `get_dynamic_override` tries each pattern against every variant (both `-:` and `+:` branches). Unmatched names keep the previous default behavior. No pattern semantics change for models where the three spaces coincide (single-variant list).

## Test

`tests/unit/test_gptq_dynamic_ignore_name_forms.py` (CPU-only, no model build): cross-form matching in both directions, suffix patterns, defaults preserved, positive overrides, and the variant helper itself. All six tests pass on v0.30.0 with the fix; they fail on the unpatched tree in the cross-form cases.

## Verified against

vLLM v0.30.0 (`ced6857afa`), Qwen3.5-family 27B GPTQ INT4 checkpoint with mixed dense bf16 tensors: patterns authored in checkpoint form now exclude the targeted modules at construction, and the checkpoint loads.

- davetha · comment · 2026-10-26T05:33:18Z · [source](https://github.com/vllm-project/vllm/pull/63631#issuecomment-6409002024)

Deeper findings from validating the fix end-to-end on a Qwen3.5-family 27B GPTQ checkpoint with mixed dense bf16 + INT4 tensors:

1. Beyond the three-name-space mismatch, there is a second silent-failure mode: `get_dynamic_override` uses `re.match` (start-anchored), so any dynamic pattern written **without** a leading `.*` (e.g. `-:layers\.0\.self_attn\.q_proj$`) never matches any of the three name forms, because every form carries a wrapper prefix. The updated `_dynamic_name_variants` now also yields the prefix-stripped name, so anchored patterns match naturally; new test `test_re_match_anchor_pattern_matches_via_variants` covers it.
2. With both fixes in place, mixed dense/quantized checkpoints load end-to-end on v0.30.0: `dynamic` negative entries for **fused** modules (`self_attn.qkv_proj`) now make them construct dense (`get_linear_quant_method` returns `UnquantizedLinearMethod`), and dense bf16 `qkv_proj.weight` tensors on disk load into `QKVParallelLinear`. Verified with a live 12-module-promotion checkpoint boot.

The combination (name-space variants + anchor-safe matching) is what actually unblocks selective-precision GPTQ for multimodal-wrapped checkpoints; either alone still fails.
