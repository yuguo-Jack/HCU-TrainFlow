# [Bugfix][Kernel] persistent_topk: don't select float4 tail lanes past the row length

[Upstream PR](https://github.com/vllm-project/vllm/pull/62467) · state: closed · merged: True

## Original PR description




## Overview

FIX #62466

`histogram_2048_topk` in `csrc/persistent_topk.cuh` can return indices `>= seq_len`. This happens when the row length is not a multiple of 4 and the top-k threshold lands in the fp16 `-inf` bin. This PR skips lanes past `seq_len` in the collection loop and adds a regression test.

## Claims

- `persistent_topk` no longer returns indices past the row length on the `histogram_2048_topk` path (k < length <= 8192, at most 32 rows).
- The out-of-bounds reads of `logits` in the refinement pass are gone.
- Rows with length % 4 == 0 and rows whose threshold is above the `-inf` bin are unchanged. The guard only drops lanes that were never real elements.

## Details

Root cause. The last float4 load of a row (`load_float4_predicated`) fills the lanes past `seq_len` with `-inf`. They are binned like real elements. The collection loop gates candidates only on `vec_valid = i < n_vec`. When fewer than k in-row scores are above the `-inf` bin, the threshold is that bin, so the tail lanes become "equal" candidates. Refinement then reads `logits[idx]` for them and can output them.

Fix. Add `in_range = vec_valid && elem_idx < seq_len` and use it for `is_above` and `is_equal`. Tail lanes still count in the histogram, but that does not move the threshold. They only add to the `-inf` bin, the lowest non-NaN bin, so the counts above it are unchanged. And since `seq_len > k`, the in-row elements alone already reach k at the `-inf` bin.

Reachability, and why there is no end-to-end repro. The kernel path needs a decode row with k < length <= 8192, at most 32 rows, and the persistent backend. The persistent backend is picked by `--sparse-indexer-topk-backend persistent`, by `auto` on SM12x and pre-SM90 GPUs, or by `auto` when the logits row stride is not divisible by 4. The bug also needs fewer than k in-row scores above the fp16 `-inf` bin. I checked every in-tree caller:

- DeepSeek V3.2 / GLM-5 style DSA decode (`sparse_attn_indexer`): in-row scores come from `fp8_fp4_paged_mqa_logits` and are finite. Prefill uses `top_k_per_row_prefill`, not this kernel.
- Qwen4-exp QSA: scores are sums of ReLU terms, so they are finite and >= 0.
- Step5 rejects the persistent backend.
- DeepSeek V4.1 `apply_candidate_mask` does write `-inf` inside decode rows. But the shipped DeepSeek-V4.1-Flash config keeps 2048 candidate blocks of 8 tokens (16384 positions) on full-length (`compress_ratio` 1) layers. Every row on this path (<= 8192) is therefore fully covered.

So no shipped model reaches the bug with default or near-default flags. Reaching it needs a config with `candidate_topk_blocks * candidate_block_size < index_topk`, or more than `length - k` scores at or below about -65504. The layer-level script in the issue shows the V4.1 composition (`apply_candidate_mask` then `SparseIndexerTopk("persistent")`) with such a candidate set. If the bug were hit, `triton_convert_req_index_to_global_index` only drops `tok < 0`, so the result would be wrong KV slots with no error.

`cooperative_topk`, `histogram_256_topk` and the radix path are not affected. I checked lengths 8193 to 70001 with all-`-inf` rows on main and saw no bad indices.

Performance: one extra compare per element in the collection loop. No measurable change expected; not benchmarked.
