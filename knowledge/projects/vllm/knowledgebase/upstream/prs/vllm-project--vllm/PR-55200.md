# [Bugfix][Pooling] Reject prompt-wide truncation for Jina ranking

[Upstream PR](https://github.com/vllm-project/vllm/pull/55200) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

Reject prompt-wide truncation for Jina ranking and remove nested reserved markers from user text before formatting the query and documents.

## Claims

- Reject `truncate_prompt_tokens` through Jina's offline and HTTP entry points before inference, including limits that would leave the prompt unchanged.
- Preserve `max_tokens_per_query` and `max_tokens_per_doc` for scoring.
- Prevent nested reserved markers in queries, documents, or instructions from changing ranking cardinality.

## Validation

The focused pooling suites and scoped pre-commit hooks pass. The committed offline and HTTP model-test helpers fail against the previous head `df2cf312cf` and pass with this change. Existing score and embedding reference comparisons still pass.

Run the related suites in a configured development environment:

```sh
.venv/bin/python -m pytest tests/entrypoints/pooling
.venv/bin/python -m pytest tests/models/language/pooling
```

Before the change, the offline truncation regression reports `Failed: DID NOT RAISE VLLMValidationError`, and nested marker text fails the clean-input comparison. The fixed checks cover `LLM.encode`, `LLM.score`, `/pooling`, `/score`, and `/rerank`, including HTTP 400 with `param="truncate_prompt_tokens"`. Separate query/document limits match client-truncated inputs.

The GPU smoke used jina-reranker-v3 with BF16, MRV2, eager execution, context 1024, and an RTX 5070 Ti. It reused precompiled native extensions and a Humming overlay, with FlashInfer autotuning disabled. Local Torch is 2.13 rather than the branch's 2.14 pin. The model regressions are selected by optional nightly Extended Pooling. Full model evaluation and upstream GPU CI remain unrun.

## Details

Jina formats the query and documents into one prompt. Truncating that combined prompt cannot express separate query and document limits and can remove ranking markers. Reject the option in the shared Jina processor; scoring callers can use the per-query/document limits, and token-embedding callers can truncate each input on the client. The restriction is local to Jina.

Sanitization runs until no reserved marker remains because removing an inner marker can expose another marker around it. The model documentation now describes the truncation restriction and supported alternatives.

No competing Jina truncation fix was found. #61363 and #61524 concern generic renderer behavior; #55359 concerns Sentence Transformers configuration.

<details>
<summary>Why this was flagged</summary>

A `/rerank`, `/score` or `/pooling` caller sends a document containing `<|embed<|embed_token|>_token|>`. `format_docs_prompts_func` runs `sanitize_input` (io_processor.py:888-890), which strips the inner marker once and leaves a real `<|embed_token|>` in the prompt. The new `render` (io_processor.py:847) counts markers in that already-formatted prompt, so `num_docs` includes the injected marker. The rendered token IDs match that count, so the guard at io_processor.py:857-860 passes. `_post_process` then returns one cosine score per marker, so callers get scores that no longer line up with their documents. The same nesting with `<|rerank_token|>` now produces a misleading "Truncation removed query or document markers" 400 even when no truncation was requested. The single-pass sanitizer is pre-existing. The PR's stated goal is to keep embeddings matched to the original documents, but the new guard cannot catch this case because it trusts the prompt's own marker count.

**Verification:** pre-existing. `sanitize_input` (io_processor.py:888-891) makes one `text.replace(token, "")` pass per special token, so `<|embed<|embed_token|>_token|>` becomes a real marker. `render` counts `num_docs = prompt.count("<|embed_token|>")` (line 847), so the check at lines 858-861 passes and `_post_process` emits more scores than documents. The base fails the same way.

🔴 Any HTTP client can now stall the Jina API server's event loop for minutes with one large document of deeply nested markers. The base sanitizer took one linear pass. <details>
<summary>Why this was flagged</summary>

A client POSTs to `/rerank`, `/score` or `/pooling` with a document like `"<|embed"*k + "<|embed_token|>" + "_token|>"*k`. Each `str.replace` pass removes only the innermost `<|embed_token|>`, so the `while True` loop at io_processor.py:865-870 runs k+1 times. Total work is quadratic: a 1 MB document means roughly 66k passes, each scanning and copying about 1 MB twice. `format_docs_prompts_func` runs inside `get_request_factory_online` (io_processor.py:954/960). That function is called synchronously at base/serving.py:85, on the asyncio event loop rather than in the `render_async` executor, so every other request and health check stalls while it runs. On the base branch the sanitizer made one linear pass. Nothing bounds the input first. `max_tokens_per_doc` is optional and defaults to 0.

**Verification:** The new `sanitize_input` (io_processor.py:865-870) repeats `str.replace` until the text stops changing. Removing the innermost `<|embed_token|>` joins a new marker, so the loop runs about k+1 times, quadratic in input length. The base did one linear pass. It is called synchronously at vllm/entrypoints/pooling/base/serving.py:85, blocking the event loop.

</details>
