# [ROCm][MoRIIO] Support DCP for decode instance in PD disaggregated serving with MoRI WRITE mode

[Upstream PR](https://github.com/vllm-project/vllm/pull/64722) · state: open · merged: False

## Original PR description



## Overview

In WRITE mode, `MoRIIOConnector` copies prefill block `i` straight into decode block `i`, so when the two instances store tokens differerntly, like a decode instance with DCP and a prefill instance without DCP, ends up with its tokens on the wrong ranks. This PR makes each prefill rank write each decode rank exactly the tokens that rank holds for MLA models and at any interleave that divides the block size.



## Claims

- A prefill instance without DCP can now feed a DCP decode instance for MLA models, including hybrid MLA + linear-attention models, and every token is written once per DCP group instead of once per decode rank.
- On DeepSeek-R1 (8x MI355X), prefill TP4 and decode TP4+DCP4 gives the decode side 3.9x the KV cache of a TP4 decode instance. Under a decode-heavy load it completes all 640 requests with 19% more output per GPU, where TP4 prefill and TP4 decode loses 214 of them to decode-block timeouts. Interleave 1 and 64 perform the same.
- On Kimi-Linear-48B-A3B-Instruct (MLA + KDA), prefill TP2 with decode TP2+DCP2 gives the decode instance 1.54x the KV cache of a TP2 one, completes every request with exact-length outputs matching the prefill server, and GSM8K scores are unchanged.
- Instances with the same DCP size keep main's rank-to-rank writes, in READ and WRITE mode and for hybrid models, and main's hybrid DCP unit tests pass unchanged.
- Layouts the connector can't transfer are refused at the handshake. The affected requests fail with an error and both instances keep serving, where before the request would hang or the decode engine would stop.

## Details

For MLA models, a TP*n* decode instance keeps a full copy of each request's latent KV on every TP rank. DCP splits the tokens across the ranks instead, so the same GPUs hold up to *n* times the tokens, and the prefill instance doesn't need DCP for that.

With this PR, a WRITE transfer into a DCP decode instance goes through four steps.
1. The decode instance deals each request's tokens to its DCP ranks in groups of `--cp-kv-cache-interleave-size` (I) tokens. With DCP N and block size B, one scheduler block covers N x B tokens, and each rank keeps its share in its own physical block under the same block id.
2. The decode scheduler sends that block list to every prefill rank, as on main.
3. Each prefill rank, which holds the prompt unsharded, writes each decode rank only the tokens that rank holds, one write per group of I tokens.
4. Each decode rank finishes the transfer once its writers have sent `write_done`.

On main the prefill rank pairs its block `i` with decode block `i`.

```
vllm/distributed/kv_transfer/kv_connector/v1/moriio/moriio_layout.py's compute_block_transfer_offsets
if len(local_block_ids) > len(remote_block_ids):
    raise ValueError("local_block_ids longer than remote_block_ids: ...")
```

So a prompt longer than one decode block fails outright, and a shorter one puts its tokens on the wrong DCP ranks. At MoRIIO's default interleave of 1, a single prefill block is spread over all the decode ranks.

This PR makes the following changes:
- It maps tokens instead of blocks for a producer without DCP (`dcp_write_runs`). Token `t` goes to DCP rank `(t // I) % N` at position `p = (t // (I * N)) * I + t % I`, which is block `ids[p // B]`, slot `p % B`, the placement `vllm/v1/worker/block_table.py` uses. Since I divides B, each group of I tokens is one write, and at I = B the writes are the existing whole-block writes. MLA latents are written this way. Other DCP-sharded MLA caches, such as the sparse MLA indexer cache of DeepSeek-V3.2, GLM-5.2 and GLM-5.3, are written in whole blocks and need I = B. Recurrent-state layers of hybrid models (Mamba, KDA) are not split by DCP and keep main's TP-slice writes.
- It advertises `dcp_size` and `cp_kv_cache_interleave_size` in the handshake, and the instance that opens the connection (the prefill instance in WRITE mode, the decode instance in READ mode) refuses layouts it can't transfer. Those are a DCP-sharded layer that isn't MLA (a GQA model, or a draft model without MLA, which the decode instance runs without DCP), an interleave that doesn't divide the block size or is below it for a whole-block layer, equal DCP sizes with different interleaves, and any other DCP size mismatch. A peer that doesn't advertise its layout is accepted as before.
- It fails only the affected requests after a refusal. In WRITE mode the prefill instance frees the request's blocks and sends `write_failed` once the decode allocation arrives, and the decode instance fails the request per `kv_load_failure_policy`. In READ mode the TP ranks agree on the refusal (`HandshakeRefusedError`), report the requests' blocks as invalid and release the prefill's blocks with an empty read, so the engine keeps running. A later release of such a request that carries no prefill address is skipped with a warning instead of raising in `build_connector_meta`.

A producer with the same DCP size as the decode instance keeps the original rank-to-rank writes in READ and WRITE mode. MoRIIO also keeps its default interleave of 1, which speculative decoding with DCP on `ROCM_AITER_MLA` needs, while the block size gives the fewest writes.

Notes:
- Over xGMI, main's completion wait can sleep out the full transfer_timeout, or fail with copies still in flight and send no write_failed. https://github.com/vllm-project/vllm/pull/64330 fixes the wait and the end-to-end runs were performed with the fix.
- Every DCP-sharded layer must be MLA, so GQA models and draft models without MLA are refused.
