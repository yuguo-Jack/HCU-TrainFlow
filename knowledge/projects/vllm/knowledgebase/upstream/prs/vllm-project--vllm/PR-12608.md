🟡 **bug** (medium)

allocate_slots now touches the new computed blocks (incrementing ref_cnt and removing evictable ones from the free queue) at the very top, before the free-block availability check. When the check fails it reverses this with _untouch. But FreeKVCacheBlockQueue.append re-inserts blocks at the tail (most-recently-used position) and the queue's eviction order relies on blocks being re-appended in reverse order for a chain. Re-appending the prefix-cache blocks on failure therefore loses their original LRU position/chain order, so under memory pressure the LRU eviction order is perturbed - blocks that should be evicted first may survive while fresher cached prefixes get evicted. It also adds an extra queue mutation on every failed allocation.

**建议**: Perform the free-block check (num_new_blocks > self.free_block_queue.num_free_blocks) before calling self._touch(...), and touch the computed blocks only after the allocation is known to succeed. That makes _untouch unnecessary and avoids ever disturbing the free-queue order. (This is also the direction the PR later took in follow-up commits.)

**证据**: `            self._untouch(new_computed_blocks)`
