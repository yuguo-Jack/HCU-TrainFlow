# [Bugfix][Core] Shut down EngineCore and its workers when the parent process dies

[Upstream PR](https://github.com/vllm-project/vllm/pull/55846) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Fixes #55510. When the process that launched vLLM dies without shutting it down (SIGKILL, OOM kill, crash), `EngineCore` and its TP workers keep running and hold the GPUs. A restart then fails the KV-cache memory check or OOMs.

Workers already exit when their parent dies, through the death pipe that `MultiprocExecutor` gives them. But their parent is `EngineCore`, and nothing tells `EngineCore` that its own parent is gone. This PR gives `EngineCore` the same death pipe, following @njhill's suggestion on #34816 ("set the shutdown flag and then kill after some delay"). On EOF the engine sends `ENGINE_CORE_DEAD` to its clients, aborts in-flight requests and runs the normal teardown, and force-kills its process tree if it is still alive 15 s later. The worker's monitor thread moves into a shared helper, `monitor_parent_death()`. Nothing changes while the parent is alive. If the parent dies during a SIGTERM drain, the engine switches to abort, since nothing is left to bound the drain.

Earlier attempts (#21915, #27686, #36055, #34816) were closed without being merged, and draft #40935 has been inactive since April.

## Validation

2× A100 80GB PCIe, torch 2.14.0+cu132, base `3dc6def360`. Reproducer: start `vllm serve hmellor/tiny-random-LlamaForCausalLM --enforce-eager`, `kill -9` the launcher, then check `ps` and `nvidia-smi`.

| Scenario | `main` | this PR |
|---|---|---|
| TP=2, kill the API server | EngineCore + 2 workers alive after 60 s, 150,790 MiB held | all exited after 8 s, 0 MiB |
| DP=2, kill the launcher | engines, workers and both API servers keep running, 150,362 MiB held | engines exited after 7 s, 0 MiB; both API servers got `EngineDeadError` and shut down (the CPU-only DP coordinator stays) |
| TP=2, kill during model load | EngineCore finishes loading, starts its workers and holds 150,790 MiB | all exited within 1 s, 0 MiB |

The 15 s force-kill never fired in these runs. @vinitrbl also confirmed `vllm run-batch` ([review](https://github.com/vllm-project/vllm/pull/55846#pullrequestreview-5424839487)).

```

pytest -v -s tests/entrypoints/launchers/test_shutdown.py                    # 8 passed
```

On `main`, `test_parent_death.py` fails for both TP sizes because EngineCore and its workers outlive the parent, and the new `parent_exited` unit cases fail too. `pre-commit run --hook-stage manual` passes. ROCm and Intel XPU were not tested.

Gave this a try with `vllm run-batch`, since it isn't in the table and it's a slightly worse case: run-batch has no SIGTERM handler, so even a normal SIGTERM kills the launcher without telling the engine.

A10G, tiny random-weight Llama, 4000-request batch, signal sent to the run-batch process once a few hundred requests had finished. Base is main at the merge base (7867d6c), PR head 81aa514, both with `VLLM_USE_PRECOMPILED=1`.

| signal | main @ 7867d6c | this PR |
|---|---|---|
| SIGTERM | EngineCore still up after 60s, 21 GB held | gone, GPU free within 5s |
| SIGKILL | | gone, GPU free within 5s |

Both PR runs log `EngineCore: parent process exited, shutting down`. I didn't redo SIGKILL on 7867d6c, but on another main-based build (the #52505 branch) it orphaned the engine the same way.

On main the next run on the same GPU fails in `request_memory` until you kill the orphan by hand, so this is a nice fix for anyone retrying interrupted batch jobs. Might be worth adding run-batch to the list of covered cases.

- AubinGil · comment · 2026-10-16T15:43:04Z · [source](https://github.com/vllm-project/vllm/pull/55846#issuecomment-6219108383)

Windows portability feedback for PR55846 (head73ce1bfbd82b12fd60e7a86cd182e36b7404dac8):

The new on_parent_death fallback uses `os.kill(os.getpid(), signal.SIGKILL)`. Windows Python has no SIGKILL, so if tree cleanup raises before killing self, the final fallback raises AttributeError too. The new shutdown test uses SIGKILL directly as well.

In CPU-only native Windows spawn fixtures using the exact PR monitor/callback functions, EOF detection worked after TerminateProcess of the parent. The unadapted early-init kill path raised AttributeError and left the child/test port alive; substituting SystemPanic's existing Windows-adapted kill_process_tree made it exit. A fake initialized engine's cooperative queue path also exited. These are mechanism tests, not real EngineCore/GPU/TP acceptance.

Could the last-resort self-exit use `os._exit(1)` after tree cleanup fails, avoiding POSIX-only signal constants, with a test injecting a tree-cleanup exception? This would make self-exit portable; it does not by itself prove worker-tree cleanup. A Windows test variant would also need Process.kill()/TerminateProcess semantics.
