# [Bugfix][Core] Shut down EngineCore and its workers when the parent process dies

[Upstream PR](https://github.com/vllm-project/vllm/pull/55846) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Make `EngineCore` and its workers exit, and release the GPUs, when the process that launched them dies without shutting them down (SIGKILL, OOM-kill, crash). Fixes #55510. Same class of report as #19849, #25850, #34643 and #43060.

## Claims

- When the launching process is SIGKILLed, `VLLM::EngineCore` and its `VLLM::Worker_TP*` processes exit within 15 s and release GPU memory. On `main` they keep running indefinitely, and a restart then fails the KV-cache memory check or OOMs.
- Validated for `vllm serve` TP=2, `vllm serve` DP=2, offline `LLM()` with TP=1/2, and SIGKILL during model loading. @vinitrbl independently confirmed `vllm run-batch` ([review](https://github.com/vllm-project/vllm/pull/55846#pullrequestreview-5424839487)): on `main` even a plain SIGTERM orphans the engine there, because run-batch has no SIGTERM handler, and with this PR the GPU is free within 5 s for both SIGTERM and SIGKILL.
- Clients that outlive the dead parent receive `ENGINE_CORE_DEAD` and fail fast instead of hanging with `/health` 200. The main example is the API-server processes in multi-API-server mode, which is the default for DP > 1.
- Nothing changes while the parent is alive. SIGTERM/SIGINT handling and the `--shutdown-timeout` drain path are untouched, and the existing shutdown tests listed below pass.

## Validation

Base `84bcbc6264`, torch 2.13.0+cu132. The branch has since been rebased onto `04462732a4` with no conflicts and an unchanged patch. The reproducer and the existing shutdown suites ran on 2× A100-SXM4-40GB (driver 580.159.03). The final test files ran on 2× A100-PCIE-40GB (driver 595.71.05) with `NCCL_P2P_DISABLE=1 VLLM_SKIP_P2P_CHECK=0`. That host needs them for TP=2 because its GPUs sit on different sockets and P2P does not work inside its container. NVIDIA only: ROCm was not validated, but the AMD "Distributed Torchrun + Shutdown" mirror runs the new test.

Reproducer for #55510: start `vllm serve hmellor/tiny-random-LlamaForCausalLM --enforce-eager`, `kill -9` the launcher, then watch `ps` and `nvidia-smi`.

| TP=2, SIGKILL during model load | EngineCore finishes loading, starts its workers and holds 75,856 MiB after 60 s | all exited within 1 s, 0 MiB |

## Details

**Root cause.** `WorkerProc` already exits when its parent dies: `MultiprocExecutor` gives each worker the read end of a death pipe and keeps the write end. But the workers' parent is `EngineCore`, and `EngineCore` has no parent-liveness check of its own:
- `CoreEngineProcManager` starts it as a plain non-daemon process.
- `run_engine_core` installs only SIGTERM/SIGINT handlers.
- Its ZMQ sockets have no heartbeat.

So when the frontend disappears, `EngineCore` idles forever and keeps its workers alive.

**Fix.** Reuse the worker mechanism one level up.
- **Shared helper.** The worker's death-pipe thread moves without behaviour changes into `vllm.utils.system_utils.monitor_parent_death()`, and `WorkerProc` calls it.
- **Pipe ownership.** `CoreEngineProcManager` creates one pipe per engine and holds the write ends until after `shutdown(procs)` has stopped the engines, so a SIGTERM drain never sees EOF. Under fork, children close the inherited write ends, as `MultiprocExecutor` already does.
- **On EOF.** `EngineCore` follows the approach @njhill suggested on #34816: "set the shutdown flag and then kill after some delay".
  - It sends `ENGINE_CORE_DEAD` to its clients.
  - It requests shutdown in abort mode and wakes the busy loop, so the normal teardown runs and terminates the workers.
  - If it is still alive 15 s later, or if the parent died before the engine finished initializing, it SIGKILLs its process tree and then itself.

<details>
<summary>Design notes and alternatives</summary>

- **Abort, not drain.** A drain is only ever bounded by the parent force-killing the engine when `--shutdown-timeout` expires, so without the parent a drain would be unbounded. RFC #24885 puts that decision with the parent, and that parent is gone. `--shutdown-timeout` defaults to 0, so default deployments abort anyway.
- **Notify clients at EOF time.** The notice goes out before teardown rather than after it, so it cannot be pre-empted by the 15 s force-kill and does not delay GPU release. As a result, in-flight requests on surviving clients fail with `EngineDeadError`, the same as when an engine crashes.
- **Not `prctl(PR_SET_PDEATHSIG)`** (#34816, draft #40935).
  - The death pipe is portable and pure Python; on #40841 prctl was described as "not easy to do in python".
  - It tracks the parent *process* rather than the thread that created the child, which matters for embedders that construct `LLM()` from a helper thread.
  - It allows a cooperative abort before any kill.
- **Not `multiprocessing.parent_process().sentinel`.** Under fork, CPython's parent keeps each child's sentinel write end open, so later siblings inherit the write ends of earlier siblings and EOF would cascade one engine at a time.
- **Earlier attempts.** #27686, #36055 and #34816 were closed for inactivity, not rejected. Compared with them, this PR keeps the `processes` API, handles inherited fds under fork, closes the write ends only after the engines have shut down (so drain is preserved), and installs no new signal handlers.

</details>

<details>
<summary>Not covered, and behaviour changes</summary>

Not covered:
- The DP supervisor itself being SIGKILLed. Its DP servers run in their own process group and keep their engines. Death of a single DP server *is* covered.
- `vllm-rs serve` managed-engine mode when the Rust binary dies, because the headless Python launcher survives it.
- CPU-only processes left behind by a SIGKILLed multi-API-server launcher: API servers (which now see `EngineDeadError`), the DP coordinator and the Rust frontend. Related: #43417.
- Ray-managed engines.
- If user code forks after creating `LLM()`, for example with a fork-mode `multiprocessing.Pool`, those children hold the write end and delay EOF until they exit. The existing worker death pipe has the same limitation.
- A narrow startup race. If the parent dies while EngineCore is still starting its TP workers, the force-kill takes a single process-tree snapshot, so a worker started in the few milliseconds after it can be missed. That worker only exits at the distributed-init timeout (600 s by default), because workers start watching their death pipe after `WorkerProc` construction. This gap already exists on `main`, for example when EngineCore is OOM-killed while spawning workers. Closing it on the worker side is left for a follow-up.

Behaviour changes:
- If the parent dies during a SIGTERM drain, the engine switches to abort.
- Multi-node DP: when one node's launcher dies, that node's ranks now exit instead of being left orphaned. They notify the head node and are force-killed after 15 s if their peers are still busy, so the DP group fails the same way it does when any rank dies.

</details>
