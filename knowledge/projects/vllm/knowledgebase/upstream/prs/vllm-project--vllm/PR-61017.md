# [Spec Decode] RecoverSSM: commit all GDN KV cache groups with one set of launches

[Upstream PR](https://github.com/vllm-project/vllm/pull/61017) · state: open · merged: False

## Original PR description

Follow-up to #58863, as suggested there (https://github.com/vllm-project/vllm/pull/58863#issuecomment-6068066255). **Stacked on #58863; only the last commit is new.**

## Purpose

`commit_step` commits each KV cache group on its own: for every group with GDN layers, a plan, a conv and a state launch (and the align update). When a model's GDN layers are split over several groups, that host cost is paid once per group, on the single-stream critical path after sampling.

This adds `GDNRecoverSSMGroupedCommit`, which merges the groups' layers into one commit context:
- Each layer records its group. The plan kernel runs one program row per group; the conv and state kernels read the layer's group state indices (and block table in align mode) through per-group address tables, and each group gets its own slice of the plan.
- Instead of a `[group, batch]` copy of the state indices, the kernels read each group's existing tensor through a small address table: copying the groups' indices into one table would itself take one launch per group.
- The shared kernels (`prepare_commit_plan_kernel`, `compact_conv_state_kernel`) take the tables as optional arguments. With `None` they run as before, so one group, PLE and KDA launch exactly as now.
- `commit_step` groups the GDN metadata when every group has spec rows with the same per-request inputs (accepted counts, query offsets, request mapping, computed tokens, block size), and falls back to the per-group loop otherwise, or when the groups' layers cannot share one context.
- The align update writes the same per-request values for every group, so it runs once.
- The address tables are rebuilt only when a group's state-index or block-table tensor moves.

`commit_step` stays where it is, outside graph capture.

## Test Result

- **New tests** in `tests/kernels/mamba/test_recoverssm_gdn.py`: three KV cache groups of two GDN layers each, spec rows 0, 2, 3 of a 5-request batch, each group with its own blocks; the grouped commit leaves every conv state and checkpoint bit for bit as one commit per group, without and with align mode, over two steps with new state-index tensors. Plus a test that mismatched groups are rejected.
- **Run on XPU** (2× Intel Arc Pro B70; one card; the CUDA-only tests run from a local copy with the device swapped): the new tests pass. The existing tests that compare the commit with the native per-token states bit for bit fail on XPU with and without this change (the same 28), so they don't say anything about this change there. The new tests compare the grouped commit with the per-group commit, not with the native kernel, so they don't depend on that comparison. **Not run on CUDA.**
- **Host time of the commit** (XPU, one card, synthetic tensors, 3 KV cache groups × 6 GDN layers like one PP stage of Qwen3.8-Flash-Next):

  | | per group (now) | grouped | one 18-layer context (reference) |
  |---|---|---|---|
  | N=1 | 401 µs | 139 µs | 131 µs |
  | N=1, align | 523 µs | 194 µs | 176 µs |
  | N=8 | 404 µs | 140 µs | 133 µs |
  | N=8, align | 541 µs | 184 µs | 182 µs |

- **Server** (2× Arc Pro B70, Qwen3.8-Flash-Next, PP=2 with our follow-up #59983, MTP K=1, on our own tree with the same change): we alternated between the per-group loop and the grouped commit inside one server process (a local-only switch, not part of this PR), because the decode slope of this setup moved between server starts by more than the expected gain (30.5 to 32.9 ms/token over four starts of the same configuration). Over 2 starts × 3 rounds, the grouped commit lowered the single-stream decode slope by 0.19 ms/token (31.39 → 31.20 ms/token; every one of the 6 rounds lower, by 0.19 to 0.22). Per-token logprobs stayed within our run-to-run noise against the Triton/FLA path without RecoverSSM, and MTP acceptance was 1.76 in both starts. The log confirmed both PP ranks took the grouped commit (3 KV cache groups, 18 GDN layers per PP rank).
- `ruff check` / `ruff format` pass on the changed files (one existing E501 in `recoverssm_gdn.py` is not from this change).
- **Not tested**: CUDA; this exact branch end to end (the server run used our tree, which also carries #59983 and our XPU changes); the fallback to the per-group loop on a server (the unit tests cover only the rejection of mismatched groups); the KDA path with several groups (KDA keeps its own commit and only gets the new optional arguments).
