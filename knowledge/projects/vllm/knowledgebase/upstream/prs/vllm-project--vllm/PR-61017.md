# [Spec Decode] RecoverSSM: commit all GDN KV cache groups with one set of launches

[Upstream PR](https://github.com/vllm-project/vllm/pull/61017) · state: open · merged: False

## Original PR description

Follow-up to #58863, as suggested there (https://github.com/vllm-project/vllm/pull/58863#issuecomment-6068066255). **Stacked on #62625 (→ #61309 → #58863); only the last commit (`de4defd53d`) is new.** Rebased on 2026-11-05 because #62625 moves the replay records out of the Mamba page.

## Purpose

`commit_step` commits each KV cache group on its own: for every group with GDN layers, a plan, a conv and a state launch (and the align update). When a model's GDN layers are split over several groups, that host cost is paid once per group, on the single-stream critical path after sampling.

This adds `GDNRecoverSSMGroupedCommit`, which merges the groups' layers into one commit context:
- Each layer records its group. The plan kernel runs one program row per group; the conv and state kernels read the layer's group state indices (and block table in align mode) through per-group address tables, and each group gets its own slice of the plan.
- Instead of a `[group, batch]` copy of the state indices, the kernels read each group's existing tensor through a small address table: copying the groups' indices into one table would itself take one launch per group.
- The shared kernels (`prepare_commit_plan_kernel`, `compact_conv_state_kernel`) take the tables as optional arguments. With `None` they run as before, so one group, PLE and KDA launch exactly as now.
- `commit_step` groups the GDN metadata when every group has spec rows with the same per-request inputs (accepted counts, query offsets, request mapping, computed tokens, block size), and falls back to the per-group loop otherwise, or when the groups' layers cannot share one context.
- The align update writes the same per-request values for every group, so it runs once.
- The address tables are rebuilt only when a group's state-index or block-table tensor moves.
- With #62625's out-of-page records, the commit takes `record_indices`: one row per request slot, the same in every group. Without it (in-page records), each group reads its records at its own state indices.

`commit_step` stays where it is, outside graph capture.

## Test Result

After the rebase we re-ran only the XPU kernel tests and the host-time benchmark; the CUDA, server and GB10 numbers below are from the earlier base (3694757f6) and were not re-run.

- **New tests** in `tests/kernels/mamba/test_recoverssm_gdn.py`: three KV cache groups of two GDN layers each, spec rows 0, 2, 3 of a 5-request batch, each group with its own blocks; the grouped commit leaves every conv state and checkpoint bit for bit as one commit per group, without and with align mode, over two steps with new state-index tensors. Plus a test that mismatched groups are rejected. After the rebase it also runs with out-of-page records.
- **Run on XPU after the rebase** (one Arc Pro B70; CUDA-only tests run from a local copy with the device swapped): 28 failed / 54 passed / 10 skipped, vs. 28 / 49 / 10 for #62625 alone. The 28 are the same tests by name on both (the native-comparison ones); the five extra passes are the grouped-commit tests.
- **Run on CUDA** (earlier base; one RTX 2080, sm_75; this branch's Python tree at ab95c36dc on top of the compiled extensions of the vLLM 0.32.0 wheel): `tests/kernels/mamba/test_recoverssm_gdn.py`, `tests/kernels/mamba/test_recoverssm_ple.py` and `tests/models/kimi_k3/test_recoverssm_boundary.py`: 87 passed, 0 skipped. That includes the 28 native-comparison tests that fail on XPU, so those failures are on the XPU side, and the tests marked CUDA-only.
- **Host time of the commit per step**, after the rebase (XPU, one card, synthetic tensors, 3 KV cache groups × 6 GDN layers like one PP stage of Qwen3.8-Flash-Next):

  | | per group (now) | grouped | one 18-layer context (reference) |
  |---|---|---|---|
  | N=1 | 332 µs | 115 µs | 105 µs |
  | N=1, align | 447 µs | 162 µs | 148 µs |
  | N=8 | 326 µs | 121 µs | 108 µs |
  | N=8, align | 441 µs | 162 µs | 148 µs |

  At N=8 the time until the GPU work drains does not change (333 → 323 µs, align 441 → 447 µs); the GPU work dominates there. The earlier base gave the same picture (N=1: 401 → 139 µs).

- **Server** (earlier base; 2× Arc Pro B70, Qwen3.8-Flash-Next, PP=2 with our follow-up #59983, MTP K=1, on our own tree with the same change): we alternated between the per-group loop and the grouped commit inside one server process (a local-only switch, not part of this PR), because the decode slope of this setup moved between server starts by more than the expected gain (30.5 to 32.9 ms/token over four starts of the same configuration). Over 2 starts × 3 rounds, the grouped commit lowered the single-stream decode slope by 0.19 ms/token (31.39 → 31.20 ms/token; every one of the 6 rounds lower, by 0.19 to 0.22). Per-token logprobs stayed within our run-to-run noise against the Triton/FLA path without RecoverSSM, and MTP acceptance was 1.76 in both starts. The log confirmed both PP ranks took the grouped commit (3 KV cache groups, 18 GDN layers per PP rank).
- **CUDA (earlier base; measured by @jschmied, [comment](https://github.com/vllm-project/vllm/pull/61017#issuecomment-6298956474))**: one DGX Spark (GB10), Qwen3.8-Flash-Next, PP=1, MTP K=3, align mode, 3 KV cache groups / 36 GDN layers, this commit cherry-picked onto #58863 on main 3897f95cf1, one server start, ABBA × 3 inside one process. `commit_step` host time ~330 → ~187 µs; the c=1 step time and decode ms/token did not move measurably (18.93 vs 18.92). So on CUDA this is a host-time cleanup, not a decode speedup.
- `ruff check` / `ruff format` pass on the changed files (one existing E501 in `recoverssm_gdn.py` is not from this change).
- **Not tested**: a CUDA server run by us (see the GB10 measurement above); this exact branch end to end (the server run used our tree, which also carries #59983 and our XPU changes); the fallback to the per-group loop on a server (the unit tests cover only the rejection of mismatched groups); the KDA path with several groups (KDA keeps its own commit and only gets the new optional arguments).

Measured this on one DGX Spark (GB10). Setup: Qwen3.8-Flash-Next (NVFP4 experts, FP8 GDN), PP=1, MTP K=3, align mode + prefix caching, `--use-replayssm`, FULL_AND_PIECEWISE graphs. #58863 at the current head plus your last commit (65ac584322, cherry-picked), on main 3897f95cf1. At PP=1 the model has 3 GDN KV cache groups and 36 GDN layers; the log shows "grouped commit: 3 KV cache groups, 36 layers".

Like you, I alternated inside one server process with a local switch (a flag file that forces the per-group loop; not part of the PR), ABBA × 3, c=1, 3 prompts × 384 tokens per round. `commit_step` host time is perf_counter around the whole call, including the align update. The step time is the interval between consecutive commits. Both are medians over windows of 100 steps.

| | per group | grouped |
|---|---|---|
| `commit_step` host time | 314–351 µs per window (~330) | 172–200 µs per window (~187) |
| c=1 step interval | 59.3 / 59.9 / 58.0 ms | 59.6 / 58.9 / 58.7 ms |

- Host time drops by about 140 µs per step (−43 %). Every grouped window is lower than every per-group window.
- The c=1 step time doesn't move measurably. 140 µs is 0.24 % of a ~59 ms step, and the windows drift by ±1 ms within a run. Client-side decode ms/token is also flat: medians 18.93 vs 18.92. This setup's greedy outputs aren't bit-reproducible, so acceptance varies between rounds.

So the saving is real on CUDA too, but on this model at c=1 it's below what the step time can resolve. Caveats: one server start. The per-group arm runs your branch's fallback loop (the kernels with `None` tables), not the code before this commit. To load this checkpoint on current main I needed our local loading patches (weight_scale_inv rename, FP8 lm_head) and the checkpoint-mapped PLE from #58439.
