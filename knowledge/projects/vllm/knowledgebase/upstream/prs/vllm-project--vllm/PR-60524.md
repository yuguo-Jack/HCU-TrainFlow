# [Bugfix] Keep compressed-tensors wNa16 linear layers batch invariant

[Upstream PR](https://github.com/vllm-project/vllm/pull/60524) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

Follow-up to #60479. With `VLLM_BATCH_INVARIANT=1`, the compressed-tensors `pack-quantized` linear scheme (`CompressedTensorsWNA16`, W4A16 and W8A16) still runs the Marlin GEMM, whose tiling and K-split depend on the number of tokens, so logprobs change with the batch size. This PR applies the same fix as #60479 to that scheme: in batch-invariant mode skip the Marlin kernel selection and repacking, keep the checkpoint layout, unpack the weight in `apply_weights()` and call `matmul_batch_invariant`. Without the flag nothing changes.

## Claims

- On `main`, `tests/v1/determinism/test_batch_invariance.py` fails for `RedHatAI/Qwen3-8B-quantized.w4a16` (dense), `RedHatAI/Qwen3-30B-A3B-quantized.w4a16` (MoE; its dense layers use this scheme) and `RedHatAI/Meta-Llama-3.1-8B-Instruct-quantized.w8a16`. With this PR all ids pass, on an A10 and on a B300.
- Accuracy is unchanged (`lm_eval` gsm8k, batch-invariant path versus Marlin), and the Marlin path is still selected when the flag is unset.
- Throughput cost of the batch-invariant path on these models is in the blocks below.

## Details

**Root cause.** `CompressedTensorsWNA16.create_weights` always builds a Marlin `MPLinearKernel` (`choose_mp_linear_kernel`), and `apply_weights` runs it. Marlin's results depend on the number of rows, so batch-invariant mode is silently violated; the determinism suite fails for every pack-quantized checkpoint tried, on A10 and B300, while the needle test often passes (greedy outputs usually survive the logprob differences).

**Change** (`compressed_tensors_wNa16.py` only). With `VLLM_BATCH_INVARIANT=1`: no Marlin kernel is created, `process_weights_after_loading` keeps `weight_packed` / `weight_scale` / `weight_zero_point` in the checkpoint layout, and `apply_weights` unpacks the weight with `compressed_tensors.compressors.pack_quantized.helpers.unpack_from_int32` (and the zero points for asymmetric checkpoints), dequantizes in the scales dtype and calls `matmul_batch_invariant`. The log line becomes `Using dequantize + batch-invariant matmul for CompressedTensorsWNA16`.

**Trade-offs and limitations.**
- The weight is unpacked on every forward in batch-invariant mode (same choice as #60479: keeping a dequantized copy would need the memory of the unquantized model). The cost is in the benchmark blocks above.
- Symmetric W4A16 and W8A16 checkpoints and an asymmetric W4A16 checkpoint were validated (blocks above).
- The MoE expert path of compressed-tensors (`CompressedTensorsWNA16MoEMethod`) is not touched: on the MoE model tested the experts run through the Triton WNA16 MoE backend and the violation disappears once the dense layers are fixed.
