# [Bugfix][DSv4.1] Fail fast on SM120 when FlashInfer lacks runtime page sizes

[Upstream PR](https://github.com/vllm-project/vllm/pull/57292) · state: open · merged: False

## Original PR description

## Purpose

Narrows this PR after review feedback (thanks @lucifer1004). Related to #56461 and #59203.

flashinfer-ai/flashinfer#5197 makes FlashInfer's SM120 sparse-MLA page sizes a runtime argument, so DeepSeek-V4.1 on SM120 no longer needs vLLM to switch to 64-token pages. #59846 serves V4.1 on SM120 with the existing 128-token kernel blocks and 32-token SWA pages. The geometry change this PR originally proposed is dropped.

What remains is a startup guard. #5197 is in FlashInfer 0.7.1rc1/rc2 but not in the pinned 0.7.0.post1, whose SM120 decode kernels are instantiated only for 64-token pages. On such a build, V4.1 on SM120 currently fails with an error that does not name the cause. This PR checks for runtime page sizes when `DeepseekV4FlashInferSM120Attention` is constructed and raises:

```
FLASHINFER_MLA_SPARSE_DSV41 on SM120 requires FlashInfer >= 0.7.1 (flashinfer-ai/flashinfer#5197). ...
```

The probe uses FlashInfer's public `supported_sparse_mla_sm120_configs()` and reads `page_block_size_is_runtime` on the `dsv4` entry. That field exists only in builds that contain #5197, so the probe needs no version parse and works with dev builds. It sits next to the existing `has_flashinfer_sparse_mla_sm120_config` probe and runs only on the SM120 path. SM90 and SM100 behavior is unchanged.

Once vLLM pins FlashInfer >= 0.7.1, the guard always passes on supported installs and only catches stale environments.

## Test Plan

```bash
pytest tests/v1/attention/test_flashinfer_sparse_mla_sm120_api.py -q
```

The new tests stub FlashInfer, so they run without an SM120 GPU. They cover: no config API, no `dsv4` entry, the 0.7.0.post1 config shape (no runtime flag), the runtime flag off, the runtime flag on, and the decode API missing.

## Test Result

- `ruff check` / `ruff format` pass.
- The probe logic was checked against the `SparseMLASm120DecodeConfig` shapes from FlashInfer v0.7.0.post1 (returns `False`) and v0.7.1rc2 (returns `True`).

- luoyuctl · comment · 2026-09-30T02:32:27Z · [source](https://github.com/vllm-project/vllm/pull/57292#issuecomment-5902914153)

@lucifer1004 Thanks, you're right. flashinfer-ai/flashinfer#5197 (merged 2026-09-18, eb5f05b) makes the SM120 sparse-MLA page size a runtime argument, including independent main/extra page sizes for the DSv4.1 dual cache. That removes the kernel-side restriction this PR originally worked around, and it covers the 32-token extra pages I had listed flashinfer-ai/flashinfer#5174 for.

The vLLM-side page declarations still need to agree, though. On current main, `FLASHINFER_MLA_SPARSE_DSV41` and `DeepseekV4SparseMLABackend` declare 128-token kernel pages on every non-SM90 GPU, while `DeepseekV41IndexerBackend` declares 64. The MLA and indexer groups share a manager block, so startup fails in `select_common_block_size` with "No common block size for 64" (the second failure mode in #59203), regardless of what the kernel accepts. This PR aligns those declarations on SM120, so I think it is still needed.

For reference, this geometry has served on 8× RTX PRO 5000 (SM120), but only on a backport image, not on this PR head:
- vLLM 64-token pages, i.e. this change
- DeepGEMM page32 (vllm-project/DeepGEMM#14)
- FlashInfer 0.6.18 with hand-added page32 dual-cache prefill, which is what flashinfer-ai/flashinfer#5197 now replaces
- the causal-SWA fix from #57152

Prompts from 46 to 10k tokens and 4-way mixed-length concurrency returned correct output. That is a smoke test, not an accuracy or throughput run.

Two caveats:
- flashinfer-ai/flashinfer#5197 is not in a FlashInfer release yet. v0.7.0 and v0.7.0.post1 don't include it, and vLLM pins 0.6.18.post1, so released FlashInfer still rejects `page_block_size=32` on SM120.
- With runtime page sizes, the per-ratio `[64, 128]` geometry in #56509 is also viable. I'm happy to consolidate with it or close this one, whichever geometry you and the maintainers prefer.

I've updated the description to depend on flashinfer-ai/flashinfer#5197 instead of flashinfer-ai/flashinfer#5174.
