# [KV Offload][Tiering] Let a tier fail a promotion and defer releasing its chunks

[Upstream PR](https://github.com/vllm-project/vllm/pull/63779) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

This adds a tiering API that lets a secondary tier fail a promotion right away while deferring the release of its primary-tier chunks until the tier confirms its I/O can no longer write to them. It is step 1 of the bounded consumer slot quarantine discussed in #61667 (comment [6418290229](https://github.com/vllm-project/vllm/pull/61667#issuecomment-6418290229)), under #63602 / #61532. The P2P tier will start using it in a follow-up PR, which is why this is a draft.

## Claims

- `JobResult(success=False, deferred_release=event)` fails the job's failed keys at once: lookups miss and the request recomputes. Their chunks go back to the free pool only after the tier sets the `threading.Event`, once its I/O can no longer touch them.
- This is one optional field. It defaults to `None`, so the fs, obj, kvcr and example tiers, and out-of-tree tiers, are unchanged.
- `reset_cache()` needs no rejection or retry path. `drain_jobs()` must set every `deferred_release` event before it returns, so the tier owns the bound.
- New per-tier metrics: a gauge `vllm:kv_offload_tiering_deferred_release_chunks` for chunks currently held, and a histogram `vllm:kv_offload_tiering_deferred_release_hold_seconds`, observed at release. The histogram shows that the hold is bounded, and it is what we'll use to tune the planned P2P timeouts. Its `_count` is the number of deferred releases, so there is no separate counter.

## Details

### The problem

`JobResult` currently carries two decisions at once:

- **outcome:** the keys fail and the request recomputes;
- **memory:** `_complete_promotion` calls `complete_write(keys, False)`, which frees the chunks.

P2P needs these at different times. When a load times out, the request should fail now. But the remote peer may still be posting an RDMA WRITE into those chunks, so they may only be reused once the peer sends AbortAck or TransferDone, or the session ends. Today P2P can only get safety by delaying the whole result: 30 s load timeout plus 10 s abort-ack wait before the request is failed. Or it can get speed by freeing early, which risks a late WRITE corrupting another request's KV.

### Chosen API: one outcome, carrying a release handle

- The outcome is reported **once**, through the existing `get_finished_jobs()`. The job leaves `_jobs` as usual, so request bookkeeping, promotion metrics, latency and `assert not self._jobs` all behave exactly as today.
- `deferred_release=event` on that result means "fail the keys, but defer releasing their chunks." The primary tier's `defer_write_release()` drops the keys from the cache policy, so a lookup misses and a re-store allocates a fresh chunk. The chunks stay counted as write-pending and are not on the free list.
- The release comes later. The tier sets the event, from any thread, and on its next polling round the manager calls `release_deferred_write()` for the held jobs of the polled tier whose event is set. The manager keeps one small table, `_deferred_releases: job_id -> (event, tier_idx, chunk_ids, deferred_at)`. The sweep runs after each tier's results, so an event that is already set releases in the same round.
- The contract is checked with asserts:
  - `deferred_release` is only allowed on a promotion with failed keys, and every failed key must still be a pending write (`defer_write_release()` asserts this, so a chunk the tier may still write to can't slip through unheld);
  - every `deferred_release` event is set before `drain_jobs()` returns.
- **Ordering holds by construction.** The handle is created and returned inside the result, so a release can never arrive before its result. There are no ordering rules, no unknown-job assert, and no buffering of an early P2P AbortAck that races its timeout.
- **Applied on the manager's thread.** Tiers may set the event from any thread, such as a network thread or an I/O worker. The chunks are freed only on the manager's own polling path, under the manager lock. The sweep is O(held jobs) `is_set()` checks, only for the polled tier, and held jobs are rare.

### Naming

The concept has one name everywhere: *deferred release*. That covers `JobResult.deferred_release`, `TieringOffloadingManager._deferred_releases`, the primary tier's `defer_write_release()` / `release_deferred_write()`, and the `deferred_release_*` metrics. A name like "released jobs" was avoided because it reads too much like "finished jobs".

### Alternatives considered

**1. A second `JobResult` with the same `job_id` and a `memory_safe` flag (#61667).**
The tier first reports `memory_safe=False`, then reports the same job again with `memory_safe=True`. We chose against this because:
- `job_id` stops meaning "one finished job". `_process_finished_jobs` must accept results for jobs it already popped, so it needs a parallel `_quarantined_jobs` table and a branch that skips outcome handling for repeats. Without that branch, a late "success" for an already-failed job could be applied a second time.
- The tier itself has to track which results it already reported (`failure_reported`, `request_finished`) so it doesn't fail the request twice.
- Keeping this safe across reset led to rejecting `reset_cache()` (`UnsafeTransferError`, a retry loop, and reordering in the offloading scheduler). With a bounded release that machinery isn't needed.

A release handle on the single result avoids all of this. Outcomes stay one per job, and a release carries no outcome, so it can never fail or succeed a request.

**2. A separate release channel: `SecondaryTierManager.get_deferred_releases() -> Iterable[JobId]` (this PR's first revision).**
This doubles the tier-facing surface (a flag plus a method). It also adds an ordering rule: a release must not be listed before its result, and an early one trips an assert. In P2P an AbortAck that beats the timeout result would have to be buffered. Replaced at @orozery's suggestion.

**3. Merge both into one `poll_updates() -> TierUpdates(finished, released)` (also suggested by @orozery).**
This changes `get_finished_jobs()` in every in-tree and out-of-tree tier. It also keeps the cross-round ordering rule, since a release in a later round still names a job reported earlier, so it doesn't remove the hazard. It only merges the two methods. A union return type from `get_finished_jobs()` has the same cost.

**4. Let the tier hold or free the primary chunks itself.**
Secondary tiers only see the primary memoryview, not the primary tier's allocator or cache policy. Giving them write access to allocator state would spread chunk ownership across tiers. With this API the TieringManager stays the only owner of primary chunks.

**5. Keep one result and delay it until the peer confirms (today's behavior).**
This is safe but slow: the request waits out the full abort-ack timeout before falling back to recompute. Getting rid of that wait is the point of this change.

**6. Free the chunks after a fixed grace timer.**
A timer can't prove that a stalled WRITE has stopped. Once P2P timeouts are shortened (planned: 10 s load / 5 s abort-ack for symmetric P2P), the timer would also be too short to serve as a safety margin.

### Planned P2P follow-up (not in this PR)

- **Load timeout:** send AbortFetch and report the failure right away with a `deferred_release` event, kept on the load's client state.
- **Late AbortAck or TransferDone:** set the event.
- **AbortAck timeout:** disconnect the session (#63715).
- **`ClientRole.close()`:** set every event still pending. As agreed in #61667, the release point is ack or disconnect.
- **Fetches never sent:** fail without deferring the release.

The residual risk is a WRITE that is stalled but still alive when the session ends. #61667 accepted that risk; it is tracked as gap 2b in #63602.

### Limitations

- Store (cascade) jobs can't defer a release yet, and the manager asserts this. The same field could later delay `complete_read` for source-side retention (gap 3 in #63602).
- Until the P2P follow-up lands, nothing in tree sets `deferred_release`.

Trying to simplify base.py by consolidating `get_finished_jobs` and `get_deferred_releases`.
One option is using e.g.:
```
@dataclass(frozen=True)
class TierUpdates:
    finished: Sequence[JobResult] = ()
    released: Sequence[JobId] = ()

def poll_updates(self) -> TierUpdates: ...
```

This will require changing existing tiers - I'm fine with it.

Another approach (suggested by Claude) is extending `JobResult`:
```
@dataclass
class JobResult:
    ...
    # Set when the tier's I/O can no longer touch the job's primary chunks.
    # None: the chunks are released with this result, as today.
    release: threading.Event | None = None
```

This means the manager does an O(held jobs) is_set() check each round, which is negligible because holds are rare.
However I think this approach is somewhat less convenient for the secondary tier implementor.
