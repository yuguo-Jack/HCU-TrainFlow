# [ROCm] Capture CUDA graphs with expandable segments off for AITER all-reduce

[Upstream PR](https://github.com/vllm-project/vllm/pull/57481) · state: closed · merged: True

## Original PR description

## Purpose

With `expandable_segments:True`, the caching allocator hands out VMM-backed pointers, which `hipIpcGetMemHandle` cannot export. AITER's custom all-reduce therefore stages every all-reduce captured in a CUDA graph through a device-to-device copy.

The activations feeding those all-reduces are allocated inside graph capture from the graph's private pool. Turning expandable segments off for the duration of `graph_capture()` makes them exportable, so AITER takes its registered, copy-free path. Weights, KV cache and allocations made outside `graph_capture()` keep expandable segments.

No flag. It applies automatically on ROCm when the TP group's AITER custom all-reduce registers graph buffers (`AiterCustomAllreduce.registers_graph_buffers`). That needs vLLM not to have turned registration off (the cuMem graph pool), the communicator to be enabled, a non-gfx1250 GPU, and AITER's public `defers_capture_registration` class marker. The marker means AITER takes the registration decision when capture begins; it was added in ROCm/aiter#5799 and first released in v0.1.26.

It is skipped when the DP group also runs AITER collectives. Under DP+EP the MoE combine reduce-scatters a persistent workspace allocated before capture, which the registered path cannot export.

Nothing changes on AITER before v0.1.26 (vLLM pins v0.1.26 since #62486), without AITER custom all-reduce, with the cuMem graph pool, on gfx1250, or when expandable segments are already off.

`non_expandable_allocations()` (`vllm/device_allocator/alloc_conf.py`) flips only that field of the live allocator config and restores the full string on exit, including on error. It uses the same read/flip/restore pattern as `CuMemAllocator.use_memory_pool`.

> > What are the drawbacks of enabling expandable segments?

@simondanielsson Sorry, missed that one. A small clarification first: this PR never enables expandable segments. It only switches them **off**, which is PyTorch's default. It does so only during `graph_capture()`, only on ROCm, and only for users who already set `expandable_segments:True`. Everyone else sees no change.

The drawbacks are why we switch them off rather than on:
- **No IPC export.** VMM-backed memory cannot be exported with `hipIpcGetMemHandle`/`cudaIpcGetMemHandle`. That is exactly what forces AITER (and vLLM's CUDA custom all-reduce, #42609) onto the copy path. Tensor IPC is unsupported too.
- **Incompatible with some memory setups.** It does not work with pluggable-allocator memory pools ([pytorch#147851](https://github.com/pytorch/pytorch/issues/147851)) or with pinned/RDMA-registered memory. That is why vLLM already turns it off around the sleep-mode pool and rejects it with KV connectors.
- **Slower first allocations.** Remapping pages involves synchronous GPU work (same allocator note).

Users turn it on anyway to avoid fragmentation OOMs when shapes vary. Switching it off only for the capture window is low-risk:
- weights and the KV cache are already allocated by then;
- only allocations made during capture (in practice, the CUDA-graph pool) use classic segments;
- the full allocator config string is restored afterwards.

The cost is the graph pool returning to its non-expandable size: about +0.5 GiB per GPU and −0.2% KV cache on DeepSeek-V4.1 TP8.
