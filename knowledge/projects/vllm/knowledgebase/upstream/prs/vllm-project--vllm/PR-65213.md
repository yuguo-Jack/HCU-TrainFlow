# [Bugfix][Frontend] Send an error event when a streamed Responses request fails

[Upstream PR](https://github.com/vllm-project/vllm/pull/65213) · state: open · merged: False

## Original PR description

## Overview

When a streamed `/v1/responses` request fails during generation, the server's error handler raises instead of telling the client, so the SSE stream just stops. This sends an `error` event and ends the stream cleanly.

## Claims

- A streamed Responses request that fails mid-generation now ends with an `error` event. Its `code` is the HTTP status of the failure: `"500"`, or `"503"` when the request can be retried.
- The handler no longer throws a pydantic `ValidationError` out of the stream generator.
- Non-streaming Responses, Chat Completions and Completions aren't changed.

## Validation

`pytest tests/entrypoints/openai/responses/test_serving_responses.py -k test_responses_stream_generation_error_ends_with_error_event`

- On main: fails with `ValidationError: 106 validation errors for union[ResponseCreatedEvent, ...]`, input `{'error': {'message': 'Internal server error', ..., 'code': 500}}`
- With this PR: `1 passed`. The rest of `tests/entrypoints/openai/responses/` that runs on CPU: `121 passed, 1 xfailed`.

I also ran it at the HTTP level: a FastAPI `StreamingResponse` through `_convert_stream_to_sse_events`, with an engine stub whose request finishes with `finish_reason="error"` after one token. On main the client gets `created, in_progress, output_item.added, content_part.added, output_text.delta`, and then the stream ends. With this PR the last event is `{"code":"500","message":"Internal server error","param":null,"sequence_number":5,"type":"error"}`. A `RetryableRequestError` gives `"code":"503"`. I didn't run a real model end to end; everything above is on CPU with a stub engine.

## Details

`responses_stream_generator` catches `GenerationError` and converts it with `_convert_generation_error_to_streaming_response`. That returns vLLM's `ErrorResponse` JSON (`{"error": {...}}`), and the handler then validates it against `StreamingResponsesResponse`. None of the events in that union has that shape, so validation raises inside the `except` block, the exception escapes the generator, and Starlette drops the connection mid-stream. It came in with #26813 and is reached whenever the engine reports a request error, for example a KV load failure under `kv_load_failure_policy="fail"` or a retryable error while generation is paused.

The fix sends OpenAI's `ResponseErrorEvent` and adds it to the union. Its fields map one to one onto vLLM's `ErrorInfo` (message, param, code), and the code keeps the 503 retry signal. I picked it over `response.failed` because that needs an `error` field on `ResponsesResponse`, which #38190 is adding. The Rust frontend PR #63903 uses `response.failed`, and I'm happy to switch if you'd rather have parity there.

Why this isn't a duplicate: #38190 handles other exceptions and leaves this branch unchanged. #49308 copies the same `validate_json` call into a new handler. #49721 fixes background replay waiting forever when the producer exits early, which is complementary. I found no open issue for this.

AI assistance (Claude) was used to find and write this change. I reviewed every changed line and ran the tests above.
