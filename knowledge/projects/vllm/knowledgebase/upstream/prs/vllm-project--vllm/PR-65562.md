# [Bugfix] Keep KV-cache scale defaults under dummy loading

[Upstream PR](https://github.com/vllm-project/vllm/pull/65562) · state: open · merged: False

## Original PR description



## Overview

With `load_format=dummy`, the dummy loader writes random values into the attention KV-cache scales. Checkpoints without KV-cache scales never overwrite them, so after a dummy start and a weight sync (the usual RL startup) they still differ from a real start. This PR makes dummy loading write the same values a real start has. Part of the direct weight reload work (#54477).

## Claims

- **Dummy start + sync now matches a real start for the attention scales.** The `KVCacheScaleParameter` scales (`q/k/v/prob_scale`) get the `-1.0` "not loaded" sentinel, the `_q/_k/_v/_prob_scale` buffers get `1.0`, and the compressed-tensors `q/k/v_scale` / zero points get `1.0` / `0.0`, all through the existing `dummy_weight_value` attribute. Post-load processing then takes the same "no checkpoint scales" path as on a real start.
- On Qwen3-30B-A3B-FP8 (TP4, `VLLM_RELOAD_MODE=direct`), the attention tensors that differ from a fresh real start after a dummy start + 1 sync drop from 1152 to 0 (auto KV cache) and from 768 to 0 (FP8 KV cache).
- Real (non-dummy) loading is unchanged: only the dummy loader reads `dummy_weight_value`.

## Details

**Root cause.** `DummyModelLoader` fills every parameter and persistent buffer through `initialize_single_dummy_weight`, which writes random values unless the tensor sets `dummy_weight_value`. The attention scales are never in a checkpoint without KV-cache scales:

- `q/k/v/prob_scale` (`KVCacheScaleParameter`) are created as `-1.0`, the sentinel post-load processing reads as "not loaded, use the default". After a dummy load they hold a random value. With one seed, that value is the same for all of them.
- `_q/_k/_v/_prob_scale` are persistent buffers registered at `1.0` by `set_default_quant_scales`. With an unquantized KV cache, post-load processing rewrites `_q_scale` and `_prob_scale` but not `_k_scale` / `_v_scale`, so those kept the dummy value.
- Compressed-tensors `q/k/v_scale` are created as `1.0` (zero points `0.0`) and used directly as the scales. A checkpoint without a `kv_cache_scheme` never writes them, so with an FP8 KV cache the random value became the scale.

A weight sync from such a checkpoint never writes these tensors, so the dummy values outlived it. Layerwise reload used to hide this by recreating the scales on every reload; direct reload writes in place and exposed it.

**Fix.** The fix sets `dummy_weight_value` to each tensor's creation value, the mechanism layernorm and ModelOpt already use:

- a class attribute on `KVCacheScaleParameter`, covering every method that uses `BaseKVCacheMethod.create_weights` (Fp8, ModelOpt, Quark, ...);
- the buffers in `set_default_quant_scales`, covering Attention, MLAAttention and the models that call it directly;
- `set_weight_attrs` in `CompressedTensorsKVCacheMethod.create_weights`.

On main, a dummy start with an FP8 KV cache kept GSM8K only because the shared random value happened to be negative and took the fallback to 1.0 (`_k_scale` / `_v_scale` match in the FP8 run above). A positive value would have become the KV-cache scale.
