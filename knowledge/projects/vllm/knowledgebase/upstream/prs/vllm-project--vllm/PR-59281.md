# [WIP][KV Connector] UMBP layer-wise KV loading in stages

[Upstream PR](https://github.com/vllm-project/vllm/pull/59281) · state: open · merged: False

## Original PR description

## Purpose

Work in progress on the layer-wise loading item of RFC #57187 for the UMBP KV
connector. **Stacked on #59276 (distributed) -> #59275 (standalone) -> #58568**,
rebased onto #58568's current head `37832fa99`. Review only the last commit:

- `[UMBP] Load layer-wise in stages of consecutive layers`

With `load_async=false`, the worker submits the loads of consecutive layers as one
stage (`layerwise_load_stages`, default 4) and each attention layer waits only for its
own stage. Before this, layer-wise loading issued one runtime call per layer and
rebuilt each block's plan per layer: 328-476 ms of Python per 7.9k-token Qwen3-8B
prompt, so restores took as long as computing the prompt. Submission now takes 5.4 ms.
#58568's new batched `load_blocks` path covers asynchronous and non-layer-wise loads;
this commit only changes the synchronous layer-wise path.

Related, in #59275: models with Mamba-style layers always load asynchronously, and
asynchronous loads no longer block the forward pass.

## Test Result (pre-rebase head, MI355X, standalone server, Qwen3-8B)

| Path | Cold | 4k-token prefix restored | Full restore | Identical to cold |
| --- | --- | --- | --- | --- |
| async (default) | 160 ms | 159 ms | 134 ms | 6/6, 6/6 |
| sync bulk | 160 ms | 122 ms | 120 ms | 6/6, 6/6 |
| sync, 4 stages | 160 ms | 128 ms | 126 ms | 6/6, 6/6 |
| sync, 8 stages | 158 ms | 124 ms | 121 ms | 6/6, 6/6 |

GSM8K (256 questions, distinct 25-shot prefixes, conc 64, 97.8% of prompt tokens
restored): cold 92.2%, layer-wise 93.0%, bulk 92.6%.

On this head: unit 282 passed, integration 19 passed / 1 skipped. The timings above
are to be re-measured, since #58568's batched loads and #59275's async fix change
the async and bulk rows.

## Open

- From a node-local DRAM pool the load is ~16 ms of a restore, so stages have little to
  overlap; the benefit has to be shown on slower tiers (remote RDMA reads, SSD).
- Layer-wise store stays disabled: MORI's ranged put requires one call to tile the
  whole object, so a block cannot be written layer by layer under one key.
