# [CI][ROCm] Give the M3 embed-sharing fixture a kernel_config

[Upstream PR](https://github.com/vllm-project/vllm/pull/62869) · state: closed · merged: True

## Original PR description

## Problem

`(MI355 DPX) V1 Executor + Worker` fails on every parametrisation of `test_m3_target_allocates_embedding_on_required_stage` with `AttributeError: 'types.SimpleNamespace' object has no attribute 'kernel_config'`.

Failing job: https://buildkite.com/vllm/amd-ci/builds/15124/list?sid=01a15db1-bce5-4cd0-a3c0-f39c922bfb4b

## Cause

#62712 wired `specialized_decode_config()` into `MiniMaxM3Model.__init__` on the AMD path, and that helper reads `config.kernel_config.monokernel` unconditionally. The `m3_config` fixture in this test builds a fake `VllmConfig` as a `SimpleNamespace` and never carried a `kernel_config`, so the constructor now raises before the test reaches its assertion. Both halves are correct on their own; the fixture simply was not updated alongside the new call.

Only the AMD variant is affected, because the fixture imports `vllm.models.minimax_m3.amd.model` on ROCm and the nvidia model has no `specialized_decode_config` call.

The last upstream nightly passed because it started before #62712 landed, not because upstream is unaffected. The same group will fail there on its next run.

## Fix

Give the fixture a `kernel_config` with `monokernel` disabled, which is the real `KernelConfig` default, so the model falls back to the non-specialized path and the test keeps asserting exactly what it asserted before. This matches the fixture style already used by the DSv4.1 mono decode tests added in #60731.

## Test plan

`pytest -v -s v1/worker/test_spec_decode_embed_sharing_pp.py` on MI355X, which is the command behind the failing CI step.
