# [Bugfix][Memory] Accurately profile CUDA graph memory for quantized/F…

[Upstream PR](https://github.com/vllm-project/vllm/pull/60673) · state: closed · merged: False

## Original PR description

[Bugfix][Memory] Accurately profile CUDA graph memory for quantized/FP8 KV caches (#60350)

When using quantized KV caches (such as fp8, int8), the block table and dequantization scale allocations per CUDA graph allocate additional memory during capture. Previously, _extrapolate_full_graph_memory used a 1 MiB per-graph floor, which under-budgeted full graph capture overhead by ~0.8 GiB across ~30 graphs and triggered out-of-memory errors during engine startup capture on 24GB GPUs.

This commit:
1. Introduces _MIN_QUANTIZED_PER_GRAPH_BYTES = 16 << 20 (16 MiB) floor when is_quantized_kv_cache(kv_cache_dtype) is true.
2. Propagates kv_cache_dtype from profile_cudagraph_memory to _extrapolate_full_graph_memory.
3. Adds regression unit tests covering quantized vs non-quantized extrapolation in test_gpu_model_runner_v2_cudagraph_profiling.py.

Fixes #60350.



## Overview

Accurately budgets CUDA graph memory for quantized/FP8 KV caches during memory profiling, preventing startup OOM errors during `capture_model()`. Fixes #60350.

## Claims

- **Prevents Startup OOM**: Correctly reserves ~0.5–0.8 GiB of CUDA graph memory headroom for FP8/INT8 KV caches across multi-size graph capture on 24 GiB GPUs (RTX 3090/4090).
- **Zero Overhead on Non-Quantized Paths**: Preserves the existing 1 MiB floor for FP16/BF16/unquantized models without reducing available KV cache block counts.
- **Unit Test Coverage**: Adds regression tests for `_extrapolate_full_graph_memory` across both standard and quantized (`fp8`, `fp8_e4m3`) cache dtypes.

## Details
## Root Cause

During worker initialization, profile_cudagraph_memory() samples the memory of the largest FULL CUDA graphs into a throwaway pool and extrapolates the total capture memory with _extrapolate_full_graph_memory().

Previously, _extrapolate_full_graph_memory floored per-graph overhead at _MIN_PER_GRAPH_BYTES = 1 << 20 (1 MiB). While sufficient for 16-bit unquantized KV caches, quantized caches (fp8, int8) hold smaller element sizes, creating 
2×2× more total blocks. During graph capture, allocating auxiliary scale factors and binding larger block tables consumes ~16–30 MiB per captured graph. For a typical batch schedule with ~30 full graphs, the 1 MiB floor underestimated graph capture memory by ~0.8 GiB, leaving insufficient headroom and triggering torch.OutOfMemoryError during the real capture_model() phase.

## Design Decisions
_MIN_QUANTIZED_PER_GRAPH_BYTES = 16 << 20 (16 MiB): Applied when is_quantized_kv_cache(kv_cache_dtype) evaluates to true.
Plumbing: profile_cudagraph_memory extracts kv_cache_dtype from runner.cache_config.cache_dtype and passes it to _extrapolate_full_graph_memory.

I’m not sure this is the right approach to fixing the underlying issue. If I understand correctly, increasing the minimum estimated memory per CUDA graph to 16 MiB would permanently reduce the available KV cache allocation for quantized KV cache configurations, even if the actual CUDA graphs don’t require that much additional memory.

My main concern is that we’re introducing a fairly arbitrary buffer here rather than fixing the underlying memory profiling. This effectively trades KV cache capacity for additional safety margins, which I don’t think is a great solution, especially since the actual overhead likely depends on the configuration.

I’d rather understand why we’re underestimating CUDA graph memory in the first place and fix the profiling to account for the actual allocations. Otherwise we’re potentially wasting a significant amount of GPU memory without knowing whether the 16 MiB is even sufficient or necessary.

Is there a reason we can’t address this in the profiling itself?

- Aravind0403 · comment · 2026-10-08T21:30:46Z · [source](https://github.com/vllm-project/vllm/pull/60673#issuecomment-6069435072)

Thanks @lucamotz, fair critique. I measured on an RTX 4090 (24 GB, CUDA 13.0, PyTorch 2.13) with `Qwen/Qwen2.5-1.5B-Instruct` (35 full graphs) to look at the numbers directly:

- **Negative sample deltas**: The sampled graph deltas came back negative (`-22 MiB` on FP8, `-24 MiB` on BF16), so the current estimate becomes `first_sample + (total_graphs - 1) * floor`. With the 1 MiB floor that evaluates to ~12 MiB for FP8 and ~10 MiB for BF16.
- **Actual capture memory** (measured):
  - **FP8 KV cache**: Real capture consumed **0.51 GiB** (~510 MiB deficit against the 12 MiB estimate).
  - **BF16 KV cache**: Real capture consumed **0.20 GiB** (~195 MiB deficit against the 10 MiB estimate).

On this model, the 1 MiB floor under-budgets for both dtypes, not just FP8. That supports your point: a static 16 MiB floor is an arbitrary constant and doesn't address why the samples collapse.

Two ways forward:
1. **Full capture during profiling** (`_max_full_descs_to_capture = None`): Measures all FULL graphs directly, so no heuristic is needed. Capturing all 35 graphs took ~4s on this model during engine warmup.
2. **Floor scaled by layer count and KV dtype**: Keeps profiling fast, but it is still a heuristic, and I'd want several models measured across different depths before trusting any formula.

If you prefer Option 1, I'm happy to rework this PR into that and validate it thoroughly on the RTX 4090. Let me know which direction you'd like!
