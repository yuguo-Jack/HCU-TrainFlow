# [ROCm] Update ROCm to 10.1 and MORI to v1.2.4 and amd-smi fixes

[Upstream PR](https://github.com/vllm-project/vllm/pull/62536) · state: open · merged: False

## Original PR description

## Overview

This PR updates the current ROCm `Dockerfile.rocm_base` to `10.1` and `MORI `to `v1.2.4`.

Things to note:

  * Cherry-picks over changes from https://github.com/vllm-project/vllm/pull/62531
  * `rocm-smi_lib` was removed from `10.1`
  * It's no longer necessary to `pip install amd-smi` anymore, its included in `10.1`
  * `MORI` version `v1.2.3.post1` doesn't have https://github.com/ROCm/mori/pull/663 but `v1.2.4` does, which builds with `10.1`
  *  The ROCR  fixes needed in `10.0` needed to be updated for `10.1` (applying the patch to the newer version in rocm-systems) [users/rasmith/10.1/hsa_gpu_edge_signal](https://github.com/ROCm/rocm-systems/compare/develop...users/rasmith/10.1/hsa_gpu_edge_signal)
  * `amd-smi` is the replacement for `rocm-smi`, but this broke a number of things:
    *  kv connector tests
    * any test that was using `rocm-smi` before
  * Fixed any breakage caused by the `rocm-smi` removal and made it use `amd-smi`
  * Needed to add a Python `.pth` file so `amd-smi` can always be found, without having to change the Dockerfile or always have to ensure one doesn't forget to add it to `PYTHONPATH`.  We might need to file an issue so that it gets installed properly through the usual Rock wheel installs.
  * `Ray` needed to be updated since the current version depends on `rocm-smi`, but the newer versions now use `amd-smi`.
  * Update the ROCm kernel symbol map tool to recognize the device code that ROCm 10.1's compiler produces, so kernel-based CI test selection keeps working, see https://github.com/vllm-project/vllm/pull/59100.


### Extra

   * `amd-smi --rocm-smi`

### Import and Install Ability

Since `amdsmi` is now included in 10.1 but is not a complete package,  I needed to add an `amdsmi` build step in the Dockerfile and make sure that the vLLM wheels would still work when users install them.  I wanted to detail the results of that here.

Every table below compares the same five vLLM builds. Tables that only concern this PR use the three 10.1 ones.

- **7.2.3** — vLLM v0.32.0, shipped.
- **10.0** — vLLM nightly, shipped.
- **10.1 base** (`bd84cb1a6f`) — this PR before the `.pth` was added. amdsmi via `ENV PYTHONPATH`.
- **10.1 .pth** (`513d206965`) — what the PR has carried since. amdsmi via a `.pth`.
- **10.1 PR** (`bc5e7f00d6`) — this change. amdsmi installed as a package.

The three 10.1 columns were measured on images built from those commits.

Every measurement is on one host with **8 GPUs** (gfx950 / MI355X), so a correct amdsmi reports 8. A 0 means it enumerated none.

#### How amdsmi reaches the user

| | 7.2.3 | 10.0 | 10.1 base | 10.1 .pth | 10.1 PR |
|---|---|---|---|---|---|
| In the image | Installed wheel | Installed, plus `ENV PYTHONPATH` | `ENV PYTHONPATH` | `.pth` file | Installed wheel |
| vLLM wheel pins amdsmi | ✅ | ✅ | ✅ | ❌ | ✅ |
| Loader patch | Not needed | `find_spec` lookup | None | None | `.patch` file |

#### In the Docker image

| | 7.2.3 | 10.0 | 10.1 base | 10.1 .pth | 10.1 PR |
|---|---|---|---|---|---|
| `import amdsmi` when CI sets PYTHONPATH | ✅ | ✅ | ❌ | ✅ | ✅ |
| Run a model when CI sets PYTHONPATH | ✅ | ✅ | ❌ | ✅ | ✅ |
| `pip show amdsmi` | ✅ | ✅ | ❌ | ❌ | ✅ |

**This is why the `.pth` was added.** CI's `run-amd-test.sh` sets `PYTHONPATH=/vllm-workspace`, replacing the `ENV PYTHONPATH` the base image relied on. `import amdsmi` then raises `ModuleNotFoundError`, vLLM falls back to `UnspecifiedPlatform`, and running a model fails with `RuntimeError: Device string must not be empty`. A `.pth` lives in site-packages, so nothing a caller puts in `PYTHONPATH` can displace it. An installed package has the same property. Without that override every column works, so the override is the whole of the difference.

#### Installing the vLLM wheel on a clean machine

A stock `python:3.12` container — no ROCm, no vLLM — with the GPUs passed through, following the install docs:

```bash
uv venv --python 3.12 --seed --managed-python
source .venv/bin/activate
uv pip install <that commit's vLLM wheel>
```

The vLLM wheel contains no amdsmi files and ships no `.pth`. It only declares `Requires-Dist: amdsmi==...`, and the index serves amdsmi as a separate 87 KB wheel that pip pulls in — the same arrangement as torch and triton.

Nothing from the ROCm image exists here, so each column is only what its own wheel brings:

| | base (pins unpatched) | .pth (pins nothing) | PR (pins patched) |
|---|---|---|---|
| `pip show amdsmi` | ✅ | ❌ | ✅ |
| `import amdsmi` on its own | ❌ `OSError` | ❌ `ModuleNotFoundError` | ✅ |
| `import torch`, then `import amdsmi` | ✅ | ❌ | ✅ |
| vLLM detects the GPUs | ✅ | ❌ | ✅ |
| Run a model | ✅ | ❌ | ✅ |

**`.pth` is the regression:** no pin, so no amdsmi, so `UnspecifiedPlatform` and `RuntimeError: Device string must not be empty`.

Two independent problems sit behind those red cells:

- **No pin.** The build pins whatever is *installed*, and a `.pth` installs nothing — so amdsmi quietly dropped out of the vLLM wheel's requirements. It was not removed on purpose.
- **An unpatched loader.** base does install amdsmi, but its copy cannot find the AMD SMI library unless something has already loaded it. vLLM survives this because it imports torch first. A bare `import amdsmi` does not.

The PR fixes both: an amdsmi wheel built from the SDK's own sources with the loader patched, installed in the image and pinned by the vLLM wheel.

#### Installing the vLLM wheel: inside the image, three ways

The same wheels, but installed **inside that commit's own vLLM image** rather than on a clean machine, with the image's own vLLM uninstalled first. The contrast with the table above is the point: here the image's `.pth` or `ENV PYTHONPATH` still exists and can rescue an install that the wheel alone would not. Three ways to make the environment — the image's system Python, a plain `python3 -m venv`, and the documented `uv venv --managed-python`.

| after installing that commit's wheel | base | .pth | PR |
|---|---|---|---|
| system `python3`: `import amdsmi` | ✅ | ✅ | ✅ |
| system `python3`: `pip show amdsmi` | ✅ | ❌ | ✅ |
| `python3 -m venv`: `import amdsmi` | ✅ | ❌ | ✅ |
| `uv venv --managed-python`: `import amdsmi` | ✅ | ❌ | ✅ |
| GPUs reported in a venv, after `import torch` (8 is correct) | **0** | no amdsmi to ask | **8** |
| which amdsmi a venv ends up using | the image's SDK copy, via `PYTHONPATH` | none | the venv's own |

**A `.pth` is the one mechanism a user's own virtual environment throws away.** It lives in the image's site-packages, so neither venv recipe sees it, and that state has no pin to install amdsmi instead.

**`ENV PYTHONPATH` surviving a venv is a liability, not a feature.** Base's pin does install amdsmi into the venv, but `PYTHONPATH` then shadows it with the image's SDK copy, which pairs with the venv's own torch and reports **0 GPUs** instead of 8 — a wrong answer rather than an error.

#### Building vLLM from source

Two kinds of editable install are tested:

```bash
python3 setup.py develop   # what the ROCm install docs prescribe. `pip install .` does not work there
pip install -e .
```

Both run inside that commit's own image against a bind-mounted checkout, with `PYTORCH_ROCM_ARCH=gfx950`, after removing the vLLM the image ships so it cannot shadow the build. They agree on every row below.

| after either editable install | base | .pth | PR |
|---|---|---|---|
| The build succeeds | ✅ | ✅ | ✅ |
| `pip show amdsmi` | ❌ | ❌ | ✅ |
| `import amdsmi` | ✅ | ✅ | ✅ |
| Run a model | ✅ | ✅ | ✅ |
| Run a model when CI sets PYTHONPATH | ❌ | ✅ | ✅ |

The last row is the developer-facing form of the CI failure: build editable on base under that `PYTHONPATH` and vLLM cannot run a model.

The docs' amdsmi step, which a source builder outside these images still needs:

| | 7.2.3 | 10.0 | 10.1 base | 10.1 .pth | 10.1 PR |
|---|---|---|---|---|---|
| The documented step runs clean | ✅ | ✅ | ❌ | ❌ | ✅ |
| Lines in that step | 1 | 2 | 2 | 2 | 4 |
| `pip show amdsmi` afterwards | ✅ | ✅ | ❌ | ❌ | ✅ |

The 10.1 SDK stopped shipping packaging metadata, so the documented `pip install` fails there. The PR's step supplies that metadata and the loader patch itself, and shrinks back to one line once a future SDK restores it.

Status note for anyone following the 10.1 switch: some independent perf data on the stack this PR builds (DeepSeek-V4-Pro TP8, 8x MI355X; ROCm 10.0 nightly image vs `rocm/vllm-dev:main-a9b727a6` on ROCm 10.1 with the same HIP/CLR runtime commit 4baa0670 this PR pins).

1. **aiter / DSV4.** With aiter at `v0.1.26` (the current `AITER_BRANCH` pin, which predates ROCm/aiter#7103), clang 24 compiles the cktile blockscale GEMM kernels into call stubs with scratch (ROCm/aiter#7099; 1,280 kernels in two modules). On DSV4 that costs, same node vs ROCm 10.0: 8k/1k conc128 TTFT +44%, TPOT +17%, total tok/s -15%; 1k/1k conc128 TTFT +34%, tok/s -5%; at conc 1/4/16/64 (8k) output tok/s -0.9% / -3.0% / -9.0% / -16.2%. The flag in ROCm/aiter#7103 fixes it (kernels verified statically and end to end; outputs bit-identical to the clang-23 build); one detail for the image build: the flag only affects fresh builds, an existing prebuilt .so in a JIT cache is imported as-is, so the aiter build in the image needs to include it. Swapping a single clang-23 `module_gemm_a8w8_blockscale_bpreshuffle_cktile.so` into the 10.1 image brings every number above back to within ~0.5%.
2. **`DEBUG_CLR_DEVICE_ORDERING_EDGE=2`.** Measured effect of this knob on the 10.1 runtime (now in the Dockerfile): without it median ITL is +2.2-2.4% and tok/s -0.8..-2.3% at conc 1/4/16/64; with it, ROCm 10.0 running 10.1's HIP/HSA matches 10.0 within +-0.2%.
3. **RCCL 2.30.7 behavior change (informational).** 10.1's DDA all-reduce path no longer skips gfx950 TP8 when `symmetricSupport` is set and the default `RCCL_DDA_THRESHOLD` goes 64 MiB -> 128 MiB; per the release branches (source reading, not bisected); in a profile this shows up as ~125 extra `__amd_rocclr_copyBuffer` per 8k prefill step (staging before `ddaAllReduceTreeIpc`), with no measurable end-to-end TTFT/throughput cost on DSV4 and gpt-oss (conc-1 and conc-16 swaps of the RCCL library either way), and ~0.8% lower KV capacity (222,620 vs 224,624 tokens at max-model-len 9472).

Caveats: 1-3 cells per arm; absolute throughput differed by up to ~35% between nodes in our pool, so only same-node contrasts are quoted. For anyone replicating on gpt-oss: median TTFT at conc 16 with fixed-length requests swung +-30% between identical configs, so we used mean TTFT / p99 / throughput instead (on those, 10.0 and 10.1 were equal).

**Environment.** 8x MI355X. A: `vllm/vllm-openai-rocm:nightly-5d35ce393` (vLLM 0.32.1rc1.dev602+g5d35ce393, torch 2.13.0+rocm10.0.0, HIP 7.15.26333, RCCL 2.30.4, clang 23). B: `rocm/vllm-dev:main-a9b727a6` (vLLM 0.1.dev1+ga9b727a61, torch 2.13.0+rocm10.1.0, HIP 7.16.26385 / CLR built from 4baa0670, RCCL 2.30.7, clang 24.0.0git d6f6cb691863). Both aiter 0.1.26 with byte-identical python and tuned CSVs.
