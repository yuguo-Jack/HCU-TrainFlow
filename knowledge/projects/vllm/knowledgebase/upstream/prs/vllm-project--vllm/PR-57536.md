# [Bugfix][ROCm] Fix GLM-5.3 kpool indexer block sizes

[Upstream PR](https://github.com/vllm-project/vllm/pull/57536) · state: open · merged: False

## Original PR description

  ## Purpose

  Fixes #54359: GLM-5.3-Flash kpool indexer overwrites its own KV cache.

  On ROCm, GLM-5.3-Flash compresses one indexer state from every
  index_kpool tokens. However, the generic ROCm indexer backend currently
  advertises the following kernel block-size support in token units:

  [1, MultipleOf(16)]

  This allows the complete KV manager block to be selected directly as the
  kernel block size.

  For index_kpool=4 and a 640-token manager block, this selects 640 tokens,
  which represents 160 compressed states. The paged-MQA kernels operate on
  pages of 32 or 64 states, so the block table is not split at the granularity
  used by the kernel.

  As described in
  #54359, this can cause
  multiple logical indexer pages to address the same physical cache slots,
  silently corrupting the indexer cache and degrading long-context retrieval.

  ## Changes

  - Add a cached kpool-aware indexer backend.
  - Scale paged-MQA state page sizes by index_kpool when advertising
    supported kernel block sizes.

  - Use the kpool-aware backend only for Glm5NextIndexerCache on ROCm.
  - Keep the non-ROCm path unchanged.
  - Keep the generic DeepSeek indexer backend unchanged.
  - Add regression coverage for both the 32-state and 64-state page cases.

  For index_kpool=4, the kpool-aware backend advertises:

  32 states × 4 tokens/state = 128 tokens
  64 states × 4 tokens/state = 256 tokens

  This causes the existing hybrid block-table implementation to split the
  manager block into correctly sized virtual kernel pages.

  ## Scope

  This change only affects the attention-backend metadata selected by the
  GLM-5.3-Flash kpool indexer on ROCm.

  It does not change:

  - KV cache allocation size;
  - model weights or model computation;
  - CUDA backend selection;
  - generic DeepSeek indexer behavior;
  - GPU kernels;
  - deployment or serving parameters.

  ## Validation

  Validation environment:

  - 8× AMD Instinct MI300X
  - gfx942:sramecc+:xnack-
  - ROCm 7.2
  - Tensor parallel size: 8
  - Model: GLM-5.3-Flash
  - index_kpool=4
  - Actual KV manager block size: 640 tokens
  - Prefix caching enabled

  The three changed files were copied to the MI300X validation container and
  syntax-checked:

  python3 -m py_compile \
    vllm/v1/attention/backends/mla/indexer.py \
    vllm/models/glm5next/common/attention.py \
    tests/v1/worker/test_gpu_model_runner.py

  Result:

  PY_COMPILE=PASS

  The current-main block-size declarations and the proposed kpool-aware
  declarations were then passed through select_common_block_size in the
  MI300X container.

  Results:
| Manager block | Before | Before states | After | After states | Virtual pages per manager block |
|---:|---:|---:|---:|---:|---:|
| 640 | 640 | 160 | 128 | 32 | 5 |
| 1280 | 1280 | 320 | 256 | 64 | 5 |
             

  GEOMETRY_ASSERTIONS=PASS

  For the production configuration, the important result is:

  manager block:  640 tokens
  index_kpool: 4 tokens/state
  old kernel block:640 tokens = 160 states
  fixed kernel block:28 tokens =  32 states
  virtual split: 640 / 128 = 5 pages

  The added regression test covers both mappings:

  pytest -q tests/v1/worker/test_gpu_model_runner.py \
    -k test_select_common_block_size_scales_kpool_pages_to_tokens

  The validation container uses an older backported vLLM runtime
  (v0.1.dev1+gfdd64a3db) and therefore cannot directly execute the complete
  current-main test module. Equivalent block-size selection assertions were
  executed successfully in the MI300X container. The repository regression
  test is intended to run in the current-main CI environment.

  ## Model correctness evidence

  The original reproducer and before/after results are documented in
  #54359:

  - distinct cache slots written: 864/4096 before and 4096/4096 after;
  - needle recall: 0/6 before and 8/8 after;
  - fixed-build coverage from approximately 6.7K to 1M prompt tokens.

  Detailed needle-in-a-haystack results are available in
  this issue comment.

  An independent MI325X/gfx942 confirmation is available in
  this issue comment.

  That independent result reports:

  - inconsistent top-k index sets before correcting the block-table granularity;
  - consistent top-k index sets across runs and TP ranks after correction;
  - needle recall improving from 1/3 to 3/3.

  This PR implements the kpool-aware backend selection described by that
  root-cause analysis.

  ## Duplicate check

  As of 2026-09-18,

  and no dedicated PR implementing kpool-scaled backend block-size selection
  was found.

  The original model-support PR,
  #53906, does not contain
  this fix.
