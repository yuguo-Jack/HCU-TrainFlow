# [Perf][Spec Decode] Pad DFlash draft inputs on extra programs of the same launch

[Upstream PR](https://github.com/vllm-project/vllm/pull/65488) · state: closed · merged: True

## Original PR description



## Overview

`prepare_dflash_inputs` pads its per-request and per-token output buffers up to `max_num_reqs` / `max_num_tokens` for CUDA-graph replay, and today the last request's program does all of that padding serially. This PR launches 32 extra programs in the same grid and splits the padding loops between them. Related: #58633 targets the same padding loop with a wider padding block; this is an alternative that stays one launch.

## Claims

- `prepare_dflash_inputs` device time drops to ~2.1 µs per call regardless of batch size, from 7.9–8.5 µs at 16K batched tokens and 5.3–5.8 µs at 8K (GB200).
- Host time per call is unchanged vs `main` (still a single launch).
- Outputs are unchanged: every output and padded buffer is bit-identical to `main`.

## Validation

Microbenchmark of `prepare_dflash_inputs` on one GB200 GPU, base `main` 79d0899cca. Verify batch with 8 query tokens per request (1 + 7 speculative steps), `max_num_reqs` 256, block size 64. Device time: CUDA graph of 20 calls, median of 30 replays. Host time: eager call-return, median of ~1,900 calls. "#58633" = that PR's diff applied to the same base.

| max_num_batched_tokens | reqs | device: main / #58633 / this PR (µs) | host: main / #58633 / this PR (µs) |
|---|---|---|---|
| 16384 | 1 | 8.52 / 8.31 / **2.11** | 32.3 / 34.0 / 33.1 |
| 16384 | 8 | 7.92 / 7.79 / **2.08** | 31.4 / 33.7 / 31.8 |
| 16384 | 32 | 7.89 / 8.17 / **2.12** | 31.9 / 34.2 / 31.7 |
| 8192 | 1 | 5.81 / 5.57 / **2.09** | 31.4 / 33.3 / 31.8 |
| 8192 | 8 | 5.30 / 5.17 / **2.08** | 31.6 / 33.3 / 32.1 |
| 8192 | 32 | 5.28 / 5.17 / **2.09** | 31.8 / 33.5 / 32.3 |

- In every row, all three variants write identical buffers (compared from the same sentinel-filled tensors).
- `pytest tests/v1/spec_decode/test_dflash_prepare_inputs.py`: 6 passed on GB200 (including the compile-once check).
- End to end: in a TP4 DFlash-style draft with 5 draft KV-cache groups (the call runs once per group per step), the padding cost went from ~58 µs to ~20 µs per decode step, about −0.2% to −0.4% of a 5–15 ms step. This is a small end-to-end gain; the claim is the per-call saving.

## Details

- Grid becomes `(num_reqs + 32, num_blocks)`. Programs with `req_idx >= num_reqs` (block 0 only) each take every 32nd padding block of each padding loop; the regular per-request programs no longer pad.
- `num_reqs` is passed as a kernel argument with `do_not_specialize`, since it is no longer `tl.num_programs(0)`.
- The padded ranges and values are the same as before; only which program writes them changes.
- Why not a wider padding block (#58633): on current `main` the padding already uses `BLOCK_SIZE = 128`, so the remaining cost is the single program walking the whole span, which a wider block barely reduces (see table), and #58633 adds ~2 µs host time. Spreading the span over more programs removes it without a second launch, which was the concern raised on #58633's earlier two-kernel version.

Co-authored with @fululi12, whose #58633 identified this padding loop as a hot spot.
