# [CI][ROCm][MoE] Add AITER_MOE_SORT_BACKEND MXFP4 DSV4 test coverage

[Upstream PR](https://github.com/vllm-project/vllm/pull/62976) · state: closed · merged: True

## Original PR description

## Purpose

Implements item 3b from the progress tracker in #54966 ("Test AITER backend and dispatch settings"): coverage for the `AITER_MOE_SORT_BACKEND` row ("Adaptive MXFP4 sorting"). Item 3a (#58393) added spawned-subprocess env-var-matrix coverage for the other three vars in that section (`AITER_USE_CK_MOE_SORTING` / `AITER_USE_FLYDSL_MOE_SORTING` / `VLLM_ROCM_AITER_MOE_DISPATCH_POLICY`) but explicitly deferred `AITER_MOE_SORT_BACKEND` — that PR's description notes it "only fires on the MXFP4 path... not yet wired into `AiterExperts`", since at the time there was no way to drive `AiterExperts` through the MXFP4 W4A4 path in the modular-kernel test harness.

That blocker is now resolved: #60886 added MXFP4 W4A16/W4A4 oracle support and `MK_QUANT_CONFIGS` entries, and #60322 split `AiterExperts` into quant-specific subclasses including `AiterMxfp4Experts`. This PR adds the deferred coverage now that it's possible.

## What `AITER_MOE_SORT_BACKEND` does

It's a module-level global read once at `aiter` import time (`_MOE_SORT_BACKEND = os.environ.get("AITER_MOE_SORT_BACKEND", "auto")`), the same import-time-caching behavior as the vars #58393 already covers. It's only consulted when aiter's internal `output_aux` flag is set. aiter sets this unconditionally for a handful of MXFP4 a4w4 kernel families it ships — including the DeepSeek-V4.1 (DSV4) path this PR tests, and Kimi-K3's SiTU path (in fact the shape aiter's own adaptive/Opus crossover heuristic is tuned against). DSV4 is the only one of these the modular-kernel test harness can currently drive end-to-end — Kimi-K3's SiTU activation is real and default-enabled in production (`VLLM_ROCM_USE_AITER_MOE_SITUV2="auto"`), but this test file currently marks it not-yet-implemented (`is_nyi_config()`) pending harness support for its weight-shuffle conversion path; that's tracked as a separate follow-up, out of scope here. No vLLM source change is required to exercise the DSV4 path this PR adds; this is purely a test-coverage gap.

Note on naming: despite being called "a4w4"/"W4A4" (aiter's own env var name, and the terminology #54966's table uses), DSV4 is reached through vLLM's **W4A16** modular-kernel quant key pair — activations aren't pre-quantized at that layer. AITER's DSV4 kernel quantizes them to 4-bit internally, which is where the "a4w4" name comes from.

## Why this matters

`VLLM_ROCM_USE_AITER_MOE_A4W4_DSV4` is a real production MoE path for DeepSeek-V4.1 on AMD, used when the specialized mono-decode kernel can't be used (for example expert-parallel or data-parallel deployments); it's validated against the model type and the installed AITER build version in `FusedMoEConfig.__post_init__`, not a debug flag. `adaptive` and `opus` are two distinct kernels in aiter rather than just a flag toggle: `adaptive` is a shape-restricted fast path, and `opus` is its fallback. Without this test, aiter silently falling back to `opus` for shapes `adaptive` is supposed to cover would regress performance without failing anything, which is exactly the kind of silent-fallback gap #54966 flagged as untested.

## Changes

- `modular_kernel_tools/common.py`: adds a `use_mxfp4_w4a4_dsv4` `Config` flag that opts a spawned worker into `VLLM_ROCM_USE_AITER_MOE_A4W4_DSV4` and a `deepseek_v41` `hf_config.model_type` (required by `FusedMoEConfig.__post_init__`'s DSV4 gate), and converts weights via the production `convert_weight_to_mxfp4_moe_kernel_format(..., use_separated_a4w4=True)` path (DSV4's SEPARATED gate/up layout) instead of the gpt-oss INTERLEAVE converter used by the existing W4A16 test. It reuses `config.mxfp4_backend` (the same derived property the gpt-oss branch and production call sites already use) rather than a hardcoded backend constant. It also fixes a latent bug in `reference_moe_impl()`'s W4A16 oracle branch, which unconditionally assumed `SWIGLUOAI` activation — this fired incorrectly for the new DSV4 case too, which uses the default `SILU` activation, and surfaced immediately as a failure in the new test.
- `test_modular_kernel_combinations.py`: adds `test_aiter_moe_sort_backend_dispatch_env_matrix_mxfp4`, parametrized over `AITER_MOE_SORT_BACKEND` in `{opus, ck, adaptive, auto}`, using `AiterMxfp4Experts` on a real DeepSeek-V4.1-tuned MXMOE shape (`E=384, K=5120, N=640, topk=6, M=16`) confirmed against the installed `aiter` build's tuned kernel config CSV. The test skips (via `config.is_valid()`) rather than asserts on hardware support, since `AiterMxfp4Experts` requires gfx950 and this file currently also runs unconditionally on the MI300 (gfx942) CI lane (`.buildkite/test-amd.yaml`); it will exercise the real dispatch path once #62907 lands gfx950 CI coverage for this file.
