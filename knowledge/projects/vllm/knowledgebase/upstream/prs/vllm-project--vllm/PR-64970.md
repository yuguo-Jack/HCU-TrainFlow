# [Bugfix][GDN] Preserve Torch exp precision in fused prefill

[Upstream PR](https://github.com/vllm-project/vllm/pull/64970) · state: open · merged: False

## Original PR description



## Overview

Use `tldevice.exp(g)` instead of `tl.exp(g)` for the final gate in fused FlashInfer GDN prefill, restoring the Torch-compatible operation used before [#64419](https://github.com/vllm-project/vllm/pull/64419). Keep fusion and the single launch. The fix has no model or GPU-architecture guard.

## Claims

- Restore Torch gate precision without changing Q/K/V/beta or log-gate preparation.
- Preserve the existing API, compiler settings, warmup and pure-decode paths.

## Validation

On RTX PRO 6000 Blackwell, Torch 2.14.0 and Triton 3.8.0:

| Exp implementation | Maximum difference from Torch in GPU fixtures |
|---|---:|
| Fast `tl.exp` | 26 ULP |
| Fused libdevice | 0 ULP |

A separate CPU instruction simulation over 65,536 FP32 inputs in [-80,0], using ideal exp2 and a 100-digit mathematical reference, gives maximum errors of 61 ULP fast versus 1 ULP compensated. This is simulation, not GPU SFU accuracy.

**Regressing weights:** [nvidia/Qwen3.8-Flash-Next-NVFP4](https://huggingface.co/nvidia/Qwen3.8-Flash-Next-NVFP4/tree/fc694b54fb0174e0913e6adf86691ef85a4ead47), revision `fc694b54fb0174e0913e6adf86691ef85a4ead47`.

With the `get_current_weather` tool, temperature 0, max_tokens 512, nonstreaming and both thinking flags false:

| Exact prompt | Fast exp | Restored Torch exp |
|---|---|---|
| `What's the weather like in Tokyo?` | No tool call | Tokyo call |
| `What's the weather in Tokyo and in Paris? Use the weather tool for each city.` | Tokyo call only | Tokyo and Paris calls |

Each case passes 0/5 → 5/5 → 0/5 when switching fast → Torch → fast. Full tool suite: 8/10 → 10/10 → 8/10. The split-Torch control also changes launch/allocation behavior, so it does not alone prove rounding-only causality. Latest fused-libdevice model checks were thinking-on only: 10/10 tools, strict JSON and two long/cached-prefix recall checks passed.

A private reasoning-on comparison observed **2.6% more tokens per usable answer** after the integration update:

| Integration | Raw correct | Usable | Caps | Errors | Tokens/attempt | Tokens/usable |
|---|---:|---:|---:|---:|---:|---:|
| Old | 791 | 772 (96.5%) | 27 | 0 | 2,782.93 | 2,883.87 |
| New fast exp, normalized | 780 | 760 (95.0%) | 40 | 0 | 2,809.68 | 2,957.55 |

Counts are per 800 attempts; the new row is normalized from 360 observations. Token costs include unsuccessful/capped outputs. This historical comparison has substantial uncertainty and does not isolate exp rounding or establish recovery.

Five GPU regression cases passed on the prior precise integration, covering gate equality, real prefill, continuation and cached state. The generalized patch compiles without GPU execution for SM90/SM100/SM120; executable PTX matches that precise specialization. Lint/mypy pass. Clean-upstream GPU/model validation remains pending; broader model-quality impact and whole-model speed are unverified.

```bash
python -m pytest -q tests/kernels/mamba/test_gdn_prefill_flashinfer.py \
  -k 'fused_gate_matches_torch or qwen4_prefill_preserves_gate_rounding_and_continuation'
```

## Details

`tl.exp` uses a rounded multiply by log2(e) followed by approximate exp2; Torch/libdevice uses compensated range reduction. Both are FP32, but their outputs differ. The runtime fix changes two lines: the import and final exp call.

Duplicate searches found no matching fix. Related work: [#60105](https://github.com/vllm-project/vllm/pull/60105) (gate conversion), [#64498](https://github.com/vllm-project/vllm/pull/64498) (state access), [#54146](https://github.com/vllm-project/vllm/pull/54146)/[#62119](https://github.com/vllm-project/vllm/pull/62119) (state precision).
