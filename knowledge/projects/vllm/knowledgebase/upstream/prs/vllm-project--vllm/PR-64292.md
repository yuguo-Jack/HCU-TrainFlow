# [Bugfix] Reject logprobs counts exceeding vocab size at validation

[Upstream PR](https://github.com/vllm-project/vllm/pull/64292) · state: open · merged: False

## Original PR description

## Overview

Fixes the validation gap reported in #64291: requests with `logprobs` / `prompt_logprobs` counts larger than the model's vocab size passed `SamplingParams._validate_logprobs()` when `max_logprobs` (default 20) exceeded the vocab size, then crashed the worker at `torch.topk` with `RuntimeError: selected index k out of range` instead of being rejected with a 4xx at request validation. Cap the effective limit at `min(max_logprobs, vocab_size)` so such requests are rejected during validation.

Not a duplicate: searched open issues and PRs (`logprobs vocab size`, `max_logprobs`, `logprobs validation`); the nearest items (#60357/#60718 rank semantics, #60095/#63919 logprob kernel performance, #63803 beam-search `max_logprobs`) do not address request validation.

## Claims

- A request with `logprobs=20` (or `prompt_logprobs=20`) against a `vocab_size=10` / `max_logprobs=20` model is now rejected in `_validate_logprobs()` with `VLLMValidationError` instead of crashing `compute_topk_scores()` in the GPU worker.
- `max_logprobs == -1` semantics (vocab-size cap) are unchanged; counts up to the vocab size, including `logprobs=-1`, still pass.
- No behavior change for real models (`vocab_size >> max_logprobs`): the cap is a no-op there.

## Validation

Reproducer (mock config `vocab_size=10, max_logprobs=20`, RTX 5070 Ti, current main):

- Before the fix: `_validate_logprobs()` accepts `logprobs=20`; `compute_topk_scores()` on `[2, 10]` logits with `num_logprobs=20` raises `RuntimeError: selected index k out of range`.
- After the fix: validation raises `VLLMValidationError` (`"which is greater than max allowed: 10"`) for both `logprobs=20` and `prompt_logprobs=20`; `logprobs=10`, `prompt_logprobs=10`, `logprobs=-1`, `prompt_logprobs=-1` still pass.

New regression tests in `tests/v1/sample/test_logprobs.py` were confirmed to fail on the pre-fix commit and pass after:

```
.venv/bin/python -m pytest tests/v1/sample/test_logprobs.py -k "validation" -q
# pre-fix:  2 failed (test_logprobs_validation_rejects_counts_above_vocab_size)
# post-fix: 7 passed

.venv/bin/python -m pytest tests/test_sampling_params.py tests/v1/sample/test_trace_replay_params.py tests/test_request_input_bounds.py -q
# post-fix: 149 passed
```

No output/accuracy impact: the change only moves a rejection from the worker to request validation and is a no-op when `max_logprobs <= vocab_size`; no model evaluation needed.

## Details

Root cause: `_validate_logprobs()` substituted `vocab_size` for the cap only when `max_logprobs == -1`; a positive `max_logprobs` was used verbatim even when larger than the vocab, while the worker's `compute_topk_scores()` calls `torch.topk(logits, num_logprobs)` on the raw request value (`SamplingStates` only resolves `-1` to the vocab size). The fix keeps the policy in one place (validation), so the worker is never handed an out-of-range `k`.

Trade-off: `--max-logprobs` values larger than the vocab are now effectively clamped at validation time. This only affects configurations that previously produced guaranteed worker crashes, and `prompt_logprob_token_ids` widths are validated against the same effective cap for consistency.
