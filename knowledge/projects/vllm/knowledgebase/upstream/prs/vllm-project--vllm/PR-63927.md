# [Perf][KV Offload] Keep offload event metadata out of the cyclic GC

[Upstream PR](https://github.com/vllm-project/vllm/pull/63927) · state: closed · merged: True

## Original PR description



## Overview

`OffloadingEventsTracker` keeps one `_OffloadEventMetadata` entry for every chunk resident in any offload tier, and each entry held three objects tracked by Python's cyclic GC. With a large secondary tier, these entries make up most of the EngineCore's long-lived heap, so every full collection pauses the scheduler for over 100 ms. This PR keeps the entries out of the cyclic GC.

Not a duplicate. The only open PR touching this class is #63129 (draft). It fixes a separate correctness problem: metadata loss when an `OffloadKey` is reused. It doesn't change how entries are tracked.

## Claims

- Each event-metadata entry goes from 3 GC-tracked objects to 0.
- In a cold-cache KV-offload serving run, the full-collection pause drops from 106 to 31 ms and ITL p99 from 119 to 55 ms, and req/s rises 7%. That is within 1.5% of the same run with GC disabled.
- No behaviour change: residency bookkeeping keeps `set` semantics, and the emitted events are unchanged.

- **Engine:** `vllm serve Qwen/Qwen3-0.6B --load-format dummy`, with `OffloadingConnector` + `TieringOffloadingSpec`: an 8 GiB CPU primary tier plus a KVCR secondary tier with 65,536 slots. KV events and `self_describing_kv_events` are on.
- **Mocks:** only the model forward and the GPU↔CPU copies are mocked, by a `UniProcExecutor` subclass passed via `--distributed-executor-backend`. A step is modeled as 10 ms plus 3 µs per prefill token. No GPU is used.
- **Load:** 64 concurrent unique 8K-token prompts, 128 output tokens.
- **Runs:** one 90 s window per arm, back to back, on `41f5146b5b`. There are no offload-path changes between that commit and this branch's base. The GC-disabled reference is a 30 s window.
- **Measurement:** pauses come from `gc.callbacks`, and object counts from `gc.get_objects()` at the end of the window. I can share the mock executor.

## Details

**Why each entry had three tracked objects:**
- the slotted dataclass, since dataclass instances are always tracked;
- the `active_residencies` `set`;
- one `(Medium, ownership)` tuple per secondary residency. `Medium` members are tracked objects, so the collector never untracks that tuple.

**The change:**
- `_OffloadEventMetadata` is now a `msgspec.Struct` with `gc=False`, the same pattern `KVCacheEvent` uses. Its fields are hashes, token ids, ints, strings and a shared `NamedTuple`, so an entry can't be part of a reference cycle.
- `active_residencies` is now an `int` bitmask. A `(medium, ownership)` pair gets the next bit the first time a store expects its removal. The table belongs to the tracker, survives `reset()`, and is bounded by the number of distinct tier/ownership pairs. A removal for a pair that was never registered clears nothing, as `set.discard` did.

`freeze_gc_heap()` doesn't help here, because it only freezes objects that exist at startup. The largest remaining source of scanned objects is the CPU tier's per-chunk `ChunkStatus`, which this PR leaves alone.
