# [Bugfix][Kernel] Use GegluTanh for GELU_TANH in the FLASHINFER_CUTLASS MoE backend

[Upstream PR](https://github.com/vllm-project/vllm/pull/64505) · state: open · merged: False

## Original PR description

## Overview

`flashinfer_cutlass` runs erf-GeGLU for MoE experts whose activation is `gelu_pytorch_tanh` (`MoEActivation.GELU_TANH`, e.g. Gemma 4), even though FlashInfer's CUTLASS fused MoE implements the exact tanh GeGLU (`ActivationType.GegluTanh`, FlashInfer >= 0.6.14, flashinfer-ai/flashinfer#3501). This PR maps `GELU_TANH` to `GegluTanh` at the CUTLASS call site only.

Related: #45354 (same goal, but changes the shared mapping, which breaks the TRT-LLM NVFP4 MoE; see Details), #56839 (closed in favour of #45354), #55238 (B200 report of the erf/tanh mismatch).

## Claims

- `FlashInferExperts` (`--moe-backend flashinfer_cutlass`) passes `ActivationType.GegluTanh` for `MoEActivation.GELU_TANH`, so its expert activation matches the model's `gelu_pytorch_tanh` and the b12x backend (which already maps `GELU_TANH` to `"gelu_tanh"`).
- No behaviour change for any other backend or activation. In particular, the TRT-LLM-gen NVFP4 MoE, which is the default NVFP4 backend on SM100, keeps `Geglu`. Its kernel rejects `GegluTanh`.

## Validation

We run this in production and have tested it extensively on SM120 (RTX Pro 6000). Re-tested recently with vLLM 0.31.0 and vLLM main nightly, FlashInfer 0.7.0post1 and FlashInfer 0.7.2.

Model used: `nvidia/Gemma-4-26B-A4B-NVFP4` (modelopt NVFP4 W4A4)

## Details

`activation_to_flashinfer_type()` maps `GELU_TANH` to `ActivationType.Geglu` for all MoE backends, which uses the `erf` GeGLU.

MoE models trained with GeGLU-Tanh gates, such as Gemma4 26B A4B, have a systematic (small) numerical drift. This PR is a correctness fix.

Issue with changing the shared map:
* `TrtLlmNvFp4Experts` lists `GELU_TANH` as [supported](https://github.com/vllm-project/vllm/blob/fa1cf1d436a0364a230c56f8e2c53a3d5043d231/vllm/model_executor/layers/fused_moe/experts/trtllm_nvfp4_moe.py#L238)
* The TRT-LLM FlashInfer [backend does not support GeGLU-Tanh](https://github.com/flashinfer-ai/flashinfer/blob/f416759b9c97e40ad21ad6fa5b5534ac8b60d4ed/csrc/trtllm_fused_moe_runner.cu#L120)
* The oracle [picks FLASHINFER_TRTLLM first](https://github.com/vllm-project/vllm/blob/c1b7dffa1457f4ffe7eafb08092eb2505a9651e4/vllm/model_executor/layers/fused_moe/oracle/nvfp4.py#L215 ) on hardware that supports it (includes SM100)

So this PR overrides only in the `FLASHINFER_CUTLASS` path.

The new test is a sibling of the existing `test_flashinfer_swigluoai_params_are_forwarded`, with the same monkeypatched kernel.

**Limitations and alternatives**:
* This does not fix FLASHINFER_TRTLLM, that one needs a change in FlashInfer
* I haven't checked if the better move is to change the shared mapping and introduce an override only for FLASHINFER_TRTLLM. This depends on whether other MoE backends support the Tanh version.
