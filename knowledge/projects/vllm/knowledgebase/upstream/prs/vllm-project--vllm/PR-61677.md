# [ROCm] Re-bump AITER to v0.1.25 and pin the DSv4.1 mono reference MoE

[Upstream PR](https://github.com/vllm-project/vllm/pull/61677) · state: closed · merged: False

## Original PR description

[DO NOT MERGE]

[ROCm] Re-bump AITER to v0.1.25 and pin the DSv4.1 mono reference MoE



## Overview

Re-lands the AITER v0.1.25 bump (#61230), which #61559 reverted because `tests/models/test_dsv41_mono_numerics.py::test_mono_decode_layer_matches_vllm[4]` failed. The failure came from AITER v0.1.25's new DSv4.1 tuned MoE configs changing the reference's numerics, not from a mono-kernel bug. This PR pins the test's reference MoE to AITER's base tuned table.

## Claims

- ROCm base images (`Dockerfile.rocm_base`, `Dockerfile.rock_base`) move from AITER v0.1.24.post1 to v0.1.25.
- `test_mono_decode_layer_matches_vllm[2]` and `[4]` pass on AITER v0.1.25 (MI355). At TP4, mono vs reference MoE is back to 0.49% relative error, from 1.53%.
- No change to the mono kernels or to production kernel selection.

## Details

**Root cause.** The mono kernel re-implements AITER's a8w4 `fused_moe` numerics. That includes quantizing the stage-2 input to MXFP8 the way the standalone `fused_dynamic_mxfp8_quant_moe_sort` does: values rounded to bf16 first, scale exponent `ceil(log2(amax / 448))`.

AITER v0.1.25 adds `aiter/configs/model_configs/dsv41_fp8_tuned_fmoe.csv`. For TP4 (intermediate 576, padded to 640) at M=4/8, it selects `_fp8` stage-1 kernels such as `flydsl_moe1_afp8_wfp4_bf16_t32x128x256_w2_gui_fp8`. These fuse that quant into the stage-1 epilogue with a different rule: quantize from f32, exponent `round(log2(amax)) - 8` (`mixed_moe_gemm_2stage_common.py` in AITER). For blocks with amax mantissa in about [1.41, 1.75), the fused rule picks a 2× larger scale. Both are valid MXFP8, but the reference drifted from 0.49% to 1.53% against mono, just past the limit. TP2's rows (intermediate 1152) at the test's batch use unfused kernels, which is why only TP4 failed.

**Fix.** In the Ray worker, `_mono_numerics` sets `AITER_CONFIG_FMOE` to AITER's base `tuned_fmoe.csv`. The reference MoE then uses the quant mono implements, independent of which tuned kernels a given AITER release picks for DSv4.1 shapes.

**Tradeoffs and limitations.**
- On the non-mono path, production TP4 decode still uses the fused-quant kernels. Its MoE numerics differ from mono's by about 1.5% relative. Both are legitimate MXFP8 roundings.
- The proper fix belongs in AITER: make the fused `_fp8` epilogue use the same scale rule as `fused_dynamic_mxfp8_quant_moe_sort`, so numerics don't depend on tuner choice. AITER issue: TODO. AITER `main` (2026-10-14) still has the same rule and rows.
- The `.buildkite/test_areas/models_basic.yaml` trigger on `docker/Dockerfile.rocm_base` (added in #61559) is kept, so AITER bumps run the mono tests.

**Not a duplicate.** This follows up the #61559 revert. Open PR search for an AITER v0.1.25 re-bump: TODO.
