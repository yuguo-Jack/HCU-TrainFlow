# [KV Connector] Per-connector "enable_kv_events" switch for KV cache events

[Upstream PR](https://github.com/vllm-project/vllm/pull/61893) · state: open · merged: False

## Original PR description



## Overview

`--kv-events-config` currently turns on the engine's GPU prefix-cache events and every KV connector's events together. This PR adds a per-connector opt-out: `"enable_kv_events": false` in a connector's `kv_connector_extra_config`. With it, a deployment can publish GPU events without, for example, a shared MooncakeStore's events.

## Claims

- New `kv_connector_extra_config` key `enable_kv_events`, default `true`, so existing behavior is unchanged. When set to `false`, that connector's events are left out of the published `KVEventBatch`; the engine's own GPU events are still published.
- Applies to every connector without per-connector code:
  - The scheduler applies the switch to the configured connector.
  - `MultiConnector` applies each child's own setting.
  - So the key can be set on a single child, or once on the `MultiConnector` to cover all of its children.
- Connectors that opt out are still drained every step, so their buffered events do not accumulate.
- `MooncakeStoreConnector` checks the switch at startup. When it is off, it skips building store events, including tracking prompt token IDs for them.

## Details

**Motivation.** A KV-aware router uses events to learn which blocks each worker holds on GPU. A shared external store like MooncakeStore does not belong to the instance that publishes its events, which causes three problems:
- Its `BlockStored` events are announced by whichever instance wrote the block.
- No removal is published when the store evicts the block.
- A router that indexes these events per worker therefore grows its lower-tier index without bound and attributes shared-pool blocks to one worker.

Today the only way to keep these events out is to disable KV events entirely, which also removes the GPU events the router needs.

**Design.**
- Every connector overrides `take_events()`, so the filter is applied at the two places that collect events for publishing: `Scheduler.update_from_output` and `MultiConnector.take_events`.
- Two small helpers in `kv_connector/v1/base.py` implement this, so no connector needs to change for the switch to take effect:
  - `connector_kv_events_enabled(vllm_config)` returns whether KV events are enabled and the connector has not opted out.
  - `take_connector_kv_events(connector, publish)` drains the connector's events and drops them when `publish` is false.
- `MultiConnector` computes each child's flag once, from the child's own `kv_transfer_config`.
- The key name matches the existing per-tier `enable_kv_events` of OffloadingConnector's FS/OBJ tiers, and LMCache's own `enable_kv_events` setting.

**Behavior with KV events disabled globally.** Unchanged. Connector events used to go to the null publisher; they are now drained without publishing.

**Limitations and follow-ups.**
- Other connectors that build events (OffloadingConnector, SimpleCPUOffloadConnector, LMCache) still build them when opted out; the events are dropped at collection. They can check `connector_kv_events_enabled` to skip that work.
- MooncakeStore's store path publishes `medium="cpu"` rather than `MEDIUM_CPU` (`"CPU"`). That will be a separate PR.
