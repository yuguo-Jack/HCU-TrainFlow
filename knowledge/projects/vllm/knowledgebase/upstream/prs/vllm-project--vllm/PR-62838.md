# [Bugfix][Mooncake] Forward decode errors through proxy

[Upstream PR](https://github.com/vllm-project/vllm/pull/62838) · state: open · merged: False

## Original PR description



## Overview

Fixes #62559 by opening the Mooncake proxy's Decode response before committing downstream headers, allowing Decode failures to retain their HTTP status, response body, and Content-Type.

## Claims

- Forward Decode response status, Content-Type, and body through both completion endpoints in streaming and non-streaming modes.
- Preserve healthy JSON and SSE response behavior without buffering the upstream body.
- Release the upstream response when downstream streaming completes or closes.
- Add focused CPU regression coverage through the real FastAPI routes and HTTPX transport boundary.

## Details

The original request flow was:

1. The proxy constructed a `StreamingResponse` with its default HTTP 200 status.
2. Starlette committed those downstream headers before iterating the body.
3. The body iterator then opened the Decode response and called `raise_for_status()`.
4. A Decode HTTP 500 therefore raised after HTTP 200 had already reached the client, resulting in a truncated response instead of the Decode error.

The updated flow opens the Decode response with `AsyncClient.send(..., stream=True)` before constructing `StreamingResponse`. The proxy can therefore use the upstream status and Content-Type while continuing to forward the body incrementally. A `finally` block closes the upstream response after normal completion, body failure, or downstream iterator closure.

Only Content-Type is copied from the upstream response. This avoids forwarding stale Content-Length or hop-by-hop headers. If Decode omits Content-Type, the proxy retains its previous JSON/SSE fallback based on the request's `stream` setting.

Network failures that occur before Decode produces an HTTP response remain proxy-side failures and are outside this change's scope. Prefill scheduling, transfer metadata, Mooncake KV transfer, and Decode error generation are unchanged.

File: `examples/disaggregated/mooncake_connector/mooncake_connector_proxy.py` · line 342

[P2] Close the eagerly opened response even if the body never starts

The upstream response is now opened before constructing `StreamingResponse`, but its cleanup only runs inside this async generator. If ASGI `send(http.response.start)` fails before the first iteration, the generator never enters its `try`, so this `finally` is never executed. Even explicitly calling `aclose()` on that unstarted generator does not close the already-open HTTPX response.

A real upstream HTTP probe through the FastAPI route leaves that response and connection open after the header-send failure; the base does not open an upstream connection in this case. Please tie upstream cleanup to the entire ASGI response invocation, including header sending, and add this early-failure regression. A background task alone would not cover an exception that exits the response call before background tasks run.
