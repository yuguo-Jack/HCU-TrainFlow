# [Bugfix] Reject a KV cache dtype that silently reinterprets the model's bits

[Upstream PR](https://github.com/vllm-project/vllm/pull/54338) · state: open · merged: False

## Original PR description

## Overview

`--kv-cache-dtype float16` on a bfloat16 model (or `bfloat16` on a float16 model) is accepted at
config time. The C++ cache writers then store the model dtype's bits in a cache that is read back
as the requested dtype. On the MLA path this produces fluent nonsense with no error on v0.30.0
(measured below); v0.31.0 has the same `kAuto` mapping and no config check. This PR rejects that
pair at config time. Related: #38922, #43330.

## Claims

- **Bug:** with an explicit unquantized cache dtype that differs from the model dtype, every C++
  `DISPATCH_BY_KV_CACHE_DTYPE` write copies raw bits instead of converting. Reachable silently
  on stock vLLM through `concat_and_cache_mla` (measured on ROCm), and through
  `reshape_and_cache_flash` on CUDA by the same macro (#38922's traceback shows the CUDA flash
  backend entering it; not measured here).
- **Root cause:** `get_fp8_kv_cache_data_type` maps `auto`, `float16` and `bfloat16` to `kAuto`,
  and the `kAuto` arm instantiates only same-type pairs (`FN(uint16_t, uint16_t)`,
  `FN(__nv_bfloat16, __nv_bfloat16)`), identically in `amd/` and `nvidia/quant_utils.cuh`. The
  cache tensor is allocated at the requested dtype, so writer and reader disagree.
- **Fix:** `VllmConfig._verify_unquantized_kv_cache_dtype()` raises a `ValueError` that names
  both dtypes. `auto`, a cache dtype equal to the model dtype, and every quantized dtype are
  unchanged.

## Validation

checked byte-identical to the `v0.30.0` tag, then this PR's diff was applied to them for the
"with this PR" column and removed again afterwards.

The two failures are the two mismatched pairs; the six supported pairs (`auto`, the model's own

| DeepSeek-V2-Lite bf16, MLA (`concat_and_cache_mla` called 378 times) | `auto` | `' Paris.\nThe currency of France is the Euro'`, cache max 17.875 | same |
| same | `float16` | **`' Paris, and\n\n\nParis\nParisParis'`**, cache max 2.7793, no error | config error, no cache write |
| Qwen3-0.6B bf16, `ROCM_ATTN` | `auto` | `' Paris. The capital of Italy is Rome. …'` | same |
| same | `float16`, block 16 and 64 | Triton `CompilationError` | config error |
| Qwen3-0.6B fp16, `ROCM_ATTN` | `bfloat16`, block 16 and 64 | Triton `CompilationError` | config error |

already fails loudly, later and with an unrelated-looking error; there this PR only moves the
failure to config time. Independently of this PR, `ROCM_ATTN` also rejects a *matching* explicit
dtype at block size 16 (`Unsupported KV cache dtype: bfloat16`); that is a separate issue and is
unchanged here.

## Details

- **Why reject instead of convert:** a conversion needs new template instantiations in both
  vendors' `quant_utils.cuh`. Rejecting restores the loud failure that #38922 removed while
  fixing its crash. A follow-up can add the conversion and remove this check.
- **Behaviour change:** the check also rejects the pair where the writer does convert (the Triton
  writer's `tl.store` converts). Both dtypes are 16-bit, so the pair saves no memory.
- **Reach:** 25 attention backends list `float16` and/or `bfloat16` in
  `supported_kv_cache_dtypes`, including `FlashAttentionBackend`, so backend validation accepts
  the request. #43330 (merged) opened explicit native dtypes in the Triton writer; its case
  (cache dtype equal to model dtype) is still accepted here.
- **Not a duplicate:** on 2026-10-03, and again on 2026-10-05, I searched open and merged PRs and issues for `kAuto`,
  `DISPATCH_BY_KV_CACHE_DTYPE`, `reinterpret`, `kv-cache-dtype bfloat16` and `38922`. Only this
  PR touches the check. `main` (`34051ad714`) and v0.31.0 still map all three strings to `kAuto`
  and have no config check.
- **Limitations:** measured on gfx90a only. The CUDA claim comes from the identical macro and
  #38922's traceback, not from a CUDA run.
