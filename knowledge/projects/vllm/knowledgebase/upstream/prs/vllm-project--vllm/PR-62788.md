# [Bugfix][Frontend] Only stream echoed prompt_token_ids when return_token_ids is set

[Upstream PR](https://github.com/vllm-project/vllm/pull/62788) · state: open · merged: False

## Original PR description

## Overview

Streaming `/v1/completions` requests with `echo=true` put the full `prompt_token_ids` on the first chunk even when `return_token_ids` was not requested. This gates the field on `return_token_ids` in the echo branch, as the non-streaming response and the non-echo streaming branch already do (#27561 fixed the non-echo branch).

## Claims

- Streaming echo responses include `prompt_token_ids` only when `return_token_ids` is true, matching non-streaming responses.
- No change when `return_token_ids` is true, or for non-echo requests.

## Validation

Real server on `34ac4f96a3` (Qwen3-0.6B, RTX 4090, `--enforce-eager`), streaming `{"prompt": "Hello, my name is", "echo": true, "max_tokens": 3, "stream": true}`. The table shows `prompt_token_ids` on the first chunk:

| `return_token_ids` | `main` | this PR |
|---|---|---|
| unset | `[9707, 11, 847, 829, 374]` | `None` |
| `true` | `[9707, 11, 847, 829, 374]` | `[9707, 11, 847, 829, 374]` |

Tests:

- New `tests/entrypoints/openai/completion/test_completion_text_offset.py::test_stream_echo_returns_prompt_token_ids_only_on_request` (CPU, drives `completion_stream_generator` with a fake `RequestOutput`, like the existing test in that file). The `return_token_ids=False` case fails on `main` (`[9] == None`) and passes with the fix.
- `pytest tests/entrypoints/openai/completion/test_completion_text_offset.py tests/entrypoints/openai/completion/test_completion_error.py tests/entrypoints/openai/completion/test_prompt_validation.py`: all pass.
- `pre-commit run --files <changed files>`: all hooks pass.

## Details

In `OpenAIServingCompletion.completion_stream_generator`, the echo branch set `prompt_token_ids_to_return = prompt_token_ids` unconditionally, while the non-echo branch next to it only does so when `request.return_token_ids` is set, and `request_output_to_completion_response` returns `prompt_token_ids` only on request. This moves the assignment under the existing `if request.return_token_ids:` in the echo branch. Besides being unrequested and inconsistent with non-streaming, the field repeats the whole prompt, which doubles the first chunk for long-prompt echo/scoring traffic.

Not a duplicate: I found no issue or PR for this (searched "echo prompt_token_ids stream", "return_token_ids echo streaming", "prompt_token_ids first chunk"). #61660 edits this function for `echo` with `max_tokens=0` usage but not this line.

AI assistance was used to find this bug, write the fix and the test, and run the validation shown above.
