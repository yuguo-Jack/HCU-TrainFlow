# [Perf][Kimi K3] KV-balanced MLA core for the latency-specialized decode

[Upstream PR](https://github.com/vllm-project/vllm/pull/64149) · state: closed · merged: False

## Original PR description



## Overview

Kimi K3's latency-specialized decode (`additional_config={"decode_backend": "latency_specialized"}`) runs its MLA attention core through tokenspeed's split-KV FP8 decode (or trtllm-gen). That core uses one split count for the whole batch, and sizes the split width from `max_model_len`. In agentic workloads, context lengths within a batch differ a lot. Once a DCP8 rank holds about 8 or more requests, each request gets a single split, so every step waits on the longest request streaming its whole KV shard.

This PR adds an opt-in core that fixes this, `additional_config={"decode_backend": "latency_specialized", "mla_core": "kv_balanced"}`. It reuses the KV-balanced FP8 MLA decode from vllm-project/vllm#63638 (`KIMI_K3_KV_BALANCED_MLA`). That decode plans a split count per request from its own KV length, on the device, inside the captured graph, and runs persistent clusters over a work list.

It swaps in for both the tokenspeed and the trtllm-gen core, under TP and under DCP:
- Under DCP, it runs every rank's heads over the local KV shard, masked causally in global positions, and writes the DcpBox rows and log2 LSE that `DcpValue` merges.
- Under TP, it runs this rank's heads over the full KV into the BF16 latent.

It is PDL-chained between `MlaQuery` and the value kernel, as tokenspeed is, so the rest of the layer is unchanged. As in `KIMI_K3_KV_BALANCED_MLA`, the first MLA layer of a forward plans, and every later layer reuses that plan.

## Claims

- **Decode attention core, AgentX context lengths on GB300:**
  - 1.8–2.0x faster than the current tokenspeed core, by geometric mean over 1–16 requests per rank. This holds for DCP8 and DCP16, and for verify with 4 and 5 draft tokens.
  - 2.8–3.2x faster at 8–16 requests per rank.
  - About 1.1x at one request.
- **Per-request decode rate in a real TP8/DCP8 server**, with the production specialized-decode flags: +1% / +6% / +9% / +15% at 1 / 4 / 8 / 12 running requests. At 12 requests, the MLA core's exposed time per step drops from 6.9 to about 2.3 ms.
- **End-to-end on AgentX, GB300:**
  - p90 interactivity is +23% at 1P2D c32, +10% at 1P2D c24 and +1% at 1P3D c16.
  - p90 E2E latency is −9% at c32.
  - Throughput is unchanged to +1.6%, because these points are prefill-bound.
- **Accuracy:** gsm8k with real speculative rejection is 0.960 (1P2D DCP8).
- **Opt-in.** Nothing changes unless `mla_core` is set to `kv_balanced`. `KIMI_K3_KV_BALANCED_MLA`'s own behaviour is unchanged.

## Changes

- `specialized_decode/cutedsl/mla/balanced.py` (new) holds the whole integration:
  - `balanced_cores()` builds the KV-balanced cores of one MLA layer, per query length.
  - `BalancedCore.run()` plans once per forward and decodes into the buffers the replaced core would have written.
  - The planner bounds default to 16 : 512 : 8 (capacity, minimum split tokens, waves), since the merged backend's 8 : 1024 : 8 under-fills the GPU at the specialized decode's small batches. `VLLM_K3_SPEC_KVB="capacity:min_split_tokens:max_waves"` overrides them.
- `specialized_decode/cutedsl/mla/prepared.py` builds the cores when `core == "kv_balanced"` and dispatches to them ahead of the tokenspeed and trtllm-gen branches.
- `kv_balanced_mla/core.py`: the planner bounds (capacity, minimum split tokens, waves), PDL and the output buffer become per-instance arguments of `KvBalancedMla`. They default to the previous constants, so `KIMI_K3_KV_BALANCED_MLA` computes exactly what it did before.

## Validation

**Numerics** (one GB300, against an FP32 reference and the cores it replaces):
- **DCP8 rank 3**, q = 1 / 5 / 6, interleave 1 and 64, with lengths that end inside the rank's chunks, plus an empty (padded) request:
  - relative error ≤ 0.024 against FP32 and ≤ 0.021 against tokenspeed;
  - LSE within 1e-4;
  - the empty request gives a zero output and an LSE of −∞.
- **TP**, 12 and 6 heads per rank (TP8 / TP16), q = 1 and 5: relative error ≤ 0.018 against FP32, ≤ 0.020 against tokenspeed and ≤ 0.026 against trtllm-gen (q = 1).
- **Plan once per forward:** three layers in one forward plan once, a new forward plans again, and calls outside a forward (compile warmup) plan every time.
- **CUDA graph:** plan plus decode captured, then replayed after the KV lengths change in place, stays within 0.021 of FP32.

The KV-balanced kernel itself is covered by `tests/models/kimi_k3/test_kv_balanced_mla.py` (vllm-project/vllm#63638). There is no test suite yet for the NVIDIA specialized decode, so this PR adds none.

- **The gain grows with requests per decode worker.** These points run about 12, 8 and 4 per worker, matching the server step rates above.
- **Throughput barely moves.** These points are prefill-bound: the single prefill engine is 90–95% busy and sets the request rate. So faster decode shortens each request instead of adding throughput.

**Accuracy.** gsm8k, 5-shot, with real speculative rejection on 1P2D DCP8 with `mla_core=kv_balanced`: exact_match 0.960 ± 0.005, for both flexible and strict extraction. The `KIMI_K3_KV_BALANCED_MLA` DCP8 reference in vllm-project/vllm#63638 is 0.967.
