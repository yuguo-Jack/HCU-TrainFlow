# [Rust Frontend] Report prompts over max_model_len like Python

[Upstream PR](https://github.com/vllm-project/vllm/pull/62824) · state: closed · merged: True

## Original PR description

## Overview

A prompt longer than `max_model_len` fails on both frontends with a 400, but the Rust message differs from Python's and has no `param`. This PR reports it like Python: `This model's maximum context length is N tokens. However, your prompt contains M input tokens, which exceeds this limit even without any output tokens. Please reduce the length of the input prompt.` with `param: "input_tokens"` (`TokenizeParams._token_len_check`, `vllm/renderers/params.py`).

## Claims

- On the Rust frontend, a prompt over `max_model_len` returns Python's message and `param: "input_tokens"` on chat, completions, and generate. Before: `this model's maximum context length is N tokens, but the prompt contains M input tokens` with `param: null`. The message shares its `This model's maximum context length is` opening with OpenAI's own error, which clients match to detect a context overflow.
- A prompt that exactly fills the context gets the same opening and `param` with accurate wording ("your prompt fills it with N input tokens, leaving no room for output tokens").

## Validation

Commands from `.buildkite/scripts/run-rust-frontend-cargo-ci.sh` (`style-clippy` and `test`), run from the repo root:

```

cargo sort --workspace --check rust                          # ok

cargo clippy --manifest-path rust/Cargo.toml --workspace --all-targets --all-features --locked -- -D warnings   # ok
cargo nextest run --manifest-path rust/Cargo.toml --workspace --all-features --locked --no-fail-fast
```

- `prompt_too_long_maps_to_invalid_request` now snapshots the full error JSON of both variants, and `chat_wrapped_prompt_too_long_maps_to_invalid_request` checks the `param`. Both fail on the base.

## Details

The text layer owns the check (`resolve_max_tokens`, `rust/src/text/src/lower.rs`) and its errors. A new `vllm_text::Error::param()` accessor (delegated by `vllm_chat::Error::param()`) gives `input_tokens`, and the HTTP boundary (`server/src/error.rs`) puts it in the error's `param` instead of hard-coding one per route. `vllm_chat::Error::PromptTooLong` is removed: nothing constructs it, since the chat path wraps the text error.

- At `prompt_len == max_model_len`, Python's length check passes and the request then fails as `max_tokens must be at least 1, got 0.`. Rust keeps rejecting it up front, as before, now as `PromptFillsContext`, because "exceeds this limit even without any output tokens" would be false there.
- Python's HTTP message also ends with ` (parameter=input_tokens, value=M)`, which `VLLMValidationError.__str__` appends to every validation error. Rust reports `param` in its own field and appends it to no message, so that suffix is left out here too.
- gRPC maps the same validation errors to `INVALID_ARGUMENT` with the error text, so its message changes too.

Not a duplicate: no open upstream PR changes this Rust error.
