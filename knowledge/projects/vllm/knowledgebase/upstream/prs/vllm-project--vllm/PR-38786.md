# Splitting MLA attention Triton kernel

[Upstream PR](https://github.com/vllm-project/vllm/pull/38786) · state: closed · merged: False

## Original PR description

A revival of PR #19774  (which, surprisingly, still seems relevant).

This splits _fwd_grouped_kernel_stage1 operation in two parts, using a temporary buffer.

## Rationale
_fwd_grouped_kernel_stage1 becomes a significant bottleneck with large context lengths due to severe GPU under-utilization (very small grid size). This patch breaks it into two kernels:
- _fwd_grouped_kernel_stage1_part1: launched with larger grid, writes into temporary buffer
- _fwd_grouped_kernel_stage1_part2: smaller grid but much lighter operation

## Affected Models
At least on ROCm, this optimization benefits GLM-4.7-Flash, DeepSeek-V3 (when AITER is off), and potentially other GLM models. (DeepSeek can handle longer contexts when AITER is on, but AITER MLA does not support the head size of GLM-4.7-Flash.)

## Code Review

This pull request refactors the MLA decoding attention mechanism by splitting the first stage kernel into two parts and introducing a temporary accumulation buffer to improve GPU utilization. However, several critical issues were identified: the kpe loading logic in the first kernel part lacks necessary FP8 dequantization, the fixed allocation size of the temporary buffer poses a high risk of out-of-memory (OOM) errors at large batch sizes, and the second kernel part requires a safety check to prevent NaN values when handling empty KV splits.

The `kpe` loading logic is missing the FP8 dequantization scaling. In the original `_fwd_grouped_kernel_stage1` kernel, `kpe` is scaled by `ks` if the buffer is FP8. Without this, MLA attention will produce incorrect results when using FP8 KV cache and `BLOCK_DPE > 0` (which is the case for DeepSeek models).

```suggestion
                kpe = tl.load(
                    K_Buffer + offs_buf_kpe,
                    mask=(offs_n[None, :] < split_kv_end) &
                    (mask_dpe[:, None]),
                    other=0.0,
                )
                if kpe.dtype.is_fp8():
                    kpe = (kpe.to(tl.float32) * ks).to(qpe.dtype)
                qk += tl.dot(qpe, kpe.to(qpe.dtype))
```

The allocation of `temp_att_buf` can lead to massive GPU memory consumption, potentially causing OOM. With `_MLA_TEMP_PAGE_COUNT = 32`, the buffer size is `32 * batch * head_num * num_splits * (head_dim + 3) * 4` bytes. For a typical MLA configuration (e.g., DeepSeek-V3 with `head_num=128`, `head_dim=512`, `num_splits=4`) and a batch size of 256, this buffer alone consumes ~8.6 GB. At `batch=1024`, it would exceed 34 GB. 

Consider making `temp_page_count` dynamic based on the batch size to maintain a reasonable grid size without excessive memory overhead, or capping the total memory used by this buffer.

If a split is empty (`split_kv_end <= split_kv_start`), `page_count` will be 0, and `e_sum` will remain 0.0. This results in `acc / e_sum` storing `NaN` into `Att_Out`. While the subsequent stage 2 kernel might ignore these values based on the same condition, it is safer and more consistent with the original implementation to wrap the stores in a condition check or ensure neutral values are stored.

```suggestion
    if cur_batch_seq_len > split_kv_id * kv_len_per_split:
        tl.store(Att_Out + offs_mid_o + offs_dv, acc / e_sum, mask=mask_dv)
        tl.store(Att_Out + offs_mid_o + Lv, e_max + tl.log(e_sum))
```

I've just checked the size of temp_att_buf in my runs. It is  32 * batch * 32 * 4 * 515 floats in DeepSeek-V3 (-tp 4) and 32 * batch * 20 * 4 * 515 floats in GLM-4.7-Flash. That's 8.4 MB and 5.3 MB per batch entry respectively. I believe vLLM splits tensors between devices along the head dimensions, which is why my number for DeepSeek-V3 is off by a factor of 4. 

Considering that just the weights of DeepSeek-V3 take 600+ GB, and you'll need 1 TB of KV cache to work with batch size 1024 and context length 100k tokens, this buffer size is negligible.

I don't mind making it dynamic, but I'm not sure if I can do a simple Python comparison here, considering that the code runs deep inside a captured CUDA graph.
