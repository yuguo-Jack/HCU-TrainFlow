## Original PR description

# [Kernel][MoE] Add HPC-Ops MoE backend for SM120 (FP8 and MXFP4)



## Overview

- Extends the existing `hpc` MoE backend (#45924, Hopper FP8) to RTX PRO Blackwell (SM120) with 128-block FP8 and MXFP4 x MXFP8 experts, backed by [hpc-ops#101](https://github.com/Tencent/hpc-ops/pull/101).
- Opt-in with `--moe-backend hpc`; no default selection changes.

## Claims

- `--moe-backend hpc` runs 128-block FP8 (Qwen3.8-Flash-Next-FP8) and MXFP4 (DeepSeek-V4-Flash) MoE on SM120.
- Serving on 4x RTX PRO 5000, prefix caching off:
  - 8k-in / 1k-out: faster than the default backend at every concurrency tested, and faster than the next-best alternative (Marlin / Triton / b12x) from concurrency 4.
    - DeepSeek-V4-Flash TP4: **+11–28% vs default**, **+3–13% vs Marlin**, **+4–16% vs b12x** (tie at concurrency 1).
    - Qwen3.8-Flash-Next-FP8 TP4+EP: **+8–20% vs default**, **+4–6% vs Triton**.
  - 1k-in / 512-out:
    - DeepSeek-V4-Flash TP4: **+12–42% vs default**, **+2–6% vs Marlin**.
    - Qwen3.8-Flash-Next-FP8 TP4+EP: **+16–24% vs default**, **+4–7% vs Triton**.
- Fastest single MoE layer at every batch size from 1 to 8192 tokens on both models (up to 1.28x vs the next kernel on DeepSeek-V4, 1.34x on Qwen3.8).
- GSM8K accuracy level with the other backends (within run-to-run noise).

## Validation

### Setup and tests

- Hardware: 4x RTX PRO 5000 (SM120), torch 2.13, hpc-ops built for SM120, b12x 1.3.0 (the version vLLM pins).
- Serving: one session per backend on `0.31.1rc1.dev382+g86b1c2ef1` with this change, then rebased onto current main without conflicts. Prefix caching off; each `(concurrency, trial)` used a distinct seed.
- Tests: `pytest tests/kernels/moe/test_hpc_sm120_moe.py` — 32 passed on SM120.
  - 29 mocked (no GPU / hpc-ops): backend selection, kernel limits, padding, load-time weight prep, BF16 activations reaching the kernel unquantized, wrappers calling the hpc-ops entries.
  - 3 real `FusedMoE` layers vs Triton (FP8, with and without `swiglu_limit`) and Marlin (MXFP4); skip unless SM120 + hpc-ops are present.
  - CI has no SM120 runner, so those three and the serving numbers below are outside CI.

## Details

- Opt-in only: `--moe-backend hpc`. Auto selection is unchanged, so Hopper HPC FP8 and every other SM120 backend keep their current defaults.
- Kernels are prebuilt in hpc-ops; nothing is compiled at vLLM startup.

### Changes

- `hpc_moe.py`: on SM120, `HPCExperts` and new `HPCMxfp4Experts` (`Mxfp4MoeBackend.HPC`) pass BF16 activations to the kernel. The kernel quantizes each token to MXFP8 once while gathering, so there is no separate quantization kernel. Gated on `has_hpc_sm120_moe()`.
- `oracle/fp8.py`: at load time, 128-block weight scales are rounded up to powers of two and the weights requantized against them in place (same as DeepGEMM on SM120), then packed (`prepare_fp8_moe_weights_sm120`).
- `oracle/mxfp4.py`: backend wiring, pad to multiples of 128, pack UE8M0 weight scales (`prepare_mxfp4_moe_weights_sm120`).
- `utils/hpc.py`: wrappers for `fuse_moe_blockwise_fp8_sm120` / `fuse_moe_blockwise_mxfp4_sm120`.
- docs: MoE kernel features table, `KernelConfig.moe_backend` docstring.

### Limits

Checked in `is_supported_config`; the oracle falls back.

| | 128-block FP8 (SM120) | MXFP4 x MXFP8 (SM120) |
|---|---|---|
| hidden / intermediate | multiples of 128 (TP shards padded by existing `pad_tp_shard_to_weight_blocks`) | padded to multiples of 128 |
| quant | 128x128-block FP8 weights; activations quantized to MXFP8 in-kernel | MXFP4 weights; MXFP8 activations in-kernel |
| activation | SiLU, optional `swiglu_limit` | SiLU, optional `swiglu_limit` |
| bias / swiglu alpha, beta | not supported | not supported |
| experts / top-k | ≤ 512 local experts, top-k ≤ 128 | same |
| EP placement | linear, with or without EPLB; `round_robin` rejected | same |
| dtype | bf16 | bf16 |

### Tradeoffs

- Decode-sized MoE calls (1–64 tokens) are only 4–10% faster than the next kernel, so short-prompt / low-concurrency serving is the smallest end-to-end gap (DeepSeek-V4 vs b12x is a tie at concurrency 1).
- The 8k-prompt tables sit in the batch sizes the kernel wins by 20–34%.
- The kernel reduces top-k routes with BF16 atomics, so MoE output is not bit-for-bit deterministic across runs.
