# [Feature][KV Connector][Mooncake] Decode-to-prefill KV reuse for multi-turn P/D

[Upstream PR](https://github.com/vllm-project/vllm/pull/63425) · state: open · merged: False

## Original PR description

## Overview

In multi-turn P/D serving, the next turn's prompt starts with the previous prompt plus the tokens the decoder just generated. Only the decoder has that KV, so the prefiller recomputes it every turn. This PR lets a `kv_both` prefiller **pull it from the decoder** over the existing Mooncake transfer engine. A router opts in per request through `kv_transfer_params`; requests without the new keys are unaffected.

Related: the MooncakeConnector RFC #60523. It doesn't cover this, and it notes that the hybrid Mamba/GDN path is fragile; this PR works for hybrid models.

## Claims

- **New `kv_transfer_params` keys** (documented in `mooncake_connector_usage.md`):
  - `hold_kv` keeps a finished decode request's KV (and, for hybrid models, its final recurrent state) for a later pull, whether the request stopped or hit `max_tokens`.
  - On the next turn, `pull_transfer_id` + `remote_num_tokens` + `remote_prefix_hash` make the prefiller load exactly that prefix and compute only the rest, while still sending to the decoder as usual.
- **Works for hybrid (GDN) models.** Prefix caching can't do this for them: recurrent-state checkpoints are only written during prefill, so a decoder never has a cache hit on its own generated tokens.
- **Measured** on a hybrid model (Qwen3.8-27B-FP8, 1P1D TP2+TP2, Mooncake RDMA with GPUDirect, Intel XPU): later-turn TTFT **6.15 s → 1.63 s** mean (3.8x), with decode ITL unchanged.

## Details

Request flow (both instances `kv_role="kv_both"`):

1. Turn t, decode leg on D: the usual pull from P, plus `do_remote_decode`, `transfer_id=H`, `hold_kv`. When it finishes, `request_finished` delays the free and D's sender waits for a pull of `H`, exactly as a prefiller waits for its decoder today.
2. Turn t+1, prefill leg on P: `do_remote_prefill` with `pull_transfer_id=H`, `remote_num_tokens=L`, `remote_prefix_hash`, plus the usual `do_remote_decode` and `transfer_id`. `get_num_new_matched_tokens` returns `L - num_computed_tokens`. P's receiver pulls `L` tokens from D (D's sender trims its blocks to the requested tail, as for a partial prefix hit), computes the rest, and holds for D.
3. Turn t+1, decode leg on D: unchanged; D pulls the prompt from P.

Implementation (about 55 lines in `mooncake_connector.py`, almost all scheduler side):
- `update_state_after_alloc`: `elif` → `if`, so one request can both load and send.
- `MooncakeConnectorMetadata.add_new_req`: a pull uses `pull_transfer_id` when present.
- `on_new_request`: `hold_kv` requests skip the P-side Mamba truncation, because they are real decodes.
- `request_finished`: `hold_kv` also keeps `FINISHED_STOPPED`; an abort before allocation still releases both sides.
- `hold_timeout_s`: a per-transfer expiry. Lowering `VLLM_MOONCAKE_ABORT_REQUEST_TIMEOUT` globally instead made ordinary P→D sends expire while D queued under load.

Tradeoffs and limitations:
- Reuse needs the next prompt to contain the generated tokens exactly. Chat templates that drop reasoning content from history prevent it, and so does trace replay with recorded responses.
- A hold occupies decoder KV until pulled or timed out. When D is KV-bound, an unused hold (the last turn of a session) delays admission of new decode requests. Holds are not evicted under memory pressure; that would need scheduler support and is left out to keep this change small.
- The router decides when to hold and pull, and tracks token ids. `examples/disaggregated/mooncake_connector/mooncake_connector_proxy.py` is unchanged.
- `kv_transfer_params` keep their existing trust model (set by the router). A client that can reach an engine directly could already set `do_remote_decode`; `hold_kv` similarly lets it pin decoder KV until `hold_timeout_s`.

Not a duplicate: open PRs touching MooncakeConnector cover decoder-side reads (#61974), layerwise transfer (#62504), compression (#61085) and bug fixes. None moves KV from decode to prefill or holds decode KV.
