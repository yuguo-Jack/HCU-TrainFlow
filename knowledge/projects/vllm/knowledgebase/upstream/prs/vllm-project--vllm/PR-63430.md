# [Bugfix][Structured Output] Allow disable_any_whitespace with the auto backend

[Upstream PR](https://github.com/vllm-project/vllm/pull/63430) · state: open · merged: False

## Original PR description

## Overview

`disable_any_whitespace` is refused at startup unless the backend is named `xgrammar` or `guidance`, so it cannot be combined with the default `auto` backend. This allows it with `auto` and makes the outlines backend (the one `auto` backend that ignored the flag) honour it. Follows up on #60088 (closed unmerged), with the review feedback there addressed below; no other open PR changes this check. This is a config fix only; it does not claim to fix #42110.

## Claims

- `--structured-outputs-config '{"disable_any_whitespace": true}'` starts with the default backend.
- Whichever backend `auto` picks for a request honours the flag: xgrammar and guidance already read it from the engine config, and outlines now passes `whitespace_pattern=""` to `outlines_core`.
- Validation stays at startup. Only `lm-format-enforcer` (which `auto` never picks) is rejected, and there are no new request-time errors.

## Validation

Repro on main (no model or GPU needed, the config fails before model load):

```bash
vllm serve Qwen/Qwen3-0.6B --structured-outputs-config '{"disable_any_whitespace": true}'
# or
python -c "from vllm.config import StructuredOutputsConfig as C; C(disable_any_whitespace=True)"
# pydantic ValidationError: disable_any_whitespace is only supported for xgrammar and guidance backends.
```

With this change both succeed.

Tests run:

- `pytest tests/v1/structured_output/test_validation.py -k whitespace`: 5 passed with this change (auto, xgrammar, guidance and outlines accepted; lm-format-enforcer rejected). On main the `auto` and `outlines` cases fail with the ValidationError above.
- `tests/v1/structured_output/test_structured_output_manager.py::test_outlines_honours_disable_any_whitespace`: added, but not run in my environment, which cannot download the test tokenizer (the existing tests in that file fail there for the same reason). I checked the behaviour it asserts directly against `outlines_core==0.2.14` with the gpt2 vocabulary: with `whitespace_pattern=""` the index rejects `{"a": 1}` and accepts `{"a":1}`; with the default pattern both are accepted.
- End to end: the same startup-check change (allowing the flag with `auto`) has been serving Qwen3.6 models with `disable_any_whitespace` on and the default backend. The outlines wiring is new in this PR and has only the check above.

## Details

Why `backend: xgrammar` is not an equivalent workaround: a named backend gets no fallback. A schema that xgrammar cannot compile (`multipleOf`, `uniqueItems`, `contains`, `minContains`/`maxContains`, some string `format`s, pattern plus length bounds; see `has_xgrammar_unsupported_json_features`) is rejected with a 400 under `xgrammar`, while `auto` serves it via guidance. Turning on compact output should not cost that fallback.

On the #60088 review:
- "server-level flag is still silently dropped with auto falling back to outlines": fixed here by wiring the flag into `OutlinesBackend.compile_grammar`. outlines' default whitespace is `[ ]?`, so before this change it could still emit single spaces.
- "deferring validation to request time turns a startup error into schema-dependent 400s": this PR adds no request-time check, so a given config either starts or fails at startup as before.
- The per-request `StructuredOutputsParams.disable_any_whitespace` field is untouched; this PR only concerns the engine config.
