# [Bugfix][CuMem] Retry the host backup copy in wake_up

[Upstream PR](https://github.com/vllm-project/vllm/pull/64465) · state: open · merged: False

## Original PR description

## Overview

`CuMemAllocator.wake_up()` clears `is_asleep` before copying a host backup back to the device. If that copy fails, the allocation stays mapped with `is_asleep=False` and `cpu_backup_tensor` still set. The next `wake_up()` skips the entry (`if not data.is_asleep: continue`), so the backup is never retried or released and the device contents are undefined.

This rolls a failed restore back to the asleep state: the allocation is unmapped again, `is_asleep` is set back to `True`, and the host buffer is kept, so a later `wake_up()` maps it again and retries the copy. The buffer is not cleared after a successful restore because main keeps it for reuse (#64630). It also makes `get_pluggable_allocator()` fail with a clear error when the cumem library is not loaded.

Split out of #52132 per [review feedback](https://github.com/vllm-project/vllm/pull/52132#discussion_r3884880794).

## Claims

- A failed host-to-device copy no longer leaves an allocation mapped with undefined contents: the wake rolls it back to asleep, and a later `wake_up()` retries the restore.
- The reusable host buffer from #64630 is preserved across both a failed and a successful restore.
- `wake_up()` still skips deferrable tags that were not requested, and still wakes non-deferrable tags unconditionally.
- The success path is unchanged; the ROCm zero-fill still runs only for allocations mapped by the current call that have no host backup.
- `get_pluggable_allocator()` raises `RuntimeError("cumem allocator library is not loaded")` instead of passing `None` into `CUDAPluggableAllocator`.

## Validation

- Added two tests to `tests/basic_correctness/memory/cumem/test_cumem.py`:
  - `test_wake_up_retries_host_backup_after_copy_failure`
  - `test_get_pluggable_allocator_requires_loaded_library`
- The retry test uses a real `CuMemAllocator`: it allocates a weights tensor in the pool, sleeps with `offload_tags=("weights",)`, injects one `cudaMemcpy` failure, then verifies that the failed wake leaves the allocation asleep with its host buffer, that a second `wake_up()` restores the tensor, and that the buffer is reused by the next sleep.
- The retry test fails on main (the failed wake leaves `is_asleep=False`, so the second `wake_up()` skips the entry). The pre-rebase revision was verified on an H20 (2 passed); this rebased revision has not been rerun on GPU yet because the test host is currently unavailable, so the CuMem CI jobs are its first run. The guard test fails without the clear error and passes with it.
- CI: `basic-correctness-cumem` runs `pytest -v -s basic_correctness/memory/cumem` on the CUDA and ROCm CuMem jobs.
- Local: `ruff check`/`ruff format --check` pass on both files; the repository pre-commit suite runs in CI.

## Details

Root cause: the wake loop treats `is_asleep` as "nothing left to do". Once `create_and_map()` succeeds, a later copy failure has no way to signal that the allocation is mapped but not restored. A retry sees `is_asleep=False` and skips it.

Fix: the wake loop decides by tag first and only maps allocations that are asleep. If the restore copy fails, it sets `is_asleep` back to `True` and unmaps the allocation, which returns it to the normal asleep state; the next `wake_up()` maps it again and retries. The host buffer is left in place because #64630 reuses it across wake cycles. The ROCm zero-fill still runs only when there is no host backup.

Scope: this only changes the host-backup retry path. A failed `create_and_map()` still leaves `is_asleep=True` and is retried by the existing code; OOM and `cuMemMap` failure handling is unchanged.
