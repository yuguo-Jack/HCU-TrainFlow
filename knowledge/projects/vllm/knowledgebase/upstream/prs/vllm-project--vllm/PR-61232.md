# [Kernel] Specialize Triton MoE on fixed weight dimensions

[Upstream PR](https://github.com/vllm-project/vllm/pull/61232) · state: open · merged: False

## Original PR description

**Draft — end-to-end validation is incomplete.** The local MoE-layer gains below have not established a repeatable whole-model improvement across the target workloads, and the eager batch-8 regression remains unresolved. This change is not ready for review or merge until those performance questions are resolved.

## Overview

Specialize `fused_moe_kernel` on the fixed weight dimensions `N` and `K`, allowing Triton to fold dimension-dependent address calculations, bounds and loop limits. Request-dependent token counts remain runtime values.

## Claims

- Reduces complete local BF16 MoE-layer GPU latency on A30 by 2.1%–24.8% across the tested Qwen3-30B-A3B-shaped workload: hidden size 2048, 128 experts, top-8 routing, intermediate sizes 96/192, and 1/8/32/128/512 tokens.
- Preserves numerical results in the tested FP16/BF16, block-INT8 and BF16 model paths. This is not an overall serving-throughput claim.

## Validation

**Correctness:** 41 focused tests passed (40 dimension/stride/routing/bias cases plus the existing scalar-scale launcher test), and 12 existing W8A8 block-INT8 cases passed. Complete MoE A/B outputs were bitwise equal in all measured cases.

```bash
CUDA_VISIBLE_DEVICES=0 PYTHONPATH=. .venv/bin/python -m pytest \
  tests/kernels/moe/test_moe.py \
  -k 'non_aligned_dimensions or launcher_passes_scalar_scale' -q
CUDA_VISIBLE_DEVICES=0 PYTHONPATH=. .venv/bin/python -m pytest \
  tests/kernels/moe/test_block_int8.py \
  -k 'fused_moe and (1-128-128 or 33-512-512 or 128-128-128)' -q
.venv/bin/pre-commit run --files \
  vllm/model_executor/layers/fused_moe/fused_moe.py tests/kernels/moe/test_moe.py
```

The local INT8 and model runs used an available older CUDA extension: both A/B arms bridged the optional scatter-index argument to the legacy alignment operator, rejecting non-None scatter output. Model runs also used the upstream PyTorch embedding fallback because that extension lacks the fused embedding operator. The unavailable optional Humming FP4 backend was disabled for these BF16 runs. These are validation-environment controls, not changes in this PR.

**Model smoke:** Qwen3-30B-A3B BF16, 4×A30, TP4, Triton attention/MoE, prefix caching disabled. Six individual prompts (32/64/96/192/256/512 tokens), four greedy output tokens: 6/6 generated token matches and zero maximum log-probability difference over 1,146 teacher-forced positions. A repeated baseline also matched exactly; the changed kernel was instrumented to confirm it was used. This is a numerical smoke test, not a benchmark-suite accuracy evaluation.

**Eager whole-engine result:** seven randomized paired `LLM.generate` runs, 128 input / 16 output tokens. Batch 8 median wall time was 1.843 s before versus 1.916 s after (about 4.0% slower); batch 32 was 2.511 s versus 2.509 s. The kernel improvement did not translate into a consistent eager-engine speedup.

**CUDA Graph whole-engine cross-check:** fresh engine per arm, `FULL_DECODE_ONLY` with capture sizes 8/32, 128 input / 64 output tokens, seven measurements after two warmups. The order was baseline, candidate, repeated baseline. Median wall time (min–max), seconds:

This cross-check does not establish a consistent whole-engine speedup. Kernel/layer improvements above remain the bounded performance claim.

## Details

The production change is two parameter annotations. `N` and `K` come from fixed expert-weight shapes, while `EM`, valid-token counts and all strides retain their existing treatment. Specializing additional weight shapes can add JIT variants/cold compilation work; request batch-size changes do not add N/K variants. No new launch configuration, synchronization, allocation, dependency or backend is introduced.

Added tests cover partial K tiles (including K smaller than the tile), a partial N tile, strided/offset storage, padded routes, nonlocal experts, routed weights and bias. They run in the existing Buildkite MoE suite. FP8, the tensor-descriptor path on newer GPUs, and ROCm were not locally validated on A30.

Duplicate checks found no open PR making these fixed dimensions constexpr. Related #56580 changes alignment specialization for runtime `EM` / valid-token counts to reduce cold JIT work; it does not specialize `N` and `K` or make the steady-state optimization here.
