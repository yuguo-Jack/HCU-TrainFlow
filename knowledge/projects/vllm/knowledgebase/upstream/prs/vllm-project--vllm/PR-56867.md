# [Metrics][KV Offload] Add vllm:kv_offload_config_info - generic info metrics for offloading the offloading connector

[Upstream PR](https://github.com/vllm-project/vllm/pull/56867) · state: closed · merged: True

## Original PR description

## Purpose

An offloading spec holds static configuration that no metric reports. The CPU cache
exports usage only (`vllm:kv_offload_cpu_cache_usage_perc` and the read/write
variants). A secondary tier exports nothing. So an operator cannot read the capacity,
the mount path, or the eviction policy of a tier from `/metrics`. Every spec that
adds such a fact today must also add its own metric, its own label list, and its own
emission call.

This adds `vllm:kv_offload_config_info`, a gauge with the constant value `1`, and two
hooks. The spec declares the label names. The manager fills the values.

```python
class OffloadingSpec(ABC):
    @classmethod
    def config_info_keys(cls, extra_config: dict[str, Any]) -> tuple[str, ...]:
        return ()


class OffloadingManager(ABC):
    def config_info(self) -> Sequence[Mapping[str, str | int | float | bool]]:
        return [{}]
```

`SecondaryTierManager` carries both methods, with the same defaults. Its
`config_info()` returns one mapping, because one tier gives one series.

### One series for each tier

The metric name carries no tier identity. One `tier` label tells the series apart. The
label value comes from `TieringMetricsTracker.tier_label()`, so it equals the `tier`
label that the tiering counters and histograms already carry. An operator joins the
two metrics on that label.

| Source | Name the tier declares and fills | Series in `/metrics` |
|---|---|---|
| a standalone CPU manager | `cpu_num_chunks` | one series, no `tier` label |
| the primary tier of a tiering manager | `cpu_num_chunks` | `tier="0:primary"` |
| secondary tier 0, tier type `example` | `example_info` | `tier="1:example"` |
| secondary tier 1, tier type `example` | `example_info` | `tier="2:example"` |

Two tiers of one type add a series. They add no label name. A new tier keeps the label
set of the other tiers, so an existing query survives.

A tier cannot know its own index, so a tier declares and fills its own names only.
`TieringOffloadingSpec.config_info_keys()` declares the union of the names of every
configured tier, plus `tier`. `TieringOffloadingManager.config_info()` adds the `tier`
label to each mapping. The label name is the constant `TIER_LABEL` in
`vllm/v1/kv_offload/tiering/base.py`, and the tiering metrics use the same
constant. The manager also writes an empty value for each name that another tier
owns, because every series of one metric carries every label.

This shape replaces the earlier revision of this pull request, which put the tier
index in the label name, as `tier1_fs_path`. The helper `config_info_prefix()` that
built such a name is gone.

The gauge is per-engine, like the other offloading gauges. Each engine reports its own
managers, not the instance total.

**This pull request publishes two facts, as a start.** `CPUOffloadingManager`
publishes `cpu_num_chunks`, the number of chunk slots in the CPU tier. The in-tree
`example` secondary tier publishes `example_info`, the value of its `custom_param`, as
a worked example for a tier author. #53902 adds the other CPU facts. The tiering
compose is here, so an out-of-tree secondary tier gets its series today.

A `ConfigInfo` dataclass in `vllm/v1/kv_offload/base.py` holds the facts of one
manager. Each field name is a label name, so one class gives both the declared names
and the filled values. `CPUOffloadingInfo` and `ExampleTierInfo` use it.

### Why the spec declares and the manager fills

`OffloadPromMetrics` runs in the API-server process. That process holds the spec
class and the `kv_connector_extra_config` dict. It never builds a spec, and it never
holds a manager. So `config_info_keys()` is a classmethod, and it takes the same dict
that the spec itself receives. The manager holds the built configuration, so it owns
every value. A new fact costs one dict entry there.

Notes:

1. The gauge exists from `__init__`, next to every other offloading metric, so the
   metric never appears late. A labelled gauge makes no child until `.labels()` runs,
   so an engine that never reports exposes no series.
2. `_observe_info()` cannot raise on a disagreement. It builds the value tuple from
   the declared names alone, so the arity always matches. An exception in
   `_get_prometheus_metric()` ends the output handler. Every in-flight request then
   waits forever while the process stays up.
3. `_observe_info()` renders each value with `str()`, so a `bool` reads `True`. That
   matches `CacheConfig.metrics_info()` in `vllm/config/cache.py`.

### The spec is the authority

The two sides need not agree on the order, because the frontend reads each declared
name out of the payload. On a name disagreement:

| Case | Result |
|---|---|
| the spec declares a name, and no tier fills it | the label value is `""` |
| a tier fills a name that the spec never declared | the frontend drops it |
| either case | one `warning_once` line for each engine |

The check runs once for each payload, and not once for each tier, because the
declaration holds the names of every tier. A name that one tier owns reads empty on
the other tiers by design. So the check cannot see a name that one tier declares and
then leaves unfilled. The docstrings of `OffloadingManager.config_info()` and
`SecondaryTierManager.config_info()` tell an implementer to assert the agreement in a
test, which catches that case in CI.

### How the info reaches the API-server process

1. `OffloadingConnectorScheduler.get_stats()` calls `manager.config_info()` one time.
   It writes the result to the stats payload under `_StatsKey.INFO`. A `_info_sent`
   flag stops a repeat. A Prometheus child keeps the values it received, so one send
   is enough.
2. `is_empty()` counts `INFO`. `vllm/v1/core/sched/scheduler.py` drops an empty
   scheduler payload, and the first payload usually carries no observation.
3. `aggregate()` copies `INFO` from `other`. The scheduler payload is the `other` in
   `kv_connector_stats.aggregate(scheduler_kv_connector_stats)`. Without this copy
   the info dies on every step that also transfers, and `_info_sent` blocks a second
   try.
4. `reduce()` ignores `INFO`, because the info belongs to Prometheus alone.
   `KVConnectorLogging.log()` now skips an empty summary, so an info-only payload
   adds no bare `KV Transfer metrics: ` line to the interval log.
5. `_observe_info()` aligns each tier mapping with the declared names, under the rules
   in **The spec is the authority**. It reports one series for each mapping.

`INFO` holds label names, not metric names, so it is no metric section. A tier that
rewrites its own metric names now walks the new `OffloadingConnectorStats.metric_sections()`,
and not `stats.data.values()`. `KVCRSecondaryTierManager` is the one such tier in tree.

### `multiprocess_mode="mostrecent"`

`_create_metric` never passed `multiprocess_mode`, so every offloading gauge took
`Gauge`'s default `sum`. Stats attach to one client's outputs per step, so `sum`
multiplies a per-engine constant by the number of frontends under
`--api-server-count > 1`. The default now lives on `OffloadingGaugeMetadata`, which is
`Gauge`-only, so a counter or a histogram cannot set it. Counters and histograms stay
as they are, because their deltas reach exactly one frontend per step. This also
corrects the seven offloading gauges that exist today, all of them per-engine
snapshots.

### Relation to #53902

#53902 adds three fields to `CPUOffloadingInfo`: `cpu_blocks_per_chunk`,
`cpu_kv_bytes_per_chunk`, and `cpu_capacity_tokens_at_max_len`.

# Proposal: single-hook config info for `vllm:kv_offload_config_info`

Alternative shape for #56867: same metric, `+11` lines in `kv_offload/base.py`
instead of `+153`, and it can publish derived values such as `num_chunks`. Each
manager qualifies its own keys, so a fact keeps one label name wherever the
manager sits. Only the secondary tiers, which cannot know their own index, are
named by their parent.

## 1. One hook, on the manager

```python
# kv_offload/base.py, OffloadingManager
def config_info(self) -> Mapping[str, str | int | float | bool]:
    """Static config facts to publish as vllm:kv_offload_config_info labels.

    Keys are the label names, already qualified by this manager, so they
    read the same whether it is used standalone or nested.

    Returns:
        Mapping of label name to value. Values are stringified into label
        values, so they must be scalars msgpack can carry, not enums or
        objects. Empty by default.
    """
    return {}
```

The same default-`{}` method on `SecondaryTierManager` (`tiering/base.py`,
beside `build_metric_definitions` / `get_stats`). Nothing on `OffloadingSpec`
and no new `@abstractmethod`, so out-of-tree specs and tiers keep working.

```python
# cpu/manager.py, CPUOffloadingManager
def config_info(self) -> Mapping[str, str | int | float | bool]:
    return {
        "cpu_num_chunks": self._num_chunks,
        "cpu_store_threshold": self.store_threshold,
    }
```

One call yields keys and values, so they cannot disagree and there is no
ordering contract to get wrong.

## 2. Tiering composes

```python
# kv_offload/tiering/manager.py, TieringOffloadingManager
def config_info(self) -> Mapping[str, str | int | float | bool]:
    info = dict(self.primary_tier.config_info())
    for i, tier in enumerate(self.secondary_tiers):
        prefix = f"tier{i + 1}_{tier.tier_type}_"
        info.update({prefix + k: v for k, v in tier.config_info().items()})
    return info
```

The primary passes through unprefixed, so `cpu_num_chunks` reads the same
standalone and tiered and one query covers both;
`CPUPrimaryTierOffloadingManager` needs nothing of its own.

The prefix mirrors the tier identity already published: `tiering/metrics.py:62`
builds the `tier` label value as `f"{tier_idx + 1}:{tier_type}"`, with
`"0:primary"` at `:20`. So `tier1_fs_path` and `tier="1:fs"` denote the same
tier, with `_` for `:`, which is legal in a label value but not a label name.
Index-first also disambiguates: gluing the digit on the end collides, since
`fs1` at index 0 and `fs` at index 10 both yield `fs10_`, and `tier_type` is a
free-form registry key (`tiering/factory.py:29`).

## 3. Its own stats key, sent once

A new `_StatsKey.INFO` alongside `TYPES`/`DATA`, and a one-shot in
`OffloadingConnectorScheduler.get_stats()` (`offloading/scheduler.py:1886`):

```python
if not self._info_sent:
    stats = stats or OffloadingConnectorStats()
    stats.set_info(self.manager.config_info())
    self._info_sent = True
```

Sent even when the mapping is empty, so the metric exists exactly when
offloading is configured and its presence alone answers "is offloading on".

`is_empty()` must count `INFO` or the scheduler gate at `scheduler.py:2245`
drops the payload. `aggregate()` needs no change — it walks only `_values`, so
`reduce()` can't emit a `vllm:kv_offload_config_info=1` line into the interval
log.

## 4. Frontend creates the gauge on first sight

`OffloadPromMetrics.__init__` holds only the spec class, so it can't know the
labelnames — this is the one metric not created in the loop at
`offloading/metrics.py:381-384`. It adds two fields:

```python
# OffloadPromMetrics.__init__
self._info_metric: PromMetricT | None = None
self._info_keys: tuple[str, ...] | None = None
```

```python
# OffloadPromMetrics.observe
info = data.get(_StatsKey.INFO)
if info is not None:
    keys = tuple(sorted(info))
    if self._info_metric is None:
        self._info_metric = self._gauge_cls(
            name=KV_OFFLOAD_CONFIG_INFO,
            documentation=_INFO_METRIC_HELP,
            labelnames=self._labelnames + list(keys),
            multiprocess_mode="mostrecent",
        )
        self._info_keys = keys
    elif keys != self._info_keys:
        raise ValueError(f"config_info keys changed: {self._info_keys} -> {keys}")
    self._info_metric.labels(
        *(self.per_engine_labelvalues[engine_idx] + [str(info[k]) for k in keys])
    ).set(1)
```

`is not None` rather than a truth test, so a spec with no facts still yields the
bare metric. `sorted()` fixes labelname order across processes. Routing through
`INFO` rather than `DATA` leaves the `_offloading_metric_metadata` /
`_offloading_metric_defs` guards at `metrics.py:412` and `:489` intact.

Result, standalone CPU and then a tiering setup with one `fs` tier:

```

    cpu_num_chunks="512",cpu_store_threshold="1"} 1.0

vllm:kv_offload_config_info{model_name="…",engine="0",
    cpu_num_chunks="512",cpu_store_threshold="1",
    tier1_fs_path="/mnt/a"} 1.0
```

@amirfr3 Two more points from Claude:

## 1. Tier index in label names

`tier1_fs_path` puts the tier identity in the label name. Adding or removing a
tier changes the whole label set, so it becomes a new time series and existing
dashboards/queries break. It also means a query has to know each tier's index.

The alternative is one series per tier with a `tier` label value, matching what
`TieringMetricsTracker.tier_label()` already does, and blanking labels that
don't apply to that tier:

```
vllm:kv_offload_config_info{engine="0",tier="0:primary",cpu_num_chunks="36",path=""} 1
vllm:kv_offload_config_info{engine="0",tier="1:fs",cpu_num_chunks="",path="/mnt/a"} 1
```

Two tiers of the same type then add a series instead of new label names.

## 2. Boolean label values

`_observe_info()` uses `str()`, so a `bool` renders as `"True"` / `"False"` —
see `tier1_fs_o_direct="True"` in the PR's test output. Prometheus convention is
lowercase. Worth normalizing in `_observe_info()` before out-of-tree tiers
depend on the current form.
