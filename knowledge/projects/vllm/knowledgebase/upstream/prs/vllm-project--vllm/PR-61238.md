# [Bugfix][NIXL] Stop reading from a remote engine whose READ has stalled

[Upstream PR](https://github.com/vllm-project/vllm/pull/61238) · state: open · merged: False

## Original PR description

## Overview

In pull mode, a READ on a wedged connection stays in `PROC` and never fails, and the connection is never taken out of use, since that only happens on an error or when the engine has no reads in flight. So every later request prefilled on that engine reads over the same connection, hangs, and pins its blocks.

This marks the engine invalid once one of its READs has been in flight for `stalled_read_timeout` (480 s by default), the same way it is already handled when its NIXL metadata is lost: new reads to that engine go straight to `kv_load_failure_policy`, and once the stalled READs finish, the engine is released and re-handshaked.

Partially addresses #59971. No other open PR addresses this.

## Claims

- After the deadline, new requests whose KV is on the stalled engine don't read from it and don't pin blocks. Other engines are unaffected.
- If the stalled READs finish, the engine is released and re-handshaked on the next request.
- Adds `stalled_read_timeout` (default 480 s, set to 0 to disable). Push mode is unchanged.

## Validation

`pytest tests/v1/kv_connector/unit/test_nixl_connector.py -k "TestPeerReplacement or stalled_read"`: 30 passed, including two new cases.

| | `main` | this PR |
|---|---|---|
| Blocks pinned at the end | 470 (78.5%) | 55 (9.2%) |
| READs posted to `bad` | 5 | 1 |
| Requests from `bad` | all 5 hang until abort | 1 hangs, 4 fail right away |
| Next request from `bad` after the READs finish | reuses the connection and hangs | re-handshakes and completes |

The 55 blocks and the one hanging request are the first read from `bad`, posted before the deadline. The four later requests from `bad` are rejected and pin nothing. Those 55 blocks are freed once that READ finishes (see below for why not earlier).

## Details

Flow on `main` (D = decode, E = prefill engine with one wedged connection):

1. Request A is prefilled on E. D starts reading its KV, and one READ stays in `PROC`.
2. A never finishes receiving, so its blocks stay pinned, even after the client aborts.
3. E always has a READ in flight, so it is never evicted or invalidated.
4. Request B from E reads over the same connection. Back to 2.

With this PR, D records a deadline when it starts a request's READs. Past it, E is marked invalid, so B is rejected at step 4 before any READ is posted.

The engine is only marked invalid, not disconnected right away. Disconnecting removes E's remote metadata, and NIXL then reports the stalled READ as failed even though the transfer underneath may still be writing into A's blocks. Freeing those blocks at that point would let the late write corrupt whichever request gets them next. So the existing cleanup waits for in-flight READs to actually finish before it releases an invalid engine, and this PR keeps that.
