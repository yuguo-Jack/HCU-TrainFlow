# [CI] Fix the Qwen2 embed memory leak and HfRunner no-cache logprobs

[Upstream PR](https://github.com/vllm-project/vllm/pull/63537) · state: closed · merged: True

## Original PR description

- `test_embedding.py`: edit the Qwen2 embed SentenceTransformer through `hf_model.model` so `HfRunner` can free it before vLLM starts
- `conftest.py`: `HfRunner` keeps only the last position of every generation step's logprobs, not just the first step's

These are two separate failures in the Extended Pooling / Extended Generation groups, each with its own culprit.

**Qwen2 embed (all platforms).** `test_embedding.py::test_models[ssmits/Qwen2-7B-Instruct-embed-base]` first broke in #62835, whose sentence-transformers 5.6 bump changed the HF reference (cosine 0.7963, [build 97017](https://buildkite.com/vllm/ci/builds/97017/list?jid=01a16ca7-c942-4db4-b589-f9460ca33724&tab=output), AMD and NVIDIA). #63452 restored the reference but bound the SentenceTransformer to a local name, so `HfRunner.__exit__` could no longer free its ~13 GiB, and the same test then failed on both vendors with memory still held when vLLM starts ([build 97064](https://buildkite.com/vllm/ci/builds/97064): NVIDIA "Free memory on device cuda:0 (18.74/32.5 GiB) … less than desired (0.92, 29.9 GiB)", MI355 DPX "Memory of devices [0] not free"). `git bisect` from 49d634bd6a (97017) to e7473bf686 (97064), measuring GPU memory held when `vllm_runner` starts, lands on #63452 (7a64fb8fc9): 7.16 GiB held at its parent e9acf48614 vs 14.89 GiB at 7a64fb8fc9 (bisect run with sentence-transformers 5.6 fixed, good/bad threshold 8 GiB).

**Domyn Edge (ROCm only).** `test_common.py::test_models[...Domyn-Edge-Base]` has failed on MI355 since the model was added in #62544, because the HF reference decodes through `varlen_attn`, which is top-left aligned on ROCm (pytorch/pytorch#201930). #63452 switched that reference to `use_cache=False`, which exposed a latent `HfRunner` bug from #4942: `_hidden_states_to_logprobs` dropped the prompt positions only on the first step, but without a KV cache every step returns all positions, so later steps read the wrong one (the failure moved from `Test0` in 97017 to `Test3` in 97064). CUDA is unaffected: its Domyn reference keeps the KV cache, and the CUDA Extended Generation job passes.

On MI350X: the Qwen2 embed test passes 10/10 with 4.2-4.6 GiB held when vLLM starts (17.9 GiB before); `use_cache=False` now gives the same top-5 as the cached run at every step (16/16 steps on pythia-70m, 2/16 before); the Domyn tests pass 20/20 over a 10x loop (3/3 failed before); and cached models are unchanged (`test_common.py -k "tiny-mixtral or stablelm or starcoder2"`: 8 passed).
