# [Bugfix][LoRA] Count pinned adapters against max_loras when scheduling

[Upstream PR](https://github.com/vllm-project/vllm/pull/63923) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Fixes #63924.

`pin_lora` keeps an adapter in one of the `max_loras` GPU slots, but the scheduler doesn't know about pins and still admits up to `max_loras` other adapters per step. With `max_loras=2` and one pinned adapter, a batch using two other adapters makes the worker evict one that the batch needs, and building the LoRA mapping raises `KeyError` in `convert_mapping`, which kills EngineCore. This makes the scheduler count pinned adapters toward `max_loras`.

## Claims

- The scheduler admits at most `max_loras` distinct adapters per step including pinned ones; a request for a pinned adapter doesn't need a new slot.
- `EngineCore.pin_lora` / `remove_lora` keep the scheduler's set of pinned adapters up to date.
- If a batch still cannot fit next to the pinned adapters (for example after pinning while requests are already running), the worker raises a clear `RuntimeError` instead of evicting an adapter the batch uses and failing with `KeyError`.
- Reloading a pinned adapter with `load_inplace=True` keeps it pinned (it was silently unpinned).

## Details

Root cause: pins live only in the worker's `LRUCacheLoRAModelManager`. `Scheduler.schedule` limits distinct adapters per step to `max_loras`, and the worker's guard checks the same total. `activate_adapter` then evicts the oldest *unpinned* active adapter to make room, which can be one the same batch just activated.

- `SchedulerInterface.set_lora_pinned` is a no-op by default, so custom schedulers keep working.
- Pinning while requests for other adapters are already running can still produce a step that doesn't fit; that now fails with the clear `RuntimeError` above rather than `KeyError`. Avoiding it entirely would mean preempting running requests on pin, which seemed out of scope here.
- The in-place reload fix records the pin before `remove_adapter` (whose `LRUCache.pop` drops pins) and re-pins after the reload.

Not a duplicate: searching issues and PRs for `pin_lora`, "pinned lora", "All items are pinned", `max_loras pinned`, `set_lora_pinned` and "pinned adapter KeyError" finds no report or fix. #59819 relies on pinning (GPU-only slot updates require a pinned adapter) but doesn't touch slot budgeting; #63077 and #63526 handle DP idle-batch adapter removal.
