# [KV Offload] Add a store trigger and isolated store trigger handlers

[Upstream PR](https://github.com/vllm-project/vllm/pull/64286) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Phase 1 of #61396. Design comments belong in the RFC.

This PR gives the offloading manager the cause of each store, and moves the connector's store code into one handler per trigger. It adds `ON_HANDOFF` for state blocks that the KV cache manager hands off. The next PR adds `ON_OVERWRITE`, lets the manager select its triggers, and adds the `lazy` store mode.

This PR replaces #61426.

## Claims

- New `StoreTrigger` enum with `ON_COMPUTE` (the chunks are complete) and `ON_HANDOFF` (a state block is about to be reused, so the store cannot be postponed).
- `prepare_store` and `complete_store` take a required keyword-only `trigger`. `complete_store` also takes `success` keyword-only. An out-of-tree manager must add both parameters.
- The connector makes store jobs through a `StoreTriggerHandler` per trigger, in `offloading/store_triggers/`. Handlers offer keys and jobs through `StoreJobSink`. The scheduler owns the job ID, status, trigger stamp, fences, flushes and completion.
- Handlers are isolated: no handler knows of another, and each keeps its own state. The scheduler keeps global state and gives every handler the same hooks (`on_load_scheduled`, `on_request_removed`, `on_request_restarted`, `reset`, `first_live_chunk_idx`, `build_store_jobs`).
- `first_live_chunk_idx` returns the first chunk of a group whose GPU block ids a handler may still read, or `None` when it reads none. The scheduler zeroes stale sliding-window block ids only from the lowest value on.
- The scheduler adds `OnHandoffStoreHandler` whenever the config has a copy-on-write source group (`MambaSpec` with `mamba_cache_mode="align"`), before the manager's triggers. The job-ID order does not change, and the manager can decline these stores in `prepare_store`.
- The tiering manager gives the trigger to its primary tier. A promotion is not a store, so `prepare_write` and `complete_write` are real methods.

## Compatibility

`prepare_store(keys, req_context, *, trigger)` and `complete_store(keys, req_context, *, trigger, success)` break out-of-tree managers. That is the only break. There is no user-visible config change.

Eager behavior is unchanged. The aligned-boundary and partial-tail stores keep the same source, the same keys and the same job-ID order. They now live in `OnHandoffStoreHandler`.

- orozery · comment · 2026-11-01T12:01:13Z · [source](https://github.com/vllm-project/vllm/pull/64286#discussion_r4435494323)

File: `vllm/distributed/kv_transfer/kv_connector/v1/offloading/store_triggers/on_compute.py` · line None

This will be useful for lazy offloading as well.
Claude suggests we put them in their own handler:

**Where should the hand-off stores live?**

`OnComputeStoreHandler` holds two store kinds that are not `ON_COMPUTE` stores: the aligned boundary stores and the partial-tail CoW stores, both fed by `kv_connector_block_state.boundary_state_offloads`. They differ from chunk stores in three ways:

- **Who decides when.** The KV cache manager sends the hand-off when the recurrent state block is about to be reused. Neither the eager nor the lazy policy picks that moment.
- **The source is short-lived.** The CoW copy is offered once, so the store can't be postponed. Lazy mode must store it at the same step as eager mode.
- **No per-request progress.** It never reads `_next_stored_chunk_idxs`; it works from `req_status` and the hand-off only.

So every store mode stores these the same way, at the same time. That makes it a trigger of its own, not part of `ON_COMPUTE`. If it stays in `OnComputeStoreHandler`, a manager that later selects only `ON_OVERWRITE` or lazy silently stops storing Mamba `align` state. Hybrid models then get no prefix hits from offload, and nothing in the logs says why.

Suggested layout:

```
store_triggers/
  base.py        StoreTriggerHandler
  on_compute.py  OnComputeStoreHandler   (chunk stores only)
  handoff.py     HandoffStoreHandler     (aligned boundary + partial tail, _cow_source_groups)
  candidates.py  select_store_candidates (was common.py; avoids two `common` modules)
```

- Add `StoreTrigger.ON_HANDOFF`, so the manager sees the real cause. A lazy manager can then admit these stores without running its overwrite admission.
- The scheduler adds this handler on its own whenever the config can produce hand-offs (`supports_partial_tail` or any `requires_cow_source` group). The manager doesn't select it. A manager can still decline these stores in `prepare_store`.
- Run it before `OnComputeStoreHandler`. That keeps today's job-ID order, so this stays a pure move.
- It also retires the name `_build_partial_tail_store_jobs`, which today also runs the aligned-boundary path.
