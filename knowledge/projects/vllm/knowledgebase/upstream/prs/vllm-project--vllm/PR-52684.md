# [ROCm] Tune gfx1100/gfx1151 unified attention for long prefill

[Upstream PR](https://github.com/vllm-project/vllm/pull/52684) · state: open · merged: False

## Original PR description

## Purpose

Use a wider query block for long unified-attention prefill on exact gfx1100
and gfx1151, while preserving decode, short prefill, and other architectures.
For non-power-of-two GQA ratios, use the full floor-divided query block instead
of rounding the ratio up before division.

Addresses #52585.

Live searches found no overlapping open PR for this unified-attention tuning.

Thanks @SCcagg5 for the gfx1151 measurements and two contributed commits, and
@youyoulyz for the independent gfx1100 floor-versus-pow2 validation.

AI assistance was used for investigation, implementation, validation, and
drafting. The commits retain their Claude, Cursor, and Copilot disclosures.
The human submitter reviewed every changed line and is responsible for the
change.

## Changes

- gate the 64-row launch to gfx1100/gfx1151, `max_seqlen_q >= 512`, and
  `num_queries_per_kv <= 16`
- compute tuned `BLOCK_Q` as `64 // num_queries_per_kv`
- preserve the existing fallback and B200 tuning
- add selector boundaries and a real q_len=512 dense-reference kernel test for
  nq=4/5/6/7

`TILE_SIZE_PREFILL` is intentionally unchanged.

## Test Result

  to the split-K tests added in #56148; the new tests now use that module's

  the split-K path, which is limited to `max_seqlen_q <= 8`.

  - selector and real tuned-kernel dense-reference tests: 13 passed;

  numerical assertions passed.

@liminfei-amd The CUDA half of #52585's open question, measured the same way @jijic137 measured the gfx1100 half: at the kernel, on an A100-SXM4-40GB.

Short version: **the architecture gate is not what separates the machines that benefit — Ampere gains as much as gfx1100 does — but `max_seqlen_q >= 512` is too low a threshold for CUDA.**

Method: vLLM 0.28.0, torch 2.13.0+cu130, Triton 3.7.1. Released 0.28.0's `triton_unified_attention.py` is byte-identical to `main` (md5 `49fab3b643bf5a88eb65303ce377996b`), so this PR applies to the release unmodified. Inputs built with the construction in upstream's own `tests/kernels/attention/test_triton_unified_attention.py`; the launch choice comes from flipping this PR's `_is_gfx1100` seam, so nothing but `(BLOCK_M, BLOCK_Q, num_warps)` differs between arms. Single-sequence prefill, CUDA-event timing, 10 warmup / 40 timed, median. 140 rows over `q_len` 256-16384 x `num_queries_per_kv` {4, 7, 8, 16} x `head_size` {64, 128, 256} x sliding window on/off x {bf16, fp16}.

`q_len=256` is below this PR's gate, so all arms select the same launch there. Those 20 rows are the control: they span 0.981 to 1.046, which puts the noise floor at +/-4.6%.

**Speed**, PR arm against stock, median over the 20 configurations at each
length:

| q_len | 256 (ctl) | 512 | 1024 | 2048 | 4096 | 8192 | 16384 |
|---|---:|---:|---:|---:|---:|---:|---:|
| median | 1.021 | 0.948 | 0.987 | 1.281 | 1.394 | 1.529 | 1.597 |
| min | 0.981 | 0.848 | 0.911 | 1.102 | 1.181 | 1.221 | 1.238 |
| max | 1.046 | 0.991 | 1.282 | 1.819 | 2.186 | 2.080 | 2.189 |

At 16384 all 20 configurations win, the smallest by 1.238x and the largest by 2.189x (bf16, `head_size=64`, nq=16) — the same order of gain #52585 reports on gfx1100.

The mechanism looks different from the gfx1100 reading, though. At `q_len=8192, nq=4` the two arms launch 16392 and 4104 workgroups against 108 SMs, so neither arm is short of parallelism on A100. What changes is how much KV traffic each program amortizes: a 4x wider `BLOCK_Q` means 4x fewer programs walking the same KV range. That also predicts the gain growing with prefill length, and it is not architecture-specific.

**The threshold is what CUDA disagrees about.** All 20 rows at `q_len=512` come
in below 1.0. A second pass swept the crossover region on a fresh VM, re-running the baseline at the end of each row so ordering drift is measured rather than assumed (median drift 1.000):

| q_len | 512 | 640 | 768 | 896 | 1024 | 1280 | 1536 | 1792 | 2048 | 3072 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| median | 0.982 | 0.996 | 0.991 | 0.982 | 0.991 | 1.165 | 1.244 | 1.363 | 1.404 | 1.536 |

The sign flips between 1024 and 1280 and the gain is solid from 1536 up. The losses below that are small, a few percent and near the control band, but they run one direction: 20 of 20 rows in the first pass, and all five lengths below 1280 here.

So the two options the evidence supports are raising the threshold if the gate goes global, or keeping `_is_gfx1100()` if 512 stays.

**The `num_warps=4` pin does nothing on A100.** A third arm ran `BLOCK_M=64`
with Triton's default warp count: median ratio against the PR arm is 1.001 over the 120 gated rows. On this hardware the wider query block is the whole effect.

**One numerical difference.** 117 of the 140 rows are bitwise-equal, matching
@jijic137's result. The 23 that are not all sit in a single slice, bf16 with `head_size=64`; bf16 at 128 and 256 and fp16 at 128 are bitwise-equal at every length tested. Measured against the local ULP that difference is **at most 1.0000 ULP, with zero elements beyond it**, on 507 of 550,502,400 elements (0.0001%). Both `BLOCK_M=64` arms differ from the baseline identically, so it comes from the wider query block and not the warp pin. Benign, but on CUDA "bitwise-equal" is not quite the right claim for that slice.
