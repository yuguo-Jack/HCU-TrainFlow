# [Bugfix][UMBP] Reject DRAM watermarks that keep MORI from evicting

[Upstream PR](https://github.com/vllm-project/vllm/pull/64676) · state: open · merged: False

## Original PR description



## Overview

Stacked on #61794: only the last commit is new; the rest belongs to #61794. Embedded UMBP accepted DRAM watermark settings that make MORI turn eviction off. The pool then fills up, and every later store fails without a visible error.

## Claims

- `dram_low_watermark >= dram_high_watermark` is rejected at config time. Before this change, equal values were accepted.
- The worker also checks the pair MORI will actually use, including its defaults (high 0.9, low 0.7), before creating the client. Setting `dram_high_watermark=0.6` alone now fails at startup.

## Validation

| Check | Without fix | With fix |
|---|---|---|
| `pytest -q v1/kv_connector/unit/test_umbp_embedded.py -k "watermark or invalid_embedded_dram or created_only_for_worker"` | 3 failed, 5 passed | 8 passed |
| e2e, Qwen3-0.6B, 64 MiB pool, low == high (0.75) | 0 external hits, repeated `MORI UMBP store retry 2 left 8/8 objects pending` | rejected when the runtime config is built (covered by the parametrized test above) |

The new worker-side test runs against the real `mori.cpp.UMBPConfig` on MI350X, using MORI v1.2.3.post1 built with UMBP.

## Details

MORI's `PageBackend::EnableLocalEviction` (`page_backend.cpp:760`) needs `0 < low < high <= 1`. Otherwise it logs a C++ `WARN` and leaves eviction off; that warning never reaches vLLM's logs. vLLM only rejected `low > high`, and only when both values were set. The check sits in `_configure_dram` because only there are MORI's defaults, and any env overrides, applied to the config object. Not a duplicate: no open PR touches UMBP watermark validation.
