# [Bugfix][Platform] Don't resolve current_platform during import vllm

[Upstream PR](https://github.com/vllm-project/vllm/pull/60766) · state: open · merged: False

## Original PR description



## Overview

Since #45424, `import vllm` resolves `current_platform` and loads platform plugins while vLLM is still half-imported, because `PIN_MEMORY` in `vllm/utils/torch_utils.py` is computed at import time. This PR computes `PIN_MEMORY` on first access, so `import vllm` no longer resolves the platform, as `vllm/platforms/__init__.py` requires. Same root cause as #48397; #48444 fixed only that issue's WSL symptom.

## Claims

- `import vllm` no longer resolves the platform. The resolver runs 0 times during `import vllm`, down from 1.
- An out-of-tree platform plugin whose `register()` imports `vllm.utils.torch_utils`, directly or through another vLLM module, is detected again. Before this change it failed with `cannot import name ... from partially initialized module 'vllm.utils.torch_utils'`, and vLLM silently fell back to another platform.
- `PIN_MEMORY` keeps its value. All `from vllm.utils.torch_utils import PIN_MEMORY` sites and monkeypatches (e.g. `tests/models/kimi_k3/test_kda_metadata.py`) keep working.

## Validation

## Details

**Root cause** (main):
1. `vllm/__init__.py:14` imports `vllm.env_override`.
2. `vllm/env_override.py:153` imports `vllm.utils.torch_utils`.
3. `vllm/utils/torch_utils.py:76` runs `PIN_MEMORY = is_pin_memory_available()`.
4. `vllm/utils/platform_utils.py:45` imports `current_platform`, which resolves the platform and loads plugins.

This happens while `torch_utils` has only run up to line 76. A plugin that imports vLLM in `register()` gets an `ImportError`. Detection swallows it (`vllm/platforms/__init__.py`, `resolve_current_platform_cls_qualname`), so vLLM falls back to another platform and caches that platform's pin-memory setting.

**Fix.** A module `__getattr__` (PEP 562) computes `PIN_MEMORY` on first access and stores it as a module global, so later reads are plain global lookups. The three uses inside `torch_utils.py` go through `_pin_memory()`, which also honours an assigned or monkeypatched `PIN_MEMORY`.

**Why the existing plugin test missed this.** The dummy plugin's `register()` imported nothing from vLLM, and the test only checks the final `device_name`. Also, the Plugin Tests CI step only triggers on changes under `vllm/plugins/` and `tests/plugins/`, so it did not run for #45424. It does run for this PR. Adding `vllm/utils/torch_utils.py` / `vllm/env_override.py` to that step's `source_file_dependencies` would catch future regressions; I left it out to keep CI load unchanged, but can add it if maintainers prefer.

**Alternative considered.** Move `is_torch_equal*` out of `torch_utils`, so `env_override` no longer imports it (3 files, +68/-51). That also fixes `import vllm`, but it leaves the import-time platform resolution in `torch_utils` for the next early importer.

**Duplicate check.** I searched open and closed issues and PRs for `PIN_MEMORY`, `is_pin_memory_available`, `current_platform` + `import vllm`, `platform plugin circular import` and `partially initialized module torch_utils`. Only related, none open: #48397 / #48444 (WSL symptom of the same root cause) and #52285 (logging of detection failures).
