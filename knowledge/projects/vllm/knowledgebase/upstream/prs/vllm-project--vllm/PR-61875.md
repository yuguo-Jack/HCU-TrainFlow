# [Perf][DeepSeek V4] Declare MXFP8 MoE activations and run them as block FP8 on Hopper

[Upstream PR](https://github.com/vllm-project/vllm/pull/61875) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

DeepSeek V4 / V4.1 MXFP4 experts now declare MXFP8 activations, the format they target on Blackwell. On Hopper, Humming runs a checkpoint-declared MXFP8 key as block FP8 (group 128), where its SM90 W4A8 kernels are tuned, instead of BF16. Builds on #62751 (`_humming_input_schema`) and the humming-kernels 0.1.18 bump (#62816).

## Claims

- DeepSeek-V4-Flash on 4x H200 (Humming, the SM90 default): decode-heavy output throughput +9-18% at TP4 and +21% at TP4 + EP, prefill-heavy +2.5% / +5%, GSM8K unchanged.
- Low-concurrency decode (4 concurrent requests) is 2% (TP4) and 6.5% (TP4 + EP) slower; tuning that belongs in Humming.
- Only the Humming path reads the declared key. Blackwell's default backends (TRTLLM MXFP8, DeepGEMM) are unchanged. `--quantization-config.moe.activation mxfp8` runs MXFP8 as requested, and `VLLM_HUMMING_INPUT_QUANT_CONFIG` still overrides both.

## Validation

DeepSeek-V4-Flash, 4x H200, humming-kernels 0.1.18, the same build for both columns. The BF16 column forces BF16 with `VLLM_HUMMING_INPUT_QUANT_CONFIG='{"allow_fallback": true}'`. Benchmarks ran twice each with seeds 1 and 2. The PR column logged `Running checkpoint MXFP8 MoE activations as block FP8 (group 128) on Hopper.`; the BF16 servers did not.

Tests: `pytest tests/quantization/test_humming_mxfp4_block_fp8.py` (11 passed; the new cases fail without the change) and `tests/kernels/moe/test_moe_kernel_oracle.py`.

## Details

- `deepseek_v4` and `deepseek_v41` quant configs pass `activation_key=kMxfp8Dynamic` to `Mxfp4MoEMethod`. Before this, they passed no key, and Humming built its input schema from `VLLM_HUMMING_INPUT_QUANT_CONFIG`, which defaults to BF16.
- `_humming_input_schema` maps a checkpoint-declared `kMxfp8Dynamic` to `kFp8Dynamic128Sym` on SM90 when the user gave no override. Humming accepts MXFP8 x MXFP4 on SM90, but its SM90 W4A8 schedules (humming #95, #126, #133) are tuned for FP8 group 128 x MXFP4 group 32.
- Earlier revisions of this PR gated on expert parallel because TP4 decode was 15% slower on humming 0.1.17. On 0.1.18 TP4 is faster too, so the gate is gone and the condition is only that the checkpoint declares MXFP8.

Behavior changes and limitations:
- `--quantization-config.moe.activation` set to anything other than `mxfp8` now fails at load for these models, because `_resolve_activation_key` rejects a conflict with the checkpoint's key. Use `VLLM_HUMMING_INPUT_QUANT_CONFIG` to run another format on Humming.
- With an explicit `--moe-backend humming` on SM100 or SM12x, these models now run MXFP8 instead of BF16.
- DeepSeek-V4's own checkpoint config describes block-128 UE8M0 FP8, while V4.1's is MXFP8-style (block 32). Both declare MXFP8 here, the Blackwell format; on Hopper both run as block FP8.
- DeepSeek-V4.1, DeepEP v2, and H100/H20 were not measured.
- The ROCm DeepSeek V4 path builds its own MoE method and is unaffected.

Not a duplicate: #59488 (closed) proposed an opt-in activation name for this method; #62751 provides the shared Humming input-schema resolution this builds on.
