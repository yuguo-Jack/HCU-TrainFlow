# [Feature] NVFP4 dispatch for fused RoPE quantization

[Upstream PR](https://github.com/vllm-project/vllm/pull/46031) · state: closed · merged: False

## Original PR description

## Purpose

Add NVFP4 dispatch to `fused_indexer_q_rope_quant` (fused RoPE). NVFP4 is NVIDIA's proprietary FP4 format used by FlashInfer CUTLASS backends on Blackwell GPUs.

This PR adds:
- `_fused_indexer_q_rope_nvfp4_kernel`: Triton kernel (mirrors MXFP4 kernel; one thread owns each 16-element
block, no warp shuffle needed)
- `_quantize_nvfp4_block`: Triton helper (amax-based scale as float8e4nv, uses tl.div_rn for the quantization
step)
- `use_nvfp4: bool = False`: Dispatch branch in `fused_indexer_q_rope_quant`

This does not wire downstream (`sparse_attn_indexer.py` cast branch, `attention.py` flag propagation).

### Why this is needed

- Part of #45668, "NVFP4 Indexer" item on the MiniMax M3 roadmap
- FlashInfer CUTLASS NVFP4 kernels need an NVFP4-quantized Q, and no NVFP4 path exists in-tree — this PR adds it, fused from day one.
- Quant cost is +2–3 µs vs MXFP4 at decode sizes (benchmark in comments); the payoff lands downstream in
the NVFP4 logits matmul (follow-up, not this PR).

## Test Plan

```bash
# Kernel correctness — compares Triton NVFP4 output against the unfused reference
```

- namgyu-yun · comment · 2026-07-07T02:45:12Z · [source](https://github.com/vllm-project/vllm/pull/46031#issuecomment-4899616125)

Kernel benchmark results (command in the Test Plan). RTX PRO 6000 Blackwell (SM120, 96 GB), torch 2.11.0+cu130, Triton path.

| num_tokens | FP8 (µs) | MXFP4 (µs) | NVFP4 (µs) | NVFP4 / MXFP4 |
| --- | --- | --- | --- | --- |
| 1 | 6.85 | 8.19 | 10.24 | 1.25× |
| 4 | 7.49 | 8.19 | 10.94 | 1.34× |
| 16 | 8.16 | 9.50 | 11.58 | 1.22× |
| 64 | 9.54 | 10.94 | 13.63 | 1.25× |
| 256 | 17.66 | 21.79 | 32.74 | 1.50× |
| 1024 | 44.32 | 59.36 | 87.36 | 1.47× |
| 4096 | 153.89 | 179.49 | 292.13 | 1.63× |
| 16384 | 597.28 | 666.91 | 1114.08 | 1.67× |

The NVFP4 path is currently slower than MXFP4: ~1.25× (+2–3 µs) at decode-size M, up to 1.67× at 16K. It is not the correctly-rounded division: re-benchmarking with per-element `tl.div_rn` replaced by block-wise reciprocal + multiply (perf probe only, changes numerics) recovered just 4% at 16K. The likely cause is structural — 16-element blocks do 2× the amax reductions and scale stores of MXFP4's 32-element blocks. I plan to look at block-granularity restructuring as a follow-up; this PR's claim is the dispatch + bit-exact correctness.
