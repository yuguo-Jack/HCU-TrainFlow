# [Frontend][Observability] Emit spec-required gen_ai.operation.name (+ gen_ai.request.model) on request spans

[Upstream PR](https://github.com/vllm-project/vllm/pull/47633) · state: open · merged: False

## Original PR description

# [Frontend][Observability] Emit spec-required `gen_ai.operation.name` (+ `gen_ai.request.model`) on request spans

## Problem

vLLM's OTel request span (`llm_request`, emitted in `OutputProcessor.do_tracing`,
`vllm/v1/engine/output_processor.py`) does not set `gen_ai.operation.name`, and never sets
`gen_ai.request.model` — the only model attribute defined in `vllm/tracing/utils.py` is
`gen_ai.response.model`, which is dead (emitted nowhere). The span name is also the hardcoded
literal `"llm_request"` rather than the conventional `{operation} {model}`.

The practical cost is at the server-operator level. A single vLLM instance commonly serves
`/v1/completions`, `/v1/chat/completions`, and embeddings at once, but today every request
emits a span with the *same* name (`llm_request`) and no operation attribute — so the
operation cannot be told apart from the span itself. An operator who runs vLLM but does not
control the calling clients has this server-side span as their only observation point; they
cannot rely on a client-side span to carry this. `gen_ai.operation.name` and
`gen_ai.request.model` are the identity fields backends use to name, group, and filter GenAI
spans, and they make each vLLM span self-identifying.

For reference, `gen_ai.operation.name` is marked *Required* on a GenAI span by the current
OpenTelemetry GenAI semantic conventions (`semantic-conventions-genai/model/gen-ai/spans.yaml`)
and `gen_ai.request.model` is conditionally-required.

> ⚠️ The GenAI conventions carry `stability: development` (experimental) and names may still
> shift, so this change makes no difference to current output unless a user explicitly opts in
> (see below).

**Span kind note:** the spec's inference span is usually CLIENT and permits INTERNAL for
models running in-process. This change sets the attributes on vLLM's existing server-side
span, which is complementary to (not a replacement for) any client-side span a caller emits —
it's aimed at the operator who only has the server span to work with. Happy to align on the
preferred span kind if you'd rather handle it differently.

## Change

Emit `gen_ai.operation.name`, `gen_ai.request.model`, and the spec span name only when the
standard `OTEL_SEMCONV_STABILITY_OPT_IN=gen_ai_latest_experimental` switch is set:

- **unset (default):** identical to today — no new attributes, span name stays `"llm_request"`.
- **`gen_ai_latest_experimental`:** set `gen_ai.operation.name` (`chat` / `text_completion`),
  `gen_ai.request.model` (served model name), and span name `{operation} {model}`.

`operation.name` is plumbed through the existing request pipeline the same way `trace_headers`
already flows (`generate` → `add_request` → `process_inputs` → `EngineCoreRequest` →
`RequestState` → `do_tracing`). `request.model` is a constant threaded into `OutputProcessor`
at init.

## This is not a one-liner

`RequestState` carried neither the model name nor the operation type, and `OutputProcessor`
did not hold the served-model name:

- **`request.model`:** thread the served-model constant into `OutputProcessor` once at init
  (cheap, no per-request cost).
- **`operation.name`:** add an `operation_name` field to `EngineCoreRequest` (mirroring
  `trace_headers`), set it in `process_inputs`, read it back in `RequestState.from_new_request`,
  and pass it from the two OpenAI generative entrypoints.

The attribute/span-name selection is a small pure helper (`latest_gen_ai_semconv_attributes`)
so it can be unit-tested without an engine.

## Explicitly out of scope

- **Token rename** `prompt/completion_tokens → input/output_tokens` — in flight in **#44373**
  (issue **#44358**). Deliberately not touched here; it can ride the same opt-in switch.
- `gen_ai.request.n → gen_ai.request.choice.count` — same mechanism, deferred.
- **`gen_ai.provider.name`** — open for a self-hosted server (vLLM isn't in the predefined
  provider enum; a prior attempt to add the old `gen_ai.system`, **#17982**, was closed
  unmerged). Not included.
- The `gen_ai.latency.*`-on-span vs. spec `gen_ai.server.*`-metrics question, and the broader
  observability tracker in **#39979** — orthogonal.
- Operation names for other entry paths (responses, scoring, beam-search, speech, offline
  `LLM`) are left `None` for now → those spans omit `operation.name` and keep the
  `llm_request` name (no regression). Easy follow-up once the approach is agreed.

## Testing

Environment: NVIDIA RTX (opt-125m), a real OpenTelemetry Collector
(`otel/opentelemetry-collector-contrib`, OTLP gRPC receiver → debug+file exporters).

**Unit** (`tests/tracing/test_gen_ai_semconv.py`, 11 cases, no GPU):

```
.venv/bin/python -m pytest tests/tracing/test_gen_ai_semconv.py -v   # 11 passed
```

Covers the opt-in gate parsing (unset / exact / list / whitespace / partial / unrelated) and
the attribute + span-name helper.

**End-to-end** through the real collector via HTTP to `vllm serve … --otlp-traces-endpoint`:

| Case | span name | gen_ai.operation.name | gen_ai.request.model | legacy tokens |
|---|---|---|---|---|
| opt-in ON, POST /v1/completions | `text_completion facebook/opt-125m` | `text_completion` | `facebook/opt-125m` | present |
| opt-in ON, POST /v1/chat/completions | `chat facebook/opt-125m` | `chat` | `facebook/opt-125m` | present |
| opt-in OFF, POST /v1/completions | `llm_request` | (absent) | (absent) | present |

The two opt-in-ON rows show the point of the change: the same instance's spans now
self-distinguish `text_completion` from `chat` by name and attribute. The opt-in-OFF row
confirms default output is byte-for-byte unchanged, and legacy token attributes are untouched
in all three cases.

`ruff check` + `ruff format --check` clean on all changed files. The GPU integration test was
extended for both the default-off and opt-in cases.

## Non-duplication

Does not overlap #44373/#44358 (token rename), #17982 (old `gen_ai.system`, closed), or #39979
(observability tracker). No existing issue/PR sets `gen_ai.operation.name` /
`gen_ai.request.model`.

## Questions for maintainers

1. Is `OTEL_SEMCONV_STABILITY_OPT_IN=gen_ai_latest_experimental` the gate you'd want the whole
   GenAI semconv migration (including #44373's tokens) to sit behind?
2. Prefer plumbing `operation.name` from the entrypoints (as here), or a coarser default for
   the unwired paths?
