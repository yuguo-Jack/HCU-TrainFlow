# [XPU][Qwen4Exp] Run QSA block selection on XPU

[Upstream PR](https://github.com/vllm-project/vllm/pull/64926) · state: open · merged: False

## Original PR description



## Overview

Part of #54595 (item 6). Stacked on #64925 (draft until it merges; only the last commit is this PR). The code change is independent; the XPU tests reuse #64925's test enablement. Needed by the QSA follow-up to #61607.

QSA block selection cannot run on Intel XPU: `_topk` only calls the CUDA ops `cooperative_topk` / `persistent_topk`,
and the decode scorer's `tl.dot` has N = 4 at a plain decode step, which Intel Triton 3.8.0 refuses to compile
(N ≥ 16). On XPU, `_topk` now calls vllm-xpu-kernels' `top_k_per_row_decode`, and the decode scorer pads its query
rows (masked) so N ≥ 16. CUDA compiles and runs the unchanged kernel and top-k.

## Claims

- On XPU, selection returns the same index sets as the torch reference in the existing selection tests (decode,
  prefill, split, no complete blocks).
- `top_k_per_row_decode` with `next_n=1` bounds row i by `visible_blocks[i]` and pads short rows with `-1`, the
  contract of the CUDA ops (vllm-xpu-kernels `csrc/topk_per_row.cpp`: `rowEnd = seqLens[row / next_n] - next_n +
  row % next_n + 1`).
- On CUDA, `MIN_DOT_N` is 1, which compiles the kernel unchanged; the top-k dispatch is untouched.

## Details

1. `_topk`: `if current_platform.is_xpu(): ops.top_k_per_row_decode(logits, 1, visible_blocks, block_indices,
   rows, stride0, stride1, block_topk)`. `visible_blocks` is int32 at every caller, as the CUDA ops require too.
   The 1 MiB CUDA top-k workspace is still allocated on XPU and unused.
2. `_qsa_mqa_paged_uniform_kernel` gains `MIN_DOT_N: tl.constexpr = 1`;
   `DECODE_QUERY_LEN_PADDED = max(next_pow2(DECODE_QUERY_LEN), MIN_DOT_N // NUM_HEADS_PADDED)`. Padded query rows
   are already masked on load and store. Launch and JIT warmup pass `_DECODE_MIN_DOT_N` (16 on XPU, 1 elsewhere),
   so the warmed specialization is the one launched.
3. Tests: the four selection tests move from the CUDA-only marker to `requires_qsa_kernels`.

Tradeoff: on XPU a plain decode scores 4× the query rows it needs (masked). With Triton 3.8 the alternative does not
compile; Intel Triton 3.9 accepts N < 16 through an FMA fallback, and whether that is faster than the padded DPAS
dot has not been measured, so the padding is not version-gated.

Not covered: deterministic tie-breaking. ReLU-summed indexer scores often tie at exactly 0.0, and neither this op nor
the CUDA ops promise a repeatable choice among ties; that is a separate change.

CI: no Intel CI step runs these tests; XPU results above were run locally. The CUDA step in
`test_areas/models_basic.yaml` runs them on CUDA.

Why this is not a duplicate: searched on 2026-10-31 for "qsa top_k_per_row_decode", "QSA XPU", "Qwen4Exp XPU".
#55122 changes `persistent_topk` on CUDA; #62589 is the AMD path; #61607 does not run QSA. #54595 reports the
problem without a PR.
