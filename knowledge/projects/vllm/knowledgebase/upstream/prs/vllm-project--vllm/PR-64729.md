# [Rust Frontend] Let the server run over any `Llm`

[Upstream PR](https://github.com/vllm-project/vllm/pull/64729) · state: open · merged: False

## Original PR description



## Overview

Let the Rust frontend's server run over any `Llm` (vllm-project/vllm#64695): either an engine-core engine it connects to itself, as today, or a caller-built `Llm`, such as a router over several engines or a client for a remote engine like the HTTP generation client planned in vllm-project/vllm#63887.

**Stacked on vllm-project/vllm#64695; only the last two commits belong to this PR.**

## Claims

- Settings that only apply when the server drives engine-core move from the server config into `EngineCoreConfig`, and the rest is renamed `ServerConfig`. This commit is a pure refactor.
- A `Server` builder replaces `serve` and `serve_with_router_extension`. `LlmSource` says where the server's `Llm` comes from:

  ```rust
  Server::new(config, LlmSource::EngineCore(engine_core))     // vllm-rs serve
  Server::new(config, LlmSource::Provided(Box::new(router)))  // an embedding frontend
      .router_extension(extra_routes)
      .serve(shutdown)
      .await
  ```

- The server treats a provided `Llm` as opaque:
  - It skips the routes and services that drive the engine-core client: dev-mode admin routes, runtime LoRA loading, checkpoints, `/kv_event_sources`, and gRPC Control.
  - gRPC health follows the `Llm`'s liveness and readiness, as for an `EngineCoreLlm`; the `vllm.Control` health status is published only when Control is served.
  - An `EngineCoreLlm` passed as `Provided` is rejected at startup.
- `Unavailable` errors map to HTTP 503 and gRPC `UNAVAILABLE`.
- No behavior change for `vllm-rs`.

## Details

- **Why split the config.** Settings such as the transport and coordinator modes, stream interval, stats logging, request ID randomization, engine lifecycle (`manages_engine`), static LoRA adapters, and the profiler only mean something for an engine-core connection. With them in `EngineCoreConfig`, a server over a provided `Llm` cannot be configured with settings that would silently do nothing. `vllm-cmd` builds both halves as a `FrontendConfig`, and `/server_info` still reports a single flat `rust_frontend_config` object.
- **Why the server builds the engine-core path itself.** Connecting to engine-core depends on state the server owns:
  - the coordinator mode depends on whether the loaded model is MoE;
  - `--custom-histogram-buckets` has to be applied before `EngineCoreLlm::new` creates the request histograms;
  - the handshake is cancellable by the shutdown token.

  The engine-core path also enables server features: server info, static LoRA loading, and engine shutdown through `Control.Shutdown`. That is also why a provided `EngineCoreLlm` is rejected: it would get the engine-core routes but none of those settings, and its histograms would already use the default buckets.
- **`TextLlm::from_boxed`.** It keeps a provided `Box<dyn Llm>` as is. Boxing it again would hide the concrete type from the downcast that finds an `EngineCoreLlm`.
- **`AppState` and `build_router` stay private,** in line with vllm-project/vllm#43774. Embedders get the whole server through the builder instead.
- **`#[allow(clippy::large_enum_variant)]` on `LlmSource`.** It is built once per server, so boxing `EngineCoreConfig` would only make callers write `Box::new`.
- **Breaking change for Rust API users.** Callers of `vllm_server::serve`, `serve_with_router_extension`, or `Config` move to `Server::new(...)` and `ServerConfig`/`EngineCoreConfig`. These are internal Rust APIs, and all in-tree callers are migrated.

**Why this is not a duplicate.** vllm-project/vllm#63887 pursues the same goal by abstracting `EngineCoreClient` beneath `Llm`; this PR builds on the `Llm` trait from vllm-project/vllm#64695 instead. Two open PRs touch nearby code:

- vllm-project/vllm#61937 adds a `ServeExtensions` registration for request observers. The `Server` builder here is the natural place for that.
- vllm-project/vllm#64426 changes the same config and CLI code; its new settings would go into `EngineCoreConfig`.

**Open questions:**

- Building a `ServerConfig` by hand needs all of its fields, which makes it verbose for embedders. A `Default` impl or a small constructor would help, at the cost of a second set of defaults next to the CLI's.
- gRPC over a provided `Llm` (Inference and health only) is not exercised end to end yet.
