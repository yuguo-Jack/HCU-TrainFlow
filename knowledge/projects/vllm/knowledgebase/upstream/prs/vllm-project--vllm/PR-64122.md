# [Bugfix][DSA] Split FlashInfer sparse MLA calls above the 65535 gridDim.z limit

[Upstream PR](https://github.com/vllm-project/vllm/pull/64122) · state: open · merged: False

## Original PR description

## Purpose

`FLASHINFER_MLA_SPARSE` returns garbage, with no exception, for any step that sends 65,536 or more tokens through sparse MQA. For example, GLM-5.3 with `--max-num-batched-tokens 65536` returns HTTP 200 with wrong output for every prompt of 64K tokens or more.

`_forward_mqa_kernel` passes each query token to trtllm-gen as its own request (`q.unsqueeze(1)`), so the kernel batch equals the step's token count. trtllm-gen uses the batch size as `gridDim.z` (`numCtasZ = params.mBatchSize` in FlashInfer `fmhaKernels.cuh`), and CUDA caps `gridDim.z` at 65,535. A larger launch fails with `CUDA_ERROR_INVALID_VALUE`, but FlashInfer's `cuErrCheck` only prints it. The kernel never runs, and the output tensor is left uninitialized. This also makes TTFT look faster than it is.

This PR splits the trtllm-gen call into chunks of at most 32,768 query rows. Rows are independent: each token carries its own top-k list. Steps of 32,768 tokens or fewer, including every decode and CUDA graph batch, still make exactly one call and skip the `torch.cat`.

Why 32,768 rather than 65,535: vLLM's FlashInfer autotune tunes power-of-two token buckets up to `max_num_batched_tokens` and rounds calls up to a bucket (`kernel_warmup.py`). The 65,536 bucket's profiling launches of `trtllm_batch_decode_mla` fail the same way (`CUDA_ERROR_INVALID_VALUE` during startup with a 65,536 budget), so a 65,535-row call would run with a tactic picked from failed launches. 32,768 is the largest power of two under the limit.

Upstream: FlashInfer flashinfer-ai/flashinfer#4534 reports the launch failure. Its fix, flashinfer-ai/flashinfer#4536, is unmerged, and it would raise an error rather than compute large batches. SGLang hit the same issue in sgl-project/sglang#34947.

## Test Plan

- New unit test `test_flashinfer_sparse_mla_splits_batch_over_grid_limit`, with and without LSE. It mocks the kernel and shrinks the limit to 3 rows. It checks the per-call batch sizes (7 tokens -> 3, 3, 1), the slicing of every per-token argument, and the concatenated output and LSE.
- Real kernel on 1x B300 with FlashInfer 0.7.2.post1, using GLM-5.3-Flash TP4 attention shapes (nope MLA: 16 heads per rank, `kv_lora_rank` 512, `qk_nope_head_dim` 256, top-k 2048, bf16 KV). The check calls `_forward_mqa_kernel` on a large step and compares its first and last 1,024 rows against separate 1,024-token calls.
- Existing FlashInfer sparse MLA tests in `tests/v1/attention/test_sparse_mla_backends.py` and `test_flashinfer_sparse_mla_workspace.py`.

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Cap DCP workspace sizing at the per-launch batch limit**

When DCP is enabled and `max_num_batched_tokens` exceeds 65,535, `FlashInferMLASparseTRTLLMMetadataBuilder.__init__` still feeds the uncapped scheduler value to `_required_workspace_bytes`, even though the new loop never launches more than `_TRTLLM_GEN_MAX_BATCH` rows. The softmax slab scales linearly with that value: with 64 gathered heads and 140,000 tokens it reserves about 17.1 GiB per rank instead of about 8 GiB, so a configuration this patch is intended to make valid can lose roughly 9 GiB of KV capacity or OOM during builder initialization. Use `min(max_num_batched_tokens, _TRTLLM_GEN_MAX_BATCH)` when computing the requirement.

**<sub><sub>![P2 Badge](https://img.shields.io/badge/P2-yellow?style=flat)</sub></sub>  Write chunk outputs directly into the final tensor**

When a step exceeds 65,535 tokens, every chunk output remains live in `outs` and `torch.cat` then allocates and copies another full result on every sparse-attention layer. For the described 65,536 × 16 × 512 bf16 shape, that is an extra 1 GiB peak allocation and 1 GiB copy per layer, scaling linearly for larger batches and reducing KV capacity while hurting TTFT. The FlashInfer entry point supports `out=` as already used by `FlashInferMLASparseSM120Impl`, so preallocate the final output and pass each row slice to the chunk call instead of materializing and concatenating all chunk results.
