# [Frontend] Stream derender on /inference/v1/generate

[Upstream PR](https://github.com/vllm-project/vllm/pull/63103) · state: closed · merged: True

## Original PR description

 ## Overview
  
Adds `stream: true` support for `output_mode: "derender"` on `/inference/v1/generate`. This is Phase 3 of #56851. 

~**Do NOT MERGE before #63148.**~

## Claims

- `stream: true` with `output_mode: "derender"` works now instead of returning a 400. Each chunk carries a chat `delta` (`role`, `content`, `reasoning`, `tool_calls`) and the chat `finish_reason`.
- For the same tokens, the output matches coupled `/v1/chat/completions` streaming because both paths run through the same `ChatStreamProcessor`. There's no second copy of the parse logic.
- No per-chunk `/derender` hop and no `stream_state`. Each choice keeps one parser for the life of the request.
- `n > 1` works. Streaming `/derender` only supports `n=1`.
- A bad `parse_context` or a parser that rejects the tools, returns a 400 before the engine does any work.
- If the stream fails partway, the request is now aborted in the engine. This applies to the `tokens` and `text` levels too.

## Validation

Unit tests use a mocked engine. Parity tests run a real model and compare against coupled chat streaming.

```bash
pytest tests/entrypoints/scale_out/token_in_token_out -v
pytest tests/entrypoints/scale_out/derender/test_derender_parity.py -v -k "inline or stream"
pytest tests/entrypoints/openai/chat_completion/test_stream_processor.py -v
```

The parity cases cover plain text, reasoning shown and hidden, tool_choice auto/required/named, parallel_tool_calls off, stop strings and n=2. For each case they check the concatenated token IDs, content, reasoning, tool calls (name, arguments, ID shape) and finish_reason. Logprobs are covered for top_logprobs, logprob_token_ids and hidden reasoning.

No model evals were run. The generated tokens don't change, only how the output is shaped and the parity tests check that shape against coupled chat.

### Benchmarks (TTFT/TPOT, inline derender vs tokens stream + `/derender` per chunk, plus mixed traffic on one pod)

@shimib benchmarked this on one A100-40G with Qwen3-8B https://github.com/vllm-project/vllm/pull/63103#issuecomment-6407286233 and Qwen3-VL-8B https://github.com/vllm-project/vllm/pull/63103#issuecomment-6446448022. The runs compare tokens only (G), tokens plus a per-chunk `/derender` call (B) and inline `output_mode: "derender"` (D). There were over 16,000 requests, zero errors and output tokens matched within 2%.

The RFC (#56851) set out to get rid of the per-chunk `/derender` hop for interactive P/D traffic and this PR does that. D's TTFT is 85–150 ms faster than B's at p50 and only 14–35 ms behind the token floor. That holds for text, tool calls, reasoning and images. D also streams token by token with ITL close to G, while B only keeps its TPOT by batching tokens which means clients get text in bursts. TPOT matches G within 0.5 ms and mixed G/D traffic on one worker doesn't hurt either side.

The weak spot is heavy reasoning load (~1.9k tok/s through the Qwen3 parser). There D's TPOT p95 rises 6 ms and colocated tokens only requests lose about 10–23 ms of TTFT because parsing runs on the API server event loop. `--api-server-count` should help but wasn't tested. E2E latency wasn't measured either.

## Details

- Parsing runs on the API server event loop, the same as coupled chat. An executor hop per chunk would add TPOT and with the default `renderer_num_workers=1`, every derender stream would queue on one thread. `--api-server-count` scales the parsing.
- Text comes from the engine's own incremental detokenizer, so stop strings and the decode flags `/render` set behave exactly as they do in coupled chat.
- `parse_context.history_tool_call_cnt` seeds each parser. Without it, deterministic tool call IDs (Kimi style) would restart at 0.
- When `include_reasoning` is false, `token_ids`, `logprobs` and `sampling_mask` are dropped on every chunk, the same as batch derender.
- The batch and stream generators now pick their logprob settings from one shared helper.

**Two choices I'd like feedback on:**

1. Where `role` goes. `role` is on the first chunk of each choice, the same as streaming `/derender`. There's no role only preamble chunk like coupled chat sends because that would add a chunk before the first token and skew TTFT comparisons.
2. Chunks where the parser emits nothing. Coupled chat drops these unless `return_token_ids` is set. Generate always returns token IDs, so these chunks are still sent while their IDs are visible. P/D clients need every token ID. With hidden reasoning the IDs are hidden, so the chunk is dropped, as in coupled chat.

Out of scope: the Rust frontend, `reasoning_tokens` in generate usage, Cohere citations (#63164), and per-request `return_tokens_as_token_ids` (#63162).

### Setup & Methodology
- **Scenarios** (same harness as §12 on #58588):
  - **S1**: plain text, "Summarize:" over a 400–1500 word prompt, 128–512 max_tokens
  - **S2**: tool call, `get_weather`, Hermes parser, `tool_choice: auto`, 64–256 max_tokens
  - **S3**: long reasoning, Qwen3 reasoning parser, 2k–8k max_tokens
- **Environment**: one A100-40G worker, `Qwen/Qwen3-8B`, `--enable-auto-tool-choice --tool-call-parser hermes --reasoning-parser qwen3 --max-model-len 16384 --enable-scale-out`, tokenizer loaded. The same worker serves every config; only the request's `output_mode` differs.
- **Build**: `vllm/vllm-openai:nightly-8e2beaa3bf` with #63103 and #63148 overlaid (`shimib/vllm@bd27d161f4`).
- **Render tier**: dedicated CPU pod on the same image + overlay.
- **Load generator**: separate CPU node, Poisson arrivals, seeded greedy prompts, 300 s of arrivals per point, then drain.
- **Configurations**:
  - **G**: `/render` → generate `stream: true` (tokens floor, consumed directly).
  - **B**: **G** + client per-chunk `/derender` with `stream_state` (coalesced 8→512 tokens/call).
  - **D**: `/render` → generate `stream: true, output_mode: "derender"` (this PR).
- **Latency spans**: TTFT = first chunk whose chat `delta` carries content, reasoning or tool_calls (**D**, **B**) or the first token-ID chunk (**G**); TPOT = span from first to last chunk over output tokens.

### Takeaways

1. **TTFT:** D sits 14–35 ms above the token floor (G); B sits 100–190 ms above it. The inline path removes the per-chunk HTTP round trips to the derender tier, worth 85–150 ms at p50, consistently across text, tool calls and reasoning.
2. **TPOT:** p50 matches G within 0.5 ms everywhere except S3 at 1.0 rps (~1.9k output tok/s through the Qwen3 reasoning parser), where D is +0.9 ms at p50 and +6.1 ms at p95. That is the parser on the API server event loop showing in the tail at the heaviest point. `--api-server-count` is the lever the description names; I did not test it.
3. **ITL:** D matches G within 1–5 ms on plain text (S1) and reasoning (S3). On tool calls (S2) D's p99 is ~9 ms above G (25–26 vs 16–17), which is the tool parser's per-chunk work.
4. **Mixed traffic:** at S1 and S2, interleaved G and D each land on their isolated numbers within 2–4 ms. At S3 1.0 rps, colocated D parsing lifts G's TTFT by +10 ms (p50) and +23 ms (p95) while D itself is unchanged, the same event-loop cost as in (2).
5. **Reliability:** 0 errors across 21 runs and 12,125 requests. Output token totals per point agree across G, B and D within 2% (exact at S1 0.5 rps); the residual is up to 3 requests of Poisson arrival difference per point plus run-to-run greedy variance under batching, largest on the long reasoning outputs. Per-request TTFT/TPOT are unaffected.
