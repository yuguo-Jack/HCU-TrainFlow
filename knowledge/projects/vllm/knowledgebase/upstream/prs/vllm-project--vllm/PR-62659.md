# [Bugfix][Model] Gemma4/Gemma3n: register the PLE cache as a non-persistent buffer

[Upstream PR](https://github.com/vllm-project/vllm/pull/62659) · state: open · merged: False

## Original PR description



## Overview

Register the pre-allocated per-layer-embedding (PLE) cache `per_layer_embeddings` as a non-persistent buffer in `Gemma4ForConditionalGeneration`, `Gemma4UnifiedForConditionalGeneration` and `Gemma3nForConditionalGeneration`, so it follows the model on `.to(device)` and is materialized when the model is built on the meta device. Same class of fix as #54213 (Gemma-4 embedding scalars) and #53507 (Gemma-3n runtime scales).

## Claims

- `per_layer_embeddings` moves with the model on `model.to(device)`. Today a model built on one device and then moved fails its first forward with `Expected all tensors to be on the same device`.
- `per_layer_embeddings` is materialized when the model is built under `torch.device("meta")`, as the IPC weight-cache loader does. Today it is left on `meta`, because `_materialize_remaining_meta_tensors` only walks `_parameters` / `_buffers`.
- No change to checkpoints or weight loading: the buffer is non-persistent, so it is absent from `state_dict()` and skipped by `AutoWeightsLoader`.
- No change on the default load path: the tensor keeps the same shape, dtype, device and allocation, and the read/write sites (`embed_input_ids`, `forward`) are untouched.

## Validation

- Existing tests: `pytest tests/models/multimodal/processing/test_gemma4.py tests/models/multimodal/processing/test_gemma4_unified.py` gives 38 passed, 19 skipped.
- Meta-device build on CPU: building tiny Gemma-4 and Gemma-3n models with `initialize_model` under `torch.device("meta")` registers `per_layer_embeddings` as a buffer, keeps it out of `state_dict()`, and lets `to_empty(device="cpu")` materialize it with the expected shape. On `main` it is not a buffer and stays on `meta`. This was not run through the weight-cache daemon on a GPU.
- Out-of-tree hardware platform that builds the model on CPU and then moves it to the device: gemma-4-E2B fails during warmup with `Expected all tensors to be on the same device` without this change, and runs with it, with no plugin-side workaround.

## Details

`nn.Module._apply`, and so `.to()` / `.cpu()` / `.cuda()`, only moves registered parameters and buffers. `per_layer_embeddings` is a `[max_num_batched_tokens, num_layers, ple_dim]` tensor stored as a plain attribute, so it stays wherever the model was built. It is written in `embed_input_ids` and read in `forward` on every step, and is added to device tensors in `project_per_layer_inputs`.

The default loader builds the model under `with torch.device(load_device)` and never moves it, so the bug is invisible on the standard CUDA path. Unlike the 0-d scalars in #54213, a CPU tensor of this size is not tolerated by CUDA kernels either, so anything that builds the model on one device and moves it, or builds it on meta, hits it.

When PLE is disabled, `Gemma4ForConditionalGeneration` and `Gemma4UnifiedForConditionalGeneration` register `None` (which `register_buffer` accepts), so the attribute is still `None` there. `Gemma4UnifiedForConditionalGeneration` rebuilds its modules without calling its parent's `__init__`, and `Gemma3nForConditionalGeneration` has the same pattern, so both need the change.
