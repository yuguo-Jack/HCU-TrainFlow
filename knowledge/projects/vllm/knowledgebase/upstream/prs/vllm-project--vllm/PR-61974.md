# [Feature][KV Connector][Mooncake] Add MooncakePullConnector for decode-side reads

[Upstream PR](https://github.com/vllm-project/vllm/pull/61974) · state: open · merged: False

## Original PR description

## Overview

Adds `MooncakePullConnector`: the decoder reads KV blocks from the prefiller over the Mooncake TransferEngine, so the prefiller holds its cache and hands out block ids instead of writing into the decoder's memory. Part of #60523.

Depends on #64871, which moves the descriptor planner out of the push worker. This PR stays a draft until that lands; then the branch is rebased onto `main` and reopened for review.

## Claims

- Selectable with `--kv-connector MooncakePullConnector` on both sides, using the existing proxy and `kv_transfer_config`. Docs and the example script (`KV_CONNECTOR=MooncakePullConnector`) cover it.
- The decoder fetches a peer's regions once, caches them under the peer's random `layout_id`, and asks again when the id changes. Everything after that carries block ids only: with 146 registered regions and a batch of 8 requests × 4 blocks, a pull request is a few hundred bytes, against 7297 B for the push handshake payload of which 7164 B is the address book.
- Reads are leased on the prefiller. Blocks go from handed out to reported, or to expired when the reader stops renewing; `ReadLeases` owns that state so the worker asks one question before freeing blocks.
- Cancellation does not release the lease early. A cancelled read reports once its engine call returns, because the read keeps touching the registered memory until then.
- Push behavior is preserved. `MooncakeXferMetadata` and `MooncakeXferResponse` gain defaulted fields (`physical_blocks_per_logical`, `producer_cache_replicated`, `layout_id`, optional `metadata`), and `SendBlockMeta` gains an `aborted` event.

## Details

**Who moves the bytes.** On the prefiller the worker keeps its KV blocks and answers a pull with the blocks it resolved. On the decoder the worker plans the copy, calls `batch_transfer_sync_read`, and reports completion, which releases the prefiller's blocks. Both connectors extend `MooncakeBaseConnector`, and the pull worker extends `MooncakeConnectorWorker`, so the scheduler, request metadata, registered regions and the side-channel loop exist once.

**Wire format.** The decoder sends `MooncakePullRequest` (which transfers it needs bytes for, and whether it wants the prefiller's regions); the prefiller answers with a `MooncakeXferResponse`, the envelope the push connector already sends, with the regions in its optional `metadata` plus the `layout_id`. `MooncakePullReading` renews a lease while the read runs, and `MooncakePullDone` reports the outcome, which is the release signal.

**Read planning.** The pull worker calls `plan_block_descriptors` with the sides swapped: remote blocks are the source, local blocks the destination. Group checks, Mamba placeholder handling, logical-to-kernel expansion, contiguous-run coalescing and the TP ratio come from the same code the push direction uses, and `MooncakeXferMetadata` carries the two fields a self-planning reader needs.

**Failure handling.** A sender worker can wait a whole abort timeout for the prefiller's blocks, so the side-channel listener answers lease traffic itself: a renewal, a reading report or a done report never queues behind a pull request, and a lease cannot lapse while its blocks are still being read. Only pull requests reach a worker. A pull for a transfer the prefiller has already expired is answered with an error on the first response; it does not wait for the ready timeout.

**Not in this PR.** The planner is #64871 and lands first. Moving connector metadata and wire structs into their own modules is #62255. Multi-segment TP slicing is #64812.

**Why this is not a duplicate.** No other open PR adds a read direction to the Mooncake connector. #64871 is the planner split out of this work, #62255 moves structs, and #64812 changes TP slicing.
