# [Feature][KV Connector][Mooncake] Add MooncakePullConnector for decode-side reads

[Upstream PR](https://github.com/vllm-project/vllm/pull/61974) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Adds `MooncakePullConnector`, a READ-mode sibling of `MooncakeConnector`: the decoder reads the prefiller's KV cache over the Mooncake TransferEngine instead of the prefiller writing into the decoder's registered memory. It is registered under its own name, and `MooncakeConnector` keeps its wire format, metadata and behavior.

Part of the Mooncake connector roadmap in [#60523](https://github.com/vllm-project/vllm/issues/60523).

## Claims

- **New connector with decoder-side reads.** The prefiller holds its KV blocks, publishes its address book and block ids, and releases a request once every reader reports the read finished; the decoder issues `batch_transfer_sync_read` at its own scheduling pace. Select it with `--kv-connector MooncakePullConnector` on both sides, using the existing proxy and `kv_transfer_config` fields; `KV_CONNECTOR=MooncakePullConnector` picks it in the example script.
- **KV layout on the handshake, not on every batch.** The decoder fetches each peer worker's layout once and caches it, keyed by a `layout_id` so a restarted peer is noticed and re-fetched. Per-request messages carry block ids only: with 146 registered regions and a batch of 8 requests × 4 blocks, the pull request payload is 309 B against 7297 B for the push handshake payload, of which 7164 B is the address book.
- **Compatibility-hash isolation.** Both sides hash model, dtype, KV heads/head size/layers, KV cache dtype, attention backend, HMA, EAGLE/MTP configuration, connector version and transfer mode, and compare the digests during the handshake. TP size, block size and KV cache layout stay out of the hash and are validated against the peer's address book instead, which keeps heterogeneous TP working. A mismatched pair fails the request with a message naming the reason.
- **Pull connector reuses the existing machinery.** `MooncakePullConnector` subclasses `MooncakeConnector` and swaps only the worker, mirroring `NixlPullConnector` and `NixlPushConnector`; scheduler, request metadata and registered regions are shared, and reads are planned in `mooncake/transfer_plan.py` from the same region helpers the push path uses.
- **Push behavior preserved.** `MooncakeXferMetadata`, `MooncakeXferResponse` and the send path are unchanged; the push connector gains only the seams both modes share (`_handle_side_channel_message`, `_send_side_channel_error`, `_send_idle`), the connector name in its bootstrap registration, and an aborted-transfer event its own path ignores.

`tests/v1/kv_connector/unit/test_mooncake_pull_connector.py` runs two workers against each other over the real ZMQ side channel and bootstrap server, with the transfer engine replaced by a byte-copying stand-in that keeps the memory-registration table, so a descriptor pointing outside registered memory fails the test. It covers byte-for-byte reads, the address book fetched once per peer and re-fetched after a peer restart, heterogeneous TP (one decoder rank reading two prefiller ranks), release on a decoder-side prefix hit, rejection of an incompatible peer (compatibility hash, block size, connector mode), reader failure and abort releasing the prefiller's blocks, and prefiller timeout failing the reader.

Serving validation on an 8×H20 node, same-host P/D pair over RDMA (both sides log `The Mooncake Transfer Engine is using rdma as its protocol`), driven through the example proxy with three greedy prompts per configuration and every completion compared character by character:

| Configuration | pull vs. non-disaggregated | push vs. non-disaggregated | pull vs. push |
| --- | --- | --- | --- |
| dense 0.5B, P tp=1 / D tp=1 | identical | identical | identical |
| hybrid 2B, P tp=1 / D tp=1 | identical | identical | identical |
| dense 0.5B, P tp=2 / D tp=1 | identical | n/a | n/a |

The worker logs show which side moves the bytes:

```text
# decoder, pull mode
DEBUG mooncake_pull_connector.py] Reading kv_caches for {'cmpl-...'} from producer worker tcp://172.31.32.3:45359
DEBUG mooncake_pull_connector.py] Reading from 172.31.32.3:15558 done, took 0.00605 (24 descriptors, 1769472 bytes)

# prefiller, push mode (same instrumentation, same run shape)

```

The three dense prompts read 24 descriptors each: 1.69 MiB in 6.0 ms, 1.69 MiB in 0.35 ms (prefix-cached), and 576 KiB in 0.68 ms. The hybrid prompts read 24 descriptors and 27 MiB each, in 7.1 ms, 1.1 ms and 1.0 ms. The prefiller log in pull mode contains no transfer line at all, while in push mode it logs one write per prompt, and neither worker logs an error.

## Details

**Protocol.** The decoder sends `MooncakePullRequest` (protocol marker, compatibility hash, reader identity, `{request id: (transfer id, needs bytes)}`, and whether it wants the layout); the prefiller answers with `MooncakePullResponse` (layout and/or producer block ids per request, or an error); the decoder reads the blocks, then reports `MooncakePullDone` and waits for `MooncakePullAck`. The prefiller holds blocks from the moment it hands out block ids until every expected reader reports in. The expected reader count comes from the same `TransferTopology` rules the push connector uses for its TP/PP fan-out, and a request that no reader takes is released after `VLLM_MOONCAKE_ABORT_REQUEST_TIMEOUT`.

**Read planning.** `plan_read_block_descriptors` turns one request's producer and consumer block ids into remote and local descriptors using the registered regions, the KV group identity, the Mamba/GDN placeholder rule, per-side logical-to-kernel block expansion and contiguous-run coalescing; it is the read-side counterpart of the push worker's descriptor loop, and region alignment and asymmetric-TP validation reuse the existing helpers.

**Who validates what.** Handing out block ids lets a reader slice the prefiller's cache by KV head, so the head-resharding check (padded pages, NVFP4) runs on the prefiller, which is the only side holding the registered layer specs, using the TP degree the reader reports. The decoder keeps the checks it can make from the address book alone: block size, physical blocks per logical block, MLA/Mamba flags, layout id, and the region-length relations of asymmetric TP.

**Failure handling.** Read and planning failures go through the connector's existing failure path (`_handle_failed_recv`, `get_block_ids_with_load_errors`), so the scheduler recomputes or fails the request according to `kv_load_failure_policy` and the prefiller releases the blocks of a failed read. The decoder reports a batch it abandons (rejected layout, compatibility mismatch, error response) the same way it reports a finished one, because the prefiller handed out those block ids before the decoder could validate the response. A prefiller that drops a request (abort or its own expiry) sets the new `aborted` event so a waiting reader fails immediately instead of waiting out its own timeout, and a reader that disappears after taking block ids stops holding them once `VLLM_MOONCAKE_ABORT_REQUEST_TIMEOUT` passes.

**Mixed pairs.** A decoder running the pull connector that finds a prefiller registered as `MooncakeConnector` (or as nothing at all, since an unset name means a prefiller predating connector names) fails the request at discovery with a message naming both connectors. The bootstrap server refuses to register two different connector names under one `dp_rank`.

**Not included, tracked elsewhere in [#60523](https://github.com/vllm-project/vllm/issues/60523):** layerwise transfer overlap (Phase 4), DCP/PCP and the wider heterogeneous-TP work (Phase 3), and de-HTTP-izing bootstrap (Phase 2 evaluation item). `kv_both` inherits the push scheduler's existing role semantics and is not exercised by tests.

**Why this is not a duplicate:** no open or merged PR adds a pull connector for the Mooncake P2P path (checked by name and by search); the closest open work fixes failure reporting on the existing push connector, which this connector already routes through. Sending the KV layout once per peer for the push handshake already landed on `main`; this change applies the same idea in the read direction.

**Validation limits.** The Mooncake transfer engine is not available in CI, so the unit tests use the byte-copying stand-in described above and GPU/RDMA validation happens outside CI. The serving runs above used a same-host P/D pair; a cross-host pair was not validated for this PR.
