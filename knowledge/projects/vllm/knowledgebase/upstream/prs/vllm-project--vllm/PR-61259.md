# [Bugfix][XPU] Make Triton int8 scaled_mm an opaque custom op

[Upstream PR](https://github.com/vllm-project/vllm/pull/61259) · state: closed · merged: False

## Original PR description



## Overview

Fix default `vllm serve` failing on XPU for every INT8 W8A8 (compressed-tensors) model by making the Triton int8 `scaled_mm` launch an opaque custom op. Follow-up to #47205.

## Claims

- Out of the box on XPU, INT8 W8A8 models die in `profile_run` with `AssertionError: cannot extract sympy expressions from TreeSpec(...)`; with this change the same command starts and serves.
- No change in numerics: the op calls the same `triton_scaled_mm`, tensor-descriptor path stays enabled by default.
- Adds tests that run the op and `TritonInt8ScaledMMLinearKernel.apply_weights` under `torch.compile(fullgraph=True)` and check the compiled graph contains `triton_scaled_mm_func`; the existing tests only call the kernel eagerly.

## Validation

Intel Arc Pro B60 (1 card), `vllm/vllm-openai-xpu:nightly` (image id `sha256:db2106e33c29`, vLLM 0.31.1rc1.dev23, torch 2.14.0+xpu, triton 3.8.0). The Python tree under test was copied over the image's `vllm/` (C++ ops from the image). Model `RedHatAI/Meta-Llama-3.1-8B-Instruct-quantized.w8a8` @ `024e24cbe4`.

```bash
vllm serve RedHatAI/Meta-Llama-3.1-8B-Instruct-quantized.w8a8 --revision 024e24cbe4 \
  --max-model-len 4096 --kv-cache-memory-bytes 4G
```

| Tree | `triton_scaled_mm_func` registered | Result |
|---|---|---|
| `main` @ e0317b28ce | no | crash in `split_graph`: `cannot extract sympy expressions from TreeSpec(...)` |
| `main` @ e0317b28ce + this PR | yes | server starts, `/v1/completions` returns text, no `TreeSpec` |

Same command, with this PR, for `RedHatAI/Qwen2.5-7B-Instruct-quantized.w8a8` @ `dae5e0d2d3` and `RedHatAI/gemma-3-4b-it-quantized.w8a8` @ `a63cba2aec`: both start, serve a completion, no `TreeSpec`.

Cost of the wrapper itself, `main` vs this PR, Llama-3.1-8B w8a8 (`vllm bench sweep serve`, random 512 in / 128 out, 100 prompts, concurrency 32, 3 runs after warmup, seed 42, same image and card):

| Mode | `main` (inline launch) | this PR |
|---|---|---|
| `torch.compile`, `VLLM_TRITON_USE_TD=0` (the only compile mode where `main` starts) | 16.4 tok/s | 26.3 tok/s |
| `--enforce-eager`, `VLLM_TRITON_USE_TD=1` | 125.7 tok/s | 126.0 tok/s |

All requests completed in every run. In eager the difference is within noise; under compile this PR is faster, but I did not investigate why. `lm_eval` gsm8k (5-shot, first 500 samples, greedy, compile, TD=0) gives identical results on `main` and with this PR (flexible-extract 0.806 ± 0.018; 0 of 1000 generations differ).

With this PR and TD on under compile (the default on XPU) throughput is 129.1 tok/s vs 27.5 with `VLLM_TRITON_USE_TD=0` (200 prompts, 3 runs), which is the point of keeping TD enabled; gsm8k is identical for both settings as the TD path is bit-exact.

Tests (same hardware): `pytest tests/kernels/quantization/test_triton_scaled_mm.py -k "td_matches_plain or custom_op or fake_impl or apply_weights"` → 44 passed, including the new `test_scaled_mm_custom_op_under_compile`, `test_scaled_mm_fake_impl_meta` and `test_int8_kernel_apply_weights_opaque_under_compile`. The `apply_weights` test fails (8/8) on `main` without this change. Dynamic-quant cases use a small tolerance because compiled `scaled_int8_quant` keeps the per-token scale in fp32 while eager rounds it to the activation dtype (independent of this PR); static cases are bit-exact.

Workaround before this change: `VLLM_TRITON_USE_TD=0` or `--enforce-eager`.

## Details

On XPU the int8 linear kernel list is Triton-only and `VLLM_TRITON_USE_TD` is auto-on, so there is no fallback. `TritonInt8ScaledMMLinearKernel.apply_weights` called `triton_scaled_mm` directly, so Dynamo traced the launch inline. With TD on, the traced graph also contains the allocator setup (`set_alloc_*` attributes and an `invoke_leaf_function` node carrying an input `TreeSpec`), and `split_module` in vLLM's `split_graph` then hits that `TreeSpec`, which it cannot handle. Registering the launch as `torch.ops.vllm.triton_scaled_mm_func` (with a fake impl) keeps it opaque, as already done for `w8a8_triton_block_scaled_mm_func` next to it.

Limitations:
- Compile with TD on cannot be compared against `main` (it does not start); the wrapper cost above is measured in compile with TD off and in eager with TD on. One model, one card, random dataset rather than a sharegpt sweep.
- Source of the `TreeSpec`, isolated with a standalone script: compiling the inline `triton_scaled_mm` and calling `torch.fx.passes.split_module` fails with the same assertion when TD is on, and succeeds with `use_td=False`; the only extra graph nodes with TD on are the allocator setup ones above, so the launch arguments themselves are not the cause. The crash is not specific to torch 2.14: it reproduces on the v0.28.0 XPU image (torch 2.13, triton 3.7.2).
- Other callers of `triton_scaled_mm` (`TritonFP8ScaledMMLinearKernel`, the `cutlass_scaled_mm` fallback in `_custom_ops.py`) are unchanged; TD is not auto-on for them.
- Accuracy was only run on Llama. The new tests need a CUDA-alike or XPU device, so CI coverage depends on the XPU/GPU runners (the fake-impl test runs on any device).
- `pre-commit` (incl. mypy and the Buildkite test-tethering check) passes on both commits.
