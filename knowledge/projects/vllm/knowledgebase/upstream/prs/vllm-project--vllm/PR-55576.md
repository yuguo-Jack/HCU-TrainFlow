# [Bugfix][KV Offload] Enable NIXL telemetry for the OBJ tier

[Upstream PR](https://github.com/vllm-project/vllm/pull/55576) · state: closed · merged: True

## Original PR description

## Purpose

The OBJ secondary tier reads NIXL transfer telemetry for every successful store or load, but creates its agent with telemetry capture disabled by default. Without `NIXL_TELEMETRY_ENABLE`, a completed transfer raises `nixlNoTelemetryError` before releasing its handles or reporting the job result.

Enable telemetry capture when constructing the OBJ agent. Make the existing mock respect the disabled default, and extend the store/load roundtrip test to check transfer timing and completion bookkeeping.

Duplicate-work checks on 2026-09-06 found no open PR implementing this fix. Searches covered OBJ telemetry, objectstore, `capture_telemetry`, and `nixlNoTelemetryError`. The open backpressure PR #50045 touches OBJ constructor plumbing but does not enable telemetry. The telemetry read was introduced by #48798.

AI assistance was used to investigate, implement, and test this change.

- zupengwang · comment · 2026-09-15T08:01:20Z · [source](https://github.com/vllm-project/vllm/pull/55576#issuecomment-5676825182)

Thanks @effi-ofer for raising this. I tested NIXL 1.3.2 against SSD-backed MinIO over loopback HTTP, comparing capture enabled plus telemetry retrieval against a working capture-disabled control that skips the telemetry read.

After an initial matrix showed agent-to-agent variation in off/off controls, I repeated the latency-sensitive reads with a fresh agent/connection pool for each phase, using 20 ABBA/BAAB cycles per case:

| Read transfer | Mean latency change | 95% paired bootstrap CI |
| --- | ---: | --- |
| 1 × 4 KiB | +4.29% | −0.17% to +10.13% |
| 1 × 256 KiB | +2.45% | −1.83% to +6.58% |
| 8 × 256 KiB | +1.07% | −1.17% to +3.30% |

The telemetry-query region itself added roughly 1–2.5 µs per transfer at the median; this excludes internal capture work during submission/completion. However, off/off controls also varied, and tight-polling client CPU time increased by about 6.6–7.6% for the single-block read cases. That CPU measurement includes worker activity and completion polling, so it does not isolate capture cost.

Across both runs, all 32,960 measured transfers passed the correctness checks. The local query cost is small relative to millisecond I/O, but these results do not yet establish negligible end-to-end overhead. They cover warm local MinIO transfers, not a production S3 deployment or full vLLM serving.


- davised · comment · 2026-10-23T04:19:18Z · [source](https://github.com/vllm-project/vllm/pull/55576#issuecomment-6357279590)

We hit this in production on the vLLM 0.30.0 release, and this one-line change fixes it for us.

**Setup:** `nvidia/Qwen3.8-Flash-Next-NVFP4`, TP=2 on 2x RTX PRO 6000 Blackwell Server Edition (driver 610.43.02). `nixl==1.5.0` with `nixl-cu13==1.5.0`. `OffloadingConnector` + `TieringOffloadingSpec`: a 200 GiB CPU primary tier, and an `obj` secondary tier on a Ceph RGW S3 bucket over https.

**What happened:** startup was clean, and the log showed "Object store tier connectivity probe succeeded". The first long request (about 229K tokens) stored 10 blocks in the bucket. Then the EngineCore died:

```
File ".../vllm/v1/kv_offload/tiering/manager.py", line 311, in _process_finished_jobs
    for completed_job in tier.get_finished_jobs():
File ".../vllm/v1/kv_offload/tiering/obj/manager.py", line 367, in get_finished_jobs
    self._poll_active_transfers()
File ".../vllm/v1/kv_offload/tiering/obj/manager.py", line 329, in _poll_active_transfers
    telemetry = self._agent.get_xfer_telemetry(entry.xfer_handle)
File ".../nixl_cu13/_api.py", line 705, in get_xfer_telemetry
    return self.agent.getXferTelemetry(handle._handle)
nixl_cu13._bindings.nixlNoTelemetryError: NIXL_ERR_NO_TELEMETRY
```

The request returned HTTP 500 and the server exited. The same code is still in a 0.32.0rc1 nightly (77154ca6).

**With the fix:** we applied the `manager.py` hunk of this PR (`nixl_agent_config(backends=[], capture_telemetry=True)`) to 0.30.0. We also wrote a regression test that drives the real `ObjectStoreSecondaryTierManager` through `submit_store`, `submit_load` and `get_finished_jobs` against the bucket. It fails with `NIXL_ERR_NO_TELEMETRY` before the change and passes after, and the loaded bytes equal the stored bytes.

In a live server with the fix, a 228,864-token session (147 objects, 6.6 GB) works end to end:

| Path | Time |
|---|---|
| cold prefill | 15.6 s |
| resume from S3, after `/reset_prefix_cache?reset_external=true` | 3.25 s and 3.21 s |
| 112K session: cold / resume from S3 | 7.45 s / 1.74 s |

There were no engine errors.

**Packaging note for other users:** the PyPI `nixl-cu13` 1.5.0 wheel ships `libplugin_OBJ.so`, but it links against `libcuobjclient.so.1`, and no PyPI wheel provides that library. conda-forge `libcuobjclient` 1.0.0.26 works. It needs the cuFile 1.16 symbols (`cuFileRDMADescStrGet`), but torch cu130 loads cuFile 1.15 first, so we had to `LD_PRELOAD` `libcufile.so.0` 1.16 and `libcuobjclient.so.1`. Without them, NIXL reports only `createBackend: unsupported backend 'OBJ'`. Run with `NIXL_LOG_LEVEL=TRACE` to see the real dlopen error.
