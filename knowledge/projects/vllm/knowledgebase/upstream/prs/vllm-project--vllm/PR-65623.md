# [Rust Frontend] Pass assistant and tool content parts to HF templates like Python

[Upstream PR](https://github.com/vllm-project/vllm/pull/65623) · state: open · merged: False

## Original PR description



## Overview

The Rust frontend's HF chat renderer now passes assistant and tool message content to chat templates in the same shapes as the Python frontend: assistant text parts stay separate parts (joined with `"\n"` under the `string` content format), and a text-only tool result reaches the template as one string.

## Claims

- Assistant content parts are no longer concatenated without a separator: `["a", "b"]` renders as `"a\nb"` under `string` and as two text parts under `openai`, as in Python.
- A tool-call-only assistant message (`content: null`) gets `[]` under `openai` instead of `[{"type": "text", "text": ""}]`, which is truthy in Jinja.
- A text-only tool result reaches the template as one `"\n"`-joined string in both content formats, as in Python (vllm-project/vllm#39899, vllm-project/vllm#40190). Tool content with a non-text part stays a list.

## Details

**Python's behavior.** Python parses assistant and tool content with the same `parse_chat_message_content_parts` as every other role, then normalizes tool content (`vllm/renderers/chat_utils/chat_message.py`):

- **Assistant, `string`:** non-empty text parts joined with `"\n"`.
- **Assistant, `openai`:** the list of text parts as sent; `[]` for a message with only `tool_calls`.
- **Tool, either format:** a text-only content list is collapsed to one `"\n"`-joined string, because most templates only handle string tool content, and clients such as Claude Code and Cursor send tool results as text parts (vllm-project/vllm#39899). A list with a non-text item stays a list (vllm-project/vllm#40190).

Shapes from Python's `parse_chat_messages` on current `main`:

| Message | `string` | `openai` |
|---|---|---|
| assistant `["a", "", "b"]` | `"a\nb"` | `[{text: "a"}, {text: ""}, {text: "b"}]` |
| assistant, `content: null` + `tool_calls` | `""` | `[]` |
| tool `["x", "", "y"]` | `"x\ny"` | `"x\n\ny"` |
| tool `"x"` | `"x"` | `"x"` |

**Root cause in Rust.** The HF renderer built assistant content from `AssistantContentBlock::text()`, which concatenates the text blocks (one per request part) with no separator, and then lowered that single string. So `openai` templates got one text part (an empty one for tool-call-only messages). Tool content went through the generic path, so text parts stayed a list under `openai`.

**Change** (`rust/src/chat/src/renderer/hf/mod.rs`):

- `to_template_message` maps each assistant `Text` block to one text content part and lowers them through `to_template_content`, the path every other role already uses.
- New `to_template_tool_content` renders a text-only tool result as one string in both formats and leaves other tool content as before.

**Ownership and layering.** The consumer is the HF renderer, which builds the template's `messages`, so the fix stays in its message conversion. The shared `AssistantContentBlock::text()` is unchanged: output aggregation and the Harmony and GLM-5 Next renderers rely on plain concatenation. The dedicated renderers (DeepSeek V3.2, Inkling, Kimi K3) own their encodings and are out of scope.

**Other producers of assistant text blocks.**

- Chat completions makes one `Text` block per request content part, so the blocks are the parts.
- The Responses API conversion (vllm-project/vllm#63902) flattens each assistant input item to one text block per turn, so its rendering does not change.
- `/v1/messages` is not served by the Rust frontend.

**Why Python's behavior is the right target.** The assistant `"\n"` join is the general parts semantics Python applies to every role; in Rust, user and system content already followed it, and the server's own `continue_final_message` helper already joins assistant parts with `"\n"` (`chat_completions/convert.rs`). The tool collapse is deliberate (vllm-project/vllm#39899, refined by vllm-project/vllm#40190). OpenAI allows text parts for both roles; the join and the tool-string normalization are vLLM's template-input contract that HF templates are written against.

**One intentional difference.** An empty text part inside a text-only tool list is dropped under `openai` too (`"x\ny"`), as Python's own `string` path does. Python keeps it under `openai` (`"x\n\ny"`) only because its `openai` collapse is a separate join.

**No duplicate.** I searched open upstream PRs for assistant/tool content parts and HF template content in the Rust frontend. The nearest is vllm-project/vllm#65293, which chooses *which* content format a template gets by probing it; this PR fixes the *shape* of assistant and tool content within a given format, in a different function. vllm-project/vllm#64471 (accepting empty message content) changes request parsing in the server crate, not the renderer.
