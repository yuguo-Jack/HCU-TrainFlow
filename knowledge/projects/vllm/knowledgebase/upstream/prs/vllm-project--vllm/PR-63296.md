# [Attention] Fold DeepseekV4 SWA validity mask and tail fill into the index kernels

[Upstream PR](https://github.com/vllm-project/vllm/pull/63296) · state: closed · merged: False

## Original PR description

# Warning: Untested AI-generated code.

## Motivation

DeepseekV4 decode builds SWA attention metadata **eagerly, once per attention group, on every step**, outside any captured CUDA graph (the captured forward reads the persistent buffers this build fills). For each group the build issued three device ops around the Triton index kernel:

1. `torch.ge(slot_mapping, 0, out=is_valid_token)` — the validity mask
2. `decode_swa_lens[num_decode_tokens:] = 0` — tail zeroing
3. `_compute_swa_indices_and_lens_kernel` — the index kernel itself

Ops 1 and 2 are pure overhead the kernel can absorb, because it already visits every token row and already reads `slot_mapping`-derived state.

## What changed

Both SWA index kernels (`_compute_swa_indices_and_lens_kernel` and the DSpark non-causal variant) now:

- compute validity in-register and **write `is_valid_token` as a side output**:

  `is_valid(t) = 1[slot_mapping[t] >= 0]`

  The buffer, its dtype, and its values are unchanged — every consumer (FlashMLA, mega-attn, flashinfer, `cache_utils`, AMD/XPU paths) reads the same tensor. The standalone `torch.ge` launches are deleted from `build()` and `update_draft_decode_metadata()`.

- take a `num_valid_tokens` boundary and are launched over all scheduled tokens for the decode call. Rows `r` with `num_valid_tokens <= r < N_total` take the existing invalid path (`lens[r] = 0`, `indices[r] = -1`), which replaces the tail fill:

  `lens[r] = 0 for r >= N_d` (old: separate `fill_` kernel; new: covered by grid extension)

  This is strictly stronger than the old fill, which zeroed only `lens` and left stale `indices` in the tail.

  The invalid path splits by output: `lens` rows zero to the end of the
  buffer (the old slice-fill's exact coverage), but the `-1` index
  row-clear stops at `num_valid_tokens`. The pre-fusion kernel never
  wrote index rows past it, and on mixed decode+chunked-prefill steps
  the far tail spans the chunk's rows, where full-width clears cost
  megabytes of dead stores per step.

## Why this matters

The cost model for the metadata phase is launch-bound at small batch:

`t_meta = Σ_{g=1..G} ( t_ge + t_fill + t_swa + 3·t_gap )`

where `G` is the number of attention groups. After this change:

`t_meta' = Σ_{g=1..G} ( t_swa + t_gap )`

so the saving per forward pass is `G·(t_ge + t_fill + 2·t_gap)`. Measured on H200 with dsv4.1 flash decode (8 attention groups): `t_ge ≈ 1.0us`, `t_fill ≈ 0.85us`, `t_gap ≈ 3us`, giving ~60us per decode step, ~16 fewer kernel launches per forward pass.

## Safety notes

- The metadata build runs eagerly every step; the widened decode grid varies with the batch and never interacts with graph replay. Buffer addresses are unchanged, so captured-graph consumers are unaffected.
- `num_valid_tokens` is in `do_not_specialize`, so the boundary does not trigger Triton recompiles.
- The prefill launch keeps its original grid; its `num_valid_tokens` never trips.
- `warmup_inputs` for both JIT-warmup wrappers carry the new `slot_mapping` / `num_valid_tokens` entries.

## Testing

- `tests/v1/attention/test_deepseek_v4_swa_visible.py` updated: passes `slot_mapping` and an output mask buffer, and asserts the kernel-written mask equals `slot_mapping >= 0`.
- Needs a GPU run of that suite plus a dsv4.1 decode smoke (the JIT warmup exercises the new kernel signature at startup); draft until that is done.
