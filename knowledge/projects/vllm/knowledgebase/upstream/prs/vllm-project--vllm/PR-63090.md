# [Model Loader] Keep side tensors on startup storage across layerwise reload

[Upstream PR](https://github.com/vllm-project/vllm/pull/63090) · state: closed · merged: False

## Original PR description

> Stacked on #57678. Only the last commit (`[Model Loader] Keep side tensors on startup storage across layerwise reload`) is new here.

## Problem

`process_weights_after_loading` often keeps tensors on objects hanging off the layer instead of registering them: `quant_method.moe_quant_config` (`_w1/_w2.scale`, `alpha_or_gscale`), `quant_method.moe_kernel.impl.fused_experts` (`g1_scale_c`, `gemm1_alpha/beta/clamp_limit`), experts objects. A layerwise reload reruns it on freshly materialized temporaries, so those objects end up holding the temporaries or freshly derived tensors. The values are copied back into the registered parameters, but CUDA graphs captured at startup keep reading the old side tensors, so decode silently uses stale scales.

Seen on Qwen3-30B-A3B NVFP4 (ModelOpt), Qwen3.5 FP8, MiniMax-M3 MXFP8 and DeepSeek-V4.1: up to 36 unregistered tensors per model change address on every reload.

## Fix

Move those tensors back onto startup storage in place with `Tensor.set_`, which every holder sees, instead of rewriting references:

- after the copy-back, each temporary is aliased onto its kernel tensor (same shape, dtype, device);
- tensors reachable from the layer's non-module attributes are collected by attribute path before the rerun; any tensor that replaced a different startup tensor at the same path is copied into it and aliased there;
- tensors that cannot be pinned (shape changed, tensor subclass, overlapping startup view) are logged with their path.

`test_reload_weights` now also checks the addresses of these side tensors.

## Test

- GB200, sliced checkpoints, cold A -> reload B -> reload B -> reload A plus a separate cold-B process, comparing state hashes, `data_ptr`s (registered and unregistered) and greedy tokens: DeepSeek-V4.1 (FP8/FP4, and FLASHINFER_TRTLLM engine), Qwen3-30B-A3B BF16 and NVFP4, Qwen3.5 FP8, Qwen3.6 BF16, MiniMax-M3 MXFP8, Kimi K3: all pass, 0 moved tensors.
- `pytest tests/model_executor/model_loader/{test_reload,test_reload_side_state,test_reload_materialize,test_reload_host_scales,test_weight_parts}.py tests/models/test_deepseek_v4_vl.py`: 109 passed.
- GB300 (SM103), same oracle: Qwen3-30B-A3B NVFP4 (incl. FULL graphs), BF16 and online MXFP8, Qwen3.5 FP8, GLM-5.3 BF16/online MXFP8/MXFP4, GLM-5.2 FP8 and NVFP4, Qwen3.8 NVFP4 and MXFP4, DeepSeek-V4.1, Kimi K3: all pass. Without #63090, DeepSeek-V4.1 moves 15 side tensors per reload there.
- H200: Qwen3-30B-A3B BF16 and NVFP4 (incl. xqa decode, eager and graphs), Qwen3.5 FP8, GLM-5.3 BF16, GLM-5.2 FP8: all pass.
