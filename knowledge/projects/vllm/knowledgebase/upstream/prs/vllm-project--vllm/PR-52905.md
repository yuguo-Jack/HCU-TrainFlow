# [Bugfix][Kernel] Promote BF16 causal-conv operands before accumulation

[Upstream PR](https://github.com/vllm-project/vllm/pull/52905) · state: open · merged: False

## Original PR description

## Purpose

Fixes #52887.

The BF16 causal-convolution Triton kernels accumulate in FP32, but their input/history values and weights were still multiplied as BF16 first. This changes those products to FP32 before accumulation, avoiding the extra BF16 rounding step.

State and output dtypes remain BF16.

- NolenLiang · comment · 2026-09-11T05:48:46Z · [source](https://github.com/vllm-project/vllm/pull/52905#issuecomment-5630092204)

Data point in favor of this change, from the training/inference-consistency side. I compared vLLM's Triton causal conv against the causal-conv1d CUDA package (1.7.0 built from source, the kernel Megatron's memory-efficient Mamba path calls) on bf16 inputs with width 4 and 700 tokens, at Nemotron-H-8B (dim 10240) and Granite-4.0-H-350M (dim 1792) shapes. On main, 35% of the bf16 outputs differ (max abs 0.031); the CUDA output is within 0.001% of a correctly rounded fp64 reference, so the BF16 product rounding is the whole gap. With the two `.to(tl.float32)` promotions from this PR applied on top of my branch, the outputs are bitwise identical to the CUDA kernel for both shapes, and the choice of exp or division implementation makes no difference at bf16 output precision (checked 24 variants). The decode-equals-prefill tests I run for batch-invariant Mamba2 still pass with the change, since both kernels move together.

Additional R9700 validation of the same fix, from #57007. That PR duplicated the two operand promotions after the initial search missed this earlier PR; I am closing it in favor of this one and contributing the additional evidence here.

Environment: AMD Radeon AI PRO R9700 (`gfx1201`), ROCm 7.14, PyTorch `2.12.0+rocm7.14`, Triton `3.7.1+gitf0b55c07`.

| Check | Result |
| --- | --- |
| Original upstream kernel at `78eaaad2c7a7f8c7864d9c9c72772e3f9f2669d0`, with the added regression | 12 BF16/FP16 failures; all six FP32 controls passed |
| Same two operand promotions, complete convolution test file from #57007 | 182 passed; no failures, errors or skips |
| Applicable pre-commit checks | Passed |

The additional parameterized regression covers the prefill and update public APIs, BF16/FP16/FP32, widths 2/3/4, a masked channel tail and exact history updates, including the reserved null slot. It checks an exactly representable cancellation residual with zero tolerance: BF16 `1.0078125 * 1.0078125 - 1.015625` should retain `2**-14`, whereas the original kernel returns zero on this stack.

The [patch and regression are available in commit `edde11d`](https://github.com/Terrydaktal/vllm/commit/edde11df8b5d524db20f01b6d479219b42cdd934); please feel free to reuse the additional coverage. The regression is selected with `pytest tests/kernels/mamba/test_causal_conv1d.py -k preserves_product_precision -q`.

For this validation, an isolated runner imported that exact kernel source and test file into the pinned vLLM 0.28 environment, with `--noconftest` and pytest plugin autoload disabled. This validates the changed source on R9700; a complete current-main installation, CUDA/XPU execution and end-to-end throughput were not tested.
