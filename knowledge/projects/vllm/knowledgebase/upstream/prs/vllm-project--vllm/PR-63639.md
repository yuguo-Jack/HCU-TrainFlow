# [ROCm][Bugfix] DeepSeek-V4.1 mono decode: wait for an index source's key table before combine reads its key count

[Upstream PR](https://github.com/vllm-project/vllm/pull/63639) · state: closed · merged: False

## Original PR description

## Purpose

On DeepSeek-V4.1 **index-source layers** (layers with their own indexer; 2, 8, 14, 20, 24, 28, 32, 36 in V4.1-Flash), the ROCm mono decode K2 builds each token's key table and key count (`KT` / `KLEN`) itself, in the same launch, because vLLM's indexer runs between K1 and K2.

- `stage_split` waits for that table (`await_flags(krdy)`) and reads it with device-scope loads.
- `stage_combine` does neither: it reads `KLEN[t]` with a plain load as its first step (`vllm/models/deepseek_v41/amd/mono/attention/back.py:521` on main).

The CTAs that run combine have no split work, so they issue that load at the start of the launch, before the table-building CTAs have stored it. They read **the count the previous layer left in the shared buffer** and merge that many key chunks. On MI355X the per-XCD L2 can also serve a stale line, so the wait alone is not enough; the load needs device scope too, exactly as in `stage_split`.

Where the stale count is smaller, keys are silently dropped (V4.1-Flash, TP4, 128-key chunks):
- **layer 2** (after the window-only layer 1), at every position from 85 on. Past 1023 tokens it merges 1 of 5 chunks: 128 of the 512 top-k compressed keys are kept, and the other 384 plus the whole 128-key window (including the token itself) are dropped.
- **layer 20** (ratio 1 after ratio 2), at most positions in 64-768. At p = 600 it merges 4 of 5 chunks and drops the whole window.

Everywhere else the stale count happens to equal the right one.

**Fix:** give `stage_combine` the same wait and device-scope load as `stage_split`. Layers whose table K1 builds are unchanged.

## Test Plan

1. **New regression test** `tests/models/test_dsv41_mono_index_source.py` (CDNA4; TP2 / TP4; M = 1 / 6 decode rows; ratio-2 and ratio-1 sources). An index source is run after a window-only layer, and with a window-only layer's counts planted in `KLEN`. Its outputs must match, bit for bit, the same layer using K1's key table. It is deterministic.
2. **Standalone reproducer** on the image's own package (no other changes): 200 trials per case on each of 4 ranks.
3. **Stock server**, InferenceX DSv4.1 MI355X recipe with `--monokernel`, TP4, `--max-num-seqs 1`, with a debug-only check that runs every K2 twice on identical inputs.
4. **Accuracy:** forced-trajectory top-20 logprobs against vLLM *without* `--monokernel` as the reference, compared to that reference's own run-to-run floor. Benchmarks: GSM8K (InferenceX CI path), RULER CWE at 32k-128k, GPQA-Diamond, HumanEval+.

## Test Result

All results on MI355X (gfx950) with the `vllm/vllm-openai-rocm:nightly-e68efc68` package, which has the identical code. "Fixed" means only `back.py` patched.

**Regression test** (`pytest --noconftest` in the image): before, 2 failed (`AssertionError: rank 0, ratio 2, 1 rows, trial 0: the index source's x differs from the layer's with K1's key table`); after, 2 passed (188 s).

**Standalone reproducer** (outputs mismatching the reference, 800 trials per cell):

| previous layer → index source | key counts (prev / own) | before | after |
|---|---|---|---|
| L1 → L2, ctx 3000 | 128 / 640 | 800/800 | 0/800 |
| L19 → L20, ctx 600 | 428 / 640 | 800/800 | 0/800 |
| L7 → L8, L13 → L14, L19 → L20 at ctx 3000, L23 → L24 ... L36 | equal | 0/800 | 0/800 |
| any source with a stale count planted | — | 800/800 | 0/800 |

M = 1 gives the same as M = 6.

**Stock server, before the fix:**
- index ratio-2 K2 calls: 3330 / 10344 mismatched (32%, which is layer 2 every time);
- index ratio-1: 1148 / 17240 (6.7%, layer 20 at short positions);
- every non-index layer kind: 0.

The after-fix counts and a TPOT A/B will follow in a comment.

**Accuracy (c1, 13 prompts at 8k-200k):** excess KL over the no-mono reference's floor, 95% CI over prompts.

| config | excess KL | top-1 agreement change |
|---|---|---|
| `--monokernel` as is (2 servers) | +0.0040 [+0.0025, +0.0056] and +0.0026 [+0.0014, +0.0040] | -0.0055 and -0.0027 |
| `--monokernel` + this fix (2 servers) | -0.0005 [-0.0014, +0.0001] and -0.0006 [-0.0013, -0.0001] | -0.0006 and -0.0002 |

The fix moves the mono decode distribution onto the non-mono reference. Benchmark scores show no measurable change either way: GSM8K, GPQA-Diamond, HumanEval+, and RULER CWE at 128k are all within noise, about ±3-4 points at 128k. At higher concurrency, stock only uses the mono decode for ≤ 48 rows, so the bug affects low-concurrency decode.

**Not run:**
- the existing `tests/models/test_dsv41_mono_numerics.py` / `test_dsv41_mono_layers.py` on main. They never exercise an index source after a smaller-count layer within tolerance (numerics has no `select`; layers compares with 3-8% tolerance), so we expect no change.
- a wait-only variant (without the device-scope load).
- gfx942, which shares `stage_combine`.
