# [ROCm][CI] Add a build.sh prebuild mode for maintainer-approved stack builds

[Upstream PR](https://github.com/vllm-project/vllm/pull/64839) · state: closed · merged: True

## Original PR description

- build.sh: new `prebuild` mode that builds only the ROCm stack, from main, with the `Dockerfile.rocm_base` and `therock_wheels.py` of a maintainer-approved PR merged in, and pushes it only to the trusted repo
- build.sh: refuses to run if the PR moved past the approved SHA or if the stack inputs don't merge cleanly into main

When a PR changes the ROCm stack, main cold-builds it after merge (about 162 minutes for the AITER bump in #63774), and PR builds started in that window rebuild the same stack in parallel. #63949 stops the parallel rebuilds. This adds the vLLM half of a maintainer-gated pre-merge build, so the image already exists when the PR lands and main reuses it when its stack key matches. Everything except the two stack inputs comes from main, this script and the bake file included, so a PR can't change how its own trusted image is built. The gating, the trusted queue and the trigger live in ci-infra (https://github.com/vllm-project/ci-infra/pull/886), and nothing calls this mode until that lands.

Tested: `bash -n`, shellcheck and pre-commit pass. ci-infra replayed the mode on CPU in shallow clones. No real trusted build has run yet.

AI assistance (Claude Code) was used to draft this change. Every line was reviewed by the submitter.

#### 1. 🟠 Should fix: Prebuild commits empty file instead of deletion, wasting the stack build: this PR falls back to empty file on git show errors
`.buildkite/scripts/rocm/build.sh:79-84`

In `prebuild`, `git show <rev>:$f > file 2>/dev/null || : > file` treats every `git show` failure as 'path absent'. If an approved PR deletes a stack input (`tools/vllm-rocm/therock_wheels.py` or `$SDF`), `git merge-file` exits 0 and an empty file is committed instead of a deletion. `git ls-tree` then puts an empty blob into `Ks` where a real merge has no entry, so post-merge main never reuses the prebuilt stack and the long prebuild is wasted. A failing lazy object fetch on the PR side is also swallowed silently. Checking with `git cat-file -e <rev>:$f` first would separate 'absent' from 'error'.

**Who is affected:** ci-infra maintainers running `build.sh rocm prebuild` for a PR that deletes a stack input, or on an agent where a lazy object fetch fails.

_Checked against the code by an independent pass._

**Related past reviews:** [#56351](https://github.com/vllm-project/vllm/pull/56351) on `.buildkite/scripts/rocm/refresh-base-image.sh`

#### 2. 🟠 Should fix: Prebuilt stack image uses checkout's bake/build.sh, not fetched main, yet main reuses it: HEAD is never verified to be main
`.buildkite/scripts/rocm/build.sh:69-89`

The comment at line 69 says everything but the two stack inputs stays main's, "this script and the bake file included", but this is not enforced. The prebuild commit is made on top of the agent's checked-out `HEAD`, which then becomes `BUILDKITE_COMMIT`, so the line-119 HEAD check passes trivially. `build.sh` and `docker/docker-bake-rocm.hcl` (layer format, cache refs) therefore come from the checkout, not from `refs/rocm-prebuild/main`. The stack Dockerfile only copies `therock_wheels.py` from the context, and `Ks` hashes only the merged files, so the gap matters only if the checkout's bake file or `build.sh` differ from main's. Either state that ci-infra must check out main's tip, or check `[[ $(git rev-parse HEAD) == $(git rev-parse refs/rocm-prebuild/main) ]]`.

**Who is affected:** Trusted-queue prebuild runs that ci-infra starts on a commit other than main's tip, or that race a main update touching the bake file or `build.sh`.

_Checked against the code by an independent pass._

#### 3. 🟠 Should fix: Prebuild silently disables the build-context HEAD guard: this PR overwrites BUILDKITE_COMMIT with the synthetic commit
`.buildkite/scripts/rocm/build.sh:89`

In `prebuild` mode, `BUILDKITE_COMMIT=$(git rev-parse HEAD)` makes the 'HEAD is not BUILDKITE_COMMIT' guard at line 119 pass by construction. This is needed, since HEAD is now the synthetic pre-build commit and the guard would otherwise always fail. The cost is that the original check (the agent's checkout is the triggered commit) never runs before the synthetic commit is stacked on top of it. Running the guard before the prebuild block, or adding a why-comment, would keep the check and document the override. The reassigned exported value reaches no consumer in this mode: only `ensure base` runs, and `BUILDKITE_COMMIT` is read only by the `kernel-symbol-map` bake target and ci mode's `TAG`.

**Who is affected:** Only ci-infra prebuild runs on the trusted queue (`build.sh rocm prebuild`).

_Checked against the code by an independent pass._

#### 4. 🟠 Should fix: Failing prebuild job leaves conflict markers and .base/.pr leftovers in its checkout: inputs removed only on success
`.buildkite/scripts/rocm/build.sh:79-85`

When `git merge-file` conflicts, the new `prebuild` block exits before `rm "$f.base" "$f.pr"`. The same happens when `git show refs/rocm-prebuild/main:$f` fails. Either way the checkout keeps untracked `.base`/`.pr` files, a conflict-marked input and the `refs/rocm-prebuild/*` refs. The Buildkite agent's default checkout (`git clean -ffxdq` plus forced checkout) removes the files and the local commit before the next job, and the refs are force-fetched on every run, so later jobs are not affected in practice. A `git merge-file` internal error (status >127) is reported as 'does not merge cleanly', but the job still fails. A `mktemp` dir with a trap, or `git merge-tree --write-tree`, would be tidier.

**Who is affected:** Only the ci-infra prebuild step on the trusted queue, when the approved PR's stack inputs conflict with main.

_Checked against the code by an independent pass._

#### 5. 🟠 Should fix: Prebuild exits claiming the PR moved past the approved SHA when given an abbreviated/uppercase SHA: input not normalized
`.buildkite/scripts/rocm/build.sh:72`

`ROCM_PREBUILD_SHA` is compared as a string with the full lowercase `git rev-parse refs/rocm-prebuild/pr` output. An abbreviated or uppercase SHA is rejected with the misleading message '#N moved past the approved SHA' even when the PR head has not moved. The unvalidated `ROCM_PREBUILD_PR` cannot make the job build unapproved code: the refspec is one quoted argument, and whatever it fetches must equal the approved full SHA or the script exits. Normalising with `git rev-parse "$ROCM_PREBUILD_SHA^{commit}"` or checking `^[0-9a-f]{40}$` / `^[0-9]+$` up front would give clearer errors.

**Who is affected:** A maintainer or ci-infra caller who starts a `prebuild` run with a short or uppercase approved SHA, or a non-numeric PR number.
