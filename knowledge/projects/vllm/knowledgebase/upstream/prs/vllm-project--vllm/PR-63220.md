# [Perf][Kernel] Reduce CUDA MEAN pooling overhead for short sequences

[Upstream PR](https://github.com/vllm-project/vllm/pull/63220) · state: open · merged: False

## Original PR description

## Overview

Reduce CUDA MEAN-pooling overhead for sequences up to 512 tokens with a registered Triton reduction that reads the existing sequence boundaries directly.

## Claims

- Avoid segment-ID construction and FP32 accumulation chunks. For FP16 inputs at batch 64, length 512, width 384, the full pooling call drops from 966.61 us to 60.94 us, and peak extra allocation drops from 16.34 MiB to 96 KiB.
- On L4 with e5-small at 512 tokens, end-to-end embedding throughput improves by 0.85–1.52% across three paired runs; median paired improvement is 1.34%.

## Validation

NVIDIA L4; vLLM base `4643f41853146eb65d03e94538a09643e33710ad`; PyTorch 2.14.0+cu130; Triton 3.8.0. Model: `intfloat/e5-small`, revision `e272f3049e853b47cb5ca3952268c6662abda68f`, FP16.

Each process embeds 8,192 seeded, pretokenized inputs of 512 tokens through `LLM.embed`, including output conversion. Prefix caching is disabled; limits are 128 sequences and 32,768 batched tokens. Two warmup calls precede five timed calls. Baseline/patch process order is AB/BA/AB on one allocated host.

| Pair | Baseline embeddings/s | Patch embeddings/s | Change |
| --- | ---: | ---: | ---: |
| 1 | 900.10 | 907.73 | +0.85% |
| 2 | 892.70 | 904.70 | +1.34% |
| 3 | 892.90 | 906.43 | +1.52% |

Values are process medians. These are three fresh-process pairs on one host; clocks were not locked. The pooling microbenchmark includes the CPU length check and uses 30 warmups, then five trials of 100 calls with synchronization after each trial.

The added tests cover ragged and strided FP16/BF16/FP32 inputs against FP64 references, full `torch.library.opcheck`, and dispatch at 512/513 tokens. They run in the existing Model Executor CI suite.

The e5-small STS12 score was 0.7422948028 versus reference 0.7422994752, an absolute difference of 4.67e-6. That evaluation used the identical registered kernel before adding the length guard. A final 64-text model comparison produced finite outputs, maximum absolute difference 8.64e-5 and minimum cosine similarity 0.9999998463. The affected server configuration also passed with `VLLM_GPU_SYNC_CHECK=error`.

## Details

The current path builds token-level segment IDs, casts chunks to FP32 and accumulates with `index_add_`. The new kernel reduces each sequence independently with FP32 accumulation and output. It supports strided hidden states and has a fake implementation for tracing.

The 512-token limit bounds the serial token loop to 16 iterations. Longer-sequence microbenchmarks exposed regressions with too little parallel work, so longer inputs retain the existing implementation. CPU, ROCm and `VLLM_BATCH_INVARIANT=1` also retain the existing path. Summation order changes, so low-bit output differences are expected.

I checked open PRs for MEAN pooling and segmented reductions. [#60035](https://github.com/vllm-project/vllm/pull/60035) fixes batch-invariant pooling; this patch targets default CUDA performance and leaves that mode alone. No matching default-path implementation was found.

This is a small end-to-end gain on one workload. H100 exploration did not establish a throughput improvement. Full MTEB, Extended Pooling CI and physical ROCm validation have not run.

I initiated and directed this contribution and thoroughly reviewed the AI-generated code. Codex assisted with identifying the pooling inefficiency, implementation, profiling and validation. I reviewed every changed line and ran the relevant tests myself.
