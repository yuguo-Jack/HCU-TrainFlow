# [Perf][Attention] Split FA3 mixed batches into decode and prefill calls

[Upstream PR](https://github.com/vllm-project/vllm/pull/64205) · state: open · merged: False

## Original PR description

## Overview

Split eligible FA3 mixed batches into single-token decode and prefill calls, so prefill query length does not suppress split-KV for long decodes. Fixes #64058.

## Claims

- On Qwen3-30B-A3B TP4 long+short serving, short-request median TTFT falls from 7.99–11.08 s to 103–106 ms and median TPOT from 131–135 ms to about 17.4 ms.
- In the original short-only ABBA, mean-of-launch median TPOT regresses by about 9%. Both arms used MRV2, whose request-sorting code is unchanged. The design keeps two calls without a decode-length threshold and documents short-shape regressions.
- The targeted backend regression fails in all four baseline parameterizations and passes all four with the fix. Model evaluation and synchronization results are below.

### Kernel benchmark and backend test

The included `benchmarks/kernels/benchmark_fa3_mixed_batch_split.py` compares one automatic-split attention call, two decode/prefill attention calls, and one forced-32-splits call using random Q/K/V. Initial benchmark invocations completed all 16 cases and checked one-call versus two-call outputs with `atol=rtol=2e-2`. Forced-32 was timed, not separately numerically asserted.

The reviewer follow-up reuses its exact 16 cases and `Batch` implementation across eight per-device Q:KV head configurations: 8:1, 8:2, 8:4, 8:8, 16:2, 32:4, 32:8, and 32:32. Each configuration has three fresh-process repetitions; all 384 One/Two output checks passed. These are single-GPU head configurations, not eight distributed model runs.

All follow-up durations are CUDA-graph GPU spans on H20/78 SM, BF16, D=128, page=16, `num_splits=0`, with CUPTI cold L2 and a 100-ms repeat window. Per process, each arm is measured twice and its two sample medians are averaged; the table averages three process results. The original measurement rotates a mirrored One/Two/Gated order; only One/Two results are shown here. Scheduler metadata is prepared outside timing. These values exclude CPU gating, metadata construction, and engine scheduling, and use earliest-kernel-start to latest-kernel-end spans rather than summed kernel durations.

Two is faster in 105/128 configurations, including 84 with at least a 5% reduction; it is at least 5% slower in eight. Counts weight each measured configuration equally, not by serving traffic. Original 8K-query cases are not truncated when their total query tokens exceed the serving budget of 8192.

<summary>Standalone graph-only reproduction of the full One/Two matrix</summary>

Use the installed fixed checkout (`FIX` below), stop serving first, and run on an otherwise idle GPU. This wrapper imports only the public `Batch` and `CASES` included in this PR. It reproduces the One/Two comparisons with paired mirrored order, rather than the original three-arm order; it does not require the experimental gate or research-repository helpers. Each stage runs in three fresh processes. The wrapper was syntax-checked during document preparation, not executed as a new GPU experiment.

```bash
(
  set -euo pipefail
  FIX=/absolute/path/to/fixed-vllm  # Installed a042b3ddaaf570453721a5765d206469b96f2817
  cd "$FIX"
  OUT=$(mktemp -d)
  export CUDA_VISIBLE_DEVICES=0 PYTHONPATH="$PWD" VLLM_PLUGINS=""
  export PYTHONDONTWRITEBYTECODE=1
  for STAGE in primary extended; do
    for REP in 0 1 2; do
      STAGE="$STAGE" REP="$REP" .venv/bin/python - > "$OUT/$STAGE-$REP.csv" <<'ONE_TWO_PY'
import importlib.util
import os
import statistics
from pathlib import Path
from types import SimpleNamespace

import torch
from flashinfer.testing import bench_gpu_time_with_cupti

path = Path("benchmarks/kernels/benchmark_fa3_mixed_batch_split.py")
spec = importlib.util.spec_from_file_location("mixed_benchmark", path)
benchmark = importlib.util.module_from_spec(spec)
spec.loader.exec_module(benchmark)
heads = [(8, 1), (32, 4), (8, 2), (8, 4), (8, 8), (16, 2), (32, 8), (32, 32)]
rep = int(os.environ["REP"])
selected_heads = heads[:2] if os.environ["STAGE"] == "primary" else heads[2:]
order = ["one", "split", "split", "one"]
if rep == 1:
    order = ["split", "one", "one", "split"]
print("rep,q_heads,kv_heads,case,one_us,two_us")
for hq, hkv in selected_heads:
    args = SimpleNamespace(num_q_heads=hq, num_kv_heads=hkv,
                           head_size=128, block_size=16, dtype=torch.bfloat16)
    for i, (_, decode_lens, prefills) in enumerate(benchmark.CASES):
        torch.manual_seed(rep * 10000 + heads.index((hq, hkv)) * 16 + i)
        batch = benchmark.Batch(args, decode_lens, prefills, torch.device("cuda"))
        batch.run("one")
        reference = batch.out.clone()
        batch.run("split")
        torch.testing.assert_close(batch.out, reference, atol=0.02, rtol=0.02)
        samples = {"one": [], "split": []}
        for arm in order:
            fn = lambda arm=arm: batch.run(arm)
            for _ in range(10):
                fn()
            torch.accelerator.synchronize()  # Setup only, outside duration.
            measured = bench_gpu_time_with_cupti(
                fn, repeat_time_ms=100, cold_l2_cache=True, use_cuda_graph=True)
            assert len(measured) > 0 and all(t > 0 for t in measured)
            samples[arm].append(statistics.median(measured) * 1000)
        one, two = (statistics.mean(samples[a]) for a in ("one", "split"))
        print(f"{rep},{hq},{hkv},C{i:02d},{one:.6f},{two:.6f}", flush=True)
        del fn, batch, reference
        torch.accelerator.empty_cache()
ONE_TWO_PY
    done
  done
  echo "Per-process results: $OUT"
)
```

For each case/head pair, average its three `one_us` values and its three `two_us` values separately, then compute `Δ=(mean_two/mean_one−1)×100%`. Do not average rounded speedups or treat these single-GPU head configurations as distributed tests.

## Details

### Root cause and design

With `num_splits=0`, FA3 selects splits automatically. Its varlen static bound uses the batch's maximum query length and a batch=1 estimate with dynamic scheduling. A large prefill query can limit even long single-token decodes to one split; per-request scheduling cannot exceed that bound.

For FA3 with DCP=1, this change reuses `_init_reorder_batch_threshold(1)` and `split_decodes_and_prefills`. Eligible mixed batches (`max_num_splits == 0`, `max_query_len > 1`, not full-CG-eligible) receive separate query offsets and AOT scheduler metadata when enabled. Forward calls decode first (`max_seqlen_q=1`), then prefill. There is no decode-length threshold or forced-32 split policy. DCP>1, batch-invariant mode, and full-CG-eligible batches do not select this branch.

**Reordering scope:** In MRV1, setting the threshold enables decode-first batch reordering for FA3 with DCP=1 even on steps that do not select the mixed split. Enabling reordering does not imply every batch changes order. MRV2 already sorts requests through `sort_batch_req_ids`; its module is byte-identical between the tested baseline and fix. Both original short-only ABBA arms used MRV2 (`VLLM_USE_V2_MODEL_RUNNER=1`), so the reported +8.99% TPOT regression cannot be explained by newly enabling MRV1's reorder switch. Short-only profiles show the additional mixed attention calls, and graph-only short-shape regressions remain after excluding host dispatch. Ordinary single-token pure-decode batches do not enter the new mixed split.

### Why no decode-KV threshold

A higher decode-KV cutoff would discard useful short-KV cases: 128×2K decodes with a fresh 2K prefill improve by 11.67% at 8:1 heads and 22.28% at 32:4 heads. Maximum decode KV alone also does not distinguish prefill work. At 8:1 heads, 16×4K decodes improve by 23.66% with one fresh 2K prefill, but regress by 9.48% with four Q512/KV4K prefills. Absolute head counts matter too: the former shape regresses by 6.93% at 16:2 heads despite the same GQA ratio of eight.

I tested a CPU-only heuristic using existing decode lengths and query offsets, without a new GPU-to-CPU synchronization. It considered maximum decode KV, prefill query length, decode-length distribution, and approximate prefill attention work. It helped short-only in exploratory serving runs, but on the full original kernel matrix it missed 25 configurations with at least a 5% Two-call reduction and selected Two in two configurations where it was slower. 

<details>
<summary>Tested experimental CPU selection rule</summary>

For well-formed eligible mixed metadata, let `Q` be maximum prefill query length, `K` maximum decode KV length, `N` decode count, and `D` the sum of decode KV lengths. For each prefill, `q_i` is this step's query length and `s_i` its complete KV length; define `W2 = Σ q_i * (2*s_i - q_i)`. The frozen prototype used:

```text
if Q < 1024:
    if K < 8192:
        choose One
    if K < 12288 and K*N < 4*D:
        choose One
factor = 2 if Q <= 2048 else 4
choose Two if K*Q >= factor*W2, otherwise One
```

An early `choose One` terminates the decision. The prototype preserves the original split eligibility and falls back to One for unavailable or non-CPU metadata. Query offsets and sequence-length upper bounds come from existing CPU metadata; the attention kernels still use real GPU lengths. This rule allows the selection counts above to be audited against the public benchmark cases. It is not added to this PR's implementation.

</details>

This PR retains the simple no-threshold split to preserve these benefits without introducing a workload-dependent selection policy. As shown in the full original 16-case × 8-head One/Two results above, the benefits outweigh the drawbacks.

### Tradeoff and memory

Two calls can cost more for short decodes or prefill-heavy batches, as the short-only regression shows. Split-KV also adds temporary FP32 accumulation/LSE scratch: the 8:1-head 278K+2K microbenchmark reports rounded extra allocator peaks of 0 / 8 / 262 MiB for one / two / forced-32 calls. Eager scratch skipped by `profile_run` must fit runtime headroom; it is not deducted from planned KV capacity. Sampled serving memory does not establish unchanged allocator peaks across configurations.

- **Calling `_get_scheduler_metadata` twice does not alias state.** Each call returns a fresh tensor from `get_scheduler_metadata`; the persistent-buffer copy happens only in `_store_scheduler_metadata` (`flash_attn.py:670-683`), which still receives only the prefill metadata. The decode metadata bypassing the store is harmless: the store only matters for FULL-CG replay, and mixed batches never replay those graphs.
- **No new GPU→CPU sync in `build()`.** `split_decodes_and_prefills` reads `query_start_loc_cpu` (`v1/attention/backends/utils.py`).
- **The split is positionally robust.** `split_decodes_and_prefills` picks the first-prefill boundary by position, and `forward` slices `[:num_decodes]` / `[num_decodes:]` with that same boundary — so even if batch reordering were ever imperfect (a 1-token request landing after a prefill), the result stays correct; only the benefit shrinks.
- **FA4-only features cannot collide with the split.** The `mm_prefix` mask_mod, R-SWA, `dynamic_causal`, and `fa4_hd256` paths all require FA4, while the split requires `fa_version == 3`. The `functools.partial` captures `causal` / `window_size` / `s_aux` identically for both calls.
- **Batch invariance is preserved.** `VLLM_BATCH_INVARIANT` forces `max_num_splits = 1`, and the split requires `max_num_splits == 0`.
