# [Rust Frontend] Validate structured-output requests to match Python

[Upstream PR](https://github.com/vllm-project/vllm/pull/47176) · state: closed · merged: False

## Original PR description

## Summary

The Rust frontend accepted several malformed structured-output requests that the Python frontend rejects at request time. This brings the two frontends into parity so invalid requests fail fast with a `400` instead of being forwarded to engine-core as ambiguous params or surfacing later as opaque generation failures.

Four parity fixes, each mirroring the corresponding Python validation:

1. **Mutual exclusivity** of constraints in the `structured_outputs` blob — exactly one of `json`/`regex`/`choice`/`grammar`/`json_object`/`structural_tag`. Mirrors `StructuredOutputsParams.__post_init__` (`vllm/sampling_params.py:90-111`).
2. **Null `json_schema`** — `response_format: {type: json_schema, json_schema: {schema: null}}` is now rejected. Python lowers a null schema to `json=None`, which then fails the "must use one constraint" check.
3. **`structural_tag` shape** — a tag matching neither the legacy (`structures`/`triggers`) nor current (`format`) shape is rejected at request time. Mirrors `validate_structural_tag_response_format` (`vllm/entrypoints/openai/engine/protocol.py:167-197`).
4. **Structured outputs + named tool** — combining structured outputs with a specific `tool_choice` function is rejected. Mirrors `chat_completion/protocol.py:800-809`.

Each fix references the Python source it mirrors and adds regression tests (property-based via `proptest`, plus example-based cases).

## Not a duplicate

Searched open PRs for structured-output / structural_tag / mutual-exclusivity validation in the Rust frontend — no existing PR addresses these request-validation gaps.
