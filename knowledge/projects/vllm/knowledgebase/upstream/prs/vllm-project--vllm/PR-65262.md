# [Feature][KV Connector][Mooncake] Export store usage metrics for MooncakeStoreConnector

[Upstream PR](https://github.com/vllm-project/vllm/pull/65262) · state: open · merged: False

## Original PR description



## Overview

Adds store-usage, allocation-size and dedup metrics to `MooncakeStoreConnector`. This lets a Mooncake store deployment report the same tier view as the CPU offloading connector's `vllm:kv_offload_cpu_cache_*_perc`. Depends on [kvcache-ai/Mooncake#5174](https://github.com/kvcache-ai/Mooncake/pull/5174) for the unevictable-memory gauges; without it, only occupancy is exported.

## Claims

- New gauges: `vllm:mooncake_store_cache_{usage,write_usage,read_usage,occupancy}_perc`. They are opt-in through `kv_connector_extra_config.mooncake_master_metrics_url` and read from the Mooncake master's `/metrics`. They keep updating while the engine is idle.
- New histogram `vllm:mooncake_store_allocation_size`: keys per `save_put`, with the same buckets as `vllm:kv_offload_cpu_allocation_size`.
- New counter `vllm:mooncake_store_save_existing_keys_total`: save candidates skipped because the store already holds them.
- New "Metrics" section in `docs/features/mooncake_store_connector_usage.md`, plus the new config key and the master's metrics port.

## Details

- **Why poll the master, and why from the frontend.** The connector cannot see the store's in-flight puts, read leases or deferred releases; only the master can. Scheduler-side connector stats only reach Prometheus on engine steps, and an idle engine blocks on its input queue, so a scheduler-side poller froze the gauges at their last busy value. `MooncakeStorePromMetrics` therefore polls `/metrics` once a second on a daemon thread in the API server process and sets the gauges directly. No core file (scheduler, engine core, model runner) changes.
- **Gauge definitions** (fractions of `master_total_capacity_bytes`):
  - `usage`: processing + leased + `master_put_start_discarded_staging_size`.
  - `write_usage`: processing.
  - `read_usage`: leased.
  - `occupancy`: allocated.
  - The discarded staging bytes are replicas displaced by an overwrite, a preempted put or a put timeout. They leave the object metadata, but stay allocated until deferred release.
- **Difference from the CPU offloading connector.** `read_usage` includes the master's whole read-lease TTL, not only the transfer time, so its values are not comparable to `kv_offload_cpu_cache_read_usage_perc`. This is documented. The CPU connector has no occupancy gauge, and there is no `stores_skipped` equivalent, because this connector has no reuse threshold.
- **Older masters.** Only `occupancy_perc` is exported, and a one-time warning is logged.
- **Multiple processes.** With several engines, every engine label gets the same value, since one store backs them all. With several API server processes, each one polls the master; the gauges use `multiprocess_mode="mostrecent"`.
- **Complexity.** About 168 non-test lines: the poller, the master-text parsing via `prometheus_client.parser`, the gauge, histogram and counter definitions, and the dedup count in the worker.
- **CI coverage gap.** CI has no Mooncake master, so there is no `LLM`/`RemoteOpenAIServer` regression test. The end-to-end checks above were run outside CI. Non-zero discarded staging was not exercised end to end: vLLM skips keys the store already holds, so that load never overwrites or preempts.
- **AI assistance.** Claude Code was used to write the code, tests and docs, and to run the validation. Every commit carries a `Co-Authored-By: Claude` trailer.
