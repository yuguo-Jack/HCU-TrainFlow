# [Rust Frontend] Report system_fingerprint from the engine's config hash

[Upstream PR](https://github.com/vllm-project/vllm/pull/65636) · state: open · merged: False

## Original PR description



## Overview

The Rust frontend returns `system_fingerprint: null` because the hash part of the fingerprint comes from `VllmConfig.compute_hash()`, and it has no `VllmConfig`. This PR has the engine report that hash (and `enable_expert_parallel`) in `EngineCoreReadyResponse`, and the Rust frontend builds `system_fingerprint` from it for every `--fingerprint-mode`.

## Claims

- The engine reports `config_hash`, the `compute_hash()` of its initialized `VllmConfig`, and `enable_expert_parallel` in `EngineCoreReadyResponse`. A hashing failure reports `None` and never fails startup.
- The Rust frontend supports `--fingerprint-mode` (`full`, `hash`, `custom`, `none`) and `--fingerprint-value`, which it previously rejected as unsupported.
- It reports `system_fingerprint` in Python's format (`vllm-<version>[-tpN][-ppN][-dpN][-ep]-<hash8>` for `full`) and placement: on non-streaming chat and completion responses, and on the last stream chunk (the finish chunk, or the usage chunk when `include_usage` adds one). Before this PR it was `null` and stream chunks lacked the key.
- The Python frontend is unchanged: it keeps hashing its own config copy, so the two frontends report different hash parts for the same deployment. A follow-up PR will switch the Python frontend to the engine-reported hash.

## Details

**Why the engine's hash rather than reproducing the Python frontend's:**
- **It describes what runs.** `compute_hash()` identifies the config that shapes the computation graph. Its value on the initialized config is the same kind of value as the torch.compile cache key, which the worker computes from its config (`compilation/backends.py`).
- **It is independent of VRAM.** Memory-derived values are ignored factors in `CacheConfig.compute_hash` (`num_gpu_blocks`, `kv_cache_size_tokens`, `gpu_memory_utilization`, `hash_block_size`, …), so the hash is stable across restarts of the same deployment. The one input that can depend on free memory is an auto-fitted `max_model_len` (`--max-model-len -1`), which does change which requests are accepted.
- **The Python frontend's hash is of a launch-config copy.** It is the launch config plus the few values `MPClient._apply_ready_response` syncs back. It misses what the engine resolves during initialization (`kv_cache_layout`, resolved in `EngineCore` before memory profiling and never synced back; on Qwen3-0.6B that field alone changes the hash) and keeps the deployment DP size that dense DP ranks reset to 1. Reproducing it would mean the engine keeping a copy of its launch config and mirroring the frontend's sync list.

**Engine** (`vllm/v1/engine/core.py`, `vllm/v1/engine/__init__.py`): `_make_ready_response` adds `config_hash` (guarded, so a hashing failure reports `None`) and `enable_expert_parallel`. Both fields have defaults, so existing consumers of the ready response are unaffected.

**Rust frontend:**
- `vllm-engine-core-client` decodes the two fields.
- The server owns the fingerprint (`fingerprint.rs`, `FingerprintMode::fingerprint`). It is built once at startup from the engine with the smallest `max_model_len` (dense DP ranks auto-fit it independently; Python's frontend keeps the smallest) and the deployment-wide DP size, stored on `AppState`, and stamped by the chat and completions handlers.
- The CLI maps `--fingerprint-mode` (the clap value enum `FingerprintModeArg`) and `--fingerprint-value` to the server's `FingerprintMode`, stored as `Config::fingerprint_mode` like Python's `fingerprint_mode`. As in Python, `custom` without a value reports no fingerprint.
- The render server has no engine and serves no response that carries the field.

**Deviations from Python:**
- The hash part is the engine's initialized-config hash, not a hash of a frontend config copy (see above); the follow-up PR aligns the Python frontend.
- When the engine reports no hash (`compute_hash()` raised in the engine, or an engine without the field), Rust reports `…-nohash`.
- Rust uses the engine-reported `vllm_version`, where Python uses its own `vllm.__version__`. They are the same install in every supported deployment.
