# [Perf][Frontend] Decode streamed custom-tool input incrementally

[Upstream PR](https://github.com/vllm-project/vllm/pull/64674) · state: closed · merged: True

## Original PR description



## Overview

For a Responses `custom` tool, every streamed argument delta re-runs `partial_json_parser` over the whole accumulated arguments, so the API server's cost per delta grows with the tool input. This decodes only the new tail of the input string. Follow-up to #57322.

## Claims

- Cost per streamed delta at 64K chars of tool input drops from 1.59 ms to 4.3 us, and at 256K chars from 14.9 ms to 11.4 us.
- On a real server (GLM-4.7-Flash, one H200), streaming a 256K-char `apply_patch` input over `/v1/responses` costs the API server 22 s of CPU against 563 s on main, and `/health` p99 stays at 0.9 ms against 42.8 ms.
- Streamed `response.custom_tool_call_input.delta` events are unchanged. After every delta the streamed payload equals `decode_custom_tool_input_prefix` of the arguments so far.
- Arguments that do not start the way `encode_custom_tool_input` writes them (`{"input": "`) keep the full decode, as does every delta after the payload string closes.
- No API, event or config change. Scope is non-Harmony Responses streaming (`responses/streaming_events.py`, `responses/utils.py`).

## Details

**Root cause.** `emit_simple_tool_call_delta` appends each delta to `state.accumulated_text` and calls `decode_custom_tool_input_prefix` on all of it. That runs `partial_json_parser.loads`, which strips and completes the whole text in Python on every call. Cost per delta is linear in the input and the total is quadratic. Custom tools carry freeform input such as patches, so long inputs are the normal case for Codex-style clients.

**Change.**
- `extend_custom_tool_input_prefix` returns the same payload as `decode_custom_tool_input_prefix`, decoding only the arguments after the end of the previous call. It matches `partial_json_parser` on a partial string:
  - it decodes up to the last complete escape;
  - it holds back a trailing high-surrogate escape, so a pair is never split between calls;
  - it holds back trailing whitespace, which `partial_json_parser` strips before completing the string.
- When the tail does not decode as a JSON string body (the closing quote, a raw control character, an invalid escape), it returns `None`. The state then uses `decode_custom_tool_input_prefix` for the rest of the call.
- `SimpleStreamingState.tool_call_payload_end` records where decoding stopped, or -1 after the fallback. `tool_call_payload` already holds the decoded payload, since `_emit_custom_tool_input_delta` stores every payload it gets.

**Cost.** The work that stays linear in the input on each delta is C-level: `accumulated_text +=`, `payload + chunk` and the `startswith` in `_emit_custom_tool_input_delta`. That is the 11.4 us at 256K chars.

**Limitations.** Arguments in another form keep the full decode on every delta. The shim arguments come from the tool parsers' `json.dumps`, which writes the canonical head.

**Unchanged here and the same on main.** A call cut off by `max_output_tokens` leaves the shim JSON unclosed. `decode_custom_tool_input` then returns the raw arguments, so `emit_simple_tool_call_done` resends them in full as a last delta, and the `done` event and the output item carry the raw JSON. In the unforced server run, both servers stream 106,815 decoded chars followed by the 109,606-char raw `{"input": "...` text. That is a separate fix.

**Not a duplicate.** Searched open PRs for `decode_custom_tool_input_prefix`, `emit_simple_tool_call_delta` and Responses custom-tool streaming. #56418 (open) changes custom-tool naming for namespaces and leaves the streaming decode as is. #56285 (open, inactive since 2026-09-18) is the original that #57322 split out.
