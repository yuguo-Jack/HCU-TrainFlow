# [Model] DeepSeek V4.1: enable DSpark speculative decoding under pipeline parallelism

[Upstream PR](https://github.com/vllm-project/vllm/pull/63619) · state: open · merged: False

## Original PR description

[Model] DeepSeek V4.1: enable DSpark speculative decoding under pipeline parallelism

Depends on #63617 (PP2 cannot complete KV allocation without it); the
input_ids PP-contract gate for requires_raw_input_tokens is already on
main (vllm/v1/worker/gpu/model_runner.py#L2009) - v0.31.0 predates it.

Stock rejects DSpark + PP for DeepSeek V4.1 at load time (the
eagle3_utils verify reads supports_aux_hidden_states_over_pp on the
inner decoder). This enables it with a model-only change:

- supports_aux_hidden_states_over_pp = True on DeepseekV4Model, plus
  the partition-independent relay: pack_local_aux_hidden_states into
  the non-last-stage IntermediateTensors and
  collect_remote_aux_hidden_states before the local aux list on the
  last stage. The slot math (_aux_slot_base_cached, bisect_right in
  _set_aux_hidden_state_layers) already lives in EagleModelMixin; V4.1
  inherits it, and reserve_aux_intermediate_tensor_slots reserves
  (batch, hidden) slots matching V4.1's aux shape
  (previous_post.mean(dim=1) -> [T, hidden], model.py:579), so the
  relay needs no further model plumbing.
- dspark.py: PP-conditional has_own_embed_tokens (the target's
  embed_tokens is a PPMissingLayer on the last stage, so mainline's
  maybe_share_target_embed must skip the share), the draft's own
  embed.weight load (~1.3 GB on the last stage) with a post-load
  assert so a renamed checkpoint key fails loudly, and the docstring
  updated where it said the draft always aliases the target's.

Verification honesty: the relay path (an aux layer upstream of the
last stage) cannot be exercised on our hardware - any split putting
layer 37 on rank 0 means 38 layers on one GB300, which does not fit.
The pack/collect is verified by the default 20/20 split plus code
read; maintainers with larger PP setups are asked for a run.

Receipts (2x DGX Station GB300, 400G CX8 RoCE, image
vllm-openai:v0.31.0 with these changes as source overlays, identical
temp-0 prompt, deterministic x3):

- All-reduces per decode step: 84 -> 0. One profiled window (3
  generations, 879 tokens, ~237 steps at ~3.7 accepted/step): 0
  AllReduce, 0 AllGather kernels; ~2 SendRecv + ~3 Broadcast per step
  (pipeline hops and draft-token distribution).
- Single-stream: 290.5 -> 391 tok/s (+34%).
- Step time 12.3 ms -> ~9.4 ms (derived: tok/s / accepted length, not
  a direct measurement).
- GSM8K: 97/100, 0 errors (temp 0, first 100 of openai/gsm8k
  test/main, 0-shot).
- Free KV cache 72.7 / 57.1 GiB per rank (~2x the TP2 pool); vision
  verified end-to-end (image tokens route through bias_vl on both
  stages; correct answers, deterministic).
- Concurrency curve on this build: C1 323 / C2 406 / C4 595 / C8 974
  aggregate tok/s - the pipeline needs admission depth to fill both
  stages, and TP2-vs-PP2 at C4-C16 is unmeasured here.

Temp-0 outputs differ from TP2 (0/24 md5s) - documented divergence:
TP2 sums bf16 GEMM partials across GPUs; PP2 computes each GEMM whole.
Deterministic within a parallel shape.

Full recipe, overlays as .diffs, verification instruments:
https://github.com/ebfio/deepseek-v41-flash-pp2-pair

- ebfio · comment · 2026-10-25T22:50:43Z · [source](https://github.com/vllm-project/vllm/pull/63619#issuecomment-6404508920)

TP2 vs PP2 at concurrency, measured after filing (identical soak script and 24-prompt corpus, fresh boot per side, temp 0.7, zero swap on both):

| C | TP2 aggregate (tok/s) | PP2 aggregate (tok/s) |
| --- | --- | --- |
| 1 | 234.2 | 323.4 |
| 2 | 326.2 | 405.7 |
| 4 | 422.9 | 594.9 |
| 8 | 547.7 | 974.4 |
| 16 | 842.5 | 1266.4 |

PP2 dominates at every measured concurrency. Mechanism: TP2's compute step is batch-insensitive, but its collective step is not — the per-step all-reduce payload grows linearly with batch tokens, and 84 calls per step stretch from ~3 ms at C1 toward ~16 ms at C16 on this fabric (per-call latency 37 → 67 → 187 µs at 61 KiB → 490 KiB → 1 MiB, from the NCCL bracket on the same fabric), so TP2's aggregate saturates at ~3.6× C1 while PP2's two p2p hops stay microseconds of bandwidth and the pipeline keeps filling with admission depth.

The single-stream +34% in the description is therefore the floor of this enablement's value, not the ceiling.

Both curves and the measurement method are in the repo: https://github.com/ebfio/deepseek-v41-flash-pp2-pair
