# [ROCm][Perf][Muse Spark] Enable the bf16x3 router GEMM on gfx942

[Upstream PR](https://github.com/vllm-project/vllm/pull/63724) · state: open · merged: False

## Original PR description

## Overview

The Muse Spark AMD model computes its FP32 router with `router_bf16x3_gemm`: three BF16 planes that sum exactly to the FP32 weight, multiplied on BF16 matrix cores. It was gated to CDNA4 (`_supports_router_bf16x3_device`) because its tile table was tuned there. On MI300X (gfx942) the router therefore falls back to an FP32 hipBLASLt GEMM on an FP32 copy of the activations, about 27 ms of a 691 ms 60k-prefill step at TP8 (router plus cast).

The kernel itself is plain Triton, but two of the existing tiles (the `≤1024`-token bucket, `BLOCK_M=128, BLOCK_N=64, BLOCK_K=128`) need 80 KiB of LDS and fail to launch on MI300X, which has 64 KiB. This PR adds a CDNA3 tile table tuned on MI300X, selects the table with `get_cdna_version()`, and opens the gate on gfx942/CDNA3. `supports_router_bf16x3` checks the table of the device it runs on.

## Claims

- On MI300X the bf16x3 router is 1.1–1.6× faster than the FP32 path from 16 to 8,192 tokens. At 8,192 tokens: 448 → 289 µs per layer, about 10 ms per 8k prefill step over 62 layers.
- It is closer to an FP64 reference than the FP32 path (max abs error 7.4e-6 against 3.3e-5 at 8,192 tokens) and picks the same top-8 experts on every row tested.
- Serving `amd/Muse-Spark-Open-816B-A42B-Quark-PTPC-FP8` at TP8 on 8× MI300X: +0.5–1.2% total throughput at 8k and 16k input with 16–64 concurrent requests (mean of three runs, positive in every run), except 16k c32, which is flat; 1k input is within ±1% noise. GSM8K is unchanged (0.9545 → 0.9522, within one standard error).

## Validation

**Unit tests.** `tests/kernels/test_muse_spark_router_bf16x3.py` (existing; 1, 33, 300, 1,100 and 5,000 tokens, relative error below 2e-6 against FP64) passes on MI300X together with the Muse Spark loading, logits and shared-RoPE model tests (20 passed, `vllm/vllm-openai-rocm:nightly-5d35ce3934` with this branch's files mounted). Before this PR the 300 and 1,100 cases select the tile that exceeds MI300X LDS (`OutOfResources: Required: 81920, Hardware limit: 65536`).

**Kernel, MI300X, one GPU.** Router shape N = 256, K = 8,192, BF16 activations. "FP32" is `F.linear(x.float(), w)`, the current gfx942 path including the cast.

**Tuning.** Tunings were done using `triton.testing.do_bench` over `BLOCK_M ∈ {32, 64, 128}`, `BLOCK_N ∈ {32, 64, 128}`, `BLOCK_K ∈ {64, 128}`, `splits ∈ {4, 8, 16, 32}` and `num_warps ∈ {4, 8}`, for each token count. The sweep skips tiles where `K % (splits * BLOCK_K) != 0` or `BLOCK_M` is larger than the batch needs, and tiles that fail to launch, which is how the 80 KiB-LDS tiles drop out on MI300X. Each bucket takes the fastest tile, checked against an FP64 reference for max error and top-8 agreement.

## Details

- **Selection.** `_device_configs()` is cached and looks the table up by `get_cdna_version()`: `_CONFIGS_CDNA3` for 3 and `_CONFIGS_CDNA4` (the former table, renamed) for 4, with no default, so an architecture without a tuned table raises instead of borrowing one. `supports_router_bf16x3` checks the same table. The gate is `get_cdna_version() in (3, 4)`. Both import `vllm.platforms.rocm` lazily, so the op module stays importable on other platforms.
- **Threshold.** `_ROUTER_BF16X3_MIN_TOKENS = 16` is kept; on MI300X the kernel is at parity with FP32 at 32 tokens and ahead everywhere else measured.
- **Limitations.** CDNA2 (gfx90a) stays on the FP32 path.
