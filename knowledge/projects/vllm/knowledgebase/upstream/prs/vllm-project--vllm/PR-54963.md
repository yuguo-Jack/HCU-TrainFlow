# [Bugfix] Keep the multi-port DP supervisor serving through fault-tolerant recovery

[Upstream PR](https://github.com/vllm-project/vllm/pull/54963) · state: open · merged: False

## Original PR description

With `--data-parallel-multi-port-external-lb --enable-fault-tolerance`, the DP supervisor tears down recovered peers when a removed rank exits. Its `/health` probes also keep readiness at 200 while the group is halted.

After initial readiness, poll each remaining child's `/v1/fault_tolerance/status`. Keep the supervisor alive while ranks are healthy, unhealthy, or diagnosing, and remove exited child ports from the probes. `/ready` requires a healthy rank; `/health` reflects supervisor liveness. Shut down after the configured threshold of sweeps with no serving or recovering rank.

Builds on #46370. Related: #41438.

## Tests

- Revision `4c34f6c5b1`: `pytest tests/entrypoints/launchers/test_dp_supervisor.py -q` — **26 passed** on CPU, including lifecycle tests. The updated status test failed against the preceding revision's unversioned endpoint and passed with this change; it also covers `diagnosing`.
- Pre-commit hooks, including mypy, passed.

Historical GPU validation, before this review update: H200, two DeepSeek-V2-Lite pools with DP/EP=4 each, TP=1, NIXL EP, EPLB and fault tolerance enabled. Under request load, a worker was killed and the pool was scaled down. The stock supervisor killed the recovered pool in 2/2 runs; this PR kept three ranks serving in 3/3 runs, with no failed requests after the removed rank exited. Without scale-down, readiness dropped in 34–38 seconds versus 132 seconds with the stock supervisor. This GPU scenario was not rerun on the current revision.

Requests already in the halted pool, or routed to its dead port before it exits, can still fail because readiness is per pool while routing uses individual ports.
