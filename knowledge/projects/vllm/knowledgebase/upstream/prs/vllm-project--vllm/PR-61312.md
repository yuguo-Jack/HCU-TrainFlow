# [Bugfix][Frontend] GLM-5.3: honour enable_thinking when the served chat template has a thinking switch

[Upstream PR](https://github.com/vllm-project/vllm/pull/61312) · state: open · merged: False

## Original PR description

## Overview

Follow-up to #56994 (which fixed #54744). The GLM-5.3 "always thinks" check reads `tokenizer.chat_template`, so a server
that serves a template *with* a thinking switch via `--chat-template` (or a request's `chat_template`) has
`enable_thinking=False` ignored: the answer comes back in `reasoning_content` and `content` is empty. This passes the
template actually used for the request to the parser and judges that one.

## Claims

- With a served template that has an `enable_thinking` switch, `enable_thinking=False` / `thinking=False` are honoured
  again for GLM-5.3 (non-streaming and streaming).
- Unchanged for the stock GLM-5.3 template, a template name such as `tool_use`, or no served template: the #56994
  behaviour (reasoning forced on) still applies.

## Validation

- Unit: `pytest tests/reasoning/test_glm4_moe_reasoning_parser.py` — 24 passed. The new
  `test_glm53_served_template_with_switch_honors_thinking_disable` fails on main and passes with this change;
  `test_glm53_served_template_without_switch_still_forces_reasoning` covers no template / a template name / the stock
  template.
- `pre-commit run --files <changed files>`: ruff, ruff-format, mypy, test tethering all pass.
- End to end, GLM-5.3-Flash (W4A16, TP4, H100) served with a `--chat-template` that adds `enable_thinking`, vLLM nightly
  `fe4df3df` with and without this patch, OpenAI-compatible requests with `chat_template_kwargs={"enable_thinking": false}`:

  | Build | json_schema, reasoning off | json_object, reasoning off | plain answer, reasoning off |
  |---|---|---|---|
  | nightly fe4df3df | content empty (answer in reasoning_content) | content empty | content empty |
  | nightly fe4df3df + this PR | conforming JSON in content | valid object in content | direct answer in content (`17 × 23 = 391`) |
  | v0.31.0 (reference) | conforming JSON in content | valid object in content | direct answer in content |

## Details

- Root cause: `_glm53_always_thinks()` (added in #56994) inspects the tokenizer's bundled template. The served template
  (`--chat-template`, or `request.chat_template`) is what is rendered, and it may define `enable_thinking` (here: the
  stock GLM-5.3 template plus `{%- set enable_thinking = ... -%}`, the effort header gated on it, and
  `'<think>' if enable_thinking else '<think></think>'`).
- Change: the chat-completions, batch, responses and derenderer parser constructions pass
  `chat_template=request.chat_template or self.chat_template` (the same choice `build_chat_params` makes); the GLM
  check judges that template when it is Jinja source and falls back to `tokenizer.chat_template` otherwise. Parsers
  already accept `**kwargs`, and legacy tool parsers do not receive construction kwargs, so other parsers are
  unaffected.
- Not duplicating: #56994 (merged) introduced the check for the stock template; #54276 (open) ignores
  `enable_thinking` for GLM-5.3 unconditionally. Neither covers a served template that has the switch.
- Unchanged: `vllm/entrypoints/openai/responses/context.py` builds parsers without any construction kwargs (no
  `chat_template_kwargs` either), so the thinking toggle doesn't reach that path today.
