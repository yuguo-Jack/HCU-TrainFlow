# fix(mamba): guard CPU GDN speculative acceptance counts

[Upstream PR](https://github.com/vllm-project/vllm/pull/56518) · state: open · merged: False

## Original PR description

## Summary

Fixes #56419. On the CPU GDN speculative path, `num_accepted == 0` makes the native convolution kernel violate its `[1, seqlen]` precondition. The Python fallback also reads history at offset `-1` and rolls rejected draft tokens into the convolution state.

The native path additionally cannot represent a valid shrunken step whose previous step accepted more tokens than the current step carries. Those rows need the Python fallback rather than a kernel call with invalid arguments.

## Changes

- Route batches with zero acceptance or acceptance outside the native kernel contract through the Python fallback.
- Clamp zero acceptance to history offset 0, compute draft outputs over the intact history, and skip the convolution-state roll for that row.
- Preserve the previous-step acceptance semantics for shrunken steps. Do not clamp the history offset to the current query length.
- If acceptance exceeds the actual stored history, use the latest valid history window and emit a one-time warning.
- Add regressions for zero-acceptance state preservation, native-kernel avoidance, and acceptance beyond the stored history. The existing cross-step regression also covers the valid `accepted > current q_i` case.

## Testing

Rebuilt on current main `e4a5b55373` and ran on an arm64 Mac with `VLLM_TARGET_DEVICE=cpu`:

- The three new regressions fail against the unfixed implementation and pass with this change.
- `pytest tests/kernels/mamba/cpu/test_cpu_gdn_ops.py -k "spec_forward or causal_conv1d_torch" --deselect "tests/kernels/mamba/cpu/test_cpu_gdn_ops.py::test_spec_forward_conv_tracks_accepted_tokens[True]"`: **11 passed, 144 deselected**. This includes the existing fallback regression for uneven current query lengths and previous-step acceptance counts.
- Ruff format, Ruff check, and `git diff --check` pass on both changed files.
- The deselected native parameter case stops during test setup because this environment's `_C` binary has no `causal_conv1d_weight_pack`. A whole-file run is likewise not green here because that binary lacks the current CPU GDN symbols. These are not reported as passing tests, and native AMX execution remains a CI/hardware validation item.

## On the contiguity path — you don't need to go hunting

You said you'd start from where the fallback's `mixed_qkv` is sliced. I isolated it after my
last comment, and it isn't there. The offending argument to
`fused_sigmoid_gating_delta_rule_update_cpu` is **`initial_state_indices`**:

```
initial_state_indices: shape=(1,) stride=(5,) dtype=torch.int32
                       is_contiguous()=True   stride(-1)=5
```

The kernel's precondition is `stride(-1) == 1`, not full contiguity — on healthy calls it
accepts `initial_state_source` with `is_contiguous()=False` because *that* tensor's last-dim
stride is 1. Every data tensor (`q`/`k`/`v`/`a`/`b`/`mixed_qkv`) had last-dim stride 1 on the
crashing call, which is why my three earlier `.contiguous()` patches all missed.

Origin, in `v1/attention/backends/gdn_attn.py`, the `spec_sequence_masks is None` branch:

```python
non_spec_state_indices_tensor = block_table_tensor[:, 0]
```

`block_table_tensor` is `(N, num_spec + 1)`, so this basic-indexing **view** carries stride
`(num_spec + 1,)` — 5 at K=4. The sibling `block_table_tensor[mask, : num_spec + 1]` is
*advanced* indexing and therefore a copy, which is why the speculative path never trips.

**And the existing guard cannot work.** `mamba/ops/cpu/gdn_attention.py` already has
`state_indices_tensor = state_indices_tensor.contiguous()` for exactly this, but when the
batch holds a single non-spec decode the tensor has one element, and PyTorch reports
`is_contiguous() == True` for any tensor with `numel <= 1` regardless of stride — so it
returns `self` and the stride-5 view reaches the kernel untouched. The bug hides behind a
line that looks like the fix.

Confirmed by forcing a genuine packed copy (`torch.empty(...).copy_(...)`, **not**
`.contiguous()`) on the read-only index arguments: the contiguity error disappears. That
repack is what let me reach your code path at all. Suggested fix is to pack it at the
producer in `gdn_attn.py`, or check `stride(-1) == 1` explicitly at the call site;
`.contiguous()` is not sufficient anywhere a length-1 batch is possible.

## One correctness question on the clamp

The clamp stops the crash, and I want to be clear I verified that and not more. It also
silently changes which history window is read for a shrunken step. Across 14 requests I saw
no garbage output, but that does not establish the conv state stays numerically correct under
sustained clamping — my runs can't distinguish "correct" from "plausible". Since the
underlying inconsistency looks like it originates in `build()` — `spec_query_start_loc` is
this step's scheduled tokens while `num_accepted_tokens` is the previous step's sampler
result, with nothing tying them together — it may be worth deciding whether the conv path
should tolerate the pair or the metadata should never emit it. Not a blocker on this PR from
where I sit; it fixes a real crash and I'd take it.
