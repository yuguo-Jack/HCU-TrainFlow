# [Bugfix][Distributed] Wake MessageQueue readers on shutdown

[Upstream PR](https://github.com/vllm-project/vllm/pull/64786) · state: open · merged: False

## Original PR description

## Overview

Fixes #64714 by allowing `MessageQueue.shutdown()` to cancel readers blocked while receiving a remote or overflow payload.

## Claims

- Remote and overflow payload readers recheck shutdown at a receive-only interval of at most 100 ms, leaving margin below the worker's 5-second exit grace.
- A timeout raised while decoding a payload remains caller-visible and does not consume the next queued message.
- Shutdown wins when it races with a payload already returning from `recv`, so a late payload is not delivered after cancellation.
- Every finite timeout retains its initial poll attempt, including zero, negative, and sub-millisecond nonblocking timeouts.
- The message wire format and shared-memory idle-reader interval remain unchanged.

## Duplicate-work check

Searches for `#64714` and `MessageQueue shutdown reader` found no competing implementation. PR #58059 covers cancellation during the startup handshake; this change covers readers already past that handshake and blocked in the remote or overflow payload receive path.

## Validation

The regressions use real `MessageQueue`, ZeroMQ, and pickle objects. Trace events only observe entry into the real `recv`/`send_multipart` methods and force the relevant ordering; no production method is patched and no fixed sleep is used.

## Details

Local shared-memory readers can be awakened through `_spin_condition.cancel()`, but remote readers and local overflow readers wait in `socket.poll()`. The payload receive path now uses a dedicated 100 ms recheck interval while preserving the existing 5-second shared-memory lost-notify interval.

`MessageQueue.recv()` distinguishes socket poll expiry from payload decoding by raising `_SocketPollTimeout` only when `socket.poll()` returns false. `_recv_interruptible()` retries only that private signal, so user payloads that raise `TimeoutError` during unpickling are not misclassified.

CPU testing of this PR's changes at head `35f330eace24`, applied to base `602811546b03`, found an exception-handling regression: `MessageQueue.recv()` also runs `pickle.loads()`, so catching every `TimeoutError` can swallow a payload’s decoding error and return the **next message** from the same `dequeue()` call.

A real-pickle regression covering SHM, overflow and remote readers gives **1 passed / 2 failed** with this PR's changes. Distinguishing poll timeouts from decoding errors fixes it while preserving callers’ `except TimeoutError` handling.

The change is limited to three places:
```python
class _SocketPollTimeout(TimeoutError):
    """No message became readable before the socket poll expired."""
```
Raise this subclass only when `socket.poll(...)` returns false in `MessageQueue.recv()`, and catch only `_SocketPollTimeout` in `_recv_interruptible()`. Leave `pickle.loads()` outside that retry classification.

With this correction and the regression below, the full `test_shm_broadcast.py` file gives **72 passed / 2 existing CUDA-only skips**. Independent checks give **9 passed**, including normal multi-buffer transfers, finite timeouts, shutdown-before-receive and repeated shutdown. Default-interval cancellation remains approximately **5.005 seconds**, consistent with this PR’s bounded-recheck design. No GPU fault-recovery validation is claimed.

```python
def _raise_payload_timeout(padding):
    raise TimeoutError("payload-decode-timeout")


class _PayloadWithDecodeTimeout:
    def __reduce__(self):
        return _raise_payload_timeout, ("padding" * 500,)


@pytest.mark.parametrize(
    "n_local_reader, max_chunk_bytes",
    [(1, 8192), (1, 128), (0, 128)],
    ids=["shm", "overflow", "remote"],
)
def test_payload_timeout_does_not_consume_next_message(
    n_local_reader, max_chunk_bytes
):
    writer = MessageQueue(
        n_reader=1,
        n_local_reader=n_local_reader,
        max_chunk_bytes=max_chunk_bytes,
        max_chunks=2,
        connect_ip="127.0.0.1",
    )
    reader = MessageQueue.create_from_handle(writer.export_handle(), rank=0)
    try:
        writer.wait_until_ready()
        reader.wait_until_ready()
        expected = "next-message" * 500
        writer.enqueue(_PayloadWithDecodeTimeout())
        writer.enqueue(expected)
        with pytest.raises(TimeoutError, match="payload-decode-timeout"):
            reader.dequeue(timeout=1)
        assert reader.dequeue(timeout=1) == expected
    finally:
        reader.shutdown()
        writer.shutdown()
```
