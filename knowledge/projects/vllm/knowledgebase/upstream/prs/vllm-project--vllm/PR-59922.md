# [Kernel] Extend LiteTopK decode to BF16 V4.1 top512 and next_n 1-6

[Upstream PR](https://github.com/vllm-project/vllm/pull/59922) · state: open · merged: False

## Original PR description

Thanks to @TKONIY for the collaboration on this work.

Stacked on [vLLM #59921](https://github.com/vllm-project/vllm/pull/59921): the first commit belongs to that PR, so please review the other two.

## Overview

Extend [vLLM #59921](https://github.com/vllm-project/vllm/pull/59921) with
MXFP4/BF16 top512 decode for n=1..6, ported from
[SGLang #42351](https://github.com/sgl-project/sglang/pull/42351).
Requires [DeepGEMM #25](https://github.com/vllm-project/DeepGEMM/pull/25),
stacked on [#24](https://github.com/vllm-project/DeepGEMM/pull/24).

## Claims

- Supports page128 H32/D128 MXFP4 decode and exact top512 of BF16 producer scores.
- Builds the paired split384 schedule from final live lengths/IDs once per
  metadata group and reuses it across layers, including draft updates and graphs.
- Uses direct FP32 input weights for n=1..5 with the new producer capability;
  preserves the explicit BF16 cast for n=6 and for older DeepGEMM versions.
- Preserves BF16 candidate publication, mask-consumer and explicit-backend fallbacks.

## Validation

B200 (148 SMs), Torch 2.13.0+cu130, Python 3.12.3, PDL enabled.
Three isolated process blocks per version; nine shuffled CUDA-graph samples per
block. Captured GLM-5.2/DSpark operands use distinct KV replicas totaling at least
256 MiB. Timings include metadata generation/copy once per eight layers and are
reported per layer. They exclude the rest of the model and are not serving
latency. Across all 40 shapes, live logits, exact histograms and logical-index
selection agree between submitted and optimized versions in all 240 cases.
The full grid with ranges, the method and the validation record are below.

**Method.** One NVIDIA B200 (148 SMs), Torch 2.13.0+cu130, Python 3.12.3, PDL enabled; clocks not locked, and the GPU was checked to be idle before each process. Operands are real captures (GLM-5.2 layer 0 FP8, DSpark layer 20 MXFP4); prefix lengths and batches are built from the captured query/weight bank, and KV bytes are copied into separate page sets per request and layer. This repeats one captured layer's operands, not an actual eight-layer model run. Each graph cycles over at least 256 MiB of actively read KV across at least eight layer replicas. The generic split256 metadata plus its copy is timed once per eight layers in every arm; the submitted BF16 version additionally builds split384 metadata and casts weights in every layer, while the optimized version builds and copies split384 metadata once per eight layers (n=1–5 pass FP32 weights, n=6 keeps the BF16 cast). Three fresh process blocks per version with alternating order; within a process, baseline/LiteTopK order is randomized for each of nine samples, each replaying its CUDA graph four times. Values are medians of the three block medians, with [min, max] block medians. Submitted and optimized DeepGEMM run as separate installed packages. Warmup, JIT, host work, operand setup, Q quantization, KV writes, candidate publication, attention and the rest of the model are outside the timed interval. Across the 40 cells, the default chain drifted between package runs by -0.55% to 0.92%.

`old/new` compares the submitted LiteTopK code with the optimized code; `default/new` compares the unchanged FP32-score + auto-selector chain with the optimized LiteTopK chain in the same process. Higher is faster. µs are per layer.

**n=6.** The first direct-FP32-weight n=6 variant regressed on long B=4 decode. An interleaved three-arm probe separated this from metadata reuse: at ~1M, reused metadata with packed BF16 weights was faster than direct FP32 weights, and vectorizing the paired shared load did not close the gap. The vLLM helper therefore keeps packed BF16 weights for n=6 at every context, with no host read of live lengths, giving up roughly 1–2 µs of the short-context gain to avoid the long-context regression.

## Details

The opt-in flag remains `--kernel-config '{"enable_litetopk_decode": true}'`.
BF16 math and lower-index tie semantics are unchanged from the submitted version;
BF16 ranking can differ from the default FP32 scores.

The earlier implementation launched split384 metadata and a weight cast in every
layer. The builder now maintains stable schedule storage after flattening,
compression and final request IDs, with refreshes for draft steps. Standalone
calls without a shared schedule still build fresh metadata.

FP32 weights are rounded inside the producer with the same BF16 rule as an
explicit cast. A three-arm captured-data probe found a long-context regression
for the n=6 swizzled direct-weight kernel. n=6 therefore retains packed BF16
weights while benefiting from schedule reuse; this avoids a context-dependent
host read and preserves the score contract.

**Duplicate-work check:** this updates the existing stacked decode/BF16 PR,
distinct from [vLLM #48726](https://github.com/vllm-project/vllm/pull/48726)
