## Overview

Add the stateless Responses API (`POST /v1/responses`, streaming and non-streaming) to the Rust frontend on top of the existing `ChatLlm` pipeline.

The original stack split this endpoint into non-streaming (2/3, this PR) followed by streaming (vllm-project/vllm#63903). The Rust frontend is streaming-first: `ChatEventStream` is the primary interface, and non-streaming Chat Completions is a fold over it. As [agreed with @franciscojavierarceo](https://github.com/vllm-project/vllm/pull/63902#issuecomment-6538867465), this PR now carries both layers in that order: streaming first, then non-streaming as a fold over the same state machine. It supersedes vllm-project/vllm#63903. Layer 1/3 (vllm-project/vllm#63901) has merged.

## Commits

Each commit builds and passes its tests on its own.

1. `da7eeffe37` (@franciscojavierarceo) — stateless streaming Responses: request lowering into `ChatRequest`, `OutputItemStreamer` for the item lifecycle, store-dependent features rejected or 404. Squashes the streaming-first part of the original stack (listed in the commit message); non-streaming returns 400 at this point.
2. `7e41889ed4` — typed wire DTOs and stream events: tools and tool choice reuse the Chat Completions definitions, input items deserialize into typed items (a message item may omit `type`, like Python), and SSE events are a typed enum with `type` and `sequence_number` added by a wrapper.
3. `2ea078d012` — defer to shared layers: the response echoes the sampling values the engine actually uses (model defaults applied, `max_output_tokens` clamped to the context), like Python's `ResponsesResponse.from_request(sampling_params)`, via `ChatEventStream::sampling()`.
4. `1c1bbe1fe5` — the streamer is the only source of `output`; output indices and the deferred `output_item.done` derive from completed items.
5. `10448da198` (co-authored by @franciscojavierarceo) — non-streaming as a fold: drive the same `OutputItemStreamer`, discard its events, and return the terminal response. The Responses terminal event carries the complete response, so `output` follows one set of item rules in both modes. Errors still map to HTTP statuses (engine errors 400/503, a broken stream 500) instead of a `failed` response.
6. `8fbae250f3` — per-request timing `metrics`, as in Python Responses.
7. `4da559a6db` — a truncated reasoning item is also marked `incomplete`, as in Python.
8. `f28f024629` — remaining vLLM request controls: forward `min_p`; reject `spaces_between_special_tokens: false`, `media_io_kwargs`, `mm_processor_kwargs`, and `enable_response_messages: true` instead of dropping them.
9. `a1d8bd8364` — unset response fields serialize as `null`, as in Python.
10. `99446a2d75` — report `usage.input_tokens_details.cache_write_tokens`, as Python has since vllm-project/vllm#60973; the OpenAI SDK `Response` type requires it. Found by the e2e below.

## Behavior

- Stateless: clients replay the full history in `input`. `store: true` executes without storing (Python's implicit downgrade); `background: true` is 400; `previous_response_id`, retrieval, and cancellation are 404.
- `max_tool_calls` limits built-in tool calls only, so with function tools alone it is accepted and echoed.
- `reasoning.summary`, `text.verbosity`, `include: ["reasoning.encrypted_content"]`, and `service_tier` are accepted compatibility inputs (Codex sends them by default) without producing summaries, applying verbosity, encrypting reasoning, or scheduling guarantees.
- Deliberate difference from Python: a generation failure during streaming ends with `response.failed` carrying the partial output, instead of a generic error frame.
- Not supported: built-in, custom, and namespace tools, `allowed_tools`, and output logprobs (rejected with 400).

### Details

Responses owns its wire envelopes and conversions while reusing the chat generation path and matching shared audio/tool primitives. the rebase preserves upstream's other route registrations and error serialization rather than restoring the older envelope.

- omitted or null `stream` selects non-streaming. omitted/null watermarking and explicit overrides follow current Chat Completions semantics.
- metadata is a string map limited to 16 pairs, 64-character keys, and 512-character values.
- omitted temperature/top-p use model defaults; explicit overrides are preserved and checked against the engine request.
- unknown service tiers, invalid summary/verbosity values, unsupported `include` outputs, and nonzero `top_logprobs` are rejected.
- unknown `previous_response_id` uses the current shared `NotFoundError` envelope: HTTP 404, `param: response_id`, numeric `code: 404`.

the frontend remains stateless: clients replay history, and agentic-api owns persistence and tool execution. the shared native adapter tracked by vllm-project/agentic-api#359 and vllm-project/agentic-api#382 is still unfinished. accepted reasoning-summary, text-verbosity, and encrypted-reasoning inputs are documented compatibility no-ops; valid service tiers are echoed without scheduling guarantees. persistence, retrieval/cancellation, built-in/custom/namespace tool execution, Harmony rendering, output logprobs, and `allowed_tools` are out of scope. the rendered [Responses documentation](https://github.com/franciscojavierarceo/vllm/blob/codex/responses-nonstreaming/docs/serving/online_serving/openai_compatible_server.md#responses-api) describes the supported subset.

these are the existing #58783 layers opened upstream at [@BugenZhao's request](https://github.com/vllm-project/vllm/pull/58783#issuecomment-6418403089), rather than competing implementations. the original authored history and discussion remain in #58783. @gcanlin's #53380 implementation is credited in the endpoint and streaming commits. #56124 covers render endpoints and #51535 covers chat `allowed_tools`; neither duplicates this endpoint.
