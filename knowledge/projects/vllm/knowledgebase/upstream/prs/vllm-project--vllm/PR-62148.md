# [Kernel][Perf] Add H20 block-FP8 fused MoE config for E=512,N=128 (Qwen3.5-397B-A17B-FP8 TP8, up to 2.0x)

[Upstream PR](https://github.com/vllm-project/vllm/pull/62148) · state: open · merged: False

## Original PR description

## Purpose

`Qwen/Qwen3.5-397B-A17B-FP8` with TP=8 runs the Triton fused MoE with `E=512, N=128` (K=4096, top-k 10, 128x128 weight blocks). No tuned config exists for this shape on `NVIDIA_H20`, so vLLM logs

```
Using default MoE config. Performance might be sub-optimal! Config file not found at .../E=512,N=128,device_name=NVIDIA_H20,dtype=fp8_w8a8,block_shape=[128,128].json
```

and uses the default config. For M > 64 the default switches to `BLOCK_SIZE_M=64`. With 512 experts and top-k 10, each expert gets only about M*10/512 rows, so most of each 64-row tile is padding. The tuned config keeps `BLOCK_SIZE_M=16` up to M=512 and uses 32 for most larger M, which roughly halves kernel time for M=96–512.

This PR adds that one config file. No code changes.

The H20-3e and H200 files for `E=512,N=128` are the unquantized (bf16) variants, so they don't apply to this block-FP8 path.

## Change

- New file: `vllm/model_executor/layers/fused_moe/configs/E=512,N=128,device_name=NVIDIA_H20,dtype=fp8_w8a8,block_shape=[128,128].json`
- Produced by `benchmarks/kernels/benchmark_moe.py --tune` from main (`a0e7137`): 18 batch sizes, 1920 candidate configs each.

## Performance

Environment:

- 8x NVIDIA H20 (96 GB), driver 595.58.03
- `vllm/vllm-openai:v0.31.0` (digest `c1c9f6fd5c10…`), torch 2.13.0+cu130, Triton 3.7.1
- Model shape: `Qwen/Qwen3.5-397B-A17B-FP8`, TP=8, block-FP8 W8A8

Method: the official `benchmark_moe.py` (no `--tune`) on the same GPU. The baseline arm has no config file (default config); the tuned arm points `VLLM_TUNED_CONFIG_FOLDER` at the new file. ## Test Plan and Results

Numerical check: the tuned config and the default config run on the same inputs through `fused_experts` (`override_config` for the tuned arm). Each output is compared with an fp32 torch reference that dequantizes the 128x128-block FP8 weights. The check covers 3 seeds x 20 batch sizes (1–4096, including M values between tuned keys, such as 3 and 200).

- Tuned vs default output: max relative L2 difference 0.0043, at the M values whose tuned config uses `BLOCK_SIZE_K=64` (1536, 3072, 4096). It is exactly 0 for every M up to 64 and for M=2048, and below 3e-4 everywhere else.
- Tuned vs reference and default vs reference: agree within 1e-5 at every point (about 0.046 relative L2). This error comes from FP8 activation quantization, which both arms share.
- All outputs finite.

```bash
python benchmarks/kernels/benchmark_moe.py --model Qwen/Qwen3.5-397B-A17B-FP8 \
  --tp-size 8 --dtype fp8_w8a8 --trust-remote-code \
  --batch-size 1 2 3 4 6 8 16 24 32 48 64 96 128 192 256 384 512 1024 1536 2048 3072 4096
```

- `python -m json.tool <config>`: passed.

- Workload: `vllm bench serve --dataset-name random --random-input-len 1024 --random-output-len 256 --ignore-eos`, with `num_prompts = 4 x concurrency` (at least 16). Each concurrency level ran twice with seeds 101 and 102; both arms used the same seeds. Values below are the mean of the two runs.

| 8 | 713.4 → 703.9 (−1.3%) | 9.55 → 9.54 | 433 → 477 |

This matches the kernel table. Each decode step runs the MoE with M ≈ the number of running requests. The kernel speedup starts at M=96, so the end-to-end gain shows up at concurrency 128, where TPOT drops by 27%. At concurrency 64 the kernel is only ~8% faster, which doesn't show end to end.

The −1% to −1.4% at concurrency 1 and 8 is within boot-to-boot variation as far as I can tell. In the kernel benchmark, M=1–8 are identical between the two configs (30.81 vs 30.80 us at M=1).
