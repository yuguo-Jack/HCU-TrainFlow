# [ROCm][Recipe] Qwen3.8-Flash-Next: add MI355X Quark MXFP4 variant (TP1/TP2)

[Upstream PR](https://github.com/vllm-project/vllm/pull/63332) · state: closed · merged: True

## Overview

Adds the AMD Quark MXFP4 checkpoint, [`amd/Qwen3.8-Flash-Next-Quark-MXFP4`](https://huggingface.co/amd/Qwen3.8-Flash-Next-Quark-MXFP4), to the [Qwen3.8-Flash-Next recipe](https://recipes.vllm.ai/Qwen/Qwen3.8-Flash-Next) as an MI355X variant at TP2 and TP1. It turns on the MI355X work from #59575 that is merged and currently supported by the stock ROCm nightlies.

## Claims

- On MI355X the builder now selects the MXFP4 variant (`meta.default_variant: { mi355x: mxfp4 }`) and renders TP2 for plain TP. The guide also gives TP1, since the checkpoint (169.8 GiB) fits on one GPU.
- The variant's MI355X settings:
  - `VLLM_ROCM_USE_AITER=1`;
  - `VLLM_ROCM_USE_AITER_FUSION_SHARED_EXPERTS=1` (#55686);
  - `AITER_USE_FLYDSL_MOE_SORTING=1`;
  - `--gdn-prefill-backend aiter_flydsl`.
- On the stock nightly, the rendered commands serve at the checkpoint card's accuracy: GSM8K 0.967 at TP2, 0.967 at TP1 and 0.965 at TEP8, against the card's 0.965.
- Speculative decoding becomes opt-in on MI355X, so the rendered MI355X commands don't include MTP; a page note for MI355X says why. Every other GPU renders exactly as before.
- The guide describes the MXFP4 flags, the TEP8/TP2/TP1 choice and the validation results in prose, without a launch command. A troubleshooting entry for the MXFP4 variant covers the engine ready timeout on slow TP2 cold starts.

## Details

- **Speculative decoding** is out of scope for now. MTP doesn't load from the published MXFP4 checkpoint until [its config.json fix](https://huggingface.co/amd/Qwen3.8-Flash-Next-Quark-MXFP4/discussions/1) is merged (details in #63124). The schema has no per-variant feature switch, and a single-mode `spec_decoding` limited to the other variants fails validation ("every checkpoint must retain at least one usable mode"). This PR therefore uses `hardware_opt_in_features: { mi355x: [spec_decoding] }`. That also turns MTP off by default for FP8 on MI355X, which still offers it as a toggle. A `notes[]` entry for MI355X explains this, and the FP8 MI355X guide section no longer passes `--speculative-config`.
- **TP size.** The variant sets `tp: { mi355x: 2 }`. TP2 matches the checkpoint card's serving command. TP1 is also possible, but since the builder keeps one TP size per variant and GPU, TP1 is only documented in the guide.
- **Strategy.** The recipe's `default_strategy` is `single_node_tep`, so the builder's MI355X default is TEP8. That works since #60816 made native AITER W4A4 MoE the default at TEP8, and it is validated above. DEP is also offered by the recipe's strategy list but wasn't tested with this variant.
