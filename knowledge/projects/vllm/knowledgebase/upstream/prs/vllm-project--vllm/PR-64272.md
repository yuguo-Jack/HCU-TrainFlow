# [CI] Enroll 13 jobs in automatic sharding

[Upstream PR](https://github.com/vllm-project/vllm/pull/64272) · state: closed · merged: True

## Original PR description

## Overview

Enrolls five more CI steps and eight AMD mirrors in automatic sharding (`automatic_shard: true`), continuing #64181 down the list on ci.vllm.ai/sharding. Most run as one job today, exactly as now; the AMD LM Eval Small Models mirror and Entrypoints Integration (OpenAI API completion) split in two. Enrolling them means the planner takes over once their tests grow, without another PR. No test changes.

## Claims

| Job | Planned shards |
|---|---:|
| `lm-eval-deepseek-v32-dp-8xh200` + AMD mirror | 1 (one gsm8k test is longer than a shard's budget) |
| `lm-eval-deepseek-r1-dp-8xh200` + AMD mirror | 1 |
| `gpqa-eval-gpt-oss-2xh100` + AMD mirror | 1 |
| `entrypoints-integration-api-server-openai-completion` + AMD mirror | 2 + 1 |
| `rust-frontend-distributed` + AMD mirror | 1 |
| `amd-lm-eval-small-models-1xb200` (base already enrolled) | 2 |
| `amd-spec-decode-draft-model-nightly-b200`, `amd-entrypoints-integration-responses-api` (bases already enrolled) | 1 |

- Each job runs the same commands, environment and timeout as on main, and every test runs exactly once across the shards.

## Validation

- Planned every step and mirror with ci-infra main's planner and main's timings, and rendered each with the pipeline generator as a PR build and in main's OTel mode: every test of the sharded mirror ran in exactly one shard with the same env; the rest stay one job.
- Every job passes on main, including the last nightly for the nightly-only steps.
- Earlier heads: `/ci run` (98049, 98568) plus scoped builds for the AMD mirrors `/ci run` leaves behind the block step (98056, 98638) passed. A fresh `/ci run` follows on this head, with per-command test counts compared against main for every sharded job.

## Details

- **AMD Batch Invariance (Distributed) left out.** Its OLMoE and Granite commands differ only in env vars, and the shard plugin identifies a planned command by its pytest arguments alone, so in build 98638 the Granite test was deselected on both shards (10 passed vs 11 on main). The plugin fix (an explicit command id) goes to ci-infra; the mirror can be enrolled after it lands.
- **`caplog`.** `tests/entrypoints/openai/responses/test_function_call_parsing.py` asserts on log text; the Responses API mirror runs as one job, so its file order is as on main.
- **CPU steps left out.** Main records no test timings for CPU jobs yet, so CPU-Quantization and CPU-Spec Decode wait until that is sorted out.
- **Timeouts unchanged.** `timeout_in_minutes` stays as it is on every step.
- **Left out, higher on the list:** Language Models (Standard) and its mirror (the planner overcounts files its `core_model and (not slow_test)` filter never runs; a planner fix comes first), Python-only Installation, Python 3.14 Smoke and the AMD LM Eval Spec Decode mirror (failing on main), and the AMD A100 Distributed mirror (its base step has no recent main run).
- **Where to look.** `.buildkite/test_areas/{entrypoints,lm_eval,misc,rust_frontend,spec_decode}.yaml`: one line per step or `mirror.amd` block.

- khluu · comment · 2026-11-02T05:39:48Z · [source](https://github.com/vllm-project/vllm/pull/64272#issuecomment-6569984152)

Holding this one for a coverage issue on head `181f4ae122b9`. The reviewed runs meet the 20-minute target (slowest enrolled job: 18m25s), but AMD Batch Invariance (Distributed) silently loses the Granite model case.

- [Main build 98597](https://buildkite.com/vllm/ci/builds/98597#01a18b6a-f606-446c-bb69-69c8a492d656) runs all five pytest commands: **11 passed** in total, including the final Granite invocation.
- [PR build 98638, shard 2](https://buildkite.com/vllm/ci/builds/98638#01a18be1-0930-494a-9b55-c67124c3d3c4) reaches command 7/7 with `VLLM_TEST_MODEL=ibm-granite/granite-3.0-1b-a400m-base`, but reports **1 deselected** and exits successfully. Across both shards, only **10 tests pass**.

The sharding plugin used by that run matches a planned command using pytest arguments alone. The OLMoE and Granite invocations have identical pytest arguments but different environment variables. Granite therefore picks up OLMoE's shard assignment: the shell guard skips it on shard 1, and the plugin deselects it on shard 2. Comparing unique node IDs alone misses this because both model configurations use the same test node ID.

The smallest fix for this PR is to leave the AMD Batch Invariance (Distributed) step out of automatic sharding. Alternatively, fix command identity in the shared sharder (for example, pass an explicit planned-command ID), then rerun this step and verify that both OLMoE and Granite execute exactly once and the total is back to 11 passes. Please include per-command/model coverage in that validation, not just a green build.
