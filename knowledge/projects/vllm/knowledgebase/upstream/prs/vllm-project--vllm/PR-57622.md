# [Model] Restore MusicFlamingo for Audio Flamingo Next checkpoints

[Upstream PR](https://github.com/vllm-project/vllm/pull/57622) · state: open · merged: False

## Original PR description



## Purpose

Fixes #57259.

NVIDIA's Audio Flamingo Next checkpoints cannot be served on vLLM today. They declare
`"architectures": ["MusicFlamingoForConditionalGeneration"]` / `"model_type": "musicflamingo"`,
an architecture that was removed in #47263. Rather than failing cleanly, vLLM falls back to the
Transformers backend and crashes during engine startup:

```
INFO  Resolved architecture: TransformersMultiModalForCausalLM
WARNING  TransformersMultiModalForCausalLM has no vLLM implementation, falling back to
         Transformers implementation.
...
  File ".../vllm/model_executor/models/transformers/multimodal.py", line 1109, in _process_audio_input
    audio_output = self.model.get_audio_features(
TypeError: MusicFlamingoModel.get_audio_features() missing 1 required positional argument: 'input_ids'
```

The Transformers backend structurally cannot serve this architecture. HF's
`MusicFlamingoModel.get_audio_features` takes `input_ids` as a required argument — it uses it to
recover, for each 30s audio chunk, that chunk's index within the audio it came from, which drives
the model's rotary *time* embedding. vLLM encodes audio separately from the text tokens, so there
is no `input_ids` to pass. No flag works around this.

### On #47263

That PR removed MusicFlamingo partly on the basis that *"MusicFlamingo has been superseded by
AudioFlamingo3 (new MusicFlamingo checkpoints use AudioFlamingo3)"*. That is true of exactly one
checkpoint and not the rest:

| Checkpoint | `model_type` | Downloads/mo |
| --- | --- | --- |
| `nvidia/music-flamingo-hf` | `audioflamingo3` | 7,064 |
| `nvidia/music-flamingo-2601-hf` | `musicflamingo` | 21,173 |
| `nvidia/music-flamingo-think-2601-hf` | `musicflamingo` | 470 |
| `nvidia/audio-flamingo-next-hf` | `musicflamingo` | 7,450 |
| `nvidia/audio-flamingo-next-think-hf` | `musicflamingo` | 557 |
| `nvidia/audio-flamingo-next-captioner-hf` | `musicflamingo` | 11,725 |

`music-flamingo-hf` genuinely was re-released on AudioFlamingo3 — the generalisation is
understandable. But the 2601 series and NVIDIA's entire current Audio Flamingo Next line stayed on
`musicflamingo`, and together account for ~41k downloads/month. (These are HF downloads, not vLLM
usage; if you have telemetry showing low vLLM traffic specifically, that is a fair counterpoint —
though arguably it was low because the model did not work.)

`nvidia/music-flamingo-2601-hf` was also the example checkpoint in vLLM's own docs row for this
architecture, and its generation fixtures are still in the tree at
`tests/models/fixtures/musicflamingo/` — the test that consumed them was removed, the fixtures were
not. This PR puts them back to work unmodified.

### What this PR is, precisely

**It is mostly a restoration, and the diff should be read that way.** The model file is ~321 lines
verbatim from the implementation deleted in #47263; **111 lines differ**, of which **one** was
required to make it run at all:

```diff
-                target=audio_token,          # a string
+                target=[audio_token_id],     # token ids
```

The prompt-update API changed while the file was deleted. The remaining ~110 lines are mypy fixes,
removal of two overrides that had become byte-identical to the base class, and extracting one
helper to module level so it can be unit-tested.

The most useful way to review this:

```bash
git diff a22e0dfc69^ -- vllm/model_executor/models/musicflamingo.py
```

**No lines are Audio-Flamingo-Next-specific.** AF-Next works because it declares the same
architecture the deleted code already implemented.

### API drift fixed during the port

| Drift | Symptom |
| --- | --- |
| `PromptReplacement(target=...)` now takes token ids | hard crash: `TypeError: Can't extract 'str' to 'Vec'` |
| `_call_hf_processor` → `parse_mm_data` + `_apply_hf_processor_main` | test `AttributeError` |
| stricter mypy | 4 errors: optional-config access, missing `isinstance` narrowing, LSP violation on `_process_audio_input` |
| encoder construction in tests needs `default_vllm_config` | fixture error |
| `pydocstyle` added to ruff (#52136) | auto-rewrote `vLLM's` → `VLLM's` in a docstring |

### On maintenance burden

The concern behind #47263 was legitimate — the drift table above is exactly the tax that
accumulates. What is different now is CI coverage:

| Test | Coverage |
| --- | --- |
| `processing/test_common.py` | 9 cells — all three AF-Next checkpoints |
| `processing/test_tensor_schema.py` | schema validation incl. the `rote_timestamps` field |
| `processing/test_musicflamingo.py` | 3 tests, incl. a **revived** HF-parity test |
| `generation/test_musicflamingo.py` | 3 tests on real weights, existing frozen fixtures |
| `test_registry.py` | the mandatory registration test |

The parity test is worth calling out: it was gated `skipif transformers >= 5.5` and **had not run
since transformers 5.5**. It is rewritten against the current
`get_audio_features(..., input_ids)` signature and now verifies on every CI run that vLLM's
`chunk_counts`-derived RoTE timestamps match HF's `input_ids`-derived ones.

A concrete data point: #57576 ("Type dummy options per modality") landed while this PR was in
review and changed `AudioFlamingo3DummyInputsBuilder.get_dummy_mm_data`'s signature. This PR needed
no change, because its dummy-inputs builder delegates rather than duplicates.

### Model evaluation — output parity vs transformers

Greedy, identical chat-templated prompt and identical 16kHz waveform to both backends,
compared at the token-id level.

**6/6 exact token match** on MMAU-Pro questions with `nvidia/audio-flamingo-next-hf`, including a
47-token musical analysis reproduced word for word.

Across audio lengths (10s / 1 chunk, 35s / 2 chunks, 396s / 14 chunks) on all three AF-Next
checkpoints, every divergence traced to a bf16 tie, not a defect. Logit margins measured at the
exact divergence points:

```
audio-flamingo-next-hf, 35s clip, token 0:
   ' noise'  -1.18320  <- HF        margin: 0.125000   (one bf16 ULP)
   ' sounds' -1.30820  <- vLLM

audio-flamingo-next-captioner-hf, 396s clip, token 0:
   'The'     -1.13630  <- HF        margin: 0.000000   (exact tie)
   'Amb'     -1.13630  <- vLLM
```

The structural argument is decisive: if the chunk-index logic were wrong, a 14-chunk input could
not match exactly while a 2-chunk input failed. It does match, and the timestamps are verified
bit-identical to HF's `input_ids`-derived ones at chunk counts 1–8 (`maxdiff=0.0`) — this is what
the revived parity test now asserts in CI.

The last row matters: `get_supported_mm_limits()` returns `{"audio": 1}`, a cap the CLI flag
cannot override, so the multi-audio path is structurally unreachable rather than merely untested.

### Throughput

One-factor-at-a-time from a baseline (35s audio, 5-token prompt, 128-token generation), n=8,
vLLM caches disabled (`enable_prefix_caching=False`, `mm_processor_cache_gb=0`) since HF has no
equivalent, and HF forced to full generation length (`min_new_tokens`) so both backends are timed
on the same work. Mean of the three AF-Next checkpoints, output tok/s:

| Config | HF batched | HF single | vLLM batched | vLLM single | vLLM/HF batched |
| --- | --- | --- | --- | --- | --- |
| baseline (35s, 128 gen) | 159.9 | 54.0 | **818.2** | 158.6 | **5.12x** |
| audio short (10s) | 163.7 | 52.8 | **1021.9** | 167.2 | **6.24x** |
| audio long (396s) | 93.8 | 43.0 | **187.4** | 81.2 | **2.00x** |
| prompt medium (68 tok) | 230.7 | 57.8 | **803.0** | 156.6 | **3.48x** |
| prompt long (347 tok) | 156.7 | 52.2 | **767.8** | 153.7 | **4.90x** |
| gen short (32 tok) | 249.7 | 57.7 | **363.9** | 109.6 | **1.46x** |
| gen long (512 tok) | 286.5 | 60.8 | **1187.4** | 176.1 | **4.14x** |

Long audio collapses the advantage to 2.0x because a 396s clip is 10,012 prompt tokens against 128
generated — prefill-bound, little for continuous batching to amortise. The three checkpoints are
performance-identical (807/840/807 tok/s at baseline), as expected from identical configs.

### Known limitations

- **One audio per request.** `get_supported_mm_limits()` returns `{"audio": 1}`. The chunk index is
  read from the chunk's position in the encoder batch, which is only correct if every chunk in that
  batch came from the same audio. Multi-audio prompts are refused rather than silently mis-encoded.
- **Greedy output is not bit-reproducible across backends** for this model, because of the frequent
  near-ties above. Occasional token-level divergence on short descriptive outputs is expected and is
  not a regression signal. `generation/test_musicflamingo.py` asserts exact token ids against
  fixtures frozen on H100 and may need attention if CI runs it on different hardware.
- **`tests/models/multimodal/generation/test_audioflamingo3.py` has a latent test-quality defect**
  that this PR fixes in its own copy: the `llm` fixture wraps `LLM(...)` in
  `except Exception: pytest.skip(...)`, silently converting real failures into green CI. It masked a
  GPU OOM twice during this work. Fixed here using vLLM's own idiom
  (`check_available_online` + `check_transformers_version`, then construct directly) — with no
  usable GPU the suite now reports 3 errors where it previously reported 3 skipped. The
  AudioFlamingo3 copy is left alone as out of scope; happy to send a follow-up.
