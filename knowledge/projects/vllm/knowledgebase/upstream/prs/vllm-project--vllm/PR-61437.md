# [Perf][Qwen4Exp] Add SM121 TP=2 merged QSA projection plans

[Upstream PR](https://github.com/vllm-project/vllm/pull/61437) · state: closed · merged: True

## Original PR description

## Overview

#59533 merged the QSA QKV/gate projection with the replicated indexer Q/K projection, so at TP=2 on DGX Spark
(GB10, SM121) the local weight is `(7296, 2560)` = 6656 + 640. `QWEN4_EXP_SM121_GEMM_PLANS` has the TP=1 merged
shape `(13952, 2560)` but not the TP=2 one, so on a 2x DGX Spark TP=2 deployment every QSA projection call falls
back to cuBLAS. This PR adds the measured `(7296, 2560)` rows for M = 1/2/4/8/16 and keeps `(6656, 2560)` for the
LoRA path, which does not fuse the indexer projection.

## Claims

- GB10, `(7296, 2560)` BF16, cold L2, fresh process, arms alternated: at M=1 the skinny kernel reads the weight at
  about 250 GB/s vs 165 GB/s for the cuBLAS `gemvx` kernel (**~1.5x**). At M=2..16 cuBLAS already reaches
  225-235 GB/s, so the gain is about 1.05x-1.15x. Cosine 0.999999 vs FP32 `F.linear` for every row.
- In a 2x DGX Spark TP=2 serving trace (MTP k=3, c=1) the projection moves from `gemvx` (218 us, M=1) /
  `cutlass_80_wmma` (170 us, M=2/4) to the planned skinny kernel (162 us): 2.57 -> 2.35 ms per decode step.
  Like #60027, this PR restores a planned dispatch path; it does not claim an end-to-end speedup (see Validation).
- No behaviour change for TP=1, other architectures, or LoRA deployments.
