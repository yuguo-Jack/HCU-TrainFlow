# [Bugfix][Frontend] Close the parent's listening sockets after launching the Rust frontend

[Upstream PR](https://github.com/vllm-project/vllm/pull/65156) · state: open · merged: False

## Original PR description

## Overview

Part of #65155. The parent process kept its copies of the HTTP and gRPC sockets after passing them to the Rust frontend, so both ports kept listening after Rust closed its listeners at shutdown. Clients that connected during a drain were never answered. This closes them right after `Popen`, where the ZMQ listeners are already closed.

## Claims

- During a drain, new HTTP and gRPC clients are refused instead of hanging. Requests already running still finish.
- New gRPC clients can still hang while another gRPC call is open. That's the Rust side of the issue and needs a separate fix.

## Validation

Ran `VLLM_USE_RUST_FRONTEND=1 vllm serve HuggingFaceTB/SmolLM2-135M-Instruct --grpc-port 50052 --shutdown-timeout 40` on the `vllm/vllm-openai-cpu:latest` image (0.33.0, same `RustFrontendProcessManager` as main; "After" has this change applied). I kept a long HTTP completion running, sent SIGTERM, and connected to each port 2s later:

| | New HTTP client | New gRPC client | In-flight request |
|---|---|---|---|
| Before | no reply after 5s | `DEADLINE_EXCEEDED` after 5s | 200 |
| After | connection refused | `UNAVAILABLE` (connection refused) | 200 |

The new test gives the manager real listening sockets and a fake `Popen`, then checks that connecting afterwards is refused. It fails on main with `DID NOT RAISE ConnectionRefusedError`.

```
pytest tests/entrypoints/launchers/api_server/test_api_server_process_manager.py  # 13 passed
```

## Details

The child already has the fds through `pass_fds` once `Popen` returns, and the parent doesn't touch the sockets after that. `test_rust_frontend_inherits_grpc_listener` now reads the fds before the manager closes them.

#64426 adds per-rank sockets to this class, so whichever PR lands second should close those too.
