# [ROCm][Kernel] Wave64 topk_softplus_sqrt fast path for DeepSeek-V4 routing

[Upstream PR](https://github.com/vllm-project/vllm/pull/64208) · state: open · merged: False

## Original PR description

## Purpose

DeepSeek-V4 / V4.1 routing calls `topk_softplus_sqrt` once per MoE layer per
step (40 times per decode step on DeepSeek-V4.1-Flash). On ROCm it runs the
generic `topkGatingSoftplusSqrt<6,384,4,8,64,...>` kernel, which keeps its row
in a dynamically indexed private array (32 B/lane of scratch) and reduces each
argmax round through LDS shuffles. The CUDA build already has a specialized
DSv4 kernel (`launchDsv4HashTopk`, hash layers only); ROCm has none.

This adds a ROCm-only fast path inside `topkGatingSoftplusSqrtKernelLauncher`
for fp32 gating output, `topk == 6`, 256/384/512 experts, wave64:

- one wave64 per row, 2 or more scores per lane via `float2` loads;
- the k loop is unrolled and nothing is dynamically indexed (0 scratch, 35 VGPRs);
- the argmax is a DPP reduction (quad_perm, row_half_mirror, row_mirror,
  row_bcast:15/31) into lane 63 plus `readlane`, so the winner is wave-uniform;
- hash rows, `bias_vl` image rows, `is_padding` rows, `renormalize` and the
  routed scaling factor follow the generic kernel, and so do the output bits:
  the weight is `(score + bias) - bias`, decoded from the argmax key, and the
  renormalize sum runs in the generic fp32 launch's order (k order on thread 0
  for score rows; per owner thread, then a 64-lane XOR butterfly, for hash rows).

It launches only on gfx950 (a runtime `gcnArchName` check), where it was
measured; other wave64 GPUs keep the generic kernel. Other shapes and dtypes
keep the existing kernel too.

## Test Plan

- `pytest tests/kernels/moe/test_topk_softplus_sqrt.py` on MI355X (gfx950)
  with the rebuilt `_moe_C_stable_libtorch`. The fp32, topk-6 cases at 256/384/512
  experts (plain, hash, padding, NaN padding, `bias_vl`, hash + `bias_vl`) take
  the new path.
- New `test_wave64_top6_matches_generic_kernel_bitwise`: bf16 input takes the
  generic kernel, and the same values converted to fp32 (exact) take the new
  one; weights and ids must match bit for bit. It covers 256/384/512 experts,
  score and hash rows, bias, renormalize and padding. Hash rows with
  renormalize are compared only at 384 experts: at 256 and 512 the generic
  kernel's bf16 launch has a different thread layout from its fp32 launch, so
  its sum order differs.
- Standalone hipGraph-replay bench of the stock kernel against the new
  kernel on the same inputs (384 experts, topk 6, bias, renormalize, scale 1.5).

CI hasn't run: `pre-run-check` is a label gate. `pre-commit` (including
clang-format) and the tests here were run locally.

## Test Result

Tests: 1794 passed, 31 skipped, 2 failed. The bitwise test has 120 passed and
24 skipped, the skips being the hash + renormalize cases at 256 and 512 experts.
The two failures are `test_hash_routing_backend_selection[triton_unfused-...]`,
a backend-selection test that never calls this kernel. They fail on the base
commit without this PR too (5d35ce393, stock `_moe_C`: 2 failed, 4 passed with
`pytest tests/kernels/moe/test_topk_softplus_sqrt.py -k hash_routing_backend_selection`).

Graph replay at head 8d8d48c2d, MI355X, µs per call (empty kernel 1.86 µs).
The variant is `topkSoftplusSqrtWave64` copied verbatim from this PR, against
the stock kernel from the base; 384 experts, topk 6, bias, renormalize, scale
1.5. Two runs in separate processes on 2026-10-30, which agree within 0.05 µs;
the table is run 1:

| rows | stock | this PR | speedup | expert ids equal | max weight diff |
|---|---|---|---|---|---|
| 1 | 8.29 | 5.38 | 1.54x | yes | 0 |
| 4 | 8.94 | 5.65 | 1.58x | yes | 0 |
| 16 | 9.45 | 5.72 | 1.65x | yes | 0 |
| 64 | 9.45 | 5.72 | 1.65x | yes | 0 |
| 128 | 9.50 | 5.76 | 1.65x | yes | 0 |
| 256 | 9.60 | 5.80 | 1.66x | yes | 0 |

The new kernel uses 29 VGPRs and no scratch; the stock one uses 32 B/lane of
scratch. The bit-identical weights (bias round trip, k-order sum) cost about
0.7 µs against the first commit's 4.74-5.04 µs. The saving is about 2.9-3.8 µs
per call, roughly 0.12-0.15 ms per decode step on DeepSeek-V4.1-Flash.
In the TP4 decode trace the routing chain (router GEMM,
this kernel, AITER sort and quant) costs 1.1–1.5 ms per step.
