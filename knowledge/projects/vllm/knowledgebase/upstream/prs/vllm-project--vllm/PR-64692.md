# [Model Loader] Refill weight-derived tensors in place on every post-load rerun

[Upstream PR](https://github.com/vllm-project/vllm/pull/64692) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

Keep tensors derived from weights (kernel constants, inverse scales, decode copies) at their startup addresses when post-load processing reruns on a weight reload, so captured CUDA graphs read the new values instead of freed memory. Part of the direct weight reload work (RFC #54477, rule 3). Builds on #64357 (merged); replaces aoshen02/vllm#180.

> **Direct reload.** #64336 (direct reload core) is now in main, and this branch has main merged. The direct reload tests that waited on it are back in this PR (see Validation). Results marked "direct" were measured with #64336 on both arms, before it merged.

## Claims

- After a weight reload with CUDA graphs on, MoE models whose post-load step derives kernel tensors serve the same output as before the reload. Without this PR they collapse:
  - gpt-oss-20b (TRT-LLM MXFP4, direct reload): GSM8K 0.39 → 0.01;
  - Qwen3-30B-A3B-NVFP4 (CuteDSL): 0.90 → 0.01 with direct reload, 0.93 → 0.00 with layerwise reload.
- With direct reload (#64336), every tensor the MoE kernel reads keeps its cold-start address across a reload on these backends: TRT-LLM MXFP4/NVFP4, CuteDSL NVFP4 (including per-locality-domain shards), FlashInfer CUTLASS NVFP4/FP8, and per-tensor FP8 (including TRT-LLM FP8 per-tensor's shuffled weights).
- After a draft-model weight update, the tensors the V2 speculator's FULL CUDA graph reads (DFlash/DSpark context K/V weights and norms, including Beam's DFlash2 and Kimi-K3's DSpark drafters) keep their addresses. Without this PR, Beam DFlash2 acceptance fell from 7.03 to 4.89 after an update.
- The same holds for linear kernels that derive tensors in their post-load step (CUTLASS/Triton INT8 asymmetric `azp_adj`, CUTLASS W4A8, Marlin W4A8-INT8/FP8, b12x NVFP4 W4A16, ModelOpt block-quant), for the ROCm gpt-oss MXFP4 AITER shuffles, Kimi-K3 AMD `_w_fold` and the bf16x3 router split, and for MXFP4 MoE on Marlin (gpt-oss-20b GSM8K 0.43 → 0.00 after a reload without this PR, 0.45 → 0.43 with it).
- Humming MoE: its post-load step runs once per quant method; direct reload refuses it (in main with #64336).
- Across 17 served models with direct reload (3 full-checkpoint updates each, measured by aoshen02), GSM8K holds after every update with this PR; on main it collapses on 8 of them (e.g. gpt-oss-120b 0.80 → 0.006, Kimi-K3 0.95 → 0.25).
- No cold-start change: GSM8K, throughput and KV cache match the base on 12 model/backend configurations, all within noise.

## Details

**Root cause.** `process_weights_after_loading` reruns on every reload (#64357), in both layerwise and direct mode. Many quant methods and models build tensors from the weights there as new allocations: kernel constants (SwiGLU alpha/beta/clamp folded by `g1_alphas`, `g1_scale_c`, inverse activation scales), experts objects rebuilt with fresh constants, decode-path copies. Captured CUDA graphs keep the startup pointers, so after a reload they read freed memory. Every weight is reloaded correctly, so comparing weight values cannot see it.

**Fix.**
- `replace_parameter` already refills parameters in place (unchanged here).
- `refill_derived(obj, name, tensor)` (new) refills a plain attribute in place when shape, dtype and device match, else replaces it. It never creates a parameter, and the held tensor must own its storage.
- MoE experts objects list the tensors their kernels read in `kept_constants`. `keep_constants(layer)` keeps them on the layer and points the new object at them. `FallbackExperts` forwards it to both wrapped experts.

**Limitations / known gaps.** Direct reload (#64336) is the target path; layerwise reload is planned for removal (F10 in the #54477 tracker), so its gaps are listed but not planned for fixing.

*Affect direct reload:*
- **Muse Spark MegaMoE:** `finalize_weights` returns early once transformed and drops checkpoint parameters, so a reload leaves the experts stale (or fails to load them), along with the hybrid TRT-LLM scales built there. Same on main. Tracked as F15.
- **DeepGEMM NVFP4 MegaMoE (MiniMax-M3 NVFP4, Step-5 NVIDIA): the L2 activation scale is a host float.** The max of `w2_input_scale` is passed by value to the Triton prepare kernel and to DeepGEMM `nvfp4_mega_moe`, so CUDA graphs keep the cold-start value when an update changes `w2_input_scale` (QAT-style updates such as verl's NVFP4 W4A4 send it on every sync). Fix: vllm-project/DeepGEMM#49 takes the scale as a device tensor, then vLLM bumps the pin and passes a buffer refilled in place. Tracked as F16; moving the max into PWAL is #64418 L2.
- **Qwen3 XPress:** `XPressHead.build_fused_buffers` builds its fused copies anew.
- **FlashInfer b12x NVFP4 MoE** (SM12x only, opt-in): it rebinds the weight scales to new storage and rebuilds their MMA views and `_fc2_input_scale`.

**2. `pack_tensors` doesn't align entries.** Verified on the current head `e21ca26e22`, nightly `2b009fc6d1`:
```python
import torch
from vllm.distributed.weight_transfer.packed_tensor import pack_tensors, unpack_tensor

weights = [("a", torch.zeros(3, dtype=torch.uint8)), ("b", torch.ones(4, dtype=torch.float32))]
c = pack_tensors(iter(weights), lambda item: item[1], buffer_size_bytes=1 << 20)
unpack_tensor(c.packed_tensor, c.names, c.shapes, c.dtypes, c.tensor_sizes)
# RuntimeError: self.storage_offset() must be divisible by 4 to view Byte as Float
# (different element sizes), but got 3
```
In a real update this happens whenever a tensor with a narrower dtype is packed before a wider one. That is what made update 1 fail on Qwen3.8-Flash-Next, Mistral-Large-3, Inkling-NVFP4 and Laguna. A possible fix is to pad each entry in `pack_tensors` to a multiple of its dtype's itemsize. Our harness took the receiver-side route instead: `unpack_tensor` clones a slice whose offset is misaligned.
