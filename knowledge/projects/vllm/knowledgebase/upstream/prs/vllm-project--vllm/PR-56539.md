# [Bugfix][Spec Decode] Prevent missing KV scale parameter validation crash in Gemma4 MTP

[Upstream PR](https://github.com/vllm-project/vllm/pull/56539) · state: closed · merged: False

## Original PR description

## Purpose

Fixes an engine initialization crash when serving Gemma 4 speculative decoding (MTP) with an official unquantized BF16 assistant drafter (`google/gemma-4-26B-A4B-it-assistant` or `google/gemma-4-31B-it-assistant`) in front of a quantized or calibrated-KV target model (e.g., ModelOpt NVFP4 or FP8 KV cache).

### Background & Root Cause
In Gemma 4 MTP architectures, the draft model decoder layers are KV-shared (`is_kv_shared_layer = True`) and read directly from the target model's physical KV cache at runtime.

When the target model has KV quantization enabled or calibrated scales, the sub-layer `Attention` modules instantiate scale parameters (`q_scale`, `k_scale`, `v_scale`, `prob_scale`) via `KVCacheScaleParameter` (an `nn.Parameter` subclass). However:
1. Official Google assistant checkpoints (`google/gemma-4-*-assistant`) are standard unquantized BF16 checkpoints that do not contain these KV scale tensors.
2. Because the assistant model config is unquantized (`model_config.quantization is None`), `default_loader.py` triggers strict uninitialized parameter tracking:
   ```python
   weights_not_loaded = weights_to_load - loaded_weights
   if weights_not_loaded:
       raise ValueError(f"Following weights were not initialized from checkpoint: {weights_not_loaded}")
   ```
3. This causes the engine to crash during startup with:
   ```
   ValueError: Following weights were not initialized from checkpoint:
   {'model.layers.0.self_attn.attn.k_scale', 'model.layers.0.self_attn.attn.v_scale',
    'model.layers.1.self_attn.attn.k_scale', ... (16 tensors)}
   ```

Because draft layers share the target's physical KV cache, scale parameters should not be loaded from the draft checkpoint; they are either default 1.0 or inherited dynamically from the target model via KV sharing (see PR #49262).

### Fix
In `Gemma4MTP.load_weights()`, mark any instantiated `self_attn.attn.*_scale` parameters as accounted for in the `loaded` set returned to `default_loader.py`.

### How This Was Found
We encountered this when deploying Google's official unquantized Gemma 4 MTP assistant drafter (`google/gemma-4-26B-A4B-it-assistant`) with a 4-bit quantized target model (NVFP4) using KV cache sharing. Standalone serving and unquantized target pairing initialized normally, but pairing the unquantized drafter with the calibrated/quantized target triggered the `default_loader` parameter validation check.

## Test Plan
Verified model loading and speculative decoding execution by pairing an unquantized assistant model with a quantized/calibrated target model:
1. Target: Gemma 4 with calibrated KV / NVFP4 quantization.
2. Speculative Drafter: `google/gemma-4-26B-A4B-it-assistant` (BF16 unquantized).
3. Without fix: Startup crashes with `ValueError: Following weights were not initialized from checkpoint: {'model.layers.0.self_attn.attn.k_scale', ...}`.
4. With fix: Engine initializes cleanly, CUDA graphs capture successfully, and speculative decoding produces identical greedy outputs to standalone baseline with zero uninitialized weight exceptions.
