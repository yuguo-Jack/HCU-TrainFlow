# [ROCm][Perf][MoE] Fuse SiLU-and-mul with per-token FP8 quant in TritonExperts and skip remote EP routes

[Upstream PR](https://github.com/vllm-project/vllm/pull/63721) · state: open · merged: False

## Original PR description

## Overview

With per-token FP8 activations (for example Quark PTPC-FP8), `TritonExperts.apply` runs `silu_and_mul` and then `scaled_fp8_quant(use_per_token_if_dynamic=True)` over every one of the `num_tokens × top_k` rows of the first GEMM's output. Under expert parallelism the first GEMM already skips the routes whose expert is on another rank (`skip_invalid`), and so do the second GEMM and `moe_sum`. The activation and the quant did not, so at EP8 about 7/8 of their work was on rows nothing reads.

This PR adds one Triton kernel, `silu_mul_token_quant`, that does the SiLU-and-mul and the per-token FP8 quant in one pass and skips rows with `expert_map[topk_ids] == -1`. On ROCm, `TritonExperts.apply` uses it when the activation is SiLU without a clamp, the weights are FP8 W8A8 with per-token activation quant, there is no block shape, no static `a2_scale`, no LoRA and no quantization emulation. Every other configuration, and every other platform, takes the existing path. Without EP the kernel still removes the BF16 round trip between the two kernels.

Not a duplicate: searched open and closed PRs. #49828 adds a CUDA C++ SiLU + per-token quant for dense activations, without the expert mask. #56827 ("Skip non-local Marlin ReLU2 activations", closed) addressed the same EP waste for Marlin ReLU2.

## Claims

- On the rows it writes, the output is bit-identical to `silu_and_mul` + `scaled_fp8_quant(use_per_token_if_dynamic=True)`: the same scales and the same FP8 bytes (MI300X, `float8_e4m3fnuz`).
- MI300X, one GPU, 256 experts, top-8, random routing: 7.6× faster than the two kernels at EP8 with 8,192 tokens (867 → 114 µs), 1.6–1.8× at TP8, and faster at every shape down to 8 tokens under CUDA graphs.
- In Muse-Spark-Open-816B-A42B PTPC-FP8 at TP8 + EP on 8× MI300X, the two replaced kernels take 829 µs per layer of an 8,192-token prefill step (498 µs `act_and_mul`, 331 µs quant), so the kernel projects to about 44 ms of a 622 ms step (7.1%) over 62 layers.
- Serving, TP8 + EP on 8× MI300X: higher total throughput at every point of a 1k–16k input × concurrency 1–64 sweep (1k output), from +0.8% at 1k input to +3.9% at 8k c64 and +5.7% at 16k c64, with median TTFT 7–9% lower at 8k and 16k inputs.

## Validation

It also checks that ids outside `[0, num_experts)` are skipped without reading `expert_map`, and that `TritonExperts.apply` takes the fused branch on ROCm (and not elsewhere), with and without EP, with output identical to the unfused path. ## Details

- **Numerics.** `silu_and_mul` rounds `silu(gate)` to the activation dtype before multiplying by `up`, then rounds the product. The kernel rounds at the same two places, takes the row amax of the rounded activation, and uses `get_fp8_min_max()` and the `1 / (fp8_max * 512)` scale floor of `dynamic_per_token_scaled_fp8_quant`, imported as `FP8_MIN_SCALING_FACTOR` from `input_quant_fp8.py` (made public here). Without the first rounding about 3% of FP8 values differed by one code.
- **Skipped rows** of the FP8 output and scale are left uninitialized. They are the rows the first GEMM did not write and that the second GEMM (`sorted_token_ids` excludes them under `skip_invalid`) and `moe_sum` do not read. The kernel drops a row by the same rule as `moe_align_block_size`: an id outside `[0, num_experts)` is invalid without reading `expert_map`, and `num_experts` is the count `TritonExperts.apply` aligns with, which includes fused shared-expert slots when the map is extended for them.
- **Scope.** Block-quantized FP8 keeps `silu_and_mul_per_block_quant`. A dynamic per-tensor scale (`a2_scale_is_global`) disables `skip_invalid` already, and this path does not apply to it. Gated activations other than SiLU, SwiGLU clamps and LoRA keep the unfused path.
- **Who else takes this path.** Any FP8 MoE checkpoint with per-channel weights and dynamic per-token activations on the Triton experts on ROCm. Those gain the same fusion; under EP they also skip the remote rows.
- **Platforms.** The path is gated to ROCm (`current_platform.is_rocm()`) because it is benchmarked only on MI300X and MI355X. On CUDA and XPU, `TritonExperts` keeps `silu_and_mul` + `scaled_fp8_quant`; for example, compressed-tensors `FP8_DYNAMIC` MoE models with the Triton backend are unchanged. The kernel itself is plain Triton and takes the FP8 range from `get_fp8_min_max()`, and its unit test runs in the "MoE Kernels" CI shards on CUDA and on MI300, so enabling CUDA later needs only performance numbers.
