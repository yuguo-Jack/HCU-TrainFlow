# [Bugfix][Spec Decode] Inkling MTP: share the target embedding under PP > 1

[Upstream PR](https://github.com/vllm-project/vllm/pull/62903) · state: open · merged: False

## Original PR description



## Overview

Inkling with MTP speculative decoding and pipeline parallelism fails at startup on the last PP rank, in `profile_run`:

```
multi_module_mtp/speculator.py _prepare_inputs
  -> self.model.embed_input_ids -> self.embed_tokens.weight
AttributeError: 'NoneType' object has no attribute 'weight'
```

`InklingMultiTokenPredictor` sets `embed_tokens = None` on purpose and relies on the target's embedding being attached at load (a replicated copy would transiently double a 2.3 GiB table). `maybe_share_target_embed` returns early under PP > 1 for any drafter that does not declare `has_own_embed_tokens`, so with PP the drafter keeps `None`. Related: #47833 (open) changes embedding sharing in the V1 `llm_base_proposer`, not `maybe_share_target_embed` in the V2 runner, where this fails.

## Claims

- Declare `has_own_embed_tokens = False` on `InklingMTP` in `vllm/models/inkling/{amd,nvidia}/mtp.py`, as the DSpark drafters do. The two copies stay identical.
- Safe under PP: the target builds and loads `embed_tokens` on every PP rank, so the last rank has the real table to share; if that ever became a `PPMissingLayer`, `maybe_share_target_embed` raises rather than serving without an embedding. `lm_head` sharing has no PP guard and the last rank owns it.

## Validation

MI250X, Inkling-Small (bf16), TP8 x PP3 + MTP: the AttributeError above without the change; with an equivalent out-of-tree change the engine starts, and a TP8 x PP2 + MTP deployment serves with it.

New `tests/v1/worker/test_spec_decode_embed_sharing_pp.py::test_inkling_mtp_gets_the_target_embedding_under_pp`: builds `InklingMTP` without weights, fakes a PP group of size 2 with the module's existing `_fake_pp` helper, and checks that `maybe_share_target_embed` attaches the target's embedding.
