# [Core][Attention] Resolve per-layer KV dtype in attention runtime

[Upstream PR](https://github.com/vllm-project/vllm/pull/56155) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

Resolve per-layer KV-cache encoding in the attention runtime, keeping allocation
specs focused on physical storage. First prerequisite for #56156 and #56116.

## Claims

- Add a default-`None` `QuantizationConfig.get_kv_cache_dtype(prefix)` hook.
- Let FlashInfer resolve the encoding from loaded attention layers when the
  global dtype is `auto`; explicit global settings retain precedence.
- Reuse existing storage-`dtype` / `kv_quant_mode` grouping for FP8 versus NVFP4.
  Neither GPU runner nor `AttentionGroup` is changed.
- Normalize equivalent read encodings (`fp8` / `fp8_e4m3`, NVFP4 scale-search
  variants), while rejecting incompatible encodings within a group.
- Preserve the existing physical quantization mode when merging sliding-window
  MLA specs. No new logical-dtype merge assertion is introduced.

## Validation

- Scoped pre-commit checks pass, including Ruff, formatting, test tethering and
  repository mypy (Python 3.11):
  `pre-commit run --hook-stage manual --files <incremental changed files>`.
- Retain alias normalization, incompatible-encoding rejection, and the
  sliding-window MLA merge regression. The latter fails against the pinned
  base implementation and passes with this change under CPU source isolation.
- Replace manual dtype assignment with real `Attention` and FlashInfer metadata
  constructors in the added pytest coverage: per-layer FP8/NVFP4, explicit
  global override and the inherited default-`None` hook.
- Local source-isolated checks pass eight resolver/merge test-body cases, 36
  resolver combinations and four `Attention.__init__` cases with unrelated
  backend/runtime dependencies isolated. Negative controls detect a missing
  hook, wrong global precedence, missing alias normalization and missing
  incompatible-format validation. These are not full-vLLM pytest results.
- The new GPU-backed constructor pytest cases have not been run. Local full
  pytest collection stops at missing `tblib`. Fresh GPU/CUDA-graph/serving
  validation remains pending; no accuracy/performance claim.

## Details

Adopts [Lucas's suggested simplification](https://github.com/LucasWilkinson/vllm/pull/6)
in response to [the grouping-key review](https://github.com/vllm-project/vllm/pull/56155#discussion_r4420136532).
It also addresses [the allocation-spec review](https://github.com/vllm-project/vllm/pull/56155#pullrequestreview-5475374302)
and [merge-assertion question](https://github.com/vllm-project/vllm/pull/56155#discussion_r4159751019).

The physical spec already separates the formats produced by #56116. E4M3 and
E5M2 share a physical spec but are different read encodings, so combining them
within one group remains an explicit error. ModelOpt's proposed mapping only
produces `fp8_e4m3` and `nvfp4`.

Logical encoding stays on attention layers, not `AttentionSpec`; format lookup
is initialization work, not a per-token lookup or new GPU synchronization.
The hook defaults to `None`, so this PR does not enable ModelOpt mixed KV.
#56156 handles allocation and #56116 activates recipes.

Tests now live beside the attention code. `tests/v1/worker/test_attn_utils.py`
matches main; compatibility tests for unchanged allocation/full-MLA code were
removed. This follow-up changes tests only, not production behavior.
