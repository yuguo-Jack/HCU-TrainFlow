# [ROCm][BugFix] Trim MoE GEMM input to valid token prefix 

[Upstream PR](https://github.com/vllm-project/vllm/pull/53108) · state: open · merged: False

## Original PR description


## Purpose
AITER's ROCm `fused_moe` (`AiterExperts`) silently corrupts its own output
(returns all-zero rows) when the allocated input buffer is much larger than
the real number of valid tokens it's asked to process. This is the normal
case for EP dispatchers like MoRI, which pre-allocate a worst-case buffer
(`max_num_batched_tokens * world_size`) while real per-step token counts are
usually a handful per rank. `AiterExperts.apply()` passed the full buffer
straight to `rocm_aiter_fused_experts()` even though `num_local_tokens`
identifies the real valid prefix.

Confirmed independent of any EP dispatcher via a standalone microbenchmark
calling AITER's `fused_moe()` directly against a from-scratch reference GEMM:
AITER zeros the valid rows whenever the buffer-to-valid-token ratio is large
enough, regardless of routing pattern.

**Fix:** in `AiterExperts.apply()`, slice `hidden_states`/`topk_weights`/
`topk_ids`/`a1q_scale` down to the valid prefix before calling
`rocm_aiter_fused_experts()`, then scatter the result into a zero-initialized
output buffer of the original shape (padding rows are never read downstream).
Applied unconditionally — no feature flag, since this is a correctness fix,
not an opt-in behavior change.

Under CUDA-graph capture, a live `.item()` read of `num_local_tokens` is
illegal, so the bound is instead a static worst-case value
(`graph_bs * topk * dispatch_group_size`) under full-graph capture with a
uniform batch, or trimming is skipped entirely when no safe bound exists
(e.g. piecewise cudagraphs).


## Test Plan

Hy3-preview (192 experts, top-8, BF16) deployment,
`--all2all-backend mori_high_throughput`, non-disaggregated, under DP-based
wideEP (`-tp 1 --data-parallel-size <N>`) and TP-based EP (`-tp <N>`, no DP).
Two checks per config: a 10-prompt known-answer probe (greedy) and full
GSM8K-1319 (5-shot, greedy).

At DP EP32 (4 nodes), ran a full 2x2 ablation — neither fix / each fix alone
/ both together — against a companion MoRI `combine()` fix
(#52639 ), since both defects trigger simultaneously
there. 
## Test Result

**EP32 ablation (4 nodes) — both fixes needed together:**

| Variant | Probe | GSM8K-1319 |
|---|---|---|
| Neither fix | 0/10 (gibberish) | 0.23% (71.0% invalid) |
| #52639 fix only | 0/10 (still gibberish) | 0.08% (66.9% invalid) |
| This trim fix only | 7/10 (incoherent misses, not gibberish) | 66.8% (1.9% invalid) |
| Both fixes | 10/10 | **92.8% (0.0% invalid)** |

Neither fix alone reaches parity: `combine()` alone makes no measurable
difference on the unfixed AITER defect; this trim alone recovers most of the
way but leaves visible incoherence. Both are independently necessary and
insufficient — only combined reaches the ~93% ceiling.

**Full matrix, both fixes :**

| Config | Nodes | Probe (before) | GSM8K-1319 (before) | Probe (after) | GSM8K-1319 (after) |
|---|---|---|---|---|---|
| EP8  | 1 | 10/10 | 94.24% | 10/10 | 93.33% |
| EP16 | 2 | 10/10 | 92.49% | 10/10 | 92.65% |
| EP32 | 4 | **0/10** | **0.15%** | 10/10 | **93.56%** |


## Unit Tests



### `tests/kernels/moe/test_rocm_mori_moe_ep.py`

Drives the real production data flow directly — real MoRI `InterNodeV1` dispatch + real AITER GEMM (`AiterExperts.apply()`) + real MoRI combine — across real multi-node hardware, reusing dispatch buffers across repeated (big round, small round) cycles to mimic real serving buffer reuse. Proves the actual real-world consequence: without the fix, a real, valid token's final *combined* output comes back wrong (all-zero), not just that some GEMM buffer contains garbage. Requires ≥2 real nodes with RDMA + `mori` installed — not routine-CI-friendly, intended as a hardware verification test.

**Run** (one command per node, `<0..N-1>` = that node's rank, `<node0-ip>` = rank-0 node's address, works at 2 nodes/EP16 or 4 nodes/EP32):
```bash
MASTER_ADDR=<node0-ip> MASTER_PORT=29525 \
torchrun --nnodes <N> --nproc-per-node 8 --node-rank <0..N-1> \
    --rdzv_backend=c10d --rdzv_endpoint=<node0-ip>:29525 \
    -m pytest -v -s tests/kernels/moe/test_rocm_mori_moe_ep.py
```

**Results:**

| Config | Fix present | Fix reverted |
|---|---|---|
| EP32 (4 nodes) | `1 passed` | `1 failed` — `AssertionError: MoRI dispatch/combine returned all-zero output for real tokens after buffer reuse` |
| EP16 (2 nodes) | `1 passed` | `1 failed` — same assertion |

Reproduced across multiple independent runs/node allocations in both directions. Note: real EP16 e2e serving doesn't show a visible GSM8K accuracy drop, but this test reproduces the underlying defect at EP16 too — the corruption mechanism isn't exclusively an EP32-scale phenomenon, it's just rare/diluted enough in ordinary EP16 traffic not to move the aggregate accuracy metric.
