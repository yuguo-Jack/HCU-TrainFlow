# [ROCm][Perf] Retune the gfx950 fp32 router GEMM for 384-512 experts

[Upstream PR](https://github.com/vllm-project/vllm/pull/64271) · state: open · merged: False

## Original PR description

## Purpose

DeepSeek-V4 / V4.1 compute their fp32 router logits on gfx950 with
`_rocm_fp32_router_gemm_kernel` at up to 32 tokens, once per MoE layer per step
(40 times per decode step on DeepSeek-V4.1-Flash). The fp32 router weight is
384 x 5120 (7.9 MB per layer). The model streams 40 of them per step, so in
decode every call reads its weights from HBM, not from MALL.

The kernel ran with `num_stages=1`. Each program walks K in dependent
iterations, so at 16 tokens the call reaches about 1 TB/s on the weights.
This retunes the launch table for 256 < num_experts <= 512 with a second
pipeline stage and larger K blocks. It came from a sweep in which every call
streams its weights from HBM: 48 distinct weight copies per CUDA graph,
E=384 and 512, K=5120. `_launch_config` now also returns `num_stages`. Other
expert counts and bf16 weights keep their current configs (`num_stages=1`).

## Test Plan

- `pytest tests/kernels/test_rocm_fp32_router_gemm.py tests/kernels/test_fp32_router_gemm.py`
  on MI355X (gfx950). `test_rocm_fp32_router_gemm_matches_reference` runs every
  token count from 0 to 32 at E=384 (K=5120 and 7168) and E=512 (K=2560), so it
  covers each new bucket (<=2, <=4, <=8, <=16, 17-32); K=5120, E=384 is
  DeepSeek-V4.1-Flash's shape.
- CUDA-graph timing of the old and new configs through the real kernel, 48 distinct
  weight copies per graph (so the weights never fit in MALL), K=5120, bf16
  activations. The new BLOCK_K values reorder the fp32 reduction, so the table
  gives both configs' error against an fp64 reference and against `F.linear`,
  and the number of rows whose top-6 expert set differs from fp64's.

CI hasn't run: `pre-run-check` is a label gate. `pre-commit` and the tests here
were run locally.

The new config's error is the old one's size, and neither flips a top-6 set.
An earlier, separate sweep session at E=384 agrees within 5% on both configs
(new: 3.57, 3.87, 4.43, 5.12, 5.18, 7.11, 7.21, 9.72, 10.23 µs at M = 1, 2, 4,
6, 8, 12, 16, 24, 32). E=512 has one session.

At 16 decode tokens that is about 2.1 µs x 40 layers, roughly 0.09 ms per
DeepSeek-V4.1-Flash decode step (TP4 TPOT about 9.2 ms).
In the same sweep, a variant that computes several experts per program and a
`tl.dot` fp32 tile were both slower. Above 32 tokens, `F.linear` stays the
dispatch; the Triton kernel only beats it at 64 tokens (16.1 vs 17.7 µs).
