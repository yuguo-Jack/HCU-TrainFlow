# [Bugfix] Keep text after DeepSeek V3.1 tool calls

[Upstream PR](https://github.com/vllm-project/vllm/pull/59589) · state: open · merged: False

## Original PR description

## Overview

The DeepSeek V3.1 tool parser dropped any text that came after a tool-calls block on the non-streaming path. Streaming already returned that text. This is the same gap as #56263. #56265 covers the V3 parser only. This change is the V3.1 parser, which is a separate file and still registered as `deepseek_v31`.

## Claims

- `extract_tool_calls` returns the text before the tool-calls block plus the text after `tool_calls_end`.
- A missing end marker keeps the old behavior: prefix only.
- Tool names and arguments are unchanged.
- Streaming is not modified.

## Validation

The non-streaming cases were run here with a tiny in-memory tokenizer: prefix only, prefix plus suffix, and suffix only. All three returned the expected content and tool names. `ruff check` and `ruff format --check` passed on the two files.

The existing unit tests download `deepseek-ai/DeepSeek-V3.1` and were not run on this machine. Importing vLLM here fails before the tokenizer step.

```bash
pytest tests/tool_parsers/test_deepseekv31_tool_parser.py
```

## Details

`extract_tool_calls` used to slice at the start marker and ignore the rest. Streaming emits a content delta once the tool-call start and end counts match again, so the text after the block reaches the client only on the streaming path.
