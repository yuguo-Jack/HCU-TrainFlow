# [Model][Qwen4Exp] Run routed experts on DeepGEMM MegaMoE (MXFP8 or MXFP4)

[Upstream PR](https://github.com/vllm-project/vllm/pull/64315) · state: open · merged: False

## Original PR description



## Overview

Runs Qwen4Exp (Qwen3.8-Flash-Next) routed experts on the DeepGEMM MegaMoE backend (`--kernel-config '{"moe_backend":"deep_gemm_mega_moe"}'`, built on `DeepGemmMegaMoEExperts` from #61538). The 128x128 block-FP8 experts of the official checkpoint are requantized at load time to MXFP8 (default) or MXFP4 (`--quantization-config '{"moe":"mxfp4"}'`).

## Claims

- Qwen4Exp can serve with `deep_gemm_mega_moe` on Blackwell with expert parallelism (TP=1; scale out with DP).
- Accuracy: MXFP8 and MXFP4 MegaMoE both pass non-inferiority against stock FP8 on AIME25, AIME26, GPQA-Diamond and MMMU-Pro on the same vLLM commit (table below).
- B300, vs the default MoE backend on the same commit:
  - TP1 prefill throughput: +12-13% (MXFP8), +15-16% (MXFP4).
  - DEP4 decode output throughput: +13-17% (MXFP8), +23-25% (MXFP4); mean TPOT -10-13% / -18-20%.
- Weight loading: requantization adds ~10 s on a TP1 engine (58 s stock vs 67 s MXFP8 / 72 s MXFP4).
- Works with layerwise reload and chunked weight updates.

## Validation

All runs: 8x B300 SXM6 nodes, vLLM nightly `edad8b03c5` plus this patch. Checkpoint: `Qwen/Qwen3.8-Flash-Next-FP8`. A later cleanup removed comments, unreachable branches and redundant tests without changing numerics, and the unit tests were re-run on it. The branch is now rebased onto `f81a414fae`; the upstream changes in between that touch these files move EPLB replica mapping into MegaMoE staging (only active with EPLB) and change fused-shared-expert selection for the default Qwen4Exp MoE block.

### Unit tests

`pytest tests/models/qwen4_exp/test_mega_moe.py`: 10 passed (~60 s) on B300. The tests cover:
- format selection from `quantization_config`, including `ignore` and `targets`;
- requantization matching DeepGEMM's own casts;
- loading into the kernel layout on one EP rank of two, batched requantization bitwise equal to per-expert requantization;
- weight and scale arriving in separate `load_weights` calls, and the strict post-load check on an incomplete pair;
- layerwise reload replacing the experts in the original storage;
- MXFP8 and MXFP4 experts end-to-end through the MegaMoE kernel against a dequantized reference.

## Details

**Requantization.** MegaMoE takes MX, NVFP4 or BF16 experts, not 128x128 block FP8 with FP32 scales.
- Each EP rank keeps only the experts it owns and stages each shard on the GPU as it arrives.
- Once a projection's owned experts have arrived, the rank requantizes them in a few batched calls, using DeepGEMM's `per_token_cast_to_fp8` / `per_token_cast_to_fp4` with UE8M0 scales over 1x32 groups. MXFP8 is exact whenever a block scale is a power of two.
- Shards are written through each parameter's own `weight_loader`. This is what lets layerwise reload (`reload_weights`, NCCL/IPC weight transfer) buffer and replay the writes into the original storage.
- Chunked updates can split an expert's weight from its scale. The end of each `load_weights` call keeps such half pairs for the next call. A pair still incomplete after loading fails in `process_weights_after_loading`, through a small `QuantizeMethodBase`, the same pattern as `Step5MegaMoEExperts`.

**Format selection.** There is no new flag: the existing online-quantization config chooses the format.
- `moe: mxfp4` or `mxfp8` picks the format, and `ignore`/`targets` patterns apply per layer.
- Requantized layers show up in the online quantization summary.
- The MTP drafter's config does not carry `--quantization-config`, so the drafter's experts stay MXFP8.

**Shared expert.** Qwen4Exp gates the shared expert per token with `sigmoid(shared_expert_gate(x))`. MegaMoE's fused shared expert has no such gate, so the shared expert stays unfused.
- It runs on an auxiliary stream while the router and top-k run, and it joins before the MegaMoE launch, which needs every SM.
- `VLLM_DISABLE_SHARED_EXPERTS_STREAM` turns the overlap off.
- The gated output is added to the routed output in the same order as the default path.

**Other changes.**
- The DeepGEMM MegaMoE warmup now covers Qwen4Exp blocks, and its cache key includes the routed-expert format.
- Docs: a re-quantization table row and example in `docs/features/quantization/online.md`.
- CI: a new B200 step (`qwen4-exp-mega-moe-b200`) runs the tests. They are not added to the H200 Qwen4 Exp job, where the SM100 kernel test would be skipped.

**Limitations.**
- TP>1 is rejected: it needs sequence-parallel inputs on the HC path. Use DP+EP instead.
- Only 128x128 block-FP8 checkpoints are supported; experts the checkpoint leaves unquantized fail with an explicit error.
- NVFP4 is not wired up. At Qwen4Exp's intermediate size (640, not a multiple of 256) the pinned DeepGEMM `nvfp4_mega_moe` kernel desynchronizes its two-tile stages: the TMA warps issue `ceil(640 / 256) = 3` stages per L2 task and the MMA warp consumes `floor = 2`. Large launches hang and small ones return wrong output. That needs a DeepGEMM fix first.
- EPLB plumbing comes from `DeepGemmMegaMoEExperts` but was not exercised here.

**Size.**
- `vllm/models/qwen4_exp/nvidia/mega_moe.py` is ~340 lines and model-local: requantization, loader and block.
- Elsewhere: +13 lines in `model.py`, +4 in `mtp.py`, +13 in the warmup.
- No changes to the generic MegaMoE layer, the scheduler or the model runner.
