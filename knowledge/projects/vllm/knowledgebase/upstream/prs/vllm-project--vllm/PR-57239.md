# [Model][ROCm][DCP] DeepSeek-V4 decode context parallelism

[Upstream PR](https://github.com/vllm-project/vllm/pull/57239) · state: open · merged: False

## Original PR description

## Purpose

Model-layer DCP support for DeepSeek-V4 (hybrid SWA + compressed KV), per RFC #57228. Builds on the merged Kimi-K3 DCP framework from #51705 + #53598 and transplants the validated mechanisms from the inactive #44573 w/ co-author credit to @baonudesifeizhai. Adds onto current main, with ROCm/AITER leg being validated on 8xMI355X.

**Draft / WIP**: opened early for visibility and design alignment, not yet ready for review. Currently only contains the foundations for the functionality.

- [x] ContextParallelLayout + Triton ownership helpers (interleaved token/slot ownership, logical block table addressing)
- [x] DSV4 DCP merge ops: sink-after-merge via the consolidated v1/attention/ops/dcp.py collectives, compressor softmax reduce
- [x] Compressor partial-stats kernel (per-rank online-softmax pooling)
- [x] Compressor finalize kernels (owner-masked insert: compressed KV + indexer K caches)
- [x] Scheduler geometry: supports_context_parallel spec flag + logical_block_size composed with dcp_world_size_for_kv_cache_spec
- [x] Metadata localization (SWA / indexer / compressed slot mapping)
- [x] Attention wiring (gather-Q, sink-free local attend + LSE, merge) w/ C4A decode top-k localization fix
- [x] ROCm kernels: LSE + deferred sink in the sparse decode/prefill Triton kernels, Triton stable-topk twin for the indexer merge
- [x] Tests + parity (tp8 vs tp8×dcp{2,4,8}, passkey + GSM8K) + AgentX benchmark on 8x MI355X


## Not duplicating

#44573 is the direct ancestor of this PR (inactive since June, NVIDIA-only, before DCP framework consolidation). This PR series is it susccessors on the current main, validated and meant for ROCm. No other open PR or issue implements DSV4 DCP (checked 2026-09-16).

@baonudesifeizhai Hi, thanks for taking a look! your original work on 44573 has been a very helpful reference.

(1) on the benchmarks: yes, we will provide these once the implementation is complete. currently the scheduler-side geometry and the DCP-aware write paths are done, and the remaining components are the indexer top-k merge, attention prefill and decode wiring, and ROCm kernel LSE changes. We will need a few more days of work before the full prototype, then we will run benchmarking and accurcacy checks on MI355X. currently we are only running pcp=1 however, and we are focusing on dcp for the kv cache capacity wins.

(2) also, just a minor heads up that we are deviating from the 44573 design by only sharding the compressed KV cache and the indexer K cache (the big ones that scale with both num_requests and sequence length). This is for (1) mainline alignment: the merged K3 stack (#51705/#53598) establishes sharding only for the MLAAttentionSpec groups and not the smaller ring buffer and SWA caches. So we want to be more in line with the current main. And (2) the SWA cache and rings are constant size, so I think sharding them does not save much HBM headroom but still requires the new corss-rank compressor collectives. I think it would be better for performance to replicate these, we can also then continue to run the existing fused ROCm kernels with no collectives.

TLDR: benchmarks will come after prototype lands (hopefully within a few business days), and we made some design decisions about which cache to shard that deviate from 44573.
