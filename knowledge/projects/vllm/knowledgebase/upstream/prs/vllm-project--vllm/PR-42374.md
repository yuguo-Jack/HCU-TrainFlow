## Code Review

This pull request standardizes the KV cache physical layout and allocation logic across all attention backends in the V1 engine, implementing RFC #42082. It introduces a unified KVCacheLayout descriptor and standardizes logical shapes to lead with the block dimension, typically packing key and value data into the final dimension. This consolidation simplifies the model runner and KV connector logic by removing backend-specific shape and stride overrides. Feedback highlights a critical regression in GPUModelRunner where a layout heuristic is ambiguous when num_blocks is 2, leading to potential crashes. Furthermore, performance regressions were identified in the FlashInfer and FlexAttention backends due to memory copies triggered by .contiguous() calls and non-contiguous reshape operations in the hot path.

- orozery · comment · 2026-05-13T08:18:41Z · [source](https://github.com/vllm-project/vllm/pull/42374#issuecomment-4438848299)

I think we should aim for:
1. KV transfer performance (bigger per-head/per-block IO size), assuming it does not harm model execution performance
2. KV connector simplicity

In terms of (1), looks like this PR keeps status-quo, i.e. use cross layers only for simple models (single group, single page size).
That's fine for start, but I think we should keep in mind that other models can also be optimized.
Specifically, we can still allocate a single tensor even for multiple groups, by using num_groups, group_size as an alternative to num_layers. This means allocating a single unified tensor for all `kv_cache_config.kv_cache_tensors`.

For (2), we currently keep using the existing `register_kv_caches`, which I think is lacking:
- It still passes a per-layer tensor. While this is required for layer-wise based transfers, most connectors use block-level transfers.
- It's not clear how to efficiently derive transfers of the given tensors.

I see that #42082 mentions adding util functions to `kv_cache_spec` for connectors to derive data of tensors, but I guess this is planned as a follow-up as I don't see it in this PR.
I think it would be better to agree on this API first before making any changes.
In particular, I feel like the connector API should be completely standalone, so it should define its own alternative to `KVCacheSpec` instead of importing the existing one. cc @markmc 

We want to force future implementations of worker-side KV cache allocations/reshaping to support KV connectors.
We can do so by requiring the model runner "allocation/reshaping" function to also return KV layout metadata for connectors.

I noticed that this PR changes the default physical layout.
When I introduced the cross-layers layout, I actually created a separate non-default allocation flow.
One of the reasons for that was not to break existing connectors which may assume the default layout.
This PR changes that.
I'm actually in favor of that, as I think it's hard to maintain 2 allocation paths.
But we should consult with existing in-tree connectors maintainers on this, and allow them to adapt. cc @NickLucche

- orozery · comment · 2026-05-14T06:02:49Z · [source](https://github.com/vllm-project/vllm/pull/42374#issuecomment-4448074740)

> KV cache groups already share the same underlying tensor when possible (via `shared_by`), backed by a single contiguous allocation. What additional optimization are you suggesting? what am I missing?

Let me explain using an example:
Say you have a model with 12 sliding-window layers and 12 full attention layers (e.g. gpt-oss-20b).
vLLM will split the layers into 2 groups:
Group0: 12 full-attention layers
Group1: 12 sliding window layers

So you have 2 groups, with each group size is 12.
For this setup, vLLM defines 12 KVCacheTensor.
Each tensor will be shared by 2 layers: 1 from each group.
For example:
Tensor 0: layer0 (full attention), layer1 (sliding window)
Tensor 1: layer2 (full attention), layer3 (sliding window)
...
Tensor 12: layer22 (full attention), layer 23 (sliding window)

Now recall that allocation of Block IDs is per-group.
When we copy KV data, we get the block IDs to copy, and we translate them to physical addresses on the allocated tensors.
So if for example we have a block ID 1234 for group0, we need to map it to [tensor[1234] for tensor in kv_cache_tensors] (assuming all tensors are num-blocks first).
So a single block maps to 12 (=group_size=num_tensors) copies.
We can save that factor, yielding a single copy per block.

To do so, instead of allocating 12 tensors, we can allocate 1 unified tensor with shape:
[num_blocks, group_size=12, ...]
Or even better (for HND):
[num_blocks, num_heads, group_size, ...]

This was implemented in #37885.
You can see the performance results there,.
It's a major improvement for KV offloading performance (and should be for P/D as well).



- orozery · comment · 2026-05-14T06:13:33Z · [source](https://github.com/vllm-project/vllm/pull/42374#issuecomment-4448135644)

So currently, for multi-group models, vLLM allocates tensors which are shared by multiple layers of *different groups*.
However, each block in the tensor contains data only for a *single layer*.

The insight is we can allocate super-blocks, shared by *multiple layers* of the *same group*.
Conceptually, this is the same as what we already todo in cross-layers layout today (in main), with [num_blocks, num_layers] - i.e. super-blocks where each super-block contains KV data for ALL layers.

In the case of multiple groups, instead of packing all layers into a block, we only pack all layers in a single group.
