# [Quantization] Add mxfp4_hadamard32_moe online quantization

[Upstream PR](https://github.com/vllm-project/vllm/pull/65398) · state: open · merged: False

## Original PR description



## Overview

Adds `mxfp4_hadamard32_moe`: online W4A4 MXFP4 for MoE experts with a 32-wide Hadamard rotation, running on Humming, with dense layers left in bf16. It extends `QuantSpec.hadamard_size` from #62750 to MoE, filling that PR's "allow MoE once validated" TODO.

**Stacked on #62750 and #56606. Only the last commit (`abf01611eb`) belongs to this PR.** It stays a draft until both merge.

## Claims

- `--quantization mxfp4_hadamard32_moe` quantizes MoE experts to MXFP4 weights and activations, with a 32-wide Sylvester Hadamard rotation. Linear layers stay unquantized.
- On Qwen3.5-35B-A3B it scores at the bf16 level on GSM8K, and higher than the same MXFP4 path without rotation in every run. The size of the gain varies by build (table below).
- `moe.hadamard_size` also works in `--quantization-config` for MXFP4 MoE weights. Other methods keep #62750's `NotImplementedError`.

## Validation

B300 (SM103), humming-kernels 0.1.18, single GPU. GSM8K, all 1319 questions, 5-shot, greedy, with `gen_prefix` disabling thinking.

| Run | No rotation (%) | `mxfp4_hadamard32_moe` (%) | Δ (paired McNemar) |
|---|---|---|---|
| This branch (stacked on #62750 + #56606) | 92.3 | 93.1 | +0.8 (p=0.23) |
| Same method on `main` (`e11a5ada53`), 2 runs | 92.3 | 93.6, 93.6 | +1.3 (p=0.053) |
| Same rotation through Humming's own online quant (`VLLM_HUMMING_ONLINE_QUANT_CONFIG`) | 92.2 | 93.7 | +1.5 (p=0.015) |

bf16 scores 93.3. "No rotation" is the plain `mxfp4` MoE shorthand on `--moe-backend humming`, with Humming forced to FP4 activations, so the only difference is the rotation. Repeat runs on one build are identical. The three runs differ in build and in weight quantizer (the third uses Humming's), so each gain should be read within its own row.

Reproduce:
```bash
vllm serve Qwen/Qwen3.5-35B-A3B --quantization mxfp4_hadamard32_moe --max-model-len 8192
```

## Details

**How it works**
- `Mxfp4HadamardOnlineMoEMethod` subclasses `Mxfp4OnlineMoEMethod`. It rotates expert weights along their input dimension with Humming's `process_input`, and quantizes them to the standard MXFP4 layout.
- It records the size on the Humming weight schemas, which `get_humming_moe_quant_config` already reads. The fused Humming experts then rotate the w13 input, and the w2 input after the activation, inside their input quantization. No new kernel is needed.
- It passes `kMxfp4Dynamic` to the Humming conversion so the experts run FP4 activations. The base online MXFP4 method passes no key and gets BF16 on Humming; I left that behaviour unchanged.

**Weight quantizer.** `mxfp4_quantize` uses the OCP scale, which rounds down and saturates the largest value in each block. With rotation, that cut the gain to +0.4 points (p=0.64). This method instead uses a round-up block scale (`2**ceil(log2(amax / 6))`), matching Humming's own quantizer. Its output has the same layout as `mxfp4_quantize`: scales and dequantized values match exactly, and only the sign of zero differs. On unrotated data the OCP scale is slightly better, so I only use the round-up scale in this method.

**Backend.** Humming is required, because it is the only MXFP4 MoE backend that fuses the rotation. `auto` selects it; any other explicit `--moe-backend` raises an error.

**Naming:** `mxfp4_hadamard32_moe` follows #62750's `mxfp4_hadamard32`.

**Limitations**
- The gain depends on the model. In a broader sweep, rotation helped Qwen3.5-35B-A3B and Qwen3.5-9B but hurt Qwen3-8B (W4A4 −7 points at H=32, p=4e-9). That's why this is an opt-in shorthand and not a default.
- Only one MoE model was evaluated end to end, on GSM8K only.
- Not validated with tensor or expert parallelism.
- On GPUs before SM100, loading fails with Humming's "no compatible input schema" error rather than a dedicated message.

**Not a duplicate:** #62750 covers linear layers only and leaves MoE as a TODO. #56606 is the loading fix this PR depends on. #63272 is ROCm linear fusion. #61993 rotates before RMSNorm.
