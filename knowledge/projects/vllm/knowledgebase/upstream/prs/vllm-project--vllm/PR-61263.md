# [Perf][HiSparse] Reduce residency hash probes

[Upstream PR](https://github.com/vllm-project/vllm/pull/61263) · state: open · merged: False

## Original PR description

Related to #60072.

At top-k 2,048, the resolver can fill 2,048 of its 2,049 hash slots. Looking up cached rows that aren't selected for the current step then requires long probe chains.

This lets the table grow toward the existing four-slots-per-position target, within the device's shared-memory budget.

Default shared memory rises from 26,148 to 75,300 bytes per block. Resident-only calls cost an extra 0.16–0.90 µs in the kernel checks. This is separate from #60103's slot-invalidation and all-resident work.

On **4 H200s, TP4, GLM-5.2-NVFP4**, with 32 concurrent requests, 16,384-token random prompts and 1,024-token outputs, median throughput improved **130.26 → 133.45 tok/s (+2.45%)**. Three runs each ranged from 130.21–130.32 and 133.36–133.69 tok/s. Reverting gave 130.01 tok/s.

This used FP8 KV, 10 GiB GPU KV per rank, a 64 GiB host pool, CUDA graphs, and no prefix caching. The serving comparison predates the rebase (`d61081dc` → `94b81a59`) and used targeted native builds with `VLLM_GPU_SYNC_CHECK=error`. Post-rebase serving, speculative serving, and other GPU architectures haven't been benchmarked.

On the final commit, `b605dfa0`:

- **1 H100 80GB:** 106 focused tests and 4 end-to-end tests passed with MRV2 and GPU sync checking enabled.
- **1 H200:** 18 resolver cases matched baseline indices, ownership, and LRU state. The 4× target beat 2× in every host-backed case tested.
- Pre-commit passed.

The earlier serving run also passed 12 cache-state comparisons and four short output checks. No full model-quality evaluation was run.
