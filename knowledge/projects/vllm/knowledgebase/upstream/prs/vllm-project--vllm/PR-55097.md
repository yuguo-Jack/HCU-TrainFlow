# [Bugfix][KV Connector][Mooncake] Drop NULL_BLOCK_ID pairs after P/D block alignment

[Upstream PR](https://github.com/vllm-project/vllm/pull/55097) · state: open · merged: False

## Original PR description

## Purpose

In a disaggregated P/D deployment, Mooncake can write KV into the wrong token block and the consumer reads it back as real KV, with no error raised anywhere. The fix touches three functions in `mooncake_connector.py`; the rest of the diff is tests.

All three sit on the path a request's block ids take from the scheduler to the transfer engine:

```diff
  producer, scheduler side                    producer, worker side
  ────────────────────────────────────        ─────────────────────────────────
  SlidingWindow / RSWA / Mamba manager
    frees a block but keeps its slot:
    req_to_blocks[i] = null_block  (id 0)

  get_block_ids_for_computed_tokens()
    ids[:num_valid_blocks] per group          head slice, keeps the prefix
    -> [0, 0, 0, 0, 0, 6, 7]

+ request_finished()                          decides whether to wait at all
    delay_free_blocks = ...
    └─ get_sw_clipped_blocks()
         blocks[-blocks_per_sw[i]:]           tail slice, per group

  build_connector_meta ─────────────────────▶ record_send_reqs
                                                send_meta.local_block_ids = ...

+                                             _build_transfer_params()
                                                align producer list to consumer's
                                                src = local_base  + id * block_len
                                                dst = remote_base + id * block_len

                                              transfer engine writes src -> dst
```

`_build_transfer_params` is where a block id stops being a list entry and becomes an address: the producer computes both ends of every copy, and the consumer's list arrives over the wire. Placeholder ids are 0, so `local_base + 0 * block_len` is a legal pointer into the placeholder's own memory — which is why nothing downstream raises.

Which deployments are exposed depends on where those placeholders land, because neither slice above removes an interior one:

| model / config | placeholders land | reaches `_build_transfer_params` |
|---|---|---|
| R-SWA | **middle gap** | **always** — the clip is keyed on `SlidingWindowSpec` |
| Mamba, `align` mode | **arbitrary interior index** | **always** — same |
| sliding-window attention | leading prefix | at some prompt lengths |
| prefix-cache padding | leading prefix | at some prompt lengths |
| the two rows above, with `--disable-hybrid-kv-cache-manager` | leading prefix | **always** — the clip is a no-op |

`_build_transfer_params` is the corruption; `request_finished` is a smaller correctness bug earlier on the same path.

### 1. `request_finished`

```python
delay_free_blocks = any(len(group) > 0 for group in block_ids)   # reads block_ids raw

if delay_free_blocks:
    self._reqs_need_send[request.request_id] = (
        request,
        self.get_sw_clipped_blocks(block_ids),                    # clipped only here
    )
```

It reads the list before any clipping, so it sees every placeholder the scheduler produced — `[0, 0, 0, 0, 0, 6, 7]` for a 100-token prompt with a 16-token window, 5 of 7 ids. Asking only whether a group is non-empty means a request with nothing real left still counts as having a transfer pending: **its blocks stay held rather than released, and an async send is registered for content that does not exist**. This PR asks whether any *real* block id is left instead, so such a request frees immediately.

Freeing early is only correct if the transfer id goes to `_reqs_not_processed` on the way out: the worker's send-map entry for this request is otherwise never reclaimed, and the consumer waits for a transfer that never starts.

<details>
<summary><b>Where that entry comes from</b> — and why draining the set is the only thing that reclaims it</summary>

A second scheduler callback puts an entry in the worker's send map long before `request_finished` runs:

```text
scheduler                                worker
─────────────────────────────────        ─────────────────────────────────
update_state_after_alloc
  _reqs_need_send[req] = (req, [])
            │ build_connector_meta
            └───────────────────────────▶ record_send_reqs
                                            block_ids empty, so:
                                            SendBlockMeta(expire_time=inf)

  ... request runs ...

request_finished
  no real block ids left  ──▶ free now
  _reqs_not_processed.add(transfer_id)
            │ build_connector_meta
            └───────────────────────────▶ record_send_reqs
                                            pops the entry
```

`inf` is the dataclass default, so the abort sweep never reclaims that entry; draining `_reqs_not_processed` is the only path that does.

</details>

### 2. `_build_transfer_params`

The filter is reached only by Mamba groups today, so this is what they already do:

```python
if is_mamba_group:
    local_group = [b for b in local_group if b != NULL_BLOCK_ID]
    remote_group = [b for b in remote_group if b != NULL_BLOCK_ID]

n_local, n_remote = len(local_group), len(remote_group)
...
elif n_local > n_remote:
    # Partial prefix cache hit: just read uncomputed blocks.
    local_group = local_group[-n_remote:] if n_remote > 0 else []
```

**Filtering before the alignment is the defect:** the alignment is what makes index `i` name the same token block on both sides. With a producer-side placeholder and a partial prefix cache hit, the whole group shifts by one:

```diff
  producer  [3, 4, 0, 5]        consumer  [7, 8, 9]        0 = NULL_BLOCK_ID

-  current ->    3   4   5
   consumer      7   8   9
+  this PR ->    4       5
```

Filtering first leaves the producer three entries long, so the tail trim never runs: `3` goes into `7`, which belongs to `4`, and `4` into `8`, which the producer has nothing for. **The consumer reads both as real KV, and no error is raised.**

This moves the filter after the alignment and drops pairs — a placeholder on either side removes that column from both lists, so lengths stay equal and index `i` keeps naming the same token block. Gating on group type goes away with it; `is_mamba_group` itself stays, as a field in the `n_local < n_remote` error log.

---

### Do placeholders get that far?

Both functions above assume the block ids they receive still contain placeholders. Two steps on the path from the scheduler slice the list, one at each end:

```python
# kv_cache_manager.py — head slice, per attention group
clipped_block_ids.append(ids[: cdiv(num_computed_tokens, spec.block_size)])

...

self._is_hma_required = (
    not vllm_config.scheduler_config.disable_hybrid_kv_cache_manager
    and any(
        not isinstance(g.kv_cache_spec, FullAttentionSpec)
        for g in kv_cache_config.kv_cache_groups
    )
)

...

def get_sw_clipped_blocks(self, block_ids):
    if len(block_ids) == 0 or not self._is_hma_required:
        return list(block_ids)
    return [
        blocks[-self.blocks_per_sw[i]:] if self.blocks_per_sw[i] > 0 else blocks
        for i, blocks in enumerate(block_ids)
    ]
```

Neither can remove an interior placeholder. The head slice keeps the prefix — exactly where SWA eviction and prefix-cache padding leave theirs. The tail slice is narrower than it looks: `blocks_per_sw` is `0` for any group whose spec is not a `SlidingWindowSpec`, so R-SWA and Mamba groups come back untouched, and `_is_hma_required` skips the whole function under `--disable-hybrid-kv-cache-manager` — the last row of the table above. Everything else on the path is assignment: `build_connector_meta` and `record_send_reqs` copy the list along.

<details>
<summary><b>Why this stayed latent</b> — the clip, its blind spots, and the one CI job that covers this path</summary>

The clip removes placeholders often enough that a value filter can look redundant. What it keeps is set here:

```python
sw_sizes_tokens = [
    (g.kv_cache_spec.sliding_window, g.kv_cache_spec.block_size)
    if isinstance(g.kv_cache_spec, SlidingWindowSpec)
    else (0, self.block_size)
    for g in kv_cache_config.kv_cache_groups
]
# cdiv(n_tokens, block_size) gives blocks/window; add 1 to
# conservatively account for boundary overlap.
self.blocks_per_sw = [
    cdiv(n_tokens, block_size) + 1 if n_tokens else 0
    for n_tokens, block_size in sw_sizes_tokens
]
```

The `+ 1` is a deliberate over-estimate, so whenever the in-window run is shorter than it, the slice reaches back into the null prefix.

Driving the real scheduler over `scheduler.py`'s own sequence (`remove_skipped_blocks()` then `get_block_ids_for_computed_tokens()`) across prompt lengths 64-160 with a 16-token window and `block_size=16`, placeholders survive the clip exactly when `(num_prompt_tokens + 1) % block_size == 0` — 6 of the 97 lengths tested:

```text
num_prompt_tokens   handed to the connector    after the clip
             111    [0, 0, 0, 0, 0, 0, 7]      [0, 7]     <- survives
             113    [0, 0, 0, 0, 0, 0, 7, 8]   [7, 8]     <- clipped clean
```

The survivors in that range are 79, 95, 111, 127, 143, 159 — every `block_size`-th length.

R-SWA escapes the clip on both counts:

```python
class RSWASpec(FullAttentionSpec):   # not SlidingWindowSpec, so the isinstance above skips it
    rswa_window: int                 # and there is no sliding_window value to clip by
```

So: mostly clipped on the common path, never clipped on the others, and silent when it does slip through. The one CI job that exercises this path end to end (`disaggregated_mooncake.yaml`) runs `Qwen/Qwen3-0.6B`, whose config sets `sliding_window: null` and `use_sliding_window: false` — no placeholder is ever produced in that run.

</details>

<details>
<summary><b>Notes on scope</b> — what the change assumes, one line that came with it, and what is deliberately left alone</summary>

**The consumer's list cannot hold a placeholder today.** They are dropped where it is built:

```python
# KVCacheBlocks.get_unhashed_block_ids_all_groups
[block.block_id for block in group
 if block.block_hash is None and not block.is_null]
```

The paired filter still checks that side. This list reaches `_build_transfer_params` deserialized from the other engine, so a guarantee that holds inside one process is not a guarantee at the boundary.

**The `n_local < n_remote` check now reads raw lengths.** It sits above the filter, so a placeholder can no longer push `n_local` under `n_remote` and trip it. Previously a filtered-away placeholder could, and the message — "local blocks(%d) < remote blocks(%d)" — would send whoever read it looking at block counts rather than at the placeholders that caused the shortfall. The other direction is now silent: a producer group that is all placeholders — `[0, 0, 4]` against `[7, 8, 9]` — used to trip this check once filtered, and now passes it, so the columns dropped below it are skipped without a log line. That is the consumer-side assumption in [One thing not verified](#one-thing-not-verified), reached from the other side.

**Two checks below the filter are load-bearing on it.** `if not any(local_block_ids_by_group)` and the per-group `if not local_block_ids` both have the "checks length, not content" shape, and are correct only because the filter above has removed the placeholders — `bool([0, 0, 0])` is `True`. They are left as they are, and the filter's comment now says they depend on it.

**One drive-by fix.** `record_send_reqs` drains `_reqs_not_processed` with a bare `dict.pop` under an `if` that only makes sense with a default; this PR doubles the paths into that set, so it now passes `None`.

**The same connector family already treats a null id as a hazard.** `mooncake/store/scheduler.py` asserts `NULL_BLOCK_ID not in block_ids` before use and filters by value where it cannot, so this PR is applying an existing house rule to the one path that missed it rather than introducing a new one.

**NIXL is not in scope.** Both `pull_scheduler.py` and `push_scheduler.py` share the ordering — `delay_free_blocks` from the raw list, `get_exchange_clipped_blocks` afterwards — but NIXL registers transfer descriptors over the whole block-index space rather than computing a pointer per request, so it is not a direct mirror. Also left alone: Mooncake gates the async-send path on `FINISHED_LENGTH_CAPPED` only, while NIXL also accepts `FINISHED_STOPPED`.

</details>

### One thing not verified

Reproducing needs a placeholder plus `n_local > n_remote` (a partial prefix cache hit) in the same request for `_build_transfer_params`; `request_finished` needs only the placeholder, since it reads the list before any clipping.

Not verified: dropping a pair leaves the consumer's block for that position unwritten, holding whatever its previous tenant left. The producer voided that position because it fell outside the window, so it should not be read — but that guarantee lives entirely on the consumer side, and this PR does not establish it. What the change removes is certain: the old paths wrote either the placeholder's own memory or another token's KV into that slot.

<details>
<summary><b>Each new test was checked against the pre-fix code</b>, not only the fixed code — five mutations and what each one breaks</summary>

- Replacing the paired filter with two independent ones, in the same position, fails the alignment test on both parametrized cases and the Mamba case. For Mamba the pointers differ by exactly one block — `[26368, 15872]` where `[26624, 15872]` is correct.
- Moving the paired filter back above the alignment fails two tests.
- Extending `blocks_per_sw` to cover R-SWA fails the clip test with `[0, 2, 5]` against `[0, 2, 0]`. The pre-existing `test_get_sw_clipped_blocks` does not catch this, since its config has no R-SWA group — that is what the new case is for.
- Reverting the `delay_free_blocks` change fails `test_request_finished_frees_immediately_when_all_null`.
- Dropping just the `_reqs_not_processed` hand-off fails the same test on its other assertion (`assert 'id-1' in set()`). That test guards both halves of the branch.

</details>

Worth stating plainly: **the Mamba file's existing placeholder coverage could not distinguish the old behaviour from the new one.** Its only such case is `producer=[0, 4]`, `consumer=[0, 7]` — holes at the same index, equal lengths — a shape where independent and paired filtering give identical results, and the whole file passed under both. The Mamba case added here uses the shape `align` mode actually produces.

No model evaluation — this does not touch model computation, and the pointer-level evidence above is the direct check. No end-to-end run either: the transfer path needs RDMA with `IPC_LOCK` and host networking, which is why CI confines it to one dedicated pool.
