# [Frontend] Recover malformed Harmony tool headers at parse time

[Upstream PR](https://github.com/vllm-project/vllm/pull/59387) · state: open · merged: False

## Original PR description

## Purpose

gpt-oss sometimes emits a malformed tool-call header, and vLLM then loses the tool call: the client receives raw text, or nothing, instead of a `function_call`. This PR fixes three related causes.

- **Remove the tool-header rendering shim.** `render_for_completion` returns exactly what `oss-harmony` renders.
- **Repair a metadata-spliced content type** (`... <|constrain|>commentary to=assistant <|constrain|>analysis to=python code<|message|>`), only after `StreamableParser.process()` rejects it.
- **Recover a complete JSON function call whose header never reached `<|message|>`**, only when `flush()` finds the parser stuck in a header at EOS.

Every repair runs only after the parser has already failed. Valid input stays on the unchanged pass-through path.

## Why the shim goes away

`oss-harmony` is public at [oss-harmony/harmony](https://github.com/oss-harmony/harmony), as declared by vLLM's `rust/Cargo.toml`. [`c16672a`](https://github.com/oss-harmony/harmony/commit/c16672a) documents both of its rendering changes as deliberate:

- channel-before-recipient matched the order emitted by gpt-oss tool calls and reduced BFCL failures
- always emitting `<|constrain|>` prevented reasoning after that token in long multi-turn conversations

The shim added in #55128 restored the old order and dropped the marker, so it works against both fixes. Natural failures in the new data below occurred only with the shim's rendering, not with the native rendering (see Validation).

## Parse-time recovery

### Metadata spliced into the content type

Recovery runs only when Harmony throws `unexpected tokens remaining in message header` at `<|message|>`. It isolates the current header, accepts only metadata-shaped corruption ending in a valid `code` or `json` type, removes the duplicated channel, recipient and constraint metadata, then replays the canonical header through a fresh parser.

### Header that never reaches `<|message|>`

gpt-oss can write a tool call's JSON arguments directly after the recipient:

```text
<|channel|>commentary to=functions.file_editor{"command": "str_replace", ...}<|call|>
```

In strict mode the parser buffers the stop token as header text, so `process_eos()` raises `Unexpected EOS while waiting for message header to complete` and `flush()` returns the whole message as text. The repair in `flush()` accepts only:

- `[<|start|>assistant]<|channel|>{analysis|commentary} to=functions.<name>`, with the name among the declared tools when a tool list is supplied;
- optional whitespace, or one real empty `<|constrain|>` marker, before the argument object;
- one complete JSON object, ending in `<|call|>`.

It keeps the original argument token ids, so ordinary text that spells a control token (a literal `<|call|>` inside a JSON string) stays text. Python, browser and undeclared recipients, truncated or non-object JSON, other stop tokens, and any authored words in the header are left exactly as today.

The unterminated-header case, the `flush()` hook and the replay approach come from a report and proposal by `strange-technologies` in [this comment](https://github.com/vllm-project/vllm/pull/59387#issuecomment-6275207552); the commits carry a `Co-authored-by` trailer. Their version re-encoded the decoded arguments with `allowed_special="all"`, which turned a literal `<|call|>` inside a JSON string into a real stop token and truncated the arguments, and it accepted any recipient. Both are covered by regression tests here.

This complements #59225, which normalizes a recipient after a successful parse. It keeps #59254's fallback for unrecognized `HarmonyError`s. Raw-text fallback for headers containing model-authored words is outside this PR and overlaps #52055. For context, #45736 describes the same missing-delimiter failure on the `final` channel.

### Natural failures on gpt-oss-120b

Real agent loops (public OpenHands 0.59.0 prompt and tool schemas, real repositories, tool calls executed in confined containers), default sampling, raw output token ids captured.

- **145 exact natural occurrences** of the missing-`<|message|>` shape from three prompts, plus 26 nearby complete-object variants, none forced or prefilled.
- On one request chosen before sampling: **5/80 (6.25%, 95% Wilson 2.70-13.81%)**. In executing agent rollouts on the unfixed head: **6/80 (7.5%)**, every one stopped with no tool call. On the fixed head: 4/80, and all four calls executed and the loop continued.
- Every positive used the shim's rendering of the history. Matched histories rendered natively gave **0/3,840 (0-0.10%)**. The median next-token probability of the failing branch was about 14 times higher under the shim rendering.
- Replaying the original token ids: the previous head and `main` recover 0 of the 145 exact cases; this head recovers all 171 complete-header cases (145 exact, 24 empty-marker, 2 whitespace) in bulk, streaming at chunk sizes 1/4/11, and the Responses context path, with every argument token sequence preserved. All 2,699 other malformed outputs parse identically before and after.

Limits. The exact request, `str_replace` arguments and hardware of the original report are not reproduced. After adopting the native rendering, the benefit of the parser repair is unproven; it guards against a failure that only appeared under the removed rendering. These runs show continuation after a recovered call, not an accuracy improvement. The reproduction scripts and raw captures are kept outside the vLLM tree.

**The shape: a header that never reaches `<|message|>`**

The model writes the JSON arguments straight after the recipient:

**The change**

In `flush()`, when `process_eos()` raises, the change first checks whether the unterminated message is exactly `[<|start|>assistant]<|channel|>{analysis|commentary} to={recipient}{JSON object}[<|call|>|<|end|>]`. **Confirmed from your comment**

- **The mechanism.** With `oss-harmony` 0.0.11, the strict parser buffers `<|call|>` as header text. `process_eos()` then raises `Unexpected EOS while waiting for message header to complete`, and `flush()` returns the message as text (`oss-harmony/src/encoding.rs:1170-1218`, tag v0.0.11). The final chunk is processed before `flush()` in Chat streaming and non-streaming, and in Responses. This failure emits no body deltas for the broken message, so recovering it at flush does not contradict anything already sent.
- **The gap.** `_repair_malformed_header` runs only when `<|message|>` is rejected, so it never sees this shape. The other open Harmony PRs (#59225, #52055, #45571) do not cover it either.
- **The `requesting code` case.** It is dropped silently, on `main` too. The cause is #59254's suppression of errors after a rejected separator. It overlaps #52055, so it is not changed here.
- **Streaming reaches the repair.** Your point about this matches what we measured at chunk sizes 1, 4 and 11.

**What differed in the proposed patch**

Both problems below are minimal, token-level counterexamples, not hypothetical ones.

- **Literal control text inside the arguments.** `<|channel|>commentary to=functions.file_editor{"x":"<|call|>"}<|call|>`, with the inner `<|call|>` written as ordinary text tokens, is valid JSON. Re-encoding the decoded message with `allowed_special="all"` turns that inner text into the real stop token, and the call comes back with arguments `{"x":"`.
- **Recipient scope.** The regex also accepts `python`, `browser.search` and undeclared names, which would reach the Python, browser or MCP paths instead of a function call.

**How the PR uses your idea**

- **Same entry point.** The repair is in `flush()`, after `process_eos()` raises. The message is replayed through a fresh parser, and the generated and reasoning token counts are restored, as in your version.
- **Original token ids are kept.** Only the header is re-encoded; argument tokens are replayed unchanged. Literal control text in JSON therefore stays text.
- **Stricter match.** It requires `functions.<name>` with the name among the declared tools (when a tool list is supplied), a complete JSON object, and a real `<|call|>`. Other recipients, truncated or non-object JSON, other stop tokens and authored header words are left as today.
- **Tests.** `TestUnterminatedToolHeader`, including the literal-marker and recipient cases. Those fail on a faithful copy of your helper. Bulk and streaming are covered.

**Real failures**

I could not verify your 70/8/1/1 table, since your request and the 80 outputs aren't available to me.

On the 120b side, a real agent loop (public OpenHands prompt and schemas) produced 145 natural occurrences of this shape, plus 26 close variants. One caveat: every positive came from a history rendered with vLLM's legacy tool-header shim, which this PR removes. Matched histories rendered natively gave 0/3,840. So the repair guards against the failure, but it is unproven how often it fires once rendering is native. The full numbers are in the PR description.
