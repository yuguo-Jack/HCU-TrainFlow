# [CI] Start CI when auto-merge is enabled

[Upstream PR](https://github.com/vllm-project/vllm/pull/61600) · state: closed · merged: False

## Original PR description



## Overview

Enabling auto-merge on a PR now starts upstream CI, the way it did before CI became comment-triggered. Builds on #61592.

## Claims

- When someone with write access enables auto-merge, the bot runs the `/ci run` path as them: it merges `main` into a stale branch (#61592) and starts Buildkite CI, then comments the result on the PR.
- No duplicate builds: if the PR head already has a non-canceled CI build (running or finished), nothing happens.
- Users without write access are ignored (GitHub already requires merge rights to enable auto-merge; this double-checks).

## Validation

```bash

```

New tests: enabling auto-merge on a stale PR merges `main` and builds the merge commit; a head that already has a build, or a sender without write access, starts nothing and posts nothing.

## Details

**Background:** `add_label_automerge.yml` still adds `ready` on `auto_merge_enabled`. That used to start CI through label-triggered webhook builds; since CI moved to `/ci run`, the label alone starts nothing, so enabling auto-merge on a PR without a build just waits forever.

**Implementation:** `run-ci-command.yml` also triggers on `pull_request_target: [auto_merge_enabled]`. It still checks out only the default branch, so no PR code runs. `main()` routes that action to `run_on_auto_merge`, which reuses `handle_run_ci` (same freshness check, auto-merge of `main`, and build payload). The failure-report step now uses `payload.sender`, which is set for both event types.

**Not changed:** AMD CI is not triggered by auto-merge; the `ready` label workflow and author notifications are untouched.
