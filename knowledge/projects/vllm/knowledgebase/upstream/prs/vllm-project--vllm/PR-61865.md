# [KV Connector][NIXL] Reject NVFP4 KV cache with heterogeneous TP head split

[Upstream PR](https://github.com/vllm-project/vllm/pull/61865) · state: closed · merged: True

## Original PR description



## Overview

The way nvfp4 lays out per-head scales it's just not that heteroTP-friendly (e.g. P TP1 -> D TP2) and would require custom logic to handle scales/KVs differently, which we don't do today.
Let's just reject this configuration as invalid, or you get a silently invalid KV at runtime at garbage output.

## Claims

- NVFP4 KV + heterogeneous-TP head split now raises at handshake instead of producing garbage output:
  `RuntimeError: NIXL KV-head re-sharding is not supported for NVFP4 KV cache (local TP 2, remote TP 1). Use matching TP sizes on prefill and decode.`
- Rejected in both TP directions (D > P and P > D).
- Unaffected: matching per-rank head counts (incl. replicated one-head-per-rank, e.g. 8 KV heads at D TP16 <- P TP8), non-NVFP4 KV dtypes, and MLA (incl. `nvfp4_ds_mla`).

## Validation

**Repro / E2E** — GB300, `NixlConnector` pull mode, P and D on separate nodes, Llama-3.3-70B-Instruct, GSM8K (500 questions, 5-shot) through the P/D proxy:

| KV dtype | P TP -> D TP | Before | After |
|---|---|---|---|
| `nvfp4` | 1 -> 2 | **0.0%** (100% invalid answers, no error) | Handshake `RuntimeError` (above) |
| `fp8` | 1 -> 2 | 85.6% | Transfers KV normally |
| `nvfp4` | 1 -> 1 | 85–87% | unchanged path |

**Unit tests** — new `TestNixlHandshake::test_handshake_rejects_nvfp4_kv_head_split` (NVFP4 2<-1 and 1<-2 rejected; NVFP4 2<-2, NVFP4 16<-8 replicated, and non-quantized 2<-1 accepted):

```
pytest tests/v1/kv_connector/unit/test_nixl_connector.py -k TestNixlHandshake   # 29 passed
pytest tests/v1/kv_connector/unit/test_nixl_connector.py                        # 182 passed, 2 failed
```

The 2 failures (`test_compatibility_hash_validation[model_name-…]`, `[escape_hatch-…]`) fail identically on `main` in our environment (offline HF `ModelConfig` validation) and are unrelated. With the guard removed, the new rejection cases fail. The file already runs in Buildkite under `v1/kv_connector/unit`.

## Details

**Root cause.** NVFP4 pages are laid out as `[K data | K scales | V data | V scales]` over *all* heads of the rank, so one head's bytes are four discontiguous fragments. NIXL's heterogeneous-TP path assumes a head is a contiguous slice of the page:

1. D (TP2) handshakes with P (TP1); `TransferTopology` sees D ranks hold 4 heads, P rank holds 8.
2. D builds remote descriptors that address each half of P's page as "heads 0–3" / "heads 4–7".
3. P runs prefill and writes NVFP4 KV into its pages.
4. Each D rank reads a contiguous half of P's page, which does not match its heads' K/V data and scales.
5. Decode attends over the corrupted KV -> garbage tokens, no error raised.

**Condition.** The guard in `_validate_remote_agent_handshake` fires only when the local and remote ranks hold a different number of physical KV heads (`local_physical_heads != max(1, total_num_kv_heads // remote_tp)`) and any attention layer uses `KVQuantMode.NVFP4`. Equal per-rank head counts move whole pages and remain allowed. `is_nvfp4` only matches the `NVFP4` mode, and MLA is skipped (its cache is replicated), so `nvfp4_ds_mla` is unaffected. Checking the local KV dtype is sufficient because `kv_cache_dtype` is part of the NIXL compatibility hash.

Supporting NVFP4 re-sharding properly would need per-fragment descriptors (data and scales for K and V); that is out of scope here.

**Not a duplicate.** Searched open/closed/merged PRs and issues for "nvfp4 nixl", "nvfp4 heterogeneous tp", "nixl nvfp4 tp", "nvfp4 kv cache nixl", "NVFP4 re-sharding"; nothing addresses this. Nearest is #52516 (Mooncake replicated-GQA fix — different connector and problem).
