- suiyoubi · comment · 2026-11-04T13:33:10Z · [source](https://github.com/vllm-project/vllm/pull/65521#discussion_r4468141227)

File: `vllm/model_executor/kernels/mhc/flashinfer_mega.py` · line 257

JIT build in the request path. prepare_mega_mhc loads its program through FlashInfer’s JIT (`MegaMHCPlan.__init__ → load_program → build_and_load`), which runs nvcc on a cache miss. Nothing builds these programs ahead of time, so each one is built the first time a step needs it.

Startup only reaches two kinds of token counts: the profile run (max_num_batched_tokens) and the CUDA-graph capture sizes. The docstring’s “under CUDA graphs that happens once, at capture” covers those. But the program choice changes with the token count (mhc_infer_switch_points / mhc_infer_tail_program). A program whose range lies between the largest capture size and max_num_batched_tokens therefore gets compiled when the first mixed step of that size arrives, during serving. That engine step, and every request in flight, waits for nvcc.

We hit this in agg TP4 serving runs on VR200 with the default capture sizes. One program was built mid-benchmark, and in-flight requests saw a multi-second ITL/TTFT spike. Pre-populating the FlashInfer JIT cache removed it.

Could you warm every program this path can select at startup, under kernel_config.enable_jit_warmup? GLM-5.3 already does this for its TileLang mHC kernels ([model.py#L487-L528](https://github.com/vllm-project/vllm/blob/dc45a5f552a8513b9f4bc5b2cde05f51b7543fa1/vllm/models/glm5next/common/model.py#L487-L528)) through VllmJitKernel / JitWarmupRegistry. MHCPreNormKernel in [kernels/mhc/warmup.py](https://github.com/vllm-project/vllm/blob/dc45a5f552a8513b9f4bc5b2cde05f51b7543fa1/vllm/model_executor/kernels/mhc/warmup.py#L23) is an example in the same package.

One token count per distinct program over [1, max_num_batched_tokens] should be enough, since preparing a plan already builds its program. If the 64 × SM-count chunk loop stays, also cover the remainder sizes it can produce. For the test plan, a serving run with an empty FlashInfer JIT cache (FLASHINFER_WORKSPACE_BASE pointing at an empty directory) that shows no FlashInfer build after “JIT kernel warmup finished” would be good evidence.

File: `vllm/model_executor/kernels/mhc/flashinfer_mega.py` · line 130

`_Workspace` is per-process state keyed by device index, so it lives longer than the engine. It also sits outside vLLM’s workspace lock. `_forbid_capture` only checks during capture, so a step after capture that needs more scratch or a new grid would allocate silently, after the KV cache has been sized from free memory. Could this use [WorkspaceManager](https://docs.vllm.ai/en/latest/api/vllm/v1/worker/workspace/) instead?
