# [Bugfix] Validate kv_transfer_params before NIXL recv registration

[Upstream PR](https://github.com/vllm-project/vllm/pull/54807) · state: open · merged: False

## Original PR description

## Summary

- Add missing-field validation in the NIXL connector's receive path to prevent malformed client-supplied `kv_transfer_params` from crashing the Decode EngineCore with an uncaught `KeyError`.
- Guard the scheduler abort paths in both `pull_scheduler.request_finished` and `push_scheduler.request_finished` to skip recv cleanup when remote transfer metadata is absent (no P-node to notify).
- Add a catch-all validation in `NixlConnectorMetadata.add_new_req_to_recv` that checks all five required remote fields before indexing.
- Validate `remote_block_ids` shape, type, non-negativity, and int32 bounds at the metadata layer, and add a range check against `num_blocks` in `_compute_desc_ids`, so hostile values cannot propagate into unguarded `np.asarray` calls.

Addresses GHSA-2xp9-2v3c-q6cg.

## Details

A client can send `kv_transfer_params: {"do_remote_prefill": true}` (missing required remote fields) alongside a request that Prefill rejects. The rejection cleanup path sees `do_remote_prefill` and forwards the incomplete dict into the engine. The NIXL connector's `add_new_req_to_recv` uses direct dictionary indexing on five required keys (`remote_block_ids`, `remote_engine_id`, `remote_request_id`, `remote_host`, `remote_port`), raising an uncaught `KeyError` that kills the Decode EngineCore.

Additionally, even when all five fields are present, hostile values in `remote_block_ids` (non-int entries, negatives, int32 overflow) can reach `_compute_desc_ids` and crash the worker via `OverflowError`/`TypeError` in `np.asarray(..., dtype=np.int32)`, which is called outside the `try/except` that wraps `make_prepped_xfer`.

The fix applies defense-in-depth at three layers:

1. **Scheduler abort path**: When `do_remote_prefill` is set but `remote_engine_id` is absent, there is no remote P-node to notify (Prefill rejected the request before producing transfer metadata), so the cleanup is safely skipped.
2. **Metadata layer**: `add_new_req_to_recv` validates all required fields exist before indexing, then validates `remote_block_ids` structure (sequence-of-sequences-of-ints), non-negativity, and int32 bounds. Hostile values are logged and skipped.
3. **Worker layer**: `_compute_desc_ids` range-checks every block ID against the peer-advertised `num_blocks` before the `np.asarray` calls, raising `ValueError` for out-of-range IDs that would otherwise index past the descriptor list.

- 0xiviel · comment · 2026-09-14T03:21:43Z · [source](https://github.com/vllm-project/vllm/pull/54807#issuecomment-5658527253)

The five-field presence check closes the `KeyError`, but the same path stays
reachable with all five fields present and a hostile value in them.
`remote_block_ids` is never range-checked against the peer-advertised
`num_blocks`.

Measured against `NixlConnectorWorker._compute_desc_ids` at HEAD
(`58d45fd76`), with `num_regions=2`, peer `num_blocks=1000`, so `dlist`
length 2000:

    [[0, 1]]      -> [0, 1, 1000, 1001]   in range
    [[1500]]      -> [1500, 2500]         2500 is past the end of dlist
    [[-1]]        -> [-1, 999]            aliases into region 0
    [[2**31]]     -> OverflowError
    [[None]]      -> TypeError

The handshake establishes `num_blocks` (`base_worker.py:2092-2098`) and
validates only peer self-consistency (`:2411-2431`); nothing compares a
client-supplied block id against it. The only numeric constraint anywhere on
the path is the incidental `np.asarray(group, dtype=np.int32)` at `:227`,
which is what raises on the last two rows.

That matters for this PR specifically: `_compute_desc_ids` is called at
`:420` and `:437`, outside the `try/except Exception` that wraps
`make_prepped_xfer` (`pull_worker.py:459, :488-499`), so an
`OverflowError`/`TypeError` there reaches EngineCore the same way the
`KeyError` this PR fixes does.

Suggestion: extend the validation added in `add_new_req_to_recv` from
presence to shape — reject non-int entries, negatives, and ids outside
`[0, num_blocks)` once the handshake has run. Static analysis only here; no
NIXL/RDMA hardware on hand, so I make no claim about what the backend does
with an out-of-range descriptor index.
