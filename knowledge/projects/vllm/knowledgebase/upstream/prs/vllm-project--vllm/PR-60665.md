# [ROCm][Perf] wvSplitK: native bf16 dot and tuned gfx1100 tile configs

[Upstream PR](https://github.com/vllm-project/vllm/pull/60665) · state: closed · merged: False

## Original PR description



## Overview

Two changes to the bf16 `wvSplitK` skinny GEMM (decode GEMMs with N = 1..5 tokens) in `csrc/rocm/skinny_gemms.cu`:
1. Use the native `v_dot2_f32_bf16` instruction for the bf16 dot product on gfx1100 and gfx1201 instead of unpacking to fp32 (2 mul + 2 add).
2. Tuned bf16 tile configs for gfx1100: fewer waves per workgroup with deeper per-wave loads once each CU has enough rows to stream. Includes a `mindiv()` fix that these configs need.

fp16, other archs and the existing gfx1151 rules are unchanged.

## Claims

On gfx1100 (Radeon Pro W7900), bf16, kernel time vs the current code:
- Over a 117-shape M x K grid (M 1024-151936, K 1024-16384), geomean: **-3.1% at N=1, -6.3% to -8.0% at N=2..5**; no shape more than 0.5% slower.
- Qwen3.5-9B decode GEMMs (all `wvSplitK` calls of one decode step, built extension): **-3.5% (N=1), -4.3% (N=2), -3.4% (N=3)**.
- Accuracy vs an fp64 reference is unchanged on real model weights (details below).

**Correctness.** 730 cases on the built extension (bf16 and fp16; N=1..5; M around the rule thresholds; K covering the sml / hf / big kernel variants; with and without bias) against an fp32 matmul: all pass.

**Accuracy of the native dot** vs an fp64 reference (Qwen3.5-9B weights: lm_head, q/o/gate/up/down projections, plus synthetic sets):

| data | mean error (bf16 ulp), fp32 path → native | outputs bitwise equal |
|---|---|---|
| real weights | 0.250 → 0.250 | 99.91-99.98% |
| normal / outlier activations | 0.250 → 0.250 | 99.89-100% |
| adversarial cancellation (paired ±w) | 0.250 → 0.276 | 97.4-98.6% |

Where outputs differ it is by about 1 bf16 ulp. Two known differences: results in the fp32 denormal range (below ~1e-38) flush to zero, and heavy cancellation is slightly less accurate. NaN/Inf propagate identically.





## Details

**Native dot.** `DOT2C`'s bf16 path on gfx1x was the fallback written for gfx90a/gfx942, which have no bf16 dot2 instruction; the gfx1x port switched only fp16 to the native dot. `v_dot2_f32_bf16` exists on all gfx11/gfx12, but it is enabled only on gfx1100 and gfx1201 (compile-time `__gfx1100__` / `__gfx1201__`): on gfx1151 it was slower at its tuned tile configs, and other targets were not measured. Accumulation stays fp32.

**gfx1100 tile rules** (bf16 only; `sYT = ceil(M / (CuCount * 4))` as in the existing heuristic):

| N | sYT | YTILE | UNRL | waves per WG |
|---|---|---|---|---|
| 1 | <= 11 | 1 | 4 | 16 |
| 1 | 12-43 | 2 | 4 | 4 |
| 1 | > 43 | 4 | 4 | 2 |
| 2-5 | <= 43 | 1 | 4 | 16 |
| 2-5 | > 43 | 2 | 4 | 4 |

The kernel is DRAM-bound; with the current 16 waves x YTILE 2, about 1500 weight rows are streamed concurrently, which collides on DRAM channels for power-of-2 strides. Fewer waves with deeper loads keep enough bytes in flight while streaming fewer rows at once. The rules were chosen from a sweep over YTILE {1,2,3,4} x UNRL {1,2,4,8} x waves {2,4,8,16} x {fp32, native dot} at N=1..5 on the 117-shape grid, requiring no shape to regress by more than ~0.5%; a per-shape oracle is only ~0.5-1% better.

**`mindiv()` fix.** It always evaluated 13 candidate wave counts (`div2 .. div2-12`), dividing by zero or a negative count when a config uses fewer than 13 waves. It now evaluates `min(13, div2)` candidates; results for `div2 >= 13` (all existing configs) are unchanged.

**Limitations.**
- Tile configs are gfx1100-only and bf16-only; fp16 was not swept.
- Weight row-stride padding as in #55090 makes the tuned configs ~0.3-0.8% slower on gfx1100 (the two address the same DRAM-channel collisions); measured, not addressed here.
