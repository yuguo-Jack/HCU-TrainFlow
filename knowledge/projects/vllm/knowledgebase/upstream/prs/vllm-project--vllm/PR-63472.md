# [Bugfix] Fail fast on incomplete local checkpoints; name the layer in the NVFP4 scale error

[Upstream PR](https://github.com/vllm-project/vllm/pull/63472) · state: open · merged: False

## Original PR description

# [Bugfix] Fail fast on incomplete local checkpoints; name the layer in the NVFP4 scale error

Fixes the index-less variant of #34859.

## Non-duplication

- #34859 (Feb 2026) reported silent partial loads for quantized checkpoints and
  proposed validating shard completeness inside `_prepare_weights` by comparing
  the index's `weight_map` against files on disk. It was closed as not planned
  by the stale bot in June 2026; no fix PR was merged, and two community
  commits that referenced it never landed.
- The index-present half of that proposal already exists on main
  (`filter_duplicate_safetensors_files` raises when a file referenced by the
  index is missing — verified on main today). **This PR covers the other half:
  when no `model.safetensors.index.json` exists at all** (manual/aria2-style
  downloads), the loader globs `*.safetensors` with nothing to compare
  against. Checked `vllm/model_executor/model_loader/weight_utils.py` on main
  (2026-10-24): no shard-completeness check exists on that path, and no open
  PR was found implementing one.
- The NVFP4 error-message change is also absent from main (still prints the
  layer-type name only).

## AI assistance

This change was developed with AI assistance (ZCode agent, GLM model): root
cause was diagnosed by an agent-driven reproduction harness, and the patch and
tests were drafted by the agent. The human submitter reviewed every changed
line, drove the end-to-end verification on the target GPU, and takes full
responsibility for the change.

## Motivation

Debugging a real-world failure on `nvidia/Qwen3.8-27B-NVFP4` (modelopt
MIXED_PRECISION, vLLM v0.32.0), the server died at startup with:

```
RuntimeError: NVFP4 weight_scale for layer 'column_parallel_linear' was never
loaded (still NaN). The checkpoint likely stores this layer as BF16 (not FP4).
Fix: pass quant_config=None when constructing this layer, or add it to the
quantization ignore list.
```

The root cause turned out to be neither of the two suggested fixes: the
checkpoint directory contained only 2 of 3 safetensors shards
(`model-00001-of-00003.safetensors`, `model-00002-of-00003.safetensors`) and no
`model.safetensors.index.json`, because the download had been interrupted. Two
things made this take hours to diagnose:

1. **Silent partial load.** Without an index file, the loader globs
   `*.safetensors` and has no manifest to compare against, so a partially
   downloaded checkpoint "loads successfully" (progress bar: `2/2`) with holes
   in the state dict. Quantized layers whose scales were never read then fail
   much later in `process_weights_after_loading` — with an error that points
   at quantization config, not at the download.
2. **The error cannot identify the layer.** It prints `layer.name`, which for
   every linear in the model is the registered layer type
   (`'column_parallel_linear'`), identical across all 64 layers.

## Changes

- **`weight_utils.raise_on_missing_safetensors_shards`** (+ call in
  `DefaultModelLoader._prepare_weights`): when there is no
  `model.safetensors.index.json` on disk, verify the shard numbering in the
  filenames: files named `*-i-of-M.safetensors` must cover all of `1..M`, else
  raise `FileNotFoundError` naming the missing shards, before any weight is
  loaded. No-op for un-numbered/mixed/ambiguous file sets, and skipped when
  the user passed explicit `allow_patterns` overrides. When an index *is*
  present, the existing `filter_duplicate_safetensors_files` check already
  covers missing files.
- **`KNvfp4Static.process` error message**: report the module `prefix`
  (e.g. `model.layers.62.mlp.gate_up_proj`) with `layer.name` as fallback,
  and mention checkpoint incompleteness as a possible cause.

With both changes, the same broken directory now fails immediately with:

```
FileNotFoundError: Checkpoint on disk is incomplete: found 2 of 3 shards
(1-2 of 1-3). Missing shard file(s): model-00003-of-00003.safetensors. A
partial checkpoint would load with uninitialized weights and fail later with
confusing errors — re-download the model.
```

and, had the hole been reached anyway, the NaN error would have named
`model.layers.62.mlp.gate_up_proj` — the exact layer whose shard was missing
(lm_head + layers 62/63 lived in shard 3).

## Testing

- `tests/model_executor/model_loader/test_missing_safetensors_shards.py`
  (8 tests): missing shard raises with the full missing filename; complete
  set, un-numbered files, mixed families, **different-prefix families whose
  indices do not collide**, out-of-range indices, and empty input are no-ops.
  Run locally against the patched `weight_utils.py` (module loaded verbatim;
  only import-time `vllm.*` names are stubbed — CPU, no vLLM install):
  `8 passed`.
- `tests/model_executor/test_modelopt_nvfp4_scale_error.py` (3 tests): NaN
  scale error contains the module prefix; falls back to `layer.name`; a
  loaded scale passes the check. Run on the target venv (Python 3.12,
  vLLM v0.32.0 + this patch, RTX PRO 6000): `3 passed` (as part of a 10/10
  run of both files at the prior patch revision; `modelopt.py` is unchanged
  since).
- Verified end-to-end on the original broken checkpoint directory (RTX PRO
  6000 Blackwell, vLLM v0.32.0 + this patch, upstream `config.json`):
  - Before completing the download (2/3 shards, no index): startup now fails
    fast with the incomplete-checkpoint error above, naming
    `model-00003-of-00003.safetensors`.
  - The partial download had also silently dropped the tokenizer files
    (`tokenizer.json`/`vocab.json`/`tokenizer_config.json`), which surfaced
    only much later as `IndexError: list index out of range` inside the API
    server's structured-decisions init (`reply_label_ids` → empty
    `encode()`), after the engine had fully loaded and captured CUDA graphs
    (tracked separately in #63474).
  - After completing the download (3/3 shards + index + tokenizer files):
    `nvidia/Qwen3.8-27B-NVFP4` loads and serves; greedy sanity on a fixed
    5-prompt corpus produces coherent output, and the MTP2 speculative arm
    serves the same corpus correctly (`SpeculativeConfig(method='mtp',
    num_speculative_tokens=2)`). Serving outputs are unchanged by this patch
    (error-path only).
