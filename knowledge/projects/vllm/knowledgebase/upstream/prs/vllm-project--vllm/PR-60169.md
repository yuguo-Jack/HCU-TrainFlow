# [ROCm][DSv4.1][Perf] Use AITER FlyDSL GEMM for DeepSeek V4.1's 32x32 MXFP8 linears on gfx950

[Upstream PR](https://github.com/vllm-project/vllm/pull/60169) · state: open · merged: False

## Original PR description

## Overview
On gfx950, DeepSeek V4.1's MXFP8 linears with 32x32 weight-scale blocks run on vLLM's Triton block-scaled GEMM (`rocm_mxfp8_block32_gemm`). With AITER enabled, this PR runs them on AITER's FlyDSL MXFP8 GEMM instead. No other model or layer changes path.

## Claims
- **+3.7% total token throughput** at ISL 350k / OSL 350 / conc 32 and **+2.6%** at ISL 32k / OSL 32 / conc 32 
- Accuracy is unchanged: GSM8K 0.9735 vs 0.9727 (strict match, ±0.0045).

ISL 350k / OSL 350 / conc 32:

|---|---|---|---|
| total tok/s | 44,011 | 45,641 | +3.70% |
| TTFT mean | 165.9 s | 159.9 s | −3.63% |
| TPOT mean | 210.9 ms | 203.4 ms | −3.55% |

## Details
- Only the GEMM call in `RocmDotScaledMxfp8LinearKernel`'s existing 32x32 branch is changed, other branches as is, and there is no new env var.
- FlyDSL runs when: AITER linear ops on, gfx950, BF16 model, 32x32 scale blocks, K % 64 == 0.
- The weights are preshuffled once at load.
- Batched gemm for attention output projection `wo_a` stays on the Triton BMM path (the perf gain in e2e wasn't worth the code footprint).

- Fangzhou-Ai · comment · 2026-10-29T04:57:24Z · [source](https://github.com/vllm-project/vllm/pull/60169#issuecomment-6488346754)

Suggestion from running this PR's FlyDSL MXFP8 path in DeepSeek-V4.1-Flash DPATP2 serving (TP1 × DP2, MI355X, AgentX c128): **warm the FlyDSL GEMM kernels at weight load.**

aiter picks the FlyDSL kernel per padded M and JIT-compiles it on first use. On a cold FlyDSL cache, the server compiled several kernels inside its first long prefill step and exceeded the 300 s execute-model RPC timeout. We saw this as a startup death on first traffic.

The fix below runs the GEMM once per distinct kernel when the preshuffled weight is loaded, once per (N, K) per process. That covers every tuned M row for the shape up to `max_num_batched_tokens`, plus powers of two for the untuned fallback. With a cold cache, a sweep of serving-sized M compiles nothing afterwards. It adds 57 lines in `rocm_block32_gemm.py` / `rocm_native.py`. Feel free to fold it into this PR if useful.
