# [PP] Place remainder PP layers on the last stage(s) when num_layers % pp_stages != 0

[Upstream PR](https://github.com/vllm-project/vllm/pull/46217) · state: closed · merged: False

## Original PR description

## Purpose

When a model's layer count isn't divisible by the pipeline-parallel size, `get_pp_indices` has to place the `L % P` remainder layers somewhere. Today they go on the **middle** stages — the loop skips the first and last stage to cap peak memory on the embedding/head stages. This PR places them on the **last** stage(s) instead, which gives better prefill throughput in practice.

It's a one-line change — `range(2, remaining_layers + 2)` → `range(1, remaining_layers + 1)` — so the extras land on `partitions[-1], partitions[-2], …` instead of `partitions[-2], partitions[-3], …`. An explicit `VLLM_PP_LAYER_PARTITION` still overrides everything.

Example at PP=4:

| model | layers | before | after |
|---|---|---|---|
| DeepSeek-V3.1 | 61 | `[15,15,16,15]` | `[15,15,15,16]` |
| Qwen3-235B | 94 | `[23,24,24,23]` | `[23,23,24,24]` |

**Trade-off:** the previous middle-placement deliberately kept the remainder off the first/last stages to cap peak memory on the embedding and head stages. End-loading trades that for throughput; memory-tight deployments can restore the old split with `VLLM_PP_LAYER_PARTITION`.

**Not a duplicate:** searched open PRs/issues for `get_pp_indices` and pipeline layer partitioning — none change this default (closest, #40246, only refactors `compile_factors`).

## Test Plan

- **Unit:** `pytest tests/distributed/test_pipeline_partition.py` — the auto-partition goldens are updated for end-placement; the custom-partition and validation tests are unchanged.
- **Benchmark:** controlled ablation where **only the partition changes** (same model / cluster / chunk / operating point). PP4 × TP4 + EP, 128K random prefill, concurrency 2, 8K chunk. Compared front-loaded (`[16,15,15,15]` / `[24,24,23,23]`), the current middle default, and end (this PR).

## Test Result

Unit tests: **14 passed.**

Prefill throughput (tok/s, higher is better):

| model | front | middle (current default) | **end (this PR)** | end vs front | end vs default |
|---|---|---|---|---|---|
| DeepSeek-V3.1 (61L) | 28,671 | 29,045 | **29,424** | +2.6% | +1.3% |
| DeepSeek-V4-Pro (61L) | 86,030 | 86,655 | **86,920** | +1.0% | +0.3% |
| Qwen3-235B (94L) | 77,441 | 79,494 | **79,611** | +2.8% | +0.15% |

End placement is the best (or statistically tied-best) on every model tested, and is **never worse than the current default**. The win comes from lowering the per-cycle pipeline bottleneck: for attention-bound models, end-loading avoids piling the extra layer onto the embedding stage (which already carries the token-embedding cost); and a concentrated bottleneck on the head stage has less per-cycle pacing variance than spreading the remainder across near-equal middle stages.
