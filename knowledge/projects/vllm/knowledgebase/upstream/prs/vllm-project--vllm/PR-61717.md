# [Bugfix] Re-probe the tier for new requests instead of reusing a cached miss in tiering AsyncLookupManager

[Upstream PR](https://github.com/vllm-project/vllm/pull/61717) · state: open · merged: False

## Original PR description


## Overview

Fixes #61658. In KV offload tiering, `AsyncLookupManager` gave a resolved "absent" verdict to every later request for that key, as long as any request still held the key. On a shared tier (fs `root_dir`, obj), this meant the instance missed blocks that another instance wrote after the first probe. With this change, a new request that finds a cached miss starts a fresh probe. Requests that already have a verdict keep it.

## Claims

- A new request no longer inherits a resolved miss. It probes the tier again. This fixes the fs tier (`FsAsyncLookupManager`) and the obj tier (`ObjAsyncLookupManager`), which both use this class.
- Present verdicts, pending probes and in-flight probes are still shared across requests. Several new requests in one step share one new probe.
- A request keeps the verdict it already got. This includes a `mark_miss` after a failed load, so the failed-load livelock [#49176](https://github.com/vllm-project/vllm/issues/49176) does not come back.
- New test: `test_new_request_reprobes_cached_miss`, with two cases (the miss came from a probe, or from `mark_miss`).

## Validation

Reproducer from the issue. A set stands in for the shared tier. The caching and probe logic are vLLM's own `AsyncLookupManager`. Run it from outside the source tree with `python -I repro1_async_lookup.py`.

```python
import time

from vllm.v1.kv_offload.base import ReqContext, make_offload_key
from vllm.v1.kv_offload.tiering.async_lookup import AsyncLookupManager

shared_tier = set()
probes = 0


class SharedTierLookup(AsyncLookupManager):
    def batch_lookup(self, keys, req_context):
        global probes
        probes += 1
        return [k in shared_tier for k in keys]


def resolve(mgr, key, req_id):
    while (found := mgr.lookup(key, ReqContext(req_id=req_id))) is None:
        mgr.flush()
        time.sleep(0.01)
    return found


mgr = SharedTierLookup(tier_type="fs")
key = make_offload_key(b"prefix-block-0", 0)

print("r1:", resolve(mgr, key, "r1"), "probes:", probes)
shared_tier.add(key)
print("r2:", resolve(mgr, key, "r2"), "probes:", probes)
mgr.cleanup("r1")
mgr.cleanup("r2")
print("r3:", resolve(mgr, key, "r3"), "probes:", probes)
mgr.shutdown()
```

## Details

**Root cause.** `AsyncLookupManager` keeps one `LookupState` per key in `_lookup_state`. `lookup` started a probe only when the key had no state. Otherwise the request joined the existing state and got its result, whatever it was. The state is removed only in `cleanup`, once no request references it. So once r1's probe resolved to `False`, every new request for that key got r1's `False` with no probe, for as long as any request held the key. Under steady traffic on a common prefix, some request always holds the key, so the instance keeps missing blocks that are already in the shared tier. Debug prints on repro1 showed r2 finding `('RESOLVED', False, ['r1'], 0)` and sending no probe. On repro2, the same fs `batch_lookup` returned hits for all 4 files once r3 probed them, so the fs tier does see the other process's files. It was just never asked for r2. The sharing comes from the per-key state design (#44193), and the in-flight probe reuse (#55823) kept it.

**Fix.** `_req_keys` changes from `req_id → {key}` to `req_id → {key: LookupState}`, so each request remembers the state that gave it its verdict.

- A request that already has a state for the key gets that state's verdict, as before.
- Otherwise it joins the key's current state, unless that state resolved to `False`. In that case a new `LookupState` with a new generation replaces it in `_lookup_state`, and a probe is queued. Older holders keep the old state and their `False`.
- `cleanup` deletes the key from `_lookup_state` only if the current state is the one the request held. Without this check, cleaning up the old request would delete the new request's state.
- A replaced state is always resolved, so no probe result can still arrive for it. The generation checks in `flush` and `drain_results` are unchanged.

**Options not taken.**

- Replace the state for all holders, and keep `_req_keys` a set. This is smaller, but a request whose load failed (`mark_miss` → `False`) would flip back to a hit and retry the failed promotion. That is the #49176 livelock again.
- A TTL on absent verdicts, which the issue suggests as an alternative. The bug stays inside the TTL, and it adds a setting and a clock read on the scheduler path.
- Change the fs and obj managers. This repeats the rule in each tier, misses later tiers, and still has to handle `mark_miss`, which lives in the shared class.
- #61187 drops absent verdicts when this instance stores the block. It does not cover blocks written by another instance, which is this bug.

**Tradeoffs.**

- A new request on a key with a cached miss gets RETRY and waits at least one more scheduler step for its own probe, the same as for a cold key.
- Absent keys are now probed once per new request (or once per step when several arrive together). Before, concurrent requests shared one absent verdict.
- After a failed load whose block is still in the tier, each new request may try the load once. On the fs tier, a short read removes the file, so the new probe misses. Other fs errors (for example `EMFILE`) leave the file, and the obj tier never removes an object after a failed load. The request whose load failed never retries. This matches the existing obj-tier comment in `get_finished_jobs`: "The miss is per-request (cleared when the request finishes)".

**`mark_miss` invariant.** `mark_miss` has no request id and acts on the key's current state, so it must never land on a pending probe that a new request started. Through `TieringOffloadingManager` this cannot happen. While a promotion is in flight, the key is allocated but not ready in the CPU primary, so `CPUOffloadingManager.lookup` returns `HIT_PENDING`. `TieringOffloadingManager.lookup` then returns before it asks any secondary tier, so no probe of that key starts. The tier calls `mark_miss` in `get_finished_jobs`, before the primary slot is freed. So `mark_miss` always finds the state that led to the load.

**Other tiers.** p2p keeps lookups per `kv_request_id`, and kvcr queries on every call. Neither shares a verdict across requests, so neither has this bug.
