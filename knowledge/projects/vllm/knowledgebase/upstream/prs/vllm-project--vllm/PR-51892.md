# Bound frontend work for Responses requests

Three paths in the Responses API did work sized by the request before the model ran, with no cap.

- **Function-call outputs:** a per-request `call_id` lookup replaces scanning every earlier call for each output.
- **Completed-stream replay:** a cursor at or past the last event returns right away instead of waiting on an event that never comes.
- **Streaming `include`:** the include list is parsed once and the logprobs decision reused for every delta.

| Path | Before | After |
|---|---:|---:|
| function-call lookup | 31 failed, 96 passed | 127 passed |
| stream replay | 1 failed, 1 passed | 2 passed |
| streaming include | 2 failed | 2 passed |

The namespace-tool bound that was here moved to #57147 at a maintainer's request.

- KernelClint · comment · 2026-09-03T13:46:05Z · [source](https://github.com/vllm-project/vllm/pull/51892#issuecomment-5526750884)

Thanks for the review. Dropped the Gemma 4 commit, agree it's better to fix the template upstream in HF first rather than diverge here.

On the namespace tool expansion: the current change avoids flattening every tool name during named-tool-choice validation, which is where the quadratic cost was. A flat max-tools/max-chars cap would also bound it, but that's a new user-facing limit needing a configurable threshold and can reject legitimate large-tool requests, so I kept the targeted fix. Happy to add a cap on top if you'd prefer a hard ceiling as defense-in-depth.


- yzong-rh · comment · 2026-09-03T16:05:18Z · [source](https://github.com/vllm-project/vllm/pull/51892#issuecomment-5528509605)

My hesitation with the namespace tool expansion is that, eventually, to actually run the request, we'll have to expand the namespace tools anyways https://github.com/vllm-project/vllm/blob/31e9c13685b484d4ba67dc4e73019b23402609c7/vllm/tool_parsers/utils.py#L204-L221

Currently, we are doing it twice, once for validation then once for rendering (when constructing tool dicts). Your fix avoids flattening on the validation side and adds an early exit before rendering. However, I wonder if a cleaner solution would be to set reasonable limits, flatten tool names once, and use them for both validation and rendering. 

But this is a larger architectural change. Your fix seems fine as it is but I'll let the maintainers decide how they want to proceed.
