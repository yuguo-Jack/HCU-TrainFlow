# [ROCm][Kimi-K3] Support Mooncake consumers with specialized decode

[Upstream PR](https://github.com/vllm-project/vllm/pull/64958) · state: open · merged: False

## Original PR description

## Overview

The Kimi-K3 specialized decode on MI355X accepts only a MoRIIO consumer as its KV connector (#63031), so a Mooncake decode falls back to the stock path. A built-in Mooncake consumer meets the same condition: its loads finish before the request is scheduled (`get_finished`) and its layer hooks are no-ops. This admits it.

## Claims

- `decode_backend=latency_specialized` starts on a built-in `MooncakeConnector` with `kv_role=kv_consumer`.
- Mooncake producers, `kv_both`, custom connector modules and other connectors are still refused.
- Kimi-K3 1P1D on MI355X with Mooncake RDMA at concurrency 1: decode step 3.7 to 4.1 ms shorter (+23% to +24% decode tok/s) than the stock decode; end to end +14.7% tok/s/GPU, GSM8K 0.958.

## Validation

- `tests/models/kimi_k3/amd_specialized_decode/test_runtime.py`: 51 passed. The new Mooncake test fails on main and passes here. pre-commit clean.
- End to end: one CI run per configuration, below.

<details><summary>Benchmarks</summary>

Kimi-K3, 1 prefill + 1 decode instance on 2 nodes of 8x MI355X, TP8 per role, FP8 KV cache, DSpark with 7 draft tokens, Mooncake RDMA, vLLM ROCm nightly `3966924d` with this change applied at startup. The decode role uses the V2 model runner and `FULL_DECODE_ONLY` graphs. The specialized decode reads BF16 `in_proj_qkvgfab`, `f_b_proj`, `o_proj` and shared-expert weights, so those stay out of the decode role's online FP8 quantization; it also needs the KDA `in_proj` padding fix in #63730.

Decode only, one request, prefix caching off on both; `auto` keeps the weights above in FP8. ms per decode step:

| Context | `auto` | `latency_specialized` |
| ---: | ---: | ---: |
| 32K | 19.4 | 15.7 |
| 384K | 21.8 | 17.7 |

End to end, InferenceX AgentX multi-turn agentic trace at concurrency 1. The `auto` run keeps decode prefix caching on and those weights in FP8:

| Decode backend | tok/s/GPU | P90 interactivity | Full-response ITL p50 / p90 | Mean TTFT | GSM8K strict |
| --- | ---: | ---: | ---: | ---: | ---: |
| `auto` | 859.7 | 173.7 | 5.3 / 5.8 ms | 1.32 s | 0.972 (local) |
| `latency_specialized` | 985.8 | 181.5 | 4.3 / 5.5 ms | 1.50 s | 0.958 |

P90 interactivity is 1 / P90 per-request full-response ITL. TTFT rises because the decode without prefix caching pulls the whole prompt each turn. Decode prefix caching stays off here because with BF16 `o_proj` and prefix caching on, some 128K + 2-token continuations decode to garbage on the stock path as well; that bug is outside this change.

</details>
