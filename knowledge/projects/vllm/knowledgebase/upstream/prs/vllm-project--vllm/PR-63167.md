# [Docs][KV Connector] NixlConnector: disable EFA shm for same-host P/D with LIBFABRIC

[Upstream PR](https://github.com/vllm-project/vllm/pull/63167) · state: open · merged: False

## Original PR description



## Overview

Docs-only. Adds a short section to the NixlConnector usage guide. With the LIBFABRIC backend on AWS EFA, same-host prefill and decode should set `FI_EFA_ENABLE_SHM_TRANSFER=0`. libfabric's default shm path for GPU memory is limited by descriptor rate, and that makes the KV handoff the bottleneck.

## Claims

- **The default shm path caps same-host KV pulls at about 40K descriptors/s.** On EFA, libfabric routes same-host transfers through its shm provider unless `FI_EFA_ENABLE_SHM_TRANSFER=0`. A NixlConnector KV pull is thousands of small descriptors (one per KV block per layer; 16-64 KB each), so it is capped at a few hundred MB/s.
- **With the variable set, same-host transfers use EFA, which was faster at every descriptor size and for both READ and WRITE**, including a single 256 MB descriptor and single 4 KB latency.
- **No effect on cross-host transfers**, which never use shm.

## Validation

**Setup:** p6-b200.48xlarge (8x B200, 8 EFA), NIXL 1.3.2 (`nixl[cu13]`), libfabric 2.6.0amzn1.0, LIBFABRIC backend. Two processes on the same host (GPU0 ← GPU4). The 256 MB VRAM buffer is read or written as N descriptors in one transfer request, the way NixlConnector issues a KV pull. Median of 7.

| Op | Descriptor | Count | shm on (default) | `FI_EFA_ENABLE_SHM_TRANSFER=0` |
|---|---|---|---|---|
| READ | 4 KB | 65,536 | 0.16 GB/s | 2.04 GB/s |
| READ | 16 KB | 16,384 | 0.65 GB/s | 7.66 GB/s |
| READ | 64 KB | 4,096 | 2.51 GB/s | 29.39 GB/s |
| READ | 256 KB | 1,024 | 13.09 GB/s | 48.13 GB/s |
| READ | 1 MB | 256 | 29.41 GB/s | 47.81 GB/s |
| READ | 256 MB | 1 | 34.20 GB/s | 48.30 GB/s |
| WRITE | 64 KB | 4,096 | 3.10 GB/s | 31.91 GB/s |
| WRITE | 256 MB | 1 | 33.20 GB/s | 47.84 GB/s |

- **4 KB READ latency, 1 descriptor:**

  | | p50 | p99 |
  |---|---|---|
  | shm on | 30.3 µs | 40.5 µs |
  | shm off | 25.5 µs | 33.5 µs |

- **The shm path is flat at ~40K descriptors/s** from 4 KB to 64 KB. The EFA path is ~450-550K descriptors/s.
- **The same result holds for an NVLink-adjacent pair** (GPU0 ← GPU1): shm 0.66 / 2.55 / 29.8 GB/s against EFA 7.86 / 30.4 / 48.3 GB/s at 16 KB / 64 KB / 256 MB.

**End to end:** vLLM 0.29.0, Llama-3.1-8B-Instruct, 1 prefill GPU + 1 decode GPU on the same host, `vllm bench serve`, random 8192 input / 128 output tokens, block size 32.

| | c16 req/s | c64 req/s | Avg KV transfer |
|---|---|---|---|
| shm on (default) | 4.41 | 4.87 | ~1,490 ms (~120 MB/s) |
| `FI_EFA_ENABLE_SHM_TRANSFER=0` | 8.53 | 9.14 | 38 ms (26.9 GB/s) |

These had no effect on the shm path:
- `num_threads` (it only applies to UCX);
- splitting into 8 or 32 parallel requests;
- NIXL `striping_threshold`;
- `FI_EFA_TX_SIZE`, `FI_EFA_TX_QUEUE_SIZE`, `FI_EFA_USE_DEVICE_RDMA`.

The microbenchmark script is available on request, or it can be added under `tests/` or `benchmarks/` if maintainers want it.

## Details

- NIXL already disables shm on AWS Neuron hosts (ai-dynamo/nixl#2094), because shm has no Neuron memory support. On CUDA hosts shm stays on by default.
- Single-host measurements on one instance type (p6-b200). I did not test p5/p5en; the descriptor-rate behavior comes from the libfabric shm/EFA path, not the GPU.
