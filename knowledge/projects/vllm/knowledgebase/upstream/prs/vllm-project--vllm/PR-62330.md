# [Bugfix][DCP] Finalize the NIXL DCP interleave size before profiling

[Upstream PR](https://github.com/vllm-project/vllm/pull/62330) · state: open · merged: False

## Original PR description



## Overview

With `NixlConnector` + DCP, `cp_kv_cache_interleave_size` is auto-pinned to the kernel block size only in `ensure_kv_transfer_initialized`, i.e. *after* the profiling run. This PR finalizes the value in the existing per-worker pre-profiling hook (`WorkerBase.set_kv_cache_layout`) instead, turns the late adjustment into a fail-closed guard, and removes the indexers' caching of the value.

**Relation to #60671:** this fixes the same bug as #60671 by @andylolu2 (draft), which first diagnosed the stale value in `SparseAttnIndexer`; credit for the root cause goes there. This PR is offered as a **smaller alternative** (5 non-test files, +44/-38, no new RPCs or config fields) in case reviewers prefer a narrower fix; it is not meant to compete. #60671 additionally moves NIXL resolution into `VllmConfig`, publishes engine-computed global KV cache groups to workers, and removes the duplicate `dcp_kv_cache_interleave_size` field. Reviewers, please pick one; I'm happy to close this in favor of #60671, or to fold the guard/tests into it.

## Claims

- NIXL P/D + DCP: every worker uses the final interleave size from the first forward pass (profiling, compile, CUDA graph capture) onward, so the sparse indexer and the attention metadata builders always agree.
- Fixes wrong sparse top-k (degraded or garbage outputs) for models whose indexer read the cached `SparseAttnIndexer` / `SparseAttnIndexerKpool` value with DCP, e.g. the `deepseek_v2` V3-with-indexer path and `glm5next`.
- Fixes a startup failure on Model Runner V2 for `glm5next` (GLM-5.3-Flash) with NIXL + DCP, where profiling builds the indexer metadata with the stale `1` and raises.
- If the post-profiling value would ever differ from the pre-profiling one, startup now fails with an actionable error instead of silently running with an inconsistent value.

## Details

Worker startup order on main (per worker; the engine drives the RPCs):

1. `load_model`, then `update_block_size_for_backend` (kernel block size becomes final here).
2. `set_kv_cache_layout` RPC from `EngineCore._initialize_kv_caches`. **This PR: interleave finalized here.**
3. `determine_available_memory`: profile run, plus (with CUDA graphs) a minimal KV cache with real attention metadata. On main the interleave is still `1`; `SparseAttnIndexer` / `SparseAttnIndexerKpool` cache it on the first forward with real metadata, and MRV2 builds indexer metadata with it.
4. Engine computes `KVCacheConfig`s; `initialize_from_config` -> `ensure_kv_transfer_initialized` -> `adjust_dcp_kv_cache_interleave_size`. **Main: 1 -> block_size happens here**; metadata builders recreated afterwards see the new value, the indexers keep the stale one -> top-k global indices computed with the wrong token-to-rank layout.
5. Compile / CUDA graph capture, serving.

Changes:
- `WorkerBase.set_kv_cache_layout`: for DCP > 1 with a KV transfer instance, derive the worker's KV cache groups with the same builder the engine uses (`get_kv_cache_groups_from_builder(get_kv_cache_config_builder(...))`) and call `adjust_dcp_kv_cache_interleave_size`. Runner-agnostic (MRV1/MRV2), and also runs on the elastic EP scale-up path.
- `adjust_dcp_kv_cache_interleave_size` takes the KV cache groups instead of a `KVCacheConfig` (logic unchanged).
- `ensure_kv_transfer_initialized`: re-runs the adjustment and raises if the value changed after profiling.
- `SparseAttnIndexer` / `SparseAttnIndexerKpool`: read the value from `parallel_config` instead of caching it.

Tradeoffs / limitations:
- The pre-profiling value is derived from the worker's own KV cache spec, whereas the engine's `KVCacheConfig` groups are computed from the merged specs of all workers. They are identical when all workers hold the same layer types (e.g. PP=1). In exotic PP layouts where page-size unification across stages could change the minimum block size, the guard fails startup and asks for an explicit `--cp-kv-cache-interleave-size`, rather than silently diverging. #60671 handles this case by publishing the global groups to workers.
- `cp_kv_cache_interleave_size` is a compile-hash factor; it is now final before the first compile, so the hash is consistent.
- The engine-process copy of the value is not updated (same as main; nothing in the engine reads it).
