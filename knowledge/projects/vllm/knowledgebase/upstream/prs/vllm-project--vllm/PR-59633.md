# [Bugfix][HiSparse] Hold freed host blocks until the step's deferred writes land

[Upstream PR](https://github.com/vllm-project/vllm/pull/59633) · state: closed · merged: False

## Original PR description

## Purpose

Since #59309, HiSparse copies a step's MTP draft-layer rows (and, in lazy mirror mode, its page spills) to host at the next step's start. By then the scheduler may already have freed a finished or preempted request's host blocks and handed one to a P/D import. NIXL writes are not ordered against the HiSparse copy stream, so the late copy could overwrite imported rows. GPU writes and host copy-on-write are already ordered by #59309.

This should be rare: it needs a nearly full host pool (freed blocks go to the tail of the free queue), an import allocated in the very next step that draws a finished request's last-step blocks, and the late copy landing after the NIXL write (most plausible with async scheduling, where the copy waits for the previous forward). When it does happen, it silently corrupts an unrelated request's KV, which is very hard to trace back, so the fix is worth its small cost.

## Changes

- The coordinator stamps each step's connector metadata with a step id.
- The coordinator's `free()` takes a freed request's host blocks and holds them, tagged with the latest scheduled step, instead of letting them return to the pool.
- The worker reports a step's deferred writes as done after flushing them, through the existing transfer enqueued/completed counts.
- Held blocks are released once their step (or a later one) is reported done, and count as pending work so an idle engine keeps stepping until then.

HiSparse-only (no core changes). Overhead: no stream or CPU synchronization; one event recorded on the copy stream per step, plus O(finished requests) scheduler bookkeeping. A freed request's host blocks return to the pool about one step later, and an engine that goes idle runs one extra empty step. The scheduler's generic `deferred_frees` fence covers the same hazard one step too early for HiSparse (and only for consumers with overlapping batches).

No other open PR addresses this. AI assistance (Claude Code) was used; changes reviewed and tested by the submitter.

- MatthewBonanni · comment · 2026-10-05T21:17:16Z · [source](https://github.com/vllm-project/vllm/pull/59633#issuecomment-6003096947)

Closing: the race this fixes is latent on `main` and can't change outputs.

- **Natural timing doesn't trigger it.** With async scheduling, a request's host blocks are freed only after its last in-flight step's output. The deferred draft-row copy then lands about 27 ms before the next NIXL post.
  - On a tiny DeepSeek-V3.2 with MTP doing P/D on 1×H100 (300 requests, concurrency 16), an instrumented probe saw 0 copies still pending when NIXL posted.
- **It fires only with an injected 75 ms delay on the copy stream.** Then `main` overwrote 27 imports and this PR overwrote 0.
- **Only MTP draft-layer rows are at risk.** Page spills take a reference on their host block, so they can't race. A late draft-row copy can lower acceptance but cannot change greedy tokens; outputs matched a non-P/D reference in every run.
- **Correction to the description:** freed unhashed host blocks go to the front of the free queue, so a nearly full pool isn't needed for reuse.

Reopen if a natural-timing repro turns up.
