# [Fusion] Apply manual activation+quant fusion to Muse-Glimmer and LFM2

[Upstream PR](https://github.com/vllm-project/vllm/pull/59470) · state: open · merged: False

## Original PR description

## Purpose

Third model batch for #43501, following the batching plan in https://github.com/vllm-project/vllm/issues/43501#issuecomment-5716717828. Applies the manual fusion pattern from #51415 to two more SiluAndMul families, one line per model plus the import, with a wiring test per model in the shape of the Nemotron-H one from #53793.

- `MuseGlimmerMLP` in `muse_glimmer.py` (meta-models/Muse-Glimmer-30B, dense, MLP in every layer)
- `Lfm2MLP` in `lfm2.py` (LiquidAI LFM2 / LFM2.5, dense, used by both the attention and the short-conv decoder layers)

Draft on purpose. Two things have to land before this is ready, both measured on one H100 (driver 580.126.20, main fc2c801ad9 with the precompiled wheel, torch 2.13.0+cu130, FlashInfer 0.7.0.post1), full logs attached.

**Muse-Glimmer is on the fallback path today.** The public FP8 checkpoint (RedHatAI/Muse-Glimmer-30B-FP8-block) uses dynamic 1x128 activation scales. On this H100 all 52 `down_proj` layers select `FlashInferFp8DeepGEMMDynamicBlockScaledKernel`, which exposes no input quant key, so `maybe_fused_act_quant` returns the plain activation on 52/52 layers and nothing changes at runtime. #57514 adds the block-FP8 consumer side, but withholds the key for kernels that quantize inside their own op, which is the one selected here, so with #57514 the fusion fires for this checkpoint only with `VLLM_BLOCKSCALE_FP8_GEMM_FLASHINFER=0`. No public static per-tensor FP8 Muse-Glimmer checkpoint exists.

**LFM2 fires, and is slower.** With vrfai/LFM2.5-2.6B-FP8 (static per-tensor, compressed-tensors) all 30 `w2` layers select `CutlassFP8ScaledMMLinearKernel` and take the fused branch on 30/30. That swaps Inductor's generated silu+mul+quant kernel for `_C.silu_and_mul_quant` (`act_and_mul_quant_kernel`), which is slower per launch on H100 in every regime, with no launch saved. Serving is 4.4% slower with the wiring. The same mechanism is already on main for Llama through #51415: with RedHatAI/Meta-Llama-3.1-8B-Instruct-FP8, main's own wiring is 3.0% slower than the same tree with the one llama.py line reverted. Numbers below. The fix belongs in the kernel, not in the model wiring; I will link the kernel PR here when it is up. This PR should not be marked ready until that kernel is at least at Inductor parity.

Not a duplicate: #57514 covers DeepseekV2, Mistral, Qwen2 and Qwen3MoE, #58665 covers Granite, Seed-OSS and EXAONE 4.0, and neither touches these two families. A search of open PRs for `maybe_fused_act_quant`, `MuseGlimmerMLP`, `Lfm2MLP` and the two model names found nothing else. The per-model test files avoid the add/add conflict both open batches would otherwise have on a shared `tests/model_executor/test_manual_fusion_models.py`.

## Test Plan

- `pytest tests/model_executor/test_muse_glimmer_quantization.py tests/model_executor/test_lfm2_quantization.py -v`, plus a negative control per model (model edit reverted, the test must fail)
- `pytest tests/fusion/test_quant_activation_contract.py tests/compile/passes/test_silu_mul_quant_manual_fusion.py tests/kernels/test_fused_quant_activation.py -q`
- In-process load of each FP8 checkpoint (`VLLM_ENABLE_V1_MULTIPROCESSING=0`), reading `get_input_quant_key(down_proj)` and the selected linear kernel class on every MLP, greedy generations
- `vllm serve <model> --max-model-len 2048` and `vllm bench serve --backend vllm --dataset-name random --random-input-len 1024 --random-output-len 128 --num-prompts 1000 --request-rate inf --ignore-eos --seed 0`, one warm-up start per arm, 3 interleaved rounds, "unfused" = the one model line reverted on the same tree
- `lm_eval --model vllm --tasks gsm8k --num_fewshot 5 --batch_size auto --seed 0` on both arms (LFM2)
- Torch profiler trace of one `vllm bench latency --batch-size 32 --input-len 1024` iteration per arm
- `pre-commit run --files <changed>` and `pre-commit run mypy-3.12 --all-files --hook-stage manual`

## Test Result

Tests: 2 wiring tests passed, both negative controls fail as expected, existing fusion tests 133 passed / 12 skipped. Pre-commit clean; mypy shows only the 3 pre-existing macOS-only errors in untouched files.

Fusion engagement:

| Checkpoint | MLP layers | `down_proj` kernel | Fused branch |
|---|---:|---|---:|
| RedHatAI/Muse-Glimmer-30B-FP8-block | 52 | FlashInferFp8DeepGEMMDynamicBlockScaledKernel | 0 / 52 |
| vrfai/LFM2.5-2.6B-FP8 | 30 | CutlassFP8ScaledMMLinearKernel | 30 / 30 |
| RedHatAI/Meta-Llama-3.1-8B-Instruct-FP8 (main, #51415) | 32 | CutlassFP8ScaledMMLinearKernel | 32 / 32 |

Serving, means of 3 interleaved rounds (every wired round is below every unfused round in both models):

| Model | Metric | Wired | Unfused | Delta |
|---|---|---:|---:|---:|
| LFM2.5-2.6B-FP8 | req/s | 83.64 | 87.49 | -4.4% |
| LFM2.5-2.6B-FP8 | mean TPOT ms | 48.29 | 46.66 | +3.5% |
| LFM2.5-2.6B-FP8 | mean TTFT ms | 4713.7 | 4365.1 | +8.0% |
| Llama-3.1-8B-FP8 | req/s | 37.77 | 38.93 | -3.0% |
| Llama-3.1-8B-FP8 | mean TPOT ms | 73.20 | 70.90 | +3.2% |
| Llama-3.1-8B-FP8 | mean TTFT ms | 11412.7 | 11068.4 | +3.1% |

Profile, one latency iteration, batch 32, 1024 in:

| Model | GPU kernel time unfused / wired | Launches | Inductor silu+quant kernel | `act_and_mul_quant_kernel` |
|---|---|---|---|---|
| LFM2.5-2.6B (128 out) | 496.2 / 538.9 ms | 55537 / 55538 | 3900 launches, 26.1 ms | 3900 launches, 70.8 ms |
| Llama-3.1-8B (32 out) | 666.3 / 695.8 ms | 14875 / 14876 | 1088 launches, 30.3 ms | 1088 launches, 69.2 ms |

Per launch on LFM2: decode-size median 1.85 us (Inductor) vs 8.67 us (CUDA kernel), 16K-token prefill mean 305 us vs 415 us. Every other kernel in the traces is within about 1 ms between arms.

Accuracy, LFM2.5-2.6B-FP8, GSM8K 5-shot: wired strict 0.7089 +- 0.0125, unfused strict 0.7051 +- 0.0126, within 1 SE. Greedy text is not bit-identical between arms (each arm is deterministic run to run; the CUDA kernel rounds silu to bf16 before the multiply, Inductor keeps fp32).

Muse-Glimmer loads and serves with the wiring (falls back on every layer, output coherent). Not measured for Muse-Glimmer: serve or profile, since the path is unchanged today.
