# [Mamba][MRV2] Plan Triton ReplaySSM decode on the GPU and support Model Runner V2

[Upstream PR](https://github.com/vllm-project/vllm/pull/65033) · state: closed · merged: True

## Original PR description



## Overview

Triton ReplaySSM (`--use-replayssm --mamba-backend triton`, #48018) was rejected on Model Runner V2: it planned each decode step on the CPU from a per-request ring origin that only the V1 input batch tracked. This PR moves that planning to the GPU using per-cache-slot ring counters (the same trackers the FlashInfer ReplaySSM backend from #52506 already uses), which enables MRV2 and deletes the runner-side plumbing.

## Claims

- Triton ReplaySSM now runs on MRV2, with logprob parity against the non-ReplaySSM baseline on both runners, with and without mamba `align` prefix caching.
- No runner changes are needed for V2; the V1-only `replayssm_decode_base_cpu` plumbing (in `CommonAttentionMetadata`, the V1 input batch, and the V1 runner) is removed.
- The per-step CPU planning in the Mamba metadata builder (about 70 lines, plus two `.tolist()` → H2D copies each step) is replaced by one small GPU kernel per KV-cache group per step.

Unit and kernel tests also pass: `tests/kernels/mamba/test_replayssm_plan.py` (new), `tests/kernels/mamba/test_replayssm_standard_decode_mamba2.py`, `tests/v1/attention/test_replayssm_metadata_builder.py`, `tests/model_executor/test_replayssm_warmup.py`, the tracker-sharing test in `tests/v1/worker/test_utils.py`, and the ReplaySSM config test in `tests/test_config.py` (168 tests).

The new kernel test drives the planner through whole decode runs and checks every step against the removed CPU formula. It covers none and align modes, buffer lengths 4, 6 and 16, align block sizes 16, 32 and 64, and prompts that end mid-block or on a block boundary. It also covers rows planned independently, padding rows, re-anchoring after a prefill reset (preemption-resume), and a stale slot counter at a prefix-cache block boundary.

Not run: the TP2 parity tests (V1 only, unchanged) and the FlashInfer ReplaySSM e2e tests (that path is unchanged apart from sharing tracker setup with Triton layers). CI's `replayssm-e2e` step (2×H100) covers both.

## Details

**Planning.** Each Mamba2 layer already gets per-slot `ring_start`/`prev_num_accepted`/`prev_query_len` tensors from `share_replayssm_ring_trackers`, shared within a KV-cache group; this PR extends that to Triton layers. For Triton, `ring_start[slot]` is the number of tokens buffered since the slot's last full-state write. The first ReplaySSM layer of each group calls `plan_replayssm_decode`, which writes that step's `write_pos`/`is_flush` into persistent builder buffers that every layer reads, then advances the counter (resetting it to 0 after a flush). Prefill resets the counters with the existing `reset_replayssm_ring_trackers`. The Triton SSU kernel is unchanged.

**Align mode.** The planner reads the GPU `seq_lens`, which both runners keep in persistent buffers. It restarts the ring on a block's first step and forces a flush on the step that completes a block, so the exact block-boundary state is materialized for prefix caching. That is what the CPU code did with `max(decode_base, block_start)`. Restarting at the block's first step also handles a prefix-cache hit on a reused slot whose counter is left over from a previous request, because such hits always land on a block boundary.

**CUDA graphs.** `write_pos`/`is_flush` were already persistent buffers for FULL graphs; they are now written on the GPU inside the graph instead of being copied in before replay. Padding rows have `NULL_BLOCK_ID` slots and are planned as no-ops.

**Behaviour change.** A one-token final prompt chunk that runs as a decode row (`prefill_to_decode`) now appends to the ring the previous chunk's prefill left empty, like any other decode step, instead of forcing a one-token flush. Both are mathematically equivalent, since the checkpoint is the state before that token. The planner unit test covers this case; the e2e tests don't deliberately trigger it.

**Limitations.** `mamba_cache_mode="all"` with Triton ReplaySSM is not rejected by config but was not handled correctly before this change either (the decode slot changes every block without a ring restart). This PR does not change that.
