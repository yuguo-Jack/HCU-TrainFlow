#  [Bugfix] Release cached allocator memory after fastsafetensors weight loading / repacking

[Upstream PR](https://github.com/vllm-project/vllm/pull/59719) · state: closed · merged: False

## Original PR description


## Purpose

Related: #57440

Temporary tensors created during `load_weights()` and `process_weights_after_loading()` (fastsafetensors staging buffers, MXFP4/FP8 repacking) stay reserved in PyTorch's caching allocator after they are freed. PyTorch allocations can reuse that pool, but raw CUDA driver allocations cannot, and several of those happen before KV-cache profiling ever calls `empty_cache()`:

- the DeepEP v2 `ElasticBuffer`, created inside `process_weights_after_loading` when the first MoE layer's prepare/finalize is built;
- NCCL buffers with `NCCL_CUMEM_ENABLE=1`;
- the draft model's fastsafetensors budget, which reads `mem_get_info()`.

On discrete GPUs `release_device_memory_under_pressure()` is a no-op (it only runs on integrated GPUs), so nothing returns that memory to the driver.

This PR adds `BaseModelLoader._release_cached_memory()` (`gc.collect()` + `torch.accelerator.empty_cache()` on CUDA-alike platforms) and calls it after `load_weights()` and after `process_weights_after_loading()`. Both run once per engine start.

Duplicate check: #57516 proposes the same two calls inline. I filed #57440 with this fix as the proposed direction, measured it on the hardware where the OOM occurs, and am submitting it here with that validation. #57516 has had no human review since 2026-09-18, and is validated only by a mocked unit test; this PR factors the calls into a helper on the loader base class and includes the end-to-end A/B below. Happy to coordinate with @debanshd on which one proceeds.

## Test Plan

Kimi-K3 (`moonshotai/Kimi-K3`, MXFP4) on 2 × 8 B200, TP4 × DP4 × EP16, `--all2all-backend deepep_v2`, `--load-format fastsafetensors`, `--kv-cache-dtype fp8`, `--gpu-memory-utilization 0.93 --max-num-seqs 192 --max-num-batched-tokens 8192 --max-model-len 32768`. Same image and config for both arms; the only difference is `base_loader.py`. Driver-free / reserved / allocated were logged at each boundary with `torch.cuda.mem_get_info()` and `torch.cuda.memory_{reserved,allocated}()`.

## Test Result

Worst rank (TP rank 3 on each DP group), GiB:

| | main | this PR |
|---|---|---|
| after `load_weights`: driver free / reserved / allocated | 0.009 / 175.0 / 137.9 | 0.009 / 175.0 / 137.9 → **36.8** / 138.2 / 137.9 after release |
| after `process_weights_after_loading` | not reached | 29.1 / 143.4 / 137.9 → **34.3** / 138.2 / 137.9 after release |
| DeepEP `ElasticBuffer` (1.9 GB) | `NCCL exception ... Cuda failure 2 'out of memory'` | ok |
| KV cache | — | 8.53 GiB, 489,335 tokens |
| server | fails to start | ready in 618 s; completion request returns `" Paris. The Eiffel Tower is located in Paris. ..."` |

37 GiB per GPU was sitting idle in the caching allocator with 9 MiB left for the driver. Releasing it at the two boundaries is what lets the ElasticBuffer allocate.

Also observed on TP8 × DP2 × EP16 (the config in #57440): main has 6–9 GiB driver-free after loading with 38 GiB stranded; the ElasticBuffer there is 1.2 GB so main happens to start, but the headroom disappears with a draft model or larger buffers.
