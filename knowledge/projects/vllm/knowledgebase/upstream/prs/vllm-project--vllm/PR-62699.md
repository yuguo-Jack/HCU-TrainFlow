# [Bugfix] Fix NixlConnector handshake StopIteration for Mamba-only models

[Upstream PR](https://github.com/vllm-project/vllm/pull/62699) · state: open · merged: False

## Original PR description


## Overview

Fixes #61617. With NixlConnector P/D, a Mamba-only model has no attention KV cache group. On such a model, the decode side's handshake crashed with `StopIteration` in `_build_fa_remote`, and the request got HTTP 500. This PR lets the two attention-group lookups in `nixl/base_worker.py` handle the case where there is no attention group. In that case it takes the split count for the "FA" placeholder rows, which are never read, from the TP plan.

Compared with #61619, this fix:

- also fixes prefill TP 2 → decode TP 1 when the decode runs on the default in-process executor. On that setup, [#61619](https://github.com/vllm-project/vllm/pull/61619) splits the unread FA rows over 2 ranks, which trips `AssertionError: Head-sharded attention reads with P_TP > D_TP and heterogeneous block sizes are not supported`, and the decode returns HTTP 500.
- does not kill the decode engine on that setup. With [#61619](https://github.com/vllm-project/vllm/pull/61619), the retried handshake registers an empty split list, the next read raises `IndexError` in `pull_worker.py` and the engine dies with `EngineDeadError`, so later plain requests also get 500. The old code fails only that one request.
- has tests that pass on the current Nx5 descriptor format and run the split loop with a real TP 2 → TP 1 plan. [#61619](https://github.com/vllm-project/vllm/pull/61619)'s tests assert the old Nx3 rows, so on 49cb2bbf7 they fail even with its own change. Its split test also uses an empty plan, so the split loop never runs.

## Claims

- NixlConnector P/D with a Mamba-only model (`state-spaces/mamba-130m-hf`) now completes the handshake and decodes. In the issue's TP 1 → TP 1 pull setup, the decode now returns HTTP 200 instead of HTTP 500.
- Prefill TP 2 → decode TP 1 with a Mamba-only model also works, with both the in-process and the `mp` decode executor. The old code fails there in `_build_local_splits_from_plan` with `RuntimeError: generator raised StopIteration`.
- Models that have an attention group take exactly the same code path as before.
- 3 new unit test cases in `tests/v1/kv_connector/unit/test_tp_mapping.py`. They fail on the old code and pass with this PR.

## Details

Request flow in the failing case (pull mode):

1. P (`kv_producer`) gets the request with `do_remote_decode: true`. It prefills 13 of the 14 prompt tokens and returns `kv_transfer_params`.
2. D (`kv_consumer`) gets the request with those params. Its NIXL worker starts a handshake with P's side channel.
3. In `add_remote_agent`, D builds the remote descriptor list. `_build_fa_remote` makes one "FA" row per block per region, and the SSM rows come after them (`_compute_desc_ids` offsets the SSM ids by `num_fa_descs`).
4. Old code: `_build_fa_remote` finds the first attention group with a bare `next()`. A Mamba-only model has only a `MambaSpec` group, so `next()` raises `StopIteration`. The handshake future fails, the request fails with `handshake_failed`, and the client gets HTTP 500.
5. With this PR: the handshake completes. D reads the conv and SSM state for the request's block, computes the last prompt token, and decodes.

`_build_local_splits_from_plan` has the same bare `next()`. It runs only when prefill TP > decode TP. Because the function is a generator, the error shows there as `RuntimeError: generator raised StopIteration`.

The fix: both lookups now use `next(..., None)`. With an attention group, the index and the path do not change. With no attention group, the FA rows are never read, because `_compute_desc_ids` gives FA ids only to attention groups. The rows only keep the SSM ids at the right offset. But NIXL still checks every remote row against the remote's registered memory, so the rows must still fit:

- `_build_fa_remote` uses `split_reads = len(plan.all_source_ranks)`. The local page of such a model is gathered from all source ranks, so each remote row is one remote page. A first version used `1`. With prefill TP 2 → `mp` decode TP 1, those rows ran past the remote region, and NIXL refused the list with `NIXL_ERR_NOT_FOUND`.
- `_build_local_splits_from_plan` uses `fa_num_splits = 1`, so each local row is one whole local block. A count above 1 trips the `Head-sharded attention reads ...` assert when the block size ratio is above 1, as with an in-process decode (ratio 128).

Not taken: building no FA descriptors at all for models without attention. That needs changes to `_build_fa_local`, `num_descs`, the id offsets in `_compute_desc_ids` and the assert in `register_local_xfer_handler`, and it changes the descriptor layout of every Mamba-only engine.

Limitations:

- Prefill TP 1 (in-process) → decode TP 2 still fails, at an earlier step, in the block size ratio check: `Local block size 16 is not divisible by remote block size 2048`. For a Mamba-only model, the NIXL block size depends on the executor. An in-process worker sees the 2048 that `vllm/v1/engine/core.py` writes to `cache_config.block_size` after the workers start, while an `mp` worker keeps 16. That is a separate problem and this PR does not change it.
- Push mode with a Mamba-only model was not run end to end. Only the issue's pull mode was.
- The unit tests do not cover a block size ratio above 1. The in-process TP 2 → TP 1 case was checked only end to end.
