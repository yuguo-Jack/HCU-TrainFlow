# [Bugfix] Honor add_generation_prompt and continue_final_message in the DeepSeek V4.1 tokenizer

[Upstream PR](https://github.com/vllm-project/vllm/pull/62729) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

Fixes #64431. Python-frontend part of #46256 on DeepSeek V4.1 (`vllm/tokenizers/deepseek_v41_encoding.py`).

The V4.1 encoder ignores `add_generation_prompt` and `continue_final_message`. When the last message is an assistant message, the prompt always ends at `<｜end▁of▁sentence｜>` without an `<｜Assistant｜>` turn prefix, so the model returns empty or garbled text with HTTP 200. With `continue_final_message=true`, the final message is still closed with EOS, so the reply cannot continue it.

This PR makes the V4.1 encoder honor both controls, and declares turn boundaries for the V4.1 parser so that the prompt-aware reasoning start from #61857 also applies to V4.1. It is the Python counterpart of the Rust-frontend fix in #62189 and uses the same semantics. The encoder change is a port of #57882 by @xijiaat (closed without review; credited as co-author of the commit) onto current `main` (after #60792, image order, and #62199, the 1017 reference encoding).

**Related, not duplicates:** #62199 (merged) and #62196 (open) sync turn handling with the 1017 reference encoder (tool-result turns) and do not touch the generation controls. #62459 (open) fixes a conversation whose final message is `system`; this PR leaves that case to it and only changes conversations that end with an assistant message. #62887 (open) fixes `continue_final_message` only, by setting `wo_eos` on the final assistant message; this PR also covers `add_generation_prompt`. #64493 (draft) makes the same change for V3.2.

**Behaviour change:** a conversation that ends with an assistant message now gets a new assistant turn by default (`add_generation_prompt=true`), as with Hugging Face chat templates and #62189. To continue the final assistant message, clients send `continue_final_message=true`. Callers that pass `add_generation_prompt=false` explicitly for a conversation ending with a user message now get a prompt without the assistant turn prefix (see Details).

## Claims

- `add_generation_prompt=true` (the default): when the final message is an assistant message, the prompt now equals the DeepSeek reference encoding of the conversation followed by the reference assistant turn prefix, `<｜Assistant｜><think>` in thinking mode and `<｜Assistant｜></think>` in chat mode. The comparison is token-for-token. Earlier assistant messages keep their EOS.
- `add_generation_prompt=false`: for a conversation that ends with an assistant message, the prompt is unchanged from before and equals the DeepSeek reference encoder output. For any other final message the prompt now ends without the assistant turn prefix, as the flag asks (before, the flag was ignored).
- `continue_final_message=true`: the final assistant message is left open (no EOS). If it ends inside its reasoning, the reasoning is left open as well. A request without a final assistant message is rejected with HTTP 400 (before, the flag was ignored and the request returned 200).
- With the default `add_generation_prompt=true`, prompts that end with a user, developer or system message are token-identical to before.
- A final assistant message that is already left open with `wo_eos` (only possible when calling `encode_messages` directly; requests cannot set it) gets no new assistant turn, so it renders exactly as before.
- With `turn_boundary_tokens` declared, the V4.1 parser starts in content when the current turn's prompt already closed reasoning (for example a continued answer after `</think>`). A `</think>` in an earlier turn does not count.
- Fixes empty and garbled replies on DeepSeek-V4.1-Flash with the Python frontend: 210/280 empty replies before this change, 2/280 after (both remaining ones hit `max_tokens` while still reasoning).

Notes:

- With thinking on, "before" shows the same failure as the section above: the reply text ends up in `reasoning_content` and `content` is empty (19/20 for `continue_final_message=true`, 16/20 for a complete final answer; above: 40/40 and 35/40). With thinking off, a complete final answer gives a user-voice line or an odd start instead (14/20 and 15/20 user-voice lines); a code prefix is mostly continued even after the EOS (17/20 and 18/20), so for that shape the old prompt fails mainly with thinking on (the code-prefix rows above were run with thinking on, the server default). This run uses a newer nightly, `--moe-backend marlin`, and classifies replies by how they open, so its counts are not comparable one to one with the section above; both runs show the same direction.
- `add_generation_prompt=False` after a complete final assistant message: the prompt is identical on both sides and equals the reference (the conversation is closed at EOS), and 9 of the 10 greedy replies are the same text on both sides. What changes with thinking on is which field the text goes to. Before, the parser treats it as still inside reasoning (19/20 reasoning only); with this PR's `turn_boundary_tokens` it does not, so the same text is returned as `content`. Both are continuations after a closed conversation, not answers.
- `add_generation_prompt=False` after a user message: the prompt now has no assistant turn, as requested, so the model continues the user's own text. With thinking on, all 20 replies start by continuing the user's sentence inside `reasoning_content` (e.g. ` It should be ... handle large numbers efficiently.`); 11 stop there with empty `content`, and 9 then also write a reply in `content`. 8 of the 20 contain special-token text such as `<｜place▁holder▁no▁798｜>` (in `reasoning_content`), and 10 hit `max_tokens`. This combination is meant for `/tokenize` or scoring, not for chat generation. Elsewhere, special-token text appears in 2 "before" replies (`<｜end▁of▁thinking｜>`) and in no "after" reply.

## Details

- **Root cause:** `render_message` appends the assistant turn prefix only after user-like messages, and `encode_messages` takes no generation-prompt arguments, so `apply_chat_template` drops `add_generation_prompt` and `continue_final_message`.
- **Encoder** (`deepseek_v41.py`, `deepseek_v41_encoding.py`; same logic as #57882, without its final-`system` rule, which #62459 covers):
  - `apply_chat_template` passes `add_generation_prompt` and `continue_final_message` to `encode_messages`.
  - A final assistant message gets the same assistant transition that a user message gets, unless `add_generation_prompt` is false or the message is already left open with `wo_eos`. Without the `wo_eos` check, a direct `encode_messages` caller that leaves the final message open would get a new `<｜Assistant｜>` turn right after it, with no EOS in between.
  - `continue_final_message` implies no generation prompt, keeps the final message open, and requires a final assistant message.
- **Parser** (`vllm/parser/deepseek_v41.py`): `turn_boundary_tokens = {<｜User｜>, <｜Assistant｜>}`. Without it, #61857 leaves V4.1 in the reasoning state, and a continued answer after `</think>` is returned as `reasoning` with empty `content`. It is in this PR because `continue_final_message` only works end to end with it: without the parser change, continuing a final assistant message whose reasoning is already closed returns the continuation as reasoning.
- **Tests:** five tokenizer tests from #57882 (14 cases; its final-`system` test is left to #62459), the reference fixture test now checked without and with the generation prompt for the four fixtures that end with an assistant message, one test that a final assistant message left open with `wo_eos` gets no new turn (6 cases), and one new parser test (current-turn vs. earlier-turn `</think>`, streaming and non-streaming).
- **Behaviour change:**
  - A client that sends an assistant prefill without `continue_final_message` used to get a continuation after EOS, which often came back empty or garbled (40/40 empty for the code-prefix shape in the matrix above). How often depends on the prefill and the sampling settings: HumanEval-instruct, with its own prefill and T=0, still scored 0.4573 this way. It now gets a new turn. To continue the prefill, send `continue_final_message=true`.
  - A caller that passes `add_generation_prompt=false` for a conversation ending with a user (or developer, or system) message, for example for `/tokenize` or a reward model, used to get the assistant turn prefix anyway, because the flag was ignored. It now gets the prompt without it, as the flag asks. This matches the Rust frontend since #56593.
  - lm-eval `humaneval_instruct` sends such a prefill without the flag, so its score drops to 0: in a new turn the model writes a complete fenced answer, and the scorer appends the reply to the prefill and cuts it at the first `` ``` ``. With `continue_final_message=true` the same task scores 0.9573 (0.3841 before, because the flag was ignored).
  - `test_reference_encoder_fixtures` changes because fixtures 1 to 4 end with an assistant message. The reference encoder has no generation-prompt control and encodes such a conversation as closed history; `add_generation_prompt=false` still reproduces it exactly, and the default adds the assistant turn prefix.
  - The same semantics are proposed for the Rust frontend in #62189, so both frontends render these requests the same way. #62189 will also get the rule that a reasoning-only continue leaves `<think>` open.
- V4 (`deepseek_v4` tokenizer) has the same encoder gap and is tracked in #46257; V3.2 is handled in #64493. This PR only touches V4.1.
