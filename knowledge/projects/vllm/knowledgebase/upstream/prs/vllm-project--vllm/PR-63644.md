# [Perf][Beam] Fuse FP8 KV-cache insertion and query quantization into QK-norm/RoPE

[Upstream PR](https://github.com/vllm-project/vllm/pull/63644) · state: open · merged: False

## Original PR description



## Overview

This PR fuses FP8 KV cache writes and query quantization into Beam's QK-norm/RoPE kernel, replacing three separate kernels (QK-norm/RoPE, `scaled_fp8_quant` on Q, and `reshape_and_cache_flash`) with one for both the target model and DFlash2 drafter.

**Duplicates**: No open PR does this. #63510 keeps the BF16-only insert. #57682, #38621 and #59035 are compile-time fusion passes for models built from vLLM’s standard norm/RoPE/cache ops, which Beam’s custom kernel doesn’t go through.

**AI assistance**: Claude is used throughout development, and I reviewed every line of code.

## Claims

- Decode step time drops on `Beam-1.0-501B-A23B-NVFP4` with an FP8 KV cache:
  - TP4 + DFlash2: 3.8% at concurrency 1, 1.6% at concurrency 64.
  - TP4 w/o spec decode: 5.5% at concurrency 1, 2.4% at concurrency 64.
- Outputs are numerically identical:
  - The fused kernel writes the same FP8 bytes as the separate quant and cache-insert kernels it replaces.
  - Greedy outputs are token-identical to main.
  - GSM8K and the spec-decode acceptance length are unchanged.

## Validation

All runs on B200s, comparing main with this PR.

- **Unit tests:** `pytest tests/models/test_beam_numerics.py tests/models/test_beam_construction.py` passed. The kernel tests capture the fused call in a CUDA graph and require FP8 Q and the whole cache to match `scaled_fp8_quant` and `reshape_and_cache_flash` byte-wise, including NaN and inf/-inf.
- **Correctness (TP4):**
  - Greedy outputs on 16 prompts are token-identical to main with an FP8 cache, a BF16 cache, and `--enforce-eager`.
  - GSM8K 5-shot (vLLM's `tests/evals/gsm8k/gsm8k_eval.py`, 1319 questions) goes from 0.939 to 0.937 (± 0.007), and the acceptance length from 5.50 to 5.50.
- **Sync and JIT checks:** with `VLLM_GPU_SYNC_CHECK=error`, an eager FP8 + DFlash2 server ran with no syncs.
- **Performance:** Median ITL from `vllm bench serve` (ISL=8192 / OSL=512, 1024 prompts per concurrency, `--max-concurrency c`) reduces comparing to `main` (w/o fusion). With spec decode, acceptance is fixed to 3.0 so both builds do the same work per step.

## Details

- **Kernel**: New `constexpr` flags (`FP8_Q`, `FP8_KV`) add FP8 stores; the BF16 path is unchanged. To match the replaced ops byte for byte:
  - K is rounded to BF16 first, as main stores it before the cache insert.
  - K/V use `div_rn(x, scale)`, then a NaN-preserving clamp to 448/-448.
  - Q uses `x * div_rn(1, q_scale)` with `scaled_fp8_quant`'s clamp order.
  - Scales are read on device, so CUDA graphs need no host sync.
- **When it fuses**: A BF16 cache, or an `fp8`/`fp8_e4m3` cache with per-tensor scales. Per-head scales and `fp8_e5m2` keep the existing path. Backend checks are unchanged.
