# [Build] Tag wheels cp311-abi3 and look up release wheel URLs in install docs

[Upstream PR](https://github.com/vllm-project/vllm/pull/61283) · state: open · merged: False

## Original PR description



## Overview

Tag vLLM wheels `cp311-abi3` instead of `cp38-abi3`, and make the release install snippets look up the wheel URL instead of hardcoding the filename.

## Claims

- The `cp38-abi3` tag is wrong: `spinloop` and `fs_io_C` import stable-ABI symbols added in Python 3.10 and 3.11. `requires-python = ">=3.11"` keeps this harmless for installers, but the tag should say 3.11.
- The release install snippets hardcode the wheel filename, including `cp38-abi3`, so they'd break with the new tag. They now look the URL up from the release's assets, which works for both tags. (The CPU snippets also currently point at `manylinux_2_34`, but v0.31.0 ships `manylinux_2_39`; see #58270.)

## Validation

`abi3audit` on the published v0.31.0 CPU x86 wheel (`vllm-0.31.0+cpu-cp38-abi3-manylinux_2_39_x86_64.whl`):

| Extension | Needs | Symbols newer than 3.8 |
|---|---|---|
| `spinloop.abi3.so` | 3.11 | `PyBuffer_Release` (3.11), `PyObject_CallNoArgs` (3.10) |
| `fs_io_C.abi3.so` | 3.11 | `PyBuffer_Release`, `PyObject_GetBuffer` (3.11), `PyUnicode_AsUTF8AndSize` (3.10) |
| `_C`, `_C_AVX2`, `_C_AVX512`, `_rust_tool_parser` | 3.8 | none |

- A CPU wheel built from this branch (macOS arm64, `setup.py bdist_wheel --py-limited-api=cp311`) is named `...-cp311-abi3-...whl`, and `abi3audit` reports no mismatches.
- In the published v0.31.0 CUDA (x86_64) and XPU wheels, every abi3 extension (13 and 1) needs at most 3.11; only `spinloop` and `fs_io_C` need more than 3.8. The CUDA wheel also bundles DeepGEMM as per-version `_C.cpython-3{10..14}` builds, which this PR doesn't change.
- A CUDA wheel built from this branch on an A40 with `docker/Dockerfile`'s command (`setup.py bdist_wheel --py-limited-api=cp311`, using `VLLM_USE_PRECOMPILED=1` to skip compiling) is named `...-cp311-abi3-linux_x86_64.whl` (CI's `detect-manylinux-tag.py` rewrites the platform tag later). `abi3audit` passes for all 13 extensions; the wheel installs into a clean Python 3.12 venv and its CUDA libraries load on the GPU; Python 3.10 refuses it via `requires-python`.
- The three doc snippets, run as written, resolve to existing assets for both `latest` (v0.31.0) and `tags/v0.30.0` (CPU x86_64, CPU aarch64, `+cu129` x86_64).
- Nothing in the release tooling depends on `cp38`: `generate-nightly-index.py` parses tags generically, `detect-manylinux-tag.py` only rewrites the platform tag, and the precompiled-wheel lookup in `setup.py` ignores the Python tag.

## Details

- `docker/Dockerfile` (3 places), `Dockerfile.cpu`, `Dockerfile.xpu`, `.buildkite/scripts/build-macos-wheel.sh`, and the usage comment in `tools/setup_deepgemm_pythons.sh`: `--py-limited-api=cp38` → `cp311`.
- `gpu.cuda.inc.md`, `cpu.x86.inc.md`, `cpu.arm.inc.md`: select the wheel from the latest release's assets with `jq` (the snippets already used the GitHub API for the version). A comment shows how to pin a release (`tags/v<version>`). The CUDA snippet's example `CUDA_VERSION=130` matches no asset, because 13.0 is the unsuffixed default wheel; that's unchanged from `main`, where the hardcoded URL 404s, and is left for a separate docs fix.
- `tools/build_rust.py`: the commented PyO3 template uses `abi3-py311`.
- Example filenames in `nightly_builds.md`, `setup.py` and `generate-nightly-index.py` describe already-published wheels and are left as is.
- The published macOS wheel is tagged `cp312-cp312` even though `build-macos-wheel.sh` passes the flag (a local macOS build with it is `cp311-abi3`). I haven't tracked down why; the script is updated only for consistency.
- Follow-up: ROCm, s390x, ppc64le and `.github/workflows/scripts/build.sh` don't pass the flag and are unchanged, so their wheels keep a per-version tag. Setting the tag once in `setup.py` would cover every build path, but it changes the ROCm wheel names, so it belongs with the ROCm owners.
- Compatibility: scripts that build release URLs with `cp38-abi3` in the filename (as the old docs did) will 404 for releases after this lands. Wheels found through PyPI or the nightly index are unaffected.

**Duplicate check.** No open PR changes the wheel tag or these install snippets.
