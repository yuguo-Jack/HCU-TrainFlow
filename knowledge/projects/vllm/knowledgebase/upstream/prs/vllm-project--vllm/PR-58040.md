# Fix QSA metadata with graph-padded query offsets

[Upstream PR](https://github.com/vllm-project/vllm/pull/58040) · state: open · merged: False

## Original PR description

## Summary

Clamp the QSA mapped-token count to `num_actual_tokens` in both Triton and Torch metadata builders. Graph capture may pad `query_start_loc_cpu[-1]` beyond the real token count, while QSA metadata buffers only contain real tokens. Without the clamp, metadata construction can read or write past those buffers during padded decode.

Add a CPU regression test with one real decode token and three graph-padding slots. The test checks the real token request mapping, logical position, visible block count, and slot mapping.

## Validation

- QSA CPU regression selection in the existing A3 test container: 8 passed (including the original padded-decode test on the same implementation and related QSA tests).
- The new four-offset regression scenario was executed directly against the patched Torch builder and returned the expected metadata `[0], [2400], [2401], [0]`.
- `compileall` and `git diff --check` passed.

CUDA/Triton execution was not available in this A3 environment; the equivalent Triton bound change is included but requires CUDA CI coverage.
