# [Rust Frontend] Compose answer constraints into parser-owned output grammars

[Upstream PR](https://github.com/vllm-project/vllm/pull/60781) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->
## Overview

Step 4 of the parser-owned output grammar rollout, stacked on #59190 (Kimi K3 full-output grammar). The request's own structured-output constraint (`response_format` or `structured_outputs`, the "answer constraint" below) now composes into the parser-built output grammar instead of competing with it. Composition follows the Python frontend's `Parser._apply_structural_tag` (#56086).

Most of the diff is regenerated grammar replay snapshots: about 3,300 of the roughly 4,100 added lines are under `rust/src/chat/tests/grammar_replay/`. The code and test changes are about 800 lines.

## Claims

- `tool_choice=auto` with tools and an answer constraint keeps both: split parsers build `Or[tool calls built as required, answer]` inside the reasoning wrapper. Today a tool grammar replaces the answer constraint, so the answer is unconstrained; without a tool grammar the native constraint applies after reasoning and leaves no room for tool calls.
- With no callable tool (no tools, or `tool_choice=none`), a parser with a reasoning grammar wraps the answer and constrains the output from token zero (`reasoning_ended = Some(true)`) instead of through the engine's reasoning gate.
- Kimi K3 places the answer inside its `response` channel for every tool choice. `auto` and `required` keep the paths with both an answer and calls, and allow the empty `response` channel the chat template writes before tool calls.
- `required` and named tool choices on split parsers keep today's behavior: the answer constraint is ignored with a one-time warning, as in Python.

All 74 generations (36 existing, 38 new) pass with XGrammar 0.2.7 (the harness pin) and 0.2.8 (`requirements/common.txt`): 70 are replayed from token zero, and the 4 final-output-only grammars (MiniMax M3, Seed-OSS) are compiled.
- GPU smoke on GB200 with the Rust frontend (temperature 0, JSON schema `{answer: string, confidence: number}`), checking that every response is either schema-valid content or valid tool calls:
  - Qwen3-8B, `qwen3` reasoning + `hermes` tools (reasoning wrapper, from token zero): 10/10. `none` and `auto` with an arithmetic prompt return schema-valid content after the reasoning; `auto` with a weather prompt returns a valid call, streaming and not; thinking off returns content without reasoning; `required` returns a call and logs the ignored constraint once; a request without tools returns schema-valid content; 16 concurrent mixed requests return 8 calls and 8 schema-valid answers.

This first-request issue predates this PR; see Details.
- Not run: model evaluation, and Kimi K3 serving (its weights need several nodes; the grammar replay covers its token-zero grammar).

## Details

- Answer normalization (`answer_format`) mirrors Python's `structured_outputs_to_format`: JSON schema, JSON object, regex, choice, EBNF grammar, and structural tags in both the current `format` and legacy `structures`/`triggers` shapes. Like Python, it ignores the request's whitespace and `additionalProperties` options, which no backend reads per request. Lark grammars (Rust has no Lark-to-EBNF converter) and structural tags that do not parse keep their native constraint.
- The output processor normalizes the answer at construction, next to the tools and tool choice it already captures, so `ChatOutputProcessor::build_output_grammar` keeps its signature.
- Tool parsers compose the answer: they implement `build_call_format` for a given tool choice (the default uses the structural-tag builder), and the provided `ToolParser::build_visible_format` adds the answer on top. `CombinedParser` takes that visible language, or the answer alone without a tool grammar, and lets the reasoning parser wrap it.
- A grammar is built whenever a reasoning or tool parser is active; a request with neither keeps its own constraint. When the reasoning parser cannot wrap an answer-only grammar (`kimi`, `minimax_m3`, `cohere_cmd`, `seed_oss`), the grammar covers the final output, behind the engine's reasoning gate as before; such a request now compiles on xgrammar, where engine-level `disable_any_whitespace` and `disable_additional_properties` do not apply, as for every parser-built grammar.
- Known limits, shared with Python: a tool parser without a structural-tag builder (GLM-4.5, MiniMax M3, Seed-OSS) leaves the answer alone, which excludes tool calls. Required tool grammars built from `triggered_tags` admit text after the calls, so under `auto` a generation can call a tool and then write unconstrained text.
- Structured-output backend: the engine instantiates one backend from the first structured-output request, and the Rust frontend sends native constraints as guidance and parser-built grammars as xgrammar. This predates this PR (strict and required tool grammars already mix with native constraints), but composition moves more requests to xgrammar. On a server with a tool parser and no reasoning parser, a schema request with tools now gets an xgrammar grammar while one without tools stays native on guidance; if the latter arrives first, later composed grammars fail to compile (`KeyError: 'triggers'`, since guidance reads only legacy structural tags). With a reasoning parser, every schema request now gets an xgrammar grammar. Selecting the backend in the Rust frontend is a separate change.
- Replay files now hold each distinct grammar once with the generations of every variant that builds it, since `auto_schema_content` and `auto_schema_calls` build the same grammar.
- Duplicate check: open PRs on Rust structured outputs, response formats, and output grammars include #47176 (request validation in the server) and #50543 (Python K3 rendering); neither composes answer constraints into output grammars.
