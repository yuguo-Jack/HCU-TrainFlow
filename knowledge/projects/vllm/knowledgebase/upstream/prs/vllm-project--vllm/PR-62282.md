# [Bugfix][KV Connector][Mooncake] Wait for all peers before completing failed receives to avoid potential KV block write-after-free

[Upstream PR](https://github.com/vllm-project/vllm/pull/62282) · state: closed · merged: True

## Original PR description



## Overview

Address premature D-side KV block reclamation when one Mooncake P peer fails while another peer can still write to the request's destination blocks (write-after-free).

- [Report failed remote KV loads to the scheduler #50984](https://github.com/vllm-project/vllm/pull/50984): adds error handling at D-side but leaves this bug.
- [#61006](https://github.com/vllm-project/vllm/pull/61006): guards stale scheduler notifications.

These related PRs do not track outstanding peer results for a failed receive.


## Motivation

### Failure mechanism

A D request can receive KV slices from multiple P peers (P0, P1), if a peer (say P0) fails to transfer a request's KV:

1. P0 reports a transfer error while P1 still holds the destination addresses.
2. `_handle_failed_recv()` marks the request failed, reports its invalid blocks, and **adds it to `finished_recving_reqs` without waiting for the other peers**.
3. With `kv_load_failure_policy=fail`, the scheduler marks the request `FINISHED_ERROR` and consumes that completion to release its blocks.
4. P1 can subsequently write to those addresses, after the blocks have returned to the pool or been allocated to another request.

Failure notification therefore permits reclamation before all writers have finished. This is a KV-block write-after-free; the underlying registered GPU allocation remains valid, so the stale WRITE can succeed. [#50984](https://github.com/vllm-project/vllm/pull/50984) fixed failure propagation and stranded requests; this reproducer exposes the remaining multi-peer destination-lifetime gap.

To trigger and observe the subtle write-after-free bug, we manually simulate P0 failed write and P1 delayed write: P0 reports `err_reqs` through its existing `MooncakeXferResponse` after a successful WRITE with 5% failure rate per request; P1 waits for a randomly sampled 0–500 ms before submitting WRITE (batch delay = maximum selected-request delay). ## Solution

Each peer keeps a pending request map sharing the existing `PullReqMeta` (`pull_metas.copy()` shallow copy). Success and failure both consume that peer's entry and decrement `pull_tasks_count`, including success after another peer failed. Report the first failure once; publish receives completion only when the count reaches zero. Partial replies, peer-wide errors, and receive exceptions settle only pending entries.

On `FINISH`, requests still pending for that peer are considered to be failed and are settled, covering expired requests omitted by P (otherwise, P0 expires + P1 successes -> `pull_tasks_count` remains positive and D's KV blocks would never be released -- also a mem-leak bug left in the current implementation).

Bootstrap failures with no peer tasks still complete; empty pulls produce no D completion. The fix is confined to connector bookkeeping. It covers error replies followed by the other peers' results; remote quiescence after a local
socket timeout remains outside its scope.

Thanks for catching this! After a careful code investigation I find it to be a new mem-leak bug that already exists before this PR: if P0 succeeds but P1 expires without reporting a result, `pull_tasks_count` stays above zero and D's blocks remain held. Previously, an explicit failure from P0 would immediately publish receive completion and allow reclamation.

This PR waits for all peer results after a failure, so an expired peer’s omitted result can now reserve D's blocks even when another peer explicitly fails. After processing a `FINISH` response, we should add a fallback:
```
if response.status == MooncakeXferResponseStatus.FINISH:
    self._handle_failed_recv(
        pull_metas,
        list(pull_metas),
        "peer finished without reporting a transfer result",
    )
    break
```
It settles the current peer’s pending entries (consider remaining pending requests as failures) and still waits for other peers. I will add another commit with this fallback to cover both the write-after-free and this mem-leak.
