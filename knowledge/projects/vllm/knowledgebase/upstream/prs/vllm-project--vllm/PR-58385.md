# [Bugfix][Frontend] Drop Harmony messages on unrecognized channels in Responses output parsing instead of raising

[Upstream PR](https://github.com/vllm-project/vllm/pull/58385) · state: open · merged: False

## Original PR description

## Purpose

Fixes #58384.

`vllm/entrypoints/openai/responses/harmony.py::_parse_message_no_recipient` raises `ValueError: Unknown channel: <x>` for any channel other than `analysis` / `commentary` / `final`. gpt-oss occasionally emits a header outside that set (we hit `comment` on `openai/gpt-oss-120b` in production logs; #22533 reported `commentaryanalysis` on `/v1/responses` in Aug 2025). Because `harmony_to_response_output` runs when the final `Response` is assembled (`serving.py::responses_full_generator`, line 757), the exception fails the whole request. For a streaming request `responses_stream_generator` calls `responses_full_generator` (line 1383) outside its `except GenerationError` (line 1370), so the SSE connection is closed before `response.completed` even though every earlier event was already delivered; the client sees an incomplete chunked read.

The rest of the Harmony handling already ignores such messages:

- `streaming_events.emit_content_delta_events` (line 599) and `emit_previous_item_done_events` (line 638) return `[]` for an unknown channel with no recipient.
- The chat-completions parser maps it to `_SegmentType.IGNORE` (`vllm/parser/harmony.py:79`).

This PR makes the completed-message parser consistent with them.

### Change

`vllm/entrypoints/openai/responses/harmony.py` (+11/-1): in `_parse_message_no_recipient`, replace `raise ValueError(f"Unknown channel: {message.channel}")` with `logger.warning_once("Dropping Harmony message on unrecognized channel %r; ...", message.channel)` followed by `return []`. The module already has `logger = init_logger(__name__)`; `warning_once` is deduplicated per distinct channel string. No behaviour change for `analysis`, `commentary`, `final`, or any message that has a recipient.

`tests/entrypoints/openai/responses/test_harmony_utils.py` (+45): two tests in `TestHarmonyToResponseOutput` that go through `harmony_to_response_output`, the same entry point `serving.py` uses:

- `test_unknown_channel_with_no_recipient_is_dropped`, parametrized over channel `comment` / `commentaryanalysis` x `incomplete` False / True (4 cases), asserts `[]`.
- `test_unknown_channel_does_not_affect_neighbouring_messages`: `analysis` + `comment` + `final` messages yield exactly a `ResponseReasoningItem("thinking")` and a `ResponseOutputMessage("answer")`.

`tests/entrypoints/openai/responses/test_streaming_events.py` (+29): `TestHarmonyUnknownChannel` pins the existing drop behaviour of `emit_content_delta_events` and `emit_previous_item_done_events` for channel `comment`, so the streaming and completed-message paths cannot drift apart again. These two tests pass before and after the fix.

### Why drop rather than render as text

- An out-of-spec channel header is a malformed control sequence, not content the model addressed to the user; rendering it would surface strings like `commentaryanalysis` to clients.
- In streaming mode the deltas were never emitted, so rendering the message at completion would put an output item into `response.completed` that never had `output_item.added` / delta events.

Trade-off: if an entire reply were emitted on a non-standard channel the client now receives an empty `output` list instead of a failed request; the one-time warning makes this visible in server logs. We are happy to switch to rendering as user-visible text if maintainers prefer that behaviour.
