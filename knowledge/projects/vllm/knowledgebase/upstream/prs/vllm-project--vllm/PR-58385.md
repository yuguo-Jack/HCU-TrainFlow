# [Frontend] Raise VLLMValidationError for an unknown Harmony channel in Responses output parsing

[Upstream PR](https://github.com/vllm-project/vllm/pull/58385) · state: closed · merged: True

## Original PR description

## Purpose

Fixes #58384 (partially, see "Not addressed" below).

`vllm/entrypoints/openai/responses/harmony.py::_parse_message_no_recipient` raises a bare `ValueError("Unknown channel: <x>")` when gpt-oss emits a Harmony message on a channel outside `analysis` / `commentary` / `final` (seen in production as `comment`; #22533 reported `commentaryanalysis`). Per review, this PR keeps that behaviour and raises `VLLMValidationError` instead, consistent with the other `VLLMValidationError` raises in the same module, so the error is classified as a vLLM client-side error rather than an unexpected exception.

## Change

- `vllm/entrypoints/openai/responses/harmony.py` (+1/-1): `raise ValueError(...)` -> `raise VLLMValidationError(...)` (the import already exists).
- `tests/entrypoints/openai/responses/test_harmony_utils.py` (+8): `test_unknown_channel_raises_validation_error`, parametrized over `comment` / `commentaryanalysis`, through `harmony_to_response_output` (the entry point `serving.py` uses).

An earlier revision dropped such messages instead of raising; it was replaced following the review discussion.

## Not addressed

For `stream=true`, the raise still happens when `responses_stream_generator` assembles the final response after the deltas were delivered, so the SSE stream still ends without `response.completed`. Happy to follow up separately (for example emitting a `response.failed` / error event there) if maintainers want that.

- longluubao · comment · 2026-10-09T04:03:43Z · [source](https://github.com/vllm-project/vllm/pull/58385#discussion_r4226497791)

File: `vllm/entrypoints/openai/responses/harmony.py` · line None

Thanks @chaunceyjiang. Agreed that the model should only ever use `analysis`, `commentary` and `final`; the question is what to do when a generated header is outside that set, and today the answer is "fail the finished response". Two reasons this PR stops raising, and I am open to mapping instead of dropping:

1. **Where the raise fires.** `_parse_message_no_recipient` runs inside `harmony_to_response_output`, i.e. when the final `Response` is assembled after generation has completed. For `stream=true`, `responses_stream_generator` calls `responses_full_generator` (serving.py:1408) after its `except GenerationError` block (serving.py:1395), so one unexpected header closes the SSE connection with no `response.completed` although every delta was already delivered to the client. For `stream=false` the whole request returns an error. So the restriction is not protecting the client; it discards a complete generation at the last step.
2. **The rest of the pipeline already tolerates it.** `streaming_events.emit_content_delta_events` and `emit_previous_item_done_events` return `[]` for a segment on an unknown channel with no recipient (streaming_events.py:597), and the chat-completions parser maps it to `_SegmentType.IGNORE` (`vllm/parser/harmony.py:76`). The completed-message parser is the only place that raises, which is why the failure only shows up at assembly and only on `/v1/responses`.

What we have actually seen are malformed headers rather than a fourth channel: `comment` (from an `openai/gpt-oss-120b` deployment; most likely a truncated `commentary`) and `commentaryanalysis` (two headers run together, #22533).

If you would rather map than drop, I can change the branch to resolve the header by prefix against the three known names (`comment` -> `commentary`, `commentaryanalysis` -> `commentary`, `fin` -> `final`, and so on) and keep the `warning_once` + drop only for a header that matches nothing. One caveat to decide on: in streaming mode the deltas of such a message were never emitted (the dispatchers dropped them), so a mapped item would appear in `response.completed` without earlier `output_item.added` / delta events, unless the dispatchers are given the same mapping. Which behaviour do you prefer: (a) drop as in this PR, (b) prefix-map at assembly only, or (c) prefix-map in both the dispatchers and the assembly parser? I will update the PR accordingly.
