# [Core] Add XPress speculative decoding method

[Upstream PR](https://github.com/vllm-project/vllm/pull/54448) · state: open · merged: False

## Original PR description


## Purpose

Adds **XPress**, a causal refiner for block-diffusion drafters, as a V1 speculative decoding method alongside DFlash and DSpark. Paper: https://arxiv.org/abs/2608.02438

A block-diffusion drafter such as DFlash proposes a whole block in one forward pass, which makes drafting cheap, and decodes it from per-position marginals, which makes it inaccurate: token *k* is drawn without seeing what the drafter chose at *k-1*. The target verifies conditionally, so blocks that are individually plausible but jointly improbable are rejected early, capping acceptance length. 


## Design

XPress adds a small head that reads the drafter's per-position hidden state, a block-global summary and the previous token, fuses them into a rank-256 bottleneck, mixes across the block with a lower-triangular (causal) mixer, and reads back out as a bias on the base logits. Everything except the two vocabulary projections lives in the bottleneck (~80M params, 96% of
which are those two matrices).

Because the mixer is true causal rather than local smooth, the block is resolved by **Jacobi iteration** rather than a left-to right loop: the same call runs K times, each pass re-feeding the previous pass's argmax, so the serial depth is a constant K instead of the block size. Both stages are fixed-shape and loop-free, so the whole draft step is CUDA-graph capturable, which is what makes K passes cheap: they cost K matmuls, not K kernel launches. Two Triton kernels keep a pass at three launches (`xpress_latent_pass`, and a fused add+argmax that writes straight into the block buffer so the [N, B, V] sum is never materialized).

`XPressSpeculator` subclasses `DFlashSpeculator` and overrides only draft generation; attention, KV cache setup and weight sharing are inherited unchanged. Existing files gain **39 lines** of method registration; everything else is new files.

## Test Plan

```bash
# e2e (80GB GPU; public Qwen3-8B + XPress checkpoint pair): full GSM8K at temperature 0,
# accuracy and acceptance metrics against reference values -- same protocol as the
# DFlash and DSpark tests in acceptance_rates/
pytest tests/v1/e2e/spec_decode/acceptance_rates/xpress/test_xpress.py -s
```

The e2e test guards GSM8K accuracy and acceptance rate and length against references, with an upper bound on acceptance length. Note that acceptance length moves by about 0.5% with anything that changes the vLLM config hash, because the hash keys torch.compile's cache and autotuning then picks different kernels, shifting the floating-point reduction order so that near-tie draft tokens flip. Under `enforce_eager=True` the paths are identical.

The e2e acceptance length is measured under the 5-shot completion GSM8K protocol the DFlash and DSpark tests share, so it is comparable to their references on the same target (DFlash 3.5, DSpark ~4.0) and, like theirs, lower than the chat-template numbers below.

The benchmarks below were measured on vLLM `82ae4164`. This PR has since been merged with current main with no functional change to the XPress path; acceptance length is deterministic and unaffected, and absolute throughput moves with upstream scheduler and kernel work, so the paired ratios are what to compare.

Qwen3-8B on one H200, FlashAttention 3, CUDA graphs and prefix caching on, greedy, K=6, `num_speculative_tokens=15`, `max_model_len=8192`, up to 2048 new tokens. Seven benchmarks x five batch sizes (1/4/16/32/64), three-way against the Markov head and the bare drafter, two independent rounds for xpress and dspark.

@tomasruizt I am sharing the re-collected evaluation results with top-c sweeping. 

**1. Acceptance is essentially flat in top-C, and saturates by 512.**

I Swept `xpress_topc` over `{full vocab, 128, 512, 1024}` on five benchmarks with Qwen3-8B target, `Qwen3-8B-XPress-b16` draft, H200, `num_speculative_tokens=15`, greedy, `enable_thinking=False`. The acceptance length results are shown below:

| benchmark | n | off (full vocab) | C=128 | C=512 | C=1024 |
|---|---|---|---|---|---|
| gsm8k | 128 | 9.580 | 9.663 | 9.663 | 9.663 |
| math500 | 128 | 9.531 | 9.537 | 9.569 | 9.569 |
| humaneval | 128 | 10.339 | 10.296 | 10.296 | 10.296 |
| mbpp | 128 | 7.398 | 7.339 | 7.329 | 7.329 |
| mt_bench | 80 | 4.426 | 4.357 | 4.372 | 4.372 |


I also repeated the whole sweep at `xpress_num_passes` 7 and 8 as well, for 60 measurements in one run. Across all 15 (benchmark, passes) cells, going from full vocabulary to C=512 moves acceptance length by between **-0.90% and +0.93%, with no consistent sign** . It rises on some tasks and falls on others. There is no per-task tuning to be done as the difference of acceptance length between the full vocabulary and top-c are not significant.

**2. Narrowing to 512 removes most of the per-iteration cost.**

Measured on H100 (Qwen3-8B, V=151936, CUDA-graph replay, x300 median). The per Jacobi iteration cost for batch size=1 is shown below:

| | full-vocab scoring | top-C=512 | |
|---|---|---|---|
| per Jacobi pass | 67.8 µs | 26.3 µs | **-61%** |


So top-c=512 could be a valid default value for XPress in terms of the accuracy and efficiency tradeoff. Therefore, I do not expect an end user to tune this, and agree the value belongs in the model's hf-config rather than as a serving flag.
