# [Frontend][Tool] Add nemotron_v3_compact parser that keeps edge newlines in tool arguments

[Upstream PR](https://github.com/vllm-project/vllm/pull/62289) · state: open · merged: False

## Original PR description



## Overview

Fixes #62078. This adds an opt-in `--tool-call-parser nemotron_v3_compact` for Nemotron 3/3.5 served with a compact chat template, so string tool arguments come through verbatim, including leading and trailing newlines. It follows the same approach #58019 used for MiMo.

## Claims

- Adds `NemotronV3CompactParser` and `nemotron_v3_compact_config`. They behave like `nemotron_v3` except that arguments go through the verbatim (no-trim) converter, and streaming uses a value extender that doesn't trim.
- Registers the tool parser key `nemotron_v3_compact`.
- Existing users see no change. `qwen3_coder` and `NemotronV3Parser` still trim one wrapper newline, as fixed in #48753.
- Adds a Nemotron section to `tool_calling.md` that describes the limit of the stock template and how to opt in.

## Validation

I only ran CPU parser tests (Python 3.12 on WSL2) and didn't load any model weights.

```bash
python -m pytest tests/parser/engine/test_nemotron_v3.py
# 39 passed

python -m pytest tests/parser/engine tests/tool_parsers/test_structural_tag_registry.py
# 6715 passed (includes 382 delegating-replay cases generated for nemotron_v3_compact)
```

To check that the new tests catch the bug, I ran them against `NemotronV3Parser`. That gives 13 failures, all of them values with an edge newline (`"alpha\n\nomega\n"`, `"\nalpha"`, `"\n"`, `"\n\n"`, non-streaming and with streaming chunk sizes 1/7/1000). Values without an edge newline pass on both parsers.

`ruff check`, `ruff format`, `tools/pre_commit/mypy.py 3.11` and the SPDX, forbidden-imports, lazy-init and test-tethering hooks are clean on the changed files.

I haven't tested this end to end. The affected checkpoints (`NVIDIA-Nemotron-3.5-Lightning-30B-A3B`, `NVIDIA-Nemotron-3.5-Super-VL-120B-A12B`) don't fit on my 8 GB GPU, so I couldn't serve a real model with a compact template. If someone with the hardware could run the `write_file` repro from the issue with `--tool-call-parser nemotron_v3_compact` and a compact template, I'm happy to provide the template.

## Details

### Root cause

The stock template renders each value as `<parameter=NAME>\n{value}\n</parameter>`. When a value ends in a newline, that newline and the template's closing newline are the same character in the same position, so `_trim_wrapping_newlines` has no way to tell them apart. As the issue says, the parser can't fix this for the wrapped format.

### Design

I kept the change opt-in, the same way #58019 did: a separate parser variant behind its own `--tool-call-parser` key, with the existing path untouched. Simply turning off the trim for the stock template would leave a stray newline on every value that doesn't end in one.

`NemotronV3Parser` gets a small `_engine_config()` hook so the subclass can swap in its config without duplicating `__init__`. The Nemotron reasoning/content swap carries over unchanged, and a test covers it. The new config reuses `_mimo_arg_converter` and `_param_value_extender(trim_newlines=False)`, so there's no new conversion code.

`NemotronV3CompactToolParser` keeps `structural_tag_model = "qwen_3_coder"`. Nemotron uses the same tag framing as Qwen3-Coder (`<tool_call>\n<function=...>\n ... \n</function>\n</tool_call>`). xgrammar's `mimo` tag drops the newlines between tags, so it doesn't match.

### Strict mode

In `qwen_xml`, string values are raw text, so a structural tag can't force the compact framing. Whether the model writes `{value}` or `\n{value}\n` comes down to the template. The stock template's system prompt also shows the wrapped format as the example, so a compact template has to change both the tool-call instructions and how past calls are rendered (`<parameter=NAME>{value}</parameter>`).

### Duplicate check

I searched open PRs for `62078`, `qwen3_coder newline` and `_trim_wrapping_newlines` and found nothing that covers this. The closest open PRs, #60770 and #53739, deal with Hermes parallel calls and flushing streamed arguments.

### Open questions

1. Is a new parser key the right way to opt in, or would you prefer selecting the converter some other way?
2. Should this PR also add a compact template under `examples/` (e.g. `tool_chat_template_nemotron_v3_compact.jinja`), or should that be left to the model publisher?
