# [Bugfix] Bump tokenspeed-mla to 0.2.21 to fix nanobind conflict with Triton 3.9

[Upstream PR](https://github.com/vllm-project/vllm/pull/61125) · state: open · merged: False

## Original PR description

## Overview

`tokenspeed-mla` depends on `tokenspeed-triton` which uses nanobind. Upstream Triton also switched to nanobind in 3.9 (triton-lang/triton#10283). Older `tokenspeed-triton` builds register the same C++ types in nanobind's shared registry, so loading both aborts with `Critical nanobind error: refusing to add duplicate key "PAD_ZERO"`. This breaks vLLM CI on the torch 2.15 RC and nightly lanes (pytorch/test-infra#9050).

[`tokenspeed-triton` 3.9.10.post20261008](https://github.com/lightseekorg/triton/tree/release/3.9.10.post20261008) uses its own nanobind domain, so the copies no longer collide, and `tokenspeed-mla` requires it from 0.2.20. This PR bumps the `tokenspeed-mla` pin from 0.2.15 to 0.2.21 to pick up that fix.

## Claims

- Fixes the `PAD_ZERO` abort with Triton 3.9.
- No numerical change on the TokenSpeed MLA path.

## Details

- Mechanism: neither upstream Triton nor older `tokenspeed-triton` sets `NB_DOMAIN`. The fixed `tokenspeed-triton` sets `NB_DOMAIN=tokenspeed`, and `tokenspeed-mla` 0.2.20+ requires it (lightseekorg/tokenspeed#2134).
- The 0.2.15 pin still allows the old `tokenspeed-triton`; the bump makes the fixed version required.
- Also picks up lightseekorg/tokenspeed#2132, which fixes an illegal memory access in decode when `tokenspeed_mla_min_split_kv` > 1 produces 256 MiB or more of partials.
- Authored with assistance from Claude.
