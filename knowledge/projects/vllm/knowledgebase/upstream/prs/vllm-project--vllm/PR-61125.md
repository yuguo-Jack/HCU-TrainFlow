# [Bugfix] Bump tokenspeed-mla to 2.0.2 to fix nanobind conflict with Triton 3.9

[Upstream PR](https://github.com/vllm-project/vllm/pull/61125) · state: closed · merged: True

## Original PR description

## Overview

`tokenspeed-mla` depends on `tokenspeed-triton` which uses nanobind. Upstream Triton also switched to nanobind in 3.9 (triton-lang/triton#10283). Older `tokenspeed-triton` builds register the same C++ types in nanobind's shared registry, so loading both aborts with `Critical nanobind error: refusing to add duplicate key "PAD_ZERO"`. This breaks vLLM CI on the torch 2.15 RC and nightly lanes (pytorch/test-infra#9050).

[`tokenspeed-triton` 3.9.10.post20261008](https://github.com/lightseekorg/triton/tree/release/3.9.10.post20261008) uses its own nanobind domain, so the copies no longer collide, and `tokenspeed-mla` requires it from 0.2.20. This PR bumps the `tokenspeed-mla` pin from 0.2.15 to 2.0.2 to pick up that fix.

## Claims

- Fixes the `PAD_ZERO` abort with Triton 3.9.
- Passes the TokenSpeed MLA correctness and CUDA graph tests on B200.

## Details

**Changes from 0.2.15 to 2.0.2:**

- The fixed `tokenspeed-triton` sets `NB_DOMAIN=tokenspeed` (lightseekorg/tokenspeed#2134).
- Also picks up lightseekorg/tokenspeed#2132 (0.2.20), which fixes an illegal memory access in decode when `tokenspeed_mla_min_split_kv` > 1 produces 256 MiB or more of partials.
- DCP visibility/masking and empty-shard output/LSE handling (0.2.16, lightseekorg/tokenspeed#1853), plus decode synchronization and zero-tile guards. The added `local_visible_lens` argument defaults to `None`; vLLM does not pass it.
- CuTe DSL 4.8 compatibility cleanup (0.2.17, lightseekorg/tokenspeed#2048), compatible with vLLM's existing CUTLASS DSL pin.
- An SM107 FP8-output decode path (0.2.18, lightseekorg/tokenspeed#2060) and subsequent scheduling/softmax tuning (2.0.1, lightseekorg/tokenspeed#2213). vLLM's current B200 call uses BF16 output and does not select this path. SM107 runtime changes were not tested here.
- Unused helper cleanup (lightseekorg/tokenspeed#2278). Existing vLLM decode/prefill calls remain compatible.
- Authored with assistance from Codex.
