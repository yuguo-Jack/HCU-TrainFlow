# [Bugfix][KV Connector] Fix DecodeBenchConnector crash on hybrid/bounded KV cache groups

[Upstream PR](https://github.com/vllm-project/vllm/pull/61543) · state: closed · merged: False

## Original PR description



## Overview

Fix `DecodeBenchConnector` crashing the whole engine on the first request for hybrid / bounded KV-cache-group models (e.g. GLM-5.3-Flash: MLA + KDA Mamba + kpool tail), and for any model with sliding-window groups:

```
AssertionError: DecodeBenchConnector block range exceeds allocated blocks:
request=..., group=1, range=[0, 130), allocated=1
```

Worker-side hybrid support landed in #54647; the scheduler-side block selection was missed. Same class of group-shape assumption as #55035 (offloading scheduler). Checked open PRs #57884, #56473 and issue #57847 — none address this path; no duplicate.

## Claims

- `DecodeBenchConnector` no longer crashes when a KV cache group's allocation is smaller than `cdiv(tokens, block_size)`: MambaSpec groups (fixed per-request state) and bounded-window groups (SlidingWindowSpec and subclasses, e.g. kpool tail rings) now fill their allocated blocks instead of asserting.
- Standard token-paged attention groups keep the exact previous behavior, including prefix-cache protection (locally computed prefix blocks are never filled).

## Validation

- New regression tests in `tests/v1/kv_connector/unit/test_decode_bench_connector.py`:
  - `test_decode_bench_connector_hybrid_mamba_group_per_request_fill`
  - `test_decode_bench_connector_bounded_window_group_fills_allocated`
- `HF_HUB_OFFLINE=1 python -m pytest tests/v1/kv_connector/unit/test_decode_bench_connector.py -q` → 31/31 pass.
- E2E on GLM-5.3-Flash, 4xH200, `-tp 2 -dp 2 -ep`, MTP `num_speculative_tokens=3`, prefix caching on, `--kv-transfer-config '{"kv_connector":"DecodeBenchConnector","kv_role":"kv_both"}'`:
  - Before: first request crashes EngineCore (`allocated=1` for the kpool-tail group with block_size 8 vs computed 130 blocks), ApiServer dies, serve exits.
  - After: full `vllm bench serve` battery (random 1k/8k ISL, conc 8-256) plus a `prefix_repetition` run (real prefix-cache hits, exercising the `num_local>0` path) pass with zero errors.
- CI note: unit tests run in the existing kv_connector CI job; the hybrid-model E2E path needs hardware/checkpoint not available in CI, validated manually as above.

## Details

Root cause: `update_state_after_alloc` treated every non-`CircularBufferSpec` group as token-paged, computing `num_computed_blocks = cdiv(total_computed_tokens, block_size)` and asserting it fits the allocation. That invariant only holds for plain token-paged attention:

- `MambaSpec` (not an `AttentionSpec`) allocates a fixed number of state blocks per request.
- `SlidingWindowSpec` and subclasses allocate only enough blocks for the window (a kpool tail ring allocates exactly 1).

Fix: apply token-range math only when all layer specs are non-circular `AttentionSpec`; otherwise select all allocated blocks. Inside the token-paged branch, when the computed range exceeds the allocation (bounded-window case), fill the allocated blocks instead of asserting. The in-range assert on `external_block_start` is kept.

Tradeoff: for bounded groups the connector fills all allocated blocks rather than a token-derived subrange — for a decode bench connector this is the desired behavior (the allocated blocks are exactly what decode reads), and it can never corrupt prefix-cached blocks because bounded groups are not prefix-cacheable in this path.

Closing this for now — an update after digging deeper into where this actually reproduces.

**Where it crashes:** the official **v0.31.0 release**, GLM-5.3-Flash, E2E: its kpool tail cache is a 1-block `KpoolTailSpec` group, which trips the assert on the very first request (`range=[0, 130), allocated=1`) and takes the whole engine down. (Verified the pod's `decode_bench_connector.py` is byte-identical to the v0.31.0 tag.)

**Why it no longer reproduces on main with this model:** #57169 replaced the kpool tail with a `CircularBufferSpec` (already covered by the existing `is_circular_buffer` path), and the Mamba groups pass the assert in both cache modes (`align` keeps position-indexed block rows so the token math happens to hold; `none` uses `mamba_block_size == max_model_len` so `cdiv` is always 1).

**What remains true on main:** the assumption in `update_state_after_alloc` — every non-circular group is token-paged — is still incorrect. The regression tests included here fail on main's code with `SlidingWindowSpec` / fixed-size `MambaSpec` groups, so any current or future bounded-spec group (sliding-window models, kpool-style rings, custom specs) can still trip it; I did not get to an E2E run with a sliding-window model on main. Users serving GLM-5.3-Flash with `DecodeBenchConnector` on the v0.31.0 release also remain affected.

Since the in-tree exposure on main is currently latent, I'm closing this to not spend reviewer time; the branch (`fix/decode-bench-connector-bounded-groups`) stays around with the fix + tests, and I'm happy to reopen if a bounded-spec group lands in main or someone hits the assert in the wild.

Thanks!
