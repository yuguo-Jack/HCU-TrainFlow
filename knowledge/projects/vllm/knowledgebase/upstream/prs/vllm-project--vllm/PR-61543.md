# [Bugfix][HiSparse][KV Connector] Fix DecodeBenchConnector crash on bounded KV cache groups

[Upstream PR](https://github.com/vllm-project/vllm/pull/61543) · state: closed · merged: True

## Original PR description

## Overview

`HiSparse` + `DecodeBenchConnector` **crashes** on `GLM-5.3` when `ISL > device_buffer_size(4096)`.

```
AssertionError: DecodeBenchConnector block range exceeds allocated blocks: request=chatcmpl-bd27629bd71bb94d-9ff77f54, group=22, range=[0, 87), allocated=64
```

The assertion fires in the scheduler on the first qualifying request, EngineCore goes fatal, and the whole serve instance dies. ISL ≤ 4096 passes only coincidentally (see Root Cause).

## Reproduction

Single 8xH200 node, TP8, vllm 0.32.0:

```
vllm serve /models/GLM-5.3 \
  --tensor-parallel-size 8 \
  --max-model-len 256000 \
  --kv-cache-dtype fp8 \
  --gpu-memory-utilization 0.90 \
  --enforce-eager \
  --kv-transfer-config '{"kv_connector":"MultiConnector","kv_role":"kv_both","kv_connector_extra_config":{"connectors":[{"kv_connector":"DecodeBenchConnector","kv_role":"kv_both","kv_connector_extra_config":{}},{"kv_connector":"HiSparseConnector","kv_role":"kv_both","kv_connector_extra_config":{"host_pool_gib":64}}]}}'
```

The assert above comes from this exact setup, on the first request with ~5.5k tokens.

## Root Cause

HiSparse (in-tree since v0.32.0, #60072) adds per-request hot-cache groups via `HiSparseHotSpec` — a direct `KVCacheSpec` subclass with a bounded allocation of `blocks_per_request = cdiv(device_buffer_size, block_size)` blocks. These groups opt out of external KV transfer (`enable_kv_transfer=False`, `vllm/v1/hisparse/layout.py`): they are ephemeral per-request replicas rebuilt from their transferable source group after a connector load. `DecodeBenchConnector.update_state_after_alloc` assumes every non-`CircularBufferSpec` group is token-paged and asserts the computed token range fits the allocation.

The numbers in the assert, decoded:

- `allocated=64`: the hot group's per-request cap — `cdiv(device_buffer_size=4096, block_size=64) = 64`, unrelated to sequence length.
- `range=[0, 87)`: the token-paged formula `cdiv(total_computed_tokens, 64)` for the request's ~5.5k tokens.
- Hence the crash is deterministic for any request with ISL > 4096, and ISL ≤ 4096 passes only because `cdiv(ISL, 64) ≤ 64` by coincidence.
- `group=22` is one of the 78 `hisparse_hot` groups of GLM-5.3.

## Fix

Skip groups that opted out of external KV transfer (i.e. groups missing from `KVCacheConfig.transfer_group_ids`): select no blocks for them at fill-scheduling time, the same way startup-fill groups are already handled. NIXL/Mooncake already key off `transfer_group_ids`; no new spec-shape heuristic is introduced.

This also aligns the fill side with the connector's load-side declaration: `get_loaded_kv_cache_group_ids()` defaults to `prefix_cacheable_group_ids`, which already excludes these groups. Skipping them additionally avoids selecting the 78 `hisparse_hot` layers that are absent from the connector's `kv_caches` (previously warned about on every request).

Groups with `enable_kv_transfer=True` (circular buffers, Mamba, sliding-window attention included) take exactly the same paths as on main — token-range math and the in-range assert are unchanged — so no currently working configuration changes behavior.

## Validation

- New regression test `test_decode_bench_connector_skips_non_transfer_groups`: builds a group from the real in-tree `HiSparseHotSpec` with `enable_kv_transfer=False` and asserts its entry in `reqs_to_fill` is empty; no checkpoint needed, runs in the existing kv_connector CI job. **Fails on main's `decode_bench_connector.py`, passes on this branch** (verified by checking out main's connector and re-running).
- `HF_HUB_OFFLINE=1 python -m pytest tests/v1/kv_connector/unit/test_decode_bench_connector.py -q` → 30/30 pass.
- E2E on the Reproduction setup (single node, TP8 + MultiConnector): on v0.32.0 as released, the first request with ISL > 4096 asserts as above; with the fill-side fix in this branch, the same serving setup handles such requests normally.

Rather than a spec-shape heuristic, can this use the existing `enable_kv_transfer` contract? HiSparse already builds its hot and resident groups with `enable_kv_transfer=False` (`vllm/v1/hisparse/layout.py`), and `KVCacheGroupSpec` documents those as ephemeral replicas rebuilt from their transferable source group after a connector load. `KVCacheConfig.transfer_group_ids` exists for this, and NIXL/Mooncake already use it. Skipping groups not in `transfer_group_ids` (appending `[]`, as is already done for startup-fill groups) would also match this connector's `get_loaded_kv_cache_group_ids()`, which defaults to `prefix_cacheable_group_ids` and so already excludes these groups. As written, `not isinstance(spec, AttentionSpec) and not spec.prefix_cacheable` is effectively a proxy for "is a HiSparse group".
