# [Tool Calling] Migrate llama3_json parser to parser engine

[Upstream PR](https://github.com/vllm-project/vllm/pull/63569) · state: closed · merged: True

## Original PR description

## Overview

llama3_json parser uses legacy implementation for streaming and has buggy implementation. To fix this issue llama3_json parser was migrated to ParserEngine implementation.
Original PR: https://github.com/vllm-project/vllm/pull/51577

**Improtant**:

Current implementation does NOT stream agrs deltas for simplicity reasons. This may affect on latency of streaming tool calls for llama. This perf improvement will stay for future work in a separate PR.

## Testing Done

[bfcl_nonstream.py](https://github.com/user-attachments/files/33303180/bfcl_nonstream.py)

- TheDuyIT · comment · 2026-10-26T08:51:02Z · [source](https://github.com/vllm-project/vllm/pull/63569#issuecomment-6411979474)

Following up on @smiyamoto3's note that arguments now arrive in one delta per call (https://github.com/vllm-project/vllm/pull/63569#discussion_r4371379571): I think this is more than a latency nit for long tool arguments, so raising it here.

1. **Proxy timeouts:** between the tool name and the call's closing `}`, the server sends no bytes at all. Measured live (A100, Llama-3.1-8B): a tool call writing a ~13 KB file goes silent for 34 s on an idle server, 45 s with 16 concurrent requests, and 77 s with 64, which is past the 60 s default idle timeout of NGINX and AWS ALB. An OpenAI SDK client with a 30 s read timeout already fails with `ReadTimeout` on the idle server, before receiving any arguments.
2. **`--sse-keep-alive-interval` doesn't cover it:** it's off by default and only wraps `/v1/chat/completions` and `/v1/completions`. With it set to 10 s, the same prompt on an idle server still went ~60 s silent on `/v1/responses` and ~38 s on `/v1/messages` without a single keep-alive line; those are the endpoints our docs point Codex and Claude Code at.
3. **Turning `stream_arg_deltas=True` back on isn't safe yet:** with the #62334 extender, streamed valid JSON on BFCL v4 drops from 850 to 595/858. The extender also only speeds up top-level strings; arrays and nested objects stay quadratic.

Since this changes behaviour for every existing `llama3_json` streaming user on upgrade, I'd rather it not become the default until argument streaming is back: either restore it here  or land this under an opt-in parser name and keep `llama3_json` on the legacy parser until then. A description note won't reach the operators who hit the timeout.

- arpera · comment · 2026-10-26T15:41:05Z · [source](https://github.com/vllm-project/vllm/pull/63569#issuecomment-6420243314)

I see this issue, yes, it is true. I suggest to do it as a separate PR. As far as I see, models that set stream_arg_deltas=True there is no evidence that they successfully pass BFCL benchmark in streaming mode. I didn't attempt to evaluate these models, but it looks like there is no special what makes them to be able to detect data types of json parts in streaming mode, they are likely to fail BFCL then.
So, if we would like to have (1) model's parser passing BFCL and (2) have good perf in streaming mode we must attempt to implement additional logic in ParserEngine that is not straightforward as I see.

I propose to do changes step by step and focus not only on implementing correct streaming mode for llama parser. All the rest things related to performance in my opinion should be done separately.
