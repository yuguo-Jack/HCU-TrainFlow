# [ROCm][Perf] Opt-in FlyDSL FP8 attention for ROCM_AITER_FA MLA prefill

[Upstream PR](https://github.com/vllm-project/vllm/pull/62447) · state: open · merged: False

## Original PR description

Draft for early review. No blocking issues; no accuracy eval yet.



## Overview

Adds opt-in `VLLM_ROCM_MLA_PREFILL_FLYDSL_FP8=1`. On gfx950 with a bf16 model, the `ROCM_AITER_FA` MLA prefill backend then quantizes Q/K/V to per-tensor FP8 and runs AITER's FlyDSL FP8 attention (shipped in the pinned AITER v0.1.25) for both new tokens and context chunks. The existing ASM FP8 prefill in `ROCM_AITER_MLA` only runs for batches without chunked context, which prefix-cache hits rule out.

## Claims

- Kimi-K3 agentic disaggregated benchmark on MI355X, with #62444 applied: +1.5% total tok/s/GPU, mean TTFT 5.6 s to 4.5 s.
- Prefill attention kernel: 1.3 to 1.8 PFLOP/s in FP8 vs 0.5 to 1.1 PFLOP/s in BF16.
- Off by default.

## Validation

- New `test_rocm_aiter_mla_flydsl_fp8_prefill.py`: 14 passed on MI355X. It builds the backend under the flag and compares output and LSE with an fp32 reference on the dequantized inputs; flipping `causal` or swapping the K/V descales fails it.
- MLA prefill registry/selector tests, `tests/test_envs.py`, `test_rocm_aiter_mla_fp8_prefill.py`: 118 passed. pre-commit clean.
- Accuracy and benchmark details below.

<details><summary>Accuracy, benchmark and test setup</summary>

Accuracy on random inputs (`num_heads` 12 and 16, lengths up to 4096) against a bf16-input fp32 reference: output relative L2 error 4.5% to 5.3%, cosine at least 0.9986, LSE within 0.13; the BF16 kernel gives 0.2%. Against the dequantized-input reference the LSE matches within 1e-4, so the remaining error is FP8 rounding, including the kernel's FP8 cast of P for the PV product. On the benchmark, spec-decode mean acceptance length is 2.93 with the flag and 2.92 without. No lm-eval or GSM8K run yet.

Benchmark: Kimi-K3, agentic multi-turn trace at concurrency 48, 1 prefill + 1 decode instance on 2 nodes of 8x MI355X, TP8 + DCP8, FP8 KV cache, `mla_prefill_backend: ROCM_AITER_FA`. vLLM ROCm nightly `81198e97` with #62444 and this patch mounted; the flag is the only config difference. One run per configuration.

| Total tok/s/GPU | 10616 | 10775 (+1.5%) |

Test setup: the unit tests and the accuracy numbers ran on one MI355X GPU against the FlyDSL sources of AITER v0.1.25 (vLLM's pin), with identical results on v0.1.24.post1.

## Details

- K/V quant is a two-pass Triton absmax + cast, ported from ATOM (MIT; notice kept in the source). Q uses `scaled_fp8_quant` over at most 256 rows. With one row per token-head, `scaled_fp8_quant`'s per-row `atomicMax` serialized and doubled prefill step time.
- Triton sizes are runtime arguments: as constexprs, every new prefill length cost about 0.3 s of host JIT.
- An all-zero tensor gets descale 1e-6 so the kernel never sees a zero scale.
- If `flydsl_flash_attn_fp8_supported` rejects the head config or the model is not bf16, the backend logs a warning and keeps BF16.
- FP8 trades accuracy for speed, hence opt-in.
