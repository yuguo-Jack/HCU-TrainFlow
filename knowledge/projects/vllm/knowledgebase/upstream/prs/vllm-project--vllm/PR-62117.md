# [Attention] Support NVFP4 KV cache at head_dim 512 (Gemma 4) on SM100

[Upstream PR](https://github.com/vllm-project/vllm/pull/62117) · state: open · merged: False

## Original PR description



## Overview


This PR adds that support through the FlashInfer backend on SM100/SM103 (B200/B300).

Adds NVFP4 KV cache support for head_dim 512 attention layers (Gemma 4 global layers) on SM100/SM103 through the FlashInfer backend. Context attention materializes the active NVFP4 pages to FP8 (nvfp4_kv_materialize_fp8) and runs the existing FP8 trtllm-gen context kernel; decode uses FlashInfer PrimTS. Also fixes NaN outputs when KV groups with different NVFP4 page layouts share the block pool, and supports MTP with full CUDA graphs.

Depends on FlashInfer #5720 (PrimTS NVFP4 decode at H512), #6445 (NVFP4 KV prefill at H512) 




## Claims


- [Gemma-4-31B-IT-NVFP4 ](https://huggingface.co/nvidia/Gemma-4-31B-IT-NVFP4) runs with `--kv-cache-dtype nvfp4` on B200/B300, including MTP with full CUDA graphs.
- Accuracy is close to FP8 KV: GPQA Diamond 85.20 vs 85.16, MMLU-Pro 86.21 vs 86.20, AIME 2025 85.26 vs 87.55.
- Throughput matches FP8 KV within a few percent: -2.6% on the perf-eval 8k-in-1k-out workload.
- NVFP4 KV holds 1.65-1.78x more tokens. On a prefix-reuse workload where only NVFP4 fits the shared prefixes, TTFT and E2E improve about 3x.
- No NaN or degenerate outputs; without the zeroing fix, 7-11% of Gemma 4 AIME responses degenerate.
- No JIT compiles while serving: PrimTS decode is planned for every batch size at startup, which takes about +40 s without MTP and about +2 min with MTP.

```bash

```

**Server** (flags as in vllm-project/perf-eval, plus the KV dtype and attention backend)
```bash
VLLM_KV_CACHE_LAYOUT=HND vllm serve nvidia/Gemma-4-31B-IT-NVFP4 \
  --tensor-parallel-size 1 --kv-cache-dtype nvfp4 --attention-backend FLASHINFER \
  --reasoning-parser gemma4 --tool-call-parser gemma4 --enable-auto-tool-choice \
  --hf-overrides '{"text_config":{"use_bidirectional_attention":null,"allow_global_per_layer_attribute_access":true}}'
```
- The FP8 baseline uses `--kv-cache-dtype fp8`.
- MTP adds `--speculative-config '{"model":"<gemma-4-31B-it-assistant>","num_speculative_tokens":3}'`.


## Details


<summary>Prefix reuse vs KV cache size (B300)</summary>

Workload: 60 groups, each a 25-27K shared prefix plus a 2-3K unique tail, OSL 100. Server flags add `--prefix-cache-retention-interval 8192 --kv-cache-memory <bytes>`. Numbers are from the second pass, averaged over 3 runs.

| Config | Concurrency | Prefix hit FP8 -> NVFP4 | Mean TTFT ms | Mean E2E ms |
| --- | --- | --- | --- | --- |
| TP1, 128 GiB KV / GPU | 32 | 32% -> 86% | 8087 -> 2447 | 21269 -> 6331 |
| TP2, 64 GiB KV / GPU | 32 | 33% -> 86% | 4704 -> 1461 | 12243 -> 3769 |
| TP2, 128 GiB KV / GPU (both fit) | 32 | 86% -> 86% | 1428 -> 1537 | 3700 -> 3779 |

- **NaN root cause:** Gemma 4 head_dim 256 and 512 groups share one block pool with different NVFP4 page layouts. A reused block's stale E2M1 bytes can sit where the other layout keeps its E4M3 block scales, and attention multiplies masked positions by them (0 * NaN). New blocks are zeroed only when several NVFP4 layouts share the pool, as vLLM already does for mamba and mixed-precision caches, so models with a single NVFP4 layout are unchanged.
- **Block size:** head_dim 512 kernel block sizes are capped at 64 tokens, because FP8 head_dim 512 context has no 128-token-page kernel.
- **Limitations:** an FP8 query is required, as for the native NVFP4 kernels. The FP8 copy is a temporary workspace outside the KV-cache budget, 4 KiB per token for Gemma 4.
