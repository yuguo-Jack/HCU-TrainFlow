# [Attention] Support NVFP4 KV cache at head_dim 512 (Gemma 4) on SM100

[Upstream PR](https://github.com/vllm-project/vllm/pull/62117) · state: open · merged: False

## Original PR description


## Summary

Adds NVFP4 KV cache support for Gemma 4 on SM100/SM103 (via FlashInfer backend), including MTP with full CUDA graphs.
- **Zero new KV blocks when NVFP4 KV groups share a pool.** The head_dim 256 and 512 groups use different NVFP4 page layouts. Stale bytes in a reused block can be read as block scales and produce NaN.
- **head_dim 512:**
  - Context materializes the active NVFP4 pages to FP8 and runs the FP8 trtllm-gen context kernel.
  - Decode runs on FlashInfer PrimTS. PrimTS plans are built at startup.
- **MTP** for NVFP4 KV at head_dim 512.
- **head_dim 256 (sliding window) also uses PrimTS decode and the FP8 context,** with only the pages inside the window materialized.
  - We saw a clear perf gain over the native NVFP4 trtllm-gen kernels: no FP8 → BF16 output copy, and faster `q_len > 1` decode under MTP.
  - It also avoids token-grouped cubins that the current artifact does not ship.

Depends on flashinfer-ai/flashinfer#5720 (PrimTS NVFP4 decode at head_dim 512), and flashinfer-ai/flashinfer#6445
## Results

Gemma-4-31B-IT, `--kv-cache-dtype nvfp4 --attention-backend FLASHINFER --block-size 64`, MTP with `google/gemma-4-31B-it-assistant`. The baseline is FP8 KV.

**Test cases**
- `pytest tests/v1/attention/test_trtllm_attention_integration.py tests/v1/core/test_kv_cache_utils.py` passes.
- Pre-commit is clean.
- No NaN or degenerate outputs. Without the zeroing fix, 7–11% of AIME responses degenerate.

**Accuracy** (B200, TP1 × DP2, MTP3)

| | FP8 KV | NVFP4 KV |
| --- | --- | --- |
| AIME 2025 (avg@64) | 86.88 | 87.40 |
| GSM8K | 94.16 | 94.77 |
| GPQA Diamond (avg@16) | 85.16 | 85.20 |
| MMLU-Pro | 86.20 | 86.21 |

**SPEED-Bench** (B200, TP2, MTP3, temperature 0)

| Split | Concurrency | Acceptance length FP8 → NVFP4 | Output tok/s NVFP4 / FP8 |
| --- | --- | --- | --- |
| qualitative | 32 | 3.01 → 3.01 | 0.98 |
| throughput_1k | 1 / 8 / 32 | 2.32 / 2.30 / 2.30 → 2.24 / 2.34 / 2.27 | 0.93 / 0.96 / 0.99 |
| throughput_8k | 1 / 8 / 32 | 2.17 / 2.18 / 2.21 → 2.15 / 2.19 / 2.20 | 0.96 / 1.02 / 1.02 |

- Note: AIPerf, temperature 0, max tokens 4096 (qualitative) / 1024 (throughput); acceptance length = 1 + accepted / drafted over the whole split.

**Performance** (B200, TP2, AIPerf, concurrency 1–128, MTP0 and MTP3)

![Throughput vs interactivity, MTP0 and MTP3](https://github.com/user-attachments/assets/90a36b4e-2641-4891-996b-96dd736ee963)

- NVFP4 KV matches FP8 KV from concurrency 8 up: 0.98–1.08× output tok/s across all shapes.
- At concurrency 1–4 on short prompts it is 1–7% slower. Both causes are being addressed in FlashInfer:
  - PrimTS decode at batch 1 is being addressed by runtime split-KV (flashinfer#6925).
  - The per-layer materialize call overhead is being addressed by a validate-once materializer API (flashinfer#8057).

**Capacity.** NVFP4 KV holds 1.77× the tokens of FP8 KV in the same memory: 5.76M vs 3.25M tokens at TP2.

**Prefix-cache hit rate** (B200, TP2, MTP3; 96 shared 16K-token prefixes + 1K unique tail, OSL 128, open loop at 2.2 req/s; KV memory set per point)

![Prefix-cache hit rate and latency vs KV cache memory](https://github.com/user-attachments/assets/5f7967d7-eeee-4a7d-aa72-34be8e160b52)

- With the same KV memory, NVFP4 keeps more prefixes cached. At 48 GiB the hit rate is 46% vs 25%, and mean E2E latency is 28–44% lower up to 64 GiB.
- NVFP4 at 48 GiB matches FP8 at 80 GiB.

**Limitations.**
- FP8 query is required.
- The FP8 copy is a temporary workspace outside the KV-cache budget.
- Kernel pages for head_dim 512 are capped at 64 tokens, so `--block-size 16` is not accepted for Gemma 4 NVFP4.
