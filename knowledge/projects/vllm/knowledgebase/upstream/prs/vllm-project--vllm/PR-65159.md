# [Bugfix][Scheduler] Drain in-flight stale output on sync KV load-failure recovery (#65131)

[Upstream PR](https://github.com/vllm-project/vllm/pull/65159) · state: open · merged: False

## Original PR description

### Problem Summary
Fixes #65131.

When a running request encounters a synchronous KV load failure and is rescheduled under `kv_load_failure_policy='recompute'`, `_handle_invalid_blocks()` rolls back `request.num_computed_tokens` to trigger recomputation of the missing blocks.

Under `AsyncScheduler` with a pipelined batch queue (`EngineCore.step_with_batch_queue`, default queue size 2), subsequent decode batches for this request may already be in flight executing on the worker using the invalid/corrupted KV cache. Previously, `_handle_invalid_blocks()` neither marked these in-flight batches as stale nor reset `num_output_placeholders`. Consequently:
1. In-flight batches returned tokens generated over invalid KV memory and delivered them to the client.
2. Stale output placeholders corrupted `is_prefill_chunk` detection and subsequently underflowed in `_update_request_with_output()`, crashing the engine with:
   ```text
   AssertionError: assert request.num_output_placeholders >= 0
   ```

### Solution
In `vllm/v1/core/sched/scheduler.py`, when `self.recompute_kv_load_failures` is active and sync requests are rescheduled:
1. Set `request.drop_stale_output = True` and `request.num_stale_output_tokens = request.num_in_flight_tokens`, ensuring that all in-flight batches executing over invalid KV cache are safely discarded upon return in `update_from_output()`.
2. Reset `request.num_output_placeholders = 0` and clear `request.spec_token_ids` so prefill recomputation starts with clean accounting.

This mirrors the canonical in-flight draining protocol already established in `_preempt_request()`.

### Testing
- Added `test_sync_kv_load_failure_recovery_inflight_stale` in `tests/v1/core/test_async_scheduler.py`.
- Verified that without this fix, the test reproduces the stale output and underflow failure.
- Verified that with this fix, all 20 tests in `tests/v1/core/test_async_scheduler.py` and all 14 tests in `tests/v1/kv_connector/unit/test_kv_load_failure_recovery.py` pass cleanly on CPU.

@Aravind0403 Thanks for addressing the stale-output draining in this PR. I'd like to coordinate a separate follow-up rather than duplicate your work.

Codex-assisted validation of head `314d520fc27ca319f8db0b650b80f446861a1af6` on H20 / Qwen3-4B BF16 found two remaining recovery-state issues with MRV2, async scheduling, eager execution, and injected synchronous KV load failure:

1. The reusable prefix is calculated by subtracting only the returning step from optimistic progress. With another batch in flight, this can retain uncommitted tokens. A deterministic scheduler regression gives `863` retained tokens versus the valid `800`.
2. A cached-request diff updates MRV2's CPU progress mirror without restoring its device-side request state after the rollback.

In the real-GPU reproducer, the unmodified PR head completes, but 2 of 4 requests differ from their no-fault references, even with `VLLM_BATCH_INVARIANT=1`. The candidate follow-up excludes all non-stale in-flight work from the rollback checkpoint and resends full request data once to refresh MRV2 state, while retaining the existing KV block table and RUNNING status. It does not introduce a preemption/full-cache-eviction fallback.

Local validation of that candidate:
- 36 scheduler/KV-recovery CPU tests pass, including the existing assertions and new queued-batch/cancellation checks.
- The new `LLM`/`vllm_runner` GPU regression fails before the change and passes afterward: all 40 generated tokens match, and every request has zero preemptions.
- 16 KV-recovery tests also pass with MRV1 explicitly selected.
- The real-GPU regression also passes with `VLLM_GPU_SYNC_CHECK=error`.
