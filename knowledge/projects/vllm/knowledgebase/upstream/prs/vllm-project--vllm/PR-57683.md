# [Bugfix][KVConnector] Skip unregistered connectors in MultiConnector stats

[Upstream PR](https://github.com/vllm-project/vllm/pull/57683) · state: open · merged: False

## Original PR description

## Purpose

`MultiConnector` can crash `EngineCore` while reconstructing KV transfer stats when a child connector is registered under a `kv_connector` name that differs from its Python class name.

The worker and logger sides disagree on the stats dict key space:

- `MultiConnector.get_kv_connector_stats()` keys the dict by `c.__class__.__name__`.
- `MultiConnector.build_kv_connector_stats()` resolves each key through `KVConnectorFactory.get_connector_class_by_name()`, but the factory registry is indexed by the `kv_connector` registration name.
- The lookup has no guard, so a key that is a class name but not a registration name raises `ValueError`, which propagates out of `AsyncLLM.output_handler` and tears down the engine.

This reaches any connector whose registered `kv_connector` name differs from its Python class name, e.g. a plugin overriding an upstream connector. The invariant behind that round-trip is implicit: all 17 in-tree registrations satisfy `name == class name`, and nothing in `KVConnectorFactory.register_connector` documents or enforces it, so it is invisible upstream and only surfaces with plugins.

This is a defense-in-depth guard: the normal path is unchanged and other connectors' stats are still reconstructed.

## Related work

- #61218 (merged Oct 16) fixed the same failure mode on the sibling path: `MultiKVConnectorPromMetrics.observe` now skips unknown connector ids instead of asserting. This PR applies the same skip-with-warning policy to the stats path so the two stay consistent.
- #27366 introduced the class-name to registry round-trip that this PR hardens.
- #55969 rewrites connector stats wholesale; this PR is 15 lines in `multi_connector.py` and should not block it. Happy to rebase or fold in there.

## Downstream context

vllm-ascend#16930 is a downstream stopgap I wrote for this bug: it registers class-name aliases (`AscendOffloadingConnector`, `UCMConnectorV1`, `AscendSimpleCPUOffloadConnector`) so the stats lookup resolves. It only covers connectors that opt in; any new plugin registered under a name differing from its class name re-introduces the crash. With an upstream guard this workaround becomes revertable once a vLLM release containing it is pinned in vllm-ascend. The field report is vllm-project/vllm-ascend#16932, closed by that stopgap rather than by an upstream fix.

## Why not fix the key space

Keying stats by the registration name is the root fix, and `self._ktc_kv_transfer_config` already holds each child's `KVTransferConfig`, so the producer side is small. I kept the guard because:

- The stats dict keys are also the keys of `MultiKVConnectorPromMetrics._prom_metrics` (built with `connector_cls.__name__`) and the labels `kv_connector_logging` prints. Changing one without the other converts the crash into silently missing metrics, and after #61218 unknown ids skip instead of asserting, so nothing would surface.
- That makes it a three-site change to the stats dict key space rather than a bugfix.
- #55969 is rewriting exactly those sites; a parallel key-space change would collide.

If you would rather have that, I can switch: stats + prom metrics + logging keys together, plus a test asserting every `to_dict()` key resolves through the factory and is present in `_prom_metrics`.
