# [ROCm][Build][2/5] Speed up ROCm build: split the topk softplus-sqrt instantiations per dtype

[Upstream PR](https://github.com/vllm-project/vllm/pull/62717) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Disclosure

AI assistance was used. The changes were reviewed and tested manually.

## Overview

**Splits the topk softplus-sqrt translation unit on two items - the `topk_indices` dtype (#40860) and, on a single-family build, the wavefront arm.**

Instantiating the fused topk softplus-sqrt kernels emitted ~1900 device kernels in one translation unit, which made it the critical path of a whole ROCm build (99.7 s of a 102 s build). Split the per-dtype instantiations into their own translation units with explicit instantiation, and drop the one instantiation axis that can never be selected.

`main` already contains #62475, so this PR is one split commit on top of it, plus a rename commit so that the moved kernels read as a rename in the diff. Part of a 5-PR series with #62716 (paged attention), #62718 (skinny GEMMs), #63364 (int4 skinny GEMM) and #63365 (fused MUSE-Spark op); the gain is joint, see *Validation*.

The single-arch rows are `pip install -e .` on MI350 (gfx950); the 9-arch row is the `setup.py bdist_wheel` described under *Validation*. All cold builds:

| build | `main` | this PR | All 5 PRs (#62921) |
|---|---|---|---|
| `MAX_JOBS=16`, gfx950 only | 107 s | 107 s | 87 s |
| `MAX_JOBS=64`, gfx950 only | 85 s | 85 s | 50 s |
| `MAX_JOBS=64`, 9 archs | 1263 s | 1243 s | 472 s |

## Claims

- Takes the fused softplus-sqrt topk unit off the build's critical path: one 8-10 s unit per (gating dtype, `topk_indices` dtype) pair instead of a single ~100 s unit.
- Halves the device kernels per unit on a single-family build (120 -> 60; 90 for the `uint32_t` index variants) by instantiating only the reachable wavefront arm.
- Cuts `_moe_C_stable_libtorch` by 36 % (32.5 -> 20.7 MB) and its compile work from 126 s to 91 s.
- Nothing about what runs changes: `main`'s dispatch is kept verbatim and the kernels are byte-identical, only the instantiation units are split.

\* the `.so` number applies to builds whose `PYTORCH_ROCM_ARCH` covers one GPU family (e.g. the CI default `gfx90a;gfx942;gfx950`, or a gfx950-only build). A mixed list such as the release base image's `gfx90a;…;gfx1151` keeps both wavefront arms, so it only gets the per-dtype split.

- 9 checked-in 13-15-line units, one per (gating dtype, `topk_indices` dtype) pair, hold the whole change; `main`'s hand-written dispatch stays byte-identical, so there is no generated code, no stamp and no configure-time step. Their `extern` declarations and their instantiations share one `VLLM_TOPK_SOFTPLUS_SQRT_DECLARE(EXT, ...)` macro, so the two cannot drift apart.
- The unit is off the build's critical path, so the series' reduction is no longer gated on it.

### Why five PRs

The two builds are bound by different things, so no single change moves both.

**Why the three single-arch PRs are all needed.** At 1 arch (`gfx950`, `MAX_JOBS=64`, `main` = 85 s) three groups take turns setting the wall, in this order:

1. topk softplus-sqrt (#62717) - 74.5 s, a single unit
2. paged attention (#62716) - 71.6 s, the slowest of 12 units
3. other skinny GEMMs (#62718) - 40.9 s, a single unit

#62717 takes (1) to 7.4 s, #62716 takes (2) to 31.1 s and #62718 stops (3) from becoming the next tail; with all three the tail moves to `selective_scan_fwd` (37.7 s) and the build goes from 85 s to 49 s. Drop any one of them and a ~70 s unit is back at the top, so the single-arch win needs all three.

**Why that is not enough at 9 archs.** A 9-arch build multiplies every unit's time by ~9, and the tail becomes two files that none of the first three touch: `csrc/rocm/skinny_gemms_int4.cu` at 1232 s and `csrc/fused_muse_spark_qknorm_rope_kv_insert_kernel.cu` at 478 s. All three merged take the 9-arch build from 1263 s to only 1253 s. #63364 splits the first (its tail drops to 448 s) and #63365 the second (to 171 s), which is what reaches 472 s.

The `skinny_gemms_int4.cu` tail is invisible in a `gfx950` build because that file **only emits its kernels for RDNA (that is part of the 9-arch build)**:

https://github.com/vllm-project/vllm/blob/f4edf9f0f078ae67392510aafd1871288948a3c3/csrc/rocm/skinny_gemms_int4.cu#L17-L19
https://github.com/vllm-project/vllm/blob/f4edf9f0f078ae67392510aafd1871288948a3c3/csrc/rocm/skinny_gemms_int4.cu#L568-L579

`csrc/fused_muse_spark_qknorm_rope_kv_insert_kernel.cu` fails differently: it has no arch guard, so a `gfx950` build compiles it for real - it is just 25 s there against 478 s across nine archs, which is why a single-arch profile ranks it as irrelevant (#63365).

## Details

`topkGatingSoftplusSqrtKernelLauncher` emits one kernel per (expert count, wavefront size, compile-time `use_hash`, gating dtype, `topk_indices` dtype, hash index dtype) - 15 expert counts x 2 wavefront sizes x 2 `use_hash` values, for the 21 launcher instantiations the dispatch asks for, i.e. ~1.3k kernels in one file, so the AMDGPU backend spent ~100 s in that unit and the whole build waited for it.

The split only needs separate translation units, so it uses plain explicit instantiation:

- `topk_softplus_sqrt_kernels.cuh` carries the kernels, the launchers and the two `VLLM_TOPK_SOFTPLUS_SQRT_{EXTERN,INSTANTIATE}` macros (819 of its 920 lines are byte-identical to `main`'s `.cu`);
- `topk_softplus_sqrt_<gating>_<indices>.cu` (9 files, 13-15 lines each) instantiate the launcher for the hash index types the dispatch uses - two per pair, three for the `uint32_t` variants, where the default `HashIndType = IndType` is a third type;
- `topk_softplus_sqrt.cu` keeps `main`'s `dispatch_topk_softplus_sqrt_launch` and `topk_softplus_sqrt` verbatim, and the `extern template` declarations keep it from instantiating the kernels a second time (verified: 0 kernels in that object). It is named after the op rather than after `main`'s file so that the move reads as a rename: keeping the old `topk_softplus_sqrt_kernels.cu` path next to the new `.cuh` made git report the ~820 moved lines as a deletion plus an addition (1092/828 changed lines instead of 469/205).

One axis that can never be selected is no longer instantiated. The wavefront size is a runtime property on ROCm (`Utils::get_warp_size()`), so both the wave64 and the wave32 kernel used to be emitted; it is fixed per GPU family - CDNA (gfx9xx) is wave64, RDNA (gfx10xx+) is wave32 - so CMake derives `VLLM_TOPK_SOFTPLUS_SQRT_WAVE{64,32}_ONLY` from `VLLM_GPU_ARCHES` and only the reachable arm is instantiated; the definition is set on `_moe_C_stable_libtorch` as a whole, so the dispatch unit parses the launcher with the same body as the units that instantiate it; mixed arch lists keep the runtime `if/else`. The single-arm builds `STD_TORCH_CHECK` the runtime wavefront size once, at the top of the launcher, so a binary built for one family that ends up on a device of the other fails loudly instead of running a kernel compiled for the wrong width. Everything else is instantiated exactly as in `main`, including the compile-time `use_hash` fork (`DISPATCH_HASH`): making that a runtime value would merge the hash path into the non-hash kernel, which changes the generated code for a path that does run.

**Change in behaviour.** None: the dropped kernels were unreachable for the targeted archs, every kernel `main` instantiates is still instantiated with the same template arguments, and `main`'s dispatch is unchanged.

**How the file got this big.** One PR created the whole instantiation space: #40860 landed the file with 1 `__global__`, 8 templates and a 15-arm switch (gating dtype x indices dtype x hash / no-hash), as a single TU. The four PRs after it (#40871, #41261, #44565, #60721) added a code path, a warning fix, the stable-ABI migration and a header cleanup - none of them changed the arm count. So the op stayed at ~1.3k kernels in one TU, which is what this PR splits into 9 units.
