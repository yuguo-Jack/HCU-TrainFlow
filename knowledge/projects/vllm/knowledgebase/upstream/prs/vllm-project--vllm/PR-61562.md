# [Bugfix] Stop engines before API servers so --shutdown-timeout drains with --api-server-count > 1

[Upstream PR](https://github.com/vllm-project/vllm/pull/61562) · state: open · merged: False

## Original PR description

## Overview

Fixes #61561. With `--api-server-count > 1` (the default whenever `--data-parallel-size > 1`), `--shutdown-timeout N` never drained in-flight requests: the launcher stopped the API servers before the engines, so every in-flight request failed with `EngineDeadError` (HTTP 500) and the engines then drained for up to N seconds with no client left to deliver to. This PR makes the shutdown proceed in three steps: stop accepting (the API servers close their listeners and the launcher closes its copy of the shared socket, so new arrivals are refused at the socket), drain the engines while the still-running API servers deliver the outputs, then stop the API servers and the coordinator. `test_multi_api_server_shutdown` now asserts the drain.

## Claims

- With `--api-server-count 2 --shutdown-timeout 30`, requests that are running when SIGTERM arrives now complete (`finish_reason=length/stop`) instead of returning HTTP 500, matching the single-API-server behaviour.
- New connections arriving during the drain are refused at the socket (`ECONNREFUSED`) rather than admitted and rejected: on a requested shutdown the launcher sends SIGUSR1 to the workers, each worker closes its listener but keeps serving the requests it already accepted (`NoSignalServer.stop_accepting`), and the launcher closes its own copy of the shared socket. The single-API-server path does the same first thing in its own SIGTERM handling. The engines' `_reject_add_in_shutdown` remains as the backstop for requests on already-open keep-alive connections.
- The launcher, API servers, engines and coordinator still exit within the budget.
- `shutdown_timeout=0` (abort mode) is unchanged in effect: requests are aborted at once either way.
- `tests/entrypoints/launchers/test_shutdown.py::test_multi_api_server_shutdown` now fails on `main` and passes with this change.

## Validation

**Before/after measurement** (1x A100-40GB, `Qwen/Qwen3-0.6B`, `--max-num-seqs 16 --shutdown-timeout 30`, 8 concurrent completions with `max_tokens=300, ignore_eos=True`, SIGTERM sent to the launcher as soon as `/metrics` reports running requests; `main` @ 201e537d98, same numbers on the v0.31.0 wheel):

|---|---|---|---|
| completed after SIGTERM | 0 of 8 | 8 of 8 returned 200: the 5 running requests completed (`length`, 300 tokens), the 3 still queued got `finish_reason=abort` | 8 of 8 (`length`, 300 tokens each) |
| HTTP 500 | 5 at +5 ms, the other 3 connections dropped at +30 s | 0 | 0 |
| launcher exited after | 32.2 s (budget exhausted, API server and engine force-killed) | 7.6 s (engine drained in 1 s, exited 5 s later, then API servers) | 5.8 s |

**Repository test** (same A100, `hmellor/tiny-random-LlamaForCausalLM`): `pytest tests/entrypoints/launchers/test_shutdown.py::test_multi_api_server_shutdown` with the new assertion fails on `main` (`1 failed in 161.86s`) and passes with this PR; together with the single-server `test_wait_timeout_completes_requests`: `2 passed in 126.78s`.

**Stop-accepting tests** (CPU, `tests/entrypoints/launchers/test_stop_accepting.py`): with uvicorn's accept loop and with the shared-socket accept loop, SIGUSR1 makes new connections fail with `ECONNREFUSED` while an in-flight request completes and the same client's next request (on its keep-alive connection) is refused as well; `stop_accepting` is idempotent and shutdown stays clean; the manager signals only live workers. `4 passed`.

**Arrival probe** (same A100, `--api-server-count 2 --shutdown-timeout 60`): one streaming completion (`max_tokens=600, ignore_eos`) in flight and 32 connection attempts spread over the shutdown: the stream completed all 600 tokens (`finish_reason=length`, 8.8 s after SIGTERM), every new connection was refused at the socket (`ECONNREFUSED`, none admitted), and the launcher exited with no leftover processes. The log shows the order: both API servers log `no longer accepting new connections`, the engine logs `draining in-flight requests count=1` and exits 8 s later, and only then are the API servers stopped. Same outcome with `--api-server-count 1`.

## Details

Each API server worker handles SIGTERM in `launcher.py::handle_shutdown` by calling `engine_client.shutdown(timeout=N)`. In multi-server mode the engines are owned by the launcher, so the worker's `MPClient.resources.engine_manager` is `None`: `MPClient.shutdown` has nothing to wait for and immediately runs `self.resources()`, which marks the engine dead, closes the ZMQ sockets and cancels the output-queue task. That task enqueues `EngineDeadError`, `AsyncLLM.output_handler` propagates it to every waiting `generate()`, and all in-flight requests get HTTP 500. The launcher only then sends SIGTERM to the engines, which log `draining in-flight requests` and compute outputs for sockets without a peer.

In single-server mode the order is reversed by construction (`MPClient.shutdown` waits for `engine_manager.shutdown(N)` while the event loop keeps relaying outputs, then closes the sockets), which is why `test_wait_timeout_completes_requests` holds there. The fix gives the multi-server launcher a three-step order: (1) stop accepting: `APIServerProcessManager.stop_accepting()` sends SIGUSR1 to the live workers, whose `serve_http` handler runs `NoSignalServer.stop_accepting()` (cancel the accept loops and close the listening sockets in shared-socket mode, or close uvicorn's asyncio servers; accepted connections keep being served; the worker publishes "not accepting" to its peers), and the launcher closes its own copy of the shared socket; (2) engines with the full budget (they finish in-flight requests while the live API servers deliver outputs); (3) the API servers, which have nothing left in flight, and the coordinator with the remaining budget. The worker entrypoint ignores SIGUSR1 until `serve_http` installs the handler, so a shutdown during worker startup cannot kill a worker with the signal's default action. The `local_engine_manager is None` case (no local engines) and the failure path (`timeout=None`) are unchanged apart from the order.

Not changed here, noted for completeness: with the default `--shutdown-timeout 0` the EngineCore is force-killed right after SIGTERM on non-ROCm platforms (#52281 added a cleanup grace for ROCm only), so the abort outputs rarely reach the clients in either mode; that is a separate issue.

Yes, and it is a better shape, thanks. Done in e7cdf6c200; the shutdown now runs in three steps: stop accepting, drain the engines, exit the API servers.

- **Stop accepting.** `NoSignalServer.stop_accepting()` cancels the accept loops and closes the listening sockets (shared-socket mode) or closes uvicorn's asyncio servers (single-socket mode); connections already accepted keep being served, and the worker publishes "not accepting" to its peers. It also shuts down the connections that are already open the way uvicorn's own graceful shutdown does: idle keep-alive connections close at once, busy ones after their current response, so a client's next request needs a new connection and is refused rather than reaching the draining engine. `serve_http` installs it as the SIGUSR1 handler and also calls it first thing in its own SIGTERM path, so the single-API-server case refuses new connections during its drain too. `APIServerProcessManager.stop_accepting()` sends SIGUSR1 to the live workers (the worker entrypoint ignores SIGUSR1 until `serve_http` installs the handler, so a shutdown during worker startup cannot kill a worker with the default action). The launcher closes its own copy of the shared socket at the same point, otherwise the kernel would keep queueing connections that no process accepts.
- **Drain, then exit.** Engines next with the full budget; then the API servers, which have nothing left in flight, and the coordinator with the remaining budget. `_reject_add_in_shutdown` is now only the backstop for a request that was already on the wire when the stop happened.

Tests: `tests/entrypoints/launchers/test_stop_accepting.py` (CPU, no model) covers both accept paths: after SIGUSR1 a new connection fails with `ECONNREFUSED` while an in-flight request completes, and the same client's next request is refused too; `stop_accepting` is idempotent and shutdown stays clean; the manager signals only live workers.

On an A100 with `--api-server-count 2 --shutdown-timeout 60`: one streaming completion (`max_tokens=600, ignore_eos`) in flight and 32 connection attempts spread over the shutdown: the stream completed all 600 tokens (`finish_reason=length`, 8.8 s after SIGTERM), every new connection was refused at the socket (`ECONNREFUSED`, none admitted), and the launcher exited with no leftover processes. The log shows the order: both API servers log `no longer accepting new connections`, the engine logs `draining in-flight requests count=1` and exits 8 s later, and only then are the API servers stopped. Same outcome with `--api-server-count 1`. The upstream `test_multi_api_server_shutdown` passes on the branch in two consecutive runs on the A100 (it is also what caught an earlier version of this change that still let requests through on open keep-alive connections), together with `test_wait_timeout_completes_requests` and `test_request_rejection_during_shutdown`. EngineDeadError` traceback when its engine client is closed during shutdown; that is the known #48745 (fix in #49000), not introduced here. PR description updated accordingly.
