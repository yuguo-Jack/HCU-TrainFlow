# [Test][Model Loader] Weight reload equals a cold start, in both reload modes

[Upstream PR](https://github.com/vllm-project/vllm/pull/65347) · state: open · merged: False

## Original PR description



## Overview

An end-to-end test that a streamed weight reload leaves the engine exactly as a cold start would, in both reload modes (`VLLM_RELOAD_MODE=layerwise` and `direct`). PR 9 of the direct weight reload stack (#54477). It is the test half of #61287, rewritten for current main; the fixes from #61287 are in PR 10.

## Claims

- **New test `tests/model_executor/model_loader/test_reload_refit.py`.** An engine starts on checkpoint A with CUDA graphs, then reloads B, A and B again the way NCCL/IPC weight transfer does: device tensors in batches through the model's own `load_weights`, between `start_reload` and `finish_reload`. It checks that:
  - after reloading A, every tensor equals the cold start on A, and after the last reload, a fresh engine on B;
  - no tensor moved, appeared or disappeared across the reloads (captured graphs read the old addresses);
  - no reload leaves PyTorch-allocated device memory held;
  - the worker actually ran in the requested reload mode.
- **"Every tensor"** is the registered parameters and buffers plus the device tensors reachable from module attributes (quant methods, kernels, quant configs). That is where derived tensors that a reload forgets to refresh live. Checksums are compared, not logits, so kernel selection between engines does not matter.
- **Cases** (TP=1, each in both modes): BF16 dense with tied embeddings (Qwen3-0.6B), FP8 block (Qwen3-0.6B-FP8_BLOCK), MLA + MoE (DeepSeek-V3 debug), Mamba hybrid (Falcon-H1-0.5B), and online FP8 MoE (layerwise only; direct mode refuses online quantization).
- **CI:** a new B200 step, `Weight Reload Refit`. The NVIDIA Model Executor step that would otherwise collect this file is commented out on main.

## Validation

GB200, nightly wheel of 61249811c1 with this branch's test file on top (job 44128):

| Case | layerwise | direct |
|---|---|---|
| bf16-dense-tied | pass | pass |
| fp8-block-dense | pass | pass |
| mla-moe | pass | pass |
| mamba-hybrid | pass | pass |
| online-fp8-moe | xfail (strict) | — |

`test_direct_reload.py`: 35 passed. The file takes about 10 minutes with checkpoints cached.

**The xfail is a real bug on main.** Layerwise reload runs post-load processing on temporary parameters and copies the results back, and `_Fp8OnlineMoEBase._setup_kernel` rebuilds `moe_quant_config` from those temporaries. After a reload the quant config holds two scale tensors (`moe_quant_config._w1.scale`, `_w2.scale`) that are not the layer's own, so the test reports them as appeared. It is tracked in the #54477 limitations.

## Details

**Changes from #61287's harness:**
- No worker extension or separate harness file: four module-level functions are passed to `collective_rpc`, as `test_reload.py` already does.
- Removed what only the closed modulewise reload plan (#59502) used: arrival orders, retention tracking, failure injection, CPU and perturbed streaming, the MoE backend matrix and the checkpoint generators.
- Added both reload modes, the B→A→B sequence (each reload changes values, so a refresh that only happens on the first reload is caught), per-reload memory and mode checks.

**Limits:**
- The DeepSeek-V3 debug checkpoints share their layer-0 norms, `e_score_correction_bias` and `model.norm.weight`, so a reload that skipped those would not be caught.
- The walk does not see tensors held only in closures or `__slots__`.
- All cases are TP=1.
- CI runs on B200; it has only been run on GB200.
