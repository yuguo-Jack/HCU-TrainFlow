# [Core][Scheduler] Add an opt-in time-bounded prefill hold

[Upstream PR](https://github.com/vllm-project/vllm/pull/64927) · state: open · merged: False

## Original PR description

## Purpose

While decodes are running, the v1 scheduler admits new prefills as they arrive, so a burst of concurrent requests is prefilled one or two at a time over many steps, and every step with a prefill slows all running decodes. This adds an opt-in, time-bounded hold: while decodes run, waiting requests stay in WAITING until the oldest has waited `VLLM_PREFILL_HOLD_MS`, so arrivals batch into one prefill wave. `VLLM_PREFILL_HOLD_MIN_REQS` disables the hold when few requests are in the engine (a low-concurrency workload has nothing to batch). Default 0 = off, no behaviour change.

Related work, opened as a draft to discuss the design: #56455 (bounded prefill admission) targets the same problem with an admission module; `--prefill-schedule-interval` (#54627) is step-count based and measured worse here (−3.8%), because the cadence opens after any long decode stretch. Open question: env vars vs `SchedulerConfig` fields.

## Test Plan

- 5 unit tests in `tests/v1/core/test_scheduler.py`: held while decodes run and released after the hold time; arrivals batched into one step; no hold without running decodes; the `MIN_REQS` gate; env defaults.

## Test Result

MiniMax-M3 VL (image) on MI355X, TP2, 8-row image sweep (ISL 256–8192, OSL 64, concurrency 4–256), output throughput: hold 200 ms **+8.0%** geomean (rows +4.9..+21.9%, the c4 row −10.7% without the gate, +8.9% with `MIN_REQS=8`). Trade-off: median TTFT rises, since requests wait up to the hold time (TTFT is reported next to throughput in any comparison).


Update (2026-11-03): second commit adds `VLLM_PREFILL_HOLD_LOW_LOAD_MS`, a separate (short) hold time used below `VLLM_PREFILL_HOLD_MIN_REQS` requests (default 0 = unchanged). At low concurrency (c4) a 50 ms hold keeps arrivals in one prefill wave: the c4 row stayed in its fast mode in 9/9 runs (+3.3% on that row); no measurable effect on the full 8-row geomean (MI355X TP4, 5 passes).

## Verified on this PR's head (2026-11-03)

Dedicated MI355X node, TP2, MiniMax-M3 VL (AttnFP8), vLLM nightly 40941f2c + this branch, full 8-row image sweep, A B B A (A = hold off, B = `VLLM_PREFILL_HOLD_MS=200 VLLM_PREFILL_HOLD_MIN_REQS=8`; the arms differ only in these two env vars):

| row (ISL/OSL, conc, image) | throughput | median TTFT | P99 TTFT | median TPOT |
|---|---|---|---|---|
| 1024/64, c16, 512x512 | **+8.2%** | 311 → 1041 ms | +25% | 26.9 → 12.8 ms |
| 1024/64, c16, 768x1024 | **+5.1%** | 575 → 1253 ms | +1% | 32.0 → 17.7 ms |
| 256/64, c16, 768x1024 | +2.6% | 523 → 1093 ms | +9% | 25.4 → 13.9 ms |
| 1024/64, c64, 768x1024 | **+1.3%** | 1.6 → 5.2 s | 0% | 99.4 → 37.8 ms |
| 2048x1600 c16, 8192/64 c16, c4, c256 rows | −0.5% … 0.0% | unchanged (c4: 234 → 184 ms) | ±1% | unchanged |
| **8-row geomean** | **+2.0%** (A/A spread 0.1%, B/B 1.3%) | | | |

The trade is explicit: at c16–c64, about half the per-token decode time and +1–8% throughput, for 2–3.3x median TTFT; P99 TTFT is unchanged. Opened for design direction next to #56455 (admission-wave approach).
