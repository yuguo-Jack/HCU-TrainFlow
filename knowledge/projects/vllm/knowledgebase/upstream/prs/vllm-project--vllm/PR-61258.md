# [Feature][Core] Enable best-effort NUMA binding by default

## Overview

Enable best-effort NUMA binding by default for eligible GPU multiprocessing launches, using soft memory preference. Explicit binding keeps its existing strict memory policy.

This continues [ivanium/vllm#53](https://github.com/ivanium/vllm/pull/53) by Yifan Qiao (@ivanium). His original commit `788505bea2c6cae925fce4afe47195188656896d` was cherry-picked with authorship, co-author trailers, and sign-offs preserved. The branch is rebased onto main (`775fefa804ca`), including the merged shared GPU-indexing fix [#61237](https://github.com/vllm-project/vllm/pull/61237).

## Claims

- Validate fresh host-local GPU-to-NUMA topology in the launcher, then pass the decision and mapping to children. Preserve constrained CPU affinity and existing non-default memory policies in automatic mode.
- Automatically prefer GPU-local memory with `--preferred`; EngineCore uses `--preferred-many` for multi-node shards. Explicit `--numa-bind` or binding lists retain `--membind`. CPU/PCT selection and EngineCore's affinity superset are unchanged.
- If the selected memory policy is rejected or unsupported, retry CPU-only, then unbound. Automatic mode never falls back to strict memory binding.
- Explicit NUMA CLI flags, including binding-list shortcuts, select `spawn` even when `fork` was requested. Omitted flags and `--no-numa-bind` leave start-method selection unchanged.

## Details

| Control | Memory policy |
|---|---|
| Omitted (`numa_bind=None`) | Best-effort soft preference; failed eligibility checks or an existing non-default memory policy mean no vLLM-added binding. |
| `--numa-bind` | Strict `--membind`; missing numactl or undetectable topology remains an error. Existing policy-probe fallback applies. |
| `--no-numa-bind` | No vLLM-added binding. |
| `--numa-bind-nodes` / `--numa-bind-cpus` | Imply explicit enablement and retain strict memory policy. Combining with `--no-numa-bind` is rejected. |

Binding lists previously enabled the config without triggering the start-method check, leaving binding ineffective when `fork` was requested. The check now recognizes all three explicit CLI flags, normalizing only the option name so `=value` and underscore spellings work too. Python API start-method requirements remain unchanged.

An internal config flag preserves automatic-policy identity after `numa_bind` resolves to `True`, so spawned workers do not mistake it for explicit strict binding. This launch-local state is excluded from the DP configuration hash; no public flag or steady-state inference operation is added.

Automatic eligibility requires CUDA/ROCm, multiple NUMA nodes, numactl and usable memory-policy support, known unrestricted CPU affinity, a default memory policy, and `spawn` with an `mp`/`uni` executor and `mp` DP. Ray, external/custom launchers, device-ID remapping, fork, and PCP remain excluded. Start-method defaults are unchanged. Each launcher uses host-local NUMA IDs, not cluster-wide IDs.

Soft preference permits allocation on other allowed NUMA nodes when local memory is unavailable, avoiding a new hard node-capacity restriction by default. Explicit strict binding still requires sufficient memory on the selected nodes. The loader's existing RAM estimates and container memory limits are unchanged; policy probes check acceptance, not allocation capacity.

Duplicate-work searches refreshed on 2026-10-15 found no competing upstream GPU automatic-default PR. Other open NUMA work addresses affinity, memory sizing, CPU execution, or ROCm packaging; this PR continues the credited fork trial.
