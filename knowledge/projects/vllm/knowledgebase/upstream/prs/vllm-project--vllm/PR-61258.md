# [Feature][Core] Enable best-effort NUMA binding by default

[Upstream PR](https://github.com/vllm-project/vllm/pull/61258) · state: closed · merged: True

## Original PR description

## Overview

Enable best-effort NUMA binding by default for eligible GPU multiprocessing launches, including PCP. Automatic mode prefers GPU-local memory; explicit binding retains its strict memory policy.

This continues [ivanium/vllm#53](https://github.com/ivanium/vllm/pull/53) by Yifan Qiao (@ivanium). His original commit `788505bea2c6cae925fce4afe47195188656896d` was cherry-picked with authorship, co-author trailers, and sign-offs preserved. The branch includes the merged shared GPU-indexing fix [#61237](https://github.com/vllm-project/vllm/pull/61237) and the CI bot's merge of main (`a1e1823967`, main parent `8977b13a1c`).

## Claims

- Validate fresh host-local GPU-to-NUMA topology in the launcher, then pass the decision and mapping to children. Preserve constrained CPU affinity and existing non-default memory policies in automatic mode.
- Automatically prefer GPU-local memory with `--preferred`; EngineCore uses `--preferred-many` for multi-node shards. Explicit `--numa-bind` or binding lists retain `--membind`. Failed automatic policy probes fall back to CPU-only, then unbound.
- Enable automatic binding for supported local PCP launches. GPU offsets include TP × PCP × PP for each DP shard, and EngineCore's CPU affinity covers its workers.
- Explicit NUMA CLI flags, including binding-list shortcuts, select `spawn` even when `fork` was requested. Omitted flags and `--no-numa-bind` leave start-method selection unchanged.

## Details

| Control | Memory policy |
|---|---|
| Omitted (`numa_bind=None`) | Best-effort soft preference; failed eligibility checks or an existing non-default memory policy mean no vLLM-added binding. |
| `--numa-bind` | Strict `--membind`; missing numactl or undetectable topology remains an error. Existing policy-probe fallback applies. |
| `--no-numa-bind` | No vLLM-added binding. |
| `--numa-bind-nodes` / `--numa-bind-cpus` | Imply explicit enablement and strict memory policy. Combining with `--no-numa-bind` is rejected. |

An internal flag preserves automatic-policy identity after `numa_bind` resolves to `True`, so spawned workers do not mistake it for explicit strict binding. This launch-local state is excluded from the DP configuration hash; no public flag or steady-state inference operation is added.

Automatic eligibility requires CUDA/ROCm, multiple NUMA nodes, numactl and usable memory-policy support, known unrestricted CPU affinity, a default memory policy, and `spawn` with an `mp`/`uni` executor and `mp` DP, including supported PCP launches. Ray, external/custom launchers, device-ID remapping and fork remain excluded. Each launcher interprets NUMA IDs on its own host. The temporary PCP exclusion is removed now that the merged indexing prerequisite and actual bound PCP+DP launches have been verified.

Soft preference permits allocations on other allowed NUMA nodes when local memory is unavailable. Explicit strict binding still needs sufficient memory on the selected nodes. Existing loader RAM estimates and container limits are unchanged; policy probes check acceptance, not allocation capacity.

Unit coverage includes worker/EngineCore policies, fallback, config-copy/hash stability, PCT CPU selection, inherited policies, topology eligibility, CLI start-method selection and PCP/DP indexing. Existing NVIDIA/AMD `utils_` CI retains unit coverage. AMD/ROCm serving, native macOS runtime, hard `cpuset.mems` restrictions, mixed-socket PCP, multi-host PCP and actual preferred-memory spillover remain untested. No throughput or production offload-capacity claim is made. Remote CI build [#97587](https://buildkite.com/vllm/ci/builds/97587) exercised the PCP follow-up; its worker-import failure is addressed by `aeef060224`, with a retry requested.

Duplicate-work searches on 2026-10-15 found no competing upstream GPU automatic-default PR. This PR continues the credited fork trial; other NUMA work addressed affinity, memory sizing, CPU execution or ROCm packaging.
