# [ROCm][DSv4.1] Avoid runtime JIT for offset combine_topk_swa_indices inputs

[Upstream PR](https://github.com/vllm-project/vllm/pull/64001) · state: open · merged: False

## Original PR description

## Purpose

The chunked sparse prefill passes `query_start_loc`, `seq_lens` and `gather_lens` to `CombineTopkSwaIndicesKernel` as views at `num_decodes` and `chunk_start` offsets, so each of these int32 pointers lands on any 4-byte offset. Triton specializes on that alignment, and the three warmed alignment variants miss reachable combinations: every DeepSeek-V4.1 server compiles the kernel 6 more times during serving (2 alignments x 3 compress ratios), and the JIT monitor reports `CombineTopkSwaIndicesKernel` once multi-request prefills arrive.

Each program reads one value from these tensors, so their alignment does not enable vectorized loads. Stop specializing on it (`do_not_specialize`, as #57667 does for `end_ptr`) and warm only the `topk_indices` alignments. This drops the warmup from 3 to 2 variants per compress ratio.

## Test Plan

pre-commit run --files vllm/models/deepseek_v41/common/ops/cache_utils.py \

The test warms the kernel, then calls `combine_topk_swa_indices` for compress ratios 0/1/2 with the offset views the chunked prefill passes (`num_decodes = chunk_start = 1`: `query_start_loc` and ROCm's `seq_lens` at offset 2, `gather_lens` at offset 1) under a Triton post-compile hook, and asserts nothing compiles.

MI355X (gfx950), DeepSeek-V4.1-Flash, TP4. Unit test on `main@3966924d56`; kernel time, E2E and GSM8K on `main@5d35ce3934` (each the host build's commit at the time).
