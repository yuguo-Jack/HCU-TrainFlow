# [Bugfix][Rust Frontend] Count tokens, not chunks, in vllm-bench output throughput

[Upstream PR](https://github.com/vllm-project/vllm/pull/62477) · state: open · merged: False

## Original PR description

## Overview

Rust counterpart of #50677. The Rust `vllm-bench` rebuilds each request's token timeline from ITL entries and adds one token per entry, but an entry is a streamed chunk, and chunks carry several tokens with speculative decoding or `--stream-interval`. So peak output throughput and the steady-state output throughput both count chunks.

Related: #37666 (closed by the stale bot, bug still on main). #50677 fixes the same thing in the Python `vllm bench serve` and only touches `serve.py`, so this is not a duplicate of it.

## Claims

- Peak output throughput in `calculator.rs` counts tokens, so it can no longer come out below the average.
- Steady-state output throughput in `steady_state.rs` (on by default in closed-loop runs) counts tokens too. It was the worse of the two: about 8x low at `--stream-interval 8`.

## Validation

Real server: `vllm/vllm-openai-cpu:v0.31.0-arm64`, `Qwen/Qwen2.5-0.5B-Instruct`, `--stream-interval 8`. Client is `vllm-bench` built from this branch and from main:

```
vllm-bench --backend vllm --base-url http://127.0.0.1:8000 --model Qwen/Qwen2.5-0.5B-Instruct \
  --dataset-name random --random-input-len 64 --random-output-len 128 \
  --num-prompts 32 --max-concurrency 8 --ignore-eos --seed 0
```

| | output tok/s | peak tok/s | steady-state output tok/s |
|---|---|---|---|
| main | 81.00 | 16.00 | 10.62 |
| this PR | 82.41 | 128.00 | 81.34 |

For reference, the Python `vllm bench serve` on main gives the same 16.00 peak against this server, and 104 against the same server with `--stream-interval 1`.

Tests, from `rust/`:
- `cargo test -p vllm-bench`: 191 passed, 0 failed
- the two new tests (`test_peak_output_throughput_counts_tokens_not_chunks`, `compute_counts_tokens_not_chunks`) fail on main with 4.0 and 1.2
- `cargo fmt -p vllm-bench --check` and `cargo clippy -p vllm-bench --all-targets` clean

## Details

Each chunk gets the request's mean tokens per chunk (`output_tokens / (1 + itl.len())`), same as #50677. Streaming only reports the token count at the end, so variable spec-decode acceptance per chunk is averaged out within a request. Totals are exact and the per-second distribution is approximate. When the server sends no usage (`output_tokens == 0`), steady-state keeps the old one-per-chunk count.

#59475 edits the same loop in `calculator.rs` for peak concurrency, so whichever lands second needs a small rebase.

AI assistance (Claude) was used to find the bug and draft the change. I reviewed every line and ran the tests and the server benchmark above myself.
