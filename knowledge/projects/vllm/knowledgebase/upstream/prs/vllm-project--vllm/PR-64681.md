# [Bugfix][LoRA] Give Mamba-1 LoRA layers every row of the batch

[Upstream PR](https://github.com/vllm-project/vllm/pull/64681) · state: open · merged: False

## Original PR description



## Overview

Fixes #61853. With LoRA enabled, `MambaMixer` (Mamba-1, used by `JambaForCausalLM` and `MambaForCausalLM`) gave `x_proj`, `dt_proj` and `out_proj` only part of the batch's rows. The LoRA kernels index rows through the whole batch's mapping, so they went out of bounds. This PR gives those layers a batch-sized input when LoRA is enabled. Root cause and GPU traces: https://github.com/vllm-project/vllm/issues/61853#issuecomment-6516409227

## Claims

- `ai21labs/Jamba-tiny-dev` with `enable_lora=True` starts under the default configuration (MRV2, CUDA graphs) instead of hitting an illegal memory access during CUDA graph capture.
- A LoRA request on Jamba no longer crashes, or silently changes another request's output, when its batch mixes prefill and decode rows.
- No change when LoRA is disabled: that code path is untouched.

## Details

**Root cause.** `forward_impl` calls `_ssm_transform` once on the decode rows and once on the prefill rows, so `x_proj` and `dt_proj` each see part of the batch, and `out_proj` sees `num_actual_tokens` rows, without CUDA graph padding. The punica kernels take `token_indices_sorted_by_lora_ids[:x.size(0)]` from `LoRAKernelMeta.meta_args`. Those are row ids of the whole batch sorted by LoRA id, so with fewer rows than the batch the expand kernel loads and stores output rows past the end. `cuda-gdb` on the capture-time core dump stops at `kernel_utils.py:231 tiled_out = tl.load(c_ptr, mask=c_mask)` in `_lora_expand_kernel`. `in_proj` already gets the full `hidden_states`. Mamba-2's `in_proj` and `out_proj` do too.

**Change.** Only when `is_lora_enabled`:
- `_ssm_transform` zero-pads its input to `hidden_states.shape[0]` rows, with the part at its batch offset (decode rows first, then prefill), runs `x_proj`/`dt_proj`, and slices the rows back.
- `out_proj` gets its input padded to `hidden_states.shape[0]` rows and keeps the first `num_actual_tokens`.

The padded copy also replaces the `.contiguous()` calls the LoRA path had. In a mixed batch, `x_proj` and `dt_proj` now run twice over the batch's rows instead of once per part. Both are small (1024→64 and 32→1024 on Jamba-tiny-dev), and only the LoRA path pays this. Slicing uses the metadata's Python ints, so there are no new host syncs.

**Tests.** No new test, per review. No test in `tests/lora` runs a Mamba-1 model, so CI does not cover this path.

**Not a duplicate.** #62553 also targets #61853. It restricts Jamba's LoRA modules to `qkv_proj, o_proj, gate_up_proj, down_proj, in_proj, embed_tokens, lm_head` and attributes the crash to MoE expert LoRA. LoRA on `experts` alone starts fine, and the crash comes from `x_proj`/`dt_proj`. That list avoids the crash by removing LoRA from those layers, and it does not cover `MambaForCausalLM`. This PR keeps LoRA on all of Jamba's modules. I searched open PRs for #61853, `mamba_mixer` + LoRA, and Jamba LoRA.

**Limitations.** Tested on Ampere (SM86) with Jamba-tiny-dev only. `MambaForCausalLM` shares the code path but I did not run a Mamba checkpoint with LoRA. Not tested with TP > 1 or on ROCm.

AI assistance (Claude Code) was used to trace the fault, write the change and the test, and run the GPU validation. I reviewed every changed line and the results.
