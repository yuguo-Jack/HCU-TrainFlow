# [ROCm] Fuse decode rope + MLA KV-cache write + fp8 query assembly via AITER

[Upstream PR](https://github.com/vllm-project/vllm/pull/55230) · state: open · merged: False

## Original PR description

## Purpose

On the ROCm/AITER MLA path of DeepSeek-R1, every decode step's per-layer q/k preparation runs:

1. `concat_and_cache_mla_rope_fused` (rope on q_pe/k_pe + the fp8 KV-cache write of
   `[kv_c | k_pe]` — already fused by the `fuse_rope_kvcache_cat_mla` compile pass).
2. a Triton concat+quant kernel assembling the fp8 decode query `[ql_nope | rope(q_pe)]`, launched via the `mla_decode_concat_quant_fp8` op.

This PR replaces 1+2 for **decode-only** with a single AITER HIP kernel
(`fused_qk_rope_concat_and_cache_mla`): rope (fp32), the fp8 KV-cache write, and the assembled
quantized decode query in one launch, so:

- the decode hot path drops from 2 kernel launches to 1 per layer (61 layers).
- prefill and mixed batches are unchanged: they fall back to the same `concat_and_cache_mla_rope_fused` kernel the baseline pass uses

**How it works**:

- The MLA wrapper hands RoPE ownership to `MLAAttention` (`attach_rotary_emb`, eligibility
  decided once at load) and passes `positions` through; the graph then contains no rope and
  no `unified_mla_kv_cache_update` node, so the existing `MLARoPEKVCacheCatFusionPass` has
  nothing to match.
- `forward_impl` branches per batch on `attn_metadata`: decode-only steps make the single
  AITER launch; steps with any prefill tokens call the same
  `concat_and_cache_mla_rope_fused` kernel the baseline pass produces (eagerly), then proceeds same as before

## Test Plan
- Benchmark: DeepSeek-R1-0528, TP8, ISL 1024 / OSL 1024, 640 prompts at concurrency 64,
  greedy client (`vllm bench serve --temperature 0.0 --top-p 1.0`), fp8 KV cache,
  `VLLM_ROCM_USE_AITER=1 VLLM_ROCM_USE_AITER_FUSION_SHARED_EXPERTS=1
  VLLM_ROCM_QUICK_REDUCE_QUANTIZATION=INT4`.
- Accuracy: full GSM8K via lm_eval (local-completions, 5-shot, n=1319).

So this is making copies because of the `.contiguous()`. That can grow pretty large. For rope 64 it would be 128k x 64 x 2B x 61 layers ~= 1 GiB.  Can you gate this so only one layer does this? Something like

```
def _fused_rope_cos_sin(self, dtype):
    assert self.rotary_emb is not None
    return self.rotary_emb.get_aiter_cos_sin(dtype
```

And then 

```
def get_aiter_cos_sin(self, dtype):
    cache = self.cos_sin_cache
    key = (cache.device, dtype)

    if key not in self._aiter_cos_sin_cache:
        cos, sin = cache.chunk(2, dim=-1)
        self._aiter_cos_sin_cache[key] = (
            cos.to(dtype).contiguous(),
            sin.to(dtype).contiguous(),
        )

    return self._aiter_cos_sin_cache[key]
```

This way only the first layer creates the sin/cos cache.
