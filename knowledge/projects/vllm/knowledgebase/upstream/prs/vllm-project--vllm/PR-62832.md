# [ROCm][KV Connector] Support sleep mode with MoRIIOConnector in WRITE mode over RDMA

[Upstream PR](https://github.com/vllm-project/vllm/pull/62832) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Lets `MoRIIOConnector` run with `--enable-sleep-mode` in WRITE mode over RDMA. It works the way the NIXL pull connector does (#59635): after a sleep, a worker registers its KV cache again under a new epoch, and the producer handshakes again with a peer whose epoch increased. Part of #59055.

**Depends on #62857** (one exportable physical allocation per KV cache tensor on ROCm). Until that merges, this PR's diff includes its commit; review the last commit only.

**Not a duplicate of #60693.** That PR implements the same feature with an INVALIDATE/ACK protocol between P and D, at about 1,000 non-test lines. This one reuses the epoch scheme and connector hooks that #59625 and #59635 already merged, at +196/−17 non-test lines.

## Claims

- `--enable-sleep-mode` is accepted with MoRIIO in WRITE mode over RDMA. READ mode and XGMI are still refused at startup.
- P, D or both can sleep (level 1) and wake while the peer keeps serving. Afterwards, outputs equal the awake baseline, and D still receives every prompt token over RDMA.
- Sleep releases the KV cache.
- After D wakes, P handshakes with it again once, on its first write to D.
- `sleep(mode=abort)` on P no longer re-registers the released KV cache through a write still queued for an aborted request. Before this fix, that left 16 GiB pinned and every later output garbage.

## Details

**When D sleeps.** In WRITE mode, P writes into D's KV cache.
1. When D sleeps, `unregister_kv_caches` deregisters its KV regions from MORI, and cuMem unmaps the pages.
2. When D wakes, cuMem maps new pages at the same addresses. `restore_kv_caches` registers the regions again, which gives them new MORI memory keys, and bumps the worker's epoch. The handshake listener serves the new registration from then on, and `EngineCore.wake_up` republishes `get_handshake_metadata()` to D's scheduler (the hook from #59635).
3. D's scheduler stamps its workers' newest epoch on the `remote_blocks` message it sends P for each request.
4. Before writing, P compares that epoch with the one it loaded for D. If the stamped one is newer, P handshakes again and drops its sessions built from the old registration.

The epoch rides on `remote_blocks` rather than in `kv_transfer_params` as in NIXL, because here the side that reads a peer's registration is P. When P sleeps, no peer needs to act: D never holds P's memory keys in WRITE mode.

**Writes queued across a release.** P's `sleep(mode=abort)` can abort a request whose write is still queued on P's writer thread, while its blocks are already freed. MORI registers memory lazily when it builds a session, and its MR pool is keyed by address with no overwrite. Running that write after the release would therefore pin the released pages again, and later writes after the wake-up would send D their stale contents. `unregister_kv_caches` first calls `MoRIIOWriter.release_registration()`, which waits for the writes in flight and fails the queued ones, telling D as for a timed-out write.

**MORI version.** cuMem memory is exported to the NIC by its allocation handle, which needs ROCm/mori#729 ("export VMM memory by allocation handle so deregistered regions are freed", in v1.2.4). vLLM's ROCm base images pin MORI `v1.2.3.post1`.

**Compatibility.**
- With sleep mode off, the only change is that layers sharing one KV cache tensor share one MORI registration. Before, the second registration leaked, because MORI keys memory regions by start address.
- Peers on an older vLLM interoperate: `registration_epoch` defaults to 0.
- Nothing in the scheduler, model runner or engine core changes, and nothing new runs on the model execution thread. The re-handshake runs on P's writer thread, and release and restore run only during sleep and wake-up.
- CI: the new unit tests run in the existing AMD `test_moriio_*` step with a fake MORI. The E2E needs two GPUs with RDMA NICs and MORI, which CI lacks, so it ran outside CI.

**Limitations.**
- Only WRITE mode over RDMA. READ mode would need D to follow P's epoch, as NIXL does through `kv_transfer_params`.
- Not tested: hybrid (Mamba) models, CUDA graphs, TP > 1 on this revision.
- Two pre-existing hangs on the WRITE-mode abort path are not fixed here. Prefer `sleep(mode=wait)` with MoRIIO.
  - P aborts a request before its forward runs. Nothing tells D, which has no deadline in WRITE mode, so D waits forever.
  - D aborts a request while it waits for remote KV. Its `request_finished` unmaps the transfer id, so the late write-done never matches and the blocks are never freed. D's prefix-cache reset, and the drain of its next sleep, then hang.
