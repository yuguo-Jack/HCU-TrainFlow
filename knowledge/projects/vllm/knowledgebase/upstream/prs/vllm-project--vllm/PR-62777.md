# [MM][CG] Support ViT full CUDA graph for Ovis2.5

[Upstream PR](https://github.com/vllm-project/vllm/pull/62777) · state: open · merged: False

## Original PR description



## Overview

Adds ViT full CUDA graph support (`SupportsEncoderCudaGraph`) for Ovis2.5 (`Ovis2_5`), images and video. Part of #38175 (claimed [here](https://github.com/vllm-project/vllm/issues/38175#issuecomment-6303889300)). No other open PR or claim covers Ovis2.5 encoder CUDA graphs; #33826 is an unrelated, stale torch.compile change.

## Claims

- `Ovis2_5` captures and replays its Siglip2-NaViT encoder through `EncoderCudaGraphManager` for images and video, on both MRV1 and MRV2.
- The eager path's output is unchanged: greedy tokens and logprobs are bit-identical to `main`.
- The eager and graph encoder paths are now free of GPU<->CPU syncs and pass `VLLM_GPU_SYNC_CHECK=error`. On `main`, eager hit a sync in `rot_pos_emb`, plus `.item()`/`.tolist()` calls on device grids.
- **Performance is not yet demonstrated.** I only have an RTX 4060 Laptop (8 GB). There the ViT is compute-bound, so graphs give no gain (see below). Datacenter-GPU numbers are still to come, so this is a draft.

## Validation

All runs used `AIDC-AI/Ovis2.5-2B` with real weights, bf16, on an RTX 4060 Laptop (SM89) with FLASH_ATTN. Inputs were images of 448², 640×480, 512×896 and 896² (batched together), one 3-image request, and one 6-frame video.

| Check | Result |
|---|---|
| Graph usage (MRV2 / MRV1) | 7/7 and 8/8 hits, 0 misses |
| Encoder embeddings, graph vs eager on the same batch | 5/7 items bit-exact; 2 items max abs diff 0.0115, min per-token cos 0.978 (see note) |
| Greedy text, graph vs eager (6 requests × 48 tokens) | 4 identical; 2 diverge at near-ties (logprob gap 0.125 and 0.000; each token is in the other's top-5) |
| Eager, this PR vs `main` | 6/6 identical tokens, max logprob diff 0.0 |
| `VLLM_GPU_SYNC_CHECK=error`, eager and graph | pass |
| `pytest tests/models/multimodal/generation/test_vit_cudagraph.py -k ovis2_5` | 2 passed* |
| `pre-commit run` on changed files | pass |

\*The stock config cannot start Ovis2.5 on 8 GB even without graphs (eager profiling of a 1792² dummy runs out of memory). I ran the test locally with `load_format="dummy"` + `dummy_hf_overrides` + `max_num_batched_tokens=4096`; the committed config is the standard one for CI.

**Embedding diff note.** The diff comes from padding inputs up to the graph's token budget, which changes GEMM M, so cuBLAS picks a different kernel. Softmax over the 65k visual vocabulary amplifies the resulting bf16 rounding differences. I verified that:
- Running the captured function eagerly on the same padded buffers gives exactly the graph output (diff 0).
- Filling the padded rows with random noise leaves the real-token outputs unchanged (diff 0), so padding does not leak into real tokens.
- `max_seqlen` has no effect.

**Encoder-only latency on the RTX 4060 Laptop** (eager → graph, ms, 20 iterations):

| Image | Exact-fit budget | Padded to default-style budget |
|---|---|---|
| 448² (198 tok) | 43.9 → 42.7 | 44.3 → 50.0 (256) |
| 640×480 (302 tok) | 57.7 → 57.6 | 68.7 → 103.9 (512) |
| 896² (786 tok) | 217.3 → 218.6 | 223.8 → 259.5 (1024) |

On this GPU the ViT is compute-bound, so removing launch overhead gains nothing, and padding to a larger budget costs compute in proportion. I expect gains on H100/B200-class GPUs, where a single-image ViT forward takes a few ms and launch overhead is a real share, as reported for other models on #38175. I'll add H100 numbers here before marking this ready; help from anyone with access is welcome.

## Details

- **`siglip2navit.py`:** all grid-dependent work now lives in `prepare_encoder_metadata()`, shared by the eager path, graph capture and graph replay. That covers the bicubic-interpolated position embeddings, rotary cos/sin, window index, `cu_seqlens`/`cu_window_seqlens` and host-side `max_seqlen`. The forward methods accept an optional `encoder_metadata`. This is the same pattern as Qwen2.5-VL's `prepare_encoder_metadata`, including its window-sequence bound for capture.
- **`ovis2_5.py`:**
  - Only the ViT (`VisualTokenizer.encode`) is captured. The visual head, the softmax over the visual vocabulary and the `vte` projection are a few large GEMMs that gain nothing from graphs, and capturing them would hold `[budget, 65536]` intermediates in the graph pool. They run in `postprocess_encoder_output`, which also wraps each item with its indicator embeddings, so outputs match `embed_multimodal`.
  - `get_encoder_cudagraph_item_specs` counts the indicator tokens in `output_tokens`, so DP gather and buffer sizing see final per-item lengths.
  - `grids` / `video_grids` are now `keep_on_cpu=True`, as in Qwen2-VL, which removes device-to-host reads in both paths.
- **Coverage gaps:**
  - `Ovis2_6ForCausalLM` / `Ovis2_6_MoeForCausalLM` map to the same class and therefore also get graph support. They are untested here: the 2B checkpoint isn't public and the MoE doesn't fit on my GPU.
  - The ViT DP mode (`mm_encoder_tp_mode="data"`) is untested (single GPU).
  - FlashInfer ViT attention isn't handled specially. It wasn't supported by this encoder's eager path before either.
- **Complexity:** +509/−91 in `vllm/`. A large part of that is existing Siglip2 logic moved into `prepare_encoder_metadata` rather than new logic.
