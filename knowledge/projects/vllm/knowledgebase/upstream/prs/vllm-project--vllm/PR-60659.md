# [Perf][GDN] Internal prefill checkpoints for the Triton/FLA and AITER FlyDSL GDN prefill backends

[Upstream PR](https://github.com/vllm-project/vllm/pull/60659) · state: open · merged: False

## Original PR description

## Overview

Internal prefill checkpoints (#52789, generalized in #57783; Mamba2 in #57329) export a prefill's block-boundary state from inside one forward, so in `mamba_cache_mode="align"` the scheduler no longer stops the prefill at its last block boundary. #60050 does this for the FlashInfer GDN prefill backend. This PR extends the same shared checkpoint mechanism to the **Triton/FLA** (CUDA, ROCm) and **AITER FlyDSL** (ROCm) GDN prefill backends, whose chunk kernels return only each sequence's final state. No kernel changes.

## Claims

- Qwen3.5-27B on 8x MI308X (TP8, AITER FlyDSL prefill), 8000-token prompts, post-rebase A/B: mean TTFT −11.4% at concurrency 4 and −18.6% at 16. This is consistent with the two pre-rebase runs (−11% to −12% and −16% to −17%). Throughput is unchanged and TPOT is +3%. At concurrency 1, TTFT is +11.8% on this setup; see Details.
- GSM8K is within run-to-run variation: original A/B 0.9636 baseline vs 0.9651 with this PR; post-rebase on the same nightly, main 0.9636 vs this PR 0.9606 (`d907ca3d8`) and 0.9636 (current head).
- Outputs, final states and exported checkpoints match the unsplit computation (both backends, fp32 and bf16 state). On the Qwen3.5-27B server, after the same primer prompt on both servers, resuming from a checkpoint this PR exported gives the same greedy tokens and logprobs, bit for bit, as resuming from the state main stores at that boundary.
- Batches without a checkpoint are unchanged. This is not enabled with speculative decoding or `prefix_match_unit` smaller than the block size.

## Details

- **Split**: the builder cuts each checkpointed row at its checkpoint in the prefill varlen batch; only a row's first segment gets the row's initial state. One chunk-kernel call over the segments leaves each checkpoint as the final state of its row's first segment. The tails (shorter than one block) started from a zero state there, so a second, small call reruns them from their checkpoints, and their outputs and final states replace the first call's. Both calls reuse the existing per-backend metadata builder.
- **Export**: conv window and recurrent state are stored by #60050's shared `MambaPrefillCheckpointExporter`. Its `recurrent_rows` argument selects each checkpoint directly from the split-state buffer.
- **Opt-in**: the Qwen GDN layer declares checkpoint alignment 1 for Triton/FLA and FlyDSL. #60050's shared all-Mamba-layer check then reserves one checkpoint block only when every Mamba layer can export a checkpoint. The metadata builder turns the split on for Qwen GDN layers, checked by layer type, whose spec reserves a checkpoint block. It does not key off the alignment value: KDA layers sharing the builder also reserve checkpoint blocks, and the spec may carry a shared Mamba checkpoint grid instead, as #61601 proposes. If a checkpoint is scheduled but neither the FlashInfer plan nor the split is set, `_forward_core` fails instead of leaving the reserved block unwritten.
- **Cost**: only steps with a checkpointed prefill pay: per GDN layer, a second chunk-kernel call over the tails, one export kernel and gathers/scatters. Where both arms run the same single step (an 8000-token prompt on a 400-token block), this measured +2 ms (+0.4%) at concurrency 1.
- **Concurrency 1**: TTFT is +11% because the PR runs the 8000-token prompt in one step (578 ms) where the baseline runs 7616 + 384 tokens in two (520–531 ms over two runs). The baseline's own single 8000-token step also takes 579 ms. At concurrency 4 and 16, the baseline's extra tail step delays other requests' prefills, and that dominates.
- **Limitations**: not enabled with speculative decoding or `prefix_match_unit` smaller than the block size. Partial-block prefix hits and speculative block relocation interact with checkpoint blocks in ways not validated here. CUDA and ROCm only.
- **Not a duplicate**: #60050 covers FlashInfer; this PR now builds on its shared checkpoint declaration/export mechanism for Triton/FLA and FlyDSL. #55873 / #55875 / #55876 add application-directed checkpoints.
- **Placement**: backend-neutral split execution lives in `gdn/prefill_checkpoint.py` instead of further growing `qwen_gdn_linear_attn.py`; backend metadata stays in `gdn_attn.py`.

Thanks for this PR. I looked at it while I measured the Mamba `align` split on a hybrid model with MTP. Two notes: a rebase hazard with #61601, and data for the configuration that this PR does not enable yet.

**1. Rebase hazard with #61601 (cc @ZJY0516).** Both PRs change the same line in the Qwen GDN layer's KV spec:
- this PR: `prefill_checkpoint_alignment=alignment`, which is `GDN_SPLIT_CHECKPOINT_ALIGNMENT` (= 1) on Triton/FLA and FlyDSL;
- #61601: `prefill_checkpoint_alignment=get_mamba_prefill_checkpoint_grid(vllm_config)`.

The builder in this PR turns the split on only when `checkpoint_alignment == GDN_SPLIT_CHECKPOINT_ALIGNMENT`. If the conflict is resolved to #61601's grid (16 with `prefix_match_unit` 16, else the block size), the split stays off. But the spec still declares `num_prefill_checkpoint_blocks=1`, so the scheduler can stop splitting at the checkpoint, and the manager can publish a checkpoint block that the forward never writes. Nothing would fail at once; a later prefix hit would read a stale state. I found this by reading the two diffs; I have not reproduced it in a test. Keying `split_prefill_checkpoints` off the backend and `num_prefill_checkpoint_blocks > 0`, instead of the alignment value, would make the two PRs independent of merge order.

**2. Data for spec decoding with `prefix_match_unit` < block.** This PR is off with speculative decoding and with `prefix_match_unit` smaller than the block. Our deployment has both (Qwen3.8-Flash-Next-FP8 with MTP 3, `--prefix-match-unit 16`, block 480, 8 × A100, multi-turn agentic workload with about 98 % prefix-cache hits), so it keeps every split:
- A scheduler step log shows each prefill admission (median 2 requests, 1,743 new tokens, which fit in one 2,048-token step) running as a chain of 3–5 mixed steps.
- `Scheduler._mamba_block_aligned_split` on a stub scheduler with that configuration (20,000 simulated admissions) gives 3.43 mixed steps per admission today and 2.33 with this PR's scheduler rule. With this PR, #60888's column rule and #61601's PLE checkpoints, and with the spec-decode and unit gates removed, it gives 1.01.
- On our model a mixed step costs much more than a decode step, so each removed step counts.

I have a local prototype of the spec-decode and unit-16 enablement on top of this PR, #60888 and #61601 (CPU tests only, not yet run on GPU). I can send it as a follow-up after these land, if that is useful.

Thanks for catching this interaction and for sharing the measurements.

**1. Rebase hazard with #61601.** You're right. On the previous head, if #61601's shared checkpoint grid (not 1) replaced the Qwen GDN alignment, an eligible final prefill could still get internal-checkpoint metadata while `split_prefill_checkpoints` stayed off. The scheduler would then skip the boundary split, and `MambaManager` would later publish the reserved checkpoint block although the forward never exported its state.

Fixed in 49b7f8677:

- Split planning no longer uses the alignment value as a layer-type tag. It requires a Triton/FLA or FlyDSL backend, a reserved checkpoint block, and Qwen GDN layers in the cache group.
- The layer check is needed because backend plus `num_prefill_checkpoint_blocks > 0` alone would also turn the split on for KDA users of the shared builder that reserve checkpoint blocks, notably `KimiK3ROCmKDAMetadataBuilder`, which exports its checkpoints through its own path. With MTP, a batch mixing spec-decode rows and a checkpointed prefill would then hit the split planner's `assert spec_sequence_masks is None`.
- `_forward_core` now fails loudly if a Qwen GDN layer receives checkpoint metadata without a FlashInfer plan or a split plan, instead of leaving the block unwritten.
- The main test now takes the spec from `QwenGatedDeltaNetAttention.get_kv_cache_spec` and covers the fail-fast path. A new test checks that the builder enables the split for a Qwen GDN layer with either alignment 1 or the block size, and not for another layer on the GDN backend.

So whichever of the two PRs lands second can take #61601's `get_mamba_prefill_checkpoint_grid(vllm_config)` line as is. I revalidated the current head on 8x MI308X with the related tests, GSM8K, and prefix-hit continuation checks; details are in the updated description. cc @ZJY0516

**2. MTP with `prefix_match_unit` < block.** Both gates stay in this PR: the split planner does not handle the spec-decode row layout yet, and sub-block checkpoints have not been validated on this path. Qwen3.8-Flash-Next also needs #61601, or equivalent PLE checkpoint support, before the scheduler takes any internal checkpoint, since every Mamba group has to export one.

I haven't reproduced the exact 3.43 / 2.33 / 1.01 figures, but the direction matches how `_mamba_block_aligned_split` places its stops: a valid internal checkpoint removes the block-boundary and tail stops, and #60888's column rule makes it valid for more mid-block starts. A follow-up after these land sounds useful; GPU accuracy runs with real prefix hits (multi-turn GSM8K, for example) would be the main thing needed to enable the spec-decode and unit-16 paths.
