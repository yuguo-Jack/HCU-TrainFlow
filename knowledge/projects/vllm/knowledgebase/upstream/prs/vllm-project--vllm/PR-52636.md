- rayhanmemon · comment · 2026-08-25T19:02:47Z · [source](https://github.com/vllm-project/vllm/pull/52636#issuecomment-5415293026)

Suggestion for the new **Pull vs Push** section (optional, please merge without it if you'd rather not grow the section!)

**Context.** I was running the two-instance disaggregated-prefill setup from the usage guide on a rented two-GPU pod — one prefiller on GPU 0, one decoder on GPU 1, the default `NixlConnector` on both, the repo's `toy_proxy_server.py` in front — and pushing a small benchmark through it at three prompt lengths. 

As part of the run, I had planned a check of which UCX transport was actually carrying the KV cache. In my run nothing announced it: clean bring-up, `NIXL compatibility check passed`, all 49 completions through the toy proxy returned 200, plausible-looking throughput — and the KV cache was crossing TCP the whole time.

The section tells a reader which connector to choose, but not how to check which path they actually got. 

Proposed addition:

> **Checking which transport you got.** Start both instances once with `UCX_PROTO_INFO=y`. In the log, find the protocol rows whose title mentions `cuda` — e.g. `remote memory read by ucp_get*(multi) into cuda/GPU0 from cuda` — and read the transport in the right-hand column. If it names `tcp/...`, the KV cache is crossing TCP rather than `cuda_ipc` (in my run the row printed `software emulation | tcp/eth0`). Note that `cuda_ipc` can appear in the advertised list — `device(cuda_ipc/cuda)  am(tcp/eth0 cma/memory cuda_ipc/cuda)` — without ever being selected; advertised is not selected. The consumer's `KV Transfer metrics ... Throughput (MB/s)` line (per transfer) gives a number to sanity-check against your hardware class, and `nvidia-smi topo -p2p r` shows whether peer access exists at all.
