# [Bugfix][HiSparse] Route by swap-row capacity, not the index-group workspace

[Upstream PR](https://github.com/vllm-project/vllm/pull/60682) · state: closed · merged: True

## Original PR description



## Overview

HiSparse crashes when a batch has exactly `max_num_seqs * max_decode_query_len + 1` tokens. With `max_num_seqs=1` the engine fails at startup, and with `max_num_seqs=2` a 3-token prompt crashes at runtime:

```
ValueError: HiSparse swap rows exceed the configured speculative decode capacity: stop=2, capacity=1.
```

Part of #60072.

## Claims

- HiSparse now routes a batch to `swap_in` only when the batch fits the swap rows that `swap_in` consumes. Larger batches take the existing all-resident fallback.
- No performance impact: the change is a Python-side routing comparison against a fixed size. Batches up to the swap capacity take the same path as before; only the single size that crashed changes path.

## Details

**Root cause.** `HiSparseMLAIndexGroup.convert_logical_to_physical_topk` sends a batch to `swap_in` whenever the batch fits `physical_topk_indices`. That index-group workspace is allocated with one spare row (`max_decode_rows + 1`). `swap_in`, however, writes into the HiSparse runtime's shared swap rows, which hold exactly `min(max_num_batched_tokens, max_num_seqs * max_decode_query_len)` rows. A batch one token larger than the swap capacity therefore passes the routing check and then overflows in `_step_rows`.

With `max_num_seqs=1`, the CUDA-graph capture sizes are `[1, 2]`. The 2-token piecewise capture follows the all-resident prefill path into this conversion, so the engine fails at startup. With `max_num_seqs=2`, capture sizes `[1, 2, 4]` skip 3 tokens, so the failure only appears when a real 3-token batch arrives.

**Fix.** Route on `HiSparseRuntime.max_swap_rows`, the capacity that `swap_in` actually consumes. The non-HiSparse `SparseMLAIndexGroup` does not change.
