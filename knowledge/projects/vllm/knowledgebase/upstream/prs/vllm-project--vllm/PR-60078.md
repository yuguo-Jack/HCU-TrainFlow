# [Bugfix][KV Offload] Order SimpleCPUOffload loads after pending compute reads

[Upstream PR](https://github.com/vllm-project/vllm/pull/60078) · state: open · merged: False

## Original PR description

## What

`start_load_kv` launches the CPU->GPU copy for `SimpleCPUOffloadConnector` without waiting on the compute stream. A GPU block reused for a load can still be mid-read by a compute op queued before the load (e.g. a pending speculative decode step), so the load can overwrite it before that read completes. The store path already guards the symmetric hazard this way (`wait_for_save`, cross-referencing #45704 in its docstring); the load path had no equivalent barrier.

Fix: record a compute-done event before each load and pass it as `wait_event` to `launch_copy`, mirroring `wait_for_save`. `DmaCopyBackend.launch_copy`'s `wait_event` handling is already direction-agnostic (`copy_backend.py`'s `_copy_loop` does `stream.wait_event(wait_event)` before the copy regardless of `is_store`), so this only required adding the missing call site, not a new mechanism.

## Why this isn't a duplicate

PR #47324 proposes the same fix but has sat since 2026-07-01 with merge conflicts, zero human review, and (as of this writing) bundles two unrelated files from a different issue (#47323's `triton_kernels.cmake` patch) into the same branch. Given it's been stale for two months, I'm opening a clean PR scoped to only this fix rather than trying to untangle that branch. Happy to close this in favor of #47324 if a maintainer prefers to pick that one up and clean it instead.

Two independent reports confirm the same mechanism on different hardware: #47282 (original, with the `_get_open_port`-adjacent ZMQ race ruled out and the actual cause narrowed to this missing barrier) and #59768 (reproduced on an RTX PRO 6000 / SM120, with a device-side check showing the exact garbage-ring-row symptom this barrier prevents).

## Test plan

```
pre-commit run --files vllm/v1/simple_kv_offload/worker.py tests/v1/simple_kv_offload/test_worker.py
# ruff check, ruff format, mypy: all pass
```

I corrected `test_transfer_hooks_pass_wait_event_for_store_only`, which asserted the missing load-side `wait_event` as expected behavior; it's now `test_transfer_hooks_pass_wait_event_for_both_load_and_store` and checks both directions get a real event.

I also added `test_load_orders_after_compute_read`, a load-direction mirror of the existing `test_store_orders_after_compute_write` race test: a compute stream reads a GPU block after a deliberate delay while a load concurrently overwrites it, asserting the unguarded case reliably corrupts and the barriered case never does.

**I do not have a CUDA/ROCm GPU to run these.** `tests/v1/simple_kv_offload/test_worker.py` skips at module level without one (`current_platform.is_cuda_alike()`), so I could not execute `test_load_orders_after_compute_read` or confirm the existing suite still passes end-to-end. I verified the change by direct code reading instead: `wait_event` is already a generic, direction-agnostic parameter threaded through `launch_copy` → `_copy_loop`, and the new load-side event-recording code is a line-for-line mirror of the existing, working store-side code in the same file (`wait_for_save`). I'd appreciate a maintainer or CI running the suite to confirm before merge; happy to fix anything that comes up.

Closes #47282, closes #59768.
