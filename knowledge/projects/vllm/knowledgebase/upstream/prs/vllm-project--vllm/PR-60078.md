# [Bugfix][KV Offload] Order SimpleCPUOffload loads after pending compute reads

[Upstream PR](https://github.com/vllm-project/vllm/pull/60078) · state: closed · merged: False

## Original PR description

## What

`start_load_kv` launches the CPU->GPU copy for `SimpleCPUOffloadConnector` without waiting on the compute stream. A GPU block reused for a load can still be mid-read by a compute op queued before the load (e.g. a pending speculative decode step), so the load can overwrite it before that read completes. The store path already guards the symmetric hazard this way (`wait_for_save`, cross-referencing #45704 in its docstring); the load path had no equivalent barrier.

Fix: record a compute-done event before each load and pass it as `wait_event` to `launch_copy`, mirroring `wait_for_save`. `DmaCopyBackend.launch_copy`'s `wait_event` handling is already direction-agnostic (`copy_backend.py`'s `_copy_loop` does `stream.wait_event(wait_event)` before the copy regardless of `is_store`), so this only required adding the missing call site, not a new mechanism.

## Why this isn't a duplicate

PR #47324 proposes the same fix but has sat since 2026-07-01 with merge conflicts, zero human review, and (as of this writing) bundles two unrelated files from a different issue (#47323's `triton_kernels.cmake` patch) into the same branch. Given it's been stale for two months, I'm opening a clean PR scoped to only this fix rather than trying to untangle that branch. Happy to close this in favor of #47324 if a maintainer prefers to pick that one up and clean it instead.

Two independent reports confirm the same mechanism on different hardware: #47282 (original, with the `_get_open_port`-adjacent ZMQ race ruled out and the actual cause narrowed to this missing barrier) and #59768 (reproduced on an RTX PRO 6000 / SM120, with a device-side check showing the exact garbage-ring-row symptom this barrier prevents).

- CodersAcademy006 · comment · 2026-10-30T08:33:37Z · [source](https://github.com/vllm-project/vllm/pull/60078#issuecomment-6518575924)

Checked this against `main` at `8b10bda57c` as you asked, and you are right: the window this PR closes is no longer reachable. I am closing it.

The literal observation in the PR description still holds. `start_load_kv` (`vllm/v1/simple_kv_offload/worker.py:272-287`) still passes no `wait_event`, so there is no stream-level ordering between a load and a pending compute read. What has changed is that nothing can still be reading the destination block. There are only two candidate readers, and both are closed.

**Earlier in-flight steps.** #45357 (merged 15 June 2026, `d467a2a7f2f0`) added deferred block freeing, and `Scheduler._request_blocks_can_be_freed` (`vllm/v1/core/sched/scheduler.py:2724`) carries the comment "We must defer freeing blocks if an async kv connector may write to them immediately (not ordered with GPU stream)", which is this hazard stated exactly. Blocks are withheld from the pool until `processed_step_seq >= request.last_sched_seq`, including on the preemption path (`scheduler.py:785`), so a freshly allocated load destination cannot be a block an in-flight step is still reading. The gate at `scheduler.py:184-186` is `max_concurrent_batches > 1 and kv_transfer_config.is_kv_consumer`, and it does cover this connector: `SimpleCPUOffloadConnector` runs as `kv_role="kv_both"` (`docs/usage/metrics.md:52`, `tests/v1/simple_kv_offload/test_integration.py:32`) and `KVConsumer = Literal["kv_consumer", "kv_both"]` (`vllm/config/kv_transfer.py:12`), so `is_kv_consumer` is true. The `max_concurrent_batches > 1` half is not a gap either, since with a single concurrent batch there is no earlier in-flight step to race.

**The current forward.** This was your point on `worker.py:273`, and it holds for a reason worth writing down. `SimpleCPUOffloadScheduler.get_num_new_matched_tokens` returns `(hit_length, True)` (`vllm/v1/simple_kv_offload/manager.py:389`), so a CPU hit is always an async load. The request therefore takes the `skip_request(request_queue); continue` path at `scheduler.py:1296`, is never appended to `self.running` for that step, and contributes no tokens to the forward that `start_load_kv` trails. In the sync-load case the mixin issues the load before the forward (`vllm/v1/worker/kv_connector_model_runner_mixin.py:83`), so there is no ordering to get wrong there either.

#47728 (merged 8 July 2026, `cd0de48d0883`) is adjacent: its `simple_kv_offload/manager.py` edit swaps `max_num_batched_tokens` for `vllm_config.max_in_flight_tokens`, which exists so that in-flight steps can transiently hold their blocks.

Given that, the rest of your review is moot on this branch, so I am not pushing the `bind_connector_metadata` move or the hook-test change. For the record, the `#45704` reference in my comment was wrong in the way you said: that is the store bug, and the comment should not have borrowed it.

Worth being precise about what your runs showed: 22/22 with the patch, and the load-event forwarding check failing on unpatched `main`, confirmed that the patch does what it claims, which is still true. What they could not show is that the engine is able to reach the unsafe state, and that is the part that does not hold.
