# [Bugfix][Kernel] Fixes issue #49290: MRotaryEmbedding Triton kernel hardcodes Neox pairing for GPT-J style models

[Upstream PR](https://github.com/vllm-project/vllm/pull/49323) · state: open · merged: False

## Original PR description

## Purpose

**Fixes #49290**


`MRotaryEmbedding.forward_cuda`'s 2D mrope branch unconditionally calls `triton_mrope`, and `_triton_mrope_forward` hardcodes **Neox-style (half-split)** rotation pairing — the instance flag `is_neox_style` is never consulted. For models whose q/k weights require **GPT-J (interleaved even/odd) pairing** (e.g. GLM-OCR, whose runtime instance has `apply_rotary_emb.is_neox_style=False`), every rotary-dimension element is paired with the wrong counterpart:

    Expected (GPT-J):  rotate(x[0], x[1]), rotate(x[2], x[3]), ...
    Actual   (Neox):   rotate(x[0], x[64]), rotate(x[1], x[65]), ...

No error is raised; the model silently produces garbled / repetitive output in eager mode. 

**Fix**: add `is_neox_style: tl.constexpr` to `_triton_mrope_forward`:

- `True` → original Neox half-split path (unchanged);
- `False` → new GPT-J even/odd branch: stride-2 loads (`2i`, `2i+1`), rotate, interleaved store.

The primary modification is to the `_triton_mrope_forward` function, where an `is_neox_style` conditional check is added. If `is_neox_style` is true, the original Neox-style rotation implementation is executed; otherwise, the newly added GPTJ-style rotation pairing logic is applied.

## Test Plan

New regression test `tests/kernels/test_mrope_kernel.py` (included in this PR), comparing `forward_cuda` (Triton kernel) against the independent pure-PyTorch `forward_native` reference on identical deterministic inputs, with GLM-OCR's exact config (`mrope_section=[16,24,24]`, `head_size=rotary_dim=128`, `theta=10000`, bf16). 25 cases, parametrized over:

- rotation style: Neox / GPT-J
- t/h/w frequency layout (`mrope_interleaved`): chunked / interleaved
- token count: 1 (decode) / 4 (short prefill) / 129 (long prefill)
- position pattern: uniform t/h/w rows (decode-stage) / distinct rows
- plus one backward-compat case: `triton_mrope()` without the new argument

```bash
pytest tests/kernels/test_mrope_kernel.py -v
```

E2E verification with GPT-J style models (e.g. GLM-OCR):

```bash
$ vllm serve <path_to_model>  --trust-remote-code  # default graph mode
$ vllm serve <path_to_model>  --trust-remote-code --enforce-eager # eager mode
```
