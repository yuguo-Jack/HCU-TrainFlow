# [Bugfix][KV Offload] Always attempt NIXL agent removal during peer teardown

[Upstream PR](https://github.com/vllm-project/vllm/pull/60279) · state: closed · merged: True

## Original PR description

## Overview

Fixes the stale NIXL peer-registration state in the P2P tiering transport that can permanently wedge the data plane after a peer-down/reconnect cycle such as SIGSTOP/SIGCONT, while the control plane keeps reporting HIT. Fixes #60205.

## Problem

`NixlTransport.remove_remote_peer()` runs two independent teardown operations in sequence: releasing the remote descriptor-list handle, then removing the remote agent. If `release_dlist_handle()` raises, the exception aborts the method before `remove_remote_agent()` is attempted, so the NIXL remote agent stays registered after the peer is gone — leaving a stale registration behind.

`_publish_peer()` has the same problem on its superseded-registration path: both teardown calls share a single `try` block, so a release failure skips the agent removal for a registration that is being discarded.

**Reporter's reproduction (#60205), condensed:** disaggregated prefill/decode, `TieringOffloadingSpec` over UCX/NIXL. After SIGSTOP of one EngineCore and SIGCONT, the control plane recovers (sessions reconnect, heartbeats and lookups keep returning HIT), but transfers to/from that rank fail permanently — `NIXL_ERR_REMOTE_DISCONNECT`, then `NIXL_ERR_NOT_FOUND` on every poll. Fetches time out after 30 s and recompute; healthy ranks keep working; only a group restart fixes the wedged rank.

## Fix

Move both teardown calls into one small `_release_remote_handles()` helper that runs each operation under its own `try`/`except`, and call it from both `remove_remote_peer()` and `_publish_peer()`. Failures from either teardown operation are logged rather than aborting teardown midway, so `remove_remote_agent()` is always attempted. The `_peer_lock`/`_peer_gen` handling in `remove_remote_peer()` on `main` is unchanged.

## Evidence from the reviewer

The reviewer reproduced the stale-registration wedge on real NIXL/UCX: two pods on different nodes, nixl 1.5.0, `rc_mlx5` over InfiniBand, DRAM-only transfers, using the same call sequence as `NixlTransport`, with every WRITE checksum-verified at the target:

- Teardown plus a same-name re-add after a 249-second SIGSTOP/SIGCONT cycle recovers cleanly; the re-add does not reuse a stale endpoint.
- With the peer frozen, the WRITE raises `NIXL_ERR_REMOTE_DISCONNECT`. If `remove_remote_agent` was also skipped (the pre-patch path when `release_dlist_handle` raises), the SIGCONT plus re-add reports OK, but every WRITE after that still fails with `REMOTE_DISCONNECT` (3 attempts over ~2 min). This matches #60205.
- Calling `remove_remote_agent` unconditionally, then re-adding, recovers it.

## Important qualification

The regression tests simulate `release_dlist_handle()` raising. Why it raised in the original incident is not confirmed.

## Scope boundary

This PR does not claim to stop in-flight writes, change transfer polling semantics, or fix the server notification ordering — `remove_remote_peer()` does not stop an in-flight WRITE. Server notification ordering and transfer-terminal handling are covered by #59790; `poll()`/`NOT_FOUND` handling stays out of scope and will be decided jointly with #59790/#49632.

## Root cause and design

**Root cause.** `remove_remote_peer()` released the dlist before removing the remote agent with no error handling — if `release_dlist_handle()` raised, `remove_remote_agent()` never ran, orphaning the NIXL registration with no Python reference left. `_publish_peer()` shared one `try` block across both calls with the same skip-on-raise behavior.

**Why teardown failures are logged, not raised:** `remove_remote_peer()` runs inside `manager._reap_dead_sessions()`, which has no exception guard up to `get_finished_jobs()`; raising would abort the reap loop and propagate into the scheduler. The EC connector's NIXL transport follows the same log-and-continue pattern.
