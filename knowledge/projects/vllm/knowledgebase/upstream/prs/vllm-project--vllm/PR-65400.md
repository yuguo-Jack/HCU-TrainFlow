# [Recipe] Kimi-K3, MiniMax-M3.1-Flash: add Rubin VR200 support

[Upstream PR](https://github.com/vllm-project/vllm/pull/65400) · state: open · merged: False

## Original PR description



## Overview

Adds Rubin VR200 to the Kimi-K3 and MiniMax-M3.1-Flash recipes, using the `vr200` profile from vllm-project/recipes#1209. Both are declared `supported`, not `verified`.

## Claims

- **Kimi-K3:** VR200 is selectable on the `default`, `nvfp4` and `fp8` variants with `vllm/vllm-openai:cu134-nightly`. It opens on `multi_node_tp` over 2 trays (8 GPUs).
- **MiniMax-M3.1-Flash:** VR200 is selectable on the `default` variant with `vllm/vllm-openai:minimax-m31-flash-cu134`, at TP4.
- **Scope:** this changes recipe content only. It claims no serving result or performance on Rubin.

## Validation

**These recipes have not been served on Rubin, and no model evaluation was run.** Validation covers rendering only.

| Check | Result |
|---|---|
| `node scripts/validate-source.mjs --source vllm --dir <this checkout>/recipes` (renderer at vllm-project/recipes `main`) | Pass |
| `pnpm test:schema`, `test:overlay`, `test:presets` | All pass |
| `pnpm test:render` | 1 fail: `resolveSelection renders every preset point identically`, which also failed on an earlier renderer baseline without these recipe changes |
| JSON API before and after, about 22,590 files, ignoring source metadata | Content changes only in these two recipes and their promoted variant pages; 30 files added |

In the rendered VR200 commands, every strategy uses the expected image, and none contains `deep_gemm` or ROCm env vars. Both images publish `amd64` and `arm64`.

## Details

A recipe's `blackwell` block doesn't apply on Rubin in the renderer, and without it these recipes lose required settings such as the KV dtype and attention backend. Each recipe now shares that block with a `rubin` block through a YAML anchor.

- **Kimi-K3 backend:** `TOKENSPEED_MLA` accepts any 10.x device, which includes SM107.
- **AMD-only modes:** MiniMax-M3.1-Flash's DBO, SP and Mono decode modes were hidden by `blackwell: unsupported`, so they now also set `rubin: unsupported`.
- **Not carried over:** GB200/GB300 MegaMoE, the tuned PD configurations, the AgentX presets and Kimi-K3's `multi_node_tp_dp`, none of which have been run on Rubin. PD on VR200 therefore renders the plain baseline.

**Where review is needed:**

- **MiniMax-M3.1-Flash image:** `minimax-m31-flash-cu134` is a local build (its labels report commit `unknown`, created 2026-10-22), so I couldn't confirm it supports these flags, in particular NVFP4 KV with the `FLASHINFER_TS` DSpark draft.
- **MSA on Rubin:** the [Rubin preview post](https://vllm.ai/blog/2026-10-09-vera-rubin-preview) lists the Rubin MSA decode kernels as unfinished and describes FP8 KV for MiniMax M3.
- **Image note on the page:** the renderer's Rubin note says only the nightly image runs on this hardware, which also shows beside MiniMax-M3.1-Flash's dedicated image. That text lives in vllm-project/recipes.

Not a duplicate: open PRs touching these two recipes cover Ascend variants, env cleanup, ROCm TP2 and GB300 presets, and none adds Rubin.
