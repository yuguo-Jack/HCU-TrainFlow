## Code Review

This pull request introduces an "unwrapped" execution mode for FusedMoE to improve compatibility with torch.compile. Key changes include the registration of `moe_expert_projection` as a custom op, the addition of `all_gatherv` and `reduce_scatterv` distributed operations, and updates to the modular kernel and MoE runner to support direct-call paths and independent tensor allocations. Review feedback highlighted a bug where the `intermediate_size` and `hidden_dim` arguments were swapped in the `w2` expert projection call, and pointed out redundant memory allocations in the `unwrapped` path within `TritonExperts` that should instead reuse existing workspace buffers.

- gemini-code-assist[bot] · comment · 2026-05-14T14:46:13Z · [source](https://github.com/vllm-project/vllm/pull/42649#discussion_r3242152643)

File: `vllm/model_executor/layers/fused_moe/experts/triton_moe.py` · line None

![high](https://www.gstatic.com/codereviewagent/high-priority.svg)

These allocations are redundant and result in excessive memory usage. In `unwrapped` mode, `workspace13` and `workspace2` are already allocated as independent tensors (not views into a shared buffer) in `modular_kernel.py`. You should reuse the passed `workspace13` and `workspace2` buffers instead of allocating new ones via `get_graph_local_tensors`. Specifically, `intermediate_cache2` can use `workspace13` directly, and `intermediate_cache1`/`3` can use `workspace2` (since they are used sequentially and can safely share memory when storage offsets are zero). If separate tensors are strictly required for `torch.compile` to avoid aliasing, they should be requested via `workspace_shapes` and allocated in `_allocate_buffers` to maintain centralized memory management.

- gemini-code-assist[bot] · comment · 2026-05-14T14:46:13Z · [source](https://github.com/vllm-project/vllm/pull/42649#discussion_r3242152650)

File: `vllm/model_executor/layers/fused_moe/experts/triton_moe.py` · line 354

![high](https://www.gstatic.com/codereviewagent/high-priority.svg)

The `intermediate_size` and `hidden_dim` arguments are swapped for the second expert projection (`w2`). For the `w2` GEMM, the output dimension is `K` (hidden dimension) and the input dimension is `N` (intermediate size). Passing them as `N, K` will cause `try_get_optimal_moe_config` to perform an incorrect configuration lookup, leading to sub-optimal kernel performance.

```suggestion
                K,
                N,
```
