# [Bugfix] Fix int32 token offset overflows in Qwen3.5 attention and GDN prefill kernels

[Upstream PR](https://github.com/vllm-project/vllm/pull/63761) · state: closed · merged: True

## Original PR description

<!-- claude-projects-attribution: {"github_login":"simon-veitner-redhat"} -->

_Requested by **Simon**_


## Overview

Fixes #63759.

Several Triton kernels on the Qwen3.5 prefill path multiply an int32 token index by a row stride before adding it to a pointer. Triton passes integer arguments below 2^31 as int32, and `tl.program_id`, `tl.arange` and the int32 `query_start_loc` are int32 too, so the offset wraps once `token * stride >= 2^31`. The result is wrong outputs or an illegal memory access. This PR computes those offsets in int64, one commit per kernel, each with a regression test.

| Kernel | Triggers when (Qwen3.5-9B unless noted) | Fix |
|---|---|---|
| `_fused_qk_rmsnorm_rope_gate_kernel` (`fused_qk_norm_rope.py`) | token index >= 209,716 (qkv row stride 10,240), i.e. a 209,717-token step; hit in the startup profile run | `tl.program_id(0).to(tl.int64)` |
| `store_cache_checkpoints_kernel` (`mamba/checkpoint.py`) | token index >= 174,763 (qkvz stride 12,288); real prefills with prefix caching only | int64 `token_idx` before `* x_stride_0` |
| `_fused_post_conv_kernel` (`fused_gdn_prefill_post_conv.py`) | token index >= 262,144 (conv row stride 8,192) | int64 per-block base offset, int32 in-block offsets |
| `chunk_gated_delta_rule_fwd_kernel_h_blockdim64` (`chunk_delta_h.py`), spotted by reviewer Roberto (`LopezCastroRoberto`) | H=64: 2+ sequences with a later one starting at token >= 131,072 | int64 before `* V * K` (as `chunk_o.py`), also h0/ht |
| `solve_tril` merge kernels (`solve_tril.py`) | H=64: a sequence with rows past 524,288, or one starting at >= 524,288 | int64 base offset and row index (16/32/64 kernels) |
| `layer_norm_fwd_kernel` for `RMSNormGated` (`layernorm_guard.py`) | H=64: 262,145 tokens (`num_tokens * H * 128 >= 2^31`), when the `rms_norm_gated` custom op is enabled, e.g. `--enforce-eager` | int64 first row of each block |

For the last three, thresholds double at H=32. The rest of the path (`causal_conv1d`, `layernorm_gated`, `gather_initial_states`, `scatter_states`, Mamba2 `ssd_checkpoint`, FlashInfer GDN prefill) already uses int64 offsets. The KDA and Qwen4Exp PLE exporters share the fixed checkpoint kernel.

Related: #43166 (closed) fixed the same overflow in the CUDA `fused_qk_norm_rope` kernel; #51406 (open) enables the first kernel on ROCm, so ROCm gets the bug and this fix.

## Claims

- On main, `vllm serve Qwen/Qwen3.5-9B --max-num-batched-tokens 209717` (or 263,168) fails in the startup profile run with an illegal memory access in `_fused_qk_rmsnorm_rope_gate_kernel`. With this PR it starts and serves correctly.
- With prefix caching, one prefill step can fill the budget. At 263,168, a 258,798-token prompt and a 262,784-token two-prompt batch serve correctly; without the checkpoint and post-conv commits they crash in those kernels.
- Each kernel matches its previous output below its threshold and the reference above it.
- Perf: about +1% on the gate kernel (141.2 vs 139.7 us at 8,192 tokens), +2.2% on post-conv, 0.2 us on the checkpoint export, and 0 to 3% on the follow-ups (`chunk_delta_h` 0% / -3.0%, `solve_tril` +1.1%, `rmsnorm_gated` +2.4 to +3.1%).

## Validation

1x B200, torch 2.14.0+cu132, Triton 3.8.0, FlashInfer 0.7.2.post1, main `ffcabb8c7a`, `Qwen/Qwen3.5-9B` at `c202236235`. "Base" is main plus only the new tests.

```bash
pytest -v tests/kernels/test_fused_qk_norm_rope_gate.py -k int64_row_offset
pytest -v tests/kernels/mamba/test_checkpoint_exporter.py -k int64_token_offset
pytest -v tests/kernels/fla/test_fused_gdn_post_conv.py -k int64_token_offset
pytest -v tests/kernels/fla/test_chunk_int64_offsets.py
pytest -v tests/kernels/fla/test_fla_layernorm_guard.py -k int64_row_offset
```

- Every new test fails on base (77.1% / 93.4% of q mismatched for the gate and post-conv kernels, illegal memory access for the other four) and passes with this PR. Existing tests in these files, `tests/kernels/fla`, `test_gdn_prefill_flashinfer.py` and `test_gdn_output_projection.py` pass.
- Server (`--max-num-batched-tokens` 209,717 and 263,168, prefix caching on, compiled and eager): base fails in the profile run; this PR finds needles near the start and end of a 196,883 / 258,798-token prompt, answers both prompts of the 262,784-token batch, scores gsm 8/8, and matches base outputs at the default budget of 16,384.
- Latency: kernels timed side by side with `triton.testing.do_bench_cudagraph` (follow-ups with `do_bench`), median of alternating rounds; a base-vs-base control gave 1.000 and outputs are bitwise equal to base.

## Details

- Tests run each kernel just past its boundary on a realistic layout (packed qkv/qkvz buffers, contiguous conv output) and compare those rows with a reference. They need about 4 to 21 GB, skip when free device memory is short, and take a few seconds each. The gate test's CI step did not list `fused_qk_norm_rope.py` in `source_file_dependencies`, so this PR adds it there and to the AMD mirror; the other tests run in steps that already depend on their kernels.
- Post-conv: an int64 per-token offset vector is a one-line change but costs 4.4% instead of 2.2%, so the PR uses an int64 base pointer. For `rmsnorm_gated` and `solve_tril` both approaches timed the same, so the simpler diff is kept.
- Not fixed here: at these budgets Qwen3.5-9B needs a lower `--gpu-memory-utilization` than 0.92, with or without this PR (FlashInfer autotune and compiled-graph OOMs). The runs above used 0.88 at 209,717 and 0.84 at 263,168.
