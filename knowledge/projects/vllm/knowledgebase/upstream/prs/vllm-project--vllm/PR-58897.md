# [Perf][MoE] Cheaper triton_kernels 3.8 routing build in the OAI Triton MoE

[Upstream PR](https://github.com/vllm-project/vllm/pull/58897) · state: closed · merged: True

## Original PR description

## Purpose

On triton_kernels 3.8, which every ROCm build ships since #50605, the MoE routing metadata is rebuilt in torch with an int64 stable `argsort` and a `scatter_add_` histogram, costing 31–178 µs per MoE layer per step on MI355X / MI325X.

- `make_routing_data` sorts the ids in their own dtype and reads per-expert counts off the sorted keys with `searchsorted` instead of an atomic histogram. This path runs under expert parallelism and in `UnfusedOAITritonExperts`, which DeepSeek-V4 uses whenever AITER's MXFP4 MoE does not apply — on gfx942 that includes `VLLM_ROCM_USE_AITER=1`.
- `routing_data_from_sparse_topk` (gpt-oss without EP) reuses the `col_sum` / `col_sorted_indx` of the `SparseMatrix` that `triton_kernels.topk` already returned, as the 3.6 path does since #45457.

The routing metadata is identical to main's. CUDA is unaffected: it pins triton_kernels v3.5.1, and only the 3.8 branches change.

## Tests

```bash
pytest tests/kernels/moe/test_gpt_oss_triton_kernels.py tests/kernels/moe/test_modular_oai_triton_moe.py
```

44 passed on both main (`74f4404f58`) and the PR, on MI325X. The new `test_make_routing_data_tk38_matches_reference` checks the 3.8 build against a stable sort plus `bincount`, including `-1` slots, and fails if the `-1` clamp is removed while every other test still passes; `test_routing_data_from_sparse_topk_parity` no longer skips on 3.8.
