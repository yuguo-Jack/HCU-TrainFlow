# [Perf][SM90] Score only candidate blocks in the DSv4.1 decode indexer

[Upstream PR](https://github.com/vllm-project/vllm/pull/62463) · state: open · merged: False

## Original PR description

> **Updated 2026-10-22:** I reran performance tests after the kernel changes and
> added accuracy results. The measurements below are from `8ed990e14a` and replace
> the earlier results. The subsequent commit, `c05a4b9558`, only changes a docstring
> and test formatting. The implementation still reads candidate K in place;
> there is no intermediate candidate-K buffer.

## Overview

Add a Triton candidate-only decode scoring path for DeepSeek V4.1 on SM90,
reading FP8 K directly from the paged indexer cache instead of scoring the
full context and masking it afterwards.

Related to #61830. This is a separate implementation from the gather-based
prototype in draft #62000: it avoids the intermediate candidate-K buffer.
The flag is off by default (`VLLM_DSA_CANDIDATE_PAGED_DECODE=1` to enable).

## Changes

- `vllm/model_executor/kernels/attention/dsa/candidate_paged_logits.py` (new):
  Triton kernels for candidate-only paged decode scoring: per-row candidate
  expansion and causal bounds, in-place FP8 K reads through the page table,
  a compact FP32 logits buffer `[rows, 16384]`, top-k remap to request-local
  positions, and persistent workspaces for CUDA graph capture/replay.
- `vllm/model_executor/layers/sparse_attn_indexer.py`: dispatches the four
  candidate-consuming indexers to the new path on SM90 with an FP8 indexer
  cache; keeps the dense score-then-mask fallback for unsupported shapes and
  platforms; logs the active path once.
- `vllm/v1/attention/backends/mla/indexer.py`: adds per-step candidate-plan
  scratch to the decode metadata. The first consumer expands the plan and the
  remaining consumers reuse it; the buffers are allocated by the metadata
  builder so they outlive CUDA graph capture.
- `vllm/envs.py`: adds `VLLM_DSA_CANDIDATE_PAGED_DECODE`, default `False`.
- `tests/kernels/attention/test_candidate_paged_logits.py` (new): FP32
  reference, selected-set comparisons, cache layout, bounds, CUDA-graph
  replay, gating/workspace reuse, and a performance smoke test.
- Not changed: the candidate-source and pre-candidate indexers, prefill,
  SM100's native sparse path, other platforms, and the dense fallback. The
  candidate path is opt-in and config-gated (SM90, FP8 indexer cache, no
  DCP/PCP, supported power-of-two geometry); it has no batch-size or
  context-length profitability gate.

## Claims

- On H20 TP8 with ~1M input, mean ITL fell **6.5% at concurrency 1 and
  23.7% at concurrency 8** over three runs per flag. At c8, acceptance was
  82.8% with the flag off and 83.6% with it on.
- The ITL reduction was larger at longer inputs. With 2k–16k inputs and 16k
  generated tokens, c1/c8 mean ITL changed by at most 2.5%; c16 ranged from
  +0.3% to -4.1%.
- Consumer logits use 16,384 candidate columns instead of the full compressed
  context. Source layers, pre-candidate layers and prefill keep their existing
  paths. Dispatch uses configuration checks rather than capture-time lengths.
- MMLU's aggregate score was unchanged; GSM8K was -0.31pp and MATH-500 was
  -0.20pp. HumanEval was **-1.83pp (3 questions)**: the audit below accounts for
  two net additional cap-hit failures and one non-truncated code failure.
  LongBench-v2 medium was +3pp; the long subset had the same scores, with
  28 over-length prompts in each run.

The measurements below use H20 and the listed workloads; other SM90 GPUs
have not been tested. The headline ITL changes are serving-level A/B results,
not isolated kernel speedups.

Notation: TP8 means tensor parallelism across eight GPUs; EP means expert
parallelism. DCP/PCP mean decode/prefill context parallelism. `CONC` is the
client concurrency limit (`--parallel`), and cN means concurrency N. Accuracy
deltas marked pp are percentage-point differences.

### Test guards

```bash
pytest -q tests/kernels/attention/test_candidate_paged_logits.py
```

The tests cover:

- **Scores and selection:** candidate logits against an FP32 reference
  (`rtol=2e-2`, `atol=1e-2`), plus selected-set comparisons for `persistent`
  and `auto` top-k. This is kernel-level coverage, not model accuracy.
- **Cache layout:** page gaps of 0/64/260 bytes with block sizes 16/64;
  invalid cache entry widths are rejected.
- **Bounds:** empty contexts, padded/out-of-range candidate blocks, and
  per-row causal limits during speculative decoding.
- **CUDA graphs:** capture on a short context, replay with changed lengths
  and page tables, then compare against eager execution.
- **Gating and workspace:** default-off behavior, rejected configurations,
  and reuse of the reserved workspace without growth during capture.
- **Performance smoke test:** an effective-bandwidth threshold over the
  candidate path, intended to catch severe regressions, not to measure
  isolated HBM bandwidth.

### Performance A/B (2026-10-22)

I tested 21 input-length/concurrency combinations, with three runs per flag
for each combination: 63 runs per flag, 126 runs in total. The run summaries
report no failed requests. Each run sends `2 * CONC` measured requests after
one warmup request, with at most `CONC` in flight. These are not necessarily
two synchronized batches on the server.

`flag0` means `VLLM_DSA_CANDIDATE_PAGED_DECODE=0`; `flag1` means `=1`.
The client arguments, including `--seed 42`, are the same for both flags and
all repeats. This fixes the random-data seed and the seed sent in requests;
it does not guarantee identical generation or scheduling.

The main latency metric is **ITL (ms)**: client-observed intervals between
streamed messages after the first response, as measured by EvalScope 1.9.1.
Each run pools the intervals from successful requests; the tables average
three run means. TPOT measures post-first-response time per output token.
Both are serving metrics, affected by acceptance, scheduling and buffering,
not direct GPU iteration timings.

#### Benchmark command and parameters

Set `MODEL` to the served model name and `TOKENIZER_PATH` to its matching
checkpoint. Use a separate `OUT` directory for each flag, shape and repeat.
`PREFIX`, `MAX_TOKENS` and `CONC` come from the table below; the command is
otherwise unchanged.

```bash
evalscope perf \
  --model "$MODEL" --api openai --stream --api-key EMPTY \
  --url http://127.0.0.1:8021/v1/chat/completions \
  --dataset random --tokenizer-path "$TOKENIZER_PATH" \
  --prefix-length "$PREFIX" --min-prompt-length 1024 --max-prompt-length 1024 \
  --number "$((CONC * 2))" --parallel "$CONC" --warmup-num 1 \
  --max-tokens "$MAX_TOKENS" --temperature 0.7 --top-p 0.95 --seed 42 \
  --extra-args '{"chat_template_kwargs": {"enable_thinking": false}, "ignore_eos": true}' \
  --outputs-dir "$OUT"
```

### Accuracy

`temperature=0.0`. Short datasets use the full evaluation sets and an

  --eval-batch-size 16 --ignore-errors --work-dir "$OUT/short" --no-timestamp \

## Details

The path prepares per-row candidate blocks and causal bounds, reads candidate
K directly through the page table, scores into a compact buffer, runs the
existing top-k, and remaps the selected columns to request-local positions.
It reuses candidate preparation and remapping from vLLM's SM100 sparse path.
FP8 dot products use FP32 accumulation; invalid columns are masked and valid
column counts are passed to top-k.

This revision skips K loads and MMA for tiles wholly past a row's valid
candidate count, writing `-inf` before returning. The grid stays fixed for
CUDA graphs. It also reuses preparation through the decode metadata: the
first consumer prepares the plan, and later consumers sharing that metadata
reuse it. Each layer still computes its own scores and top-k. The shared-plan
unit test compares the selected set against a freshly prepared plan.

For the tested model, `index_head_dim=128`, `index_n_heads=32`,
`candidate_topk_blocks=2048`, `candidate_block_size=8`, and `index_topk=512`.
The compact FP32 logits buffer is `[rows, 16384]` (1.5 MiB at 24 rows).
With five speculative tokens, six decode rows represent one fully populated
request in the kernel input; this is not necessarily the client's concurrent
request count because scheduling and graph padding can change the batch.

The path requires SM90, an FP8 indexer cache, no DCP/PCP, and supported
candidate geometry. When disabled or rejected by the availability check, the
existing dispatch remains in use; existing unsupported combinations may still
raise errors. The gate has no batch-size or context-length profitability
threshold. Avoiding a K copy does not remove preparation, sorting, top-k or
remapping costs. The short-input tests above cover one workload; they do not
guarantee no regression for short outputs or every batch shape.
