# [Perf][SM90] Score only candidate blocks in the DSv4.1 decode indexer

[Upstream PR](https://github.com/vllm-project/vllm/pull/62463) · state: open · merged: False

## Original PR description





## Overview

Add a Triton candidate-only decode scoring path for DeepSeek V4.1 on SM90,
reading FP8 K directly from the paged indexer cache instead of scoring the
full context and masking it afterwards.

Related to #61830. This is a separate implementation from the gather-based
prototype in draft #62000: it avoids the intermediate candidate-K buffer.
The flag is off by default (`VLLM_DSA_CANDIDATE_PAGED_DECODE=1` to enable).

## Claims

- On H20 TP8 with ~1M input tokens, the evalscope A/B below measured a
  **9.6–23.8% reduction in mean ITL** across concurrency 1/2/4/8.
- Consumer logits use 16,384 candidate columns instead of the full compressed
  context. The candidate-source layers, pre-candidate layers and prefill path
  are unchanged.
- Path selection uses configuration checks, not capture-time context lengths.
  Live lengths and page tables remain device inputs during CUDA graph replay.

These results cover the measured long-context workload, not a general
no-regression claim. Accuracy and shorter-workload checks are still pending.

## Validation

### Environment

- Machine: 8x NVIDIA H20 96GB, TP8; driver 535.161.08, CUDA 13.0
- Software: torch 2.14.0+cu130, triton 3.8.0, deep_gemm 2.8.1, vLLM at this
  PR's commit
- Server: `--tensor-parallel-size 8 --max-model-len 1048576 --max-num-seqs 16
  --enable-prefix-caching`, speculative decoding with
  `num_speculative_tokens=5`. The A/B runs differ only in
  `VLLM_DSA_CANDIDATE_PAGED_DECODE` (0 vs 1)

### Test guards

```bash
pytest -q tests/kernels/attention/test_candidate_paged_logits.py
```

The tests cover:

- **Scores and selection:** candidate logits against an FP32 reference
  (`rtol=2e-2`, `atol=1e-2`), plus selected-set comparisons for `persistent`
  and `auto` top-k. This is kernel-level coverage, not model accuracy.
- **Cache layout:** page gaps of 0/64/260 bytes with block sizes 16/64;
  invalid cache entry widths are rejected.
- **Bounds:** empty contexts, padded/out-of-range candidate blocks, and
  per-row causal limits during speculative decoding.
- **CUDA graphs:** capture on a short context, replay with changed lengths
  and page tables, then compare against eager execution.
- **Gating and workspace:** default-off behavior, rejected configurations,
  and reuse of the reserved workspace without growth during capture.
- **Performance smoke test:** an effective-bandwidth threshold over the
  candidate path, intended to catch severe regressions, not to measure
  isolated HBM bandwidth.

The current L4 attention CI job skips the SM90 GPU cases. A saved H20 pytest
report for the submitted revision is still needed; the coverage above does
not imply those cases passed in CI.

### End-to-end A/B (1M context)

I ran both configurations on the same commit with the same client arguments.
There is one run per configuration, with 2/4/8/16 measured requests at
concurrency 1/2/4/8 respectively. Set `MODEL` to the served model name and
`TOKENIZER_PATH` to the matching local checkpoint:

```bash
evalscope perf \
  --model "$MODEL" --api openai --stream --api-key EMPTY \
  --url http://127.0.0.1:8021/v1/chat/completions \
  --dataset random --tokenizer-path "$TOKENIZER_PATH" \
  --prefix-length 1028976 --min-prompt-length 1024 --max-prompt-length 1024 \
  --number 2 4 8 16 --parallel 1 2 4 8 --warmup-num 1 \
  --max-tokens 16384 --temperature 0.7 --top-p 0.95 --seed 42 \
  --extra-args '{"chat_template_kwargs": {"enable_thinking": false}, "ignore_eos": true}'
```

The logs report 1,029,974 input tokens and 16,384 output tokens per request.
The configured prefix length is 1,028,976; input counts above are the measured
counts after prompt construction, not a sum of the CLI length arguments.
The tables report zero cached prompt tokens, but that alone does not verify
server-side prefix-cache hits, especially with this shared-prefix workload.

I use ITL as the main latency metric here, with TPOT and throughput as
supporting results. Under speculative decoding, streamed chunks can contain
multiple tokens: client ITL is not necessarily one GPU iteration, nor is it
independent of acceptance, scheduling or buffering. TPOT remains a valid
user-facing metric, but neither metric alone isolates the kernel change.

This is one A/B pair, not a confidence-interval result. Many intervals within
the same requests do not replace independent runs. At concurrency 4, overall
completion throughput was 827.33 -> 814.72 tok/s (-1.5%) despite lower ITL,
so this is not a throughput win at every concurrency.

I also ran an earlier TP4 test at 200K context. It showed a much smaller ITL
change; the TP8 evalscope run and trace below are the main evidence here.

### Kernel-level trace

The measurement record uses **PyTorch Profiler**, with 100 decode iterations
at ~1M context and client concurrency 12. On rank 0:

| Observation | Dense | Candidate-only |
| --- | ---: | ---: |
| Mean decode rows/step | 55.2 | 44.3 |
| Scoring time/call | 2027.0 us | 56.4 us |
| Candidate expansion + remap/call | — | 8.2 + 1.8 us |
| Candidate mask + flags, total | 68.10 ms | absent |
| Cooperative top-k time/call | 221.1 us | 94.2 us |

The dense scoring bucket groups the candidate source and four consumers;
the new scoring kernel runs only for the four consumers. All eight ranks
show the new kernel and no consumer mask kernel (400 scoring calls per rank).
This confirms that serving actually exercises the new path.

The batches differ, so these are attribution measurements, not a matched-load
speedup. Even dividing by row count does not fully remove differences in
occupancy and batch composition. End-to-end latency comes from evalscope,
not the profiler's summed CUDA time.

## Details

The path prepares per-row candidate blocks and causal bounds, reads candidate
K directly through the page table, scores into a compact buffer, runs the
existing top-k, and remaps the selected columns to request-local positions.
It reuses candidate preparation and remapping from vLLM's SM100 sparse path.
FP8 dot products use FP32 accumulation; invalid columns are masked and valid
column counts are passed to top-k.

For the tested model, `index_head_dim=128`, `index_n_heads=32`,
`candidate_topk_blocks=2048`, `candidate_block_size=8`, and `index_topk=512`.
The compact FP32 logits buffer is `[rows, 16384]` (1.5 MiB at 24 rows).
With five speculative tokens, six decode rows represent one fully populated
request in the kernel input; this is not necessarily the client's concurrent
request count because scheduling and graph padding can change the batch.

The path requires SM90, an FP8 indexer cache, no DCP/PCP, and supported
candidate geometry. When disabled or rejected by the availability check, the
existing dispatch remains in use; existing unsupported combinations may still
raise errors. The gate has no batch-size or context-length profitability
threshold. Avoiding a K copy does not remove preparation, sorting, top-k and
remapping costs, so short-context performance still needs checking.

## What's next

- **Accuracy:** compare lm-eval results with the flag off and on.
- **Performance outside 1M:** benchmark shorter contexts, small batches and
  smaller real datasets to check for latency or throughput regressions.
- **Kernel work:** try a CUDA/CUTLASS implementation and compare it with
  Triton. I'll profile scoring, candidate preparation and top-k before
  deciding which part to optimize; there is no measured speedup for this yet.

I'd appreciate feedback on the implementation while I finish the accuracy and
short-workload checks. Those results still need to be confirmed before merge.
Prefill optimization is outside this PR.
