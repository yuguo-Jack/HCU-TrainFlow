# [Bugfix][Frontend] Aggregate per-engine ORCA metrics under data parallel

[Upstream PR](https://github.com/vllm-project/vllm/pull/63445) · state: open · merged: False

## Original PR description

## User impact
With data parallel enabled, the `endpoint-load-metrics` ORCA header reports only one engine's load to the gateway: the JSON `named_metrics` dict kept a single value per metric name, so every engine but the last was silently dropped. Gateways doing load-based routing see a skewed picture (e.g. one engine at 95% KV cache and 40 queued, another at 5% and idle, with only the idle engine's numbers reported).

## Technical cause
`get_named_metrics_from_prometheus()` appends one `(name, value)` tuple per Prometheus sample, i.e. one sample per engine per mapped metric. `create_orca_header()` then built the JSON `named_metrics` dict with a dict comprehension, collapsing duplicate keys and keeping only the last engine's value.

## Fix
Aggregate duplicates before emitting, in both TEXT and JSON formats:
- utilization-style metrics (names ending in `_perc`) are averaged across engines
- everything else (e.g. `num_requests_waiting`) is summed

Two drive-by fixes in the same function, verified from code reading:
- the unsupported-format warning passed the builtin `format` instead of `metrics_format` (line 36), so the log message always printed "<built-in function format>"
- `logger.info("Created ORCA header ...")` fired on every response; demoted to debug

No behavioral change for the single-engine case (one sample per name aggregates to itself).

Closes #61898
