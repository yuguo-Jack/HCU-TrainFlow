# [model] Support MiniCPM-OCR 1.0

[Upstream PR](https://github.com/vllm-project/vllm/pull/63095) · state: closed · merged: True

## Original PR description

## Overview

MiniCPM-OCR 1.0 is the MiniCPM-V 4.6 stack with a different `model_type`, so
this adds `MiniCPMOcrForConditionalGeneration` as a subclass of
`MiniCPMV4_6ForConditionalGeneration` and registers it in the model registry and
the chat-template fallback.

One difference: the image placeholder is counted from the `target_sizes` the
image processor returns instead of being recomputed from the image size, because
the small-image upsize tier is decided from the pixels. This also covers
`adaptive_tile_upsize`, where tiles in one grid no longer share a geometry.

## Additional information

Requires a transformers build that ships `minicpm_ocr` (`MiniCPMOcrConfig`,
`MiniCPMOcrImageProcessor`, `MiniCPMOcrProcessor`).

`chat_template_kwargs={"enable_thinking": false}` is needed for plain
transcription, otherwise the template emits `<think>`.

File: `vllm/model_executor/models/minicpm_ocr.py` · line None

🔴 If slices in one grid differ in size (the PR claims `adaptive_tile_upsize` does this), the image placeholder token count is wrong and the request fails. The builder reads `tgt_sizes` row 1 only and repeats that count for every slice. The comment says slices share one geometry, which the PR description contradicts. Fix: sum `tgt_sizes[i].prod() // token_divisor` per slice row and emit each `<slice>` with its own count, so every per-tile geometry is covered.

<details>
<summary>Why this was flagged</summary>

Trigger: a request passes `adaptive_tile_upsize` (or any option that resizes tiles one by one) as a flat `mm_processor_kwargs` key. `_flat_processor_kwargs` (minicpmv4_6.py:164-180) keeps flat keys, so the option reaches the image processor in `process_images`. The PR description says tiles in one grid then no longer share a geometry, so the `target_sizes` rows 1..N differ. `_ocr_image_prompt_text` at minicpm_ocr.py:299-305 takes only `patch_tokens_per_slice[1]` and repeats it `num_rows * num_cols` times. The placeholder token count then no longer matches the vision embeddings built from the real per-slice `tgt_sizes`, so vLLM rejects or aborts the request. The PR claims this case is handled. The `num_rows * num_cols + 1 != tgt_sizes.shape[0]` guard only checks the row count, not that the per-row sizes are equal, so it does not fall back. No test uses unequal slice rows; test_minicpm_ocr.py:307 uses identical `[8, 8]` slices.

**Verification:** In `_ocr_image_prompt_text` (vllm/model_executor/models/minicpm_ocr.py, about lines 299-305), the code uses only one row: `slice_tokens = int(patch_tokens_per_slice[1])` followed by `rows = [slice_ph * num_cols for _ in range(num_rows)]`. If rows 2..N of `tgt_sizes` differ from row 1, the placeholder token count stops matching the number of embeddings the vision tower produces.

</details>

- claude[bot] · comment · 2026-10-22T10:41:37Z · [source](https://github.com/vllm-project/vllm/pull/63095#discussion_r4347342280)

File: `vllm/model_executor/models/minicpm_ocr.py` · line 243

🔴 Video requests can get a placeholder count that differs from the frame embeddings when the image processor is set to skip or adapt small-image upsizing. This happens with small, unsliced frames. `_drop_image_upsize_kwargs` only strips per-request flat keys. The shared image processor still applies its own `disable_small_image_upsize` / `adaptive_small_image_upsize` defaults to each frame. Fix: in `process_videos`, pass explicit values that turn off every upsize option, so frames always upscale the way `_compute_visual_tokens` counts them. Alternatively, count video placeholders from `video_tgt_sizes`.

<details>
<summary>Why this was flagged</summary>

Trigger condition (cannot be checked from this checkout): the `MiniCPMOcrImageProcessor` instance has a non-default upsize setting. The checkpoint's preprocessor_config.json could set these defaults. `process_videos` (minicpm_ocr.py:222-230) only removes flat request keys. The 4.6 `process_videos` (minicpmv4_6.py:441) then calls that same instance per frame with no upsize kwargs, so the instance defaults apply. A small frame such as 480x360 (unsliced) stays at native size, or gets an adaptive target. Its `video_tgt_sizes` rows end up smaller than or different from what `get_video_prompt_texts` counts through `_compute_visual_tokens`, whose unsliced branch uses `allow_upscale=True` (minicpm_ocr.py:136-141). The placeholder and embedding counts disagree, which the 4.6 code itself notes makes the engine abort (minicpmv4_6.py:232-234). Images are not affected because they are counted from `tgt_sizes`. Base has no OCR model, so this is new.

**Verification:** Triggering condition: the loaded `MiniCPMOcrImageProcessor` instance has a non-default `disable_small_image_upsize` or `adaptive_small_image_upsize` value, and a video has small frames that are not sliced. `_drop_image_upsize_kwargs` removes the flat per-request keys and nothing else. The 4.6 `process_videos` (minicpmv4_6.py:402-407) then runs the shared image processor on each frame.

</details>
