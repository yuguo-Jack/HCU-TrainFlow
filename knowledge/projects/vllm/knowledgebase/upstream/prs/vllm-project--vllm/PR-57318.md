# [Kernel][GDN] Use flashinfer bf16 mm for the GDN gate projection

[Upstream PR](https://github.com/vllm-project/vllm/pull/57318) · state: open · merged: False

## Original PR description

## Purpose

The Gated DeltaNet gate projection (`in_proj_ba`) costs 112 ms of a 1494 ms decode (7.5%) on an RTX 5090 at batch size 1 with MTP speculative decoding — to produce 96 numbers per token. cuBLAS selects a degenerate kernel for its shape. Routing it to FlashInfer's `mm_bf16` drops it to 14 ms, cutting decode by 6.5%.

## Root cause

`in_proj_ba` is `[tokens, 5120] x [5120, 96]` in bf16. It stays unquantized on NVFP4/FP8 checkpoints because it matches neither quant group. At 2–4 tokens cuBLAS picks `cutlass_80_wmma_tensorop_bf16_s161616gemm_bf16_16x16_128x2_tn_align8`:

- 16x16 tiling over N=96 gives 6 tiles (grid rounded to 8 by `GemmIdentityThreadblockSwizzle<8>`), and M=4 gives one tile-row
- 8 CTAs of one warp each, on 170 SMs, each walking all of K=5120 serially
- 35.8 GB/s achieved against 1790 GB/s available — latency bound, not bandwidth bound

This is a heuristic gap, not a general small-M problem. cuBLAS is fine at 1 token (GEMV path) and at 8+ (tiled with split-K). Batch size 1 with 3 speculative tokens lands exactly in between. Confirmed with `CUBLASLT_LOG_LEVEL=5`, which shows `numSplitsK=16` chosen at 24 tokens but a plain tiled kernel at 4.

## Where the win exists

Three conclusions:

- **Every shape wins at 2 and 4 tokens on sm_120 and sm_121** (1.48x-6.16x). Smaller K narrows the win but never reverses it.
- **All but one shape *loses* at 1 token**, by up to 2.1x. cuBLAS has a dedicated GEMV path there that FlashInfer does not beat. The routing is therefore bounded below as well as above (`_BA_PROJ_MIN_TOKENS = 2`) — without that, plain non-speculative decode would regress on five of six models.
- **Neither sm_100 nor sm_103 shows a gap** (0.90–1.13 across both). cuBLAS already selects a good kernel on datacentre Blackwell, so there is nothing to win and a little to lose. The routing is gated to the sm_12x family; **B200 and B300 are unaffected**, verified on both rather than inferred.

`2 * num_v_heads` is 96 or less for every model above, so `_BA_PROJ_MAX_N = 96` is a guard against a future wider model rather than a tuning knob, and no shipped model is near it.

## End to end

`nvidia/Qwen3.8-27B-NVFP4`, RTX 5090, bs=1, `num_speculative_tokens=3`, 86 decode steps:

| | before | after |
|---|---|---|
| `in_proj_ba` per call | 27.2 us | 3.40 us |
| `in_proj_ba` total | 112.4 ms | 14.0 ms |
| decode | 1494.3 ms | 1397.7 ms (−6.5%) |

After the change the layer runs as `cudnn_generated_..._matMul` (2.74 us) + `splitk_reduce_contiguous_kernel` (0.66 us) — FlashInfer doing the split-K decomposition cuBLAS declines to. On GB10 the same projection goes 34.0 us -> 6.2 us per call.

## Changes

Dispatches `in_proj_ba` to `flashinfer_bf16_mm` when the token count and shape qualify, falling back to the layer otherwise. **Off by default**, gated by `VLLM_GDN_BA_GEMV_MAX_TOKENS` (default 0); 4 is the measured crossover, clamped to 32 (FlashInfer's `mm_bf16` limit). Routing additionally requires the sm_12x family, 2+ tokens and `N <= 96`, all hardcoded from the sweep above — no user override.

The size check lives in a registered custom op rather than a plain Python branch: the model is compiled via `TorchCompileWithNoGuardsWrapper`, so a shape comparison in the traced region is frozen at whatever shape the single tracing pass saw (prefill), permanently selecting one side.

Routing away from the layer skips whatever the layer would have applied, so the gate declines whenever the layer might be doing more than a plain bf16 matmul:

- a quantized `quant_method`, or a bias
- **LoRA** — adapters wrap the module *after* construction, and the fast path would compute only the base projection
- **batch-invariant mode** — it has its own unquantized kernel and a bitwise contract that routing only below a token threshold would break
- backend support is resolved through `is_flashinfer_bf16_gemm_supported`, which also keeps ROCm out (`forward_hip` can fall back to `forward_cuda`)

The concrete backend is named rather than left to `"auto"`, so this layer does not silently diverge from the configured linear backend.

The per-call shape guard reuses `bf16_mm_shape_supported` rather than restating it. Extracting that from `_can_use_flashinfer_cutedsl_bf16` leaves the cute-dsl entry behaviourally identical (it keeps its sm_10x gate) and avoids a second copy drifting — in particular the shared guard enforces FlashInfer's `1 <= m <= 32` bound.

## Why this is not a duplicate

Two open PRs touch this layer; I checked both against their branches rather than their descriptions.

**#53645 (FlashInfer fused decode for Qwen GDN)** does fold the b/a GEMV in, but only on plain non-spec decode. Its own docstring: *"Everything else — prefill, spec/MTP decode, the gated RMSNorm, the output projection — stays with vLLM."* The regime measured here is MTP spec decode at M=2–4, which that PR explicitly leaves on `self.in_proj_ba(...)`. The two compose rather than collide: this change lands in the `if not use_fi_fused_decode:` branch that PR introduces. It is additionally gated on `VLLM_GDN_DECODE_KERNEL=cuda` and on FlashInfer exposing `gdn_fused_decode_step`.

**#55260 (concat tiny GEMMs, C6)** folds `in_proj_ba` into the `in_proj_qkvz` GEMM, but two independent gates exclude this configuration:

```python
if not (current_platform.is_cuda() and self.gqa_interleaved_layout):
    return                          # Qwen3-Next layout only
if qkvz_w.dtype not in (torch.bfloat16, torch.float16, torch.float32):
    return                          # quantized qkvz (NVFP4) skipped
```

Note those two PRs require *opposite* layouts — #53645 needs non-interleaved, #55260 needs interleaved. This change is layout-agnostic and works with a quantized `qkvz`.

## Risk

- Opt-in; default behaviour is unchanged.
- Numerics shift slightly — FlashInfer accumulates split-K partials in a different order than cuBLAS. α and β feed a sigmoid, so the effect should be small.
- Benefit is batch-size dependent: at 8+ tokens the gate declines and cuBLAS is used. This helps low-batch latency and does nothing under serving load.
- The win is SM-count dependent; measured on sm_120 (RTX 5090) and sm_121 (GB10).

## Test plan

`tests/kernels/mamba/test_gdn_ba_proj_dispatch.py` has one case per guard. Routing bypasses `in_proj_ba`, so the tests assert that everything the layer might otherwise apply declines it — a quantized projection (parametrized over the flag both set and unset, since such a layer registers `qweight` and has no `weight` at all), LoRA, `VLLM_BATCH_INVARIANT`, a bias, a non-2D weight, and FlashInfer present without a bf16 backend for the device. Plus the three measured bounds: sm_12x only, 2+ tokens, and `N <= 96`.

Two of them matter most:

- `test_routed_path_matches_linear` — the routed call must equal the layer it bypasses, parametrized over all five model shapes at 2 and 4 tokens. `mm_bf16` takes `b` pre-transposed, so a layout mistake would otherwise pass every eligibility test and silently corrupt output.
- `test_op_dispatches_on_token_count` — exercises the op itself with a stubbed forward context, checking 2 and 4 route while 8 defers to the layer.
