# [Perf][DSv4.1] MegaAttn: wo_a writes wo_b's MXFP8 input

[Upstream PR](https://github.com/vllm-project/vllm/pull/60118) · state: closed · merged: True

## Original PR description

## Overview

MegaAttn's (`FLASHMLA_MEGA_ATTN_DSV41`) `wo_a` einsum now writes `z` directly as MXFP8, together with the F8_128x4 UE8M0 scales that `wo_b`'s FlashInfer MXFP8 GEMM reads. `wo_b` therefore no longer quantizes a BF16 `z`, at any token count. It uses vllm-project/DeepGEMM#40 (merged), which adds the 128x4 scale layout to DeepGEMM's FP8 einsum epilogue. This PR bumps the DeepGEMM pin to it.

## Claims

- `_o_proj` drops the standalone `mxfp8_quantize` kernel. On GB200 it is 0.4-2.0 us per layer faster in decode (1-256 tokens) and 2.8-141 us faster in prefill (512-32768 tokens). The one regression is +0.6 us at 384 tokens (see Details).
- `wo_b` receives byte-identical FP8 data and scales, so model outputs do not change.
- Only `flash_mla_mega_attn.py` changes (+33/-5 lines vs main). Shared o_proj code and other backends are untouched.

## Validation

`_o_proj` alone (`wo_a` einsum, then `wo_b` CuTe-DSL MXFP8 GEMM) at DeepSeek-V4.1-Flash TP1 shapes: 8 groups x 4096 -> 1024, `wo_b` 8192 -> 5120. Setup: 1 x GB200, CUPTI, full CUDA graph, cold L2, median of 3 rounds, both arms in one process. Software: torch 2.13.0+cu132, FlashInfer 0.7.0.post1, DeepGEMM a7a9277 + DeepGEMM#40. Outputs are bitwise identical at all 20 sizes measured.

## Details

- **Why the gate is gone.** DeepGEMM's einsum could only write MN-major packed scales, so `wo_b` needed a separate swizzle kernel. Below about 1024 tokens, that launch cost about as much as the quantization it saved. vllm-project/DeepGEMM#40 changes only the scale address in the einsum epilogue, so no extra kernel is left.
- **Gate conditions (unchanged).** The path runs when the einsum uses the per-32 recipe, `o_lora_rank % 128 == 0`, and `wo_b` is an MXFP8 kernel that accepts F8_128x4 scales (`can_fuse_query_quant`). It also requires no GEMM-RS, because the fused GEMM + reduce-scatter takes a BF16 `z` only.
- **Padded scale rows.** Rows past the last token in the final 128-row tile are not written. They only feed `wo_b` output rows that are never stored, so the test compares valid rows only.
- **384 tokens.** At 128-384 tokens (and at 2048 tokens), DeepGEMM's FP8-output einsum is slower than its BF16-output einsum, for example 17.9 -> 22.3 us at 384. The old MN-major scales show the same slowdown, so it is independent of this change. It is a DeepGEMM kernel-selection issue that can be fixed there.
- **DeepGEMM pin.** The pin points at `727f847`, the merge commit of DeepGEMM#40 on the fork's `dev` branch. The einsum selects the 128x4 scales with `use_128x4_sfd_layout=True`, which an older externally installed `deep_gemm` (vLLM prefers site-packages) does not accept.
- Merged `main` to resolve conflicts.
