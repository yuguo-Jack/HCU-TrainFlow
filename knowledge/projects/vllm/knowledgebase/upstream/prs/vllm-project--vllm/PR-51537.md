# [Perf] Rotate q/k as a packed zero-copy view in Qwen-VL vision attention

[Upstream PR](https://github.com/vllm-project/vllm/pull/51537) · state: open · merged: False

## Original PR description

## Purpose

`Qwen2_5_VisionAttention` materialized a contiguous copy of q+k before applying rotary embeddings: `rearrange` to `(two*b, s, head, head_dim)` followed by `.contiguous()`, then an out-of-place rotation into a second buffer. The q and k heads are already adjacent in the fused qkv projection output, so flattening `(two, head)` is a zero-copy stride merge (verified: same `data_ptr`, 0 MiB allocated) — and the flash-attn Triton rotary kernel takes strided inputs natively; feeding it the strided view instead of a contiguous buffer costs +0.13% on average (measured below).

Layout note: this moves the rope path's q/k from contiguous to strided; last-dimension stride remains 1. The FlashInfer/cuDNN wrapper explicitly materializes contiguous q/k, so performance on that backend has not been established by these measurements.

The mm encoder runs eager by default (`compile_mm_encoder=False`), so the copy is real per-layer work Inductor never sees. The attention class is shared by the Qwen2.5-VL, Qwen3-VL, Qwen3-VL-MoE and Qwen3-Omni vision towers.

## Warmup follow-up (2026-11-02)

Updated to main `0e5b2ba11` and addressed the warmup feedback in `6d18a371`. Vision warmup now constructs sequence-major QKV and takes the same packed, strided `(1, S, 2H, D)` Q/K view as runtime. The existing vision test uses a real small Qwen3 vision transformer to check shape and stride equality, full-tower exclusion, and CPU-offload skipping. The cuDNN wrapper's outdated contiguity comment is removed.

Validation on Colab Tesla T4 (SM75), FP16, Python 3.12.3, PyTorch 2.14.0+cu132, Triton 3.8.0, Transformers 5.22.0. Source is based on `0e5b2ba11`; precompiled binary extensions are from published nightly `76c6f3f2a`. The published commit's tree is identical to the tested tree.

- Actual rotary kernel: **20 FP16 cases bitwise equal** to the original implementation, covering batch 1/2, head dimensions 72/80, and sequence lengths 4–4096; QKV unchanged and packed view shares storage.
- Compiler-hook validation: **0 additional rotary compilations after packed warmup** across the tested runtime shapes. Legacy warmup also had 0 on this T4; this is layout synchronization, not a reproduced JIT-latency regression.
- Real-weight `Qwen/Qwen3-VL-2B-Instruct`, one generated 224×224 image, greedy 16-token request: **all prompt/output token IDs identical** between current main and the patch. Torch compilation/CUDA graphs disabled explicitly, JIT warmup enabled; production vision warmup logged before JIT-monitor activation, with no rotary inference-JIT warning.
- Changed-file `pre-commit run --files ...`: **all applicable hooks passed on Colab**, including mypy and CI test tethering.

No new H20/SM120 benchmarks or BF16/ROCm validation were run for this follow-up. The enabled AMD Model Executor CI step selects the test; its NVIDIA counterpart is currently disabled upstream. T4 evidence uses Torch SDPA vision attention and does not establish FlashInfer/cuDNN performance.

Related work: #63094 adds a custom NVIDIA BF16 packing/rotary fusion. This PR reuses the existing rotary operator and backend dispatch, including FP16; it does not introduce a new kernel.

## Results (historical SM120 / H20 measurements)

Layer level at the 8×(896×1344)-image batch shape (S=49152, 16 heads, head_dim=80, bf16, median of 30):

| | RTX PRO 6000 (SM120) | H20 (SM90) |
|---|---|---|
| rearrange + contiguous + rotate (before) | 787.2 µs | 780.4 µs |
| packed-view rotate (after) | 433.4 µs | 280.3 µs |
| speedup | **1.82×** | **2.78×** |

The "before" columns agree within 1%, so both boxes measure the same baseline; H20's rotary kernel is simply faster on the strided view.

H20 full sweep — 28 configs (S 1024–98304 × head_dim {80, 72} × {bf16, fp16}): **28/28 faster, 1.36–2.78×, mean 1.98×**. head_dim=72 is the Qwen3-VL / Qwen3-Omni geometry (1.90–2.06× at large S). Full table in the fold.

Mechanism check (H20): the rotary kernel on the strided view vs the old contiguous input differs by **+0.13% mean** (−15 to +22 µs, inside noise) — the win is entirely the deleted copy, and the per-shape saving tracks the copy cost (S=49152: copy 531 µs, saving 500 µs). Side effect: one q+k-sized transient allocation per layer is gone (240 MiB at this shape; per-layer attention peak 1080 → 840 MiB). Tower-level peak memory is unchanged — it lives in the MLP.

End to end (real weights, greedy, encoder runs every repetition):

| | SM120 | H20 |
|---|---|---|
| before | 810.9 ms | 1266.9 ms |
| after | 795.9 ms | 1233.1 ms |

One caveat worth stating: with `compile_mm_encoder=True` the tower-level win shrinks from 3.1% to 0.9% (H20) — Inductor recovers most of this copy on its own. That flag is off by default upstream, so the eager numbers are what deployments get today.
