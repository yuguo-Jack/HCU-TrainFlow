# [Frontend][Multimodal] Accept features together with content_parts in /generate

[Upstream PR](https://github.com/vllm-project/vllm/pull/57796) · state: open · merged: False

## Original PR description

## Purpose

Multi-turn multimodal RL on `/inference/v1/generate`: by turn N the prompt holds earlier images already expanded (from the previous response's `prompt_token_ids` / `mm_placeholders`) plus a new image with a compact placeholder. Today the request has to pick one of two mutually exclusive inputs, and neither fits:

- `content_parts` only: the processor matches the first placeholder tokens it finds, which sit inside the earlier expanded runs, so the prompt is silently corrupted unless the caller collapses every earlier run first.
- `features` only: the new image has no processed data.

As discussed below with @DarkLight1337 and @hickeyma, this PR lets the two be used together instead of detecting expansion in the processor (the earlier version of this PR):

- `features` carries the earlier items, already expanded, at explicit ranges.
- `content_parts` carries the new media. Only the prompt after the last `features` range is rendered, so the matcher never sees the expanded runs; its placeholders are shifted past that prefix and appended to the `features` items.

A new placeholder placed before the last `features` range is not in the rendered part, so it cannot be matched and the request gets a 400. The only processor change turns that unmatched-item `assert` (a 500) into a `VLLMValidationError`. Requests that use only one of the two fields behave as before.

## Why this is not a duplicate

Searched open PRs for `content_parts features`, `generate multimodal features`, `mm_placeholders generate`. #53169 reprocesses raw images to shrink payloads and does not combine the two inputs. #54548 (keep `is_embed` across the round trip) is orthogonal; until it lands, `features` items lose `is_embed` as they already do today.

Thanks, I missed 53385.

The Renderer has a gap for multi-turn RL:
- `/v1/chat/completions/render` follows the Chat protocol: images go in message content parts, but the input is messages only, with no way to pass token IDs.
- `/v1/completions/render` follows the legacy Completions protocol: `prompt` is text or token IDs, with no content parts, so there is nowhere to put an image.

RL needs both: the tokens sampled in earlier turns must be kept exactly, and later turns can bring new images. That leaves only chat render, so the caller either re-renders the whole conversation (detokenize then retokenize, which is not guaranteed to round-trip) or splices tokens and shifts offsets itself.

Separately, an expanded prompt sent back as-is is still silently expanded a second time (128 -> 255), and with #57781 closed nothing catches it.

Two low-cost options:
1. An explicit flag: when the request says the prompt is already expanded, only locate placeholders and skip expansion. The default path costs one boolean check.
2. A local check: when the matcher hits the first placeholder, look at the next token to see whether it is still a placeholder, without scanning the whole prompt.

what do you think?

I agree that a request level contract is better than having the processor guess. One thing though. `/inference/v1/generate` already takes `token_ids` + `content_parts` and that's where this bug shows up. So adding `prompt_token_ids` + media to chat completions would run into the same problem. What we actually need to decide is whether those ids are compact or expanded.

If they're compact, RL callers still have to collapse the expanded runs back to one placeholder (dedup) themselves, like OpenRLHF/verl/TRL do today. If they forget, the prompt gets corrupted without any error. If they're expanded, we need "find the placeholders, don't expand" and that's what this PR does.

The `features` path on generate already takes expanded ids, so maybe the smaller change is letting `features` (earlier turns) work together with `content_parts` (new media in later turns), instead of keeping them mutually exclusive. Then RL stays on tokens-in and chat completions doesn't need a new field. 

What do people think?

+1 to @hickeyma's proposal: let `features` (earlier turns) and `content_parts` (new media) be used together on `/inference/v1/generate`. Two things the implementation needs to get right:

1. Matching for the new items must skip the ranges declared in `features`. Otherwise a new image binds to the first placeholder token it finds, which can sit inside an earlier image's expanded run, and we are back to silent corruption.
