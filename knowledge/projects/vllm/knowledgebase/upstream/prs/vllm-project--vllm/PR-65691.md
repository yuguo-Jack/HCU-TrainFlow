# [Perf][Spec Decode] Fused logits gather for the DSpark draft head of opted-in models

[Upstream PR](https://github.com/vllm-project/vllm/pull/65691) · state: open · merged: False

## Original PR description



Depends on #65436 (this PR stacks on it; only the last commit is new).

## Overview

#65436 fuses the vocab-parallel logits gather for the target logits of models that opt in with `SupportsFP32LogitsGather` (MiniMax-M3 / M3.1). This PR applies the same fused gather to the DSpark draft head's base logits for those models. They are gathered in the head's dtype, so the logits are unchanged.

The DSpark speculator computes its draft logits outside any forward context, so #65436 left them on main's gather. This PR does not wrap all of `propose()` / `capture()`. It wraps only the `compute_draft_logits` call in the same narrow `set_forward_context(None, ..., logits_gather_dtype=...)` that #65436 uses for the target logits.

## Claims

- **Scope.** This applies only to the DSpark speculator under Model Runner V2, and only when the target model opts in with `SupportsFP32LogitsGather`. Today that means MiniMax-M3 / M3.1 with their DSpark drafter. Every other target, every other speculator, the batch-sharded sequential path (`compute_draft_logits_local`, which does no gather) and draft models that run their own `sample_sequential` keep main's code path.
- **Bitwise-equal draft logits.** The draft logits are gathered in the head's dtype and are bitwise equal to main's, both eagerly and replayed from a CUDA graph.
- **Faster draft step** (measured on #65436's earlier revision, where every vocab-parallel head used the fused gather; the draft head there took the head-dtype gather, the same path as this PR). MiniMax-M3.1 Flash, GB300, TP4, DSpark K=7, DSpark draft CUDA-graph span p50, µs, two runs per arm:

  | concurrency | main | fused draft gather | mean change |
  |---|---|---|---|
  | 1 | 648 / 645 | 642 / 638 | −6 |
  | 8 | 911 / 961 | 944 / 904 | −12 (within run noise) |
  | 16 | 1057 / 1063 | 1039 / 1034 | −24 |
  | 32 | 1349 / 1357 | 1292 / 1292 | −61 |

  At concurrency 32 that is about −60 µs per decode step, on top of #65436's target-side saving (about −192 µs).

## Validation

- `tests/distributed/test_vocab_parallel_logits_gather.py` (TP 2 and 4) gets one more check in the existing worker, `_check_dspark_draft_opt_in`. It calls `DSparkSpeculator._compute_draft_logits` on a real `ParallelLMHead` and a real `LogitsProcessor` with a logit scale, as the Qwen3 / MiniMax DSpark heads have.
  - With a target that does not opt in, the speculator takes main's gather.
  - With a target that opts in, it takes the fused gather. The output is contiguous, while main's sliced gather is not, so the check can tell the two paths apart.
  - In both cases the logits are bf16 and bitwise equal to main's.
  - The same call is also captured in a CUDA graph (under `graph_capture`, as the speculator's FULL draft graph is) and replayed on new hidden states. It replays the gather chosen at capture time and is again bitwise equal to main.
- CI: the test already runs in "Distributed Comm Ops". This PR adds `vllm/v1/worker/gpu/spec_decode/dspark/speculator.py` to that step's `source_file_dependencies`.
- **On a `main` build** (the nightly wheel for a900ac810e on the GB300 image, with this branch's files): `tests/distributed/test_vocab_parallel_logits_gather.py` passed 3/3, and with `tests/v1/worker/test_gpu_sampler_in_place.py` and `tests/v1/worker/test_gpu_logits_processors.py` 12/12. The TP 2 and TP 4 cases both run the new draft check, including CUDA-graph replay. A 12-request M3.1 Flash smoke serve (TP4, DSpark K=7) completed 12/12. A probe showed the opt-in on all 4 ranks and the draft logits going through the fused bf16 gather during DSpark graph capture. Compared with #65436 alone on one node: GSM8K chat (320 questions, c32) greedy 0.9750 vs 0.9719, temperature 1 / top-p 0.95 0.9656 vs 0.9719; accepted / drafted tokens 0.526 vs 0.525 overall, no change beyond sampling noise.
- Re-measured on this branch (nsys, two nodes, two runs per arm, DSpark draft CUDA-graph span p50, µs, #65436 → this PR): c1 695 / 698 → 693 / 692; c8 996 / 1030 → 984 / 1000; c16 1180 / 1185 → 1153 / 1167; c32 1505 / 1507 → 1448 / 1446. That is about −4 / −21 / −22 / −59 µs per decode step. Whole-step periods vary by about ±200 µs between runs, so the gain shows only in the draft span.

## Details

- `vllm/v1/worker/gpu/spec_decode/dspark/speculator.py`: `load_model` records `fused_logits_gather = supports_fp32_logits_gather(target_model)`. `_compute_draft_logits` wraps `self.model.compute_draft_logits` in the narrow forward context when that flag is set. Both dense call sites use it: `_sample_sequential` and the top-k `_sample_sequential_topk`.
- **Head dtype, not FP32.** Gathering the draft logits in FP32 would save no copy. The Markov bias is added in the head's dtype, and `gumbel_sample` upcasts inside its kernel. FP32 would also change the bias addition's rounding, so the draft logits would no longer match main's. Like the target path, the context passes the hidden-state dtype, and `LogitsProcessor` then writes the head's dtype.
- **CUDA graphs.** The draft's `_run_model` exits its own forward context before the Markov sampling. So during warmup, capture and replay, the draft logits run either with no forward context (main's gather) or under this narrow one. Nothing else reads it. Its `attn_metadata` and `num_tokens` are None, so it does no batch-size timing sync and builds no DP metadata. Whether the fused gather is used depends only on the target model, which is fixed for the speculator's lifetime. The capture warmup (`forward_fn(CUDAGraphMode.NONE)`) runs the same call eagerly first, so the Triton layout kernel is compiled before capture.
- **Gate.** The opt-in is the target's. On a target that opts in, the draft's gather keeps the head dtype, and nothing runs on the draft logits in a different dtype. So the draft model does not need the passthrough guarantee that `SupportsFP32LogitsGather` asks of the target. A draft-side opt-in would add a second flag with nothing more to check.
- The Markov bias head (`markov_w2`) is replicated (`disable_tp=True`) and does no gather, so it is not affected.
