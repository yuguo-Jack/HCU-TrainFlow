# [Bugfix][Tool Parser] Parse bare FunctionGemma arguments and stream them as valid JSON

[Upstream PR](https://github.com/vllm-project/vllm/pull/63992) · state: closed · merged: True

## Original PR description

## Overview

Fix the `functiongemma` tool parser dropping every non-string argument, and make its streamed arguments reassemble into valid JSON. Fixes #63983.

## Claims

- Bare booleans, numbers, `null`, arrays and objects are parsed in streaming and non-streaming, nested containers included.
- Streamed deltas of a multi-argument call concatenate to one JSON object.
- A streamed call still gets closed when its end tag shares a delta with the next call's start tag.
- A streamed call with no arguments sends `{}` instead of an empty string.

## Details

The template's `format_argument` macro wraps only strings in `<escape>`, e.g. `enabled:true,hour:7,days:[<escape>mon<escape>],snooze:{minutes:5}`. The old `arg_regex` only matched `key:<escape>...<escape>`, so bare values were dropped. A small recursive parser for that grammar replaces it. With `partial=True` (streaming) it stops at the first incomplete value, so each value is streamed once in its final form. A bare word that is not a JSON literal stays a string.

Streaming diffs are computed by length against `json.dumps(args)`, so the closing brace is held back until the call ends. That left two gaps, both fixed here. When an end tag and the next start tag arrive together, the start branch returned before closing the earlier call, so it never got its brace, or any arguments if they were still unsent. A call with no arguments streamed nothing because the end branch skipped empty arguments. Both paths now go through `_close_tool_call`. Deltas can merge when the client falls behind the engine or `stream_interval` is above 1.

Known limitation: from `stream_interval=10` in these runs, a call's name can share a delta with its end tag, and the name is lost. At 64 the second call is lost too. main behaves the same or worse here, so this is left for a follow-up.

Related PRs:

- #63947 fixes #63906, a separate bug. `<escape>` values keep their current decoding here, so `<escape>123<escape>` is still the integer 123.
- #48705 fixes the brace issue the same way. It is included here because the streaming tests cannot reassemble a multi-argument call without it. Happy to rebase if #48705 lands first.
- #64360 targets the same issue and was opened a day after this PR.

Thanks for working on this. I found one streaming case that breaks the JSON: when `<end_function_call>` and the next `<start_function_call>` come in the same delta, the first call never gets its closing `}`, so the client ends up with `{"city": "Paris"`.
Closing the previous call before starting the next one ([L331-L337](https://github.com/vllm-project/vllm/blob/fa086599ec56f3e88022745824d61b22e9d53af5/vllm/tool_parsers/functiongemma_tool_parser.py#L331-L337)) fixes it for me:

```diff
             if start_count > prev_start_count and start_count > end_count:
+                # The previous call may have ended in this same delta.
+                closing = None
+                if end_count > prev_end_count and self.current_tool_id >= 0:
+                    calls = self.tool_call_regex.findall(current_text)
+                    if self.current_tool_id < len(calls):
+                        match = calls[self.current_tool_id]
+                        if match[0]:
+                            args = self._parse_arguments(match[1])
+                            closing = self._stream_arguments(args, final=True)
                 self.current_tool_id += 1
                 self.current_tool_name_sent = False
                 self.streamed_args_for_tool.append("")
                 self.prev_tool_call_arr.append({})
                 logger.debug("Starting new tool call %d", self.current_tool_id)
-                return None
+                return closing
```

#64360 and #63947 overlap with this. With #63947's schema check in `_parse_arguments`, I think their `<escape>` value tests pass here too.
