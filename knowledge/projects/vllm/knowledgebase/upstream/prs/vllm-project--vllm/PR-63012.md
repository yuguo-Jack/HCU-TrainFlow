# [Bugfix][Attention] Stop advertising head_dim 64 in the b12x backend

[Upstream PR](https://github.com/vllm-project/vllm/pull/63012) · state: closed · merged: True

## Original PR description

## Overview

`--attention-backend b12x` accepts head_dim 64 models at selection and then crashes after model load, at the first forward, inside the b12x paged planner (`no valid NUM_MMA_KV typed shared-memory allocation fits the device`). The b12x package cannot plan head_dim 64 decode at all, so this stops advertising 64 and lets selection fail fast. Fixes #63011.

## Claims

- head_dim 64 models with `--attention-backend b12x` are now rejected at backend selection with `Selected backend AttentionBackendEnum.B12X is not valid for this configuration. Reason: ['head_size not supported']`, before weights load, instead of crashing in CUDA graph capture.
- head_dim 128/192/256 are unchanged.
- One list entry removed, one unit test added. No kernel or runner changes.

## Validation

DGX Spark (GB10, sm_121, aarch64), CUDA 13.0, torch 2.14.0+cu132, flashinfer-python 0.7.2 (provides the `b12x` module), vLLM main @ 35d01660f.

```python
from vllm import LLM
LLM("Qwen/Qwen2.5-0.5B-Instruct", attention_config={"backend": "B12X"}, block_size=128, dtype="bfloat16")
```

| | before | after |
|---|---|---|
| startup | model loads, torch.compile runs, then `Capturing CUDA graphs` dies: `traits.py ... select_paged_forward_traits ... ValueError: no valid NUM_MMA_KV typed shared-memory allocation fits the device` | `ValueError: Selected backend AttentionBackendEnum.B12X is not valid for this configuration. Reason: ['head_size not supported']` at selection |

Same before/after with `tiiuae/Falcon-H1-0.5B-Instruct` (hybrid, head_dim 64). head_dim 128 (Qwen3-0.6B) still selects and runs b12x.

```
$ pytest tests/v1/attention/test_b12x.py
44 passed in 38.41s   # DGX Spark, GB10; includes the 4 new parametrized cases
```

The new test fails on main (`supports_head_size(64)` is True there) and passes with this change. `pre-commit run --files ...` is clean.

## Details

Root cause is inside the b12x package (same in `flashinfer/experimental/b12x` on FlashInfer main and in the `b12x==1.5.1` wheel pinned by the `[b12x]` extra), reported upstream as flashinfer-ai/flashinfer#6977:

- `_paged_determine_cta_tile_q()` returns `cta_tile_q = 16` for every decode/verify plan, and for that family `select_paged_forward_traits()` only sweeps `num_mma_kv = 1`.
- `_paged_is_invalid()` keeps FA2's rule that `num_mma_d_vo == 4` (head_dim 64) with an odd `num_mma_kv` is invalid, so the single candidate is rejected and the sweep raises.
- The decode kernel itself (`PagedForwardKernel`, `base_use_paged_kv_tma_decode`) only accepts `num_mma_kv == 1` for the generic bf16 16-row family, so the two constraints contradict each other for head_dim 64. FlashInfer's own b12x paged tests only cover head_dim 128/192/256.

I tried the obvious package-side patches on the Spark before settling on this: forcing two KV tiles for head_dim 64 decode is rejected by the kernel constructor (`PagedForwardKernel now only supports exact-plane paged K/V TMA decode`), and relaxing the odd-tile rule for the decode family lets graph capture succeed but the head_dim 64 extend kernel warmup then compiles for 30 minutes without finishing (killed at the bound, twice). So head_dim 64 is not a working path in any released b12x, and the honest thing for vLLM to do is to not offer it. The package API has no head-dim capability query, so a static list is the only fail-fast available; 64 can be re-added, version-gated, once a b12x release supports it.

AI assistance (Claude Code) was used for the investigation and this PR; I reviewed and tested the change on my own hardware.
