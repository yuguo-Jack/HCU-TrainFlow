[Upstream PR](https://github.com/vllm-project/vllm/pull/63993) · state: open · merged: False

## Original PR description

# Intel XPU Kernel Nightly

This workflow builds a wheel from the vLLM XPU kernel repository, uses it to
build a vLLM XPU test image, and runs the Intel XPU tests with that image.
It is intended for nightly or manually triggered integration testing. It does
not publish the wheel to PyPI or public storage.

## Workflow

When enabled, the pipeline:

1. Checks out the configured kernel repository and ref (by default, `main`).
2. Builds the kernel wheel in the builder image specified by the kernel
   repository's `wheel-per-commit.yaml` workflow.
3. Uploads the wheel, checksum, and build information as Buildkite artifacts.
4. Builds the regular vLLM XPU image, installs the wheel into it, and commits
   the result as a uniquely tagged image.
5. Runs the Intel XPU tests with the image produced by the image-build step.

The wheel artifact is stored by Buildkite. Its availability and retention
depend on the Buildkite artifact settings; it is not a public wheel download
URL.

## Enable the workflow

Set these variables in the Buildkite pipeline environment:

```yaml
env:
  VLLM_XPU_KERNEL_NIGHTLY: "1"
  RUN_ALL: "1"
  NIGHTLY: "1"
  MAX_JOBS: "8"
```

`VLLM_XPU_KERNEL_NIGHTLY` must be set to `1` for both the XPU image-build job
and Intel test jobs. `RUN_ALL` and `NIGHTLY` are used by the pipeline generator
to select the full nightly test suite. If the pipeline is generated in a
bootstrap step, make sure these variables are also present in the generated
pipeline; variables exported only in the bootstrap shell do not automatically
carry over to other Buildkite jobs.

The image-build job needs Docker with BuildKit support and permission to push
to the configured image registry. The wheel is copied into a temporary
container after the regular vLLM image is built; it is installed there before
the container is committed as the nightly image. This avoids changing
`docker/Dockerfile.xpu`. The test jobs must be able to read Buildkite metadata
and pull that image.

## Configuration

All variables below are optional unless marked as required.

| Variable | Default | Description |
| --- | --- | --- |
| `VLLM_XPU_KERNEL_NIGHTLY` | `0` | Required to enable this workflow: set to `1`. Values other than `0` or `1` are rejected. |
| `VLLM_XPU_KERNEL_REPO` | `https://github.com/vllm-project/vllm-xpu-kernels.git` | Kernel source Git repository URL. |
| `VLLM_XPU_KERNEL_REF` | `main` | Kernel branch, tag, or other Git ref to build. |
| `VLLM_XPU_KERNEL_BUILD_IMAGE` | Read from the kernel repository's `wheel-per-commit.yaml` | Builder container image. Set this to override automatic lookup. |
| `VLLM_XPU_KERNEL_ONEAPI_VARS` | `/opt/intel/oneapi/2026.1/oneapi-vars.sh` | Path to the oneAPI environment script inside the builder container. |
| `MAX_JOBS` | `8` | Maximum parallel build jobs. Lower this if the builder runs out of memory; higher values may build faster but use more memory. |
| `RUN_ALL` | Not set by the kernel build scripts | Set to `1` to ask the pipeline generator to include all tests. |
| `NIGHTLY` | Not set by the kernel build scripts | Set to `1` for nightly pipeline generation and related CI behavior. |

If the Buildkite agent has proxy variables set (`http_proxy`, `https_proxy`,
`no_proxy`, or their uppercase forms), they are forwarded to the builder
container.

The wheel build also sets
`VLLM_CHUNK_PREFILL_CONFIG=chunk_prefill_default.conf` and
`VLLM_PAGED_DECODE_CONFIG=paged_decode_default.conf`. These are fixed by the
script and are not currently configurable through Buildkite environment
variables.

## Artifacts and test image

The kernel wheel and metadata are uploaded under
`build/xpu-kernel-wheel/`, including the wheel, `SHA256SUMS`,
`kernel-commit.txt`, `build-info.txt`, and `build-environment.txt`.

The image-build job records its generated image name in Buildkite metadata.
Intel test jobs use that image and fail if it is missing or still marked as
pending; they will not silently fall back to a regular XPU image.

`IMAGE_TAG_XPU` is normally not needed. If provided to a nightly test job, it
must exactly match the image name recorded by the image-build job.
