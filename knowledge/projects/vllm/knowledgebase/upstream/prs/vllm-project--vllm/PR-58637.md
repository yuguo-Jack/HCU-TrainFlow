# [Bugfix][Kernel] Restore MiniMax CUDA IPC handle exchange

[Upstream PR](https://github.com/vllm-project/vllm/pull/58637) · state: closed · merged: False

## Original PR description

Fixes #58599.

`cuda-bindings` 13.4 removed the Python `.reserved` field from `cudaIpcMemHandle_t`. MiniMax's Lamport workspace uses that field to exchange CUDA IPC handles, so workspace setup fails and serving falls back from the fused all-reduce and RMSNorm path.

Copy the runtime's 64-byte IPC handle through `getPtr()` when gathering and opening peer handles. Reject a missing or wrongly sized peer payload before passing it to CUDA. The same path works with bindings 13.0.3 and 13.4.3.

On two H100 GPUs with bindings 13.4.3, `test_minimax_reduce_rms_qk(2, 1, (6144, 1024), torch.bfloat16, 1e-6, 42)` failed before the patch with `AttributeError: ... has no attribute 'reserved'`. With the patch, the direct fused call completed and Q/K outputs matched the eager reference. The human submitter ran the patched case in DACHS job `132174`. The case also passed after updating this branch to current `main`, at commit `8b9c416`, in job `132921`; Slurm recorded exit `0:0` and `fused_qk_matches_eager=True`. Both runs used Torch `2.13.0+cu130`, bindings `13.4.3`, and precompiled v0.30.0 extensions.

A separate cross-process IPC check on an L40S passed with bindings 13.0.3 and 13.4.3 after the patch; the old code failed on 13.4.3. The two-H100 case is a model-component numerical check. A complete MiniMax model run and throughput benchmark were not run, so no serving speedup is claimed.

AI assistance was used to prepare the patch and verification. I reviewed every changed line and ran the relevant GPU test as the human submitter.
