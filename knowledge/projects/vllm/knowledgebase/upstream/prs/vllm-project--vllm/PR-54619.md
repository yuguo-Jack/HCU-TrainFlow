# [Bugfix] Reap orphaned /dev/shm region files via flock-based liveness

[Upstream PR](https://github.com/vllm-project/vllm/pull/54619) · state: open · merged: False

## Original PR description

## Purpose

Follow-up to #52596 (merged), as promised in [this comment](https://github.com/vllm-project/vllm/pull/52596#issuecomment-5318600058): reap orphaned `/dev/shm` region files, also covering `ec_shared_region.py`. cc @Etelis 

Fix — liveness the kernel maintains for us, in a new `vllm/utils/shm_utils.py` used by both region classes:

- **Shared `flock` for the life of the mapping.** Every process that maps a region holds `LOCK_SH` on its fd; the kernel releases it however the process exits, SIGKILL included. An orphan is then exactly a file whose *exclusive* lock is free, so reclamation keys on kernel state rather than on a filename match, which would race engines sharing the host's `/dev/shm`.
- **Atomic publication.** A creator builds its region under a `mkstemp` name — flock, `check_shm_free_space`, `ftruncate` — and only then publishes it with `os.link()`. `link()` is atomic and fails if the name is taken, so exactly one racing creator wins and the losers join its region instead of silently mapping a second one. This replaces the `O_EXCL` election.
- **Two invariants follow.** A file at the published path is *always* fully sized, so joiners never observe a partial region and no size polling is needed (`_wait_for_file_size` and its 30 s timeout are gone; a size mismatch now fails immediately with an explanatory error instead). And a published file is locked from the instant it appears, so a starting engine can never be mistaken for an orphan — including the previously fatal case of a creator killed between `O_EXCL` and `ftruncate`, whose 0-byte file used to be skipped by the sweep forever and wedge every subsequent start with that `engine_id`.
- **Every failure path releases the region.** The fd carries the lock leaking it on an error would make the file unreclaimable for the life of the process — defeating the mechanism. Both constructors now close the fd (and the creator unlinks) on any failure, `SharedOffloadRegion.cleanup()` unlinks before closing the fd so the file is never briefly unlocked, and a creator that fails mid-build leaves no temp file behind.

The sweep's inode re-check under the exclusive lock narrows, but cannot fully close, the window in which another process republishes the same name between the check and the `unlink()` — there is no `unlinkat`-by-inode primitive. Worth noting for rolling upgrades: liveness is keyed purely on the flock, so a live region created by a
pre-change vLLM instance sharing the same `/dev/shm` holds no lock andstance's sweep. Established mappings survive, but a late-joining workerof the old instance would fail.

The create/join/lock logic was written out separately in both region classes; it is now a single `open_region_file()` in `vllm/utils/shm_utils.py`, so each constructor is two lines. `_wait_for_file_size`, which `shared_offload_region.py` and `ec_shared_region.py` had each defined their own copy of, is gone entirely: creators now build the region under a temp name and publish it with an atomic `os.link()`, so a published file is always fully sized and there is nothing to poll for. That also removed the retry/timeout handling around it and, as a side effect, fixed the case a 0-byte file left by a creator killed before `ftruncate` was previously unreclaimable and wedged every later start with the same `engine_id`.

Reviewing it again for leaks in that spirit turned up three more, all now fixed with tests: neither constructor closed its fd on failure, and since the fd carries the flock that marks a region live, that leak made the file unreclaimable for the life of the process — the mechanism defeating itself; and `SharedOffloadRegion.cleanup()` closed the fd before unlinking, leaving the file briefly unlocked for a concurrent sweep to reclaim.

- bojiang3 · comment · 2026-09-02T05:15:18Z · [source](https://github.com/vllm-project/vllm/pull/54619#issuecomment-5504751376)

Nice cleanup — the atomic publish via `mkstemp` + `link()` removes the
zero-length window entirely, which is a lot better than sniffing for empty
files. I had an overlapping PR (#54124) and I'm closing it in favour of this
one. Two things from having sat in this file:

**1. `open_region_file` leaks the fd on the size-mismatch path, which makes that
region permanently unreapable.**

When the joiner raises the "different offloading configuration" error, `joined`
is already `True`, so the `finally` skips `os.close(fd)` and the fd escapes
still holding `LOCK_SH`. `SharedOffloadRegion.__init__` can't clean it up
either: the tuple assignment never happened, so `self.fd` is still `None` when
its `except` block runs — the block whose comment says "leaving it open would
make the file unreclaimable for the life of this process". That's exactly what
happens, and `reap_orphaned_region_files` can then never take `LOCK_EX` on it.

Reproduced against `0dc1dd4`, with a control:

```
=== CONTROL: orphan created and released normally ===
  reclaimed by the sweep: True    <- expected

=== TEST: same orphan, but a joiner hit the size-mismatch error ===
  open_region_file raised: Shared region file ... is 4096 bytes ...
  reclaimed by the sweep: False
  exclusive lock REFUSED -> an fd leaked from the raising call still holds
     LOCK_SH, so this region can never be reaped
```

Smallest fix is to let the existing `finally` handle it:

```python
                actual_size = os.fstat(fd).st_size
                if actual_size < size:
                    joined = False   # so the finally below closes the fd
                    raise RuntimeError(...)
```

Happy to send the repro script if useful.

**2. Minor: the `while True:` in `open_region_file` is unbounded.** With
`_wait_for_file_size`'s 30 s timeout now gone, nothing bounds startup if a
process keeps losing the `link()` race or keeps finding the name reclaimed
between the `open` and the `flock`. It should converge in practice, but a
bounded retry with a clear error seems worth it in engine-startup code.

**3. Not a change request, just supporting evidence** for the "didn't #52596
already fix this?" question: #52596's unlink-after-barrier only covers
`CPUOffloadingSpec`, the one call site that passes a barrier
(`cpu/spec.py:185`). `TieringOffloadingSpec` builds the region at two sites with
no barrier (`tiering/spec.py:301` and `:394`), where only the graceful
`cleanup()` unlinks — so a SIGKILL there still orphans the file and this sweep
is still needed.
