# [Bugfix] Set _enable_mm_lora on DiffusionGemma to fix image-input engine crash

[Upstream PR](https://github.com/vllm-project/vllm/pull/54309) · state: open · merged: False

## Original PR description

## Purpose

Since v0.28.0, sending **any image** to a served DiffusionGemma model fatally crashes the EngineCore (all in-flight requests die); text-only requests are unaffected.

`DiffusionGemmaForConditionalGeneration` borrows the Gemma4 multimodal methods as unbound class attributes:

```python
_process_image_input = Gemma4ForConditionalGeneration._process_image_input
embed_multimodal = Gemma4ForConditionalGeneration.embed_multimodal
```

but #42662 ([LoRA][Gemma4] Support vision tower LoRA) made `_process_image_input` read `self._enable_mm_lora`, which is set only in `Gemma4ForConditionalGeneration.__init__`. DiffusionGemma never sets it, so the first image request raises

```
AttributeError: 'DiffusionGemmaForConditionalGeneration' object has no attribute '_enable_mm_lora'
```

inside `_execute_mm_encoder` and takes the engine down. v0.27.1 and earlier are unaffected (the attribute did not exist).

This PR mirrors Gemma4's assignment in DiffusionGemma's `__init__`. With tower/connector LoRA off it evaluates to `False`, which follows the exact pre-#42662 memory-chunked encoder path.

## Test Plan

Reproduced and verified on an A100 (sm_80) with `nvidia/diffusiongemma-26B-A4B-it-NVFP4` on v0.28.0:

```
vllm serve nvidia/diffusiongemma-26B-A4B-it-NVFP4 \
  --max-model-len 65536 --attention-backend triton_attn
# then POST /v1/chat/completions with an image_url content part
```

## Test Result

- Before: the request above raises the AttributeError, EngineCore dies, every subsequent request fails.
- After (this patch applied to the same install): the image is answered correctly, and a follow-up text battery (5/5 GSM-style questions) passes on the same still-alive engine.

- he-yufeng · comment · 2026-09-13T22:47:24Z · [source](https://github.com/vllm-project/vllm/pull/54309#issuecomment-5656703715)

Same root cause found independently while triaging #56712 — good to see a fix already up. One hardening suggestion that would make it robust for the whole class, not just this borrower.

Setting the flag on `DiffusionGemma` fixes this instance, but the invariant that actually broke is weaker: `_process_image_input` is *designed for delegation* (DiffusionGemma borrows it by class assignment), yet it reads init-time state that only exists if Gemma4's own `__init__` ran. The next borrower, or a Gemma4 subclass that skips `super().__init__`, reintroduces the same crash. Reading the flag defensively at the two use sites keeps Gemma4 behavior identical (`__init__` always sets it) and makes every borrower safe:

```suggestion
        if getattr(self, "_enable_mm_lora", False):
```

at `gemma4_mm.py:1317` and `:1364` (the batch-size branch). I verified the delegated path end-to-end on a bare borrower that never ran `__init__`: without the change it raises the exact `AttributeError: ... has no attribute '_enable_mm_lora'` from #56712; with `getattr(..., False)` the no-MM-LoRA path runs and returns correctly shaped per-image embeddings.

If you'd rather keep the diff to one file, the borrower-side assignment works too — but consider taking the two-line getattr as well so this stops being a per-borrower whack-a-mole.

- jagat-primitive-org · comment · 2026-09-15T20:31:20Z · [source](https://github.com/vllm-project/vllm/pull/54309#issuecomment-5687668398)

Taken — added the two-line `getattr` hardening at `gemma4_mm.py:1317` and `:1364`.

Keeping both halves rather than swapping one for the other, because they do different jobs:

- The `getattr` default is what makes the *delegated* path safe for any borrower, including future ones and any `Gemma4` subclass that skips `super().__init__()`. That also covers the bare-borrower case from #56712.
- The `diffusion_gemma.py` assignment is still needed for **correctness**, not just crash-safety. With only the `getattr`, `DiffusionGemma` would silently take the `False` branch, so `enable_tower_connector_lora` would be quietly ignored for it rather than honoured. The assignment computes the real value; the `getattr` is the net under it.

The defensive read is also already the local idiom here — the block immediately below the first site does `getattr(getattr(self, "multimodal_config", None), "mm_processor_kwargs", None)`.

`Gemma4` behaviour is unchanged either way: its `__init__` always sets the attribute, so the `getattr` resolves identically on every existing path.
