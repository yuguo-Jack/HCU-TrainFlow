# [Bugfix][Kernel] Sync cluster before DSMEM stores in ll_bf16 split-K router GEMM

[Upstream PR](https://github.com/vllm-project/vllm/pull/61463) · state: open · merged: False

## Original PR description

## Purpose

The cuteDSL `ll_bf16` split-K router GEMM (#42562, used for M >= 8) writes each CTA's partials into every peer CTA's shared memory (`st.shared::cluster`) before any cluster barrier. CUDA requires a cluster sync before the first DSMEM access, since a peer CTA may not have started yet. When it hasn't, the GPU raises Xid 13 `Graphics SM Cga Exception: CTA Not Present`, which surfaces as `CUDA error: unspecified launch failure`.

Fix: a relaxed cluster arrive/wait at kernel start, the same pattern `gemm_rs_ar.py` already uses. No other cuteDSL kernel under `kernels/linear/cute_dsl/` uses DSMEM.

cc @LopezCastroRoberto

## Reproduction

Only seen with HiSparse P/D over NIXL, the default HiSparse P/D path on `main`, where the decode server's host-pool KV imports keep many copy streams busy alongside the router GEMM. It is a timing race, so the fault can't be forced from software.

**Decode on `main` (`cbe1f9740d`; `_ll_bf16_splitk.py` identical to current `main`):** GLM-5.3 (`RedHatAI/GLM-5.3-NVFP4`) P/D across 2 coreweave H200 nodes, no instrumentation. Setup:
- Decode TP4, PIECEWISE cudagraphs, `MultiConnector[HiSparseConnector (host_pool_gib=300), NixlConnector kv_consumer]`.
- Workload: evalscope `swe_smith` multi-turn, `--parallel 8 --number 16 --max-tokens 220`.

Caveats: the decode tree also carried the 11-line `hisparse/connector.py` patch from #60117 (P/D connector only, unmerged), and prefill ran the #55398 tree. Result: crash about 6 minutes into pass 1.
```
(Worker_TP2) torch.AcceleratorError: CUDA error: unspecified launch failure
dmesg: Xid (PCI:0000:cb:00): 13, Graphics SM Cga Exception on (GPC 7, TPC 6, SM 0): CTA Not Present ... name=VLLM::Worker
```
The same signature appeared in two more decode-on-`main` runs: FP8 GLM-5.3 TP8 P/D, one with PIECEWISE and one with `sparse_indexer_topk_backend=persistent`. The persistent run rules out `cooperative_topk`, the other cluster kernel on that path.

**#55398 stack, same P/D setup, decode TP4 with `--num-gpu-blocks-override 14000`:**

| Decode router GEMM | Result |
|---|---|
| unpatched | crashed 4/4 runs within 2 passes; `dmesg`: Xid 13 CTA Not Present |
| `ll_bf16` disabled | 6/6 passes clean (48,439 host imports) |
| this PR | 6/6 passes clean (1,248/1,248 requests, 48,411 host imports) |

**Not reproduced:**
- **Single-server HiSparse on pristine `main` (`67516b6`, 4xH200 TP4):** same flags without NIXL; 10 passes plus 6 passes with 2000 output tokens, 256/256 requests clean. Host-to-device traffic was heavy (54M hot-buffer misses in one sample window).
- **Standalone stress on H100:** ~45M split-K launches PDL-chained in CUDA graphs, against 8–32 background streams of HiSparse-like zero-copy and spin kernels.
- **compute-sanitizer:** memcheck is clean with and without the fix. synccheck reports the same pre-existing warnings in both. racecheck hangs on this kernel.

So the trigger needs the SM contention from the P/D host-import path. A pristine-`main` P/D run will replace the `cbe1f9740d`+#60117 evidence once an 8xH200 node is free.


On H200, the fixed kernel matches `torch.mm` on 25 shapes (K ∈ {4096, 5120, 6144, 7168}, N ∈ {64, 128, 160, 256}, M ∈ {1, 2, 4, 8, 16}; split-K path used for M >= 8): all cos = 1.000000, max_abs <= 3.3e-6.

Kernel latency on H100: median of 30 CUDA-graph replays of 200 back-to-back PDL launches, µs per call.

| K, N | M | main | PR |
|---|---|---|---|
| 6144, 256 | 8 / 12 / 16 | 2.71 / 2.75 / 2.81 | 2.81 / 2.85 / 2.90 |
| 7168, 256 | 8 / 12 / 16 | 2.84 / 2.89 / 2.91 | 2.93 / 2.96 / 3.01 |

The barrier costs ~0.1 µs per call. Moving the wait to just before the DSMEM stores recovered only ~0.04 µs. That version also leaves the DMA warps exiting without a wait, so I kept the simpler form that was validated in the serving workload.

No regression test is included: the fault requires the hardware to delay one CTA of the cluster, which can't be forced from a test.

- Skyseaee · comment · 2026-10-16T07:05:13Z · [source](https://github.com/vllm-project/vllm/pull/61463#issuecomment-6210051133)

@MatthewBonanni We have an independent single-GPU reproduction that may help with validation here. It reproduces without model weights, a connector SDK, RDMA, or a P/D deployment.

The trigger is running the ll_bf16 split-K router concurrently with ordinary CUDA kernels that write directly to mapped pinned host memory on another stream. The copy kernels do not use clusters, and their buffers are separate from the router's buffers.

Environment:
- B300 / SM103, driver 580.159.04
- vLLM 0.30.1.dev15+ga6bb06c0f, torch 2.13.0+cu130
- CUDA toolkit 13.0.88, CUTLASS DSL 4.7.1, cuda-bindings 13.4.3
- PDL enabled; CUDA_LAUNCH_BLOCKING unset

The unpatched _ll_bf16_splitk.py is byte-identical to upstream main at fa75d3456d60a5ffe923818c4b495295675b38e1 (SHA256 f282d0c1c4649d3affb19d694b7edf66cecf7764946b4effe57737830ec7a3ad). The rest of the environment is not a pristine-main build.

Reproduction procedure (sources and logs are in the attached ZIP):
1. Use BF16 A[8,7168] and W[896,7168], FP32 output; dispatch selects split_k=6, num_stages=4.
2. Capture 256 ll_bf16_gemm calls in one CUDA graph.
3. Allocate a GPU source of shape [27,4096,576] bytes and a pinned-host destination of shape [4096,27,576]. Obtain the destination's device pointer with cudaHostGetDevicePointer.
4. On a separate stream, enqueue four groups of 27 non-cluster uint4 copy kernels (one launch per layer, 4096 blocks x 128 threads), each group writing 60.75 MiB directly to mapped host memory. Replay the router graph on the main stream, then synchronize both streams and repeat.

From the extracted directory, in an existing vLLM environment:

```bash
mkdir -p results
nvcc -O3 -shared -Xcompiler -fPIC -arch=sm_103 copy.cu -o libhostcopy.so
unset CUDA_LAUNCH_BLOCKING
export CUTE_DSL_DISABLE_FILE_CACHING=1
export CUDA_DEVICE_WAITS_ON_EXCEPTION=0
.venv/bin/python -u router_probe.py --tag baseline --mode direct --seconds 10
# Apply this PR's patch, then use a fresh process:
.venv/bin/python -u router_probe.py --tag pr61463 --mode direct --seconds 120
```

Please select an isolated GPU with CUDA_VISIBLE_DEVICES. The README includes environment and patching instructions. Compare dmesg before/after each run for new Xid lines.

On 2026-10-16 we tested exactly the patch in this PR, with no other router changes:

| Kernel | Result |
| --- | --- |
| Unpatched | Failed in the first batch: CUDA unspecified launch failure and new Xid13 / CTA Not Present |
| This PR's exact patch | 4,887,808 router calls over a 120-second stress loop; router output and copied-byte checks passed; no additional Xid |

The final recorded elapsed time is 130.383 seconds, including correctness checks after the loop. Generated PTX confirms the new arrive/wait precedes the first st.shared::cluster. This validates our isolated reproduction; we have not yet run a full-model serving soak test with this exact patch. Detailed results are in VALIDATION.txt in the attached ZIP.

This is a timing-sensitive reproduction established on B300 with the environment above; we have not established reproduction on Hopper. Hopefully it provides a smaller validation workload than a full P/D deployment.
