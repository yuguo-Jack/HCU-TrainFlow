# [Bugfix][Frontend] Keep special tokens when truncating from an explicit side

[Upstream PR](https://github.com/vllm-project/vllm/pull/61363) · state: open · merged: False

## Original PR description

## Overview

Fixes #61359. With `truncate_prompt_tokens` and an explicit `truncation_side`, truncation now keeps
the special tokens the tokenizer adds (`[CLS]`/`[SEP]`, BOS, EOS), as the tokenizer's own truncation
does. Before, the ones at the truncated end were cut.

## Claims

- Text prompts truncated from an explicit side keep their special tokens and match the tokenizer's
  own truncation on both sides, with any tokenizer: left truncation on BGE keeps `[CLS]`, right
  truncation on Qwen3-Embedding keeps the EOS it pools on, left truncation on Llama, and on Mistral
  in the `mistral` tokenizer mode, keeps BOS.
- Embeddings for these requests match `transformers` again: `LLM.embed`, `/v1/embeddings`, and
  Cohere `/v2/embed` with `truncate="START"`.
- `prompt_token_offsets` stay aligned with the kept tokens.
- Unchanged: requests without an explicit `truncation_side` (the tokenizer still truncates those
  itself), prompts without special tokens (`add_special_tokens=False`, the chat default), multimodal
  prompts.

## Details

Root cause: the tokenizer can only truncate from its own `truncation_side`, so with an explicit side
`get_encode_kwargs()` turns tokenizer truncation off and `_token_truncation` slices the full token
ids from the requested side. The slice doesn't know which tokens the tokenizer added and cuts the
ones at that end.

- `BaseRenderer._tokenize_prompt`, when `_truncation_slice` will cut a prompt truncated from an
  explicit side, tokenizes the text again with `add_special_tokens=False`, and applies the indices
  that `_truncation_indices` keeps to the token ids and offsets. `apply_post_tokenization` then finds
  the prompt within the limit.
- `TokenizeParams._truncation_indices` finds the text tokens inside the full token ids, keeps the
  tokens around them, which are the ones the tokenizer added, and fits the text between them into
  the rest of the limit, as `transformers` does. It returns `None`, so the plain slice applies, when
  no tokens were added, there is no room for them, or the text tokens are not found.
- This works with any tokenizer and renderer. The first revision asked for `special_tokens_mask`,
  which only `HfRenderer` did: `MistralTokenizer` can't return it, and the Cohere, Inkling and
  Kimi-K3 renderers have HF tokenizers but never asked. The cost is a second tokenization of the
  already length-bounded text, only for prompts that an explicit side truncates. Multimodal prompts
  are skipped, since `_truncate_expanded_prompt` slices them again after placeholder expansion.

`test_completion_render_truncated_token_offsets` asserted that the first offset after left truncation
starts past the beginning of the prompt, which only held because BOS was dropped. It now checks that
BOS is kept with a `(0, 0)` offset.

When the special tokens alone exceed the limit (`truncate_prompt_tokens=1` with `[CLS] … [SEP]`), the
plain slice still applies instead of raising as `transformers` does.

Left out: cross-encoder pairs in `scoring/io_processor.py`, which slice the same way but also carry a
`[SEP]` between the segments and `token_type_ids`, and the Rust frontend's `PromptTruncation::apply`.

I used an AI assistant to investigate this and to write the code and tests; I reviewed every change
and ran the tests myself.

- vadiklyutiy · COMMENTED · 2026-10-15T22:46:15Z · [source](https://github.com/vllm-project/vllm/pull/61363#pullrequestreview-5540842454)

The mask is only enabled in `HfRenderer` (`_can_produce_special_tokens_mask`), but the slice that drops the tokens is in the shared `BaseRenderer`, so other renderers still lose BOS with an explicit `truncation_side`.

E.g. `mistralai/Mistral-7B-Instruct-v0.3` with `--tokenizer-mode mistral`, `truncate_prompt_tokens=4`: side unset gives `[1, 18666, 4682, 29491]`, `"left"` gives `[1040, 18666, 4682, 29491]`. `MistralTokenizer` doesn't support `return_special_tokens_mask`, so this needs a fallback, e.g. re-tokenizing with `add_special_tokens=False` to find the added tokens.

- roydonsequeira · comment · 2026-10-13T11:46:16Z · [source](https://github.com/vllm-project/vllm/pull/61363#issuecomment-6144821541)

For context on the Transformers side: there is no per-call `truncation_side`. In 5.19, `__call__` takes `padding_side` but not `truncation_side`, and the fast tokenizer reads `self.truncation_side` and writes it into the Rust tokenizer with `enable_truncation(direction=...)`. Setting it per request means changing state the tokenizer shares with every other request, so the renderer turns tokenizer truncation off and slices the ids itself. This PR only keeps the special tokens in that slice.

If Transformers took `truncation_side` per call the way it takes `padding_side`, the explicit-side path could use the tokenizer's own truncation, and both the slicing and the mask handling here would go away.
