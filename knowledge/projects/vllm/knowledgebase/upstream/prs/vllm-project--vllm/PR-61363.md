# [Bugfix][Frontend] Keep special tokens when truncating from an explicit side

[Upstream PR](https://github.com/vllm-project/vllm/pull/61363) · state: open · merged: False

## Original PR description

## Overview

Fixes #61359. With `truncate_prompt_tokens` and an explicit `truncation_side`, truncation now keeps
the special tokens the tokenizer adds (`[CLS]`/`[SEP]`, BOS, EOS), as the tokenizer's own truncation
does. Before, the ones at the truncated end were cut.

## Claims

- Text prompts truncated from an explicit side keep their special tokens and match the tokenizer's
  own truncation on both sides, in `HfRenderer` and `MistralRenderer`: left truncation on BGE keeps
  `[CLS]`, right truncation on Qwen3-Embedding keeps the EOS it pools on, left truncation on Llama,
  and on Mistral in the `mistral` tokenizer mode, keeps BOS.
- Embeddings for these requests match `transformers` again: `LLM.embed`, `/v1/embeddings`, and
  Cohere `/v2/embed` with `truncate="START"`.
- `prompt_token_offsets` stay aligned with the kept tokens.
- Unchanged: requests without an explicit `truncation_side` (the tokenizer still truncates those
  itself), prompts without special tokens (`add_special_tokens=False`, the chat default), multimodal
  prompts, and the other renderers (see Details).

## Details

Root cause: the tokenizer can only truncate from its own `truncation_side`, so with an explicit side
`get_encode_kwargs()` turns tokenizer truncation off and `_token_truncation` slices the full token
ids from the requested side. The slice doesn't know which tokens the tokenizer added and cuts the
ones at that end.

- `HfRenderer._tokenize_prompt`, for a prompt truncated from an explicit side, asks the tokenizer
  for `special_tokens_mask` in the same call and applies the indices that `get_truncation_indices`
  keeps to the token ids and offsets. `MistralRenderer._tokenize_prompt` does the same for BOS, the
  only token mistral-common adds, as `MistralTokenizer` can't return the mask.
  `apply_post_tokenization` then finds the prompt within the limit.
- `get_truncation_indices`, in `vllm/renderers/inputs/tokenize.py`, keeps the tokens that the mask flags and fits the text into
  the rest of the limit from the requested side, as `transformers` does. It returns `None`, so the
  plain slice applies, when no tokens were added or there is no room for them.
- `BaseRenderer` is unchanged, as asked in review. Each renderer handles what its
  own tokenizer adds, and no prompt is tokenized twice. The Cohere, Inkling and Kimi-K3 renderers
  have HF tokenizers but subclass `BaseRenderer`, so they still cut these tokens; they can take the
  same override in a follow-up. Multimodal prompts are skipped, since `_truncate_expanded_prompt`
  slices them again after placeholder expansion.

`test_completion_render_truncated_token_offsets` asserted that the first offset after left truncation
starts past the beginning of the prompt, which only held because BOS was dropped. It now checks that
BOS is kept with a `(0, 0)` offset.

When the special tokens alone exceed the limit (`truncate_prompt_tokens=1` with `[CLS] … [SEP]`), the
plain slice still applies instead of raising as `transformers` does.

Left out: cross-encoder pairs in `scoring/io_processor.py`, which slice the same way but also carry a
`[SEP]` between the segments and `token_type_ids`, and the Rust frontend's `PromptTruncation::apply`.

I used an AI assistant to investigate this and to write the code and tests; I reviewed every change
and ran the tests myself.

- roydonsequeira · comment · 2026-10-13T11:46:16Z · [source](https://github.com/vllm-project/vllm/pull/61363#issuecomment-6144821541)

For context on the Transformers side: there is no per-call `truncation_side`. In 5.19, `__call__` takes `padding_side` but not `truncation_side`, and the fast tokenizer reads `self.truncation_side` and writes it into the Rust tokenizer with `enable_truncation(direction=...)`. Setting it per request means changing state the tokenizer shares with every other request, so the renderer turns tokenizer truncation off and slices the ids itself. This PR only keeps the special tokens in that slice.

If Transformers took `truncation_side` per call the way it takes `padding_side`, the explicit-side path could use the tokenizer's own truncation, and both the slicing and the mask handling here would go away.

🟡 (optional) Long prompts truncated from an explicit side now cost twice the tokenizer CPU on the renderer's single default worker thread. The second call at base.py:701-704 re-tokenizes the whole pre-trimmed text, not a short one. That text is bounded only by `max_input_tokens * max_chars_per_token` characters, not by `truncate_prompt_tokens`. Fix: find the added tokens without a second full pass, e.g. `return_special_tokens_mask=True` on the first HF call, or a short probe string. Keep the re-tokenization only as a fallback for tokenizers that cannot report the mask, such as `MistralTokenizer`.

<details>
<summary>Why this was flagged</summary>

The trigger is any text request with `truncate_prompt_tokens` and an explicit `truncation_side` whose prompt is longer than the limit. In this mode `get_encode_kwargs` (params.py:382-386) turns tokenizer truncation off. The text is only pre-trimmed by `_text_len_check` (params.py:400-419) to `max_input_tokens * tokenizer.max_chars_per_token` characters, where `max_chars_per_token` is the longest vocab entry (hf.py:124). `_tokenize_prompt` (base.py:698-707) then tokenizes all of it a second time with `add_special_tokens=False`, just to learn which few tokens at either end were added. Tokenization runs in `self._executor`, which has `renderer_num_workers` threads and defaults to 1 (config/model.py:412). So every such request doubles its tokenizer time, and other requests queue behind it. On the base branch each prompt is tokenized once.

**Verification:** In this mode, `get_encode_kwargs` (params.py:382-386) returns `dict(truncation=False, add_special_tokens=...)`, so the first call at base.py:693 tokenizes all of the pre-trimmed text. The call at base.py:701-704 uses the same `truncation=False` kwargs, so it is a second full pass over the same text, not a short probe.

</details>
