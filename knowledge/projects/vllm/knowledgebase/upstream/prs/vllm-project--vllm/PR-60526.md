# [Feature][Multimodal] Support KV-backed continuation through Generate inputs

[Upstream PR](https://github.com/vllm-project/vllm/pull/60526) · state: open · merged: False

## Original PR description

## Purpose

Let a decode instance continue a multimodal request from existing decoder KV, without the media and without encoder capacity. Closes #60521.

This revision is the engine contract only, cut down to the scope discussed in the review (@Isotr0py's [`mm-kv-minimal`](https://github.com/Isotr0py/vllm/tree/mm-kv-minimal) and the reduced scope offered on Oct 26):

- **Generate API:** `features.requires_kv` on `MultiModalFeatures`. All items must already be covered by decoder KV; they carry hashes and placeholder positions only, and the validator rejects serialized payloads in `kwargs_data` / `mm_metadata` and empty hashes. The field is omitted from the wire format when false. `engine_input_from_features` turns a Generate request into the engine input (`mm_requires_kv=True`), and `serve_tokens` uses it.
- **Engine input / feature spec:** `MultiModalInput.mm_requires_kv` and `MultiModalFeatureSpec.requires_kv` carry the same flag per request and per item through IPC.
- **Admission (`InputProcessor`):** KV-only inputs are exempt from the encoder-cache capacity check, so a decode worker with `--limit-mm-per-prompt '{"image": 0}'` admits them. They must carry a nonempty hash and no payload per item, stay within the prompt, and end before the final prompt token, which is always recomputed. Prompt logprobs, pooling, M-RoPE and encoder-decoder models are rejected: M-RoPE derives its positions from the media the input does not carry, so it needs a metadata channel first.
- **Scheduler:** `Request.mm_required_kv_tokens` caches the furthest required position. `_try_schedule_encoder_inputs` fails the request (`FINISHED_ERROR`) whenever `num_computed_tokens` is below it, instead of running the decoder over placeholder ids. The check re-applies after preemption and after failed KV loads, and `_update_request_as_session` raises the boundary when a streaming session appends a `requires_kv` feature.
- **Receiver cache / renderers:** the receiver cache skips `requires_kv` features (`data=None` is a deliberate absence, not a cache reference), and the renderers refuse to render such inputs again, so `LLM.generate()` cannot silently drop the requirement.

With the prefill-side hashes and placeholder positions, the decode engine computes the same block hashes as prefill, so the local prefix cache and hash-keyed KV consumers see the same blocks on both sides; the alternative of folding image hashes into `cache_salt` rewrites every decode block hash ([data](https://github.com/vllm-project/vllm/pull/60526#issuecomment-6500329741)).

Removed from the previous revision: the Python `prepare_multimodal_kv_handoff` / `restore_multimodal_kv_handoff` / `export_multimodal_kv_handoff` helpers, the `kv_handoff` version/position-state descriptor and the model fingerprint, the `vllm/inputs/mm_features` package (types and serde stay in `token_in_token_out/`), the `is_embed` round-trip on `PlaceholderRangeInfo` (separate PR), and the long docs section. Callers that embed `AsyncLLM` build the input with `mm_input(...)` plus `mm_requires_kv=True`, or through `engine_input_from_features`.

- gty111 · comment · 2026-10-09T00:51:13Z · [source](https://github.com/vllm-project/vllm/pull/60526#issuecomment-6071996631)

Thanks for putting this together — the `requires_kv` semantics and the scheduler-side coverage enforcement (incl. preemption/load-failure rechecks) look like the genuinely new and valuable part of this PR.

One design concern before this goes further: the descriptor/API layer looks like a third parallel schema next to the existing metadata-only paths, and I think it should be aligned with what vLLM already has instead:

1. **Descriptor format**: `MultiModalKvHandoff` largely duplicates the `mm_metadata` serialization in `token_in_token_out/mm_features.py` (hashes, placeholder offsets/lengths). The one real gap there is that `PlaceholderRange.is_embed` is not preserved on main today — fixing that in `mm_features.py` would benefit both the EC path and this one, and seems like a prerequisite either way. Could the handoff payload reuse/extend that format (e.g. model fingerprint as a field) rather than introducing a separate struct?

2. **Admission path**: instead of a new Python-only export/restore API, could this ride on the existing Generate-protocol admission for metadata-only items? `_require_ec_for_metadata_only` currently hard-couples metadata-only features to `ec_transfer_params`; generalizing it to also accept a KV-backed fulfillment claim (e.g. `kv_transfer_params` or an explicit flag) would give KV continuation the same door the EC path already uses, with the scheduler coverage check you added here as the actual enforcement.

The lifecycle contract itself (bypassing the receiver cache for intentionally-absent media, and failing the request whenever KV coverage is missing — including after preemption) has no counterpart in the EC path and does need new logic; my suggestion is only that the descriptor and admission layers not fork from the existing protocol.

<summary>Minimal example: what the KV handoff carries</summary>

There are two separate pieces: the **input descriptor** carries token IDs, media hashes, placeholder positions and the KV-coverage requirement; **`kv_transfer_params`** tells the configured connector how to retrieve the matching attention KV. The descriptor contains neither the original image nor the KV tensors. Export/restore alone does not transfer KV or prove it is present.

The following extracts the engine calls from the benchmark adapter. Run `prefill` on the P worker and pass its returned JSON to `decode` on the D worker. Both engines must already be initialized with matching model/cache settings and a working NIXL connector. These are Python engine calls, not a standalone launcher or stock HTTP route.

```python
"""Core engine calls, extracted from worker.py; not a standalone launcher.

P and D are separately initialized AsyncLLM engines with matching model/cache
settings and a working NIXL connector. Run each function on its owning worker.
"""

import json
import uuid

from vllm import SamplingParams


async def prefill(p_engine, raw_prompt):
    # raw_prompt contains text + PIL image; rendered contains image inputs.
    rendered, descriptor = await p_engine.input_processor.prepare_multimodal_kv_handoff(
        raw_prompt
    )
    params = SamplingParams(
        temperature=0, seed=42, max_tokens=1, ignore_eos=True,
        extra_args={"kv_transfer_params": {
            "do_remote_decode": True, "do_remote_prefill": False,
        }},
    )
    result = None
    async for result in p_engine.generate(rendered, params, uuid.uuid4().hex):
        pass
    assert result is not None and result.kv_transfer_params
    # Only metadata crosses HTTP here. NIXL moves the actual KV separately.
    # P's generated token is discarded; D continues from the original prompt.
    return json.dumps({"input": descriptor,
                       "kv_transfer_params": result.kv_transfer_params})


async def decode(d_engine, wire_json):
    wire = json.loads(wire_json)
    restored = d_engine.input_processor.restore_multimodal_kv_handoff(wire["input"])
    # No image loading/rendering. requires_kv is enforced by the scheduler.
    params = SamplingParams(
        temperature=0, seed=42, max_tokens=32, ignore_eos=True,
        extra_args={"kv_transfer_params": wire["kv_transfer_params"]},
    )
    result = None
    async for result in d_engine.generate(restored, params, uuid.uuid4().hex):
        pass
    assert result is not None and result.outputs[0].finish_reason != "error"
    return list(result.outputs[0].token_ids)
```

> Hmmm, I think passing --language-model-only should also archieve same targets

2. `--language-model-only` plus a pixel-less text prompt (what smg-project/smg#2640 does) gets close, and this PR is meant to run on exactly such workers: validated KV-only inputs are exempt from the encoder-cache capacity check, so a decode worker with `--limit-mm-per-prompt '{"image":0}'` admits them. The differences are in what the engine can guarantee:

   - **Block identity.** SMG keeps same-size images apart by folding the image hashes into `cache_salt`. The salt enters the first block hash and chains through every later block, so decode's block hashes no longer equal prefill's, and the shared text prefix before the image no longer prefix-caches across requests on the decode side. NIXL does not care because it addresses blocks by id, but anything that looks blocks up by hash (shared-storage and offloading-tier connectors, hash-based reuse between instances) cannot match them. With the real `mm_hashes` and placeholder ranges in `features`, decode computes the same block hashes as prefill and prefix caching keeps its normal semantics.
   - **Fail-closed.** A text-only prompt gives the scheduler nothing that stops it from recomputing the image span from placeholder token ids: after a preemption whose blocks are evicted before the request resumes, or a failed load under `kv_load_failure_policy=recompute`, the request completes with HTTP 200 and an answer conditioned on garbage. That is the same class of silent wrong answer as the Dynamo incident with a different trigger, and a caller-side check cannot see it because it happens after admission. `requires_kv` makes the scheduler fail the request instead, for the whole request lifetime.
   - **One implementation.** The Generate API already carries metadata-only `features` for the EC path (#54659). Reusing that door means orchestrators do not each re-derive expanded ids, placeholder layout and hash identity, plus the carve-outs SMG needed (M-RoPE, media refs, n>1), and keep them in sync with vLLM's processors.

If the concern is the amount of surface this adds, I am happy to cut it down to the engine contract only: `is_embed` round-tripping in `PlaceholderRangeInfo`, and `features.requires_kv` with the receiver-cache bypass, the admission exemption and the scheduler coverage check. The Python prepare/restore helpers and the model fingerprint would go (text-only P/D does not fingerprint model configs between workers today and relies on the orchestrator pairing them, so this path can too). Would that scope be acceptable, or would you prefer `is_embed` and `requires_kv` as two separate PRs?
