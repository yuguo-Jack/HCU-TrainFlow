# [ZenCPU] Add zen5 CPU tests reusing the pushed zen image

[Upstream PR](https://github.com/vllm-project/vllm/pull/60824) · state: open · merged: False

## Original PR description

## Overview

Add two Zen CPU hardware-test steps (kernel + platform-detection) on the `zen5`
queue, gated on zen source changes. They reuse the zen CPU image published by the
existing `zen-cpu-image-build` step instead of recompiling on the scarce Zen5 box:
that step now **pushes** `<repo>:<commit>-zen-cpu` to public ECR, and
`run-zen-cpu-test.sh` **pulls** it (with a local-build fallback). Builds on the
merged zen image-build work in #60016; assumes the zentorch 2.14.0.1 / fp16
enablement from #61411.

## Claims

- Adds `Zen-CPU-Kernel Tests` and `Zen-CPU-Platform-Detection Tests` on
  `device: zen5`, gated on zen source changes.
- `zen-cpu-image-build` now publishes `<repo>:<commit>-zen-cpu` to public ECR, so
  the zen5 steps pull it (anonymous pull, no credentials on the test side) rather
  than rebuilding on scarce hardware.
- `run-zen-cpu-test.sh` pulls the prebuilt zen image (local-build fallback:
  published `-cpu` base, else from source); installs zentorch directly via
  `ZENTORCH_VERSION` to avoid the `vllm[zen]` transitive triton-cpu URL failure;
  verifies the installed zentorch version + its `torch.compile` backend before
  tests; and removes pulled/built images on exit so they don't accumulate on the
  shared host.
- Adds a consistency test asserting the `ZENTORCH_VERSION` in `cpu.yaml` and
  `run-zen-cpu-test.sh` match the `zen` extra in `setup.py`.
- Gates the fp16 case of `test_cpu_unquantized_gemm_dispatch.py` on
  `zentorch_is_fp16_supported()` (AVX512-FP16 / Venice+), so the Turin-class zen5
  CI doesn't run an fp16 matmul the hardware can't execute.

## Validation

**Full flow verified end-to-end in CI (build #98237)**, commit `22762f66…`:
- `image-build-cpu` pushes `…:<commit>-cpu`.
- `zen-cpu-image-build` logs `Using published CPU image as base: …-cpu`,
  installs `zentorch==2.14.0.1` (no `vllm[zen]`, no triton error),
  `Login Succeeded`, pushes `…-zen-cpu`.
- Both zen5 steps log `Using published Zen image: …-zen-cpu` — reuse confirmed,
  not the fallback.
- Kernel step: `7 passed, 1 skipped` (fp16 skipped on this non-AVX512-FP16
  part); Platform step: `10 passed`.

## Details

- Reuse mirrors the existing `-cpu` image reuse: the push is guarded on `REGISTRY`
  (CI only); pulls are anonymous public ECR, so test nodes need no credentials.
  The zen5 agent env lacks `REGISTRY`/`REPO`, so the test steps pass the
  public-ECR coordinates explicitly (matching `ci_config.yaml`'s main/premerge
  mapping).
- Test steps `depends_on: zen-cpu-image-build` with `allow_dependency_failure:
  true`, so the local-build fallback still runs if that build fails/soft-fails.
  `run-zen-cpu-test.sh` is in the build step's `source_file_dependencies` so the
  build step is never pruned while a test runs (which would otherwise make
  `depends_on` error at pipeline upload).
- `ZENTORCH_VERSION` pinned to `2.14.0.1` (matching the `zen` extra in `setup.py`,
  per #61411) keeps `Dockerfile.zen` on its direct-zentorch `if` branch and avoids
  `uv` re-resolving `vllm[zen]` (which fails on vLLM's transitive `triton @ <url>`
  CPU wheel).
- The zen5 preflight asserts `importlib.metadata.version("zentorch")` equals the
  pin and `"zentorch" in torch._dynamo.list_backends()`, so a version/ABI mismatch
  or a stable-only build fails loudly instead of silently testing a different
  zentorch.
- fp16: the dispatch test's fp16 parametrize is skipped when
  `zentorch_is_fp16_supported()` is false; the mock-zentorch x86 lane (no such op)
  still exercises fp16 via its `F.linear` stub, mirroring
  `ZenCpuPlatform.supported_dtypes`.
