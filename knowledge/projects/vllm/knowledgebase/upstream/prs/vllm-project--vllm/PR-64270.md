# [Bugfix] Muse: keep a last parameter missing its closing tag

[Upstream PR](https://github.com/vllm-project/vllm/pull/64270) · state: open · merged: False

## Original PR description



## Overview

Muse Glimmer sometimes ends a tool call's last parameter without `</atem:parameter>`. The Python Muse tool parser drops that parameter, which leaves `{}` for a call with one parameter. The Rust parser rejects the whole ATEM block, and the Rust frontend then sends the raw markup to the client as text. Both parsers now end such a value where its `</atem:invoke>` begins.

## Claims

- Python (`MuseToolParser`): a last parameter missing `</atem:parameter>` keeps its value. Before this change it was dropped silently, and earlier closed parameters were kept.
- Rust (`MuseUnifiedParser`): the same input parses into the tool call. Before this change it failed with `invalid Muse ATEM block`, and `unified.rs` fell back to plain text.
- Output for well-formed calls is unchanged.
- The Muse section of `docs/features/tool_calling.md` states the rule.

## Validation

New tests, 4 per parser: an unclosed only parameter, an unclosed last parameter after a closed one, an unclosed parameter followed by a second invoke in the same block, and an unclosed string value followed by its separating newline.

The test with a second invoke also guards the boundary in `atem_parameter_value`: without the check that a closed value does not contain `</atem:invoke>`, the first invoke's value runs into the second invoke and the block yields 1 call instead of 2.

With the fix: `cargo test -p vllm-parser` passes 628 of 628, and `cargo test -p vllm-chat --test roundtrip` passes 25 of 25. `cargo fmt --check`, `cargo clippy --all-targets --all-features --locked -- -D warnings`, ruff 0.14.0 and markdownlint are clean.

I also checked the regex against real model output, from `Inferact/Muse-Glimmer-30B-NVFP4-W4A4` served by `vllm/vllm-openai:v0.32.0` during a 500-question agentic RAG evaluation. In v0.32.0 the regex lives in `muse_glimmer_tool_parser.py`. For every response with tool calls, I requested `return_token_ids`, decoded the ids with the server's `/detokenize` (framing tokens kept), and parsed that text with the v0.32.0 parser and with the patched one. The same generated tokens go through both parsers, so the comparison is deterministic.

| | Responses with tool calls | Unpatched parser reproduces the served calls | Calls the patch recovers |
|---|---:|---:|---:|
| 500 questions | 2,273 | 2,273 | 190 (161 `cite`, 23 `search`, 6 `execute_code`) |

All 190 recovered calls had arrived with `{}` arguments, and each one gained exactly its one missing parameter.

## Details

Root cause: `_PARAM_RE` required a closing `</atem:parameter>`. On text like

```
<atem:invoke name="cite">
<atem:parameter name="chunk_ids">["07657059-389d-4601"]</atem:invoke>
```

the regex finds no match for that parameter, so it is skipped. Here it is the call's only parameter, so the call reaches the client with `{}`. The Rust `atem_parameter` uses `take_until(PARAMETER_CLOSE)` followed by `literal(PARAMETER_CLOSE)`, so the invoke fails, and with it the block.

Fix: a value ends at the earlier of `</atem:parameter>` (consumed) and `</atem:invoke>` (left for the invoke). A value that ends at the invoke drops the newline before `</atem:invoke>`. The Python regex and the Rust `atem_parameter_value` implement the same rule. A value cannot cross its invoke in either parser.

Limitations:

- No `RemoteOpenAIServer` test. The trigger is sampled output from the 30B checkpoint, which I cannot reproduce deterministically in CI. The parser tests use the exact text the model produced.
- The Rust frontend was not run end to end with the model. Its fix is covered by the unit tests and the chat roundtrip suite.
- #62345 fixes a different problem, quadratic attribute scans, but edits the same `_PARAM_RE` line (`[^>]*?` to `[^<>]*?`). The two changes touch different parts of the pattern, so whichever merges second needs a small rebase.
