# [Bugfix][Tool Parser] Fix hunyuan_a13b streaming arguments with braces and deep nesting

[Upstream PR](https://github.com/vllm-project/vllm/pull/64962) · state: open · merged: False

## Original PR description



## Overview

`hunyuan_a13b` streaming now returns the same tool arguments as non-streaming when a value contains braces or the arguments nest three or more levels. These calls used to finish with `finish_reason: tool_calls` and broken or empty arguments, so nothing signalled the error.

```diff
 _handle_tool_args_streaming
-  find arguments with a regex that ignores strings and follows one nested level
-  if a later call exists, re-slice at the first "},{"
+  find arguments with a regex that takes strings whole and recurses into objects
   emit "{", then the rest
```

| Arguments in the model output | Streaming before | Streaming after |
|---|---|---|
| `{"a": {"b": {"c": 1}}}` | empty string | same as the output |
| `{"a": "{"}` | `{"a": "{"}}` | same as the output |
| `{"a": "}"}` | `{"a": "}` | same as the output |
| `{"a": {"b": {"c": 1}}}`, then a second call | both calls empty | both calls intact |

## Claims

- Arguments nested three or more levels stream in full, and no longer lose the next call's arguments with them.
- `{`, `}` and `},{` inside string values and keys no longer move the end of the arguments.
- Non-streaming is untouched, and no fuzz trial that matched before changed its streamed result to a mismatch.

## Details

**Root cause:** `tool_non_empty_arg_reg` treated every `{` and `}` as structure, including those inside strings, and allowed only one nested level. A brace in a value ended the match early or late. At three levels the arguments never matched, which also shifted the index the next call read. Its own `TODO` and the old xfail already recorded the nesting half.

**Why this shape:** the pattern stays in place, so the indexing and the `{` then rest emission do not change. Strings are matched whole, `(?1)` recurses, and the quantifiers are possessive so a partial object fails without backtracking.

- `json.JSONDecoder.raw_decode` is shorter, but it rejects text the stream passes today, such as `{'a': 1}`, and then cannot find the end of that object to reach a valid call after it.
- A Python character scan would run over the whole text on every delta. The regex is cheaper than the old one: about 0.27 ms against 6-7 ms per scan at 100 KB of arguments.
- On 100,000 random JSON objects the pattern ended exactly where `raw_decode` did, and it matched none of 408,742 strict prefixes.

**Removed `},{` re-slice:** it could not tell a separator from a string value. It also never ran: when a later call exists the name step returns first, so the arguments step only sees the last call found so far. Coverage over 42,000 fuzz trials and targeted merged-delta inputs confirmed that.

**Not a duplicate:** on 2026-11-01 I searched open PRs for `hunyuan_a13b`, `hunyuan a13b`, `hunyuan tool parser`, `tool_non_empty_arg_reg`, and combinations of hunyuan with nested, brace, arguments and streaming JSON. #49535 changes `tool_name_reg` and #47954 changes the empty-argument lookup, and neither fixes this. This branch does not touch those regexes or their use. Their diffs merge with it without textual conflict, alone and together, when applied to the same base. #60360 and #51698 are `xlam` only. #52133 adds a Rust parser. #58412, #63632 and #54499 are reasoning parsers.

**Earlier attempt:** #38103 addressed nested JSON here. The stale bot closed it on 2026-07-27 without a merge or a maintainer rejection. This branch does not use its code.

**Format evidence:** the chat template in the Hugging Face `tencent/Hunyuan-A13B-Instruct` files has no tool branch. The evidence is this repo's `examples/tool_chat_template_hunyuan_a13b.jinja`, which instructs this format. The brace and depth-3 inputs rendered through it with the real tokenizer appear verbatim in the assistant turn. Weights were not run, so I have not observed the model producing them.

**Limitations:**

- The tests sit at the parser's extraction interface. The new test uses the real `default_tokenizer` fixture from `tests/tool_parsers/conftest.py`, and the older tests in this file keep their `MagicMock` tokenizer. There is no test through `LLM` or `RemoteOpenAIServer`, which would need weights and a GPU. That coverage gap needs a maintainer's call.
- The new tests split the text per character. Real token boundaries are covered by the local fuzzer only.
- Deltas merged by `--stream-interval` or a lagging consumer can still cut arguments short, as on main. Some depth-3 trials moved from an empty string to `{`. Neither is correct.
- Output with an odd number of unescaped quotes in a value, such as `{"a": "5" tall"}`, used to stream verbatim as invalid JSON and now streams empty arguments, and a later call in the same block loses its arguments. Non-streaming rejects the whole block. The other 16 malformed or truncated inputs I compared, including unescaped quotes in pairs, stream the same as before.
- Out of scope: `<tool_calls` leaking into `content`, which has no open PR.

**Door:** two-way. One regex in one parser, with no API or config change.

**Blast Radius:** parser-local. Only `--tool-call-parser hunyuan_a13b` streaming arguments can change.
