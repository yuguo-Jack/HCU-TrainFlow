# [KV Connector][Mooncake] Start async lookup on the input thread via on_preschedule_request

[Upstream PR](https://github.com/vllm-project/vllm/pull/61292) · state: open · merged: False

## Original PR description



## Overview

Start MooncakeStore's async prefix lookup on the engine-core input thread as soon as a request arrives, so the lookup overlaps both the wait for the busy loop to pick up the request and the wait in the scheduler's waiting queue. GPU KV allocation and transfer remain in the scheduler's existing path.

This adds a generic connector hook, `KVConnectorBase_V1.on_preschedule_request(request)`, in place of using `on_new_request()` (which runs on the scheduler thread, after the request has already waited in the input queue).

## Design: start on the input thread, hand off via the request, adopt on the scheduler thread

`on_preschedule_request` runs on the input thread and may run concurrently with `schedule()`. To keep connectors free of locks:

- The hook must not read or write mutable connector or scheduler state. It may only start self-contained, thread-safe background work and return a handle.
- `EngineCore.preprocess_add_request` stores the handle on `request.kv_preschedule_handle`. The request then travels through the input queue, which gives the scheduler thread a happens-before edge on the handle.
- The connector adopts the handle on the scheduler thread (Mooncake: in `get_num_new_matched_tokens`) and owns it from then on.

For MooncakeStore:

- `LookupKeyClient.prefetch()` (input thread) only takes a slot from a `BoundedSemaphore` and submits to the single lookup executor. The ZMQ socket is still used only by that executor thread. It returns a `LookupState` without registering it.
- `LookupKeyClient.adopt()` (scheduler thread) registers the state in `_lookups`, which only the scheduler thread touches. The existing `lookup()` reuse, signature-change and TTL logic then applies unchanged.
- An unadopted handle is cancelled in `request_finished` (a request aborted while it was still waiting). Adopted lookups are discarded on finish, preemption, reset and close, as before.
- Requests with `skip_reading_prefix_cache`, sub-alignment prompts, or no block hashes are not prefetched.

## Claims

- With `lookup_async=True`, `enable_lookup=True`, and a positive `lookup_prefetch_limit`, eligible requests submit their lookup on the input thread at arrival. Off by default.
- `lookup_prefetch_limit` caps arrival-time lookups in flight. A slot is released when the RPC completes or is cancelled, so it cannot leak if a request never reaches the scheduler. Over the cap, the request is looked up when the scheduler first reaches it. Scheduler lookups are not capped.
- Arrival-time lookups create no `LoadSpec` or GPU allocation. The scheduler still computes the external tokens to load from its current local-prefix hit count.
- An arrival-time result older than `lookup_prefetch_ttl_s` (default 2 s) at the scheduler's first probe is looked up again. Cached async results expire the same amount of time after their first read. A changed token/hash range also triggers a fresh lookup.
- `MultiConnector` does not forward `on_preschedule_request` yet (base default: no-op), so the feature is off when MooncakeStore is wrapped in a `MultiConnector`.

## Validation

```bash
.venv/bin/python -m pytest --confcutdir=tests/v1/kv_connector/unit \
  tests/v1/kv_connector/unit/test_mooncake_store_scheduler.py \
  tests/v1/kv_connector/unit/test_mooncake_store_connector.py -q
```

**124 passed** (Linux, Python 3.12, on current `main`). New and updated cases cover:

- an input-thread prefetch adopted by the scheduler-thread lookup with a single RPC
- the in-flight cap, including slot release on completion and scheduler lookups bypassing the cap
- a duplicate adopt keeping the existing lookup
- expiry before the first probe, and changed or expired queries
- skipping ineligible requests
- cancelling an unadopted handle on finish, and discarding on finish or preemption

`pre-commit run --files <changed files>`, `pre-commit run mypy --hook-stage manual`, and `git diff --check` all passed.

Not run: GPU serving, real Mooncake transfers, model evaluation, TTFT/throughput benchmarks. Those, plus human line-by-line review, are required before marking this ready.

## Trade-offs

An earlier lookup adds backend work for requests that later abort or hit entirely in the local cache, and the single lookup worker can queue that work ahead of later requests. The cap bounds this. The TTL can cause a second lookup after a long queue wait. Both defaults need measurement on real workloads. Cancelling a queued future works; an RPC that is already running cannot be interrupted.

Duplicate-work checks: searched open vllm-project/vllm PRs for Mooncake lookup, async/prefetch lookup, `on_new_request` lookup, and connector input-thread hooks. #48230 skips lookups for locally reused prefixes, which is a different change. #42321 (enqueue-time prefetch for `LMCacheMPConnector`, scheduler-thread `on_new_request`) was closed for inactivity, not rejected. This PR adds an input-thread hook with a handle-handoff contract, which also lets `LMCacheMPConnector` start its lookup earlier if it adopts the hook.
