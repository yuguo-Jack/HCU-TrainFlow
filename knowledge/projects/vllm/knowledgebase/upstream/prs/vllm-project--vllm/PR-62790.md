# [Bugfix][Model Runner V2] Use int64 logits row offsets in the grammar bitmask kernel

[Upstream PR](https://github.com/vllm-project/vllm/pull/62790) · state: open · merged: False

## Original PR description

## Overview

The MRV2 grammar bitmask kernel computes the logits row offset as an int32 product, so it overflows once `row * vocab_size` exceeds 2**31. With a 151936-token vocab that happens from logits row 14135, which wide spec-decode verification with structured outputs can reach at large batch sizes (e.g. 15 draft tokens and ~900 requests). The kernel then writes `-inf` outside the logits tensor and leaves the intended row unmasked. This loads the row index as int64, like the other MRV2 row-offset kernels fixed in #46560 and for #57030.

## Claims

- Grammar bitmasks are applied to the right logits rows past the int32 offset limit, instead of writing out of bounds.
- No behavior change below the limit.

## Validation

- New `tests/v1/worker/test_gpu_row_offsets_i64.py::test_grammar_bitmask_high_row`, following the other tests in that file: one request's logits row below the limit and one above it (bf16 logits, vocab 8192, row `2**31 // 8192 + 1`) in the same kernel launch. On `main` it fails with `CUDA error: an illegal memory access was encountered`; with the fix both rows are masked except the allowed token. Tested on an RTX 4090.
- `pytest tests/v1/worker/test_gpu_row_offsets_i64.py`: 5 passed. `pytest tests/v1/worker/test_gpu_batch_shard.py`: 17 passed.
- `pre-commit run --files <changed files>`: all hooks pass.

No end-to-end run: reaching row 14135 needs a ~4.3 GB logits tensor from a wide spec-decode batch with structured outputs, which I can't build on one 24 GB GPU. The new test runs the same kernel through `StructuredOutputsWorker.apply_grammar_bitmask` at the overflowing offset; like the rest of that file it is skipped without ~11 GiB of free device memory.

## Details

`_apply_grammar_bitmask_kernel` (`vllm/v1/worker/gpu/structured_outputs.py`) loads `logits_idx` from the int32 `cu_num_logits` and stores to `logits_ptr + logits_idx * logits_stride + block_offset`. Triton keeps the product in int32, so it wraps to a negative offset. The fix casts the loaded index to int64; the other products in the kernel stay far below 2**31 (`bitmask_idx * bitmask_stride` is bounded by the number of grammar rows times `vocab_size / 32`).

Not a duplicate: I found no issue or PR for this (searched "grammar bitmask overflow", "apply_grammar_bitmask int64", "bitmask kernel int32 overflow", "logits row offset overflow"). #46560 and #60736 fixed the same class of overflow in the sampler and index-mapping kernels but not this one.

AI assistance was used to find this bug, write the fix and the test, and run the validation shown above.
