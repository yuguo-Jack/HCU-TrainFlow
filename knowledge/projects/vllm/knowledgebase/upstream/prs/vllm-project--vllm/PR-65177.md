## Overview

Fixes #58532

`QuarkW8A8Int8MoEMethod` can load static per-tensor activation scales with per-output-channel weight scales. The legacy Triton `fused_experts` path still used `per_act_token_quant` to pick both layouts, so static activations (`per_act_token_quant=False`) also took the tensor weight-scale branch. Routed experts' channel scales were ignored.

This keeps the legacy static-INT8 path (no oracle migration) and splits the two flags:

- `int8_w8a8_moe_quant_config` now takes `per_out_ch_quant` and Quark/compressed-tensors/online INT8 callers set it from the actual weight scheme.
- The shared non-block W8A8 Triton kernel indexes A scales with `per_act_token_quant` / `per_channel_quant` and W scales with `per_out_ch_quant`.

No open PR already covers this combo. #57092 is the opposite mixed case (per-token acts + per-tensor weights) and is still open.

- bnellnm · CHANGES_REQUESTED · 2026-11-03T18:17:52Z · [source](https://github.com/vllm-project/vllm/pull/65177#pullrequestreview-5757366644)

An LLM code review flagged this particular issue:

"[P2] FusedMoEQuantConfig.make now infers per_out_ch_quant=True whenever per_act_token_quant=True when the caller omits it (vllm/model_executor/layers/fused_moe/config.py:571). That is too broad for a shared factory. Fp8MoEMethod omits the flag (vllm/model_executor/layers/quantization/fp8.py:777), and under VLLM_BATCH_INVARIANT=1 it uses per-token activations with per-tensor weights (vllm/model_executor/layers/quantization/fp8.py:515). I confirmed this combination now reports per_out_ch_quant=True despite having 1-D per-tensor scales. TritonExperts forwards that flag into the per-channel scale branch (vllm/model_executor/layers/fused_moe/experts/triton_moe.py:456, vllm/model_executor/layers/fused_moe/fused_moe.py:499). The current 1-D Triton scale layout happens to make stride_bsn=0, masking the error, but the quant config contract is wrong and any 2-D scale or backend that branches on this flag will mis-index. Prefer passing per_out_ch_quant=False explicitly from Fp8MoEMethod, or keep the factory default False and confine the legacy fallback to the legacy launcher."

I don't think the flag change itself is unreasonable but the callers of `FusedMoEQuantConfig.make` should be audited (and maybe made more explicit) to make sure that the existing behavior for other quantization methods has not been changed.
