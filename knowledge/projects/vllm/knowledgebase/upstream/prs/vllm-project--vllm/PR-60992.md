# [Perf][Model][Qwen4Exp] QSA: decode four FP8 e4m3 bytes per register below sm_89

[Upstream PR](https://github.com/vllm-project/vllm/pull/60992) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

On GPUs below sm_89 (A100, A10, RTX 30xx), Triton cannot load FP8 e4m3 directly. So the QSA reader loads the FP8 KV cache as `uint8` and turns each byte into an fp16 value with integer ops (#60602).

This PR does that conversion four bytes at a time. One 32-bit register holds four cache bytes, and six PTX instructions turn them into four fp16 values. Only the body of the `uint8` branch in `_maybe_dequant` changes. Nothing else changes.

**Result on one A100:** the FP8 reader takes 0.64–0.78× of its current time at 128–2,048 rows. The output is bitwise equal to `main`.

## Claims

- **Same output:** the reader output is bitwise equal to `main` for FP8 and BF16 caches at every tested row count. All 256 byte values decode to the same fp16 bits as `main`, in each of the 4 byte positions of a register.
- **Faster on A100:** FP8 reader time is 0.64–0.78× of `main` at 128–2,048 rows and 0.76–0.88× at 32–80 rows. It is unchanged at 8–16 rows.
- **No effect elsewhere:** BF16 caches and sm_89+ GPUs never reach the `uint8` branch. No new CPU/GPU sync.

## Details

**Why the old path is slow.** Each cache byte becomes one 16-bit value with two masks, two shifts and an `or`. At prefill-sized row counts this conversion is a large part of the reader time on A100.

**What the asm does, per 32-bit register (4 bytes in, 4 fp16 out):**
1. `shf` rotates the word right by 1. Bits 6..1 of each byte move to bits 5..0.
2. `lop3` puts each sign bit back in place.
3. Two `prmt` pair the bytes into the high and low halves of two fp16 pairs.
4. Two `and` with `0xBF80BF80` clear the bits that are not part of the value.

The result is the fp16 of `x * 2^-8`. The `2^8` is already folded into the host scales (#60602). The two NaN codes read as ±480, as on `main`.

**Byte order.** With `pack=4`, Triton gives element k in byte k of the input register and in half k of the two output registers. Triton's own sm<89 fp8 → fp16 asm uses the same mapping.

**Alternative considered.** A plain-Triton version (sign-extend, then one shift and one mask) is also bitwise equal, with no asm. It is 4–10 % slower than this PR at 128–2,048 rows (0.70–0.83× of `main`). After review, we chose the asm.

**Scope.** All GPUs that use the `uint8` path (sm_80, sm_86). Measured on sm_80 only.

**CI.** There is no sm_80 runner. The A100 data come from our cluster.

- kimseunghyun-kr · comment · 2026-10-13T14:48:54Z · [source](https://github.com/vllm-project/vllm/pull/60992#issuecomment-6148277015)

Thanks, @gau-nernst. I removed the new test.

The byte order is now explicit. The kernel loads the K/V cache as little-endian 32-bit words, and the asm (`pack=1`) writes byte `i` of each word to output `i`, so output `i` is head dims `4 * word + i`. Nothing depends on how Triton packs elements into registers.

My first try put the bytes back in head-dim order with `tl.join`/`tl.reshape` per tile. That lost the whole gain (0.95–1.05× of `main`). So this version keeps the 4 byte planes through the loop instead: q is loaded as 4 matching strided planes, QK is 4 chained dots, PV writes 4 accumulators, and one join/reshape after the loop restores the order for the epilogue.

On A100 the FP8 reader now takes 0.64–0.78× of `main` at 128–2,048 rows. BF16 is unchanged and bitwise equal.

One trade-off: FP8 output is no longer bitwise equal to `main`, because the QK sum over the head dims runs in a different order (max abs difference 1.2e-4 to 4.9e-4). The error against a float64 reference is the same as `main`'s. If you prefer bitwise equality, I can use planes for V only and keep `main`'s decode for K. That gives a smaller gain, and I have not built it.
