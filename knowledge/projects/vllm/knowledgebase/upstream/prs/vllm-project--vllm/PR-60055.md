# [Bugfix][ROCm] Skip AITER Gluon MLA when Triton cannot compile it

[Upstream PR](https://github.com/vllm-project/vllm/pull/60055) · state: open · merged: False

## Original PR description

## Overview

Skip AITER's Gluon MLA kernel when the installed Triton cannot compile it. On the ROCm vLLM image, MI355 (gfx950) ships with Triton 3.6, and selecting Gluon fails while capturing CUDA graphs.

## Claims

- Head counts that currently take Gluon on gfx950 (decode for 1, 2, 4 and 8 heads, and multi-token verify below 16 heads) fall back to the padded ASM path when `PaddedSharedLayout` has no `cga_layout` field.
- A Triton that accepts `cga_layout` keeps the existing Gluon routes, including an explicit `gluon` mode for 12-head decode.

## Validation

On MI355, Triton 3.6.0, against this checkout of main (`710ac56`):

```
pytest tests/v1/attention/test_rocm_aiter_mla_fp8_decode_routing.py --noconftest
493 passed
```

The same process reproduces the compile failure the gate checks for:

```
PaddedSharedLayout fields: interval_padding_pairs, offset_bases, block_bases, shape
PaddedSharedLayout(..., cga_layout=[]): TypeError: unexpected keyword argument 'cga_layout'
```

`ruff check` and `ruff format --check` pass on the two changed files.

This checkout has no compiled `vllm._rocm_C`, so the run above is the routing suite, not a server. The same gate was previously brought up end to end on the image's vLLM 0.27.1: Kimi-K3 at TP8 (12 heads per rank) reached `Application startup complete` with no `CompilationError`. On current main, 12-head decode already uses padded ASM; verify and divisor heads still selected Gluon, which is what this change covers.

## Details

`aiter/ops/triton/gluon/mla_gluon.py` calls `PaddedSharedLayout` with `cga_layout`. Triton 3.6 names that parameter `block_bases` and raises `TypeError`, so the kernel never compiles. `_gluon_mla_decode_supported()` only checked for gfx950, and the ROCm image is gfx950 plus Triton 3.6, so the Gluon path was selected and then failed.

The gate now also requires `cga_layout` on `PaddedSharedLayout`. An explicit `gluon` mode does not override an uncompilable Triton. Newer Triton keeps the Gluon path. The check is the same one `use_gluon_decode` and `use_gluon_verify` already share, so both entry points move together.

The failure was reproduced on the image this work ran on, which is not the stack in `docker/Dockerfile.rocm_base`. Marking this PR as a draft.

Versions on that image:

- AITER 0.1.19
- Triton 3.6.0
- vLLM 0.27.1

`docker/Dockerfile.rocm_base` on main pins AITER `v0.1.24.post1` and Triton `669b31a` (`release/internal/3.8.x`). AITER `v0.1.24.post1` still calls `PaddedSharedLayout(..., cga_layout=...)`. At Triton `669b31a`, `PaddedSharedLayout` has a `cga_layout` field (`python/triton/experimental/gluon/language/_layouts.py`), so that constructor does not raise there. The `TypeError` is from Triton 3.6.0, where the same field is named `block_bases`.

Reproduce on Triton 3.6.0:

```bash
python3 - <<'PY'
from triton.experimental.gluon import language as gl
print(list(gl.PaddedSharedLayout.__dataclass_fields__))
gl.PaddedSharedLayout(
    interval_padding_pairs=[[512, 16]],
    offset_bases=[[0, 1]],
    cga_layout=[],
    shape=[64, 512],
)
PY
```

```
['interval_padding_pairs', 'offset_bases', 'block_bases', 'shape']
TypeError: PaddedSharedLayout.__init__() got an unexpected keyword argument 'cga_layout'
```
