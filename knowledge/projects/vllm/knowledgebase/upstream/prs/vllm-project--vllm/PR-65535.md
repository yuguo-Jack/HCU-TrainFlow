# [Bugfix][Multimodal] Skip the encoder CUDA graph for precomputed embeddings

[Upstream PR](https://github.com/vllm-project/vllm/pull/65535) · state: open · merged: False

## Original PR description

## Overview

Fixes #65531. With `enable_mm_embeds=True` and `cudagraph_mm_encoder=True`, one request with precomputed image or video embeddings crashes the engine. This PR sends embeddings batches to the eager path in both model runners.

## Claims

- Precomputed image and video embeddings no longer crash the engine when the encoder CUDA graph is on. This holds in Model Runner V1 and V2.
- Pixel inputs still replay the graph.
- Nothing changes for batches without a `<modality>_embeds` key.

## Validation

## Details

- **Root cause.** Both runners pick the encoder graph by modality only. An embeddings item keeps its modality, `"image"` or `"video"`, so it reaches the graph manager. The model's graph hooks then look for pixel inputs and fail. #65531 shows how each model fails.
- **The fix.** `EncoderCudaGraphManager.supports_batch(modality, mm_kwargs)` returns `False` when the batch has the `<modality>_embeds` key. Both runners call it where they called `supports_modality`. The check runs before `execute()`, so embeddings never reach the data-parallel encoder path either. `group_and_batch_mm_kwargs` never puts pixel and embeddings items in one batch. So in a step with both, the pixel batch still replays the graph.
- **Why this key.** Embedding inputs reach the runner as `<modality>_embeds` (`multimodal/parse.py:244`). Models that take embeddings as a dict use the same names. The check matches the exact key, not a suffix. So a pixel input whose key ends in `_embeds`, such as Phi-4MM's `input_image_embeds`, is not taken for embeddings. Phi-4MM has no encoder graph today.
- **Why not inside `execute()`.** Returning `[]` there still fails the sanity check. Returning `None` would also work, because both runners already fall back to eager on `None`. But it widens `execute()`'s return type for a case the runners can check up front. I'm happy to switch if you prefer.
- **Why V1 too.** V1 is still used when V2 lacks a feature. `XPUModelRunner` also subclasses it.
- **Overlap with #58122.** #58122 is the LLaVA encoder graph PR. It adds `"image_embeds" not in mm_kwargs_batch` to the same two runner lines. This PR moves that check into the manager and also covers `video_embeds`. Whichever PR lands second gets a one-line conflict in each runner. The fix is to keep `supports_batch()` and drop the inline check. A local trial merge shows this works. With that fix, the merged `test_encoder_runner.py` passes. #59193 (BLIP-2) relies on #58122's check. `supports_batch()` covers it too.
- **Limits.**
  - On EC and KV consumers, a request may send only `image_grid_thw` and no embedding tensor. Such an item has no `image_embeds` key. So if it were encoded locally, it would still reach the graph. But the eager path would fail on it too, before and after this PR. So this PR doesn't change that case.
  - The new GPU test skips unless the platform is CUDA or ROCm, like `test_vit_cudagraph.py`. It still runs on the AMD mirrors. It was tested on NVIDIA only.
- **Not a duplicate.** No open PR fixes this for both image and video embeddings. #58122 covers `image_embeds` only, inside a LLaVA feature PR. #56277 (Pixtral and Mistral 3, merged on 2026-11-03) avoids the crash inside the model. It turns the encoder graph off whenever `enable_mm_embeds` is on. The open PR #52229 (Cosmos3-Edge) does the same. With `supports_batch()`, those models could keep the graph for pixel inputs.
