# [Bugfix][Model] Make compile_mm_encoder work for RADIO/NaViT encoders

[Upstream PR](https://github.com/vllm-project/vllm/pull/63415) · state: closed · merged: True

## Original PR description

FIX #63414, where the bug is:
Serving nvidia/Nemotron-3.5-Parse with --compilation-config.compile_mm_encoder true kills
the engine on the first image request, and the server stops answering entirely
(Connection refused afterwards — it is a fatal EngineDeadError, not a per-request 500):

```
AttributeError: 'NoneType' object has no attribute 'cu_seqlens'
  vllm/model_executor/models/radio.py:501 in forward   (under torch._dynamo.aot_compile)
EngineCore encountered a fatal error -> **EngineDeadError**

```
## Purpose of this PR

`--compilation-config.compile_mm_encoder true` does nothing for RADIO. Since the encoder
was rewritten to standalone modules (#58468), `RadioLayer` carries no
`@support_torch_compile`, so the flag is silently a no-op for `Nemotron-3.5-Parse`,
`Nemotron-Parse-2.0` and `nano_nemotron_vl` — the encoder is never compiled and nothing
says so.

Simply decorating the layer does not work either. Three independent static-shape
assumptions are in the way, each only visible once the previous one is fixed:

1. **Wrong dynamic dim.** RADIO packs NaViT tokens into dim 1, so marking dim 0 (the
   value inherited from InternVL before the refactor) bakes the packed length.
2. **Varlen metadata is unaddressable.** `dynamic_arg_dims` keys by argument name, and
   `cu_seqlens` was wrapped in the `MaskMetadata` dataclass, so its length could not be
   marked dynamic. It now travels as tensor arguments.
3. **Traced vs runtime mismatch.** `mask_meta` was built only when more than one image
   was present. Encoder profiling uses 2 items, so tracing saw an object while real
   single-image requests passed `None`. A no-guards graph keeps whichever form it traced
   and drops the other **silently** — measured below. When the layer is compiled, every
   call now carries metadata: one image gives `cu_seqlens [0, n]` (unmasked attention
   over a single sequence), and a uniform `[B, n, C]` batch is packed the way the conv3d
   video path already did.

Two things that review caught and this PR now does deliberately:

- **Packing only happens when the layer is compiled.** TORCH_SDPA does not synthesise
  `cu_seqlens` the way the FlashAttention and Triton wrappers do — handed a packed
  sequence it splits it and runs one attention call per item. Always packing cost a
  uniform batch B calls per layer instead of one (B=8, 2 layers: 16 `apply_sdpa` calls
  vs 2, bit-identical output), plus a `.tolist()` host sync per layer; a 128-frame video
  chunk would be 128 launches per layer. A consistent `cu_seqlens` form is only required
  for the no-guards graph, so uncompiled the batch stays unpacked and the default path is
  unchanged from main.
- **Only dim 1 is marked dynamic.** Every path reaching the compiled layer packs to
  `[1, total, C]`, and torch specializes a size-1 dim to 1 even when it is marked
  dynamic, so listing dim 0 bought nothing and implied a batch dim that cannot vary.
  Correctness rests on the batch-1 invariant, which is now asserted once in
  `RadioVisionEncoder.forward` so an unpacked caller fails on a clear precondition
  instead of a size/stride assert deep inside inductor.

Building the metadata must not copy host memory: `torch.tensor(list, device=cuda)` is a
blocking host sync on every encoder forward, which `VLLM_GPU_SYNC_CHECK=error` rejects.
Uniform batches use a device-side `arange`; the variable-length helper stages through
pinned memory.

`RadioVisionEncoder.forward` keeps its `MaskMetadata`-facing signature and unpacks once,
so `nemotron_parse3_5` and `nano_nemotron_vl` need no changes.


silently and hides this), torch 2.14.0: marking `[0, 1]` and marking `[1]` specialize
dim 0 identically, so dim 0 was inert.

## Behaviour note

Enabling the flag changes the output for some pages. The first difference is always a
bounding-box coordinate of ~0.001 normalised (1-2 px), but under greedy decoding that can
rewrite the rest of a long generation, so similarity ranges from 1.000 to 0.43 by page.
This is **torch.compile on the encoder, not the varlen path**: with the flag off this PR
is byte-identical to main on all three models and on both attention backends, and
`cu_seqlens [0, n]` for one image is bit-exact against unmasked attention. Flagging it
since the flag is opt-in.

One remaining issue: `RadioVisionEncoderLayer` is now decorated twice (its own `@support_torch_compile` plus the inherited one on `InternVisionEncoderLayer`), so `TorchCompileWithNoGuardsWrapper.__init__` runs twice per layer. Each run registers a bytecode hook, and the second one overwrites `_bytecode_hook_handle`, so the first hook can never be removed. `cleanup()` on engine deletion drops only the last one, and Dynamo's hook table keeps the layer alive.

With an in-process engine (`VLLM_ENABLE_V1_MULTIPROCESSING=0`) and `compile_mm_encoder` on, Nemotron Parse 3.5 keeps all 27 RADIO layers and ~947 MiB on the GPU after `del llm` (33 MiB on main). The static path (Parse 2.0, fixed-tile `nano_nemotron_vl`) is affected too, and it did not leak before.

A two-line fix in `vllm/compilation/wrapper.py`:

    if envs.VLLM_USE_BYTECODE_HOOK and mode != CompilationMode.STOCK_TORCH_COMPILE:
        # A decorated subclass of a decorated class runs this init twice.
        self.cleanup()
        self._bytecode_hook_handle = (...)

Plus a regression test: decorate `A` and a subclass `B(A)` with `@support_torch_compile`, construct `B`, call `cleanup()`, `del`, `gc.collect()`, and assert a weakref to it is `None`. It fails without the line.

🔴 Every RADIO encoder layer now gets an empty weight prefix. Quantization ignore lists and per-layer FP8 encoder-attention scales stop matching for Parse 2.0, Parse 3.5 and nano_nemotron_vl. The new `@ support_torch_compile` wrapper takes `prefix` as a keyword. It forwards `prefix` only if the wrapped `__init__` declares it, and `RadioVisionEncoderLayer.__init__(self, *args, **kwargs)` does not. Fix: have `RadioVisionEncoderLayer.__init__` take `prefix` (and the other named args) explicitly and pass them to super, or drop the redundant decoration, so `{prefix}.layers.{i}` reaches `InternVisionEncoderLayer`.

<details>
<summary>Why this was flagged</summary>

`InternVisionEncoder` builds each layer with `prefix=f"{prefix}.layers.{layer_idx}"` (intern_vit.py:351). The new decorator on `RadioVisionEncoderLayer` (radio.py:482) wraps its `__init__(self, *args, **kwargs)`. `_support_torch_compile.__init__` (decorators.py:377, 401) binds `prefix` itself and forwards it only when `"prefix" in sig.parameters`. That check is False for `*args, **kwargs`, so the prefix is silently dropped. On the base branch the undecorated subclass passed `prefix` through `**kwargs`, so the names were correct. One trigger is FP8 encoder attention with `mm_encoder_fp8_scale_path`. There, `MMEncoderAttention.layer_name` (mm_encoder_attention.py:340) is the same for all layers, and the scale lookup at :481 raises "FP8 attention enabled but scales not found for layer". The decorator's "support decorating multiple times" guard (decorators.py:360) does not help here. It only checks direct `__bases__`, and `TorchCompileWithNoGuardsWrapper` is a base of the parent, not of this class.

**Verification:** The wrapper forwards `prefix` only `if "prefix" in sig.parameters` (decorators.py:401-402), which is False for `RadioVisionEncoderLayer.__init__(self, *args, **kwargs)` (radio.py:482-492). On the base commit the Radio class was undecorated, so `prefix` passed through `**kwargs` and was forwarded correctly. This is a regression.

</details>

`hidden_states` dim 0 is not actually dynamic here. Every path now packs to `[1, total, C]`, and torch specializes a size-1 dim to 1 even when it is marked dynamic. Checked on torch 2.13 (the vLLM image): `mark_dynamic(h, [0, 1])` on `h.shape == (1, 7, 4)` compiles, and the next call with shape `(2, 9, 4)` fails with `expected size 2==1 ... at dim=0`.

So correctness rests on the batch-1 invariant, not on dim 0 floating. Suggest `{"hidden_states": 1, "cu_seqlens": 0}`, say so in the comment, and assert `inputs_embeds.shape[0] == 1` once in `RadioVisionEncoder.forward` so an unpacked caller fails loudly instead of with a size/stride assert deep in inductor.

Failing case: TORCH_SDPA backend with a uniform batch (Parse 2.0 fixed-res images, nano_nemotron_vl non-conv3d video chunks of up to 128 frames, CPU). Before, `cu_seqlens=None` hit one batched SDPA call. Now `torch_sdpa_wrapper` sees `cu_seqlens`, does `(cu_seqlens[1:] - cu_seqlens[:-1]).tolist()` (a device sync) and loops B separate SDPA calls plus a `cat`. For a 128-frame chunk that is 128 kernel launches per layer instead of one.

The "equivalent to the unpacked call" docstring holds for FA and Triton only; those synthesize the same `arange`. Suggest packing uniform batches only when the layer is compiled (`should_torch_compile_mm_encoder(vllm_config)`), or skipping the pack on SDPA.
