# [Bugfix][MLA] Size the profile-run chunked-prefill workspace from the active backend's builder

[Upstream PR](https://github.com/vllm-project/vllm/pull/57170) · state: closed · merged: False

## Original PR description

## Purpose

`MLAAttention.chunked_prefill_workspace_size` (`vllm/model_executor/layers/attention/mla_attention.py`) unconditionally called `MLACommonMetadataBuilder.determine_chunked_prefill_workspace_size()` — the **dense** MLA sizing, `min(max(8 * max_model_len, 4 * max_num_seqs * block_size), 64K)` rounded up to the block size — regardless of which backend the layer actually runs on.

That value is used only during the profile run (`forward_impl`, `attn_metadata is None` branch) to allocate a worst-case
`torch.empty((workspace_size, num_heads, qk_nope_head_dim + v_head_dim))` that simulates the `kv_b_proj` up-projection performed by `_compute_prefill_context`.

Sparse MLA backends (DeepSeek-V3.2-style DSA: `FLASHMLA_SPARSE`, `FLASH_ATTN_MLA_SPARSE`, `FLASHINFER_MLA_SPARSE` / `FLASHINFER_MLA_SPARSE_SM120`) build their metadata with `SparseMLACommonMetadataBuilder` (`vllm/model_executor/layers/attention/sparse_mla_attention.py`), which overrides `determine_chunked_prefill_workspace_size` to cap the workspace at `max_num_seqs * index_topk` rows. Their `_project_kv` can therefore never see more context rows than that cap, yet the profile run reserved the dense worst case — and the KV cache was then sized against that inflated activation peak.

The fix asks the active backend for its own builder: `self.attn_backend.get_builder_cls()`, then `getattr(builder_cls, "determine_chunked_prefill_workspace_size", MLACommonMetadataBuilder.determine_chunked_prefill_workspace_size)`.

Builders defining the classmethod today (`grep -rn determine_chunked_prefill_workspace_size vllm/`):

- `MLACommonMetadataBuilder` (dense MLA: `TRITON_MLA`, `FLASHMLA`, `FLASH_ATTN_MLA`, `CUTLASS_MLA`, `FLASHINFER_MLA`, ROCm/CPU MLA, …) — **unchanged**, same function as before.
- `SparseMLACommonMetadataBuilder` (the sparse backends above) — now actually used by the profile run.
- `XPUMLASparseMetadataBuilder` does not define it, so it keeps the dense sizing via the fallback (no behaviour change).

The change is hardware-agnostic: it is pure Python config arithmetic in the layer, with no kernel or device-specific code.

> Note: this PR was written with AI assistance (Claude Code); the change and all measurements below were reviewed and run by the submitter.

`ruff format` / `ruff check` on both changed files: clean. `mypy` reports no new findings in the changed lines (the file has pre-existing unrelated errors, unchanged at 36 before and after).

Sizing arithmetic for the measured configuration (GLM-5.3-Flash, `canada-quant/GLM-5.3-Flash-W4A16-MTP`: 64 attention heads, `qk_nope_head_dim = v_head_dim = 256`, `index_topk = 2048`, `--max-num-seqs 8`, `--max-model-len 32768`, KV block size 4352 — the model's KDA/mamba state forces that page alignment):

| | rows | profile allocation (bf16) |
|---|---|---|
| dense formula (before) | 69,632 (`8 * 32768` capped at 65,536, rounded up to 4352) | 69,632 x 64 x 512 x 2 B = **4.25 GiB** |
| sparse builder cap (after) | 16,384 (`8 * 2048`) | **1.00 GiB** |

A `torch.cuda.memory._record_memory_history` snapshot taken at the profile peak attributed **4.250 GiB** of the 4.5 GiB "peak activation" to this single allocation, at `mla_attention.py` in `forward_impl` (`unified_mla_attention_with_output` -> `forward_impl`).

End-to-end, before -> after:

| metric | before | after |
|---|---|---|
| peak activation per GPU | 4.52–4.60 GiB | 1.29–1.35 GiB |
| available KV cache (rank 0) | 9.84 GiB | 13.09 GiB (**+3.25 GiB**) |
| GPU KV cache size | 770,703 tokens | 1,102,315 tokens (**+43%**) |
| GSM8K | 0.98 | 0.98 |
| MTP acceptance | unchanged | unchanged |

Hardware tested: 4x NVIDIA CMP 170HX (GA100, sm_80, 64 GB), `--pipeline-parallel-size 4`, using an out-of-tree sm_80 sparse-attention backend whose builder subclasses `SparseMLACommonMetadataBuilder` (that backend is **not** part of this PR). The bug and the fix are in backend-agnostic layer code and apply equally to the in-tree sparse MLA backends on Hopper/Blackwell (`FLASHMLA_SPARSE`, `FLASH_ATTN_MLA_SPARSE`, `FLASHINFER_MLA_SPARSE`); a Hopper/Blackwell reproduction of the before/after KV cache numbers from a reviewer would be very welcome.

Dense MLA models are unaffected: the property resolves to exactly the same function it called before.
