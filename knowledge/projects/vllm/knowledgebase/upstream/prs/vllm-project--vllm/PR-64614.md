# [Bugfix][ROCm] Use 64-bit row offsets in the RDNA hybrid W4A16 GEMM

[Upstream PR](https://github.com/vllm-project/vllm/pull/64614) · state: closed · merged: True

## Original PR description

## Overview

`_triton_w4a16_skinny_fmt_kernel` indexed activations and outputs with int32 row offsets, which wrap once M × K or M × N passes 2^31: the store faults with `HSA_STATUS_ERROR_MEMORY_FAULT` and the process hangs, and the load returns mapped garbage, so 127 rows come back NaN. Same class as #63049, which #63054 fixed for the CDNA kernel; this is the gfx11/gfx12 sibling.

## Claims

- cast `pid_m` to int64, which widens both `offs_m * stride_am` and `offs_m * N`; `offs_m` is the only offset here that scales with M.

## Validation

```bash
pytest tests/kernels/quantization/test_rdna_hybrid_w4a16.py -k int32_offsets   # R9700, gfx1201
```

| (K, N), M = 2^31 // max(K, N) + 128 | main | this PR |
|---|---|---|
| (256, 34816), M=61,808 | `Fatal Python error: Aborted` on the store, then hangs | 2 passed, 0.023 max abs dev |
| (17408, 256), M=123,489 | 127 NaN rows, first at row 123,362 | 2 passed, 0 NaN rows over all M |

Manually tested on an R9700 (gfx1201): both parametrizations fail on main and pass with the change. No CI pool covers gfx11/gfx12, so the test is gated on `on_gfx1x()` like the file's other kernel tests, because `tests/kernels/quantization` runs on MI300 and MI355 and neither ships this kernel.

## Details

Test tolerance stays at the file's `rtol=1e-2, atol=5e-2`, since a K=17,408 bf16 dot accumulates differently at 64-wide BLOCK_K.

#### 1. 🟠 Should fix: Prefill int32-offset test OOMs on 16 GB RDNA cards: fp32 activation allocation peaks at ~17 GB
`tests/kernels/quantization/test_rdna_hybrid_w4a16.py:1243`

For the `(17408, 256)` case, `_make_prefill_case` builds `x` as fp32 `randn` (8.6 GB) times `0.25` (another 8.6 GB temporary) before the bf16 cast. That peaks at about 17 GB of device memory, so the test errors with OOM on gfx11/gfx12 cards with 16 GB or less. The `(256, 34816)` case needs only about 4.4 GB. Generating `x` directly in bf16, or skipping when `torch.cuda.mem_get_info()` reports too little free memory, would keep it runnable on smaller cards. The sibling `test_triton_w4a16_gemm_rows_past_int32_offsets` (#63054) has no such guard either; this test copies its pattern.

**Who is affected:** Developers or CI running this test on gfx11/gfx12 GPUs with 16 GB of VRAM or less; production users are unaffected.
