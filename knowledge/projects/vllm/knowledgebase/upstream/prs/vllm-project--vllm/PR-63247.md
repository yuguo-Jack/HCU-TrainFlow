# [Compile] Make the compile cache device-neutral with compile_on_one_rank

[Upstream PR](https://github.com/vllm-project/vllm/pull/63247) · state: closed · merged: True

## Original PR description



## Overview

Make the torch.compile cache device-neutral, so a cache built on one GPU can be reused on another. Since #45026 a worker's local rank no longer implies its device, so a cache built with `--device-ids 0` and reused with `--device-ids 1` crashes on startup. This enables torch 2.14's `compile_on_one_rank` mode via a new `VLLM_COMPILE_ON_ONE_RANK` (default on for torch >= 2.14 on CUDA/ROCm and XPU).

## Claims

- Fixes `CUDA driver error: invalid argument` during the first warm-up forward when a compile cache built on one device is reused on another (`--device-ids`).
- The cache is reused across device indices with no recompile.
- `VLLM_COMPILE_ON_ONE_RANK` is part of the compile cache key: caches built with the mode off are never loaded with it on, and vice versa.
- No throughput or output change (TP=1 and TP=2, greedy outputs identical).

## Validation

All runs: Qwen3-0.6B, 2x H100, torch 2.14.0, `vllm serve --max-model-len 4096 --gpu-memory-utilization 0.5`, one fresh `VLLM_CACHE_ROOT` shared by the runs of each table.

**Reproducer.** Run A builds the cache, then B and C reuse it:

| Run | Device in-process | Before this PR | With this PR |
|---|---|---|---|
| A `--device-ids 0` | cuda:0 | Up, compiles, writes the cache | Up, compiles, writes the cache |
| B `--device-ids 1` | cuda:1 | **Crash**: loads A's AOT cache, `CUDA driver error: invalid argument` | **Up**: loads A's AOT cache, no recompile |
| C `CUDA_VISIBLE_DEVICES=1` (control) | cuda:0 | Up | Up |

C runs on the same physical GPU as B and reuses the same cache, but in-process it is `cuda:0`, so the device index alone decides the failure.

| Mode off | 76 | 0 |
| Mode on | 0 | 62 |

**Cache-key isolation.** Starting with `VLLM_COMPILE_ON_ONE_RANK=0` on a cache root built with the mode on recompiles instead of loading it.

**TP=2.** Cold and warm start with the mode on and off: warm starts load both ranks' caches with no recompile, and there are no CUDA errors.

**Outputs.** Greedy completions (32 tokens, 3 prompts) are identical with the mode on and off, at TP=1 and TP=2.

**Tests.** `tests/compile/test_compile_on_one_rank.py`: the default and its gates, the flag being a compile cache factor that changes the hash, `env_override` applying it to torch, and (on CUDA) that Inductor's generated code bakes in the device index with the mode off and resolves it at run time with it on. ## Details

**Root cause.** The AOT compile cache lives under `torch_aot_compile/<hash>/rank_{rank}_{dp_rank}`, where the hash covers the vLLM config and env factors. Neither includes the device. That was safe while rank r always ran on `cuda:r`. Since #45026, `--device-ids` maps logical ranks to physical devices without narrowing `CUDA_VISIBLE_DEVICES`, so a rank can run on any device index. Inductor bakes the compile-time device in two places:

1. **The generated wrapper code:** `torch.cuda._DeviceGuard(0)`, `torch.cuda.set_device(0)`, `get_raw_stream(0)`.
2. **Each Triton kernel's load device:** statically launched kernels are loaded into the device recorded at compile time.

Reusing the cache on `cuda:1` launches kernels against `cuda:0`'s stream (`invalid argument`). In an experiment on torch 2.13, rewriting only the wrapper code still failed (`invalid resource handle`), because the kernels are loaded into `cuda:0`'s context. Both have to be device-relative.

**Fix.** torch 2.14's `torch.compiler.config.compile_on_one_rank` makes Inductor emit `torch.cuda.current_device()` in the wrapper and compile kernels with `DeviceProperties(index=None)`. That covers both places, so no Inductor patching is needed in vLLM. Torch also includes the mode in Inductor's own cache key. vLLM's AOT cache key needs it as well, which a registered vLLM env var provides through `envs.compile_factors()`. `env_override` sets torch's config from `VLLM_COMPILE_ON_ONE_RANK` in every vLLM process, so an outside `TORCH_COMPILE_ON_ONE_RANK` cannot make the compiled code disagree with the cache key.

**Relation to #38962 / #53312.** #38962 fixed the same crash by adding the device index to the cache path; it was reverted in #53304 for a CPU regression, and #53312 re-lands it. That approach stops the crash but gives each device index its own cache, so replicas on different GPUs recompile instead of sharing one. This PR keeps a single cache that works on any device index, and its default is off on CPU. The two can coexist; with this PR, device-keyed paths are no longer needed for correctness.

**Limitations.**
- On torch < 2.14 the mode does not exist, so the default stays off and the bug remains. Fixing it there would need patches to Inductor's codegen and its static Triton launcher.
- The default is off on platforms other than CUDA/ROCm and XPU, because Inductor raises for backends without `current_device_idx_expr()`.
- Existing caches recompile once after upgrading, because the cache key changes.

- kouroshHakha · comment · 2026-10-27T21:49:26Z · [source](https://github.com/vllm-project/vllm/pull/63247#issuecomment-6454474426)

@zou3519 To make compiled artifacts device-invariant. Without it, Inductor bakes the compile-time device index into the generated code (_DeviceGuard(N), get_raw_stream(N), the static launcher's load device). In a multi-replica setup where a new replica reuses another replica's compile cache for fast scale-up (e.g. via ModelExpress), a replica on a different GPU index (say cuda:1, with no CUDA_VISIBLE_DEVICES remapping) loads a cache built on cuda:0 and fails with CUDA driver error: invalid argument. With compile_on_one_rank, the generated code uses the current device instead, so the same artifacts work on any device index.

I was thinking where to put this fix. It should ideally be in torch compile, otherwise we have to patch the generated artifacts (which is a workaround I am using for torch < 2.14). So my agent found that in torch 2.14 this flag basically achieves that device invariant property that we are looking for.
