# [Bugfix][Responses] Accept assistant input items without a "type" field

[Upstream PR](https://github.com/vllm-project/vllm/pull/63324) · state: open · merged: False

## Original PR description

## What

Fixes #63310.

Multi-turn `/v1/responses` requests that replay a previous assistant turn as a
message item **without a `type` field** (with `output_text` content parts — the
shape clients such as ECA/Emacs send) were rejected with a 400 and ~239
validation errors, even though the OpenAI API accepts this exact shape.

```json
{
  "input": [
    {"role": "user", "content": "My name is Alice."},
    {"role": "assistant", "content": [{"type": "output_text", "text": "Nice to meet you, Alice."}]},
    {"role": "user", "content": "What is my name?"}
  ]
}
```

Adding `"type": "message"` to the assistant item made it work, which pointed at
the pre-validation normalizer.

## Root cause

`ResponsesRequest.input` is validated against the OpenAI SDK union
`ResponseInputOutputItem`. The `input_item_parsing` `model_validator(mode="before")`
coerces an assistant message to `ResponseOutputMessage` (which *does* allow
`output_text` parts) **only when `item.get("type") == "message"`**.

A `type`-less assistant item fell into the `else` branch and was passed through
unchanged, so pydantic validated it as `EasyInputMessageParam` — whose content
parts only allow `input_text`. Every `output_text` part (and the union attempts
around it) produced a validation error → 239 errors → HTTP 400.

## Fix

In `vllm/entrypoints/openai/responses/protocol.py`, treat an assistant message
that **omits** the `type` field the same as one with `type == "message"`:

- broaden the coercion branch to
  `(item_type == "message" or "type" not in item) and item.get("role") == "assistant"`, and
- default the missing `type` to `"message"` (alongside the existing `id` /
  `status` / `annotations` defaults) before building the `ResponseOutputMessage`.

Two scoping choices keep the change minimal (per review):
- **Omitted key only.** `item.get("type")` is `None` for both an omitted key and
  an explicit `"type": null`, so the branch uses `"type" not in item` to target
  only the reported shape. An **explicit `"type": null` keeps the base behavior
  (rejected)** — it is not treated as an omitted key.
- **String content is untouched.** A plain-string assistant item is already a
  valid `EasyInputMessageParam`, so it is not coerced.

Net: a small condition change + the `type` default + docstring; no behavior
change for any input that already validated (and none for explicit `null`).

## Tests (CPU, no model / server needed)

The failure happens at request **parsing**, so it reproduces with plain
`ResponsesRequest.model_validate(...)` on CPU.

New regression tests in `tests/entrypoints/openai/responses/test_protocol.py`:
- `test_responses_input_assistant_message_without_type_field` — the reported
  case; asserts it validates and the assistant `output_text` content is preserved.
- `test_responses_input_assistant_message_with_explicit_type_still_valid` — control.
- `test_responses_input_assistant_string_content_without_type_still_valid` —
  guards the string-content path that must stay a plain `EasyInputMessageParam`.
- `test_responses_input_assistant_explicit_null_type_still_rejected` — pins that
  an explicit `"type": null` keeps the base (rejected) behavior, so the fix is
  strictly scoped to the omitted-key case.

elif (item_type == "message" or "type" not in item) and item.get("role") == "assistant":
