# [Bugfix][KV Connector] MoRIIO READ: trim to prompt blocks before clipping SWA groups

[Upstream PR](https://github.com/vllm-project/vllm/pull/62165) · state: open · merged: False

## Original PR description



## Overview

MoRIIO READ pairs prefill and decode sliding-window blocks by clipping each block list from its end. A lookahead tail that only one leg allocated shifts the decoder's window by one block, so the decoder reads the wrong KV for the end of the prompt. This PR trims both lists to the prompt's blocks before clipping.

## Claims

- Fixes wrong outputs in MoRIIO READ P/D for sliding-window hybrid models when the two legs have different lookahead tails. On DeepSeek-V4-Pro, ~14% of prompt lengths were affected.
- Also fixes the full-attention pairing when only the prefiller has a lookahead tail.
- No change when both legs hold the same number of blocks.

## Details

**Flow.** Example: DSv4-Pro SWA cache, `block_size=64`, `sliding_window=128`, so `blocks_per_sw = cdiv(128, 64) + 1 = 3`. Prompt `N = 440` tokens fills 7 blocks. The decoder reserves `k` lookahead slots and the prefiller none; the observed failure range `(N - 1) % 64 ∈ [55, 63]` implies `k = 9`.

1. P (`request_finished`): 440 slots, 7 blocks `P0..P6`. Clip keeps `[P4, P5, P6]` and sends them as `remote_block_ids`.
2. D admission: `load_kv_async=False`, so the scheduler allocates `440 + 9` slots, 8 blocks `D0..D7`. The async-load path sets lookahead to 0 to keep block counts equal, but synchronous READ does not take it.
3. D (`update_state_after_alloc`): clip keeps `[D5, D6, D7]`. `_align_read_blocks` sees equal lengths and pairs `P4→D5, P5→D6, P6→D7`.
4. The window of the last prompt token needs `D4..D6`. It gets wrong or missing KV, so the model answers as if the end of the prompt were missing.

The failure condition with no prefill-side lookahead is `(N - 1) % block_size >= block_size - k`. `_align_read_blocks` cannot detect the shift because it runs after the clip.

**Fix.** `get_exchange_clipped_blocks` takes an optional `num_prompt_tokens`. When it is set, every transfer group is first trimmed to `cdiv(num_prompt_tokens, block_size)` blocks, using the existing `_group_block_sizes`. Both exchange points pass it: `request_finished` on the producer and `update_state_after_alloc` on the consumer, both on the non-mamba path. The list lengths then depend only on the prompt, not on either leg's lookahead.

**Safety.**
- `update_state_after_alloc` receives `kv_cache_manager.get_blocks(request_id)`. That is the full position-indexed list, including prefix-hit blocks, so the trim never drops a prompt block.
- The hybrid mamba path is unchanged. It does not clip sliding-window groups, and its prefiller drops the last prompt token.
- `_clamp_to_prompt_blocks` (WRITE save path) is not reused. Its non-mamba branch skips sliding-window groups, which are the groups this fix needs.

**Limitation.** `_group_block_sizes` and `blocks_per_sw` use the spec block size without the DCP factor. Under DCP > 1 the trim keeps too many blocks and does not fix the shift. It does not regress either.

**Duplicate check.** I searched `gh pr list --repo vllm-project/vllm --state open --search "moriio"`, `"moriio sliding window"` and `"moriio hybrid READ"`. No open PR trims before the SWA clip. Two PRs are related:
- #54301 (async READ lifecycle) would remove the decoder-side admission tail, but not a prefill-side tail.
- #60867 (multi-group hybrid READ) adds another `get_exchange_clipped_blocks` caller in `split_block_groups`. That caller can pass `num_prompt_tokens` the same way.
