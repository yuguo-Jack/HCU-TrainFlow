# [ROCm][Perf] Prequantized FP8 attention for Qwen3.8-2.4T-A95B with an FP8 KV cache

## Overview

On gfx950 with `--kv-cache-dtype fp8` and the ROCM_AITER_FA backend, Qwen3.8-2.4T-A95B now prepares Q/K/V in FP8 in one fused kernel (Q/K RMSNorm, partial RoPE, gate extraction and FP8 quantization), and the backend consumes them directly for prefill and chunked-prefill attention. Decode keeps the existing paged-attention path. There is no new flag: the path is scoped to the one validated checkpoint by its exact text config, and every other model, KV cache dtype and platform runs as before.

The kernel is `fused_qk_norm_rope_gate_fp8_quant` from [ROCm/aiter#5002](https://github.com/ROCm/aiter/pull/5002) (merged), released in AITER v0.1.25. vLLM `main` pins that release since [#61697](https://github.com/vllm-project/vllm/pull/61697).

Not a duplicate: searched open PRs for "prequantized FP8 attention ROCm", "fp8 qkv aiter fmha" and "fused qk norm rope gate fp8". [#58713](https://github.com/vllm-project/vllm/pull/58713) is stacked on this PR and replaces the chunked context loop with one paged-prefix call; [#53989](https://github.com/vllm-project/vllm/pull/53989) enables the BF16 fused QK-norm+RoPE+gate kernel on XPU.

## Claims

- 60K input / 600 output on Qwen3.8-2.4T-A95B MXFP4, TP8 MI355X: output throughput +4.2% at c1, +11.1% at c4, +9.6% at c8. <TODO: replace with the re-measurement on nightly-3f1bcfd8>
- 128K input / 1K output: +11.3% at c1, +19.4% at c4; mean TTFT −23.0% at c1 and −19.1% at c4. <TODO: same>
- Flat at 1K/1K c16 and 8K/1K c8: short prompts spend little time in prefill attention, and decode does not take the new path.

## Details

Before this PR, Qwen3.8 runs Q/K normalization, partial RoPE and gate extraction into BF16, and a chunked prefill makes two BF16 attention calls: causal attention within the chunk, then the chunk's queries over the cached K/V, which is first dequantized from the FP8 cache into a BF16 workspace. `merge_attn_states` combines the two.

With this PR, one AITER kernel does the normalization, RoPE, gate extraction and FP8 quantization, and writes FP8 Q/K/V plus their descales. They travel to the backend as a `PrequantizedQKV` bundle, a backend-neutral argument of `unified_attention` that backends without support reject. The AITER FA backend runs the causal call on the FP8 tensors, and for the context call it copies the FP8 cache into an FP8 workspace without dequantizing it. Pure decode ignores the bundle and keeps the paged-attention kernel, since decode attention is bandwidth bound on the KV cache and gains nothing from FP8 queries.

**There is no env flag to turn this on/off**. FP8 attention changes numerics, so instead of an opt-in the path is scoped to what was validated:

- **The model.** `_is_qwen38_2p4t_a95b` matches the Qwen3.8-2.4T-A95B text config exactly (hidden size, layer count, heads, KV heads, head dim, experts). Qwen3.8 loads through the Qwen3.5 classes, and Qwen3.8-27B has the same attention geometry as Qwen3.5-27B, so the architecture name cannot tell the models apart.
- **The KV cache.** Only an FP8 KV cache: a user who picked it has already accepted FP8 precision for K/V. With a BF16 cache the model keeps BF16 attention.
- **The kernel.** gfx950, ROCM_AITER_FA, head size 256, a query-to-KV head ratio of 1, 2, 4, 8 or 16, full causal attention without sinks or soft cap, a text-only model and `max_num_seqs` ≤ 256.

**Limitations and CI gaps.**

- Measured on gfx950 only. gfx942 does not take the path, because the AITER kernel targets gfx950 only.
- TP8 only; no other TP size measured.
- Not exercised: NIAH at long context, MTP / speculative decoding. No other model takes the path.
- CUDA: shared code changes are limited to the optional `PrequantizedQKV` argument of `unified_attention` and one entry in the default piecewise CUDA graph splitting ops; a graph that never calls that op splits exactly as before. `test_unified_attention_standard_path_is_unchanged` covers the path without the bundle.

Major issue AI found out after removing the gating env variable:
> The backend and the model decide separately whether the FP8 path is on.
> - Backend: the builder makes the chunked-prefill context workspace FP8 if every layer's impl is capable: gfx950, head size 256, FP8 KV cache (rocm_aiter_fa.py:477-508).
> - Model: it sends FP8 Q/K/V only if it opts in: the exact Qwen3.8-2.4T config, text-only, max_num_seqs ≤ 256 (qwen3_next.py:421-430).
> 
> The removed env flag used to keep the two in sync. Now, whenever a layer is capable but the model declines, extend_forward gathers cached K/V into the FP8 workspace and calls CK with a BF16 query and FP8 K/V. CK rejects that on the first batch with cached context (a chunked prefill or a prefix hit).
> 
> That covers:
> - the target model with the default max_num_seqs (1024 on MI355X, which includes the description's serve command);
> - other Qwen3.5/3.8/Qwen3-Next models with FP8 KV on ROCM_AITER_FA.
> 
> Suggested fix: Let the builder follow the model's decision:
> 
> ```
> # attention.py, Attention.__init__
> self.uses_prequantized_qkv = False
> # qwen3_next.py, after computing use_prequantized_qkv
> self.attn.uses_prequantized_qkv = self.use_prequantized_qkv
> # rocm_aiter_fa.py:477
> supports_prequantized_qkv &= layer.uses_prequantized_qkv
> ```
> Optional: in extend_forward, raise a clear error if the workspace is FP8 and prequantized_qkv is None.
> 
> The model is built before the builder, so the flag is always set in time, and every other model keeps the BF16 workspace. Add a builder test: capable impl plus FP8 KV, but the model hasn't opted in, so the workspace is BF16. Optionally, raise a clear error in extend_forward if the workspace is FP8 and no prequantized Q/K/V were passed.

Another issue AI spotted:

Please run tests/compile/passes/test_fusion_attn.py, and recheck after rebasing onto #42755 (conflict in rocm_aiter_fa.py)

I think also adding a long context accuracy test would be beneficial (e.g., RULER niah_single_2 at 64k and 128k, baseline vs PR)
