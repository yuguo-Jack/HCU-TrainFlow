# [ROCm][Perf] Prequantized FP8 attention for Qwen3NextAttention with an FP8 KV cache

[Upstream PR](https://github.com/vllm-project/vllm/pull/53823) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Adds a ROCm AITER FP8 attention path for gated-attention Qwen3-Next-family models on gfx950. One AITER kernel does Q/K norm, RoPE, gate extraction and FP8 quantization, and `ROCM_AITER_FA` consumes the FP8 Q/K/V directly in prefill and chunked prefill. Decode stays BF16.

**There is no opt-in flag.** `Qwen3NextAttention` takes the path whenever the layer and the backend allow it (see Design); everything else keeps the BF16 attention path.

Needs ROCm/aiter#5002, which is in AITER v0.1.25 and pinned on main.

Not a duplicate: searched open PRs for "prequantized fp8 attention", "fused qk norm rope gate fp8" and "FP8 Q/K/V aiter attention". #58713 builds on this PR (paged FP8 prefix path). #59035 quantizes Q to FP8 inside `QkNormRopeKvCacheFusionPass`, a different mechanism from quantizing Q, K and V in the gated-attention projection here.

## Claims

- Prefill-heavy workloads on four models get faster, and the gain grows with context length. At 128K input / 1K output and concurrency 4, output throughput is +62% (Qwen3.5-35B-A3B), +60% (Qwen3.6-35B-A3B), +39% (Qwen3.5-397B-A17B) and +23% (Qwen3.8-2.4T-A95B), and mean TTFT is −51%, −51%, −37% and −28%. At concurrency 1 the gains are +28%, +35%, +27% and +16%.
- At 32K and 60K input and concurrency 4: +15% to +27% on the 35B models, +9% and +17% on the 397B. No measurable change on the 2.4T, where these cells vary by up to 20% between runs in both arms. At 60K input and concurrency 8: +22% on the 397B, +13% on the 2.4T (per pass +26%, +13%, 0%).
- At 8K input: +2% to +4% on the 35B and 397B models, flat on the 2.4T.
- Single-stream decode (128K/1K, concurrency 1) is unchanged within about ±5% TPOT, as expected since decode stays BF16.
- GSM8K is unchanged on all four models: paired per question, exact McNemar p between 0.21 and 1.0 over six comparisons.

## Details

**What runs.** Before: Q/K norm, RoPE and gate extraction produce BF16, and chunked prefill makes two attention calls, a causal one within the chunk and a non-causal one over cached K/V gathered into a BF16 workspace. After: one fused AITER kernel emits FP8 Q/K/V with per-sequence, per-KV-head descales. The causal call consumes them directly. The cached K/V is gathered into an FP8 workspace. `merge_attn_states` combines the two results. Pure decode keeps the BF16 query and the paged-attention path.

**Design.**

- **Capability gating.** `Qwen3NextAttention` takes the path when all of these hold: gated attention, NeoX RoPE in BF16, ROCm, text-only (`--language-model-only` for multimodal checkpoints), `max_num_seqs <= 256`, and the backend reports `supports_prequantized_qkv_input`. `AiterFlashAttentionImpl` reports it for gfx950, head size 256, GQA ratio in (1, 2, 4, 8, 16), no soft cap, no sliding window, no sinks, FP8 KV cache.
- **Builder.** The FP8 context workspace is enabled only when every layer both supports and receives prequantized Q/K/V, the KV cache is FP8 and the shuffle layout is off. `extend_forward` raises if an FP8 workspace arrives without prequantized Q/K/V, so a model that is not fed cannot silently get unscaled K/V.
- **No off switch.** Models that satisfy the conditions above change behaviour on this backend. A dedicated opt-out can be added if reviewers want one; `attention_config.use_prefill_query_quantization` was not reused because it is read only by MLA backends today and this path also quantizes K and V.
- **Input contract.** `Attention` and `unified_attention_with_output` take six optional prequantized tensors, default `None`; a backend opts in through `supports_prequantized_qkv_input`. Other backends and models are unaffected. `Qwen3NextAttention._project_qkv_gate` keeps its four-value return because Qwen4Exp's attention subclasses it; the FP8 path is `_project_prequantized_qkv_gate`.
- **Compile.** `vllm::fused_qk_norm_rope_gate_fp8_quant` is added to `splitting_ops` on every platform. It reads per-step attention metadata, so it runs outside piecewise CUDA graphs. It appears in a graph only where the FP8 path is active.
- **AITER.** Calls go through `rocm_aiter_ops` with no import probe. With an AITER that lacks the kernel, the first prefill raises.

**Limitations and CI gaps.**

- gfx950, head size 256, full causal attention, no sinks or soft cap, FP8 KV cache. The BF16 KV cache is not supported.
- Measured on Qwen3.5-35B-A3B, Qwen3.6-35B-A3B and Qwen3.5-397B-A17B MXFP4 (TP1 and TP2), and Qwen3.8-2.4T-A95B MXFP4 (TP8). Not covered: Qwen3-Next-80B, NIAH at 64k and 128k, MTP/spec decode, gfx942, models with a GQA ratio outside the supported set (for example the Qwen3.6/3.8 27B dense models, ratio 6, keep the BF16 path).
- CI: the MI300 mirror runs the unit tests, which mock the AITER kernels. The gfx950 kernels are exercised only by the end-to-end runs above.

Major issue AI found out after removing the gating env variable:
> The backend and the model decide separately whether the FP8 path is on.
> - Backend: the builder makes the chunked-prefill context workspace FP8 if every layer's impl is capable: gfx950, head size 256, FP8 KV cache (rocm_aiter_fa.py:477-508).
> - Model: it sends FP8 Q/K/V only if it opts in: the exact Qwen3.8-2.4T config, text-only, max_num_seqs ≤ 256 (qwen3_next.py:421-430).
> 
> The removed env flag used to keep the two in sync. Now, whenever a layer is capable but the model declines, extend_forward gathers cached K/V into the FP8 workspace and calls CK with a BF16 query and FP8 K/V. CK rejects that on the first batch with cached context (a chunked prefill or a prefix hit).
> 
> That covers:
> - the target model with the default max_num_seqs (1024 on MI355X, which includes the description's serve command);
> - other Qwen3.5/3.8/Qwen3-Next models with FP8 KV on ROCM_AITER_FA.
> 
> Suggested fix: Let the builder follow the model's decision:
> 
> ```
> # attention.py, Attention.__init__
> self.uses_prequantized_qkv = False
> # qwen3_next.py, after computing use_prequantized_qkv
> self.attn.uses_prequantized_qkv = self.use_prequantized_qkv

> supports_prequantized_qkv &= layer.uses_prequantized_qkv

> Optional: in extend_forward, raise a clear error if the workspace is FP8 and prequantized_qkv is None.

@nholmber @mjkvaak-amd this per-sequence descale is not applied by AITER. With AITER v0.1.26 (the version pinned on main), the FP8 hd256 varlen kernel (`fmha_v3_varlen_fwd` → `fwd_hd256_fp8_causal_group`) reads only `descale[0, 0]`. The `(batch, num_kv_heads)` shape passes AITER's `is_fmha_v3_fp8()` check, but every sequence after the first and every KV head after the first gets scaled with the first entry.

Checked on MI355X (gfx950) with FP8 Q/K/V quantized per (sequence, KV head), comparing against BF16 attention on the same FP8 values dequantized with their own descales:

| case | per-(seq, KV head) descales | one global descale |
|---|---|---|
| 4 q / 1 kv, seqs (300, 129, 2, 1000) | 79% rel. error | 1.0% |
| 32 q / 2 kv, one seq of 2048 | 44% | 0.9% |
| 16 q / 2 kv, seqs (500, 700) | 82% | 1.0% |

Setting every descale entry except `[0, 0]` to 50x the right value gives bit-identical output, so the other entries are never read.

So any prefill batch with more than one sequence, or more than one KV head per rank (35B and 397B at TP1/TP2 both have 2), runs with wrong scales. With the producer's real output the error is 10-20% (vs 1-2% expected) on mixed batches.
