# [KV Offload] SimpleCPUOffload: opt-in cap on GPU blocks pinned by pending stores

[Upstream PR](https://github.com/vllm-project/vllm/pull/64394) · state: open · merged: False

## Original PR description

## Purpose

An eager SimpleCPUOffload store pins its GPU blocks until every worker has copied them, and nothing bounds how many stores are pending. When the offload tier writes more slowly than KV is computed, the backlog grows without limit and pins GPU KV, which starves scheduling. A disk backend on saturated storage is one example.

We hit this on a GB300 TP4 deployment with the disk backend on a saturated RAID5 array:
- Pending stores averaged 27.7K and peaked at 35.8K of 37,071 GPU blocks per worker. That is 75% of GPU KV on average, and up to 97%.
- GPU KV usage reached 0.99 and the router shed requests.
- With `max_pending_store_blocks: 4096`, the store backlog no longer built up.

This PR adds `kv_connector_extra_config.max_pending_store_blocks`, an integer ≥ 0. The default, `0`, means no cap and keeps today's behavior. The cap limits the blocks in stores that are queued, in flight or awaiting release, which is the quantity the existing `vllm:simple_kv_offload_pending_store_blocks` gauge reports.

- **Eager mode:** candidates past the cap are skipped, not deferred.
  - The per-group cursor moves past them without a CPU block or GPU pin, so they stay out of the offload tier unless a later request holding the same blocks stores them.
  - This applies to positional stores, boundary-state hand-offs and the finish-time flush.
- **Lazy mode:** the free-queue walk stops at the cap as if the CPU pool were full. The cursor stays, so the blocks are retried on a later step.
- **Metrics:**
  - a new counter, `vllm:simple_kv_offload_capped_store_blocks_total`, counts eager blocks skipped by the cap;
  - boundary hand-offs dropped by the cap get a new `dropped_store_cap` outcome on `save_outcomes_total`.
- **Docs:** a usage section in `docs/features/kv_offloading_usage.md` and one caveat line in `docs/usage/metrics.md`. The metric table there is generated from `metrics.py`.

The core change is about 75 lines in `vllm/v1/simple_kv_offload/manager.py`, all inside the connector. No scheduler or KV cache manager code changes.

New tests in `tests/v1/simple_kv_offload/test_scheduler.py`:

- `test_eager_store_cap_skips_blocks_past_the_cap`: with 2 requests × 2 blocks and a cap of 3, three blocks are stored.
  - The fourth gets no CPU block and no GPU pin, and its cursor moves on.
  - The cap spans steps.
  - Store completion frees the budget, and the skipped block is not retried.
- `test_finished_eager_store_respects_store_cap`: the finish-time flush stops at the cap.
- `test_lazy_store_cap_defers_to_a_later_step`: lazy mode retries the remaining block after completion.
- `test_boundary_handoff_dropped_at_store_cap`: a hand-off past the cap is counted as `dropped_store_cap`.

`test_simple_cpu_offload_metrics.py` now includes the new counter in the registered-metric set.
