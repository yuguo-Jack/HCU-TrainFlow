# [Bugfix][Frontend] Keep streamed completion text_offset in step with tokens

[Upstream PR](https://github.com/vllm-project/vllm/pull/60668) · state: closed · merged: True

## Original PR description



## Overview

Streamed `/v1/completions` logprobs return wrong `text_offset` values when `stop` strings are set. Non-streaming is correct.

## Claims

- Streamed `text_offset` now matches the non-streaming response for the same output.

## Validation

- New `tests/entrypoints/openai/completion/test_completion_text_offset.py`: fails on main (`[0, 2, 5] != [0, 3, 6]`), passes with the fix.
- Real `OutputProcessor` and detokenizer with the gpt2 tokenizer, `stop=["\n\n", "STOPNOW"]`, fed into the stream generator: on main 15 tokens sit at the wrong offset; with the fix none do, and offsets equal the non-streaming ones.
- `pytest tests/entrypoints/openai/completion/` (server-free tests) and `pre-commit run` on the changed files pass.

## Details

With stop strings, the detokenizer holds back up to `len(longest stop) - 1` characters until it can rule out a match, but logprobs for those tokens go out immediately. The stream advanced its offset by the emitted `delta_text`, so every later offset fell short. It now advances by the reported token lengths, as the non-streaming path does (keeps the #47815 echo fix). Not a duplicate: #47815 fixed the echo case only; no open PR touches this. The Rust frontend was not checked.
