# [Bugfix][ROCm][Kimi-K3] Stage fused KDA decode weights after loading

[Upstream PR](https://github.com/vllm-project/vllm/pull/61207) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

The ROCm Kimi-K3 fused KDA decode kernel read uninitialized memory as its conv1d and gated-norm weights whenever the model was loaded without the weight loaders, e.g. with `--load-format dummy`. The copies are now built from the final parameters after loading, for every loader.

## Claims

- `KimiK3DeltaAttention.process_weights_after_loading` stages `decode_conv1d_weight` and `decode_norm_weight` from `conv1d.weight` and `o_norm.weight`; the two side-effect weight loaders in `kda_decode.py` are removed.
- Fixes the intermittent NaN logprobs (HTTP 400 `Out of range float values are not JSON compliant: nan`) in `tests/models/kimi_k3/test_prefix_cache.py` on MI355.
- `test_amd_kda_decode.py` gains a regression test that fails without the fix and passes with it.

## Validation

MI355 (gfx950), `VLLM_ROCM_USE_AITER=1`.

Correctness, `test_prefix_cache.py::test_turns_reuse_prefix_and_match_recompute[offload-partial]`, single GPU:

| Check | Before | After |
|---|---|---|
| Runs with NaN logprobs (HTTP 400 on turn 0) | 5 of 21 | 0 of 20 |
| `decode_conv1d_weight` / `decode_norm_weight` after dummy load | all zeros, or uninitialized values with NaN/Inf | equal to the parameters |
| `test_decode_weights_staged_after_loading` | failed: 18432 / 18432 elements mismatched (NaN) | passed |

Performance, `riverclouds/Kimi-K3-8L-dummy` with `--load-format dummy` (the only available checkpoint that runs this layer), TP1, `vllm bench serve` random 4096 in / 256 out, 200 prompts, concurrency 16. 5 runs per column, interleaved, fresh server each run; mean ± sd:

| Metric | Before | After |
|---|---|---|
| Request throughput (req/s) | 7.687 ± 0.025 | 7.672 ± 0.009 |
| Output throughput (tok/s) | 1967.8 ± 6.5 | 1964.1 ± 2.3 |
| Mean TTFT (ms) | 634.4 ± 6.5 | 633.5 ± 2.5 |
| Mean TPOT (ms) | 5.434 ± 0.004 | 5.454 ± 0.017 |

The decode kernel and its launches are unchanged; only the weight values differ under dummy load (zeros before, the dummy parameters after), and the kernel alone times the same with zero and random weights. `pytest -v -s models/kimi_k3 --ignore=models/kimi_k3/test_prefix_cache.py` passes (311 passed, 71 skipped), and `test_prefix_cache.py -k 'plain or offload'` passes 3/3. No real-weight Kimi-K3 checkpoint was available for an accuracy run; with real weights the buffers receive the same values the weight loaders wrote before.

## Details

The fused decode from #50654 reads `[3, width, channel]` fp32 copies of the q/k/v conv1d weights and an fp32 copy of the gated-norm weight. They are registered as non-persistent `torch.empty` buffers and were only written inside the conv1d and o_norm weight loaders. `DummyModelLoader` never calls weight loaders and skips non-persistent buffers, so with dummy weights the fused decode ran on whatever the allocator returned: zeros in most runs, sometimes leftover data containing NaN or Inf. The first NaN appeared in the warmup decode step, poisoned the recurrent state, and every later decode step produced NaN logits; the prefill path reads the real parameters, so the first token was always finite. Even when the memory was zero, the fused decode computed with zero conv and norm weights while prefill used the dummy parameters.

The layer now defines `process_weights_after_loading`, which the loader's post-load pass runs for attention layers after quantization and linear post-processing, so the parameters are final. That covers the default and dummy loaders and layerwise reload (the buffer storage is reused, so CUDA-graph captures stay valid), and it returns early when weights arrive already processed (weight-cache IPC). The layout and dtype from #50654 are unchanged.

The NVIDIA `KimiK3DeltaAttention` (`vllm/models/kimi_k3/nvidia/kda.py`) stages its decode buffers the same way and has the same latent issue with dummy weights; it is left for a follow-up because it could not be validated here. No open PR fixes this; #59245 reads these buffers for speculative decode and will need a rebase against this change.
