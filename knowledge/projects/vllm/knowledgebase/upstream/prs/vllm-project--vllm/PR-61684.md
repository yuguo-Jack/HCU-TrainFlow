# [CI] Fix /ci run reporting a failed merge on fork PRs

[Upstream PR](https://github.com/vllm-project/vllm/pull/61684) · state: closed · merged: True

## Original PR description



## Overview

Fix a race in the `/ci run` auto-merge from #61592: on fork PRs the bot merged `main` successfully but then reported "could not merge (API returned 404: Not Found)" and started no CI.

## Claims

- `/ci run` no longer reports a failed merge (and skips CI) when the merge into a fork branch succeeded.

## Validation

```bash
cd .github/workflows/scripts
uv run --no-project --python 3.12 python -m unittest test_run_ci_command
# Ran 60 tests ... OK
```

New regression test `test_run_waits_for_fork_merge_commit_to_reach_base_repo` (first post-merge compare returns 404, next succeeds) fails on current `main` (no build created) and passes with this change. pre-commit passes.

## Details

**Seen on #61556:** `/ci run` at 17:46:35; the bot's merge commit `8bc708e` landed on `jinzhen-lin/vllm` at 17:46:57; the bot replied ❌ "...could not merge upstream `main` into this branch (API returned 404: Not Found)" at 17:47:02. A second `/ci run` started build #94876 on the same commit.

**Root cause:** after `update-branch`, the script polls the PR until its head SHA changes and then calls `compare/main...<new head>` on `vllm-project/vllm` to confirm the branch is fresh. For fork PRs the PR's head SHA updates before the new commit is reachable from the base repository (`refs/pull/N/head` syncs a few seconds later), so that compare returns 404, and every `ApiError` was treated as a failed merge.

**Fix:** treat a 404 from the post-merge compare as "not visible yet" and keep polling within the existing ~2 minute window. Other errors still fail. Waiting until the compare succeeds also makes sure the commit is reachable from the base repo before Buildkite checks it out.
