File: `vllm/entrypoints/launchers/api_server/rust_frontend.py` · line 80

🔴 Rust-frontend deployments lose the open-file limit raise, so the Rust server and engines keep the default soft limit (often 1024). Many concurrent connections can then fail with EMFILE. The base path got this from `setup_server`. The new path binds through `setup_listen_address_from_args` and skips `setup_server`'s other steps too: `set_ulimit()`, `init_parser_plugin`, `validate_api_server_args` and `log_version_and_model`. Fix: run the same pre-bind steps before spawning the engines and the Rust process (for example, factor them out of `setup_server` and call them here), so both launch paths stay identical.

<details>
<summary>Why this was flagged</summary>

`vllm serve` with VLLM_USE_RUST_FRONTEND set now dispatches to `run_rust_frontend` (vllm/entrypoints/cli/serve.py:152). On the base branch it went to `run_multi_api_server`, which called `setup_server` (vllm/entrypoints/launchers/launcher.py:342-360). That function calls `set_ulimit()`, which raises RLIMIT_NOFILE to 65535. A repo-wide grep shows launcher.py:360 is the only caller of `set_ulimit`. The new `_run_rust_frontend` calls `setup_listen_address_from_args` directly (rust_frontend.py:43), so the limit is never raised. The engine processes and the Rust frontend inherit the default soft limit (often 1024) and can fail under high concurrency with `Too many open files`. The same bypass drops tool/reasoning parser plugin import (`init_parser_plugin`). It also drops `validate_api_server_args`, so an invalid `--tool-call-parser` or reasoning parser is no longer rejected at startup, and the version/model and non-default-args log lines are gone.

**Verification:** On the base, the Rust-frontend path called `setup_server` at base serve.py:298, which runs `set_ulimit()` (launcher.py:360). After this change, serve.py:152 dispatches to `run_rust_frontend`, and `_run_rust_frontend` binds only through `setup_listen_address_from_args` (rust_frontend.py:43). So the Rust server now runs with the default soft limit, and many concurrent connections can fail with EMFILE.

</details>

File: `vllm/entrypoints/launchers/api_server/rust_frontend.py` · line 204

🔴 With `VLLM_PORT` set and DP>1, the Rust frontend can now give the DP master the HTTP `--port`, so engine startup fails with EADDRINUSE. The base bound the HTTP socket before `create_engine_config`. This change builds the config at rust_frontend.py:169 and only binds later in `_run_rust_frontend`. Fix: bind the HTTP and gRPC listen sockets before `create_engine_config`, as the base and the #8204 comment in listen.py require, then pass the sockets into `_run_rust_frontend`.

<details>
<summary>Why this was flagged</summary>

Condition: data parallel >1 without elastic EP, plus `VLLM_PORT` near `--port` (for example VLLM_PORT=8000 and --port 8002). `create_engine_config` runs at rust_frontend.py:169 and calls `get_open_ports_list(5)` (vllm/config/parallel.py:1013). That scans upward from VLLM_PORT, probing each port with a throwaway bind. The HTTP port is not bound yet, so it counts as free and can become `data_parallel_master_port`. The HTTP socket is then bound at rust_frontend.py:42, and the DP process-group init later fails on that port. The base ran `setup_server` (which binds the socket) before `create_engine_config` in `run_multi_api_server`. That ordering kept the port reserved, which is what the 'Bind before the engine starts ... #8204' comment in listen.py:45-46 is for. Without VLLM_PORT the race is narrower but still possible with ephemeral --port values.

**Verification:** In the new `run_rust_frontend`, `create_engine_config` runs at rust_frontend.py:167, outside the ExitStack. Because the HTTP/gRPC port is not bound yet, it counts as free and can be put in the DP master port list. The HTTP socket is then bound and listening at line 42. When the engine processes start the DP process group on that port, they get EADDRINUSE and startup fails.

</details>

File: `vllm/entrypoints/launchers/utils/listen.py` · line None

🔴 Servers started with `--uds` no longer raise the open-file limit, so busy Unix-socket deployments can hit EMFILE where the base did not. The UDS branch returns at listen.py:66, before `set_ulimit()` at listen.py:108. Base `setup_server` called `set_ulimit()` for both UDS and TCP. Fix: call `set_ulimit()` on every successful bind, UDS and TCP, for example by moving it ahead of the `if uds:` return.

<details>
<summary>Why this was flagged</summary>

An operator runs `vllm serve --uds /path.sock`, either the single API server or multi-API-server/Rust frontend through `setup_server`. `setup_listen_address` binds the Unix socket and returns `f"unix:{uds}", sock` at listen.py:66. It never reaches `set_ulimit()` at listen.py:108, so RLIMIT_NOFILE stays at the default soft limit (often 1024). The base `setup_server` (old launcher.py) called `set_ulimit()` unconditionally after binding either socket type. The comment says it exists to keep uvicorn from dropping requests under heavy concurrency. Under load, UDS deployments can now fail with `Too many open files`. The earlier resolved finding was about the Rust launcher skipping `setup_server` entirely. This one is the UDS branch inside the new helper and needs a different fix.

**Verification:** In the new `setup_listen_address` (vllm/entrypoints/launchers/utils/listen.py), the UDS branch binds the socket and returns at line 66 (`return f"unix:{uds}", sock`). The only call to `set_ulimit()` is later, at line 109, on the TCP path, so the UDS path never reaches it. In the base, `setup_server` in launcher.py called `set_ulimit()` unconditionally after binding either socket type.

</details>

🟡 (optional) Non-root developers and CI runners where unprivileged users can bind port 80 get a failing `test_real_kernel_denial` ("DID NOT RAISE"). It also leaks the bound socket. The test is skipped only when `os.geteuid() == 0`. Two common setups still let a non-root bind to 127.0.0.1:80: Docker containers, where `net.ipv4.ip_unprivileged_port_start` is 0 by default, and macOS Mojave and later. Fix: skip unless a real probe bind to a privileged port fails with EACCES, rather than keying on euid. Alternatively, drop the real-kernel case, since the mocked `test_error_message_points_at_privileges` already covers the message.

<details>
<summary>Why this was flagged</summary>

The trigger is running `pytest tests/entrypoints/launchers/utils/test_listen.py` as a non-root user where binding below 1024 is allowed. Examples are a Docker 20.10+ container with its own network namespace (it sets `net.ipv4.ip_unprivileged_port_start=0`), rootless podman, or macOS 10.14 and later. The skipif at test_listen.py:408-411 only checks `os.geteuid() == 0`. So the test runs and `setup_listen_address(host="127.0.0.1", port=80, reuse_port=False)` at line 414 binds successfully. `pytest.raises(OSError, match="Permission denied binding")` then fails with DID NOT RAISE. The returned socket is never closed, so later runs on that host see port 80 held. If something already listens on port 80, the bind raises the EADDRINUSE-wrapped "Port 80 is already in use" message, and the match fails that way too. The PR lists this file as its validation, so the result depends on the environment, not on the code under test. The base branch had no such test.

**Verification:** Lines 408-411 gate the test only on `os.geteuid() == 0`. Line 415 then calls `setup_listen_address(host="127.0.0.1", port=80, reuse_port=False)`. When the bind succeeds, no OSError is raised, so the EACCES branch at listen.py:93-98 is never reached. The function returns `(listen_address, sock)` at listen.py:124, and `pytest.raises` fails with "DID NOT RAISE".

</details>
