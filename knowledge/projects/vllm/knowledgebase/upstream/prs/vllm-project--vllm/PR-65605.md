# [Frontend] Add generative box answers for multimodal models on /v1/systemone

[Upstream PR](https://github.com/vllm-project/vllm/pull/65605) · state: open · merged: False

## Original PR description

## Overview

Add generated bounding-box answers to `/v1/systemone` for text-described targets in images. The implementation reuses the served multimodal model, its chat renderer, and the existing generation engine to return normalized box coordinates.

Related: [#62247](https://github.com/vllm-project/vllm/issues/62247), [#62248](https://github.com/vllm-project/vllm/pull/62248). This implementation uses constrained coordinate generation; #62248 reads spatial answers from GUI-Actor's trained pointer head.

## Claims

- Handle `box` questions using the image and target description supplied in the request. The target comes from `instructions`, and the handler obtains the served model name from the running server configuration.
- Render the image and localization instruction through the served model's multimodal chat path, preserving the image input passed to the engine.
- Generate `bbox_2d: [x_min, y_min, x_max, y_max]` under a JSON Schema constraint, then validate and convert coordinates to normalized `left`, `top`, `right`, and `bottom` edges.
- Reject malformed, truncated, out-of-range, reversed, and degenerate coordinate outputs.
- Support one image with up to four Box questions, processed serially, and requests that combine Box with `choice`, `noul`, and `score` questions.
- Return `confidence: null` for generated boxes. Separate `noul` questions provide target-existence judgments.

## Details

### Generation path

The handler separates Box questions from the existing typed decisions. For each Box question, it combines the supplied image with a localization instruction describing the target, coordinate range, and output field order. Additional business state is preserved in the prompt.

The served model's chat renderer builds the multimodal engine input. The handler calls the existing engine client directly with greedy decoding, structured-output constraints, and a default 96-token output budget.

### Coordinate conversion

The internal schema requires exactly four integers in the range 0–1000. The response parser verifies `x_min < x_max` and `y_min < y_max`, then divides the edges by 1000 to produce the public coordinates:

```json
{
  "type": "box",
  "box": {
    "left": 0.1,
    "top": 0.2,
    "right": 0.6,
    "bottom": 0.8
  },
  "confidence": null
}
```

These coordinates are an illustrative conversion example. The real-image and document evaluations above measure the generated boxes against labeled locations.

### Typed-decision integration

Existing `choice`, `noul`, and `score` questions continue through their existing read path. Mixed requests merge the answers by question ID and aggregate token usage across the Box generations and ordinary reads. Client disconnects trigger an abort attempt for unfinished Box generation.

The handler obtains the model identity through the existing serving-model configuration and reuses its renderer and engine. Model paths, served aliases, devices, and ports remain standard server configuration.
