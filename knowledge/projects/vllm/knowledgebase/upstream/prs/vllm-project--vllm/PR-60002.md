# [Feature][Rust Frontend] Return token offsets from render endpoints

[Upstream PR](https://github.com/vllm-project/vllm/pull/60002) · state: open · merged: False

## Original PR description

## Overview

Support `return_token_offsets` on the Rust frontend's `/v1/chat/completions/render` and `/v1/completions/render`, which return per-token character spans of the prompt like the Python render endpoints (#44280). Taking over this PR from @ryouol: the original commit is kept with its authorship, two follow-up commits rework where the flag lives and tidy the render types, and the branch is rebased onto current `main`. The original description is kept below.

## Claims

- With `return_token_offsets: true`, each render result carries `token_offsets`: the Unicode character span `(start, end)` of every prompt token, aligned with `token_ids` (after truncation), referring to the completion prompt or the templated chat prompt. Special tokens without source text get `(0, 0)`.
- Token IDs never change: on the default fastokens backend, offsets come from a lazily loaded Hugging Face tokenizer and are returned only when its IDs equal fastokens' IDs; otherwise `token_offsets` is omitted.
- Requests that do not opt in tokenize once, as before; `token_offsets` is omitted when not requested and for pre-tokenized or multimodal prompts. The rendered result is still accepted by `/inference/v1/generate` unchanged.

- `offsets_match_hf_source_characters_and_preserve_token_ids` checks spans over multi-byte, combining and special-token text on both the HF and fastokens backends, with and without special tokens.
- `fastokens_offsets_ignore_hf_settings_but_reject_changed_tokenization` checks that the companion tokenizer ignores `tokenizer.json` padding and that offsets are dropped when its IDs disagree with fastokens.
- The render route tests check `token_offsets` on chat and completions, its absence by default, and offsets after truncation.

## Details

Changes on top of the original commit:

- **The flag lives on the request.** `return_token_offsets` sits on `ChatRequest`/`TextRequest` next to `add_special_tokens`, instead of on the `TextRequestProcessor` config, so render no longer clones the processor per request. The companion tokenizer loads on the first opted-in encode; the explicit warm-up hook is gone.
- **Prompt preparation normalizes the request in place.** It tokenizes and truncates the prompt, records the offsets and clears the truncation, so preparing the same request twice is a no-op and offsets need no separate carry-through.
- **Render-only wrappers.** `RenderRequest<T>` adds `return_token_offsets` to the flattened OpenAI request and `RenderResponse` adds `token_offsets` to the flattened `GenerateRequest`, so neither the OpenAI DTOs nor `/generate`'s input carry render-only fields. The renderer docs and README additions were dropped.

Cost: an opted-in request on the fastokens backend keeps a second tokenizer in memory (about 120 MiB for Qwen3) and encodes the prompt twice; the original measurements are in the collapsed description below. The earlier concern that the HF backend applied `tokenizer.json` truncation and padding is gone since #63707 clears both for every backend.

## Overview

Support `return_token_offsets` on Rust completion and chat render endpoints, covering the item in #44280. Responses include per-token character spans from the supplied completion prompt or templated chat prompt.

Fastokens has no offset API. Keep its token IDs and return spans from a lazily cached HF tokenizer only when the complete ID sequences match. Default requests still encode once; opting in retains another tokenizer and encodes twice.

## Claims

- Return Unicode character spans aligned with token IDs, including after truncation. Chat spans refer to the templated prompt.
- Preserve token IDs; return `null` when offsets are not requested or unavailable.

## Details

With Qwen/Qwen3-0.6B, this request to `/v1/completions/render`:

```json
{"model":"Qwen/Qwen3-0.6B","prompt":"café 🙂","max_tokens":8,"add_special_tokens":false,"return_token_offsets":true}
```

returns these fields in its first result:

```json
{"token_ids":[924,58858,27484],"token_offsets":[[0,2],[2,4],[4,6]]}
```

Companion initialization runs on a blocking worker; encoding remains synchronous. Long opted-in requests can delay other requests on constrained workers.

<summary>Local performance diagnostic</summary>

A single two-worker debug run used 16,384-token Qwen prompts. Warm offset requests took 54–55 ms versus 7–9 ms without offsets; first-use initialization and encoding took about 1.04 s. Observed RSS rose about 120 MiB, including allocator retention and caches. A health request overlapping four long offset requests took 98 ms. All 31 reference checks passed.

These measurements describe opt-in costs; they are not a production throughput benchmark.
