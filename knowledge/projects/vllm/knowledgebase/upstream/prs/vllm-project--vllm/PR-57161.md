# [GLM-5.3-Flash] Rework kpool compress and dual-stream indexer scheduling

[Upstream PR](https://github.com/vllm-project/vllm/pull/57161) · state: open · merged: False

## Original PR description


## Purpose

Supplements vLLM's `Glm5Next` sparse-MLA kpool indexer with the kpool optimizations

What changes in vLLM:

- `vllm/models/glm5next/{nvidia,amd}/ops/kpool_compress.py`: `_kpool_softmax_rotate_write_cache_kernel` switches from a two-pass to an **online softmax** (each pool's gate scores are read once instead of twice) and takes a (row stride, slot stride, row offset) triple so one kernel serves both the pooled `[n_pools, kpool, D]` layout (`row_offset = 0`) and the **flat token layout** (`row_offset = kpool - 1`: row `i` pools tokens `i - kpool + 1 .. i`, SGLang's "assemble" kernel shape). Rows whose slot is negative, or too early in the batch to own a full pool, return before any load — replacing the `write_mask` mechanism. The prefill and decode kernels share one `_hadamard_quantize_fp8` helper; the decode/verify kernel also uses the online softmax (matching SGLang's verify-side kernel).
- `vllm/models/glm5next/{nvidia,amd}/sparse_indexer.py`: the prefill insert becomes a single launch of the new `kpool_compress_tokens_and_write_cache` on the prefill slice (was: `arange`/`clamp`/`>=`/`&`/index tensors + `k[idx]`/`gate_score[idx]` gathers + int64 conversion = 12 launches per indexer layer per prefill step). On **eager pure-prefill batches** the compress + tail-seed writes now run on the global aux stream, overlapping the current stream's topk-buffer fill and gather/logits preparation, joined before the first KV gather (SGLang's `_can_overlap_prefill`). The overlap is gated off under CUDA graph capture and breakable CUDA graphs.
- `vllm/compilation/breakable_cudagraph.py`: new `is_in_breakable_cuda_graph()` (true during breakable capture or replay) so cross-stream code can stay single-streamed under breakable graphs — the vLLM counterpart of SGLang's guard with the same rationale (the BCG eager break must finish its indexer work on one stream).
- `vllm/models/glm5next/common/attention.py` (`Indexer.forward`): the head gate is `torch.mm(hidden, w.t(), out_dtype=torch.float32)` on the bf16 operands on CUDA (fp32 accumulation and output, no `hidden.float()` copy, no cached fp32 weight; the fp32-upcast fallback is kept for other platforms). Under CUDA graph capture the K path (wk GEMM, k_norm, compress-gate GEMM) runs on the aux stream while the current stream projects, Hadamard-rotates and quantizes Q and computes the head gate — the two streams join before the indexer op (SGLang's "rebalance dual-stream indexer preparation"). Eager batches stay sequential (the fork/join would cost host time there).

## Duplicate-work check

`kpool`, `GLM-5.3-Flash indexer` and `glm5next` (2026-09-15) shows no PR touching the compress kernels, the prefill insert path, the head-gate GEMM or the indexer's stream scheduling. Related but different open PRs: #55358 moved `sparse_attn_indexer_kpool.py` into the model folder (a refactor this PR is rebased on top of), #54951 shards long-context indexer prefill rows across TP, #56607 / #56059 are ROCm fixes to the Q quant and the tail-seed kernel, #55270 fixes the paged-MQA varlen launch mode.

## Perf Changes

Kernel-level microbenchmarks (H100, GLM-5.3-Flash shapes: kpool 4, head_dim 128, 32 indexer heads, page 64):

- Prefill compress-write path per indexer layer: 12 launches -> 1. Wall time 154-216 us -> 32-36 us at n = 256 / 2048 / 8192 tokens (-79% .. -84%); summed GPU kernel time 29.0 -> 4.4 us at n = 2048 and 67.9 -> 6.7 us at n = 8192. 
- Online softmax was validated across 44 numerical and boundary cases (pool sizes 4/16). The maximum FP32 difference from the previous two-pass algorithm was 4.77e-7, and the new flat, pooled-prefill, and decode writers produced byte-identical caches. Bitwise equivalence with the previous algorithm is not guaranteed near BF16 rounding boundaries: constructed midpoint cases showed 0.22–0.32% relative L2 differences after dequantization, while both algorithms had approximately 3.16% total quantization error against the ideal reference, with no material additional error observed in these cases.
- `Indexer.forward` GEMM/quant sequence, CUDA-graph replay time: T = 48 tokens 39.7 -> 34.3 us (head gate) -> 22.7 us (head gate + dual stream), -43%; T = 288 (48 sequences x MTP 6) 50.8 -> 30.8 us, -39%; T = 1024: 94.4 -> 54.3 us, -42%; T = 4096 (head gate only; the stream overlap is off above 1024 tokens): 255.4 -> 172.7 us, -32%. Head-gate weights differ by at most 1.3e-9 (fp32 summation order).
- Decode tail-update kernel: unchanged time (launch-bound, ~36.5 us at B = 48, next_n 1 and 6) and byte-identical output.

End-to-end (`vllm bench serve`, GLM-5.3-Flash, `--tensor-parallel-size 8 --enable-expert-parallel --max-num-seqs 48 --max-model-len 131072 --speculative-config '{"method":"mtp","num_speculative_tokens":5}'`, breakable CUDA graphs; client `--dataset-name random --ignore-eos --seed 0`; main = 206e45d470, same machine, back-to-back runs):

## Tests

- `tests/kernels/test_kpool_decode_update_batched.py`: 3 new tests — the flat-token writer equals the pooled writer on explicitly gathered rows across a request boundary that is not pool-aligned inside the batch (kpool 4 and 16), a slot on a row too early to own a full pool is skipped, and a batch shorter than one pool writes nothing. The existing exact-equality tests against the two-pass fp32 CPU reference (incl. 20 fuzz seeds) and the decode-vs-prefill writer equality keep passing with the online-softmax kernels. Whole file: 31 passed, 2 skipped (ROCm-only). `tests/v1/attention/test_kpool_tail_slot_mapping.py`, `tests/v1/attention/test_sparse_indexer_decode_seq_lens.py`: pass (50 passed / 2 skipped combined).
- Live server (breakable CUDA graphs: prefill PIECEWISE/FULL + decode FULL graphs captured cleanly with the dual-stream fork/join inside, MTP speculator): greedy sanity (`17 * 23` -> `391` with a correct reasoning trace, identical to main) and the bench runs above.
- GSM8K (`tests/evals/gsm8k/gsm8k_eval.py --num-questions 300 --max-concurrency 1`, 5-shot, greedy, MTP k=5, same servers): this PR 0.920, main 0.923 on the paired run; across all runs on this machine both sides span 0.920-0.923 (greedy outputs are not bitwise reproducible across runs on this fp8 MoE + EP deployment even on unmodified main), so this is parity, not an accuracy claim. The only numerics that changed are bounded: 9 of 278,784 cache bytes on an 8192-token prefill (fp8 rounding from the online softmax) and <= 1.3e-9 fp32 summation order in the head gate.
- Pre-commit hooks (ruff, ruff-format, mypy, typos, ...) pass on all changed files.
