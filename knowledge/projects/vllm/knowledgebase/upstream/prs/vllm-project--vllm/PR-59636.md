# [Bug]: Fix Rust vllm-bench missing usage.prompt_tokens

[Upstream PR](https://github.com/vllm-project/vllm/pull/59636) · state: open · merged: False

## Original PR description

**Title: [Bug]: Fix Rust vllm-bench missing usage.prompt_tokens**

**Description**
Fixes #59576

This PR resolves an issue in the Rust vllm-bench where total input tokens were being under-reported because it relied on a client-side estimate rather than the server-reported usage.prompt_tokens. This discrepancy became especially noticeable in random multimodal (VLM) benchmarks where image tokens were entirely missing from the client estimate, making Rust and Python benchmark results incompatible.

**Changes introduced:**

Backend (backends/mod.rs): Updated ChunkUsage struct to deserialize prompt_tokens: Option<u64>.
Streaming endpoints (openai_chat.rs & openai_completions.rs): Extracted prompt_tokens from the usage chunk and assigned it to output.prompt_len, superseding the initial client estimate.
Metrics (metrics/calculator.rs & metrics/steady_state.rs): Updated both the main calculator loop and the steady-state window logic to sum output.prompt_len (the actual server-reported length) instead of input_requests[i].prompt_len.
Preserves fallback behavior: if the server omits prompt_tokens, output.prompt_len retains the client-side estimate it was originally initialized with.

- esmeetu · COMMENTED · 2026-10-13T12:00:31Z · [source](https://github.com/vllm-project/vllm/pull/59636#pullrequestreview-5503162288)

Thanks for this. Using the server-reported prompt tokens makes sense to me. A few things before it lands:

1. **Partial or zero `usage.prompt_tokens` should not override the client value** (inline).
2. **Multi-turn now changes semantics without saying so.** Total and per-turn input switch to server counts, but `cumulative_input_tokens` and the max-model-len filter still use the client estimate (inline on `calculator.rs`).
3. **`input_requests` is now unused.** It should be removed from `calculate_metrics` / `steady_state::compute` and their callers, not renamed to `_input_requests`.
4. **Stale docs and inconsistent reporting:**
   - The `steady_state::compute` doc still says the request list is used "for input-token attribution".
   - The `calculate_embedding_metrics` doc still lists `output.prompt_len` vs `input_requests[i].prompt_len` as a difference from `calculate_metrics`.
   - The dry-run "Total input tokens" (`benchmark.rs:644`) still sums the client estimate, so dry-run and real runs will now disagree (most visibly for multimodal).
5. **Tests:**
   - Add a completions-backend test for `prompt_tokens`.
   - The steady-state test fixtures build `requests` from `o.prompt_len`, so they can't tell request lengths from output lengths. Making them differ in one test would pin the new behavior.
6. **Optional cleanup:** the usage block is now duplicated in chat and completions. A small `ChunkUsage::apply(&self, &mut RequestFuncOutput)` helper in `backends/mod.rs` would keep the two in sync.
