# [ROCm][Perf][GLM-5.3-Flash] Allow AITER fused shared experts at TP2 on gfx950

[Upstream PR](https://github.com/vllm-project/vllm/pull/63603) · state: open · merged: False

## Original PR description



## Overview

Admit TP2 in the GLM-5.3-Flash fused shared-expert gate on gfx950. AITER now ships tuned block-FP8 fused-MoE rows for the TP2 fused shape (ROCm/aiter#6077), and with Quark MXFP4, which has no tuned rows at any TP, the fused path is faster at TP2 too (below). Follows #59221; touches the same lines as #60604, which keeps gfx950 at TP4/TP8.

## Claims

- With `VLLM_ROCM_USE_AITER_FUSION_SHARED_EXPERTS=1` on gfx950 at TP2, GLM-5.3-Flash runs the shared expert inside the AITER fused MoE (E=289, top-k 9). Before, the flag was ignored with a warning.
- Unchanged: the flag's default (off), TP1/TP16, other GPUs, and data, prefill-context or expert parallelism.
- At TP2 on 2× MI355X with Quark MXFP4, the flag raises output throughput by 20.4 / 7.0 / 4.0 % at concurrency 4 / 16 / 64 (random 1k/1k), and by 9.6 / 12.3 / 4.3 % with breakable CUDA graphs (`FULL_AND_PIECEWISE`). GSM8K changes by −0.27 and −0.76 pp, within about 1.3 per-run standard errors.

## Details

- **Why the gate refused TP2.** #59221 limited fusion to the shapes AITER had tuned for (ROCm/aiter#5735: gfx950 TP4/TP8). ROCm/aiter#6077 added the TP2 rows. At AITER v0.1.26 (the version in `docker/Dockerfile.rocm_base`), `a8w8_blockscale_tuned_fmoe_glm5_3_flash_shared_gfx950.csv` has (289, 9) rows at inter_dim 1024 (TP2, 14 rows), 512 (TP4, 7) and 256 (TP8, 9).
- **MXFP4.** AITER has no MXFP4 (289, 9) rows at any TP (ROCm/aiter#6435 adds them). MXFP4 at TP2 therefore runs AITER's default kernels, as it already does at TP4/TP8. On the measured image the routed-only (288, 8) MXFP4 shape has no tuned rows either, so both arms of the serving comparison run default configs.
- **Correctness at TP2.** Without EP, the shared expert is split by TP like the routed experts (1024 per rank at TP2), and the appended top-k column is the same for every rank. No code on the fused path branches on TP2.
- **#60604.** Both PRs change the same TP check. Whichever lands second adds 2 to the gfx950 entry of `tuned_tp_sizes`.
- **Scope.** Only `vllm/models/glm5next/common/model.py`'s gate and its test. Qwen3-Next-based models have no TP condition on this flag.

Thanks for contributing! 

Some comments:

1. Measure the block-FP8 checkpoint at TP2. The MXFP4 runs exercise the fused path at TP2 (E=289), but not the kernels ROCm/aiter#6077 tuned. Those rows are keyed per_1x128 FP8, and AITER's config lookup matches on quantization type, so MXFP4 (per_1x32) falls back to default heuristics. For FP8 at TP2, both the fused (289, 9) and routed-only (288, 8) shapes have tuned rows in AITER v0.1.26, so that A/B can come out differently. Please add a flag-off vs flag-on run for **zai-org/GLM-5.3-Flash FP8** at TP2 on the same image, with the E=289 config log line and no "flag ignored" warning.

2. Low-concurrency points and TTFT. The tables cover concurrency 4/16/64, and @amd-sriram's covers 4–256. Please could you add concurrency 1 and 2 and report TTFT next to TPOT. With tuned MXFP4 rows the gain drops to +0.7% at c=4, so c=1/2 is where a tuned-vs-tuned regression would show first. Also include TTFT for the long-input points (60k and 128k), since the fused MoE also runs in prefill. I would say that `vllm bench serve` is preferred over `sglang.bench_serving` for vLLM PRs, why did you use sglang.bench?

3. Accuracy run. For a MoE change, please run  `lm_eval --model local-completions` against the served model, with num_concurrent=256, num_fewshot ≥ 20, and both strict and flexible match, for FP8 and MXFP4. Under breakable CUDA graphs, both flag-on GSM8K runs (95.15 / 95.15) are below both flag-off runs (96.13 / 95.68). That is probably noise, but a 5-shot, strict-only run without stated concurrency can't settle it. The GPQA Diamond result in the comment (n=198) points the other way but is too small to decide.
