# qwen4_exp: reinterpret FP8 PLE as int8 for SM86 lookup

[Upstream PR](https://github.com/vllm-project/vllm/pull/58856) · state: closed · merged: False

## Original PR description

## Purpose

Fix FP8 E4M3 PLE lookup for Qwen3.8-Flash-Next when using the pinned-host PLE embedding path.

Qwen3.8-Flash-Next supports FP8 E4M3 PLE embeddings, which can be stored in CPU pinned memory and accessed from the GPU through the existing pinned-host PLE lookup path. The lookup kernel only needs to copy the FP8 values from the PLE table into the output tensor.

In the current vLLM implementation, passing the FP8 tensor directly to the Triton lookup kernel fails on architectures where Triton does not support the native FP8 pointer type (`fp8e4nv`):

```text
ValueError("type fp8e4nv not supported in this architecture.
The supported fp8 dtypes are ('fp8e4b15', 'fp8e5')")
```

Since the kernel only copies the underlying bytes, the FP8 tensor can be reinterpreted as `int8` for the lookup without changing the stored values.

This change:

* Reinterprets FP8 E4M3 PLE storage as `int8` when invoking the pinned-host lookup kernel.
* Reinterprets the output tensor as `int8` for the corresponding byte-wise store.
* Leaves the existing path unchanged for non-FP8 PLE embeddings.

## Test Plan

Tested [Jon-Nielsen/Qwen3.8-Flash-Next-AWQ-INT4-FP8PLE](https://huggingface.co/Jon-Nielsen/Qwen3.8-Flash-Next-AWQ-INT4-FP8PLE) on 4× NVIDIA RTX 3090 (SM86).

The model `config.json` was updated for the test with: `"ple_embedding_dtype": "float8_e4m3fn"` which causes vLLM to select `Qwen4ExpPLEFp8EmbeddingMethod` for the FP8 PLE table and enables the checkpoint to use the built-in PLE CPU-offload path on SM86.

The test run used TP4/EP4 with the built-in PLE CPU-offload path.

```bash
vllm serve Jon-Nielsen/Qwen3.8-Flash-Next-AWQ-INT4-FP8PLE \
  --tensor-parallel-size 4 \
  --enable-expert-parallel \
  --engram-config '{"cpu_offload": true}' \
  --gpu-memory-utilization 0.96 \
  --max-num-seqs 1 \
  --max-model-len auto
```

Validation:

* TP4 / EP4 model initialization succeeded on 4× RTX 3090 (SM86).
* FP8 PLE embedding initialized with `Qwen4ExpPLEFp8EmbeddingMethod`.
* PLE weights loaded on CPU pinned memory.
* The pinned-host lookup executed using the `int8` view of the FP8 storage.
* vLLM server reached `Application startup complete`.
* Sent an inference request after startup.
* Received a valid response.

## Test Result

* Model initialization succeeds on 4× RTX 3090.
* The pinned-host lookup executes using an `int8` view of the FP8 storage.
* Inference succeeds and returns a valid response.

The `int8` reinterpretation is byte-preserving: FP8 E4M3 and `int8` both occupy one byte per element, and the lookup kernel only gathers/stores those bytes.
