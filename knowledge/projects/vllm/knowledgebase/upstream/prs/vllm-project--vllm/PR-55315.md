# [Test] Split test_sampling_mask_preserves_top_k_boundary_ties to remove Triton-kernel-specific assumption Description

[Upstream PR](https://github.com/vllm-project/vllm/pull/55315) · state: closed · merged: True

## Original PR description

## What
`test_sampling_mask_preserves_top_k_boundary_ties` (added in #54901) fails
on Triton-backed platforms (e.g. XPU) with `assert 3 > 3`.

## Why
The test builds its fixture by calling the real `apply_top_k_top_p` on
tied top-k boundary logits, and assumes ties are always preserved
(count > k). That's true for the PyTorch fallback, but the Triton kernel
intentionally trims boundary duplicates to always return exactly k
(same tradeoff already documented in `test_topp_tie_break_deterministic`).
So the test baked in one backend's behavior as a cross-backend contract.

## Fix
Split into two tests, matching what this case actually used to cover
before #54901:
- `test_sampling_mask_matches_processed_top_k_top_p_support`: end-to-end
  check that `SamplingMaskTensors` matches whatever `apply_top_k_top_p`
  produces, with a backend-agnostic assertion.
- `test_sampling_mask_preserves_top_k_boundary_ties`: hand-built logits
  (no `apply_top_k_top_p` call) to reliably test the `max_num_kept`
  overflow/bitmask-fallback path.

No production code changed (test-only).

## Test
`python -m pytest tests/v1/test_outputs.py -v` → 14 passed
(previously 1 failed on XPU).
