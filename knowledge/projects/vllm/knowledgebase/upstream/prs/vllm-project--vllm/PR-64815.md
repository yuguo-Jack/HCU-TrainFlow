# [Perf][MXFP8] Keep DeepSeek-V4.1 fusions on the torch._scaled_mm kernel

[Upstream PR](https://github.com/vllm-project/vllm/pull/64815) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

Lets the existing `TorchMxFp8LinearKernel` (cuBLASLt through `torch._scaled_mm`) keep DeepSeek-V4.1's input-quant fusions, so a prefill instance can run its MXFP8 linear GEMMs on cuBLASLt with one existing setting. The default kernel is unchanged. This replaces the earlier revisions' DeepSeek-V4.1 linear method and `VLLM_DSV41_MXFP8_CUBLASLT_MIN_M`.

```bash
vllm serve <model> --kernel-config '{"linear_backend_per_quant":{"mxfp8":"torch"}}'
```

## Claims

- GB200, DEP4 target-model prefill forward, dummy weights, one run per arm: at 16K and 32K rows per rank, 2.6% and 3.0% faster than autotuned CuTe-DSL. 2K and 8K are 2.4% and 3.7% faster, within that arm's sample spread.
- Against this kernel before the change, the query path spends 36-84% less GPU time and about 75% less host time per call, because it no longer quantizes twice.
- GEMM only, 210 shapes: cuBLASLt beats tuned CuTe-DSL on 54/70 shapes from 8192 rows and 85/140 below, where it is up to 32% slower. Median host time per call is 45.5 us against 147.9 us. This is why it is opt-in, for instances dominated by long prefill.
- No full-weights accuracy or serving result for this revision; see Limitations.

## Details

- **Why the fusions can stay.** This kernel already quantizes to the F8_128x4 swizzled scales that FlashInfer uses. It now declares `kMxfp8Dynamic` on CUDA and reads a `QuantizedActivation`, and the DeepSeek-V4.1 `can_fuse_query_quant` and `_can_fuse_wo_a` gates accept it. Those gates cover the query-quant, mega-attention `wo_a` to `wo_b` and batched Engram WKV paths, plus fused WO-A. XPU keeps its current path.
- **Not enabled.** GEMM-RS and specialized decode still require a FlashInfer kernel. Specialized decode belongs to decode instances, and GEMM-RS only runs with tensor parallelism.
- **P/D.** The kernel config is not part of the NIXL compatibility hash, so only prefill instances need this setting; decode stays on CuTe-DSL.
- **Other models.** The setting is opt-in, so they change only with an explicit `torch` MXFP8 backend. In that case MiniMax-M3 has two key-only checks that now see this kernel: the fused MoE finalize at TP > 1, and `FLASHINFER_TS` with an FP8 KV cache, which requests an FP16 attention output that this kernel would return as FP16. Neither combination was run.

### Limitations

- The GB200 results use dummy weights and balanced MoE routing, so they show performance only. No GSM8K or serving run was done on this revision, because the checkpoint was not accessible in the validation environment.
- One run per arm with a fixed order, and fresh prefill only, with no prefix hits.
- Below 8192 rows, single GEMMs can be up to 32% slower than tuned CuTe-DSL. There is no row threshold.
- This kernel has no `N % 16` fallback and was not run with such a width. The seven measured DeepSeek-V4.1 shapes all satisfy it.
- `supports_pre_processed_weights` stays `False`, so this backend does not work with the weight cache daemon.
- The batched Engram WKV input and `VLLM_GPU_SYNC_CHECK=error` were not exercised. The change adds no host reads of GPU tensors.
- No CI test is added. `pre-commit` passes.

Not a duplicate: #64417 bypasses eager custom-op dispatch, #61577 targets BF16 GEMM, #46400 changes online-quantization numerics, #63921 / #61869 target specialized decode, and #64373 covers GLM-5.3 online quantization.

**Verified against `main`:**

- Equivalence is structurally sound — same data, same layout, same scales. The FlashInfer CuTe-DSL kernel stores the weight column-major as `[K, N]` (`flashinfer.py:161` `weight.contiguous().t()`, read back at `:172` `K, N = weight.shape`) and feeds it as operand B to `mm_mxfp8(A=[m,k], B=[k,n])`. The PR's `torch._scaled_mm(input_mxfp8 [M,K], layer.weight [K,N])` computes the same `A@B -> [M,N]` on the identical operands with no re-transpose or requantization. Scales are passed via `.view(torch.float8_e8m0fnu)` of the stored `uint8` swizzled factors — a zero-copy reinterpretation of the same bytes FlashInfer consumes, and E8M0 is the correct reading of those bias-127 exponent bytes.
- The threshold gates the right dimension (M = input rows): `m = qa.data.shape[0]` for a quantized activation, `m = x.numel() // K` for a plain tensor — both are row counts, not K or N. `VLLM_DSV41_MXFP8_CUBLASLT_MIN_M` (default 8192) is a proper int env var, and `0` disables the path.
- It can't trigger on unbenchmarked hardware: the cuBLASLt branch only runs when `type(self.kernel) is FlashInferCutedslMxfp8LinearKernel`, which is selected only after `is_supported()` passes `is_device_capability_family(100)` (SM100/103 Blackwell) + the CuTe-DSL module. Elsewhere it falls through to `super().apply`. It also respects explicit `--linear-backend` overrides (only arms when the effective mxfp8 backend is `"auto"`), and `out_dtype`/bias/final-reshape match the CuTe-DSL path.

**Two non-blocking notes:**

1. No fallback if `torch._scaled_mm` rejects the MX operands. Once `m >= min_m and N % 16 == 0`, `torch._scaled_mm` is called unconditionally — no torch-version check and no try/except back to `kernel.apply_weights`. The MX E8M0 block-scale path needs a recent PyTorch (body cites 2.14.0+cu132); an older torch on SM100 with `linear_backend="auto"` would raise at first forward rather than fall back. A version guard or a one-time capability probe would make the opt-in safer.
2. The `N % 16` requirement is a `torch._scaled_mm` MX-alignment constraint documented only in the env comment / body, not tied to a torch constant. Could you confirm 16 is the actual cuBLASLt MX alignment for the targeted torch version? It's handled by falling back when it fails, so not a correctness risk, just a magic number worth anchoring.

Validation note: the bitwise-equality test over 70 shapes (`torch.equal`) is exactly the right check for the equivalence claim, but it runs only in B200 CI — I could confirm the scales are passed byte-identically (necessary) but not that `torch._scaled_mm` interprets the 128x4-swizzled E8M0 block layout the same way as FlashInfer (sufficient), which needs the hardware run.
