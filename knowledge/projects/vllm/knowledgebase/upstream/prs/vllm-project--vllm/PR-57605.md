# kv-cache: honor scheduler lookahead in mamba align-mode allocation

[Upstream PR](https://github.com/vllm-project/vllm/pull/57605) · state: closed · merged: False

## Original PR description

## Problem

In mamba align cache mode (mamba-hybrid models with prefix caching), `MambaManager.allocate_new_blocks` and `get_num_blocks_to_allocate` discarded all lookahead tokens by resetting `num_tokens` to `num_tokens_main_model`. When the scheduler schedules lookahead capacity beyond a main-model sequence that ends exactly on a page boundary, this corrupts the recurrent state in two ways.

## Root cause

A mamba state table row is page-indexed: the worker's running-state column is `cdiv(main_end, bs) - 1`.

1. **Missing next page.** When a chunk ends exactly on a page boundary and lookahead tokens extend beyond it, the next page was not materialized with the current schedule. The boundary token's state write then targeted a block-table entry that still held a recycled stale block — the recurrent state is corrupted from that point on (one-step NaN followed by a repetition lock at every page boundary).

2. **Displaced running-state column.** If a page was materialized for the lookahead, the null padding was derived from the inflated `num_tokens`, so the reserved page displaced the real running-state column. The worker's running-state index (0 for a chunk ending at the first page boundary) pointed at the null slot; the next chunk's state pre-copy chained from the null slot and spec-decode acceptance collapsed to zero permanently for that request.

## Diagnosis

Reproduced on a 4-node Arm (Thor SM110) cluster serving GLM-5.3-Flash (mamba-hybrid + MTP + prefix caching) with deterministic single-turn probes: prompts whose prefill chunk ends exactly on a page boundary produced 0% spec-decode acceptance from the first decode step, while boundary-crossing-free prompts were healthy. The failure moved with cache layout across boots, and per-request scheduler dumps of the mamba state-table rows showed the displaced null column exactly at the worker's running-state index. The corruption was confirmed to chain through the state pre-copy (pre-copy source = the null slot).

## Fix

- Materialize the next state page when lookahead extends a page-aligned main-model sequence (both `get_num_blocks_to_allocate` and `allocate_new_blocks`), so the boundary token's state write has a real block.
- Derive the null padding from `num_tokens_main_model`, not the lookahead-inflated `num_tokens`, so the reserved page can never displace the running-state column.
- Grow the allocation budget by one when the next page is materialized.

## Testing

- Verified on a 4-node Thor SM110 cluster with GLM-5.3-Flash (NVFP4, MTP spec decode, prefix caching, chunked prefill): before the fix, deterministic 0% acceptance on boundary-ending chunks; after, the full prompt-size ladder and a 22-turn multi-turn conversation (360k prompt tokens) are coherent with mean acceptance length ~3.
- `num_tokens == num_tokens_main_model` (no lookahead) keeps the original padding math exactly.

Closing this PR — thanks to @MaCoredroid for the careful CPU-only analysis, which proved correct on all three points.

On closer inspection against current main, the align-mode manager has evolved substantially since this patch was written (scratch/speculative-column relocation, updated checkpoint handling), and the boundary condition this PR targeted is covered by that evolution. Re-running the manager and chunk-split suites on top of the upstream manager shows the lookahead-inflation materialization this PR added is redundant — and breaks the block economy the existing suites encode (off-by-one held blocks at page boundaries).

The historical failure mode that motivated the patch was real on the manager version of that era (a lookahead-inflated num_tokens deriving the null-padding count displaced the running-state column, collapsing spec-decode acceptance), but it does not reproduce on the evolved manager.

Upstreaming takeaways that did hold up elsewhere in our tree: the finished-request double-delivery placeholder-drain skip (with a was-finished-before gate so stop-trimmed finishes still resolve their own placeholders) remains needed — current main still unconditionally drains. That may be worth a separate, smaller PR.
