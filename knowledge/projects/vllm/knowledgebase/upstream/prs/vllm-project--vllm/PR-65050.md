# [Kernel] Enable CuteDSL GDN prefill on SM110

[Upstream PR](https://github.com/vllm-project/vllm/pull/65050) · state: closed · merged: True

## Original PR description



## Overview

Lets the opt-in CuteDSL GDN prefill backend (`--gdn-prefill-backend cutedsl`) run on SM110 (Jetson Thor), and fixes its kernel launch on GPUs with fewer SMs than value heads. Related: #63284 rewrites the same selector function, so whichever PR merges second will need a small rebase. #62149 is a separate Thor GDN warmup crash that this PR does not fix.

## Claims

- `--gdn-prefill-backend cutedsl` now runs on SM110. Before, the selector fell back to Triton/FLA.
- On GPUs with fewer SMs than value heads, the CuteDSL kernels failed to launch with `CUDA_LAUNCH_INVALID_CONFIG`. Thor has 20 SMs and Qwen3.8-27B has 48 value heads. The kernels now launch at least one CTA per head.
- On Thor with `Qwen/Qwen3.8-27B`, cutedsl lowers TTFT on 16k-token prompts by about 6% compared with triton. GSM8K is within error.
- `auto` makes the same choice as before on every platform. On SM10x, the larger grid size only takes effect for models with more than 148 value heads.

## Validation

Jetson AGX Thor (SM110, 20 SMs), CUDA 13.2, `Qwen/Qwen3.8-27B` (BF16, `head_k_dim=128`, 48 value heads).

**Kernel test** (`tests/kernels/mamba/test_gdn_prefill_cutedsl.py`):

| | Result |
|---|---|
| Without the `num_sms` fix | 6 failed, 7 passed: every `num_v_heads=160` case raises `CUDA_LAUNCH_INVALID_CONFIG` in `kkt_inv_uw_cutedsl` |
| With the fix | 13 passed |

**End to end**, `--gdn-prefill-backend triton` vs `cutedsl` (startup logs confirm the selected kernel):

| Backend | GSM8K strict | GSM8K flexible | Mean TTFT (ms) | Median TTFT (ms) | P90 TTFT (ms) |
|---|---|---|---|---|---|
| triton | 0.7058 | 0.7339 | 16573.6 ± 8.9 | 16563.6 ± 11.8 | 16634.4 ± 14.0 |
| cutedsl | 0.6990 | 0.7240 | 15555.3 ± 1.0 | 15551.1 ± 1.6 | 15565.8 ± 6.6 |

- GSM8K: full 1319-question set, 5-shot. lm-eval reports a standard error of ±0.012–0.013 per score, so the −0.7 / −1.0 point differences are within noise.
- TTFT: 16k-token random prompts, 1 output token, concurrency 1, 16 prompts per run, 3 runs with seeds 1–3 (mean ± stdev). `max_num_batched_tokens=8192`, so each prompt is prefilled in two chunks.
- All 48 benchmark requests succeeded on both backends, and neither server log has errors.

CI has no SM110 runner. The B200 `Kernels` job runs the updated test, and its `num_v_heads=160` case exceeds the B200's 148 SMs, so it covers the grid fix.

## Details

- **Root cause:** `kkt_inv_uw_cutedsl` and `o_cutedsl` launch `grid = (num_sms // Hv, Hv, 1)`. When `num_sms < Hv`, the first grid dimension is 0 and CUDA rejects the launch. Both kernels now clamp the first grid dimension to at least 1 (`cutlass.max(num_sms // Hv, 1)`), which gives one CTA per head and also covers direct callers of the kernels. Both kernels loop over chunks with a stride equal to the grid size (`range(bid, num_global_chunks, grid_x)`), so the grid size doesn't affect results. `kernel_h` uses a `(Hv, N)` grid and isn't affected.
- **Selector:** SM11x with `head_k_dim == 128` and CUDA 13+ now allows CuteDSL. It doesn't allow FlashInfer, so `auto` still resolves to Triton on SM110.
- **Not a duplicate of #63284:** that PR splits "can run" from "preferred" for FlashInfer and CuteDSL, but doesn't add SM110 or touch the kernel grid size. If it merges first, this PR only needs SM110 added to its `can_run_cutedsl` check and its "targets SM100" error text updated.
- **Test gap:** no unit test checks that the selector picks CuteDSL on SM110. CI has no SM110 GPU, and faking the GPU type would need mocks. The startup log line from the Thor run is the evidence instead.
- **Docs:** the `--gdn-prefill-backend` help text now says where `cutedsl` works.
- AI assistance (Claude) was used to write and validate this change. I reviewed every changed line and ran the tests and benchmarks above.

Thanks for the question. FlashInfer is what I actually want on SM110. It's much faster than CuteDSL on Thor: 2.0–8.7× vs FLA at the kernel level, against 1.4–1.8× for CuteDSL (table in #65054). But it doesn't work on SM110 with the FlashInfer version vLLM pins:

- vLLM's selector only offers FlashInfer GDN prefill on SM90/SM10x/SM12x, so on Thor it falls back to Triton/FLA.
- Even with the selector changed, FlashInfer 0.7.2.post1's public `chunk_gated_delta_rule` only dispatches compute-capability major 10 to its CuTe DSL kernel. On SM110 it raises `GDN prefill DSL kernel is unavailable`, although the same kernel builds and runs correctly on `sm_110a` when called directly.

I've opened flashinfer-ai/flashinfer#7827 to route SM110 to those kernels. It's approved pending CI. Once it's in a FlashInfer release and vLLM's pin includes it, I plan to send a follow-up that enables FlashInfer on SM110 and makes `auto` prefer it.

I used CuteDSL here because it's the only faster kernel that works on SM110 without a FlashInfer bump. The end-to-end gain is modest, though (about 6% TTFT on 16k prompts). If you're planning to remove the CuteDSL kernel, I'm happy to close this PR and go straight to the FlashInfer path.

- gau-nernst · comment · 2026-11-02T05:13:40Z · [source](https://github.com/vllm-project/vllm/pull/65050#issuecomment-6569625687)

Pushed f4be172d29 moving the `Hv > num_sms` guard out of `chunk_gated_delta_rule_cutedsl`'s `num_sms` computation and into the launch logic of the two affected kernels (`kkt_inv_uw`, `o`), where the grid is computed:

```python
grid = (cutlass.max(num_sms // self.Hv, 1), self.Hv, 1)
```

Rationale: the invariant is "every head gets at least one CTA", which is a property of the grid, not of `num_sms`. Clamping `num_sms` in the wrapper made it no longer the true device SM count, coupled the wrapper to both kernels' launch shapes, and left direct callers of `kkt_inv_uw_cutedsl` / `o_cutedsl` unprotected (they default to / expect the real SM count). `cutlass.max` works on dynamic `Int32` in `@cute.jit` (cf. `cutlass.min` in `PrepMetaKernel`), and pre-commit hooks pass.

Note: I have no GPU on this machine, so please re-run `pytest tests/kernels/mamba/test_gdn_prefill_cutedsl.py` on Thor/B200 to confirm the `num_v_heads=160` cases still pass.
