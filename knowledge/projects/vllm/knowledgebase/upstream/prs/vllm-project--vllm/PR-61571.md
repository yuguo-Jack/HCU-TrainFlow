# [Feature][Observability] Add tool-calling metrics

[Upstream PR](https://github.com/vllm-project/vllm/pull/61571) · state: open · merged: False

## Original PR description


## Overview

Add bounded tool-calling metrics for Chat Completions and Messages, covering streaming and non-streaming responses without changing parser behavior or model output.

## Claims

- Add normalized tool-choice/count labels, native API attribution, and surfaced parse_failure outcomes to the new response counter, preserving the existing parser invocation counter's labels and classifications.
- Add vllm:tool_call_responses_total and vllm:tool_calls_emitted_total, counting calls after filtering and Messages conversion without double-counting streaming fragments.

## Validation

375 focused tests passed: 60 parser/metrics, 176 Chat serving, 130 Messages conversion, and 9 engine regression tests. All applicable pre-commit checks passed. Existing Buildkite jobs cover these suites.

Live validation of the metrics-only revision (`f9798f7e27`): 24/24 CPU cases passed on ROSA with Qwen3-0.6B and tracing disabled. Verified 20 tool-bearing response outcomes, 14 emitted calls, and four plain-request controls with no new counter increments. Streaming `n=2` counted one outcome and two calls; the legacy counter retained its schema and Messages attribution. This used the exact Python source over the existing CPU image's native libraries, not a rebuilt candidate image. A non-tool performance comparison remains pending. No end-to-end performance claim is made.

## Details

Tracing changes are being split into a follow-up, keeping this PR focused on metrics.

The new telemetry exports no tool names, schemas, arguments, bodies, or content-derived hashes. Failures cover surfaced exceptions only; internally swallowed errors and existing payload logging remain outside this PR.

This differs from [#51814](https://github.com/vllm-project/vllm/pull/51814) and [#53365](https://github.com/vllm-project/vllm/pull/53365), which cover invocation tests/hooks, and [#54117](https://github.com/vllm-project/vllm/pull/54117)/[#55254](https://github.com/vllm-project/vllm/pull/55254), which classify parser completions against schemas. This PR measures actual API response outcomes after filtering/conversion.

- bbrowning · comment · 2026-10-14T20:59:41Z · [source](https://github.com/vllm-project/vllm/pull/61571#issuecomment-6178370004)

Thanks for pushing on our observability! I went through some human and AI-assisted review with this, and found a few things we should probably adjust before merging this. Items 1 and 2 are the bigger ones; 3–4 are small and can go in the same push. Reviewed at 5f74a0c.

I did not mark these as request changes, because I know others have been tagged for review and am leaving room for them to push back or override my suggestions below.

**1. Every Chat output now pays for a pydantic private-attribute read**

[`serving.py#L557`](https://github.com/vllm-project/vllm/blob/5f74a0c080c04468aefc3d34c4a1a680a47f9079/vllm/entrypoints/openai/chat_completion/serving.py#L557) and [`#L1025`](https://github.com/vllm-project/vllm/blob/5f74a0c080c04468aefc3d34c4a1a680a47f9079/vllm/entrypoints/openai/chat_completion/serving.py#L1025) read `request._tool_calling_spans` on every `RequestOutput`, for every Chat request, including ones with no tools and tracing off. Pydantic private attributes are resolved through `BaseModel.__getattr__`, so each read costs about 670 ns, against about 11 ns for a normal field (pydantic 2.14). I benchmarked `chat_completion_stream_generator` on CPU, feeding it 1,000 mocked outputs with no tools and no tracing. Median time went from 12.19 ms on base to 13.12 ms on this PR, and back to 12.14 ms with the read moved out of the loop. This isn't an end-to-end number, but it's a cost on the hot path for a feature most requests don't use. Please read it once before each loop using something like:

```python
tool_calling_spans = request._tool_calling_spans
async for res in result_generator:
    if tool_calling_spans is not None:
        tool_calling_spans.extend(res._tool_calling_spans or ())
        res._tool_calling_spans = None
```

**2. Don't change the labels on `vllm:tool_call_parser_invocations_total` unless we deprecate/migrate first**

This counter has shipped since v0.24.0 (#44448) with labels `model_name, mode, outcome, request_type`. This PR moves Messages traffic from `request_type="chat_completions"` to `"messages"` and adds `tool_choice` and `tool_count` ([`metrics.py#L236-L260`](https://github.com/vllm-project/vllm/blob/5f74a0c080c04468aefc3d34c4a1a680a47f9079/vllm/parser/metrics.py#L236-L260)). Dashboards and alerts that select `request_type="chat_completions"` would silently lose Messages traffic after an upgrade. The new `vllm:tool_call_responses_total` already has `tool_choice` and `api_surface`, so could we leave the existing counter as it is and put the new dimensions on the new counters (including `tool_count`, if you want it)? If you'd rather change the existing counter, it needs an explicit deprecation and migration note, but I think leaving it alone is the faster way to land this. What I want to avoid is surprising people with production deployments on upgrades.

**3. Errors from the new close calls escape the stream's `finally`**

At [`serving.py#L981`](https://github.com/vllm-project/vllm/blob/5f74a0c080c04468aefc3d34c4a1a680a47f9079/vllm/entrypoints/openai/chat_completion/serving.py#L981) and [`anthropic/serving.py#L1277`](https://github.com/vllm-project/vllm/blob/5f74a0c080c04468aefc3d34c4a1a680a47f9079/vllm/entrypoints/anthropic/serving.py#L1277), if `aclose()` raises (for example, the engine abort fails while the generator closes), the exception escapes after the error chunk has been yielded. Chat never sends `[DONE]`, and the Messages stream breaks. This can only happen with tracing on and tools present, because that's the only case where Chat closes the engine generator. Still, it's a new failure mode on the error path. Please wrap both calls in `try/except Exception: logger.exception(...)` so cleanup failures get logged instead of raised.

**4. A few accuracy fixes in `docs/usage/metrics.md`**

- [L61](https://github.com/vllm-project/vllm/blob/5f74a0c080c04468aefc3d34c4a1a680a47f9079/docs/usage/metrics.md?plain=1#L61) says Messages argument-conversion errors count as parse failures. That's only true for non-streaming. Streaming forwards argument fragments without validating them, so invalid or truncated JSON is recorded as `success`. Qualifying the sentence is fine for this PR.
- Cohere v2 calls `create_chat_completion` without setting `_api_surface`, so its traffic is counted as `chat_completions`, before the Cohere conversion. Please mention that in one sentence, or exclude Cohere explicitly.
- On a request with tools, an exception from the combined parser, including the reasoning parser, is recorded as `parse_failure`. That's a reasonable signal, but the table describes it as a tool-parser failure, so please say this explicitly.


- bbrowning · comment · 2026-10-14T21:13:58Z · [source](https://github.com/vllm-project/vllm/pull/61571#issuecomment-6178641859)

 One additional note as I dug into the labels themselves - consider keeping `tool_choice` and `tool_count` off `tool_call_parser_invocations_total` regardless of how `request_type` is handled. That counter goes up once per streamed chunk, so a single streamed request that produces 300 chunks adds 300, while a non-streamed request adds 1. That makes it hard to answer questions like "how many requests set `tool_choice=required`?" from it. Since these describe the request, they fit better on `tool_call_responses_total`, which counts each request once.

The cardinality of the new labels isn't a concern either way, but keeping the old counter's labels unchanged also keeps it around I believe 18 series instead of potentially as high as 720 with this change as-is.

I find this pretty impenetrable, given this is user-facing. Before getting into the semantics of the labels, I'd open with something like

---

Tool-calling metrics describe three parts of handling a request: parsing model output, recording the request's outcome, and returning individual tool calls to the client.

These counters measure different units, so their totals need not match. All three include the `model_name` label.

| Counter | What it counts |
|---|---|
| `vllm:tool_call_parser_invocations_total` | Each time the tool parser examines model output. Streaming can require many invocations for one request. |
| `vllm:tool_call_responses_total` | One outcome per completed tool-bearing request, or per surfaced parsing failure. |
| `vllm:tool_calls_emitted_total` | Individual tool-call objects returned to the client. One response can contain several calls. |

For example, a streamed request asks for weather in two cities. The parser examines 20 output fragments, and the completed response contains two `get_weather` calls:

- Parser invocations increase by **20**.
- Response outcomes increase by **1**, with `status="success"`.
- Emitted tool calls increase by **2**.

Fragments extending an existing call's arguments do not count as additional calls. Emitted calls are instructions for the client application to execute; these metrics do not measure tool execution.

Streaming calls can be emitted before the response finishes. Some tool-calling paths bypass the parser recording hook, so this is a conceptual relationship rather than a fixed counting ratio.
