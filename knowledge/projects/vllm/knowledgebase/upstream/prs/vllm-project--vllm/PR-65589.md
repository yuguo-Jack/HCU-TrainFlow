# [Perf][Startup] Don't import vllm.parser from vllm.v1.structured_output

[Upstream PR](https://github.com/vllm-project/vllm/pull/65589) · state: open · merged: False

## Original PR description



## Overview

Every engine core and worker process imports `vllm.v1.structured_output` (through `vllm.v1.request`). It imported `ParserEngineReasoningAdapter` at module level only for two `isinstance` checks, and that import pulls in `vllm.parser` and with it `openai`, `fastapi`, `starlette` and the `vllm.entrypoints` protocol modules. This is the "EngineCore imports fastapi and the openai protocol types through v1.request → structured_output → parser → entrypoints.*.protocol" item in #59433, and a follow-up to #65423. This PR checks the class through `sys.modules` instead, so nothing is imported.

## Claims

- After `import vllm.v1.engine.core`, `openai`, `fastapi`, `starlette`, `vllm.entrypoints` and `vllm.parser` modules are no longer loaded (counts below). The same holds for `vllm.v1.worker.gpu_worker` and `vllm.v1.executor.multiproc_executor`.
- No import happens at runtime either: if `vllm.parser.engine.adapters` was never imported, no adapter instance can exist, so the check is a dict lookup.
- Scope: this is import-time. When `--reasoning-parser` is set, `StructuredOutputManager.__init__` still loads the parser (and, for non-engine parsers, the protocol modules) at engine start. So the runtime saving applies to engines without a reasoning parser.

## Details

- `_is_parser_engine_reasoner` returns `TypeIs[ParserEngineReasoningAdapter]`, following `vllm/model_executor/models/interfaces.py`, so the call sites keep their narrowing.
- A function-local import would also work, but this helper runs inside `grammar_bitmask` in the scheduler step. With a non-engine reasoning parser, the first structured-output request would then pay for importing `vllm.parser` (~110 ms on CPU) inside one scheduling step. The `sys.modules` check avoids that.
- The test imports `vllm.v1.structured_output` under the existing `openai` block. `vllm.v1.engine.core` can't be used there yet, because `vllm.utils.deep_gemm` still imports `torch._inductor.async_compile`; a separate PR addresses that.
- CI: `lazy_imports.py` currently runs only in the `(CPU) Params, Env, Tokenizers, Parser` job, which is commented out in `.buildkite/test_areas/misc.yaml` (#63609). #64414 restores it.
- Not a duplicate: no open PR changes this import. #57310 and my deep_gemm PR also edit the end of `lazy_imports.py`, so whichever lands later needs a trivial rebase.
