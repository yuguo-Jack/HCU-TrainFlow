# [Bugfix][Spec Decode] Keep a full uniform-decode batch reachable by FULL graphs

[Upstream PR](https://github.com/vllm-project/vllm/pull/62040) · state: open · merged: False

## Original PR description



## Overview

A full `max_num_seqs` uniform-decode batch can end up with no FULL CUDA graph when the manager's query length does not divide the capture sizes. The DSpark draft (`sample_from_anchor`) decodes `num_speculative_tokens` tokens per request, but the default sizes follow the target's `1 + num_speculative_tokens` (#50488). With `max_num_seqs=72` and 5 draft tokens:

- 352 rounds up to 355, which is 71 requests;
- 368 rounds up to 370, which is 74 requests, so it is skipped;
- every full-batch step therefore runs the draft eagerly.

This PR clamps the rounded size to `max_num_seqs * query_len` for managers with a single query length.

Not a duplicate:
- No open or merged PR changes this skip. The new test fails on main, on main + #56136 and on main + #61882.
- #61882 refactors the same loop. It is a textual conflict only, with no behavior overlap.
- #56136 changes the candidate ladders in the same function. It is orthogonal and applies cleanly together with this PR.
- #50488, #53407 and #57355 fixed other "batch has no graph" cases: the target's sizes, padding up, and q=1 respectively.

## Claims

- On DeepSeek-V4.1-Flash with DSpark and `max_num_seqs=72`, a full batch's draft now runs from its FULL graph instead of eagerly. Decode throughput rises +4.4% at DEP4 on main.
- Dynamic speculative decoding (several query lengths) is unchanged. Clamping there would add graphs for tiers that never reach a full batch, and those graphs would shadow other tiers' FULL graphs.
- Each affected manager gains at most one FULL graph, plus its LoRA and DBO variants. The graph is added only when the full batch was unreachable.

## Validation

- `pytest tests/v1/cudagraph/test_cudagraph_manager.py tests/v1/spec_decode/test_dynamic_sd_cug.py` on GB200: 30 passed. On main, 29 passed and the new test fails.
- DeepSeek-V4.1-Flash on one GB200 node:
  - Config: DEP4, default MoE backend (`FLASHINFER_TRTLLM_MXFP4_MXFP8`), DSpark with 5 tokens, `max_num_seqs=72`.
  - Load: 288 requests, 72 pinned to each DP rank. Each has a ~1k-token prompt and 14k output tokens (`ignore_eos`, temperature 0).
  - Throughput is measured over 30 s while all 288 requests are decoding. Main and this PR ran interleaved, two rounds each.

  | | main | this PR |
  |---|---|---|
  | Decode throughput, rounds 1 / 2 (tok/s) | 62,752 / 60,899 | 64,586 / 64,528 |
  | Draft acceptance rate | 0.988 / 0.988 | 0.987 / 0.987 |
  | DSpark FULL graphs captured | 40 | 41 |
  | Draft kernels in a 4 s CUDA profile | eager (graph id 0) | in their own graph |

  - Throughput is +4.4%, and every PR round is above every main round.
  - The profile also shows decode steps at 40.6 ms on main vs 26.8 ms with this PR. The profiler inflates the cost of each eager launch, so treat that ratio as qualitative only.

- Host time per decode step, on a downstream branch with the same `CudaGraphManager` code: DEP16, 72 requests per rank, steady state, 2000-step windows.

  | | main logic | this PR |
  |---|---|---|
  | Full-batch draft dispatches that ran eager | ~80% | 0% |
  | `propose` (host) | 9.7 ms | 0.4 ms |
  | `sample_tokens` (host) | 11.0 ms | 1.6 ms |
  | Host slack per step | 7.5 ms | 17.4 ms |
  | Step time | 24.2 ms | 24.2 ms |

  At DEP16 the step is GPU-bound, so its step time does not change; the freed host time only shows up where the host is on the critical path, as at DEP4 above.

## Details

- The clamp leaves the existing `max_decode_tokens` and `max_num_reqs` checks in place. Those checks still drop oversize sizes for dynamic speculative decoding.
- #61869 copies the old rounding rule into `AttnMetadataCudaGraphs.capture_keys` for the target's query length. That copy may want the same treatment once both PRs land.
