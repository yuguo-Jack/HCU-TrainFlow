# [Bugfix] Retry multimodal cache misses in common endpoints

[Upstream PR](https://github.com/vllm-project/vllm/pull/61656) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Propagates multi-modal processor-cache drift as a structured request result
instead of changing the `AsyncLLM` generator exception contract. Serving paths
can then retry a transient request once while other consumers retain their
existing output-based error handling.

This supersedes the earlier exception-based implementation in this PR and
addresses both review findings without passing replay callbacks into
`AsyncLLM`.

## Claims

- Add `RequestOutput.error: RequestError | None`, aligned with the existing
  `PoolingRequestOutput.error` contract.
- Represent a generation cache miss as `finish_reason="error"` plus
  `RequestError(code="multimodal_cache_miss", retryable=True, ...)`.
- Abort sibling children for an `n > 1` parent request and emit one structured
  terminal error to the parent collector.
- Retry a pre-output transient error once in Chat Completions and Completions.
  Multi-modal cache misses re-render the retained source request with
  `skip_mm_cache=True`; other retryable errors re-render normally.
- Keep `_collect_batch` as the common pooling error boundary and retry its
  `RetryableRequestError` once in the ordinary pooling serving path. This
  covers OpenAI and Cohere Embeddings while preserving the retryable 503
  mapping for direct `_collect_batch` consumers such as flash score/rerank.
- Preserve a second failure as `RetryableRequestError`; non-streaming HTTP
  requests receive 503.

## Details

P0 keeps a metadata-only shadow of the P1 multi-modal cache. On a P0 hit, the
rendered engine input may omit the tensor. If P1 has lost that item, replaying
the same rendered input cannot recover. The engine therefore invalidates the
stale P0 hash and emits a structured retryable error. Eligible serving paths
retain the source request, rebuild it, and bypass the sender cache only for the
multi-modal cache-miss retry.

Keeping the miss in `RequestOutput` avoids changing the `AsyncLLM` contract for
Responses, Batch, Beam Search, Speech-to-Text, scale-out, and other consumers.
They continue to receive terminal output with `finish_reason="error"` and can
apply their existing error policy.

### Why this is not duplicate work

#61645 was the earlier external/client-retry alternative and was closed in
favor of this maintainer-requested endpoint-owned direction. A current open-PR
search found no other implementation of this recovery path; #61656 is the
existing PR being updated, not a new duplicate.

@DarkLight1337 Thanks for triggering the review. After tracing both findings, I agree that using an exception from AsyncLLM as the cache-miss control signal changes the contract for every AsyncLLM consumer. In particular, beam search expects a terminal `RequestOutput` with `finish_reason="error"`; if `generate()` raises, `asyncio.gather()` exits before that logic runs. Responses, speech-to-text, and flash late-interaction pooling have similar compatibility issues.

I would therefore like to revise the design as follows:

- `AsyncLLM.generate()` and `encode()` will not raise `MultiModalCacheMissError` as the retry signal.
- Add structured `RequestOutput.error: RequestError | None` for generation, aligned with the existing `PoolingRequestOutput.error`.
- Represent a generation cache miss as `finish_reason="error"` plus `RequestError(code="multimodal_cache_miss", retryable=True, ...)`.
- Chat Completions and Completions will inspect this structured terminal output before yielding anything, re-render with `skip_mm_cache=True`, and retry once.
- OpenAI Embeddings will make the same decision from `PoolingRequestOutput.error`.
- Responses, Batch, Beam Search, Speech-to-Text, scale-out, score/rerank, and Cohere will not gain automatic retry; they will retain their existing output-based error behavior. In particular, flash score/rerank will preserve the existing retryable 503 mapping.
- For parent requests with `n > 1`, a cache miss from one child will abort the siblings and emit one structured terminal error to the parent collector.

This is a somewhat larger output-contract change than the exception approach, but it keeps a cache miss as a request-level result rather than a generator failure and avoids regressions in existing consumers.

Does this revised structured-output direction look acceptable before I implement it?

File: `vllm/v1/engine/async_llm.py` · line None

🔴 Endpoints without the new retry wrapper now get a raw `MultiModalCacheMissError` (a RuntimeError) instead of an output with `finish_reason="error"`. Streaming Responses, beam search and speech-to-text lose their error handling. The output-processor branch fires for every AsyncLLM request with a queue. AsyncLLM re-raises the miss unconverted at both sites. Fix: have AsyncLLM raise a `RetryableRequestError` that wraps the miss, or a subclass of it the retry wrappers can catch, so every consumer gets a GenerationError. This covers both sites (async_llm.py:807, async_llm.py:1072).

<details>
<summary>Why this was flagged</summary>

The trigger is a P0/P1 multi-modal cache drift on any AsyncLLM request that does not come from chat or completion. Examples are Responses (responses/serving.py:665), beam search (beam_search/online.py:90) and the decisions `encode` calls. The new branch at output_processor.py:749 now puts `MultiModalCacheMissError` on the queue whenever `req_state.queue is not None`. AsyncLLM then re-raises it unchanged at async_llm.py:807/1072. On the base branch these callers got a RequestOutput with finish_reason "error", or a pooling output with a retryable `error`. They turned that into a GenerationError and returned a 500, or an SSE error event. Now streaming Responses only catches `GenerationError` (responses/serving.py:1395), so the RuntimeError escapes and the SSE stream is cut off with no error event. Non-streaming paths return 500 instead of the 503 the PR description promises for ineligible paths.

**Verification:** output_processor.py:749-771 puts `MultiModalCacheMissError(...)` on the queue and does `continue`, so no RequestOutput with finish_reason="error" is produced. async_llm.py:807 and 1072 re-raise it unchanged as a plain `RuntimeError` (multimodal/cache/base.py:33). Streaming Responses catches only `GenerationError` at serving.py:1395, so the SSE stream is cut off with no error event.
