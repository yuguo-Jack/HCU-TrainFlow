# [Bugfix][Attention] FlashInfer sparse MLA: launch at most 65535 tokens per trtllm-gen call 

[Upstream PR](https://github.com/vllm-project/vllm/pull/63791) · state: closed · merged: True

## Original PR description


## Overview

The FlashInfer sparse MLA kernel silently skips attention for every token of a forward pass with more than 65535
tokens (e.g. any full prefill step at `--max-num-batched-tokens 65536`), returning uninitialized memory. This PR
launches it in chunks of at most 65535 tokens that write into one preallocated output. Root cause on the FlashInfer
side: flashinfer-ai/flashinfer#3125.

## Claims

- Fixes the silent skip for `FLASHINFER_MLA_SPARSE` (**DeepSeek-V3.2 / GLM-5 / GLM-5.3 DSA layers**) and for the prefill of
  `FLASHATTN_MLA_SPARSE` (FA4), which delegates prefill to the same kernel. Covers prefill, decode, mixed steps and DCP.
- Steps with <= 65535 tokens issue the same single launch as before (decode and CUDA graphs are unchanged).
- No extra memory: chunks write into slices of one output (and LSE) buffer.
- The DCP softmax-stats workspace is sized for one launch (<= 65535 tokens) instead of `max_num_batched_tokens`.

<details>
<summary>Why not FlashInfer's <code>cum_seq_lens_q</code> (#3131 / #3238)?</summary>

Measured at kernel level (FP8 KV, top-k 2048, 16 and 64 heads, 1 to 131072 tokens):
- trtllm-gen cannot return the LSE with `cum_seq_lens_q`, and DCP needs it.
- `seq_lens` becomes per request. The static-sparse (rope) path uses it as each token's active top-k length, so rows
  shorter than the top-k width attend the `-1` padding and give wrong outputs.
- Grouping tokens by real request launches `num_reqs x max_q_len` CTAs: one long prefill plus 511 decodes ran ~9.5x
  slower.
- Packing tokens into uniform pseudo-requests (no-rope, no LSE) is bit-exact but no faster (within 1%): the MLA
  generation kernels still run one CTA per token.
- For comparison, chunked launches cost the same per token as one launch. Chunk + `torch.cat` is 2-11% slower, and
  its extra output copy (8 GiB at 65536 tokens with 64 heads) is outside vLLM's memory profile.

</details>

## Details

**Root cause.** `FlashInferMLASparseImpl._forward_mqa_kernel` passes every query token to
`trtllm_batch_decode_with_kv_cache_mla` as its own request (`q.unsqueeze(1)`, `topk_indices.unsqueeze(1)`), and
trtllm-gen maps requests to `gridDim.z`, whose CUDA limit is 65535. A larger launch makes `cuLaunchKernelEx` return
`CUDA_ERROR_INVALID_VALUE`, which FlashInfer only prints to stderr. Found with a profile that showed zero sparse-MLA
kernels in every 65536-token step.

**Fix.** Allocate `out` (and `lse`) once and call the kernel on row slices of at most 65535 tokens, passing the
matching `out` / `lse` slices. FlashInfer accepts caller-owned output, so no copy is needed. The trtllm-gen
softmax-stats slab is carved per launch, so the DCP workspace only needs to cover one launch.

**Limitations.** Steps with more than 65535 tokens issue one extra kernel launch per additional chunk.

AI assistance (Claude Code) was used to investigate and write this change. The submitter reviewed every changed line
and ran the tests above. Not a duplicate: no open vLLM PR touches this backend's 65535-token limit (searched
"flashinfer_mla_sparse", "65535 flashinfer", "cum_seq_lens_q").
