# [Frontend][Responses] Support client-executed tool_search

[Upstream PR](https://github.com/vllm-project/vllm/pull/59792) · state: open · merged: False

## Original PR description

## Purpose

Responses clients can defer tools behind a client-executed `tool_search` tool. Codex does this for MCP servers and connectors when the model catalog sets `supports_search_tool`. vLLM renders only `function` and `namespace` tools, so with such a client:

1. the model never sees `tool_search` (it is dropped while building the chat-template tools);
2. tools returned in a `tool_search_output` item are never exposed to the model;
3. the follow-up request that carries the `tool_search_call` / `tool_search_output` items fails with `Unsupported input item type: tool_search_call`.

Clients that inline every tool instead pay for it on each turn: with Codex and a typical MCP and connector setup, the request was 647 KB (about 158K prompt tokens) per turn, against 71 KB with deferred tools.

## Changes

- `responses/tool_search.py` (new): a client `tool_search` is presented to the model as a function named `tool_search`; tools loaded by `tool_search_output` input items are added to the tools the model sees (namespaces loaded by separate searches are merged).
- `ResponsesRequest.model_tools` / `client_tool_search`: the tool list used to render the prompt, build the parser and map tool-call names. `request.tools`, which is echoed back in the response, is unchanged.
- Output: a model call to `tool_search` becomes a `tool_search_call` item (`execution: "client"`, parsed arguments), in both the non-streaming and the simple streaming path. Streaming emits it as `response.output_item.added` / `response.output_item.done` without argument deltas, since the SDK defines no tool-search delta events.
- Input: a `tool_search_call` item becomes an assistant tool call; a `tool_search_output` item becomes a tool message listing the loaded tools by callable name.
- Server-executed `tool_search` is still not exposed. A function tool literally named `tool_search` keeps its normal behavior.

Not covered: the Harmony (gpt-oss) path, and strict structural tags under `VLLM_ENFORCE_STRICT_TOOL_CALLING`, which still build from `request.tools`.

## Not a duplicate

No open or merged PR or issue covers `tool_search` in the Responses API (searched `tool_search`, `tool_search responses`, `client-executed tool search`). Namespace-tool support is the closest prior work; this builds on its flattening and name mapping.
