# [CI] Update stale branches before committer `/ci run`

[Upstream PR](https://github.com/vllm-project/vllm/pull/58424) · state: closed · merged: False

## Original PR description

Committers currently have to update a stale PR branch before commenting `/ci run`. This makes `/ci run` (including `all` and `nightly`) attempt that update first, wait for the new head, and reuse the existing freshness and duplicate-build checks before launching CI.

Automatic updates require repository write, maintain, or admin permission. Update failures, timeouts, and branches that remain stale do not start a build. `--allow-stale` skips updating; author delegation, `/amd-ci`, labels, and auto-merge behavior stay unchanged.

The workflow uses its existing `GITHUB_TOKEN` with `contents: write`. Fork updates remain subject to the bot's access, and GitHub Actions checks following bot updates may require maintainer approval. Live fork permissions have not been tested.

- Thangnguyenvn98 · COMMENTED · 2026-09-23T21:24:31Z · [source](https://github.com/vllm-project/vllm/pull/58424#pullrequestreview-5296957143)

Thanks for picking this up, the script logic looks right to me: it passes `expected_head_sha`, the recursion is bounded, and it rechecks builds on the new head. My concern is the credential. I think `GITHUB_TOKEN` will stop the update from working in a lot of real cases:

**1. It can't push a merge that includes workflow-file changes.** GitHub rejects any push from a GitHub App that touches `.github/workflows/` unless the app has the `workflows` permission, and `GITHUB_TOKEN` can never be given that permission. So when main has changed a workflow since the branch point, `update-branch` fails with `refusing to allow a GitHub App to create or update workflow ... without workflows permission`. We've already hit this in the org: vllm-project/semantic-router#3902 (Mergify, same cause). Main has had 11 workflow-touching commits in the last 30 days, so most branches older than a few days will trail one. This PR itself edits a workflow, so right after it merges every stale PR would fail the auto-update. The failure is safe (no build starts), but in those cases the feature does nothing.

**2. It probably can't push to forks.** The docs say `GITHUB_TOKEN` is "limited to the repository that contains your workflow". The push target for a fork PR is the fork, and almost all of our open PRs come from forks. I haven't verified this live, and as the PR description notes, neither has anyone else, so it's worth testing before we rely on it.

**3. When it does work, it adds a different click.** Per the [GITHUB_TOKEN docs](https://docs.github.com/en/actions/concepts/security/github_token), a `synchronize` event caused by `GITHUB_TOKEN` creates workflow runs in an approval-required state. After the auto-update, pre-commit and the other `pull_request` checks sit waiting on the new head until someone clicks "Approve and run". That swaps the "Update branch" click for another one.

**Suggestion:** keep the workflow at `contents: read`. Mint a token from a vLLM GitHub App (with `contents: write` and `workflows`) using [`actions/create-github-app-token`](https://github.com/actions/create-github-app-token), and use it only for the `update-branch` call. That:
- handles merges that include workflow files
- triggers normal `pull_request` runs, since only `GITHUB_TOKEN` pushes get the suppression and approval gate
- should be able to push to fork branches that allow maintainer edits (Mergify does this as an installed app), though it still needs a live check
- keeps write access off the other command paths and the self-hosted runner job
