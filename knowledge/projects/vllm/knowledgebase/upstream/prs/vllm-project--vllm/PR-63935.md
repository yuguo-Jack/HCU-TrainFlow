# [Perf][Attention][DCP] Gather the MLA chunked prefill context in fp8 under decode context parallelism

[Upstream PR](https://github.com/vllm-project/vllm/pull/63935) · state: open · merged: False

## Original PR description

## Overview

Stacked on #64548, which replaces `reorg_kvcache` with an index-based row gather; please review that one first. Until it merges, this PR also shows its two commits. This PR adds the last three:

- `[Attention][DCP] Dequantize fp8 rows in the MLA DCP context row gather`
- `[Attention][DCP] Keep the MLA DCP context in fp8 through the all-gather`
- `[ROCm][DCP] Take the AITER MLA DCP context rows from the chunk metadata` (not fp8; can be dropped, see Details)

With decode context parallelism (DCP), a plain fp8 KV cache and an fp8 prefill query, the MLA chunked-context loop dequantizes each rank's cached rows into a bf16 (or fp16) workspace and all-gathers those rows across the DCP group. This PR keeps the rows in fp8 as stored through the local gather and the all-gather, and dequantizes them with the layer's `k_scale` in #64548's row-gather kernel. Everything after the gather (`kv_b_proj`, the K/V pack, attention, LSE merge) gets the same tensors as before.

## Claims

- Half the DCP context all-gather bytes (576 B per row instead of 1,152 B) and half the DCP context workspace.
- The prefill K/V are bit-identical to the default path whenever this path is on. The kernel dequantizes like `gather_and_maybe_dequant_cache` (fp32 product, rounded to nearest even), and every DCP rank holds the same `k_scale`, so dequantizing after the all-gather gives the same values as dequantizing before it. This holds for any `k_scale`; the previous revision of this PR required `k_scale == 1.0`.
- Off unless the backend opts in (`supports_fp8_dcp_context`, set only for `TOKENSPEED_MLA`), DCP > 1, the prefill query is fp8, the model dtype is bf16 or fp16, and every layer of the KV-cache group has an `fp8`/`fp8_e4m3` cache. Otherwise the default path runs unchanged.

### Performance

End-to-end results for this revision are being measured on top of #64548. They will be added here before this PR is marked ready for review.

Component: all-gather plus row gather per chunk, on one node of 4 NVIDIA GB300 GPUs (NCCL `all_gather_into_tensor`, CUDA events, median over 300 calls after 20 warm-ups, time of the slowest rank in each call; chunks built by `build_mla_chunked_context_metadata`, `k_scale` 0.37):

| DCP | Chunk | bf16 rows (#64548) | fp8 rows (this PR) |
|---|---|---|---|
| 2 | 66,304 rows, 1 request | 131.7 us | 92.8 us |
| 2 | 64,000 rows, 64 requests | 131.7 us | 92.8 us |
| 2 | 4,096 rows, 1 request | 47.8 us | 39.6 us |
| 4 | 66,304 rows, 1 request | 150.2 us | 105.1 us |
| 4 | 64,000 rows, 64 requests | 152.2 us | 107.2 us |
| 4 | 4,096 rows, 1 request | 45.7 us | 35.5 us |

The two paths' outputs were bit-identical on every rank and every chunk (12 chunks per DCP size).

## Details

- **Workspace:** allocated in fp8, not viewed from a bf16 one, because the direct symmetric-memory KV gather sizes its buffers from the workspace dtype; both halve.
- **JIT warmup:** with a plain fp8 cache, the MLA DCP manager (see #64548) also registers the dequantizing variant of the row gather, because the builder picks the path per KV-cache group. When the group keeps the default path, that variant costs one small compile at startup.
- **No power-of-two requirement:** the previous revision needed power-of-two `kv_lora_rank` and `qk_rope_head_dim` because its kernel used them as block widths. #64548's kernel masks padded blocks, so that condition is gone.
- **Separate ROCm commit:** the ROCm AITER MLA DCP prefill now takes its context row indices from the chunk metadata (`context_row_indices`, cast to the int32 its fused gather takes) instead of building them with its own helper, which is removed with its test. It is not fp8 and was not run on ROCm; it can move to its own PR or be dropped.
- **Not covered end to end:** backends other than `TOKENSPEED_MLA` (they stay off; enabling one is a one-line opt-in after validation).
