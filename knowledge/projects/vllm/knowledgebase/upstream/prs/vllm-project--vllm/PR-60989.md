# [MRV2][Spec Decode] Refactor AR speculators and enable CUDA Graph for draft model

[Upstream PR](https://github.com/vllm-project/vllm/pull/60989) · state: closed · merged: True

## Original PR description

## Overview
Enable CUDA graph capture and replay for Model Runner V2 draft-model speculators, as follow-up work to [#43091](https://github.com/vllm-project/vllm/pull/43091). 

It also introduces a shared `AutoRegressiveSpeculator` base class to unify the CUDA Graph management and autoregressive decoding logic between target-dependent and standalone draft-model speculators.

## Claims

1. Introduce a shared AutoRegressiveSpeculator abstraction
    - Move common CUDA Graph management and multi-step decoding logic into `AutoRegressiveSpeculator`.
    - Introduce `_prefill()` and `_generate_draft()` hooks to handle implementation-specific behavior.
    - Keep target-dependent hidden-state and multimodal handling in `TargetDependentARSpeculator`.
    - Keep standalone draft-model input preparation and correction-token handling in `StandaloneARSpeculator`.

2. Enable CUDA Graph support for standalone draft models
    - Support CUDA Graph capture and replay for draft-model prefill and multi-step decode.

## Validation
Ran the offline draft-model spec-decode evaluation with `FULL_AND_PIECEWISE` on Qwen3-32B / Qwen3-1.7B using 400 MT-Bench prompts, temperature 0, and 256 output tokens:

```
python examples/features/speculative_decoding/spec_decode_offline.py \
  --method draft_model \
  --model-dir /shared/models/modelscope/models/Qwen/Qwen3-32B \
  --draft-model /shared/models/modelscope/models/Qwen/Qwen3-1.7B \
  --num-spec-tokens 3 \
  --dataset-name hf \
  --dataset-path philschmid/mt-bench \
  --num-prompts 400 \
  --temp 0 \
  --output-len 256 \
  --max-model-len 10000 \
  --cudagraph-mode FULL_AND_PIECEWISE \
  --gpu-memory-utilization 0.95
```

Thanks @wxsIcey for following up on the cudagraph work!

Now that the cudagraph support has been added, i see opportunities for code sharing between `TargetDependentARSpeculator` and `StandaloneARSpeculator`. But rather than having the latter derive from the former, I think they should both be siblings deriving from the same base class. We can call the base class `AutoRegressiveSpeculator`. The hierarchy would look like:
```
DraftModelSpeculator
└── AutoRegressiveSpeculator          (new)
    ├── TargetDependentARSpeculator   (Eagle / MTP / Gemma4)
    └── StandaloneARSpeculator
```
**`AutoRegressiveSpeculator`** owns the CUDA graph managers and the decode loop, moved from `TargetDependentARSpeculator` mostly unchanged: `init_cudagraph_manager`, `capture`, `_multi_step_decode`, `_fused_multi_step_decode`, `_generate_fused_drafts`, and the decode half of `propose()`. Subclasses implement two methods:
- `_prefill(...)`: the prefill graph body (forward + sample draft 0).
- `_generate_draft(...)`: one decode step (forward, sample, write `draft_tokens[:, current_draft_step]`, advance inputs for the next step).

**`TargetDependentARSpeculator`** is a pure move with no behaviour change. It keeps its hidden-state/multimodal handling, `_prefill`, `_generate_draft`, and the prefill half of `propose()`.
**`StandaloneARSpeculator`** keeps only what's specific to a separate draft LM: the expanded prefill with the correction token, `_prepare_decode_inputs`, and a simple `_generate_draft`. It sets `draft_seq_len_offset = 1` to account for the correction token.

What do you think of that direction?

```bash

  --max-model-len 4096 --max-num-seqs 256 \
  --speculative-config '{"method": "draft_model", "model": "Qwen/Qwen3-0.6B", "num_speculative_tokens": 3}'

python tests/evals/gsm8k/gsm8k_eval.py --port 8000 --num-questions 1319 \
  --max-concurrency 256 --max-tokens 256 --temperature 0 --seed 0
```

**What we see**
- On main it is intermittent: one launch finished GSM8K at 88.6% (same as no CUDA graphs). Another segfaulted in `cuGraphLaunch` (`at::cuda::CUDAGraph::replay()`) partway through, right after the draft prefill had replayed FULL uniform graphs of about 180–200 requests (5 tokens each).
- With wider uniform decode graphs, it fails on the first full batch every time, with `CUDA error: an illegal memory access`. In our case these come from #63406, which lets SM100 decode graphs reach `max_num_seqs` (256 requests × 5 tokens).
- Keeping the draft prefill on eager or PIECEWISE (no FULL uniform graphs for the expanded `K + 2` batch) avoids the crash, and GSM8K matches main.
- With decode graphs capped at 64 requests, it also runs cleanly.
- EAGLE3 on the same setup is unaffected.

So the trigger seems to be replaying the draft-model FULL prefill graph for a large uniform batch (`num_reqs × (K + 2)` tokens). We're happy to help dig into the root cause; let us know if you'd like more logs.

- Pb314314 · comment · 2026-11-04T05:23:34Z · [source](https://github.com/vllm-project/vllm/pull/60989#issuecomment-6623315086)

@wxsIcey Following up on the crash above: we found the root cause and opened a fix in #65598. We'd like your opinion on it.

**Root cause**
1. The standalone draft-model prefill is a uniform batch of `K + 2` tokens per request (it adds the correction token). FlashInfer's `reorder_batch_threshold` is `max_decode_query_len()` = `K + 1`, so the builder classifies every request as a prefill. On SM100 it then takes the TRTLLM prefill path.
2. On that path, `FlashInferMetadataBuilder.build()` creates `cum_seq_lens_q` as a new tensor on each call (`qo_indptr[prefill_start:] - qo_indptr[prefill_start]`).
3. Metadata is built outside the graph, so the FULL draft-prefill graph keeps the address that tensor had at capture time. The tensor is then freed and its memory reused. At replay, the TRTLLM context kernel reads query offsets from that memory. The result is wrong drafts or, for large batches, an illegal memory access or a segfault in `cuGraphLaunch`.

This explains what we saw:
- It is intermittent on main and depends on what the freed memory holds.
- It does not happen with EAGLE3: its `K + 1` prefill takes the decode path, which only reads persistent buffers.
- It goes away when the draft prefill runs eagerly or with PIECEWISE graphs.
- It reproduces reliably once uniform graphs cover more requests.

**Fix in #65598**

`build()` now writes the offsets into a persistent buffer, the same way `paged_kv_indptr` already works. On 1x GB200 (Qwen/Qwen3-8B with Qwen/Qwen3-0.6B as the draft, K=3, GSM8K, 1319 questions):
- C256 and C32 both reach 0.886.
- Mean accepted tokens per draft is 2.44, the same as with `cudagraph_mode=PIECEWISE`.
- The new unit test fails on main and passes with the fix.

**Questions for you**
1. Is fixing the TRTLLM prefill metadata the right approach? The alternative is to treat the `K + 2` draft prefill as a decode, for example by having `max_decode_query_len()` account for the standalone draft model. Its docstring currently says no V2 speculator builds a query wider than `K + 1`, which is no longer true after this PR. That would route the draft prefill through the decode kernels, but it would also change the target's decode/prefill split. So we kept the fix local to the metadata.
2. With an FP8 KV cache and a non-FP8 query, the same TRTLLM prefill path also makes a contiguous copy of `block_tables` on each build, which looks like the same problem under a FULL graph. We haven't tested that configuration. Do you know whether the draft model runs with that combination in practice?

Happy to adjust the fix based on your feedback.
