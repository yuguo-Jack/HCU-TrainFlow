# [Bugfix][Core] Drop streaming updates that would overflow max_model_len

[Upstream PR](https://github.com/vllm-project/vllm/pull/63113) · state: open · merged: False

## Original PR description



## Overview

Streaming-input sessions merged the next input chunk into their prompt without checking the accumulated length against `max_model_len`, wedging or crashing the engine. This PR rejects such an update at merge time, parks the session so a shorter update can continue it, and adds scheduler-level and e2e regression tests.

Fixes #62707 (V2 evidence). Same defect family as #42489, whose fix PR #42502 has been stalled with merge conflicts since Sep 30.

## Claims

- A streaming update whose merged session would leave no room for a sampling step within `max_model_len` is now dropped (with a server-side warning) instead of being merged.
- The session stays **resumable** (`WAITING_FOR_STREAMING_REQ`): a subsequent, shorter update continues it normally. This is the softer outcome requested in the [#42502 review](https://github.com/vllm-project/vllm/pull/42502#issuecomment-3624351968) ("rather than FINISHED_LENGTH_CAPPED, end the reply and leave the session resumable").
- No regression for sessions whose updates fit: the merge path is unchanged apart from the pre-check, which only trips in the previously-fatal region.

Ran on an aarch64 dev box (Jetson Thor) against this checkout with `VLLM_TARGET_DEVICE=cpu`, `pytest 7.4.4` via `uv`/`.venv` per the contributing guide.

**1. New tests fail on base (`main` @ b3b0bc3059) for the reported reason:**

```
$ VLLM_TARGET_DEVICE=cpu .venv/bin/python -m pytest tests/v1/streaming_input/test_scheduler_streaming.py -q -k "overflow"
4 failed, 15 deselected
```

The regression test diverges exactly at the unguarded merge (`assert <RequestStatus.WAITING: 1> == <RequestStatus.WAITING_FOR_STREAMING_REQ: 4>`), i.e. main merges an update that pushes the session to 19 tokens with `max_model_len=16`.

A standalone scheduler-level drive of the same scenario on base shows the downstream failure — the session is merged beyond the limit and then wedges with empty schedules forever:

```text
after stop: status=WAITING num_tokens=19        # > max_model_len=16, merged anyway
turn 3 (poisoned):
  scheduled={'session': 5} num_tokens=19 computed=16   # prefill clamped mid-way
  scheduled={} num_tokens=19 computed=16               # wedged: zero-token clamp (skip), never progresses
```

On the V2 runner this zero-clamp path is the one that produced the negative `num_scheduled_tokens` (-14 / -36) and the `assert num_tokens > 0` EngineCore crash reported in #62707; on current main the clamp is floored at zero, so the session wedges in `RUNNING` and the client hangs with no further outputs and no error.

**3. No regression in the core scheduler suite.** `tests/v1/core/test_scheduler.py` run on base vs. with the fix (237 tests): `54 failed, 183 passed` on both, with **byte-identical failure lists** — all 54 are environment failures on this box (model-architecture inspection subprocess / GPU-only fixtures), unaffected by this change.

**4. CI coverage / disclosure.** The new scheduler-level tests run in the `V1 Executor + Worker` step (`pytest -v -s v1/streaming_input`, H200 MIG 18GB). The new e2e test in `tests/v1/e2e/general/test_streaming_input.py` runs in the `E2E` step (`pytest -v -s v1/e2e/general ...`). **I could not run the GPU e2e test locally** (the dev box is aarch64 Jetson Thor without a CUDA build of this checkout); it mirrors the existing patterns in that file (`finish_reason` turn-boundary counting, event-based input pacing, `asyncio.wait_for` timeout instead of sleeps) and needs CI/human confirmation. The e2e test asserts: the overflowing chunk produces no turn, the session continues with a fitting chunk (2 turn boundaries), and the stream finishes with `has_unfinished_requests() == False`.

No model evaluation is included: the change does not alter generation for sessions that stay within `max_model_len` (the guard only trips in the previously-fatal region, where no valid output exists to preserve).

## Details

**Root cause.** `_update_request_as_session` extends the session prompt with (all outputs but the last sampled token) + the update's tokens, with no length check. `check_stop` only fires when output tokens are appended, so nothing bounds the session at a turn boundary. Once the merged `num_tokens` exceeds `max_model_len`:

1. The waiting-branch prefill schedules the full remaining chunk (it has no `max_model_len` clamp), computing positions past the limit, and drives `num_computed_tokens` past it.
2. The running-branch clamp `max_model_len - num_computed_tokens - num_sampled_tokens_per_step` then goes negative. On current main `_reserve_prefill_lookahead` floors it to zero, so the request is skipped every step and **wedges permanently in `RUNNING`** while occupying a sequence slot; on the V2 build in #62707 the negative value reached `num_scheduled_tokens` and killed EngineCore (`assert num_tokens > 0` → `EngineDeadError` for the client).

**Fix.** Reject the update **before** mutating the session when the merged token count `(num_tokens - 1) + len(update.prompt_token_ids)` plus one sampling step would exceed `max_model_len`. On rejection:

- `_handle_stopped_request` (queued-update path) parks the session in `WAITING_FOR_STREAMING_REQ` and returns `False`, reusing the exact bookkeeping of the existing queue-empty path (the caller's `continuing_reqs` machinery then re-enqueues it into the KV-holding waiting queue).
- `add_request` (parked-session path) needs no change: the rejected update simply leaves the session parked.

The boundary matches the one reviewed in #42502: a merged session of `max_model_len` tokens is rejected (`>=`), one token less is accepted; the accepted edge case yields at most a single-sampled, length-capped turn, which mirrors how an ordinary request with a `max_model_len`-boundary prompt behaves.

**Relationship to #42502.** Not a duplicate: #42502 predates the V2 scheduler split, has been unmergeable (conflicts) since Sep 30, and its outcome (`FINISHED_LENGTH_CAPPED` for the whole session) is the one the maintainer asked to soften. This PR implements the softer outcome on current main; #42502 can be closed in favor of it.

**Limitations / follow-ups.**

- The dropped chunk is reported only via a server-side `logger.warning`; there is no per-chunk error surfaced to the client stream (the collector has no channel for it today). Surfacing a turn-level `model_context_window_exceeded` — as the `/v1/messages` path does (#59616) — is a natural follow-up, as is the bounded-session design discussed in #51948/#53876.
- Sessions already parked at the boundary reject every further update until closed; they hold KV blocks exactly like any other parked streaming session and are cleaned up when the client closes the input generator.
