# [ROCm][Perf] Reuse compiled FlyDSL host launchers

[Upstream PR](https://github.com/vllm-project/vllm/pull/64008) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

Reduce CPU overhead for warm FlyDSL launches by reusing compiled host launchers instead of repeating JIT argument binding and cache-key construction. Covers DeepSeek V4/V4.1 mono decode, Kimi K3 specialized decode, TurboQuant and UltraQuant.

## Claims

- Fix all nine remaining in-tree FlyDSL host launchers using the warm JIT path.
- Reduce measured host enqueue overhead by approximately 88% for TurboQuant and 89% for UltraQuant.

## Validation

Measured on gfx950 with PyTorch 2.10.0 and FlyDSL 0.4.0: 30 alternating batches of 100 launches, with GPU synchronization outside timed sections. Times are median (min–max), µs.

| Launcher configuration | Before | After |
| --- | --- | --- |
| TurboQuant: B1, Hk8, GQA8, D128, BS16, context256 | 72.33 (70.71–74.15) | 8.57 (8.15–9.74) |
| UltraQuant: B1, Hk1, GQA8, D256, BS32, context2048 | 73.57 (72.98–79.64) | 8.30 (8.08–10.94) |

Existing GPU correctness suites: **68 passed before and after**. Dynamic batches **1→2→4→8→3→1** reuse the same compiled callable and match reference outputs. Dynamic arguments, row strides, compile-only and graph replay checks passed; pre-commit including mypy passed.

```bash
.venv/bin/python -m pytest --noconftest -q \
  tests/kernels/turboquant/test_flydsl_turboquant_decode.py \
  tests/kernels/ultraquant/test_flydsl_decode_d256.py
```

Validation used a source-only editable installation. Full-model accuracy, TP serving and end-to-end performance were not measured because the target checkpoints and a complete ROCm extension build are unavailable.

## Details

Targets host dispatch during warm eager execution and graph capture. The results measure host enqueue time; steady graph-replay speedup was not measured. Open-PR searches found no duplicate fix for these call sites.
