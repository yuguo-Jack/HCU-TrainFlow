# [Bugfix] Prevent prompt text leaking into streamed output when prompt ends mid-UTF-8

[Upstream PR](https://github.com/vllm-project/vllm/pull/48854) · state: open · merged: False

## Overview

Fixes #48853. Some `/v1/completions` requests send token ids that end partway through a UTF-8 character. For those requests, `FastIncrementalDetokenizer` streams the whole prompt text in its first delta. This PR sends such requests to `SlowIncrementalDetokenizer`.

It also fixes a gap in the slow path's `detokenize_incrementally` that this routing exposes for byte-fallback (SentencePiece `<0xNN>`) tokenizers.

## Claims

- **No prompt leak.** A token-id prompt that ends mid-character no longer echoes the prompt text in the streamed output. This holds for byte-level BPE (gpt2, Qwen, Llama-3) and byte-fallback (Llama-2/CodeLlama, Gemma) tokenizers.
- **Byte fallback drops only the straddled character.** For byte-fallback tokenizers, the output after such a prompt drops only the character that straddles the prompt boundary. Byte-level BPE has always behaved this way. Before this fix, a prompt ending k bytes into a character also lost the next k−1 generated characters, and later characters in the same byte run could come out as U+FFFD.
- **Byte-level BPE output is unchanged.** It is identical before and after the fix on every cut checked (503 prompt cuts over five tokenizers).
- **Trailing special tokens no longer hide the tail.** Skipped trailing special tokens no longer hide an incomplete prompt tail from the routing check. This follows a review comment.

## Details

**Root cause of the leak.** `FastIncrementalDetokenizer` primes `DecodeStream(ids=prompt_token_ids)`. The stream's lazy prefill sets its text prefix only when the decoded prompt does not end in U+FFFD. So for a prompt ending mid-character the prefix stays empty, and the first completed decode returns the whole prompt. `from_new_request` now checks the last 8 non-skipped prompt tokens for a trailing U+FFFD and uses the slow path for those requests.

**Root cause of the byte-fallback over-skip.** The routing made this reachable for fast tokenizers. `detokenize_incrementally` slices `new_text[len(prefix_text):]`.
- Byte-level BPE decodes an incomplete sequence to one U+FFFD.
- The tokenizers `ByteFallback` decoder emits one U+FFFD per byte, and for the whole byte run whenever the run fails to decode. That includes complete characters earlier in the run.
- So `prefix_text` was k or more characters longer than the text it stands for.

The fix:
- When `prefix_text` ends in U+FFFD and `new_text` does not start with it, the trailing U+FFFD run is counted as bytes. Only the characters those bytes cover are skipped, including the straddled one.
- After that first delta, the next window keeps starting at `prefix_offset` rather than the mid-character `read_offset`. Otherwise generated bytes that continue the same run decode as U+FFFD.
- For byte-level BPE the run is one U+FFFD covering one character, so the result equals `len(prefix_text)` and nothing changes.

The online derenderer also uses `detokenize_incrementally`, and its window trimming already follows `prefix_offset`.

**Why the U+FFFD-collapse idea was not used.** Collapsing the trailing run to a single U+FFFD fixes prompts where the dangling bytes form their own byte run. When a complete prompt character shares the run, it under-skips and emits U+FFFD. Example: `เลข ๗๗ จังหวัด` cut after `๗` plus one byte gives `'๗� จังหวัด'`.

**Why fall back instead of repairing the fast path.** Re-priming `DecodeStream` with a trimmed prompt and stripping already-seen text is possible. But it changes the output convention (the straddled character would be emitted) and needs more fast-path code. The fallback affects only requests whose prompt ends mid-character.

**Why this is not a duplicate.**
- #51961 (mine) only adds Thai test coverage.
- #63668 caps how many tokens the slow path holds back for malformed output. It edits the same hold condition in `detokenize_incrementally`, so whichever merges second needs a small rebase. The two do not overlap in behavior.
- #51281 and #57330 bound the `DecodeStream` priming window. They do not handle prompts ending mid-character.

**Limitations.**
- Byte-level BPE (and now byte fallback) drops the character that straddles the prompt boundary. This is the existing slow-path convention, and the test oracle `full_text[len(prompt_text):]` encodes it.
- The slow path primes from the last 7 prompt tokens and slices a 5-token prefix window from them. Two cases still give U+FFFD after this PR, as before it, with no prompt leak:
  - The window starts inside a byte-fallback run.
  - Seven or more skipped special tokens follow the incomplete tail.
- A forced `FastIncrementalDetokenizer` (constructed directly) still has the prefill limitation. The `test_decode_streaming` matrix skips forced-fast combos whose prompt ends mid-character, because `from_new_request` never selects that path for them.
- On older transformers, routed requests can render `<|im_start|>` literally. This was seen in the GB10 run (vLLM 0.25.1 image, transformers 5.13.1) for `nvidia/Qwen3-8B-NVFP4` and typhoon2.5-4b. The cause is a transformers bug: an empty `extra_special_tokens` drops `additional_special_tokens` (huggingface/transformers#47848, fixed in 5.18.0). Main's floor (`>= 5.16.1`) still admits 5.16/5.17, but I have not re-checked those versions.
- CI: `tests/tokenizers_` currently runs in no Buildkite step. The "(CPU) Params, Env, Tokenizers, Parser" step in `.buildkite/test_areas/misc.yaml` is commented out ("Disabled until the cmake installation is locked"). The tests above were run locally.

### Suggested helper patch

Move the end index past trailing special IDs **only when `skip_special_tokens=True`**, then take the bounded window. When the flag is false, special-token text is part of the decoded prompt and must remain in the check. This also avoids an O(prompt length) `list(prompt_ids)` copy: the scan visits the trailing special-token run and the slice copies at most eight IDs.
