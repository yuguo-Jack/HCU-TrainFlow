# [Feature] Support batch invariance for ShortConv (LFM2) models

[Upstream PR](https://github.com/vllm-project/vllm/pull/62367) · state: open · merged: False

## Original PR description



## Overview

Fix #61319. LFM2 models (`Lfm2ForCausalLM`, `Lfm2MoeForCausalLM`) can't use batch-invariant mode: with `VLLM_BATCH_INVARIANT=1` the engine refuses to start with `RuntimeError: VLLM batch_invariant mode is not supported for SHORT_CONV_ATTN.` That leaves them without the documented way to get reproducible greedy outputs. This PR lets `SHORT_CONV_ATTN` declare batch invariance. `PLE_SHORT_CONV_ATTN` stays opted out.

## Claims

- LFM2 models start and are batch-invariant under `VLLM_BATCH_INVARIANT=1`. `LiquidAI/LFM2-8B-A1B` passes the full `tests/v1/determinism/test_batch_invariance.py` suite (22/22) on an A40.
- The symptom in #61319 (round 0 of repeated `generate()` calls differs from later rounds) goes away in batch-invariant mode, with prefix caching on.
- No change when `VLLM_BATCH_INVARIANT` is unset.

## Details

**Why #61319 happens.** LFM2 runs with prefix caching on by default (`mamba_cache_mode=align`, block size 16). From round 1 on, any prompt with a full block gets a cache hit, so the first prefill step shrinks (92 → 76 tokens in my probe, where only the 17-token prompt hits). Without batch invariance, kernel selection depends on batch shape. Every sequence in that step then moves by a few ULPs, and near-tied argmaxes flip later. In my runs, two warm rounds never disagreed. With prefix caching on but no prompt long enough to hit, all rounds match. This is the documented "no bitwise reproducibility by default" behavior, and the documented fix is batch-invariant mode, which LFM2 couldn't use. Setting `CUBLAS_WORKSPACE_CONFIG=:16:8 CUBLASLT_WORKSPACE_SIZE=1`, as #61440 does, still leaves 2/8 prompts differing, because this isn't run-to-run atomics.

**Why ShortConv qualifies.** `causal_conv1d_fn` (prefill) and `causal_conv1d_update` (decode) compute each output token from that sequence's own `L_cache` window plus its conv-state slot. There is no reduction across sequences and no split depending on batch size. The rest of the layer is `in_proj`/`out_proj`, which already go through the batch-invariant linear path, plus elementwise gating. The new test pins that property: one sequence's output and final conv state must be bitwise-identical alone and inside batches of different sizes and offsets, with and without an initial state. The test passes on main as well. It guards the property the opt-in relies on, against future kernel changes. What fails on main is engine startup.

**Scope and limitations.**
- `PLE_SHORT_CONV_ATTN` (Qwen4Exp's dilated conv) inherits from `ShortConvAttentionBackend`. It is explicitly kept at `False`: it uses its own packing path, and I couldn't validate it.
- All runs used Model Runner V2 (the default). The check is shared with V1 through `get_mamba_attn_backend`, but V1 wasn't run.
- Spec decoding under batch invariance and LFM2-VL weren't tested.
- Only Ampere (SM86) was tested. The kernel test is wired into the `(H100) Batch Invariance` step.
- I didn't add an end-to-end LFM2 line to CI. If you want one, `VLLM_TEST_MODEL=LiquidAI/LFM2-1.2B ... -k FLASH_ATTN` on the needle test costs ~35 s per variant, and I'm happy to add it.

**Not a duplicate.** The only PR linked to #61319 is #61440. It forces deterministic cuBLAS/cuDNN settings globally, which doesn't address this (see above), and its diff currently spans 891 files. I searched open PRs for `supports_batch_invariance`, `SHORT_CONV_ATTN`/ShortConv, and LFM2 batch invariance. #45819 (GDN) and the Mamba2 BI PRs touch other backends only.
