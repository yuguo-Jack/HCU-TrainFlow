# [Bugfix][Compile] Load AOT compile artifacts serially on every platform

[Upstream PR](https://github.com/vllm-project/vllm/pull/64066) · state: open · merged: False

## Original PR description

## Overview

Load standalone AOT artifacts sequentially in saved order on all platforms, extending the existing ROCm behavior. This removes overlapping restores from `load_all`, which can race over Inductor's shared Triton autotuner cache when bundled snapshots for the same kernel source carry different configurations. Follow-up to [the mechanism report in #58899](https://github.com/vllm-project/vllm/issues/58899#issuecomment-6435155528).

## Claims

- Artifact deserializations started by one `load_all` call now complete one after another in saved order. This removes this caller's concurrent updates to Inductor's shared Triton cache.
- On the tested cache and GPU, 4/4 patched loads produced 1 distinct token-ID/logprob-map pair for one fixed 512-token greedy request. Unpatched loads produced 3 across 4/4 loads. The patched class did not occur among these four unpatched loads. Four loads do not exhaust possible outcomes, and E1 does not compare against the original compiling engine or establish which class is more accurate. These observations do not establish general determinism.
- With tracing enabled on this 20-artifact cache, patched minus unpatched median startup time was −0.05 s launch-to-health and −0.08 s `init engine`. These are descriptive sample differences; uninstrumented startup overhead was not measured. Per-arm counts and ranges are in the table below.
- On full GSM8K (1,319 questions, `tests/evals/gsm8k/gsm8k_eval.py` defaults) with the same model and cache, the two patched loads averaged 71.57% and the two unpatched loads 71.38%. The difference, +0.19 percentage points, is within our predeclared 1.0 percentage-point tolerance on this GSM8K set. That is a screen, not a statistical confidence bound or proof of no regression.
- ROCm behavior is unchanged: it already loaded serially.

**Reproduction (outside CI).** The race needs a compile cache in which several bundled autotuners share one kernel source but carry different configs. Ours comes from a checkpoint we cannot share. The recipe below has replaceable paths (`$MODEL`, `$CACHE`) and one private input, the E1 request.

1. **Build the cache once**, with `VLLM_CACHE_ROOT=$CACHE` and the serve flags in step 3. These flags enter the compile-cache hash, so building and loading must use the same ones.
2. **Check that it qualifies.** During one load, wrap `torch._inductor.triton_bundler.TritonBundler.load_autotuners` and log, for each bundled kernel, its source key and the configs in its `compile_results`. The cache qualifies if one key arrives from several artifacts with different configs. In ours, the fused RMSNorm reduction kernel arrived 36 times, including `R0_BLOCK` 8192 and 4096.
3. **Start, probe, stop**, N times per arm on one GPU, alternating arms (u1 s1 u2 s2 …), each start on a fresh copy of the cache:

   ```bash
   cp -a "$CACHE" "/tmp/cache-$i"
   VLLM_CACHE_ROOT="/tmp/cache-$i" vllm serve "$MODEL" --served-model-name m --port 8000 --seed 42 \
     --max-model-len 262144 --gpu-memory-utilization 0.90 --max-num-seqs 1 --max-num-batched-tokens 8192 \
     --kv-cache-dtype fp8 --mamba-ssm-cache-dtype float32 --mamba-cache-mode align --enable-prefix-caching \
     --attention-config '{"backend":"FLASHINFER"}' \
     --kernel-config '{"linear_backend_per_quant":{"nvfp4_w4a4":"marlin","fp8_w8a8":"marlin"}}' \
     --reasoning-parser qwen3 --default-chat-template-kwargs '{"enable_thinking":true}' --generation-config vllm \
     --limit-mm-per-prompt '{"image":0,"video":0}' --enable-auto-tool-choice --tool-call-parser qwen3_xml
   # after /health:
   python repro_probe.py 8000 > "start-$i.txt"   # one SHA-256 over token IDs and logprobs
   ```

   Then compare the hashes within each arm and across arms.
4. **Requests.**
   - **E1's request (private):** one streamed chat completion with a 128,345-token prompt from an agent transcript; `max_tokens` 512, temperature 0, seed 42, `logprobs` with `top_logprobs` 5, `return_token_ids`, `enable_thinking` with `reasoning_effort` "xhigh", and a per-start `cache_salt`. E1's table compares token IDs plus logprob maps of this request.
   - **Public candidate:** `repro_probe.py` (below) sends vLLM's first 16 five-shot GSM8K prompts from `tests/evals/gsm8k/gsm8k_eval.py` one at a time (temperature 0, seed 42, `max_tokens` 256, the eval's stop strings, `logprobs` 5, `return_token_ids`) and hashes the token IDs, sampled-token logprobs and top-logprob maps. In the four GSM8K loads, every load gave a different hash. On the same GPU, the patched and unpatched loads differed in token IDs on 2 (GPU1) and 4 (GPU0) of the 16 prompts, and in logprobs on all 16. The two patched loads ran on different GPUs and also differed (token IDs on 5 prompts), so these runs do not show whether the probe separates repeated loads on one GPU. We offer it as a candidate request for independent reproduction; E1's private request is the one we have shown to separate the arms over repeated loads.

## Details

**Root cause.**
1. `load_all` maps `_load_entry` over the saved artifacts on a default `ThreadPoolExecutor`.
2. Deserializing an artifact with the static CUDA launcher (the default) reaches `TritonBundler.load_autotuners`. That function stores each bundled autotuner in `CompiledTritonKernels._cache[key(source)]`, one process-wide slot per kernel source.
3. In this bundled loading path, `AsyncCompile.triton` retrieves a static future and removes its source slot. A miss loads the kernel from generated source, may reuse an autotune-cache entry, and can also compile or tune. Static-future resolution itself rechecks the autotune cache.

**What goes wrong.** When several artifacts bundle autotuners for the same source with different configs, concurrent loads interleave these installs and takes. In one earlier traced load, one of 18 sites used a bundled 4096 instance and 17 used source-loaded 8192 kernels. Across seven historical loads, four of which had forced config interventions, we saw five configuration/output classes, and observed vectors that were equal matched on the probes. Dropping the bundled instances gave matching probes in four loads on another physical GPU, so that comparison was not a same-device interleaved A/B (details in #58899).

**Scope.** Serial loading removes interleaving between artifact deserializations started by this `load_all` call. In the inspected PyTorch loading path (main and release/2.14), static-cache lookups happen on the caller, and compilation futures are resolved before restoration returns.

What it does not do:
- give each call site ownership of its bundled instance;
- exclude other concurrent users of the cache;
- disable autotune-cache rechecks or tuning at startup.

Numerical repeatability therefore still depends on the configuration; #58899 and #61053 describe additional tuning-related variation.

**Not a duplicate.** As of 27 October 2026, our searches of open and closed vLLM PRs and issues for `load_all`, AOT thread pools, serial AOT loading and #58899 found no equivalent change extending serial artifact loading to non-ROCm platforms. Related work changes numerical policy instead:
- In vLLM: #60074 (open) pins Inductor reduction configs under `VLLM_BATCH_INVARIANT`, and #61118 (merged) enables Inductor `batch_invariant` in that mode. #56879 (open) rejects empty AOT mega artifacts and does not change the load order.
- In PyTorch, related work addresses different paths:
  - [pytorch/pytorch#198954](https://github.com/pytorch/pytorch/pull/198954) adds the precompile runtime cache;
  - [pytorch/pytorch#194918](https://github.com/pytorch/pytorch/pull/194918) prunes saved bundles;
  - [pytorch/pytorch#200522](https://github.com/pytorch/pytorch/pull/200522) pins compile-time choices for standalone emitted modules.

  None of these changes vLLM's `load_all` order. The serial ROCm branch came from #50607, as a workaround for a `hipModuleLoad` deadlock.

**Tradeoff.** Startup loses parallel deserialization. With the trace hook enabled on this 20-artifact cache, all eight loads reached health in 68.6–68.7 s; `init engine` took 37.75–38.47 s unpatched and 37.80–38.18 s patched. Health was polled approximately once per second and recorded to 0.1 s. These measurements do not establish zero startup overhead without tracing. Without the hook (the four GSM8K loads, on two GPUs), launch-to-health took 69.5–71.5 s unpatched and 69.4–70.5 s patched, and `init engine` 38.20–38.82 s and 38.15–38.17 s; two loads per arm give no cost estimate beyond these values. We have not measured models with many more artifacts, or warm starts on other GPUs. A config switch would keep the race as the default, so we did not add one. The compilation-cache section of `docs/design/torch_compile.md` now describes the behavior and its startup cost.

**CI coverage.** The existing PyTorch Compilation step selects both tests (`.buildkite/test_areas/pytorch.yaml`). They check the loading strategy and loaded-versus-compiled token equality on gpt2; they do not reproduce the numerical race. This particular cache fixture is not available in CI, and we have not found a compact mixed-config cache for it. The real-weights validation above was run outside CI.
