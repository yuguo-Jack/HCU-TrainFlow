# [Bugfix] DeepSeek V4/V4.1: honor enable_thinking over legacy thinking and treat null flags as unset

[Upstream PR](https://github.com/vllm-project/vllm/pull/56708) · state: open · merged: False

## Original PR description

## Purpose

DeepSeek V4 and V4.1 resolved thinking mode with `bool(thinking or enable_thinking)` and treated a present-but-null key as specified. That caused two inconsistent public-API cases:

- Canonical `enable_thinking: false` lost to legacy `thinking: true`.
- `thinking: null` or `enable_thinking: null` disabled thinking instead of acting as unspecified.

Both keys can coexist because `chat_template_kwargs` is a free-form public dictionary that accepts the canonical name and its legacy alias. A concrete conflicting request is:

```json
{"chat_template_kwargs":{"thinking":true,"enable_thinking":false}}
```

This PR applies one rule throughout both families:

1. A non-null `enable_thinking` is canonical.
2. A null `enable_thinking` falls through to legacy `thinking`.
3. Absent or all-null flags default to thinking enabled.
4. `reasoning_effort: "none"` disables thinking afterward, as before.

The normal default request path does not inject conflicting keys.

## Changes

- `vllm/tokenizers/deepseek_v4.py`, `vllm/parser/deepseek_v4.py`, and `vllm/tokenizers/deepseek_v41.py` use the same precedence and null rules.
- The V4 tokenizer/parser matrices cover conflicting and null combinations, plus a render-and-parse round trip for streaming and non-streaming disabled-thinking responses.
- The V4.1 tokenizer/parser matrices mirror those combinations.

`DeepSeekV41Parser` inherits `DeepSeekV4Parser.__init__`, so the parser fix is shared. `DeepseekV4Renderer` delegates to the registered tokenizer and has no independent flag resolution. The duplicated four-line resolution at the tokenizer and parser boundaries is intentional; mirrored tests guard against drift. Encoding, model, kernel, and runtime files are unchanged.
