# [Core] Count V2's KV cache init memory against the KV cache budget

[Upstream PR](https://github.com/vllm-project/vllm/pull/60186) · state: open · merged: False

## Original PR description

## Purpose

The V2 CUDA graph memory profile runs the real KV cache init on a minimal cache and then measures only the capture. What that init allocates beside the KV cache, such as FlashInfer's float workspace, is torn down with the profiling state and allocated again after the KV cache is sized. Nothing counts it, so with FlashInfer the engine can start above `gpu_memory_utilization`.

This change measures the drop in free device memory across the minimal init, subtracts each KV cache storage once (layers that share a cache share one storage), and counts the rest as consumed memory: it comes out of the KV cache budget and goes into the consumed total used to calculate the startup-plan KV budget, while the profiling result itself is left as measured. It is kept apart from the CUDA graph estimate, so `VLLM_MEMORY_PROFILER_ESTIMATE_CUDAGRAPHS=0` does not drop it, and it is added after the ROCm fallback. The startup plan schema is bumped so plans recorded without it are not reused. When and in which memory pool the init allocates is unchanged.

Scope: V2 with CUDA graphs. Eager mode runs no such profile and is unchanged. Backends that allocate nothing new at init (FlashAttention in the runs below) get the same KV cache size as before.

## Test Plan

- Unit tests: the init cost is measured apart from the graph estimate with a shared KV cache excluded once; the worker counts it once with the graph estimate on or off and after the ROCm fallback, and leaves the profiling result as measured.
- GPU runs on one sm_80 GPU comparing the baseline and this change for Gemma 4, Llama and Qwen, in CUDA graph and eager modes.

## Test Result

```text
pytest -q tests/v1/worker/test_gpu_model_runner_v2_cudagraph_profiling.py tests/v1/worker/test_gpu_worker.py
40 passed
```

Baseline: main `64cb683842` + [#47547](https://github.com/vllm-project/vllm/pull/47547) (`5cd3a3cd5e`) + [#46558](https://github.com/vllm-project/vllm/pull/46558) (`ec504f113a`), which let Gemma 4 run FlashInfer on sm_80. This change: the same tree + an earlier revision of this commit, which added the init memory to the profiling result instead. Both revisions compute the KV cache budget and the consumed total the same way; the Llama FlashInfer graph row was re-run on the current revision with the same KV cache size, the same used − budget after init, and identical outputs. Each run builds `LLM(...)` in process with the V2 model runner, `gpu_memory_utilization=0.8`, `max_num_seqs=256`, `max_model_len=32768`, prefix caching off, default KV cache dtype and `seed=0`; the startup plan is off. All runs use a warm torch.compile cache, because a run that compiles from scratch measures a higher profiling peak (up to 1.5 GiB on Qwen) and would mask the difference. "Used − budget" is device memory in use right after `LLM(...)` returns, minus 80% of the device.

| Model | Attention | Mode | KV cache (MiB) | Init counted (MiB) | Used − budget after init (MiB) |
|---|---|---|---|---|---|
| Gemma 4 26B-A4B NVFP4 | FlashInfer (auto) | graph | 28,833 → 28,279 | 554 | +341 → −214 |
| Llama 3.2 3B | FlashInfer (forced) | graph | 44,253 → 43,839 | 414 | +252 → −164 |
| Qwen3.6 35B-A3B NVFP4 | FlashInfer (forced) | graph | 27,448 → 26,936 | 512 | −294 → −810 |
| Llama 3.2 3B | FlashAttention (auto) | graph | 44,613 → 44,613 | 0 | −130 → −130 |
| Qwen3.6 35B-A3B NVFP4 | FlashAttention + GDN (auto) | graph | 27,808 → 27,808 | 0 | −776 → −776 |
| all three | auto | eager | unchanged | 0 | unchanged (not recorded for Gemma 4) |

- The counted init includes FlashInfer's float workspace (394 MiB on Llama, 512 MiB on Gemma 4 and Qwen) and other init-time state. In these warm runs the profiling peak matched between baseline and change, and the KV cache shrank by the counted amount. One earlier Gemma 4 run with a 24 MiB lower profiling peak shrank by 530 MiB.
- The budget result holds right after startup. Later requests can still go over: the workload's last request (prompt logprobs on a ~2k-token prompt) exceeds the budget in baseline and change alike, which this PR does not address.
- Outputs, compared on greedy generations and teacher-forced prompt logprobs:
  - Llama: identical tokens and prompt logprobs in both graph rows.
  - Qwen FlashInfer: the change matches a second baseline run token for token. The first baseline run diverges from both at the same token. Mean |Δ logprob| is 0.0012 between the two baseline runs and 0.0012–0.0014 against the change.
  - Qwen FlashAttention: same tokens, mean |Δ logprob| 0.0033, against 0.0014 between two baseline runs.
  - Gemma 4: this path is not run-to-run deterministic. Mean |Δ logprob| is 0.049 between two baseline runs and 0.037–0.049 against the change.
- Sleep mode: see the sleep/wake check below.

### Further checks

Same conditions as above unless noted: warm torch.compile cache, and runs whose profile differed because of a cold compile are left out. Runs not marked as the current revision used the earlier revision.

- Newer main (current revision): the commit applies cleanly on `a3e0243b1c`. These seven test files give `198 passed, 1 skipped` on both `64cb683842` and `a3e0243b1c` with the commit applied: `tests/v1/worker/test_gpu_model_runner_v2_cudagraph_profiling.py`, `test_gpu_worker.py`, `test_gpu_model_runner_v2.py`, `test_gpu_model_runner_v2_eplb.py`, `test_gpu_profiler.py`, `test_worker_memory_snapshot.py`, `tests/v1/spec_decode/test_dflash_profile.py`.
- With [#56698](https://github.com/vllm-project/vllm/pull/56698) (current revision). #56698 profiles a pinned `kv_cache_memory_bytes` on the same minimal KV cache, so its profile already includes the init memory; this change leaves the profiling result that its check reads untouched. Measured with Llama 3.2 3B and a 20 GiB pin on main `48eb44b719` + #56698 (`f9063298c9`): the non-KV usage the check reports is 7.63 GiB with FlashInfer and 7.22 GiB with FlashAttention, with and without this change. The earlier revision raised them to 8.02 and 7.24 GiB.
- Default backend selection: Llama 3.2 3B with `kv_cache_dtype="fp8"`, attention backend left to auto, and prefix caching on. FlashAttention cannot serve FP8 KV here, so FlashInfer is selected. Init counted 414 MiB; KV cache 44,253 → 43,839 MiB; used − budget after init +252 → −162 MiB. Tokens and prompt logprobs are identical.
- Sleep/wake, same config with `enable_sleep_mode=True`, then `sleep(level=1)` and `wake_up()`. Device memory in use while asleep is 1,221 MiB in both. Before sleeping it is 52,185 → 51,791 MiB: the KV cache is smaller by the 394 MiB counted in this mode. After `wake_up()`, tokens and prompt logprobs are identical.
- Startup plan, same config with `VLLM_ENABLE_STARTUP_PLAN=1`. The change ignores the plan the baseline saved under schema 1, profiles, and saves its own. That plan's KV budget is 45,687,552,717 → 45,253,442,253 bytes, 414 MiB lower. The next boot applies it and skips profiling.
- MTP: Qwen3.6 35B-A3B NVFP4, FlashInfer forced, `num_speculative_tokens=1`.
  - Init counted is 1,026 MiB in total. The target/draft split was not measured; the draft likely holds a second FlashInfer workspace.
  - KV cache 25,792 → 24,766 MiB (1,026 MiB less). Used − budget after init +328 → −544 MiB (872 MiB less).
  - Tokens differ, but they also differ between two baseline runs. Mean |Δ logprob| is 0.0021, against 0.0025 between the baseline runs.

All results above come from local runs on one sm_80 GPU.
