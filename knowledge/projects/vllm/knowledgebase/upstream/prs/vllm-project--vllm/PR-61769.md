# [Bugfix][KV Connector] Evict invalid blocks of requests aborted mid-step

[Upstream PR](https://github.com/vllm-project/vllm/pull/61769) · state: open · merged: False

## Original PR description



## Overview

Fixes #61768. A request aborted in the same step its synchronous KV load fails leaves the scheduler before the failure report is processed, so its never-loaded blocks stay prefix-cache hits. This keeps the departing request's block ids until its in-flight outputs arrive, and evicts them when a late failure report names them.

## Claims

- After a sync KV load failure whose owner was aborted in the same step, the invalid block and every block after it are evicted, under both `kv_load_failure_policy` values and with sync and async scheduling. With async scheduling or PP this relies on deferred freeing, which is on for a top-level `kv_consumer`/`kv_both`; see Tradeoffs and limits for a top-level producer whose connector loads.
- A later identical prompt recomputes instead of decoding from never-loaded KV (GPU: r2 cached 1904 → 0, output matches the full-recompute baseline).
- An abort whose load succeeded keeps its valid cached KV (unchanged behavior).

## Details

**Root cause.** `EngineCore.step` and `step_with_batch_queue` apply queued aborts before `update_from_output`. `allocate_slots` hashes blocks at schedule time, before an external load completes, and `free_blocks` keeps hashes. `_handle_invalid_blocks` only looks for affected requests in `running` and `kv_holding_waiting`, so when the owner was freed in between, it returns before evicting.

**Why the request's lifetime isn't enough.** The request object is gone once it is freed, but outputs of the steps that scheduled it can still arrive, and only they carry the failure report. So the departing request's block ids are kept for as long as it has scheduled-but-unprocessed tokens.

**Change** (`vllm/v1/core/sched/scheduler.py`, +51 lines):
- *Capture:* `_free_request` records the block ids and `num_in_flight_tokens` of a request freed while it still has in-flight tokens, before the delayed-free branch, so connector-delayed and `defer_block_free` paths are covered. Only with a KV connector and a single KV cache group, matching `_handle_invalid_blocks`.
- *Evict:* `_handle_invalid_blocks`, before its early return and under both policies, evicts from the first invalid block onward for every recorded request. The `recompute` no-evict path stays for live owners only: a finished request never recomputes. Every record is checked, not only those in this batch, because a finished request may have computed its own later blocks over a block that failed in an earlier batch.
- *Retire:* `update_from_output` counts each record down by the step's scheduled tokens before its main loop and drops it at zero. It runs before the loop because the loop decrements `num_in_flight_tokens` first, so records created there already exclude this step.

**Relation to other work.** [#42461](https://github.com/vllm-project/vllm/pull/42461) ([RFC #35780](https://github.com/vllm-project/vllm/issues/35780)) proposes replacing block-level failure reporting with request-level reporting. If it lands, this path and this bug go away with it; until then, every connector that reports `invalid_block_ids` reaches this code, under the default `fail` policy too. PR [#53298](https://github.com/vllm-project/vllm/pull/53298) covers the recompute-policy repair of requests that are still alive; this change covers the owner that is already gone. Against its head `1eca68f4`, `scheduler.py` merges cleanly; both add a line to the test helper `assert_scheduler_empty`, a one-line conflict for whichever lands second.

**Tradeoffs and limits.**
- No GPU work and no host sync: Python bookkeeping only. With sync scheduling, records are created only for requests aborted mid-step. With async scheduling, also for requests that finish while their next batch is in flight; each such record holds a tuple of block ids for one step. A record lives at most `max_concurrent_batches` steps, so the number of records is bounded by the requests that finish within that window. The retire step returns immediately when there are no records; the scan over recorded block ids runs only when a failure is reported.
- Keeping physical block ids, without hashes, requires that a recorded id not identify a different allocation when the failure report is handled. With one batch in flight, nothing allocates between the abort and `update_from_output`, which handles the report and retires the record. With several batches in flight, this holds when `defer_block_free` is on (top-level `kv_consumer`/`kv_both`): the freed blocks are held until the step fence at free time has been processed. Deferred frees may drain before `_handle_invalid_blocks()`, but no scheduling allocation occurs between that drain, failure handling, and record retirement in the normal engine output path. With overlapping batches and a top-level producer whose connector loads, `defer_block_free` is off and a recorded id can be reallocated before the report. In CPU probes this PR then additionally evicts the new allocation's cache entries; the late report failing or rewinding that unrelated request already happens on main (#61905). Whether producer-role loading needs handling before this merges is a call for review.
- Known limit: preempted owners are not tracked here. A consumer-role `reset_prefix_cache(reset_running_requests=True)` can preempt an owner whose load is in flight and then fail to clear the cache, leaving failed-load blocks as prefix hits; producer-role synchronous loaders can also reach this through KV-pressure preemption. Tracked in #61912.
- Multiple KV cache groups are out of scope: `_handle_invalid_blocks` already raises for them, because block ids are only unique within a group.
- Requests still running that share an invalid block are handled by the existing `running` scan; recompute-policy repair ordering for live sharers is #53298's scope.
- The model's next-token distribution is used in validation because greedy equality alone can miss partial corruption.
