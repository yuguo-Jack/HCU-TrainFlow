# [Bugfix] Keep DP dummy runs from writing Mamba/linear-attention state into live requests' blocks

[Upstream PR](https://github.com/vllm-project/vllm/pull/63776) · state: open · merged: False

## Original PR description

## Purpose

With a hybrid model (Mamba-style / linear-attention layers), prefix caching (`mamba_cache_mode="align"`), FULL CUDA graphs and data parallelism, a DP dummy run can write linear-attention state into KV-cache blocks owned by other live requests. Those requests then read corrupted K/V and produce NaN logits.

**When it happens.** An engine runs dummy batches (`execute_dummy_batch`) while its persistent batch still holds live requests. The usual trigger is `pause_generation(mode="keep")` with DP: until all DP ranks agree to pause, the paused ranks keep stepping dummy batches. RL frameworks use this for in-flight weight updates. In our runs that meant 2–56 dummy steps per pause, with every running request still in the batch.

**Root cause.** In `GPUModelRunner._dummy_run` (FULL mode):

- It commits the live block table to the GPU with `commit_block_table(num_reqs_padded)`, then builds attention metadata from it.
- It calls `_build_attention_metadata(num_reqs=num_reqs_padded, ...)` without a separate `num_reqs_padded`, so the "fill unused rows with `NULL_BLOCK_ID`" range in `_get_block_table` is empty. Every dummy row keeps a live request's block IDs.
- Dummy `seq_lens` are 1. In align mode `mamba_get_block_table_tensor` picks block index `(seq_len - 1) // block_size = 0` of each row's mamba block list. For a long request, entry 0 is an old state block that the allocator has since freed and reused, often as another request's attention block.
- Attention KV writes are disabled for dummy runs (`slot_mapping = -1`), but the mamba/GDN kernels have no such guard. They update the state in place at that block.
- Attention and mamba layers share the same physical KV-cache tensors in the hybrid allocator, so the state write overwrites the other request's K/V. The fp32 recurrent state read as bf16 contains NaN patterns, and the next real step reads it.

PIECEWISE/eager dummy runs build no attention metadata, so the cache layers skip them and the bug does not appear there. The newer model runner (`vllm/v1/worker/gpu/`) already builds separate block tables for dummy runs (`get_dummy_block_tables`).

**Fix.** In `_dummy_run`, point every row of the dummy batch at `NULL_BLOCK_ID` in all KV-cache groups, instead of committing the live rows. Dummy kernels then only touch the reserved null block, as padding rows already do in real steps. Real steps are unaffected: `_prepare_inputs` re-commits the block table from its CPU copy at the start of every step.

## Test Plan

- Hybrid MoE model with 11 full-attention and 31 KDA (`GDN_ATTN` backend) layers, 1 node with DP=4 and EP=4, FULL_AND_PIECEWISE CUDA graphs, prefix caching on. Long generations (`ignore_eos`, 4K tokens) were paused with `pause_generation(mode="keep")` and the weights updated in place while 32 requests per engine were in flight.
- An instrumentation probe checksummed every KV-cache block across each pause and recorded the state blocks each GDN metadata build handed to the kernels.

## Test Result

| | before | after |
|---|---|---|
| requests with NaN logits after an in-flight pause | 90 over 16 pauses | 0 over 19 pauses (2 runs) |
| pauses during which dummy steps changed live requests' blocks | 30 / 64 checks | 0 / 76 checks |
| decode throughput per step | — | unchanged |

- Before the fix, the probe showed the dummy row's stale entry-0 state blocks had become other requests' attention blocks. Exactly those requests had non-finite K/V before the next real step, starting right after the bf16 conv-state bytes, and they produced NaN logits on that step.
- PIECEWISE graphs (dummy runs without metadata) gave 0 NaNs and no pause writes on the same workload.
- A 16-node RL production run with the fix had 0 NaN sequences over 17 in-flight weight updates. The same configuration without the fix masked 150 NaN sequences in its first 19 steps.
