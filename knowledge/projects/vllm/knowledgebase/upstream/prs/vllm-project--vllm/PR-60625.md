# [Bugfix][DeepSeek V4/V4.1] Fix Engram and O-group sharding at TP16/TP32

[Upstream PR](https://github.com/vllm-project/vllm/pull/60625) · state: open · merged: False

## Original PR description

## Summary

Fix DeepSeek V4/V4.1 TP16/TP32 sharding (https://github.com/vllm-project/vllm/issues/59394):

- Allow Engram ranks with no owned hash heads.
- Support O-groups spanning multiple physical TP ranks.
- Mirror complete WO-B shards per node and reduce with an isolated node-local TP group, preserving TP8 O-projection numerics.
- Reject unsupported sequence-parallel/GEMM-RS/symmetric-memory combinations and bind FlashInfer workspaces to their process group.

Latest commit: `388c720d074587169755cb685b79da395eaeea5a`.

## Validation

Environment: DeepSeek-V4.1-Flash, 2x8 H20, pinned nightly `81198e97ba7eee2a22540caaa756b7fdddcb4d93`.

- TP16 startup passed; ranks 0-15 initialized, ranks 12-15 accepted empty Engram shards, and both Pods stayed Ready with zero restarts.
- Fixed-input T=1/T=7 O-projection checks are bitwise equal between TP8 and TP16 through WO-A, WO-B, reduction, and final output.
- Smoke: TP8 and TP16 both passed 21/21.
- GSM8K-200: TP8 196/200, TP16 196/200.
- Full GSM8K-1319: TP8 1287/1319, TP16 1274/1319. All requests succeeded with zero errors; TP16 had 19 correct-to-wrong and 6 wrong-to-correct flips.
- Output length still regresses at TP16: 6 vs 2 `max_tokens`, mean 438 vs 329, and p99 4156 vs 2243.

The projection-specific numerical mismatch is fixed, but the end-to-end TP16 accuracy/output-length gate still fails. TP32 has not been run.

Fixing the remaining issue requires substantially more changes than initially expected. TP16 may not be a common parallel configuration for V4/V4.1 because TP8 is generally sufficient, so whether the additional complexity is worthwhile needs to be weighed carefully. This PR remains draft pending that decision.
