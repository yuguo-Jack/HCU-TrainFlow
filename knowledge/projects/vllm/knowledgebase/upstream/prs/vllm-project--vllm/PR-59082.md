# [CPU] Improve long-context MTP attention scheduling on AMX

## Purpose

Extend CPU attention's grouped-query (GQA) scheduling to eligible
causal multi-token requests, including MTP verification and short prefill. The
existing batch-level GQA fast path requires an all-q1 decode batch, so these
requests do not receive the same grouped scheduling. The scheduler evaluates
grouped query heads and split-KV work using each request's query length,
causality, and AMX geometry, then selects a plan through its cost model. This
applies with auto, FP8 E4M3, and FP8 E5M2 KV cache.

## Duplicate-work Check

PR [#46154](https://github.com/vllm-project/vllm/pull/46154) is related but not
a duplicate. It fixes generic mixed-batch GQA decode classification when
split-KV can divide a prefill request into one-token work items. This change
adds request-level eligibility based on causality, prefill state, and
verification query length, and uses it to enable AMX speculative multi-token
GQA scheduling with BF16 attention and FP8 KV.

Issue [#46131](https://github.com/vllm-project/vllm/issues/46131), its comments,
open PRs referencing the issue, and open PRs matching CPU attention/GQA/spec
decode terms were checked. #46154 was the relevant overlap found.

## Test Result

Serving used 100k input/1k output tokens with zero failures. Main
`6b24bd8e75a3` values are medians of three timed requests. Auto-KV branch
`65e9381658fe` values are also three-request medians; FP8 branch
`59b2f5f7b4` is one timed request after one warmup, built from the same source
state just before that commit. The FP8 fix leaves auto-KV scheduler selection
unchanged.

| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| No MTP, auto KV | 6.73 | 7.08 | 79.29 | 75.49 | 71.04 | 67.39 |
| MTP3, auto KV | 8.01 | 9.48 | 48.72 | 34.33 | 77.99 | 72.88 |

The original FP8 branch run had **87.14 s TTFT**: its new AMX work
materializer also handled ordinary FP8 prefill. Routing FP8 batches without
eligible multi-token verification through the existing legacy materializer
reduced TTFT to **81.20 s**, within **0.58%** of main. FP8 MTP acceptance was
**98.7%** on the post-fix timed request (767/777 draft tokens). The generic
`--kv-cache-dtype fp8` option maps to E4M3 in CPU attention on both arms.

- Original CPU attention and metadata tests: **1,637 passed, 1,154 skipped**.
  After the FP8 fallback, **24 focused cases passed** across AMX FP8 prefill,
  q=1, mixed MTP, builder masking, and forced VEC. FP8 E4M3/E5M2 attention
  with serving cache strides was within 0.3% of main at 98k context. Commit
  hooks passed.
- Original forced-VEC parity: **3/3 passed** with identical outputs. Native
  `amx_fp8` and ARM hardware were unavailable. The full kernel timing matrix
  was not repeated after the rebase.
- Qwen3.5-4B MTP3 MRCR: auto KV passed **40/40** on both main and branch with
  identical 2/4/8-needle scores (**0.9952 / 0.8444 / 0.7632**). Post-fix FP8
  KV completed **40/40** with scores **0.9952 / 0.9049 / 0.7055**, no lower
  than saved main (**0.9952 / 0.8581 / 0.7055**). Both fail the same n8 cutoff
  (**0.7055** versus **0.7100**); this is not an absolute FP8 MRCR pass.

- bigPYJ1151 · comment · 2026-10-08T15:56:47Z · [source](https://github.com/vllm-project/vllm/pull/59082#discussion_r4221226600)

File: `csrc/cpu/cpu_attn_impl.hpp` · line None

Since this PR is refactoring the scheduler, I think it's better to clarify the rules for GQA packing and build up a more concise schedule procedure. Otherwise more and more flags will make the code become hard to maintain. In my opinion:
- `max_num_q_per_iter % original_q_head_per_kv == 0`, regular cases, enable GQA by default, natural for prefill and decode requests.
- `max_num_q_per_iter % original_q_head_per_kv != 0 && max_num_q_per_iter >= original_q_head_per_kv`, enable GQA for decode and short prefill requests. The AMX tiles are not fully used, but GQA can reduce memory access for such memory bound cases.
- `max_num_q_per_iter < original_q_head_per_kv`, fallback to MHA. Such cases can enable GQA by split heads of a query to multiple iterations. But they should be very rare for AMX impls, which can support `max_num_q_per_iter = 32`.
