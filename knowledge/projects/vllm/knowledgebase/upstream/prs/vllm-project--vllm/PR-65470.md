# [Perf][Model] Qwen4Exp QSA: compact grid for indexer prefill scoring

[Upstream PR](https://github.com/vllm-project/vllm/pull/65470) · state: open · merged: False

## Original PR description



## Overview

Qwen4Exp QSA: launch the indexer prefill scoring kernel `_qsa_mqa_paged_prefill_kernel` on `num_queries // TILE_R + num_requests` programs instead of `num_requests x cdiv(longest request, TILE_R)` when that is fewer, with the q-block layout of `find_seq_idx`. Logits are bit-equal. Related: #62344 (sm_80 config for this kernel; the second to merge needs a small rebase in `_prefill_logits`). Follow-up: #65471, an sm_120 config for this kernel, stacked on this PR.

`split_decodes_and_prefills(require_uniform=True)` sends short requests of differing lengths (decodes with different draft counts, short extends) to the prefill kernel beside the step's long chunk. The request grid gives each of them as many row-tile programs as the longest request: one 2048-row chunk plus 100 requests of 1-4 rows launches 3,232 programs for 132 row tiles with the BF16 config (6,464 for 164 with FP8). The compact grid launches 136 (172).

## Claims

- Mixed steps on RTX PRO 6000 (sm_120), 8k to 64k context: indexer prefill scoring 1.06x to 1.14x faster with a BF16 index cache, 1.11x to 1.33x with FP8. Bit-equal.
- Single requests and equal-length chunks keep the request grid, so their launch is unchanged (1.00x to 1.03x measured, within run-to-run spread).
- One new `COMPACT` specialization of the kernel; the request lookup is a binary search over `query_start_loc`.

## Validation

**Tests** (38 passed on 1 x RTX PRO 6000):
- New `tests/models/qwen4_exp/test_qsa_indexer_compact.py`, added to the `qwen4_exp` CI step: compact grid against the request grid, bit for bit, BF16 and FP8, over 11 layouts (one request, equal chunks, a mixed step, zero-row requests, a request longer than a tile, windows into a chunk, across requests and over 60 requests, a leading empty run, a long request after 160 short ones, requests outside the window). The grid is launched at its exact size; a grid one tile short fails the test.
- `test_qsa_reference.py::test_qsa_prefill_selection_correctness` gains a `long_and_many_short` case that goes through `qsa_select_paged_prefill` and takes the compact grid.

**Kernel benchmark:** 1 x RTX PRO 6000 Blackwell Server Edition (driver 580.82.07, CUDA 13.0), torch 2.14.0+cu130, triton 3.8.0, vLLM `3b6eeb06` with and without this PR (the branch is rebased onto `866bccf`; the touched files differ only by the `_topk` condition of #56102). `Qwen/Qwen3.8-Flash-Next` indexer shapes (4 heads, head_dim 128, compress ratio 4), random tensors. `_prefill_logits` against the request grid at the same launch config; CUDA graph of 20 calls, 128 MB L2 flush before each of 5 replays; median of 3 runs (run-to-run spread of a speedup at most 3.6%).

## Details

Request `r` owns the row tiles from `clipped_start(r) // TILE_R + r`, where `clipped_start` is its first row clamped to the scored window `[query_offset, query_offset + num_queries)`. That gives it `clipped_start(r + 1) // TILE_R - clipped_start(r) // TILE_R + 1` slots, at least the `cdiv` of its clipped length, so `num_queries // TILE_R + num_requests` programs cover every tile, as in `triton_unified_attention.py`. `_find_row_tile_request` is a binary search like `find_seq_idx`, with the window clamp applied to each probed offset. Programs past a request's last tile return at once. The per-tile code and the K-split axis are unchanged, so each output is computed by the same instructions in the same order.

The compact grid is chosen when `num_queries // TILE_R + num_requests < num_requests * cdiv(min(num_queries, max_query_len), TILE_R)`, from host values only. The prefill path runs outside CUDA graphs (`_run_qsa` breaks capture), so the grid may vary per step.
