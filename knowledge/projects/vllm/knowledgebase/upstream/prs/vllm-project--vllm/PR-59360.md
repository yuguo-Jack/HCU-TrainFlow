# [Core] Release the FlashInfer allreduce workspace (MNNVL or TRT-LLM) with --enable-nccl-comm-suspend

[Upstream PR](https://github.com/vllm-project/vllm/pull/59360) · state: closed · merged: True

## Original PR description

## Purpose

Part of #59055 (sleep-mode residual memory).

With `--enable-sleep-mode --enable-nccl-comm-suspend`, `CudaCommunicator.suspend()` only suspends pynccl. The FlashInfer MNNVL allreduce workspace (used by the allreduce+RMSNorm fusion and by standalone FlashInfer allreduce) stays resident while asleep. That is 512 MiB/GPU on DeepSeek-V4 TP4 on GB300.

This PR makes `suspend()`/`resume()` also detach and reattach the group's FlashInfer allreduce workspaces. It reuses the existing `checkpoint_prepare_fi_ar_workspaces` / `checkpoint_restore_fi_ar_workspaces` helpers, which wrap FlashInfer's stable-VA checkpoint API:
- `checkpoint_prepare()` unmaps and releases the physical handles.
- `checkpoint_restore()` recreates them at the same virtual addresses, re-exchanges them over the gloo `cpu_group`, and resets the Lamport flags.
- Because the addresses don't change, captured CUDA graphs stay valid.

Details:
- **Idempotence** comes from FlashInfer 0.7.0: `checkpoint_prepare()` returns early when already detached and `checkpoint_restore()` when already mapped, before any barrier. The executor already blocks a double sleep. There is no extra flag, so if a restore fails (e.g. `cuMemCreate` OOM) a retried `wake_up` retries the restore.
- **Order vs. NCCL** doesn't matter, since FlashInfer synchronizes over gloo. Resume runs in reverse order: pynccl first, then FlashInfer.
- **No workspace** (FlashInfer AR unused): the helper finds nothing and the call is a no-op.
- **Workspaces backed by torch symmetric memory** raise `NotImplementedError` in FlashInfer. The helpers skip them per workspace (`skip_unsupported=True`, set only by `suspend()`/`resume()`), so the other workspace is still released, and log once at info level that the workspace stays resident. The CUDA-checkpoint path (`checkpoint_prepare()`/`checkpoint_restore()`) still raises.
- **FlashInfer all2all** managers also expose `checkpoint_prepare/restore`. They are left out of scope because the default all2all backend doesn't use them.

## Test Plan

- Unit tests in `tests/distributed/test_comm_ops.py`, with a distinct mock per workspace:
  - `test_cuda_communicator_suspend_detaches_flashinfer_workspaces[mnnvl|symm-mem+mnnvl]`: suspend/resume routing, and a symm-mem workspace next to a normal one (the normal one is still released and restored);
  - `test_cuda_communicator_checkpoint_rejects_symm_mem_workspace`: the CUDA-checkpoint path still raises;
  - `test_cuda_communicator_resume_retries_failed_restore`: a retried resume after a failed restore calls restore again.
- GB300 tests on the `nightly-af7f9488` image with this file overlaid (identical to `d86cf91240` for the touched file).
- Single-node config: DeepSeek-V4-Flash, TP4 + EP, MTP n=1, `--enable-sleep-mode --enable-nccl-comm-suspend`. The log shows `FlashInfer Allreduce norm fusion workspace with backend=mnnvl`.
- Harness: gated, deterministic batches. It runs 11 rounds of 553 requests (groups 1 to 256, temperature 0) compared bit-exactly: token ids, logprobs and prompt logprobs. Rounds come after a full wake and after a selective wake (`weights`, then `kv_cache`).
- Then 10 level-1 sleep/wake cycles alternating full and selective wake. Each cycle records per-GPU memory while asleep, and bit-exactly checks the first request after wake against the pre-cycle reference.
- 2-node config: DeepSeek-V4.1-Flash, TP8 over 2 nodes, no MTP, same flags.

## Test Result

- Unit tests: 18/18 pass (`pytest tests/distributed/test_comm_ops.py -k "flashinfer or symm_mem or restore"`, torch 2.13.0+cu130).
- The GB300 numbers below were measured on the first commit (08b09bf453). The follow-up commit changes only the failure and symm-mem paths; on the MNNVL happy path the same prepare/restore calls run.

Level-1 asleep memory, per GPU (nvidia-smi):

| Config | Without this PR | With this PR | Δ |
|---|---|---|---|
| V4-Flash TP4, main | 14029 MiB | **13517 MiB** | −512 |
| V4-Flash TP4, stacked with the other sleep PRs of #59055 | 5161 MiB | **4649 MiB** | −512 |
| V4.1-Flash TP8, 2 nodes (all 8 GPUs) | 19885 MiB | **19373 MiB** | −512 |

- **Stability.** Asleep memory is identical across all 10 cycles with no drift, and awake memory is unchanged. There are no errors or tracebacks, and host MemAvailable is flat.
- **Bit-exactness, single node.** All 553/553 requests are bit-identical in every round, after both full and selective wake, both with and without this PR. The first request after every wake matches exactly in 10/10 cycles; that request is the one that exercises the Lamport flag reset.
- **Bit-exactness, 2 nodes.** Upstream V4.1 TP8 is already not bit-reproducible between two *awake* rounds: 84.1% of requests are identical, and some prompt-logprob NaN 400s occur. Both runs show exactly the same 84.1% in every round, before and after sleep, so this PR causes no regression there.
- **Wake latency.** The mean full `wake_up` goes from 1.58 s to 1.64 s on TP4, and from 1.06 s to 1.09 s on TP8 2-node. The cost is re-creating the fabric handles plus a gloo exchange and barrier. Sleep latency is unchanged.

### AMD MI355X (ROCm)

ROCm also uses `CudaCommunicator`, so the new calls run there, but they are a no-op: FlashInfer allreduce is unavailable and a probe on every worker found 0 workspaces. Verified on DeepSeek-V2-Lite TP2 / TP2 eager / DP2 with `--enable-nccl-comm-suspend`: memory while asleep matches unpatched within ±20 MiB, outputs are bit-identical after full and selective wake, wake latency is unchanged (0.37–0.42 s), with no errors. Separately, RCCL's comm suspend frees ~0 MiB by default because RCCL does not allocate with cuMem (with `NCCL_CUMEM_ENABLE=1` it frees 505 MiB, but cuMem adds 389 MiB).
