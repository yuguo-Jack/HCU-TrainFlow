# [Qwen4Exp] PLE disk offload

[Upstream PR](https://github.com/vllm-project/vllm/pull/59958) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Adds `--engram-config '{"disk_offload": true}'` for Qwen4Exp. The PLE n-gram table stays in the checkpoint files, and each step reads only its rows on the host. On DGX Spark (GB10), Qwen3.8-Flash-Next NVFP4 loads with 27.0 GiB less memory. Decode is within 3.5% of the resident table, and GSM8K is unchanged.

This carries forward @Trosfy's design from #58815 (their commits are kept, co-authored). It is rebased onto the NVFP4 PLE tables from #56273 and renamed `disk_offload` to pair with `cpu_offload`.

## Claims

- **Memory:** no table in GPU or pinned host memory, and no copy in an offload directory. Recently read rows sit in the OS page cache, which the kernel can reclaim. On unified-memory Spark, `cpu_offload` does not help, because pinned memory comes out of the same pool as the weights and the KV cache.
- **Formats:** BF16, FP8 and NVFP4. Rows are read in checkpoint format and decoded on the GPU with the existing PLE kernel.
- **CUDA graphs:** the forward reads fixed device buffers, so graphs replay unchanged.
- **Cost:** decode within 3.5% at c=1/4/8, and about 11% higher TTFT.

## Validation

Qwen3.8-Flash-Next-NVFP4 (`local-inference-lab@6c01ac3`), one GB10, both arms in one job on the same node. MTP n=3, FP8 KV (6 GiB), prefix caching off.

| | Resident | `disk_offload` | Delta |
|---|---|---|---|
| Weights loaded | 99.09 GiB | 72.09 GiB | -27.0 GiB |
| Host `MemAvailable` after startup | 4.6 GiB | 32.0 GiB | +27.4 GiB |
| Decode tok/s/user, c=1 | 33.63 | 32.45 | -3.5% |
| Decode tok/s, c=4 | 72.57 | 73.33 | +1.0% |
| Decode tok/s, c=8 | 94.04 | 91.99 | -2.2% |
| MTP acceptance length, c=1 | 2.33 | 2.31 | flat |
| TTFT, 8K prompt (median of 15) | 2540 ms | 2820 ms | +11.0% |
| GSM8K | 247/256 | 246/256 | -1 |

- Decode: aiperf, SPEED-Bench coding prompts, 1024 output tokens, active decode time only. One run per arm, so noise is a few percent.
- TTFT: exact-length random token ids with `max_tokens=1`. With the page cache dropped, the first 8K request took 3018 ms.
- The image was `vllm/vllm-openai:nightly-5555a2d8f7`, with every file touched by this PR and #56273 overlaid from this branch.
- CI: the H200 and CPU Qwen4 Exp lanes run the new tests. The Spark numbers were measured outside CI because there is no GB10 lane. On GB10 the new tests pass for all three formats.

## Details

- **Load:** the default loader hands over zero-copy safetensors mmap views. Their file and offset are found in `/proc/self/maps`, the files are opened read-only, and the views are released. Loading fails if the shards do not cover the table, if a dtype does not match, or if a view is not file-backed (for example `.bin` or `fastsafetensors`).
- **Per step:** `Qwen4ExpModelState.prepare_inputs` computes and deduplicates the n-gram ids, reads each row with `preadv` (after a `WILLNEED` read-ahead hint), and copies the rows to the staging buffers.
- **Parallelism:** every TP rank stages full rows, so no ETP reduction is needed. Elastic EP is rejected.
- **Alternatives:** #58439 reads the checkpoint mapping from the GPU through host page tables. #54070 writes a second copy of the table to disk. This PR reads rows on the host from the files the loader already opened.

This PR does not batch the per-row reads for long prefills (that is the TTFT cost) or support weight reload.
