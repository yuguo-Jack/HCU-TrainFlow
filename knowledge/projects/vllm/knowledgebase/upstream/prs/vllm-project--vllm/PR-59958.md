# [Qwen4Exp] PLE disk offload

[Upstream PR](https://github.com/vllm-project/vllm/pull/59958) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

Adds `--engram-config '{"disk_offload": true}'` for Qwen4Exp. The PLE n-gram table stays in the checkpoint files, and each step reads only its rows on the host. On DGX Spark (GB10), Qwen3.8-Flash-Next NVFP4 loads with 27.0 GiB less memory. Decode is within 3.5% of the resident table, and GSM8K is unchanged.

This carries forward @Trosfy's design from #58815 (their commits are kept, co-authored). It is rebased onto the NVFP4 PLE tables from #56273 and renamed `disk_offload` to pair with `cpu_offload`.

## Claims

- **Memory:** no table in GPU or pinned host memory, and no copy in an offload directory. Recently read rows sit in the OS page cache, which the kernel can reclaim. The page cache does fill up over a long session (ids are hashed, so there is no locality), but the kernel reclaims it on demand without hurting decode; the cost of a cold table is in TTFT (below). Use it with the checkpoint on local NVMe: on network storage a cold prefill is 2 to 4.5x slower. On unified-memory Spark, `cpu_offload` does not help, because pinned memory comes out of the same pool as the weights and the KV cache.
- **Formats:** BF16, FP8 and NVFP4. Rows are read in checkpoint format and decoded on the GPU with the existing PLE kernel.
- **CUDA graphs:** the forward reads fixed device buffers, so graphs replay unchanged.
- **Cost:** decode within 3.5% at c=1/4/8, and about 11% higher TTFT.

## Validation

Qwen3.8-Flash-Next-NVFP4 (`local-inference-lab@6c01ac3`), one GB10, both arms in one job on the same node. MTP n=3, FP8 KV (6 GiB), prefix caching off.

| Decode tok/s/user, c=1 | 33.63 | 32.45 | -3.5% |

- The image was `vllm/vllm-openai:nightly-5555a2d8f7`, with every file touched by this PR and #56273 overlaid from this branch.

### Cold cache and memory pressure

Same PR head (`396e7e0102`) and serve command, checkpoint on the node's local NVMe (ext4), one GB10. Page-cache residency is measured with `mincore` over the PLE shards; the memory cap is a cgroup `memory.max` on the container (GPU allocations are not charged to it). Short runs (3 to 6 rounds), so decode differences under ~10% are within noise.

| | Table in page cache | Decode c=1 | TTFT, 8K prompt | Disk read per 8K prefill |
|---|---|---|---|---|
| Resident table | n/a | 40.1 tok/s | 2597 ms | 0 |
| `disk_offload`, warm (prompt rows cached for TTFT) | 8 to 25% | 35.8 tok/s | 2832 ms | 0 |
| `disk_offload`, page cache dropped before every request | 0% | 36.3 tok/s | 3110 ms | 1.04 GB |
| `disk_offload`, cgroup cap leaving 2 GiB for page cache | held at 4.7% | 37.6 tok/s | 3174 ms | 1.0 GB |
| `disk_offload`, checkpoint on NFS, cold | 0% | 34.5 tok/s | 6547 ms | 1.04 GB |

- Decode reads 5 to 17 MB/s from disk in every state, so it does not depend on the cache; c=4 aggregate stays at 81 to 90 tok/s cold and capped.
- A cold 8K prefill reads about 1 GB (300 to 330 MB/s on NVMe): +20% TTFT vs the resident table. Each PLE row is 80 B of NVFP4 weights plus 10 B of scales in separate tensors, so a lookup touches two 4 KiB pages; bytes read from disk were 3.6x the bytes requested.
- Without memory pressure the cached part of the table grows linearly, about 0.36% of the table per 1K generated tokens (11.8% after 33K tokens, no plateau). When memory is needed, the kernel reclaims it with no decode loss (residency held at 4.7% under the 2 GiB cap).

## Details

- **Load:** the default loader hands over zero-copy safetensors mmap views. Their file and offset are found in `/proc/self/maps`, the files are opened read-only, and the views are released. Loading fails if the shards do not cover the table, if a dtype does not match, or if a view is not file-backed (for example `.bin` or `fastsafetensors`).
- **Per step:** `Qwen4ExpModelState.prepare_inputs` computes and deduplicates the n-gram ids, reads each row with `preadv` (after a `WILLNEED` read-ahead hint), and copies the rows to the staging buffers.
- **Parallelism:** every TP rank stages full rows, so no ETP reduction is needed. Elastic EP is rejected.
- **Alternatives:** #58439 reads the checkpoint mapping from the GPU through host page tables. #54070 writes a second copy of the table to disk. This PR reads rows on the host from the files the loader already opened.

This PR does not batch the per-row reads for long prefills (that is the TTFT cost), change the checkpoint layout (rows and scales in one tensor would halve the pages per lookup), or support weight reload.

- aijanai · comment · 2026-10-29T18:01:59Z · [source](https://github.com/vllm-project/vllm/pull/59958#issuecomment-6504475235)

Thanks for this, the approach of serving PLE rows straight from the checkpoint files is neat. We've been looking at Qwen4Exp on GB10 (unified memory) and read the diff with that use case in mind. We have three concerns; they come from reading the code, and we haven't measured them yet.

**1. The memory saving is mostly reclaimable page cache, not freed memory.** The rows still come through the page cache: `preadv` on the shard fds fills it, and the reported `MemAvailable` gain (4.6 → 32.0 GiB) counts that cache as available. The ids are hashes, uniform within each head's sub-table, so the set of pages a workload touches grows quickly with the number of distinct n-grams. At steady state, with varied prompts, we'd expect most of the ~27 GiB table to sit in the page cache. Under memory pressure (KV cache growth, a CPU or fs KV offloading tier, other ranks on a unified-memory box) the kernel evicts those pages and lookups silently fall back to random NVMe reads, with no sharp limit on the latency cost. Could you share page-cache residency of the PLE shard files (e.g. `fincore`) after a run with varied prompts (e.g. aiperf synthetic), plus decode/TTFT with a cold cache? We suspect the posted numbers come from a small, warm working set.

**2. Prefetching with `posix_fadvise(WILLNEED)` reads far more than it needs, given the file layout.** An NVFP4 row is 80 B of weights plus 10 B of scales, stored in two separate tensors, so a 4 KiB page holds ~51 weight rows or ~409 scale rows. With hashed ids, consecutive distinct ids almost never share or neighbour a page. The run-coalescing in `_read_rows` therefore rarely merges anything, and each needed row pulls a whole page into the cache: roughly 51× read amplification on weights and 409× on scales on a miss. On top of that, `_read_rows` issues one `os.preadv` per distinct row and plane from a single-threaded Python loop. An 8K prefill chunk with 16 heads means on the order of 10^5 syscalls per step, which may well explain the +11% TTFT even with a warm cache.

**3. The per-step stream sync removes CPU/GPU overlap.** The rows the forward reads are no longer a resident table: they are a per-step staging buffer, rebuilt every step from the files. Its contents depend on the token sampled in the previous step, so `stage_checkpoint_rows` has to `synchronize()` the stream, then read, then H2D-copy before the forward can launch. That serializes the CPU and the GPU and cancels async scheduling's overlap. At c=1 this costs 3.5%, but the host-side work grows with the batch while the GPU sits idle. Numbers at higher concurrency (e.g. c=8/32) would help.

**Possible direction (just a suggestion).**
- Keep a compact device-side row cache: set-associative, indexed directly by the n-gram id, since ids are already uniform hashes. It holds only rows that are actually used, so it is ~50× denser than the page cache.
- Read misses with `RWF_DONTCACHE` or `O_DIRECT`, so they don't pollute the page cache.
- Prefetch prompt-side ids from the host. Prompt tokens are known before scheduling, so the bulk of distinct ids can be loaded ahead of time.
- Only decode misses then need a host round-trip.

Whether this pays off depends on the hit-rate curve of real traffic, which can be estimated offline from tokenized prompts and the same splitmix hash. We're looking into that and will share it if it's useful.
