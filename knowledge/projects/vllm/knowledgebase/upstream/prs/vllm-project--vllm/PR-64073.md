# [Multimodal] Let encoder-decoder plugins process text-only encoder prompts (T5Gemma 2)

[Upstream PR](https://github.com/vllm-project/vllm/pull/64073) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Adds `EncDecMultiModalProcessor.process_text_only_encoder_prompt`, which lets encoder-decoder models whose encoder reads the prompt tokens (T5-style text encoders) accept text-only prompts with vLLM's own renderer, and lists the [vllm-t5gemma2-plugin](https://github.com/Chen-afk-art/vllm-t5gemma2-plugin) for T5Gemma 2 in the docs.

Following the review, the Model Runner V2 and `CrossAttention` changes of the first version moved into the plugin, which now runs on unmodified vLLM. This PR keeps only the processor-side hook, for the discussion with @DarkLight1337 below.

## Claims

- **`EncDecMultiModalProcessor.process_text_only_encoder_prompt`** (default `False`): when a processor sets it, the renderer sends encoder prompts without multimodal data through the processor too, so the processor can turn the prompt into the encoder item.
- **Without it**, such a plugin has to register its own renderer and copy `BaseRenderer._process_enc_dec(_async)`, as [the plugin does today](https://github.com/Chen-afk-art/vllm-t5gemma2-plugin/blob/use-vllm-extension-points/vllm_t5gemma2/renderer.py). The flag removes that copy, which would break when the renderer changes. Alternatively, bart-plugin asks users to pass the encoder text as `multi_modal_data`.
- **Docs**: list the T5Gemma 2 plugin, and document the flag for plugin authors.
- **No change for in-tree models**: the flag defaults to the current behavior.

## Details

**Why the encoder needs the processor.** vLLM V1 runs the encoder of an encoder-decoder model through the multimodal encoder path, so the encoder only sees what the processor packs into multimodal items. Encoder prompts without multimodal data skip the processor, which leaves a text encoder with no input.
- With the flag, `_process_singleton(force_mm_processing=True)` calls `_process_multimodal(prompt_token_ids, {}, ...)` and copies `prompt` and `cache_salt`, as `_process_tokens` does.
- It lives in `_process_singleton` rather than `_process_tokens` because `HfRenderer` overrides `_process_tokens`.
- `_process_enc_dec(_async)` enables it for the encoder prompt only.

**What moved into the plugin** (vllm-t5gemma2-plugin, branch `use-vllm-extension-points`):
- A `ModelState` from `get_model_state_cls()`: Model Runner V2 builds the tower LoRA mapping in the order of `scheduled_encoder_inputs`, while `EncoderDecoderModelState` runs the encoder in batch order. The plugin's state runs the encoder in the mapping's order, and the model moves the cross-attention K/V into batch order after projecting them.
- A `CrossAttention` subclass that passes the plugin's backend to `Attention.__init__`.
- On GPU with Model Runner V2, the plugin's tests pass with these (float16 on FlashAttention, and float32 on its PyTorch attention). With the plugin's state replaced by `EncoderDecoderModelState`, its LoRA test fails again.

**Duplicate check.**
- Open PRs matching "T5Gemma", "text-only encoder" and "encoder-decoder plugin" show nothing that overlaps.
- vllm-project/vllm#32617 (T5Gemma 2 in-tree) was closed after the review asked for a plugin. This PR follows that guidance and keeps the model out of tree.
