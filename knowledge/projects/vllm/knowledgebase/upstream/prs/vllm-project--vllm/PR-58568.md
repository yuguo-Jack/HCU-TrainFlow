# [Feature][KV Connector] Add UMBPStoreConnector for embedded and standalone DRAM

[Upstream PR](https://github.com/vllm-project/vllm/pull/58568) · state: open · merged: False

## Original PR description

## Overview

Implementation of [RFC: Scheduler-Aware Multi-Tier KV Caching for vLLM with MORI-UMBP](https://github.com/vllm-project/vllm/issues/57187). It adds one `UMBPStoreConnector` that offloads KV blocks to MORI-UMBP DRAM and restores them after they leave GPU memory. Embedded mode keeps a private pool in each worker. Standalone mode attaches to a node-local server so engines on the host share one pool.

This updates the earlier embedded-only snapshot on this PR with the shared connector, standalone mode, lazy offload, and the Mooncake comparison from [charxwu/vllm#7](https://github.com/charxwu/vllm/pull/7). Each commit is one review slice under Modifications.

- [charxwu/vllm#4](https://github.com/charxwu/vllm/pull/4) is the previous combined review branch (`review/umbp-merged-series`).

## Claims

- One V1 connector serves embedded and standalone UMBP. Runtime topology stays behind `IUMBPRuntime`.
- vLLM keeps scheduling, GPU blocks, prefix hashes, and cache-group rules. UMBP owns DRAM allocation, lookup, publication, and eviction.
- Transfers use registered GPU ranges. The connector does not build a contiguous host staging copy.
- Missing, evicted, timed-out, or partial objects are cache misses and can be recomputed (`kv_load_failure_policy: recompute`).
- On the recorded MI355X run, embedded UMBP store overhead stays close to no-offload, and forced external restore is faster than Mooncake RDMA on the same GPU. See Validation for the exact tree and the cases Mooncake wins.

### Speed

Lower latency is better. Hardware: AMD Instinct MI355X, physical GPU4, NUMA 1, CPU affinity 96-111. Model `openai/gpt-oss-20b`, TP1 / PP1. GPU KV cache 40 GiB. External DRAM pool 80 GiB. Block size 32.

UMBP connector settings for these tables: `num_workers=8`, `lookup_workers=2`, `lookup_async=false`, `load_async=true`, `lazy_offload=false`, `dram_numa_node=1`, `dram_prefault=false`. Mooncake used local `rdma4` and a local master. Embedded Mooncake contributed an 80 GiB RDMA segment. Standalone Mooncake used an external 80 GiB owner and `global_segment_size=0`.

- YukioZzz · comment · 2026-09-30T02:08:50Z · [source](https://github.com/vllm-project/vllm/pull/58568#issuecomment-5902672044)

Thanks for the base PR. While preparing the standalone runtime on top of this PR, I noticed two embedded-mode issues that I think are worth fixing here rather than later:

**1. Lookup socket paths collide across DP ranks / engines on the same host**

`_lookup_socket_path()` (`runtime/embedded.py`) derives the path from `sha256(namespace:rank_namespace)` only, where `rank_namespace` is `(tp, pcp, dcp, pp)`. Neither the DP rank nor any engine identity is part of it, and `UMBPNamespace` is intentionally engine-independent (model/layout/topology only).

So with `data_parallel_size=2` on one node — or two independent embedded engines serving the same model — worker `tp0` of each engine resolves to the same `/tmp/vllm-umbp-<digest>.sock`. `_MoriLookupServer.start()` unlinks an existing path before binding, so the second engine silently takes over the socket instead of failing with `EADDRINUSE`. From then on, DP0's scheduler queries DP1's private pool. The result is false-positive hits followed by load failures (or recompute loops, depending on `kv_load_failure_policy`), while DP1's own pool is never consulted by DP0.

The existing tests cover TP=4 within a single engine, so this doesn't surface there.

For reference, `MooncakeStoreConnector` handles the same problem in `get_zmq_rpc_path_lookup()` by including the hostname and `parallel_config.data_parallel_index` in the IPC path, plus an optional `lookup_rpc_port` to separate independent engines:

```python
f"ipc://{base_url}/lookup_rpc_port_{rpc_port}_host_{hostname}_dp_rank{dp_rank}"
```

Suggested fix: include `data_parallel_index` (and an optional user-provided instance id / port) in the digest input, and default `lookup_dir` to `envs.VLLM_RPC_BASE_PATH` for consistency with other connectors. It would also be safer to fail loudly if the path is already bound by a live listener rather than unlinking it unconditionally. A unit test with two `RankTopology`s that differ only in DP rank would pin this.

**2. The scheduler process allocates a DRAM pool it never uses**

`UMBPStoreConnector.__init__` calls `UMBPRuntimeFactory.build()` for both roles, and `EmbeddedRuntime.from_config()` constructs `UMBPClient(client_config)` eagerly. In the scheduler process that client is never used: `_MoriSchedulerHandle` only talks to the workers over the lookup sockets.

This isn't just a handle. In MORI, the embedded client is a local-only `DistributedClient` whose DRAM `PageBackend` self-allocates at `Init()`, and `UMBPDramConfig::prefault` defaults to `true` (it's only overridden here when `dram_prefault` is set explicitly). So each engine's scheduler process maps and prefaults one full per-rank capacity — 64 GiB by default, or `total_capacity_bytes / rank_count`. With DP>1 this repeats once per engine. It also means host RAM is effectively over-committed relative to what `total_capacity_bytes` claims to budget.

Suggested fix: make client construction lazy, e.g. keep `UMBPConfig` on `_MoriEmbeddedRuntime` and create the `UMBPClient` in `create_worker_handle()`, so `create_scheduler_handle()` never touches MORI allocation. A quick check is the EngineCore process RSS before and after the change with a small `capacity_bytes` and `dram_prefault` left at its default.

- YukioZzz · comment · 2026-09-30T17:07:00Z · [source](https://github.com/vllm-project/vllm/pull/58568#issuecomment-5915997368)

Thanks for the update. I rebased the standalone/distributed stack (#59275, #59276, #59281) onto `37832fa99`; the lazy scheduler client and the load-only `failed_block_ids` already cover two of my earlier fixes, so those are dropped. Re-reviewing the new head turned up three issues in the shared/embedded code. Each has a fix plus test at the bottom of #59275, and you're welcome to take them into this PR:

**1. Hybrid (Mamba-style) models with `load_async=false` read stale state.** Embedded mode advertises `layerwise_load=True`, so a synchronous load is split per layer. Linear-attention/Mamba layers never call `wait_for_layer_load`, and vLLM copies the restored Mamba state into the running slot while preparing inputs, before the load lands. On Kimi-Linear-48B-A3B GSM8K (256 questions, conc 64) restored prompts fell from 89% to 52% with `load_async=false`. Waiting in `start_load_kv` does not help, because the copy has already happened. The Qwen3.5 checks in the description use async load, so they do not cover this. Fix: the scheduler forces async load when any group is a `MambaSpec` and warns ([commit](https://github.com/vllm-project/vllm/pull/59275/commits/9a717fab1bb5842a88dacc61abcbf101a16a1178)).

**2. With `load_async=true`, every forward step waits for all in-flight restores.** `load_blocks` jobs are stored as `{None: job}`, and `_drain_load_jobs(wait=True, layer_name=...)` always includes `None` in `selected`. So the first attention layer of each step blocks until every other request's asynchronous load finishes, even though those requests are not in the batch and nothing reads their blocks. This puts restores back on the running batch's critical path. Single-request restore tests and random-prompt serving don't show it. Fix: `wait_for_layer_load` returns immediately for async loads, and preemption drains the jobs directly ([commit](https://github.com/vllm-project/vllm/pull/59275/commits/28d27cbd52374068ffe803a42ffef987e01341db)).

**3. Lookup socket collision** (from my earlier comment, still present): the path now also hashes `data_parallel_index` and an optional `lookup_instance`. A live listener on the path fails startup instead of being unlinked and taken over ([commit](https://github.com/vllm-project/vllm/pull/59275/commits/fd6ab36dbb0db1eedd279531aa7bbdee180eafdc)).

A note on the new `poll()` behavior: raising `TimeoutError` once a store passes its deadline fails the engine step from `get_finished`. That is a reasonable fail-stop for an in-process DRAM pool. For the shared-pool modes, where a stalled server or master is an expected failure, #59275 overrides `poll()` so the store stays pending and the store event keeps its source blocks pinned, while new transfers are refused. If you prefer the base class to own that policy, a per-runtime capability flag would work too.
