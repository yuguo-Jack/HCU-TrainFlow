# [Bugfix][Spec Decode] DSpark: store draft KV cache in model dtype for MLA-only cache layouts; fail fast on DCP

[Upstream PR](https://github.com/vllm-project/vllm/pull/48381) · state: open · merged: False

## Original PR description

FIX #48380

Two DSpark fixes for DSA-family targets:

1. **Draft cache dtype.** With `--kv-cache-dtype fp8_ds_mla` the DSpark draft — a dense (non-MLA) Qwen3-style transformer — inherited the target's `cache_config` and tried to use the MLA-only fp8_ds_mla layout, which no dense attention backend accepts (`ValueError: No valid attention backend found for cuda ...`). `load_dspark_model` now falls back to the model dtype for the draft's KV cache; the draft cache is a few dense layers, so the memory cost is negligible.
2. **DCP fail-fast.** The DFlash/DSpark draft slot mapping is DCP-blind (`ctx_pos // block_size`), so with `decode_context_parallel_size > 1` the draft reads wrong KV blocks and acceptance silently collapses to ~0% (reported by @Leoyzen in #46514). Config validation now rejects the combination instead of degrading silently.

**Not a duplicate:** #47934 (FP4 target on B300) and #47626 (H20 fp8) crash later, in FlashInfer draft attention; no open PR touches the draft cache-config inheritance or adds a DCP guard for dflash/dspark.

**Testing** (4×H200, GLM-5.2-NVFP4 target, RedHatAI/GLM-5.2-speculator.dspark):
- Before: the repro from #48380 fails at draft load with the ValueError above.
- After: server boots, output coherent end-to-end; 95 tok/s N=1, 341 tok/s aggregate N=8, mean accepted length ~2.4 (metrics: 4065 accepted / 2999 drafts / 20993 draft tokens).
- DCP guard: same command + `--decode-context-parallel-size 2` now fails at config validation with a clear NotImplementedError (previously: silent ~0% acceptance).

AI assistance was used for this change (Claude); the submitter reviewed every line and ran the tests above.

- Leoyzen · comment · 2026-07-13T01:43:22Z · [source](https://github.com/vllm-project/vllm/pull/48381#issuecomment-4953698864)


Nice catch on the DCP guard — that's a real footgun.

One issue with the draft cache dtype fallback though: it breaks DeepSeek V4 DSpark.

The assumption in the comment ("The draft is a dense (non-MLA) Qwen3-style transformer") holds for generic DSpark targets like GLM-5.2, but **not** for DS V4. The DS V4 DSpark draft (`DSparkDeepseekV4ForCausalLM` in `models/deepseek_v4/nvidia/dspark.py`) reuses `DeepseekV4DecoderLayer`, which instantiates the same MLA attention class as the target (`DeepseekV4FlashMLAAttention` or `DeepseekV4FlashInferSM120Attention`, both with `use_fp8_ds_mla_layout = True`).

So when the target runs with `--kv-cache-dtype fp8_ds_mla` (or `fp8`, which gets resolved in-place to `fp8_ds_mla` by `_resolve_dsv4_kv_cache_dtype`), this PR forces the draft cache to `"auto"`. The draft's MLA attention then hits the assertion in `attention.py:83`:

```python
assert kv_cache_dtype.startswith("fp8"), (
    f"DeepseekV4 fp8_ds_mla layout only supports fp8 kv-cache, got {kv_cache_dtype}"
)
```

`"auto"` doesn't start with `"fp8"` → `AssertionError` at draft model load.

The fix needs to be model-aware: only fall back to `"auto"` when the draft is actually a dense (non-MLA) model. For DS V4 DSpark the draft **is** MLA and should keep the target's `fp8_ds_mla` cache dtype as-is.

- drakosha · comment · 2026-07-13T10:39:32Z · [source](https://github.com/vllm-project/vllm/pull/48381#issuecomment-4957073171)

@Leoyzen You're right, and it's not hypothetical: the patched `cache_config` does reach the DS V4 draft's MLA layer (`initialize_model` enters `set_current_vllm_config(draft_vllm_config)`, and `DSparkDeepseekV4Model` builds its `DeepseekV4DecoderLayer` from `get_current_vllm_config()`), so `"auto"` trips the `startswith("fp8")` assert at draft load.

Fixed in [`66208a7`](https://github.com/vllm-project/vllm/pull/48381/commits/66208a739): the fallback is now gated on `draft_model_config.use_mla`. Only a dense draft gets the model-dtype KV cache; the DS V4 DSpark draft keeps the target's `fp8_ds_mla` layout, unchanged from today. The gate holds for speculators-format checkpoints too — `RedHatAI/GLM-5.2-speculator.dspark` converts to `Qwen3DSparkModel` with `transformer_layer_config.model_type: qwen3`, so `use_mla=False`.

I can only cover the dense path here (GLM-5.2-NVFP4 + `fp8_ds_mla`, 4×H200: boots, coherent, mean accepted length ~2.4). If you can run DS V4 DSpark with `--kv-cache-dtype fp8` against this commit, a confirmation would be welcome. Same for #48392, now out of draft — it adds real DCP support for the DFlash/DSpark draft (kv-head-replicated draft cache) and replaces the fail-fast here with precise gates, including an explicit reject for DS V4 DSpark + DCP. I've validated it on 4×H200 (accept-len 2.63 vs ~1.10 broken); an 8×H200 run would be the missing piece.
