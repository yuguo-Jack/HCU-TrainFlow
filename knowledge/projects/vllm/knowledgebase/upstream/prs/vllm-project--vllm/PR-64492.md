# [Bugfix][Rust Frontend] Accept assistant turns without content like Python

[Upstream PR](https://github.com/vllm-project/vllm/pull/64492) · state: closed · merged: True

## Original PR description

## Overview

The Rust frontend returns a 400 for an assistant message with no content (`content: null`, `content` omitted, or `content: []`) and no tool calls. The Python frontend accepts all three and renders an empty assistant turn, same as `content: ""`, which Rust already accepts. This brings Rust in line.

I ran into it while diffing render output between the two frontends. `{"role": "assistant", "content": null}` shows up a lot in replayed history (tool calls stripped by the client, placeholder turns), so it's worth matching.

## Claims

- Assistant turns with null, missing or `[]` content and no tool calls are accepted on `/v1/chat/completions`, `/v1/chat/completions/render` and `/tokenize`, and render the same as `content: ""`.
- Token IDs match the Python frontend for these, including when the empty turn is the last message, with and without `continue_final_message`.

## Validation

`Qwen/Qwen3-0.6B`, `/v1/chat/completions/render`, messages `[user "hi", <assistant>, user "hi"]`:

| `<assistant>` | Python | Rust main | Rust this PR |
|---|---|---|---|
| `{"role":"assistant","content":""}` | 200 | 200 | 200 |
| `{"role":"assistant","content":null}` | 200 | 400 | 200 |
| `{"role":"assistant"}` | 200 | 400 | 200 |
| `{"role":"assistant","content":[]}` | 200 | 400 | 200 |
| `{"role":"assistant","content":null,"tool_calls":[]}` | 200 | 400 | 200 |

The 400s are `Assistant messages must contain text, reasoning content, or tool_calls.` All the 200s return the same 20 token IDs. I also checked the empty turn as the final message: 18 tokens with default flags and 13 with `continue_final_message: true, add_generation_prompt: false`, same as Python in both cases.

The new route test sends all five variants (plus `content: null` with `reasoning: ""`) and checks for a 200 and identical token IDs. It fails on main at the `content: null` case and passes with the change.

```bash
cd rust
cargo test -p vllm-server --lib -- render_chat_accepts_assistant_turn_without_content
cargo test -p vllm-server   # 546 passed
```

`cargo fmt`, clippy and pre-commit are clean on the changed files.

After the follow-up commit that removes the check instead of adding an empty text block: `cargo nextest run -p vllm-server -p vllm-chat --lib` passes (1060 tests), the route test fails with the check restored, and clippy is clean.

## Details

`convert_message` in `chat_completions/convert.rs` builds an assistant message out of reasoning, text and tool-call blocks, and it bailed when that list came out empty. `content: ""` produces one empty text block, so it passed. The other forms of the same empty turn produced nothing and got rejected. The check is removed, so an assistant message may now have no blocks. Every renderer already treats that like one empty text block: they either join the text blocks or skip empty ones. So these turns render the same as `content: ""`. Leaving out a synthetic empty text block also keeps `content: null` without a text part, which is what Python passes to `openai`-format templates (`[]`). Rust's own non-streaming response returns `content: null` with no tool calls when the generated text is empty, so a client replaying that history used to get this 400.

Since #62424, an empty `reasoning: ""` is kept as its own block, and the check also rejected a turn whose only blocks were empty reasoning. With the check gone, `{"role": "assistant", "content": null, "reasoning": ""}` also renders as an empty turn instead of a 400, like Python; the route test covers it as a sixth variant.

I didn't find an existing issue or PR for this. #54368 is the Python side (null content with tool calls), and #63132 and #63137 are about the reasoning field aliases, so they don't overlap.
