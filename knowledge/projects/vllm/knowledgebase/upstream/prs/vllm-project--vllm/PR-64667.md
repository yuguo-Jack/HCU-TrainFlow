# [Frontend] Add --enable-log-request-ids-only

[Upstream PR](https://github.com/vllm-project/vllm/pull/64667) · state: open · merged: False

## Original PR description



## Overview

Adds `--enable-log-request-ids-only`, which logs request IDs and lifecycle events without any request content (prompts, parameters, LoRA requests, JSON bodies). Fixes #64654.

## Claims

- `--enable-log-request-ids-only` turns on request logging by itself. The frontend logs `Received request <id>.`, and the engine's existing `Added request`, `Request ... aborted` and `Request ... failed` lines are unchanged.
- In this mode `RequestLogger` writes no prompt, token IDs, `SamplingParams`, LoRA request or JSON body at any log level, DEBUG included.
- Startup rejects the flag together with `--enable-log-requests`, `--enable-log-outputs` or an explicitly set `VLLM_REQUEST_BODY_LOG_LEVEL`. The error lists every option that conflicts.
- Default behavior is unchanged when the flag isn't set.

## Validation

New tests:

- `test_request_logger.py::test_request_logger_ids_only_omits_request_content` puts one marker string in the prompt, `stop`, `bad_words`, `extra_args`, the structured-output regex, the LoRA request and the JSON body, with DEBUG enabled. In ids-only mode the marker never reaches the logger and the only INFO call is `Received request req-1.`. The `ids_only=False` case checks the marker does appear, so the test can't pass vacuously.
- `test_cli_args.py`: the flag is rejected with `--enable-log-requests`, with `--enable-log-outputs`, with both, and with `VLLM_REQUEST_BODY_LOG_LEVEL` set. Alone it passes validation and reaches `AsyncEngineArgs`.

Before the change (base `335dd77b09`, changed source files reverted):

```text
$ pytest tests/entrypoints/serve/utils/test_request_logger.py tests/entrypoints/common/test_cli_args.py -k ids_only
E   TypeError: RequestLogger.__init__() got an unexpected keyword argument 'ids_only'
E   SystemExit: 2      # argparse: unrecognized --enable-log-request-ids-only
7 failed, 79 deselected
```

With the change (CPU, WSL2, `VLLM_TARGET_DEVICE=cpu`):

```text
$ pytest tests/entrypoints/serve/utils/test_request_logger.py tests/entrypoints/common/test_cli_args.py tests/entrypoints/launchers/render/test_app_state.py
88 passed
```

End to end with the GPU-less render server (`vllm launch render Qwen/Qwen3-0.6B`), sending a `/v1/chat/completions/render` request whose message and `stop` contain `MARKER-64654`:

| Run | Log level | Marker lines in server log |
|---|---|---|
| `--enable-log-requests`, `VLLM_REQUEST_BODY_LOG_LEVEL=INFO` | INFO | 1 (the JSON body) |
| `--enable-log-request-ids-only` | DEBUG | 0 |
| `--enable-log-request-ids-only --enable-log-requests` | - | startup fails: `TypeError: Error: --enable-log-request-ids-only cannot be combined with --enable-log-requests` |

The render server doesn't call `log_inputs`, so this run covers the JSON body path and startup validation. The unit test covers `log_inputs`. I don't have a GPU here, so I didn't run `vllm serve` with a model; the engine-side change is only the `log_requests` flag passed to `AsyncLLM`.

`ruff check` and `ruff format` are clean. mypy on the changed files reports no errors on changed lines; the existing errors in `arg_utils.py` and `async_llm.py` are on untouched lines. The new tests run in the existing "Entrypoints Unit" (`entrypoints/common`) and "Entrypoints Integration (API Server)" (`entrypoints/serve`) steps.

## Details

- Design follows the discussion in the issue: ids-only is a restriction on content logging, not a peer mode, so it's a standalone flag whose startup check is the one place that keeps request content out of the logs. A future content-logging option should be added to that check.
- The flag lives on `AsyncEngineArgs` next to `--enable-log-requests`, because the engine's lifecycle logs are switched by the same `log_requests` value. The three places that pass it to `AsyncLLM` (`from_engine_args`, the API server and gRPC launchers) now use `enable_log_requests or enable_log_request_ids_only`, and both `RequestLogger` construction sites pass `ids_only`.
- `--max-log-len` has no effect in this mode, and the flag's help text says so. The help text is also the rendered CLI reference, and `--enable-log-requests`'s help points to the new flag.
- The `--enable-log-outputs requires --enable-log-requests` check now runs after the ids-only check, so `--enable-log-request-ids-only --enable-log-outputs` reports the ids-only conflict instead.
- Out of scope: sanitizing exception messages, third-party logs or user-supplied request IDs, and the Rust frontend.
- Duplicate check: no open or merged PR adds ID-only request logging. #35864 adds a structured `request_id` field to log records and doesn't change what content is logged.
- AI assistance was used to write this change. I reviewed every line and ran the tests above myself.
