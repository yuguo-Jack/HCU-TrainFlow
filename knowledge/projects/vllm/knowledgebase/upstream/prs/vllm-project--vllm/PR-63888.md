# [ROCm][Perf][DSv4.1] Skip the top-k -1 fill on the rows vLLM's decode top-k writes

[Upstream PR](https://github.com/vllm-project/vllm/pull/63888) · state: open · merged: False

## Original PR description

## Overview

The paged MXFP4 sparse indexer (gfx950, #58671) fills the step's top-k rows with -1 before its top-k kernels run. On decode rows that go to vLLM's `top_k_per_row_decode` (gfx950 k = 512 path: #56743), the fill is dead: that kernel writes all k entries of every row. This PR skips the fill on those rows, as the gfx942 indexer already does (#60731), and adds a GPU test for the mixed and padded steps the skip also covers.

## Claims

- **Same output as main.** Below 128 rows and below k = 2048, every path of `top_k_per_row_decode` stores all k slots of each row, with -1 past a short row's end, so the skipped -1 would always be overwritten. On the gather path, `_remap_compact_topk` then rewrites every slot. This write-all property was checked on MI355X at k = 32, 512 and 1024, rather than by diffing outputs against main:
  - A sentinel sweep of the kernel, called as `_topk` calls it, found no unwritten slot in 480 of 480 cases (240 shapes, each with two data distributions).
  - With the fill removed from every row, the indexer's GPU tests still pass, except the 6 cases with trailing padding rows. Those fail only on the padding rows, after their decode and prefill rows have passed.
- **8 fewer kernels per decode step (measured), all inside the decode graph.** That is one per index layer of DeepSeek-V4.1-Flash. `FillFunctor<int>` drops from 17 to 9 per decode step at both c1 and c2. Total kernels per step drop by exactly 8, and the `topKPerRowDecode`, mono K1 and eager-fill counts do not change.
- **Gain: small.** A 2-round ABBA on a main nightly measured -13 us (-0.25%) per decode step at c1 and -7 us (-0.11%) at c2.
  - The gain has the same sign and size on both GPU halves: -13 / -14 us at c1, -8 / -7 us at c2.
  - The 8 removed fills took about 37 us of in-graph kernel time per step in the profile, so the end-to-end saving is about a third of that.
  - There is no regression.
- **Accuracy unchanged.** GSM8K-1319: 0.9191 vs 0.9183. Real AL: 3.579 vs 3.576. Both are means over 4 runs per arm. Per-question flips between main and this PR (mean 66.9 questions) are within the flips between two runs of the same code (main 72.8, PR 63.2).
- **Unchanged elsewhere.** These rows keep the fill:
  - rows that aiter's top-k takes (128+ decode rows, which is about 19+ requests at DSpark k = 6, or k >= 2048);
  - steps without decode rows;
  - rows after the decode rows (padding, prefill).

**Sentinel sweep.** The output is pre-filled with -777. The kernel is then called as `_topk` calls it: `torch.ops._C.top_k_per_row_decode(logits, 1, lengths, out, rows, logits.stride(0), logits.stride(1), k)`, with fp32 logits and 1-D int32 lengths.
- Parameters:
  - k: 512 and 1024.
  - Rows: 1, 7, 14, 32, 33, 60, 64, 65, 100 and 127.
  - Widths: 4096, 12287, 12288, 16385, 65537, 199999, 200000, 262145, 524288 and 1048576.
  - Row lengths: 0, 1, k-1, k, k+1, the full width, and random.
  - Data: randn, and a tie-heavy integer distribution.
  - Logits: contiguous, plus a strided view at two widths.
- This reaches every gfx950 k = 512 config below 128 rows (one block; split + merge for <= 32 rows above 16K, and for <= 128 rows above 64K). For k = 1024 it reaches the insertion, radix, split and device-length-aware paths.
- For each row of length L and n = min(k, L), it checks:
  - no -777 is left;
  - there are exactly n distinct indices in [0, L);
  - each index's logit is >= the n-th largest;
  - exactly k - n slots hold -1.
- The two controls each fail 480/480:
  - one leaves one -777 slot;
  - the other turns a -1 slot into a stale index. That index is in range wherever the row is not empty, and the checker catches it as a duplicate.

- Steps are delimited by the mono K1 kernel for 7 rows or 14 rows. The 7-row steps include the c2 window's single-request steps.
- A fill counts as in-graph when its runtime call is `hipGraphLaunch`. Kineto records no grid or block for graph-replayed kernels, so the indexer fill is identified by the kernel just before it.
- Step times in a profiled run are inflated and are not used.

**Why every vLLM-kernel row is fully written** (`csrc/sampler.cu` on main):
- `topKPerRowJob` either takes the `rowLen <= topK` shortcut (indices, then -1 up to k) or ends in the final store loop over all k slots.
- gfx950 k = 512 (`topKPerRowDecode512DeviceLengthAware`): a row runs either in one block that stores directly, or in split blocks plus a merge launch. Both launches compute the same `activeBlocks`, so each row is written exactly once.
- The k = 1024 path and the generic insertion, radix and split+merge paths end in the same store loop.
- `rowEnd` is clamped to >= 0, so a padding row (length 0) is written as all -1.
- Rows are addressed at stride k. Both callers, DeepSeek-V4 and V4.1, allocate the buffer as `[max_num_batched_tokens, index_topk]`, so its width is k.

## Details

**Design.** `_vllm_topk(rows, k)` holds `_topk`'s dispatch condition (`rows < 128 and k < 2048`). Both entry points call `_fill_topk_rows`.
- When `_vllm_topk` holds for the decode rows, the fill starts after them. Otherwise it fills from row 0, as before.
- Decode rows lead the step (flattened). Padding requests have seq_len 0, so the kernel writes all -1 for their rows.
- Both decode paths write exactly `topk_buffer[:rows, :k]`.

**Gate and tradeoffs.**
- **Env-free and shape-only.** FULL graphs capture the same choice, and breakable graphs decide per step. No device tensor is read on the host.
- **In-graph.** At c1/c2 every decode step replays a FULL uniform-decode graph of 7/14 rows (`v1/worker/gpu/cudagraph_utils.py`). Mono takes a layer only in NONE or FULL mode, and `eager_break_during_capture` passes the op through under FULL. So the op and main's 8 fills are captured in the graph, and the saving is in-graph GPU time only. Only mixed and prefill steps (breakable PIECEWISE) run the op as an eager break.
- **Scope.** #60731 requires a pure-decode, unpadded step. This gate also skips the decode rows of padded and mixed steps.
  - The new GPU test covers both: decode rows followed by prefill rows, and by padding rows, at k = 32, 512 and 1024.
  - The GSM8K runs at 8 in parallel also run mixed steps end to end.
  - The decode-only form (`metadata.prefill is None`) is a one-line change if reviewers prefer it.
- **Models.** The op serves DeepSeek-V4.1 and, on CDNA4 with AITER on, DeepSeek-V4 by default (#63669). DeepSeek-V4 decode takes the same skip whenever its `index_topk` is below 2048 (512 on V4-Flash, 1024 on V4-Pro). V4-Flash has 21 indexer layers, so its decode step should drop 21 fills rather than V4.1's 8. It has not been run end to end; see Validation.
- **Contract.** The skip relies on vLLM's kernel writing every slot. These tests check that:
  - `test_topk_matches_torch_on_both_kernels[8-4096-512]`: vLLM's kernel at k = 512, pre-filled with 7, with a row shorter than k.
  - The new mixed/padded test: the full op at k = 32 / 512 / 1024.
  - `test_top_k_per_row_decode_gfx950_k512_1d_seq_lens` and `_masked_graph_replay`, which pre-fill -777.

  The decode-layer tests run k = 32, the generic path. The shared predicate guards edits to `_vllm_topk` only; other edits to `_topk`'s aiter branch are caught only by these GPU tests. Rows taken by aiter's top-k keep the fill.

**Limitations.**
- **Small gain.** The profile removes ~37 us of in-graph kernel time per step. The end-to-end ABBA measured -13 us at c1 and -7 us at c2, on 2 rounds, one MI355X node and a main nightly.
- **No DeepSeek-V4 end-to-end run.**
- **CI coverage.** Default CI runs only the CPU plan test here: `:amd: (MI300) V1 Attention` and `:amd: (MI355 DPX) V1 Attention` are not optional and start once the PR is `ready`. The GPU indexer test runs only in AMD CI's optional `:amd: (MI355 DPX) Attention Kernels`, which needs `/amd-ci run` and an Unblock. No CI job runs `test_top_k_per_row.py` on gfx950.
