# [Bugfix][Attention] Bound batch_size in GDN cudagraph padding branches

[Upstream PR](https://github.com/vllm-project/vllm/pull/50680) · state: open · merged: False

## Original PR description

Fixes #50623

## Summary

The FULL cudagraph padding branches in the GDN attention metadata builder guard on `num_decodes`/`num_spec_decodes` but slice their preallocated buffers by `batch_size`:

- **Spec-decode branch** (`vllm/v1/attention/backends/gdn_attn.py`): `batch_size` may include zero-length padded requests, so the guard does not bound the slice. A batch exceeding `decode_cudagraph_max_bs` would silently clamp the slice to the preallocated buffer length and downstream kernels would index a shorter tensor than the batch implies.
- **Non-spec branch**: `batch_size == num_decodes` in a pure decode batch, so the guard does bound the slice — but this is not obvious from the code.

This PR adds `assert batch_size <= self.decode_cudagraph_max_bs` in both branches (as suggested by the reporter), making the invariant explicit and converting any future violation into a loud failure instead of silent misbehavior. No runtime behavior change in valid scenarios.

Also updates stale TODOs in `csrc/rocm/skinny_gemms.cu` per the issue's analysis: K % 8 is enforced by the call-site `TORCH_CHECK`, and the LDS-resident kernels are only dispatched when the activation fits in LDS (`WVSPLITK_CFG`), so the old "64 KB" and "K multiple of 8" warnings no longer describe the code. The file-level TODO's integer-overflow and stride notes are intentionally left untouched (stride fix pending in #50618; widening index math is a perf risk).
