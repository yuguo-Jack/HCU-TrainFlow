# [Bugfix][Spec Decode] Propagate rope hf_overrides to MTP draft

[Upstream PR](https://github.com/vllm-project/vllm/pull/58094) · state: open · merged: False

## Original PR description

Fixes #58080

`--hf-overrides` as a dict (the YaRN / rope CLI path) was dropped when building the speculative draft `ModelConfig`. The target ran extended RoPE, the MTP draft stayed on native encodings, and acceptance went to 0% past the draft's native `max_position_embeddings`.

This forwards rope-relevant mapping-style overrides (`rope_parameters`, `rope_scaling`, `max_position_embeddings`, including nested `text_config`) onto the draft before architecture mapping. Callable overrides are unchanged.

#37443 targets the same bug (#37435) but is conflicted against current `compose_draft_hf_overrides` and would drop callable composition from #45352, so this is not a duplicate of that PR.

1. **Context Window Scale Parity**:
   When the target base model applies RoPE scaling overrides (e.g. `rope_theta`, `yarn_scaling_factor`, or extended position factor mappings via `hf_overrides`), failing to forward these overrides to the MTP draft worker causes frequency misalignment in relative position embeddings.

2. **Draft Verification Stability**:
   Forwarding `hf_overrides` to the draft runner ensures the speculative proposal heads match the target model's positional representation exactly across long-context sequences (>32k tokens), preventing false speculative rejection rates.

```python
# Verification of draft config propagation
draft_hf_config = copy.deepcopy(target_hf_config)
```

**MTP**, no `max_model_len` in the speculative config:
- v0.30.0 + this PR, K=4: needle found 18/18 at prompts up to 979K, 3.4-3.8 tokens/step. In production since 2026-10-04, where it replaced a `max_model_len` pin in the speculative config.

**DFlash2** (z-lab/Qwen3.8-27B-DFlash2, flat config) with the same nested target override fails at startup:

```
pydantic ValidationError ... SpeculativeConfig
  Value error, The text_config extracted from the model config does not have `num_attention_heads` attribute
```

It's raised from `get_hf_text_config` in `vllm/transformers_utils/config.py`. Reverting this PR's two files (`vllm/config/speculative.py`, `vllm/config/model.py`) boots the same command.

My read of the cause: the draft-override composition runs for every method except medusa. The nested `text_config.rope_*` keys land on a draft config that has no `text_config`, which creates a bare `text_config` dict, and transformers' `get_text_config()` then returns that dict.

Two ways out: only descend into a nested key when the draft hf_config already has that sub-config (otherwise skip it or apply the rope keys at top level), or limit the forwarding to MTP-style drafts. A test with a flat draft config and a nested target override would catch it. I only ran DFlash2; DSpark and EAGLE drafters with flat configs look like they take the same path.

- lucifer1004 · comment · 2026-10-14T00:26:21Z · [source](https://github.com/vllm-project/vllm/pull/58094#issuecomment-6158089211)

Ran the MTP path on hardware: this fixes a hard crash, not only the acceptance collapse in #58080.

Setup: `nvidia/Qwen3.8-Flash-Next-NVFP4` (Qwen4Exp), TP2, MTP3 with the V2 model runner, YaRN x4 via `--hf-overrides '{"text_config":{"max_position_embeddings":1048576,"rope_parameters":{..."rope_type":"yarn","factor":4.0,"original_max_position_embeddings":262144}}}'`, `--max-model-len 1010000`. Reproduced on both H200 and RTX PRO 6000.

Without this PR, a single prompt past 262,144 tokens kills the engine with `CUDA error: an illegal memory access`. With `--enforce-eager` and `CUDA_LAUNCH_BLOCKING=1` the fault is in `_qsa_prepare_kernel` (`vllm/models/qwen4_exp/nvidia/ops/qsa_prepare.py`), called from the draft's QSA layer during `speculator._prefill`. The draft keeps the native config, so its M-RoPE cos/sin cache has 262,144 rows, and the kernel indexes it by position without a bound. Before #59853 the 4x M-RoPE cache headroom hid this (the draft just ran unscaled RoPE past 262K); since #59853 the draft cache is exactly the native length, so this is now a crash on main.

With this PR (581e6d4ecd) merged onto main 98f7211162, the same server serves 300K, 600K and 900K-token prompts, and the PR's tests pass (23 passed).
