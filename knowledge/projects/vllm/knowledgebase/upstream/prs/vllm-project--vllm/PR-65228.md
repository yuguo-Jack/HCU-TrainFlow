# [Attention] Prefer 128-token KV blocks for FA4 on Blackwell

[Upstream PR](https://github.com/vllm-project/vllm/pull/65228) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Make the FlashAttention backend prefer a 128-token KV cache block size when FA4 runs on Blackwell (SM100/SM103) with `head_size >= 128`. FA4's SM100 forward loads paged KV via TMA only when `page_size == tile_n` (128); any other page size takes the slower gather path.

General replacement for the hd256-only special case that #65203 removes.

## Claims

- FLASH_ATTN + FA4 on SM100/SM103, `head_size >= 128`: default block size 16 -> 128 when `--block-size` is not set. Kernel support is unchanged (`MultipleOf(16)`); a pinned `--block-size` still wins.
- Attention kernel time on B300, block 128 vs 16 (geomean over 16 shapes x 4 head configs): hd128 **1.07x** (bf16 KV) / **1.08x** (fp8 KV); hd256 (unified FA4) **1.16x** / **1.19x**.
- hd64 is excluded: prefill/extend regress (0.91–0.98x bf16, 0.81–0.94x fp8 KV).

## Validation

Hardware: 1x B300 (SM103) per run, upstream main `5cdeea9b13` + this PR, precompiled wheel, CUDA graphs on.

## Details

- Only `get_preferred_block_size` changes. The preference applies only when FLASH_ATTN is the sole non-SSM backend; multi-backend models keep `_preferred_block_size_for_backends`'s common-size logic, and hybrid models still go through mamba page alignment afterwards. MLA backends are separate and unaffected. Subclasses (`FLASH_ATTN_DIFFKV`, Step5) inherit it, but their head shapes fall back to FA2, so nothing changes for them.
- hd64 exclusion: with bf16 KV, hd64 decode/mixed shapes do gain (up to 1.21x, and -3–5% TPOT end to end on Llama-3.2-1B). But pure prefill/extend regress, and with fp8 KV both prefill and mixed regress (0.82–0.94x). `>= 128` is the conservative cut. Head sizes 80/96/112 were not measured.
- Tradeoffs of 128-token blocks: prefix-cache hits are block-granular, so up to 127 tokens of a shared prefix may go unreused. The last partial block of each request wastes up to 127 slots, versus 15 with 16-token blocks.
- Conflict with #65203: `get_preferred_block_size` auto-merges cleanly, but #65203 removes the `supports_fa4_hd256` kwarg from `get_flash_attn_version`, so that argument must be dropped here on rebase or the merge breaks at runtime. #65203 also deletes the `_blackwell` test helpers this PR edits (the test case needs a new home), and it edits the docs paragraph next to the one changed here.

### Stacked on #65203, FLASH_ATTN fails at engine init

#65203 removes two things this PR's new `get_preferred_block_size` branch uses: the `supports_fa4_hd256` kwarg of `get_flash_attn_version` and the `FlashAttentionBackend.head_size_v` attribute (only the DiffKV subclass still has it). With this PR rebased onto #65203 `d203078a1`, every FLASH_ATTN model with `head_size >= 128` on SM100 fails at engine init in `update_block_size_for_backend`:

```
TypeError: get_flash_attn_version() got an unexpected keyword argument 'supports_fa4_hd256'
AttributeError: type object 'FlashAttentionBackend' has no attribute 'head_size_v'
```

The second appears once the kwarg is dropped. `flash_attn.py` merges without a conflict, so this is easy to miss on rebase. The fix:

```diff
             and get_flash_attn_version(
                 head_size=head_size,
-                head_size_v=cls.head_size_v,
-                supports_fa4_hd256=True,
+                head_size_v=getattr(cls, "head_size_v", None),
             )
```

This fix is needed only because of the stack on #65203. It is [`29bc61f2d`](https://github.com/simon-veitner-redhat/vllm/commit/29bc61f2d444666d7a70942e37e7866f15fefdda) on [`pr65228-review-fixes`](https://github.com/simon-veitner-redhat/vllm/tree/pr65228-review-fixes), which holds this PR's three commits rebased onto `d203078a1`. On B300 with it and no `--block-size`, Gemma 2 9B starts on FA4 at block 128 (GSM8K, 300 questions, 0.860), and Qwen3.5-4B starts at block 128, with page 640 for mamba alignment (0.757).

The rebase also had conflicts in `docs/design/attention_backends.md` and `tests/kernels/attention/test_attention_selector.py`. #65203 deletes the `_blackwell` helpers that your selector-test edits change, so on that branch the test file takes #65203's side and your test changes need a new home.

### Block 128 brings back runtime FA4 JIT compiles

On Gemma 3 12B (FLASH_ATTN, text only, max len 32768, fresh FA4 cache), we counted FA4 compiles after `Application startup complete` under a GSM8K, essays and needles workload:

| Tree | Block | FA4 compiles after ready |
|---|---|---|
| base (vLLM `28dd9c36`) | 128 | 6 |
| #65203 | 16 | 0 |
| #65203 + this PR | 128 | 6, 4, 6 (three runs) |
| #65203 + this PR + fix below | 128 | 0, 0 (two runs) |

vLLM's jit_monitor logged `CuTeDSL JIT compilation during inference` in every run without the fix. There are two causes. `register_warmup` runs only for `gemma4` / `gemma4_unified`, so Gemma 3 and Qwen3.5 get no FA4 warmup at all. And outside full CUDA graphs, `FlashAttentionMetadataBuilder` passes `num_splits=0`, so FA4's heuristic picks a split prefill (with its `FlashPrepareScheduler` kernel) and a non-split mixed-batch variant that the warmup keys (split counts 1 and 2) do not cover.

[`7e0748697`](https://github.com/simon-veitner-redhat/vllm/commit/7e0748697cdb7132c7515853b37f1da0985a056c) on the same branch registers the FA4 warmup for every FA4 model (the keys still limit it to SM100/SM110 hd256 and SM90 hd512), adds an auto-split choice, and compiles with the real head counts, because the scheduler kernel's cache key includes them. JIT warmup takes 16.5 s on Gemma 3. Qwen3.5-4B (page 640) goes from 3 compiles after ready to 1, and Gemma 2 9B also has 1; the one left is a `FlashAttentionForwardCombine` at a split count the warmup does not cover (`log_max_splits=6`). GSM8K stays within one stderr (Gemma 3 0.877, Qwen3.5 0.772, Gemma 2 0.830), and needles are all found. The selector, FA4 and warmup tests pass (71 + 14 skipped, 64, 46). It has not been run on Hopper (Gemma 4 hd512).

### Two claims to correct (non-blocking)

- Hybrid models never get a 128-token page. Mamba page alignment wins, so Qwen3.5-4B runs FA4 at page 640 (1152 with FP8 KV) and the TMA path does not apply. The impact is small: the 100k-token prefill is within 4 % of the base.
- The hd64 and hd128 numbers were measured on FA before #213. On FA#213, `8q1s4k` (q32 kv8, bf16 KV) gains 1.45x at hd64 and 1.25x at hd128, against the claimed 1.00x and 1.04x, which reproduce exactly on fork-main FA. Excluding hd64 is still right, because hd64 prefill still regresses (0.94 to 0.96x bf16, 0.83 to 0.92x FP8).

The hd256 numbers reproduce at every shape we ran, within 1 % for the 32/8 table.
