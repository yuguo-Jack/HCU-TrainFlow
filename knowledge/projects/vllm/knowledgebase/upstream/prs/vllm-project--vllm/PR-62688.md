# [Bugfix][CPU] Keep seeded sampling working when chunked prefill splits a prompt

[Upstream PR](https://github.com/vllm-project/vllm/pull/62688) · state: open · merged: False

## Original PR description



## Overview

Fixes #62687. On the CPU backend, a seeded request whose prompt is split by chunked prefill crashed the engine with `RuntimeError: CPU Generator does not use offset`. This saves and restores those CPU generators around sampling instead of rewinding an offset they don't have.

No open issue or PR covers this (searched issues and PRs for the error string, `set_offset`, and seed + chunked prefill + CPU). Related: #49171 stops sampling unfinished prefills, but only in Model Runner V2.

## Claims

- A seeded request (`seed`, `temperature > 0`) no longer kills the CPU engine when chunked prefill splits its prompt. With `vllm serve`'s CPU default of `max_num_batched_tokens=2048`, one seeded completion over 2048 tokens was enough to take the server down.
- Its output is the same as without chunked prefill, so the seed stays reproducible however the prompt is chunked.
- Non-CPU devices keep the existing offset rewind; nothing changes for them.

## Validation

Seen outside my setup too: a user hit the same crash on the released `vllm/vllm-openai-cpu:v0.31.0` image (arm64, `/v1/chat/completions`, Qwen3-0.6B, a 2,369-token prompt with `seed=1234`), where every in-flight request failed ([report](https://github.com/vllm-project/vllm/issues/62687#issuecomment-6324951803)), and it was independently reproduced on Linux with torch 2.14 and confirmed fixed by this branch ([comment](https://github.com/vllm-project/vllm/pull/62688#issuecomment-6297545859)).

Reproducer (SmolLM2-135M, CPU backend, `max_num_batched_tokens=32` so ~60-token prompts are split; prefix caching off):

| | `main` `3ff10ddeb0` | this PR |
|---|---|---|
| seeded, chunked (`max_num_batched_tokens=32`) | `RuntimeError: CPU Generator does not use offset`, engine dead | 3/3 outputs identical to the unchunked run (budgets 16/48/64 match too) |
| seeded, unchunked (`max_num_batched_tokens=512`) | works | works, same outputs as before |

New test `tests/v1/e2e/test_cpu_seeded_chunked_prefill.py` (`facebook/opt-125m`, `cpu_model`): three seeded prompts, two of them longer than one chunk, must give the same token ids with `enable_chunked_prefill=False` and with `max_num_batched_tokens=32`.

It is added to the `CPU-Language Generation and Pooling Model Tests` step in `.buildkite/hardware_tests/cpu.yaml`, next to the existing CPU chunked-prefill test.

Server, default flags, before this PR: one seeded `/v1/completions` with a 2551-token prompt returns 500, a following plain request returns 500, and `/health` returns 503 (`CPU Generator does not use offset` in the log).

On CPU, `tests/v1/sample` and `tests/v1/worker` (without the engine-starting files) give the same result as `main`: 765 passed, and the same 98 tests fail on both (CPU-environment failures, mostly `test_rejection_sampler.py`). `tests/v1/sample/test_sampling_params_e2e.py` passes 8/8, including `test_seed`. `test_sample_passes_reordered_draft_probs_to_rejection_sampler` builds a minimal `input_batch` stand-in, which now needs the `generators` field every real input batch has.

The CUDA path isn't exercised here (no GPU access): for non-CPU generators the code path is unchanged, apart from an early `if self.input_batch.generators:` guard on the new CPU loop.

`pre-commit`: ruff check and format, mypy and the other hooks passed. `check-test-tethering` and `check-root-lazy-imports` also pass when run with Python 3.12.

## Details

**Root cause.** For a request whose current step is a non-final prompt chunk, the sampled token is discarded. `_bookkeeping_sync` then rewinds that request's seeded generator with `gen.set_offset(gen.get_offset() - 4)` so the discarded draw doesn't shift its sequence. `get_offset` / `set_offset` are only implemented by Philox-based device generators; PyTorch's CPU generator (Mersenne Twister) raises `CPU Generator does not use offset`. `CPUModelRunner` inherits `_sample` and `_bookkeeping_sync` from `GPUModelRunner`, so the first seeded request split by chunked prefill crashes the worker.

**Fix.** In `_sample`, before calling the sampler (or the rejection sampler), save `get_state()` of every CPU generator whose request is marked in `discard_request_mask`, and restore it with `set_state()` after sampling. `_bookkeeping_sync` keeps the offset rewind for the other devices. Restoring the full state is exact on CPU, where a fixed offset of 4 wouldn't describe how much state the draw consumed. Only skipping the rewind is not enough: it stops the crash, but the discarded draw then shifts the sequence, and in my runs the seeded output changed with the chunk size.

**Scope.** Model Runner V2 derives sampling randomness from a stateless hash of the seed and position (`vllm/v1/worker/gpu/sample/gumbel.py`) and has no per-request generators, so it isn't affected. The change stays in MRV1 because that is the path the CPU backend runs by default (`CPUModelRunner` subclasses `GPUModelRunner`; MRV2 requires Triton, and the CPU MRV2 runner is opt-in via `VLLM_USE_V2_MODEL_RUNNER=1`). The state copy happens only for CPU generators; on other devices the only addition is a mask scan when the batch has seeded requests.
