# [Mistral] Use get_grammar_for_chat_request in MistralParser and require mistral-common 1.13.0

[Upstream PR](https://github.com/vllm-project/vllm/pull/64169) · state: closed · merged: True

## Original PR description

## Overview

Switch `MistralParser.adjust_request` to mistral-common's single-pass grammar entry point `GrammarFactory.get_grammar_for_chat_request` (new in mistral-common 1.13.0) and require `mistral_common >= 1.13.0`.

## Claims

- vLLM no longer picks the grammar mode for Mistral tokenizers. It builds a mistral-common `ChatCompletionRequest` with `from_openai(**request.model_dump(include={messages, tools, tool_choice, parallel_tool_calls}, exclude_none=True), response_format=...)` and mistral-common renders the grammar. This replaces the manual `get_lark_from_jinja` / `get_lark_for_json_schema` routing.
- `response_format` is passed to mistral-common unchanged and follows its defaults: a `json_schema` is enforced by the grammar only when `strict` is true; otherwise any JSON object or array is accepted. `structured_outputs.json` has no `strict` field and stays enforced. See the open question for maintainers on `_mistral_response_format`.
- `check_json_nesting` and the errors for unsupported `structured_outputs` / `response_format` types stay in vLLM.
- mistral-common validation errors (pydantic `ValidationError`, e.g. an invalid JSON schema, and `InvalidRequestException`, e.g. a JSON response format with tools and `tool_choice="required"`) surface as `VLLMValidationError` (400) instead of 500. See the open question for maintainers on the `except` line.
- Bump `mistral_common` to `>= 1.13.0` in `requirements/common.txt` and the test requirements; the compiled test pins move to `1.13.0`. Its dependency floors are already met by the existing pins, so no other pin changes.

### Behaviour changes for Mistral grammar-capable tokenizers

- **Text + no tools + `tool_choice` auto/None:** no grammar is attached and `_grammar_from_parser` stays `False` (previously a text grammar was attached).
- **`tool_choice="required"` or a named tool:** on the base template the model can no longer write text before the tool call; a named choice pins the tool name. Think templates are unchanged.
- **JSON response format + tools + `tool_choice="auto"`:** the grammar allows only the JSON answer or tool calls; plain text is rejected.
- **`json_schema` without `strict: true`:** the grammar constrains output to any JSON object or array instead of the schema (previously always enforced).
- **`json_schema` with no schema:** 400 (previously fell back to `json_object`).
- **`parallel_tool_calls: null`:** treated as allowed, as in OpenAI (previously `False`).

## Details

- `tests/parser/mistral/test_tool_calls.py`: existing `adjust_request` tests now patch `get_grammar_for_chat_request` and assert the request it receives. Added grammar-content, `strict`, invalid-schema and no-grammar tests. Removed the `null_tool_choice` case of the parametrized grammar test, since that request now correctly gets no grammar.
- `tests/v1/structured_output/test_backend_xgrammar_lark.py`: pass `force_tool_names=False`, now required by `get_lark_from_jinja`. This is the only direct `get_lark_from_jinja` call left in vLLM.
- `tests/tokenizers_/test_mistral.py`: mistral-common 1.13.0 accepts all OpenAI `reasoning_effort` levels, so the test asserting `"medium"` is rejected is replaced by a check that every level is accepted.
- Removed the now-unused `_DEFAULT_JSON_SCHEMA` and the manual `tool_choice` / message / tool conversion.
- The non-grammar branch (pre-v11 tokenizers, unsupported structured outputs) is unchanged.
- Not a duplicate: no open PR touches `get_grammar_for_chat_request` or the mistral-common 1.13.0 bump.

Question for maintainers: this passes the client's `response_format` to mistral-common as-is, so the schema follows mistral-common's defaults. It is enforced by the grammar only when `json_schema.strict` is true; with `strict` unset or false the grammar accepts any JSON object or array. That matches OpenAI's meaning of `strict` and the prompt rendering in `vllm/renderers/mistral.py`, which already passes the same field.

The trade-off: `structured_outputs_from_response_format` enforces the schema for other models whatever `strict` says, and most clients do not send `strict`. Before this PR, Mistral models also always enforced it. `structured_outputs.json` stays enforced here because it has no `strict` field.

Should Mistral follow `strict` (this PR), or keep enforcing the schema regardless, like other models?
