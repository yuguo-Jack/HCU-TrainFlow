# [Build] Reuse the CMake build directory for editable installs

[Upstream PR](https://github.com/vllm-project/vllm/pull/60906) · state: open · merged: False

## Original PR description



## Overview

Make `uv pip install -e . --no-build-isolation` rebuild incrementally. Today, every editable install reconfigures CMake and recompiles all extensions, because setuptools builds editable installs in a throwaway temp directory.

Related: #54532 adds a CI smoke test for `pip install -e .`. This PR conflicts with #56409 (which moves the Marlin MoE block) and #57625 (which adds a method at the same spot in `cmake_build_ext`); I'm happy to rebase whichever lands second.

## Claims

- Re-running `uv pip install -e . --no-build-isolation` recompiles only changed files. Commands are unchanged.
- A40 (`sm_86`): a no-op rebuild takes ~25s and a one-`.cu` change 32s, instead of a ~34 min full rebuild.
- Reuse is safe across changes to the venv, torch, CUDA/ROCm toolkit, CMake generator, compiler launcher (ccache/sccache), `CMAKE_ARGS` and compiler/flag env vars, `CMAKE_PREFIX_PATH`, the CUTLASS source dir, and after `git clean -X`, interrupted kernel generation, or switching between build dirs with different arch lists.

## Validation

A40, torch 2.13.0+cu126, `TORCH_CUDA_ARCH_LIST=8.6`, `uv pip install -e . --no-build-isolation --no-deps`:

| Step | Time | Objects compiled |
|---|---|---|
| Cold build (every install on `main`) | ~34 min | 359 |
| No-op rebuild | 26s | 0 |
| Touch one `.cu` | 32s | 1 |
| After `git clean -X`, an interrupted generation, or another build dir regenerating for `8.6;9.0a` | 2–5 min | 15–30 (only Marlin regenerated) |

- After the arch switch: `test_marlin_gemm.py` (394 passed) and `test_moe.py -k marlin` (244 passed).
- macOS CPU: no-op rebuild takes 6–8s with 0 objects (vs ~90s with 16 on `main`). Also checked:
  - switching Ninja ↔ Makefiles, adding and removing ccache, and adding and removing a `CMAKE_ARGS` or `CXXFLAGS` flag;
  - `VERBOSE=1` not sticking, `python` vs `python3` (no rebuild), a corrupt marker, and a failed configure before and after an environment change.
- `run_source_generator` in a toy CMake project:
  - regenerates on an input or key change and when outputs are deleted, and skips otherwise;
  - on failure, removes the stamp so the next run regenerates;
  - editing an input reruns configure from `ninja`;
  - after a second build dir regenerates for another arch, `ninja`/`make` in the first reruns configure and regenerates (before: `missing and no known rule`).
- Marlin generator: output is byte-identical to the old script across 9 arch lists run in sequence (8.0, 8.6, 7.5,8.0, 8.0,8.9, 8.6,9.0a, 12.0a, ...), and a truncated file is rewritten.
- A toy FetchContent project confirms `CUTLASS_DIR` stays stale after switching `VLLM_CUTLASS_SRC_DIR` while `cutlass_SOURCE_DIR` follows it.
- The A40 numbers above predate the review fixes. They were measured on torch 2.13 with a since-dropped fix for its header hotfix; `main` now pins torch 2.14, where that hotfix doesn't run.
- The review fixes were re-checked on an A40, configure only (torch 2.14.0+cu130, nvcc 12.8):
  - auto-detected arch (8.6), then `8.6;9.0a`: Marlin, MoE Marlin and Machete generate once and skip on an unchanged reconfigure;
  - each regenerates on its own arch-key change, or when its output is deleted;
  - editing `generate_kernels.py` or `vllm_cutlass_library_extension.py` makes `ninja` rerun configure and regenerate only the affected generators;
  - `pip install -e . --no-build-isolation` twice: the second run reconfigures in 11s with no reset, reuses the generated sources, and resumes compiling.

## Details

**Root cause.** setuptools' PEP 660 `editable_wheel` uses a `TemporaryDirectory` for `build_temp`, which for vLLM holds the whole CMake/Ninja tree.

**Changes**

- `setup.py`: editable builds use the persistent `build/temp.<plat>-<cache_tag>` directory.
  - A `vllm_build_env.json` marker records the resolved Python, torch dir and version, resolved CUDA/ROCm toolkit, generator, compiler launcher, and the env vars CMake reads only on first configure (`CMAKE_ARGS`, `CC`, `CXXFLAGS`, `CMAKE_TOOLCHAIN_FILE`, ...).
  - When any of these change, setup.py warns which ones and reconfigures with `cmake --fresh`.
  - The marker is removed first, so if that configure fails, the next run starts fresh again.
  - `CMAKE_VERBOSE_MAKEFILE` and `NVCC_THREADS` are always set or cleared, so one-off values don't stick in the cache.
- Marlin, Marlin MoE, Machete:
  - The "already generated" hash moves from `CMakeCache.txt` to a gitignored file next to the generated sources in `csrc/`, so the two can't disagree.
  - The three copies of this logic are now one helper, `run_source_generator`.
    - It hashes the generator's input files.
    - It regenerates when any expected output (e.g. Marlin's `.cu` files, not just `kernel_selector.h`) is missing.
    - It makes those inputs and the stamp configure dependencies, so a build dir reconfigures after another one regenerates.
  - Machete's inputs now include `vllm_cutlass_library_extension.py` and CUTLASS's `cutlass_library` sources.
  - Machete and CUTLASS MLA use `cutlass_SOURCE_DIR`, not `CUTLASS_DIR`, which CUTLASS caches on first configure and so would keep the old tree after a `VLLM_CUTLASS_SRC_DIR` change.
  - The Marlin generator now writes only changed files and removes only stale ones, so an arch-list switch recompiles just the kernels that differ (e.g. 8.0 ↔ 8.0,8.9 touches `kernel_selector.h` and the `sm89` files; the 14 `sm80` kernels keep their mtime).
- `MANIFEST.in` keeps the generator stamps out of sdists, so an sdist build regenerates.
- The CPU attention dispatch header is now rewritten only when its content changes. Before, it forced 16 recompiles per install.
- Docs: the CUDA install guide and `incremental_build.md` describe the pip rebuild loop.

**Limitations**

- With build isolation, every build still recompiles everything, as it does today, and now leaves its tree in `build/`.
- `build/` now persists (several GB for CUDA). `rm -rf build/` resets it; the generated kernel sources in `csrc/` also need `git clean -fdX csrc/`.
- ROCm without `PYTORCH_ROCM_ARCH`: CMake caches the detected GPU arch on first configure (torch 2.12 doesn't override it; 2.14 does), so a build dir reused on a different GPU keeps the old arch. Set `PYTORCH_ROCM_ARCH`, as the ROCm docs do. This already applies to `setup.py develop` on `main`.
- Not tested: ROCm, and running Machete kernels (needs SM90+).

**Follow-ups**

- Replace `tools/generate_cmake_presets.py`, which has drifted from `setup.py`.

**Duplicate check.** No open PR changes the editable build dir or the generator caching.
