[Upstream PR](https://github.com/vllm-project/vllm/pull/59698) · state: open · merged: False

## Original PR description

# [Startup] Add --flashinfer-autotune-cache-only to load the FlashInfer autotune cache and skip startup autotuning

## Purpose

When every rank has a matching per-rank cache file, `flashinfer_autotune()` already loads it and skips the dummy-run sweep (#63088). When any rank's file is missing, stale or rejected, though, it silently falls back to a full tuning pass. Deployments that restart the same configuration repeatedly, or that need restart-to-restart reproducibility, have no way to say "use the cache I prepared, do not tune, and refuse to start if it is unusable".

This PR adds an opt-in `KernelConfig.flashinfer_autotune_cache_only`, exposed as `--flashinfer-autotune-cache-only`. It sits next to `--enable-flashinfer-autotune` / `--disable-flashinfer-autotune`.

- **Disabled by default.** With the flag unset, `flashinfer_autotune()` is unchanged.
- **When enabled**, every rank loads its own legacy per-rank cache file (`autotune_configs_dp{dp}_rank{r}.json`, from #57635). After a successful load, the autotune dummy runs, ReplaySSM tuning, `set_autotune_process_group`, the trailing barrier and the cache save are all skipped. `_autotune_kimi_k3_kda_qkvg` still runs, outside the autotune context (no profiling, no collectives), because it also raises the Kimi K3 KDA projection-overlap limit on the model (2 → 14 tokens), which the cache does not carry. #60085 takes the same approach.
- **Fail-closed.** It does not fall back to autotuning or heuristics. If any rank's file is missing, empty or unreadable, or if `AutoTuner.load_configs()` raises or returns `False` on any rank (FlashInfer's environment-metadata mismatch), every rank raises the same `RuntimeError` naming the failing ranks and files.
- **Consistent decision across ranks.** Each rank's error (or `None`) is collected with one `all_gather_object` over the world CPU group, following the pattern in `engram.py`. Every rank issues exactly that one collective and reaches the same decision, including under PP > 1, where a missing file on a stage-1 rank also stops stage-0 ranks. Nothing is written to the cache directory.
- **Not supported on the managed `autotune_v2` cache (#55671).** `autotune_v2(mode="replay")` serves misses with default tactics instead of failing, and deployments on that path (currently single-GPU, single-node) never write the per-rank files. Passing the flag there fails at startup with a clear message instead of silently doing something weaker.
- **Scoped to `flashinfer_autotune()`.** DeepGEMM, JIT and attention warmups, and the separate SM12x sparse-MLA decode autotune, are untouched. With FlashInfer autotune disabled, the flag has no effect and a warning is logged. The field is excluded from `KernelConfig.compute_hash()`, like `enable_flashinfer_autotune`.

### What a successful load does and does not mean

`load_configs()` returning `True` only means FlashInfer accepted the file. It does not mean every op this engine runs has an entry. Ops without an entry use FlashInfer's default tactic, and the log line says so. Per-rank files (#57635) hold each rank's rank-keyed MoE entries (`MoERunner.get_cache_key_extras`). Cache-only mode does not tune, so it does not need the cross-rank fingerprint match that the normal path uses to avoid the tuning deadlock; FlashInfer's loader validates each rank's file.

## Not a duplicate

Searched open and closed issues/PRs (titles and bodies) for "flashinfer autotune cache", "autotune cache only", `FLASHINFER_AUTOTUNE_CACHE`, `autotune_configs.json`, "skip flashinfer autotune", "flashinfer autotune load_configs", "reuse/offline/pretuned autotune" and related terms, plus flashinfer-ai/flashinfer. Related work and how this differs:

- #55671 (merged) adds the managed `autotune_v2` cache. Its replay mode has no fail-closed behaviour, which is why this PR rejects the flag on that path (see above).
- #57635 (merged; this PR builds on its per-rank files), #57579 (closed), #54618 (closed) and #57423 (issue) fix the warm-cache deadlock by making cache hits consistent across ranks. That covers cache content and consistency, not skipping the pass.
- #60085 (merged) skips the pass when the weight-cache daemon supplies a table, and falls back to tuning on a miss. That is daemon-only and fail-open. This PR covers file-based caches and is fail-closed.
- #52292 (opt out of synchronized tuning) and #48268 (`VLLM_FLASHINFER_AUTOTUNE_SKIP_OPS`, merged) control *how* tuning runs, not whether it is skipped.

## Test Plan

- success at (PP, TP) = (1, 1), (1, 2) and (2, 2): every rank loads its own file, no tuning runs, nothing is written to the cache directory, and the Kimi K3 KDA overlap-limit step runs on every rank;
- a missing or empty file on the leader (rank 0) or on a non-leader (rank 3), at PP=1×TP=4 and PP=2×TP=2: all ranks fail with the same message naming that rank, including stage-0 ranks when the failure is on stage 1;
- the loader returns `False`, or raises, on rank 0 or rank 3: all ranks fail with the same message naming that rank;

- flag off: every existing autotune test in the file runs with the new field set to `False` and still passes.

### GPU validation status

That build predates the per-rank file layout and the managed cache. No startup-time measurements are claimed.

Checks I'd ask a GPU-equipped reviewer to run (Hopper or Blackwell, current pinned FlashInfer):

1. TP=2 (+EP) MoE model: a normal boot writes per-rank files; a second boot with the flag loads them on every rank, every rank reports MoE cache hits, there are no `Tuning …` lines, and serving works.
2. TP=2, with one rank's file missing or from a different FlashInfer/GPU: all ranks fail with the same error, nothing deadlocks, and nothing autotunes.
3. PP=2: every rank's file loads, and a missing file on a stage-1 rank fails the whole engine.
4. Single GPU: the flag fails at startup with the managed-cache message. (Done on GB10, above.)
5. Flag unset: ordinary autotune and cache persistence are unchanged.
6. After cache-only startup, representative FlashInfer ops (MoE, GEMM, attention) execute, and no runtime JIT or tuning happens on first requests.

## Notes

- This started as `VLLM_FLASHINFER_AUTOTUNE_CACHE_ONLY` and moved to a `KernelConfig` field plus CLI flag, to sit next to `--enable/--disable-flashinfer-autotune`.
- Supporting the managed cache would need a fail-closed replay mode in FlashInfer (or a way to detect replay misses). I've left that out until one exists.
- Known limitation: a rank that dies hard, for example from a segfault inside `load_configs`, can't take part in the gather, and the other ranks then wait for the process-group timeout. The engine's existing worker-death handling applies, as it does for any collective.
- Follow-up interest: @billdenney has a branch that adds record-on-first-start and record-time consistency checks on top of this (see their comment). I'd prefer to land this minimal fail-closed load first and take those as a follow-up.

AI assistance was used to investigate, draft and test this change. I reviewed every changed line and ran the tests above.

We have been measuring restart-to-restart reproducibility of batch-invariant serving on two NVIDIA GB10 servers (Qwen3-30B-A3B and gpt-oss-20b in bf16, `VLLM_BATCH_INVARIANT=1`, `TRITON_ATTN`, CUDA graphs). Within one process the outputs are bitwise identical under every batch composition we tried; across a plain restart with identical settings they are not: the same 15 greedy requests gave 0 % bitwise-identical logprobs and 47 % to 93 % identical parsed answers, and six fresh starts of one host fell into three distinct states. A fail-closed load of the FlashInfer autotune cache, as this PR does, is the mechanism we want, so we would rather build on it than open a parallel PR.

Three things we needed on top, which we have working on a branch and would offer as a follow-up once this merges, or fold in here if you prefer:

1. Record on the first start: when no rank has a cache file, tune once and save, so the first start under the setting produces the record instead of an error. With this a deployment needs one mode rather than "tune once, then flip the variable".
2. Check the record at record time: gather the per-rank fingerprints after the save and fail that start if they differ, so an inconsistent record is caught when it is written rather than at every later start.
3. Save an empty record when nothing was tuned, so a model with no tunable FlashInfer op does not re-record at every start.

Our version is a `KernelConfig` field with a derived flag (`--flashinfer-autotune-cache-mode replay`) rather than an environment variable, and it logs one line on load and one on save so a deployment can record which happened; we have no strong view on the interface and will follow whatever lands here. Happy to share the branch and the GB10 measurements.

1. **FlashInfer internals.** The store check reads `tuner._managed_cache` and `store.entries_dir`, and re-derives `ManagedAutotuneCache._entry_path`'s naming (`sha256(key)[:24]`). The miss counter replaces `tuner.search_cache` on the instance. Any of these can break silently on a FlashInfer bump. A public replay API in FlashInfer, one that raises on a miss or returns a miss count, would let vLLM rely on it. It may be worth raising with flashinfer-ai in parallel.
2. **What the store check proves.** It passes on any well-formed entry. The store is keyed by environment, not by vLLM config, so another model's entries under the same root would satisfy it.
3. **Prepared but empty.** As your run showed, "tuned and found nothing" and "never tuned" look the same. Your manifest-marker idea fits naturally with the empty-record piece for the per-rank files.
4. **Other tuning contexts.** `tune_mode=False` covers the dummy runs, but `autotune_hisparse_flashinfer_attention` and `replayssm_autotune_warmup` also run inside the replay context. I haven't confirmed whether either opens its own tuning context, so they're worth checking.
5. **Log or fail on a miss.** Logging is a reasonable default, and it matches this PR, which doesn't check completeness either. For reproducibility, an opt-in "fail on miss" would make the guarantee explicit.
