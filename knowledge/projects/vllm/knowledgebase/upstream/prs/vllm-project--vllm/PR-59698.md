# [Startup] Add VLLM_FLASHINFER_AUTOTUNE_CACHE_ONLY to load the FlashInfer autotune cache and skip startup autotuning

[Upstream PR](https://github.com/vllm-project/vllm/pull/59698) · state: open · merged: False

## Original PR description

## Purpose

`flashinfer_autotune()` runs the FlashInfer autotuning pass on every engine start, even when a persisted cache for the same configuration exists: the cache is loaded, then the tuning dummy runs execute anyway. Deployments that restart the same configuration repeatedly have no way to say "use the cache I prepared and do not tune".

This PR adds an opt-in `VLLM_FLASHINFER_AUTOTUNE_CACHE_ONLY=1`:

- **Disabled by default.** With the variable unset, `flashinfer_autotune()` is unchanged.
- **When enabled**, each tuning group's leader reads its existing cache file (same path as today, including the per-PP-stage file), broadcasts it within the tuning group, and every rank loads it. After a successful load, the autotune dummy runs, ReplaySSM/Kimi tuning, the BF16 pass, `set_autotune_process_group`, the trailing barrier and the cache save are all skipped.
- **Fail-closed.** It does not fall back to autotuning or heuristics. If the file is missing, empty or unreadable, or if `AutoTuner.load_configs()` raises or returns `False` (FlashInfer's environment-metadata mismatch) on any rank, every rank raises the same `RuntimeError` naming the failing ranks.
- **Consistent decision across ranks.** Each rank's error (or `None`) is collected with one `all_gather_object` over the world CPU group, following the pattern in `engram.py`. Every rank therefore issues the same collectives (one tuning-group broadcast, one world gather) and reaches the same decision, including under PP > 1, where a missing stage-1 cache also stops stage 0. The cache is loaded from a per-rank temporary file, so nothing is written to the (possibly read-only) cache directory.
- **Scoped to `flashinfer_autotune()`.** DeepGEMM, JIT and attention warmups are untouched. The separate SM12x sparse-MLA decode autotune (`flashinfer_sparse_mla_decode_autotune_warmup`) is also unaffected. If `enable_flashinfer_autotune=False`, the variable has no effect and a warning is logged.
- Added to the `compile_factors()` ignore list next to `VLLM_FLASHINFER_AUTOTUNE_CACHE_DIR`, so toggling it does not invalidate the torch.compile cache. It does not enter `vllm_config.compute_hash()`, so the autotune cache path is the same with and without it.

### What a successful load does and does not mean

`load_configs()` returning `True` only means FlashInfer accepted the file. It does not mean every op this engine runs has an entry. Ops without an entry use FlashInfer's default tactic, and the log line says so. In particular, FlashInfer keys some MoE entries by `tp_rank`/`ep_rank` (`MoERunner.get_cache_key_extras`), so a cache saved by rank 0 alone (today's behaviour) has no MoE entries for other ranks; see #57423 / #57635. In cache-only mode those ranks do not deadlock, because nothing is tuned, but they run those MoE ops with the default tactic. Making the persisted cache cover all ranks is a separate problem (#57635, #55671) and is intentionally not part of this PR.

## Not a duplicate

Searched open and closed issues/PRs (titles and bodies) for "flashinfer autotune cache", "autotune cache only", `FLASHINFER_AUTOTUNE_CACHE`, `autotune_configs.json`, "skip flashinfer autotune", "flashinfer autotune load_configs", "reuse/offline/pretuned autotune" and related terms, plus flashinfer-ai/flashinfer. Related work and how this differs:

- #55671 (draft) migrates warmup to `autotune_v2` managed per-entry caches. It changes cache ownership and persistence and "does not claim … zero warm-start profiling". It has no opt-in skip and no fail-closed mode. The two touch the same function, so one will need a rebase onto the other. This PR is a small early-return and should be easy to carry.
- #57635 / #57579 (closed) / #54618 (closed) / #57423 (issue) fix the warm-cache deadlock by making per-rank cache hits consistent. That is cache content and consistency, not skipping the pass.
- #59435 skips the pass when the weight-cache daemon (`--load-format ipc_cache`) supplies a table, and falls back to tuning on a miss. That is daemon-only and fail-open. This PR covers file-based caches and is fail-closed.
- #52292 (opt out of synchronized tuning) and #48268 (`VLLM_FLASHINFER_AUTOTUNE_SKIP_OPS`, merged) control *how* tuning runs, not whether it is skipped.

## Test Plan

CPU-only tests in `tests/model_executor/test_flashinfer_autotune_warmup.py`. They use a fake `AutoTuner` and fake process groups whose collectives rendezvous across one thread per rank, so a rank that skips or adds a collective shows up as a barrier timeout instead of a hang:

- success, TP=1 and TP=2: every rank loads the leader's bytes, no tuning runs, nothing is written to the cache directory;
- missing / empty / unreadable (directory) cache: all ranks fail with the same message naming rank 0, and no rank calls the loader;
- loader returns `False`, or raises, on the leader (rank 0) or on a non-leader (rank 3): all ranks fail with the same message naming that rank;
- PP=2 × TP=2: each stage loads its own `_tp_<ranks>` file through its TP-group broadcast; one world gather; a missing stage-1 cache fails stage-0 ranks too;
- variable set to `0`: the existing autotune path (synchronized tuning and rank-0 save) still runs.

Commands (macOS arm64, Python 3.12, torch 2.13.0 CPU, source tree on `PYTHONPATH`, no vLLM C extensions or FlashInfer installed):

```bash
PYTHONPATH=. PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 .venv/bin/python -m pytest --noconftest \
  tests/model_executor/test_flashinfer_autotune_warmup.py -q
PYTHONPATH=. PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 .venv/bin/python -m pytest --noconftest \
  tests/test_envs.py -q
pre-commit run --files docs/configuration/optimization.md vllm/envs.py \
  vllm/model_executor/warmup/flashinfer_autotune_cache.py \
  vllm/model_executor/warmup/kernel_warmup.py \
  tests/model_executor/test_flashinfer_autotune_warmup.py
pre-commit run mypy-3.12 --hook-stage manual --files <same files>
```

### GPU validation status

**No GPU validation has been done on this upstream implementation.** I don't currently have access to a GPU machine.

The only GPU evidence is historical and comes from a different, locally patched build: a two-rank MiMo-V2.6-Flash deployment (TP=2, EP, FP8, `flashinfer_cutlass` MoE, DFlash speculative decoding) on vLLM `0.29.1rc1.dev449` with FlashInfer `0.6.18.post1` on SM 9.0a. It ran with a local cache-only patch that this PR's design is based on, but not identical to. Both ranks logged `Loaded 84 configs` from the same cache file, the cache-only message, and `Config cache hit … source=config file` for the MoE GEMMs, and the engine served normally afterwards. That deployment also used a separately prepared cache containing entries for every rank, which this PR does not include. No startup-time measurements are claimed.

Checks I'd ask a GPU-equipped reviewer to run (Hopper or Blackwell, current pinned FlashInfer):

1. Single rank, cache hit: startup logs the cache-only message, no `Tuning …` lines, and serving works.
2. Single rank, missing cache and a cache from a different FlashInfer/GPU: startup fails with the cache-only `RuntimeError`, without autotuning.
3. TP=2 (+EP) MoE model, cache hit: all ranks load the cache and startup completes without a collective hang. Check which ranks report MoE cache hits (see the rank-keying note above).
4. TP=2, missing or invalid cache on one rank's node: all ranks fail with the same error and nothing deadlocks.
5. PP=2: per-stage caches load, and a missing stage cache fails the whole engine.
6. Variable unset: ordinary autotune and cache persistence are unchanged.
7. After cache-only startup, representative FlashInfer ops (MoE, GEMM, attention) execute, and no runtime JIT or tuning happens on first requests.

## Notes

- Env var versus `KernelConfig` field: I followed the neighbouring `VLLM_FLASHINFER_AUTOTUNE_CACHE_DIR` / `VLLM_FLASHINFER_AUTOTUNE_SKIP_OPS` env vars. Happy to switch to something like `--kernel-config.flashinfer_autotune=cache_only` if maintainers prefer.
- Known limitation: a rank that dies hard, for example from a segfault inside `load_configs`, can't take part in the gather, and the other ranks then wait for the process-group timeout. The engine's existing worker-death handling applies, as it does for any collective.
