# [ASR] Add Voice Activity Detection (VAD)

[Upstream PR](https://github.com/vllm-project/vllm/pull/46126) · state: open · merged: False

## Original PR description

Addresses: https://github.com/vllm-project/vllm/issues/25750

Current Whisper/ASR models served with vLLM can hallucinate when processing long segments of background noise. While users can build custom preprocessing pipelines around vLLM, providing an integrated Voice Activity Detection (VAD) option significantly improves the out-of-the-box ASR experience.

This PR integrates [silero-vad](https://github.com/snakers4/silero-vad) to enable VAD-based preprocessing for ASR requests. The default parameters are adopted from [`faster-whisper`](https://github.com/SYSTRAN/faster-whisper/blob/ed9a06cd89a93e47838f564998a6c09b655d7f43/faster_whisper/vad.py#L41-L48), while still allowing users to tune or override them based on their workload and quality requirements.

VAD is applied on a per-request basis and is disabled unless requested by the user. As a result, existing deployments and workloads that do not use VAD are unaffected.

### TL;DR

whisper-large-v3-turbo on 1x H100, concurrency 128, VAD-enabled requests vs no VAD:

* **Long audio (15-22 min):** RTFx overhead of ~8% with `VLLM_MAX_VAD_WORKERS=4`.
* **Short audio (<30 s):** no measurable RTFx overhead (+2.7%, 95% CI [-1.2, +6.5]).
* **WER:** VAD can improve WER on Whisper (default VAD hyperparam):
  * whisper-large-v3, long audio (`ArtificialAnalysis/Earnings22-Cleaned-AA`): 9.44 -> 8.19
  * whisper-large-v3-turbo, long audio (`ArtificialAnalysis/Earnings22-Cleaned-AA`): 10.51 -> 9.61
  * whisper-large-v3-turbo, short audio (`D4nt3/esb-datasets-earnings22-validation-tiny-filtered`): 13.69 -> 13.66 (neutral)

### Keeping VAD overhead low

The stock silero-vad model is a streaming model: it runs one tiny ONNX call per 32 ms frame from a Python loop (~37k calls for a 20 min file). That loop holds the GIL, so VAD running on a thread pool inside the API server starves the event loop and does not scale with more threads. In the first revision of this PR, this dropped RTFx at concurrency 128 from 1740 to 312.

To fix this, this PR:

* Uses the offline sequence ONNX model added to silero-vad in [snakers4/silero-vad#795](https://github.com/snakers4/silero-vad/pull/795) (released in silero-vad 6.2.3). It runs the same computation as one ONNX call per block of up to 512 frames (~16 s), so almost all of the VAD time is spent in GIL-releasing ONNX Runtime kernels. Its speech timestamps are bit-exact with the stock streaming path.
* Adds an optional dedicated thread pool for VAD-enabled requests, so VAD can scale independently of audio decoding. Its size is set by `VLLM_MAX_VAD_WORKERS`. The default `0` keeps VAD on the existing audio preprocessing pool, so no extra threads are used unless configured. Requests without VAD keep the existing path. For high-concurrency long-audio workloads with VAD enabled, `VLLM_MAX_VAD_WORKERS=4` gives the best throughput (see results below).
* Returns an empty transcript when VAD detects no speech in the audio, instead of transcribing the original audio.

### Chunking with VAD

For models that support chunking (e.g. Whisper), VAD first finds the speech segments. Segments longer than `max_audio_clip_s` (30 s for Whisper) are then split with the existing RMS-based split, while shorter segments are kept as they are. Finally, consecutive pieces are greedily packed into chunks of up to `max_audio_clip_s`, with the non-speech between them removed, similar to `faster-whisper`. Packing keeps the number of engine requests per audio bounded by the amount of speech, whatever VAD parameters the client sends, instead of one engine request per VAD segment. The `vad_config.*` fields are also range-checked.

### Not supported yet: VAD with timestamps

Because VAD removes non-speech audio, segment timestamps from the model refer to positions in the trimmed audio, not the original. Supporting `verbose_json` with VAD needs a map from each packed chunk back to the original audio, which is left to a follow-up PR ([ekagra-ranjan/vllm#7](https://github.com/ekagra-ranjan/vllm/pull/7)) to keep this one small. Until then, requests with VAD enabled and `response_format=verbose_json` return a 400 error. Requests without VAD are unchanged.

### Results

whisper-large-v3-turbo on 1x H100, `--max-concurrency 128`. RTFx is the mean ± std dev of 5 runs after 1 warmup run. The 95% CI is for the RTFx difference vs no VAD, expressed as a percentage of no VAD.

* Long audio: `ArtificialAnalysis/Earnings22-Cleaned-AA` (6 files of 15-22 min), 128 prompts
* Short audio: `D4nt3/esb-datasets-earnings22-validation-tiny-filtered` (511 clips of 0.2-26 s), 511 prompts

| Audio | Config | No VAD RTFx | VAD RTFx | VAD vs no VAD (95% CI) |
|---|---|---|---|---|
| Long | `VLLM_MAX_VAD_WORKERS=4` | 1792 ± 82 | 1648 ± 26 | -8.0% [-13.6, -2.5] |
| Short | `VLLM_MAX_VAD_WORKERS=1` | 331 ± 10 | 340 ± 3 | +2.7% [-1.2, +6.5] |

For long audio, the VAD overhead drops from ~82% (1740 -> 312 in the first revision of this PR) to ~8% (1792 -> 1648) with `VLLM_MAX_VAD_WORKERS=4`, a ~5.3x RTFx improvement for VAD-enabled requests. For short audio, there is no measurable overhead.

A rerun after removing the VAD timestamp mapping from this PR gave the same picture: long -9.2% [-23.2, +4.8] (1684 ± 188 -> 1529 ± 115, a noisier run) and short +0.8% [-2.7, +4.3] (347 ± 4 -> 350 ± 10).

Each short-audio run takes ~10 s, so RTFx varies by up to ~6% between server restarts, more than the VAD effect. The short-audio no-VAD and VAD runs above were therefore run against the same server.

### WER impact

WER is computed with the Whisper `EnglishTextNormalizer` and `jiwer`, as in `test_transcription_api_correctness.py`.

| Model | Dataset | No VAD | VAD |
|---|---|---|---|
| whisper-large-v3 | Long audio (`test_long_audio_wer_correctness`) | 9.44 | 8.19 |
| whisper-large-v3-turbo | Long audio (Earnings22-Cleaned-AA, 6 files) | 10.51 | 9.61 |
| whisper-large-v3-turbo | Short audio (earnings22-validation-tiny-filtered, 511 clips) | 13.69 | 13.66 |

VAD improves long-audio WER by ~1 point by filtering non-speech regions before transcription, and is neutral on short audio, where clips contain little non-speech. The number of VAD workers does not affect the transcripts.

### Guide for reviewers

Most of the changes in this PR live in just two files (each ~150 LOC). `vllm/multimodal/audio.py` decides *what* audio gets sent to the model. `vllm/entrypoints/speech_to_text/base/serving.py` decides *where and when* that work runs, and what the server returns. VAD is opt-in per request through `vad_config`. When it is off, requests take the same path as before.

**`vllm/multimodal/audio.py`** adds the VAD itself and the logic that combines it with the existing RMS Split chunking. Before splitting long audio into model-sized chunks, we run silero-vad to find where speech is and drop the silence and noise around it. Only speech segments that are still longer than the model's max clip length go through the existing energy-based (RMS) splitter. We use silero's offline ONNX sequence model (https://github.com/snakers4/silero-vad/pull/795), which processes whole blocks of audio per call instead of one 32 ms frame at a time. This keeps VAD from holding the GIL under concurrent load. Each worker thread gets its own model instance, so requests run VAD in parallel without contending for a shared session. If no speech is found, the splitter returns no chunks.

**`vllm/entrypoints/speech_to_text/base/serving.py`** connects that logic to the transcription and translation endpoints. The old decode-and-chunk step is split into two parts: decoding and chunking. VAD-enabled requests can then run their chunking on a separate thread pool (`VLLM_MAX_VAD_WORKERS`), so VAD scales independently of audio decoding. The default is 0, which keeps everything on the existing preprocess pool, so deployments that don't use VAD or only serve short audio get no extra threads. The file also handles audio that contains no speech: instead of sending silence to the model (where Whisper tends to hallucinate), the server skips the engine entirely and returns an empty transcript in whatever response format the client asked for, including streaming.

<details>
<summary>Why this was flagged</summary>

Timestamps after the first gap are then relative to the trimmed audio, not the file. On the base branch, chunks were contiguous slices of the full waveform, so the summed offsets matched the uploaded audio. No code turns the VAD `start` values back into offsets.

**Verification:** Trigger: a transcription request with VAD enabled and response_format=verbose_json.
