# [Attention] FlashMLA sparse: stage fp8 mixed-batch q/out in the workspace

[Upstream PR](https://github.com/vllm-project/vllm/pull/60220) · state: open · merged: False

## Original PR description



## Overview

The FlashMLA sparse `fp8_ds_mla` mixed-batch path now writes the head-padded query and the kernel output into the workspace buffers that `FlashMLASparseImpl` already reserves for `max_num_batched_tokens`, so it no longer allocates them on every call. This removes about 4.25 GiB of per-call allocation at 32K tokens per step. That allocation isn't counted by the startup memory profile, so it can cause runtime OOMs.

Related: #59305, #57878. Complements vllm-project/FlashMLA#29, which removes the kernel-internal fp32 split-KV `o_accum` buffer (the other 8 GiB at T=32K). This PR only covers the wrapper side.

## Claims

- On the fp8 mixed-batch path, the padded q (`T x 64 x 576` bf16) and the output (`T x 64 x 512` bf16) are written into the reserved workspace, and the output buffer is passed to the kernel via `out=`. At T=32768 this saves 4.25 GiB per call, measured. The workspace was already reserved, so KV cache capacity does not change.
- Outputs and LSE are bit-identical to the allocating path.
- GLM-5.3-Flash FP8 on 8xH100 (TP8, `max_num_batched_tokens=32768`, `gpu_memory_utilization=0.85`) previously hit a runtime OOM in `flash_mla_with_kvcache` during warmup. With this change it serves the same workload without errors, and GSM8K accuracy matches.

| T | before (allocating path) | after (workspace path) | saved | outputs equal |
|---|---|---|---|---|
| 1024 | 0.384 GiB | 0.251 GiB | 0.133 GiB | yes |
| 8192 | 3.068 GiB | 2.006 GiB | 1.063 GiB | yes |

| 32768 | 12.273 GiB | 8.023 GiB | 4.250 GiB | yes |

The remaining ~8 GiB at T=32768 is the kernel's `o_accum`, which is addressed by vllm-project/FlashMLA#29.

**End-to-end, previously crashing config.** GLM-5.3-Flash FP8, 8xH100, `--tensor-parallel-size 8 --max-num-seqs 256 --attention-backend FLASHMLA_SPARSE --kv-cache-dtype fp8_ds_mla --max-num-batched-tokens 32768 --gpu-memory-utilization 0.85 --max-model-len 131072`.
- Before this change: during the warmup with 8K input and concurrency 256, the server failed with `torch.OutOfMemoryError` (tried to allocate 8 GiB with 5.29 GiB free), and 255 of 256 requests failed.
- After this change: warmups at 8K/c256 and 64K/c64 completed with no errors, and there are no OOM lines in the server log. Peak `nvidia-smi` memory.used was 80923 / 81559 MiB. This is tight because `o_accum` is still allocated per call until FlashMLA#29 lands.

## Details

**Root cause.** For `fp8_ds_mla` with fewer than `MIN_HEADS_FOR_BF16_PREFILL` heads per rank (`fp8_use_mixed_batch`), every step makes a single `flash_mla_with_kvcache` call with `s_q = num_tokens`. The wrapper pads q to 64 heads with `new_zeros`, and the kernel allocates `out`, `lse` and `o_accum`, all O(T * 64). The profile run skips attention, so none of this is counted when the KV cache is sized. At large `max_num_batched_tokens`, a full step therefore OOMs after startup.

**Fix.** `__init__` already reserves `(max_tokens, padded_heads, 576)` and `(max_tokens, padded_heads, 512)` bf16 workspace slots for the BF16 prefill path, which is not used in mixed-batch mode. `_fp8_flash_mla_kernel(use_workspace=True)` takes flat views of those slots sized for the FP8 decode padding (the reserved head padding is at least as wide). It zeroes only the padding heads and passes `out=` to the kernel.
- Only the mixed-batch caller turns this on. Pure-decode, HiSparse and separate prefill/decode callers keep the allocating path, because their T is small.
- The returned output aliases the workspace. It is consumed by the `v_up` projection or the DCP merge before any other workspace user runs. The separate prefill/decode path already returns workspace-backed output the same way.
- The q input comes from workspace slot 0, the q-concat buffer, so it doesn't overlap the padded-q slot.
- No new CPU/GPU synchronization: the added checks are host-side shape asserts.
- `lse` is still allocated by the kernel (T x 64 x 4 B = 8 MiB at 32K).

**Limitations.** The kernel-internal `o_accum` (2 x T x 64 x 512 x 4 B = 8 GiB at T=32K on SM90) is still allocated per call and isn't counted by the profile run. That is fixed in vllm-project/FlashMLA#29. This PR removes the wrapper-side share.

#59319 (ours, open) stops reserving the bf16 prefill workspace on the fp8 mixed-batch path. Its first revision skipped the whole block, including the three `max_num_batched_tokens` buffers this PR stages q and out in. The two PRs merge without a conflict, but together `workspace_specs` on that path holds only `q_concat`, and the `get_simultaneous` unpack fails on the first forward with `ValueError: not enough values to unpack (expected at least 3, got 1)`.

The current revision of #59319 skips only the `5 * max_model_len` buffer (plus the PCP+DCP gather buffer) and keeps the three `max_num_batched_tokens` buffers, so either merge order works. On one H200 (nightly `af7f9488c` with both files swapped in), `test_sparse_backend_decode_correctness` for FlashMLA + `fp8_ds_mla` fails in all 14 TP=8 cases with the first revision plus this PR, and passes with the current one: 72 passed, including your two staging tests and the #59319 unit tests.

`test_flashmla_fp8_mixed_batch_stages_in_workspace` builds `workspace_specs` by hand, so it won't catch a change in what `__init__` reserves. The TP=8 cases #59319 adds go through the real `__init__` and do.
