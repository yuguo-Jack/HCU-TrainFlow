# [Perf][ROCm][Kernel] Fuse Qwen3.8 MTP verify conv, GDN, and RMSNorm

[Upstream PR](https://github.com/vllm-project/vllm/pull/61675) · state: closed · merged: False

## Original PR description

## Overview

Opt-in ROCm kernel that fuses Qwen GDN MTP verify: the width-4 causal convolution over 1–4 verify tokens, the gated-delta recurrence, and gated RMSNorm. Enable with `VLLM_ROCM_QWEN_MTP_GDN=1` (default off). Prefill and ordinary decode stay on the stock path.

No open PR implements this fusion. Related work: #61855 ports the fused GDN MTP recurrence + norm to Triton without the conv; #62381 makes the same `forward_hip` → `forward_cuda` routing choice under speculative decoding; the Qwen3.8 mono-decode drafts (#60833, #61325) are a different design.

## Claims

- On MTP verify steps, two Triton launches replace `causal_conv1d_update`, `fused_sigmoid_gating_delta_rule_update`, and `RMSNormGated`. Uniform and mixed per-sequence widths both take the same two launches, with no host sync, so mixed batches are graph-capturable.
- On Qwen3.8-27B (gfx950, bf16, TP=1) the fused op is 1.6–2.3x faster than the stock chain at batch 1, 1.6–2.1x at batch 8, and 1.15–1.45x at batch 32.
- End-to-end fixed-length decode throughput with MTP-3 improves by 3.2–7.2% at batches 1, 8, and 32, on two GPUs with the run order swapped.
- GSM8K (1319 examples, MTP-3) matches the baseline within stderr at batches 1, 8, and 32.

## Details

**Dispatch.** The verify step is dispatched from `qwen_gdn_attention_core_rocm_mtp`. It is a custom op, registered as a piecewise-graph splitting op and marked eager during CUDA-graph capture; a Python branch in the compiled forward would be specialized away on a non-spec trace. When the flag is off, or the platform is not ROCm, `forward_cuda` and `forward_hip` are unchanged. When it is on, `forward_hip` uses `forward_cuda`, so the fused path is reachable even if AITER is present.

**Launches.** The first launch runs conv + gated delta, with grid `(V tiles, HV, n_seq)`. The second shifts the conv state and applies gated RMSNorm, writing in place into `core_attn_out`. The caller then only runs `out_proj`.

Mixed widths read each sequence's rows from `spec_query_start_loc` on device, so there is no `torch.cat`, no host read of lengths or slots, and no extra copy. The launcher takes the full `spec_state_indices_tensor` row because the incoming state is read at column `num_accepted_tokens - 1`, which can exceed the step width. Padded rows outside every sequence stay zero. Stock steps still run the core, then `self.norm` once on the real tokens. An MTP step the kernel cannot run raises `ValueError` instead of silently falling back.

**Supported configurations.**
- Heads and head dims come from the tensors and need `HV % H == 0`.
- bf16 or fp16 activations, fp32 SSM state.
- TP=1, conv kernel width 4, 1–4 tokens per sequence.
- SiLU/swish conv activation; silu/swish/sigmoid norm gate.
- Block ids use int64 addressing.

Model-config checks run once per layer and are cached. Per step, the layer only asserts the spec metadata, like `_forward_core`. Shape, dtype, and stride checks live in the launcher and read host-side tensor metadata only.

No `docs/` change. The flag is default-off, and its comment in `vllm/envs.py` is included by `docs/configuration/env_vars.md`.
