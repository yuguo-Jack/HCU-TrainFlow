# [Bugfix][Frontend] Apply batch tool_choice rules to streamed tool calls

[Upstream PR](https://github.com/vllm-project/vllm/pull/63345) · state: closed · merged: True

## Original PR description

## Overview

Streaming chat now drops tool calls in the same cases batch does. Fixes #63346. Follow-up to #63148 which listed this as not covered.

#42752 fixed #42747 for `"none"` but only inside `DelegatingParser`. Two cases still slip through on main:

- gpt-oss with `"none"`: `HarmonyParser` isn't a `DelegatingParser` so the guard never runs.
- `null` with any parser: nothing gates it, so streaming keeps tool calls while batch drops them.

This PR moves the rule into one place that batch and streaming both call, so it no longer depends on each parser.

## Claims

- With `stream: true`, `/v1/chat/completions` now follows the same `tool_choice` rules as batch. gpt-oss (Harmony) with `"none"` and any tool parser with `null` stop returning tool calls. This PR doesn't decide what `null` should mean, it only makes streaming match batch.
- Streaming `/v1/chat/completions/derender` gets the same fix because it uses the same `ChatStreamProcessor`.
- `finish_reason` is `stop` in those cases, not `tool_calls`.
- No change for `"auto"`, `"required"` or named tools. Anthropic and Cohere turn `null` into `"auto"` when tools are set, so they're not affected.

## Details

`ChatStreamProcessor` passed `parse_delta()` output straight through and relied on the parser to check `tool_choice`. Not every parser does. `HarmonyParser` ignores `"none"` and the base `Parser` treats `null` like `"auto"`. Non-streaming doesn't have this problem because `assemble_chat_message_fields()` applies the rule itself.

The rule now lives in `keeps_tool_calls()` and both paths call it. `ChatStreamProcessor` takes `enable_auto_tools` and `parser_cls` as required keyword arguments, so a new caller can't skip them by accident.

When tool calls are dropped, the stream sends nothing for them. That matches batch which returns `content: ""`. Whether `"none"` should return tool-call-shaped text as content is #55080 and this PR doesn't change that. If a delta is empty after stripping, the processor returns `None`. Both callers already skip sending a `None` delta, the same way they handle hidden reasoning.

## Related PRs

- #42752 (merged): gates `"none"` in `DelegatingParser` only. This PR covers what that misses.
- #42868: targets the old `serving.py` streaming code which has since moved to `ChatStreamProcessor`. Obsolete and conflicting.
- #55089 / #55080: whether tool-call-shaped text should come back as content when tools are off. Out of scope here.
- #54321: makes an explicit `null` behave like an omitted field, so `"auto"` when tools are set. Complementary to this PR. If it lands, both paths follow it.
