# [Benchmark][Attention] Support int8_per_token_head KV cache in attention_benchmarks

[Upstream PR](https://github.com/vllm-project/vllm/pull/62112) · state: open · merged: False

## Original PR description

## Overview

`benchmarks/attention_benchmarks` cannot currently time attention on an `int8_per_token_head` KV cache. `--kv-cache-dtype` accepts only `auto` and `fp8`. Also, `_create_kv_cache` builds the spec without `kv_quant_mode`, so `TritonAttentionBackend.customize_spec` adds no inline scales. Also, the runner never writes the KV cache, so every kernel is timed over an all-zero cache. This PR allocates the cache the way the attention layer does, writes it before timing, gives each layer its own impl, rejects the dtype on backends that cannot read it, and adds a config.

AI assistance was used: an AI coding agent wrote the code and tests under my direction, drafted this description, and automated the test and benchmark runs; I chose the approach and reviewed every changed line and the results.

The kernel numbers in #62113 (16-byte-aligned per-token-head KV slots) were measured with this tool change and can be reproduced with it.

## Claims

- `--kv-cache-dtype int8_per_token_head` allocates the packed `[K | k_scale | V | v_scale]` cache through the backend's `customize_spec`, so `TRITON_ATTN` runs on the layout it serves.
- Each layer gets its own impl, as in a model. `TritonAttentionImpl` binds its scale views to the first cache it sees, so with a shared impl every layer read layer 0's scales.
- Before timing, the runner writes random K/V for every cached token through `impl.do_kv_cache_update`, the path the attention layer uses. Until now it called only `forward`, which for `TRITON_ATTN`, `FLASH_ATTN` and `FLASHINFER` does not write the cache (`forward_includes_kv_cache_update = False`), so all of them were timed over zeros. Backends whose `forward` writes the cache are left as they were.
- New `configs/int8_per_token_head.yaml` (decode, 4-token verify, prefill; head_dim 128 and 256).
- `--kv-cache-dtype int8_per_token_head` on a backend whose `supports_kv_cache_dtype` rejects it (only `TRITON_ATTN` lists it) or on any MLA backend raises an error instead of timing a different cache.
- `auto` and `fp8` allocations are unchanged.

## Validation

**Why it is needed.** On main, `int8_per_token_head` is slower than the bf16 cache in all 12 cells we measured, at 1.48–2.29× the bf16 time, although it reads about half the bytes. This tool change is what made that measurable. Per layer, median (IQR) of 5 processes, cache populated by this PR:

| Hq/Hkv/D | cell | bf16 (`auto`) | int8_per_token_head | int8 / bf16 |
|---|---|---|---|---|
| 12/2/256 | q1s8k | 48.8 (0.0) µs | 103.9 (0.1) µs | 2.13 |
| | q1s128k | 667.5 (1.0) µs | 1424.4 (0.6) µs | 2.13 |
| | q8s128k | 1155.0 (3.4) µs | 1772.7 (2.3) µs | 1.53 |
| | q8ks128k | 855.7 (0.9) ms | 1265.5 (0.7) ms | 1.48 |
| 32/8/128 | q1s8k | 58.4 (0.2) µs | 87.2 (1.1) µs | 1.49 |
| | q1s128k | 814.4 (1.2) µs | 1364.4 (1.0) µs | 1.68 |
| | q8s128k | 1240.8 (3.6) µs | 2023.9 (3.8) µs | 1.63 |
| | q8ks128k | 903.2 (1.7) ms | 1346.0 (1.6) ms | 1.49 |

*RTX 3080 (sm_86), 220 W cap, image `8c1434bf…5035e`, vLLM `g49cb2bbf7` (attention files = `fa75d3456d`), Triton 3.8.0, this branch's `benchmarks/` mounted read-only.*

Equivalent command (5 processes per arm; each ran both head configs and both dtypes through the tool's `run_benchmark`):

```bash
cd benchmarks/attention_benchmarks
python benchmark.py --backends TRITON_ATTN --kv-cache-dtype {auto,int8_per_token_head} \
  --num-layers 8 --block-size 16 --head-dim {256,128} --num-q-heads {12,32} --num-kv-heads {2,8} \
  --batch-specs q1s8k q1s32k q1s128k q8s128k q8ks32k q8ks128k
```

**Cache fill on GPU.** After the fill, 99.0 % (12/2/256) and 99.1 % (32/8/128) of the int8 K/V bytes are non-zero (the rest are quantized zeros), the scales are real (0.013–0.046, none equal to the zero-cache value 1.0), the bf16 cache is 100 % non-zero, and the attention output is finite and non-zero in every probed case. Without the fill, the same probe gave an all-zero output.

The fill changes the numbers. Compared with earlier runs over a zero cache (same image, tool without the last commit), prefill/extend kernels take 8–24 % longer for int8 and 17–37 % longer for bf16. For the per-token-head slot alignment change we measured with this tool, the int8 speedup on those cells dropped by 0.10–0.21× (e.g. 2.09× → 1.88×); on decode cells it moved by at most 0.10×.

**Checks.**
- `pre-commit run --from-ref f8112704d5 --to-ref HEAD` passes on all 6 changed files. In the nightly image with no GPU visible, `python benchmark.py --help` works, `runner` and `mla_runner` import, and the guard rejects `int8_per_token_head` for `FLASH_ATTN`, `FLASHINFER`, `TRITON_MLA`, `FLASHMLA` and `FLASHINFER_MLA` while `TRITON_ATTN` passes it.
**GPU checks** (RTX 3080 20GB, sm_86, nightly image `sha256:8c1434bf…`, branch head):
- `benchmark.py --config configs/int8_per_token_head.yaml`: all 18 cells ran in one process with finite times, for int8 and with `kv_cache_dtype: auto`. Without a wait after the cache fill, cell 13 (`2q4s128k`) hit an illegal memory access, because `do_bench_cudagraph` times on a side stream; the fill now ends with a device sync.
- Cache fill on FLASH_ATTN, FLASHINFER and TRITON_ATTN (bf16 and int8), 12/2/256 and 32/8/128, q1s8k/q1s32k/q8ks32k: cache non-zero (bf16 100 %, int8 99 %), output finite and non-zero.
- `--kv-cache-dtype int8_per_token_head` on FLASH_ATTN / FLASHINFER, and `fp8` on TRITON_ATTN (sm_86), print a per-cell error instead of timing a different cache.
- All 10 runs completed without errors.
- The kernel received the packed cache: 520-byte slots at D=256 and 264-byte slots at D=128, with the V pointer at `% 16 = 4`.
- A `torch.profiler` run confirmed that q8s128k takes the 3D split-K path (`reduce_segments` launched) and q8ks128k the 2D path.

## Details

- `runner.py` maps the dtype with `STR_DTYPE_TO_TORCH_DTYPE` and passes `kv_quant_mode=get_kv_quant_mode(kv_cache_dtype)`, as `Attention.get_kv_cache_spec` does. For `fp8` the spec now carries `FP8_PER_TENSOR`, which no backend's `customize_spec` acts on.
- Only `int8_per_token_head` is added to the CLI choices, because it is the mode validated here.
- Cache fill: request `i` owns blocks `[i * max_blocks_per_request, ...)` of the benchmark's block table, so its `kv_len` tokens map to slots `i * max_blocks_per_request * block_size + arange(kv_len)`. One random K/V pair per request is written into every layer's cache; the transient tensors are one request's K/V. The fill ends with a device sync, because `do_bench_cudagraph` times on a side stream that does not wait for the default stream.
- Known tool limits, not changed by this PR:
  - The tool hard-codes the `meta-llama/Meta-Llama-3-8B` config, which is a gated repo; our runs used a local stand-in config. The `auto` cache and q/k/v take that config's dtype (bf16 here); `BenchmarkConfig.dtype` is not used for them.
  - The metadata builder is built without a speculative config, so split-K scratch is sized for one query token.
  - The tool exports only mean and std, so the medians above are taken across processes.
- No unit test: `attention_benchmarks` has no test suite.
- Measured only on RTX 3080 (sm_86); other GPUs were not run.

If #59774 lands first, this PR reduces to the cache fill, the per-layer impl and the config.
