# [Mooncake] Route KV transfers through a backend interface

[Upstream PR](https://github.com/vllm-project/vllm/pull/64363) · state: open · merged: False

## Original PR description

## Purpose

`MooncakeConnectorWorker` creates `mooncake.engine.TransferEngine`, asks it for its RPC port, registers KV memory with it, and runs both transfer directions against it, so the connector is bound to one engine implementation.

This PR puts that role behind an interface and wraps the Transfer Engine in an adapter, and the connector stops touching `mooncake.engine.TransferEngine`. Behaviour is unchanged: same status text, same per-request failure fan-out, no new configuration key, no wire change.

What the interface covers:

- `register_regions` / `unregister_regions`: pin and release KV memory.
- `submit(peer, op, ranges)`: start one request; every range carries an id.
- `poll()`: terminal outcome per range.

`TransferEngineBackend` implements it with the same blocking batch call the connector made before, and reports the batch status for every range of the request. The Transfer Engine settles a request inside the call, so the events of a submission come back to the submitting thread; the adapter keeps them per thread so concurrent sender workers never read each other's results.

## Why per-range events

The engine answers with one status per batch today. Keeping that status as per-range events keeps a failure attached to the blocks it happened on, and gives an engine that reports finer outcomes a place to put them without another change in the connector.

## Duplicate work

No open PR puts an interface in front of the engine usage in the Mooncake connector. #61974 adds the pull-mode connector and edits `mooncake_connector.py`; it keeps calling `mooncake.engine.TransferEngine` directly, so the two changes can be combined in either order.
