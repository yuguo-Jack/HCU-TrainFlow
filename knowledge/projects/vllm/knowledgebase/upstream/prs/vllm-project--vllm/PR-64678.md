# [Bugfix][KV Offload][P2P] Fail a dead peer's sibling ports on the same host at once (opt-in)

[Upstream PR](https://github.com/vllm-project/vllm/pull/64678) · state: open · merged: False

## Original PR description



## Overview

Fixes 1 and 3 of #56828.

A P2P peer is identified by `host:port` (`vllm/v1/kv_offload/tiering/p2p/manager.py:128-133`), and each DP rank binds its own port (`manager.py:344-348`). So a source pod with 8 DP ranks is 8 unrelated sessions on the consumer. When one rank's session dies, `_reap_dead_sessions` reaps only that `peer_id` (`manager.py:872`, `:878`). The sessions to the pod's other ranks stay up, and so do their loads.

With the new P2P tier option `group_peers_by_host`, a dead peer also takes down the sessions to the other ports on its host, and that host gets no new outbound sessions for 10 s. The option is off by default. Separately, the load-timeout warning now prints the job id and the seconds since submit.

## Claims

- With `group_peers_by_host: true`, when a session dies, every other session to the same host is closed in the same reap, through the same teardown. Their in-flight loads fail at once. Their kv_request_ids go into `_failed_req_ids`, so `lookup()` returns MISS (`manager.py:427`) and the requests prefill locally.
- For the next 10 s, `_get_or_create_session` returns None for any port on that host. `on_new_request` then marks the request failed (`manager.py:473-475`), so a new request naming that host prefills locally instead of opening a session.
- Sessions to other hosts are untouched.
- With the option off (the default), nothing changes: the reap is per peer, as on main.
- The warning at `session/client.py:527` now reads `P2PSession <peer>: <req> round=0 job_id=7 timed out 10.0s after submit, sending abort`. Since #63781 a load times out after 10 s (symmetric P2P) or 30 s (PD) (`session/client.py:37`, `:40`), so the old line did not say which applied. Bytes moved are not logged: the fetch protocol has no progress signal to read them from.

## Details

The issue's timeline, mapped to main:

1. Rank 7777's control connection closes. `_reap_dead_sessions` reaps that session only (`manager.py:872`, `:878`).
2. The sessions to 7778-7784 stay up. A new request naming 7779 reuses its session (`manager.py:757-759`, called from `:473`), and the PD path returns HIT (`manager.py:451`).
3. If 7779's data path is gone, the load runs to its load timeout (`session/client.py:525`). Since #63781 and #64256 that is 10 s for symmetric P2P and 30 s for PD, down from 36-43 s. But every load to a sibling rank still pays it.

**Why the host, and why opt-in.** Nothing in the P2P tier knows which ports make up one pod. The host part of `peer_id` is the only key they share. It is right for one pod per IP, as in the issue's llm-d deployment. It is wrong when independent instances share a host: `run_accuracy_test.sh` starts every instance on `127.0.0.1` (line 103), and the open fault slice #64511 checks that pulls from a healthy co-located source keep hitting while the other source faults. Turned on there, this would fail the healthy source's loads for up to 10 s. So it is a tier option, documented in `kv_offloading_usage.md`. If you would rather have an explicit failure domain (for example a field next to `remote_host` that the router sets), I can do that instead.

**Quarantine.** It is time-based only: 10 s, the ZMQ heartbeat timeout (`control/zmq.py:27`). An inbound connection from the host does not lift it, because a sibling rank that is still control-alive could reconnect at once. It only blocks new outbound sessions. Inbound connections are accepted as before.

**Teardown.** The siblings go through the same path as the dead session: `close()` sends each one `DisconnectMsg` (`session/session.py:416`), their running transfers are retained (#64250), and `remove_remote_peer` deregisters them. No reconnect backoff is scheduled for them, since they had no data-plane fault. The peer-down line names the dead peer and the number of loads failed.

Fix 2 of the issue (abort a load with no data-path progress) is not here. It needs a progress signal in the fetch protocol.

**Not a duplicate.** No open or merged PR references #56828 or groups sessions by host. Closest merged: #63781 (per-mode load timeout), #64256 (fail a timed-out load at once), #64501 (prefill locally while a handshake is pending), #64251 (fault a peer whose source WRITE stalls). Each bounds one peer's own wait; none touches the sessions to its sibling ports. Closest open: #64060 (ZMQ reconnect handover), #61667 and its splits #64298, #64299, #64300 (consumer slots, buffered terminal messages, failed ids), #64006 (IPv6 literals; `_host_of` uses the same last-colon split as its `host:port` parsing).

- A whole host down is already caught per port, in ~1s (sockets closed) or ~10s (heartbeat).

- It can misfire: an idle eviction or a single handshake failure takes down the whole host, it cascades to the healthy side, and co-located instances break it.
