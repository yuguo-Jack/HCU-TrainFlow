# [Quantization] Make activation-quantization fallbacks explicit, add VLLM_STRICT_QUANT_SCHEME

[Upstream PR](https://github.com/vllm-project/vllm/pull/59460) · state: open · merged: False

## Original PR description

## Purpose

Weight-only kernels (Marlin, Humming's weight-only conversions, CPU W8A16) accept whatever activation key the oracle passes and silently run activations unquantized. So an FP8 W8A8 or NVFP4 W4A4 layer quietly becomes W8A16/W4A16 when the native kernels are unavailable (e.g. `--quantization fp8` or an FP8 checkpoint on A100). That fallback is useful, but it is invisible, and there is no way to require that a quantization config is actually respected.

This supersedes #57091, which made Marlin strict on its own. That would break every oracle that passes the checkpoint's declared key to Marlin (NVFP4 auto, MXFP8, ...). Here each backend declares what it actually runs, and the check is enforced centrally:

- **Per-backend declaration:** `executed_activation_key(...)` is a hook on the MoE experts base (`FusedMoEExperts`) and on the linear kernel family bases (`MMLinearKernel`, `ScaledMMLinearKernel`, `NvFp4LinearKernel`, `Mxfp8LinearKernel`, `MxFp4LinearKernel`). It defaults to "runs the requested activation quantization", so a new backend is strict by default. Weight-only backends override it in their own file:
  - MoE: `MarlinExperts`, `TritonWNA16Experts`, CPU FP8 W8A16, `B12xExperts` (under `VLLM_B12X_MOE_FP4_FORCE_A16`) and Humming.
  - Linear: Marlin FP8/NVFP4/MXFP8/MXFP4, Humming FP8/INT8 scaled-mm, CuteDSL NVFP4 W4A16 and CPU FP8 W8A16.
- **Central enforcement:** `FusedMoEExperts.is_supported_config` checks support against the executed key and then calls `check_activation_quant_fallback()` (`quant_utils.py`) as its last step, so every oracle gets it without per-oracle code. The linear selection paths (scaled-mm FP8/INT8, NVFP4, MXFP8, MXFP4) call the same helper.
  - A fallback warns once by default, or rejects the kernel under `VLLM_STRICT_QUANT_SCHEME=1`. Selection then moves on to the next backend, so backend priority order is unchanged and strict mode can still land on e.g. NVFP4 `EMULATION`.
  - Adding activation quantization to an unquantized request is not flagged.
- **Humming:** its executed schema depends on how its weights are converted. The Humming quant method, WNA16/W4A8 weights and `VLLM_HUMMING_INPUT_QUANT_CONFIG` honor the requested schema; the FP8/NVFP4/MXFP8/INT8 oracles convert weight-only. This is declared in `fused_humming_moe.py`. Its internal input-schema fallback now also warns, and strict mode forces `allow_fallback=False`.
- **Cleanups that fall out:** the nvfp4 `_use_a16` activation-key special case is removed, FP8 block-shape refinement uses the executed key, and Marlin MXFP4's ad-hoc warning is replaced by the central one.

Default selection behavior is unchanged; the only default-mode difference is the new warnings.

Known gaps: Quark weight-only MXFP8 goes through `init_mxfp8_linear_kernel`, which assumes W8A8, so a Marlin pick there would warn spuriously. Runtime/per-layer fallbacks (e.g. CPU MLA `kv_b_proj`) are not covered.

## Test Plan

- Unit tests:
  - `tests/kernels/moe/test_moe_kernel_oracle.py`: strict mode skips NVFP4 Marlin for emulation while keeping priority order; FP8 -> Marlin still works by default and errors under strict.
  - `tests/kernels/quantization/test_scaled_mm_kernel_selection.py`: Humming FP8 linear override is parametrized over strict.
  - `tests/kernels/quantization/test_mxfp4_kernel_selection.py`: the Marlin warning is now asserted through selection.
- Existing selection suites: mxfp4/mxfp8 kernel selection, b12x (incl. force-A16), mxfp8 aiter, unquantized, fp8 TP loading, `test_modelopt.py`.
- E2E on B300 (`chg run -g=1`), greedy generation with `Qwen/Qwen3.6-35B-A3B` + `--quantization fp8`, `Qwen/Qwen3.6-35B-A3B-FP8`, `RedHatAI/Qwen3.6-35B-A3B-NVFP4`, each with auto / forced `marlin` / forced `humming` backends, with and without `VLLM_STRICT_QUANT_SCHEME=1` (rerun after moving the declarations onto the backends).

## Test Result

- Unit/selection suites: 222 passed, 13 skipped. Two failures in `test_modelopt.py` (`test_modelopt_w4a16_respects_linear_backend[auto-MarlinNvFp4LinearKernel]`, `test_modelopt_fp8_pb_wo_checkpoint_setup`) also fail identically on a clean `main` checkout on this machine (SM103), so they are unrelated.
- E2E:

| Case | Default | `VLLM_STRICT_QUANT_SCHEME=1` |
|---|---|---|
| Auto backends (online FP8, FP8 ckpt, NVFP4 ckpt) | native kernels, correct output | same (no false positives) |
| `--moe-backend marlin --linear-backend marlin` (all three) | warns for MoE + linear, correct output | startup error |
| `--moe-backend humming --linear-backend humming` (FP8 ckpt) | warns for MoE + linear, correct output | startup error |
| `--moe-backend marlin` only (FP8 ckpt) | – | MoE oracle error |

Example strict error: `FP8 MoE backend MARLIN does not support the deployment configuration since MARLIN MoE backend runs QuantKey(f8e4m3fn,scale(f32,dynamic,GroupShape(row=1, col=128)),symmetric) activations as unquantized, which VLLM_STRICT_QUANT_SCHEME=1 forbids.`

No accuracy evals: selection is unchanged in default mode, and forced-fallback outputs match the native ones on the sampled prompts.
