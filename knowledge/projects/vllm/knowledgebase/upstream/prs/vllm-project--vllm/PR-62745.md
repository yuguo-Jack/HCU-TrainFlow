# [Perf][Kernel] mHC TileLang: skip Sinkhorn on non-finite padding rows; single-pass fused post+pre for <=4 tokens

[Upstream PR](https://github.com/vllm-project/vllm/pull/62745) · state: closed · merged: True

## Original PR description


## Overview

Two small mHC TileLang changes in `vllm/model_executor/kernels/mhc/tilelang_kernels.py` that speed up low-batch decode for GLM-5.3-Flash (hidden 4096, hc_mult 4):

1. `mhc_pre_big_fuse_with_norm_tilelang` skips the remaining Sinkhorn iterations when a row's RMS is non-finite. Output is bit-exact. CUDA-graph padding rows reach this kernel as NaN; the root cause is below.
2. `mhc_fused_post_pre_split_config` uses a single-pass config (tile_n 2, 16 splits, 256 threads) for <= 4 tokens when `hidden_size == 4096`. on CUDA devices with compute capability >= 10.0 (where it was tuned). SM90, older GPUs and the ROCm TileLang fallback keep the existing configs.

Related: #61461 tunes the same function for SM90 (H20). This PR targets hidden 4096 on Blackwell and SM107; both changes speed up both. The numbers below are for Blackwell (GB300, RTX PRO 6000). 

## Claims

- **Fused mHC post + pre op** (one per sublayer boundary, ~89 calls per GLM-5.3-Flash decode step), clean rows: **1.08-1.19x** at 1-3 tokens on GB300 and RTX PRO 6000, 0.99-1.05x at 4 tokens, unchanged from 5 tokens on.
- **Decode batches smaller than their CUDA-graph size:** the mHC ops on the padded batch are **1.2-1.55x** faster, saving ~3 us on each of ~89 calls per padded step. Clean rows are unchanged.
- **SM107:** both changes are also faster there, at 1-4 tokens and on padded batches, with the same numerics. 
- **Numerics:**
  - Change 1 is bit-exact for all inputs.
  - Change 2 only reorders an fp32 split-sum: post/comb differ by at most 2.4e-7, and `layer_input` is bit-identical in the kernel A/B.
  - GSM8K (5-shot, greedy, 1319 questions) on a GLM-5.3-Flash NVFP4 server with both changes stayed within the baseline's run-to-run spread (91.2% vs 91.8%; baseline spread 1.0 pt).

## Validation

**Unit tests:** `pytest tests/kernels/mhc` on GB300 and on RTX PRO 6000. The branch's mHC files were overlaid onto a nightly image, and the same harness was run on `main`.
- All of `test_mhc_jit_warmup.py` and `test_mhc_tilelang_jit.py` pass on both GPUs. This includes the new band cases (1 and 4 tokens -> (2, 16, 256); 5 tokens -> (2, 8, 128)) and the warmup-input check for the new compile key.
- GB300: 278 passed with this PR vs 275 on `main`.
- The remaining errors are identical on `main`: DSv4.1 tests that need `tests/conftest.py` fixtures the out-of-tree harness lacked.

**End to end on GB300**:
- Setup: GLM-5.3-Flash NVFP4, agg TP4, `vllm serve` behind the Dynamo frontend, sa-bench ISL 8192 / OSL 1024, `random_range_ratio 1.0`, 10 × C prompts. FlashInfer TRT-LLM MoE with autotune, FP8 KV cache, max-num-batched-tokens 32768.
- Baseline: the nightly image at 1b2a666, whose `tilelang_kernels.py` is identical to `main`. "This PR" = the same image with only this PR's `tilelang_kernels.py`.
- 3 runs per arm, each on its own node; all requests completed.

| concurrency | main: tok/s/user (range), TPOT | this PR: tok/s/user (range), TPOT | change |
|---|---|---|---|
| 1 | 216.5 (215.5-217.1), 4.48 ms | 228.9 (228.4-229.7), 4.23 ms | **+5.8%** |

- C1 has no CUDA-graph padding, so its gain comes from change 2 alone.
- C6 runs every decode step in the 8-token graph, which is above the 4-token band, with 2 padding rows. So its gain comes from change 1 alone. It matches the kernel saving (~3 us x ~89 calls).
- The C1 gain (0.25 ms per step) is larger than the isolated-kernel saving (~0.06 ms per step). We see the same ratio on SM107. We have not profiled why.
- TTFT is unchanged.
- At concurrencies that exactly fill a graph (e.g. 8, 32, 128) neither change applies, so no gain is expected there. On SM107 we measured none.

## Details

**Why padding rows are non-finite (root cause).**
- In GLM-5.3-Flash, layer 0 is a KDA layer.
- `fused_recurrent_gated_delta_rule_fwd_kernel` returns early for `NULL_BLOCK_ID` slots (CUDA-graph padding) without storing its output.
- Those rows of `core_attn_out` (`torch.empty`) therefore keep stale graph-pool memory, and the padding rows are non-finite from layer 1 on.
- An nsys trace of a padded decode step matches this: the layer-0 mHC pre runs at clean speed, and every later one is slower by the same amount.
- In `pre_big_fuse`, the Sinkhorn then runs ~40 IEEE divisions on NaN in its serial warp-0 chain, each taking the slow path.

**Why the guard is bit-exact.** A non-finite RMS already makes the whole comb result NaN, so skipping the remaining iterations changes nothing. Real rows are unaffected: every op on this path is row-local, and padding outputs are discarded.

**Scope.**
- The guard also covers other sources of non-finite padding, such as other attention backends and the DSv4 delayed mHC path.
- Writing zeros for null slots in the FLA recurrent kernels, as the packed-decode kernel already does, is the complementary source-side fix. It affects all GDN/KDA hybrids and will be proposed separately.

**Why one pass helps at <= 4 tokens.**
- With 8 splits x 128 threads over hidden 4096, each thread makes four serial load passes. At 1-4 tokens the grid (96 CTAs per token) is too small to hide their latency.
- Twice the splits with 256 threads gives each thread a single pass. From 5 tokens on, the existing (2, 8, 128) config is as fast or faster.
- The band is limited to hidden 4096; DeepSeek-V4's 5120/7168 configs are untouched.
- It is gated to SM100+ because that is where it was measured. The mechanism (latency hiding at tiny grids) is generic, but #61461 found a different optimum on SM90, so other architectures keep their current configs.
- It adds one compile key. Warmup now compiles it together with the (2, 8, 128) key, which the old `warmup_inputs` never selected (it JIT-compiled at runtime for 5-15 tokens).
