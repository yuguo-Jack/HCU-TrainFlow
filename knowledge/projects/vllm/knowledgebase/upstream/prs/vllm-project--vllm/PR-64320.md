# [Bugfix][PP][Spec Decode] Relay Qwen3-MoE EAGLE3 aux hidden states over PP

[Upstream PR](https://github.com/vllm-project/vllm/pull/64320) · state: open · merged: False

## Original PR description



## Overview

Enables EAGLE3 (and other aux-hidden-state drafters) for Qwen3-MoE targets at PP > 1 on Model Runner V2. Same pattern as Qwen2 (#50514) and MiniMax-M3 (#57197); the Qwen3.5 counterpart is #61180.

## Claims

1. **Qwen3-MoE + EAGLE3 runs at PP > 1.** Base rejects it at load (`ValueError: Qwen3MoeForCausalLM does not support eagle3 with pipeline parallelism`). With this PR the last rank gets all taps in order; acceptance length (2.755 vs 2.753) and GSM8K match PP1.
2. **A tap on a PP stage boundary is recorded once.** The default taps `(2, 24, 45)` put one on the PP2 boundary of the 48-layer models.
3. **No change at PP = 1 or without aux layers**, except that a layer-0 tap is now cloned (see Details).

## Validation

**Setup:** 2x H200, `Qwen/Qwen3-30B-A3B-Instruct-2507-FP8` + `RedHatAI/Qwen3-30B-A3B-Instruct-2507-speculator.eagle3` (`num_speculative_tokens=3`, default taps `(2, 24, 45)`), `main` at ab0e5ef795, Model Runner V2, default compile/CUDA graphs. The branch was then rebased onto 3c39dda2a5 (no upstream changes to the touched production files or the aux-relay helpers; #64111 split the shared fake layer, so the Qwen3 cases wrap it in a single-call `forward`); CPU tests and pre-commit were rerun there.

## Details

**Root cause.** `Qwen3MoeModel` had no #50514 opt-in, so MRV2 rejects aux-state drafters at PP > 1. Its `forward` already captured taps, but only stage-locally: a non-last rank dropped them from `IntermediateTensors`, the last rank never collected upstream taps, and every rank recorded its `start_layer` tap, so a boundary tap was taken twice (end of stage N-1 and start of stage N).

**Fix.** Set `supports_aux_hidden_states_over_pp` and follow `Qwen2Model.forward`: record the entry tap on the first rank only, `pack_local_aux_hidden_states` on non-last ranks, `collect_remote_aux_hidden_states` + local taps on the last rank. As in #57197, a layer-0 tap aliases `residual`, which fused add-RMSNorm may update in place, so it is cloned (any PP size; CPU-tested only, the GPU runs above use taps 2/24/45).

**Subclasses.** `Qwen3MoeLLMModel` in `qwen3_vl_moe.py` and `qwen3_omni_moe_thinker.py` override `forward` (deepstack) without the relay, so they set `supports_aux_hidden_states_over_pp = False` and keep today's startup error instead of inheriting the opt-in and silently dropping taps. Same approach as `MiMoModel` over `Qwen2Model`. Enabling them is a separate change.

**Size.** 3 production files, +24/−4. Tests: +109 CPU (fixture mirrors the MiniMax-M3 one), +42/−9 E2E (`_run` takes model/draft/prompts/lengths; Llama case unchanged).

**Limits.** Aux relay is MRV2-only. Validated EAGLE3 only; DFlash/DSpark on Qwen3-MoE at PP > 1 are now accepted but untested. Untested: Qwen3-235B-A22B, TP > 1 combined with PP, ROCm. Each PP hop carries one extra `[tokens, hidden]` tensor per upstream tap (not benchmarked). The new E2E test needs 2 GPUs and the 30 GB FP8 checkpoint at `gpu_memory_utilization=0.45` (run on H200; not tried on 80 GB cards), and takes ~2.5 min; the existing Llama case only runs where 4 GPUs are available, so maintainers may prefer a different CI placement. The CPU tests use `SimpleNamespace`/monkeypatch fakes like the existing MiniMax-M3 cases in the same file, which `tests/AGENTS.md` discourages; the E2E test is the real-object coverage. #57337 also edits `Qwen3MoeModel.forward` (possible conflict). No duplicate found (`gh pr list` / `gh issue list` for Qwen3-MoE + PP + EAGLE3/aux; #61180 covers Qwen3.5 only).
