## Purpose

`--tool-call-parser xlam` produces streaming responses that diverge from
non-streaming parsing of the same model output, in two ways:

1. **Tool-call arguments are duplicated.** The streaming parser tracks what
   it has sent only in private state and never updates the base class's
   `streamed_args_for_tool`. At end of stream,
   `finalize_generation → get_remaining_unstreamed_args()` therefore
   computes "everything is still unstreamed" and appends the full argument
   string to the final delta. Whenever the final chunk completes the
   argument object (alignment-dependent, so it looks intermittent
   downstream), OpenAI-compatible clients reconstruct
   `{"city": "X"}{"city": "X"}` or `{{"city": ...}` — invalid JSON that
   breaks tool execution.
2. **Wrapper markers and partial tool-call JSON leak into `delta.content`.**
   For ` ```json ` / `[TOOL_CALLS]` / `<tool_call>` wrapped outputs, deltas
   stream as content until both `"name"` and `"arguments"` appear in the
   accumulated text, so clients see e.g.
   `I'll check the weather for you.[TOOL_CALLS][{"name": "get_current_weather", "arguments`
   as assistant content. Non-streaming strips all of it.

This PR reworks `extract_tool_calls_streaming` around a single forward scan
of `current_text` that classifies each span as chat content, tool-block
markup, or tool-call JSON:

- content that could still turn out to be a wrapper marker is withheld until
  disambiguated, so markers and tool JSON never reach `delta.content`;
- whitespace is withheld until more content follows, matching the `.strip()`
  the non-streaming path applies around the tool block;
- argument deltas are mirrored into `streamed_args_for_tool`, so the serving
  layer's end-of-stream flush has nothing left to re-append.

The non-streaming path (`extract_tool_calls`, `preprocess_model_output`) is
unchanged. The exception fallback now returns `None` instead of echoing the
raw delta as content (the old fallback re-introduced the leak; other parsers
return `None` here too).

**Not a duplicate:** the two open PRs touching this parser are orthogonal —
#49535 anchors the `"name"` regex against arguments literally named "name",
and #47954 anchors empty-args detection. Neither changes
`streamed_args_for_tool` bookkeeping nor the content path (verified against
both diffs). No existing issue or PR covers either bug fixed here. Happy to
rebase over whichever lands first.

## Test Plan

- `pytest tests/tool_parsers/test_xlam_tool_parser.py` — all pre-existing
  tests, plus new `test_streaming_matches_nonstreaming` (10 cases, including
  empty-arguments-then-second-tool): streams token-by-token with the file's
  existing incremental-detokenization generator, reconstructs applying the
  same conditional end-of-stream flush as `finalize_generation` (remaining
  unstreamed args appended only when the final delta carries tool calls),
  then asserts
  - streamed content equals non-streaming content (regression guard for the
    marker leak),
  - per-tool reconstructed arguments are JSON-equal to non-streaming —
    `json.loads` fails on the old duplication, so this guards the
    `streamed_args_for_tool` bookkeeping end to end.
- A standalone streaming-vs-nonstreaming differential harness (mirrors the
  in-tree feed loop plus the serving layer's conditional
  `get_remaining_unstreamed_args` flush) run over 9 xLAM output corpora Ã— 6
  chunk alignments, including markers split mid-token.
