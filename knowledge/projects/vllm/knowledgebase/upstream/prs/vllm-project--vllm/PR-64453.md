# WIP

[Upstream PR](https://github.com/vllm-project/vllm/pull/64453) · state: open · merged: False

## Original PR description

WIP: makes `--chat-template` (and per-request `chat_template`) effective for models served with `--tokenizer-mode deepseek_v32`, so variants reusing the DeepSeek-V3.2 tokenizer can ship their own template, e.g. a custom tool-calling format consumed by a tool parser.

## Problem

The template is silently dropped in two places:

- `DeepseekV32Renderer` hardcodes `content_format="string"` and calls the tokenizer directly, skipping the shared `safe_apply_chat_template` resolution/validation path.
- `_DeepseekV32Tokenizer.apply_chat_template` ignores the `chat_template` kwarg and always encodes with the built-in V3.2 templates (see #37839).

## Changes

- `vllm/renderers/deepseek_v32.py`: when `params.chat_template` is set, detect the content format from that template and render through `safe_apply_chat_template` (sync + async); unchanged when no template is given.
- `vllm/tokenizers/deepseek_v32.py`: when a `chat_template` is supplied, delegate to the underlying HF `apply_chat_template` (so `tools` are handled natively) instead of the built-in encoding; also accept the template passed as keyword-only `conversation=`.
- `tests/tokenizers_/test_deepseek_v32.py`: covers the default encoding, a custom template, and tool forwarding.

## Status

Opened as WIP: unit tests added but not yet run against a vLLM build, and doc/release-note updates are still missing.

Related: #37839, #46256
## Example

A DeepSeek-V3.2-based model that ships its own template (here: a tool-calling format that a custom tool parser expects) can now be served with:

```bash
vllm serve <model> --tokenizer-mode deepseek_v32 \
  --chat-template ./telechat_tool_template.jinja \
  --enable-auto-tool-choice --tool-call-parser <custom-parser>
```

Before this change the `--chat-template` was accepted but never used, so the prompt was rendered with the built-in V3.2 encoding and the tool parser saw output it could not parse.
