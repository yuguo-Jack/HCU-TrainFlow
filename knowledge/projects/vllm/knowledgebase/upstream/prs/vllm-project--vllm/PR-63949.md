# [ROCm][CI] Untrusted base builds wait for main's images instead of rebuilding them

[Upstream PR](https://github.com/vllm-project/vllm/pull/63949) · state: closed · merged: True

## Original PR description

- `build.sh`: an untrusted base build computes the image keys of its merge base with main, and for each image whose key is main's it waits for main's CI build to push it instead of building the same image in parallel
- `build.sh`: a trusted base build marks the image it is building (`rocm/vllm-ci:building-<tag>`, refreshed every 5 minutes); others wait only while that mark is fresh, with a 10-minute start grace spent once per build
- `build.sh`: a branch that changes an image's inputs still builds it at once; trusted builds never wait, and if main cannot be read nothing waits
- `test_rocm_build.py`: waiting and reusing main's images, building at once when main is not building them, the once-per-build grace, registry errors while waiting, and the heartbeat not holding up the build

When a ROCm base image key changes on main, every PR base build that starts before main's base build finishes misses the trusted image and rebuilds the same stack in its own `pr<N>-` namespace, so the amd-cpu queue fills with identical builds that take hours each; on 2026-10-27 about 30 `refresh-rocm-base-amd` jobs were rebuilding the same base at once. A failed or canceled main build stops refreshing its mark, so builds waiting on it notice within 15 minutes and build the image themselves. The 300-minute deadline on all waits is only a backstop for a hung main build or a planted mark (PR hosts can still push to `rocm/vllm-ci` until the PR-host split), and a stack built after it may not fit the step's 540-minute timeout. Nightlies and branch builds wait too, and #64131 also edits `ensure()`, so whichever of the two merges second needs a small rebase. Follow-up to #61939; `pytest tests/tools/test_rocm_build.py` passes 38 tests (17 new) in 10 runs out of 10, and HEAD's image keys are unchanged from main's.
