# [KV Offload] Load small CPU-tier hits synchronously within the step

[Upstream PR](https://github.com/vllm-project/vllm/pull/61961) · state: open · merged: False

## Original PR description

## Overview

On wide-EP MoE prefill (such as GLM-5.3), a step takes 0.3 to 0.5 s. Almost every request has a small CPU-tier hit, and an async load parks it for about 2 steps although the copy takes ~1 ms.

This adds an opt-in `sync_load_max_tokens` option (`kv_connector_extra_config`, default 0, off): smaller hits load in the same step. The change stays in the offloading connector's scheduler and worker.

## Changes

- `scheduler.py`: hits up to `sync_load_max_tokens` return `load_async=False`, so the request is scheduled in this step; the load targets its blocks by position and is marked sync.
- `worker.py`: waits for sync loads before the forward pass and does not report them in `finished_recving`.
- `common.py`: a `TransferJob.sync` flag carries that decision from scheduler to worker.

## Claims

- Hits up to the limit load in the same step. The limit exists because the whole batch waits for the copy. A hit that would leave nothing to compute stays async.
- Sync-load blocks are hashed at allocation, so the load range is found by position. Other requests can match them in the same step, which is safe since the forward pass waits for the copy.
- The worker waits for sync loads with the existing `OffloadingWorker.wait()` before the forward pass.
- With the option at 0, behavior is unchanged.

## Validation

Qwen3-30B-A3B on H100, OffloadingConnector + TieringOffloadingSpec. 12k-token prefix in GPU cache, 2k-token tail only in the CPU tier. Median extra TTFT vs a GPU-hit control:

| Setup | Without fix | With fix (limit 4096) |
|---|---|---|
| 1 node: DP=2 + EP (this version, 10 reps) | +219 ms | +1 ms |
| 2 nodes: TP=8, DP=2, EP over 16 GPUs (12 reps) | +344 ms | +8 ms |

GLM-5.3, one prefill group (4x8 H100, wide EP), request latency with a CPU-tier hit: ~1.9 s without the fix or above the limit, ~0.85 s under it (hits of 2k to 15k tokens).

Correctness: greedy continuation with the tail served from the CPU tier is correct 7/7 (Qwen3 and GLM-5.3).

- Etelis · COMMENTED · 2026-10-19T13:03:49Z · [source](https://github.com/vllm-project/vllm/pull/61961#pullrequestreview-5571946818)

I agree this is a real issue in the specific scenario we’re seeing.
However, for a general-purpose inference engine, I’m concerned that `sync_load_max_tokens` adds more tuning complexity than value.

Users would need to choose an appropriate threshold for each deployment, and that value may become suboptimal as the workload changes. 
For example, many individually small loads could all qualify for synchronous loading while collectively causing a substantial batch-wide delay.

I’d suggest either keeping the existing async behavior and accepting the latency cost, or exposing a simple`sync_loads` flag, defaulting to async. That would make KV loading synchronous before the forward pass and give users a clear, predictable tradeoff.

Another direction might worth exploring is reducing the async completion round trip from two scheduling steps to one where possible.

I think @orozery needs to decide.
