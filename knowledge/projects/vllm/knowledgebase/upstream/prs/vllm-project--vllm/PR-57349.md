# [Bugfix][torch.compile] Honor an explicit RoPE+KV-cache fusion request

[Upstream PR](https://github.com/vllm-project/vllm/pull/57349) · state: closed · merged: False

## Original PR description

## Overview

An explicit `fuse_rope_kvcache=True` is silently reset to `False` because `set_splitting_ops_for_v1` splits out `vllm::unified_kv_cache_update`, the op the fusion rewrites; this PR keeps that op in the compiled graph when a fusion requests it and layer names are hoisted (`_USE_LAYERNAME`).

The split protects Inductor graph reuse (#33267). Reuse only breaks while `layer_name` is a string constant in the graph. On torch >= 2.11 it is a graph input, so keeping the op costs +0.08 s per compile range on a Llama-3.1-8B cold start. With hoisting off it costs 12.8x (1.26 s → 16.02 s), so the request is still refused there, and the warning now states that reason. `fuse_qk_norm_rope_kvcache` and `fuse_rope_kvcache_cat_mla` (with `unified_mla_kv_cache_update`) are handled the same way.

`_set_compile_ranges()` now runs after `set_splitting_ops_for_v1()`, so a dropped fusion no longer leaves its endpoint behind (`[256, 256, N]`). `enable_qk_norm_rope_kvcache` also gains the `splitting_ops_contain_kv_cache_update()` guard that `enable_rope_kvcache_fusion` has.

An optimization level alone still cannot enable the fusion; #57900 fixes that on its own, and the two compose.

## Claims

- With `VLLM_ROCM_USE_AITER=1`, an explicit request for any of the three fusions is honoured. With `VLLM_USE_LAYERNAME=0` it is refused with a warning, and endpoints are `[N]`.
- The fused kernel is **+51.0%** (`ROCM_ATTN`) and **+48.1%** (flash layout) faster at 1–64 tokens on MI355X. It breaks even at 192–256 tokens, the existing `rope_kvcache_fusion_max_token_num` default.
- Llama-3.1-8B serving improves median TPOT by **−2.6%** and median TTFT by **−14.9%**.
- One pattern is replaced on Llama-3.1-8B, Mixtral-8x7B and gpt-oss-120b. QK-norm (Qwen3, gemma-4) and MLA-only models match 0.

## Validation

`main@7128f568ac`, MI325X, torch 2.12: `tests/compile/test_config.py -k splitting_ops` passes 8. Of the new cases, 6 fail on `main`, and 3 fail with the `_USE_LAYERNAME` guard removed. At `-O2`, `fuse_rope_kvcache=True` resolves to on with endpoints `[256, N]`. On Llama-3.1-8B the pass logs `Replaced 1 patterns`.

The numbers below are from MI355X at `0aee727ff6`, before the rebase, and have not been re-measured. `RopeKVCacheFusionPass` has not changed since.

Serving: `vllm bench serve`, random 128 in / 1024 out, 600 prompts, concurrency 50, three runs per arm.

| model | median TPOT | median TTFT | total tok/s |
|---|---:|---:|---:|
| Llama-3.1-8B | **−2.6%** | **−14.9%** | +3.7% |
| Mixtral-8x7B | −4.1% | +3.0% | +1.8% |
| Qwen3-14B-FP8 (0 patterns) | +0.1% | +2.3% | +0.1% |

Only the bold Llama deltas have disjoint ranges; total tok/s means only no regression.

GSM8K, 5-shot, greedy, 1319 items:

| model | patch Δ | base-repeat Δ | stderr |
|---|---:|---:|---:|
| Llama-3.1-8B | +0.0008 | +0.0008 | 0.0089 |
| Mixtral-8x7B | −0.0045 | +0.0000 | 0.0093 |
| gpt-oss-120b | +0.0167 | +0.0243 | 0.0087 |

The output is not bit-exact. Per-sample text agreement is 98.6% on Llama and 55.5% on Mixtral, against 99.3% and 99.6% for a base repeat.

## Details

#49142 and #60326 overlap only the MLA hunk. If either lands first, that hunk is dropped. #60326 also guards HiSparse, where an explicit `fuse_rope_kvcache_cat_mla=True` would now put the MLA cache-update op inside a piecewise graph.
