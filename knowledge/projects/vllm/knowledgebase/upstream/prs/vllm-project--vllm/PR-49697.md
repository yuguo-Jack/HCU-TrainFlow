File: `vllm/v1/worker/gpu/input_batch.py` · line 749

🟡 **Severity: MEDIUM**

`_post_update_torch` executes **after** the Triton `_post_update_kernel` on the same mutable tensors (`total_len`, `num_computed_tokens`, `all_token_ids`). Both increment `total_len` and `num_computed_tokens`, causing double-counting. The torch version reads the already-advanced `total_len`, writing sampled tokens at wrong offsets in `all_token_ids`—risking out-of-bounds access and cross-request data leakage.
Helpful? Add 👍 / 👎

<details>
<summary>💡 Fix Suggestion</summary>

**Suggestion:** The `post_update` function unconditionally calls both `_post_update_kernel` (Triton) and `_post_update_torch` on the same mutable tensors, causing double-counting of `total_len`, `num_computed_tokens`, and writing sampled tokens at wrong offsets. These two functions are meant to be mutually exclusive alternatives.

Fix:
1. Add `HAS_TRITON` to the import on line 8: `from vllm.triton_utils import HAS_TRITON, tl, triton`
2. In the `post_update` function (lines 766-793), gate the two calls with a conditional:
```python
    if HAS_TRITON:
        _post_update_kernel[(num_reqs,)](
            idx_mapping,
            num_computed_tokens,
            last_sampled_tokens,
            output_bin_counts,
            output_bin_counts.stride(0) if output_bin_counts is not None else 0,
            sampled_tokens,
            sampled_tokens.stride(0),
            num_sampled,
            num_rejected,
            query_start_loc,
            all_token_ids,
            all_token_ids.stride(0),
            total_len,
            num_warps=1,
        )
    else:
        _post_update_torch(
            idx_mapping,
            num_computed_tokens,
            last_sampled_tokens,
            output_bin_counts,
            sampled_tokens,
            num_sampled,
            num_rejected,
            query_start_loc,
            all_token_ids,
            total_len,
        )
```
This ensures only one implementation runs, matching the intent described in `_post_update_torch`'s docstring ("replaces `_post_update_kernel` when platform doesn't support triton").

The `_temperature_torch` function is a pure-torch fallback meant to be used *instead of* the Triton kernel (not after it). Calling both causes temperature to be applied twice (logits ÷ temperature²).
