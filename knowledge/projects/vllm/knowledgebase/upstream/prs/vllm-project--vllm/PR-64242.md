# [Bugfix][Kernel] Promote rejection sampler's global logsumexp to fp64

[Upstream PR](https://github.com/vllm-project/vllm/pull/64242) · state: open · merged: False

## Original PR description



## Overview

Fixes a precision bug deferred from #61383: the rejection sampler's global logsumexp silently
collapses a real near-1.0 probability to exactly 1.0 under fp32 rounding.

## Claims

- `_compute_global_logsumexp` combined per-block max/sumexp arrays in fp32. At a typical
  confident logit magnitude (~25), fp32 ULP (~3e-6) rounds away the correction term whenever a
  runner-up token trails the max by more than ~14 in logit-space.
- Fix: promote the per-block terms to fp64 before summing (summing in fp32 first reintroduces a
  smaller version of the same loss), and carry `target_rejected_logsumexp`/
  `draft_rejected_logsumexp` as fp64 through their downstream call sites.
- O(1) cost per block/request — not O(vocab_size) — so the fp64 promotion is free.

## Validation

```
CUDA_VISIBLE_DEVICES=7 .venv/bin/python -m pytest tests/v1/spec_decode/test_rejection_sampler_utils.py -q
# 89 passed, 1 failed -- the 1 failure is a CUDA OOM from a concurrent process on a shared GPU
# (confirmed unrelated: fails in isolation too, with "61.29 GiB memory in use" by another PID).

CUDA_VISIBLE_DEVICES=1 .venv/bin/python -m pytest \
  tests/v1/spec_decode/test_rejection_sampler_utils.py::test_global_logsumexp_keeps_near_max_correction -v
# PASSED. Stashed the fix and reran: FAILED with `25.0 == 25.0` -- reproduces the exact bug.
```

New test constructs a synthetic 2-block vocab (max logit 25.0, runner-up 11.0, i.e. gap=14) and
calls `_compute_global_logsumexp` directly through a minimal probe kernel, asserting the result
against the closed-form `max + log1p(exp(-14))` rather than exactly `max`.

## Details

**Root cause:** `global_max + log(sum(sumexp_i * exp(max_i - global_max)))` -- both operands fp32.
`log(sum)` for a gap-14 runner-up is `~8.3e-7`, below fp32's half-ULP (`~1.49e-6`) at magnitude 25,
so it rounds away. Reported and root-caused on #61383; shiannn13 is handling that issue's
empty-residual crash separately and deferred this precision issue to its own PR.

**Scope:** `_compute_global_logsumexp`'s return dtype, plus the ~6 call sites that read an LSE
value, each casting back to fp32 only after the fp64-sensitive subtraction/exp is done (needed to
keep loop-carried Triton variables at a single dtype).

**Why this isn't duplicating an existing PR:** searched open issues/PRs for "logsumexp precision",
"fp32 precision rejection sampling", and `draft_lse`/`61383 in:body` -- no existing issue or PR
touches this function or this bug.

**Docs:** none -- internal precision fix, no user-visible interface change.

- shiannn13 · comment · 2026-10-29T01:57:29Z · [source](https://github.com/vllm-project/vllm/pull/64242#issuecomment-6485759678)

Hi Alejandro, thanks for picking this up!

I've also been investigating #61383 and wanted to share some reproduction results. It looks like the fp64 global LSE fix addresses part of the numerical issue, but there are still cases where the residual becomes empty.

**Reproduction setup**

The reproducer uses real XGrammar with the Qwen3-4B tokenizer, the production grammar mask, and top-k/top-p.

At the rejected position (row 2):
- The target distribution supports only `"`, after grammar masking and top-k/top-p.
- The draft distribution is not grammar-masked. The logit for `"` is 25, the logit for `\t` is `25 - gap`, and all remaining logits are initialized to -20.
- The rejected draft token `\t` is grammar-valid but outside the target's support, so the sampler should resample `"`, not token 0 (`!`).

I tested the actual Triton kernels on an RTX 2050 with fp32 input logits. Both standard and block verification produced the same results:

| Draft gap | main | #64242 | A+B+C |
|---|---|---|---|
| 10 | OK | OK | OK |
| 14 | Emits `!` (token 0) | OK | OK |
| 18 / 20 / 30 / 80 | Emits `!` | Emits `!` | OK |

Note that at gap=80, the background draft logits also contribute to the residual, so this case does not isolate an `exp(-80)` contribution.

**What I tried (all fp32)**

- **A — Shifted log-softmax:** Keep LSE as `(max, correction)` and compute `(logit - max) - correction`, avoiding precision loss when adding a small correction to a large maximum.
- **B — Stable log-softmax (inspired by [[Barron et al., ](https://jonbarron.info/softmaxfix/)*[A Fix for Softmax and Cross-Entropy](https://jonbarron.info/softmaxfix/)*](https://jonbarron.info/softmaxfix/)):** Exclude one max element from each block's sumexp and use `log1p` during the global merge to preserve small corrections.
- **C — Stable residual computation:** Replace the `exp()`-based subtraction with `log_p + log(-expm1(log_q - log_p))` when `delta < 0`.

With A+B, the small LSE correction is preserved, but gap ≥ 18 still fails because `exp(delta)` rounds to `1.0`. Adding C resolves the empty-residual problem in all tested cases.

I think this FP32 approach could be worth comparing against the fp64 implementation, especially in terms of correctness and performance.

I’d be happy to contribute the implementation and tests. I could open a PR against your branch so the changes can be merged into this one, or, if you think it’s more appropriate, open a separate PR for the FP32 approach that references this one. Which would you prefer?
(AI assistance was used for the analysis and implementation; I reviewed and ran all the results above.)

- zyongye · comment · 2026-11-02T08:13:29Z · [source](https://github.com/vllm-project/vllm/pull/64242#issuecomment-6572302406)

We're folding this change into #65103 (draft), which takes the target log-sum-exp from a top-p cutoff kernel (#65101) and relies on the fp64 global combine here. Your commit is included as is, and you're listed as co-author on the follow-up commit described below.

One change on top: on GB300, whose fp64 throughput is a small fraction of fp32, the per-element fp64 math made block verification much slower. At 16 requests, K = 7, V = 200,064, top-p 0.95, `_compute_local_residual_mass_kernel` went from 25 µs to 1,565 µs and `_resample_kernel` from 18 µs to about 45 µs; the whole verify step ran at 0.25–0.49× of main.

In #65103 the global combine stays fp64 as here, but per-element log-probabilities are computed in fp32: the fp64 lse is split once per program into an fp32 pair and `x - lse` is taken as `(x - hi) - lo`. That subtraction is exact for tokens near the max, where the extra precision matters, so the near-max correction survives. Your `test_global_logsumexp_keeps_near_max_correction` passes, and block verification is back to fp32 speed.

If you'd rather land this here first, we can rebase #65103 onto it once the per-element math is fp32.
