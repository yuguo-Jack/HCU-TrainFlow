# [ROCm][MiniMax-M3] Backport #61889: fix sparse PA KV block count

[Upstream PR](https://github.com/vllm-project/vllm/pull/63270) · state: closed · merged: True

## Original PR description

## Purpose

Backport of #61889 (by @ykamiset, still open against `main`) to `minimax-m31-flash` (#63232). The commit is cherry-picked unchanged, author kept.

With an fp8 KV cache and `VLLM_ROCM_SHUFFLE_KV_CACHE_LAYOUT=1` (the AITER sparse PA path, which the ROCm mono decode `VLLM_ROCM_MINIMAX_M3_MONO=1` needs), the resolved LBHNC layout interleaves K and V pages in each block, so the V view is 8 pages shorter than K. aiter 0.1.26 `pa_decode_gluon` asserts equal K/V block counts, and the engine dies at startup. This branch's `Dockerfile.rocm_base` pins aiter v0.1.25, which has no such check, but the released `vllm/vllm-openai-rocm:minimax-m31-flash` image ships aiter 0.1.26. The fix passes K trimmed to V's page count; the dropped K rows are never addressed.

Not a duplicate: #61889 targets `main`; this carries the same commit to the M3.1 branch.

## Test Plan

MI355X, TP4, image `vllm/vllm-openai-rocm:minimax-m31-flash` (aiter 0.1.26), `amd/MiniMax-M3.1-Flash-Quark-MXFP4`:

```bash
VLLM_ROCM_USE_AITER=1 VLLM_ROCM_USE_AITER_MOE=1 VLLM_ROCM_USE_AITER_FUSION_SHARED_EXPERTS=0 \
VLLM_ROCM_SHUFFLE_KV_CACHE_LAYOUT=1 VLLM_ROCM_MINIMAX_M3_MONO=1 \
vllm serve amd/MiniMax-M3.1-Flash-Quark-MXFP4 -tp 4 --block-size 128 --disable-hybrid-kv-cache-manager \
  --moe-backend aiter --kv-cache-dtype fp8 --attention-config '{"indexer_kv_dtype": "fp8"}' \
  --compilation-config '{"cudagraph_mode": "FULL_DECODE_ONLY"}' --gpu-memory-utilization 0.85 \
  --reasoning-parser minimax_m3 \
  --speculative-config '{"method":"dspark","num_speculative_tokens":3,"attention_backend":"TRITON_ATTN","kv_cache_dtype":"fp8","draft_sample_method":"probabilistic"}'
```

1. Direct call of `minimax_m3_sparse_attn_decode_aiter` on a packed fp8 K|V cache (60000 blocks), 64 and 1024 requests x 4 query tokens, in the image.
2. Start the server above.

## Test Result

1. Without the change: `AssertionError: key/value caches must have the same number of blocks, but got key=torch.Size([960000, 1, 8, 16, 16]), value=torch.Size([959992, 1, 1, 128, 16])`; the server dies the same way at startup (`key=[8192, ...]`, `value=[8184, ...]`). With it: both batch sizes run, output finite.
2. With the change the server starts and serves (`MiniMax-M3 mono decode on: shared expert separate MXFP8`).
