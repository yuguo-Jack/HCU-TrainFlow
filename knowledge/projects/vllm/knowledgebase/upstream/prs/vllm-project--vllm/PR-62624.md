# [Feature][MoE] Add platform hook for routed-expert capture rows

[Upstream PR](https://github.com/vllm-project/vllm/pull/62624) · state: closed · merged: True

## Original PR description

## Overview

Add `Platform.get_routed_experts_local_rows` so out-of-tree MoE backends can restore their routing rows without replacing the shared capturer. This is a deliberately smaller alternative to #62441 for #61539.

Follow-up commits `ccb5f10`, `a43477b` and `27324c6` refine the change: the hook docstring covers stream/graph requirements and the MRV2 aux-output wiring, `docs/design/plugin_system.md` lists the optional hook, and the fallback test exercises the default TP gather. The capturer deliberately performs no validation of platform results; the buffer write is the contract.

## Claims

- A platform can return logical expert IDs in local token order, including an empty tensor. Only `None` selects the existing generic DP/TP restoration.
- Router selection and capture callback signatures, default restoration, and the capture-before-EPLB ordering remain unchanged.

## Validation

- **Linux regression, H20 cluster** (SGP H20e, 1x H20-3e on `vllm-sgp-h20-01`): exact base wheel `vllm-0.32.1rc1.dev118+g3897f95cf` from `wheels.vllm.ai`, with this PR's two production files overlaid onto the wheel:
  `pytest --import-mode=importlib -p no:cacheprovider -q --confcutdir=tests/model_executor tests/model_executor/test_routed_experts_capture.py`
  -> **55 passed in 19.26s** (`vllm 0.32.1rc1.dev118+g3897f95cf`, `torch 2.13.0+cu130`).
  Caveat: the shared H20 venv carries torch 2.13.0 while the wheel metadata pins 2.14.0. The module is CPU-only and imports/runs cleanly, but a torch-2.14 run remains outstanding.
- **Ruff 0.14.0** (the version pinned in `.pre-commit-config.yaml`), `ruff check` and `ruff format --check` on the changed files: PASS.
- `git diff --check`: PASS.
- CI `pre-commit`, `DCO` and test-tethering checks: PASS.
- Not validated: accelerator collectives, graph replay, downstream Ascend integration. The hook's collective path is only exercised by downstream platforms (tracked separately).

## Details

Some out-of-tree MoE prepare implementations transform the routing input before expert selection. Generic inference from row counts cannot recover uneven TP shards or padding inside shards reliably. The platform already owns the communication/layout details and can normalize the routing rows through this hook.

The default returns `None`. The capturer passes the forward context, DP rank and TP size, accepts platform results without evaluating tensor truthiness, and assigns them to the capture buffer. The interface documents token order, empty results, stream/graph requirements and collective participation. The hook itself introduces no device synchronization or tensor value reads.

**Alternative design and duplicate-work check:** #62441 addresses the same use case through explicit layout objects, shared gather/select logic, and changes to both router implementations. This proposal intentionally keeps those signatures intact and adds a single platform normalization seam instead. The tradeoff is that platform-specific gathering and row selection remain the platform's responsibility rather than a common declarative executor. These are competing designs for #61539, not two independently needed fixes; they should be evaluated as alternatives. Searches for `61539 in:body`, routed-expert layouts, and the hook name found #62441 and no existing Platform-hook implementation PR. The alternative is explained in [the RFC discussion](https://github.com/vllm-project/vllm/issues/61539#issuecomment-6284702593).

The production diff touches only the Platform interface and capturer. Existing tests are extended with multi-element, empty, zero-valued and fallback-padding cases. Downstream Ascend integration is separate and is not included or claimed as working here.

AI assistance was used for implementation, review, tests and this description.
