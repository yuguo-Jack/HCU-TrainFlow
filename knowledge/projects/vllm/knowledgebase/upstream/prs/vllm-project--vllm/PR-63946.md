# [Bugfix] Kimi K3: withhold truncated XTML marker fragments in content

[Upstream PR](https://github.com/vllm-project/vllm/pull/63946) · state: open · merged: False

## Original PR description



## Overview

Non-streaming Kimi K3 content leaked raw XTML control-marker fragments when generation was cut mid-marker (`max_tokens`); the streaming path already kept them out of content, so the two paths returned different content for the same output. Gives `_strip_response_content` the streaming path's holdback and first-close boundary. Fixes #63941.

## Claims

- Non-streaming and streaming now parse every prefix of a K3 turn identically: the in-tree sweeps cover four turn shapes exhaustively (967 cut positions + 967 delta-split positions) — 174 divergent cut positions pre-fix, 0 post-fix, every divergence a raw marker fragment in content. The issue's parser-level scan over six turn shapes (1,525 conforming-family + 107 stray-control cut positions) found 235 pre-fix (216 + 19), 0 post-fix.
- No marker text reaches `content` on the truncation axis this PR fixes: the sweeps assert identical, marker-free `content` at every cut and delta-split position — the assert checks for `<|`, the common prefix of every XTML delimiter, so partial fragments like `<|clos` are caught too. The `message_close` family (model omits `response_close`) is a known residual, unchanged by this PR — see Details.
- No behavior change for complete (untruncated) conforming turns. Non-conforming complete outputs change by design toward streaming's boundary — e.g. body text sitting after a complete close is now dropped, matching what streaming already does.

## Details

Root cause: the streaming path withholds a trailing partial control marker via `_partial_tag_overlap` (`_extract_response_content`); the non-streaming `_strip_response_content` had no equivalent, so a cut inside `<|close|>response<|sep|>`, `<|open|>tools<|sep|>` or the `<|close|>message<|sep|>` trailer stayed in `content` verbatim. Each marker is three tokens — two atomic delimiters plus the channel word (the delimiters are added tokens in Kimi K3's tokenizer, and `response`/`message`/`tools` are single BPE tokens) — so `max_tokens` cuts land inside them routinely.

Fix, in `_strip_response_content`:

- When no complete response close caps the text, trim a trailing partial marker with the same `_partial_tag_overlap` call and the same three-marker set (`response_open` / `response_close` / `tools_open`) the streaming path uses — parity by construction. A complete close keeps capping, so a body legitimately ending in `<` before a complete close is preserved exactly as streaming sends it.
- Cap at the first response close (`text[:m_close.start()]`) instead of stripping all occurrences and joining, which mirrors the streaming sendable boundary and stops trailer text after the close (e.g. a truncated `<|close|>message<|sep|>`) from leaking into content.
- Deliberately unchanged: `message_close` is not in the holdback set (neither path has it there). When a model omits `response_close` (reachable per #51399), a partial `<|close|>mes` trailer still surfaces in **both** paths identically — parity holds, the fragment still leaks — and the complete `<|close|>message<|sep|>` still leaks in **streaming** only (#51399/#54273, fix #51400 open). Adding `message_close` to one path alone would recreate the divergence in the opposite direction; this PR's mirrored set follows #51400 in lockstep.

Tradeoff: a body whose final character is a marker prefix (e.g. `… 5 <`) and whose generation ends exactly there is now withheld in non-streaming too — identical to what streaming already does, so the paths agree. The open draft #60642 flushes that same withheld tail at stream EOF instead (every character kept, raw marker text in `content`); the directions are mutually exclusive for mid-marker cuts with no complete close, so whichever wins should win on both paths — withhold implemented here per #51400/#54273/#47903's framing, maintainer's call.
