# [Bugfix][Structured Output] Honor resolved backends in mixed requests

[Upstream PR](https://github.com/vllm-project/vllm/pull/62246) · state: open · merged: False

## Original PR description

## Overview

Compile each structured-output request with its validated backend and normalize native mask storage to the model logits vocabulary. Related to #43920 and #55152.

## Claims

- Cache compilers by the resolved backend name without changing explicit configuration or the `auto` validation/fallback policy.
- Give each native backend its exact batch work-buffer shape. Transport model-width masks; crop the native/model intersection and clear constrained padding bits. Zero-padding for a narrower native buffer is defensive and untested. Equal-width backends fill the model buffer directly.
- Allocate work buffers before parallel fills, with independent row slots. Preserve shutdown-before-destruction and clear compiler/mask caches afterward.

## Validation

Native CPU command (cached tokenizer/config assets; no model weights or GPU):

```bash
VLLM_TARGET_DEVICE=cpu HF_HUB_OFFLINE=1 .venv/bin/python -m pytest \
  tests/v1/structured_output/test_structured_output_manager.py -vv
```

Final candidate: **83 passed, 1 existing expected xfail**, no failures/errors or resource skips. The original 17 mixed-order/lifecycle controls are included, not additional: 28 passing cases comprise those 17 plus 11 new controls. The rest covers existing reasoning, speculative, parallel-fill and outlines flows. Applicable normal pre-commit hooks, including mypy and pinned Ruff 0.14.0, pass without bypass.

With identical final new tests, posted draft `ab6b402398f1f621eac936cdc16907c72519fa1f` fails all 11: eight real native width failures, two invalid reasoning-end indices, and one oversized guidance-only model-output mask. Removing just the candidate's tail-bit clearing makes its dedicated native tail test fail. Earlier intermediate runs and test-fixture mistakes are retained separately and are not extra coverage.

The mixed batch uses real cached GPT-2 + 64 HF-added tokens: model vocabulary 50257, tokenizer 50321; guidance allocates 1573 int32 words and xgrammar 1571. Both initial orders and synchronous/asynchronous compilation run through serial and existing parallel fill paths. All three requests are submitted before waiting, including two guidance requests whose masks demonstrably differ. Every active row is compared to an independent exact-shape native mask across generation steps; wrong tool names/invalid JSON are rejected.

The tail test additionally loads a real serialized GPT-2 BPE vocabulary extended by 64 ordinary core tokens: a native-allowed token beyond model vocabulary must be removed from the transported mask. Ordinary HF-added/control tokens are already suppressed by llguidance, so that earlier fixture did not establish this adversarial premise. No compiler/native-mask stubs or cleanup bypass are used; the reasoning-index unit cases reuse the existing synthetic reasoner fixture.

Packages: PyTorch `2.14.0+cpu`, xgrammar `0.2.8`, llguidance `1.7.6`, Transformers `5.19.0`, Tokenizers `0.23.3`. Tests run on the candidate based on `0c5dd18e7a0ace18d99438fb16b8375572ea76b5`, not a newer upstream/merge result. No model/GPU/HTTP serving evaluation, throughput or quality claim.

## Details

Validation may choose guidance for JSON features and xgrammar for modern tool structural tags. Previously the manager reused the first compiler; after fixing that, reusing its native mask shape was still unsafe. Guidance can build its native tokenizer for `max(model vocabulary, tokenizer length)`, whereas xgrammar's HF path uses model vocabulary. Both native APIs enforce exact work shapes, so a merely wider shared tensor is also invalid.

The manager now keeps exact per-backend batch work buffers and a model-width output. Each fill uses its own indexed row, then copies only the representable intersection. Zero-padding for a narrower native buffer is defensive and untested. This is storage adaptation, not a compiler fallback or permission to generate tokenizer-only IDs. Invalid reasoning-end IDs are excluded before native validation/indexing. Unequal native widths need extra CPU mask storage/copying; no performance benchmark is claimed.

This differs from #49625, which rejects later requests resolving to another backend. It does not add modern-tag support to explicitly configured guidance (#55153) or change Rust/gRPC lowering (#61892).

Native coverage remains GPT-2 and its documented synthetic vocabulary variants. Mistral/Tekken, other tokenizer implementations, additional backend combinations, model execution and serving remain unqualified. This is **not a qualified v0.31 backport**: the original posted diff failed the v0.31 `db9527a46873454610df6dbedf79a36d6bf1a7f6` cleanup hunk; the updated contribution has no new clean-apply/backport/serving qualification. No hunk trimming or parent substitution is proposed.
