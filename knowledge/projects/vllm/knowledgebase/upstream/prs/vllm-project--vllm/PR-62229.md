# [Bugfix][Frontend] Listen on IPv4 and IPv6 when --host is unset

[Upstream PR](https://github.com/vllm-project/vllm/pull/62229) · state: open · merged: False

## Original PR description



## Overview

Without `--host`, `vllm serve` binds an IPv4-only socket, so the server is unreachable over IPv6 (#22816, closed by the stale bot, still reproducible on main). This makes the unset host bind a dual-stack socket instead. Supersedes #22823 with a smaller, single-socket approach.

## Claims

- With no `--host`, the OpenAI API server (and the render / gRPC listeners that share `create_server_socket`) accepts connections on both IPv4 and IPv6.
- Explicit `--host` values are unchanged: an IPv4 address still gets an `AF_INET` socket, an IPv6 address an `AF_INET6` one.
- Hosts without dual-stack support (`socket.has_dualstack_ipv6()` is false) keep today's IPv4-only behaviour.

## Validation

- New `tests/entrypoints/launchers/test_server_socket.py`: `test_unspecified_host_accepts_ipv4_and_ipv6` fails on main (`ConnectionRefusedError` on `::1`) and passes here. The IPv6 part is skipped when the host has no IPv6 loopback, which is what broke #22823 in CI.
- `pytest tests/entrypoints/launchers/{test_server_socket,test_cli_args,test_balanced_accepts,test_launch_cli}.py` → 185 passed.
- End-to-end with `vllm launch render --model Qwen/Qwen3-0.6B --port 18765` (no `--host`), macOS 15 / Python 3.12:

  | | `curl http://127.0.0.1:18765/health` | `curl http://[::1]:18765/health` |
  |---|---|---|
  | main | 200 | connection refused |
  | this PR | 200 | 200 |

- `pre-commit run` on the changed files passes.

## Details

- Root cause: `setup_server()` passes `(args.host or "", port)`, and `create_server_socket()` picks `AF_INET` for any non-IPv6 host string, including `""`.
- Fix: when the host is empty and the platform supports it, bind an `AF_INET6` socket to `::` with `IPV6_V6ONLY=0`. It is still a single listening socket, so the existing single-`sock` plumbing (multi-API-server `SO_REUSEPORT`, Rust-frontend listener inheritance, render/snapshot entry points) is untouched. #22823 instead returned a list of sockets, which no longer fits that plumbing.
- `SO_REUSEPORT` on the dual-stack socket behaves as before on Linux (all API-server processes bind the same `[::]:port`). I validated on macOS only and have not run the multi-API-server or Rust-frontend paths on Linux; CI covers the former.
- Related: #39619 also touches `create_server_socket` (at its old path) for IPv6-only hosts; with this change an unset host already works there too, since `::` binds without IPv4.
- Credit to @smarterclayton for #22823 and the original report.
