# [Bugfix][SleepMode] Exact-size, reusable pinned CPU backup for level-1 sleep

[Upstream PR](https://github.com/vllm-project/vllm/pull/64630) · state: closed · merged: True

## Original PR description

## Problem

Level-1 sleep backs up every cumem allocation to host memory with `torch.empty(size, pin_memory=True)`. torch's `CachingHostAllocator` rounds each pinned block up to a power of two and keeps freed blocks in its cache, so the level-1 backup costs up to ~2x the offloaded bytes in host memory, and that memory is never returned to the OS. On Mistral Large 4 at TP8 the backup is 85.19 GiB per GPU, which turned into roughly +578 GiB of host memory per node.

## Root cause

The backup size is chosen by the caching host allocator, not by the allocation. The old code already kept the memory across wake-ups: the freed pinned block stayed in the cache and was handed back on the next sleep, which is why repeated sleeps were fast. The bug is the rounding. Nothing in this path asks for the cache.

## Fix

Data model: `AllocationData.cpu_backup_tensor` is the allocation's host backup buffer, one per allocation.

- Lifetime: created exact-size on the first level-1 offload of that allocation, reused on every later offload, released only when the allocation is freed or its contents are discarded (level-2 sleep, tags not offloaded, `discard()`).
- Validity is derived, not stored: wake restores an allocation iff it is asleep and has a buffer.
- Invariant: asleep + buffer => the buffer holds this sleep's data. Every transition to asleep (`sleep` and `discard`) goes through one helper, `_put_to_sleep(ptr, data, offload)`, which either copies into the buffer or releases it before unmapping. So a buffer left over from an earlier offload can never be restored after a discard. The existing already-asleep policy checks (`cpu_backup_tensor is not None` on asleep allocations) keep their meaning unchanged.
- CUDA/ROCm (`cumem.py`): the buffer is an anonymous `mmap` wrapped with `torch.frombuffer` and pinned with the existing `libcudart.cudaHostRegister` wrapper. If registration fails, the error is drained with `cudaGetLastError`, a warning is logged once and the backup stays pageable, the same fallback as the other `cudaHostRegister` callers (`shm_tensor_arena.py`, `ec_shared_region.py`). Release unregisters only a pinned buffer, ignores the return code (draining any error) and never raises, since it also runs from the allocator's free callback; then the reference is dropped, which unmaps it.
- XPU (`xpumem.py`): same single-field reuse/release semantics with its existing pinned torch tensor. Exact-size pinning is not available there.

No config, env var, API or protocol change. None is needed: the old behavior already kept the backup memory between sleeps, and this keeps it at exactly the offloaded size.

## Results

Qwen3-8B, 1x GB200, `enable_sleep_mode=True`, 4 cycles of `sleep(level=1)`, `wake_up()` and greedy generate. Host memory is node `MemTotal - MemAvailable` relative to before the first sleep.

| | host asleep | host awake | first sleep | later sleeps | wake | outputs identical |
|---|---|---|---|---|---|---|
| main | 23.00 GiB | 22.99 GiB | 1.16 s | 0.16-0.18 s | 0.13-0.14 s | yes (4/4) |
| this PR | 16.92 GiB | 16.92 GiB | 0.84 s | 0.15 s | 0.13 s | yes (4/4) |

Host memory is flat across cycles in both cases. Sleep and wake are as fast as before.

## Test plan

No new test function; the existing tests in `tests/basic_correctness/memory/cumem/test_cumem.py` are strengthened with deterministic checks (no RSS thresholds). Every level-1 backup must be exactly its allocation's size and page-locked, and torch's pinned host caching allocator must not be used across sleep (`torch.cuda.host_memory_stats()["allocated_bytes.allocated"]` unchanged).

- `test_release_kv_cache_memory_preserves_generation` (kv-only / sleep-1 / sleep-2) and `test_sleep_with_only_weights_asleep` (first x second level): 3 and 2 sleep/wake cycles with greedy output identical to pre-sleep every cycle. Worker-side state is read via `collective_rpc`: offloaded tags hold exact pinned backups and others hold none; the same buffers are kept after wake and reused on the next sleep; a level-1 then level-2 cycle leaves weights with no backup.
- `test_basic_cumem` (`pinned` / `register-fails`): 3 level-1 cycles with changing data, same buffers reused. A sleep that does not offload the tag releases (unregisters) its backup. Freeing an allocation releases its backup. In `register-fails`, `cudaHostRegister` returns an error: sleep/wake data is still correct, backups are pageable, a warning is logged, and release never calls `cudaHostUnregister`.
- `test_discard_tags`: `discard()` releases the kv backup, so the following wake has nothing stale to restore; weights keep and reuse theirs.
- `test_level2_discards_ordinary_tensor_with_weights_tag`: level-1 cycle, then a level-2 style sleep releases the backup; the poisoned wake proves nothing was restored.
- `test_reentered_tag`: freeing an offloaded allocation while awake releases its backup.
- `test_runtime_state_survives_sleep`: runtime backups are exact, pinned and kept at both levels without the host caching allocator.

## Test result (GB200)

- With this PR: full `test_cumem.py` 22 passed, 3 runs in a row; `test_basic_cumem[pinned]` and `test_basic_cumem[register-fails]` also pass run alone. `register-fails` fails on the previous revision of this PR, which raised on a registration failure.
- Same tests against main's `cumem.py`: 13 failed, 8 passed. Failing: `test_basic_cumem`, `test_release_kv_cache_memory_preserves_generation[sleep-1,sleep-2]`, `test_sleep_with_only_weights_asleep[all 4]`, `test_runtime_state_survives_sleep[sleep-1,sleep-2]` (torch host caching allocator used during sleep: +32 MiB to +2.5 GB), and `test_discard_tags`, `test_reentered_tag[both]`, `test_level2_discards_ordinary_tensor_with_weights_tag` (backups dropped on wake). With the host-stats check neutralized, the same 13 still fail on backup reuse.
- Engine smoke: see the table above.

XPU change is untested on hardware.

Follow-up option: an opt-in "release the backup on wake" for host-memory-constrained colocated RL is one extra `release_cpu_backup` after the restore copy in `wake_up`. The invariant still holds because it only constrains asleep allocations. Not part of this PR.
