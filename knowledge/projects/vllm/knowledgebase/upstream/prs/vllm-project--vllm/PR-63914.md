# [Bugfix][DSv4.1] Keep the specialized decode's FlashInfer paths on newer FlashInfer

[Upstream PR](https://github.com/vllm-project/vllm/pull/63914) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

The DeepSeek-V4.1 `latency_specialized` decode (#61868) turned on four of its FlashInfer paths only when `flashinfer-python` was exactly 0.7.2. #63466 moved `requirements/cuda.txt` to 0.7.2.post1, so on `main` all four have been off since then: the server logs a warning per path and runs the stock path, and the numerics test that covers two of them skips. This PR gates each path on what it actually needs, so they run on 0.7.2.post1 and later releases. Thanks to @mgoin for catching it ([comment](https://github.com/vllm-project/vllm/pull/61868#discussion_r4380766753)).

## Validation

On one GB300 tray with `main`'s FlashInfer (0.7.2.post1):

- `test_numerics.py` (4 GPUs) passes instead of skipping; it compares the publishing `wo_b` GEMM and the MXFP8 layer input with FlashInfer's own GEMM and quantize bitwise.
- `test_kernels.py::test_sparse_mla_persistent_kv_counters` and `::test_low_latency_mxfp8_mm`: 18 passed, none skipped.
- `vllm serve` with `decode_backend=latency_specialized` logs "specialized decode on" and no fallback warning, and answers a completion and a chat smoke request correctly.

## Details

- Publishing `wo_b` GEMM and MXFP8 layer input (they use FlashInfer internals): FlashInfer ≥ 0.7.2 instead of == 0.7.2. Those internals are unchanged in 0.7.2.post1, and `test_numerics.py` now runs on the pinned release, so a later change to them fails the test instead of turning the paths off.
- Pinned MXFP8 tactics: no version gate; they already fall back to tuning every tactic when FlashInfer does not list the pinned one.
- Sparse-MLA KV counters: on the decode taking `multi_ctas_kv_counter_buffer`.
