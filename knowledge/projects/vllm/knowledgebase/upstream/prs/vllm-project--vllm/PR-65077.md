# [Perf][Quantization] Honor FP8 activations for Humming linear on SM100/SM110

[Upstream PR](https://github.com/vllm-project/vllm/pull/65077) · state: open · merged: False

## Original PR description

## Overview

Honor requested FP8 activations in Humming dense linear layers on SM100–SM119, including MXFP8 group-32/E8M0 schemas, instead of falling back to BF16. Bump `humming-kernels` to 0.1.19 for the required dense-tuner correctness fix ([humming#178](https://github.com/vllm-project/humming/pull/178)).

## Claims

- Quark MXFP4/MXFP6 checkpoints requesting FP8 dynamic activations (including MXFP6/MXFP8 requests, converted to FP8 E4M3) now actually run FP8 activations in dense linear layers on SM100/SM103. Previously these were silently downgraded to BF16 by two gates in `check_and_fallback_input_schema`: a blanket sub-16-bit "deprecated" predicate on SM100–SM119, and an SM120-only exception for the MXFP8-style group-32/E8M0 schema.
- MXFP6 GEMMs are 1.4–1.9× faster at decode batch sizes and ~1.7× at the measured prefill size (B300, CUDA-graph replay device time).
- Wikitext perplexity stays within the existing CI tolerance on a real MXFP6 checkpoint. MoE grouped GEMMs keep the BF16 fallback on SM100–SM119.

## Details

Root cause: the gates date from before Humming had performant FP8 on SM10X ("Humming has not yet implemented high-performance FP8 computation on SM10X and SM11X"). As of humming-kernels 0.1.18/0.1.19 the dense path has native FP8 UMMA support — block-scaled (mxf8f6f4) for MX-style group-32/E8M0 scales, epilogue-scaled for per-token/per-channel — and it is faster than the BF16 path at every measured batch size under CUDA graphs.

This PR exempts FP8 dtypes from the dense-path deprecation and lowers the MXFP8 groupwise exception to SM100. The MoE call sites (expert selection in `HummingMoEMethod.__init__` and weight processing in `utils/humming/moe.py`) pass `allow_fp8_sm100=False` because Humming's grouped-GEMM FP8 path on SM100 is not yet validated (the two-CTA tuner bug below was found and fixed on the dense path; the MoE path has not been exercised). FP4 and other sub-16-bit dtypes keep their gates; SM90 and SM120+ behavior is unchanged.

The pin bump to 0.1.19 is required: 0.1.18's SM100 dense tuner could emit invalid two-CTA UMMA configs (`block_m % 16 != 0`), crashing e.g. a 6144×2048 MXFP6 + FP8-activation layer at engine startup on SM103 (fixed upstream in [humming#178](https://github.com/vllm-project/humming/pull/178)).

Tradeoffs: in eager mode the FP8 path adds ~70 µs/call of Python dispatch overhead (Humming's `process_input`), the same overhead the already-ungated per-token FP8 path pays on SM90; under CUDA graphs it disappears. FP8 E4M3 activations add quantization noise vs BF16 — measured impact is within the existing CI tolerance (see Accuracy).

Caveat for developers flipping this code path in place: vLLM's AOT compile-cache key does not include the resolved activation schema or the humming version, so reusing a warm cache across this change under the same vLLM version string can load a stale artifact and fail with a size/stride assert. Clear the compile cache when switching; release upgrades are unaffected (the version string is part of the key).

Related PRs:

- [#59460](https://github.com/vllm-project/vllm/pull/59460) makes activation-quantization fallbacks explicit/strict; complementary, does not un-gate FP8 on SM100.
- [#61666](https://github.com/vllm-project/vllm/pull/61666) adds compressed-tensors MXFP6 support; orthogonal (these checkpoints route here once supported).
- [#64802](https://github.com/vllm-project/vllm/pull/64802) bumps humming-kernels to 0.1.19 independently; this PR's pin bump will be dropped if that lands first.
