# [Kernel] Exact top-p cutoffs and kept log-sum-exps for bf16 logits

[Upstream PR](https://github.com/vllm-project/vllm/pull/65101) · state: open · merged: False

## Original PR description

## Overview

Adds `topp_cutoffs_lse`, a CUDA op (SM90 and datacenter Blackwell) that turns each bf16 logit row into its exact top-p cutoff, keeping every token tied at the cutoff, and the fp64 log-sum-exp of `x / T` over the kept tokens, in one launch. Nothing calls it yet; #65102 uses it to apply top-p to speculative-decoding verification rows as the rejection kernels load them. Part of #61024; 2/4 of a stack (see the end).

**Update (2026-11-02):** the second commit reworks the kernel after an ncu pass. It picks the cluster size per batch, halves the histogram's cost and adds a fixed-point tier ahead of the fp64 fallback. It gives the same cutoffs bit for bit and is 2.4× faster than the first commit from 128 rows up. The third makes every CTA of a cluster start before a peer writes its shared memory (found by racecheck).

**Fix (2026-11-03):** the op now reads `expanded_idx_mapping` as int64, the dtype Model Runner V2 has built its index mappings in since #60736. It accepted only int32, so with #65102 the first verification chunk that took the top-p path raised `expanded_idx_mapping must be int32` and took EngineCore down. The tests and the benchmark built int32 mappings, so they missed it; it was found by an end-to-end serving test of the stack, and #65102 now adds an `LLM` test that runs the op on the model runner's own mappings.

## Claims

- One launch replaces what verification runs for top-p rows today: an fp32 copy of the target logits, the temperature kernel and the Triton top-k/top-p mask. At V = 151,936: 763 → 43 µs for 256 rows (64 requests, K = 3) and 2,470 → 137 µs for 1,024; 12 µs for one row. At V = 202,048: 1,099 → 51 µs for 256 rows (CUPTI, cold L2, GB300).
- Exact: cutoffs match an fp64 reference on every row tested, ties included, and do not depend on reduction order. The log-sum-exp is within 1.2×10⁻⁷ of fp64 (within one ulp in the rare rows settled by the precise tier); the max token's log-probability it implies is never positive.
- A row whose cutoff falls inside the integer search's error band costs about 10 µs more, where the first commit's fp64 fallback cost about 155 µs: the band is redone in fp32/integer arithmetic with a rigorous bound, and only rows within ~10⁻¹³ of the boundary run in fp64 (slow on GB300: FP64 runs at 1/64 of the FP32 rate, and one fp64 `exp` takes ~790 cycles per warp).
- Works for every current vocabulary; tested up to 262,144.

The 4 skips are the cases a cluster size cannot hold.

Beyond the tests, a standalone harness compared the reworked kernel bit for bit with the first commit's on 300-row synthetic batches (V = 32,000 to 262,144), 1,024 real Qwen3-0.6B verify rows per profile (creative writing, math chat), mixed greedy / top-p = 1 / top-p batches, NaN, ±inf, all-tied and strided rows, at C ∈ {1, 2, 4, 8}. Every cutoff is identical, and so is every log-sum-exp outside the precise tier's rows. compute-sanitizer racecheck reports 0 hazards at C ∈ {1, 2, 4, 8}, with and without each fallback forced.

## Details

- **Why a histogram.** A bf16 row takes at most 65,536 distinct values, so the nucleus is fixed by a count histogram over the 16-bit order key. Each row gets one thread-block cluster of C CTAs. Each CTA counts its slice of the row into its own shared-memory histogram (u16 counts in pairs) and turns its occupied 256-key blocks into masses for rank 0. One warp of rank 0 then finds the boundary block, then the boundary key.
- **Cluster size per batch.** A cluster has a fixed cost of ~8-10 µs (barriers and serial stages), and only one CTA fits per SM. The op therefore picks C from the device's cluster occupancy and a per-stage cost model: on GB300, 4 CTAs per row up to 36 rows, 2 up to 76, then 1 (152 rows per wave). With one or two CTAs a slice can exceed 65,535 tokens, so the counts are checked against the slice length; if a count wrapped, the slice is recounted with every wrap recorded.
- **Histogram.** It was integer-ALU bound. Both bf16 halves of a word are now converted to keys with one `prmt` and one `lop3`, and the key range is tracked with packed u16 min/max. NaN and `-inf` are counted into keys that are never read, and `-0` is merged afterwards. The histogram is now limited by shared-memory atomics.
- **Exactness.** Masses are `floor(2^40 · exp(x̃ - x̃max))` summed as int64, so sums are order-independent. Each mass carries an error bound for `ex2.approx`. If the target falls within that bound of the boundary key's interval, the row is redone with `2^62 · exp(x̃ - x̃max)` computed to ~2⁻⁴⁵ in fp32 float-float plus a 64-entry table, summed exactly in 128 bits with a rigorous accumulated bound (0 violations on 4.2M keys against fp64; the 200 worst against mpmath at ≤ 0.022× the bound). Only rows still inside that bound run the fp64 sums, spread over every warp of the cluster in the first commit's summation order. Both fallbacks keep the terms of the integer search's boundary block as they compute them, so their descents skip recomputing them. Fallback rows are rare: none of 2,048 real rows, 9 of 1,024 bf16 Gaussian rows with σ = 3.
- **Per-key loops.** Every key's mass is computed once, by the CTA that counted it. The loops are specialized at compile time per block: one sign per block, temperature 1 (no division), and only blocks 0 and 255 hold invalid keys.
- **Log-sum-exp.** The search already holds the kept mass Z ≥ 2⁴⁰ (the max key alone contributes 2⁴⁰). With Z = 2ᵉ(1 + f) split from the exact integer, `lse = x̃max + (e - 40) ln 2 + log1pf(f)`, in fp64. This keeps corrections down to 2⁻⁴⁰ of the max token's weight and guarantees `x̃max - lse ≤ 0`.
- **Temperature contract.** `x̃ = x / T` rounded to nearest (`__fdiv_rn`), matching `tl.div_rn` in Triton (#64496 moves MRV2's temperature kernels to `tl.div_rn`). Any kernel that combines this lse with its own `x̃` must scale the same way.
- **Index mapping.** `expanded_idx_mapping` is int64, as the model runner builds it; each entry is narrowed to an `int` request index.
- **Test hooks.** `cluster_size` (0 = automatic) and `force_fallback` (1 = precise tier, 2 = fp64) replace the first commit's `force_fp64`; nothing outside this stack calls the op.
- **Limits.** bf16 logits only; SM90 and 10.x (`9.0a;10.0f;10.3f`), since each CTA needs ~150-220 KB of shared memory and thread-block clusters. Not built for sm_12x. The cluster occupancy is queried per device, but the per-stage costs in the model were measured on GB300.
- **Not duplicating.** #65004 (Triton histogram-bracket top-p, opened 2026-11-01) targets the same verify batches in the shared Triton top-k/top-p mask: four streaming passes per row, ties at the boundary broken by index, Kahan-compensated fp32 sums (it reports matching float64 except where the boundary mass is within fp32 rounding of p), no log-sum-exp. This op is one launch, keeps every tie, is exact via integer sums plus bounded fallbacks, and returns the log-sum-exp the rejection sampler needs; it is bf16/SM90+ only. #48928 (FlashInfer AIR top-p rejection sampling) and the sort-based Triton mask are the other existing paths. Searched open PRs for "top-p histogram", "topp cutoff", "top-p rejection sampling", and #61024.
- **Stack.** 1 #65100 resample skip (independent) · **2 this** · 3 #65102 top-p as target logits load · 4 #65103 target log-sum-exp from this op. #65104 (draft log-sum-exp from the drafter) closed: a net loss once the drafter's cost is counted.
