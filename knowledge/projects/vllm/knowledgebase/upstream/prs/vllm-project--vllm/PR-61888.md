# [Distributed] Opt-in FP16 partial sums for tensor-parallel row-parallel layers

## Overview

With tensor parallelism every row-parallel layer (`o_proj`, `down_proj`, linear-attention `out_proj`) rounds its per-rank partial sum to BF16 before the all-reduce, while a single GPU rounds the full sum once. The extra rounding is small on average but explodes where the two halves cancel, which is frequent: on real Qwen3-4B / Qwen3-14B activations at TP=2, outputs whose error exceeds 1% of the row's RMS occur **4.75x / 5.53x as often as on one GPU**. Converting the BF16 partials to FP32 before the all-reduce (#50972) cannot help at TP=2: the rounding has already happened, and the result is bit-identical.

This PR adds `VLLM_TP_FP16_PARTIAL_SUMS=1` (off by default): the row-parallel GEMM writes its partial sum in FP16 (8x finer than BF16, same bytes on the wire), the all-reduce runs in FP16, and the output is rounded to BF16 once, after the sum, as on one GPU; an exact power-of-two prescale (2^-2 by default) keeps partial sums far from the FP16 range limit. The large-error events return to the single-GPU level, the BF16 output gets measurably closer to an FP32 reference than both TP=2 today and TP=1, and throughput does not change.

**Not a duplicate of #50972.** That PR upcasts the BF16 partial sums to FP32 before the all-reduce; at TP=2 this is bit-identical to today (`bf16(a) + bf16(b)` is exact in FP32), because the extra rounding happens earlier, when each rank's GEMM writes BF16. This PR changes the precision of the partial sums themselves. Related: #40725 (did not reproduce on our setup, see Details), #57042.

## Claims

- Opt-in FP16 partial sums for tensor-parallel row-parallel layers: unquantized BF16 layers, NVFP4 CUTLASS and block-scaled FP8 CUTLASS/Triton kernels. Default behavior unchanged.
- At the source (real activations, TP=2 emulated per layer): errors > 1% of the row RMS per token, Qwen3-4B 712 -> 155 (one GPU: 150), Qwen3-14B 1,441 -> 271 (one GPU: 260).
- At the output, Qwen3-4B BF16, 292k tokens: NLL excess over an FP32 reference +0.00062 -> **+0.00039** (TP=1: +0.00058); agreement with TP=1 at near-tied tokens improves (p 0.012-0.049).
- No throughput change (Qwen3-4B TP=2 decode: batch 1 -0.9%, batch 16 +-0%); bytes exchanged unchanged; GSM8K unchanged (`tests/evals`, see Validation).
- Quantized models (FP8, W4A4): same source-level reduction; output-level differences at the edge of significance or within activation-quantization noise in our measurements.

## Details

**Root cause.** A row-parallel layer at TP=2 computes `a = x[:, :K/2] W[:, :K/2]^T` and `b = x[:, K/2:] W[:, K/2:]^T` with FP32 accumulation, writes them as BF16, and all-reduces. Rounding `a` and `b` separately adds an error proportional to `|a| + |b|`, not to `|a + b|`; where the halves cancel, it dominates. `bf16(a) + bf16(b)` is exact in FP32, so upcasting the BF16 partials before the all-reduce leaves the result bit-identical at TP=2 (checked on 2^20 random pairs).

**Change.** `RowParallelLinear` decides once at construction (`_fp16_partials_mode`) whether FP16 partials apply: TP > 1, `reduce_results`, BF16 params, CUDA, not batch-invariant, and either the default unquantized GEMM (computed here with `torch.mm(..., out_dtype=float32)` then scaled, saturated and cast to FP16, since there is no BF16 -> FP16 GEMM output) or a quantized kernel declaring `supports_partial_sum_dtype` (NVFP4 CUTLASS; block FP8 CUTLASS/Triton). Those kernels read `layer.partial_sum_dtype` / `partial_sum_scale`, write FP16 directly and fold the scale into parameters they already take (NVFP4 `alpha`, FP8 weight block scales). After the all-reduce the output is cast to BF16 and multiplied by 2^k. No host synchronization is added in forward (all decisions are Python values fixed at construction); the default path is unchanged.

**Tradeoffs / limits.** On Hopper (SM90) and SM100, where the all-reduce + RMSNorm fusion pass is enabled by default, the FP16 all-reduce no longer matches the fused pattern, so enabling the flag there trades that fusion for accuracy; we could not measure it (no such hardware). FP16 range: values that still exceed 65504 * 2^k saturate instead of becoming inf. Partials below 2^-14 * 2^k lose relative precision to FP16 subnormals (absolute error <= 2^-24 * 2^k, far below the BF16 rounding of normal rows). Not covered: other FP8/NVFP4 kernels (DeepGEMM, the default block-FP8 kernel on SM120, Marlin, FlashInfer), the MoE expert reduction, sequence-parallel reduce-scatter. Measured at TP=2 only (two GPUs); at TP=N each rank rounds 1/N of the sum, so the excess is expected to grow with N. The 2-GPU test runs where the existing `test_comm_ops.py` TP=2 tests run; the model-level validation above ran outside CI. Possible follow-ups we left to the maintainers' judgement: precomputing the scaled `alpha` / weight scales instead of scaling per call, and a single output-dtype signature for all block-FP8 kernels (today only the two covered kernels implement `apply_block_scaled_mm_out`).

**Origin.** We found this while investigating why TP=2 runs of [capy-flash](https://github.com/ValerioDolci/capy-flash) (Apache-2.0, Qwen3.8-Flash-Next NVFP4 with tensor parallelism over PCIe on two consumer GPUs) drifted from a single-GPU reference; there, FP16/FP32 partial sums removed ~85% of the TP=2-vs-single-GPU distance to the reference logits. All numbers above are measured on vLLM.
