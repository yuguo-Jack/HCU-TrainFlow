# [Metrics][KV Offload] Fill vllm:kv_offload_config_info with the CPU cache capacity

[Upstream PR](https://github.com/vllm-project/vllm/pull/53902) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Purpose

GPU KV-cache capacity is observable. `num_gpu_blocks` and `kv_cache_size_tokens`
are labels on `vllm:cache_config_info`. The CPU offload tier exports only usage
(`vllm:kv_offload_cpu_cache_usage_perc` and the read/write variants) and no
capacity. The size is not recoverable externally either, because it depends on
`blocks_per_chunk`, page alignment, and whether a replicated layout deduplicates
the per-worker copies. All three are connector-internal.

This PR fills `vllm:kv_offload_config_info` with the CPU cache facts. The gauge,
the label rendering and the emission call come from #56867, the generic
config-info PR. The CPU side adds four labels:

| Label | Meaning |
|---|---|
| `cpu_num_chunks` | Chunk slots in the tier. Chunks, not GPU blocks. |
| `cpu_blocks_per_chunk` | GPU blocks in one chunk: the chunk-to-block conversion factor. |
| `cpu_kv_cache_size_bytes` | Size of the tier in bytes: `cpu_num_chunks` times the page-aligned bytes of one chunk. |
| `cpu_kv_cache_size_tokens` | KV tokens the tier holds for requests of `max_model_len` tokens. It is computed like the GPU `kv_cache_size_tokens`. |

No name carries a tier index, so a CPU fact reads the same under
`CPUOffloadingSpec` and under `TieringOffloadingSpec`. The gauge is per engine.
Sum across the `engine` label for the instance total. The Info shape is the
extensible container the reviewers of #49307 asked for.

### `cpu_kv_cache_size_tokens`

The tier is content-addressed (`OffloadKey = block_hash + group_idx`), so there is
no per-request allocation to divide by, and no analogue of the GPU
`max_concurrency`. The token capacity depends on the request length. The label
fixes the length at `max_model_len`, as the GPU `kv_cache_size_tokens` does:

```
chunks_per_request       = sum over groups of min(cdiv(max_model_len, tokens_per_chunk), cap)
cpu_kv_cache_size_tokens = num_chunks * max_model_len // chunks_per_request
```

Both `tokens_per_chunk` and `cap` are per group. `tokens_per_chunk` is
`blocks_per_chunk * tokens_per_block` of that group. `cap` is the chunks of that
group the tier keeps for one request: `None` for attention that reaches back
without a bound, `cdiv(window, tokens_per_chunk)` for a sliding window, and 1 for
Mamba. A capped group holds a fixed number of chunks however long the request
grows.

Two values cross the `OffloadingConfig` boundary for this:
`OffloadingGroupConfig.sliding_window_size_in_chunks` and
`OffloadingModelConfig.max_model_len`. `build_offloading_config` computes the first
one with `get_sliding_window_size_in_chunks`. The connector scheduler now reads the
same field, so the value has one source. Both new fields have a default, so a
spec that does not read them does not change.

`None` covers two cases: a `max_model_len` of 0, and no KV cache group at all. Zero
chunks reports `0`, not `None`, because zero slots hold exactly zero tokens.

`CPUOffloadingInfo.from_config(config, num_chunks, kv_bytes_per_chunk)` builds the
labels. The CPU spec builds it once as `cpu_info`, and passes it to the manager
as the last keyword argument `info`. `TieringOffloadingSpec` inherits `cpu_info`
and passes it to its primary tier.

### Why this estimate

The GPU side answers the same question in the same three steps.
`get_kv_cache_capacity` (`kv_cache_utils.py:2291`) builds `kv_cache_size_tokens`
like this:

```
num_blocks_per_request = sum over groups of cdiv(max_memory_usage_bytes, page_size_bytes)
max_concurrency        = num_blocks / num_blocks_per_request
kv_cache_size_tokens   = int(max_concurrency * max_model_len)
```

Sum the per-request cost over the groups, divide the pool by that sum, multiply by
the request length. The formula above does the same, with chunks in place of blocks.

The per-group cap matches too. `SlidingWindowSpec.max_memory_usage_bytes` calls
`max_admission_blocks_per_request`, which bounds a windowed group by its window
(`kv_cache_interface.py:716`). `MambaSpec.max_memory_usage_bytes` charges one page
for each request in the default cache mode (`kv_cache_interface.py:922`).

Both numbers report an upper bound, because both assume that every request reaches
`max_model_len`. An operator reads the two side by side.

### Worked examples

Every number below is pinned in `tests/v1/kv_offload/cpu/test_capacity.py`.
`held` is `min(cdiv(max_model_len, tokens_per_chunk), cap)`.

**Qwen3-8B**, TP 2, 1 full group, `tokens_per_chunk` 256, 4500 slots,
`max_model_len` 36864: `chunks_per_request = 144`, and `4500 * 36864 // 144 = 1152000`.

**gemma-3-27b-it**, TP 2, 1 full group and 6 sliding-window groups, window 1024
tokens, so `cap` is 4. `tokens_per_chunk` 256, 4000 slots, `max_model_len` 36864:

| Groups | cap | cdiv(36864, 256) | held | subtotal |
|---|---|---|---|---|
| 1 full | None | 144 | 144 | 144 |
| 6 SWA | 4 | 144 | 4 | 24 |

`chunks_per_request = 168`, and `4000 * 36864 // 168 = 877714`.

**granite-4.0-h-small**, TP 2, 1 full group and 9 Mamba groups, `tokens_per_chunk`
528, 8000 slots, `max_model_len` 36864:

| Groups | cap | cdiv(36864, 528) | held | subtotal |
|---|---|---|---|---|
| 1 full | None | 70 | 70 | 70 |
| 9 Mamba | 1 | 70 | 1 | 9 |

`chunks_per_request = 79`, and `8000 * 36864 // 79 = 3733063`.

**A hybrid with one group of each kind**, `tokens_per_chunk` 256, 4000 slots,
`max_model_len` 36864, window 1024 tokens: `chunks_per_request = 144 + 4 + 1 = 149`,
and `4000 * 36864 // 149 = 989637`. If all three groups grew with the request, the
answer would be 341333. The caps carry most of the number on a hybrid model.

### Relation to #56867, #49307 and #51615

**#56867** adds `vllm:kv_offload_config_info` and the mechanism that fills it, with
no real value behind it. This PR supplies the CPU values. #56867 has landed
(`775fefa804`), and this branch is rebased on top of it through current `main`.

**#49307 (@yanburman)** became this same metric after review (@orozery: bundle
static tier information into one Info metric following `vllm:cache_config_info`),
emitted once at engine startup. That needed a new public `get_config_info()`
connector API, an `EngineCoreReadyResponse` field, a runtime-populated
`KVTransferConfig` side-channel and a `record_config_info()` chain. All of those
edit code outside `kv_offload/` and `offloading/`, which reviewers objected to.
**#51615 (@nilig, draft)** emits `vllm:kv_offload_cpu_capacity_tokens` through the
existing connector-stats path.

This PR takes the metric shape of #49307 and the emission mechanism of #51615. The
cost is that the metric is absent (no series, never `0`) until the first scheduler
step.

## Test Plan

- **Unit tests** - 15 new test functions, over four sections of the change.

    - **The capacity arithmetic** - `test_capacity.py` calls
      `CPUOffloadingInfo.from_config` and covers the four model shapes above, a
      pure-Mamba model, an empty tier, and the two cases with no token scale.
    - **The tier sizing** - the labels of a real `CPUOffloadingSpec` report the
      numbers the spec resolved, under tensor parallel, under a replicated
      layout, and with a second group that shares the slots.
    - **The config boundary** - `build_offloading_config` fills the two new
      fields, `sliding_window_size_in_chunks` on the group and `max_model_len` on
      the model.
    - **The tiering pass-through** - the primary tier reports the four labels
      on the `0:primary` series, the tiering spec gives it `cpu_info`, and the
      tiering spec declares exactly the names the manager fills.

    Files: `tests/v1/kv_offload/cpu/test_capacity.py` is new and holds 2 (11 cases).
    `tests/v1/kv_offload/test_factory.py` holds 10,

- **GPU and data-parallel sanity runs** - four servers on the pokprod cluster, one

Two things. The metric doesn't exist until the first scheduler step, and that's only in the description — a `group_left` join comes back empty rather than unknown, and `absent()` can't tell "offloading is off" from "nothing's come through yet". Worth putting in the HELP string.

Also worth a line in the description: the `multiprocess_mode` default shifts the seven existing gauges under `--api-server-count > 1`. A fix rather than a regression, but people should hear it from you first. Keep it in this PR though — without it a gauge pinned to 1 reports how many frontends you're running.

Evaluate once at max_model_len, with no search over candidate lengths:
