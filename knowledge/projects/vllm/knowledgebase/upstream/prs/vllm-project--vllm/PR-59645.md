# [Bugfix] Make cooperative TopK exact on candidate overflow

[Upstream PR](https://github.com/vllm-project/vllm/pull/59645) · state: open · merged: False

## Original PR description

## Summary 
Cooperative TopK groups FP32 scores into coarse bins before selecting candidates. If too many scores land in the bin containing the TopK threshold, its bounded candidate buffer can drop scores that belong in the result.

This PR detects that overflow before scattering candidates and uses exact FP32 selection for the affected row. The usual path remains in place when the threshold bin fits.

# Context

We need to differentiate three things here:

* Synthetic vs. real score distributions.
* Exact vs. approximate top-K in real NSA/DSA.
* The impact of overflow. Even when overflow occurs (which *is a rare event*) the discarded candidates will have the same high bits as the retained ones. Retained and discarded candidates belong to the same current radix-threshold bin. Therefore, they share the radix prefix examined so far, meaning their values are very close.

For this reasons, even if we can force the overflow with synthetic inputs, that doesn't mean non-exact topK translates into an negative accuracy impact for the reasons above. See https://github.com/vllm-project/vllm/pull/53287 for more context.

## Validation and performance

I checked selected values against `torch.topk`, along with index range and uniqueness, across ordinary inputs and concentrated-score inputs, including the 2,048/2,049-candidate boundary.

B300 CUDA-graph microbenchmarks show that ordinary-input latency is generally close to main. Recovery is not free: at 250K width, 64 rows, and k=2048, a controlled case measured ~40 µs with 2,048 candidates in the threshold bin, ~54 µs with 2,049, ~75 µs when the whole row was concentrated in [1.0, 1.01]. The last case is deliberately extreme and unrealistic; the 2,049 case shows the cost of merely entering recovery.

The goal here is an exact TopK result when overflow occurs, not a claimed improvement in model accuracy. Whether the correction changes an evaluation score depends on how often a real workload reaches this condition and how sensitive it is to the selected positions.

DeepSelect and Flashinfer topK are now integrated in vLLM and can be selected using `--sparse-indexer-topk-backend deep_select` and `--sparse-indexer-topk-backend flashinfer` respectively.

### E2E results (deepseek-ai/DeepSeek-V4.1-Flash, topk=512)

DeepSeek-V4.1-Flash serving runs here show little change in mean TPOT or ITL. Together, these suggest limited practical impact for the workloads tested, but neither experiment measures overflow frequency or rules out an impact on other score distributions. We are including exact selection because the bounded candidate path can potentially drop better scores, while the normal-path overhead is small.


Input / output, concurrency | Main TPOT / ITL | Exact cooperative TPOT / ITL | DeepSelect TPOT / ITL

Some small remarks:
