# [Bugfix][Spec Decode] Always transfer draft tokens to the scheduler

[Upstream PR](https://github.com/vllm-project/vllm/pull/60902) · state: closed · merged: False

## Original PR description

## [Bugfix][Spec Decode] Always transfer draft tokens to the scheduler

Refs #54437

## Purpose

`DraftTokensHandler` is a single slot shared across steps. Its
`set_draft_tokens` fast path cleared `draft_tokens_np` whenever the batch
had no structured-output requests, so a later `get_draft_tokens` returned
`-1` placeholders that the scheduler treated as real draft tokens. Two
failure modes:

- **Async scheduling disabled** (our production case, PP + MTP): the `-1`
  placeholders are scheduled as real drafts, producing a 1-query-row vs
  2-logits-rows mismatch that assert-fails and kills the PP worker.
- **Async scheduling enabled** (#54437's analysis): stale hand-offs leave
  `-1` placeholders in `spec_token_ids`, and the structured-output
  bitmask fails open — unconstrained sampling.

#54437 documents this bug class in depth; this PR closes its "second,
more direct path" (the fast path and the inaccurate "only happens when
async scheduling is disabled" comment). The single-slot staleness race
needs the identity design discussed there and is **not** addressed here —
the two fixes are complementary.

## Reproducer

Unit-level, hermetic, runs on any CUDA GPU (e.g., an RTX 3090 24GB):

```bash
python -m pytest tests/v1/worker/test_draft_tokens_handler.py -x -q
```

A batch with `has_structured_output_reqs = False` and drafts `[[10, 11],
[12, 13]]`: before the fix, `get_draft_tokens` returns `[[-1, -1], [-1,
-1]]` [evidence: before.log]; after the fix it returns the real drafts
[evidence: after.log].

## Fix

Remove the fast path — always transfer, on the existing side-stream async
copy (cheap, already paid for structured-output batches). Also correct
the `get_draft_tokens` fallback comment: the `-1` branch is reachable in
both async and non-async configurations, not only the latter.

## Test plan

```bash
python -m pytest tests/v1/worker/test_draft_tokens_handler.py -x -q
```

New test `test_draft_tokens_transferred_without_structured_output`
(hermetic, no model download): asserts the real drafts survive the
round-trip for a no-structured-output batch.

## Test results

- Before fix: `assert [[-1, -1], [-1, -1]] == [[10, 11], [12, 13]]` —
  the handler returned placeholders [evidence: before.log]
- After fix: `1 passed` [evidence: after.log]

## Duplicate work check

Searched open issues and PRs for: `DraftTokensHandler`,
`draft_tokens_np`, `take_draft_token_ids placeholders`, `spec decode
structured output -1`. #54437 documents the bug class; #54442 (merged
2026-10-01) fixed the downstream symptom — a structured-output request
sampling from an unmasked row — at the structured-output/scheduler
layer, and does not touch `DraftTokensHandler`. This PR removes the
placeholder *generation* (the fast path), which remains on main and is
complementary: #54442 constrains the consumer, this fixes the producer.

- njhill · COMMENTED · 2026-10-09T22:26:53Z · [source](https://github.com/vllm-project/vllm/pull/60902#pullrequestreview-5475915171)

Thanks for the PR. I don't think this change fixes either failure mode it describes, so I don't think it should merge as-is:

**1. `-1` placeholders on the scheduler side are by design in MRV2.** The worker builds `input_ids` from its GPU-resident `req_states.draft_tokens`; the scheduler only needs draft *values* for grammar validation. The fast path skips the D2H copy only when the batch has no structured-output requests (`has_structured_output_reqs` is batch-level), i.e. exactly when nobody consumes the values.

**2. The non-async PP + MTP crash can't come from this code path.** The assert that fired (`num_scheduled_tokens_np >= num_logits` in `_prepare_inputs`) depends only on per-request draft *counts*: `num_draft_tokens_np` is `len(scheduled_spec_decode_tokens[req_id])`. `get_draft_tokens` returns lists of length `num_draft_tokens` whether it copies real values or fills `-1`, so changing the values can't change any count. The crash you hit must have a different root cause. Could you share an e2e repro against current `main`? There may well be a real bug there, but this diff wouldn't address it.

**3. No effect on the async path.** A structured-output request that isn't in the batch which last called `set_draft_tokens` is absent from `req_ids` either way, so `update_draft_token_ids_in_output` skips it with or without the fast path. The "second, more direct path" from #54437 is really the same single-slot staleness, and #54442 (merged) already makes that fail closed via `num_acceptable_drafts`.

**4. Cost with no benefit.** This adds a side-stream D2H copy every spec-decode step for all workloads, including those with no structured output. With async scheduling disabled it also adds a sync + `tolist()` + `validate_tokens` per step. The fast path existed to avoid that.

**5. The test re-states the implementation.** It asserts that the handler returns what was put in. It doesn't exercise the crash or any scheduler/grammar behavior.

Minor: the new comment block is long for vLLM style. After this change the `-1` fallback in `get_draft_tokens` would only be reachable before the first `set_draft_tokens`, so it could become an assert or be removed.

On #54437 more broadly: correctness is handled by #54442. What remains is acceptance-rate loss for structured output under PP, where drafts are lost and then rejected. A per-request draft store on the worker (along the lines of the patch @zebgop-ops linked in #54437) would be the useful follow-up, ideally with throughput numbers.
