# [ROCm][Perf][GLM-5] Fused decode with the MonoKernel in vLLM

[Upstream PR](https://github.com/vllm-project/vllm/pull/60831) · state: open · merged: False

## Original PR description

## Overview

Opt-in decode path for GLM-5 (`glm_moe_dsa`) on ROCm gfx950. With `VLLM_ROCM_MONO_DECODE=1` (the switch DeepSeek-V4.1 uses, #60397), each decoder layer of a pure decode step (3 dense, 75 MoE) runs as one FlyDSL MonoKernel launch per GPU. That launch includes the sparse indexer and both tensor-parallel all-reduces.

The kernel lives under `vllm/models/deepseek_v32/amd/ops/mono/`; the vLLM side is `vllm/models/deepseek_v32/amd/mono/`. The kernel comes from ROCm/FlyDSL#1204 and ROCm/ATOM#2435, with the paged indexer, the dense-layer mode and fixes from ROCm/aiter#6173. This PR replaces #60216.

Follows the MonoKernel standard proposed in #60904: one `forward_layer` call per layer, refusals that list every reason, bounded waits with fail-stop, checked weight views, the kernel under `ops/mono/` trimmed with an assembly-identity proof, and CPU plus MI355 CI.

## Claims

Same build for both arms, only the flag differs. MI355X, GLM-5.3 MXFP4, fp8 KV.

- TP8: TPOT -46% at concurrency 4 and -32% at 8 (8K input / 1K output); -26% and -18% (60K / 600).
- TP4: TPOT 1.83x faster at concurrency 1 (8K / 256).
- Accuracy: full GSM8K (1319 questions) within run-to-run noise (McNemar p = 0.79 at TP8, no consistent difference over 3+3 runs at TP4); NIAH 20/20 up to 128K at TP4 and TP8.
- Default off. Steps the kernel does not cover keep the regular layers and their CUDA graphs.

## How it plugs in

- **One routing call per layer.** `DeepseekV32Model.forward` calls `mono.forward_layer(...)` in its layer loop. On a kernel step, each layer is one launch and returns `(zeros, residual)`; the final norm reads the residual. Otherwise the call is the regular layer.
- **Built after weight loading.** `process_weights_after_loading` views or repacks the weights once. The per-width kernels are built on the first eager decode step, before CUDA graph capture; reaching the path first inside capture raises.
- **Refusals with every reason, in three places.**
  - At config time: gfx950 with 256 CUs, `glm_moe_dsa`, TP 4 or 8, fp8 KV, V2 model runner, FULL decode graphs. No PP, DP, EP, EPLB, DCP/PCP, speculative decoding, LoRA, KV transfer, routed-expert capture, prompt embeds, sleep mode or CPU offload.
  - After loading: fused shared experts, the MoE layout and the RoPE tables.
  - Per step: 1, 2, 4 or 8 tokens, one token per request, no PIECEWISE graph. Anything else takes the regular path.
- **Cache re-check.** The KV cache and block-table layout are re-validated whenever their address or size changes.

## Safety

- Every mailbox wait in the kernel is bounded (`POLL_LIMIT`). An expired wait sets its stage's error word and this rank's flag on rank 0, then finishes the launch instead of hanging.
- After each step, the host reads the error words without blocking the stream. On an expired wait, ranks other than 0 exit, and rank 0 raises after dumping tracebacks. `VLLM_MONO_UNSAFE_WARN=1` only logs.
- `VLLM_MONO_FAULT_INJECT="rank=R,step=N,us=D"` stalls one rank for tests; unset, no code is generated.
- `EngineCore` batch-queue fix: a failed forward is re-raised instead of returning `None`.

## Weights and numerics

- Weights are viewed where the kernel reads them as stored. Shapes, dtypes and contiguity are checked, with a clear error. The MXFP4 experts are checked as contiguous bytes in the TP-shard layout.
- Declared at startup: expert inputs are quantized to MXFP8 (vLLM: MXFP4), and TP all-reduces run in BF16 inside the launch.

## Validation

MI355X, GLM-5.3 MXFP4, a ROCm build of vLLM `43b4aaea` with this branch's `vllm/models/deepseek_v32/amd/` and `envs.py` on top. Both arms use the same build and differ only in the flag.

**Kernel code.** The kernel now keeps only the variant vLLM builds; dropping the unreachable branches leaves the compiled code unchanged. All 20 distinct kernels built by the op tests and the latency bench at TP4 and TP8 have byte-identical instruction streams before and after. Their outputs hash identically, and per-layer latency is unchanged.

**Tests.**
- CPU: `tests/models/deepseek_v32/amd_mono/test_glm_mono_routing.py` (refusals, step routing, cache re-check, fail-stop) and `test_glm_mono_weights.py`: 55 passed.
- GPU (4x MI355X): the MoE, dense and paged-indexer op tests pass at TP4 and TP8. `test_glm_mono_safety.py` checks 300 graph replays bit-identical at 2, 4 and 8 rows, and a fault run (rank 1 stalled 2 s) finishes with every rank reporting the expired stages and rank 0 seeing all four flags.
- Buildkite: the CPU tests join "Basic Models Other"; a new MI355 step runs the GPU tests.

**Cost of the bounded waits.** Per layer +0.2% to +1.3% depending on width and TP (for example 61.9 to 62.5 us at TP4, 2 rows). Against the previous revision (unbounded waits), two TP4 servers side by side, swapped across two rounds: TPOT 6.28 to 6.35 ms at concurrency 1 (+1.0%) and 8.72 to 8.80 ms at 4 (+0.9%) (8K / 256).

**Accuracy.**

| Eval | Flag off | Flag on |
|---|---|---|
| TP4, GSM8K 5-shot strict, 1319 questions, 8 concurrent, 3 runs | 0.897 / 0.884 / 0.900 | 0.889 / 0.901 / 0.904 |
| TP8, GSM8K, same setup, 1 run | 0.889 | 0.892 |
| TP4 and TP8, NIAH at 8K/32K/60K/128K, 20 prompts | 20/20 | 20/20 |

- McNemar (exact) over per-question results: on vs off p = 0.79 at TP8. At TP4 the nine on/off pairs give p from 0.03 to 1.0, and the one pair below 0.05 favours the flag on; off/off pairs give 0.08 to 0.80.
- Greedy agreement, 32 prompts, 64 tokens: the first 8 tokens match the regular path for 9-10 prompts, and every token is in its top 5 for 25-26 prompts. Two regular-path servers against each other give 6 and 29: this stack is not run-to-run deterministic, so this check only bounds the drift.

**Startup.** Cold start at TP8 is 1148 s with the flag vs 1027 s without (+2 min, FlyDSL builds the kernels for four widths; most of both is AITER JIT in a fresh container).

**Not covered.** Stage outputs are compared with the kernel's own references, not with vLLM's ops. The GPU tests need gfx950 and the GLM-5 checkpoint.

<summary>Server command (TP8)</summary>

```bash
VLLM_ROCM_USE_AITER=1 VLLM_ROCM_USE_AITER_FUSION_SHARED_EXPERTS=1 \
VLLM_ROCM_MONO_DECODE=1 VLLM_ROCM_QUICK_REDUCE_QUANTIZATION=INT4 \
VLLM_ROCM_USE_AITER_SPARSE_INDEXER=1 VLLM_USE_V2_MODEL_RUNNER=1 \
vllm serve amd/GLM-5.3-Quark-MXFP4-AttnFP8 \
  --tensor-parallel-size 8 --kv-cache-dtype fp8 --block-size 64 \
  --max-num-seqs 256 --max-num-batched-tokens 16384 --max-model-len 258048 \
  --no-enable-prefix-caching --async-scheduling --trust-remote-code \
  --compilation-config '{"pass_config": {"fuse_rope_kvcache_cat_mla": true}, "use_inductor_graph_partition": true}' \
  --hf-overrides '{"use_index_cache": true, "index_topk_freq": 4, "index_share_for_mtp_iteration": false}'
```

The baseline is the same command with `VLLM_ROCM_MONO_DECODE=0`.
