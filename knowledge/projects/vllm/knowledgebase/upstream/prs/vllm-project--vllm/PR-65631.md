# [Bugfix][KV Offload] Keep whole-chunk max_load_tokens caps with sliding window groups

[Upstream PR](https://github.com/vllm-project/vllm/pull/65631) · state: open · merged: False

## Original PR description

## Overview

With sliding window groups, the OffloadingConnector applied its prompt-end `-1` after the `max_load_tokens` / `max_num_new_tokens` caps, so a whole-chunk cap lost a chunk (a one-chunk cap loaded nothing). Follow-up to #55885.

## Claims

- With sliding window groups (and no partial-tail support, e.g. gpt-oss, Gemma 2/3), `max_load_tokens = k * tokens_per_chunk` now loads `k` chunks instead of `k - 1`.
- The same lost chunk is fixed for `max_num_new_tokens` (the bound from groups the connector does not offload).
- No change when there is no cap: the hit still stops before the last prompt token.

## Validation

New test `test_max_load_tokens_preserves_aligned_sliding_window_chunk` (16-token chunks, 65-token prompt, mixed full/sliding-window groups):

| Cap | Before | After |
|---|---|---|
| 16 tokens | 0 | 16 |
| 32 tokens | 16 | 32 |
| none | 64 | 64 |

```bash
pytest tests/v1/kv_connector/unit/offloading_connector/test_scheduler.py \
  -k "max_load_tokens or sliding"   # 132 passed
pytest tests/v1/kv_connector/unit/offloading_connector
```

## Details

`_lookup_complete_chunks` computed `min(num_tokens, computed + cap) - 1`. The `-1` exists so a sliding-window hit stops before the last prompt token, which must be recomputed. When a cap ends earlier, it is already a supported boundary, but the `-1` moved it one token below, and the per-group `round_down` then dropped a whole chunk. The fix applies the `-1` to the prompt-end ceiling only: `min(num_tokens - 1, computed + cap)`. This matches the partial-tail path, which already uses `num_prompt_tokens - 1` with uncapped limits. Mamba alignment is unchanged.

No existing issue or PR covers this (searched `max_load_tokens`, `max_hit_size_tokens`, sliding window + offloading). Draft #62932 edits nearby lines for a different purpose (capacity-bounded loads); expect a trivial rebase for whichever lands second.
