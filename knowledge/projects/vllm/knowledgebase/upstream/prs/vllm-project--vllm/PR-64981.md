# [Perf] Enable PDL for Inductor-generated Triton kernels in 'interactivity' performance mode

[Upstream PR](https://github.com/vllm-project/vllm/pull/64981) · state: open · merged: False

## Original PR description



## Overview

Inductor can emit programmatic dependent launch (`griddepcontrol.wait` / `launch_dependents`) in the Triton kernels it generates (`torch._inductor.config.triton.enable_pdl`), so each generated kernel starts while its predecessor drains instead of waiting for the launch gap. vLLM currently only picks this up if the user sets `TORCHINDUCTOR_ENABLE_PDL=1` in the environment.

#40543 discussed enabling it: the measured gain is a few percent at small batch, the concern was host overhead for prefill-heavy, high-concurrency serving, and #40555 (gate on `performance_mode == "interactivity"`, via the environment variable) went stale. This PR implements that gating through the Inductor options instead of the environment:

- `VllmConfig.__post_init__` sets `compilation_config.inductor_compile_config["triton.enable_pdl"] = True` when `performance_mode == "interactivity"`, the vLLM Inductor backend is in use (`CompilationMode.VLLM_COMPILE` with backend `"inductor"`, checked after the mode is resolved from the optimization level) and the GPU is SM90+ (`has_device_capability(90)`, the NVML check, so the frontend process does not initialize CUDA). An explicit `inductor_compile_config` value or a `TORCHINDUCTOR_ENABLE_PDL` environment variable (Inductor's own switch) wins.
- Going through `inductor_compile_config` keeps the option in the compile cache key (#40627), so switching modes recompiles instead of reusing the other variant's kernels.
- `balanced` and `throughput` are unchanged.

## Claims

- **H200, TP=1, decode TPOT at concurrency 1:** -3.1% on Qwen3-8B (BF16), -4.2% on Qwen3-8B-FP8, -3.5% on Qwen3-14B-FP8. At concurrency 32: -1.2% / -1.8% / -2.6%. At concurrency 8: -1.0% on the BF16 model but +1.4% / +0.9% on the two FP8 models (consistent over both runs), so the option is not a free win at every batch size, which is why it stays behind `interactivity`.
- **TTFT:** within run-to-run spread at concurrency 1 and 8 on all three models; at concurrency 32 unchanged on the BF16 model and +3% on Qwen3-14B-FP8 (711 / 714 -> 734 / 736 ms), consistent with the host-overhead concern in #40543 for the piecewise (prefill) part of a step.
- **No behaviour change** outside `interactivity` mode, and none for users who already set `TORCHINDUCTOR_ENABLE_PDL` or `inductor_compile_config["triton.enable_pdl"]`.

## Details

- **Why only `interactivity`.** #40543: the win is at small batch (the generated norm / activation / RoPE kernels are a few microseconds each and the launch gap is a visible fraction), while PDL adds host-side cost per launch outside CUDA graphs, i.e. in the piecewise (prefill) part of a mixed step. `interactivity` mode already optimizes for small-batch latency (fine-grained CUDA graph sizes), so it is the right place for this default. The H200 runs above show a small loss at concurrency 8 on the FP8 models and slightly higher TTFT at concurrency 32, so a wider default is not proposed here.
- **Interaction with other PDL kernels.** FlashInfer's norm kernels, the CuTe DSL skinny GEMMs and the Triton kernels from #64846 already wait on their predecessor with PDL; with the Inductor kernels also launched with the attribute, the chain is no longer broken at every generated kernel (the "alternating pattern" noted in #40543).
