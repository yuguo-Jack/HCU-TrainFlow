# [Performance] Memoize waiting prefix cache hits across retries

[Upstream PR](https://github.com/vllm-project/vllm/pull/62310) · state: closed · merged: False

## Original PR description

## Overview

Memoize long prefix-cache hits after failed KV admission so waiting requests can reuse them on the next scheduler step. This targets the repeated scheduler-thread lookup described in [#61604](https://github.com/vllm-project/vllm/issues/61604).

## Claims

- Remember only hits of at least four full blocks, and only for the built-in single full-attention group with prefix caching enabled, no EAGLE block drop, and DCP/PCP = 1.
- Revalidate remembered blocks by request hash, primary block hash, and physical block hash-lifecycle version; resume normal lookup at the first invalid or not-yet-memoized position.
- Keep request records weakly keyed and clear them on admission, free, and successful cache reset. Blocks are not pinned and refcounts are not changed by memoization.

This is an independent implementation of the proposal in #61604. The issue author, @apex-mochen, reported unpublished local work; no related upstream PR was found. The lifecycle-version validation and duplicate-physical-block tests specifically cover invalidation and ABA behavior.

## Validation

- CPU prefix-cache suite: **191 passed** on the exact three-file source snapshot recorded for this patch, using `--noconftest` to avoid unrelated global/GPU fixtures.
- Targeted lifecycle checks and CPU scheduler replay passed; replay exercised failed admissions, cache removals, preemption/cancellation, memo reuse, and verified cleanup/refcounts.
- Ruff and `git diff --check` passed.
- H100 serving with Qwen3-0.6B was exploratory. The high-pressure synchronous scenario completed five pairs: throughput geometric mean **+3.13%**, paired 95% interval **[-3.77%, +10.52%]**. This does not establish an end-to-end gain. High-pressure async completed three pairs at **+0.33%** throughput geometric mean (wide interval); the default-capacity async screen was one pair at **-0.64%**. A single instrumented diagnostic pair showed `schedule()` CPU time **-25.5%**, which is mechanism evidence, not an E2E claim.

The H100 build used shared native extensions because `nvcc` was unavailable and the extension build/runtime versions were not fully matched. The GPU numbers are therefore exploratory and are not presented as a general serving-performance claim. Detailed run manifests and raw results are archived locally.

## Details

When a waiting request cannot allocate KV blocks, `get_computed_blocks()` repeats the full prefix walk on every scheduling step. This change records only a sufficiently long hit after allocation failure. On retry it validates the request's prefix hashes and each physical block's hash plus lifecycle version, then uses the normal hash-table lookup from the first invalid position. This preserves lookup behavior when blocks are moved, evicted, reused, or when an equivalent duplicate becomes the selected copy.

The fast path is gated to a narrow configuration; other coordinators and parallelism settings use the existing lookup. A four-block threshold avoids memo bookkeeping for short hits. The threshold is a conservative implementation guard, not a benchmark-specific workload requirement.

Existing nearby work such as [#54625](https://github.com/vllm-project/vllm/pull/54625) changes waiting-request admission order; it does not avoid rescanning a blocked request's prefix hit. Searches for #61604 and the repeated-lookup path found no overlapping open PR.

AI assistance was used for implementation, test development, benchmark analysis, and PR preparation. The human author has reviewed the source and validation evidence.
