# [Bugfix][Frontend] Sync DeepSeek V4.1 encoder with the 1017 reference (tool-result turns, content-block tool results)

[Upstream PR](https://github.com/vllm-project/vllm/pull/62196) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

This PR syncs vLLM's DeepSeek V4.1 prompt rendering, both the Python tokenizer and the Rust chat renderer, with DeepSeek's updated reference encoder. The reference change is [deepseek-ai/DeepSeek-V4.1-Flash@314113f](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash/commit/314113f8a7dadb388215396ba5fbee2c610a04d6), "fix(encoding): preserve tool image order and current-turn thinking" (2026-10-16). The resulting `encoding.py` is byte-identical to the [`encoding/encoding.py`](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash-1017/blob/1bae0e1088993b9b82de08f59de5be5a34e42170/encoding/encoding.py) shipped with DeepSeek-V4.1-Flash-1017. 1017's config and tokenizer are unchanged from V4.1-Flash, so it is served by this same code path.

**Not a duplicate.** I searched open and closed PRs and issues for "deepseek v4.1 encoding", "1017", "drop_thinking", "find_last_user_index", "current-turn thinking" and "tool result", and found nothing that ports this change. #60792 is related but separate: it fixes tool-result image order in the Python frontend (see Details).

## Claims

- **Tool results no longer end the assistant's turn.** In thinking mode with `drop_thinking` in effect (the default when no `tools` are declared), the reasoning of the assistant message that made a tool call is now kept while its tool results come back. Before, it was dropped from the prompt partway through its own turn. Reasoning from completed turns is still dropped, as in the reference.
- **Content-block tool results stay structured.** At the encoder level, tool results passed as content-block lists (`content_blocks` or list `content`) are kept as blocks, as in the reference.
- **Image placeholder in text is a request error.** A literal `<｜deepseek_image｜>` in message text or reasoning now raises a `ValueError` (400). Before, it was rendered as an image sentinel with no image behind it.
- **Byte-identical prompts.** On 10,679 test conversations, Python prompts match the 1017 reference byte for byte (760 differ on `main`). The Rust renderer matches on every comparable request.
- **No rendering-time cost.** The first commit alone made rendering quadratic in two places: long agent loops in Python, and large blocks of parallel tool results in Rust. The second and third commits make both linear again, back to `main`'s speed (timings below).

## Details

**Root cause.** Before 2026-10-16, vLLM's V4.1 encoder was a faithful port of the reference: every corpus case outside the reference delta matches the previous reference. DeepSeek then changed the reference.

In both the old reference and vLLM, `find_last_user_index` treated the user message built by merging tool results as the latest user turn. `drop_thinking` keeps reasoning only after that index, so it dropped the reasoning of the assistant message that had issued the call, partway through its own turn. That is not what the model sees in DeepSeek's agentic loops.

Example (thinking mode, no `tools`, `drop_thinking` default): `[user q1, assistant a1 (reasoning r1), user q2, assistant (reasoning r2, calls lookup), tool]`

```text
before: <｜User｜>q2<｜Assistant｜></think>\n\n<｜DSML｜ calls>…<｜User｜><tool_result>value</tool_result><｜Assistant｜><think>
after:  <｜User｜>q2<｜Assistant｜><think>r2</think>\n\n<｜DSML｜ calls>…<｜User｜><tool_result>value</tool_result><｜Assistant｜><think>
```

`r1` belongs to a completed turn and is still dropped. `r2` belongs to the turn in progress and is now kept.

**Changes.**

| Reference change | vLLM |
|---|---|
| Tool-result-only user messages do not start a turn | `find_last_user_index` in `vllm/tokenizers/deepseek_v41_encoding.py`. Rust: new `starts_user_turn` in `rust/src/chat/src/renderer/deepseek.rs`, used for both the last-user render index and the historical-developer boundary, and gated to the V4.1 dialect (V4 unchanged). |
| Keep tool `content_blocks` / list content; use user list content as blocks | `merge_tool_messages`. The OpenAI path already flattens list content in `_normalize_messages`, so this only affects callers that pass encoder-format messages directly. |
| Validate image placeholder tokens on every message before merging | `_normalize_messages` in `vllm/tokenizers/deepseek_v41.py` rejects `<｜deepseek_image｜>` in string content, text parts and reasoning, for every role, before image parts become placeholders. |
| Merge/sort before image collection | `encode_messages` merges `context` before the joint call-order sort. Prompts are unchanged, but the encoder no longer mutates the caller's `context` dicts. |

**Who is affected.** Only thinking-mode requests with `drop_thinking` in effect, which means no `tools` declared (declaring tools already disables `drop_thinking`), and whose conversation contains tool results. With tools declared, prompts are byte-identical to before. The placeholder check turns requests that contain a literal `<｜deepseek_image｜>` in text into 400s. Existing serving controls are unchanged: thinking defaults, `reasoning_effort` (including `xhigh` and `"none"`), `drop_thinking`, and tools attached to the first system message.

**Performance (second and third commits).** Deciding whether a user-content block starts a turn now looks at the whole block. On its own, the first commit made that check quadratic in both frontends. Neither fix changes the rendered prompt.

- **Python (second commit).** `render_message` calls `find_last_user_index` once per rendered message. Now that tool-result-only messages no longer stop that backward scan, each call walks back across every tool round since the last real user message, so agent loops render in O(n·k) time. The fix computes the index once in `encode_messages` and passes it down, as the V4 and V3.2 encoders already do. It also extends `test_encode_messages_scans_last_user_once_per_conversation` to V4.1.
- **Rust (third commit).** `starts_user_turn` scans the whole block for a user message, and the last-user `rfind` called it for every entry, so a block of k consecutive tool results cost O(k²). Sequential loops were not affected, because their blocks hold one tool result each. The fix evaluates only the first entry of each block. The resulting index is only compared with developer message positions, which never fall inside a block. On the 7,354-request corpus, the prompts are identical to those before the fix. `large_tool_result_blocks_render_in_linear_time` renders 100,000 parallel tool results in a debug build: about 0.13 s now, about 27 s without the fix. It fails above 5 s.

**Not in this PR.**
- **Python tool-result image order.** When image-carrying tool results arrive out of call order, the Python renderer attaches images in message order rather than placeholder order. The pre-fix reference had the same bug, and the Rust frontend already returns `media_order` in placeholder order. #60792 addresses this. Both PRs edit `_normalize_messages`, so whichever lands second may need a small rebase.
- **Tool namespaces.** The reference has supported them since 2026-09-10. They are not ported to either frontend, which is unrelated to this change.
