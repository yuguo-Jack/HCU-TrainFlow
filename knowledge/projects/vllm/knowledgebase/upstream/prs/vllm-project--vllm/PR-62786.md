# [Bugfix][Frontend] Render GPT-OSS chats with Harmony in /tokenize

[Upstream PR](https://github.com/vllm-project/vllm/pull/62786) · state: closed · merged: True

## Original PR description



## Overview

For GPT-OSS, `/tokenize` renders a chat with the model's HF chat template, while the chat route renders it with Harmony. So `/tokenize` returns ids that the chat route never prefills, which breaks the invariant `test_tokenize_matches_render_for_multimodal_input` already states for multimodal input: `/tokenize` matches `/v1/chat/completions/render`. This PR renders GPT-OSS chats in `/tokenize` through `OnlineRenderer.render_chat`, the function the chat route and the render endpoint use.

## Claims

- For GPT-OSS chats, `/tokenize` returns the ids of `/v1/chat/completions/render`. Through the shared `render_chat`, those are the ids `/v1/chat/completions` prefills; that route itself was not run. Before this change they differed for chats with a system message and no tools, and for tool-call histories.
- Other models are unchanged: their chats still go through `preprocess_chat`.

<summary>Reproducer script</summary>

```python
import json, sys, urllib.request

BASE = sys.argv[1]  # e.g. http://127.0.0.1:8000 for `vllm launch render openai/gpt-oss-20b`
T = "the cat sat on a warm mat and then ran to the old red barn"
CHATS = {
    "system,user,assistant": [{"role": r, "content": T} for r in ("system", "user", "assistant")],
    "system,user": [{"role": "system", "content": T}, {"role": "user", "content": T}],
    "user": [{"role": "user", "content": T}],
}

def post(path, body):
    req = urllib.request.Request(BASE + path, json.dumps(body).encode(), {"Content-Type": "application/json"})
    with urllib.request.urlopen(req, timeout=60) as r:
        return json.loads(r.read())

for name, messages in CHATS.items():
    tokens = post("/tokenize", {"messages": messages})["tokens"]
    token_ids = post("/v1/chat/completions/render", {"messages": messages})["token_ids"]
    print(name, len(tokens), len(token_ids), tokens == token_ids)
```

## Details

Root cause: `ServingTokenization.create_tokenize` calls `OnlineRenderer.preprocess_chat` for every chat, which applies the HF chat template. `OnlineRenderer.render_chat` takes its Harmony branch when `model_type` is `gpt_oss`.

The fix: for GPT-OSS, `/tokenize` builds a `ChatCompletionRequest` from the request's chat fields (`TokenizeChatRequest.to_chat_completion_request`) and calls `render_chat`, as `/v1/chat/completions/render` does. Only declared chat fields are copied, so undeclared body fields such as `stream_options` or `reasoning_effort` do not reach the chat request's validation, as in the Rust frontend's `TokenizeChatRequest::into_chat_request`. An empty `tools` list, which `/tokenize` accepts and the chat route rejects, is dropped.

Behaviour changes for GPT-OSS `/tokenize`, which now follows the chat route:
- `add_generation_prompt`, `continue_final_message`, `chat_template` and `chat_template_kwargs` no longer change the ids. The chat route ignores them for GPT-OSS today.
- A `chat_template` sent without `--trust-request-chat-template` is ignored rather than refused, since it is never rendered.

Open question: the Rust frontend's Harmony renderer honours `add_generation_prompt: false` and rejects `continue_final_message`. Doing the same in `_make_request_with_harmony` would apply to the chat route and `/tokenize` together; I left it out of this PR because it changes the chat route.

Why `/tokenize` rather than pointing callers to `/v1/chat/completions/render`: the render endpoint is off unless the server runs with `--enable-scale-out`, while `/tokenize` is always on. The Rust frontend's `/tokenize` already renders GPT-OSS chats with its Harmony renderer, through the same `prepare_text_request` as its chat route.

Related: #33693 (a draft, idle since April) moves Harmony encoding into the renderer layer, which would make this branch unnecessary. #58414 changes how Harmony is detected; this PR reads `online_renderer.use_harmony`, so `/tokenize` keeps following the chat route either way. #52513 fixes a different `/tokenize` vs chat-route mismatch (`reasoning_content`). No open issue or PR covers this one.
