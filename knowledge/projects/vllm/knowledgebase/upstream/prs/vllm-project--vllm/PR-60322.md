# [ROCm][MoE] Split AiterExperts by weight-quantization key

[Upstream PR](https://github.com/vllm-project/vllm/pull/60322) · state: open · merged: False

## Original PR description

## Summary

 Split AITER experts by weight quantization key. Splits the single catch-all `AiterExperts` modular-kernel class into five narrower leaf classes, one per weight-quantization scheme:

- `AiterUnquantizedExperts` — `(None, None)`
- `AiterFp8BlockExperts` — `(kFp8Static128BlockSym, kFp8Dynamic128Sym)`
- `AiterFp8TensorExperts` — `(kFp8StaticTensorSym, {Static,Dynamic}TensorSym)`
- `AiterFp8ChannelExperts` — `(kFp8StaticChannelSym, kFp8DynamicTokenSym)`
- `AiterMxfp4Experts` — `(kMxfp4Static, {None, kMxfp4Dynamic})`, gfx950-only 

`AiterExperts` becomes a shared, non-instantiable base class. All other methods (`apply()`, `workspace_shapes()`, device/activation/parallel-config gating, weight-conversion dispatch) stay on the base since they're already scheme-agnostic at runtime — only `_supports_quant_scheme()` meaningfully diverges per scheme, so that's the only thing that moved into the leaves. This is intentionally scoped narrowly: `apply()`'s internal `quant_method` derivation, the `asm_moe_tkw1` dispatch, and MXFP4's `gate_mode`/bias selection all remain in the shared base, still keyed off runtime `quant_config` flags rather than owned per-leaf. Moving `quant_method` down is a reasonable follow-up; `gate_mode` is more tangled (it checks `activation == SITU` before weight-quant key) and likely stays shared. Issue #54966's "own apply()/scale contract per leaf" isn't done by this step — only the scheme-gating (`_supports_quant_scheme`) is.

This mirrors the pattern already used by the Cutlass family (`CutlassExpertsFp8Base`, `CutlassExpertsNvfp4`, `CutlassExpertsMxfp4`), where `AiterExperts` was the remaining monolithic outlier. Part of #54966

## Known limitations / follow-up

- `AiterMxfp4Experts`'s harness registration (`mk_objects.py`) doesn't currently produce any modular-kernel test case — `MK_QUANT_CONFIGS` has no `quant_dtype="mxfp4"` entry, so it's registered but unreachable. Real MXFP4 modular-kernel coverage is tracked separately in #60886.
- This PR only moves `_supports_quant_scheme()` to the leaves (see Summary); other scheme-specific runtime dispatch stays in the shared base for now.

## Bugs found and fixed along the way

- Merging main brought in two new tests (#59333/#59334: `test_aiter_moe_padding_matrix`, `test_aiter_moe_token_padding_garbage_rows`) that build a `Config` with `fused_experts_type=AiterExperts` directly. Since the split makes `AiterExperts` a non-instantiable base no longer registered in the harness, this fails `config.is_valid()` (`expert_info(AiterExperts)` → `AssertionError`). Fixed both call sites to pick the correct per-scheme leaf class from the quant config instead.
- `modular_kernel_tools/common.py`'s `_maybe_convert_weights_for_experts` gated the gfx950 AITER weight-preshuffle workaround (#60633) on `fe_name == "AiterExperts"` — a literal class-name string match that no longer matches any instantiated class after the split, silently turning off the preshuffle and falling back to JIT-compiling `preshuffle_off` for every AITER harness case (the exact slowdown #60633 fixed). Switched to `issubclass(fe_type, AiterExperts)`.
- Separately, main added a `model_config.sleep_mode_offload_cudagraph` read in `VllmConfig.use_cumem_cudagraph_pool` that the modular-kernel harness's fake `model_config` (a bare `SimpleNamespace`) didn't have, breaking any multi-GPU modular-kernel test. Added the missing fields with their real `ModelConfig` defaults.

#### Why this isn't a duplicate

No PR performs this exact split. #59333/#59334 (merged into main after this PR was opened) do instantiate `AiterExperts` directly in two new tests — as noted above, merging main surfaced this as a real incompatibility, now fixed by picking the correct leaf class in both tests.
