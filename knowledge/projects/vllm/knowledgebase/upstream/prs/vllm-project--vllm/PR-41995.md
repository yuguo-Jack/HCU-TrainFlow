# Fix Mamba copy metadata high-bit pointers

[Upstream PR](https://github.com/vllm-project/vllm/pull/41995) · state: closed · merged: False

## Original PR description

Fixes #41817.

### Summary

`collect_mamba_copy_meta` stores source and destination device pointers in NumPy-backed CPU buffers before Triton consumes them as pointer arguments. On XPU, valid device pointers may have the high bit set (`>= 2**63`). Assigning those Python integers into signed `int64` NumPy arrays raises `OverflowError`.

This change writes pointer values through a `uint64` view of the existing buffers so the raw pointer bit pattern is preserved without signed integer conversion. It also adds a focused regression test that exercises high-bit source and destination pointers.

- RagingNoper · comment · 2026-06-19T16:20:10Z · [source](https://github.com/vllm-project/vllm/pull/41995#issuecomment-4753235817)

Confirming this on our side: Intel Arc Pro B70 (Battlemage BMG-G31), Qwen3.6-35B-A3B (`Qwen3_5MoeForConditionalGeneration`), vLLM main with `--enable-prefix-caching`. Without the patch we hit the exact `OverflowError` at `collect_mamba_copy_meta` once a request crosses the mamba block boundary — the XPU allocator returns device pointers with the high bit set (>= 2**63) and the signed-`int64` numpy assignment rejects them. Writing through a `.view(np.uint64)` of the existing buffer stores the raw 64-bit pointer bit pattern, and since the Triton copy kernel casts to `tl.pointer_type` (a bitwise reinterpretation) the kernel side is unaffected. With the fix applied, decode crosses the boundary cleanly and prefix caching works end-to-end (large TTFT drop on shared-prefix requests). This matches the other XPU confirmations here (Arc Pro B60, 2x Arc B50 Pro).
