# [Tests] Centralize GSM8K eval definitions

[Upstream PR](https://github.com/vllm-project/vllm/pull/52219) · state: open · merged: False

## Original PR description

## Purpose

GSM8K correctness evals were spread across domain test files, scheduled shell
jobs, and the existing model YAML runner. That made it difficult to see which
profiles, sample sizes, and accuracy floors CI actually uses.

This draft makes `tests/evals/gsm8k/` the common ownership area:

- `configs/evals.yaml` inventories 68 concrete eval cases across 20 scattered
  suites. Each entry records its source launcher, model, benchmark profile,
  metric, question/few-shot/token counts, accuracy floor, and tolerance.
- Distributed, entrypoint, connector, quantization, offloading, and
  speculative-decoding tests now load named YAML specs instead of defining
  GSM8K baselines inline.
- Five scheduled integration scripts use `--eval-spec` so their question
  counts and thresholds also come from the common manifest.
- Existing `configs/*.yaml` files remain the model definitions for the generic
  GSM8K server runner.
- A typed result and assertion contract verifies that each result matches the
  YAML-selected profile and metric before applying its one-sided accuracy
  floor.

Topology-specific launch code remains with its owning suite so GPU markers,
fixtures, process setup, and non-GSM8K feature assertions stay discoverable.

This does not duplicate #48253. That PR adds an opt-in chat evaluation mode and
a gpt-oss model config; this PR centralizes the existing cross-suite eval
inventory and result contract. The overlapping harness file will need
coordination if both changes proceed.

- arrdel · COMMENTED · 2026-08-14T02:05:45Z · [source](https://github.com/vllm-project/vllm/pull/52219#pullrequestreview-4933184600)

Nice tightening of the harness contract. `GSM8KResult` typing plus the explicit `profile`/`metric` fields makes it much easier to read a test failure at a glance, and moving the accuracy assertion to one-sided is the right call — regressions and improvements were previously indistinguishable under `abs(measured - expected) < tol`, and that shape loses real signal.

Three non-blocking observations:

1. **lm-eval-v3 results underpopulate `GSM8KResult`.** `result_from_lm_eval` sets `accuracy`, `profile`, and `metric` but leaves everything else at its dataclass default. Downstream consumers reading `result.invalid_rate`, `result.num_questions`, `result.latency`, or `result.num_shots` will silently get `0` / `0.0` for the lm-eval-v3 profile while getting real numbers for isolated-v1. Two ways to close the gap:
    - Populate what's cheap. `num_shots` is the `num_fewshot` kwarg the adapter already receives; `num_questions` is on `results["results"][GSM8K_TASK]` (typically `n_samples` or similar). That closes two of four fields at zero cost.
    - Or type the profile-specific fields as `float | None` and let readers see the availability difference explicitly.

2. **The `try/except` removal in `call_vllm_api` / `call_vllm_chat_api` is a subtle contract change.** The old code silently converted HTTP errors to `("", 0)`, which quietly depressed accuracy — the PR description names this correctly. The new behavior fails loud, which is right. But it also changes what downstream tests surface: existing tests that assert on accuracy floors will now surface unreachable-server issues as unhandled `RuntimeError` rather than accuracy assertion failures. Worth a one-line comment near the removed try/except or a note in the changelog, so the failure-mode change is discoverable when a CI job flips from "accuracy 0.14" to "connection refused".

3. **`test_min_accuracy_is_one_sided` pins the semantics but not the tolerance floor.** The `at_floor` case at exactly `expected - tolerance = 0.72` passes only because of the `math.isclose(..., abs_tol=1e-12)` branch. Consider two explicit boundary cases: one at `minimum - 1e-15` (should still pass) and one at `minimum - 1e-8` (should fail). Cheap regression protection for the boundary logic — the current test would still pass if someone accidentally deleted the `math.isclose` fallback and left a strict `<`.

The `isolated-v1` vs `lm-eval-v3` framing is also independently useful — I've been chasing pooled-vs-mean-of-means aggregation drift on `mean_acceptance_length` in the same neighborhood ([#42508](https://github.com/vllm-project/vllm/issues/42508), [#52169](https://github.com/vllm-project/vllm/pull/52169)), and the "these two profiles are not score-equivalent" note here is exactly what that other surface still needs.
