# [RFC] Universal Translator: TP topology flexibility framework (Phase 1: ConstraintGroupedNorm + Ling pilot)

[Upstream PR](https://github.com/vllm-project/vllm/pull/41509) · state: closed · merged: False

## Original PR description

## Summary

This PR adds the Universal Translator framework — a TP-topology-flexibility layer for vLLM that lets models load on tensor-parallelism configurations they weren't designed for, with measurable, bounded cost. **Phase 1 ships one constraint type (`ConstraintGroupedNorm`) plus the full RFC document**; future constraints follow the same pattern.

The design doc is at [`docs/design/universal-translator.md`](https://github.com/MidasMining/vllm/blob/rfc/universal-translator/docs/design/universal-translator.md) (added in this PR).

## What this PR contains

- **Framework patch** in `vllm/model_executor/models/bailing_moe_linear.py` (+141 lines): the `ConstraintGroupedNorm` mitigation pattern. Replaces the hard-asserted `tp_size <= group_norm_size` and `group_norm_size % tp_size == 0` with a conditional that installs a cross-rank-reduce wrapper when the constraint is violated. The constraint-satisfied fast path is preserved (zero overhead in the common case).
- **RFC document** at `docs/design/universal-translator.md` (678 lines): the full v2 RFC, post-pilot, post-cross-LLM-review.
- **Subgroup memoizing factory** that ensures `dist.new_group` is called collectively (every rank in deterministic order) to avoid NCCL hangs from non-collective subgroup creation.

## Phase 1 deliverable: validated end-to-end

| Metric | Result |
|---|---|
| Model | Ling-2.6-flash (BailingMoeV2_5, INT4 AWQ MoE, 28 linear-attn + 4 MLA layers) |
| Topology | 8× RTX A4000 (Ampere SM 8.6, PCIe Gen4, no NVLink) |
| TP=8 (previously asserted) | Now loads and produces coherent output |
| Cross-rank-reduce overhead | **~3.3% per token at batch=1** (inside the original 5–15% estimate) |
| Correctness | 3/8 prompts bit-exact match vs TP=4 reference; semantically coherent across the full prompt set; expected fp-reduction-order drift on remainder |
| CUDA-graph compatibility | Validated for the `vllm::linear_attention` custom op in piecewise mode |
| Standalone unit test | Passes bit-exact across 4 configurations (`gloo`-CPU multi-rank, no GPU required) |

## Reframing vs. v1 RFC (per pilot data)

The v1 RFC implied TP=8-flexed beats PP fallback. The pilot disproved this empirically on PCIe-class hardware: TP=8-with-mitigation is ~34% slower than PP=2×TP=4 on Ling/8× A4000 because the per-layer collective tax dominates the framework's overhead.

**v2's reframing:** the framework's value is *optionality with measured tradeoffs*, not "always faster." Users gain the option to make the choice with full cost information instead of hitting an assertion. On NVLink/Hopper-class topologies the framework's TP-flexed config likely wins; on PCIe-class it likely doesn't. Both outcomes are valid and the user can now navigate the tradeoff.

## Related contributions (separable PRs/issues)

Three things surfaced during the pilot that are independent of the framework but worth landing alongside:

- **vllm-project/vllm#41508** — `lightning_attn`: make `CBLOCK` device-aware to fit Ampere SMEM. Affects every Lightning-LA model on Ampere consumer hardware (MiniMax-Text01, MiniMax M2/M2.5/M2.7, Ling/Bailing-class).
- **flashinfer-ai/flashinfer#3219** — `BatchMLAPagedAttentionWrapper(backend="fa2")` returns zeros for non-contiguous `kv_indices` on Ampere bf16. Affects every user of FlashInfer's MLA wrapper class on non-Blackwell.
- **Pending vLLM PR** — FlashInfer-MLA fa2 adapter for Ampere/Hopper (depends on the upstream FlashInfer fix above; opens MLA-class models like Ling, GLM-4.7, DeepSeek-V2/V3 to a new hardware tier).

These are documented in the RFC's "Pilot Case Study" section as evidence that the framework's anti-pattern (defensive constraints masquerading as hardware reality) recurs at every layer of the inference stack — five integration gates were peeled in this single Ling integration, four nested layers deep.

## How the design was shaped

This RFC went through two rounds of cross-LLM review (Gemini, Grok, Nemotron). The methodology and worked example are at [https://github.com/MidasMining/universal-translator](https://github.com/MidasMining/universal-translator).

3-way reviewer-converged must-fix items already integrated:

- `register_constraints()` as a first-class peer of `@translate` decorator (post-hoc registration is the path for HF-imported models)
- `HardwareContext` on `estimate_cost` (cost is hardware-dependent — NVLink vs PCIe, batch size)
- Phase 1 scope narrowed to one validated constraint instead of five

The `sg_ranks` are constructed using indices relative to the tensor parallel group (0 to `tp_size - 1`), but `torch.distributed.new_group` expects global ranks. This will cause incorrect group creation or hangs in multi-node or multi-instance deployments where the TP group does not start at global rank 0. You must map these indices to global ranks using `get_tp_group().ranks`.

```python
            tp_ranks = get_tp_group().ranks
            for sgid in range(self.group_norm_size):
                sg_ranks = tuple(tp_ranks[i] for i in range(
                    sgid * ranks_per_group,
                    (sgid + 1) * ranks_per_group,
                ))
```

Good catch — fixed in e2e704f. The cross-rank subgroup ranks are now mapped to global ranks via `tp_group.ranks` before being passed to `dist.new_group`, so multi-node TP×PP / TP×DP deployments will get correct subgroups.
