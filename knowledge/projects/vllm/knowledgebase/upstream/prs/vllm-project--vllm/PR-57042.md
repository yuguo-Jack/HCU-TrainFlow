# [Kernel] Accumulate ranks in absolute order in 2-stage custom all-reduce

[Upstream PR](https://github.com/vllm-project/vllm/pull/57042) · state: open · merged: False

## Original PR description

## Purpose

`cross_device_reduce_2stage` rotates the rank pointers, so each partition's owner starts its sum at its own rank. `cross_device_reduce_1stage` sums ranks in absolute order `0..N-1`. Both reduce through the same `packed_reduce`, which accumulates into float32 (`csrc/custom_collective_common.cuh:87`, `:323-330`). When those partial sums round, the two kernels can return different bits for the same all-reduce — and the choice between them is made by message size (`csrc/custom_all_reduce.cuh:298-307`: 1-stage below 512 KiB at ≤4 ranks and 256 KiB at ≤8, 2-stage above).

(Line numbers are at main `b49c921a27`, this PR's base; the comment added here shifts the `.cuh` ones after line 47 by 2 on this branch.)

The rotation also makes 2-stage output depend on the total tensor size, even with no switch between kernels. This was independently measured by @curvedinf ([comment](https://github.com/vllm-project/vllm/pull/57042#issuecomment-5686335910)). `part = size / ngpus` moves the ownership boundaries whenever the size changes (`csrc/custom_all_reduce.cuh:38-40`), and each owner starts its sum at its own rank (`:45-48`). In their on-GPU in-vitro run of the unmodified kernels at 4 ranks and fp32, 14.86% of the elements of a 1664×5120 tensor differ bitwise from the same rows of its 2048×5120 parent. Both sizes are above the 512 KiB threshold, so this comes from a chunked-prefill geometry change alone. The 1-stage control on the same data is bit-identical, which pins the cause to the rotation this PR removes.

This PR makes the 2-stage kernel read the rank pointers in absolute order, so both kernels produce identical bits whichever one the heuristic selects, and 2-stage output no longer depends on the tensor size. The direction was proposed by @sfeng33 in the review of #50505; this is that change, split out and self-contained against main. cc @sfeng33

**The change** is one line in `csrc/custom_all_reduce.cuh`: `ptrs[i] = (const P*)_dp->ptrs[target]` → `_dp->ptrs[i]`.

Only `ptrs` loses the rotation. `tmps[i]` must keep it: `tmp_out = tmps[0]` has to be the rank's own scratch buffer, and the stage-2 gather indexes `tmps` with the same `(rank + i)` rotation. De-rotating both would make every rank write its stage-1 results into rank 0's scratch region. The code comment records this.

**Why the kernels then agree bit-for-bit.** For every element, both compute `downcast(((up(x0) + up(x1)) + ...) + up(xN-1))` through the same float32 accumulator. There are no partial sums on the 2-stage path: each partition's owner computes the full N-term sum, and stage 2 only copies already-downcast values. Once the order matches, every operation matches.

**Effect outside batch invariance.** This changes 2-stage output bit patterns for all runs, not only under `VLLM_BATCH_INVARIANT=1`. Before and after, each result sums the same terms through the same float32 accumulator; only the order of the additions differs. How often bits actually change depends on the data and dtype: in the CPU emulation below, plain random fp16/bf16 inputs changed no elements and fp32 inputs changed ~32% (31.28% on GPU in @curvedinf's run, below). No existing test asserts bit-exact 2-stage output: the custom all-reduce tests either run at TP=2, which always selects 1-stage, or force 1-stage (`test_custom_allreduce_chunked`), and the bit-exact all-gather/reduce-scatter tests never dispatch `allreduce()`.

**Prior art, and why this is a separate PR.** #52231 by @mawong-amd already contains this same one-line change, with `ptrs` de-rotated and `tmps` kept rotated. It is part of a 36-file PR adding batch invariance on ROCm, which describes the change as making 2-stage batch-invariant and keeps that path disabled on CUDA pending tuning. This PR splits out only the kernel line, with a 4-rank differential test, so it can be reviewed and land on its own. If #52231 lands first, this PR reduces to the test. cc @mawong-amd

#56358 also targets fixed-order TP reduction, but through an opt-in Python gather-and-sum path (`VLLM_TP_FIXED_ORDER_ALLREDUCE`); it doesn't touch this kernel. Relationship to #50505: complementary. This PR makes kernel *selection* irrelevant to the bits; #50505 keeps *backend* selection (custom vs NCCL) batch-independent. Whichever lands second should drop #50505's force-1-stage gate.

## Test Plan

New test `test_one_and_two_stage_allreduce_bitwise_identical` in `tests/distributed/test_custom_all_reduce.py`. No NVIDIA CI job runs this file: the `:nvidia: (A100) Distributed` step it is declared in is no longer emitted, because the A100 fleet is retired. Its AMD mirror, `:amd: (MI355) Distributed`, still runs it on 4× MI355. The mirror inherits `optional: true`, so it runs only when someone unblocks it (`Run :amd: (MI355) Distributed` in build #93586).

- 4 ranks. It forces each kernel in turn with `VLLM_CUSTOM_ALLREDUCE_ALGO=1stage|2stage` (read on every `allreduce()` call, `csrc/custom_all_reduce.cuh:271`) over the same per-rank inputs, and asserts bitwise-identical outputs.
- fp16 / bf16 / fp32 × 4 sizes, from 16,336 B to 4,194,224 B. The sizes straddle the 512 KiB threshold, and three leave an uneven last partition.
- Adversarial inputs: each element holds `+B`, `-B` and small terms below float32's resolution at `B`, in a random rank order. Ordinary random fp16/bf16 data almost never detects a change of order, because its float32 partial sums are almost always exact (see the emulation below).
- Both forced kernels must also return the exact sum on integer inputs. The existing custom all-reduce tests run at TP=2 or force 1-stage, so none of them reaches 2-stage.
- Why 4 ranks: at 2 the rotation only turns `a+b` into `b+a`, which is commutative, so no 2-rank run can tell the orders apart.
- Skips cleanly with fewer than 4 GPUs, without the custom all-reduce ops, or without full NVLink (custom all-reduce disables itself above 2 PCIe-only ranks).

CPU emulation of `packed_reduce`'s float32 accumulation (emulated, not GPU). For each element, 1-stage order vs the unpatched 2-stage owner-rotated order, downcast and compared bitwise at 4 ranks:

| inputs | fp16 | bf16 | fp32 |
|---|---|---|---|
| this test's adversarial inputs, all 4 sizes | 62.5–62.6% of elements differ | 62.4–62.5% | 61.8–62.5% |
| plain `randn` | **0** differ | **0** differ | ~32% |

Partition owner 0 differs in 0% of elements, as expected (its order already matches); owners 1–3 differ in ~83%. The plain-`randn` row is why the test uses adversarial inputs. The fp16/bf16 zeros are structural at 4 ranks, not luck. Those terms carry 11 or 8 significant bits, so float32's 24-bit accumulator adds them exactly unless their magnitudes differ by roughly 2^11–2^14 or more. The rare rounding that remains is erased by the downcast: in an emulation with @curvedinf's input distribution, 480 of 10.5M 1-stage bf16 sums round in float32, and 0 bits differ between orders after the downcast. For realistic data the practical impact is on fp32 all-reduces. fp16/bf16 bits change mainly for inputs like this test's cancellation.

`pre-commit run --files csrc/custom_all_reduce.cuh tests/distributed/test_custom_all_reduce.py`: all applicable hooks passed (ruff check/format, clang-format, typos, mypy, SPDX).

No model evaluation was run. The change only reorders a float32 accumulation of the same terms, so outputs can differ at the bit level but not in expected accuracy. Happy to run an lm-eval comparison if reviewers want one.
