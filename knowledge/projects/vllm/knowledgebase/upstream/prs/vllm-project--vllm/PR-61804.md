# [LoRA] Fail loudly on kv_b_proj adapters for MLA models

[Upstream PR](https://github.com/vllm-project/vllm/pull/61804) · state: open · merged: False

## Original PR description



## Overview

Interim guard for #48974: LoRA adapters carrying `kv_b_proj` weights on MLA models currently load with zero warnings and are silently never applied. Until the real fix lands (#56718, currently in merge conflicts, with a proposed consolidation into #56327), loading such an adapter should fail visibly.

## Claims

- An adapter whose every LoRA module targets `kv_b_proj` (and has no `modules_to_save`) is now **rejected** with a `ValueError` citing #48974 — loading it is a provable complete no-op (verified on hardware: large-`lora_B` `kv_b_proj`-only adapter produces outputs byte-identical to base, [evidence on the issue](https://github.com/vllm-project/vllm/issues/48974#issuecomment-6155402656)).
- A mixed adapter (working targets + `kv_b_proj`) still loads, with a loud one-line warning that the `kv_b_proj` deltas are not applied — rejecting it would break adapters whose other modules work.
- MLA is detected **structurally** (`any(isinstance(m, MLAAttention) ...)` at manager init) rather than via `model_config.use_mla`, whose hard-coded model-type list misses some MLA checkpoints (e.g. `sarvam_mla`); the structural check covers every family that instantiates `MLAAttention` (directly, via `MultiHeadLatentAttentionWrapper`, or the Transformers backend) and stays off on DeepSeek's non-MLA fallback paths, which build a different attention class.
- The guard runs in `WorkerLoRAManager._load_adapter` — the path every production entry point takes (runtime `add_lora`, `--lora-modules`, engine args) — and deliberately not in `_add_adapter`, where warmup dummy LoRAs (which cover all wrapped modules, `kv_b_proj` included) would warn spuriously.

## Validation

Full `tests/lora/test_lora_manager.py` on an A100 against nightly `vllm 0.32.0rc1.dev100+g77154ca61` (`torch 2.13.0+cu129`) with the two source files from this diff overlaid:

```
$ python -m pytest tests/lora/test_lora_manager.py -q
35 passed in 20.44s
```

28 pre-existing tests unaffected; the 7 new cases (5 tests) cover reject / warn / pass-through semantics, the structural detection helper, and the `_load_adapter` wiring. Lint: `ruff format --check` / `ruff check` (pinned v0.14.0) pass on all three files.

The three new tests exercise the real guard method (reject / warn / non-MLA pass-through via the file's existing `__new__` validator-test convention), the real structural detection helper, and the `_load_adapter` wiring (monkeypatch-assert the validator is invoked). All CPU-only, no downloads.

## Details

- Validation inspects the loaded `LoRAModel.loras` dict, not `adapter_config.target_modules`, because config `target_modules` may name modules absent from the checkpoint — safetensor keys are the source of truth. `kv_b_proj` is never part of any `packed_modules_mapping`, so names are still raw at validation time.
- Root cause being guarded (not fixed here): decode uses absorbed `W_UK`/`W_UV` computed from raw weights, and the prefill path calls `impl.kv_b_proj` — a plain attribute on a non-`nn.Module` that LoRA's alias rewiring never reaches. Full trace on #48974.
- This is deliberately interim and trivially removable: one validator method + call site + tests, no semantic coupling. Whichever of #56718/#56327 makes `kv_b_proj` apply should delete it.
- Not a duplicate: no open PR adds load-time guarding for this; #56718/#56327 change the application path itself (and are stalled/unreviewed respectively).
