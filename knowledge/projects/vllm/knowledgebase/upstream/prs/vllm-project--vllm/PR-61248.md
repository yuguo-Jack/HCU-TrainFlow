# [Bugfix][KV Connector] Drain and validate HF3FS save writers

[Upstream PR](https://github.com/vllm-project/vllm/pull/61248) · state: open · merged: False

## Original PR description



## Overview

Drain every submitted HF3FS save writer before returning its shared staging buffers, and require complete allocation/write results before confirming cache keys.

## Claims

- An early writer failure or a later submission exception cannot bypass draining of previously submitted writers.
- Only one non-Boolean integer full-page result per submitted page authorizes confirmation; empty and truncated results fail.
- Malformed allocation replies fail before gathering KV. Failed saves do not release ownership-ambiguous page indices.

## Details

The old nested `all(...)` short-circuits on the first bad write result, while later writers may still read the same staging buffers. A submission exception has the same lifetime problem. Empty/truncated result lists can also satisfy the old success check without proving all pages were written.

Two private helpers track batch sizes and drain every accepted future. Allocation validation checks key order, cardinality and unique nonnegative integer page indices before gathering. The change adds 85 production lines in one connector-local file and no public API or new main-thread device synchronization.

The current allocator can return an existing complete key's live page without identifying ownership. A failed save therefore retains raw page indices rather than guessing that they may be released. **This may leak newly allocated capacity on failure.** An accepted writer that never terminates keeps the save worker blocked; a timeout cannot safely authorize buffer reuse.

This is partial hardening, not the complete page-ownership or source-lifetime fix. It does not make overwriting an existing complete page transactional, protect source GPU blocks before gathering, fix loads, or change external key identity. Those need separate changes.
