# Fix LMCache MP LoRA cache salt keying

[Upstream PR](https://github.com/vllm-project/vllm/pull/45549) · state: closed · merged: False

## Original PR description

## Purpose

Fixes #44250.

LMCache MP keys external KV entries from token IDs plus `cache_salt`. For LoRA requests, K/V tensors are adapter-dependent, so two adapters sharing the same base model, prompt tokens, and user salt could collide in LMCache and reuse each other's KV blocks.

This change folds the vLLM LoRA adapter name into the internal LMCache MP cache salt. The salt is domain-separated and hashes each component so arbitrary adapter names and user salts remain safe for LMCache file/object keys. The same namespaced salt is used for lookup, store/retrieve metadata, and lookup-lock release.

Thanks for picking this up — the repro is unambiguous (two adapters resolving to the same chunk hashes / external fs key under a shared salt), and folding adapter identity into the MP salt is the right shape of fix. A few things I'd want resolved before it's solid:

**1. `lora_name` is the correct identity field — and it's worth leading with *why*.** This isn't arbitrary: vLLM's own APC block hashing keys LoRA the same way. `_gen_lora_extra_hash_keys()` (`vllm/v1/core/kv_cache_utils.py`) returns the request's `lora_name`, and `LoRARequest.__eq__`/`__hash__` are both defined purely on `lora_name`. So keying the external MP salt on `lora_name` keeps it consistent with how vLLM identifies adapters everywhere else — that consistency is the strongest argument for the design.

The flip side, inherited directly from APC: `lora_name` is a logical label, not a content hash. If a name is later remapped to different weights (relaunch with `--lora-modules a=/new/path`, or `load_inplace=True`), the salt collides again — and with a persistent L2 store (the repro uses an `fs` adapter with a `base_path`) that reopens the bug across restarts. I don't think this PR needs to solve it (it matches the APC contract and the issue's minimal ask), but since the issue title says "identity/version", a one-line note that name-reuse-with-changed-weights is out of scope would set expectations honestly.

**2. `test_lmcache_mp_cache_salt_domain_separates_user_salt` doesn't test what it claims.** It feeds the LoRA-salt output back in as the *non-LoRA* `cache_salt` and asserts they differ — but the second call has `lora_name=None`, so its output is `..._lora_<sha256("")>_salt_<sha256(lora_salt)>`, which is `!= lora_salt` trivially by format. That's a tautology; it doesn't exercise the property the name implies (that the lora and salt components can't be concatenated into a collision). The construction is in fact collision-safe — fixed-width 64-char sha256 per component with literal `_lora_`/`_salt_` separators, so no byte can shift between components — but this test wouldn't catch a regression there. A real test would build two requests that differ only in *where* the boundary falls (e.g. `lora="a", salt="b"` vs `lora="a_salt_b", salt=""` style) and assert distinct outputs.

**3. One small test gap (determinism is already covered — credit where due).** `test_lmcache_mp_request_tracker_uses_lora_cache_salt` already pins determinism (`tracker.cache_salt == _make_lmcache_mp_cache_salt(request)` — same request, same output), which is the "same-adapter reuse is preserved" property, so that's handled. The one case not directly asserted is **LoRA vs no-LoRA at an equal non-empty salt**: `_make(salt="S", lora=None)` vs `_make(salt="S", lora="x")` must differ. The tracker test compares a LoRA request against the raw string `"shared"`, and the empty case is covered separately, but the equal-salt LoRA/no-LoRA pair — the exact collision class the issue is about — is the one-liner I'd add.

**4. The new lock-release keying closes a pre-existing gap — call it out.** The change routes the new `tracker.cache_salt` through the existing sites, but only the `free_lookup_locks(cache_salt=...)` call is *newly* passing a salt; lookup/STORE/RETRIEVE already passed `tracker.cache_salt` on `main`, so you've only changed what it resolves to. That lock-release site was previously the lone path omitting the salt, so this also closes a pre-existing lock-key/​data-key mismatch independent of the LoRA fix — worth a sentence in the description, since a reviewer wouldn't expect a lock-release correctness change under "fold the LoRA name in."

Also worth a line in the test plan: this takes effect on the external `lmcache.integration.vllm` adapter (what the repro exercises). The vendored fallback `lmcache_integration/multi_process_adapter.py` is already divergent on `main` — its `maybe_submit_lookup_request`/`_create_key` don't take `cache_salt` and there's no `free_lookup_locks` — so if you've only validated against the external adapter, say so, so a reviewer doesn't assume the fallback is covered.
