# [Perf][MLA] Cap TRITON_MLA decode num_kv_splits for single-request batches on ~100 KiB-smem GPUs

[Upstream PR](https://github.com/vllm-project/vllm/pull/63623) · state: open · merged: False

## Original PR description



## Overview

Under FULL CUDA graphs, TRITON_MLA decode uses the split count (S) computed from `max_model_len` at capture time: S = 376 at every step for GLM-4.7-Flash on a 188-SM RTX PRO 6000, whatever the live context length. This PR caps S for single-request decode batches on GPUs that fit one stage-1 program per SM (shared memory per block < 128 KiB: SM86/89/12x), for the 512+64 latent tile with 16-bit KV.

Draft: the GPU numbers below come from an earlier revision with the same S rule; the final revision has only run CPU unit tests. The planned GPU checks are listed under "Not yet validated".

Related: #33529 (split heuristic), #42885 (FULL graphs for TRITON_MLA), #40614, #40750, #51685, #60173.

## Claims

- GLM-4.7-Flash-AWQ, TRITON_MLA, RTX PRO 6000 Blackwell WS, default `max_model_len` (202752), batch 1: TPOT **−30.9 % at 8K input, −23.6 % at 32K** (measured revision).
- MTP k = 1, batch 1: decode step **−31 % / −20 %** at 8K / 32K.
- No change for batches of two or more requests, quantized KV, other latent tiles, GPUs with ≥ 128 KiB shared memory per block (A100, H100, B200), or non-CUDA platforms.

## Details

**Root cause.** `_compute_num_kv_splits` (#33529) picks S = min(next_pow2(`max_seq_len` // 512), 2 × SMs). With FULL graphs (#42885), decode is captured with `max_seq_len = max_model_len` (both model runners), and S is a launch constant, so every replay keeps the capture-time S. A PIECEWISE trace at 8K shows grid-Z = 16 (live length); FULL shows 376 even at 128-token input.

nsys, 8K input, batch 1, 600 W host, per decode step summed over 47 layers:

| S | stage-1 programs | stage 1 | stage 2 |
|---|---|---|---|
| 376 (default `max_model_len`) | 752 | 751 µs | 3188 µs |
| 128 (`--max-model-len 65536`) | 256 | 875 µs | 1106 µs |
| 64 (PR) | 128 | 748 µs | 576 µs |

Stage 2 is linear in S (~0.18 µs per split per layer over these points). A stage-1 program uses 128 threads, 190 registers per thread and ~62 KiB of shared memory (bf16 KV, two pipeline stages). Registers would allow two programs per SM, but SM86/89/12x have 100 KiB per SM, so one fits. Splits beyond one wave therefore add merge work without adding stage-1 parallelism.

**Rule.** For one request, S = min(S_main, prev_pow2(SMs // (rows × ⌈H/16⌉))): 64 for GLM (128 programs, 60 SMs idle), 32 with MTP k = 1. This is an empirical choice, not a proven optimum:
- H = 20, batch 1 kernel sweep (powers of two plus 376): S = 64 is fastest at every length from 8K to 196K (0.34–0.89 of S = 376; S = 128 gives 0.48–0.96).
- S = 64 vs S = 128 end to end at 8K: −10.5 % (PRO 6000, `max_model_len` 65536) and −10.3 % (RTX 5090, S forced by a test-only override).
- Stage 1 at S = 128 (875 µs, a partial second wave) is slower than at both 64 and 376; I have no model that explains all three points.

**Gate.** Per-block opt-in shared memory < 128 KiB stands in for "per-SM shared memory < two programs": for SM86/89/12x the per-block limit is 99 KiB (per SM 100), for SM80 163 (164), for SM90/SM100 227 (228). `shared_memory_per_multiprocessor` would state this directly; happy to switch. Quantized KV is excluded because the ~62 KiB figure was only measured for bf16 KV.

**Guard.** With more than one head tile and more than 4 programs per split, S stays at S_main (GLM with MTP k ≥ 2, H = 128 models). The threshold is empirical. Kernel sweep, H = 20, one-wave S relative to S = 376, equal-length batch rows standing in for query rows (one measurement per cell, noise up to ~12 %):

| rows (one-wave S) | 8K | 64K | 131K | 196K |
|---|---|---|---|---|
| 4 (16) | 0.39 | 0.81 | 1.00 | 1.08 |
| 8 (8) | 0.32 | 0.90 | 1.10 | 1.16 |
| 16 (4) | 0.38 | 0.99 | 1.18 | 1.22 |

S is fixed before the live length is known, so the guard gives up the short-context gain to avoid the long-context loss.

**Why only one request.** S is one constant per launch. A one-wave S sized for a mixed-length batch starves the longest request: with 196K + 1K at batch 2, the one-wave S is 1.40× slower than S = 376 (H = 20) and 1.21× slower (H = 16).

**Interaction with #60173.** That open PR sets `num_stages = 1` for stage 1 on every < 128 KiB GPU. If it lands, a bf16 program needs less shared memory, two programs may fit per SM, and this PR's one-program-per-SM premise and `_STAGE1_SHARED_MEMORY_BYTES` must be re-measured.

<summary>Further results and caveats</summary>

- **Hosts.** 550 W host: RTX PRO 6000 WS power-locked by the provider at 550 W of 600 W (throttle reason 0x4 in ~13 % of samples), EPYC 7543; E2E, MTP, kernel checks, gsm8k. 600 W host: same GPU unlocked, EPYC 9554; nsys profile, S sweep, guard sweep, E2E repeat. vLLM `87b804f09` (MRV2), torch 2.14.0+cu132, triton 3.8.0. Throttling may affect both absolute times and the comparison; the unlocked host gave similar gains.
- **MTP.** Step time 10.3 → 7.1 ms (8K) and 13.0 → 10.4 ms (32K), out-of-tree script, ABBA. The k = 3 control keeps S = 376 by the guard and differs by −0.09 / +0.03 ms. TPOT is not compared because greedy outputs and acceptance vary between processes even for the same build.
- **Long context, kernel only, batch 1** (relative to S = 376): H = 20 0.33 / 0.57 / 0.70 / 0.87 / 0.87 at 8K / 32K / 64K / 128K / 196K; H = 16 (S = 128) 0.45 / 0.57 / 0.67 / 0.81 / 0.87. The 24–31 % E2E gain at 8K–32K does not carry to 128K+.
- **Numerics.** Capped S vs S = 376 output, max|diff| / max|out_376|: ≤ 0.0043 over 10 batch-1 cells. Both this and the FP32 comparison are normalized by the largest element, so they can hide errors in small elements. Outputs are not bitwise identical to main (different fp32 merge order); `VLLM_BATCH_INVARIANT` (S = 1) is unchanged.
- **gsm8k** flips: PR vs main 5 lost / 7 won, main vs its rerun 6 / 8; 95 % CI of the difference [−1.9, +3.5] pp. Prompts are ~1k tokens, so this only rules out gross breakage.
- **Workarounds today.** `cudagraph_mode=PIECEWISE` is +108 % / +82 % slower than main on the EPYC 7543 host (host-launch bound; faster CPUs may narrow this). A lower `--max-model-len` also lowers S: at 65536 the cap still gives −10.5 % at 8K, at ≤ 32768 nothing.
- **Eager / PIECEWISE.** The cap also applies when the live-length S exceeds the one-wave S (single requests above ~32K); not measured end to end, kernel sweep favours the cap there.
- **#51685** (open, needs rebase) changes the same heuristic more broadly and notes the same capture-time bound; its rule assumes 2 programs per SM. A rule-level estimate (each rule's S looked up in my kernel sweep; its branch was not run) favours its S in all 40 batch ≥ 2 cells and this PR's S in 9 of 10 batch-1 cells (one tie). Happy to fold this into #51685 if its author prefers.
- **Duplicate check (26/10).** Open PRs searched for "num_kv_splits", "triton mla splits", "TRITON_MLA decode", "kv splits cudagraph": no other single-request cap. #40614 / #40750 tried it before and were closed without review. Possible textual conflicts: #51861 (`forward_mqa`), #60173 / #61068 / #57094 (`triton_decode_attention.py`).
- `_decode_programs_per_split` replaces the inline expression in `rocm_aiter_mla.py` (no behaviour change); `GROUPED_BLOCK_H` is now a module constant. The default S still uses device 0's SM count, as on main.
