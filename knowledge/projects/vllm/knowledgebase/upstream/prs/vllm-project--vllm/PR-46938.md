# [Misc] Report prefix cache hit rate in vllm bench serve

[Upstream PR](https://github.com/vllm-project/vllm/pull/46938) · state: open · merged: False

## Original PR description

## Purpose

`vllm bench serve` reports latency and throughput, but not the prefix cache
hit rate — so benchmarking prefix caching means manually scraping `/metrics`
and computing the rate by hand. That is error-prone: the Prometheus counters
are cumulative since server start, and the server's logged hit rate uses a
rolling 1000-request window — neither corresponds to "this run".

This mirrors the existing spec-decode / diffusion metric handling: snapshot the
`vllm:prefix_cache_queries_total` / `vllm:prefix_cache_hits_total` counters
before and after the main run and report the per-run hit rate (plus raw queries
and hits) in the console summary and the saved JSON. The rate uses vLLM's own
definition (`hits / queries` in tokens, see `CachingMetrics.hit_rate`). When
prefix caching is disabled or the backend is not vLLM, the fields are omitted.

## Test Plan

512-token prefix so the cache is exercised:

This would have saved me a fair amount of time, so a data point in favour.

On an H100 with Qwen3-8B, a concurrency ladder built from repeated
`vllm bench serve` runs against one server sits at a 98.4% prefix cache hit rate

output, there was nothing to indicate it was happening.

Review notes on `03efaed9`, read against main at `ffa18e55` (line numbers are for that revision):

1. Lint hasn't run on this branch: `pre-run-check` fails here (it needs a `ready` or `verified` label, or 4 merged PRs from the author), so `pre-commit` was skipped. `except (aiohttp.ClientError, asyncio.TimeoutError)` in `fetch_prefix_cache_metrics` should trip ruff `UP041` (the repo targets Python 3.11+, and the sibling fetchers use `TimeoutError`, `serve.py:270` and `:332`). I haven't run ruff, so `pre-commit run --all-files` locally is the quick check.
2. `_parse_prefix_cache_metrics` silently drops the fields when a label value contains a space, for example `--served-model-name "my model"`: `line.split(None, 1)` splits inside the label, `float()` raises, `suppress(ValueError)` hides it, and the function returns `None`. The function from this branch returns `None` for `vllm:prefix_cache_hits_total{model_name="my model",engine="0"} 101888.0`; `line.rsplit(None, 1)` gives the right counts. `fetch_spec_decode_metrics` and `fetch_diffusion_metrics` have the same `split(None, 1)` (`serve.py:238`, `:311`), so it matches the file; your call.
3. The tests only cover the parser. Moving the delta and rate arithmetic out of `benchmark()` into a small function would let a test cover the "no queries, omit the fields" rule.
4. Docs: the rate is device-local (it excludes `vllm:external_prefix_cache_hits_total` from KV connectors, which the parser test pins) and a percent, like `spec_decode_acceptance_rate`. The repeated-runs warning at `docs/benchmarking/cli.md:113-120` (from #53920) says to interpret cache metrics but doesn't point at one; a sentence there about the new line would close that.

Sweeps: I don't think anything is needed there. `bench sweep serve` resets the prefix cache after each run (`sweep/server.py:72-75`, `sweep/serve.py:118-119`), writes every field of each run's JSON to `summary.csv` (`sweep/serve.py:383-384`), and `bench sweep plot` accepts any result column as `--var-x` or `--var-y` (`sweep/plot.py:299-308`), so the new keys should flow through once this merges. That is from reading the code, not from a run.

I haven't run this PR against a live server; the parser check was a standalone script around the function from this branch, not a vLLM test run. I used Claude Code to research and draft this review.
