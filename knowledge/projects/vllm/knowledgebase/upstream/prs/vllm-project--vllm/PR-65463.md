# [Bugfix][KV Cache] Re-fit `--max-model-len auto` after the extensible KV cache shrinks

[Upstream PR](https://github.com/vllm-project/vllm/pull/65463) · state: open · merged: False

## Original PR description



## Overview

With the extensible KV cache (default on CUDA/ROCm with model runner V2, #56492), `--max-model-len auto` is fitted at planning time, against a budget that leaves out CUDA graphs and warmup on purpose: the KV cache is committed later, from the memory measured after warmup. When that measurement can no longer hold the fitted length, `finalize_extensible_kv_cache` only checks it and startup fails, even though the user never asked for that length. This PR fits the length again to the measured capacity, for `auto` only.

## Claims

- `--max-model-len auto` no longer fails at startup when CUDA graphs and warmup leave less KV cache than the planning-time fit assumed. It starts at the longest length that fits the measured capacity and logs the reduction.
- No change for any configuration that starts today:
  - An explicit `--max-model-len` that does not fit still fails, as before.
  - For `auto`, the re-fit searches only lengths at or below the current one, so when the measured capacity holds the current length, it is kept and nothing else happens.
- +24 lines: `kv_cache_planning.py` +19, `engine/core.py` +5. Plus one unit test.

## Validation

**Unit test:** `tests/v1/core/test_kv_cache_planning.py::test_finalize_extensible_kv_cache_refits_auto_max_model_len`. It fails without the fix (startup `ValueError`) and passes with it. The whole file passes: 66 passed. Pre-commit passes.

**Reproducer on GB200 (4x GPU, TP4), on main alone.** The model is MiMo-V2.5-Pro-FP4-DFlash with the command from `docs/features/speculative_decoding/adaptive_verification.md`, adaptive verification off. Both trees are main `254a2a3390`; the PR tree adds this fix. CUDA graphs take 3.93 GiB in every run, and the full 1,048,576-token context needs 15.06 GiB of KV cache.

The same failure happens at the default utilization whenever graphs or warmup take more memory. With the wider CUDA graphs of #63406, about 12.7 GiB of KV cache is left, and main fails the same way. With this fix on top, the server starts at 846,480 tokens and scores 94.24% on GSM8K at C256 and at C1024.

## Details

Root cause: under the extensible KV cache, `profile_cudagraph_memory` returns 0, because the capture footprint is measured after warmup rather than estimated. That is right for sizing the KV cache, but `auto` still picks its length from the pre-capture budget. `finalize_extensible_kv_cache` then commits the measured block count, and `shrink_kv_cache_configs` raises if one request of `max_model_len` no longer fits.

The fix calls the planning-time `_auto_fit_max_model_len` again, with the measured block count and the same bytes-per-block and null-block accounting that `shrink_kv_cache_configs` checks. If the length changes, the engine core syncs it to the workers with the existing `update_max_model_len`, as the planning-time auto-fit already does.

Shrinking after capture is safe: buffers sized from the planning-time length, such as block tables, still cover a shorter one. Moving the whole `auto` decision after warmup is not an option, because block tables, warmup steps and drafters need a length before capture.

The extensible KV cache is only enabled with model runner V2, so model runner V1 is unaffected.

@njhill Thanks a lot for the review and the cleanup! Before this goes in, we found a case where it can change behavior and would like to test it more completely first.

When the re-fit shrinks `max_model_len` after warmup, CUDA graphs were already captured with the planning-time length, and some drafters bake that length into their graphs. For example, the EAGLE/EAGLE3/MTP draft decode graphs clamp draft positions to `max_model_len - 1` inside the captured graph (`target_dependent_ar/speculator.py`). So for a request near the new, smaller limit, draft steps could step past the KV cache the scheduler allocated. We'd like to reproduce this and test the drafters fully before asking for a merge, so I'm converting this to a draft for now.
