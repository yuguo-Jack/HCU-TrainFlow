# [KV Connector][NIXL] Poll transfer completion on a background thread

[Upstream PR](https://github.com/vllm-project/vllm/pull/61638) · state: open · merged: False

## Original PR description



## Overview

Adds an opt-in thread to `NixlConnector` (`kv_connector_extra_config.async_completion_poll`) that checks NIXL transfer completion every 1 ms, so the transfer latency vLLM reports is the actual transfer time rather than the time until the next engine step.

## Claims

- **Currently, reported NIXL transfer latency includes engine-step stalls.** NIXL stamps `xferDuration` at the first status check that sees a transfer complete ([`nixlAgent::getXferStatus`](https://github.com/ai-dynamo/nixl/blob/22df9863d891112974f7454a454e8449ff83b911/src/core/nixl_agent.cpp#L1268-L1297)). vLLM makes that check only in `_pop_done_transfers()`, once per engine step.
- **In production this shows up as false network tail latency.** A first-use Triton JIT compile of a sampler kernel stalls a decode step for 0.8–3.8 s. Every in-flight KV transfer then reports over 1 s, on all DP ranks at once, which looks exactly like a fabric problem. With polling on, that tail disappears (the stalls themselves remain).
- **Typical latency is overstated too**, because completion is noticed one step late: 9–25 ms average falls to 1.7–3.5 ms.
- **No serving change.** It is off by default. When on, the engine consumes completions at the same point in the step, and release, notification and failure handling are unchanged.

## Validation

GLM-5.3 (HiSparse, 1M context), P/D on 8×8 H100 over RoCE (prefill DP4 × PCP8/DCP8, decode DP4 × TP8, MTP-3), aiperf agentic traces (≈100k-token inputs), with a 25-minute window per level and one run per arm. The table shows transfer latency reported on decode, before → after:

| backend | level | avg | ≤ 5 ms | > 200 ms | > 1 s |
|---|---|---|---|---|---|
| UCX | c96 | 8.9 → **1.7 ms** | 76.3 → **93.8%** | 89 → **5** | 72 → **0** |
| UCX | c128 | 8.7 → **2.5 ms** | 75.6 → **90.8%** | 151 → **18** | 0 → 0 |

- **The tail is the JIT stalls.** Before the change, every > 1 s transfer at c96 (72/72 UCX, 246/246 UCCL) fell within 60 s of a logged compile.
- **The mechanism.** On a single GPU pair without vLLM, checking every 1 / 5 / 30 ms makes `xferDuration` p50 read 1.08 / 5.08 / 30.1 ms, against 0.36 ms when busy-polled. UCX and UCCL behave the same.
- **Serving (UCX).** Throughput was +1% and ITL p50/p99 within 1 ms. TTFT p99 moved both ways, within run-to-run spread. There were no transfer failures.
- **The final branch, end to end.** The GLM runs used the original patch on `f6d5a33`. This branch (`a3fca5e525`) passed a 1P+1D smoke test (Qwen3-0.6B, one H100 node): all requests completed with 0 transfer failures, shutdown was clean, and outputs were byte-identical to a run with polling off.
- **Unit tests** (`tests/v1/kv_connector/unit/test_nixl_async_poll.py`, CPU, in the `cpu_test` CI job) cover:
  - completion stamping while the step is blocked;
  - failures reported identically with polling on and off;
  - exactly one check and one release per handle;
  - shutdown;
  - where the option is supported.

## Details

- **The poll thread** walks `_recving_transfers` under a lock shared with `_pop_done_transfers()`, and records each terminal state with its telemetry, or the exception raised. The engine step reads that result through `_poll_xfer()` and does everything else as before.
- **One checker per handle, never after a terminal state.** UCCL frees the transfer status at the first DONE, so a second check would read freed memory.
- **The agent uses `NIXL_THREAD_SYNC_STRICT`.** The thread is joined at shutdown before handles are released. An unexpected error is logged and retried instead of killing the thread, which would otherwise leave every transfer in progress.

**Limitations**
- **All NIXL calls on the worker are serialized** by `NIXL_THREAD_SYNC_STRICT`. This was measured as neutral on one configuration only.
- **The thread needs the GIL**, so native code that holds it can still delay a stamp. The full fix is for NIXL to stamp completion in the backend.
- **Pull mode only.** `NixlPushConnector` also completes `_sending_transfers`, which is not polled, so it ignores the option with a warning. So do NIXL builds without `nixl_agent_config`.

Both options are documented in `docs/features/nixl_connector_usage.md`.
