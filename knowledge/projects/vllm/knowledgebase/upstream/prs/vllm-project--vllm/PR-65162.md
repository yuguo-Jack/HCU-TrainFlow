# [Build] Fetch `triton_kernels` from a source tarball instead of a `git clone` (avoiding +400 MB pull)

[Upstream PR](https://github.com/vllm-project/vllm/pull/65162) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Disclosure

AI assistance was used. The changes were reviewed and tested manually.

No open PR changes how `triton_kernels` is fetched: #28788 added the external project and #64331 bumps its pinned Triton revision, but neither touches the fetch mechanism.

## Overview

This PR downloads `python/triton_kernels` from an archive tarball of the pinned Triton revision instead of git-cloning the Triton repository **(7.7 MB instead of 405 MiB pulled, 443 MB on disk)** when installing with `VLLM_USE_PRECOMPILED=0 pip install -e .` on ROCm and CUDA.

The ROCm build pins that revision to a bare commit sha, and `FetchContent` cannot shallow-clone a sha (https://github.com/vllm-project/vllm/blob/30565c39372c08b91d164779a120b1f3ba77dc85/cmake/external_projects/triton_kernels.cmake#L22-L29), so `GIT_SHALLOW` is ignored and the full ROCm/triton history is cloned — 405 MiB of objects, 443 MB on disk — to copy a handful of Python files.

The pin, the `SOURCE_SUBDIR`, the install layout and the `TRITON_KERNELS_SRC_DIR` local-development override are unchanged, so builds are otherwise identical. `docker/Dockerfile.rocm` already prefetches this same archive into `TRITON_KERNELS_SRC_DIR`, so the saving applies to non-Docker builds (`pip install -e .`, wheel builds); the URL form now matches that Dockerfile so both paths download identical sources.

## Claims

- Payload pulled for `triton_kernels` drops from 405 MiB of git objects to a 7.7 MB archive on ROCm (443 MB → 31 MB on disk in `.deps/triton_kernels-src`) and from 861 MB to 23 MB on CUDA.
- Configure time follows that payload, depending node's network speed: **96.1 s → 6.2 s of configure on the MI350 node tested for the configure time**, and 165 s → 139 s up to the same `vllm-flash-attn` stop on the H100 node (top-level configure does not complete there, see Validation).
- The `python/triton_kernels/triton_kernels` sources are byte-identical to the clone (`diff -rq` reports nothing), so no behaviour change.
- Docker and non-Docker ROCm builds fetch the same archive (`codeload.github.com/ROCm/triton/tar.gz/<sha>`), so both install identical `triton_kernels` sources.
- `VLLM_USE_PRECOMPILED=1` skips this step on both ROCm and CUDA (cmake never runs), so only `VLLM_USE_PRECOMPILED=0` builds are affected.
- The CUDA path keeps its `v3.5.1` pin (a movable tag, unchanged from `main`).

Left to other PRs:
- [ ] Pin the CUDA revision to a commit sha as the ROCm path does: `v3.5.1` is a movable tag today (https://github.com/vllm-project/vllm/blob/30565c39372c08b91d164779a120b1f3ba77dc85/cmake/external_projects/triton_kernels.cmake#L18-L19), unchanged from `main`.
- [ ] Run a full CUDA build: on the CUDA base image used here, configure stops at `vllm-flash-attn` because the image's default Python is 3.14 and flash-attn supports 3.9–3.13, after the `triton_kernels` fetch has already succeeded (see Validation).
- [ ] No CI check watches the duration of this build step, so a regression in it would go unnoticed there; CI does not track per-step wall-clock.

Builds ran on AMD Instinct MI350X (gfx950), ROCm 10.0.0, AMD clang 23.0.0git and on NVIDIA H100 80GB, CUDA 13.0.2 (nvcc 13.0.88), with an empty `FETCHCONTENT_BASE_DIR` and an empty `CCACHE_DIR` per run.

```bash
# this PR: tarball

```

`main` reports:

```
-- [triton_kernels] Fetch from https://github.com/ROCm/triton.git:669b31acc1dd1b3fd93286afd5db67f65d9f7557
-- Configuring done (96.1s)
```

this PR reports:

```
-- [triton_kernels] Fetch from https://codeload.github.com/ROCm/triton/tar.gz/669b31acc1dd1b3fd93286afd5db67f65d9f7557
-- Configuring done (6.2s)
```

Fetched sources are the same, and the package imports from the checkout:

```
$ diff -rq /tmp/deps-main/triton_kernels-src/python/triton_kernels/triton_kernels \
            /tmp/deps-ev/triton_kernels-src/python/triton_kernels/triton_kernels
$ python -c "import vllm; from vllm.third_party import triton_kernels; print(vllm.__version__)"
0.0.0+evidence
```

Both runs end with `Successfully installed vllm-...`. No unit test targets this step; the build itself is the check.

`VLLM_USE_PRECOMPILED=1` bypasses this step on both targets, because `precompiled_build_ext.run()` returns immediately: cmake never runs, and `triton_kernels` is unpacked from the precompiled wheel (0 `[triton_kernels] Fetch from` lines in either log). It is not a no-op on ROCm either: ROCm resolves precompiled wheels under `wheels.vllm.ai/rocm/nightly/<variant>` (here `rocm100`) and skips the fetch as well. Only `VLLM_USE_PRECOMPILED=0` builds exercise the change.

CUDA, `VLLM_USE_PRECOMPILED=0`:

```
-- [triton_kernels] Fetch from https://codeload.github.com/triton-lang/triton/tar.gz/v3.5.1
```

and leaves 23 MB of `python/triton_kernels/triton_kernels` in `.deps/triton_kernels-src`, then stops with `Python version (3.14) is not one of the supported versions: 3.9;3.10;3.11;3.12;3.13` from `.deps/vllm-flash-attn-src/cmake/utils.cmake:20` — the CUDA base image ships Python 3.14, which is unrelated to this change. Neither `main` nor this PR reaches `-- Configuring done` on that image, for that same reason; what differs is the step before it: 861 MB and 165 s on `main` versus 23 MB and 139 s here. The CUDA archive is 6.4 MB and downloads in 0.8 s on that node (three runs: 0.75–0.81 s).

## Details

- `URL` downloads honour `http_proxy`/`https_proxy`/`no_proxy`, but git-specific configuration no longer applies: an `insteadOf` mirror, `http.proxy` in `.gitconfig`, or a git-level proxy is bypassed for this step. Such setups must keep using `FETCHCONTENT_SOURCE_DIR_TRITON_KERNELS` or `TRITON_KERNELS_SRC_DIR`.
- The archive URL swaps `github.com` for `codeload.github.com` and appends `/tar.gz/<ref>`, the URL form `docker/Dockerfile.rocm` uses; it assumes a GitHub-hosted repository.
- Docker and non-Docker builds install identical `triton_kernels` sources only while `ROCM_TRITON_KERNELS_COMMIT` in `docker/Dockerfile.rocm` equals `TRITON_KERNELS_TAG`; that Dockerfile already prints a warning when the two diverge.
- No `URL_HASH`: the ROCm URL already carries the commit sha, and GitHub archives are not guaranteed byte-stable, so a hash would turn a repack into a failed build for everyone.
- Changing the declared arguments re-runs the populate step, which wipes and re-extracts an existing `.deps/triton_kernels-src`, so a previous git clone is replaced rather than reused. Offline builds upgrading across this commit must pass `FETCHCONTENT_FULLY_DISCONNECTED=ON` (reusing the old checkout) or one of the two source overrides.
- Rejected: `GIT_SHALLOW TRUE` with a branch/tag name (loses the commit pin); `git clone --filter=blob:none` through extra `GIT_CONFIG` arguments (still materializes a `.git`, and the behaviour depends on the CMake version).
