# [ROCm][MiniMax-M3.1] NVFP4 indexer: decode CP for DSpark 7

[Upstream PR](https://github.com/vllm-project/vllm/pull/64448) · state: closed · merged: True

## Original PR description



## Overview

On ROCm TP4 with `indexer_decode_cp`, the NVFP4 indexer's context-parallel decode scorer (`ops/index_cp`, from #64111) takes exactly 4 rows per request (DSpark 3). With DSpark 7 (8 rows per request) the gate `query_len != CP_QUERY_LEN` turns CP off without a log line, and every rank scores its index head over the whole context. This PR scores a request of k x 4 rows as k 4-row CP requests on the host, so DSpark 7 keeps the CP path. It also sets CP up when DBO is enabled: a step DBO splits already scores locally, and the steps it does not split (every pure decode step of the AgentX recipe) now take CP. The kernel does not change.

Split out of #63528 by @Fangzhou-Ai (co-author), which does the same inside the kernel as part of a larger draft stacked on the pre-#64111 `minimax-m31-flash` branch. This PR is that one piece, on `main`.

## Claims

- DSpark 7 decode steps (8 rows per request) take the CP scorer at TP4 instead of the single-head fallback; DSpark 3 is unchanged (k = 1 returns the metadata as is).
- Scores and top-k ids are bit for bit those of the single-head scorer (new test, 8 cases).
- Per step, a rank reads 1/2 of each request's index pages instead of all of them (two 4-row tiles over its quarter; a native 8-row tile would read 1/4, which needs a kernel change and is left out).
- With DBO (InferenceX AgentX recipe, DSpark 7 at the golden AL 4.04), CP on raises P90 interactivity at c32 from 100.0 to **106.6** (+6.6%) and cuts ITL p50 by 4.3%; at c16 the P90 gain is +1.7% (inside the noise), ITL p50 -3.9%. Against the DSpark 3 setting the InferenceX recipe runs at c16 / c32 today, DSpark 7 + CP raises P90 interactivity by +23.0% / **+28.4%**.
- Without DBO there is no measurable change end to end at 126K-token contexts, c1-c16: the index scan is ~2% of a decode step there. The gain grows with context length and batch size.

## Details

- `_cp_requests` turns request i with k = query_len / 4 row groups into k CP requests on its block table row, with sequence lengths `seq_len - 4 * (k - 1 - j)`: the 4 rows of group j see exactly the tokens they see in the 8-row request, so the per-block max over visible tokens is unchanged. It is built once per step and cached on the shared decode metadata (all layers reuse it).
- The gate now accepts any multiple of 4 rows and counts 4-row requests against `CP_MAX_REQS` (256), so DSpark 7 takes CP up to 128 requests.
- Cost of the host split: one `repeat_interleave` of the block table per step (e.g. 104 x 8192 int32 = 3.4 MB at 52 requests and 1M context) and each request's pages read twice. #63528 avoids the copy by indexing the block table row inside the kernel.
- DBO: `index_cp.init()` no longer returns when `use_ubatching` is set (#63528 drops the same guard). The one set of CP buffers and flags is still never shared by two microbatches, because `_decode_cp` returns `None` inside a microbatch (`dbo_enabled()`), so a split step scores locally as before. Under the AgentX recipe a step splits only at >= 16384 prefill tokens or >= 32768 decode tokens, so every pure decode step takes CP.
- Unchanged: CP stays off at TP != 4.
- Other open indexer-CP PRs do not overlap: #57840 (AITER fp8 indexer), #59980 (NVIDIA MSA indexer).
