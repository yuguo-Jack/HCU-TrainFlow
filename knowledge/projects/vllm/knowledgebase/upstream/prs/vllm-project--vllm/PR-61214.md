# [ROCm][MoE] MXFP8 MoE via AITER moe_gemm_a8w8 on gfx942

[Upstream PR](https://github.com/vllm-project/vllm/pull/61214) · state: open · merged: False

## Original PR description

## Purpose

Adds an `AITER_MXFP8_A8W8` MoE backend so ModelOpt MXFP8 MoE models (e.g. `tencent/Hy4-preview-FP8`) run on MI300X / MI325X (gfx942) with expert weights kept in MXFP8.

On gfx942 the MXFP8 oracle currently falls through to `EMULATION`, which dequantizes every expert weight to BF16 at load and roughly doubles MoE weight memory. With this backend, Hy4-preview-FP8 at TP8 goes from **185.87 GiB to 99.27 GiB per rank**, which is what lets it fit on 192 GB MI300X.

Depends on ROCm/aiter#6219, which adds fnuz FP8 / MXFP8 support to `moe_gemm_a8w8` on gfx942.

## Changes

- `fused_moe/experts/aiter_mxfp8_a8w8_moe.py` (new): `AiterMxfp8A8W8ExpertsMonolithic`
  - At load, OCP e4m3fn weights are reinterpreted as fnuz in place (E8M0 exponent + 1, `0x80 -> 0`), keeping one byte per element.
  - E8M0 scales are stored N-contiguous so per-K-step scale loads coalesce (gate/up GEMM 10-19% faster).
  - Router logits go through AITER's fused top-k and sort, then two `moe_gemm_a8w8` calls with MXFP8 activations and vLLM's activation op in between. CUDA-graph capturable.
  - Supports gfx942, `kMxfp8Static` weights with `kMxfp8Dynamic` activations, and TP without EP/EPLB.
- `oracle/fp8.py`: adds `Fp8MoeBackend.AITER_MXFP8_A8W8` and its weight preparation.
- `oracle/mxfp8.py`: auto-selected ahead of `EMULATION`, or explicitly with `--moe-backend aiter_a8w8`.
- `config/kernel.py`: adds `aiter_a8w8` to `MoEBackend`.

## Test Plan

8x MI300X (gfx942), `vllm/vllm-openai-rocm:nightly-rocm100-fe4df3df0eb703862c686b256e9fe44fa94c8945` with this PR applied, AITER built from source with ROCm/aiter#6219.

Validated with **dummy weights only**.

```bash
VLLM_ROCM_USE_AITER=1 \
VLLM_ROCM_QUICK_REDUCE_QUANTIZATION=INT4 \
HF_HUB_CACHE=/data/hf_home \
vllm serve tencent/Hy4-preview-FP8 \
  --trust-remote-code \
  --tensor-parallel-size 8 \
  --port 8000 \
  --kv-cache-dtype fp8 \
  --max-model-len 65536 \
  --reasoning-parser hy_v4 \
  --moe-backend aiter_a8w8 \
  --load-format dummy
```

```bash
vllm bench serve --backend openai-chat --base-url http://localhost:8000 \
  --endpoint /v1/chat/completions --model tencent/Hy4-preview-FP8 \
  --trust-remote-code --dataset-name random \
  --random-input-len 1024 --random-output-len 256 \
  --num-prompts 64 --max-concurrency 32 --ignore-eos
```

## Test Result

- Backend: `Using 'AITER_MXFP8_A8W8' MxFp8 MoE backend (user-requested).`
- Model weights: 99.27 GiB per rank
- KV cache: 60.1 GiB per rank, 1,347,888 tokens (20.57x concurrency at 65,536 context)
- CUDA graph capture completes and the server starts. `/v1/chat/completions` returns 200; output text is meaningless with dummy weights.
- Benchmark: 64/64 requests succeeded, no errors in the server log, `/health` returns 200 afterwards.

| Metric | Value |
|---|---|
| Output throughput | 582.5 tok/s (peak 1184) |
| Total throughput | 2960.3 tok/s |
| Mean / P99 TTFT | 5648 / 7469 ms |
| Mean / P99 TPOT | 32.9 / 40.5 ms |

Kernel correctness is covered by `op_tests/triton_tests/moe/test_moe_gemm_a8w8.py` in ROCm/aiter#6219.
