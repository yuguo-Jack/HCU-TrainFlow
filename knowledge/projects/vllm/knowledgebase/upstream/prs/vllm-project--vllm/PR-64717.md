# [RL][Model Loader] Load split FP8 weights and scales independently (GLM5-next MLA, indexer wk, MiMo-V2 qkv)

[Upstream PR](https://github.com/vllm-project/vllm/pull/64717) · state: open · merged: False

## Overview

Loads every FP8 checkpoint tensor of GLM5-next's MLA projections, the sparse-attention indexer `wk` and MiMo-V2's fused `qkv_proj` on its own, instead of holding a weight until its scale arrives. Part of the direct weight reload work (RFC #54477); builds on #64357 (merged); replaces hao-aaron/vllm#5.
## Claims

- RL weight updates split a weight from its scale across `load_weights` calls. Those updates now load correctly, in either order, with direct reload (#64336). On the base they were silently dropped, applied wrongly or raised. Layerwise reload is not supported for these layers: it is being removed (#54477), and this PR carries no layerwise-only machinery.
  - GLM-5.3-Flash (split weight/scale, direct reload with #64336, TP2): base has 8 projection weights wrong and different greedy outputs. This PR matches a fresh server.
  - MiMo-V2.6 shapes (requantize path, direct reload, TP2): this PR matches a fresh server.
- BF16 tensors under the same names still load, which is what RL trainers send.
- Cold start is unchanged: GSM8K, MTP acceptance length match the base, and KV cache is within 131 tokens of it, on GLM-5.3-Flash, GLM-5.3 FP8, GLM-5.3-NVFP4, Hy4 and MiMo-V2.6-Flash-RL. Throughput is within run-order noise.
- The pairing code is removed from 14 model and MTP loader files: 715 lines added, 676 removed under `vllm/`.

## Details

**Why.** Some loaders held a checkpoint tensor until its partner arrived: an FP8 weight waited for its scale, and the pair was dequantized or resharded inside `load_weights`. RL updates call `load_weights` once per bucket, so the pair can be split across calls, in either order. Depending on where the buffer lived, the base silently dropped the split pair (local buffer: GLM5-next, HY-V4), parked it on the GPU (buffer on the model: DeepSeek-V2/V3.2, MiMo-V2) or raised (dots3). Direct reload (#64336) also needs every checkpoint tensor to have a registered place to live.

**Design.** Each checkpoint tensor is a parameter under its checkpoint name and loads on its own. Post-load processing combines the parts in place, so addresses stay stable for CUDA graphs.

1. **GLM5-next FP8 MLA projections.** New `Fp8DequantConfig` / `Fp8DequantLinearMethod` (`layers/quantization/fp8_dequant.py`) for layers that a checkpoint stores as block FP8 but that run in BF16.
   - The weight is the BF16 weight. An FP8 tensor loads through an FP8 view of the same storage (row *i* into the first half of BF16 row *i*'s bytes), so no memory is added. Post-load processing dequantizes those rows in place, in chunks; BF16 rows and dummy weights are left alone.
   - `weight_scale_inv` is a regular block scale, retired after processing but registered for reloads.
   - `fp8_rows` (host bookkeeping on the CPU) marks the rows loaded as FP8, so post-load processing dequantizes only those.
   - The scale starts as `FP8_SCALE_SENTINEL`; at cold start, post-load processing raises if an FP8 row's scale never arrived. On a direct reload, a missing scale is caught by the update-completeness check (#54477 F2) instead.
   - Loaders only adapt single tensors: the Quark `weight_scale` name and NoPE `kv_a` padding. A BF16 tensor needs no scale; `Fp8DequantLinearMethod` marks its `weight_scale_inv` `optional_in_checkpoint`, which the opt-in strict loaded-weights check (`enable_weights_track`, `default_loader.py`) honours, so BF16 checkpoints don't report it as missing (also when the GLM-5.2 low-latency GEMM wraps the layer).
2. **Indexer `wk`** (DeepSeek-V2/V3.2, HY-V4, GLM5-next, their MTPs, dots3). `wk_weights_proj` uses `Fp8DequantLinearMethod`. Checkpoints store the `wk` scale as 128×128 blocks, per channel, per tensor or MXFP8 E8M0. The layer is replicated, so its scale is one float32 per row and 32 columns, and each layout is expanded into it as it loads (widths must be multiples of 32, as the indexer's are). The `_try_load_fp8_indexer_wk` helpers and buffers are removed. The GLM-5.2 low-latency GEMM wraps `Fp8DequantLinearMethod` layers, keeping their post-load processing.
3. **MiMo-V2 fused FP8 `qkv_proj`** (model and MTP). The checkpoint is pre-sharded for `num_key_value_heads` ranks.
   - The weight loader writes this rank's rows in the forward's layout; it needs no scale.
   - `weight_scale_inv` holds one checkpoint scale per row; its loader also records whether the rows need requantizing, which depends on the scale tiling.
   - Post-load processing (`_Fp8RowScalesLinearMethod`, adopted from the layer's `Fp8LinearMethod`) turns row scales into block scales in the same storage. Where rows form whole checkpoint blocks it takes each block's scale; otherwise it dequantizes and requantizes as the base did. It raises if the weight was loaded without its scale.
   - Both tensors are written with `default_weight_loader`, as on main; the MTP's BF16 fused branch is unchanged from main.

**Known limitations**
- MiMo `qkv_proj` must be in every update, like any block-FP8 linear layer: its post-processing (DeepGEMM on SM100) rewrites the weight and scales. A direct reload that leaves out its weight, or sends only its scale, post-processes the previous load's bytes without an error here; the update-completeness check (#54477 F2, aoshen02/vllm#176) raises for both before post-load processing runs.
- A bare `model.load_weights` of FP8 tensors without the reload lifecycle leaves FP8 bytes in those rows until post-load processing runs. BF16 tensors load and run as before. This includes the sparse NCCL engine, which runs only `finalize_model_weights` and never the layers' post-load step.
- Layerwise reload is not supported for these layers (it is being removed, #54477). A direct reload that sends FP8 rows without their scale reuses the previous scale; the update-completeness check (#54477 F2) is what rejects that.
- **Sharded RDT is not supported for these models**, on main or with this PR:
  - On main, GLM5-next fails when the engine initializes (`unhashable type: 'list'`), and DeepSeek-V3.2 fails on the second sync (`CUDA error: unspecified launch failure`). FP8 updates into these layers are refused at bake time.
  - This PR leaves the RDT engine unchanged. The fix is the load plan, #64418: its `TraceTensor` replaces the RDT bake and ignores constant writes, and RDT moves onto direct reload.
- **Out of scope: other loaders that pair checkpoint tensors across calls, left as on main because these models are not RL targets:**
  - Molmo / Molmo2 (`molmo.py`, `molmo2.py`): concatenates `wte.embedding` and `wte.new_embedding` in one call. VLM.
  - Flint (`vllm/models/flint/ops/moe.py`, `flint/model.py`): waits for all expert tensors and repacks in the loader; re-reads the GGUF. Niche NVFP4/GGUF.
  - Jina-embeddings-v3 (`bert_with_rope.py`): merges LoRA A/B into the base weight. Embedding model.
  - Reranker conversions: Qwen3-Reranker, mxbai-rerank-v2, bge-reranker-v2-gemma (`adapters.py`). They derive `score.weight` from `lm_head` rows. Pooling models.
  - BERT MLM (`bert.py`): copies the decoder from the embedding when it is absent. Encoder-only.
  - Whisper family: voxtral, ultravox, ming_audio, moss_transcribe_diarize, glmasr (`whisper.py`). They add a zero k_proj bias per call. Audio.
  - Nemotron-3.5 Transcribe (`nemotron3_5_transcribe_audio.py`): checks audio-tower completeness per call. ASR.
  - openPangu (`openpangu.py`): derives the attention sinks per call. Niche.
  - AliceAI (`alice_ai.py`): checks completeness per call. Niche.
  - FoPE / InternS1-Pro (`rotary_embedding/fope.py`): builds its cos/sin cache at the first forward. Niche.
  - ColBERT, ColPali, ColQwen3, ColQwen3.5: their loaders bypass the parameters' weight loaders. Retrieval models.
  - Drafters that are rarely updated: Qwen3 XPress, LiLiCorr, Laguna DFlash, and the Qwen3 DFlash `mask_embedding` (re-read from disk).
  - torchao and humming: direct reload refuses them.

Notes from a review pass, for reviewers. Not changed in this PR:

- **`fp8_rows` is loader-set state that post-load processing reads.** Correct today: every path runs the loader. It conflicts with #64418 §5 rule 3, and if the load plan delivers these rows directly (§9, W2), FP8 bytes would run as BF16 without an error. The code comment's "rule 3 exception" is not in the RFC. Tracked as a known issue in #54477 (indexer `wk_weights_proj`, ~120 MB per model, and the GLM5-next MLA projections); the MiMo flags are non-tensor state, which the bake already treats as fallbacks.
