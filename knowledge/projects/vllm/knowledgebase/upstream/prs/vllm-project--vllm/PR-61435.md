# [ROCm][Perf][Kimi-K3] Specialized decode on MI355X: K1/K2 + MLA M1a/M1b (FlyDSL, TP8, DCP1/DCP8)

[Upstream PR](https://github.com/vllm-project/vllm/pull/61435) · state: open · merged: False

## Original PR description

## Purpose

Kimi-K3 specialized decode on MI355X, structured like #60683 and enabled the same way: `--additional-config '{"decode_backend": "latency_specialized"}'`. A Kimi-K3 spec-verify decode step (TP8, DCP1 or DCP8, fp8 KV) runs each MoE decoder layer on persistent FlyDSL kernels instead of vLLM's per-op launches. Everything lives in `vllm/models/kimi_k3/amd/specialized_decode/`; nothing under `vllm/v1/` or `vllm/config/` changes except one small AITER MLA backend change (commit 3). Based on `main`; five commits:

1. **Specialized decode for Kimi-K3 on MI355X.**
   - **K1:** a KDA layer's attention prologue and epilogue.
   - **K2:** AttnRes, the o_proj all-reduce, the router and the MoE (shared and routed experts). It handles up to 64 rows a launch, with a few-rows route table at ≤ 16 rows.
   - **M1a / M1b:** an MLA layer's prologue and epilogue around AITER's `mla_decode_fwd`, which is unchanged.
     - **M1a** does AttnRes, the input norm, `qkv_a` + `g_proj`, the q/kv norms, the fp8 KV-cache write, `q_b`, MXFP4 W_UK and the DCP query all-gather, done in-kernel through peer memory.
     - **M1b** does the DCP LSE combine, MXFP4 W_UV and the gate.
     - At DCP1 the peer traffic compiles out: M1a writes `forward_mqa`'s query directly, and M1b reads AITER's `o` as the latent.
   - **Row cap:** a step serves at most 16 rows (`MAX_ROWS`). The kernels tile up to 64 (`MAX_TOKENS`), but 32 and 64 rows measured slower than vLLM's path.
   - **MXFP4 bmms:** M1 runs W_UK / W_UV as AITER's MXFP4 bmms, so the specialized decode is refused unless `VLLM_ROCM_USE_AITER_FP4BMM=1`, which is off by default since `main`'s 81503550f3.
   - **Reference:** `runtime/mla.py` runs the same split with vLLM's ops and is the tests' reference.
2. **Faster K2 at every served width.** Per launch, TP8, graph-replayed:

   | Rows | 4 | 8 | 16 | 32 | 64 |
   |---|---|---|---|---|---|
   | before | 74.6 µs | 99.4 µs | 156.3 µs | ~287 µs | 446.4 µs |
   | **after** | **73.6 µs** | **96.2 µs** | **138.3 µs** | **273.9 µs** | **408.1 µs** |

   - **Route:** the router keys go through a threshold select and compaction. A 32-step radix select runs only when more than 64 candidates tie. The logits are polled in one batch, and the shared SiTU's h is issued before the route so its loads land under the logits.
   - **Latent norm:** each token's row runs on one CTA, so the sum of squares needs no peer hop.
   - **Above 8 rows:** the o_proj all-reduce and the final reduction are two-shot. Each partial goes to its columns' owner rank, which reduces and broadcasts, so each link carries 2/8 of the one-shot's bytes. Above 16 rows, the up tasks also split by 16-row token tile.
   - **At ≤ 16 rows:** the latent's last partial producer quantizes the MXFP4 latent and puts it, so the routed experts poll once instead of quantizing.
   - **sdown:** its remaining tasks are pipelined a task ahead.
3. **M1a writes AITER's padded cprr query.** At DCP8, a k ≥ 2 verify step takes AITER's round-robin (cprr) asm decode, which has kernels only at 16/32/64/128 heads. So in every MLA layer, `forward_mqa` copied the 96 gathered heads into a 128-head q (repeat + slice + contiguous).
   - M1a's unpack now writes that layout itself: gathered head g < 32 also lands at 96 + g.
   - `forward_mqa` takes a q that already has the cprr head count as is.
   - M1a's own cost doesn't change (36.1 µs at 8 rows).
   - The removed copy cost 7.1 / 8.8 / 12.6 / 19.3 µs per MLA layer at 8 / 16 / 32 / 64 rows (about 23 MLA layers).
   - DCP8 c1 TPOT: 4.01 → 3.94 ms.
4. **M1b runs inside K2's launch, and the DCP8 push is untagged.**
   - **Fusion:** an MLA layer's K2 now carries its M1b (`K2Build.m1b_qlen`). Every CTA pushes its DCP partials; CTAs 0..55 combine and run W_UV, writing core with a ready flag per (head, 4 tokens); the o_proj CTAs, their weights already in flight, poll a core tile's flags before they load it. The M1b → K2 launch boundary is gone. `runner.fuse_m1b` (on) keeps the separate M1b launch reachable.
   - **Push:** M1b's DCP8 push was xGMI-bound (15 µs at 8 rows). A wave now pushes a (token, head)'s `o` row untagged, drains, then puts the LSE pair as the row's flag: half the bytes.
   - M1b + K2 per MLA layer, TP8, graph-replayed:

     | Rows | 8 | 16 |
     |---|---|---|
     | DCP8 before | 120.1 µs | 169.5 µs |
     | **DCP8 after** | **108.6 µs** | **148.8 µs** |
     | DCP1 before | 101.6 µs | 143.1 µs |
     | **DCP1 after** | **98.2 µs** | **140.6 µs** |
5. **Restructure as #60683.**
   - **Switch:** `--monokernel` is gone. `additional_config={"decode_backend": "latency_specialized"}` turns the path on; `auto` (the default) runs vLLM's decode.
   - **Trigger:** the model's `__init__` calls `specialized_decode_config()`, which raises with every reason from `unsupported()` (#60683's checks plus DCP, KV interleave, fp8 KV and FP4BMM). The loaded weights (`weight_reasons`, including each MLA layer) are checked when the model state builds the executor; the KDA states and MLA caches (`cache_reasons`) at every KV-cache bind.
   - **Removed:** the shared `vllm/models/common/mono` runtime, `SupportsMonoKernel`, `KernelConfig.monokernel`, `step_health`, the monokernel metrics and every `vllm/v1` / `vllm/config` change they needed.
   - **Fail-stop:** as in #60683, `compute_logits` queues a non-blocking copy of each rank's FAILED word; every 16 steps the TP ranks agree and all raise at the same step (`guards.FailStop`).
   - **Layout:** `hooks.py` (`SpecializedDecodeMixin`), `model_state.py` (`KimiK3ModelState`), `runtime/` (config check, executor, guards, layer kernels, runner, peer memory, MLA reference), `mono/` (kernel source). The model files only call in: `linear.py`, `model.py`, `mla.py` (`skip_o_proj`), as in #60683.

## Supported concurrency × speculative tokens

A decode step runs on the kernels when **requests in the step × (k + 1) ≤ 16**, where k is `num_speculative_tokens`. `DecodeConfig.widths` builds one kernel width for every multiple of k + 1 up to 16 (`MAX_ROWS`). A step whose row count isn't one of those widths runs vLLM's layers.

| Spec tokens k | Rows per request | Max requests per specialized step | Kernel widths built |
|---|---|---|---|
| 1 | 2 | 8 | 2, 4, …, 16 (8 widths) |
| 2 | 3 | 5 | 3, 6, …, 15 (5) |
| **3** | **4** | **4** | **4, 8, 12, 16 (4)** |
| 4 | 5 | 3 | 5, 10, 15 (3) |
| 5 | 6 | 2 | 6, 12 (2) |
| **7** | **8** | **2** | **8, 16 (2)** |
| 15 | 16 | 1 | 16 |

**Deployments refused at startup** (one `ValueError` listing every reason; `decode_backend=auto` runs vLLM's decode):
- TP other than 8; pipeline, data, expert or prefill context parallelism; EPLB; DBO.
- DCP other than 1 or 8, or a KV interleave other than 1 at DCP8.
- No speculative decoding, k + 1 > 16, adaptive verification, dynamic speculative decoding.
- A non-fp8 KV cache; KDA cache dtypes other than BF16 conv / FP32 recurrent; ReplaySSM / RecoverSSM.
- MLA without the AITER MXFP4 bmms (`VLLM_ROCM_USE_AITER_FP4BMM=1`).
- LoRA, KV connectors, routed-expert capture, sleep mode, CPU weight offload, weight updates.
- The V1 model runner, `STOCK_TORCH_COMPILE`, another model's shapes, a GPU other than a full MI355X.
- At load: kernel layers whose weights aren't the expected contiguous BF16 shapes (e.g. FP8 dense linears), a MoE backend other than `AITER_MXFP4_BF16` (K3 SiTU), or MLA layers the M1 kernels can't serve.

**Steps that run vLLM's layers even with valid settings:**
- More requests than the table's limit for k.
- A step with any prefill in it, or requests of different lengths.
- A Gluon MLA decode step.
- Piecewise cudagraph steps.

## Test Result

**Unit tests, this PR's head:** 135 passed in 12 min.

### InferenceX Kimi-K3 recipe, k = 7, concurrency 1

Recipe `kimik3-fp4-mi355x-vllm-agentic-mtp`, arm `override_tp8_c1`: TP8, fp8 KV, DSpark with 7 speculative tokens, `--max-num-seqs 2`, FULL_AND_PIECEWISE graphs (capture sizes 8, 16), `VLLM_ROCM_USE_AITER_FP4BMM=1`.
- **Workload:** random 8k in / 1k out, `--ignore-eos`, 5 prompts, synthetic acceptance (acceptance length 3.84–3.85 in every run).
- **Setup:** this PR's head, same tree and image for every arm; the four arms ran one after another on pit2-p03-g09, each in a fresh container. Base and specialized differ only in `decode_backend` (`auto` vs `latency_specialized`). The server log confirms 92 kernel layers at widths 8 and 16.
- **Change from the recipe, in every arm:** `--quantization-config` (FP8 online quantization of the dense linears) is removed, because the kernels need BF16 dense weights. The base is therefore no-quant too.

### Higher concurrency (why the 16-row cap)

These runs were measured before commits 2–4, on an earlier base: k = 3, random 1k in / 1k out. Without the cap, 32- and 64-row steps ran on mono and were slower than vLLM's path:

| Concurrency | Rows | DCP1 tok/s, base → mono | DCP8 tok/s, base → mono |
|---|---|---|---|
| 1 | 4 | 69.5 → **100.3** (+44%) | 65.7 → **103.4** (+57%) |
| 4 | 16 | 233.9 → **256.2** (+10%) | 214.4 → **248.6** (+16%) |
| 8 | 32 | **403.1** → 315.9 (−22%) | **373.2** → 300.0 (−20%) |
| 16 | 64 | **644.7** → 401.2 (−38%) | **585.6** → 375.4 (−36%) |

- DCP1 has no M1 peer traffic and regresses the same way, so the main candidate is K1/K2 at 32 and 64 rows.
- Commit 2 cuts K2 at 32/64 rows by 13/38 µs, but `MAX_ROWS` stays 16 until those widths beat vLLM end to end.

**Caveats:**
- GSM8K and the higher-concurrency sweep have not been re-run on this head. Commits 2–5 pass the K2 and M1 numerics tests above.
- Fail-stop detection takes up to about 16 steps (as in #60683), so tokens of a failed step can reach the client before the engine stops.

- The test container needs the NCCL socket env of the recipe (`NCCL_SOCKET_IFNAME=lo`, `NCCL_IB_DISABLE=1`, …) on some nodes, and `VLLM_PORT` below the ephemeral range (e.g. 29650) for the stall test; otherwise TP8 init can hang or lose its TCPStore port, a test-harness issue.
