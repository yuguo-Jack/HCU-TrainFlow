# [Bugfix][KV Offload] Catch async lookup iterator errors

[Upstream PR](https://github.com/vllm-project/vllm/pull/63126) · state: closed · merged: True

## Original PR description



## Overview

Catch errors raised while *consuming* the `batch_lookup` iterator in tiering `AsyncLookupManager`, so a lazy backend failure resolves the request group as misses instead of losing the whole batch and stalling worker progress. Follows the issue addressed by closed, unmerged PR #59187.

## Claims

- An exception raised mid-iteration of `batch_lookup` (not just on the initial call) now resolves that request group as misses instead of dropping the batch.
- Healthy request groups in the same batch, and subsequent batches, keep making progress.
- Regression tests cover both a failure before the first result and after a partial result.

## Validation

- New regression test fails without the fix and passes with it:
  - Without fix: `pytest tests/v1/kv_offload/tiering/test_async_lookup.py::TestAsyncLookupManager::test_iterator_failure_returns_misses_and_preserves_progress` → `2 failed` (`fail_after=0` and `fail_after=1`).
  - With fix: full file passes.
- Full test file: `.venv/bin/python -m pytest tests/v1/kv_offload/tiering/test_async_lookup.py -q` → `22 passed`.
- `ruff check` and `ruff format --check` on both changed files → passed.

## Details

### Root cause

The lookup worker calls `self.batch_lookup(keys, req_context)` inside a `try`, but `batch_lookup` may return a lazy iterator (it is typed `Iterable[bool]`). Before this change, an exception raised by the backend *during iteration* escaped the `try` (which only guards the call), aborted the entire lookup-worker loop iteration, and dropped the results of all healthy request groups in the same batch. Following batches never got submitted, so worker progress stalled.

```text
Before: batch_lookup(...) returns generator -> zip() raises OSError outside try -> whole batch lost, worker loop breaks
After:  list(batch_lookup(...)) inside try -> OSError caught -> failing group resolves as misses, healthy groups proceed
```

### Implementation

A one-line change: materialize the iterator inside the `try` via `list(self.batch_lookup(keys, req_context))`, so full consumption happens where the existing exception handler applies. The `except` branch already resolves the group as misses (`hits = (False for _ in keys)`), preserving prior behavior for call-time failures. `hits` is consumed exactly once downstream (`zip`), so materializing to a list has no side effects.

### Not a duplicate

- #59187 addressed the same failure mode but was closed unmerged.
- Open PR #61988 scopes lookup verdicts per request on failed promotions (`mark_miss` isolation); it does not cover iterator-consumption errors. #61717 covers re-probing for new requests, also unrelated.
