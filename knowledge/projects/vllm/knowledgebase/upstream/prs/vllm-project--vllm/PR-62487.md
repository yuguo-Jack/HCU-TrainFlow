# [Bugfix] Carry the last Qwen3-ASR tower chunk into realtime flush

[Upstream PR](https://github.com/vllm-project/vllm/pull/62487) · state: open · merged: False

## Original PR description

## Overview

Qwen3-ASR realtime flush prepends the previous full segment's last tower chunk once, then drops it. Fixes #62347.

## Claims

- `read_audio` still yields an exact 5 second segment and does not prepend the carry.
- `flush` prepends `rem_frames * hop_length` samples, where `rem_frames = feature_lens % (n_window * 2)`, or one full chunk when that remainder is 0.
- At hop 160, both `n_window` 50 and 100 carry 16000 samples from an 80000-sample segment. A 1600-sample tail then flushes to 17600 samples.
- An empty buffer flushes to `None` even when a carry is held.
- ChatML `prompt_token_ids` are unchanged. The extra audio is only in `multi_modal_data["audio"]`.

## Validation

CPU assertions against `Qwen3ASRRealtimeBuffer` passed for both window sizes, the empty flush, a later segment that must not be prefixed, replacement of the carry by the latest segment, and a tail-only flush.

`tests/models/multimodal/test_qwen3_asr_realtime_buffer.py` imports vLLM. This machine has torch 2.5.1 and cannot import current main, so pytest was not collected here. No GPU realtime session was run. That session is the remaining check before this leaves draft.

## Details

`flush` used to return only the samples still sitting in the buffer. The tower's next window then had no left context, and the endpoint wrapped that tail in a fresh ChatML prompt.

The carry size is `len(segment) // hop_length`, not `n_window_infer`. `n_window` comes from `thinker_config.audio_config`. `hop_length` comes from the feature extractor. The carry is stored when a full segment is yielded and consumed only by `flush`.

AI assistance was used (Grok). This is a first-cut draft so the issue is linked to our branch. The diff still needs a human pass and a realtime GPU run before it is marked ready.
