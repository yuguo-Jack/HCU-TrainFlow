# [Perf][DSv4.1] Share Engram host tables as host-NUMA cuMem across DP ranks

[Upstream PR](https://github.com/vllm-project/vllm/pull/62359) · state: open · merged: False

## Original PR description

## Overview

With `dp_shared_memory`, node-local DP ranks share one registered `/dev/shm` mapping for the Engram host tables (2 layers x 94.4 GiB on DeepSeek-V4.1-Flash). Lookups are random row reads and on GB200 they are bound by GPU TLB misses: the registered mapping uses 64K pages.

This PR allocates the shared table as host-NUMA cuMem instead, which the GPU maps with 2M pages. Rank 0 creates it and broadcasts a FABRIC handle; the other node-local DP ranks import and map it. Where FABRIC handles are unavailable (probed once: create + export), the existing `/dev/shm` path is used and logged. Rank 0 decides the backing and broadcasts it so every rank runs the same collectives. A mapping failure on any rank raises on all ranks.

- New NVIDIA-only `vllm/models/deepseek_v41/nvidia/ops/engram_host_table.py` (~125 lines of code).
- `common/engram.py`: +42/-7, `DPSharedEngramStorage` keeps its interface; startup log says `via cuMem` or `via /dev/shm`.
- No new config option.

Not a duplicate: open Engram PRs cover pinned sizing (#59849), SP/PCP sharing (#57195, #61553), Mooncake and disk offload (#57023, #62238); none changes the shared host table backing.

## Performance

GB200, DEP4, `--numa-bind`-equivalent binding (`numactl` per rank), dummy weights, uniformly random tokens. Same node, back-to-back A/B.

Engram lookup, one layer, fresh ids every iteration:
