# [Perf][DSv4.1] Share Engram host tables as host-NUMA cuMem across DP ranks

[Upstream PR](https://github.com/vllm-project/vllm/pull/62359) · state: closed · merged: True

## Original PR description

## Overview

With `dp_shared_memory`, node-local DP ranks share one registered `/dev/shm` mapping for the Engram host tables (2 layers x 94.4 GiB on DeepSeek-V4.1-Flash). Lookups are random row reads and on GB200 they are bound by GPU TLB misses: the registered mapping uses 64K pages.

This PR allocates the shared table as host-NUMA cuMem instead, which the GPU maps with 2M pages. Rank 0 creates it on its GPU's NUMA node and broadcasts FABRIC handles; the other node-local DP ranks import and map them. Where FABRIC handles are unavailable (probed once: create + export), the existing `/dev/shm` path is used and logged.

Allocation never OOMs; it falls back instead:

- Rank 0 allocates in 2 GiB chunks and stops once its NUMA node would drop below a 5% reserve. Freed cuMem pages stay in the driver's page pool (`NVreg_EnableSystemMemoryPools`), which this estimate does not count, so reusing them after a restart is not penalized.
- The driver allocates with `__GFP_RETRY_MAYFAIL | __GFP_THISNODE`: the kernel compacts for 2M pages and fails the allocation rather than invoking the OOM killer. It never falls back to small pages.
- Any create, export, import or map failure on any rank releases everything on every rank, logs a warning, and falls back to `/dev/shm`.

Two `/dev/shm` fixes, since that path is now the fallback:

- **Orphaned tables:** rank 0 used to unlink the backing file only after every peer had registered it, and registration faults in the whole table. A rank killed in that window left a fully populated 94 GiB file in `/dev/shm` that nothing owned. Every rank now opens the file first, rank 0 unlinks it while it is still sparse, and only then do ranks mmap and register.
- **OOM kills:** `check_shm_free_space` only checks tmpfs capacity. A table larger than available host memory was faulted in anyway and the OOM killer made room. `/dev/shm` sharing now also requires the tables to fit in available host memory (cgroup-aware; `get_available_memory`, moved from `weight_utils` to `cpu_resource_utils`), both when sharing is decided and before allocating. The pre-check requires this even where cuMem will be used, so a per-layer fallback always has room.
- **NUMA binding:** under `--numa-bind` (`numactl --membind`), the fallback is most likely exactly when the GPU's node is full, and the membind confined the `/dev/shm` pages to that node, so the OOM killer fired despite free memory on the other node. The mapping now gets `mbind(MPOL_LOCAL)`: local node first, then any node.

Lookups only sort rows when the table has small (64K) pages. Sorting was keyed on "no THP", so cuMem tables were sorted too, which only adds the sort.

Files:

- New NVIDIA-only `vllm/models/deepseek_v41/nvidia/ops/engram_host_table.py` holds all cuMem code, including the create/broadcast/import protocol (`share_host_table`).
- `common/engram.py` (shared with ROCm): `DPSharedEngramStorage` keeps its interface. On CUDA it tries `share_host_table` first, behind an `is_cuda()` check and a lazy import; ROCm goes straight to `/dev/shm` as before. The `/dev/shm` fixes are platform-neutral and apply to ROCm too. The startup log says `via cuMem` or `via /dev/shm`.
- No new config option.

Not a duplicate: open Engram PRs cover pinned sizing (#59849), SP/PCP sharing (#57195, #61553), Mooncake and disk offload (#57023, #62238); none changes the shared host table backing.

### Row sorting (GB300)

`ParallelEngramEmbedding.lookup` microbenchmark on GB300 with one real DeepSeek-V4.1-Flash layer (24 heads x 16M rows x 256, 94.4 GiB), shared by two ranks. Each cell is the median of 20 iterations with fresh uniformly random ids, packed FP8 output, and the sort included in the time. The ratio is sorted time over unsorted time.

| tokens | cuMem unsorted | cuMem sorted | ratio | /dev/shm unsorted | /dev/shm sorted | ratio |
| --- | --- | --- | --- | --- | --- | --- |
| 128 | 62 us | 202 us | 3.24 | 141 us | 235 us | 1.67 |
| 512 | 72 us | 217 us | 3.03 | 369 us | 384 us | 1.04 |
| 1024 | 84 us | 250 us | 2.99 | 690 us | 624 us | 0.90 |
| 1536 | 105 us | 265 us | 2.52 | 1021 us | 856 us | 0.84 |
| 2048 | 124 us | 288 us | 2.33 | 1341 us | 1108 us | 0.83 |
| 4096 | 192 us | 352 us | 1.84 | 2636 us | 2161 us | 0.82 |
| 8192 | 330 us | 497 us | 1.51 | 5174 us | 3270 us | 0.63 |
| 16384 | 609 us | 776 us | 1.27 | 10308 us | 4386 us | 0.43 |
| 32768 | 1167 us | 1343 us | 1.15 | 61864 us | 37227 us | 0.60 |

- **cuMem:** sorting only adds its own ~150-175 us at every size.
- **/dev/shm:** sorting pays off from about 1024 tokens, which matches the existing 36864-row (1536-token) threshold, so the threshold is unchanged.
- **This PR:** cuMem lookups now take the unsorted path, and the default thresholds measure the same as forced unsorted.
- **Chunk size:** 1 handle, 48 x 2 GiB and 189 x 512 MiB chunks give the same lookup latency.
