# [Bugfix][MRV2][Spec Decode] Count NaNs in logits per request, not per logits row

[Upstream PR](https://github.com/vllm-project/vllm/pull/65147) · state: open · merged: False

## Original PR description

## Overview

With Model Runner V2, `VLLM_COMPUTE_NANS_IN_LOGITS` / `VLLM_RAISE_ON_LOGIT_NANS` attribute NaN counts to the wrong requests whenever a request has more than one logits row (speculative decoding, or `num_new_sampled_tokens_per_step > 1`). `get_num_nans` counts NaNs per logits row and `AsyncOutput` zips that array with `req_ids`, so request `j` gets row `j`'s count and rows past `num_reqs` are dropped. This PR makes `get_num_nans` return one count per request.

Related: #63811 notes this as a separate bug (that issue was closed by the unrelated #63827). #38506 fixed it together with a dict-to-ndarray refactor for MRV1 and MRV2 and was closed by the stale bot on 2026-11-01 without merging. This PR is a minimal MRV2-only fix.

## Claims

- `SamplerOutput.num_nans` is `[num_reqs]` on every MRV2 path (`Sampler`, `RejectionSampler`, TP batch-shard gather), so `num_nans_in_logits`, `vllm:corrupted_requests` and `VLLM_RAISE_ON_LOGIT_NANS` see each request's own count.
- No host sync is added; the per-request sum happens in the Triton kernel, keyed by the on-device `input_batch.cu_num_logits`.
- The kernel is not slower than the old per-row kernel in any of 40 measured shapes on a B300, and about 2-9x faster at up to 32 requests.

## Details

The rejection sampler is where this shows up in practice: it has `1 + num_draft` rows per request. `Sampler` had the same mapping problem when `num_new_sampled_tokens_per_step > 1` without drafts; with one row per request its result is unchanged. The TP batch-shard path already summed rows per request in `_pack_sampler_output_kernel`, so the two paths disagreed on what `SamplerOutput.num_nans` meant.

Fix:
- `get_num_nans(logits, cu_num_logits)` launches one program per (request, 2048-wide vocab chunk). Each program loops over that request's rows for its chunk and `tl.atomic_add`s into a zeroed `[num_reqs]` output. Integer atomics keep the count exact. Rows are clamped to `logits.shape[0]`.
- `Sampler` and `RejectionSampler` pass `input_batch.cu_num_logits`.
- The batch-shard pack kernel copies the per-request value and drops its `local_cu_num_logits_ptr` argument. `AsyncOutput` is unchanged.

Notes:
- The old kernel ran one program per row, which under-occupied the GPU for small batches. A first version with one program per request looping all rows was 2-4x slower at 4 rows per request and was dropped.
- The output needs `torch.zeros` (one extra memset) because chunks accumulate with atomics. This path is opt-in (`VLLM_COMPUTE_NANS_IN_LOGITS`, off by default).
- MRV1 (`count_nans_per_row` / `nans_to_dict` in `gpu_model_runner.py`) has the same row-to-request mapping with spec decode. It is left unchanged to keep this PR MRV2-only; happy to follow up.
