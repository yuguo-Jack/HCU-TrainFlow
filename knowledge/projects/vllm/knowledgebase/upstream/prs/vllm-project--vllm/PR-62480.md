# [ROCm][Kernel] Add W4A8 MoE decode kernel for RDNA3/RDNA3.5 (gfx11)

[Upstream PR](https://github.com/vllm-project/vllm/pull/62480) · state: open · merged: False

## Original PR description

## Overview

This PR adds `moe_w4a8_decode_rdna3`, a fused MoE decode op for RDNA3/RDNA3.5 (gfx11) that runs int4 expert weights against int8 activations. It also adds an opt-in WNA16 MoE backend, `rdna3_w4a8`, that uses it (`--moe-backend rdna3_w4a8`). The default backend selection does not change.

**Why.** On RDNA, batch-1 decode of int4 MoE models is dominated by the Triton WNA16 path (`fused_moe_kernel_gptq_awq`). On Strix Halo (gfx1151) with Qwen3.6-35B-A3B UINT4-G128, the routed experts take 14.4 ms of a 29.4 ms TPOT. Each token reads only about 525 MB of expert weights across 40 layers, a 2.6 ms floor at 211 GB/s. The Triton path reaches about 18% of that bandwidth at M=1: it pays for `moe_align_block_size` padding and has no tuned config for this GPU and shape. The kernel below follows llama.cpp's `mul_mat_vec_q` MoE design (int8 activations, int8 dot products, no token sorting).

**Design.**

- **Weights:** the op reads the `TritonWNA16Experts` tensors as they are (uint8 nibble codes, scales, optional nibble-packed zero points). There is no repack and no extra weight memory, and the Triton fallback shares the same tensors.
- **Three launches, no atomics:**
  1. Activations are quantized to symmetric int8 per 32 values, with a scale and a block sum.
  2. Gate and up projections run fused with SiLU; the intermediate is re-quantized to int8.
  3. The down projection fuses the routing weights and the top-k sum, so each output element is written once. There is no zero-fill, and the result is deterministic.
- **Math:** `v_dot4_i32_iu8` (`__builtin_amdgcn_sudot4`) on the raw 4-bit codes; zero points are applied through the activation block sums.
- **Routing:** top-k expert ids are read directly, so there is no sorting, alignment or padding. Slots whose id is outside `[0, E)` are skipped, which covers experts owned by other ranks under expert parallelism (`expert_map` gives -1).
- **Dispatch:** `Rdna3W4A8Experts` subclasses `TritonWNA16Experts`. It uses the decode kernel when all of the following hold, and falls back to the Triton WNA16 kernels otherwise:
  - 1 to 8 tokens;
  - SiLU activation, no clamp limit;
  - no expert bias, no router weight on the input, no LoRA, no `post_gemm2_hook`;
  - fp16/bf16 activations;
  - hidden size, intermediate size and both group sizes are multiples of 32.

  Prefill and larger batches therefore keep their current performance.
- **Build:** the kernel is compiled with the existing RDNA3 sources (next to `moe_gptq_gemm_rdna3`) and registered under the same guard. `rdna3_w4a8_moe_kernel_available()` requires a gfx11 device and the compiled op, and `Rdna3W4A8Experts` reports itself unsupported otherwise.

## Claims

On Strix Halo (Radeon 8060S, gfx1151, 40 CUs, LPDDR5X about 211 GB/s) with a Quark UINT4 group-128 export of Qwen3.6-35B-A3B (256 routed experts, top-8, hidden 2048, intermediate 512), compared with the Triton WNA16 path:

**End-to-end decode** (512 input / 512 output tokens, batch size 1, greedy, `ignore_eos`, median of 5 runs after 3 warmups, `--enforce-eager`):

| MoE backend | TPOT (ms) | Output tok/s | Speedup |
|---|---|---|---|
| Triton WNA16 (default) | 29.41 | 34.0 | 1.00x |
| **`rdna3_w4a8` (this PR)** | **20.62** | **48.5** | **1.43x** |

- All five `rdna3_w4a8` runs were within ±0.03 ms TPOT.
- With CUDA graphs (`FULL_AND_PIECEWISE`), `rdna3_w4a8` measures 20.64 ms, the same as eager, because decode is bandwidth-bound. Graphs help the Triton path more: 28.4 ms TPOT in a 512 in / 256 out serving benchmark. The new backend is still about 1.4x faster.

**Routed-expert time per token** (`torch.profiler`, 40 layers, M=1):

| Kernel | ms/token | Share of the 2.61 ms bandwidth floor |
|---|---|---|
| Triton `fused_moe_kernel_gptq_awq` | 14.4 | 18% |
| **`moe_w4a8_decode_rdna3`** | **4.27** (3.4x) | **61%** |
| ├ gate/up + SiLU | 3.22 | |
| ├ down + routing weight + top-k sum | 0.97 | |
| └ activation quantization | 0.08 | |

**Accuracy:** GSM8K is unchanged within noise (see Validation).

## Validation

**Kernel tests:** `pytest tests/kernels/quantization/test_rdna3_moe_w4a8.py` runs 63 tests, all passing on gfx1151:

- `test_matches_w4a8_reference` (48 cases): compared with a torch reference that applies the same int8 activation quantization, at tight tolerance. Covers:
  - Qwen3.6-35B-A3B g128, Qwen3-30B-A3B g32 and small g64 shapes;
  - M = 1, 2, 4, 8;
  - fp16 and bf16;
  - with and without zero points.
- `test_close_to_triton_wna16` (12 cases): compared with the Triton WNA16 `fused_experts` path on the same tensors. The tolerance only allows for the int8 activation error, and the test also pins the shared weight layout.
- `test_masked_slots_are_skipped`, `test_repeated_expert_and_zero_input` and `test_deterministic`.

**Wiring:** `tests/kernels/quantization/test_rdna3_compile_guards.py` checks:

- that the op and source are in the RDNA3 compile guards;
- that the backend maps to `Rdna3W4A8Experts`;
- that the backend is opt-in;
- that the kernel reports unavailable on a mocked non-gfx11 device.

**GSM8K** (lm-eval, 5-shot, no thinking, first 100 questions; standard error about ±3.3 points):

| MoE backend | flexible-extract | strict-match |
|---|---|---|
| Triton WNA16 | 88% | 88% |
| `rdna3_w4a8` | 89% | 88% |

75 of the 100 generations are identical between the two backends. A separate 0-shot completion run on the same questions gave 87% vs 88%.
