# [Bugfix][KV Offload] Protect the step's reported HITs from promotion eviction

[Upstream PR](https://github.com/vllm-project/vllm/pull/63551) · state: open · merged: False

## Original PR description

## Purpose
Fix an fs→RAM promotion race in `TieringOffloadingSpec` (CPU primary tier + secondary tier) that crashes the engine under load:

```
AssertionError: Chunk ... not found in cache   (vllm/v1/kv_offload/cpu/manager.py, prepare_load)
```

## Root cause
`lookup()` reports primary-tier chunks as HIT for the current scheduler step, but the scheduler only *pins* them later in the step. Between the two, a secondary→primary **promotion** calls `prepare_write()` on the CPU manager, whose eviction policy may pick exactly those HIT chunks as victims (they look idle). When `prepare_load()` later runs for the reported HITs, the chunk is gone → assert.

Observed in production on v0.32.0 under sustained multi-tenant load: **5 engine crashes in one day** (each `docker logs` shows the assert above from the scheduler's `update_state_after_alloc`). Reported in #60729 (case 2) and #54914; also discussed on #62615.

## Fix
- The tiering manager records the keys its own lookups reported HIT during the current step (`_step_hit_keys`) and passes them as `extra_protected` to the promotion's `prepare_write()`, so the CPU policy cannot evict them. Cleared at `on_schedule_end()`.
- If protecting them leaves no room, the promotion returns `None` and the chunk degrades to a **MISS that the scheduler recomputes** — the pre-existing slow path, never a crash.
- `prepare_write()` gains the optional `extra_protected` argument, applied as a union *view* (no copy of the protected set). The manager's own input keys keep their existing protection.

## Test plan
- New `tests/v1/kv_offload/tiering/test_step_hit_protection.py`: reproduces the assert on unpatched code (promotion evicts the reported HIT) and passes with the fix; also covers the no-room → MISS path and the `_step_hit_keys` clearing.
- Ran the full kv_offload suite in the production image (v0.32.0 + this patch): **116/116 pass** (3 new + 113 existing).
- Production datapoint: the patched image has been serving for ~11 h since deployment with 0 recurrence of the assert, where the unpatched image crashed 5×/day.

Fixes #60729 (case 2). Related: #54914, #62615.

The window this closes is narrow and real. I agree with the comments on this pull request: https://github.com/vllm-project/vllm/pull/63551#issuecomment-6410393225
Regarding the lifespan of the pin, I believe the current fix addresses the symptom, not the underlying issue with the interface.

The `lookup()` function in each tier performs both querying and promotion: it informs the caller
A primary HIT was reported, but the results were not retained for the HIT's lifecycle. The caller must
call `prepare_load()` or `create_store_job()` requires a specific order for correct execution.
Therefore, each new method of calling can potentially reintroduce the same race condition.

I don't recommend using the `extra_protected` flag for steps. A more secure approach would be to implement protection for the results of batch lookups.
probe_batch()
-> primary HIT
-> promote_batch()
-> complete_read()

#62615 has provided the preliminary implementation of probe_batch() and promote_batch(), but has not migrated the scheduler and has not accessed the above life cycle. I can continue to complete these tasks and supplement scheduler, P2P, KVCR and release path tests.

```
# lookup(), primary HIT
self._track_hit(req_context.req_id, key)   # resets on req_id change; skips already-pinned

# _initiate_promotion(), before prepare_write
if self._unpinned_hits:
    self.primary_tier.prepare_read(self._unpinned_hits, req_context)
    self._pinned_hits.update(self._unpinned_hits)

self._release_hits()   # complete_read(self._pinned_hits), clear both sets
```

- jsboige · comment · 2026-10-25T23:48:45Z · [source](https://github.com/vllm-project/vllm/pull/63551#issuecomment-6405089487)

Thanks @orozery — pinning at `_initiate_promotion()` instead of filtering `extra_protected` by the step's HIT set is indeed simpler and stronger: it also covers a promotion initiated by a later request in the same step, which my step-scoped set only protects by accident of ordering.

One check on the release discipline before I rework the branch: the pinned set must be released on **every** exit path, otherwise a single aborted request leaks ref_cnt on its HIT chunks forever and the primary tier stops evicting (silent capacity loss, not a crash). In my reading that means:

- `prepare_load()` success → transfer the tracked keys into the request's load, released by `complete_load()` as today;
- `on_schedule_end()` → release anything still tracked but never pinned by a load (request not scheduled this step);
- `reset_cache()` → release everything, after `drain_jobs()`;
- and the `_unpinned_hits` reset on `req_context.req_id` change must happen **before** `lookup()` reports a new HIT, or the previous request's leftovers get pinned under the wrong context.

If you agree with those four points I'll rework #63551 onto that shape and keep the reproduction test (it fails on stock, passes with the pin). Meanwhile our production runs the step-set variant plus an fs write-admission filter (#198 in our fork: −68 % new fs files, GDN −75 %, disk-served share up from 2.2 % to 4.6 % of prompt tokens in the first 2 h) — the admission filter is orthogonal to this fix and will be proposed separately once the pin lands.

@Alex-ai-future I'd keep #62615 and this PR as alternative fixes for the same race and let @orozery pick the shape, rather than closing either unilaterally — the production datapoint (5 crashes/day on v0.32.0 with RAM+fs tiers) is the same for both.
