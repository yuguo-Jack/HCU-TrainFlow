# [Bugfix][Frontend] Put required properties first in strict tool grammars

[Upstream PR](https://github.com/vllm-project/vllm/pull/65316) · state: open · merged: False

## Original PR description



## Overview

Fixes #65173. Strict tool grammars pin object properties to schema declaration order, so an optional parameter declared before a required one cannot be generated after the model has emitted the required one. This PR reorders each object schema's `properties` so required properties come first in the grammar. It does not change the prompt or the request's tool definitions.

## Claims

- With DeepSeek V4.1 (`deepseek_v41` parser, `--tool-strict-level parameter`) and the issue's schema A (`[locations, action, query]`, `required: ["action"]`), the grammar now accepts `action, locations`. It no longer forces the model into `action, query`. Both property orders in the issue (A and B) now accept the intended call.
- Strict enforcement is unchanged: a missing required parameter and a duplicated parameter are still rejected. This is why the PR does not use `any_order=True`.
- The fix is applied once, in `_dump_tool_for_xgrammar`, and recurses into nested object schemas. It therefore covers every structural-tag model whose grammar pins property order, both the xgrammar builtins (deepseek_v3_1/v3_2/v4/v4_1, qwen_3_coder, kimi, llama, ...) and vLLM-owned builders such as glm_4_7 strict.

## Details

**Root cause.** `get_model_structural_tag` passes the tool's `parameters` to xgrammar (`get_model_structural_tag(model="deepseek_v4_1", ...)`) without `any_order`, so parameters must appear in declaration order. The same holds for JSON-schema values and vLLM-owned `any_order=False` builders such as glm_4_7 strict. For schema A, once the model emits the required `action`, only `query` can follow. The model reasoned that it needed `locations` but could only produce `{action, query}`. Schema B declares `locations` after `action`, so it works. The two schemas are semantically identical.

**Why not `any_order=True`.** It only bounds the number of entries. I verified that it accepts a call with the required `action` missing and a call with `action` duplicated, which weakens strict mode. #55558 (closed) reached the same conclusion.

**Why required-first is safe.** JSON object member order carries no meaning, so every generated call still validates against the user's schema. Within each group (required, then optional), declaration order is kept. After any accepted prefix, the properties that required-first makes unreachable are a subset of those that declaration order makes unreachable:
- Emitting a required property never makes anything unreachable, because every earlier property is required and has already been emitted.
- Emitting an optional property makes only the earlier optional properties unreachable, which declaration order does too.

The cost is that some strings the old grammar accepted are now rejected, namely an optional property generated before a required one. Under constrained decoding this redirects the model rather than losing a property: it emits the required properties first and can still emit any optional property afterwards. This is the change behind the one existing test update: `test_kimi_k3_property_ref_to_root_defs_compiles_and_accepts` checks `$defs` re-attachment, and its nested value listed optional `build` before required `index`. It now lists them required-first.

**Design choices.**
- *Grammar-only.* The prompt-rendered schema is unchanged. Reordering the prompt, as #55558 did for GLM, would change model inputs for every user, including non-strict ones. Under the grammar a model that follows prompt order can still produce any valid parameter set.
- *Recursive.* Nested object values are JSON-schema constrained with the same declaration-order pinning. #55558 reported this failure mode on nested objects (a required `tag` was dropped after an optional `choices`). The helper descends through `properties`, `items`/`prefixItems`, `additionalProperties`, `anyOf`/`oneOf`/`allOf`/`not`, `patternProperties` and `$defs`/`definitions`. It never touches data keywords (`const`, `enum`, `default`, `examples`), where key order could matter.
- *One shared place.* `_dump_tool_for_xgrammar` is the single path for both xgrammar builtins and vLLM-owned builders. It copies the dicts it changes and never mutates request objects; the tests assert this. Non-strict tools are unaffected because their grammars do not use the schema. Builders that are already order-agnostic (kimi_k3 top-level arguments) or already required-first (hy_v4) produce equivalent results.
- Docs: `docs/features/tool_calling.md` (Strict Mode) describes the enforced order.

**Limitations / follow-ups.**
- The experimental Rust frontend builds its own tool grammar inputs in `rust/src/parser/src/output_grammar.rs::tool_params` (serde_json with `preserve_order`), so it keeps declaration order. That is a temporary divergence from the Python frontend. No Rust toolchain was available to build and test a port, so it is left as a follow-up.
- Tool parsers without a structural tag fall back to a plain JSON-schema grammar for `tool_choice="required"` or a named tool (`get_json_schema_from_tools`). That grammar pins declaration order too: `xgr.Grammar.from_json_schema` on schema A rejects `{"action": ..., "locations": ...}`. This PR does not change that path. It does not affect DeepSeek V4.1 or other structural-tag parsers, and could be a follow-up.
- `allOf` schemas that put `required` and `properties` in different branches are not reordered; their behavior is unchanged.

**Not a duplicate.** `gh pr list --repo vllm-project/vllm --state open --search "65173 in:body"` returns nothing, and keyword searches ("required first property order tool", "structural tag property order") found no open PR touching this. #55558 (closed by its author) was GLM-only and reordered the prompt as well. This PR is grammar-only and applies to all structural-tag models. #50933 (open) resolves `$ref`/`$defs` and is orthogonal.
