# [Rust Frontend] Match DeepSeek DSML markers by token identity

[Upstream PR](https://github.com/vllm-project/vllm/pull/62875) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

Make the Rust DeepSeek DSML tool parser (V3.2, V4, V4.1) treat the tool-calls and invoke markers as structure only when their `｜DSML｜` is the dedicated token, so DSML written with ordinary tokens stays text. Stacked on #62874, which passes attributed deltas and the tokenizer to tool parsers. The matching reasoning change for `</think>` is #62892, independent of this stack.

## Claims

- DSML written with ordinary tokens, for example the model explaining the format in its answer, no longer starts a tool call.
- Ordinary `</｜DSML｜invoke>` / `</｜DSML｜tool_calls>` inside a string argument no longer end the invoke early.
- An ordinary partial `<｜DS` streams immediately instead of being held back.
- Output with the dedicated token parses exactly as before. DeepSeek V3.2-Exp, whose tokenizer has no `｜DSML｜` token, keeps matching by spelling.

## Details

- **Root cause:** the parser matched every marker with `literal` / `take_until` on decoded text, so it could not tell the dedicated `｜DSML｜` token from the same bytes spelled by ordinary tokens.
- **Markers:** in every DSML marker only `｜DSML｜` is an added token (V4/V4.1 id 128825, `special=false`; V3.2 id 128793, `special=true`); `<`, `tool_calls>`, `invoke`, `parameter` are ordinary pieces. Each marker is therefore `Marker::text("<").then_special(｜DSML｜).then_text("tool_calls>")`: the guard sits mid-marker, candidates come from text occurrences, and the identity check happens when the marker is parsed. This reuses the Kimi K3 `Marker` / `MarkerStream` utilities from #58358; no new utility types.
- **Parsing:** the buffer is a `DecodedText` parsed with `parse_buffered_event_attributed`. The invoke closer is found with `take_until_marker` on the streaming buffer, so an ordinary closer inside a value no longer ends the invoke.
- **Fallback:** when the tokenizer lacks `｜DSML｜` (DeepSeek V3.2-Exp spells DSML with ordinary tokens), the markers fall back to spelling.
- **Why token identity:** DeepSeek's own streaming output parser matches these markers the same way: it splits each marker into plain and special segments and lets special segments match only bytes decoded from the added token ([deepseek-recipe `output_parser.rs`](https://github.com/deepseek-ai/deepseek-recipe/blob/935817c66f5d6e64838f419692545f06787e485f/deepseek-recipe/src/stream/output_parser.rs#L338-L408)).
- **Known limitation, parameters:** as for the Kimi K3 call body in #58358, a complete invoke body is still parsed from text, so an ordinary `</｜DSML｜parameter>` inside a string value still ends the value. Guarding parameter markers needs an attributed view of a complete body; that interface is left to a follow-up shared with the K3 call body. Keeping parameters text-matched also agrees with the output grammar, whose `deepseek_xml` argument style constrains parameter markers by text.
- **Known limitation, grammar:** the tool-call structural tags still constrain DSML by text. Under `tool_choice=required`, a named function or `strict` tools, a grammar-forced tool-calls or invoke marker spelled with ordinary tokens would be accepted by XGrammar but read as text by the parser. The model strongly prefers the dedicated token, so this is unlikely, but it is silent. XGrammar 0.2.7 can express token-level boundaries (`Token` in sequences, `token_dispatch`); that is a separate change.

Not a duplicate: the open DeepSeek DSML PRs (#62517, #62259, #54686, #58322, #61142) change the Python parsers or the tokenizer encoding. #62290 changes the same Rust DSML parser to drop an incomplete call at `max_tokens`; it is a different behavior, and whichever lands second needs a rebase.
