# [CI] Run H100 fusion config sweeps and batch invariance nightly only

[Upstream PR](https://github.com/vllm-project/vllm/pull/65567) · state: open · merged: False

## Original PR description



## Overview

Make three H100 steps nightly-only (`optional: true`) to relieve the saturated `mithril-h100-pool` queue: `fusion-e2e-config-sweep-h100`, `fusion-e2e-tp2-ar-rms-config-sweep-h100` and `batch-invariance-h100`. Their AMD mirrors keep running on PRs (`optional: false`, same pattern as `distributed.yaml` / `lora.yaml`).

## Claims

- Frees ~465 of the ~483 GPU-hours/week these steps used on the H100 pool (~10% of `ci`'s H100 GPU-hours). They now run once per nightly instead of on every selected PR and main build.
- No loss of per-PR coverage in either area apart from the H100-specific runs listed under Details.
- No change to AMD scheduling.

## Validation

Data from Oct 27 – Nov 3 2026, collected through the Buildkite REST API for the `ci` pipeline:

| step | GPUs | GPU-h / week | PR jobs passed | PR jobs failed |
|---|---|---|---|---|
| `batch-invariance-h100` | 1 | 226 | 585 | 0 |
| `fusion-e2e-tp2-ar-rms-config-sweep-h100` | 2 | 207 | 360 | 0 |
| `fusion-e2e-config-sweep-h100` | 1 | 50 | 360 | 0 |

The PR jobs that didn't pass were canceled or `waiting_failed`; none failed.

Generator behavior was checked locally against ci-infra `main` (`eb2d628f`) by loading the edited yaml with `step.parse_steps_from_yaml`, then evaluating `_step_should_run` and `_get_amd_mirror_effective_step` on a PR diff touching `vllm/compilation/` and `vllm/model_executor/determinism/`:
- NVIDIA steps: `optional=True`, so they don't run on a PR and do run with `NIGHTLY=1`.
- AMD mirrors: `optional=False`, so they still run on the PR.

When `ci-selector` is on, `pipeline_generator._selector_decision` removes optional keys from the selector's choice, as on every PR build today; recent decisions show `selector_optional_dropped` of ~148 keys per build. AMD keys stay on the path rules.

`pre-commit run --files .buildkite/test_areas/compile.yaml .buildkite/test_areas/misc.yaml` passes.

## Details

Why these steps:
- The H100 pool's p90 queue wait was 46 min that week (p99 115 min), compared with 5–14 min on the H200-slice and B200 queues.
- Each of the three steps had 0 PR failures and has a sibling that still runs per-PR:
  - The fusion sweeps run the full config grid. `fusion-e2e-quick-h100` and `fusion-e2e-tp2-quick-h100` (plus `fusion-e2e-tp2-b200`) still cover fusion on PRs. The B200 sweep (`fusion-e2e-config-sweep-b200`) is already nightly.
  - `batch-invariance-b200` runs on PRs and its commands are a superset of the H100 step's.

What moves to nightly-only:
- **Hopper batch invariance.** The Qwen3-FP8 `FLASH_ATTN` needle test on H100 exercises FA3; on B200 the same test takes a different FlashAttention path.
- **Full H100 fusion sweeps.** Only the quick subsets keep running on H100 per PR.
- PRs can still run these steps through "Run more jobs" or a `ready-run-all-tests` label.
- A PR that edits one of these step definitions still runs it, through the selector's changed-steps rule.

Not in this PR: `replayssm-e2e` is 26.5% of `ci`'s H100 GPU-hours. Narrowing its `source_file_dependencies` would not help, because on 22 of 30 recent PR builds that ran it, `ci-selector` chose it itself (`added-by-coverage`). The remaining 8 were run-all, nightly or explicit builds. Reducing it needs a selector or test-size change, which will be a separate discussion.

Duplicate check: `gh pr list --repo vllm-project/vllm --state open --search` on "batch invariance nightly", "config sweep nightly", "fusion e2e sweep", "H100 nightly" and "batch-invariance-h100" returned no PR that changes these steps' scheduling.
