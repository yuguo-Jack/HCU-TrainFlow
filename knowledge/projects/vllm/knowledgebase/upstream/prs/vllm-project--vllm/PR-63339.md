# [Bugfix][CPU] Match GPU conv-state layout in GDN spec decode

[Upstream PR](https://github.com/vllm-project/vllm/pull/63339) · state: closed · merged: True

## Original PR description



## Overview

On CPU, the GDN speculative-decode path updates the conv state with a different layout from the GPU `causal_conv1d_update`. The two agree only when a row has the full `num_spec + 1` tokens. Any shorter row, such as one where the drafter proposed fewer tokens, or a decode row with no drafts that MRV2 still keeps as a spec row, makes the next step read the wrong conv history. If the previous step accepted more tokens than the row now has, it crashes:

```
RuntimeError: The size of tensor a (6) must match the size of tensor b (5) at non-singleton dimension 1
```

#62888 started running the MRV2 kernel warmup on CPU. That warmup always produces such a row, so `CPU-Spec Decode` (`tests/v1/e2e/test_cpu_spec_decode.py::test_v2_speculator_smoke[mtp]`) has failed at engine startup on every main build since [96655](https://buildkite.com/vllm/ci/builds/96655). See the [log in 96693](https://buildkite.com/vllm/ci/builds/96693#01a164c7-7cb9-4409-9585-8ef607bba33f).

This PR makes the CPU path write the conv state with the GPU layout.

## Claims

- CPU GDN spec decode convolves over exactly the accepted token history for any per-row token count `1..num_spec+1` and any `num_accepted`. Previously it crashed when `num_accepted > query_len`, and returned wrong conv outputs after a row shorter than `num_spec + 1`.
- `test_v2_speculator_smoke[mtp]` gets past the startup warmup again.
- Full-length batches still use the native AMX / Arm BF16 kernel.

The new test runs several spec steps with uneven per-row token counts and accepted counts. For each step it compares `_spec_forward`'s conv output against a naive `F.conv1d` over the true accepted history. The CPU SSM kernel is stubbed out, since it does not touch the conv state.

## Details

**Layout.** The conv buffer is `(dim, state_len)` with `state_len = width - 1 + num_spec`. Each step reads its history at column `num_accepted - 1`. The GPU kernel then writes `[history[1:], x]`, i.e. `width - 2 + q` columns, from column 0, so the next step's offset lands right after the accepted tokens. The CPU fallback instead wrote `[B[num_accepted : ...], x]` right-aligned to the end of the buffer. That only matches when `q = num_spec + 1`, and when `num_accepted > q` it produced a slice one column short, which is the crash. The fallback now writes `conv_in[:, 1:]` (the history it just read plus `x`) from column 0. The native `causal_conv1d_update_cpu` kernel also right-aligns, and it rejects `num_accepted > seqlen`. It is now used only when every row is full-length, where the two layouts are identical. Mixed-length batches already used the fallback, so in practice this adds the fallback only for batches where every row is equally short.

**Why CI broke now.** MRV2 keeps decode rows without drafts as spec rows (`q = 1`) carrying the previous step's `num_accepted` (`mamba_hybrid.py`). `warmup_kernels` runs an all-spec step and then a mixed step in which one request has no drafts, so warmup always reaches the crash. Serving reaches the same state whenever a request gets fewer drafts than `num_spec`.

**Relation to #56518.** That open PR handles `num_accepted == 0` in the same fallback loop, so the two will conflict textually. The cases are independent, and whichever lands second needs a trivial rebase.

**Not a duplicate.** Searched open PRs and issues for `_spec_forward`, `gdn_attention cpu`, `CPU GDN conv`, `test_cpu_spec_decode`, `62888` and `cpu spec decode mtp`. Only #56518 touches this code, for a different case.

No model evaluation: the e2e smoke test above exercises MTP on Qwen3.5-0.8B, and the unit test checks the conv outputs against a reference.
