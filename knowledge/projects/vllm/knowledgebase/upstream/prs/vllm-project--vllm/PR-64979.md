# [Perf] Add SM90 skinny GEMM plans for dense Qwen3 and Llama-3.1 decode (TP=1)

[Upstream PR](https://github.com/vllm-project/vllm/pull/64979) · state: open · merged: False

## Original PR description



## Overview

#62956 routes unquantized BF16 linear layers and LM heads through the shape-dynamic CuTe DSL skinny GEMM when `skinny_gemm_plans.py` has a measured plan for the device, the local `(N, K)` and the token count. SM90 has no plans, so on H100 / H200 every dense decode GEMM still goes to cuBLAS, which reads the weight at 2.3-3.7 TB/s at 1-4 tokens.

This PR adds `SM90_SKINNY_GEMM_PLANS` for the TP=1 local shapes of Qwen3-4B / 8B / 14B / 32B and Llama-3.1-8B (QKV, o_proj, fused gate/up, down, LM head), registered under capability `(9, 0)`. No code path changes: shapes or token counts without a plan keep using cuBLAS.

## Claims

- **E2E, H200, one request:** median TPOT -14.9% on Qwen3-8B (6.02 -> 5.12 ms), -12.5% on Qwen3-4B, -11.0% on Llama-3.1-8B, -10.5% on Qwen3-14B, -12.7% on Qwen3-32B (20.24 -> 17.68 ms). Two concurrent requests: -8.3% to -12.2%. Four: -5.4% on Qwen3-8B, -3.9% on Qwen3-32B, -2.3% on Qwen3-14B, within run-to-run spread on Qwen3-4B and Llama-3.1-8B. Eight: unchanged (batch > 4 stays on cuBLAS).
- **`Qwen/Qwen3-30B-A3B` (BF16 MoE, `torch.compile`), added after the first review round:** three dense cells (fused QKV `(5120, 2048)`, o_proj `(2048, 4096)`, LM head `(151936, 2048)`): median TPOT -5.5% at one request (4.755 -> 4.493 ms), -2.6% at 2, about -3% at 4, unchanged at 8 (no plan).
- **Accuracy:** GSM8K 5-shot on Qwen3-8B (1319 questions, greedy, 2 concurrent requests so decode runs the planned kernels): 0.8886 without, 0.8893 with the plans.
- **Kernels:** 52 cells, each 1.07x-1.61x faster than cuBLAS with the weight read from HBM. A cell is listed only when it also wins with a hot L2 and, for 4 tokens, inside a running model (see Details).

## Details

- **4 tokens are checked inside the model.** For 4 tokens the isolated benchmark does not always predict the model. Each 4-token candidate was checked with an nsys trace of 4 concurrent requests (GEMM time per projection per decode step, cuBLAS time including its split-K reduce). Kept: Qwen3-8B o_proj 511 -> 427 us, gate/up 2071 -> 1922 us, down 1158 -> 1041 us; Qwen3-4B o_proj 387 -> 320 us, gate/up 1137 -> 1103 us; Llama-3.1-8B o_proj 452 -> 383 us; Qwen3-14B down 2077 -> 1898 us; Qwen3-32B o_proj 1811 -> 1553 us, down 4867 -> 4393 us. Dropped although they win in isolation: Llama-3.1-8B down `(4096, 14336)` (1.09x isolated, 1075 -> 1349 us in the model, made concurrency 4 3% slower) and Qwen3-14B QKV `(7168, 5120)` (1.15x isolated, 970 -> 1025 us in the model).
- **A/B testing plan changes needs a cold compile cache.** Whether a layer calls the skinny op is decided while `torch.compile` traces the model, and the plan file is not part of the compile cache key. Two servers of the same vLLM build, one with and one without a plan, can therefore load each other's cached graph. All E2E numbers above use `VLLM_DISABLE_COMPILE_CACHE=1`; without it, a second run of the PR arm reproduced the baseline.
- **Why the gain is largest at 1 token.** cuBLAS picks small-M `nvjet` tiles (often split-K with a separate reduce kernel) that reach 2.3-3.7 TB/s on these weights; the skinny GEMM streams the weight once with vectorized loads, reaches 3.6-4.3 TB/s, and removes the reduce kernel.
- **Startup cost.** The planned configs are compiled by the CuTe DSL warmup before CUDA graph capture: 12 compile units for Qwen3-8B (9 for Llama-3.1-8B), about 5-10 s in the server logs, once per process (no disk cache for CuTe DSL kernels today, same as the existing SM121 plans).
- **H100 / H800 / H20.** The plans are keyed by capability `(9, 0)` and were measured on an H200 only (132 SMs, 4.8 TB/s). The kernel is bandwidth bound at these sizes, so the ranking should hold on H100, but the margins were not measured there and the table header says so. I can re-measure on an H100 if a reviewer has one; otherwise the existing per-capability keying is what the SM121 table also relies on.
- **Scope.** TP=1 dense models only; TP>1 local shapes and MoE models are not covered.
