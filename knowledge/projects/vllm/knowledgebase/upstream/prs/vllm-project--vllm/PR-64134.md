# [Bugfix][FA4] Warm non-persistent SM90 prefill kernels for Gemma-4

[Upstream PR](https://github.com/vllm-project/vllm/pull/64134) · state: open · merged: False

## Original PR description

## Overview

On H100, Gemma-4 with FA4 JIT-compiles `FlashAttentionForwardSm90` on its first requests, about 4 s each. The SM90 dense warmup only builds the statically persistent kernel. This PR also warms the non-persistent prefill variant for the hd512 full-attention and hd256 sliding-window layers. Related: #49349, #63279.

## Claims

- No runtime FA4 JIT on Gemma-4 SM90 (2 per rank before).
- First short request: 4.2 s → 0.28 s. First tool-call request: 3.9 s → 0.05 s.
- Blackwell keys and the SM90 SplitKV/combine keys are unchanged.

## Validation

Gemma-4 31B BF16 + MTP (k=4), TP8, H100, `--attention-config '{"flash_attn_version": 4}'`, `--jit-monitor-verbose`, with mixed sampling/JSON/tool traffic at batch sizes 1–64:

| | FA4 warmup keys | Runtime FA4 JIT | 1st request | 1st tool call |
|---|---|---|---|---|
| `main` | 5 | 2 per rank | 4.20 s | 4.02 s |
| This PR | 8 | 0 | 0.28 s | 0.05 s |

No unit test yet, and no Hopper CI step covers this path.

## Details

FA4 only runs the persistent kernel when the packed query fits in one Q tile. Warmup compiles with `max_seqlen_q=1`. The V2 warmup's long-query runs all use more than 256 requests, which selects a different kernel variant (the varlen batch lookup). A small batch with a prompt longer than 16 tokens (hd512) or 64 tokens (hd256) therefore hit an uncompiled kernel. The SM90 hd256 sliding layers had no warmup keys at all.

The fix adds `is_static_persistent` to the compile key. Non-split keys compile with `max_seqlen_q=257`, which exceeds every SM90 tile. Warmup goes from 5 to 8 compiled kernels, still only for Gemma-4 with FA4.

#63279 makes a similar change for Blackwell only and leaves SM90 as is. Both PRs edit the same function, so whichever lands second needs a rebase.
