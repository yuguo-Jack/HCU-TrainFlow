# [Benchmark] Fix benchmark_marlin so it runs, and add a ragged-M sweep

[Upstream PR](https://github.com/vllm-project/vllm/pull/60066) · state: open · merged: False

## Original PR description

## The problem

Two things, and the first one surprised me.

**`benchmark_marlin.py` does not currently run at all.** I hit three independent failures in order on a fresh A10G:

1. It imports `rand_marlin_weight_fp4_like`, which no longer exists anywhere in the tree. The helper was split into nvfp4 and mxfp4 variants (`tests/kernels/moe/test_moe.py` already uses the new names) and this import was never updated, so the module dies at import time before parsing a single argument.
2. `gen_marlin_params` bare-returns for quant type and group size combinations Marlin does not support, but the caller unpacks the result, so you get `TypeError: cannot unpack non-iterable NoneType object`. This fires on the default sweep, for example `float4_e2m1f` at any group size other than 16.
3. `repack_supported` only checks the group size, so `uint4` reaches `gptq_quantize_weights`, which accepts GPTQ types only and asserts with `Unsupported gptq type = uint4`.

**Separately, the default batch-size sweep cannot see what a ragged M costs.** The default is `[1, 16, 32, 64, 128, 256, 512, 1024, 2048, 4096, 8192]`, and every entry above 64 is a multiple of 64. Marlin sets `max_thread_m_blocks = 4`, so one launch covers at most 64 rows of M and the `while (rest_m)` loop in `marlin.cu` gives the leftover rows their own launch. In that loop only `A_ptr`, `a_s_ptr` and `C_ptr` advance; `B_ptr` and `b_s_ptr` do not, so the extra launch streams the whole packed weight a second time. Since the sweep never leaves a remainder, that cost is invisible.

It matters for decode, where M is however many sequences happen to be running and is usually not a multiple of 64.

## The changes

No kernel code. One file.

The three fixes above, each minimal: retarget the import to `rand_marlin_weight_nvfp4_like` (which matches the `group_size == 16` guard immediately below it), skip the shape when `gen_marlin_params` bails instead of unpacking `None`, and check the quant type as well as the group size before using the GPTQ repack path.

Then an opt-in `--ragged-m` flag that, for every requested batch size at or above one M tile, also sweeps just past that size's tile boundary (offsets of 1 and 8 rows). The default sweep is unchanged, so existing numbers cannot move. With the flag the default grid grows from 11 sizes to 27, adding 65, 72, 129, 136, 257, 264, 513, 520, 1025, 1032, 2049, 2056, 4097, 4104, 8193 and 8200. That covers both the 64-row tile knee and the 1024-row knee where `max_par = 16` runs out.

I deliberately left the kernel alone. Whether the remainder launch should reuse B is worth discussing on its own, and I would rather the benchmark be able to measure it first.

## Testing

Ran on one A10G (sm86, 80 SMs), vLLM nightly `0.30.1rc1.dev671+gedde9d2ce`, torch 2.13.0+cu130.

Default sweep still behaves exactly as before, and now completes:

```
$ python benchmark_marlin.py --batch-sizes 16 64 128 --limit-k 4096 \
    --limit-n 4096 --limit-group-size 128 --limit-num-bits 4
Batch sizes: [16, 64, 128]
...
      q=uint4b8, g=128, MKN=(16x4096x4096)   |      75.7      |      33.4     |        35.2        |         42.3
      q=uint4b8, g=128, MKN=(64x4096x4096)   |      75.1      |      49.4     |        51.0        |         42.3
      q=uint4b8, g=128, MKN=(128x4096x4096)  |      83.7      |      79.4     |        84.8        |         42.3
```

With `--ragged-m`, the sweep picks up the ragged sizes and the steps show up:

```
$ python benchmark_marlin.py --batch-sizes 64 128 --limit-k 4096 \
    --limit-n 4096 --limit-group-size 128 --limit-num-bits 4 --ragged-m
Batch sizes: [64, 65, 72, 128, 129, 136]
...
      q=uint4b8, g=128, MKN=(64x4096x4096)   |      74.9      |      49.3     |        50.8        |         42.3
      q=uint4b8, g=128, MKN=(65x4096x4096)   |      90.1      |      71.6     |        74.7        |         42.3
      q=uint4b8, g=128, MKN=(72x4096x4096)   |      90.2      |      71.8     |        75.1        |         42.3
      q=uint4b8, g=128, MKN=(128x4096x4096)  |      83.8      |      79.4     |        84.9        |         42.3
      q=uint4b8, g=128, MKN=(129x4096x4096)  |     163.6      |     101.9     |       110.3        |         42.3
      q=uint4b8, g=128, MKN=(136x4096x4096)  |     163.6      |     102.4     |       110.7        |         42.3
```

`marlin_gemm` goes from 49.3 us at M=64 to 71.6 us at M=65, so one extra row costs 45%, and 79.4 to 101.9 at the 128 boundary. Worth noting the `pytorch_gemm` reference column steps as well, 83.8 to 163.6 at the same 128 boundary, so cuBLAS has its own breakpoints there. That seems worth being able to see.

Also ran, on a machine without a GPU:

- `ruff check` and `ruff format --check`, pinned 0.14.0, on the changed file: both clean.
- `ast.parse` on the changed file: clean.
- Checked `expand_ragged_m` on Python 3.12: it is additive, every default entry survives, output is sorted and deduplicated, sizes below one tile are left alone, and 11 sizes becomes 27.

One thing I could not run: full `pre-commit`. Its `clang-format` hook builds LLVM from source and the host I have has GCC 7.3.1 where CMake wants 7.4 or newer. That is my environment, not this diff.

## Not a duplicate

`gh pr list --state open --search "benchmark_marlin"` returns nothing and `gh issue list --state all --search "benchmark_marlin batch size"` returns nothing. A broader search for "marlin benchmark batch sizes" returns only keyword noise (#55225, #38338, #48032, #52915 and similar), none touching this file or any batch-size grid. The last three commits to the file (#32688, #32952, #24722) did not revisit the sweep. I found no open issue reporting that the script fails to import.

Two existing issues concern Marlin M tiles in the opposite direction, selecting a tile that is too large rather than leaving a remainder: #48066 and #56744. Neither touches the benchmark.
