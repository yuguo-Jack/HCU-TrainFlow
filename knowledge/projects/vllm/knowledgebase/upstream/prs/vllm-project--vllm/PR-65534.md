# [Core][MM] Make the multimodal encoder cache size configurable 

[Upstream PR](https://github.com/vllm-project/vllm/pull/65534) · state: open · merged: False

## Original PR description

## Motivation
Currently: encoder_cache_size is currently tied to max_num_batched_tokens, preventing independent control of encoder cache residency and limiting cross-request reuse. In Production traffic serving, we found that it is not good. 

`SchedulerConfig.encoder_cache_size` was derived from `max_num_batched_tokens` and marked `Field(init=False)` with a standing TODO. Add `--encoder-cache-size` so it can be set on its own, defaulting to the current derivation.

The two encoder knobs are different quantities that happen to share a value today: `max_num_encoder_input_tokens` is a per-step compute budget, while `encoder_cache_size` is a capacity that decides how long encoder output stays resident across requests. Deriving the second from a per-step batch budget caps cross-request encoder reuse at `max_num_batched_tokens / tokens_per_item` items with no way to raise it independently.

Also fix the memory profiling for it. `get_encoder_budget()` returns `min(compute_budget, cache_size)` and that feeds how many dummy items `profile_encoder_cache` leaves resident, so once the cache is larger than the compute budget the profiled peak under-reserves and the surplus is handed to the KV cache. `reserve_encoder_cache_residency()` tops the dummy cache up to the configured capacity at all three profiling sites; the dummy compute batch is left alone so the activation peak being profiled does not change. `get_encoder_budget()` itself is unchanged -- it also bounds `mm_max_items_per_batch`, which is correctly limited by both budgets.

Keep the existing `max(..., max_tokens_per_mm_item)` floor, without which a small value would start rejecting single items in `_validate_model_input`, and warn when it raises an explicit request. Log the resolved capacity in GiB as well as tokens, since the cached tensor is the multimodal embedding width and the cost per token is model-dependent.
