# [Perf][Attention][PCP] Reuse MLA context across PCP virtual rows

[Upstream PR](https://github.com/vllm-project/vllm/pull/57668) · state: open · merged: False

## Original PR description

## Purpose

PCP represents chunks of the same request as separate virtual rows. During MLA prefill with an existing KV cache, adjacent PCP rows from the same request can independently materialize overlapping historical context.

This PR reuses the shared cached context across eligible PCP virtual rows. For an adjacent two-row same-request layout, the shared historical context is materialized once, while the second row only processes the additional cached tail it needs.

The optimization preserves the original query slices and attention semantics. Unsupported layouts fall back to the existing chunked-context path.

The current optimization is limited to:

* dense causal MLA;
* DCP=1;
* no sliding-window attention;
* at most two adjacent PCP rows for the same request.

The change is complementary to existing MLA context optimizations: it specifically removes duplicated same-layer historical-context preparation introduced by PCP virtual rows.

### Relation to existing work

This PR does not duplicate the closest existing MLA context optimizations:

* #50613 changes how MLA context chunks are scheduled into the workspace to reduce the number of chunks. It does not deduplicate overlapping historical context represented by multiple PCP virtual rows of the same request.
* #53166 fuses the cost of an individual MLA context gather/projection path on ROCm/AITER. This PR instead reduces how many times the same historical context is materialized, and targets the common dense MLA path used by PCP.
* #56986 reuses the same main-KV gather across multiple DeepSeek-V4.1 decoder layers and explicitly excludes PCP. This PR operates within one layer, reusing context across adjacent PCP virtual rows of the same request.

The optimization here is therefore PCP-specific, same-layer reuse across virtual rows, rather than workspace scheduling, per-gather kernel fusion, or cross-layer reuse.

AI assistance was used during implementation and review. All changes and test results were reviewed by the submitter.

## Test Plan

Unit test:

```bash
pytest -q tests/v1/attention/test_pcp_context_reuse_mla.py
```

The tests cover:

* shared-context reuse plus an additional cached tail;
* non-page-aligned cached-context gaps;
* mixed decode/prefill batches;
* singleton requests around a PCP pair;
* fallback when DCP > 1.

## Test Result

### End-to-end performance

At 192K input length, average end-to-end latency over 3 runs decreased from:

```text
58.21 s -> 54.75 s
```

a **5.9% reduction**.

The benefit increases with context length, consistent with eliminating duplicated processing of shared historical context.

### 192K profiler attribution

| GPU work                              | Baseline PCP | Context reuse |     Change |
| ------------------------------------- | -----------: | ------------: | ---------: |
| `gather_and_maybe_dequant_cache_page` |     651.5 ms |      325.7 ms | **-50.0%** |
| `direct_copy` kernel family           |     17.561 s |       9.123 s | **-48.0%** |
| CUTLASS GEMM candidates               |     21.083 s |      12.750 s | **-39.5%** |
| Dynamic FP8 quantization              |      1.266 s |       0.830 s | **-34.4%** |
| FlashAttention variants, combined     |    281.029 s |     277.817 s |  **-1.1%** |
| `concat_and_cache_mla`                |     118.6 ms |      119.3 ms |        ~0% |
| `merge_attn_states`                   |     909.9 ms |      961.4 ms |      +5.7% |
| PCP AllGather + ReduceScatter         |     13.499 s |      13.489 s |        ~0% |

The near-50% reductions in KV gather/dequant and direct-copy work are consistent with eliminating duplicated materialization of shared historical context for the second PCP virtual row.

In contrast, aggregate FlashAttention time, MLA cache concatenation, attention-state merging, and PCP collective time remain approximately unchanged. The measured benefit is therefore concentrated in cached-context preparation rather than the underlying attention computation or communication.

Profiler values are summed CUDA kernel durations. PCP values sum kernel time across both GPUs, so these totals should not be interpreted as wall-clock latency.

The CUTLASS kernels and FlashAttention variants cannot be uniquely mapped to individual MLA operations from this trace because corresponding business-level NVTX ranges are not present. They are therefore reported as kernel families/candidates rather than attributed to a specific projection or attention sub-path.
