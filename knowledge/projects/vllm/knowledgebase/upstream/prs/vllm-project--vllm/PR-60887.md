# [KV Connector][Mooncake] Publish Store residency once per complete block

[Upstream PR](https://github.com/vllm-project/vllm/pull/60887) · state: open · merged: False

## Original PR description

## Summary

`MooncakeStoreConnector` now publishes a block's `BlockStored` event once, when every Store namespace that a later lookup probes for the block's cache group has reported. The previous rule decided quorum from how many workers reported during one engine step; that count carries no rank identity, so one rank reporting a block twice after an eviction reached a two-worker quorum alone, and entries whose second report never arrived stayed forever.

Builds on #58293, which adds the base residency event plumbing. This PR adds the per-cache-group namespace quorum and the Store wipe epoch.

## Change

- `MooncakeStoreKVEvents` keys pending state by `(group_idx, block_hash)` and releases a block when the reporting ranks' namespaces cover the set `_lookup_key_prefixes` holds for its cache group. Coverage accumulates across engine steps, so ranks finishing the same block in different steps produce one announcement.
- The announcement carries the payload the accumulator holds: a tokenless completion cannot replace tokens an earlier report carried, and a later report with the token ids replaces a held tokenless payload.
- The quorum uses the group's own prefixes, so replicated GQA/MQA, rank-specific shards, PCP, DCP, PP and `store_tp_size` layouts need no second topology formula.
- Events name the cache group by the core cache group id, not the Store's group index, which shifts when the Store skips a group the core keeps.
- Dedup hits count: an all-resident block is reported, and a partial `batch_put` failure reports only the blocks it committed.
- A Store wipe bumps `_residency_epoch`; every rank applies the newer epoch through the connector metadata before its own lookups and saves: it joins its send queue, removes the Store objects its buffered reports name while skipping keys the wipe already removed, and drops those reports. `AllBlocksCleared` retires the accumulator's epoch, and the announced-block ledger survives only if the reset failed.
- `KVOutputAggregator` folds worker containers with `KVConnectorKVEvents.merge`; the base implementation preserves the previous `add_events(get_all_events())` behavior, so other connectors are unaffected.

## Validation

Unit suite on this head, CPU run (Python 3.12.14, torch 2.14.0):

```
pytest tests/v1/kv_connector/unit/test_mooncake_store_*.py \
       tests/v1/kv_connector/unit/test_output_aggregator.py \
       tests/v1/kv_connector/unit/test_lmcache_connector.py -q
```

`582 passed, 5 skipped`. `ruff check` and `ruff format --check` are clean on the changed files.

End to end on one 8xH20 host, two ranks, TP=2, `kimi-linear-flashkda` with `--mamba-cache-mode align`, embedded Mooncake segment per rank, 4106-token prompts with the first prompt repeated at the end of each run. The collector snapshots the Store key list as every event batch arrives. The baseline is the same tree with the four connector files taken from #58293.

| revision | segment/rank | put failures | announcements | distinct blocks | announced twice |
| --- | --- | --- | --- | --- | --- |
| this PR, 8 prompts + repeat | 4 GB | 0 | 152 | 152 | 0 |
| #58293, same workload | 4 GB | 0 | 152 | 152 | 0 |
| this PR, 8 prompts + repeat | 24 MB | 9 / 10 / 12 | 107 / 108 / 134 | = announcements | 0 / 0 / 0 |
| #58293, same workload | 24 MB | 11 / 11 | 117 / 118 | 106 | 11 / 12 |

Healthy runs announce exactly what the Store holds: 176 objects and 152 complete blocks, none premature, none missing, and the repeated prompt adds none. Under 24 MB segments puts fail and the old rule announces 11 and 12 blocks twice, while this revision announces each block once and never announces an uncommitted one. The Store also reclaims objects it accepted there, ending with 72-73 objects and 58-64 complete blocks out of roughly 150 written per rank while only 9-12 puts failed.

Known limits:

- Coverage for a block that never completes is kept until the epoch ends.
- Permanent put failures accumulate entries holding event payloads until the pending ledger's 2^14-entry ceiling drops the oldest; the announced-block ledger holds at most 2^18 entries.
- The wipe runs on rank 0; other ranks bind the new epoch at their next step, so a lookup the scheduler issues for that step can run before they bind.
- Evictions stay invisible, so a re-store after an eviction can complete coverage for an object the Store has since dropped.
