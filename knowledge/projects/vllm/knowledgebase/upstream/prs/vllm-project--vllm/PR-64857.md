# [ROCm][Perf] gfx942 sparse MLA decode: load e8m0 scales once per 64 columns, BLOCK_K 16

[Upstream PR](https://github.com/vllm-project/vllm/pull/64857) · state: open · merged: False

## Original PR description

Contributed by **Krai Ltd.** (hasith@krai.ai) as part of its MLPerf Endpoints v1.0 DeepSeek-V4.1-Flash submission on 8x AMD Instinct MI300X; this commit is one of the patches disclosed in that submission.

## Purpose

On gfx942 (MI300X/MI325X) the DeepSeek-V4/V4.1 sparse MLA decode runs `_sparse_attn_decode_partial_kernel`. Each `BLOCK_K`-token step gathered the 8 per-token e8m0 scale bytes as a `[BLOCK_K, NOPE_BLOCK]` byte tile (`nope_offsets // 64`), so every scale byte was loaded 64 times and `exp2` ran on 512 values per token. On gfx942 that gather was 112 of the kernel's 155 global loads, and the kernel ran at 1 wave/SIMD (291-308 VGPRs): latency bound, far below the HBM roof. At high concurrency it is the top decode kernel on MI300X (45 % of the per-step cost growth from 128 to 192 concurrent requests per TP4 replica).

This PR:

1. loads the scales as `[BLOCK_K, NOPE_BLOCK // 64]` and broadcasts them to `[BLOCK_K, NOPE_BLOCK]` in registers, in both the main (SWA) and extra (top-k) loops. The gfx950 path (`_load_fp8_ds_mla_gfx950_nope_exact_chunk`) already loads them this way. The padding byte (columns 448-511, masked out of `k_nope`) keeps `other=127`, so every scale value is unchanged: **bit-exact**.
2. launches the partial kernel with `BLOCK_K=16` instead of 32 on non-gfx950 (32 was tuned on gfx950): 227/232 VGPRs, 16 KB LDS instead of 32 KB. This changes the online-softmax summation order (bf16 rounding level).

gfx950 is untouched (separate kernel and launch branch), and so is the fallback `_sparse_attn_decode_ragged_kernel` used on other architectures. `_decode_num_splits` is unchanged.

## Test Plan

- `tests/kernels/attention/test_rocm_triton_attn_dsv4.py` on one MI300X (gfx942), before and after.
- Microbenchmark: 64 consecutive real decode calls (one engine step) dumped from a serving run at 128 and 192 concurrent requests, replayed against a KV pool at real geometry, MALL flushed before each call, 12 interleaved rounds; the unmodified kernel is the reference.
- End to end: DeepSeek-V4.1-Flash, TP4, DSpark k=5, agentic workload (MLPerf Endpoints client), before and after side by side on the same node; plus a full-length run with inline accuracy and SWE-bench.

## Test Result

**Unit tests** (MI300X, gfx942): 91 passed, 38 skipped (gfx950-only) both before and after, with identical per-test outcomes. The 20 `test_sparse_attn_decode_split_k_kernel` cases cover this kernel against the reference (1/2/3/4/8 splits, with and without the extra cache and the sink), with fnuz fp8 on gfx942.

**Microbenchmark**, per 64-call step:

| Query rows per call | Before | (1) scales | (1)+(2) BLOCK_K 16 |
|---|---|---|---|
| 1086 (181 seqs x 6) | 88.5 ms | 42.7 ms (-51.7 %) | 33.5 ms (-62 %) |
| 708-720 | 55.3 ms | 26.6 ms (-51.9 %) | 21.7 ms (-61 %) |
| 84-540 (sliced) | | | a further -12 to -21 % vs (1) |

**Correctness**

- (1): `torch.equal` with the previous kernel on all 128 dumped calls.
- (2): max error 7.6e-3 of the row max (bf16 outputs), cosine >= 0.99999997, 0.03-0.05 % of elements more than 2 bf16 ulps apart.
- Full-length accuracy with (1)+(2) (and #63719, an allocation-only change, applied alongside), MLPerf Endpoints agentic benchmark (613 trajectories, 256 concurrent, TP4): inline accuracy 53.19 % (stock 52.86 %), SWE-bench 197/200 (stock 98.0 %), OSL 840 tokens per turn, DSpark acceptance length 3.75 (stock 3.73).
