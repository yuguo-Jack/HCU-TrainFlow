# [Rust Frontend] Serialize unset completions and first-chunk keys as null like Python

[Upstream PR](https://github.com/vllm-project/vllm/pull/63766) · state: closed · merged: True

## Original PR description

## Overview

Follow-up of vllm-project/vllm#63061, which made the Rust non-streaming chat response serialize unset fields as `null` like Python. Two more places still omit keys that Python sends as `null`: the non-streaming completions response, and the first chunk of a chat stream. One commit each.

## Claims

- Non-streaming `/v1/completions` now includes `service_tier`, `choices[].routed_experts` and `choices[].weight_versions` as `null`, like Python's `CompletionResponse.model_dump()`.
- The first chat stream chunk carries `prompt_token_ids` (the IDs with `return_token_ids`, otherwise `null`) and `prompt_text: null`; later chunks carry neither, like Python under `exclude_unset=True`.

## Validation

Commands from `.buildkite/scripts/run-rust-frontend-cargo-ci.sh` (`style-clippy` and `test`), run from the repo root:

```
cargo fmt --manifest-path rust/Cargo.toml --all -- --check   # ok
cargo sort --workspace --check rust                          # ok
cargo deny --manifest-path rust/Cargo.toml --config rust/deny.toml check bans   # ok
cargo clippy --manifest-path rust/Cargo.toml --workspace --all-targets --all-features --locked -- -D warnings   # ok
cargo nextest run --manifest-path rust/Cargo.toml --workspace --all-features --locked --no-fail-fast
# 2311 tests run: 2311 passed, 13 skipped
```

The first commit alone also passes workspace clippy and nextest.

- `non_stream_completions_return_json_response` checks explicit `null` for the three completions keys; it fails on `main` with "expected explicit null `service_tier`".
- `happy_path_returns_sse_stream` checks explicit `null` `prompt_token_ids`/`prompt_text` on the first chat chunk and neither on later chunks; it fails on `main` with "expected explicit null `prompt_token_ids` on the first chunk".
- `chunk_stream_returns_prompt_token_ids_on_first_chunk_only` pins the `return_token_ids=true` path (IDs on the first chunk, `prompt_text` present as `null`).

## Details

- Completions (`completion/serving.py:288`, `completion/protocol.py:700-711`): `CompletionResponse` gains `service_tier`, and `CompletionChoice` gains `routed_experts` and `weight_versions`, always `None`, with the same doc comments as the chat types from vllm-project/vllm#63061. Only serialization changes; `return_weight_versions` is still rejected by its existing placeholder.
- First chat chunk (`chat_completion/serving.py:607-620`, chunks serialized with `exclude_unset=True` at `:498`): `ChatCompletionStreamResponse.prompt_token_ids` becomes a flattened `prompt: Option<ChatCompletionStreamPrompt>`, set only on the start chunk. The struct holds `prompt_token_ids` and `prompt_text` without skipping `None`. This models Python's "set on this chunk" as the struct's presence instead of an `Option<Option<_>>` per field.

Both are wire-shape rules of the OpenAI response DTOs, so they stay in `vllm-server`'s response types and the chat start-chunk builder; no lower crate changes.

Not changed: Python's first chunk also carries `delta.content: ""`, `logprobs: null` and `finish_reason: null` on the choice; Rust sends a role-only delta.

Not a duplicate: no open PR changes these Rust response keys.
