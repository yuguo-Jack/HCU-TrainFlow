# [Bugfix] Rebuild npcache when source checkpoint shards are updated

[Upstream PR](https://github.com/vllm-project/vllm/pull/64716) · state: open · merged: False

## Original PR description

fixes #64696

### what changed
`np_cache_weights_iterator` only checked whether `weight_names.json` existed to decide if the cache was ready. if the underlying `.bin` files were replaced or updated in place, fresh runs kept serving the old cached numpy arrays silently.

stores a lightweight manifest of shard sizes and mtimes in `weight_names.json`. if any shard path, size, or mtime changes (or if upgrading from the legacy plain-list format), the cache invalidates and rebuilds automatically. added unit tests for update detection and legacy cache upgrades.

- adenzhou1350 · comment · 2026-10-30T11:56:28Z · [source](https://github.com/vllm-project/vllm/pull/64716#issuecomment-6522095347)

Independent native CPU check at `49b26020025d`: the rebuild works for a 2-second mtime change, but a same-size update with a 0.5-second change still returns stale weights. `_npcache_is_stale()` discards that observable change with `abs(...) > 1.0`.

Minimal case in the PR checkout (no sleep or GPU needed):

```python
import os
import tempfile
from pathlib import Path
import torch
from vllm.model_executor.model_loader.weight_utils import np_cache_weights_iterator

with tempfile.TemporaryDirectory() as directory:
    p = Path(directory) / "pytorch_model.bin"
    read = lambda: dict(np_cache_weights_iterator(directory, None, directory, [str(p)], False))["w"]
    t = 1_790_000_000_000_000_000
    torch.save({"w": torch.ones(4)}, p)
    os.utime(p, ns=(t, t))
    size = p.stat().st_size
    assert torch.equal(read(), torch.ones(4))
    torch.save({"w": torch.full((4,), 5.0)}, p)
    os.utime(p, ns=(t + 500_000_000, t + 500_000_000))
    assert p.stat().st_size == size
    print(read(), torch.load(p, weights_only=True)["w"])
    # cached: [1, 1, 1, 1]; source: [5, 5, 5, 5]
```

Could the comparison use the actual timestamp identity (e.g. `st_mtime_ns`) without the 1-second tolerance, with a subsecond regression? Coarse filesystems can fail to record a change, but that needn't cause a visible change on a finer filesystem to be ignored.

My check used real Torch save/load and files in separate cache-writer/reader processes, with unchanged-cache and 2-second positive controls. Complete unmodified `weight_utils` and its same-head `cpu_resource_utils` dependency ran with installed vLLM 0.32 / Torch 2.13 dependencies; this is a scoped cache-function check, not the full current build (which pins Torch 2.14), original project suite, or model serving. AI assisted the investigation; I executed and inspected the controls independently.
