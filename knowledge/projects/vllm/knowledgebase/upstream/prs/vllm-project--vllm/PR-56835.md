# [XPU] [Feature] Adding triton/sycl GDN toggle

[Upstream PR](https://github.com/vllm-project/vllm/pull/56835) · state: closed · merged: True

## Original PR description

## Purpose

Adds a `sycl` choice to `--gdn-prefill-backend` so the GDN attention kernel can be selected on XPU.

On XPU, `QwenGatedDeltaNetAttention` previously always called the fused SYCL op `_xpu_C::gdn_attention`, with no way to switch to the Triton/FLA kernels. This PR:

- Adds `sycl` to `--gdn-prefill-backend` (XPU only). Unlike the other choices, it selects a fused whole-layer op, so conv1d and decode are replaced as well as prefill.
- Keeps `forward_xpu` for the Qwen GDN layer and dispatches inside it: `gdn_attention_core_xpu` for SYCL, `qwen_gdn_attention_core` for Triton.
- Resolves `sycl` in `_resolve_gdn_prefill_backend`; the function signature is unchanged. With `auto`, Qwen gets SYCL whenever `_xpu_C::gdn_attention` is built, which matches the previous default behavior. `auto` never fails; without the kernel it uses Triton/FLA.
- OLMo Hybrid rejects `sycl` explicitly. Its layer calls the FLA kernels directly and cannot use the SYCL op: the op hardcodes `beta = sigmoid(b)`, which does not cover `linear_allow_neg_eigval`. `GDNAttentionMetadataBuilder` treats `sycl` like Triton and builds the FLA chunk metadata.
- Requesting `sycl` when it cannot be honored raises `ValueError` at startup instead of silently running a different kernel: on a non-XPU platform, when `_xpu_C::gdn_attention` is not built, or for OLMo Hybrid.

Behavior on XPU:

| Model | no flag (`auto`) | `triton` | `sycl` |
|---|---|---|---|
| Qwen3.5 / Qwen3-Next | SYCL (Triton/FLA if kernel not built) | Triton/FLA | SYCL (`ValueError` if kernel not built) |
| OLMo Hybrid | Triton/FLA | Triton/FLA | `ValueError` at startup |

CUDA/ROCm/CPU behavior is unchanged for existing choices; `sycl` raises `ValueError` there.

Not a duplicate: searching open PRs for `gdn sycl` returns only this PR and #50038, which is unrelated (FlashAttention-in-graph gating on oneAPI 2026.0+).

AI assistance was used for parts of this change. All changed lines were reviewed and tested by the submitter.

## Test Result

`_log_gdn_backend_decision` does not log on XPU (#54871), so the kernel column is based on the requested backend in `non-default args` and the warmup time: Triton/FLA spends 267–325 s autotuning during the initial profiling run, while SYCL takes 0.06–0.07 s.

Qwen3.5-4B:

| Flag | Kernel | req/s | total tok/s | output tok/s | Initial profiling run | Engine init |
|---|---|---|---|---|---|---|
| none | SYCL | 1.90 | 2185.87 | 242.87 | 0.07 s | 58.4 s |
| `triton` | Triton/FLA | 1.53 | 1765.35 | 196.15 | 267.09 s | 331.7 s |
| `sycl` | SYCL | 1.91 | 2205.63 | 245.07 | 0.07 s | 60.3 s |

SYCL gives about 25% higher total throughput than Triton/FLA (one run per configuration). Engine init is about 4.5 min shorter with SYCL because Triton/FLA autotunes its kernels during the initial profiling run.

OLMo Hybrid 7B (dummy weights):

| Flag | Kernel | req/s | total tok/s | output tok/s |
|---|---|---|---|---|
| none | Triton/FLA | 1.07 | 614.60 | 68.29 |
| `triton` | Triton/FLA | 1.02 | 587.47 | 65.27 |
| `sycl` | – | `ValueError: GDN prefill backend 'sycl' is not supported for OLMo Hybrid.` at startup | – | – |

Both OLMo runs use the same kernel, so the throughput difference is run-to-run variation.

gsm8k (5-shot, 1319 samples), Qwen3.5-4B:

| Backend | exact_match, flexible-extract | exact_match, strict-match |
|---|---|---|
| `triton` | 0.7536 ± 0.0119 | 0.7384 ± 0.0121 |
| `sycl` | 0.7528 ± 0.0119 | 0.7384 ± 0.0121 |

Strict-match is identical; flexible-extract differs by one sample, well within the standard error. SYCL does not change accuracy.

Lint: all hooks pass, including mypy 3.10 and mypy 3.12.
