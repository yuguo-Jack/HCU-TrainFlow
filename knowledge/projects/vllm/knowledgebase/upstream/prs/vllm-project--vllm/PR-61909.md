# [Frontend][Perf] Tokenize long prompts in parallel pieces

[Upstream PR](https://github.com/vllm-project/vllm/pull/61909) · state: closed · merged: False

## Original PR description



## Overview

Tokenize a long text prompt as pieces in one tokenizer call, so that the Rust tokenizer encodes the pieces on all CPU threads. For a 1M-token prompt with `Qwen/Qwen3-0.6B`, the render request takes 0.30 s instead of 1.64 s, and the token IDs are the same. #45514, #47583 and #48544 are related, but they do something else (see Details).

## Claims

- `POST /v1/completions/render` with a 1M-token prompt takes 295 ms instead of 1637 ms on a 16-core CPU. With two such requests at the same time, the slower one takes 620 ms instead of 3157 ms. The prompt is tokenized before the request reaches the engine, so this time comes off the time to first token.
- The token IDs are the same as those of the normal tokenizer call, also with truncation on the left or the right side.
- Tokenizers, arguments and texts that this does not handle go through the normal call as before.

## Validation

Unit tests on CPU:

```bash
pytest tests/tokenizers_/test_parallel_encode.py tests/renderers/test_completions.py
```

All 65 tests pass: 28 new tests in `tests/tokenizers_/test_parallel_encode.py`, and 37 tests in `tests/renderers/test_completions.py`, 2 of them new. The new tests compare the token IDs with the normal call on 3M characters of mixed text for `Qwen/Qwen3-0.6B` and `Qwen/Qwen3.5-0.8B`. They also cut a 262K-character text at each of its more than 20,000 cut places, check truncation on both sides, call the thread-pool tokenizer of the renderer from 4 threads, and check that unsupported tokenizers, configurations and arguments use the normal call. The renderer tests check that the renderer takes the new path and that a prompt that is too long still fails the length check.

Outside CI, I compared the token IDs for `Qwen/Qwen2.5-0.5B-Instruct`, `Qwen/Qwen3-0.6B`, `Qwen/Qwen3.5-0.8B` and `Qwen/Qwen3.8-2.4T-A95B` on 28 texts: 24 random mixed texts of 0.3M to 1.2M characters, 4M characters of `vllm/**/*.py`, 2M characters of `docs/**/*.md`, and the `vocab.json` and `merges.txt` of Qwen3. All 112 results are the same as the normal call, and so are the token IDs of the pieces cut at each of the 10.3M cut places. `vocab.json` has no cut place, so it used the normal call.

End to end, I started the render server on main and on this PR:

```bash
VLLM_ALLOW_LONG_MAX_MODEL_LEN=1 vllm launch render Qwen/Qwen3-0.6B --port 8199 --max-model-len 1048576
```

The client sends `{"model": "Qwen/Qwen3-0.6B", "prompt": text}` to `/v1/completions/render` and measures the time until the response with the token IDs arrives. `text` is the first 4,533,131 characters of `vllm/**/*.py` in path order, which is exactly 1,000,000 tokens. The 1,000,000 token IDs from the server with this PR are the same as those of `AutoTokenizer.from_pretrained("Qwen/Qwen3-0.6B")(text)`.

| 1M-token prompt | main (`9e2b579aabe9`) | this PR |
|---|---|---|
| one request at a time, median of 6 | 1637 ms (1583 to 1661) | 295 ms (277 to 311) |
| two requests at the same time, slower request, median of 3 pairs | 3157 ms | 620 ms |

The CPU is an AMD Ryzen 9 9950X with 16 cores and 32 threads. The packages are tokenizers 0.23.3 and transformers 5.19.0.

This PR includes no GPU serving benchmark. The change only affects the tokenizer call in the API server, which the render server runs in the same way, and the engine gets the same token IDs as before, so the model output does not change.

## Details

`BaseRenderer._tokenize_prompt` calls the new `try_parallel_encode` before the normal tokenizer call. It returns `None` for a prompt of fewer than 262,144 characters, for a request that needs token offsets, for encode arguments other than `add_special_tokens`, `truncation` and `max_length`, and for an unsupported tokenizer. The renderer then makes the normal call.

The text is cut into pieces of at least 65,536 characters, and each piece ends at a cut place: before a space, or after a line break, where an ASCII letter or digit follows. With the pre-tokenizer regex of Qwen2 to Qwen3, and the one of Qwen3.5 and later, a space in front of a letter or digit always starts a pre-token, and no alternative runs from a line break into a letter or digit. The regexes also find the same pre-tokens in a piece as in the whole text, because they have no lookbehind, and their one lookahead, `(?!\S)` after a run of whitespace, gives the same result at the end of a piece as in the whole text. BPE merges never cross a pre-token, so the token IDs of the pieces, put one after the other, are the token IDs of the whole text.

A tokenizer is supported when:

- it is a `TokenizersBackend` with a Rust `tokenizers.Tokenizer`,
- the normalizer is NFC or none,
- the pre-tokenizer is a `Split` with one of the two regexes (`Isolated`, not inverted), followed by `ByteLevel` without `add_prefix_space` and `use_regex`,
- the model is BPE without dropout, and the post-processor is `ByteLevel` or none,
- no added token has `lstrip`, `rstrip`, `single_word` or a cut place inside its content,
- and the normal call on a short sample gives the same token IDs as the sample cut at every cut place, with and without special tokens. This catches a tokenizer class that changes the text or adds tokens in Python.

The result is cached per tokenizer object in a `WeakKeyDictionary`. The pieces are encoded with the public call `tokenizer(pieces, add_special_tokens=False, return_attention_mask=False)`, so they go through the thread-pool wrapper from #41181 like every other call. Truncation is applied to the result on the truncation side of the tokenizer, as the normal call does.

This PR does not duplicate an open PR. #45514 adds an opt-in tokenizer mode that splits the text on a special-token delimiter, so it does not help a long document without that token. #47583 adds an opt-in cache that reuses the encoding of the previous turn of a multi-turn chat. It also hooks `_tokenize_prompt`, and the two compose, because a cache miss can go to this path. #48544 batches many offline prompts into one call, and it does not split one long prompt.

Tradeoffs and limits:

- A long prompt uses all threads of the Rust thread pool for about 0.2 s per 1M tokens. Two long prompts at the same time share that pool, as the second row of the table shows.
- Only the two Qwen regexes are on the list. Other regexes, for example those of Llama 3 or DeepSeek V3, need the same argument before they can be added to `_SPLIT_REGEXES`.
- A text with no cut place, such as CJK text without ASCII words, uses the normal call.
