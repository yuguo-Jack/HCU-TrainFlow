# [Bugfix][KV Connector] Fix KV role detection for MultiConnector with nested connectors

[Upstream PR](https://github.com/vllm-project/vllm/pull/65060) · state: closed · merged: True

## Original PR description

## Overview

`KVTransferConfig.is_kv_producer` and `is_kv_consumer` only look at the top-level `kv_role`, but a `MultiConnector` never passes that role to its child connectors; each child uses its own. The documented MooncakeStore prefiller (top-level `kv_producer`, with a `kv_both` MooncakeStore child) therefore does not look like a consumer, so the scheduler does not defer freeing blocks, and a step still running for an aborted request can overwrite KV that was just loaded into the reused blocks. This PR makes both properties follow the child connectors' roles.

Credit to @nandanadileep, who found this issue and proposed the first fix in [#62438](https://github.com/vllm-project/vllm/pull/62438), and is a co-author of this PR. #62438 defers block freeing for every connector; this PR instead fixes how a `MultiConnector`'s role is determined, so blocks are deferred only when one of its child connectors loads KV.

## Claims

- For a `MultiConnector`, `is_kv_producer` and `is_kv_consumer` follow the roles of its child connectors. The top-level `kv_role` no longer matters.
- The documented prefiller is now a consumer, so it defers block freeing and its loaded KV is no longer overwritten after an abort. If every child is `kv_producer`, blocks are still freed immediately.

## Validation

**Regression test.** `test_multi_connector_role_follows_children` checks both properties for four combinations of top-level and child roles. On main, the three where the top-level role disagrees with the children fail; with this PR, all four pass. It is marked `cpu_test`, so the CPU CI step runs it.

```bash
pytest -v tests/v1/kv_connector/unit/test_multi_connector.py::test_multi_connector_role_follows_children
```

**Effect on the documented configs.** For each config, I built a real `VllmConfig` (Qwen2.5-VL-3B-Instruct) and a `PrometheusStatLogger` on main and with this PR. Changed values are shown as main → this PR.

| Config | `is_kv_consumer` | `is_kv_producer` | KV fetch metric | Requests may omit multimodal embeddings |
| --- | --- | --- | --- | --- |
| Prefiller: top-level `kv_producer`; MooncakeConnector `kv_producer` + MooncakeStore `kv_both` | False → True | True | missing → present | no → yes |
| Decoder: everything `kv_consumer` | True | False | present | yes |
| Top-level `kv_consumer`; MooncakeConnector `kv_consumer` + MooncakeStore `kv_both` | True | False → True | present | yes |

`is_kv_consumer` also decides whether the scheduler defers freeing blocks (only with async scheduling or PP), and `is_kv_producer` decides whether `finalize_partial_tail_offloads` runs when a request finishes.

**End to end.** The prefiller config on B300, PP=4, Model Runner V2, async scheduling, MooncakeStore over RDMA with `load_async`. Four concurrent loops each abort a request, then send a request whose prefix is loaded from MooncakeStore into the blocks just freed. Every loaded block is checksummed when its load completes and again before the request's first forward pass; a mismatch means the KV was overwritten in between.

| Model / setting | Top-level `kv_producer`, no deferred freeing | With deferred freeing | How deferred freeing was enabled |
| --- | --- | --- | --- |
| Qwen3-32B, 1 s sleep added to the aborted request's steps | 13/24 loads overwritten | 0/24 | This PR |
| Qwen3-32B, no added sleep | 0/298 | 0/598 | This PR |
| Qwen2.5-7B, no added sleep (`70d67f19d`) | 0/300, 3/300, 3/300, 4/300 by PP rank | 0/303 on every rank | Top-level `kv_both` |

The added sleep runs on the compute stream in steps that contain the aborted request, so its writes land after the load and the overwrite shows up often.

## Details

**Root cause.** `Scheduler.__init__` sets `defer_block_free` from `kv_transfer_config.is_kv_consumer`. Deferring keeps a finished request's blocks out of the free pool until its in-flight steps are done. With the documented prefiller config:

1. Request A is aborted while one of its steps is still queued on the GPU.
2. The top-level role is `kv_producer`, so A's blocks go back to the free pool at once.
3. Request B finds its prefix in MooncakeStore and is given those blocks. The `kv_both` child loads B's KV into them over RDMA, which is not ordered with the GPU compute stream.
4. A's queued step runs and writes A's KV into the same blocks. B then computes on that KV without any error.

**Change.** For a `MultiConnector`, `is_kv_producer` and `is_kv_consumer` read each child's `kv_role` from `kv_connector_extra_config["connectors"]`, the same way `has_connector()` and `uses_custom_mem_pool()` read the children. Behavior only changes when the top-level role disagrees with the children, as in the three test cases that fail on main: a top-level `kv_producer` with a child that loads KV (the documented prefiller) becomes a consumer; a top-level `kv_consumer` with a `kv_both` child becomes a producer; and a top-level `kv_both` with only `kv_producer` children is no longer a consumer, so it frees blocks immediately, since nothing loads into them.
