# [Frontend] Enforce max_tool_calls for Responses built-in tools

[Upstream PR](https://github.com/vllm-project/vllm/pull/47112) · state: open · merged: False

## Original PR description

## Purpose

This PR makes `ResponsesRequest.max_tool_calls` effective for Responses built-in tool execution.

The Responses API already accepts and returns `max_tool_calls`, but the built-in tool generation loop did not enforce it before calling tools. This change threads the request value into the loop and stops executing further built-in tool calls once the configured limit is reached.

I checked existing open PRs/issues for `max_tool_calls responses` and did not find an overlapping change. This PR was developed with AI assistance.

Independent verification that this bug is real (I opened a duplicate PR #62323 against current main before finding this one — closed mine, the evidence belongs here):

Reproduced the unbounded loop against `_generate_with_builtin_tools`: with `request.max_tool_calls = 2` and a model that emits a builtin tool call on every turn, the loop performed 50+ engine round-trips (stopped only by an external emergency cap), while the request carried and echoed `max_tool_calls=2` as if a quota were in effect. The field has zero consumers in serving code (declared, echoed, and copied only), and every turn re-derives `sampling_params.max_tokens` from the full remaining budget, so nothing else bounds the loop.

This PR's approach matches what I'd independently implement. Hope the verification helps get it reviewed — happy to test the branch against current main if useful.
