# [Bugfix][LoRA][MoE] Use int64 token offsets in MoE-LoRA Triton kernels

[Upstream PR](https://github.com/vllm-project/vllm/pull/59407) · state: open · merged: False

## Original PR description

## Purpose

The MoE-LoRA Triton kernels compute output/input row addresses as
`offs_token * stride`, where `offs_token` is loaded from the int32
`sorted_token_ids` (or built from `pid_m`). Once
`num_tokens * top_k * N >= 2**31` the product wraps in int32 and the kernel
writes outside the output tensor (illegal memory access, or silent
corruption). With MoE LoRA enabled this is reachable in a single prefill step,
e.g. ~37K tokens for DeepSeek-V3/Kimi-K2 shapes or ~65K tokens for
Qwen3-235B, including the profile run when `max_num_batched_tokens` is large.

The base `fused_moe` kernel already casts `offs_token` to int64 for exactly
this reason (`fused_moe.py`: "stride_cm * offs_token can exceed int32 for
large token counts"); the LoRA kernels were missing the cast.

Changes:
- `fused_moe_lora_op.py`: cast `offs_token` to int64 in
  `_fused_moe_lora_one_shot_kernel` and in `_get_token_offs` (used by the
  legacy `fully_sharded` kernel for both `stride_am` and `stride_cm`).
- `fused_moe_lora_fp8_op.py`: same fix in its own copy of `_get_token_offs`.
- `trtllm_lora_moe.py`: promote the row/token and permuted indices to int64 in
  `_unpermute_activation_kernel` and `_finalize_lora_kernel`, which have the
  same `row * stride` pattern with `num_tokens * top_k` rows.
- Add `do_not_specialize=["num_valid_tokens", "stride_tl_", "stride_el"]` to
  the one-shot kernel, matching the legacy kernel, so per-step scalars do not
  cause runtime recompiles.

Not a duplicate: I searched open PRs/issues (`fused_moe_lora int64`,
`moe lora offs_token overflow`, `LoRA MoE int32 overflow`) and found nothing
addressing these kernels. #57524 fixes a similar int32 row-offset wrap, but in
the MRV2 staged-write / penalties path, not in the LoRA MoE kernels.

## Test Plan

New regression test
`test_fused_moe_lora_kernel_one_shot_int64_row_offset`: output of
`(2**31 // (top_k * N) + 16, top_k, N)` bf16 where only the last 16 flat
tokens (offsets past 2**31) are routed, compared against a torch reference.
It skips when free device memory is below ~4.7 GB.

```bash
# existing + new MoE-LoRA kernel tests (single GPU)
python -m pytest tests/lora/test_fused_moe_lora_kernel.py -q -k "not tensor_parallel and not fully_sharded"

# new test on main (kernel change reverted)
python -m pytest tests/lora/test_fused_moe_lora_kernel.py -q -k int64_row_offset
```

The `fully_sharded` tests require 2 GPUs, so I additionally ran the legacy
`fully_sharded=True` path through the test's
`use_fused_moe_lora_kernel_tensor_parallel` helper with `world_size=1`
(fp16/bf16 x rank 16/64 x column/row parallel).

`pre-commit run --files <changed files>` passes.

## Test Result

Environment: RTX 5060 (8 GB), WSL2, torch 2.13.0+cu130.

- Without the fix, the new test fails with
  `torch.AcceleratorError: CUDA error: an illegal memory access was encountered`.
- With the fix: `406 passed, 12 deselected` (includes the new test).
- Legacy `fully_sharded` path at `world_size=1`: all 8 configurations match the
  torch reference.

Not covered locally: `fused_moe_lora_fp8_op.py` has no existing test, and
`trtllm_lora_moe.py` only runs on SM100 with FlashInfer. Those changes are the
same index-dtype promotion. No model eval: the change only widens index
arithmetic and does not change results for shapes that did not overflow.

AI assistance (Claude via Cursor) was used to locate the issue, write the fix
and the test. I reviewed every changed line and ran the tests above.

- BeichenHuang · COMMENTED · 2026-10-17T00:37:20Z · [source](https://github.com/vllm-project/vllm/pull/59407#pullrequestreview-5555102334)

LGTM on the fix. Validated on H20 (SM90).

**E2E:** in a real engine main doesn't crash; it silently drops the LoRA delta. OLMoE-1B-7B + MoE LoRA, 132K-token prefill in one step: on main, the last tokens' rows never get the LoRA update (0/32 overflowing calls), so their logits/logprobs silently come from the base model. With this PR all 32 calls update them. Might be worth saying so in the description.

At DeepSeek-V3 w2 shape (38K tokens), main IMAs on the one-shot path (rank 16–128), on the rank-256 fallback, and in both trtllm helpers (run directly on SM90). All correct with this PR.

**One remaining spot:** on SM90 the rank > 128 fallback uses TMA with `sort_c=True`, and `_get_c_ptrs` still computes `lora_id * EM * stride_cm` in int32. It still IMAs with this PR at rank 256, max_loras=32, ~38K tokens.

<details><summary>fix (verified, kernel tests pass)</summary>

```diff
     if sort_c:
-        offs_token_id = pid_m * BLOCK_SIZE_M + offs
+        offs_token_id = (pid_m * BLOCK_SIZE_M + offs).to(tl.int64)
         c_ptrs = (
             cur_c_ptr
-            + lora_id * EM * stride_cm
+            + lora_id.to(tl.int64) * EM * stride_cm
```
</details>

Also: the new test fails on main and passes here; `test_fused_moe_lora_kernel.py` passes (414).
