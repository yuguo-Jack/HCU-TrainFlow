# [Bugfix][Frontend] Accept Cohere v2 safety_mode OFF with the cmd3 format

[Upstream PR](https://github.com/vllm-project/vllm/pull/62722) · state: open · merged: False

## Original PR description



## Overview

With `--cohere-format cmd3`, a `/cohere/v2/chat` request with `safety_mode: "OFF"` fails with HTTP 400. `OFF` is one of the three values Cohere documents for v2 (`CONTEXTUAL`, `STRICT`, `OFF`), and the SDK says that with `OFF` "the safety instruction will be omitted". This PR maps `OFF` to melody's `none`, which omits that instruction.

## Claims

- `safety_mode: "OFF"` now renders with cmd3 and leaves the safety instruction out of the prompt, as Cohere's API does.
- `CONTEXTUAL`, `STRICT` and the v1 spelling `NONE` behave as before.

## Validation

- New tests in `tests/renderers/test_cohere.py`:
  - `_build_render_config` maps `OFF`, `off` and `NONE` to `none`.
  - A request goes through `CohereChatV2Request.model_validate`, `CohereServingChatV2._convert_v2_to_chat_completion`, `_build_render_config` and the real `cohere_melody.render_cmd3`. `OFF` renders the same prompt as `NONE`, and a different one from `CONTEXTUAL` and `STRICT`.
  - The 2 `OFF` mapping cases and the rendering test fail on main. The `NONE` case passes on both and guards the existing value.
- `pytest tests/renderers/test_cohere.py tests/entrypoints/cohere`: 346 passed on this branch (4 new tests). Main without the new tests gives 342 passed. On both, the 9 server tests in `test_chat_v2.py` error in my CPU environment because they need a model download.
- `pre-commit run --files` on the changed files passes, including mypy.
- Before the fix, on main (4964e4482), the script below prints:

```
CONTEXTUAL -> renders OK (template kwarg safety_mode='contextual')
STRICT -> renders OK (template kwarg safety_mode='strict')
OFF -> HTTP 400 | Invalid config: safety_mode: invalid SafetyMode 'off', expected one of: unknown, none, strict, contextual
```

<details><summary>Script</summary>

```python
"""Cohere v2 safety_mode="OFF" fails to render with the cmd3 format."""
import cohere_melody as melody
from vllm.entrypoints.cohere.protocol import CohereChatV2Request
from vllm.entrypoints.cohere.serving import CohereServingChatV2
from vllm.entrypoints.serve.exception_handling.error_response import create_error_response
from vllm.renderers.cohere import _build_render_config

conv = [{"role": "user", "content": "hi"}]
for mode in ("CONTEXTUAL", "STRICT", "OFF"):
    req = CohereChatV2Request.model_validate(
        {"model": "m", "messages": [{"role": "user", "content": "hi"}], "safety_mode": mode})
    chat_req = CohereServingChatV2._convert_v2_to_chat_completion(req)
    kw = dict(chat_req.chat_template_kwargs, cohere_format="cmd3")
    try:
        _, cfg = _build_render_config(conv, kw)
        melody.render_cmd3(cfg)
        print(mode, "-> renders OK (template kwarg safety_mode=%r)" % kw["safety_mode"])
    except Exception as e:
        err = create_error_response(e)
        print(mode, "-> HTTP", err.error.code, "|", err.error.message[:160])
```

</details>

## Details

The conversion lowercases `safety_mode` and forwards it to the renderer, and `_build_render_config` passes it to melody's cmd3 `safety_mode` slot. Melody accepts `unknown`, `none`, `strict` and `contextual`, so `off` fails its validation. The v1 API spelled this mode `NONE`, which is why the existing code, typed with the v1 enum, never needed a mapping.

The mapping lives in `_build_render_config` next to the other melody normalizations (such as `citation_options.mode` to `citation_quality`). That is deliberate: callers that pass `safety_mode` directly through `chat_template_kwargs` to the Cohere renderer get the same mapping. cmd4 does not use `safety_mode` (`test_cmd4_no_safety_mode_field`), so it is unaffected. Both SDK types for the field (`ChatRequestSafetyMode` and v2's `V2ChatRequestSafetyMode`) are `Union[Literal[...], Any]`, so request validation already accepts `OFF`; only the renderer needed the change.
