# [ROCm][Perf][Muse Spark] fp8 KV cache for the specialized decode (draft, stacked on #63246)

[Upstream PR](https://github.com/vllm-project/vllm/pull/63527) · state: open · merged: False

## Original PR description

## Overview

**Draft, stacked on #63246** (which is stacked on #62766). The first two commits here are those PRs; review only the top four. [Diff of those four commits](https://github.com/vllm-project/vllm/compare/b5e908a76af4...amd-mghanimi:muse-spark-mono-fp8kv). Adds an fp8 (e4m3) KV cache option to the Muse Spark specialized decode, so `--monokernel` serves with `--kv-cache-dtype fp8` as well as bf16. Related: RFC #60904.

The reason: on 8x MI355X the best stock serve for Muse Spark Open is `--max-num-batched-tokens 16384 --kv-cache-dtype fp8`, and until now the mono kernel refused fp8 KV, so the two speedups could not be combined.

## Claims

- `--kv-cache-dtype fp8` (and `fp8_e4m3`) is accepted in every mono mode. `fp8_e5m2` and other dtypes are still refused at config time, and the cache tensors are checked at bind time (`uint8` / `float8_e4m3fn` under fp8, `bfloat16` otherwise).
- **Phase A** (`mono_front=stock`, `mono_core=tensor`, the default) and **B2** (`gated`) do not touch the cache: vLLM inserts and attends, so fp8 needs only the guards. Attention numerics are stock's.
- **K1** (`mono_front=k1`) inserts e4m3 in-kernel: `bf16(k) * (1 / k_scale)`, clamped to ±448, RNE through `v_cvt_pk_fp8_f32`. This is the stock ROCm insert's order of operations, and the bytes match it bit for bit.
- **The split core** (`mono_core=split`) reads e4m3 pages: one dwordx4 of K and four dwords of V a lane, widened in registers to bf16 times the layer's `k_scale` / `v_scale`. The rest of the core is unchanged.
- The scales are read by address from `attn._k_scale` / `_v_scale` (fp32, one element), so in-place updates are picked up. The bf16 kernels are unchanged: `kv_fp8` is a build key, compiled only when the cache is fp8.

## Validation

8x MI355X (gfx950), ROCm image `amdsiloai/vllm-private:nightly-83c078d_..._62766_63246` with this tree overlaid.

**Unit and kernel tests.** All pass:
- `test_runtime.py`: 161 passed. This includes fp8 accepted × front × core, e5m2 refused, and fp8 cache dtypes at bind time.
- `test_compile.py`: 89 passed, including the split and K1 builds with `kv_fp8` (ISA gate).
- `test_numerics_core.py::test_layer_chain_split`: 4 passed (stock / K1 front × bf16 / fp8).
- `test_numerics_core.py::test_graph_replay_follows_metadata`: 2 passed.
- `test_numerics_front.py`: K1 front passed.

**fp8 numerics.** TP8 layer chain with scales of 0.75 / 1.25:

| | vs fp64 attention of the cache's values: cos | max abs err |
|---|---:|---:|
| split core, fp8 cache | 0.999997 | 0.007 – 0.013 |
| stock `paged_attention_v1`, same fp8 cache | 0.996 – 0.998 | 0.24 – 0.54 |

Stock fp8 decode is lossy by itself. A one-GPU probe on random q / KV puts it at cos 0.997 against fp64 with scales of (1, 1), (0.75, 1.25) and (0.05, 0.05); on a bf16 cache it is at 0.999997. The split widens e4m3 to bf16 and keeps q in bf16, so on an fp8 cache the test holds the split to fp64 rather than to stock. For the same reason stream_out is checked against the stock tail on the split core's own rows (cos 1.0000000). Its cos against the full stock chain is 0.9988–0.9991, because the core differs.

**DSpark experiment.** The earlier 12-cell plain-decode sweep is not the right
experiment for this PR, so it is deliberately not used as the performance
comparison below. This PR changes the mono path used by DSpark verify steps.

The comparison names are:

1. **No mono kernel** — DSpark on the same image, without `--monokernel`.
2. **BF16 KV mono kernel** — `--monokernel` with vLLM's `bfloat16` KV cache.
3. **FP8 KV mono kernel** — `--monokernel --kv-cache-dtype fp8`.

(`bfloat16`, not IEEE fp16, is the supported non-fp8 cache dtype.)

For static DSpark K = 1, 3, 5 and 7, one request verifies K + 1 target-model
rows. The matrix covers 8k/1k and 64k/1k at max concurrency c = 1, 2, 4, 8,
12, 16, 18, 24 and 32, in all three modes:

| c | K=1 (2 rows/request) | K=3 (4) | K=5 (6) | K=7 (8) |
|---:|---:|---:|---:|---:|
| 1 | 2 | 4 | 6 | 8 |
| 2 | 4 | 8 | 12 | 16 |
| 4 | 8 | 16 | 24 | 32 |
| 8 | 16 | 32 | 48 | 64 |
| 12 | 24 | 48 | 72 | 96 |
| 16 | 32 | 64 | 96 | 128 |
| 18 | 36 | 72 | 108 | 144 |
| 24 | 48 | 96 | 144 | 192 |
| 32 | 64 | 128 | 192 | 256 |

The entries are `c × (K + 1)` target-model verify rows. Mono replaces only
whole-request steps through eight rows; larger entries are intentional
same-server fallback controls. The runtime now builds the applicable widths:
K=1: 2/4/6/8; K=3: 4/8; K=5: 6; K=7: 8.

Each K / mode run also does a 50-sample NIAH screen at 64k and 128k for every
listed concurrency. A full 500-sample confirmation follows the screen for any
mode / K / concurrency that changes accuracy.
