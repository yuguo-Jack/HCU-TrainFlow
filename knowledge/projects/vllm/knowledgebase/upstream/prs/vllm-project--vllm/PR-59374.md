## Original PR description

# Refactor KV offload copy backend interface

## Summary

This PR refactors the CPU KV offload transfer path around a shared logical
`CopyRunDescriptor` protocol. The worker builds structured run information,
while the selected copy backend expands it for the existing copy API and owns
the descriptor buffers used by that API.

This is a refactor. It does not add a C++ or Triton kernel and does not change
the underlying DMA or Triton batch entry points.

## Value

1. **Simpler worker responsibilities.** `SingleDirectionOffloadingHandler`
   keeps the transfer-specific logic: block and run construction, stream/event
   ordering, writer rotation, partial-block handling, and byte accounting. It
   no longer imports kernel-selection helpers or owns backend descriptor
   tensors.
2. **One backend input protocol.** DMA and Triton batch backends consume the
   same `CopyRunDescriptor` values. Each implementation owns its descriptor
   conversion and buffer lifecycle, so later backend work can be developed
   independently of the worker.

## Changes in this PR

- Added `vllm/v1/kv_offload/cpu/copy_backend.py` with:
    - the abstract `CopyBackend` interface;
    - existing batch DMA and Triton batch implementations;
    - backend resolution for host pinning, platform support, Triton
    availability, page-size thresholds, and run alignment;
    - backend-owned fragment descriptor expansion and buffer reuse.
- Replaced the worker's eager fragment `CopyPlan` arrays with structured
  `CopyRun` plans and per-transfer `CopyRunDescriptor` values, while keeping
  direct layouts on whole-page runs even when a reference carries a mapping.
- Removed direct worker dependencies on `_custom_ops`, Triton utilities, and
  the Triton batch helper.
- Removed backend descriptor tensors from `Transfer`; transfer records now
  retain only job, stream/event, and accounting information.
- Moved backend selection tests to `copy_backend` and added coverage for
  unaligned canonical runs selecting DMA.

## Compatibility intent

The refactor keeps the existing DMA and Triton batch entry points, transfer
ordering, CUDA event sequencing, host-memory handling, writer rotation,
partial-block handling, and transfer byte accounting. The intended data-movement
behavior is equivalent to the previous implementation; the change is in the
ownership and representation of the copy descriptors.

No new kernel, C++ binding, benchmark, or run-level copy implementation is
included here.

## Follow-up directions

The shared backend protocol leaves room for follow-up work without changing the
worker contract:

1. Add a run-level C++ or Triton kernel behind another `CopyBackend`
   implementation.
2. Add transfer-level backend selection based on the actual run descriptors,
   such as descriptor count and fragment sizes, while retaining static
   capability checks during handler initialization.

## Scope and related work

The open PR search for `KV offload` and `copy backend` found related layout and
offload work, but no PR with this worker/backend protocol refactor. Those PRs
address layout namespace or packed-layout behavior; this PR focuses on the
worker/backend boundary and keeps the existing copy kernels.
