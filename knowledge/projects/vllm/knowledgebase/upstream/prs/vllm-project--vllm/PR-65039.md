# [Doc] Use the dash-separated CLI flag names in scoring and tool-calling docs

[Upstream PR](https://github.com/vllm-project/vllm/pull/65039) · state: open · merged: False

## Original PR description

## Purpose

Part of [#65042](https://github.com/vllm-project/vllm/issues/65042)

This is a documentation-consistency change.

`vllm serve` parses its arguments with `FlexibleArgumentParser`, which rewrites underscores in option names to dashes before the options are looked up, so both spellings are accepted:

```bash
--hf_overrides    == --hf-overrides
--tokenizer_mode  == --tokenizer-mode
--config_format   == --config-format
--load_format     == --load-format
```

The underscore spellings were therefore not broken, they were only inconsistent with the rest of the docs, which use the dash-separated spelling of the very same options:

- `docs/models/pooling_models/scoring.md` used `--hf_overrides` in five places, while the same page documents `--hf-overrides`.
- `docs/features/tool_calling.md` mixed `--tokenizer_mode`, `--config_format` and `--load_format` with the dash form `--tool-call-parser` on the same line.

This PR makes the two pages use the dash-separated spelling consistently.

Documentation-only change; no code is touched.

## Test Plan

Every `vllm serve` command in the two pages was replayed against the option parser that `vllm serve` actually builds, i.e. `FlexibleArgumentParser` with `EngineArgs.add_cli_args` (`vllm/engine/arg_utils.py`) and `FrontendArgs.add_cli_args` (`vllm/entrypoints/common/cli_args.py`).

With `FlexibleArgumentParser`, all documented commands parse with either spelling, before and after this change. The same commands fail on the underscore spelling only when the options are registered on a plain `argparse.ArgumentParser`, i.e. without the underscore-to-dash rewrite.

## Test Result

- `docs/models/pooling_models/scoring.md`: 0 underscore-style options left, 0 unresolved options in the documented `vllm serve` commands.
- `docs/features/tool_calling.md`: 0 underscore-style options left, 0 unresolved options in the documented `vllm serve` commands.
