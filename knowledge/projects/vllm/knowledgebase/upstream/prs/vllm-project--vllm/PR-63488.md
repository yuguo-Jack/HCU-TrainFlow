# [Bugfix] Restore engine memory budget after IPC fallback

[Upstream PR](https://github.com/vllm-project/vllm/pull/63488) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

When `ipc_cache` falls back to disk (e.g. the daemon is reachable but its weights do not match the engine config), the worker keeps charging the daemon's weights against its memory budget even though it no longer maps them, so the KV cache is smaller than with a direct disk load by the daemon's weight size. This removes the charge of each model that falls back, so a fallback is sized exactly like a direct disk load.

Follow-up to #62583.

## Claims

- After an IPC disk fallback, the engine budget and KV cache size match a direct disk load (Qwen3-4B, `gpu_memory_utilization=0.1`: KV cache 10.82 → 18.34 GiB, equal to the direct load).
- Only the charge of the model (target or draft) that fell back is removed; models still mapped from the daemon keep theirs.

## Details

**Root cause.** `Worker.init_device` charges daemon-held weights (`get_external_weight_memory`, added in #57298) before the model is loaded. If `IpcModelLoader.load_model` then falls back to disk, the engine allocates its own copy of the weights, but `requested_memory` still excludes the daemon's copy, so KV sizing pays for weights the engine does not map.

**Fix.**

- `IpcModelLoader` records each zero-copy daemon's charge by socket and role when it is queried, and after a successful disk fallback reports that role's charge once.
- `ExternalWeightCharges.track()` binds the worker's charges during the query and the model load and accumulates `fallback_bytes`.
- `Worker._resolve_requested_memory()` recomputes the budget with `external_weight_memory - fallback_bytes`, leaving `external_weight_memory` as queried at startup. It runs after `load_model` when a fallback happened, and in `disable_extensible_kv_cache`, which re-sizes after loading. Without a fallback, both paths behave as on main.

**Tradeoff.** A fallback now behaves like a direct disk load with the daemon as another process on the GPU. The daemon's resident weights are already excluded from `init_snapshot.free_memory`, so `request_memory`'s free-memory check and the extensible KV cache's measured sizing still bound physical memory. With estimate-based sizing, a configuration that fits only because the daemon's weights were charged (budget above startup free memory) now fails at startup after a fallback, as a direct disk load would, instead of running with a smaller KV cache.

**Duplicate work.** Searched open PRs for "ipc fallback memory budget", "external_weight_memory" and "weight cache fallback": no equivalent fix. #59813 restores model state before an IPC fallback; this PR fixes memory accounting after a successful fallback.
