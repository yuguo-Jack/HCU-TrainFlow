# [Fast Start] Share FlashInfer autotune artifacts between daemons

[Upstream PR](https://github.com/vllm-project/vllm/pull/61841) · state: open · merged: False

## Original PR description

## Overview

Add a standalone daemon-to-daemon path for sharing FlashInfer autotune JSON artifacts during `vllm preload`. A target daemon fetches rank-matched tables from a source daemon over an authenticated TCP JSON endpoint before warmup.

This extracts the autotune-artifact building block from the broader design discussed in [#60086](https://github.com/vllm-project/vllm/pull/60086), and is based on the current `main` branch.

## Claims

- Add source and target CLI options for an authenticated, rank-aligned artifact exchange.
- Add a bounded artifact store with exact cache-key matching, size limits, malformed-payload rejection, and atomic installation into the existing FlashInfer cache.
- Preserve the existing local-warmup fallback when a source or compatible artifact is unavailable.
- Reduce the autotune portion of a new daemon's cold start from approximately **8.3–8.8 s** to near zero when the matching artifact is available.

## Validation

- Matched daemon cold-start A/B on a representative K3 MoE workload:
  - Without a matching artifact, the FlashInfer autotune phase took approximately **8.3–8.8 s**.
  - With a matching artifact, the same phase completed in near-zero time.
- The target daemon loaded the rank-matched artifact, skipped the expensive FlashInfer profiling phase, and reached READY.
- The target `ipc_cache` engine mapped weights through `zero_copy` and completed a real generation request.
- Pre-commit and targeted compile checks passed for the changed files.

## Details

The source daemon retains the per-rank FlashInfer table in a bounded in-memory store. The target connects to the corresponding source endpoint over TCP, authenticates with a shared token, validates the JSON artifact and cache key, and installs a matching table into its existing on-disk FlashInfer cache. The daemon then performs warmup without repeating the expensive tuning work; an absent or incompatible table falls back to local autotuning.

The artifact transport deliberately uses the control plane because the payload is a small JSON configuration table. Model-weight transfer, CUDA IPC handles, and RDMA remain outside this first stage.

This is the first stage of the D2D startup work. [PR2](https://github.com/UNIDY2002/vllm/pull/1) stacks on this branch and transfers compiled cache artifacts with Mooncake TransferEngine to further reduce compilation and autotune-related startup overhead.
