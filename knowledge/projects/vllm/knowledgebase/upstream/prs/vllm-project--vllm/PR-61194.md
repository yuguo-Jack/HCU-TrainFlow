# [Bugfix][Watermarking] Skip incomplete opening contexts

[Upstream PR](https://github.com/vllm-project/vllm/pull/61194) · state: open · merged: False

## Original PR description



## Overview

Skip watermarking until the response contains a complete generated-token context, across Gumbel and dual-key Gumbel standard and speculative sampling. Follow-up to the shared padded-opening issue discussed in #58426; that PR adds SynthID and leaves this behavior question separate.

## Claims

- The first `context_width` output tokens use ordinary sampling independently of context deduplication, including draft, recovery, and bonus tokens.
- Detection behavior and PRF mappings are preserved.

## Validation

- `../vllm_fork/.venv/bin/python -m pytest tests/watermarking -q`: 134 passed, 61 accelerator-only tests skipped on macOS.
- All applicable pre-commit hooks passed, including mypy and test tethering.
- Rescored all 23 pre-change golden generations with the default detector: scores, p-values, scored-token counts, and decisions match within the existing 1e-9 tolerance.
- GPU engine validation remains pending. Retained model outputs establish detection compatibility only; they do not evaluate generation with this patch.

## Details

Response-local contexts are padded with -1 before enough output tokens exist. With a fixed key, this reuses the same opening watermark randomness across prompts and can reduce opening diversity. The patch combines an incomplete-context mask with the existing sampling masks; it adds no host read or device synchronization. Prompt tokens remain excluded from the seed under every deduplication setting; `all` still searches the prompt for repeated contexts.

Submitted detection text may be a fragment and need not start at the generation boundary, so this PR does not change detector preprocessing or add detector options. On new full responses, the unwatermarked opening positions can dilute the detector signal. Generation can diverge beyond the opening because later tokens depend on earlier choices.

Goldens reflect the new generation behavior. Engine reproducibility tests now pin request seeds because openings use ordinary randomness. The repetitive-fixture confidence guard allows a p-value ratio up to 0.6 rather than 0.5: one updated fixture has ratio 0.514 while remaining below the unchanged detection threshold.

Thanks for splitting this out of #58426. The change looks right to me. I ran the watermarking tests on 2x H200 at 401ebef503.

One GPU test now fails, and CI does not catch it.

`tests/watermarking/test_watermarking_e2e.py::test_llm_generated_sequence_is_watermarked` fails on every run: `p_value` is 1.1e-08 against the bound `9.83e-20 * 10`. It passes on the merge base. The watermarked request has no seed, so its opening now comes from ordinary sampling and the response changes (18 tokens instead of 23). The recorded p-value belongs to the old shared opening. Pinning the request seed and re-recording fixes it. With `seed=0` I get 26 tokens and p = 2.68e-29 on every run. The PR doesn't touch this file, so I can't leave an inline suggestion. This is the change:

```diff
-    params_use_wm = SamplingParams(temperature=1.0, max_tokens=256, watermarking=True)
+    # Openings use ordinary sampling, so the recorded p-value needs a fixed seed.
+    params_use_wm = SamplingParams(
+        temperature=1.0, max_tokens=256, watermarking=True, seed=0
+    )
@@
-    recorded_p_value = 9.83e-20
+    recorded_p_value = 2.68e-29
```

For reference, I also checked how much detection this costs under the default config on Qwen3-8B (300 prompts x 4 seeds, p <= 0.01). Detection drops by 12 points at 8 tokens, 8 at 32 and 5 at 64, and is unchanged from 128 tokens on. All of the drop comes from the 4 unwatermarked opening tokens, which is the trade-off the description already states, so I don't think it needs a change here.
