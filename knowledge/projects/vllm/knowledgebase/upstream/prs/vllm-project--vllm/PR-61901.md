# [Bugfix][LoRA] Validate dtype at config time for Triton LoRA kernels

[Upstream PR](https://github.com/vllm-project/vllm/pull/61901) · state: open · merged: False

## Original PR description

## Overview

Fixes #61851.

With `enable_lora=True`, an unsupported dtype such as `dtype="float32"` is accepted at config time and only fails later, on a bare assert inside the Triton LoRA kernels during the profiling run. The user sees `RuntimeError: Engine core initialization failed` with no indication of the cause. This PR rejects the combination in `LoRAConfig.verify_with_model_config()` with a clear error message.

## Claims

- Unsupported dtypes for the Triton LoRA backend now raise a `ValueError` during config validation, before model loading or engine startup.
- Both the model dtype and the resolved `lora_dtype` are checked. Besides the case in the issue, this covers an fp16 model with `lora_dtype=float32`, and a float32 model with `lora_dtype="float16"` (which fails at the shrink kernel's dtype-match assert).
- The check only applies when the platform uses `PunicaWrapperGPU` (CUDA/ROCm, or XPU with `XPU_USE_TRITON_KERNEL=1`). The CPU backend uses the torch ops, which handle float32, so float32 LoRA on CPU keeps working.
- The dtype asserts in `lora_shrink_op.py` and `lora_expand_op.py` now include a message with the received dtype.

## Validation

### End-to-end

Tested on an RTX 5080 Laptop GPU with this script:

```python
from vllm import LLM, SamplingParams

llm = LLM(
    model="Qwen/Qwen2.5-0.5B-Instruct",
    dtype="float32",
    enable_lora=True,
    max_lora_rank=16,
    max_model_len=2048,
    gpu_memory_utilization=0.6,
    enforce_eager=True,
)
llm.generate(["The capital of France is"], SamplingParams(temperature=0.0, max_tokens=8))
```

Before:

```
File ".../vllm/lora/ops/triton_ops/lora_shrink_op.py", line 281, in _lora_shrink
  assert inputs.dtype in [torch.float16, torch.bfloat16]
AssertionError
...
RuntimeError: Engine core initialization failed. See root cause above.
```

After:

```
pydantic_core._pydantic_core.ValidationError: 1 validation error for VllmConfig
  Value error, LoRA on this platform requires dtype and lora_dtype to be float16 or bfloat16, got dtype=torch.float32 and lora_dtype=torch.float32.
```

With `dtype="float16"`, the engine starts and generates normally both before and after this change.

## Details

**Root cause:** `lora_dtype="auto"` resolves to the model dtype in `verify_with_model_config()`, but nothing checks the result against what the active LoRA backend supports. The Triton shrink/expand kernels only support float16 and bfloat16, so the mismatch was only caught when the kernels first ran during `profile_run`. The trace in the issue fails in `lora_expand` because LFM2 is an MoE model and goes through the fused MoE LoRA path; dense models hit the equivalent assert in `lora_shrink` first.

**Design choice:** The check is keyed on the punica wrapper rather than `current_platform.is_cuda_alike()`, so it matches exactly the platforms that run the Triton kernels, including XPU with `XPU_USE_TRITON_KERNEL=1`, and leaves CPU alone. I'm happy to switch to `is_cuda_alike()` if that is preferred.

**Out of scope:** Adding float32 support to the Triton kernels themselves would be a larger change and is not attempted here.

1. **`tests/lora/test_lora_manager.py` will fail on CUDA/ROCm with the new gate.** `test_lru_cache_worker_adapter_manager` (lines 772-788) and `test_worker_adapter_manager` (lines 888-893) build `VllmConfig(model_config=ModelConfig(max_model_len=16), lora_config=LoRAConfig(..., lora_dtype=DEFAULT_DTYPE))`, where `DEFAULT_DTYPE = torch.get_default_dtype()` (line 49) is `torch.float32`. `VllmConfig.__post_init__` calls `verify_with_model_config` (`vllm/config/vllm.py:1528`), a `torch.dtype` passes through lines 140-141 of `vllm/config/lora.py` unconverted, and the check at lines 144-154 raises before either test reaches an assertion. Intel CI is unaffected because XPU defaults to `PunicaWrapperXPU`. Fix: use `torch.float16`/`bfloat16` in those tests. I traced this in the code but haven't run it.
2. **The check lets mixed half precision through, which still hits the bare assert.** The whitelist accepts any pair from {float16, bfloat16}, so an fp16 model with `lora_dtype="bfloat16"` (or the reverse) passes. But the LoRA weights are allocated at `lora_config.lora_dtype` (`vllm/lora/layers/base_linear.py:139,150`), the activations reach `lora_shrink` uncast (`punica_gpu.py:113-114`), and `lora_shrink_op.py:280` (`assert inputs.dtype == lora_a_weights[0].dtype`, no message) fires before the newly messaged asserts. Requiring `lora_dtype == model_config.dtype` in the gate, or giving line 280 a message, would close it. Traced, not executed.
3. Nits:
   - `vllm/config/lora.py:143`: the comment "The Triton LoRA kernels only support fp16/bf16 activations and weights" isn't true of the expand kernel, which accepts fp32 inputs (`lora_expand_op.py:179`) because the shrink buffer is float32 (`punica_gpu.py:252`).
   - `vllm/config/lora.py:144`: `.endswith("PunicaWrapperGPU")` silently turns the check off if the wrapper is renamed or moved. `current_platform.is_cuda_alike()`, already used in this file, would fail closed.
   - `lora_expand_fp8_op.py:233-236` keeps the same bare weight assert you gave a message in `lora_expand_op.py:181-183`, if you want the two to match.
