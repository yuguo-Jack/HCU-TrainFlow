# [Bugfix][HiSparse] Preserve per-layer offsets in KV cache bindings

[Upstream PR](https://github.com/vllm-project/vllm/pull/57027) · state: closed · merged: True

## Original PR description

FIX https://github.com/vllm-project/vllm/issues/57019

## Purpose

Fix cross-layer KV overwrites when HiSparse packs multiple layers into one allocation. Both resident and hot bindings used the tensor's base offset for every layer, allowing later layers to overwrite earlier layers' cached rows. Compute `tensor.offset + layer_index * tensor.layer_stride` once per layer and use it in both bindings.

Addresses #57019; the faulty bindings were introduced by #53781.

Add a nightly HiSparse GSM8K job using the existing accuracy harness and real `nvidia/GLM-5.2-NVFP4` weights. It runs on four B200s with TP4, BF16 KV, eager execution, and a 32 GiB host pool. All 1,319 questions are evaluated with 5 shots and an explicit 90% minimum accuracy. The job is optional in regular CI, following the existing nightly-job convention. No new unit test or standalone evaluation harness is added.

Duplicate-work check: read #57019 and its comments, searched open PRs for `57019 in:body`, `HiSparse`, and `HiSparse offset`. No open PR addressing these missing layer offsets was found. The host-mirror replay work in #56158 addresses a separate failure path.

AI assistance: OpenAI Codex assisted with investigation, implementation, validation, and this description. The human submitter is responsible for line-by-line review and independent test validation.

## Test Result

- New nightly configuration, run locally on four B300s: **94.39% (1,245/1,319)**, **zero invalid answers**, evaluation time **594.9 seconds**. The 90% accuracy assertion passed. B200 execution remains for CI.
- Local pytest teardown failed in the existing `RemoteOpenAIServer._get_gpu_memory_used` check: it reads physical NVML indices `0..3` instead of mapping `CUDA_VISIBLE_DEVICES=0,2,5,6`, so growth in another user's GPU allocations exceeded its baseline. All our server/worker processes exited and GPUs 0, 2, 5, and 6 returned to 0 MiB; the full pytest command is therefore **not** reported as passing.
- Set `request_timeout_seconds: 1800` because the evaluator's total timeout includes waiting for a connection. An initial run with the default 600 seconds timed out approximately 60 queued requests; the final configuration completed all requests without API errors or timeouts.
- Negative control for the nightly server configuration: restored only the original `bind_hisparse_kv_caches` from `0136df94b0` in all four workers, keeping TP4, BF16 KV, concurrency 32, and automatic GPU cache sizing. The first **64 GSM8K questions scored 0/64 (0%)**, with no request errors or timeouts (72.9 seconds). This was a sampled negative control, not a full 1,319-question unpatched run. Its GPU pool was 138.1 GiB and reported about 8.4% usage, demonstrating that low cache capacity is unnecessary to expose the missing layer offsets. This does not establish memory-pressure spill coverage. The local validation helper scoped NVML cleanup checks to the reserved GPUs; production code and the GSM8K scorer were unchanged.
- HiSparse attention tests on B300: **30 passed**.
- Spill/prefix-restore tests on B300: **2 passed**, covering standalone/offload variants and FULL CUDA graph replay.
- All applicable pre-commit hooks passed, including Buildkite step-key validation.

Earlier sampled evaluation, separate from the new nightly configuration: `nvidia/GLM-5.2-NVFP4` revision `53e0691e21895a3863a606dfd12910c69eba94ab`, TP2 on B300, automatically selected FP8 KV, eager mode. Used the existing GSM8K scorer with the first 64 questions, 5 shots, 256 output tokens, temperature 0, seed 42, concurrency 16; server limits were model length 8192, 32 sequences, and 4096 batched tokens.
