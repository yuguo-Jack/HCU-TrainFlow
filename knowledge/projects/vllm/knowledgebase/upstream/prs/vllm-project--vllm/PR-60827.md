# [Model] Kolibri 1 via the Transformers modeling backend

[Upstream PR](https://github.com/vllm-project/vllm/pull/60827) · state: closed · merged: True

## Original PR description

## Overview

Serve `Kolibri1ForCausalLM` via the Transformers modeling backend.
Not a duplicate of #60026: this is the Transformers-backend alternative its review suggested.

## Details

- Needs the `kolibri1` model from huggingface/transformers#49463.
- MoE blocks map to one of three modes: vLLM experts only, vLLM experts and shared experts with Transformers routing, or everything in vLLM. This PR adds the second, which Kolibri 1 uses: the shared expert runs in `MoERunner` and overlaps with the routed experts, as under vLLM routing.
- @hmellor's commit merges the matching into a single `MoEBlockFuser.match`. A block is fused only when its output is exactly `experts(x, ids, weights) [* c] [+ shared(x)]` with `_, weights, ids = gate(x)`; other blocks keep the HF forward.

## Validation

- `pytest tests/models/transformers` (macOS, CPU) on head `85c178df42`: 159 passed; the 16 failures and 1 error also fail on main `f395a6b1ad`.
- vs #60026 with transformers#49463 installed, real FP8 weights, DeepGEMM off in both since #60026 forces it off:
  - GSM8K: 94.2% vs 94.5% on B200, 94.2% vs 94.2% on DGX Spark.
  - B200, mean of two runs each in mirrored order (throughput: 256 prompts of 1024 in / 256 out; latency: 512 in / 256 out):

    | | Output tok/s | bs1 latency | bs32 latency |
    |---|---|---|---|
    | #60026 | 9930 | 1.297 s | 2.246 s |
    | This PR | 9822 (−1.1%) | 1.375 s (+6.0%) | 2.267 s (+0.9%) |

- TP=2 (2× DGX Spark, tiny random Kolibri): same error vs HF fp32 with and without the second commit.
- Tiny random Qwen2-MoE (internal routing): outputs unchanged by the second commit.
