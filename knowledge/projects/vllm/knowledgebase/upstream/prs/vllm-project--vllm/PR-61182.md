# [Bugfix][Core] Warn when align mode discards --mamba-block-size

[Upstream PR](https://github.com/vllm-project/vllm/pull/61182) · state: open · merged: False

## Original PR description

## Overview

Warn when a user-supplied `--mamba-block-size` is discarded by hybrid align-mode block alignment,
instead of overwriting it silently. Fixes #60838.

## Claims

- A `--mamba-block-size` passed to a hybrid attention/mamba model is discarded with no warning, so the
  flag looks like it worked while the derived value is used. This adds the warning.
- The flag is **not** dead and is **not** deprecated here: it still takes effect on models without
  attention layers. See Details — this corrects the "no effect in any valid configuration" claim in the
  issue title, which was my own and which I verified to be too strong.
- No behavior change beyond the log line; the derived block size is unchanged.

## Validation

Environment: 1×H20, vLLM 0.30.0 for the engine runs; this branch (rebased on `99b44c7`) for the unit
tests and the align-branch runs.

**The flag works on a model without attention layers** — `state-spaces/mamba-130m-hf`, prefix caching on:

| requested `--mamba-block-size` | resolved `block_size` | resolved `mamba_block_size` |
|---|---|---|
| (unset) | 16 | 16 |
| 64 | 64 | 64 |
| 128 | 128 | 128 |
| 256 | 256 | 256 |

All four generate identical text. The resolved values are read back from the KV cache groups
(`v1/engine/core.py`, `min(participating spec block_size)`), so they reach the `MambaSpec`, not just the
config object. `--block-size 32 --mamba-block-size 128` resolves both to 128, so the mamba flag is also
not redundant with `--block-size`.

**The warning fires exactly where intended** — driving the patched align branch through a real
`CacheConfig`:

| scenario | warns | `mamba_block_size` |
|---|---|---|
| user 64, derived 784 (the issue's H20/Qwen3.8 case) | yes | 784 |
| user 64, derived 528 (@lazypool's 4090/Granite repro) | yes | 528 |
| user 1568 > derived 784 | yes | 784 |
| no flag supplied | **no** | 784 |
| user value == derived | **no** | 784 |

**Tests:** `pytest tests/test_config.py -k align_mode` — 2 passed.

`pre-commit`'s `ruff-check` and `ruff-format` pass on all three files. The full `tests/test_config.py`
run is not clean in my environment (CPU-only torch; conftest teardown calls
`torch.accelerator.empty_cache()`), but it is **equally** unclean without this patch: 145 failed on both,
287 passed before vs 289 after, the difference being the two tests added here. I could not run the full
CUDA suite locally.

## Details

**Root cause.** With prefix caching on, `mamba_cache_mode` is forced to `"align"`
(`model_executor/models/config.py`); the default `mamba_block_size` is filled only when it is `None`, so
a user value survives that step. `Platform._align_hybrid_block_size` then unconditionally overwrites it
with the attention block size. @he-yufeng traced this chain in the issue; this patch adds the warning at
that overwrite.

**Why warn and not honor the value.** Align mode requires the mamba page to equal the attention page —
the padding logic immediately below the overwrite enforces exactly that — so an arbitrary
`--mamba-block-size` cannot be honored.

**Why not deprecate the flag.** The other option discussed in the issue was deprecation, on the premise
that the flag was unreachable. That premise is wrong: `update_block_size_for_backend` returns early when
`_find_non_ssm_backends` finds nothing, so for attention-free models the alignment step never runs and
the user value survives — the table above. Removing the flag would regress those users. The warning is
therefore scoped to the align overwrite, and pure-SSM users see nothing.

**Why restore `user_specified_mamba_block_size`.** #58997 removed it along with
`mamba_cache_mode="all"`, so the overwrite site can no longer tell a user value from a defaulted one.
`mamba_block_size != block_size` is not a usable substitute: the default is filled from `block_size` as
it stands at hook time, and later phases may raise `block_size`, which would make that comparison warn on
configurations the user never touched. The restored field has a live consumer again; it is in
`compute_hash`'s ignored set, as before.

**Not duplicating an existing PR.** No open PR references #60838 or touches
`user_specified_mamba_block_size`. #52898 only rewords comments in the same function; #43624 validates
divisibility by 8; #48402 warns about a different inert-prefix-caching condition in a different file.
None overlap.

**Follow-up, out of scope:** #57266 reports that on 0.27.1 an explicit `--mamba-block-size` on a hybrid
model reached the engine and produced an out-of-range strided slice. The current overwrite masks that
path rather than fixing it, so any future change that makes align mode honor user values needs to
address #57266 first.
