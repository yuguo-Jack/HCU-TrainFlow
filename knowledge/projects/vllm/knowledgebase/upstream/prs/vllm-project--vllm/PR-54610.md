# [Bugfix][Offloader] Prioritize sparse MoE experts in UVA CPU offloading

[Upstream PR](https://github.com/vllm-project/vllm/pull/54610) · state: closed · merged: False

## Original PR description

## Description

Fixes #54593.

`UVAOffloader` currently processes model parameters in Python declaration order when `--cpu-offload-params` is not explicitly specified. For Transformer MoE architectures, this can cause dense parameters such as attention projections, layer norms, and router gates to be offloaded before sparse expert weights.

Dense parameters are accessed on every forward pass, whereas sparse expert weights are accessed only for the experts selected by the router. Offloading dense parameters first can therefore introduce significantly more PCIe traffic and degrade inference throughput, as demonstrated in #54593.

### Changes

* **Workload-aware parameter prioritization**

  * When `--cpu-offload-params` is not specified, prioritize sparse MoE expert parameters for CPU offloading.
  * Dense parameters are considered only after the available expert weights have been exhausted.

* **Robust sparse-expert classification**

  * Use dot-delimited parameter-name segments to identify sparse expert parameters.
  * Explicitly avoid classifying shared experts, router/gate parameters, and unrelated parameters as sparse experts.

* **Global multi-layer prioritization**

  * Evaluate candidates across all modules passed to `wrap_modules()`.
  * This prevents dense parameters in earlier layers from consuming the offload budget before sparse experts in later layers are considered.

* **Preserve existing behavior**

  * Explicit `--cpu-offload-params` selections continue to take precedence over the default heuristic.
  * Dense-only models retain their existing declaration-order offloading behavior.
  * If the offload budget exceeds the total sparse-expert weight size, remaining capacity is used for dense parameters in declaration order.
  * An informational message is emitted when dense parameters are also offloaded under the default heuristic.

### Tests

Added `tests/model_executor/offloader/test_uva_offload_priority.py` covering:

* Sparse-expert parameter classification and false-positive cases
* Sparse-expert prioritization within a single MoE layer
* Global expert prioritization across multiple layers
* Spillover from expert to dense parameters when the budget allows
* Explicit `--cpu-offload-params` behavior
* Preservation of declaration-order behavior for dense models

## Cause

`wrap_modules` changed from offloading **as the generator yields** to **materialising every
layer first**:

```python
# before
modules = [self._maybe_offload_to_cpu(m, prefix) for m in modules_generator]
# this PR
modules = list(modules_generator)      # <- all 48 decoder layers built on device
self._offload_modules(modules, prefix)
```

`make_layers` (`models/utils.py`) passes a **generator that constructs each decoder layer**.
`list(...)` builds all of them before any offloading happens, so on a model that does not fit
the card, the device fills up during construction and OOMs before `_offload_modules` is ever
reached for the language model. Offloading exists to avoid that allocation, so the eager
materialisation defeats it.

Instrumented `_offload_modules` to confirm:

```
this PR:  UVA probe #1: modules=1 candidates=333 (sparse=0 dense=333) prefix='visual.'
          UVA probe #1 done: bytes=0.84GB stopped_by_budget=False
          <OOM in wrap_modules -> FusedMoEFactory -> routed_experts.py:176>
```

Only the tower ran. The language model never became a candidate, and it stopped because
candidates ran out — not because the budget was reached. That also explains the
`uva.py:178` warning firing: with `sparse=0, dense=333` the dense flag is set, but the text
("budget exceeded sparse expert weights") does not describe this situation.

## Shape that works

Keep the incremental offload, get the priority from two passes:

```python
modules = []
for module in modules_generator:
    self._offload_modules([module], prefix, only_priority=0)   # sparse experts, as built
    modules.append(module)
if self.cpu_offload_bytes < self.cpu_offload_max_bytes:
    self._offload_modules(modules, prefix, only_priority=1)    # dense, if budget remains
```

(`only_priority` filters the candidate list; ~15 lines total.)

### The thing I would flag

With the PR at default, the run still logs:

```
Dense parameters were offloaded to CPU because the offload budget exceeded sparse expert
weights or all parameters were eligible.
```

I instrumented the `priority == 1` branch to see what that was. On this model it is **the entire
vision tower**:

```
[PROBE] dense offloaded #1: visual.patch_embed.proj.weight   (0.003 GiB)
[PROBE] dense offloaded #3: visual.pos_embed.weight          (0.005 GiB)
[PROBE] dense offloaded #6: visual.merger.linear_fc1.weight  (0.040 GiB)
[PROBE] dense total: 333 params / 0.836 GiB
        (budget 47.000 GiB, cpu_offload_bytes at that moment: 0.836 GiB)
```

The last line is the part I find interesting: **at the moment the dense pass ran, the total
offloaded was 0.836 GiB — no sparse expert had been offloaded yet.** That is consistent with an
offload call whose module set contains no sparse parameters, running while the budget was still
empty.

Whole-model arithmetic says dense should never be reached here: sparse experts are 62.11 GiB
against a 47 GiB budget.

The two numbers do not fully reconcile, so I will not overstate it: the end state differs by
0.45 GiB (`47.69` at default versus `47.24` with explicit `--cpu-offload-params experts`) while
the probe totals 0.836 GiB for the dense pass. Expert granularity may absorb part of the
difference. **What the probe shows directly is the ordering, not the accounting** — dense ran
while the budget was still empty, before any expert had competed for it.

Text-only throughput is unaffected here (7.14 vs 7.11), so this is not costing us speed. What it
costs is placement: **the vision tower ends up resident on the host — the outcome the
prioritisation exists to prevent.**

I have not pinned down which call it arrives through, and I would rather not guess at your
construction order — `_maybe_offload_to_cpu` passing `only_priority=None` is the shape I would
