# [KV Offload][P2P] Fail faster: per-mode load timeout, shorter abort-ack and lookup timeouts

[Upstream PR](https://github.com/vllm-project/vllm/pull/63781) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

Part of #63602: the P2P KV offload tier fails faster on a stuck peer. Symmetric-P2P loads time out after 10s instead of 30s, PD loads keep 30s, the abort-ack timeout drops from 10s to 5s, and the lookup no-progress timeout drops from 30s to 8s.

## Claims

- A stuck symmetric-P2P fetch is surfaced as failed (and recomputed locally) after ~15s (10s load + 5s abort-ack) instead of ~40s.
- A stuck PD fetch fails after ~35s (30s load + 5s abort-ack) instead of ~40s; the PD load timeout itself is unchanged.
- An unanswered symmetric-P2P lookup expires the session after 8s without progress instead of 30s.

## Validation

- `pytest tests/v1/kv_offload/tiering/p2p/`: 325 passed.
- New `test_load_timeout_depends_on_mode`: a probed (P2P) load and an unprobed (PD) load are both backdated past the P2P timeout; only the P2P one aborts.

**E2E, two pods (1×H200 each, `meta-llama/Llama-3.2-1B`, `OffloadingConnector` + `TieringOffloadingSpec` with a `p2p` secondary tier, `p2p_connector_proxy.py`).** Each fault was injected with a temporary pod-only hook (not part of this PR) that drops one inbound message type on the producer while the ZMQ session stays healthy. Each case is one request with a fresh, unique ~600-token prompt, `max_tokens=16`, `temperature=0`; latency is curl `time_total` on the pod.

| Case | Dropped on producer | Path | Request latency | Decoder log |
|---|---|---|---|---|
| Baseline | – | PD via proxy / P2P `remote_kv_source` | 1.80 s / 1.75 s (first request, cold) | – |
| P2P load timeout | `fetch` | P2P | **10.12 s** | `timed out, sending abort` → failure after abort, local recompute |
| PD load timeout | `fetch` | PD | **30.13 s** | same, at 30 s (unchanged) |
| Abort-ack timeout | `fetch` + `abort_fetch` | P2P | **15.11 s** (10 + 5) | `abort_ack timed out` 5 s after the abort |
| Lookup timeout | `lookup` | P2P | **8.11 s** | `lookup response timed out ... after 8.0s without progress`, peer down |
| Recovery | – | P2P / PD | 0.18 s / 0.13 s | KV pulled again, ~0.8 prompt tok/s computed locally |

- Every faulted request still returned the same greedy text as the baseline (it fell back to local prefill); there were no tracebacks, engine deaths or segfaults on either pod.
- Deploy sanity on the branch: French-Revolution prompt (254 tokens) gives coherent text, the counting prompt continues with `30`, and the decoder reports an external prefix cache hit rate of 96%.

## Details

- **Per-mode load timeout.** `_InboundLoadState` gets a `timeout_s` fixed at `request_blocks` time: `_P2P_LOAD_TIMEOUT_S` (10s) when the id ran the lookup phase (`st.probed`), otherwise `_PD_LOAD_TIMEOUT_S` (30s). A symmetric fetch only goes out for keys the peer has already confirmed it holds, so a fetch that has not landed after 10s is stuck. A PD prefiller may still be computing the blocks when the fetch arrives, so PD keeps room for a full prefill.
- **Abort-ack 5s** applies to both modes. Once we have sent `AbortFetchMsg`, waiting longer for the ack does not depend on whether the blocks needed computing.
- **Lookup 8s** stays above the producer's `_LOOKUP_PENDING_TIMEOUT_S` (5s), so a producer holding a `HIT_PENDING` key answers MISS before the consumer gives up.
- `_REAPED_ID_RETENTION_S` (60s) still exceeds the longest load timeout (30s).
- Tradeoff: on a slow but healthy data plane (e.g. very large symmetric fetches over degraded NICs), a fetch that genuinely needs >10s now aborts and falls back to local recompute. The timeouts remain module constants; they are not made configurable here.
