## Overview

Base Labs' decision models mammoth-1 (Qwen3.5-27B) and elephant-1 (9B) ([post](https://www.baseten.co/blog/the-best-decision-models-in-the-world-mammoth-1-and-elephant-1/), [report](https://labs.baseten.co/articles/mammoth-1-and-elephant-1-frontier-decision-models)) were trained with a block-bidirectional mask on their full-attention layers (`modeling_overrides` in `config.json`). Stock vLLM ignores the mask. This PR serves them as trained on `/v1/systemone` and `/v1/decisions`, with prefix caching on.

Related: #63033 (PaliGemma, whole prompt as one PrefixLM block). It does not duplicate this PR; see [Related work](#related-work).

<img src="https://raw.githubusercontent.com/simon-veitner-redhat/vllm/mammoth-elephant-pr-assets/block-bidirectional-mask.png" width="560" alt="Causal mask vs block-bidirectional mask: inside a block a query also sees the later keys of its block; across blocks the mask stays causal.">

No core model-state file and no `attn_utils.py` change. The model's own state class overrides the existing `prepare_attn`, as `diffusion_gemma.py` and DeepSeek V4.1's model state do. On a prefill step with PrefixLM ranges, `MambaHybridModelState` builds the linear-attention groups and the slot state builds the full-attention groups with `build_attn_metadata(mm_req_doc_ranges=...)`, the path Gemma's image ranges take. It writes no field of a built metadata object and imports no backend class.

| commit | what |
|---|---|
| Add `PrefixLMScheduler` for prefix caching with a PrefixLM mask | the scheduler subclass and its tests; it stands alone |
| Add `Qwen3_5ForSlotDecision` and `SlotLMStrategy` | the model, its model state, its config hook, the slot strategy, tests and docs |

## Claims

- `Qwen3_5ForSlotDecision` + `SlotLMStrategy` reproduce the public board: Decision Index 75.36 for mammoth-1 (board 75.34) and 72.27 for elephant-1 (board 72.24).
- No new hook or interface on the core model states.
- Prefix caching stays on with no change to `scheduler.py`, `request.py`, `kv_cache_manager.py`, `kv_cache_utils.py` or any core config file. A `PrefixLMScheduler` subclass that the model selects holds the rules. On a DI 0.3 sample at c64 it makes the masked model 1.51x faster on mammoth-1 and 1.58x faster on elephant-1.
- Other hybrid models are unchanged: Qwen3.5-9B gives bitwise-equal greedy outputs and the same throughput as main.
- Settings that would give wrong reads or hang are refused at startup ([list](#refusals)).

### How it works

```
request ── SlotLMStrategy ── extra_args["prefix_lm_len"] = P, cache_salt = "prefix-lm:" + sha256(prefix)
             │
             ├─ PrefixLMScheduler: hit capped at P · rest of prompt in one step (or wait at queue head)
             │
             └─ Qwen3_5SlotDecisionModelState.prepare_attn: ranges [(0, P-1), (P, L-1)] on prefill steps
                  → super() builds the GDN groups; build_attn_metadata(mm_req_doc_ranges=ranges) the full-attention groups
```

A prefix token's KV and Mamba state depend on the whole prefix, and a question token's depend on the whole prompt. So a cache hit is valid only up to P and only for the same prefix, and a step must never end inside a block.

| rule | where |
|---|---|
| Hits stop at `min(P, num_tokens - 1)` and respect upstream's `max_cache_hit_length` | `_get_local_prefix_cache_hit` |
| The rest of the prompt is prefilled in one step. Otherwise `num_new_tokens = 0` keeps the request at the queue head. A whole prompt from a block boundary skips the Mamba split. | `_mamba_block_aligned_split` |
| Hits need the same prefix: a missing or forged salt is moved into its own namespace, and causal requests are moved out of it | `add_request` |
| Streamed and multimodal requests are read causally (one-time warning), with or without prefix caching | `add_request` |
| A step that ends inside a block raises instead of returning a wrong read | model state |
| FULL CUDA graphs run one-token queries, so the model state skips the ranges there | model state |

Requests without `prefix_lm_len` are scheduled exactly as by `Scheduler`. Under async scheduling, `PrefixLMScheduler.__new__` builds `PrefixLMAsyncScheduler`, because the model hook picks the scheduler before async scheduling is decided.

### Defaults the model sets

| setting | value |
|---|---|
| `--max-model-len` | 16,384, the trained length, when not set (`max_position_embeddings` is 262,144). An explicit value is kept. |
| `--max-num-batched-tokens` | raised to `--max-model-len` when below it, as `EngineArgs` does with chunked prefill off |
| attention backend | `TRITON_ATTN` (the only one that applies the ranges per request) |
| prefix caching | on with FlashInfer GDN prefill (Hopper, or Blackwell with CUDA 13). Otherwise turned off with a log line. |
| scheduler | `PrefixLMScheduler`, with chunked prefill on with prefix caching and off without it |

### Refusals

At startup:

- KV connectors, `--kv-offloading-size`, speculative decoding, context parallelism and micro-batching
- any attention backend other than `TRITON_ATTN` for full attention, including through `backend_per_kind`
- `--max-num-scheduled-tokens` below `--max-model-len`
- `--scheduler-cls`, and with prefix caching `--prefix-match-unit`
- Model Runner V1
- unknown `modeling_overrides`, or `n_slots` outside 1-256

Per request (400): `instructions`, `chat_template_kwargs` other than `{"enable_thinking": false}`, media, prompts that do not fit `--max-model-len` with the answer token, scores with more than 10 levels, and `/v1/decisions` options with repeated labels.

If `SlotLMStrategy` cannot start (for example on a non-fp32 head), a warning says why `/v1/systemone` and `/v1/decisions` are off.

### Trade-offs

- The step budget is only raised to `--max-model-len`. While decodes run, a full-length slot prompt waits at the queue head until they leave room: a 32,514-token read behind 256 decodes waited 13.35 s at a 32,768 budget and 1.07 s at 33,792 (earlier head). Set `--max-num-batched-tokens` to `--max-model-len` plus `--max-num-seqs` to avoid the wait.
- `PrefixLMScheduler` overrides two private `Scheduler` methods. If upstream renames them, the behaviour tests fail and the model-state guard raises instead of returning wrong reads.
- `PrefixLMScheduler` needs Mamba `align` mode, so a non-hybrid PrefixLM model cannot reuse it as is.
- `cache_salt` changes meaning on this server. KV-event consumers see `prefix-lm:<digest>[:<user salt>]`.
- `MAX_LOGPROB_TOKEN_IDS` 128 → 256 (Python and Rust) doubles `LogprobTokenIdsState` on every MRV2 server: 1 MiB at 1,024 requests. It measured no step cost.
- The GDN check calls the private `_resolve_gdn_prefill_backend`, as `olmo_gdn_linear_attn.py` already does.

### Alternatives considered

| option | why not |
|---|---|
| rules inside `Scheduler` | about 50 lines in 6 core files, plus a one-model `SchedulerConfig` field |
| prefix caching off | no core change, but loses the 1.58x / 1.51x DI speed-up |
| content keys in block hashes | correct for connectors and offloading by construction, but needs `request.py` / `kv_cache_utils.py` changes and chunked prefill off server-wide |
| a new hook on `DefaultModelState` that the model state overrides | extends the core model-state interface for one model |
| writing the ranges onto the built `TritonAttentionMetadata` | the same reads and 35 fewer source lines, but the model state would edit objects the base class built, and a composite backend would never see the ranges |
| `TRITON_FLASHINFER` (routes PrefixLM steps to Triton, decode to FlashInfer) | the ranges reach it through `mm_req_doc_ranges`, and it gives the same answers on B200, but it measured no gain (earlier head: decisions/s at c64 0.8% lower, the same decode tok/s), so the hook refuses it |

### Related work

#63033 (open, fixes #62968) makes PaliGemma's whole prompt one bidirectional block. It adds a flag in `Scheduler` and turns chunked prefill and prefix caching off. This PR serves another model family, with two request-defined blocks, keeps prefix caching and leaves `scheduler.py` and the core model states alone.

### Limitations

- `TRITON_ATTN` and Model Runner V2 only.
- `Qwen3_5ForSlotDecision` subclasses `model_executor/models/qwen3_5.py` and runs with torch.compile, like the other Qwen3.5 derivatives on main (D3, colqwen3_5, minicpmv4_6). It does not use main's new eager Qwen3.5 model.
- `/v1/decisions` reads every question as a choice, so a predicate is rendered as a two-option choice rather than the trained yes/no prompt.
- An explicit large `--max-model-len` is kept. At a 263,168-token budget startup crashes with an illegal memory access, which stock Qwen3.5-9B on main does too.
- The Rust frontend accepts 256 `logprob_token_ids`, but like the other decision models it does not serve `/v1/systemone` or `/v1/decisions`.

Hi @simon-veitner-redhat, thanks for the PrefixLM scheduler. We use it to cache the state blocks of Decision 3.0

   The scheduler now says so once.
3. **A PrefixLM prompt no step can prefill.** It returned 0 tokens forever, a silent head-of-line hang. It now
   finishes with a validation error. Only the prompt has to fit a step; outputs of a resumed request don't count.

(We also had to set `supports_mm_inputs` in the hybrid model state tests. Your later commit does the same, so
ignore that one.)
