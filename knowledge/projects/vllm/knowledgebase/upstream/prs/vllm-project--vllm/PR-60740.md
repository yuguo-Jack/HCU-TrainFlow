# [CPU] Optimize routed INT8 W8A8 MoE GEMM dispatch

[Upstream PR](https://github.com/vllm-project/vllm/pull/60740) · state: open · merged: False

## Original PR description

## Overview

Extend the routed CPU MoE dispatch approach from [#50949](https://github.com/vllm-project/vllm/pull/50949) to INT8 W8A8: select brgemm from each expert tile's actual row count instead of the call-wide average. Use brgemm for four-row tiles and share the existing tinygemm arithmetic between BF16 and FP16.

On a 32-core Qwen3 W8A8 serving comparison, the change improves the geometric mean of output throughput across nine concurrency levels by 1.41%, with 5.76% at concurrency 32 and 4.42% at concurrency 64. Peak-concurrency throughput remains at parity. The concurrency-32 baseline varies between repeats; both runs are shown below.

As #50949 describes the approach:
> Select BRGEMM from each expert block's actual `M` and `N`.

Open-PR searches for CPU INT8 MoE and routed GEMM dispatch found no duplicate. #50949 covers FP8/MXFP4; this change covers the separate INT8 W8A8 implementation.

## Claims

- Concentrated routing can use brgemm even when the average tokens per expert would select tinygemm.
- Both routed INT8 GEMM stages select their kernel per tile and release brgemm state when used by the parallel callback.
- BF16 and FP16 support small expert tiles through the same VNNI arithmetic, with conversion directly to the requested intermediate dtype.

## Details

The previous selector uses `max(1, M * topk / E)` for the whole call. That average hides concentrated routing and expert-block tails. Both stages now use actual tile dimensions, skip empty tiles, and track brgemm use within each parallel callback.

The routed INT8 two-argument selector uses `M > 3` for full-width tiles. The existing one-argument selector continues to serve INT8 linear, INT4, and shared-expert callers. FP8/MXFP4 thresholds are unchanged.
