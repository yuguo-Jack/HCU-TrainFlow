# [Perf][Startup] Keep torch._inductor out of import vllm (restore #40056 lazy import)

[Upstream PR](https://github.com/vllm-project/vllm/pull/57310) · state: open · merged: False

## Original PR description


## Purpose

`import vllm` pulls in the whole Inductor/Dynamo stack again. #40056 had removed the eager `torch._inductor` import from `env_override.py`, but #42129 added `_patch_inductor_fallback_allow_list()`, which runs at import time and does `from torch._inductor import lowering`. That's ~1400 modules and about a second on my machine, paid by anything that imports vllm but never compiles: `vllm --help`, `vllm chat`, plugin discovery, library users, the model-inspection subprocess.

The fix keeps the #42129 patch but applies it lazily. `env_override.py` already has a one-shot `MetaPathFinder` for the cpp `indirect_assert` backport (#40973); I generalised that helper and use it to run the wrap right after `torch._inductor.lowering` finishes importing (or immediately, if it's already loaded). `torch._inductor.graph` is the only consumer of `FALLBACK_ALLOW_LIST` and imports it from `lowering` at module load (checked 2.12, 2.13, 2.14 and main), so the wrap is always in place before any `GraphLowering` runs.

I also looked at why CI didn't catch the regression. `tests/standalone_tests/lazy_imports.py` sets `sys.modules["torch._inductor.async_compile"] = None`, which does make the eager import raise, but the patch swallows that in an `except ImportError` after the package has already been imported. So I added a plain post-import check that `torch._inductor` and `torch._dynamo` aren't in `sys.modules`. It fails on main and passes here. (Gated to torch >= 2.12; on older torch the file still has version-gated backports that import Dynamo eagerly.)

To be clear about scope: this does nothing for the API server or the engine core. Both import the stack anyway through `vllm/config/compilation.py -> inductor_pass.py` and the module-level `@torch.compile` decorators, so their module counts don't change. That edge is a separate follow-up.

I considered applying the patch at the compile call sites instead (the way #36152 does for `constrain_to_fx_strides`). That's simpler, but it loses the process-wide semantics #42129 wanted, so I kept the finder. Happy to switch if you'd rather have the call-site version.

## Test Plan

```
python tests/standalone_tests/lazy_imports.py
pytest tests/compile/test_inductor_fallback_allow_list_patch.py
python -X importtime -c "import vllm" 2>&1 | grep -c torch._inductor
```

Plus a few manual checks: importing `lowering` first vs `graph` first, Inductor already imported before vllm, and a `torch.compile` of a function calling a `vllm::` custom op, which still gets no implicit-fallback lowering.

## Test Result

- `lazy_imports.py` passes here and fails on main at the new assertion.
- The 18 tests in `test_inductor_fallback_allow_list_patch.py` pass.
- `import vllm` on an M3 Pro (torch 2.13, CPU build): 2613 -> 1194 modules, `torch._inductor*` 160 -> 0, wall ~1.4 s -> ~0.5 s.
- Couldn't run the ROCm lane locally. Nothing in the deferred set loads a native library in a different order (the #51151 failure mode), but please let the AMD mirror run before merging.

Not a duplicate as far as I can tell: the only PR touching `FALLBACK_ALLOW_LIST` is #42129 itself, and #54446 (dead torch-2.9 patches in the same file) edits a different region.
