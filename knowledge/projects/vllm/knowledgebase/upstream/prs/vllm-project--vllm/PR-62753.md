# [Bugfix][Benchmark] Count tool call deltas as generated tokens in openai-responses

[Upstream PR](https://github.com/vllm-project/vllm/pull/62753) · state: closed · merged: True

## Original PR description

## Overview

`vllm bench serve --backend openai-responses` marks every tool-call-only response as failed. It counts only `output_text` and `reasoning_text` deltas as tokens, and a forced tool call streams only `function_call_arguments` deltas. This counts the four tool delta events the vLLM Responses server emits, as `openai-chat` counts `tool_calls` deltas.

## Claims

- 100 tool calls the server completed with HTTP 200 went from 0 to 100 successful, with totals now identical to `openai-chat` on the same workload.
- Added events: `function_call_arguments`, `custom_tool_call_input`, `mcp_call_arguments`, `code_interpreter_call_code` (from `responses/streaming_events.py`). Tool arguments are timed but not added to `generated_text`, as on chat.

## Validation

New tests in `tests/benchmarks/test_responses_request_func.py`: a tool-call-only response (TTFT, ITL, usage, `latency - ttft == sum(itl)`), each tool delta type, and text followed by a tool call. 30 passed; the 6 new ones fail on `main` with "Never received a token delta". Timing tests (29) and pre-commit pass.

RTX 3080, `Qwen/Qwen2.5-0.5B-Instruct` with `--enable-auto-tool-choice --tool-call-parser hermes`, 100 prompts, concurrency 16, `tool_choice: "required"` via `--extra-body`:

| | `main` | this branch | `openai-chat` |
|---|---|---|---|
| completed / failed | 0 / 100 | 100 / 0 | 100 / 0 |
| input / output tokens | 0 / 0 | 20,610 / 2,090 | 20,610 / 2,090 |

Per request, output tokens match the server's `usage` and ITL counts match the token events recorded on the wire.

## Details

#54628 added this backend with tool calls out of scope. Leaving them out fails the request, so tool-calling workloads such as the BFCL dataset (#42457) can't be measured on it. The Rust `vllm-bench` Responses backend has the same gap; I'll send that separately.

No issue or PR covers this. Open PRs touching `endpoint_request_func.py` (#51155, #55719, #57519, #58734) don't change these events.

AI assistance (Claude) was used to find this and write the change and tests. I reviewed every line and ran the tests and GPU comparison.
