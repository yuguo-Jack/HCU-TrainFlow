# [Bugfix] Resolve eager_break_during_capture at call time, not import time

[Upstream PR](https://github.com/vllm-project/vllm/pull/59941) · state: closed · merged: True

## Original PR description



## Overview

Fixes #59940. `@eager_break_during_capture` decided whether to wrap a function when the decorated module was
imported. With `VLLM_BATCH_INVARIANT=1`, the breakable-graph flag is turned on later, inside `VllmConfig` (#57586).
Any import of `attention.py` before that point leaves `unified_attention_with_output` unwrapped, and FA2 then produces
wrong tokens for short prefills. This PR makes the decorator always return its wrapper, so the setting is read at call
time. It's a 2-line removal plus CPU tests.

## Claims

- Breakable-graph eager breaks no longer depend on import order. In-process and default-fork engines with a cold
  model-info cache now get the wrapped attention op.
- With the flag off, behavior is unchanged: the wrapper calls the function directly when no breakable capture is
  active.
- Every current and future user of the decorator is covered (33 sites, plus those added by #46372 and #57881), with no
  new imports.

change, the cost only arose when the flag was on.

## Details

- **Root cause:** `vllm/compilation/breakable_cudagraph.py` had `if not is_breakable_cudagraph_enabled(): return fn`.
  On a cold model-info cache, `ModelConfig` construction imports `attention.py` via `registry._save_modelinfo_to_cache`
  → `weight_utils.atomic_writer` before `VllmConfig._maybe_enable_breakable_cudagraph` sets the env. Forked engine
  cores inherit the bare op. First reported by @Taimys in #58918 and in the #57311 thread.
- **Scope beyond batch invariance:** as @LioEinaudi pointed out in #59940, the other branch of
  `_maybe_enable_breakable_cudagraph` (`_uses_breakable_cudagraph_by_default`, #52861) sets the same env var after the
  same early import, for the `DEFAULT_BREAKABLE_CUDAGRAPH_ARCHITECTURES` models on CUDA, with no
  `VLLM_BATCH_INVARIANT` involved. The ordering hazard is the same and this change covers it. I only validated the
  `VLLM_BATCH_INVARIANT=1` path above, and I did not run those models, so I can't say whether their outputs are
  affected.
- **Why this isn't a duplicate of #57311:** #57311 (open) removes that particular import chain, and @Taimys confirmed it
  fixes that trigger on L20. The decorator stays import-order dependent, though: with #57311 applied on main and a warm
  cache, a user script that imports `vllm.model_executor.model_loader` before building `LLM` still ends up with the
  unwrapped op (verified by inspecting the op, not by comparing outputs). #53293 fixed the same root cause for Ray only. This PR removes the
  dependence at its source and works alongside #57311.
- **Dynamo:** the wrapper's thread-local lookup traces without a graph break (`fullgraph=True` test), so no
  `is_compiling()` fast path is needed.
- **Not included:** a GPU end-to-end regression test. Maintainers: would you like one (for example a cold-cache
  `VLLM_BATCH_INVARIANT=1` FA2 run in the BI test suite)?
