# [Bugfix][GLM-5.3-Flash] persistent topk kernel loses candidates on overflow

[Upstream PR](https://github.com/vllm-project/vllm/pull/58785) · state: open · merged: False

## Original PR description

## Purpose

The persistent-topk kernel can miss higher-scoring entries, and the entries it misses depend on atomic ordering, so identical runs can differ.

On a GB10, rows of 6000 to 32768 candidates with tight score distributions drop 89 to 6603 winners across five rows.

We can add detection for overflow which add one extra comparison/load on the hot paths for cases that do not overflow. On overflow, we select the bin's top members exactly with a byte-wise radix pass over the row. In the vast majority of cases this is not hit. On the fast path, we are within 1 to 2 µs at 25 to 55 µs per call. The fallback itself, which should be rare outside of the failure case, costs ~2 µs per call at about 10k pools and ~18 µs at about 30k pools.

`radix_topk` has no capped buffer and is unaffected. `FilteredTopKUnifiedKernel`, `cooperative_topk`, and `histogram_4096_topk` have the same buffer limit pattern on sm_90 and sm_100 and are not changed here...  PRs to follow there. (see #53287 as well)

<summary> Repeating prompt generator (`topk_flat_prompts`) </summary>

```
#!/usr/bin/env python3
"""Flat prompts that overflow persistent_topk's threshold-bin buffer.

Each prompt is one short unit repeated to ~40k or ~120k tokens, then a question
so the model decodes. Repetition makes the sparse indexer's scores nearly flat,
so the bin holding the k-th score holds far more entries than the kernel's
buffer (4096 on the 256-bin path). Repeat counts below are the ones used on
GLM-5.3-Flash; other tokenizers land at slightly different lengths.

  python3 topk_flat_prompts.py --write DIR           # write the 8 prompts as .txt
  python3 topk_flat_prompts.py --url http://HOST:PORT --model NAME

Serve with --sparse-indexer-topk-backend persistent (or the kernel config
equivalent) and --enforce-eager if you hook the decode top-k from Python to
compare it against torch.topk. Standard library only.
"""
import argparse, json, os, time, urllib.request

TOOL = ("<tool_call>Bash<arg_key>command</arg_key><arg_value>ls -la</arg_value></tool_call>\n"
        "<tool_response>total 0\n</tool_response>\n")
# (name, unit, repeats at ~40k tokens, repeats at ~120k tokens)
UNITS = [
    ("ok", "ok\n", 20000, 60000),
    ("a", "a ", 39999, 119999),
    ("fox", "The quick brown fox jumps over the lazy dog.\n", 4000, 12000),
    ("tool", TOOL, 2000, 6000),
]
QUESTION = "\nHow many times does the line above repeat? Answer with a number."


def prompts():
    for label, idx in (("40k", 2), ("120k", 3)):
        for u in UNITS:
            # the header line makes each prompt unique, so no prefix cache hit
            yield f"{u[0]}_{label}", f"session {label}-{u[0]}\n" + u[1] * u[idx] + QUESTION


def main():
    ap = argparse.ArgumentParser()
    ap.add_argument("--write", metavar="DIR")
    ap.add_argument("--url")
    ap.add_argument("--model", default="glm53")
    ap.add_argument("--max-tokens", type=int, default=128)
    a = ap.parse_args()
    if not (a.write or a.url):
        ap.error("pass --write DIR or --url URL")
    for name, text in prompts():
        if a.write:
            os.makedirs(a.write, exist_ok=True)
            with open(os.path.join(a.write, name + ".txt"), "w") as f:
                f.write(text)
            print(f"{name}: {len(text):,} chars")
        if a.url:
            body = {"model": a.model, "temperature": 0, "max_tokens": a.max_tokens,
                    "messages": [{"role": "user", "content": text}]}
            req = urllib.request.Request(a.url.rstrip("/") + "/v1/chat/completions",
                                         data=json.dumps(body).encode(),
                                         headers={"Content-Type": "application/json"})
            t0 = time.time()
            with urllib.request.urlopen(req, timeout=1800) as r:
                usage = json.loads(r.read()).get("usage", {})
            print(f"{name}: prompt_tokens={usage.get('prompt_tokens')} "
                  f"completion_tokens={usage.get('completion_tokens')} {time.time() - t0:.1f}s", flush=True)


if __name__ == "__main__":
    main()
```

Dropped winners on my card, your definition (score strictly greater than the smallest score returned, not returned), rows 6000/8192/10500/20000/32768:

```
distribution    k=512              k=1024             k=2048
one_bin         5/5 rows,  7239    5/5 rows, 14260    5/5 rows, 29095
one_bin_ties    5/5 rows,  6998    5/5 rows, 14101    5/5 rows, 28831
normal          2/5 rows,   145    3/5 rows,  1579    3/5 rows,  5994
```

Same magnitude as your 89-6603, and the `normal` row is the one that matters for real traffic.

**On the fix.** Three things I checked because they look wrong at a glance and aren't:

The two-ended fill in the emit pass is not racy. `out_count` enters at `TopK - remaining_k`, `count(key > prefix)` is exactly `remaining_k - remaining_k_final`, so the `atomicAdd` side fills `[TopK-remaining_k, TopK-remaining_k_final)` and the tie side fills `[TopK-remaining_k_final, TopK)` from the top via `TopK - slot`. Disjoint, and exactly full.

The shared-memory reuse is in bounds on both paths. Decode: `hist` is `decode_smem[0..255]` while `scratch` is `decode_smem[8186..8188]` (`SBASE=8184`, `sREF=2`), and `scratch[2]` aliases `sBUF0` which is dead once `raw_buf0` is read. Medium: `hist` is the first 256 of `shared_histogram[0]` (384 ints) and `scratch` is `medium_scalars[2..4]`, which is exactly the 5 slots allocated — `scratch[0]` overwrites `shared_buffered_count[0]`, but the `__syncthreads()` after zeroing `hist` means every thread has already evaluated the overflow condition.

`remaining_k >= 1` holds at both call sites (`return` at 304 and 486), which matters because if no `(lane, j)` satisfied `above < remaining_k <= above + counts[j]` the pass would silently reuse the previous pass's `scratch[0]`. Might be worth an assert or a comment on that precondition, since the failure mode is a wrong answer rather than a crash.

**One coverage note.** Dispatch is `seq_len <= TopK` trivial, `<= 8192` the 2048-bin path, `<= 32768` the 256-bin path, and **`> 32768` goes to `radix_topk`**, which this PR doesn't touch. Your five row lengths cover both patched kernels (6000/8192 → 2048-bin, 10500/20000/32768 → 256-bin) and the largest is exactly the dispatch boundary, so one more candidate falls off the fix. You named `FilteredTopKUnifiedKernel` and `histogram_4096_topk` as follow-ups but not `radix_topk` — does it share the buffer pattern too? Asking because your e2e is 42k tokens of context while the max bin stays near 30k, so the boundary is close to real traffic rather than theoretical.

Cross-link: #55122 changes the same kernel and removes this failure by construction. It replaces the capped candidate buffers with a radix select that rescans the row for each key byte (at most five reads of the row), so there is no buffer to overflow; exact-key ties at the k-th value are ranked by index, which also makes the output deterministic. On a second GB10 it measured 21–28 % faster than the exact-topk workaround.

- LoongPei · comment · 2026-09-30T02:50:52Z · [source](https://github.com/vllm-project/vllm/pull/58785#issuecomment-5903108014)

Data point for the `cooperative_topk` follow-up mentioned in the description: it is reachable on SM90 with DeepSeek-V3.2 in the default decode configuration, and under tensor parallelism it shows up as TP ranks selecting different (wrong) sets. It may also help with the question in #53287 of whether overflow is hit in real use: here it is, at long context.

**Setup.** vLLM 0.30.0, DeepSeek-V3.2, 8x H20-3e (SM90), TP8, `--kv-cache-dtype fp8_ds_mla`, `--enforce-eager`, default `sparse_indexer_topk_backend` (auto). Closed-loop replay of public Claude Code traces (SemiAnalysis `cc-traces-weka-062126`), 16 concurrent sessions, contexts up to 163,840 tokens, no speculative decoding.

**What we saw.** We wrapped `SparseIndexerTopk.forward` and, after every call, all-gathered per-row checksums of the selected set and of the logits window `[0, seq_len)` over the TP group.

- All 6,099 decode calls in a 10-minute window resolved to `cooperative`.
- 314 calls (5.1%) had at least one row whose selected set differed across ranks, 341 rows in total. For all 341 rows the logits windows were bitwise identical on all 8 ranks.
- The 24 rows we dumped (seq_len 77,765 to 95,183): on every rank the output is not a valid top-2048. Each rank misses 5 to 228 keys whose score is strictly above the 2048th score. There are no ties at the 2048th score (it occurs once). One row returned only 2,017 indices.

**Stand-alone replay.** The same 24 logits rows fed to the kernels directly on one GPU, with a zeroed workspace, `max_seq_len` = row length, and `stride(0) % 4 == 0`:

| kernel | rows with an invalid top-k (5 replays each) |
|---|---|
| `cooperative_topk` | 24 / 24, every replay |
| `persistent_topk` | 0 / 24 |
| `top_k_per_row_decode` | 0 / 24 |

Random Gaussian logits never fail `cooperative_topk` at lengths from 4K to 164K. In the real rows, 1,700 to 5,500 entries share the top 12 bits of their fp32 score with the 2048th score, which fits the overflowing-threshold-bin pattern described in this PR.

**How often.** We then checked every decode row on TP rank 0 against `torch.topk` (same replay, 10 minutes, about 11,000 `cooperative_topk` calls; a row is invalid when it misses a key whose score is strictly above the 2048th score):

| row length | rows | invalid | share | true top-k keys missed per invalid row |
|---|---|---|---|---|
| 32K–64K | 9,780 | 9 | 0.09% | 23 |
| 64K–128K | 49,794 | 1,209 | 2.43% | 50 |
| 128K–164K | 6,405 | 419 | 6.5% | 52 |

**Why it matters.** With `auto`, SM90 decode batches of up to 64 rows go to `cooperative`, so at long context V3.2 attends to a wrong set of tokens in some layers without any error, in about 1 row in 15 beyond 128K. `--sparse-indexer-topk-backend per_row` avoided it on the dumped rows.

Happy to share the 24 rows (float32 logits windows with their seq_len, as a zip of npz files) as test vectors for the follow-up.
