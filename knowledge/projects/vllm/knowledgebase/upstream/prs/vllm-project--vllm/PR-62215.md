# [Bugfix] Treat negative decimal CLI values as values, not dotted args

[Upstream PR](https://github.com/vllm-project/vllm/pull/62215) · state: open · merged: False

## Original PR description

## Overview

Fix `FlexibleArgumentParser` treating negative decimal values (e.g. `-0.5`) as dotted JSON args, which broke `vllm bench serve --presence-penalty -0.5` / `--frequency-penalty -1.0`.

## Claims

- `--presence-penalty -0.5`, `--frequency-penalty -1.0` (and any negative decimal value given as a separate token) now parse the same as with plain `argparse`.
- Fixes the two observed failures: `unrecognized arguments: -0 {"5": "--next-flag"}` when another arg follows, and `IndexError: list index out of range` when the value is the last arg.
- Dotted args (`--hf-overrides.key`, `-cc.mode`, `+` list appends) behave exactly as before.

## Validation

Tested on `main` @ `0c5dd18` (Python 3.13, CPU).

**Before:**
```
$ vllm bench serve --model dummy --presence-penalty -0.5 --num-prompts 1
error: unrecognized arguments: -0 {"5": "--num-prompts"}

$ vllm bench serve --model dummy --num-prompts 1 --frequency-penalty -1.0
  File ".../vllm/utils/argparse_utils.py", line 469, in parse_args
IndexError: list index out of range
```

**After:** both parse to `presence_penalty=-0.5` / `frequency_penalty=-1.0`.

**Tests:**
```
pytest tests/utils_/test_argparse_utils.py -k negative_decimal
# without the fix: 2 failed (the two errors above)
# with the fix:    2 passed

pytest tests/utils_/test_argparse_utils.py --deselect tests/utils_/test_argparse_utils.py::test_convert_ids_list_to_tokens
# 33 passed, 1 skipped
```
(`test_convert_ids_list_to_tokens` was deselected only because it downloads a tokenizer from the HF Hub, which wasn't reachable in my environment; it is unrelated to this change.)

`pre-commit run --files` on both changed files passes (ruff, ruff-format, typos, mypy, test-tethering, etc.).

## Details

**Root cause:** `parse_args` rewrites dotted args before handing off to argparse, and it identifies them with `processed_arg.startswith("-") and "." in processed_arg`. A negative decimal value like `-0.5` satisfies that, so it was split into option `-0`, key `5`, and the *next* token was consumed as its value (or indexed past the end of the list).

**Fix:** skip tokens that fully match a negative decimal (`_NEGATIVE_DECIMAL`, also covering `-.5` and exponents like `-1.5e-3`) before the dotted-arg handling. A registered-option lookup isn't viable here because this preprocessing runs in the top-level `vllm` parser, before subcommand dispatch, so it doesn't know the subcommand's option strings. Negative integers never reach this branch (no `.`), and the `--flag=-0.5` form was already handled.

**Limitations:** a non-numeric value that starts with `-` and contains `.` (e.g. `--served-model-name -foo.bar`) passed as a separate token to a non-dotted option is still misread; that's out of scope here.

**Duplicates:** I searched for existing issues/PRs about negative CLI values and `FlexibleArgumentParser` dotted-arg parsing and found none.
