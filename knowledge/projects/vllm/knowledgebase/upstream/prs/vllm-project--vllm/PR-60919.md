# [JIT][ROCm] Fully warmup GLM-5.3-Flash

[Upstream PR](https://github.com/vllm-project/vllm/pull/60919) · state: closed · merged: True

## Original PR description

## Overview

It used to JIT several triton kernels during runtime. This PR
1. registers those kernels for warmup.
2. fixes a bug where even after registering for warmup, triton re-compiled during runtime on ROCm

#### **Explanation for the triton fix:**: 
- Triton on AMD specializes kernels on buffer size being below or above 2GiB, i.e int32 addressable. 
- When <2GiB, this allows the compiler to lower to buffer load/store intrinsics which require 32-bit offsets
- The warmup code previously assumed all buffers passed during warmup were <2GiB. 
- In `kpool_tail_seed_dispatch` we pass the kv cache which can be large. During warmup it specialized on a <2GiB KV cache, whereas at runtime it gets passed a larger KV cache and re-compiles _without_ buffer loads. See https://github.com/ROCm/triton/blob/0ec280cf80dd91e9a86887981a670f2d4541a32b/third_party/amd/backend/compiler.py#L76-L110 for details
- This PR removes that assumption and instead passes the real buffer size

## Claims

- No runtime compilation on GLM-5.3-Flash, i.e. doesn't crash with `--jit-monitor-mode error`

## Validation

Expect lots of runtime compilation on main, none on this branch

- eppaneamd · comment · 2026-10-30T17:22:44Z · [source](https://github.com/vllm-project/vllm/pull/60919#issuecomment-6528961138)

**Optional, not blocking: the kpool kernels can warm with 2 compiles instead of 8**

This PR warms 8 variants of the two kpool kernels: `_kpool_softmax_rotate_write_cache_kernel` for `loc_ptr` aligned or not, and `_kpool_tail_seed_kernel` for `tslot_ptr` aligned or not × `n_tokens` = 1, a multiple of 16, or other. On gfx950 they compile to the same code, except that the `n_tokens == 1` variant compares the mask against a constant instead of the argument (same instruction count). `loc_ptr` and `tslot_ptr` are only read by scalar loads, and `n_tokens` only feeds the `i + KPOOL < n_tokens` mask.

**Proposed fix:** opt the two kernels out of these specializations:

```python
@triton.jit(do_not_specialize_on_alignment=["loc_ptr"])
def _kpool_softmax_rotate_write_cache_kernel(...)

@triton.jit(do_not_specialize=["n_tokens"], do_not_specialize_on_alignment=["tslot_ptr"])
def _kpool_tail_seed_kernel(...)
```

Measured through this PR's warm-up at its head on MI355X: 2 + 6 compiles become 1 + 1, and the warm-up of the two kernels takes 538 ms instead of 769–775 ms per process. In both cases, 24 prefill-write batches after the warm-up compile nothing and write identical cache bytes. With JIT warm-up off (`--kernel_config.enable_jit_warmup=False`, or `--enforce-eager` unless fault tolerance is enabled), serving compiles at most 2 variants instead of up to 8.

- MI355X (gfx950), `vllm/vllm-openai-rocm:nightly-rocm72-3966924d56` (Triton 3.8.0), this PR's `vllm` tree with and without the decorators on `PYTHONPATH`. `get_warmup_keys` and `warmup` of `kpool_compress_dispatch` and `kpool_tail_seed_dispatch`, then the AMD indexer's prefill writes for 0–3 decode and 1–1024 prefill tokens at GLM-5.3-Flash index shapes. Two runs of each in the order PR, decorators, decorators, PR, with an empty Triton cache per run.
- ISA: gfx950 code of the decorated kernels compared with all 8 original variants, at the 4 warps they launch with.
- Scope: the AMD kernels only; the NVIDIA twins in `nvidia/ops/kpool_compress.py` are not checked.
