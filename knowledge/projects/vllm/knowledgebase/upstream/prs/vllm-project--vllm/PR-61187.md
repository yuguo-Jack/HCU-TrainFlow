# kv offload: invalidate cached absent verdicts after a successful store

[Upstream PR](https://github.com/vllm-project/vllm/pull/61187) · state: open · merged: False

## Original PR description

## Overview

A block that a secondary KV-offload tier previously probed as **absent** keeps
serving that stale "absent" verdict even after the block is later **stored**
into the tier. `AsyncLookupManager` only corrects a cached negative verdict on a
*failed load* (`mark_miss`); there was no path to correct it when the block was
later *written* to the tier, so the scheduler kept skipping a block that was
actually on disk.

This PR adds `AsyncLookupManager.invalidate()` and calls it from
`FileSystemTierManager.get_finished_jobs()` when a store job succeeds, so freshly
stored blocks are re-probed instead of served as a stale miss.

## Claims

- Fixes a correctness bug: a block stored into a secondary tier after its
  absence was cached is still served as absent (the cached negative is never
  invalidated on a successful store).
- `invalidate()` is conservative: it drops **only** resolved-absent
  (`result is False`) entries. Present, in-flight, and unknown keys are left
  alone, so it is safe to call with a store job's full key list.
- `FileSystemTierManager` now tracks store-job keys unconditionally (previously
  only when KV events were enabled) and pops them unconditionally on completion,
  so the key map cannot leak.
- No change to KV-event emission: an event is still emitted iff a store succeeds.
- Additive and non-breaking: `invalidate()` is a new method, and the `cleanup()`
  change is a strict superset of the previous behavior.

## Validation

New unit tests in `tests/v1/kv_offload/tiering/test_async_lookup.py`:

- `test_invalidate_drops_stale_absent_and_reprobes` - after a stored block, the
  cached negative is dropped and the next lookup re-probes and sees the block as
  present (not the stale miss).
- `test_invalidate_is_noop_for_present_and_unknown_keys` - `invalidate()` leaves
  a present entry alone and is a no-op for an unknown key (plants nothing).
- `test_cleanup_is_safe_after_invalidate` - `cleanup()` does not raise
  `KeyError` when a tracked key was dropped by `invalidate()`.

Command + result (run on a local build):
```
pytest tests/v1/kv_offload/tiering/test_async_lookup.py -q
```
- With the change: all tests pass (including the 3 new ones).
- Without the change: exactly the 3 new tests fail (`invalidate` not defined);
  all pre-existing tests in the file still pass.

Pre-existing tests in the file are unaffected - the change is an additive method
plus a strict-superset `cleanup()` guard, so no existing behavior changes. Model
evaluation is not applicable: this is offload bookkeeping and does not change
model output, accuracy, or serving. The full suite runs in CI.

## Details

Root cause: `AsyncLookupManager` caches a probe's verdict per key. A negative
verdict (`result is False`) is only ever overridden by `mark_miss()` (the
failed-load livelock fix, #49176). But the *store* path
(`FileSystemTierManager.get_finished_jobs`) never touched the lookup manager, so
once a block was cached as absent, storing it into the tier left the stale
negative in place and the scheduler kept treating the block as absent.

Design:
- `AsyncLookupManager.invalidate(keys)` drops only entries where
  `result is False`. It intentionally does **not** touch present (`True`),
  in-flight, or unknown keys, so it is safe to call with a job's full key list
  and idempotent.
- `FileSystemTierManager` tracks `_store_job_keys` for every store job (it used
  to only track them when KV events were enabled) and, on a *successful* store,
  calls `invalidate()` on those keys before (and independently of) emitting any
  KV event. The map is popped unconditionally in `get_finished_jobs`, so no keys
  accumulate when events are disabled.
- `AsyncLookupManager.cleanup()` switches its per-key lookup from a direct index
  (`self._lookup_state[key]`) to a guarded `.get()` + `continue`, because
  `invalidate()` can drop a key that a tracked request still references; without
  the guard that path would raise `KeyError`.

Tier-agnostic: the fix lives in the shared `AsyncLookupManager`, so it applies to
any secondary tier, not just the filesystem tier.

## Why this is not duplicating existing work

Searched open PRs and issues in `vllm-project/vllm` (2026-10-12):

- No open PR invalidates a cached absent verdict on a successful store. The
  "invalidate" PRs are unrelated subsystems (startup plans, GPU budget, LazyDict,
  KDA conv weights, HiSparse, CPU metadata).
- The closest open offload PRs are distinct: `#59096` guards the *mark_miss*
  (failed-load) path - the complement to this store path; `#53158` is hash
  promotion; the rest are telemetry / wait-bounding / per-group publish / metrics.
- No open issue tracks this bug, and the fix is not present on `main`.
