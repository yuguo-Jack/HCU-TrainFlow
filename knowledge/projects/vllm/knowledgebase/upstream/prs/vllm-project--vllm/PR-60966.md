# [Fast Start][Bugfix] Snapshot GPU memory after external weights are ready

[Upstream PR](https://github.com/vllm-project/vllm/pull/60966) · state: closed · merged: True

## Original PR description


<!-- markdownlint-disable -->

## Overview

When the IPC weight-cache daemon loads zero-copy weights concurrently with engine startup, the current initialization order counts the daemon's late allocations twice. This can leave no valid memory budget for the KV cache even though the GPU has enough free memory.

## Claims

- Take `init_snapshot` after external weight memory is ready.
- Restore automatic KV-cache sizing for static EP IPC loading.

## Validation

```text
python3 -m pytest -q -s tests/model_executor/model_loader/test_weight_cache.py -k qwen3-ep --timeout=1800
```

With a real Qwen3-30B-A3B-Instruct MoE model used by #57320, TP=2, EP enabled, and the fixed KV-cache override temporarily removed in the validation harness: `1 passed, 15 deselected`. Baseline, cold fallback, warm zero-copy, and zero-copy restart all produced identical outputs; both zero-copy runs mapped 676 tensors per rank. Automatic sizing reported about 28 GiB of available KV-cache memory and 611,440 KV-cache tokens. The test file is unchanged in this PR.

## Details

Assume 100 GiB total memory and `gpu_memory_utilization=90%`:

```text
Memory usage
100 ┤
 90 ┤──────────────────────────────── budget limit
 80 ┤
 75 ┤                         ┌──────────────┐
 70 ┤                         │ daemon 50    │
 60 ┤                         │ engine 25    │
 50 ┤               ┌─────────┴──────────────┘
 40 ┤               │ daemon 50
 30 ┤               │
 20 ┤     ┌─────────┘
 10 ┤     │ daemon 20
  0 ┼─────┴────────────────────────────────────→ time
       t0              t1                 t2
   snapshot        daemon ready       profiling
```

At `t0`, the daemon uses 20 GiB, so `init_snapshot` records 80 GiB free. At `t1`, daemon loading completes at 50 GiB and `get_memory()` reports 50 GiB. At `t2`, the engine itself uses 25 GiB, so the actual total is 75 GiB.

The target budget is 90 GiB. The intended engine budget is `90 - 50 = 40 GiB`, but profiling measures `80 - 25 = 55 GiB` from the old snapshot. That 55 GiB includes the daemon's late 30 GiB allocation and the engine's 25 GiB allocation. The daemon's 30 GiB is therefore charged once through `get_memory()` and again through the profiling delta. The resulting requested KV-cache budget is reduced by 30 GiB too much; in the real Qwen3 EP test it became `-2.46 GiB`, so KV-cache initialization failed.

With the snapshot taken after daemon readiness, the profiling delta is `50 - 25 = 25 GiB`, which measures only engine allocations. The external-weight deduction and profiling baseline then describe the same memory state.
