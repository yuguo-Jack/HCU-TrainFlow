# [Bugfix] Keep MRV2 model state in the runtime pool under sleep mode

[Upstream PR](https://github.com/vllm-project/vllm/pull/63548) · state: closed · merged: True

## Original PR description



## Overview

Build the Model Runner V2 model state in the `runtime` cuMem pool when sleep mode is on, so its device tensors survive level-2 sleep. Same approach as the LoRA state in #62358. #60009 lists Qwen4Exp `ngram_context_offsets` as out of its scope ("held by non-module objects"); this covers it.

## Claims

- **Bug fix:** after `sleep(level=2)` + `wake_up()`, Qwen4Exp's `ngram_context_offsets` (a constant `arange(-ngram_context_len, 0)` on `Qwen4ExpModelState`) comes back as garbage (zeros in practice). Every later PLE n-gram context is wrong, so outputs are corrupted even when the weights are reloaded bit-exact. With this change it survives.
- **Scope:** every MRV2 model state, not only Qwen4Exp: all of `init_model_state`'s device tensors move from the `weights` pool to the `runtime` pool. Only under `enable_sleep_mode` on CUDA/ROCm (XPU excluded: no nested pools, as in #62358).
- **Cost:** level-2 sleep now copies the model state to host memory, as level 1 already did, instead of discarding it. These are per-request bookkeeping buffers (`max_num_reqs`-sized), plus `inputs_embeds` (`max_num_tokens x hidden`) for models that use it.
- **Test:** `test_deep_sleep_model_state` checks that every model-state device tensor is allocated in the `runtime` pool and is unchanged after level-2 sleep + weights wake-up.

The Qwen3.8 repro uses `LLM(model, tensor_parallel_size=4, enable_sleep_mode=True, max_model_len=4096, gpu_memory_utilization=0.5, disable_custom_all_reduce=True)`, then generate → `sleep(level=2)` → `wake_up(tags=["weights"])` → `collective_rpc("reload_weights")` → `wake_up(tags=["kv_cache"])` → generate. The slice has random weights, so greedy TP=4 decoding is not run-to-run deterministic even without sleep. A no-sleep control (generate twice on one engine, 3 runs per arm) produces the same few late divergence patterns (none, or tokens 5–63) that this PR shows after sleep. On main, every prompt diverges at token 0–1.

## Details

**Root cause:** `Worker.load_model` runs `GPUModelRunner.load_model` inside the `weights` pool. `init_model_state` runs there too, so the model state's tensors land in that pool. Level-2 sleep discards the `weights` pool, and wake-up restores only `model.named_buffers()` (and parameters, through the weight update). The model state belongs to the model runner, not the model, so registering its tensors as module buffers (the #60009 approach) does not apply.

**Fix:** wrap `init_model_state` in `use_memory_pool(tag="runtime")` under sleep mode. Nested `use_memory_pool` calls restore the outer tag, so the weights pool around the rest of `load_model` is unaffected. Restoring from the pool keeps tensor addresses, so captured CUDA graphs stay valid.

**Unrelated, seen while testing:** exiting while the KV cache is still asleep (level-2 sleep, weights-only wake) intermittently logs `CUDA Error: invalid argument at csrc/cumem_allocator.cpp:249` on main too (also with LoRA), from freeing the asleep KV-cache allocation; on CUDA, `_python_free_callback` unmaps asleep allocations. The new test wakes the KV cache before exiting.
