# [CI] Enroll 6 jobs in automatic sharding: steps whose failures match main

[Upstream PR](https://github.com/vllm-project/vllm/pull/64606) · state: open · merged: False

## Original PR description

## Overview

Enrolls six jobs in `automatic_shard`: three steps that fail on main today, the PPL step, which passes on main again, and two AMD mirrors. Sharding these steps adds no failure: the PR build fails the same tests as main's latest nightly, with the same pass counts. The failures come from the tests themselves and are left to their owners. Part of the series that enrolls every remaining test step (#64590-#64599).

## Claims

| Job | Plan | PR build vs main nightly |
|---|---|---|
| `lm-eval-humming-b200-act` | 4 shards | 1 failed, 15 passed: the same `test_gsm8k_correctness[Qwen3-30B-A3B-MXFP4A16-humming-act-fp8]` failure as main |
| `fusion-e2e-config-sweep-b200` | 1 shard | 1 failed, 16 passed, 38 skipped: the same `test_tp1_fp4_mixed_precision_act_fusion` failure as main |
| its AMD mirror | 1 shard | passed, as on main |
| `dsv41-nvidia-kernels-4xb200` (renamed on main from `dsv41-nvidia-specialized-decode-4xb200`, now 4 commands) | 1 job: main has no passing run to time it | 2 failed, 88 passed: the same `test_engram_wkv_prefetch_matches_inline[False/True]` failures as main |
| `multi-modal-models-extended-ppl` | 1 shard | 10 passed, as on main |
| its AMD mirror | 1 shard | passed, as on main |

- Humming Activation's slowest shard finishes in a quarter of the step's current one-job wall time, at about the same machine time.
- One-shard plans run the same tests as on main, as one job, and split by themselves once their tests grow.

## Validation

- Planned each job with ci-infra main's planner against main's timings.
- The sharding harness (each shard's commands run against a mock test tree, as a PR build and as main with the OTel wrapper) shows every Humming Activation test runs exactly once.
- `split_check.py` finds no step whose jobs each run the whole suite.
- `/ci run` build 99620 and scoped build 99630 for the AMD mirrors, on the head before the rebase onto the renamed DeepSeek-V4.1 step; a new `/ci run` follows the rebase. Failed test IDs and pass counts compared against main's nightly build 99535.

## Details

- **The red jobs are main's failures.** Each one fails the same tests in main's nightly. The DeepSeek-V4.1 job stops after its second command (`test_kernels.py`) in a PR build, as it does on any PR build without sharding, because that command already fails on main.
- **Timeouts unchanged.** `timeout_in_minutes` stays per job. Fallback-aware timeouts belong in a central timeout setting.
