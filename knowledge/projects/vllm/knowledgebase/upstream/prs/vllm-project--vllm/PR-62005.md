# [Quantization] Report the resolved kernel per layer in model inspection

[Upstream PR](https://github.com/vllm-project/vllm/pull/62005) · state: open · merged: False

## Original PR description

## Overview

Model inspection now reports the quantization kernel or backend that was actually selected for each layer, instead of only the quant method class name. This implements the "log selected kernels/backends by layer type" item from the Q4 roadmap (#61024, SIG Quantization), which was requested in #52167.

Before:

```
QLinear(quant=Fp8Config, in_features=16, out_features=8)
```

After:

```
QLinear(quant=Fp8Config(kernel=CutlassFP8ScaledMMLinearKernel), in_features=16, out_features=8)
```

## Claims

- Each quantized layer reports its resolved kernel, or the backend enum name for MoE methods that record one.
- MoE layers now report a kernel at all. The load time log moved out of `create_model` to the end of `load_model`, after `process_weights_after_loading`. That step is where `moe_kernel` gets assigned, because it starts as `None` in `fused_moe/fused_moe_method_base.py:33`. Before this change every MoE layer printed no kernel while linear layers printed one, so the output was inconsistent.
- Works with the full set of kernel attribute names used across quant methods (`moe_kernel`, `fp8_linear`, `linear_kernel`, `ocp_mx_linear`, `kernel`, `experts_cls`), and with the compressed-tensors `module.scheme`. A kernel object is preferred over a backend enum, because the enum is set earlier and can go stale. `FusedMoEKernel` has no name of its own, so it prints as `FusedMoEKernel(experts=<ExpertsClass>)`.
- Unquantized layers, and inspection that runs before weights are processed, still report only `quant=<Name>`. Nothing is guessed.

## Validation

Tests, 31 total, all CPU only:

```
python -m pytest tests/model_executor/model_loader/test_model_inspection.py -q
31 passed
```

Pre-commit on the changed files passes, including `check-test-tethering`, `mypy`, `check-spdx-header` and `validate-config`.

Two of the new tests were confirmed to fail against the old code before the fix, so they do catch the bugs:

- load order: `assert [None] == ['MarlinMxFp4LinearKernel']`
- stale enum: `assert 'MARLIN' == 'MarlinMxFp4LinearKernel'`

Wider run over `tests/model_executor/` and `tests/config/` with and without the change gives the same failures and errors (125 failed, 70 errors both times, all pre-existing and caused by no network access and no GPU). The passed count goes from 1111 to 1142, which is the 31 new tests.

Not run: a real `vllm serve` with a quantized checkpoint. The machine used for this only has an ARM Mac, so there is no vLLM CPU build, no Triton and no GPU. The kernel attribute names were instead derived by scanning the quant method sources, and a test now does that scan automatically so the list cannot silently go stale. A run on real hardware would still be good to have.

## Details

Motivation is #52167, where 200lz asked for the resolved path per module, and fxmarty-amd agreed. This PR covers the kernel and backend stage of that. It does not cover the dequantizer or the checkpoint source.

Design decisions:

- The log call was moved rather than duplicated. `create_model` runs before the weights are processed, so it cannot see MoE kernels. It is also called on its own by the weight cache daemon, so that path now calls the log directly and keeps the old behaviour.
- The other entry point, `LLM.__repr__` through `WorkerBase.get_model_inspection()`, already runs after loading and did not need changes.
- The kernel attribute name is not the same in every quant method, so the code checks a fixed list of known names. If a method stores its kernel somewhere else it will not be reported until that name is added. `test_kernel_attributes_cover_every_selector_call_site` re-derives the list from the source and fails when a new name appears, so this should not go unnoticed.

Tradeoff and limitations:

- Kernel differences now split layers into separate groups in the inspection output, because `_get_child_signature` hashes the per module string. Output gets longer on mixed precision models. This is intended, but it does change existing inspection output.
- Selected kernel only. No dequantizer or checkpoint source information.
- Inspection still does not run on weight reload, only at load time.
- No accuracy evals. The change only formats attributes that already exist and moves one log call, so kernel selection and numerics are untouched.

Duplicate work check:

- Open PRs matching `model_inspection`, `VLLM_LOG_MODEL_INSPECTION` and `log_model_inspection`: none.
- The only open PRs that reference #52167 are #51808 and #53847, both unrelated to inspection output.
- #59460 by mgoin makes activation quantization fallbacks explicit and adds `VLLM_STRICT_QUANT_SCHEME`. It changes `quant_utils.py` and the kernel base classes, not `model_inspection.py`. That PR warns at selection time, this one reports the selection in the inspection output. They should compose through `executed_activation_key()`.
