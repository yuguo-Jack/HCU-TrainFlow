# [Quantization] OSCAR KV cache presets for the TurboQuant backend

[Upstream PR](https://github.com/vllm-project/vllm/pull/65354) · state: open · merged: False

## Original PR description



## Overview

Adds OSCAR KV-cache presets to the TurboQuant attention backend:
`--kv-cache-dtype turboquant_{k3v3,k3v2,k2v2}_oscar` store K/V as clipped 3- or
2-bit uniform codes (head_dim 256: 200 / 168 / 136 B per token per KV head, vs
262 B for `turboquant_4bit_nc`) and attend each request's most recent (and first)
tokens from an int8 copy. Related: #46774 (a different 2-bit design, WIP).

## Claims

- `turboquant_k3v3_oscar` matches `turboquant_4bit_nc` accuracy (Qwen3-4B GSM8K
  0.831 vs 0.824) with ~1.3x the bytes-per-token density.
- On a model where 2-bit keys hold up (Ternary-Bonsai-2-27B),
  `turboquant_k2v2_oscar` gives a 1.63x larger KV pool than `turboquant_4bit_nc`
  at the same memory, with long-context retrieval at 135–137/144 vs 141/144.
  2-bit keys are strongly model dependent (Qwen3-4B GSM8K collapses to 0.204);
  this is documented and the preset is opt-in.
- Decode attends quantized tokens without dequantizing them; decode kernel time
  is 0.6–1.1x of the `turboquant_4bit_nc` decode (1–16 rows, 0.5K–128K context)
  and end-to-end decode throughput is unchanged.
- CUDA graphs, chunked prefill (both continuation paths), prefix caching and
  `OffloadingConnector` work unchanged; no scheduler / model-runner / KV-manager
  changes.

## Details

Format (per head and token, rotated space, W = head_dim / 4):
`[low 2-bit plane: W B][high 1-bit plane: W/2 B, 3-bit only][scale fp16][min fp16]`
for K and for V. Store = Hadamard rotation (in-register FWHT) + clip at a per-row
|x| quantile + asymmetric uniform codes + a row-norm correction folded into
scale/min (all divisions round-to-nearest, so the kernel matches the reference).
Decode computes `score = scale * (q . code) + min * sum(q)` and
`sum p*v = (p*scale) . code + sum(p*min)` with four K=W tensor-core dots per tile;
the split count depends only on the batch size (CUDA-graph safe) and is chosen to
fill the GPU.

Recent window: the last `recent` tokens (1024 for the 2-bit-value presets, 256
for k3v3) and the first `sink` = 16 tokens of each request are attended from an
int8 copy. This is what brings the low-bit codes to `4bit_nc` accuracy
(attention-output error on Bonsai K/V for k2v2: 0.142 with a 256-token window,
0.097 with 1024). The copy lives in a staging table keyed by physical KV page
(`OscarWindow`, updated by the metadata builder with GPU-only ops); a staged token
is used only if its page still owns the row and a checksum of the quantized record
matches, so prefix-shared pages share it and block reuse / offload restore fall
back to the codes instead of reading stale values.

Integration: preset fields `oscar_recent` / `oscar_sink` on `TurboQuantConfig`;
the backend routes store / decode / continuation prefill to
`vllm/v1/attention/ops/oscar_kv.py` (~1000 lines incl. docs, isolated) and adds
~190 lines of hooks elsewhere.

Limitations / tradeoffs:
- head_dim 128 and 256 only (checked at init).
- The window copy is a fixed cost: `windows x (recent + sink) x layers x kv_heads
  x 2 x head_dim` bytes for up to 8 concurrent windows, capped at 10% of the free
  GPU memory at startup (allocated before the KV cache is sized, so it is
  accounted for). On a small GPU it can cancel the capacity gain (Qwen3-4B on a
  12 GB GPU: k3v2 pool = 4bit_nc pool).
- On hybrid models, a smaller attention page raises the block size chosen to
  match the Mamba/GDN page (Bonsai: 1584 -> 3056 tokens), so prefix-cache hits are
  coarser: a second question on the same 15K–46K-token document was 1.1 s slower
  on average (third and later questions unchanged).
- Clip quantiles were tuned on one model's K/V dumps.
