# [Rust Frontend] Make unhandled `vllm serve` frontend flags explicit

[Upstream PR](https://github.com/vllm-project/vllm/pull/62431) · state: open · merged: False

## Original PR description



## Overview

Python `vllm serve` reads `--custom-histogram-buckets`, `--enable-tower-connector-lora`, and `--enable-elastic-ep` in the frontend, but the Rust frontend did not declare them and dropped them without a warning. This PR makes them fail startup (`Unsupported`). It also accepts `--disable-fastapi-docs` as a no-op, since Rust serves no API docs routes.

## Claims

- `--custom-histogram-buckets`, `--enable-tower-connector-lora`, and `--enable-elastic-ep` now fail startup on both `vllm-rs serve` and the Python-supervised `--args-json` path, instead of being silently ignored by the frontend.
- `--disable-fastapi-docs` is accepted with a no-op warning instead of failing startup. The Rust frontend serves no OpenAPI, Swagger, or ReDoc endpoints, so it already behaves as if the flag were set.

With `rust/src/cmd/src/cli/unsupported.rs` reverted to `main`, both new tests fail.

## Details

**Where the code lives.** Argument recognition belongs to the CLI layer. The flags reuse the existing `Unsupported` / `Noop` markers in `rust/src/cmd/src/cli/unsupported.rs`, which already apply to both the `vllm-rs serve` (clap) and `--args-json` (serde) paths. No new mechanism is added.

**Why each flag is rejected rather than ignored.**

- `--custom-histogram-buckets` replaces the default buckets of the frontend Prometheus histograms ([`vllm/v1/metrics/loggers.py`](https://github.com/vllm-project/vllm/blob/852989f580820849113d67d13fd8053e279d0444/vllm/v1/metrics/loggers.py#L821)). The Rust histograms use fixed buckets, so the requested buckets were silently not applied.
- With `--enable-tower-connector-lora`, Python's `InputProcessor` prefixes the multimodal hash with the LoRA name so encoder-cache entries do not collide across adapters ([`vllm/v1/engine/input_processor.py`](https://github.com/vllm-project/vllm/blob/852989f580820849113d67d13fd8053e279d0444/vllm/v1/engine/input_processor.py#L297-L311)). Rust always sends the bare hash, so with the flag on, the engine could reuse encoder outputs computed under a different adapter.
- With `--enable-elastic-ep`, Python's core client hands engine input sockets over during scaling ([`vllm/v1/engine/core_client.py`](https://github.com/vllm-project/vllm/blob/852989f580820849113d67d13fd8053e279d0444/vllm/v1/engine/core_client.py#L637)) and the API server exposes the scaling routes. The Rust frontend has neither, so it could not follow a scale event that the engine went through.

**`--structured-outputs-config`.** An earlier revision forwarded it to the managed engine. vllm-project/vllm#62456 parses it in the Rust frontend (it selects the structured-outputs backend) and forwards it itself, so this PR reverts that part and leaves the flag untouched.

**Behavior changes for existing users.**

- `--disable-fastapi-docs` now starts instead of failing.
- The three new `Unsupported` flags were either not honored by the Rust frontend before or could produce wrong results with it.

**Not a duplicate.** Searching open PRs for each flag finds no PR that changes how the Rust frontend handles them. vllm-project/vllm#50698 (inactive since 2026-10-02) adds a supervisor-side control channel for elastic EP scaling but does not touch `--enable-elastic-ep` handling in the Rust CLI. vllm-project/vllm#50101 edits the neighboring `stream_interval` entry in `unsupported.rs`, a different flag.
