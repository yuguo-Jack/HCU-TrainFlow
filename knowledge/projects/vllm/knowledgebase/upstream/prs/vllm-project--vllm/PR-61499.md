# [Bugfix][NIXL] Report failed pulls per request with several KV cache groups

[Upstream PR](https://github.com/vllm-project/vllm/pull/61499) · state: open · merged: False

## Original PR description



## Overview

On a model with several KV cache groups whose transfer groups are all full attention, one failed NIXL KV pull stops the decode engine. HiSparse decode is such a model: it adds KV cache groups that take no part in the transfer (`enable_kv_transfer=False`). The worker reports the failed request's block IDs in `invalid_block_ids`, and `Scheduler._handle_invalid_blocks` raises for any model with more than one KV cache group. This reports those failures through `failed_recving` only, so the request fails (or is recomputed) and the engine keeps serving.

Related: #53779 (transfer groups), #53781 (HiSparse host-resident groups), #52232 (HMA receive failures).

## Claims

- With more than one KV cache group, a failed pull is reported only in `failed_recving`. `invalid_block_ids` stays empty, so the scheduler no longer raises, and the request ends as `FINISHED_ERROR` (or is recomputed under `kv_load_failure_policy: recompute`).
- With one KV cache group nothing changes: the request's block IDs are still reported.
- HMA layouts are unchanged; they already skip `invalid_block_ids`.

## Validation

**Unit, CPU.** `test_transfer_setup_failure_returns_finished` gains a case with a second KV cache group outside the transfer, the shape HiSparse adds. On main the new case fails with `assert {7, 8, 9} == set()`: the block IDs the scheduler then rejects. With this change it passes.

**Production, GLM-5.3 on H100.** P/D with NIXL 1.5.0, decode TP8 with HiSparse, vLLM main `d6aca837c3` plus three unrelated PRs. On 2026-10-13, 15 decode engines died in 4 hours, each with `RuntimeError: A KV connector reported block-level load failures (invalid_block_ids) which is not supported for models with multiple KV cache groups` right after a pull failed with `NIXL_ERR_REMOTE_DISCONNECT`. The condition in this change has run as a startup patch on every decode engine started after 15:56 UTC, all 36 by 20:15 UTC. None has died this way since. Two engines of one decode group failed 101 requests on pulls from two prefill workers between 18:46 and 19:33 UTC and kept serving. Why those connections fail is a separate issue; #61500 recovers from it.

## Details

Path of the failure, decode side:

1. The scheduler admits a request with remote KV and allocates blocks in every KV cache group, including the HiSparse groups outside the transfer.
2. `NixlConnectorWorker.start_load_kv` posts the read for the transfer groups. The read fails (`NIXL_ERR_REMOTE_DISCONNECT`, or `transfer_setup_failed`).
3. `get_transfer_results` lists the request in `failed_recving`. Because `_is_hma_required` is derived from the transfer groups only (all full attention here), it also puts the request's group-0 block IDs in `_invalid_block_ids`.
4. `Scheduler.update_from_output` handles `failed_recving` (`_handle_failed_recving`), then `invalid_block_ids`. `_handle_invalid_blocks` raises because `kv_cache_groups` has more than one group, and the engine core dies.

The change gates step 3 on `len(kv_cache_config.kv_cache_groups) == 1`, the same group set and condition the scheduler checks. Step 4 then only sees `failed_recving`.

Not a duplicate. Open PRs found with `gh pr list --repo vllm-project/vllm --state open --search` for "invalid_block_ids", "failed_recving", "nixl hma failed transfer" and "kv load failure hybrid":

- #52232 propagates HMA receive failures per request. It keys on `_is_hma_required`, which is false in this case, and has merge conflicts with main, which has since gained `failed_recving`.
- #54733, #48216, #50742, #45497 and #56135 make the scheduler recover failed block loads for hybrid models. Each would let the scheduler accept these block IDs in some form. This change keeps the NIXL worker within the scheduler's current contract and does not depend on them.
