# Add per-request KV load wait and pure queue time metrics

[Upstream PR](https://github.com/vllm-project/vllm/pull/62685) · state: open · merged: False

## Original PR description

## Overview

Adds per-request remote KV load wait observability for PD-disaggregated deployments: two new engine-core events (`KV_LOAD_STARTED` / `KV_LOAD_FINISHED`) recorded around the `WAITING_FOR_REMOTE_KVS` window, two new Prometheus histograms (`vllm:request_kv_wait_time_seconds`, `vllm:request_pure_queue_time_seconds`), and a `kv_role`-gated structured `REQ_STAGE_METRIC` log record per finished request on P/D instances.

Related: #53198 (draft) measures a similar window; see Details for the comparison.

## Claims

- On a decode instance, `vllm:request_queue_time_seconds` is dominated by the remote KV load wait, so it cannot distinguish "slow KV transfer" from "slow scheduling". This PR splits the two:
  - `vllm:request_kv_wait_time_seconds`: time spent in the `WAITING_FOR_REMOTE_KVS` window, measured in the scheduler and therefore **connector-agnostic** (works for NIXL, Mooncake, SharedStorage, ...).
  - `vllm:request_pure_queue_time_seconds`: queue time excluding that wait.
- Adds a per-request `REQ_STAGE_METRIC` log record gated on `kv_role` (producer: queue/prefill; consumer: kv-transfer/pure-queue/inference) for deployments that read engine logs directly instead of scraping Prometheus.

## Validation

Validated end-to-end on a single-node PD-disaggregated deployment (8x Ascend 910B, vLLM-Ascend plugin with MooncakeConnectorV1, DeepSeek-class MoE model, TP=4 prefill + TP=4 decode behind a PD router):

1. Healthy path: `kv_transfer_s` from the new log record matches the connector-level transfer time and the operator-level measurement (`hixlOpBatchRead` in the Ascend PyTorch profiler) within expected Python-side overhead; `d_waiting_s` stays in the millisecond range.
2. Degraded path (device with a link-down RoCE panel port in the deployment): `kv_transfer_s` reports ~20 s (two 10 s connect timeouts plus PCIe fallback) while `d_waiting_s` stays low — cleanly separating transfer stalls from scheduler queuing. With only `vllm:request_queue_time_seconds` the two were indistinguishable.

Example records from the two cases:

```
REQ_STAGE_METRIC request_id=chatcmpl-xxxx kv_transfer_s=0.021 d_waiting_s=0.003 d_running_s=0.180 ts_ms=...
REQ_STAGE_METRIC request_id=chatcmpl-yyyy kv_transfer_s=20.380 d_waiting_s=0.004 d_running_s=0.177 ts_ms=...
```

No new unit tests: the change is additive bookkeeping behind `if self.log_stats:`; validated on hardware instead.

## Details

Decode-instance request flow (numbers mark where the new timestamps are taken):

1. request arrives -> `QUEUED` event
2. scheduler admits it for async KV load -> `KV_LOAD_STARTED` (new)
3. connector pulls remote KV (any KVConnectorV1 implementation)
4. `finished_recving` arrives -> `KV_LOAD_FINISHED` (new)
5. request becomes runnable -> `SCHEDULED` event
6. decode runs to completion -> finished-request stats emitted

Design notes:

- Measurement lives in the scheduler around the `WAITING_FOR_REMOTE_KVS` window; no connector code is touched, so every KVConnectorV1 implementation gets the metric for free.
- Both timestamps keep only the first event (`== 0.0` guard), mirroring the existing QUEUED/SCHEDULED handling.
- The log record is gated on `kv_role`: it only fires on PD instances. Non-PD deployments see no change apart from two extra histograms that observe 0.
- Diff is +87 lines, mostly histogram registration boilerplate and the two event arms.

Comparison with #53198 ("Expose per-request remote KV wait time", draft): that PR measures the wait inside the NIXL connector and surfaces `remote_kv_wait_time_ms` through the generate API response / Rust client. This PR is intended as complementary rather than duplicate: (a) connector-agnostic scheduler-level events (Mooncake, SharedStorage, ...), (b) Prometheus histograms for existing scraping setups, (c) the queue-time split (`pure_queue_time`), and (d) the producer-side view. Happy to align on a single design if maintainers prefer — opened as draft to discuss.
