# [Bugfix][XPU] Fail loudly instead of no-op NCCL weight transfer

[Upstream PR](https://github.com/vllm-project/vllm/pull/57022) · state: open · merged: False

## Original PR description

## Purpose

On a non-CUDA accelerator, an NCCL weight-transfer round can report complete success
while moving zero bytes: every route answers 200, the trainer sees no error, and the
workers keep serving the weights they already had. An RL run then trains against a
frozen policy with nothing in any log to say so.

Two things combine to produce that, and this PR fixes both. **Neither changes behavior
on CUDA or ROCm.**

1. `packed_tensor.py` builds and enters CUDA streams unconditionally
   (`torch.cuda.Stream`, `torch.cuda.stream`). Off CUDA that raises `RuntimeError:
   torch.cuda.Stream requires CUDA support` *mid-update* — after `start_weight_update`
   → `initialize_layerwise_reload` → `restore_layer_on_meta` has already moved the
   worker's params to the meta device, so the engine is unusable afterwards
   (`reshape_and_cache_flash ... with Meta tensors` on the next generation), and the
   error names streams rather than the actual problem. Routing both call sites through
   `current_platform` resolves to the accelerator's own stream API. On CUDA,
   `current_platform.Stream` *is* `torch.cuda.Stream` — `Platform.__getattr__` looks up
   `getattr(torch, self.device_type)` — so the CUDA path gets the same objects it had.

2. With streams fixed the rendezvous is reached, and `PyNcclCommunicator` **soft-disables
   itself** (`available=False, disabled=True`) when the NCCL library will not load; every
   collective then early-returns. Degrading to a no-op is a reasonable default for the
   inference collectives that behavior was written for, but for weight transfer a no-op
   broadcast is silently stale weights. So reject a disabled communicator at rendezvous,
   in both `stateless_init_process_group` and `uid_init_process_group` (covering trainer
   and worker, dense and sparse).

   That guard is **scoped to non-cuda-alike platforms** — it returns early when
   `current_platform.is_cuda_alike()`. On CUDA and ROCm a disabled communicator means
   `world_size == 1` or `VLLM_DISABLE_PYNCCL`, both long-standing behavior, and leaving
   them alone keeps this a platform fix rather than a semantics change for existing
   users. The cost is that the same silent no-op stays reachable on CUDA through those
   two settings; I am happy to widen the guard if maintainers would rather fix that too,
   but it is deliberately out of scope here.

**Why one commit and not two.** Fix 1 alone is a regression: it removes the
`RuntimeError` that was accidentally acting as a safety net, turning a loud (if
misleading) mid-update failure into the silent frozen-policy run above. Fix 2 is what
closes that window. They are only safe together.

The `cuda-ipc` call sites in the same file (`current_stream().synchronize()`,
`get_device_properties().uuid`) are deliberately left CUDA-only: cuda-IPC has no meaning
elsewhere.

## Test Plan

```bash
pytest tests/distributed/test_weight_transfer_nccl_uid.py

pre-commit run --files vllm/distributed/weight_transfer/nccl_common.py \
  vllm/distributed/weight_transfer/packed_tensor.py
```

No test is added, on purpose: CI runs on CUDA, where the new guard returns early by
design, so a test would have to fake the platform to reach it at all. Happy to add one
if you want that coverage.

## Test Result

- End-to-end, before this change, on 2× Intel Arc Pro B70 with an RL trainer driving
  `/init_weight_transfer_engine` → `/start_weight_update` → `/update_weights`: every
  route 200, run exits 0 in ~20 s, and the metrics show nothing moved —
  `importance_sampling_ratio` mean/min/max all `0`, `sampling_logp_difference` ≈ `1.0`
  (≈ `0.015` on a run that does transfer), `clipped_ratio` `1`, loss and `grad_norm` `0`.
  After this change the rendezvous raises and names the reason, on both ranks.
- `tests/distributed/test_weight_transfer_nccl_uid.py`: 14 passed in a vLLM environment
  on that 2-card Arc Pro B70 machine; this PR does not touch the file.
- `pre-commit`: all applicable hooks pass, including `Prevent new 'torch.cuda' APIs
  call` and mypy.
- Checked the guard is inert on cuda-alike: with `is_cuda_alike()` forced to `True`,
  `_require_usable_communicator` hands back even a `disabled=True, available=False`
  communicator untouched; off CUDA both rendezvous helpers raise.
