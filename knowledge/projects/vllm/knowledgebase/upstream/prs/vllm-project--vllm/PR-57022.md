# [Bugfix] Fail loudly instead of no-op NCCL weight transfer

[Upstream PR](https://github.com/vllm-project/vllm/pull/57022) · state: closed · merged: True

## Original PR description

## Purpose

An NCCL weight-transfer round can report success while moving zero bytes. `PyNcclCommunicator` disables itself (`disabled=True`) when the NCCL library won't load (e.g. on XPU) or when `VLLM_DISABLE_PYNCCL=1`, and every collective then returns early. The workers keep their old weights, and an RL run trains against a frozen policy with nothing in any log.

This PR rejects a disabled communicator at rendezvous, in `stateless_init_process_group` and `uid_init_process_group` (trainer and worker, dense and sparse), on every platform. A weight-transfer group always has `world_size >= 2`, so on CUDA it only fires with `VLLM_DISABLE_PYNCCL=1` or a missing libnccl, which is the same bug.

## Test Plan

```bash
pytest tests/distributed/test_weight_transfer.py -k disabled_communicator
pre-commit run --files vllm/distributed/weight_transfer/nccl_common.py tests/distributed/test_weight_transfer.py
```

## Test Result

- New test passes; it fails with the check removed.
- 2x Intel Arc Pro B70, RL trainer driving `/init_weight_transfer_engine` -> `/start_weight_update` -> `/update_weights`: before, every route returns 200 and nothing moves (`importance_sampling_ratio` 0, loss and `grad_norm` 0). After, the rendezvous raises on both ranks.

The code was co-developed with Claude Code.

- xuechendi · comment · 2026-10-28T16:40:48Z · [source](https://github.com/vllm-project/vllm/pull/57022#issuecomment-6474902220)

Thanks, I checked this on 2x Arc Pro B60 (vllm-openai-xpu v0.32.0 with this PR's two files): before the change, a 2-rank `stateless_init_process_group` on xpu returns a `disabled=True` communicator on both ranks (a silent no-op); with the PR, both ranks raise the new RuntimeError at rendezvous, before params go to meta. `current_platform.Stream`/`.stream` gives working XPU streams. LGTM in direction, a few suggestions:

1. `nccl_common.py:181`: I'd drop the `is_cuda_alike()` gate. A weight-transfer group always has world_size >= 2, so on CUDA `disabled=True` only comes from `VLLM_DISABLE_PYNCCL=1` or a missing libnccl, which is the same silent stale-weights bug. Checking unconditionally is simpler (it also covers @aoshen02's "simplify"), and `disabled`/`available` are always set together, so `if comm.disabled:` is enough.
2. With the check unconditional, a small unit test (`VLLM_DISABLE_PYNCCL=1` or a monkeypatched communicator -> `stateless_init_process_group` raises) runs in CUDA CI without faking the platform.
3. `nccl_engine.py:237` and `:419` still use `torch.cuda.current_stream()`. On in-tree XPU the new check fires first, so the stream change only matters for a non-CUDA platform whose PyNccl loads, and that platform would still fail there. Could you switch those to `current_platform.current_stream()` too, or drop the stream change and keep just the check?
4. Nit: shorter message, e.g. "PyNccl communicator is disabled on {device_type}; NCCL weight transfer would be a no-op."
