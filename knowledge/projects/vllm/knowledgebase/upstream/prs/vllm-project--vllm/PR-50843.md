# [Bugfix] Bound tile-local argmax to vocab_size in samplers

[Upstream PR](https://github.com/vllm-project/vllm/pull/50843) · state: open · merged: False

## Original PR description

## Summary

The sampling kernels reduce over a `BLOCK_SIZE`-wide tile of the logits row and
form the token id as `block_idx * BLOCK_SIZE + idx`. The out-of-vocab tail lanes
of the last tile are loaded as `-inf`, so when every in-vocab lane of that tile
is also `-inf`, the reduction can settle on a tail lane and emit
`token_id >= vocab_size`.

Nothing downstream bounds a sampled token id.

Three sites share the pattern:

| Site | Path |
|---|---|
| `vllm/v1/worker/gpu/sample/gumbel.py` | non-greedy sampling |
| `vllm/v1/worker/gpu/spec_decode/rejection_sampler_utils.py` (`_compute_local_logits_stats_kernel`) | greedy |
| `vllm/v1/worker/gpu/spec_decode/rejection_sampler_utils.py` (resample) | recovered-token resampling |

## Impact

On most models the bad id is absorbed by `VocabParallelEmbedding`, which masks
out-of-range ids to a zero embedding — so it degrades silently into a garbage
output token rather than failing loudly.

On DeepSeek-V4 it is fatal. The hash-MoE router indexes
`tid2eid[token_id * topk]` directly; an out-of-vocab id reads past the
`[vocab_size, topk]` table and the resulting garbage expert id faults the
context on **every** rank with a Warp MMU fault.

## Evidence

Reproduced in production on DeepSeek-V4-Flash (TP2, expert parallelism,
speculative decoding) under bursty concurrency, in 90 s – 5.5 min.

`vocab_size` is 129280, which is not a multiple of the 8192 tile, so the last
tile has 1792 masked lanes. The emitted id was exactly

    15 * 8192 + 6400 == 129280

i.e. the first out-of-vocab lane of the last tile. A check on `input_ids` right
after `combine_sampled_and_draft_tokens` reported this on real scheduled rows
(not cudagraph padding) at ~78 occurrences/minute; after the fix, 0 over a
40-minute run at the same load.

**What I could not reproduce synthetically.** I have not built a minimal input
that makes the argmax select a tail lane. Feeding a fully `-inf` row, or a fully
NaN row, does not do it (they select lane 0 and the last lane of tile 0
respectively). So the exact condition that steers `idx` onto the first
out-of-vocab lane is not established, and I would rather say so than invent a
mechanism.

What is established is the causal link, via a clean A/B under identical
production load:

| Clamped sites | out-of-range `input_ids` |
|---|---|
| none | ~78/min |
| `gumbel.py` only | 4 over ~15 min |
| all three | **0 over 30 min** (1322 requests) |

The middle row is what identified the greedy rejection-sampler site as the
active path.

## Fix

Clamp the tile-local argmax to `vocab_size - 1`. In a fully `-inf` tile no
in-vocab lane is a valid answer anyway, so any index is equally arbitrary — the
clamp only guarantees the result is addressable.

## Test

No unit test: as noted above I could not construct a synthetic input that
reproduces the tail-lane selection, and I did not want to ship a test that passes
with and without the fix. Validation is the end-to-end A/B table above, plus a
30-minute randomized-concurrency run with zero faults where the same load
previously killed the engine in 90 s - 5.5 min.

If a reviewer knows the condition that steers the tile argmax off the end, I am
happy to add a focused test for it.

The producer-side bound is a reasonable safety guard and the production A/B evidence is valuable, but this can have a focused regression test despite the current test setup not reproducing it.

The PR notes that an all-NaN row selects the last lane of tile 0. Existing coverage uses `vocab_size=20000`, so that index (`8191`) is still globally in range and the test cannot expose this bug. Use a vocabulary smaller than `BLOCK_SIZE` (for example 999 or 1000) with an all-NaN row: before this patch, the tile-0 argmax can yield 8191; after the patch, every emitted ID must satisfy `0 <= token_id < vocab_size`. Please add this old-code-fails regression for the Gumbel path and the relevant greedy/resample rejection-sampler paths (covering the applicable temperature modes), then run the focused GPU suite/upstream CI.

The test and code comments should also state the precise contract: this patch guarantees an addressable in-vocabulary fallback for a degenerate non-finite tile; it does not define which token is semantically correct or fix the source of NaN/all-`-inf` logits. With that bounded contract and regression coverage, the clamp itself looks acceptable.

## Production data point: the in-range channel is the one that hurts silently (8×B300 Kimi-K3, TP8)

Took this alongside #50183 in production and want to flag why this PR matters **independently**, since the two get bundled easily.

### The distinction we hit

#50183's out-of-bounds argmax read produces *wildly* out-of-range token ids — they crash loudly (`indexSelectSmallIndex` assert, or an Xid 13 in an unbounded penalties deref) and you find them.

This PR's channel produces **in-range** wrong ids: a tile whose in-vocab lanes are all `-inf`/NaN settles on an out-of-vocab tail lane, and the emitted `token_id` is *plausible*. Nothing downstream distinguishes that from a real token, so it does not crash — it just puts a wrong token in the output.

We tried to defend the consumer first, and that experience is the argument for this PR: we added a bounds check where the sampled token is used (`last_sampled_tokens`), which does stop the crashes. It **cannot** stop this channel, because a valid-looking id passes any consumer bound by construction. The clamp has to be at the producer, which is what this PR does.

There is a related sharp edge worth knowing: the consumer gather truncates the int64 index to u32 *before* its bounds check, so garbage whose low 32 bits land under `vocab_size` also passes the assert and silently gathers the wrong embedding row. In our instrumentation, poison incidence **exceeded** crash incidence — i.e. the quiet failures outnumbered the loud ones.

### Environment / rollout

8×B300, TP8, fp8 KV, `--mamba-cache-mode align`, DSpark spec-decode (`num_speculative_tokens=7`), prefix caching on. Cherry-picked this PR together with #50183 onto a frozen K3 base (`d20260727`) — both applied cleanly as overlays — and rolled across a 3-box pool under live traffic. Crashes stopped (details and the discriminating A/B are in my comment on #50183); the silent-corruption side is by nature not directly observable, which is exactly why we wanted this hunk in.

Also relevant: #51039 reports NaN logits on Kimi-K3 after long-context prefill, which would be a live source of the all-`-inf`/NaN tiles this PR guards.
