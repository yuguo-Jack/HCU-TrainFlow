# [Bugfix][Distributed] Fall back from FlashInfer PCIe IPC all-reduce without peer access

## Overview

`VLLM_ALLREDUCE_USE_FLASHINFER_PCIE_IPC=1` aborts engine startup on multi-GPU hosts without full CUDA peer access (no P2P between GPUs, or P2P only within PCIe-switch pairs). This adds the missing peer-access check so the backend falls back like its other unsupported cases. Context: #60762 (discussion with @Lei-010 and @xzwgit), #59203.

## Claims

- On hosts without full peer access (no P2P, or P2P only within PCIe-switch pairs), `FlashInferPcieIpcAllReduce` now disables itself with a `warning_once` and dispatch falls through to the next all-reduce backend, instead of `PcieIpcAllReduceWorkspace` raising `CUDART error: peer access is not supported between these two devices` and taking the engine down.
- Hosts with full peer access are unaffected: `FLASHINFER_PCIE_IPC` stays the primary backend.
- The decision is agreed across ranks before any IPC allocation, so ranks cannot diverge.

## Details

- **Root cause:** `FlashInferPcieIpcAllReduce.__init__` already falls back (`warning_once`) for a missing FlashInfer workspace, non-CUDA, unsupported world size, multi-node TP, and later for dtype / capture sizes / DBO, but never checked peer access. The IPC workspace maps every peer's buffer, so on a partial-P2P topology it fails at construction during kernel warmup.
- **History / scope:** not previously reported; present since the backend was introduced in #53576 (v0.30.0). Affects any model when the opt-in env var is set on a multi-GPU host without full peer access, e.g. hosts without P2P or with P2P only within PCIe-switch pairs (see Validation). Default deployments (env var unset) are unaffected. cc @lucifer1004 (author of #53576).
- **Fix:** reuse `CustomAllreduce`'s existing helpers, `_can_p2p` (cached `gpu_p2p_access_check`, honours `VLLM_SKIP_P2P_CHECK`) and `_all_ranks_true` (MIN all-reduce on the CPU group), so the two PCIe backends make the same decision the same way. +13 lines, no new abstractions.
- **Unrelated, observed while testing:** on 4× RTX PRO 4500 with full P2P the IPC backend is kept (correct), but startup then stalls in FlashInfer's `pcie_ipc_all_reduce` autotuning for >20 min — identically with and without this change, while IPC off boots in ~4.5 min. Out of scope here; likely the cold-start autotune cost discussed in flashinfer-ai/flashinfer#5898.
- **Limitation:** like `CustomAllreduce`, it assumes TP rank == local device index on a single node (already required by the existing same-node check).

AI assistance was used to write the code, tests and this description; I reviewed every changed line and ran the tests and hardware validation above. Not a duplicate: no open PR touches `flashinfer_pcie_ipc_all_reduce.py`; #47544 applies the same pattern to a different backend.
