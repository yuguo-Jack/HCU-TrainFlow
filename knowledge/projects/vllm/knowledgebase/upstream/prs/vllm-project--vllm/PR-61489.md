# [Docs] Point users at --no-enable-flashinfer-autotune

[Upstream PR](https://github.com/vllm-project/vllm/pull/61489) · state: open · merged: False

## Original PR description

## Overview

`--no-enable-flashinfer-autotune` has been a top-level flag since #34006, but most docs, tests and eval configs show `--kernel-config '{"enable_flashinfer_autotune": false}'`, so that is what people copy. This makes the short flag the one people find.

## Claims

- Help text for `--enable-flashinfer-autotune` now says what autotuning does, that it is on by default except at `-O0`, and that disabling it speeds up startup.
- The autotune startup log line mentions `--no-enable-flashinfer-autotune`.
- `docs/design/optimization_levels.md` uses the short flag in the `-O0`/`-O1` settings and in the "Startup Time Too Long" troubleshooting entry.
- Tests, the Humming GSM8K eval configs and the ReplaySSM benchmark use `enable_flashinfer_autotune=False` / `--no-enable-flashinfer-autotune` instead of the `kernel_config` form.
- No behaviour change.

## Validation

- `pre-commit run` on the changed files passes.
- `chg run -g=1 -- .venv/bin/python -m pytest tests/compile/fusions_e2e/test_tp1_quant.py -x` on a B300: 63 passed, 0 failed through 79% of the file, then my 45-minute GPU reservation timed out. The remainder was not run.
- Not run locally: `tests/compile/fusions_e2e/test_tp2_ar_rms.py`, the two `test_sharded_sampling.py` files, and the GSM8K Humming evals.

## Details

`EngineArgs.create_engine_config` copies the top-level `enable_flashinfer_autotune` into `KernelConfig`, so the two spellings are equivalent. In the `fusions_e2e` tests, dropping the explicit `kernel_config` dict lets the conftest default `{"enable_jit_warmup": True}` apply, which matches what the dict form produced before.

`tests/models/multimodal/pooling/test_colpali.py` is intentionally left on the `kernel_config` form: it goes through `VllmRunner`, whose default `kernel_config` disables JIT warmup, so switching it would change that test's behaviour.

Not a duplicate: searched open PRs for `flashinfer autotune` and `enable-flashinfer-autotune docs`; the open autotune PRs (#59698, #55671, #61403 and others) change autotune behaviour, not how the flag is documented. Related: #61479 adds `--disable-x` as an alias for `--no-enable-x`.
