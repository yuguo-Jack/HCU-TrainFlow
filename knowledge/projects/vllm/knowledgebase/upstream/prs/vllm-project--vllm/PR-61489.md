# [Docs] Point users at --disable-flashinfer-autotune

[Upstream PR](https://github.com/vllm-project/vllm/pull/61489) · state: closed · merged: True

## Original PR description

## Overview

Since #61479, `--disable-flashinfer-autotune` is the advertised way to turn off FlashInfer autotuning. Docs, recipes, tests and eval configs still mostly show `--no-enable-flashinfer-autotune` or `--kernel-config '{"enable_flashinfer_autotune": false}'`, so that is what people copy. This switches them to the advertised flag.

## Claims

- **Help text:** `--enable-flashinfer-autotune, --disable-flashinfer-autotune` now says what autotuning does, that it is on by default except at `-O0`, and that disabling it speeds up startup.
- **Startup logs:** both autotune cache log lines (managed v2 cache and per-rank cache file) mention `--disable-flashinfer-autotune`.
- **Docs:** `docs/design/optimization_levels.md` uses the CLI flags in the `-O0`/`-O1` settings and mentions `--disable-flashinfer-autotune` under "Startup Time Too Long".
- **Recipes and eval configs:** model recipes (DeepSeek, Kimi-K3, MiniMax-M3, GLM-5.3, Inkling) and GSM8K eval configs use `--disable-flashinfer-autotune` instead of `--no-enable-flashinfer-autotune` / `--kernel-config.enable_flashinfer_autotune=False`.
- **Python tests and benchmarks:** these use the top-level `enable_flashinfer_autotune=False` kwarg instead of `kernel_config={...}`.
- **No behaviour change:** the old spellings still parse.

## Validation

- `pre-commit run` on the changed files passes.
- On the rebased branch:

  | serve args | `enable_flashinfer_autotune` |
  | --- | --- |
  | `--disable-flashinfer-autotune` | `False` |
  | `--no-enable-flashinfer-autotune` | `False` |
  | `--enable-flashinfer-autotune` | `True` |

  `vllm serve --help=flashinfer-autotune` shows the new help text.
- Before the rebase, `tests/compile/fusions_e2e/test_tp1_quant.py -x` on a B300 had 63 passed and 0 failed through 79% of the file, then my 45-minute GPU reservation timed out. Those test edits are unchanged by the rebase.
- Not run locally: `tests/compile/fusions_e2e/test_tp2_ar_rms.py`, the two `test_sharded_sampling.py` files, `tests/models/kimi_k3/test_prefix_cache.py`, the GSM8K evals and the recipes. Their only change is the flag spelling, and both spellings parse identically.

## Details

`EngineArgs.create_engine_config` copies the top-level `enable_flashinfer_autotune` into `KernelConfig`, so all spellings are equivalent. In the `fusions_e2e` tests, dropping the explicit `kernel_config` dict lets the conftest default `{"enable_jit_warmup": True}` apply, which matches what the dict form produced before.

`tests/models/multimodal/pooling/test_colpali.py` keeps the `kernel_config` form on purpose. It goes through `VllmRunner`, whose default `kernel_config` disables JIT warmup, so switching it would change the test's behaviour.

Other `--no-` spellings in recipes, such as `--no-disable-hybrid-kv-cache-manager`, are out of scope here.

On making autotune off by default (raised in review): I'd keep it on. Autotuning picks noticeably faster kernels, and the aim is to make it cheap enough that people rarely need to turn it off.

Not a duplicate: searched open PRs for `flashinfer autotune` and `enable-flashinfer-autotune docs`. The open autotune PRs (#59698, #61403 and others) change autotune behaviour, not how the flag is documented. Follow-up to #61479.
