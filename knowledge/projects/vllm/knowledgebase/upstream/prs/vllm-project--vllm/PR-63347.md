# [Core] Grow padded full attention blocks

[Upstream PR](https://github.com/vllm-project/vllm/pull/63347) · state: open · merged: False

## Original PR description



## Overview

Grow the block of padded full attention layers so they fill the unified KV page instead of leaving much of it empty. Fixes #40388.

## Claims

- More KV cache capacity for hybrid models whose full attention page is padded, with `fp8_per_token_head`: Gemma-4-26B +15.8%, Qwen3.6-35B + DFlash +15.6%, Gemma-4-31B + DFlash (TP2) +16.0%.
- Never reserves more KV memory than before: the page, block strides and pool block count are unchanged, and blocks only grow.
- Same outputs in CUDA graph mode: prompt logprobs are identical before and after.
- No throughput regression.
- Models without a padded full attention page are unchanged, including every tested model with plain fp8.

## Details

**Root cause.** In hybrid models all layers share one KV block pool, so `unify_kv_cache_spec_page_size` gives every layer the same physical page. A layer whose page does not divide the largest one keeps its block size and pads its page up. The padding repeats on every block, and for full attention it grows with the context length. It shows up whenever per-token sizes stop being integer multiples of each other, e.g. per-token-head KV scales, head dims that are not powers of two, or a drafter with a different head layout. Gemma-4 with `fp8_per_token_head` leaves about half of every full attention page empty.

**Change.** The page stays as is, and padded full attention layers grow their block to the largest multiple that still fits. For Gemma-4, full attention goes from block 16 to 32 and the padding per page drops from 33,536 B to 512 B, the block structure plain fp8 already uses. The existing loop only records which layers it padded; `_grown_block_sizes` then adjusts those. This follows the sliding window block choice in `attention.py` and the hidden-state block choice, applied to padded full attention.

**Everything else stays as before: the stored KV values, the page layout and every other layer are unchanged, and models without a padded full attention page take the existing path.**

**Rules.**
- Only plain `FullAttentionSpec` grows. Other specs, including full attention subclasses, may tie their block size to a model constant (e.g. Inkling's conv state, static sinks).
- A padded page cannot be split into kernel blocks, so a grown block must run as one kernel block.
- The scheduler block (lcm of group block sizes) may grow only up to the larger of the largest chosen block and its value without growth, so block sizes stay multiples of each other. With several grown specs the combination is chosen jointly: Gemma-4-31B + DFlash picks (32, 32) instead of (32, 48), whose lcm would be 96.
- The result depends only on the KV cache specs, so prefill and decode instances with the same parallel layout agree on the layout.

**Alternatives.** Growing the page and padding sliding window layers instead can save more in some configurations, but which choice is cheaper depends on `max_model_len` and batch settings. Those often differ between prefill and decode instances, and KV connectors need both sides to use the same layout, so the page stays fixed.

**Limitations.**
- OffloadingConnector with `block_size` in `kv_connector_extra_config` requires all groups to share one block size, so it now fails for padded hybrids such as Gemma-4 pth, as plain fp8 already does. `blocks_per_chunk` works.
- Prefix cache hits align to the scheduler block, which can grow (Gemma-4: 16 → 32). Plain fp8 already uses the same block structure.
- Sliding window layers are not grown, so models where a sliding window page is the padded one see no change.

- KaloyanNaumov · comment · 2026-10-31T20:27:14Z · [source](https://github.com/vllm-project/vllm/pull/63347#issuecomment-6548720765)

Another case this covers, from Intel XPU (Arc Pro B70): Qwen3.6-35B-A3B + DFlash (K=7) with `int8_per_token_head` KV on TRITON_ATTN. The target's full-attention layers (2 KV heads × 520 B per token) end up at block 2176, set by the GDN page, while the drafter's full-attention page (8 heads × 264 B) is 4,595,712 B. The ratio is 2.03, so on main each target page is padded to the drafter's and 49% of every target block is padding.

We have been running an equivalent local change (take the integer multiple of the block that fits, then pad). It moves the target block 2176 → 4352, which leaves 1.5% padding. Walking `_grown_block_sizes` by hand for these specs gives the same 4352: candidates (4352, 2176) for the target, both drafter specs stay at 2176, and the lcm stays at 4352. TRITON_ATTN declares only `MultipleOf(16)`, so `block_stride_alignment` stays `None` and the kernel-block cap doesn't apply. In our deployment the reported KV cache went from ~212K to ~401K tokens with the change. The pool size was not identical between those two boots, so take the ratio as approximate; per token of context the target's pool cost halves.

I haven't run this branch on the GPU yet; I'll report back if it doesn't reproduce our block once it's in our tree.
