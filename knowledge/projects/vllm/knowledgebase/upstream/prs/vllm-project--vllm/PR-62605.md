# [ROCm][Perf] prefix_prefill: run mixed batches on all XCDs and skip empty query blocks

[Upstream PR](https://github.com/vllm-project/vllm/pull/62605) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

`context_attention_fwd` in `prefix_prefill.py` runs `ROCM_ATTN`'s prefills and spec-decode verifies. It gets much slower when a long prefill shares a batch with short requests, which is the normal mixed step of chunked prefill. This PR fixes two causes:

1. **Grid order.** The grid was `(batch, head, query_block)`, with the batch on the fastest axis. MI300/MI355 deal workgroups round-robin over 8 XCDs. The programs of one request have linear ids `i, i + b, i + 2b, ...` for batch size `b`, so with even `b` they reach only some of the XCDs. Decodes (`query_len == 1`) return at once, so a prefill batched with decodes runs on part of the GPU. This PR uses `(head, query_block, batch)`, with the batch on the slowest axis.
2. **Empty query blocks.** Every request gets `cdiv(max_query_len, BLOCK_M)` query blocks. A 4-token verify batched with a 16k-token chunk gets 128 blocks. 127 of them have no rows but still loop over the whole context. They now return early.

Found while profiling `ROCM_ATTN` against `ROCM_AITER_UNIFIED_ATTN` for #61433.

## Claims

- A prefill mixed with decodes or spec verifies runs as fast as the prefill alone. Before this PR it was up to 16× slower.
- The output is bit-identical to the current kernel.
- `ROCM_ATTN` end-to-end throughput rises up to 6.3× on Qwen3-8B (MI355X, 64k input, EAGLE3).
- Requests served one at a time do not change.

## Validation

**Kernel.** 8k-token chunk on a 16k prefix, Qwen3-8B shapes (32 query heads, 8 KV heads, head size 128, bf16, block size 16), MI355X, `triton.testing.do_bench`. The chunk is batched with `b - 1` decodes:

| main (ms) | 9.1 | 18.4 | 10.4 | 36.8 | 10.3 | 20.8 | 10.3 | 80.2 | 40.3 | 143.9 |

| --- | --- | --- | --- |

**Unit tests.** `tests/kernels/attention/test_prefix_prefill.py` gives the same results with and without this PR. On the nightly image I used, 41 cases fail on both sides, all with `TypeError: chunked_prefill_paged_decode() got an unexpected keyword argument 'use_interleaved_v_cache'` or `'types.SimpleNamespace' object has no attribute 'use_cascade'`. They come from the image's other modules being older than the tests, not from this kernel.

**End to end.** Qwen3-8B with YaRN ×4, `ROCM_ATTN` (the default), MRV2, 1024 output tokens with `--ignore-eos`, temperature 0, MI355X. Nightly `0.30.1rc1.dev558+g0cbac6cd1` with only `prefix_prefill.py` swapped. Without spec decode, decodes return at once, so only the grid order matters.

## Details

- Both kernels (`_fwd_kernel` and `_fwd_kernel_alibi`) read `cur_head`, `start_m` and `cur_batch` from program ids 0, 1 and 2, and both launches use the new grid order.
- The early return skips query blocks with no rows. Such a block loaded no queries and stored no output (both are masked by `offs_m < cur_batch_query_len`), so the output does not change.
- Not fixed here: a spec verify with `query_len` of 2–4 still takes a whole `BLOCK_M = 128` tile per query head. That makes `ROCM_ATTN`'s verify step 3–14× slower than `TRITON_ATTN`'s decode kernel. It needs a separate kernel change.
- Tests: no new test. The change only reorders the grid and skips query blocks that have no rows, The existing `test_prefix_prefill.py` cases already cover it for both kernels: they draw random query lengths per request, so shorter requests get query blocks with no rows. They run in the AMD `kernels/attention` CI step.
