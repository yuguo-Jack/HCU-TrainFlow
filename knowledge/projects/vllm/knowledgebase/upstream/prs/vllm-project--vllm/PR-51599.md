# [Bugfix][MRv1] Decouple async Mamba align D2H counts from InputBatch row shifts (#51571)

[Upstream PR](https://github.com/vllm-project/vllm/pull/51599) · state: open · merged: False

## Original PR description

### Purpose
Fixes #51571: In ModelRunner V1 (`MRv1`) with hybrid models (Mamba / GatedDeltaNet) and speculative decoding (MTP), accepted token counts get out of sync when requests finish and batch rows shift, leading to repeated/corrupted tokens.

### Root Cause
1. **Async Mode (`use_async_scheduling=True`):** Step N copies accepted token counts over D2H asynchronously. Meanwhile, Step N+1 runs `_update_states()` on CPU (`condense()`, `swap_states()`). If D2H writes straight to `InputBatch.num_accepted_tokens_cpu_tensor`, the in-flight DMA races with CPU row moves, and gathering through `prev_positions` in `_prepare_inputs()` permutes the counts twice.
2. **Sync Mode (`use_async_scheduling=False`):** In sync mode, execution finishes before row moves, so `InputBatch` naturally moves counts with requests. As @amittell and @WonkaRed pointed out, doing an unconditional 1:1 copy from the runner buffer in `_prepare_inputs()` overwrites the newly moved rows with stale Step N indices (`[2, 4, 1]` regressed to `[5, 4, 3]`).

### Solution
- **Async mode (`use_async_scheduling=True`):** D2H copies to `self.num_accepted_tokens.cpu` (runner buffer). In `_prepare_inputs()`, `_sync_num_accepted_tokens()` remaps counts through `prev_positions` and updates `input_batch`.
- **Sync mode (`use_async_scheduling=False`):** D2H copies to `self.input_batch.num_accepted_tokens_cpu_tensor` directly. We also sync `num_accepted_tokens_event` at the start of `_update_states()` so the copy finishes before requests are removed or condensed. In `_prepare_inputs()`, `_sync_num_accepted_tokens()` reads the moved counts directly from `input_batch`.
- Thanks to @WonkaRed and @amittell for isolating the sync replay test and catching the row-shift edge case (both added as co-authors on the commit).

### Scope Clarification
- This PR strictly fixes #51571 (output token corruption).
- The separate multi-GPU `Xid 31` memory crash in #50021 was investigated in PR #53613 (input-prep hoisting, closed by @amittell on Oct 5). This PR does not touch or claim to fix #50021.

### MRv1 Scope & Community Impact
While MRv2 keeps tokens device-resident and is unaffected, ModelRunner V1 (`MRv1`) is still widely used across community and enterprise setups:
- @Capsup and @WonkaRed hit this on hybrid speculative decoding.
- @CubeLander independently confirmed reproducing this exact token corruption bug on Ascend hardware with Qwen3.5-35B-A3B MTP, confirming that this fix eliminated corrupted tokens and gave 100% clean output (7/8 to 8/8 exact retrievals). https://github.com/vllm-project/vllm/issues/51571#issuecomment-5809397655
- @kar100ai (RadianVector) hit this on RTX 4090 GPUs.
The changes are strictly contained to `gpu_model_runner.py` (<40 lines) with zero impact on MRv2 or standard transformer models.

### Testing
- 8 unit tests in `TestSyncNumAcceptedTokens` covering async remap, empty fallback, sync direct read, D2H targets for both align and non-align modes, and `_update_states` sync guard.
- CPU replay test verifying row shifts (`condense()` + `swap_states()`) with synthetic draft patterns across both sync and async modes.
- `ruff check` and `ruff format` clean.

- QwertyJack · comment · 2026-08-11T01:36:08Z · [source](https://github.com/vllm-project/vllm/pull/51599#issuecomment-5248037397)

The production fix direction looks correct: under async scheduling, the D2H result should be owned by a runner-side previous-iteration snapshot and remapped only after the existing event synchronization.

One ownership boundary still looks implicit. When `use_async_scheduling=True` but `prev_req_id_to_index` is empty, the code falls into the current `else` branch (commented as "Non-async mode") and reads from `InputBatch`:

```python
else:
    self.num_accepted_tokens.np[:num_reqs] = (
        self.input_batch.num_accepted_tokens_cpu[:num_reqs]
    )
```

The usual empty-mapping cases may already contain neutral values, but this relies on an invariant that is not encoded here. Once async D2H ownership moves to `self.num_accepted_tokens.cpu`, it would be clearer and safer to make the three ownership cases explicit:

```python
if self.use_async_scheduling:
    if prev_req_id_to_index:
        # Remap the previous-iteration runner snapshot through prev_positions.
        ...
    else:
        self.num_accepted_tokens.np[:num_reqs].fill(1)
        self.input_batch.num_accepted_tokens_cpu[:num_reqs].fill(1)
else:
    # InputBatch owns current-request counts and condense/reorder moves them.
    self.num_accepted_tokens.np[:num_reqs] = (
        self.input_batch.num_accepted_tokens_cpu[:num_reqs]
    )
```

A small `_sync_num_accepted_tokens()` helper would encode this lifecycle cleanly and give the regression test a production function to exercise. It would also remove the inner `if self.use_async_scheduling` used to select `src_accepted_counts`, whose `else` arm is unreachable inside the outer async-only branch.

This keeps the patch allocation- and synchronization-neutral while making the previous-row snapshot -> current-row state transition explicit.

- WonkaRed · comment · 2026-09-30T01:53:47Z · [source](https://github.com/vllm-project/vllm/pull/51599#issuecomment-5902516840)

Ran into this on vLLM 0.30.0: TP=2 across 2x RTX 3090, a Qwen3.8-27B hybrid (mamba) model with MTP, async scheduling on, and `mamba_cache_mode=align` (the hybrid default with prefix caching). It matches #51571 exactly: silent state corruption, no error, just wrong output once requests start finishing at different times.

Root cause as I read it: `postprocess_mamba_align_gpu` copies the step's accepted-token counts D2H, non-blocking, into `input_batch`'s pinned array. The next step's `_update_states` moves rows (`add_request`, `condense`, the GDN decode-first `swap_states`) before `_prepare_inputs` waits on the copy event and gathers by `prev_positions`. So a copy that lands before the row move gets permuted twice, once by the move and again by the gather, and a request reads another request's count and shifts its GDN/conv state by the wrong number of tokens.

The direction here is right: redirect the D2H target off `input_batch` and remap through `prev_positions` after the wait. But the current head does the redirect unconditionally, sync mode included. Sync mode doesn't need a remap. The sampled-token readback already waits for the copy before the step returns, so the stock 1:1 write into `input_batch` is correct there. Redirecting anyway hands requests the previous step's row order after this step's rows have moved: the same class of bug, now in sync mode. I reproduced it on CPU with a test that replays the real `_update_states_after_model_execute`, the `InputBatch` row ops, `_compute_prev_positions` and the accepted-count block of `_prepare_inputs`. Running this PR's head through a four-request add/condense/swap scenario in sync mode gives `[4, 1, 3]`, where each request should read back its own count, `[3, 2, 1]`.
