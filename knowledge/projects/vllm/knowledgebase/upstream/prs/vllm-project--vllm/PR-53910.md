# [Core] Add PROMOTION_LATENCY histogram metric for tiering offload

[Upstream PR](https://github.com/vllm-project/vllm/pull/53910) · state: closed · merged: True

## Original PR description

## Purpose

Add the Prometheus histogram `vllm:kv_offload_tiering_promotion_latency_seconds` for secondary-to-primary
promotion attempts, labeled by tier.
The histogram measures elapsed time from `TransferJob` creation until the tier reports completion. It includes time waiting in the tier queue and failed promotion attempts. It does not use `JobResult.transfer_time`, which measures
active data transfer only. P2P promotions are measured even when their `JobResult` has no `transfer_time`.


The `vllm:kv_offload_tiering_promotion_latency_seconds` histogram has a `result` label with values `success` and `failure`.
- `success` is recorded when `JobResult.success` is `True`.
- `failure` is recorded when `JobResult.success` is `False`, including P2P load timeouts.
This keeps failed promotions visible while letting users query success and failure latency separately.

[P1] Record promotion latency for the P2P tier

This observation is nested under completed_job.transfer_time, but the real P2P load-completion path appends JobResult(job_id=lr.job_id, success=lr.success) in tiering/p2p/manager.py and never populates that field, whose default is None. The added test only supplies transfer_time manually and does not exercise a backend. Please time the P2P load lifecycle and populate JobResult.transfer_time with a completion regression, or explicitly exclude/document tiers that cannot emit this metric.
