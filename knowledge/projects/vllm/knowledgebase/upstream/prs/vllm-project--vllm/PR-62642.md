# [Rust Frontend] Truncate prompts against max_model_len like Python

[Upstream PR](https://github.com/vllm-project/vllm/pull/62642) · state: closed · merged: True

## Original PR description

## Overview

Python budgets `truncate_prompt_tokens` against the context length only: `-1` keeps `max_model_len - 1` prompt tokens (`TokenizeParams.max_truncation_tokens` in `vllm/renderers/params.py`), and an explicit value is rejected only above `max_model_len`; `max_tokens` is an upper bound clamped after tokenization, not a reservation (vllm-project/vllm#57035, vllm-project/vllm#62010). The Rust frontend budgets `max_model_len - max_tokens` instead. This PR applies Python's budget in the Rust text layer.

## Claims

- `truncate_prompt_tokens=-1` without `max_tokens` now truncates and generates instead of failing as "prompt too long".
- With `max_tokens`, Rust keeps the same prompt tokens Python keeps; generation gets the remaining context through the existing `max_tokens` clamp.
- An explicit `truncate_prompt_tokens` is rejected only above `max_model_len`, with Python's message.

Example with `max_model_len=10`, a 15-token prompt, and `truncate_prompt_tokens=-1`:

| `max_tokens` | Rust before | Rust after (= Python) |
|---|---|---|
| absent | 400, prompt too long | 9 prompt tokens, `max_tokens=1` |
| 5 | 5 prompt tokens, `max_tokens=5` | 9 prompt tokens, `max_tokens=1` |

- `auto_truncation_leaves_one_output_token` (`vllm-text`) runs the table above through `TextRequestProcessor::prepare`. It fails on the base: the `max_tokens`-absent case hits the prompt-too-long error.
- `input_budget_holds_back_one_token_for_output` and `fixed_limit_cannot_exceed_max_model_len` replace the unit tests that pinned the old budget.

## Details

Truncation is owned by `vllm-text` (`PromptTruncation::apply`, called from `TextRequestProcessor::prepare_prompt_tokens`), which chat, completions, and gRPC all reach, so one change covers every entry point that accepts `truncate_prompt_tokens`. Only generation paths set a truncation policy (`/tokenize` and `/inference/v1/generate` never do), so the held-back output token always applies, as in Python, where only no-output requests such as pooling keep the full context. `prepare_prompt_tokens` no longer needs `max_tokens`, and the error variant is renamed to `TruncatePromptTokensExceedsMaxModelLen` to match what it checks.

Not a duplicate: no open upstream PR changes the Rust truncation budget; vllm-project/vllm#61363 changes special-token handling in Python truncation.
