# [Bugfix][Frontend] Stop beam search on generation config EOS tokens

[Upstream PR](https://github.com/vllm-project/vllm/pull/62072) · state: closed · merged: True

## Original PR description

## Overview

Beam search (`LLM.beam_search` and `use_beam_search` in the OpenAI server) only treats `tokenizer.eos_token_id` as the end of a beam. Normal generation also stops on the extra `eos_token_id` entries from the model's generation config. For chat models whose end-of-turn token is one of those extra ids, beam search keeps going after the answer and writes the next turn until `max_tokens`.

## Claims

- Beams finish on every EOS id that normal generation stops on (the tokenizer EOS plus the generation config's `eos_token_id`), unless `ignore_eos=True`.
- The OpenAI server reports the token that actually ended the beam as `stop_reason` and leaves it out of the text, as it already does for the tokenizer EOS. The length-normalized beam score discounts it the same way.

## Validation

[`zai-org/glm-edge-1.5b-chat`](https://huggingface.co/zai-org/glm-edge-1.5b-chat) has `<|endoftext|>` (59246) as tokenizer EOS, and its generation config adds `<|user|>` (59253) and `<|observation|>` (59255). The model ends its turn with `<|user|>`.

```python
from vllm import LLM, SamplingParams
from vllm.sampling_params import BeamSearchParams

llm = LLM("zai-org/glm-edge-1.5b-chat", enforce_eager=True, max_model_len=512)
tokenizer = llm.get_tokenizer()
text = tokenizer.apply_chat_template(
    [{"role": "user", "content": "What is the capital of France?"}],
    add_generation_prompt=True,
    tokenize=False,
)
prompt = {"prompt_token_ids": tokenizer.encode(text, add_special_tokens=False)}

print(llm.generate(prompt, SamplingParams(temperature=0, max_tokens=48))[0].outputs[0].text)
beam = llm.beam_search([prompt], BeamSearchParams(beam_width=2, max_tokens=48))[0].sequences[0]
print(tokenizer.decode(beam.tokens[len(prompt["prompt_token_ids"]):], skip_special_tokens=True))
```

I ran this on an L4 with the published wheel for cffc0cfa3 (`main`) and with the same wheel plus this change. I also sent the same question to `/v1/chat/completions` with `"use_beam_search": true, "n": 2, "max_tokens": 48`:

| | `main` | This PR |
| --- | --- | --- |
| Greedy `LLM.generate` | `The capital of France is Paris.` (8 tokens) | same |
| `LLM.beam_search` | `The capital of France is Paris.\nThank you for the quick response! Is there another capital city …` (48 tokens, the model writing the next user turn) | `The capital of France is Paris.` (8 tokens) |
| `/v1/chat/completions` with beam search | the same kind of 48-token text, `finish_reason: length`, `stop_reason: null` | `The capital of France is Paris.`, `finish_reason: stop`, `stop_reason: 59253` |

For "Name the three primary colors.", beam search on `main` also ran to the 48-token limit. With this change it returned `The three primary colors are:\n\n1. Red\n2. Blue\n3. Yellow` with `stop_reason: 59253`.

On `microsoft/Phi-3-mini-4k-instruct` (tokenizer EOS 32000, generation config `[32000, 32001, 32007]`), every beam on `main` ended in `<|end|><|endoftext|>` with `stop_reason: 32000`. With this change, beams end at `<|end|>` with `stop_reason: 32007`. Greedy generation and `ignore_eos=True` gave the same tokens before and after.

```bash
pytest tests/samplers/test_beam_search_online.py tests/samplers/test_beam_search.py -k "not test_beam_search_single_input and not test_beam_search_with_concurrency_limit and not test_beam_search_passes_multimodal_data and not test_beam_search_structured_output"
```

- The new `test_beam_search_respects_generation_config_eos` runs the offline and online beam loops with no, a scalar, or a list config EOS, with and without `ignore_eos`. 4 of its 12 cases fail on `main`.
- With this change: 37 passed. The 4 deselected tests need a GPU.
- `pre-commit run --files` on the changed files passes.

## Details

Both loops compared each candidate token with `tokenizer.eos_token_id`. The one-token engine requests they send already get the generation config applied, but the loops expand the returned logprobs and decide completion themselves.

I resolve the EOS ids once, with the existing `SamplingParams.update_from_generation_config(...)` on the beam's base sampling params. Then I use `all_stop_token_ids` in the completion check, for the online `stop_reason` and text trimming, and in `get_beam_search_score`.

Duplicate check: I searched open and closed issues and PRs for beam search with EOS, `eos_token_id`, `generation_config`, `ignore_eos` and the changed files. #9627 (merged) fixed stripping the tokenizer EOS from beam text. #52621 (beam search stop strings) and #36285 (online structured output) touch the same files but still compare with `tokenizer.eos_token_id` only. The other open PRs on these files (#60327, #60550, #59506, #47630, #60787, #55437, #60562, #51891, #60094, #52249) change unrelated parts.

File: `vllm/entrypoints/generate/beam_search/online.py` · line None

🔴 Beam search on models whose generation config lists an EOS id >= the model vocab size now fails every request, while normal generation still works. The EOS lookup calls update_from_generation_config on the params sent to the engine, which copies config EOS ids into stop_token_ids. The engine checks those ids against the vocab in verify(), which runs before it applies the generation config itself. Fix: work out the EOS set without changing the request params (e.g. on a copy, or straight from generation_config_fields), so the engine still validates them as before. This covers both sites (online.py:75, offline.py:130). [also at: vllm/entrypoints/generate/beam_search/offline.py:133 - If a generation-config EOS id is at or above the model vocab size, every beam search request now fails validation, while normal generation still works. update_from_generation_config now writes those ids into stop_token_ids before the engine calls params.verify().]

<details>
<summary>Why this was flagged</summary>

Trigger: a model whose generation_config eos_token_id contains an id >= model_config.get_vocab_size(). The request comes in through LLM.beam_search (offline.py:130) or use_beam_search in the OpenAI server (online.py:75). Both now call update_from_generation_config on the per-step SamplingParams. That call sets stop_token_ids to the config EOS ids (sampling_params.py:799-803), and these params are then passed to the engine. InputProcessor.process_inputs calls _validate_params -> params.verify() first (input_processor.py:389, 157). verify() runs _validate_stop_token_ids, which raises VLLMValidationError "in stop_token_ids contain out-of-vocab token ids" (sampling_params.py:1061-1073). On the base branch the engine added config EOS ids only afterwards, in its own update_from_generation_config call (input_processor.py:489), so verify() never saw them and beam search ran. No safeguard catches it, because the generation config is never validated against vocab_size anywhere else.

**Verification:** update_from_generation_config writes the extra config EOS ids into self.stop_token_ids (sampling_params.py:798-803) on the params sent to the engine (online.py:75-78, offline.py:130-133). verify() then raises VLLMValidationError for any id >= vocab_size (sampling_params.py:1050-1073). On the base commit, beam search never filled stop_token_ids, so it worked.

</details>
