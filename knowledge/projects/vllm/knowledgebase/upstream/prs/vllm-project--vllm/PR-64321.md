# [ROCm][CI] Raise bf16 atol to 2e-2 for ROCM_AITER_FA prefill in test_mla_backends

[Upstream PR](https://github.com/vllm-project/vllm/pull/64321) · state: closed · merged: False

## Original PR description

## Purpose

`test_chunked_context_backend_correctness[False-trtllm-gen-auto-glm-MLAPrefillBackendEnum.ROCM_AITER_FA]` fails on every run of `:amd: (MI355 DPX) V1 Attention Shard 2/4` on main, on both decode backends:

```
[AttentionBackendEnum.TRITON_MLA] output differs from SDPA baseline. Max diff: 0.015625, max rel diff: nan)
[AttentionBackendEnum.ROCM_AITER_MLA] output differs from SDPA baseline. Max diff: 0.015625, max rel diff: nan)
```

Failing runs: [ci#97886](https://buildkite.com/vllm/ci/builds/97886/list?jid=01a18140-a4a6-4350-b502-10e0b5e36821&tab=output) (3 of 3 attempts) and [ci#97976](https://buildkite.com/vllm/ci/builds/97976) (2 of 2).

The error comes from the `ROCM_AITER_FA` prefill that both backends share. I compared each implementation against an exact fp32 reference, on inputs shaped like this test.
- AITER's bf16 `flash_attn_varlen_func` on gfx950 uses about 50% of the tolerance in the median case.
- torch SDPA (the test's reference) and FlashAttention-2 numerics both use about 29%.

As a result, AITER exceeds `atol=1e-2` on some inputs: 27 of 300 seeds fail. The CUDA prefill backends that run this test (FLASH_ATTN, TRTLLM_RAGGED) pass at `1e-2`.

It started failing now because the module seeds once at import, so this test's inputs depend on the tests that run before it. The runtime-shard planner recently started splitting `test_backend_correctness` by case. That put 286 more cases ahead of this test in Shard 2/4 and changed its inputs to a failing set.

This PR raises the bf16 `atol` to `2e-2` on ROCm, where `ROCM_AITER_FA` is the only prefill backend tested. The CUDA, XPU and fp8 tolerances are unchanged. Test-only change.

## Test Plan

Run on MI355X (gfx950) with the ci#97886 build (`665bfc8`). CUs are masked to 128 to match the DPX CI nodes.

```bash
export VLLM_ROCM_USE_AITER=1 ROC_GLOBAL_CU_MASK=0x100000000ffffffff CU_NUM=128
cd tests
# the 328 tests of Shard 2/4 from ci#97886, in CI order
pytest -v -s @shard2_order.txt
```

The failing test was also run with seeds 0–299. A local pytest plugin re-seeds right before the test body, so the result does not depend on test order.
