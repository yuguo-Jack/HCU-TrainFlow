# [Bugfix][Benchmark] Don't count content-free chunks as streamed outputs in chat

[Upstream PR](https://github.com/vllm-project/vllm/pull/62341) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

The chat benchmark clients count the opening role-only chunk as a streamed output, so TTFT is measured to a chunk with no output in it and the first real token appends a spurious ITL sample. A check prevented this between #3768 and #12288; this restores it in a form that also handles `reasoning` and `tool_calls`. Original report: #3759.

Benchmark client only. No engine, scheduler or serving code is touched, and no measured figure here reflects a change in how fast vLLM runs.

## Claims

- TTFT for `--backend openai-chat` is measured to the opening `delta: {"role": "assistant", "content": ""}` chunk, which carries no output.
- As a result 208 of 600 requests recorded `len(itl) == output_tokens`, which cannot happen when every interval sits between two tokens; there are at most `output_tokens - 1`. `/v1/completions` on the same server recorded exactly 200 x 255 samples and zero impossible counts.
- Every request on `main` carried a first ITL sample timing the role chunk, median 4 microseconds, so the minimum and low percentiles time metadata arrival. The error runs in the flattering direction: `main` reports chat as slightly faster than it is. With the fix, the minimum and each request's first sample rise to real decode intervals, and vLLM's actual speed is unchanged.
- This does **not** materially change any printed summary metric. Mean and median TTFT, ITL and TPOT all move by less than the run-to-run spread. The fix is to the sample array, which `--save-detailed` writes to JSON.
- 43 lines across the two clients, no new abstraction, no change to `async_request_openai_completions` or `async_request_openai_audio`.

Across those 600 requests on `main`:

- all 600 had a first sample under 0.1 ms, timing the arrival of the role chunk, median 0.0040 ms. That is exactly one spurious sample per request and never more than one, and it is what drags the reported minimum ITL down to 0.0025 ms.
- 208 recorded `len(itl) == output_tokens`, more intervals than exist between that many tokens. These are the requests where no two tokens happened to share a read, so nothing offset the extra sample. The other 392 carried it too and landed under the limit.

On this branch, no request records `len(itl) == output_tokens` and none exceeds `output_tokens - 1`. Two of 600 had a first sample under 0.1 ms, both from two tokens arriving in a single read.

`/v1/completions` on the same server, same workload, recorded exactly 51,000 samples for 200 requests of 256 tokens, which is 200 x 255, and no impossible counts.

## Details

### Root cause

#3759 reported a chat TTFT of 0.005 s and printed the chunk it had been measured to, a role-only delta with `content: null`. @ywang96 identified the role chunk as the cause and #3768 added:

```python
delta = data["choices"][0]["delta"]
if delta.get("content", None):
```

#12288 restructured the same block to read token counts from the usage chunk. That required tolerating a trailing chunk with `choices: []`, since `data["choices"][0]` raises on it, and the gate became:

```python
if choices := data.get("choices"):
    content = choices[0]["delta"].get("content")
```

`content` is still read but no longer decides anything. The packaged client in `vllm/benchmarks/lib/` has the same shape. #3768's own note explains why nothing caught it: "This does not affect existing CI results since by default vLLM uses completions instead of chat completions for benchmarking."

### Tokens that render as empty strings

#12288 left this note on the completions side:

```python
if choices := data.get("choices"):
    # Note that text could be empty here
    # e.g. for special tokens
    text = choices[0].get("text")
```

That is correct: a token can decode to an empty string under `skip_special_tokens=True`, and dropping it would lose a real interval. #3768's truthiness gate would drop it. So the check here tests whether the chunk carries a token:

```python
if delta.get("content") or delta.get("reasoning") or delta.get("tool_calls") or delta.get("function_call"):
    return True
return delta.get("content") == "" and "role" not in delta
```

The two cases are distinguishable on the wire. An empty-rendering token serialises as `{"content": ""}`. The opening chunk serialises as `{"role": "assistant", "content": ""}`, and `role` is set only there, on the first iteration of `chat_completion_stream_generator`, and on no other `DeltaMessage` in the streaming path. A suppressed or finish chunk serialises as `{}`. A third-party server that repeats `role` on every chunk is unaffected, because a chunk with real content satisfies the first condition.

Three of the four fields, `content`, `reasoning` and `tool_calls`, are what vLLM's own streaming logger checks to decide whether a delta carried anything, in the same file. `function_call` is the fourth and vLLM never emits it; it is there because OpenAI's legacy spec puts it on streaming deltas and these clients are pointed at third-party OpenAI-compatible servers too.

### Tradeoffs and notes

The gate is a named helper with one call site per file, which §3.3 of the PR checklist would normally have inlined. It is kept because the two clients must stay in sync, per #55508, and a shared name makes a divergence between them visible; and because the second condition needs the comment explaining why an empty string counts, which reads badly inline.

Content-free chunks now reach the `elif usage:` branch, which the `if choices:` arm used to swallow. Under `continuous_usage_stats` the opening chunk carries both `choices` and `usage`, so its `completion_tokens: 0` is read and then overwritten by every later chunk. For servers that attach usage to an empty finish chunk with no trailing `choices: []` chunk, the count is now captured where it was dropped before.

`most_recent_timestamp` advances only inside the gated branch, so #55508's `latency - ttft == sum(itl)` guarantee is unchanged. #54708's rejection of tokenless streams is unchanged and now also fires on a stream whose chunks all carry content-free `choices`.

### Relation to #46652

#46652 proposed inserting zero-duration ITL samples so `len(itl)` matched the token count. `docs/benchmarking/cli.md` says ITL records only the gaps between streamed outputs and adds no zero-duration gaps for tokens in the same output, so #46652 is closed. This PR removes a sample with no output on either side of it. Both came out of #27485, which the stale bot closed; the reasoning and tool-parser case reported there is a different cause.

### Duplicate check

Nobody is fixing this. Every reference to #3759, #3768 and #12288 across issues and PRs is a coincidental numeric match; the 190 hits for 12288 are hidden and intermediate sizes. The regression was never re-reported after #12288 merged, so #3759 is still the only issue describing it.

A search by fix shape found nothing either. No PR restores a content gate, and `_choice_has_streamed_output` has no hits. #55508 touched this exact function on 2026-09-13 to make TTFT and latency accounting consistent across endpoints and left the gate ungated. #28183 attempted per-token ITL from continuous usage stats and was closed unmerged without adding a gate.

Open PRs touching either client file are #49720, #51155, #51172, #55719, #57519 and #58734. None modify the chunk gating. My own #46652 is in this area and is being closed.

#59722 is related. It reports the Rust `vllm-bench` chat backend counting token-less streams as successful and notes that Python fails them, which is true for the case tested there: a stream with no `choices` chunks at all, which `first_chunk_received` already rejects. It is not true for a stream whose chunks all carry content-free `choices`, which is the third behaviour above.
