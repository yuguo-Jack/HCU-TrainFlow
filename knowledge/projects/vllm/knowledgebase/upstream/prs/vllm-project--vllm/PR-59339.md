# [Bugfix][Core] Reclaim KV blocks from idle streaming-input sessions under KV pressure

[Upstream PR](https://github.com/vllm-project/vllm/pull/59339) · state: open · merged: False

## Original PR description

## Purpose

Under KV pressure, resumable streaming-input sessions that are paused (`WAITING_FOR_STREAMING_REQ`) or resumed-but-unscheduled retain their KV blocks indefinitely, which can deadlock the engine: sessions park holding blocks, resume with continuations that no longer fit, and every `schedule()` breaks out of the waiting loop with nothing scheduled, while preemption only reclaims from `running` (which is empty).

This PR reclaims those retained blocks at the waiting loop's allocation-failure point. Victims are, in order: (1) paused sessions — idle with no pending work, zero-cost victims; (2) WAITING resumable sessions still holding blocks — picking the newest/lowest-priority victim, mirroring the running loop's preemption choice. Victims are found by their resource fact (`_holds_kv_blocks`) across all waiting containers, not by queue membership, so the search is robust to the scan loop's step-local bookkeeping. The victim is freed exactly like a preemption (blocks, encoder cache, inflight-prefill tracking, `num_computed_tokens = 0`, PREEMPTED event, `reset_preempted_req_ids`) but keeps its status and its `num_waiting_for_streaming_input` accounting; it moves out of the kv-holding queues and recomputes from scratch when resumed. Each reclaim strictly shrinks the candidate set, so the retry provably terminates. Reclaim is skipped when the victim's blocks can only be freed lazily (deferred frees can't help this step's allocation), matching the running loop's discipline.

## Relationship to other PRs

- Supersedes/extends #49439 (whose approach — reclaim from a WAITING resumable peer — is retained here, hence the Co-authored-by). #49439's victim search is broken on current main: it references the removed `skipped_waiting` queue and misses `kv_holding_waiting`. This PR is built on the post-#58947 queue structure (`kv_holding_waiting` / `waiting` / `deferred_waiting`) and additionally covers paused sessions, which #49439 did not.
- Depends on the `_update_request_as_session` fold fix (`keep_end = max(session.num_computed_tokens, session.num_tokens - 1)`) from #58778, now on main: without it, a session reclaimed while paused would fold its next chunk with `num_computed_tokens == 0` and lose its whole prompt.
