# [Bugfix][Tool Parser] Preserve whitespace in HYV4 argument names

[Upstream PR](https://github.com/vllm-project/vllm/pull/61542) · state: closed · merged: True

## Original PR description

## Overview

Preserve schema property names exactly in HYV4 streaming tool calls. For an integer property named `" count "`, streaming currently emits `{"count": "7"}` while non-streaming returns `{" count ": 7}`.

This addresses the argument-key whitespace case explicitly excluded from #60788.

## Claims

- Preserve whitespace in argument names in both completed-pair and partial-value streaming paths.
- Use the exact key for schema type lookup and keep `"count"` and `" count "` distinct, matching non-streaming parsing.

### End-to-end validation with real HYV4 weights (H20, 2026-10-30)

I served the real `Tencent-Hunyuan/Hy4-preview-FP8` checkpoint and compared streaming against non-streaming tool calls, before and after this PR.

**Setup**
- 1× NVIDIA H20 (SM90), vLLM `0.32.1rc1.dev507+g85e199e60` wheel, torch 2.14.0+cu130.
- Only `vllm/tool_parsers/hy_v4_tool_parser.py` differs between the two runs:
  - baseline = `d5e62627a3` (sha256 `d0aa7524…`, identical to the file shipped in the wheel);
  - patched = `04aa841` (sha256 `5b38e435…`).
- Serve flags:
  ```
  vllm serve Hy4-preview-FP8 --tool-call-parser hy_v4 --enable-auto-tool-choice \
    --reasoning-parser hy_v4 --hf-overrides '{"num_nextn_predict_layers":0}' \
    --cpu-offload-gb 690 --cpu-offload-params experts \
    --max-model-len 8192 --max-num-seqs 1 --enforce-eager --gpu-memory-utilization 0.92
  ```
  The routed experts (MxFP8, HUMMING backend) sit in host memory, since the model does not fit on one GPU.
- Request:
  - one tool `record` whose only property is `" count "` (integer, one leading and one trailing space);
  - prompt asks the model to call it with 7;
  - `temperature=0`, `seed=0`, `reasoning_effort=no_think`.
  - The same body is sent once with `stream=false` and once with `stream=true`. The streamed arguments are rebuilt from the raw SSE deltas.
- There is no grammar or logit bias beyond what vLLM applies for each `tool_choice`.

**Results**

| tool_choice | non-stream (both) | baseline stream | patched stream |
|---|---|---|---|
| `required` | `{" count ": 7}` | `{"count": "7"}` ❌ | `{" count ": 7}` ✅ |
| named `record` | `{" count ": 7}` | `{"count": "7"}` ❌ | `{" count ": 7}` ✅ |

- In each case, the generated token ids are identical across all four requests (baseline/patched × stream/non-stream), so the difference comes from the parser alone.
- The model emits the atomic `:opensource` marker tokens (ids 120033–120043), so this exercises the token-id streaming path.
- On baseline, the stripped key no longer matches the schema, so the value also loses its integer type (`"7"`).

A tiny-random HYV4 model run on the same host showed the same pattern:
- guided (string) path: baseline stream `{"count": "-451"}`, patched `{" count ": -451}`;
- token-id path: same as above;
- non-stream `{" count ": -451}` throughout.

**Unrelated observation**
- With `tool_choice="auto"`, the real model produced a malformed call: `<arg_key:opensource> count </arg_value:opensource><arg_value:opensource>7…`, i.e. the key is closed with `</arg_value>`.
- Non-streaming then returns no tool call and puts the text in `content`, while streaming emits `record` with `{}`.
- Baseline and patched behave identically here, so it is outside this PR's scope. It is a separate stream/non-stream divergence on malformed output.

## Details

`_extract_streaming_incremental` strips keys in two places before schema lookup and argument tracking. This changes valid property names, can stringify non-string values, and can collapse two distinct properties. Remove those two normalizations; the structural-tag grammar already preserves exact schema keys.

Regression coverage includes whitespace-only names, seven value types, colliding trimmed names in both orders, whole/token/character chunks, both token suffix variants, emitted JSON prefixes, and state cleanup between tool calls. Four grammar cases check exact required/optional keys.

Upstream overlap was rechecked on 2026-10-14 at main `d5e62627a3ece4b2d045cbb2b22ac26c061c8313`: both key normalizations remain. No direct duplicate was found. #60788 excludes this case; #59620 handles truncated calls and inter-tag whitespace; #61205 limits grammar whitespace length. Those changes do not preserve whitespace inside argument keys.
