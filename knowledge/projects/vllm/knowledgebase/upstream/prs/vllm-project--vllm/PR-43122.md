# [Frontend] Add readiness endpoint and engine health checks

[Upstream PR](https://github.com/vllm-project/vllm/pull/43122) · state: open · merged: False

## Original PR description

## Purpose

Add a `/health/ready` readiness endpoint so orchestrators can tell a live engine apart from one that should receive traffic. `/health` stays the liveness check.

`/health/ready` returns:

- `200` when the engine is idle, or busy and making progress.
- `503` when the engine is dead (`EngineDeadError`).
- `503` when the engine has unfinished requests and has produced no output for `VLLM_READY_CHECK_IDLE_TIMEOUT_S` (default 30 s) since it became busy, or no output for `VLLM_READY_CHECK_PROGRESS_TIMEOUT_S` (default 10 s) after the last output (`EngineUnhealthyError`).
- `503` when the engine core does not answer the readiness check within `VLLM_READY_CHECK_TIMEOUT_S` (default 5 s), e.g. when a forward pass or collective hangs and the busy loop never services the utility call.

Progress means any request output with new tokens, a pooling output, or a finish reason, so pooling/embedding servers under sustained load stay ready. The busy timer starts only when the scheduler goes from idle to busy, so a steady stream of new requests cannot mask a stall. With DP load balancing, every engine is checked and the first unready engine is reported.

## Changes

- `EngineCore.check_ready` plus readiness bookkeeping in `add_request` / `abort_requests` / step outputs.
- `check_ready_async` on the core clients; `DPLBAsyncMPClient` checks all engines.
- `EngineClient.check_ready` / `AsyncLLM.check_ready`, bounded by `VLLM_READY_CHECK_TIMEOUT_S`.
- `EngineUnhealthyError` in `vllm/v1/engine/exceptions.py`.
- `GET /health/ready` route, excluded from Prometheus HTTP metrics like `/health`.
- New env vars: `VLLM_READY_CHECK_IDLE_TIMEOUT_S`, `VLLM_READY_CHECK_PROGRESS_TIMEOUT_S`, `VLLM_READY_CHECK_TIMEOUT_S`.
- Docs and the Helm chart now point readiness probes at `/health/ready`.

File: `vllm/v1/engine/async_llm.py` · line None

![critical](https://www.gstatic.com/codereviewagent/critical.svg)

The current readiness check logic has a critical flaw: it will incorrectly raise an `EngineUnhealthyError` after the engine has been idle for longer than `VLLM_READY_CHECK_PROGRESS_TIMEOUT_S`. 

Because `last_progress_at` is never reset to `0.0` after requests finish, a new request arriving after an idle period will be compared against a stale `last_progress_at` timestamp from the *previous* busy period. If that idle period was longer than 10 seconds, the check will fail immediately upon the arrival of the next request. 

The logic should instead compare `last_progress_at` against `_last_request_at` to determine if we are waiting for the first bit of progress for a new batch of work, and ensure `_last_request_at` is reset when the engine becomes idle.

```suggestion
        if not self.output_processor.has_unfinished_requests():
            self._last_request_at = 0.0
            return

        now = time.monotonic()
        last_progress_at = self._last_progress_at_ref[0]

        # If we haven't seen progress since the engine became busy, 
        # use the idle timeout against the time the first request was admitted.
        if last_progress_at < self._last_request_at:
            if now - self._last_request_at > envs.VLLM_READY_CHECK_IDLE_TIMEOUT_S:
                raise EngineUnhealthyError(
                    "Engine has unfinished requests but has not produced "
                    "initial progress.")
            return

        # Otherwise, check if we've made progress recently.
        if now - last_progress_at > envs.VLLM_READY_CHECK_PROGRESS_TIMEOUT_S:
            raise EngineUnhealthyError(
                "Engine has unfinished requests but has not made recent progress.")
```

File: `vllm/v1/engine/async_llm.py` · line None

![high](https://www.gstatic.com/codereviewagent/high-priority.svg)

The `_last_request_at` timestamp is currently updated for every request admitted to the engine. If the engine is stalled but continues to receive new requests, this logic will continuously reset the timeout, potentially masking the stall indefinitely. It should only be updated when the engine transitions from an idle to a busy state (or when `_last_request_at` has been reset).

```suggestion
        if self._last_request_at == 0.0:
            self._last_request_at = time.monotonic()
```
