# [Bugfix][torch.compile] Read traced source files as UTF-8 when hashing

[Upstream PR](https://github.com/vllm-project/vllm/pull/64365) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Read traced source files as UTF-8 when computing the torch.compile code hash. Under a non-UTF-8 locale, AOT compile artifacts currently never load: `_verify_source_unchanged` fails decoding vLLM's own sources and every warm start recompiles.

Follow-up to the `UnicodeDecodeError` noted in #32416.

## Claims

- AOT compile artifacts load under non-UTF-8 locales (e.g. `LC_ALL=C` without C-locale coercion / UTF-8 mode, as when Python is embedded in another process).
- The JIT code hash in `VllmBackend.__call__` no longer silently drops non-ASCII traced files from the hash under such locales.
- No change to hashes under UTF-8 locales.

## Validation

New test `test_compute_code_hash_ignores_locale_encoding` hashes a UTF-8 file containing `—` in a subprocess forced to an ASCII locale (`LC_ALL=C PYTHONCOERCECLOCALE=0 python -X utf8=0`) and compares against the hash of the file's real content.

```bash
pytest tests/compile/test_aot_compile.py -k compute_code_hash_ignores_locale_encoding
```

| | Result |
|---|---|
| Without fix | FAILED: `UnicodeDecodeError: 'ascii' codec can't decode byte 0xe2 in position 2` |
| With fix | 1 passed |

`ruff check` / `ruff format --check` (v0.14.0) pass on the changed files.

**End to end on GPU.** `vllm/vllm-openai:v0.26.0` image (torch 2.11.0+cu130), 1× B300, `Qwen/Qwen3-0.6B`. Each case runs `LLM(...)` + one `generate` twice in separate processes against a fresh shared `VLLM_CACHE_ROOT`, with `LC_ALL=C PYTHONCOERCECLOCALE=0 PYTHONUTF8=0 VLLM_USE_AOT_COMPILE=1` (`locale.getpreferredencoding()` = `ANSI_X3.4-1968`). "After" is the same image with this PR's two-line change applied to the installed package.

| | Run 2 (warm) | `torch.compile` total, run 1 → run 2 |
|---|---|---|
| Before | `WARNING [decorators.py:321] Compiling model again due to a load failure from .../rank_0_0/model, reason: 'ascii' codec can't decode byte 0xe2 in position 30951: ordinal not in range(128)` | 14.50 s → 7.81 s |
| After | `INFO [decorators.py:311] Directly load AOT compilation from path .../rank_0_0/model` | 14.55 s → 2.67 s |

Production observation that motivated this (vLLM 0.26.0, L4, embedding model): every warm start logged

```
Compiling model again due to a load failure from .../torch_aot_compile/<hash>/rank_0_0/model,
reason: 'ascii' codec can't decode byte 0xe2 in position 3712: ordinal not in range(128)
```

with seven distinct positions across replicas. Six match the first non-ASCII byte of `vllm/utils/torch_utils.py`, `layers/attention/attention.py`, `layers/activation.py`, `platforms/interface.py`, `distributed/parallel_state.py`, `_custom_ops.py` in 0.26.0. The position varies because `_compute_code_hash` iterates a `set` of paths.

## Details

**Root cause.** On AOT load, `_verify_source_unchanged` compares the source content stored in the artifact against `_compute_code_hash(files)`, which re-reads each file with `open(filepath)` and so uses `locale.getpreferredencoding()`. Under an ASCII locale this raises on the first non-ASCII source file. `_try_load_aot_compiled_fn` catches the exception and recompiles. The save path never re-reads files as text, so artifacts are written fine and then can never be loaded.

`VllmBackend.__call__` has the same `open()` but catches `UnicodeDecodeError` (#32416), so under an ASCII locale those files are silently left out of the JIT code hash. This PR sets the encoding there too, so both paths read sources the same way.

**Why not a duplicate of #62628.** That PR makes `_compute_code_hash` catch `UnicodeDecodeError` and hash the file as empty. On AOT load the expected checksum is computed from the real stored content, so the checksums would still differ. The load would still fail (as "Source code has changed"), just with a misleading message. This PR fixes the decode instead. The two changes are compatible.

Python source is UTF-8 by default (PEP 3120), so `encoding="utf-8"` matches how the interpreter itself reads these files.
