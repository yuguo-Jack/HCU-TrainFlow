# [Bugfix][Core] Count only held blocks against the sliding window admission cap

[Upstream PR](https://github.com/vllm-project/vllm/pull/60045) · state: open · merged: False

## Original PR description

## Purpose

Fixes a scheduler deadlock with asynchronous KV loads (KV connectors) on models that have sliding-window or chunked-local KV cache groups.

`_request_remaining_blocks` (#44560) reserves, for every request whose KV is still loading, the blocks it will need to resume prefill, so that further loads are not admitted into that space. For recycling-aware groups the reservation is capped by `max_admission_blocks_per_request`, but the cap was compared with `len(req_to_blocks)`, and that list pads the positions outside the window with null blocks. For a request with a long computed prefix the length far exceeds the cap, the subtraction comes out negative, and the sliding-window reservation becomes zero, even though every prefill chunk still needs one slot per token in those groups. The non-fast path has the same problem through `num_skipped_blocks`.

With the reservation undercounted, loads keep being admitted until the free pool is smaller than one prefill chunk of the queue head. The head cannot allocate, `schedule()` breaks on it, and because nothing is running there is nothing to preempt: the engine sits at `Running: 0` forever.

**Observed in serving.** DeepSeek-V4-Flash (full-attention plus sliding-window KV groups with block sizes 4 and 8) served with pipeline parallelism, the CPU `OffloadingConnector` and DSpark speculative decoding, with contexts up to 1M tokens. While serving, the engine stopped at `Running: 0, Waiting: 20` and never recovered. The scheduler state, dumped from the live `EngineCore`:

- 16 requests had finished their async loads and were waiting to resume; the connector had no jobs in flight.
- The free pool held 502 blocks; the sum of the in-flight reservations was 168.
- The queue head (645,989 prompt tokens, 638,720 computed) needed 846 blocks for its next 2048-token chunk, 771 of them in the two sliding-window groups. Its reservation was 30.

**Fix.** In the capped branch, count the blocks from the first one still inside the window, capped, and subtract the real blocks the request already holds (the non-null suffix of its block table) and the real blocks among the effective prefix hits. Execution allocation is unchanged; only the reservation and the admission estimate move. The uncapped path keeps its previous arithmetic.

**Cost.** The capped branch no longer takes the running-request fast path, but `apply_admission_cap=True` is only used at admission time: by `_request_remaining_blocks` when a new async load is admitted, and by `allocate_slots(full_sequence_must_fit=True)`. Per-step allocation for running requests still uses the fast path. Inside the branch, the backward scan stops at the first null block, so it is bounded by the cap (the window plus in-flight tokens, in blocks).

### Not a duplicate

Searched open PRs and issues touching `max_admission_blocks_per_request`, `_request_remaining_blocks`, `get_num_blocks_to_allocate` and the sliding-window admission path (2026-10-05):

- #55818 caps execution allocation at the window and drops the in-flight term from the admission cap, which reverses the invariant covered by `tests/v1/core/test_swa_inflight_window_free.py` (out-of-window blocks must stay allocated until the step that reads them has been processed). This PR leaves allocation unchanged and only fixes the reservation.
- #42568 lets a queue head that cannot allocate be skipped instead of breaking. It would mask this deadlock in some shapes but does not fix the undercounted reservation.
- #50169 changes drafter grouping and pool sizing and explicitly leaves the runtime admission gate unchanged.
- #39734 is the origin of the admission cap; this PR keeps its semantics.

Second model family for this bug: Gemma 4 31B on 0.31.0, standard `SlidingWindowSpec`, no spec decode, no PP. Same undercount, and it stalls the engine.

## What we saw

Gemma 4 31B (5 sliding-window groups, window 1024, block 16; 1 full-attention group, 32-token pages), `--max-num-batched-tokens 1024`, async scheduling, `max_model_len` 32768, 2,188 GPU blocks, a KV connector with async loads (CPU offload tier).

Two returning requests with long prefixes in the CPU tier were admitted in one pass. Each took 1,006 blocks (686 full + 5 x 64 sliding). Usage hit 92% with 175 blocks free. Each then needed about 350 blocks for its next 1,024-token chunk. Neither fit. The waiting loop breaks on the first request it cannot allocate, and with `Running: 0` nothing is preempted. The log sat at `Running: 0 reqs, Waiting: 2 reqs`, 92% KV, until the client aborted about an hour later.

## Why (0.31.0 line numbers)

In `get_num_blocks_to_allocate` (`single_type_kv_cache_manager.py`), the cap is a count of held blocks (`cdiv(1023 + 2048, 16) + 1 = 193`), but `num_skipped_blocks` is a position (`(21952 - 1023) // 16 = 1308` for a 21,952-token hit). `max(193 - 1308, 0) = 0` for every sliding group. The fast path does the same against `len(req_to_blocks)`, which counts the null padding. Two callers rely on it:

- the full-sequence check in `allocate_slots` counts 719 blocks (full attention only), then allocates 1,006;
- `_request_remaining_blocks` reserves 33 blocks for the in-flight load, so the second load is admitted against 1,181 free minus 33.

```python
"""CPU-only repro: sliding-window blocks are not counted at admission for a long async (connector) prefix hit.

Uses only vLLM's KVCacheManager. No GPU, no model. Calls mirror what Scheduler.schedule() does for a waiting
request whose prefix is loaded asynchronously by a KV connector (e.g. OffloadingConnector):
  allocate_slots(..., num_external_computed_tokens=hit, delay_cache_blocks=True,
                 full_sequence_must_fit=True, reserved_blocks=<sum of _request_remaining_blocks>)

KV layout matches Gemma 4 31B: 5 sliding-window groups (block 16, window 1024) and 1 full-attention group
(block 32), 2,188 blocks in the shared pool, max_model_len 32768, --max-num-batched-tokens 1024 with async
scheduling (2 batches in flight -> max_in_flight_tokens 2048).

Run: python repro.py
"""
import torch

from vllm import SamplingParams
from vllm.utils.hashing import sha256
from vllm.v1.core.kv_cache_manager import KVCacheManager
from vllm.v1.core.kv_cache_utils import get_request_block_hasher, init_none_hash
from vllm.v1.kv_cache_interface import FullAttentionSpec, KVCacheConfig, KVCacheGroupSpec, SlidingWindowSpec
from vllm.v1.request import Request, RequestStatus

NUM_BLOCKS = 2188
PROMPT, HIT, CHUNK = 23000, 21952, 1024  # prompt tokens, tokens loaded by the connector, next prefill chunk

init_none_hash(sha256)
swa = [KVCacheGroupSpec([f"swa{g}"], SlidingWindowSpec(block_size=16, num_kv_heads=16, head_size=256,
                                                       dtype=torch.bfloat16, sliding_window=1024)) for g in range(5)]
full = KVCacheGroupSpec(["full"], FullAttentionSpec(block_size=32, num_kv_heads=4, head_size=512,
                                                    dtype=torch.bfloat16))
cfg = KVCacheConfig(num_blocks=NUM_BLOCKS, kv_cache_tensors=[], kv_cache_groups=swa + [full])
kv = KVCacheManager(cfg, max_model_len=32768, scheduler_block_size=32, hash_block_size=16,
                    max_in_flight_tokens=2048)
managers = kv.coordinator.single_type_managers
hasher = get_request_block_hasher(16, sha256)


def make_request(rid, seed):
    r = Request(rid, [seed * 100000 + i for i in range(PROMPT)], SamplingParams(max_tokens=128), None,
                block_hasher=hasher)
    r.status = RequestStatus.WAITING
    return r


def per_group_count(r, total_computed):
    """The full_sequence_must_fit count (kv_cache_manager.py:519-536), per KV cache group."""
    return [m.get_num_blocks_to_allocate(r.request_id, r.num_tokens, [], total_computed, total_computed,
                                         r.num_tokens, apply_admission_cap=True,
                                         prefill_end=r.num_prompt_tokens) for m in managers]


def per_group_held(r):
    return [sum(not b.is_null for b in m.req_to_blocks.get(r.request_id, ())) for m in managers]


def remaining(r):
    """Scheduler._request_remaining_blocks (scheduler.py:3003): the reservation for an in-flight async load."""
    return kv.coordinator.get_num_blocks_to_allocate(
        request_id=r.request_id, num_tokens=r.num_tokens, new_computed_blocks=kv.empty_kv_cache_blocks.blocks,
        num_encoder_tokens=0, total_computed_tokens=r.num_computed_tokens,
        num_local_computed_tokens=r.num_computed_tokens, num_tokens_main_model=r.num_tokens,
        apply_admission_cap=True, prefill_end=r.num_prompt_tokens)


def admit_async_load(r, reserved):
    """The waiting loop for a request with an async external hit (scheduler.py:1194-1230)."""
    out = kv.allocate_slots(r, 0, num_external_computed_tokens=HIT, delay_cache_blocks=True,
                            full_sequence_must_fit=True, reserved_blocks=reserved, has_scheduled_reqs=False)
    if out is not None:
        r.status, r.num_computed_tokens = RequestStatus.WAITING_FOR_REMOTE_KVS, HIT
    return out is not None


groups = [f"swa{g}" for g in range(5)] + ["full"]
cap = managers[0].max_admission_blocks_per_request
print(f"pool {NUM_BLOCKS} blocks; sliding-window admission cap {cap} blocks/group")
print(f"request: {PROMPT} prompt tokens, {HIT} loaded asynchronously by the connector\n")

# (a) the admission count leaves out the sliding-window groups
A = make_request("A", 1)
counted = per_group_count(A, HIT)
free0 = kv.block_pool.get_num_free_blocks()
assert admit_async_load(A, reserved=0)
held = per_group_held(A)
print("(a) request A, admission check vs allocation")
print(f"    {'group':6} {'counted':>8} {'allocated':>10}")
for g, c, h in zip(groups, counted, held):
    print(f"    {g:6} {c:8} {h:10}")
print(f"    {'total':6} {sum(counted):8} {free0 - kv.block_pool.get_num_free_blocks():10}")
print(f"    A's in-flight reservation (_request_remaining_blocks): {remaining(A)} blocks; "
      f"sliding-window part: {sum(per_group_count(A, HIT)[:5])}\n")

# (b) a second async load is admitted next to A; afterwards neither can schedule its next chunk
B = make_request("B", 2)
reserved = remaining(A)
free_b = kv.block_pool.get_num_free_blocks()
ok = admit_async_load(B, reserved)
print(f"(b) request B: free {free_b}, reserved for A {reserved} -> {'ADMITTED' if ok else 'refused'}")
print(f"    after both loads: usage {kv.usage:.1%}, free {kv.block_pool.get_num_free_blocks()} blocks")
loaded = [A, B] if ok else [A]
for r in loaded:  # loads finish (_update_waiting_for_remote_kv); requests go back to WAITING
    kv.cache_blocks(r, r.num_computed_tokens)
    r.status = RequestStatus.WAITING
results = []
for r in loaded:
    out = kv.allocate_slots(r, CHUNK, full_sequence_must_fit=True, has_scheduled_reqs=False)
    results.append(out is not None)
    print(f"    {r.request_id}: next {CHUNK}-token chunk -> {'allocated' if out is not None else 'REFUSED'}")
if not any(results):
    print("    STALL: no waiting request can schedule; with nothing running, nothing is preempted or freed.")
```

## Under load

The stall above came from a Gemma 4 replay through our own async-load offload connector. Since we applied this diff to 0.31.0, we have run 8 replays of about an hour each (7 on Gemma 4 31B, 1 on Qwen3.8-27B; four KV-offload setups, 1x RTX PRO 6000). None stalled on admission.

Checked `main` at fabaecbfa5 (2026-10-12): the code is unchanged there, so the bug is live on main.

A separate hardening, not needed for this fix: when nothing is running, the waiting loop could preempt or defer a waiting request that holds blocks from a finished async load, so an undercount anywhere cannot wedge the engine (#42568 is related).
