# [Bugfix][LoRA] Avoid block_n=128 for lora_expand on Hopper

[Upstream PR](https://github.com/vllm-project/vllm/pull/48638) · state: open · merged: False

## Original PR description

block_n=128 triggers a NaN-producing Triton codegen bug in the single-slice lora_expand kernel on sm_90, garbling LoRA output. Blackwell isn't affected, so drop to block_n=32 on Hopper only.

Fixes #48590.

Co-authored-by: Claude

- BeichenHuang · COMMENTED · 2026-10-15T20:48:17Z · [source](https://github.com/vllm-project/vllm/pull/48638#pullrequestreview-5539713995)

Thanks for tracking this down! I dug into the root cause (details in [my comment on #48590](https://github.com/vllm-project/vllm/issues/48590#issuecomment-6201927209)). It's triton-lang/triton#9433: ptxas older than 13.3 reuses the A registers of an in-flight register-A wgmma when the loop is pipelined. Given that, I have a few concerns about using `block_n=32` as the fix:

1. **It works by accident.** `block_n=32` still pipelines a register-A wgmma. ptxas happens to serialize the wgmmas for that tile shape (advisory C7515), which hides the hazard. Other shapes with the same `num_stages=2, num_warps=4` still fail, e.g. `block_n=64` at R=128. A different rank, `BLOCK_K` or Triton codegen change could bring the bug back.
2. **Performance.** It is about 2× slower on prefill-sized batches, including ranks that were never affected. Single-slice expand, H=4096, fp32 input, µs on H20:

   | R | T | main | this PR | `num_stages=1` |
   |---|---|---|---|---|
   | 16 | 8192 | 82.7 | 141.0 | 82.6 |
   | 64 | 8192 | 79.1 | 161.0 | 86.7 |
   | 128 | 8192 | 101.8 | 210.1 | 122.9 |

3. **Tuned configs bypass it.** Configs loaded from `VLLM_TUNED_CONFIG_FOLDER` are returned unchanged, so a tuned `num_stages≥2` entry brings the bug back.
4. **No test.** The repro in #48590 uses bf16 inputs, which never fail. The existing expand tests only use fp16/bf16 inputs, while the model path uses fp32 (`CAST_TYPE`), so this fix isn't covered.

I've opened #61906. It forces `num_stages=1` for the fp32-input path on SM90, which is structurally safe and applies after config selection. It also adds an fp32-input regression test that fails on main (8/36) and passes with the fix. Happy to coordinate: we could fold it into this PR or close one of the two, whichever you and the maintainers prefer.
