# [Bugfix][PCP][Spec Decode] Fix MTP with PCP decode sharding and CUDA graphs

[Upstream PR](https://github.com/vllm-project/vllm/pull/62998) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Fixes MTP speculative decoding under MRV2 PCP with round-robin decode sharding (DCP=1). On main it produces wrong outputs in eager mode, and it crashes when capturing CUDA graphs now that #62377 allows decode-only full graphs for DSv3.2/GLM-5.2/5.3.

## Claims

- PCP + MTP outputs are correct: GLM-5.3-NVFP4 TP1 × PCP4 + EP with MTP3 scores GSM8K 0.857–0.882 on main and 0.907 with this PR (TP4 + MTP3 reference: 0.914).
- `FULL_AND_PIECEWISE` CUDA graphs work with PCP + MTP: GSM8K 0.902 / 0.911 (2 runs), acceptance length 3.32, matching TP4.

## Validation

GLM-5.3-NVFP4 on 4×B300, `VLLM_USE_V2_MODEL_RUNNER=1 vllm serve ... -tp 1 -pcp 4 --enable-expert-parallel --kv-cache-dtype fp8 --max-num-seqs 64 --speculative-config '{"method":"mtp","num_speculative_tokens":3}'`. Eval: GSM8K, 1319 questions, 5-shot, greedy, concurrency 64. "main" is main @ 82a24bb82d + #62377; this PR was run rebased on 0d34366b14.

| Config | cudagraph_mode | GSM8K | Mean acceptance length |
|---|---|---|---|
| TP4 + MTP3 (reference) | FULL_AND_PIECEWISE | 0.914 | 3.32 |
| PCP4 + MTP3, main | NONE | 0.857 / 0.870 / 0.882 (3 runs) | 3.18 |
| PCP4 + MTP3, main | FULL_AND_PIECEWISE | crashes in draft prefill capture | – |
| PCP4 + MTP3, this PR | NONE | 0.907 | 3.32 |
| PCP4 + MTP3, this PR | FULL_AND_PIECEWISE | 0.902 / 0.911 (2 runs) | 3.32 / 3.31 |
| PCP4 + MTP3 `draft_sample_method=probabilistic`, temperature 0.6, this PR | FULL_AND_PIECEWISE | 0.901 | 3.29 |

`pytest tests/v1/worker/test_gpu_pcp_manager.py tests/v1/worker/test_gpu_target_dependent_ar_speculator.py`: 123 passed. No new unit tests: the failures need multi-rank PCP with graph capture, so they are covered by the GSM8K runs above (CI has no PCP + MTP model job).

## Details

- **Draft divergence (eager accuracy):** under decode sharding, each request's target hidden states come from its owner rank, and every rank samples the full batch. Draft decode steps run replicated on every rank, but they are not bitwise identical across ranks: in a debug run, 0% / ~0.1% / ~1.7% of rows differed at draft positions 0 / 1 / 2. Ranks then verified different drafts, and `num_sampled` diverged. The fix broadcasts the draft tokens from PCP rank 0 at the end of `propose`; with `draft_sample_method=probabilistic` it also broadcasts the batch's draft-logit rows. The source of the cross-rank numeric difference is not identified; the broadcast keeps verification consistent regardless.
- **Draft prefill graphs:** draft prefill runs on the rank-local PCP batch. Capture now stages that batch through the `PCPManager`, and capture and replay both read the `PCPManager` input buffers. Before this, capture read the speculator's buffers, so replay saw stale inputs (acceptance length ~1.4 at concurrency 64). Draft prefill also uses the mixed mode (piecewise) under PCP, because it all-gathers rank-local hidden states with a per-step partition.
- All changes are confined to the target-dependent AR (MTP/EAGLE) speculator; `PCPManager` and the model runner are unchanged. #61994 adds the same kind of broadcast in the DFlash speculator.
