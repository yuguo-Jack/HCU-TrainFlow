# [Bugfix][Kernel][MoE] Zero-expert identity kernel silently drops output for hidden_dim not a multiple of 256

[Upstream PR](https://github.com/vllm-project/vllm/pull/49087) · state: open · merged: False

## Original PR description

## Purpose

**Bug: the zero-expert (identity) MoE kernel silently returns wrong output whenever
`hidden_dim` is not a multiple of 256.**

`zero_experts_compute_triton` / `compute_identity_kernel` in
`vllm/model_executor/layers/fused_moe/fused_moe.py` compute, per token,
`out[t] = hidden_states[t] * sum_k(zero_expert_scales[t, k])`. The kernel is launched on a
**floor-division** grid:

```python
grid = lambda meta: (num_tokens * (hidden_dim // meta["BLOCK_SIZE"]),)   # BLOCK_SIZE = 256
```

and the kernel recovers `(batch_id, dim_offset)` from that same floor division. So:

- For `hidden_dim` **not** a multiple of 256, the **tail block is never launched**. Those
  elements are returned as `0` instead of a scaled hidden value. The output looks
  plausible — there is no error, no NaN, just a silently truncated row. It is masked today
  only because the output happens to be allocated with `torch.zeros_like`.
- For `hidden_dim < 256`, the grid is `num_tokens * 0 = 0`: the kernel **never runs at all**
  and the entire output is zeros.

The bug is currently baked into the test suite as an assumption
(`hidden_size must be >= 256 ... BLOCK_SIZE=256 causes grid=0 when hidden_dim<256`) rather
than being fixed.

This path is reachable in-tree: `FusedMoEFactory` wires it through
`vllm/model_executor/layers/fused_moe/router/zero_expert_router.py`
(`ZeroExpertRouter._compute_routing`) for `zero_expert_type="identity"` models such as
LongCat-Flash / DeepSeek-style MoE.

### Fix

Launch a **2-D ceil-div grid** `(num_tokens, triton.cdiv(hidden_dim, BLOCK_SIZE))` — axis 0
is the token row, axis 1 a `BLOCK_SIZE`-wide column tile:

```python
batch_id   = tl.program_id(0)
dim_offset = tl.program_id(1) * BLOCK_SIZE
offs = dim_offset + tl.arange(0, BLOCK_SIZE)
mask = offs < hidden_dim
```

The ceil-div covers the full hidden dimension for **any** `hidden_dim`, and the existing
`offs < hidden_dim` mask guards the partial tail block. Because axis 0 now ranges exactly
over `[0, num_tokens)`, the old `pid` integer decode and the `batch_id >= num_tokens` guard
become unreachable and are removed (which also leaves `num_tokens` unused as a kernel
argument, so it is dropped from the signature and the single call site — it still sizes grid
axis 0 in the wrapper).

Semantics are otherwise unchanged: same fp32 `top_k` scale reduction, same output dtype,
same public entry point and signature for `zero_experts_compute_triton`.

**Secondary cleanup, enabled by the fix:** the output was allocated with
`torch.zeros_like(hidden_states).to(hidden_states.device)`. Now that the grid provably
covers every element, the zero-init is a redundant full-tensor HBM write on a purely
memory-bound op, and the trailing `.to(device)` is a no-op — so this switches to
`torch.empty_like`. Note the two changes are **coupled**: `empty_like` is only safe *because*
the grid was fixed to cover the tail; on `main`'s floor-div grid it would turn the dropped
tail from silent zeros into uninitialized garbage.

A dead 1-D `grid` lambda (and the `N` it read) at the top of `zero_experts_compute_triton`
is also removed: it was already overwritten before any use, and once the identity launch
became 2-D, keeping it failed `mypy` (incompatible tuple arity on reassignment) and then
`ruff` F841.

## Test Plan

```bash
pytest tests/kernels/moe/test_zero_expert_moe.py::test_zero_expert_identity_kernel_covers_all_dims -v
```

`tests/kernels/moe/test_zero_expert_moe.py` gains
`test_zero_expert_identity_kernel_covers_all_dims`, which drives
`zero_experts_compute_triton` directly against a plain-PyTorch fp32-reduce reference across
the full matrix `hidden_dim ∈ {200, 257, 300, 768, 1000, 4096, 7168}` (note the
non-multiples of 256 and the sub-256 case) × `num_tokens ∈ {1, 7, 128}` × `top_k ∈ {2, 8}`
— 42 cases.

Routing is deterministic rather than random: row `r` gets `1 + (r % top_k)` zero-expert
slots with strictly positive scales, so every row — including the `num_tokens=1` case —
routes at least one zero expert and a dropped tail block is always distinguishable from the
reference. Multi-row cases also include one all-normal row, which verifies the kernel
explicitly *writes* zeros rather than relying on pre-zeroed output memory (the property
`empty_like` depends on). The obsolete `hidden_size >= 256` comment in the fixture is removed.

Performance is measured with a standalone before/after microbenchmark (torch + triton, one
GPU), `torch.allclose` against the fp32-reduce PyTorch reference; speedup =
`before_ms / after_ms`, CUDA-event median of 50 iters × 5 repeats.

Run on **A100-SXM4-80GB** and **NVIDIA H100 80GB HBM3**, torch 2.12 / triton 3.7.

### Performance

Fixing the grid is the point of this PR; the `empty_like` change also makes the op faster,
which is a bonus rather than the motivation.

**Production shapes are bit-for-bit unchanged.** LongCat-Flash / DeepSeek use
`hidden_dim ∈ {4096, 7168}`, both multiples of 256, so before/after outputs are identical
there — on those shapes the diff is purely a memory-traffic reduction, and no model-eval
regression is possible.

## Notes

- **Scope.** The larger per-call overhead the wrapper carries elsewhere
  (`expert_scales.clone()` + boolean masking before the kernel) is intentionally left
  untouched to keep this focused on the bug.
- **Pre-existing assumption, unchanged:** the kernel indexes `batch_id * hidden_dim`, i.e.
  it assumes `hidden_states` is contiguous with row stride `== hidden_dim`. That assumption
  is identical before and after this PR; this change neither introduces nor fixes it.
- Not a duplicate: `gh pr list --repo vllm-project/vllm --state open --search
  "compute_identity_kernel"` and `--search "zero_experts_compute_triton in:body"` return no
  other open PR touching this kernel.
- `pre-commit run --files <changed files>` is clean (ruff, ruff-format, mypy-3.10 and the
  rest of the hook set).
