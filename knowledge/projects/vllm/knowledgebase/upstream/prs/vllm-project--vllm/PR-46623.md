# [Model] Add LongCat-Next multimodal model support

[Upstream PR](https://github.com/vllm-project/vllm/pull/46623) · state: open · merged: False

## Original PR description

Closes #46620

## Summary

This PR adds support for [LongCat-Next](https://huggingface.co/meituan-longcat/LongCat-Next), a unified multimodal model from Meituan that supports text, audio, and video modalities.

The model uses:
- **Language model**: LongCat-Flash (MoE with MLA attention)
- **Audio encoder**: Whisper-style encoder
- **Visual encoder**: Qwen2.5-VisionTransformer variant

This PR reuses existing vLLM components following established patterns from 8+ models that subclass `WhisperEncoder` (ultravox, kimi_audio, minicpmo, voxtral, etc.).

---

## Why MoE Changes Were Needed

LongCat-Next uses LongCat-Flash as its language backbone, which has two unique requirements:

### 1. Extended Vocabulary with Tensor Parallelism

LongCat-Next has an **extended vocabulary** (vocab_size=282,624) that includes special codec tokens for audio/image/video processing. When using tensor parallelism (TP>1):
- Each GPU holds only a shard of the vocabulary (e.g., 141,312 tokens per GPU with TP=2)
- But multimodal token IDs can be in the full range (up to 282,624)

**Fix in `vllm/model_executor/layers/utils.py`:**
The `scatter_add_` operation in `get_token_bin_counts_and_mask()` was accessing out-of-bounds indices when token IDs exceeded the per-shard vocab size. The fix clamps token IDs to `[0, vocab_size]` before the scatter operation. Tokens >= vocab_size land in a padding bin and are safely discarded.

This prevents CUDA crashes when processing audio/image/video concurrently with TP>1.

### 2. Zero Expert Architecture

LongCat-Flash uses a **zero expert** architecture where certain tokens (e.g., special multimodal tokens) need to bypass normal MoE routing and be processed differently.

**Fix in `vllm/model_executor/layers/fused_moe/runner/moe_runner.py`:**
Instead of modifying router return types (which would break compatibility with upstream), we use a **property getter pattern**:
- `ZeroExpertRouter` computes the zero expert output and stores it as a property
- `MoERunner.forward()` retrieves it via `getattr(self.router, "zero_expert_output", None)`
- If present, the zero expert output is added to the final result

This approach:
- Maintains backward compatibility with upstream 2-tuple router design
- Only affects LongCat-Next (other routers return `None`)
- Clean separation of concerns

---

## Why `whisper.py` Changes Were Needed

LongCat-Next's audio encoder requires **variable-length sequence masking** - different audio samples in a batch can have different lengths, and padded positions must be zeroed out after encoding.

The original `WhisperEncoder` didn't support passing `cu_seqlens` (cumulative sequence lengths) through the encoder stack, which is required for:

1. **FlashAttention variable-length masking**: Instead of additive attention masks (O(n²) memory), we use `cu_seqlens` to tell FlashAttention the actual length of each sequence in the batch
2. **Proper position embedding**: Each audio sample needs position embeddings relative to its own start, not the batch start

Changes made:
- Threaded `cu_seqlens` parameter through `WhisperEncoder.forward()` → `WhisperEncoderLayer` → `WhisperAttention`
- Updated `LongcatNextWhisperEncoder` subclass to compute and pass `cu_seqlens` based on `output_length`

---

## Why `qwen2_5_vl.py` Changes Were Needed

LongCat-Next uses `Qwen2_5_VisionTransformer` for visual encoding but **does not need the merger module**. The merger is designed to compress visual tokens for language model consumption, but LongCat-Next processes visual features directly with its own projection.

Previously, the code created the merger then deleted it after construction - wasteful and unclear. The fix adds a `skip_merger=True` parameter to `Qwen2_5_VisionTransformer.__init__()` that:

1. **Skips merger construction entirely** - saves GPU memory
2. **Makes intent explicit** - clearer than "create then delete"
3. **Follows existing patterns** - similar to how other models have optional components

## 代码检视 — LongCat-Next multimodal model support

感谢这个 PR！整体架构清晰，对 MoE router 的重构方向正确。以下是基于 diff 的一些观察和疑问，供参考。

### ✅ 写得好的地方

1. **移除了 `ZeroExpertRouter` 的可变实例状态** (`zero_expert_router.py`)：将 `self._zero_expert_output`（通过 property "取后即清" 的副作用模式）改为从 `_compute_routing` 显式返回。这让数据流更清晰，对 `torch.compile` 更友好，是一个好的设计改进。

2. **移除了重复赋值** (`fused_topk_bias_router.py`): 删除了 `self.scoring_func = scoring_func` 的重复行。

3. **whisper.py 的参数透传是正确的**：`WhisperEncoderAttention` 调用 `super().forward(..., cu_seqlens=, max_seqlen=, sequence_lengths=)`。已确认父类 `MMEncoderAttention.forward_native/forward_cuda/forward_cpu/forward_xpu` 均已接受这三个参数，所以这只是把原本被丢弃的参数正确传递下去，向后兼容。

### ⚠️ 需要确认的点

4. **`mutates_args` 声明变更** (`moe_runner.py`, `_moe_forward` 自定义算子):
   ```python
   -    mutates_args=["hidden_states"],
   +    mutates_args=[],
   ```
   这是 `torch.compile` 正确性相关的关键改动。请确认 `_forward_impl` 及其下游（`_maybe_apply_shared_experts`、`forward_monolithic` 等）确实不再就地修改入参 `hidden_states`。如果存在任何就地写入路径而 `mutates_args` 未声明，`torch.compile` 下会出现静默的正确性 bug。建议补充一条针对 `torch.compile` 路径的测试。

5. **`_maybe_combine` 返回 tuple 时的 `torch.stack`** (`moe_runner.py` `_forward_impl`):
   ```python
   combined = self._maybe_combine(shared_output, hidden_states)
   if isinstance(combined, tuple):
       combined = torch.stack(combined, dim=0)
   return [combined.clone(), zero_expert_output.clone()]
   ```
   当 `_maybe_combine` 返回 tuple 时，`torch.stack(..., dim=0)` 会新增一维（变成 `[2, ...]`）。而此前是 `return self._maybe_combine(...)` 直接返回 tuple。请确认这条 tuple 分支的实际触发场景，以及上层 `result = result_list[0]` 拿到的形状是否符合预期——这里看起来存在形状语义变化的风险。

### 📌 影响范围较广，建议讨论

6. **`utils.py` `get_token_bin_counts_and_mask` 的 token 钳制**：
   ```python
   clamped_tokens = tokens.clamp(max=vocab_size)
   bin_counts.scatter_add_(1, clamped_tokens, torch.ones_like(clamped_tokens))
   ```
   这个改动对**所有**使用该函数的模型生效，而非仅 LongCat-Next。此前 token 越界会直接报错（暴露 bug），现在会被静默吸收到 padding bin 丢弃。对 LongCat-Next 的 codec token（可达 282624）是必要的，但是否希望对其他模型也静默吞掉越界 token？建议至少在 debug 日志里记录被钳制的 token 数量，或考虑将行为限定到需要的模型，避免掩盖其他模型的潜在问题。

### 🔎 小问题

7. **`qwen2_5_vl.py` 的 substring 匹配** (`load_weights`):
   ```python
   if self.skip_merger and "merger" in name:
       continue
   ```
   `"merger" in name` 是子串匹配，可能误伤路径中恰好含 `merger` 的其他权重。范围足够小的话影响有限，但更精确的匹配（如 `name.startswith(f"{prefix}.merger")`）更稳妥。
