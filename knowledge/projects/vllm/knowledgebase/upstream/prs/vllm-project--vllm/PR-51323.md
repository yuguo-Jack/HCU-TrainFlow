Built from source at 5a1cec5ee8 against torch 2.11.0+cu130 and flashinfer 0.6.16.post3, TORCH_CUDA_ARCH_LIST=12.0a.

Two quick bugs in the branch first...

- current head doesn't build: hisparse_kernels.cu:392 uses `stats` but nothing declares it in that kernel, I assume it belongs to the metrics PR. I deleted the block to get past it.
- with hisparse disabled entirely, warmup crashes at compressor.py:414 with AttributeError: 'DeepseekV4IndexerCache' object has no attribute 'hisparse_cache'. The None check is already on the next line, so a getattr with a None default fixes it.

Didn't get to actual perf numbers though, and it's not this PR's fault...  V4 on SM120 doesn't really work on stock main. The indexer decode path (fp8_fp4_paged_mqa_logits / get_paged_mqa_logits_metadata) only has the DeepGEMM implementation on CUDA, and DeepGEMM's attention API bails with "Unsupported architecture" on SM120 (apis/attention.hpp:227). That was the end of the road for me. Everything I hit before that, in order, in case anyone else tries this:

- DeepGEMM SF transform assert in FP8 weight postprocessing (layout.hpp:60). VLLM_USE_DEEP_GEMM=0 gets past it.
- mhc_pre_broadcast_tilelang calls tf32_hc_prenorm_gemm unconditionally. The other two mhc_pre functions guard on is_deep_gemm_supported() and fall back to tilelang, this one just doesn't (hyperconnection.hpp:56, same unsupported-architecture assert). Added the missing guard plus a torch fallback per the docstring contract.
- cutlass blockwise fp8 dense linear rejects the shape at dispatch (scaled_mm_helper.hpp:17). --linear-backend triton works.
- ...but then the triton kernel chokes on float8_e8m0fnu weight scales (KeyError in triton's dtype canonicalization). Widened the scales to fp32 after load, lossless since ue8m0 is just powers of two.
- deep_gemm_fp8_o_proj: the recipe helper treats cap.major >= 10 as SM100 and fp8_einsum asserts on layout (layout.hpp:39, t.dim() == N). Swapped in the ROCm bf16 reference path (rocm_inv_rope_einsum), which turns out to be platform-neutral and runs fine on CUDA.
- indexer decode logits, see above. No workaround short of writing a kernel.

All the local fixes were single-file volume mounts over the image, happy to share diffs if useful. With them the engine gets through weight load, the profiling pass and KV sizing (218,471 tokens at gmu 0.96, max-model-len 131072, fp8 kv cache) and dies in the indexer warmup.

If an SM120 path for the indexer logits shows up (the flashinfer sparse-MLA-SM120 work?), I'll run the no-offload vs host_pool_gib A/B at C=1/4/8 on this box. PCIe-only host links should be a decent worst case for the interactivity question. The #41834 fork runs this model on SM120 today with triton sparse-MLA kernels, so that might be the shortest path for consumer-Blackwell HiSparse testing.

Ok so I looked through it a bit more and I think this is a non-issue for HiSparse. `skip_topk_buffer_clear=False` means these positions are just -1 rather than stale indices and HiSparse just masks off -1's in `hisparse_swap_in_kernel`

But the whole principle of HiSparse is that the same tokens get repeatedly attended to anyway (like 99% cache hit rates at cache size 4096 for topk 2048), so it's honestly likely that the "stale" token would already be loaded anyway.
