# [KV cache] Add an mxfp4 kv_cache_dtype

[Upstream PR](https://github.com/vllm-project/vllm/pull/64358) · state: open · merged: False

## Original PR description

## Overview

Adds `kv_cache_dtype="mxfp4"` for a non-MLA KV cache: E2M1 data with one E8M0 scale per 32 elements (OCP MX), stored as `uint8`.

- `CacheDType` gains `"mxfp4"`, and `STR_DTYPE_TO_TORCH_DTYPE` maps it to `torch.uint8`.
- `KVQuantMode.MXFP4 = 17` (15 is `MXFP4_DS_MLA` in #64120, and 16 is used by another open MXFP4 PR), returned by `get_kv_quant_mode("mxfp4")`, with an `is_mxfp4` property. It is its own mode, not `CUSTOM`, so backends can key on it like `NVFP4`.
- `mxfp4_kv_cache_full_dim(head_size)` gives the packed bytes per head: `head_size / 2 + head_size / 32`, which is 68 for 128. Unlike `nvfp4_kv_cache_full_dim` (72 for 128), there is no global scale.

## Motivation

MiniMax-M3.1 on MI355X (gfx950) can decode from an MXFP4 KV and index cache using the native `V_MFMA_SCALE_F32_*_F8F6F4` instructions, which take E8M0 per-32 scales. That's 204 B per token and layer, against 216 B for NVFP4. An accuracy check that rounds K, V and index-K to MXFP4 on today's FP8 path showed no significant loss against the NVFP4-KV baseline (paired exact McNemar, seed 42):

| Bench | NVFP4 KV | MXFP4 KV (emulated) | p |
|---|---|---|---|
| GSM8K (1319) | 94.31% | 94.31% | 1.0 |
| GPQA-Diamond (198) | 80.30% | 83.33% | 0.39 |
| RULER NIAH multikey-2 32k (50) | 100% | 100% | 1.0 |

## Stack

This is the bottom of a stack; the first consumer is the MiniMax-M3 MXFP4 page writer, which is stacked on #63232. Readers and the backend that selects this dtype follow in later PRs. Until then nothing selects `"mxfp4"`.

## Validation

`tests/config/test_kv_cache_dtype.py::test_mxfp4_kv_cache_dtype` covers the dtype name, `CacheConfig`, the torch dtype, the quant mode and its properties, and the 68-byte full dim. It passes on CPU.
