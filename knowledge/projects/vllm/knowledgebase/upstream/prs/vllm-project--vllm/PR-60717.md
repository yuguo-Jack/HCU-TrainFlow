# [ROCm][Kimi-K3] Use vLLM's FP8 max in the fused AttnRes quantization

[Upstream PR](https://github.com/vllm-project/vllm/pull/60717) · state: closed · merged: True

## Original PR description



## Overview

Fixes `test_amd_attn_res_fp8_preserves_prefix_and_quantized_output` on MI300 (fnuz FP8), which has failed since #59069 landed.

## Claims

- The fused AttnRes per-token FP8 quantization now uses `get_fp8_min_max()` (224 on fnuz) instead of `torch.finfo(dtype).max` (240), matching vLLM's `QuantFP8` and the unfused path before #59069. MI355 (OCP `e4m3fn`, 448 either way) is unchanged.
- The test's FP8 code-distance check orders codes by value, so a midpoint step across zero (`0x00` vs `0x81`) counts as one step rather than 129.

## Validation

MI300X (gfx942), AMD CI test image for #58761 (`rocm/vllm-ci:build-01a11cfd-…`, ROCm 10). Both changed files are identical on main.

| `pytest models/kimi_k3/test_amd_attn_res.py` | Result |
|---|---|
| main | 3 failed, 13 passed (same 3 cases as CI) |
| kernel fix only | 1 failed (`[320-8-False-False]`, the zero-crossing case) |
| kernel + test fix | 16 passed |

The MI300 Kimi K3 CI job's full test set (`test_amd_attn_res.py test_amd_kda_decode.py test_kda.py test_kda_metadata.py`) passes: 139 passed, 30 skipped. I did not run an end-to-end Kimi-K3 eval (no checkpoint or hardware here). On MI300 this restores the 224 scale convention that `QuantFP8` used before the fusion.

## Details

On fnuz, every scale the fused kernel produced was 240/224 of `QuantFP8`'s (relative diff exactly 1/15). The remaining failure was a value at the rounding midpoint near zero (−0.000484 vs midpoint −0.000488): the kernel quantizes its fp32 result, the reference quantizes the bf16-rounded one, so they land on adjacent codes on opposite sides of zero.

Not a duplicate: no open PR changes this. #58861 touches the same `QUANT_MAX` line as context and will need a trivial rebase.
