# [Build][KV Connector] Validate PyTorch family after dependency install

## Original PR description

## Purpose

Follow-up to #57945. Related to #56829.

#57945 fixed CUDA 12 KV connector dependency selection and constrained the installed Torch/CUDA stack. This PR adds focused post-install build guards:

- verify `torch`, `torchvision`, and `torchaudio` still match the versions selected when vLLM was built;
- verify `torch`, `torchvision`, `torchvision.ops`, `torchaudio`, and `vllm` can be imported after KV connector installation.

A Dockerfile contract test keeps these guards and the existing constraint paths in place. This follows the merged resolver fix rather than duplicating it; the remaining diff changes only the post-install guards and their contract test. Open PR searches for #56829 and PyTorch-family guards found no competing follow-up.

The full-environment `uv pip check --system` gate was dropped because the official cu129 image contains unrelated or intentional dependency divergences, including the NCCL override. A global consistency check is too broad for this Torch-family invariant. The stronger `_C_stable_libtorch` import is also outside this build gate because it requires the NVIDIA driver library, which is absent on the driver-less CPU runner used below.

AI assistance: OpenAI Codex assisted with the focused build guards, contract tests, and CPU-only image validation. I reviewed the changes and am responsible for the implementation and validation.

Minimal import reproducer against that immutable image:

```bash
docker run --rm --platform linux/amd64 --entrypoint python3 \
  vllm/vllm-openai@sha256:94b8353e862813ca39efe0054f05bc453c0244fee48f90dc080e99b9cb09669c \
  -c 'import torch; print(torch.__version__, torch.version.cuda); import torchvision'
```

Our original execution was inside a Kubernetes container using this exact digest. `import torchvision` failed with `RuntimeError: operator torchvision::nms does not exist`. Loading `torchvision/_C.so` through `torch.ops.load_library()` exposed:

```text
undefined symbol: _ZN3c104cuda29c10_cuda_check_implementationEiPKcS2_jb
```

Layer isolation: removing the original optional-KV-connectors layer (`sha256:98a7009c347a9720dd60a464f6b2eb451c837b4abd3edd806dc0e83c8f7d5b5b`) restored `torch 2.13.0+cu129`, `torchvision 0.28.0+cu129`, and `triton 3.7.1`. We then restored only the original image's NIXL 1.4.1 distributions for the connector under test; its runtime selected `nixl_cu12._api`. The remaining original filesystem layers were retained. No vLLM source change was needed for this dependency workaround.

The resulting image passed actual imports of `torch`, `torchvision`, `vllm._C_stable_libtorch`, `vllm.engine.arg_utils.EngineArgs`, and `nixl._api.nixl_agent`. It also loaded the model and served ordinary/streaming requests in subsequent NVIDIA H800 deployments, including real NIXL PD transfer.

These results validate the dependency diagnosis and our downstream workaround, **not this PR's current head**. In particular, the workaround retained only the NIXL connector scope we tested; it is not a substitute for the PR's complete dependency-consistency/import checks or other connector validation. Import checks were performed in zero-GPU diagnostic Pods; inference validation used GPUs.

Sharing this evidence to add the affected release digest and support fixing the dependency invariant in the upstream build rather than maintaining downstream layer surgery. This comment was prepared with AI assistance from recorded test artifacts.
