# [MoE] Add MoNe experts pruning support

[Upstream PR](https://github.com/vllm-project/vllm/pull/50415) · state: closed · merged: True

## Original PR description

## Purpose

Mixture of Novices and Experts (MoNe) is an expert pruning method accepted at ICLR-2026 https://arxiv.org/pdf/2507.00390
 
The method computes statistics (access frequency and output variance) about experts during calibration, identifies redundant experts and replaces them with constant vectors which are their unbiased estimators. MoNe is planned to be supported in the llm-compressor https://github.com/vllm-project/llm-compressor/pull/2906 

Implementation
- Defines a generic expert-substitution format in compression_config.
- Supports constant-v1, where a substituted expert returns a stored constant vector while keeping its original router weight.
- Automatically detects compatible MoE layers and loads only retained expert weights, preserving the GPU memory saving.
- Provides a default path for compatible decomposed MoE backends by sending substituted routes with zero weights.
- Validates checkpoint metadata and tensor loading, including tensor-parallel correctness.
Models using the standard FusedMoEFactory and RoutedExperts loading path do not need architecture-specific changes.

Hi @vadiklyutiy thank you! 

I would say it is possible to support stadardised MoE models and most of backends using a non-optimised execution. This still gives a memory win. On top of that it is possible to further optimise specific backeds to make them faster.

Here is the proposal:


For models, `FusedMoEFactory` would automatically discover substitution metadata using the module prefix it already receives. Generic loading and validation hooks would handle the substitution tensors. This should make the feature work by default for most models using the standard fused-MoE path, without modifying each model implementation.

For backends, a generic adapter would run after routing. It would compute the constant contribution, map retained logical experts to compact physical IDs, and replace substituted routes with valid IDs carrying zero weights. Most decomposed MoE backends could then execute the result without knowing anything about expert substitution.

This default path would be correct but might still execute unnecessary GEMMs for the zero-weight routes. The current Triton implementation would demonstrate an optimized path: it recognizes and removes those routes before scheduling GEMMs. Other backends could add the same optimization later, but it would not be required for correctness or initial model support.

Would a generic default path for most models and decomposed backends, with Triton as the first optimized implementation, address your concerns?

> @ieBoytsov, here, I think, it makes sense to specify clearly what are the conditions for the models to work as is with substituted weights? This might help us understand if PR could be improved here.

@milakov I think a model should work without model-specific substitution code when:
- It constructs its routed experts through `FusedMoEFactory` with a module prefix that can be matched to a configured substitution target.
- Its router produces standard logical top-k IDs and weights with router weights applied to expert outputs.
- The substitution value is in the same output space and uses the same scaling semantics as the routed experts.
