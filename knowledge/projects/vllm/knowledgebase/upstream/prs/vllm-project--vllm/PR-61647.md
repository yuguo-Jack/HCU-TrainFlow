# [Bugfix] Engage indexer TP row sharding on total rows, not per-rank rows

[Upstream PR](https://github.com/vllm-project/vllm/pull/61647) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

> This PR description was written by @ZJY0516.

## Overview

Follow-up to #54951, addressing https://github.com/vllm-project/vllm/pull/54951#discussion_r4267244007: gate the sparse-indexer TP row sharding on **total** scheduled prefill rows instead of per-rank rows, so the 8xH100 TP8 recipe can actually engage it. The floor becomes `AttentionConfig.indexer_tp_shard_min_rows` (default 65536).

Not a duplicate: no other open PR changes how this floor scales with TP. #60601 lowers the same floor on ROCm only; whichever lands second needs a rebase.

## Claims

- TP8 engages row sharding at `--max-num-batched-tokens 65536`; before, it needed 131072, which OOMs on 80 GB Hopper.
- −34.1% mean TTFT on a 1.02M-token prompt at TP8 under an H100-equivalent memory budget.
- TP4 engagement point unchanged (64K total rows). TP2 moves from 32K to 64K total rows by design.
- The floor is configurable, e.g. `-ac '{"indexer_tp_shard_min_rows": 131072}'`.

## Validation

**Problem reproduced** on 8xH200 with an 80 GB-equivalent budget (`--gpu-memory-utilization 0.56`, TP8, BF16 KV, merged-commit build `3e8e1364`):

| Config | Result |
|---|---|
| `--max-num-batched-tokens 131072` | engine init fails: `Available KV cache memory: -6.94 GiB` |
| `--max-num-batched-tokens 65536` | server healthy, but a 70K-token request schedules `num_rows=65536 < threshold=131072` on every chunk → **0 engagements** |

**TTFT at the H100 budget** (8xH200, `--gpu-memory-utilization 0.568` ≈ 81,662 MiB/card vs H100's 81,559 MiB), TP8, `--max-num-batched-tokens 65536`, `--max-model-len 1048576`, FP8 KV, `FLASH_ATTN_MLA_SPARSE`, streaming completions with one request in flight; only the floor differs between arms:

| Prompt | row-sharded (default) | replicated (floor = 2,000,000) | Δ mean TTFT |
|---|---|---|---|
| 1.02M tok (n=2) | **31.57 s** | 47.92 s | **−34.1%** |

The replicated arm was measured with an earlier revision's `VLLM_INDEXER_TP_SHARD_MIN_ROWS=2000000`; the equivalent now is `-ac '{"indexer_tp_shard_min_rows": 2000000}'`. The gain grows with context depth (0.48 s saved at 255K vs 16.35 s at 1.02M): per-row indexer cost ramps with causal depth while the per-row exchange cost stays constant.

**Tests**

- `pytest tests/v1/attention/test_indexer_tp_row_shard.py`: 12 passed (TP8 parametrization, total-not-per-rank floor, TP2 32K–64K window stays replicated, floor never below `tp_size`).
- End-to-end serve + long-context completions on TP8 at the H100-equivalent budget; engagement verified via NCCL coll logging, outputs sane.

## Details

Per rank, the saved replicated indexer work (`~ (1 - 1/tp) * rows`) and the `all_gatherv` index traffic (`~ (tp - 1)/tp * rows * topk * 4B`) both scale with `(tp - 1)/tp`, so the engagement crossover in total rows is tp-independent to first order. The old per-rank floor grew the total requirement linearly with `tp`. 65536 is the TP4-calibrated total floor from #54951.

- TP2 now engages later (64K instead of 32K total rows); the exchange's fixed latency term is largest at small `tp`.
- `balanced_prefill_row_shard` takes the floor as an argument and clamps it to at least `tp_size`, so every rank always gets at least one row.
- The floor was calibrated on H200 with NVSwitch; other interconnects were not measured. Startup auto-calibration is a possible follow-up.
