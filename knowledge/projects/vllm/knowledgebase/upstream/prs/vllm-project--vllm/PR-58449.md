# [Spec Decode][Qwen3.8] Enable fused draft metadata updates for the QSA side cache

[Upstream PR](https://github.com/vllm-project/vllm/pull/58449) · state: open · merged: False

## Original PR description

## Purpose

With MTP `num_speculative_tokens > 1`, the Model Runner V2 autoregressive speculator reuses one
attention-metadata build across draft steps only if every attention group's builder sets
`supports_draft_decode_metadata_update`. Qwen3.8-Flash-Next's QSA side-cache builder
(`QSAMetadataBuilder`, backend `QWEN4_EXP_EXP_QSA_STATE`) does not, so the speculator logs

```
Fused multi-step draft decode is not supported by attention backend(s) QWEN4_EXP_EXP_QSA_STATE;
falling back to rebuilding attention metadata between draft steps.
```

and rebuilds metadata on every draft step for the whole model.

This PR opts the QSA builder in. `update_draft_decode_metadata` re-launches the builder's own
`_build_qsa_metadata_kernel` in place on the metadata's persistent tensors, following the
pattern of `DeepseekSparseSWA`'s update, so draft-step metadata (`token_to_req`,
`logical_positions`, `visible_blocks`, `slot_mapping`, and the compressed cache's
`k_work_metadata`) is computed by exactly the code path `build()` uses.

## Changes

- `vllm/models/qwen4_exp/common/qsa_cache.py`
  - Factor the kernel launch out of `build_qsa_metadata_triton` into
    `_launch_qsa_metadata_kernel`, shared by `build()` and the new update. No behavior change
    for `build()`.
  - `QSAForwardMetadata` gains `common_slot_mapping` (the compressed layout reads it to keep
    padded tokens inert) and `num_mapped_tokens` (previously read from `query_start_loc_cpu`,
    which is not capture-safe inside the draft loop).
  - `QSAMetadataBuilder.supports_draft_decode_metadata_update = HAS_TRITON` and
    `update_draft_decode_metadata`. The PyTorch fallback builder keeps the rebuild path.
- `tests/models/qwen4_exp/test_qsa_reference.py`
  - `test_qsa_draft_decode_metadata_update_matches_rebuild`: for the plain, compressed and
    circular layouts, an in-place update after advancing `seq_lens` by one equals a fresh
    `build()` at `seq_lens + 1`. The sequence lengths cross a compression boundary, so
    `visible_blocks` must change; the test also asserts the update changed state.

`max_seq_len` is intentionally not refreshed: in this model it is only consumed by the prefill
selection path, and the fused draft loop is decode-only.

## Not a duplicate

- #55292 adds `supports_multi_step_drafting = True` to the same builder. That is a different
  capability (the V1 proposer's multi-step validity check, ROCm-gated) and does not add
  in-place draft metadata updates. The two changes touch adjacent lines of the same class and
  should rebase trivially onto each other.
- #54790 does the equivalent for sparse MLA backends under DCP — different backend.
- No open PR sets `supports_draft_decode_metadata_update` for `QSAMetadataBuilder`.

## Accuracy

Speculative decoding is exact; the fused path only changes when draft-step metadata is
computed. Mean acceptance length is unchanged at every concurrency (e.g. 4.13–4.26 vs
4.08–4.31 at c=2, 4.15–4.21 vs 4.16–4.21 at c=16–64), and per-position acceptance at c=64 is
0.90 / 0.83 / 0.77 / 0.68.

temperature 0.6 / top-p 0.95 / top-k 20, max 32k tokens, 32 concurrent requests), two
runs per arm to measure run-to-run noise:

| run | accuracy | truncated |
|---|---|---|
| this PR #1 | 97.75 % | 0 |
| this PR #2 | 98.00 % | 0 |
| stock #1 | 97.75 % | 0 |
| stock #2 | 97.25 % | 0 |

Per question, the two runs of the same arm disagree on 8 (this PR) and 7 (stock) of the 400;
the four cross-arm pairs disagree on 8, 5, 2 and 7. Cross-arm disagreement is no larger than
within-arm disagreement, i.e. no measurable change in outputs.

Hi @bilikaz, thanks for this PR. We hit the same cost on Qwen3.8-Flash-Next + MTP 3 (8 × A100, TP8 + EP, agentic workload at concurrency 8): in a py-spy profile of a TP worker, `_multi_step_decode > _build_uniform_attn_metadata` takes 5.2 % of the samples, and the startup log says `Attention backend(s) QWEN4_EXP_EXP_QSA_STATE cannot update draft decode metadata in place; falling back to rebuilding attention metadata eagerly.` So this change matters for us too, and I would like to help it land rather than open a competing PR.

Two notes from going through it against current main:

1. **Conflict with #64110.** #64110 (merged 30 Oct) renamed `qsa_cache.py` / `QSAStateBackend` to `common/qsa_indexer.py` / `QSAIndexerMetadataBuilder` (`QWEN4_EXP_QSA_INDEXER`). The MTP layer still owns an indexer, so on current main the drafter still falls back to the eager rebuild; `Qwen4ExpQSAMetadataBuilder` already declares the in-place update.

2. **`num_mapped_tokens` on a padded replay.** This PR stores `num_mapped_tokens = int(query_start_loc_cpu[-1])` at build time and reuses it in `update_draft_decode_metadata`. In a FULL-graph draft step the captured value is replayed for every batch padded to that size, so when the live batch has fewer real requests, the rows past the real tokens are treated as mapped (they get a request index and logical position that a rebuild would mark as padding). The slot writes are probably still harmless, but the metadata no longer equals a rebuild. Reading the count on the device from `query_start_loc[num_reqs]` inside the kernel avoids this.

I ported the idea onto the renamed builder with that device-side count, in case it is useful for your rebase: https://github.com/kimseunghyun-kr/vllm/compare/main...qsa-indexer-draft-decode-update (one commit, `e323f912dc`). It routes `build()` and `update_draft_decode_metadata()` through one writer, so the update is a rebuild of the same fields on the same device tensors; the torch fallback also takes the token-to-request map from device tensors. Its test advances `seq_lens` / slot mappings for three draft steps with one padding request and checks every field bitwise against a fresh `build()` for the raw, compressed and circular-buffer caches (the torch path passes on CPU; GPU result below).

Feel free to take any of it into this PR (a `Co-authored-by` would be nice but is not necessary). If you would prefer that I open it as a follow-up on top of yours instead, tell me. I can also run your rebased version end to end on our A100 setup.

**Update, 31 Oct: GPU run.** One A100-SXM4-40GB, `tests/models/qwen4_exp/test_qsa_reference.py`, current main (`2b009fc6d1`) against the branch (`e323f912dc`), with the compiled ops from our v0.32.0 CUDA 13 image. The 9 new cases pass: `test_qsa_indexer_draft_decode_update_matches_fresh_build` (3 cache kinds x torch / Triton) and `test_qsa_indexer_draft_decode_update_replays_in_cuda_graph` (one capture replayed over the draft steps, 3 cache kinds).
