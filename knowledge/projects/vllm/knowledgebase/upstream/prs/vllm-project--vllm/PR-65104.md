# [Perf][Spec Decode] Record the draft log-sum-exp when the drafter samples

[Upstream PR](https://github.com/vllm-project/vllm/pull/65104) · state: closed · merged: False

## Original PR description



## Overview

`DraftLogitsCache` gains a [rows, steps] fp64 `lse`. When `gumbel_sample` caches draft logits it also reduces each block's max and sum of exp of the cached logits / T, and a small kernel combines them in fp64 into `lse[row, col]`; `rejection_sample` then skips the draft half of the stats pass. 5/5 of a stack; part of #61024.

**Stacked, draft.** Contains #65101, #65102 (with #61344), #65103 (with #64242). **New code is the last commit only.** It touches the same Gumbel kernel as #64476 (Markov sampling for DSpark); whichever lands second rebases.

## Claims

- Verification step for top-p requests with a drafter that fills the cache (K = 3, top-p 0.95, Qwen3-0.6B creative-writing logits, GB300): 637 → 591 µs at 256 requests with T = 1 and 698 → 651 µs with T = 0.7; 186 → 171 µs at 64; within 1.5 µs either way below 16 requests. With #65103 the stats kernel then only computes the greedy argmax.
- Same samples as the stats pass's draft reduction (test below).
- **Not measured:** the drafter's added cost (one extra block reduction in the Gumbel kernel and a combine launch per draft step). The step times above take the draft lse as given.

## Details

- **Scaling.** The lse is over `cached.to(fp32) / temp`, the expression the rejection kernels use when they reload the cached draft logits, so the two agree bit for bit (if #64496 moves both to `tl.div_rn`, they move together).
- **Who fills it.** The generic speculator's `sample_draft` (EAGLE, MTP, DFlash) passes the buffer and sets `lse_filled`; the watermarked path clears it; DSpark and draft models with their own sampling kernels never set it and keep the stats pass. PCP broadcasts the lse with the draft logits. `rejection_sample` uses it only when `lse_filled` and the draft vocabulary is not wider than the target's.
- **How.** Same as #65103: one (lse, 1) partial per row in an fp64 `draft_local_max`, so no consumer changes; the stats kernel skips its draft pass under `HAS_DRAFT_LSE`.
- **Not duplicating.** #56724 (drafting under top-k/top-p) would change what the draft distribution is, and the lse would then have to cover the drafter's kept set; #64476 changes the Gumbel kernel's sampling, not what is cached. Searched open PRs for "draft logsumexp", "DraftLogitsCache", and #61024.
- **Stack.** 1 #65100 · 2 #65101 · 3 #65102 · 4 #65103 · **5 this**.

- zyongye · comment · 2026-11-02T18:49:49Z · [source](https://github.com/vllm-project/vllm/pull/65104#issuecomment-6585449261)

Closing. Once the drafter's own cost is counted, this is a net loss.

Recording the draft log-sum-exp in the fused Gumbel kernel makes each draft step slower: +3.5 µs at 1 request, +5–6 µs at 16, and +16–21 µs at 128 (V = 151,936 / 202,048, GB300). A verification step pays that K times. What it saves at verification, the stats kernel's draft pass, is smaller: a median 3.6% of the step on its own.

Over a 360-configuration stress matrix (K ∈ {1, 3, 7}, block verification on/off, T ∈ {0.6, 0.95, 1, mixed}, top-p ∈ {0.95, 1}, 1/16/128 requests), this branch plus the drafter's extra cost was never faster than #65103 on the 216 configurations with draft logits: +2.8% at best, +17% at the median. The cheapest variant I tried, which reuses the logits the Gumbel kernel already loads and drops the second launch, still adds 11 µs per draft step at 128 requests.

#65100–#65103 don't depend on this; the stack ends at #65103.
