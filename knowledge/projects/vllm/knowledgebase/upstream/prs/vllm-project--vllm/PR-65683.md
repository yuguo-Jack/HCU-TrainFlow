# [Bugfix][KV Offload] Size the lazy walk target for sliding-window allocations

[Upstream PR](https://github.com/vllm-project/vllm/pull/65683) · state: open · merged: False

## Original PR description



## Overview

Size the lazy CPU offload walk's target for the blocks a step allocates in sliding-window groups. Stacked on #65237, whose walk from the head of the free queue exposes the undersized target: only the last commit is new here.

## Claims

- With #65237, models with prefix-cacheable sliding-window groups evict cached blocks before the lazy walk offloads them. On Gemma 4 31B, 27.1% of cached GPU evictions had no CPU copy; with this change, 0.0%.
- That removes the recompute it caused: prompt tokens computed fall from 18.7k/s to 13.1k/s, and mean engine time per request from 748 ms to 396 ms.
- No change for models without sliding-window groups. The change is 2 lines outside tests.

## Details

**Root cause.** `_estimate_lazy_target_blocks` counted a prefix-cacheable sliding-window group as its window, `cdiv(sliding_window, block_size) + 1`. A step that schedules `max_num_batched_tokens` allocates `cdiv(max_num_batched_tokens, block_size)` blocks in every attention group, sliding-window ones included.

For Gemma 4 (five sliding-window groups with a 1,024-token window and one full-attention group), `target_free` was 2 × (5 × 65 + 256) = 1,162, while one chunked-prefill step can allocate about 2,800 blocks. About two thirds of the head of the queue were uncached sliding-window blocks, so a walk from the head offloaded a few hundred cached blocks, and the allocator evicted past them. The cursor walk before #65237 hid this: it kept offloading deeper over successive steps.

**Fix.** Count every attention group by the blocks a step can allocate, as full attention already was. #64229's term for non-prefix-cacheable sliding-window groups is unchanged.

**Tradeoff.** The target grows with the number of sliding-window groups: 1,162 to 5,632 here. So the walk visits up to that many free-queue nodes per step, which we did not measure on its own.

**Limitations.**
- The end-to-end runs are single 5-minute runs on one workload.
- This PR still trails the build without a83dbfd8 on median latency and CPU-tier share, which longer runs should settle.
