# [Bugfix][ROCm][DBO] Create hipBLASLt handles in microbatch threads before graph capture

[Upstream PR](https://github.com/vllm-project/vllm/pull/64423) · state: closed · merged: True

## Original PR description

Fixes a crash on ROCm during FULL CUDA graph capture with V2-runner DBO. It turned AMD CI's `test_dbo_v2_features_gsm8k` red after #61464: https://buildkite.com/vllm/ci/builds/98127#01a184f5-5c73-4e2a-9dc4-578724d0239d

- `ubatch_utils.py`: before capture, each microbatch thread runs a 1x1 GEMM on its compute and comm streams, so its hipBLASLt handles exist before capture starts.
- With this fix, V2-runner DBO with DeepEP low-latency starts on ROCm, both with and without spec decode. Before it, the server crashed in `hipblasLtCreate` (`hipblaslt.cpp:164`) every time.

On ROCm, PyTorch keeps one hipBLASLt handle per thread and stream and creates it lazily on the first GEMM. Creating one calls `hipMalloc`, which is not allowed while a stream is capturing. `CUDAGraph::capture_begin` creates the handle ahead of time, but only for the thread that starts the capture. With the V2 model runner, DBO runs the GEMMs on separate microbatch threads, and captures on a dedicated stream. When capture starts, the capturing thread takes a handle that a warmup microbatch thread had just released to PyTorch's handle pool. One microbatch thread then has to create a new handle mid-capture, and hipBLASLt exits the process. I confirmed this order of events by tracing every `hipblasLtCreate` and `getCurrentCUDABlasLtHandle` call by thread.

The pre-capture warmup added in #51700 only called `torch.cuda.current_blas_handle()`. On CUDA that object also serves cuBLASLt; on ROCm the hipBLASLt handle is a separate object. The bug has been there since #51700 (the commit before it rejects V2 DBO with CUDA graphs). It surfaced when #61464 added the first AMD CI test that runs V2-runner DBO.

The extra GEMM only runs on the capture path, once per microbatch thread per stream, before capture begins. Steady-state steps are unaffected. On CUDA it is a no-op apart from one tiny kernel before each DBO capture. The V1 runner's DBO capture has the same incomplete warmup but doesn't crash today, because its capture stream is one the main thread already holds a handle for; this PR leaves V1 alone.

Validated on MI350X (gfx950), torch 2.13.0+rocm10.0.0, DeepEP at the `Dockerfile.rocm` pin.

| Run | Without fix | With fix |
|---|---|---|
| `pytest -v -s tests/v1/distributed/test_dbo.py -k v2_features` | crash | 10/10 passed (`spec_decode`; `dcp` skipped, needs 4 GPUs) |
| `vllm serve` V2 DBO + `deepep_low_latency`, no spec decode | crashed 3/3 | — |
| Standalone torch repro (one worker thread doing the GEMMs during capture) | crashed 3/3 | passed 3/3 |

The existing `test_dbo_v2_features_gsm8k` covers this path in AMD CI, so this PR adds no new test.
