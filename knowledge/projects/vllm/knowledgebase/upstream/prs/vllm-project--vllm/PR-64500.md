# [Perf][DSv4.1] Prefetch CPU-offloaded Engram rows for eager prefill

[Upstream PR](https://github.com/vllm-project/vllm/pull/64500) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Add opt-in host row prefetch for CPU-offloaded DeepSeek V4.1 Engram tables on PCIe-attached GPUs. A Numba worker hashes prompt tokens and gathers rows ahead of the eager forward; lookups read the staged rows that match and otherwise read the existing host table without waiting.

Draft: H200 kernel, timeline and lifecycle validation are done; full-model B200 serving, end-to-end performance and output evaluation are pending.

## Claims

- Enable with `--engram-config.host_prefetch_threads 8`; the default `0` disables it. Requires CUDA, Model Runner V2, `cpu_offload` and unsharded tables: tensor, pipeline and prefill context parallel sizes of 1, and `dp_shared_memory` with data parallelism. Config validation rejects anything else before the model loads. The docs scope it to PCIe hosts and advise leaving it off on NVLink-C2C systems (GH200, GB200).
- Lookup output is bitwise identical to main for ready, late and hash-mismatched rows. The main thread never waits for the worker or an upload (`VLLM_GPU_SYNC_CHECK=error`).
- On H200, a staged lookup takes 0.15–0.32 ms versus 1.9–5.0 ms for main's host lookup (10–16×) at 8K/16K tokens; a lookup whose rows are not ready is within +0.7% of main.
- The first Engram layer keeps main's overlapped schedule, so a late upload costs about what main costs; later layers look up at use and pick up rows that land mid-lookup.
- Sleep and discard wait out in-flight uploads before releasing device memory. Without this, an upload still gathering after the last step wrote into released staging buffers (reproduced on H200).

## Details

**Worker and staging.** The worker makes one Numba `nogil` parallel call per layer and fills two pinned/GPU staging slots. It copies them on a private stream: values, scales and hashes first, then the step marker. The kernel reads a staged row only when the marker equals the step token and the staged hash equals the row's hash. It re-reads the marker per tile, so rows that land mid-lookup serve the remaining tiles. Host loads keep their original cache policy; staging uses `.cg`.

**Lookup schedule.** The first Engram layer has the least time to hide a host read, so it follows main's schedule: the side stream below the inline threshold, and at use above it. Later layers look up at use, which gives the worker more time.

**Buffer reuse and fallbacks.**

- Each slot keeps its upload events across cancelled tasks, which protects the pinned source.
- Each accepted step gets new per-layer consumption events. The lookup that reads the staging records them, including on the side stream, and the next upload into that slot waits for them.
- Rows are gathered from the current parameters on every task, so a layerwise reload that replaces the weight storage is picked up.
- These fall back to the regular lookup: token ids outside the hash map, image markers, unknown histories and busy slots.
- CPU-gather errors are logged and fall back for unpublished layers. Other worker and CUDA errors propagate to the runner once: at the next step, at slot reuse, or on drain and close.

**Runner integration.** The V2 runner creates the worker after model load. `begin_step` retires the previous step and tracks prompts, `submit` starts eligible steps, and shutdown closes the worker. With sleep mode enabled, the staging buffers live in the weights pool, so `Worker.sleep` and `Worker.discard` first call the runner's `drain_background_work()`, which cancels and waits out in-flight uploads. Outside the model and its config, the change adds these runner hooks, two 2-line calls in `gpu_worker.py`, and a 4-line CUDA/V2 check next to the existing Engram validation in `vllm/config/vllm.py`. Prefetch applies only above the maximum CUDA-graph size. At two layers, 24 columns and 16K tokens, the two slots take about 402 MiB of pinned host memory and 402 MiB of GPU memory per rank. `host_prefetch_threads` is excluded from the config hash because it only changes where eager lookups read rows from.

**Why PCIe only:** on H200, main's random 264-byte host reads reach about 20 GB/s over PCIe (52 MB in 2.5 ms), while the bulk upload uses the copy engine and leaves the SMs free. NVLink-C2C GPUs read host rows directly at far higher bandwidth, so prefetch there would mostly add CPU gather work and host memory traffic. This is documented rather than detected.

**Duplicate-work check:** I searched open PRs for `engram prefetch` and `engram host`. #63326 overlaps the ROCm WKV chain after lookup. #62238, #57023 and #64395 provide disk-, Mooncake- or RDMA-backed tables. #64082 and #62359 share host tables across instances or ranks. None of them gathers prompt rows on the CPU ahead of the forward.

**Remaining validation:**

- Full-model B200 serving, end-to-end performance, output-quality evaluation and sustained CPU-contention behavior.
- The B200 inline-threshold path was exercised on H200 only by forcing the thresholds.
- A historical p65 B200 run had an unexplained illegal memory access. Later runs did not reproduce it, and this PR does not claim its root cause is resolved.
