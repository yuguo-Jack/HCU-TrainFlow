# [Feature][Kernel] Triton autotune fused MoE

[Upstream PR](https://github.com/vllm-project/vllm/pull/61688) · state: open · merged: False

## Original PR description

## Purpose

Depends on #59492.

Builds on the generic Triton autotune warmup (`--kernel-config.enable_triton_autotune`) and adds a fused MoE table. A GPU or model with no bundled `fused_moe/configs/*.json` can now tune its own launch configs at startup instead of falling back to the heuristic default.

The search does not read any bundled or user tables, so it works the same on new hardware as on hardware with shipped configs.

cc @vanshbhatia-amd 

Changes:

- **Bounded search.** At most 48 configs are timed per M bucket. The search starts from the default config, 8 random configs and up to 2 nearby-M winners, then expands neighbors of the fastest config that hasn't been expanded yet. The M buckets are the same 18-bucket grid as `benchmarks/kernels/benchmark_moe.py`, clipped to `max_num_batched_tokens`.
- **Backend-derived search space.** Launch options (`waves_per_eu`, `matrix_instr_nonkdim`, `kpack`), the warp size and the shared-memory limit come from the installed Triton backend. Nothing is keyed on GPU name. Configs that exceed registers or shared memory are skipped. Block FP8 configs are clamped or rejected so tiles align with the quant block. `BLOCK_SIZE_M` is capped by the rows per expert.
- **Routing-robust timing.** Timing runs in a CUDA graph and cycles through 10 routing draws. At small M the number of active experts changes which config is fastest, and a single draw can crown a config that is usually slow.
- **Correctness and noise guard.** A winner must match the default config's output (rtol 1e-2). It must also beat the default by at least 5% in a side-by-side re-timing, otherwise the default is kept.
- **Nearby-bucket seeding.** Winners tuned on the same rank seed later buckets. This matters under TP, where ranks split the work and the neighboring bucket is often tuned elsewhere.
- **Partial-cache resume.** Only missing M buckets are tuned. Shapes with a user or bundled table are skipped unless `VLLM_TRITON_AUTOTUNE_FORCE=1`.
- **Config lookup in `fused_moe.py`.**
  - `get_moe_configs` gains the autotune cache as a lookup layer.
  - Path, load and save helpers are shared by the loader and the warmup table.
  - `fused_moe/__init__.py` is unchanged. `run_moe` re-raises a failing candidate after `override_config` exits, so a failed config is never left active.

Lookup priority: `VLLM_TUNED_CONFIG_FOLDER`, then the autotune cache, then bundled configs, then the default.

Scope: plain `TritonExperts` layers in bf16/fp16 and FP8 W8A8 (per-tensor, per-channel, block). Other quantizations and backends are skipped.

## Notes for reviewers

- **Fewer candidates, not exhaustive.** A 48-config budget can miss the true optimum. The post-search check against the default keeps a bad result from replacing it.
- **Wider search space than the bundled tables.** It adds `BLOCK_SIZE_K=32`, `num_stages` 1–5 and ROCm launch options. All are validated against the default output before they can win.
- **Startup cost.** Triton compile time dominates, and configs are compiled one at a time on purpose, to avoid touching `override_config` in `__init__.py`. One MoE shape on one GPU takes about 5.7 minutes, and TP splits the work across ranks. There is no total time limit across shapes yet.
- **Partial cache with a bundled table.** The autotune cache is looked up before the bundled configs and the two are not merged. After a forced re-tune of a shape that has a bundled table, any bucket missing from the cache uses the nearest cached bucket, not its bundled entry.
- **Inference path is unchanged.** `fused_moe.py` only gains the lookup layer and the load and save helpers.
