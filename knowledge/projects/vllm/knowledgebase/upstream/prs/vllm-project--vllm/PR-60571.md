# There are several scenarios where we can achieve performance gains from TPSP.

## #1 PCIE Communication Topology (Communicationas the Long Pole vs. GEMM)
By splitting a slow All-Reduce into fast peer-to-peer (P2P) intra-node copies, we successfully mitigated the All-Reduce bottleneck and overlapped GEMM computations within the communication phase (except for the first and last micro-chunks). This resulted in a ~40% performance gain, as demonstrated in the down_proj + norm example below.

## #2 NVLink Communication Topology (GEMM as the Long Pole vs. Communication)
By tuning SM allocation and chunk size, we successfully split All-Reduce and normalization into Reduce-Scatter + All-Gather + Normalization (RS + AG + Norm), allowing them to overlap seamlessly with GEMM computations(except for the first & last micro chunk). This resulted in a ~8% performance gain, as demonstrated in the down_proj + norm example below.

## 🛠️ Design Challenges

1. **Multi-Dimensional Tuning & Benefit-to-Penalty Thresholds**  
   TPSP does not fit every situation. The main challenge is setting a clear threshold to make sure the speedup from turning TPSP on is always bigger than the overhead cost. Because this threshold depends on many factors—like microchunk size, SM count, and communication methods—testing it by hand is way too much work. This makes automated scanning a must-have.

2. **Layer-Specific Constraints (`o_proj`/`down_proj` Alignment)**  
   `o_proj` and `down_proj` might work best with different microchunk sizes. However, to avoid extra `gather` or `scatter` steps between them during residual splitting, both projections must use different chunks but share the same threshold. Setting this up by hand across different setups is a huge amount of work, which is another reason we need auto-scanning.

3. **Non-Intrusive Integration & Backward Compatibility**  
   Adding TPSP must not break or change how the code works by default, ensuring that existing workloads run safely without any impact.

---

## 💡 Key Highlights

* **Safety First via Auto-Scanning:** TPSP performance is highly sensitive to tuning factors. To prevent regressions, TPSP is automatically gated by auto-tuning scan results, ensuring zero performance penalty in uncertain conditions.
* **Model-Level Isolation:** TPSP is enabled on a model-by-model basis. Un-enabled models safely fall back to the legacy path with zero impact.
* **Platform Compatibility Check:** TPSP features platform backend detection. It will automatically disable itself on platforms that lack the required backend support.
* **Zero Regression Risk:** The existing default behavior remains entirely unchanged—TPSP acts purely as an opt-in performance booster where applicable.
