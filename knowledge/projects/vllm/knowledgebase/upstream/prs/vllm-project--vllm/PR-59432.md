# [KV Cache] Skip the zero fill in allocate_kv_cache when the platform does not need it

[Upstream PR](https://github.com/vllm-project/vllm/pull/59432) · state: open · merged: False

## Original PR description

**What this changes**

`allocate_kv_cache()` always zero-fills the backing buffer (`torch.zeros`). On a device whose KV cache lives in unified memory that memset writes every page of a multi-GB pool at startup — the pool is resident before the first request and stays that way, even though a serving run only ever writes the blocks it allocates.

The function now takes `zero_fill: bool = True`. With `zero_fill=False` it builds the same layout from `torch.empty`, so a platform can skip the fill. Default behaviour is unchanged.

**Why the fill is not always needed**

The kernels already assume the invariant `KVCacheConfig.needs_kv_cache_zeroing` encodes: every position below the sequence length is written before a reader runs (the same layer writes K/V with `reshape_and_cache`, or an earlier chunk did), and attention masks everything at or past the sequence length. The caches that genuinely read before writing — Mamba state, mixed-precision caches — are exactly the ones that set that flag, and they keep their zeros (up front, or per block as the scheduler hands blocks out).

So the fill is a convenience for the unified-memory case, not a correctness requirement for uniform-precision attention caches. Making it opt-out lets an out-of-tree platform (vllm-metal, Apple Silicon) stop paying for it; the caller takes on the guarantee above.

**What the opt-in caller also takes on: residency**

The flag changes *when* the pages become resident, not whether the OS can take
them back. On unified memory the pool is an ordinary anonymous allocation that
nothing pins — MLX's `set_wired_limit()` covers its own buffers, not memory it
imports in place — so the kernel may compress or swap any of it under pressure,
zeros or live KV alike. The fill never bought a reservation; it only made the
pages resident up front.

The ceiling is unchanged: resident KV is bounded by the blocks in use, so a run
that fills the pool peaks where the eager build peaked, and never needs bytes
the fill had not already committed. Measured on an Apple M4 (16 KiB pages):

| | allocation | first write |
|---|---|---|
| `torch.empty(2 GiB)` | RSS flat, ~0 extra faults | 2 GiB resident, 131,477 faults (= 2 GiB / 16 KiB) |
| `torch.zeros(2 GiB)` | 2 GiB resident, 131,489 faults | another 131,451 faults — the kernel had already reclaimed them |

There is no new error path either: a fault into an already-mapped page is
satisfied from the compressor or the swap file, it does not return `ENOMEM`, so
Python never sees a `MemoryError` here. A machine that exhausts both ends the
process the same way it would end a startup zero-fill.

Two caveats belong to the platform that opts out:

- **Admission.** An uncommitted pool is invisible to anything that sizes itself
  off free memory (`psutil`, a second server, any app), where the eager fill's
  resident pages at least showed up as used. On a shared machine,
  `--gpu-memory-utilization` bounds cache *capacity*, not admission.
- **Timing.** The faults now land during serving — a long prefill can demand
  hundreds of megabytes at once — rather than before the first request.

Neither is a correctness issue, and neither reaches CUDA: `cudaMalloc` commits
the device allocation regardless of the memset, so no platform that exists today
changes behaviour under the `True` default.

**Measurement**

Apple M4, vllm-metal serving Qwen3-0.6B-4bit / Qwen3-1.7B-4bit at `--gpu-memory-utilization 0.5`. Same five fixed workloads, one process per model:

| | before | after |
|---|---|---|
| peak RSS | 6.45 GB | 2.16 GB (−67%) |
| paired runs | 3887 / 4008 MB | 1269 / 1270 MB |
| KV cache capacity | 44,368 tokens | 44,368 tokens (unchanged) |

Adversarial check on the plugin side: filling the whole pool with a bf16 NaN pattern produces byte-identical outputs to the zeroed build, and served-path parity against native `mlx-lm` is unchanged before and after.

**Tests**

`tests/v1/worker/test_utils.py::test_allocate_kv_cache_zero_fill_can_be_skipped` asserts that the default fill still happens, that `zero_fill=False` does not fill, and that both produce the identical layout (shapes, strides, storage offsets, dtypes). It fails if `zero_fill` is accepted but ignored. `ruff check` / `ruff format` (0.14.0, the pre-commit pin) are clean on both files.
