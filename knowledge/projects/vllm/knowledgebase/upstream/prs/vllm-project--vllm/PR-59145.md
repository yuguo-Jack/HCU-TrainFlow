# [Bugfix][Parser] Constrain tool-call markers by token ID in engine st…

[Upstream PR](https://github.com/vllm-project/vllm/pull/59145) · state: open · merged: False

## Original PR description

## Purpose

Fixes #58315. Related to #58105.

Under `tool_choice="required"` (and named tool choice) vLLM constrains generation
with an xgrammar structural tag built from xgrammar's builtin model templates.
Those templates spell the tool-call markers as **strings**
(`TriggeredTagsFormat(triggers=["<tool_call>"])`, `TagFormat(begin="<tool_call>get_weather", end="</tool_call>")`),
so the grammar admits any tokenization of that text, including `<` `tool_call` `>`
assembled from ordinary sub-tokens.

The streaming parser engine, once it has seen token IDs, recognises the markers listed
in `token_id_terminals` only by their dedicated token ID
(`StreamingParserEngine._process_lex_tokens`, `strict` branch) and treats the assembled
spelling as content. The two sides therefore disagree on what a tool call is:

| encoding of `<tool_call>get_current_time</tool_call>` (GLM-5) | grammar | parser |
|---|---|---|
| dedicated ids `[154843, ..., 154844]` | accept | 1 tool call |
| ordinary ids `[27, 14163, 13420, 29, ..., 522, 14163, 13420, 29]` | **accept** | **0 tool calls, text in `content`** |

A `required` request can thus return no tool call at all. For Qwen3 the parser recovers
the call through `<function=`, but leaks the literal `<tool_call>` into `content`.

## Change

`ParserEngineToolAdapter.get_structural_tag` now passes the builtin tag through
`bind_marker_tokens()` (new `vllm/tool_parsers/structural_tag_markers.py`), which
rewrites it so that every marker the engine resolves by token ID is matched by
xgrammar as that single token:

- `TriggeredTagsFormat` whose triggers all start with a marker →
  `TokenTriggeredTagsFormat(trigger_tokens=[marker])`
- `TagFormat` begin/end that start/end with a marker → `TokenFormat`, with the remaining
  literal text (`get_weather`, `\n<function=get_weather>\n`, ...) folded into the tag
  content as `ConstStringFormat`, so the accepted text is byte-identical
- `ConstStringFormat` containing a marker → sequence of literals and tokens
- `excludes` → `exclude_tokens`, keeping only entries that are single tokens

Markers that are not a single token in the vocabulary are left as strings, which is
exactly how the engine treats them (it only puts vocabulary hits in
`_resolved_token_ids`). So the invariant is: **the grammar constrains by token ID exactly
the terminals the parser recognises by token ID.**

`ParserEngine.token_id_markers` exposes that set. This touches `vllm/parser/engine/`
because the behaviour is wrong for every engine parser that declares
`token_id_terminals` (GLM-4.7/5, Qwen3, DeepSeek V3.2/V4, MiniMax, Kimi K2, ...),
not for one model.

Semantics that change for the free-text spans in `auto` mode: string `excludes`
(e.g. forbidding the text `</think>` in any tokenization) become token-level
`exclude_tokens`, because `TokenTriggeredTagsFormat` has no string excludes. That
matches the parser: with token IDs it reads the split spelling as content, and on the
text-only path (`extract_tool_calls`) a stray `</tool_call>` / `<arg_key>` in content is
also just content (verified on the GLM engine). The auto-mode test pins this down: a stray
dedicated `</tool_call>` token is still rejected where the builtin excludes it, the split
spelling is admitted and parsed as plain content. `required` remains as strict as before:
text before the first call is still rejected (verified against the builtin on GLM-5 and
Qwen3.6).

Note that today the two parser paths already disagree on the split spelling: the
text-only path parses `<tool_call>get_weather</tool_call>` spelled from ordinary tokens
as a tool call, the token-ID streaming path does not. Constraining the grammar removes
the ambiguity at the source instead of teaching one path the other's answer.

## Not a duplicate

- #58847 fixes the same issue on the parser side: a GLM-only config field that lets the
  streaming engine accept the text spelling of `<tool_call>` / `</tool_call>` under
  `tool_choice="required"` after `</think>`. That leaves the grammar unchanged, so named
  tool choice and every other engine parser with `token_id_terminals` (Qwen3, DeepSeek
  V3.2/V4, MiniMax, Kimi K2) keep the mismatch, and it reintroduces text matching for
  exactly the terminals the engine keys by ID. This PR changes no parser logic and covers
  all engine parsers and all three tool-choice modes. The two are alternatives, not
  complements; I am happy to consolidate whichever direction maintainers prefer.
- mlc-ai/xgrammar#935 switches the `glm_4_7` builtin to `TokenFormat` unconditionally and
  hand-builds the sequence/star structure instead of `TriggeredTagsFormat`. Even if it
  lands, vLLM pins xgrammar and other templates stay string-matched, so the vLLM-side
  binding is still needed; it is also a no-op on a template that already uses tokens.
- #58219 (docs) documents the contract for *user-supplied* grammars and does not change
  runtime behaviour. This PR fixes vLLM's own `required`/named grammar. Both can land.
- #50986, #57553, #56661 change how the Qwen3 parser validates/accepts markers in text;
  none touch the structural tag. No file overlap.
- No open PR references #58315. On #58105 the commenters explicitly deferred a code fix
  to a maintainer decision; this is that fix on the grammar side, where the reporter
  measured that only token elements reject the split encodings.
- Upstream I am proposing the same binding as an opt-in get_model_structural_tag(..., token_markers=True) in xgrammar (default output unchanged, per-builder marker_tokens; mlc-ai/xgrammar#940). Once an xgrammar release ships it, this rewrite can be replaced by passing that flag.

## Model evaluation

No model run is included. The change only affects which token sequences the
`required`/named-tool grammar admits; it removes encodings the parser could never turn
into a tool call and leaves the dedicated-token encoding (the one models are trained on)
unchanged. A CPU reproduction with the real tokenizers is in the new test file.
I can run GLM-4.7-Flash with `tool_choice="required"` before/after if reviewers want
frequency numbers.

- thediymaker · comment · 2026-10-24T00:03:18Z · [source](https://github.com/vllm-project/vllm/pull/59145#issuecomment-6377224615)

Independent data for the diagnosis here. With GLM-5.2 and GLM-5.3 (`glm47` tool and reasoning parsers), streamed `tool_choice="required"` returned the call as plain text in `delta.content` (no `tool_calls`, `finish_reason: "stop"`) in 4 of 16 and 3 of 16 requests. With `stream=false` the same output parsed as a call. In every leaking stream `</think>` was the dedicated id and the whole call was ordinary pieces starting with a plain `<`, mostly on prompts that did not really need a tool.

From reading the diff, the `TokenTriggeredTagsFormat` / `TokenFormat` rewrite makes that spelling unreachable under `required` and named choice, so it fixes this at the source. We had been carrying a parser-side workaround along the lines of #58847, and this is the better place for it.

One case to check: `auto` with a `strict: true` tool. Today the string trigger also fires on the split spelling, so that call is still grammar-constrained, and the text-only (non-streaming) path returns it as a tool call. After the rewrite the split spelling is free text, so non-streaming can return a tool call whose arguments were never constrained by the schema. A test pinning the intended non-streaming behaviour there would help.
