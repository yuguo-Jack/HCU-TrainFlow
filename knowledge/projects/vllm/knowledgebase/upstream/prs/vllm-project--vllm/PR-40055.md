# Quantized fused MOE optimization

[Upstream PR](https://github.com/vllm-project/vllm/pull/40055) · state: open · merged: False

## Original PR description

This optimization drastically increases throughput for certain MXFP4 quantized MoE models on hardware without native MXFP4 support.

The rationale is as follows.  This code dequantizes inputs for all experts, even though, when we're in single-token decode mode, only a few of the experts will actually be used (and we know exactly which ones). E.g., with Qwen3-235B,  w1/w2 first dimension is 160, but we only use 8 experts. By weeding out unused experts before dequantization, we avoid an extremely expensive operation.

On 1x MI325 with Qwen3-235B-A22B-Thinking-2507_moe_w_mxfp4_a_mxfp4_kv_fp8, I see a speedup from ~4 token/s to 21 token/s after this patch.

## Code Review

This pull request introduces a selective dequantization optimization for MXFP4 weights during single-token decode in the Fused MoE layer, remapping expert IDs to a contiguous range to reduce overhead. Feedback indicates that the current implementation will cause an IndexError in Expert Parallel (EP) configurations because it uses global indices to slice local weight tensors. It is also suggested to extend this optimization to MXFP6 quantization schemes to resolve similar performance bottlenecks.

## Code Review

This pull request optimizes the fused MoE layer for single-token decoding by dequantizing only the active experts instead of the entire expert set. This implementation is broken for Expert Parallel (EP) configurations. In EP, `topk_ids` contains global expert indices, while `w1` and `w2` only contain the subset of experts assigned to the current rank (of size `E`). Slicing `w1[unique_expert_ids]` using global indices will result in an `IndexError` or incorrect data access if the global index exceeds the local expert count. 

To fix this, you must first map the global `topk_ids` to local indices using the `expert_map` (if provided), filter out experts not on the current rank (where `local_id == -1`), and then perform the slicing and remapping. Additionally, if you remap `topk_ids` to a contiguous range `[0, num_active)`, you must set `expert_map` to `None` for the subsequent `moe_align_block_size` call to prevent it from attempting a second (and now incorrect) mapping.

When slicing the weights `w1` and `w2` to include only active experts, any associated auxiliary tensors such as `w1_bias`, `w2_bias`, `w1_zp`, and `w2_zp` must also be sliced using `unique_expert_ids`. Failure to slice these tensors will cause the kernel to index into incorrect values (e.g., using biases for experts 0..N instead of the actual selected experts) or potentially lead to out-of-bounds access if the kernel expects the expert dimension to match the weight tensor.

```suggestion
            w1 = dequant_fn(w1[unique_expert_ids], w1_scale[unique_expert_ids])
            w1_scale = None
            if w1_bias is not None:
                w1_bias = w1_bias[unique_expert_ids]
            if w1_zp is not None:
                w1_zp = w1_zp[unique_expert_ids]
            w2 = dequant_fn(w2[unique_expert_ids], w2_scale[unique_expert_ids])
            w2_scale = None
            if w2_bias is not None:
                w2_bias = w2_bias[unique_expert_ids]
            if w2_zp is not None:
                w2_zp = w2_zp[unique_expert_ids]
```
