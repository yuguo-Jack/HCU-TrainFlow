# [Bugfix] Make Humming DeviceInfo lookups traceable under torch.compile

[Upstream PR](https://github.com/vllm-project/vllm/pull/61858) · state: closed · merged: True

## Original PR description



## Overview

Fixes vllm-project/humming#147 for vLLM: models served through Humming fail torch.compile with `RecursionError` whenever Humming's forward path quantizes or Hadamard-transforms activations (seen during warmup of MXFP4 MoE checkpoints on H200). This patches Humming from the `vllm.utils.humming` facade so the pinned `humming-kernels==0.1.17` works for v0.32.0.

## Claims

- torch.compile (`fullgraph=True`) works again on Humming forward paths that run `may_process_input` (input quantization, Hadamard): no `RecursionError`, no Dynamo `Unsupported`.
- Works with the currently pinned humming 0.1.17. The upstream fix (vllm-project/humming#148, in the upcoming 0.1.18) is **not sufficient on its own** for vLLM (see Details).
- No behavior change in eager mode, apart from no longer re-querying device properties on every forward call.

## Details

**Root cause.** On every call, `LayerConfig.check_device` and the PDL heuristics (`_resolve_use_pdl` → `get_heuristics_class`) build a new `humming.device.DeviceInfo(device)`. vLLM traces these from `may_process_input` inside its fullgraph-compiled region. Two problems stack up:
1. `DeviceInfo` has `__slots__` and a catch-all `__getattr__`. When Dynamo creates the instance, it reads the unset `_value` slot, which re-enters `__getattr__` and recurses forever. humming#148 fixes this by raising `AttributeError` for private names.
2. With (1) fixed, Dynamo still can't trace the pybind `_DeviceInfo(index)` constructor, so fullgraph compile fails with `Unsupported`. Reading attributes from an extension object that already exists does trace fine; that's why the module-global `current_device` already works under compile. Humming main still has these per-call constructions, so 0.1.18 alone would still break vLLM.

**Fix.** On first use of the facade, `_patch_humming()`:
- backports the #148 `__getattr__` change (also fixes `copy.copy(DeviceInfo)`), and
- replaces the `DeviceInfo` name in the five Humming modules that call it (`config.config`, `transform`, `tune`, `tune.process_input`, `utils.smem`) with a factory that returns one cached instance per device index. `prepare_layer_config` populates the cache eagerly during weight processing, so at trace time Dynamo only sees a dict lookup on an existing object.

All vLLM Humming access goes through the lazy facade, so the patch is always applied before any layer is prepared. The swap is skipped for any module whose `DeviceInfo` is no longer Humming's class. `DeviceInfo` only exposes static device properties, so caching it is safe.

**Follow-up.** This should be removed once Humming's `DeviceInfo` can be constructed in traced code (for example, by caching inside Humming itself); there's a TODO. I'll raise this on the Humming side so 0.1.18+ can drop the patch.
