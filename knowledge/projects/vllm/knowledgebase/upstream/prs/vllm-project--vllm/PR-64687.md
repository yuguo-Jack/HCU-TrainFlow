# [Models][XPU] Port eager Qwen3.5 models and fuse MoE decode

[Upstream PR](https://github.com/vllm-project/vllm/pull/64687) · state: open · merged: False

## Original PR description



## Overview

Move Qwen3.5 models and MTP on XPU to the eager, breakable-graph design introduced by [vLLM #51012](https://github.com/vllm-project/vllm/pull/51012). Recover small-batch MoE decode fusion by calling the routed/shared expert provider from [vllm-xpu-kernels #670](https://github.com/vllm-project/vllm-xpu-kernels/pull/670) directly in the XPU model, without model-level `torch.compile` or a compiler fusion pass. Fusion is bounded to eligible 1–8-token FP16/BF16 calls with per-tensor FP8-e4m3 weights; the routed/shared expert outputs share one TP reduction. Other configurations retain the existing MoE path.

## Claims

- TP2, async, graph-on MoE B1: streamed TPOT **-21.0% to -20.1%**, output throughput **+16.3% to +25.4%** for 1K/8K/32K input and 512 output tokens versus the compiled XPU baseline.

## Validation

Environment: two Intel Xe2 GPUs, 32 GB per card, cards 0/1, TP2, PyTorch `2.14.0+xpu`, FP16 with online `fp8_per_tensor` quantization. Performance checkpoints: **Qwen3.6-35B-A3B (MoE)**, using the Qwen3.5 implementation, and **Qwen/Qwen3.5-9B**, measured at **BF16, no quantization, TP1 on card 0**, with TP2 greedy checks on cards 0/1.

Baseline: main `fa3b9d1377`, original XPU model with `VLLM_COMPILE` (mode 3). This PR: `dd6f1ccb15`, XPU eager model (mode 0). Both use the same kernel build (`0becdcc76c`, the #670 Qwen native implementations). Matching serving flags: async scheduling, prefix caching off, block size 64, max model length 40960, max batched tokens 8192 and max sequences 128. Offline runs use max sequences 32. Graph-on is `FULL_DECODE_ONLY`.

```bash
#!/usr/bin/env bash
set -euo pipefail
source_dir=${VLLM_SOURCE_DIR:-$PWD}
exec "${PYTHON_BIN:-$source_dir/.venv/bin/python}" - "${1:?model name}" "${2:-8000}" "${3:-results}" <<'PYCLIENT'
import json, os, random, statistics, sys, threading, time, urllib.request
from concurrent.futures import ThreadPoolExecutor
from pathlib import Path
model, port, destination = sys.argv[1:]
out = Path(destination)
out.mkdir(parents=True, exist_ok=True)
def request(prompt, barrier):
    payload = dict(model=model, prompt=prompt, max_tokens=512, temperature=0,
                   seed=0, ignore_eos=True, stream=True, return_token_ids=True,
                   stream_options={"include_usage": True})
    req = urllib.request.Request(f"http://127.0.0.1:{port}/v1/completions",
        data=json.dumps(payload).encode(), headers={"Content-Type": "application/json"})
    client = urllib.request.build_opener(urllib.request.ProxyHandler({}))
    first = last = usage = None
    tokens = 0
    barrier.wait(timeout=30)
    start = time.perf_counter()
    with client.open(req, timeout=900) as response:
        for line in response:
            if not line.startswith(b"data: "):
                continue
            data = line[6:].strip()
            if data == b"[DONE]":
                break
            chunk = json.loads(data)
            if chunk.get("error"):
                raise RuntimeError(chunk["error"])
            usage = chunk.get("usage") or usage
            for choice in chunk.get("choices", []):
                ids = choice.get("token_ids") or []
                if ids:
                    last = time.perf_counter()
                    first = last if first is None else first
                    tokens += len(ids)
    end = time.perf_counter()
    assert usage and usage["prompt_tokens"] == len(prompt)
    assert usage["completion_tokens"] == tokens == 512 and last > first
    return dict(start=start, end=end, tpot_ms=(last-first)*1000/511,
                ttft_ms=(first-start)*1000, output_tokens=tokens)
summaries = []
for length in map(int, os.environ.get("INPUT_LENGTHS", "1024,8192,32768").split(",")):
    rng = random.Random(0)
    prompt = [rng.randrange(1000, 20000) for _ in range(length)]
    for batch in map(int, os.environ.get("BATCHES", "1,2,4,8").split(",")):
        rounds = []
        for index in range(4):  # One warmup, three measured rounds.
            barrier = threading.Barrier(batch)
            with ThreadPoolExecutor(max_workers=batch) as pool:
                requests = list(pool.map(lambda _: request(prompt, barrier), range(batch)))
            assert max(r["start"] for r in requests) < min(r["end"] for r in requests)
            elapsed = max(r["end"] for r in requests)-min(r["start"] for r in requests)
            rounds.append(dict(round=index, requests=requests,
                tpot_ms=statistics.mean(r["tpot_ms"] for r in requests),
                ttft_ms=statistics.mean(r["ttft_ms"] for r in requests),
                output_tok_s=batch*512/elapsed))
        summary = dict(input_tokens=length, batch=batch, rounds=rounds,
            median={k: statistics.median(r[k] for r in rounds[1:])
                    for k in ["tpot_ms", "ttft_ms", "output_tok_s"]})
        summaries.append(summary)
        (out / "summary.json").write_text(json.dumps(summaries, indent=2))
        print(length, batch, summary["median"], flush=True)
PYCLIENT
```

## Details

This extends the merged [#51012](https://github.com/vllm-project/vllm/pull/51012) design to XPU. Unlike [#61163](https://github.com/vllm-project/vllm/pull/61163), which installs a compiler pass, this dispatches the companion [kernel #670](https://github.com/vllm-project/vllm-xpu-kernels/pull/670) directly from the eager model. The companion PR is currently open; wheels without its provider use the existing MoE path.

Shared projections must use `XPUW8A16FP8LinearKernel`; explicit W8A8 selection retains its activation quantization through the fallback. The performance and evaluation tables above retain their stated original measurement revisions.

  (https://github.com/vllm-project/vllm/tree/de53c2deed03abd19cdef4f2bddcfcef60a84610/vllm/models/deepseek_v41/nvidia/specialized_decode) have model-specific specialized_decode implementations. The Qwen3.5 XPU integration takes inspiration from their separation of model integration,
  initialization, weight qualification and runtime dispatch:

  • Initialization: hooks.py builds FusedMoeDecode exclusively through the existing model post-load hook, after quantization and before graph capture. Forward never initializes executors or prepares weights. This follows the separation illustrated by AMD’s hooks
    (https://github.com/vllm-project/vllm/blob/de53c2deed03abd19cdef4f2bddcfcef60a84610/vllm/models/kimi_k3/amd/specialized_decode/hooks.py) and the post-load construction in NVIDIA’s model state
    (https://github.com/vllm-project/vllm/blob/de53c2deed03abd19cdef4f2bddcfcef60a84610/vllm/models/deepseek_v41/nvidia/specialized_decode/runtime/model_state.py#L62-L82). XPU uses standard model post-load hooks without a Model Runner V2-specific ModelState dependency.

  • Weight qualification/preparation: weights.py checks static configuration, backend, dtype and layout eligibility, informed by AMD’s weight guards
    (https://github.com/vllm-project/vllm/blob/de53c2deed03abd19cdef4f2bddcfcef60a84610/vllm/models/kimi_k3/amd/specialized_decode/runtime/guards.py#L15-L94). Necessary contiguous model-owned layouts are prepared before executor binding. Static initialization failures report a fallback
    reason once.

  • Runtime dispatch: FusedMoeDecode checks the current input in vLLM, including 1–8 token rows and rows * top_k <= 512, before calling the fused provider. Ineligible or uninitialized calls use the existing MoE forward. This follows the guarded dispatch/fallback patterns in NVIDIA’s
    MoEStep (https://github.com/vllm-project/vllm/blob/de53c2deed03abd19cdef4f2bddcfcef60a84610/vllm/models/deepseek_v41/nvidia/specialized_decode/moe/step.py#L72-L103) and AMD’s decode planning
    (https://github.com/vllm-project/vllm/blob/de53c2deed03abd19cdef4f2bddcfcef60a84610/vllm/models/kimi_k3/amd/specialized_decode/runtime/decode.py#L155-L192).

  • Parameter ownership: After preparation, the executor directly references model-owned tensors. Supported in-place kernel-format reloads remain visible to captured graphs. Changes to storage, layout or eligibility require rebuilding the executor and recapturing graphs.

  The XPU model and MTP implementations remain independent. Fusion covers local routed/shared expert computation; routing/top-k and the single final TP reduction remain in vLLM. This revision leaves native kernel math unchanged.
