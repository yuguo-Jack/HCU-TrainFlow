# [Bugfix] Drop enable_in_kernel_fc2_reduce from FlashInfer CuteDSL MegaMoE config

[Upstream PR](https://github.com/vllm-project/vllm/pull/59900) · state: open · merged: False

## Original PR description

## Overview

Fixes #59887. `--moe-backend flashinfer_moe_ep_cutedsl` (added in #54049) passes `enable_in_kernel_fc2_reduce` to FlashInfer's CuTeDSL MegaMoE config. The pinned FlashInfer 0.7.0.post1 calls that field `in_kernel_fc2_reduce`, so the backend raises `TypeError` while the layer is built. This PR drops the kwarg and adds a regression test that doesn't need SM100. `flashinfer_moe_ep_mega_deep_gemm` is unaffected.

## Claims

- With the pinned `flashinfer-python==0.7.0.post1`, `flashinfer_moe_ep_cutedsl` no longer raises `TypeError` when the layer is built. Behavior is as intended: `False` is the field's default in every FlashInfer release from v0.7.0 through v0.7.1.
- The fix doesn't depend on the FlashInfer version: 0.7.1 (released 2026-10-09; #60948 bumps the pin) renames the field but keeps its `False` default, and the new test passes against 0.7.1's config types (constructor check only; the backend itself was not run on 0.7.1). With 0.7.1, `main`'s current kwarg becomes valid too; this PR keeps 0.7.0.x working and adds the drift test.
- On 4× GB200 at current `main`, with `nvshmem4py` installed and #61041's decoder-replay fix copied in, the backend serves DeepSeek-V4.1-Flash with default CUDA graphs (FULL and PIECEWISE captured). GSM8K is 0.891 (one run), vs 0.901 for `deep_gemm_mega_moe` and 0.910 for the default MoE backend on the same image.
- New test `test_adapter_kwargs_match_installed_flashinfer`: it builds the adapter against the installed FlashInfer's real config types, without SM100 or multiple GPUs (it also passes with no GPU visible). It lives in `tests/kernels/moe`, which the L4 `kernels-moe-test` job runs; no Buildkite job has run on this PR yet.
  - **What it catches:** a renamed or removed kwarg in FlashInfer's MoE-EP config types, or removal of the deprecated `Nvfp4CutedslMegaMoeConfig`/`DeepGemmMegaMoeConfig` aliases. Before, these only failed at model load on SM100.
  - **What it doesn't cover:** `MoEEpTensors` and the megakernel layer's own methods. Only the SM100 e2e test covers those.

## Details

**Root cause.** FlashInfer renamed `in_kernel_fc2_reduce` to `enable_in_kernel_fc2_reduce` in flashinfer-ai/flashinfer#4604, first shipped in v0.7.1rc1 and now in v0.7.1. The adapter was written against the new name while vLLM still pins 0.7.0.post1 (`requirements/cuda.txt`). Every other kwarg and method the adapter uses on FlashInfer's MoE-EP types is present in both 0.7.0.post1 and 0.7.1, so this was the only mismatch.

**Why CI missed it.** The only test that constructs the adapter, `test_init_warmup_forward_is_exact_on_grid_inputs`, needs SM100 and 2+ GPUs. `kernels-moe-test` runs on L4, so it always skips there, and no B200 job runs this file. The new test fakes four things:
- `flashinfer.moe_ep.MoEEpMegaLayer`, which allocates symmetric memory;
- the EP group;
- the device index;
- `_expose_deep_gemm_to_flashinfer`, which imports DeepGEMM.

Everything FlashInfer receives is its own config dataclasses plus a real `MoEWeightPack`.

**Relation to #60948 (FlashInfer 0.7.1).** #60948 bumps the pin to 0.7.1 and doesn't touch `flashinfer_moe_ep.py`; the two PRs don't conflict and pass in either order. After #60948, `main`'s explicit `enable_in_kernel_fc2_reduce=False` would be valid; dropping it still gives the same `False` default (0.7.1 documents the flag as an opt-in to nondeterministic accumulation), keeps the backend working on 0.7.0.x, and the new test guards both versions.

**Alternatives considered.** *Version-gate the kwarg name:* unnecessary, since the value equals the default.

**Related, found while validating.**
- **`nvshmem4py` packaging:** vLLM's images don't ship `nvshmem4py`, so without it `flashinfer_moe_ep_cutedsl` fails at FlashInfer's runtime bootstrap. Tracked in #59903, fixed by #59912.
- **Decoder replay under load:** on current `main`, DeepSeek-V4.1 with either FlashInfer MegaMoE backend crashes under GSM8K load in the decoder-replay CUDA graph. Tracked in #61040, fixed by #61041.
- **Earlier limitations that no longer reproduce at current `main`:** full CUDA-graph capture with this backend (FULL graphs captured above), and the DeepGEMM "type Runtime is already registered" import error (#59904; the vendored DeepGEMM moved to `TORCH_LIBRARY` in #48962). The one-off 2-GPU e2e hang did not recur in 16 cases.
- The adapter still imports FlashInfer's deprecated `Nvfp4CutedslMegaMoeConfig`/`DeepGemmMegaMoeConfig` aliases, which FlashInfer has scheduled for removal. Switching to the `Sm100_*` names is a follow-up; the new test would flag the removal.

**Duplicate check.** Apart from #59887, which I filed for this bug, no open or closed issue or PR mentions `enable_in_kernel_fc2_reduce`, `in_kernel_fc2_reduce`, `flashinfer_moe_ep_cutedsl` or `Nvfp4CutedslMegaMoeConfig` as a fix for it. #60948 (FlashInfer 0.7.1 bump) makes `main`'s kwarg valid but leaves 0.7.0.x broken and adds no test.
