# fix(models): reject LoRA on Mamba2/Zamba2 with descriptive ValueError

[Upstream PR](https://github.com/vllm-project/vllm/pull/61870) · state: closed · merged: False

## Original PR description



## Overview

Replaces bare `assert not is_lora_enabled` statements in `Mamba2Model` and `Zamba2Model` constructors with descriptive `ValueError` exceptions when LoRA is enabled. Fixes #61850.

## Claims

- When `enable_lora=True` is provided for Mamba2 or Zamba2 models, initialization raises a descriptive `ValueError("enable_lora=True is not supported for Mamba2.")` or `ValueError("enable_lora=True is not supported for Zamba2.")` instead of an uninformative bare `AssertionError`.
- Prevents silent bypass of LoRA checks when running Python with bytecode optimizations (`-O` / `PYTHONOPTIMIZE=1`).

## Validation

- Added unit tests in `tests/models/test_zamba2_mamba2_lora.py` validating that initializing `Mamba2Model` and `Zamba2Model` with an active `lora_config` raises `ValueError` matching the expected message.
- Passed local linter checks: `ruff check` and `ruff format`.

## Details

In `vllm/model_executor/models/mamba2.py` and `vllm/model_executor/models/zamba2.py`, LoRA support was guarded by a bare `assert not is_lora_enabled`. This resulted in:
1. EngineCore dying with an opaque `AssertionError` with no explanation of why LoRA is unsupported or which model caused it.
2. In production deployments running Python with `-O`, assertions are omitted entirely by the Python interpreter, which could lead to deeper undefined runtime failures.

Replacing the bare assertion with an explicit `ValueError` makes the error actionable and robust across execution environments.
