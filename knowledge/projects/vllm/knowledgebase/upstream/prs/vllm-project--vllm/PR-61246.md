# [Model] Support ModernBERT decoder (Ettin) via the Transformers modeling backend

[Upstream PR](https://github.com/vllm-project/vllm/pull/61246) · state: open · merged: False

## Original PR description



## Overview

Supports `ModernBertDecoderForCausalLM` (the [Ettin](https://huggingface.co/collections/jhu-clsp/encoders-vs-decoders-the-ettin-suite-686303e16142257eed8e6aeb) decoders, 17M–1B) through the Transformers modeling backend. To do this, the backend's causal LM head learns to handle output heads that transform the hidden states before the output embeddings.

There is no existing issue or PR for this. I searched open and closed issues and PRs for `ModernBertDecoder`, `ettin`, `modernbert decoder`, and for output-head / `lm_head` changes to the Transformers backend.

## Claims

- `jhu-clsp/ettin-decoder-*` models load and generate with vLLM. Before this change, loading failed with `ValueError: There is no module or parameter named 'lm_head.dense' in TransformersForCausalLM`.
- Generic: the Transformers backend now supports any `ForCausalLM` whose output embeddings are not called `lm_head`, plus one module applied to the hidden states before them. For example, `decoder(lm_head(hidden_states))` with a biased, tied `decoder`.
- No cost or behavior change for other models. Only classes that override `get_output_embeddings` are inspected: 31 of the 178 `AutoModelForCausalLM` classes in Transformers 5.19. The other 147 return early without building anything. The inspected ones that already work keep their behavior; for example, GPT-NeoX's `test_common` still passes.

## Validation

H100 80GB, `VLLM_USE_PRECOMPILED=1` editable install on top of `ffec221276`, Transformers 5.19.0, torch 2.13.

**Correctness against Transformers.** Greedy, 32 tokens, the 8 prompts in `tests/prompts/example.txt`, float32 on both sides:

| model | identical generations |
|---|---|
| `jhu-clsp/ettin-decoder-17m` | 8 / 8 (32/32 tokens each) |
| `jhu-clsp/ettin-decoder-150m` | 7 / 8 (the 8th diverges only at its last token, 32/32) |

In bfloat16, `check_logprobs_close` against `HfRunner` fails for both sizes. At each mismatch the two candidate tokens have identical vLLM logprobs (e.g. ` detect` / ` identify` both −3.1181, `performance` / `throughput` both −0.8469). That is a bf16 near-tie in small models, not a model difference, so the end-to-end test runs in float32.

## Details

**Root cause.** The backend builds `AutoModel` (the base model) and adds its own `ParallelLMHead` named `lm_head`. It assumes the Transformers `ForCausalLM` is `lm_head(model(...))`. ModernBERT decoder is instead `decoder(lm_head(model(...)))`:

- its `lm_head` is a prediction head (dense → GELU → LayerNorm);
- `decoder` is the output projection, tied to the input embeddings and with its own bias.

So the checkpoint's `lm_head.dense.*` had nowhere to load, and skipping the prediction head would also produce wrong logits.

**Change** (`transformers/causal.py`, about 90 lines):

- `CausalMixin._output_head` finds the output head:
  - It returns at once unless the `ForCausalLM` class overrides `get_output_embeddings`; only such a class can name its output embeddings differently.
  - Otherwise, it builds that class on `meta`, as `SequenceClassificationMixin` already does for classifiers. It takes the output embeddings' attribute name, plus the one parameterized child that is neither the base model nor the output embeddings, if there is exactly one.
  - With more than one such child, the order of application can't be known. The backend logs a warning and keeps today's behavior.
- `load_weights` renames the output embeddings' weights to `lm_head.*` and the transform's weights to `lm_head_transform.*`. The existing `lm_head.bias` handling then loads `decoder.bias` unchanged.
- `compute_logits` applies `lm_head_transform`, if present, before the logits processor. It runs only on the sampled positions and outside the compiled region. It adds no CPU/GPU synchronization.

The transform stays a plain Transformers module, replicated on every TP rank. It is a hidden×hidden matrix, so this is negligible.

**Why the Transformers backend and not a native model file.** Small dense models are being moved to the backend (#48100, #53615, #59679, #59701). This architecture runs on it once the head is understood: separate q/k/v projections are fused into `QKVParallelLinear`, and per-layer sliding windows are mapped from `layer_types`. A native implementation would be about 300 lines for one architecture. For reference, I wrote one first (out of tree, as a plugin), and it matches this PR's outputs.

**Who else this helps.** These architectures also overrode `get_output_embeddings` with a non-`lm_head` name or a transform head in the scan:

- `BioGpt` (`output_projection`)
- `Electra` (`generator_predictions` + `generator_lm_head`)
- `GPTNeoXJapanese` (`embed_out`)
- `TrOCR` (`output_projection`)

They are not registered here and I did not test them.

**Limitations and untested paths:**

- Single GPU only. I had no multi-GPU machine.
- **TP > 1:** ModernBERT decoder has no TP plan, so it relies on the backend's fallback: QKV and attention are sharded, everything else replicated. `Wi` holds the GLU input and gate halves in one matrix; it is not fused, so it stays replicated, which is correct but not optimal.
- **PP:** the transform is only built on the last rank, next to `lm_head`.
- **Docs:** the LoRA and PP checkmarks in `supported_models.md` follow the backend's general support, like the other backend entries. They were not exercised for this model.
- **Fusion count:** the GLU fusion count in the e2e test is `(0, 1)` because `Wi` is already a single matrix.
