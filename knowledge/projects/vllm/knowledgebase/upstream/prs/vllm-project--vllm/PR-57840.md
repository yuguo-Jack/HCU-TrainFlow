# [ROCm][Model][MiniMax-M3] Context-parallel AITER sparse indexer (fp8, opt-in)

[Upstream PR](https://github.com/vllm-project/vllm/pull/57840) · state: open · merged: False

## Original PR description

## Purpose

Adds **context-parallel decode scoring** for the AITER fp8 indexer on ROCm (gfx950, fp8 index cache, TP>1, opt-in via `VLLM_ROCM_MINIMAX_INDEXER_CP=1`).

Same distributed algorithm as #57832 (Triton bf16 path), adapted for the AITER kernel interface:
- Each rank scores its 1/world_size shard of KV blocks via `pa_sparse_block_score_decode` with a shard block table
- Scores scattered into global-shape `[heads, tokens, max_block]` tensor pre-filled with `-inf`
- MAX allreduce reconstructs all positions from their owning rank
- `pa_sparse_block_topk` runs on the complete allreduced scores

**Default: OFF** (`VLLM_ROCM_MINIMAX_INDEXER_CP=False`). Same env var as #57832. AITER path selected when fp8 index cache + gfx950 + TP>1. The per-step allreduce adds latency that only pays off at moderate-to-high concurrency and mid-range context (10k–90k ISL).

### MiniMax-M3 sparse attention pipeline

| Stage | Backend | Index cache dtype | When selected |
|---|---|---|---|
| Indexer | Triton (#57832) | `bf16` | `indexer_kv_dtype=bf16` — default |
| Indexer | **AITER** (this PR) | `fp8_e4m3` | `indexer_kv_dtype=fp8` — requires AITER sparse PA |
| Attention | **AITER_SPARSE_PA** | — | `SHUFFLE_KV_CACHE_LAYOUT=1` + `ROCM_AITER_UNIFIED_ATTN` |

This PR targets the **AITER fp8 indexer** path. The fp8 MFMA scoring kernel is faster per block than the Triton bf16 path, so CP provides the same absolute latency reduction but against a faster baseline.

**Indexer:** AITER fp8 (`indexer_kv_dtype=fp8`) | **Attention:** AITER_SPARSE_PA (`kv_cache_dtype=fp8`)

|---|---|---|---|---|---|
| **20k** | 364.2 | **473.3** | **+29.9%** | 6,130 → 3,281 | 18,095 → **6,612** |

At 20k: **+30% throughput**, **−46% mean TTFT**, **−63% p99 TTFT**.
At 64k+: neutral — AITER sparse attention dominates; indexer is not the bottleneck.

### Comparison: AITER fp8 vs Triton bf16 indexer (both with CP)

| ISL | Triton bf16 CP (#57832) | AITER fp8 CP (this PR) |

The AITER fp8 path is consistently faster due to the fp8 MFMA scoring kernel; the CP delta is similar for both paths.

### Benchmark C — AgentX Pareto Sweep (MXFP4+EAGLE3, TP=4, vLLM 0.3.1)

**Benchmark:** aiperf `inferencex-agentx-mvp`, Weka trace `semianalysis_cc_traces_weka_062126_256k`, 900s per point
**Methodology:** Single server per run (baseline then CP back-to-back), 60s warmup — eliminates ISL trace variance.

The AITER fp8 indexer already scores blocks in ~1/8 the time of a single-rank Triton bf16 scorer; CP further reduces this to ~1/64 — but at these concurrencies and ISLs the attention kernel dominates.

### Correctness

Mathematical equivalence: MAX of non-overlapping partial scores = MAX of full scores. Same algorithm as #57832 (validated with GSM8K 5-shot: 93.5% on both CP=0 and CP=1 with the Triton path).

### Architecture Concerns

**`reuse-existing-internal-api-over-reimplementation`**
- `dist.all_reduce(..., op=MAX, group=get_tp_group().device_group)` reimplements a collective that `tensor_model_parallel_all_reduce` already provides. Use the canonical API.
- `select_aiter_cp_indexer_impl_cls` in `indexer_aiter_cp.py` duplicates the same env-var + TP>1 gating and log message already present in `select_aiter_indexer_impl_cls`. Remove the duplicate or consolidate to a single dispatch site.
- `score.fill_(float('-inf'))` after `self._new_score(...)` allocates two full score buffers every forward; consider pre-allocating in `__init__`.

**`gate-feature-on-upstream-kernel-readiness`**
Same as #57832: the MAX-allreduce-over-`-inf` pattern is a manual workaround for the absence of a CP-aware sparse-indexer primitive. The entire `MiniMaxM3IndexerAiterCPImpl` subclass and `select_aiter_cp_indexer_impl_cls` dispatcher exist only to host this workaround. Mark clearly as experimental and track the upstream CP primitive as a prerequisite.

**`minimal-fix-over-parallel-class-proliferation`**
The CP behavior is a single `forward()` branch (shard scoring + allreduce vs. full scoring). Consider folding it into the base `MiniMaxM3IndexerAiterImpl.forward()` behind `if self.cp_enabled:` (set from the env var at `__init__`), eliminating the subclass and the extra dispatch branch.

**`drop-in-replacement-over-invasive-module-swap`**
The `MiniMaxM3IndexerAiterCPImpl.forward()` override relies on several base-class attributes (`_new_score`, `_table_rows`, `topk_indices_buffer`, `init_blocks`, `local_blocks`, etc.) that are not shown in the diff. Verify these are the actual base-class API names; otherwise the class-swap breaks at runtime.

**`deep-logic-bugs`**
- `indexer_aiter_cp.py:151` — In the prefill branch, `super().forward()` is called with `decode_page16_block_table=None` while `md.num_decodes` may be > 0. The base `MiniMaxM3IndexerAiterImpl.forward()` still evaluates `md.num_decodes > 0` and may assert/deref `decode_page16_block_table`, causing a crash in mixed decode+prefill batches.
- `indexer_aiter_cp.py:126` — `shard_bt` compacts owned blocks into contiguous columns, so `pa_sparse_block_score_decode` writes `shard_score` at contiguous indices. But the scatter `score[..., owned_cols[:n_owned]] = shard_score[..., :n_owned]` assumes `shard_score`'s block axis is also contiguous. If the kernel uses global-indexed columns, the source slice is wrong. The comment and code make contradictory assumptions — verify the kernel's output layout.
