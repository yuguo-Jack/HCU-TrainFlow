# [Benchmark] Add small-M NVFP4 linear benchmark across vLLM kernels

[Upstream PR](https://github.com/vllm-project/vllm/pull/64646) · state: open · merged: False

## Original PR description

## Overview

Adds `benchmarks/kernels/benchmark_nvfp4_small_m.py`, a microbenchmark that runs vLLM's NVFP4 linear kernels (FlashInfer CUTLASS/b12x/cuDNN/CuTe DSL, native b12x, vLLM CUTLASS, Marlin, Humming) through `process_weights_after_loading` + `apply_weights` on Qwen3.8-27B shapes, at decode and prefill M, on SM120.

Not a duplicate: no open PR adds a NVFP4 linear kernel benchmark (searched "NVFP4 small-M benchmark", "benchmark_nvfp4_small_m", "nvfp4 benchmark kernels"). Related: #55405.

## Claims

- One script times 10 kernels (13 providers including autotuned variants) on the path the model runs (activation quant, padding, GEMM) with FlashInfer CUPTI on a CUDA graph that rotates weight copies past L2, and checks cosine similarity against the dequantized weight (`--min-cos`).
- On SM120 no single kernel is best across M. Per-forward linear time, the M-sweep and an end-to-end check on `nvidia/Qwen3.8-27B-NVFP4` are below.
- vLLM's default NVFP4 kernel on SM120 (`FlashInferCutlassNvFp4LinearKernel`) is 1.4-1.5x slower than the best W4A4 options in the decode microbenchmark; end to end, `humming` shortens the batch-1 decode step by about 18% (22.65 to 18.63 ms).

## Validation

Hardware and versions: RTX PRO 6000 Blackwell Server Edition (SM120, 1597 GB/s datasheet), torch 2.14.0+cu130, flashinfer 0.7.2.post1, humming-kernels 0.1.18. `ruff` and `pre-commit` pass on the file.

```bash
uv pip install cupti-python
python benchmarks/kernels/benchmark_nvfp4_small_m.py --output-json nvfp4_small_m.json
python benchmarks/kernels/benchmark_nvfp4_small_m.py --shapes mlp.down gdn.in_proj_qkvz mlp.gate_up gdn.out_proj \
    --m 64 80 96 112 128 144 160 192 224 256 320 384 448 512 --output-json fine_m.json
```

## Details

- Pre-padding M to a multiple of 128 for `fi-cute-w4a4` (pad and slice included in the timing) helps where it is slow: -22% on `mlp.down` at M=144-224, -14 to -18% on `gdn.out_proj`, but +2 to +5% on `qkvz`/`gate_up` at M=80-224. Geomean over the 56 cells improves from 1.268x to 1.198x vs the best of 5 providers, still behind fi-b12x (1.048x). Not included in this PR.
- `fi-cute-w4a4` is gated to sm_10x in vLLM, so it is measured by bypassing `is_supported` (relies on `NvFp4LinearKernel.__init__` only setting `config`). It rejects N=96 (`in_proj_ba`, needs N % 64 = 0). `fi-trtllm` is unsupported on SM120, `fbgemm` and the torch kernel are unavailable here and are not benchmarked.
- The checkpoint is mixed precision: only the MLP projections and `lm_head` are NVFP4, attention and GDN projections are FP8. End-to-end numbers therefore reflect the MLP and `lm_head`. `--linear-backend` also swaps the FP8 kernels, so the per-quant override is needed to isolate NVFP4.
- FlashInfer autotune at engine start was disabled for the end-to-end runs: on this host it grew past the GPU memory with about 16 GiB held by another process. Microbenchmark `-tuned` variants differed from untuned by at most 2.2% on large shapes.
- Mechanisms in the review comments (GEMV at M=1 for `fi-cute-w4a16`, underfill at M>1) come from reading the FlashInfer 0.7.2.post1 source and the measured shapes; they are not verified with profiling.
- Single run on one GPU and one machine; differences under about 2% are noise. CUPTI sums kernel durations and excludes launch gaps. Microbenchmark plus one model only; no accuracy evaluation, since the PR changes no model code.
