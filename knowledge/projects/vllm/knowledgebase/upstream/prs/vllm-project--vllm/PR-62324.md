# [Bugfix][Responses] Reject negative starting_after in event replay

[Upstream PR](https://github.com/vllm-project/vllm/pull/62324) · state: open · merged: False

## Original PR description

## Overview

`GET /v1/responses/{response_id}?starting_after=N` accepted any integer
for `starting_after`. Negative values flowed into
`start_index = starting_after + 1` and indexed the event `deque` from
the right (Python negative indexing), producing either an HTTP 500 or a
silently corrupted replay. This PR bounds the query parameter and clamps
the computed index.

## Claims

- `starting_after` below -1 is rejected with 422 by FastAPI
  (`Query(ge=-1)`).
- The replayed stream always starts from a non-negative deque index; the
  `response.completed` terminal event is always reachable.

## Validation

- Before the fix, two failure modes were reproducible at logic level
  against the exact generator code (`serving.py`, `retrieve_responses`
  streaming path):
  - `starting_after=-5` with a 3-event buffer:
    `IndexError: deque index out of range` → HTTP 500.
  - `starting_after=-2` with a 3-event buffer: replay began from the
    LAST buffered event (`deque[-1]`), emitted events out of order, and
    never delivered `response.completed` — the stream hung.
- After the fix: `ge=-1` rejects lower values with 422, and
  `max(0, starting_after + 1)` guarantees a valid start index even for
  `-1` (replay from the beginning, matching the "no value" behavior).

## Details

`starting_after + 1` is intended as "resume after the given event
index". For negative inputs Python's deque indexing wraps from the tail,
which breaks both the ordering invariant of SSE replay and the
termination condition of the streaming loop (the loop exits only when it
yields an event of type `response.completed`; a tail-starting replay
skips it).

The clamp and the schema bound are redundant by design: the schema bound
gives clients a clean 422, the clamp protects the generator against any
future caller path.
