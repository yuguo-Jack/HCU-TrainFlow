# [Bugfix][Mooncake] Settle decoder pull preparation failures

[Upstream PR](https://github.com/vllm-project/vllm/pull/65671) · state: open · merged: False

## Original PR description

## Overview

Mooncake decode now reports pull-preparation failures through the existing KV load failure path, instead of leaving the request waiting for a transfer that never started.

## Claims

- Topology, rank-map, empty-worker, and pull-metadata encoding errors are reported with `_handle_failed_recv` before any producer I/O. The scheduler then applies the existing `kv_load_failure_policy` (default `"fail"`, or `"recompute"`).
- One peer's preparation failure does not finish a request while another peer is still running, and does not release that peer's destination blocks early.
- Cancelling a receiver before the pull is sent fails the request. Cancelling it after the pull is sent logs the error and keeps the destination blocks; that is not treated as remote write completion.
- This does not duplicate #65575. That PR fails a pull that was already sent when the prefill worker is lost. This PR covers failures before the pull is sent.

## Validation

Recorded on the parent commit, same new tests:

```bash
.venv/bin/python -m pytest tests/v1/kv_connector/unit/test_mooncake_connector.py -k 'decode_preparation_failure or decode_metadata_encoding_failure or decode_cancelled or decode_cancellation_after' -q
```

Result on the parent: **9 failed, 1 passed**. Failures were the real `AssertionError: Remote tensor parallel size 3 is not divisible by local tensor parallel size 2`, `KeyError: 0`, and `UnicodeEncodeError`, plus `Task exception was never retrieved`. The requests waited until timeout. The existing per-peer socket preparation error still passed and still does not release blocks early.

After this change, including a rerun on the rebased commit `ef2ab93492`:

```bash
HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1 HF_DATASETS_OFFLINE=1 \
.venv/bin/python -m pytest tests/v1/kv_connector/unit/test_mooncake_connector.py tests/v1/kv_connector/unit/test_mooncake_connector_hma.py -m cpu_test -q
```

Result: **19 passed, 159 deselected**. The 10 new cases are included. The focused filter on the pre-rebase patch was **10 passed, 146 deselected**.

No GPU, RDMA, serving, or model-eval run. Successful transfers are unchanged, so there is no accuracy comparison. The GPU "V1 KV Connectors" step is disabled; these tests are `cpu_test` and are selected by the existing `(CPU) V1 Others` step (`pytest -m cpu_test v1/kv_connector/unit`), which this PR triggers by changing `tests/v1`.

## Details

Decode allocates blocks and calls `start_load_kv`. The worker then looks up producer workers and builds pull metadata. Before this change, a bad topology (`handshake` divisibility, a missing TP rank, or an empty PP map), an encoding error, or cancellation of the receiver task escaped the task. Nothing called `_handle_failed_recv`, so the scheduler never applied `kv_load_failure_policy` and the request stayed waiting. Unretrieved task exceptions were the visible symptom.

The fix settles those cases on the existing failure path:

1. Worker selection is wrapped before any peer task is started. New and cached engines both use it.
2. Metadata build and encode sit inside the per-peer error boundary. `pull_tasks_count` is the peer count, and each peer owns its own pending set.
3. Receiver tasks are retained and their terminal result is consumed, including cancellation before the coroutine body runs. A cancelled bootstrap query wakes its waiters and drops the placeholder so a later request can query again.
4. Once the pull has been sent, task cancellation is logged and the destination blocks stay held. Python cancellation does not drain a remote WRITE and this PR does not add recovery for that case.

P-side accounting, abort, placeholders, connector shutdown, Store, and EC are unchanged. A failed transfer whose remote write was not drained is still unresolved.

Rebased onto current `main` (`59519ec0`). The eight commits in between do not touch these files.
