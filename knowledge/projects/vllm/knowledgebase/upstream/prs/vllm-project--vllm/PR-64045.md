# [ROCm][Kernel] Add fused MoE int4_w4a16 config for E=256,N=512 on AMD Radeon AI PRO R9700

[Upstream PR](https://github.com/vllm-project/vllm/pull/64045) · state: open · merged: False

## Original PR description



## Overview

Adds a tuned fused-MoE Triton config for `E=256,N=512,dtype=int4_w4a16` on the AMD Radeon AI PRO R9700 (gfx1201, RDNA4). Without it, int4 W4A16 MoE models of this shape (for example Qwen3.5/3.6-35B-A3B GPTQ Int4 at TP=1) log `Using default MoE config. Performance might be sub-optimal!`. Config file only; no code change. Same GPU, other shape: #60893.

## Claims

- Fused-MoE kernel time is 7–42% lower than the default config at all 17 measured batch sizes (1 to 2048). No batch size is slower.
- End to end (Qwen3.6-35B-A3B GPTQ Int4, `vllm bench serve`): +3.9% output tok/s at 1 request, +17.7% at 4 requests, prefill TTFT unchanged.
- No accuracy change: GSM8K (200 samples, greedy) 88.5% before and after; 20/20 greedy prompts give identical tokens.

## Details

- **How it was tuned:** `benchmark_moe.py --tune --tp-size 1 --dtype int4_w4a16`, one batch size per run. Keys 1, 2, 4, 8, 12, 16: the full pruned search space. Keys 256, 1024, 2048: a coarse sweep of 82 candidates (BLOCK_SIZE_M/N/K in {32, 64, 128}, num_warps in {2, 4, 8}, plus the batch-size-1 winner), because the full space at large M takes many hours on this GPU. Other batch sizes use the nearest key; the table above includes 3, 6, 9, 24, 32, 64, 128 and 512 to show that the nearest-key choice is also faster than the default there. About 11.5 hours of tuning in total.
- **Local script changes for tuning (not part of this PR):** (1) on ROCm, the script renames `HIP_VISIBLE_DEVICES` to `ROCR_VISIBLE_DEVICES`; with Ray 2.59 in this image, Ray then stops with "Please use HIP_VISIBLE_DEVICES instead of ROCR_VISIBLE_DEVICES". We removed the rename and set `HIP_VISIBLE_DEVICES=0` (without it, Ray also sees the iGPU). (2) An optional candidate list for the coarse sweep. Neither change affects the produced file format.
- **`SPLIT_K: 1`** is in every entry because the script fixes it for `int4_w4a16` (the gptq_awq kernel needs the constexpr).
- **Limitations:** validated with one checkpoint (GPTQ, 4-bit, group 128, `sym: true`, `desc_act: false`); other int4 W4A16 checkpoints with E=256, N=512 on this GPU will also load this file, which is untested. On ROCm the script tunes with fp16 activations; bf16 serving was measured end to end (table above). Validated on the image build only, not on `main`. The end-to-end servers also ran a local backport of #52637 so that the RDNA hybrid linear kernel works with symmetric GPTQ; it changes only the linear layers and was the same in both arms.
- **Duplicate check:** no R9700 `int4_w4a16` config with E=256, N=512 on `main` or in an open PR (searched 2026-10-27); #60893 is E=128, N=704.
