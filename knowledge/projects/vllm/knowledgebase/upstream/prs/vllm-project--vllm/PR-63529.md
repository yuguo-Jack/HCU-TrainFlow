# [Bugfix][Frontend] Reject nonzero priorities without priority scheduling

[Upstream PR](https://github.com/vllm-project/vllm/pull/63529) · state: open · merged: False

## Original PR description



## Overview

Return HTTP 400 for nonzero effective priorities on the Python generation and pooling serving paths when priority scheduling is disabled, enforcing the existing request-field contract.

## Claims

- Validate chat, completion and Responses priorities after applying existing header precedence and invalid-header fallback.
- Validate body priorities on batch chat, token-input generation and shared pooling paths.
- Preserve zero-priority acceptance and nonzero-priority acceptance with `--scheduling-policy priority`.

The standalone probes covered chat, completions, Responses, batch chat, token-input generation, embeddings and `/pooling`. They used greedy generation and `VLLM_BATCH_INVARIANT=1`. Model evaluation: not applicable. This change validates request admission without changing model computation, sampling or scheduler ordering. Real-model serving checks and accepted-output comparisons are reported above.

## Details

The generation resolver returned a priority without checking the scheduler policy, while pooling and two direct generation paths forwarded body priorities unchecked. The frontend now raises `VLLMValidationError` with `parameter="priority"` before engine submission when the effective value is nonzero and the policy is not `priority`.

Clients whose nonzero priorities were previously ignored under FCFS now receive the documented error. The server documentation explains the default FCFS behavior and how to enable priority scheduling.

Header precedence and invalid-header fallback remain unchanged on chat, completions and Responses. Batch chat, token-input generation and pooling retain body-only priority handling.

This change covers the Python serving paths described above. Renderer-only endpoints, offline APIs, the Rust frontend, generative scoring and structured decisions are outside its scope.

Saved open-PR searches for `priority fcfs`, `priority validation scheduling`, `"non-zero" "priority" "scheduling"`, `"priority" "reject" "fcfs"` and `"X-Vllm-Priority"` found no matching policy-validation fix. [#62727](https://github.com/vllm-project/vllm/pull/62727) addresses batch-header propagation, and [#62253](https://github.com/vllm-project/vllm/pull/62253) addressed beam-priority propagation. This change does not duplicate either propagation fix.
