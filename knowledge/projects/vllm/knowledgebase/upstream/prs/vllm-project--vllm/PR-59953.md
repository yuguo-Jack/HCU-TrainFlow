# [Bugfix][NIXL] Count pull completion notifications per transfer

[Upstream PR](https://github.com/vllm-project/vllm/pull/59953) · state: open · merged: False

## Original PR description

## Overview

**We add a generic way to count notifs to expect for a READ that doesn't use consumers as a "proxy", but allows each D to just tell P how many xfers it's started**. This is the case for HiSparse(see below), but also enables future protocols where D may want to send multiple reads (or similarly P writes for push mode, looking ahead).

For HiSparse in particular, mixed DRAM/device NIXL pulls currently notify the producer only after the decoder polls both READ handles complete. Attach native completion notifications to each READ and count them on the producer, so a paused decoder does not strand the producer's release acknowledgement.

Alternative approach to #58041: that PR keeps the paused decoder stepping; this changes pull completion accounting and removes its deferred notification queue.  

Duplicate-work searches found no open PR implementing this protocol change. Broader pause/resume and retained-export semantics remain separate from this change and #59670.

## Claims

- Every posted pull READ carries a completion notification. A split read declares its number of nonempty transfers before either can complete; the producer waits for all of them.
- The producer counts notifications per NIXL sender agent, allowing different readers of the same request to issue different numbers of transfers. Topology still determines how many readers must finish.
- Full cache hits, empty slices, and unused MLA replicas send explicit zero-transfer acknowledgements. Missing completions after partial submission or transfer failure leave the source retained until its existing lease expires.

## Details

The pull notification payload becomes `request_id:expected_readers:transfers_from_this_reader`. `get_new_notifs()` supplies the sender agent identity. The producer retires each reader only after its declared number of notifications arrives, then releases the request once every expected reader is finished. A zero-transfer reader sends one standalone acknowledgement.

Mixed reads prepare every nonempty handle with the full split count before submitting any handle. If only one sibling completes, its notification cannot release the producer's source blocks. Local receive polling, postprocessing, and failure retirement retain their existing responsibilities.

This replaces one manually sent notification per mixed read with one native notification per transfer and adds producer bookkeeping per reader. NIXL connector protocol version is bumped from 13 to 14: P and D must upgrade together. Push notification payloads are unchanged.

Queued reads, handshake progress during pause, lease validity, cache invalidation, and weight-update coordination are outside this PR's claim. In particular, native notifications do not establish full P/D pause/resume safety.
