[Upstream PR](https://github.com/vllm-project/vllm/pull/50778) · state: open · merged: False

## Original PR description

[Bugfix][Elastic EP] Clear scaling flag on failure to prevent permanent 503s

## Purpose

A failed elastic-EP scale could leave the server returning 503 to every request
until the process was restarted.

`_scale_elastic_ep` sets `_scaling_elastic_ep(True)`, which makes
`ScalingMiddleware` reject all traffic while a scale is in flight. It cleared the
flag only on the success path:

    set_scaling_elastic_ep(True)
    if envs.VLLM_ELASTIC_EP_DRAIN_REQUESTS:
        await self._drain_requests_for_elastic_ep(drain_timeout)   # had its own except
    await self.engine_core.commit_elastic_ep()                     # unprotected
    self.vllm_config.parallel_config.data_parallel_size = new_data_parallel_size
    set_scaling_elastic_ep(False)                                  # unreachable on failure

The drain step was covered by its own `except BaseException`, so the `TimeoutError`
that `/scale_elastic_ep` explicitly catches did not wedge anything. But
`commit_elastic_ep()` sat between the set and the clear with no protection. If it
raises, or the task is cancelled there, the flag stays `True` for the process
lifetime — `set_scaling_elastic_ep` has only three call sites and none of the
others clears it.

The router turns the exception into a single 500, so the caller sees one failed
request while every later client sees a dead server. `ScalingMiddleware` has no
path exemptions, so the latched flag also blocks `/scale_elastic_ep` itself —
there is no way to recover through the API — and `/health`, so a Kubernetes
liveness probe fails and the replica enters a restart loop.

Scope: `prepare_elastic_ep()` runs before the flag is set, so a non-elastic-EP
deployment fails early and leaves the flag clean. This affects elastic-EP
deployments specifically.

### The fix

Put the flag's lifetime in a `try/finally` covering the drain, `commit_elastic_ep()`
and the `data_parallel_size` assignment. `finally` also covers
`asyncio.CancelledError`, which is what the old `except BaseException` was
reaching for.

Also removes the now-redundant partial reset in `_drain_requests_for_elastic_ep`.
Its only caller is inside the new `try`. Leaving it would keep two owners of the
flag's lifecycle — the split responsibility that let `commit_elastic_ep()` slip
through uncovered. There is now one set site and one clear site.

| Path | Before | After |
|---|---|---|
| Scale succeeds | cleared | cleared |
| Drain times out | cleared (inner `except`) | cleared |
| `commit_elastic_ep()` raises | **latched permanently** | cleared |
| Task cancelled mid-scale | **latched permanently** | cleared |
| `old_size == new_size` (early return) | never set | never set |

A failed scale now leaves both `_elastic_ep_lock` free (it already released on
exception) and the flag clear, so the operation is retryable rather than needing
a pod restart. No behaviour change on the success path. No effect on model
outputs — this touches only the HTTP-availability flag, not tokenization,
sampling or engine numerics, so no accuracy evaluation applies.

- itayalroy · comment · 2026-08-09T11:31:03Z · [source](https://github.com/vllm-project/vllm/pull/50778#issuecomment-5231289377)

This is intentional.

If preparation succeeds but draining requests times out, it just means that some requests did not finish within the timeout. This is not fatal, the prepared state is still valid, so we can try draining again and committing.

If commit fails however, we currently have no rollback logic, and we left the system in an undefined state, so we cannot safely serve requests anymore
