# [Bugfix][Frontend] Stop Hermes streaming tool parser leaking keys that follow "arguments"

[Upstream PR](https://github.com/vllm-project/vllm/pull/65247) · state: open · merged: False

## Original PR description

## Overview
 
Fixes #65242. `Hermes2ProToolParser._extract_tool_args` assumed `"arguments"` is the last key of the tool call object, so any key after it leaked into the streamed arguments string. The non-streaming path was already correct; this makes the streaming path agree with it.
 
## Claims
 
- Streamed `arguments` now equal the non-streaming result for `{"arguments": {...}, "name": "f"}` and `{"name": "f", "arguments": {...}, "id": "x"}`; previously they were `{"a": 1}, "name": "f"` and `{"q": 1}, "id": "x"`, not valid JSON.
- No behaviour change while the arguments value is still partial (still streaming), and none for the existing test inputs.
- 10-line change in one function plus a parity test; no new dependencies.

Reproduction script from the issue (token-by-token streaming with the `Qwen/Qwen3-32B` tokenizer) prints `MATCH` for both shapes on this branch and `MISMATCH` on `main`. Run on CPU, editable install with `VLLM_USE_PRECOMPILED=1`.
 
## Details
 
Root cause: the streaming helper sliced by position (`tc_json[match.end():]`, then strip one `}` when complete) instead of by JSON value boundary. The fix calls `json.JSONDecoder().raw_decode(tc_json, match.end())`, which parses exactly one JSON value and returns where it ends; the slice stops there. If the value is not yet complete, `raw_decode` raises and the helper returns the raw tail as before. This is the same technique #48353 uses on the non-streaming path for a different problem.
 
Not a duplicate: #53638 rewrites the same function with brace matching to handle a stray `<tool_call>` marker under speculative decoding and bundles a spec-decode gate; this change is independent and much smaller. #45310 / #48353 / #63327 / #63375 address `</tool_call>` boundaries and malformed regions, not key order. #51937 migrates Hermes to the Parser Engine; the parity test added here is useful for that migration as well.
 
Limitations: `_extract_tool_name` still takes the first `"name": "..."` in the body, so `{"arguments": {"name": "Bob"}, "name": "f"}` would report the wrong tool name in streaming. That is a separate issue and is not changed here. The `is_complete` parameter of `_extract_tool_args` is no longer used inside the helper; I left the signature unchanged to keep the diff minimal and can remove it if preferred.
 
AI assistance: Claude was used to validate the test; I reproduced the failure on `main` with the Qwen3 tokenizer, reviewed every changed line, and ran the tests listed above. Commit carries a `Co-authored-by` trailer per the contributing guide.
