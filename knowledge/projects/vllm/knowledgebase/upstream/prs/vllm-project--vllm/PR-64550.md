# [Misc] Watermarking: read the key from a file

[Upstream PR](https://github.com/vllm-project/vllm/pull/64550) · state: open · merged: False

## Original PR description

## Overview

Adds `key_file` to `WatermarkConfig`, so the watermark key can come from a mounted secret instead of the command line, and stops `WatermarkConfig` validation errors from quoting the key. Related: RFC #53916.

## Claims

- `--watermark-config '{"algorithm":"gumbel","key_file":"/run/secrets/watermark_key"}'` reads the key once at startup. `key` and `key_file` are mutually exclusive; `key` works as before.
- Errors about the key file name the file but never quote its content.
- `WatermarkConfig` validation errors no longer quote the input. On `main`, `WatermarkConfig(key=2**64)` prints the key in the error message.
- No change to generation, detection or performance; only how the config is built.

## Validation

**Unit tests**, both in the "Engine Core" CI step:

```bash
pytest tests/test_config.py tests/engine/test_arg_utils.py -k watermark   # 21 passed
```

- `test_watermark_config_cli_reads_key_file` parses `--watermark-config '{"key_file": ...}'` through `EngineArgs`.
- `tests/test_config.py` covers `key` with `key_file`, invalid content (`not-a-key`, `-5`, `2**64`, `+1000`, `1_000`), a missing file, and errors that must not quote the key.
- Both no-quote tests fail without their fix: with a plain `int()` the error contains `invalid literal for int() with base 10: 'not-a-key'`; without `hide_input_in_errors`, the key appears in the message.

**Failure before the fix** (commit 2), on `main`:

## Details

**Motivation.**
- **The key leaks through the command line.** `--watermark-config '{"key":...}'` puts it in `ps` output, `docker inspect`, Kubernetes pod specs and shell history.
- **Containers already deliver secrets as files.** Docker and Kubernetes mount them that way, and images such as Postgres or RustFS read them through a `*_FILE` setting.
- **The workaround is a shell wrapper.** Without this change, a deployment has to write the key into a generated `--config` file before starting vLLM.

**Design.**
- **`key_file` is a config field, not an environment variable.** That way it works with `--watermark-config` JSON and the Python API.
- **A `before` validator reads the file.** It uses the same pattern as `PoolerConfig.reject_removed_parameters` and injects `key` from the file. `key` stays an `int` and no caller changes.
- **The file is read where the config is built,** in the API server or in `LLM`. The engine-core processes receive the resolved key with the pickled config, so the file only has to exist where the config is constructed.

**Related work and duplicates.** Related but separate: #62966 (`watermark_config.enforce`, server-side override of request opt-outs).

```suggestion
_DECIMAL_KEY = re.compile(r"[0-9]{1,20}")

def _read_key_file(path: str) -> int:
    try:
        text = Path(path).read_text().strip()
    except OSError as error:
        raise ValueError(
            f"Cannot read watermark key file {path!r}: {error.strerror}"
        ) from None
    if not _DECIMAL_KEY.fullmatch(text) or int(text) > 2**64 - 1:
        raise ValueError(
            f"Watermark key file {path!r} must contain a decimal integer "
            "between 0 and 2**64 - 1."
        )
    return int(text)
```
