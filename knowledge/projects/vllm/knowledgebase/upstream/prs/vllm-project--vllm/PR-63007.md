# [Bugfix][ROCm][DSv4.1] Gather Engram hashes across DP replicas in the AMD model

[Upstream PR](https://github.com/vllm-project/vllm/pull/63007) · state: closed · merged: True

## Original PR description

The AMD DeepSeek V4.1 model never got the data-parallel Engram wiring that #56512 and #57651 added to the NVIDIA model. Whenever DP > 1 splits the Engram tables across replicas, ROCm returns wrong Engram rows, and the V1 model runner hangs. This PR ports that wiring.

`Engram._ready_rows` assumes the staged rows came from hashes gathered across the DP group: one slot of tokens per replica, which it then all-gathers and slices. The AMD model passed only its own hashes. As a result, rank 0 read its peer's heads for the peer's own tokens, and rank 1 read stale staging rows. On the V1 runner, an idle replica skipped the Engram lookups while the busy replica blocked in the DP all-gather, so the engine hung. The default `dp_shared_memory=true` path does not use the DP gather, so DP deployments that fit in `/dev/shm` were unaffected.

The fix mirrors the NVIDIA model line for line. With DP1, `gather_engram_hashes` returns its input unchanged and the dummy-hash branch is never taken. The THP hooks (`drop_checkpoint_cache`, `collapse_huge_pages`) only affect memory, not correctness, so they are left for a follow-up. On ROCm CI, the multi-GPU test only runs once the CUDA-only skip is lifted, which #62298 does.

- `amd/model.py`: look up the hashes gathered across the DP group (`gather_engram_hashes`), not just this replica's hashes.
- `amd/model.py`: give a replica with no attention metadata `dummy_hashes`, so it still joins the DP-sharded lookup collectives.
- `amd/model.py`: call `can_share_engram_tables` before building the layers. When `/dev/shm` is too small, ROCm now logs a warning and falls back to sharded tables, as NVIDIA does, instead of failing at startup.
- `test_engram_dp_shard.py`: on ROCm, the dummy-hash model-forward check runs the AMD model instead of the NVIDIA one.

Validated on MI300X, DP2 x TP1 on 2 GPUs, dummy weights. The proxy is DeepSeek-V4.1-Flash's config cut to 24 layers and 8 experts. A full-size check also used the 40-layer, 32-expert proxy with its two 23.6 GiB tables. Every Engram table row is filled with a fixed function of its global row id. A test-only hook checks each `Engram.embed` result against that function, so a wrong row shows up directly. Each replica's outputs are also compared with the DP2 `dp_shared_memory` run, which does not use the DP gather and has correct rows. Rank 1 gets one short request, so it runs idle (dummy) steps for most of rank 0's decode.

- 10 loops each of the DP2 sharded e2e on the V2 and V1 runners, with an idle rank: 20/20 finish with 0 wrong Engram rows. 9/10 V2 runs are bit-identical to the shared run. The other runs land on a few alternative outputs, which also appear in the shared mode when rank 0 starts 2 s late. So those differences come from DP batch timing, not from Engram.
- `tests/distributed/test_engram_dp_shard.py` multi-process test, run on ROCm with `WORLD_SIZE=2`/TP1 because only 2 GPUs were available: passes 10/10 with this PR. On main, the AMD forward check fails with `assert hashes is not None` on the idle replica.
- Not run here: the 4-GPU shapes of that test (TP2xDP2, TP1xDP4), MI355X and `--monokernel`.
