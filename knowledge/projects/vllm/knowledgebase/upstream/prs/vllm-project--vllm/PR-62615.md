# [Bugfix][KV Offload] Protect lookup HITs from promotion eviction

[Upstream PR](https://github.com/vllm-project/vllm/pull/62615) · state: closed · merged: False

## Original PR description

## Overview

A primary-tier HIT can be evicted by a later secondary-tier promotion before the scheduler consumes it. This change keeps lookup pins manager-owned and releases them at the load/store handoff or before the manager lock is released.

## Claims

- A primary HIT reported by `lookup()` is pinned before a later promotion can evict it.
- `prepare_load()` and `create_store_job()` take over the needed pins and release all temporary lookup pins held by that request.
- Unconsumed pins are released at schedule end and after each tier-poll round. `reset_cache()` asserts that no lookup-pin owner remains.
- A focused regression test checks that consuming one HIT releases the other lookup pins, allowing a secondary promotion to use the freed slot.

## Validation

- `tests/v1/kv_offload/tiering/test_tiering_offloading.py -k test_prepare_load_releases_all_lookup_pins -q`: 1 passed, 82 deselected. Ran with the main worktree's Python 3.12 venv and its compiled vLLM extension.
- Commit hooks passed for `manager.py` and `test_tiering_offloading.py` (Ruff, typos, mypy, and repository hooks).
- The full CPU/tiering suite passed on the prior PR revision (700 passed, 1 skipped); it was not rerun after this pin-lifecycle simplification.
- No model evaluation applies to this cache-lifecycle fix.

## Details

The scheduler can report a primary HIT before it calls `prepare_load()`. A subsequent lookup may find a secondary-tier HIT and immediately allocate primary space for promotion; eviction during that allocation can remove the earlier HIT.

The manager now tracks temporary pins for one lookup owner at a time. Lookups for a request must remain contiguous until `prepare_load()` or `create_store_job()` consumes them. Starting a lookup for a different request releases the previous owner's temporary pins. Schedule-end and tier-poll cleanup release any unconsumed pins before the lock is released. The consumer first pins its load or transfer keys, then the manager releases all temporary lookup pins.

Reading the v0.32.0 code, the shape matches your failing case. `offloading/scheduler.py` (L687 prefix walk, L724 sliding-window walk) calls `self.manager.lookup(key, ...)` one key at a time. - jsboige · comment · 2026-10-24T18:56:09Z · [source](https://github.com/vllm-project/vllm/pull/62615#issuecomment-6388218127)

Follow-up to my datapoint above, with a fix that covers the scheduler path as well.

**Count update:** our earlier comment reported 2 crashes. The total for that day is 5 (14:32, 15:18, 15:35, 17:10, 17:50 UTC). The stack is identical each time, and the same chunk key crashed the engine twice.

**Fix we are now running** (stock v0.32.0 + 2 files, deployed 18:49 UTC). Rather than reorder the lookup walk, it protects HITs at the manager level, so every caller is covered (the scheduler's prefix walk, its sliding-window walk, and P2P):

- `TieringOffloadingManager.lookup()` records each primary `HIT` it returns during the current step in `_step_hit_keys`.
- `_initiate_promotion()` passes that set as `extra_protected` to `primary_tier.prepare_write()`.
- `CPUOffloadingManager.prepare_store()` merges it with the promoted keys before `self._policy.evict(...)`. It uses a read-only membership view, so nothing is copied, because policies only test `key in protected`.
- The set is cleared at the end of `on_schedule_end()` and in `reset_cache()`. By then, every HIT has either been pinned by `prepare_load()` or belongs to a request that was not scheduled and will be looked up again.
- If no idle chunk is left, `prepare_write()` returns `None`. The promotion then fails and the key is reported as `MISS` (recompute) instead of crashing in `prepare_load()`.

**Tests** (5-chunk primary + `ExampleSecondaryTierManager`):
1. In one step, `lookup(oldest)` returns HIT, then `lookup(secondary_only)` returns HIT_PENDING, then `prepare_load([oldest])`. On stock this raises `AssertionError: Chunk ... not found in cache`, the production message verbatim. With the patch it passes.
2. When every resident chunk was a HIT this step, the secondary lookup returns `MISS` and `prepare_load(all)` succeeds.
