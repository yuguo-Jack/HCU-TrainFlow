# [Observability] Add opt-in diagnostics for stalled engine stages

[Upstream PR](https://github.com/vllm-project/vllm/pull/49628) · state: open · merged: False

## Original PR description



## Purpose

Production engine stalls are difficult to diagnose when the EngineCore process remains alive but stops making progress. These incidents do not raise an exception, so the existing exception-triggered diagnostic path never runs. Operators may see requests hang without enough evidence to determine whether the engine is waiting on model execution, token sampling, structured output processing, or another thread.

This PR adds an opt-in, stage-aware watchdog for slow V1 engine execution. When a monitored stage exceeds the configured timeout, vLLM captures the scheduler state associated with that iteration and prints Python stack traces for all threads while the stall is still occurring.

This provides production operators with:

- The stalled stage: `execute_model`, `execute_model_wait`, `sample_tokens`, or `sample_tokens_wait`.
- A bounded configuration and scheduler summary, including queue state and request counts.
- Up to 20 representative request samples distributed across new and cached requests.
- Request IDs for correlation, with oversized IDs bounded and accompanied by their length and SHA-256 digest.
- Relevant sampling parameters, token counts, KV-block counts, multimodal counts, and embedding shapes.
- Python stack traces for every thread in the EngineCore process, which help identify where execution stopped making progress.
- Per-watchdog, per-stage throttling so a persistent stall does not flood production logs.

Prompt text, prompt token values, generated token values, multimodal contents, and unrestricted configuration objects are intentionally not logged. The complete structured summary is capped at 32 KiB.

The feature is controlled by a dedicated environment variable:

```bash
export VLLM_ENGINE_SLOW_STAGE_DUMP_S=60
```

The diagnostic is disabled when the environment variable is unset or set to `0`. In the disabled path, no watchdog thread is started and no diagnostic snapshot is constructed.

The diagnostic path is designed to fail open:
- Failure to start the watchdog disables only the diagnostic and does not prevent EngineCore startup.
- Snapshot failures fall back to a minimal diagnostic.
- Context-generation failures are reported without interrupting request processing.
- Watchdog shutdown is bounded.
- Repeated dumps for the same stage are throttled for 300 seconds.
- Throttle state belongs to each watchdog instance, so one EngineCore does not suppress diagnostics from another EngineCore in the same process.

This extends the existing exception-only dump path to cover the distinct “alive but stuck” failure mode. I did not find another open PR implementing the same V1 slow-stage watchdog.
AI assistance was used while developing this PR. I reviewed every changed line and validated the implementation and its performance.

## Test Plan
Unit/static checks:
```bash
uv run ruff check \
  vllm/logging_utils/dump_input.py \
  vllm/v1/engine/core.py \
  tests/v1/engine/test_slow_stage_diagnostics.py \

python -m py_compile \
  vllm/logging_utils/dump_input.py \
  vllm/v1/engine/core.py \
  tests/v1/engine/test_slow_stage_diagnostics.py

PYTHONPATH=. python -m pytest \
  tests/v1/engine/test_slow_stage_diagnostics.py \
  tests/v1/engine/test_engine_core.py::test_async_step_skips_sampling_for_mm_encoder_only
  -q
```

The focused tests cover:
- Default-off behavior without a watchdog thread or diagnostic snapshots.
- Watchdog startup failure and bounded shutdown.
- Arming, disarming, stale generations, re-arming, and race-sensitive wakeups.
- Every retained execution stage and EngineCore batch-queue wiring.
- Synchronous `execute_model` stalls and incomplete asynchronous futures.
- Per-watchdog and per-stage throttling.
- Snapshot failures and diagnostic-output failures.
- Bounded output and request-ID truncation.
- Sampling fairness across new and cached requests.
- Sampling-parameter cache pruning.
- Sampling-parameter summarization only for requests selected for the bounded diagnostic.
- Prompt, token, and configuration sanitization.
- Real SchedulerOutput, NewRequestData, and CachedRequestData objects.
- Real VllmConfig, ModelConfig, SchedulerConfig, CacheConfig, ParallelConfig, OffloadConfig, and SpeculativeConfig field contracts, so future allowlist drift fails CI.
- Current CPU-offload reporting through OffloadConfig; the removed swap-space field is not reported.

Runtime smoke validation on an H100:
1. Start vLLM with VLLM_ENGINE_SLOW_STAGE_DUMP_S=1.
2. Inject a temporary local delay into `execute_model_wait` to deterministically trigger the watchdog.
3. Send an OpenAI-compatible completion request.
4. Verify that the diagnostic reports the stage, scheduler summaries, and EngineCore stack traces.
5. Verify that the request still completes successfully with 200 OK.
6. Verify that another timeout for the same stage is throttled.
7. Separately inject a 1.5-second delay into synchronous `UniProcExecutor.execute_model`.
8. Verify that the watchdog reports the `execute_model` stage while the synchronous call is blocked and that inference still completes normally.
