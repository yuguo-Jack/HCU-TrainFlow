# [RL][Model Loader] Direct weight reload: write checkpoint tensors into the live model

[Upstream PR](https://github.com/vllm-project/vllm/pull/64336) · state: closed · merged: True

## Original PR description

Thanks to Tony Wang (@new-TonyWang) for design and review contributions.

## Problem

RL weight sync reloads the checkpoint into a serving engine. The layerwise reload moves every layer to meta, materializes it again, loads the checkpoint and reruns post-load processing per layer. That costs a second copy of each layer at a time, and its correctness depends on per-layer completeness bookkeeping, so partial or reordered updates are hard to get right.

## Fix

`VLLM_RELOAD_MODE=direct` (registered in `vllm/envs.py`, ignored by `compile_factors`; the default stays `layerwise`) writes checkpoint tensors straight into the live model and reruns cold-start post-load processing once, at the startup addresses:

- At cold start, before `process_weights_after_loading` (PWAL), record each tensor's checkpoint layout and the parameter names that hold checkpoint tensors.
- `start_reload` / `finish_reload` (`reload/lifecycle.py`) dispatch on `VLLM_RELOAD_MODE`, which is fixed for the process (workers cache envs after init). The NCCL, IPC and M2N engines and `reload_weights` call them and pass their device through.
- `begin_direct_reload` views every tensor whose layout PWAL changed back to its checkpoint layout, on the same storage, and restores the loader metadata (packed/input/output dims) PWAL retagged on a kept parameter (AWQ repacks along another dim). The loaders then write the checkpoint tensors in place.
- `finish_direct_reload` clears the one-shot "already processed" guards of quant methods and reruns PWAL for every module, then the model-level hook, as cold start does.
- `replace_parameter` keeps a parameter's address when PWAL changes its layout. Since #62407, main already copies a `new_tensor` into the parameter's own storage when it fits in the old tensor's range (`_in_own_storage`). In direct mode, `_in_own_storage(whole_storage=True)` writes the new tensor into a view of the existing storage whenever it fits in the storage, so a weight that grows on reload keeps its address too, as do a padded view with gaps (ROCm FP8 padding) and an emptied weight. It never copies a `new_tensor`'s recorded checkpoint layout onto the target.
- Refused at startup, by config validation (`VllmConfig._verify_direct_reload_compat`, `ValueError`):
  - `draft_lm_head_quantization`: the quantized draft lm_head would be written into the target lm_head it shares;
  - an online quantization config, alone or on top of a checkpoint config: finish clears the guard that keeps it from quantizing already-converted bytes again;
  - torchao: its `load_weights` runs a layerwise reload, and its PWAL replaces the weight parameter;
  - weight offloading (CPU/UVA and prefetch): CPU/UVA offload gives parameters new storage on every PWAL, and prefetch offload shares one buffer between layers;
  - LoRA: it wraps layers after cold start, and the wrappers forward `quant_method`, so finish would process each base layer twice. Support is follow-up F11 in the tracker;
- Still refused at cold start, by a module scan before PWAL (`RuntimeError`):
  - online linear/MoE methods (also without an online config, e.g. `experts_int8`) and online fused shared experts: finish clears the same guard;
  - humming (linear and MoE): its PWAL runs once per quant method (a guard on the method, not the module), so a reload would keep the checkpoint bytes. For online fused shared experts, PWAL also deletes the staging parameters a reload would load into.
- Refused at `begin`, before anything is modified:
  - no layout was recorded (also the case for pre-processed IPC weight-cache weights, already in runtime layout);
  - PWAL registered a new parameter object under a checkpoint name. The loader would write checkpoint bytes into its runtime layout. This enforces the #62407 contract instead of assuming it;
  - a storage is too small for its checkpoint layout;
  - a tensor shared from another model (a target `lm_head` or embedding in a draft) whose PWAL changed its layout, e.g. a quantized target `lm_head`: the draft's finish would reprocess bytes a draft update does not resend. No flagship checkpoint quantizes its `lm_head`, so an unquantized shared module (PWAL a no-op) is reprocessed harmlessly.
- Marlin writes the permuted bias in place (`replace_parameter`) instead of rebinding `.data`, so captured CUDA graphs keep reading it.
- `sharded_rdt` with direct mode is refused by the same startup config validation, because its replay plan is baked by a layerwise (meta) dry run.
- Between `begin` and a successful `finish`, the model holds checkpoint-layout bytes and must not run. There is no rollback: after a failed update, the next full update repairs the model. A finish without a `begin` (e.g. retried after a failed finish) raises instead of running again, because some modules may already be processed; on a failed direct finish the worker ends the weight-update session, so a new full update can start. A failed layerwise finish stays active and can be retried, as before.

**Delivery contract.** An update must deliver every checkpoint tensor of each module whose PWAL changes the tensor's layout or is not idempotent. Tensors without such processing, for example a frozen embedding table, may be left out and keep their bytes. **Nothing in this PR checks the contract**: until the completeness follow-up (F2, aoshen02/vllm#176) merges, a violation is not detected.

**Known limitations**

- Nothing refuses to run a model whose direct update is pending or failed. After a failed `update_weights` chunk, the worker resumes serving with checkpoint-layout bytes in re-laid-out tensors: output is silently wrong until the next full update, where layerwise mode would fail loudly on meta tensors.
- PWAL code that rebinds `.data` of a checkpoint tensor moves its address; nothing checks this until F4 (aoshen02/vllm#177). Known remaining sites are platform-specific: quark W4A16 (AMD), XPU / ROCm gfx11 weight padding in `linear.py`, FlashInfer b12x MoE (SM12x).
- The direct-mode `replace_parameter` views and the `begin` views are bounded by the storage size, not by the tensor's own range, so they assume nothing else lives in that storage. No overlap check exists yet, and F4 (aoshen02/vllm#177) does not add one. The one known in-tree case, the DeepSeek-V4 ROCm fused compressor weight, is noted on aoshen02/vllm#180.
- Non-default MoE backends whose PWAL reallocates derived constants on a rerun are not yet refilled in place: TRTLLM FP8 per-tensor, FlashInfer CUTLASS NVFP4/MXFP4, CuteDSL, and compressed-tensors FP8 constants. They are fixed in the derived-tensor follow-up (aoshen02/vllm#180).
- Online quantization and `draft_lm_head_quantization` are refused until F8 (aoshen02/vllm#190) / F7 (not opened).
- PWAL code must not read a local alias of a parameter's old data (`w = layer.weight.data`) after `replace_parameter` grows it: on a reload the new tensor may be written over those bytes. No such call site is known; the `replace_parameter` docstring says so.

## Tests

- `tests/model_executor/model_loader/test_direct_reload.py` uses a toy model with the hazards found on real models: a parent-derived tensor, a layout change, a loader bypass, a consumed scale, non-idempotent packing and a padded (growing) weight. It checks:
  - a reload equals a fresh cold start bit for bit, at unchanged addresses;
  - an unsent table without PWAL keeps its bytes;
  - refusals leave the model untouched (storage too small, replaced parameter object, online quantization (method, config alone or composed, fused shared experts), draft lm_head quantization, torchao, weight offloading, LoRA, humming linear and MoE);
  - an aborted update stays pending and can be retried;
  - `start_reload` / `finish_reload` run a direct reload at unchanged addresses, and a finish retried after a failed finish is refused;
  - a padded view with gaps and an emptied weight keep their addresses across a reload;
  - `replace_parameter` keeps the target's checkpoint layout;
  - `begin` restores retagged loader metadata;
  - a draft sharing a re-laid-out target module is refused, with the target untouched;
  - guards of modules without a quant method are kept.

Review of f301b8b (codex gpt-6-astra at ultra effort plus an independent Claude review; I re-checked each item in the code). The default layerwise path is unchanged. Everything below affects only `VLLM_RELOAD_MODE=direct`, and most of it gives silently wrong output.

### Major

1. **Shared storage after PWAL.**
   - `begin` reuses the cold-start `storage_offset` on the storage the parameter has after PWAL, and only bounds the view by that storage's size.
   - DeepSeek-V4 ROCm `prepare_compressor_gemm_fusion` (`models/deepseek_v4/amd/rocm.py:1248-1251`) views the indexer weight at offset 0 of the fused buffer, so a reload writes the indexer checkpoint over the main compressor.
   - Finish cannot repair this: it returns early because `_fused_compressor_weight` exists.
   - The PR body lists this case as known, but nothing refuses it.
   - *Fix:* record the storage pointer at cold start. If the storage changed, refuse (or use the current offset bounded by the tensor's own range), and check views for overlap.
2. **PWAL that rebinds `.data` moves addresses, and finish never checks `data_ptr`.**
   - `layer.bias.data = marlin_permute_bias(...)` (`kernels/linear/mixed_precision/marlin.py:181`) affects every GPTQ/AWQ-Marlin model with a bias, e.g. Qwen2/2.5 qkv. After a reload, the CUDA graph keeps reading the old storage, which now holds the raw, unpermuted checkpoint bias.
   - The same pattern appears in `quark_w4a16_int4.py:178/185`, `linear.py:228/230` (XPU / ROCm gfx11 padding) and `flashinfer_b12x_moe.py:106/111`.
   - *Fix:* snapshot `data_ptr` before finish PWAL, then copy back or raise if it moved; or convert these sites to `replace_parameter`.
3. **`begin` does not restore MP-linear loader metadata.**
   - `replace_parameter` and `permute_param_layout_` write runtime `_packed_dim` / `_input_dim` / `_output_dim` onto the kept parameter object (`auto_awq.py:132-140`, `parameter.py:567-574`).
   - On reload, the fused QKV and merged loaders read these runtime dims (`parameter.py:176-189`), so the shard math is wrong: it either asserts or writes the wrong rows.
   - Confirmed for AWQ. GPTQ and compressed-tensors WNA16 use the same code and are likely affected too.
   - *Fix:* record the metadata alongside `_ckpt_layout` and restore it in `begin`, or refuse these kernels.
4. **Direct finish re-ties word embeddings** (`model_loader/utils.py:159` → `maybe_retie_word_embeddings`).
   - If one update has `lm_head == embed_tokens`, `lm_head` becomes the embedding parameter, and `AutoWeightsLoader` then skips any later, different `lm_head`. Layerwise mode does not do this.
   - It also copies both vocab tables to the host on every update.
   - *Fix:* skip the retie in direct finish.
5. **Known limitations that should be refused rather than documented:**
   - a model whose update is pending or failed keeps serving;
   - a draft-only update reprocesses a quantized `lm_head` it shares with the target.

### Minor
- Finish does not clear Zentorch's `_zentorch_processed_weights` guard, so weights are not repacked on reload (CPU only).
- `_check_params_kept` misses parameters set to `None` or deleted, and replaced buffers.
- `start_reload` should refuse while a direct reload is pending. Today it runs a full layerwise load before failing, with a misleading error.

### Tests
- Not covered: items 1–4 and draft/target sharing.
- The worker test sets the pending flag by hand instead of reading it through `get_model()`.
- `test_layerwise_finish_does_not_keep_addresses` mocks both layerwise functions, so it only checks the ContextVar.

### Simplifications
- Choose the mode once at cold start and store it on the model. This removes `_reload_mode`, `keeping_addresses(False)` and the env-flip tests.
- Merge `_view_in_place` and `_in_own_storage` into one function with a `bound=` argument.
- Factor out the duplicated worker teardown.

The same pattern appears in:
- `quark_w4a16_int4.py:178/185`
- `linear.py:228/230` (XPU / ROCm gfx11 padding)
- `flashinfer_b12x_moe.py:106/111`

Suggest snapshotting `data_ptr` before this PWAL, then copying back or raising if it moved. Alternatively, convert those sites to `replace_parameter`.
