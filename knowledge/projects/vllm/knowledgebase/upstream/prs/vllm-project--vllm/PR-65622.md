# [Rust Frontend] Count vllm:watermark_requests from the engine-reported flag

[Upstream PR](https://github.com/vllm-project/vllm/pull/65622) · state: open · merged: False

## Original PR description

## Overview

With a `watermark_config`, the Python frontend exports `vllm:watermark_requests{status}` (vllm-project/vllm#58715): every finished request counts once as `watermarked`, `skipped` (it asked for watermarking but the sampler cannot apply it, e.g. greedy or trace replay) or `not_watermarked` (it opted out with `watermarking=false`). The Rust frontend never exports the family, and `docs/features/watermarking.md` says so.

Since vllm-project/vllm#62966, EngineCore decides the final flag itself: `watermark_config.enforce` overrides request opt-outs, and the scheduler reports what the sampler applies in a new trailing `EngineCoreOutput.watermarking` field, set on the request's first output and only when the engine has a `watermark_config`. Python's `IterationStats` takes `is_watermarked` from that field. Rust decodes `EngineCoreOutput` with `AllowTrailingFields`, so today it silently drops the field.

This PR decodes the field and counts each finished request by the engine-reported flag, like Python.

## Claims

- `vllm-engine-core-client`: decode the trailing `watermarking: Option<bool>` on `EngineCoreOutput`; the Python msgpack fixture now sets it.
- `vllm-metrics`: register `vllm:watermark_requests` with labels `model_name`, `engine`, `status`.
- `vllm-llm`: the request metrics tracker keeps whether the request asked for watermarking (`EngineCoreSamplingParams.watermarking`, `true` unless the client opted out). When an output carries the engine's flag it picks the status (applied → `watermarked`; asked but not applied → `skipped`; opted out and not enforced → `not_watermarked`) and counts it once at finish, like Python's `update_from_finished_request`.
- Docs: drops the stale line in `docs/features/watermarking.md` saying the Rust frontend does not export the counter.

## Validation

New test `vllm-llm` `generate_records_watermark_status_reported_by_engine` drives three requests through a mock engine, each reporting the flag on a non-terminal first output and finishing on a later one: a greedy request reported as not applied (`skipped`), an opt-out the engine enforces (`watermarked`), and a plain opt-out (`not_watermarked`). It snapshots the counters before the first request (no series) and after each request. Red-green: classifying from the request alone (ignoring the engine flag), swapping `skipped` and `not_watermarked`, or reading the flag only from the terminal output each fail it. `python_msgpack_fixtures_match_rust_encoding_and_record_nixl_metrics` checks the new field against Python's msgpack encoding.

## Details

**Layering.** The consumer of the new wire field is the per-request metrics tracker in `vllm-llm`, which already turns `EngineCoreOutput` fields into request counters (`num_nans_in_logits` → `vllm:corrupted_requests`). The engine owns the decision (enforcement, greedy, trace replay), so Rust takes the applied flag from it instead of re-deriving Python's frontend `resolve_watermarking`, and needs no `--watermark-config` in the frontend.

**Deviations from Python:**

- **Series appear on the engine's first report, not at startup.** Python creates the three series per engine from its own `vllm_config.watermark_config`. The Rust frontend has no copy of that engine config (a `--watermark-config` frontend arg could disagree with an externally launched engine; a new `EngineCoreReadyResponse` field would be a Python change), and the engine-reported field is the only signal. The three series of an engine are created together, at zero, when its first output carries `watermarking`.
- **Requests that finish before their first output are not counted** (aborted while queued, rejected by the engine): the engine never reports a flag for them. Python counts them by its frontend prediction. No tokens were sampled for them, so no status describes an output.

**Not a duplicate.** No open PR adds `vllm:watermark_requests` or reads `EngineCoreOutput.watermarking` in the Rust frontend (searched open PRs for `watermark_requests`, `watermarking rust frontend` and `watermark metrics`). The open watermarking PR vllm-project/vllm#56859 adds a new algorithm on the Python side.
