# [KV Offload] Carry request provenance through stored events

[Upstream PR](https://github.com/vllm-project/vllm/pull/52103) · state: open · merged: False

## Original PR description

## Purpose

Carry request provenance through asynchronous KV-offload completions so locally initiated stores and promotions can emit full `BlockStored` events.

The current tracker snapshots full payloads at scheduler lookup/store time and keeps them in a global map. This PR instead keeps a lazy event locator with the request and builds the payload when the raw stored event arrives.

```text
Request + KV-group geometry
            |
     ReqContext event state
            |
   existing async job paths
            |
CPU / FS / OBJ completion
            |
OffloadingEvent(key, ReqContext)
            |
      full BlockStored
```

## Changes

- Attach request-scoped event state to `ReqContext`.
- Lazily resolve a stored key to its full-chunk or partial-tail boundary.
- Carry the exact `ReqContext` through CPU, FS, OBJ, cascade, and promotion completion.
- Use context identity, not request ID, when an old completion is finalized.
- Generate GPU-equivalent per-block `extra_keys`, including multimodal and prompt-embedding inputs.
- Keep placeholders for external work, unsupported cache shapes, and unsafe token-mutating requests.
- Keep only detached chunk hashes for the existing CPU removal contract; #49413 PR 2 removes that table.
- Preserve queued CPU removals and their detached expansion metadata across reset.
- Move context ownership from active work to the raw stored event, then release it after translation; failed submissions and shutdown unwind their owners.

## Scope

This PR does not change:

- `OffloadKey = (block_hash, group_idx)`;
- `prepare_store` admission or batching;
- worker transfer metadata;
- the legacy expanded-removal contract; or
- the public KV-event schema.

Single-key admission, k-way ordering, and #44865 remain separate work.

This PR is based on the KV-group block-granularity fix merged in #51614. Token-mutating paths affected by #49377 keep placeholder payloads until their hash and offload state are safe.

- Whamp · comment · 2026-08-29T15:58:34Z · [source](https://github.com/vllm-project/vllm/pull/52103#issuecomment-5463400613)

Thanks for handling the stale-result case here. I ran into the same cleanup/relookup race while preparing a smaller fix and noticed one behavior that may be worth preserving.

With this branch, `cleanup()` deletes an unresolved `LookupState`. If another request asks for the same key while the original `batch_lookup()` is still running, it creates a new generation and submits a second backend probe. The generation check safely ignores the old result, but the filesystem or object-store backend still does the lookup twice.

Both current production implementations derive the result from the key and do not use `ReqContext`, so the in-flight result can be shared. I tested an alternative that keeps unresolved state until the result arrives, lets a later request attach to it, and discards the result if no request claims it. The deterministic regression blocks the backend and verifies that only one probe runs: https://github.com/Whamp/vllm/commit/ce61e390551ec85c2daf91b27dc75bac3bd13061

I did not open a separate PR because this one already covers the same lifecycle. Would you be open to folding that behavior into this cleanup path? I can also adapt the regression to the request-context IDs used here if that would help.

- hyeongyun0916 · comment · 2026-10-09T03:25:29Z · [source](https://github.com/vllm-project/vllm/pull/52103#issuecomment-6073641580)

Following up from Slack, posting our flow and what we need from the events here so it's on the record.

We subscribe to vLLM's KV event stream (`BlockStored` / `BlockRemoved`) out of process and
build a prefix-cache-aware routing index across workers. Engine hashes are worker-local, so
they can't serve as cluster-wide keys: we re-key each block from its token content instead of
the engine's hash, deriving the chain's root seed from that block's cache identity.

**Flow**: CPU-tier offload. The goal is to keep a pod that still holds a prefix in CPU memory
routable after those blocks are evicted from GPU.

**What we need**: that an offload `BlockStored` carries the same per-block `extra_keys` as the
GPU `BlockStored` for the same block — the `cache_salt` on the block at `start_token_idx == 0`,
plus any mm identifiers overlapping the block, aligned 1:1 with `block_hashes`.

The identity mismatch raised in #49413 shows up on our side like this: we drop every parentless
offload event that carries no extras, because indexing one as unsalted would let a request with
no salt match another tenant's blocks. Dropping that root also strands the blocks chained behind
it, so the CPU tier disappears from the routing index entirely — including on deployments that
never send a salt.

Once the shape is settled we can confirm from our side that an out-of-process consumer decodes
the actual wire bytes and derives the same key as the GPU event. Happy to review the PR as well.

- Change72 · comment · 2026-10-09T05:31:39Z · [source](https://github.com/vllm-project/vllm/pull/52103#issuecomment-6074947803)

@hyeongyun0916 Thanks for laying out the use case. This is exactly the CPU-tier flow aims to support. The branch builds per-block `extra_keys` using the same helper as GPU events; I’m checking the on-wire result shortly.

One question: do you need to distinguish missing `extra_keys` (`None`) from `[None]`, e.g. `extra_keys=None` and `extra_keys=[None]`, which explicitly describes an unsalted block? 

- hyeongyun0916 · comment · 2026-10-10T08:04:10Z · [source](https://github.com/vllm-project/vllm/pull/52103#issuecomment-6095484469)

Yes, having the distinction would help.

On the consumer side, when `extra_keys` is absent we have to know whether the block is unsalted or salted with the extras simply not carried. LMCache CPU events don't have an `extra_keys` field yet, so today we can't tell the two apart and drop parentless offload events that carry no extras.

If #52103 sends unsalted blocks as `[None, …]`, the same way GPU events do, we can split them: treat `[None, …]` as unsalted and index it, and keep treating events with no `extra_keys` (LMCache, or older vLLM) as unknown and drop them. So `[None, …]` would work better for us.
