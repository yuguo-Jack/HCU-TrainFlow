# [Perf][Attention] Candidate-only FP8 indexer decode scoring on SM90

[Upstream PR](https://github.com/vllm-project/vllm/pull/62000) · state: open · merged: False

## Original PR description



> **Status: draft.** Opened early to get direction feedback before investing in
> the long-term version. The optimization itself works and is measured; the
> path-selection policy is deliberately provisional and will be reworked (see
> [Roadmap](#roadmap)). Comments on the approach are more useful than comments
> on the gating details, which are expected to change.

## Overview

On SM90 the DSv4.1 candidate-consuming indexers have no paged sparse scoring
kernel, so they score the entire compressed context per decode row and then
mask down to the candidate blocks. This adds an opt-in path that gathers the
candidate K from the paged FP8 indexer cache and scores only the candidates.
Implements the alternative-A direction of #61830.

Not a duplicate: #57858 and #57859 implement candidate-only scoring for ROCm
(gfx950); this is the SM90/CUDA counterpart called for in #61830.

## Claims

Claiming only what is measured at this stage:

- At ~1M context, 9 concurrent requests on 8x H20 (TP8): the four
  candidate-consuming indexer layers drop from **9.57 ms to 3.05 ms** per step,
  and per-step time from **39.04 ms to 31.53 ms** (profiler-derived).
- Selected top-k sets are equivalent to the existing dense score-then-mask
  path.
- Default behaviour is unchanged: the feature is off by default, and
  unsupported shapes or platforms fall back to dense rather than failing.
- Known cost: a single-request step is about **11.6% slower** than dense, since
  the candidate path carries a per-step fixed cost. The provisional workload
  gates exist to avoid that region until a better policy lands.

## Validation

Setup: 8x H20, TP8, DSv4.1, `num_speculative_tokens=5`, ~1M token context.
With `1 + 5 = 6` tokens per request the SM90 paged kernel takes the flatten
path, so one active request contributes roughly 6 decode rows.

**Kernel / unit**

```bash
pytest tests/kernels/attention/test_candidate_gather_cudagraph.py
pytest tests/model_executor/layers/test_mla_short_prefill_indexer.py
```

- `test_candidate_gather_cudagraph.py` (new): gather + scoring + remap under
  CUDA graph capture and replay.
- `test_mla_short_prefill_indexer.py` (extended): dense vs. candidate-only
  equivalence of the selected top-k set.

**Equivalence**

With `VLLM_DSA_CANDIDATE_GATHER_FORCE=1`, the selected top-k index set matches
the dense path on identical inputs. Note that #61830's alternative-A hoped for
bit-identical results; this verifies set equivalence instead, since the
gather-then-score path uses a different scoring kernel and top-k tie-breaking
can differ (documented in the module docstring).

**Server-level**

Real `vllm serve` at ~1M context, torch profiler traces collected with the
feature off and on:

| Configuration | Per step | Four consumer indexer layers |
| --- | --- | --- |
| Dense (feature off) | 39.04 ms | 9.57 ms |
| Candidate-only (feature on) | 31.53 ms | 3.05 ms |

at 9 concurrent requests (~54 decode rows).

To reproduce, enable on an SM90 FP8-cache deployment:

```bash
export VLLM_DSA_CANDIDATE_GATHER_DECODE=1
export VLLM_DSA_CANDIDATE_GATHER_MIN_ROWS=16
```

**Validation still in progress** — explicit about what the numbers above do
*not* yet cover, and queued in this order:

1. A profiler-free end-to-end throughput/latency A/B (current timings are
   profiler-derived).
2. Model-level accuracy evaluation plus an independent numerical reference
   (correctness evidence so far is top-k set equivalence against vLLM's own
   dense path).
3. Cross-hardware validation on SM90 parts other than H20 — the reason no
   crossover constant is hardcoded.

I will keep appending results to this PR as they come in.

## Details

**Why the dense path is wasteful here.** The candidate-consuming indexers are
handed a small, fixed-width candidate set, but SM90 lacks a paged sparse
scoring kernel, so they score the whole context and discard everything outside
the candidate blocks. The discarded work grows linearly with context length
(~98% of the scoring work at 1M context, per #61830).

**What the new path does.**

1. Gather each candidate block's K from the paged FP8 indexer cache into a
   compact per-row buffer.
2. Score only the gathered candidates with the existing non-paged FP8 scoring
   kernel.
3. Remap the selected columns back to request-local token positions, so the
   output is identical in meaning to the dense path.

**Scope kept narrow on purpose.** Only the candidate-consuming indexers take
the new path; the candidate-source and pre-candidate indexers stay dense, as
they have no candidate set to exploit. Restricted to SM90 with an FP8 indexer
cache and no context parallelism — SM100 already has native sparse kernels,
and all other platforms keep today's behaviour.

**Tradeoff, and why the current gating is provisional.** Dense cost scales
with `rows x context`, while candidate scoring is dominated by a per-step
fixed cost, so the crossover tracks scanned work relative to the candidate
width rather than context length alone. Since the profitable threshold is
hardware-dependent, this PR does not bake in a device-specific constant and
instead exposes host-side gates (details collapsed below), treating them as a
**stopgap, not the intended final interface**. Defaults impose only
shape-level lower bounds, and the H20 values above are reported as
measurements, not recommended defaults.

**Known structural limitation.** Path selection is host-side per step and is
*not* graph-aware: a fully-captured CUDA graph fixes whichever path was active
at capture time. `FORCE` exists to make that behaviour testable. This is the
main reason the feature ships disabled by default.

<details>
<summary>Workload gates (provisional)</summary>

| Env var | Default | Meaning |
| --- | --- | --- |
| `VLLM_DSA_CANDIDATE_GATHER_DECODE` | `0` | Master switch. |
| `VLLM_DSA_CANDIDATE_GATHER_MIN_ROWS` | `1` | Minimum decode rows in the step (speculative rows included). |
| `VLLM_DSA_CANDIDATE_GATHER_MIN_WORK_RATIO` | `1` | Requires `rows * context >= ratio * candidate_width`. |
| `VLLM_DSA_CANDIDATE_GATHER_FORCE` | `0` | Validation only: bypass the workload gates. |

</details>

## Roadmap

This PR is a reviewable first increment, not the finished design:

1. **Graph-aware path selection**, so the choice is not frozen by full CUDA
   graph capture. This is the blocker for enabling the feature by default.
2. **Replace the manual env gates** with an automatic, device-independent
   decision (calibration or a cost model), with proper small-batch protection
   instead of a hand-set row threshold.
3. **Longer term**, a native paged sparse scoring kernel for SM90 is the
   cleaner fix than gather-then-score — a much larger change. This PR first
   establishes whether the candidate-only direction is worth it, which the
   numbers above suggest it is.

Happy to run specific concurrency levels, context lengths, or accuracy
benchmarks on request.
