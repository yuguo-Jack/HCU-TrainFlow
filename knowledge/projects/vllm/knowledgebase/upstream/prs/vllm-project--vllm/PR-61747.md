# [Simulator] Add vLLM Simulator for hardware-aware serving simulation on CPU

[Upstream PR](https://github.com/vllm-project/vllm/pull/61747) · state: open · merged: False

## Original PR description

## Overview

Adds `tools/vllm-simulator`, the simulator half of RFC #61406. It runs the real vLLM v1 engine on a CPU-only host and bypasses model forward. A simulation clock then advances by a hardware-aware per-step latency prediction. The output is the same set of metrics `vllm bench serve` reports, for a target model, accelerator, and parallel configuration.

This PR is fully independent of the CPU-based CI PR (#61407) and modifies no file outside `tools/vllm-simulator`. Once #61407 lands, the simulator can be simplified on top of it: its own mock platform and model-runner stub can be replaced, and real parallel ranks become possible. See [Relationship to the CPU-based CI PR](#relationship-to-the-cpu-based-ci-pr). The simulator is built by the same team, and with the same design, as the SGLang simulator (sgl-project/sglang#21891).

> [!IMPORTANT]
> **Maintainer decisions needed:** where the simulator should live, and which engine seams it may hook. See [Decisions requested](#decisions-requested).

## Claims

- **Transparent to users.** Serving and the local engine API accept the same arguments and expose the same interfaces as `vllm serve`, `vllm bench serve`, and `AsyncLLM`.
- **Zero changes to vLLM.** All 56 files are under `tools/vllm-simulator`, of which the core vLLM hooks (`src/vllm_simulator/simulation/vllm`) account for 1428 lines. Request admission, scheduling, prefix caching, block allocation, and KV-connector bookkeeping run on unmodified vLLM code.
- **Two clock modes.** `NON_BLOCKING` (default) advances a virtual clock. `BLOCKING` sleeps for the predicted latency, so the server can stand in for a real deployment in real time.
- **Pluggable predictors:** [AIConfigurator](https://github.com/ai-dynamo/aiconfigurator) (default), replay table, sklearn model, and linear model. See [Predictors](#predictors).
- **Topologies:** multi-instance with load balancing, and PD disaggregation through the native `DecodeBenchConnector`.
- **Baseline collector.** Exports per-iteration batch composition and latency from real GPUs, for replay tables, ML predictor training, and accuracy validation.

## Validation

**Functional tests.** Run on a CPU-only host with no CUDA runtime, against the [AIConfigurator](https://github.com/ai-dynamo/aiconfigurator) `SOL` database for a simulated B300. Models cover the main attention and KV-cache layouts:

- dense GQA: Qwen3-8B;
- hybrid full attention + Gated DeltaNet: Qwen3.5-27B;
- sparse MLA (DSA): GLM-5;
- hybrid MLA + KDA: Kimi-K3;

## Details

### Why hooks instead of in-tree changes

The primary goal is a workflow that is transparent to users.

| Workflow | Real | Simulated |
|---|---|---|
| Serving | `vllm serve` | `python -m vllm_simulator.simulation.vllm.launch_server` |
| Benchmark | `vllm bench serve` | `python -m vllm_simulator.simulation.bench_serving` |
| Local engine | `AsyncLLM.generate` | same code, after `init_hook()` |

Arguments, request formats, and output metrics are unchanged. The entry point can also stay unchanged by installing the hooks from a startup file, either a [`.pth` import line](https://docs.python.org/3/library/site.html#path-extensions-pth-files) or, on Python ≥ 3.15, a [`.start` entry point](https://docs.python.org/3/library/site.html#startup-entry-points-start-files). Such a file would need an environment-variable gate, and this PR does not ship one.

An in-tree implementation would spread non-serving changes across `vllm/`:

- arrival replay;
- a virtual clock;
- stats export;
- a device-less platform and model runner;
- no-op connector transfers.

Each of these would add branches to hot paths. Hooks keep all of them in `tools/vllm-simulator`. They are installed at class-definition time, before vLLM is imported.

**Maintenance cost.** Keeping the hooks outside `vllm/` does not make them free to maintain. The cost depends on how close each hook sits to low-level code, and the hooks fall into two kinds:

- **`wrapped_*` functions** keep the native call and only add simulation state around it: arrival replay, the clock, and stats. They sit on engine-level interfaces (`EngineArgs`, `EngineCore`, `UniProcExecutor`) that rarely change.
- **`override_*` functions** replace native behavior, almost entirely to remove hardware dependencies: device initialization, memory profiling, pinned buffers, and transfers. Together with the mock platform and the model-runner stub, these are the hooks most tightly coupled to low-level code. That is exactly the layer meta-CI (#61407) covers in-tree, alongside the code it depends on. Once #61407 lands, these hooks can be removed, leaving only the stable `wrapped_*` interfaces.

Hooks also apply to modules outside vLLM. External components, such as KV stores with their own capacity management, can therefore be brought into the simulation directly instead of waiting for each one to add simulation support.

### Design

- **Engine core.** `EngineCore.add_request` parks requests until the clock reaches their logical `created_time`. `UniProcExecutor.execute_model` converts each `SchedulerOutput` into `(scheduled tokens, past KV length)` pairs, queries the predictor, and advances the clock. `EngineCore.profile` dumps per-request and per-iteration stats.
- **Worker.** A stub stands in for Model Runner V2. The KV-cache spec comes from a meta-device model walk under the simulated TP size and accelerator architecture. The KV budget comes from the target accelerator's HBM.
- **Connectors.** KV offload and PD transfers complete immediately, so scheduler-side hits behave normally.

### Predictors

Each predictor maps one step's batch, a list of `(scheduled tokens, past KV length)` pairs, to a latency. The predictor is selected by `predictor.name` in the simulator config.

| Predictor | Source of latency | Typical use |
|---|---|---|
| `aiconfigurator` (default) | [AIConfigurator](https://github.com/ai-dynamo/aiconfigurator) per-operator performance model for the target model, accelerator, and TP/EP size. Database modes: `SILICON` (measured kernels), `HYBRID`, `EMPIRICAL`, `SOL`, `SOL_FULL` (speed-of-light). | Hardware that is not available locally; capacity planning |
| `replay` | Real per-iteration latencies exported by the baseline collector, matched by exact batch composition, with optional KNN interpolation on misses | Debugging by separating predictor error from scheduler and cache behavior |
| `ml` | sklearn regressor trained on collector exports, over batch-composition features | A deployed model and accelerator with collected baselines |
| `linear` | `base_ms + per_token_ms × scheduled tokens`; a constant step latency when `per_token_ms = 0` | Debugging |

### Relationship to the CPU-based CI PR

The two efforts are independent by nature.

- **Origin of meta-CI.** #61407 grew out of discussions in which functional CI also turned out to need CPU execution. It is in-tree because it goes deeper than the simulator: execution reaches model forward and runs fake kernels through their full lifecycle.
- **What the simulator gains.** The simulator never executes model forward. For it, meta-CI only reduces the CPU-execution support it has to carry itself.
- **Plan.** #61407 is not merged and may still change, so this PR ships its own minimal mock platform and model-runner stub. Once meta-CI lands, a follow-up will drop the `override_*` hooks, simplify the model runner, and allow real TP/EP/PP ranks. The `wrapped_*` hooks and the out-of-tree approach stay as they are.

### Decisions requested

1. **Location and ownership.** Is `tools/vllm-simulator` acceptable as a separately installed package with its own dependencies?
2. **Hooked seams.** The hooks cover `EngineArgs`, `EngineCore`, `Scheduler`, `UniProcExecutor`, `Worker`, the platform, and three KV-connector workers. Should any of these become narrow public extension points, such as a request-arrival hook or a step-latency callback?

### Limitations

- **Version coupling.** A hook that fails to apply logs a warning, so a renamed method can degrade silently.
- **Accuracy.** Only the comparison above is reported. `NON_BLOCKING` does not model the ~2.5 ms/step engine residual.
- **Scope.** Text generation only, on Model Runner V2, eager mode, synchronous scheduling. Parallelism is modelled by the predictor only.
- **KV cache transfer.** Transfer time is not modelled yet, for either external prefix cache loads and stores or PD prefill-to-decode transfers. Both complete instantaneously, so only the hit and miss decisions are simulated. Transfer models are follow-up work.
