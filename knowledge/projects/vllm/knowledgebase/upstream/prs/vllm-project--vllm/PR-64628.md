# [Core][KV Connector] Cap requests holding blocks for async KV loads (--max-num-inflight-kv-loads)

[Upstream PR](https://github.com/vllm-project/vllm/pull/64628) · state: closed · merged: False

## Original PR description

## Purpose

Some requests get their KV from an async connector load, such as a NIXL pull or a load from an offloading tier. Each one holds KV cache blocks from admission until it runs: while the load is in progress, and after it lands until the scheduler picks the request up. These requests don't count toward `max_num_seqs`, so nothing bounds how many there are. A burst of slow loads can hold blocks that running requests need for their next steps, and force preemptions.

`--max-num-inflight-kv-loads` caps them. It also gives a bound to anything sized per request in flight. For example, a pool sized for `max_num_seqs` running requests plus this many loads.

## Changes

- `SchedulerConfig.max_num_inflight_kv_loads` / `--max-num-inflight-kv-loads`. The default `None` means no cap, the current behavior.
- `Scheduler`:
  - A new async KV load is admitted only while fewer requests than the cap hold blocks for one. Both stages count: loads in progress (`KV_FETCH_IN_PROGRESS`) and loads finished but not yet scheduled (`KV_FETCH_COMPLETED_WAITING`).
  - A request past the cap waits in WAITING without allocating. It is handled like a load whose blocks don't fit: admission stops for the step, and resumes once an in-flight load's request runs or ends.
  - A request aborted while its load is in progress keeps its blocks until the worker reports the load done, so it keeps counting until then.
  - `Scheduler.num_inflight_kv_loads()` returns the count, read from the per-stage counters behind `vllm:num_requests_kv_fetch_by_stage`. Those counters are now kept whenever the cap is set, not only when stats are on.

**Not a duplicate.** I searched open PRs for `max-num-inflight-kv-loads`, `inflight kv loads`, `async KV load cap` and `WAITING_FOR_REMOTE_KVS limit`. Two related PRs:
- #61725 (`--max-async-kv-loads-per-step`) limits how many loads start in one step, to bound the step's scheduling time. It doesn't limit how many loads hold blocks at once, which is what this PR caps. The two compose.
- #64379 makes async-load admission linear-time and leaves its decisions unchanged.

New test: `test_max_num_inflight_kv_loads[None|2]`.
- Five async loads arrive. With the cap at 2, two start and three wait without blocks.
- A finished load still counts until its request runs; then the next load starts.
- Without the cap, all five start.
- With the scheduler change reverted, the capped case fails. It also passes with stats disabled.

New test: `test_aborted_inflight_kv_load_counts_until_its_blocks_are_freed`. With a cap of 1, aborting the in-flight load keeps the next load waiting until the worker reports the aborted one done. Without the abort counting, the count drops to 0 at the abort.
