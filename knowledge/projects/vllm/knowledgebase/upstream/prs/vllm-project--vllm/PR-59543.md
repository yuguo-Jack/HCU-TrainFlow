# [Core] Opt-in per-request return of the last hidden states in generation (MRV2)

[Upstream PR](https://github.com/vllm-project/vllm/pull/59543) · state: open · merged: False

## Original PR description

## Overview

Adds an opt-in, per-request output: for each generated token, the hidden state its logits were computed from (`SamplingParams.return_last_hidden_states`, returned in `CompletionOutput.last_hidden_states`; the engine must allow it with `--enable-return-last-hidden-states`).
It travels through a small typed token-output channel (`vllm/v1/token_outputs.py`), with the last hidden states as its first entry, so that a further per-token output is a new entry and not a new path (RFC #62145 asks for this; see "Channel" below).
Implements RFC #59542; related: #48743, #56916 / #57736, #57185, #62145 / #62272 (differences in the RFC and below).

## Claims

What the code does, by design and by the CPU tests below:

- **New output:** row `i` is the tensor `compute_logits` received for generated token `i` (gathered after sampling, not recomputed), shaped `[len(token_ids), hidden_size]`, CPU, model dtype, returned with the final output; rows follow stop tokens and `max_tokens`. `output_kind=DELTA` is rejected for a request that asks (its final output holds only the last tokens, so one row per token would not hold).
- **Off by default:** with the engine flag off the model runner holds no state and does no work; a request that asks on an engine without the flag is rejected at validation.
- **Only the requests that ask pay:** one gather of their logits rows per step and a non-blocking device-to-host copy on the output copy stream.
- **Small:** 237 library lines across 12 library files (87 of them the new module, about 21 of those docstring); Model Runner V2 only; refused at start-up with speculative decoding, pipeline or context parallelism.

**Not claimed for this head until a GPU has run it:** bit-identical outputs when off or unused, no host synchronization (`VLLM_GPU_SYNC_CHECK=error`), the rows reproducing the engine's raw logits, latency. The GPU test file collects (4 tests), the numbers below that come from a GPU are from the earlier transport of this change, and a run of the GPU tests on this head (an RTX PRO 6000 or a B200) is requested in a comment.

## Details

**Why this is not duplicate work.**
#57185 returns the final prompt-position state for one-token, `n = 1`, non-streaming requests on native Qwen2 and Qwen3.5 through `kv_transfer_params`; #57736 (RFC #56916) captures windows of output-token rows for rollouts with a capture plan, optional auxiliary layers, and its own lifecycle; #48743 returns states captured by the extraction connector.
This change returns the exact `compute_logits` input for every generated token, on any Model Runner V2 generation model, through a typed field; the RFC compares them in a table.

**Channel.**
`vllm/v1/token_outputs.py` holds the entry names, `allowed(model_config)` (the engine flags), `requested(sampling_params)` (the request's opt-in) and `TokenOutputs`, the worker-side holder of which requests asked for which entry. The runner keeps one only when an entry is allowed; after `sample()` it gathers the asking requests' rows by the same `logits_indices` `sample()` used, into `ModelRunnerOutput.token_outputs` (entry, then request id, then rows); `AsyncOutput` copies them to the host on the output copy stream; the scheduler cuts each request's rows to its kept tokens into `EngineCoreOutput.new_token_outputs` (appended last for `array_like` compatibility); the output processor concatenates each entry on finish, as `routed_experts` is, and the `CompletionOutput` field of the entry takes it.
A request with no logits row in a step gets no entry for it. The returned tensor is a `torch.cat` copy, never a view of the zero-copy transport frame the decoder produced.
The channel exists because #62145 / #62272 propose named, model-defined readouts with the same needs (an engine flag off by default, a per-request opt-in, the rows `compute_logits` saw, the same transport): they become a second entry on this channel, in a follow-up commit and PR on top of this one (branch `aux-readouts-on-channel`), with @sylvanus4's code and authorship kept.

**Tradeoffs and limitations.**
- Rows are returned with the final output only (like `routed_experts` and `sampling_mask`); per-step delivery could follow.
- Not exposed in the OpenAI-compatible HTTP responses; Python API only for now.
- Bitwise reproducibility is the platform's: the GPU test compares token ids exactly and logits and rows within four fp16 ULPs, within a batch and across runs, because with CUDA graphs an identical batch moved a row by 3 ULPs between runs on an RTX PRO 6000 (eager runs bit-identical), and on an RTX 4090 one of three identical sequences in a batch differed by one fp16 step in 1 of 30 batches, in both cases whoever asked.
- Configurations refused at start-up (speculative decoding, pipeline and context parallelism) can be enabled with tests later.

**Backport.**
For deployments pinned to v0.30.0: [`rfc/return-last-hidden-states-v0.30.0`](https://github.com/aminry/vllm/tree/rfc/return-last-hidden-states-v0.30.0), the same change hand-ported with the earlier transport; the deployment numbers above come from it.

### A note on Qwen3.5 subclasses

`MODELS_CONFIG_MAP` is keyed by architecture name. A `SupportsAuxReadout` subclass registered under a new name therefore skips `Qwen3_5ForConditionalGenerationConfig`, which sets the mamba SSM state dtype from the HF config.

In our test subclass, the dtype stayed at `auto` instead of the model's `float32`. With the flags on, 8 of the 64 generations differed until we passed `mamba_ssm_cache_dtype="float32"` explicitly. With the dtype matched, flags on and flags off were identical across all 64 prompts.

This comes from how we registered the test subclass, not from the typed output channel. It may be worth a line in the docs for people writing custom readout models.
