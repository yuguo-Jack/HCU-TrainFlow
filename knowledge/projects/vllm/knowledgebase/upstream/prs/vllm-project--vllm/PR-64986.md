# [Bugfix][Attention] Fix KV-sharing fast prefill hang from unsynchronized host offsets

[Upstream PR](https://github.com/vllm-project/vllm/pull/64986) · state: open · merged: False

## Original PR description

## Overview

Fixes #64985. Under async scheduling, `--kv-sharing-fast-prefill` can hand the attention metadata builders a `query_start_loc_cpu` whose device-to-host copy has not finished yet. The trtllm-gen decode kernel then receives a garbage query length and hangs.

## Claims

- Fixes the hang: `query_start_loc_cpu` from `make_kv_sharing_fast_prefill_common_attn_metadata` now always holds final values.
- No new sync on the common path. With one logit per request (no speculative decoding), the host offsets are built with `torch.arange` instead of being copied.
- Adds a regression test that fails on `main` and passes with this change.

## Validation

**Unit test** `tests/v1/attention/test_kv_sharing_fast_prefill_metadata.py`. The CUDA case keeps the stream busy and reads the host offsets without a sync, the way the builders do.

```

E       assert [0, 0, 0, 0, 0] == [0, 2, 3, 6, 7]

8 passed
```

**End-to-end.** Setup: B200, Gemma 4 E4B fine-tune (bf16), `vllm serve --kv-sharing-fast-prefill --enable-prefix-caching -cc '{"cudagraph_mode":"PIECEWISE"}'`, MRV2, async scheduling on. The workload replays `/v1/completions` requests (`max_tokens=1`, 96 concurrent).

**Review follow-up (9c5b0d7, rebased on main).** `arange` now uses `device="cpu"`. Added `[1, 1, 1, 0]` (a request with no logits) and `[2, 1, 1, 0]` (`num_logits_indices == num_reqs` with `max_logits_per_req > 1`) so each branch condition is tested on its own, plus a CUDA test under `torch.device("cuda")`. CPU run: `5 passed, 3 skipped (CUDA)`. Removing either branch condition makes exactly one of the new cases fail. The CUDA cases were not re-run in this round (no GPU available right now); the earlier CUDA results above are unchanged code paths. Only `ruff check`/`ruff format --check` were run locally, not the full official pre-commit.

## Details

`decode_query_start_loc` is computed on the GPU, and its host copy was made with `.to("cpu", non_blocking=True)`. The builders read it on the host right away:

- `split_decodes_and_prefills`
- FlashInfer `_compute_decode_query_lens`

With async scheduling the copy sits behind in-flight GPU work, so the host reads unfinished memory. Instrumentation is in the issue. The bug reproduces on MRV1 and MRV2 and with both PIECEWISE and FULL_AND_PIECEWISE.

The change:

- **One logit per request** (`max_logits_per_req == 1` and `num_logits_indices == num_reqs`): the offsets are `[0, 1, ..., num_reqs]`, built on the host directly.
- **Otherwise** (speculative decoding with fast prefill, e.g. #63553): use a blocking copy. Correctness requires the values now. A sync-free alternative would pass the host-side per-request logits counts from the model runner (MRV2 already has `cu_num_logits_np` in `FastPrefillHelper.prepare`). I kept that out of this fix to avoid touching `CommonAttentionMetadata` and the runners, and I'm happy to follow up.

Relation to #60445: it builds the same one-logit host offsets with `arange`, so that path overlaps. Its multi-logit fallback still uses `.to("cpu", non_blocking=True)`, which has the same race. This PR makes the fallback safe to read immediately and adds regression tests for both paths, so it is worth merging on its own; whichever lands second can drop the duplicate one-logit branch.
