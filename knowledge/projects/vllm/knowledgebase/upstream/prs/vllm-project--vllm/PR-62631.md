# [XPU][LoRA] Support MXFP4 MoE LoRA via XpuFusedMoe hooks

[Upstream PR](https://github.com/vllm-project/vllm/pull/62631) · state: open · merged: False

## Original PR description



## Overview

Support LoRA for the XPU MXFP4 MoE backend (gpt-oss) by applying w13/w2 LoRA deltas through the new `activation_hook` / `output_hook` of `XpuFusedMoe.apply`. Depends on vllm-project/vllm-xpu-kernels#648 (draft until released and `requirements/xpu.txt` is bumped).

## Claims

- Stacked on #62807: `XPUExperts` now carries `LoRAExpertsMixin` and the hook path (SWIGLUOAI gate/up interleave, EP masking, single routing-weight application, `BLOCK_SIZE_N >= 16`). This PR only enables `XPUExpertsMxFp4` for LoRA (drops its `supports_lora()` opt-out) and adds the GPT-OSS test, CI step and docs.

## Validation

AI assistance (GitHub Copilot) was used.

- `tests/lora/test_gptoss_tp.py::test_gpt_oss_lora_tp2` passes on 2x Intel XPU. XPU uses `enforce_eager=True` there because TP>1 with CUDA graph produces garbage output on XPU even without LoRA (separate pre-existing issue).
- New `test_xpu_mxfp4_moe_lora_matches_reference` in `tests/lora/test_fused_moe_lora_kernel.py` (needs the kernels hooks).

## Details

Not a duplicate: vllm-project/vllm#61310 adds XPU LoRA for FP8/W4A16 by re-implementing the grouped path in vLLM, and leaves MXFP4 without LoRA. Hooks avoid maintaining a second copy of the fused MoE flow; commented there. Same single-class layout as `TritonExperts`; #61310 can reuse it by dropping its manual path.
