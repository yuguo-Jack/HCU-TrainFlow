# [Kernel][Fusion] Fuse GELU-tanh+Mul with NVFP4 quantization (Gemma 2/3/4)

[Upstream PR](https://github.com/vllm-project/vllm/pull/59467) · state: open · merged: False

## Original PR description

## Purpose

Gemma 2/3/4 use `gelu_pytorch_tanh` in their gated MLPs. With NVFP4 checkpoints the input quantization of `down_proj` is always a custom op (`scaled_fp4_quant`), so Inductor cannot fuse it with the activation: every layer runs `gelu_tanh_and_mul` (or the Inductor-generated gelu·mul kernel) and then `cvt_fp16_to_fp4`, writing and re-reading a bf16 activation of `intermediate_size` elements per token. All existing fused activation+quant kernels in vLLM are SiLU-only (`silu_and_mul_nvfp4_quant`, `silu_and_mul_quant`, ...).

This PR:

- generalizes `silu_mul_cvt_fp16_to_fp4` into `act_mul_cvt_fp16_to_fp4<Type, ActMul>` and adds `gelu_tanh_and_mul_nvfp4_quant` (same launch, same swizzled block-scale layout; `compute_silu_mul` keeps its arithmetic);
- registers `(GeluAndMul, kNvfp4Dynamic)` in the manual act+quant fusion registry (`fused_act_quant.py`, follow-up to #51415 / tracker #43501), with a predicate that only accepts `approximate="tanh"` and `d % 16 == 0`;
- wires `maybe_fused_act_quant` into `Gemma2MLP`, `Gemma3MLP`, `Gemma4MLP` (one line each, like `llama.py`);
- launches the fused kernel with programmatic dependent launch (PDL), the same protocol `cvt_fp16_to_fp4` already uses (`cudaGridDependencySynchronize()` + `cudaTriggerProgrammaticLaunchCompletion()` at kernel start, `cudaLaunchKernelEx` with `ProgrammaticStreamSerialization`). **This also changes the launch of the existing `silu_and_mul_nvfp4_quant`**, which shares the template; its outputs are bit-identical (see below), but I have not measured a SiLU model end to end. Happy to split this into its own PR if preferred;
- adds the defunctionalization branch for the new op, tests, a benchmark and a docs line.

Numerics: the fused kernel evaluates `gelu(gate) * up` in fp32 and rounds once to the input dtype before quantizing, like `compute_silu_mul` and like the default Inductor path. The CUDA op `gelu_tanh_and_mul` rounds the activation to bf16 before the multiply, so the two are not bit-identical (~0.7 % of FP4 codes differ at 4096×43008); against an fp32 single-rounding reference the fused kernel produced 0 differing FP4 codes on every shape tested (up to 4096×43008). The two large test shapes therefore run only in the single-rounding test: the existing `assert_close` test compares against a reference that rounds twice, and at ~1e5 elements a one-code FP4 flip exceeds its tolerance for the upstream SiLU kernel as well.

Not a duplicate: #51415 (merged) added the SiLU manual fusion; #53874 (ROCm GeGLU+FP8 group quant, closed by the author after "TTFT worse") is a different quant path, and its failure mode (the GEMM after the fused kernel slowing down) is measured below; #59384 (ReLU2+NVFP4, open) covers a different activation and model but edits the same registry file, so one of the two will need a trivial rebase. No open PR touches GELU + NVFP4.

### Scope / limitations

- Dense MLPs only. `nvidia/Gemma-4-26B-A4B-NVFP4` keeps its dense MLPs in bf16, so it does not exercise this path; MoE experts already fuse the activation inside the FlashInfer kernels. Gemma 2/3 are wired but not measured (no official NVFP4 checkpoints).
- Measured on RTX 5090 (SM120) only; the kernel is built for `sm_100a` and `sm_120a` like the SiLU one. Numbers on B200 / RTX PRO 6000 welcome.
- `GeluAndMul(approximate="none")` keeps the unfused path (test included).

|---|---|---|---|---|

| decode 64 in / 512 out, batch 16 (kernel without PDL, see below) | 4318.6 (4316.0–4321.2) | 4314.8 (4311.8–4317.3) | −0.09 % (pairs −0.06/−0.13/−0.20/+0.03 %) | 0.12 % → noise |

Why the fused kernel launches with PDL: the first version of this kernel (a straight generalization of `silu_mul_cvt_fp16_to_fp4`, which launches with `<<<>>>`) made batch-1 decode **0.24 % slower** (+17 us per step) although a profiled 512-step generate showed 48 fewer kernels per step, 12 ms less kernel time and identical CUDA runtime call counts. A gap analysis of the traces showed the gap between the fused kernel and the following down GEMM was 0.96 us instead of the 0.27 us seen after `cvt_fp16_to_fp4`: `scaled_fp4_quant` launches with `cudaLaunchAttributeProgrammaticStreamSerialization` and calls `cudaGridDependencySynchronize()` / `cudaTriggerProgrammaticLaunchCompletion()` at kernel start (`nvfp4_quant_kernels.cu`), so the PDL-aware FlashInfer GEMM can launch early; the fused kernel did not. Adding the same protocol turned batch-1 decode into −1.4 % and left prefill unchanged (−3.1 % before, −3.2 % after: at 4096 tokens the fused kernel runs 170 us, so 0.7 us of launch latency does not matter). The consumer of the fused kernel's output is the same `down_proj` GEMM that consumes `scaled_fp4_quant`'s output on the unfused path (only `FlashInferCutlassNvFp4LinearKernel` exposes `kNvfp4Dynamic`), so the early trigger has the same safety argument as the existing quant kernel. The batch-16 decode row above and the isolated MLP-block table were measured with the pre-PDL kernel; the block benchmark uses vLLM's own CUTLASS GEMM, which is not PDL-launched, and did not change with PDL (block −9.1 % at M=4096).

One prefill forward under torch.profiler (48 layers; attention is NVFP4 too in this checkpoint, so 4 quant kernels per layer in the base arm):

| group | base (ms) | fused (ms) |
|---|---|---|
| Inductor gelu·mul (`triton_poi_fused_gelu_mul_…`, 48×) | 10.52 | 0 |

The fusion fires in 48/48 layers (48 fused kernels, 48 fewer quant kernels, the Inductor gelu·mul kernel gone).

### Accuracy (GSM8K, 5-shot, greedy, chat template, `RedHatAI/gemma-4-12B-it-NVFP4`, RTX 5090)

| | base | base again (A/A) | fused |
|---|---|---|---|
| accuracy, 1319 questions | 93.56 % | 93.25 % | 93.18 % |
| accuracy, first 500 | 94.20 % | 94.40 % | 93.60 % |
| same final answer as base (1319) | – | 95.7 % | 95.3 % |
| identical generated text vs base (1319, batched) | – | 35.9 % | 24.3 % |
| identical generated text vs base (first 200, `max_num_seqs=1`, greedy) | – | **200/200** | **200/200** (accuracy 96.0 % both) |

Batched greedy decoding in vLLM is not batch-invariant (the base model against itself reproduces only 36 % of the texts at the default batch size), so text identity is measured at batch size 1, where decoding is deterministic (base vs base: 200/200): on these 200 questions the fused path reproduces the base model's generations token for token.
