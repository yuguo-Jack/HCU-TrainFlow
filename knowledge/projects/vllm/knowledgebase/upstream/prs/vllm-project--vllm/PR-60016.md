# [CI] Enable Zen CPU image build on AMD CI

[Upstream PR](https://github.com/vllm-project/vllm/pull/60016) · state: closed · merged: True

## Original PR description

`amd-zen-build` at `ff2bb67566` is a Zen CPU image-build step on the `amd-cpu` queue. It mirrors [vllm-project/vllm#56303](https://github.com/vllm-project/vllm/pull/56303) and applies the review comments: pull the published CPU image when registry and repo are passed in, and run the build only when Zen CPU sources change.



## Overview

This adds `.buildkite/image_build/image_build_zen_cpu.sh` and an `AMD: Build Zen CPU image` step in `.buildkite/hardware_tests/amd.yaml`. The step runs on `device: amd_cpu`. When `<registry>` and `<repo>` are passed, it pulls the CPU image published by `image-build-cpu` (`$REGISTRY/$REPO:$COMMIT-cpu`) and layers `docker/Dockerfile.zen` `--target vllm-zen-test` on it. If that pull fails, or the script is called with only the commit, it builds the CPU base from `docker/Dockerfile.cpu` and does not push either image. Zen5 hardware tests are out of scope.

## Claims

- The Zen image build runs on the ROCm fleet's x86 host (`device: amd_cpu`, queue `amd-cpu`), separate from the ROCm image chain.
- With registry and repo set, the base is the published `-cpu` image. The local tag `zen-cpu-base:$COMMIT` is used only when that pull fails.
- The step is gated by `source_file_dependencies` on the Zen Docker files, CPU image inputs, zentorch kernels, platform files, and Zen CPU tests. CUDA test requirements and the Rust / `csrc/cpu` inputs called out in review are not in that list.
- No image is pushed. The step checks that the Zen test image builds.

## Validation

This commit has not been built in CI yet. The check is the new Buildkite step succeeding.

On main CI, `$REGISTRY` and `$REPO` are filled in from `ci_config.yaml`, so the command takes the three-argument path. On AMD CI those variables are not injected; unless the pipeline already exports them, the step takes the one-argument path and builds the CPU base from source.

Local reproduction on an x86 host with Docker and BuildKit:

```bash
# Reuse a published CPU image.
DOCKER_BUILDKIT=1 .buildkite/image_build/image_build_zen_cpu.sh <registry> <repo> <commit>

# No registry: build the CPU base locally, then the Zen test image.
DOCKER_BUILDKIT=1 .buildkite/image_build/image_build_zen_cpu.sh <commit>
```

A pull hit logs `Using published CPU image as base`. A miss logs `Published CPU image unavailable; building base from source`. The fallback build uses `docker/Dockerfile.cpu` `--target vllm-openai`.

An earlier confirmation build, on the previous Zen image PR, produced `vllm-zen-cpu:local` from `Dockerfile.zen` `--target vllm-zen-test` on a local `vllm-openai` base. That was not a rerun of this commit. Runtime and accuracy tests on Zen5 hardware are follow-up work.

## Details

[vllm-project/vllm#56303](https://github.com/vllm-project/vllm/pull/56303) built the Zen image from the ROCm image script and always compiled the CPU base. Review asked for two changes: pull the image `image-build-cpu` already publishes, and trigger the build from Zen CPU sources rather than CUDA and Rust inputs.

The script lives next to `image_build_cpu.sh`. The step lives in `hardware_tests/amd.yaml` because that is the file whose steps set `device: amd_cpu`. The label is `AMD: Build Zen CPU image` so it does not start with `:docker:` (the generator would otherwise ignore `device` and use the generic CPU queue). The key is `zen-cpu-image` so it does not start with `image-build` (those keys ignore `source_file_dependencies` and always run). `depends_on` is empty, so the step does not wait on the ROCm base. It also does not wait on `image-build-cpu`: `hardware_tests/` is loaded by both main CI and AMD CI, and that CPU image step exists only on main CI.

When none of the listed files change, the generator leaves the step blocked for a manual unblock, which is the same behavior as the other `hardware_tests/` jobs.

Known limits, left for a follow-up after review:

- AMD CI does not inject `$REGISTRY` and `$REPO`, so `/amd-ci run` builds the CPU base from source unless those variables are already set in the pipeline.
- The published `-cpu` image is `Dockerfile.cpu` `--target vllm-test`. The source fallback in this PR is `--target vllm-openai`, matching #56303. `Dockerfile.zen` accepts either base.
- `requirements/build/rust.txt` is still a dependency.
- `cleanup` in the new script is only reached from the `EXIT` trap. Pre-commit ShellCheck reports that as `SC2329` until a disable comment is added.
- The fallback rewrites the Rust relink stage in `Dockerfile.cpu` and looks for `tools/build_rust.sh`. A later edit to that stage fails the source build until the search string is updated. The pull path does not use that rewrite.
