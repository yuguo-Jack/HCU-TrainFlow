# [Frontend] Support /v1/completions in run-batch

[Upstream PR](https://github.com/vllm-project/vllm/pull/64097) · state: closed · merged: True

## Original PR description

## Overview

Adds `/v1/completions` to `vllm run-batch`. The batch README listed it as "coming soon"; every other OpenAI endpoint the server exposes for generation already worked in batch mode.

No open PR covers this: searched open and closed PRs for `run-batch v1/completions` and `run_batch CompletionRequest` on 2026-10-26. #44445 adds an online Batch API, which is a separate path.

## Claims

- `run-batch` accepts lines with `"url": "/v1/completions"` and a `CompletionRequest` body, and writes `CompletionResponse` bodies, through the same `OpenAIServingCompletion` handler `vllm serve` uses.
- `/v1/chat/completions` keeps working unchanged.
- A line with an unknown URL still gets a per-line "not a supported endpoint" error instead of failing the batch.

## Validation

- `pytest tests/entrypoints/launchers/test_run_batch.py`: same results as `main` for every existing test. On this machine (macOS, no GPU) the tests that spawn `vllm run-batch` cannot run on either branch; all others pass.
- New `test_completions_endpoint` runs `vllm run-batch` on `hmellor/tiny-random-LlamaForCausalLM` with a string prompt, a list prompt and a chat line in one batch, and checks each line gets its own response type. It runs in the existing `entrypoints/launchers` step (`.buildkite/test_areas/entrypoints.yaml`). Passed on a Tesla T4 (Colab, `VLLM_USE_PRECOMPILED=1 pip install -e .` at the base commit, then `pytest tests/entrypoints/launchers/test_run_batch.py -k "test_completions_endpoint or test_completions or unsupported_url"`): 4 passed in 220s.
- `ruff check` and `ruff format --check` (v0.14.0, the pre-commit pin) pass on both changed Python files.

## Details

**Routing.** `run_one_request` looked up the registry by the last URL segment, and the chat entry was keyed `completions`, so `/v1/completions` would have been routed to the chat handler. Routing now walks the registry and uses the existing `url_matches` rule, which `handle_endpoint_request` already applies; the chat entry is renamed `chat_completions`. The registry has seven entries, so the linear scan costs nothing measurable.

**Why `CompletionRequest` is not in `BatchRequestInputBody`.** A line whose URL matches no branch of `check_type_for_url` is parsed against the whole `BatchRequestInputBody` union. `CompletionRequest`'s model validator raises `VLLMValidationError`, which is not a `ValueError`, so pydantic does not treat it as a failed union member and it escapes. With `CompletionRequest` in the union, an unknown-URL line carrying a chat body failed the whole batch instead of producing its per-line error (`test_unsupported_url_error_lists_registry_endpoints` caught this). `CompletionRequest` is therefore added to the `body` field's annotation and kept out of the fallback union.

**Docs.** `examples/features/openai_batch/README.md` now lists `/v1/completions` and drops "coming soon".
