# [Perf] Make DeepEP high-throughput SM count configurable

[Upstream PR](https://github.com/vllm-project/vllm/pull/61900) · state: open · merged: False

## Original PR description



## Purpose

`DeepEPHTAll2AllManager` only calls `deep_ep.Buffer.set_num_sms()` from the DBO micro-batching path (`set_num_sms`, via `ubatch_utils`). Without DBO, DeepEP high-throughput dispatch/combine always run on DeepEP's default of 20 SMs, and the manager's `num_sms` cap is hard-coded to 20, so there is no way to give them more.

This adds `VLLM_DEEPEP_HIGH_THROUGHPUT_NUM_SMS` (default `20`, so behaviour is unchanged unless set) and applies it to the DeepEP buffer when the handle is created. Under DBO, the per-micro-batch `set_num_sms` call still applies and is capped by this value as before.

Larger values need more NVLink buffer: on 8 ranks, 96 SMs fails DeepEP's buffer-size assertion with the default `VLLM_DEEPEP_BUFFER_SIZE_MB=1024` and works with 2048.

## Test Plan

8x B300 (SM103, CUDA 13.0, torch 2.13.0+cu130), one node, GLM-5.3 FP8 (DeepSeek-V3.2-style MoE, 256 experts, top-8), prefill-only engine: `--prefill-context-parallel-size 8 --enable-expert-parallel --all2all-backend deepep_high_throughput --max-num-batched-tokens 32768`, DeepEP `d4f41e4e` built for `10.3a`.

Closed-loop real-prompt prefill load (`max_tokens=1`, prompt mix 1k-200k tokens, 12 and 24 requests in flight, 240 s), every prompt with a unique per-run prefix; `prompt_tokens_details.cached_tokens` was 0 for every request in every run.

The runs used vLLM v0.31.0 with the equivalent change applied at startup (`deep_ep.Buffer.set_num_sms(N)` next to the `num_sms` cap), not this exact branch.

## Test Result

Served prompt tokens/s:

| DeepEP SMs | `VLLM_DEEPEP_BUFFER_SIZE_MB` | 12 in flight | 24 in flight |
|---|---|---|---|
| 20 (current behaviour) | 1024 | 56.3k | 56.9k |
| 64 | 1024 | 70.7k | 72.2k (+27%) |
| 96 | 2048 | 71.5k | 73.2k |
| 128 | 3072 | 71.2k | 73.6k |

For reference, `--all2all-backend allgather_reducescatter` with FlashInfer TRT-LLM MoE on the same setup: 60.4k / 60.7k.

Greedy outputs on a fixed prompt set are identical at 20 and 64 SMs.

Single runs on one model and node; the best value will depend on GPU SM count and EP size, hence an env var rather than a new default.

AI assistance was used in preparing this change; the measurements above were run on our hardware.
