# [ROCm][Perf] Muse Spark Open Shard residual stream across TP

[Upstream PR](https://github.com/vllm-project/vllm/pull/63085) · state: open · merged: False

## Original PR description



## Overview

On ROCm, Muse Spark keeps the full residual stream on every TP rank, and each rank repeats the per-token work between the attention and MoE collectives for all tokens, namely the norm, squeeze and expand. This PR splits the residual stream by tokens across the TP ranks for large forwards, controlled by an environment flag `VLLM_ROCM_MUSE_SP_MIN_TOKENS`. The all-reduces become reduce-scatters and all-gathers, and the per-token work runs on each rank's sharded tokens only.



## Claims

- For Muse Spark Open (amd/Muse-Spark-Open-816B-A42B-Quark-MXFP4) on MI355X, this achieves ~2.0% - ~8.7% throughput gain at TP8+EP8 and ~5.9% - ~15.7% at TP8 across concurrencies, with ~15% lower TTFT at TP8+EP8 and ~22-26% at TP8
- With DSpark (7 speculative tokens, Inferact/Muse-Spark-Open-DSpark): TTFT −14% to −22%, output throughput +5.2% / +9.7% at concurrency 16 / 32 on TP8 and +4.2% at 32 on TP8+EP8. Accuracy and the DSpark acceptance length on GSM8K are unchanged
- End-to-end accuracy is measured unchanged

## Details

In a Muse Spark decoder layer with TP attention, the ranks exchange data in two places: the all-reduce after `o_proj`, and the reduction of the MoE output. Everything in between, RMSNorm, gated residual update, router, squeeze and expand, works on one token at a time, but every rank runs it on all `T` tokens. At TP8, 7/8 of them is repeated work that other ranks require that they already have.

This PR keeps only a slice of the tokens on each rank when forwards have at least `VLLM_ROCM_MUSE_SP_MIN_TOKENS` tokens (1024 by default). The collectives are changed accordingly:

| layer | main | PR |
|---|---|---|
| before attention | — | all-gather |
| after `o_proj` | all-reduce | reduce-scatter |
| before the experts | — | all-gather of the projected input and the router logits |
| after the experts, TP+EP | all-reduce | reduce-scatter |
| after the experts, TP-sharded | reduce-scatter of the route rows + all-gather (8 of each chunk) | one reduce-scatter of all route rows |

An all-reduce moves the same bytes as a reduce-scatter all-gather combination, and the extra cost is collective launches. Under EP there are three more per layer, which take ~0.12 ms at 8k tokens, while working per-token saves ~0.84 ms. Below ~1k tokens the extra launch latency costs about as much as the sharding saves, so the sharding threshold is set to 1024 by default so that smaller forwards keep the current path. That includes decode and every CUDA-graph-captured batch. `o_proj` and, under EP, the MoE layer are built with `reduce_results=False` when sharding is possible, and do the same reduction in `forward` as before when a forward is not sharded.

With speculative decoding drafters that read the target's intermediate hidden states, the states of those layers are all-gathered for the drafter.

The change is limited to the ROCm Muse Spark path. It is enabled with TP > 1 and either expert parallelism or a bf16 MoE reduction, and requires DP = PP = PCP = DCP = 1. It can be set by `VLLM_ROCM_MUSE_SP_MIN_TOKENS`, and setting it `=0` turns it off.
