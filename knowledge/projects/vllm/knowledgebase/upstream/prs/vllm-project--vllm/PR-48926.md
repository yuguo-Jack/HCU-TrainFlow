# [Bugfix] Fix Marlin W4A8 signed scale corruption

[Upstream PR](https://github.com/vllm-project/vllm/pull/48926) · state: open · merged: False

## Original PR description

`marlin_act_int8_process_scales` stores per-group scales as signed `int16_t`, but the kernel's int8-activation scale-application path (`a_type == kS8`) reads them as `uint16_t*`, causing negative scales to be zero-extended to large positive integers. With ~50% negative group scales (common in AutoRound-quantized W4A16 checkpoints) the output is effectively corrupted.

### Fix

Change `reinterpret_cast<uint16_t*>` to `reinterpret_cast<int16_t*>` in two Marlin template headers:

- `csrc/libtorch_stable/quantization/marlin/marlin_template.h`
- `csrc/libtorch_stable/moe/marlin_moe_wna16/marlin_template.h`

### Companion PR

This is the kernel half of the fix for negative Marlin int8-activation group scales. The Python half is #59895 (`marlin_act_int8_process_scales` normalized by `abs().max()`, plus regression tests), from @plawanrath.

Landing order:

- land #59895 with or after this PR, never before. This PR closes #48905;
- land #59895 closes #59403, the same root cause.

### Why this is not duplicating an existing PR

PR #38066 fixes the W4A8-INT compressed_tensors path (int4 weight type not recognized, activations not quantized) but does not address the signed scale read in the kernel template. No other open PR references issue #48905 or the `uint16_t*` to `int16_t*` fix until this PR is created.

#59895 is a companion, not a duplicate: it touches only the Python scale normalization and tests, while this PR touches only the kernel read. Neither is a complete fix on its own.

- gagecane · comment · 2026-09-09T16:11:18Z · [source](https://github.com/vllm-project/vllm/pull/48926#issuecomment-5605000232)

Additional regression boundary for the signed-read fix (AI-assisted analysis; CPU arithmetic checked, CUDA PR not built/tested):

The downstream [syv-ai workaround](https://github.com/syv-ai/qwen38-27b-rtx3090/blob/main/patches/marlin-int8-negative-scales.patch) folds negative scales into signed-int4 codes before packing. That cannot preserve the q=-8 edge: q=-8, scale=-1 gives +8, but sign-flipping and clipping to q=+7 gives +7. Fixing the signed read in this PR avoids needing that lossy transformation.

Compiled and ran a C++17 assertion check with g++ -Wall -Wextra -Werror. For stored int16 values [-32768, -1024, -1, 0, 1, 32767], conversion through uint16 produces [32768, 64512, 65535, 0, 1, 32767]; signed promotion preserves all six values. The clipped-int4 check gives 7 versus the original 8. This only verifies the arithmetic, not device execution.

A useful kernel regression would include mixed-sign group scales, positive controls, and q=-8 with a negative scale, comparing both dense and MoE W4A8 paths to a dequantized reference. The sign-folding workaround must be disabled in that test, or it masks the negative-scale path. The current downstream serving configuration uses W4A16, so its successful chat tests are not evidence for this W4A8 fix.
