# [Bugfix] Return vocab rank instead of list position for logprob_token_ids

[Upstream PR](https://github.com/vllm-project/vllm/pull/60718) · state: open · merged: False

## Original PR description

## Overview

Fixes #60357. With `logprob_token_ids`, the `rank` of each returned token was its 1-based position in the request list, not its rank in the vocab. This PR ranks every requested id in the vocab on both model runners, and makes the Python and Rust frontends use those ranks.

Related open PRs:
- #60377 fixes only Model Runner V1 and Rust. V2, the default runner, still returns list positions. 
- #36746 targets a different bug (#36660) and gives per-entry ranks on V2 only as a side effect. Its kernel ranks `-inf` ids above the vocab size. No commits since 2026-09-16.

## Claims

- A `logprob_token_ids` entry now gets its vocab rank. This is the number of vocab entries with a logprob `>=` its own, which is the definition vLLM already uses for the sampled token. The rank no longer depends on the order of the list.
- When the sampled token is also in the list, it keeps its true rank. Before, its list position overwrote it (" Paris": rank 5 instead of 1).
- Fixed on Model Runner V1 and V2, through the TP batch-shard gather, and in the Rust frontend decoder. The issue shows the bug on both runners.
- Requests without `logprob_token_ids` are unchanged: 1-D ranks, the same GPU work, and no new Triton compile while serving.

## Validation

Reproducer, from the issue. Model `Qwen/Qwen3-0.6B`, run with `python repro.py`:

```python
from vllm import LLM, SamplingParams

llm = LLM("Qwen/Qwen3-0.6B", max_logprobs=-1, gpu_memory_utilization=0.8)
prompt = "The capital of France is"
ids = [279, 264, 13, 11, 12095]  # " the", " a", ".", ",", " Paris"

full = llm.generate(prompt, SamplingParams(temperature=0, max_tokens=1, logprobs=-1))
sel = llm.generate(prompt, SamplingParams(temperature=0, max_tokens=1, logprob_token_ids=ids))

full_pos = full[0].outputs[0].logprobs[0]
for tid, lp in sel[0].outputs[0].logprobs[0].items():
    print(f"{tid:>6}  logprob={lp.logprob:7.3f}  rank={lp.rank}  (logprobs=-1 says {full_pos[tid].rank})")
```

Setup: 1 × NVIDIA H100 80GB HBM3. Base commit `43b4aaea3e40e20ef53ce2bfecfa1b72060bf2b5` (`0.31.1rc1.dev23+g43b4aaea3`). Default V2 model runner. The issue used an H100 MIG slice, which has the same SM architecture.

Before: 2 runs on the base commit (the nightly image and an editable install). Both gave this output, digit for digit:

```

   279  logprob= -3.780  rank=1  (logprobs=-1 says 3)
   264  logprob= -4.780  rank=2  (logprobs=-1 says 9)
    13  logprob= -8.280  rank=3  (logprobs=-1 says 112)
```

After: 2 runs on the final patch (my run and an independent re-check). Both gave this output:

```
 12095  logprob= -0.405  rank=1  (logprobs=-1 says 1)
   279  logprob= -3.780  rank=3  (logprobs=-1 says 3)
   264  logprob= -4.780  rank=11  (logprobs=-1 says 9)
    13  logprob= -8.280  rank=118  (logprobs=-1 says 112)
    11  logprob= -6.155  rank=28  (logprobs=-1 says 27)
```

The ranks are no longer the list positions 5, 1, 2, 3, 4. " Paris" and " the" match `logprobs=-1`. " a", "." and "," are tied with other tokens, in groups of 3, 7 and 2 tokens with the same logprob. `logprobs=-1` numbers a tie group one by one. The `>=` rank gives the last place in the group. In each case the difference is exactly the group size minus 1. The reporter's later comment on the issue keeps the `>=` definition. The logprob values are unchanged.

## Details

**Root cause.** For each position, the worker sends one real rank: the sampled token's, in column 0. `append_logprobs_for_next_position` (`vllm/logprobs.py`) then gives the other columns the ranks `1..num_logprobs`, as if they were the top-k in rank order. That is correct for `logprobs=k` and `logprobs=-1`. With `logprob_token_ids`, the columns are the requested ids in request order (V1 `Sampler.gather_specific_token_logprobs`, V2 `_fill_logprob_token_ids_kernel`), so each id gets its list position as its rank. When the sampled token is also in the list, it is written twice to the same dict key, and the list position wins. The Rust decoder (`PositionLogprobs::from_decoded_row`) uses the same rule. A debug print in `LogprobsProcessor._update_sample_logprobs` showed that the worker sends the right ids and logprobs, in request order, with a single rank. The worker had no way to send the other ranks, so the fix changes both the worker and the frontends.

**Changes.**

- V2 `_ranks_kernel` (`vllm/v1/worker/gpu/sample/logprob.py`) now runs on a (row, column) grid. Column 0 is the sampled token, as before. When the batch has `logprob_token_ids`, the kernel also ranks each row's requested ids. Top-k rows in the same batch keep ranks 1..k. The new stride arguments are in `do_not_specialize`, and the mapping pointer is passed only together with the per-request counts. So batches without `logprob_token_ids` use one kernel variant, as before. A jit-monitor run with `logprobs=0, 1, 5, 15, 20` and `prompt_logprobs=1, 15` shows no `_ranks_kernel` compile while serving.
- The kernel no longer counts the padding lanes past `vocab_size`. Requested ids can have a `-inf` logit (for example, `processed_logprobs` with `top_k`). Without this change, such an id would get 155648 for a 151936 vocab.
- V1 `gather_specific_token_logprobs` (`vllm/v1/sample/sampler.py`) now ranks every gathered column. When `simple_compile_backend == "inductor"` (every in-tree platform), this is one call to the compiled `batched_count_greater_than` with a 3-D broadcast. On other backends it compares one column at a time, because the unfused 3-D compare builds a `[batch, cols, vocab]` tensor. vllm-ascend sets `"eager"` and inherits this method. With the backend forced to `"eager"` on CUDA, 64 requests × 128 ids needed 10766.6 MiB extra with the 3-D call. Column by column needs 83.6 MiB, the same as the old code.
- `selected_token_ranks` / `sampled_token_ranks` are `[rows, cols]` only when the batch has `logprob_token_ids`, and 1-D otherwise. `append_logprobs_for_next_position` accepts a list with one rank per entry. Three places would break on 2-D ranks, and they are updated: the TP batch-shard all-gather (`batch_shard.py`), diffusion_gemma's `_concat_logprob_stashes`, and the Rust decoder, which now accepts `[rows]` or `[rows, cols]`.

**Compatibility.** The engine-core wire field for ranks can now be 2-D. An out-of-tree consumer that reads it as 1-D needs the same change as the Rust decoder.

**Cost.** Batches without `logprob_token_ids` do the same work as before. For a batch with `logprob_token_ids`, V2 now scans the vocab once per requested id (at most 128 per request) instead of once per row. This is the same cost V1 already pays. In V1, the first `logprob_token_ids` request in a process compiles one 3-D graph: 1215 ms, against 80 ms on the old code. Other list lengths (2 to 128) and batch sizes (1 to 16) do not recompile.

The old V2 cost was low because it ranked only one token per row, and those ranks were wrong. A possible follow-up is a kernel that loads each vocab block once and compares it with all ranked values of the row.

</details>

**Limitations.**

- diffusion_gemma's "allowed" path has the same kind of wrong ranks. It is a different feature, so I left it for a follow-up.
- On V2, a batch with a `logprobs=-1` request and a `logprob_token_ids` request stalls on the base commit too. Because of that, the `[batch, 1 + vocab]` rank tensor this patch builds for such a batch was not run end to end.
- The new V1 test cases fail if they run after `tests/v1/sample/test_sampler.py` in the same process. That file calls `torch.set_default_device` and does not reset it. CI runs `test_logprobs.py` first, so this does not happen there.
- `test_gather_sampler_output_per_column_ranks` repeats about 60 lines of the harness from `test_gather_sampler_output_logprobs_and_nans`. I am open to making it a parametrize of the existing test instead.
