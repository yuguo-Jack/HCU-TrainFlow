# [Bugfix][Elastic EP] Keep FlashInfer autotuning working on stateless groups

[Upstream PR](https://github.com/vllm-project/vllm/pull/65307) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

An Elastic EP engine with `--all2all-backend nixl_ep` fails in warmup with `Process group ... is not initialized in the world group map`. FlashInfer's autotuner calls `dist.get_backend` on the tuning group, and the stateless groups of Elastic EP are not in torch's world map. Add the group to the map only while tuning.

## Claims

- `tests/distributed/test_elastic_ep.py::test_elastic_ep_scaling[cuda_graphs_heavy_nixl_ep]` starts and scales on B200 with an empty autotune cache.
- Groups that torch already knows, and non-Elastic deployments, are unchanged.
- The default `allgather_reducescatter` Elastic path never reads the registered entry, so this change does not affect it.

## Validation

Results used NVIDIA B200 GPUs and a precompiled build of main `b2a9480dc7`. The comparison tree is this branch with only `kernel_warmup.py` restored to main.

```sh
.venv/bin/python -m pytest tests/model_executor/test_flashinfer_autotune_warmup.py -q
VLLM_WORKER_MULTIPROC_METHOD=spawn RAY_ADDRESS=local .venv/bin/python -m pytest \
  tests/distributed/test_elastic_ep.py -k "cuda_graphs_heavy" -v -s
```

```text
Without this PR: FAILED tests/model_executor/test_flashinfer_autotune_warmup.py::test_flashinfer_autotune_on_stateless_group
                 ValueError: Process group <...> is not initialized in the world group map. Please initialize the group first.
With this PR:    the file passes
```

That regression uses a real stateless gloo group. The end-to-end runs below started with `~/.cache/vllm/flashinfer_autotune_cache` removed. They ran from a copy of the test without the `ray stop --force` fixture, because that command stops the Ray instance of the host environment, and with `RAY_ADDRESS=local`.

| Variant | Main | This PR |
| --- | --- | --- |
| `cuda_graphs_heavy_nixl_ep` | Fails in all 3 runs, with the world map error | Passes in 7 of 8 runs, including scale-up and scale-down |
| `cuda_graphs_heavy` | Scale-down fails in 1 of 10 runs | Scale-down fails in 5 of 13 runs |

The one `nixl_ep` failure was the first run on a fresh pod. It failed with `Fault detected in EP all2all communication: one or more ranks timed out during dispatch/combine`, in a run that also built FlashInfer JIT modules. I did not confirm that the JIT builds caused it.

The `cuda_graphs_heavy` failures have the same symptom with and without this PR: the scale-up completes, and the scale-down fails with `Scale failed: wait timeout after 300000ms, keys: /eep_ready/0, /eep_ready/1`. Because the counts differ, I checked whether this PR can affect that path. An instrumented copy recorded every lookup of the registered entry while it was in the map. All tuning windows of `cuda_graphs_heavy` had 0 lookups. `cuda_graphs_heavy_nixl_ep` had 45, from `choose_one` through `_sync_oom_across_tune_group` and `_profile_single_kernel`. So nothing reads the entry on the `cuda_graphs_heavy` path, and I treat the difference in counts as chance. This PR does not address that existing flake, and I did not find its cause.

Model quality was not evaluated, because this change only affects engine startup.

**CI coverage:** `(MI300) Model Executor` selects the new regression and triggers on these files, but ROCm was not run. The NVIDIA step for `test_elastic_ep.py` is commented out, and the changed files do not trigger the optional `(MI300) Elastic EP Scaling` step, so CI does not run the end-to-end test. Upstream checks are stopped at contributor authorization, so Buildkite has not run this branch.

## Details

`flashinfer_autotune` calls `set_autotune_process_group(tune_group.cpu_group)`. FlashInfer 0.7.2.post1 then calls `dist.get_backend(group)` in `_sync_oom_across_tune_group`, which raises for a group that is not in `_world.pg_map`. `StatelessGroupCoordinator` creates its groups outside that map on purpose, and `DeviceCommunicatorBase` uses their absence to detect them, so registering them permanently is not an option.

This PR registers the group for the duration of the autotune context and removes it afterward. Only `nixl_ep` reaches FlashInfer's profiling path in these runs, which is why the default variant does not hit this error. I did not trace why the default variant skips profiling. It uses a private torch attribute, as `DeviceCommunicatorBase` already does. FlashInfer main still calls `dist.get_backend` on this group, so an upgrade does not remove the need for this change.

This does not duplicate an open PR. Searches for the error text, for stateless autotuning, and for `nixl_ep` found no PR for this. #62972 adds NIXL EP v2 and does not change this path.
