# [ROCm][AMD] Generalize MiniMax-M3 mono decode architecture for TP=2, TP=4, and TP=8 on gfx950

[Upstream PR](https://github.com/vllm-project/vllm/pull/61273) · state: open · merged: False

## Original PR description

## Summary

This PR extends and generalizes the monolithic fused decode kernel ("Mono Decode" from PR #59705) for MiniMax-M3 architectures to natively support **tensor parallel sizes TP=2, TP=4, and TP=8** on AMD Instinct MI355X (gfx950) accelerators.

While the original PR #59705 introduced the monolithic fused decode layer for TP=4, attempting to run on TP=2 previously failed due to hardware Compute Unit (CU) exhaustion, GQA multi-KV-head divergence, and workgroup Local Data Share (LDS) budget overflow.

This PR solves these architectural challenges cleanly:

### Key Architectural Improvements

1. **Sequential GEMV Task Folding in K1 (`mono/kernels/pre_attn.py`):**
   - On TP=2, MiniMax-M3's local QKV projection rows increase to 4,992, requiring 304 GEMV tasks. Under a 1-to-1 task-to-CTA mapping, total persistent CTAs reached 364, exceeding the 256 physical CUs of the MI355X and failing grid assertions (`assert XT0 + OTHER_GEMV <= BLOCKS`).
   - We introduced sequential task folding (`TASKS_PER_CTA = 2 if TP == 2 else 1`). Each GEMV CTA loads token activations once and sequentially computes two row groups, bounding total persistent CTAs to **214 <= 256**.

2. **Multi-KV-Head GQA Attention Sub-Passes in K4 (`mono/kernels/post_attn.py`):**
   - MiniMax-M3 has a 16:1 GQA ratio (64 Q heads, 4 KV heads). On TP=2, each rank has 32 Q heads and 2 KV heads (`LOCAL_KV_HEADS = 2`).
   - Implemented iterative 16-head attention sub-passes in `stage_split`, allowing ranks with multiple KV heads to reuse the 16-head matrix core MFMA accumulator (`opart`) in LDS without register spills or wave divergence.

3. **Dynamic LDS Activation Pool Scoping & Padding Optimization (`mono/layout.py` & `mono/kernels/post_attn.py`):**
   - At decode batch size $S=16$, down-projection activations on TP=2 grew to 142.5 KB. Combined with separate allocations for `p8`, `q8`, `hst`, `keys`, and `ranks`, workgroup LDS reached 174,592 bytes, exceeding the 160 KB hardware limit (163,840 bytes) and failing LLVM compilation.
   - We scoped these temporary arrays inside the activation pool `xs`/`fpool` when `WIDE = True` ($S \ge 4$), and eliminated redundant `MIDSC_ROW` padding on TP=2 ($\text{INTER} // 32 = 48$, which is naturally bank-staggered), reducing LDS to **161,648 bytes (157.86 KB)** (< 160 KB).

4. **Multi-TP Sharding & Replication Support ($TP \in \{2, 4, 8\}$):**
   - Generalized head mappings and KV cache page indexing across `LOCAL_Q_HEADS`, `LOCAL_KV_HEADS`, and `LOCAL_INDEX_HEADS`.
   - Supports TP=8 KV cache replication (2 ranks per KV head) and generalized in-kernel peer all-reduce.
