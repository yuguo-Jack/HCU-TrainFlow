# [P/D][Mooncake] Send KV to D when prefill first token is a stop token

[Upstream PR](https://github.com/vllm-project/vllm/pull/46008) · state: closed · merged: False

## Original PR description

In P/D-disaggregated serving the proxy forces the prefill (P) request to `max_tokens=1`, so a successful prefill normally finishes as `FINISHED_LENGTH_CAPPED`. However, when the single sampled token happens to be an EOS / stop token, vLLM resolves stop before length and the request finishes as `FINISHED_STOPPED` instead.

`request_finished()` only sent the KV when the status was exactly `FINISHED_LENGTH_CAPPED`, so these requests were dropped into `reqs_not_processed` and the producer refused to send the KV. The decode (D) worker that issued `do_remote_prefill` needs this KV to produce its first token (the P-side placeholder token is discarded by the proxy), so it waited on `ready` in `send_kv_to_decode()` until `VLLM_MOONCAKE_ABORT_REQUEST_TIMEOUT` (default 480s), stalling the request well past typical first-token deadlines.

Fix:
- Accept both `FINISHED_LENGTH_CAPPED` and `FINISHED_STOPPED` as successful prefill terminal states in `request_finished()`; both must send the KV to D. Only genuinely interrupted requests (abort / preemption) stop being tracked.
- Log a warning when a P/D prefill request finishes with an unexpected status.
- In `record_send_reqs()`, use `pop(..., None)` to avoid a potential KeyError and wake any D-side coroutine already waiting on `ready` so it takes the "expired" branch and returns immediately instead of hanging until timeout.
