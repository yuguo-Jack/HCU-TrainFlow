# [Core] Reuse one CUDA graph capture stream per device

[Upstream PR](https://github.com/vllm-project/vllm/pull/59537) · state: open · merged: False

## Original PR description

## Purpose

`graph_capture()` creates a new `torch.cuda.Stream` on every call. As a result, each capture pass (CUDA-graph memory profiling, model capture, speculator capture, encoder capture) runs on its own stream. PyTorch allocates a 32 MiB cuBLAS workspace for each stream at its first GEMM and keeps it until the process exits. Each extra capture stream therefore holds another 32 MiB, plus any other per-stream kernel state (for example DeepGEMM mHC barriers on DeepSeek-V4.1). This memory stays allocated while awake and is one of the untagged leftovers that survive `sleep()` (#59055).

This PR caches one capture stream per device. Every `graph_capture()` caller (`cudagraph_utils.py`, `encoder_runner.py`, `gpu_model_runner.py`) runs one after another on the worker thread, and the calls are never nested, so one stream per device is enough.

One thing for reviewers: PyTorch's `CUDAGraph::reset()` calls `clearCublasWorkspacesForStream()` on the graph's capture stream. With one shared stream, destroying any graph frees the workspace that every graph on that stream uses. Every current destruction path destroys all graphs together and does so before any recapture: profiling teardown happens before the real capture (and `freeze_gc_for_cudagraph_capture` runs `gc.collect()` first), elastic EP's `release_graphs()` clears the model and speculator graphs together, and shutdown destroys everything. On GB300 I checked after serving that the capture stream still held the same workspace (touching the handle allocated 0 bytes).

Why this is not a duplicate: no open PR changes the stream used by `graph_capture()`. #52553 deals with FlashInfer's GEMM workspace, not the per-stream cuBLAS workspace.
