# [Kernel][ROCm] CDNA HIP attention kernels for INT8/INT4 per-token-head KV cache (MI300)

[Upstream PR](https://github.com/vllm-project/vllm/pull/43835) · state: closed · merged: False

## Original PR description



## Purpose

vLLM currently ships HIP attention kernels for `int8_per_token_head` and `int4_per_token_head` KV caches targeting **RDNA3** (the `paged_prefill_attn_rdna3.cuh` family). This PR adds the **CDNA** equivalents so the same per-token-head INT8/INT4 KV-cache attention runs on MI300-class GPUs 

Existing RDNA3 HIP kernels branch link: https://github.com/JartX/vllm/tree/feat/rdna3_int8_int4_hip_kernels 
Ask: https://github.com/vllm-project/vllm/pull/41394#issuecomment-4470714451
Reference PR: https://github.com/vllm-project/vllm/pull/41394

## **What's added**

C++/HIP kernels (`csrc/attention/`):
- `paged_prefill_attn_cdna_int8` / `paged_prefill_attn_cdna_int4` — paged-prefill
  attention with INT8 / INT4 per-token-head KV cache.
- `pth_decode_int8_cdna` / `pth_decode_int4_cdna` — split-KV paged decode.
- `reshape_and_cache_int4_cdna` — packs fp16/bf16 K/V into the INT4
  per-token-head paged cache and stores the (scale, zero-point) alongside.
- `paged_prefill_attn_cdna.cuh` — shared MFMA helpers.

Build & registration:
- `CMakeLists.txt` adds the new `.cu` files to the HIP source list, gated on
  `gfx942` / `gfx950` / `gfx90a` being selected. The kernels compile to no-op
  stubs on unsupported archs, so adding them is safe regardless of target.
- `csrc/ops.h` + `csrc/torch_bindings.cpp` register all ops under `USE_ROCM`.
- `csrc/spinloop.cpp`: include `<x86intrin.h>` instead of the standalone
  `<mwaitxintrin.h>`, which fails to compile on the ROCm 7.2 / amdclang
  toolchain.

Python integration:
- `vllm/v1/attention/ops/cdna_int8_prefill.py` and `cdna_int4_prefill.py`
  wrap the ops (the INT4 wrapper includes the `pack_scale_zp` helper).
- `vllm/v1/attention/backends/triton_attn.py`: adds `_maybe_dispatch_cdna_pth`,
  an **opt-in** dispatch (env `VLLM_USE_CDNA_PTH_ATTN=1`). It only engages on MI3xx, with `kv_cache_dtype` in {`int8_per_token_head`, `int4_per_token_head`}, `head_size` in {64, 128}, and no alibi / sliding-window / sinks / softcap.
  In every other case it returns `False` and the existing Triton path runs unchanged, so default behavior is unaffected.

- logeshmcw · comment · 2026-06-09T10:10:32Z · [source](https://github.com/vllm-project/vllm/pull/43835#discussion_r3379767404)

File: `tests/kernels/attention/test_cdna_int4_decode.py` · line 124

INT8 (rtol=atol=2e-2): 8-bit quantization has 256 levels, so each KV element carries a rounding error of about half a step relative to its range. Attention sums these errors over the head_size dimension (the Q·K and P·V dot products), where they partly cancel rather than add up, and fp16/MFMA accumulation + softmax add a small floor - so the output error lands around 1%. 2e-2 is ~2× that, leaving margin without masking a real regression.

INT4 (rtol=atol=4e-2): 4-bit has only 16 levels (16× coarser than INT8), so per-element error is ~6-7%; the same dot-product averaging brings the output error down to ~2%, hence 4e-2 (2× the INT8 tolerance). Both values were confirmed against the measured error across all swept shapes.

TritonAttentionBackend is the backend that owns the per-token-head quantized KV dtypes — int8_per_token_head / fp8_per_token_head are already in its supported_kv_cache_dtypes, and this PR adds int4_per_token_head to the same list. So the CDNA HIP kernels hook in here as an accelerated drop-in for a path this backend already serves, which keeps the per-token-head dtype handling in one place.
 
That said, I agree the inline logic was too heavy for the backend file. I've moved the whole dispatch out into a dedicated module, vllm/v1/attention/ops/cdna_pth_attn.py; the backend now just makes a single maybe_dispatch_cdna_pth(...) call. we can even relocate the dispatch into a ROCm-specific backend instead if you'd prefer it not live under Triton at all.
