# [Bugfix][MiniMax-M3] Scope prompt reasoning-end checks to the last message

[Upstream PR](https://github.com/vllm-project/vllm/pull/63492) · state: closed · merged: True

## Original PR description



## Overview

With `--reasoning-parser minimax_m3`, streamed chat completions from MiniMax-M3.1-Flash put the whole `<mm:think>…</mm:think>` block (or a leading `</mm:think>`) in `delta.content` and never set `delta.reasoning`; non-streaming responses are split correctly. This fixes it in the M3 reasoning parser, on top of #63232's branch. It is the remaining failure tracked in #50549, reported for this checkpoint in [MiniMax-M3.1-Flash discussion #6](https://huggingface.co/MiniMaxAI/MiniMax-M3.1-Flash/discussions/6).

## Claims

- Streaming responses split reasoning from content again, in single-turn, multi-turn, tool-call, and `reasoning_effort` requests.
- For structured outputs, the grammar starts after the model's `</mm:think>` rather than at the first generated token, which matches non-streaming parsing.
- Non-streaming extraction and the handling of output-only token ids are unchanged.

## Validation

**Unit:** I added two tests to `tests/reasoning/test_minimax_m3_reasoning_parser.py`, covering a prompt shaped like the M3.1 template (thinking instructions in the system message, a prior assistant turn prefixed with `</mm:think>`). Both fail without the change and pass with it. The 22 existing tests pass either way.

```
python -m pytest tests/reasoning/test_minimax_m3_reasoning_parser.py
# without the change: 2 failed, 22 passed
# with the change:    24 passed
```

**End to end:** MiniMaxAI/MiniMax-M3.1-Flash on `vllm/vllm-openai:minimax-m31-flash` (`sha256:86f582da…`, vLLM `0.1.dev23341+g8744dd2fb`), 8x A100, TP4 x PP2, `--reasoning-parser minimax_m3 --tool-call-parser minimax_m3 --enable-auto-tool-choice`. Each request was sent once streamed and once not; the table shows the streamed `content` (non-streaming was correct before and after).

| request | before: streamed content | after: streamed content / reasoning |
|---|---|---|
| single turn, default | `</mm:think>391` | `391` |
| `chat_template_kwargs.reasoning_effort: low` | `<mm:think>17 * 23 = 391.</mm:think>391` | `391` / 14 chars |
| top-level `reasoning_effort: high` | `</mm:think>391` | `391` / 14 chars |
| multi-turn (prior turn with `reasoning`, `reasoning_content`, inline markers, or none) | `</mm:think>Berlin.` | `Berlin.` |
| tools offered, first turn | `</mm:think>I'll check the weather…` | `I'll check the weather…` + tool call |
| after a tool result | `</mm:think>The weather in Tokyo is…` | `The weather in Tokyo is…` |
| `response_format: json_schema` | JSON from the first token, no reasoning | reasoning first, then valid JSON |

The deployment applies this change as a patch at container start. That patch's helper reverses the list and calls `list.index`, where the PR uses a plain reverse loop; the two behave the same. The unit tests ran on the PR's version.

## Details

**Root cause.** The M3.1 chat template's system message describes the thinking format with a literal `<mm:think></mm:think>` pair and tells the model to "begin your response directly after the `</mm:think>` prefix". It also prefixes assistant turns that have no reasoning with `</mm:think>`. `DelegatingParser.parse_delta()` calls `is_reasoning_end(prompt_token_ids)` once at the start of a stream. Because the parser's `rfind` finds a closer after the last opener, it returns `True`, so `reasoning_ended` is set before the first generated token and every delta bypasses `MiniMaxM3ReasoningParser`. `ChatCompletionRequest.resolve_reasoning_ended()` uses the same check, which is why structured outputs were constrained from token 0. Non-streaming never consults the prompt, which is why it worked.

The `thinking_mode: "enabled"` workaround from #45687 does not apply here. It worked on M3, whose template prefills `<mm:think>`, so the prompt's last marker was an opener. The M3.1 template does not read `thinking_mode` and never prefills one.

**Fix.** `is_reasoning_end()` and `is_reasoning_end_streaming()` now look only at the ids after the last `]~b]`, the token the template opens every message with, including the generation prompt `]~b]ai\n`. A continued final message is handled the same way. Output-only ids contain no `]~b]` and are scanned whole, as before. If a tokenizer has no `]~b]` in its vocabulary, nothing changes.

**Tradeoffs.** For prompt-prefixed ids the backward scan stops at the generation prompt. For output-only ids it walks the whole output, the same order of cost as the existing `_contains_token_sequence` scans it sits next to. #50594 addresses the same issue more broadly, with prompt-boundary hooks across the serving paths (17 files). This change stays inside the M3 parser, so it can land on the model branch without touching shared code.
