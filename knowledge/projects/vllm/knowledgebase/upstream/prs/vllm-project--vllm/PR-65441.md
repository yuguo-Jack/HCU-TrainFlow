# [CI][Model] Fill the model info cache once in the model init and tensor schema tests

[Upstream PR](https://github.com/vllm-project/vllm/pull/65441) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

Add `ModelRegistry.fill_model_info_cache()`, which inspects every lazily registered model that is missing from the model info cache in one subprocess, and call it once per module in `tests/models/test_initialization.py` and `tests/models/multimodal/processing/test_tensor_schema.py`. Today every case in those modules pays a ~10 s cache miss. Related: #23558 (added the cache), #51746 (closed; proposed a CLI to pre-fill it).

## Claims

- One fill of all 418 registered architectures takes 17.4 s; after it, each case reads the cache. Per case, `EngineArgs.create_engine_config` drops from a median of 10.3 s to 0.4 s in the init test, and `ModelConfig(...)` from 11.9 s to 1-2 s in the tensor schema test.
- Same cases, same results, less time on MI300X: 16 init cases 516 s -> 352 s (-32%), 14 tensor schema cases 335 s -> 211 s (-37%).
- Expected CI saving, at the last 7 days' run rate of main plus PR builds: about 155 machine-hours a day across (MI355 DPX) Basic Models (Extra Initialization), Multimodal Processor and Basic Models (Initialization). NVIDIA and XPU jobs running these modules pay the same miss today.
- No behavior change outside callers of the new method: `inspect_model_cls` is unchanged apart from moving its module hash lookup into `_get_module_hash()`.

## Details

- Root cause: on a miss, `_LazyRegisteredModel.inspect_model_cls` imports and inspects the model class in a fresh subprocess (to keep CUDA out of the caller), then writes `VLLM_CACHE_ROOT/modelinfos`. CI jobs start with an empty `VLLM_CACHE_ROOT`, and these modules test each architecture once, so every case missed.
- `fill_model_info_cache()` runs one `_run_in_subprocess` call that, for every lazily registered model whose cache entry is missing or stale, inspects the model and writes the result with the existing `_save_modelinfo_to_cache`. Entries are keyed by the model file hash exactly as `inspect_model_cls` keys them.
- The cache lookup runs in the subprocess too: resolving a module outside `vllm/model_executor/models` (the `vllm.models.*` packages) imports its package, and some of those import model code that initializes CUDA. A first version looked up the cache in the caller; in the CI image that initialized CUDA in the caller, which would break fork-based NVIDIA runs. With the lookup in the subprocess, the caller imports no new vLLM modules and leaves CUDA uninitialized (checked).
- Best effort: a model that fails to inspect in the batch (3 of 418 on ROCm: `Terratorch` needs an uninstalled package, `Dots3NoteForCausalLM` and `Dots3NoteMTPModel` import CUDA-only flash attention) gets no entry and is inspected by `inspect_model_cls` as before, so its error still surfaces in its own case. If the subprocess fails as a whole, the method logs a warning and returns.
- The calling process imports no model modules, so fork-based NVIDIA runs are unaffected.
- Tradeoff: about 17 s per module per job, even when a job runs one case from the module (the Intel job that runs a single `test_can_initialize_large_subset` case). With a warm cache the call still starts one subprocess (about 10 s) to check it.
- Docs: the method is documented by its docstring, which the API reference renders; no user-facing behavior changes.
- Not a duplicate: I searched open PRs for "model info cache", "modelinfos" and "inspect_model_cls subprocess". The only related open PR, #57311, moves `atomic_writer` out of `weight_utils` and does not change when the cache is filled. #51746 proposed a `vllm prepare-model-info` command and was closed.
