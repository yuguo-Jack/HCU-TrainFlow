# [Perf][MRv2] Read the vocabulary once in the token-logprob kernel, and split rows across programs

[Upstream PR](https://github.com/vllm-project/vllm/pull/60097) · state: open · merged: False

## Original PR description

## Overview

`_topk_log_softmax_kernel` reads every vocabulary row twice and launches one program per row, so small decode batches leave the GPU idle. This makes `compute_token_logprobs` read each logit once and split a row across programs when the batch is small.

Closes #60095.

## Claims

- Each row's vocabulary is loaded once. The logsumexp is an online `(max, sumexp)` update; only the requested token ids are gathered afterwards.
- Decode batches that cannot fill the SMs use a `(batch, num_splits)` partial reduction plus the same merge as `spec_decode/rejection_sampler_utils.py` (`M = max mᵢ`, `S = Σ sᵢ·exp(mᵢ − M)`).
- Output dtype (fp32), layout, and existing call sites are unchanged. `_ranks_kernel` is untouched.
- `VLLM_BATCH_INVARIANT` forces the fused one-program-per-row kernel, because the split count depends on batch size and would change FP32 summation order.

## Validation

New parametrized tests in `tests/v1/sample/test_logprobs.py`. They run on GPU, or on CPU tensors when `TRITON_INTERPRET=1`. Every kernel test compares against `torch.log_softmax(x.double()).gather(...)` on the fused path (`num_vocab_splits=1`), the split path (2, 3, and 8; 3 is not a power of 2, and 8 leaves some chunks empty for small vocabs), and the auto path.

| Test | What it covers |
|---|---|
| `test_compute_token_logprobs_matches_torch` (450 cases) | fp32 / bf16 / fp16 × V ∈ {1, 7, 1023, 1025, 3001} × `-inf` patterns: none, scattered, all but the last 3, all but the first 3, a single finite logit (logprob exactly 0), an entirely `-inf` row (NaN, neighbours unaffected). Always gathers the first, middle, and last ids. |
| `test_compute_token_logprobs_many_logprobs` | `num_logprobs` ∈ {1, 1023, 1024, 1025, 2100} |
| `test_compute_token_logprobs_strided_and_int32` | Row-strided slice of a padded buffer whose padding is `+inf`/NaN; int32 ids; non-unit column strides |
| `test_compute_token_logprobs_non_finite_row_isolated` | `+inf` or NaN at the start, middle, or end of a row → that row is NaN, other rows are exact |
| `test_compute_token_logprobs_extreme_values` | ±1e4 offsets, near the fp16 max, very peaked, nearly uniform; row max placed in the last tile |
| `test_compute_token_logprobs_fused_and_split_agree` | Fused vs. 2/3/4/5/8 splits over the whole vocab; `exp(logprobs)` sums to 1 |
| `test_compute_token_logprobs_empty` | Batch 0, `num_logprobs` 0 |
| `test_num_vocab_splits_heuristic` (120 cases) | Power of 2, ≤ 64, never more than 2·SMs programs, each chunk ≥ 8192 logits, worked H100 values, forced to 1 under batch invariance |

Mutation check. Breaking the kernel on purpose:

| Mutation | Failing tests |
|---|---|
| no `-inf` guard in the online update | 66 |
| running sum not rescaled when the max grows | 25 |
| split chunk end not clamped to `vocab_size` | 287 |

Removing the `-inf` guard in the merge kernel failed no tests. An all-`-inf` row is NaN either way, so that guard was not kept.

```bash
# CPU only (Triton interpreter)
TRITON_INTERPRET=1 pytest -v tests/v1/sample/test_logprobs.py -k "compute_token_logprobs or num_vocab_splits"
# GPU
pytest -v tests/v1/sample/test_logprobs.py
```

CPU-only run (Python 3.13, torch 2.14.1, triton 3.8.0, `TRITON_INTERPRET=1`, no GPU):

- New tests: 608 passed in about 2m50s.
- Existing tests in `tests/v1/sample/test_logprobs.py` are unchanged: 18 passed / 13 skipped, and the same failure set as unmodified `main`. Those failures need a Hugging Face download (`meta-llama/Llama-3.2-1B-Instruct`) or a GPU engine.
- Not run here: the full `test_logprobs.py` on GPU (model and engine tests, plus the >2³¹ int64-offset regression), and a performance comparison against the old kernel. `_SPLIT_TARGET_PROGRAMS_PER_SM = 2` and `_SPLIT_MIN_CHUNK_SIZE = 8192` should be checked with a GPU timing sweep before relying on them.

`ruff check` and `ruff format --check` (0.14.10) pass on the three changed files.

Thanks for the issue and the PR, @Aravind-11. Your description lists the GPU suite, the >2^31 test and a perf comparison as not run, so I ran them on one H200 (132 SMs, torch 2.13.0+cu130, triton 3.7.1) on 0ddd601 merged onto main c23ca06b6d, with main as the baseline. AI assistance was used to build and run the harness and to draft this.

- **Correctness:** all 608 new GPU tests and the >2^31 int64-offset test pass (32 tests need the gated Llama-3.2-1B and couldn't run; same set on main). A float64 oracle check over 4 vocab sizes, 3 dtypes, masked/inf/NaN rows and auto/fused/forced splits: 10,080 cases, 0 failures, max error 1.9e-6.
- **Kernel time** (V=151936 bf16 K=6, CUDA-graph device time): 12-13x faster than main at B <= 16, 2.4-8x at B 17-132, 1.32-1.52x at B >= 133; no measured config is slower in device time. Host dispatch is higher: about 47 vs 19 us per call on the split path and about 23 vs 19 us on the auto fused path.
- **Split heuristic:** at B <= 128 its choice is 32-286% slower than the best forced `num_vocab_splits` (e.g. B=128: 2 splits 47.5 us vs 16 or 32 splits 18.0 us), which suggests 2 programs per SM is too few on H200. A higher target and a smaller minimum chunk might recover most of it (untested).
- **Compiles after warm-up:** MRv2 warm-up only reaches B=1024, 2 and 1, so serving at B 17-132 compiles 4 new kernels (partial kernel's non-multiple-of-16 `num_splits` variant; merge kernels for 8/4/2 splits); main compiles none. In `vllm serve` Qwen3-0.6B with an empty Triton cache, max TTFT in those bands went from 36-99 ms to 165-233 ms. Warming those variants, or a fixed `PADDED_NUM_SPLITS` plus `do_not_specialize_on_alignment` on `num_splits`, should avoid it (untested). #55918's B=1 warm-up would only cover the 16-split variants here.
- **HBM bytes:** for B <= 64 main's second pass hits L2, so DRAM bytes are equal on both trees; the 2x reduction shows from B=256.
- **End to end** (Qwen3-0.6B, logprobs=5, 3 servers per tree): TPOT p50 about 1.4% lower at concurrency 1 (all 3 pairs; p99 ITL 1-7% higher in all 3), no difference I can separate from noise at 16 and 64 (at 64 TPOT p50 was 1.6-3.3% higher with the PR in all 3 pairs). Greedy outputs identical.
