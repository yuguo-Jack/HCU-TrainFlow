# [Perf][LoRA][MoE] Use problem-sized shrink/expand configs for MoE-LoRA batches of up to 256 tokens

[Upstream PR](https://github.com/vllm-project/vllm/pull/64746) · state: open · merged: False

## Original PR description

Stacked on #64653; review only the last commit ("Use problem-sized shrink/expand configs for MoE-LoRA batches of up to 256 tokens"). Diff of that commit: 6 files, +320 / -7.

## Purpose

#64653 sends batches of up to 64 tokens to `_fused_moe_lora_shrink` + `_fused_moe_lora_expand`, but their default configs come from the base-MoE `get_default_config`, which knows nothing about the LoRA rank, split-K, or how many token-expert blocks are active. This PR sizes the configs from the problem and, with them, moves the threshold from 64 to 256 tokens.

## Changes

1. **Problem-sized default configs** (`get_fused_moe_lora_two_kernel_config` in `vllm/lora/ops/triton_ops/utils.py`, used by `try_get_optimal_moe_lora_config` for batches up to the threshold when no `VLLM_TUNED_CONFIG_FOLDER` is set). Inputs are token count, top_k, experts, max_loras, slices, K, N, rank and the SM count. There are no per-GPU tables.
   - `BLOCK_SIZE_M = 16` for both w13 and w2 (it also sets the `moe_lora_align_block_size` block, so the two stay equal).
   - Shrink: `BLOCK_SIZE_N = clamp(next_pow2(rank), 16, 64)`. Active M blocks are estimated as `min(pairs, max_loras * E + pairs / 16)`. `SPLIT_K` is the largest power of 2 that brings the grid to about 2 x SMs (at most 16). `BLOCK_SIZE_K = clamp(K / SPLIT_K, 64, 256)`, halved if the pipeline does not fit in shared memory. `SPLIT_K` is then raised so that no program runs more than 16 K iterations. `SPLIT_K = 1` under `VLLM_BATCH_INVARIANT`.
   - Expand: `BLOCK_SIZE_N = 256`, halved (down to 64) while the grid is under one wave.
   - How the rule was picked: I swept shrink `BLOCK_SIZE_K x SPLIT_K` and expand `BLOCK_SIZE_N x num_warps` on 360 problems per GPU (5 MoE shapes x rank 16/32/64 x max_loras 1/4 x M 1-256 x w13/w2). Against the best swept config, the rule is within 2.3% (geomean) for shrink on both GB200 and H200, worst case 1.17x (GB200) and 1.27x (H200). For expand it is within 1.4%, worst case 1.12x.
2. **Split-K partials are added in fp32.** When `SPLIT_K > 1` the shrink output buffer is fp32, so the atomics are fp32 (bf16 atomics are both slower and lossier: with them, w13 at M=1 in the table below takes 20.9 µs instead of 8.2). Expand rounds the value to the 16-bit input dtype before its dot, so the result has the same rounding as the `SPLIT_K = 1` path. The kernel now picks the weight pointer type from the input when its output is fp32.
3. **Token threshold 64 -> 256.** Batches above 256 tokens keep the one-shot kernel. From 512 to 2048 tokens shrink/expand is still faster on average, but it loses by up to 1.8x on shapes with small hidden size and low rank, so I kept the cut simple.

`SPLIT_K` uses atomics, so as with the dense LoRA shrink defaults, the last bit of the fp32 intermediate can vary between runs. `VLLM_BATCH_INVARIANT` disables it. No new env vars.

## Test Plan

- New `test_fused_moe_lora_two_kernel_config` checks the heuristic's decisions (split to fill the SMs, `BLOCK_SIZE_K` follows the split on small K, the K-loop cap, no split on a full grid, the shared-memory cap, rank tiling, expand N tiles, and `SPLIT_K=1` under batch invariance).
- New `test_moe_lora_default_config_block_size_m_matches` checks that w13/w2 shrink/expand defaults agree on `BLOCK_SIZE_M` and use 16 exactly up to the threshold.
- The dispatch, expert-parallel, early-exit and zero-grid tests follow the constant; `test_fused_moe_lora_kernel_small_rank` uses 300 tokens instead of 100 so it still reaches the one-shot kernel.
