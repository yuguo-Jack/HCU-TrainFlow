# [Turing] Restore flashinfer support for SM75

[Upstream PR](https://github.com/vllm-project/vllm/pull/55380) · state: open · merged: False

## Original PR description

FlashInfer supports SM75+.
The SM75 64 KiB smem limit for HEAD_DIM 256 prefill was fixed in flashinfer PR [#3526](https://github.com/flashinfer-ai/flashinfer/pull/3526) (shipped in v0.6.16).
HEAD_DIM > 256 is not supported on SM75 due to the 64 KiB opt-in smem ceiling.

The upstream FlashInfer project has actually resolved the issue where SM75 functionality was regressing.
However, in the latest version (**v0.6.18**), FlashInfer removed the JIT cache for _SM75_ and _SM121a_ by default. This caused SM75 support to break again in the default vLLM container images.
Fortunately, recent versions of the vLLM container images include the `nvcc` compiler, making it possible to restore support simply by uninstalling `flashinfer-jit-cache` within the container (using `uv pip uninstall --system flashinfer-jit-cache`).

**Kernel tests on T4:** `tests/kernels/attention/test_flashinfer.py` only
parametrizes `torch.bfloat16`, which SM75 doesn't support, so it aborts on the
first case (`CUDA error: unspecified launch failure`). With `DTYPES` switched
to `torch.float16` locally: 108 passed, 52 skipped (fp8-KV / NVFP4), and 6
failed. All 6 are `test_flashinfer_prefill_with_paged_kv` with block_size 32,
num_heads (32, 8), head_size 128/256, each with 4 / 552,960 elements just over
tolerance (max abs diff 0.0545 vs atol 0.05). block_size 16 prefill and all
decode cases pass. Might be worth an fp16 parametrization (or a bf16 skip on
SM75) so Turing has some CI-visible coverage. I haven't dug into whether the
block_size 32 near-misses are anything more than fp16 tolerance.

**Why the gap is so large:** since Triton 3.3 (triton-lang/triton#5066), Triton
doesn't emit tensor-core MMA for compute capability < 8.0 and falls back to FMA.
On this T4, the compiled `kernel_unified_attention` PTX has 0 `mma.sync`. So on
Turing, TRITON_ATTN and FLEX_ATTENTION both run without tensor cores, and
FlashInfer is the only tensor-core attention path. Details in #60821.

**Three things that may be worth handling here:**

1. **Head size > 256 is still auto-selectable on SM75.** On the inline thread
   about this, I think the API can express it after all:
   `AttentionBackend.validate_configuration()` calls
   `cls.supports_combination(head_size, ..., device_capability)`, and
   `FlashInferBackend.supports_combination` already uses that for an
   NVFP4/head-size/capability rule. With this PR applied, validation on SM75
   currently returns no invalid reasons for head_size 512:

   ```
   SM75 head_size=128: invalid_reasons=[]
   SM75 head_size=256: invalid_reasons=[]
   SM75 head_size=512: invalid_reasons=[]
   ```

   So a head_size-512 model (e.g. Gemma 4 global layers) on Turing would
   auto-select FlashInfer, which per this PR's description can't run it on
   SM75. On Turing those models need TRITON_ATTN plus #39018 (still open, see
   #57712). Something like this in `supports_combination` would keep them on
   Triton:

   ```python
   if device_capability == DeviceCapability(7, 5) and head_size > 256:
       return "head_size > 256 not supported on SM75 (64 KiB smem)"
   ```

2. **The sampler is also switched on.** `flashinfer_sampler_supported()`
   reuses `FlashInferBackend.supports_compute_capability`, so with this change
   the FlashInfer top-k/top-p sampler also activates on SM75, even with
   `--attention-backend TRITON_ATTN`. When the JIT build fails, engine init
   fails for users who never chose FlashInfer (same class as #50705; #51741 /
   #60514 add a sampler fallback). Maybe gate the sampler separately here, or
   land after one of those?
3. **JIT toolchain outside the official image.** Your `flashinfer-jit-cache`
   warning covers the container case. A different case I hit with a pip
   install: on the AWS Deep Learning AMI, `/opt/pytorch/cuda` has nvcc but no
   `lib64/libcudart.so`, so the JIT link fails with `cannot find -lcudart` and
   engine init crashes rather than falling back to TRITON_ATTN. JIT temp files
   also overflowed a small tmpfs `/tmp` ("Disk quota exceeded"). Maybe just a
   doc note for pip installs on Turing.

Happy to rerun anything on the T4. If you're short on time, I'm also glad to
help push this over the line (tests, the sampler gating) in whatever way works
for you.

@ir1ka, following up on note 1 from my earlier comment: here's a ready patch
for the head_size > 256 case, in case it's useful. It applies cleanly on top of
this PR (rebased on current main):

```diff
--- a/vllm/v1/attention/backends/flashinfer.py
+++ b/vllm/v1/attention/backends/flashinfer.py
@@ class FlashInferBackend(AttentionBackend):
             if has_sink:
                 return "the sink prefill wrapper cannot read an NVFP4 KV cache"
+        # SM75 has a 64 KiB opt-in smem ceiling, too small for head_size > 256.
+        if device_capability == DeviceCapability(7, 5) and head_size > 256:
+            return "head_size > 256 not supported on SM75 (64 KiB smem)"
         return None
```

plus a GPU-free unit test in `tests/kernels/attention/test_attention_selector.py`:

```python
@pytest.mark.parametrize(
    "head_size,capability,supported",
    [
        (256, DeviceCapability(7, 5), True),
        (512, DeviceCapability(7, 5), False),
        (512, DeviceCapability(8, 0), True),
    ],
)
def test_flashinfer_rejects_head_size_above_256_on_sm75(
    head_size, capability, supported
):
    from vllm.v1.attention.backends.flashinfer import FlashInferBackend

    reason = FlashInferBackend.supports_combination(
        head_size=head_size,
        dtype=torch.float16,
        kv_cache_dtype=None,
        block_size=16,
        use_mla=False,
        has_sink=False,
        use_sparse=False,
        use_mm_prefix=False,
        device_capability=capability,
    )
    assert (reason is None) == supported
```
