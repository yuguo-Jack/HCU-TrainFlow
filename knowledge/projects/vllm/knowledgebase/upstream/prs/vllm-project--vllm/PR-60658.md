# [ROCm][Perf] TRITON_ATTN: tuned launch configs for gfx1100 and gfx1201

[Upstream PR](https://github.com/vllm-project/vllm/pull/60658) · state: closed · merged: False

## Original PR description

## Purpose

Tune the launch parameters of `kernel_unified_attention` (the `TRITON_ATTN` backend) for gfx1201 (RDNA4) and gfx1100 (RDNA3).

> **Status:** gfx1201 is done (results below). The gfx1100 sweep, same method and grid, is still running; its section will be filled in when it finishes.

Upstream launches the 2D kernel with `BLOCK_M=16`, `TILE_SIZE=32` and Triton's default warps/stages. With `BLOCK_Q = BLOCK_M / GQA`, each program then covers only 1–16 query positions. That is far too little work per program for prefill, chunked-prefill and mixed batches, which run 2–3x faster with taller blocks on gfx1201.

What changes:
- **Only launch parameters:** `BLOCK_M`/`BLOCK_Q`, the 2D `TILE_SIZE`, `num_warps`, `num_stages`. The kernel math is untouched.
- **Gating:** applies only on the exact arch (`on_gfx1201()`, `on_gfx1100()`), to bf16/fp16 queries with head_dim 64/128/256 and GQA ≤ 16, and is skipped under batch invariance. Everything else keeps the upstream launch.

The configs come from a sweep over a synthetic, model-agnostic grid of attention shapes and batches (below), not from one model's traces.

## Change

### gfx1201

**Prefill / chunked / mixed batches** (2D kernel, `max_seqlen_q > 64`):

| head_dim | `64 < max_seqlen_q < 4096` | `max_seqlen_q >= 4096` |
|---|---|---|
| 64 | `BLOCK_M=64`, `TILE=64`, 4 warps, 1 stage | `BLOCK_M=128`, `TILE=64`, 8 warps, 1 stage |
| 128 | `BLOCK_M=64`, `TILE=32`, 4 warps, 1 stage | `BLOCK_M=128`, `TILE=32`, 8 warps, 2 stages |
| 256 | `BLOCK_M=32`, `TILE=32`, 4 warps, 1 stage | `BLOCK_M=128`, `TILE=32`, 8 warps, 1 stage |

These batches keep the upstream launch:
- `max_seqlen_q <= 64`;
- decode-heavy mixed batches where the tuned block would be tall per KV head: `BLOCK_M // num_queries_per_kv > 16` and fewer than 16 query tokens per sequence on average.

  In such a batch (GQA 1–2 with dozens of decodes), every decode sequence would get a program padded to 32–64 query rows.

**Decode batches on the 2D kernel** (`max_seqlen_q == 1`, more sequences than the 3D threshold): `TILE=16`, 2 warps, 1 stage for head_dim 128 and 256. Head_dim 64 keeps the upstream launch.

**Decode on the 3D (split-KV) kernel** and the 2D/3D threshold: unchanged.

### gfx1100

_Sweep running._ The configs will be derived the same way, from the same synthetic grid, on a Radeon Pro W7900 (8 GPUs). The rule table will be added when the sweep finishes; its structure follows the data, so it may differ from gfx1201.

## How the configs were found

Both architectures use the same method and grid; the numbers in this section are for gfx1201.

### 1. Synthetic grid

The grid covers the attention shapes a model hits per GPU, and the batches vLLM's scheduler produces.

**Model shapes: 138**
- head_dim {64, 128, 256}
- × 23 (GQA, KV heads per GPU) pairs: GQA {1, 2, 4, 6, 8, 16} × KV heads {1, 2, 4, 8}, at most 64 query heads
- × KV block size {16, 528}

**Batches: 214 per shape**

| family | grid | count |
|---|---|---|
| decode | seqs {1, 2, 4, …, 256} × KV length {512 … 32k} | 63 |
| prefill / chunked prefill | seqs {1, 4, 16} × query {64 … 4096} (+8192 for 1 seq) × prior context {0, 4k, 16k, 32k} | 76 |
| mixed | one prefill chunk {64 … 8192} + {7, 15, 31, 63} decodes at KV {1k, 4k, 16k}, plus 4×512-token chunks + 28 decodes | 75 |

**Scope:** bf16, causal attention, no sliding window, sinks, softcap, ALiBi or fp8 KV.

**Total:** 29,532 (shape, batch) pairs; 444 are skipped because their KV cache exceeds 6 GB.

### 2. Configs

The pilot ran the full launch space on 2 shapes × 214 batches:
- **2D kernel, 72 configs:** `BLOCK_M` {16, 32, 64, 128} × `TILE` {16, 32, 64} × warps {2, 4, 8} × stages {1, 2}.
- **3D kernel, 48 configs:** `TILE` {16, 32} × warps × stages × segments {4, 8, 16, 32}.

A greedy cover then kept the 29 configs that bring every pilot batch within 2% of its best: 18 2D and 11 3D.

The main sweep ran those 29 configs, plus the upstream launch, on all 29,532 pairs.

### 3. Measurement

- **Kernel:** vLLM's own `unified_attention`, with KV in the paged layout vLLM uses. Each sequence's blocks are scattered across the cache.
- **Timing:** CUDA-graph timed with cache rotation. Each timed launch reads its own copy of Q/KV/block table, with ≥ 512 MB of KV per measurement. KV therefore comes from DRAM, not from the 64 MB Infinity Cache.
- **Correctness:** every config's output was checked against an fp32 reference (atol 2e-2 + rtol 2e-2). **0 wrong outputs** in 29,088 measured batches. The upstream launch was correct on every batch.

### 4. Choosing the rule

Each candidate rule was scored by geomean speedup over the upstream launch, worst case, and the number of batches slower than 0.97x. The rule above was the simplest one close to the per-batch best:
- **Configs depend on head_dim.** One config for all head sizes fails badly. E.g. the head_dim 64 config is 0.36x worst on head_dim 256, where `BLOCK_M` above 32 runs out of registers.
- **Two `max_seqlen_q` bands are enough.** `BLOCK_M=128` wins on every head size once a prefill chunk is ≥ 4096 tokens, but drops to 0.31–0.51x on shorter ones.
  - A third band, or extra splits by GQA, KV heads or block size, adds at most 0.03x geomean.
  - Banding by average or total query tokens instead of `max_seqlen_q` gives the same result (within 0.02x).
- **`max_seqlen_q <= 64` keeps the upstream launch.** Tuning it would add 0.1–0.2x geomean, but brings about 4x more regressions. Query lengths 2–63 (e.g. spec decode) were not in the grid.
- **The decode-heavy mixed guard** costs ~0.01x geomean and lifts the worst case from 0.76x to ≥ 0.93x.
- **Decode on the 3D kernel stays as is.** The best single config is only 1.02–1.06x faster and regresses to 0.87x on some batches.

## Notes / limitations

- **Head sizes:** tuned at head_dim 64/128/256. Other head sizes (e.g. 96, 192) keep the upstream launch until validated.
- **Scope:** bf16/fp16 and causal only. fp8 KV, sliding window and sinks keep the upstream launch.
- **3D threshold:** the gfx1201 sweep also suggests the 2D/3D decode threshold (`seqs × kv_heads ≤ 128`) is too high on gfx1201. 2D is already faster from about 32. That change is left for a follow-up.
- **Model outputs:** no change expected. Only launch parameters change, and every measured config matched the fp32 reference.
