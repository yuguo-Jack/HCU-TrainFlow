# [Perf][GDN] Run short prefills through the recurrent kernel with the decodes

[Upstream PR](https://github.com/vllm-project/vllm/pull/62343) · state: open · merged: False

## Original PR description



## Overview

A GDN batch with any prefill runs the FLA chunk pipeline (prep + 6 kernels per layer) even when the prefill is a few tokens long, plus a separate recurrent launch for the decodes. This PR runs batches whose longest non-spec query is short (default ≤ 32 tokens) through the existing recurrent kernel `fused_sigmoid_gating_delta_rule_update`, decodes and prefills in one launch. Longer batches keep the chunk pipeline. The route applies only to the FLA (`triton`) prefill backend.

## Claims

- Per GDN layer on A100, a mixed batch of 108 decodes + 1 short prefill: **1.99× at 1 token, 1.71× at 8, 1.43× at 16, 1.13× at 32** (graph-timed, L2 flushed). At 64 tokens the chunk pipeline is faster, so the limit stays at 32.
- Not less accurate: against an FP64 sequential reference, the output error of the recurrent route is equal to or lower than the chunk path's in every measured case; with an FP32 state, the final-state error drops from about 2e-3 to about 1e-7.
- Two latent issues in the recurrent kernel's multi-token path are fixed, which this route needs: with 1-D state indices it stored token *t*'s state into slot `indices[n + t]` (another sequence's slot), and it had no `has_initial_state` mask. No current caller reaches either (decode has one token per sequence; spec decode uses 2-D indices).
- No change for decode-only batches (FULL CUDA graphs), spec-decode rows, other prefill backends, or prefills longer than the limit. `additional_config={"gdn_recurrent_prefill_max_query_len": 0}` turns the route off.

## Validation

**Kernel benchmark** (1 × A100-SXM4-40GB, Qwen3.8-Flash GDN shapes at TP8: 2 key heads, 6 value heads, head dim 128; BF16 state; one CUDA graph of 20 calls over 4 state pools, 128 MB L2 flush before each of 5 replays, median). "chunk" is the current path (decode launch + prep + FLA chunk pipeline + state gather/scatter + concat), "recurrent" is this PR (one launch).

|---|---|---|---|---|
| 108 | 1 × 1 | 110.2 µs | 55.3 µs | 1.99× |
| 108 | 1 × 8 | 113.1 µs | 66.3 µs | 1.71× |
| 108 | 1 × 16 | 105.1 µs | 73.5 µs | 1.43× |
| 108 | 1 × 28 | 108.9 µs | 92.2 µs | 1.18× |
| 108 | 1 × 32 | 109.7 µs | 96.9 µs | 1.13× |
| 108 | 1 × 64 | 117.1 µs | 143.1 µs | 0.82× (kept on chunk) |
| 108 | 4 × 8 | 103.7 µs | 66.0 µs | 1.57× |
| 108 | 4 × 32 | 111.0 µs | 109.6 µs | 1.01× |
| 0 | 1 × 8 | 47.2 µs | 22.4 µs | 2.11× |

Accuracy (max abs error against an FP64 sequential reference, 108 decodes + 1 × 28): output 1.9e-4 (chunk) against 1.2e-4 (recurrent); final state 2.8e-3 against 1.9e-3. With an FP32 state pool (no decodes, 1 × 28): final state 2.1e-3 against 5.1e-8.

**Where the cost comes from** (eager nsys trace of Qwen3.8-Flash, 8 × A100, TP8, C32 agentic workload, per worker): a decode-only step runs 36 GDN kernels (0.88 ms); a mixed step with 28 prefill tokens runs 252 (2.25 ms), 7 per layer.

**Tests** (1 × A100, vLLM nightly image with this branch's Python tree): `tests/kernels/fla/test_fused_sigmoid_gating_delta_rule.py` (new multi-token 1-D-index case against an FP32 sequential reference) and `tests/kernels/mamba/test_gdn_forward_core_split.py` pass. `tests/v1/attention/test_gdn_metadata_builder.py` (new selection tests) could not run in that environment: the existing tests of the file fail there as well, with and without this change (device inference against the older image), so it relies on CI.

**Not yet done:** end-to-end serving A/B (TTFT/TPOT) and an accuracy eval; GPUs other than A100; other TP sizes; `pre-commit` (ruff was not available on the machine that made the last edit).

## Details

- **Selection** (`GDNAttentionMetadataBuilder`): `use_recurrent_prefill` is set when the batch has prefills and the longest non-spec query (`non_spec_query_start_loc_cpu`, host data, no device sync) is ≤ the limit. The longest query, not the total, decides: the kernel walks each sequence's tokens in order and runs sequences in parallel, while the chunk pipeline costs about the same from 1 to 64 tokens.
- **Forward** (`_forward_core`): with the flag, the chunk branch, the decode peel and the concat are skipped; the existing non-spec recurrent call covers `num_decodes + num_prefills` sequences with `has_initial_state`.
- **Kernel** (`fused_sigmoid_gating.py`): new `STORE_STATE_PER_TOKEN` (2-D indices, spec decode, unchanged) against one store per sequence after its last token (1-D indices); optional `has_initial_state` mask on the initial-state load. One-token decodes give the same result as before.
- **Warmup** compiles the new 1-D-index + mask variant, so the first mixed step does not compile.
- **Batch effect:** whether a short prefill takes this route depends on the other sequences in its batch, so the float rounding of a request can depend on its batch (both routes are exact algorithms; the recurrent one is the sequential definition).
- **With #61952 (GDN core captured in breakable PIECEWISE segments of mixed batches):** the captured static core ignores `use_recurrent_prefill` and always runs the decode launch plus the chunk pipeline, so captured segments stay correct; the route then runs only in eager segments. #61952 also stages `has_initial_state` for decode-only batches as a per-build tensor, so with both PRs the decode-only launch must keep passing `has_initial_state=None` (a FULL decode graph would otherwise keep a stale address). On `main` alone, `has_initial_state` is `None` for decode-only batches.
- **Related:** #60659 adds prefill checkpoints for the Triton/FLA backend; the recurrent route exports none, so with both PRs the selection must also require that no prefill checkpoint is planned for the batch (as it already does for FlashInfer checkpoints). #60033 (batch-invariant mode, routes all non-spec tokens through the recurrent kernel without a length gate) touches the same lines; the kernel fixes here would also serve it.
