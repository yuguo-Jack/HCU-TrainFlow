# [Model] Enable LoRA support for tower and connector in Voxtral

[Upstream PR](https://github.com/vllm-project/vllm/pull/45697) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Part of #31479. Enables tower + connector LoRA for **Voxtral**, reworked on top of the `get_mm_lora_token_counts()` interface merged in #42662 (which replaced the two token-count helpers this PR originally added). Addresses all three of @linitra24's review findings.

## Claims

- `AudioLanguageAdapter.w_in` / `w_out` are converted from `nn.Linear` to `ReplicatedLinear`, so the connector is actually LoRA-wrappable (`from_layer` previously left plain `nn.Linear` unwrapped). Parameter names are unchanged, so existing checkpoints and adapter target names keep resolving.
- `get_mm_lora_token_counts` is implemented for Voxtral's chunked encoder path: at runtime the chunk count is derived from the item's padded audio in `mm_kwargs`, so `tower_tokens = num_chunks * max_source_positions` equals the exact M the whisper tower forwards (punica's `token_lora_mapping.size(0) == M` holds). The `mm_kwargs=None` path (punica wrapper sizing, encoder-cache-served items) ceils `num_mm_embeds` to whole 30-second chunks, fixing the under-allocation in the review example: budget 16384 now sizes 44 chunks → 66000 rows, not `16384 * 4 = 65536`.
- `VoxtralRealtimeGeneration` opts out (`supports_tower_connector_lora = False`): its streaming processor skips chunk padding and builds placeholders from raw sample counts, so the chunk-derived counts would not hold there.

## Validation

Run on an A100 (nightly `vllm 0.31.1rc1.dev376+g5555a2d8f`, `torch 2.13.0+cu129`) with the modules from this diff:

```

```

Lint: `ruff format --check` / `ruff check` (pinned v0.14.0) pass on the three changed files.

The new test exercises the supported path rather than helper arithmetic: it runs the real Voxtral multimodal processor on synthetic audios of awkward lengths and asserts the hook's runtime counts against the processor's actual chunk-padded outputs, that the cache-served path (`mm_kwargs=None` with the item's placeholder count) returns identical counts, and that the sizing call upper-bounds the runtime totals — including the non-multiple-of-375 budget case (`num_mm_embeds=16384` → `(66000, 16384)`), which fails under the old formula. A second test asserts the adapter linears are vLLM-native and LoRA-wrappable with stable parameter names.

Pending before `ready`: end-to-end LoRA inference on GPU with an adapter targeting `whisper_encoder` + `audio_language_adapter.{w_in,w_out}` (multi-item, multi-chunk batch), and a load check of a quantized mistral-format checkpoint now that `quant_config` is threaded into the adapter. I'll post both here.

## Details

- Runtime vs sizing is the split #42662 was designed for: sizing needs an upper bound from the encoder budget, runtime needs exact per-item counts, and Voxtral's independent per-item 30s padding means the two cannot be computed from one formula. `connector_tokens = num_mm_embeds` on both paths because the adapter consumes exactly one row per LM audio embed (see `embed_multimodal`).
- The exactness of the cache-served path relies on the feature extractor padding audio to whole 30s chunks before placeholder counting, making every placeholder count a multiple of `ceil(max_source_positions / downsample_factor) = 375`.
- Not a duplicate: no open PR implements `get_mm_lora_token_counts` or connector conversion for Voxtral (checked `gh pr list --search "voxtral lora"` / `"get_mm_lora_token_counts"`; the active tower/connector PRs cover GLM-ASR #53149, Phi-4 #54832, Nemotron #58658, Whisper #59558 — different models).
- AI assistance (Claude Code) was used for this rework. I reviewed every changed line; the test commands and results above are from my own runs.

@jeejeelee — a note on tower vs connector for this model, since they behave differently:

- **Tower (`whisper_encoder`)** is vLLM's native `WhisperEncoder` (QKV/Column/Row-parallel, including the explicit `MergedColumnParallelLinear` K/V split the code comments call out as enabling LoRA), so tower LoRA attaches and `get_num_mm_encoder_tokens` is load-bearing — the whisper encoder runs at `downsample_factor`× the LM-visible audio tokens, which is the length the tower mapping needs.
