# [Kernel][XPU] Tensor-descriptor Q loads in Triton MLA decode attention

[Upstream PR](https://github.com/vllm-project/vllm/pull/64881) · state: open · merged: False

## Original PR description



## Overview

On Intel XPU, `_fwd_grouped_kernel_stage1` (TRITON_MLA decode) now loads its Q and Q-PE tiles through tensor descriptors instead of masked pointer loads, for the 576-wide MLA tile (`kv_lora_rank` 512 + `qk_rope_head_dim` 64) only. The K/V loop and the math are unchanged. The KV gather stays on pointer loads: this is a Q-tile change, not a descriptor path for the paged gather.

Context: RFC vllm-project/vllm#42545 recorded that this kernel could not use descriptors because of its paged KV gather. That still holds for K/V; the change here covers only the Q tile, which is a plain strided 2D tile, and only on XPU.

Scope: the gain applies to XPU runs that use `--attention-backend TRITON_MLA` explicitly, or that reach it as the fallback when `XPUFlashAttnMLABackend` rejects a config (`vllm/platforms/xpu.py`). The default XPU MLA backend (FlashAttnMLA) is faster than TRITON_MLA even with this change, and it is not affected. End-to-end numbers are on one model (DeepSeek-V2-Lite-Chat); most are with `--attention-backend TRITON_MLA` forced, plus one real fallback configuration (`--block-size 16`, where FlashAttnMLA rejects the config). Fp8 KV was not measured end to end. CUDA and ROCm launch the unchanged kernel.

Not a duplicate: no open PR adds tensor descriptors to this kernel. 18 other open PRs touch `triton_decode_attention.py` or its test file. Those that change the same code:
- vllm-project/vllm#51861 (draft) rewrites the Q-PE load; after it lands the descriptors here (`shape=[q_head_num, Lk]`) must be rebuilt for the split Q / Q-PE layout.
- vllm-project/vllm#51685 lets TRITON_MLA take a native fp8 KV cache and an fp8 query; the descriptor path would then see an fp8 Q, which is not tested here.
- vllm-project/vllm#52019 changes the stage-1 launcher signature and call site.
- vllm-project/vllm#61068, vllm-project/vllm#60173, vllm-project/vllm#54013 change `num_stages` handling next to the gate.
- vllm-project/vllm#63795, vllm-project/vllm#63796, vllm-project/vllm#48605 add a sliding-window constexpr to the same kernel next to `USE_TD`.
- vllm-project/vllm#57094, vllm-project/vllm#62725, vllm-project/vllm#40705, vllm-project/vllm#63623, vllm-project/vllm#57902, vllm-project/vllm#52472, vllm-project/vllm#50629 touch other parts of the kernel file and/or append tests; vllm-project/vllm#64783 and vllm-project/vllm#64534 touch only the test file.

Whichever lands second needs a mechanical rebase.

## Claims

- On XPU, `VLLM_TRITON_USE_TD` unset (the default) or `1` loads the Q / Q-PE tiles of the 576/512 MLA tile (one KV head) through descriptors. `0` keeps the pointer load. Outputs are bit-identical to the pointer load. The 288/256 tile keeps the pointer load for now: with descriptors its kernel-level result is mixed (faster on 8 of 12 shapes, 5.2-6.5% slower on the other 4), and no 288/256 model was run end to end.
- On 2× Intel Arc Pro B60 (`deepseek-ai/DeepSeek-V2-Lite-Chat`, TP=2, TRITON_MLA), the decode step is 4.3-6.0% faster at batch 1 and 17.7-24.0% faster at batch 8/32. Serve median TPOT drops by 4.4% / 17.7% / 22.2% at concurrency 1 / 8 / 32. gsm8k showed no significant difference (1 run per arm, see Accuracy).
- Per launch, the kernel is faster on all 24 bf16 and all 12 fp8-KV shapes of the 576/512 tile (table below, default arm).
- CUDA/ROCm: no behaviour change. The descriptor branch is a `tl.constexpr` that is always `False` there, and the gate checks the platform before reading the env var. `VLLM_TRITON_USE_TD=1` does not enable this path outside XPU.

## Details

- **Why it is faster:** on XPU, the masked pointer load of the 16 × 512 Q tile lowers to an SLM relayout (288 SLM `d16u32` loads in the 576/512 kernel). The descriptor load lowers to 18 2D block reads that land directly in the DPAS operand layout, and the relayout disappears (288/256: 9 block reads, 144 SLM loads removed). With TP=2 on DeepSeek-V2-Lite, stage 1 is 83-87% of decode device time at input 4096 with batch 8/32, and its per-launch time drops from 8.08 ms to 6.08 ms at input 4096, batch 8 (`torch.profiler`, eager).
- **Gate:** `is_xpu() and is_mla and Lk == 576 and kv_group_num == head_num and use_tensor_descriptor()`, plus a unit last stride and 16-byte-aligned base and strides of `q`. The platform check comes first, so CUDA/ROCm do no env lookup. `use_tensor_descriptor()` supplies the `VLLM_TRITON_USE_TD` tri-state (unset: on for XPU, `0`: off), as in vllm-project/vllm#46340 and vllm-project/vllm#47205. Unlike those, this kernel's descriptor path is XPU-only: `1` does not force it on CUDA/ROCm, where it has not been validated. `vllm/envs.py` is not changed.
- **Masking:** with one KV head, the kernel's row mask reduces to `row < q_head_num`, and the descriptor's bounds pad exactly those rows with zeros. `BLOCK_DMODEL` is below `Lk`, so the column mask is all-true, and the Q-PE descriptor starts at column `BLOCK_DMODEL`. That is why the results match bit for bit. Descriptor loads take no `.ca` cache hint.
- **No allocator needed:** every XPU descriptor build here has `global_scratch_size = 0`, so no `triton.set_allocator` call is added.
- **Tradeoffs and limits:**
  - The 288/256 tile is mixed with descriptors: faster on 8 of 12 shapes (batch 1 at 1k and 8k context, batch 8/32 at 1k context), 5.2-6.5% slower on the other 4 (batch 8/32 at 8k context), and no 288/256 model was run end to end. It is left out of the gate until the slowdown is understood.
  - Only Intel Arc Pro B60 was measured; B70 and B580 were not.
  - The kernel spills about 98 KB on XPU in both paths. The descriptor load does not change that (576/512: 97,920 B vs 99,584 B).
  - Tuning `num_warps` (2/4/8) and the GRF mode did not beat the pointer path's gain from this change, and did not improve the descriptor path beyond `num_warps=4`.
  - gsm8k generations are not reproducible across processes on this setup even with the same compiled kernel (see Accuracy for the measured TD-off vs TD-off noise floor).
