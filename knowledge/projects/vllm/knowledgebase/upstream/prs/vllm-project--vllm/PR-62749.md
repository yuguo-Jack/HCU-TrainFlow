# [Perf][MRV2] Record FULL decode attention metadata builds in CUDA graphs

[Upstream PR](https://github.com/vllm-project/vllm/pull/62749) · state: open · merged: False

## Original PR description

## Overview

Record the attention metadata build of each uniform FULL-decode batch shape during CUDA graph capture and replay it on matching steps, instead of rebuilding it on the host before every graph replay. This lifts the mechanism from the DeepSeek-V4.1 specialized decode (#61868) into Model Runner V2's `DefaultModelState`, with FlashInfer trtllm-gen decode as the first opted-in builder.

## Claims

- B=1 decode step on `facebook/opt-125m` (B300, FlashInfer trtllm-gen decode): **1217 → 1115 µs (−8%)**; B=8: 1342 → 1262 µs (−6%).
- `DefaultModelState.prepare_attn`: 103 → 23 µs per step. `build_attn_metadata` runs 0 times per decode step.
- With #62748 on top: **1217 → 987 µs (−19%)** at B=1 and 1342 → 1116 µs (−17%) at B=8.
- No change in outputs: greedy tokens are identical to main, with and without ngram speculative decoding.
- No measurable change in startup: graph capture time (2–4 s) and graph memory are unchanged.

## Validation

**Decode step timing.** Decode step = (T(1024 output tokens) − T(1 token)) / 1023 through the offline `LLM` API, greedy, `ignore_eos`, median of 5 reps per run. Configurations were interleaved over 3 rounds on one B300.

| opt-125m B=8 (3 runs) | 1339 / 1355 / 1332 | 1265 / 1240 / 1281 | 1131 / 1110 / 1107 |

  - I checked that it fails when the enumeration stops rounding capture sizes to whole requests.

## Details

**What gets recorded.**
- A FULL decode graph bakes the attention kernels' arguments at capture and reads persistent buffers. Before each replay, the runner still rebuilds the metadata on the host; for small batches that is a large share of the host step.
- `AttnMetadataCudaGraphs` (`vllm/v1/worker/gpu/attn_metadata_cudagraphs.py`) records, inside `capture_inner_cudagraphs`, the build of every uniform-decode key `(num_reqs, num_reqs_padded, num_tokens, num_tokens_padded)` a FULL decode graph serves. Each build runs on a padded dummy batch, like a capture.
- Before recording, each key is built once eagerly to warm lazy allocations.
- On a matching step, `DefaultModelState.prepare_attn` replays the recorded graph, which re-runs any device writes the build makes (for example `_with_kernel_block_table`). It then returns the metadata objects recorded with it.
- Any other step builds eagerly as before.

**Builder opt-in.**
- `AttentionMetadataBuilder.supports_recorded_decode_build` (default `False`) declares that a builder's uniform-decode build:
  - only launches capture-safe work into persistent buffers;
  - reads no host value the batch shape does not fix.
- FlashInfer sets it under the same condition as `supports_draft_decode_metadata_update`: trtllm-gen decode, no DCP. Its trtllm-gen decode build only wraps the device `seq_lens`, block table and `query_start_loc`; its host inputs (`num_decodes`, `q_len_per_req`) are fixed by the key.
- Like a FULL capture, the recorded metadata carries `max_seq_len = max_model_len`. The FULL forward graph already bakes that capture-time value.

**Scope and opt-outs.**
- Model states that override `prepare_attn` keep the eager build (MambaHybrid, EncoderOnly, and model-specific states), since they may feed builders per-step host values. GDN/Mamba builders are a natural follow-up: hybrid Qwen3.5 spends ~375 µs/step on metadata.
- DCP/PCP, micro-batching, KV connectors (which inspect metadata in `pre_forward`), KV-sharing fast prefill and mm prefix-LM models also keep the eager build.
- Adaptive-verification steps (`max_query_len` set) and non-uniform batches never match a key.

**Relation to #61868.** This is the same mechanism and key scheme. If both land, #61868's model-local copy could use this module and opt its DSv4.1 builders in through the flag.

**Not duplicate work.** I searched open PRs for metadata-build graph capture in core and found only #61868 (model-local, DSv4.1 builders). #52440 guards metadata addresses before replay and #61779/#61952 make GDN metadata static. Neither records host builds.
