# [Spec Decode] Lazy recovery in rejection sampling: compute recovered tokens in-kernel on first rejection

[Upstream PR](https://github.com/vllm-project/vllm/pull/41258) · state: open · merged: False

## Original PR description

## Summary

This PR changes rejection-sampling recovery from eager to lazy.

Today, the rejection sampler prepares recovery sampling work before it knows whether recovery is needed. In speculative decoding, each request needs at most one recovered token for a speculative step: the token at the first rejected draft position. If all draft tokens are accepted, recovery is not needed. If an early draft token is rejected, later draft positions are discarded, so recovery work for those later positions is wasted.

This PR moves recovery sampling into `rejection_random_sample_kernel`. The kernel first runs accept/reject logic, and only on the first rejection does it sample a recovered token from the residual distribution `(target_probs - draft_probs)+`. For `draft_probs=None`, it samples from the target distribution with the rejected draft token excluded, matching the existing no-draft-probs behavior.

The result is the same sampling distribution, but without eager full-vocab recovery buffers in the production path.

## What changed

Changed files:

```text
vllm/v1/sample/rejection_sampler.py
tests/v1/sample/test_rejection_sampler.py
```

Implementation changes:

- `rejection_random_sample_kernel` now computes recovery lazily on first rejection.
- Recovery uses the same exponential-race formulation as the eager helper: `score = residual_prob / Exp(1)`, and the argmax is the recovered token.
- `generate_recovery_seeds` creates one int64 seed per speculative token. The full-vocab random values are generated in-kernel only when recovery is actually needed.
- `USE_FP64_GUMBEL` is supported in the lazy path with a constexpr branch, so fp32 and fp64 paths specialize independently.
- The eager `sample_recovered_tokens` helper remains for tests/compatibility, but production rejection sampling no longer materializes recovered tokens eagerly.
- Greedy sampling remains on the existing greedy path.

## Why this helps

Let:

- `B` = batch size
- `k` = number of draft tokens
- `V` = vocab size
- `R` = number of requests in the batch that actually need recovery

The old eager recovery path prepares recovery candidates before knowing which draft positions will reject. The scoring work scales roughly like:

```text
B x k x V
```

Lazy recovery first determines whether a request rejects. It scans the vocab only for requests that actually need a recovered token:

```text
R x V, where R <= B
```

So even in the worst case, where every request rejects, lazy recovery removes the `k` multiplier:

```text
old worst case: B x k x V
new worst case: B x V
```

If all drafts are accepted, lazy recovery does zero full-vocab recovery work.

Example with `B=64`, `k=16`, and `V~128k`:

```text
old eager recovery scoring: 64 x 16 x 128k ~ 131M vocab lanes
new worst case: 64 x 128k ~ 8M vocab lanes
new all-accepted case: 0 recovery lanes
```

Approximate reduction by recovery incidence:

| Requests needing recovery | Rough recovery-work reduction |
|---:|---:|
| 100% | 16x |
| 25% | 64x |
| 10% | 160x |
| 1% | 1600x |
| 0% | eager still pays; lazy pays zero |

There is also a random-number-generation win. In the benchmarked `B=64`, `V=50,272`, `k=16` shape, the eager helper generated about:

```text
64 x 50,272 ~ 3.2M exponential values
```

The lazy production path uses:

```text
64 x 16 = 1,024 int64 recovery seeds
```

That is about `3,142x` fewer random values in that shape.

Memory-wise, the eager helper materializes a full-vocab recovery-noise buffer of shape `B x V`. The lazy production path eliminates that recovery buffer.

Measured eager helper allocation sizes:

| batch | vocab | dtype | eager recovery buffer | lazy production recovery buffer |
|---:|---:|---|---:|---:|
| 64 | 50,272 | fp32 | 12.27 MiB | 0 bytes |
| 64 | 50,272 | fp64 | 24.55 MiB | 0 bytes |
| 64 | 128,256 | fp32 | 32.00 MiB peak | 0 bytes |
| 64 | 128,256 | fp64 | 62.62 MiB | 0 bytes |

This is a recovery-buffer allocation measurement, not a claim that whole-server peak memory drops by exactly these amounts.

## EAGLE / draft-probs coverage note

Validation showed default EAGLE3 in this tree uses greedy draft mode with `draft_logits=None`, which corresponds to the `draft_probs=None` path at rejection sampling time.

So the coverage statement is intentionally narrow:

- `temperature > 0` EAGLE traffic would exercise the same `NO_DRAFT_PROBS=True` lazy-recovery branch as ngram.
- It does not exercise the `draft_probs=True` residual-subtraction branch.
- The `draft_probs=True` branch is covered by unit tests, direct eager-vs-lazy equivalence tests, and mechanism benchmarks with `draft_probs=True`.
- This PR does not include a dedicated EAGLE end-to-end performance claim.

## Limitations / tradeoffs

- Random sampling is distribution-equivalent, not bitwise-RNG-identical to main.
- End-to-end throughput is expected to be near-neutral when the rejection sampler is a small share of total decode time.
- The performance claim is intentionally scoped to mechanism-level wins and recovery-buffer/RNG elimination, not a broad e2e speedup headline.
- Default EAGLE3 in this tree covers `draft_probs=None`; `draft_probs=True` is covered by tests and mechanism benchmarks rather than EAGLE e2e.

The refactoring of `apply_sampling_constraints` has removed temperature scaling and the expansion of per-request `top_k` and `top_p` values to per-token values. This is a critical issue as it will lead to incorrect sampling behavior for non-greedy requests.

1.  **Missing Temperature Scaling**: The `logits.div_(temperature.unsqueeze(-1))` operation has been removed. Without temperature scaling, the probability distribution will be incorrect for random sampling.
2.  **Incorrect `top_k`/`top_p` Application**: The `apply_top_k_top_p` function is now called with per-request `top_k` and `top_p` tensors (`[batch_size]`) on a per-token `logits` tensor (`[num_tokens, vocab_size]`). The previous implementation correctly expanded `top_k` and `top_p` to be per-token using `expand_batch_to_tokens`. This change will likely cause `apply_top_k_top_p` to fail or produce incorrect results.

The logic for applying temperature and expanding sampling parameters needs to be restored to ensure correct sampling.

The `dtype` for `uniform_probs` has been changed from `torch.float64` to `torch.float32`. The original code included a comment explaining that `float64` was used deliberately to avoid the non-negligible chance of `torch.rand` producing exactly 0.0 with `float32`, referencing a known PyTorch issue (https://github.com/pytorch/pytorch/issues/16706).

While the probability is low, `uniform_prob` being exactly 0.0 can lead to incorrect behavior in the rejection sampling logic (e.g., `target_prob / draft_prob >= 0.0` could be true even when it shouldn't). Reverting to `torch.float64` would be safer to ensure correctness and reproducibility, as was the original intent.

```suggestion
    uniform_probs = torch.empty(
        (num_tokens,),
        dtype=torch.float64,
        device=device,
    )
    uniform_probs.uniform_()
```
