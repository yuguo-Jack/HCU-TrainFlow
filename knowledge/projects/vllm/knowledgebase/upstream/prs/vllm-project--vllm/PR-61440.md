# Fix non-deterministic greedy decoding across repeated generate() calls

[Upstream PR](https://github.com/vllm-project/vllm/pull/61440) · state: open · merged: False

## Original PR description

## Summary

Fixes vllm-project/vllm#61319

cuBLAS may use split-K GEMM algorithms whose partial-result reduction order depends on GPU thread scheduling. With atomicAdd-based reduction, tiny floating-point differences can accumulate between successive calls on the same engine, eventually flipping an argmax boundary in greedy (temperature=0) sampling.

## Root cause

The non-determinism stems from cuBLAS split-K GEMM kernels that use atomicAdd to accumulate partial results from different thread blocks. The order in which these atomicAdd operations execute depends on GPU scheduler timing, producing subtly different floating-point sums across repeated calls. Over many transformer layers, these small differences can compound and flip the argmax in greedy decoding.

## Fix

Configure cuBLAS and cuDNN to use deterministic algorithms by default in `vllm/platforms/cuda.py`:

- Set `CUBLAS_WORKSPACE_CONFIG=:16:8` — forces cuBLAS to use non-split-K kernels with fixed algorithm selection
- Set `CUBLASLT_WORKSPACE_SIZE=1` — prevents cuBLASLt from using split-K GEMM
- Enable `torch.backends.cudnn.deterministic = True` — cuDNN uses deterministic algorithms
- Disable `torch.backends.cudnn.benchmark = False` — disables cuDNN autotuner

All environment variables use `os.environ.setdefault()` so explicit user-provided values are preserved.

## Verification

The fix applies unconditionally when vLLM initializes on a CUDA platform. Users who have already set these environment variables explicitly will not be affected (the fix uses `os.environ.setdefault`).

## Alternative considered

vLLM already has deterministic settings gated behind `VLLM_BATCH_INVARIANT=1`. This fix makes determinism the default for the CUDA platform, aligning with user expectations that greedy/temperature=0 decoding should be reproducible.
