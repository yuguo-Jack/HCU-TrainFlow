# [Observability] Add structured per-request context to preemption warnings

[Upstream PR](https://github.com/vllm-project/vllm/pull/42827) · state: closed · merged: False

## Original PR description

## Summary

Add a `logger.warning()` call inside `Scheduler._preempt_request()` that emits
structured per-request context at the exact moment a request is evicted from the
running queue due to KV cache exhaustion.

## Motivation

When preemption occurs under memory pressure, the current V1 runtime has:
- A cumulative Prometheus preemption counter
- A `PREEMPTED` lifecycle event recorded per request (for latency metrics)
- `preempted_req_ids` in `SchedulerOutput`

None of these produce a human-readable log entry at the preemption site with
context useful for diagnosing the root cause. Operators observing latency spikes
from preemption thrash (e.g. #25538, closed not_planned) currently have no way
to identify which request was evicted, how much computed work was discarded, or
what memory pressure looked like at the moment it happened.

## What this PR adds

A single `logger.warning()` in `_preempt_request()`, capturing:

- `request_id` — which request was evicted
- `num_computed_tokens` lost — recompute cost on resume (captured before `free()`)
- `kv_cache_usage` before → after — memory pressure context
- per-request `num_preemptions` — identifies thrash on a single long request

Example output:
```
WARNING [scheduler.py] Preempting request cmpl-abc123: 480 computed tokens lost
(recompute on resume), kv_cache_usage 98.4% -> 96.1%. Preemption count for this
request: 1. To reduce preemptions, increase gpu_memory_utilization or
max_model_len, or decrease max_num_seqs.
```

## Relation to #36449

This PR is not a duplicate of #36449 ("[Observability] Add scheduler preemption
metrics"). That PR adds aggregate metrics and summary-level log visibility.
This PR adds per-event structured context at the preemption call site itself —
complementary, not overlapping. Both can merge independently.

## Changes

- `vllm/v1/core/sched/scheduler.py`: capture `num_computed_tokens` and
  `kv_cache_manager.usage` before `free()`, emit `logger.warning()` after.
  No behavior changes. Existing counters and events are unchanged.
- `tests/v1/core/test_scheduler.py`: two new tests using the existing
  `create_scheduler` / `create_requests` / `ModelRunnerOutput` harness.
  Forces KV exhaustion to trigger preemption, asserts warning is emitted with
  expected structured fields. No GPU required.

The advice to "increase max_model_len" to reduce preemptions is misleading. In vLLM, `max_model_len` defines the maximum sequence length allowed; increasing it allows requests to grow longer and consume more KV cache blocks, which actually increases memory pressure and the likelihood of preemption. To reduce preemptions, users should either increase `gpu_memory_utilization` (to allocate more physical blocks) or decrease `max_model_len` or `max_num_seqs` (to reduce the total number of blocks required by active requests).

```suggestion
            "To reduce preemptions, increase gpu_memory_utilization, or "
            "decrease max_model_len or max_num_seqs.",
```
