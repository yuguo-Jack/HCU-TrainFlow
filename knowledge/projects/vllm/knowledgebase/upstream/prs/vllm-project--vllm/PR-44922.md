# [Metrics] Add vllm:request_received counter labeled by input modality

[Upstream PR](https://github.com/vllm-project/vllm/pull/44922) · state: open · merged: False

## Original PR description

## Purpose

Today every request metric is modality-agnostic, so there is no way to answer "what fraction of my request rate is text vs multi-modal?" from Prometheus. The only multi-modal metrics that exist (`vllm:mm_cache_queries`/`vllm:mm_cache_hits`) count cache *items*, not requests.

This PR adds a new **`vllm:request_received`** counter labeled by input `modality`, so request rate can be split by input type:

- `text` — text-only request (no multi-modal data)
- `mixed` — request combining more than one distinct modality
- otherwise the model-reported modality string, passed through as-is (`image`, `audio`, `video`, …)

The modality is derived from the request's `mm_features` (each `MultiModalFeatureSpec` exposes a `modality` string), computed once at request creation. The counter is incremented when a request is **admitted to the engine-core queue** (the `QUEUED` engine-core event), so it counts every received request once, regardless of how it finishes.

A dedicated counter — rather than adding `modality` to `vllm:request_success` — keeps the label set small (no `finished_reason` × `modality` cross-product) and lets the modality string be handed straight to the Prometheus child. Only the `text` bucket is pre-registered per engine (so it always shows as `0` in scrapes); every other modality's child is created lazily by `prometheus_client` on first use, so label cardinality stays bounded by the modalities the loaded model actually serves.

Example queries this enables:

```promql
# image request rate
rate(vllm:request_received_total{modality="image"}[5m])
# overall multi-modal request rate
sum(rate(vllm:request_received_total{modality!="text"}[5m]))
```

**Not a duplicate:** I searched open `vllm-project/vllm` PRs for `modality metric`, `request_received`, and `multimodal request rate` — no open PR adds modality labeling to request metrics.

### Changes

- `vllm/v1/metrics/stats.py` — `compute_request_modality()` helper (returns `text` / single modality string / `mixed`); `RequestStateStats.modality`; `IterationStats.received_requests`, appended once on the `QUEUED` event.
- `vllm/v1/engine/output_processor.py` — modality computed from `request.mm_features` at request creation and stored on the request's stats.
- `vllm/v1/metrics/loggers.py` — new `vllm:request_received` counter with a `modality` label; `text` pre-registered per engine, other modalities created lazily; incremented from `iteration_stats.received_requests`.
- `docs/design/metrics.md` — documented the new metric and example queries.
- `tests/v1/metrics/test_stats.py` — unit tests for modality derivation and received-request tracking.
- `tests/entrypoints/serve/instrumentator/test_metrics.py` — registered `vllm:request_received_total` in the metrics-endpoint test.

`vllm:request_success` is unchanged.

Thank you for your contribution!

The first issue we need to consider is backwards compatibility - what is the effect on existing dashboards, alerts, queries, etc. using `vllm:request_success_total` when we add a new label? The effect of the new label is to add multiple time-series where there was previously only one, and this is arguably a breaking schema change. I think in some cases, a query without the modality label (but with this new version of the metric) will have the same effect as with the old version ... but I would take a lot of persuasion that there's no risk of breakage in some cases.

The safest thing would be to add a new `vllm:request_success_by_modality_total` metric instead

> Today the `vllm:request_success_total` counter (and every other request metric) is modality-agnostic, so there is no way to answer "what fraction of my request rate is text vs multi-modal?" from Prometheus. 

And I'm honestly a little sceptical of the value these 25 (5 reasons x 5 modalities) new time series for something that doesn't seem terribly actionable ... e.g. what sort of scaling decisions or operational alerts might be based on these metrics? In fairness, we do have plenty of existing metrics that are more informational than operational, but I'm just calling out the fact we're actually adding 25 of them here!
