# [Bugfix][Attention] Keep FA sliding window active under batch invariance

[Upstream PR](https://github.com/vllm-project/vllm/pull/65627) · state: open · merged: False

## Original PR description



## Overview

With `VLLM_BATCH_INVARIANT=1`, keep FlashAttention's sliding window active in every step, so Gemma-2 outputs on H100 (FA3) no longer depend on which requests share the batch.

Fixes #65587

## Claims

- Fixes #65587: under batch invariance, a sliding-window request on FA3 gives the same tokens and bitwise-equal logprobs alone as when it decodes next to other requests' prefill chunks.
- A 9-line change in `FlashAttentionImpl.forward`. It only runs with `VLLM_BATCH_INVARIANT=1` on layers that have a sliding window; every other configuration is unchanged.
- Adds `test_sliding_window_logprobs_bitwise_alone_vs_mixed_batch` to `tests/v1/determinism/test_batch_invariance.py`, which the existing H100 and B200 batch invariance CI jobs already run.

## Details

**Root cause.** FA3 picks its kernel on the host from `max_seqlen_k`:

- It drops a left window that covers the longest sequence ([`hopper/flash_api.cpp#L865`](https://github.com/vllm-project/flash-attention/blob/b273a02621d3c94bc747df67204f591b67f38fae/hopper/flash_api.cpp#L865): `if (window_size_left >= seqlen_k - 1) window_size_left = -1;`), which turns local attention off.
- For head dim 256 the KV tile is `is_local ? 64 : 80` ([`hopper/tile_size.h#L51`](https://github.com/vllm-project/flash-attention/blob/b273a02621d3c94bc747df67204f591b67f38fae/hopper/tile_size.h#L51)). A different tile changes the online-softmax accumulation order, and with it the output bits.

vLLM passes the batch's real maximum as `max_seqlen_k` in eager steps, but `max_model_len` when capturing FULL CUDA graphs (`for_cudagraph_capture` in MRV1 `gpu_model_runner.py` and MRV2 `model_states/default.py`). With `max_model_len` above the window (8192 vs 4096 in the issue), uniform-decode steps replay graphs that keep the window. Mixed prefill/decode steps run attention eagerly and drop it, unless some sequence in the batch is longer than the window. Without CUDA graphs the same flip happens whenever a batch contains a sequence longer than the window. This matches the issue's results, which were invariant in four cases: with `max_model_len=4096`, with CUDA graphs off and only short prompts, with TRITON_ATTN, and with the sliding window disabled.

**Fix.** Under batch invariance, raise `max_seqlen_k` to at least `window_left + 2` for windowed layers. FA then keeps the window and uses the local kernel in every step, matching the captured graphs. FA2's drop rule (`window_size_left >= max_seqlen_k`) is covered by the same floor.

**Why it is safe.** FA uses `max_seqlen_k` only for host-side decisions (window drop, tile and scheduling heuristics, declared page-table extent). Per-request lengths come from `seqused_k`, which is how captured graphs already run with `max_model_len`. Two existing tests run below the window (`max_model_len` 2048 and 4096, so the floor exceeds `max_model_len`), and both pass on FA2. The added code only compares Python ints, so it adds no GPU sync.

**Not a duplicate.**

- No open PR references #65587.
- #48694 (open, for #47069) routes all regular Hopper attention to FA2 under batch invariance. That would also hide this bug, but it gives up FA3 for every model. This change keeps FA3 and fixes the window-specific cause, and the two are independent.
- flash-attention#169 (open) adds an FA3 `batch_invariant` mode that pins the MMA warpgroup, paged-KV TMA, split-KV and decode causal choices. It leaves the window drop alone, so it would not fix this on its own.

**Tradeoffs and limitations.**

- Under batch invariance, head-dim-256 windowed layers on FA3 now always use the 64-wide local tile. That includes `max_model_len` at or below the window, where they previously always used the 80-wide one. Not benchmarked; batch-invariant mode only.
- Head-dim-128 windowed models (e.g. Gemma-2-27B, Granite SWA) get a 128-wide tile from both kernels on vLLM's paged-KV path, which is why they were not affected.
- `_forward_encoder_attention` (encoder-only sliding-window models) drops the window the same way. I left it out because there is no report for it and nothing to test it on here.
- In CI, only the H100 batch invariance job runs this on FA3. B200 and A100 run FA2 under batch invariance, so they pass with or without the fix, and ROCm skips the test.
