# [Bugfix][KV offload] Validate computed device pointers before copy

[Upstream PR](https://github.com/vllm-project/vllm/pull/53271) · state: open · merged: False

## Original PR description

## Problem

`compute_sub_block_ptrs()` in `vllm/v1/kv_offload/cpu/gpu_worker.py` derives raw
device addresses from `data_ptr()`, `stride(0)` and `shape[1]`:

```python
base_ptr = tensor.data_ptr()
row_stride = tensor.stride(0)
block_page_size = tensor.shape[1] // blocks_per_chunk
all_ptrs = (base_ptr + block_ids * row_stride) + sub_offsets
```

Those addresses are handed to the swap kernel, which dereferences them as
`int64*`:

```python
src = tl.load(src_addrs + job).to(tl.pointer_type(tl.int64))
words = tl.load(sizes + job) // 8
data = tl.load(src + idx, mask=idx < words, other=0)
```

The `mask` bounds the copy against the *declared* size, not against the
allocation, and nothing validates the pointers themselves. The arithmetic
assumes a flat, unpadded row layout; a cache whose pages carry alignment
padding produces addresses that walk off the buffer.

### Reproduction

Enabling `OffloadingConnector` with a `fs_python` tier on DeepSeek-V4, whose MLA
pages are padded to 576B (`fp8_ds_mla`) or 584B, kills the worker during
startup:

```
RuntimeError: Worker failed with error 'CUDA error: an illegal memory access
was encountered'
```

Reproduced on v0.27.1 with and without the b12x attention backend, so it is not
backend-specific.

An IMA is the *lucky* outcome. Because the kernel masks against the declared
size rather than the allocation, the same mismatch can instead copy the wrong
bytes successfully and corrupt KV silently.

## Change

Adds a host-side bounds check on the computed pointer array, on both exit paths
of `compute_sub_block_ptrs()`. One `min`/`max` over the array per batch, which
is negligible next to the transfer itself.

On violation it raises a `ValueError` naming the offending range, the tensor
shape, dtype and `stride(0)`, and points at the likely cause, instead of
faulting inside the kernel.

## Scope

This does **not** add MLA/padded-page support to the offload path. It makes the
unsupported case fail diagnosably rather than dangerously. Supporting padded
layouts would additionally require deriving per-block offsets from
`MLAAttentionSpec.page_size_bytes`/`alignment` rather than `tensor.shape[1]`,
and handling multiple KV cache groups with differing geometry.

## Test

Logic verified for in-bounds, out-of-bounds and empty pointer arrays. Happy to
add a unit test under `tests/v1/kv_offload/` if you would like it in this PR;
I did not want to guess at the preferred fixture style.

- maci0 · comment · 2026-10-02T04:22:05Z · [source](https://github.com/vllm-project/vllm/pull/53271#issuecomment-5945553433)

Thanks for looking at it.

**Config where we see it.** DeepSeek-V4-Flash, `--kv-cache-dtype fp8_ds_mla` (MLA pages pad to 576B/584B), `--block-size 256`, offloading enabled via `--kv-offloading-size` with `--kv-offloading-backend native`. On v0.27.1 that killed the worker during startup with `RuntimeError: Worker failed with error 'CUDA error: an illegal memory access was encountered'`, with and without the b12x attention backend, so it is not backend-specific. At the time the enabling path was `OffloadingConnector` with an `fs_python` tier; the flag names above are what current main calls it.

**Why your run may not reach it.** The failing arithmetic only runs when `blocks_per_chunk > 1`. That value is set at `gpu_worker.py:360` from the page-size relationship the comment there states — `cpu_page_size = gpu_page_size * blocks_per_chunk`, i.e. it is greater than 1 only when the GPU *kernel* page is smaller than the manager block. If your DSV4 run kept the kernel page equal to the manager block, `blocks_per_chunk == 1` takes the fast path at line 112 (`base_ptr + block_ids * row_stride`) and the sub-block offset math never executes, so nothing mismatches.

When it does execute, the sub-block stride is `tensor.shape[1] // blocks_per_chunk` (line 119). That assumes a row splits evenly into equal, unpadded kernel pages. A padded MLA page places sub-block `j` at `j * page_size_bytes`, which is not that quotient once the row carries alignment padding, so the offsets walk past the row. If you can say which `--block-size` and which kernel block size your run used, that should pin down whether you were on the fast path.

**On fixing the core rather than validating.** Agreed that the core fix is the right end state, and it is the flat-page assumption above. Doing it properly means deriving each sub-block offset from the spec (`MLAAttentionSpec.page_size_bytes` / `alignment`) instead of dividing `shape[1]`, which is what the Scope section of the description flags as not included here. I kept this PR to the guard because the current failure mode is not only the crash: the swap kernel masks against the declared size rather than the allocation, so the same mismatch can also copy the wrong bytes and corrupt KV silently, and a guard turns that into a named error immediately.

Happy to do the core fix as a follow-up, or fold it into this PR if you would rather have one change — say which. One caveat on the follow-up: I cannot exercise padded-page offload on our two-node GB10 rig, so I would be writing that pointer math without a run behind it and would want your repro to validate it.
