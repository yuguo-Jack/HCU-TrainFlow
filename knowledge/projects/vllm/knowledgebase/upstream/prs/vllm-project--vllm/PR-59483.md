# [ROCm][Perf] Fuse the MXFP4 activation quant into AITER AR+RMSNorm

[Upstream PR](https://github.com/vllm-project/vllm/pull/59483) · state: open · merged: False

## Original PR description

## Purpose

With `VLLM_ROCM_USE_AITER_FP4_ASM_GEMM=1`, an MXFP4 linear fed by an all-reduce + RMSNorm runs three launches at decode: the fused AR+RMSNorm, a separate `per_1x32_f4_quant_hip` activation quant, and the GEMM. AITER already has a fused AR+RMSNorm+MXFP4 epilogue that quantizes inside the all-reduce kernel, but nothing in vLLM reaches it. It also had no Gemma `(1 + w)` mode, which Qwen3.5/3.8 and Gemma need; ROCm/aiter#6000 adds one.

This PR adds `AiterAllreduceFusedAddRMSNormMxfp4GemmPattern` and its Gemma variant, matching `all_reduce -> fused_add_rms_norm -> gemm_with_dynamic_quant`. They lower to a new `rocm_aiter_fused_allreduce_rmsnorm_mxfp4_gemm` op:

- **Below M=32, on a shape with a tuned preshuffled FP4 GEMM config:** the op quantizes the normed activation in the all-reduce epilogue and passes the unshuffled per-1x32 scales straight to `gemm_afp4wfp4_preshuffle`, which is the scale layout it takes below M=32.
- **Everywhere else:** the existing AR+RMSNorm op, then the GEMM, exactly as today. This covers M ≥ 32 (shuffled scales), untuned shapes (ASM `gemm_a4w4`) and shapes neither fused launcher accepts.
- **Other consumers of the norm:** the bf16 normed activation stays a pattern output, so they keep working. In Qwen3.5/3.8 GDN layers, the bf16 `in_proj_ba` reads the same norm as the MXFP4 `in_proj_qkvz`.
- **When the patterns register:** only when the AITER build's `fused_ar_rms_mxfp4_quant` takes `gemma_norm` and the ASM FP4 GEMM dynamic-quant path is enabled.
- **Kernel choice:** `AiterCustomAllreduce.mxfp4_fused_ar_rms_stage` picks the one- or two-stage kernel, mirroring AITER's `CudaCommunicator.fused_allreduce_rmsnorm_mxfp4_quant`.

The patterns register first in the pass, since they span the AR+RMSNorm subgraph plus the linear. The Gemma variant keeps #58547's approach of matching the effective-gamma expression and passing the raw weight with `gemma_norm`.

On Qwen3.8 the fused path needs the tuned `N=4608-K=8192` preshuffled config for `in_proj_qkvz` (ROCm/aiter#5998) and the logical-K config probe from #59406. Without them `in_proj_qkvz` runs the ASM GEMM and this op takes the unfused route.

## Test Plan

- Hardware: 8× MI355X (gfx950)
- Unit tests: new `tests/distributed/test_aiter_ar_rms_mxfp4_gemm.py` (CPU-only):
  - decode routes to the fused epilogue with `gemma_norm` passed through;
  - M=32, an untuned shape and a rejected shape fall back to the unfused sequence;
  - the one- or two-stage choice at TP8.
- AITER kernel test at TP8 in the same image: `op_tests/multigpu_tests/test_fused_ar_rms_mxfp4_quant.py` from ROCm/aiter#6000
- Model: `amd/Qwen3.8-2.4T-A95B-Quark-MXFP4`, TP8, `max_num_batched_tokens=8192`, GDN `in_proj_qkvz` and `out_proj` quantized online to MXFP4, `VLLM_ROCM_USE_AITER_FP4_ASM_GEMM=1`, with #58547, #59406 and ROCm/aiter#5998 in both arms
- Trace A/B: c=4, ISL=8192, OSL=1024, profiled decode steps on rank 0
- Accuracy: GSM8K, 1319 problems, 5-shot, thinking off, temperature=0.0
- Serving A/B: random dataset, ISL=8192, OSL=1024 (`random-range-ratio` 0.8), concurrency 4, 16 and 64; control image without this PR and #6000, otherwise identical

### Kernels

From c=4 profiled decode steps (rank 0):

| | Control | This PR |
| --- | --- | --- |
| AR + RMSNorm before `in_proj_qkvz` | 1-stage AR+RMSNorm 12.0 µs + `per_1x32_f4_quant_hip` 4.5 µs | `allreduce_fusion_kernel_1stage_mxfp4` 13.9 µs |
| Calls per decode step | 68 + 68 | 68 |
| Median decode step | 11.03 ms | 10.81 ms (−2.0%) |

There are 69 GDN layers; the first has no all-reduce in front of it, so 68 fuse. 68 × 2.6 µs ≈ 0.18 ms of the 0.22 ms step difference.

### Serving

| ISL/OSL | Concurrency | Output tok/s (control → PR) | Mean TTFT ms | Mean TPOT ms |
| --- | --- | --- | --- | --- |
| 8192/1024 | 4 | 341.5 → 338.9 (−0.7%) | 341.8 → 329.1 | 11.1 → 11.2 |
| 8192/1024 | 16 | 692.0 → 694.3 (+0.3%) | 621.5 → 620.9 | 21.8 → 21.7 |
| 8192/1024 | 64 | 1379.9 → 1386.9 (+0.5%) | 2342.3 → 2318.7 | 42.4 → 42.2 |

End to end the difference is within run-to-run noise at all three concurrencies. The fused epilogue only runs for decode batches below M=32 (c=4 and c=16 here); at c=64 both arms take the unfused route. The 0.22 ms per decode step saved in the c=4 trace is not resolved by the serving benchmark.

### Accuracy

GSM8K: 0.9680 with this PR, against 0.9658 for the control image in the #59406 A/B.
