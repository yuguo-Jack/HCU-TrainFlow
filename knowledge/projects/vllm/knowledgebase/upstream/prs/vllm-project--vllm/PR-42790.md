# [WIP] Automatic pod snapshotting for quick resume

[Upstream PR](https://github.com/vllm-project/vllm/pull/42790) · state: closed · merged: False

## Original PR description

## Purpose

Introduces automatic pod and GPU snapshotting as an entirely new feature. It establishes a pluggable provider interface via `BaseSnapshotProvider` that is dynamically discovered through the plugin registry by the  `SnapshotManager`. To support this, `enable_snapshot` and `snapshot_provider` configuration optaions are integrated into `EngineArgs`, with automatic invocation wired into the engine lifecycle during startup in `LLMEngine` and `AsyncLLM`. Furthermore, snapshot triggering is natively integrated into the FastAPI server health checks in health, returning a 503 service unavailable status while background snapshots are actively in progress, and complete unit tests are provided in `test_snapshot_manager.py`.

(2) Integration test planned: build image, execute, check for snapshot (GKE-specific for now)

- RyanRosario · comment · 2026-05-22T21:03:55Z · [source](https://github.com/vllm-project/vllm/pull/42790#discussion_r3291200174)

File: `vllm/v1/engine/llm_engine.py` · line 135

The comment there is misleading and I will push it with the next update: `# Setup snapshot manager if enabled`. We setup the snapshot manager there, not the triggering. The actual triggering occurs in the **FastAPI server's** initialization, not the vLLM server. The `/health` endpoint is a route within the FastAPI server and GKE sends requests to that health route to check pod readiness.

* When the health endpoint returns 503, GKE sees that the web server is running and responding to checks, but is not yet ready to handle traffic. In our case, this means the snapshot is not done yet.
* When it returns 200, the pod is then ready and can serve user traffic. In our specific case, the snapshot is complete.

If I trigger the snapshot inside `__init__`, the FastAPI server will be blocked, thus will never respond to liveness/health checks and GKE will kill or restart the pod.

So, yes, the end of `__init__` *is* the end of the initialization, but it is still **before** the FastAPI server starts, where the health endpoint lives.
