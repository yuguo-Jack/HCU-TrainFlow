# [CPU] UltraQuant 4-bit KV cache on CPU

[Upstream PR](https://github.com/vllm-project/vllm/pull/61168) · state: open · merged: False

## Original PR description

## Purpose

Runs the `ultraquant_4bit` KV cache on CPU. The format, its config plumbing and the GPU backend landed in #57057; this adds the CPU half, so the same 4-bit cache that serves long contexts on MI355X also serves them on Zen/x86.

Nothing in the existing GPU path changes. The format modules under `vllm/v1/attention/ops/ultraquant/` are imported, not duplicated, so both backends are held to one definition of the layout.


## Test Plan

- `tests/kernels/ultraquant/test_cpu_store_vs_reference.py` and `test_cpu_decode_vs_reference.py`, checked against the same `ops/ultraquant/reference.py` the Triton tests use, and wired into the `CPU-Kernel Tests` Buildkite job.
- Accuracy: GSM8K 5-shot, KV dtype as the only variable.
- Performance: concurrency sweeps at five context shapes on Turin.

## Usage

```
vllm serve amd/Phi-4-mini-instruct-w4a16-llmcompressor --kv-cache-dtype ultraquant_4bit
```

## Test Results

**Accuracy — GSM8K 5-shot, Phi-4-mini-instruct-w4a16**, lm-eval 0.4.12, flexible extract, chat template, greedy, 1319 problems:

| KV dtype | exact_match |
|---|---|
| fp8 | 73.16% ± 1.22 |
| ultraquant_4bit | 71.19% ± 1.25 |

**Performance.** Phi-4-mini-instruct-w4a16 on 30 Turin cores, 24 GB KV budget, one server per dtype, concurrency as the only variable. Output token throughput, UltraQuant against fp8:
