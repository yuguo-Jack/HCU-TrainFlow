# [Bugfix][KV Connector] Cap MooncakeStore lookup at num_tokens - 1

[Upstream PR](https://github.com/vllm-project/vllm/pull/55113) · state: open · merged: False

## Original PR description

---
## Summary

Caps the MooncakeStore lookup result at `num_tokens - 1` inside `MooncakeStoreScheduler.get_num_new_matched_tokens`, so a lookup that reports the full prompt can no longer drive `num_new_tokens` to zero in `Scheduler.schedule()` and trip `assert num_new_tokens > 0` (`vllm/v1/core/sched/scheduler.py:923`) on the sync (`load_async=False`) path.

The cap is applied before both uses of the value, the returned `need_to_allocate` and the cached `load_specs.kvpool_cached_tokens`, so the round trip through the scheduler back into `update_state_after_alloc` (which asserts `num_external_tokens == kvpool_cached_tokens - vllm_cached_tokens`) stays consistent. No scheduler code is touched.

## Background

The last prompt token must always be recomputed locally to obtain logits. That rule is already enforced in three places: the local prefix cache lookup (`get_computed_blocks`), five in tree connectors (example, HF3FS, LMCache v1 adapter, MoRIIO READ, decode bench), and the MooncakeStore worker itself, which rederives a full hit below the request end (`worker.py:1854`). The MooncakeStore scheduler side component was the one place that passed the raw lookup count through uncapped.

One precision note for reviewers: through a matched pair of in tree server and scheduler components, the worker side rederivation keeps the lookup below N today. This change caps the scheduler side component itself, so the assert gated sync path no longer depends on server side behavior. The scheduler side receives its number over ZMQ from a server the base connector contract does not bound, and any server returning N (a third party implementation, a custom `LookupKeyServer`, or a future refactor) would crash `schedule()` without this guard.

## The fix

`vllm/distributed/kv_transfer/kv_connector/v1/mooncake/store/scheduler.py` (+10 lines): `min(num_external_hit_tokens, max(request.num_tokens - 1, 0))` immediately after the lookup resolves and before `need_to_allocate` and `load_specs` are derived. The cap is idempotent against values the worker already truncated, preserves the async flag, and leaves every below cap result byte for byte unchanged.

Verified the failure mode and the accounting here. On the sync path an uncapped full-prompt hit drives `num_computed_tokens` to `request.num_tokens` and `schedule()` trips the `assert num_new_tokens > 0` after the budget min, so the crash is real and connector-side is the right place to fix it. The round trip is also consistent, `need_to_allocate` and `kvpool_cached_tokens` both derive from the same capped value and the scheduler passes `num_external_computed_tokens` through unchanged into `update_state_after_alloc`, so the equality assert there holds without the special-casing the LMCache adapter needs.

For the in-tree pair this is a no-op as described. The lookup server already rederives a full hit through `align_lookup_length(num_tokens - 1)` before replying (it lives in `LookupKeyServer.lookup` around worker.py:2202 these days, not 1854), so anything the client sees is already floored to a hash or block boundary below N. Which is also my one real concern with the shape of the cap, see inline.

On the cited idiom, moriio READ and decode_bench match as described. example and hf3fs both floor after the -1 rather than using the raw value, and the LMCache v1 adapter is a different mechanism, it only decrements the returned count when the hit equals `num_tokens`, keeps `lmcache_cached_tokens` uncapped, and skips the equality assert for that case. So the closest precedent for capping the hit itself is example/hf3fs, and both align, which is what the inline comment is about.

The only server this can change anything for is one that returns `hit_length >= num_tokens`, and for that server the capped length is not on an `align_lookup_length` boundary, while the `LoadSpec` below still carries the `tail_key_boundaries` that server computed for its uncapped hit. The worker then loads with `token_len = kvpool_cached_tokens` and takes the `end == token_len` substitution in `_handle_request`, indexing `block_hashes` with the stale boundary. So in the one scenario this guard exists for, the loud scheduler assert becomes a quiet mis-keyed tail load. I would mirror the server's own rederivation instead, floor to the `align` already computed at the top of this method and drop the returned `tail_key_boundaries` whenever the cap fires (an aligned end takes no substitute key). That is also how example and hf3fs apply the idiom, both floor after the -1.
