# [DSV4.1][DEP] Opt in switch for mori EP combine to FP4

[Upstream PR](https://github.com/vllm-project/vllm/pull/64235) · state: open · merged: False

## Original PR description

## Motivation

MoRI's intra-node combine sends each expert output back to the token's owning
rank as BF16 and reduces the top-k copies there. MoRI also ships a packed-FP4
(E2M1) blockwise codec for exactly that transport — `QuantType::Fp4BlockwiseQuant`,
the quantize/dequantize device primitives, the half-sized staging slots, and the
registered `EpCombineIntraNodeKernel_bf16_nop2p_fp4_blockwise*` kernels are all
already there.

Nothing in vLLM selects it. `MoriAll2AllManager._make_all2all_kwargs` never
passes `quant_type` when it builds the handle, so the config always lands on the
`"none"` default and the combine always moves BF16.

Turning the codec on cuts combine traffic substantially. Per token at hidden
5120, top-k 6, no combine weights:

| transport | bytes/token |
| --- | --- |
| BF16 | `5120 x 2` = 10240 B |
| FP4 | `5120 / 2 + 40 scales x 4 B` = 2720 B |

That is 3.76x less data on the MoE residual path. The codec is lossy, so it is
strictly opt-in and off by default.

Companion mori PR: [ROCm/mori#891](https://github.com/ROCm/mori/pull/891).

## Summary of changes

- **`vllm/envs.py`**: add `VLLM_MORI_FP4_COMBINE` (bool, default `0`), alongside
  the DeepEP combine knobs.
- **`vllm/distributed/device_communicators/all2all.py`**: when the flag is set,
  `MoriAll2AllManager._make_all2all_kwargs` passes
  `quant_type="fp4_blockwise"` instead of letting it default to `"none"`. The
  sending rank then quantizes each token to FP4 with one fp32 scale per block,
  and the receiving rank dequantizes back to BF16 as it accumulates.
- Same function gains an eager arch/topology guard. mori splits this check: it
  rejects a non-gfx950 arch at handle construction, but only rejects a
  non-IntraNode kernel type at the *first combine*, i.e. several minutes into a
  run. Both now raise before any weights are loaded.

No behavior changes with the flag unset — the kwargs are byte-for-byte what they
were.

### Configuring the scale block size

Blockwise combine sizes its scale blocks as `ceil(hidden_dim / scale_dim)`, from
mori's `MORI_FP8_COMBINE_SCALE_DIM` (default 56, chosen for hidden 7168 where it
gives exactly 128). mori only registers vectorized kernels at block sizes 128 and
256, and its send-side quantizer only vectorizes at those sizes too, so a hidden
dim that lands elsewhere silently falls back to scalar paths on both sides. At
hidden 5120, `MORI_FP8_COMBINE_SCALE_DIM=40` gives `5120 / 40 = 128`. The default
56 would give 92, which is not registered.

## Validation

8x MI355X (gfx950), DeepSeek-V4.1-Flash, DEP8 (TP1 x DP8 x EP8) with `mori_high_throughput`.
8192 in / 1024 out, 256 prompts at concurrency 256, speculative decoding off.

Measured against the stock ROCm nightly `vllm/vllm-openai-rocm:nightly`
(`0.33.0rc1.dev484+g76c6f3f2a`, mori `1.2.3.post1`) with only this PR and
[ROCm/mori#891](https://github.com/ROCm/mori/pull/891) applied.

This PR needs [ROCm/mori#891](https://github.com/ROCm/mori/pull/891). On today's mori, top-k 6
has no `AccumNum=6` symbol to select, and at the DEP8 decode shape the slice each warp is handed
is not 8-aligned, so the receive side takes the scalar per-nibble reduce either way and hands
back in the reduce what the transport saves.

### Performance

| Metric | Baseline | Both PRs, flag off | Both PRs, flag on | Improvement |
| --- | ---: | ---: | ---: | ---: |
| Output token throughput (tok/s) | 5621.45 | 5614.81 | 5777.16 | **+2.77%** |
| Total token throughput (tok/s) | 50593.04 | 50533.31 | 51994.42 | **+2.77%** |
| Median TPOT (ms) | 36.05 | 36.10 | 35.41 | **-1.78%** |
| Mean TPOT (ms) | 35.89 | 35.94 | 35.26 | -1.77% |
| Median ITL (ms) | 28.76 | 28.82 | 28.62 | -0.49% |
| Median TTFT (ms) | 9291.82 | 9297.34 | 8708.25 | -6.28% |
| Median E2EL (ms) | 46176.01 | 46232.32 | 44936.13 | -2.69% |
| Benchmark duration (s) | 46.63 | 46.69 | 45.38 | -2.70% |

Means over 2 warm runs per arm; the first run after each server boot is excluded as warmup.
Warm runs, output tok/s: baseline 5615.7 / 5627.2, flag off 5617.1 / 5612.6, flag on 5779.2 / 5775.1.

**The middle column is the control**: both PRs applied with `VLLM_MORI_FP4_COMBINE=0`. It lands
within **-0.12%** of the stock baseline, confirming the patches are inert with the flag unset and
that the gain is the FP4 combine rather than anything else in the two branches.

The gain is concurrency-dependent. At concurrency 64 the same build gives only ~+1.4%
(2114.1 -> 2143.8 tok/s): c64 over DEP8 is about 8 tokens per rank per decode step, below the
range where the combine reduce is the bottleneck, while c256 is about 32. See the per-kernel
table in [ROCm/mori#891](https://github.com/ROCm/mori/pull/891) for where that threshold sits.

### Accuracy

gsm8k, 5-shot, all 1319 questions, greedy.

| Arm | strict-match | stderr | flexible-extract | Delta |
| --- | ---: | ---: | ---: | ---: |
| Baseline | 0.9340 | 0.0068 | 0.9340 | — |
| `VLLM_MORI_FP4_COMBINE=1` | 0.9212 | 0.0074 | 0.9212 | -0.0128 |

About 1.3 sigma on the difference, so not significant at 95% on a single run each, but in the
direction a lossy codec predicts. `VLLM_MORI_FP4_COMBINE=0` restores the BF16 transport exactly.

### Reproduction

Server:

```bash
export VLLM_ROCM_USE_AITER=1
export VLLM_ROCM_USE_AITER_MOE=1
export VLLM_ROCM_USE_AITER_TRITON_SPARSE_MLA=True
export VLLM_USE_BREAKABLE_CUDAGRAPH=1
export VLLM_USE_RUST_FRONTEND=1

# FP4 arm only. 40 gives block_elems = 5120/40 = 128, a registered block size;
# mori's default of 56 would give 92, which is not, and silently falls back to
# the scalar path on both the quantize and the reduce side.
export VLLM_MORI_FP4_COMBINE=1
export MORI_FP8_COMBINE_SCALE_DIM=40

vllm serve /model/DeepSeek-V4.1-Flash \
  --served-model-name deepseek-ai/DeepSeek-V4.1-Flash \
  --tensor-parallel-size 1 \
  --data-parallel-size 8 \
  --enable-expert-parallel \
  --all2all-backend mori_high_throughput \
  --moe-backend aiter \
  --max-model-len 16384 \
  --gpu-memory-utilization 0.9 \
  --max-num-batched-tokens 8192 \
  --max-cudagraph-capture-size 1024 \
  --block-size 128 \
  --tokenizer-mode deepseek_v41 \
  --tool-call-parser deepseek_v41 \
  --reasoning-parser deepseek_v41 \
  --enable-auto-tool-choice \
  --language-model-only \
  --no-swa-bounded-replay \
  --no-enable-prefix-caching \
  --disable-uvicorn-access-log \
  --attention-config '{"indexer_kv_dtype":"mxfp4","indexer_sparse_logits":true}'
```
