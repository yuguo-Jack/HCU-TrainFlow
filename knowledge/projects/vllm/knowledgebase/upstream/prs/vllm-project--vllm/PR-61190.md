# [Bugfix][Frontend] systemone: take option labels from option names

[Upstream PR](https://github.com/vllm-project/vllm/pull/61190) · state: open · merged: False

## Original PR description



## Overview

Fixes #61189. `/v1/systemone` labels each option by position, so a score named `"1".."5"` reads one level high and a choice named `C, A, D, B` reads the wrong option. This PR takes the labels from the option names, in the question type, and applies the same rule to the example DiffusionGemma gateway.

No open PR fixes this. I searched open PRs for `systemone`, `structured_decisions`, `question_types`, `structured_server` and `score labels systemone`. #60465, #60713 and #60745 move the question types and keep positional labels. #60676 adds a `labels()` hook with positional `1..n` score labels for d1, which has the same clash; I will leave a note there once this lands. #61064, #58429 and #60288 also match `systemone`; #61064 adds a read without labels, and the other two change other parts of `structured_server.py`.

The reproducer from the issue on Qwen3-4B, main and then this PR:

```text
main                                          this PR
want level 2, got level 3, label_mass 1.000   want level 2, got level 2, label_mass 1.000
want level 3, got level 4, label_mass 1.000   want level 3, got level 3, label_mass 1.000
want level 4, got level 5, label_mass 1.000   want level 4, got level 4, label_mass 1.000
want level 5, got level 5, label_mass 0.000   want level 5, got level 5, label_mass 1.000
want choice B, got choice A, label_mass 1.000 want choice B, got choice B, label_mass 1.000
```

## Claims

- A score level named with its own distinct ASCII digit (`"1".."5"`, `"0".."4"`, `"1 star"`, `"5".."1"`) keeps that digit as its label, and the prompt shows the name alone.
- A scale with any other digit in its names (`"1".."10"`, `"-1"`, `"poor", "2", "3"`, non-ASCII digits) gets letter labels, and the prompt asks for a letter.
- Word-only scales keep today's labels and byte-identical prompts.
- A choice named with distinct single capital letters keeps its letters as labels. Other choices keep `A` to `Z` by position.
- The answer shape does not change: `score`, `legend` and `probabilities` stay 0-indexed by position.
- The example gateway gets a copy of the same rule. One test pins the labels of both paths.

## Validation

- `pytest tests/entrypoints/generate/structured_decisions/ -k "not e2e"` (CPU): 36 passed. One parametrized test pins one case per rule branch on both paths, through `build_question()` and the gateway's `parse_schema()`.
- `pytest tests/entrypoints/generate/structured_decisions/test_structured_decisions_e2e.py` (GPU, Qwen3-0.6B): 14 passed. The new `C, A, D, B` quiz case fails on main (`{'key': 'A'} != {'key': 'B'}`).
- Accuracy: `"1".."5"` on Qwen3-4B goes from +0.92 to -0.27 levels. Letter options out of order go from 18/24 to 24/24 on Qwen3-4B and from 6/24 to 24/24 on the DiffusionGemma gateway. Details below.
- Perf: +1-4 µs per question build; e2e p50 unchanged beyond a server-to-server offset seen equally on byte-identical prompts.

## Details

Root cause: `build_question()` took `qtype.label_set[: len(options)]` for every question, and the gateway's `parse_schema()` took `1..n` or `A..Z`. Nothing compared a label with the name next to it.

The rule lives in `QuestionType.labels()`, so every read strategy, autoregressive or DiffusionGemma, gets it without changes. The labels stay inside the existing label table (digits and `A` to `Z`), so the token ids the strategies resolve at startup cover them. A score's letter labels take their ids from the choice type's `label_set`.

The gateway copies the rule instead of importing it. It imports only the standard library, `pybase64`, `regex` and `transformers`; importing vLLM would tie the example to a vLLM version.

Limits: the built-in endpoint still allows at most 10 score levels. On Qwen3-4B, own-digit scales still read about 0.27 levels low, which I have not explained. Plus/minus grades (`A+`, `A`, `A-`) and choices that mix letters with other names (`["B", "Other"]` shows `A: B`) still clash with letter labels in the prompt; for the grades I measured no accuracy loss. The two paths render an own-digit level differently: the built-in prompt shows the name alone (`1`), the gateway keeps `1: 1`. The labels match, and the gateway accuracy above was measured with `1: 1`, so I left its prompt as it is.
