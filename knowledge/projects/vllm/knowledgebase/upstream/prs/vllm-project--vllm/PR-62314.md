# [Performance] Memoize waiting prefix cache hits across retries

[Upstream PR](https://github.com/vllm-project/vllm/pull/62314) · state: open · merged: False

## Original PR description

## Overview

Memoize long prefix-cache hits after failed KV admission so waiting requests can reuse them on the next scheduler step. This targets the repeated scheduler-thread lookup described in #61604.

## Claims

- Memoize only hits of at least four full blocks, within a narrow configuration: one full-attention group, no EAGLE block drop, and DCP/PCP = 1.
- Revalidate remembered blocks using the request hash, primary block hash, and physical block lifecycle version; resume normal lookup at the first invalid position.
- Store records with weak request keys and clear them on admission, free, and successful cache reset. Memoization does not pin blocks or change refcounts.

This is an independent implementation of the proposal in #61604. The issue author, @apex-mochen, described unpublished local work; no overlapping upstream PR was found. This change adds lifecycle-version validation and tests for ABA and duplicate physical blocks.

## Validation

- `tests/v1/core/test_prefix_caching.py`: 191 passed with `--noconftest`.
- Ruff check, Ruff format check, and `git diff --check` passed.
- CPU scheduler replay covered failed admissions, cache removals, memo reuse, preemption/cancellation, and cleanup; refcounts returned to zero.
- H100/Qwen3-0.6B measurements were collected against base commit `a2fb482732`, before rebasing this branch onto current `main`. They are exploratory and were not repeated after the rebase:
  - High-pressure synchronous: 5 pairs, throughput geometric mean +7.57%.
  - High-pressure asynchronous: 3 pairs, throughput geometric mean +0.33%, with a wide interval.
  - Default-capacity asynchronous: one screening pair, throughput -0.64%.
  - One instrumented diagnostic pair showed `schedule()` CPU time -25.5%; this is mechanism evidence, not an end-to-end serving gain.

The H100 runs used shared native extensions because `nvcc` was unavailable and the build/runtime versions were not fully matched. These results do not establish a general end-to-end improvement or rule out regressions.

## Details

When KV capacity prevents a waiting request from being admitted, `get_computed_blocks()` repeats the prefix walk on each scheduler step. This change records a sufficiently long hit after allocation failure. On retry, it validates each remembered block and resumes the normal lookup at the first invalid or not-yet-memoized block.

The fast path is restricted to the configuration above; other configurations retain the existing lookup. The four-block threshold avoids memo bookkeeping for short hits.

Related work such as #54625 changes waiting-request admission order; it does not avoid rescanning the prefix of a blocked request.

AI assistance was used for tests and PR preparation.
