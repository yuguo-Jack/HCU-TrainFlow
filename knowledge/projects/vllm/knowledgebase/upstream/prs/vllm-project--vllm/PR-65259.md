# [RL][Model Loader] Make expert scale and Mamba v2 sharded loaders copy_-only

[Upstream PR](https://github.com/vllm-project/vllm/pull/65259) · state: open · merged: False

## Original PR description



## Overview

Part of #64418 (L3): write per-tensor expert scales and the Mamba v2 sharded conv1d/bias parameters with `Tensor.copy_` instead of index assignment, so a load plan or tracer sees the write. No change to loaded bytes. Depends on nothing; does not overlap #55091 (see Details).

## Claims

- The five index-assignment writes in these loaders now use `Tensor.copy_`, so tracing `load_weights` classifies them as direct writes instead of falling back (`write via __setitem__`).
- Loaded values are byte-identical to the previous index assignment, including `(1,)`-shaped per-tensor scales written into 0-D slots.
- On the L3 measurement (M0 trace, TP=1), fallback names drop: Qwen3-30B-A3B ModelOpt static per-tensor FP8 (synthetic header) 36,864 -> 0; Qwen3.5-4B 48 -> 24.

## Details

Not a bug fix. `param[i] = x` already copied in place, so eager results are unchanged. The only difference is that it dispatches through `Tensor.__setitem__`, which a tracer that records `copy_` cannot see as a write; the loaded name then falls back to the slow path in a load plan.

`_load_single_value` also reshapes the source to the destination shape. Index assignment broadcast a `(1,)` checkpoint scale into a 0-D slot; `copy_` does not and would raise. The same function also loads the size-2 `weight_shape` (compressed-tensors), so `_to_scalar` is not reused. The "Assign directly" comment became "Copy directly".

`mamba_v2_sharded_weight_loader` previously assigned a slice; it now calls `copy_` on the same slice view. `kernels.yaml` adds `mamba_mixer2.py` to the Mamba kernels step's `source_file_dependencies` so the new test runs when the loader changes; the MoE test is picked up by the existing `kernels/moe` step.

#55091 changes only the shard computation inside `mamba_v2_sharded_weight_loader`; this PR only changes how the computed slice is written, so the two are independent and should rebase trivially.

Limitations: TP>1 not exercised end to end. The Qwen3-30B-A3B figure uses a synthetic header with real shapes, not a real checkpoint.

Thanks, the loader changes LGTM. Two asks:

1. Could you drop the two new test files and the `kernels.yaml` change? The tests compare against an inlined copy of the old loader, so they pass before and after (as noted in the description). They don't exercise the tracer, which is what L3 is about. That coverage comes from P2's per-family loopback test. The inlined Mamba shard math would also have to change in lockstep with #55091, and the `source_file_dependencies` entry triggers the GPU Mamba kernels step on every `mamba_mixer2.py` edit just to run a CPU-only test.
2. Could you also cover Inkling here? It's an RL family, and `load_expert_weight` in `vllm/models/inkling/{nvidia,amd}/moe.py` still writes the per-expert `_scale_2` / `_global_scale` scales, plus NVIDIA's per-channel `w2_weight_scale`, with `param.data[lids] = ...`. A plain `copy_` swap won't make these direct, because the index list, the `.float()` cast and the `expand` all make the name a fallback. They'd need a `narrow` + `copy_` per local expert in the checkpoint dtype. A checkpoint value shared by both w13 halves would become one `copy_` per half instead of an `expand`.
