# [Bugfix] FlashInfer `flashinfer_b12x` MoE backend runs W4A16 checkpoints as W4A4

[Upstream PR](https://github.com/vllm-project/vllm/pull/56535) · state: closed · merged: False

## Original PR description

## Overview

Add W4A16 (NVFP4 weights, BF16 activations) support to the FlashInfer B12x fused-MoE backend on SM12x, with a version guard for FlashInfer releases whose W4A16 kernel is broken. Not a duplicate: no open PR adds `quant_mode="w4a16"` plumbing for `FlashInferB12xExperts` (searched open PRs for "b12x"/"w4a16").

## Claims

- `--moe-backend flashinfer_b12x` now serves weight-only NVFP4 MoE checkpoints (e.g. `nvidia/Qwen3.6-35B-A3B-NVFP4`) via FlashInfer's `B12xMoEWrapper(quant_mode="w4a16")` with BF16 activations, instead of silently quantizing activations to FP4.
- Recovers ~2.4 GSM8K points over the previous in-kernel FP4-activation (W4A4) behavior and matches Marlin W4A16 accuracy (table below).
- Guards against FlashInfer 0.6.18–0.7.0.post1, whose W4A16 kernel rejects its own TC-decode fc2 tile at CUDA graph capture; affected versions get a clear startup error instead of a crash, with `VLLM_FLASHINFER_B12X_W4A16_IGNORE_BROKEN=1` as an escape hatch for patched builds.

## Validation

GSM8K, `nvidia/Qwen3.6-35B-A3B-NVFP4`, single GB10 (SM121), 1319 questions, 5-shot, greedy:

| MoE path | Activations | Samples | Mean |
|---|---|---|---|
| **b12x W4A16 (this PR)** | BF16 | 0.9136 ¹, 0.9158 ² | **0.915** |
| Marlin (weight-only) | BF16 | 0.9083, 0.9121, 0.9121 | 0.911 |
| b12x W4A4 (previous behavior) | FP4 | 0.8886, 0.8817, 0.8908, 0.9007 | 0.890 |

¹ FlashInfer 0.6.16.post3 · ² FlashInfer 0.7.0.post1 + forced-tile validation fix (see Details)

- Kernel test: `tests/kernels/moe/test_flashinfer_b12x_moe.py::test_flashinfer_b12x_moe_w4a16` — 36/36 on GB10. The reference now runs `torch_moe` on the exact dequantized NVFP4 weights (same methodology as the Marlin MoE tests), so quantization error cancels and the tolerance is `atol=4e-2, rtol=0` (was 1e-1/1e-1 against unquantized weights).
- Guard test: `tests/kernels/moe/test_b12x.py::test_b12x_w4a16_broken_flashinfer_version_guard` — 6/6, dependency-free.
- Guard behavior verified live: on stock FlashInfer 0.7.0.post1 the server fails at backend selection with an actionable message (previously: `ValueError: force_tile_config fc2 tile (tile_k=32, tile_n=512) does not fit problem N/K=2048/512 at moe_block_size=8` deep in graph capture).

Reproduce:
```bash
pytest tests/kernels/moe/test_flashinfer_b12x_moe.py -k w4a16
pytest -s tests/evals/gsm8k/test_gsm8k_correctness.py --config-list-file=configs/models-sm12x.txt
```

CI note: the kernel and eval tests require SM12x hardware (GB10 / RTX Pro 6000) plus FlashInfer with `B12xMoEWrapper`; they skip elsewhere. All validation above was run on GB10.

## Details

- **Why W4A16:** weight-only NVFP4 checkpoints have no activation scales; the previous b12x path dynamically quantized activations to FP4 anyway (synthesized unit scales), costing ~2.4 GSM8K points. W4A16 keeps activations BF16 and is numerically equivalent to Marlin stage-for-stage (same exact fp4→bf16 dequant, pre-MMA bf16 block scales, fp32 accumulation and split-k, fp32 top-k combine).
- **FlashInfer version guard:** FlashInfer 0.6.18–0.7.0.post1 (incl. the current pin) auto-select a TC-decode "ultra" fc2 tile with `tile_k=32`, then reject that same tile when re-pinning it across the torch custom-op boundary, because the forced-tile re-validation applies a generic `tile_k >= 64` search-space floor (`moe_w4a16_kernel.py:5507`/`:384` in 0.7.0.post1). Reported upstream with a fix (relax the floor for forced tiles): <FLASHINFER_ISSUE_LINK>. 0.6.16.post3 predates the re-pin code; note the current tree requires >= 0.7.0 for the GDN `backend=` kwarg, so on the current pin W4A16 stays guarded off until a fixed FlashInfer release (or a patched build + the escape hatch).
- **Eval configs:** the b12x and new Marlin GSM8K configs are identical (threshold 0.90, tolerance 0.03) so both backends are held to the same bar on SM12x. Accuracy alone cannot detect a silent W4A4 fallback (W4A4 samples can clear the floor); the structural fix is that a weight-only checkpoint now either runs W4A16 or fails loudly.
- AI assistance (Claude Code) was used for the test-reference rework, the version guard, and the numerics/root-cause investigation; all changes reviewed and validated by the submitter.
