# [Bugfix][Pooling] Fix HTTP 500 from max_tokens_per_doc when the query…

[Upstream PR](https://github.com/vllm-project/vllm/pull/61871) · state: closed · merged: True

## Original PR description



## Overview

**TL;DR:** On BERT-style cross-encoders, `/rerank`, `/score` and `LLM.score` return HTTP 500 when `max_tokens_per_doc` is set and the query alone fills the token limit. This falls back to the usual truncation in that case.

No existing issue or PR covers this. #60877 edits the same file but not this code.

## Claims

These requests no longer fail with HTTP 500:
- `truncate_prompt_tokens` below the query length plus special tokens, with or without an empty document. They now get the usual truncation, as without `max_tokens_per_doc`.
- A query longer than `max_model_len` without truncation. It now gets the usual 400 "maximum context length" error.

Requests that work today produce the same tokens.

## Validation

`vllm serve cross-encoder/ms-marco-MiniLM-L6-v2` on a T4. The query is a passage (as in "find similar"), with `max_tokens_per_doc=8`:

| Request | main | this PR |
|---|---|---|
| `truncate_prompt_tokens=16` | 500 | 200 |
| same, plus an empty document | 500 | 200 |
| 600-token query, no truncation | 500 | 400 "maximum context length" |

On main all three fail with `Truncation error: Sequence to truncate too short to respect the provided max_length`. With the fix, the relevant document still ranks first.

Tests, main → this PR:
- `tests/entrypoints/pooling/scoring/test_io_processor_unit.py`: 10 → 14 passed. The 4 new tests are listed below; 3 of them fail on main.
- `test_cross_encoder_online.py` 20/20, `test_cross_encoder_offline.py` 6/6, `tests/models/language/pooling/test_max_tokens_per_doc.py` 20/20, on both.

Also compared the preprocessing on main and this branch over 18,360 combinations of query and document length and both limits. Only the 2,250 that failed on main changed, and none of them goes over either limit.

## Details

**Root cause.** With `max_tokens_per_doc`, `get_score_prompt` encodes the pair with `truncation="only_second"`. That can only shorten the document, so the tokenizer raises when query + special tokens already reach `max_length`.

**Fix.** Use `only_second` only when the query leaves room for at least one document token. Otherwise the existing `truncation=True` arguments apply. The document is already cut to `max_tokens_per_doc` as text before encoding, so that limit still holds.

**Trade-off.** In the fallback the query is shortened. This can't be avoided when the query alone fills the limit, and it's what `truncate_prompt_tokens` already does without a document limit.

**New tests**, using a toy BERT-style tokenizer:
- When the query fits, only the document is cut. This passes on main too.
- When the query fills the limit, the usual truncation applies, for a normal and an empty document.
- A query that is too long without truncation gets the usual validation error.
