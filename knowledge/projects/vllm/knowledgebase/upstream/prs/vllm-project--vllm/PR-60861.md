# [Bugfix][Qwen4Exp] Carry and checkpoint the PLE short-conv state in align mode

[Upstream PR](https://github.com/vllm-project/vllm/pull/60861) · state: open · merged: False

## Original PR description

## Purpose

Fix the PLE (per-layer n-gram embedding) short-conv state handling of `qwen4_exp` (Qwen3.8-Flash-Next) in `mamba_cache_mode="align"`, so that a request resumed from a prefix hit delivered by a KV connector (OffloadingConnector loads, PD) reads a valid conv state, and so that the blocks the prefix cache and the offloading tiers store for the PLE group are actually written.

Part of the Qwen3.8-Flash-Next tracking issue #55922 (KV offload section). Same component as #59642 (PD side of the PLE state). Possibly related symptoms: #55357 (episodic 0% MTP acceptance with prefix caching on), #53912.

## Root cause

In align mode the PLE metadata builder (`short_conv_attn.py`) takes `block_table[:, 0]` of the align-gathered block table, i.e. the block of the last *scheduled* token, and uses it both to read the initial conv state and to write the final one. The Mamba/GDN backends instead receive `block_idx_last_computed_token` and read the resumed state from the block of the last *computed* token inside their kernels; the PLE conv kernel has no align support at all.

Two consequences:

1. A request resumed at, say, 6400 computed tokens with 3714 new tokens has its loaded state in block 1 but the PLE reads block 3, which was just allocated and never written. When that memory contains NaN the NaN appears in the PLE output of layer 1 with clean inputs and poisons the whole model; when it contains finite garbage the state is silently wrong.
2. Blocks that end at a 3200-token boundary crossed by a prefill chunk are never written, so the prefix cache and the offloading tiers store uninitialized memory for the PLE group. Inspecting the stored blocks showed NaN in the PLE slot of every block of that group.

GPU-local flows (chunked prefill, local prefix hits) were not affected because the KV cache manager copies the state forward for them; connector loads do not go through that path.

## Changes

- `short_conv_attn.py`: in align mode compute per row the carry source (block holding the state after the computed tokens) and destination (block the kernels address). Decode and spec rows go into persistent builder buffers padded with `NULL_BLOCK_ID`, like `spec_state_indices_tensor`, so full CUDA graph replay reads valid indices. Prefill rows also carry the block-table rows, `seq_lens` and `num_computed_tokens` needed to write boundary checkpoints.
- `ple_layer.py`: copy the conv state from source to destination before each conv (decode, spec and prefill paths); after a prefill, write the exact state at every block boundary the chunk crossed into the block ending there, and zero the speculative scratch columns so stored blocks never carry garbage.

No behavior change when `mamba_cache_mode != "align"`: the new metadata fields stay `None` and the layer code paths are skipped.

## Test Plan

Qwen3.8-Flash-Next-NVFP4 on DGX Spark (GB10, 119 GiB unified memory), `OffloadingConnector` with `TieringOffloadingSpec` (CPU tier + fs secondary tier), `mamba_cache_mode=align`, MTP k=3, prefix caching on, 8 GiB GPU KV cache. Load: 48 conversations of ~10.1k tokens (3200 shared system prompt + 6600 per-conversation context), 256 requests at concurrency 4, so most prefix hits come from the offloading tiers (6400-token external hits, ~49% of prompt tokens overall). A per-layer NaN probe was injected for the diagnostic runs.

## Test Result

Validated at TP=1 on two single-GPU hosts (GB10 and GB300). Not applicable to multi-node TP, for a reason unrelated to this fix (see below).

| run (GB10) | fix | external hits | NaN in model | MTP acceptance | stored PLE blocks |
|---|---|---|---|---|---|
| TP=2 baseline | no | 31% | yes, born in PLE layer 1 on resumed prefills | 2.2 -> 1.0 as hits start | NaN in PLE slot |
| TP=1 | no | 49% | none (uninitialized memory happened to be finite) | 2.13 | NaN in PLE slot |
| TP=1 | yes | 49% | none, 17,751 probe records | 2.19 | fully initialized, scratch zeroed |
| TP=1, tier on local NVMe | yes | 49% | none | 2.18 | fully initialized |
| GB300 Station, TP=1, CPU tier 32 GiB + NVMe tier | yes | 49% | none | 2.12 | fully initialized |
| GB300 Station, TP=1, CPU tier 4 GiB so hits are promoted from NVMe (1134 chunk hits from the fs tier) | yes | 49% | none | 2.08 | fully initialized |

The stored-block inspection is the direct evidence for the write side of the fix: before, the PLE slot of every stored block of that KV group contained uninitialized memory; after, it holds the boundary state with the three speculative columns zeroed. The TP=1-without-fix row shows why the bug can hide: the engine reads the wrong block either way, and only shows symptoms when that memory happens to hold NaN.

On a GB300 Station (256 GB HBM, 494 GB DRAM, local NVMe) the same load shows the expected gain with the fix in place: median TTFT 0.81 s for first occurrences vs 0.31 s for repeated conversations with hits served from the CPU tier, and 0.97 s vs 0.36 s when the CPU tier is shrunk to 4 GiB so that hits are promoted from the NVMe tier; MTP acceptance stays at 2.1 throughout. Before the fix the same hits made it collapse to 1.0.

Revalidated after rebasing on `main` (371745ebd6, after #58114 and #58997) with an image built from this branch, no file injection: GB300 Station, TP=1, MTP k=3, CPU tier 4 GiB + NVMe tier, 256 requests. No errors (the all-speculative decode path that the earlier rebase broke runs on every steady-state step), 1134 chunk hits served from the NVMe tier, 49% external prefix hits, MTP acceptance 2.12 on average (2.02-2.20 per window, flat from 0% to 49% hits), median TTFT 0.90 s first occurrence vs 0.40 s repeated. Note that on current `main` `--mamba-cache-mode` is deprecated and align mode follows `--enable-prefix-caching`, so this path is active by default whenever prefix caching is on.

TTFT on GB10 at TP=1 does not improve with offloading (10.5 s first occurrence vs 11.1 s repeat, both on NFS and on local NVMe) because the 99 GiB model leaves the node memory-starved (host<->GPU copies at 200 MB/s versus 56 GB/s on an idle node, prefill at ~750 tok/s); that is a platform limit of this model on a single GB10, not a property of the fix.

TP=2 on GB10 means multi-node TP (one GPU per node), and there the tiering manager runs in the scheduler process on rank 0's node and only sees that node's mmap region: only `_r0` files are ever written, rank 1 never creates the secondary tier, and on a load rank 1 copies a stale slot from its own `/dev/shm`. The result is wrong but finite KV on rank 1 (0 NaN in the layer probe, MTP acceptance collapses to 1.0 as soon as external hits start), with or without this fix and with or without #58413. That is the single-host assumption of #54415 (addressed by #46556); details posted there. A TP=2 validation of this fix needs a single host with two GPUs.

`spec_req_idx_cpu` is unbound in the all-speculative branch of `build()`.

After #58114 ("Reduce PLE metadata construction overhead", merged 2026-09-28), `spec_req_idx_cpu = spec_sequence_masks_cpu.nonzero(as_tuple=True)[0]` is assigned only in the mixed-batch `else:` branch of `short_conv_attn.py`. This PR's new call

```python
align_fields = self._ple_align_fields(
    m,
    decode_req_idx_cpu if num_decodes > 0 else None,
    prefill_req_idx_cpu if num_prefills > 0 else None,
    spec_req_idx_cpu if num_spec_decodes > 0 else None, ...
```

runs for every batch. In a pure speculative batch (`num_decodes == 0 and num_prefills == 0`, `num_spec_decodes > 0`, the normal steady state with MTP) the `else:` branch is skipped, so the conditional expression reads an unbound local and raises `UnboundLocalError` before `_ple_align_fields` can check the cache mode. It fires in every cache mode, not only align.

Reproduced on 2x DGX Spark (GB10), TP=2, nightly 77154ca6 + #59958 + this PR, Qwen3.8-Flash-Next NVFP4 with MTP: engine dies on the first all-spec decode step with

```
short_conv_attn.py", line 571, in build
UnboundLocalError: cannot access local variable 'spec_req_idx_cpu'
```

Fix (with it the engine boots and served our full eval runs): hoist the assignment above `if num_decodes == 0 and num_prefills == 0:`; see the diff below.
