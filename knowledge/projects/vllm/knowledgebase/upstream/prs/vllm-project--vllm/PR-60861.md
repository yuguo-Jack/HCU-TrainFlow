# [Bugfix][Qwen4Exp] Carry the PLE short-conv state from the last computed block in align mode

[Upstream PR](https://github.com/vllm-project/vllm/pull/60861) · state: closed · merged: False

## Original PR description

> **Relation to #61601.** #61601 fixed the *write* side of the PLE state in align mode: the boundary checkpoints of the PLE group are now written, so the blocks stored in the prefix cache, offloaded to CPU/disk or sent over PD hold the correct conv state. This PR fixes the *read* side, which is still broken on `main`: when a request resumes from a prefix hit delivered by a KV connector (OffloadingConnector load or PD transfer), the PLE reads its initial conv state from the wrong block and never sees the state that was loaded. The original version of this PR fixed both halves; after rebasing on #61601 only the read-side fix remains.

## Purpose

Fix the PLE (per-layer n-gram embedding) short-conv state handling of `qwen4_exp` (Qwen3.8-Flash-Next) in `mamba_cache_mode="align"`, so that a request resumed from a prefix hit delivered by a KV connector (OffloadingConnector loads, PD) reads the conv state that was loaded for it.

Part of the Qwen3.8-Flash-Next tracking issue #55922 (KV offload section). Same component as #59642 (PD side of the PLE state). Possibly related symptoms: #55357 (episodic 0% MTP acceptance with prefix caching on), #53912.

## Root cause

In align mode the PLE metadata builder (`short_conv_attn.py`) takes `block_table[:, 0]` of the align-gathered block table, i.e. the block of the last *scheduled* token, and uses it both to read the initial conv state and to write the final one. The Mamba/GDN backends instead receive `block_idx_last_computed_token` and read the resumed state from the block of the last *computed* token inside their kernels; the PLE conv kernel has no align support at all.

Two consequences:

1. A request resumed at, say, 6400 computed tokens with 3714 new tokens has its loaded state in block 1 but the PLE reads block 3, which was just allocated and never written. When that memory contains NaN the NaN appears in the PLE output of layer 1 with clean inputs and poisons the whole model; when it contains finite garbage the state is silently wrong.
2. Before #61601, blocks that end at a 3200-token boundary crossed by a prefill chunk were never written, so the prefix cache and the offloading tiers stored uninitialized memory for the PLE group (inspecting the stored blocks showed NaN in the PLE slot of every block of that group). #61601 fixes this one.

GPU-local flows (chunked prefill, local prefix hits) are not affected because the KV cache manager copies the state forward for them (`_apply_cow`); external loads only extend the block table (`allocate_external_computed_blocks`), so consequence 1 is still present on `main` after #61601.

## Changes

- `short_conv_attn.py`: in align mode compute per row the carry source (block holding the state after the computed tokens) and destination (block the kernels address). Decode and spec rows go into persistent builder buffers padded with `NULL_BLOCK_ID`, like `spec_state_indices_tensor`, so full CUDA graph replay reads valid indices.
- `ple_layer.py`: copy the conv state from source to destination before each conv (decode, spec and prefill paths), and after a prefill zero the speculative scratch columns of the addressed block so stored blocks never carry garbage. Boundary checkpoints are left to #61601's exporter.

No behavior change when `mamba_cache_mode != "align"`: the new metadata fields stay `None` and the layer code paths are skipped.

## Test Plan

Qwen3.8-Flash-Next-NVFP4 on DGX Spark (GB10, 119 GiB unified memory), `OffloadingConnector` with `TieringOffloadingSpec` (CPU tier + fs secondary tier), `mamba_cache_mode=align`, MTP k=3, prefix caching on, 8 GiB GPU KV cache. Load: 48 conversations of ~10.1k tokens (3200 shared system prompt + 6600 per-conversation context), 256 requests at concurrency 4, so most prefix hits come from the offloading tiers (6400-token external hits, ~49% of prompt tokens overall). A per-layer NaN probe was injected for the diagnostic runs.

On a GB300 Station (256 GB HBM, 494 GB DRAM, local NVMe) the same load shows the expected gain with the fix in place: median TTFT 0.81 s for first occurrences vs 0.31 s for repeated conversations with hits served from the CPU tier, and 0.97 s vs 0.36 s when the CPU tier is shrunk to 4 GiB so that hits are promoted from the NVMe tier; MTP acceptance stays at 2.1 throughout. Before the fix the same hits made it collapse to 1.0.

Closing this as superseded by #61601. Summary for anyone landing here from the PLE state corruption:

- **The bug.** With `mamba_cache_mode="align"`, Qwen3.8-Flash-Next requests resumed from a prefix hit delivered by a KV connector (OffloadingConnector loads, PD transfers) ran on a corrupted PLE short-conv state. The PLE checkpoint blocks at the cacheable boundaries were never written, so the prefix cache and the offloading tiers stored uninitialized memory for the PLE group, and the resumed request started from it. With NaN in that memory, MTP acceptance collapsed from ~2.2 to 1.0 as soon as external hits started (measured on GB10 and GB300). This PR identified it and fixed it on October 9 by writing the boundary checkpoints and carrying the state into the block the kernel reads.
- **Why it is no longer needed.** #61601 (internal prefill checkpoints for the PLE short conv, merged October 20) makes the PLE export its conv window at the checkpoint, which writes exactly the blocks that were left uninitialized. The read side was already covered on `main`: in align mode MRV2's `preprocess_state` (`model_states/mamba_hybrid.py`) copies every Mamba state, including the PLE short conv via `short_conv_state_copy_func`, from the block of the last computed token to the block the kernels address before the forward. So the carry in this PR duplicates an existing copy.
- **Verification on `main` (9d4192aaa1) without this PR**, GB300 Station, Qwen3.8-Flash-Next-NVFP4, TP=1, MTP k=3, OffloadingConnector with CPU + NVMe tiers:
  - offloading lab, 256 requests up to 49% external prefix hits: no errors, MTP acceptance flat at 2.11 (2.12 with this PR);
  - state probe on every resumed prefill (chunked prefill and loads from the tier): the initial conv state the PLE kernel reads matches the state after the computed tokens bit for bit (48/48 rows, max abs diff 0, no NaN, no zeroed blocks), with or without the carry.
- **One open point.** The #61601 description says the PLE checkpoints are only exported where #60050's are (FlashInfer GDN prefill, prefix caching on); our runs used the FlashInfer GDN prefill. I have not checked whether the PLE boundary blocks are written when those checkpoints are off; if they are not, the corruption described above would come back in that configuration, and I will open a separate issue if a probe shows it.

Thanks @EagleClaw89 for the review that caught the all-spec `UnboundLocalError`.
