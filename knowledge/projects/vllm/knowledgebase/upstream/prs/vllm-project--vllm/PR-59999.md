# [Bugfix] FlashInfer: declare only KV layouts it can address

[Upstream PR](https://github.com/vllm-project/vllm/pull/59999) · state: closed · merged: True

## Original PR description

## Purpose

Fixes #59998. On non-SM100 GPUs, declare the five KV cache layouts FlashInfer can address, so layout resolution can no longer pick LHBNC.

### User case

1. FlashInfer on SM80/SM90/SM120 with `VLLM_KV_CACHE_LAYOUT=LHBNC`.
2. `FlashInferBackend.supported_kv_cache_layouts()` returns `None` there, so `resolve_kv_cache_layout` accepts LHBNC.
3. FlashInfer only takes NHD/HND pages; `get_flashinfer_layout_string` has no LHBNC entry.
4. The engine dies at startup on `AssertionError: KV cache layout LHBNC has no FlashInfer equivalent` (A100, Llama-3-8B) instead of rejecting the layout at resolution.

The fix returns the default preference order without LHBNC (LBNHC, LBHNC, BLNHC, BLHNC, BHLNC) instead of `None`.

Unchanged: the default layout (still LBNHC), the SM100 set, connector preferences (LBHNC and BLHNC stay valid), and every layout FlashInfer could already run.

Not a duplicate: no open issue or PR covers this. #46329 and #56550 add an SM120 branch to the same function but keep the `None` fallback. Related: #55431, #55312.

Hi @hyunnnchoi, thanks for the contribution.

LGTM. Declaring a set instead of `None` also gives FlashInfer a vote in `get_supported_kv_cache_layouts` when it shares a worker with another declaring backend. Against every backend that declares a set at this head (b12x, QSA, the DSv4 indexer, Dots3, kpool tail, sparse MLA SM90, flex/TurboQuant/HPC), the resolved layout comes out the same, so the only behaviour change is the earlier error for LHBNC.

`envs.py` says LHBNC "hoists the head dim outside the block dim; backends must opt in via AttentionBackend.supported_kv_cache_layouts()", but `_DEFAULT_LAYOUT_PREFERENCE` still lists LHBNC, so every backend that returns `None` gets it without opting in. That gap is the common root of this bug and #60005. If opt-in is the intended contract, dropping LHBNC from the default list and having the backends that do handle it (FlashAttention and Triton, per your A100 runs) declare it would fix both in one place and cover the next backend that returns `None`. If it isn't, the `envs.py` comment is stale. Fine to land this as the FlashInfer-side fix either way, but worth settling which one is intended.

@vadiklyutiy Yes, both only show up when LHBNC is forced, but they're different bugs. This PR is about FlashInfer.
