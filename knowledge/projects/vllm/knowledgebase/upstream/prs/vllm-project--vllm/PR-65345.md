# [Security] Use weights_only=True for EPLB all_gather_object collectives

[Upstream PR](https://github.com/vllm-project/vllm/pull/65345) · state: open · merged: False

## Original PR description

## Purpose

Harden the EPLB object collectives against untrusted deserialization.

`NixlEplbCommunicator` and `SymmMemEplbCommunicator` exchange agent and expert-weight metadata through `torch.distributed.all_gather_object` (`vllm/distributed/eplb/eplb_communicator.py`), which deserializes peer-contributed data with pickle and no `weights_only` guard. On elastic-EP / fault-tolerant deployments these collectives run over rebuilt groups whose membership and coordination store are unauthenticated, so they are the remaining ungated pickle sinks in the distributed layer — every other deserialization path in vLLM is already guarded (`weights_only=True` for prompt_embeds/adapters; `VLLM_ALLOW_INSECURE_SERIALIZATION` for the RLHF ipc-handles and serial_utils paths).

Discussed privately in GHSA-v8vv-h2j8-g9mx; agreed there to land this as hardening.

## Change

Add `weights_only=True` to the three EPLB `all_gather_object` call sites (`_init_remote_agents`, `_exchange_remote_send_meta`, and the SymmMem NVLink check). The gathered payloads are plain data — nixl agent-metadata bytes and `dict[tuple[int, int], tuple[int, int, int]]` of ints — so the restricted loader accepts them unchanged.

## Why this is safe / no functional change

- `weights_only=True` restricts only the load side; senders still pickle normally. The payloads contain no custom classes or `__reduce__` objects, so the restricted unpickler loads them identically.
- `torch==2.14.0` (already required by this path) supports `weights_only` on the object collectives; default is `False`.

## Scope note

This intentionally does **not** change the `StatelessProcessGroup` object methods (`send_obj`/`recv_obj`/`broadcast_obj`). Those legitimately carry Python dataclasses (e.g. shm `Handle`, weight-transfer envelopes, pynccl ids), so `weights_only=True` would reject valid payloads. Hardening them requires a safe-globals allowlist and is left as separate work.

## Testing

Ran on CPU with `torch==2.14.0` (the pinned version):

- `ruff-check` and `ruff-format` (pinned pre-commit rev v0.14.0) on the changed file: pass.
- Functional + security regression, single-process gloo, CPU:
  - PASS regression: bytes + dict-of-int-tuples + list[int] round-trip under `weights_only=True`
  - PASS security: malicious `__reduce__` rejected -> `UnpicklingError`

The regression case all-gathers the exact EPLB payload types and asserts they are returned unchanged. The security case confirms a malicious `__reduce__` object is rejected rather than executed. Instantiating `NixlEplbCommunicator` itself requires nixl + a GPU, so the patched collective was additionally confirmed on a GPU box during the advisory investigation. No model-output behavior changes, so no evals required.
