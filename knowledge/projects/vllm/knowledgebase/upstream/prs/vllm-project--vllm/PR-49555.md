# [Feature][AuxOutput] Replay ordinary raw indexer selections

[Upstream PR](https://github.com/vllm-project/vllm/pull/49555) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Return ordinary sparse-attention TopK selections through the existing AuxOutput
SHM lifecycle. This is the raw-int32 foundation for #47280; Profile/Codec model
formats are separated into #62915 and host-memory admission into #63535.

## Claims

- Capture ordinary raw selections from DeepSeek V3.2 / GLM-5.2, the shared MLA
  path and Dots3 NOTE. Preserve actual source-layer order, TopK order and padding.
- Capture DeepSeek V4 C4A's raw compressed-cache indices without expanding token
  coordinates or adding a Profile; HCA/SWA layers add no source planes.
- Support Indexer-only and combined routed-expert output using existing accepted
  cursors, prefix restoration, async copying, SHM hashes and teardown.
- Allocate the persistent Indexer capture buffer through main's merged #63237
  profiling path, before the profiling forward and automatic KV sizing. Clone
  each step's active rows for asynchronous transfer.
- Return `indexer_topk` through Python output/APIs and Rust engine IPC plus the
  Rust token `/inference/v1/generate` path. Rust Indexer OpenAI delivery is not
  included. Raw layout is `[tokens, sources, topk]`, int32.

## Details

`GPUModelRunner.profile_run()` creates the Connector, whose constructor allocates
and binds each enabled capturer. Indexer's persistent device buffer therefore
enters automatic KV memory profiling outside the weights pool. Per-step snapshots
clone the active rows for asynchronous transfer. `snapshot()` returns the cloned Tensor
directly; the single-field `IndexerSnapshot` wrapper is removed. Real KV initialization reuses the Connector and calls
`initialize_output_storage()` with the resolved layout on the output TP rank.
Main's fallback remains when profiling was skipped; explicit KV byte budgets
remain manual. There is no separate GPUWorker load-model capture hook or
`initialize_capturers()` phase. Startup Plan schema follows main (version 2).

Capture remains immediately after actual logical TopK scoring and before an
attention backend can overwrite shared buffers. Explicit source capabilities,
non-contiguous layer-to-column mapping, MTP/shared-consumer exclusion and existing
forced-scoring/skip conditions remain. No Python forward hooks or validity bitmap
are introduced. The existing Indexer close/unbind and graph-before-buffer teardown
are retained. V4 backbone replay disables the unscored short-context shortcut;
MTP keeps its original shortcut. ROCm V4 monokernel bypasses the common capture
entry and is explicitly rejected with Indexer Replay. Duplicate persistent
Indexer allocation is removed. This update does not change R3 snapshot behavior.

Both artifacts share row-count/range extraction with independent prompt offsets.
Current-step output slices reuse the separately owned typed CPU arrays; packed
rows still feed SHM storage. History restoration uses common unpacking that keeps
combined artifacts contiguous and independent, and store-backed Indexer output
writable. NumPy views retain the CPU allocation until the consumer releases them.
Storage layout calculation returns the per-token shape and dtype separately from
SHM initialization. No latency improvement is claimed without measurement.
Generic SHM buffering/publication/materialization lives in `artifacts.py`; packed
record widths determine default KV-derived arena capacity. Host probing, admission
and its environment override/tests are reviewed separately in #63535, based on
main, so this PR can be reviewed independently of that policy.

MRV2 generate and prefix caching are required; existing PP/DCP/PCP, adaptive
verification and remote-PD restrictions remain. V4.1, GLM-5.3 KPool, Qwen QSA,
Step5 and HY-V4 Profile formats belong to #62915; MiniMax-M3 has no adapter.
See `docs/training/indexer_replay.md` for the output format and limits.

This updates the existing #49555 rather than creating a competing PR; #63237 is
reused from main, and the two split PRs cover distinct admission/model contracts.
AI assistance was used. The human submitter remains responsible for reviewing
all changed lines and completing relevant validation before requesting review.

#### Parallel configuration

- **TP4 (DeepSeek-V4, 0.90)** doubles KV capacity to 8,692,342 tokens, which needs **916.1 GiB** of SHM. On a 700 GiB allocation the admission check refuses it and reports `Maximum Supported Blocks: 63488` with `--num-gpu-blocks-override`. This is the expected behavior: more parallelism means more KV blocks, hence a larger arena, and the check catches it before allocation.
- **GLM-5.1 requires TP8** on 140 GiB devices (88 GiB of weights per rank); TP4 cannot load the model, so the failing axis there is the KV planner (0.85), not replay.

#### Host-memory admission check

- Passes when the host is not binding: GLM at 0.90 reports `maximum supported=21368` blocks against `4766` in use.
- Refuses when it is: DS-V4 TP4 as above.
- Prefix-cache hit returns identical prompt rows: in a 4,096-token request the first 4,096 rows are byte-identical and only the 7 generated rows differ (diagnosed on a small DSA proxy with the same code path; the full-size runs report `identical=false` only because the comparison includes those generated rows). Those 7 rows are independent decode steps with random weights, so they are not a replay-correctness signal.
- Two gaps were found and fixed:
  1. the suggestion could name a block count that cannot serve `--max-model-len`. With a 50 GiB arena the check used to suggest `--num-gpu-blocks-override 1312` (83,968 tokens) for a 202,752-token model, and following it failed again in the KV planner. It now raises `No feasible AuxOutput configuration: this host budget supports at most N tokens ... but max_model_len=M` (`e504477b`).
  2. when the scheduler does not enforce its memory request through a cgroup controller (this cluster's `memory.max` is `max`), the check only saw the host's ~1.95 TiB. A first revision probed `SLURM_MEM_PER_NODE`, which couples vLLM to one scheduler; `81d09a837` replaces it with the scheduler-agnostic `VLLM_AUX_OUTPUT_HOST_MEMORY_BYTES` override — a job wrapper exports its own allocation and startup takes `min(available RAM, cgroup headroom, override)`.

### Indexer snapshots: clone per step instead of a pre-allocated pool (H20 validation)

**Commit tested:** `a42e0a21fa` (this branch; the branch has since advanced with a parallel merge of main and a host-row refactor, which the numbers below do not cover).
**Environment:** SGP H20e (H20-3e, 141 GB), Slurm jobs on nodes 01/02/05. Compiled extensions are the wheel for the merge-base `08e3f26458` (`vllm-0.33.0rc1.dev458+g08e3f2645`) extracted and overlaid with this branch's Python tree, run through the shared venv. Dummy weights at full size.

#### What changed

`IndexerCapturer` no longer pre-allocates `max_concurrent_batches` full `(max_num_batched_tokens, layers, topk)` buffers. `snapshot()` now clones only the forwarded rows:

```python
return IndexerSnapshot(self.device_buffer[:num_rows].clone())
```

`release_snapshot()`, the free-slot list and the connector's `indexer_snapshot_slot` are gone; the tensor lives as long as the `PendingAuxOutput` that reads it. Stream ordering is unchanged: the clone is enqueued on the forward stream, and the async D2H still waits on that stream (`copy_stream.wait_stream(main_stream)` before `enqueue_cpu_copy`).

#### Memory: KV capacity freed at init

`max_concurrent_batches=2`, `max_num_batched_tokens=8192`; both variants measured on the same job.

| Model | Variant | Available KV | KV tokens | Change |
|---|---|---|---|---|
| DS-V4 TP2, util 0.85 | pool | 40.39 GiB | 4,209,967 | — |
| | **clone** | **41.05 GiB** | **4,278,361** | **+0.66 GiB / +68,394 (+1.6%)** |
| GLM-5.1 TP8, util 0.90 | pool | 18.12 GiB | 316,416 (1.56×) | — |
| | **clone** | **24.22 GiB** | **423,167 (2.09×)** | **+6.10 GiB / +106,751 (+33.7%)** |

The DS-V4 delta matches the analytic pool size (`2*8192*21*512*4 = 0.656 GiB`). The GLM delta is smaller than the analytic `9.74 GiB` because the pool is allocated only on the output TP rank and KV capacity is the minimum across ranks.

At runtime the clone costs the actual batch only: a 4K GLM request drops free memory by ~2.4 GiB instead of the 10.5 GB pool worst case. With `C=2` full 8192-token batches the worst case returns to the pool worst case, so a fully saturated batch still needs the same headroom — this is the budget change to keep in mind (no new admission logic in this change).

#### Runtime

| Scenario | Result |
|---|---|
| DP2 × TP2 (4 GPUs, `VLLM_DP_RANK` processes) | rank 0 `[1024, 21, 512]`, rank 1 `[2048, 21, 512]`, int32, distinct checksums |
| Two concurrent requests in one TP2 engine | shapes/rows per prompt, no cross-contamination; a repeated run (prefix-cache hit) returns byte-identical rows |
| Old pool code, same concurrent scenario | `AssertionError: Indexer snapshots were not consumed in order` |

That last row is the failure mode the change removes: two in-flight batches plus a new step exceeded the fixed slot count.

#### Rust and hooks

- `cargo fmt --all -- --check` → exit 0 after formatting `client.rs` / `generate.rs` (see `a42e0a21fa`).
- `cargo nextest run -p vllm-llm --all-features --locked` → `33 tests run: 33 passed, 0 skipped`.
- `run-precommit.sh` on the branch commit → exit 0; DCO check `ok 472c97bc97`.

#### Not verified

- **CUDA graph path.** With the current tree, engine init fails inside `profile_cudagraph_memory()` → `sparse_attn_indexer` (`max(c.max_local_total_seq_lens for c in prefill_metadata.chunks)` with empty chunks). It reproduces with the merge-base wheel and happens before any snapshot is created, so it is unrelated to this change, but it means all runtime runs above used `enforce_eager=True`. `VLLM_MEMORY_PROFILER_ESTIMATE_CUDAGRAPHS=0` did not avoid it.
- Real-weight numerical equality, MTP, and preemption recovery.
- TP/DP coverage is the two configurations above, not a matrix.
