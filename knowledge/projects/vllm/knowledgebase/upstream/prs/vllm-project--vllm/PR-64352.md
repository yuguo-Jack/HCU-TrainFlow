# [Model Loader] Direct reload: reset MoE expert padding at begin

[Upstream PR](https://github.com/vllm-project/vllm/pull/64352) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

At the start of a direct weight reload (`VLLM_RELOAD_MODE=direct`, #64336), reset MoE expert padding to its cold-start value, so that post-load processing reruns over the same bytes as a cold start. Part of the direct weight reload work (#54477).

MoE expert parameters are often larger than the checkpoint tensors loaded into them: DeepEP rounds the hidden size up, MXFP4 / TRT-LLM / AITER backends round the intermediate size, and block-aligned FP8 TP pads shards. Loaders copy only the checkpoint part. On a direct reload the padding then holds the previous post-processed bytes, which post-load processing processes again. After a `load_format=dummy` cold start (the usual RL setup) it holds random values.

## Claims

- **gpt-oss-20b (TP2, MXFP4), direct reload through IPC weight transfer:** every tensor is bit-identical to a fresh start, both after 3 same-weight syncs and after a dummy start plus one sync. On main, 168 expert tensors differ after every sync and drift from one sync to the next. After a dummy start, 288 differ and GSM8K drops about 2 points.
- Cold start and layerwise reload are unchanged.
- No loader changes: whether to fill is decided from `moe_config` when the checkpoint layout is recorded at cold start, so it also covers dummy and other cold starts that skip loaders, and the load plan (#64418) that bypasses them.

## Details

**Design.**
- `RoutedExperts.has_padding()` is true if `moe_config` shows the hidden size or the per-partition intermediate size rounded up past its unpadded value, or block-aligned TP sharding.
- `padding_fill_params()` returns the parameters the quant method's `create_weights` registered, minus per-expert scalars. A parameter is filled if `ndim >= 3` or it has shape `(E, n)` with `n > 2`. So per-tensor and static input scales, which may be absent from the checkpoint, are kept.
- `record_checkpoint_layout` stores `(module, name, value)` at cold start, before post-load processing. Some post-load processing pads only the runtime copy and writes the padded size back into `moe_config`, so the decision must not be made later.
- `begin_direct_reload` looks up each name after the view-back, skips parameters post-load processing has dropped, and fills the rest whole with `padding_value`. Loaders then overwrite every checkpoint region.

**Requirement.** The fill erases the checkpoint region too, so every checkpoint tensor loaded into these parameters must be resent on every update. The direct delivery contract in `direct.py` says so; the completeness check (F2 in #54477) will enforce it.

**Padding value.** Weights and every scale default to 0. Only the ones-initialised scales of the target models carry `padding_value=1`: the fp8 block scales (DeepSeek-V4.1 FP8 experts, GLM-5.3, Qwen3.8) and Quark OCP_MX's uint8 scales (Inkling on AMD; 0x01). MXFP4 (DeepSeek-V4.1, gpt-oss) and NVFP4 scales are created as zeros or empty and need nothing. Other MoE methods (compressed-tensors, other Quark schemes) are left unchanged: their padded scales refill with 0 rather than 1, which only multiplies zero padding weights. Weights created with `torch.empty` had uninitialised padding at cold start; they get 0 here.

**`moe_config` is the source today, not the only possible one.** A layer padded some other way extends `has_padding()` or implements `padding_fill_params()` and reuses the same fill.

**Not changed.** Layerwise reload, the block-aligned TP loader fill, and `_zero_intermediate_padding` (cold start still needs it, since those weights are `torch.empty`).

**History.** This replaces this PR's earlier design, where loaders recorded the padding regions on every load and `fill_padding` wrote them before post-load processing. That design worked with layerwise reload and partial updates. Under the decision to require full updates and to drop layerwise reload (#54477), the fill at begin is much smaller and needs no loader changes. The streamed gpt-oss MXFP4 TP split moved to #65353, and Inkling AMD's padding (#64690) is covered by this fill.

Thanks, this is the right place for the fill. A few suggestions to make it smaller, plus a measurement.

**1. Explicit padding value instead of `_initial_padding_value`.** The byte scan guesses the initial value from the bytes after `create_weights`. Proposal: default the padding value to 0, and have the few methods that create scales with `torch.ones` set `padding_value=1` on the parameter explicitly. That removes the heuristic (including the 0x01 edge case) and the scan over every expert parameter.

**2. **On your four points** (all done locally, not pushed yet):

   - fp8 block scales;
   - compressed-tensors MoE w8a8 fp8/int8, wna16, w4a8 int8/fp8 and w4a16 flydsl;
   - Quark W8A8 fp8/int8, W4A8 fp8 and OCP_MX (uint8, back to 0x01).

   This also fixes IPC weight-cache starts, where the byte scan saw meta tensors and returned 0 for everything.
2. **Storage lookup instead of `param=`: I'd keep the plumbing.** Every call site already has the parameter, and the storage scan is slower: 1.7–3.8 µs per call against about 0.3 µs for the current lookup. That's roughly 3–8 ms more per DeepSeek-V4.1-Flash layer, not less. It can also pick the wrong parameter when two share a storage, and it can't tell a scratch tensor from an unregistered parameter, which drops the warning you asked for.
3. **MXFP4 TP split: moved** to #65353 with its test.
4. **Cost: agreed it's the marking.** It's now recorded once per (parameter, split) per load and checked before any padding view is built. CPU micro-benchmark per loader call: main 7.8 µs, previous head 14.4 µs, now 10.2 µs. So about 5 ms per layer at your shapes instead of about 18.

**Proposal: drop this PR and fill at begin in a later PR.** Almost all of the machinery here (recording in every loader, `param=` through four loaders and gpt-oss, the per-load records and their cost) exists for two reasons:
- **Layerwise reload:** it puts back the kernel tensors of layers an update didn't send, so it may only fill padding where this load actually left some.
- **Partial updates:** we don't assume an update resends everything.

Once every update must resend every checkpoint tensor (F2's completeness check) and the worker refuses to serve while an update is pending (F17), direct reload doesn't need to know where padding is:
- **begin:** fill each parameter of a padded MoE layer, whole, with its `padding_value` (0 by default);
- **load:** the loaders overwrite every data region, because everything is resent, so what they leave is exactly the padding, already at its cold-start value;
- **finish:** post-processing reruns over bytes that match a cold start.

That is about 15 lines in direct `begin` plus the `padding_value` attributes:
- The loaders stay as on main.
- There's no per-load cost, only a memset of the MoE weights, a few ms per update.
- It works for load-plan direct writes (#64418) too, since it doesn't depend on any loader running.

It should be limited to padded MoE layers, not every tensor, because some parameters keep meaningful values that no checkpoint tensor overwrites: KV-scale defaults, and the FP8 sentinels in #64717.

**The cost is that layerwise reload stays as on main**, so the gpt-oss-20b layerwise fix in this PR (96 → 0 padded parameters differing after an NCCL sync) would wait until layerwise is removed (F7). The fill at begin also depends on F2 and F17 landing first: without them, an update that leaves out a padded MoE layer would zero it silently.

So I'm inclined to close this PR and do the fill at begin in a later PR, where breaking layerwise is acceptable, after F2/F17 and together with or after F7. If you think the layerwise fix is worth having before then, I can push the reworked version above instead. What do you think?
