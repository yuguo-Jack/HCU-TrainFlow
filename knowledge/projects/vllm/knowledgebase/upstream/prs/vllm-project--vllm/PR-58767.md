# [Bugfix][Distributed] MergedColumnParallelLinear TP Rank Sync, Scale Parameter Sharding, and Bounded Multi-Threaded Loader

[Upstream PR](https://github.com/vllm-project/vllm/pull/58767) · state: open · merged: False

## Original PR description

## Purpose

Addresses correctness and memory stability issues in core distributed parameter sharding and multi-threaded safetensors checkpoint loading:

1. **`MergedColumnParallelLinear` TP desync on replicated layers**:
   - *Problem*: Instantiating `MergedColumnParallelLinear(..., disable_tp=True)` set `self.tp_rank = 0`, but child parameters (`weight`, `weight_scale`, `bias`) retained the global worker rank. On multi-GPU deployments with replicated linear layers, worker ranks 1+ attempted out-of-bounds slicing during `load_merged_column_weight`, crashing during initialization with `RuntimeError: start (...) + length (...) exceeds dimension size (...)` or `IndexError: start out of range` (from `loaded_weight.narrow(...)` slicing past shard bounds).
   - *Fix*: Synchronize `tp_rank = 0` and `tp_size = 1` across child parameters in `__init__` when `disable_tp=True`.

2. **Block quantization scale parameter sharding**:
   - *Problem*: In `MergedColumnParallelLinear.weight_loader_v2`, `adjust_block_scale_shard` was only invoked if `isinstance(param, BlockQuantScaleParameter)`. When quantized layers used `GroupQuantScaleParameter` or standard parameters for `weight_scale`, the scale tensor was sliced using the unadjusted full weight `shard_size` rather than the block-scaled dimension. This triggered `RuntimeError: start (...) + length (...) exceeds dimension size (...)` or `IndexError: start out of range` during `param.load_merged_column_weight`.
   - *Fix*: Extend block scale shard adjustment in `weight_loader_v2` to recognize `GroupQuantScaleParameter` and `getattr(self, "weight_scale", None)`.

3. **Unbounded task submission in multi-threaded safetensors loader**:
   - *Problem*: `multi_thread_safetensors_weights_iterator` passed a generator of `executor.submit` tasks to `concurrent.futures.as_completed`. Because `as_completed` internally converts its input to a `set`, all checkpoint shards (48–131 files) were submitted simultaneously. Completed worker threads retained loaded shard dictionaries in memory until earlier shards were consumed, causing host memory spikes and risking out-of-memory worker termination (`SIGKILL`) during multi-rank startup on shared nodes.
   - *Fix*: Implement a bounded sliding window of `max_workers + 1` shards using `collections.deque`, strictly bounding in-flight submitted tasks and peak staging memory.
