# [Perf][DSpark] lossless improve DSpark throughput by W2 matrix topk pruned

[Upstream PR](https://github.com/vllm-project/vllm/pull/56694) · state: open · merged: False

## Original PR description

## Purpose

Reduce DSpark draft latency with opt-in candidate pruning of the Markov projection. At each position, candidates are the union of the top-k backbone logits and the top-m precomputed Markov-bias entries. The sequential walk evaluates and samples within that union. `markov_topk=0` keeps the full-vocabulary path.

This changes the draft proposal distribution. Correct probabilistic rejection sampling must use exactly the truncated distribution used to draw the draft tokens; draft quality and acceptance length can change. Target-distribution preservation therefore depends on sampler/cache correctness and is not established by throughput measurements alone.

## Implementation and compatibility

- Use a fused Triton walk over base-logit and optional static Markov candidates.
- Cache the candidate proposal logits for probabilistic rejection sampling.
- Preserve draft-to-target vocabulary mapping.
- Keep pruning disabled by default; unsupported quantized or sharded Markov heads use the dense path.

- Use the existing platform-aware top-k dispatcher so importing DSpark does not unconditionally require FlashInfer.
- Use the maximum score for overlapping candidate IDs, matching token-keyed Gumbel sampling; synchronize cache clearing before updates.
- Fall back to dense drafting when online acceptance estimation or draft watermarking is enabled. Trained confidence heads remain supported.
- Exclude padded W2 rows before building static candidates.
- Narrow the optional speculative config before resolving the candidate budget.
- Extend the existing DSpark test suites for greedy chains, probabilistic sampling/cache agreement, reduced vocabularies, CUDA graph cache reuse, static-candidate construction, and dense fallbacks.

Platform-aware top-k uses deterministic sorted selection. GPU correctness, accuracy, and performance validation of the final implementation remain outstanding.

## Prior benchmark results

The author previously reported throughput measurements on 8 Hopper GPUs with Qwen3-4B. For base top-k=32 and Markov top-m=32, the reported improvements were approximately 5.51% on C-Eval, 4.99% on GSM8K, 5.18% on Math500, 6.41% on HumanEval, and 5.86% on MBPP. The later SPEED measurements at temperature=0 reported 4.2% on 16K and 5.3% on 8K.

These are historical measurements from before the correctness and compatibility fixes described above. Gains are configuration-dependent: some settings regress, so this PR does not claim a speedup for every top-k/top-m combination. The existing tables report throughput and acceptance metrics, not task accuracy.

No statistically significant speedup is established. An exploratory two-sided exact label-permutation diagnostic, using the absolute log ratio of medians and all 20 allocations of three versus three trials, gives the following p-values:

| Workload | c | Steady throughput p | AIPerf whole-run throughput p |
| --- | ---: | ---: | ---: |
| 8K | 1 | 0.6 | 0.6 |
| 8K | 4 | 1.0 | 0.4 |
| 8K | 8 | 0.4 | 0.4 |
| 16K | 1 | 0.4 | 0.2 |
| 16K | 4 | 1.0 | 1.0 |
| 16K | 8 | 0.4 | 0.2 |

These are exploratory diagnostics, not confirmatory tests. Modes ran in sequential blocks, with one server startup per mode within each sweep. The three repeats therefore do not measure startup-to-startup variation, the blocks do not justify exchangeability, and duration-bounded runs consume different prompt prefixes. Several observed ranges overlap. A stronger speedup claim needs matched workloads and randomized, interleaved comparisons across independent startups.

Hi @tomasruizt, glad to update some info

**Q1: "Reuse dspark_draft_topk for both candidate sets"**
Already done. The current PR uses a single dspark_draft_topk=32 to control both the base top-k and the Markov top-k. There is no separate markov_bias_topk parameter.

**Q2: "Adding markov top-k almost restores the AL of full DSpark. Is this already driving most of the gains? Perhaps we can drop all other optimizations."**
Yes. Markov candidates are the primary source of gain. On our GSM8K benchmark with Qwen3-4B at c=8:

| dense, full vocab     | 3.59   |              
| base-only k=32       | 3.11    | −0.48          
| base+Markov k=32 | 3.55   | −0.04          

Markov candidates recover 0.44/0.48 = 91.7% of the AL lost to top-k truncation. Also, GSM8K dense full vocab accept len is 5.96, and base+Markov k=32 accept len is 5.94

This suggests most of the gap comes from missing good candidates that the Markov bias can identify, and the remaining optimizations (Triton fusion, separate proposal cache, separate config) are not necessary.

The current PR has already dropped all other optimizations, keeping only the precomputed candidate ID table. The C-online ablation confirms  switching to online computation yields identical acceptance rates (31.6%), so the quality gain is from Markov candidates themselves, not from  precomputation.

**Q3: "Fusing the loop with Triton — how much improvement does this actually drive?"**
Not included and not needed. The Python for loop overhead (~0.8 ms per step for 8 iterations) is hidden by CUDA async dispatch, not worth the complexity of a custom Triton kernel.


**Q4: "Same for pre-computation — how much does it actually drive?"**
Precomputation does not affect correctness, only speed. 
Ablation results:

│ precomputed table       │ 737 tok/s │ 4151 tok/s  │ 31.6%           
│ compute online             │ 666 tok/s │ 4016 tok/s │ 31.6%           

Precomputation saves 9.7% at c=1 and 3.2% at c=64.
Cost: the table is vocab_size × k × 8 = 151,936 × 32 × 8 ≈ 37 MB of GPU memory. Runtime GPU memory usage is unchanged. First startup incurs ~20 s to build the table; subsequent starts have no extra overhead.
Conclusion: precomputation is worth keeping. A 9.7% speedup for 37 MB of memory is a good trade-off.
