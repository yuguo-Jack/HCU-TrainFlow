# [Bugfix][ROCm] Refuse ROCM_AITER_FA shuffle-layout configs it cannot decode

[Upstream PR](https://github.com/vllm-project/vllm/pull/63678) · state: open · merged: False

## Original PR description


_Requested by **Tun Jian**_



## Overview

Stacked on #63675 (the ROCM_AITER_FA test suite). Only the last commit is new; please review it after #63675 lands. Part of the attention backend test standard RFC (https://github.com/vllm-project/vllm/issues/63640).

**Before:** With `VLLM_ROCM_SHUFFLE_KV_CACHE_LAYOUT=1`, ROCM_AITER_FA accepted sliding-window, sink, soft-cap, ALiBi and multi-token-decode configs. It then asserted, or returned wrong results, at the first decode. Muse Spark, Gemma 4 and GPT-OSS crashed this way.

**After:** Those configs are refused up front with a clear reason. A sliding window or sinks are rejected by the selector, so another backend is picked. Soft cap or ALiBi raise in the impl, and spec decode raises in the builder.

This deletes the `shuffle-unsupported-features` entry from `known_defects.py`. Its 6 unit + 1 engine tests were strict xfails on the tests-only PR and now pass.

## Validation

MI350X (gfx950), `vllm/vllm-openai-rocm:nightly` (AITER 0.1.26), full unit suite including the nightly matrix:

- Unit: 3796 passed, 72 xfailed, 0 unexpected.
- Engine: `test_shuffle_layout_refuses_sliding_window_model` passes.

## Details

`paged_attention_common` has no window, sink, soft cap or ALiBi input and takes one query token per request. The backend now says so in `validate_configuration`, `AiterFlashAttentionImpl.__init__` and the metadata builder.


## Related upstream PRs

These open PRs add support for configs that this PR refuses under the shuffle layout:

- #46847 (reger-men) adds window-correct shuffled fp8 decode for sliding-window layers, using a new AITER kernel (`paged_attention_decode_shuffle_swa`), and fixes the SWA extend context gather.
- #45144 (waqahmed-amd-fi) makes MTP spec decode (multi-token decode) work with fp8 KV and the shuffle layout by calling `pa_fwd_asm` directly.

They are not equivalent: this PR rejects what today's kernels cannot decode, while those PRs make some of it decodable. If either lands, the matching guard here should be lifted and the suite's shuffle declarations updated, so the suite then checks the new path instead of the rejection.
