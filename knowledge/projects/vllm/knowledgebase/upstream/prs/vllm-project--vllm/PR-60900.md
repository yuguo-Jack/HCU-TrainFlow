# [Bugfix][MoE] Decouple DeepEP low-latency dispatch size from max_num_batched_tokens

[Upstream PR](https://github.com/vllm-project/vllm/pull/60900) · state: open · merged: False

## Original PR description



## Overview

`--all2all-backend deepep_low_latency` crashes at startup whenever `--max-num-batched-tokens` is set above a few hundred. This happens with an ordinary prefill-friendly config such as `--max-num-batched-tokens 4096`. The cause is that the per-rank dispatch capacity of the DeepEP LL buffers is taken directly from `max_num_batched_tokens`. This PR decouples the two: the LL buffers are sized for a fixed number of tokens per rank, and larger forward passes are split into several dispatch rounds that stay in sync across the DP ranks.

Related: #57894 / #57915 (draft). That PR adds a fail-fast error for the same 32 GiB limit, but the config still cannot run. This PR makes the config run.

## Claims

- DP8xEP8 `deepep_low_latency` with `--max-num-batched-tokens 4096` now starts and serves correctly with no `NVSHMEM_*` env tuning. Before this PR it crashed in `deep_ep.Buffer.__init__`.
- The memory used by the LL RDMA buffer and the batched-expert workspaces no longer grows with `max_num_batched_tokens`.
- A clear `ValueError` is raised when a user-set `NVSHMEM_QP_DEPTH` is too small. Previously this was a bare `AssertionError` deep inside DeepEP.
- No behavior change for the default LL config: when `max_num_batched_tokens` is not set it already defaults to 256, so no chunking happens and the buffer size is unchanged.
- No behavior change for other all2all backends. Chunking only triggers when a rank's batch exceeds `prepare_finalize.max_num_tokens_per_rank()`. Other prepare/finalize implementations report `max_num_batched_tokens` or `None` there, so they never trigger it.

## Details

**Root cause.** `maybe_make_prepare_finalize` passes `moe.max_num_tokens` (= `max_num_batched_tokens`) as `num_max_dispatch_tokens_per_rank` to DeepEP LL. DeepEP has two hard limits on that value:

1. **RDMA buffer limit.** `Buffer.get_low_latency_rdma_size_hint` grows linearly at about `num_experts * (2*hidden + hidden/32)` bytes per token. For this model on 8 ranks that is about 9.58 MB per token:

   | tokens/rank | size hint |
   |---|---|
   | 256 | 2.45 GB |
   | 512 | 4.91 GB |
   | 3584 | 34.35 GB |
   | 4096 | 39.26 GB |

   DeepEP asserts `num_rdma_bytes / 16 < INT_MAX`, which caps the buffer at about 34.36 GB (32 GiB). So any value above 3584 crashes.
2. **QP depth.** `deep_ep` asserts `NVSHMEM_QP_DEPTH >= 2 * (num_max_dispatch_tokens_per_rank + 1)`. `NVSHMEM_QP_DEPTH` defaults to 1024, so even `max_num_batched_tokens=512` crashes unless the user sets `NVSHMEM_QP_DEPTH`.

The same value also sizes the batched-expert workspaces, `(local_experts, tokens * num_ranks, max(N, K))`. So even when the limits are not hit, a large `max_num_batched_tokens` spends GPU memory that the KV cache needs. With `--max-num-batched-tokens 4096` and `gpu_memory_utilization=0.92`, the KV cache left for this model was:

| LL capacity (tokens/rank) | KV cache memory | Result |
|---|---|---|
| 512 | 3.2 GiB | fails the `max_num_seqs=64` check |
| 256 | 6.8 GiB | OK |

**Fix.**
- `DeepEPLLAll2AllManager.max_dispatch_tokens_per_rank` picks the LL capacity:
  - By default it is `min(max_num_batched_tokens, 256)`. 256 is the existing `SchedulerConfig.DEFAULT_MAX_NUM_BATCHED_TOKENS_FOR_BATCHED_DP`.
  - If the user sets `NVSHMEM_QP_DEPTH`, it is `min(max_num_batched_tokens, NVSHMEM_QP_DEPTH // 2 - 1)`, so users can opt into larger rounds.
  - It is then halved until the RDMA size hint fits DeepEP's limit.
  - The user's `NVSHMEM_QP_DEPTH` is read once and cached. `deep_ep.Buffer.__init__` writes its default (1024) back into the environment, so re-reading it would make later MoE layers size their buffers differently.
- `FusedMoEKernelModularImpl.apply` splits the batch into rounds of `prepare_finalize.max_num_tokens_per_rank()` tokens.
  - Dispatch and combine are collectives, so every EP rank must run the same number of rounds. The round count is derived from `dp_metadata` (`num_tokens_across_dp_cpu`, or `local_sizes` under sequence parallelism).
  - A rank that runs out of tokens processes a 1-token dummy round and discards its output. This mirrors the old `forward_impl_chunked`.
  - Shared experts run once over the full input, in the first round.

**Tradeoffs / limitations.**
- Prefill-sized batches now take several LL rounds. In the example above, a 4096-token batch takes 16 rounds per layer. LL kernels are tuned for decode, so prefill-heavy workloads should still prefer `deepep_high_throughput` or the default all2all backends.
- Deferred finalize (`UnfinalizedMoEOutput`, produced only by the FlashInfer deferred-GEMM2 path) is asserted to not occur in the chunked path.
- Not exercised end to end: DBO/ubatching combined with chunking.
