# [ROCm] Harden DeepSeek-V4/V4.1 sparse prefill against zero-query-token chunks

[Upstream PR](https://github.com/vllm-project/vllm/pull/55695) · state: closed · merged: False

## Original PR description

## Overview

On ROCm, DeepSeek-V4 and V4.1 `_forward_prefill()` breaks on a prefill chunk with zero query tokens, so this PR computes each chunk's query bounds first and skips the chunk before any gather, combine or attention is launched. On current `main` I found no route that forms such a chunk, so this is hardening, not a fix for a live crash.

Such a chunk can form because `split_decodes_and_prefills()` counts padded request slots after the last prefill as prefills, and `get_prefill_chunk_plan()` can put those slots in a chunk of their own. On V4, `combine_topk_swa_indices()` then raises `cannot reshape tensor of 0 elements into shape [0, -1]`; on V4.1 the error comes earlier, at the `kv` view.

## Claims

- A chunk with no query rows launches nothing on V4 or V4.1. Chunks with query rows run unchanged, so outputs cannot change.
- The crash was real on v0.26.0 (DSv4, TP4), where breakable-PIECEWISE graphs padded `num_reqs` (#48822). #49302 removed that padding, and DP attention, DP2×TP2, TP4+MTP, eager and CPU KV offload never put an empty row in the prefill range on current `main`. The guard keeps the loop correct if padding reaches an eager prefill again.
- #51489 fixes the same condition in the shared planner; the two changes compose, and this PR can be closed in its favour.

## Validation

- New regression test, for V4 and V4.1: `pytest tests/kernels/attention/test_rocm_triton_attn_dsv4.py -k padding_only`. It runs the real planner on one prefill followed by five padded slots, with the kernel entry points recorded. It fails on `main`, where V4 launches the gathers, combine and attention on the empty chunk and V4.1 raises `cannot reshape tensor of 0 elements into shape [2, 0, -1]`, and passes with this PR.
- With #49302 reverted on a recent build, DSv4-Flash at TP4 under load crashes in 14 s without the guard and runs 10 min clean with it.
- On MI325X, replaying the chunk loop against the real planner and `combine_topk_swa_indices()` crashes 21 of 42 batch shapes unpatched and none patched, so the mechanism is not gfx950-specific. End to end on `main` it never triggers.
- The existing DSv4 ROCm suites are unchanged: 134 passed, 39 skipped. MI325X serving throughput and GSM8K (30-shot, concurrency 128: 0.929 base, 0.927 patched) are at parity; launch command and full numbers are in [this comment](https://github.com/vllm-project/vllm/pull/55695#issuecomment-5583539299).

Tested on 2×MI325X (gfx942), on current `main` (`a69402aaa8`) after a full ROCm rebuild.

**Summary:** MI325X reproduces the failure mechanism. It is not triggerable end-to-end in the configurations I can run here — the crash was originally hit on a `0.28.1rc1` build. I'd take this as a defensive fix.

### Launch command

```bash
VLLM_USE_V2_MODEL_RUNNER=1 VLLM_USE_BREAKABLE_CUDAGRAPH=1 VLLM_ROCM_USE_AITER=1 \
vllm serve DeepSeek-V4-Flash \
  -tp 2 --max-model-len 6144 --kv-cache-dtype fp8 --no-enable-prefix-caching
```

`-tp 2` for the 2 GPUs on this box. `VLLM_USE_V2_MODEL_RUNNER=1` is needed because ROCm defaults DSv4 to the V1 runner while the crash path is in the V2 runner. `VLLM_USE_BREAKABLE_CUDAGRAPH=1` is needed on `main` — it is no longer auto-enabled, and without it startup aborts with `piecewise CUDA graphs (cudagraph_mode=FULL_AND_PIECEWISE) unavailable, model is not torch-compiled and breakable CUDA graph is off`. Prefix caching is off so repeated benchmark runs don't reuse prompts. Both sides reported an identical `GPU KV cache size: 382,902 tokens`.

### Reproduction on gfx942

Replaying the `_forward_prefill()` chunk loop against the real `split_decodes_and_prefills()` and the real `combine_topk_swa_indices()` Triton launch, over the 42 batch shapes from the description:

| | |
|---|---|
| unpatched crashes | 21 / 42 |
| patched crashes | 0 |
| non-empty chunk execution differences | 0 |

Same error (`cannot reshape tensor of 0 elements into shape [0, -1]`) and same trigger (`pad >= PREFILL_CHUNK_SIZE`, independent of `num_speculative_tokens`). So the mechanism is not gfx950-specific.

### Not reachable end-to-end here

I instrumented `_forward_prefill()` to count zero-query-length slots in the prefill range and got zero hits across full 500-request runs, both plain and with `--speculative-config '{"method":"mtp","num_speculative_tokens":1}'` (500/500 successful, no crash).

Request padding only happens for FULL-cudagraph batches; this backend is `AttentionCGSupport.UNIFORM_BATCH`, so mixed batches always go PIECEWISE (`num_reqs=None`), and the FULL graphs that do pad require `max_query_len <= decode_query_len <= decode_threshold`, which forces `num_prefills == 0`. Those conditions are mutually exclusive. All three facts are unchanged on current `main`.

I could not run the reported DSpark config: my checkpoint lacks `dspark_noise_token_id`, so it refuses to start.

### End-to-end perf — parity

`bench serve`, random 1024 in / 128 out, 500 prompts:

| | base | patched |
|---|---|---|
| c64 req/s | 6.14 | 6.18 |
| c64 total tok/s | 7076 | 7123 |
| c64 mean TPOT (ms) | 60.46 | 60.34 |
| c128 req/s (4 runs) | 7.72 / 7.68 / 7.71 / 7.72 | 7.65 / 7.71 / 7.72 / 7.70 |

No gain and none expected: the guard only skips padding-only chunks, and those never occur here, so the dropped gathers and sparse-attention launch are never actually saved.

### GSM8K, 30-shot, concurrency 128

500 questions, `temperature 0`, `max_tokens 256`, 3 runs each, 0 invalid responses throughout:

| | run 1 | run 2 | run 3 | mean |
|---|---|---|---|---|
| base | 0.928 | 0.922 | 0.936 | 0.929 |
| patched | 0.928 | 0.922 | 0.930 | 0.927 |

Parity. 16 greedy prompts (half long enough to chunk the prefill) also produced bit-identical completions patched vs unpatched, which is what you'd expect since the guard is a no-op whenever no chunk is empty.
