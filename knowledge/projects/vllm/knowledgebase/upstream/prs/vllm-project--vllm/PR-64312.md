# [Quantization] Support CSF-compressed NVFP4 block scales in ModelOpt

[Upstream PR](https://github.com/vllm-project/vllm/pull/64312) · state: closed · merged: True

## Original PR description

## Overview

Lets vLLM load ModelOpt checkpoints whose routed-expert NVFP4 block scales are CSF-compressed. Each layer names its format in `quantized_layers[...]["weight_scale_encoding"]`, and two formats ship today: `csf` in `nvidia/Qwen3.8-Flash-Next-FP4-Local` and `csf_32x2_v1` in `nvidia/GLM-5.3-Flash-FP4-Local`. This started from #60646 (draft since Oct 8); its two commits are still in the history, and the `csf` decoder comes from it.

## Claims

- `ModelOptNvFp4FusedMoE` takes the CSF streams as its own params, decodes each scale matrix once all of its streams have arrived, and loads it through the scale param's own weight loader. TP and EP sharding, the MoE backends and the kernels see the same E4M3 scales as with an uncompressed checkpoint.
- Each encoding is one entry in `layers/quantization/utils/csf_scales.py`: its stream names and its decoder. The ModelOpt config renames `<proj>.weight_scale.<stream>` to the method's params, so model loaders don't change.
- A stream param sets `weight_loader_target` to the scale it fills. `track_weights_loading` counts the scale as loaded through it, and layerwise reload leaves its loader unwrapped so the scale's own wrapper buffers and counts the load.
- Both decoders are lossless against NVIDIA's reference decoders.
- An unknown encoding, or an encoding on a non-NVFP4 layer, fails when the config is built. An encoding on any layer other than routed experts, including one shard of a fused linear, fails in `get_quant_method`. Malformed streams and matrices with missing streams raise instead of loading wrong bytes.

## Validation

On CPU, main (`dc45a5f552`) plus this PR:

```text
pytest tests/model_executor/model_loader/test_csf_scales.py  # 13 passed
pytest tests/model_executor/model_loader/test_registry.py    # 9 passed
pytest tests/model_executor/model_loader/test_reload.py      # 64 passed, 33 skipped, 1 failed, 2 errors
pytest tests/quantization/test_modelopt.py                   # 109 passed, 2 skipped, 2 failed, 3 errors
pre-commit run --files <changed files>                       # passed
```

The failures and errors in `test_reload.py` and `test_modelopt.py` start an engine and need a GPU, which was hidden for this run; they fail the same way without this PR. The new `test_registry.py` and `test_reload.py` cases and the stream test in `test_csf_scales.py` fail without the `weight_loader_target` handling.

`csf`: all 73,728 scale matrices in a local copy of Qwen3.8-Flash-Next-FP4-Local decode byte-identical to `decode_csf_slab_scales` in NVIDIA's reference implementation, with up to 13,793 exceptions in one matrix and no stream pair split across shards. The whole decode takes 25.3 s in one process.

`csf_32x2_v1`: 378 GLM-5.3-Flash-FP4-Local matrices fetched from the Hub (every CSF layer, three experts each, gate/up/down) decode byte-identical to `decode_csf_scales` in the same reference.

End to end on two SM80 GPUs with TP=2, running this PR's Python against the compiled ops of nightly `0.32.1rc1.dev467+g444d69110`: Qwen3.8-Flash-Next-FP4-Local (`--language-model-only`) loads with `enable_weights_track` and no missing weights, holds 96 decoded scale params per rank, and answers five greedy prompts correctly. `reload_weights` then processes all 48 CSF MoE layers on each rank with no delayed or failed loads, and leaves the scale checksums and the greedy outputs unchanged.

## Details

The decode happens at load time rather than in `process_weights_after_loading` because the compressed streams can't be TP-sliced: holding them until then would keep every layer's compressed scales on each rank. The streams add up to 4.0 GB in Qwen3.8 and 10.3 GB in GLM-5.3, summed from the safetensors headers. The stream params are empty, so they never reach kernels or EPLB.

The decoders run in numpy rather than torch: every small torch op goes through the intra-op thread pool, which the loader sizes to CPUs per local worker, and that made the `csf` decode about 1.7x slower in #60646's form.

Both checkpoints keep weights in a `tensors/` subdirectory, which the default loader doesn't search yet: all 21 Qwen3.8 shards, and the 214 attention and indexer tensors of GLM-5.3. Neither loads in full from the Hub until that lookup lands in #64739.

Not a duplicate: #63908 decodes CSF inside the Qwen4Exp NVIDIA model file. Searching open PRs for "CSF", "weight_scale_encoding" and "nvfp4_csf" turns up nothing else.

Like #60646, this doesn't keep the scales compressed in GPU memory; that needs kernels that read compressed scales.

- cnsiva · comment · 2026-10-31T17:35:49Z · [source](https://github.com/vllm-project/vllm/pull/64312#issuecomment-6546833620)

Independent-implementation datapoint, in case it helps: I had a model-local CSF decoder for this exact checkpoint in #63908 (now closed as superseded by this PR). A few notes from validating it against `nvidia/Qwen3.8-Flash-Next-FP4-Local`:

- The checkpoint carries **147,456 CSF stream tensors** — all on routed experts (`mlp.experts.*` `gate/up/down_proj.weight_scale.nvfp4_csf_{fixed,exceptions}`); the `linear_attn.*` NVFP4 scales are already plain `weight_scale`. So the routed-experts-only scope here matches what the checkpoint actually needs today.
- My decoder (`base + nibble codes`, low nibble first, 24-bit position / 8-bit value exception scatter) is byte-identical in algorithm to `_decode_csf`; I diffed decoded scale bytes against the uncompressed reference on real layers and got an exact match.
- Two edge cases worth having in the tests (both covered by my 3 unit tests, happy to port): `exceptions.numel() == 0` (checkpoints with no fixups), and the `float8_e4m3fn` reinterp view must be taken on the **uint8** decoded buffer (a cast would silently reinterpret rather than re-view — the bug my PR title was about).

Also 👍 the numpy-vs-torch choice for the decode itself — at ~74K scale pairs the per-op thread-pool sync dominates; I saw that too when the torch-op version ran multi-threaded loading.
