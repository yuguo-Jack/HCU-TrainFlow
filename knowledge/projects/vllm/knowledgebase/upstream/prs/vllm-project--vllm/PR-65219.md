# [Bugfix][NIXL] Reject NVFP4 KV cache when the prefill block size is smaller than decode's

[Upstream PR](https://github.com/vllm-project/vllm/pull/65219) · state: open · merged: False

## Original PR description

## Overview

Fixes #65218. With NVFP4 KV cache, NIXL P/D returns garbage without any error when the prefill block size is smaller than the decode block size, or when `enable_permute_local_kv` permutes the layout on receive. This PR rejects both setups at handshake, the way #61865 does for heterogeneous TP.

## Claims

- NVFP4 KV with a smaller prefill block size, or with a receive-side layout permute, now fails at handshake with:
  `RuntimeError: NIXL does not support NVFP4 KV cache with different block sizes (local 64, remote 16) or KV cache layouts (local LBHNC, remote LBHNC) on prefill and decode. Use the same block size and KV cache layout on both.`
- NVFP4 with matching block sizes and layouts, and every other KV dtype, behave as before.
- The NIXL compatibility page lists the restriction.

## Validation

## Details

**Flow**, with prefill block size 16 and decode block size 64:

1. On the first request from this prefill, decode runs the NIXL handshake. `_validate_remote_agent_handshake` checks layouts, TP and block sizes. The new check fires here.
2. Decode reads four 16-token prefill pages into each 64-token local block, end to end (`_map_block_ids_for_block_size_ratio`).
3. When the read finishes, `get_transfer_results` calls `post_process_device_kv_on_receive(..., convert=True)`. It regroups the four small pages into one big page (`kv_postprocess_blksize_on_receive`) and zeroes the token tail that wasn't transferred.

**Root cause.** Decode stitches four 16-token pages into one 64-token page in step 3, and that code assumes each token has its own row of bytes. NVFP4 pages don't work that way: all the 4-bit data comes first, then all the scales (`_nvfp4_kv_views` in `flashinfer.py`). So the stitching mixes data and scales. On a small CPU test, 72 of 144 bytes come out wrong for NVFP4, while the same test on bf16 is correct. The layout permute behind `enable_permute_local_kv` has the same problem.

**The fix.** A check in `_validate_remote_agent_handshake` rejects NVFP4 whenever that stitching or permute would run (`block_size_ratio > 1 or enable_permute_local_kv`). I kept it separate from the #61865 TP check, since #64475 and #64812 both change that code.

**Why not support it?** That needs data and scales regrouped separately for both layouts, which is a bigger change. Happy to do it as a follow-up if you'd prefer, possibly on top of #64812.

Tested on H100 only. Blackwell uses the same page layout, so it should be affected too.
