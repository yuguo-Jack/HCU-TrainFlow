# [Perf][Model] Stack K2-Horizon MoVA value experts once after loading

[Upstream PR](https://github.com/vllm-project/vllm/pull/62952) · state: open · merged: False

## Original PR description

## Overview

Stack the K2-Horizon MoVA value experts once after loading instead of on every forward. `K2HorizonMoVAAttention.compute_mova_v_sparse` ran `torch.stack` over all value-expert weights in each step, which copies 335 MB per MoVA layer per step for `IFM/K2-Horizon-MoVA-36B-A4B`: ~15 GB per decoded token.

Related: #56637 also removes this copy, as part of a larger refactor (see *Duplicate work* below).

## Claims

- Decode on a DGX Spark (GB10, 273 GB/s): **5.6 → 19.6 tok/s** single stream with `IFM/K2-Horizon-MoVA-36B-A4B-FP8` (vLLM 0.32.0, `vllm/vllm-openai:v0.32.0`).
- One MoVA layer, decode (1 token): **3.11 ms → 0.14 ms**, with bitwise-identical output.
- Real loader + `torch.compile` + FULL CUDA graphs (6-layer dummy-weight run): **21.3 → 13.0 ms per token**. The CUDA graph pool also no longer holds the per-forward stack outputs (1.33 GiB → ~0 for 3 MoVA layers).
- No extra weight memory: the experts become views of the stacked tensor.
- Outputs don't change: `fused_mova_impl` receives the same tensor values as before.

## Details

**Root cause.** `compute_mova_v_sparse` needs the value experts as one `[num_experts, kv_size, hidden_size]` tensor for `fused_mova_impl`, but the experts are 64 separate `ColumnParallelLinear` weights. `torch.stack(...)` in the forward therefore copied all of them on every step, including decode: about 2 × 335 MB of memory traffic per MoVA layer. On a bandwidth-limited GPU like the GB10 that is most of a decode step.

**Fix.** `K2HorizonForCausalLM.process_weights_after_loading()` (the model-level post-load hook, which runs after per-layer quant processing) calls `K2HorizonMoVAAttention.stack_v_experts()`. That method:

1. stacks the expert weights once into the non-persistent buffer `v_experts_weight`;
2. points every expert's `weight.data` at its slice, so there is no second copy, and writes to the expert weights reach the buffer in place;
3. returns early when the experts are already views of the buffer, so a second call keeps the storage that CUDA graphs captured.

`compute_mova_v_sparse` reads the buffer and keeps the old per-forward stack only when the buffer is unset.

**Kept on the old path:**
- Quantized value experts (not `UnquantizedLinearMethod`). The current code doesn't support them anyway; #56637 adds GPTQ.
- CPU-offloaded experts (CPU device or UVA). Stacking them would move them back to GPU memory, or, without UVA, leave the buffer on CPU.

**Compatibility checked:**
- TP: each rank stacks its local shards, the same tensor the forward stacked before.
- PP: missing layers have no MoVA modules.
- Kernel-format `reload_weights` (`param.copy_`) and direct `load_weights` calls write into the views, so the buffer stays current and at the same address.
- Layerwise (checkpoint-format) reload puts the original buffer and expert parameters back: same storage, experts still views. It does not update the value experts, but that is true on main too. The `v_experts` branch of `load_weights` writes through `default_weight_loader` rather than the param's (wrapped) loader, so the new values go to the meta placeholders. Checked on v0.32.0 with and without this PR. Fixing that means reworking the TP slicing of that branch, which #56637 does.
- Weight-cache IPC loader: the hook runs again in the engine. In zero-copy mode the experts still alias the buffer, so it returns early. In copy mode it re-stacks once.

**Duplicate work.** I searched open PRs and issues for `k2_horizon`, `K2-Horizon`, `MoVA` and `v_experts`. #56637 (open since 2026-09-12, no maintainer review yet) replaces the expert list with a fused `MergedColumnParallelLinear` to support GPTQ INT4 and fix TP loading. That removes this copy as a side effect. This PR is a separate ~45-line fix for the BF16 checkpoints people run today:
- If #56637 merges first, this PR is obsolete and I'll close it.
- If this one merges first, #56637 drops these lines when it rebases.

Independent numbers on a different card, for reviewers.

Setup: RTX PRO 6000 Blackwell Max-Q (sm_120), vLLM 0.32.0, `IFM/K2-Horizon-MoVA-36B-A4B-FP8`, TP1, 256-token prompt, 128 greedy tokens, `ignore_eos`. Compile cache disabled so the stock graph is not reused.

| batch | stock tok/s | stacked once tok/s | speedup |
|---|---|---|---|
| 1 | 30.2 | 81.9 | 2.71x |
| 8 | 213.6 | 493.1 | 2.31x |
| 32 | 644.8 | 1136.8 | 1.76x |

Greedy output is identical in both arms (same hash over all generated token ids).

In an eager-mode profile of the stock build at batch 1, `aten::cat`/`stack` was 55% of GPU time. After the change it drops out of the top kernels.
