## Overview

Prevent native KV offloading from reusing persisted blocks when the same checkpoint is restarted with a different model configuration. Fixes #56311.

## Claims

- Snapshot the full HF configuration, computation dtype, construction-time `max_model_len`, and runtime quantization overrides before loading or memory auto-fit can change them.
- Include that snapshot in FS/object-store namespaces and the P2P handshake, including native offloading nested inside `MultiConnector`.
- Cover runtime quantization, multimodal settings and real offloading fingerprints in regression tests; document the conservative compatibility boundary.

## Details

Checkpoint names and token hashes do not capture all inputs that affect KV. RoPE changes can alter cached keys with the same weights and tokens; Phi3 can select LongRoPE factors using construction-time `max_model_len`. The snapshot is frozen before model loading or memory auto-fit, and includes the full HF config and runtime quantization overrides.

The hash is conservative: output-only fields and context limits can cause cold FS/OBJ namespaces or reject P2P connections even when their KV would otherwise match. `_commit_hash`, `_name_or_path` and `transformers_version` are excluded recursively. Matching fingerprints assume unchanged weights and a compatible runtime; they do not verify checkpoint contents or every kernel choice.

The docs cover cold FS/OBJ migration, retained legacy data without fallback, and rejection of mismatched nonempty P2P fingerprints. Existing acceptance of an absent peer fingerprint is unchanged. KVCR is outside this contract. #55907 separates physical layouts; this change separates model configurations even when layouts match. The earlier overlap check found no other open PR referring to #56311.

Yeah, that's fair. I went with the full text config to avoid missing model-specific inputs with a RoPE-only allowlist, but it isn't a complete KV compatibility check.

Two cases I was working from:

- In [#56311](https://github.com/vllm-project/vllm/issues/56311), changing only RoPE scaling with the checkpoint held fixed reused 1,168 tokens from the old cache. The first generated token differed from a clean run of the **same target configuration**. The scripts and results are [here](https://gist.github.com/JiataiWang/3efe0744be7bddf118edf928e0e9f763#file-reproduction-md).
- [Phi3 LongRoPE](https://github.com/vllm-project/vllm/blob/2c88fb131c7ae0be01907cd8c276911db5e7aad4/vllm/model_executor/layers/rotary_embedding/phi3_long_rope_scaled_rope.py#L51-L55) can select long factors based on `max_model_len` at construction. That's why I included that separately from the HF config. Computation `dtype` is also separate from the KV storage dtype already in the namespace.

I excluded `_name_or_path`, `_commit_hash` and `transformers_version` as source path/revision and serialization version tags, assuming unchanged weights and a compatible runtime. That assumption needs to be explicit; excluding those tags doesn't make different revisions or library versions compatible.

So yes, this patch can cause extra misses for output-only config changes, while still missing runtime quantization overrides outside the text config. Matching fingerprints only cover the recorded inputs, not general KV equivalence.

How about starting with an explicit field list: RoPE/position settings, computation dtype and construction-time `max_model_len`, then checking which runtime overrides need to join them? That should give us a better basis for deciding whether keeping the full text config is worth the extra misses.
