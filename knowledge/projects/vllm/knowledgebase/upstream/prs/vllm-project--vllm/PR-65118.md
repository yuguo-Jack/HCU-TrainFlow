# [Bugfix][Mistral] Keep skip_special_tokens for MistralTokenizer in Responses / legacy parser path

[Upstream PR](https://github.com/vllm-project/vllm/pull/65118) · state: closed · merged: True

## Original PR description



## Overview

Stop `MistralParser.adjust_request` from forcing `skip_special_tokens=False` when the tokenizer is a `MistralTokenizer`. This fixes corrupted non-ASCII output (`�`) from `/v1/responses` with tools for Tekken models. Alternative to #64743, which fixes the same symptom by changing the tokenizer and the derender stream state.

## Claims

- `/v1/responses` with tools no longer corrupts multi-byte characters (e.g. Korean `맑음` → `��음`) for Mistral models. This holds streaming and non-streaming, with and without reasoning.
- Responses now decodes Mistral output the same way as Chat Completions, which already runs with `skip_special_tokens=True` on the grammar path.
- Tool calls and reasoning are still parsed: `MistralTokenizer` keeps `[TOOL_CALLS]`, `[ARGS]`, `[THINK]` and `[/THINK]` when skipping special tokens.

### E2E

Tool calls (`get_weather` for 부산 and 서울) and reasoning items are parsed identically on both servers. Over 15 requests per server with reasoning on, a request occasionally returns no tool call: on `main` 1/15 non-stream and 3/15 stream; with this PR 2/15 and 3/15. In those cases the model emits `get_weather[ARGS]{...}` without `[TOOL_CALLS]`. `main` keeps every special token, so if the marker had been emitted it would appear there; this is model behaviour, not caused by this change.

## Details

**Root cause.** `MistralParser.adjust_request` sends every `ResponsesRequest` through its legacy (non-grammar) branch. That branch calls `ParserEngine.adjust_request`, which unconditionally sets `skip_special_tokens=False`, and then sets it to `False` again when tools are present. With `False`, `MistralTokenizer.convert_ids_to_tokens` returns `id_to_piece` directly. That skips its Tekken byte-fallback handling, so partial UTF-8 pieces become `�` before they are joined.

**Why `False` isn't needed for `MistralTokenizer`.** With `skip_special_tokens=True`, `MistralTokenizer` already keeps exactly the tokens the parser needs (`[TOOL_CALLS]`, `[ARGS]`, `[THINK]`, `[/THINK]`) in both `convert_ids_to_tokens` and `convert_tokens_to_string`. The parser also matches `[TOOL_CALLS]` and `[ARGS]` by token id. The original tool parser guarded this explicitly with `not isinstance(self.model_tokenizer, MistralTokenizer)` and the note "we don't want skip_special_tokens=False with MistralTokenizer as it is incompatible". The guard was lost when Responses requests were routed into this branch (#38150), and the unified parser (#48947) carried that behaviour over.

**Change.** In the legacy branch, only call `ParserEngine.adjust_request` (which forces `False`) for non-Mistral tokenizers, i.e. HF chat-template tokenizers driving the Mistral parser. The behaviour for those is unchanged.

**Limitations.** A client that explicitly sends `skip_special_tokens=False` still hits the byte-fallback bug in `MistralTokenizer.convert_ids_to_tokens`. Fixing that changes the token pieces returned to other callers (`_vocab_dict`, `/tokenize`, derender stream state), which is what #64743 does, so it's left out of this PR to keep it small.
