# [ROCm][Perf][DSv4.1] Mono: issue the FFN seam's static loads before their polls

[Upstream PR](https://github.com/vllm-project/vllm/pull/61934) · state: closed · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

DSv4.1-Flash mono decode (MI355X): K2's FFN seam read its static data (norm weight, score bias, slice inputs) only after the poll before it, so that load latency sat on the layer's critical path. They are now issued before the poll, as the attention front and back already do. Follow-up to #60397 and #61082; outputs are bit for bit unchanged. Touches the same files as #60731 (gfx942 port), so whichever merges second needs a rebase.

## Claims

- K1 + K2 per layer is 2.8-3.6 us faster for M = 1 and 6 at TP2 and TP4 (-2.5% to -4.8%); larger steps gain 0.4-1.5%. No point is slower.
- End to end, TP4 c1 decode ITL drops 1.7-1.8% (1.704 -> 1.675 ms and 1.710 -> 1.680 ms, DSpark, synthetic acceptance 3.51).
- Kernel outputs are bit for bit identical to `main`, and `test_dsv41_mono_numerics` passes at TP2 and TP4.

## Validation

Each cell is the mean of two runs with the two builds on swapped GPU sets (`main` in a separate worktree). Two runs of identical code differ by up to 0.4 us (M <= 12) and 2.4 us (M = 48).

## Details

A per-CTA timeline of K2 (stamps after each stage, TP4, M=6) put the FFN seam on the critical path as: last slice -> norm (3.8 us) -> xrdy -> router -> route -> ug. Inside the norm, the 8 norm-weight loads per thread were issued after the rstd, so the apply step took 2.4 us. The same pattern was in two more places:

- `stage_norm`: the norm weight is loaded before the `lin` poll (K1's seam norm shares this function and gains too).
- `stage_route`: the score bias is loaded before the logits poll.
- `stage_slice` in K2's FFN seam: the residual rows, mixes and `hc_fn` are loaded before the attention all-reduce's poll (`slice_preload`; `batched_rounds` takes the first batch's loads ready-made, later batches load as before). The FFN launch (`part`) takes the same path.

The values read are unchanged, so every output is too. The change is 47 lines in the mono package, and the K2 kernel's VGPR (246) and LDS use are unchanged.

<details><summary>Tried and not included</summary>

All measured with the same kernel microbenchmark; none changes the outputs.

- **Router gate weights before the x wait:** -1.4 us at TP4 M=12, but +1.9 us at M=6 (repeatable on other GPUs). The 3.9 MB burst lands while the norm stage is on the critical path (norm finishes about 0.9 us later). Kept out.
- **Deeper weight-load pipelining in the routed ug GEMV** (`ahead = slices`): neutral at TP4, +7 us at TP2 M=48.
- **Two poll loads in flight:** LLVM merged the duplicate loads, so only instructions were added; +0.7 to +1.4 us.
- **L2 weight prefetch of the static weights** (an oracle that touches them before each launch): under 1% of K2, so no kernel work was done.
- **The gate stage is not on the critical path:** it runs on CTAs 160-165 in parallel with norm (166-171); a faster Sinkhorn would not shorten the layer.
- **Attention back and the expert phase:** the back already issues its static loads before its polls; the expert phase is HBM-bound and its tasks quantize (22 experts x 18 parts on 256 CTAs). No cheap change found.

</details>

Limitations: MI355X only (CDNA4, as the kernels), TP2 / TP4, decode steps of at most 48 rows; the kernel-level numbers use warm weights, so they say nothing about expert-weight streaming (which this change does not touch). I found no open PR making this change. Developed and measured with Claude Code; the submitter's line-by-line review is still pending.
