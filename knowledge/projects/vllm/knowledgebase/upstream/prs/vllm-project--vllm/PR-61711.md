# [Perf] Enable the envs cache once AsyncLLM is initialized

[Upstream PR](https://github.com/vllm-project/vllm/pull/61711) · state: closed · merged: False

## Original PR description

## Overview

Call `enable_envs_cache()` at the end of `AsyncLLM.__init__`, so the process hosting `AsyncLLM` gets the same cached `envs` lookups the engine core and the multiprocess executor already enable for themselves.

## Claims

- Every `envs.X` read on the API-server side of the engine (input processing, output processing, stats) becomes a cached attribute lookup after engine construction instead of a module `__getattr__` plus `os.getenv` call. Measured on the installed vLLM (CPU, aarch64): one `envs.VLLM_COMPUTE_NANS_IN_LOGITS` read goes from 2.4 µs to 0.43 µs, and the per-output `IterationStats.update_from_output` that reads it from 4.1 µs to 2.1 µs.
- No behaviour change for deployments that set environment variables before starting the engine, which is the documented contract for `enable_envs_cache()` ("environment variables should NOT be updated after the service is initialized").

## Validation

- py-spy GIL profile of an `AsyncLLM`-hosting worker streaming a few thousand concurrent requests showed `envs.__getattr__` frames under the output-processing loop; with the cache enabled they disappear.
- `pre-commit run --files vllm/v1/engine/async_llm.py` passes.
- In-process engine-core tests already run with the cache enabled (`EngineCore.__init__` enables it in the same process), so the test suite already exercises cached `envs` in the API-server code paths.

## Details

`enable_envs_cache()` is idempotent (it checks whether `__getattr__` is already wrapped), so enabling it here is safe when `EngineCore` runs in-process and has enabled it first. The call sits after the stat loggers are built and before the output handler starts, which is the last point in `__init__` where engine configuration is read.

Trade-off: a process that constructs an `AsyncLLM`, then changes a `VLLM_*` environment variable and expects the new value to take effect, will no longer see the change. That was already the case for the engine core and the workers, and the `envs` module documents it.

- peilii · comment · 2026-10-15T17:04:50Z · [source](https://github.com/vllm-project/vllm/pull/61711#issuecomment-6197738189)

That is a fair concern, and I agree the trade-off is different here. The engine core and the multiproc executor own their processes; `AsyncLLM` does not, and freezing `vllm.envs` for a host program that may legitimately change environment variables between calls is a side effect that is hard to reason about from inside vLLM.

With #61710 merged, the per-output path no longer reads the environment at all (the NaN flag is read once per `IterationStats`, i.e. once per engine step), and the remaining `envs` reads on the `AsyncLLM` side are per step or rarer, so the measurable part of this change is already in. I will close this PR rather than add a process-wide switch for a residual gain. If a specific per-request read shows up in a profile later, hoisting it the way #61710 did is the safer pattern.
