# [KV Connector] Add ConnexConnector: P/D disaggregation that survives decode-instance failures

[Upstream PR](https://github.com/vllm-project/vllm/pull/63804) · state: open · merged: False

## Original PR description



## Overview

Registers `ConnexConnector`, a pull-based P/D connector whose prefill-side KV stays available as a renewable hold, so a request whose decode instance dies can be resumed on another decode instance without a second prefill. The implementation ships in the optional [`connex-ai`](https://github.com/HeterInfra/connex) package (same pattern as `LMCacheConnectorV1`); vLLM gains no dependency and no code path changes for other connectors.

**Not a duplicate:** searched open PRs/issues for `connex`, P/D fault tolerance and elastic P/D connectors. #55151 ("[wip] support PD seperate mode for fault-tolerance", no description or code yet) targets fault tolerance in vLLM's own P/D path; this PR does not touch that path and adds an external connector with request-level resume. #59330 (stop P/D transfers at N-1) changes NIXL/Mooncake semantics for sliding-window models; ConnexConnector currently supports full-attention models only and follows the current N-token load.

## Claims

- New `kv_connector="ConnexConnector"`: decode pulls prompt KV with one-sided RDMA reads (connex-rs over UCX with GPUDirect RDMA, or Mooncake Transfer Engine).
- Killing a decode instance mid-run loses no requests: affected requests resume elsewhere by re-pulling the held KV (0 extra prefills, 0 tokens off the argmax).
- Steady-state TTFT/TPOT/throughput on par with `NixlConnector` on the same setup.
- A prefill instance dying during a transfer fails only the affected loads (under `kv_load_failure_policy`).

## Details

Existing P/D connectors free the prefill blocks as soon as decode has read them, so once decoding starts the prompt KV exists in one place. If the decode instance dies (crash, preemption, spot scale-down), every in-flight request must be prefilled again or errors out.

ConnexConnector makes the prefill-side copy a hold: a lease named by a transfer id, renewed by every pull, released by the decode instance when the request finishes or dropped after `retain_s` (default 60 s). `release: after_pull` frees blocks after the first read like other connectors. To resume, a router resends the same `kv_transfer_params` with the prompt plus the k generated tokens; the new decode instance async-loads `remote_num_tokens` and computes the k tokens locally. Instances can register their P/D role with the Connex front-router so instances can be added or removed at run time.

Request flow:
1. Prefill instance (`kv_producer`) runs the prompt; on finish the scheduler keeps the blocks and returns `transfer_id`, `remote_ctrl`, `remote_num_tokens`.
2. Decode instance (`kv_consumer`) schedules the request as `WAITING_FOR_REMOTE_KVS` and pulls the blocks with one-sided reads.
3. Decode generates; on finish it sends a release, and the prefill worker reports the transfer done so the blocks are freed.
4. If decode dies before step 3, the router resends to another decode instance, which repeats step 2 against the still-held blocks.

Changes: `v1/connex_connector.py` (lazy re-export with install hint), registration in `factory.py`, `docs/features/connex_connector_usage.md` plus an entry in `disagg_prefill.md`, and scheduler-level tests through the real `Scheduler`.

Limitations: full-attention KV only; equal TP and block size on both sides.

Developed with AI coding assistance; all changes were reviewed and tested by the author.
