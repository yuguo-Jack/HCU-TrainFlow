# [Bugfix][Frontend] Fix tool_reference results on DeepSeek V4.1 and /v1/messages

[Upstream PR](https://github.com/vllm-project/vllm/pull/64971) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

The DeepSeek V4.1 encoder rejects `tool_reference` content parts with a 400, and `/v1/messages` turns a `tool_result` with `tool_reference` items into two `tool` messages for one call. This renders each reference on V4.1 as the tool's name and emits one `tool` message per `tool_result`, so conversations that use Claude Code's tool search work on DeepSeek V4.1 and render one result per tool call.

## Claims

- Requests with `tool_reference` parts render on DeepSeek V4.1. On main they fail with `DeepSeek V4.1 supports text and image content only; got 'tool_reference'`. This covers `tool_result` blocks with `tool_reference` items on `/v1/messages`, and `tool_reference` parts on `/v1/chat/completions`.
- On V4.1, each reference renders as the tool's name inside its call's `<tool_result>`. Several references are joined with `\n\n`, the separator the encoder already uses between parts.
- `/v1/messages` emits one `tool` message per `tool_result`: the `tool_reference` parts first, then the text. On main, a tool search result renders an extra empty result before the references, on GLM-5.3 as well as V4.1, so after parallel tool calls the results no longer line up with the calls.
- Templates that expand references keep working: GLM-5.3 renders the referenced tool definitions as before.
- A `tool_result` without `tool_reference` items converts as before, and other unsupported part types still return 400 on V4.1.
- The change is in `_convert_user_tool_result` (`vllm/entrypoints/anthropic/serving.py`) and `_normalize_messages` (`vllm/tokenizers/deepseek_v41.py`): 15 lines added and 11 removed, plus three tests.

## Details

**Root cause.** #40190 added `tool_reference` parts. `_convert_user_tool_result` emits a `tool` message with the result's text (empty for a plain tool search), then a second `tool` message with the `tool_reference` items, both for the same `tool_use_id`. An image in the result goes into a `user` message between the two. Templates and encoders that render one result per `tool` message render one result too many. Separately, V4.1 renders with its own encoder, and `_normalize_messages` raises `ValueError` for any part type other than text and image. The `tool_result` stays in the conversation history, so on V4.1 every later request in that conversation fails too, and an agent session that runs a tool search cannot continue.

**Why one message, references first.** Templates that expand references look for a `tool` message whose first part is a `tool_reference` (GLM-5.3's does), so the references lead and the text follows. Images stay in the `user` message after the `tool` message. Limitation: GLM-5.3's template expands such a message and skips its other parts, so text that sits beside references in one `tool_result` no longer renders there; on main it rendered as an extra result. The tool search docs show results that hold only `tool_reference` blocks.

**Why the name.** `apply_chat_template` puts every request tool into the V4.1 system prompt, deferred ones included, so the definitions a reference points at are already in context. The name tells the model which tools the search returned. The Cohere renderer renders these parts the same way (`vllm/renderers/cohere.py`). The model's Jinja template on the Hub drops unknown block types, which would render the search result empty.

**Related.** #52498 and #52610 (open, for #52489) rewrite `tool_reference` items as text in the Anthropic converter for every model. That would also stop the V4.1 400 on `/v1/messages`, but `/v1/chat/completions` requests with these parts would still fail, and the structured parts that templates expanding references rely on would be gone.

Thanks for digging into this! I think the root cause is a bit upstream though. The Anthropic converter (`_convert_user_tool_result`) turns one tool_result with tool_reference parts into two tool messages: an empty one, then one with the references. So every renderer that pairs results with calls by position sees one extra result, not just V4.1.

I checked with `vllm launch render`. DeepSeek V4 and GLM-5.1 (the template tool_reference support was first built for) both render an extra empty result for a plain tool search result on main. The V4.1 merge also misses two cases: a result with an image (the image's user message sits between the two tool messages) and a result with no tool_use_id.

What do you think about fixing it in the converter instead? It would emit a single tool message per tool_result, with the tool_reference parts first and then any text. Then the merge pass in the V4.1 encoder isn't needed, and you keep your tool_reference-to-name rendering.
