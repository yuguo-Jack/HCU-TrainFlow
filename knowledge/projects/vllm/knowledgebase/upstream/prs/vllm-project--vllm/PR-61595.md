# [ROCm] Default AITER on for CDNA3+ when the package is installed

[Upstream PR](https://github.com/vllm-project/vllm/pull/61595) · state: open · merged: False

## Original PR description

## Summary
- When `VLLM_ROCM_USE_AITER` is unset, vLLM now turns AITER on only if the package is installed and the GPU is CDNA3 or newer (MI300, MI355). NVIDIA, MI250, and machines without AITER stay on the current path.
- Explicit `VLLM_ROCM_USE_AITER=0` still opts out. `=1` still forces it on. Recipes on supported GPUs no longer need to export `=1`.
- A partial AITER install that cannot do non-causal MLA now reports unsupported instead of raising, so backend selection can fall through to Triton MLA.

## What this does not close
This is a draft. Do not merge until AMD CI is green with the new default.

- An AITER kernel that passes the support check and then faults at runtime is still a crash. The known gfx942 case is non-causal MLA reaching `cannot get heuristic kernel!` when the backend is selected anyway. Selection now rejects that case when `supports_non_causal()` is false, but other shape or arch gaps inside AITER are not covered.
- Custom allreduce, RMSNorm, GEMM, and the fusions whose sub-flags already default on will follow the master switch. Numerics change for recipes that were calibrated on the Triton path and did not pin `--attention-backend` or `--moe-backend`.
- Explicit `--attention-backend` and `--moe-backend` still win. FP8 MoE that is explicitly requested with `VLLM_ROCM_USE_AITER=1` and is unsupported still fails the same way it does today. Omitting the variable uses the existing try-next-backend loop.
- unified attention, shared-expert fusion, sparse MLA, Triton RoPE, FP4 ASM GEMM, and HIPBMM stay default-off.

## Test plan
- [ ] `tests/rocm/test_aiter_default_on.py`: explicit 0/1, unset without AITER, unset on CDNA3, unset on MI250
- [ ] `test_missing_causal_arg_fails_closed` expects False instead of RuntimeError
- [ ] AMD CI on MI300 and MI355 with the variable unset: MLA, MoE, and a recipe that previously set `=1`
- [ ] Confirm `VLLM_ROCM_USE_AITER=0` still matches today's off path
- [ ] Confirm a recipe that pins `--attention-backend TRITON_MLA` does not switch

## Local case results

Ran on a Windows host against commit `9f07395d09`. No ROCm GPU, so CDNA version and the AITER package were mocked. The switch itself is the real `vllm.envs._vllm_rocm_use_aiter_enabled`. The MLA helpers were executed from the changed source, because this machine cannot import the full attention stack.

28/28 passed.

### `VLLM_ROCM_USE_AITER`

| Case | Result |
| --- | --- |
| Explicit `0` or `false`, even if the mocked GPU is CDNA4 | off |
| Explicit `1`, `true`, `TRUE` | on |
| Explicit `yes` or empty string | off. Only `1` and `true` count as on |
| Unset, AITER package missing, even on CDNA4 | off |
| Unset, AITER present, CDNA 0 (NVIDIA-like) | off |
| Unset, AITER present, CDNA2 (MI250) | off |
| Unset, AITER present, CDNA3 (MI300) | on |
| Unset, AITER present, CDNA4 (MI355) | on |
| Unset, AITER present, CDNA5 (gfx1250) | on |
| Unset, while `vllm.platforms.rocm` is still importing | off |
| Unset, GPU query raises | off |

`envs.VLLM_ROCM_USE_AITER` matched the helper in every explicit case.

### MLA fallback

| Case | Result |
| --- | --- |
| `mla_decode_fwd` has no `causal` argument | returns False, does not raise |
| `mla_decode_fwd` has `causal` | returns True |
| `aiter.mla` cannot be imported | the helper raises ImportError |
| `supports_non_causal()` and the helper raises `RuntimeError` | returns False, so selection can continue |

### Not run here

- Real MI300 / MI355 kernel execution, custom allreduce, RMSNorm, GEMM, and fusions.
- Recipe accuracy against a Triton-calibrated baseline.
- AMD CI with the variable unset, and with `VLLM_ROCM_USE_AITER=0`.
- A recipe that pins `--attention-backend TRITON_MLA`.
