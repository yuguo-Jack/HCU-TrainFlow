# [BugFix] Reset num_output_placeholders on KV load failure recomputation

[Upstream PR](https://github.com/vllm-project/vllm/pull/45146) · state: open · merged: False

## Original PR description

## Related Issue

Closes: #45138

## Description

When a request's KV blocks fail to load via the KV connector and recomputation is triggered, only `num_computed_tokens` was being reset to the longest valid prefix boundary in `_update_requests_with_invalid_blocks`. However, `num_output_placeholders`, which may have been incremented by `AsyncScheduler._update_after_schedule` before the forward pass, was left stale.

This caused the scheduling arithmetic in subsequent steps to be corrupted: `num_new_tokens` would include the stale placeholder count (`num_new_tokens = num_tokens_with_spec + num_output_placeholders - num_computed_tokens`), leading to an overflow that eventually triggers the async-scheduling stop check prematurely, permanently stranding the request in the running queue.

## Root Cause Analysis

The complete bug trigger path:

1. Request enters with all prompt tokens hitting prefix cache → `num_computed_tokens` covers full prompt
2. `is_prefill_chunk` evaluates to `False` → `AsyncScheduler._update_after_schedule` increments `num_output_placeholders += 1`
3. Model forward runs, KV connector reports load failure for the cached blocks
4. `_handle_invalid_blocks` → `_update_requests_with_invalid_blocks` correctly resets `num_computed_tokens` to the longest valid prefix, but **does not reset `num_output_placeholders`** (the bug)
5. `update_from_output` skips the request (it's in `failed_kv_load_req_ids`), so `num_output_placeholders` is never decremented
6. On next schedule: `num_new_tokens = num_tokens + 1 - 0` instead of `num_tokens - 0`, corrupting scheduling arithmetic
7. Request eventually triggers the stuck check and is permanently stranded

## Fix

Reset `request.num_output_placeholders = 0` in both branches of `_update_requests_with_invalid_blocks` where `num_computed_tokens` is adjusted downward due to invalid blocks. This is consistent with the existing preemption path in `reset_prefix_cache` (scheduler.py:1971) which also zeroes placeholders when restarting prefill from scratch.

## Testing

- Verified via code-flow analysis simulating the exact scenario from the issue
- Confirmed the fix prevents the stale-placeholder scheduling corruption
- The change is purely CPU-side scheduler logic — no GPU required

Could you add a focused regression test for this path? The fix relies on resetting `num_output_placeholders` when `_update_requests_with_invalid_blocks()` rewinds `num_computed_tokens`, but the PR currently only includes code-flow analysis.

A unit test can construct a request with `num_computed_tokens` past an invalid KV block and `num_output_placeholders = 1`, call `_update_requests_with_invalid_blocks(...)`, and assert the placeholder count is reset to 0 while the request is marked affected. Ideally it should cover both branches touched here, since a future refactor could easily preserve the token rewind but lose the placeholder reset and reintroduce the async-scheduler stuck-request bug from #45138.

Thanks for the review @harjothkhara! I've added two focused regression tests covering both branches:

- **`test_update_invalid_blocks_resets_output_placeholders_branch1`** — constructs a request with `num_output_placeholders = 1` and a unique invalid block, calls `_update_requests_with_invalid_blocks` directly, and asserts the placeholder is reset to 0 alongside the token truncation.

- **`test_update_invalid_blocks_resets_output_placeholders_branch2`** — two requests sharing a common-prefix block; the first request hits Branch 1, the second falls through to the shared-block path where `marked_invalid_block` stays `False`. Also asserts `num_output_placeholders == 0` on that path.

Both tests call `_update_requests_with_invalid_blocks` directly (no end-to-end scheduling roundtrip needed), so they should be fast and resistant to future refactors accidentally dropping the placeholder reset. Let me know if you'd like any adjustments!

- he-yufeng · comment · 2026-10-09T14:26:10Z · [source](https://github.com/vllm-project/vllm/pull/45146#issuecomment-6082893110)

Overlap note for whoever triages #45138: #59793 closes the same issue and includes this placeholder reset, plus two pieces this narrower take leaves open. Output already in flight from the failed load is marked stale and dropped as it returns (the `drop_stale_output` idiom shared with `_handle_stopped_request`), and `spec_token_ids` are cleared so stale drafts do not survive the recompute. Zeroing placeholders alone still lets an in-flight frame sampled from the invalid KV land as a valid token when it returns.
