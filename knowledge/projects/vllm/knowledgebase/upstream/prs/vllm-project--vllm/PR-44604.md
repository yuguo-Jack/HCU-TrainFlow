# [Kernel] Optimize fused_add_rms_norm with software pipelining

[Upstream PR](https://github.com/vllm-project/vllm/pull/44604) · state: closed · merged: False

## Original PR description

[Kernel] Optimize fused_add_rms_norm with software pipelining

## Summary
Optimizes `fused_add_rms_norm_kernel` in
`csrc/libtorch_stable/layernorm_kernels.cu` by introducing software pipelining
in the RMS normalization phase (Phase 2), reusing the first residual vector
computed in Phase 1, and fixing an integer overflow bug in index calculation.

## Problem
The original kernel reads `residual` and `weight` in the same loop iteration as
computation, causing memory latency to block the pipeline:

```cpp
// Original: load and compute in same iteration
res = residual_v[id];          // load
w = weight_v[idx];             // load
out = res * s_variance * w;    // compute
input_v[strided_id] = out;     // store
```

Additionally, the vectorized path used `int` for row offset calculation, which
can overflow with very large tensors.

## Solution

### 1. Software Pipelining (Phase 2)
Prefetch the next iteration's `residual` and `weight` data while computing the
current iteration:

```cpp
// Optimized: overlap next load with current compute
res_current = res_next;
w_current = w_next;
res_next = load_f16_vec(residual_v, next_id);
w_next = load_f16_vec(weight_v, next_idx);
out = res_current * s_variance * w_current;
```

### 2. Reuse First Residual Vector From Phase 1
Phase 1 already computes `input + residual` and writes it back to `residual`.
The optimized path keeps each thread's first computed vector in a register and
reuses it in the Phase 2 prologue:

```cpp
_f16Vec<scalar_t, width> first_residual;
...
first_residual = temp;
...
res_next = first_residual;
```

For `hidden_size=8192`, `width=8`, and `block_size=1024`,
`vec_hidden_size == block_size`, so this avoids rereading the full first Phase 2
residual pass from global memory.

### 3. Scoped 128-bit Vector Loads/Stores
Phase 2 uses local helpers for width-8 FP16/BF16 loads and stores, keeping the
change scoped to `fused_add_rms_norm_kernel` without changing the shared
`_f16Vec` definition used by other kernels:

```cpp
res_next = load_f16_vec(residual_v, next_id);
w_next = load_f16_vec(weight_v, next_idx);
store_f16_vec(input_v, strided_id, out);
```

### 4. FP16/BF16-Only Width-8 Dispatch
The width-8 path is only dispatched for `Half` and `BFloat16`; `Float` keeps
using the generic width-0 fallback.

### 5. Integer Overflow Fix
Changed row index calculation to `int64_t` with an explicit cast:

```cpp
int64_t id = (int64_t)blockIdx.x * vec_hidden_size + idx;
```

### Analysis

The kernel remains memory-bound, with DRAM throughput at 82.14% of peak. The
latest register reuse optimization improves elapsed cycles by 2.71% and reduces
wall-clock duration by 0.44% in this profiling configuration. Since DRAM
bandwidth is still the dominant limiter, further gains will likely require
reducing total memory traffic or fusing adjacent work rather than only improving
instruction scheduling inside this kernel.
