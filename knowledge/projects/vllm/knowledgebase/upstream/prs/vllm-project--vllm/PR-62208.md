# [Bugfix][DeepSeek V4.1] Inject Engram at pipeline stage entry

[Upstream PR](https://github.com/vllm-project/vllm/pull/62208) · state: open · merged: False

## Original PR description

## Overview

DeepSeek-V4.1 applies trained Engram modules at configured transformer layers. If a pipeline partition starts a non-initial stage on one of those layers, the stage-entry control-flow branch calls mHC pre directly and bypasses the normal Engram branch. Certain valid PP partitions can therefore silently skip an Engram operation for every request. The real DeepSeek-V4.1-Flash configuration triggers this at layer 14 with `VLLM_PP_LAYER_PARTITION=14,26`.

This PR restores the missing NVIDIA operation by applying the local stage-entry Engram after receiving the previous stage's completed residual stream and before mHC pre.

**AMD is affected by the same issue. We currently only have access to NVIDIA hardware, so this PR fixes only the NVIDIA implementation for now.**

## Claims

- Restore Engram when its layer is the first layer of a non-initial pipeline stage.
- Preserve the incoming `pre_mix`, selected Engram hash column, mask, and existing no-hash behavior.
- Add a non-identity regression test to the NVIDIA model CI job.

### Verify Engram execution at the pipeline boundary

This check verifies that layer 14 executes its trained Engram module before mHC pre when it is the first layer of a pipeline stage.

We compared three configurations using the real DeepSeek-V4.1-Flash checkpoint:

- **Without this PR, PP=1:** the reference configuration. Layer 14 runs within the same pipeline stage as the preceding layers.
- **Without this PR, PP=2 (`14,26`):** the configuration that exposes the bug. The first stage contains 14 layers, so the second stage starts at layer 14.
- **With this PR, PP=2 (`14,26`):** the same pipeline partition with the fix applied, tested independently on both H20 nodes.

Each configuration received the same fixed 256-token prompt and generated two tokens, each constrained to a single allowed token ID. This kept the token sequence fixed across configurations. Each configuration was run twice in eager mode.

#### Was layer 14's Engram actually executed?

| Configuration | Layer 14 Engram executed? | Input passed to layer 14's mHC pre |
| --- | --- | --- |
| Without this PR, PP=1 — reference | Yes | Engram output |
| Without this PR, PP=2 (`14,26`) | **No** | Tensor received from the previous stage, without applying Engram |
| With this PR, PP=2 (`14,26`) — both nodes | **Yes** | Engram output |

The unpatched PP=2 configuration had valid Engram hashes and masks available at layer 14, but never called its Engram module. The missing operation was therefore caused by the stage-entry control flow.

#### Did mHC receive the correct tensor?

We recorded SHA-256 checksums of the full tensors at the pipeline handoff, Engram input/output, and mHC pre input. These checksums track tensor contents; they are separate from the token hashes used by Engram.

For every TP rank, measured step, and repeat, the checks confirmed these paths:

- **Without this PR, PP=2:** the tensor sent by the previous stage was passed directly to mHC pre. Engram was skipped.
- **With this PR, PP=2:** the received tensor was passed to Engram, and Engram's output was passed to mHC pre.
- **PP=1 reference:** Engram's output was also passed to mHC pre.

These comparisons verify the data flow within each run; they do not require bitwise-identical outputs between PP=1 and PP=2.

#### Did Engram make a measurable change?

For runs that executed Engram, we measured the difference between its input and output at layer 14:

| Step | RMS of the Engram update | Tensor elements whose stored values changed |
| --- | ---: | ---: |
| Prefill | 0.03445–0.03557 | 67.22%–67.82% |
| Decode | 0.05899–0.06505 | 81.83%–83.14% |

The update RMS is `RMS(Engram output − Engram input)`. These nonzero differences confirm that skipping this trained Engram module changes the tensor passed to mHC pre.

**This check confirms that the affected PP partition skips a trained Engram operation and that this PR restores it before mHC pre on both tested nodes.** It does not establish an accuracy improvement: captured logits varied across repeated runs and nodes by an amount comparable to the patch effect. The GSM8K results below report the separate end-to-end accuracy evaluation.

## Details

At the end of a pipeline stage, the previous rank completes its final mHC post and sends the full 3-D residual stream together with `pre_mix`. The next stage starts with `residual=None`, assigns that received stream to `residual`, and calls mHC pre directly. Because normal Engram injection lives in the following `elif`, an Engram on the stage's first layer is silently skipped.

This change injects the local Engram after accepting the completed stream and before mHC pre. It does not repeat the previous stage's post or alter first-layer embeddings, in-stage Engram execution, or batches without Engram hashes.

The real DeepSeek-V4.1-Flash configuration has Engram layers 1 and 14. A pipeline partition beginning its second stage at layer 14 can therefore reach this path. Open PR searches for the same Engram pipeline-stage fix found no direct duplicate; related PCP work such as #62183 does not implement this injection.
