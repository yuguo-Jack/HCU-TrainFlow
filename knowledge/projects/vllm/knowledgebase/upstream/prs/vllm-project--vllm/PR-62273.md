# [Doc][ROCm] Align Kimi-K3 MI355X recipe with InferenceX #4215

[Upstream PR](https://github.com/vllm-project/vllm/pull/62273) · state: closed · merged: True

## Original PR description



## Overview

Align the Kimi-K3 MI355X TP8 recipe and its AgentX guide with [SemiAnalysisAI/InferenceX#4215](https://github.com/SemiAnalysisAI/InferenceX/pull/4215) (branch revision `6e72cbc11234e624d66b8fc5eaddac50068db15c`), which supersedes the InferenceX #3833 lane that vllm-project/recipes#1093 documented. Recipes for vLLM-served models now live here (#61302), so this changes only `recipes/models/moonshotai/Kimi-K3.yaml`.

## Claims

- MI355X TP8 command builder: drop the `--load-format fastsafetensors` override so the AMD profile's default loader applies (on the lane's image, fastsafetensors ran out of GPU memory while loading weights, [InferenceX run 38975751686](https://github.com/SemiAnalysisAI/InferenceX/actions/runs/38975751686)), and add `AITER_FLYDSL_STAGE2_FP8=1`.
- AgentX guide: the ten #4215 cells (dcp1 c1/c4; dcp8 c4-c60 with SimpleCPUOffload), per-cell online FP8 target quantization (c1 no longer ignores `*in_proj_qkvgfab`; every other cell quantizes only `in_proj_qkvgfab`), `VLLM_ROCM_QUICK_REDUCE_QUANTIZATION=INT4` with `VLLM_ROCM_QUICK_REDUCE_MIN_SIZE_BYTES_MB=16`, the pinned image, and the golden-AL table for 7/5/4 draft tokens.
- Fix two errors in the previous guide: `seq -s, 2 "$MAX_CAPTURE"` captured odd CUDA-graph sizes (now even only, as the text states), and `AITER_QUICK_REDUCE_QUANTIZATION` is not read by vLLM (the lane sets `VLLM_ROCM_QUICK_REDUCE_QUANTIZATION`).
- Real serving stays on block verification; synthetic acceptance stays in the separate throughput-only section. The `Inferact/Kimi-K3-DSpark` draft stays at its shipped precision: BF16 weights and activations, FP8 KV.

## Validation

- Ground truth: the #4215 lane recipe and `amd-master.yaml` entry at `6e72cbc` are identical to in-PR commit `8a2aec3`, which passed all ten cells and their evals in [InferenceX run 39002920671](https://github.com/SemiAnalysisAI/InferenceX/actions/runs/39002920671) on `vllm/vllm-openai-rocm:nightly-rocm100-49cb2bbf71cfd36ee5aa33d1e184b1cddff55294`, with real block verification: GSM8K 0.969 strict/flexible (dcp8 c60) and `kimi_tool_call_schema_full` 0.978-0.998 (nine cells).
- From vllm-project/recipes main (`b8bec4f`), pointed at this checkout: `node scripts/validate-source.mjs --source vllm --dir <vllm>/recipes` (valid, 215 recipes), `node scripts/build-recipes-api.mjs` and `pnpm build` all pass; the rendered MI355X builder command and guide section were checked in a local browser.
- Generated-command diff against this branch's base: of the 71 Kimi-K3 JSON API files, only `hw/mi355x.json`, the two MI355X Mooncake KV-store strategies (which reuse the TP8 command) and `Kimi-K3.json` (guide, `date_updated`) change. The MI355X command changes only `--load-format fastsafetensors` to `auto` and adds `AITER_FLYDSL_STAGE2_FP8=1`; every other hardware and strategy file is identical.
- The guide's reproduction script, run for each of the ten cells with `vllm` stubbed, resolves arguments and environment equal to the #4215 lane: draft tokens, `--max-num-seqs`, `--max-num-batched-tokens`, even capture sizes 2..max, quantization, speculative and offload configs, DCP8, QuickReduce and `PYTHONHASHSEED`. Stale #3833 cells (dcp8 c1/c2/c12/c14/c44) are rejected. All 12 guide bash blocks pass `bash -n`, and all 12 embedded JSON values parse.
- `pre-commit run --files recipes/models/moonshotai/Kimi-K3.yaml` passes; `git diff --check` is clean.
- No new GPU run: the recipe documents the exact configuration validated by the InferenceX run above.

## Details

- Not duplicate work: no open PR in vllm-project/vllm or vllm-project/recipes references InferenceX #4215, `in_proj_qkvgfab`, `AITER_FLYDSL_STAGE2_FP8` or `VLLM_ROCM_QUICK_REDUCE_MIN_SIZE_BYTES_MB` (searched 2026-10-18); the open Kimi-K3 MI355X PRs here are kernel changes.
- INT4 QuickReduce is lossy, so as before it stays out of the builder and appears only in the exact reproduction command. The 16 MiB floor keeps it off the draft: the draft's all-reduces carry at most 600 draft-step tokens x 7,168 BF16 values (about 8.2 MiB at c60), and its context projection is replicated.
- `AITER_FLYDSL_STAGE2_FP8=1` stores the FlyDSL MoE down-projection route outputs as MXFP8 before the top-k sum. It changes only the target's MoE (the DSpark draft MLP is dense) and the lane sets it at every cell, so it goes in the builder. `AITER_BF16_FP8_MOE_BOUND=0` is not read on the SiTUv2 path and stays out of both, as before.
- Per-cell settings (`--max-num-seqs`, batched tokens, graph sizes, target quantization) remain guide-only; the builder keeps its general defaults.
- Not changed: the MI355X disaggregated P/D example still uses `fastsafetensors` and the rolling `nightly` image; it is a separate deployment that #4215 does not cover.
- AI assistance (Claude Opus 5.5 in Cursor) was used to prepare this change and its validation.
