# [Perf][MRV2] Stage buffer contents by reference and copy straight into UVA

[Upstream PR](https://github.com/vllm-project/vllm/pull/63633) · state: closed · merged: True

## Original PR description



## Overview

Builds on #63210 (typed-array staging in `StagedWriteTensor`), which is the first commit here. Only the last commit belongs to this PR. That commit stages numpy and `array.array` contents by reference, concatenates all staged contents straight into a UVA buffer slot, and has the write kernel read them through UVA for GPU-resident targets too. Ideas are taken from #59908 (@benenzhu) and #62702 (@Juntian777), who are credited as co-authors.

## Claims

- On both GB200 and MI350X, `apply_write` is faster than main and than #63210 alone, in GPU time and in host time, across every shape measured. This includes the small block-table writes, where #63210 alone was slightly slower than main.
- A numpy array or `array.array` is staged without a copy. For example, mrope positions or a 131k-token `array('i')` take about 65µs to stage and apply on GB200, against 4–13ms on main.
- The write kernel reads staged contents through UVA for GPU-resident targets too, not only UVA targets. This removes the per-apply pinned allocation and `cudaMemcpyAsync`. Without pinned memory, the existing `NonUvaBuffer` fallback copies into a preallocated device buffer.
- There is no new option. All existing callers get the same values in the same rows.

<details>
<summary>Method</summary>

- **Builds compared:** all three `buffer_utils.py` versions (main, #63210, and this PR) are loaded side by side in one process, on one GPU.
- **GPU time:**
  1. Stage the writes; this part is not timed.
  2. Enqueue `torch.cuda._sleep` so the GPU is busy.
  3. Record a CUDA event, call `apply_write`, and record a second event.
  4. Keep the sample only if the GPU was still sleeping when the host finished enqueueing.

  This measures what `apply_write` enqueues back to back (the H2D copy plus the kernel, or just the kernel), without host launch gaps. Each case uses 600 samples.
- **Host time:** median wall time of stage + apply, with `synchronize()` excluded from the "host" number.
- **Distributions:** on GB200 the H2D variants are bimodal, at about 11µs and about 19µs. With UVA contents, p10–p90 stays within about 2µs.

</details>

There is no end-to-end serving benchmark yet. The gains are on the step-critical path of MRV2 input preparation (block-table updates every step, prompt staging on admission). They are microbenchmarks only, so the effect on whole steps is unmeasured.

## Details

- **Buffer inputs by reference.**
  - `stage_write` keeps an `np.ndarray` or `array.array` as its own chunk, closing off any pending list contents into a chunk first.
  - Lists still go through `array.fromlist`, and other iterables through `extend`.
  - `apply_write` does one `np.concatenate(chunks, out=uva_slot, casting="unsafe")`.
  - Callers must not modify a staged buffer before `apply_write`. Values are cast to the target dtype, and out-of-range values wrap. Both behaviours are documented in the docstring.
  - `rope.py` now passes `prefill_positions[i].numpy()` instead of `.tolist()`.
- **Direct copy into UVA** (after #59908). `UvaBufferPool._next_buf` and `copy_chunks_to_uva` write the concatenation straight into the pool slot, with no intermediate contents buffer.
- **UVA contents for GPU targets.**
  - Before: #63210, like main, copied contents with `async_tensor_h2d` for GPU-resident targets. That costs about 25µs of host time per apply (a pinned allocation plus `cudaMemcpyAsync`) and about 10–25µs of GPU time for the copy engine.
  - Now: the kernel reads the pinned contents directly. Both approaches cross the link once and run serialized on the same stream. The UVA read was cheaper on NVLink-C2C (GB200) and on PCIe (MI350X) alike, including for 512KB dense writes.
  - `FusedStagedWriter` gets a UVA contents pool for the same reason.
- **No rollback in `stage_write`.** The try/except from #63210 is removed: `fromlist` is already atomic, and a failed staging call is a caller bug.
- **Typecode map.** `TORCH_DTYPE_TO_ARRAY_TYPECODE` moves to `vllm/utils/torch_utils.py`, next to `TORCH_DTYPE_TO_NUMPY_DTYPE`.
- **Interaction with #62702.** #62702 keeps prompt token ids as int32 `array`s end to end. With this PR, those arrays are staged into `all_token_ids` without any copy.
- **Tests.**
  - `test_staged_write_input_types`: interleaves lists, ranges, int64 and strided int32 arrays, `array('i')`, empty arrays and `stage_write_elem`.
  - `test_staged_write_uses_uva_contents`: now covers both target kinds, pinned to the target's device. Without that, a leftover current device from an earlier test makes the GPU-target case fail when two GPUs are visible.
  - `test_staged_write_without_uva`: forces the `NonUvaBuffer` fallback through `apply_write` and through `FusedStagedWriter`.
