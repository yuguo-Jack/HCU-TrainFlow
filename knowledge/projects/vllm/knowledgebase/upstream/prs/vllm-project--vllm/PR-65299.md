# [Bugfix][MoE] Keep grouped top-k weights independent of batch size

[Upstream PR](https://github.com/vllm-project/vllm/pull/65299) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

The single-group grouped top-k router returns different weights for identical logits when a batch crosses 1,024 tokens. The warp kernel rebuilds each weight by subtracting the correction bias from a rounded selection score, while the block kernel keeps the original score. Compute the unbiased score from the logits of the selected experts.

## Claims

- Identical logits get identical routing weights on both sides of the 1,024-token kernel switch.
- Expert selection does not change, and the kernel cost stays within about 2 us at the sizes that I measured.
- This is a determinism fix. I did not measure an end-to-end quality improvement.

## Validation

End to end, I ran GLM-5.3-Flash-BF16 at TP=8 through the OpenAI server, twice per tree and with the whole node to itself. Quality does not change beyond run-to-run noise, so I do not claim a quality gain.

| Tree | GSM8K on 256 questions, run 1 | GSM8K on 256 questions, run 2 |
| --- | --- | --- |
| Without the fix | 0.9336 | 0.9219 |
| With the fix | 0.9375 | 0.9219 |

Two long prompts send more than 1,024 tokens through the router. The first gave the same greedy text in all four runs. The second gave the same text in three runs, and one run with the fix differed after about 12 tokens. The other run with the fix matched the runs without it, so this does not show a consistent effect. Earlier runs on this model also had logprobs that moved up to 0.6 between identical runs.

**CI coverage:** `(L4) MoE Kernels` selects the test file and rebuilds the kernel, because `csrc/moe/` is in its file list. Its `(MI300)` mirror skips this test, because the test runs only on CUDA. Upstream checks are stopped at contributor authorization, so Buildkite has not run this branch.

## Details

`single_group_topk_warp_kernel` selects experts with a biased score, and a later step needs the unbiased score as the weight. The block kernel keeps the original value for that step. The warp kernel recovered it as `lane_score - bias`, and `lane_score` is already rounded, so the result can differ from the original in the last bits. Models with a correction bias, such as GLM-5.3-Flash, switch kernels at 1,024 tokens, so the same token can get different weights depending on the batch it is in.

The fix calls `preprocess_score` again on the selected expert's logit, which is what the block path computes. This adds one score computation per selected expert.

We carry a local runtime workaround for this defect in our GLM-5.3 deployment, and this change would let us remove it.

This does not duplicate an open PR. #60775 adds a group count constraint in the same file and does not change this calculation. #54955 is a draft for batch-invariant kernels and does not change this file.
