## Purpose

The boot line `GPU KV cache size: N tokens` reports `max_concurrency × max_model_len`. For single-group models that happens to coincide with the pool's token capacity; for hybrid models it does not, and neither `num_blocks` nor `num_blocks_per_request` is recoverable from the line. A reader seeing `1,553,140 tokens` against a 643-block pool has no way to get from one to the other.

This PR does two things, both logging-only:

1. Labels `N` in the existing line as `(max_concurrency × max_model_len)`, so the number is no longer mistaken for the pool's token capacity.
2. Adds a second `info_once` with the pool size, the per-request block cost, and a per-group breakdown — the numbers that actually explain where the pool went on a hybrid model.

`get_max_concurrency_for_kv_cache_config` already computed the per-group block counts and discarded them, so it now returns them as a `KVCacheBlockBudget` and is renamed `get_kv_cache_block_budget`. `max_concurrency` stays a derived property, which keeps the invariant `max_concurrency == num_blocks / sum(blocks_per_group)` in exactly one place — the alternative, recomputing the per-group expression at the log site, would leave two copies of the per-request cost model free to drift.

**No computed value changes.** `kv_cache_size_tokens` and `kv_cache_max_concurrency` are byte-identical: same `cdiv(max_memory_usage_bytes, page_size_bytes)` per group, same sum, same division, same `int(max_concurrency * max_model_len)`. See the token counts in the before/after below — they match on all three configurations.
