# [KV Offload] Refactor cpu offloading - calculate gpu pointers and introduce fs ABC

[Upstream PR](https://github.com/vllm-project/vllm/pull/56076) · state: open · merged: False

## Original PR description


## Purpose
As described in RFC #54777, the kv OffloadingWorker interface passes logical device block IDs to workers, which then internally resolve them to device pointers. This duplicates tensor layout logic in every worker implementation. As part of our GDS implementation, we refactor the worker interface so that device pointer resolution happens once and workers receive pre-resolved device pointers.

We also introduce FSOffloadingWorker, an abstract base for file-based device offloading, so that different filesystem backends (GDS/cuFile, POSIX, NIXL, etc.) can be added without duplicating logic. Following this PR, we will introduce the GDS component as a concrete class inheriting from the FSOffloadingWorker ABC.

# PR #56076 — store-path ordering across FS backends

## Problem

`FSOffloadingWorker.submit_store` hands raw device pointers to host-side I/O. The
pages were written by kernels on the compute stream, and host I/O is not ordered
against that stream, so the DMA can read bytes that are still in flight.

The earlier revision had `torch.cuda.current_stream().synchronize()` in
`submit_store`; it was removed to avoid stalling the engine thread, and nothing
replaced it. Correctness now rests on the engine's incidental per-step stream
drain, which is not a contract the worker can rely on — and it becomes less safe,
not more, once a backend submits asynchronously.

## API change

Record the dependency once, on the engine thread (non-blocking), and let each
backend honor it however suits it:

```python
    def _submit_io(self, device_ptrs, keys, is_store):
        file_ops, total_bytes = self._build_file_ops(device_ptrs, keys)
        ready_event = torch.Event()
        ready_event.record()
        return self.submit_io(file_ops, is_store, ready_event), total_bytes

    @abstractmethod
    def submit_io(
        self,
        file_ops: list[FileOps],
        is_store: bool,
        ready_event: torch.Event,
    ) -> list[IOCompletion]:
        """...

        Args:
            ready_event: the device data is not valid until this event
                completes. Honor it with ready_event.synchronize() on an I/O
                thread, or stream.wait_event(ready_event) on a backend stream.
                Never wait on it on the calling thread.
        """
```

An event is the right currency because it is consumable **both** host-side and
stream-side. A pre-synchronized world, or a `bool already_safe`, would serve only
one backend shape.

Recording at submit time is correct even for deferred stores: the event lands
later in the stream than the producing kernels, so waiting on it is conservative,
never insufficient.

## Honoring it, per backend

| Backend | How it honors `ready_event` |
|---|---|
| `ThreadPoolFSWorker` (`pread`/`pwrite`, blocking `cuFileRead`/`Write`) | `ready_event.synchronize()` inside the pool task, before the I/O call |
| `cuFileReadAsync`/`cuFileWriteAsync` (stream-ordered) | `stream.wait_event(ready_event)` on its registered stream — no host wait at all |
| `cuFileBatchIOSubmit` (host-async, not stream-ordered) | `ready_event.synchronize()` on its submitting thread, before `cuFileBatchIOSubmit` |

In every case the engine thread pays only `Event.record()`.

## Companion change this requires

`submit_io` must not return `list[Future]`. Neither a device event nor a cuFile
batch handle is a `Future`, so a stream-ordered backend would have to park a
thread purely to resolve one. The tracking code only ever calls `done()` and
`result()`, so widen the type to that protocol:

```python
class IOCompletion(Protocol):
    def done(self) -> bool: ...
    def result(self, timeout: float | None = None) -> object: ...


class _StreamCompletion:
    def __init__(self, event: torch.Event):
        self._event = event

    def done(self) -> bool:
        return self._event.query()

    def result(self, timeout: float | None = None) -> None:
        self._event.synchronize()
```

`Future` satisfies this unchanged, so `ThreadPoolFSWorker` and the existing tests
don't move — and a stream-ordered backend then needs zero threads, with
`FSOffloadingWorker`'s completion tracking working untouched.

## Also needed for the thread-pool path

Pool threads must be bound to the right device, or `synchronize()` (and any
future `cuFileBufRegister`) attaches to device 0 on a multi-GPU worker. There is
no `set_device` anywhere in `vllm/v1/kv_offload/` today:

```python
        def _init() -> None:
            current_platform.set_device(device)
            if pool_initializer is not None:
                pool_initializer()

        self._pool = ThreadPoolExecutor(max_workers=max_io_threads, initializer=_init)
```

## Direction

Apply the event on loads as well as stores. The load path is currently safe
because `wait()`/`get_finished()` join host-side before the blocks are consumed,
but the target blocks can still be referenced by previously-enqueued kernels —
the hazard the CPU worker's `stream.wait_stream(current_stream())` covers for
free. One event per job removes the need for anyone to re-derive which direction
is safe, which is the derivation that broke here.

## Not solved by this

A stream-ordered backend will eventually want to publish the reverse edge on
loads, so compute does `wait_event(io_done)` instead of the engine joining
host-side. `IOCompletion` leaves room to add a device-event accessor later
without touching `submit_io`. Follow-up, not this PR.
