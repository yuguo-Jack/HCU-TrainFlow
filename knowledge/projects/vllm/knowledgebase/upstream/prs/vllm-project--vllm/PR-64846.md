# [Perf] Launch the Qwen GDN decode and Triton fused-MoE kernels with PDL

[Upstream PR](https://github.com/vllm-project/vllm/pull/64846) · state: open · merged: False

## Original PR description



## Overview

On SM90+, four Triton kernels on the decode path still use ordinary launches, so each one starts about 0.45 us after its predecessor finishes, even inside a CUDA graph: the Qwen GDN packed recurrent decode (`fused_recurrent_gated_delta_rule_packed_decode`), the Qwen3.5 gated RMS norm (`fused_gdn_gated_rms_norm`), the attention output gate (`fused_sigmoid_gate_mul`) and the Triton fused-MoE expert GEMM (`fused_moe_kernel`, two launches per MoE layer). This PR launches them with programmatic dependent launch (PDL), the same way `causal_conv1d_update` and the LoRA Triton ops already do: `launch_pdl=current_platform.is_arch_support_pdl()` at the launch and `gdc_wait()` before the first load. The kernels do not trigger their dependents early (no `gdc_launch_dependents()`): the trigger happens implicitly when the grid completes, which hides the launch latency without letting the next grid take SM slots while this one is still running. Off SM90, and on other platforms, `launch_pdl` is False and the code is unchanged.

PDL changes no math: every kernel still waits for its predecessor to complete and flush before it reads, so outputs are bitwise identical.

## Claims

- **`Qwen/Qwen3.6-35B-A3B-FP8`, H200 TP1:** median TPOT −3.2% at concurrency 1 (3.890 → 3.765 ms) and −1.1% at concurrency 8; output throughput +3.3% and +1.3%. At concurrency 32 TPOT is within the main run-to-run spread (+0.4%, throughput +0.9%).
- **`Qwen/Qwen3.8-27B-FP8` (dense, no MoE):** median TPOT −0.5% / −0.4% / −0.6% at concurrency 1 / 8 / 32. Small, but the main runs agree to within 0.05% at concurrency 1 and 8.
- **Where it comes from.** In a concurrency-1 decode step (1,194 kernels), the GPU idle time right before the four kernels drops from 56 to 17 us per step; the step goes from 3,863 to 3,750 us. At concurrency 32 the step goes from 8,187 to 8,125 us.
- **No math changes:** outputs and states are bitwise identical with and without `launch_pdl` for all four kernels. No new buffers, no change to CUDA graph capture.

## Details

- **Why no early trigger.** A first version also called `gdc_launch_dependents()` in the three GDN kernels once their inputs were loaded. At concurrency 1 that was no faster than the wait-only version, and at concurrency 32 it was 2-4% slower on both models (the next grid's blocks take SM slots while the recurrent kernel's 30k programs are still running). The wait-only version has no such regression, so the kernels rely on the implicit trigger at grid completion.
- **Launch sites (decode path).** Each of the four kernels is issued on the current stream directly after its producer, with no stream switch in between; the only auxiliary stream on this path (`in_proj_ba` in `QwenGDNLinearAttention.forward_cuda`) is joined before the core attention op. `fused_recurrent_gated_delta_rule_packed_decode` follows `causal_conv1d_update` in `QwenGDNLinearAttention._forward_core_decode_non_spec` (`vllm/model_executor/layers/mamba/gdn/qwen_gdn_linear_attn.py`). `fused_gdn_gated_rms_norm` follows the `torch.ops.vllm.qwen_gdn_attention_core` call (that recurrent kernel) in `forward_cuda` of the same file. `fused_moe_kernel` is launched through `invoke_fused_moe_triton_kernel` in `TritonExperts.apply` (`vllm/model_executor/layers/fused_moe/experts/triton_moe.py`): the w13 GEMM after `moe_kernel_quantize_input`, the w2 GEMM after `self.activation` and the second `moe_kernel_quantize_input`. `fused_sigmoid_gate_mul` follows `self.attn(q, k, v)` in `Qwen3NextAttention.forward` (`vllm/model_executor/models/qwen3_next.py`).
- **Early exits after `gdc_wait()`.** Two programs return right after the wait (padding rows in `fused_moe_kernel`, invalid state index in the packed GDN decode). They are correct with wait-only PDL and now carry a comment that an explicit `gdc_launch_dependents()`, if ever added, must also run on those paths.
- **Warmup.** `launch_pdl` is a constexpr, so it is part of the Triton compile key. None of the four kernels go through the Triton JIT warmup registry, so no warmup entry changes.
- **Not covered.** `act_and_mul`, `moe_sum` and the FlashInfer block-scale quant/GEMM chain are CUDA kernels in other code paths and are left for separate changes.

**Verified against `main`:**

- SM90+ gating is correct and the pre-Hopper / non-CUDA path is byte-identical to today. `launch_pdl` is a `tl.constexpr` defaulting to `False` in all four kernels, and `current_platform.is_arch_support_pdl()` (`cuda.py:742`, `major >= 9`) returns `False` off Hopper/Blackwell and on non-CUDA (base `interface.py` returns `False`), so the `if launch_pdl:` block — and the `gdc_wait()` inside it — is constant-folded away. No grid-dependent-launch attribute is set below SM90.
- The `gdc_wait()` is placed before the first memory load in every one of the four kernels (sigmoid-gate-mul, fused_moe, gdn-gated-norm, fused_recurrent), which is the PDL requirement that matters — the consumer can't read the producer's output before the wait. The wait-only form (no explicit `gdc_launch_dependents()`) relies on the implicit trigger at full-grid completion, matching the existing in-tree pattern in `causal_conv1d` / `dsv4_topk`, and your A/B showing the early-trigger variant regresses at concurrency 32 is a good justification for not adding it.

**Two non-blocking notes:**

1. A few programs run `gdc_wait()` and then take an early-return path (fused_moe's `pid_m*BLOCK_SIZE_M >= num_tokens_post_padded` return; fused_recurrent's `state_idx <= 0` zero-store return). Correct today under wait-only PDL, but if anyone later adds `gdc_launch_dependents()` it would have to be emitted on every exit path including these early returns — a one-line comment at those sites would prevent a future regression.
2. The overlap's correctness/speedup rests on each kernel actually being launched on the same stream immediately after its true producer on the decode path; that sequencing isn't in this diff, so reviewers can only take the bitwise-equality validation (24/24) as the evidence it holds. If you can point to the decode-path launch site that chains these, it'd make the producer→consumer assumption self-evident in review.
