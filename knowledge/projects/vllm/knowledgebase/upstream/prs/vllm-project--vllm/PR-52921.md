# [Bugfix] Align CPU offload pool size across PP/spec-decode workers

[Upstream PR](https://github.com/vllm-project/vllm/pull/52921) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

Fix CPU offload block-count mismatches between the scheduler and workers under uneven pipeline parallelism or speculative decoding, preventing out-of-bounds offload copies.

## Claims

- Workers synchronize the block count with MIN before allocating offload storage.
- The engine queries the aligned count only for enabled `SimpleCPUOffloadConnector` configurations, including `MultiConnector`, and requires a valid worker result.
- The scheduler uses that count directly. Removed the unused config-based fallback and per-worker config plumbing.

## Details

CI dependencies: merged main to include the AMD fixture fix in [#62869](https://github.com/vllm-project/vllm/pull/62869). Also cherry-picked only [`4ca9ef5ded05`](https://github.com/vllm-project/vllm/commit/4ca9ef5ded05b393c6a6978574dba4598a2dd543) from the still-open [#62879](https://github.com/vllm-project/vllm/pull/62879), preserving its author and provenance. Its 11-line test-script change waits for prefillers to be ready before starting decoders that share their GPUs, preventing overlapping memory profiling and weight loading. This addresses a Nixl CI failure also observed on main; GPU validation is pending CI. The dependency is already proposed upstream rather than being a separate new fix PR here.

Heavier PP ranks can store fewer blocks in the same byte budget, while the scheduler previously sized its pool using a lighter rank. The resulting block IDs could exceed a worker's allocation and crash a copy operation.

Workers derive capacity from live KV storage; the startup RPC transfers the aligned result to the scheduler. With offloading enabled, a missing result is an initialization error rather than a reason to estimate capacity again. The explicit `num_cpu_blocks` override remains supported.

This provides automatic alignment rather than requiring per-topology tuning such as InferenceX's `KV_OFFLOAD_MAX_CPU_BLOCKS` workaround. Open PRs were searched for matching SimpleCPUOffload/PP alignment work at initial submission; none matched this automatic fix.

- charxwu · comment · 2026-10-19T09:19:32Z · [source](https://github.com/vllm-project/vllm/pull/52921#issuecomment-6263886686)

Thanks @ivanium for the review, and for landing #61674 as a stopgap. I agree that touching engine core needs a strong justification. That said, I have two concerns about relying on an explicit `num_cpu_blocks` as the fix:

1. **It moves the framework's job to the user.** The correct count depends on the per-block bytes of the *heaviest* worker, which depends on model layout, TP/PP/DCP, KV dtype, and whether spec decode adds draft KV on the last stage. vLLM already computes this on every worker. In practice, users have to launch once, look for the smallest `SimpleCPUOffloadWorker [CPU]: ... CPU blocks` value across all ranks, then relaunch with that number. They also need to redo this whenever the deployment changes. And if they don't set it, the default path is still broken: the scheduler can still issue out-of-bounds block IDs, which shows up as a segfault in the copy kernel rather than a clear error.

2. **The knob is confusing.** From a user's point of view, `cpu_bytes_to_use_per_rank` already says how much memory to use. A second knob that overrides it with a block count, and is only needed because ranks may disagree internally, exposes an implementation detail. Users won't know when they need it until they hit a crash.

To address the intrusiveness concern, I'm happy to shrink this PR. One option is to keep everything inside the connector: when `num_cpu_blocks` is unset, workers do a MIN all-reduce in `register_kv_caches`. If ranks disagree, we fail fast at startup with an actionable message (e.g. `ranks disagree (809 vs 746); set num_cpu_blocks=746`). This adds no engine RPC and no scheduler changes, and turns the silent OOB into a clear startup error. Full auto-alignment would still need the aligned value to reach the scheduler, so I'd like your view on whether a minimal hook for that would be acceptable, or whether the fail-fast version is the preferred direction.
