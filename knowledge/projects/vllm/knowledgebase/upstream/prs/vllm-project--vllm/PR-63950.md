# [Bugfix][Kernel] Use padded intermediate size for non-gated FlashInfer b12x NVFP4 MoE

[Upstream PR](https://github.com/vllm-project/vllm/pull/63950) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Fix a first-forward crash in the FlashInfer b12x NVFP4 MoE backend (`moe_backend="flashinfer_b12x"`, SM12x) for non-gated activations (relu2) whose intermediate size is not a multiple of 128, e.g. `Nemotron-3.5-Lightning-30B-A3B-NVFP4` (`moe_intermediate_size=1856`). `B12xMoEWrapper` is now built with the padded intermediate size actually present in the prepared weights.

Complementary to #60069 (shared b12x workspaces across layers), which is needed separately to fit larger models on 32 GB cards. This PR does not include that change.

## Claims

- Fixes `RuntimeError: shape '[344064, 116]' is invalid for input of size 41287680` raised from FlashInfer's `_pad_intermediate_to_tile` on the first forward of non-gated NVFP4 MoE models with a non-128-aligned intermediate size on the `flashinfer_b12x` backend.
- No numerical change: the extra channels are zero padding that vLLM already adds during weight prep.
- Gated models and non-gated models whose intermediate size is already a multiple of 128 are unaffected (wrapper size unchanged).

## Testing

**Runs on CPU, and selected by CI.** `tests/kernels/moe/test_flashinfer_b12x_moe_prep.py` (new) has no SM12x guard. Random packed NVFP4 weights and block scales at Nemotron-like shapes (4 experts, hidden 2688) go through the real `FLASHINFER_B12X` preparation, `convert_to_nvfp4_moe_kernel_format` -> `prepare_nvfp4_moe_layer_for_fi_or_cutlass`, so the real scale swizzle and padding run. The test then builds `FlashInferB12xExperts`, runs `process_weights_after_loading` and `apply()`, and checks the `intermediate_size` passed to `B12xMoEWrapper`. That class is the only thing replaced, since its kernels need SM12x. The size must equal the prepared `w13` rows (1920 for relu2 1856) and `2 *` the `w2` packed columns. relu2 2048 and SiLU 1856 / 2048 must be unchanged. On a CPU-only machine two documented shims apply: `FusedMoEConfig` rejects non-gated layers off CUDA/ROCm/XPU, and `swizzle_blockscale` calls `.cuda()`. The test skips if `flashinfer.fused_moe` or `flashinfer.cute_dsl.utils` cannot be imported. The `(L4) MoE Kernels` step selects everything in `tests/kernels/moe`, so it should run there. It has not been run on an L4 yet.

## Details

**Root cause.** For the `FLASHINFER_B12X` backend, `prepare_nvfp4_moe_layer_for_fi_or_cutlass` swizzles `w13_weight_scale`, which rounds rows up to a multiple of 128. For non-gated activations it then zero-pads `w13` rows and `w2` / `w2_scale` columns to match (1856 -> 1920). `FlashInferB12xExperts._ensure_wrapper` still built `B12xMoEWrapper(intermediate_size=moe_config.intermediate_size_per_partition)`, i.e. 1856. FlashInfer then pads the already-padded scales again in `_pad_intermediate_to_tile`, and the MMA-layout reshape fails (`128 x 2688 x 120` elements; `120 x 16 = 1920`).

**Fix.** In `process_weights_after_loading`, for non-gated layers, set `intermediate_size_per_partition` to the row count of the prepared `w13` scale tensor, which equals the padded `w13` row count. This happens before the wrapper is lazily built. Gated layers are detected with `moe_config.is_act_and_mul` rather than by comparing activation names. They keep the configured size, because this prep path raises instead of padding gated weights.

**Known FlashInfer limitation (not addressed here).** FlashInfer's static path (routed rows <= 1024) pads `n` to a multiple of 256 and caches full padded copies of the weights, about 17 GiB for this model. That does not fit on a 32 GB card, so the end-to-end numbers above force the dynamic path with `FLASHINFER_B12X_STATIC_COMPACT_CUTOVER_PAIRS=0`. This is a FlashInfer follow-up.
