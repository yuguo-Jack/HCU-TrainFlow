## Overview

The CUDA `awq_dequantize` kernel ([`dequantize_weights`](https://github.com/vllm-project/vllm/blob/e2b672312328d3f95980f5b82869f7937194fd62/csrc/quantization/awq/gemm_kernels.cu#L352-L409)) wrote each thread's 8 dequantized halves as 8 scalar 2-byte stores. This PR writes them as a single 16-byte `uint4` store instead. The math is unchanged and the output is bitwise identical. On H100:

- The kernel is 2.44–3.66× faster across the Llama-3-8B layer shapes, going from 0.6–0.85 TB/s to about 2 TB/s.
- Serving `Meta-Llama-3.1-8B-Instruct-AWQ-INT4` with `VLLM_BATCH_INVARIANT=1`, TPOT drops from 34.9 to 16.0 ms at concurrency 1, and output throughput rises 1.85× at concurrency 32.
- GSM8K accuracy, greedy outputs and logprobs are unchanged.

A second, separate commit fixes two bugs in `benchmarks/kernels/benchmark_machete.py`. It packed the Marlin zero points with K instead of the number of groups, so its zero-point results were wrong. It also rejected every value of `--group-zero-type`.

## Details

**Root cause.** Each thread already holds its 8 output halves in a `uint4` register. The kernel copied that register into a per-thread array and then stored the 8 halves to global memory one at a time. The compiler kept the array in registers (ncu shows 0 local-memory sectors), so the cost comes entirely from the scalar stores. Neighbouring threads' outputs are 16 bytes apart, so each warp store instruction spanned 16 sectors but filled only 64 bytes of them. The kernel therefore issued 8× the store instructions and moved 8× the sector traffic. Warps stalled on full load/store queues (MIO/LG throttle) while DRAM throughput stayed at about 12% of peak, even with 83% achieved occupancy.

**Alignment.** `C_ptr2 = C + 8 * (col + row * N)` is a multiple of 8 halves. `C` is allocated inside the op, so the `uint4` store is always 16-byte aligned, for every `thx`/`thy` launch configuration.

**Who benefits.** The kernel's only caller is `AutoAWQLinearMethod` ([`auto_awq.py#L905`](https://github.com/vllm-project/vllm/blob/e2b672312328d3f95980f5b82869f7937194fd62/vllm/model_executor/layers/quantization/auto_awq.py#L905)). On CUDA, vLLM normally runs AWQ checkpoints with Machete or Marlin, but it disables Marlin under batch-invariant mode. In that mode every layer runs dequantize + matmul on every forward pass. Otherwise the kernel only runs for layers Marlin cannot take, at M ≥ 256. The default H100 serving path is unaffected (see the control above). The kernel is built only for CUDA.

**CI.** The new test runs in the existing L4 "Quantization Kernels" step, which runs `tests/kernels/quantization` when `csrc/quantization/` changes. All validation here was on SM90; the change does not depend on the GPU architecture.

**Follow-up.** The kernel now reaches about 60% of the 3.35 TB/s peak, with long-scoreboard stalls dominant. Each thread's 4-byte weight load is probably the next limit, so wider loads per thread would be the next step. Related work: #55462 profiles the separate `awq_gemm` kernel, which has a different bottleneck.

**Not a duplicate.** No open or merged PR changes `dequantize_weights`. #55532 changed the `awq_gemm` inner loop and was closed without merging.

**AI assistance.** Claude Code was used to help find the root cause, draft the change and the test, and run the profiling and benchmarks. I reviewed every changed line, reran the tests and benchmarks above, and ran my own ncu profiles.
