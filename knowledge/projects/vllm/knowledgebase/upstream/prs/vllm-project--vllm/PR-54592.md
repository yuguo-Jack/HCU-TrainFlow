# [Attention][DeepSeek-V4] Add SM90 Q8KV8 sparse MLA prefill

[Upstream PR](https://github.com/vllm-project/vllm/pull/54592) · state: closed · merged: False

## Original PR description



## Purpose

This PR adds an opt-in native SM90 Q8 x KV8 sparse MLA prefill path for
DeepSeek-V4 on the NVIDIA FlashMLA backend.

The existing prefill path gathers the packed DeepSeek-V4 FP8 KV cache into a
BF16 workspace before calling FlashMLA. The new path instead:

1. gathers and requantizes the UE8M0 paged cache directly to OCP E4M3;
2. converts the BF16 query to OCP E4M3 in a reusable workspace;
3. maps padded sparse indices to a zero sentinel row; and
4. runs a native SM90 Q8KV8 sparse MLA kernel with attention-sink and
   variable-top-k support.

The kernel is adapted from the SGLang/FlashMLA implementation with its source
license retained. It is registered through the libtorch stable ABI as
`torch.ops._C.sparse_mla_q8kv8_prefill_sm90` and is built only for `sm_90a`
with CUDA >= 12.3.

Runtime selection is fail-closed and default-off through
`AttentionConfig.use_deepseek_v4_q8kv8_prefill`. Enabling it requires:

- an exact SM90 NVIDIA GPU;
- BF16 model activations;
- the FlashMLA DeepSeek-V4 sparse backend; and
- the canonical `fp8_ds_mla` KV-cache layout.

The existing BF16 gather + FlashMLA path remains unchanged when the option is
disabled.

## Test Plan

All Python invocations used the repository `.venv` and all GPU work ran through
Slurm on NVIDIA H20-3e (`sm_90`, CUDA 13.0).

```bash
# Incremental CUDA build and stable-op registration check
.venv/bin/cmake --build cmake-build-q8kv8-gcc13 \
  --target _C_stable_libtorch --parallel 32
.venv/bin/cmake --install cmake-build-q8kv8-gcc13 \
  --component _C_stable_libtorch

# Native kernel/reference and sentinel tests
.venv/bin/python -m pytest \
  tests/kernels/attention/test_flashmla_sparse.py -k q8kv8 -vv

# Packed-cache BF16/direct-FP8 gather tests
.venv/bin/python -m pytest \
  tests/kernels/test_compressor_kv_cache.py \
  -k dequantize_and_gather_k_cache -vv

# Configuration parsing
.venv/bin/python -m pytest \
  tests/engine/test_arg_utils.py::test_attention_config -vv

# Correctness-gated CUPTI microbenchmark
.venv/bin/python \
  benchmarks/kernels/benchmark_q8kv8_sparse_mla_prefill.py --batch-size 4

# Repository checks
pre-commit run --all-files
pre-commit run --from-ref upstream/main --to-ref HEAD
pre-commit run mypy-3.12 --all-files --hook-stage manual
```

The benchmark uses CUDA graphs and CUPTI activity timing, performs warmup
outside the measured region, and fails closed when CUPTI is unavailable. Its
timed boundary includes packed-cache gather/requantization, query conversion,
and sparse attention for the Q8 path; the shared index-construction work is
excluded from both paths.

## Test Result

### Build and focused tests

- Incremental build succeeded; the SM90 op registration check returned `True`
  (Slurm job 2037).
- Native Q8KV8 tests: `3 passed` for 64/128 heads, partial top-k,
  attention-sink handling, finite statistics, and repeatability.
- Cache gather tests: `2 passed`; the direct OCP E4M3 output matches the
  reference conversion exactly on valid rows.
- AttentionConfig test: `1 passed`.
- Full pre-commit, rebased-diff pre-commit, manual mypy 3.12, `compileall`, and
  `git diff --check` passed.

### Production `_forward_prefill` A/B

The real DeepSeek-V4 FlashMLA `_forward_prefill` method was exercised on an
H20 with identical compressed/SWA paged caches, sparse indices, and metadata.
The baseline arm used BF16 gather + FlashMLA; the candidate arm used direct
E4M3 gather + sentinel + Q8KV8.

Configuration: query length 128, sequence length 192, 64 heads, top-k 64.

| Metric | Q8KV8 vs BF16 FlashMLA |
| --- | ---: |
| Mean absolute error | 0.00005155 |
| P99 absolute error | 0.00027466 |
| Max absolute error | 0.00070190 |

Both outputs were finite and the integration gate passed (Slurm job 2055).

### Full-model evaluation note

A deterministic DeepSeek-V4-Flash-0731 TP4 comparison was attempted with a
fixed 4096-token prompt, eight greedy output tokens, and chosen-token
logprobs. The shared `vllm-h20-02` node emitted NVIDIA Xid 13/43
`Out Of Range Address` faults on three devices during initialization. The Xid
records belonged to PIDs outside this evaluation's worker PID set, and the
engine exited before either arm produced tokens. Therefore this PR does not
claim generated-token/logprob parity or model-level latency from that run.

To avoid substituting an invalid result, correctness was instead verified on a
different, clean H20 through the production `_forward_prefill` A/B described
above. The full deterministic model comparison should be repeated when a clean
four-GPU node is available.
