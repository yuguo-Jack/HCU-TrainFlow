# [Bugfix] Fix wrong output when the MoE ops are piecewise splitting ops

[Upstream PR](https://github.com/vllm-project/vllm/pull/61179) · state: open · merged: False

## Original PR description



## Overview

Fixes #61150. With PIECEWISE CUDA graphs, adding `vllm::moe_forward` / `vllm::moe_forward_shared` to `splitting_ops` gives wrong decode output. With this change the graph is split at new `_with_output` variants of the MoE ops instead. These write into outputs allocated in the graph, the way `unified_attention_with_output` does.

## Claims

- With the MoE ops in `splitting_ops`, greedy output is token-identical to the default split (attention only), with FX-level splitting and with Inductor graph partition. Covered: `moe_forward` on both model runners, `moe_forward_shared` on the V2 runner.
- The graph is still split at the MoE op, so the MoE layers still run outside the CUDA graphs.
- Nothing changes unless the MoE ops are in `splitting_ops`. The default path still calls `moe_forward` / `moe_forward_shared`, with the same output and throughput.

## Details

**Root cause.** `moe_forward(_shared)` returns a freshly allocated tensor. As a splitting op it runs eagerly between two captured graphs. On replay, the graph after the MoE op reads its input from the address it had at capture time, but this step's MoE output is somewhere else.

The default splitting ops avoid this because they write into buffers passed in from the graph before them. `CUDAGraphWrapper` only checks replay input addresses with `VLLM_LOGGING_LEVEL=DEBUG`, so normally the output is silently wrong.

This is the general problem from #37363 (closed). It is also the "outputs do not seem to have consistent addresses" issue in #30910, which reverted the automatic MoE split for DeepEP HT.

**Fix.**
- `moe_runner.py` adds two ops, `moe_forward_with_output` and `moe_forward_shared_with_output`. They run the existing op body, copy the result into the outputs passed in (`mutates_args`), and return `None`.
- When the matching name is in `splitting_ops`, `MoERunner._select_forward` returns a small wrapper. The wrapper allocates the outputs in traced code with the existing fake impls, calls the new op, and returns the outputs. The allocation lands in the graph before the split, so its address belongs to that graph and is the same on every replay.
- `compilation.py`: `set_splitting_ops_for_v1` maps `vllm::moe_forward` / `vllm::moe_forward_shared` (with or without `.default`) to the new names, so existing configs keep working. This runs only in `VLLM_COMPILE` mode, the only mode where `splitting_ops` is used.

**Cost.** One device copy of the MoE output per MoE layer per step (two with shared experts). It happens only when the MoE ops are in `splitting_ops`, including the case where CUDA graphs end up disabled.

**Not changed.**
- TPU and CPU still call the Python functions directly.
- The deferred-finalize path (Kimi-K3) calls `_forward_impl` directly and doesn't go through these ops.

**Related.**
- #37190 (MoE expert CPU offload, open) adds the MoE ops to `splitting_ops` itself. It works around this bug with a persistent per-layer copy (`_maybe_stabilize_output`), and it checks for `"vllm::moe_forward" in splitting_ops`. After this change it would need to check the new names, and could then drop its workaround.
- #52383 (open) moves activation padding into the MoE op and renames the ops' `hidden_dim_unpadded` argument. It fixes a different bug. Whichever of the two lands second needs that rename in the new ops too.

**Duplicate check.** No open PR references #61150 or adds an output-argument MoE op. I searched for `61150`, `moe_forward`, `moe_forward_with_output` and `splitting_ops`.
