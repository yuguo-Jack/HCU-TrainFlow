# [ROCm][Perf] Add native per-token FP8 Triton linear backend and RDNA4 tuning

[Upstream PR](https://github.com/vllm-project/vllm/pull/61091) · state: open · merged: False

## Original PR description

## Purpose

Add a native Triton per-token FP8 scaled-MM linear backend, with tuned configurations for Radeon AI PRO R9700 / gfx1201. Select it with `--linear-backend triton` for dynamic per-token activation scales and per-channel weight scales.

Related: [#60672](https://github.com/vllm-project/vllm/pull/60672), which enables the existing AITER per-token FP8 backend. This PR provides the vLLM-native implementation and keeps its tuning configurations in vLLM.
this fixes the regression in #57838 without disabling the working but slower `RowWiseTorchFP8ScaledMMLinearKernel` in #57861

The per-token FP8 runtime lives in `linear/scaled_mm/triton.py`, reuses the existing shared Triton scaled-MM kernel, and supports BF16/FP16 output, bias, compiled dynamic shapes, and graph replay. Tile and scheduling choices live in configuration files, with guarded fallbacks for unsupported layouts and unmeasured shapes. The per-token backend is registered only for ROCm and requires `current_platform.supports_fp8()`.

## Validation

Test environment: Radeon AI PRO R9700 / gfx1201, Torch 2.13 with ROCm 10, and Triton 3.8. Model: `RedHatAI/gemma-4-12B-it-FP8-Dynamic`.

Validation covers operator correctness, backend selection, compiled execution, graph replay, strided scales, and tile/layout boundaries. Kernel comparisons use identical FP8 operands and scales against Torch RowWise, with quantization excluded from the timings. Serving performance compares Torch RowWise and native Triton with the same attention backend and AITER linear disabled.

```bash
uv run pytest \
  tests/kernels/quantization/test_triton_scaled_mm.py \
  tests/kernels/quantization/test_scaled_mm_kernel_selection.py \
  -k 'not rocm_compressed_tensors_w8a8'
```

Operator and backend-selection tests, rerun after simplifying the tests: **152 passed, 1 deselected** (INT8 checkpoint smoke test excluded by the command above). Pre-commit checks passed. The simplification removes launch-recording fixtures, exact tuning-policy assertions, and redundant large-shape cases while retaining numerical correctness, compiled dynamic shapes, graph replay with mutated inputs/scales, strided scales, and operand-boundary coverage. The shared Triton kernel and tuning configurations are unchanged from the benchmarked version. The fresh serving comparison below completed **480 successful requests**, with no errors or incomplete requests.

Benchmark correctness validation uses `torch.testing.assert_close` with `rtol=atol=1e-2`. **44 cases** (11 installed shapes × M=1/64/256/2048) passed for both heuristic and tuned paths. BF16/FP16 smoke checks passed, and injected mismatches and non-finite outputs were rejected.

### Accuracy validation

GSM8K accuracy was evaluated with vLLM's `tests/evals/gsm8k/gsm8k_eval.py` on the full **1,319-question** test set: **5-shot**, greedy decoding (`temperature=0`, seed 42), chat completions with thinking disabled, a 1,024-token output limit, and 32 concurrent requests. Both runs used **TP2**, **FP8 KV cache**, and default serving settings, changing only `--linear-backend`. Attention was selected automatically (`TRITON_ATTN`); no attention or AITER environment override was used. Evaluated PR commit: `bf64ce9836f2`.

| Backend | Correct / questions | Accuracy | Invalid answers |
|---|---:|---:|---:|
| Torch RowWise | 1,255 / 1,319 | 95.15% | 0 |
| Native Triton | 1,251 / 1,319 | 94.84% | 0 |

Triton minus Torch RowWise: **-0.30 percentage points**. In the paired comparison, Triton answered 13 questions correctly that Torch missed, and missed 17 questions Torch answered correctly. Triton answered 4 fewer questions correctly in this single run. All **2,638 evaluation requests** completed successfully; 0 responses reached the output-token limit. These results cover this model and GSM8K configuration; other models and platforms need separate evaluation.

This accuracy comparison uses default attention. The TP1 serving performance measurements below use explicitly selected `ROCM_AITER_UNIFIED_ATTN`.

To reproduce, start each server separately, using `torch` for the baseline and `triton` for the candidate:

```bash
vllm serve RedHatAI/gemma-4-12B-it-FP8-Dynamic \
  --tensor-parallel-size 2 \
  --kv-cache-dtype fp8 \
  --linear-backend torch
```

Run the evaluator against each server:

The shared `triton_scaled_mm` changes do affect existing INT8 callers, so I checked end-to-end Quark INT8 inference against the original shared implementation.

The Quark INT8 route is `QuarkW8A8Int8.apply_weights` → `TritonInt8ScaledMMLinearKernel.apply_weights` → INT8 activation quantization → `triton_scaled_mm` → `scaled_mm_kernel`. It retains the default launch policy and skips `_get_scaled_mm_launch_policy`; the new FP8 tuning-config loader is not on this route. `_scaled_mm_tile_coords` runs as compiled Triton.

I ran [Gemma 4 12B Quark W8A8 INT8](https://huggingface.co/rajasingh012/gemma-4-12b-it-quark-w8a8-int8) on two AMD Radeon AI PRO R9700 GPUs (gfx1201) with TP2, default cuda graph mode.  Both cases explicitly select the existing Triton INT8 backend. 

The run was testing using the same benchmark configs in the Pr Message above.

| Streams | Per-request output TPS change | Mean TTFT change | Mean end-to-end latency change |
|---:|---:|---:|---:|
| 1 | +0.15% | −4.70% | −0.29% |
| 2 | +0.67% | −10.06% | −0.93% |
| 4 | +0.63% | −8.72% | −1.22% |
| 8 | −1.63% | +4.86% | +2.50% |

Positive TPS changes and negative latency changes improve performance. Runtime logs confirm over 16,000 FULL graph replays in each case. Replay bypasses repeated Python wrapper/launch work inside captured regions; uncaptured prefill and other serving overhead remain.

The measured serving impact is small in this graph-enabled Quark test, with no consistent slowdown across stream levels.

For the CUDA CUTLASS path, I also inspected checkpoint/config coverage. When CUTLASS is selected, the shared wrapper uses native CUTLASS if the weight's K and N dimensions are multiples of 16. The FP8 CUTLASS linear backend also pads weights and activations to satisfy this alignment. Grouping the inspected checkpoints by architecture, size, and precision gives three distinct examples:

| Model group (representative checkpoint) | Evidence for avoiding the shared Triton fallback |
|---|---|
| [Gemma 4 12B FP8 Dynamic](https://huggingface.co/RedHatAI/gemma-4-12B-it-FP8-Dynamic) | Local checkpoint inspection: all 328 FP8 matrices have aligned K/N dimensions. |
| [Qwen2.5-VL 3B W8A8 INT8](https://huggingface.co/lsm0729/Qwen2.5-VL-3B-Instruct-quantized.w8a8) | Published configs: quantized text-layer dimensions are aligned; vision layers are excluded from INT8. Groups the inspected 3B W8A8 and SmoothQuant variants. |
| [Qwen2.5-VL 7B W8A8 INT8](https://huggingface.co/RedHatAI/Qwen2.5-VL-7B-Instruct-quantized.w8a8) | Published configs: quantized text-layer dimensions are aligned; vision layers are excluded from INT8. Groups the inspected RedHatAI, lsm0729, and zzen0008 variants. |

For these inspected models, the shared Triton changes are unlikely to affect the CUDA path through the alignment fallback. Irregular INT8 layers and irregular direct FP8 wrapper inputs can still reach Triton, but with default cuda graph capture enabled it seems the small launch overhead is negligible.
