# [ROCm][Perf] Add native per-token FP8 Triton linear backend and RDNA4 tuning

[Upstream PR](https://github.com/vllm-project/vllm/pull/61091) · state: open · merged: False

## Original PR description

## Overview

Add a native Triton per-token FP8 scaled-MM linear backend, with tuned configurations for Radeon AI PRO R9700 / gfx1201. Select it with `--linear-backend triton` for dynamic per-token activation scales and per-channel weight scales.

Related: [#60672](https://github.com/vllm-project/vllm/pull/60672), which enables the existing AITER per-token FP8 backend. This PR provides the vLLM-native implementation and keeps its tuning configurations in vLLM.
this fixes the regression in #57838 without disabling the working but slower `RowWiseTorchFP8ScaledMMLinearKernel` in #57861

## Claims

The per-token FP8 runtime lives in `linear/scaled_mm/triton.py` and supports BF16/FP16 output, bias, compiled dynamic shapes, and graph replay. It uses tuned configurations when available and a hardware-aware untuned heuristic on FP8-capable RDNA. The heuristic selects shared, contiguous, split-K, or persistent launches using shape, processor count, and last-level data-cache capacity; unsupported operands retain the shared fallback. The per-token backend is registered only for ROCm and requires `current_platform.supports_fp8()`.

### Earlier R9700 retuning (`dba246dd44`; historical)

In `dba246dd44`, retuned the 11 existing BF16-output N/K families on both R9700/gfx1201 GPUs at M=1,2,4,...,32768: 176 search points, with **103 tuned entries and 73 explicit heuristic fallbacks**. A measured entry applies only at its exact M; unmeasured token counts retain the production heuristic. Existing tables without the new flags preserve their previous nearest-M behavior. The tuner now compares the actual RDNA heuristic and exports a tuned entry only above its minimum gain (default 2% and 0.15 µs).

Independent measurements use the actual runtime backends, fresh inputs, shuffled paired rounds, and graph/eager timing after compilation. Across 352 anchor GPU-case records:

| Measurement | Speedup vs heuristic-only | Speedup vs Torch RowWise |
|---|---:|---:|
| Captured graph GPU time | 1.030× | 1.799× |
| Batched eager completion | 1.004× | 1.708× |
| CPU submission | 0.883× | 0.982× |

The selected tuned points alone average 1.051× graph speedup over the heuristic. Unmeasured-M and rotating-weight controls are retained, including adverse samples and followups. Host lookup adds about 13.2% CPU submission latency versus heuristic-only; these are primarily graph-serving optimizations.

### Earlier untuned RDNA heuristic update (2026-10-29, before retuning)

The earlier heuristic update included the work through `0435cb2d20`. Backend eligibility does not require a tuning file. RDNA devices with FP8 support use the new heuristic; existing tuned maps take priority within their covered token-count ranges. Processor count and cache capacity are read during backend initialization, and selections/compiled launchers are cached. That earlier update did not change tuning JSON files; the retuning above replaces them. There is no custom FP8 startup warmup: ordinary graph preparation and first-use JIT compile the required variants.

### Accuracy validation

GSM8K accuracy was evaluated with vLLM's `tests/evals/gsm8k/gsm8k_eval.py` on the full **1,319-question** test set: **5-shot**, greedy decoding (`temperature=0`, seed 42), chat completions with thinking disabled, a 1,024-token output limit, and 32 concurrent requests. Both runs used **TP2**, **FP8 KV cache**, and default serving settings, changing only `--linear-backend`. Attention was selected automatically (`TRITON_ATTN`); no attention or AITER environment override was used. Evaluated PR commit: `bf64ce9836f2`.

| Backend | Correct / questions | Accuracy | Invalid answers |
|---|---:|---:|---:|
| Torch RowWise | 1,255 / 1,319 | 95.15% | 0 |
| Native Triton | 1,251 / 1,319 | 94.84% | 0 |

Triton minus Torch RowWise: **-0.30 percentage points**. In the paired comparison, Triton answered 13 questions correctly that Torch missed, and missed 17 questions Torch answered correctly. Triton answered 4 fewer questions correctly in this single run. All **2,638 evaluation requests** completed successfully; 0 responses reached the output-token limit. These results cover this model and GSM8K configuration; other models and platforms need separate evaluation.
