# [Bugfix] Fix Gemma 4 encoder CUDA graph capture OOM at startup

[Upstream PR](https://github.com/vllm-project/vllm/pull/61365) · state: closed · merged: True

## Original PR description

## Overview

Fixes #61045.

With `cudagraph_mm_encoder` on, Gemma 4 made every encoder CUDA graph capture buffer far bigger than any batch its token budget can hold. Because of this, `nvidia/Gemma-4-26B-A4B-NVFP4` ran out of memory at engine start on a 32 GB GPU. This PR captures one graph per budget and per row width (70, 140 or 280 soft tokens). Each graph gets only as many rows as the budget can fill, so no capture buffer is larger than `budget * 9` patches.

Compared with #61092, this fix:

- Fixes the reported startup OOM. [61092](https://github.com/vllm-project/vllm/pull/61092) limits the number of rows but keeps every row 2520 patches wide. On the reported setup, [61092](https://github.com/vllm-project/vllm/pull/61092) still dies in encoder CUDA graph capture (`Tried to allocate 662.00 MiB ... 8.43 GiB allocated in private pools`), both with the issue's flags and with images only.
- Makes video graph output match eager output (mean cosine 0.9994). On [61092](https://github.com/vllm-project/vllm/pull/61092) the graph rows stay 2520 patches wide but the replay gathers at 630, so video output stays wrong.
- Adds 4 CPU test cases. They fail on the old code and also on [61092](https://github.com/vllm-project/vllm/pull/61092). [61092](https://github.com/vllm-project/vllm/pull/61092) adds no test.

## Claims

- With the issue's flags, `nvidia/Gemma-4-26B-A4B-NVFP4` now starts on 1x RTX 5090 32 GB: 21 encoder graphs, 2.61 GiB CUDA graph pool. Before: OOM at startup (`Tried to allocate 6.69 GiB`).
- The images-only variant (`--limit-mm-per-prompt '{"image": 1, "video": 0}'`) also ran out of memory at startup before. It now starts and serves images.
- Encoder graph output now matches eager output for video and for batches of 70-token and 140-token images. On the old code these outputs were wrong.
- The change is only in `vllm/model_executor/models/gemma4_mm.py` (+49/-10). It uses the existing `capture_axes` support of the encoder CUDA graph manager. The manager and other models do not change.

## Details

Root cause: the Gemma 4 encoder graph takes pixels as `(rows, patches_per_row, 768)`, with one image or video frame per row. `prepare_encoder_cudagraph_capture_inputs` made this buffer too large in both dimensions:

1. Rows: it used `max(max_batch_size, max_frames_per_batch)` for every budget. With video on, that is `58 * 32 = 1856`. But every row is at least 70 soft tokens, so a batch that fits 4096 tokens has at most 58 rows.
2. Width: every row had the width of the widest image, `min(budget, 280) * 9 = 2520` patches. A video frame, or a 70-token image, needs only 630.

So the 4096-token graph got a `(1856, 2520, 768)` bf16 buffer of 7,184,056,320 bytes: the 6.69 GiB in the issue. The first operation of the patch embedder needs another tensor of the same size. Limiting only the rows is not enough. The 4096 graph then still runs the vision tower on about 4 times the patches its budget can hold and takes 8.57 GiB of graph pool, and the next budget's warm-up runs out of memory. The width problem alone also breaks image-only configs, where every budget of 280 or more gets 58 rows of 2520 patches.

The fix, all in `gemma4_mm.py`:

- `get_encoder_cudagraph_config` declares one capture axis: the row width in soft tokens, `(70, 140, 280)`, up to the configured maximum.
- `select_encoder_cudagraph_items` returns the batch's row width as the axis key: 70 for video frames, and the padded width for images.
- `prepare_encoder_cudagraph_capture_inputs` builds rows of exactly that width, and `min(max(max_batch_size, max_frames_per_batch), max(1, budget // width))` rows. The one-row minimum is there only so that capture works when one row is wider than the budget.
- The replay pads list images of mixed widths to the widest one. So `get_encoder_cudagraph_item_specs` sets `path_output_tokens` to that widest width, and the manager never packs more rows into a batch than its graph has. `output_tokens` stays the real count and is still used to slice the output. Note: the docstring of `EncoderItemSpec.path_output_tokens` says single-path models leave it empty. Gemma 4 now sets it on its one path, for this reason.

The graph row width now equals the replay gather width. That is why video and narrow-image graph output, which were wrong before, now match eager.

Trade-offs:

- With the issue's flags, encoder graphs go from 7 to 21, one per budget and width. 3 of them can never be replayed: budget 70 with widths 140 and 280, and budget 140 with width 280. Each is one row. Skipping them would need a change to the manager's capture loop.
- In a config that already worked (images only, budgets `[280, 1120, 2240]`, 4 items per batch), the graph pool grew from 0.93 to 1.12 GiB and the KV cache shrank from 7.71 to 7.46 GiB. This was measured before the final row-count change.
- A list of images of mixed widths is packed at its widest width. It can need a bigger budget, or run eagerly when no budget fits it. The output stays correct.

Not changed here. These are older defects that are the same before and after this PR, and each needs a different change:

- Video frames with padding (for example 320x240, 63 real tokens per frame): the graph path counts the padding slots, so its output is longer than eager output (2240 against 2016 tokens) and later frames are shifted.
- Images with `max_soft_tokens` 560 or 1120 crash when `cudagraph_mm_encoder` is on, because the vision config has no `num_soft_tokens` attribute.
- `Gemma4UnifiedForConditionalGeneration` fails at encoder graph capture.
