# [Bugfix] Make PyTorch top-k tie-breaking deterministic

[Upstream PR](https://github.com/vllm-project/vllm/pull/62379) · state: open · merged: False

## Original PR description



## Overview

Make the PyTorch top-k/top-p fallback resolve exact ties by lower token ID. Top-k filtering retains exactly k finite candidates when available, before any subsequent top-p filtering. This follows up on closed, unmerged #50979 and the sampling consistency work in #42259.

**Draft for discussion of the semantic change and CPU cost:** CPU top-k-only took **1.924x** the original implementation's time on captured model inputs and **2.684x** on BF16-quantized synthetic inputs. These are CPU tensor microbenchmarks, not serving throughput.

## Claims

- Both PyTorch paths select the same deterministic top-k support, including cutoff ties, without mutating the caller's k/p tensors or perturbing retained logits.
- The sorting path keeps the ascending cumulative-probability calculation, resolves top-p ties consistently, and preserves disabled p=1 rows even when softmax tails underflow.
- Restore exact top-k comparison against Triton for ordinary inputs, with explicit mask, fixed-noise sampling, and parameter-preservation regressions. This does not claim universal agreement with every backend's degenerate-row safety fallback.

## Details

The old implementation filters with `logit < kth_value`, which retains all tokens tied at the cutoff. The sorting path also leaves tie order unspecified. Stable descending sort followed by a flip provides ascending values with higher IDs first among ties; positional top-k masking therefore keeps the lower IDs. The existing ascending top-p cumulative sum is retained rather than changing its numerical behavior near p=1.

For CPU top-k-only, inspect one extra candidate to skip tie scans when no cutoff splits a tie. When a tie is split, the selected cutoff-tie IDs bound a prefix containing enough ties; cumulative ranks within that prefix choose the lower IDs. The prefix can approach the full vocabulary and affect the whole batch, explaining the performance risk. New host reads are CPU-only; the GPU helper retains its pre-existing synchronization constraint.

The contract intentionally changes the common keep-all-cutoff-ties convention and needs maintainer agreement. Since #54651 removed the GPU batch threshold, the motivation is fallback/platform consistency, not restoring a CUDA batch-size boundary. Triton and FlashInfer kernels are unchanged. The relaxed comparison introduced by #60726 is tightened for ordinary top-k inputs; no blanket rollout-determinism claim is made.

Duplicate-work checks on 2026-10-19 found #50979 closed and unmerged and no open PR referencing it. Related #48913 optimizes sorting while retaining threshold semantics, and #41598 handles the V1 k=1 special case; neither defines deterministic support for general k. The patch also applies cleanly to the checked main revision `38127f629025`; GPU results above still refer to the tested source base, not a new run on main.
