# [Perf] Qwen GDN: fold in_proj_ba into the in_proj_qkvz GEMM

[Upstream PR](https://github.com/vllm-project/vllm/pull/62961) · state: closed · merged: False

## Original PR description

## Overview

This PR speeds up decode on Qwen3.5-architecture models by removing work from every gated delta net (GDN) layer and from Model Runner V2's per-step attention metadata. On Qwen3.8-27B at TP4 on B300, decode at batch 1 is **5.8% faster without speculation and 5.6% faster with MTP**. It is independent of #62800, #62962, #62963 and #62964.

At batch 1 a GDN decode step is a long chain of short kernels plus host-side metadata work, so each GEMM, copy or metadata build it drops shows up directly in per-token latency. With this PR each GDN layer runs one projection GEMM instead of two and reads its gates in place, the one-shot fused all-reduce and RMSNorm triggers PDL completion early on FlashInfer 0.7.2 and newer, and the full-attention KV cache groups of one spec share one metadata build.

## Claims

- `in_proj_ba` runs inside the `in_proj_qkvz` GEMM. Per GDN layer at one token (Qwen3.8-27B shapes at TP4 on B300, CUDA graph, cold L2), the two GEMMs take 9.98 us and 3.72 us, and the fused GEMM takes 10.05 us.
- Packed decode reads the `b` and `a` gates as strided views, which removes one copy kernel of about 1.3 us per GDN layer and step. This part comes from #51954 and is credited below.
- The spec-decode gated RMSNorm reads the output gate in place through a shared-weight mode of `layer_norm_fwd`. At 16 verify rows it takes 2.73 us per layer instead of 6.36 us, and its output is bitwise equal from 1 to 16384 rows.
- With FlashInfer 0.7.2 or newer, the one-shot fused all-reduce and RMSNorm triggers PDL completion early, which saves 1.9 us per all-reduce at TP2 and 1.4 us at TP4. #45448 moved the trigger to the end because of a stale read that FlashInfer 0.7.2 fixes, and older FlashInfer versions keep the end trigger.
- Model Runner V2 shares attention metadata across the full-attention KV cache groups of one spec, as it already does for Mamba groups (#58762) and as the V1 runner does. Qwen3.8-27B at TP4 has 6 full-attention groups, so each step makes 5 fewer metadata builds.

I served 33 SPEED-Bench prompts one at a time (greedy, 384 new tokens, thinking off) on Qwen3.8-27B at TP4 on 4x B300, with Model Runner V2 and prefix caching off, and started the servers in base, PR, PR, base order. Both builds ran on upstream `main` at `40210d8317`, the PR build with this PR's commits only. The per-kernel timings under Claims were measured on the earlier base `56e67b46a3`.

| MTP, 3 tokens | 503.8 / 504.7 | 533.2 / 532.2 | +5.6% |

Each cell is the median per request on one server, two servers per build, and higher is better. Mean MTP acceptance length stays close, 3.13 and 3.11 on the base servers against 3.06 and 3.08 with this PR. The MTP servers log no inference-time JIT warning, and each no-speculation server, base included, logs one for `_fused_post_conv_kernel`.

The fused GEMM rounds bf16 differently, so greedy outputs change, while the gate, norm and PDL changes are bitwise neutral. 9 of 33 prompts match base exactly, which is close to how often base at batch 1 matches base at batch 16 (7 of 33), and each build reproduces itself across restarts (33 of 33). On GSM8K (first 500 test questions, zero-shot chat, greedy, two servers per build), base scores 94.4% and 95.0% and this PR 94.6% and 95.4%.

For the PDL change, I called the fused op the way vLLM's pass does (bf16, 16 x 5120, one-shot, PDL on) and compared every output bitwise with the same step without PDL. FlashInfer 0.7.2 gives 0 stale reads in 50 steps at TP2 and in 200 at TP4, eager and in CUDA graphs. With FlashInfer's fix reverted, the same chain reads a stale residual in every step. This is a synthetic reproducer, separate from #45448's Kimi-K2.6 plus EAGLE-3 setup.

## Not a duplicate

I ran the duplicate-work searches from `AGENTS.md` §1 (open PRs, with keywords for `in_proj_ba`, GDN gate copies, the gated norm, PDL and `trigger_completion_at_end`, metadata reuse, GDN state indices and `flashinfer_cutedsl` GEMMs). Apart from #51954, this PR uses no code from the related PRs below.

- #51954 (packed decode reads the gates in place) is included as its own commit with its original author. If #51954 lands first, this commit drops out.
- #57318 routes the separate `in_proj_ba` GEMM to FlashInfer `mm_bf16` for small batches, as an opt-in. This PR folds that GEMM away on the unquantized, TP-sharded CUDA path, and #57318 still applies to the quantized, LoRA and Marlin-replicated paths that keep it. Both edit the same lines in `forward_cuda`.
- #41457 and optimization 3 of #55260 also remove the separate `ba` GEMM, through a 6-way `MergedColumnParallelLinear` with a new checkpoint mapping and through a fold for Qwen3-Next's interleaved layout. This PR folds after weight loading, so the loaders, the `in_proj_ba` module, LoRA and the quantized paths stay as they are.
- #58851 (cross-group reuse inside the GDN, Mamba and KDA builders) and #52297 (GDN batch-level spec metadata once per step) cover the per-group GDN and Mamba metadata cost. This PR extends #58762's reuse to full-attention groups, which neither covers. #58851 moves the same reuse code out of `update_block_table`, and #60426 (metadata reuse for AITER MLA and KDA on ROCm) lifts the same `MambaSpec`-only check in `attn_utils.py`, so whichever of these lands second rebases.
- #50279 fuses the GDN decode RMSNorm with a strided SiLU gate on SM103. This PR lets the spec-decode gated norm read the output gate in place, on every CUDA architecture. Both touch the gate tensor in `qwen_gdn_linear_attn.py`.
- #61577 lowers FlashInfer CuTeDSL BF16 GEMMs above 32 tokens to aten. This PR leaves GEMM routing as it is.

## Details

- The fold appends the `ba` rows to `in_proj_qkvz`'s weight after loading, and both layers keep views of the fused tensor, so the weight loaders stay as they are. The fused rows are zero-padded to a multiple of 16, so the output's row stride stays divisible by 16 like an unfused output, and Triton kernels that read these views reuse the specialization compiled at warmup and graph capture.
- The shared-weight norm mode is a `SHARED_WEIGHT` constexpr in the JIT key, and the Qwen Triton warmup compiles the new keys.
- Metadata is shared only between groups with the same effective KV spec and builder type and no per-group inputs (`per_group_common_attn_kwargs` marks encoder-decoder cross attention). The reuse path refreshes the group's kernel-mapped block table before `update_block_table`, as a normal build does, so groups whose manager page is larger than the kernel page get kernel page ids. Without the refresh, 32 of the 64 kernel-page cases in `test_attn_utils.py` fail (16 on CPU, 16 on CUDA).
- #62962 (speculative-method registry) moves the same gate copy in `QwenGatedDeltaNetAttention._forward_core` for its own path. The two PRs merge without conflicts, and whichever lands second drops the resulting second pair of `b.contiguous()` and `a.contiguous()` calls.

@gau-nernst is right that the side stream covers more checkpoints. The fold applies only when both projections are unquantized and `in_proj_ba` is TP-sharded, so I'd keep it as a fast path on top of #64425, with the fused GEMM where it applies and the side stream everywhere else.
