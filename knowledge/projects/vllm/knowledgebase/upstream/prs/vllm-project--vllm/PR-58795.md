# [CI] Prebuild mamba-ssm and causal-conv1d from pinned commits in a torch-keyed test-image stage

[Upstream PR](https://github.com/vllm-project/vllm/pull/58795) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Trunk change: needs line-by-line review. It changes the CUDA test image every CI job uses and the commands of three test steps.

Three NVIDIA jobs, `Language Models (Hybrid)`, `Granite Language Model Compatibility` and `Language Models (Extended Generation)`, compile `mamba-ssm` and `causal-conv1d` from source before pytest on every run. This PR builds them once in the test image instead, so the jobs only verify them. It takes over @khluu's #52333; his three commits are kept with authorship.

The earlier revision of this PR built them at the end of `test-deps`. That layer reruns whenever any test or runtime requirement changes: 31 commits on `main` in the last 30 days. Each of those reruns would also have redone the ~14-minute extension build, delaying every job in that CI build. This revision keys the build on the torch versions only; they changed once in the same 30 days.

## Claims

- The three jobs run the verifier and pytest, with no source builds.
- The extensions rebuild only when the torch, torchvision or torchaudio version (the stage copies all three from `base`; they change together), the pinned commits, the build-tool list, the build script, the toolchain stage or a build argument such as `max_jobs` changes. A requirements-only change leaves them cached.
- Both are fetched by commit SHA (`mamba` v2.3.0 = `f1493ff6`, `causal-conv1d` v1.6.0 = `da6dbaa9`), not by tag.
- Nothing they declare as a dependency is installed. Their runtime dependencies come only from the hash-pinned `requirements/test/cuda.txt`, and their build tools from a new hash-pinned list.

## Validation

- `tests/tools/test_dependency_pins.py`: 9 new tests pass. They check that the verifier and the build script pin the same commits, that every build tool has a hash, and the verifier's pass and fail paths. A mutation run on the verifier leaves no surviving mutants.
- `pre-commit run` on the changed files passes, including mypy, the Dockerfile graph and `docker/versions.json`. `docker build --check` reports no new findings beyond one known false positive for a repeated `ARG`.
- CI:
  - [x] [#99812](https://buildkite.com/vllm/ci/builds/99812) (`/ci run`, cold): `hybrid-test-wheels` built in about 6 minutes, compiling only sm_80 and sm_90, alongside the vLLM CUDA compile, which took longer, so it did not delay any test. Hybrid (both shards) and Granite passed; each verifier line shows both commits, and no test logged transformers' "falling back to its reference PyTorch implementation" warning for these packages. The one failure, an Entrypoints Unit shard (`test_shutdown.py` timeout), is unrelated.
  - [x] [#99858](https://buildkite.com/vllm/ci/builds/99858) (a throwaway commit touching only `requirements/test/cuda.in`, since removed): every `hybrid-test-wheels` step was `CACHED`; `test-deps` reran and installed the wheels in about a second. Granite and Extended Generation passed with the same verifier lines and no fallback warnings.
  - [x] [#99976](https://buildkite.com/vllm/ci/builds/99976) (`TORCH_NIGHTLY=1`): the wheels built against torch `2.16.0.dev20261102` with no warning, the nightly test image installed them, and Granite passed on that image with the same verifier line and no fallback warnings. The H200 jobs in that build never started: a host hook pre-pulls the plain commit tag, which only exists when a normal image build has run for the same commit, as it always has on `main`. H200 is covered by the two builds above.
- Both builds still rebuilt the vLLM CUDA extensions, because `base`'s torch install bind-mounts all of `requirements/`, so any file there changes its cache key. That predates this PR, and this stage is not affected by it.

## Details

**Decisions to check**
- **A separate stage, not a step in `test-deps`.** `base` is split at its slow-changing section into `base-toolchain` (OS packages, compilers, uv, Python) and `base`, which is otherwise unchanged. `hybrid-test-wheels` starts from `base-toolchain` and copies only `torch_lib_versions.txt` from `base`. A copied file is cached by its contents, so requirement changes in `base` do not invalidate the stage. Starting it from `base` instead would rebuild it about as often as the earlier revision did.
- **Fail the image build if the extensions fail to build.** The earlier revision only warned, but a step that warns is cached as a success, and the image would then lack the extensions until torch next changed. Rebuilds happen about once a month, so a failure is rare and visible. The exception is the torch-nightly image build: its torch changes every run and it has no layer cache, so a failure there warns, leaves the wheels out, and fails only the three jobs (at their verifier) rather than the whole nightly run. A compile failure repeats exactly, so the build does not retry it; only the GitHub fetch is tried twice.
- **Compile for sm_80 and sm_90 only.** Upstream hard-codes 9 targets on CUDA 13. Only these jobs load the extensions, through the transformers reference path, and they run on L4 (sm_89 runs sm_80 code) and H200. The one Blackwell hybrid test, `v1/e2e/test_hybrid_chunked_prefill.py`, has no transformers reference.
- **Hash-pinned build tools in their own small list** (`requirements/build/hybrid-test-deps.txt`) instead of `requirements/build/cuda.txt`, which has no hashes and leaves `ninja` and `wheel` unpinned. The list has no pre-commit hook; regenerate it with the command in its header.
- **torch is the same exact version `base` installed, without a hash check,** the same as in `base` today.
- **arm64 and Rubin images skip the build.** No job on those images runs these tests.
- **The stage honours `max_jobs`**, like the vLLM build stage, since on a rebuild the two compile at the same time.

**Also changed:** the CPU test image copies in `requirements/build/hybrid-test-deps.txt`, since the CPU tools step runs the new tests. Changes to the build script, the build-tool list or the verifier now trigger the three jobs and the CPU tools step. The Hybrid job drops its Git HTTP/1.1 setting, which only its source installs needed.

**Unchanged:** AMD mirrors and `test-amd.yaml`; the ROCm image already builds its own mamba fork. Release images (`vllm-openai`) do not include `test-deps`, so they never build this stage.

**Not done:** the torch-nightly image build has no layer cache at all, so it rebuilds this stage on every run, along with everything else.
