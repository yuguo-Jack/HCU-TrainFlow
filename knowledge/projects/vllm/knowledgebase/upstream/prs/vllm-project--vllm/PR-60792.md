# [Bugfix][Frontend] Align DeepSeek V4.1 images with rendered content

[Upstream PR](https://github.com/vllm-project/vllm/pull/60792) · state: closed · merged: True

## Original PR description

## Overview

Fix Python DeepSeek V4.1 rendering when tool results reorder image placeholders or thinking mode drops historical developer content. Carry source image indices through the native encoder and apply the resulting order to both image data and UUIDs.

This follows the source-order approach of #56366, which fixed the Rust frontend only.

## Claims

- Out-of-order tool results keep their own images after sorting into tool-call order.
- Images belonging to dropped developer content no longer reach multimodal prompt expansion without a placeholder.

## Details

The encoder already decides which content survives and in what order it renders. Image indices now follow those same merge/sort/drop operations; the renderer does not duplicate those policies or scan text for image markers. The V4.1 renderer applies the order to media and UUIDs together. Existing prompt fixtures and rendering parity checks retain the encoded text.

Duplicate checks covered open PRs, the related Rust PR's changed files and discussion, and V4.1 frontend searches. #56366 changes Rust files only; #60522 only moves Python imports and does not fix this behavior. No matching Python fix was found.

- robertgshaw2-redhat · comment · 2026-10-17T22:51:13Z · [source](https://github.com/vllm-project/vllm/pull/60792#issuecomment-6242587401)

What this fixes: the assistant calls two tools, `red` then `blue`, and the results come back in the other order, each with an image.

```python
[{"role": "assistant", "tool_calls": [call("red"), call("blue")]},
 {"role": "tool", "tool_call_id": "blue", "content": [text("blue"), image("blue")]},
 {"role": "tool", "tool_call_id": "red",  "content": [text("red"),  image("red")]}]
```

The encoder sorts tool results into call order, so the prompt reads `<tool_result>red <image>` then `<tool_result>blue <image>`.

**Broken (main):** images are passed in message order, `[blue, red]`, so each result gets the other result's image.

**Fixed (this PR):** images follow the prompt order, `[red, blue]`.

Verified with `test_tool_images_follow_rendered_order`: it fails on main (`['blue', 'red'] != ['red', 'blue']`) and passes here.


- robertgshaw2-redhat · comment · 2026-10-17T22:54:46Z · [source](https://github.com/vllm-project/vllm/pull/60792#issuecomment-6242635595)

The official DeepSeek encoder had this bug too and fixed it on 2026-10-16 ([`314113f`](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash/commit/314113f8a7dadb388215396ba5fbee2c610a04d6), also in the 1017 release). It now sorts tool results before collecting images, so on the case above it returns `['red.png', 'blue.png']`, the same as this PR.

The approach differs: the reference encoder collects the images itself and returns them in prompt order, while vLLM collects them earlier, so this PR records each image's index and reorders afterwards.
