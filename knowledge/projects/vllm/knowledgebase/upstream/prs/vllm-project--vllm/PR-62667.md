# [Frontend] Support sanitize_control_tokens in chat templates

[Upstream PR](https://github.com/vllm-project/vllm/pull/62667) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Let chat requests encode control tokens written in message content as plain text, so that only the chat template can emit them. Examples are a literal `<|im_end|>` or `<think>` in `reasoning_content`, a tool result, or tool call arguments. This wires up `apply_chat_template(..., sanitize_control_tokens=True)` from huggingface/transformers#47386 (released in transformers 5.20.0), and applies the same marking to vLLM's own tokenizers and renderers.

## Claims

- `--sanitize-control-tokens` (or `LLM(sanitize_control_tokens=True)`) sanitizes every chat request, and requests cannot turn it off. Without the flag, a single request can opt in with `chat_template_kwargs={"sanitize_control_tokens": true}`. Default behavior is unchanged.
- Covered renderers:
  - HF chat templates
  - DeepSeek-V3.2/V4/V4.1, Kimi-Audio and Cohere, which build prompts in Python or Rust
  - Mistral, Kimi-K3 and Terratorch, which never turn message text into control tokens
  - Inkling, which now always encodes message text as ordinary tokens in both the Python and Rust frontends
- HF chat templates reject multimodal requests whose chat template content format is `"string"`. vLLM inserts the placeholders into the message text, so they would be sanitized too.

## Details

**Root cause.** For HF tokenizers, the online and offline chat paths render the template with `tokenize=False` and then encode the whole prompt string. At that point the boundary between template text and message text is lost, so any added-token spelling in a message is matched as that token. Calling `apply_chat_template(tokenize=True)` alone does not help, since transformers' default implementation also renders first and encodes the whole string.

**Flow.**

- `vllm/config/model.py`, `vllm/engine/arg_utils.py`: `ModelConfig.sanitize_control_tokens` / `--sanitize-control-tokens`, next to the other renderer option `renderer_num_workers`. Excluded from the compile hash.
- `vllm/renderers/base.py`: with the flag on, `render_chat` / `render_chat_async` force `sanitize_control_tokens=True` into `chat_template_kwargs`, overriding the request. These two are the only callers of `render_messages`.
- `vllm/renderers/hf.py`: when the kwarg is set, force `tokenize=True`, the same override `prompt_embeds` already uses. transformers only sanitizes while tokenizing. The kwarg reaches transformers through the existing `resolve_chat_template_kwargs` allow-list, as it is part of `apply_chat_template`'s signature.
- `vllm/tokenizers/control_tokens.py` (new, ~30 lines): `mark_chat_control_tokens` / `encode_marked_prompt` wrap transformers' `mark_control_tokens` / `encode_marked_chat`. There is no Jinja template to scan, so every non-whitespace added token counts as a control token.
- `vllm/tokenizers/deepseek_v32.py`, `deepseek_v4.py`, `deepseek_v41.py`, `kimi_audio.py`, `vllm/renderers/cohere.py`: mark the messages and tools (Cohere: the whole melody config except `template_jinja`) before rendering, then encode the rendered prompt with `encode_marked_prompt`.
  - V4.1 marks before `_normalize_messages`, which inserts the trusted image tokens.
  - Kimi-Audio gains `_encode_without_added_tokens`, which `encode_marked_chat` needs.
- `vllm/renderers/inkling.py`, `rust/src/chat/src/renderer/inkling/mod.rs`: message text is encoded with `_encode_without_added_tokens` / Rust `encode_ordinary`, matching what the Kimi-K3 Rust renderer already does. Structural tokens are emitted separately, so this applies unconditionally. It changes Inkling's default tokens only for messages that contain literal structural tokens.
- `requirements/common.txt`: raise the transformers floor to 5.20.0. The cap was already raised to `< 5.21.0` in #61983, and CI runs 5.20.2. With older transformers the kwarg would be dropped silently by the allow-list, and the marking helpers would not exist.

**Duplicate check.** No open issue or PR covers this. #31735 (closed, unmerged) tried a vLLM-side placeholder scheme in the since-removed `entrypoints/chat_utils.py`. This PR instead reuses the upstream transformers implementation, so vLLM and training frameworks that call `apply_chat_template` tokenize identically. #11691 (closed) only touched `/tokenize` and split the template's own special tokens too.

**Limitations / follow-ups.**

- Relies on transformers internals: `_get_control_token_patterns` and `_encode_without_added_tokens` are private, and `mark_control_tokens` / `encode_marked_chat` are not documented API. They are pinned by the `< 5.21` cap.
- Multimodal requests with the `"string"` content format are rejected under sanitize on HF templates. A follow-up could mark the text before vLLM inserts the placeholders.
- `trust_remote_code` tokenizers that override `apply_chat_template` are not sanitized unless their own code handles it.
- Not covered:
  - `/score` and `/rerank` with a score template (`pooling/scoring/io_processor.py`)
  - one structured-decisions strategy (`openai/decisions/strategies.py`)
  - the Rust frontend

  They call `apply_chat_template` directly or don't read the flag.
- Templates can still parse message text themselves, e.g. GLM splits a past assistant `content` on `</think>` when `reasoning_content` is absent.
- Unrelated pre-existing issue found while testing: `KimiAudioTokenizer.apply_chat_template` passes a single conversation to `render_jinja_template`, which expects a batch, so message contents are dropped. Left for a separate PR.

- fengyuli-dev · comment · 2026-10-20T23:29:09Z · [source](https://github.com/vllm-project/vllm/pull/62667#issuecomment-6304123984)

Verified the DeepSeek-V4.1 path of this PR (head b5c9488) against a workaround we run in a DeepSeek-V4.1-Flash (1017 checkpoint) deployment. Our workaround encodes `<think>`, `</think>` and `｜DSML｜` in message text as ordinary tokens.

With the 1017 tokenizer, `apply_chat_template(..., sanitize_control_tokens=True)` returns exactly the same token IDs as our workaround in every case it covers. That holds with thinking on and off:
- a plain prompt;
- a user message quoting `<think>`/`</think>`;
- a user message quoting `<｜DSML｜ calls>` with tools;
- a tool result containing `</think> <｜DSML｜ calls>`.

This PR also sanitizes turn tokens such as `<｜User｜>`, which our workaround leaves alone. So the comment in #62724 that this PR leaves DeepSeek unsupported doesn't match this head.

Why it matters for this model: without sanitizing, a prompt that quotes `<think>`/`</think>` gives the model real control tokens. The model then writes `</think>` as the control token inside its reasoning (6–21 times per answer in an A/B of 6 each, against 1 with the tags encoded as text). Reasoning ends after about 130–320 characters, and the rest spills into `content`. On the live endpoint this went from 0 of 12 correct answers to 20 of 20 once the tags were encoded as text.

One interaction for DeepSeek: with the option on, the model writes a quoted `<｜DSML｜ calls>` as ordinary text. The `deepseek_v41` parser matches DSML by text, so it treats that text as a tool-call opener and drops everything after it. In a streamed example, reasoning stopped at "The opener is", and neither the rest of the reasoning nor the answer came back. #56661's `validate_tool_preamble` option, enabled for `deepseek_v41`, fixes this; details in that PR.

- BorisLoveDev · comment · 2026-11-01T17:55:22Z · [source](https://github.com/vllm-project/vllm/pull/62667#issuecomment-6561684444)

Thanks for this, the input side looks right to me. I think the output side needs the same treatment, at least for DeepSeek-V4.1, otherwise a model can still forge structure just by writing the marker text.

**Why V4.1 is exposed.** The DSML markers are not single tokens. `<｜DSML｜ calls>` encodes as `<` + `｜DSML｜` (id 128825, an added token, not special) + ` calls` + `>`. So the `token_id_terminals` entries for the DSML markers never resolve to a token ID, and the parser engine matches them by text. `</think>` is a single token (128822), and main already guards it.

**What I reproduced on current main (8530a77), real V4.1 tokenizer, both streaming via `ParserManager` and `DeepSeekV41Parser.parse` with token IDs:**
- A tool call written with ordinary tokens (for example, the model quoting an example call) becomes a real tool call.
- The same text inside reasoning ends reasoning early.
- DSML tags written as text inside a string argument cut the value and add a fake parameter.

**What I think a fix needs:** trust a DSML marker only where its `｜DSML｜` arrived as token 128825, and track those offsets through the lexer and into tool-argument parsing. Without token IDs, keep today's text matching. I tried this and hit several traps worth knowing about:
- Offsets must be exact. Binding token IDs to text with `rfind` puts a genuine marker on a later text copy. A UTF-8 character split across deltas (emoji) is enough to trigger it.
- The reasoning-to-tool handoff passes only the current delta's IDs, while the text can hold a marker assembled from earlier deltas.
- Stop-string holdback makes the text lag behind the IDs by a few characters.
- Non-streaming through `ParserManager` drops `model_output_token_ids`, so it stays text-only until #50676 or #60256 lands.

DeepSeek-V4 uses the same `｜DSML｜` token, so it likely has the same gap.

Would you prefer to cover this here, or should it go to a separate PR? I have a work-in-progress branch with regression tests for the cases above and can open it as a follow-up.
