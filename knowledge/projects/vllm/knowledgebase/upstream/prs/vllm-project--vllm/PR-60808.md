# [Bugfix][KV Connector][ROCm] MoRIIO READ: await every read before the forward

[Upstream PR](https://github.com/vllm-project/vllm/pull/60808) · state: open · merged: False

## Original PR description

## Overview

MoRIIO READ loads KV synchronously (`load_kv_async=False`), so the decode worker posts every READ in `start_load_kv` and must not run the forward until they land. Main awaits all of them only when the forward context says FULL; otherwise it awaits only mamba/KDA reads and leaves attention to the per-layer `wait_for_layer_load` hook. Two cases fall through:

- **MRv2 FULL replay.** `pre_forward` runs before `run_fullgraph` with no forward context (`gpu/model_runner.py`), so `start_load_kv` sees mode NONE and awaits only KDA reads, and the per-layer hook never runs inside the graph. All attention-side reads (MLA, indexer K, kpool tail) can still be in flight when the graph consumes them. #60636 addresses this case by passing the FULL context.
- **PIECEWISE / eager.** Indexer caches (`DeepseekV32IndexerCache` and subclasses) never call `wait_for_layer_load`, so their reads are never awaited.

This PR awaits every READ posted in the step inside `start_load_kv`, in every cudagraph mode, and makes `wait_for_layer_load` a no-op (kept because the base method is abstract). Attention-only failures no longer stop the wait early, so one request's failure can't let the forward run on another request's in-flight reads; hybrid still fails fast and raises.

## Validation

## Details

**Tradeoff.** Steps that admit a transferred request outside FULL lose per-layer overlap; the added wait is bounded by the transfer tail that overlapped the forward. It is a host wait on RDMA completion statuses, no device sync, and only runs when the step has sync loads and posted reads. Steady-state decode is unchanged.

**Failure semantics.** Attention-only: the barrier waits for every request's reads (bounded by `transfer_timeout`) and failed requests are reported via `get_block_ids_with_load_errors`. Hybrid: fail fast and raise, since HMA load-error recovery is unsupported. Not changed here: a read still pending at `transfer_timeout` is reported at `recv_abort_timeout`, as on main.

**Relation to #60636.** Complementary. #60636 fixes the MRv2 FULL context; it does not cover indexer reads outside FULL. With both, FULL steps already await everything and this PR adds the non-FULL coverage.

> @MIR-AMD @whx-sjtu In general wouldn't WRITE mode offers better overlap and performance? I have been seeing many READ mode PRs these days. Just wonder what are your thoughts?

@tjtanaa  I think both READ & WRITE have tradeoffs, and both are needed.

**WRITE: overlaps better**. P pushes each layer during prefill and D loads asynchronously, so the transfer hides behind prefill compute.
**READ saves decode kvcache memory**. In WRITE, D has to allocate the blocks and send their ids to P before P can push, so D holds them while P is still prefilling. In model that is running kvcache bound(many models in https://kvcache.ai/tools/kv-cache-size-calculator/), the idle reservation shrinks the decode batch and hurt the performance. 
Which one wins depends on whether decode is bound by KV capacity or by TTFT, so I think keep both is need.

Also related: The connector-agnostic KV checksums in #62211 would catch this class of bug like this PRs.

I agree that timeout swallowing predates this PR, but applying one deadline to every layer also widens its impact. For example, let `T = transfer_timeout`: A’s layer 0 read stays pending past `T`, while B’s layer 0 is complete and B’s layer 1 completes at `1.5T`. The previous non-FULL per-layer waits still held B until its layer 1 completed; the new global wait exits at T, and B’s layer 1 hook is now a no-op.
`_pop_done_transfers()` sees B as `PENDING`, so it reports no invalid blocks before `recv_abort_timeout`. If B subsequently completes, it is released successfully without invalidating the forward that consumed incomplete KV. I reproduced this difference using the actual base/head methods with deterministic clock/status doubles.
Could we make the global-timeout path prevent pending reads from feeding the forward—for example, fail the step closed while any reads remain pending—and add a deterministic regression covering this case? Safe cancellation/recovery would also work, but merely marking blocks invalid while RDMA can still write into them would need additional lifetime handling.
