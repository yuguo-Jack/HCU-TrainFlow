# [Bugfix][KV Connector][ROCm] MoRIIO READ: await every read before the forward

[Upstream PR](https://github.com/vllm-project/vllm/pull/60808) · state: open · merged: False

## Original PR description

## Overview

MoRIIO READ loads KV synchronously (`load_kv_async=False`), but outside a FULL target forward it awaited only mamba/KDA reads before the forward and left the rest to the per-layer `wait_for_layer_load` hook. That hook misses the sparse-attention indexer caches and drafter forwards that replay a FULL graph, so a decode step could read KV still arriving over RDMA. This awaits every READ posted in the step inside `start_load_kv`, in any cudagraph mode, and makes `wait_for_layer_load` a no-op.

## Claims

- **Connector-only net deletion** (`moriio_connector.py`, +27 / −75, net −48): no core/scheduler/model-runner/model changes.
- **Supersedes the per-layer hook from #48534 and is strictly safer** — it awaits a superset of today's behavior (all reads, every mode, vs. only mamba reads outside FULL), so no previously-correct step regresses.
- **Prevents** two misses main has outside a FULL forward: (a) indexer K / kpool tail caches (`DeepseekV32IndexerCache` and subclasses — GLM-5.x, DeepSeek-V3.2) that have no `@maybe_transfer_kv_layer` hook; (b) MTP/EAGLE drafter forwards, which pick their own cudagraph mode and can replay FULL (hook skipped) after a PIECEWISE target. Symptom: intermittent long-context recall misses under P/D.
- Steady-state decode (no new transfers) does no extra work; FULL forwards are unchanged.

## Validation

Lint: `pre-commit` + `mypy-3.12` pass.

## Details

**P/D flow.** D's scheduler admits a READ request with `load_kv_async=False` → `has_sync_kv_loads=True`, so the worker calls `start_load_kv` **before** the forward; `_read_blocks` posts one RDMA READ per layer (attention, indexer K, kpool tail, KDA, MTP). `_await_reads_issued_this_step` then awaits them. Before this PR it awaited all reads only on a FULL target forward; in PIECEWISE/NONE only `Attention`/`MLAAttention` layers called `wait_for_layer_load`, so the indexer read its caches mid-flight, and a FULL drafter forward skipped the hook entirely.

**Why `start_load_kv`.** It is the only connector call that is both outside any graph and before the forward on sync-load steps (`KVConnectorModelRunnerMixin`; MRv2 `ActiveKVConnector.pre_forward`). Async connectors (NIXL/Mooncake) don't hit this — they hold the request in `WAITING_FOR_REMOTE_KVS`. Correctness rests on the eager handshake covering every referenced engine (so reads are always posted on the sync-load step, not a later post-forward one); this PR adds an assert on that invariant.

**Tradeoff.** Non-FULL steps that admit a transferred request lose per-layer overlap; the added latency is at most the forward compute that overlapped the transfer tail. It is a host wait on RDMA completion statuses — no stream/device sync. Fires only when `has_sync_kv_loads` and ≥1 read was posted.

## Not a duplicate

- #58968 **closed**; #53250 **merged** (in base, no overlap); #54301 **open** — makes READ async (the competing direction; larger lifecycle change). #48534/#51052/#59164 (merged) define the current READ flow; this supersedes #48534's forward-time hook.

## Limitations (pre-existing)

- The lazy background-handshake fallback is unreachable on current main (the eager handshake covers every engine — now asserted); a single-token prompt reports 0 external tokens, so its step has no sync load.
