# [Structured Outputs] Make `auto` pick one backend per server instead of per request

[Upstream PR](https://github.com/vllm-project/vllm/pull/62877) · state: open · merged: False

## Original PR description



## Overview

With the default `structured_outputs_config.backend="auto"`, each request picks its backend from its own content: xgrammar first, then guidance or outlines when xgrammar rejects the constraint. EngineCore keeps a single backend, the one the first structured request chose, so a request's outcome depends on the traffic before it. Before #49625 a request that resolved to the other backend was compiled by the wrong one, silently dropping constraints or failing with HTTP 500; since #49625 it is a 400. This PR makes `auto` choose one backend per server from the tokenizer alone, so every request on a server names the same backend and the result no longer depends on request order.

## Claims

- `auto` resolves to `guidance` for Tekken-based Mistral tokenizers and to `xgrammar` for every other tokenizer, for every request. It no longer falls back per request.
- A constraint the selected backend cannot enforce (for example a JSON schema with `multipleOf` under xgrammar) is rejected with the backend's validation error (400), on a fresh server and after any other traffic alike. Selecting `guidance` explicitly restores it.
- On Tekken Mistral servers, the Lark grammars the Mistral tool parser generates and the server's JSON schema and regex requests all use guidance, instead of mixing guidance (Lark) and xgrammar (everything else).

## Validation

## Details

**Why per request is the wrong granularity.** `StructuredOutputManager` builds one backend from the first structured request and #49625 now rejects requests naming another one. Under the old `auto`, a server receiving both an xgrammar-compatible schema and a `multipleOf` schema answered the second one differently depending on which came first:

| First request | Then a `multipleOf` schema (resolves to guidance) | Then a plain schema (resolves to xgrammar) |
|---|---|---|
| plain schema (xgrammar) | 400 (backend mismatch) | 200 |
| `multipleOf` schema (guidance) | 200 | 400 (backend mismatch) |

The tokenizer is fixed for the server's lifetime, so resolving from it gives one backend per server, consistent with what EngineCore can serve.

**Why Tekken Mistral selects guidance.** The Mistral tool parser emits llguidance-dialect Lark for grammar-capable Mistral tokenizers, and the xgrammar backend declares no special tokens for Mistral tokenizers, so a regex like `.` can match `[TOOL_CALLS]` as text (#58321). Before this PR only those Lark grammars went to guidance; JSON schema and regex requests on the same server went to xgrammar, so Mistral servers mixed backends too. Guidance handles both.

**Behavior change.** Requests that relied on the fallback are now rejected under `auto`:
- JSON schemas with keywords xgrammar does not enforce (`multipleOf`, `uniqueItems`/`contains`, unsupported string `format`s, `pattern` with length bounds, ...), and regexes or grammars xgrammar cannot compile. They previously worked only while the engine had not latched xgrammar.
- Non-Tekken Mistral requests that fell back to outlines.

`--structured-outputs-config.backend guidance` (or `outlines`) selects those backends for the whole server. The removed fallback also leaves `has_guidance_unsupported_json_features` unused, so it is deleted.

**Migration.** This changes the default behavior, so it could instead first ship one release in which `auto` still falls back but logs a deprecation warning naming the backend to configure. The rejection message is the selected backend's own; an `auto`-specific hint pointing to `--structured-outputs-config.backend` could be added.

**Rust frontend.** vllm-project/vllm#62456 gives the Rust frontend the same model: one configured backend, `auto` meaning xgrammar. The Rust frontend does not load Mistral tokenizers, so the Tekken rule does not apply there.

**Not a duplicate.** No open PR changes how `auto` resolves. #49625 (merged) rejects mismatched backends in EngineCore; #62246 (draft) would let EngineCore hold several backends, which would allow request-level selection later.
