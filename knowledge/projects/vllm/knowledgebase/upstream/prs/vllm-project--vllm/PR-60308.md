# [Bugfix][Frontend] Return 400 for images rejected by Pillow's bomb check

[Upstream PR](https://github.com/vllm-project/vllm/pull/60308) · state: open · merged: False

## Original PR description

## Overview

`ImageMediaIO.load_bytes` lets Pillow's `DecompressionBombError` escape, so an image above Pillow's pixel limit gets an HTTP 500 from the API server. This converts it to a `ValueError` like the other undecodable-image errors, so the client gets a 400.

Fixes #60303

## Claims

- A 23 KB PNG of 14000x14000 pixels (196M pixels, above the 178,956,970 default of both Pillow's 2x limit and `VLLM_MAX_IMAGE_PIXELS`) changes from `500 InternalServerError` to `400 BadRequestError`.
- `ImageMediaIO.load_bytes` now raises `ValueError` for these images instead of `PIL.Image.DecompressionBombError`, so `MediaConnector.fetch_image`, `fetch_image_async` and the `video/jpeg` frame path of `VideoMediaIO.load_base64` report them as client errors too.
- No change to which images are accepted or rejected, and no change to the `VLLM_MAX_IMAGE_PIXELS` check.

## Details

Root cause: `Image.open` calls Pillow's `_decompression_bomb_check`, which raises `Image.DecompressionBombError` for an image above `2 * Image.MAX_IMAGE_PIXELS` (178,956,970 pixels by default). That class derives from `Exception`, not `OSError`, so the `except (OSError, Image.UnidentifiedImageError)` in `ImageMediaIO.load_bytes` does not catch it. The raw exception propagates through `MediaConnector.fetch_image_async` and `AsyncMultiModalItemTracker.resolve_items`, and `create_error_response` has no mapping for it, so it falls through to `InternalServerError` (500). A `ValueError` takes the `BadRequestError` (400) branch.

The default `VLLM_MAX_IMAGE_PIXELS` (178,956,970) equals Pillow's 2x threshold, and Pillow's check runs inside `Image.open`, before the `VLLM_MAX_IMAGE_PIXELS` check. So with default settings an oversized image is always stopped by Pillow first, and the 400 that `VLLM_MAX_IMAGE_PIXELS` is meant to provide (see `docs/usage/security.md`) is only reachable once the variable is lowered. The variable does not change Pillow's limit, so raising it or setting it to `0` leaves the same 500.

The fix adds `Image.DecompressionBombError` to the exception tuple, so the message is reported as `Failed to load image: ...` with the original exception chained. It is the same treatment #38253 gave truncated and corrupt images.

Scope and limits:

- Pillow's own limit stays in force. Images between `Image.MAX_IMAGE_PIXELS` and twice that still only produce Pillow's `DecompressionBombWarning` and load as before.
- Only the exception type seen by callers changes. Nothing is decoded that was not decoded before.

Not a duplicate. I searched `vllm-project/vllm` issues and PRs, open and closed, for `DecompressionBombError`, `decompression bomb`, `DecompressionBombWarning`, `VLLM_MAX_IMAGE_PIXELS`, `MAX_IMAGE_PIXELS`, `ImageMediaIO` and `oversized image 500`, and listed open PRs matching `multimodal/media/image.py`, `decompression bomb image` and `Pillow image error`. Nothing covers this bug. Closest hits:

- #47010 (merged) added `VLLM_MAX_IMAGE_PIXELS` and the pixel check in `load_bytes`. It does not handle the exception Pillow raises from `Image.open`.
- #38253 (merged) returned 400 for corrupt or truncated images. It covers `OSError` and `UnidentifiedImageError` only.
- #56527 (closed issue) is a 500 from malformed EXIF in `MultiModalHasher.serialize_item`, a different code path.
- #57752 (open, marked "Don't merge", `needs-rebase`) is an experiment that moves media decoding into the multimodal processor. It keeps the same `except (OSError, Image.UnidentifiedImageError)` tuple, so it does not address this and would need the same one-line addition if it lands.
