# [Perf][Kernel] Vectorized MLA KV-cache write for large launches

[Upstream PR](https://github.com/vllm-project/vllm/pull/59289) · state: closed · merged: False

## Original PR description

## Overview

In short: `concat_and_cache_mla` writes each token's latent row (`kv_lora_rank` elements) and rope row (`pe_dim` elements) into the MLA KV cache, on every layer of every MLA model, in prefill and decode. The kernel copies one element per thread with one 512-thread block per token, so prefill-sized launches are latency-bound: on main, 16K tokens move 38 MB in 46 us, which is 0.8 TB/s on a 3.35 TB/s H100. This PR adds vector variants of the kernel and of its grouped form. The launchers use them from 512 tokens (plain cache) and from 1024 tokens (fp8 cache). Below these thresholds the existing kernels run unchanged.

On an H100 SXM:
- From 1024 tokens the kernel is 1.25-3.5x faster than main. Below the thresholds it runs the same kernel as main.
- The cache bytes are identical to main (380/380 cases, bitwise).
- End-to-end throughput on DeepSeek-V2-Lite-Chat does not change beyond noise. The kernel time in one `vllm bench latency` iteration drops from 9.94 to 7.75 ms (bf16 cache).

## Key results

- New kernels `concat_and_cache_mla_vec_kernel` and `concat_and_cache_mla_grouped_vec_kernel`: one 32-lane group per token, 4 tokens per 128-thread block, vector accesses through `vectorize_with_alignment`. Loads are 16 bytes. Stores are 16 bytes for the plain cache, and 8 bytes for the fp8 cache from 16-bit inputs. The fp8 scale is read once per thread, not once per element.
- The original kernels are not changed. The launchers select a kernel by token count: `mla_cache_vec_min_tokens<kv_dt>()` is 512 for `auto` and 1024 for fp8.
- Bitwise vs main: 380 identical, 0 mismatched. `test_cache.py`: 698 passed. GSM8K (bf16 cache) is the same as main to the last digit.
- Kernel, bf16 input, `kv_lora_rank` 512, `pe_dim` 64, `k_pe` passed as a slice of the latent projection (the layout the model uses), us per call:

## Validation

**Setup.**
- GPU: 1x H100 80GB HBM3 SXM.
- Software: CUDA 13.0, torch 2.13.0+cu130.
- main = 0af34418e9. PR = main + this PR's first commit (d35c2422e4 at the time, same kernel code as now). Measured on 2026-09-29.

**Bitwise.**
- Method: dump the cache bytes from main on CPU-seeded inputs, apply the PR, and compare the sha256 of each case.
- Inputs: bf16, fp16 and fp32. Caches: `auto` and `fp8`. Token counts: 1 to 16384.
- (`kv_lora_rank`, `pe_dim`): (512, 64), (256, 64), (512, 0) and (128, 32).
- Layouts: contiguous, `k_pe` as a slice of the latent projection, and rows at an odd offset (not 16-byte aligned). Each case has one padded slot (-1).
- The grouped kernel over 3 layers.
- Result: 380 identical, 0 mismatched.

**Tests** (PR tree at d35c2422e4):

```
pytest tests/kernels/attention/test_cache.py   # 698 passed, 590 skipped
```

- `test_concat_and_cache_mla` now asserts `torch.equal` for both cache dtypes. Before, both cases used `assert_close`.
- New `test_concat_and_cache_mla_strided_input`: it passes `k_pe` as a latent slice and `kv_c` at an odd column offset. It asserts `torch.equal` against contiguous inputs and against the reference. It runs at 1, 42, 1000 and 4096 tokens, so it covers both kernels for both cache dtypes.
- `test_concat_and_cache_mla_grouped` now also runs at 2048 tokens, which is above both thresholds. Before, it ran only at 42 tokens, so the grouped vector kernel had no test.

- For the fp8 cache, the server also gets `--kv-cache-dtype fp8`.

The means differ by 1.6%, and main alone spreads 6.6% (54.78-58.37). So the two builds are not separable here.
- Profile: on the PR build, the 3429 decode launches stay on the original kernel (6.92 ms bf16, about 2.0 us each). The 81 prefill launches go to the vector kernel: 0.83 ms (bf16) and 0.96 ms (fp8). On main, the same launches take about 3.0 ms. I derived this value as the main total minus the PR's original-kernel time (9.94 - 6.92 ms for bf16, 10.56 - 7.52 ms for fp8). This workload has no launches between 512 and 1023 tokens, so only the microbenchmark shows the lower plain-cache threshold.

## Details

**Where the kernel runs.** `MLAAttentionImpl.do_kv_cache_update` calls `concat_and_cache_mla` inside the `unified_mla_kv_cache_update` op. The CPU and AMX MLA backends override it. So the kernel runs eagerly on every GPU MLA backend, with and without torch.compile. The grouped form is used by the Kimi K3 DSpark draft model (`dspark_mla.py`).

**Why the original kernel is slow at prefill sizes.** Each token gets one 512-thread block, and each thread copies one element per iteration. A token is 576 scalar 2-byte loads and stores. 448 threads are idle during the 64-element rope copy. On the fp8 path every element dereferences the scale pointer. At decode sizes this is at the launch floor, and there is nothing to gain. At prefill sizes the kernel is latency-bound (0.8 TB/s at 16K tokens).

**Design.**
- One 32-lane group per token and 4 tokens per block. Each lane moves 16 bytes per load, so a 512-element bf16 latent row is 2 loads per lane. Stores are 16 bytes for the plain cache and 16 / sizeof(input) bytes for fp8.
- The vector accesses use `vectorize_with_alignment`, the helper `reshape_and_cache_flash` already uses. If a row is not 16-byte aligned, the helper copies the unaligned prefix and tail with scalar accesses. It copies the whole row with scalar accesses only when the source and cache rows cannot both be aligned. So `k_pe` as a slice of the latent projection needs no host-side check.
- Both layouts apply the same per-element conversion (`CopyWithScaleOp`, the same `scaled_convert` with the same scale). So the cache bytes are identical on both paths.
- The two new kernels share one per-token device function. The grouped launcher now uses one macro for the bf16 and the two fp8 cases, in place of a separate bf16 launch and an fp8 macro.

**Why a threshold, and why 512 and 1024.**
- I first measured the vector layout at every token count (exploration runs on main 0376f81530 with CUDA 12.9). Against main it is 0.63-0.99x at 1-128 tokens, 1.00-1.50x at 1024 tokens, and 1.63-3.76x from 4096 tokens. At small sizes each lane's serialized vector round trips cost more than the extra threads save. For fp8, each vector also needs 8 converts.
- Wider layouts (64 or 128 lanes per token) trade one regime for the other. A small path through the vector helper at width 1 measured 0.1 us slower than the original loop.
- The exploration sweep has no points between 128 and 1024 tokens. So I set each threshold from a separate fact, and the fine sweep checks the result at the threshold.
- Plain cache, 512: the original 512-thread blocks fit 528 tokens in one wave on an H100 (132 SMs x 4 blocks). Past that they need a second wave: 2.54 us at 512 tokens, 3.04 us at 640. The vector kernel stays at about 2.4 us. At 512 the PR is 1.01-1.09x faster than main over both fine-sweep rounds.
- fp8, 1024: at 1024 tokens the vector layout is only at parity for rank 256 (1.00-1.01x in exploration, 1.02x in the fine sweep).

**Not a duplicate.**
- No other open PR vectorizes `concat_and_cache_mla_kernel` or the grouped kernel.
- #62102 adds a `skip_scale` flag to the original kernel. It does not change the copy layout. Both PRs edit `CALL_CONCAT_AND_CACHE_MLA`, so the PR that lands second needs a small rebase.
- The open rope + cache-insert fusions (#45573, and the ROCm/AITER ones such as #55230 and #45798) call their own fused kernels and do not change this kernel.

**Limitations.**
- Measured on H100 SXM only. The thresholds come from H100 wave counts and the H100 crossover sweep. On a GPU with a different SM count, the 528-token wave boundary moves. I have not measured other GPUs.
- The same code is built for ROCm. I have not built or measured it on ROCm.
- End-to-end throughput on DeepSeek-V2-Lite-Chat does not change beyond noise. The kernel is 0.46-0.63% of GPU time in the profile, so the PR stands on the kernel time.

I used Claude Code for this change. I reviewed every line and ran the tests and benchmarks above myself.
