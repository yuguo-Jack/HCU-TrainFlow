# [Perf][Kernel] Vectorized MLA KV-cache write for large launches

[Upstream PR](https://github.com/vllm-project/vllm/pull/59289) · state: open · merged: False

## Original PR description

## Purpose

`concat_and_cache_mla` writes one token's latent row (`kv_lora_rank` elements) and rope row (`pe_dim` elements) into the MLA KV cache. It runs for every MLA model on every layer, prefill and decode, from `MLACommonBaseImpl.do_kv_cache_update` inside the `unified_mla_kv_cache_update` op, so it is eager on every backend.

The kernel copies one element per thread with a 512-thread block per token: 576 scalar 2-byte loads and stores per token, 448 threads idle during the rope copy, and on the fp8 path a dereference of the scale pointer per element. At decode sizes that is at the launch floor and there is nothing to gain. At prefill sizes it is latency-bound: 16K tokens take 46 us to read and write 38 MB, 0.8 TB/s on a 3.35 TB/s part.

This PR adds vector variants of the kernel and of its grouped form (Kimi K3 MTP context insertion) and switches to them from 512 tokens for the plain cache and 1024 tokens for the fp8 cache: one 32-lane group per token, four tokens per block, 16-byte loads and stores through `vectorize_with_alignment` (the helper `reshape_and_cache_flash` uses), scale read once per thread. Rows that are not 16-byte aligned or not a multiple of the vector size fall back to scalar copies inside the helper, so `k_pe` passed as a slice of the latent projection is handled without a host-side check. Below the threshold the existing kernels run unchanged.

Why the threshold: I first measured the vector layout on its own (exploration runs on 0376f81530 with CUDA 12.9, under `exploration/` in the logs). It is 2.3x to 3.8x faster from 1K tokens but 0.63x to 0.9x at 1 to 128 tokens, where each lane's serialized vector round trips (and, for fp8, eight converts per vector) cost more than the extra threads save. Wider layouts (64 or 128 lanes per token) trade one regime for the other. Routing the small path through the vector helper at width 1 also measured 0.1 us slower than the original loop. The crossover sweep put parity at 256 tokens for the plain cache and 768 to 1024 for fp8. The thresholds are 512 and 1024. For the plain cache, the original 512-thread blocks fit 528 tokens in one wave on an H100 and pay a second wave past that (2.54 us at 512 tokens, 3.04 us at 640), while the vector kernel stays at 2.4 us. For fp8, rank 256 only reaches parity at 1024 tokens. Every measured shape is at or above main.

Cache bytes are identical on both paths: the `auto` path is a copy, and the fp8 path applies the same per-element `scaled_convert` with the same scale. Verified below.

**Where it matters.** Kernel time at prefill. End-to-end throughput on DeepSeek-V2-Lite is within noise (tables below); the profiles show the kernel's share of GPU time before and after.

**Not a duplicate.** No open PR touches `concat_and_cache_mla_kernel` or the grouped kernel. The closest is #38646 (@ZJY0516, opt-in torch.compile pass that fuses rope into the MLA cache insert; stale and needs-rebase since 2026-09-02): it rewrites the graph to call the separate `concat_and_cache_mla_rope_fused` kernel that already exists on main, so it changes which op the compiled path calls and does not touch this kernel, which stays the default path for every MLA backend. #45573 is the manual-fusion port of the same pass, #57640, #55230, #45798 and #41099 are ROCm/AITER fusions in the AMD model files, #55654 is a DSpark context insert in its own kernel file, and #38354 is an SM100 fused decode draft. None of them change the code here.

## Test Plan

- Bitwise vs `main` (0af34418e9): sha256 of the cache bytes over bf16/fp16/fp32 inputs, `auto` and `fp8` caches, token counts 1 to 16384, (`kv_lora_rank`, `pe_dim`) in {(512, 64), (256, 64), (512, 0), (128, 32)}, three input layouts (contiguous, `k_pe` as a latent slice, odd-offset unaligned rows), a padded slot (-1), plus the grouped kernel over 3 layers.
- `pytest tests/kernels/attention/test_cache.py`. The MLA test now asserts `torch.equal` for both cache dtypes, and a new `test_concat_and_cache_mla_strided_input` asserts `torch.equal` between strided and contiguous inputs and against the reference. The strided test runs at 1, 42, 1000 and 4096 tokens, so both the original and the vector kernels are asserted exactly for both cache dtypes.
- Microbenchmark: H100 80GB, CUDA 13.0, torch 2.13.0+cu130, `do_bench_cudagraph` median; new `benchmarks/kernels/benchmark_concat_and_cache_mla.py --strided` (k_pe as a latent slice, as the model passes it), plus a finer sweep around the thresholds, two interleaved rounds.
- E2e on deepseek-ai/DeepSeek-V2-Lite-Chat (MLA, `kv_lora_rank` 512, `pe_dim` 64, 27 layers), bf16 cache and `--kv-cache-dtype fp8`:

```bash
lm_eval --model vllm --model_args pretrained=deepseek-ai/DeepSeek-V2-Lite-Chat,trust_remote_code=True,max_model_len=4096,gpu_memory_utilization=0.9,seed=0 --tasks gsm8k --num_fewshot 5 --batch_size auto --seed 0
vllm serve deepseek-ai/DeepSeek-V2-Lite-Chat --trust-remote-code --max-model-len 4096 --gpu-memory-utilization 0.9
vllm bench serve --backend vllm --model deepseek-ai/DeepSeek-V2-Lite-Chat --trust-remote-code --dataset-name random --random-input-len 1024 --random-output-len 128 --num-prompts 1000 --request-rate inf --seed 0
```
