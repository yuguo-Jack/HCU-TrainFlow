# [V1][Perf] Skip the block-table H2D copy when no row changed

[Upstream PR](https://github.com/vllm-project/vllm/pull/58403) · state: closed · merged: False

## Original PR description

## Purpose

`BlockTable.commit_block_table()` in the V1 model runner re-uploads the whole
active `[num_reqs, max_num_blocks_per_req]` block table host→device on every
step, for every KV-cache group, even when no row changed since the last upload.

A row only changes when a request is admitted, moved, removed, or crosses a
KV-block boundary. This PR tracks a conservative interval of rows changed since
the last commit that covered them and skips the copy when that interval lies
outside `[0, num_reqs)`. When it does copy, it is the same single contiguous
bulk transfer as today.

Model Runner V2 already avoids this (`StagedWriteTensor`), and #47936 (same
idea, per-row scatter) was closed for that reason. The V1 runner is still the
**default** on ROCm for `DeepseekV32ForCausalLM`, `DeepseekV4ForCausalLM` and
`GlmMoeDsaForCausalLM` (`ROCM_DEFAULT_MRV1_ARCHITECTURES`, added in #53155 after
#47936 was closed), and on every platform when V2 is declined (ngram /
draft-model / suffix / medusa spec decode, elastic EP, DBO, SP at TP>1,
`VLLM_USE_V2_MODEL_RUNNER=0`, ...). If V1 is going away soon enough that this
is not worth carrying, say so and I will close it.

**This is a CPU-overhead cleanup, not a throughput PR.** The whole
`commit_block_table` is ~58 µs of a 10–44 ms DeepSeek-V4-Flash step, so the
end-to-end ceiling is a fraction of a percent, and the e2e runs below are flat
within noise. What it removes is per-step host work and a host→device copy on
the compute stream whose size scales with
`num_reqs × max_model_len / block_size` per KV-cache group.

### Details

- `append_row` / `clear_row` / `move_row` / `swap_row` widen the dirty interval
  (`add_row` goes through `append_row`). `move_row` marks **both** rows: since
  #49757 it also zeroes the vacated source, and a later padded dummy-run commit
  must upload that zeroed row.
- `commit_block_table(num_reqs)` only transfers `[0, num_reqs)`, so rows dirtied
  at or beyond `num_reqs` stay dirty (`[num_reqs, hi]`) until a commit wide
  enough to cover them.
- The table starts fully dirty, so the first commit (a warmup dummy run) still
  performs the transfer. Without this every warmup commit is skipped and the
  first real request pays the first H2D copy from the pinned buffer — measured
  at 20–30 ms on GLM-5.3.
- Bookkeeping is two Python ints rather than a per-row numpy flag array: a flag
  array made the always-dirty case 12–16 % slower than main (numpy
  `.any()`/`.fill()` per group per step); the interval form is flat there.
- `mark_dirty()` for the two callers that write the host buffer directly and
  would otherwise lose their transfer: `model_executor/warmup/replayssm_warmup.py`
  and `distributed/elastic_ep/elastic_execute.py`.

## Test Plan

- 6 new unit tests in `tests/v1/worker/test_gpu_block_table.py`, each checked
  against a plausible-but-wrong build: no initial dirty state fails
  `first_commit_copies_even_without_row_writes`; resetting the interval on
  every commit fails `keeps_rows_beyond_num_reqs_dirty` and
  `uploads_vacated_move_row_source`; marking only the `move_row` target fails
  `uploads_vacated_move_row_source`.
- Randomized differential test (outside the repo): 4000 steps × 3 groups × 2
  seeds of random add/append/clear/move/swap, direct host writes +
  `mark_dirty()`, full clears and random `num_reqs`; GPU[:n] == CPU[:n] after
  every commit.
- In-engine check: sync and compare the GPU and CPU block tables after every
  commit during a real generate run.
- Micro benchmark of `MultiGroupBlockTable.commit_block_table` using per-group
  dirty rates measured in the engine.
- GSM8K A/B with a base-repeat control, and `vllm bench serve` e2e, on
  DeepSeek-V4-Flash-0731 (TP=1) and GLM-5.3 FP8 (TP=4), plus Llama-3.1-8B
  (takes V2, never reaches this code) as a no-op control.

## Test Result

8× MI355X (gfx950). main = `e6dc16cebd`, this PR rebased on it; vLLM nightly
`0.3.1.dev311+ge97573215` binaries with main's Python (no op-schema changes
between the two), torch `2.12.0+rocm10.0.0`. `VLLM_ROCM_USE_AITER=1`. Every
DeepSeek-V4 / GLM-5.3 run logged "Defaulting to V1 model runner".

**Correctness.** Differential test 0/24000 mismatches (the wrong builds above
give 76–898). In-engine: 0 mismatches over 7905 group-commits on
DeepSeek-V4-Flash-0731, 7905 on DeepSeek-V4-Pro (13 layers, dummy weights), 1580
on GLM-5.3 (8 layers, dummy weights); the skip count equals the number of
commits whose content was unchanged, i.e. no over-copying.
