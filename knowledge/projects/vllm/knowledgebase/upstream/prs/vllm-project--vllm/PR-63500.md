# [Bugfix] Don't initialize CUDA when importing the FLA ops

[Upstream PR](https://github.com/vllm-project/vllm/pull/63500) · state: open · merged: False

## Original PR description



## Overview

Importing the vendored FLA ops (`vllm/third_party/flash_linear_attention/ops`) initialized CUDA in the importing process. The frontend imports multimodal model classes while it builds `ModelConfig`, so `LLM()` / `vllm serve` with a GDN model such as Qwen3.5 initialized CUDA in the frontend. vLLM then has to spawn the engine core instead of forking it. As a result, scripts without an `if __name__ == "__main__":` guard (like the quickstart example) crash. This PR makes the FLA import-time platform checks CUDA-free.

## Claims

- `LLM(model="Qwen/Qwen3.5-0.8B")` no longer initializes CUDA in the caller. The engine core is forked again, and the `We must use the spawn ... Reasons: CUDA is initialized` warning is gone.
- With a GDN model, a script without a `__main__` guard works again. Before, it failed with the multiprocessing bootstrapping `RuntimeError` → `Engine core initialization failed`.
- The engine-config step that the `vllm serve` API server runs no longer initializes CUDA.
- No kernel-config change: `is_nvidia_hopper`, `check_shared_mem()` and the derived `BKV_LIST` / `NUM_WARPS` / `BS_LIST` are identical before and after.

## Validation

Hardware: 1x RTX 2060 SUPER (sm_75, 8 GB), driver 580, torch 2.14.0+cu130. The fix was applied to a recent `main` nightly; `vllm/third_party/flash_linear_attention/ops/utils.py` is byte-identical on current `main`.

## Details

**Root cause.** For multimodal models, the frontend builds `ModelConfig`, and `_supports_multimodal_inputs` calls `MULTIMODAL_REGISTRY.get_processing_info`. That imports the model class, e.g. `qwen3_5`, which imports `qwen_gdn_linear_attn`, which imports `vllm.third_party.flash_linear_attention.ops`. Its `utils.py` runs two platform checks at import time:
- `_check_platform()` → `triton.runtime.driver.active.get_current_target()` → `torch.cuda.current_device()` → `torch.cuda._lazy_init()`;
- `is_nvidia_hopper` → `torch.cuda.get_device_name(0)` / `get_device_capability()`.

`_maybe_force_spawn()` then sees `torch.cuda.is_initialized()` and switches to spawn. Of the model modules I checked, only the FLA-based ones do this on import: `qwen3_5` and `qwen3_next` do, while `llava`, `qwen2_vl`, `qwen2_5_vl`, `qwen3_vl`, `gemma3_mm`, `llama` and `qwen3` do not.

**Fix** (`utils.py` only):
- `_check_platform()` returns `"nvidia"` from `current_platform.is_cuda()` instead of probing Triton's driver.
- `is_nvidia_hopper` uses `current_platform.get_device_name()` / `has_device_capability(90)`, which are NVML-backed on CUDA. The result is the same as before.
- `check_shared_mem()` reads `shared_memory_per_block_optin` via `vllm.utils.platform_utils.cuda_get_device_properties()` on NVIDIA. This is the same attribute as Triton's `max_shared_mem`. Swapping the `torch.cuda` calls alone is not enough. Once CUDA is no longer initialized at import, Triton's `get_device_properties()` raises, and `check_shared_mem()` would silently return `False`. A forked engine inherits `BKV_LIST` / `BS_LIST` computed at import time, so GPUs with more shared memory (A100, H100, B200) would quietly get the smaller autotune configs. `cuda_get_device_properties()` queries in-process once CUDA is initialized, and otherwise in a short-lived forked helper (the same mechanism `NvmlCudaPlatform.get_device_total_memory` uses).

**Tradeoffs and limitations.**
- A process that imports the FLA ops before initializing CUDA (the frontend) pays one short helper subprocess, about +0.1 s on the import above. The previous behaviour paid for a CUDA init in the frontend plus a spawned engine.
- ROCm/XPU paths are unchanged.
- Non-NVML CUDA platforms still go through `torch.cuda` in `current_platform`, as before.
- If the helper cannot run (e.g. in a daemonic process), `check_shared_mem()` falls back to `False` through its existing `except`.
- No runtime/steady-state code path changes; there is no new CPU/GPU sync.

**Tests / CI.** The new test lives in `tests/cuda/test_platform_no_cuda_init.py`, next to the existing "no premature CUDA init" checks. It runs `LLM()` for Qwen3.5-0.8B (dummy weights, eager, `language_model_only`) in a subprocess script without a `__main__` guard. It asserts that the caller did not initialize CUDA, that the engine generates, and that `check_shared_mem()` matches the device's opt-in shared-memory limit. The test is skipped on non-CUDA platforms. `vllm/third_party/flash_linear_attention/` is added to the CUDA Platform step's `source_file_dependencies` so CI selects it.

**Not a duplicate.** I found no open issue or PR about this. Searches covered `gh issue list` / `gh pr list` for "CUDA is initialized spawn", "bootstrapping phase", "Qwen3.5 spawn", "fla initialize CUDA", "check_shared_mem", "flash_linear_attention" and similar.
- #37700 (open, targets the pre-move `vllm/model_executor/layers/fla` path) also replaces the `torch.cuda` calls in `is_nvidia_hopper`, but to fix SM12x Hopper/TMA classification. It does not address CUDA initialization or `check_shared_mem()`.
- #43047 (open) adds an autotune pruner and is unrelated.

**Side note.** The comment in `tests/models/test_registry.py::test_registry_inspect_does_not_init_cuda` says Llava/Qwen2-VL initialize CUDA on import. They no longer do, so that test currently only warns. This PR leaves it unchanged.
