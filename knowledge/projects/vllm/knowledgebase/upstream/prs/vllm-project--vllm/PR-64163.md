# [MoE] Use sorted fused-MoE path on integrated GPUs for multi-token batches (#63943)

[Upstream PR](https://github.com/vllm-project/vllm/pull/64163) · state: open · merged: False

## Original PR description

## Summary

Triton fused MoE currently engages the low-latency unpermuted "naive block assignment" path when `num_tokens * top_k * 4 <= global_num_experts`, bypassing `moe_align_block_size`.

- **On discrete HBM GPUs (A100, H100, B200):** This yields a ~12–19% decode speedup at `M=2..4` by eliminating the fixed CUDA launch overhead of the alignment kernel.
- **On integrated/unified-memory GPUs (NVIDIA GB10 / DGX Spark with UMA LPDDR5x):** Multiple tokens routing to identical experts cause redundant weight reads over shared memory bandwidth, leading to an 8% to 52% decode regression (#63943).

This PR introduces an adaptive, architecture-aware threshold:
1. **Integrated / UMA GPUs (`current_platform.is_integrated_gpu()`):** Restricts naive assignment strictly to `num_tokens == 1` where expert collision is impossible, routing multi-token batches (`M >= 2`) through the sorted `moe_align_block_size` path.
2. **Discrete GPUs:** Preserves the existing `num_tokens * top_k * 4 <= global_num_experts` heuristic.

> **Hardware Scope:** Measured on NVIDIA GB10 (DGX Spark) only; other integrated GPUs such as Jetson Thor take the same path but are unmeasured.

Fixes #63943.

## Test Plan

1. **Unit tests in `tests/kernels/moe/test_moe.py`:**
   - `test_integrated_gpu_expert_assignment`: Parameterized across `M in [1, 2, 4, 8]` for both integrated and discrete GPUs, verifying integrated GPUs take sorted path at `M >= 2` while taking naive path at `M=1`, and discrete GPUs preserve naive path at `M <= 4`.
   - `test_host_resident_weights_take_sorted_path`: Verifies zero regression on host-resident weights (#62054).

2. **GB10 Hardware Validation (by @ks-huang):**
   Evaluated on NVIDIA GB10 (sm_121, `is_integrated = 1`) with Qwen3-30B-A3B BF16, TP=1, `--moe-backend triton`, greedy decode (128 tokens):
   - **CUDA Graphs (`FULL_AND_PIECEWISE`):**
     - Batch 1: 31.1 ms/step (unchanged)
     - Batch 4 (4 different prompts): 73.7 ms -> 67.2 ms (**-8.8%**)
     - Batch 4 (4 identical prompts): 65.8 ms -> 29.7 ms (**-55.0%**)
   - **Eager Mode:**
     - Batch 1: 32.8 ms/step (unchanged)
     - Batch 4 (different prompts): 75.3 ms -> 69.1 ms (**-8.2%**)
     - Batch 4 (identical prompts): 67.3 ms -> 32.4 ms (**-52.0%**)
   - Output text is identical to stock in all runs.

3. **A100 Discrete Baseline Microbenchmark:**
   Verified on NVIDIA A100-PCIE-40GB (`E=128`, `top_k=8`) that naive path remains ~19% faster at `M=2` even under 100% expert collision due to dedicated HBM bandwidth absorbing redundant reads.

   | M (batch) | Scenario | Naive (µs) | Grouped (µs) | Delta |
   |---|---|---|---|---|
   | 1 | Independent | 345.5 | 428.5 | **+19.4% (Naive)** |
   | 1 | Shared Experts (100% collision) | 344.0 | 427.4 | **+19.5% (Naive)** |
   | 2 | Independent | 342.1 | 423.6 | **+19.3% (Naive)** |
   | 2 | Shared Experts (100% collision) | 345.4 | 426.1 | **+18.9% (Naive)** |

   <summary>A100 Benchmark Script (Standalone Reproduction)</summary>

   ```python
   import torch
   from vllm.config import VllmConfig, set_current_vllm_config
   import vllm.model_executor.layers.fused_moe.fused_moe as fused_moe_module
   from tests.kernels.moe.utils import fused_moe

   def benchmark_latency(fn, warmup=50, iters=200):
       for _ in range(warmup):
           fn()
       torch.cuda.synchronize()
       start = torch.cuda.Event(enable_timing=True)
       end = torch.cuda.Event(enable_timing=True)
       start.record()
       for _ in range(iters):
           fn()
       end.record()
       torch.cuda.synchronize()
       return (start.elapsed_time(end) / iters) * 1000.0

   def run_suite():
       vllm_config = VllmConfig()
       device = "cuda:0"
       dtype = torch.bfloat16
       e, topk, k, n = 128, 8, 2048, 1024

       torch.manual_seed(42)
       torch.cuda.manual_seed(42)
       w1 = torch.randn((e, 2 * n, k), device=device, dtype=dtype) / 8
       w2 = torch.randn((e, k, n), device=device, dtype=dtype) / 8

       orig_align = fused_moe_module.moe_align_block_size
       orig_prep = fused_moe_module._prepare_expert_assignment

       def forced_grouped_prep(*args, **kwargs):
           topk_ids = args[0] if len(args) > 0 else kwargs['topk_ids']
           config = args[1] if len(args) > 1 else kwargs['config']
           global_num_experts = args[4] if len(args) > 4 else kwargs['global_num_experts']
           expert_map = args[5] if len(args) > 5 else kwargs['expert_map']
           ignore_invalid = kwargs.get('ignore_invalid_experts', False)
           return orig_align(topk_ids, config["BLOCK_SIZE_M"], global_num_experts, expert_map, ignore_invalid_experts=ignore_invalid)

       for m in [1, 2, 4, 8]:
           for scenario in ["Independent", "Shared Experts"]:
               a = torch.randn((m, k), device=device, dtype=dtype)
               score = torch.randn((m, e), device=device, dtype=dtype) if scenario == "Independent" else torch.randn((1, e), device=device, dtype=dtype).repeat(m, 1)

               fused_moe_module._prepare_expert_assignment = orig_prep
               with set_current_vllm_config(vllm_config):
                   time_naive = benchmark_latency(lambda: fused_moe(a, w1, w2, score, topk, renormalize=False))

               fused_moe_module._prepare_expert_assignment = forced_grouped_prep
               with set_current_vllm_config(vllm_config):
                   time_grouped = benchmark_latency(lambda: fused_moe(a, w1, w2, score, topk, renormalize=False))

               fused_moe_module._prepare_expert_assignment = orig_prep
               diff_pct = ((time_grouped - time_naive) / time_grouped) * 100.0
               print(f"M={m} | {scenario:<14} | Naive: {time_naive:.1f}us | Grouped: {time_grouped:.1f}us | {diff_pct:+.1f}%")

   if __name__ == "__main__":
       run_suite()
   ```

**GB10 (DGX Spark) validation: works as intended**

Tested on GB10 (sm_121, `is_integrated = 1`) with **Qwen3-30B-A3B BF16, TP=1, Triton MoE backend, eager mode, greedy decoding, 128 tokens per run**. Running with vLLM (0.1.dev21546, 2026-09-28) predates #62054, so I ported the PR's decision logic onto that build's `_prepare_expert_assignment`, leaving out the host-resident term. I checked the port against the PR's code for combination of token count, top-k, expert count, integrated flag and override value.

| | stock | this PR | change |
|---|---|---|---|
| batch 1 | 32.8 ms/step | 32.7 | unchanged |
| batch 4, four different prompts | 75.3 | 69.1 | −8.2% |
| batch 4, four identical prompts | 67.3 | 32.4 | −52% |

Output text is identical to stock at both batch sizes, and the numbers match the sorted path I measured in the issue (69.1 / 32.3), so the PR **recovers the full gain**. I measured eager mode only, not CUDA graphs.

A few notes from reading the diff:
1. **Override values:** `1`/`true` means "the existing threshold", while other integers cap the token count. So no value expresses "naive only at batch 1", the integrated behavior, which is the natural setting to force for an A/B on a discrete GPU. Treating integers uniformly as a cap (`1` = batch 1 only), with keywords for the rest, would remove the ambiguity.
2. **Tests:** the override test covers `0` and `1`; an integer cap and an unparseable value aren't exercised.
3. **Hot path:** the inline import, the env lookup and `get_device_properties()` run on every MoE layer call. That's a few µs each, small but visible in eager decode on GB10. Resolving the override and the per-device flag once (e.g. `functools.cache`) would make it free.
4. **GH200:** the `is_integrated_gpu` docstring lists GH200 among UMA systems. If GH200 reports `is_integrated = 1`, it would get the batch-1-only rule despite HBM3. Worth confirming. ROCm keeps today's behavior, since the default returns False.
