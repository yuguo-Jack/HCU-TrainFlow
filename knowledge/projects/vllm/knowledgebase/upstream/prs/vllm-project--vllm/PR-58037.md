# [Core] Count preemptions by reason

[Upstream PR](https://github.com/vllm-project/vllm/pull/58037) · state: open · merged: False

## Original PR description

## Purpose

The scheduler preempts running requests for three different reasons — no free KV cache blocks for a running request (FCFS victim), a higher-priority request needing the blocks under `--scheduling-policy priority`, and `reset_prefix_cache` with requests running. `vllm:num_preemptions` sums them, so a rising counter cannot be attributed to KV pressure vs. priority churn without reading logs.

This PR records the reason on the `PREEMPTED` `EngineCoreEvent` and exports

```
vllm:num_preemptions_by_reason{model_name, engine, reason="kv_full"|"priority"|"prefix_cache_reset"}
```

following the existing `vllm:num_requests_waiting_by_reason` pattern. `vllm:num_preemptions` is unchanged; the reasons sum to it. `EngineCoreEvent.reason` defaults to `None`, so serialization stays compatible, and `_preempt_request(..., reason=...)` defaults to `kv_full`.

Not a duplicate: no open PR or issue adds a preemption reason label (searched "preemption reason", "preemptions_by_reason"). Related but orthogonal: #54644 (victim-selection extension point) and #38080 (least-computed-first victims) change *which* request is preempted; this PR only labels *why*.

The docs table in `docs/usage/metrics.md` is generated from the `documentation=` string, so no manual doc change.

```
vllm:num_preemptions_total{engine="0",model_name="facebook/opt-125m"} 3.0
vllm:num_preemptions_by_reason_total{engine="0",model_name="facebook/opt-125m",reason="kv_full"} 2.0

vllm:num_preemptions_by_reason_total{engine="0",model_name="facebook/opt-125m",reason="prefix_cache_reset"} 0.0
```

Overhead: one dict update per preemption event on the frontend; nothing on the hot path when no preemption happens.
