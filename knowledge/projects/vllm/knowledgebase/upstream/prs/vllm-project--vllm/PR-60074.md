# [Bugfix][Compile] Pin Inductor kernel configs under VLLM_BATCH_INVARIANT

[Upstream PR](https://github.com/vllm-project/vllm/pull/60074) · state: open · merged: False

## Original PR description

## Purpose

Part of #58899 (second direction listed in the issue).

With `VLLM_BATCH_INVARIANT=1`, greedy outputs can still change between restarts. Inductor autotunes the generated reduction kernels on the device at first launch, for example the fused q/k RMSNorm + RoPE combo kernel in Qwen3. The candidate configs reduce in a different order, so which one wins the timing changes the numerics.

This PR adds the following for `VLLM_BATCH_INVARIANT=1`:
- Sets Inductor's `batch_invariant` option (torch >= 2.13). This implies Inductor's deterministic reduction configs, so reductions are no longer autotuned at runtime. It also keeps the config stable across batch sizes.
- Turns off `benchmark_combo_kernel`. Combo kernels stay on.
- Keeps any explicit user value in `inductor_compile_config`.

**Why `batch_invariant` and not `deterministic`:** in my issue comment I proposed Inductor's `deterministic` flag. With `benchmark_combo_kernel` on, that flag fails at startup in `may_ban_benchmarking`, which #59074 fixes. `batch_invariant` does not raise there and matches what vLLM's mode wants, so this PR does not depend on #59074.

**Not a duplicate:** #59074 handles the `TORCHINDUCTOR_DETERMINISTIC` startup failure. No open PR changes Inductor settings under `VLLM_BATCH_INVARIANT`.

## Test Plan

- `pytest tests/compile/test_config.py -k batch_invariant_pins`
- End-to-end on 1x RTX 4000 Ada (sm_89), torch 2.13.0+cu132, `Qwen/Qwen3-0.6B`, `VLLM_BATCH_INVARIANT=1`. I used the deterministic repro from #58899: patch `CachingAutotuner.benchmark_all_configs` so that the first or the last candidate always wins. Each run used a fresh process and fresh Inductor/Triton/vLLM caches. 8 prompts, greedy decoding, 64 tokens, logprobs=5.

- IridiumMaster · comment · 2026-10-13T07:15:39Z · [source](https://github.com/vllm-project/vllm/pull/60074#issuecomment-6140370384)

An independent check of this change, applied by config on a released build rather than the PR branch.

**Setup:** `vllm/vllm-openai:v0.31.0` (torch 2.13.0+cu130), one RTX 4090, `Qwen/Qwen3-4B`, `VLLM_BATCH_INVARIANT=1`, torch.compile on (default compilation mode).
- A producer `vllm serve` process runs 48 concurrent requests: prompts of 27–2,666 tokens, 160 output tokens with `ignore_eos`, chunked prefill (`max_num_batched_tokens` 2048), no prefix caching. It records the decode-time logprobs.
- A separate `vllm serve` process, in a fresh container with a fresh compile cache, rescores prompt + output with `prompt_logprobs`.
- We compare the float32 bits of every generated token's logprob.

To mirror this PR, we passed its end state through the compilation config:
`--compilation-config '{"inductor_compile_config": {"batch_invariant": true, "combo_kernels": true, "benchmark_combo_kernel": false}}'`.
`combo_kernels` is set explicitly so that 0.31's `__post_init__` doesn't turn `benchmark_combo_kernel` back on.

| config | requests bit-identical | tokens bit-identical | max abs logprob diff |
|---|---|---|---|
| default | 0/48 | 1,710/7,680 | 0.29 |
| this PR's settings, bf16 | 48/48 | 7,680/7,680 | 0 |
| this PR's settings, FP8 (online W8A8) | 48/48 | 7,680/7,680 | 0 |

The same harness with producer and checker in one process was already exact (48/48) without the change. The difference is entirely across processes, consistent with the autotuning explanation in #58899.
