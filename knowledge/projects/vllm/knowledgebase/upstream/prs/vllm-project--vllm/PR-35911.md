# [RL] Send NCCL weight metadata once and reuse it

[Upstream PR](https://github.com/vllm-project/vllm/pull/35911) · state: closed · merged: True

## Original PR description

## Purpose

Every NCCL `update_weights` call ships the full `names` / `dtype_names` / `shapes` lists out of band (about 19,000 entries for Qwen3-30B-A3B), even though an RL trainer sends the same parameters every round.

This PR sends that metadata once and reuses it:

| `update_info` sent | Worker loads |
| --- | --- |
| lists filled in | exactly these parameters, and saves the list |
| all three lists empty (`{}`) | the list saved by the previous call on the same model |
| empty, nothing saved yet | nothing (unchanged behavior) |

- The saved list is per model, so target and draft updates keep separate lists.
- `init_weight_transfer_engine` clears the saved lists.
- `NCCLTrainerWeightTransferEngine.send_weights` sends empty lists when `metadata()` equals what the last successful round sent, so users of the built-in trainer engine get this for free.
- Callers that keep sending full metadata (TRL, HTTP trainers without vLLM) see no change.
- Docs: new section "Metadata is sent once, then reused" in `docs/training/weight_transfer/nccl.md`, plus a pointer from the HTTP-without-vLLM section.

### Why not send the metadata over NCCL

This PR originally broadcast a JSON metadata blob over NCCL before the weights (original head: `4170ecd4f7f1bbdc01a13257b9bb5067ae6657d6`). Reusing the previous call's metadata is smaller (no wire-protocol change, no parsing of untrusted bytes on the worker, about 25 lines of non-test code) and removes the per-round cost entirely instead of moving it onto NCCL.

## Code Review

This pull request introduces a mechanism to transfer weight metadata (names, dtypes, shapes) via NCCL, eliminating the need for out-of-band metadata passing. It utilizes new options in `NCCLTrainerSendWeightsArgs` and `NCCLWeightTransferUpdateInfo` and helper functions `_broadcast_metadata` and `_receive_metadata` for JSON serialization and transfer. However, the implementation lacks proper validation of data received from the network, which introduces high-severity denial-of-service (DoS) vulnerabilities. A compromised or malicious trainer could crash inference workers by sending excessively large size values or malformed metadata. The use of unvalidated strings to access `torch` module attributes via `getattr` is also a security risk, requiring a strict whitelist of allowed data types. Additionally, there is an opportunity to optimize memory usage during metadata broadcast.

![security-high](https://www.gstatic.com/codereviewagent/security-high-priority.svg) ![high](https://www.gstatic.com/codereviewagent/high-priority.svg)

The `_receive_metadata` function receives a size value from the network via NCCL broadcast and uses it directly to allocate a GPU tensor (`torch.zeros`) without any validation or upper bound. An attacker controlling the source of the broadcast (the trainer) can provide an excessively large size, causing an Out-of-Memory (OOM) error and crashing the worker process. This is a significant denial-of-service vector in a distributed environment.

**Remediation:** Implement a reasonable upper limit on the metadata size and validate the received size against this limit before attempting to allocate memory.

![security-high](https://www.gstatic.com/codereviewagent/security-high-priority.svg) ![high](https://www.gstatic.com/codereviewagent/high-priority.svg)

The `receive_weights` function populates `update_info` with `names`, `dtype_names`, and `shapes` received from the network without any validation. This data is subsequently used in sensitive operations, such as `getattr(torch, dtype_name)` and `torch.empty(shape, ...)`. An attacker can provide malicious values (e.g., invalid attribute names for `torch` or extremely large shapes) to cause crashes or resource exhaustion on the worker. Specifically, `getattr(torch, dtype_name)` allows for arbitrary attribute access on the `torch` module, which is a security risk.

**Remediation:** Validate all metadata received from the network. Specifically, ensure `dtype_names` are restricted to a whitelist of allowed `torch.dtype` names and that `shapes` are within reasonable bounds before they are used to allocate memory or access attributes.
