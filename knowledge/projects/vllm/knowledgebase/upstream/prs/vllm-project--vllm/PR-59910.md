# [Test] Fix kernel tests on Blackwell GPUs

[Upstream PR](https://github.com/vllm-project/vllm/pull/59910) · state: open · merged: False

## Original PR description

## Overview

Fix four test-side bugs that only surface on SM100-family (Blackwell) GPUs. I found them by running the kernel tests on NVIDIA GB300 (SM 10.3); none of these tests is exercised on Blackwell by CI today. Test-only change, no product code is touched.

## Claims

- `test_silu_mul_fp8_quant_deep_gemm` no longer passes uninitialized memory to DeepGEMM's UE8M0 scale packer. On GB300, 22 of 23 cases failed with `CUDA_ERROR_LAUNCH_FAILED`; all 23 pass with this change.
- `test_w8a8_block_fp8_torch_scaled_mm_matmul` is skipped on CUDA GPUs other than SM90, matching the support guard of the kernel it tests. On GB300 it failed with `CUBLAS_STATUS_NOT_SUPPORTED`; it is now skipped.
- `test_unquantized_bf16_flashinfer_trtllm_backend` gives its dummy layer the `moe_config` and `routing_sink` attributes that the unquantized MoE method reads. It failed with `AttributeError`; it now passes.
- `test_marlin_vs_trtllm_mxint4` unwraps the list returned by FlashInfer's raw `trtllm_mxint4_block_scale_moe`, as the product wrapper does. 2 of 5 cases failed with `AttributeError: 'list' object has no attribute 'to'`; all 5 pass now.

## Validation

NVIDIA GB300 (SM 10.3), driver 580.167.08, CUDA toolkit 13.1, torch 2.13.0+cu130, FlashInfer 0.7.0.post1, vLLM `f590eb2448`:

| Command | Before | After |
| --- | --- | --- |
| `pytest tests/kernels/moe/test_silu_mul_fp8_quant_deep_gemm.py -q` | 22 failed, 1 passed | 23 passed |
| `pytest tests/kernels/quantization/test_block_fp8.py -q -k torch_scaled_mm` | 1 failed | 1 skipped |
| `pytest tests/kernels/moe/test_moe.py::test_unquantized_bf16_flashinfer_trtllm_backend` | 1 failed | 1 passed |
| `pytest tests/kernels/moe/test_marlin_vs_trtllm_mxint4.py` | 2 failed, 3 passed | 5 passed |

The first two tests are unchanged on a pre-Blackwell GPU (NVIDIA A10, SM 8.6): 23 passed and 1 skipped, same as before. The other two are already skipped off Blackwell by their own guards. `pre-commit` passes on all four files.

## Details

**`test_silu_mul_fp8_quant_deep_gemm`.** `ref_with_scale_fmt` allocates the reference scale tensor `ref_s_f32` with `torch.empty` and fills only the first `tokens_per_expert[e]` rows of each expert. With DeepGEMM UE8M0 scales on SM100, the test then passes the whole tensor, padding rows included, to `transform_sf_into_required_layout`. DeepGEMM's packer has a device-side assert that every fp32 scale is a non-negative power of two, so leftover values in the padding rows trap the kernel (`compute-sanitizer` reports a trap in `transpose_and_pack_fp32_into_ue8m0`, not an out-of-bounds access), and the poisoned CUDA context fails the remaining cases. The only case that passed has no padding rows. Zero-initializing the tensor keeps the padding rows valid. Product code does not have this problem: activation scales are produced by the packed quantization kernels, which initialize or skip padding (see `test_deepgemm_moe_permute_initializes_padding_scales`), and weight scales come from checkpoint data.

**`test_w8a8_block_fp8_torch_scaled_mm_matmul`.** The skip condition used `has_device_capability(90)`, which is true for every GPU at or above SM90. PyTorch implements DeepSeek-style block scaling in `torch._scaled_mm` only for SM90, and `BlockWiseTorchFP8ScaledMMLinearKernel.is_supported()` already requires exactly SM90, so this kernel is never selected on other CUDA GPUs. The test now uses the same predicate, `is_device_capability(90)`.

**`test_unquantized_bf16_flashinfer_trtllm_backend`.** The test (added in #33715) builds a bare `torch.nn.Module` as the layer. Since #43461 the unquantized MoE method reads `layer.moe_config` in `_setup_kernel`, and `apply_monolithic` reads `layer.routing_sink`; real `RoutedExperts` layers have both. The test now sets them on its dummy layer. #59757 notes the same failure on an unmodified nightly.

**`test_marlin_vs_trtllm_mxint4`.** The test calls FlashInfer's raw `trtllm_mxint4_block_scale_moe` and chains `.to(dtype)` on the result. With the FlashInfer version vLLM pins (0.7.0.post1) the call returns a list. The product wrapper in `flashinfer_mxint4_moe.py` already unwraps a tuple or list before casting; the test now does the same.

**CI coverage.** All four tests need SM100, and no CI job runs them there: the B200 kernels shard runs only `test_w8a8_block_fp8_cutlass_matmul` from `test_block_fp8.py` and does not list the three MoE files, and the DGX Spark nightly job selects `-k b12x`. That is why these failures were not visible in CI, and why I validated on GB300 outside CI.

**Related work.** Draft PRs #51941 and #52979 include the same zero-initialization as part of larger MoE changes. This PR is the standalone fix.
