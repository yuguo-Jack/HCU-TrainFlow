# [ROCm][Perf][MiniMax-M3.1] Retune the MXFP8 dot_scaled GEMM tiles for M=17-256

[Upstream PR](https://github.com/vllm-project/vllm/pull/65530) · state: open · merged: False

## Original PR description

## What

`RocmDotScaledMxfp8LinearKernel` (Triton `tl.dot_scaled`) picks its tile in `_select_cfg`. For the MiniMax-M3.1 TP4 linears on gfx950, M=17-64 used a single narrow 16x16 tile and M=65-256 a 64x64 / 8-warp tile. This adds a shape-scoped tile table (`_M31_TP4_TILES`, keyed by the local `(N, K)`) for M <= 256 covering the fused qkv, o_proj, shared-expert gate_up / down, dense gate_up / down and the DSpark qkv. Decode and verify batches are M = 8 x requests, so M = 8..256 spans c1..c32.

Everything else is unchanged: M <= 16 for qkv / gate_up / shared down keeps its tile, M > 256 and every other shape use the existing selection, every other arch is untouched (the tile table is gated on CDNA4, `get_cdna_version() == 4`, i.e. gfx95x where it was tuned).

## Why

These GEMMs read each weight byte once and are weight-bandwidth bound (FLOPs are under 10% of the time at M=32, about 40% at M=128). What matters is how many M tiles re-read the same weights and how many programs fill the 256 CUs. A BLOCK_M that follows M, three pipeline stages for the shorter K tiles, and 4 warps for the 64x64 tiles remove most of the gap: for example fused qkv at M=64 goes from 4 M tiles of 16 to 2 tiles of 32.

## Results

## Correctness

Only the launch configuration changes. For every shape and M above the output is bit-identical to the current kernel (0 elements differ) and the error against the dequantized reference is unchanged (relative error 1.7e-3, below the 0.5% bound used in `benchmarks/kernels/benchmark_mxfp8_tp4.py`). The unit tests pin the new table on gfx950 and check that every tile's BLOCK_K divides K (the K loop is unmasked); `tests/kernels/quantization/test_rocm_mxfp8_linear.py` passes (191 tests) on MI355X. The in-GEMM activation quant path (`_select_fused_quant_cfg`, M <= 16) is not touched.

## Relation to other work

This keeps the Triton kernel and its `QuantizedActivation` input, so the fused norm / swiglu / attention-epilogue quantization from #65478 and #65508 keeps applying, and it is independent of #65479 (AITER FlyDSL GEMM): it improves the kernel that remains the fallback for shapes AITER has no tuned rows for.
