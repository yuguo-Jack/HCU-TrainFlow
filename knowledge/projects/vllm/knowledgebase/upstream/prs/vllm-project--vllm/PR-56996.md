# [Perf][Attention] Source Triton metadata builder geometry from kv_cache_spec

[Upstream PR](https://github.com/vllm-project/vllm/pull/56996) · state: closed · merged: True

## Original PR description

## Overview

`TritonAttentionMetadataBuilder` is built per KV-cache group but sizes its 3D-kernel threshold and split-K scratch from the model-wide KV head count and head dim, so on heterogeneous models such as Gemma 4 decode stays on the slower 2D kernel; this PR reads both from the group's `kv_cache_spec`, as `FlashAttentionMetadataBuilder` already does (#42650 did the same for `num_heads_q`).

`unified_attention` takes the 2D grid's `num_kv_heads` from `k.shape[2]`, the group's own count. On `gemma-4-26B-A4B-it` the full-attention group has 2 KV heads against a model-wide 8, so `seq_threshold_3D` is `128 // 8 = 16` instead of `128 // 2 = 64`: at batch 24 the grid is 48 blocks, below `MIN_LAUNCH_GRID_SIZE_2D = 128`, yet the builder stays on 2D. The sliding groups size `softmax_segm_output` for head dim 512 instead of 256.

The buffer uses `head_size`, the stride `unified_attention` applies (`next_power_of_2(q.shape[2])`); `head_size_v` belongs to the DiffKV path, which re-sizes its own buffer. Switching kernel changes the bf16 reduction order, so generated text can differ. Where the spec matches the model-global values, nothing changes.

#54191 changes `num_heads_kv` only. #57409 changes `headdim` only, inside a DFlash change. This PR does both, and the new tests fail on either half alone. #47520 rescales the grid-size target and keeps the divisor, so it composes with this.

## Claims

- Gemma 4 full-attention decode at batches 24–64 moves from the 2D to the 3D kernel: **+66%** at batch 24 (506 µs → 172 µs) and **+36%** at batch 64 on MI325X. Batches that keep their kernel are flat.
- On vLLM v0.29.0 (MI355X), `vllm bench serve` of gemma-4 at 32K input and concurrency 24 gives **+6.7%** total tok/s and **−11.5%** median TPOT, with TTFT flat. Not re-taken on this `main`.
- GSM8K strict-match on that build goes from **0.4155 to 0.4511**; a repeated base run is bit-identical.
- Affected locally: gemma-4-26B-A4B and gemma-4-31B, which `Gemma4Config` forces onto `TRITON_ATTN` on ROCm. Homogeneous models are unchanged.

## Details

Of 17 local checkpoints, only Gemma 4 reaches this builder without an explicit backend selection; the others, forced onto it, match `main` in every builder field. Under full graph capture with an off-grid `max_num_seqs=50`, batches 49–50 pad to 56 tokens and stay on 2D on both arms; that sizing comes from `main`.

### MiMo-V2-Flash / V2.5: measurement setup and data

**Arms.** vLLM main `dfe4a3025` built from source for gfx950, versus the same wheel with only this PR's `vllm/` diff applied. A recursive diff of the two installed packages differs only in `triton_attn.py`. None of the files involved (`triton_attn.py`, `triton_attn_diffkv.py`, `triton_unified_attention*.py`, `mimo_v2.py`) changed between this PR's merge base and `dfe4a3025`.
**Platform.** 8× MI355X, vLLM ROCm nightly image (ROCm SDK 10.0.0, torch 2.13.0+rocm10.0.0, Triton 3.8.0+git669b31ac). `VLLM_ROCM_USE_AITER=0` as in the MiMo recipe. MiMo selects `TRITON_ATTN_DIFFKV` (head 192 / v 128), whose builder inherits `TritonAttentionMetadataBuilder.__init__`.

#### 1. Builder fields at runtime

Read from each worker's `attn_groups` with `LLM(load_format="dummy")`, `max_num_seqs=256`, `FULL_AND_PIECEWISE` CUDA graphs. All ranks agree; V2.5 at TP4 matches V2-Flash.

| TP | sliding group: spec KV heads | `num_heads_kv` main → PR | `seq_threshold_3D` main → PR | full-attention group |
|---|---|---|---|---|
| 1 | 8 | 4 → 8 | 32 → 16 | unchanged (4 KV heads, threshold 32) |
| 2 | 4 | 2 → 4 | 64 → 32 | unchanged (64) |
| 4 | 2 | 1 → 2 | 128 → 64 | unchanged (128) |
| 8 | 1 | 1 → 1 | 128 → 128 | unchanged (128) |

The sliding group covers 39 of 48 layers: window 128, sinks, block size 16. At TP4, sliding decode batches 65–128 move from 3D to 2D. TP8 is unchanged.

#### 2. Kernel: `unified_attention_diffkv`, sliding-group shape, decode

bf16 KV, block 16, window 128, sinks, `num_par_softmax_segments=16`, random block tables over a 64K-block pool. 2D or 3D is forced through `seq_threshold_3D`. Each point is the median of 5 `triton.testing.do_bench_cudagraph` runs, with run order alternated.

| shape (per rank) | ctx | batch | 2D µs | 3D µs | main | PR | gain |
|---|---|---|---|---|---|---|---|
| TP4 (16 Q / 2 KV) | 256 | 72 / 128 | 7.38 / 9.28 | 16.18 / 23.08 | 3D | 2D | +119% / +149% |
| | 1024 | 72 / 96 / 128 | 7.33 / 8.77 / 9.12 | 19.08 / 22.08 / 26.73 | 3D | 2D | +160% / +152% / +193% |
| | 16384 | 72 / 96 / 128 | 7.27 / 8.79 / 9.39 | 22.39 / 25.80 / 30.73 | 3D | 2D | +208% / +194% / +227% |
| | 65536 | 72 / 128 | 7.23 / 9.06 | 22.22 / 30.60 | 3D | 2D | +207% / +238% |
| TP2 (32 Q / 4 KV) | 256 / 4096 | 64 | 10.93 / 10.70 | 27.16 / 36.33 | 3D | 2D | +148% / +240% |
| TP1 (64 Q / 8 KV) | 256 / 4096 | 32 | 10.74 / 10.79 | 26.11 / 35.55 | 3D | 2D | +143% / +229% |

Across every moved point (contexts 256–64K, all three shapes), 2D is 2.2–3.5× faster than 3D. 2D and 3D outputs agree to 1–2×10⁻³ relative L2. With a 128-token window, 15 of the 16 3D segments get no tiles, the remaining segment walks the same window with tile 16 instead of 32, and a reduce kernel follows. That is consistent with the existing note in `unified_attention_diffkv` that sliding-window layers stay 2D for spec-decode.

The full-attention group is the opposite case: 3D wins clearly there (TP4, ctx 16384, batch 16: 3D 55 µs vs 2D 465 µs). This PR does not change that group's threshold for MiMo.
