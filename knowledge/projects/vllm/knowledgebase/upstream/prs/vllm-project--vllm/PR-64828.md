# [Quantization][MoE] Keep MXFP4 expert scales resident in CSF on B12X

[Upstream PR](https://github.com/vllm-project/vllm/pull/64828) · state: closed · merged: False

## Original PR description

## Overview

Keep eligible B12X MXFP4 expert scales compressed in GPU memory with `VLLM_B12X_MOE_MXFP4_CSF=1` (off by default). Encode each TP rank's E8M0 scales losslessly and use FlashInfer's prepared execution API for supported inline plans, with shared expansion scratch for other plans.

**Stacked draft on #64753 and its dependency #64312.** The MXFP4 contribution is the last five commits ([diff against the parent](https://github.com/kirillbilchenko/vllm/compare/a6b2e2cb1...4ce6126d3ad7b83ea6dfecfb4aa4636bab371114)); the inherited NVFP4 work remains in the branch until the parent lands. This PR needs rebasing after those dependencies merge.

The optional full-N128 inline path is proposed separately in [FlashInfer draft #8060](https://github.com/flashinfer-ai/flashinfer/pull/8060). Stock FlashInfer already supports this vLLM feature through expansion and existing compact layouts.

Related investigation: [FlashInfer #8053](https://github.com/flashinfer-ai/flashinfer/pull/8053) fixes a dropped NVFP4 inline capability in the legacy tensor API used by #64753. That one-line NVFP4 fix is separate from this MXFP4 feature. Its isolated timings and limitations are documented there and [linked from the parent](https://github.com/vllm-project/vllm/pull/64753#issuecomment-6534497781).

## Claims

- Keep E8M0 scale bytes exact using per-row bases, one-bit selectors and exact-byte exceptions; release original scale parameters after preparation and share expansion scratch by geometry/dtype.
- Prepare native execution capacities during weight loading, then reuse cached plans for live batches and CUDA graphs. Shape/activation/dtype capabilities drive selection; there are no model-name checks or inference-time device readbacks.
- Reduce reported GLM TP2 model allocation from 83.55 to 80.02 GiB per rank with stock FlashInfer (7.06 GiB total saved). Serving latency and model evaluation are measured below; compression is a memory/performance tradeoff.

No duplicate found in open-PR searches for `64753 in:body` and `MXFP4 CSF`. #64753 covers resident NVFP4; #64312 decodes NVFP4 checkpoint scales at load; #64399 concerns a different MXFP4 quantization integration. The resident MXFP4 follow-up was described in the parent discussion. This remains a draft while the parent is under review.

## Details

The encoder chooses the adjacent-byte window minimizing exceptions per row, preserves gate/up order and uploads canonical 16-row slabs. PreparedExperts and a module-owned PreparationSession retain native launchers. Powers-of-two capacities plus the scheduler maximum are prepared once during weight loading; live shapes reuse the next capacity. Shared scratch is passed through the existing vLLM workspace mechanism. No source/checkpoint metadata changes are needed.

Eligibility requires the installed CSF API, B12X MXFP4/MXFP8, gated experts, H divisible by 256, per-rank I divisible by 128 (or compact I%128==64 with native API, SiLU and BF16 I/O), dimensions<=8160. Other configurations retain their existing representation and warn once. Expert biases/EP remain unsupported. Resident CSF weight reloads are rejected; shared scratch requires serialized layer execution on one CUDA stream. BF16 activation backends remain outside this feature.

Encoding and capacity preparation add startup work. Native inline support depends on the installed FI package and can trade extra resident bytes for less expansion work. The default remains off. This does not compare W4A8 accuracy/performance against Marlin W4A16.

AI assistance was used for implementation, tests, profiling and validation tooling.
