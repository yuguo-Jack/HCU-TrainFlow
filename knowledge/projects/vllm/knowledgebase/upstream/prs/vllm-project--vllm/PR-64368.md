# [Spec Decode][ROCm] draft_lm_head_quantization for DSpark drafters

[Upstream PR](https://github.com/vllm-project/vllm/pull/64368) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

This lets the DeepSeek-V4/V4.1 DSpark drafters use `draft_lm_head_quantization` (#59973), which so far was limited to EAGLE and MTP. A drafter that shares the target `lm_head` then computes its base logits through a private FP8 or NVFP4 copy of that head, while the target keeps verifying with its own BF16 head. It is the vLLM counterpart of sgl-project/sglang#39622.

```bash
vllm serve <model> --speculative-config \
  '{"method": "dspark", "num_speculative_tokens": 5, "draft_lm_head_quantization": "fp8"}'
```

## Claims

- DeepSeek-V4.1-Flash on MI355X, AgentX, `"fp8"`: ITL P50 is 4.0% lower at TP2 c1 and 2.4% lower at TP4 c1. A trace shows the draft-head GEMM going from 348 µs to 60 µs per step. From c8 up the result is neutral within noise.
- Acceptance length and GSM8K are unchanged within run-to-run noise, because the target still verifies with its own head.
- No new mechanism: the sharing logic EAGLE and DSpark had in common is now one helper, `share_target_lm_head`, and DSpark opts in through `DSparkSpeculatorConfig.supported_options`. Off by default.

## Details

- **Changes**:
  - `share_target_lm_head` in `eagle/utils.py`, next to `_should_share`, installs the target head or its quantized copy, raises if quantization was requested but the drafter keeps its own head, and returns the installed head. `load_eagle_model` uses the returned head for the MTP `shared_head` fixup. `load_dspark_model` passes its vocab-size check as `can_share`. `load_dflash_model` can adopt it with `quantization=None` in a follow-up.
  - `DSparkSpeculatorConfig` accepts `draft_lm_head_quantization` only for `DSparkDraftModel` and `DSparkV41DraftModel`. Other DSpark drafters may read `lm_head.weight` directly: Muse Spark casts its activations to the head's dtype, which would be FP8 for a quantized copy. They are rejected during config validation, before the target loads. EAGLE's `head_dtype` check is shared through `check_draft_lm_head_quantization`.
  - Weight reload and weight transfer already refresh the copy, because `refresh_quantized_lm_heads` and `share_source_lm_heads` run on any `DraftModelSpeculator`.
- **Not a duplicate of #47584**: that PR adds a separate env var (`VLLM_DSPARK_FP8_DRAFT_HEAD`) and a new rowwise FP8 module, for the NVIDIA DeepSeek-V4 DSpark path only. This PR reuses the existing `draft_lm_head_quantization` config and kernel selection, so it works on any platform with an FP8 linear kernel.
- **Kernel on ROCm**: `"fp8"` resolves to `RowWiseTorchFP8ScaledMMLinearKernel` (hipBLASLt FP8 `_scaled_mm`).
- **Why c1 benefits most**: at M=5 (one request, five drafts) the BF16 dispatch picks `wvSplitK`, which is about 3.5x slower than at M=10. `deepseek_v41/amd/ops/draft_lm_head.py` already pads around that, but only on gfx942. A lossless fix to that dispatch is a separate follow-up.
- **Memory**: one extra FP8 copy of the per-rank head shard, about 0.33 GB at TP2 and 0.17 GB at TP4 for DeepSeek-V4.1-Flash. It is created during model loading, so KV sizing accounts for it.
- **CI coverage**: the quantized copy and its refresh are covered by the existing `tests/v1/worker/test_gpu_draft_lm_head.py`. The shared EAGLE/MTP path is covered by the MTP e2e test above. The DSpark path is validated end to end above. CI has no DSpark checkpoint test for it. `"nvfp4"` takes the same path but was not measured here.

- stecasta · comment · 2026-11-03T07:38:19Z · [source](https://github.com/vllm-project/vllm/pull/64368#issuecomment-6598087085)

Hi @fxmarty-amd, `draft_lm_head_quantization` comes from #59973, so let me answer for it. `targets` does not cover this case today:
1. The EAGLE/MTP/DSpark drafters share the target's `ParallelLMHead`. A `targets` entry quantizes that module in place, so the target's verification head would also become FP8 and outputs would change. `draft_lm_head_quantization` builds a private quantized copy for the drafter and leaves the target's BF16 head untouched, so target outputs are unchanged.
2. `targets` resolves only `LinearBase` and `RoutedExperts` layers; a pattern matching `lm_head` raises `online quantization is not supported for ParallelLMHead`.

We could consider a drafter-scoped key in `targets` that maps onto the same copy path, in case we want a single quantization surface.


- fxmarty-amd · comment · 2026-11-03T09:21:49Z · [source](https://github.com/vllm-project/vllm/pull/64368#issuecomment-6599875575)

> draft_lm_head_quantization builds a private quantized copy for the drafter and leaves the target's BF16 head untouched, so target outputs are unchanged.

Thanks @stecasta! Makes sense, so existing `--quantization-config.targets` is not be expressive/flexible enough in case we have tied (shared) weights. `--quantization-config.targets '{"*draft_model.*.lm_head":"xyz"}'` should eventually be possible.

As there is work to extend online quantization for lm head (#62708, #63402, #61815), I think indeed centralizing the API under `--quantization-config` would be nice.
