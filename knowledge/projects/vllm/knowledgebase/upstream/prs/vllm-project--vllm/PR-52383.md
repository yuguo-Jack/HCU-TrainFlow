# [Bugfix][MoE] Pad MoE activations inside the custom op to fix CUDA-graph corruption

[Upstream PR](https://github.com/vllm-project/vllm/pull/52383) · state: closed · merged: False

## Original PR description

## Purpose

Root-cause fix for #52308. When a model's activations must be padded to the MoE kernel hidden dim (e.g. 2688→2816 for TRTLLM NVFP4 on `nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B-NVFP4`), the `F.pad` ran in the traced region and fed the opaque `vllm::moe_forward(_shared)` custom op. Inductor optimizes that pad into an aliased, stride-remapped view (generated code: `buf12 = reinterpret_tensor(buf14, (s72, 2688), (2816, 1))` feeding the op). Under CUDA graph capture, the op's captured kernels end up reading a buffer the replayed graph never refreshes — instrumented at replay, the op consumed **frozen capture-time zeros** for `hidden_states` while `router_logits` carried real request data. Result: deterministic, fluent-but-semantically-destroyed output on every graph mode (`PIECEWISE`, `FULL`, `FULL_AND_PIECEWISE`); eager was correct. The kernel itself is fine: it passes FlashInfer's own tests at this exact geometry and survives standalone capture (raw, shared-pool, multi-size, autotuned).

## Fix

- Move the activation padding inside the custom op (`MoERunner._forward_impl`), so the traced graph passes the original, properly tracked activation tensor and no pad intermediate exists at the opaque-op boundary.
- Plumb the fused-output width as an op arg (`out_hidden_dim`, generalizing the former `hidden_dim_unpadded`: narrower for TRT-LLM MXFP4, wider for internally padded kernels) so the fake impls stay pure shape functions of their inputs.
- Update the two `kimi_k3` latent MoE runners, which used the identical traced-pad→opaque-op pattern (same exposure). Neither overrides `_forward_impl`, so the in-op pad applies to them unchanged — kernels receive byte-identical tensors. Could not e2e-verify Kimi-K3 (2.8T params exceeds available hardware); flagging for owners of a K3 rig.
