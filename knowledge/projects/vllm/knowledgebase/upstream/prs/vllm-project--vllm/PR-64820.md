# [Kernel] Qwen4Exp: compute HyperConnection and PLE gate row offsets in int64

[Upstream PR](https://github.com/vllm-project/vllm/pull/64820) · state: closed · merged: True

## Original PR description



## Overview

The Qwen4Exp HyperConnection kernels (`nvidia/ops/hc.py`, `amd/ops/hc.py`) and the PLE gate kernel (`common/ops/ple.py`) compute each token row's address as `ptr + row * stride` with `row = tl.program_id(0)`, so the product is evaluated in int32 and wraps once it exceeds 2**31 - 1. This widens the row index to int64 once per kernel.

## Claims

- For a 2560-wide hidden state with 4 HC streams, the HC row stride is 10240 elements and the PLE key/value row stride is 12800. The products wrap from row 209,716 and row 167,773 respectively, so any forward pass over 167,774 or more tokens loads and stores at the wrong rows. The startup profile run alone reaches this when `max_num_batched_tokens >= 167,774`.
- After the change every row offset in the 11 kernels is int64. Column, group, stream and tile indices stay int32.

## Validation

- `tests/models/qwen4_exp/test_row_offsets.py` (new) runs every HC op and `ple_gate` on inputs whose third row starts 2**31 + 8192 elements into its storage. It compares the result with the same rows stored contiguously, with `atol=0, rtol=0`. On CPU under `TRITON_INTERPRET=1`:
  - on `main` (`212f3666`) both tests crash (SIGSEGV);
  - on this branch both pass.
- Compiled for sm90 with Triton 3.6.0, no GPU needed: `_grouped_gemma_rmsnorm_kernel` on `main` emits `arith.muli %row, %stride_x : i32` (PTX `mul.lo.s32`), and on this branch `arith.muli %row_1, %x : i64`. `_ple_gate_kernel` behaves the same way for `t * key_rs`, `t * value_rs` and `t * HC * H`.
- A CPU-interpreter run of each kernel at rows 209,715 / 209,716 / 262,143 (and 167,772 / 167,773 for the PLE gate), with Flash-Next-sized row strides, reads the row at the int32-wrapped offset on `main`. On this branch it reads the right row. The NVIDIA and AMD variants behave the same.
- Not run on a GPU, and performance was not measured. The change adds one int64 conversion per program. The AMD kernels get the identical one-line change but no ROCm test.

## Details

- `hc_silu`'s own row strides (336/320) stay below the limit at these sizes. It is widened anyway so that every kernel in the file follows one rule.
- The test is in a new file because `test_hc_ops.py` is CUDA-only at module level, and some of its bit-exact comparisons do not hold under the interpreter. The new file holds only stride-invariance checks. It is added to the `models_basic` test area.
