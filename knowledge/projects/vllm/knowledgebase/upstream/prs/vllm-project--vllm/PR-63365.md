# [ROCm][Build][5/5] Speed up ROCm build: instantiate the fused MUSE-Spark op per head size

## Disclosure

AI assistance was used. The changes were reviewed and tested manually.

## Overview

**Splits the fused MUSE-Spark op on one item - `head_dim` (64/128/256), the whole op having landed in #62132 five days ago.**

`csrc/fused_muse_spark_qknorm_rope_kv_insert_kernel.cu` holds the whole fused MUSE-Spark qknorm/rope/kv-insert op: its host entry dispatches `head_dim` x `heads_per_group` x rope type, so 18 kernel instantiations land in a single translation unit. On a 9-arch build that unit is one of the longest compiles of the build - 478 s, behind only the int4 skinny GEMM (1232 s).

This PR instantiates one unit per `head_dim` (64/128/256): the kernels move into an include-only `fused_muse_spark_qknorm_rope_kv_insert_kernel.cuh` whose entry is a template over `HEAD_DIM`, each unit is two lines (`#include` + `VLLM_MUSE_SPARK_ENTRY(, hd)`), and `fused_muse_spark_qknorm_rope_kv_insert_api.cu` keeps the public symbol and dispatches on `head_dim`, `extern template` keeping the device code in the three units.

Same kernels, same dispatch rules, same numerics: the only change is which translation unit generates which `head_dim`, plus the runtime forward in the API unit. At 1 arch the file is not the build's tail, so the single-arch wall is unchanged.

**This one only pays off once the int4 unit is split** (#63364): while that 1232 s unit exists it is the tail regardless of what this op costs, so on `main` alone this PR is expected to be neutral. The 9-arch numbers below are therefore measured on top of the int4 split.

The single-arch rows are `pip install -e .` on MI350 (gfx950); the 9-arch row is the `setup.py bdist_wheel` described under *Validation*. All cold builds:

| build | `main` | this PR | All 5 PRs (#62921) |
|---|---|---|---|
| `MAX_JOBS=16`, gfx950 only | 107 s | 108 s | 87 s |
| `MAX_JOBS=64`, gfx950 only | 85 s | 87 s | 50 s |
| `MAX_JOBS=64`, 9 archs | 1263 s | 1241 s | 472 s |

## Claims

- Removes the second-longest compile of the 9-arch build (478 s, one unit) by instantiating one unit per `head_dim`: 3 units of the same total device code.
- Only pays off once the int4 unit is split; on `main` alone the 1232 s int4 unit stays the tail, so this PR is measured on top of #63364.
- Single-arch is unchanged within noise (107 -> 108 s at 16 jobs, 85 -> 87 s at 64).
- The op is not re-instantiated or reduced: each lane emits its `head_dim` arm's 18 configurations (2 dtypes x 3 heads_per_group x 2 rope types) exactly as before.
- One entry template with one explicit instantiation per `head_dim`, i.e. three distinct symbols; specialising a shared body by macro instead made the linker keep one copy and fail `head_dim` 128/256 at runtime.

### Why five PRs

The two builds are bound by different things, so no single change moves both.

**Why the three single-arch PRs are all needed.** At 1 arch (`gfx950`, `MAX_JOBS=64`, `main` = 85 s) three groups take turns setting the wall, in this order:

1. topk softplus-sqrt (#62717) - 74.5 s, a single unit
2. paged attention (#62716) - 71.6 s, the slowest of 12 units
3. other skinny GEMMs (#62718) - 40.9 s, a single unit

#62717 takes (1) to 7.4 s, #62716 takes (2) to 31.1 s and #62718 stops (3) from becoming the next tail; with all three the tail moves to `selective_scan_fwd` (37.7 s) and the build goes from 85 s to 49 s. Drop any one of them and a ~70 s unit is back at the top, so the single-arch win needs all three.

**Why that is not enough at 9 archs.** A 9-arch build multiplies every unit's time by ~9, and the tail becomes two files that none of the first three touch: `csrc/rocm/skinny_gemms_int4.cu` at 1232 s and `csrc/fused_muse_spark_qknorm_rope_kv_insert_kernel.cu` at 478 s. All three merged take the 9-arch build from 1263 s to only 1253 s. #63364 splits the first (its tail drops to 448 s) and #63365 the second (to 171 s), which is what reaches 472 s.

The `skinny_gemms_int4.cu` tail is invisible in a `gfx950` build because that file **only emits its kernels for RDNA (that is part of the 9-arch build)**:

https://github.com/vllm-project/vllm/blob/f4edf9f0f078ae67392510aafd1871288948a3c3/csrc/rocm/skinny_gemms_int4.cu#L17-L19
https://github.com/vllm-project/vllm/blob/f4edf9f0f078ae67392510aafd1871288948a3c3/csrc/rocm/skinny_gemms_int4.cu#L568-L579

`csrc/fused_muse_spark_qknorm_rope_kv_insert_kernel.cu` fails differently: it has no arch guard, so a `gfx950` build compiles it for real - it is just 25 s there against 478 s across nine archs, which is why a single-arch profile ranks it as irrelevant (#63365).

## Details

The kernel is untouched: the `__global__` template and the `DISPATCH_ARGS`/`DISPATCH_HPG`/`DISPATCH_ROPE_T` tower are unchanged. What changed is how the `head_dim` arm is selected - `HEAD_DIM` is a template parameter of `launchFusedMuseSpark`, so the runtime `switch (head_dim)` is a single `DISPATCH_ROPE_T(HEAD_DIM)` and each unit's symbols carry their own head_dim - plus the API unit dispatching to `..._typed<64/128/256>`. A `head_dim` outside 64/128/256 still reports "unsupported head_dim".

**How the file got this big.** It has no growth history: #62132 landed the whole op five days ago, in one TU, as 1 `__global__` with 8 templates and `head_dim` {64,128,256} x `heads_per_group` {1,2,4} x rope type {fp32, scalar_t} - 18 configurations per dtype pair, plus the fp8-output arms. Nothing has been added to it since.

So its 478 s at 9 archs is the cost of that configuration set on day one, not of accretion; this PR splits it into 3 units.

#### 1. 🔴 Blocking: Lane-dependent template body risks ODR violation across units
`csrc/fused_muse_spark_qknorm_rope_kv_insert_kernel.cu:579`

`launchFusedMuseSpark<scalar_t,...>` has external linkage (not in the anonymous namespace) and its `if constexpr` body varies per TU via `FUSED_MUSE_SPARK_LANE`, so the linker keeps one arbitrary weak copy for all three suffixed entry points. Two of three head_dims may hit `STD_TORCH_CHECK(false, "head_dim N not compiled")` depending on link order and inlining. Make the function depend on `head_dim` as a template parameter or place it in an anonymous namespace.

**How it is reached:** MuseSpark model forward (vllm/models/muse_spark/amd/model.py:588, gated at :545-554 on head_dim in (64,128,256), bf16/fp16, supported kv cache) or tests/kernels/test_fused_muse_spark_qknorm_rope_kv_insert.py -> vllm._custom_ops.fused_muse_spark_qknorm_rope_kv_insert -> torch.ops._C op -> _api.cu switch -> fused_muse_spark_qknorm_rope_kv_insert_hd{128,256} -> vllm::muse_spark_fused_ops::launchFusedMuseSpark<st,CACHE_T,KV_DTYPE> (weak symbol, linker keeps one lane's copy, likely hd64 by CMake order) -> STD_TORCH_CHECK(false, "head_dim N not compiled") at kernel.cu:579+

**Who is affected:** Every CUDA or ROCm build of _C: the fused MuseSpark op fails at runtime for every head_dim whose lane copy the linker dropped (two of 64/128/256), so the MuseSpark model's fused path and the kernel tests break.

_Checked against the code by an independent pass._

#### 2. 🟠 Should fix: No single-process test covers all three head_dims on split build
`tests/kernels/test_fused_muse_spark_qknorm_rope_kv_insert.py:251`

`launchFusedMuseSpark<scalar_t, cache_t, kv_dt>` is now implicitly instantiated with a different, `FUSED_MUSE_SPARK_LANE`-dependent body in each of `_hd64`/`_hd128`/`_hd256`.cu under one mangled name. Unless it is inlined, the linker keeps one body, and the other head_dims hit `head_dim N not compiled` at runtime. Only `test_fused_query_quant_matches_separate_quant` covers head_dim 128/256; the other tests use `HEAD_DIM=64`. That test is skipped on ROCm GPUs whose `fp8_dtype()` is FNUZ (gfx942/MI300), so there a broken build passes the whole file. Add head_dim 64/128/256 (and an unsupported head_dim) coverage that does not depend on E4M3FN Q output, or give the lane functions internal linkage.

**Who is affected:** ROCm FNUZ GPUs (MI300/gfx942) running this test file; on CUDA and E4M3FN ROCm the line-251 test still covers all three head_dims.

_Checked against the code by an independent pass._

#### 3. 🔵 Nit: Op signature hand-duplicated with no shared declaration
`csrc/fused_muse_spark_qknorm_rope_kv_insert_api.cu:12`

`fused_muse_spark_qknorm_rope_kv_insert_api.cu` hand-copies the 16-parameter op signature four times (three `_hdN` prototypes plus the entry definition) and does not include `csrc/ops.h`, which already declares the entry. If the signature changes in `kernel.cu`/`ops.h` but not here, a mismatch just creates a different C++ overload. The error then appears only when the `_hdN` or `torch_bindings.cpp` symbol is resolved (link, or `vllm._C` import), not at compile time. The `#define`-before-`#include` renaming in each `hdN.cu` is confined to that unit and does not touch vLLM's `ops.h` (`kernel.cu` includes only torch's `stable/ops.h`). Consider sharing one parameter-list macro or including `ops.h`, as `csrc/rocm/attention_dispatch.cu` does with `ATTN_ENTRY`.

**Who is affected:** Developers who later change this op's signature; no runtime effect on users of the current code.

_Checked against the code by an independent pass._

#### 4. 🔵 Nit: Dead LANE==0 fallback path is never built or validated
`csrc/fused_muse_spark_qknorm_rope_kv_insert_kernel.cu:576`

The `FUSED_MUSE_SPARK_LANE` default-0 fallback, the `LANE == 0 ||` guard clauses, and the comment describe a mode the build never uses, and a typo'd macro silently compiles a TU rejecting every head_dim at runtime. Replace the fallback with `#ifndef ... #error` at file scope, add a `static_assert`, and drop the `== 0 ||` clauses.

**Who is affected:** Maintainers of the MUSE-Spark kernel sources; no runtime effect in any shipped build configuration.

_Checked against the code by an independent pass._

**Related past reviews:** [#37503](https://github.com/vllm-project/vllm/pull/37503) on `CMakeLists.txt`

`csrc/fused_muse_spark_qknorm_rope_kv_insert_kernel.cu`

The now include-only kernel file keeps its `.cu` extension and still defines the unsuffixed `fused_muse_spark_qknorm_rope_kv_insert`; re-adding it to a source list would duplicate that symbol. Rename it to `.cuh` or add `#error` when `FUSED_MUSE_SPARK_LANE` is undefined, matching the attention split.

**Who is affected:** Only a future maintainer who adds `csrc/fused_muse_spark_qknorm_rope_kv_insert_kernel.cu` back to a CMake source list; today's build is unaffected.
