# [XPU] Route flash-attn imports through fa_utils in FlashAttn MLA sparse and dots3

[Upstream PR](https://github.com/vllm-project/vllm/pull/62985) · state: open · merged: False

## Original PR description

## Overview

Several modules import CUDA-only packages at module level, so they fail to import on XPU. The fix:
- Switch these modules to the platform-dispatching re-exports in `vllm.v1.attention.backends.fa_utils` and `vllm.utils.deep_gemm`.
- Make `fa_utils.is_fa_version_supported()` report FA2 on XPU.

Behaviour on CUDA is unchanged.

Related: #58913

## Claims

- On XPU, `vllm.v1.attention.backends.mla.flashattn_mla_sparse` and backends that subclass `FlashAttnMLASparseBackend` can now be imported. Their `flash_attn_varlen_func` is the XPU one from `vllm_xpu_kernels`.
- The `vllm.models.dots3_note` package now imports on XPU:
  - The text DSA attention, vision encoder and audio encoder use the platform `flash_attn_varlen_func`.
  - The vision and audio encoders select FA2 instead of falling back to eager attention.
- On XPU, `is_fa_version_supported(v)` now matches `get_flash_attn_version()`: `True` only for `v == 2`. Before this change it was `False` for every version.
- The vision MoE FP8 weight cast uses the in-tree `vllm.utils.deep_gemm.per_block_cast_to_fp8`. On XPU its output is bit-exact with DeepGEMM's `gran_k` formula.

## Details

**Root cause.** Three modules import CUDA-build-only packages at module level:

| Module | Import that fails on XPU | Why it fails |
|---|---|---|
| `flashattn_mla_sparse.py` | `vllm.vllm_flash_attn.flash_attn_interface` | not built on XPU |
| dots3 `attention.py`, `audio_encoder.py`, `vision_attention.py` | `vllm.vllm_flash_attn` | not built on XPU |
| dots3 `vision.py` | `vllm.third_party.deep_gemm` | only vendored by CUDA builds that bundle DeepGEMM (`cmake/external_projects/deepgemm.cmake`) |

`vllm/models/dots3_note/__init__.py` imports `multimodal`, which imports `vision`. So the `vision.py` import breaks every import from the `dots3_note` package on XPU, not only the vision encoder.

**The fix.** Import through the existing platform-dispatching helpers, as the other flash-attn backends already do:
- `fa_utils.flash_attn_varlen_func`: on CUDA it is the same `vllm_flash_attn` object; on XPU it is `xpu_ops.flash_attn_varlen_func`.
- `fa_utils.is_fa_version_supported`: on CUDA it still delegates to `vllm_flash_attn`.
- `vllm.utils.deep_gemm.per_block_cast_to_fp8` with `block_size=[block_size, block_size]`. This is the same math as DeepGEMM's `gran_k=block_size`, using `current_platform.fp8_dtype()`.

**Effect on CUDA.**
- The flash-attn import change is a no-op: the same function objects are used.
- The vision FP8 cast now uses the in-tree pure-torch port instead of the vendored DeepGEMM helper. The math is identical, and it runs once, at weight loading.

**Limitations.** On XPU, the FlashAttn MLA sparse path and the dots3 sparse DSA path call `flash_attn_varlen_func(..., q_v=...)`. Two more pieces are needed before those results are numerically correct on XPU:
- the `q_v` kernel in vllm-xpu-kernels (<K2 PR link>);
- a follow-up PR that forwards `q_v` in `xpu_ops` and bumps the `vllm_xpu_kernels` pin.

This PR only makes the modules importable and correctly wired.
