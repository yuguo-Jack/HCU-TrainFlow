[Upstream PR](https://github.com/vllm-project/vllm/pull/64416) · state: open · merged: False

## Original PR description

## Overview

Document how to diagnose incorrect KV contents when NIXL reports successful transfers, including the GH200 configuration reported in #64048, the identified RDMA-core root cause, and the upstream Linux fix. Add an entry from the distributed troubleshooting guide.

## Claims

- Add P/D versus local controls, block/layer content verification, and registration-address tracking across restarts.
- Attribute the hardware results to the reporter and preserve the B300/x86 counterexample and GPUDirect prerequisites.
- Describe the registration alignment/length trigger and link Linux fix `15fe76e23615`, included in v7.1. Explain why the active RDMA stack must contain it or an equivalent backport; a kernel upgrade alone may not replace external DOCA-OFED DKMS modules.
- Document separate dma-buf, host-staging, and TCP experiments without changing runtime behavior.

## Details

Issue-number and area searches found no equivalent open documentation PR at preparation time. This documents the findings and reproducer from the closed investigation ai-dynamo/nixl#2512 and complements #62211 (runtime KV checksums). The warning proposal ai-dynamo/nixl#2536 was closed without merging; the guide no longer presents it as active work.

The guide distinguishes transfer completion from data integrity, explains why changing allocation addresses can confound restart comparisons, and removes the RDMA-only device restriction for the TCP control. The root cause is attributed to the reporter's latest findings and linked to torvalds/linux@15fe76e23615 ("RDMA/umem: Fix truncation for block sizes >= 4G"). The note explains the 32-bit iterator truncation for large contiguous DMA blocks, the DOCA-OFED 26.01-1.0.0 DKMS caveat, and upgrading the RDMA modules actually loaded on both hosts. The revision states the virtual/DMA alignment and registration-length requirements, explains the reported first bad layer, and adds the clean control. It corrects the hardware description and firmware details, retains the B300/x86 counterexample with matching forced alignments, and adds `modinfo -n ib_core` guidance without treating a module path as proof that a fix is loaded. Lower-level allocation/registration workarounds are distinguished from vLLM startup settings. Disabling dma-buf does not guarantee unchanged performance on other deployments.

- 0z5a · COMMENTED · 2026-10-31T14:03:32Z · [source](https://github.com/vllm-project/vllm/pull/64416#pullrequestreview-5723085734)

Thanks for writing this up! I reported #64048, and I checked the text against the issue, ai-dynamo/nixl#2512 and torvalds/linux@15fe76e23615. The root-cause description, the DOCA-OFED DKMS caveat and the evidence table are accurate. A few things to fix before this is merged:

1. **Stale links (L550-553).** ai-dynamo/nixl#2512 is closed, and ai-dynamo/nixl#2536 was closed without being merged. I'd drop the warning-proposal sentence and point to #2512 as the closed investigation that has the data and the NIXL-only reproducer, rather than "follow it for the investigation".

2. **State the trigger, so readers can tell whether they are affected (after L489).** Something like:

   > The bug can only trigger when a GPU memory registration's base is aligned to exactly 2^k with k >= 32, in both virtual address and DMA address, and the registration is longer than 2^k. Bytes at offset >= 2^k then hit offset mod 2^k (the registration wraps), while the transfer still reports success with the full byte count. k = 31 was clean in all reported runs. It was observed on the dma-buf registration path, which is why `UCX_CUDA_COPY_DMABUF=no` avoids it (UCX then registers through `nvidia_peermem`). In vLLM the KV cache is layer-major, so with a 2^32-aligned base the layers that lie below the 4 GiB offset arrive intact. The first bad layer is ceil(4 GiB / per-layer stride), which was layer 3 at about 1.48 GiB per layer in the report.

   Relatedly, L494 ("virtual-address alignment alone does not diagnose the failure") is true, but a base aligned to 2^32 or more is *necessary*, just not sufficient. It would help to say that explicitly, and to say "the same" alignment at L492 (the B300 test used exactly 2^31/2^32/2^33). The unforced runs with a base aligned to only 2^29–2^31 (6/6, all 262 blocks matched) could also go in the table as the clean control.

3. **Fixed release (L489).** The fix is in Linux v7.1. Adding that next to "marked for stable backporting" lets readers identify a fixed kernel.

Nits:
- L466: the issue says "GH200 480GB". The HBM size isn't from the report. Adding the NIC firmware (32.38.3056 and 32.43.1014, both affected) would help rule firmware out.
- L462: the heading reads as GH200-only, while x86 isn't proven immune. Maybe "RDMA-core truncation with >= 4 GiB-aligned GPU registrations (reported on GH200)".
- L506: a concrete way to check the loaded module would help, e.g. `modinfo -n ib_core` shows whether it comes from a DKMS/OFED `updates/` path or from the in-tree one.
- Optional: the other two workarounds from the root-cause comment (registrations of at most 2 GiB, avoiding bases aligned to 2^32 or more) apply below vLLM, since vLLM has no knob for them.
