# [CI] Run test_depyf_integration in a spawned process

[Upstream PR](https://github.com/vllm-project/vllm/pull/65473) · state: open · merged: False

## Original PR description



## Overview

`test_depyf_integration` forks its test process on CUDA, so it fails with `Cannot re-initialize CUDA in forked subprocess` whenever an earlier test in the same pytest session has initialized CUDA. This runs it in a spawned process instead, as ROCm already does. Needed before vllm-project/ci-infra#888 merges: that PR changes how PyTorch Fullgraph is sharded, and its new plan puts such a test first in the same session.

## Claims

- `test_depyf_integration` passes no matter which tests run before it in the session.
- No other test changes: one decorator argument.

## Validation

- **Without the fix:** staging build [99301](https://buildkite.com/vllm/ci/builds/99301) (ci-infra#888's sharding plan): PyTorch Fullgraph shard 5/7 ran `test_clone_elimination.py`, then `test_depyf_integration` failed with `Cannot re-initialize CUDA in forked subprocess`.
- **With the fix:** staging build [99622](https://buildkite.com/vllm/ci/builds/99622), same plan, same order on shard 5/7: all 7 shards passed. 42 passed / 1 skipped, the same counts and the same test IDs as a recent main build.
- On main today the test passes only because no CUDA-initializing test runs before it in its shard.

## Details

- **Root cause:** `create_new_process_for_each_test()` defaults to fork on CUDA (`tests/utils.py`). `test_clone_elimination.py` creates a CUDA tensor in the pytest process, so a forked child of that process can't initialize CUDA. The failure depends on test order, not on depyf.
- **Why spawn on the test, not on the step:** it fixes the test wherever it runs, and the same decorator argument is already used by the cudagraph and worker tests.
