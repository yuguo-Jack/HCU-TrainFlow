# [Bugfix][Spec Decode] Validate the dynamic SD schedule when building the config

[Upstream PR](https://github.com/vllm-project/vllm/pull/62974) · state: open · merged: False

## Original PR description



## Overview

Validate the dynamic speculative decoding schedule (`num_speculative_tokens_per_batch_size`) while building `VllmConfig`, so an invalid schedule fails at startup instead of after the model has loaded.

## Claims

- An invalid schedule (overlapping ranges, not starting at 1, negative K, start > end) now raises in `EngineArgs.create_engine_config()`, before the model loads.
- An empty schedule warns and falls back to the static `num_speculative_tokens`. Before, it crashed engine startup on Model Runner V2.
- Schedules that vLLM already drops (data parallelism, methods Model Runner V1 doesn't support) are still dropped with the existing warning, not rejected.
- The schedule rules are documented in the field docstring and on the Dynamic Speculative Decoding page.

## Details

**Root cause.** The schedule was only validated in `build_dynamic_sd_schedule_lookup`. Its callers that raise run in `EngineCore` after the model loads: the V2 CUDA graph manager (which hits it first) and `Scheduler.__init__`. The early call in `VllmConfig`'s capture-size code caught and ignored the `ValueError`.

**Fix.** `VllmConfig._validate_dynamic_sd_schedule()` runs right after `_maybe_disable_dynamic_sd_for_data_parallel()` and `_maybe_disable_dynamic_sd_for_v1()`, so a schedule they drop is never validated and those configs keep starting. A `SpeculativeConfig` field validator would run before those steps and break them. The now-dead `try/except` in the capture-size code is removed, and the `object` parameters in `dynamic/utils.py` are typed.

**Not changed.** `build_dynamic_sd_schedule_lookup` still validates its own input. K values above `num_speculative_tokens` are still capped silently (now documented).

**Not a duplicate.** No open PR validates the schedule at config time. #48944 and #54801 extend the schedule; this change only calls the module's validator, so it should carry over. #52087 edits the same `VllmConfig` methods, so one of the two will need a small rebase. #54748 and #61123 are complementary.
