# [Bugfix][CPU] Point the short-node KV cache error at --gpu-memory-utilization

[Upstream PR](https://github.com/vllm-project/vllm/pull/63442) · state: open · merged: False

## Original PR description

## Overview

Since #59405 removed the reservation check in `CPUWorker.__init__`, `determine_available_memory` is the only place that checks the CPU memory reservation. When the node is short of memory, its error only says to free memory elsewhere, so a default `LLM(...)` / `vllm serve` on a busy machine no longer mentions `--gpu-memory-utilization`, which is the actual fix. This PR makes the error suggest a reservation that fits, or an explicit KV cache size.

## Changes

- When the node is short of free memory, the error explains that `--gpu-memory-utilization` sets the CPU reservation and suggests a value: `floor((worker_rss + available - 1 GiB) / total, 2)`, worded as "X or lower". It also mentions `--kv-cache-memory-bytes` / `VLLM_CPU_KVCACHE_SPACE`.
- The 1 GiB of headroom was added after review: suggesting the exact boundary got the worker OOM-killed on a 7.76 GiB node (see the thread).
- When even that leaves no room for KV (node almost full), only the old advice is given, so the error does not suggest a fraction that would hit the "worker outgrew its reservation" error from #59472.
- Only the error path changes. When the budget fits, sizing and startup are unchanged.

## Validation

Apple M3 Pro, 18 GiB, macOS 15.6.1, CPU backend, `Qwen/Qwen3-0.6B`, `dtype=float16`, defaults otherwise (`gpu_memory_utilization=0.92`):

| | Result |
|---|---|
| `main` | `ValueError: Available memory on node 0 (4.21/18.0 GiB) on kv cache allocation is less than requested memory for kv (14.9/16.56 GiB). Reduce CPU memory used by other processes.` |
| this branch | `ValueError: Available memory on node 0 (2.71/18.0 GiB) on kv cache allocation is less than requested memory for kv (15.76/16.56 GiB). On the CPU backend, the `--gpu-memory-utilization` flag controls the fraction of CPU memory reserved (despite its name). To resolve: decrease `--gpu-memory-utilization` to 0.13 or lower (free memory varies between runs), set the KV cache size explicitly with `--kv-cache-memory-bytes` or VLLM_CPU_KVCACHE_SPACE, or reduce CPU memory used by other processes.` |
| this branch, `gpu_memory_utilization=0.13` | starts (`Auto set (1.0/18.0) GiB for KV cache on node 0`), generation OK |

On the 7.76 GiB Codespace from the review, the previous revision suggested 0.63 and the worker was OOM-killed, while 0.50 ran. For the same numbers the new formula gives 0.50; this case is now a unit test.

## Details

**Root cause.** #59405 removed the startup check because pooling models without a KV cache should not need the reservation; `determine_available_memory` was expected to catch the KV case later. #59472 reworded one of its two errors (worker outgrew its reservation). The other (node short of memory) still says `Reduce CPU memory used by other processes.` With the startup check gone, nothing tells users to lower `--gpu-memory-utilization`, even though the default is 0.92 of RAM.

**Suggested value.** The worker needs `rss + kv <= reservation`, and the node can supply at most `available` more, so `(rss + available) / total` is the boundary. The suggestion stays 1 GiB below it, because memory is still allocated after this check and `available` changes between runs.

**Why not restore the startup check?** It was removed at the maintainer's request in #59405; restoring it would break pooling models in small containers again.

**Tests.** Unit-level, following the existing file. Free host memory cannot be controlled reliably through `LLM` in CI, so the end-to-end check is the manual run above.

**Related.** #62653 (open, docs) documents the startup message removed by #59405; this PR puts equivalent advice in the KV allocation error. #58924 (open) changes which memory node is queried (s390x); whichever lands second needs a trivial rebase.

**Not a duplicate.** No open issue or PR covers this error. Searched on 2026-10-24 and again on 2026-11-03.
