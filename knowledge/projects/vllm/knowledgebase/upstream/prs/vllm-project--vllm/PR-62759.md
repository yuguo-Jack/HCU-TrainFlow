# [Quant] LUT-B MoE with MXFP8 activations: native Rubin kernel + emulation

[Upstream PR](https://github.com/vllm-project/vllm/pull/62759) · state: open · merged: False

## Original PR description

<!-- claude-projects-attribution: {"github_login":"mgoin"} -->


## Overview

Adds `--quantization lut_b_moe`: online LUT-B quantization of routed MoE experts with MXFP8 activations. On Rubin (SM 10.7) it runs a new native grouped GEMM built on `tcgen05.mma.kind::mxf8f6f4.block_scale.decompress::lut::b`; every other GPU emulates the same numerics so accuracy can be checked without Rubin hardware.

This reworks #51880 on current main. That PR emulated LUT-B weights with BF16 activations, which Rubin cannot run natively (the LUT-B tensor core forms only take FP8/FP6/FP4 A), and it needed a fused Triton decode GEMM plus a dequantize fallback. This PR replaces it; #51880 can be closed. No other open PR touches LUT-B.

## Claims

- New `lut_b_moe` online scheme (MoE only, dense layers unquantized): 3-bit indices into an E4M3 codebook plus a UE8M0 exponent per 8x64 weight tile (3.14 bits/weight logical), MXFP8 activations (E4M3, UE8M0 per 1x32).
- Native Rubin path (`LutBSm107Experts` + `ops.lut_b_moe_gemm`): weights stay packed in memory and are decoded by the tensor core (`UTCQMMA.LUTB` in SASS). A deliberately simple kernel, not tuned for peak throughput.
- Emulation path (`LutBEmulationTritonExperts`): dequantize weights once at load, MXFP8 quantize-dequantize activations before each GEMM, run the existing BF16 `TritonExperts`. Selected automatically off Rubin, or with `--moe-backend emulation`.
- GLM-4.7-Flash on Rubin: GSM8K for native (0.839) and emulated (0.843) LUT-B agree within one standard error and sit about 1.5 points below BF16 (0.857). Loaded memory drops from 56.3 to 15.9 GiB (Qwen3.6-35B-A3B: 65.5 to 18.6 GiB).

## Validation

All runs on one Rubin GPU (CC 10.7, CUDA 13.4, driver 615.22).

**Kernel/unit tests** (`tests/kernels/moe/test_lut_b_moe.py`, 14 tests, plus `test_quantization_config_args.py` and `test_online.py::test_online_lut_b_moe`): 46 passed on Rubin. They cover packing, the SM107 tile layout against an independent per-element decoder, emulation against a loop reference, one native grouped GEMM against an FP64 reference of the decoded operands, and native vs emulated full MoE for 1/33/300 tokens.

**GSM8K, reference model** zai-org/GLM-4.7-Flash (lm_eval 0.4.13, 5-shot, all 1319 questions, non-thinking chat mode, `max_gen_toks=2048`, TP=1, one Rubin GPU):

## Details

**Format.** Same tile as #51880 (8 output channels x 64 K, eight E4M3 entries), plus one UE8M0 exponent per tile. The exponent maps onto the instruction's per-32-K B scale, which has to be supplied anyway, so it is free at runtime. Without it, small-magnitude tiles fall into the E4M3 subnormal grid: on Qwen3.6-35B-A3B experts (layers 0/10/20/39, gate_up and down) relative weight MSE is 0.038-0.040 with the exponent versus 0.044-0.045 without.

**Rubin kernel** (`csrc/moe/lut_b_moe_sm107.cu`, compiled only for `10.7f` with CUDA >= 13.4). One CTA computes a 128x128 output tile of one expert over rows from `moe_align_block_size(block_size=128)`. Four warps fill a 3-stage `cp.async` pipeline (gathered E4M3 rows, A scales, and a pre-laid-out 7 KB weight tile per 128N x 128K), one thread copies scales/codebooks to TMEM with `tcgen05.cp` and issues the two K64 LUT MMAs per K128 (collector fill, then lastuse), and all warps run a TMEM-to-BF16 epilogue that scatters rows back to `sorted_token_ids` order. Weights are rearranged once at load (`lut_b_to_sm107_tiles`, 3.5 bits/weight resident including padding). Layouts and instruction descriptors follow the dense LUT-B probes that were validated on Rubin.

**Limitations.**
- Native path needs hidden and per-partition intermediate sizes divisible by 128, no bias, and no LoRA; otherwise it falls back to emulation with a log line.
- M is padded to 128 rows per expert, so decode wastes tensor-core work. No swap-AB / small-N tile, no TMA, no persistent scheduling.
- Expert parallelism goes through the standard `expert_map` handling but was not exercised on hardware.
- Emulation stores dequantized weights: it validates accuracy, not memory or speed.

**CI coverage.** CI has no Rubin GPUs, so the native tests skip there; the emulation, layout, and config tests run on any CUDA GPU.
