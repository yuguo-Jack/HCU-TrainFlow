# [Bugfix] [Rust Frontend]Reject unsupported gRPC sleep levels

[Upstream PR](https://github.com/vllm-project/vllm/pull/62774) · state: closed · merged: False

## Original PR description



## Overview

Reject gRPC `Sleep` requests with levels above 2 before they reach the
engine. Previously, unlike the Python and Rust HTTP endpoints, the gRPC
endpoint forwarded unsupported levels and could leave model buffers
unrecoverable after wake-up.



## Claims

- Return gRPC `INVALID_ARGUMENT` for sleep levels above 2.
- Preserve the existing default and valid levels 0, 1, and 2.
- Reject invalid levels before acquiring the RL lock or calling the engine.
- Add an in-process gRPC regression test that verifies invalid requests are
  not forwarded while level 2 remains accepted.



## Validation
```
cargo nextest run -p vllm-server \
  control_sleep_rejects_level_above_two_before_engine_call

cargo nextest run -p vllm-server --all-features --locked  --no-fail-fast

cargo clippy  -p vllm-server --all-targets --all-features  --locked -- -D warnings
```



## Details

The Python sleep endpoint constrains `level` to the range 0 through 2, and
the Rust HTTP endpoint performs the same validation. The gRPC handler only
applied the default value and forwarded the result directly to the engine.

An unsupported value such as 3 reaches the GPU worker as a level greater
than or equal to 1. Model buffers are saved only for level 2, while weights
are offloaded only for level 1. As a result, level 3 can discard resources
without preserving all state needed by wake-up, allowing later inference to
return incorrect output without a request-level error.

The validation is placed at the gRPC boundary owned by `vllm-server` and
uses the same error message as the Rust HTTP endpoint. No protobuf, engine,
worker, or Python behavior is changed.
