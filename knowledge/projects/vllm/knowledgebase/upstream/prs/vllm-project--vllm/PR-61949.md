# [Rust][Frontend] Return routed experts from the generate route

[Upstream PR](https://github.com/vllm-project/vllm/pull/61949) · state: closed · merged: True

## Original PR description

## Purpose

The Rust `/inference/v1/generate` route silently drops routed-expert (R3) data. With `--enable-return-routed-experts`, the Python route returns `choices[].routed_experts` (base64 `.npy`, shape `[num_tokens - 1, num_layers, top_k]`) on the terminal response; the Rust route has no such field, so R3 is unavailable behind the Rust frontend.

This PR returns the same field from the Rust route:

- `vllm-engine-core-client`: decode `EngineCoreOutput.routed_experts` as a `WireNdArray` (previously an opaque value) and resolve its aux frame.
- `vllm-llm`: collect per-step rows in `GenerateOutputStream` and concatenate them on the terminal output, as Python `RequestState.make_request_output()` does; a dtype or row-shape change returns an error instead of a corrupt array.
- `vllm-server`: return `routed_experts` on the non-streaming response and on the final streaming chunk. The existing float32-only `npy_base64` now encodes any NumPy dtype and shape, byte-identical to `numpy2base64`.
- `vllm-text`: accept `sampling_params.routed_experts_prompt_start` (previously always lowered as 0), validate `0 <= start <= prompt_len` like the Python input processor (400 otherwise), and forward it to EngineCore.

The Rust generate route has no API-side stop strings, so Python's stop-string row trimming does not apply. Returning routed experts from the OpenAI-compatible routes is out of scope.

## Test Plan

```bash
cd rust
cargo test -p vllm-engine-core-client -p vllm-llm -p vllm-text -p vllm-server
cargo fmt --all --check
cargo clippy --workspace --tests
```

- `python_msgpack_fixtures_match_rust_encoding`: the Python fixture now carries an inline `|u1` ndarray, decoded by Rust.
- `generate_merges_outputs_by_stream_interval`: rows from six engine steps, merged by `stream_interval`, appear only on the terminal output, concatenated in order.
- `routed_experts_match_numpy2base64`: byte-identical to `numpy2base64` for 3-D `uint8`, 3-D `int32`, 1-D `uint16` and an empty `(0, 2, 2)` array.
- `generate_chunk_stream_returns_routed_experts_on_final_chunk`: only the final streaming chunk carries the field.
- `lower_sampling_params_validates_routed_experts_prompt_start`: default 0, `start == prompt_len` accepted, `start > prompt_len` rejected as a request validation error.
- `prepare_generate_request_maps_token_prompt_and_sampling_params`: the generate route parses and forwards the field.

Each server: non-streaming and streaming with `routed_experts_prompt_start` in {0, 5, prompt_len}, a 213-token prompt, an EOS finish, and 16 concurrent mixed requests. Checked that rows == `prompt_len + num_output_tokens - 1 - start`, shape `[rows, 48, 8]` uint8, expert ids in range and distinct per row, only the final streaming chunk carries the field, streaming equals non-streaming, and `start = k` returns the suffix of `start = 0`. `start = prompt_len + 1` returns 400.

Rust vs Python frontend, same greedy requests (16- and 213-token prompts): identical `token_ids` and byte-identical `routed_experts` base64 strings.
