# [Bugfix] Skip Ray actor kill after the driver has disconnected

[Upstream PR](https://github.com/vllm-project/vllm/pull/45328) · state: open · merged: False

## Original PR description

## Overview

Skip Ray actor cleanup when its owning driver has already disconnected. This prevents shutdown from starting another Ray session with stale actor handles.

Fixes the teardown `ActorHandleNotFoundError` from #45318 (closed by the stale bot). The reporter confirmed this guard on four DGX Spark nodes with Ray 2.55.1: the error no longer appears and the real initialization failure surfaces instead. Not a duplicate: `gh pr list --state open --search "45318 in:body"` returns nothing, and no open PR changes these shutdown paths.

## Claims

1. The engine actor manager and the Ray executor avoid actor or placement-group RPCs after disconnect.
2. Connected cleanup still runs, including local message-queue cleanup.
3. Worker initialization failures retain the original diagnostic without a secondary `ActorHandleNotFoundError` (shown on the previous base; not re-run after #61712 removed the legacy executor).

## Validation

Tested with Ray 2.56.1 on an RTX PRO 6000, on the previous base `0154979656`:

1. `pytest tests/v1/engine/test_core_engine_actor_manager.py -q`: nine passed.
2. Actual local Ray actor and placement-group checks for all three shutdown paths: six connected/disconnected cases passed, including a compiled DAG for the V1 executor.
3. Two-layer Qwen3 with dummy weights and Ray data-parallel/worker backends: four tokens generated, then connected cleanup completed. Explicit driver disconnect followed by engine cleanup leaves Ray disconnected; the fixture waits for its asynchronous monitor before exiting.
4. A supported custom worker raising during `init_device` reproduces a secondary stale-handle error on main. The patch preserves the original worker error without that extra error.
5. Ruff 0.14.0 check/format and `git diff --check` pass.

No model-quality, performance, or multi-GPU result is claimed. The initial immediate-exit fixture exposed a Ray native wait still running during Python finalization. Waiting for that monitor makes the fixture exit normally; this patch does not claim to fix general concurrent Ray shutdown or immediate interpreter exit.

## Details

`RayExecutorV2.shutdown` now always clears `ray_worker_handles`; the `shutting_down` flag already prevents re-entry. The new unit test covers `CoreEngineActorManager.shutdown`; the executor guard was checked with the local Ray cases above.

Ray actor operations can initialize a driver implicitly. During partial initialization cleanup or after an explicit disconnect, old actor handles belong to a finished session. Guard those RPCs with the existing `ray.is_initialized()` API while preserving local cleanup and the manager stop event.

Rebased onto upstream `f46021a7faa62015016f2862d02f2a64c24bb960`. Main removed the legacy Ray executor (#61712), so that file's hunk is gone; the guards in the engine actor manager and `ray_executor_v2.py` are unchanged. On the rebased head, the 10 tests in `tests/v1/engine/test_core_engine_actor_manager.py` that do not start a Ray cluster pass, including the new `test_shutdown_skips_ray_cleanup_after_driver_disconnect`, which fails with main's `vllm/v1/engine/utils.py`; the 5 cluster-backed tests were not rerun here. The related worker-extension lifecycle-hook and elastic scale-up proposals have different triggers and do not replace these disconnected-driver guards.
