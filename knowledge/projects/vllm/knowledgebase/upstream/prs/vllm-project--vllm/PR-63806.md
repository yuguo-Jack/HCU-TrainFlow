# [Perf] Compile the logprobs rank op during V1 sampler warm-up

[Upstream PR](https://github.com/vllm-project/vllm/pull/63806) · state: open · merged: False

## Original PR description



## Overview

On the V1 model runner, the `torch.compile` of `batched_count_greater_than` (token ranks in `Sampler.gather_logprobs`) runs inside the first real request that asks for logprobs, not at startup. This PR runs `compute_logprobs` + `gather_logprobs` once in `_dummy_sampler_run` so the compile happens during warm-up.

**Not a duplicate:** searched open PRs/issues for `batched_count_greater_than`, "logprobs warmup" and "logprobs first request". #38933 (merged) removed the batch-size-1 recompile; #55918 and #59976 cover MRV2 warm-up only.

## Claims

- No dynamo graph is compiled on the request path for the first `logprobs` / `prompt_logprobs` request (1 before, 0 after).
- First logprobs request 0.28-0.45 s faster (Qwen2.5-1.5B, 1x A40); startup time within noise.
- The profile run now accounts for the transient float32 `[max_num_seqs, vocab]` logprobs buffer.
- No output change: warm-up results are discarded and the sampling path is unchanged.

The new test checks that `_dummy_sampler_run` compiles the op exactly once and that later `gather_logprobs` calls with batch sizes 1 and 3 do not compile again. On main d0d681e4 it fails (`assert 0 == 1`); with this change it passes. Full run on d0d681e4: 58 passed, 1 skipped, plus `test_batched_count_greater_than.py` 2 passed. pre-commit on changed files passes; mypy shows no new errors.

End to end with `bench_first_logprobs.py` (below): `LLM(Qwen/Qwen2.5-1.5B-Instruct)`, `VLLM_USE_V2_MODEL_RUNNER=0`, 1x A40; one plain request, then three with `logprobs=1`, then a batch of 7, counting dynamo graphs compiled during requests. Fresh process per run; "cold" runs use fresh `VLLM_CACHE_ROOT`, `TORCHINDUCTOR_CACHE_DIR`, `TRITON_CACHE_DIR`. These numbers were measured on an earlier main (550c1cb) and not re-run on d0d681e4.

```python
"""Latency of the first vs. later requests with logprobs (V1 model runner).

Run in a fresh process per measurement so the dynamo cache is cold.
"""
import os
import sys
import time

os.environ.setdefault("VLLM_USE_V2_MODEL_RUNNER", "0")
from vllm import LLM, SamplingParams  # noqa: E402

model = sys.argv[1] if len(sys.argv) > 1 else "Qwen/Qwen2.5-1.5B-Instruct"
t0 = time.perf_counter()
llm = LLM(model=model, gpu_memory_utilization=0.5, max_model_len=2048, seed=0)
startup = time.perf_counter() - t0
prompt = "The capital of France is"
plain = SamplingParams(max_tokens=8, temperature=0)
lp = SamplingParams(max_tokens=8, temperature=0, logprobs=1)
llm.generate(prompt, plain, use_tqdm=False)  # generic first-request costs
import torch._dynamo.utils as du  # noqa: E402

graphs0 = du.counters["stats"]["unique_graphs"]
res = []
for p in (lp, lp, lp):
    t = time.perf_counter()
    llm.generate(prompt, p, use_tqdm=False)
    res.append(time.perf_counter() - t)
t = time.perf_counter()
llm.generate([prompt] * 7, lp, use_tqdm=False)
batch7 = time.perf_counter() - t
print("compiled_graphs_during_requests", du.counters["stats"]["unique_graphs"] - graphs0)
print(f"RESULT startup_s={startup:.2f} first_logprobs_ms={res[0]*1e3:.1f} "
      f"second_ms={res[1]*1e3:.1f} third_ms={res[2]*1e3:.1f} "
      f"batch7_ms={batch7*1e3:.1f}")
```

## Details

Root cause: `batched_count_greater_than` is `torch.compile`'d with the batch dim marked unbacked since #38933, so one compile covers every batch size. But `_dummy_sampler_run` (profile run and post-capture warm-up) samples with `max_num_logprobs=None`, so the compile never ran at startup. The first request with logprobs paid dynamo + inductor compile, on every fresh replica (restart, scale-up).

Fix: 8 lines in `_dummy_sampler_run`, inside the existing OOM-guarded block. The legacy MRV1 path needs this because it is still the runner for deployments not on MRV2; MRV2 is not affected (it computes ranks with a Triton kernel, and #55918 / #59976 cover its warm-up). Tradeoff: the profile run briefly allocates the `max_num_seqs * vocab_size * 4` byte buffer, the same buffer a full batch with logprobs allocates at serving time.

Confirmed and fixed in e4a8d85a. In `raw_logits`/`processed_logits` modes the prompt scores are `logits.to(torch.float32)`, which is a no-op for an fp32 LM head, so they keep the padded-vocab row stride and Dynamo compiles a second graph of `batched_count_greater_than`. The warm-up now also runs `gather_logprobs` on `logits.to(torch.float32)` in those two modes, i.e. the exact layout `_get_prompt_logprobs_dict` produces. The new test `test_dummy_sampler_run_compiles_padded_vocab_logits_scores` uses fp32 logits sliced from a padded vocab (stride 32, width 30) for both modes and checks that the prompt and sampled paths at batch sizes 1 and 3 add no compile after warm-up; it fails without the change (2 compiles instead of 1) and passes with it.
