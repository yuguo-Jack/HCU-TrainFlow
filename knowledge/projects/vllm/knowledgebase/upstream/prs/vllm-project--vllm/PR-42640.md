# linear: add CDNA-tuned W4A16 linear kernel 

[Upstream PR](https://github.com/vllm-project/vllm/pull/42640) · state: open · merged: False

## Original PR description

## Summary

Adds `CDNAHybridW4A16LinearKernel`, a W4A16 GPTQ/AWQ linear kernel for AMD CDNA GPUs (MI300 — gfx942 / gfx950). Closes the CDNA gap on issue #34008 that neither of the existing W4A16 PRs addresses:

- **#40977** (`HybridW4A16LinearKernel`) gates on `on_gfx1x()` — gfx11/gfx12 only. Its HIP skinny GEMM is wave32-locked (DPP masks and `__shfl_xor(val, 16)` are hard-coded for 16-lane half-waves), so it cannot be reused on CDNA wave64 even with the gate removed.
- **#41394** (`RDNA3W4A16LinearKernel`) gates on `on_gfx11()` — gfx1100 only, using WMMA which doesn't exist on CDNA at all.

AITER ships no W4A16 GEMM (only A4W4 and A8W8, and A4W4 explicitly errors on gfx942), so there is no AMD-native op to wrap. This PR adds the missing pure-Triton path, gated by `on_mi3xx()`; non-CDNA ROCm boxes fall through to `TritonW4A16LinearKernel` automatically.

## Why a new kernel instead of tuning the existing Triton W4A16

The existing `TritonW4A16LinearKernel` is correct on CDNA but leaves performance on the table because of three layout choices that are wrong for wave64 decode:

1. **Weight layout** is `[K, N//8]` (GPTQ sequential along N). With this layout, each wave's 64-lane load straddles 64 different N-columns and the per-output-column scales must be re-fetched for every K-group. Switching to `[N, K//8]` (ExLlama shuffle along K — same format used by PR #40977) makes each wave's load contiguous in the K-dimension for one output row, and lets the per-output scale + zero-point be loaded once per output row.
2. **Tile dispatch** picks tiles purely by M. The same tile is used for `down_proj` (tall-K) and `gate_up_proj` (wide-N) at any given M. The new kernel branches on the `(K, N)` aspect ratio inside each M-bucket, and uses a separate decode-shaped tile (`BLOCK_M=16, BLOCK_N=128`) for the M ≤ 16 regime that dominates single-token serving.
3. **Zero-points** are stored packed (4 bits/zero in int32) and unpacked inside the kernel each K-iteration via `interleave x3 + shift + mask`. The new kernel pre-unpacks zero-points to fp16/bf16 once at load time, so the asymmetric (uint4 / AWQ) path has zero in-kernel unpack cost.

The win comes from the layout change; the other two are smaller layered gains.

## End-to-end performance

All numbers on **MI300X** (gfx942), input=output=128, with **cudagraph and torch.compile enabled**. Speedups are `triton / cdna` (higher = this PR is faster).

### Headline wins

| Workload | Metric | Speedup |
|---|---|---:|
| Chunked prefill (100 prompts × 128 input) | Mean TTFT | **2.79× – 2.99×** |
| bf16 decode (single sequence) | Median TPOT | **1.10× – 1.20×** |
| High concurrency throughput | Total tok/s | **1.17× – 1.19×** |
| Asymmetric (AWQ) decode at concurrency=50 | Median TPOT | **1.24×** |

### Full sweep — `Qwen/Qwen2.5-7B-Instruct-AWQ` (asymmetric, group=128)

| Config | TPOT | TTFT (mean) | Output tok/s |
|---|---:|---:|---:|
| fp16, num_seq=1 | 1.00× | **2.34×** | 1.02× |
| bf16, num_seq=1 | **1.20×** | 1.01× | **1.20×** |
| fp16, num_seq=max, 50 prompts | **1.24×** | 0.81× ⚠️ | 1.17× |
| fp16, num_seq=max, 100 prompts | 1.00× | **2.79×** | **1.19×** |

### Full sweep — `RedHatAI/Qwen3-4B-quantized.w4a16` (symmetric, group=128)

| Config | TPOT | TTFT (mean) | Output tok/s |
|---|---:|---:|---:|
| fp16, num_seq=1 | **1.08×** | 0.98× | 1.08× |
| bf16, num_seq=1 | **1.10×** | 0.95× | 1.09× |
| fp16, num_seq=max, 50 prompts | 1.02× | 1.04× | 1.03× |
| fp16, num_seq=max, 100 prompts | 0.95× ⚠️ | **2.99×** | 1.04× |

### Why TPOT ties at `Qwen2.5-7B fp16 / num_seq=1`

Both kernels post TPOT = 29.45 ms exactly. Cudagraph eliminates per-kernel launch overhead so aggressively that the W4A16 GEMM is no longer the decode bottleneck at M=1; attention and KV-cache update set the floor. The same model in **bf16** at the same settings shows a 1.20× decode win, because Triton's bf16 path is slow enough that the GEMM remains the bottleneck even after cudagraph.
