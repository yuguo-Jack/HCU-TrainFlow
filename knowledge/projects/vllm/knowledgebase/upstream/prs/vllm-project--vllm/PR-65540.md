# [Build] Marlin: drop SM12x-specific cubins and rely on compute_80 PTX

[Upstream PR](https://github.com/vllm-project/vllm/pull/65540) · state: open · merged: False

## Original PR description



## Overview

Part of #65560.

Revert the SM12x-specific cubins that #40923 added for the fp16/bf16 Marlin and Marlin-MoE kernels, and go back to building them as `8.0+PTX` only. On SM12x the driver JIT-compiles the existing PTX (compute_80 for fp16, compute_90 for bf16), which on current main is correct and runs at the same speed.

## Claims

- #40923's premise (Marlin-MoE gives wrong output on SM12x without native cubins) does not reproduce on current main: Marlin kernel tests and an end-to-end Marlin-MoE eval through the PTX JIT match the native-cubin build on GB10 (SM121).
- Removes the sm_120 SASS for every fp16/bf16 Marlin and Marlin-MoE kernel from multi-arch builds (with `TORCH_CUDA_ARCH_LIST="8.0;9.0;12.0"`: `_C_stable_libtorch` 74.6 → 70.0 MB, `_moe_C_stable_libtorch` 35.0 → 29.0 MB, −10.6 MB total; compile time for these two targets 656 s → 593 s).
- Cost: a one-time PTX JIT on SM12x, about +5–9 s on a cold driver JIT cache (`~/.nv/ComputeCache`); nothing once the cache is warm.

## Validation

All on DGX Spark (GB10, SM121), CUDA 13.0, built with `TORCH_CUDA_ARCH_LIST=12.1`. Confirmed with `cuobjdump` that the PR build has no sm_120 SASS for the fp16/bf16 Marlin kernels (only sm_80/sm_90 SASS + compute_80/compute_90 PTX), so every test below goes through the JIT.

| Check | main (native sm_120) | this PR (PTX JIT) |
|---|---|---|
| `tests/kernels/quantization/test_marlin_gemm.py` | 520 passed, 2 failed | 522 passed |
| `tests/kernels/moe/test_moe.py -k marlin` | 305 passed, 6 skipped | 305 passed, 6 skipped |
| gpt-oss-20b, `--moe-backend marlin`, GSM8K (100 q) | 0.36, 1395 tok/s | 0.33, 1400 tok/s |
| Startup to `/health`, cold JIT cache, Qwen2.5-3B-GPTQ-Int4 | 90.6 s / 89.1 s | 97.8 s |
| Startup to `/health`, cold JIT cache, gpt-oss-20b Marlin MoE | 30.4 s / 26.3 s | 35.5 s |

The main column uses the precompiled main wheel. Its 2 dense failures were not investigated, and they did not occur with the PR build. The GSM8K gap is within noise for 100 questions. Output is coherent, not the gibberish described in #40923.

```bash
vllm serve openai/gpt-oss-20b --moe-backend marlin --max-model-len 8192
python tests/evals/gsm8k/gsm8k_eval.py --port 8000 --num-questions 100
```

## Details

- `MARLIN_ARCHS`, `MARLIN_BF16_ARCHS` and `MARLIN_MOE_ARCHS` go back to `8.0+PTX` (bf16 keeps `9.0+PTX` for the atomicAdd path). The CUDA < 13.0 `12.0a;12.1a` branches go too.
- The FP8-activation kernels (`MARLIN_FP8_ARCHS` / `MARLIN_MOE_FP8_ARCHS`) keep their 8.9/12.x targets: they use e4m3 MMA, which compute_80 PTX cannot express. #65542 removes Marlin's 8-bit activation paths entirely in favor of Humming; the two PRs are independent.
- A build that targets only SM12x gets bigger (sm_80 SASS + PTX instead of only sm_120 SASS: 46.0/27.0 MB vs 37.3/15.5 MB for `_C_stable_libtorch`/`_moe_C_stable_libtorch`). The release wheel targets many archs and already ships the sm_80 + PTX copy, so it only loses the sm_120 copy.

Not a duplicate: no open PR changes these arch lists (searched "marlin PTX sm120", "marlin 12.0f").
