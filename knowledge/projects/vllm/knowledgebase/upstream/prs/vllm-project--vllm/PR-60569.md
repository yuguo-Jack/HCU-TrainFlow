# [Bugfix] Fix KV cache allocation for empty KV cache groups on a PP stage

[Upstream PR](https://github.com/vllm-project/vllm/pull/60569) · state: closed · merged: False

## Original PR description

## Overview

Fix KV cache allocation with pipeline parallelism when a KV cache group has no layers on one PP stage. DeepSeek-V4 with `-tp 4 -pp 2` fails at startup with `StopIteration`, and the engine reports an empty error message.

## Claims

- DeepSeek-V4 starts with TP=4, PP=2. Before this change, the PP0 workers crashed during KV cache initialization.
- If a KV cache tensor's layer is in no group, `allocate_kv_cache` now raises a `RuntimeError` naming the layer. Before, it raised `StopIteration`, which has no message, so the engine reported an empty error: `Worker failed with error ''`.

## Details

With PP, `_project_kv_cache_groups_to_worker` narrows each group's `layer_names` to the stage's own layers. When a group has no layers on a stage, it keeps the original `UniformTypeKVCacheSpecs`, which still lists other stages' layers. `get_kv_cache_config_from_groups` iterated `kv_cache_specs`, so it created tensors for layers the stage does not own. `allocate_kv_cache` then found no group for those layers.

Fix:

- `vllm/v1/core/kv_cache_utils.py`: iterate `group.layer_names` instead of the spec's layers, so empty groups produce no tensors.
- `vllm/v1/worker/utils.py`: raise a `RuntimeError` naming the layer when a tensor's layer is in no group.

There is no change when PP=1 or when no stage has an empty group.

## Validation

Setup: DeepSeek-V4-Flash truncated to its first 6 layers (local checkpoint), 8x Intel Arc Pro B60 (XPU), `BLHNC` KV cache layout.

```bash
vllm serve DeepSeek-V4-Flash-6L --trust-remote-code \
  --tensor-parallel-size 4 --pipeline-parallel-size 2 \
  --kv-cache-dtype fp8 --max-model-len 8192 --max-num-seqs 2 \
  --gpu-memory-utilization 0.85
```

Before (PP0 workers): the error message is empty because `StopIteration` has no message.

```text
File "vllm/v1/worker/utils.py", line 432, in allocate_kv_cache
    group_id, group = next(
StopIteration
RuntimeError: Worker failed with error '', please check the stack trace above for the root cause
```

After: all 8 workers allocate the KV cache and the server starts. If a tensor's layer is ever outside every group again, the error names the layer instead of being empty (covered by `test_allocate_kv_cache_rejects_tensor_outside_groups`):

```text
RuntimeError: KV cache tensor layer '<layer_name>' is not in any KV cache group.
```

Unit tests (`tests/v1/core/test_kv_cache_utils.py`):

- `test_get_kv_cache_config_skips_empty_projected_uniform_group`
- `test_allocate_kv_cache_rejects_tensor_outside_groups`
- `test_get_kv_cache_configs_empty_pp_group_replans_to_min_blocks`


```bash
pytest -v tests/v1/core/test_kv_cache_utils.py \
  -k "empty_projected_uniform_group or rejects_tensor_outside_groups or empty_pp_group"
```
