# [Bugfix] Llama3 JSON tool parser: flush buffered '{...}' as content when it isn't a tool call

[Upstream PR](https://github.com/vllm-project/vllm/pull/58829) · state: open · merged: False

## Original PR description

## Summary
`Llama3JsonToolParser.extract_tool_calls_streaming` decides between content and tool call from the first character only (`current_text.startswith("{")`), and never falls back. A plain answer that happens to start with `{` but never produces a `"name"` key (e.g. `{"a": 1} is a dict`, or just `{}`) is buffered forever and silently dropped: non-streaming returns it as content, but streaming returns `content=None` and no tool calls — the model's whole reply disappears for a streaming client.

This is the most serious of the three streaming/non-streaming mismatches in the issue (content loss, case 1). This PR tracks whether the buffered object has finished parsing without ever producing a `"name"` (nor `"parameters"`/`"arguments"`); once that's confirmed, it flushes everything buffered so far as content and passes the rest of the stream through as plain content instead of continuing to try (and fail) to parse it as a tool call.

Note: cases 2 and 3 from the issue (empty-arguments formatting, text-before-call) are also covered by the broader `ParserEngine` port in #51577, which the issue author flagged might supersede this one. This PR is scoped narrowly to the content-loss case so it stays reviewable independently of that larger port.

## Test plan
- [x] Manually traced the fix against the three fixture cases from the issue (`l3-json-answer-not-a-call`, `l3-bug-leading-json-object-in-content`) — case 1 now streams the JSON text as content instead of dropping it.
- [x] Verified existing streaming behavior for actual tool calls is unaffected (the new branch only triggers when the buffered object completes without a `name`).

Fixes #58824
