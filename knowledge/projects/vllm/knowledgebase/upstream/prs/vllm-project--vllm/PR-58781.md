# [CI] Shard (H200 MIG 18GB) Language Models (MTEB) into 3 directory shards

[Upstream PR](https://github.com/vllm-project/vllm/pull/58781) · state: closed · merged: False

## Original PR description

## What
`Language Models (MTEB)` runs all of `models/language/pooling_mteb_test` in one job, at about 41–43 minutes of pytest on recent `main` nightly runs. This PR hash-shards that same directory three ways with pytest-shard, so the same tests run with no filters, no file moves and the same trigger paths.

## Old
```
Language Models (MTEB)            key language-models-test-mteb   pytest models/language/pooling_mteb_test
  mirror: (MI250) Language Models (MTEB)
```

## New
```
Language Models (MTEB) Shard %N   key language-models-test-mteb   parallelism: 3
  pytest models/language/pooling_mteb_test --num-shards=$BUILDKITE_PARALLEL_JOB_COUNT --shard-id=$BUILDKITE_PARALLEL_JOB
  mirror: (MI250) Language Models (MTEB) Shard %N   (inherits the command and parallelism: 3)
```

## Notes
- Coverage is the same: the job still runs `pytest <dir>`, so any new file added there is picked up, and `source_file_dependencies` did not change. It collects 128 cases and runs 33 of them; the other 95 are models with `enable_test=False`.
- No semantic split: the files are grouped by model family, and the embed and rerank helpers are used together inside `test_baai`, `test_gte`, `test_jina` and `test_nemotron`, so there's no clean line for splitting the folder. Pattern A on the whole directory is the smallest change.
- The legacy `test-amd.yaml` MI300 MTEB step is not touched.
- Evidence: unsharded nightly `main` builds [91173](https://buildkite.com/vllm/ci/builds/91173), [91049](https://buildkite.com/vllm/ci/builds/91049) and [90513](https://buildkite.com/vllm/ci/builds/90513). Per-case times are read from their logs, and the pytest-shard hash assignment (sha256, little-endian) is replayed on them.

## Expected runtime and overhead
Predictions come from per-case times in the three builds above. Each shard gets that build's non-pytest overhead.

| Job / replica | pytest (predicted) | running wall | non-pytest overhead | main overhead cause |
|---|---|---|---|---|
| MTEB Shard 1 | 13.9–15.0m | ~16.5–18.6m | 1.8–3.6m | checkout, image pull, container start |
| MTEB Shard 2 | 15.0–16.0m | ~17.5–19.6m | 1.8–3.6m | same |
| MTEB Shard 3 | 11.1–12.1m | ~13.5–15.6m | 1.8–3.6m | same |

- Total worker-minutes: about 43 → 48 on a typical run, and 46.7 → 54 on the slowest run in the last two weeks. That is **+5 to +7 extra**, within the 20-minute budget. Pytest collection takes about 6 seconds and repeats on each shard.
- Slowest shard: about 16 minutes of pytest in the worst observed run, down from about 43.
- Why 3 shards: 2 shards leave the slowest one at about 22–23 minutes. 4 shards reach about 12–13 minutes, but add a fourth worker and leave one shard at about 7 minutes. The MI250 mirror stays inside the target at 3 shards, within budget.

**Coverage:** the three shards ran 11, 12 and 10 cases (33 passed, 95 skipped over 128 collected), the same as unsharded `main`. The replayed pytest-shard hash put all 33 run cases on the shard they actually ran on.

| Job / replica | cases run | pytest | running wall | non-pytest overhead | main overhead cause | predicted pytest |
|---|---|---|---|---|---|---|
| MTEB Shard 1 | 11 | 10.8m | 11.9m | 1.1m | checkout, image pull, container start (~1.0m before pytest starts) | 13.9–15.0m |

| MTEB Shard 3 | 10 | 8.6m | 9.7m | 1.1m | same (~1.0m before pytest starts) | 11.1–12.1m |

- **Total worker-minutes:** 43.1 on `main` build 91173 → 37.4 here. That comparison is not like-for-like, because pytest ran faster on this build: every case was quicker than in 91173, and the case sum was 31.9m versus 38.7m. So the fairer measure of added cost is non-pytest overhead, which went from 2.5m to 3.5m in total, plus about 6 seconds of repeated collection per shard. That's about **+1 extra worker-minute**, within the 20-minute budget.
- **Slowest shard:** 14.5m of pytest (Shard 2), 15.8m wall, down from about 41–43m of pytest unsharded.
- **Shard balance:** Shard 2 is the heaviest and Shard 3 the lightest, about 6 minutes apart, which matches the prediction's ordering. With `main`'s per-case times, Shard 2 is predicted at 15–16m, which is still inside the 20-minute target.
- **Mirror:** the MI250 mirror passed on all 3 shards. It covered the same cases as its unsharded `main` run, stayed inside the target on every shard, and added worker-minutes within budget.

4 shards are not needed. I'll re-check Shard 2 on the first nightly `main` builds after merge.
