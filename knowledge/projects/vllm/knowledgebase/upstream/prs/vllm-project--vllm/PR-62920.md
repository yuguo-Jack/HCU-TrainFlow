# [Feature][RL] Per-request opt-out from routed-expert capture

[Upstream PR](https://github.com/vllm-project/vllm/pull/62920) · state: open · merged: False

## Original PR description



## Overview

Adds a per-request `return_routed_experts` flag (default `true`). On a server started with `--enable-return-routed-experts`, a request that sets it to `false` skips routed-expert capture: vLLM neither stores nor returns its routing.

**Why:** RL inference servers record routing for every request, but some requests never use it, such as online evals that run next to the rollouts. Today they pay the full capture cost and the rows are thrown away. Recording has to stay on for the rollouts, so the opt-out has to be per request.

## Claims

- The flag works on `SamplingParams`, `/v1/completions`, `/v1/chat/completions` and `/inference/v1/generate`, in both the Python and Rust frontends.
- Opted-out requests get their own prefix-cache namespace: an extra tagged key on the first block hash, like `cache_salt`. Their blocks have no stored routing, so they must never serve a request that records it.
- Opted-out requests skip the KV-tier routing retention from #62591. Their blocks are not retained, and their KV hits are not capped by stored routing, since they never read it.
- On a server that doesn't record routed experts, the flag is ignored.

## Validation

DeepSeek-V4-Flash, one 8×B300 node, DEP8, multi-turn agent load. Generated tok/s per GPU:

| | 512 agents | 1,024 agents |
|---|---:|---:|
| every request records | 1,778 | 2,153 |
| every request opts out | 2,133 | 2,949 |
| capture off | 2,079 | 2,854 |

New tests cover the scheduler, the worker, prefix-cache isolation, the OpenAI and generate endpoints, and the Rust frontend. They pass, and the new scheduler, worker and isolation tests fail without the change. The existing routed-expert, KV-cache and Rust tests also pass.

On 2026-10-28 I rebased onto main, which now includes #62591, and added `test_routed_experts_opt_out_skips_retention` for the retention bypass. The throughput numbers and test runs above are from before the rebase and have not been rerun since. An independent run on DEP4 [reproduced the recovery](https://github.com/vllm-project/vllm/pull/62920#issuecomment-6502754339): 14,777 tok/s with every request opting out, against 14,747 and 15,292 with capture off.

## Details

Not a duplicate: open #57968, #61086 and #62056 and merged #62591 change routed-expert storage, transport, P/D and retention, but none adds a per-request opt-out.

- aoshen02 · comment · 2026-10-29T16:44:38Z · [source](https://github.com/vllm-project/vllm/pull/62920#issuecomment-6502754339)

I reproduced the throughput regression this PR addresses and broke it down component by component. Short version: the cost of recording routed experts is mostly worker-side per-request work done during capture, not the cost of returning the rows. So an opt-out must skip capture bookkeeping, as this PR does. Skipping only the return is not enough. Details, numbers and prototype optimizations follow.

## Setup

- 1× GB200 node (4 GPUs), DeepSeek-V4-Flash, nightly image from main `00b6c4c565` (2026-10-26), V2 model runner, async scheduling, `FULL_AND_PIECEWISE` CUDA graphs.
- Both frontends (Python `/inference/v1/generate` and the Rust frontend); `--enable-return-routed-experts`.
- Load: 512 closed-loop agents, 16-turn episodes, each turn resends the whole history. The history is a shared 2k system prefix, a 1k task, then 512 observation + 256 output tokens per turn, so the prompt grows from ~3k to ~14.6k and every turn after the first is a prefix hit.
- Incremental mode sets `routed_experts_prompt_start` to the previous turn's length; full mode returns all rows.

### Measurement note

Fixed-window tok/s is unreliable with this load. The agents move in lockstep, so which turns land in the window depends on how fast the server ran before it. The same config varied by 10–27% between runs (mean prompt in the window was 8.8k in one run and 10.0k in another). I switched to fixed work:

1. Every agent finishes one warm-up episode.
2. All agents pass a global barrier.
3. I time one complete 16-turn episode: 8,192 requests, with identical token work for every config.

Configs run in mirrored order (A B C … C B A). The two runs of each config agree within 1–2 s.

## Breakdown (TP4 single engine, Rust frontend, 512 agents, mean of 2 runs)

| config | episode time | vs off | throughput |
|---|---:|---:|---:|
| capture off | 225.9 s | — | — |
| capture on, worker output-thread bookkeeping disabled, nothing returned (ablation) | 258.7 s | +32.8 s | −12.7% |
| capture on, all requests skip only the return | 285.8 s | +59.9 s | −21.0% |
| incremental return | 295.4 s | +69.5 s | −23.5% |
| full return | 321.7 s | +95.8 s | −29.8% |

Where the time goes in incremental mode:

- **~33 s: capture side.** This is GPU capture, the D2H copy, worker main-thread `begin_step`/`prepare_output`, and EngineCore connector metadata. A torch-profiler trace shows `begin_step` on the worker main thread dominates. It stringifies every block hash into a store key and retains it, which is ~550 keys per new turn of a 9k-token prompt. `prepare_output` and the per-layer `capture()` are small.
- **~27 s: output-thread bookkeeping.** This is per-request `capture` into block tails and block publishing. It runs inside the worker lock, which the main thread's `begin_step`/`prepare_output` also take. Burning 4 ms/step of pure Python on the output thread *outside* the lock had no measurable effect (293.1 s vs 295.4 s). The cost is the main thread waiting on that lock, not GIL pressure.
- **~10 s: the return path.** This covers `take_output`, packing, and transport to the frontend.
- **Full mode adds ~26 s on top.** The worker reads ~550 hit blocks from the store per new turn and ships ~2.3 MB per request through worker → EngineCore → frontend.

Things that are *not* the cause:

- **EngineCore.** py-spy shows its R3 functions at ~1.6% of samples. With R3 on, EngineCore spends more time waiting for workers (38% → 49%). A CPU microbenchmark of the EngineCore side gives ~1.25 ms per 512-request decode step.
- **Prefix-cache hit rate.** It is unchanged: 87.7% off vs 87.5–87.9% on.

The cost scales with requests per worker. In TP4 one worker carries all 512 requests. On DEP4 (128 per rank) the same load lost single-digit percent in incremental mode with the Rust frontend, but those were fixed-window numbers, so treat them as rough.

## Reproducing this PR's numbers (DEP4, earlier fixed-window runs, 512 agents, Python frontend)

| config | tok/s |
|---|---:|
| capture off (two runs) | 14,747 / 15,292 |
| full return | 11,469 (−24%) |
| all requests `return_routed_experts=false`, this PR | 14,777 |
| all requests `return_routed_experts=false`, skip-return-only variant | 13,958 |

The opt-out recovered to the off band, which matches the PR description. A skip-return-only variant keeps capture and store writes and only suppresses the output. In the fixed-work TP4 table above, that variant still costs −21%. I have not yet run this PR's opt-out under fixed-work TP4; I will add it.

Separately, Python full return had an extra bottleneck: the generate route serialized `JSONResponse(model_dump())` through `json.dumps`. That took ~21 ms per 3 MB response and blocked the event loop. `Response(model_dump_json())` takes ~1.6 ms and produces identical bytes. With that fixed, #61086 also starts to help on the Python frontend. Without it, #61086 only helps the Rust frontend.

## Prototype optimizations (fixed-work TP4, Rust frontend, same baseline)

| change | incremental | full |
|---|---:|---:|
| baseline (#61086) | 295.4 s (−23.5%) | 321.7 s (−29.8%) |
| vectorized per-step commit + incremental key skipping | 267.6 s (−15.6%) | — |
| above + shared-memory store, EngineCore gathers hit rows | — | 290.9 s (−22.3%) |
| above + lock-free main thread (single-writer worker) | 269.0 s | 294.8 s |

What each prototype does:

- **Vectorized commit.** The per-step commit converts arrays to Python ints once and appends single-row captures with one fancy-index write. It also skips publish work for requests with no new blocks and stops rebuilding per-request state objects every step. CPU per 128-request decode step drops from 0.64 ms to 0.36 ms.
- **Incremental key skipping.** On a request's first schedule, EngineCore sends only the block hashes from the block containing `routed_experts_prompt_start` onward. The worker records the offset. The skipped blocks are cache hits the request never reads, and the KV-mirror retention already keeps them. Admission CPU per new turn drops from 0.77 ms to 0.45 ms.
- **Shared-memory store.** The store arena moves to named shared memory. For hit rows, the worker ships slot indices, and EngineCore gathers them. This removes the worker-side store read and the worker → EngineCore copy. A hit-row self-consistency check passes 8/8: rows returned on a prefix hit equal the rows of the request that computed them.
- **Lock-free main thread.** The worker main thread only snapshots and enqueues. The output thread applies step metadata in order before each commit. It gave no further gain, so the worker lock is no longer the bottleneck once the commit is cheap.

The remaining ~16% (incremental) and ~22% (full) is still worker step time. I'm bisecting it now with ablations that separately disable in-model capture, the worker snapshot/commit, and the scheduler metadata.

## Takeaways for this PR

1. The opt-out needs to skip capture and store bookkeeping, as it does now, to recover throughput. A return-only opt-out leaves most of the cost.
2. Recording requests still pay a per-request worker cost that grows with requests per worker. The prototypes above recover about a third of it; a fuller fix belongs in the connector, not in this PR.


- aoshen02 · comment · 2026-11-01T03:46:36Z · [source](https://github.com/vllm-project/vllm/pull/62920#issuecomment-6553031106)

Pushed 7a2fd9413 on top of this branch. It generalizes the opt-out from routed experts to all RL auxiliary outputs.

**What changed**
- `SamplingParams.return_routed_experts` becomes `return_aux_outputs` (default `True`). With `False`, the request skips routed-expert recording and return, sampling masks, and sample `logprobs` / `logprob_token_ids`. `prompt_logprobs` and the `top_k` sampling parameter are unaffected.
- Prefix-cache isolation moves out of `kv_cache_utils`: `EngineCore.preprocess_add_request` salts the request's `cache_salt`. An opted-out request therefore never shares blocks with a recorded one, so a recorded request can't hit blocks whose rows were never written. This path is shared by both frontends.
- Rust frontend: `/inference/v1/generate` accepts `return_aux_outputs` and does not render logprobs for opted-out requests (before, it returned a 500 when `logprobs` was set).
- Dropped the completions/chat plumbing of the old flag. Those endpoints don't return routed experts.

**E2E A/B** (DeepSeek-V4-Flash, TP4 + EP, one engine, GB200; fixed work: 512 closed-loop agents × 16 turns, one warm episode, then 8,192 measured requests; `top_k=256`, 256 logprobs; tok/s; one run per node, two nodes per frontend):

| | Frontend | Recorded | Opted out | Server flags off |
|---|---|---|---|---|
| R3 + sampling mask + logprobs | Rust | 5,014 / 5,129 | 8,799 / 8,803 | 9,092 / 9,353 |
| R3 + sampling mask + logprobs | Python | 494 / 509 | 6,937 / 8,455 | 8,892 / 9,098 |
| sampling mask only | Rust | 8,629 / 8,811 | 9,074 / 9,212 | |
| logprobs only | Rust | ≈8.0k (8 runs) | ≈9.26k (7 runs) | |
| logprobs only | Python | 556 / 557 | 8,790 / 8,898 | |

There were 0 errors in all runs. Every recorded response carried all requested outputs, and no opted-out response carried any. A smoke test on both frontends also checks two things:
- opted-out repeats still hit the prefix cache;
- a recorded request after opted-out ones on the same prefix gets 0 hit tokens.

The remaining ~3–4% for opted-out requests is batch-level work (routing capture and mask computation inside the CUDA graph) that can't be skipped per request.
