# [Bugfix][Quantization] Do not select DeepGEMM with float32 scales on SM12x

[Upstream PR](https://github.com/vllm-project/vllm/pull/57512) · state: open · merged: False

## Original PR description

Fixes #57486. Reported and diagnosed by @ivanusto, who also found the MoE half and handed the patch
over.

## Problem

The 120 family has no working float32-scale path — its DeepGEMM kernels read packed UE8M0 scales.
With `VLLM_USE_DEEP_GEMM_E8M0=0` the oracle resolves to `FLOAT32`, and vLLM still selects DeepGEMM:

- **linear**: `should_use_deepgemm_for_fp8_linear()` considers only dtype and N/K multiples.
- **MoE**: `_valid_deep_gemm()` never consults the format. `DeepGemmExperts` does read the oracle,
  but only to compute `use_ue8m0 = scale_fmt == FLOAT32_CEIL_UE8M0`, so on SM12x with E8M0 off it
  resolves False and float32 scales still reach the grouped kernels.

Per #57486, that yields NaNs on DeepGEMM `ad1f1726` (up to 22% of outputs) and a hard `RuntimeError`
since `a6bbb80`.

## Fix

One predicate, consulted by both selection sites. On the 120 family, DeepGEMM is only selected when
the resolved format is not `FLOAT32`; every other family is untouched.

**The oracle is deliberately left alone.** `DeepGemmQuantScaleFMT.from_oracle()` also drives scale
*layout* for non-DeepGEMM consumers — `QuantFP8` (`input_quant_fp8.py:67`) and four sites in
`fp8_utils.py` — and `FLOAT32` is the correct answer for them, including when DeepGEMM is simply
absent. Making the oracle return UE8M0 on SM12x would fix selection by mis-describing layout
elsewhere, so this gates at selection time instead.

## Verification

GB10 (sm_121, cc 12.1, driver 580.95.05, CUDA 13.0), `main` at `bf13ecc2f7`:

```
E8M0=1  oracle=UE8M0    scale_fmt_ok=True   linear_gate=True    <- unchanged, DeepGEMM still used
E8M0=0  oracle=FLOAT32  scale_fmt_ok=False  linear_gate=False   <- was True; kernel no longer reached
```

Family isolation, oracle forced to `FLOAT32`:

```
family 90  -> True    family 100 -> True    family 120 -> False
```

so Hopper's `FLOAT32_CEIL_UE8M0` path and the 100 family keep their current behaviour.

ruff (repo-pinned 0.14.0) and mypy clean.

## Scope

I verified the *selection* change on hardware. @ivanusto then ran the branch end-to-end on GB10
with DeepGEMM built from the fork at the `a6bbb80` pin: E8M0 on is `torch.equal` with main across
five shapes, and E8M0 off no longer reaches the kernel from either selection site. That run also
turned up a third site — the grouped-GEMM warmup calls
`m_grouped_fp8_gemm_nt_contiguous` directly, so `_valid_deep_gemm()`'s check never applied to it and
startup still failed after dispatch had already moved to Triton. Fixed here; the scale format is now
checked in `_fused_moe_grouped_gemm_may_use_deep_gemm` as well.

Tests are in `tests/model_executor/test_deep_gemm_warmup.py`: the device-family matrix for the
shared gate, and one asserting the warmup predicate consults it before touching the module.

## Out of scope

Two more consumers take the FLOAT32 oracle to sm120 kernels that only accept int scales at
`a6bbb80`, both found by reading rather than running (@ivanusto's note):

- `BatchedDeepGemmExperts` — `_supports_current_device()` is just `is_deep_gemm_supported()`, and it
  feeds `fp8_m_grouped_gemm_nt_masked`, whose sm120 branch requires `kInt` scales. Only reachable
  with a batched activation format such as DeepEP low latency.
- `DeepGemmFP4Experts` — listed for family 120 and derives `use_ue8m0` from the scale format, so it
  sends float32 activation scales with E8M0 off.

Neither of us can exercise those configurations, so they're named rather than patched.

- hclsys · comment · 2026-09-18T16:20:11Z · [source](https://github.com/vllm-project/vllm/pull/57512#issuecomment-5732884026)

That's a much better test than I could run here — I only have the vendored `vllm.third_party.deep_gemm`, not the external package at the pin, so the warmup path never fired on my box. Fix pushed in `9ab6751`.

I took your three-line version rather than the `_supports_current_device()` one, and the reason is in `fallback.py`:

```python
@classmethod
def _supports_current_device(cls) -> bool:
    experts_cls, fallback_cls = cls.get_clses()
    return (
        experts_cls._supports_current_device()
        and fallback_cls._supports_current_device()
    )
```

It's an **and**. Gating `DeepGemmExperts` there doesn't make `TritonOrDeepGemmExperts` fall back to Triton — it disqualifies the composed kernel outright at `modular_kernel.py:547`, so the layer stops being served by that kernel at all rather than by its Triton half. That's a selection change with a blast radius I can't measure from one card, and it'd also lean on there being another viable candidate for every sm_120/121 FLOAT32 config. The warmup check keeps this a dispatch-level fix, which is what the rest of the PR is.

On my card the predicate-level half reproduces:

```
E8M0=1  oracle=UE8M0    scale_fmt_ok=True   dg_supported=True
E8M0=0  oracle=FLOAT32  scale_fmt_ok=False  dg_supported=True
```

`is_deep_gemm_supported()` staying True is the part that matters — every other gate in `_fused_moe_grouped_gemm_may_use_deep_gemm` passes, and nothing there consulted the format.

Added the tests to `tests/model_executor/test_deep_gemm_warmup.py`: the family matrix (120 x FLOAT32 declines, the other three don't), and one that the warmup predicate actually asks. The second uses a stand-in that raises if the predicate touches it, so it pins the ordering rather than just the return value. Both are red without the guard.

Also noted `BatchedDeepGemmExperts` and `DeepGemmFP4Experts` in the description as out of scope with your reasoning — I can't reach either here (no DeepEP low-latency setup, no mxfp4 checkpoint), and guessing at a gate I can't exercise seemed worse than naming them.
