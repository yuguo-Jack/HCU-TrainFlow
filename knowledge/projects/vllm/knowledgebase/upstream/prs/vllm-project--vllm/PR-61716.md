# [Bugfix][Kernel] silu_and_mul_quant: run the vectorized loop

[Upstream PR](https://github.com/vllm-project/vllm/pull/61716) · state: closed · merged: True

## Original PR description

## Purpose

`silu_and_mul_quant` (`act_and_mul_quant_kernel` in `csrc/quantization/activation_kernels.cu`) is the fused SiLU-and-mul + static per-tensor FP8 quant that the manual activation+quant fusion (#51415, `maybe_fused_act_quant`) routes static-FP8 models through by default.

Its 128-bit vectorized loop has never executed. The loop bound is computed as `round_to_previous_multiple_of(elems_per_128bit_load, block_end)`, with the two arguments swapped: the helper rounds its first argument down to a multiple of its second, so this rounds 8 down to a multiple of `block_end`, which is 0 for any `d > 8`. With `vec_loop_end = 0` the vectorized loop has an empty range and every element goes through the scalar cleanup loop with 2-byte loads and 1-byte stores. Present since the kernel landed in #10867. Runtime proof on `main`: with the input and output pointers misaligned by 8 bytes the op completes and matches the aligned result for d = 14336 and 10752 (no 16-byte load executed), and faults with `misaligned address` at d = 8, the one shape where the bound is non-zero.

The cost: on H100 the kernel runs at 1.9 TB/s effective against 3.1 TB/s for the Inductor-fused kernel it replaced, and Llama-3.1-8B-FP8 serves about 3.5% slower with the fusion wired than on the Inductor path (numbers below).

This PR:

- Fixes the argument order, so the bound is `block_end` rounded down to the vector width and the 128-bit loop covers the block.
- Takes the vectorized path only when `d` is a multiple of the vector width (8 for bf16/fp16) and both data pointers are 16-byte aligned, via the existing `vllm::is_16byte_aligned`. Rows of other widths are not 16-byte aligned (d = 781, hidden size 1562 in the unit test, starts odd rows 4 bytes off) and would fault on the fixed loop; they keep the scalar loop, which is what every shape runs today.
- In the scalar case the cleanup loop starts at the block's own `block_start` instead of 0. With 2 to 4 blocks per row at 32 tokens or fewer, starting at 0 made each block redo the preceding blocks' elements (same values written, wasted bandwidth).

Output is bit-identical to `main`: both loops evaluate the same per-element expression. Verified below. No change to grid, block size or arithmetic; the remaining gap to the Inductor kernel (0.9x at prefill, about 0.5x at decode) is the subject of a separate follow-up.

**Not a duplicate.** No open PR touches this kernel. #49828 adds a separate per-token dynamic kernel in the same file with its own launch. #59514 is my earlier PR that bundled this fix with a kernel rewrite; it is being split into this fix and a follow-up so each can be reviewed on its own.
