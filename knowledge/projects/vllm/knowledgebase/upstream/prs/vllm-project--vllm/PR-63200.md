# [Perf][Kernel] BF16 prefill top-k for the sparse indexer, drop the FP32 upcast

[Upstream PR](https://github.com/vllm-project/vllm/pull/63200) · state: closed · merged: False

## Original PR description

## Purpose

Closes #63198.

Since #61149, the SM100 MQA logits come back as BF16. The prefill indexer then upcasts the whole logits matrix to FP32 with `as_fp32_logits`, only so that `top_k_per_row_prefill` can read it. On long prompts that extra pass costs more than half of the top-k itself.

This PR makes `top_k_per_row_prefill` accept BF16 logits directly. The prefill paths in `sparse_attn_indexer.py` and `glm5next/nvidia/sparse_indexer.py` now skip the upcast, except when an FP32 consumer follows (the candidate-block selection or the DCP merge).

**The BF16 kernel** is CUDA-only; ROCm keeps the FP32 kernel and raises a clear error on BF16 input.
- It turns each value into an order-preserving 16-bit key.
- A 14-bit shared-memory histogram comes first. That gives 32 bins per binade, like the FP16 first step of the FP32 kernel. Indexer logits sit in a few binades, and an 11-bit first pass was 3× slower because the atomics serialise.
- A 2-bit pass over the threshold bin follows, staged in shared memory when the bin holds 6144 or fewer elements. Ties are then filled exactly.
- It has the same contract as the FP32 kernel: indices relative to `rowStarts`, `-1` padding for rows shorter than k, order unspecified.

## Test Plan

- `tests/kernels/test_top_k_per_row.py`:
  - `test_top_k_per_row` is now parametrized over `float32` and `bfloat16`;
  - new `test_top_k_per_row_prefill_bf16_long_rows` covers 16k and 128k rows, offset row starts, and a tie-heavy variant with 64 distinct values. It checks that the selected values equal those from `torch.topk`.
- Benchmarks on B300 (SM103): GLM-5.x indexer shapes, 32 heads × 128, top-k 2048, DeepGEMM `727f847` logits, kernel time from `torch.profiler`.
- Selected values compared with the upcast + FP32 path on real DeepGEMM logits.

## Test Result

I could not build vLLM main on the B300 nodes I have, so the test results come from a harness instead:
- `csrc/sampler.cu` from this branch compiles with `nvcc` for sm_103a with no warnings.
- The harness includes it and launches the new kernel exactly as `top_k_per_row_prefill` does.
- It passes the parametrized prefill cases (1/32/2050 rows, k 2048/3000, cleaned and uncleaned) and all four long-row cases, including writes into a strided output buffer.
- `pre-commit` passes.

| context (2048 rows) | logits + `as_fp32_logits` + FP32 top-k | logits + BF16 top-k |
|---|---|---|
| 16k | 0.218 ms | 0.216 ms |
| 64k | 0.819 ms | 0.653 ms (−20%) |
| 128k | 1.584 ms | 1.189 ms (−25%) |
| 192k | 2.342 ms | 1.756 ms (−25%) |

The top-k alone is 0.54 → 0.42 ms at 128k on random logits. On a tie-heavy row it is 1.90 → 0.55 ms, because the FP32 kernel falls into its later radix steps. On real DeepGEMM logits, 0 of 256 sampled rows differ at 192k.

Not changed: the decode path (`as_fp32_logits(logits, seq_lens)` before the decode top-k backends) can be done the same way in a follow-up.
