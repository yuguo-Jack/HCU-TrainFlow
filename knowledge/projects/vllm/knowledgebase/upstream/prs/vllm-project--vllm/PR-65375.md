# [Rust Frontend] Drop incomplete tool-call markup at the end of output like Python

[Upstream PR](https://github.com/vllm-project/vllm/pull/65375) · state: closed · merged: True

## Original PR description

## Overview

When generation stops inside a tool call (`max_tokens`, a stop string, or EOS before the closer), drop the unfinished tool-call markup and keep the text before it, like the Python parser engine (vllm-project/vllm#47562, pinned by `tests/parser/engine/test_parser_engine.py::TestTruncatedToolOpenerStreamParity`). Today the Rust frontend returns the truncated markup as assistant `content`.

## Claims

- For Python's own test input `"Checking the weather. <tool_call>\n<function"` with `qwen3_coder`, Rust returned `content: "Checking the weather. \n<function"`; it now returns `"Checking the weather. "`, like Python. An output that is only a truncated call ends with no content.
- Applies to every Rust tool parser family and every finish reason, in streaming and non-streaming (chat completions and the Responses API share the path).
- Other finish errors (malformed but complete markup, e.g. Llama's `invalid Llama JSON`) still fall back to text as before.

## Details

- `ToolParserError::IncompleteToolCall { parser }` and `UnifiedParserError::IncompleteToolCall { parser }` replace the generic `ParsingFailed("incomplete … tool call")` at every "output ended inside a call" site: the JSON family (Hermes, Qwen3 JSON, Mistral, Phi-4-mini, InternLM2 through the shared parser; Llama JSON; Granite 4), DeepSeek V3/V3.1 JSON, DeepSeek DSML (V3.2/V4/V4.1), GLM-4.5/4.7, Kimi K2, Qwen Coder (and Seed-OSS, Step-5, MiMo through it), MiniMax M2/M3, HY, and the unified Gemma 4, Inkling, Kimi K3 and Muse parsers. `UnifiedParserError::is_incomplete_tool_call` covers both, including a tool parser's error carried through `CombinedParser`.
- `UnifiedParserState::finish` (`rust/src/chat/src/output/default/unified.rs`) drops the parser buffer on that error only. Events already emitted stand, so text before the call is kept. Before this change, every finish error reset the parser and re-emitted the buffer as text (added by vllm-project/vllm#47289 so a truncated-only output would not come back empty).
- Ownership: the parser alone knows it ended inside a call, so it reports a typed error; what to show the client is output policy in `vllm-chat`, so the drop sits in `UnifiedParserState::finish`, the one consumer of `UnifiedParser::finish`. Streaming and non-streaming agree by construction, since non-streaming assembles the same event stream.

**Differences from Python.**

- Python drops the markup for its parser-engine families and still returns raw content in non-streaming for legacy ones (e.g. `hermes`); Rust drops it for every family. Half a tool-call opener is neither text nor a call, and a client cannot act on it.
- A call whose header already streamed (`ToolCallStart`, partial arguments) before the cut stays in the response with truncated arguments, as streaming clients already saw it. Python's non-streaming path drops such a call; retracting a streamed call is a separate question.
- The `hf` and Beam template parsers are not changed: a tool-call region still open at EOF is closed and parsed by the template's content rules, and a parse failure already drops the body, so the markup never reaches the text.

Not a duplicate: vllm-project/vllm#62290 drops an incomplete DeepSeek DSML call at `max_tokens` only; this PR covers every family and finish reason. vllm-project/vllm#52886 recovers malformed Kimi K3 calls mid-stream, a different case; the two touch neighboring lines in `kimi_k3.rs` `finish`.
