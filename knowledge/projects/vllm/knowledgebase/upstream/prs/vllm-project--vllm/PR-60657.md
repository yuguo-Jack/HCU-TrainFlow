# [Kernel][ROCm] qwen4_exp: fused HyperConnection combine+mix for gfx1100 decode

[Upstream PR](https://github.com/vllm-project/vllm/pull/60657) · state: open · merged: False

## Original PR description



## Overview

**Depends on #60650** (serve the AMD qwen4_exp path in fp16): this kernel is fp16-only, and without #60650 the model cannot run in fp16 on ROCm. This branch is stacked on it; the first two commits are #60650, only the last one is this PR. Draft until #60650 lands.

Fused HIP kernels for `GatedResidual.combine_and_mix` (qwen4_exp HyperConnection) on gfx1100 decode: the five-kernel chain becomes two kernels for 1-4 tokens. +5.8% decode tok/s for Qwen3.8-Flash-Next on 4x RX 7900 XTX.

Related: #59442 targets the same boundary on CDNA (MI355X) through an AITER FlyDSL kernel, opt-in and waiting on ROCm/aiter#5913. AITER does not run on RDNA3, so the two do not overlap: this path is gated on gfx1x and on the kernel being built (`VLLM_ROCM_GFX1100`), and leaves the ROCm fallback untouched.

## Claims

- Decode, Qwen3.8-Flash-Next, TP4 on 4x RX 7900 XTX, fp16 KV cache, no spec decode, one user: **72.5 -> 76.6 tok/s (+5.8%)**.
- HyperConnection time per decode step (96 calls, cold weights, CUDA graph): **2.85 -> 2.18 ms** at 1 token, 3.36 -> 2.87 ms at 4 tokens.
- Same output as the unfused chain within fp16 rounding; deterministic (fixed-order reduction, no split-K atomics).

## Details

The unfused chain is combine+RMSNorm (Triton), the merged down+inject GEMM `[336, 10240]`, SiLU, the up GEMM `[10240, 320]` and the gate mix: five launches, 96 times per decode step, over 13 MB of weights that every TP rank holds in full (the HC weights are replicated). At decode sizes it is latency-bound.

- **Down kernel** (81 blocks): each block owns 4 rows of the down weight over the whole K, so the dot products need no split-K partials: the per-wave sums meet in a fixed-order LDS reduction, which keeps the op deterministic. The weights are requested first and the combine + RMSNorm overlaps with their arrival; the RMS of each stream is two waves exchanging sums through LDS. It writes the new residual, the normalized input, SiLU(lora) and the injection logits.
- **Up kernel** (80 blocks): the up GEMM and the gate mix in registers; lane reductions use DPP `row_xmask` and `v_permlanex16`.
- **Dispatch** inside the custom op (opaque to torch.compile, so the token count is a runtime value, not a trace-time one): 1-2 tokens take both kernels; 3-4 keep the Triton combine+norm and run the fused mix from its output (measured at 4 tokens: 2.82 ms against 2.91 ms for the full fusion; at 1 token the full fusion wins, 2.21 against 2.43 ms); 5+ keep the unfused chain, which is faster from 5 tokens on.
- Shapes are compile-time constants (hc_count 4, hidden 2560, lora rank 320, the only config using this path today); any other shape, dtype or non-contiguous weight falls back to the unfused chain.
- No spills (`.vgpr_spill_count` 0 for all template instances; 136-183 VGPRs).

**Tradeoffs and limitations**

- A persistent single-kernel variant (grid barrier between the halves) measured 78.4 tok/s, but it needs all 81 blocks co-resident, which occupancy predicts and nothing guarantees at launch; a cooperative launch guarantees it and captures in a graph on ROCm, but costs 21 us per launch against 4 us. Two kernels are kept.
- gfx1100 only (`VLLM_ROCM_GFX1100`); other ROCm targets and CUDA are unchanged.
- Prefill keeps the unfused path.
