# [Warmup] Let model packages register their kernel warmups

[Upstream PR](https://github.com/vllm-project/vllm/pull/64125) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

`kernel_warmup()` imports and calls the Kimi-K3, Qwen4Exp, Step5 and MiniMax-M3 warmups by name from `vllm/model_executor/warmup/`. This moves each one into its model package, which registers it on import, a step toward the model isolation and the per-model `optimize_and_warmup()` hook described in #42770.

## Claims

- `vllm/model_executor/warmup/` no longer contains model-specific warmup modules, and `kernel_warmup()` no longer names these four models.
- New `register_model_warmup(phase)` / `run_model_warmups(worker, phase)` in `vllm/model_executor/warmup/model_warmup.py` (38 lines), following the `register_backend` / `register_quantization_config` pattern.
- Same warmups run at the same two points (`"jit"`: with JIT warmup enabled, before the other warmups touch the runner; `"full"`: skipped by process-local warmups such as elastic EP). Function bodies are unchanged.

## Validation

Qwen3.8-Flash-Next NVFP4 (Qwen4Exp, MoE + MTP) served on GB10 (sm_121) with the same flags, from two images built on the same base `a94c4481e0`: one from this branch, and one from #64124 (quantization-only, so its warmup path equals main). Both start and answer a chat request correctly, and print the same warmup sequence with identical QSA profiles; only the emitting module changes:

```
JIT kernel warmup finished in 4.32s.
Warming up Qwen GDN Triton kernels for model_type=qwen4_exp_text.
Warmed Mamba batch_memcpy_kernel.
Warmed up Qwen4Exp QSA decode kernels: ((1, 1), (2, 1), (3, 1), (4, 1)).
Warmed up Qwen4Exp QSA sparse attention kernels: ((32, 1, 1), (32, 4, 1), (32, 8, 1), (32, 16, 1), (32, 64, 4), (64, 1, 2), (64, 4, 2)).
Warming up ll_bf16 router GEMM kernels for shapes: ((2560, 512),).
```

Registration of all four packages, checked in the same image on GB10: the registry is empty before any model import; importing `vllm.models.kimi_k3`, `qwen4_exp` (on first access of a model class, via its lazy `__getattr__`), `step5` and `minimax_m3` registers each warmup in its expected phase only, and re-importing does not duplicate entries:

```
jit:  vllm.models.kimi_k3.warmup.kimi_k3_triton_warmup, vllm.models.qwen4_exp.nvidia.warmup.qwen4_exp_qsa_triton_warmup
full: vllm.models.step5.nvidia.warmup.step5_dsa_warmup, vllm.models.minimax_m3.nvidia.warmup.minimax_m3_msa_warmup
```

Not served end to end: Kimi-K3, Step5 and MiniMax-M3 (no checkpoints that fit this hardware); their warmup function bodies are unchanged.

## Details

| Warmup | From | To | Phase |
|---|---|---|---|
| Kimi-K3 Triton (CUDA + ROCm) | `warmup/kimi_k3_triton_warmup.py` | `models/kimi_k3/warmup.py` | jit |
| Qwen4Exp QSA | `warmup/qwen4_exp_qsa_warmup.py` | `models/qwen4_exp/nvidia/warmup.py` | jit |
| Step5 DSA | `warmup/step5_dsa_warmup.py` | `models/step5/nvidia/warmup.py` | full |
| MiniMax-M3 MSA | `warmup/minimax_m3_msa_warmup.py` | `models/minimax_m3/nvidia/warmup.py` | full |

- Registration happens in the model package `__init__.py`, on the platform branches the warmup already supported (the registry imports that package, or one of its submodules, when the model loads). Each warmup already returned early when the loaded model lacks its layers, so registering more than one model in a process is harmless, as calling all four unconditionally was before.
- Ordering: within `"jit"`, Qwen4Exp now runs before `watermark_sample_warmup` instead of after it. In `"full"`, Step5 DSA now runs at the end, after the DeepGEMM and b12x warmups, together with MiniMax-M3. Both Step5 and MiniMax drive mixed prefill/decode batches through the model, so running them after the shared kernel warmups only means fewer kernels compile during those runs.
- Out of scope, as follow-ups: the DeepSeek-V4 / Kimi-K3 mega-MoE branch inside `deep_gemm_warmup.py`, which needs an interface on the MoE module, and `_autotune_kimi_k3_kda_qkvg`, which runs inside the FlashInfer autotune context with the runner rather than the worker.
- No new test: this is a move behind a registry with no new behavior; the validation above checks the moved path end to end.

We are migrating, model by model, the warmups to the new infra. See https://github.com/vllm-project/vllm/issues/49349

The warmup infra is model-agnostic: it just follow the stack trace for a given setup and warmups the kernels that are going to be used. This means that, once the remaining models are migrated, we won't have `model_warmup()` specializations anymore.

In that picture, `register_model_warmup()` is not needed either iiuc.
