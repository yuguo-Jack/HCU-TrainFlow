# [Feature] Enable triton autotuning for config reliant kernels

[Upstream PR](https://github.com/vllm-project/vllm/pull/59492) · state: open · merged: False

## Original PR description

## Purpose

Adds `--enable-triton-autotune` (equivalent to `--kernel-config.enable_triton_autotune`). When enabled, vLLM tunes Triton kernels that read launch configs from JSON tables during kernel warmup, before CUDA graph capture, and only for model shapes that have no config yet. Mamba `selective_state_update` (SSU) is the first kernel to use it. I will built on top of this PR and extend this to the other three families of kernels, namely: `fused_moe`, `w8a8 block fp8 gemm`, `lora`. Further information can be found in my proposal #58751.

- **Off by default** at every optimization level (`-O0` to `-O3`).
- **Generic:** a kernel opts in by implementing `TunableConfigTable` (`pending_items`, `tune`, `commit`) in `vllm/model_executor/warmup/triton_autotune.py`.
- **Safe with multiple GPUs:** ranks gather the union of the work they need, split it deterministically, gather the results, and every rank saves the same configs. Every rank reaches every collective, so if one rank's tuning fails, startup logs a warning instead of hanging.
- **Cached:** results are written to `$VLLM_TRITON_AUTOTUNE_CACHE_DIR` (default `$VLLM_CACHE_ROOT/triton_autotune/triton=<version>/<table>`). Later startups reuse them, even with the flag off.
- **Validated:** candidates are timed with the same method as `benchmarks/kernels/benchmark_selective_state_update.py`. A winner is only saved if its output matches the default config's.

Re-scoped based on the reviews in https://github.com/vllm-project/vllm/pull/48980. I coordinated with the author of draft https://github.com/vllm-project/vllm/pull/58982, and we agreed to build on this branch instead of duplicating the work.

## Testing

### Unit tests

```bash
pytest -q tests/engine/test_arg_utils.py -k triton_autotune   # 1 passed
pytest -q tests/model_executor/test_triton_autotune.py        # 5 passed (2-rank gloo test)
pytest -q tests/kernels/mamba/test_ssu_autotune.py            # 3 passed (GPU)
pytest -q tests/kernels/mamba/test_mamba_ssm_configs.py       # 8 passed (GPU)
```

- `test_arg_utils`: dotted, JSON and shorthand CLI forms, plus the error when both forms are set.
- `test_triton_autotune`: single-rank tuning, nothing pending, failed items not saved, flag off, and 2 ranks splitting uneven work with identical results on both.
- `test_ssu_autotune`: batch bucket selection; the tuned config comes from the search space and matches the default config's output; the table fills missing configs and has nothing left to tune on a second pass.
- `test_mamba_ssm_configs`: config loading and saving, including the order in which the user folder, the autotune cache and the bundled configs are checked.

### End to end (AMD MI350)

**`state-spaces/mamba-130m-hf`, TP=1** (shape `headdim=1536, dstate=16`, no bundled config):
- 5 configs tuned and saved in 2.7 s.
- The second startup found nothing to tune and loaded the cached file.
- Identical output across three runs: flag on, flag on with the cache reused, and flag off.

**`ibm-granite/granite-4.0-h-small`, TP=8** (run with `VLLM_TRITON_AUTOTUNE_FORCE=1`, because this shape has a bundled MI350 config):
- 5 items split 1/1/1/1/1/0/0/0 across the ranks. All 8 ranks saved the same file in 2.8 s, with no hang.
- Output matches a flag-off run.

SSU kernel time for Granite's per-rank shape at TP=8 (16 heads, `headdim=64`, `dstate=128`), best of 5 × 200 graph replays:

| Request batch | Default | Bundled (offline-tuned) | Warmup-tuned | Tuned vs. default |
|---|---|---|---|---|
| 1  | 3.59 µs  | 3.60 µs | 3.56 µs | 1.01× |
| 8  | 5.26 µs  | 4.15 µs | 4.19 µs | 1.26× |
| 16 | 7.27 µs  | 4.87 µs | 4.87 µs | 1.49× |
| 32 | 11.46 µs | 6.24 µs | 6.24 µs | 1.84× |
| 64 | 19.35 µs | 9.39 µs | 9.04 µs | 2.14× |

Warmup tuning matches the offline-tuned bundled table, so shapes without a bundled table now get the same speedup without running the manual benchmark. `vllm bench latency` against the bundled table (TP=8, batch sizes 1/16/64, input 32, output 256) was within run-to-run noise (−0.6% to +1.6%), as expected since both use equivalent configs.

## Usage

```bash
# CLI (shorthand or config field)
vllm serve ibm-granite/granite-4.0-h-small -tp 8 --enable-triton-autotune
vllm serve ibm-granite/granite-4.0-h-small -tp 8 --kernel-config.enable_triton_autotune true
```

```python
from vllm import LLM
llm = LLM(model="state-spaces/mamba-130m-hf", kernel_config={"enable_triton_autotune": True})
```

| Environment variable | Effect |
|---|---|
| `VLLM_TRITON_AUTOTUNE_CACHE_DIR` | Where tuned configs are saved and loaded (default `$VLLM_CACHE_ROOT/triton_autotune`) |
| `VLLM_TRITON_AUTOTUNE_FORCE=1` | Retune even if a tuned, user or bundled config already exists |
