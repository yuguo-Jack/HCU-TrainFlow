# [ROCm][Qwen3.8-Flash-Next] gfx950 fast path for the mxfp4_qsa QSA reader (stacks on #64123)

[Upstream PR](https://github.com/vllm-project/vllm/pull/64405) · state: open · merged: False

## Original PR description

> [!IMPORTANT]
> **Stacks on #64123** (`mxfp4_qsa` format, writer and portable reader). Until #64123 merges, this PR's diff includes its commits; this PR's own change is the top commit, `7b78edb36`. Draft until #64123 merges.

## Purpose

The gfx950 fast path for the `mxfp4_qsa` QSA split-K reader added in #64123. On MI355X it makes the MXFP4 reader 1.18x–1.45x faster than FP8 from 16 rows up, where #64123's portable reader (dequantize K and V to BF16) is slower than FP8.

## Changes

- `vllm/models/<model-pkg>/amd/ops/qsa.py`, split-K sparse reader:
  - On gfx950, QK runs on the scaled MFMA (`tl.dot_scaled`, bf16 x e2m1), and V is decoded with the hardware `v_cvt_scalef32_pk_bf16_fp4`, which is bit-identical to the portable decoder. Both are on by default on gfx950; other targets keep #64123's portable decode.
  - **Deviation: PV runs in BF16 on dequantized V**, not on the block-scaled MFMA, because V's scale groups run along the head dim. A native P×V (V's E8M0 scales folded into P, P re-quantized to E4M3) was built and measured: it holds numerics but runs at **0.63x–0.75x** of this path at 1–128 rows, so it is not adopted.
  - An mxfp4 split-K profile uses 64-wide tiles with fewer splits from 16 rows up. It was swept on MI355X at one shape (TP2, top-k 2048); top-k 512/1024 below reuse it untuned. The BF16/FP8 profile is unchanged.
- `ops/mxfp4_kv.py`: the hardware E2M1 row decoder used by the reader.
- `test_qsa_mxfp4_amd.py`: the reader test runs with both QK paths and both V decoders against an fp32 attention over the dequantized cache.

`<model-pkg>` is the model's package directory on vLLM main.

## Kernel timings (split-K reader, MI355X)

The shape is the TP2 decode shape: 12 Q heads, 1 KV head, head_dim 256, 32K context per request, and one request per row. Selections are indexer-shaped: top-k compressed blocks of 4 consecutive tokens. L2 and the 256 MB MALL are flushed before every timed call, and each value is the median of 30. FP8 uses #61529's unchanged reader and profile.

Top-k 2048:

| Rows | BF16 (µs) | FP8 (µs) | MXFP4 (µs) | MXFP4 vs FP8 | KV-read roofline: BF16 / FP8 / MXFP4 |
|---|---|---|---|---|---|
| 1 | 16.9 | 17.8 | 18.4 | 0.97x | 3% / 1% / 1% |
| 4 | 19.0 | 19.3 | 19.7 | 0.98x | 9% / 5% / 2% |
| 16 | 28.8 | 28.0 | 23.7 | **1.18x** | 24% / 13% / 8% |
| 64 | 73.8 | 47.7 | 40.0 | **1.19x** | 38% / 29% / 19% |
| 128 | 123.3 | 84.2 | 58.0 | **1.45x** | 45% / 33% / 26% |
| 256 | 189.6 | 137.6 | 103.5 | **1.33x** | 59% / 41% / 29% |
| 512 | 304.7 | 222.9 | 178.9 | **1.25x** | 74% / 50% / 33% |

MXFP4 vs FP8 at top-k 1024 is 0.98x / 0.98x / 1.05x / 1.09x / 1.39x / 1.39x / 1.30x. At top-k 512 it is 0.98x / 0.99x / 0.96x / 1.05x / 1.30x / 1.41x / 1.35x (same row order).

- **Roofline basis.** The roofline column is the KV-read floor (selected rows × bytes per token ÷ measured device copy bandwidth, 4.79 TB/s) divided by measured time. Arithmetic intensity is 12–45 FLOP/B, far below MI355X's ridge point, so every arm is bandwidth-bound in principle.
- **Where the time goes.** At 1–4 rows a fixed latency of about 16 µs dominates: dependent index → page → KV gathers plus the split reduction. MXFP4 is still latency- and issue-bound, at 33% of its byte floor at 512 rows.
- **Effect of each change**, at 256 rows:
  - The portable decode with dequantized K ran at 309 µs, and `dot_scaled` QK alone at 163 µs.
  - Adding the hardware V decode brought that to 125 µs; the split-K profile brought it to 104 µs.
- **Retuning FP8 too.** The same sweep finds 10–15% for FP8 by retuning its profile; that is left to #61529's path. Against that tuned FP8, MXFP4 is still 1.04x–1.28x faster from 16 rows up.

## Serving A/B (MI355X, TP2)

Both arms use the same image, the same BF16 checkpoint, the same flags except `--kv-cache-dtype`, and an FP8 indexer cache. Both also carry #64161, the dtype-independent Mamba-align scheduler fix, which is a separate PR. Without that fix this branch's larger hybrid block (5904 tokens versus 3136 for FP8) idles part of every prefill step. The benchmark is `vllm bench serve` with random prompts and `--ignore-eos`, two waves per point.

**KV capacity:** 14.36M tokens for FP8 versus 21.74M for MXFP4 (+51%), which is 110 versus 166 concurrent 128K-token requests.

Low-bit gain (MXFP4 versus FP8, both with #64161):

| input / output | concurrency | FP8 output tok/s | MXFP4 output tok/s | Δ | FP8 / MXFP4 mean TTFT | FP8 / MXFP4 mean TPOT |
|---|---|---|---|---|---|---|
| 7K / 512 | 1 | 130.3 | 129.9 | 0% | 0.41 / 0.41 s | 6.89 / 6.92 ms |
| 7K / 512 | 64 | 1185 | 1201 | +1% | 6.12 / 6.07 s | |
| 32K / 1K | 64 | 686 | 686 | 0% | 22.4 / 22.6 s | 71.1 / 71.0 ms |
| 32K / 1K | 128 | 1043 | 1006 | -4% | 41.7 / 46.3 s | 80.8 / 80.9 ms |
| 32K / 1K | 256 | 1080 | 1097 | +2% | 94.7 / 91.8 s | 141.5 / 140.7 ms |
| 64K / 2K | 128 | 620 | 630 | +2% | 184 / 180 s | 114.6 / 112.9 ms |
| 64K / 2K | 256 | 729 | **1072** | **+47%** | 268 / **194** s | 188.4 / **140.0** ms |

- The win shows where FP8 runs out of KV: 256 × 66K tokens is 16.9M, above FP8's 14.4M, so FP8 queues and MXFP4 doesn't. Below capacity the arms are within noise, because the current reader is no faster than FP8 at 1–4 rows (table above) and decode at low concurrency is not KV-read-bound.
- The 7K c1 row is a repeat run; the first run of each suite includes one-time JIT. The 7K c16 point is omitted: its run-to-run spread on the same server (about ±15%) is larger than the arm difference.
- Dtype-independent gain (#64161 alone, MXFP4 arm): 7K c64 goes from 1069 to 1201 output tok/s (+12%), with mean TTFT from 9.54 s to 6.07 s. On FP8 the fix is neutral. Details are in #64161.
- **Objective status:** this falls short of +10% decode throughput at C1 and at the served concurrency. The next lever is native P×V and QK on the block-scaled MFMA (E4M3 P/Q × E2M1 K/V), which targets the 1–64-row reader latency.
