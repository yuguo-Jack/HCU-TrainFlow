# [Security] Cap OpenPangu video sampling at the source frame count

[Upstream PR](https://github.com/vllm-project/vllm/pull/58571) · state: closed · merged: False

## Original PR description

## Summary
`OpenCVDynamicOpenPanguVideoBackend` sizes an `np.linspace` buffer from request `num_frames`. The only existing clamp runs when `fps > 0` and `num_frames` is at least `duration * fps + 1`, so `fps=-1` or a value just under that bound allocates from the request count. Cap `num_frames` at the container frame count before that allocation.

## Changes
- `vllm/multimodal/video.py`: after the existing fps branch, set `num_frames` to `total_frames_num` when the request asks for more frames than the container has.
- `tests/multimodal/test_video.py`: cover `fps=-1`, a count just under the fps bound, and a request that stays within the container.

## Codepath coverage
`load_bytes` always decodes through `decode_video` → `compute_frames_index_to_sample`. Chat completions, embeddings, responses, tokenize, invocations, and offline `LLM` all reach that method via `MediaConnector` / `VideoMediaIO`. The cap is on the method, so every caller is covered. This backend hardcodes the OpenCV decoder.

## Duplicate-work check
Searched open and merged PRs for `openpangu`, `num_frames`, and `vllm/multimodal/video.py`.
- #56390 only treats `num_frames < 0` (the linspace crash). A large positive `num_frames` with `fps=-1` is unchanged.
- #51969 clamps `num_frames` in `VideoMediaIO.merge_kwargs` against a finite engine ceiling. It does not touch this backend, and a request value still passes through when the engine ceiling is `-1`.
- #46836, #50990, #46153, and #55582 do not add this bound.
