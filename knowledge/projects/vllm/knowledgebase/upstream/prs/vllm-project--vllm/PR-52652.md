# [Perf][Kernel][Quantization] Tensor-descriptor path for int4 fused_moe_kernel_gptq_awq (XPU default, sm100 opt-in)

[Upstream PR](https://github.com/vllm-project/vllm/pull/52652) · state: open · merged: False

## Original PR description

## Overview

Adds a tensor-descriptor (TD) path to `fused_moe_kernel_gptq_awq` for grouped `int4_w4a16` weights, mirroring the one [#42436](https://github.com/vllm-project/vllm/pull/42436) added to `fused_moe_kernel` (RFC [#42545](https://github.com/vllm-project/vllm/issues/42545)). A is gathered with `tensor_descriptor.gather`; packed int4 B is loaded as bytes and unpacked with `tl.interleave`. `int8_w8a16` keeps the pointer path.

## Claims

- **When TD runs:** `VLLM_TRITON_USE_TD` resolves on (unset: XPU only; `1`: also CUDA sm100+) and the launch reaches the Triton WNA16 kernel. On XPU that needs `--moe-backend triton`, since default serving picks `XPUExpertsWNA16`. sm90 and ROCm always use the pointer path.
- **Fallbacks to the pointer path:**
  - `VLLM_BATCH_INVARIANT=1`: TD and pointer may round differently, so all batch sizes stay on one path.
  - `BLOCK_SIZE_M < 8`: the `gather()` minimum.
  - `BLOCK_SIZE_M == 32`: TD is −42% there on Arc Pro B60. Not measured elsewhere, so this applies on every device.
  - A single-token batch, in both GEMMs: the down projection now receives the layer's token count as `num_input_tokens`, because its A has tokens × top_k rows.
  - `K % BLOCK_SIZE_K != 0` (with a one-time warning, like `invoke_fused_moe_triton_kernel`).
  - `BLOCK_SIZE_K < 32`: the packed-byte descriptor needs a 16-byte inner block.
- **Kernel speed:** Arc Pro B60 +13…+17% at M 2–20 and +28…+31% at M 41–4096; Arc Pro B70 +10…+13% at M 4–16 but −4.8% at M 2. Pointer path at M 1 and 21–40.
- **E2E (B70):** prefill-heavy +10–11% for both models and Qwen3-30B mc4 +6.0%. Single-stream decode no longer regresses (+0.8%, was −3.6%). Qwen1.5 mc4 is −1.6% (see Validation). The pointer path matches `main` within 0.7%.
- **Accuracy:** gsm8k differences are within the A/A spread. That rules out a drop larger than about 1.5–2 points, not every drop.

## Details

- **Overlap with [#52577](https://github.com/vllm-project/vllm/pull/52577):**
  - #52577 masks the pointer-path B load, which this PR moves under `else:`. The conflict is textual.
  - The `K % BLOCK_SIZE_K` fallback routes ragged-K launches onto that same unmasked load, so #52577 should land first. Whichever lands second keeps its mask.
- **Other open PRs on this launch site:**
  - [#56154](https://github.com/vllm-project/vllm/pull/56154) rewrites it into a warmup dispatcher.
  - [#56788](https://github.com/vllm-project/vllm/pull/56788) and [#57558](https://github.com/vllm-project/vllm/pull/57558) add tuned XPU configs, which use BLOCK_SIZE_M=32 for some shapes. Those launches would stay on the pointer path.
  - No open PR adds TD to this kernel.
- **Allocator:** `set_triton_allocator` is registered as in `invoke_fused_moe_triton_kernel`. [#61583](https://github.com/vllm-project/vllm/pull/61583) reports that XPU never calls it and that registering it can break torch.compile `split_module`. The graph-mode E2E runs above did not hit that.
- **Design:**
  - The B descriptor is built inside the kernel, as in `fused_moe_kernel`'s TD path.
  - [#63820](https://github.com/vllm-project/vllm/pull/63820) builds a host `TensorDescriptor` for fp8 B on sm90 (`USE_TMA_B`), which ignores `VLLM_TRITON_USE_TD`. A host descriptor for packed int4 B was not tried.
- **Default on XPU:** RFC #42545 asks for a separate PR to flip a kernel's default. Like #42436, this PR converts the kernel and follows the shared XPU default in one step; `VLLM_TRITON_USE_TD=0` turns it off. Its `envs.py` entry now lists every consumer.
- **Not covered:** TP > 1, EP, int8, AWQ and Quark checkpoints.
