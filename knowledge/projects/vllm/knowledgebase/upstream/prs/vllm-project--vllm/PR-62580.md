# [KV Offload] Add valkey secondary tier

[Upstream PR](https://github.com/vllm-project/vllm/pull/62580) · state: open · merged: False

## Original PR description



## Overview

This change adds a new secondary tier pair, valkey and
valkey-large-object, next to the fs and obj tiers.

The valkey provider uses plain get/set through valkey-glide, and
valkey-large-object uses RDMA over efa-direct. The new module is
valkey-io/valkey-large-object.

In preliminary time-to-first-token tests using an RTX Pro 4500
Blackwell with Qwen3-8B-FP8 and a 15k token prompt, plain
valkey (4056ms) is slower than GPU recompute (1809ms). However,
valkey-large-object (359ms) is close to local NVMe (329ms).

I lifted the thread pool to tiering, and the job bookkeeping into
a shared PooledTierManager. The fs and both valkey tiers now
consume these components. The fs test helpers also moved to
pooled_tier_utils.py so the new tier tests can share them.

https://github.com/valkey-io/valkey-large-object

## Claims

Extends the tiering infrastructure to support Valkey. While Valkey itself
over tcp does not look particularly compelling, the RDMA path through
valkey-large-object appears competitive with local ssd, with attendant
pros and cons to shared remote KV cache.

## Validation

An end-to-end time to first token test was chosen to get a first
approximation of performance. KV caches were flushed between runs to
make it relatively fair, and the deltas are large enough to at least show
the form of the change.

Model choice was based on convenience and fit for the hardware I was
able to get. There will definitely be a different prefill:load break-even point
on different hardware - and on different network interfaces.

### To reproduce:
First, recognize this is a module under active development and client releases are being worked on. With that said,

#### vllm
* Build [the WIP glide-sync client](https://github.com/anitarua/valkey-glide/tree/feat/rdma-4-python-sync) with GLIDE_SYNC_RDMA=1
* Generate the `glide_shared/protobuf` pb2 modules with protoc, because glide source doesn't include them.
* Install libfabric, either from the EFA installer or a libfabric package if you use the tcp provider. (Or use an instance with libfabric already installed on the system)

#### valkey-large-object
Build the module https://github.com/valkey-io/valkey-large-object
```
valkey-server --save "" \
    --loadmodule libvalkey_large_object.so operating-mode Dram dram-maxmemory 4gb
```

```
VLLM_TEST_VALKEY_LARGE_OBJECT_NODES=127.0.0.1:6379 \
    .venv/bin/python -m pytest tests/v1/kv_offload/tiering/test_valkey_large_object_tier.py -v
```

## Details

The valkey-large-object project is very new, and currently inconvenient to use. But over the coming months,
the glide client will be updated and the module will have releases. RDMA-capable hardware and specialty
networking is required to make the most of this secondary tier. For users on AWS, there is some choice there,
and support for other RDMA hardware is planned.
