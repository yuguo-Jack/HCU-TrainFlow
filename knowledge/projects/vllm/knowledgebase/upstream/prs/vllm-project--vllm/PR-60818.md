# [Bugfix][Parser] Keep text after a quoted Qwen <tool_call> marker

[Upstream PR](https://github.com/vllm-project/vllm/pull/60818) · state: open · merged: False

## Original PR description



## Overview

Fixes #56658. Stop the Qwen3 engine parser from discarding text that follows a `<tool_call>` marker the model writes as plain text, for example when quoting the marker in prose or in reasoning. Supersedes #60610, which lost its head branch.

Not a duplicate: no other vLLM PR targets #56658. The related PRs named in the issue (#53297, #55848, #53739, #55562) cover different parsers or paths, and the fix referenced there is in a downstream repository, not in vLLM.

## Claims

- Text after a quoted `<tool_call>` stays in its original channel, content or reasoning. When the marker is quoted inside reasoning, the closing `</think>` and the final answer are no longer lost.
- Real tool calls are parsed as before. This includes a call that follows a quoted marker and a call that directly ends reasoning.
- Truncated openers (#47137) and empty or unparsable `<tool_call>…</tool_call>` blocks are still dropped, as before.

## Validation

### End-to-end

Served `Qwen/Qwen3.5-2B` on an RTX 4070 with `--enable-auto-tool-choice --tool-call-parser qwen3_coder --reasoning-parser qwen3`. The model was served once on `main` (459764104d) and once on this branch. Each prompt ran non-streaming and streaming at temperature 0. Non-streaming and streaming results were identical in every case.

```text
Quoted in content (thinking off; model asked to repeat a sentence):
  main:    content = "The literal marker is "
  this PR: content = "The literal marker is <tool_call> and it starts a tool call. END"

Quoted in reasoning (model asked to write <tool_call> while thinking, then answer DONE):
  main:    reasoning = 'The user is asking me to write the exact text "'   content = ""
  this PR: reasoning = full thinking (334 chars, both quoted markers kept)   content = "<tool_call>\nDONE"

Real call (get_weather):
  main:    tool_calls = [get_weather]
  this PR: tool_calls = [get_weather]
```

### Unit tests

Added `TestQuotedToolCallMarker` to `tests/parser/engine/test_qwen3_reasoning.py`. It covers:

- a marker quoted in content;
- a marker quoted in reasoning;
- a quoted marker followed by whitespace, then prose;
- a real call after a quoted marker;
- a real call that ends reasoning;
- an opener cut off by EOS.

Each case runs through `Qwen3Parser` and through the `DelegatingParser` pairing that `vllm serve` uses, in both `parse()` and `parse_delta()`. Streaming uses deltas of 1, 7 and all tokens, in text-only and full token-ID streams, and ends with EOS. On `main`, 48 of the 64 cases fail. With this change, all 64 pass.

```bash
pytest tests/parser/engine/test_qwen3_reasoning.py -k QuotedToolCallMarker
pytest tests/parser/
```

`pytest tests/parser/` reports the same set of failing tests before and after this change. The failures that exist on `main` come from tokenizers that could not be downloaded in the test environment. `ruff check` and `ruff format --check` pass.

## Details

`qwen3_config` maps `TOOL_START` in `CONTENT`/`REASONING` directly to `TOOL_PREAMBLE`. `StreamingParserEngine` applies that transition as soon as the marker is lexed. Text in `TOOL_PREAMBLE` produces no events, so prose after a quoted marker is dropped. Inside reasoning, the `</think>` that follows has no transition from `TOOL_PREAMBLE` either, so the answer is lost as well.

This PR adds `ParserEngineConfig.tool_start_confirm_terminals`, which is empty by default. When it is set, the engine holds the opener and the text after it instead of transitioning immediately, and resolves the hold as follows:

- **A confirming terminal arrives** (`<function=` or `</tool_call>` for Qwen3). The opener is processed as before, and the held text is replayed.
- **A terminal that has a transition from the original state arrives** (`</think>`, another `<tool_call>`). The marker was quoted, so the held text is emitted in its original channel.
- **The output ends after prose.** The held text is emitted in its original channel.
- **The output ends after only whitespace or a partial `<function`.** The opener is treated as a truncated call and dropped, as before. EOS and other dropped special tokens are still dropped while an opener is held.

`vllm serve` splits parsing into a reasoning pass (`skip_tool_parsing`) and a tool pass, and both passes are covered:

- The reasoning pass holds an opener only while in `REASONING`; once reasoning ends, the tool pass makes the decision.
- The tool pass receives only the current delta's token IDs. If the reasoning pass confirms an opener in a later delta than the one it arrived in, the opener's token ID is no longer available. In that case the reasoning pass forwards the call starting from the confirming `<function=`, which the existing `<function=` fallback transition parses.

Only `qwen3_config` enables the option, which means the parsers built on it are affected: MiMo, Step-3.5, Nemotron-v3 and Granite-thinking. Other configs are not affected. The change is confined to the parser engine and adds no code to the core engine or scheduler.

Limitations:

- In streaming, text after a quoted marker is released when the marker is resolved, not token by token. Real tool calls are not delayed, because `<function=` follows the opener directly.
- A quoted `<tool_call>` that is later followed by a quoted `</tool_call>` is still treated as an empty block, as on `main`.
- `is_reasoning_end` and `find_reasoning_end_offset` operate on token IDs for structured-output gating. They are unchanged and still treat the `<tool_call>` token as the end of reasoning.
