# [Bugfix][Multimodal] Fix DP vision encoder hang: type an empty rank's output with the model's compute dtype

[Upstream PR](https://github.com/vllm-project/vllm/pull/65352) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Fixes a hang in the shared data-parallel vision encoder helper `run_dp_sharded_mrope_vision_model` (`--mm-encoder-tp-mode data`, TP >= 2) when a vision tower's first parameter has a different dtype from the embeddings it returns. It also documents the helper's dtype contract and checks it at runtime. Follows up on the dtype choice made in #56872.

## Claims

- **Fix:** a rank that receives no images now types its empty output with the model's declared `dtype` when present, falling back to the first parameter's dtype as before. This removes the startup hang of MiniMax-M3 at TP2 with `--mm-encoder-tp-mode data`, observed on vLLM nightlies after #64111.
- **Contract:** the docstring states that `vision_model.dtype`, when defined, must be the returned embedding dtype, and that a model whose output dtype differs from its first parameter must define it.
- **Runtime check:** with TP > 1, each rank that ran the model compares its output dtype with the empty-rank dtype before its all-gather and raises a `ValueError` naming the model and the fix. This is a local dtype comparison with no added collective communication. TP = 1 behaviour is unchanged.

## Validation

All runs are on MI355X (ROCm, RCCL) with `vllm/vllm-openai-rocm:nightly-40941f2c4ba96fba0a7e282a5355e89cd74d9ac5` plus this branch's files, unless noted.

**End to end** (MiniMax-M3, TP2, `--mm-encoder-tp-mode data`):
- With `amd/MiniMax-M3-MXFP4-AttnFP8` and the PR's first commit (dtype selection only), the server hung in `profile_run` without the fix on 3 of 3 starts on one node (600 s RCCL watchdog) and on 2 of 2 starts on a second node. With the fix it started and served image requests. On the second node this held for the stock nightly with only this PR's `vision.py` swapped in.
- With this PR's final `vision.py` (`amd/MiniMax-M3-MXFP4`, OOB TP2 server flags without the reasoning/tool parsers):
  - The encoder profile ran with one item on two ranks.
  - The server became ready without the check firing and answered one image request with HTTP 200 in 2.3 s.
  - This was a start-and-serve check only, not an accuracy evaluation. The check can only raise; it does not change values.

**Failure handling.** These are additional experiments, not CI tests. The scripts and logs are not in the PR. The cases below exercise the check with a mixed-dtype toy tower; the rank processes ran either independently or under a supervisor:

| case (TP2 unless noted) | result |
|---|---|
| correct `dtype`, 1 image (one rank empty) | output equals direct (bf16) |
| matching dtypes, no `dtype` (fallback), 1 image | output equals direct |
| missing `dtype`, 2 images | both ranks raise |
| wrong `dtype` (fp32 declared, bf16 returned), 2 images | both ranks raise |
| TP1, missing or wrong `dtype` | unchanged, no error, output equals direct |
| TP2, no images | unchanged |
| missing `dtype`, 1 image, **independent unsupervised processes** | the busy rank raises; the empty rank stays stuck in the queued all-gather until an external kill at 120 s |
| wrong `dtype`, 1 image, independent unsupervised processes | the busy rank raises; the empty rank is aborted by PyTorch's NCCL heartbeat monitor after 2.7 s (a race, not a clean exit) |
| missing `dtype`, 1 image, under `torch.multiprocessing.spawn` | the supervisor terminates the run 2.8 s after the error |

The helper on its own therefore does not shut down cleanly when a rank is empty; cleanup relies on the caller's supervision.

One real server run checked that supervision. The setup was MiniMax-M3 TP2 with `--mm-encoder-tp-mode data` and the OOB server flags, plus a test-only override, not part of this PR, that restores the old first-parameter rule so the check fires:
- Worker TP0 raised `ValueError: MiniMaxVLVisionModel returned torch.bfloat16 embeddings, but a rank without images would send torch.float32. Set `dtype` on the vision model to its output dtype.` in `profile_run`.
- EngineCore failed to start, and the executor shut the workers down.
- The server exited about 11 s after the error, never reported ready, and left no vLLM or GPU worker processes.

**Not validated:** CUDA, TP > 2 failure handling, failure during active serving (as opposed to the startup profile run), repeated server runs (n = 1), and an accuracy evaluation. No accuracy run is included because the change alters only the dtype of empty placeholders and adds a raise.

**Checks:** `pre-commit run` on the changed files passes, including ruff, mypy, typos and test tethering.

## Details

**Root cause.**
- The helper all-gathers padded per-rank embeddings. A rank that receives no images builds an empty output, and before this PR typed it with `next(vision_model.parameters()).dtype`.
- Since #64111, MiniMax-M3's vision tower keeps its first parameter, the patch-embedding weight, in fp32, while it computes and returns bf16 and declares `dtype = bf16`.
- The empty rank therefore entered the all-gather with fp32 while the other rank sent bf16, and the collective never completed.
- Reproducing this needs an empty rank. In the reported failing configuration, the encoder profile run encoded one dummy item on two ranks, which left one rank empty. During serving, the same happens whenever an encoder batch has fewer images than ranks.

**Why `dtype`.** Callers already treat `visual.dtype` as the tower's dtype for embeddings (e.g. `image_embeds.type(self.visual.dtype)`), and MiniMax-M3 already declares it. Reusing it avoids a second declaration that could drift. Models without `dtype` keep the old first-parameter behaviour.

**Callers checked.** Qwen2-VL, Qwen2.5-VL, Qwen3-VL, GLM-4.1V, dots.ocr, Cohere Compass and Cosmos3-edge define `dtype` as their patch-embedding dtype. Kimi-VL and the Kimi-K2.5 ViT use the fallback. None of them trips the check in their standard configuration; MiniMax-M3 is the only confirmed failure.

**What the check does and does not do.**
- It raises on ranks that ran the model, before their all-gather.
- It does not cast weights or outputs to hide a mismatch.
- It does not add a collective. A coordinated pre-check would cost an extra collective on every encoder call to handle a configuration error that the executor already cleans up in the tested configuration.

**Duplicate check.** No other open PR changes this dtype selection; #53164 and #55587 touch the same feature for different issues.

**AI assistance.** AI assistance was used to write the code, tests and this description and to run the experiments. The submitter reviewed every changed line and ran the tests above.
