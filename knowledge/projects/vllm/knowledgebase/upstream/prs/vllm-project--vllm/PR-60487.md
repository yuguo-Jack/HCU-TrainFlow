# [Bugfix][ROCm] Count attention sinks once in AITER FA chunked-context extend

[Upstream PR](https://github.com/vllm-project/vllm/pull/60487) · state: open · merged: False

## Original PR description



## Overview

`ROCM_AITER_FA` counted the learned attention sink once per partial when it merged the attention for a request that has cached context. The fix is to pass the sink only to the causal call over the new tokens. Every model with sinks (gpt-oss) gets wrong attention on this backend whenever a request goes through `extend_forward`'s full-attention path: any prompt longer than one prefill chunk (chunked prefill), and any prefix-cache hit. The bug came in with sink support in #43817 and is still on `main`. I found no open PR or issue that fixes it (details below).

## Claims

- Fixes the sink overcount in `AiterFlashAttentionImpl.extend_forward` (full-attention layers). After the fix, chunked-context extend matches unsplit attention to within bf16 noise.
- The change is one argument (`sink_ptr=None` on the cached-context chunk calls). The sliding-window extend path, plain prefill, decode and models without sinks are not affected: the no-sink output is bit-identical before and after.
- Adds a regression test to `tests/kernels/attention/test_rocm_aiter_fa.py`. It fails on the current code and passes with the fix.

## Details

**Root cause.** For an extend request, `extend_forward` (when `sliding_window == -1`) computes:

1. a causal `flash_attn_varlen_func` over the new tokens, returning `(out, lse)`;
2. one non-causal call per cached-context chunk, each returning `(out_i, lse_i)`;
3. a merge of all partials, weighted by `exp(lse)`, through `merge_attn_states`.

All of these calls passed `sink_ptr=self.sinks`. AITER adds the sink as an extra logit with zero value, so each partial's normalizer was `D_part + exp(s)` instead of `D_part`. Merging by LSE adds the normalizers together, so the final denominator was

```
D + (num_chunks + 1) * exp(s)    instead of    D + exp(s)
```

Attention to the real keys was scaled down by a factor that depends on context length and on the chunk size `_CP_TOKENS_PER_ITER_ROCM // num_extends`. A request in a ragged batch also gets an extra `exp(s)` from each empty context chunk, because a sink-only partial has `lse = s`. The overcount is large in heads where the sink holds a big share of the softmax mass.

**Fix.** The causal call over the new tokens covers every query row, so the sink is added there exactly once. The context-chunk calls now pass `sink_ptr=None`. Their partials are then plain softmax partials, and the existing LSE merge is exact. Empty context chunks now return `lse = -inf`, which `merge_attn_states` already handles: it keeps the other side, and when both sides are empty it outputs 0 / `-inf`. The test covers empty chunks.

**Not affected.** `extend_for_sliding_window` makes one causal call and no merge, so it was already correct. Plain prefill and decode use a single call. Without sinks, `sink_ptr` was already `None`.

**Test design.** The test runs the backend through `AiterFlashAttentionMetadataBuilder` and `forward`, like `test_aiter_fa_shared_kv_matches_reference`. It monkeypatches `_CP_TOKENS_PER_ITER_ROCM` to 96, so three extends with context lengths 128 / 32 / 69 produce 4 context chunks, including empty chunks for two of the requests. The block table is scrambled, and the reference is `ref_paged_attn` extended with an optional sink logit. The model config (`Qwen/Qwen2.5-0.5B-Instruct`) was chosen because it has head_dim 64. At head_dim 128, aiter routes bf16 varlen calls to its v3 kernel (`can_impl_fmha_v3_fwd` in `aiter/ops/mha.py` has no sink check, and `fmha_v3_varlen_fwd` takes no sink), so the sink is ignored; head_dim 64, the gpt-oss size, goes to the CK kernel, which applies it. I measured this on aiter 0.1.21.post2, and the same dispatch is in 0.1.24.post1 and on aiter main. That is a separate aiter issue.

**CI.** The test lives in a file that the `:amd: (MI300) Attention Kernels` shards already run. I did not validate on gfx942 myself.

**Duplicate check.** I searched open and closed PRs and issues for "aiter sink", "rocm_aiter_fa sink", "sink_ptr", "sinks extend_forward" and "aiter sinks chunked prefill". #43817 added sinks to this backend and introduced the pattern. #35146 (open) is an older version of the same sink support with the same per-chunk sink. #47672 and #54180 change decode routing and do not touch the extend context path.
