# [Bugfix][Core] Raise a fresh EngineDeadError per request instead of re-raising the shared instance

[Upstream PR](https://github.com/vllm-project/vllm/pull/56947) · state: open · merged: False

## Original PR description

### Purpose

Fixes #56943.

When the engine dies, `AsyncLLM.output_handler` logs the root cause once and then `OutputProcessor.propagate_error()` hands the **same** exception instance to every in-flight request's `RequestOutputCollector`. Each consumer's `raise output` prepends its own frames onto the shared `__traceback__`, and the OpenAI serving layer logs that accumulated traceback once per request (`logger.exception("Error in chat completion stream generator.")`). Log volume therefore grows quadratically with the number of in-flight requests: an incident log showed 93 ever-growing tracebacks (233 → 845 lines per traceback) totaling 41,340 ERROR lines in ~10 minutes for ~90 concurrent requests.

Fix: in `RequestOutputCollector.get()`/`get_nowait()`, raise a fresh `EngineDeadError() from None` when the collected output is an `EngineDeadError`:

- Each request then logs only its own constant-size traceback; the root cause is still logged exactly once by `AsyncLLM.output_handler`.
- `from None` keeps the shared instance out of the `__context__` chain that logging would also print.
- The message users see is unchanged: `EngineDeadError` always carries the standard "EngineCore encountered an issue. See stack trace (above) for the root cause." text (`_format_exception` never attaches per-incident args).
- Non-`EngineDeadError` exceptions still pass through as the same instance, so per-request error behavior is unchanged.
- New requests already fail fast with a fresh instance via `ensure_alive()`, so this makes the in-flight path consistent with the new-request path.
- This follows the existing precedent in `generate()`, which wraps failures into a fresh `EngineGenerateError() from e` instead of re-raising a shared instance.

The collector is the single choke point through which both consumers (`generate()` and pooling `collect()`) receive the error, so the fix covers all current and future consumers.

Note on the base: this branch is based on the fork's `main` (the fork could not be synced to upstream `main` with the available token scopes). I verified with `git merge-tree` that it merges cleanly into today's `main`, and the merged `vllm/v1/engine/output_processor.py` is byte-identical to applying the same patch directly on `main`. Happy to rebase if preferred.

### Test Plan

Added `tests/v1/engine/test_request_output_collector_errors.py`:

- `test_collector_raises_fresh_engine_dead_error`: a shared `EngineDeadError` whose `__traceback__` was pre-grown by 10 re-raises is put into collectors; both `get()` and `get_nowait()` must raise a *fresh* instance whose traceback is shorter than the accumulated one, with `__suppress_context__` set.
- `test_collector_reraises_request_error_instance_unchanged`: non-`EngineDeadError` exceptions are still re-raised as the same instance.

### Test Result

Standalone reproduction of the collector mechanics (this machine has no full vllm dev env; CI will run the new unit tests):

```
shared error pre-grown to 10 tb entries
fixed:    get_nowait() : 3 fresh errors, constant tb depth 3
fixed:    await get(): 3 fresh errors, constant tb depth 4
control:  shared instance tb depth grows per consumer [12, 14, 16]
control:  ValueError re-raised as the same instance (unchanged behavior)
```

i.e. before the fix each consumer re-raising the shared instance grows its traceback by one consumer round per request; after the fix every consumer gets a constant-size traceback and the shared error stays out of the logged chain.

Related: vllm-ascend companion fix vllm-project/vllm-ascend#16570 (a model wrapper that amplified the same storm with extra frames), reported in vllm-project/vllm-ascend#16567.
