# [Bugfix][Parser] Resolve stripped special-token terminals without holding the stream

[Upstream PR](https://github.com/vllm-project/vllm/pull/57255) · state: open · merged: False

## Original PR description

## Purpose

Fixes #57232

With an engine-based tool parser, no reasoning parser and a request without tools, the renderer never calls `adjust_request()`, so `skip_special_tokens` stays `True` and the detokenizer strips the reasoning markers from `delta_text`. `TokenIDScanner` then defers the marker terminal and waits for text that never arrives: every later delta is held, and at `finish()` the deferred terminals are flushed after the held text with text decoded from their ids, which the `skip_reasoning_parsing` bypass from #47562 emits as content. On the wire the stream returns nothing until the last delta, and that delta ends with the stripped markers.

This is not gemma4-specific. The same shape on `qwen3_coder`, `deepseek_v4`, `qwen3_xml` and `minimax_m2` (`<think>`/`</think>` ids, no reasoning parser, `skip_special_tokens=True`) returns `plananswer<think></think>` on main.

Fix: the scanner receives the terminal ids the tokenizer strips (`all_special_ids`) and the request's `skip_special_tokens`. A deferred terminal that can never receive text is resolved text-less at the next delta, or at finish, in token order. Hold-back deferral for text that may still arrive is unchanged. This changes `engine/` rather than `gemma4.py` because the behavior is wrong for every engine parser.

Three test fixtures streamed special-token text under a request that still said `skip_special_tokens=True`. Serving never produces that shape, since `adjust_request()` clears the flag before such text reaches a parser, so those fixtures now clear it (`replay_harness.py`, `test_gemma4_streaming_reasoning.py`, `tests/parser/test_streaming.py`).

### Why this is not duplicating an existing PR

#57247 fixes the gemma4 half inside `Gemma4Parser._preprocess_feed` and also covers #57231. I tested its head (`0c51215a7`): the gemma4 rows are fixed there, but the four other engine parsers above still return `plananswer<think></think>`, because the deferral lives in the scanner. This PR is the engine-level half, does not touch `gemma4.py`, and does not claim #57231. Duplicate checks (`gh pr list --search "57232 in:body"` and area keyword searches) were run before pushing; #57247 is the only related open PR.
