# Allow reset_prefix_cache to clear cached prefixes without preempting running requests

[Upstream PR](https://github.com/vllm-project/vllm/pull/64900) · state: open · merged: False

## Original PR description

## Background

Issue #64853 requested a new behavior for `reset_prefix_cache` that clears
the prefix cache without preempting running requests. The endpoint currently
offers two behaviors while requests are running:

- **Default mode**: the reset fails (`success: false`) while any block is held
  by running requests. Under sustained load, the window where nothing is in
  flight can be vanishingly small or absent entirely.
- **`reset_running_requests=true`**: the reset succeeds, but every running
  request is preempted and restarts from scratch, adding repeated prefill
  work on top of the cache-loss shock.

Neither mode lets operators separate the effect of losing the cache from the
effect of restarting all running requests.

## Problem

There was no way to invalidate all prefix-cache hashes while keeping
in-flight requests undisturbed. The `BlockPool.reset_prefix_cache` gate
required that every GPU block (except the null block) be free before
proceeding, which makes the default reset unusable under sustained load,
and the preempt mode couples cache invalidation with request disruption.

## Solution

Add a new `preserve_running_requests: bool = False` parameter throughout the
call chain — from `BlockPool.reset_prefix_cache` up through
`KVCacheCoordinator`, `KVCacheManager`, `Scheduler`, `EngineCore`,
`CoreClient`, `LLMEngine`, `AsyncLLMEngine`, `LLM`, `EngineClient`
protocol, and the dev API router (`POST /reset_prefix_cache?preserve_running_requests=true`).

When `preserve_running_requests=True`:

1. The block-hash lookup tables (`cached_block_hash_to_block`,
   `cached_block_hashes_by_block`) are cleared, so new requests cannot hit
   any stale cached prefixes.
2. Every block (including those still held by running requests) has its
   hash metadata reset, which removes them from the logical prefix cache
   without touching the KV data or releasing them back to the free queue.
3. The `BlockPool`'s "all blocks must be free" guard is skipped, so the
   reset always succeeds regardless of load.

Running requests keep their allocated blocks and continue generating
normally; they already have their block tables fully established and do
not re-query the prefix cache mid-inference.

`reset_running_requests` and `preserve_running_requests` are mutually
exclusive. Passing both raises `ValueError` at the `Scheduler` layer to
prevent ambiguous intent.

### Wire API (dev cache router)

```
POST /reset_prefix_cache?preserve_running_requests=true
```

Returns `{"success": true}`. `reset_running_requests` and `preserve_running_requests`
are individually optional but may not both be `true`.

## Testing

- Verified all modified files parse cleanly with `ast.parse` (equivalent to
  `python3 -m compileall`).
- Call chain verified: `LLM.reset_prefix_cache` → `LLMEngine.reset_prefix_cache`
  → `EngineCore.reset_prefix_cache` → `Scheduler.reset_prefix_cache` →
  `KVCacheManager.reset_prefix_cache` → `KVCacheCoordinator.reset_prefix_cache`
  → `BlockPool.reset_prefix_cache(preserve_running_requests=...)`.
- Mutually-exclusive guard: `reset_running_requests=True` +
  `preserve_running_requests=True` → `ValueError` with descriptive message.
- No existing callers pass `preserve_running_requests` (defaults to `False`),
  so all existing behavior is preserved byte-for-byte.
- CI not run locally (GPU environment unavailable). Recommend running
  `tests/v1/core/prefix_cache/` and `tests/v1/core/test_scheduler.py` before
  merge.
