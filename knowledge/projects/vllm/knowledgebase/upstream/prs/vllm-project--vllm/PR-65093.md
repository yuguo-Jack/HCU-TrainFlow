# [Bugfix][Pooling] Fix scoring token limits with MistralTokenizer

[Upstream PR](https://github.com/vllm-project/vllm/pull/65093) · state: closed · merged: True

## Original PR description



## Overview

Fixes #65075. Bi-encoder scoring with a positive `max_tokens_per_query` or `max_tokens_per_doc` failed with a `TypeError` for models served with `MistralTokenizer`, because `truncate_text_to_tokens` always requested `return_offsets_mapping=True`. For `MistralTokenizer`, the cut point now comes from the decoded token prefix instead.

## Claims

- `max_tokens_per_query` and `max_tokens_per_doc` now work with `MistralTokenizer` in `LLM.score()`, `/score` and `/rerank`. Before, any positive limit failed (HTTP 400 online), even one that truncated nothing.
- A binding limit cuts the text to a prefix of the original with at most that many tokens. On every input tested, the cut lands at the same point as the HF `offset_mapping` path for the same model. A non-binding limit leaves the text unchanged.
- HF tokenizers are unaffected: they keep the existing `offset_mapping` code.

## Details

**Root cause.** `truncate_text_to_tokens`, added in #38827, calls `tokenizer(text, add_special_tokens=False, return_offsets_mapping=True)` before checking the length. vLLM's `MistralTokenizer.__call__` has a fixed signature without that argument, so every positive limit raised, even for text already within it. Forwarding the argument would not help, because transformers' `MistralCommonBackend` raises a `ValueError` for `return_offsets_mapping=True`. This went unnoticed because `test_max_tokens_per_doc.py` only covers HF tokenizers.

**Who is affected.** Pooling models that end up with `MistralTokenizer`: either `--tokenizer-mode mistral`, or the default `auto` on official Mistral repos, such as `--convert embed` on `mistralai/Mistral-7B-Instruct-v0.3`. Bi-encoder, late-interaction and Jina-ranking scoring all go through `_truncate_scoring_data`, so they share the fix. Cross-encoder scoring already rejects `MistralTokenizer`. Popular Mistral-based embedding models (e5-mistral, SFR-Embedding-Mistral, Linq-Embed-Mistral) ship HF tokenizers and were never affected.

**Fix.** For `MistralTokenizer`, the helper encodes the text, decodes the first `max_tokens` ids, and cuts the original text at the length of that decoded prefix. The existing loop then re-encodes and repeats until the text fits, as on the offsets path. The result is therefore always a prefix of the original text and never exceeds the limit. `skip_special_tokens=True` is required: without it, `MistralTokenizer.decode` returns raw SentencePiece pieces (`'▁line▁one<0x0A>line'`), whose length doesn't match the original text.

**Why `is_mistral_tokenizer`.** `MistralTokenizer.is_fast` is `True`, so an `is_fast` check (what `HfRenderer._can_produce_offsets` uses) would still send it down the offsets path. The renderer's private method also isn't reachable from this helper. The cross-encoder processor uses the same `is_mistral_tokenizer` check to reject Mistral.

**Cost.** A binding limit usually takes two encodes, one to find the cut and one to confirm it, plus one decode of at most `max_tokens` ids. The worst case on the strings above was four passes. Only `MistralTokenizer` takes the new branch.

**Tests.** The unit test covers both Mistral tokenizer formats, SentencePiece and Tekken. The end-to-end test, in `test_bi_encoder_offline.py`, goes through `LLM.score()` with `PoolingParams(extra_kwargs=...)`. It checks that the prompt token ids match scoring `"What is the"` against the unchanged document. It uses dummy weights and one layer, so it downloads only config and tokenizer files (about 620 KB). It sets `gpu_memory_utilization=0.3` so it fits next to the file's module-scoped e5 engine. Both tests run in the "Entrypoints Integration (Pooling)" CI step.

**Not a duplicate.** No open PR references #65075. Two open PRs touch `return_offsets_mapping`, #61363 and #62691, but both change only renderer and tokenizer code, not the scoring helper. #62691 adds `return_special_tokens_mask`, not offsets, to `MistralTokenizer.__call__`.

No docs change: this adds no options, and the docs don't say Mistral tokenizers are unsupported.
