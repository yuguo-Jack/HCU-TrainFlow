# [Bugfix][Benchmark] Fix probe latency and duration in bench serve

[Upstream PR](https://github.com/vllm-project/vllm/pull/60511) · state: closed · merged: True

## Original PR description



## Overview

Fixes two measurement errors in `vllm bench serve --probe-request-rate` (added in #49611). Probe latency included waiting for a client connection when `--max-concurrency` was saturated, and the benchmark duration included the probe loop's last sleep.

## Claims

- Probes use their own connection, so their latency no longer includes waiting for a slot in the main connection pool.
- `benchmark_duration` is computed before the probe task stops, as before #49611, so throughput no longer counts the trailing probe interval.
- Runs without probes are unchanged.

## Validation

One `vllm serve` instance on an RTX 3070 with `Qwen/Qwen3-0.6B`, vLLM at 8a26869bca. Only the bench client changes between columns.

| `--max-concurrency 32 --probe-request-rate 5`, 3 runs: probe p50 | 214–250 ms | 36–37 ms |
| same: probe p99 | 3.0–7.8 s | 0.24–0.29 s |
| same: probes completed | 18–19 | 86–88 |
| `--request-rate 4 --probe-request-rate 5`: probe p50 | 22.9 ms | 20.0 ms |
| `--max-concurrency 32`, no probes: duration, TTFT p50 | 22.14 s, 199.0 ms | 22.10 s, 199.8 ms |
| `--request-rate 4 --probe-request-rate 0.1`, 40 prompts, 2 runs: duration | 20.04 s | 11.35 s (11.35 s without probes) |

```bash
vllm serve Qwen/Qwen3-0.6B --max-num-seqs 64
vllm bench serve --backend openai --model Qwen/Qwen3-0.6B --dataset-name random \
  --random-input-len 512 --random-output-len 256 --ignore-eos --seed 42 \
  --num-prompts 200 --max-concurrency 32 --probe-request-rate 5
```

The runs served a local copy of the same model with `--served-model-name Qwen/Qwen3-0.6B`. Full logs are attached.

- `pytest tests/benchmarks/test_serve_cli.py` on GPU: 3 passed. `test_bench_serve_insecure` now also sends probes, which checks that the probe session honors `--insecure`.
- `pytest tests/benchmarks` on CPU: 187 passed on main and on this PR. The 6 tests that need the `vllm` CLI or model downloads fail the same way on both.
- `pre-commit run --files vllm/benchmarks/serve.py tests/benchmarks/test_serve_cli.py` and `mypy-3.12`: pass.

## Details

Probes skip the `--max-concurrency` semaphore but shared the main `aiohttp` session, whose connector has `limit=max_concurrency`. When the workload held every connection, a probe waited for one inside `session.post`, after the request function had started its timer, so the wait was reported as probe latency. Probes now run on a separate session from the same `make_session` helper, so both sessions use the same connector settings. One connection is enough because probes are sent one at a time.

#49611 also placed the probe shutdown before `benchmark_duration`, so the duration included up to `1 / probe_request_rate` of sleep plus any in-flight probe.

The first probe, and probes spaced further apart than the server's keep-alive, open a new connection. With several API server processes, all probes go to one process.

No open or closed issue or PR covers this. I searched for probe, probe-request-rate, probe latency, connection pool and TCPConnector, and checked the open PRs that touch `vllm/benchmarks/serve.py`.
