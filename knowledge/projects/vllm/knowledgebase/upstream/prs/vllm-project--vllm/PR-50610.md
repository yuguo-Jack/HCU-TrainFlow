# [Bugfix] Fix NVFP4 shape mismatch in flashinfer_scaled_fp4_mm

[Upstream PR](https://github.com/vllm-project/vllm/pull/50610) · state: open · merged: False

## Original PR description

Fixes: #50577

## Purpose

Some NVFP4 checkpoints (e.g. `AxionML/Gemma-4-12B-NVFP4`) store weights in the
standard PyTorch layout `(in_features // 2, out_features)` rather than the
vLLM-expected `(out_features, in_features // 2)`. The NVFP4 loaders previously
did not normalize this orientation, so `flashinfer_scaled_fp4_mm` hit
`assert a.shape[1] == b.shape[1]` during `profile_run()` on SM120+ hardware
(e.g. RTX 5060 Ti).

## Changes

- Wrap the NVFP4 weight and per-block scale loaders so genuinely misoriented
  checkpoints are transposed before TP sharding and shape validation. The guard
  uses the expected checkpoint input width (global, not the TP-local partition),
  so correctly oriented fused gate/up and q/k/v shards are left untouched.
- Preserve the global `input_size` in `Shapes` so row-parallel layers at TP > 1
  detect transposed checkpoints correctly.
- Add CPU unit tests for the transpose wrapper (fused shards, misoriented
  weights/scales, TP > 1) and the row-parallel global-input case.
- Add tests confirming NVFP4 `exclude_modules` written in checkpoint naming map
  onto the vLLM module paths for both Gemma 4 model classes.

Re-read the current loader changes. I still see two correctness problems.

`_wrap_weight_loader_for_transpose` treats any dimension-zero mismatch as a transposed checkpoint weight, but these mismatches are normal before fused and tensor-parallel loaders shard. Gemma gate and up tensors load separately into `gate_up_proj`: a valid `[15360, 1920]` gate weight is compared with the fused `[30720, 1920]` parameter, gets transposed to `[1920, 15360]`, then reaches the `MergedColumnParallelLinear` loader in the wrong orientation. The same condition affects q/k/v fusion, two-dimensional weight scales, and global-to-local TP weights. Detection needs the expected checkpoint shape, not a raw loaded-versus-parameter dimension comparison.

Stripping `model.` before the model-specific mapper also breaks Inkling exclusions. `model.llm...` becomes `llm...`, so the mapper no longer translates it to `model.layers...`.

I do not think this is safe to approve until both paths are handled.

- Mahnoor-Zaffar · comment · 2026-08-02T16:37:53Z · [source](https://github.com/vllm-project/vllm/pull/50610#issuecomment-5159287579)


Good catch on both points. I dug into this more and you're right — the late transpose was a dead end.

**The timing issue**: The transpose in `process_weights_after_loading` was unreachable for transposed checkpoints because `_ColumnvLLMParameter.load_column_parallel_weight` narrows along dim 0 and asserts shape match *before* we ever get there. I moved the orientation normalization into a weight_loader wrapper so the transpose happens before TP sharding and shape validation. The late transpose is gone.

**The parameter name issue**: After inspecting the actual `AxionML/Gemma-4-12B-NVFP4` checkpoint, I found the real problem is in `exclude_modules`. The checkpoint lists patterns like `model.language_model.layers.0.self_attn*`, but by the time vLLM checks them in `is_layer_excluded`, the prefix has already been remapped to `language_model.model.layers.0.self_attn.qkv_proj`. The `fnmatch` never matches, so all the self_attn layers that should be excluded from quantization end up getting the NVFP4 treatment — and their quantized weights don't exist on disk.

Added a `_translate_exclude_modules` step in `_from_config` that rewrites checkpoint patterns to vLLM naming before they're stored. So `model.language_model.layers.0.self_attn*` becomes `language_model.model.layers.0.self_attn*` and the matching actually works.

I should note — I still can't fully verify this end-to-end without a GPU + the actual checkpoint, since the safetensors are ~10GB each and won't download on this machine. But the logic checks out against the code paths. Happy to adjust if you see something off.
