# fix(llama): use weightless RMSNorm for FlashNorm-folded checkpoints (has_weight=False)

[Upstream PR](https://github.com/vllm-project/vllm/pull/41431) · state: open · merged: False

## Original PR description

## Summary

Adds `has_weight=False` plumbing to the Llama model so that FlashNorm-folded HuggingFace checkpoints load cleanly. Three `RMSNorm(...)` call sites in `vllm/model_executor/models/llama.py` get one extra keyword argument each, gated by a `flashnorm_folded` flag on the model config, plus a loader-side rule to ignore the all-ones norm tensors that FlashNorm-folded checkpoints still carry for HF compatibility.

**Status update (2026-07-12):** the kernel-side half of this work is now merged. #44109 (fixes the companion issue #41430) made `weight` optional in the `rms_norm` / `fused_add_rms_norm` CUDA and CPU kernels, so `has_weight=False` now skips the per-channel multiply on the GPU path instead of substituting an all-ones tensor. That makes this PR the remaining piece: on current `main`, FlashNorm-folded Llama checkpoints still cannot be loaded with weightless norms, because `llama.py` always constructs `RMSNorm` with the default `has_weight=True`. With this PR, the [`weightless-rmsnorm` collection on HuggingFace](https://huggingface.co/models?other=weightless-rmsnorm) (this PR covers the Llama path) both loads and reaches the merged weightless kernels.

Rebased onto current `main` (2026-07-12). `LlamaModel.load_weights` was refactored upstream to use `AutoWeightsLoader`, so the loader-side skip is now expressed as `ignore_unexpected_suffixes=["norm.weight"]`, passed only when the config has `flashnorm_folded=True` (details below).

## Problem

Loading `open-machine/Llama-3.2-1B-FlashNorm` (or any other FlashNorm-folded Llama checkpoint with `"flashnorm_folded": true` in `config.json`) in stock vLLM fails at engine init:

```python
from vllm import LLM
LLM(model='open-machine/Llama-3.2-1B-FlashNorm', dtype='bfloat16', enforce_eager=True)
# RuntimeError: Engine core initialization failed.
```

Root cause: `vllm/model_executor/models/llama.py` always calls `RMSNorm(...)` with the default `has_weight=True`, so the loader expects every per-layer `*_layernorm.weight` and `model.norm.weight` tensor, and the norm layers always run the weighted path. FlashNorm-folded checkpoints either (a) keep those weights as all-ones for HF compatibility or (b) omit them; neither layout gets the weightless treatment today.

## Background: FlashNorm

[FlashNorm](https://arxiv.org/abs/2407.09577) (Graef et al., 2024) folds the per-channel RMSNorm weight into the next linear, leaving an RMSNorm whose weight is mathematically all ones. A runtime that recognizes this can skip the per-channel multiply and recover an end-to-end speedup.

vLLM's `RMSNorm` class has supported `has_weight=False` since #10739, and since #44109 the CUDA/CPU kernels take `weight=None` and skip the multiply. What is missing is a model whose loader actually sets `has_weight=False` from checkpoint metadata; this PR adds that for Llama. (#40117 proposed the same pattern for Gemma-4 KV-shared `k_norm` but was closed without merging.)

## Proposed change

Three RMSNorm call sites in `vllm/model_executor/models/llama.py` get one keyword argument each, gated by a `flashnorm_folded` flag read from the model's config:

```python
flashnorm_folded = getattr(config, "flashnorm_folded", False)

# In LlamaDecoderLayer.__init__:
self.input_layernorm = RMSNorm(
    config.hidden_size, eps=config.rms_norm_eps,
    has_weight=not flashnorm_folded,
)
self.post_attention_layernorm = RMSNorm(
    config.hidden_size, eps=config.rms_norm_eps,
    has_weight=not flashnorm_folded,
)

# In LlamaModel.__init__:
self.norm = RMSNorm(
    config.hidden_size, eps=config.rms_norm_eps,
    has_weight=not flashnorm_folded,
)
```

Two supporting changes:

1. `LlamaModel.load_weights` (now `AutoWeightsLoader`-based upstream) passes `ignore_unexpected_suffixes=["norm.weight"]` when `flashnorm_folded=True`. FlashNorm-folded HF checkpoints still carry the norm weights as all-ones tensors for HF compatibility; with `has_weight=False` those norms register no weight Parameter, so the incoming tensors are unexpected and would otherwise raise. The rule only applies to unexpected tensors and only under the config flag, so it cannot mask unrelated missing-tensor bugs.
2. `RMSNorm.__init__` registers the all-ones weight as a non-persistent buffer (instead of a plain Tensor attribute) when `has_weight=False`, so it moves with the module under `.to(device)` and stays out of `state_dict` (raised by gemini-code-assist review).

The `flashnorm_folded` flag is read from the HF config via `getattr(...)` with a `False` default, so existing non-flashified Llama checkpoints are unaffected. No schema changes anywhere.

## Empirical verification

Measured before #44109 landed (runtime equivalent of this patch, Colab A100, vllm 0.9.2, bf16, 256-token greedy decode, 20 trials, `enforce_eager=True`, `tensor_parallel_size=1`):

| Model | tok/s |
|---|---|
| `unsloth/Llama-3.2-1B-Instruct` (stock vLLM, no patches) | 94.09 |
| `open-machine/Llama-3.2-1B-FlashNorm` (with `has_weight=False` set on Llama RMSNorms) | 94.05 |

At the time this confirmed correctness (the model loads, runs, and matches the unfolded baseline) with no speedup, because the kernels still ran the weighted path on an all-ones tensor. With #44109 now merged, `has_weight=False` reaches kernels that skip the multiply, so a speedup is expected; for scale, the equivalent weight-null branch in HuggingFace Transformers (`F.rms_norm(weight=None)`) gave **+12.77% end-to-end** on the same model and hardware. Happy to re-run the benchmark on top of current `main` if reviewers want fresh numbers in-thread.

## Other architectures

The same one-line pattern applies to `mistral.py`, `qwen2.py`, `qwen3.py`, `phi3.py`, and any other RMSNorm-based architecture whose checkpoint can be flashified. Happy to follow up with separate small PRs for those if there is interest; this PR is scoped to Llama for review focus.
