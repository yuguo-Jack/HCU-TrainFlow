# [ROCm][Perf] Use the Triton fp32 router GEMM up to 128 tokens for small routers on gfx950

[Upstream PR](https://github.com/vllm-project/vllm/pull/65480) · state: open · merged: False

## Original PR description


**AI assistance:** this change was developed with Claude Code (Claude Sonnet 5.5); the tests and benchmarks below were run on MI355X (gfx950).

## Purpose

On gfx950 the fp32 router logits are computed by `_rocm_fp32_router_gemm_kernel` for `num_tokens <= 32`
(`_MAX_TOKENS`, also the cap in `fp32_router_gemm_dispatch_impl` and `rocm_bf16x3_router_gemm_dispatch_impl`).
Above that the dispatchers fall back to `F.linear(x.float(), w)`, i.e. three kernels per MoE layer:
a bf16->fp32 cast, a hipBLASLt split-K GEMM and its split-K reduce.

MiniMax-M3.1 decode with speculative decoding sends 8 query tokens per request, so 5 or more concurrent
requests (40..192 tokens/step) fall off the Triton path on every MoE layer (57 layers).
Profiled at N=5 (40 tokens), rank 0, median of 60 decode steps:

| router logits kernels, per layer | before | after |
|---|---|---|
| bf16->fp32 cast | 5.3 us | - |
| hipBLASLt GEMM (`Cijk_..._MT32x32x32`) | 7.1 us | - |
| hipBLASLt split-K reduce (`PostGSU16`) | 4.9 us | - |
| `_rocm_fp32_router_gemm_kernel` | - | 7.7 us |
| **total** | **17.3 us** | **7.7 us** |

The router sits at the head of the routed-expert chain (topk -> sort -> GEMM1 -> GEMM2) that is the critical path of
a decode layer, so the 9.6 us/layer (0.55 ms/step) shows up in the step time.

This PR lets routers with at most `6144 x 128` weight elements (6144x128, 3072x256, 4096x192, 2880x128, 5120x16, ...)
use the Triton kernel up to 128 tokens and adds a launch config for 33..128 tokens. Wider routers
(2560x512, 7168x384, 8192x256, 4096x352, ...) keep the 32-token cap because their crossover with `F.linear` is shape
dependent (measured below), so no shape that was not measured changes behaviour.

### Why this is not a duplicate

`gh pr list --repo vllm-project/vllm --state open --search "rocm_fp32_router_gemm"` /
`"router gemm gfx950 tokens"` / `"fp32_router_gemm_dispatch"`: the only related open PR is #64271
(retunes the *launch table* for 256 < experts <= 512 at <= 32 tokens, adds `num_stages`). It does not touch the
token limit or the 33..128 range; the two touch `_launch_config` and will need a trivial rebase against each other.
#63243 (gfx1250) and #57626 (fp32 weights auto-enable) are unrelated.

  --reasoning-parser minimax_m3 --tool-call-parser minimax_m3 --enable-auto-tool-choice --trust-remote-code
# client: N concurrent streaming completions with random 150K-token prompts (N = 1 2 3 4 5 6 8 12 16), 900 output tokens each; the reported number is the p50 gap between streamed chunks once all N streams are decoding

TTFT is dominated by CPU launch time and varies by 10-14% between launches of the *same* configuration on this host, so no TTFT
effect is claimed (neither gain nor loss). By construction nothing changes above 128 tokens, and the Triton launch costs less CPU
than the cast + `F.linear` path it replaces below that (19.7 us vs 30-34 us per call measured in eager).

### Correctness

* New and existing router GEMM tests: `pytest tests/kernels/test_rocm_fp32_router_gemm.py tests/kernels/test_gate_linear_rocm_dispatch.py` on MI355X: **1014 passed, 0 failed** (6m17s).
  `pre-commit run --files ...` (ruff check/format, typos, mypy, SPDX, check-test-tethering) passes.
* The kernel output is checked against `F.linear` in fp32 with the file's existing tolerance (`atol=5e-4`),
  and the top-k expert set is checked against `F.linear` (ties within 1e-3).
* End-to-end quality on the server with this change plus the unrelated MoE tuned rows from the ROCm/aiter PR: GSM8K (chat, temperature 0, 250 questions)
  0.920 vs 0.896 for the unmodified server (+-1.9% s.e.); the sanity prompt "What is 17*23? Answer briefly." -> "17*23 = 391." in both. Token-level logprob
  comparisons between launches are not informative on this model (speculative decoding with synthetic acceptance makes greedy outputs non-reproducible even for identical configs).

### Limitations / not verified

* Only MiniMax-M3.1 (6144x128) was run end to end; the other shapes are covered by the microbenchmark and unit tests.
* The gain is at most ~0.5 ms/step on a 14 ms step (3-3.4%); at >= 12 requests (96+ tokens) the Triton kernel's advantage over
  hipBLASLt shrinks to a few us and the effect is below the noise.
* No change for MI300 (gfx942) / CUDA paths.
