# [Benchmark] Add PCP support to vllm bench forward

[Upstream PR](https://github.com/vllm-project/vllm/pull/63613) · state: closed · merged: True

## Original PR description

## Overview

Add prefill context parallelism (PCP) support to `vllm bench forward`, including PCP with expert parallelism and decode context parallelism.

## Claims

- Validate requested batch shapes against the global batch and inject the correct token slices into each rank's split or replicated request rows.
- Account for PCP workers in balanced MoE routing fixtures and report local batch sizes/order in per-rank results.
- Document PCP usage and the distinction between full-forward graph timing and serving latency.

## Validation

- Seven CPU tests passed in `tests/benchmarks/test_forward_cli.py` (all tests except the existing single-GPU model test). The new two-rank parameterized regression checks split prefill slices with a continued prefix, replicated decode inputs, and untouched padding. This file runs in the existing Benchmarks CLI Buildkite job.
- All pre-commit hooks passed on the four changed files.
- Before the change, the four-GPU CLI reproducer fails in `_check_batch` with `AssertionError: ['bench-0', 'bench-0']`. With the change, uneven prefill, mixed prefill/decode, and decode cases complete.
- On four GB200 GPUs, GLM-5.2 NVFP4 with dummy weights was exercised with PCP4/EP4, PCP2/TP2/EP4, and PCP2/TP2/DCP2/EP4. DCP used `ag_rs`, `FLASHMLA_SPARSE`, and `fp8_ds_mla`. Real and balanced synthetic routing were exercised; full-model timing was compared with `vllm serve`.
- Real `nvidia/GLM-5.3-NVFP4` weights were also tested with PCP4/EP4, normal routing, and both TRTLLM and NVFP4 MegaMoE backends:

| MoE backend | Prompt tokens | Forward graph (ms) | Serving TTFT (ms) |
| --- | ---: | ---: | ---: |
| `flashinfer_trtllm` | 1,024 | 50.708 | 94.067 |
| `flashinfer_trtllm` | 8,192 | 163.816 | 174.005 |
| `flashinfer_moe_ep_cutedsl` | 1,024 | 58.483 | 95.870 |
| `flashinfer_moe_ep_cutedsl` | 8,192 | 153.638 | 160.496 |

These are functionality/timing checks, not speedup claims for the patch. Forward timing used 10 replays × 3 samples; MegaMoE sample spread was 0.14% / 0.49% for 1K / 8K. TTFT is the median of 10 serial requests after four warmups. Both paths used identical README-derived prompt IDs, disabled FlashInfer autotuning, and real routing; serving used `FULL_AND_PIECEWISE`, while the benchmark captures the full forward. Kernel traces confirmed the selected MoE implementations.

Outputs were finite. The real-weight 1K graph/eager comparison was exact; the 8K case showed variability even between eager repeats, so these results do **not** establish 8K numerical parity or task-level accuracy. No inference/model implementation is changed.

## Details

PCP can represent one global request with two disjoint local rows. Previously the benchmark required unique local request IDs and copied the entire query for every row. It now checks the global batch contract and derives each local token slice from its computed-token offset and scheduled-token count. Balanced routing includes PCP in the EP world size and reserves capacity for gathered PCP rows without EP.

Duplicate-work checks found no open PCP/forward benchmark PR or matching issue. #62300 addresses CUPTI profiling and is separate from this change. No issue number was supplied.
