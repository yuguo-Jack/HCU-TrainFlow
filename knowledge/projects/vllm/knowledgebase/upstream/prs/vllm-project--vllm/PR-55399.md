# [Rust Frontend] Report engine errors on completion streams that request logprobs

[Upstream PR](https://github.com/vllm-project/vllm/pull/55399) · state: open · merged: False

## Original PR description

## Purpose

Since #62872 the Rust frontend answers an engine `validation_error` with 400 and a retryable engine error with 503. A `/v1/completions` stream that requests `logprobs` still hides both. When the engine finishes the request with an error, the stream looks for generated logprobs first and sends `completion stream requested logprobs but generation returned none` as an internal server error in place of the engine's error. Since #64220 an echoed stream reads its prompt logprobs when it starts, so with or without generation it sends `echoed completion prompt requested logprobs but generation returned none` instead.

This PR checks the terminal finish reason before it asks for logprobs, so the stream reports the engine's error. An echoed stream holds a missing prompt logprobs error until the request finishes, reports the engine's error when there is one, and still fails as before when the request finishes normally without prompt logprobs.

It also stops the engine client from logging a validation error at error level as an engine failure, as it already does for retryable errors, and drops "internal" from the `FinishReason::Error` doc, since the error can now be the client's.

An earlier version of this PR added the 400 mapping itself, which #62872 has since landed, so this version keeps only the stream fix. It also turned an untyped engine error on non streaming `/inference/v1/generate` into a 500; #62872 keeps that as finish reason `error`, like Python, and this version leaves it so.

AI assistance was used for this change. The submitter reviewed every changed line and ran the tests below.

## Test Plan

```
cd rust
cargo fmt --all --check

cargo test --no-fail-fast -p vllm-server -p vllm-llm -p vllm-engine-core-client
```

`engine_request_errors_map_to_http_status` gains three completion streams that request logprobs, a plain one, an echoed one and a prompt only one, so both the retryable and the validation error run through them. `completion_chunk_stream_rejects_missing_prompt_logprobs` covers a prompt only stream that finishes normally without prompt logprobs.

## Test Result

| Completion stream with `logprobs` that the engine ends with an error | main | this PR |
| --- | --- | --- |
| plain stream | `InternalServerError`: `completion stream requested logprobs but generation returned none` | the engine's error: 503 for a retryable one, 400 for a validation error, with its message |
| echoed stream, with or without generation | `InternalServerError`: `echoed completion prompt requested logprobs but generation returned none` | the engine's error, as above |

On main with only the new test cases, the route test fails on the first of them:

```
/v1/completions {"model":"Qwen/Qwen1.5-0.5B-Chat","prompt":"hello","logprobs":1,"stream":true}: data: {"error":{"message":"completion stream requested logprobs but generation returned none","type":"InternalServerError","param":null,"code":500}}
```

With the change, `cargo test` over the three crates passes 743 of 743, and `cargo clippy ... -D warnings` and `cargo fmt --all --check` are clean.
