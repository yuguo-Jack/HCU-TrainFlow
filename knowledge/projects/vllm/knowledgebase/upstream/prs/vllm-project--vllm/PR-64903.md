# [Bugfix][MoE] Avoid double router weighting in TRTLLM FP8 experts

[Upstream PR](https://github.com/vllm-project/vllm/pull/64903) · state: open · merged: False

## Original PR description

## Overview

Avoid double router weighting in TRTLLM modular block-FP8/MXFP8 experts when `apply_router_weight_on_input=True`, as used by Llama4 top-1 routing. Use unit output weights after prepare has weighted the input.

## Claims

- Fix input-weighted modular FP8 routing; preserve ordinary output weighting and monolithic experts.
- Add four nonzero block-FP8/MXFP8 regressions to the existing FlashInfer suite and document the argument, default and top-k restriction.

## Validation

B300, Torch 2.14.0+cu130 / FlashInfer 0.7.2.post1, baseline/candidate source-bound module overlays:

| Check | Before | After |
| --- | --- | --- |
| Selected existing project suite, block-FP8 + MXFP8 | 8 passed, **4 failed**, 2 skipped | **12 passed**, same 2 skipped |
| Actual LLM, MoE-only block-FP8, DP2/EP2: routed-layer checks | 0/6 passed; relative L2 0.403–0.474 | 6/6 passed; relative L2 0.0588–0.0614 |

Reproduce the native selection on both arms using the PR test file, changing only the expert implementation:

```bash
.venv/bin/python -m pytest -v -s \
  tests/kernels/moe/test_flashinfer.py::test_trtllm_fp8_input_router_weight_applied_once \
  tests/kernels/moe/test_flashinfer.py::test_trtllm_fp8_block_moe_deferred_finalize \
  tests/kernels/moe/test_flashinfer.py::test_trtllm_mxfp8_minimax2_routing_applies_routed_scale
```

All four new input-weighting checks fail before repair and pass after with exact equality. Existing deferred-finalize/layout and Minimax2 route controls pass; the two existing unsupported MXFP8 transposed-scale cases remain skipped. The `kernels-b200` Buildkite step already selects this test file and implementation.

For the supplementary LLM check, both arms load `ngxson/TEST-Tiny-Llama4@24071fa7c15a663c545dff8fdfc58b500db05be9` using `quantization="online"`, `quantization_config={"moe": {"weight": "fp8_per_block_static"}}`, `moe_backend="flashinfer_trtllm"`, eager execution and `all2all_backend="flashinfer_nvlink_one_sided"`. Both ranks verify actual modular experts/prepare, nonzero E4M3 weights and six finite one-token responses. Passive layer outputs are checked against independent Torch expert math using the checkpoint weights round-tripped through native block-FP8 weight quantization. The predeclared relative-L2 limit is 0.1; activation/intermediate FP8 rounding is not emulated. Each capture is judged against its own input.

This is a routed-layer correctness evaluation, **not trained accuracy, MXFP8 model, graph or performance evidence**. The checkpoint's attention-temperature integer4 was explicitly normalized to `true` for Transformers compatibility. Validation used official0f6b precompiled artifacts with matching expert/helpers and audited online-path source, not a full current-main rebuild. Official CI remains unverified. Scoped Linux pre-commit passed, including mypy, Markdown and CI tethering, without modifying the reviewed files.

## Details

Prepare applies the routing score before quantization, but the expert forwarded it again to fused output finalization. Replacing only those output weights with ones preserves the input-weighted computation without mutating upstream routing tensors. No CUDA/C++ kernel or tolerance changes.

This follows #63700 (BF16) and #64047 (NVFP4), touching a different expert class. Open-PR checks found no same FP8 fix: #47611 handles older FlashInfer signatures; #62019/#63024 concern LoRA. The three changed files remain unchanged upstream through main `0c63ce9f0e0`; an offline merge-tree check is clean. The only drift in the audited FP8 selector/helpers is Humming-specific weight-scale rebinding; the TRTLLM route is unchanged. Earlier native results are retained, not presented as a fresh full-main run.

AI assistance was used. The human submitter reviewed and understood every changed line.
