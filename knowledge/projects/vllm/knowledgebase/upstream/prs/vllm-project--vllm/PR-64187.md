# [Perf][Model Loader] Make the EP weight filter EPLB-aware

[Upstream PR](https://github.com/vllm-project/vllm/pull/64187) · state: open · merged: False

## Original PR description

## Overview

Let `--enable-ep-weight-filter` work with `--enable-eplb`. Since #37322 the loader turns the filter off whenever EPLB is enabled, so every rank of an EPLB deployment reads every expert weight. This derives the experts each rank needs from EPLB's initial placement instead. Follow-up to #37136, #37351 and #37322.

## Claims

- With EPLB, each rank reads only the experts its physical slots hold in the initial placement, including redundant replicas. DeepSeek-R1-0528-NVFP4-v2 with DEP8 and 32 redundant experts: **105.2 GiB per rank instead of 384.9 GiB** (the plain EP filter without EPLB reads 100.1 GiB).
- Outputs match EPLB without the filter within run-to-run noise, across 32-33 rebalancing steps: GSM8K 0.9636 vs 0.9621 (A/A 0.9629), and the same final answer on 97.4% of questions, equal to the A/A agreement. Weight loading on a warm page cache: 43.6 s to 39.8 s (A/A 43.9 s).
- The comparison is sensitive: a negative control that applies the plain EP filter under EPLB (main without #37322's guard) falls far outside the run-to-run noise.
- Falls back to loading every expert, as on main, for elastic EP and whenever the model's MoE layout (`num_logical_experts`, `num_physical_experts`) differs from the config, e.g. for MoE models that don't implement `MixtureOfExperts`.

**Negative control** (separate job on the same kind of node, smoke only): mounting the nightly loader with only #37322's EPLB guard removed, i.e. the plain EP partition under EPLB (`loading 32/256 experts`), leaves 144 of the 288 physical slots without their weights. Compared with main in the same job, greedy outputs are identical for 0/4 prompts and prompt-logprob top-1 agreement drops to 75.3% / 80.4% / 31.5%, far outside the A/A noise above (95.9% / 94.7% / 77.8%). Its short greedy answers can still be correct, so the logprob comparison, not answer accuracy alone, is what separates a wrong expert set from run-to-run noise.

Load times were measured with the checkpoint already in the page cache (NFS, where vLLM also auto-prefetches), the same condition as #37136's numbers; the saving comes from not materializing non-local expert tensors. The 8 ranks of one node share the page cache and together need every expert, so reads from storage don't shrink on a single node; the per-rank saving matters more where ranks read independently, e.g. EP across nodes or a page cache that cannot hold the checkpoint.

## Details

- **Root cause.** EPLB allocates N + R physical slots per MoE layer and splits them linearly across EP ranks. Slot p initially holds logical expert `initial_map[p]` from `EplbState.build_initial_global_physical_to_logical_map` (identity, then `i % N` for the redundant slots), so a rank's redundant slots replicate experts from other ranks' default partitions. The plain filter skips those, which left the replicas uninitialized; #37322 therefore disabled the filter under EPLB.
- **Fix.** The filter keeps `{initial_map[p] for p in this rank's physical slots}`, built from the same map `RoutedExperts.build_expert_params_mapping` uses to route checkpoint tensors to slots, so the two cannot disagree. Rebalancing moves weights GPU-to-GPU and never re-reads the checkpoint, so loading only has to satisfy the initial placement. Custom initial maps (#49572, open) are applied after loading through `rearrange_expert_weights_inplace`, so they stay compatible.
- **Linear placement.** `determine_expert_placement_strategy` refuses round-robin when EPLB is enabled, so the filter always splits physical slots linearly; a test pins this.
- **Layout check.** The expert set comes from the config, so it is used only when the model reports the matching `MixtureOfExperts` layout (resolved with `get_mixture_of_experts_model`, which unwraps VLMs). This matters because `--enable-eplb` is accepted for MoE models that don't implement `MixtureOfExperts`: EPLB is simply not registered for them, and they allocate only N slots, so the EPLB set would skip experts they need.
- **Loaders.** Every loader that consumes `local_expert_ids` uses the new set under EPLB: the safetensors iterator (all load strategies; auto-prefetch on NFS still reads whole files, but tensors are skipped per name) and InstantTensor (#61167), which was not validated end to end. The multi-threaded and fastsafetensors loaders don't filter at all (#48891 addresses the former).
- **Test coverage.** The fallback for a mismatched layout has no automated test: exercising it needs a MoE model whose layout disagrees with its config, and the guard is a single comparison.
- **Unchanged.** Elastic EP keeps loading every expert (padded capacity, placement evolves at runtime). Scale and metadata tensors are still never filtered, so #37322's NVFP4 fix is untouched.
- **Not a duplicate.** Open PRs and issues searched for "EP weight filter EPLB", "ep_weight_filter", "enable-ep-weight-filter", "37322 in:body" and "weight filter redundant experts" found nothing equivalent. Related but orthogonal: #48891 (apply the filter in the multithreaded safetensors loader) and #63075 (EPLB expert-weight regions in `RoutedExperts`).
- **Limitations.** Not validated with speculative decoding; DeepSeek MTP's MoE follows the same EPLB layout and passes the check, but the run above has no drafter.
