# [ROCm][Perf] W4A16: dequantize then matmul for large prefill on gfx1151

[Upstream PR](https://github.com/vllm-project/vllm/pull/61193) · state: open · merged: False

## Original PR description

## Overview

On gfx1151, `RDNAHybridW4A16LinearKernel` prefill uses a fused Triton dequant GEMM whose throughput falls from about 24 to 10 TFLOP/s as M grows to 8192. From M=4096 rows, this dequantizes the weight with a small Triton kernel and runs one dense matmul instead. Related: #60710 and #60644 (also speed up this prefill path, see below).

## Claims

- Large prefill on gfx1151 is faster: GEMM throughput x1.4 to x1.7 at M=4096 and x3.0 to x3.3 at M=8192 on the Qwen3-8B qkv/o/gate_up shapes (bf16 and fp16).
- End to end on a 27B hybrid model, prefill of an 8k-token state 49.0 → 32.7 s and 16k 132 → 95.4 s. No change below M=4096.
- No extra weight memory and no accuracy change.
- Other GPUs are unchanged: the path is gated on gfx1151.

## Validation

All on gfx1151 (Radeon 8060S), nightly `0.31.1rc1.dev273`, torch 2.13, Triton 3.8.

**Kernel**, `benchmarks/kernels/benchmark_rdna_hybrid_w4a16_gemm.py --models RedHatAI/Qwen3-8B-quantized.w4a16 --dtype {bfloat16,float16}`, TFLOP/s of `_rdna_hybrid_w4a16_apply_impl`, main → PR (symmetric weights; the asymmetric provider matches within 2%):

| M | qkv (N=6144, K=4096) | o (4096, 4096) | gate_up (24576, 4096) | down (4096, 12288) |
|---|---|---|---|---|
| 4096 (bf16) | 17.7 → 29.9 | 19.4 → 27.7 | 21.4 → 33.4 | 23.5 → 23.6 |
| 8192 (bf16) | 10.1 → 31.7 | 10.0 → 30.1 | 10.6 → 35.0 | 23.6 → 24.6 |
| 4096 (fp16) | 18.5 → 29.5 | 20.2 → 27.6 | 21.7 → 33.1 | 23.5 → 23.5 |
| 8192 (fp16) | 10.0 → 31.1 | 10.0 → 29.7 | 10.4 → 34.2 | 22.9 → 24.8 |

Below M=4096 the PR does not run (same code as main). I picked 4096 because a lower threshold loses on the `down` shape (K=12288): with the switch at 1024, the sweep gave 0.80 (bf16) and 0.75 (fp16) of main at M=1024, and 0.86 in fp16 at M=2048, while the other shapes gained 1.0 to 1.3 there. From 4096 every shape is at least on par.

**End to end**, Qwen3.8-27B (compressed-tensors 4-bit, asymmetric, group 128, Qwen3_5 hybrid, MTP 3), `/v1/systemone` reads with a state of the given size, same seed, otherwise identical flags (`--max-num-scheduled-tokens 16384`), p50 latency for 4 questions:

| state | main | this PR |
|---|---|---|
| 2048 tokens | 8.1 s | 8.1 s |
| 8192 tokens | 49.0 s | 32.7 s |
| 16384 tokens | 132.0 s | 95.4 s |

Throughput with 8 concurrent requests of 8 questions: 0.143 → 0.200 req/s. Label accuracy on 120 synthetic tickets is identical (0.90 / 0.67 / 1.00). A torch profile of a 16k read with this kernel shows the dequant kernel at 0.8% of GPU time and the GEMMs at about 41 TFLOP/s (model FLOPs over GEMM time).

**Tests**:

```bash
pytest tests/kernels/quantization/test_rdna_hybrid_w4a16.py -k "not process_weights"
```

136 passed. The 8 deselected tests need the `dist_init` fixture from `tests/conftest.py`, which my setup does not load; they exercise `process_weights_after_loading`, which this PR does not touch. New tests: dequantized weight vs an FP32 reference (fp16/bf16, all group sizes, with and without zero points, K=1024 in 16-bit is the 2 KiB stride that gets padded), the dispatch boundaries (below M, at M on gfx1151, at M elsewhere), and the apply op at M=4096 against the reference. I did not run GSM8K.

## Details

- `dequant_w4a16` dequantizes one [64, 128] tile per program (BLOCK_K <= group size) with the same arithmetic as the fused kernel, into a transient buffer in the scales dtype. Its rows are padded off the 2 KiB stride cliff, as `_pad_activation_rows` does for activations; `torch.matmul` takes the strided view.
- Memory: the buffer lives for one call and is freed after it, at most N x K x 2 bytes (356 MB for the largest layer of the 27B). It is included in the memory profiling pass, which runs a full `max_num_batched_tokens` forward.
- Difference with #60710 (opt-in dense weight cache, M >= 256): this keeps the 4-bit weights and pays the dequantization on each call, so it costs no memory, but it only wins from M=4096 on the shapes measured here. The two are not exclusive. #60644 makes the fused kernel's dequant cheaper (fp16 only) and also touches `rdna_hybrid_w4a16.py`; whichever lands second needs a small rebase.
- Limits: measured on gfx1151 only, with the shapes above plus the 27B ones. The threshold is a constant; other RDNA parts keep the fused kernel.
