# [Perf][MoE] Enable SM90 block-FP8 MegaMoE via FlashInfer MoE-EP

[Upstream PR](https://github.com/vllm-project/vllm/pull/62603) · state: open · merged: False

## Original PR description



## Overview

vLLM has no MegaMoE that runs on Hopper today:

- the DeepGEMM MegaMoE (`deep_gemm_mega_moe`) requires SM100;
- the FlashInfer MoE-EP megakernels (`flashinfer_moe_ep_cutedsl`, `flashinfer_moe_ep_mega_deep_gemm`) require SM100

This PR runs block-FP8 MoE checkpoints on Hopper with FlashInfer's SM90 FP8 MegaMoE, which ships in FlashInfer 0.7.2. The kernel fuses dispatch, both expert GEMMs and combine. It goes through the existing `--moe-backend flashinfer_moe_ep_cutedsl` path with no model code, so any block-FP8 MoE can use it.

Related:
- #58540: the same kernel, but for DeepSeek-V4 FP4 checkpoints converted to FP8, and on files that #54049 removed.
- #62073: Beam on SM100. It contains the same idle-rank change as this PR.
- #60895: DeepGEMM MegaMoE for GLM-5.3-Flash, SM100 only.
- #53527: DeepSeek-V4 through a DeepGEMM fork.

## Claims

- GLM-5.3-Flash decode on 8x H200 (DP8/EP8, 128K/512, MTP3): +11% to +18% output throughput and -6% to -14% TPOT p50, at concurrency 8 to 192.
- GLM-5.3-Flash prefill on 4x H200 (TP2/DP2/EP4, MTP3, ISL 2048 / OSL 1): +23% saturated throughput, and TTFT p50 -14% to -54% at 15 to 21 req/s.
- One MoE layer at EP8: -7% at 8 tokens/rank, up to -48% at 8192 tokens/rank.
- GSM8K is unchanged in both configurations.
- The backend is opt-in. Default backends do not change.

## Details

- **Kernel.**
  - FlashInfer `Sm90PullFp8MegaMoeConfig`, with FP32 128x128 weight scales and a SwiGLU clamp.
  - FlashInfer's push-style SM90 backend has no SwiGLU clamp, so it cannot serve `swiglu_limit` models.
- **Weights.**
  - The kernel wants FC1 rows interleaved as `[pair, {gate, up}, 8]` under one 128x128 scale. Each scale block therefore covers rows from two checkpoint blocks, and both use `max(s_gate, s_up)`.
  - This is exact for power-of-two scales, which GLM-5.3-Flash has. Other checkpoints get one extra E4M3 rounding on half of the FC1 rows.
- **Workspaces.**
  - The kernel always processes its whole token buffer, with a launch geometry picked for that size. With a single buffer sized at `max_num_batched_tokens`, decode is slower than the baseline.
  - The adapter therefore adds 64-, 256- and 1024-token workspaces. Each call uses the smallest one that fits the largest batch across DP ranks. Without DP-wide token counts it uses the default workspace, because every rank must pick the same buffer.
- **Loaders.**
  - The fp8, compressed-tensors, online FP8 and Quark FP8 MoE methods now call the experts' `process_weights_after_loading`. It is a no-op for other experts.
  - The SM90 path is chosen from the quant config, not the weight dtype. FP8 weights keep their dtype, so a rebuild from preprocessed weights picks the same path.
- **Idle ranks.** With pass-through stages, the experts own the EP collective. A rank without tokens therefore still enters them. The change is identical to the one in #62073.
- **Limitations.**
  - The backend needs expert parallelism and `nvshmem4py`.
  - It rejects DBO, runtime weight transfer and `apply_router_weight_on_input`.
  - Shared experts are not fused.
  - FlashInfer's SM90 input staging is torch-composed, about 1.2 ms per step at C128.
