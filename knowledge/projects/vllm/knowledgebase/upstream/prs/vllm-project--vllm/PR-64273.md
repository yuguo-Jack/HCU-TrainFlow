# [ROCm] MiniMax-M3: allow the AMD monokernel decode on MiniMax-M3.1

[Upstream PR](https://github.com/vllm-project/vllm/pull/64273) · state: closed · merged: False

## Original PR description

## Purpose

Let the AMD fused-FFN decode launch (`--monokernel`, Model Runner V2) run on MiniMax-M3.1. Today it refuses the checkpoint for three reasons:

- The KV cache is NVFP4. The fused launch starts after attention and doesn't read the KV cache, so `spec.py` now accepts `nvfp4` for the KV and indexer caches as well as FP8.
- M3.1 has sparse attention on every layer, including the leading dense-FFN layers. Those layers run the stock path, so the check now requires only that the fused layers are sparse.
- The qkv and o projections are MXFP8. The launch wants BF16, so `weights.py` gives it a dequantized copy. E4M3 times a power-of-two scale is exact in BF16, so the copy is lossless. The stock path keeps serving the MXFP8 weights.

Serving M3.1 this way also needs `VLLM_ROCM_USE_AITER_FUSION_SHARED_EXPERTS=1`, `--quantization-config.targets '{"*shared_experts*": "mxfp4"}'` and `indexer_decode_cp=false`. The shared-expert requant is lossy, and the accuracy gate is still pending (see below).

The recipe gets a `monokernel` mode under `mono_decode` for the mxfp4 variant, carrying those settings. `mono` stays the default. The monokernel path accepts only EAGLE3 speculation, so it can't run with the recipe's DSpark draft; the mode description says to turn Speculative decoding off. The recipe schema has no way to express that conflict.

## Test Plan

- `tests/models/minimax_m3/amd_specialized_decode/test_runtime.py`. The refusal test now puts a dense layer inside the fused range, and a new test accepts the M3.1 layout.
- End to end: MiniMax-M3.1 Quark MXFP4, TP4 on MI355X, NVFP4 KV, 8192 in / 512 out.
- Accuracy: GSM8K and GPQA-Diamond with McNemar against the baseline.
- Recipe: `node scripts/validate-source.mjs --source vllm --dir recipes` from a vllm-project/recipes checkout.

## Test Result

- Unit: 6 passed in the selected config tests.
- Recipe: valid against the renderer.
- Both arms ran without speculative decoding (see the DSpark caveat below).
- The server log shows the fused launch running: `MiniMax-M3 FFN launch: rows (1..16)`, 57 sparse layers per step. Batches above 16 rows use the stock path.

| Concurrency | Baseline tok/s | This PR tok/s | Change | TPOT (ms) |
|---|---|---|---|---|
| C1 | 156.0 | 209.3 | +34% | 4.43 |
| C16 (warm) | 1552 | 1609 | +4% | 8.99 |
| C64 | 1647 | 1824.5 | +11% | 28.38 |

KV capacity is 16.58M tokens, against 16.91M for the baseline. The C64 gain can't come from the fused launch, which stops at 16 rows; it's most likely the MXFP4 shared experts.

**DSpark caveat.** The baseline in this table isn't the recipe's real default. On AMD the recipe turns DSpark on (3 speculative tokens), and this path refuses DSpark, so its fair comparison is against the same baseline with DSpark. That run is pending. Until it lands, these numbers show the gain only for deployments that run without speculative decoding, and they may not beat the recipe default at all.

Accuracy: pending.
