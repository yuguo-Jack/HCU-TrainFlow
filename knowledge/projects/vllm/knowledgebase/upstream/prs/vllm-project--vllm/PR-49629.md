- LCAIZJ · comment · 2026-08-04T16:01:09Z · [source](https://github.com/vllm-project/vllm/pull/49629#issuecomment-5181555820)

Hi @MatthewBonanni，We are actually implementing a similar feature https://github.com/vllm-project/vllm/issues/48203, but we have a much more comprehensive long-term roadmap for this functionality. Specifically, we plan to continue working on the following optimizations:
1. Fused Operator Optimization: Fuse H2D transfers with Sparse Attention computation to achieve better overlap.
2. Direct KV Cache Transfer: Enable direct transfer of KV Cache from Prefill to the Decode host.
3. Shared Offloading Memory across TP Ranks: Allow multiple Tensor Parallel (TP) ranks to share a single offloading memory space during decoding, eliminating redundancy.
4. Prefill-Side Offloading: Implement offloading on the prefill side, which will become increasingly valuable as supported context lengths continue to grow.
5. Dynamic Offloading Activation: Dynamically enable offloading based on batch size—disabled for small batches where it offers no benefit, and enabled for large batches to maximize performance gains.
6. Multi-Node Memory Offloading: Extend offloading from single-node to multi-node memory to support larger capacity, leveraging supernode memory semantics.

Given our extensive long-term plans for DSA model offloading and the fact that we have a dedicated team working on this, would it be possible for us to take ownership of this feature? This would allow us to progressively deliver these subsequent optimizations in a cohesive manner. We'd love to hear your thoughts on this proposal.

- MatthewBonanni · comment · 2026-08-06T22:11:09Z · [source](https://github.com/vllm-project/vllm/pull/49629#issuecomment-5209469429)

Hi @LCAIZJ, I really appreciate all the work you've done to flesh this feature out in vllm-ascend. I've taken a look at your implementation and I do like the flexibility of the connector-based approach. I've taken some steps to move my PR a bit in that direction while still maintaining some of the key performance characteristics of the original implementation. The main breakdown of the architecture in my PR is:

- `HiSparseCoordinator` : a scheduler-side coordinator that makes residency decisions about which GPU pages to offload and coordinates the hot buffer allocations
- `HiSparseConnector` : a KV connector that brings spill commands from the scheduler to the worker (and completion IDs back)
- `HiSparseWorker` : executes all the scheduler commands
- `HiSparseRuntime` : what the attention layer actually interacts with. Does the cache resolution

My implementation is only focused on decode and will compose nicely with the prefill offloading you describe in #48203. We're also committed to maintaining the feature and continuing to optimize it further down the road. Any contributions you would like to make, either as suggested changes to my PR or future optimizations, are definitely welcome!
