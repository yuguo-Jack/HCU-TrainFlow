# [MM][CG] Support Qwen3 image graphs with video pruning

[Upstream PR](https://github.com/vllm-project/vllm/pull/63954) · state: open · merged: False

## Original PR description



## Overview

Keep Qwen3-VL image encoder CUDA graphs available when video pruning is configured. Append the image mRoPE metadata outside the captured vision forward, using the same helper as eager encoding and retaining the complete DeepStack output.

Related: #38175. This is separate from #63951 (skipping capture when no modalities are eligible), #60112 (replay-capacity fallback), and #49432 (encoder interface refactoring). Open PR searches for encoder/cudagraph/pruning and image pruning found no equivalent image postprocessing change.

## Claims

- With EVS or VidCom2 configured, image encoding can use encoder CUDA graphs in the default `mm_encoder_tp_mode="weights"` mode when the configured image limit is positive.
- The five image position channels are appended after replay or eager fallback, with all visual and DeepStack channels preserved.
- Returned embeddings own their storage and survive later replays. Video encoding and pruning with encoder data parallelism remain eager.

The new regression checks real graph hits for one and two distinct images, an oversized-image eager fallback, exact position metadata, preservation of all visual channels, retained outputs across subsequent replays, and 16-token greedy generation with top-5 logprob comparisons against encoder-CG-disabled execution. It uses MRV2 and `TRITON_ATTN`; the existing Buildkite core-model selection covers this file. The additional local variant changes the backend to `FLASH_ATTN` and temporarily sets the real model's public image-limit configuration to `ImageDummyOptions(count=0)`, checking that `get_encoder_cudagraph_config().modalities` becomes empty, then restores the original configuration.

## Details

Pruning currently disables both graph modalities because image and video eager postprocessing add position metadata that the raw graph output lacks. Image postprocessing has a fixed five-channel format, so it can run after the existing graph and fallback paths. This change enables images in weights mode and reserves the extra five channels in the advertised output width; video pruning stays outside this scope.

The postprocessor uses CPU grid metadata already selected by the manager, reuses `_postprocess_image_embeds_evs`, and scatters outputs back to their original item indices. Concatenating the position channels creates owned output tensors, so an additional clone is unnecessary. An image limit of zero leaves both graph modalities disabled, composing with #63951 for video-only deployments.

Tensor comparisons use matching execution shapes. An initial test accidentally compared two separate 64-token forwards with a single batched 128-token forward. A control reproduced the same differences in eager alone, while each graph output was bit-exact with its corresponding separate eager forward. The regression now captures 64 and 128 token budgets; no numerical tolerance was widened.

Coverage gaps: full video-pruning generation, multi-GPU execution, MoE checkpoints, MRV1, and other GPU architectures. No latency or memory-saving percentage is claimed. An exploratory FlashInfer run hit its existing `return_lse=True` assertion before exercising the new postprocessor.

AI assistance was used for implementation, review, tests and validation. The reported remote runs were executed by an AI agent on the submitter's server.
