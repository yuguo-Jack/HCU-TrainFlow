[Upstream PR](https://github.com/vllm-project/vllm/pull/51577) · state: open · merged: False

# Purpose

`llama3_json` streaming and non-streaming disagree: the legacy parser re-parses a cumulative buffer with fixed separator arithmetic, so at more than one token per SSE delta it returns tool calls that do not parse — **174/858 valid at 5 tokens/delta (20.3%), against 858/858 here**. This migrates `Llama3JsonToolParser` (registry names `llama3_json`, `llama4_json`) onto the declarative `ParserEngine`, where non-streaming replays the same state machine as streaming, so the two agree by construction. It also un-breaks `llama4_json`, which raised at construction on real Llama-4 tokenizers.

Measured live, **streaming**, on the full BFCL v4 set (858 cases, `simple_python`/`live_simple`/`multiple`): each parser's exact generated tokens replayed through `extract_tool_calls_streaming` at 1/2/5 tokens/delta, scored with `bfcl-eval`'s own `ast_checker`. <summary><b>Design</b></summary>

The LLama JSON format is a bare envelope with no wrapper and no end marker:

```
[<|python_tag|>]{"name": "f", "parameters": {...}}; {"name": "g", ...}
```

Most tool-call formats tell the engine where a call starts and ends for free. Qwen3 wraps a call in `<tool_call>...</tool_call>`. Granite has no closing token, but `<tool_call>` still marks the start, and the body is one JSON array the engine already knows how to split. Llama's `<|python_tag|>` is optional, and when present isn't always followed by JSON — the model can put ordinary ipython-style text after it — so it isn't trusted as an opener the way Granite's marker is; the engine just consumes it as text and waits to see what actually follows. `{` ends up doing the opener's job instead: it's both the opener and ordinary text (prose can contain one too), and the call ends only when the JSON balances.

Llama's bare envelope doesn't match an existing engine mode, so this parser answers four questions those other formats get for free:

- **When does tool call ends** When the JSON balances - a new engine flag `tool_call_ends_on_args_balance` rather than a closing terminal, so separators (`;`, a newline) don't matter.
- **What's the tool name, and what are its arguments** The envelope's top level `"name"` key (not one nested in the arguments), `arguments/parameters` are the model's own text, not a rebuilt JSON object - so the client sees exactly what the model wrote.
- **What if the model never finishes the JSON** Cut back to the longest prefix that's still valid and closed by appending - never by rewriting text already streamed.
- **What if it looks like a call but it isn't** A balanced `{...}` with no top-level `"name"` key is prose. Its events are retracted and the text restored as content.

Implementation notes:

- Separators `;`, newlines, commas, a second `<|python_tag|>`, or nothing at all (the xgrammar `llama` structural tag for `tool_choice="required"` forces back-to-back `{...}{...}`) all work, since the parser isn't looking for one.
- The top-level `"name"` lookup is a structural scan, not the engine's regex fallback, which would match a `"name"` nested inside `parameters`.
- A prose `{...}` that gets retracted has its slot recycled, so real calls still stream with dense indices from 0.
- `tool_choice="required"` and named choice are handled by this parser directly (`supports_required_and_named = False`), as the other engine parsers do.
- `llama_tool_parser.py` is gutted in place to an adapter shim keeping the class name and `structural_tag_model="llama"`, so the registry needs no change.

<summary><b>Behaviour changes vs the legacy parser (9)</b></summary>

Each is forced by streaming/non-streaming unification or is a strict improvement. Every example is measured: the same input fed to `origin/main`'s `Llama3JsonToolParser` and to this branch. `CALL` abbreviates `{"name": "f", "parameters": {"a": "x"}}`.

1. **Leading prose before a call is returned as content** (legacy: `content=None`); text after the first completed call is still dropped.

   ```text
   in      Let me check. CALL
   legacy  f({"a": "x"})   content=null
   new     f({"a": "x"})   content="Let me check."
   ```

   Legacy *streaming* is worse than its own non-streaming result here — it never detects the call at all:

   ```text
   legacy (streaming)  no call, content = the entire string
   new    (streaming)  f({"a": "x"})   content="Let me check."
   ```

2. **An envelope needs `parameters`/`arguments` next to `name` to be a call.** Name-only and prose user-data shapes stay content — unchanged from legacy, and listed because it is a refusal worth preserving.

   ```text
   in      {"name": "John", "age": 30}
   legacy  non-streaming: content = input, no call
   legacy  streaming:     a tool call named "John" with empty arguments
   new     both:          content = input, no call
   ```

   Non-streaming this is unchanged from legacy. Streaming, legacy promotes the user's own data to a tool call — the migration removes that by construction.

3. **Valid `name` + malformed params → a call whose arguments are cut back to the longest closeable prefix**, so they always parse. See "One deliberate deviation" below.

   ```text
   in      {"name": "f", "parameters": {"a": "x", bad}}
   legacy  no call, whole string as content
   new     f({"a": "x"})
   ```

4. **A valid call followed by a bad object no longer drops the valid call** (#49923's bug 2 — legacy was all-or-nothing).

   ```text
   in      CALL I used {searchTool} here
   legacy  no call, whole string as content
   new     f({"a": "x"})
   ```

5. **Arguments are the verbatim model span**, not `json.dumps` re-serialisation — same JSON value, the model's own whitespace.

   ```text
   in      {"name": "f", "parameters": {"a":   "x"}}
   legacy  f({"a": "x"})
   new     f({"a":   "x"})
   ```

6. **The constructor no longer raises when `<|python_tag|>` is absent.** This un-breaks `llama4_json`, which was unusable at startup on real Llama-4 tokenizers.

   ```text
   in      Llama-4 tokenizer (no <|python_tag|> in vocab)
   legacy  RuntimeError: could not locate the bot token '<|python_tag|>'
   new     constructs, and parses <|python_start|> ... <|python_end|>
   ```

7. **Truncated mid-JSON generation emits the partial arguments, repaired to valid JSON, in both modes.** A real generation cut at `max_tokens=16`:

   ```text
   in      {"name": "get_weather", "parameters": {"location": "Boston
   legacy  non-streaming: no call, raw partial as content
   legacy  streaming:     get_weather({"location": "Boston"})     <- and so disagrees with itself
   new     both:          get_weather({"location": "Boston"})
   ```

   Legacy streaming also hands the client arguments that do not parse at all, at other truncation points — `{"query": "ll` from a real `max_tokens=20` run, and 14 of 80 cells in the workload below.

8. **Prose containing braces is preserved byte-identically in streaming too.**

   ```text
   in      Code: if (x) { y(); } done
   legacy  content = input
   new     content = input
   ```

9. **Argument values are coerced to their declared schema type, and only when the value is invalid for it.** Legacy did no coercion at all; the shared engine coerces unconditionally and so corrupts already-valid values, so this guard is what keeps it from being a regression. Largest measured difference in the eval below.

   ```text
   in      {"name": "f", "parameters": {"n": "10"}}     with  n: integer
   legacy  f({"n": "10"})   <- str where the schema says int
   new     f({"n": 10})
   ```

Legacy streaming additionally advanced a fixed two characters past each parsed call (`start_idx += end_idx + len("; ")`), so any separator those two characters do not cover silently dropped every call after the first (#49923's bug 1):

```text
in      CALL;CALL          (bare ";", not "; ")
legacy  1 of 2 calls
new     2 of 2 calls
```

## One deliberate deviation worth flagging

Behaviour change 3 — a malformed or truncated envelope with a valid `name` is **promoted to a tool call** with its arguments cut back to the longest parseable prefix, where legacy failed closed and returned content.

This follows the contract the other engine parsers already implement, and the alternative is worse: rejecting the call at close means withholding the tool name until the envelope balances, which removes incremental argument streaming for every Llama call, not just malformed ones. I have taken that as the right trade. If maintainers prefer failing closed for this parser specifically, say so and I will implement it — it is a contained change, and it is the only decision here I would expect to be contentious.

<summary><b>Other known limitations</b></summary>

- **Named tool choice can return the whole envelope as the arguments** for schemas that constrain the object, when `VLLM_ENFORCE_STRICT_TOOL_CALLING=0` removes the structural tag and the model emits the envelope anyway. What prevents that is the decoding grammar, and it is backend-dependent: xgrammar rejects the envelope for a typed schema, llguidance 1.7.6 at vLLM's defaults accepts it unless `disable_additional_properties` is set. Default configuration (strict on) is unaffected.
- The equivalent coercion guard for `ParserEngine._coerce_value`, which would affect the other engine parsers, is deliberately not in this PR — attempted once during the size-reduction pass and reverted when it broke gemma4's and deepseek_v32's own tests, which pin different, deliberate best-effort coercion behavior. Left as a narrowly-scoped follow-up PR with full cross-parser coverage.
