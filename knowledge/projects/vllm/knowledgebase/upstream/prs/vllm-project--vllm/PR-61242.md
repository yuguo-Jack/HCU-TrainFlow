# [Perf][Model] Qwen4Exp QSA DCP: opt-in sharded selector

## Overview

Opt-in **sharded** QSA selector for Qwen4Exp decode context parallelism (DCP). With `--attention-config '{"qsa_dcp_selector": "sharded"}'`, each DCP rank stores and scores only the compressed indexer keys of the tokens it owns. One all-gather of the ranks' local top-k candidates then gives the same global top-k as the replicated selector. The default stays `"replicated"` (#59279); nothing changes without the opt-in.

**Depends on #61728, which depends on #59279.** This branch is #61728 (head ce2f6f0c6) plus 7 commits; review only the commits after ce2f6f0c6. As @sungsooha asked, this follow-up is its own PR. It replaces this draft's earlier content (a full QSA DCP implementation that overlapped #59279).

## Claims

- With the opt-in, the selector cache and the selector scoring per rank shrink by the DCP size, for one extra collective per selection. The selection result is the same as with the replicated selector (end-to-end GPU test on N simulated ranks).
- Measured on 8 × A100-SXM4-40GB, DCP 4: the GPU KV cache holds **1.33×** the tokens at the same KV memory (6,545,304 against 4,925,984 tokens, 13.21 against 13.26 GiB).
- No change to core files: the only change outside the model code is the `AttentionConfig.qsa_dcp_selector` option. The sharded selector joins the main KV cache group (main block size), so it uses the runner's block-table width and needs no kernel block table.
- The global top-k merge with 2 or 4 DCP ranks uses sorted int64 keys and a bitonic merge tree: one rank's pack + select is **1.47-2.04× faster** on A100 than the 32-warp full sort of the previous commit (550 → 270 µs at 1,920 rows), and the output is bitwise equal to the full sort. Serving A/B (2 pairs): TPOT P95 −4.4 % and −3.1 %.
- Requirement: `cp_kv_cache_interleave_size` must be a multiple of the indexer compress ratio (4 here). The cache refuses other values at start.

**Global top-k merge kernel (1 × A100-SXM4-40GB).** `_select_qsa_dcp_topk_kernel` sorts DCP × top-k = 2,048 int64 keys in one program. Launch-parameter sweep at the per-GPU shapes of the serving setup (32 requests × 4 query tokens, CUDA graph, L2 flushed before each replay): 32 warps take 64.0 / 48.9 / 49.1 µs at 8k / 32k / 128k context, against 91.2 / 70.3 / 70.3 µs with the earlier 8 warps (1.43×); the output is bit-equal. `test_qsa_dcp_sharded_selector.py`: 72 passed with the change.

**Sorted-key merge (latest commit).** With 2 or 4 DCP ranks and a power-of-two k, each rank packs its local top-k as int64 keys sorted descending (the same key as `_select_qsa_dcp_topk_kernel`), and the select merges them with a bitonic merge tree instead of sorting all DCP × k keys. Other cases keep the full sort.

- *Exactness:* the keys are a strict total order. The elementwise max of a descending and an ascending sorted block holds exactly the top k of their union as a bitonic sequence, and a bitonic merge sorts it. So the output is the first k keys of the full sort: the same ids, order and −1 padding. Checked bitwise at 72 points (DCP 2 and 4, interleave 1 and 4, random / tie-grid / padded rows, 1-1,920 rows).
- *Kernel (1 × A100, CUDA graph, 16,800 states per rank, k 512):* one rank's pack + select is 53 → 25 µs at 80 rows, 229 → 90 at 480, 421 → 165 at 960 and 695 → 247 at 1,920 (2.1-2.8×).
- *Serving A/B (8 × A100, same setup as the table above but on the current stack, ABBA in one job, KV memory pinned, 1 × 60 min per arm, 0 failed requests):*

TPOT P95 is lower in both pairs (−4.4 %, −3.1 %). TTFT P95 is +0.7 % in pair 1 and −5.6 % in pair 2, so the TTFT effect is not clear from two pairs. **Baseline note:** the "full sort" serving arm used the earlier 8-warp launch of `_select_qsa_dcp_topk_kernel`, not the 32-warp launch of the previous commit. - The sharded selector holds 1.34× the GPU KV tokens. At C48 this keeps the GPU prefix-cache hit rate at 96.7 % against 70.9 %, and gives −21 % TTFT P95, −18 % TPOT P95 and +13 % throughput.
- At C64 the replicated selector fills the GPU KV cache (99.8 %) and almost all prefix hits move to the CPU tier; the sharded selector gives +23 % throughput and −40 % TTFT P95.
- The C64 sharded repeat agrees with the first run within 1 % at P50 and 7 % at TTFT P95.

## Details

| Commit | What and why |
|---|---|
| opt-in sharded selector cache and metadata | `AttentionConfig.qsa_dcp_selector`; the sharded compressed-key cache spec (rank-local tokens) and its side-cache metadata (rank-local visible blocks). |
| sharded selector scoring and exact global top-k merge | Each rank scores its local compressed keys; the ranks' top-k candidates are all-gathered and merged into the exact global top-k. |
| fuse expand and localize for the sharded selector | One kernel expands the selected blocks and writes this rank's local token ids and count into the layer top-k buffer, so the indexer skips its separate localize step in sharded mode (the replicated path is unchanged). |
| warm the sharded selector kernels | Compile the new kernels before CUDA graph capture. |
| test the sharded selection end to end on N simulated ranks | The sharded result equals the replicated expand + localize result on every rank, also through the indexer. |
| more warps for the global top-k merge | `num_warps = min(32, max(4, BLOCK_N // 64))`: 32 warps for 2,048 keys instead of 8 (1.43× on A100, bit-equal). |
| sorted-key bitonic merge for the global top-k | With 2 or 4 DCP ranks and a power-of-two k: sorted int64 keys per rank, then a bitonic merge tree (1.47-2.04× against the 32-warp full sort on A100, bitwise equal). Other cases keep the full sort above. |
