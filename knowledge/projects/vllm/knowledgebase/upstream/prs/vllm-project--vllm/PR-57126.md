# [Bugfix][ROCm] Guard compressed-tensors FP8 KV cache auto-selection

[Upstream PR](https://github.com/vllm-project/vllm/pull/57126) · state: open · merged: False

## Original PR description

## Purpose

Fixes #56992.

Compressed-tensors checkpoints with a `kv_cache_scheme` currently change the KV cache dtype from `auto` to `fp8` during `Attention` initialization. On gfx1100/RDNA3, vLLM's ROCm platform does not advertise FP8 support, and the Triton paged-attention path must software-convert FP8 K/V values. This is slower than retaining the model dtype (BF16).

This change:

- keeps `auto` on ROCm platforms where `current_platform.supports_fp8()` is false;
- emits a warning that identifies the fallback and the explicit override;
- preserves automatic FP8 on supported ROCm platforms and all non-ROCm platforms;
- preserves explicit `--kv-cache-dtype fp8` and explicit non-FP8 choices.

### Duplicate-work check

No open PR references #56992.

This is complementary to #45038, not a duplicate. That PR guards the same override with CUDA-style `has_device_capability(90)`. ROCm gfx1100 reports device capability 11.0, so that numeric check evaluates true and does not prevent the RDNA3 override. This PR uses the existing ROCm platform capability policy instead; `RocmPlatform.supports_fp8()` is false on gfx1100 and true on supported CDNA/RDNA4 targets.

- AMD Radeon PRO W7900D (`gfx1100`), physical GPU 2

The local checkpoint's current config has `kv_cache_scheme=null`, so the exact scheme from #56992 was injected into an isolated hard-linked model view; weights were unchanged. The checkpoint has no KV-scale tensors, so this is performance evidence only and not an accuracy claim.

All 64 formal benchmark requests succeeded.

| KV mode | Mean TPOT @1K | Mean TPOT @2K | Output throughput @1K | Output throughput @2K | Context slope |
|---|---:|---:|---:|---:|---:|
| patched `auto` (BF16) | 178.015 ms | 262.065 ms | 25.895 tok/s | 16.025 tok/s | 82.08 us/context-token |
| explicit `fp8` | 204.855 ms | 297.470 ms | 25.405 tok/s | 14.955 tok/s | 90.44 us/context-token |

The patched auto/BF16 path reduced mean TPOT by 13.10% at 1K context and 11.90% at 2K context. Its output throughput improved by 1.93% and 7.15%, respectively. FP8's context-length decode slope was 1.10x the BF16 slope. Repeat TPOT range was at most 0.118%.

With the same 18.52 GiB KV budget, capacity changed as expected:

| KV mode | Attention block size | KV capacity |
|---|---:|---:|
| patched `auto` (BF16) | 784 | 131,754 tokens |
| explicit `fp8` | 1,568 | 175,672 tokens |

#45916 remains open and was not present in the tested vLLM 0.27.0 runtime, so these measurements do not include the proposed split-KV optimization.
