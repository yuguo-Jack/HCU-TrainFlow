# [Kernel][Build] Bump DeepGEMM to the 26/09/30 release and adapt the sparse indexer

[Upstream PR](https://github.com/vllm-project/vllm/pull/61149) · state: open · merged: False

## Original PR description

## Overview

Bump the vendored DeepGEMM pin to the tip of `vllm-project/DeepGEMM` `dev` (`1448881`): upstream's 26/09/30 public release (vllm-project/DeepGEMM#30, deepseek-ai/DeepGEMM#462) plus a vendoring import fix (vllm-project/DeepGEMM#31). Adapt vLLM to the breaking MQA-logits API.

## Claims

- vLLM builds, vendors and imports DeepGEMM 2.8.1.
- The DSA sparse indexer (DeepSeek-V3.2, GLM-5.x, GLM-5.3, DeepSeek-V4/V4.1, HY-V4) keeps working on SM90/SM100/SM120 with the new MQA-logits API.
- On SM100 the FP8 indexer cache stays numerically identical: same FP8 values and the same per-token power-of-two scale, now stored as four packed UE8M0 bytes (a valid MXFP8 encoding) because SM100 MQA kernels only take MX scales.

## Breaking changes in DeepGEMM `1e1842a` → `1448881`

| Change | vLLM impact | Handling |
|---|---|---|
| `deep_gemm/__init__.py` imports a new `deep_gemm/locality_domain.py` | not vendored → `import vllm.third_party.deep_gemm` fails | install it in `deepgemm.cmake` |
| `_C.py` registered the locality-domain shim as `deep_gemm._C.locality_domain` | relative import fails when vendored as `vllm.third_party.deep_gemm`, and vLLM then silently treats DeepGEMM as unavailable | fixed in vllm-project/DeepGEMM#31 (in the pin); `tools/check_wheel_deepgemm.py` now imports the package so CI catches this |
| `fp8_mqa_logits`, `fp8_paged_mqa_logits`, `fp8_gemm_nt_skip_head_mid`, `get_bf16_mega_gate_config` removed | unused by vLLM | none |
| `clean_logits` / `logits_dtype` removed from `fp8_fp4_(paged_)mqa_logits`; `max_seqlen_k` now required (> 0) | wrapper signatures | `vllm/utils/deep_gemm.py`; prefill chunk metadata carries a host `max_seqlen_k` bound (no device sync) |
| `fp8_fp4_mqa_logits` returns **compressed** logits `[M, max_seqlen_k]` (row `i` starts at K position `ks[i]`) on every arch | prefill top-k / candidate-block / DCP consumers indexed absolute columns | consumers run on row starts `0`, ends `ke - ks`; output indices are unchanged (already relative to `ks`) |
| SM100 MQA kernels take only MXFP8/MXFP4 with packed UE8M0 scales, **BF16 weights**, return **BF16 logits**; paged is varlen-only | FP8 indexer (fp32 per-token scale, scale folded into fp32 weights) rejected | see below |
| `bf16_mega_gate` default `scoring_func` → `'sqrtsoftplus'` | vLLM always passes it | none |
| FP8×FP4 / BF16 Mega MoE assert DeepGEMM's SM count equals the device's | only DBO + DeepEP-HT lowers it (`ubatch_utils.py`), not combined with Mega MoE today | none (noted) |
| Epilogue classes (`epilogue=` kwarg), locality domains, `shutdown` | additive | none |

### SM100 FP8 indexer

Every CUDA FP8 indexer writer already stores an exact power-of-two scale `2^ceil(log2(amax/448))` per 128-wide token. On SM100 (`mqa_logits_use_mx_scales()`) the writers store that scale's exponent as four equal UE8M0 bytes instead of the fp32, which is an exact MXFP8 encoding of the same values (same cache size, same FP8 bytes):

| Writer | Models |
|---|---|
| C++ `indexer_k_quant_and_cache` (`scale_fmt="mxfp8"`) | DeepSeek-V2-class `Indexer` (V3.2 via that class, DeepSeek MTP), HY-V4, DeepSeek-V3.2 under PCP |
| DeepSeek-V3.2 fused norm/RoPE (`_fused_norm_rope_kernel`) | DeepSeek-V3.2, GLM-5/5.2 (`GlmMoeDsa`), Dots3Note, V3.2 MTP |
| DeepSeek-V4 compressor (Triton; the CuTeDSL compressor is head-512 MLA only) | DeepSeek-V4 |
| DeepSeek-V4.1 `indexer_k_norm_rope_store` | DeepSeek-V4.1 |
| GLM-5.3 kpool prefill compress + decode update | GLM-5.3 |

Readers need no change: `cp_gather_indexer_k_quant_cache` (prefill, all of the above) and the DCP/PCP gathers copy the 4 scale bytes verbatim, and DeepGEMM reads the paged cache directly. The 512-wide MLA caches, MXFP4 caches, and the MiniMax-M3 / Qwen4 indexers are untouched.

FP8 Q keeps folding its per-(token, head) power-of-two scale into `weights`; `mqa_logits_mx_inputs` passes unit MX Q scales (exact, since `relu(s·x) = s·relu(x)` for `s > 0`) and casts weights to BF16. The BF16 logits are upcast to FP32 for the existing FP32-only top-k kernels (`as_fp32_logits`); routing BF16 logits straight to a BF16-capable top-k (DeepSelect / LiteTopK, #59921/#59922) is a follow-up.

SM90 and SM120 keep the FP8 format, FP32 weights and FP32 logits. Consequently the FP8 indexer cache's scale bytes now differ between SM100 and other architectures: moving that KV cache between SM100 and non-SM100 nodes (cross-generation PD disaggregation, shared KV offload) is not supported for these models. Same-architecture setups are unaffected.

## Validation

All on 4x GB200 (SM100), CUDA 13, torch 2.13; baseline = `main` with the old pin `1e1842a`, same build otherwise.

**GLM-5.3-Flash** (FP8, TP4 + EP, MTP=3, `--max-model-len 131072 --max-num-batched-tokens 131072 --kv-cache-dtype fp8_e4m3 --reasoning-parser glm47`, `reasoning_effort=low`), on the rebased branch vs `main` bfa7e5b7af. MRCR prompts are far longer than the indexer's coverage (2048 pools × 4 = 8K tokens), so they exercise top-k selection; long prefills also engage the TP prefill row sharding from #54951 (confirmed with a temporary log, e.g. 129K-row steps split `[47458, 18791, 42577, 19957]` across ranks):

| | `main` + `1e1842a` | this PR |
|---|---|---|
| MRCR, 60 samples of 16K–32K tokens (`tests/evals/mrcr`), match ratio (2 / 4 / 8 needles) | 0.794 (0.823 / 0.798 / 0.760) | 0.810 (0.904 / 0.791 / 0.735) |
| MRCR, 24 samples of 57K–66K tokens, match ratio | 0.578 (4 runs hit max_tokens) | 0.665 |
| GSM8K (1319, 5-shot) | 90.8% | 91.6% |
| Serving, 4 runs of 128 × (4096 in / 512 out) at concurrency 32, output tok/s | 1492 / 1544 / 1491 / 1471 | 1484 / 1476 / 1337 / 1501 |
| Median ITL | 19.85 ms | 19.9 ms |

GLM-5.3 serving throughput tracks the MTP acceptance length, which varies per run (the 1337 tok/s run had 1.31 vs ~1.7–1.8 elsewhere); runs with matching acceptance agree (1476 @ 1.70 vs 1471 @ 1.71).

**DeepSeek-V4-Flash** (before the rebase onto current `main`; baseline 26a488ad93), TP2 + EP, `--kv-cache-dtype fp8 --attention_config.indexer_kv_dtype=fp8`, `--max-model-len 8192`; GSM8K via `tests/evals/gsm8k/gsm8k_eval.py` (1319 questions, 5-shot, 2 rounds). GSM8K prompts fit inside the indexer's coverage (512 × 4 = 2K tokens), so this checks the SM100 path end to end rather than top-k selection:

| indexer cache | `main` + `1e1842a` | this PR |
|---|---|---|
| fp8 | 95.5% / 94.6% | 94.8% / 94.6% |
| mxfp4 | 94.9% | 94.7% |

**Serving** — same server, `vllm bench serve --dataset-name random --random-input-len 4096 --random-output-len 512 --num-prompts 256 --max-concurrency 64 --ignore-eos`, one warm-up + 3 runs each, sequential on the same GPUs:

| | output tok/s | mean TPOT | median ITL |
|---|---|---|---|
| `main` + `1e1842a` | 2968 (2962–2974) | 18.73 ms | 12.80 ms |
| this PR | 2946 (2928–2958) | 18.89 ms | 12.94 ms |

The ~0.8% gap matches the two extra small kernels per indexer layer on SM100 (weights → BF16, row-aware logits → FP32, ~3 µs together). Feeding BF16 straight from the Q producers and into a BF16 top-k removes both.
