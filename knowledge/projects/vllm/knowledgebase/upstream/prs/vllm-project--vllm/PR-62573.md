# [EPD] Support metadata-only audio-in-video requests

[Upstream PR](https://github.com/vllm-project/vllm/pull/62573) · state: closed · merged: True

## Original PR description

## Overview

Support metadata-only `use_audio_in_video` requests for Qwen2.5-Omni and Qwen3-Omni in the Python EPD frontend/proxy.

## Claims

- Forward video timing and audio lengths without repeating media preprocessing on the consumer.
- Preserve both features' EC hashes and transfer handles; fall back to raw media for the whole request when metadata is incomplete.

## Validation

Original validation before the review fixes, GB200, 1E + 1PD, Model Runner V2: **48/48 functional smoke requests succeeded** across ECExample, Mooncake TCP, and CPU/NIXL with `Qwen/Qwen2.5-Omni-3B` and `Qwen/Qwen3-Omni-30B-A3B-Instruct`.

Covered one/two videos with audio, image + video, and audio disabled, each repeated twice. Audio-enabled requests use `mm_processor_kwargs={"use_audio_in_video": true}`; both instances use `--trust-request-mm-kwargs`.

Review-fix validation:

- GB200, cached Qwen3-Omni-30B-A3B-Instruct weights, MRV2, eager mode, `enable_mm_embeds=True`, no EC connector: **4/4 synthetic embedding requests completed** (one/two images and one/two videos), followed by a successful text request on the same engine. Inputs used BF16 embeddings shaped `(4 * n, 8192)` with `grid_thw=[[1,4,4]] * n`; this checks request completion and item handling, not semantic accuracy. Runtime: Torch 2.13.0+cu130, Transformers 5.15.0, existing precompiled extensions.
- `VLLM_GPU_SYNC_CHECK=error` passes the changed embedding-split path, then stops at the pre-existing `input_ids.cpu()` in Qwen3-Omni's `embed_input_ids`; the successful smoke above ran without that strict check. The full EPD connector matrix was not rerun for this follow-up.

## Details

A video with audio produces two encoder features. Carry both in one `video_embeds` content part with a companion `audio_embeds` payload and shared source UUID, preserving the chat template's single video item and interleaved placeholders.

Review fixes keep precomputed vision embeddings split by `grid_thw` in the shared Omni mixin. For push transfers, proxy-assigned IDs remain per occurrence even when encoder responses aggregate repeated hashes. Encoder response modalities select the audiovisual path; a single video feature uses the existing matching and raw-fallback behavior. Non-push connector-provided transfer handles remain supported.

Related: #52409. Duplicate checks found no equivalent PR; #57275 fixes raw-fallback identity and transfer lifecycle, not audiovisual metadata-only inputs.

🔴 Qwen3-Omni servers running `--enable-mm-embeds` now crash on any dict `image_embeds`/`video_embeds` request. On the base branch the parser rejected these with a validation error. The Qwen2.5-Omni parser now accepts them, but the inherited `_process_image_input`/`_process_video_input` return one unsplit tensor. `embed_multimodal` wraps it in `tuple(...)`, which yields one row per token, so `sanity_check_mm_encoder_outputs` fails its assertion. Fix: split precomputed embeds by `image_grid_thw`/`video_grid_thw` in `Qwen2_5OmniConditionalGenerationMixin`, as Qwen2.5-VL does. Otherwise keep rejecting non-EC vision embeds for Qwen3-Omni.

<details>
<summary>Why this was flagged</summary>

Trigger: Qwen3-Omni is served with `--enable-mm-embeds` and no EC connector, and a client sends an `image_embeds` chat part (a `video_embeds` part fails the same way). On the base branch, `Qwen3OmniMoeThinkerMultiModalDataParser` declared only audio `embedding_fields`, so `DictEmbeddingItems` raised "Cannot parse 'image' embeddings: every declared field is optional" and the request was rejected. After the change, `get_data_parser` at qwen3_omni_moe_thinker.py:1188 returns `Qwen2_5OmniThinkerMultiModalDataParser`, so the item parses and reaches the encoder. `_process_image_input` (qwen2_5_omni_thinker.py:1056-1057) and `_process_video_input` return the whole `(num_tokens, D)` tensor without splitting it. `embed_multimodal` then does `tuple(image_embeddings)`, which gives `num_tokens` 1-D rows. `sanity_check_mm_encoder_outputs` (vllm/v1/worker/utils.py:701/708) then fails its assertion inside `execute_model`, and the engine core goes down for every user. The enable_mm_embeds warning about wrong shapes does not cover this: correctly shaped embeds fail too.

**Verification:** On the base branch, `Qwen3OmniMoeThinkerMultiModalDataParser.embedding_fields` declared only `"audio"`, so `DictEmbeddingItems` rejected dict embeds at parse.py:289-294. Now qwen3_omni_moe_thinker.py:1188 returns `Qwen2_5OmniThinkerMultiModalDataParser`. The inherited methods return the tensor unsplit (qwen2_5_omni_thinker.py:1056-1057), so `sanity_check_mm_encoder_outputs` (v1/worker/utils.py:701/708) fails.

</details>

🔴 With Mooncake, a request that repeats one image now hands the decoder the same transfer id for both copies. One pushed embedding is then never cancelled and holds consumer buffer for up to 300 s. The proxy now prefers `reported.get("transfer_id")`, but the Mooncake producer stores one id per hash, so the last copy's id wins. Fix: use the proxy's per-copy id, `item_transfer_ids[idx][feature_index]`, for every item. It already matches the producer's positional `ec_items` in batched and audio/video cases alike.

<details>
<summary>Why this was flagged</summary>

Trigger: the same image appears twice in one chat request, so both copies land in one encoder batch with positional `ec_items` [t0, t1]. The Mooncake producer pushes both copies under t0 and t1. Its `request_finished` (mooncake/scheduler.py:549-552) runs `items[feature.identifier]["transfer_id"] = transfer_id` once per copy, so the single entry for that hash reports only t1. The proxy at disagg_epd_proxy.py:794 copies that reported id to both items, and `rewrite_for_decode` sends `ec_items` [{h, t1}, {h, t1}]. On the consumer, `request_finished` cancels only ids that `_request_transfer_id` resolves, which is just t1. When t1 is loaded, the t0 push stays AVAILABLE until `_expire_transfers` reaches its `_RESERVATION_TTL_SECONDS` (300) deadline, so each such request holds a push buffer for minutes. The base used `item_transfer_ids[idx]` for each copy, so both ids reached the consumer and both were cancelled. test_image_batches_preserve_item_identity asserts "per-occurrence transfers", but its mock encoder reports no `transfer_id`, so it never runs this path.

**Verification:** `request_finished` runs `items[feature.identifier]["transfer_id"] = transfer_id` once per copy (scheduler.py:549-552), so the single reported entry ends up with only t1. Nothing ever cancels t0, which stays reserved for up to 300 s (config.py:15). The base proxy always used `item_transfer_ids[idx]`, so both reservations were cancelled.

</details>

<details>

On the base branch, a single reported entry was matched through `len(indices) == 1 and len(params) == 1` and the request went ahead. With `consumer_zmq` set, the encoder also gets a second transfer id that no feature uses. No safeguard checks the model's capabilities before this branch runs. The kwarg is the only input it looks at.

**Verification:** In disagg_epd_proxy.py, lines 650-658 decide `num_features` from the request kwarg alone, line 753 sends the item into the new branch, and lines 754-758 raise `HTTPException(502, "Encoder must report video and audio")` unless both modalities are reported. On the base, `elif len(indices) == 1 and len(params) == 1` matched a single video feature and the request was served.

</details>
