# [ROCm][Perf][GLM-5.3-Flash] mxfp4_mla: native gfx950 kernel for prefill and mixed steps (on #64323)

[Upstream PR](https://github.com/vllm-project/vllm/pull/64823) · state: open · merged: False

## Original PR description

## Overview

With the `mxfp4_mla` KV cache, prefill and mixed (prefill + decode) steps of GLM-5.3-Flash run the sparse prefill kernel, which unpacks every gathered row to bf16 for each query. At 8K context that makes mxfp4 KV 3-10% slower than e4m3 end to end (#64121, #64323), almost all of it in prefill. The e4m3 and bf16 caches instead run AITER's `triton_sparse_mla_fwd`, which does not accept `mxfp4_mla`. This PR routes those steps to #64323's native gfx950 kernel, which reads the packed rows on the scaled MFMA.

**Stacked on #64323** (and through it on #64121, #61662 and #60321), which has not landed, so the diff against main includes them. This PR's own changes are the last two commits, `da5ceb963a` and `58a930677b`: [compare against #64323](https://github.com/amd-dlimpus/vllm/compare/182b295005...58a930677b).

**Status:** draft until GEAK and the KV accuracy gate pass. The PR's unit tests pass on gfx950 (MI355X): 9 passed. The kernel is being tuned for prefill shapes (GEAK task below) before the end-to-end runs.

## Why

Booking E (8K input, 1K output, TP2, `--monokernel`, two boots per arm) against e4m3 KV:

| 8K load | mxfp4 / native output tok/s vs e4m3 | Median TPOT vs e4m3 | Median TTFT vs e4m3 |
|---|---|---|---|
| C1 | -3.4% / -3.5% | 6.11 vs 6.10 ms | 525 vs 362 ms |
| C4 | -6.5% / -6.8% | 7.43 vs 7.32 ms | 1.67 vs 1.25 s |
| C32 | -9.9% / -8.2% | 25.4-25.9 vs 22.9 ms | 2.76 vs 2.27 s |

At C1 decode is unchanged and the 0.22 s of extra TTFT per request accounts for the whole gap. At C32 TPOT includes other requests' prefill chunks.

One-rank kernel timings at TP2 shapes (32 heads, latent 512, top-2048, one causal 8,192-token sequence), ms per sparse-MLA layer:

| Path | ms |
|---|---|
| AITER `triton_sparse_mla_fwd`, fp8 (e4m3 KV) | 1.26 |
| AITER `triton_sparse_mla_fwd`, bf16 | 2.35 |
| Sparse prefill kernel, bf16 rows | 6.10 |
| Sparse prefill kernel, `mxfp4_mla` rows (before this PR) | 8.75 |
| Native kernel (#64323), 1 split (this PR) | 2.80 |

GLM-5.3-Flash has 11 sparse-MLA layers, so an 8K prefill spends about 96 ms in this attention before this PR, about 31 ms after, and about 14 ms with e4m3. Decode-only steps are not the problem: at 32 rows the native kernel takes 0.063 ms against 0.109 ms for AITER fp8. Writing the 8K rows (`store_mxfp4_mla`) costs 0.036 ms against 0.023 ms for fp8.

## The change

- Backend (`rocm_aiter_mla_sparse.py`): the native kernel runs in every step when the cache is `mxfp4_mla`, the device is gfx950 and the latent is 512, not only in decode-only steps. The split count comes from `rocm_sparse_decode_mxfp4_native_num_splits`, which gives 1 split at prefill row counts. Other devices and latent widths keep the bf16 unpack.
- Test: `test_native_on_prefill_rows` runs causal prefill rows (query t sees min(t + 1, topk) of the first t + 1 slots, topk 128 and 300), covering rows shorter than a tile and the top-k boundary. It makes two checks:
  - Tight, against a torch emulation of the kernel's arithmetic: MXFP8 Q, exact K and V, and online softmax over 128-token tiles with P rounded to e4m3 at P·256. Bounds are max 0.075 and mean 3.5e-4, today's measured error plus about 25%. The max is bf16 output rounding (outputs reach 24, where half a bf16 step is 0.0625). Any error beyond the intended quantization fails here.
  - Loose, against exact-dequant attention: max ≤ 7% of max|ref| and mean ≤ 4% of mean|ref|, as a guard on the quantization's size. Measured: 4.6-5.6% and 3.4-3.45%.

## Accuracy

**Prefill now also quantizes Q.** Before this PR, prefill and mixed steps unpacked the rows to bf16 and kept Q in bf16. Now they apply #64323's three lossy steps: Q as MXFP8, P as e4m3, and V tokens more than 2^8 below their block maximum flushing toward zero. These are the same steps decode rows already take, and Q dominates the error. On the test's prefill rows the kernel differs from exact attention by mean 5.4e-3 to 6.8e-3 (about 3.4% of mean|ref|), while it differs from the emulation by only 2.2e-4 to 2.8e-4. So the error is the designed quantization, not something else. Prefill error reaches every prompt token's hidden state, so the end-to-end gate below, not the unit test, decides whether that loss is acceptable. Before this leaves draft it needs the KV accuracy gate (GSM8K, GPQA-Diamond seeds 42-44 with paired McNemar and the question-clustered analysis, RULER NIAH 32K) against #64323's native arm.

## Pending

- GEAK on the native kernel at prefill shapes (task `glm53_mxfp4_mla_prefill`). Baseline is 2.80 ms at 8K and the target is AITER fp8's 1.26 ms, with decode at 4 and 32 rows no more than 2% slower. First lever: one CTA for all 32 heads, so each K/V tile is loaded and widened once per query instead of twice.
- A per-kernel profile of whole 8K steps (C1, C4, C32), e4m3 against native. The attention above explains about 40-50% of the C1 TTFT gap; the profile will show the rest.
- The 8K throughput and TPOT A/B against e4m3, and the accuracy gate.
