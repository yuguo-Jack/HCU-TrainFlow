# [Perf][DSA] Rank the prefill indexer logits with DeepSelect in BF16

[Upstream PR](https://github.com/vllm-project/vllm/pull/62240) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

With `sparse_indexer_topk_backend="deep_select"`, the sparse-indexer prefill path still upcasts DeepGEMM's BF16 MQA logits to FP32 and ranks them with `top_k_per_row_prefill`. This PR ranks the BF16 logits with DeepSelect directly, as decode already does since #56464.

## Claims

- On SM100 with `deep_select`, each indexer prefill chunk drops the FP32 upcast (`as_fp32_logits`) and its top-k gets 3.7x faster.
- DeepSeek-V4.1-Flash prefill, DEP2 on GB200, 8 requests per rank of 4,096 new tokens on a 128K prefix hit: 429.8 -> 401.5 ms per step (-6.6%), indexer 64.5 -> 30.9 ms.
- The selected top-k values are unchanged: BF16 widens to FP32 exactly. Which index wins among exactly equal logits was already unspecified (see #56749).
- Accuracy is unchanged: GSM8K strict-match 0.924 / 0.923 over two runs and passkey retrieval 20/20 at ~8K / 31K / 62K-token prompts (DEP4 on GB200).
- Default behavior is unchanged: only `--kernel-config '{"sparse_indexer_topk_backend":"deep_select"}'` takes the new path. DCP, XPU, other top-k backends and logits whose row stride DeepSelect cannot read keep the FP32 path.

## Validation

Top-k alone, one GB200, CUPTI, cold L2, median of 3 rounds. Rows of one query chunk over 65,536 compressed keys (a 128K V4.1 request) with causal row ends, top-k 512, random BF16 logits. Base is `as_fp32_logits` + `top_k_per_row_prefill`, new is `deep_select_topk(..., end=row_ends)`:

| rows | base (us) | new (us) | speedup |
|---:|---:|---:|---:|
| 128 | 66.5 | 13.6 | 4.9x |
| 2048 | 414.4 | 110.1 | 3.8x |
| 4096 | 777.2 | 210.0 | 3.7x |
| 8192 | 1503.9 | 410.7 | 3.7x |

On every row both select exactly the values `torch.topk` selects; index sets differ only among ties at the 512th value, and all indices lie inside the row.

Prefill step, `vllm bench forward`, DeepSeek-V4.1-Flash with dummy weights, DEP2 on one GB200 node, `--case 'ds8x4k=8*4096@131072' --kv-len-jitter 0 --max-num-batched-tokens 34816`, no speculative decoding, FlashMLA MegaAttn with the MXFP4 indexer, `deep_select` top-k, rank 0 under nsys, ms per step:

| | before | after |
|---|---:|---:|
| step (bench median) | 429.8 | 401.5 |
| indexer logits + top-k | 64.5 | 30.9 |
| of which upcast + top-k | 39.4 | 5.7 |

The step numbers come from our DSv4.1 branch (nightly 49cb2bbf plus DSv4.1 changes outside the indexer); `sparse_attn_indexer` there is identical to main before this change.

Tests on GB200, same branch with this change:

```
pytest tests/kernels/test_top_k_per_row.py -k "deep_select or sparse_indexer" \
  tests/model_executor/layers/test_mla_short_prefill_indexer.py \
  tests/v1/attention/test_indexer_tp_row_shard.py tests/v1/attention/test_indexer_dcp_localize.py
43 passed, 4 skipped
```

No new test: `test_deep_select_topk` and `test_deep_select_topk_preallocated_output` already cover what this path relies on (BF16 input, per-row `end`, -1 fill for rows shorter than top-k, output into a slice of a wider buffer).

Accuracy with this change (`vllm serve`, DeepSeek-V4.1-Flash, DEP4 on one GB200 node, `sparse_indexer_topk_backend="deep_select"`, DSpark K=5 with standard rejection sampling, greedy):

| eval | result |
|---|---|
| passkey retrieval, ~8K / 31K / 62K-token prompts (20 each; 4K-31K compressed keys per row, well above top-k) | 20/20, 20/20, 20/20 |
| GSM8K, lm_eval 5-shot, max 1024 tokens, concurrency 32, strict-match (two runs) | 0.9242 / 0.9227 (±0.0073) |
| DSpark acceptance length over the second GSM8K run | 3.44 (48.9% per draft token) |

The GSM8K and acceptance numbers match what we saw before this change on the same model (0.9318 strict-match and 3.36 in a P/D setup).

## Details

- Multi-request chunks: since #61149, DeepGEMM returns compressed logits in which every row starts at column zero (`row_starts is None` on CUDA), so `end = cu_seqlen_ke - cu_seqlen_ks` is each row's full causal interval for any number of requests in a chunk. #57206 tried this before that change, limited itself to single-request chunks, and was closed.
- Duplicate check: #57206 (closed, see above); #62172 lets `cooperative_topk` read BF16 logits on the decode path; #60618 (WIP) fuses scoring and top-k for prefill in a new kernel; #56749 changes tie-breaking of the existing prefill kernel. None changes the `deep_select` prefill path.
- The logits chunk budget (`VLLM_SPARSE_INDEXER_MAX_LOGITS_MB`) still assumes FP32 logits; counting BF16 would allow chunks twice as tall and is left for a follow-up.
- AI assistance (Claude Code) was used to find, write and validate this change and to draft this description.
