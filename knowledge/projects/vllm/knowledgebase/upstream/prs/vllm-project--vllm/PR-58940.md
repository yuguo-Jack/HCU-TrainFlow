# Check nested JSON schemas in structural_tag for xgrammar support

[Upstream PR](https://github.com/vllm-project/vllm/pull/58940) · state: open · merged: False

## Original PR description

## Summary

Fixes #58930.

`validate_xgrammar_grammar()` skipped the unsupported-feature check for JSON schemas nested inside a `structural_tag`, while the plain `json` branch rejects them. xgrammar silently drops keywords such as `multipleOf` when compiling a structural tag, so a tag whose nested schema used them validated successfully and `backend="auto"` never fell back — the model could emit schema-violating values with no error.

This PR extracts the nested schemas from both structural tag shapes (legacy `structures`/`triggers` and the new `format` — including the deprecated `qwen_xml_parameter` node type, which embeds its schema directly) and runs the same `has_xgrammar_unsupported_json_features()` check on them. Behavior:

- **explicit `xgrammar` mode** rejects the request with an informative error;
- **`backend="auto"` + legacy-shaped tag** falls back to the guidance backend, like plain `json` schemas already do;
- **`backend="auto"` + new-style tag** fails with a clear error explaining that no backend can enforce the constraint (instead of being served with a silently wrong grammar, or dying with a misleading `KeyError: 'triggers'` / "Invalid grammar specification" inside the guidance serializer).

Request-level validation (`validate_structural_tag_payload`) deliberately does *not* reject well-formed tags for unsupported features: at request-parse time no backend fallback is possible, so rejecting there would make the fallback unreachable from the OpenAI API. Malformed tags are still rejected as bad requests. The guidance serializer now also reports new-style tags with a clear error instead of `KeyError`.

## Duplicate check

No existing PR addresses this: #57788 covers `$ref` cycles and #56753 covers `allOf`; both are unrelated to structural tags. A search for PRs referencing #58930 returned none.

## Notes

- The new exception subclasses `VLLMValidationError`, so every existing `except VLLMValidationError` handler behaves exactly as before.
- The guidance backend intentionally still does not *compile* new-style structural tags — only the legacy `structures`/`triggers` shape — matching main's capability; this PR only makes that limitation fail clearly instead of via `KeyError`.

@vadiklyutiy Thank you for the careful review — all four points are addressed in this rework:

1. **HTTP path / unreachable fallback**: the request-parse-time check (`validate_structural_tag_payload`) no longer rejects well-formed tags whose nested schemas use features xgrammar doesn't support, since no backend fallback can happen at parse time. The engine's `auto` selection now handles the fallback, which is reachable from the OpenAI API again. Malformed tags are still rejected at parse time.

2. **Guidance-backed servers**: same root cause — those requests are accepted again, and legacy-shaped tags with unsupported features actually fall back to guidance instead of being served by xgrammar with silently-dropped constraints.

3. **Strict tools / Harmony**: the new-style tag path no longer dies with `KeyError: 'triggers'` inside the guidance serializer (previously surfaced as the misleading "Invalid grammar specification"). Since no backend can enforce constraints on a new-style tag with unsupported features, `auto` mode now raises a clear error saying exactly that — what to remove, and that the legacy shape is the one that falls back to guidance.

4. **`qwen_xml_parameter`**: fixed — the traversal now collects `json_schema` from both `json_schema` and `qwen_xml_parameter` format nodes (the deprecated xgrammar node type that embeds the schema directly).

The PR description now describes the actual behavior, and the tests assert it — including that request-parse-time validation does *not* reject unsupported-feature tags. Thanks again for the thorough review.
