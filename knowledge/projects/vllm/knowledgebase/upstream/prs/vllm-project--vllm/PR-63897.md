# [Distributed] Allow a plugin to provide the PP GroupCoordinator

[Upstream PR](https://github.com/vllm-project/vllm/pull/63897) · state: open · merged: False

## Original PR description



## Overview

Part of #63818 (RFC: pluggable PP transport), Phase 1. Adds `--pp-group-cls`, which lets a plugin supply the `GroupCoordinator` of the pipeline-parallel group, and routes the V2 model runner's sampled-token broadcast through that group (`sibling_broadcast`), so a plugin can carry all PP traffic over its own transport.

## Claims

- `ParallelConfig.pp_group_cls` / `--pp-group-cls <qualname>`: `initialize_model_parallel` constructs the PP group with this `GroupCoordinator` subclass (same arguments); TP/DP/EP/PCP/DCP groups are unchanged. Default `""` keeps `GroupCoordinator`; a name that is not a subclass fails at startup. Same pattern as `--worker-cls`.
- `GroupCoordinator.sibling_broadcast(tensor, src, group)`: `PPHandler` (MRV2) now issues its sampled-token / draft broadcasts through it instead of calling `torch.distributed.broadcast` directly. The default implementation is that same call, so there is no behaviour change; a PP group class overrides it together with `make_sibling_device_group`.
- With these two, an out-of-tree PP group (here: UCX via connex-rs) serves Llama-3-8B with PP=2 and PP=4 on vLLM main with the default V2 model runner, greedy outputs pass a teacher-forced check, and latency/throughput are within a few percent of NCCL (numbers below).

The NCCL rows are vLLM main unchanged (the flag is not set); NCCL path numbers are not affected by this PR (the default `sibling_broadcast` is the old call).

## Details

- Why a class name and not a registry: it mirrors `--worker-cls` / `--worker-extension-cls`; plugins only need to be importable. If #50853 lands a `PPTransport` owner, this flag can select that class instead.
- Why `sibling_broadcast` is needed: with MRV2, PP traffic is not only `isend/irecv_tensor_dict`; the last rank broadcasts sampled tokens on a sibling NCCL communicator. Without the hook a plugin that replaces the transport still needs NCCL for this, which defeats the purpose (e.g. stages that are not in one NCCL communicator).
- The plugin used above, for reference only (not part of this PR): https://github.com/HeterInfra/connex, `connex/adapters/vllm/pp`. Its receive path makes the CUDA stream wait for a host flag (`cuStreamWaitValue32`), which keeps the CPU of the receiving stage off the critical path like a NCCL receive.
- Not a duplicate: open PRs touching PP communication change the in-tree transport or the MRV2 PP schedule; none makes the PP group replaceable (searched `#63818`, "pp-group-cls", "pipeline parallel GroupCoordinator plugin").
- Follow-ups in the RFC: running each stage as its own instance (`--pipeline-stage-rank`, separate PR stacked on this one) and recomputing requests whose KV was lost on a replaced stage (separate PR).

Update on the numbers in the description (no code change in this PR).

The plugin now moves same-host stage-to-stage traffic over CUDA IPC with `cuStreamWaitValue32` / `cuStreamWriteValue32` on shared pinned flags, so nothing on the data path runs in Python, as with NCCL. Cross-host hops stay RDMA. Re-measured on 4x A40 (PCIe), Llama-3-8B, 3 runs per cell (mean ± std), median TPOT ms:

| | C=1 NCCL | C=1 plugin | C=8 NCCL | C=8 plugin | C=32 NCCL | C=32 plugin |
|---|---|---|---|---|---|---|
| PP=2 | 28.24 ±0.00 | 28.23 ±0.01 | 33.03 ±0.43 | 32.94 ±0.07 | 41.55 ±1.24 | 40.65 ±1.35 |
| PP=4 | 28.33 ±0.00 | 28.35 ±0.00 | 32.77 ±1.90 | 31.93 ±1.60 | 40.21 ±1.10 | 40.20 ±0.19 |
| PP=2 x TP=2 | 15.53 ±0.00 | 15.51 ±0.01 | 17.62 ±0.17 | 17.76 ±0.09 | 22.87 ±0.10 | 23.20 ±0.38 |

Within run-to-run noise in every cell (the single runs in the description, over RDMA loopback, were 2-4% slower at C=1). Two hosts (RDMA, 3 runs): C=1 28.28 vs 28.94 ms, p99 TPOT 28.28 vs 29.08 ms; C=32 41.00 vs 41.87 ms.

Per hop, same `isend/irecv_tensor_dict` calls, one host, 3 runs: 32 MB 1.54 ±0.00 ms (NCCL) vs 0.80 ±0.04 ms (plugin); 16 KB 0.41 ±0.01 vs 0.52 ±0.12 ms (the plugin's small-message latency is noisy, Python on the control path).

One design note relevant to this API: a stream wait that only a Python thread of the same process can release deadlocks against CUDA calls that hold the GIL and synchronize the device (a first Triton kernel load does). The plugin avoids it on one host by having the sender's GPU release the receiver's waits. Across hosts the waits are still released by a Python thread, so the risk remains there outside warmup (where it waits on the CPU instead).
