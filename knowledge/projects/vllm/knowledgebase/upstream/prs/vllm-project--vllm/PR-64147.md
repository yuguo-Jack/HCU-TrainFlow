# [Perf][DSv4.1] Pin the low-latency MXFP8 GEMM tactics at TP8 and without autotuning

[Upstream PR](https://github.com/vllm-project/vllm/pull/64147) · state: open · merged: False

## Original PR description



## Overview

Pin the specialized decode's low-latency MXFP8 GEMM tactics for TP8 too, and use the pins without autotuning. **Stacked on #64146 and #64144** (their commits are included; please review only the last commit).

## Claims

- The pins are keyed by (N, K, TP), and the TP8 shapes are added.
- The pinned tactic now goes first in FlashInfer's tactic list for good. So the untuned runner (`enable_flashinfer_autotune: false`) and the publishing `wo_b` GEMM use it too, instead of FlashInfer's generic first tactic.
- TP8 over two GB300 trays, DSpark, autotuning off: one request's decode step **3,926 → 3,834 µs (+2.4 % tok/s)**.

## Validation

- `test_kernels.py::test_low_latency_mxfp8_mm` and the new `test_pinned_tactics_by_tensor_parallel_size` pass on GB300 (vLLM nightly `5d35ce39`, FlashInfer 0.7.2.post1).
- A TP8 serve with this stack starts and answers correctly.
- Step time: 5–8 requests per variant, same trays, with our deployment's patch set (`c50aca1` + #61869 + these PRs). Tetris single request: 1,500 ± 36 → 1,543 ± 79 tok/s.

## Details

- Without autotuning, FlashInfer's runner takes the first tactic in the list: one CTA per 128 output columns. At TP8 that is 14 CTAs for `fused_wqa_wkv` (N=1792) and 32 for `wq_b` (N=4096).
- Autotuning across two trays is slow, because of the cross-rank tuning sync. And split-K tactics tuned in isolation are slower inside the decode step's PDL chain, which is why the pins exist in the first place.
- `fused_wqa_wkv` is replicated, so at TP8 it has the same shape as at TP4. It pins split-K 2 there instead of 4. `wq_b` and `wo_b` halve.
- If FlashInfer does not list a pinned tactic, the order is unchanged and it falls back to tuning or its default as before.
- #63921 re-keys the TP4 pins per row bucket. Whichever lands second will merge the two tables.
