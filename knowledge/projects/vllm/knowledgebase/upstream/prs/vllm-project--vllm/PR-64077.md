# [Perf] Muse Spark Open Specialized Decode: Optimized GB300 Decode (1.5x)

[Upstream PR](https://github.com/vllm-project/vllm/pull/64077) · state: closed · merged: True

## Original PR description

## Overview

This is an NVIDIA-developed specialized decode of Muse Spark Open (NVFP4, DSpark speculative decoding) for GB300 that gives 1.5x single-stream decode throughput, in the form of the Kimi K3 specialized decode (#61867).

- Tensor parallel 4, 8 or 16 with expert parallelism (EP = TP); at TP8 the routed experts run tensor-parallel inside the executor.
- DSpark verification with 7 draft tokens, including the draft model's forward and its Markov sampling loop.
- Any context length up to `--max-model-len`, including sliding-window layers.

It is opt-in with `--additional-config '{"decode_backend": "latency_specialized"}'`; the default, `auto`, keeps the stock decode. Changes are localized to `vllm/models/muse_spark/` (the executor in `nvidia/specialized_decode/`, the model hooks, and the DSpark draft model, which implements the speculator's `sample_sequential` hook) plus three CUDA C ops in `csrc/muse_spark/` and their registration (`CMakeLists.txt`, `csrc/ops.h`, `csrc/torch_bindings.cpp`, `vllm/_custom_ops.py`, additions only). No other shared vLLM code changes.

## Claims

Single-stream decode (ISL 1, OSL 1000, concurrency 1, DSpark K 7 with forced acceptance length 6) on GB300 NVL72 trays, ours and stock vLLM on one allocation per row:

- **TP8+EP8: 1.53x** (698.60 -> 1072.14 tok/s/user)
- **gsm8k matches stock** within one standard error at TP8+EP8 (1253 vs 1255 of 1319).

## Details

### vLLM Integration

The Muse Spark model builds a `SpecializedDecode` after its weights load (`nvidia/model_state.py`, using the ModelState protocol and `initialize_kv_cache()` as #61867 does) and calls it from `forward()`. It serves the verify step of one request (1 + 7 draft tokens) captured into FULL CUDA graphs; when `plan()` returns None (prefill, mixed batches, several requests, partial drafts, eager or PIECEWISE steps) the stock forward runs. `unsupported()` checks the deployment at startup and names the first requirement it fails. The lm_head, `compute_logits` and the attention backend's metadata and KV cache stay shared.

The executor runs, per layer, the input boundary, the attention (fused QKV + QK-norm + RoPE + KV insert, decode attention fused with the output norm and gate, o_proj), the attention boundary and the MoE (FP32 router, routing that also writes the routed experts' metadata, pooler GEMM with a fused all-gather + norm + NVFP4 quantization, the TRT-LLM-gen routed experts, finalize, unpooler GEMM), each block a provider in `specialized_decode/runtime/`. The fused all-reduce boundaries sum in the order of the stock FlashInfer all-reduce backend the deployment resolves (MNNVL or TRT-LLM), so TP4 needs vLLM's FlashInfer all-reduce. The draft model runs its forward and, through the DSpark speculator's `sample_sequential` hook, the Markov loop over a vocab-parallel Markov head (`runtime/draft.py`, `runtime/markov.py`).

Kernels are in `specialized_decode/cutedsl/` (CuTe DSL) and `csrc/muse_spark/` (CUDA C: the QKV front, the decode attention and the routing). FlashInfer is used only from `runtime/flashinfer_ops.py`: the public routed experts ops, and on NVFP4 layers the runner below the public op, fed by the package's routing metadata, with the expert-TP tactic pinned per trtllm-gen cubin package (the op's default under any other). Kernels that reuse FlashInfer code are adapted from its source at a public sha, each header carrying the Apache-2.0 notice.

Unit and kernel tests are kept out of this PR, as in #61867 (available on request; 2735 passed on one GB300 tray).
