# [Bugfix] Require cudnn-frontend >=1.31.0: cuDNN could replay an unloaded kernel from a CUDA graph

[Upstream PR](https://github.com/vllm-project/vllm/pull/61465) · state: closed · merged: True

## Original PR description

## Purpose

Raise the `nvidia-cudnn-frontend` floor in `requirements/cuda.txt` from
`1.19.1` to `1.31.0`, the first release containing
[NVIDIA/cudnn-frontend#1195](https://github.com/NVIDIA/cudnn-frontend/pull/1195),
"Keep execution plans alive for the CUDA graphs recorded from them".

Before that fix, cuDNN could unload a just-in-time compiled kernel's library
when the last cuDNN owner of it went away, while a CUDA graph still contained
a node that launched that kernel. Replaying the graph then dispatched whatever
had taken over that code address. The upstream fix makes the graph hold a
reference for as long as it can launch the kernel.

The affected `vllm/vllm-openai:v0.29.0-ubuntu2404` stack has both conditions:

- `FlashInferFP8ScaledMMLinearKernel` is first in `_POSSIBLE_FP8_KERNELS` for
  CUDA and calls `bmm_fp8(..., backend="auto")`. Because
  `requirements/cuda.txt` declares `nvidia-cudnn-frontend`, the `cudnn` module
  is importable and `auto` admits the cuDNN runner.
- FlashInfer memoises those cuDNN graphs in
  `functools.lru_cache(maxsize=2048)`, keyed per shape, and the cache evicts
  cold entries. The GEMMs themselves are captured into the decode CUDA graphs.

In that stack, an eviction can release the last owner of a kernel that a live decode graph
still launches. The observable outcomes are an illegal-address fault, a CUDA
error reported at synchronisation, or — the case that matters most for a
serving stack — **silently wrong output with no error reported at all**.

FlashInfer 0.7.2, pinned by the tested base, now has a
[capture-retention helper](https://github.com/flashinfer-ai/flashinfer/blob/v0.7.2/flashinfer/gemm/gemm_base.py#L3761-L3774)
that keeps captured cuDNN GEMM graphs alive for the process lifetime. This
separately mitigates the GEMM eviction path on current `main`. The frontend
floor still ensures that cudnn-frontend's own CUDA-graph lifetime fix is
installed.

## What this fixes

| Issue | Verdict | Note |
|---|---|---|
| #52225 | root cause identified directly | The investigation that led here, and the attribution is not statistical. A GPU coredump and CUDA-GDB independently confirmed the faulting kernel as `cudnn_generated_fort_native_sm80_matMul_pointwise_pointwise_knob_0_256x128x128_3_0`, launched with block (384,1,1) against a cubin declaring a 256-thread launch bound and 246 registers — the instruction-issue rejection that reports as Xid 13 `Out Of Range Register`. In the retained fault run, the cuDNN LRU eviction destroying a cold captured graph's plans and runtime kernels was observed directly, 436 µs after a newly compiled graph of a different shape, with the evicted kernel's CUDA graph node still live and no host launch since its capture 66 minutes earlier. A source audit confirmed no graph retention existed in the deployed cuDNN. That is the mechanism this fix removes. |
| #55571 | likely fixed | A third-party report, so the attribution is indirect: no coredump of their fault was analysed and no run on their hardware used the fixed wheel. What makes it strong is that *either* `VLLM_DISABLED_KERNELS=FlashInferFP8ScaledMMLinearKernel` *or* `--enforce-eager` reportedly makes it go away, and those remove exactly the two conditions this defect needs — the cuDNN lane, and CUDA graph capture. |

Deliberately **not** claimed:

- **#61007** (GB10 hang inside a cuDNN FP8 GEMM) is the same lane but a
  different failure: an unbounded host-side hang while cuDNN builds a plan
  lazily per shape in the hot path. This change does not address plan
  construction cost. #57209 is the change aimed at that.
- **#61069, #60119, #59768, #49926** share the Xid 13 or illegal-access
  symptom class but implicate other kernel families, and in #60119's case the
  report itself declines to claim a common root cause. No evidence either way.

## Relationship to #57209

[#57209](https://github.com/vllm-project/vllm/pull/57209) pins `bmm_fp8` to
cuBLAS on sm_12x, avoiding the cuDNN lane. This PR fixes the lane instead, by
taking the upstream fix, and is not an alternative proposal to it: #57209 also
cites host-side plan-construction latency in the serving hot path, which a
frontend bump does not change. If #57209 lands, this bump still matters for
every other cuDNN consumer reached through cudnn-frontend — the
`flashinfer_cudnn` NVFP4 linear backend and the cuDNN ViT and multimodal
encoder attention paths — and for sm_100 and sm_121, which #57209 does not
cover.

## Why the frontend and not the backend

Both upstream fixes work and each is sufficient alone: cuDNN 9.27.0.42 fixes it
for every caller including torch's own, while the frontend fix covers
cudnn-frontend consumers only.

In fairness to upstream, they consider the backend the thorough fix and the
frontend a workaround, and the frontend fix retains the whole `ExecutionPlan`
where the backend retains only the kernel code — so it holds more memory per
plan captured into a live graph. That cost is not quantified here.

The frontend is still the right change *for vLLM*: vLLM already declares a
floor for it and this is one line, whereas pinning `nvidia-cudnn-cu13` would
override the cuDNN version torch resolves transitively. Upstream chose to
write the frontend fix for exactly this reason — so that frameworks could pick
it up without waiting on a backend upgrade — and it is the vehicle they
offered for this report.

The consequence is stated plainly: cuDNN callers that do not go through
cudnn-frontend are unaffected by this PR. In vLLM that means torch
convolutions (`vllm/model_executor/layers/conv.py`) and torch's
`SDPBackend.CUDNN_ATTENTION` (`phi4mm_utils.py`). Those are fixed when torch's
transitive cuDNN pin reaches 9.27.0.42, which is the right lever for them; they
are not known to be affected today. If maintainers would rather take the
thorough fix, the backend pin is the alternative and I am happy to switch —
but it should be one or the other, since applying both creates two user
objects for the same kernel.

Upstream has already commented on #52225 pointing at the frontend fix:
<https://github.com/vllm-project/vllm/issues/52225#issuecomment-5900569717>.

Hardware: RTX PRO 6000 Blackwell Server Edition (sm_120), driver 580.126.20.

**Frontend fix, either side of the upstream merge commit**, with the backend
wheel as a second axis — 96 cells each side across backends 9.19.0.56 through
9.26.0.51, varying graph construction, workload profile, kernel-cache size and
owner-lifetime arm:

| frontend | reproducing cells |
|---|---|
| `07c939a6cce4` (pre-fix) | 22 of 96 |
| `4d4e428bd747` (PR #1195) | **0 of 96** |

Every reproducing cell is in the arm that releases the owner. The paired
`retain` and `user-object` arms are clean on both sides, which is what makes
this a comparison rather than an absence of failure.

**Backend fix on the public wheel**, with the pre-fix frontend held fixed so
the wheel is the only variable, run control-first within each configuration:

| configuration | 9.20.0.48 | 9.27.0.42 |
|---|---|---|
| populate, cache default/off, release | `SIGSEGV` | clean |
| stream capture, cache default/off, release | CUDA error 718, invalid program counter | clean |
| profile 52225, cache default/off, release | **3,948,544 of 5,275,648 elements wrong, 2,637,824 non-finite, `sync_status=0`** | clean, 0 mismatches |
| all six of the above, retain arm | clean | clean |

The wrong-result rows report no error to the host. The 9.27.0.42 release notes
carry the matching entry: "Runtime-compiled kernel code now stays loaded for
as long as a CUDA graph can launch it."

**The fix is in the binary vLLM actually imports.** vLLM reaches cuDNN through
FlashInfer's `import cudnn`, the compiled module in the wheel, not through
headers:

| wheel | `cuda_graph_retention.h` | retention symbols in `_compiled_module*.so` |
|---|---|---|
| 1.30.0 | absent | 0 |
| 1.31.0 | present | 41 |

**Cost**, measured on the stock `vllm/vllm-openai:v0.29.0-ubuntu2404` image
with only the frontend wheel swapped, three repetitions per arm, medians:

| measurement | 1.28.0 | 1.31.0 |
|---|---|---|
| CUDA graph replay | 45.04 µs | 45.04 µs |
| CUDA graph capture | 192.0 µs | 229.1 µs |
| plan build | 7655 µs | 7710 µs |
| max relative error vs cuBLAS | 0.000000 | 0.000000 |

Replay is unchanged, so the steady-state decode path pays nothing. Capture
costs about 37 µs more, once per captured graph at warmup, and the capture
ranges do not overlap across repetitions. The plan-build difference is within
noise at three samples. Numerics are unchanged against the cuBLAS backend.

Eager execution, measured separately because the cost might not be specific to
graphs — per-call host time with GPU work left asynchronous, two repetitions of
seven rounds — shows no regression either: 1.31.0 medians 95.80 and 94.88 µs
against 1.28.0's noisier 112.10 and 95.34 µs, with overlapping ranges.

One nuance for anyone assessing exposure: from backend 9.22 onward the pre-fix
frontend stops reproducing at the default kernel-cache size and still
reproduces with the cache disabled, because the cache was holding a second
reference. Backend version alone therefore does not tell you whether a
deployment is exposed.

Note also that `vllm/vllm-openai:v0.29.0` resolves cudnn-frontend **1.28.0**
against the declared floor of 1.19.1, so the effective bump for that image is
1.28.0 → 1.31.0.

## Not measured

- **No end-to-end serving before-and-after with the released wheel.** The
  mechanism is directly established and the fix is verified on the
  deterministic reproducer, but the remaining step — serving the affected
  model at full exposure on the released wheel and showing the fault rate go
  to zero — is a multi-hour stochastic measurement and is not included. An
  earlier run with both fixes built from source did not reproduce the bug on
  Nemotron-3.5-Lightning-30B-A3B-NVFP4.
- **Read the lane ablation carefully if you cite it.** Disabling the
  FlashInfer FP8 class gave 7 of 12 against 0 of 12 at p≈0.0023 on the
  *family* endpoint (any `0x0d`/`0x0e`/`0x0f` fault in a cuDNN matMul); on the
  exact `0x0d` subtype alone it is 1 of 12 against 0 of 12, p=0.5 and
  uninformative. It corroborates that the lane is necessary; it is not the
  basis for the root-cause attribution, which is the coredump evidence above.
- **A Python-level reproduction was attempted and failed to fault its own
  control**, so it proves nothing in either direction and is not offered as
  evidence. The deterministic reproducer pins the engine and kernel config for
  both the target and the reoccupying donor, and FlashInfer's Python API
  exposes no way to select either.
- **The memory retained by the frontend fix is not quantified.** It keeps the
  whole execution plan alive per plan captured into a live graph, where the
  backend fix keeps only the kernel code.
- **No specific models are claimed as fixed.** There are internal reports that
  the backend upgrade resolved corruption for some FP8 Nemotron checkpoints,
  but they are soak observations without a paired control, so they are not
  offered here as evidence.
- The plan-build cost difference and cuDNN 9.28's expected opt-out are
  unresolved here.
