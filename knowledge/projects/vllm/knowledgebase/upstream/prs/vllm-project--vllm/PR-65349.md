# [Perf] Warm up JIT kernels that only long prefills, eager drafters and constrained decoding reach

[Upstream PR](https://github.com/vllm-project/vllm/pull/65349) · state: open · merged: False

## Original PR description

## Overview

Warm up JIT kernels that are currently compiled lazily, on live traffic: the FA4 MLA split-KV combine, the DCP all-to-all fallback pack/unpack kernels, Triton MLA decode for eager-only (e.g. draft) layers, and the xgrammar bitmask kernel in the V1 sampler warmup. Motivated by ML4 on Blackwell, where the first long prefill after a pod becomes ready stalled for seconds on JIT compilation.

## Why this is not duplicating an existing PR

Searched open PRs in `vllm-project/vllm` for warmup-related work; none covers these kernels:
- #62015 ("Signature-driven JIT warmup") is a generic framework draft, orthogonal.
- #64134 fixes FA4 SM90 prefill warmup for Gemma-4, not MLA layer-config coverage or the split-KV combine.
- Various per-model warmup PRs (Hi V4, DSv4, ROCm backends) target different kernels.

## Claims

- FA4 MLA prefill warmup now covers every distinct layer config (sliding-window layers, NoPE layers, drafters with their own head count), not just the target model's full-attention config.
- The FA4 split-KV combine kernel is compiled at startup with the runtime compile key (varlen, `num_splits_dynamic_ptr`), which compile-only forward warmup never reaches. On cold-cache Blackwell pods this removes a first-long-prefill stall measured in the low single-digit seconds per rank.
- The DCP NCCL all-to-all fallback (pack/unpack Triton kernels + lazy NCCL communicator creation) is warmed with a real combine at startup instead of firing on the first overshoot of the direct symmetric-memory workspace.
- Triton MLA decode kernels are warmed for layers that never run under CUDA graph capture (e.g. an EAGLE drafter), across both `seq_lens` dtypes and both MLA/non-MLA tilings.
- The xgrammar bitmask kernel is warmed in the V1 `_dummy_sampler_run` (V1 currently compiles it on the first constrained request; V2 already warms it).

## Details

- `FA4MLAPrefillKernel.get_warmup_keys` gains an optional `layer_configs` argument and traces layer configs as a second `zip_inputs` row group (existing `_trace_dispatch` supports multiple groups); `_is_valid_warmup_shape_probe` now requires causality for sliding-window probes. Defaults preserve the current behavior exactly.
- `FA4MLAPrefillKernel.compile_many` now warms the split-KV combine from its own key set via `_flash_attn_fwd_combine` under `FakeTensorMode` (same technique the dense-FA4 warmup already uses in `vllm/v1/attention/backends/flash_attn.py`), passing the runtime flag set: varlen `cu_seqlens`, scheduler-metadata `num_splits_dynamic_ptr`, no `seqused`/`virtual_batch_idx`. Because it lives in `compile_many`, the registry's default registration and the per-layer sweep take the same path. Auto-split workers keep `ceil(log2(num_splits))` at the kernel's floor of 5, so no extra split buckets are compiled.
- The DCP warmup runs one real `dcp_manager.combine` per (num_heads, kv_lora_rank, dtype, lse-mode) layer config at `max_num_workspace_tokens + 1` tokens, which forces the NCCL fallback path, and one call per distinct (Triton int class, next-power-of-2) `num_seqs` bucket, `max_num_seqs` bounded. It runs only under `enable_jit_warmup`, after the `process_local_only` phase, and must be reached by every DCP rank (it is a collective).
- The Triton MLA decode warmup mirrors `MLAAttention.forward_impl`, including the uint8->fp8 cache view, and skips zero-initialized caches. `sliding_window` was dropped from the compile key relative to the internal port: upstream `TritonMLAImpl` rejects sliding windows, so the term is constant.
- The grammar bitmask warmup covers the row-count specialization classes (1 / generic / multiple-of-16) and both `indices=None` (all rows structured) and explicit-indices variants used by `apply_grammar_bitmask`.
- Fork-only items in the internal PR were deliberately not ported: the MLA SWA scatter warmup (`triton_swa_scatter_combined` is a fork-only kernel) and its `do_not_specialize` change.
