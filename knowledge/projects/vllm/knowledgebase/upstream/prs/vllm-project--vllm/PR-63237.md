# [Refactor][R3] Initialize routed experts capturer before KV cache profiling

[Upstream PR](https://github.com/vllm-project/vllm/pull/63237) · state: closed · merged: True

## Original PR description

## Overview

Allocate R3 capture buffers in the V2 runner's `profile_run()`, before KV-cache memory profiling and outside the weights memory pool. Adopt the minimal two-phase connector initialization from [aoshen02/vllm#189](https://github.com/aoshen02/vllm/pull/189).

## Claims

- Create the AuxOutput connector and bind the capturer during profiling so automatic KV budgeting includes the persistent capture buffers and any monolithic routing sinks.
- Defer output storage until the resolved KV configuration is available, using `initialize_output_storage(kv_cache_config)` on the output TP rank. Retain connector construction as a fallback when normal profiling was skipped.
- Bump the Startup Plan schema to invalidate budgets recorded before this allocation moved into profiling.
- Keep GPUWorker, capturer binding, shutdown, and the existing R3 data-transfer paths unchanged from main. `profile_run()` creates the connector whenever aux output is enabled; this change does not guarantee repeated profiling is idempotent.

## Details

Previously `initialize_kv_cache()` constructed the connector after `determine_available_memory()` had fixed the automatic KV budget. The connector allocated persistent R3 GPU buffers too late to be accounted for.

The connector constructor now accepts the model and vLLM configuration, allocates the capturer and binds routing callbacks. Real KV initialization reuses that connector and calls `initialize_output_storage()` with the resolved layout; profiling KV initialization does not build the output data plane. Only the output TP rank builds the store and request buffer. The runner keeps the `None` fallback for initialization paths that skip normal profiling.

Production changes are limited to `gpu/model_runner.py`, `aux_output_connector/worker.py` and `startup_plan.py`. The earlier load-model initialization, ownership/unbind/rollback mechanisms and shutdown reordering have been removed. R3 SHM, prefix-cache, snapshots, asynchronous D2H and request-state behavior are unchanged.

Capture allocations remain resident outside the sleep allocator's weights/KV pools. Explicit `kv_cache_memory_bytes` remains a manual budget and is not automatically reduced.

This updates the existing upstream PR and incorporates all three commits from aoshen02/vllm#189, retaining cherry-pick provenance. It does not create a competing upstream PR. AI assistance was used for implementation, checks and preparation. Full runtime/GPU validation and human review remain outstanding before merge.

### KV-cache budget delta (end-to-end)

Same tiny model, `max_num_batched_tokens=131072`, eager, R3 off vs on:

| Run | `num_gpu_blocks` | block size | KV cache |
|---|---:|---:|---:|
| R3 off | 4,519,296 | 16 | 68.96 GiB |
| R3 on | 4,518,016 | 16 | 68.94 GiB |
| **delta** | **1,280 blocks** | | **20 MiB** |

1,280 blocks x 16 KiB = 20 MiB. The capturer buffer itself is `131072 x 2 layers x 2 top-k x 4 B = 2 MiB`; the measured 20 MiB is PyTorch's caching-allocator large-pool segment (`kLargeBuffer = 20 MiB`) backing that allocation. The point of the test is that the allocation made before profiling is charged to non-KV memory, and `num_gpu_blocks` decreases accordingly. With `max_num_batched_tokens=8192` the same buffer fits in an existing allocator segment and the delta is hidden by 2 MiB block-count alignment, which is why the larger token budget was used.

### Why the ownership marker is no longer needed

The lower-level binding function is not the duplicate-prevention boundary:

1. `GPUWorker.load_model()` rejects a runner that already owns a connector before entering the weights pool.
2. `AuxOutputWorkerConnector.initialize_routed_experts_capturer()` is idempotent via `_capturer is not None`.
3. Weight reload, sleep/wake, and graph replay never call the binding function again.
4. Normal execution creates exactly one connector per model runner.

The marker only guarded direct repeated calls to `bind_routed_experts_capturer()`, which is outside this PR's supported API. That constraint is now documented at the function instead of enforced by a second ownership registry.

### `partial` equivalence

`partial(capturer.capture, layer_id)(topk_ids)` calls the same bound method with the same positional arguments as the old closure: `capturer.capture(layer_id, topk_ids)`. The same `partial` object is stored in `bindings` and installed on the target, so identity-based restore still identifies exactly this binding. No custom attributes are needed.

All three paths use it directly:

- Direct `RoutedExpertsCaptureSource`: appended inline.
- `BaseRouter`: `capture_fn = partial(...)`, then `set_capture_fn`.
- Monolithic MoE: `capture_fn = partial(...)` passed to `RoutedExpertsSink`.

### Explicit usage constraint

`bind_routed_experts_capturer()` does **not** support two active capturers nested on one model. Callers must unbind the current binding before binding another. Binding B over A would install B's callbacks; unbinding A then skips the replaced targets by identity, and unbinding B restores A's callbacks. Normal Worker/Connector paths cannot reach this state.
