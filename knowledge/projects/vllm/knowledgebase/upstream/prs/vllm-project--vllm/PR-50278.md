# [LoRA] Fix FP8 shrink batch invariance and document shrink determinism

[Upstream PR](https://github.com/vllm-project/vllm/pull/50278) · state: open · merged: False

## Original PR description

## Summary

Addresses #50059 while preserving the default Punica shrink behavior and tuned
configs.

Following [the earlier review](https://github.com/vllm-project/vllm/pull/50278#pullrequestreview-4833409319), I restored the default `split_k` selection and `VLLM_TUNED_CONFIG_FOLDER` behavior. The PR now documents why split-K shrink can be non-deterministic and adds W4A16 all-layer LoRA regression coverage for the batch-invariant path from #59377.

While validating that path, I found a separate FP8 gap: batch-invariant shrink
still changed `BLOCK_K` from 256 to 32 at 128 tokens. Block-wise FP8 scales are
applied per K tile, so the same input row produced different output across that
boundary. This revision fixes the batch-invariant FP8 config at `BLOCK_K=32`.

## Changes

- `vllm/lora/ops/triton_ops/utils.py`
  - Keep FP8 shrink at `BLOCK_K=32` in batch-invariant mode.
- `vllm/lora/ops/triton_ops/README_TUNING.md`
  - Document split-K non-determinism and the supported deterministic options.
- `tests/v1/determinism/test_lora_shrink_batch_invariant.py`
  - Add block-wise FP8 coverage across 31–129 tokens.
- `tests/v1/determinism/test_lora_w4a16_batch_invariant.py`
  - Add W4A16 all-layer LoRA coverage for ranks 8, 16, and 32, repeated
    requests, and engine restarts.

## Test results

Direct FP8 kernel reproduction on Hopper (96GB HBM), PyTorch 2.11/cu129:

- Before: the same row changed at 128 and 129 tokens. All 16 outputs differed,
  with maximum absolute difference `2.3324`.
- After: the row was bit-exact at 31, 32, 33, 127, 128, and 129 tokens.
- `test_lora_shrink_batch_invariant.py`: 7 passed.
- `test_lora_w4a16_batch_invariant.py`: 6 passed, covering ranks 8, 16, and
  32 across repeated requests and engine restarts.

My reading of #50602 so far:

2. Custom single-writer Triton/CUDA interiors, and even feeding `.clone()` snapshots of `x` / LoRA weights / token-mapping, still flip → that weakens “racy reads of the LoRA inputs” as the remaining root cause.
3.
