# [ROCm][Perf] Fuse Gemma add+RMSNorm into the AITER MXFP4 GEMM's activation quant

[Upstream PR](https://github.com/vllm-project/vllm/pull/61902) · state: open · merged: False

## Original PR description



## Overview

Fuse the Gemma add+RMSNorm in front of an AITER asm MXFP4 GEMM into the GEMM's activation quant (one kernel instead of a norm kernel plus a separate HIP quant kernel), opt-in on gfx950, for the two norms of a decoder layer: the post-attention norm that feeds the MLP's gate_up (`VLLM_ROCM_AITER_FP4_POSTNORM_QUANT_FUSION`) and the input norm that starts the layer (`VLLM_ROCM_AITER_FP4_INPUTNORM_QUANT_FUSION`). An input norm whose output feeds two GEMMs (a gated delta net layer: `in_proj_qkvz` and `in_proj_ba`) is quantized once, and both GEMMs take the same codes and scales; the GEMMs quantized the same tensor twice before. Builds on #59153 (its commit is the first commit of this PR, unchanged); the PR also puts that pass behind an env flag and adds a start-up check that a fusion flag that is on really rewrote the target model.

Not a duplicate: #59153 fuses the activation (SiLU/GELU+Mul) before the down projection on the same asm path; #59610 folds RMSNorm and SiLU+Mul into the MXFP4 quant on the Triton `afp4wfp4` path with `fused_rms_mxfp4_quant` (plain RMSNorm, measured on Llama-3.1-8B); #59483 and #59553 fuse the quant into AR+RMSNorm and into the GDN gated RMSNorm. This PR adds the add+Gemma-RMSNorm into the asm GEMM, with AITER's `add_rmsnorm_quant`. The files overlap with #59610 (`mxfp4/aiter.py`, `rocm_aiter_fusion.py`, `_aiter_ops.py`); both PRs conflict with #59153 in `mxfp4/aiter.py` in the same place, and I will rebase on whichever lands first.

## Details

**The fusion.** On the asm path the MXFP4 linear quantizes its input inside the `gemm_with_dynamic_quant` custom op, so Inductor cannot fuse the norm into it. The new op `rocm_aiter_rmsnorm_mxfp4_quant(x, residual, weight, epsilon)` calls AITER's `add_rmsnorm_quant` and returns the MXFP4 codes, the shuffled e8m0 scales and the residual output; the GEMM takes the codes and scales through its existing `x_scales` argument. The pass `RocmAiterRMSNormMxfp4GemmFusionPass` rewrites `fused_add_rms_norm -> gemm_with_dynamic_quant` (asm path) into the op plus that GEMM(s). It is built once per enabled flag: `sites="post"` takes the post-attention norm of each decoder layer (one GEMM, gate_up), `sites="input"` takes the input norm that starts a layer, so each flag is judged and logged on its own and both flags together give two passes. The two kinds look the same by shape; the pass tells them apart by where the residual comes from, which needs the graph split at the attention ops, and refuses to be built without that split.

**The shared quantization.** An input norm feeds one GEMM in a full-attention layer (`qkv_proj`) and two in a gated delta net layer (`in_proj_qkvz`, `in_proj_ba`). The pattern matcher cannot match a norm whose output has users beyond the pattern's, so the input pass registers a second pattern, `AiterAddRMSNormMxfp4GemmPairPattern`, for two GEMMs: one fused op, and both GEMMs take its codes and scales through `x_scales`. A site is fused for all of its consumers or for none: a norm with a third GEMM, a reader that is not a GEMM, or one GEMM that is ineligible (below) is left whole. The pair pattern has two GEMM slots; the matcher can bind both to the same GEMM depending on the order in which the graph lists the users, so `extra_check` refuses that match and the matcher goes on to the real pair (a test lists the users both ways). The pass uuid includes the site kind, so the compile cache never serves one kind's graph for the other.

**What the pass refuses, at match time** (the op's fake raises on what it cannot take, so these must not reach it): tensor parallel size above 1, hidden size not a multiple of 32 or above 8192, non-bf16 or non-2D inputs, and a GEMM weight shape (of any GEMM of the site) with a tuned Triton preshuffle config (that GEMM may take a small-M branch that reads unshuffled scales; the op writes the asm layout). The op's argument contract is one pure function, `rocm_aiter_rmsnorm_mxfp4_quant_args_error`, used by the op, its fake and the pass.

**Start-up check.** `TargetGraphSiteCheckMixin` counts rewritten sites per compile range (the first piece of a model has no site, so nothing is judged per piece). `PostGradPassManager.finish_compile`, called by `VllmBackend` after the last piece and before the compile cache index is saved, makes the pass judge the whole graph: a target model graph in which the pass ran for a compile range and rewrote nothing fails the start, naming the flag; speculative decoding graphs (`is_target_model_graph`, e.g. the bf16 MTP head) are only logged. If the pass never ran because Inductor served every piece from its cache, a warning is logged. The backend hands the graph name to the pass manager as an attribute and calls `finish_compile` only if the pass manager has it, so a platform's own pass manager (`get_pass_manager_cls`) keeps working unchanged. N in the log line counts the sites in the pieces the pass ran on; vLLM compiles identical pieces once.

**Small shared changes.** `VllmPatternReplacement.extra_check` (default accepts everything) is forwarded by `VllmFusionPatternMatcherPass.register`, so a replacement can refuse a match; existing replacements are unaffected. The fake of `gemm_with_dynamic_quant` takes its arguments in the real op's order (already in #59153; a test pins it, because passing `x_scales` and `out_dtype` positionally depends on it).

**Limits.** gfx950 asm MXFP4 path only; tensor parallel 1; Gemma-style norm (the kernel adds 1 to the weight). Not covered: the gated RMSNorm inside a gated delta net (the subject of #59553), and layer 0's norm, which is a plain `rms_norm` with no residual. Size: about 820 lines of source on top of #59153 (the op and its contract 180, the passes and the start-up check 555, wiring and flags 86) and about 2650 lines of tests, most of them on fake tensors; I can split it: the op and its contract, then the post-attention pass and the start-up check, then the input pass and the pair pattern. Expected to work on any gfx950 (MI350X, MI355X, MI350P); tested only on MI350P (128 CU). On 256-CU parts, AITER's shipped tuned tables route some GEMM shapes to the Triton preshuffle path, which the pass refuses, so fewer sites may fuse there. Open PRs that would change these figures if they land first: #58139 routes 96-row scale tiles (the GDN `in_proj_ba` GEMM) to Triton, so the 47 GDN input-norm sites would stay unfused and the 63-site and launch-count figures would drop; #61278 removes `VLLM_ROCM_USE_AITER_FP4_ASM_GEMM`, which the commands above set. I will update this PR if either merges first.
