## Overview

Put the AITER act_and_mul + MXFP4 activation-quant fusion of #59153 behind an opt-in env flag (`VLLM_ROCM_USE_AITER_FP4_ACT_QUANT_FUSION`, gfx950 only), fix the small-batch path, split the compile ranges where the fusion stops paying, and add CI and tests. Builds on #59153 (its commit is the first commit of this PR, unchanged). Today that pass is registered whenever `fuse_act_quant` is on (by default vLLM enables that switch only in some configurations), so every start of an MXFP4 model on ROCm with that switch on would rewrite its down_proj sites. With this PR a default start is unchanged. With the flag on, the pass logs one line per pass call saying how many patterns it replaced, and the flag cannot fail a start: a model with no site logs 0 and runs.

The two Gemma add+RMSNorm fusions this PR first carried (the post-attention norm and the input norm) were dropped from this PR. On main the asm MXFP4 GEMM is chosen only for shapes that also have a tuned Triton preshuffle config (`process_weights_after_loading`, since #61278), and the fused norm op cannot serve those shapes yet (the small-M Triton branch reads unshuffled scales, the op writes the asm layout), so those fusions could not fire on main.

Not a duplicate: this PR adds no new fusion, the speed comes from #59153's kernel. #59153 is the fusion (SiLU/GELU+Mul before the down projection, on the asm path); this PR gates it, fixes the small-batch path it left, splits the compile ranges, and adds CI and tests. #59610 folds RMSNorm and SiLU+Mul into the MXFP4 quant on the Triton `afp4wfp4` path, which this pass does not touch. The files overlap with #59610 (`mxfp4/aiter.py`, `rocm_aiter_fusion.py`); both PRs conflict with #59153 in `mxfp4/aiter.py` in the same place, and I will rebase on whichever lands first.

## Claims

- On gfx950 with `VLLM_ROCM_USE_AITER_FP4_ACT_QUANT_FUSION=1` (and `fuse_act_quant` on, `VLLM_ROCM_USE_AITER=1`), each SiLU/GELU+Mul that feeds an asm MXFP4 GEMM (a down_proj) in a compile range above 64 tokens becomes one AITER kernel, as in #59153.
- Observable with the flag on: the pass logs one INFO line per pass call, `AITER act-mul + MXFP4 GEMM fusion: replaced N pattern(s)`, and the same count goes to the debug summary `fusion pass matches`. It is warn-and-skip, not a failure: when the model has no site, when AITER picks the Triton preshuffle GEMM for every shape, or when Inductor served every piece from its cache so the pass never ran, nothing is replaced and the start continues. An earlier version of this PR failed the start in some of those cases; that check is gone.
- Nothing changes with the flag unset (default off; the pass also needs `fuse_act_quant` on, AITER enabled and a gfx950). With the flag off there is no extra compile-range split either.
- With the flag on, compile ranges split at 64 tokens and the pass applies only to ranges that start above 64 (`MXFP4_PRESHUFFLE_MAX_M`), so a batch of 64 tokens or fewer compiles the unfused graph and the start compiles one more range. There the activation runs on the fused `_C` act-and-mul ops. Run A4's 32 user decode shows no measurable change.
- Speed and accuracy with only this flag on: measured on Llama 3.3 70B MXFP4 in run A4 and the GSM8K block under Measurements. Prefill TTFT median -1.8%, decode at 96 and 128 users around 1% better (mixed evidence, see the note under the table), decode at 32 users unchanged, GSM8K 5-shot exact match (flexible extract) 93.00% off and 94.33% on. An earlier version of this body claimed an act-site count of 64 on Qwen3.8-27B from a start-up log on an older head; that log no longer exists, the count was never taken on this head, and it is dropped here.

## Details

**The gate.** `act_mxfp4_pass_registered` (`vllm/_aiter_ops.py`) is the single rule for the pass: `rocm_aiter_ops.is_enabled()`, the pass config's `fuse_act_quant`, `VLLM_ROCM_USE_AITER_FP4_ACT_QUANT_FUSION=1` and a gfx950. `PostGradPassManager` registers `RocmAiterActMulMxfp4GemmFusionPass` only when that holds. The other AITER passes have a rule for RDNA AITER (gfx12); this one does not register there, because the asm MXFP4 GEMM it folds into needs gfx950. The flag is part of the compile cache key like every vLLM env var (a test checks that the flag changes the compile cache key).

**The compile-range split.** `VllmConfig` adds a compile-range endpoint at `MXFP4_PRESHUFFLE_MAX_M` (64, `vllm/_aiter_ops.py`) exactly when that same rule holds, and the pass's `is_applicable_for_range` applies it only to ranges that start above 64. At 64 tokens or fewer AITER can pick its tuned Triton preshuffle GEMM, where `gemm_with_dynamic_quant` splits the activation out again, so the fusion would save nothing there. With the flag on the split applies to any model, so a start compiles one more range.

**Small batches.** In the branch the fusion does not cover, `gemm_with_dynamic_quant` calls `_act_and_mul`, which runs one `torch.ops._C.silu_and_mul`, `gelu_and_mul` or `gelu_tanh_and_mul` per call instead of an eager activation and multiply, so the small-batch path no longer runs a separate eager activation kernel.

**The ROCm tanh GELU warning.** The pass now builds the tanh GELU pattern only when the `gelu_and_mul` custom op is on. With it off (the default under torch.compile), that pattern traces to the same graph as exact GELU on ROCm and was dropped anyway, so the pass no longer creates the layer and the warning is not logged. With it on, the warning still logs once per process.

**Limits.** gfx950 asm MXFP4 path only. The fusion applies to the down_proj layers where AITER selects the asm GEMM, which on main means shapes with both an asm tuned config and a tuned Triton preshuffle config; layers with other shapes are left unfused and the pass simply reports 0 replacements there. Size: 13 files changed (10 under `vllm/` and `tests/`, plus two CI files and one doc), 1139 lines added and 6 removed, about 870 of them tests. Expected to work on any gfx950 (MI350X, MI355X, MI350P); tested only on MI350P (128 CU). On 256-CU parts, AITER's shipped tuned tables route some GEMM shapes to the Triton preshuffle path, which is not an asm GEMM and so not a site, so fewer sites may fuse there.
