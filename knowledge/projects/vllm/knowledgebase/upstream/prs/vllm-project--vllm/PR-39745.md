# [v1] Expose num_prompt_tokens in CommonAttentionMetadata

[Upstream PR](https://github.com/vllm-project/vllm/pull/39745) · state: closed · merged: False

## Original PR description

## Summary

Add `num_prompt_tokens` (per-request original prompt length) to `CommonAttentionMetadata` so that model layers can access it during the forward pass via `get_forward_context()`.

## Motivation

Under chunked prefill (`max_num_batched_tokens < prompt_length`), a long sequence is split into multiple chunks. Model layers that need to make decisions based on the full prompt length cannot rely on `positions.max()` of the current chunk, since it only reflects the chunk size, not the total prompt length.

A concrete example: [`Phi3LongRoPEScaledRotaryEmbedding`](https://github.com/vllm-project/vllm/blob/main/vllm/model_executor/layers/rotary_embedding/phi3_long_rope_scaled_rope.py#L68-L78) maintains separate short/long RoPE caches and must decide which to use. It currently works around the chunked prefill issue by making an init-time decision based on `max_model_len`, forcing **all** requests to use the same cache. With `num_prompt_tokens` available per-request in the forward context, RoPE implementations (including custom ones registered via vLLM's [plugin system](https://docs.vllm.ai/en/latest/design/plugin_system.html)) can make correct per-sequence decisions — short prompts use the short cache, long prompts use the long cache — even when chunks are smaller than the switching threshold.

Related: [#6135](https://github.com/vllm-project/vllm/issues/6135) (Phi-3 long context / LongRoPE issues)

## Changes

- **`vllm/v1/attention/backend.py`**: Add optional `num_prompt_tokens: torch.Tensor | None` field to `CommonAttentionMetadata`, with handling in `unpadded()`.
- **`vllm/v1/worker/gpu_model_runner.py`**: Pass the already-computed `num_prompt_tokens_cpu` tensor (transferred to GPU with `non_blocking=True`) when constructing `CommonAttentionMetadata`.

The data already exists in [`InputBatch.num_prompt_tokens`](https://github.com/vllm-project/vllm/blob/main/vllm/v1/worker/gpu_input_batch.py#L137-L143) (set once at `add_request` time). This change simply threads it through to where model code can read it.

## Impact

- No behavioral change for existing models — the field defaults to `None` and is only read by models that opt in.
- Enables per-sequence prompt-length-aware decisions in model layers under chunked prefill without monkey-patching.

## Testing

- Verified that the field is correctly populated and accessible via `get_forward_context()` in a custom RoPE plugin.
- Existing CI tests should pass unchanged since the new field is optional and defaults to `None`.

File: `vllm/v1/worker/gpu_model_runner.py` · line None

![high](https://www.gstatic.com/codereviewagent/high-priority.svg)

This implementation has two significant issues:

1. **CUDA Graph Compatibility**: Creating a new GPU tensor via `.to(..., non_blocking=True)` in every iteration results in a dynamic memory address. If this metadata is accessed during a captured forward pass (e.g., by RoPE layers as intended), it will break CUDA graph capture and replay because CUDA graphs require stable memory addresses for all captured inputs. You should use a persistent GPU buffer in `GPUModelRunner` (e.g., initialized in `__init__`) and copy the values into it during the input preparation phase.

2. **Initialization Bug**: `num_prompt_tokens` is not initialized for non-streaming new requests in `_update_states`. While it is explicitly set for streaming requests at line 1493, the loop for normal new requests (starting at line 1124) does not set it. This will lead to incorrect or stale values in the batch tensor, which affects the `is_prefilling` calculation at line 2174 and the metadata passed to the model forward pass.
