# [Bugfix][Offloading] UVA offloader: release the accelerator blocks it frees

[Upstream PR](https://github.com/vllm-project/vllm/pull/54972) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

With `--offload-backend uva --cpu-offload-gb N`, model loading can run out of GPU memory part-way through, whatever `N` is. Offloaded weights give up their GPU storage, but the caching allocator keeps those blocks reserved, so offloading frees nothing the next layer can use. The offloader now calls `torch.accelerator.empty_cache()` after each module it offloads from.

## Claims

- `torch.accelerator.empty_cache()` runs once for each module that offloaded at least one parameter.
- It runs before the next module is built, so the next module can reuse the freed memory.
- Modules that offload nothing do not flush the cache.
- It only affects loading. Weights and forward computation are unchanged, so there is no model eval.

## Validation

The tests run the real `UVAOffloader` under `FakeTensorMode` with a lazy module generator, and record every `empty_cache` call:
- `test_offload_releases_blocks_before_next_module` asserts the order build0, release, build1, release, build2, release. This one fails on `main`.
- `test_no_release_when_nothing_offloaded` asserts there is no release when nothing matches `cpu_offload_params`.

`ruff check` and `ruff format --check` pass on the changed files.

Local-only workaround: vLLM's autouse teardown calls `torch.accelerator.empty_host_cache()`, which segfaults on CPU-only macOS torch. For these runs it was stubbed out with a local pytest plugin. The tests patch `empty_cache` themselves, so the stub does not affect what they check.

**GPU measurement.** These numbers come from the original revision of this PR, which called `torch.cuda.empty_cache()`. They have **not** been re-run on the current head.

Setup: GLM-5.3-Flash, 181.3 GiB NVFP4 checkpoint, 43 MoE layers, RTX PRO 6000 Blackwell 96 GiB, `--cpu-offload-params experts`.

| | `main` | this PR |
| --- | --- | --- |
| `memory_reserved` growth per MoE layer | 4.06 GiB | tracks `memory_allocated` |
| `memory_allocated` growth per MoE layer | 0.30 GiB | 0.30 GiB |
| Load | OOM around layer 22 | loads and serves |

At 4.06 GiB per layer, 43 layers would reserve about 175 GiB on a 96 GiB card.

## Details

**Root cause.**
- `_maybe_offload_to_cpu` copies each parameter to host and points `p.data` at the host copy.
- The old GPU storage is freed, but the caching allocator keeps the block reserved.
- With `expandable_segments:True`, the next module grows the segment instead of reusing that block.
- Reserved memory therefore grows with every offloaded module, while live memory does not.

**Why per module, not once at the end.** `make_layers` passes `wrap_modules` a lazy generator, so module N+1 is only built after module N has been offloaded. A single release after the loop would come too late to prevent the OOM.

**Not covered.** `PrefetchOffloader` drops GPU storage the same way and may have the same problem. I have not reproduced it there, so it is not part of this PR.

**Overlapping PRs.** Several open PRs touch `uva.py`: #56413, #46690, #53981, #57215, #57472, #60299 and #43453. None of them releases the cached blocks (I checked their diffs on 2026-10-14). #46690 also adds `tests/model_executor/test_uva_offloader.py`, so that file may conflict.
