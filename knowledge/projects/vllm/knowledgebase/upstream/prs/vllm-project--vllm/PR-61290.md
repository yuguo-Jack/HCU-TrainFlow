# [Kernel][MoE] Add small-batch BF16 SiLU Triton expert path on Hopper

[Upstream PR](https://github.com/vllm-project/vllm/pull/61290) · state: open · merged: False

## Original PR description



## Overview

For 1-2 token BF16 SiLU decode on H100 at the Granite 3.1 1B-A400M MoE shape (E=32, H=1024, I=512, top-k=8), `TritonExperts` spends most of its time on `moe_align_block_size` and padded GEMMs. This adds a guarded Triton path that skips the alignment, fuses gate/up with SiLU and reduces with `ops.moe_sum`. Every other call takes the existing path.

## Claims

- Granite 3.1 1B-A400M, H100, B=2: +14.6% end-to-end decode tok/s (1247 -> 1430), identical greedy tokens.
- B=1 is flat (-0.3%). Nothing else changes.

## Validation

Paired runs (default / patched / default, 7 repeats each, 128-token prompts, 256 greedy tokens). One run on a second sandbox gave only +1.8%; raw JSON, logs and the harness are in https://gist.github.com/ToukoUrsin/ca54726753f88327446bc0d8137c3af4

`pytest tests/kernels/moe/test_moe.py -k "test_small_bf16_silu_expert_path or test_fused_shared_expert_alignment"`: 3 passed on H100. The new test checks against `torch_experts` and asserts the new path ran. pre-commit passes.

## Details

The guard is exact-shape on purpose; generalizing to other shapes or B=4/8 didn't pay off. Happy to move it behind a flag or a separate experts class if you prefer.
