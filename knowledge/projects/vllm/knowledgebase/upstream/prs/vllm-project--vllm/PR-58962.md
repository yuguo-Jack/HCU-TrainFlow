# [ROCM][KVConnector][MoRIIO] Add WRITE-mode consumer timeout

[Upstream PR](https://github.com/vllm-project/vllm/pull/58962) · state: open · merged: False

## Original PR description

## Purpose

Fixes the consumer half of ROCm/mori#655 and the hang in #59114.

**The #59114 hang is only fixed when `write_recv_timeout` is set below the
client timeout.** With the 540s default and that report's ~400s client, the
client gives up first; at the deadline decode logs the timeout and the
scheduler ignores it for the already-aborted request.

In MoRIIO WRITE mode the consumer parks a request in `WAITING_FOR_REMOTE_KVS`
until the producer's `write_done` arrives. If the producer dies that never
happens: the request waits until the client gives up, nothing is logged, and
`/health` stays 200. This adds a per-request receive timer on the consumer
scheduler; at the deadline the request is failed instead of wedging. It
complements ROCm/mori#670 (merged), which fails the producer-side transfer on a
QP error but still tells decode nothing.

Config: `kv_connector_extra_config["write_recv_timeout"]` (seconds, default 540,
finite and > 0, validated at startup). Documented in
`docs/features/moriio_connector_usage.md`.

Not a duplicate: the other open MoRIIO timeout PRs cover the prefill side
(#51301, #56465) or the handshake (#63856).

## Scope: this fails the request, it does not free the blocks

RDMA writes are one-sided, so a passed deadline does not prove the producer's NIC
has stopped; releasing a block could let a late write corrupt another request.
Blocks stay held until a real `finished_recving` (lifecycle split in #59382).
That `finished_recving` only reaches the scheduler with #59058, which keeps the
transfer mapping for a request that finishes mid-receive. So the second symptom
in #59114, KV usage staying elevated, is deliberately **not** fixed here.

## Design

* Armed in `update_state_after_alloc` on **every** consumer scheduler holding the
request (a DP rank that does not notify still waits for `write_done`).
* Stops on `finished_recving`, **not** when the request finishes: a request that
has its KV is never failed while it decodes.
* At the deadline the request id goes scheduler -> worker in
`MoRIIOConnectorMetadata.write_recv_timed_out_req_ids`, and every worker reports
it in `failed_recving` but **not** `finished_recving`. With
`kv_load_failure_policy="fail"` the scheduler fails the request and holds its
blocks (delayed free) until a real `finished_recving`.
* A client abort keeps the timer running (#59114); at the deadline the scheduler
ignores the failure for the already-aborted request, so it is not failed a
second time.
* Other connectors are unchanged. On `main`, `KVOutputAggregator` forwards a
failure only together with a finish, so at TP>1 a failed-only report would be
dropped. A new `KVConnectorBase_V1.reports_failed_recving_before_finished()`
(default `False`) lets a connector opt in to forwarding a receive that every
worker reported failed. Only MoRIIO in WRITE mode returns `True`;
`MultiConnector` returns `True` only if a child does. With `False` the
aggregator takes the same code path as on `main`.
* Works at any TP size and does not depend on the model: reporting by request id
through `failed_recving` is the path the scheduler requires for several KV cache
groups, and the delayed free is per request. So it covers every model MoRIIO
WRITE supports, including the attention + Mamba/KDA hybrids of #60544.
* The deadline starts at block allocation. Set it above worst-case prefill
queueing plus transfer time and below the client timeout. The 540s default
matches Mooncake's decode-side timeout (`VLLM_MOONCAKE_ABORT_REQUEST_TIMEOUT` +
60) and is under the OpenAI client's 600s default.
* Under `kv_load_failure_policy="recompute"` the timer is not armed, with a
startup warning: a failed receive cannot leave `WAITING_FOR_REMOTE_KVS` there.
* A producer `write_failed` (#57705) stops the timer like any completed receive.

(sorry for long post) Thanks for the work! I think the problem we're trying to solve makes sense, but I think we can simplify this a bit.

**Suggestion 1**: Can we please see if we can refactor this to instead use the `failed_recving` hook rather than the invalid_block_ids hook? Since the latter explicitly doesn't support hybrid/swa models we will eventually need another similar fix for those models. I think we might be able to just add the timed out request to failed_recving but **not** simulatenously add it to done_recving. Can you check if this would make things simpler?

Reminder: finished_recving means the request can be either (a) scheduled in the next step or (b) freed. Failed_recving means the scheduler will fail the request

**Suggestion 2**: Let's trim the test suite and just keep one or two that encapsulates this bug and the intended behavior. I.e. 
1. P dies: send a request, kill the P instance, the D eventually times out, the requests is aborted/failed, but **blocks remain allocated**. (the allocation part needs a separate fix, but that's for a different PR, as you correctly say) 
2. P is just slow: send a request, assume the d instance triggers its timeout, the request is failed but blocks are still allocated on D, P eventually writes into the blocks and send write_done, then the blocks are correctly freed.  

IMO this maps quite well to my understanding of the bug (to re-iterate)
> **Setup**: In WRITE mode, decode allocates blocks and sends a message to prefill saying "write here", and then parks the request in WAITING_FOR_REMOTE_KVs. The request is only scheduled after recving a `write_done` from prefill
> **Problem:** two cases 
> 1. if prefill dies, it never sends this `write_done` message to decode. Decode hence holds the blocks indefinitely
> 2. if prefill is extremely slow (unbounded?), the decode might be stuck forever waiting for the write_done message.
 
**One solution that doesn't work**: You already saidd this but just to re-iterate: add a timeout on decode and _free the blocks after the timeout_. This does't work because if the prefill simply takes longer than this timeout, the write will override the recycled blocks (see [this Z.AI blogpost if you're interested](https://z.ai/blog/scaling-pain)!)

<img width="1104" height="421" alt="Image" src="https://github.com/user-attachments/assets/bb4096d8-a688-4076-a372-669533dc32f3" />**

**Suggestion 3**: Let's remove most of the comments. Save them for explaining parts of the code that really needs an explanation 👍 

**As a followup:** to fix the issue with indefinite allocations on D if P dies, I think we need to a mechanism for D to ask P if it's safe to reclaim the blocks. This is exactly what ZAI did in the above mentioned blogpost. I.e. D sends `request_aborted` to P, and if P is live then it responds with `dont_free_blocks`, and D then doesn't free its blocks. In contrast, if  P is dead, then D will never get the `dont_free_blocks` reply, and hence it can go ahead and free the blocks.

Thanks @simondanielsson, all three suggestions are addressed in b42c485.

Suggestion 1 (failed_recving). Done. A timed-out request is now reported in failed_recving but not in finished_recving. With kv_load_failure_policy="fail" the scheduler fails it and holds its blocks (delay_free_blocks) until a real finished_recving, which is exactly the semantics you described. This removed the block-id tracking, the single-group guard (so it also works for hybrid / multi-group now) and the orphan bookkeeping: an aborted request is already finished, so the scheduler simply ignores its failure.

One finding while doing this. With TP > 1, KVOutputAggregator only emitted failed_recving together with finished_recving (failed = pending & finished), so a failed-only report was silently dropped; with TP = 1 there is no aggregation, so it went straight through. I changed the aggregator to also forward a receive that every worker reported failed, counting failures the same way it counts finishes (so outputs replayed from failed workers still count). Connectors that follow the existing contract (failed implies finished on the same rank) see no change. I documented the failed-only case in KVConnectorTransferResults. Happy to split this core change into its own PR if you prefer.

Suggestion 2 (tests). Trimmed to your two scenarios, through the real Scheduler and the real worker start_load_kv / get_transfer_results, at TP = 1 and TP = 2 (TP = 2 goes through the aggregator):

P dies: D times out, the request is failed, its blocks stay allocated.
P is slow: D times out, the request is failed with its blocks still allocated, and the late write_done then frees them.

One caveat on scenario 2. The test hands the worker the late write_done already translated to the request id. In the real path that translation fails today: when the request fails, request_finished drops the consumer's transfer_id -> request_id mapping, so a late write_done stays unmatched and the blocks are held until restart. #59058 keeps that mapping for a request that finishes mid-receive, so the test checks the scheduler side of the release and #59058 provides the delivery. I kept the two separate to avoid conflicting with it.
Suggestion 3 (comments). Removed most of them.

Follow-up (safe reclaim). Agreed that freeing after a timeout alone is unsafe. One nuance on the Z.AI approach as I read their post: D frees only after P positively replies that it is safe to reclaim (no writes started, or all completed). The case that stays hard is a P that is dead or unreachable, because "no reply" doesn't prove its NIC has stopped writing. We're prototyping a receiver-side fence in MoRI for that (ROCm/mori#848): D revokes P's remote access to the request's memory first, then frees, which is safe whether P is slow or dead. I'll follow up separately once it's validated.

@ErliCai thanks — you were right on both counts, and both are fixed in the
revision I just pushed. I also reproduced each divergence on hardware first so
the change isn't just reasoning.

**Too early.** Confirmed, and it is exactly #59114. With a client timeout below
the deadline, `request_finished` disarmed the timer before it could fire: the
watchdog never ran and consumer KV stayed elevated for the rest of the
observation with no traffic. The timer is now kept across an abort — the request
is marked orphaned and still timed, since the scheduler holds its blocks
regardless of what the client did. At the deadline an orphaned request gets a
log line rather than a second terminal outcome.

**Too late.** Also confirmed as a real hazard: `_handle_invalid_blocks` scans
`self.running` with `evict_blocks=True`, so a request that had already received
its KV and was still decoding would have been failed. The timer is now stopped
on *receive* completion in `update_connector_output`, which is the change you
proposed. I instrumented a build to log every arm and every `finished_recving`:
the counts match exactly, the ids are identical, and a successful request now
sits well past its deadline untouched.

Two things beyond your comment, since they change the shape of the PR:

**It no longer reclaims.** Per the lifecycle split in #59382, a timeout now
fails the request but does not free its blocks — a one-sided RDMA write can
still land, so releasing could corrupt a block that has been handed to another
request. Blocks stay held until a real `finished_recving`. The title and the log
line changed accordingly; the old "Reclaiming N block(s)" message was claiming
something that never happened. This does mean the KV-usage half of #59114 is
deliberately not fixed here — that needs #59058 plus a no-further-writes
guarantee that MoRI-IO does not currently expose at per-request granularity.

**Own blocks only.** `get_block_ids()` also returns prefix-cache hits shared
with other requests, so reporting them at the deadline would have failed those
requests too; NIXL and Mooncake use the unhashed ids for the same reason. Tested
with the cache actually warm: a request whose prefix was ~99.6% cached reported
**1 block** rather than the 256 it referenced.

The rebase onto current main also turned up something worth flagging to you and
@YukioZzz: #51052 added a `get_block_ids_with_load_errors` to
`MoRIIOConnectorWorker` after this PR was opened, and this PR had added one of
its own. Both definitions merge cleanly and Python keeps the later one, so the
timeout drain was silently shadowed — green rebase, dead feature, no error. I
removed this PR's copy and routed timed-out blocks through the existing
`_invalid_block_ids` set, so the two paths now share one drain. Worth knowing
that method is doing double duty for READ load failures and WRITE timeouts.

Validation is in the PR description. Happy to adjust the lifecycle split if you
or @yuzhouo7 read #59382 differently.
