# [ROCM][KVConnector][MoRIIO] Add WRITE-mode consumer timeout

[Upstream PR](https://github.com/vllm-project/vllm/pull/58962) · state: open · merged: False

## Original PR description

## Purpose

Fixes the consumer half of ROCm/mori#655 and the hang reported in #59114.

In MoRIIO WRITE mode the consumer parks a request in `WAITING_FOR_REMOTE_KVS`
until the producer's `write_done` arrives. If the producer dies, that never
happens: the request waits until the client gives up, nothing is logged, and
`/health` stays 200. ROCm/mori#655 captures the production form of this — a
single lost RDMA ACK puts the sender's QP in ERROR while the receiver's stays
RTS and healthy, so decode waits forever and the rank needs a manual restart.

This adds a per-request receive timer on the consumer scheduler. At the deadline
the request is failed instead of wedging.

The producer half of ROCm/mori#655 is ROCm/mori#670 (merged). With it, a QP
error or a fatal verbs async event fails the in-flight transfer instead of
leaving it pending forever, and the RC retry budget can be widened with
`MORI_IO_QP_TIMEOUT` / `MORI_IO_QP_RETRY_CNT` / `MORI_IO_QP_RNR_RETRY`. That
frees the producer, but the producer still sends decode nothing: its write
worker marks the request done and frees its own blocks. Decode only finds out
through the timer in this PR, so the two are complementary.

Configuration: `kv_connector_extra_config["write_recv_timeout"]` (seconds,
default 540, must be finite and > 0; validated at startup). Documented in
`docs/features/moriio_connector_usage.md`.

## Scope: this fails the request, it does not free the blocks

The timeout does **not** free the request's KV blocks. RDMA writes are
one-sided, so the deadline passing does not establish that the producer's NIC
has stopped; a retried write landing in a block already handed to another
request would silently corrupt it. Blocks stay held until a real
`finished_recving`, per the lifecycle split in #59382.

On its own this PR cannot deliver that `finished_recving`. When a request is
failed by the timeout or aborted by the client, the consumer's
`request_finished` unmaps its `transfer_id`, and the worker only reports
`finished_recving` for a mapped `transfer_id`. A late `write_done` is then
dropped and the blocks stay held until restart even if the producer recovers.
#59058 keeps the mapping for a request that finishes while its receive is in
flight, which covers both the abort and the timeout case; with it, a late
`write_done` releases the blocks.

That means the second symptom in #59114 — KV usage staying elevated — is
deliberately **not** fixed here. Releasing those blocks needs #59058 (so a
genuine late `write_done` can still complete cleanup) plus, for a producer that
never completes, a no-further-writes
guarantee that does not exist in MoRI-IO today: the only primitives that stop an
inbound one-sided write are `ibv_dereg_mr` or QP teardown, both of which are
MR/connection scope and would invalidate the registration for every request on
the rank.

## Design

* The timer is armed in `update_state_after_alloc` on **every** consumer
  scheduler that holds the request, not only the one that sends the notify (a
  DP rank that does not notify still waits for `write_done`).
* It records only the request's **own** (unhashed) blocks, so a prefix-cache hit
  shared with another request is never reported and never fails that request.
  NIXL and Mooncake do the same.
* It stops on `finished_recving` (in `update_connector_output`), **not** when
  the request finishes. A request that already has its KV is never failed while
  it decodes.
* A client abort keeps the timer running (#59114). At the deadline an aborted
  request is logged as orphaned instead of failed a second time.
* On timeout the block ids ride `MoRIIOConnectorMetadata.write_load_failed_block_ids`
  to the worker, which feeds them into `_invalid_block_ids` so they drain through
  `get_block_ids_with_load_errors` like READ failures do.
* The deadline starts at block allocation, so it includes any wait before the
  producer starts. Set it above worst-case prefill queueing plus transfer time
  and below the client timeout.
* `VLLM_MORIIO_WRITE_TIMEOUT_S` is no longer read.
* Startup logs a warning if `kv_load_failure_policy="recompute"` is used with a
  WRITE consumer, since a timed-out request cannot leave `WAITING_FOR_REMOTE_KVS`
  under that policy.
* The timer is only armed with a single KV cache group. Timeouts are reported
  as block ids, and `_handle_invalid_blocks` raises for several groups because
  block ids are only unique within a group. Hybrid WRITE (#60544, merged) has
  several groups, so there the timer is off and a startup warning says so;
  arming it would turn a timeout into an engine crash.
* A producer `write_failed` (#57705) reaches the scheduler as
  `finished_recving` plus `failed_recving`, so it stops the timer like any
  completed receive and the request is not failed a second time.

## Test plan

### Unit tests

`tests/v1/kv_connector/unit/test_moriio_write_recv_timeout.py` — 52 tests, no GPU,
RDMA or `mori` package needed (`cpu_test`, so they run in the CPU CI job).

* Config: read from `kv_connector_extra_config`, rejects zero / negative / NaN /
  inf, env var ignored (through the real `__init__`); timer disabled with a
  warning for several KV cache groups.
* Lifecycle: arming with own blocks only, deadline reaping, reported exactly
  once, orphan on abort, stop on `finished_recving`, metadata shipping, worker
  drain.
* **Real `Scheduler`** (built with `create_scheduler` + `create_model_runner_output`,
  with only the connector's clock faked):
  * a timed-out request becomes `FINISHED_ERROR`, keeps its blocks, and a late
    `finished_recving` releases them exactly once;
  * an aborted request is not failed a second time, and is released if its KV
    arrives late, or in time;
  * a request that received its KV is never failed while decoding;
  * only the stuck request fails; several requests expiring in one step all fail;
  * the exact deadline boundary;
  * a producer `write_failed` (reported as `finished_recving` +
    `failed_recving`) fails the request once and stops the timer.

  These tests inject `finished_recving` into the scheduler directly, so the
  release cases check the scheduler contract. End to end, that
  `finished_recving` only reaches the scheduler with #59058 (see Scope above).

Checked that the tests catch regressions by breaking the connector on purpose:
stopping the timer in `request_finished` (the #59114 bug) fails 4 tests, never
stopping it on `finished_recving` fails 8, not reporting the blocks fails 8,
failing an aborted request again fails 2, dropping the single-group guard fails
1. All 52 pass on the unmodified code, also with the `mori` package hidden and
no GPU.

The whole MoRIIO unit suite (`tests/v1/kv_connector/unit/test_moriio*.py`) runs
against the full rebased source tree: 345 passed on this branch, 293 passed on
current main (the difference is this file); no failures on either. `ruff check`
and `ruff format --check` (v0.14.0, as pinned in `.pre-commit-config.yaml`) are
clean on the changed files.

### End-to-end hardware validation

1P1D MoRIIO WRITE, 2 nodes, `gpt-oss-120b` TP8 on gfx950,
`--disable-hybrid-kv-cache-manager` (WRITE mode does not support HMA), MoRI
built from main at `f8e3239` (includes ROCm/mori#670). Run on the earlier
revisions of this PR and re-run on a build of commits 1–4, with identical
results. Also run with GLM-5.2-FP8 (dummy weights, TP8), where the timeout test
passes too. Re-run on 2026-10-18 on the current head (`935d33b`, rebased onto
main with #57705 and #60544), on fresh nodes and a vLLM nightly at `1b2a66639`
with the same MoRI build: both arms gave the same counters and timings as below.

**Forcing the failure deterministically.** Killing the producer at an arbitrary
moment does not reproduce anything: on this stack a 4-request round trip of
30720-token prompts completes in ~2.4s, so the `WAITING_FOR_REMOTE_KVS` window
is too narrow to land a kill in. Instead the producer is `docker pause`d first,
which holds the consumer in `WAITING_FOR_REMOTE_KVS` for as long as needed, and
only once decode reports `waiting>=1` is the producer removed (`docker rm -f`).
Prompt length must satisfy `prompt + max_tokens <= --max-model-len` or the
request is rejected before it can ever defer.

**Compressing the race.** `write_recv_timeout=60` instead of the 540s default.
What determines behavior is the *ordering* of (client timeout, deadline), not the
magnitudes; 40s/90s against a 60s deadline reproduces the same two orderings as
#59114's 400s client against the 540s default, in minutes rather than hours. The
consumer is relaunched fresh for the suite, so the counters below are measured
from zero.

**What is measured.** `vllm:kv_cache_usage_perc` on the consumer (a fraction,
not a percent) plus the consumer's own log. `/health` is not a signal — it
stayed 200 throughout the failures in #59114 and here.

| arm | ordering | counter delta | result |
|---|---|---|---|
| client aborts first | 40s client vs 60s deadline | orphan **+4**, timedout **0**, kv-load-failure **0** | clients abort at 40.1s; at the deadline each request gets a warning, not a second terminal outcome; blocks retained |
| deadline fires first | 90s client vs 60s deadline | timedout **+4**, orphan **+0** | all 4 clients released at **60.1s** with the request failed, instead of hanging to their own 90s timeout; blocks retained |

Neither arm bled into the other. No "Reclaiming N block(s)" text appeared in
either.

Without the `request_finished` change the first arm produces no watchdog event
at all and the request wedges — that is #59114 exactly, reproduced here as
consumer KV usage pinned for 166s with no traffic.

**Healthy traffic.** Instrumented a build to log every arm and every
`finished_recving`: counts matched exactly and no successful request was ever
timed out, including ones left idle well past their deadline.

**Prefix-cache sharing**, for the own-blocks-only change. A 4096-token prompt is
sent twice with the producer alive to warm the cache (`prefix_cache_hits_total`
goes 0 -> 4080), then a third request sharing that prefix has its producer
killed. The timer still arms and fires, and reports **1 block** — the request's
own unhashed tail — rather than the 256 blocks it references. With
`get_block_ids()` it would have reported all 256, including 255 shared with
other requests, failing them too.

## Not covered

* `recompute` failure policy: the request is marked failed but still cannot
  leave `WAITING_FOR_REMOTE_KVS`. Only the default `fail` policy benefits (a
  startup warning says so).
* A `write_done` arriving within about one scheduler step of the deadline can
  still fail a request that just received its KV.
* With a dead producer the retained blocks are held until the engine restarts.
  Without #59058 this is true for every timed-out or aborted request, even one
  whose producer later completes the write.
* Hybrid (multi-group) WRITE, enabled by #60544: the timer is off there (see
  Design), so a hybrid WRITE consumer can still wait forever on a dead
  producer. Covering it means reporting timeouts by request id through
  `failed_recving`, which the worker can now do via `get_transfer_results`
  (added by #57705). That is the follow-up to this PR.
* The producer-side half of the failure is #57705 (merged): a prefill whose
  deferred write expired sends `write_failed` to decode. That PR and this one
  cover different failures (prefill alive but never started the write, versus
  prefill dead or silent mid-transfer) and are meant to be used together.
* This PR conflicts in `moriio_connector.py` with #59058 and #60852 (stacked on
  #59058). #59058 tracks the same in-flight receive lifecycle as
  this timer (armed at allocation, cleared on `finished_recving`), so this PR
  can be rebased on top of it and reuse that tracking. Suggested order: #59058,
  then this PR.
* A producer whose transfer fails after the write started (a QP error surfaced
  by ROCm/mori#670, or `transfer_timeout`) still frees its blocks without
  telling decode; decode learns of it only through this timer. Sending
  `write_failed` on that path too, as #57705 does for an expired deferred
  write, is possible follow-up work.

## Note on the default

540s is longer than typical client timeouts — in #59114 the client disconnected
at ~400s, so the consumer never acted first. Since the timeout no longer frees
anything its length is a latency choice rather than a safety one, but it should
sit below the client timeout to be useful.

I wonder if the watchdog might be better cleared when the receive finishes rather than when the request finishes. I think the two can diverge in a couple of ways:

@ErliCai thanks — you were right on both counts, and both are fixed in the
revision I just pushed. I also reproduced each divergence on hardware first so
the change isn't just reasoning.

**Too early.** Confirmed, and it is exactly #59114. With a client timeout below
the deadline, `request_finished` disarmed the timer before it could fire: the
watchdog never ran and consumer KV stayed elevated for the rest of the
observation with no traffic. The timer is now kept across an abort — the request
is marked orphaned and still timed, since the scheduler holds its blocks
regardless of what the client did. At the deadline an orphaned request gets a
log line rather than a second terminal outcome.

**Too late.** Also confirmed as a real hazard: `_handle_invalid_blocks` scans
`self.running` with `evict_blocks=True`, so a request that had already received
its KV and was still decoding would have been failed. The timer is now stopped
on *receive* completion in `update_connector_output`, which is the change you
proposed. I instrumented a build to log every arm and every `finished_recving`:
the counts match exactly, the ids are identical, and a successful request now
sits well past its deadline untouched.

Two things beyond your comment, since they change the shape of the PR:

**It no longer reclaims.** Per the lifecycle split in #59382, a timeout now
fails the request but does not free its blocks — a one-sided RDMA write can
still land, so releasing could corrupt a block that has been handed to another
request. Blocks stay held until a real `finished_recving`. The title and the log
line changed accordingly; the old "Reclaiming N block(s)" message was claiming
something that never happened. This does mean the KV-usage half of #59114 is
deliberately not fixed here — that needs #59058 plus a no-further-writes
guarantee that MoRI-IO does not currently expose at per-request granularity.

**Own blocks only.** `get_block_ids()` also returns prefix-cache hits shared
with other requests, so reporting them at the deadline would have failed those
requests too; NIXL and Mooncake use the unhashed ids for the same reason. Tested
with the cache actually warm: a request whose prefix was ~99.6% cached reported
**1 block** rather than the 256 it referenced.

The rebase onto current main also turned up something worth flagging to you and
@YukioZzz: #51052 added a `get_block_ids_with_load_errors` to
`MoRIIOConnectorWorker` after this PR was opened, and this PR had added one of
its own. Both definitions merge cleanly and Python keeps the later one, so the
timeout drain was silently shadowed — green rebase, dead feature, no error. I
removed this PR's copy and routed timed-out blocks through the existing
`_invalid_block_ids` set, so the two paths now share one drain. Worth knowing
that method is doing double duty for READ load failures and WRITE timeouts.

Validation is in the PR description. Happy to adjust the lifecycle split if you
or @yuzhouo7 read #59382 differently.
