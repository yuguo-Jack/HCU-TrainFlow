# [Bugfix][KV Offload] Fix shared-region ownership and startup cleanup

[Upstream PR](https://github.com/vllm-project/vllm/pull/53073) · state: open · merged: False

## Original PR description

## Overview

Fix the shared `/dev/shm` KV-offload mmap lifecycle so pathname ownership is
explicit, startup failures remove abandoned regions, and normal cleanup only
releases process-local resources.

This PR contains the lifecycle/startup-abort fix and integrates the relevant
commits from [#57422](https://github.com/vllm-project/vllm/pull/57422), while
leaving its `external_launcher` synchronization and stale-replacement
protection under the original author's commits.

## Claims

- A ready mmap no longer depends on persistent creator state. The selected
  caller unlinks the pathname at the safe success point, including restart
  cases where every opener is a joiner.
- CPU offload selects the unlink owner within each DP engine. For
  `external_launcher`, the local TP/PP/PCP topology is used even when the
  independent-DP setup has reset `data_parallel_size` to one.
- Tiering workers map first without unlinking; the scheduler unlinks after its
  mapping/synchronization step. Worker-side initialization failures use the
  explicit startup-abort path so the pathname is not leaked before the
  scheduler exists.
- Normal `cleanup()` only releases local tensors, memoryviews, mmap objects,
  and file descriptors. Path removal is handled by successful initialization
  or `abort_startup_cleanup()`.
- HiSparse keeps only the ownership and startup-abort changes required by this
  fix. Its independent tensor-lifetime changes are intentionally deferred to a
  follow-up.

## Details

### Root cause

`O_CREAT | O_EXCL` identifies the process that first creates a pathname, but
that construction event is not a lifetime ownership guarantee. A ready file
can survive a restart, allowing every new opener to join an existing mapping.
The old creator-gated cleanup therefore had no reliable unlinker. Cleanup-time
fallback unlinking also required persistent ownership state and could race with
the next generation of the same pathname.

### Implementation

- `SharedOffloadRegion` tracks path creation only during construction. The
  constructor-local `unlink_owner` is consumed on successful initialization;
  `cleanup()` is idempotent local resource release, while
  `abort_startup_cleanup()` additionally removes the still-owned path.
- `unlink()` verifies the mmap file identity before removal, narrowing the
  stale-generation/replacement race covered by #57422.
- CPU and tiering call sites explicitly select their success-path owner, and
  startup rollback paths are separate from normal shutdown.
- The tests cover joiners, barriers, sequential openers, canonical layout,
  startup failures, DP-local ownership, and independent-DP rank reset.

This is not a duplicate of the earlier creator-gated unlink work: the change
removes the creator-lifetime dependency and coordinates the tiering startup
and abort paths. The HiSparse tensor-view lifetime redesign is independent and
will be handled separately.

Thanks @Etelis, I agree that #52596's map-after-barrier unlink is the right cleanup point. I think a small follow-up is still useful for two reasons.

First, the current `O_CREAT | O_EXCL` election can objectively leave a restarted engine with no live creator. If the original creator prepared the file but the engine/pod later fails, the shared-memory path may survive the K8s restart. Every worker in the new engine then takes the joiner path, so none has `_creator=True`. They can map the ready file and reach the barrier, but the current `_creator` gate leaves no process to perform the unlink.

Second, this simplifies the state model. `O_EXCL` should be only a transient preparation detail; it should not create a lifecycle attribute or cleanup responsibility. After rebasing on #52596, I propose to remove `_creator` entirely, avoid adding a replacement owner attribute, remove path unlinking from normal `cleanup()`, and directly use `is_local_first_rank()` at the post-barrier commit point to unlink each node-local path.

This leaves a simpler lifecycle: prepare the file, map on every worker, unlink at the barrier commit point, then let `cleanup()` release only process-local resources. What do you think?

Thanks for checking. I traced the Tiering startup order: workers create and map the shared region first, and the scheduler maps the same path afterwards. A worker-side barrier unlink could therefore remove the path before the scheduler can open it.

To avoid introducing a new cross-process handshake, I propose making the unlink role an explicit caller-supplied policy, independent of O_EXCL creator state:

 - CPU offload: worker local rank 0 is the cleaner.
 - Tiering: the scheduler-side region is the cleaner, since it is created after workers have mapped the file.
This keeps the unlink logic generic and removes the creator-lifetime dependency. The tradeoff is that, in Tiering, the scheduler performs the unlink even though a worker may have created the file. Does this fit with your planned Tiering barrier work?
