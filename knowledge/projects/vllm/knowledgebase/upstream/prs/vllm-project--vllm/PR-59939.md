# [Core] Release DeepEP all2all buffers on sleep with comm suspend

[Upstream PR](https://github.com/vllm-project/vllm/pull/59939) · state: open · merged: False

## Original PR description

## Purpose

Part of RFC #59055 (release more GPU memory in sleep mode).

With `--enable-nccl-comm-suspend`, sleep mode now also releases the DeepEP all2all buffers of `deepep_high_throughput` and `deepep_low_latency`. Before this change those buffers (the NVL IPC buffer, plus the NVSHMEM heap for low-latency) stayed on the GPU while the engine was asleep.

How it works:

- `All2AllManagerBase` gets two no-op hooks, `suspend()` and `resume()`. `CudaCommunicator.suspend()` / `resume()`, which `--enable-nccl-comm-suspend` already calls on every group from `Worker.sleep()` / `wake_up()`, now call them.
- `DeepEPAll2AllManagerBase.suspend()` calls `Buffer.destroy()` on every cached buffer. vLLM already creates the buffers with `explicitly_destroy=True`.
- `resume()` re-runs `Buffer.__init__()` on the same Python object with its cached kwargs. The prepare/finalize objects keep a reference to that object, so they stay valid, and the handle cache still finds it.
- One flag, `_suspended`, records that the buffers are destroyed. While it is set, `destroy()` (shutdown) skips them, so shutting the engine down while asleep is clean.
- Both steps are collective over the EP group, like `ncclCommSuspend`: `destroy()` has GPU barriers and `__init__()` exchanges handles with `all_gather_object`. As with NCCL suspend, the engine must be idle.
- With `--enable-nccl-comm-suspend`, `NVSHMEM_DISABLE_NCCL=1` becomes the default (a value the user sets wins). NVSHMEM otherwise builds NCCL communicators for its default teams on every init, which DeepEP never uses; they cost ~1.6 GiB/GPU while awake, ~4 s per wake and most of the per-cycle growth below.

The buffers stay on the GPU, and a log line says why, in two cases:

1. **CUDA graphs on** (`cudagraph_mode != NONE`). Captured graphs hold the buffer addresses, and the NVL buffer and workspace get new addresses when they are re-created. In a standalone test, replaying a graph captured before a destroy/re-create matched for two cycles and then failed with `cudaErrorIllegalAddress` on the third. The NVSHMEM buffer happened to come back at the same address, but the NVL buffer did not. Releasing the buffers with graphs on would need either graph recapture on wake or fixed-address allocation inside DeepEP; neither is in this PR. In practice this means `deepep_low_latency` with CUDA graphs (the default for that backend) keeps its buffers. `deepep_high_throughput` runs without CUDA graphs when DP > 1, so it is covered.
2. **`VLLM_DEEPEP_LOW_LATENCY_USE_MNNVL=1`**. In this mode DeepEP allocates the NVL buffer with fabric handles. Its `destroy()` does not drop all references to that allocation (`cuMemRetainAllocationHandle` in `get_mem_handle` is never released), so the memory is not freed. On GB300 each destroy/re-create cycle leaked one NVL buffer (+1036 MiB per GPU per cycle with the default 1 GiB buffer, +518 MiB with 512 MiB). The legacy `Buffer` that vLLM pins (d4f41e4) has this bug; DeepEP main no longer has the legacy `Buffer`.

The default behavior does not change. Without `--enable-nccl-comm-suspend`, nothing new runs.

Known limitations (not handled in this PR):

- `--enable-fault-tolerance` with DeepEP LL: re-init zeroes DeepEP's rank mask, but vLLM keeps its last-seen mask, so a rank masked before sleep could show up as a new fault after wake. A dead rank also makes the re-init hang.
- A weights-only wake (`wake_up(tags=["weights"])`) already re-creates the buffers (and runs NVSHMEM init for LL), as NCCL resume does today, so they come back before the KV cache.
- Two LL buffers with different shapes in one process would share the global NVSHMEM state, which the second `destroy()` finalizes twice. No current vLLM model creates two LL buffers; shutdown `destroy()` already has this issue.

Relation to #59360: #59360 uses the same `CudaCommunicator.suspend()` / `resume()` path for FlashInfer all-reduce workspaces. The two PRs do not conflict in behavior. Each adds an independent call, and neither uses NCCL (DeepEP syncs with its own GPU/NVSHMEM barriers and gloo), so the order relative to NCCL and to each other does not matter. They do conflict textually: both add lines to `CudaCommunicator.suspend()` / `resume()` and add tests next to each other in `tests/distributed/test_comm_ops.py`. Whichever lands second keeps both calls.

## Test Plan

Unit tests (`tests/distributed/test_comm_ops.py`):

- `test_cuda_communicator_suspend_recreates_deepep_buffers[ht-eager|ht-cudagraph|ll-eager|ll-cudagraph|ll-mnnvl]`: builds the real HT/LL manager (so the policy set in `__init__` is covered), then suspends twice and resumes twice through `CudaCommunicator`. The handle cache holds only weak references; the test keeps the buffers alive the way the prepare/finalize objects do. With CUDA graphs off, each buffer is destroyed once and re-initialized in place with its original kwargs. With CUDA graphs, or LL with MNNVL, it is left alone. MNNVL does not affect HT. NCCL suspend/resume are still called.
- `test_deepep_destroy[awake|asleep]`: shutdown `destroy()` destroys each buffer exactly once and clears the cache, both awake and while suspended.
- Mutation check (16 mutants): each makes at least one test fail. Policy: ignoring the resident reason, removing the CUDA graph check, removing the MNNVL check, applying the MNNVL check to HT. State: no double-suspend guard, not setting or not clearing the flag, no resume guard, re-creating a new object instead of re-init in place, re-init without the kwargs, destroying only some handles, `destroy()` ignoring the flag, never destroying, or not clearing the cache. Wiring: `CudaCommunicator` not calling the all2all suspend or resume.

Hardware (NVIDIA GB300, 4 GPUs per node, driver 580.105.08, CUDA 13.0):

- Same image for stock and patched. The changed files are bind-mounted one by one, with sha256 checks against the base commit and the patch.
- Server flags: `--enable-sleep-mode --enable-nccl-comm-suspend --enable-expert-parallel --data-parallel-size 4|8 --no-enable-prefix-caching`.
- DeepSeek-V4-Flash also uses `--trust-remote-code --kv-cache-dtype fp8 --max-model-len 8192`, plus `--max-num-batched-tokens 8192` (HT) or `256` (LL).
- A driver sends 16 greedy prompts (48 tokens), one at a time, with each prompt pinned to one DP rank by `X-data-parallel-rank`. It records the awake outputs, runs level-1 sleep/wake cycles (and one level-2 cycle in some cases), and compares the outputs after every wake with the awake outputs.
- GPU memory while asleep is read with nvidia-smi on every GPU of every node, 4 s after `/sleep` returns.

## Test Result

Unit tests: 9 passed (`-k "deepep or suspend or checkpoint"`, 5 runs). pre-commit passes on the changed files.

Shutdown while asleep: after the last cycle of each run, the driver puts the server to sleep and sends SIGTERM or SIGINT to the `vllm serve` process. Every server exits with code 0, and no log has a DeepEP traceback or a DeepEP "destroy() was not called" warning.

- With the default `--shutdown-timeout 0`, the process manager kills the engine processes right away, so the workers never run `destroy()`. To exercise that path, the Qwen3 HT and LL runs were repeated with `--shutdown-timeout 60`. The workers then go through `destroy_model_parallel()` while asleep and exit gracefully. As a control, the earlier version of this PR (without the skip in `destroy()`) raises `AttributeError: 'NoneType' object has no attribute 'destroy'` on the same run.
- Unrelated noise, also seen when the PR changes nothing: some runs log one `EngineDeadError` traceback from an API server's output handler during shutdown, including V4-Flash LL with CUDA graphs, where the buffers stay resident. With `--shutdown-timeout 60`, each worker logs `CUDA Error: invalid argument at cumem_allocator.cpp:258` once at exit; stock logs the same 4 lines.

GPU memory used while asleep, per GPU (MiB). All GPUs in a run were within 4 MiB of each other.

| Model, setup | Backend | CUDA graphs | Stock | This PR | Freed |
|---|---|---|---|---|---|
| Qwen3-30B-A3B, DP4 EP, 1 node | `deepep_high_throughput` | off (forced) | 2813 | 1749-1751 | 1062 |
| Qwen3-30B-A3B, DP4 EP, 1 node | `deepep_low_latency` | off (`--enforce-eager`) | 6177 | 1769 (cycle 1) | 4408 |
| DeepSeek-V4-Flash, DP4 EP, 1 node | `deepep_high_throughput` | off (`--enforce-eager`) | 2529 | 1469-1473 | 1058 |
| DeepSeek-V4-Flash, DP4 EP, 1 node | `deepep_low_latency` | off (`--enforce-eager`) | 7473 | 1481 (cycle 1) | 5992 |
| DeepSeek-V4-Flash, DP4 EP, 1 node | `deepep_low_latency` | FULL_AND_PIECEWISE | not run | 9503 (kept, log line printed) | 0 |
| Qwen3-30B-A3B, DP8 EP, 2 nodes | `deepep_low_latency`, MNNVL | off (`--enforce-eager`) | 6041 | 6041 (kept, log line printed) | 0 |
| DeepSeek-V4-Flash, DP8 EP, 2 nodes | `deepep_low_latency`, MNNVL | off (`--enforce-eager`) | not run | 7337 (kept, log line printed; earlier revision, same resident path) | 0 |

Outputs: 16/16 identical to the awake outputs after every level-1 wake, in every run above (3 cycles, 15 for the drift runs).

Sleep and wake time (level 1):

- HT: same as stock, within 0.1 s.
- LL: wake is about 4-5 s slower than stock and sleep about 1-2 s slower (NVSHMEM finalize and init). Example, V4-Flash LL: wake 5.7-6.1 s vs 1.4 s stock.
- With the `NVSHMEM_DISABLE_NCCL=1` default (latest revision), Qwen3-30B-A3B LL eager, 15 level-1 cycles, outputs 16/16 every cycle:

  | Setup | Before the default | With the default |
  |---|---|---|
  | 1 node: asleep cycle 1 -> 15, growth per cycle, wake | 1769 -> 1801 MiB, 2.29 MiB, 4.6-5.4 s | 1761 -> 1791 MiB, 2.14 MiB, 1.5-1.75 s |
  | 2 nodes (RDMA): asleep cycle 1 -> 15, growth per cycle, wake | 1773 -> 1889 MiB, 8.29 MiB, 5.0-5.6 s | 1761 -> 1791 MiB, 2.14 MiB, 1.0-1.3 s |

  The remaining ~2.1 MiB/GPU per cycle is NVSHMEM 3.4.5 leaking 4 CUDA streams and 2 events on every init/finalize (`init.cu`, `ibgda.cpp`; still present in v3.8.0), reproduced with a 40-line NVSHMEM-only program. It needs an NVSHMEM fix.

Repeated cycles:

- HT: flat. V4-Flash stays at 1469-1473 MiB over 3 cycles. In a standalone DeepEP test, used memory rises by 32 MiB over the first 3 destroy/re-create cycles and then stays flat through 30.
- LL: about +2 MiB per GPU per cycle, and it does not level off. Qwen3 over 15 cycles: 1769 -> 1801 MiB with this PR, flat 6177 MiB with stock. A standalone DeepEP test shows the same rate (+72 MiB over 30 cycles). The rate is the same with no NVL buffer and with `NVSHMEM_REMOTE_TRANSPORT=none`, so the leak comes from NVSHMEM finalize + init, not from DeepEP's NVL buffer or the IB transport. On one node, 1000 cycles cost about 2.3 GB, still far less than the ~4.4-6 GB per GPU that LL frees on each sleep. Across nodes the rate is higher (see the RDMA path below).

Level 2: Qwen3 HT and LL match 16/16 after level-2 sleep, `reload_weights` and wake. DeepSeek-V4-Flash does not match after level 2: HT gives 0/16 with this PR and also 0/16 on stock with the same flags. LL gives 3/16 with this PR and the same 3/16 (same prompts) on stock. This is a separate problem in V4-Flash weight reload, not in this change.

Cross-node:

- The two nodes are in one NVLink domain (same fabric cluster UUID and clique, IMEX running), and they have 4 GPUs each.
- DeepEP's legacy `Buffer` treats up to 8 ranks as NVLink peers (`LEGACY_NUM_MAX_NVL_PEERS = 8`). So DP8 over two 4-GPU nodes never takes the RDMA (NVSHMEM over RoCE) path; the run that works uses the NVLink fabric. These limits also hold on stock; this PR does not change buffer creation:
  - `deepep_high_throughput` fails at startup with `num_ranks > LEGACY_NUM_MAX_NVL_PEERS or low_latency_mode`, because vLLM asks for an RDMA buffer when the group spans nodes.
  - `deepep_low_latency` with the default IPC handles fails at startup (`cudaIpcOpenMemHandle` cannot open buffers on the other node).
  - `deepep_low_latency` with `VLLM_DEEPEP_LOW_LATENCY_USE_MNNVL=1` runs. With this PR the buffers stay resident (case 2 above). Outputs were 16/16 after each of 3 cycles, with no hang and no growth across cycles.
- Without the MNNVL check (an earlier version of this PR), the same Qwen3 run freed memory on the first sleep (2801 MiB asleep), then grew by 1036 MiB per cycle (2801 -> 3837 -> 4875 -> 5911). That is the DeepEP leak described above, and the reason for the check.
- RDMA path (LL only):
  - DeepEP's legacy `Buffer` accepts fewer than 8 ranks or a multiple of 8 (`buffer.hpp:114`); DP12 on 4-GPU nodes fails at startup on stock with that assert. HT internode needs blocks of 8 ranks that share plain IPC handles, and those blocks span two nodes here, so HT cannot use RDMA on this cluster.
  - LL uses RDMA across nodes with the NVL buffer off and MNNVL off (`VLLM_DEEPEP_BUFFER_SIZE_MB=0`, DP8 over 2 nodes): NVSHMEM lists only the local GPUs as P2P peers and reaches the other node through IBGDA on RoCE.
  - With `--enable-nccl-comm-suspend --enforce-eager`: Qwen3-30B-A3B goes from 5013 to 1773-1791 MiB per GPU asleep, DeepSeek-V4-Flash from 6307 to 1483-1501. Outputs are 16/16 after each of 3 level-1 wakes. Wake is about 4.3 s slower than stock. Nothing hangs, and SIGTERM while asleep exits cleanly on both nodes.
  - Asleep memory grows by about 8 MiB per GPU per cycle across nodes (2.4 on one node), in vLLM and in a 30-cycle standalone DeepEP test. It appears only with remote IBGDA peers, so it comes from NVSHMEM finalize and init. At that rate, about 400-600 cycles in one process use up what one sleep frees.

Note: the DeepEP in the current vLLM image is built for `sm_90a` / `sm_100a` only (`TORCH_CUDA_ARCH_LIST='9.0a 10.0a'` for ep_kernels in the Dockerfile), so DeepEP kernels fail on GB300 (`sm_103`). For these tests, DeepEP d4f41e4 was rebuilt with `10.0a 10.3a`. That is a separate issue and is not changed here.
