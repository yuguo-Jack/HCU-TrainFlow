# [ROCm][DSv4.1] Shard the sparse-indexer prefill rows across TP

[Upstream PR](https://github.com/vllm-project/vllm/pull/65555) · state: open · merged: False

## Original PR description



## Overview

On ROCm, shard the DeepSeek-V4.1 sparse-indexer prefill rows across TP ranks, including the two-level candidate layers (the candidate source and its consumers). Each rank scores a contiguous slice of the prefill rows and the ranks all-gather the final int32 top-k. This reuses the existing `balanced_prefill_row_shard` / `PrefillRowShard` / `all_gatherv` machinery and the existing `indexer_tp_shard_min_rows` threshold; until now the row-sharding gate was CUDA-only.

## Claims

- DeepSeek-V4.1-Flash on MI355X, single 1M-token request: TTFT −17% to −18% at TP4 (two runs) and −9.9% at TP2 on the recipe configuration (MXFP4 indexer cache, `indexer_sparse_logits`). With `--no-swa-bounded-replay`, where the candidate layers run on every prefill row, TTFT is −18.3% (MXFP4) and −52% (FP8 indexer cache) at TP4.
- Accuracy unchanged: GSM8K 0.970 → 0.971 (TP4) and 0.972 → 0.973 (TP2); passkey retrieval at 64K–512K 18/18 in every configuration.
- No throughput regression on 8K/1K at concurrency 1–64 (−0.6% to +5.8%).
- Opt-in through the existing threshold, e.g. `--attention-config '{"indexer_tp_shard_min_rows": 512}'`. The default (65536 total prefill rows) is unchanged, so steps with `--max-num-batched-tokens` below it stay replicated, as on CUDA.

Arm "off" is the same build with `indexer_tp_shard_min_rows=1000000000`, arm "on" with `512`; one server per arm.

**Tests** (MI355X):
- `tests/kernels/attention/test_rocm_dsv41_indexer_row_shard.py` (new) and `test_rocm_paged_mxfp4_indexer.py::test_prefill_row_shard_matches_replicated` (new) run the FP8 and MXFP4 ops as each rank of a 2- and 4-way shard over a multi-chunk prefill whose rank boundaries cut requests and chunks: the ratio-2 layer, the candidate source, and a consumer whose candidate rows of other ranks hold junk. ## Details

- **Gate.** `tp_prefill_row_sharding_supported` now also accepts ROCm, for models with the DeepSeek-V4.1 two-level indexer only (`candidate_source_layer_id >= 0`): those are the ROCm ops that handle the shard. Every other condition (no DCP/PCP, PyNCCL, no FULL mixed CUDA graph, …) is unchanged, and CUDA behavior is unchanged.
- **Candidate layers.** The source (layer 20) and its consumers (24/28/32/36) read one indexer metadata entry, keyed by the source's K cache, so they get the same row slice. A consumer only reads candidate rows its own rank wrote, so only the final top-k is exchanged, not the candidates.
- **FP8 path** (`rocm_aiter_sparse_attn_indexer`): each chunk is narrowed to the rank's rows with `PrefillRowShard.narrow`; chunks outside them are skipped, K gather included. One `exchange_topk` after the prefill loop.
- **MXFP4 path**: its kernels read K from the paged cache in place, so the builder narrows the chunks (`narrow_prefill_chunks`) before planning; the plans and the consumers' gather launches follow. Both ops call `exchange_topk` after their prefill loop.
- **Collective safety.** `row_shard_sizes` is computed on the host from the step's lengths, identically on all ranks, and every rank reaches the exchange once per indexer layer, including a rank whose slice misses every chunk. Decode rows are never sharded. The profiling run reserves the exchange's transient memory, as on CUDA.
- **Limitation.** The threshold counts a step's total prefill rows, so with the default the shard does not engage at `--max-num-batched-tokens` ≤ 65536; set `indexer_tp_shard_min_rows` (512 measured above) to use it.
