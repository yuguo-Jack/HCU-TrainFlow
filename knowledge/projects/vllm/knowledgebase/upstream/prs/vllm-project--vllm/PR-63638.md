# [Perf][Kimi K3] Opt-in KV-balanced FP8 MLA decode for agentic workloads

[Upstream PR](https://github.com/vllm-project/vllm/pull/63638) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

Adds an opt-in MLA attention backend for Kimi-K3 on Blackwell, `--attention-backend KIMI_K3_KV_BALANCED_MLA`. Its decode splits each request's KV by its own length, so the decode stays balanced across the GPU when the context lengths in one batch differ a lot, as they do in agentic workloads. It is a standalone backend built on the common MLA backend classes (`MLACommonBackend`, `MLACommonImpl`, `MLACommonMetadataBuilder`); it does not depend on `TOKENSPEED_MLA`. The code lives in `vllm/models/kimi_k3/nvidia/kv_balanced_mla/`. Outside it, the PR only adds the backend's entry to `AttentionBackendEnum` (as the DeepSeek V4, MiniMax M3 and Step5 backends in `vllm/models/` have).

## Claims

- **Decode attention, AgentX context lengths on GB300:** 1.34–1.59x faster than `TOKENSPEED_MLA` with `tokenspeed_mla_min_split_kv=8`, and 1.91–2.67x faster than its default (geometric mean over batch sizes, DEP16 and DCP8, target verify and draft).
- **End-to-end, AgentX on GB300:**
  - DEP16 decode (3P1D c336): +7.8% TPS/GPU and +20% p90 interactivity.
  - DCP8 decode: +4.6% TPS/GPU and +10% p90 interactivity at 3P4D c240, and +2.7% / +13% at the prefill-bound 2P3D c240.
  - The baseline is `TOKENSPEED_MLA` with `tokenspeed_mla_min_split_kv=8`, the setting these recipes already use.
- **Accuracy:** gsm8k with real speculative rejection on the latest revision is 0.961 (DEP16) and 0.967 (DCP8).
- **Opt-in.** The backend is never selected automatically; without `--attention-backend KIMI_K3_KV_BALANCED_MLA` nothing changes.

## Validation

**Unit tests** (`tests/models/kimi_k3/test_kv_balanced_mla.py`, 12 tests, passing on GB300). They check the kernel against an FP32 reference for:
- unequal lengths and an empty request;
- the DSpark draft block (non-causal);
- a DCP8 shard on rank 0, and on rank 5 with interleave 64. The rank-5 lengths end inside that rank's chunks, so the causal mask cuts its last keys. Passing the wrong rank or interleave gives about 80% error, versus 2% when correct.
- a peaked softmax that fails without the P prescale;
- plan plus decode captured in a CUDA graph and replayed with KV lengths changed in place;
- a shared workspace larger than 2 GiB.

The backend tests check that `KIMI_K3_KV_BALANCED_MLA` resolves to this backend, its builder and its base-2 LSE convention, and is in no platform's priority list; that selection rejects an FP16 model, a non-FP8 KV cache, a non-SM10x GPU and a `kv_lora_rank` other than 512; and that `forward_mqa` only runs the kernel. The decode tests check one plan per forward, the DCP path with the LSE, and that a step the kernel can't run raises a `ValueError`.

**Microbenchmark.** Time per decode step on one rank, from CUDA-graph replays, mean of 5 random batches per N. Context lengths are sampled from the AgentX trace (median about 98K tokens, p90 about 284K). Every variant decodes the same requests and was checked against an FP32 reference.

## Details

**KV imbalance in agentic decode.** An agentic decode batch mixes very different context lengths, for example 5K, 20K, 98K and 300K tokens. To spread one request's attention over the GPU, the decode cuts its KV into splits; clusters process the splits in parallel and a reduction merges them. `TOKENSPEED_MLA`, the existing FP8 MLA decode for this model, uses one split count for the whole batch: it's chosen from the batch size and SM count, with `tokenspeed_mla_min_split_kv` as a floor. With a skewed batch, any single count is wrong for most requests:
- **Too many splits for short requests.** Short requests are cut into tiny splits that each pay the per-split setup and the reduction.
- **Too few splits for long requests.** The longest requests leave a tail in which a few clusters stream hundreds of thousands of keys while the rest of the GPU is idle.

`min_split_kv=8` helps the long requests and hurts the short ones; at DCP8 N=128 it is slower than the default (see `ts8` vs `ts1`).

**What the KV-balanced decode does:**
1. **Plan.** A Triton planner gives each request its own split count from its KV length: 1 to 8 splits of at least 1024 tokens, sized to fill at most 8 waves of the GPU's clusters. It writes the planned (query tile, request, split) entries as a device work list. It reads nothing on the host, so it is captured in the decode CUDA graph. It runs once per forward, and every MLA layer reuses it.
2. **Execute.** One wave of persistent 2-CTA clusters walks the work list, so every cluster gets about the same amount of KV.
3. **Skip the merge where possible.** A request planned as a single split stores its final output directly, and the reduction skips it.
4. **Keep small probabilities.** Long splits can make probabilities small enough to flush to zero in E4M3, so P is stored scaled by 2^6 and the LSE removes the factor.

**Code layout** (`vllm/models/kimi_k3/nvidia/kv_balanced_mla/`):
- `kernel.py` and `helpers.py`: TokenSpeed MLA 2.0.3's FP8 decode kernel (MIT), vendored with the changes above. Compared with the release, the kernel adds 347 lines (including renames and casts so it passes `typos` and mypy) and drops its 1,252-line benchmark harness; the helpers add 59 lines, the work-list tile scheduler. They do not import the `tokenspeed_mla` package at runtime.
- `core.py`: the planner and the compiled kernel.
- `decode.py`: the per-layer dispatch: the once-per-forward plan, the DCP arguments and the shape checks.
- `backend.py`: `KimiK3KvBalancedMLABackend`, `KimiK3KvBalancedMLAMetadataBuilder` and `KimiK3KvBalancedMLAImpl`. The impl's `forward_mqa` runs the kernel.
- `vllm/v1/attention/backends/registry.py`: the `KIMI_K3_KV_BALANCED_MLA` entry.

Kimi-K3's MLA layer (`mla.py`) is unchanged: it calls the selected backend's `forward_mqa`.

**Why a standalone backend.** The backend is about 190 lines on the common MLA classes, and it states everything the kernel relies on itself, so a later change to `TOKENSPEED_MLA` can't silently change what this backend runs:
- the FP8 KV cache layout (576 values per token, pages of 32 or 64);
- the decode metadata (`seq_lens`, `block_table`, `dcp_tot_seq_lens`) with uniform query lengths and `UNIFORM_BATCH` CUDA graphs;
- the packed FP8 query from the common MLA impl;
- the base-2 LSE convention of the DCP combine (`lse_base_on_e=False`);
- non-causal multi-token decode for the DSpark draft, with and without DCP.

Prefill uses the configured MLA prefill backend, as in the other MLA backends.

**Supported configurations.** An FP8 E4M3 KV cache, an SM10x GPU, a BF16 model and MLA dimensions (`qk_nope_head_dim`, `qk_rope_head_dim`, `v_head_dim`, `kv_lora_rank`) = (128, 64, 128, 512); backend selection rejects anything else with the reason. Alibi, sliding window, soft cap and non-decoder attention raise a `ValueError` when the layer is built. The kernel also needs more than 64 query rows per request (heads × query tokens) and at most as many requests as it plans for; the head count isn't known at selection, so these fail at model build with a `ValueError`. There is no fallback decode: a decode step the kernel can't run raises a `ValueError` with the reason. In the end-to-end runs every decode shape (target verify q=1–5, draft q=4) ran on the kernel. `cp_kv_cache_interleave_size` is read from the parallel config on every call, since NIXL P/D sets it after the model is built. The DSpark draft takes its backend from the speculative config's `attention_backend`.

**Tradeoffs and limitations:**
- **Size:** the vendored kernel adds about 4.9K lines. Integrating through the `tokenspeed_mla` package instead (reusing its compiled kernel with planned per-request splits) gave about 20% less speedup in our microbenchmarks. The work-list scheduler, direct output and P prescale need kernel changes.
- **Memory:** the split-KV scratch is sized as requests × query tiles × 8 splits of FP16 partial outputs. That's about 0.5 GB for 128 requests at heads=96, q=5, versus about 0.23 GB for TokenSpeed's SM-based bound; it's logged at startup.
- **Host syncs:** by inspection, the decode path adds none. Planning is a device kernel, and the once-per-forward check compares the forward context and a data pointer. This was not checked with `VLLM_GPU_SYNC_CHECK=error`.
