# [Bugfix] Fix M-RoPE positions stride assertion in compile_sizes graphs

[Upstream PR](https://github.com/vllm-project/vllm/pull/62151) · state: open · merged: False

## Original PR description

## Overview

Fixes #50046. When `compile_sizes` is set, `Qwen/Qwen3.5-397B-A17B-FP8` with TP=4 dies at start-up, during CUDA-graph memory profiling, with `AssertionError: expected size 3==3, stride 4097==512 at dim=0`. The cause is `create_concrete_args` in `vllm/compilation/piecewise_backend.py`. It set every symbol, stride symbols included, to the compile size. With this fix, a symbol that Dynamo created only for an input's stride or storage offset keeps its traced value.

Compared with #50445, this fix:

- Also fixes the stride where the graph takes the stride symbol as a SymInt input. [#50445](https://github.com/vllm-project/vllm/pull/50445) still sets that symbol to the compile size, so on Qwen3.5 every single-size graph passes `positions_stride_m` = size to the fused M-RoPE kernel, and the crash becomes silently wrong H/W positions. With vLLM's `fused_qk_rmsnorm_rope_gate` at compile size 16, [#50445](https://github.com/vllm-project/vllm/pull/50445) gives output that differs from eager (`Tensor-likes are not close!`), and this fix matches eager.
- Does not break a case that works today. Take a tensor with no token dim whose stride is the token count, passed across a split: with [#50445](https://github.com/vllm-project/vllm/pull/50445) the size-16 graph fails with `stride 16==64`, and the old code and this fix both pass.
- Adds a test that catches the bug. [#50445](https://github.com/vllm-project/vllm/pull/50445) adds no test.

## Claims

- The command from the issue now starts and serves requests on 4 x H200 with torch 2.14, instead of failing in CUDA-graph memory profiling.
- Graphs compiled for a single entry of `compile_sizes` now keep input strides and storage offsets that do not depend on the token count. Here that is the M-RoPE positions row pitch, 4097. Sizes, SymInt inputs and unbacked sizes still become the compile size, as before.
- New test `test_compile_sizes_keep_input_strides` in `tests/compile/test_compile_ranges.py`. That file already runs in CI.

## Validation

Hardware and software: 4 x NVIDIA H200, torch 2.14.0+cu130, vLLM `0.32.0rc1.dev281+g49cb2bbf7` (commit `49cb2bbf71cfd36ee5aa33d1e184b1cddff55294`), and this commit on top of it for the "after" runs.

Reproducer: the command from the issue. No request is needed, because the bug stops the server at start-up. I added `NCCL_P2P_DISABLE=1` because it was needed to get past NCCL start-up on the test machine. It is not related to the bug.

## Details

Root cause: `create_concrete_args` came in with #35472. It builds the example inputs for graphs compiled for one entry of `compile_sizes`, and it replaced every free symbol in each input's shape, stride and storage offset with the compile size. The M-RoPE `positions` input is `RopeState.positions[:, :num_tokens]`, a slice of a persistent `(3, max_num_tokens + 1)` = `(3, 4097)` buffer. Dynamo gives its row stride a symbol of its own, with traced value 4097. The old code set that symbol to 512, so the size-512 graph asserted stride `(512, 1)`, but the real tensor has stride `(4097, 1)`. Inductor size asserts are on by default for torch >= 2.12, so the assert fails during CUDA-graph capture. On torch < 2.12 the asserts are off by default. There the old code did not crash, but the kernels in the size graphs would read M-RoPE rows 1 and 2 at the wrong offset. This change fixes that case too. I did not run the model on torch < 2.12.

Fix: a symbol is a layout symbol when all of its Dynamo sources (`shape_env.var_to_sources`) are `TensorPropertySource` with a property other than `SIZE`. A layout symbol keeps its traced value, from `shape_env.backed_var_to_val` on torch >= 2.11 or from `var_to_val` before that. Every other symbol takes exactly the old path. I added a temporary debug print and ran the real model with it. The only symbol the fix changes there is `positions.stride(0)`: the old value was the compile size (1 to 512), and the new value is 4097, for every size on all 4 ranks.

Why ask Dynamo where the symbol came from, instead of the simpler options:

- Giving every stride its traced value is wrong for contiguous inputs, whose stride does depend on the size.
- Calling a symbol a size only when it appears in a shape gets it wrong for a size symbol that appears only in a stride, or only as a SymInt input of a subgraph.

Tradeoff: a size graph now fixes each layout symbol to its traced value, not to the compile size. Take a caller that traces with a strided view and later passes a contiguous tensor at a compile size. That worked by chance before, and it now fails the size assert. No vLLM runner does this: MRV1, MRV2 and the spec-decode proposer pass a slice of the same persistent buffer at trace time and at run time.

Not fixed here: one combination fails in the range graph, on the old code and the new code alike. It is unbacked dynamic shapes, plus M-RoPE positions, plus a splitting op. The error is `AssertionError: Shape: 8193 out of considered ranges: [(1, 8192)]`. The cause is that `PiecewiseBackend.__call__` dispatches on the first SymInt input, and there that input is the stride symbol. It needs a different change.
