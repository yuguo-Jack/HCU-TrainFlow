# [Bugfix][MRV2] Write a new request's block-table update once

[Upstream PR](https://github.com/vllm-project/vllm/pull/60123) · state: closed · merged: False

## Original PR description

## Purpose

Fixes #60109 (HiSparse servers crash with an illegal memory access on prefix hits).

A `block_table_updates` row supersedes a request's normal block-table write, and `update_requests` already skips `new_block_ids` for running requests that have one. New requests lacked that guard. `add_requests` staged the `NewRequestData` row, `update_requests` staged the update, both for the same row in the same step, and `_apply_write_kernel` applies staged writes as unordered programs. Ranks could keep either row. With HiSparse prefix-copy adoption, ranks that kept the stale row read null resident pages, and the decode residency resolver overflowed.

Fix: `add_requests` skips the `NewRequestData` row when a table update exists, and `update_requests` writes the update as before.

## Why this instead of #60117

- **It fixes the race where it happens.** MRv2 accepts two unordered writes to one row; #60117 only stops today's single producer (HiSparse) from sending them.
- **It's smaller and symmetric.** Five lines extend the guard `update_requests` already has. #60117 instead has the HiSparse connector rewrite an already-built `NewRequestData`, which also changes what every other reader of that field sees.
- **It costs nothing for other users.** A dict lookup per new request, and one fewer GPU row write when an update exists.

Tradeoff: this touches `gpu/model_runner.py`, while #60117 is HiSparse-only.
