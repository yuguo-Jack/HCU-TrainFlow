# [Bugfix] Disable CUDA graphs for --cpu-offload-gb without pinned memory

[Upstream PR](https://github.com/vllm-project/vllm/pull/60299) · state: open · merged: False

## Original PR description



## Overview

`--cpu-offload-gb` crashes at startup during CUDA graph capture when pinned memory is unavailable, which is the default on WSL2. This disables CUDA graphs for that combination, with a warning that names `VLLM_WSL2_ENABLE_PIN_MEMORY=1` as the way to keep them. Related: #37883 (WSL2 offload crashes, closed as stale), #46690 (open, reworks the same fallback wrapper; complementary, see Details).

## Claims

- WSL2 default (`VLLM_WSL2_ENABLE_PIN_MEMORY` unset) with `--cpu-offload-gb`: startup no longer crashes; the engine runs with torch.compile and without CUDA graphs.
- Pinned-memory platforms (native Linux, or WSL2 with the env var) are unchanged: the new check is skipped and CUDA graphs are still captured.

## Validation

**Unit test** `tests/test_config.py::test_cpu_offload_without_pinned_memory_disables_cudagraphs` calls `CudaPlatform.check_and_update_config` with pinned memory unavailable / available. On main the unavailable case fails (`PIECEWISE == NONE`); with this PR both cases pass.

**End to end** on an RTX 4050 Laptop 6 GB, WSL2 (Ubuntu 24.04, driver 581.86), torch 2.13.0+cu130, main `dac35c5b`, Qwen3-0.6B, `LLM(..., cpu_offload_gb=...)` with defaults otherwise (V2 runner, torch.compile, CUDA graphs), greedy, 3 prompts x 32 tokens:

| Run | main | this PR |
|---|---|---|
| `cpu_offload_gb=0.5`, pinned memory off (WSL2 default) | offloads 0.51 GiB, then `RuntimeError: Cannot copy between CPU and CUDA tensors during CUDA graph capture unless the CPU tensor is pinned` | starts with the new warning, offloads 0.51 GiB (model loading 0.62 GiB vs 1.12 GiB without offload), token ids identical to the no-offload run |
| `cpu_offload_gb=0.5`, `VLLM_WSL2_ENABLE_PIN_MEMORY=1` | CUDA graphs captured | CUDA graphs captured (unchanged path) |
| `cpu_offload_gb=0` | CUDA graphs captured | CUDA graphs captured |

On main, the same offload run with `compilation_config={"cudagraph_mode": "NONE"}` works and gives the same tokens as the no-offload run, which is the configuration this PR selects. Token comparisons across restarts are affected by #58899 (Inductor picks reduction configs by timing): two unmodified-main runs of the pinned arm already differ from each other in one of the three prompts, so I only claim that the no-pin run starts and generates correctly, not bitwise equality across all restarts.

## Details

Root cause: `is_uva_available()` requires pinned memory, so without it `UVAOffloader` takes its fallback path and keeps offloaded parameters in pageable CPU memory, copying them to the GPU inside every wrapped `forward`. Under torch.compile those copies end up in the captured region, and PyTorch refuses to capture a copy from unpinned CPU memory, blocking or not (checked: `copy_` with `non_blocking=True` and `False` both raise the error above inside `torch.cuda.graph`). So no form of the fallback wrapper, including #46690's blocking copies, can run under CUDA graphs without pinned memory; the choice has to be made at config time.

The check sits in `CudaPlatform.check_and_update_config`, next to the existing WSL2 offload warning, and follows the existing pattern of disabling CUDA graphs with a warning for unsupported combinations (XPU graphs, MoonEP). The existing WSL2 warning about pinned-memory limits now fires only when pinned memory is actually in use.

Tradeoff: running without CUDA graphs is slower than WSL2 with pinned memory, but pinned memory on WSL2 is opt-in on purpose (see the existing warning about the WDDM pinned-memory cap), so this keeps that choice with the user instead of crashing.

Not tested: native Linux with pinned memory unavailable, ROCm, TP/PP, MoE or quantized models.

Duplicate check: no open or closed PR changes CUDA graph handling for offload without pinned memory. #46690 changes the fallback wrapper in `offloader/uva.py`, #43453 keeps scale parameters on the GPU, #50784 adds WSL2 troubleshooting docs without offload; none touch this config path.
