## Original PR description

# [Perf][FA4] Warm up dense (paged) FA4 attention kernels

**Repo:** `vllm-project/vllm` · **Branch:** `fa4-dense-cutedsl-warmup`

## Summary
The CuTeDSL warmup path (`register_cutedsl_warmup_provider`) currently only warms the
FA4 **MLA prefill** kernel. Standard GQA models on the `FLASH_ATTN` backend
(`FlashAttentionForwardSm100`) therefore **JIT-compile the dense prefill specialization**
(`q_stage=2`, paged, `seqused_k`) on the first serving request — a large one-time latency
spike (~8 s) that `jit_monitor` explicitly flags as
`CuTeDSL JIT compilation during inference: FlashAttentionForwardSm100`.

This registers the dense FA4 backend (`FlashAttentionMetadataBuilder`) as a CuTeDSL warmup
provider (new `vllm/model_executor/warmup/fa4_dense_config.py`) and precompiles the dense
decode and prefill specializations at startup, mirroring the existing MLA-prefill provider
in `mla/prefill/flash_attn.py`.

- Restricted to the vLLM-compile path (`CompilationMode.VLLM_COMPILE`), where query and
  paged-KV tensors have the contiguous/paged strides the compiled kernel bakes. Under
  `enforce_eager`, tensors can be strided views, so warmup is skipped and eager falls back
  to stock in-serving JIT (unchanged).
- Emits fp8-descale variants when the KV cache is fp8.

## Dependency (why this is a draft)
Requires the paged compile-spec support in `vllm-flash-attention`:
**vllm-project/flash-attention#158** (`compile_flash_attn_varlen_func_from_specs`:
`seqused_k`/`page_table`/`k_stride`/`descale`). The cmake `GIT_TAG` here points at that
PR's commit; it must be updated to the **merged** flash-attn commit before this can build
in CI. Kept as a **draft** until #158 lands.

## Not a duplicate
- #46182 (merged) and #47451 (open) add the CuTeDSL warmup **infrastructure** and apply it
  to FA4 **MLA prefill** only. Neither touches the dense backend
  (`vllm/v1/attention/backends/flash_attn.py`) nor warms `FlashAttentionForwardSm100` for
  standard GQA models. This builds on the merged #46182 provider registry and fills that gap.
- #46167 adds the runtime *monitor* for post-warmup CuTeDSL compiles (the detector), not the
  dense fix. Searched open PRs/issues for dense-FA4 / `FlashAttentionForwardSm100` warmup —
  none found.

## Tests run + results
Hardware: 1× B200 (SM100), vLLM built from this branch. Throughput via
`vllm bench throughput --attention-backend FLASH_ATTN --dataset-name random
--input-len 1024 --output-len 1024 --num-prompts 256`, cold CuTeDSL cache, `VLLM_PLUGINS=""`.

| Model | Metric | Before (stock main) | After (this PR) | FlashInfer ref |
|---|---|--:|--:|--:|
| Llama-3.1-8B (bf16) | output tok/s | 19,935 | **54,957** (2.75×) | 61,320 |
| Llama-3.1-8B (bf16) | in-serving CuTeDSL JIT | 1 (~8 s spike) | **0** | 0 |
| Qwen3-VL-8B-Instruct-FP8 | output tok/s | 21,875 | **64,567** (2.95×) | 73,984 |
| Qwen3-VL-8B-Instruct-FP8 | in-serving CuTeDSL JIT | 1 | **0** | 0 |

- Single-pass FA4-vs-FlashInfer throughput gap: **3.0× → ~1.12×**.
- **`jit_monitor`:** 0 `CuTeDSL JIT compilation during inference` during serving (was 1, the
  dense prefill kernel).
- **Eager fallback:** `--enforce-eager` runs to completion (rc=0), warmup skipped — no regression.

## Model evaluation (output correctness)
Greedy generation (`temperature=0`) with `FLASH_ATTN` vs `FLASHINFER` on Llama-3.1-8B is
**byte-identical** across test prompts (e.g. "17 × 23" → "391", primes → "2, 3, 5, 7, 11").
Warmup only pre-populates the same `compile_key` the engine would JIT, so numerics are
unchanged.

## Residual warmed gap — out of scope for this PR (kernel, not warmup)
After cold-start is eliminated, a ~12% gap remains on decode-heavy workloads. Isolated
attention-kernel microbenchmarks (FA4 vs FlashInfer trtllm, identical paged inputs, outputs
validated to match, CUDA-event timed) attribute it entirely to the FA4 **decode** kernel;
**prefill is at parity or faster**:

| Phase | Scenario (heads 32/8, hd128, bf16, paged) | FA4 vs FlashInfer |
|---|---|--:|
| decode | batch 64, ctx 1024 | 1.55× slower |
| decode | batch 256, ctx 1024 | 1.59× slower |
| decode | batch 256, ctx 4096 | 1.38× slower |
| prefill | batch 1, seq 4096 | 0.80× (FA4 faster) |
| prefill | batch 4, seq 2048 | 0.97× (parity) |
| prefill | batch 8, seq 1024 | 1.02× (parity) |

CUDA graphs (which vLLM already uses for FA4 decode as FULL graphs) eliminate FA4's per-call
host overhead, so at serving batch sizes these pure-kernel ratios drive the end-to-end gap.
Closing it would require FA4 decode-kernel work (a dedicated `q_stage=1` kernel / better
split-KV vs FlashInfer's trtllm-gen decode cubin) — a separate effort, not this PR.
