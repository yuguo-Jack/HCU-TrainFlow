# [Feature] Add MXFP8 expert online quantization to DeepGEMM MegaMoE

[Upstream PR](https://github.com/vllm-project/vllm/pull/65117) · state: open · merged: False

## Original PR description



## Overview


Add an online quant mxfp8 path for DeepGEMM MegaMoE: BF16 expert shards are quantized to MXFP8 with canonical per-32 UE8M0 scales while loading, DeepSeek-V4 selects it automatically when the config requests dynamic MXFP8 experts.

## Claims


- Add a dynamic MXFP8 quantization path for MoE experts: `DeepGemmMegaMoEExperts(..., online_quant=True)` quantizes each BF16 expert shard to `fp8_e4m3` with canonical per-1x32 UE8M0 scales while loading, so the checkpoint needs neither pre-quantized expert weights nor expert scales.
- Enable MXFP8 MegaMoE for DeepSeek-V4: the model resolves `MEGA_MOE_MXFP8` with online quantization when `quantization_config.moe.weight` is dynamic MXFP8, and keeps the existing offline MXFP4 path for every other expert precision.
- Accuracy: with BF16 dense layers, full GSM8K scores 0.9356 and 0.9378 with MXFP8 online experts versus 0.9439 with BF16 experts.

**Accuracy** 
DeepSeek-V4-Flash, full GSM8K test set (1319 questions), 5-shot, greedy. Dense is bf16, the two arms differ only in whether use mxfp8 megamoe or bf16 experts.

| arm | GSM8K |
| --- | ---: |
| bf16 experts | 0.9439 |
| mxfp8 megamoe | 0.9356 / 0.9378 |

**End to end** 
DeepSeek-V4-Flash (BF16) served on 4×SM100 GPU, TP4 + EP:

```bash
vllm serve "$MODEL_PATH" \
  --trust-remote-code \
  --tensor-parallel-size 4 \
  --enable-expert-parallel \
  --quantization mxfp8 \
  --quantization-config '{"ignore": ["*.wo_a"]}' \
  --moe-backend deep_gemm_mega_moe \
  --max-model-len 8192 \
  --gpu-memory-utilization 0.85 \
  --port 30082
```

## Details


**Motivation.** 
The MegaMoE path currently supports only MXFP4 experts. MXFP8 MegaMoE keeps expert accuracy while bringing a substantial speedup (see the DeepGEMM benchmark), so this PR adds an MXFP8 MegaMoE path to vLLM. Because a BF16 checkpoint carries neither fp8 expert weights nor the per-1x32 scales the kernel consumes, the experts are quantized during loading instead of requiring a pre-quantized checkpoint, and the loader writes both the quantized values and their scales into the existing kernel layout so nothing is transformed after load.

**Implementation.**

- `vllm/model_executor/layers/fused_moe/deep_gemm_mega_moe.py`: add `online_quant` to `DeepGemmMegaMoEExperts`; the weight loader routes non-scale expert shards to `_load_online_weight`, which converts the shard to BF16, calls `mxfp8_e4m3_quantize` with the canonical (non-swizzled) scale layout, and stores values and scales through the existing `_load_weight` path. The constructor rejects online quantization for any format other than MXFP8.
- `vllm/models/deepseek_v4/nvidia/model.py`: `resolve_mega_moe_weight_format` returns `(MEGA_MOE_MXFP8, True)` for dynamic MXFP8 experts and `(MEGA_MOE_MXFP4, False)` otherwise; `DeepseekV4MoE` passes that flag to the experts and skips the fp4-only `expert_dtype` check on the online path.

**Tests and docs.** `tests/model_executor/layers/test_mega_moe_online_quant.py` covers config resolution; `tests/kernels/moe/test_deep_gemm_mega_moe.py` checks that online loading is byte-identical to loading pre-quantized shards; `docs/features/quantization/online.md` documents the serving configuration.
