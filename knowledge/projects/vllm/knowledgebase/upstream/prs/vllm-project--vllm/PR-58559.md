# [Warmup] Cover DSv4 sparse top-k and DFlash input-prep Triton specializations that JIT at first request

[Upstream PR](https://github.com/vllm-project/vllm/pull/58559) · state: open · merged: False

## Original PR description

## What

Two Triton kernels still JIT-compile at the first real request despite the JIT warmup, found via Triton cache forensics on PD-disaggregated DeepSeek-V4-Flash DSpark serving (per-config `TRITON_CACHE_DIR` timeline + TTIR diff of warmup-time vs serving-time cache entries). Mid-inference compiles are normally just a one-time latency spike, but on a PP rank that also hosts the Mooncake bootstrap HTTP server they hold the GIL long enough to starve the 5s bootstrap query and fail the first PD request (#58543); they would also trip `--jit-monitor-mode=error` (#56693).

**`ComputeGlobalTopkIndicesAndLensKernel`** (DSv4 sparse attention):
- Its warmup keys pinned `topk_indices_stride == topk` (compact rows). C128A prefill actually passes views into the `c128a_max_compressed`-wide persistent buffer (`sparse_mla.py`), so the physical row stride (e.g. 512) differs from the batch-dependent logical width (128/256/512). The warmup now enumerates the padded-stride variants that serving launches.
- `token_to_req_indices` / `is_valid_token` are sliced at arbitrary token offsets at serving time, so their pointer alignment varies per batch. Both are scalar loads, so the divisibility hint buys nothing: they now use `do_not_specialize_on_alignment`, collapsing the alignment variant matrix instead of enumerating it.

**`_prepare_dflash_inputs_kernel`** (DFlash/DSpark speculator):
- `BLOCK_SIZE = min(256, next_power_of_2(max_tokens_per_req))` follows the largest per-request span in the batch; the worker warmup's tiny synthetic steps only reach the smallest buckets, and the first large prefill chunk compiles a new variant mid-inference. `DFlashSpeculator.warmup_prepare_inputs()` now launches the kernel once per reachable bucket over the speculator's real buffers, wired into `kernel_warmup()`. The prefill-only producer variant (`context_only=True`, #56957) is covered when that mode is present.

## Duplicate-work check

Searched open PRs for triton warmup coverage of these kernels. The DSv4 warmup series ([7/N] #50177, [8/N] #53567, [10/N] #55967), #54345 (prefill metadata JIT), #55918 (logprobs topk widths), and #45601 (sampler top-k/top-p) each cover different kernels; none touch `ComputeGlobalTopkIndicesAndLensKernel` or `_prepare_dflash_inputs_kernel`. This PR follows the pattern established by #55918 (`do_not_specialize_on_alignment` + explicit startup warmup of the reachable specialization set).

## Tests

- `pytest tests/v1/attention/test_indexer_deepseek_v4_slot_mapping.py::test_topk_lens_warmup_uses_physical_c128a_buffer_stride` — warmup keys carry the physical C128A buffer stride (new, CPU).
- `pytest tests/v1/spec_decode/test_dflash2.py::test_dflash_warmup_covers_reachable_block_size_buckets tests/v1/spec_decode/test_dflash2.py::test_dflash_warmup_covers_prefill_only_buckets` — bucket coverage for aggregated and prefill-only modes (new, CPU).
- All three pass; `pre-commit` (ruff, mypy, test-tethering, etc.) is green.

## Model evaluation

No serving-path numerics change: the patch only precompiles specializations that serving would otherwise compile lazily, and drops two alignment specializations that are unused by codegen (scalar loads). The motivating PD both-PP DSpark deployment (prefill PP2×TP2 + decode PP2×TP2, Mooncake) scores GSM8K strict-match 0.9447 on the same stack (#56957), with the compile stalls present; this PR removes them at the root.

AI assistance was used in preparing this PR (root-cause forensics, implementation, and tests).
