# [BugFix][Quantization] Surface FP8 kernel rejection reasons for fp8_per_channel

[Upstream PR](https://github.com/vllm-project/vllm/pull/61324) · state: open · merged: False

## Original PR description

## Overview

Make `quantization="fp8_per_channel"` fail with the scaled-mm chooser's per-kernel rejection reasons instead of a post-allocation Marlin/Humming guard. Fixes #61316.

## Claims

- `MarlinFP8ScaledMMLinearKernel.can_implement` and `HummingFP8ScaledMMLinearKernel.can_implement` reject per-token activation FP8 (W8A16 weight-only) with an explicit reason.
- Both kernels still accept per-tensor activation configs used by the W8A16 / online per-tensor fallback path.
- When no earlier FP8 kernel can implement a PTPC config, `choose_scaled_mm_linear_kernel` raises with the full `Reasons:` list, including Marlin and Humming rejections (no silent W8A16 selection).
- `Fp8PtpcOnlineLinearMethod.create_weights` selects the kernel before allocating weights and prefixes chooser failures with `quantization="fp8_per_channel"`.

## Details

**Root cause:** Marlin's (and Humming's) `can_implement` returned `(True, None)` for every config. For PTPC (`kFp8DynamicTokenSym` + `kFp8StaticChannelSym`), earlier kernels may be rejected (no Cutlass FP8, no torch FP8 scaled_mm, etc.), a W8A16 kernel is selected, and the collected `failure_reason_list` is discarded. A later isinstance guard in `Fp8PtpcOnlineLinearMethod.create_weights` then raised a generic "Requires SM89+ / ROCm MI3xx" message after `super().create_weights()`.

**Approach:** Reject per-token activation in Marlin and Humming so the chooser either falls through to a real W8A8 kernel (e.g. ChannelWiseTorch when available) or raises with all rejection reasons. Move PTPC kernel selection before weight allocation and wrap chooser `ValueError`s with an `fp8_per_channel` prefix while preserving the Reasons list.

**Follow-up from review:** Humming sits after Marlin in `_POSSIBLE_FP8_KERNELS`. Without the same per-token rejection, Marlin's new refusal would fall through to Humming and reintroduce the silent-wrong-kernel failure. Also rebased onto main so the Marlin+Humming post-allocation guard from #60163 is replaced by the chooser path (and the now-unused Humming import in `online/fp8.py` is removed).

**Tradeoff:** Devices that previously selected Marlin/Humming for PTPC and then crashed will now either succeed via an earlier capable kernel or fail earlier with actionable Reasons. Per-tensor / W8A16 Marlin and Humming paths are unchanged.

**Not duplicating:** Searched open PRs for `#61316`, `fp8 rejection reasons`, and `failure_reason_list`. Related open work (#57600) gates Marlin on weight group shapes only; it does not reject per-token activation or fix the PTPC error path. #60163 already documented Humming as W8A16 for PTPC and added the post-allocation isinstance guard this PR replaces.

- selimfedakar · comment · 2026-10-30T15:27:24Z · [source](https://github.com/vllm-project/vllm/pull/61324#issuecomment-6526495394)

Thanks for the fix — I hit the same error-reporting gap while triaging this area, so I read this closely. The approach (reject per-token in Marlin's `can_implement` + select the kernel before weight allocation) looks right, and I verified the main claims against current `main`. One issue I believe is blocking, plus a rebase note.

**Blocking: `HummingFP8ScaledMMLinearKernel` reintroduces the exact bug this PR fixes.**

In the CUDA chooser list (`vllm/model_executor/kernels/linear/__init__.py`, `_POSSIBLE_FP8_KERNELS`), Humming comes *after* Marlin:

```
FlashInfer → Cutlass → B12xTensor → PerTensorTorch → ChannelWiseTorch → Marlin → Humming
```

`HummingFP8ScaledMMLinearKernel.can_implement` unconditionally returns `(True, None)`, and its `is_supported` only requires CUDA + humming installed + SM75+ (`scaled_mm/humming.py`). So on a pre-SM89 box with humming installed, this PR's new Marlin rejection makes the chooser fall through to Humming, which is silently selected for a PTPC config — a W8A16 weight-only kernel quietly serving a config that requested per-token activation FP8. That's the same silent-wrong-kernel failure mode as the original Marlin bug, just one slot later in the list.

This matters more because `main` has moved since this branch was cut: the post-allocation guard in `Fp8PtpcOnlineLinearMethod.create_weights` now excludes **both** Marlin and Humming (`isinstance(self.fp8_linear, (MarlinFP8ScaledMMLinearKernel, HummingFP8ScaledMMLinearKernel))`). This PR deletes the old Marlin-only version of that guard, so after a rebase the Humming protection is gone with nothing replacing it.

Suggested fix: add the same per-token rejection to `HummingFP8ScaledMMLinearKernel.can_implement` (it's W8A16 weight-only for the same reason as Marlin), plus a test mirroring `test_marlin_fp8_rejects_per_token_activation`. That also keeps the "either a real W8A8 kernel or a full Reasons list" invariant you state in the PR description.

**Rebase note:** besides the guard conflict above, once the tuple-guard is removed the `HummingFP8ScaledMMLinearKernel` import in `online/fp8.py` becomes unused → ruff will flag it.

**Things I checked that look safe** (sharing so reviewers don't have to re-derive them):

- The Marlin `can_implement` change can't break the standard `--quantization fp8` Marlin fallback on pre-SM89: `Fp8LinearMethod` only passes `kFp8DynamicTokenSym` when `cutlass_fp8_supported()` (or XPU) — otherwise it uses per-tensor, which Marlin still accepts (`quantization/fp8.py`, activation key selection in `__init__`).
- compressed-tensors FP8_DYNAMIC checkpoints don't reach this path on old GPUs either — the scheme level already falls back to `CompressedTensorsW8A16Fp8` below SM89 (`compressed_tensors.py`), so Marlin never sees a per-token key from there.
- The pre-allocation `weight_shape = (sum(output_partition_sizes), input_size_per_partition)` matches what `OnlineLinearBase.create_weights` actually allocates (`(output_size_per_partition, input_size_per_partition)`), so moving kernel selection before `super().create_weights()` doesn't change the config the chooser sees. It's arguably more robust than the old `layer.weight.shape` read, which assumed the standard weight path.
