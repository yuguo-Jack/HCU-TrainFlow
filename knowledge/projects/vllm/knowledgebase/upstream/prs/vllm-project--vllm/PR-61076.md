# [RL] Add configurable staging and parallel stage pulls to sharded RDT

[Upstream PR](https://github.com/vllm-project/vllm/pull/61076) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Add opt-in host receive staging and parallel owner-stream pulls to the existing
sharded-RDT weight-transfer backend. Defaults remain GPU staging and one stream
in flight.

This extends [#43375](https://github.com/vllm-project/vllm/pull/43375); it does
not replace the backend or alter the weight-reload API. Searches for open PRs
covering sharded-RDT host staging or parallel stage pulls found no duplicate.

## Claims

- `staging_device="host"` receives RDT objects into registered pinned memory
  and asynchronously scatters them to GPU layers. GPU staging remains the
  default.
- `stages_in_flight=N` pulls from up to N independent owner-connected streams,
  each with `num_rdt_buffers` receive slots. The default remains one stream.
- Sync-tagged free signals, bounded slot polling, quant-stream tensor lifetime,
  and transactional re-init preserve correctness under the added concurrency.
- The quant-stream commit also added `update_param_tp_status` to the
  sharded-RDT quant path, so the engine re-reconciles parameter TP state after
  `process_weights_after_loading` like upstream's reload path already did; this
  fixes replicated (`disable_tp`) weights on a subsequent reload through
  sharded RDT. Both paths now share one helper, `_process_loaded_layer` in
  `model_loader/reload/layerwise.py`, so they cannot drift again.
- Host-staging slots are page-locked with `cudaHostRegister` at their exact
  size (no pinned-allocator rounding or caching) and released on every drop
  path; a slot whose release cannot be proven safe is parked, never freed.

## Validation

Current-vLLM validation:

- Post-trim targeted suite on CPU: **28 passed, 3 CUDA-only skipped**:
  `test_sharded_rdt_engine.py`, `test_sharded_rdt_settings.py`, the host-scatter
  and quant-stream CUDA tests, the changed plan invariants, and the
  sync-tagged producer tests.
- Focused sharded-RDT suite on one H100, Ray 2.58, torch 2.13:
  **301 passed, 3 deselected, 0 failed**. The three pre-existing real-model
  bake cases need the repository-wide fixture and were not part of the focused
  harness.
- Four-H100 `examples/rl/rlhf_sharded_rdt_small_ep.py` run over real
  NIXL-UCX, once with GPU staging and once with pinned-host staging. In both
  modes sync 0 changed the generation and sync 1 reproduced it.
- `ruff check`, `ruff format --check`, and `git diff --check` pass.

Large-model end-to-end measurements from the pre-upstream implementation of
the same staging and scheduling behavior:

| workload | serialized | parallel | change |
| --- | ---: | ---: | ---: |
| Qwen3-235B, PP8, two trainer nodes | 7.54 s | 3.86 s, host S=8 | -49% |
| Kimi-K2, published 48-node/four-replica shape | 7.53 s | 4.30 s, host S=8 | -43% |

The current-vLLM smoke validates the port and real GPU/host transport paths.
Its uniform ownership produces one stream, so current-vLLM S>1 coverage is a
targeted scheduler deadlock regression plus plan/pool invariant tests; the
large-model runs above provide the multi-stream performance evidence.

## Details

The existing consumer has one ordered K-deep pull window. Increasing K overlaps
chunks from that order but does not keep independent trainer PP stages active.
This change:

1. partitions the call plan by connected producer ownership;
2. gives each active stream a disjoint K-slot receive block;
3. schedules up to `stages_in_flight` streams while preserving per-owner order;
4. optionally allocates those slots in pinned host memory.

Receive memory is:
`effective_lanes * num_rdt_buffers * rounded_slot_size`. GPU slots remain
outside `gpu_memory_utilization`; host mode moves the receive pool to pinned
memory, but layer materialization still uses GPU memory. Host staging requires
Ray >=2.58; GPU staging retains the Ray >=2.56 floor.

Sync 0 remains one stream at depth one so registration completes before
concurrent transfer. Changes 3-4 from the broader POC (first-arrival packing
and dynamic share-group splitting) are deliberately out of scope.

## Review of 0dcb2d906

I reviewed this PR for correctness and overall simplicity, together with a second independent reviewer, and we cross-checked each other's findings. Line numbers refer to the PR head. `engine` means `sharded_rdt_engine.py` and `trainer` means `sharded_rdt_trainer.py`.

### Correctness

We found no correctness bugs. These are the parts we traced:

- **Defaults** (`staging_device="gpu"`, `stages_in_flight=1`): `_run_lanes` with one lane keeps the old drain-before-issue FIFO order, and empty chunks still signal immediately. `non_blocking=True` has no effect on device-to-device copies.
- **Multiple lanes:**
  - `_stage_components` puts every producer in exactly one stream, and a stream runs in exactly one lane whose window is at most K. A consumer therefore never has more than K produce calls in flight to any one producer, even across a stream handoff.
  - So `max_concurrency = num_consumers * num_rdt_buffers + 4` is still the right size for any `stages_in_flight`, and the producer-ring safety argument still holds.
  - We found no scheduler deadlock. The blocking-issue branch only waits for a slot that a scatter is reading, never for one held by the lane's own undrained window. The bounded `wait_any` breaks the cross-replica shared-pack cycle.
- **Sync-tagged frees:** the trainer increments `_sync_idx` at the start of `send_weights`, and `begin_sync` is only called with it. Early signals are kept for their sync, and signals for a sync that has already ended are dropped. The untagged one-argument call is kept for older producers.
- **Host staging:**
  - The `non_blocking` H2D copy is enqueued before the slot's read-done event is recorded.
  - Slot reuse waits on the generation handshake and on that event.
  - When a slot is regrown, the old host slot is released only after its read-done event.
  - Release failures park the slot instead of freeing it.
- **Quant stream:** `record_stream` on the reloaded layer tensors is the correct fix for cross-stream lifetime.
- **Re-init:** rejecting a geometry change once the worker has started is an improvement. On main, `_ensure_proc_worker` is idempotent, so growing K would have left the event and counter lists too short.

### Simplicity

1. **Hand-written rollback in `init_transfer_engine`** (engine:532-627). About 90 lines snapshot and restore some 15 fields plus copies of their contents. Building the candidate state (router, plan, pool) in locals or a small object, and assigning it only on success, would be much smaller and would not silently miss a field added later.
2. **Duplicated quant post-processing** (engine:1871-1881). `online_quantization_timing_context` plus `update_param_tp_status` is a line-for-line copy of `reload/layerwise.py:_layerwise_process`. A shared helper would stop the two copies from drifting apart. This is also an independent behaviour fix (replicated `disable_tp` weights on reload). It lands inside the "Hold sharded-RDT tensors on the quant stream" commit, and neither that commit message nor the PR body mentions it. Please call it out.
3. **`getattr(self, "_sync_idx", -1)` / `getattr(self, "_sync_idx", None)`** (trainer:1336, 1391): initialize `_sync_idx` in `__init__` instead.
4. **`_check_streams`** (engine:1997): `_stage_components` already merges every co-owner of a group, so the "trainer rank" and "gather group" checks can never fire by construction. Only the "module loading" check guards a real assumption.
5. **Smaller items:**
   - The error-text helper `_host_alloc_request` and the three `validate_*` helpers are more verbose than they need to be.
   - The 5 ms `ray.wait` polling while a lane waits for slot reuse (`_SLOT_POLL_S`, engine:2027) deserves one sentence in the docs.

### Nits

- `_alloc_page_locked_slot` (engine:117-121): if the NIXL registration fails and the rollback `cudaHostUnregister` also fails, the buffer is freed while possibly still page-locked. This is the one path that skips the "park, never free" policy.
- `receive_weights` compares `update_info.sync_idx >= 0` without a type check, so a malformed payload raises a bare `TypeError`.
- The engine tests build objects with `object.__new__` and set every attribute by hand. A new attribute read in a touched path then fails with `AttributeError` rather than as a behaviour failure.
- The new CUDA tests are only scheduled in the NVIDIA CI step; the AMD mirror step was not extended.

`torch.empty(..., pin_memory=True)` goes through PyTorch's CUDA caching host allocator, which rounds every request up to the next power of two. In torch 2.13 the cutoffs `pinned_max_round_threshold` / `pinned_max_cached_size` both default to unlimited (see `CachingHostAllocator.h` / `AllocatorConfig.h`). Combined with the 256 MiB rounding in `buffer_alloc_bytes`, the pinned footprint can be well above the `min(S, stream_count) * K * rounded_slot_size` the docs give:

| slot | pinned |
|---|---|
| 1.25 GiB | 2 GiB (+60%) |
| 2.25 GiB | 4 GiB (+78%) |
| 3 GiB | 4 GiB (+33%) |

For example, S=8, K=2 with 2.25 GiB slots pins 64 GiB per worker, not 36 GiB. That's 256 GiB of locked host RAM on a 4-GPU node. Freed blocks also stay in the allocator's cache, so the regrow path in `_issue_pull` and `shutdown()` don't give the memory back.

Could we allocate pageable memory and register it with `cudaHostRegister` instead? `vllm/v1/kv_offload/cpu/host_register.py` already does this for KV offload, and `non_blocking` copies from registered memory are still async. If that's too much for this PR, at least round slot sizes to a power of two up front so the docs' sizing formula matches reality.
