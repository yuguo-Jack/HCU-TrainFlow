# [Security] Forward cache_salt into LMCache V1 keys

[Upstream PR](https://github.com/vllm-project/vllm/pull/58561) · state: open · merged: False

## Original PR description

## Summary
`LMCacheConnectorV1` stored and loaded external KV from prompt token ids and never mixed in `cache_salt`. Two requests with different salts could therefore reuse the same external chunks, including across a worker restart that emptied the local prefix cache. LMCache's `CacheEngineKey` already isolates keys by `lmcache.tag.*` entries taken from `sampling_params.extra_args["kv_transfer_params"]`. This change stamps `request.cache_salt` into that tag on lookup and on store, for both the default external LMCache adapter and the in-tree adapter. Requests with no salt are unchanged. A request that has no `sampling_params` gets a temporary params object only for the adapter call, then the original `None` is restored so the worker does not see it.

## Changes
- `vllm/distributed/kv_transfer/kv_connector/v1/lmcache_connector.py`: stamp `lmcache.tag.cache_salt` before lookup and before connector metadata is built, and restore temporary sampling params afterward.
- `tests/v1/kv_connector/unit/test_lmcache_connector.py`: cover distinct salts, preserved user tags, overwrite of a conflicting tag, and the no-sampling-params restore path.

## Codepath coverage
- Scheduler lookup (`get_num_new_matched_tokens`) and store metadata (`build_connector_meta`) both stamp the same tag. `update_state_after_alloc` stamps again when lookup is skipped because the request already has local tokens.
- HTTP `/v1` routes, `/invocations`, gRPC, and batch all become `Request` objects that reach those methods when `LMCacheConnectorV1` is enabled.
- The default `use_native=False` path and `use_native=True` both read the tag from sampling params. `LMCacheMPConnector` already forwards `cache_salt` and is unchanged.
- Pooling requests, which have no sampling params, still pass the salt into the adapter for the duration of lookup and metadata build.

## Duplicate-work check
Searched open and merged PRs for `LMCacheConnectorV1`, `lmcache_integration`, and `cache_salt` with LMCache. #56643 binds salt by XOR-mixing token ids, but only inside the in-tree adapter (`use_native=True`), and it also changes multimodal and LoRA keying. The reported cross-salt hit uses the default external adapter, which that diff does not touch. This PR does not repeat that token-id mixing. Other open LMCache salt PRs (#40041, #44097, #45549) are the multi-process connector.
