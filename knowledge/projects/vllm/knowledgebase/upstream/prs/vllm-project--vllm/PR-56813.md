# [MRV2] Cache multimodal prefix ranges per request

[Upstream PR](https://github.com/vllm-project/vllm/pull/56813) · state: open · merged: False

## Original PR description

## Purpose

`compute_mm_prefix_ranges` currently rebuilds PrefixLM multimodal document ranges on every MRV2 attention-preparation step, even though its current inputs are request-lifetime data for a request generation.

This change memoizes those per-request ranges in `EncoderCache` and reuses them across steps while still constructing a fresh batch-index dictionary for the current request order.

Implementation details:

- Keep the memo optional, so direct callers without it preserve existing behavior.
- Partition memoized ranges by `sliding_window`, the current semantic input that affects range filtering.
- Cache present requests, including present empty/non-visual requests, but do not accumulate absent request IDs.
- Let `EncoderCache` own the memo and invalidate a request across all memo contexts on add/replacement/remove.
- Do not mutate or clear previously returned lists during invalidation, so already-built metadata retains its original contents.
- Pass the memo from `DefaultModelState.prepare_attn` only under the existing multimodal PrefixLM gating.

Request finish/preemption and the existing remove/re-add path continue to provide the lifetime invalidation boundary. I also checked current MRV2 consumers of `mm_req_doc_ranges`; no in-place mutation of these range lists was found.

### Duplicate-work check

Before readiness I searched open vLLM PRs for `compute_mm_prefix_ranges` and for multimodal prefix-range caching. I found no existing request-lifetime cache for this host-side range construction.

The closest work is intentionally separate:

- #50539 changes V2 sliding-window/clamp semantics and proposes a new `clamp_in_kernel` semantic input to `compute_mm_prefix_ranges`; it does not cache per-request ranges.
- #48736 buckets downstream multimodal range widths to reduce Triton recompilations; it does not remove per-step host range extraction.

If #50539 lands first, this PR must be rebased so the memo context also includes its new semantic input rather than reusing ranges across different clamp modes.
