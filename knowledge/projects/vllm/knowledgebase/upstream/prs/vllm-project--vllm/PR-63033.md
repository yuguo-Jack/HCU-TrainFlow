# [Bugfix][Multimodal] Make PaliGemma's whole prompt one bidirectional block

[Upstream PR](https://github.com/vllm-project/vllm/pull/63033) · state: open · merged: False

## Original PR description



## Overview

Fixes #62968. PaliGemma attends bidirectionally over its whole prompt (image, BOS, prefix text, trailing newline) in Transformers, but vLLM only made the image span bidirectional. This PR builds the PrefixLM range over the whole prompt for PaliGemma, and keeps each prompt in a single prefill step.

## Claims

- PaliGemma and PaliGemma 2 use the same prompt mask as Transformers. Greedy outputs now match Transformers' default (`token_type_ids == 0` for the whole prompt) instead of Transformers with only the image marked as prefix.
- Applies to both model runners (MRV2 and V1). Other PrefixLM models (Gemma 3, Gemma 4, Molmo2, …) keep their image-span ranges.
- For PaliGemma, chunked prefill and prefix caching are off by default. A prompt is never split across steps, because every prompt token attends to the tokens after it.

<summary>Remaining PaliGemma 2 logprob gap (separate, pre-existing)</summary>

vLLM's PaliGemma 2 first-token logprobs differ from HF fp32 by 0.65–0.83 with or without this PR. The cause is the final logit soft cap: vLLM's PaliGemma reuses `Gemma2ForCausalLM`'s `LogitsProcessor(soft_cap=30)`. Transformers' `PaliGemmaForConditionalGeneration` and big_vision's PaliGemma decode without it. Applying `tanh(x / 30) * 30` to the HF logits brings the gap to 0.12–0.20. Greedy tokens are unaffected because the soft cap is monotonic. I'll send that fix as a separate PR.

## Details

**Root cause.** Both model runners build `mm_req_doc_ranges` from `mm_position.extract_embeds_range()`, i.e. the image placeholder only. PaliGemma's processor marks the whole prompt with `token_type_ids == 0`, and `PaliGemmaModel.forward` turns that into one bidirectional block (`block_sequence_ids`). So in vLLM the image tokens could not see the instruction, and the instruction tokens attended causally.

**Fix.**
- `ModelArchitectureConfig.mm_prefix_whole_prompt` is set by the convertor for `model_type == "paligemma"` when the PrefixLM path is on.
- The shared `compute_mm_prefix_ranges` (`vllm/v1/attention/backends/utils.py`, unified in #56937) takes optional per-request `prompt_lens` and returns `(0, prompt_len - 1)` for each request that has one.
- MRV2: `DefaultModelState` records each request's `prompt_len` and passes it. Dummy requests have no prompt length and keep the image ranges (none).
- V1: `GPUModelRunner` passes `num_prompt_tokens`.
- The range is the original prompt length, so resumed (preempted) requests keep their output tokens causal.

**Single prefill step.** With the whole prompt bidirectional, a token's KV depends on later prompt tokens. So the prompt cannot be chunked, and its blocks cannot be shared through prefix caching.
- `is_chunked_prefill_supported` and `is_prefix_caching_supported` return False for these models, which turns both off by default.
- The scheduler also refuses a partial prompt prefill for a waiting request. That covers the cases where a request gets less than its full prompt even with chunked prefill off: a shared token budget or the encoder budget.

**Tradeoffs and limitations.**
- PaliGemma loses chunked prefill and prefix caching by default. Users who still enable them get correct ranges only for prompts that fit one step.
- A prompt longer than the sliding window keeps the previous image-only ranges. The existing rule drops any range wider than the window. This only applies to PaliGemma 2 896 checkpoints (4096 image tokens).

**Duplicate check.** No open or closed PR references #62968, and nobody claimed it on the issue. The PRs found by keyword (#59637 Triton mm_prefix tile pruning, #62782 drafter shift in the unchunked mm rollback) change other code.
