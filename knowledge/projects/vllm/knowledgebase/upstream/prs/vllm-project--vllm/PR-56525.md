# [Bugfix][Mamba] Guard state-block prefix-cache hits behind the writing step's commit fence

[Upstream PR](https://github.com/vllm-project/vllm/pull/56525) · state: open · merged: False

## Original PR description

# [Bugfix] Guard mamba prefix-cache hits against state not yet committed by its writing step (abort/race poisoning)

**Status: draft pending CI + unit tests. Validated in production on an 8×B300 node serving `moonshotai/Kimi-K3`.**
Depends on / pairs with: *Zero mamba state blocks on (re)allocation* (sister PR).

## Problem

For hybrid models with mamba/KDA cache groups in `align` mode, `MambaManager.cache_blocks` publishes state-block hashes into the prefix cache **at schedule time** — including the checkpoint-block re-key in `_cache_partial_tail_block` — while the chunk that actually writes that state executes **later** (or never, e.g. client abort mid-prefill). The existing staleness guard, `MambaManager.cached_blocks_this_step`, is cleared by `new_step_starts()` at the next schedule pass, so a request scheduled while the publishing step is still in flight can hit a hash whose state does not exist yet.

Observed production failure (`Kimi-K3`, TP8 B300, `VLLM_USE_V2_MODEL_RUNNER=1`, async scheduling): client aborts a ~40–240k-token prefill ~1–2 s in and immediately retries the same prefix. The retry hits the aborted request's deepest published-but-never-written boundary hash, loads it as its initial recurrent state, and generates unbounded garbage (multilingual word salad / raw control tokens). Because the retry then *completes normally*, it commits hashes pointing at poisoned state — every future request sharing the prefix is poisoned until engine restart. Repro rate unpatched: ~1–2/36 cycles (and a real-user incident requiring engine restart).

## Fix

Replace the one-step guard with a fence-based one, mirroring `deferred_frees`:

1. `Scheduler.schedule()` tags each pass with `sched_step_seq + 1`; `KVCacheManager.new_step_starts(seq)` forwards it.
2. `MambaManager` records `_hash_publish_step[hash] = seq` for every hash it publishes (full blocks, partial-tail re-keys, CoW targets) instead of adding to `cached_blocks_this_step`.
3. `Scheduler.update_from_output()` — the point where all GPU writes of the step have landed — increments `processed_step_seq` (now ungated from `defer_block_free`) and calls `kv_cache_manager.commit_step(processed_step_seq)`.
4. `MambaManager.get_num_blocks_to_allocate` defers a hit whose publish seq is above the commit fence with the existing `num_gpu_blocks + 1` "not enough blocks" mechanism — the request waits one step and re-hits a valid boundary. Publishing entries are pruned at commit and dropped on request free (`pop_blocks_for_free`).

Nothing else changes: publication still happens at schedule time (preserving the fast path where a racing retry inherits a *valid* just-written state), and hit-length/reconciliation logic is untouched.

## Why not the alternatives

- *Evict hashes of uncommitted tokens at free time*: insufficient — the racing retry reads the hash **before** the abort is processed, then commits the poisoned state as valid (verified in production A/B).
- *Defer all mamba hash publication to commit time*: closes the race but destroys the same-prefix fast path used by agentic multi-turn workloads (every turn re-resolves to a shallow boundary), and made things observably worse in production testing.
