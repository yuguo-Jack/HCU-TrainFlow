# [Feature] Support MP-backed elastic expert parallelism for single-node DP scaling

[Upstream PR](https://github.com/vllm-project/vllm/pull/60798) · state: open · merged: False

## Original PR description



## Overview

Enable Elastic EP scaling on XPU using multiprocessing (MP) data parallelism, eg. DP 2->4 scaling up. This adds local process management and stateless XPU communication to the existing Elastic EP workflow.

## Claims

- Enable MP Elastic EP scale-up and scale-down on XPU by starting with a live coordination TCPStore and creating or retiring local DP engine processes, without changing the Ray scaling path.
- Support stateless XCCL process groups, XPU communication, and synchronous EPLB weight transfers through a Gloo staging path for stateless groups.

## Validation

### Reproduction
Reproduce on four Intel XPUs:

```sh
# initialize server with dp2
vllm serve axolotl-ai-co/tiny-mixtral-30m --host 0.0.0.0 --port 18080 \
  --tensor-parallel-size 1 --data-parallel-size 2 --data-parallel-backend mp \
  --api-server-count 1 --enable-expert-parallel \
  --all2all-backend allgather_reducescatter --enable-eplb \
  --eplb-config.use_async false --eplb-config.num_redundant_experts 0 \
  --enable-elastic-ep --elastic-ep-max-dp-size 4 \
  --max-model-len 1024 --enforce-eager --attention-config.backend TRITON_ATTN
```

In another terminal:

```sh
curl -fsS --retry 120 --retry-delay 2 --retry-connrefused \
  --retry-max-time 360 http://127.0.0.1:18080/health

generate() {
  curl -fsS http://127.0.0.1:18080/v1/completions \
```

### Test Results
Before this PR: On the main branch at `87d9996abe`, MP Elastic EP cannot initialize DP=2: workers attempt to connect to `127.0.0.1:0`, raise `torch.distributed.DistNetworkError`, and the API exits before scaling.

After this PR: the server returned HTTP 200 for both dp2->dp4 and dp4->dp2 scale requests and also for completion requests.

## Details

### Motivation

Elastic EP scaling is not currently supported on XPU. The existing scale-up and scale-down flow manages Ray actors, while XPU deployments using the local MP backend need to create and retire local engine processes. This PR enables Elastic EP scaling on XPU through MP.

### Design

- Reuse the existing Elastic EP prepare/commit flow. Add MP-specific scale-up and scale-down methods to the local process manager; keep the Ray actor path unchanged. The MP manager retains the coordination store, starts new engines with the existing frontend addresses, and tracks active ranks so retiring processes are not treated as failures.
- Create stateless XCCL groups on XPU for reconfiguration. The registered-group EPLB `P2POp` path cannot operate on these groups, so stateless synchronous EPLB transfers stage through Gloo; registered-group transfers retain their original path.
- Keep the original XPU uneven collective and post-transfer warmup behavior rather than adding feature-specific replacements.

### Limitations

MP scaling currently requires all DP ranks on one node and enough local XPUs for the target size. The Intel CI job requests only `gpu: 1+`, so its four-XPU collective test may skip on smaller agents; the four-XPU serving run above provides end-to-end validation for the tested configuration, not accuracy or performance coverage for other models.

### Duplicate PR Check

[#57196](https://github.com/vllm-project/vllm/pull/57196) independently adds the XPU stateless process-group factory. That method is the overlapping code; after #57196 merges, will rebase and drop the duplicated method here. 

[#43202](https://github.com/vllm-project/vllm/pull/43202) addresses externally managed Elastic EP ranks, not local MP process creation and retirement.
