# [Feature] Support MP-backed elastic expert parallelism for single-node DP scaling

[Upstream PR](https://github.com/vllm-project/vllm/pull/60798) · state: open · merged: False

## Original PR description

## Overview

Enable single-node Elastic EP scaling with multiprocessing (MP) data parallelism, including DP 2->4->2 on CUDA. The MP backend creates and retires local DP engine processes during scaling, while reusing the existing Elastic EP prepare/commit workflow.

## Claims

- Support single-node MP Elastic EP scale-up and scale-down on CUDA by adding and retiring local DP engines while serving requests.
- Preserve expert-parallel communication and synchronous EPLB weight transfers across DP reconfiguration, without changing the existing Ray scaling path.


Result:

| Test | Goal | Result | Accuracy: initial DP2 / scaled DP4 / scaled DP2 | Output tokens/s: initial DP2 / scaled DP4 / scaled DP2 |

| `eager_none` | Scale without sustained traffic; check active ranks and GSM8K. | PASS | 0.910 / 0.910 / 0.910 | 143.871 / 286.540 / 145.079 |
| `eager_light` | Scale with one rank-pinned client. | PASS | 0.887 / 0.914 / 0.910 | 110.342 / 271.632 / 141.239 |
| `eager_heavy` | Scale with one unpinned client per source rank. | PASS | 0.914 / 0.898 / 0.922 | 121.653 / 274.325 / 153.146 |
| `cuda_graphs_heavy` | Scale with heavy traffic under CUDA Graph. | PASS | 0.918 / 0.898 / 0.906 | 188.431 / 398.051 / 191.692 |

Eager and CUDAGraph mode passed the tests. scaled vs cold comparisons met the acceptance thresholds.

*Defensive comments*: Why does throughput vary between initial DP2 runs? Why is cold DP4 slower than scaled DP4? Both are mainly due to synchronous expert rearrangements counted in the evaluation time and not issues caused by mp implementation. Initial `eager_none` had two (65.86 + 60.72 s), `eager_light` three (57.87 + 64.95 + 58.16 s), and `eager_heavy` three (55.40 + 54.02 + 50.32 s). Scaled DP4 had one (42.61 s); cold DP4 had two (67.42 + 42.91 s), with the second delaying its last five questions.

## Details

### Design

- Reuse Elastic EP's prepare/commit flow. The MP process manager keeps the coordination TCPStore alive, starts or retires local DP engines, and tracks active ranks; the Ray path is unchanged.
- Rebuild the distributed communication groups as DP membership changes and use the existing CUDA EP/EPLB reconfiguration path.

### Limitations

- This PR support single-node Elastic EP only.

### Duplicate PR Check

[#43202](https://github.com/vllm-project/vllm/pull/43202) addresses externally managed Elastic EP ranks, not local MP process creation and retirement.

<details>
<summary>Reproduce commands</summary>

Run the following two commands in two terminals in the same environment. `vllm` needs to be installed from the checkout of this PR.

### 1. Start vLLM at DP2

```bash
cd /workspace/vllm  # MP Elastic EP checkout
export CUDA_VISIBLE_DEVICES=0,1,2,3

vllm serve Qwen/Qwen3-30B-A3B \
  --host 127.0.0.1 --port 8000 \
  --tensor-parallel-size 1 \
  --data-parallel-backend mp --data-parallel-size 2 \
  --enable-expert-parallel \
  --all2all-backend allgather_reducescatter \
  --enable-elastic-ep --elastic-ep-max-dp-size 4 \
  --enable-eplb --eplb-config.use_async false \
  --eplb-config.num_redundant_experts 0 \
  --gpu-memory-utilization 0.9 --max-model-len 4096 \
  --api-server-count 1 --no-enable-prefix-caching \
  2>&1 | tee /tmp/mp-elastic-ep-e2e.log
```

### 2. Check each rank, scale up, then scale down

```bash
set -euo pipefail
BASE=http://127.0.0.1:8000

for i in {1..480}; do
  if curl -fsS --max-time 3 "$BASE/health" >/dev/null 2>&1; then break; fi
  sleep 5
done
curl -fsS "$BASE/health" >/dev/null

check_ranks() {
  local dp_size="$1" rank
  for ((rank=0; rank<dp_size; rank++)); do
    printf 'DP%s rank %s: ' "$dp_size" "$rank"
    curl -fsS --max-time 180 "$BASE/v1/completions" \
      -H 'Content-Type: application/json' \
      -H "X-data-parallel-rank: $rank" \
      -d '{"model":"Qwen/Qwen3-30B-A3B","prompt":"What is 2 + 2?","max_tokens":32,"temperature":0}' |
      python -c 'import json,sys; r=json.load(sys.stdin); assert r["choices"][0]["text"]; print("HTTP 200, non-empty completion")'
  done
}

scale_to() {
  local target="$1"
  curl -fsS --max-time 1200 "$BASE/scale_elastic_ep" \
    -H 'Content-Type: application/json' \
    -d "{\"new_data_parallel_size\":$target}" |
    python -c 'import json,sys; n=sys.argv[1]; r=json.load(sys.stdin); assert r["message"] == f"Scaled to {n} data parallel engines", r; print(r["message"])' "$target"
}

check_ranks 2
scale_to 4
check_ranks 4
scale_to 2
check_ranks 2
echo 'PASS: DP2 -> DP4 -> DP2'
```
