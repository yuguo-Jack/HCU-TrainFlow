# [Model] Quantize Muse Spark BF16 routed experts to NVFP4 at load time

[Upstream PR](https://github.com/vllm-project/vllm/pull/64552) · state: open · merged: False

## Original PR description

The ModelOpt NVFP4 checkpoint of Muse Spark Open keeps the routed experts of layers 0 and 61 in BF16 (24 GiB each). With the opt-in `muse_spark_quantize_bf16_experts` text-config field (set through --hf-overrides), those layers are built as NVFP4 and their experts are quantized while they load, so all 62 MoE layers run the NVFP4 TRT-LLM MoE and the weights shrink by ~34 GiB. Attention, projections and norms of those layers stay BF16.

Each full expert is quantized on the GPU, one at a time, into the ModelOpt checkpoint layout with the existing online NVFP4 quantizer (one global scale per expert, shared by gate and up), then goes through the normal NVFP4 weight loader. The quantized tensors stay on the GPU until the loader copies them into the parameters: copying them back to fresh pageable host memory stalled late in loading on GB300 (Grace). Quantizing before the TP/EP split matches an offline requantized checkpoint at any TP size. The checkpoint has no activation calibration for these layers and the TRT-LLM NVFP4 MoE takes static input scales, so after loading they take the max input scales of the two nearest calibrated NVFP4 layers.

The field is rejected with MegaMoE and off SM100, and is documented in the ModelOpt quantization page.

Could we use existing online quantization infrastructure here?

Namely:
- `--quantization-config.targets`:
```
     --quantization-config '{"targets":{"*layers.0.feed_forward.experts*":"nvfp4_per_token", "*layers.61.feed_forward.experts*":"nvfp4_per_token"}}'
```
- (re-)quantization of checkpoints https://github.com/vllm-project/vllm/pull/60276 https://github.com/vllm-project/vllm/pull/64378

In https://github.com/vllm-project/vllm/issues/32412 / https://github.com/vllm-project/vllm/issues/32029 and followup https://github.com/vllm-project/vllm/issues/52167, the goal is to have vLLM frontend not be dependent on the model producer library (modelopt, compressed-tensors, etc.), and if possible not on the model arch.

As muse spark MOE is a normal `RoutedExperts`, the API at https://github.com/vllm-project/vllm/blob/main/vllm/model_executor/layers/quantization/online is the one that fits naturally.

A welcome extension would be to have `Nvfpv4OnlineMoEMethod` & NVFP4 oracle compatible with Muse, if any change is needed (or have `MuseSparkNvfp4OnlineMoEMethod(Nvfpv4OnlineMoEMethod)`, alternatively, but using oracle would be cleaner)
