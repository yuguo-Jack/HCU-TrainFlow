# [Perf][Kernel] Tune fused mHC post + pre-norm for SM90 at up to 8 tokens

[Upstream PR](https://github.com/vllm-project/vllm/pull/61461) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

SM90 gets its own split config for the fused mHC post + pre-norm op (DeepSeek-V4/V4.1, GLM-5.3-Flash) at 1–8 tokens, `(tile_n, n_splits, n_thr) = (12, hidden / 512, 256)`, instead of the GB300-tuned bands; other GPUs and token counts are unchanged. Warmup now visits every token count up to 32, so each split compiles at startup.

## Claims

- **Faster on H20 at 1–8 tokens:** 4.7–16.0% at hidden 4096, 8.3–14.0% at 5120 and 12.1–22.6% at 7168 (0–2.5% at 6–7 tokens). This covers DSpark k=5 decode at C1, which runs 6 tokens per step.
- **Numerics:** residual streams are bit-identical; the mixing coefficients, and through them the layer inputs, differ only in FP32 summation order.

## Validation

- Minimum traffic is 1.7–3.9 MB per op: 162–298 GB/s with this PR, 151–275 GB/s on main.
- From 9 to 32 tokens both arms use the same config and agree within ±0.8%.
- At 5120 the new config had the lowest total time over 1, 2, 4, 6 and 8 tokens among 63 configs swept.
- Measured before the last rebase; the kernels and configs are unchanged since.

**Tests:** `pytest tests/kernels/mhc` on H20 at this head: 238 passed, 139 skipped, 1 failed. The failure, `test_mhc_fused_post_pre[4-7168-128]`, runs 128 tokens, outside the band, and fails the same way on main. CI runs `kernels/mhc` only on B200 and MI355.

**End to end** (DeepSeek-V4.1-Flash, 8×H20, TP8, DSpark k=5, before the rebase):
- 1K in / 1K out at a synthetic acceptance length of 3.51, one run per server in the order main, PR, PR, main. At C1 both PR runs beat both main runs: output throughput +0.9%, TPOT p50 −1.0%. At C64, outside the band, both PR runs fall between main's two runs.
- GSM8K 5-shot with real DSpark verification: 1274 / 1319 correct on main and 1276 / 1319 with this PR; acceptance length 3.863 and 3.868.
- A 1-hour serving run built no TileLang kernels after warmup.
- GLM-5.3-Flash and DeepSeek-V4 were checked at the op level only.

## Details

- **Why it is faster:** every (token, tile, k-slice) block recomputes the post mapping. main's `(2, 8, 128)` runs 12 tiles with 4–7 serial memory round trips per thread; the new config runs 2 tiles with 2.
- **Band:** `(12, 8, 128)` also helped 9–18 tokens on H20, but that may depend on H20's 78-SM grid, so the band stops at 8.
- **H100/H200:** not measured. The steps in the H20 timings fit 9 resident blocks per SM for main and 2 for the new config; with 132 SMs, neither would need a second wave up to 8 tokens. On H20, the only cells where the new config spills and main does not (7168 at 6–7 tokens) still match or beat main.
- **Batch invariance:** #65066 (draft) needs one config for every token count, so this branch must be off under it, like the SM100+ one. Whichever of the two lands second adds that condition.
