# [Perf][Kernel] Tune fused mHC post + pre-norm for SM90 at up to 8 tokens

[Upstream PR](https://github.com/vllm-project/vllm/pull/61461) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

The fused mHC post + pre-norm kernel runs twice per decoder layer in DeepSeek-V4/V4.1 and GLM-5.3-Flash. Its split configs were tuned on GB300 (#56633). This PR gives SM90 its own config for 1–8 tokens: `(tile_n, n_splits, n_thr) = (12, hidden / 512, 256)`. Other architectures and token counts are unchanged.

## Claims

- On H20 at 1–8 tokens, the op gets faster:
  - DeepSeek-V4-Flash and GLM-5.3-Flash (hidden 4096): 4.4–16.3%.
  - DeepSeek-V4.1-Flash (hidden 5120): 9.1–14.1%.
  - DeepSeek-V4-Pro (hidden 7168): 2.1–22.8%.
- The band includes DSpark k=5 decode at C1, which runs 6 tokens per step.
- Residual streams are bit-identical. The mixing coefficients, and through them the layer inputs, differ only in FP32 summation order.
- Startup warmup compiles the new variant. Off SM90, the set of compiled kernels is unchanged.

## Validation

**Microbenchmark.** H20, `hc_mult = 4`, FlashInfer CUPTI with a CUDA graph and a cold L2, median of 3 runs of 200 replays. Outputs are checked before timing.
- The 4096 and 7168 columns time `mhc_fused_post_pre_tilelang`, which DeepSeek-V4 and GLM-5.3-Flash call.
- The 5120 column times `mhc_fused_post_pre_delayed_tilelang`, which DeepSeek-V4.1 calls.

- The minimum tensor traffic is 1.7–3.9 MB per op, corresponding to an effective bandwidth of 152–308 GB/s.
- From 9 to 32 tokens, main and this PR pick the same config, and their times agree within ±1.1%.
- At 5120, the new config had the lowest total time over 1, 2, 4, 6 and 8 tokens in a sweep of 63 configs. It was within 4.6% of the best config at each of those token counts.

**Tests.** `pytest tests/kernels/mhc/test_mhc_jit_warmup.py tests/kernels/mhc/test_mhc_kernels.py` passes on H20, with one exception: `test_mhc_fused_post_pre[4-7168-128]`. That case runs 128 tokens, outside the band, and fails the same way without this change.

A 1-hour TP8 serving run built no TileLang kernels after warmup. CI runs `kernels/mhc` on B200 only, so this H20 run is the only coverage for the SM90 cases.

**E2E sanity check.** DeepSeek-V4.1-Flash on 8×H20 with TP8, 1K in / 1K out. It ran on main 240ee8d (2026-10-07) with this change applied; `kernels/mhc/` has not changed since.
- DSpark k=5 at a synthetic acceptance length of 3.51.
- One run per server, in the order main, PR, PR, main.

At C1, both PR runs beat both main runs: output throughput +0.9%, TPOT p50 −1.0%. At C64, which is outside the band, both PR runs fall between main's two runs in throughput and TPOT p50.

**Accuracy.** DeepSeek-V4.1-Flash on the same build, GSM8K, 5-shot, with real DSpark verification:
- Correct answers: 1274 / 1319 on main, 1276 / 1319 with this PR.
- Acceptance length: 3.863 and 3.868.

GLM-5.3-Flash and DeepSeek-V4 were checked at the op level only.

## Details

- **Why it is faster.** Every (token, tile, k-slice) block recomputes the post mapping.
  - main's `(2, 8, 128)` runs 12 tiles, and each thread makes 4–7 serial memory round trips.
  - The new config runs 2 tiles with 2 round trips each.
- **Band.** A separate candidate config, `(12, 8, 128)`, improved latency at 9–18 tokens on H20. Those gains may depend on H20's 78-SM grid scheduling and have not been validated on H100/H200, so this PR leaves that band unchanged.
- **H100/H200.** These GPUs are not measured. Both grids should fit in one wave on 132 SMs, so the gain is expected to carry over. The 6–7-token dip at 7168 looks like a wave spill on H20 and is not expected there.
- **Scope.** SM100, SM120 and ROCm are untouched. No open PR changes this config.
