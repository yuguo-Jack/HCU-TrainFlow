# [Bugfix] Allow pipeline parallelism for Qwen4Exp PLE models and their MTP drafter

[Upstream PR](https://github.com/vllm-project/vllm/pull/60234) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Fixes #54709. Qwen4Exp models with n-gram PLE layers (here `Qwen/Qwen3.8-Flash-Next-FP8`) refused every `--pipeline-parallel-size > 1`, and their MTP drafter failed on the last PP rank. Since #61016, Model Runner V2 passes `input_ids` to every PP stage for models with `requires_raw_input_tokens` (Qwen4Exp sets it), so the PP refusal is obsolete. This PR removes it and fixes the two remaining failures on that path: KV cache allocation on PP ranks and the MTP drafter.

## Claims

- PP>1 works for Qwen4Exp PLE models, with PLE layers on any PP rank.
- KV cache allocation no longer fails on a PP rank that owns none of the layers of a uniform-type cache group.
- The MTP drafter works with PP>1. This is the second bug in the issue. With PP>1 it also needs #62129 (see Details).

## Validation

Hardware and software: 4× NVIDIA H200, branch head `8d2dd01d18` on top of `b515648641`, Model Runner V2, CUDA graphs on. Model: `Qwen/Qwen3.8-Flash-Next-FP8` (48 layers, `ple_layer_ids = [2]`, so decoder layer 1 has PLE).

```bash
VLLM_ENGINE_READY_TIMEOUT_S=3600 vllm serve Qwen/Qwen3.8-Flash-Next-FP8 \
  --pipeline-parallel-size 4 --tensor-parallel-size 1 --max-model-len 8192
```

Before (`main`): exits at config validation, before weights load:

```
NotImplementedError: Qwen4Exp N-gram PLE embedding requires pipeline_parallel_size=1 because non-first pipeline ranks do not receive the raw input_ids it needs. Please run with PP=1.
```

After:

| Config (PP=4) | Result |
|---|---|
| Default partition (PLE layer on rank 0) | `Application startup complete.`, coherent greedy output. Reference for the rows below. |
| `VLLM_PP_LAYER_PARTITION=1,15,16,16` (PLE layer on rank 1) | Serves. Greedy output matches the reference until the first near-tie: 28/32, 4/32 and 32/32 identical tokens on 3 prompts. Max \|Δ logprob\| before divergence 0.11. Needs a local core workaround, see Details. |
| Default partition + `--speculative-config '{"method":"mtp","num_speculative_tokens":1}'` | Serves, also with 4 concurrent requests. `Avg Draft acceptance rate: 89.6%`, mean acceptance length 1.90. Greedy output matches the reference: 28/32, 32/32, 32/32. Run with #62129 applied locally. |

## Details

**Root cause.** PLE needs the raw `input_ids`. Until #61016, the V2 model runner set them to `None` on every PP rank except the first, so `Qwen4ExpForConditionalGenerationConfig.verify_and_update_config` and `Qwen4ExpModelState.__init__` (nvidia and amd) refused any PP>1 when PLE was present. #61016 keeps `input_ids` on later stages for `requires_raw_input_tokens` models but left those refusals in place.

Changes:

1. `vllm/model_executor/models/config.py` and `vllm/models/qwen4_exp/{nvidia,amd}/model_state.py`: remove the PP refusals. The state they guarded (`ngram_context`, query start locations) is built from `req_states`, which every PP rank keeps, and the model forward passes `input_ids` to PLE layers on any rank. If PLE inputs are ever missing, the decoder layer still raises `PLE inputs were not prepared`.
2. `vllm/v1/core/kv_cache_planning.py` (core): on PP ranks without PLE, `allocate_kv_cache` raised `StopIteration`. `_project_kv_cache_groups_to_worker` keeps the global `UniformTypeKVCacheSpecs` for a group whose layers are all on another rank, with empty `layer_names`, so that the worker still has a block size for that group. But `get_kv_cache_config_from_groups` took the layer list from the spec, so those ranks got a cache tensor for `layers.1.ple`, which only one rank has. It now loops over `group.layer_names` with `_get_per_layer_spec`, as `_get_kv_cache_bytes_per_block` and `validate_kv_cache_layout` already do. For every non-empty group, `layer_names` and the spec's dict hold the same layers in the same order, so the layout does not change. Only the empty-group case changes.
3. `vllm/models/qwen4_exp/{nvidia,amd}/mtp.py`: `Qwen4ExpMultiTokenPredictor.forward` branched on `get_pp_group().is_first_rank`. The V2 speculator builds the whole drafter on the last PP rank and calls it with `hidden_states` and no `intermediate_tensors`, so with PP>1 it took the wrong branch. It now branches on `intermediate_tensors is None`, as `qwen3_5_mtp.py` already does.

Tests: `test_kv_cache_config_skips_uniform_group_owned_by_other_pp_stage` is new. The old `test_qwen4_exp_rejects_pipeline_parallel_only_with_ple` asserted the refusal and is removed. The mocked MTP test from an earlier revision is removed per review. The PP path itself is not covered in CI: it needs ≥2 GPUs and this checkpoint.

**Needs attention:**

- MTP with PP>1 hangs in kernel warmup on current `main`, independent of this PR. `warmup_kernels` runs a second greedy pass only when `rejection_sampler is not None`, which is true only on the last PP rank, so that rank waits forever for activations. #62129 fixes it, and the MTP row above was run with that change applied.
- PLE on a later rank for this checkpoint means `VLLM_PP_LAYER_PARTITION=1,...`, which leaves rank 0 with only a linear-attention layer. Startup then fails in `resolve_kv_cache_layout` with `Workers disagree on supported KV cache layouts` (rank 0 supports all layouts, the other ranks `BLNHC`/`BLHNC`). That check is unrelated to PLE and is not changed here. For the PLE-on-rank-1 row, it was relaxed locally to the intersection of the reported layouts.
- `kv_cache_planning.py` is core code. The change only affects the case described in item 2.
