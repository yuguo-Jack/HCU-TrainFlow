# [Bugfix][Muse Spark] Keep the FP32 RoPE tables in FP32

[Upstream PR](https://github.com/vllm-project/vllm/pull/63078) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Muse Spark builds FP32 RoPE tables, but three call sites rotate through `RotaryEmbedding`'s forward, which replaces the table with a BF16 copy (eager) or casts the whole table on every call (compiled): the DSpark context-key precompute and the unfused attention branch of the AMD and NVIDIA attention. This PR passes the table straight to `ops.rotary_embedding` at all three, so the tables stay FP32.

## Claims

- **DSpark context keys** (`MuseSparkDSparkModel.precompute_and_store_context_kv`) are rotated with the drafter's FP32 table, as its config requests (`rope_use_fp32_in_outer_product=True`). The precompute no longer replaces draft layer 0's table, which that layer's fused QK-norm/RoPE/KV-insert kernel also reads. Context-key rotation error goes from 2.36 to 0.25 BF16 ulp on average.
- **Unfused attention** (`MuseSpark1xAttention._qk_norm_rope_kv_insert` in `amd/model.py` when the fused KV insert is unavailable, and in `nvidia/model.py`) no longer replaces each target layer's FP32 table on the first call. In the compiled drafter it no longer casts the full `[1048576, 64]` table to BF16 in every layer on every step (78 µs per layer on MI355X).
- No performance or accuracy change on the default 8×MI355X recipe. TTFT, throughput, GSM8K and acceptance length are within noise, and greedy target outputs are bit-identical.

## Validation

**Reproducer.** The new `tests/models/test_muse_spark_fp32_rope.py` fails on the base branch and passes with this PR. It builds a real 3-layer `MuseSparkDSparkModel` from a DSpark `SpeculativeConfig` with `custom_ops=["all"]`, as in serving, and the Triton attention backend, so attention takes the unfused branch. The tests run the context-K precompute and layer 0's `_qk_norm_rope_kv_insert`. Both assert that the table is still the same FP32 tensor, and that every rotated element is within 1 BF16 ulp of an FP64 rotation with the FP32 table, plus FP32 product rounding where the result nearly cancels. A BF16 table fails that tolerance on its own.

## Details

**Root cause.** `RotaryEmbeddingBase._match_cos_sin_cache_dtype` is called by every `RotaryEmbedding` forward (native, CUDA, HIP/AITER, XPU, CPU). In eager mode it replaces the module's buffer with `cos_sin_cache.to(query.dtype)`; under `torch.compile` it returns a cast copy on every call. Muse Spark's tables are FP32, and Q/K are BF16:

1. The DSpark context-K precompute called `self._rotary_emb(positions, k, None)`. It always runs eager, starting with the memory-profiling dummy run, so it replaced the FP32 table of draft layer 0. From then on, the context keys and layer 0's own Q/K were rotated with a BF16 table. This happens in the default recipe.
2. The unfused attention branch called `self.rotary_emb.forward_cuda(positions, q, k)`. The fused path requires `ROCM_AITER_FA` without the shuffle KV layout, and is also off with DCP, nvfp4 KV, KV sharing, a weighted QK-norm, and temperature-tuned drafts. In those configurations, and in the NVIDIA attention (`nvidia/model.py`, same call), the target (eager) replaced each layer's table, and the drafter (compiled) cast the full table in every layer on every step.

It was found by reading the DSpark context path. It was then confirmed on the base tree under the serving compilation config, where `custom_ops` includes `all` so the RoPE custom op dispatches to `forward_hip`/`forward_cuda`: after one context step, `cos_sin_cache` was a new BF16 tensor. The unit test above reproduces this.

**Fix.** `ops.rotary_embedding` dispatches the Q/K dtype and the table dtype separately and computes in FP32, so all three sites call it with `rotary_emb.cos_sin_cache` directly. On a table of the same dtype the result is identical to `forward_cuda`, which calls the same kernel. The context path passes the keys once (as Q, with `key=None`), because the kernel rotates in place.

**Relation to #62757.** #62757 shares one target RoPE table to save memory; it does not touch the DSpark context path and keeps `forward_cuda` on the unfused branch. It has since merged; this PR is rebased on top of it.

**Limitations.**
- **CUDA was not validated on CUDA hardware.** The NVIDIA attention (`nvidia/model.py`) gets the same one-call change as the AMD one. On CUDA the test's drafter builds NVIDIA layers, so the H200 "Basic Models (Other)" step will be its first CUDA run; we ran the test on MI355X only. The kernel (`csrc/pos_encoding_kernels.cu`) and its dtype dispatch are shared between CUDA and ROCm.
- Memory: in configurations that take the unfused branch, the per-layer target tables now stay FP32 (256 MiB each at 1M positions) instead of being replaced by BF16 copies on the first call.
- The changed sites no longer go through `CustomOp` dispatch, so they don't use the AITER Triton RoPE when `VLLM_ROCM_USE_AITER_TRITON_ROPE=1`. That path also casts the table first, and RoPE takes microseconds here.
- Computing cos/sin in FP32 inside the kernel, instead of reading a table, was measured as an alternative: 2–5% slower than reading the FP32 table on MI355X, and it only saves table memory.
