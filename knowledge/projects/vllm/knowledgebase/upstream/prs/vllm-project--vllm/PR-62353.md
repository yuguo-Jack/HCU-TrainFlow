# [Bugfix][Offload] Free stale pinned copy during prefetch-offload weight loading

[Upstream PR](https://github.com/vllm-project/vllm/pull/62353) · state: open · merged: False

## Original PR description



## Overview

With --offload-backend prefetch, _CpuParamOffloader keeps its original pinned copy of each weight until post_init() while device_loading_context pins a new one, so peak pinned host memory during load is about 2× the offloaded bytes (2.5× with the default allocator). This PR drops the stale reference until sync_cpu_storage(). Related: #60909 (complementary exact-size pinning), #47380 (zero-element pinned assert).

## Claims

- Peak pinned host memory during a prefetch-offload load drops from **2.0× to 1.0×** the offloaded bytes
  with exact-size pinned blocks, and from **2.5× to 1.26×** with PyTorch's default pinned allocator. With
  the default allocator, main also keeps the extra copy *after* loading: it is freed into PyTorch's
  pinned cache, which keeps holding it.
- A 27B W4A16 checkpoint with 11.0 GB offloaded under a 13 GiB memory cap: main is OOM-killed in
  `process_weights_after_loading`; with this change it loads and serves.
- No output change (greedy token ids and logprobs bit-identical).

## Details

**Root cause.** `_CpuParamOffloader._offload_to_cpu_internal()` allocates the pinned copy, points
`param.data` at it, and also keeps it in `_cpu_storage`. Afterwards `process_weights_after_loading` runs
every module with a `quant_method` through `device_loading_context` (also `UnquantizedLinearMethod`, since
`requires_device_loading` defaults to True), then the attention layers in a second pass. The context moves
CPU parameters to the GPU and, on exit, restores each into a new pinned tensor. `_cpu_storage` still
references the old one, so it is only freed when `post_init()` → `sync_cpu_storage()` re-points
`_cpu_storage` at `param.data`. By then every offloaded weight of those modules exists twice. With PyTorch's default pinned allocator, the freed old blocks go to its
cache rather than back to the OS, so the 2× is still held after loading (measured at the end of the run:
`allocated_bytes.current` 4.59 vs 2.30 GiB, VmRSS 6.85 vs 4.57 GiB, BF16 row above).

**Change.** `_offload_to_cpu_internal()` sets `_cpu_storage = None` after pointing `param.data` at the
copy, so `param.data` is the only owner during loading. `sync_cpu_storage()` already rebuilds
`_cpu_storage` from `param.data`. Its device branch handles a weight that is still on the device at sync
time, which is reachable via model-level `process_weights_after_loading()` hooks: they run after the
per-module pass, outside `device_loading_context`. That branch used to copy into the old storage, which
needs the original shape; it now allocates storage from the weight's current shape when there is none.
None of the model runs above take this branch; the first test covers it. The assert message in
`assign_static_buffer()` and the comments that described a stale `_cpu_storage` now say it is set by
`sync_cpu_storage()`.

**Who reads `_cpu_storage`.** Only `prefetch.py`. `get_param_infos()`, `assign_buffer_slot()`,
`assign_static_buffer()` and `start_onload_to_static()` all run in or after `post_init()`, after the sync.
After `post_init()` the state is the same as on main. Reload (`reload_weights`, layerwise), weight
transfer (`update_weights`) and sleep/wake run after `post_init()` and don't call the offloader. Deleted
parameters (`k_scale`/`v_scale`) still end up `_param_deleted` with `_cpu_storage = None`. With
`VLLM_WEIGHT_OFFLOADING_DISABLE_PIN_MEMORY=1` the copies are pageable, and loading and outputs are
unchanged.

**Not changed / limitations.**
- `reload_weights()` with the prefetch offloader changes outputs on main already (4/8 prompts identical
  after an in-place reload of the same weights); the reload module documents "Composition with CPU
  offloading has not been implemented". This PR gives the same outputs as main after a reload (8/8).
- #60909 makes these two allocations exact-size but keeps the old reference, so with it alone the peak
  would be 2.0× instead of 2.5×. The two changes compose; whichever lands second should use #60909's
  allocation helper in the device-branch allocation here.
- Model runs on CUDA (sm_89) only, not on ROCm; all `--enforce-eager` (no CUDA graphs), single GPU. The
  new unit tests also run in CI's Model Executor step, including its MI300 mirror.
- One run per configuration. The reproducer re-run of the BF16 rows on the final commit gave the same
  values (2.299 GiB / 1.833 GiB).
