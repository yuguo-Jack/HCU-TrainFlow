# [ROCm][Perf] Add RDNA4 FP8 block-scale FlyDSL kernels

[Upstream PR](https://github.com/vllm-project/vllm/pull/56005) · state: open · merged: False

## Original PR description

## Purpose

Add FlyDSL FP8 block-scaled GEMM kernels for RDNA4 (`gfx1200` / `gfx1201`)

These kernels are commonly used at for native FP8 models like `Qwen3.8-27B-FP8`
## Dependency

Validated with FlyDSL main at `65e5d8efac9e8732e28f3b412d5cd868f2361258` as of 2026-09-10. building FlyDsl is a requirement for now until its included into the next release

## Performance

On AMD Radeon AI PRO R9700 (`gfx1201`), the included production-router benchmark passed all **18 shapes** against Triton and was faster in every measured case: **1.786× geometric mean**, minimum **1.257×**.

This uses the cached-graph harness with 32 calls and 15 replays, and stock Triton configuration lookup/defaults. These are focused kernel measurements, not an end-to-end serving speedup or a full model-shape sweep.


## Prior work and attribution

The original duplicate search found no competing RDNA4 FP8 block-scale FlyDSL PR. Related [#28649](https://github.com/vllm-project/vllm/issues/28649) concerned model configuration and AITER/Triton enablement; this change adds a vLLM-owned FlyDSL GEMM family. to bring performance natively into vLLM

### Testing

With a working ROCm vLLM installation and the pinned FlyDSL revision.

```bash
python -m pytest \
  tests/kernels/quantization/test_block_fp8.py -k rdna4 -q

python \
  benchmarks/kernels/benchmark_rdna4_fp8_block_scaled_mm.py \
  --calls 32 --replays 15
```

Benchmark vllm serve, same serving params as baseline

```bash
vllm serve Qwen/Qwen3.8-27B-FP8  \
  -tp 4 \
  --load-format fastsafetensors \
  --max-num-seqs 32 \
  --max-model-len auto \
  --kv-cache-dtype fp8 \
  --gpu-memory-utilization 0.90 \

```
benchmark workload
- Streams: 1, 2, 4, and 8
- Synthetic prompt: 2,048 tokens per turn
- Output: 512 tokens per turn
- Turns per conversation: 8

## Validation

- **Run on 2026-09-10, commit `9f79714fc`: 116 passed, 477 deselected, 136 warnings in 51.00 seconds.** No failures or skips. Warnings include AMD SMI, PyTorch, and Triton deprecations.
- Coverage includes graph replay with changed scales, 64-column scale ownership, split-K, ragged M, odd K-block counts, padded weight rows, and large-M register tiles.
- **Qwen3.8-27B-FP8, TP2:** 32 varied-length prompts with eager deterministic decoding produced **32/32 exact generated-token matches against Triton**. Both workers exercised prefill; captured kernel source hashes match the submitted implementation. 


### Benchmark results

The requested benchmark (`--calls 32 --replays 15`) passed **18/18 correctness checks** (`atol=0.0625`, `rtol=0.02`). FlyDSL was faster on **18/18 shapes**: **1.786× geometric mean**, **1.257× minimum**, **2.957× maximum** versus Triton. Largest reported absolute difference: **0.062500**.

Both commands exited successfully and ran sequentially on physical GPU2, AMD Radeon AI PRO R9700 (`gfx1201`), using commit `9f79714fc`, FlyDSL `65e5d8efac9e8732e28f3b412d5cd868f2361258`, Python 3.14.6, and Torch 2.11.0+rocm7.14.0.

Latency is the median of 15 graph replays, each containing 32 calls, divided by 32. Speedup is Triton latency / FlyDSL latency; higher is better. Inputs are cached. Triton uses stock configuration lookup/defaults and emits missing-tuned-config warnings for several shapes. These are kernel timings, not end-to-end serving results.

Thanks for the solid work on the RDNA4 FP8 block-scale FlyDSL kernels.
