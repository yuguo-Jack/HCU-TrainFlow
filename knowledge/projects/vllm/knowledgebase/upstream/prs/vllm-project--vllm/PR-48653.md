# fix: Add FP8 type dispatch to per_token_group_quant_8bit for transformers backend

[Upstream PR](https://github.com/vllm-project/vllm/pull/48653) · state: closed · merged: False

## Original PR description

## Description

When using `--model-impl transformers` with FP8-quantized MoE models (e.g., GLM-5.2-FP8), the engine crashes during initialization because `per_token_group_quant_8bit` doesn't dispatch `Float8_e4m3fn` input types.

## Root Cause

`VLLM_STABLE_DISPATCH_FLOATING_TYPES` at line 274 of `per_token_group_quant.cu` only handles `float`, `half`, `bfloat16`. When the transformers backend passes FP8-quantized tensors through vLLM's quantization fusion ops, the dispatch has no code path for FP8 input.

The kernel template already handles arbitrary types via `static_cast<float>(src)`. Only the dispatch macro was missing FP8 cases.

## Fix

- Added `VLLM_STABLE_DISPATCH_FLOATING_AND_FP8_TYPES` macro to `dispatch_utils.h` that dispatches FP8 types with `scalar_t` alias (not `fp8_t`) so kernel code referencing `scalar_t` works for both floating and FP8 types
- Changed the main kernel dispatch (line 274) to use the new macro
- Left the packed register kernel (line 598) as `HALF_TYPES` — its `static_assert(GROUP_SIZE==128)` only works for 2-byte types (half/bfloat16). FP8 (1 byte) changes the vectorization width and breaks the constraint.

## Testing

- Built vLLM 0.25.1 from source with this patch on 8×B200
- Model: GLM-5.2-FP8 (finegrained FP8 MoE, 78 layers, 754B params, GlmMoeDsaForCausalLM)
- Before patch: `RuntimeError: "per_token_group_quant_8bit" not implemented for 'Float8_e4m3fn'`
- After patch: Model loads successfully (103 sec, all 141 shards)

Note: A separate issue (#48652) blocks the transformers backend from completing the profile run on GLM MoE models. This PR fixes the FP8 dispatch issue only.

- fattchris · comment · 2026-08-03T20:03:05Z · [source](https://github.com/vllm-project/vllm/pull/48653#issuecomment-5171126385)

@hmellor I investigated why this isn't necessary for native models. Here's what I found:

**Native backend:** vLLM controls the full forward pass. Even for FP8-quantized MoE models, intermediate activations (hidden states) are kept in bf16/fp16. Inside `FusedMoE.forward()`, the bf16 activation is passed to `per_token_group_quant_fp8()` → `per_token_group_quant_8bit`. FP8 weights are stored separately and consumed by the GEMM kernel — they never flow through `per_token_group_quant_8bit`. Since input is always bf16, `VLLM_STABLE_DISPATCH_FLOATING_TYPES` is sufficient.

**Transformers backend:** With `--model-impl transformers`, HuggingFace runs the forward pass. For FP8-quantized models, transformers' FP8 linear layers emit FP8-typed activation tensors. vLLM patches these with quantization fusion ops (`+quant_fp8`), which receive FP8-typed input and call `per_token_group_quant_fp8()` → `per_token_group_quant_8bit`. Input dtype is `Float8_e4m3fn` → dispatch macro has no case for it → crash.

**The fix is safe because:**
- The kernel template `per_token_group_quant_8bit_kernel<T, DST_DTYPE, ...>` already handles arbitrary types via `static_cast<float>(src)` — only the dispatch macro was missing FP8 cases
- The PR adds `VLLM_STABLE_DISPATCH_FLOATING_AND_FP8_TYPES` which extends dispatch to `Float8_e4m3fn` (and `Float8_e4m3fnuz` on ROCm), binding as `scalar_t`
- The packed register kernel (line ~598) is untouched — it still uses `VLLM_STABLE_DISPATCH_HALF_TYPES` with `static_assert(GROUP_SIZE==128)` and `VEC_SIZE = 32 / sizeof(T)`. For FP8 (1 byte), VEC_SIZE would be 32 instead of 16, which would break `GROUP_SIZE == THREADS_PER_GROUP * VEC_SIZE`, so correctly left unchanged.

Happy to run any additional tests if needed.

@hmellor — here's a minimal reproducer that doesn't need a full model or the transformers backend. It calls the same C++ kernel that the MoE quantization path uses, with an FP8-typed input tensor:

```python
import torch

group_size = 128

# bf16 input (native backend path) — works
x = torch.randn(8, 2 * group_size, dtype=torch.bfloat16, device="cuda")
x_q = torch.empty_like(x, dtype=torch.float8_e4m3fn)
x_s = torch.empty((8, 2), device="cuda", dtype=torch.float32)
torch.ops._C.per_token_group_fp8_quant(x, x_q, x_s, group_size, 1e-10, -448.0, 448.0, False, False, False)
print("bf16: OK")

# fp8 input (transformers backend path) — crashes
x_fp8 = x.to(torch.float8_e4m3fn)
x_q2 = torch.empty_like(x_fp8, dtype=torch.float8_e4m3fn)
x_s2 = torch.empty((8, 2), device="cuda", dtype=torch.float32)
torch.ops._C.per_token_group_fp8_quant(x_fp8, x_q2, x_s2, group_size, 1e-10, -448.0, 448.0, False, False, False)
# RuntimeError: "per_token_group_quant_8bit" not implemented for 'Float8_e4m3fn'
```

Verified on NVIDIA GB10 (vLLM 0.23.1rc1) and on 8×B200 (vLLM 0.25.1). Same crash at `per_token_group_quant.cu:253` (or `:274` on the PR branch).

**Why native models don't hit this:**

Both backends use `MoERunner` — you're right about that. The difference is **what dtype `hidden_states` has when it arrives at `per_token_group_quant_fp8()`**:

- **Native backend:** vLLM's `Fp8LinearMethod` sets `self.input_dtype = model_config.dtype` (bf16). The linear layer quantizes activations to FP8 *internally*, runs `_scaled_mm`, and returns bf16 output. So `hidden_states` is always bf16 when it reaches the MoE quantization kernel.

- **Transformers backend:** HuggingFace's `compressed-tensors` FP8 linear layers output `Float8_e4m3fn` tensors directly. These FP8-typed activations flow into `TransformersMoERunner.forward()` → `_forward_super()` → `MoERunner.forward()` → `_forward_impl()` → `_apply_quant_method()` → `Fp8MoEMethod.apply()` → `moe_kernel.apply()` → `process_a1()` → `per_token_group_quant_fp8(x_fp8, ...)`. The dispatch crashes because `VLLM_STABLE_DISPATCH_FLOATING_TYPES` only handles `float/half/bfloat16`.

The call chain in the transformers backend:
```
HF forward (FP8 linear → FP8 output)
  → TransformersMoERunner.forward(hidden_states_fp8)
  → _forward_super() → MoERunner.forward()
  → _forward_impl() → _apply_quant_method()
  → routed_experts.forward_modular() → Fp8MoEMethod.apply()
  → moe_kernel.apply() → process_a1()
  → per_token_group_quant_fp8(x_fp8, group_size)
  → torch.ops._C.per_token_group_fp8_quant(x_fp8, ...)
  → VLLM_STABLE_DISPATCH_FLOATING_TYPES  ← CRASH on Float8_e4m3fn
```

**Why the fix is safe:**

The kernel template `per_token_group_quant_8bit_kernel<T, DST_DTYPE, ...>` already handles arbitrary types:
- `ComputeGroupScale` does `static_cast<float>(src)` — works for `Float8_e4m3fn` (via `cuda_fp8.h`)
- `QuantizeGroup` does `static_cast<float>(src) / y_s` — same
- Vectorization uses `vec_size = 16 / sizeof(T)` — FP8 (1 byte) gives `vec_size=16` vs bf16's `vec_size=8`, but `vectorize_with_alignment` is templated and handles this

Only the dispatch macro was missing the FP8 case. The packed register kernel at line 598 is correctly left as `HALF_TYPES` because its `static_assert(GROUP_SIZE==128)` assumes 2-byte types.

Let me know if you'd like me to also post a full `vllm serve` reproducer, but the kernel-level repro above triggers the exact same code path with no model download needed.

- hmellor · comment · 2026-10-14T14:02:50Z · [source](https://github.com/vllm-project/vllm/pull/48653#issuecomment-6170188392)

The crash is real, but FP8 dispatch is not the right fix. On GLM-5.2-FP8, the DSA indexer runs `self.weights_proj(hidden_states.to(self.weights_proj.weight.dtype))`. The Transformers modeling backend FP8-quantizes `weights_proj` because it does not exclude `_keep_in_fp32_modules` from quantization (HF's quantizers do), so the activations are cast to FP8 without any scaling before they reach `per_token_group_quant_fp8`. With FP8 dispatch added, the model would run on those unscaled activations. The fix is to leave `_keep_in_fp32_modules` linears unquantized, which I will include in DSA support for the Transformers modeling backend (GLM-5.2 currently fails earlier there, in DSA attention, see #48652).
