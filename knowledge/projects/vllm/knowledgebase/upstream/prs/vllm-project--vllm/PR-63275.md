# [Spec Decode] Support trace replay with speculative decoding

[Upstream PR](https://github.com/vllm-project/vllm/pull/63275) · state: closed · merged: True

## Original PR description



## Overview

Allow `trace_decode_token_ids` (MRv2 trace replay) together with speculative decoding. A draft is accepted only if it equals the trace token at its position, and the verified tokens are replaced by the trace, so the replay emits the trace and scores it on the decode path while skipping target forward passes for drafts that match.

## Claims

- Trace replay works with ngram, EAGLE3 and MTP speculators; emitted token ids equal the trace for every request.
- With `VLLM_BATCH_INVARIANT=1`, the returned raw logprobs (trace token and top-5) are bitwise equal to trace replay without spec decode.
- Replay speedup with a good drafter: 1.47x–2.03x (EAGLE3, Qwen3-8B), 1.64x–1.88x (MTP, Qwen3.5-35B-A3B-FP8).

## Validation

### Experiments

GB300, one GPU per run, nightly `8e2beaa3bf` with this patch overlaid (the three source files), MRv2. 64 traces per model, up to 512 tokens, 3/4 sampled at temperature 1.0 with a seed and 1/4 greedy, generated by the target model without spec decode. Each replay uses `trace_decode_token_ids=trace, max_tokens=len(trace), logprobs=5`. Arms: A = replay without spec, A2 = A with reversed request order (numerical floor), B = replay with spec (k=3), `*1` = batch size 1 on 16 traces, `*bi` = `VLLM_BATCH_INVARIANT=1`. All arms returned every request with ids equal to the trace and a logprob entry per token.

| Qwen3-8B / EAGLE3 (RedHatAI/Qwen3-8B-speculator.eagle3) | A vs A2 (floor) | - | - | 86.0% | 82.4% |
| | A vs B | 1.47x | 46% | 39.4% | 24.8% |
| | A1 vs B1 | 2.03x | 47% | 100% | 100% |
| | Abi vs Bbi | 1.82x | 46% | 100% | 100% |
| Qwen3.5-35B-A3B-FP8 / MTP | A vs A2 (floor) | - | - | 10.7% | 5.6% |
| | A vs B | 1.64x | 66% | 9.3% | 4.4% |
| | A1 vs B1 | 1.88x | 66% | 9.4% | 4.6% |
| Qwen3-0.6B / ngram | A vs A2 (floor) | - | - | 99.7% | 99.7% |
| | A vs B | 0.82x | 3.5% | 97.7% | 97.7% |

| | Abi vs Bbi | 1.05x | 3.5% | 100% | 100% |

Without batch invariance, the spec arm changes batch shapes, so logprobs differ at the same order as reordering requests. With batch invariance they are bitwise equal. The FP8 MoE model is not batch invariant even run-to-run, so for MTP the evidence is exact token match plus differences at the reorder floor. ngram accepts few drafts on these chat traces and is slower; that is a drafter-quality effect.

Sampling parameters and off-distribution traces (Qwen3-8B / EAGLE3, replay with `temperature=0.5, top_p=0.95`, `logprobs_mode=processed_logprobs`; "random" traces replace every trace token with a uniformly random id, so drafts almost never match):

| traces | comparison | speedup | acceptance | trace-token logprob bitwise equal | top-5 ids equal |
|---|---|---|---|---|---|
| model-generated | Abi vs Bbi | 2.14x | 46% | 99.99% | 98.97% |
| model-generated | A vs B | 2.32x | 46% | 92.1% | 97.1% |
| random | Abi vs Bbi | 0.89x | 0% | 99.36% | 99.99% |
| random | A vs B | 0.68x | 0% | 99.19% | 82.9% |

Emitted ids equal the trace in every arm. Raw logits are bitwise equal under batch invariance (table above), so the remaining processed-logprob differences come from top-p masking: `apply_top_k_top_p_triton` uses the split top-p pipeline for at most 64 rows (`_SPLIT_MAX_BATCH`) and the monolithic kernel above that, and the two can place the nucleus boundary differently. Verification expands each request to k+1 rows, so the two arms land on different paths. This is an existing batch-invariance gap of top-p masking (non-spec decoding hits it too when the batch crosses 64 rows), not specific to trace replay.

## Details

`RejectionSampler._verify` runs the usual rejection sampling, then for requests with a trace `TraceReplayState.apply_trace_to_verified` rewrites the verified tokens: starting from the current trace step, it writes trace tokens while each draft equals the trace token at its position, stopping at the first mismatch, at the bonus position, or at the end of the trace, and sets `num_sampled` accordingly. Logprobs, rejection counts, the committed tokens and the drafter's next-step inputs all read the rewritten `sampled`/`num_sampled`, so no other path changes. The hook is a single kernel launch per verify step with no host synchronization, and requests without a trace return immediately in the kernel.

Penalties stay consistent with non-spec replay: row i of the verify step folds in drafts 0..i-1, and a row is emitted only if all of those drafts matched the trace, so the history of every emitted row is the trace prefix.

Limitations:
- Bitwise equality with non-spec replay requires batch invariance, and for processed logprobs under top-k/top-p it is limited by the top-p masking path switch described above.
- Not covered by tests or experiments: preemption/resume mid-trace, prefix caching, TP/DP, non-neutral penalties. Code reading shows the trace step comes from `total_len - prompt_len`, which these paths keep consistent.
