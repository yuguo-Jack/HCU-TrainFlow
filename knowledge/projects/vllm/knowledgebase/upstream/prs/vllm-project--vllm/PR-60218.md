# [hw-agnostic] Opt-in infrastructure for OOT plugins

[Upstream PR](https://github.com/vllm-project/vllm/pull/60218) · state: open · merged: False

## Original PR description

## Overview

Makes the Transformers backend's private `_resolve` public as `vllm.model_executor.hw_agnostic.resolve`, so out-of-tree plugins can register overrides that reach the layer class vLLM builds. The environment variable `VLLM_USE_HW_AGNOSTIC` is still orthogonal and can be used to choose whether the in-tree or the hw-agnostic implementations should be used. The Transformers backend resolves its layers through the same function.

Usage example:

  ```python
  RMSNorm = hw_agnostic.resolve("layernorm", "RMSNorm")

  @RMSNorm.register_oot
  class MyRMSNorm(RMSNorm): ...
  ```

## Claims

```bash
pytest -v tests/models/transformers/test_layer_registry.py   # 11 passed (1x A100)
```

The new tests cover:
- a plugin override reaching the class the backend builds, with the variable at `0` and `1`, including `GeluAndMul`, which has no hw-agnostic port;
- a missing hw-agnostic module falling back to in-tree, while a broken one raises;
- the in-tree-override warning and the wrong-base `TypeError`.

## Details

- **Opt-in, not rebinding.** Two alternative approaches where tried: A rebinding approach via https://github.com/vllm-project/vllm/pull/57715 and a re-exporting via https://github.com/vllm-project/vllm/pull/53153. However, this approach currently seems to be the best trade-off between isolation and user/developer-experience.
- **Fallback is allowed and logged once.** On the hw-agnostic path, a layer with no hw-agnostic port resolves to the in-tree class, with a single warning. The backend falls back the same way, so the override still applies. That lets a plugin switch all its imports to `resolve` at once. A strict mode could be added later as a backward-compatible flag.
- **Only reachable through `vllm.model_executor.hw_agnostic`.** It lives in `hw_agnostic/_resolve.py`. The module name is private so the `resolve` function doesn't shadow the submodule.
- **The check is in the hw-agnostic `__new__`.** A helper shared by `CustomOp` and `PluggableLayer` replaces their duplicated override lookup. The in-tree `CustomOp` is unchanged.
- **Limitations:**
  - `VLLM_USE_HW_AGNOSTIC` only affects the Transformers backend. Models with a native vLLM implementation build the in-tree class even when it is set, so a plugin that also serves them registers its override for the in-tree class too. This is documented in `custom_op.md`.
  - Type checkers reject a variable as a base class. The docs show a `TYPE_CHECKING` pattern for plugins that run mypy.
  - The in-tree `get_act_and_mul_fn` caches the instance it builds first. An activation built before plugins load keeps the un-overridden class. This is unchanged by this PR and doesn't happen in normal startup.
