# [Bugfix][Core] Uncount stop-trimmed spec tokens from num_computed_tokens

[Upstream PR](https://github.com/vllm-project/vllm/pull/58668) · state: closed · merged: True

## Original PR description

## Purpose

When a speculative decode step stops on an accepted draft (EOS, a stop token, or `max_tokens` reached before the bonus token), `_update_request_with_output` trims the step's later tokens, but `num_computed_tokens` keeps counting them. Rejections are rolled back in `update_from_output`; trimmed tokens are not.

Ordinary requests are freed right after the stop, so the count is never read again. A resumable (streaming-input) request continues: `_update_request_as_session` uses `num_computed_tokens` as the fold boundary, so the next chunk starts "already computed" over positions whose KV belongs to the trimmed drafts.

Prompt `[1, 2, 3]`, `max_tokens=2`, k=2. The prefill samples `10`; a step with drafts `[11, 12]` returns `[11, 12, 13]` (both accepted) and stops at `11`. Folding in the next chunk `[7, 8]`:

| | `all_token_ids` | `num_computed_tokens` | next step computes |
| --- | --- | --- | --- |
| main | `[1, 2, 3, 10, 11, 7, 8]` | 6 | `8` only; `7` reuses draft `12`'s KV |
| this PR | `[1, 2, 3, 10, 7, 8]` | 4 | `7, 8` |

The fix uncounts the trimmed tokens, so `num_computed_tokens` again covers all new tokens but the last kept one. The fold then drops that token exactly as it drops the final sampled token of a non-speculative turn, which is what makes a session's output identical with and without speculative decoding (see the GPU check below).

Under async scheduling the trimmed tokens' placeholders were never released either (`num_output_placeholders` was decremented by the post-trim count), so they are released too. `num_computed_tokens - num_output_placeholders` is unchanged, so neither the async `cache_blocks` frontier nor the `C - P` frontier from #58259 moves.

This count is also what stale block-hash truncation keys on (#52806, and the `del session.block_hashes[num_computed_tokens // hash_block_size:]` suggested on #58259): with the overshoot, the cut point lands too late and leaves stale hashes behind.

Diffusion schedulers inherit the change; resumable diffusion requests were not exercised.

## Not a duplicate

- #44526 clamps `num_computed_tokens` to `num_prompt_tokens` after the fold. That catches only an overshoot past the whole new chunk (`num_new_tokens <= 0`); in the example above it is a no-op and `7` is still skipped. This PR fixes the count where it goes wrong.
- #58259 (merged) fixed the async handoff race. Its `C - P` frontier also covers this case under async scheduling, but not under sync scheduling, where `num_output_placeholders` is always 0. This PR keeps `C - P` unchanged, so the two compose.
- #54979 caps its terminal `cache_blocks` call at `request.num_tokens` to work around the same overshoot; the cap stays correct.
- Searched open and closed PRs and issues for streaming input + speculative decoding, `num_computed_tokens` trimming, and `_update_request_as_session`; no other PR fixes this.

Good catch on this bug! LGTM

A good way understand imo is that, when spec decode requests are retired via `update_from_outputs`, we need to adjust `num_computed_tokens` and `num_output_placeholders` (decrementing both by `num_rejected`). https://github.com/vllm-project/vllm/blob/7871963fcc8cd3484addb2f7abddcd0f2478028d/vllm/v1/core/sched/scheduler.py#L2054-L2066

However, when spec decode tokens are "trimmed" due to a STOP condition, this was not done. Leading to the issues above. Effectively, we need to
```
trimmed = num_new_tokens - retained

# discard trimmed positions, was missing!
num_computed_tokens -= trimmed
num_output_placeholders -= trimmed

# resolve retained output placeholders
num_output_placeholders -= retained 
```

As an optimization, to avoid decrementing `num_output_placeholders` twice (once by `retained`, once by `trimmed`, this PR
```
num_computed_tokens -= trimmed
num_output_placeholders -= num_new_tokens
```

NIT1: Not sure the logprob comparison GPU test is necessary in CI

NIT2: Perhaps we should assert on `num_computed_tokens` being equal to `len(all_token_ids)` when resumable requests stop (after the `_update_request_as_session` but before appending a new streaming input chunk)
