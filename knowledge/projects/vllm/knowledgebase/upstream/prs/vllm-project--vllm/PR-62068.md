# [Bugfix][MoE] Keep per-expert gate/up halves separate under stacked mappers

[Upstream PR](https://github.com/vllm-project/vllm/pull/62068) · state: open · merged: False

## Original PR description



## Overview

Fixes silent weight corruption in `RoutedExperts.load_weights`. A model mapper with `orig_to_new_stacked` (e.g. `LlamaModel.hf_to_vllm_mapper`) renames per-expert `experts.E.gate_proj` / `experts.E.up_proj` to `experts.E.gate_up_proj` and tags the tensor with `shard_id`. `RoutedExperts` then loads each half as a fused `[gate; up]` block, so `up` overwrites `gate` and the gate rows of `w13` are never loaded. Nothing errors, and the output is garbage for any model that combines such a mapper with per-expert expert checkpoints (GPTQ/AutoRound exports, BF16 experts in mixed checkpoints).

Found while bringing up MuseSpark (#61879, a `LlamaModel` subclass) with `intel-ai/Muse-Spark-Open-816B-A42B-INT4`. The change is independent of #61879.

## Claims

- Under a stacked mapper, a per-expert tensor tagged `shard_id` 0 is loaded as `gate_proj` and one tagged 1 as `up_proj`. Before this change both went through the fused `gate_up_proj` chunking path.
- Fused all-expert tensors (no expert id in the name) are unchanged.
- Untagged per-expert `gate_up_proj` tensors (real per-expert fused checkpoints) are unchanged.
- `down_proj` and all other names are unchanged.
- The fix covers every param suffix: `weight`, `qweight`, `scales`, `qzeros`.
- On MuseSpark, MoE block output vs an fp32 reference goes from cos-sim −0.07 (layer 0, BF16 experts) and −0.11 (layer 5, INT4 experts) to 0.99999 (layers 0, 1, 5).

## Details

**Root cause** (`vllm/model_executor/layers/fused_moe/routed_experts.py`):
- `WeightsMapper.orig_to_new_stacked` matches by substring, so the `.gate_proj` → `.gate_up_proj` (shard 0) and `.up_proj` → `.gate_up_proj` (shard 1) rules meant for the dense MLP also rewrite `mlp.experts.E.gate_proj` / `up_proj`. The mapper sets `tensor.shard_id`.
- `RoutedExperts.load_weights` resolves the per-expert name `E.gate_up_proj.*` through the expert mapping as a fused gate/up tensor. It chunks the half-tensor in two and TP-shards each piece into the `w13` gate and up slots, so `up` overwrites what was written from `gate`.

**Fix:**
- New helper `_unstack_per_expert_gate_up(name, tensor)`, called at the top of the per-weight loop in `RoutedExperts.load_weights`.
- It rewrites `gate_up_proj` → `gate_proj` / `up_proj` only when both of these hold:
  - the name has an expert id (`(?:^|\.)\d+\.gate_up_proj\.`);
  - the tensor carries a mapper-assigned `shard_id` in {0, 1}.
- **Why it's scoped this way:**
  - Fused all-expert tensors have no expert id, so the regex skips them.
  - Real per-expert fused checkpoint tensors have no `shard_id`, so the attribute check skips them.
  - No mapper, model or quant-method changes.
  - The diff is +20 lines in `routed_experts.py` plus a 55-line test.

**Alternatives considered:**
- *Fix in the model's `load_weights`.* This was the first version, in `MuseSparkRoutedExperts.load_weights` on #61879. Rejected because every model with a stacked mapper and per-expert checkpoints is exposed.
- *Drop gate/up from the mapper, or exclude `experts.` in `WeightsMapper`.* The dense MLP still needs stacking, and a change to `WeightsMapper` touches the name mapping of every model.
- *Raise on an ambiguous `gate_up_proj`.* Turns silent corruption into an error but leaves the checkpoint unloadable.

**Risk:**
- Low. Only names with an expert id and a mapper-set `shard_id` are affected, and those were already loaded wrong.
- Restored names are always `gate_proj` / `up_proj`. That assumes the expert mapping uses those checkpoint names, as the HF-style mappings that produce this pattern do.
- Only MuseSpark was verified end to end. Other models on `main` that combine stacked mappers with per-expert expert checkpoints were not audited.
- **Unit test coverage:** the unit test covers the helper and the mapper interaction. The `w13` load path itself is covered by the end-to-end check above, not by a unit test.
