# [Bugfix][Core] Fix the PAUSED_NEW unfinished count with a session that stopped while preempted

[Upstream PR](https://github.com/vllm-project/vllm/pull/63447) · state: closed · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

During `pause_generation(mode="wait")` (`PAUSED_NEW`), `get_num_unfinished_requests()` counts `kv_holding_waiting` but subtracts every paused streaming session. A session that stopped while preempted (kept since #58778) holds no blocks and sits in `waiting`, so subtracting it cancels out a running request. The engine goes idle and the pause completes with that request unfinished; with the default `clear_cache=True` the cache reset then preempts it.

## Claims

- Under `PAUSED_NEW`, paused sessions are skipped inside `kv_holding_waiting` instead of subtracted from it, so the count can't drop below the requests that still drain. `UNPAUSED` counting is unchanged.

## Validation

New scheduler test, next to the existing `PAUSED_NEW` count tests:

```
$ pytest tests/v1/core/test_scheduler.py::test_pause_new_counts_running_request_beside_preempted_session
# base c50aca144:  assert 0 == 1  (where 0 = get_num_unfinished_requests())
# with fix:        PASSED

$ pytest tests/v1/core/test_scheduler.py tests/v1/core/test_async_scheduler.py tests/v1/streaming_input/test_scheduler_streaming.py
# base:      56 failed, 230 passed
# with fix:  55 failed, 231 passed
```

The only difference is the new test. The 55 shared failures are multimodal tests that fail in my local env on `LlavaForConditionalGeneration` inspection, with or without this change.

Reaching the state needs a streaming session preempted under KV pressure while its last step is in flight, which the scheduler test sets up directly, as #58778's tests do.

## Details

Introduced by the combination of #60572 (counts only `kv_holding_waiting` under `PAUSED_NEW`) and #58778 (keeps sessions that stop while preempted, with `num_computed_tokens == 0`, so they're enqueued in `waiting`). The new sum walks `kv_holding_waiting` only while paused; that queue holds requests with allocated blocks, so it stays small.

No open issue or PR covers this (searched `get_num_unfinished_requests pause`, `kv_holding_waiting`). AI assistance (Claude Code) was used; I reviewed the change and ran the tests locally.
