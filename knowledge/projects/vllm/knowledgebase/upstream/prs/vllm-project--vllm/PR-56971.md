# [KV Connector] Fingerprint MooncakeStoreConnector keys by cache configuration

[Upstream PR](https://github.com/vllm-project/vllm/pull/56971) · state: open · merged: False

## Original PR description

## Problem

`MooncakeStoreConnector` keys named the model directory, the optional
`cache_prefix`, and the parallel layout. Two instances of the same model
directory that differed in any setting that decides a block's bytes or shape
therefore addressed the same objects, and the consumer applied its own strides
to the producer's raw device memory. Rank-local deployments (the default) carry
no format in their store namespace at all, so `--kv-cache-dtype`, `--dtype`,
`--quantization`, the Mamba cache dtypes, block sizes and the resolved KV cache
layout all collided.

Before this change, on main:

```text
E  AssertionError: assert 'test-model@tp_rank:0@pcp0@dcp0@pp_rank:0@group:0@68617368' != 'test-model@tp_rank:0@pcp0@dcp0@pp_rank:0@group:0@68617368'
```

## Change

- `KeyMetadata` gains `config_fingerprint`; `PoolKey.build_prefix` and
  `_make_mooncake_group_id` embed it as `@cfg:<digest>`.
- `build_store_config_fingerprint()` hashes the settings that decide a block's
  bytes: KV cache dtype, model dtype, quantization, both Mamba cache dtypes, the
  resolved hash block size, every stored cache group's full spec and layer
  count, the resolved KV cache layout, and the parallel sizes the key namespace
  does not already carry (TP/PP/PCP/DCP for rank-local keys; PCP/DCP for
  TP-shared namespaces, whose store TP and PP are in the namespace).
- Head counts are described per whole TP group, so a producer and a consumer of
  different TP sizes still share keys for equal blocks.
- A spec field the digest cannot describe raises instead of being dropped,
  because silently skipping it would let two differently shaped caches share a
  key.
- The digest is logged at startup and documented in the new `Store Key Layout`
  section of `docs/features/mooncake_store_connector_usage.md`.

## Scope

The decode-phase Mamba boundary save this PR originally carried is in main via
#54307, so this PR now carries only the store key fingerprint. The scheduler
changes and their tests are gone.

## Duplicate check

- #56331 adds startup configuration to native KV-offloading namespaces
  (FS/object/P2P); it does not touch Mooncake store keys.
- #64126 adds load-time KV checksums; it detects corrupted payloads and does not
  separate keys.
- #55220 adds commit manifests to the KV offloading connectors; not a store key
  format.

## Tests

```bash
VLLM_TARGET_DEVICE=cpu PYTHONPATH=$PWD .venv/bin/python -m pytest tests/v1/kv_connector/unit/test_mooncake_store_worker.py -x -q
# 252 passed

VLLM_TARGET_DEVICE=cpu PYTHONPATH=$PWD .venv/bin/python -m pytest tests/v1/kv_connector/unit/test_mooncake_store_hma_e2e.py -x -q
# 44 passed, 5 skipped
```

The new tests fail on main (the assertion above), and
`test_mqa_p4_to_d2_uses_shared_rank_zero_namespace` also asserts the fingerprint
is present in a shared-namespace key.

Equal configurations still produce identical keys across processes and ranks,
so hit rates and model outputs for one configuration are unchanged. Existing
store contents become unreachable because the digest is part of the key: the
first requests after an upgrade miss and repopulate. This is called out in the
docs.

AI assistance was used to prepare this change.

- CAICAIIs · comment · 2026-09-15T08:35:57Z · [source](https://github.com/vllm-project/vllm/pull/56971#issuecomment-5677234721)

Two follow-ups I left out of this PR:

- The wider claim window still assumes every group stores each block as it fills, same as the prefill window did. A dropped or aborted decode save can therefore leave a Mamba-only key that no lookup completes. Store bloat, not corruption; making it exact means tracking stored boundaries per group in the scheduler.

- The warning only covers `--prefix-cache-retention-interval 0`. A stale non-zero value either refuses startup or quietly restores the old behaviour, and the connector can't derive the right value because the core's coordinator reads it before the connector is built. Whether it should warn or fail fast I can change here.

Say the word if you want either in this PR; otherwise I'll file them separately.
