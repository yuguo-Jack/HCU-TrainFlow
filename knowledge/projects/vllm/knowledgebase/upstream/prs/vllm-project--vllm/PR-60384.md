# [Perf][ROCm][Quantization] gfx942 MXFP8 linear for decode via AITER asm A16W8 GEMM

[Upstream PR](https://github.com/vllm-project/vllm/pull/60384) · state: open · merged: False

## Original PR description



## Overview

On gfx942 (MI300X, MI325X), MXFP8 linear layers are dequantized to BF16 at load time and run through hipBLASLt. This PR adds an opt-in kernel that uses AITER's MXFP8 GEMM for decode-sized batches instead, reading the FP8 weights directly.

Requires ROCm/aiter#6172.

## Claims

- Faster decode for MXFP8 models on gfx942. On DeepSeek-V4.1-Flash (TP4, MI325X) the dense GEMMs take 0.4 to 0.6 ms less per decode step.
- No accuracy change on GSM8K.
- Off by default. Enable with `VLLM_ROCM_USE_AITER=1 VLLM_ROCM_USE_AITER_MXFP8_ASM_GEMM=1`.

## Validation

`pytest tests/kernels/quantization/test_rocm_aiter_a16w8_mxfp8.py` passes on MI325X. It compares the new kernel with the existing emulation kernel and also checks kernel selection and CUDA graph replay.

End to end on DeepSeek-V4.1-Flash, 4x MI325X, TP4:

| Concurrency | Dense GEMM time per decode step, without | with |
|---|---|---|
| 2 | 2.91 ms | 2.32 ms |
| 4 | 3.00 ms | 2.55 ms |
| 6 | 3.41 ms | 3.00 ms |
| 8 | 3.46 ms | 3.03 ms |

GSM8K 5-shot: 0.9272 with the kernel, 0.9257 without.

These numbers were measured with an earlier revision of this branch that used the same kernels.

```bash
VLLM_ROCM_USE_AITER=1 VLLM_ROCM_USE_AITER_MXFP8_ASM_GEMM=1 \
  vllm serve <DeepSeek-V4.1-Flash> --tensor-parallel-size 4
```

## Details

- The kernel is only used on gfx942, with the flag set, and for weight shapes that AITER has tuned. Everything else keeps the current path.
- Prefill and other large batches still use hipBLASLt, so the layer keeps its BF16 weight next to the FP8 one. For DeepSeek-V4.1-Flash at TP4 that is about 2 GB more memory per GPU.
- The choice between the two paths is made inside a custom op, so it works with `torch.compile` and CUDA graphs.
