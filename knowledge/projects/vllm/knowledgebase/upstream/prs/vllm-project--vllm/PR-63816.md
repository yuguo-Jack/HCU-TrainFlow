# [Bugfix][ROCm][DSv4.1] Guard NaN scores in gfx942 mono routing

[Upstream PR](https://github.com/vllm-project/vllm/pull/63816) · state: closed · merged: True

## Original PR description

## Overview

On gfx942, DeepSeek-V4.1-Flash with `--monokernel` and adaptive DSpark verification dies with `Memory access fault` during CUDA graph capture. The profile replays a context over KV blocks no request has written. The draft FFN then sees NaN router scores. `stage_route` ranks with `fx.max`, which keeps the NaN, so the same expert is picked twice and a later gather indexes off the slot table.

A NaN score now ranks last, and the winner ballot ignores lanes past the expert count. Both edits are in this patch. The KV fill is gone.

## Claims

- Without this patch, the serve command faults during the real capture and the server does not start.
- With both router edits and no KV zero, the real capture finishes and the server starts.
- Finite scores pick the same experts. TPOT on the shapes below stays with stock.
- No config or API change.

## Validation

MI325X, 4 GPUs, gfx942. The fault is on current main. The runs below are nightly `0.32.1rc1.dev505+g00b6c4c56` with main's Python over it, including this `stage_route`. The binaries were not rebuilt from this tree.

## Details

`batches_to_profile` is the only caller that passes a nonzero `context_len` into `_dummy_run`. `set_dummy_context` fills block tables with ids nobody has written, and the draft reads them. Two requests replay 10 tokens, the gfx942 monokernel's multi-tile draft FFN, and that launch faults.

`fx.max` keeps a NaN, and the NaN then compares equal to itself, so the draft shape emits the same expert id twice. The route counts winners with a bitmap, the count comes up short, and the gather reads off the slot table. Ranking the NaN as `-inf` after the max, and masking the ballot with `cursor < ept`, removes the duplicate. Kimi-K3 and MiniMax-M3 already drop NaN scores before ranking. The ballot mask is particular to this router, which holds 2 experts per lane and picks 3.

A local ranking check matches that. Unguarded draft NaN rows pick `[[0, 64, 0], [0, 64, 0]]`, bitmap 28 against 30 slots. With both edits the bitmap is 30 and there are no duplicates. Finite draft scores, and the target 384/6 shape, match with and without the guard. That check is the ranking logic, not the GPU kernel.

`stage_route` runs on every monokernel FFN launch, including target-only decode with adaptive verification off. The TPOT rows are that path.

Warmup and `profile_run` leave `context_len` at 0. `set_dcp_capture_context` is the other fabrication, only when `cp_size > 1`, and this PR does not change it.

`test_nan_draft_route_stays_in_range` launches that draft shape with NaN logits. With this patch it finishes, and each token's ids are unique:

- frida-andersson · comment · 2026-10-27T02:39:24Z · [source](https://github.com/vllm-project/vllm/pull/63816#issuecomment-6432386892)

Yes that makes sense. I've looked into this a bit more. The capture points the block table at blocks no request has written, so draft attention produces non-finite activations for the FFN. `stage_route` is meant to drop those, and this comment says a NaN score weighs 0 and never wins:

https://github.com/vllm-project/vllm/blob/fe77d0906be0c38c5e2c575cd61b545a2fa687e4/vllm/models/deepseek_v41/amd/mono/stages/moe.py#L434-L436

The weight is set to 0, but the score used for ranking is `fx.max(score + bias, -inf)`. `fx.max` propagates NaNs, so they are still present in the top-k selection. For the DSv4.1 draft shape (128 experts, top-3), that can select an expert more than once. The route-table construction assumes unique picks, which is where the later gather can go out of bounds and fault.

`kimi_k3` already pushes a NaN logit to the bottom:

https://github.com/vllm-project/vllm/blob/fe77d0906be0c38c5e2c575cd61b545a2fa687e4/vllm/models/kimi_k3/amd/specialized_decode/mono/stages/moe.py#L397-L399

`minimax_m3` sets a NaN ranking score to `-inf` and its weight to 0:

https://github.com/vllm-project/vllm/blob/fe77d0906be0c38c5e2c575cd61b545a2fa687e4/vllm/models/minimax_m3/amd/specialized_decode/mono/ffn.py#L482-L483

`deepseek_v4` has the same unguarded ranking code, but its mono kernel skips draft layers. So DSv4.1 on gfx942 is the only exposed path I found.

The unread block table comes from the shared capture path, but the fault is this DSv4.1 routing path. I tested startup with the KV zero removed and two defensive changes in `stage_route`: rank NaNs last, and exclude lanes whose cursor is past its expert entries. It reached startup with no fault. I think moving the fix into `stage_route` makes more sense. Let me know what you think @simondanielsson

File: `vllm/v1/worker/gpu/model_runner.py` · line None

This path does not run only at startup. On every elastic EP scale-up and scale-down, surviving workers call capture_model() again via warm_and_capture (elastic_execute.py:604 and :620, for every all2all backend except nixl_ep). That call runs inside preserve_serving_state, and the commit pause keeps caches (clear_cache=False, core_client.py:2053). preserve_serving_state keeps that warmup out of live KV by redirecting writes to the null block and re-zeroing only block 0, but this zero_() wipes the whole pool. With --enable-elastic-ep and DSpark enable_adaptive_verification, which no config check rejects, a prefix-cache hit or a resumed streaming session after a scale event attends over zeroed K/V. The result is wrong tokens with no error. Skip the fill when self.block_tables.redirect_writes_to_null_block is True, or run it only on the first capture.
