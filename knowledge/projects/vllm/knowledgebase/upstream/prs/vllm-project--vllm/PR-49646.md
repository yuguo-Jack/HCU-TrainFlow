# [Bugfix][Spec Decode] Route dflash on Qwen3DSparkModel arch to dspark

[Upstream PR](https://github.com/vllm-project/vllm/pull/49646) · state: open · merged: False

## Original PR description

## Problem

`deepseek-ai/dflash_qwen3_4b_block7` (DFlash, `markov_rank == 0`) and
`deepseek-ai/dspark_qwen3_4b_block7` (DSpark) ship the **same** architecture,
`Qwen3DSparkModel`, and `Qwen3DSparkForCausalLM` serves both -- its Markov head is a no-op
at rank 0.

`SpeculativeConfig` infers the method from the draft **name** before looking at the
architecture, so a `dflash_*` checkpoint gets `method="dflash"`, is EAGLE-renamed to the
unregistered `DFlashQwen3DSparkModel`, and the engine refuses to start. Explicit
`method="dflash"` takes the same path.

Fixes #49614.

## Fix

Route a `dflash` method (explicit or name-inferred) to the dspark path when the draft ships
a self-contained Qwen3 DSpark architecture (`Qwen3DSparkModel`, `Qwen3OmniDSparkModel`).
Standalone DFlash drafts, which have their own registered architecture, are untouched.

## Reproduction

1x H100 80GB, vLLM `0.32.1rc1.dev161+gb272cff36` (commit `b272cff368`); `# Now` is that
same build plus this diff. Local model paths are rewritten to `/models/...` in the logs
below; nothing else is edited. The directory basename matters -- the method is inferred
from the `dflash` in it. Each server below was started on its own free `$PORT`.

```bash
MODEL=/models/Qwen3-4B                 # snapshot of Qwen/Qwen3-4B
DRAFT=/models/dflash_qwen3_4b_block7   # snapshot of deepseek-ai/dflash_qwen3_4b_block7

vllm serve $MODEL --served-model-name Qwen3-4B --max-model-len 4096 \
  --gpu-memory-utilization 0.60 --port $PORT --host 127.0.0.1 \
  --speculative-config "{\"model\":\"$DRAFT\",\"num_speculative_tokens\":7}"
```
