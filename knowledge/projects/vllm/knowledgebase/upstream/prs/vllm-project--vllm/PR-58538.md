# [Security] Reject unresolved paths in Kimi vision loading

[Upstream PR](https://github.com/vllm-project/vllm/pull/58538) · state: open · merged: False

## Original PR description

## Summary
`KimiK25FusedVisionProcessor._to_pil` opened a raw string with `Image.open`, so a path or URL passed in `multi_modal_data` never went through `MediaConnector` or `--allowed-local-media-path`. Non-`data:` strings are now rejected before any file is opened. In-memory images, bytes, and `data:` URIs are unchanged. The chat and tokens-only paths already resolve media through the connector and still pass a `PIL.Image`.

## Changes
- `vllm/transformers_utils/processors/kimi_k25_vision_fused.py`: reject local paths, `file:` URLs, and `http(s)` URLs in `_to_pil`. Image and video-chunk frames share this function.
- `tests/transformers_utils/processors/test_kimi_k25_vision_fused.py`: cover a real image path, a `file:` URL, an `http` URL, a missing path, a non-image file, and a video-chunk frame path. All raise the same `ValueError`. A `PIL.Image` still loads.

## Codepath coverage
- `LLM.generate` with a string inside `vision_chunk` image or video-chunk frames hits `_to_pil` and is rejected.
- Chat, `LLM.chat`, and tokens-only content parts still fetch through `MediaConnector` and pass a `PIL.Image`, which `_to_pil` accepts.
- No other processor calls `Image.open` on a caller-supplied path. `inkling.py` opens bytes only.

## Duplicate-work check
Searched open, draft, and merged pull requests for `kimi_k25_vision_fused`, `_to_pil`, and `KimiK25FusedVisionProcessor`. No open or merged diff rejects this `Image.open` on a raw string. The merged fused-preprocessing change introduced the open and did not confine it. No private fork exists for this report. This is not a duplicate.
