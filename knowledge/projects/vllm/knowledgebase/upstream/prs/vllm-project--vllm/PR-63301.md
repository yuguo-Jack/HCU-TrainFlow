# [Rust Frontend] Fix audio span callsite race and serialize gemma4_hf test

[Upstream PR](https://github.com/vllm-project/vllm/pull/63301) · state: open · merged: False

## Original PR description



## Overview

Fix two test isolation and concurrency races in `vllm-chat`: a `tracing_core` callsite registration race in `audio_pipeline_attributes_stage_timings_to_request` when run in isolation, and concurrent HF Hub cache lock contention between `roundtrip_gemma4` and `roundtrip_gemma4_hf`.

## Claims

- Warms up the multimodal audio pipeline callsites (`vllm.mm.fetch`, `vllm.mm.decode`, `vllm.mm.preprocess`, `vllm.mm.placeholders`) before entering `.with_subscriber(subscriber)` in `audio_pipeline_attributes_stage_timings_to_request`, ensuring the test passes both in isolation and in the full test binary.
- Adds `#[file_serial(hf_gemma4)]` to `gemma4_hf` in `rust/src/chat/tests/roundtrip.rs` to match `roundtrip_gemma4` (which shares the `google/gemma-4-E4B-it` HF Hub cache lock and test vector generation), and removes a stale `#[allow(dead_code)]` attribute on `kimi_k25`.

## Validation

- **Reproducer (without fix vs with fix):**
  - Without fix: Running `cargo test --manifest-path rust/Cargo.toml -p vllm-chat --lib --locked -- audio_pipeline_attributes_stage_timings_to_request` in isolation fails (`assertion failed: timing.placeholders_s > 0.0`), and running `roundtrip_gemma4` + `roundtrip_gemma4_hf` concurrently with an unpopulated cache fails with `Lock file ".../models--google--gemma-4-E4B-it/.locks/..." is already owned by the current process`.
  - With fix: Both pass deterministically in isolation and in parallel.
- **Test commands run:**
  ```bash
  cargo test --manifest-path rust/Cargo.toml -p vllm-chat --lib --locked -- audio_pipeline_attributes_stage_timings_to_request
  cargo test --manifest-path rust/Cargo.toml -p vllm-chat --lib --locked -- audio::tests
  cargo test --manifest-path rust/Cargo.toml -p vllm-chat --test roundtrip --locked -- roundtrip_gemma4
  cargo fmt --manifest-path rust/Cargo.toml --all -- --check
  cargo clippy --manifest-path rust/Cargo.toml --workspace --all-targets --all-features --locked -- -D warnings
  ```
- **Results:** `1 passed; 0 failed` in isolation, `10 passed; 0 failed` in `audio::tests`, `2 passed; 0 failed` in `roundtrip_gemma4*`, and zero `cargo fmt` / `cargo clippy` warnings.
- **Model evaluation:** N/A (test-only reliability fixes in `vllm-chat`).

## Details

- **Root cause:**
  1. `tracing::instrument::WithSubscriber` installs a thread-local default subscriber via `tracing::dispatcher::with_default` as the future is polled on Tokio worker threads. When `with_default` rebuilds `tracing_core` callsite interest caches, only callsites that have already executed at least once are registered in the global callsite list; callsites reached for the first time after a worker thread polls the future can retain `Interest::never()` when no global subscriber is installed. Warming up `info.prepare_multimodal(...)` once before `.with_subscriber(subscriber)` registers all four stage callsites beforehand.
  2. `roundtrip_gemma4` had `#[file_serial(hf_gemma4)]`, whereas `roundtrip_gemma4_hf` resolved and wrote test vectors for the same `google/gemma-4-E4B-it` model without `#[file_serial(hf_gemma4)]`.
- **Duplicate-PR check:** Searched open PRs via `gh pr list --repo vllm-project/vllm --state open --search "audio_pipeline_attributes_stage_timings_to_request OR gemma4_hf"`; no existing PR addresses these test races.
- **AI assistance:** AI assistance was used to diagnose the test races and prepare this PR; all changes were reviewed and verified locally.
