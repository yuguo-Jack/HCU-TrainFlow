# [Bugfix] Exclude cudagraph padding rows from the per-tensor FP8 MoE amax

[Upstream PR](https://github.com/vllm-project/vllm/pull/62138) · state: open · merged: False

## Original PR description

## Purpose

Fixes #62124.

With a dynamic per-tensor FP8 activation scale, the Triton fused-MoE path computes the amax over every row of the batch the model runner hands it. Under CUDA graphs that batch is padded to the capture size, and the padding rows hold whatever the previous step left there: stale hidden states, or, once the router skips padding (`VLLM_MOE_SKIP_PADDING=1`, the default), workspace rows that the first GEMM never wrote. So the scale used for a request's own rows, and with it the request's output, depends on the request that ran before it. The reporter's script shows the first generated token changing with the previous request; `--enforce-eager` is clean because nothing is padded.

Two quantizations see the padding rows: the expert input (`a1`, in `MoEPrepareAndFinalizeNoDPEP.prepare`) and the post-activation intermediate (`intermediate_cache2`, in `TritonExperts.apply`). This PR zeroes the padding rows of both right before the quantization, using the `is_padding` mask the model runner already keeps for the router. The second one reuses the existing `a2_scale_is_global` condition, which already documents this hazard for the rows of remote experts under EP. The V2 model runner only filled that mask under `VLLM_MOE_SKIP_PADDING`; it now fills it always, so the fix does not depend on that flag. Nothing changes for static or per-token/block activation scales (the masked_fill is skipped), and nothing changes without CUDA-graph padding (the mask is all False).

Not covered here: the legacy functional `fused_experts()` entry point and the distributed prepare/finalize implementations, which quantize `a1` themselves; the local path used by the issue's deployment (TP=1, no DP/EP) is the one fixed.

`VLLM_BATCH_INVARIANT=1` does not change this amax, so the contamination is also present in batch-invariant mode; the run below shows it, and the fix removes it there too. (A dynamic per-tensor scale still depends on the other valid rows of the batch, which is a separate concern from this fix.)

## Test Plan

Everything on one NVIDIA GB300 (SM 10.3), `main` at `ce49c47cbb` vs `main` + this PR, `ibm-granite/granite-3.1-1b-a400m-instruct` with the issue's exact command (`--quantization fp8_per_tensor --moe-backend triton`, capture sizes `[1,2,4,8]`, `FULL_AND_PIECEWISE`) and the issue's `repro.py` (claim mode and `--search`; exit code 1 = present, 0 = absent):

- `main`: default, `VLLM_BATCH_INVARIANT=1`, `VLLM_MOE_SKIP_PADDING=0`, `--enforce-eager` (control), and a repeat of the default.
- this PR: default, `VLLM_BATCH_INVARIANT=1`, `VLLM_MOE_SKIP_PADDING=0`, `VLLM_USE_V2_MODEL_RUNNER=0` (the V1 runner), and a repeat of the default.
- Correctness of the masked rows: the eight probe prompts of `repro.py` cut to 28 lengths, 5 greedy tokens with top-20 logprobs after a plain primer, on four servers: `main` and this PR with capture sizes equal to the prompt lengths (so the prefill step has no padding rows), and `main` and this PR with capture sizes `[1,2,4,8,16]` (padded). With this PR the padded answer must equal the unpadded one, and the first token (the unpadded prefill step of the `main` server) must equal `main`'s.
- `lm_eval` gsm8k (5-shot, 1319 problems) on `main`, `main --enforce-eager` and this PR, same model and flags.
- Cost: `vllm bench throughput` (random dataset, 2000 prompts, seed 0), `main` vs this PR alternating, six runs per side, same model and flags. The second command of each pair passed `--input-len 64 --output-len 256`, but the random dataset's defaults take precedence over those legacy flags (the bench warns about it), so all twelve runs sampled 1024-token prompts with 128 output tokens; the sampled lengths and token totals from each log are included below.
