# [Bugfix] Treat tool parameter schemas without a type as allowing any type

[Upstream PR](https://github.com/vllm-project/vllm/pull/47569) · state: closed · merged: False

## Original PR description

## Purpose

Fixes #47557

Per JSON Schema semantics, a schema without a `type` constraint permits **any** type, and the official OpenAI API behaves that way. vLLM's `extract_types_from_schema()` in `vllm/tool_parsers/utils.py` instead defaulted to `["string"]` whenever no type information could be determined, so a tool parameter whose schema omits `type` (e.g. only has a `description`) always came back as a string — the issue's repro produced `{"value": "5"}` where OpenAI produces `{"value": 5}`.

## Changes

- `extract_types_from_schema()` now returns the full set of JSON types (`string, number, integer, boolean, null, object, array`) when no type info is found, instead of `["string"]`. With the full set, `coerce_to_schema_type()`'s existing priority order (null > integer > number > boolean > object > array > string) coerces values to their natural JSON type: `"5"` → `5`, `"true"` → `true`, `"hello"` → `"hello"`, matching OpenAI behavior.
- `DeepseekV32ToolParser._param_types_for_name()` (the only production caller) now routes its fallback through the same helper, so the streaming path buffers and coerces untyped params exactly like the non-streaming path. No change to `_can_stream_raw_param()` behavior: untyped params were buffered before (string ⊄ {object, array}) and still are.
- Updated the three fallback unit tests and added a `TestUntypedSchemaCoercion` suite covering the issue repro (integer, float, boolean, null, object, array, plain text, and quoted-JSON-string values against an untyped schema).

```

extract_types_from_schema({"type": "string"}) == ["string"]         # unchanged
```

When the DeepSeek parser has no tool schema (or sees an extra parameter), `_convert_params_with_schema` calls `extract_types_from_schema(param_config.get(name, {}))`; with this fallback an empty dict now returns every JSON type, so no-schema `string="false"` parameters like `count=42` and `flag=true` are emitted as JSON number/bool instead of strings. This changes behavior even though there is no JSON Schema to apply the “missing type permits any type” rule to, and it breaks the existing `tests/tool_parsers/test_deepseekv32_tool_parser.py::test_no_schema_keeps_strings` expectation.
