# [Perf][HiSparse] Avoid repeated prefix scans and residency updates

[Upstream PR](https://github.com/vllm-project/vllm/pull/57930) · state: closed · merged: True

## Original PR description

## Purpose

HiSparse's scheduler overhead grew with both context length and the number of resident groups:

- `plan_prefix_materialization` rescanned every computed page on each call, including the durable prefix it always skips.
- `plan_prefix_materialization` and `update_residency` ran from `HiSparseResidentManager.cache_blocks`, which the generic per-group loop calls once per resident group. With 20 resident groups this repeated the same coordinator-wide work 20 times per request per step.

At 2,048 concurrent agentic requests this used most of a scheduler core and delayed workers before their DP collective.

## Changes

- **Scan cursor:** the write-back scan starts at `max(ready_prefix_pages, importing_pages)`. Every page below `ready_prefix_pages` is already durable, so nothing it skipped is lost.
- **Once per step:** the per-step residency work (`plan_prefix_materialization` + `update_residency`) moves to `HiSparseConnectorScheduler.build_connector_meta` through `HiSparseCoordinator.advance_scheduled`, which runs once per scheduled request. The `cache_blocks` override in `single_type_kv_cache_manager.py` is removed, so this PR only shrinks core.
- **Adoption publishes a block-table update:** adopting GPU copies on a host-prefix hit (#59282) now happens after the step's block IDs are captured, so `_adopt_copies` adds the request to `block_table_updates`. Without this the worker keeps reading the page from host while the coordinator pins its copy.
- **Reprefillable tokens stay out of write-backs:** like `KVCacheCoordinator.cache_blocks`, `advance_scheduled` excludes the last `num_reprefillable_tokens` (re-prefilled by multi-module MTP), so a page is not written back and marked durable before its rows are final. The auxiliary managers no longer force `enable_caching`, whose only purpose was the removed hook.

Behavior differences, both on the pressure path only:

- A request that just received its hot buffer releases its durable pages, and the low-pool watermark check runs, one step later than before. Pages written back at completion are still released in `update_connector_output`, before scheduling.
- Adoption runs after the whole scheduling pass, so a later request's allocation in the same pass can evict a copy first. The eviction watcher keeps this safe; the page is read from host instead.

## Performance

B300, one EP8 prefill node and one EP8 decode node, 2,048-concurrent Scale-SWE agentic rollouts, GLM-5.3 NVFP4, HiSparse 300 GiB/decode GPU (measured by @S1ro1 on a `7f47d2b`-based build; instrumented live-system measurements, not a fixed-batch benchmark). "Full fix" here deduplicated per-group work with a first-manager check; this revision gets the same deduplication by running it once from the connector.

| Phase | Output tokens/s/decode GPU | Mean ITL | Planner + residency CPU/step |
|---|---:|---:|---:|
| Original | 1,527 | 158.7 ms | 110.64 ms |
| Cursor only | 2,429 | 93.9 ms | 33.68 ms |
| Full fix | 2,711 | 79.1 ms | 2.68 ms |
| Original restored | 1,300 | 187.2 ms | 133.77 ms |
| Full fix restored | 2,782 | 81.7 ms | 2.85 ms |

CPU microbenchmark, 20 resident groups, 512 durable pages: 512.01 → 24.83 → 6.63 µs per request cache update (original / cursor / full fix).

This revision, same setup (20 resident groups, 512 durable pages, one request's per-step residency work, CPU platform): **327.9 µs on main → 1.3 µs** (main runs `cache_blocks` once per resident group; this PR runs `advance_scheduled` once).
