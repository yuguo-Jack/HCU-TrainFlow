# [Bugfix][Core] Clear stale block-table row tails on shrinking add_row/move_row

[Upstream PR](https://github.com/vllm-project/vllm/pull/65437) · state: open · merged: False

## Original PR description

## Overview

Follow-up to #49757: two more block-table row-update paths can leave previously-valid block ids beyond a row's live region. This PR clears the target-row tail on a shrinking `move_row` and the rebuilt-row tail on a shrinking `add_row`, in `vllm/v1/worker/block_table.py` (`MultiGroupBlockTable` inherits the fix via delegation). Related upstream report on the Ascend fork: vllm-project/vllm-ascend#20827.

## Claims

- `move_row` onto a shorter target row no longer leaves the target row's stale tail; the vacated source row remains cleared as in #49757.
- `add_row` rebuilding a row shorter than its previous content (a request landing on a recycled row slot) clears the stale tail.
- `append_row` is growth-only and needs no change once the two shrinking paths are fixed.
- Regression tests added for both paths.

## Validation

Fail-before / pass-after, running the real `BlockTable` on CPU (unpatched module vs the same file with this PR's fixes applied; the patched functions are textually identical between this module and the vllm-ascend one):

```
[BEFORE (unpatched)] add_row shrink : live=[7, 8]  tail cells 2:10 = [2, 3, 4, 5, 6, 7, 8, 9]  -> STALE block ids survive
[BEFORE (unpatched)] move_row       : vacated src row[:2] = [20, 21]  tgt row tail 2: = [12, 0, ...] -> STALE block ids survive
[AFTER  (PR fix)]    add_row shrink : tail cells 2:10 = [0, 0, 0, 0, 0, 0, 0, 0]  -> clean
[AFTER  (PR fix)]    move_row       : vacated src row[:2] = [0, 0]  tgt row tail 2: = [0, ...] -> clean
```

New tests (CUDA-gated, selected by the existing Buildkite step for `tests/v1/worker/test_gpu_block_table.py`):
- `test_v1_block_table_move_row_clears_target_row_tail`
- `test_v1_block_table_add_row_clears_tail_of_shrunk_row`

Production impact of the unfixed paths (hybrid mamba/GDN model, prefix caching on, 2× Ascend 910B, dense KV layout): 12/12 deterministic garbled outputs on prefix-cache-hit requests, bitwise-identical signatures across devices; 410 operator-level parameter dumps trace the corruption to stale block-table cells consumed via slot-mapping/state-index reads. Full analysis in vllm-project/vllm-ascend#20827.

## Details

Root cause: rows are read by request metadata — kv_len-derived columns, slot-mapping positions over the flat GPU buffer, mamba/GDN state indices — not by `num_blocks_per_row`. Cells beyond a row's live region therefore still get dereferenced, and the stale values are previously-valid block ids: they pass every value/structure check while pointing at blocks that may already have been freed and reallocated, across KV cache groups in hybrid models that recycle ids through one free stack.

MRV2: `append_block_ids(overwrite=True)` can likewise leave stale tails in the persistent staging rows, but MRV2 consumers gather live cells under `offset < num_blocks` masks and dummy runs route through `get_dummy_block_tables` (zeroed rows), so the dereference path fixed here does not exist on MRV2. This change targets the legacy (MRV1) path, which remains in use and is where the production failures above were traced.

Tradeoffs: none material — host-side numpy clears proportional to the shrink delta (a few int32 cells per rebuild/move); no device work, no synchronization added (`VLLM_GPU_SYNC_CHECK` unaffected).
