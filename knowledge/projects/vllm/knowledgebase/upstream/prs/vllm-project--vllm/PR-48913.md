#  [Perf] Avoid full-vocab sort in the small-batch top-k/top-p sampler path

[Upstream PR](https://github.com/vllm-project/vllm/pull/48913) · state: open · merged: False

## Original PR description




## Background

`apply_top_k_top_p_pytorch` is the sampler filter used on the small-batch (`batch_size < 8`) GPU path and on CPU. Whenever top-p is requested it sorts the **entire** vocabulary (`logits.sort` over `[B, V]`, e.g. `V=151936` for Qwen3), which dominates the op's cost. 

## Change

Resolve top-k/top-p from a fixed **top-N candidate window** (`N = 1024`, grown to `k.max()` when a larger top-k is requested) via `torch.topk` instead of a full sort:

- **top-p only**: nucleus found on the top-N candidates; softmax denominator  uses a full-vocab `logsumexp`, so probabilities stay exact.
- **top-k + top-p**: the top-k set fits in the window (`N >= k`), so the candidate softmax is exact.
- **top-k only**: threshold is the k-th largest logit.

The exact sort-based implementation is kept verbatim as `_apply_top_k_top_p_sort` and used as a fallback when the window can't resolve exactly: a tie sits at the window boundary, the top-p nucleus spills past N, or `p >= 1.0`. CPU (`allow_cpu_sync`) behavior is unchanged.

## Testing

- `pytest tests/v1/sample/test_topk_topp_sampler.py` → **95 passed, 36 skipped,  0 failed** (skips are FlashInfer-only, unavailable on the ROCm host). This suite exercises `apply_top_k_top_p_pytorch` directly and as the reference for the Triton kernel tests.
- Correctness vs the sort reference: kept-set matches token-for-token across a large synthetic grid (p/k/vocab/dist/seed/batch) and on real captured  Qwen3-14B logits; residual differences are only exact fp-boundary ties.
- Model eval (real Qwen3-14B, real ShareGPT, small-batch path): generated text is identical to the sort path (no quality change); end-to-end throughput **+6.1%** tok/s.

Independent confirmation of this problem from the CPU side, measured on a 2-socket Xeon Gold 6530 (Emerald Rapids).

On the PyTorch fallback path (no triton-cpu), the full-vocabulary sort in `apply_top_k_top_p_pytorch` was one sort per decode step and about a third of decode self-time. With the same window approach as this PR (topk on a window, nucleus resolved with a full-vocab logsumexp, exact fallback on ties) we measured **+34% at 16 users and +92% at 96 users** on Qwen3-4B with Qwen's default sampling, greedy control unchanged, outputs token-identical to the sort; `tests/v1/sample` pass on current main.

On today's default x86 install the Triton CPU kernels (#43633, pinned since #58140) bypass this function, and we re-measured the change as neutral there. It still applies wherever `HAS_TRITON` is false (generic triton without a CPU backend, source builds, non-x86), which is this PR's path.

Happy to attach the full tables, harness and tests if useful.

- thediymaker · comment · 2026-10-24T00:03:27Z · [source](https://github.com/vllm-project/vllm/pull/48913#issuecomment-6377226526)

Data from a non-Triton accelerator, plus two points from reading the diff.

Without Triton, `apply_top_k_top_p` falls to `apply_top_k_top_p_pytorch` at every batch size, not just small batches. On a model with a 202K vocab whose generation config sets `top_k`/`top_p` (so every request that does not override them pays for it), the full sort took about half of each decode step at batch 128. Aggregate throughput then stopped scaling with `max-num-seqs`.

1. On current main, `apply_top_k_top_p_pytorch` takes `allow_cpu_sync` and only syncs on CPU. The window path adds `int(k.max())` and up to three `bool(... .any())` checks per step on accelerators, which works against async scheduling and graph-captured backends.
2. Rows without top-k carry `k == vocab_size` (`gpu_input_batch.py`), so one such row in a mixed batch makes `n = V`, and the `topk` covers the whole vocab. Taking `n` from rows with `k < V` only, and treating `k == V` rows as top-p-only within the window, would keep the speedup there.

What we run on that backend avoids both: the batch's max top-k comes from the input batch's CPU copy, `K` is bucketed (64 to 1024) to keep the set of shapes small, and the token is drawn inside the `K` window, so no full-vocab softmax is needed. Seeded and mixed batches keep the stock path.
