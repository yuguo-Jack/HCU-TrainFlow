# [CI][Build] Publish macOS wheels to PyPI.

[Upstream PR](https://github.com/vllm-project/vllm/pull/63596) · state: closed · merged: False

## Original PR description

## Overview

Resolves #63595

Enable macOS Apple Silicon CPU release wheels to meet PyPI's version and dependency metadata requirements. List macOS wheels in both the root and `/cpu/` indices on `wheels.vllm.ai`, and document their installation.

This follows PyTorch's index layout, which lists macOS wheels in both its [root wheel index](https://download.pytorch.org/whl/torch/) and its [CPU wheel index](https://download.pytorch.org/whl/cpu/torch/). Also they publish macOS wheels in PyPI.

## Claims

- Remove the CPU local-version suffix from macOS wheels and omit their Triton direct-URL dependencies, which PyPI rejects even when platform markers exclude them.
- Include macOS wheels in the root and `/cpu/` indices.
- Preserve existing non-macOS wheel versions, dependencies, storage paths and index entries. Build pipelines and image publishing scripts are unchanged.

## Validation

I built a macOS wheel locally, uploaded it to PyPI, and verified that it installs successfully with plain `uv pip install` using PyPI alone, without `--torch-backend` or `--extra-index-url`.

Local review compared base `c7476c7a6f` with head `43749080db`:

- A temporary comparison harness produced identical index HTML and metadata, excluding timestamps, across 13 scenarios covering releases, release candidates, nightlies, partial builds, legacy macOS wheels, ROCm dependencies and the XPU Triton shim. Three additional scenarios confirmed that the new macOS filenames change only macOS entries, placing them in the root and `/cpu/` indices.
- The same harness exercised the version and requirement functions across 90 simulated Linux configurations; results matched the base for CPU, CUDA, ROCm, XPU, TPU and empty-device builds. These were function-level checks, not hardware builds.
- The real setuptools `prepare_metadata_for_build_wheel` backend succeeded on macOS in a temporary source checkout with `SETUPTOOLS_SCM_PRETEND_VERSION=0.33.0`. The generated metadata had version `0.33.0`, `Requires-Python: >=3.11,<3.15`, and no direct-URL dependencies.
- `ruff check --no-fix`, `ruff format --check`, `shellcheck`, `bash -n` and `markdownlint-cli2` passed on the relevant changed files; `git diff --check main...HEAD` also passed.

The Buildkite publishing path and an inference smoke test of the installed wheel have not yet been validated. The existing macOS smoke workflow installs editable source rather than a built wheel. No model evaluations were run; this change does not modify inference code.

## Details

`alias_to_default` previously copied the entire default index into a variant index. Once the default index includes macOS wheels, that would also list them under `/cu130/`. Rename the parameter to `fallback_variant` to reflect its narrower role: it selects an additional index only for wheels whose variant could not be inferred.

The generator first extracts the variant from the wheel's version suffix. Wheels without a recognized suffix get `is_default=True`. For those wheels, a `macosx_` platform tag additionally sets `variant="cpu"`, while retaining `is_default=True`. Existing ROCm variant inheritance clears `is_default` on inherited entries, keeping ROCm dependencies out of the default and fallback indices.

Grouping then applies three rules:

1. Wheels with an inferred variant enter `variant_to_files[variant]`.
2. Wheels with `is_default=True` also enter `variant_to_files["default"]`.
3. Wheels whose variant is still unknown enter `variant_to_files[fallback_variant]`, when configured. The upload script sets this to `cu130`.

This preserves the default CUDA index and keeps macOS wheels in both the root and CPU indices. `is_default` is internal bookkeeping and is not emitted in `metadata.json`. Wheel storage locations and upload destinations are unchanged.

Build scripts can be improved and simplified but I tried to keep diff minimal so it could be easier to review.
Documentation was mostly copied from x86 and arm and adapted.
