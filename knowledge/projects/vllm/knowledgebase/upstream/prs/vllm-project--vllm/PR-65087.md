# [ROCm][Perf][MiniMax-M3.1] Four-wave decode top-k for the NVFP4 indexer

[Upstream PR](https://github.com/vllm-project/vllm/pull/65087) · state: closed · merged: True

## Original PR description



## Overview

On gfx950, the MiniMax-M3.1 NVFP4 indexer picks the 16 best blocks of every decode row with one wave per row. This PR gives each decode row four waves and merges their top-16 lists exactly, so the ordered block ids are unchanged. No other kernel, flag or call site changes.

## Claims

- Decode top-k is 4.1x faster over the decode shapes of a served MiniMax-M3.1 AgentX run (18.9 -> 4.65 us per call, weighted by how often each shape occurs, real index scores); 4.07x in the live server (21.2 -> 5.2 us per call). With random scores the same shapes give 1.26x: the old kernel is much slower on real scores (see Details).
- End to end (TP4, 2 runs per arm): c16 +1.34% and c32 +2.47% tok/s/GPU, TPOT p50 -12.2% / -12.0%, p90 -8.3% / -8.2% (interactivity p50 +13.9% / +13.6%, p90 +9.0% / +8.9%).
- Same output as before: bit-for-bit equal to AITER's `pa_sparse_block_topk` and to the old kernel in 4,500 sweep cases (772,650 rows); eager and CUDA-graph replay agree. In a replay of the real served calls 1 of 2,816 decode rows differs, in a call with duplicate page ids where the old kernel's own output changes from run to run. GSM8K and spec-decode accept length are unchanged.
- **Costs:** With random scores a call is up to 12% slower when every row is under about 213k tokens; with real scores that only shows for calls in which no row triggers the old kernel's slow path. See Limits.

```python
# bench_topk.py (random scores)
import sys, json, math, statistics, torch
from vllm.models.minimax_m3.amd.ops.index_topk_decode.host import minimax_m3_index_topk_decode_indices as topk
K, QL = 16, 4
width = lambda msl: (1 << (math.ceil(math.ceil(msl / 128) / 64) - 1).bit_length()) * 64
flush = torch.empty(1 << 30, dtype=torch.uint8, device="cuda"); res = {}
for msl in [65536, 131072, 262144, 524288, 1 << 20]:
    for nr in [1, 2, 3, 4, 6, 8, 12, 16, 32, 64, 100]:
        gen = torch.Generator().manual_seed(nr * 1000003 + msl)
        seq = torch.randint(msl // 2, msl + 1, (nr,), generator=gen).int().cuda()
        scores = []
        for _ in range(K):
            s = torch.randn(1, nr * QL, width(msl), generator=gen)
            s = torch.where(torch.rand(s.shape, generator=gen) < 4.0 / s.shape[-1], s + 6, s)
            s[:, :, 0] = 1e30; scores.append(s.cuda())
        outs = [torch.empty(1, nr * QL, 16, dtype=torch.int32, device="cuda") for _ in range(K)]
        def fn():
            for i in range(K): topk(scores[i], outs[i], seq, max_seq_len=msl, query_len=QL)
        fn(); torch.accelerator.synchronize()
        g = torch.cuda.CUDAGraph()
        with torch.cuda.graph(g): fn()
        ts = []
        for _ in range(20):
            flush.zero_(); a, b = torch.cuda.Event(enable_timing=True), torch.cuda.Event(enable_timing=True)
            a.record(); g.replay(); b.record(); torch.accelerator.synchronize(); ts.append(a.elapsed_time(b) * 1000 / K)
        res[f"{nr}x{msl}"] = statistics.median(ts)
json.dump(res, open(sys.argv[1], "w"))
```

## Details

Each decode row is one workgroup that walks the row's block scores in windows, keeps a running top 16 and ranks the candidates. The old kernel did this with a single wave over windows of 1,664 blocks (213k tokens); rows longer than that serialize on the one wave. Now the workgroup has four waves, each walking every fourth window of 1,024 blocks with its own candidates and running top 16, and the lists are merged by an exact rank over (score, block id), which reproduces AITER's order including ties, NaN and infinities. A wave with no live window pads its list with dead entries, and a row of at most one window skips the merge. The lane-bound threshold uses 16 bits instead of 12 and falls back to all 32 bits when too many keys pass. Prefill compiles to the same code as before. The kernel name for decode changes from `..._w26` to `..._w16`.

Why real scores matter: the old kernel keeps the keys above a bound and ranks at most 64 of them per window; when more pass, it rebuilds the candidates, and with many near-ties it runs an exact bit search on one wave. Random scores never reach that. Real index scores sit in a narrow range, so the 12-bit bound lets more than 64 keys through in about a third of the rows (emulated on the captured rows: 33% of rows with the old bound and window size, 6% with the 16-bit bound), and a call takes as long as its slowest row. Calls in which no row overflows run at the random-score time. I did not build a 16-bit-bound-only or four-wave-only variant, so I cannot say how much of the 4x comes from each.

Limits:
- Slower in some calls: when every row is under about 213k tokens and no row overflows the old kernel's candidate buffer, a call is up to 12% slower (about 0.5 us on a 4 us call; random-score table, and the 0.88x-0.92x served calls there) and 8-9% slower at 100 requests under 131k tokens. In my real-score runs no cell (20 served calls, 32 grid cells, 6 cells of 131k-213k rows) is slower than stock (lowest 1.04x), but about 30% of single-request calls with 131k-213k rows have no overflowing row (emulation). The launch only sees the graph's `max_seq_len` (1M in serving), not the row lengths, so the host cannot choose between the two kernels.
- The real-score grid cells are re-scored captured requests, not replays of served calls; the max length 1M column is random-score only.
- E2E was run on the published ROCm image with the two files overlaid, not on a build of current main: the CI recipe (DBO with this multimodal model) does not start on main under Model Runner V2, and I did not change the recipe. The kernel files are identical to main's; other kernels' shares differ on main (for example the MXFP8 fusions), so the gain on main may differ.
- c16 and c32 only (c1-c8 do not use this indexer path; c64 not run); one model, TP4, DSpark, DBO on; 2 runs per arm.
- Validation is gfx950 only, and no Buildkite step runs the test file on gfx950 (I ran it on MI355X). The microbench is not in `benchmarks/kernels/`.
- A 2-way merge for rows up to 2,048 blocks would halve the 131k-213k regression (+8 lines); it is not in this PR.

Not a duplicate: no open PR changes the top-k files or their test file (checked against main at 76c6f3f2a9). #64198 (MXFP4 K/V and index cache) does not touch them. #64264 (NVFP4 kernel warmup at startup) and #64273 (monokernel decode on M3.1) are closed drafts that only carried the same bytes of these files as main. #64448 (decode CP for DSpark 7) is open and edits the indexer module and the CP push kernel, not the top-k kernel, so it is complementary.
