# [Benchmark] Add steady-state PP support to bench forward

[Upstream PR](https://github.com/vllm-project/vllm/pull/63616) · state: closed · merged: True

## Original PR description



## Overview

Add pipeline parallelism to `vllm bench forward`, measuring a microbatch's full-pipeline forward latency under steady-state load from identical microbatches. Builds on the merged PCP support in #63613.

## Claims

- Includes PP transfers and waits between the first stage's forward start and the last stage's forward completion; excludes pipeline fill/drain, input preparation before the forward, and sampling.
- Captures each stage's forward in a CUDA graph and streams matching microbatches without a per-step host barrier. Reports stage timelines and estimated cross-rank clock uncertainty.
- Adds rendered CLI documentation and a two-GPU CLI/profiler regression test wired into the existing distributed CI job.

## Validation

Full 93-layer Kimi K3 with dummy MXFP4 weights on **4 nodes × 4 GB200 GPUs**. Balanced routing, 8,192 query tokens per microbatch, EP enabled. PP2 uses TP8/EP8; PP4 uses TP4/EP4. Kimi currently disables SP with PP.

Median full-pipeline GPU latency (ms):

| PP | Prefill | TRT-LLM bench | TRT-LLM serving | MegaMoE bench | MegaMoE serving |
|---|---|---:|---:|---:|---:|
| 2 | 8 × 1K | 338.3 | 339.3 | 525.4 | 525.8 |
| 2 | 1 × 8K | 357.1 | 357.9 | 517.6 | 518.1 |
| 4 | 8 × 1K | 490.7 | 491.6 | 645.7 | 646.9 |
| 4 | 1 × 8K | 507.3 | 505.5 | 637.8 | 637.2 |

Serving measurements match request IDs across stages and use the same first/last GPU-event boundaries; these are not TTFT or Prometheus prefill histogram values. Serving uses piecewise graphs. All differences are within 0.35%. Benchmark-only KV restoration is outside stage compute timing but can affect pipeline cadence.

Each benchmark case has 100 measured microbatches (5 × 20), trimming 4 × PP microbatches at each end. Final-run sample-median spread was below 1%; estimated cross-rank clock uncertainty was about 0.18–0.21 ms. All intermediate and final benchmark outputs were finite and matched the eager pipeline reference exactly. These dummy-weight checks validate execution and timing, not model quality. Both MoE backends use MXFP8 × MXFP4. MegaMoE's additional cost here includes replicated token dispatch with SP disabled; this PR does not change the model or MoE implementation.

## Details

The implementation is isolated to the benchmark. A benchmark-specific external-launcher executor enables stage loading; the benchmark drives the runners directly, without serving schedulers or sampling broadcasts. It reuses runner input preparation, forward context, KV-state handling, and PP/TP transfer conventions.

Cross-device CUDA events cannot be subtracted directly. Pre/post calibration correlates each GPU's timeline to rank zero's monotonic clock using CPU ping-pong and host/GPU event bracketing. The benchmark reports the earliest first-stage TP start to latest last-stage TP completion for each microbatch, with the calibration uncertainty retained in JSON. This adds code compared with timing isolated stages, but is needed to measure pipeline traversal while other stages remain occupied.

The full-model validation covers prefill with PP+TP+EP. Decode and combinations with PCP/DCP are not covered by these full-model runs. No serving/model code or non-PP benchmark behavior is changed.

Duplicate check: searched open PRs for `"bench forward"`, pipeline benchmarking, PCP/PP benchmarking, and references to #63613. No open PR implements this feature. #62300 fixes profiling in the existing forward path and is separate from PP support.
