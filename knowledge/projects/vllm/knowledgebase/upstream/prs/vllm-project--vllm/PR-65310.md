# [ROCm][MiniMax-M3] LM-path speedups: fused norm + FP8 quant, dense short MSA prefill, JIT warm-ups

[Upstream PR](https://github.com/vllm-project/vllm/pull/65310) · state: open · merged: False

## Original PR description

## Purpose

MiniMax-M3 on ROCm: three LM-path changes found while profiling the image workload on MI355X (TP4). One commit per change; all opt-in.

| # | Change (commit) | Why | Measured (MI355X, MiniMax-M3 VL, TP4) | Opt-in | Test |
|---|---|---|---|---|---|
| 1 | Fuse qkv_proj's per-token FP8 input quant into the input RMSNorm (FP8-attention checkpoints) | norm and quant ran as separate kernels | unit: 137 vs 150 + 57 µs at M=17,424; profile: norm + quant 14.2 → 11.1 ms per ~12.6k-token step (−1.5%), decode-64 steps −2.2% | `VLLM_MINIMAX_M3_FUSE_NORM_FP8` | pytest in `tests/kernels/test_minimax_m3_amd_ops.py` (39 passed on MI355X): residual and scales bitwise equal, ≤14 of 52M FP8 values differ |
| 2 | Opt-in dense causal attention for short MSA prefill steps | when every prefill request is within the sparse window, the sparse path keeps every block anyway but costs more | MSA attention 228 → 143 µs per layer (−2.4% of a ~12.6k-token step); dense vs sparse on real data ≤0.215% mean deviation over 32 checks | `VLLM_MINIMAX_M3_MSA_DENSE_PREFILL=N` (+ `_CHECK` for validation), default off | in-server dense-vs-sparse check (`_CHECK`) |
| 3 | Warm up Triton GEMM variants (ROCm unquantized GEMM, bf16x3 router) that compile inside the first requests | 0.5–2.6 s of JIT inside user requests | router `_reduce_terms_kernel` no longer compiles while serving (864 warm-up calls, 2.65 s at startup) | `VLLM_ROCM_GEMM_JIT_WARMUP` | server logs |
| 4 | Warm up MiniMax-M3's sparse PA decode variants (`ONE_SHOT` × alignment) before serving | variants compiled while serving in every pass, costing a measured row up to ~14% | no sparse-PA compile while serving in 8/8 full passes (before: in every pass); MMMU 0.636–0.678 | part of the MiniMax ROCm path (4 calls, ~0.9 s per rank) | server logs |

Full stack with these: up to 120.2% of a B200 reference on the 8-row image sweep (TP4).
Notes: (3) could hang off main's `kernel_config.enable_jit_warmup` registry instead of an env var. #52963 / #64172 (sparse prefill), #62509 / #61119 (decoder-layer norm) are related; whichever lands later rebases. Consolidates #65309 and #65308.

## Verified on this PR's head (2026-11-03): known issue, fix in progress

Dedicated MI355X node, TP4, MiniMax-M3 VL (AttnFP8), vLLM nightly 40941f2c + this branch, full 8-row image sweep, A B B A, fresh server per pass. A = flags off; B = `VLLM_MINIMAX_M3_FUSE_NORM_FP8=1 VLLM_MINIMAX_M3_MSA_DENSE_PREFILL=2560 VLLM_ROCM_GEMM_JIT_WARMUP=1`.

- **Cold-start regression, reproduced:** with B, startup pre-builds only the AITER `pa_ps` paged-attention variants for 4-8 context partitions, not 2 and 3. The first 768x1024 c16 batch then JIT-builds them while serving (13 s stall, max ITL 13.3 s, that row −42% in one pass). 8-row geomean **−7.3%** (A/A 0.5%).
- **Without that row:** 7-row geomean −0.8%, i.e. flat. B lowers median TTFT on the c64 row (−23%) but raises TPOT on the image rows (+15%).
- The per-flag split points at `VLLM_MINIMAX_M3_MSA_DENSE_PREFILL` as the flag that removes partition counts 2/3 from the warm-up. The fix is to warm every split count the decode path can reach; a steady-state A/B (warm server) and the per-flag numbers will follow. Draft until then.
