# Fix unbounded series accumulation in vllm:lora_requests_info

[Upstream PR](https://github.com/vllm-project/vllm/pull/63493) · state: open · merged: False

## Original PR description

## vllm:lora_requests_info leaks a series per observed adapter-set state

I run 8×TP2 pods serving 200 LoRA adapters and noticed the llm-d router
(the downstream metrics consumer) intermittently dropping healthy pods from
its scheduling pool during benchmarks. Chasing that led here.

The gauge encodes the current running/waiting adapter sets in its *labels*:

```python
self.gauge_lora_info.labels(**lora_info_labels).set_to_current_time()
```

prometheus_client keeps every distinct label combination exposed forever,
and nothing ever removes the previous child. So every time a request starts
or finishes and the in-flight set changes, that exact (running, waiting)
pair becomes a permanent series in /metrics. With 200 adapters the churn is
combinatorial. From the Prometheus data I collected during a 5 minute
benchmark on v0.31.0:

```
t=   0s:    1 series
t=  60s:  291 series
t= 140s: 1352 series
after 5 min: 4451 series   # for this one gauge
```

The exposition grows until scrapes slow down enough that the router (1s
refresh, 2s staleness threshold) starts considering pods stale and filters
them out of the candidate set. While all 8 pods were healthy and Ready:

```
candidate sizes: {1: 26, 2: 20, 4: 15, 5: 6, 8: 24}   # 91 requests
```

74% of requests were scheduled against a shrunken pool, which is what
broke the adapter-affinity routing (session bindings kept migrating as
their bound pod flapped in and out).

## The fix

Remember the last label values per engine and `remove()` the previous
child when the set changes, so the exposition holds only the current
state. Per-engine so DP engines don't delete each other's children.
Ray gauges have no child series to remove, so `RayGaugeWrapper` gained a
no-op `remove()` to keep the gauge API the same; Ray deployments behave as
before.

One series per engine is the correct steady state — this is a
current-state gauge, not a history log. Prometheus already keeps history:
each state change is its own time series there, and consumers are expected
to pick the latest (the llm-d router sorts by the gauge value, which is the
state's refresh timestamp).

| | before | after |
|---|---|---|
| series in exposition | unbounded (4451 measured) | 1 per engine |
| scrape size | grows forever | constant |
| stale series in Prometheus | flatlined forever | marked stale in 5 min |
| healthy pods dropped by staleness-sensitive routers | yes (measured) | no |

## Workaround

Until this lands, I run the router (llm-d EPP) with
`--metrics-staleness-threshold=30s` so transiently slow scrapes don't evict
healthy pods from the scheduling candidate pool. That masks the routing
symptom but doesn't stop the exposition from growing.

## Testing

New unit tests in `tests/v1/metrics/test_lora_requests_info.py` covering
accumulation, current-state exposure, per-engine isolation, shared label
sets between engines, and the no-lora-config case.

`test_lora_requests_info_does_not_accumulate_series` fails on unpatched
v0.31.0 and passes with the fix; all 5 pass in a v0.31.0-based container.

```release-note
Fix unbounded prometheus series accumulation in `vllm:lora_requests_info`
when serving LoRA adapters: the previous label set is now removed when the
running/waiting adapter sets change, keeping the `/metrics` exposition at
one series per engine.
```

nice one, took care of it.

To answer the question: removing a label set that is no longer present is a no-op in prometheus_client (`dict.pop` with a default), so a stale removal cannot raise. The shared-label case between engines was real though — an update by one engine could drop the series another engine still held. Fixed in ddae03b: the removal is skipped when another engine's most recent label values equal the set being removed, so the series is dropped only once the last engine holding it moves on. New test covers it (fails without the guard).
