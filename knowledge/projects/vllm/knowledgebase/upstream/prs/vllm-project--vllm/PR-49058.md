# fix: LoRA Triton kernel OOB crash with NVFP4/EP padded buffers

[Upstream PR](https://github.com/vllm-project/vllm/pull/49058) · state: open · merged: False

## Original PR description

## Summary

Fixes the LoRA + NVFP4 (modelopt_fp4) CUDA crash reported in #48862.

When serving NVFP4-quantized MoE models (e.g. `nvidia/GLM-5.2-NVFP4`) with `--enable-lora` and `--enable-expert-parallel`, vLLM pre-allocates LoRA buffers to `max_num_batched_tokens` (8192). The Triton fused MoE LoRA kernels use the buffer size as a grid dimension, but the token mapping arrays only have entries for actual token counts. Padded positions contain sentinel values that compute out-of-bounds addresses, causing `cudaErrorIllegalAddress`.

### Fix 1: clamp the OOB a-row index in every kernel that computes it

Padded positions in `sorted_token_ids` carry sentinels (`>= num_valid_tokens`). The sentinel fills the whole row with `num_valid_tokens` (see `csrc/moe/moe_align_sum_kernels.cu`), so `offs_token // token_mapping_factor` evaluates to exactly `num_tokens` — one full row past the end of the allocation. The load mask already zeroes these results, so clamping the address is safe.

Three sites in the shrink/expand path compute this index. All three are now clamped:

| File | Kernel | Reached when |
|---|---|---|
| `fused_moe_lora_op.py` | `_fused_moe_lora_one_shot_kernel` | `> 64` tokens, rank `<= 128` |
| `fused_moe_lora_op.py` | `_fused_moe_lora_kernel` (legacy) | `<= 64` tokens, rank `> 128`, or `fully_sharded` |
| `fused_moe_lora_fp8_op.py` | fp8 twin | same conditions, fp8 path |

The legacy and fp8 sites matter for the reported config: small-batch decode falls under the 64-token threshold, so the earlier one-shot-only clamp left the crash reachable during single-request decode.

```python
safe_a_rows = tl.where(token_mask, offs_token // token_mapping_factor, 0)
a_ptrs = cur_a_ptr + (safe_a_rows[:, None] * stride_am + offs_k[None, :] * stride_ak)
```

`token_mask` is already in scope at each site, and every one of these loads is masked.

### Fix 2: initialise the padded LoRA mapping buffers to the no-LoRA sentinel (`lora_kernel_metadata.py`)

`token_lora_mapping` and `token_indices_sorted_by_lora_ids` are allocated with `torch.empty`, so padded entries beyond the real token count hold **uninitialised garbage**, not zero. `_reset()` now fills both with `-1`, which is already the documented no-LoRA sentinel (`if lora_id < 0: return` in the kernels).

This is hardening rather than a demonstrated root cause: every reader of the metadata I traced (`lora_shrink_op`, `lora_expand_op`, `naive_dp_ep.py:205`) indexes these bounded by `lora_token_start_loc` / `num_tokens_per_lora`, never by value, so the filled tail is normally not consulted. It removes a class of nondeterminism rather than fixing a specific observed fault.

### Fix 3: allow SP + LoRA + EP (`fused_moe.py`)

`_ep_check` asserts `not is_sequence_parallel` for every MoE layer whenever `--enable-lora` is on, which blocks LoRA adapters that target only attention layers (`q_b_proj`, `kv_b_proj`, `o_proj`) from being used with `--enable-expert-parallel`.

**Scope caveat, stated plainly:** this removes the assertion globally, so it also permits SP+EP for adapters that *do* target MoE layers. That combination was not tested here — the adapters in the test plan below are attention-only. A narrower fix would move the SP check into `create_lora_weights`, where the adapter's target modules are known. If reviewers prefer that shape, I am happy to restructure.

## Why this is not a duplicate

- **PR #34421** adds LoRA + NVFP4 support via the MarlinExperts backend — a different approach (backend swap) vs. this PR (fixes the existing Triton kernel).
- **PR #48887** implements a zero-weight LoRA slice skip for performance. It does not address the padded buffer OOB crash or the SP assertion. Once this crash is fixed, #48887 can skip zero-weight layers safely.
- **PR #48861** fixes the NVFP4 `out_dtype` mismatch (float32 vs model dtype). Necessary for correct output, but it does not address the CUDA crash.

## Test Plan

Tested on **8×B200** with `GLM-5.2 NVFP4` + LoRA adapter (r=96, attention-only: `q_b_proj`, `kv_b_proj`, `o_proj`) with:

```bash
vllm serve /workspace/models/GLM-5.2-NVFP4 \
  --tensor-parallel-size 8 --enable-expert-parallel \
  --enable-lora --lora-modules aesop=/workspace/adapters/combined \
  --max-lora-rank 128 --max-loras 1 \
  --kv-cache-dtype fp8_e4m3 --gpu-memory-utilization 0.92
```

**Results:**
- Without any fix: `cudaErrorIllegalAddress` after first request with LoRA
- With fix 1 (one-shot only, first revision): crash moves to a different kernel
- With fixes 1+2: crash moves to the SP assertion
- With all 3 fixes: no crash, correct output, sustained serving
- Removing any one fix reintroduces the crash

Base model (no LoRA) works correctly without any fixes.

- fattchris · comment · 2026-11-02T23:52:40Z · [source](https://github.com/vllm-project/vllm/pull/49058#issuecomment-6591516569)

Second commit pushed, plus corrections to the description. I re-audited this against current `main` instead of trusting the original write-up, and found a real gap.

**The fix was incomplete.** Clamping only `_fused_moe_lora_one_shot_kernel` left two sites computing the same out-of-bounds index:

- `_fused_moe_lora_kernel` (`fused_moe_lora_op.py`) — the legacy two-kernel path
- `fused_moe_lora_fp8_op.py` — the fp8 twin

Both build `a_ptrs` from `offs_token // token_mapping_factor` with no clamp, under the same `token_mask`-only protection. Reachability matters here:

```python
if (
    not fully_sharded
    and max_lora_rank <= _FUSED_MOE_LORA_ONE_SHOT_MAX_RANK      # 128
    and topk_weights.shape[0] > FUSED_MOE_LORA_TWO_KERNEL_MAX_TOKENS   # 64
):
```

The one-shot kernel only runs above **64 tokens**. Single-request decode, rank > 128, and `fully_sharded` all take the legacy path — so the crash stayed live in exactly the low-concurrency case a user hits first. `3c75210` applies the same `tl.where` clamp at both sites.

I verified the mechanism against `csrc/moe/moe_align_sum_kernels.cu`: the sentinel fills the entire row with `numel`, so the computed row is `num_tokens` exactly — one full row past the allocation, and a full `num_valid_tokens` rows past when `mul_routed_weight=True` (factor 1). Clamping to 0 is safe because the load is masked.

**Two description claims were wrong and are now corrected:**

1. Fix 1 claimed the clamp was "applied in both `_fused_moe_lora_one_shot_kernel` and `_fused_moe_lora_small_batch_kernel`". The `small_batch` hunk is pure inlining — `x_row = pair_idx // token_mapping_factor` collapsed into a single expression — with zero behavioral change. And `small_batch` never needed a clamp anyway: `pair_idx < num_tokens * top_k_num`, so the row is in range. The clamp lived only in the one-shot kernel.
2. Fix 2 claimed the buffers "were initialized to 0 (`torch.zeros`)". They are `torch.empty` — uninitialised garbage, not zero. That also means the stated mechanism ("defaulting to LoRA index 0") was a mis-diagnosis. The `fill_(-1)` change is still worth keeping as hardening, and the description now says so honestly rather than claiming it fixes something specific.

**On Fix 3**, I added a scope caveat to the description: removing the assertion from `_ep_check` is global, so it also permits SP+EP for adapters that target MoE layers — untested here, since the test adapter is attention-only. A narrower fix would move the check into `create_lora_weights` where the target modules are known. Flagging rather than silently shipping the broader behavior; happy to restructure if that is preferred.

Still blocked on the same thing: `pre-run-check` needs a `verified` / `ready` / `ready-run-all-tests` label before pre-commit will run, or 4+ merged PRs from the author. The code side is ready for that gate.
