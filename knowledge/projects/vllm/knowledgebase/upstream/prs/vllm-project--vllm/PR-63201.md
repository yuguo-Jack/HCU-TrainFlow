# [CI][Test] Compare bf16 token embeddings by cosine similarity

[Upstream PR](https://github.com/vllm-project/vllm/pull/63201) · state: closed · merged: True

## Original PR description

## Purpose
`test_embeddings_without_chunking_match_pooling` (added in #61772) requires `/v1/embeddings` and `/pooling` to return bit-identical bf16 token embeddings. That only holds if both requests are batched the same way, which vLLM does not guarantee (only with `VLLM_BATCH_INVARIANT=1`).

On ROCm, the `[text, "Short."]` case fails intermittently: the scheduler sometimes runs "Short." (4 tokens) in its own step, where linear layers use the skinny GEMM (`wvSplitK`, n <= 5), and sometimes batched with the long prompt (21 tokens, hipBLASLt).

The two kernels round a few bf16 values differently, giving two equally valid results (each ~0.01 from an fp32 reference, cosine 0.99997). Verified on MI300X: outputs are bit-identical with `VLLM_ROCM_USE_SKINNY_GEMM=0`.

CI since #61772: AMD (MI355 DPX) 18/593 runs failed on this test. e.g. https://buildkite.com/vllm/ci/builds/96694

Compare with `check_embeddings_close` (cosine similarity), as the rest of this file already does.

## Test Plan
Ran the test 10x on MI300X in the CI image for main@38955340b7, before and after.

## Test Result
Before: fails intermittently on `inputs2`, same as CI. After: all runs pass.
