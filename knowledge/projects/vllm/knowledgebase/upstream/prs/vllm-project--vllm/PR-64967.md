# [Quantization][Attention] Enforce power-of-two head size validation in TurboQuant attention

[Upstream PR](https://github.com/vllm-project/vllm/pull/64967) · state: open · merged: False

## Original PR description



## Overview

Enforces power-of-two head size validation in the TurboQuant attention backend (`TurboQuantAttentionBackend.supports_head_size`), rejecting incompatible head dimensions at engine configuration time rather than crashing during inference store matmuls.

Fixes #64956.

## Claims

- **Rejects incompatible head dimensions at configuration time**: `TurboQuantAttentionBackend.supports_head_size` now validates that `head_size` is a positive power of two, enabling `AttentionBackend.validate_configuration()` to cleanly report `"head_size not supported"`.
- **Defensive guard against invalid Hadamard rotations**: `_build_hadamard_cached` raises a fast `ValueError` if called with a non-power-of-two dimension rather than overshooting to an incompatible dimension ($80 \rightarrow 128 \times 128$) and improperly normalizing by $1/\sqrt{d}$.
- **Zero regression on power-of-two models**: All standard power-of-two head dimensions ($16, 32, 64, 128, 256$) remain fully supported.
- **Automated CPU test coverage**: Added 21 parametrized tests in `tests/quantization/test_turboquant.py` verifying power-of-two acceptance, non-power-of-two rejection, and Hadamard matrix properties.

## Validation

### 1. Reproduction & Fix Verification
Tested against the configuration reported in #64956 (`head_size=80`, e.g. `microsoft/phi-2` with `kv_cache_dtype="turboquant_3bit_nc"`):

* **Before fix**:
  * `TurboQuantAttentionBackend.supports_head_size(80)` returned `True`.
  * `TurboQuantAttentionBackend.validate_configuration(...)` returned `[]` (accepted).
  * `_build_hadamard(80)` produced a $128 \times 128$ matrix divided by $\sqrt{80}$.
  * Execution crashed on first store with `RuntimeError: mat1 and mat2 shapes cannot be multiplied (512x80 and 128x128)`.

* **After fix**:
  * `TurboQuantAttentionBackend.supports_head_size(80)` returns `False`.
  * `validate_configuration(...)` returns `['head_size not supported']`.
  * `_build_hadamard(80)` raises `ValueError: Hadamard rotation requires power-of-two dimension, got 80`.
  * Power-of-two dimensions (e.g. 128) continue to return `supports_head_size(128) == True` and valid configurations return `[]`.

## Details

### Root Cause
1. `_build_hadamard_cached(d)` uses Sylvester construction by doubling $H$ while $H.shape[0] < d$. When $d$ is not a power of two (such as $d=80$), $H$ doubles past $d$ up to $128 \times 128$, and normalizes by $1/\sqrt{80}$ rather than $1/\sqrt{128}$.
2. In `triton_turboquant_store`, `x_hat` ($[N \cdot H, 80]$) is multiplied by `PiT` ($[128, 128]$), crashing with a PyTorch shape mismatch on the first forward pass.
3. `TurboQuantAttentionBackend.supports_head_size()` previously returned `head_size > 0` based on a stale assumption that `head_size` represented `effective_head_size`, preventing `validate_configuration()` from catching the incompatibility during engine bring-up.

Enforcing `head_size > 0 and (head_size & (head_size - 1)) == 0` aligns `TurboQuantAttentionBackend` with the mathematical prerequisites of the Hadamard rotation and Triton power-of-two kernel tiling.
