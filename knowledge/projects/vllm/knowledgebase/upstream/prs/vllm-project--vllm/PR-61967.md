# [ROCm][Perf][DSv4.1] HIP sparse MLA decode kernel for batched decode on gfx942

[Upstream PR](https://github.com/vllm-project/vllm/pull/61967) · state: open · merged: False

## Original PR description

On gfx942 the Triton split-K sparse MLA decode path for DeepSeek-V4 / V4.1 spends most of its time gathering scattered fp8 rows out of the paged cache. At batch the MFMAs mostly wait on those gathers, so the kernel is latency bound rather than compute bound

This adds a gfx942-only HIP kernel that keeps K in registers as the MFMA A operand, pipelines tiles through a small register ring, and brings V through LDS. It is registered as `_rocm_C::sparse_mla_decode_fp8_ds_mla` and covers the per-rank DSv4 / V4.1 decode shape (16 heads x 512 = 448 nope + 64 rope) over fp8_ds_mla caches, including the SWA main cache, optional top-k extra cache, optional attention sink, ragged indices with -1 holes, and a split-K plus reduce

`rocm_sparse_attn_decode` dispatches to it on gfx942 when the op is present, the output is bf16 (no MXFP8 epilogue), the head shape matches, and the step has at least `_HIP_SPARSE_DECODE_MIN_TOKENS` (64) decode tokens. Below that gate the HIP path's fixed cost (split-K plus a separate reduce kernel) is not paid back, and Triton is as fast or faster, so smaller steps stay on the Triton split-K kernel. Like the aiter path it returns 0 so the caller applies the inverse RoPE

NaN elements of gathered rows count as zero, matching what the Triton scrub intends. Device code is compiled only under `__gfx942__`. Other targets build empty kernels and the host op refuses to run off gfx942. CUDA builds never see `csrc/rocm`

Complementary, not overlapping: #60583 turns on AITER sparse MLA on gfx942 for other models and excludes DSv4 / V4.1. #60731 is an opt-in mono decode path for very small steps. This PR is the batched decode path at 64+ tokens on the Triton fallback shapes those leave alone. #61968 retunes the Triton tile on gfx942 for the small steps that stay on that path
