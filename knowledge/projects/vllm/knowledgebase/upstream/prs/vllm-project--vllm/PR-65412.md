# [Bugfix] Granite4Vision: strip padding tiles for list pixel_values

[Upstream PR](https://github.com/vllm-project/vllm/pull/65412) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Fix a `split_with_sizes` crash in Granite 4.1 Vision (`Granite4VisionForConditionalGeneration`) when one encoder batch contains images with different anyres tile counts from more than one request. Padding tiles were stripped only when `pixel_values` arrived as a 5-D tensor, not when it arrived as a list of per-image tensors. Also removes a GPU<->CPU sync in `embed_input_ids` that CI's sync check rejects for every Granite 4.1 Vision image request.

## Claims

- Fixes `RuntimeError: split_with_sizes expects split_sizes to sum exactly to N ... but got split_sizes=[...]`, which kills EngineCore and fails every in-flight request (`EngineDeadError`).
- Per-image embeddings on the fixed list path are bit-identical to encoding each image alone.
- Removes the GPU<->CPU sync from zeroing image positions in `embed_input_ids` (`text_embeds[is_multimodal] = 0.0` with a CPU mask), which fails under `VLLM_GPU_SYNC_CHECK=error`. Output is unchanged.
- Adds a regression test that fails on `main` and passes with the fix, checking batched outputs against running each request alone.

## Validation

New test `tests/models/multimodal/generation/test_granite4_vision.py`, run on an H100:

```bash
VLLM_GPU_SYNC_CHECK=error pytest tests/models/multimodal/generation/test_granite4_vision.py -v
```

| Code | Result |

| padding fix only | `FAILED` — `RuntimeError: GPU<->CPU sync detected - avoid it or wrap with gpu_sync_allowed()` (`granite4_vision.py:824`, `embed_input_ids`); the same failure as the first CI run of this PR |

On a standalone check with `torch.cuda.set_sync_debug_mode("error")` and the same shapes and devices (pinned CPU bool mask, GPU embeddings), `emb[cpu_mask] = 0.0` synchronizes and `emb.masked_fill(mask_on_gpu.unsqueeze(-1), 0.0)` does not; the two results are `torch.equal`.

Also passing with this PR: `tests/models/test_initialization.py -k Granite4Vision`, `tests/models/multimodal/processing/test_common.py -k granite-vision-4.1` (3 cases), `tests/models/test_registry.py -k Granite4Vision`, and pre-commit.

## Details

**Root cause.** The HF processor pads every image in one call to that call's largest tile count. A request with images of 5 and 10 tiles therefore produces two 10-tile tensors, the first with 5 trailing zero tiles. `MultiModalFieldConfig.batched` stacks the items of an encoder batch only when their shapes match. Add a second request with a 7-tile image to the same batch, and `embed_multimodal` receives a list of tensors with 10, 10 and 7 tiles.

`_get_all_layer_features` removed padding with `pv[:num_patches]` only for 5-D input. `embed_multimodal` concatenated the list as-is (27 tiles), while the per-image split used the real counts from `image_size_to_num_patches` (5 + 10 + 7 = 22):

```
EMBED call: list tiles/item=[(10,), (10,), (7,)] image_sizes=[[480, 640], [876, 1300], [768, 1024]]
RuntimeError: split_with_sizes expects split_sizes to sum exactly to 27 ... but got split_sizes=[5, 10, 7]
```

**Fix.** Apply the same per-image slice for list input, and move the concatenation into `_get_all_layer_features` so both layouts go through one path. The change is model-local: no core or runner changes. Both model runners call `embed_multimodal` with the same batched kwargs.

**GPU<->CPU sync.** `embed_input_ids` zeroed image-token positions with `text_embeds[is_multimodal] = 0.0`. The model runner passes `is_multimodal` as a pinned CPU tensor, so boolean indexing a GPU tensor with it synchronizes on every request with images. It wasn't visible before because the only existing Granite 4.1 Vision generation test (`test_common.py`) is skipped; once the padding fix lets the new test reach this line, CI's `VLLM_GPU_SYNC_CHECK=error` rejects it. Replaced with `masked_fill_` using the mask copied to the device non-blocking (a no-op when it is already there). The deepstack buffer fill a few lines below (`target[is_multimodal] = ...`) does not sync and is unchanged.

**When it triggers.** It needs images with different tile counts, from more than one request, none served from the encoder cache, in the same encoder batch. That depends on load, so in production it is intermittent: we first hit it after 17 hours of GRPO rollouts.

**Test design.** The test runs the engine in-process (`VLLM_ENABLE_V1_MULTIPROCESSING=0`) so both requests are queued before the first engine step and their images are encoded together. With a separate engine process, the same test passes on `main`: the two requests can reach the scheduler in different steps. I checked that the processor cache isn't the reason: with a separate engine process, `main` doesn't crash with the cache on, off, or set to `shm`. The two requests are first run in one call (one encoder batch, list `pixel_values`), then each alone on a fresh engine (5-D `pixel_values`, no cache reuse), and the outputs are compared with `check_logprobs_close`, since batching can flip greedy tokens. Images are synthetic solid colors, so the test needs no assets.

**Not in this PR.** The existing `granite4_vision` entry in `tests/models/multimodal/generation/test_common.py` is always skipped, because the registry marks the model `is_available_online=False`. This PR leaves that entry as it is.
