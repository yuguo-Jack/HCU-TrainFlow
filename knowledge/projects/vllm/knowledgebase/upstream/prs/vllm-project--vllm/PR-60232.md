Adds `GraniteSwitchForCausalLM`: a Granite MoE-hybrid variant whose LoRA adapters live in
the checkpoint and are selected **per token** by control tokens in the prompt. Four new
files plus five small registration edits.

checkpoint we are still publishing, so CI will not be green yet.

## Claims

- Serves a checkpoint holding N LoRA/aLoRA adapters, routing each token to one of them
  with no runtime load, swap or eviction. One request can mix adapters across its tokens.
- One fused Triton kernel computes the base projection and all applicable adapter deltas
  in a single GEMM, skipping tiles whose tokens select no adapter.
- Supports TP, PP, `torch.compile` and CUDA graphs. Also serves the Shadow Residual
  dual-stream variant from the same class.
- No core-component changes: nothing in the model runner, scheduler, KV cache manager or
  `vllm/lora/`. Existing files take 1, 1, 2, 28 and 143 added lines.

## Details

### Why not `vllm/lora/`

`vllm/lora/` serves adapters that arrive at runtime: `LoRARequest`, slot allocation,
eviction, Punica. These arrive in the checkpoint, with each adapter's shrink rows already
concatenated onto the base weight into one tensor — no `lora_A`/`lora_B` pair is left to
load or swap. Selection is per token rather than per request, so there is no slot to
allocate. The problem is routing, not adapter lifecycle, and the kernel is specialized to
this weight layout, so nothing else in the tree could call it.

Precedent: `jina.py:143-149` wraps a base model with four task-specific LoRA adapters and
merges the selected one at load time, touching none of `vllm/lora/`. That folds one
adapter statically; N live token-switchable adapters is new. We would rather generalize
later from a working implementation than design the abstraction up front. `SupportsLoRA`
is deliberately not declared, since the adapters are baked in.

### MultiSwitch routing

Mapping a control token to an adapter index has to survive flattened batching and the
paged KV cache. MultiSwitch allocates two real `vllm.Attention` layers
(`SWITCH_CACHE_LAYERS = 2`): a counting head whose `1/(1+n)` attention signal gives the
token's write address, and a memory head keyed by Kerdock/Delsarte-Goethals codewords
that reads the adapter index back out. Control token ids are then rewritten with a
branch-free `torch.where` so the region stays traceable.

Those two layers are counted in the checkpoint's `num_hidden_layers` so a Transformers
`DynamicCache` sizes correctly, which is why `get_num_hidden_layers()` subtracts them for
PP slicing — same as `DeepSeekMTPModelArchConfigConvertor`. An RFC with the numerical
margins will follow.

### Design notes

- **Rank tiers.** Adapter ranks snap to `(16, 32, 64, 128, 256, 512)` and zero-pad, which
  is what the kernel specializes on. Validated at config time so an off-tier rank fails
  at startup rather than inside a Triton compile.
- **Startup validation.** A misread config here does not raise — it misroutes tokens or
  reads a KV cache that was never allocated — so `GraniteSwitchConfigVerifier` asserts
  its premises instead of relying on them. The main one: `attribute_map` aliases
  `layers_block_type` to `layer_types`, and vLLM's hybrid layer counter matches the
  literal `"attention"`, which Transformers renames to `"full_attention"`. The branch
  does not fire today, so the model works by coincidence; the verifier turns that into an
  enforced invariant.
- **Counting-head dtype.** The verifier rejects an fp8 KV cache, which would saturate the
  `1/(1+n)` signal and the scaled codebook keys, and reports bf16's exact-inversion bound
  (188 control tokens per sequence) at startup. fp32 extends it past 4095.
- **Platform.** CUDA and ROCm, via Triton. The bitmask op has a native PyTorch fallback,
  and `num_adapters == 0` is a plain Granite model on any backend.
- **Config location.** In-tree under `vllm/transformers_utils/configs/`, kept a thin
  `PretrainedConfig` with no behavior so relocating it to Transformers later
  (cf. e3cae8d2ac, #8837) stays mechanical.
