# [Bugfix][Core] Keep scheduling running requests after a priority self-preemption

[Upstream PR](https://github.com/vllm-project/vllm/pull/61976) · state: open · merged: False

## Original PR description

## Purpose

Under `--scheduling-policy priority`, when a running request cannot get KV blocks the scheduler preempts the lowest-priority running request. `self.running` is in admission order, not priority order, so that request can sit in the middle of the list, for example when higher-priority requests arrived after it. If it is the request currently being scheduled, it preempts itself, and the running loop then `break`s:

```python
if new_blocks is None:
    # Cannot schedule this request.
    break
```

Every running request after it gets no tokens in that step, even though they all have higher priority, the self-preemption just freed blocks, and budget remains. This is a priority inversion: the requests the policy is meant to protect lose a step whenever a lower-priority request ahead of them runs out of KV.

After a self-preemption the request has already been removed from `self.running` (`del self.running[victim_index]` with `victim_index == req_index`), so `req_index` already points at the next request. The fix continues the loop in that case. Nothing changes for FCFS: it preempts `running[-1]`, so a self-preemption there only happens on the last request. Other reasons for a failed allocation (a deferred free that will not help, pending connector frees) still end the loop.

Related but different: #49097 (fixed by #49206) adjusted `req_index` when the victim sits before the cursor. #39375, a larger rework of this preemption path that has been open since March, would also remove this `break`.

Hi @yewentao256 — would you be able to take a look at this when you have a moment? You merged #58259 in this part of the scheduler recently, so I thought you might be a good fit.

Under `--scheduling-policy priority`, when the request being scheduled is the lowest-priority running request and cannot get KV blocks, it preempts itself, and the running loop then `break`s. Since `running` is in admission order, higher-priority requests that arrived later sit behind it and get no tokens that step, even when they need no new blocks and budget remains.

The fix is to `continue` instead of `break` after a priority self-preemption; `req_index` already points at the next request because the preempted one was removed from `running`. FCFS and the other allocation-failure paths are unchanged. Verification on `fd33f32468`: the new test fails on main and passes here; `tests/v1/core` has the same failure set as main (+1 pass). A random-workload stall check went from 1/40 stalled seeds on main to 0/40.

One review focus: I limited the `continue` to the PRIORITY self-preemption case and kept `break` for the other ways the allocation can fail (deferred frees, pending connector frees). Happy to adjust if you'd prefer it broader.
