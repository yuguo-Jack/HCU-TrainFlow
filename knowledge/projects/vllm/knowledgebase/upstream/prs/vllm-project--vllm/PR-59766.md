# [MOE][Quantization] Extend correctness test of `AITER_MXFP4_BF16` MOE backend and temporarily fix correctness issues with Swiglu + no bias code path

[Upstream PR](https://github.com/vllm-project/vllm/pull/59766) · state: open · merged: False

## Original PR description



## Disclosure

AI assistance was used. The changes were reviewed and tested manually.

## Overview

This PR adds correctness test for `AITER_MXFP4_BF16` MOE backend without bias in `tests/kernels/moe/test_ocp_mx_moe.py` and bypasses two uncovered AITER bugs until AITER fixes are merged, released, and the AITER version is bumped in vLLM, with workarounds.

These bugs were uncovered using `AITER_MXFP4_BF16` on a real internal model.

## Claims

This PR implements these two temporary fixes for numerical correctness:

- Use `GateMode.SEPARATED` in this case where `INTERLEAVED` is numerically wrong, fixing wrong outputs of `AITER_MXFP4_BF16` for bias-free SwiGLU (`SWIGLUOAI` / `SWIGLUOAI_UNINTERLEAVE`).
- Fix `GateMode.SEPARATED` numerically wrong case for certain `model_dim` dimensions (non-multiple of 512) by extending `mxfp4_round_up_hidden_size_and_intermediate_size`, fixing wrong outputs on that path when the **hidden size is not a multiple of 512 (e.g. 256, 768)**

These two bugs arise with bias-free SwiGLU MXFP4 models (e.g. [amd/MiniMax-M3-MXFP4](https://huggingface.co/amd/MiniMax-M3-MXFP4)) served with `AITER_MXFP4_BF16` MOE backend and have fixes submitted to AITER:

- https://github.com/ROCm/aiter/pull/6022
- https://github.com/ROCm/aiter/pull/6086

`test_rocm_mxfp4_moe_oracle` is now parametrized over `has_bias`, hidden size, and intermediate size, and tests:

- the bias-free `AITER_MXFP4_BF16` path with strict thresholds (95% within `rtol=0.1`, 99.5% equal signs, was 70% within tolerance),
- an `EMULATION` reference case and an `AITER_MXFP4_BF16_SILU` case (SiLU on `AITER_MXFP4_BF16`, 90% within `rtol=0.5`, 98% equal signs), whose H=384 cases cover the hidden size alignment fix.

Other backends are skipped on bias-free weights and on the new shapes, and `AITER_MXFP4_BF16_SILU` with bias is skipped as AITER has no kernel for it (`TODO: ungate`).

**Note that on `main`, this test only covers weights with bias (GPT-OSS layout). The bias-free path was untested and fails for every shape (see below).**

## Details

**ROCm/aiter#6022.** With interleaved gate/up, AITER runs CK-Tile stage 1 with `split_k=1`. No `(Swiglu, HasBias=false, split_k=1)` dispatcher specialization is built, so the default one runs SiLU. vLLM now selects `GateMode.SEPARATED` for bias-free SwiGLU-OAI in `rocm_aiter_moe.py` and shuffles the weights to match in `convert_weight_to_mxfp4_moe_kernel_format`.

**ROCm/aiter#6086.** The separated path forces CK-Tile split-K >= 2 for stage 1. The host derives the loop count from K rounded to the 256-wide K tile, while the kernel splits K at 32 granularity without masking, so results are correct only when `K % (split_k * 256) == 0`. AITER's `get_ksplit` only returns valid split counts but falls back to `split_k=2`, so the path is correct for hidden sizes that are multiples of 512. Two changes on the vLLM side:

- `mxfp4_round_up_hidden_size_and_intermediate_size` takes a new `has_bias` argument and pads the hidden size to a multiple of 512 for `AITER_MXFP4_BF16` + SwiGLU-OAI + `has_bias=False` only. The MoE runner already pads activations and slices outputs.
- `hidden_pad=0` is passed to AITER on this path. AITER uses it as `k_pad_zeros`, which skips the tail of the last K tile of every split-K partition, not only the last one, so passing the real `hidden_pad` drops real data (padding H=768 to 1024 with the real `hidden_pad` gives 68.20% sign agreement).

**Hidden size alignment for SiLU/SiTU.** #50582 and #51473 aligned both sizes to 128 for SiLU/SiTU on `AITER_MXFP4_BF16`, to keep Kimi-K3's and DeepSeek-V4's native intermediate sizes (e.g. 384 per partition at TP8). AITER's untuned FlyDSL fallback uses `tile_k=256` for stage 1, whose K is the hidden size, while stage 2 picks `tile_k=128` for intermediate sizes that are not 256-aligned. Hidden sizes that are odd multiples of 128 therefore read past K in stage 1. This was not visible before because only `Mxfp4MoEMethod` forwarded `activation`, and Kimi-K3/DeepSeek-V4 have H=7168.

## Conflicts with `main` and how they were resolved

- **`vllm/model_executor/layers/fused_moe/oracle/mxfp4.py`**: #55104 split the ROCm alignment into `intermediate_alignment` / `hidden_alignment` (W4A4 intermediate aligned to 128, hidden to 256). I kept `main`'s `intermediate_alignment`, including the W4A4 case, and used this PR's hidden rule: `hidden_alignment = 128 if is_situ_or_silu and triton_uses_128 else 256`. This rule already gives 256 for W4A4. The bias-free SwiGLU 512 padding is unchanged.
- **`tests/kernels/moe/test_ocp_mx_moe.py`** (`test_rocm_mxfp4_moe_oracle`): kept both sides. That covers `main`'s `requires_gfx1250` skip and `assert isinstance(out, torch.Tensor)`, and this PR's shape/bias skips and `gate_modes == ["separated"]` assertion.
- **`test_rocm_mxfp4_round_up_hidden_and_intermediate`** (added on `main` by #55104) pinned `AITER_MXFP4_BF16` + SiLU/SiTU to keep hidden size 384. This PR shows that this alignment gives wrong outputs (see above), so the expectation is now 512. I also parametrized the test on `has_bias` (see below).
- **mypy**: `main` added the `RocmBackendConfig` TypedDict. I declared this PR's `backend` and `sign_percent` config keys as `NotRequired` in it.

## New and updated test cases

`test_rocm_mxfp4_round_up_hidden_and_intermediate` now takes a `has_bias` column (`None` for the existing rows):
- `AITER_MXFP4_BF16` + `SITU`/`SILU`, `has_bias` in `None`/`True`/`False`: hidden 384 -> 512 (was 384), intermediate stays 384.
- `AITER_MXFP4_BF16` + `SWIGLUOAI`/`SWIGLUOAI_UNINTERLEAVE`, `has_bias=False`: hidden 256 -> 512, 384 -> 512, 768 -> 1024, 1024 -> 1024 (`# TODO` linking ROCm/aiter#6086).
- `AITER_MXFP4_BF16` + `SWIGLUOAI` with `has_bias` `True`/`None`: hidden 768 stays 768, so no 512 padding with bias.
- `AITER_MXFP4_FP8` + `SWIGLUOAI`, `has_bias=False`: hidden 768 stays 768, so the padding only applies to `AITER_MXFP4_BF16`.
