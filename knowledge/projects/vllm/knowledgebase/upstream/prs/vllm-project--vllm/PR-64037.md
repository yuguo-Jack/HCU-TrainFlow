# [Kernel][MiniMax-M3] Enable SM90 split-K in the Triton indexer

[Upstream PR](https://github.com/vllm-project/vllm/pull/64037) · state: closed · merged: True

## Original PR description

## Overview
Enable the existing MiniMax-M3 indexer split-K path on SM90 with a fixed target of 1056 CTAs. SM120 behavior is unchanged.

## Claims
Fresh validation on h200_agent (2026-10-29): 8×H200, TP8, BF16 real weights, 2048 batched tokens, concurrency 1, random-token prompts, 64 output tokens. TTFT median of 3 runs (min–max in parentheses):

| Input tokens | Baseline, seconds | Split-K, seconds | TTFT reduction |
|---|---|---|---|
| 32,768 | 1.6701 (1.6639–1.6734) | 1.5760 (1.5497–1.5763) | 5.6% |
| 131,072 | 8.7296 (8.7288–8.7438) | 6.5041 (6.5040–6.5149) | 25.5% |
| 229,376 | 18.9614 (18.9611–18.9618) | 12.1225 (12.0730–12.1276) | 36.1% |

## Validation
- Baseline/optimized greedy completion text SHA-256 hashes match at 4K, 32K and 131K inputs (64 output tokens, fixed seeded prompts).
- H200 standalone split-K score checks pass bit-exactly for long-context and mixed-request inputs.
- `ruff check`, `ruff format --check` on both changed files, and `git diff --check` pass; 576 launch-policy combinations checked locally.

Reproduction: serve each arm with `--block-size 128 --tensor-parallel-size 8 --max-num-batched-tokens 2048 --gpu-memory-utilization 0.95 --max-num-seqs 64 --max-model-len auto`, warm up at 8192 tokens, then issue each input length 3 times. Baseline uses the pre-PR score wrapper; optimized uses b775ed3. Only the indexer score wrapper differs between serving arms; row sharding is disabled in both.

## Details
Chunked prefill underfills Hopper with the unsplit grid. Splits write disjoint score columns. Removed A/B and tuning flags, standalone test scaffolding, and row sharding. Complements #57420 (sparse attention); this change targets indexer scoring. Validation uses the existing v0.31.0 serving environment with the score wrapper overlaid, rather than a full rebuild of current main.

> how much speedup is coming from split-K and from shard-Q individually? I wonder if we should split it into 2 PRs

| Config | 32K | 131K | 229K |
| --- | --- | --- | --- |
| baseline | 1.67 s | 8.66 s | 18.75 s |
| split-K only | 1.54 s (+7.4%) | 6.82 s (+21.3%) | 12.07 s (+35.6%) |
| split-K + row-shard | 1.54 s (+7.6%) | 6.39 s (+26.2%) | 11.67 s (+37.7%) |
| row-shard only | ±1% | ±1% | ±1% |

So split-K is the dominant contributor and carries essentially all of the gain. The row-shard adds a further ~+2–5pp only on top of split-K: with split-K disabled, the score grid is severely under-occupied (32 CTAs on 132 SMs at mnbt=2048), and halving rows per rank just reduces CTA count further without shortening the latency-bound wall time — row-shard starts paying off only once split-K has restored occupancy.
