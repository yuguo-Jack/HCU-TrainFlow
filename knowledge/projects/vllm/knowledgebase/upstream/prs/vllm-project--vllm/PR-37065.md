# [Bugfix][sleepmode] Serialize GPU VMM operations to fix sleep/wakeup race condition

[Upstream PR](https://github.com/vllm-project/vllm/pull/37065) · state: open · merged: False

## Original PR description

## Purpose
Fixes #36753

This PR addresses a critical race condition in vLLM V1's sleep and wake_up transitions when multiple engine instances share the same GPU.

### Problem
In vLLM V1, independent API server processes manage their own physical memory mappings via CUDA VMM. When multiple models on the same GPU attempt concurrent VMM operations, specifically when Model A is sleeping (releasing memory) while Model B is waking up (acquiring memory), the CUDA driver's internal state becomes inconsistent.

### This leads to two failure modes:
Silent Livelock: The process hangs indefinitely in kernel space.
EngineDeadError: The process crashes with a hard error during memory re-mapping (as reported by users).

### Solution
Implemented a Node-Local Atomic Signaling mechanism in Executor:
Atomic Serialization: Uses os.O_EXCL to ensure only one process per GPU can perform VMM operations (sleep/wake_up) at any given time.
Self-Healing: Automatically detects and cleans up stale signal files if a process crashes (through os.kill(pid, 0)), preventing deadlocks.
Cluster Safety: Incorporates hostname in the signal path to prevent false contention on shared filesystems (NFS/Ceph).

## Test Plan
Environment
GPU: A100 80GB (or H100)

Config: lmcache and Two V1 instances (Model A & Model B) with gpu_memory_utilization=0.8. 
see user original issue script

Reproduce Steps
Concurrent Wakeup: Trigger wake_up for both models simultaneously.

Transition Race:
Wake up Model A.
Simultaneously send POST /sleep to Model A and POST /wake_up to Model B.

Expected Behavior
Processes should wait for each other in a queue. Logs should show GPU VMM busy (Owner: ...), waiting... instead of hanging or crashing.

This block has two potential issues:
1.  **Security Risk**: `os.chmod(sig_dir, 0o777)` makes the signal directory world-writable. On a multi-user system, this allows any user to interfere with the locking mechanism by creating or deleting signal files, which could lead to deadlocks or other race conditions.
2.  **Broad Exception Suppression**: `contextlib.suppress(Exception)` is too broad. It can hide important errors, such as `PermissionError` if the process lacks permissions to create or modify the directory, making potential issues difficult to debug.

A safer approach would be to use more restrictive permissions (like `0o1777` with a sticky bit) and handle specific exceptions.

```python
        try:
            # The sticky bit (0o1000) ensures that only the owner of a file
            # in this directory can delete or rename it.
            mode = 0o1777
            sig_dir.mkdir(mode=mode, parents=True, exist_ok=True)
            if os.name != "nt":
                # Ensure permissions are set in case the directory already existed.
                os.chmod(sig_dir, mode)
        except OSError as e:
            logger.warning(
                "Failed to create or set permissions on signal directory %s. "
                "GPU VMM serialization may not work correctly. Error: %s", sig_dir, e)
```

`contextlib.suppress(Exception)` is too broad and can hide important errors. If `unlink` fails here (e.g., due to a `PermissionError`), the exception will be suppressed, and the stale lock file will not be removed. This will cause the `while True` loop to continue indefinitely, attempting to acquire a lock that can never be obtained, effectively causing a livelock. It's better to catch specific exceptions and log an error if the stale lock file cannot be removed.

```python
                    try:
                        signal_path.unlink(missing_ok=True)
                    except OSError as e:
                        logger.error("Failed to remove stale lock file %s: %s. "
                                     "This may lead to a deadlock.", signal_path, e)
                        # Avoid a tight loop if unlink fails continuously.
                        time.sleep(1)
```

![high](https://www.gstatic.com/codereviewagent/high-priority.svg)

`contextlib.suppress(Exception)` is too broad and can hide critical errors. For instance, if reading the lock file fails (`OSError`), or parsing the PID fails (`ValueError`), the exception will be silently ignored, and the lock will not be released. This could lead to the process holding the lock if it doesn't crash, or leaving a stale lock file if it crashes later, potentially causing a deadlock for other processes. It's better to handle specific exceptions and log warnings for unexpected failures.

```python
        try:
            if not signal_path.exists():
                return
            with open(signal_path) as f:
                content = f.read().strip()
            if content and int(content) == os.getpid():
                signal_path.unlink(missing_ok=True)
        except (OSError, ValueError) as e:
            logger.warning("Error releasing GPU access lock %s: %s", signal_path, e)
```

The current lock implementation relies solely on the process ID (PID) to identify the lock owner. This can be unreliable due to PID recycling. If a process holding a lock crashes, and its PID is reassigned to a new process before the stale lock file is removed, the new process could be mistaken for the lock owner, potentially leading to deadlocks.

To make the locking mechanism more robust, I suggest including the process start time in the lock file along with the PID (e.g., `f"{pid}:{start_time}"`). When checking the lock, you can then verify both the PID and the start time of the process to ensure it's the original lock owner. The `psutil` library, which is already a dependency, can be used to get the process start time (`psutil.Process(pid).create_time()`).

You'll also need to add `import psutil` at the top of the file.

```python
        my_pid = os.getpid()
        try:
            my_create_time = psutil.Process(my_pid).create_time()
        except psutil.Error:
            # Fallback for robustness, though it should not happen in normal use
            my_create_time = -1.0
        my_lock_info = f"{my_pid}:{my_create_time}"
        acquired_paths: list[Path] = []

        for d_id in sorted_ids:
            sig_path = self._get_gpu_access_signal_path(d_id)
            while True:
                try:
                    flags = os.O_CREAT | os.O_EXCL | os.O_WRONLY
                    fd = os.open(str(sig_path), flags)
                    with os.fdopen(fd, "w") as f:
                        f.write(my_lock_info)
                    acquired_paths.append(sig_path)
                    break
                except FileExistsError:
                    owner_pid = -1
                    try:
                        content = sig_path.read_text().strip()
                        if not content:
                            raise ValueError("Lock file is empty.")

                        owner_pid_str, owner_create_time_str = content.split(":", 1)
                        owner_pid = int(owner_pid_str)
                        owner_create_time = float(owner_create_time_str)

                        if owner_pid == my_pid and owner_create_time == my_create_time:
                            # Re-entrant lock by the same process instance
                            acquired_paths.append(sig_path)
                            break

                        p = psutil.Process(owner_pid)
                        if p.create_time() != owner_create_time:
                            # PID was recycled.
                            raise ProcessLookupError

                    except (psutil.NoSuchProcess, ProcessLookupError, ValueError,
                            OSError):

                        with contextlib.suppress(OSError):
                            sig_path.unlink(missing_ok=True)
                        continue

                    logger.info(
```
