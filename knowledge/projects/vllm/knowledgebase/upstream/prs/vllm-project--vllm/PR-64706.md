# [Kernel] Port fused_deepseek_v4_qnorm_rope_kv_insert to CuTe DSL

[Upstream PR](https://github.com/vllm-project/vllm/pull/64706) · state: open · merged: False

## Original PR description

### Description

On CUDA, replaces `csrc/fused_deepseek_v4_qnorm_rope_kv_insert_kernel.cu` with a CuTe DSL module, `vllm/model_executor/kernels/attention/fused_deepseek_v4_qnorm_rope_kv_insert.py`, per @tlrmchlsmth's request on #63308 (closed): no DSv4-only kernel object code in the wheel, no extension compile time.

Same four entry points, same positional schemas, so call sites keep their argument lists. Math is ported bit for bit: fp32 accumulation, bf16 double-round before the absmax, warp shuffle reduction order, UE8M0 exponent-field scales, both paged record layouts (V4 584 B/token, V4.1 mxfp8 528 B/token), the full-cache bf16/fp8 variants, and graph-replay-safe launches. Scalar min/max/abs/rsqrt use the DSL's `cute.arch`/`cute.math` ops rather than hand-rolled helpers, and compile to the same instructions the .cu's intrinsics compiled to, with NaN handling following the hardware ops as in the .cu.

**ROCm is preserved.** The `.cu` stays but is built only for HIP (`CMakeLists.txt`), with its four torch ops registered under `#ifdef USE_ROCM`, so CUDA builds no longer compile or ship the kernel and AMD behavior is unchanged. The six production call sites (deepseek_v4/v41 attention and dspark) import the four functions from a new dispatch module, `fused_deepseek_v4_qnorm_rope_kv_insert_dispatch`, which routes ROCm to the extension op and everything else to the CuTe DSL module (imported lazily, failing closed with a named RuntimeError when nvidia-cutlass-dsl is missing).

The `kv`-only entry point also takes optional `kv_norm_weight`/`kv_norm_eps`; current call sites leave them unset, and the ROCm op does not take them (the dispatch raises `NotImplementedError` there instead).

### Performance vs the preserved .cu (H200)

Benchmarks ran on an H200 (sm_90a, CUDA 13.0, torch 2.14, nvidia-cutlass-dsl 4.8.0). The `.cu` is JIT-compiled with the CMake flags this file builds with (`-O3`, no fast-math, sm_90). Inputs are identical for both implementations, and timing uses CUDA-graph replay so the numbers are kernel-only. The benchmark checks correctness on every case (`q_max_ulp`, `q_bits_differ`, `k_bytes_differ`).

Measurements on the initial port (`a3f899ebab`):

| quant_insert, 2048 tok | 118 | 291 | DSL 2.5× slower |

Every case is faster. The closest is full_cache_bf16 T=512 (5.72 vs 5.55 µs), whose 68 MB working set is L2-resident and latency-bound for both implementations. The `.cu` launcher still switches to its reduced-grid kernel at 1024 tokens (`NUM_TOKEN_CUTOFF`); the DSL module no longer has a reduced-grid variant (see the launch-geometry section below). kv_rope_insert with a packed uint8 cache schedules the quant-insert kernel with zero query heads, and both full-cache dtypes run `fusedDeepseekV4FullCacheKernel`. quant_insert outputs are bit-exact against the `.cu` at every size (zero differing bits, zero differing cache bytes). Over runs on the final artifact, T=2048 measured `.cu` 118.5–118.7 µs vs DSL 101.0–101.1 µs, and T=8192 measured `.cu` 448.4–450.0 µs vs DSL 396.0–396.3 µs.

Each fix below came from diffing the DSL-generated SASS against the `.cu` SASS.

#### 128-bit vectorized memory access (`668d0b3bbd`)

The initial port touched memory through per-element DSL tensor indexing, which lowered to 32-bit loads and stores. Reworking the layouts so each lane's 16 elements move as one folded `cute.copy` with a 128-bit copy atom gave the paged kernel LDG.128/STG.128 and took quant_insert T=8192 from 1070 to ~453 µs (~1.4 to ~3.5 TB/s). The kernel is bandwidth-limited after this change, matching the `.cu`.

#### bf16 encode/store tail as one inline-asm block (`668d0b3bbd`)

This change fixed full_cache_bf16 (T=4096: 82 → 37.8 µs). The full-cache Q path ends with eight `cvt.rn.bf16x2.f32` (F2FP) feeding two 128-bit stores. In the DSL-generated SASS the eight conversions issued back-to-back and both stores waited on the last F2FP with nothing left to overlap. The `.cu` does not have this tail because its store address comes from runtime division and modulo, a long integer dependency chain that interleaves with the conversions.

The fix is `_q_tail_store_bf16`, a single inline-asm PTX block that owns both the conversions and the address math, hand-interleaved so the two chains hide each other:

```ptx
{
    .reg .b32 t0, t1, w0..w7;  .reg .b64 d0, d1;
    shl.b32            t0, $3, 8;               // slot   -> word offset
    cvt.rn.bf16x2.f32  w0, $6, $5;
    cvt.u64.u32        d0, t0;
    cvt.rn.bf16x2.f32  w1, $8, $7;
    mad.wide.u32       d1, $2, {row_words}, d0;  // token*row_words + slot
    cvt.rn.bf16x2.f32  w2, $10, $9;
    shl.b32            t1, $4, 3;                // lane   -> word offset
    cvt.rn.bf16x2.f32  w3, $12, $11;
    cvt.u64.u32        d0, t1;
    cvt.rn.bf16x2.f32  w4, $14, $13;
    add.u64            d1, d1, d0;
    cvt.rn.bf16x2.f32  w5, $16, $15;
    shl.b64            d1, d1, 2;                // words  -> bytes
    cvt.rn.bf16x2.f32  w6, $18, $17;
    add.u64            d1, d1, $1;               // + tensor base
    cvt.rn.bf16x2.f32  w7, $20, $19;
    st.global.v4.b32   [d1],    {w0, w1, w2, w3};
    st.global.v4.b32   [d1+16], {w4, w5, w6, w7};
}
```

The tensor base comes from `q.iterator.to_llvm_ptr()` → `llvm.ptrtoint(T.i64())` and is bound with the `l` constraint. `row_words` is a per-compile-key constant (`HQ * 256`), baked into the asm string as an immediate rather than passed as a register operand. The block is marked `has_side_effects=True` for the stores. It is bit-exact against `cute.copy` + `_encode_words` on every suite case, because the DSL's `fp32x2_to_bf16x2` lowers to `cvt.rn.bf16x2.f32`.

The asm tail slows the paged kernel at large T. Routing the paged kernel's Q store through this block (measured, then rejected) took T=2048 from 120.3 to 126.4 µs (0.94×) and T=8192 from 452.8 to 469.9 µs (0.96×). At 3.5+ TB/s, issuing stores early matters more than hiding conversion latency, and `cute.copy`'s folded store address issues earlier than an address chain interleaved with the conversions. The paged kernel keeps `cute.copy`, and only the latency-bound full-cache kernel uses the asm tail.

#### Rope-lane-guarded cos/sin loads in the paged kernels (`3f5bb3ad31`)

This change closed the last sub-parity cases (quant_insert T=2048/8192, 0.98×/0.99× → 1.09×/1.10×). RoPE only touches the last `ROPE_DIM` of each 512-dim head, which is 4 of 32 lanes per warp (`dim_base >= NOPE_DIM`). The rope step in the DSL was already guarded by that condition, but the cos/sin loads were not. SASS of the paged kernel before the fix contains four unpredicated `LDG.E.128` per lane on all 32 lanes:

```
/*1ca0*/  LDG.E.128 R8,  desc[UR6][R28.64+0x80] ;
/*1cb0*/  LDG.128   R12, desc[UR6][R28.64] ;
/*1cc0*/  LDG.E.128 R16, desc[UR6][R28.64+0x90] ;
/*1cd0*/  LDG.E.128 R20, desc[UR6][R28.64+0x10] ;
```

That is 2 KB of L2-resident loads per warp per slot where 256 B suffice. `_load_cos_sin` also computes `half_base = (dim_base - NOPE_DIM) >> 1`, which is negative on the 28 non-rope lanes, so those lanes loaded from out-of-bounds addresses (the values were never consumed, which is why nothing failed). The `.cu` guards all of this behind `is_rope_lane`. Guarding the `pos_ids` fetch and `_load_cos_sin` call with the same `dim_base >= NOPE_DIM` condition the rope step already uses is semantically identical (`pos` and `cos_v`/`sin_v` have no other reader) and improved T=2048/8192 by ~10% and mid T by 4-8% (T=64 1.39×→1.55×, T=512 1.44×→1.50×), at a small cost in the decode-size case (T=1 1.32×→1.21×).

The same guard slows the full-cache kernel. Applying it to the full-cache kernel's two identical load sites (measured, then reverted) dropped T=128 from 1.19× to 1.04×, T=256 from 1.11× to 0.99×, and T=512 from parity to 0.96×. Each warp in that kernel owns one token end-to-end and the early unconditional loads overlap subsequent work, so serializing the pos→cos/sin loads behind a branch costs more than the wasted L2 bandwidth saves. The asymmetry between the two kernels is deliberate and documented in the commit message.

#### Launch geometry: grid shape and CTA size (`5ab6c0fc4b`, `901bb03375`)

The `.cu` dispatches a second, reduced-grid kernel (one CTA per token, warps walking slots) above 1024 tokens. The initial port replicated that dispatch. Measuring the DSL's two grids against each other showed the DSL standard grid (one warp per `(token, slot)`) is faster at every size above the cutoff, so the reduced-grid kernel, its compile-key field, and `NUM_TOKEN_CUTOFF` are deleted from the DSL module:

| T | reduced-grid µs | standard-grid µs |
|---|---|---|
| 1024 | 56.2 | 51.9 |
| 2048 | 108.6 | 105.4 |
| 4096 | 210.8 | 200.2 |
| 8192 | 410.1 | 399.7 |

Both grids are bit-exact against the `.cu`. The `.cu` keeps its own reduced-grid kernel; its per-warp slot loop is what its software prefetch (below) is written against, and the register cost of that pattern is why it needs the coarser grid.

CTA size is also measured, per kernel. The paged kernel moved from 256-thread to 128-thread CTAs (equal or faster at every size; T=64 4.68 → 4.44 µs, T=8192 440.4 → 437.9 µs). The full-cache kernel now carries its CTA size in the compile key and picks it per store dtype and launch size:

| T | bf16/128 | bf16/256 | fp8/128 | fp8/256 | `.cu` bf16 | `.cu` fp8 |
|---|---|---|---|---|---|---|
| 128 | 2.32 | 2.45 | 2.54 | 2.40 | 2.87 | 2.73 |
| 512 | 5.53 | 5.64 | 5.03 | 4.50 | 5.70 | 5.05 |
| 1024 | 8.61 | 8.58 | 7.67 | 6.74 | 9.03 | – |
| 2048 | 15.11 | 15.33 | 15.76 | 16.99 | 17.20 | – |
| 4096 | 37.22 | 37.87 | 29.69 | 31.27 | 47.26 | 39.88 |

bf16 rows prefer 128-thread CTAs at every size. fp8 rows, half the bytes, prefer 256-thread CTAs while the working set is L2-resident (latency-bound) and 128-thread CTAs once the launch spills to DRAM, so the fp8 entry point switches at 2048 tokens. The same matrix is in the comment above the constants in the module.

#### SASS and occupancy, reduced-grid paged kernel

Measured before that variant was deleted; the numbers below explain the prefetch result that follows. Bench key: 64 Q heads padded to 128, q-norm + q-rope, bf16 KV, T at or above the reduced-grid cutoff.

| | `.cu` | DSL |
|---|---|---|
| instructions | 861 | 723 |
| registers/thread | 71 | 50 |
| resident CTAs/SM (warps) | 3 (24) | 5 (40) |
| LDG | 10 | 15 |
| SHFL | 16 | 7 |

The DSL kernel is smaller and runs at higher occupancy, so the pre-guard deficit of 1-2% at T=2048/8192 came from memory-level parallelism rather than instruction count or occupancy. The rope-lane guard recovered it; the slot-loop prefetch below was the next attempt at the same asymmetry and was rejected.

#### Measured and rejected: slot-loop prefetch and buffer rotation

The `.cu`'s reduced-grid kernel software-prefetches the next slot's `uint4`s and rotates buffers inside the slot loop, and it calls `cudaGridDependencySynchronize()` once before the loop instead of once per iteration:

```cpp
if (warpId < slot_end) {
  int curr_slot = warpId; uint4 v0_curr, v1_curr;
  load_slot(curr_slot, v0_curr, v1_curr);          // prologue
  while (curr_slot < slot_end) {
    int const next_slot = curr_slot + warpsPerBlock;
    uint4 v0_next, v1_next;
    if (next_slot < slot_end) load_slot(next_slot, v0_next, v1_next); // prefetch
    processDeepseekV4Slot(v0_curr, ...);
    v0_curr = v0_next; v1_curr = v1_next;          // rotate
  }
}
```

Porting this to the DSL measured slower on every case it touches, with bit-exact outputs: quant_insert T=2048 108.6 → 111.2 µs, T=8192 410.0 → 431.1 µs, T=64 4.78 → 4.99 µs, kv_rope_insert 5.79 → 5.98 µs. The `.cu` fits this pattern in 71 registers because ptxas turns the buffer rotation into a register rename. In the DSL the rmem buffers are memrefs, so the rotation is an explicit per-slot word copy whose prefetched result must stay live across the full processing of the previous slot, and the register allocator grows the reduced-grid kernel from 50 to 110 registers per thread (`cuobjdump --dump-resource-usage`), cutting residency from 5 CTAs/SM (40 warps) to 2 (16 warps). At ~3.9 TB/s the kernel does not lack memory-level parallelism, so the prefetch trades occupancy it cannot spare for overlap it already has. The DSL slot loop stays serial. The reduced-grid kernel carrying that slot loop was later deleted outright (see the launch-geometry section); this result is recorded for anyone re-introducing a slot loop in the DSL.

#### Methodology

Each optimization was measured with an ablation harness on the H200 pod: apply one source edit to the module in place, bench in a restricted environment, restore the module, and compare against the unedited baseline. SASS came from `--keep-cubin` + `nvdisasm` dumps in a fresh cwd, because the DSL resolves the cubin output path from the process start directory. All numbers in the tables above were re-measured on the exact pushed artifact (md5-verified deployment), and the 227-test suite ran against that same artifact.

### Test plan

- The branch's 227-test kernel suite passes on an H200 (sm_90, CUDA 13.0, torch 2.14, nvidia-cutlass-dsl 4.8.0) in 92s and validates the `cute.arch`/`cute.math` scalar ops on Hopper. RoPE outputs are compared at `rtol=1e-2`/`atol=1e-6` (FMA contraction in the eager reference).
- Between the two implementations, cache bytes are identical (mxfp8) or differ in ≤8 of 4.8M (V4 record, RoPE rounding ties). q outputs differ on ~7e-7 of elements, all on the sin lane of a rope pair, where a 1-ULP normed-input difference is amplified by cancellation, within the suite's tolerances.
- The kernel suite tests the DSL module directly; the AMD replay test keeps main's `torch.ops` path; the mono-numerics suites keep main's CDNA4-only gating (they exercise the extension op on ROCm); the compressor and PCP tests call/patch the dispatch functions.
- Local: `py_compile`, pinned-ruff (0.14.0) check + format, and the CI mypy wrapper (1.20.2) clean on the changed files; CUDA suites to run in CI.
