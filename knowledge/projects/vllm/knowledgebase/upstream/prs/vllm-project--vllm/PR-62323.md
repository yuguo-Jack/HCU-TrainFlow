# [Bugfix][Responses] Enforce max_tool_calls bound in builtin tool loop

[Upstream PR](https://github.com/vllm-project/vllm/pull/62323) · state: closed · merged: False

## Original PR description

## Overview

`max_tool_calls` is declared on `ResponsesRequest` and echoed back in
response objects, but it had no consumer anywhere in serving code: the
builtin tool loop in `_generate_with_builtin_tools` is an unbounded
`while True` whose only exit condition is the model itself stopping to
call tools. This PR enforces the declared bound and adds `ge=0`
validation on the field.

## Claims

- The builtin tool loop now stops after exactly `max_tool_calls` builtin
  tool calls have been executed.
- `max_tool_calls` rejects negative values with 422 at the protocol layer
  (`Field(default=None, ge=0)`).

## Validation

- Before the fix: a request carrying `max_tool_calls=2` against a model
  that emits a builtin tool call on every turn performed an unbounded
  number of engine round-trips (observed 50+ under an external emergency
  cap; the loop itself has no limit), while the request carried and
  echoed `max_tool_calls=2` as if a quota were in effect.
- After the fix: the loop exits after exactly `max_tool_calls` tool
  calls (`sub_request + 1 >= max_tool_calls` check after
  `context.append_tool_output`). Logic-level reproduction script and
  loop-level unit test included in test runs.

## Details

Root cause: the field is declared (protocol.py `ResponsesRequest`),
echoed in `ResponsesResponse`, and copied through sub-requests, but the
serving loop never reads it. Each turn additionally re-derives
`sampling_params.max_tokens` from the full remaining budget
(`get_max_tokens(...)` at the bottom of the loop body), so nothing
bounds the number of turns.

The check lives after `context.append_tool_output(tool_output)` so the
tool result of the final allowed call is still appended to the context
before exiting.
