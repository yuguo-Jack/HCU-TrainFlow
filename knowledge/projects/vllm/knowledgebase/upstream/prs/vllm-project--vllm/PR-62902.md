# [Bugfix][ROCm] Inkling: zero CUDA-graph padding rows in decode attention

[Upstream PR](https://github.com/vllm-project/vllm/pull/62902) · state: open · merged: False

## Original PR description



## Overview

With `FULL_DECODE_ONLY` CUDA graphs, Inkling on ROCm can hit a GPU memory fault in `fused_moe_kernel` once a few requests decode concurrently (`--enforce-eager` avoids it). Decode graphs are replayed at fixed batch sizes, so 3 live requests run in the batch-4 graph with one padding row. That row has `cache_seqlens` 0 and belongs to no request, but its attention output flows through the residual into the MoE gate, and two paths can leave NaN there. A NaN gate logit can make top-k return an index past the routed experts. Related: #61413 (open) moves this code to `inkling/common/`; both bugs are still in its version, and we are happy to rebase onto it or have it fold this in.

## Claims

- Split-KV decode: `_split_kv_stage2` combines zero splits for an empty row and stores `acc / row_sum` = 0 / 0. It now divides only where `row_sum > 0`, so an empty row stores exactly 0; rows with at least one split are bit-identical.
- Single-pass decode (`INKLING_SPLIT_KV=0`, and every layer where split-KV is not selected): the kernel never writes the padding row, and `InklingAttention.forward` allocated the output with `torch.empty`, i.e. graph-pool memory. It is now `torch.zeros` (the non-dict-metadata branch already called `zero_()`, now folded in). Cost: one memset of the attention output per layer, not measured separately.
- The NVIDIA Inkling path uses different kernels and is not changed.

## Validation

MI250X, Inkling (MXFP4 weights, emulated MoE), TP8 x PP4 on 4 nodes, `FULL_DECODE_ONLY` graphs:

| change | result |
|---|---|
| neither | memory fault in `fused_moe_kernel` at 3 concurrent requests; eager runs the same load |
| stage-2 guard only | fault returns at 7 concurrent (batch-8 graph, one padding row); per-layer instrumentation shows layer 0's attention output non-finite at the padding row, differing across TP ranks |
| both | the 7-request load passes; our MI250X Inkling deployments have run with graphs and both changes since |

New `tests/models/inkling/rocm/test_rel_attention.py::test_split_kv_decode_padded_row_is_zero`: one real row (257 tokens) and one padding row through split-KV decode; the real row must match the reference and the padding row must be exactly 0. The directory's conftest skips below gfx950, so CI runs it on MI355X; we ran it on 1x MI250X (gfx90a) with that skip lifted locally (the kernels are plain Triton).

## Details

**No test for the single-pass path.** `torch.empty` returning non-finite memory is not reproducible outside a graph pool; the end-to-end run above is the evidence for that half.

**Not tested.** The new test on gfx950, the CI target for this directory.

@tjtanaa could you please take a look at this when you have a moment, since you added Inkling on ROCm in #48841? With `FULL_DECODE_ONLY` CUDA graphs, the padding rows in decode attention can come out as NaN. The split-KV combine computes 0/0 for an empty row, and the single-pass path leaves the row as uninitialized graph-pool memory. A NaN gate logit then sends top-k past the routed experts and faults in `fused_moe_kernel`. This change zeroes those rows; rows with real work are bit-identical.
