# [Bugfix][Core] Keep offline DP ranks' collectives aligned with async scheduling

[Upstream PR](https://github.com/vllm-project/vllm/pull/64457) · state: closed · merged: True

## Original PR description



## Overview

Offline data parallelism (`LLMEngine` with the in-process client, e.g. `distributed_executor_backend="external_launcher"`) hangs with async scheduling when one DP rank gets a step that runs no model forward. `LLMEngine.step()` now runs `execute_dummy_batch()` for such a step when DP is on, as `DPEngineCoreProc.run_busy_loop` already does for `vllm serve`.

## Claims

- Offline DP2 with async scheduling no longer hangs when the ranks' workloads differ; both Model Runner V2 and V1 finish.
- The V1 runner's `external_launcher`-only `_dummy_run(1)` (#28774) is removed, since the engine now runs the dummy batch for every in-process DP backend and V1 would otherwise sync twice.

## Validation

Reproducer (`torchrun --nproc-per-node 2`, Qwen/Qwen3-0.6B, `data_parallel_size=2`, `distributed_executor_backend="external_launcher"`, `async_scheduling=True`, greedy; rank 0 runs 1 prompt with `max_tokens=8`, rank 1 runs 4 prompts with `max_tokens=256`, `ignore_eos`), one GB200 node:

The new test fails on main for the step that ran no forward.

## Details

- Root cause: the offline loop needs every rank to run exactly one forward, and so one DP sync, between two `has_unfinished_dp()` all-reduces. With async scheduling, a rank whose only remaining request already reaches `max_tokens` through placeholders schedules 0 tokens (or only pops a queued batch). The V2 runner then returns before `dispatch_cg_and_sync_dp`, so that rank goes on to the `has_unfinished_dp()` all-reduce while the other rank waits in its forward's DP sync: the two ranks wait in different collectives.
- `InprocClient.get_output()` records whether its step executed the model, and `LLMEngine.step()` runs the dummy batch when it did not. Multiprocess clients don't set the attribute, so their behavior is unchanged: `DPEngineCoreProc` already runs the dummy batch itself.
- Related: #43547 reports a similar DP desync on the V1 runner with the ray / mp backends; this PR does not change those backends.
