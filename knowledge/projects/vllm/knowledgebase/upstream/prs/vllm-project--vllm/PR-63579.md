# [Attention] Trace-driven fusion follow-ups: DFlash pad split, native decode lens, Gumbel finalize

[Upstream PR](https://github.com/vllm-project/vllm/pull/63579) · state: closed · merged: False

## Original PR description

# Warning: Untested AI-generated code.

Stacked on #63296, #63307, #63393 and #63523 — the head branch
carries those PRs' commits; only the last three commits are new.

## Motivation

A torch-profiler trace of the four-PR stack (campaign
dsv41-pd-fusions-prof-002, 8xH200 PD decode, c16, MTP 3) classifies
every kernel around the captured decode forward as graph-launched
or eager and measures the eager slice at 34 kernels / 170.7 us of
GPU time per step. Three of the remaining items are fixable kernel
fusions; this PR carries them.

## Split DFlash buffer padding into one wide launch

`_prepare_dflash_inputs_kernel` padded the drafter's CUDA-graph
buffers inside every per-group launch, blocked at the BLOCK_SIZE
derived from the per-request token span — 8 on a decode step — so
the four pad regions cost thousands of serialized 8-wide stores,
repeated once per draft KV cache group over shared output buffers.
The trace shows 3 launches per step at 42.7-44.8 us each: 131 us of
the 170.7 us eager GPU section, 77% of it. The padding now runs as
its own launch with a fixed 256-wide block, called once from
`propose()` before the per-group loop: one grid spans the qsl,
seq_lens, sample and query pad regions (each indexes its own buffer
from zero, so the grid covers the largest region end), and pads
every draft group's row of the shared slot-mapping table through a
cached group-id tensor. Buffer addresses and every written value are
unchanged, so replay semantics and the existing
`test_dflash_prepare_inputs` assertions hold.

## Build the native indexer decode lens in one kernel

The native MTP branch of `_prepare_decode_tensors` built the
`(B, max_decode_len)` per-token context lengths as a broadcast chain
(sub, add, clamp) into the decode seq-lens view. That is three
launches per indexer metadata build, and the profiled step ran the
chain on each of its builds between graph replays. It is now one
`PrepareNativeDecodeLensKernel` launch writing
`max(seq_lens[b] - max_decode_len + j + 1, 0)` directly over a
256-wide block-strided grid (`cdiv(num_decodes * max_decode_len,
256)` programs, each covering a vector of rows), following
the warmup-registered `PrepareUniformDecodeKernel` pattern
(compile key over the max_decode_len specialization class,
registered in the three attention backends that register its
sibling). The now-unused `offsets_buffer` arange is removed. The
compress-ratio divide stays a separate op: it must run after DCP
localizes the decode seq lens, so folding it in would change
floor-div semantics under sharding.

## Fuse the Gumbel sample finalize into one kernel

`gumbel_sample` reduced its per-block partials with
`local_max.argmax` followed by a gather of `local_argmax` — two
kernels inside the captured decode graph, ~6 us per sampling round
at three rounds per step. One finalize kernel now reduces the
partial row and loads the winning token id in a single program,
preserving torch.argmax's first-occurrence tie break via a where/min
index select. This one saves in-graph GPU time only; it removes no
host dispatch.

## Ruled out by the trace

- The 301 us/step `nvjet` GEMM is the in-graph lm_head streaming
  ~1.85 GB of bf16 weights at tiny M — weight-bandwidth-bound, not a
  fusion item.
- The engram hash/lookup chain is in-graph, with per-layer embedding
  tables prefetched on a side stream; batching the lookups would
  serialize work the prefetch currently overlaps.
- The two paged-MQA metadata builds cannot merge: deep_gemm returns
  fresh tensors and the DtoD copies exist to keep CUDA-graph address
  stability.
- Folding the image-sentinel mask polarity saves no launches: both
  polarities are consumed.

## End-to-end measurement

Campaign dsv41-pd-fusions-e2e-fus-004-20261025-1430 on the PD
deployment (2x8 H200, TP1 x DP8, MTP 3, aiperf CC-trace load,
nyann, gsm8k), stacked on the same base as the four-PR run before
it (`vllm-main` at `e9acf4861`; exp = `dsv41-decode-fusions` at
`e39a4dcd`, i.e. this PR on top of #63523). The previous campaign
(fus-003) is the four-PR stack, so the delta isolates this PR.

- aiperf ITL p50: c8 4.93 -> 4.85 ms, c16 5.07 -> 4.98, c32
  5.77 -> 5.72, c64 6.78 -> 6.70, c128 8.77 -> 8.66. ITL p90 came
  down at every stage as well. Request counts, ISL/OSL p50 and
  error counts match between the runs; output tok/s holds within
  +-0.8% at c16-c128.
- nyann ITL p50 (ISL/OSL 2048): 15.5 -> 15.3, 18.2 -> 18.0,
  23.0 -> 22.9 ms.
- gsm8k flexible-extract 0.9697 +-0.0047 -> 0.9712 +-0.0046,
  strict-match 0.9689 -> 0.9682 (within stderr), 0 errors.

Each individual latency number sits inside the +-2% band same-build
repeats of this deployment span; the sign is uniform across all
thirteen decode-latency measurements (aiperf p50 and p90 at five
concurrencies, nyann p50 at three). The c16 saving, ~90 us/step,
matches the trace's ~120 us eager-GPU estimate net of the new pad
launch.

The branch now sits above the measured build through commits carried
in by the rebase and one local refinement: #63523's mypy narrowing
fix and its upload-on-change params-table cache (no per-step copy),
plus this PR's decode-lens kernel moving to a 256-wide block-strided
grid in place of one program per token.
