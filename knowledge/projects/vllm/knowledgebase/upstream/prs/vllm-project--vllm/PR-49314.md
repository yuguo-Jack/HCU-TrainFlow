# fix(sampler): fall back to native sampling when flashinfer is absent

[Upstream PR](https://github.com/vllm-project/vllm/pull/49314) · state: open · merged: False

## Original PR description

`flashinfer_sampler_supported()` imports the FlashInfer backend unconditionally when `VLLM_USE_FLASHINFER_SAMPLER` is on (the default). flashinfer isn't available on every CUDA platform (e.g. aarch64), so on a build without it the import raises `ModuleNotFoundError` and **crashes engine init** instead of falling back to native sampling — even though the rest of the codebase treats flashinfer as optional via `has_flashinfer()`.

Hit this on a from-source build on **GB10 (sm121, aarch64)** where flashinfer isn't installed:
```
ModuleNotFoundError: No module named 'flashinfer'   # from Sampler.__init__ -> flashinfer_sampler_supported()
```

Fix: guard the import with `has_flashinfer()` and route absence through the existing "unsupported" path — warn + degrade by default, or a clear `RuntimeError` if the user explicitly set `VLLM_USE_FLASHINFER_SAMPLER=1` (instead of the raw import error). No change when flashinfer is present.

Verified on GB10: engine now starts and generates with top-p/top-k sampling. Added a regression test (mock CUDA platform + absent flashinfer).

@joynerwk03 you were right that the rebase narrowed this to `except ImportError` and left "FlashInfer installed but can't build" uncovered. I hit that case for real today, so I've pushed the part that was missing.

On a DGX Spark (GB10, sm_121, CUDA 13) with plain `vllm serve`-equivalent startup:

```
RuntimeError: Engine core initialization failed
  ...
  vllm/v1/worker/gpu/sample/sampler.py:336 _sample_random
  vllm/v1/sample/ops/topk_topp_sampler.py flashinfer_sample
  flashinfer/sampling.py top_k_top_p_sampling_from_logits
  flashinfer/jit/cpp_ext.py run_ninja
RuntimeError: Ninja build failed. <command-line>: fatal error: cuda_runtime.h: No such file or directory
```

`nvcc` is on PATH, `ninja` is on PATH, the arch is fine, so `has_flashinfer()` and `check_cuda_arch()` both pass — then the lazy JIT build fails on the first sample, inside startup profiling, past the point where the gate could have chosen native. The toolchain is nothing exotic: conda `cuda-nvcc` without `cuda-cudart-dev`, i.e. a compiler with no headers.

So the guard has to cover "compiles" and not just "exists". The change builds the sampling kernel in the gate, cached, and turns a failure into an ordinary unavailability reason:

```python
@functools.cache
def _flashinfer_sampling_build_failure() -> str | None:
```

Nothing is wasted by building there — vLLM JIT-warms this same kernel at startup anyway.

Before / after on that box:

```
before  RuntimeError: Engine core initialization failed
after   WARNING ... unavailable: sampling kernel failed to build (Ninja build failed ...); falling back
        engine up in 31.9s, generates normally
VLLM_USE_FLASHINFER_SAMPLER=1  still raises, with the build error as the reason
tests/v1/sample/test_topk_topp_sampler.py  34 failed / 98 passed / 37.6s, identical to this branch
        without the change, same runtime (those 34 are the same local flashinfer build gap)
```

New test fails without the src change (`AttributeError` on the probe) and passes with it.

Worth noting this is a different failure from #58360, which fixes finding a toolkit that is off PATH or missing `ninja`. Here both are found; the toolkit itself can't compile. The two compose — that one improves detection, this one stops an undetected case from being fatal.
