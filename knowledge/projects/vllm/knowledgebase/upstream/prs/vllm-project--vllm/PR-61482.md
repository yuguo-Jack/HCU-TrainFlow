# [ROCm][Perf][DSv4] Mono decode layer for DeepSeek-V4-Pro on MI355X, on shared mono kernels

[Upstream PR](https://github.com/vllm-project/vllm/pull/61482) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

This PR moves the DeepSeek-V4.1-Flash mono decode kernels of #60397 into a shared package, `vllm/models/common/amd/mono/`, and plugs DeepSeek-V4-Pro into the same kernels at TP8 on MI355X (gfx950). Pro adds no kernel code of its own. It uses a `MonoSpec` (widths, numerics, variant flags) and a `MonoDecode` subclass of about 300 lines. Opt-in with `--monokernel`, as for V4.1.

Related: RFC #60904. #61311 drafts the RFC's runtime layer (`vllm/models/common/mono/`: routing, fail-stop, guards) and leaves the kernel code to each model. This PR covers the other half: one set of FlyDSL kernel stages shared by two models. The two can coexist; see Details.

## Claims

- DeepSeek-V4-Pro, TP8, MI355X, InferenceX AgentX (`inferencex-agentx-mvp`, DSpark with 6 drafts, synthetic acceptance 3.77), mono on vs off:

  | | c1 off → on | c4 off → on | c8 off → on |
  | --- | --- | --- | --- |
  | Interactivity P50 (tok/s/user) | 241 → **299** (+24%) | 218 → **247** (+13%) | 192 → **201** (+5%) |
  | Interactivity P90, InferenceX's slow tail (tok/s/user) | 227 → **278** (+22%) | 169 → **176** (+5%) | 119 → **147** (+23%) |
  | Inter-token latency P50 (ms) | 4.16 → **3.34** (−20%) | 4.59 → **4.04** (−12%) | 5.20 → **4.96** (−5%) |
  | Output throughput (tok/s) | 87.8 → 93.8 | 144 → 194 | 292 → 302 |

  One 900 s run per point. AgentX replays agent sessions closed-loop, so a faster server completes a different mix of turns. Mean inter-token latency and total throughput therefore move with the prompt-length mix and with prefill stalls, not only with decode speed. For example, the c4 mono-on run happened to serve shorter contexts (mean input 136K vs 181K tokens). P90 at c4 / c8 mostly reflects stalls behind other users' long prefills, which run vLLM's own path. The P50 rows are the decode-speed comparison.

- GSM8K at TP8 matches mono off (see Validation).
- V4.1 builds the same kernels as on `main`: 48 of 48 variants are byte-identical, apart from one race fix in the combine stage of index-source layers. That fix was timed and shows no regression.
- One more model of this family needs a spec and a docking class, not a kernel fork. The package README has an "Adding a model" section.

## Details

- **Package layout.** `spec.py` holds `MonoSpec` and `Dims`, a rank's share of every width. `stages/` holds the mHC seam, MoE, router and all-reduce. `attention/` holds the sparse-MLA front and back. `layer.py` and `runner.py` hold the launches and host side. `decode.py` is the vLLM-side base class: deployment checks, step eligibility, record views. A variant is a spec flag read with `const_expr`, so each model's kernels are compiled only from its own flags:
  - `delayed_seam` (V4.1)
  - `q_head_norm`, `preshuffled`, `padded_rows` (Pro)
  - `two_hop_rows`
- **What Pro needs beyond V4.1:**
  - the non-delayed mHC seam (aiter's `mhc_pre` collapse)
  - a weightless per-head q RMSNorm
  - aiter's (16, 16)-preshuffled FP8 weights and `VLLM_ROCM_FP8_PADDING` row strides
  - hash routing for layers 0–2
  - HCA layers, which read every compressed row from vLLM's c128a table
  - 128×128 block scales, expanded exactly to the kernels' 32×32 E8M0 scales
- **HCA key table.** At a 1M context the table is 8192 rows wide. The key table, the split units and the combine stage cover only each token's own keys (`bounded`). Without this, an HCA layer took ~240 µs and mono was 10% slower end to end than mono off.
- **Two-hop all-reduce.** In `stages/allreduce.py`, each rank sends a column to its owner rank. The owner sums the ranks in order and sends the bf16 sum back out. This moves 2/tp of the bytes of the one-hop path and is bit-identical to it. It costs ~10 µs at 7 rows and saves ~20 µs at 56, so Pro enables it from 42 rows.
- **Race fix (V4.1 and Pro).** On index-source layers, K2's combine stage could read a token's key count before the CTA building that key table had published it. Combine now waits on the table's ready flag and reads the count at device scope.
- **Limits:**
  - Pro's compressor and indexer still run as vLLM ops between K1 and K2, serially, where vLLM overlaps them on side streams.
  - At 56 rows a layer is ~3% slower than vLLM in the kernel bench; AgentX c8 still gains.
  - TP8 only for Pro.
- **Relation to #61311 / #60731.**
  - This PR does not touch the runtime layer #61311 proposes. If it lands, `MonoDecode` here can become that PR's per-model glue.
  - #60731 (V4.1 on gfx942) edits the files this PR moves, so whichever lands second needs a rebase. The move is a pure `git mv` plus spec parameterization.
