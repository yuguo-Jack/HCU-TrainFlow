# [Bugfix][Multimodal] Guard GLMGA video sampling against zero source fps

[Upstream PR](https://github.com/vllm-project/vllm/pull/54396) · state: open · merged: False

## Original PR description

## Motivation

`GLMGAVideoBackend.compute_frames_index_to_sample` divides by `source.original_fps` in two places — the duration fallback (`round(max_frame_idx / original_fps) + 1`) and `duration_per_frame = 1 / original_fps` — without validating it. vLLM reports `original_fps == 0` for clips with an unknown or variable frame rate (VFR, malformed containers, failed webcam captures), so those inputs crash with a bare `ZeroDivisionError: float division by zero`.

Every other fps-driven backend in `vllm/multimodal/video.py` already guards this (`Qwen2VLVideoBackend`, `Qwen3VLVideoBackend`, `GLM46VVideoBackend`, and `Molmo2VideoBackend` in fps mode); GLMGA is the remaining one without the check.

## Modifications

- Added the same `original_fps <= 0` guard to `GLMGAVideoBackend`, raising a descriptive `ValueError` that names the backend and the cause, mirroring the existing Qwen2-VL / Qwen3-VL behavior.
- Added a regression test covering both crash paths (duration reported vs. duration missing).

## Verification

- `pytest tests/multimodal/test_video.py::test_glmga_video_backend_rejects_unknown_source_fps` -> 1 passed.
- On unpatched `main`, the same test fails with `ZeroDivisionError: float division by zero` for both `duration=5.0` (at `duration_per_frame = 1 / original_fps`) and `duration=0.0` (at the duration fallback).
- Neighbor sampling tests `pytest tests/multimodal/test_video.py -k glm46v`: 12 passed; the single failure (`test_video_processor_from_model_repo[glm46v]`) is an unrelated missing `av` module in my local environment and fails identically on unpatched `main`.

## Duplicate check

Searched open PRs and issues for `glmga`, `glmga fps`, and `video original_fps`: nothing covers the GLMGA backend. #53844 fixes the same bug class for `Qwen3VLVideoBackend` only and does not touch GLMGA; this PR is scoped to GLMGA so the two can land independently.

- Hotragn · comment · 2026-10-13T07:25:34Z · [source](https://github.com/vllm-project/vllm/pull/54396#issuecomment-6140522925)

The description says GLMGA is the last fps-driven backend without the guard. On current `main` (`4e4eab73ed`) there are two more sites in `vllm/multimodal/video.py` that divide by the source fps:

- **`Glm5NextVideoBackend._sample_frame_indices`, line 951**: `duration_per_frame = 1 / fps`. The duration fallback a few lines above is already guarded (`... if fps else 0`), but this division runs unconditionally. `fps` here is `source.original_fps`, which the OpenCV decoder reports as 0 when the container doesn't know it (`video_decoders/opencv.py:102`). So any GLM-5.3-Flash video like that raises `ZeroDivisionError` from `load_bytes`. The media connector doesn't wrap it, and `create_error_response` only maps `ValueError`/`TypeError`/`OverflowError` to 400, so the client gets a 500. HF's `Glm5NextVideoProcessor.sample_frames` raises `ValueError` when the fps is missing, so the guard you added to GLMGA would give the same behavior here.
- **`Molmo2VideoBackend.compute_frames_index_to_sample`, line 1360**: in the `uniform_last_frame` + `max_fps` branch, `np.arange(..., step=float(video_fps / max_fps))` raises `ZeroDivisionError` when the step is 0.0. This one is narrower. It only runs when an operator sets `frame_sample_mode="uniform_last_frame"`, `max_fps`, and a positive `num_frames` through `--media-io-kwargs`. With the default `frame_sample_mode=None`, every frame is returned without any division. The `fps` branch is covered, as you say, through `get_candidate_target_fps`.

Glm5Next is the same one-line guard as GLMGA, so it seems to belong in this PR. For context, I have #57717 open against `DynamicVideoBackend` in the same file. It's a different backend and a different defect, and I'm not planning a separate PR for either site above.
