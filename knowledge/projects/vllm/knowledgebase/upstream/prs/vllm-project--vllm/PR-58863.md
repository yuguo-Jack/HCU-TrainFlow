# [Spec Decode][Qwen4Exp] RecoverSSM for Qwen GDN and the PLE short conv

[Upstream PR](https://github.com/vllm-project/vllm/pull/58863) · state: open · merged: False

## Original PR description

## Purpose

Speculative decoding on Gated DeltaNet today snapshots the full recurrent state after every draft position, and
reserves one Mamba block per draft position. This PR brings the **RecoverSSM** protocol that Kimi-K3 KDA already uses
to the Qwen GDN layers of Qwen4Exp (Qwen3.8-Flash-Next), plus its PLE dilated short conv:

- **Verify** runs from a read-only checkpoint and stores a small per-token replay record
  `[correction (V), normalized key (K), gate (1)]` in fp32.
- **Commit** (after sampling) replays only the accepted tokens and writes the recurrent state once, plus the
  block-boundary state in align mode. The PLE short conv compacts its accepted window with the same plan.
- `num_speculative_blocks = 0`: no per-draft Mamba blocks.

Enabled like KDA's: `--use-replayssm` together with speculative decoding. Qwen4Exp (CausalLM, ConditionalGeneration,
MTP) declares `SupportsReplaySSM`; without spec decoding the flag is rejected on Qwen4Exp (there is no plain ReplaySSM
path for its GDN/PLE layers). Requires the V2 model runner for align mode, the Triton mamba backend and PP=1 (the same
checks as KDA). The GDN and PLE RecoverSSM builders declare `AttentionCGSupport.UNIFORM_BATCH`, so the default
`FULL_AND_PIECEWISE` captures FULL graphs for uniform spec-decode batches (and PIECEWISE for mixed ones). Graph padding
rows get a null state slot and a zero-length window, so the verify writes nothing for them. With breakable CUDA graphs
(auto-enabled on this setup; they split at attention with an empty `splitting_ops`) a PIECEWISE fallback used to drop
to NONE; it now resolves to PIECEWISE there.

Note: under FULL decode graphs `resolve_cudagraph_mode_and_sizes` requires `max_num_seqs <= num_blocks`. The replay
record makes the unified page about 6 % larger, so a pool that just fits the default `max_num_seqs` under native MTP
can fall short with `--use-replayssm` (seen on one H200 at TP1, 983 Mamba blocks); lower `--max-num-seqs` there.

The larger page also widens the attention block that hybrid models align to the Mamba page (Qwen3.8-Flash-Next on
one GB10: 1,600 → 1,664 tokens). Prefix reuse counts whole blocks, so a repeated prompt can reuse up to one block
less (a 9,698-token repeat reused 6,656 instead of 8,000 tokens in @k3dani's run); long repeats are unaffected.
The decode gain comes from dropping the per-draft state write-back, so it grows with the draft length: measured at
MTP K=3 and K=5 here; at K=2 with PIECEWISE graphs @k3dani measured c=1 decode 1.9–4 % slower.

Commits:
1. `[Mamba] Share RecoverSSM commit kernels and helpers across models`: the commit-plan and conv-compaction kernels
   move from `models/kimi_k3` to `model_executor/layers/mamba/ops/recoverssm.py` (Kimi keeps its private names as
   aliases; kernel source unchanged); `mamba/recoverssm_utils.py`; generic request-mapping helpers in
   `v1/attention/backends/recoverssm_metadata.py`; `CacheConfig.use_kda_recoverssm` → `use_recoverssm`. No functional
   change for Kimi-K3.
2. `[Spec Decode][Qwen4Exp] RecoverSSM for Qwen GDN and the PLE short conv`: GDN verify/commit kernels
   (`mamba/gdn/recoverssm_gdn.py`), metadata builders (`gdn_recoverssm.py`, `ple_recoverssm.py`), the layer and model
   integration. The verify reads strided q/k/v views of the conv output and writes straight into the layer output.
   The generic Mamba metadata builder no longer allocates the Mamba2 ReplaySSM ring-buffer workspaces when
   `--use-replayssm` selects RecoverSSM (the PLE short conv uses that builder).
3. `[Mamba] RecoverSSM align: keep a boundary-ending state in its block`: a window whose accepted tokens end exactly on
   a block boundary commits into the block holding its last token (`(n - 1) // block`), not the next, possibly
   unallocated column.
4. Three fixes by @lucifer1004 (jschmied/vllm#2): release the recorded RecoverSSM step in `_teardown_profiling_state`
   (its commit contexts kept the profiling KV cache alive; ~26 GiB on H200 and a startup OOM); read the RecoverSSM flag
   with `getattr` in `_forward_core`; one fold per program in the align-mode commit (290 → 197 µs on H200).
5. `[Spec Decode][Qwen4Exp] RecoverSSM: FULL cudagraphs for uniform spec-decode batches` (above).
6. `[Bugfix][Mamba] RecoverSSM align commit: fold final states before boundary states`: the split commit ran both folds
   in one launch, and a boundary state can land in the window's source slot, so a program could read a source tile
   another had overwritten. Final folds now run first, boundary folds second (skipping windows whose boundary slot is
   their final slot).

Related: #49887 and #56466 (ReplaySSM for GDN) take the ring-buffer route; this PR reuses the merged RecoverSSM
protocol instead (discussed in https://github.com/vllm-project/vllm/pull/56466#issuecomment-5845393579).

## Fused CUDA verify

The PW column's low-concurrency loss comes from two changes that we did not measure separately:
- PIECEWISE graphs.
- The fused CUDA MTP kernel is dropped. `--use-replayssm` forces `gdn_decode_kernel = "triton"`, so spec batches leave `fused_gdn_decode_post_conv_mtp`, which fuses the recurrence, gated RMSNorm and output gate, for the Triton verify plus a separate norm.

We added a replay mode to that CUDA kernel. The window starts from the read-only checkpoint in `state_indices[:, 0]` and writes this PR's replay record `[correction, normalized key, log decay]` instead of per-token states. Everything else is unchanged:
- the existing commit folds the records;
- the outputs are bit-identical to the snapshot mode;
- padding rows write nothing.

Pure spec-decode batches take it, and mixed batches keep the Triton verify. At C8 on H200 the verify drops from 36.9 µs to 21.3 µs per layer, because the per-token state writes disappear.

It builds on this PR's record layout and commit, so we plan to open it as a follow-up once this lands. Happy to share it earlier if that helps review.

On XPU, the 28 tests that compare the RecoverSSM commit with the native per-token states bit for bit fail (I mentioned them in #61017). I tracked them down. The two kernels round in different orders on XPU. Neither one is wrong.

`fused_sigmoid_gating_delta_rule_update_kernel` does `b_h *= exp(g); b_h += b_v[:, None] * b_k[None, :]`, and Triton contracts it into an FMA implicitly. The two backends pick different products:

| | native state (the compiler contracts it) | commit (already writes `tl.fma` out) |
|---|---|---|
| CUDA (RTX 2080, sm_75) | `fma(corr, k, round(h·decay))` | `fma(corr, k, round(h·decay))` |
| XPU (Arc Pro B70) | `fma(h, decay, round(corr·k))` | `fma(corr, k, round(h·decay))` |

How I checked: I had the native kernel write out the corr, k and decay it used, on both devices. They are bit-identical to what the verify kernel stores in the replay record. Rebuilding the first-token state from those values on the CPU, only one order matches the native state on each device (above). On XPU that is `fma(h, decay, round(corr·k))` (0 of 786,432 elements differ in each of the 3 requests; the commit's order differs in ~33%). The differences are about 1 ULP per update (median): ~33% of the state elements differ after one token, ~44% after four, at most 9e-8 absolute (states up to ~0.9). Against an fp64 reference the two have comparable error (max 1.2e-7 for both; mean 3.8e-9 native, 3.8e-9 commit).

The commit already writes the FMA out. Writing it out the same way in the native kernel, and in the verify kernel (which rebuilds the state for its output), pins the order everywhere:

```diff
# vllm/third_party/flash_linear_attention/ops/fused_sigmoid_gating.py
-        b_h += b_v[:, None] * b_k[None, :]
+        b_h = tl.fma(b_v[:, None], b_k[None, :], b_h)
# vllm/model_executor/layers/mamba/gdn/recoverssm_gdn.py (verify)
-        new_state = new_state + corr[:, None] * k[None, :]
+        new_state = tl.fma(corr[:, None], k[None, :], new_state)
```

Root cause found since the report above — the in-page replay-record suspect is
ruled out, and the first-re-send miss turns out to be a mainline coordinator
interaction that RecoverSSM's geometry triggers. Posting in case it saves the
authors some digging; happy to test any fix variant on our rig.

## What we ruled out first: publishing and retention are correct

We instrumented serving runs with per-group prefix-cache dumps at request
finish and at lookup (per-group hit lengths from the coordinator, per-group
cached-hash sets from the block pool). After the first (cold) send finishes,
each Mamba group holds **exactly two** cached states — the sparse-retention
replay-boundary set, nothing missing:

- Mamba groups (block 1792, spec_blks=0): `{23,296, 25,096}` — 23,296 =
  13×1792 is the `replay_boundaries` position (`(num_prompt−1)//block×block −
  block`), 25,096 is the prompt-end partial tail.
- The eagle ring (MLA-spec group at hash-block 8): 15 hashes, tail
  `{23,296, 25,088, 25,104}`.

The RecoverSSM worker code never touches the cache tables (no registration,
eviction, or free calls into the pool/managers). So the states exist and are
published; the miss happens at **lookup**.

## The collapse: the fixed point undercuts its own boundary state

Per-group hits for the first re-send, traced per iteration of
`HybridKVCacheCoordinator.find_longest_cache_hit` (our trace of the live
server; prompt 25,102, `max_cache_hit_length` 25,101):

```
FP idx=0 spec=MLAAttentionSpec gid=5 max_len=25096 -> hit=23288 drop=True
FP idx=1 spec=MambaSpec       gid=0 max_len=23288 -> hit=0
FP idx=2 spec=MambaSpec       gid=3 max_len=23288 -> hit=0
FP FINAL max_in=25101 hit=0 unc=23288
```

1. The eagle group matches its boundary-region hash at 23,296 and, per the
   eagle drop, lands at **23,288** — one hash unit **below** the Mamba
   boundary state (23,296).
2. The fixed point re-runs the Mamba finders at the reduced candidate
   23,288. Sparse retention retained nothing at or below 23,288, so Mamba
   collapses from 23,296 to **0**, and the reconciled hit is 0
   (`unc=23,288` is the longest single-group hit). Full cold re-prefill.

The crux is the re-evaluation after an eagle group shrinks the candidate. The
eagle-margin branch in the loop (`if drop_eagle_block and not
isinstance(spec, MambaSpec)`) gives non-Mamba groups a match-and-land-back
unit, with the inline comment "No margin for mamba: its finder never drops …
so the hit would grow past the candidate." That reasoning holds on the first
pass, but on re-evaluation the Mamba state the eagle group just matched (the
shared boundary state) sits exactly one drop unit **above** the new candidate
— the finder needs the same treatment to keep it.

## Why sends 3+ recover (and why the steady state is 23,288)

The cold re-send is scheduled with `shared_prefix_boundary = hit + unc =
23,288` pinned, and with the shared-prefix checkpoint enabled its prefill
stops there and registers the Mamba state at 23,288 — the eagle-landing
position. From the third send on, the fixed point resolves at 23,288 (the
measured steady state). The system converges after exactly one wasted cold
prefill; the first producer just doesn't retain the landing position.

## Why our non-RecoverSSM run didn't collapse

Same instrumented run, RecoverSSM off: the eagle group's dropped hit (24,712)
sits **above** the Mamba boundary (23,072 = 14×1648), so the re-evaluation
still finds the boundary state and the reconciled hit is 23,072 — the clean
send-2 hit in the table above. In the RecoverSSM run the eagle's dropped hit
(23,288) landed **below** the Mamba boundary (23,296) — the collapse
precondition. The eagle ring is dense (every block boundary plus the prompt
tail), so which hash it matches is set by where the sibling prompts diverge
relative to the resend boundary, not by block size alone: a non-RecoverSSM
sibling pair diverging at or below its resend boundary would collapse
identically. We have not tested other models; the mechanism lives in
mainline coordinator code, so any eagle + sparse-retention hybrid where the
dropped hit undercuts the retained boundary is susceptible.

## Fix direction (not yet implemented — offered for discussion)

The direction we'd pursue: make the first producer retain the eagle-landing
position, the same thing the shared-prefix checkpoint already does for send
3+. Two pieces are required, because the landing position is sub-block
(23,288 is one hash unit below the block-aligned boundary 23,296):

- the sparse-retention reachable set gains the eagle-landing position
  (`boundary − hash_block_size` under eagle), and
- the partial-checkpoint registration gate accepts that position for the
  producer's own prompt end (the retention mask operates in block units, so
  the mask alone cannot retain a sub-block state — the gate that registers
  the junction state for send 3+ is the mechanism that can).

That should make the first re-send hit 23,288 directly, matching the steady
state. We deliberately did not pursue margin-style fixes on the lookup side:
an SSM state ending at 23,296 cannot serve a resume at 23,288 (the rolling
state would double-count tokens 23,288–23,295), and growing the hit past the
candidate would break the fixed point's convergence contract — the "No
margin for mamba" caveat is right about that, even though it misses the
retention-side gap.

- michael-gpu · comment · 2026-10-28T22:02:54Z · [source](https://github.com/vllm-project/vllm/pull/58863#issuecomment-6481796733)

**K=0 throughput regression: draft-less decode rows forced onto the spec path — root cause, fix, scope**

Second independent finding from our serving validation of this PR (internal
nightly ported at 3694757f; the prefix-cache findings and fix above are
separate). This one is pure throughput, it is in this PR's own row
classification, and it has a small fix with profiled proof.

**Mechanism.** `recoverssm_spec_rows` puts every active decode row on the
spec path — the `>= 0` predicate is aligned with the runner's deliberate
zero-draft marking ("some recurrent backends may read the previous step's
state at an offset that only the speculative path applies",
gpu_model_runner.py:2216-2227). Under a batch-size ladder like
`[[1,8,2],[9,16,1],[17,32,0]]`, the >16 tier schedules decode rows with no
drafts. For those rows the window is T=1 and always accepted, and the
post-sampling commit fold of one token is bit-for-bit the in-place update
the regular decode kernel writes directly — the detour buys nothing and
costs, per step at c32:

- the verify premium: **+74% per call** vs the regular decode kernel,
- a **2.13 ms/step** out-of-graph state commit (**3.62 GB/step** at ~1.7
  TB/s effective — bandwidth-optimal, pure overhead),
- **~1.75 ms/step** of CPU commit staging.

House bench (c32, warm prefix, qwen3.8-flash-next TP1): **1006-1047 tok/s**
with RecoverSSM vs **1202-1300 control** — −15-18%, enough to make
RecoverSSM unshippable at the concurrency our interactive traffic lives at,
despite the design's real memory win on our side (the one-slot state model
frees the 2 spec blocks per mamba group: **+2.3% KV pool** at fixed pin).

**How this fits the thread's numbers.** lucifer1004's MTP3 table shows
RecoverSSM losing at low concurrency (PW arm −4% to −41% at C1-C16) and
winning at high concurrency (+12-17% at C32-64, pool-driven — preemptions
188→0 at C64). Our finding is a third cost that only appears where the
scheduler's batch-size ladder disables drafts: the no-draft tier was forced
onto the spec path and paid the verify premium plus the commit for zero
benefit. Shapes that keep drafts on at every concurrency never enter that
tier.

**Fix** — classify spec rows by real draft presence:

```diff
--- a/vllm/v1/attention/backends/recoverssm_metadata.py
+++ b/vllm/v1/attention/backends/recoverssm_metadata.py
@@ -35,14 +35,18 @@ def recoverssm_spec_rows(
-    query_lens = query_start_loc_cpu[: num_reqs + 1].diff()
-    active_decode = (~is_prefilling_cpu[:num_reqs]) & (query_lens > 0)
-    spec_mask = (num_decode_draft_tokens_cpu[:num_reqs] >= 0) | active_decode
+    draft_counts = num_decode_draft_tokens_cpu[:num_reqs]
+    spec_mask = (draft_counts > 0) & ~is_prefilling_cpu[:num_reqs]
```

plus small staging updates in the GDN (13 lines) and PLE (4 lines) builders:
draft-less rows fall through to the base builders' regular in-place decode,
and capture dummies classify faithfully so each graph matches the runtime
tier that replays it. K>=1 tiers keep the full RecoverSSM machinery;
transitions are free — `num_speculative_blocks=0` means the checkpoint
column IS the block-table-addressed running slot, and replay records are one
window deep, consumed only by the same step's commit.

**Profiled proof** (torch profile of a c32 wave, before → after):
`_commit_gdn_state_kernel` **362.9 → 5.4 ms** (−98%);
`_gdn_recoverssm_verify_kernel` **437.7 → 7.1 ms** (−95%); the residual
verify calls are exactly the drain-tail K>=1 steps (27×12=324). Bench:
broken 1046.9/1006.8 → fixed **1189.3/1251.4/1149.0** (mean 1197) vs control
mean 1244 — parity within run-to-run noise. Greedy canary coherent both arms
(20 vs 21 unique completions from 32 identical prompts — different regular
kernels, last-ulp argmax variance). Regression tests: 6 cases in
`tests/v1/attention/test_recoverssm_spec_rows.py`.

**Scope — what we validated, and what we checked before claiming.**
End-to-end: Qwen GDN + PLE only. The runner's offset warning is a real
hazard for recurrent backends, so we did not assume the routing generalizes
— we checked the second family that ships its own RecoverSSM path:

- **KDA (Kimi-K3)**: at the kernel/state layer the same routing is safe.
  KDA's verify+commit fold writes the same recurrent state
  `fused_recurrent_kda` writes in-place: within **one bf16 ulp** for bf16
  state (1-2 fp32 ulps from rsqrt vs 1/sqrt in the k-normalization; bf16
  rounding absorbs them except rare rounding-boundary elements — measured
  0-8 of 65,536 per case), <=2 fp32 ulps for fp32 state, attention outputs
  within the same bound. Test: 8 cases (T=1 draft-less window = the K=0
  shape, T=4 full-window fold, both gate forms, both dtypes, torch reference
  guard, non-zero pool slot so wrong-offset state reads fail) — happy to
  attach the file.
- **K3's builder** (`kimi_k3/nvidia/kda_metadata.py`) classifies with the
  same `>= 0` shape, so K3 pays the same K=0 tax today — but its builder
  staging port is not done, and we are not claiming it.
- **GLM (#61566)**: separate PR, untested here. **DeepSeek**: no RecoverSSM
  family relationship (no references in the model trees).

**The K>=1 cost is design-space, not inherent.** The thread has already
measured it from the other side — lucifer1004's nsys at C8 put pure-decode
steps 0.3 ms above native, decomposed as "verify −0.56 ms, commit +0.82
ms", and their FULL-graph arm's remaining −1-2% at C4-C16 is this tax. Our
profiled attribution agrees and extends it: at c16/K=1, +1.3 ms/step GPU
(verify 1.39 + commit 1.17 vs control gdn_mtp 1.33) + ~0.5 ms exposed CPU;
at c4/K=2 it is ~all launch overhead (~10 extra launches + Python per
step). #59366's fused CUDA verify attacks the verify side; the commit
remains. The direction we would take for the commit: **deferred-write** —
pre-fold the previous window's records in-register (acceptance is known by
then), store the running state mid-kernel, records stay one window deep;
commit/prepare_commit_plan/boundary folds leave the critical path; state
traffic 3.15 vs 4.65 MiB/layer-row. It composes with the K=0 fix unchanged,
is complementary to #62625 (which relocates the record buffer) and adjacent
to #61017/#56082 (commit launch overhead). Happy to write it up as a
follow-up.
