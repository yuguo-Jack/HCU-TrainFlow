# [Spec Decode][Qwen4Exp] RecoverSSM for Qwen GDN and the PLE short conv

[Upstream PR](https://github.com/vllm-project/vllm/pull/58863) · state: open · merged: False

## Original PR description

## Purpose

Speculative decoding on Gated DeltaNet today snapshots the full recurrent state after every draft position, and
reserves one Mamba block per draft position. This PR brings the **RecoverSSM** protocol that Kimi-K3 KDA already uses
to the Qwen GDN layers of Qwen4Exp (Qwen3.8-Flash-Next), plus its PLE dilated short conv:

- **Verify** runs from a read-only checkpoint and stores a small per-token replay record
  `[correction (V), normalized key (K), gate (1)]` in fp32.
- **Commit** (after sampling) replays only the accepted tokens and writes the recurrent state once, plus the
  block-boundary state in align mode. The PLE short conv compacts its accepted window with the same plan.
- `num_speculative_blocks = 0`: no per-draft Mamba blocks.

Enabled like KDA's: `--use-replayssm` together with speculative decoding. Qwen4Exp (CausalLM, ConditionalGeneration,
MTP) declares `SupportsReplaySSM`; without spec decoding the flag is rejected on Qwen4Exp (there is no plain ReplaySSM
path for its GDN/PLE layers). Requires the V2 model runner for align mode, the Triton mamba backend and PP=1 (the same
checks as KDA). The GDN and PLE RecoverSSM builders declare `AttentionCGSupport.UNIFORM_BATCH`, so the default
`FULL_AND_PIECEWISE` captures FULL graphs for uniform spec-decode batches (and PIECEWISE for mixed ones). Graph padding
rows get a null state slot and a zero-length window, so the verify writes nothing for them. With breakable CUDA graphs
(auto-enabled on this setup; they split at attention with an empty `splitting_ops`) a PIECEWISE fallback used to drop
to NONE; it now resolves to PIECEWISE there.

Note: under FULL decode graphs `resolve_cudagraph_mode_and_sizes` requires `max_num_seqs <= num_blocks`. The replay
record makes the unified page about 6 % larger, so a pool that just fits the default `max_num_seqs` under native MTP
can fall short with `--use-replayssm` (seen on one H200 at TP1, 983 Mamba blocks); lower `--max-num-seqs` there.

The larger page also widens the attention block that hybrid models align to the Mamba page (Qwen3.8-Flash-Next on
one GB10: 1,600 → 1,664 tokens). Prefix reuse counts whole blocks, so a repeated prompt can reuse up to one block
less (a 9,698-token repeat reused 6,656 instead of 8,000 tokens in @k3dani's run); long repeats are unaffected.
The decode gain comes from dropping the per-draft state write-back, so it grows with the draft length: measured at
MTP K=3 and K=5 here; at K=2 with PIECEWISE graphs @k3dani measured c=1 decode 1.9–4 % slower.

Commits:
1. `[Mamba] Share RecoverSSM commit kernels and helpers across models`: the commit-plan and conv-compaction kernels
   move from `models/kimi_k3` to `model_executor/layers/mamba/ops/recoverssm.py` (Kimi keeps its private names as
   aliases; kernel source unchanged); `mamba/recoverssm_utils.py`; generic request-mapping helpers in
   `v1/attention/backends/recoverssm_metadata.py`; `CacheConfig.use_kda_recoverssm` → `use_recoverssm`. No functional
   change for Kimi-K3.
2. `[Spec Decode][Qwen4Exp] RecoverSSM for Qwen GDN and the PLE short conv`: GDN verify/commit kernels
   (`mamba/gdn/recoverssm_gdn.py`), metadata builders (`gdn_recoverssm.py`, `ple_recoverssm.py`), the layer and model
   integration. The verify reads strided q/k/v views of the conv output and writes straight into the layer output.
   The generic Mamba metadata builder no longer allocates the Mamba2 ReplaySSM ring-buffer workspaces when
   `--use-replayssm` selects RecoverSSM (the PLE short conv uses that builder).
3. `[Mamba] RecoverSSM align: keep a boundary-ending state in its block`: a window whose accepted tokens end exactly on
   a block boundary commits into the block holding its last token (`(n - 1) // block`), not the next, possibly
   unallocated column.
4. Three fixes by @lucifer1004 (jschmied/vllm#2): release the recorded RecoverSSM step in `_teardown_profiling_state`
   (its commit contexts kept the profiling KV cache alive; ~26 GiB on H200 and a startup OOM); read the RecoverSSM flag
   with `getattr` in `_forward_core`; one fold per program in the align-mode commit (290 → 197 µs on H200).
5. `[Spec Decode][Qwen4Exp] RecoverSSM: FULL cudagraphs for uniform spec-decode batches` (above).
6. `[Bugfix][Mamba] RecoverSSM align commit: fold final states before boundary states`: the split commit ran both folds
   in one launch, and a boundary state can land in the window's source slot, so a program could read a source tile
   another had overwritten. Final folds now run first, boundary folds second (skipping windows whose boundary slot is
   their final slot).

Related: #49887 and #56466 (ReplaySSM for GDN) take the ring-buffer route; this PR reuses the merged RecoverSSM
protocol instead (discussed in https://github.com/vllm-project/vllm/pull/56466#issuecomment-5845393579).

## Fused CUDA verify

The PW column's low-concurrency loss comes from two changes that we did not measure separately:
- PIECEWISE graphs.
- The fused CUDA MTP kernel is dropped. `--use-replayssm` forces `gdn_decode_kernel = "triton"`, so spec batches leave `fused_gdn_decode_post_conv_mtp`, which fuses the recurrence, gated RMSNorm and output gate, for the Triton verify plus a separate norm.

We added a replay mode to that CUDA kernel. The window starts from the read-only checkpoint in `state_indices[:, 0]` and writes this PR's replay record `[correction, normalized key, log decay]` instead of per-token states. Everything else is unchanged:
- the existing commit folds the records;
- the outputs are bit-identical to the snapshot mode;
- padding rows write nothing.

Pure spec-decode batches take it, and mixed batches keep the Triton verify. At C8 on H200 the verify drops from 36.9 µs to 21.3 µs per layer, because the per-token state writes disappear.

It builds on this PR's record layout and commit, so we plan to open it as a follow-up once this lands. Happy to share it earlier if that helps review.

| 3 (mean of 3 runs) | 2607 | 2871 | **+10.1%** (runs: +16 / +5 / +9%) |
| 5 (mean of 3 runs) | 2529 | 2723 | **+7.6%** (runs: +10 / +9 / +4%) |
| 7 (1 run) | 2436 | 2693 | +11% |
| 1 (1 run) | 2062 | 2010 | −3% |

At c=1 the two are within ±1% for every K. At c=8 we measured K=3 +8%, K=5 +2%, K=7 +3% (single runs).

Accept length is unchanged in every run (e.g. K=5: 3.941 vs 3.939; per-position .856/.694/.558/.457/.376 vs .856/.693/.558/.456/.375).

The gain grows with batch size and K. At c=1, and at K=1, the commit's fixed cost cancels the saving, which matches the K=2 / c=1 slowdown you mention. It may be worth noting in the docs that RecoverSSM pays off at K ≥ 3 under load.

**Correctness.** Outputs aren't bit-identical to the stock kernels, as expected when float math is reordered. We checked with greedy decoding + top-5 logprobs:
- Every first divergence is at a near-tie: the stock run's top-1 − top-2 gap there is ≤ 0.875 nats (median 0.25), versus a median of ~11 over all positions.
- This also holds when a follow-up turn's prefix hits blocks whose boundary state was written by the commit during decode.

**Observation: record in the page vs. prefix reuse.** You note the record makes the Mamba page larger, which widens the attention block. In our setup it grew the block from 576 to 656 tokens. On a workload where requests share a ~1.9k-token system prompt ending mid-block, shared-prefix hits land on block multiples:
- Every request reused 1,312 tokens (2 × 656) instead of 1,728 (3 × 576).
- On a sequential probe of 40 requests, the prefix hit rate dropped from 0.489 to 0.381.

The record only lives from a step's verify to the same step's commit, so we moved it out of the KV pool into a per-layer buffer (`[max_num_seqs, HV, K+1, V]` fp32 correction + `[max_num_seqs, HV, K+1, K+1]` key/gate). The Mamba page is then the native size, and the block and hit rate match stock. Our prototype indexes rows by spec-decode position, which isn't safe once PP keeps several steps in flight (#59983); an upstream version would key on the request-state slot.

1. Declare `SupportsReplaySSM` for Qwen3.5 / Qwen3-Next (+ MTP), with tests on the public checkpoint.
2. Keep the replay record out of the Mamba page (request-slot indexed).

Happy to open these once this lands, or adjust if you'd rather fold either into this PR. Does that direction sound OK?
