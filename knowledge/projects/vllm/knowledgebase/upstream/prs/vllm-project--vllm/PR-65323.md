# [XPU][UT] Preserve RoPE buffer dtype for HF reference in the privacy-filter model test on XPU

[Upstream PR](https://github.com/vllm-project/vllm/pull/65323) · state: open · merged: False

## Original PR description

## Overview

Fix the privacy-filter token-classification test on XPU by preserving the HFrunner model’s original FP32 RoPE frequency buffers (eg, inv_freq) instead of downcasting them to BF16. This change aligns the buffer dtype of hfrunner with vllmrunner.

Following [#64705](https://github.com/vllm-project/vllm/pull/64705), this PR triaged the root cause and resolved it.

## Claims

-  The ROPE buffer dtype of `hfrunner` and `vllmrunner` are bf16 and fp32, respectively. This leads to numerical diff during model inference and make this ut fail with the fifth prompt on XPU.
- This PR preserves the buffer dtype as fp32 only for this case and only on XPU.
- On Cuda, the fifth prompt (the one failed on XPU) also shows larger output diff with RoPE buffer downcasting (0.0508 with bf16, 0.0354 with fp32). This diff still remains within the tolerance so the ut passed on cuda.

## Details

### Some references
- HfRunner’s whole-model BF16 conversion also downcasts the inv_freq buffer to BF16: [tests/conftest.py#L531-L535](https://github.com/vllm-project/vllm/blob/cd1effa2e7d204b22527f14739734751f38ed737/tests/conftest.py#L531-L535).

- vLLM explicitly initializes RoPE with FP32, computes inv_freq in FP32, and uses it to generate the cos/sin cache: [gpt_oss.py#L111-L117](https://github.com/vllm-project/vllm/blob/cd1effa2e7d204b22527f14739734751f38ed737/vllm/model_executor/models/gpt_oss.py#L111-L117) → [yarn_scaling_rope.py#L51-L74](https://github.com/vllm-project/vllm/blob/cd1effa2e7d204b22527f14739734751f38ed737/vllm/model_executor/layers/rotary_embedding/yarn_scaling_rope.py#L51-L74) → [yarn_scaling_rope.py#L81](https://github.com/vllm-project/vllm/blob/cd1effa2e7d204b22527f14739734751f38ed737/vllm/model_executor/layers/rotary_embedding/yarn_scaling_rope.py#L81).

### More exp on XPU about inv_freq bf16 vs fp32
- Frequency precision: Downcasting changes 31 of the 32 frequencies. eg, 0.6890442967414856 (FP32) -> 0.6875 (BF16).
- First-layer attention output: 3/7 prompts fail assert_close(atol=0.1, rtol=0.01).
