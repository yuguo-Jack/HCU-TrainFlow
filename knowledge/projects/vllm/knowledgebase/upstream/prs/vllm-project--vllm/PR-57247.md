# [Bugfix][Parser] Preserve Gemma4 content when reasoning parsing is disabled

[Upstream PR](https://github.com/vllm-project/vllm/pull/57247) · state: open · merged: False

## Original PR description

## Summary

- Prevent Gemma4 from injecting a synthetic `<|channel>` marker when reasoning parsing is disabled.
- Prevent stripped Gemma4 reasoning markers from being restored from token IDs at stream completion.
- Add regression coverage for visible and stripped marker variants in direct streaming and serving parser paths.

## Root cause

When no reasoning parser is configured, the Gemma4 tool parser is instructed to skip reasoning parsing. The parser still ran its first-feed channel-opener injection and its pending-token flush path, causing channel markers to leak into user-visible content. The fix makes the skip-reasoning path preserve markers that are actually visible in decoded text while discarding marker IDs whose text was removed by special-token skipping, and bypasses synthetic opener injection.

## Scope and duplicate-work check

- Rechecked issues #57231 and #57232, their comments, and related open PRs.
- PR #57255 addresses the generic engine-level scanner behavior for stripped special-token terminals. This PR covers the Gemma4-specific first-feed injection and retains a local marker-ID safeguard for Gemma4; the changes are complementary rather than identical.
- Existing PR #57089 addresses the separate aborted-stream behavior from #57082.

```
row 22  no tools, first two steps merged
        '<|channel>thought\nwork it out: 17*23the answer is 391<|channel><channel|>'  ->  'thought\nwork it out: 17*23the answer is 391'
```

Row 22 is the text-only guard case from #57231. With the opener's text stripped, the first feed is `('thought', [100, 45518])`. It's fixed here because the new filter drops id 100 before the first-feed check, so the guard at `gemma4.py:463` (@ base) never has to see it.

Three things I'd raise:

1. **The tests don't cover per-token delivery.** Both cases pass the whole sequence as one delta. Under default streaming (`stream_interval=1`), `thought` arrives alone in the first delta and hits the `delta_text == "thought"` trigger (row 10 above). The plain-markup case starts with `thought\n` and contains `<channel|>`, so it hits the other two triggers instead. Likewise, the stripped-markup case never has a marker id arriving in an empty-text delta like `('', [101])`, which is the shape the scanner defers in #57232. The fix handles both (rows 10, 15 and 19); the tests just don't pin them. Running the tests both ways (the whole sequence as one delta, and one token per delta) would.
2. **The tests skip the serving construction path.** They build `Gemma4Parser` directly and set `skip_reasoning_parsing` by hand, so neither the `DelegatingParser` opt-in nor non-streaming `parse()` (rows 1 and 5) is covered. Building through `ParserManager.get_parser(tool_parser_name="gemma4", enable_auto_tools=True)` covers both.
3. **The fix's scope.** `_preprocess_feed` is a base-class hook (`parser_engine.py:226` @ `0983aef8da`, called once at `:238`), and gemma4 is currently its only override. This PR makes gemma4 skip injection when the flag is set, but the bypass itself still doesn't account for tokens a hook injects, so a future override would reintroduce #57231. Whether that belongs here or in a follow-up is a maintainer call. Separately, the stripped-marker half overlaps #57255, which fixes rows 15 and 19 at the scanner level for every engine parser and doesn't touch the injection rows. If #57255 lands, the id-filter block here may be redundant for gemma4, and this PR could be `Fixes #57231` alone.

Happy to share the head and base run outputs.
