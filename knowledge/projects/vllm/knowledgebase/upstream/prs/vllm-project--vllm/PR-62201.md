# [Model] Add native support for Lfm2BidirectionalModel

[Upstream PR](https://github.com/vllm-project/vllm/pull/62201) · state: closed · merged: True

## Original PR description



## Overview

Add initial PyTorch-native support for [Lfm2BidirectionalModel](https://huggingface.co/LiquidAI/LFM2.5-Embedding-350M) with minimal changes to the existing LFM2 implementation. 

Implement noncausal short conv over packed sequences, with request-boundary and padding
masking, encoder-only attention, and CLS pooling.

File: `vllm/model_executor/models/lfm2.py` · line 329

🔴 With `VLLM_MOE_SKIP_PADDING=0` on the default V2 runner, LFM2.5 embeddings become batch-dependent: the conv mixes neighbouring requests and padding rows. The new conv reads `forward_context.is_padding` with no gate. Model Runner V2 only refreshes that mask when `VLLM_MOE_SKIP_PADDING` is set (gpu/model_runner.py:1378). Otherwise it holds the all-True fill left by CUDA graph capture. Fix: always pass an accurate real-token mask to this conv, whatever MoE env vars are set. For example, fill `is_padding` unconditionally in V2 `prepare_inputs`, or derive the real-token count from the forward context. Every other reader of the mask gates on that env var.

<details>
<summary>Why this was flagged</summary>

The trigger is an operator who sets `VLLM_MOE_SKIP_PADDING=0` while serving `Lfm2BidirectionalModel` on Model Runner V2. In V2, `prepare_inputs` (v1/worker/gpu/model_runner.py:1377-1380) fills `input_buffers.is_padding` only under that env var. It still passes the buffer to `set_forward_context(is_padding=input_batch.is_padding)` (model_runner.py:2042). CUDA graph capture runs `input_buffers.is_padding.fill_(True)` on the whole buffer (gpu/cudagraph_utils.py:720,747). As a result, every real token reaches `_bidirectional_conv1d` marked as padding. At lfm2.py:267 all sequence ids then become -2, so the `same_sequence` mask never separates requests. On the base branch nothing in this model reads `is_padding`. Every existing consumer gates on `envs.VLLM_MOE_SKIP_PADDING`. The new test only runs with the default value of 1.

**Verification:** `prepare_inputs` refreshes the mask only under that env var (vllm/v1/worker/gpu/model_runner.py:1377-1380). CUDA graph capture runs `input_buffers.is_padding.fill_(True)` (cudagraph_utils.py:720, 747). The new code reads that mask with no gate. The new batch-invariance test does not catch this because it runs with the default env.

</details>

- claude[bot] · comment · 2026-10-23T16:01:50Z · [source](https://github.com/vllm-project/vllm/pull/62201#discussion_r4361552953)

File: `vllm/model_executor/models/lfm2.py` · line 517

🟡 (optional) Users of the new LFM2.5 embedding model only get the "embed" task. Per-token embeddings ("token_embed") are rejected, unlike other embedding models such as BERT, CLIP and SigLIP. `pooler_for_embed` builds a bare `SequencePooler` whose `EmbeddingPoolerHead` supports only {"embed"}. Fix: build the pooler with `DispatchPooler.for_embedding(pooler_config)`, the same way `bert.py:525`, `clip.py:836` and `siglip.py:946` do, so both "embed" and "token_embed" are available.

<details>
<summary>Why this was flagged</summary>

`Lfm2BidirectionalModel.__init__` (lfm2.py:504) sets `self.pooler = pooler_for_embed(pooler_config)`. `pooler_for_embed` (pooler/seqwise/poolers.py:97) returns a `SequencePooler` with an `EmbeddingPoolerHead`. That head's `get_supported_tasks` (seqwise/heads.py:56-57) returns only {"embed"}, and `SequencePooler.get_supported_tasks` (poolers.py:69-74) intersects with it. So a request through `LLM.encode(..., pooling_task="token_embed")`, or the token-embedding pooling API, is rejected as an unsupported task for this model. Every other dense embedding model in the tree builds its pooler with `DispatchPooler.for_embedding` (special.py:29-35), which serves both "token_embed" and "embed". This is a new architecture, so there is no base-branch behaviour; the gap is relative to how other embedding models behave.

**Verification:** lfm2.py:504 sets `self.pooler = pooler_for_embed(pooler_config)`, a bare pooler with no dispatcher. `EmbeddingPoolerHead.get_supported_tasks` in seqwise/heads.py returns only `{"embed"}`. So the model advertises only "embed", and `token_embed` requests are rejected as unsupported. Among standalone embedding models, lfm2.py is the only one that uses bare `pooler_for_embed`.

</details>

Thanks for catching this. I am not sure whether always fill an accurate real-token mask might have any unnecessary impact on the performance of a dense model, So I added an optional model capability  `requires_padding_mask`, which defaults to False, and enabled it for `Lfm2BidirectionalModel`. Model Runner V2 now refreshes the mask when either the model requires it or `VLLM_MOE_SKIP_PADDING` is enabled. This makes the convolution’s correctness independent of the MoE optimization flag while preserving conditional updates for other models.  could u also help cc. @DarkLight1337 thank u very much.
