# [KV Offload][2/N] Add ON_OVERWRITE stores and the lazy store mode

[Upstream PR](https://github.com/vllm-project/vllm/pull/65681) · state: open · merged: False

## Original PR description





## Overview

> [!NOTE]
> This PR is an implementation suggestion for #61396. It shows one way to
> implement phase 2, so that reviewers can see the `ON_OVERWRITE` stores and
> the `lazy` policy in code. It is on top of #61426. The names, the config
> keys, the data structures in the connector, and the split into PRs can change
> after the RFC review. Please put comments on the design in the RFC, and
> comments on the code here.

Phase 2 of #61396, on top of #61426. The stack is six commits on top of
`29f69746b0`, the current tip of #61426; review the range
`29f69746b0..f75d71ffee`. The intermediate branches of the stack stay local,
so `git range-diff 29f69746b0..f75d71ffee` shows the six commits.

This PR adds lazy stores. With the new `lazy` store mode, the CPU stores a
chunk only when HBM is about to overwrite it, and not when the model computes
it. Then the CPU holds mainly the chunks that HBM lost, and not copies of the
chunks in HBM. So the total cache can come near the sum of HBM and CPU.

The default mode stays `eager`. With `eager`, the connector keeps no new
data, and the behavior is the same as on #61426.

```python
"kv_connector_extra_config": {"store_mode": "lazy"}
```

## Claims

- The manager selects its store triggers: `OffloadingManager.store_triggers`
  is an ordered tuple, `(ON_COMPUTE,)` by default. The CPU manager reads the
  new `store_mode` key. `lazy` gives `(ON_OVERWRITE,)`.
- `StoreHandlerFactory` replaces the `HANDLER_FOR_TRIGGER` dict of #61426: a
  class-level registry keyed by trigger, `register_handler(handler_cls)` which
  takes the key from `handler_cls.trigger`, and
  `create_handlers(config, manager_store_triggers, events_tracker,
  vllm_config, kv_cache_config, extra_config)`. The factory puts the layout
  handlers first, then one handler per trigger that the manager asks for, and
  refuses a trigger set that is empty or has duplicates.
- `check_support` gains the connector's `extra_config` and the events tracker
  that the handler will get, so a handler refuses a configuration from the
  object it will actually use.
- The new `OnOverwriteStoreHandler` sends `ON_OVERWRITE` stores, with
  `req_context=None`. It stores a chunk in the step in which core gives a block
  of the chunk to a new owner that does not expect the chunk data there. The
  store completes before the forward pass of the step.
- The handler keeps an overwrite map, from GPU block to the chunks in HBM on
  that block. A chunk enters the map when the model computes it, and when a
  load from the CPU completes; a load that fails contributes nothing. A
  request that starts again from token 0 records its chunks again.
- A prefix hit is not an overwrite. The handler compares the expected key of
  each block in the step, from `req.block_hashes`, with the block key in the
  map. A block copy, and a block of a group that is not offloaded, expect new
  data.
- Sliding window groups and preempted requests work in lazy mode. The new
  `first_live_chunk_idx` hook gives the first chunk of a group whose block ids
  the handler may still read, so the scheduler zeroes stale sliding-window
  block ids only past it.
- New handler hooks: blocks allocated to a request, the blocks allocated in a
  step (a read-only snapshot), load complete, and the first live chunk. The
  scheduler keeps only the set of blocks allocated in the step.
- The cache policy hooks take `req_context=None` for a store after the
  request finishes: `insert` and `on_store_miss`. The LRU policy orders a
  chunk by the key positions of its request; without a request, it uses the
  plain recency rank. ARC does not read the context.
- New checks at start, in `OnOverwriteStoreHandler.check_support`:
  - `self_describing_kv_events`: the payload is built from the request that
    stored the chunk, and an `ON_OVERWRITE` store has no request.
  - The V2 model runner, if the KV cache needs zeroing (a KV cache with more
    than one dtype): V2 zeroes a reused block, and applies the CoW copies,
    before the store reads it.
- Mamba `align` groups are not a refusal. `select_store_candidates` skips a
  CoW-source group, and the scheduler adds the `ON_HANDOFF` handler of #61426
  for a mamba-align layout, which stores that group. On V2 such a layout needs
  KV cache zeroing, so the check above refuses it there.
- The CPU manager refuses `ON_OVERWRITE` with a `store_threshold` of 2 or
  more. The tiering spec accepts only `eager`.
- `docs/features/kv_offloading_usage.md` documents `store_mode`, including the
  V2 restriction.

## Details

- **Why the connector keeps a map.** When core gives a block to a new owner,
  the connector sees only the block id. The old request can be gone, and the
  block pool removes the block hash at that time. So the connector records the
  key and the blocks of each chunk at its offer. The manager keeps no GPU
  data, as today.
- **Why `req_context=None`.** A lazy store can come after
  `on_request_finished`. A late `on_request_finished` or a dummy request makes
  the manager and each tier keep the request state while HBM holds any block of
  the request.
- **Why the V2 check.** The V2 model runner zeroes new blocks and applies the
  CoW copies in `update_requests`, before `handle_preemptions` flushes the
  `ON_OVERWRITE` stores. Thus such a store can read zeroed or copied data, and
  save it under a valid key. No connector hook runs earlier on V2, so the
  handler refuses KV cache zeroing. The V1 runner flushes first.
- **CoW copies on V2 are not refused.** CoW copies are not only for Mamba.
  `SingleTypeKVCacheManager` also copies a block at a partial local prefix
  hit: with `prefix_match_unit` smaller than the block size, or with KV cache
  groups of different block sizes. On V2, such a copy runs before the
  `ON_OVERWRITE` store. I read this in the code; no test or run shows it. This
  PR does not refuse it. Use `VLLM_USE_V2_MODEL_RUNNER=0` for these setups.
- **Mamba `align` layouts.** The lazy handler does not store a CoW-source
  group: `select_store_candidates` skips it. #61426 adds the `ON_HANDOFF`
  handler for such a layout, and that handler stores the group when the
  scheduler hands the boundary block off, so a hybrid layout works in lazy
  mode on the V1 runner. On V2 a mamba layout needs KV cache zeroing
  (`KVCacheConfig.needs_kv_cache_zeroing`), so the zeroing check refuses lazy
  there. A fix outside the connector would be for V2 to call
  `handle_preemptions` before `update_requests`, as V1 does.
- **Known limits.**
  - Each lazy store completes before the forward pass, so the step waits.
  - With more than one KV cache group, the groups of one chunk leave HBM at
    different times. The chunk can give no hit for a short time. This costs hit
    rate only.
  - The partial last chunk is not stored. This is also true for EAGLE and
    MTP models, which store their complete chunks with the same rule as
    `eager`.
  - No self-describing KV events (see the start checks).
  - No KV cache zeroing on the V2 model runner. Use
    `VLLM_USE_V2_MODEL_RUNNER=0`.
  - No tiering. The secondary tier API needs a `ReqContext`.
- **Not a duplicate.** Re-checked on 2026-11-04 with the `gh` searches of
  `AGENTS.md`. The only open PR that mentions #61396 is #64286, the predecessor
  of this one. The lazy-mode work for the other connector is separate:
  `SimpleCPUOffloadConnector` has a `lazy_offload` mode, and #44791, #64394 and
  #65237 change it. That connector stores the blocks of the GPU free queue
  before the loss; this PR changes the offloading connector and stores at the
  loss.
