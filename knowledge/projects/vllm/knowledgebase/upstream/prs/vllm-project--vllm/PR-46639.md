# [Kernel] Support batch invariance for WNA16 Marlin MoE

[Upstream PR](https://github.com/vllm-project/vllm/pull/46639) · state: open · merged: False

## Original PR description

## Overview

Makes the WNA16 Marlin MoE GEMM (`moe_wna16_marlin_gemm`) batch-invariant under
`VLLM_BATCH_INVARIANT=1`, so quantized MoE models that run on Marlin (AWQ-INT4,
GPTQ-INT4/INT8, MXFP4, NVFP4) can be served in batch-invariant mode. No existing
open PR covers this kernel; the related FP4/MXFP4 batch-invariance PRs target
different kernels.

## Claims

- With the flag on, a token's Marlin MoE output is bitwise identical regardless
  of batch size or position in the batch, for all five schemes.
- `MarlinExperts` / `BatchedMarlinExperts` are now selectable when the flag is
  on (the modular-kernel selector previously rejected them). For example, gpt-oss
  on A100 now runs its MoE on Marlin in this mode.
- The default path is unchanged: with the flag off, outputs are bit-identical to
  `main`.
- Cost with the flag on: +2.6–3.4% on the MoE call at decode sizes (GB10), almost
  all from pinning `block_size_m`; `use_full_k` alone measured +0.0–0.3%.

## Validation

**Unit test** (A100 SXM, 108 SMs): 5 schemes × 3 shapes × batch sizes
`{4, 16, 64, 257}`. Every token is run alone, then the batched output (in normal
and reversed order) must match those results bit-exact, and every row must match
a dequantized reference.

```bash
pytest tests/v1/determinism/test_marlin_moe_batch_invariant.py
# 60 passed
```

Without the fix, the same test fails 50/60. Every scheme fails somewhere:

```bash
env -u VLLM_BATCH_INVARIANT pytest --noconftest -p vllm.config \
  tests/v1/determinism/test_marlin_moe_batch_invariant.py
# 50 failed, 10 passed
```

**Independent runs** (thanks @yuvalluria, @Bizuayeu):
- H100 NVL: an earlier version of the test (4 schemes, 2 shapes), 32/32 passed.
- GB10 (SM121, 48 SMs): 60/60 with the flag on. With the flag off, the
  rebuilt kernel's outputs are bit-identical to the nightly's (640/640).
- GLM-5.3-Flash NVFP4 shapes on GB10, with 40 random routings: one request computed alone vs. batched with a partner.

| request rows (alone → together) | stock: request differs | this PR |
|---|---|---|
| 4 → 8 | 14/40 | 0/40 |
| 8 → 16 | 23/40 | 0/40 |

**MoE call time** on GB10 at GLM-5.3-Flash shapes (µs, CUDA events, median of 5 rounds):

| | M=4 | M=8 |
|---|---|---|
| stock (block 8) | 957 | 1777 |
| this PR (block 64) | 982 (+2.6%) | 1838 (+3.4%) |
| `use_full_k` only, block 8 | 957 (+0.0%) | 1782 (+0.3%) |

**End-to-end** (A100, `openai/gpt-oss-20b`, MoE backend selected: `MARLIN` /
`MarlinExperts`): logprobs are bitwise identical between batch size 1 and batch
size N.

```bash
VLLM_TEST_MODEL=openai/gpt-oss-20b pytest \
  tests/v1/determinism/test_online_batch_invariance.py -k TRITON_ATTN
# 1 passed
```

## Details

**Root cause.** Three things in the launch depend on the number of tokens `M`:
1. The `block_size_m` heuristic picks the block size from `M * topk / E`.
2. `determine_exec_config` adjusts each candidate's `blocks_per_sm` by `prob_m`
   and picks the highest, so M can change which thread config (`thread_k` /
   `thread_n`) is used.
3. The DP + two-tile Stream-K split sizes the work as
   `global_mn_tiles = parallel * n_tiles`, where `parallel` is the number of
   MoE blocks. That decides `part2_mn_tiles` / `iters`, which decide where each
   output tile's K reduction is cut across thread blocks.

Either a different cut or a different thread config changes the summation order,
which can flip output rounding.

**Fix** (only when the flag is on):
- Kernel: a `use_full_k` flag makes one block reduce each output tile over the
  full K (`iters = k_tiles`), and `determine_exec_config` no longer adjusts
  `blocks_per_sm` by `prob_m`, so the thread config is fixed for a given shape.
- Python: `block_size_m` is pinned to 64 in `fused_marlin_moe` and
  `batched_fused_marlin_moe`.

**Why 64.** Any fixed `block_size_m` is batch invariant. 64 is the largest value
the existing heuristic picks (the one it uses for large batches) and was already
the batched path's default. A smaller pin would reduce the decode cost above, but
could increase prefill latency. Deriving the value from static config
(e.g. `max_num_seqs`) is a possible follow-up.

**Limitations.**
- `BatchedMarlinExperts` (the expert-parallel batched layout) calls the same
  kernel with the same pin, but isn't tested directly since it needs an EP setup.
- Dense (non-MoE) Marlin is out of scope.

- Bizuayeu · comment · 2026-09-25T13:25:20Z · [source](https://github.com/vllm-project/vllm/pull/46639#issuecomment-5833157491)

A data point for NVFP4, which is not in this PR's test matrix, on GB10 (SM121) at the nightly this PR was tested on (`385dce36`). We have not run this PR's branch.

We serve GLM-5.3-Flash NVFP4 (288 experts, top-8, hidden 4096, `moe_intermediate_size` 2048 → 1024 per TP=2 rank) through `fused_marlin_moe` with `float4_e2m1f` weights (group 16, global scales). The same M-dependent split shows up there:

- At decode sizes (M=4 and M=8, `block_size_m` 8) the profiler shows one kernel and one grid for both: 128 threads, thread_n 128, thread_k 64, grid 144 (48 SMs × 3). What moves with the other request's tokens is `parallel = num_tokens_past_padded / moe_block_size`, which moves `part2` / `iters` in `marlin_template.h` (L356–377) and so where the last tiles are cut along K.
- A request's 4 rows (one decode step at MTP depth 3), computed alone and with another request's 4 rows in the same call: 29 of 40 random routings and inputs differ in at least one row (19 of 40 in the first request's rows), in the last bits of bf16. A partner routed to exactly the same experts (block count unchanged) gives identical rows, and putting the partner before or after the request never changes them.
- Making every tile whole removes it: with the launch pinned to what the kernel picks by itself (`thread_k=64, thread_n=128, blocks_per_sm=3`) and the moe blocks padded with empty blocks (sentinel ids, last real expert) until `parallel * n_tiles` is a multiple of the grid for both GEMMs, `part2` equals the grid and `iters` equals `k_tiles`; 0 of 40 differ. That is the full-K reduction of this PR's `use_full_k`, reached without a kernel change. The empty blocks still stream their expert's weights, though: +3% on the MoE call at M=8 and +13% at M=4 on GB10, so the kernel flag is the better fix.

Since `float4_e2m1f` goes through the same `Marlin` template, an NVFP4 case in `test_marlin_moe_batch_invariant.py` might be worth adding.

**`test_marlin_moe_batch_invariant.py`**
- `VLLM_BATCH_INVARIANT=1`: 60 passed.
- Flag unset: also 60 passed, but that is not a control. The `conftest.py` in `tests/v1/determinism` sets the flag for every test, and the kernel reads the env var on its first call.
- To get a control, I ran a copy without the `assert envs.VLLM_BATCH_INVARIANT` line, with `--noconftest` and the flag unset: 37 of 60 fail, all at the `front` bit-equality check.
  - awq_int4 fails 12/12, gptq_int4 10/12, gptq_int8 10/12.
  - mxfp4 fails only at xlarge (4/4).
  - nvfp4 fails 1/12, only large at batch 64. **nvfp4 xlarge passes at all four batch sizes without the flag.**
- The same copy with the flag on passes 60/60.
- So on GB10 the NVFP4 cases do not detect the variance. Each case compares one token from one seed, and whether bf16 rounding flips is luck. Comparing every filler row against its own single-row result, or using several seeds, would make the NVFP4 cases bite.

**GLM-5.3-Flash NVFP4 shapes** (288 experts, top-8, K=4096, N=1024 per rank, group 16). 40 random routings and inputs; one request computed alone, then with a partner of the same size in one call (both orders):

|---|---|---|

| 8 (8 → 16) | 23 / 33 of 40 | 0 / 0 |

**MoE call time** (µs, CUDA events, 25 × 50 calls per variant, 5 process pairs alternating order; median over rounds, range across rounds):

| | M=4 | M=8 |
|---|---|---|
| stock (block 8, grid 144) | 957 (953–958) | 1777 (1771–1783) |
