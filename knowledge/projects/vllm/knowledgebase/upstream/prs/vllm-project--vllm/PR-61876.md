# [Bugfix][Frontend] Detokenize echoed prompts after truncation

[Upstream PR](https://github.com/vllm-project/vllm/pull/61876) · state: closed · merged: True

## Original PR description

## Overview

`/v1/completions` with `echo=true` and `truncate_prompt_tokens` echoes the full, untruncated prompt for token-ID prompts, although the engine only sees the truncated tokens. The renderer detokenizes the prompt before `apply_post_tokenization` truncates it; this PR detokenizes after truncation instead, restoring the behavior from before the renderer refactor.

## Claims

- For token-ID prompts, the echoed `text` is now the decode of the tokens that reach the engine, so it agrees with `usage.prompt_tokens`, `logprobs.tokens` and `logprobs.text_offset`.
- Fixed for both truncation sides, and for streaming and non-streaming responses (both read `RequestOutput.prompt`).
- No change for text prompts, chat `echo`, or `/detokenize`.

## Validation

Real server on `a9fe30e9f6` (Qwen3-0.6B, RTX 4090, `--enforce-eager`), before and after the fix. Request: token IDs of `"one two three four five six seven eight"` (8 tokens) with `echo=true, max_tokens=1, logprobs=0, truncate_prompt_tokens=4`. `usage.prompt_tokens` is 4 in every case.

| `truncation_side` | Echoed `text` before | Echoed `text` after | `text_offset` indexes `text` correctly (before → after) |
|---|---|---|---|
| unset (tokenizer default, left) | `one two three four five six seven eight com` | ` five six seven eight com` | no (`text[0:5] == "one t"` for token `" five"`) → yes |
| `left` | `one two three four five six seven eight com` | ` five six seven eight com` | no → yes |
| `right` | `one two three four five six seven eight five` | `one two three four five` | yes, but `text` contains 4 prompt tokens the model never saw → yes |

Tests:

- New `tests/renderers/test_completions.py::TestRenderPrompt::test_detokenization_matches_truncated_tokens` covers the sync and async paths with left and right truncation. It fails on `main` (the echoed prompt contains all 10 tokens) and passes with the fix.

## Details

Root cause: in `BaseRenderer._tokenize_singleton_prompt` and its async twin, `needs_detokenization` decoded `prompt_token_ids` before `TokenizeParams.apply_post_tokenization` applied `truncate_prompt_tokens`, so `prompt` described the original token list while `prompt_token_ids` was truncated. `needs_detokenization` is only set for completions/chat `echo` (without `return_token_ids`) and `/detokenize`. Before the renderer refactor, `OpenAIServing._normalize_prompt_tokens_to_input` truncated first and decoded the truncated IDs (see `v0.10.1`).

Limitation: text prompts keep echoing the original string, as they did in `v0.10.1` (the Rust frontend also echoes the request prompt). Aligning that would need the renderer to know whether tokenizer-side truncation actually dropped tokens; I left it out to keep this fix small, and can follow up if maintainers want it.

Not a duplicate: I found no issue or PR for this (searched "echo truncate", "detokenize prompt", "truncate_prompt_tokens", "truncation_side", "echo text_offset"). #61363 and #61524 change which special tokens truncation keeps, not when the echoed text is decoded.
