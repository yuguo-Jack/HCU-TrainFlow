# [Loader] Pinned host staging for the Run:ai streamer path

[Upstream PR](https://github.com/vllm-project/vllm/pull/61303) · state: open · merged: False

## Original PR description

## Overview

Adds a `pinned_staging` key to the Run:ai streamer loader's `--model-loader-extra-config`. When set, the streamer's CPU staging buffer is page-locked once per load and the streamer copies every tensor to the device out of it, so the weight loaders only see device tensors and the host-to-device traffic is DMA out of pinned memory rather than pageable memcpy. Off by default; nothing changes when the key is unset.

## Claims

- On a copy-bound load, the model-loading stage gets substantially faster. Measured on vLLM **0.20.2** (this PR is the port to `main`, see Validation): GLM-5.2-NVFP4 (433 GiB, 232k tensors) as four TP=2 replicas on an 8xB300, `"Model loading took"` 75–79 s → 39–42 s (−48 %), four replicas serving at 133 s instead of 170 s from script start.
- Weights are bit-identical to the stock loader (every GPU parameter hashed after `process_weights_after_loading` on both paths), and throughput is unchanged.
- Any failure to pin (no CUDA, `cudaHostRegister` error, streamer internals changed) falls back to the existing path with a warning.

## Validation

- `tests/model_executor/model_loader/runai_streamer_loader/`: new tests for the extra-config validation, the bounded default `RUNAI_STREAMER_MEMORY_LIMIT`, and the CPU fallback of the iterator with `pinned_staging=True`; the existing buffer-reuse and loader tests still pass (13 passed locally on CPU, `--noconftest`).
- `pre-commit` `ruff-check`, `ruff-format`, `typos` pass on the changed files.
- **Not yet re-run on hardware against `main`.** The numbers above come from the same change on 0.20.2 (patch on the loader in `vllm/model_executor/model_loader/weight_utils.py` with `runai-model-streamer` 0.16.1). Since then `main` started cloning tensors out of the streamer (#43464); on the pinned path the streamer's own `.to(device)` is that copy, so the clone is skipped there (and kept for the distributed streamer, whose device buffer is reused). I will re-measure on `main` as soon as I have the node again and post the numbers here; until then this stays a draft.

Repro of the measurement: `vllm serve nvidia/GLM-5.2-NVFP4 -tp 2 --load-format runai_streamer --model-loader-extra-config '{"pinned_staging": true}'` vs. without the key, same node, same page-cache state; compare the `Model loading took` log line.

## Details

The streamer reads each tensor into one reusable pageable host buffer (`requests_iterator.buffer`), and `param.copy_()` out of it runs as a driver-staged pageable memcpy per tensor: about 2.4 GB/s per worker with eight workers on this node, 4.5 GB/s alone. With the buffer registered (`cudaHostRegister`) the copies run at about 15 GB/s per worker.

Registration of a large buffer is single-threaded and page-fault-bound, so the buffer is first faulted in with `MADV_POPULATE_WRITE` from 16 threads (and advised `MADV_HUGEPAGE`), then registered: about 0.2 s/GB, i.e. 3–4 s for the 16 GB default. Because that cost is per byte of buffer, the streamer's 40 GB default `RUNAI_STREAMER_MEMORY_LIMIT` is bounded to 16 GB when `pinned_staging` is set and the user did not set `memory_limit` (16 GB showed no streaming penalty on this model). The buffer is unregistered in a `finally` when the iterator is exhausted.

Where it does not help: at TP=8 on the same node the gain was 2–4 s on 47 s, because every rank reads the whole checkpoint through the page cache and the stage is a memcpy, not the copy path.
