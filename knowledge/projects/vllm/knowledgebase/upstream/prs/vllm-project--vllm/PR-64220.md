# [Rust Frontend] Report prompt logprobs on streamed completions echo like Python

[Upstream PR](https://github.com/vllm-project/vllm/pull/64220) · state: closed · merged: True

## Original PR description

## Overview

With `echo` and `logprobs`, streamed `/v1/completions` on the Rust frontend now requests and reports the prompt logprobs with the echoed prompt, like the Python frontend.

## Claims

- A streamed `echo` + `logprobs` request asks the engine for prompt logprobs, and the echoed prompt chunk carries `logprobs` for the prompt tokens from text offset 0 (the first prompt token with `null` logprob and top logprobs).
- The generated tokens' `text_offset` continues after the reported prompt tokens, as in Python, instead of after the prompt's character count.

## Validation

Commands from `.buildkite/scripts/run-rust-frontend-cargo-ci.sh` (`style-clippy` and `test`), run from the repo root on this branch:

```
cargo fmt --manifest-path rust/Cargo.toml --all -- --check   # ok
cargo sort --workspace --check rust                          # ok
cargo deny --manifest-path rust/Cargo.toml --config rust/deny.toml check bans   # ok
cargo clippy --manifest-path rust/Cargo.toml --workspace --all-targets --all-features --locked -- -D warnings   # ok
cargo nextest run --manifest-path rust/Cargo.toml --workspace --all-features --locked --no-fail-fast
# 2377 tests run: 2377 passed, 13 skipped
```

New route test `completions_echo_stream_reports_prompt_logprobs`: the mock engine checks that the request carries `prompt_logprobs=1` and returns prompt logprobs with the first output. The stream reports `hello` with tokens `h e l l o`, logprobs `[null, -0.3, -0.4, -0.45, -0.5]`, first top logprobs `null`, offsets `0..4`, then `h` at offset 5 and `i` at offset 6. A `return_tokens_as_token_ids` case makes the reported prompt tokens (`token_id:NNN`, 60 characters) longer than the prompt text, so the generated offsets are 60 and 72. It fails on `main` (no `prompt_logprobs` on the engine request), with only the lowering change (no `logprobs` on the prompt chunk), and with the old text-length offset.

## Details

Python's `CompletionRequest.to_sampling_params` falls back to `logprobs` for `prompt_logprobs` when `echo` is set, and `completion_stream_generator` reports them with the echoed prompt (`vllm/entrypoints/openai/completion/serving.py`). Rust requested prompt logprobs only for non-streaming or prompt-only (`max_tokens=0`) echo, so a streamed echo returned the prompt chunk without `logprobs`.

- `completions/convert.rs`: request prompt logprobs for every `echo` with `logprobs`, like Python. An explicit `prompt_logprobs` still wins, and an explicit one with `stream` is still rejected by validation, as in Python.
- `completion_chunk_stream`: attach the prompt logprobs to the echoed prompt chunk through the helper that prompt-only echo already used (renamed `prompt_only_logprobs_to_openai` → `echoed_prompt_logprobs_to_openai`, since it now serves every echo), and advance the next text offset by the reported prompt tokens.

**Layering.** The sampling-param lowering and the SSE chunk shape are both completions-protocol behavior owned by the completions route in `vllm-server`; the text layer already decodes prompt logprobs into the `Start` event.

**Remaining difference.** Rust streams the echoed prompt as its own chunk before the first generated chunk, while Python sends the prompt and the first generated text in one chunk. The concatenated `text` and `logprobs` across chunks are identical.

Not a duplicate: first-time contributor PRs vllm-project/vllm#62684 (echo with `return_token_ids`) and vllm-project/vllm#63926 (logprob token strings) touch the same files but not this behavior; this diff stays in the echo `Start` branch and the lowering line.
