# [Perf][Attention] FA2: split mixed prefill/decode batches into two calls

[Upstream PR](https://github.com/vllm-project/vllm/pull/58013) · state: open · merged: False

## Original PR description

## Purpose

On FA2 GPUs (SM8x: A100/A800/A10/A40/L4/RTX 30xx/40xx), `FLASH_ATTN` runs every mixed prefill+decode batch as one `flash_attn_varlen_func` call. FA2 has no tile scheduler; its grid is `ceil(max_seqlen_q / 64) × batch × heads`, so with chunked prefill each decode request launches `max_seqlen_q / 64` CTAs, all but one empty. The decodes also miss FA2's `max_seqlen_q == 1` path (packed GQA + split-KV), which only activates when the whole call is decode.

This PR splits FA2 mixed batches into a decode call (`max_seqlen_q=1`) and a prefill call. Decodes already lead the batch under MRv2 (`sort_batch_req_ids`); for the V1 runner the builder now sets `reorder_batch_threshold=1` when splitting. FA3/FA4 (tile-scheduled) and DCP are untouched.

- Only active when `fa_version == 2`, DCP is off, `max_query_len > 1`, no cascade, and both parts are non-empty.
- CUDA graphs are unaffected: FA2 full graphs are only captured for uniform batches, which never split; mixed batches already run attention outside the graph.
- Spec decode: verify requests (q_len > 1) sort first, so `split_decodes_and_prefills` finds no leading decodes and the path is not taken.

Not a duplicate: I searched open/closed PRs and issues for FA2 mixed-batch/decode-prefill splitting. The closest are #51320 (FA2 `num_splits > 1` for spec decode, kernel-side, blocked on vllm-project/flash-attention#176) and #57709 (opt-in FlashInfer paged prefill, FlashInfer backend only); neither changes how `FLASH_ATTN` issues FA2 calls.

## Test Plan

All on 1× A800 80GB PCIe (SM80), torch 2.13.0+cu130, `main` @ 3df4ae153, `--attention-backend FLASH_ATTN` (the SM80 default).

1. Kernel microbenchmark (CUPTI, cold L2), FA2 one call vs split, Llama-3-8B geometry (32/8 heads).
2. `pytest tests/v1/attention/test_attention_backends.py -k "causal_backend_correctness or sliding_window_backend_correctness or non_causal_backend_correctness"` on main and on this PR. The `mixed_*` specs are decode-first with context-bearing extends, so they exercise the split on any FA2 GPU (including CI's L4).
3. `vllm bench throughput`, random dataset, 1000 prompts, 3 reps alternating main/PR order.
4. GSM8K (`tests/evals/gsm8k/gsm8k_eval.py`, full 1319, 5-shot, greedy) against `vllm serve`, main vs PR.
5. `vllm bench serve`, Poisson arrivals.

## Test Result

|---|---:|---:|---:|
| 240 decodes @1K + 16×1024 prefill | 3703 | 1764 | 2.10× |
| 128 decodes @2K + 2×2048 prefill | 3242 | 1208 | 2.68× |

**6. Numerics** (prompted by @troycheng's independent SM120 check below). The decode subcall has `max_seqlen_q == 1`, which is the only branch in `flash_api.cpp` that reaches `set_params_splitkv`, so decode rows now get heuristic split-K; `main`'s single mixed call never does. That changes accumulation order for decode rows only (~1 ULP BF16). One fixed set of decode rows, three call shapes, 1x A800, BF16, 16 Q / 4 KV heads, D256, KV length 3072, 2048 query tokens:

| decode rows, bitwise | num_splits=0 (heuristic) | num_splits=1 |
|---|---|---|
| this PR vs a **pure-decode step** | **0 differing** / 122,880 | 0 differing |
| `main` (mixed call) vs a pure-decode step | **52,735 differing**, max abs 0.00048828 | 0 differing |
| prefill rows, this PR vs `main` | 0 differing / 8,265,728 | 0 differing |

So this PR's decode rows are bitwise identical to what a decode-only step already produces, and `main`'s mixed-batch rows are the ones that differ from it: today a decode token's numerics depend on whether a prefill shared its step, and the split removes that dependence. With 60 decodes + 646/1342 prefills all three agree bitwise (the heuristic picks one split once the decode grid is saturated). Under `VLLM_BATCH_INVARIANT=1` the builder forces `max_num_splits = 1`, the right-hand column, where this PR is numerically a no-op.

Thank you for running this — that is a careful piece of work, and it reproduces on SM80. Your diagnostic result (forcing effective `num_splits=1` restores byte equality) identifies the mechanism exactly, and I think the direction of the difference is worth making explicit, because it argues for the split rather than against it.

**Mechanism.** In `flash_api.cpp`, `set_params_splitkv` is reached only through the `seqlenq_ngroups_swapped` branch, which requires `max_seqlen_q == 1`. So:

- `main`, mixed batch: one call with `max_seqlen_q > 1` → gate never opens → no split-K, decode rows walk the whole KV serially.
- this PR: the decode subcall has `max_seqlen_q == 1` → gate opens → heuristic split-K (plus the packed-GQA swap).

Different accumulation order, hence ~1 ULP BF16 differences confined to decode rows, and byte equality once splits are pinned to 1. That matches your table on both counts.

**Which side is the outlier.** A pure-decode step in `main` today already runs the `max_seqlen_q == 1` path, so I compared one fixed set of decode rows three ways: `P` = pure-decode call, `M` = `main`'s single mixed call, `S` = this PR's split calls. 1× A800 (SM80), BF16, 16 Q / 4 KV heads, D256, KV length 3072, 2048 query tokens, seed 20261006 (your parameters, block size 16):

| decode rows, bitwise | num_splits=0 (heuristic) | num_splits=1 |
|---|---|---|
| **S vs P** (PR vs pure-decode step) | **0 differing** / 122,880 | 0 differing |
| **M vs P** (main vs pure-decode step) | **52,735 differing**, max abs 0.00048828 | 0 differing |
| S vs M (PR vs main) | 52,735 differing, max abs 0.00048828 | 0 differing |
| prefill rows, S vs M | 0 differing / 8,265,728 | 0 differing |

So this PR's decode rows are bitwise identical to what a decode-only step already produces; `main`'s mixed-batch rows are the ones that differ from it. Today a decode token's attention numerics depend on whether a prefill happened to land in the same step — the split removes that dependence rather than introducing one.

**Two further notes from the same run:**

- With 60 decodes + 646/1342 prefills, *all three* agree bitwise (0 differences). The heuristic picks a single split once the decode grid is already saturated, so nothing changes. The divergence appears in the few-decodes / long-context regime — which is also where the speedup is largest.
- Under `VLLM_BATCH_INVARIANT=1` the builder forces `max_num_splits = 1`, i.e. the `num_splits=1` column: this PR is numerically a no-op there.

**End-to-end accuracy** (already in the PR description): GSM8K, full 1319 questions, 5-shot, greedy, Llama-3.1-8B-Instruct on A800 — 0.759 on `main` vs 0.760 with this PR, invalid-response rate 0.002 on both.

<summary>Script for the P/M/S comparison above</summary>

```python
# verify_fa2_split_numerics.py — one fixed set of decode rows, three call shapes.
import sys
import torch
from vllm.vllm_flash_attn import flash_attn_varlen_func

HQ, HKV, D = 16, 4, 256
KV_LEN = 3072
BLOCK = 16


def build(n_dec, pre_lens, seed):
    g = torch.Generator(device="cuda").manual_seed(seed)
    q_lens = [1] * n_dec + list(pre_lens)
    B = len(q_lens)
    bps = KV_LEN // BLOCK
    k_cache = torch.randn(B * bps, BLOCK, HKV, D, dtype=torch.bfloat16, generator=g)
    v_cache = torch.randn_like(k_cache)
    block_table = torch.randperm(B * bps, generator=g, device="cuda").int().view(B, bps)
    q = torch.randn(sum(q_lens), HQ, D, dtype=torch.bfloat16, generator=g)
    cu_q = torch.tensor([0] + q_lens, dtype=torch.int32, device="cuda").cumsum(0, dtype=torch.int32)
    seqused = torch.full((B,), KV_LEN, dtype=torch.int32, device="cuda")
    return q, k_cache, v_cache, block_table, cu_q, seqused, q_lens


def call(q, kc, vc, cu_q, max_q, seqused, bt, out, num_splits):
    flash_attn_varlen_func(
        q, kc, vc, max_seqlen_q=max_q, cu_seqlens_q=cu_q, max_seqlen_k=KV_LEN,
        seqused_k=seqused, softmax_scale=D**-0.5, causal=True, block_table=bt,
        out=out, fa_version=2, num_splits=num_splits,
    )


def diff(a, b):
    return f"{int((a != b).sum()):>9,} differing / {a.numel():,}   max |d| {float((a.float() - b.float()).abs().max()):.7g}"


def run(n_dec, pre_lens, num_splits, seed):
    q, kc, vc, bt, cu_q, seqused, q_lens = build(n_dec, pre_lens, seed)
    nd = n_dec
    out_pure = torch.empty(nd, HQ, D, dtype=torch.bfloat16, device="cuda")
    call(q[:nd], kc, vc, cu_q[: nd + 1], 1, seqused[:nd], bt[:nd], out_pure, num_splits)
    out_mixed = torch.empty_like(q)
    call(q, kc, vc, cu_q, max(q_lens), seqused, bt, out_mixed, num_splits)
    out_split = torch.empty_like(q)
    call(q[:nd], kc, vc, cu_q[: nd + 1], 1, seqused[:nd], bt[:nd], out_split[:nd], num_splits)
    call(q[nd:], kc, vc, cu_q[nd:] - nd, max(pre_lens), seqused[nd:], bt[nd:], out_split[nd:], num_splits)
    torch.cuda.synchronize()
    print(f"\n=== n_dec={n_dec} prefills={pre_lens} num_splits={num_splits} (decode rows)")
    print(f"  S vs P : {diff(out_split[:nd], out_pure)}")
    print(f"  M vs P : {diff(out_mixed[:nd], out_pure)}")
    print(f"  S vs M : {diff(out_split[:nd], out_mixed[:nd])}")
    print(f"  prefill rows, S vs M : {diff(out_split[nd:], out_mixed[nd:])}")


torch.set_default_device("cuda")
seed = int(sys.argv[1]) if len(sys.argv) > 1 else 20261006
for num_splits in (0, 1):
    run(30, [526, 1492], num_splits, seed)
    run(60, [646, 1342], num_splits, seed)
```

Runs against an unmodified build (it calls the kernel directly, so it does not depend on which version of the backend is installed).
