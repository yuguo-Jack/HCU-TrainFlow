# [Bugfix][LoRA] Disable shared-expert aux stream with fully-sharded LoRA

[Upstream PR](https://github.com/vllm-project/vllm/pull/61284) · state: open · merged: False

## Original PR description

## Purpose

Fixes #60845.

With `--fully-sharded-loras`, the shared experts' LoRA layers all-gather / all-reduce across TP, and the routed experts' fused MoE LoRA kernel does its own collectives on the main stream. Running the shared experts on the aux stream puts two collectives in flight on the same communicator. Under CUDA graph capture they become independent graph branches, and the replay order is not guaranteed to match across ranks, so NCCL deadlocks (first LoRA decode step hangs, then `RPC call to sample_tokens timed out`).

This PR runs the shared experts on the main stream when fully-sharded LoRA is enabled, same as the existing EPLB / flashinfer exclusions in `SharedExperts._disable_shared_experts_overlap`.

## Test Plan

Qwen3.5-35B-A3B, TP=2, `--enable-lora --fully-sharded-loras --max-lora-rank 32`, default CUDA graphs, two rank-32 adapters alternating.

- v0.28.0 (reproduces the hang on the first LoRA request): with this patch, first request returns in 1s, 1000/1000 requests OK.
- v0.31.0 / main: 1000/1000 requests OK.

## Test Result

No hang, 0 failed in both runs.

LGTM. The fix removes the concurrency instead of relying on enqueue order, and it matches the existing rule that LoRA's own dual stream is already disabled with `fully_sharded_loras` (`_build_lora_context`, `LoRAConfig` validation).

Validated on 2× H20 (TP=2, Qwen3.6-35B-A3B, 2D + 3D adapters, default CUDA graphs): v0.28.0 hangs on the first LoRA request (`RPC call to sample_tokens timed out`) and passes with `VLLM_DISABLE_SHARED_EXPERTS_STREAM=1`. Current main does not hang on H20 (same as B200), so whether it triggers really depends on the hardware. This PR passes, and its outputs differ from main only by the usual run-to-run noise.
