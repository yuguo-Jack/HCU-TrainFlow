# [Doc] Clarify keep-mode pause and clear_cache semantics

[Upstream PR](https://github.com/vllm-project/vllm/pull/57970) · state: open · merged: False

## Original PR description

## Purpose

`pause_generation(mode="keep")` behaves in two different ways depending on `clear_cache`. The docs did not explain this:

- With `clear_cache=True` (the default), `_finish_pause` calls `_reset_caches(reset_running_requests=True)`. That preempts every running request: its KV blocks are freed, `num_computed_tokens` is reset to 0, and it goes back to the waiting queue. On resume it is scheduled like any preempted request, so its KV is either recomputed or loaded from a KV connector that still holds it.
- With `clear_cache=False`, the running requests keep their KV cache. Tokens generated after resume attend to KV computed with the old weights.

`docs/training/async_rl.md` described `keep` as "Freeze requests in the queue". Because `clear_cache` defaults to `True`, that reads as if the KV cache is always preserved across a keep pause.

A related detail was also undocumented. `clear_cache=True` asks the KV connector to reset its cache, but `Scheduler.reset_connector_cache()` treats a `None` return from `reset_cache()` as success. So connectors that do not implement it, such as the LMCache connectors, keep their cache, and resumed requests can load KV computed with the old weights from them.

## Changes

- `docs/training/async_rl.md`:
  - Reword the `keep` row.
  - Add a table for `clear_cache` under `mode="keep"`.
  - Note that connectors without `reset_cache()` keep their cache.
  - Note that `clear_cache=True` fails while a request is still waiting for remote KV, for example on the decode side of disaggregated prefill/decode.
  - Reword the flow paragraph to match.
- Docstrings for `EngineClient.pause_generation`, `AsyncLLM.pause_generation`, and both `pause_scheduler` implementations now state what `clear_cache` does under `keep`.
