# [MRV2][Spec Decode] Close DFlash/DSpark and adaptive-verification JIT warmup gaps

[Upstream PR](https://github.com/vllm-project/vllm/pull/63819) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

Three Triton kernels on the MRV2 spec-decode path still JIT-compile during serving after warmup, triggering `Triton kernel JIT compilation during inference: ...` from the JIT monitor and a latency spike on that step (and a hard failure under `--jit-monitor-mode=error`). Seen while serving Muse-Spark-Open with a DSpark drafter; reproduced on small models.

## Claims

- `_prepare_dflash_inputs_kernel` (DFlash/DSpark) compiles once instead of once per power-of-two prefill chunk bucket; decode-time kernel GPU time drops ~3x as a side effect.
- `_accumulate_kernel` (adaptive verification acceptance estimator) compiles once for all batch sizes.
- `_refit_kernel` is compiled at warmup instead of 100 steps into serving.
- No output changes: `prepare_dflash_inputs` outputs are bitwise identical; estimator statistics differ only by fp32 summation order.

## Validation

**End to end, `jit_monitor_verbose=True`, MRV2, B300** (repro script runs a battery of batch sizes / prompt lengths after warmup):

| Config | Runtime JIT before | Runtime JIT after |
|---|---|---|
| Qwen3-4B + `RedHatAI/Qwen3-4B-speculator.dspark`, k=7, prompts 5–3000 tokens | `_prepare_dflash_inputs_kernel` `BLOCK_SIZE=128`, `BLOCK_SIZE=256` | none |
| Qwen3-8B + `z-lab/Qwen3-8B-DFlash-b16`, k=7, `enable_adaptive_verification`, `max_num_seqs=1024`, bs 1/200/300/600/1000, >100 steps | `_refit_kernel`, `_accumulate_kernel` `BLOCK_R=512` (bs=300) | none from these kernels |

## Details

**Root cause.** Each kernel had a `tl.constexpr` derived from the live batch, and warmup only reaches a few of its values:

- `prepare_dflash_inputs` set `BLOCK_SIZE = min(256, next_power_of_2(max_query_len + num_query_per_req))`. Warmup prefill/decode steps are tiny, so 128/256 (and, depending on config, smaller buckets) first compile on a real prefill chunk. A fixed `BLOCK_SIZE` with a variable `num_blocks` grid covers every span with one variant. It also fixes a perf cliff: the padding loops at the end of the kernel stride by `BLOCK_SIZE`, so at decode (`BLOCK_SIZE` 8/16) they walked `max_num_tokens` in 8- or 16-element steps.
- `_accumulate_kernel` used `BLOCK_R = max(256, next_power_of_2(num_reqs))`. Warmup reaches 256 and `max_num_seqs`, not the buckets in between. `BLOCK_R` is now computed once from `max_num_reqs`.
- `_refit_kernel` runs every `REFIT_INTERVAL` (100) steps. `OnlineAcceptanceEstimator.warmup()`, called at the end of `warmup_kernels`, clears the per-round statistics and runs a refit. With zero statistics the Newton step is exactly zero, so the coefficients don't move. This also stops dummy warmup observations from leaking into the first real refit round, which is a small behavior change.

**Scope.** The estimator is only active with adaptive verification and a drafter without a confidence head (e.g. DFlash). DSpark checkpoints with `enable_confidence_head` disable it.

**Related PRs.**
- #58559 also targets `_prepare_dflash_inputs_kernel`, by explicitly launching every `BLOCK_SIZE` bucket at warmup. This PR removes the variant set instead: one compile, no warmup code, and faster decode. #58559 has merge conflicts and no review activity since September. Its DSv4 top-k part is unrelated to this PR.
- #58633 gives the padding loops a separate `PAD_BLOCK_SIZE`. It overlaps with the decode speedup here, and its `min(1024, next_power_of_2(pad_span))` sizing varies with batch size, so it could reintroduce runtime compiles.
- #56323 / #56654 added, then reverted, explicit JIT warmup for these MRV2 kernels.

**Known remaining gap, not addressed here.** `_gumbel_sample_kernel` (main sampler, `APPLY_TEMPERATURE=False, IS_DRAFTING=False`) still JITs on the first request that takes the non-fused sampling path: no top-k/top-p, or explicit seed, or processed logprobs. Warmup's sampled pass uses top-k/top-p, so it takes the fused FlashInfer sampler path, and its other pass is greedy.
