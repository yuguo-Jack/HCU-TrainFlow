# [Core] WhisperEncoder support `torch.compile` 

[Upstream PR](https://github.com/vllm-project/vllm/pull/30549) · state: closed · merged: False

## Original PR description

## Overview

This PR enables compiling of WhisperEncoder.
This is particular important when running Whisper as the encoder execution time is independent of the input sequence/audio length (spectogram gets padded/truncated).

As Encoder-Decoder models move closer to MM abstractions, the compilation introduced here follows the same approach proposed for MM models here https://github.com/vllm-project/vllm/pull/23207, wherein compilation is turned on a model by model basis. 
Similarly, I am using the same `compile_mm_encoder` flag to turn on encoder compilation.

Please note that **encoder compilation is enabled by default for Whisper, but NOT for models that build on WhisperEncoder** (eg voxtral/ultravox).
This is to avoid unintended changes to compound architectures. cc @patrickvonplaten to make sure all is well voxtral-side.

I am also leveraging a recent PR https://github.com/vllm-project/vllm/pull/30125/ that added an `MMEncoderAttention` CustomOp, sharing its usage with ViTs. 
Alternatively, we could create a separate fa wrapper function specifically for encoder-decoder models, if we believe the two impl could diverge.  cc @DarkLight1337 @Isotr0py and @MatthewBonanni for thoughts on FA.

## Code Review

This pull request refactors the Whisper model's attention mechanism and encoder input handling, primarily to enhance `torch.compile` compatibility. Key changes include modifying the `Attention` layer in `vllm/attention/layer.py` to utilize a new `vit_flash_attn_wrapper` for Flash Attention, passing `softmax_scale` through, and simplifying output handling in `vllm/attention/ops/vit_attn_wrappers.py`. The `WhisperEncoder` in `vllm/model_executor/models/whisper.py` is updated with a `support_torch_compile` decorator and its `forward` method now accepts a single `torch.Tensor` for simplified batching, with `cast_overflow_tensors` being commented out due to `torch.compile` incompatibility. The `Voxtral` model's `whisper_encoder` call is adjusted accordingly. Additionally, the encoder cache management logic in `vllm/v1/core/sched/scheduler.py` is refactored to consistently update cache state. Review comments highlight the need to correct a hardcoded `batch_size=1` to `bsz` and move an import statement out of the `forward` method in `vllm/attention/layer.py`, as well as remove various blocks of commented-out debugging code found in `vllm/attention/ops/vit_attn_wrappers.py` and `vllm/model_executor/models/whisper.py` for improved code clarity.

## Code Review

This pull request introduces explicit `softmax_scale` parameter propagation across various attention operations in `vllm/attention/layers/mm_encoder_attention.py` and `vllm/attention/ops/vit_attn_wrappers.py`. A significant portion of the changes focuses on enabling `torch.compile` for the Whisper encoder, achieved by applying a `support_torch_compile` decorator to `WhisperEncoder`, introducing a conditional `should_torch_compile_encoder` function, and modifying `WhisperEncoderLayer` to conditionally skip `cast_overflow_tensors` when compiled. The `WhisperEncoder`'s `forward_conv` method is refactored to accept a single `torch.Tensor` instead of a list, simplifying its internal batching and positional embedding logic. Furthermore, the `CompilationConfig` now includes a `verify_with_model_config` method to disable specific compilation features for encoder-decoder models, and the `VllmConfig` automatically enables encoder compilation for Whisper models at higher optimization levels, alongside a revised warning condition for Whisper's multiprocessing method.

While this change is correct to adapt to the new `WhisperEncoder` interface, there appears to be a critical issue in how `input_embeds` is created in the `prepare_inputs_for_conv` function, which is called on a preceding line.

The `torch.stack(chunked_features)` call inside `prepare_inputs_for_conv` will fail if the feature chunks have different sizes. This can happen if the melspectrogram length is not a multiple of `self.chunk_size` (6000). The melspectrogram length is guaranteed to be a multiple of 3000, but not necessarily 6000. For example, if the length is 9000, `feature.split()` will produce one chunk of 6000 and one of 3000, causing `torch.stack` to fail.

To fix this, the last chunk of each feature should be padded to `self.chunk_size` before being added to `chunked_features` inside `prepare_inputs_for_conv`.
