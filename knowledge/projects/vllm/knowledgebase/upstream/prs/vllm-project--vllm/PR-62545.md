# [Observability] Count device prefix-cache block evictions

[Upstream PR](https://github.com/vllm-project/vllm/pull/62545) · state: open · merged: False

## Original PR description

## Overview

Add `vllm:prefix_cache_evictions`, a counter of device prefix-cache blocks dropped because their slot was reused for new data, or because the block was explicitly removed. The counter is blocks, not tokens, so it is not a ratio against `vllm:prefix_cache_hits`. It does not duplicate #48488 (which block to evict), #27793 (sampled residency histograms, already merged), or #53893 (CPU offload evictions).

## Claims

- Operators can graph blocks evicted per second with `rate(vllm:prefix_cache_evictions_total[5m])`.
- One series per engine. A prefix-cache reset does not increment the counter. Preemptions stay on `vllm:num_preemptions`.
- One increment per block, however many hashes that block carried. An uncached block, including a partial tail that was never hashed, does not increment it.
- The same counter is recorded by the Python metrics logger and the Rust frontend.

## Validation

Python unit tests were run on a CPU VM against this branch. This laptop cannot import current vLLM main.

```bash
pytest tests/v1/core/test_prefix_caching.py::test_maybe_evict_cached_block \
  tests/v1/core/test_prefix_caching.py::test_prefix_cache_eviction_counter_ignores_reset_and_uncached_blocks \
  tests/v1/core/test_prefix_caching.py::test_scheduler_make_stats_drains_prefix_cache_evictions_once \
  -q --noconftest
```

Result: 3 passed. Four real evictions drain to 4, and the next drain is 0. A prefix-cache reset stays at 0. The uncached case is the next free block, which is non-null and has no hash; `blocks[0]` is the null placeholder and is not the block `get_new_blocks` walks. `Scheduler.make_stats()` returns the drained count once, then 0.

CPU serves used block size 32 and 8 blocks. The CPU attention kernel rejects block size 16. Each prompt plus one generated token fills two blocks. Only the full block is cached. One of the 8 blocks is the null placeholder, leaving 7 usable. Uncached tails are reused first and do not count, so eight sequential completions evict two whole blocks.

```bash
vllm serve facebook/opt-125m \
  --dtype float32 \
  --max-model-len 64 \
  --block-size 32 \
  --num-gpu-blocks-override 8
```

The other three rows use the model and environment variables in the table below.

| Frontend | Model runner | Model | `vllm:prefix_cache_evictions_total` |
|---|---|---|---|
| Python | V2 | `facebook/opt-125m` (61 prompt tokens) | `0.0` then `2.0` |
| Python | V1 (`VLLM_USE_V2_MODEL_RUNNER=0`, worker loaded `cpu_model_runner.py`) | `facebook/opt-125m` | `0.0` then `2.0` |
| Rust (`VLLM_USE_RUST_FRONTEND=1`) | V2 | `Qwen/Qwen2.5-0.5B` (60 prompt tokens) | `0` then `2` |
| Rust (`VLLM_USE_RUST_FRONTEND=1`) | V1 (`VLLM_USE_V2_MODEL_RUNNER=0`, worker loaded `cpu_model_runner.py`) | `Qwen/Qwen2.5-0.5B` | `0` then `2` |

The eight prompts were distinct, so the count of 2 holds only when no request gets a prefix-cache hit.

```bash
for i in $(seq 0 7); do
  prompt=$(yes "item$i" | head -n 30 | tr '\n' ' ')
  curl -s http://127.0.0.1:8000/v1/completions \
    -H 'Content-Type: application/json' \
    -d "{\"model\":\"facebook/opt-125m\",\"prompt\":\"$prompt\",\"max_tokens\":1,\"temperature\":0}"
done
curl -s http://127.0.0.1:8000/metrics | grep prefix_cache_evictions
```

For the Qwen rows, set `model` to `Qwen/Qwen2.5-0.5B`.

Rust unit tests were run on the same VM with Rust 1.95:

```bash
cargo test -p vllm-engine-core-client -- prefix_cache_evictions
```

Result: `omitted_prefix_cache_evictions_decode_as_zero` and `prefix_cache_evictions_are_recorded` passed. An omitted `prefix_cache_evictions` field decodes as 0, and recording stats emits `vllm:prefix_cache_evictions_total`. No model-output or accuracy change.

AI assistance was used to write this change.

## Details

The block pool and the `/metrics` process are separate, so the count follows the same path as `vllm:prefix_cache_hits`: increment in `BlockPool._maybe_evict_cached_block` only after cached hashes are removed, drain through `SchedulerStats`, and increment the Prometheus counter in the frontend. The Rust frontend decodes that field (`#[serde(default)]` so older engines still parse) and records the same series.
