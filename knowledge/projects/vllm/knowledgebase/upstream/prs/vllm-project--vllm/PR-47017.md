# [ROCm] Enable DeepSeek-V4 on gfx11

[Upstream PR](https://github.com/vllm-project/vllm/pull/47017) · state: closed · merged: True

## Original PR description


## Purpose

This PR enables DeepSeek-V4 checkpoints on ROCm gfx11/RDNA devices.

It removes Python-side blockers in the ROCm sparse-indexer path and allows DeepSeek-V4 checkpoints mapped to `INCConfig` to pass ROCm platform validation:

- Register ROCm sparse-indexer ops on gfx11.
- Let `SparseAttnIndexer.forward_hip()` delegate to the ROCm sparse-indexer custom op and use the op-level fallback instead of failing early on platform capability checks.
- Add `inc` to `RocmPlatform.supported_quantization` so the checkpoint passes ROCm validation.

## Test Plan

The validation checkpoint is:

```text
Intel/DeepSeek-V4-Flash-W4A16-AutoRound
```

Manual validation on ROCm gfx11/RDNA:

1. Build the branch for ROCm gfx1100:

```bash
VLLM_TARGET_DEVICE=rocm \
PYTORCH_ROCM_ARCH=gfx1100 \
python setup.py build_ext --inplace
```

2. Serve the model with fp8 KV cache:

```bash
python -m vllm.entrypoints.openai.api_server \
	--model Intel/DeepSeek-V4-Flash-W4A16-AutoRound \
	--served-model-name dsv4-w7900d \
	--tensor-parallel-size 8 \
	--dtype bfloat16 \
	--kv-cache-dtype fp8 \
	--trust-remote-code
```

For gfx1100 validation, the following Triton workaround was used:

```bash
export AMDGCN_USE_BUFFER_OPS=0
```

Without it, Triton 3.6.0's AMD backend fails compiling the DeepSeek-V4 `fused_q_kv_rmsnorm` Triton kernel with `TritonAMDGPUCanonicalizePointers / make_ttgir: PassManager::run failed`.

## Test Result

Manual validation passed on:

- 2x Strix Halo / Radeon 8060S / gfx1151 with `TP=2 + EP=2`.
- 8x Radeon PRO W7900D / gfx1100 with `TP=8` and source-built ROCm extensions.

Validation covered:

- DeepSeek-V4 model load.
- OpenAI-compatible serving startup.
- `/v1/completions` and `/v1/chat/completions` smoke tests.
- Concurrent decode benchmark.

Functional integration result:

- TP1, three-layer, dummy-weight, eager DeepSeek-V4-Flash-0731 run reached KV-cache initialization and server readiness.
- /v1/models, /health, and a one-token /v1/completions request all returned HTTP 200; the completion took 4.497858 s.
- Because this used three dummy layers, this is liveness/path evidence only, not official-weight quality or end-to-end performance evidence.

I also ran a focused formal scorer gate with FP8 Q/K, production [N,1] scales, H=64, D=128, and TopK=512:

- 9/9 shapes passed for M in {1,8,32} and N in {512,2048,8192}.
- Routed values, masks, and TopK512 indices were exact to both the direct Torch fallback and a separately expressed reference.
- A masked-range fixture and ten-repeat tie fixture passed.
- Instrumented dispatch recorded exactly one Torch-fallback call and zero AITER scorer-module probes.
- Scorer-only p50 ranged from 0.188491 ms (M1/N512) to 1.000216 ms (M32/N8192); p99 ranged from 0.241520 ms to 1.108022 ms.

One independent startup boundary is worth keeping separate: without gfx1100 W8A8 shape configs, the default N=32768,K=1024 Triton compilation did not finish inside a 600 s gate (the worker spent more than seven minutes compiling while the GPU was idle). I used small diagnostic config mounts only to reach the indexer; they are not tuned, installed, or counted as performance evidence. The successful first request also JIT-compiled four sparse decode/packing helpers.

Conclusion: this validates the functional fallback behavior of the sparse-indexer change on gfx1100 without broadly enabling unsupported AITER paths. It does not establish first-class gfx1100 performance, graph capture, full 43-layer TP8/DSpark acceptance, or optimized AITER scorer dispatch.
