# [Bugfix][ROCm] Keep extend context when model runner v2 reorders the batch

[Upstream PR](https://github.com/vllm-project/vllm/pull/63676) · state: open · merged: False

## Original PR description


_Requested by **Tun Jian**_



## Overview

Stacked on #63675 (the ROCM_AITER_FA test suite). Only the last commit is new; please review it after #63675 lands. Part of the attention backend test standard RFC (https://github.com/vllm-project/vllm/issues/63640).

**Before:** Under model runner v2, ROCM_AITER_FA computed attention for an extend without its cached context whenever a shorter prefill was ordered before it in the batch. In engine runs, prompt logprobs drifted by up to 1.17 from TRITON_ATTN, against about 0.05 for a correct backend.

**After:** Runner v1 and v2 give the same results, and every runner-v2 engine test matches TRITON_ATTN within the calibrated tolerance.

This deletes the `mrv2-batch-order` entry from `known_defects.py`. Its 1 unit + 15 engine tests were strict xfails on the tests-only PR and now pass.

## Validation

MI350X (gfx950), `vllm/vllm-openai-rocm:nightly` (AITER 0.1.26), full unit suite including the nightly matrix:

- Unit: 3795 passed, 77 xfailed (other fixes' entries), 0 unexpected.
- Engine: all 15 runner-v2 tests that were xfail in #63675 pass (`test_engine_modes`, `test_engine_modes_full`, `test_ngram_spec_decode` with model runner v2).
- `test_attention_splitting.py`: the new order cases pass.

## Details

`split_decodes_prefills_and_extends` assumed extends come before prefills, but runner v2 sorts non-decodes by token count. A prefill placed before the last extend is now counted as an extend with zero context, so the returned ranges stay contiguous and every extend keeps its context. `tests/v1/attention/test_attention_splitting.py` gains order cases for both runners.


## Related upstream PRs

Two open PRs fix the same model runner v2 batch-order bug:

- #63542 (qli88) makes the same change to `split_decodes_prefills_and_extends`: everything between the leading decodes and the trailing run of context-free requests goes through the extend path. It also splits the extend context workspace only among requests that have context. It is equivalent to this PR and was opened first.
- #59098 (phambinhfin) fixes it from the scheduler side, by making MRV2's sort context-aware, and also clamps the prefill boundary in the splitter.

Whichever of these lands, the `mrv2-batch-order` entry in #63675's `known_defects.py` should be deleted with it; this PR's tests then check that fix. If #63542 or #59098 merges first, this PR reduces to that registry deletion and the order cases in `test_attention_splitting.py`.

- mjkvaak-amd · comment · 2026-10-31T19:34:02Z · [source](https://github.com/vllm-project/vllm/pull/63676#issuecomment-6548155360)

I was looking into possibility of making `ROCM_AITER_FN` the default when `VLLM_ROCM_USE_AITER=1` since its typically _a lot_ faster than the current default `ROCM_ATTN`, when I stumbled upon the bug that this PR fixes. In nutshell, vLLM's newer v2 scheduler can put a brand-new prompt in front of a long prompt that's only half processed. AITER FA's code assumes everything after the first new prompt is also new, so it handles the rest of the long prompt without looking at its first half, and the model "forgets" whatever was there, like the hidden needle. As said in the PR body, there are sibling PRs #59098 and #63542 that fix the same issue. 

I ran this comparison

Mistral-7B,   NIAH | 1 | 0.754 | 1 | 1 | 1
Qwen3-8B,   NIAH | 1 | 0.996 | 1 | 1 | 1

Throughput: the three PRs are within 5% of each other, and none is consistently fastest. They are all substantially faster than `ROCM_ATTN`.
