# [Model] Support hotwords for MOSS-Transcribe-Diarize

[Upstream PR](https://github.com/vllm-project/vllm/pull/62329) · state: closed · merged: True

## Original PR description



## Overview

`MossTranscribeDiarizeForConditionalGeneration.get_generation_prompt` ignores `stt_params.hotwords`, so `hotwords` sent to `/v1/audio/transcriptions` is silently dropped for MOSS-Transcribe-Diarize (only Fun-ASR consumes it today). This PR appends the hotwords to the prompt using the [model card's hotword recipe](https://huggingface.co/OpenMOSS-Team/MOSS-Transcribe-Diarize) (`<instruction>热词提示：w1, w2`).

Not a duplicate: no open PR or issue touches MOSS hotwords (`gh pr list --state open --search "hotwords"` / `"MOSS-Transcribe-Diarize"`). #50362 (verbose_json) edits the same model file in a different function and does not conflict.

## Claims

- `hotwords` now takes effect for MOSS-Transcribe-Diarize, with or without a custom `prompt`. Blank `hotwords` keeps the old prompt byte-for-byte.
- With a short relevant list, error rates on hotwords roughly halve on public biasing benchmarks (tables below); overall WER/CER also drops.
- Documents `hotwords` (previously undocumented) in the speech-to-text guide, including a note that long or unrelated lists can hurt accuracy.

## Validation

Setup: RTX 6000 Ada, nightly wheel at the base commit plus this patch, `vllm serve OpenMOSS-Team/MOSS-Transcribe-Diarize --trust-remote-code`, `temperature=0`.

**Unit tests**: `pytest tests/models/multimodal/processing/test_moss_transcribe_diarize.py`: before the patch 2 failed (`hotwords`, `custom-prompt-hotwords`); after, 14 passed.

**E2E reproducer**: `curl localhost:8000/v1/audio/transcriptions -F model=moss -F file=@clip.wav -F temperature=0 -F hotwords="珞珈数科, 钛动科技"`. Before the patch the output was identical to sending no hotwords; after, it is identical to writing the model card recipe into `prompt` by hand (洛嘉数科 -> 珞珈数科). Outputs without hotwords are unchanged.

**Public biasing benchmarks** (real speech, short relevant lists):

| benchmark | metric | no hotwords | `hotwords` |
|---|---|---|---|
| Aishell1-NE, 808 utts | CER / hard-hotword recall | 6.46% / 18.3% | **2.54% / 93.8%** |
| LibriSpeech test-clean, N=100 | WER / B-WER | 2.23% / 9.45% | **2.02% / 5.05%** |
| LibriSpeech test-other, N=100 | WER / B-WER | 4.93% / 21.54% | **3.83% / 10.39%** |

## Details

- **Root cause**: #39674 added `TranscriptionRequest.hotwords` and `SpeechToTextParams.hotwords`, but each model must map it into its own prompt format; the MOSS implementation (#47729) never read the field.
- **One hint for all languages**: the model card has a Chinese default instruction with `热词提示：` and an English variant with `Hotwords:`. On English audio, the Chinese default with `热词提示：` beat the English recipe on both LibriSpeech sets (B-WER 5.05% vs 6.16% and 10.39% vs 12.43%) and had far fewer runaways (3 vs 23 and 1 vs 17), so there is no per-language switch.
- **The list is passed through verbatim** (stripped) rather than re-joined, matching how Fun-ASR treats the same field.
- **Limitation (model behavior, not this patch)**: long lists (400 zh / 1000 en terms) cause repetition loops or leak list terms after the transcript, and accuracy drops below the no-hotword baseline even after excluding runaways. The docs now advise keeping the list short; callers can bound runaways with `max_completion_tokens`.
- **Eval caveats**: English normalization was lowercasing and punctuation stripping only, with no number normalization, so absolute numbers are not comparable to papers, but conditions are comparable to each other. Runaway filtering favors the N=1000 rows. Greedy decoding only.

AI assistance (Claude Code) was used to write the patch, tests, and evaluation scripts, and to run the validation above on my machine.
