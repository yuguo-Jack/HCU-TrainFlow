# [Bugfix][KV Offload][P2P] Stop DEALER monitor before closing its reader

[Upstream PR](https://github.com/vllm-project/vllm/pull/63207) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

`ZmqConnection.close()` closes the monitor's reader while the DEALER can still raise monitor events. libzmq sends those events with a blocking send from its only I/O thread, so the send never returns and every P2P control socket in the engine stops until restart; P2P lookups to all peers then wait out their 30 s deadline before falling back to local prefill. Two paths raise such an event: a DEALER kept alive by its `LINGER` after its peer stalls, and a DEALER whose TCP connect is still in progress when it is closed (a peer address with no host behind it, as after a pod leaves or a node is lost). This stops the DEALER's monitor before closing its reader. The DEALER keeps the bounded 500 ms `LINGER` from #63708, so a final `DisconnectMsg` still reaches the peer.

Found while qualifying the P2P tier for a GLM-5.3 P/D deployment. Rebased on #63708, which bounds the DEALER `LINGER` at 500 ms; the wedge reproduces on main with that linger.

## Claims

- A peer that stalls for longer than the ZMQ heartbeat timeout (10 s) no longer wedges the P2P control plane; lookups resume once the peer answers again.
- A request naming a peer address that never answers the SYN no longer wedges the control plane; the request still waits the 30 s handshake deadline, then prefills locally.
- No behavior change for connections that close normally. A `DisconnectMsg` sent right before `close()` still reaches the peer, including on a connect still in progress.

## Details

Mechanism in libzmq 4.3.5 (`src/socket_base.cpp`, `src/stream_connecter_base.cpp`):

1. `socket_base_t::event()` takes `_monitor_sync` and calls `monitor_event()`, which sends each event to the monitor's PAIR socket with a blocking `zmq_msg_send` (no `ZMQ_DONTWAIT`). These calls run on the I/O thread.
2. Once the reader PAIR is closed, that send never returns. The context has one I/O thread, so the ROUTER and every other peer's DEALER stop moving messages, and `ctx.term()` at shutdown hangs.
3. Stall path: `zmq_close` hands a DEALER with queued messages to the reaper, which keeps it reconnecting for the `LINGER` period; each reconnect or handshake failure raises an event. The 500 ms `LINGER` from #63708 bounds that window, and an event inside it still blocks the I/O thread (`close_with_unsent_message` fails on main).
4. No-host path: a connect still in progress is torn down at close. `stream_connecter_base_t::process_term()` calls `close()`, which closes the socket and raises `EVENT_CLOSED` (in vLLM's mask) before the DEALER's monitor is stopped. This happens with any linger.
5. `disable_monitor()` is `zmq_socket_monitor(s, NULL, 0)`, which runs `stop_monitor()` under `_monitor_sync`: it closes the internal PAIR and clears `_monitor_events`, so no event is sent after the reader closes. With the bounded `LINGER`, a dead session's DEALER stops reconnecting to its peer after 500 ms.
6. `disable_monitor()` waits for `_monitor_sync`, which the I/O thread holds only while sending an event. That send completes: the reader is still open, and its pipe (default HWM) holds far more than the few fatal events a dead connection raises before `ZmqTransport.poll()` closes it.

Not in scope: a request naming a peer that never answers still waits the 30 s handshake deadline (`VLLM_P2P_HANDSHAKE_TIMEOUT_S`) before prefilling locally, and nothing backs off from such a peer across requests.

**Suggestion: use a short bounded linger instead of `linger=0`**

`linger=0` also drops the `DisconnectMsg` that the send-then-close callers rely on. In `_accept_new_peers`, the reconnect-backoff branch does:

```python
# Tell the peer, so its lookups fall back now rather than
# at the handshake deadline.
with contextlib.suppress(Exception):
    conn.send({TYPE_KEY: DisconnectMsg.TYPE})
conn.close()
```

That `conn` is the inbound DEALER opened in the same `poll()`, so its TCP connect hasn't finished when `close()` runs. With `linger=0` the queued message is discarded, so the rejected peer waits out `VLLM_P2P_HANDSHAKE_TIMEOUT_S` (30 s), which is what that comment is there to prevent. `session.close()` sends the same message the same way, so it's exposed when the session is new or the peer is slow.

I measured this with two `ZmqTransport`s on one host (pyzmq 27.1.0, libzmq 4.3.5). Each trial sends `DisconnectMsg` and then calls `close()`, and counts whether the peer's ROUTER receives it within 1–3 s:

| `close()` variant | right after `connect()` | on an established connection |
|---|---|---|
| main (default linger) | 30/30 | 30/30 |
| this PR (`linger=0`) | **0/30** | 30/30 |
| `disable_monitor()` + `linger=500` | 30/30 | — |

With `disable_monitor()` + `close(linger=500)`, both new tests pass 3/3 locally. I didn't use the default infinite linger: `disable_monitor()` with the default linger hangs `test_close_with_unsent_message_keeps_transport_usable` in 3/3 runs, so some limit is needed.

So I'd suggest something like:

```python
# Bounded so a final DisconnectMsg still flushes, including on a connect
# still in progress, without leaving a DEALER reconnecting to a dead peer.
self._sockets.dealer.close(linger=_CLOSE_LINGER_MS)
```

with `_CLOSE_LINGER_MS = 500` next to the heartbeat constants. `close()` still returns immediately; only the background teardown waits, for at most 500 ms.
