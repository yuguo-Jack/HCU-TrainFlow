# [ROCm][Perf] Use AITER top-k for the DeepSeek-V3.2/GLM-5 sparse indexer

[Upstream PR](https://github.com/vllm-project/vllm/pull/61943) · state: closed · merged: True

## Original PR description



## Overview

On gfx950 with AITER enabled, the uncompressed sparse indexer of DeepSeek-V3.2 and GLM-5.x (`index_topk` 2048) now takes AITER's top-k for decode and for prefill chunks whose longest row reaches 32K tokens, through the adapters #52882 added for DeepSeek-V4. Related: #55327, #50470, #46172, #60012.

## Claims

- GLM-5.2-MXFP4, MI355X, TP4, `--max-model-len 133120`: 128K/1K TPOT -7.0% / -4.6% / -3.0% at c1 / c8 / c16, MTP3 c8 -3.0%; 8K/1K within noise; gsm8k and passkey unchanged.
- DeepSeek-V3.2, TP4, default max_model_len (163840): 128K/1K c1 TPOT -15.6%, 4K/1K c16 -1.1%, 4K/1K c1 +0.7% (+0.085 ms); gsm8k unchanged.
- Compressed indexers, other `index_topk`, GLM-5.3-Flash kpool, gfx942, AITER off and non-ROCm are unchanged.

## Details

- Gate: compress ratio 1 and k=2048 only. Decode always takes AITER (FULL graphs are not keyed by context length); prefill when `chunk.max_seqlen_k`, a host int, reaches 32K.
- Cost: with max_model_len between 131072 and 200000 and up to 48 rows, AITER loses 3-6 us per layer below 8-16K context. DeepSeek-V3.2 (default 163840, 61 indexer layers) measures +0.085 ms TPOT at 4K/1K c1. Keeping the in-tree kernel for that width band would also give up the 2.53 ms gain at 128K on the same deployment, so the gate does not exclude it.
- Not measured end to end: GLM-5/5.1, TP8. CI (MI300, NVIDIA) runs only the new selection test; the GPU tests need gfx950.

<details>
<summary>Design notes, pre-existing failure and related PRs</summary>

- Cause: the in-tree decode kernel has gfx950 policies only for k=512 and k=1024 (#55327). At k=2048 its cost grows with context; AITER's stays near flat.
- Semantics come from #52882's wrappers. ROCm DSA decode carries `(B, next_n)` bounds for native MTP1 and one row per token otherwise, so `seq_lens.reshape(-1)` with `next_n=1` gives AITER each row's exact end. Prefill turns AITER's chunk-global indices into sequence-local ones and keeps `-1`.
- Decode is not split by context length because a FULL graph replays one kernel for every length. Eager decode could use the length, but would then pick a different kernel for the same shape depending on graph mode. AITER's extra host time per call only shows in eager steps.
- `test_aiter_decode_topk_matches_per_row_under_mtp` (from #58167, `requires_gfx950`, so not in CI) fails identically on main: it passes `(B, 1)` seq_lens with `next_n=4` to the in-tree k=512 gfx950 kernel, which reads any 2-D `seq_lens` per row, so its reference rows are wrong. It does not reach the code changed here.
- #60012 (open) tunes the in-tree k=2048 kernel above 200000 columns for #55327. With this PR it still serves AITER-off deployments and short prefill chunks; the gate should be re-measured if it lands. #57844 (open) edits the same selector. #59421 (draft, native MTP above `next_n=2`) is compatible because decode flattens the bounds.
- #50470 (draft) and #46172 also move the k=2048 decode top-k to AITER. Both have merge conflicts and no activity since 2026-08-22, and both swap the call unconditionally, passing vLLM's `next_n` with its 2-D MTP bounds. On both, the author of #52882 noted that AITER v0.1.19 needs those bounds adapted and asked to treat #52882 as the consolidated direction; #52882 then merged with AITER enabled for compressed indexers only. This PR applies its adapters to the k=2048 path, adds prefill and serving results, and leaves every other indexer unchanged. The `aiter.top_k_per_row_decode` entry point that #50470 waited for ships in AITER 0.1.25 and is the function called here.
- Duplicate search, `gh pr list --state all --search`: "aiter topk", "top-k ROCm", "topk ROCm", "indexer ROCm", "indexer aiter", "DeepSeek-V3.2 ROCm", "GLM-5 ROCm", "sparse indexer AMD", "top_k_per_row_decode", "top_k_per_row_prefill", "compress_ratio aiter topk".
