# [Rust Frontend] Accept FastAPI boolean spellings on dev route query parameters

[Upstream PR](https://github.com/vllm-project/vllm/pull/65372) · state: closed · merged: True

## Original PR description



## Overview

Accept FastAPI's boolean spellings on the Rust frontend's dev and RL route query parameters, so `requests.post(f"{url}/pause", params={"clear_cache": True})` works as it does against the Python frontend instead of returning 400.

## Claims

- `clear_cache` on `/pause`, `reset_running_requests` and `reset_external` on `/reset_prefix_cache`, and `include_dp` on `/get_world_size` accept `true`/`t`/`yes`/`y`/`on`/`1` and `false`/`f`/`no`/`n`/`off`/`0`, case-insensitively, like FastAPI.
- Any other value is still rejected with 400.

- With the routes back on plain `bool`, the four tests fail (the route tests with 400 instead of 200, the table test on `True`).
- No real model or live server was run; the change is limited to query parsing.

## Details

**Root cause.** The Python routes declare these parameters as `bool` query parameters, which FastAPI parses with pydantic's lenient coercion. The Rust routes declared them as plain `bool` under axum's `Query`, and serde only takes lowercase `true` and `false`. `requests` encodes Python's `True` with `str()`, i.e. `True`, so a call that works on Python gets a 400 on Rust. Python's own RL test helpers send exactly this (`tests/entrypoints/rl/conftest.py`: `pause(..., clear_cache=...)`, `get_world_size(..., include_dp=...)`). `httpx` sends lowercase and is not affected.

**Change.** One `deserialize_query_bool` in `vllm-server`'s `utils`, next to `utility_call_error` which the same handlers already use, applied to the four fields of `PauseParams`, `ResetPrefixCacheParams` and `WorldSizeParams`. Nothing below the routes changes. These are the only boolean query parameters on routes the Rust frontend serves.

**Why only query parameters.** JSON request bodies are typed: clients encode a boolean as `true`/`false`, so pydantic's leniency there (accepting `"True"`, `"yes"`, `1` for a `bool` field) is never exercised by a real client, and the Rust bodies stay strict. A query string is untyped text whose spelling is chosen by the client library, which is where the difference shows up.

**Behavior left as is.**

- An invalid value is a 400 on Rust and a 422 on Python, as for other invalid query values.
- `/pause` reports `param: "mode"` for every query error, now including an invalid `clear_cache`; this mapping predates the PR.
- A repeated key (`?a=1&a=0`) is a 400 on Rust; Python takes the last value.

**Python tests.** `tests/entrypoints/rl/state_transitions/test_pause_resume.py` pins `clear_cache=True` and `False`, but its fixture launches `python -m vllm.entrypoints.openai.api_server`, which never delegates to the Rust frontend, so it cannot cover this path without a fixture change, which is out of scope here.

Not a duplicate: no open PR changes query parsing on the Rust dev routes (searched open PRs for `clear_cache`, `query bool`, `boolean query`, `reset_prefix_cache`). vllm-project/vllm#64900 adds a `preserve_running_requests` query parameter on the Python side only; it does not overlap.
