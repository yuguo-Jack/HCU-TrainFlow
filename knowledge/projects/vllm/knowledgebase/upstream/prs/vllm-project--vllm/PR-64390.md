# [Bugfix][Rust Frontend] Rust vllm-bench accepts --max-concurrency 0 and hangs forever (Python rejects it since #54887)

[Upstream PR](https://github.com/vllm-project/vllm/pull/64390) · state: closed · merged: True

## Original PR description

Fixes #64319.

Rust `vllm-bench` accepted `--max-concurrency 0` and then hung forever on `Semaphore::new(0)`, while Python `vllm bench serve` rejects 0 since #54887. This change rejects 0 fail-fast on every Rust bench path that builds a concurrency semaphore:

- Serve path (`config.rs`): `--max-concurrency 0` and `--multi-turn-concurrency 0` are rejected with a clear error instead of hanging.
- Sweep path (`sweep.rs`): any 0 in `--sweep-max-concurrency` is rejected before the first sweep point runs.
- `mm-processor` path (`mm_processor.rs`): `--max-concurrency 0` is rejected at the entry point, before the managed engine is spawned, since this subcommand does not go through `BenchConfig::from_args`.

Why this is not duplicating an existing PR: a search for open PRs mentioning #64319 returns only this PR, and #64319 itself has no linked PR.

Tests run:
- `cargo test -p vllm-bench --lib`: 191 passed, 0 failed, 12 ignored.
- `cargo test -p vllm-bench --lib concurrency`: 8 passed, 0 failed (the zero/positive max-concurrency, multi-turn, and sweep cases).
- `rustfmt` clean under the workspace `rustfmt.toml` (style edition 2024, chain width 80).

No output, accuracy, or serving behavior changes, so no model evaluation results apply. No new CLI args or defaults, so no documentation update is needed.

AI-assistance disclosure: AI assistance was used in preparing this change.
