# [Responses] Normalize OpenResponses input items to match openai-python SDK requirements

[Upstream PR](https://github.com/vllm-project/vllm/pull/35508) · state: closed · merged: True

## Original PR description

## Overview

Accept incomplete assistant and reasoning history in Responses API requests without losing turns or crashing on empty assistant content. Related to #33089 and openai/codex#12669.

## Claims

- Fill missing assistant/reasoning fields through the existing `input_item_parsing` validator, preserving supplied metadata and non-assistant inputs.
- Preserve the message discriminator so typeless assistant turns retain their content.
- Handle empty tool-only assistant turns and keep dict-form reasoning/assistant merging consistent with typed items.
- Preserve current tool-schema validation when integrating upstream changes.

## Details

The validator normalizes raw dictionaries before SDK object construction. The conversion changes handle typed or dict-form history later, including empty assistant content. This follows the review suggestion to reuse `input_item_parsing`; it does not add a parallel entry point. The empty-content and dict/model merge-policy reports in this discussion are addressed in the same history-conversion path.

The latest main integration retained upstream tool-schema validation. This continues the existing PR and its issue scope rather than opening a competing implementation. AI assistance was used for implementation, upstream integration, tests and this description.

## Additional issues discovered during E2E testing

While adding E2E tests (`test_input_history_openai_shape_e2e`, etc.), the server returned 500 errors, which led to discovering and fixing two additional issues.

### 1. `utils.py` — dict-form reasoning items unhandled in non-harmony path (`KeyError: 'role'`)

Non-harmony models (e.g. Qwen3) use `_construct_single_message_from_response_item()` in utils.py to convert input items. This function only performed Pydantic model isinstance checks (`isinstance(item, ResponseReasoningItem)`, etc.), but when Pydantic parses the `ResponseInputItemParam` TypedDict union, input items may remain as **plain dicts** rather than model instances. All checks would fail and fall through to `return item`. Since reasoning dicts have no `role` key, this caused `KeyError: 'role'` downstream.

**Fix**: Added dict-form handling for reasoning (`type == "reasoning"`) and assistant message (`role == "assistant"`) items.

### 2. `harmony.py` — improved handling for items with missing type field

Changed `response_msg["type"]` direct access to `.get("type")` and added fallback heuristics: presence of `"role"` key → message, presence of `"summary"` key → reasoning. Also made `content` access on reasoning items safe via `.get()` with an empty assistant message fallback.

### 3. Pydantic `ValidatorIterator` issue

TypedDict `Iterable` fields (`summary`, `content`) may remain as `ValidatorIterator` (lazy iterator) after Pydantic parsing, causing `TypeError: object of type 'ValidatorIterator' has no len()`. Fixed by materialising with `list()` before indexing.

Finally tested all e2e test (test_simple.py) in my local enviroments. Please take a look @chaunceyjiang. Thanks for suggesting e2e tests.

Thanks for the review @chaunceyjiang!

Yes, `input_item_parsing` is exactly the function this PR is modifying — not adding a parallel one. The change extracts the per-item normalization into a new static helper `_normalize_openresponses_input_item` and routes `input_item_parsing` through it, so the entry point stays the same.

Two reasons for the refactor:

1. **Stricter "missing field" detection.** The original code only filled `id` when `"id" not in item`, but the OpenResponses payloads I hit in production also send `id=None` and `id=""`. Same for `status`. The helper now treats all three (missing / None / empty string) as needing a default, so SDK validation no longer rejects them.
2. **Reasoning item `summary` default.** The original only normalized `id` on reasoning items; an OpenResponses-conformant request can omit `summary` entirely, which the openai-python SDK rejects. The helper now defaults `summary=[]` when it's None.

Separately, the `utils.py` change is a different layer that `input_item_parsing` can't cover:

- `input_item_parsing` is a Pydantic `@model_validator(mode="before")` hook — it runs on **raw dicts before** model construction.
