# [Doc] Add startup-cache-image agent skill

[Upstream PR](https://github.com/vllm-project/vllm/pull/65244) · state: open · merged: False

## Original PR description

## Overview

Add a contributor skill for generating vLLM compilation caches, baking them into a pinned image, and checking a fresh container loads them and preserves inference outputs.

## Claims

- Uses existing public cache interfaces; adds no cache implementation or serving behavior.
- Connects generation, portable-cache staging, image building and verification in one discoverable agent workflow, with the standard Claude symlink.
- Corrects the linked Docker/security guidance: Triton's cache is not always redirected under `VLLM_CACHE_ROOT`.

## Validation

A fresh agent exercise produced a runnable procedure, followed by a real GPU/image roundtrip using stock `vllm/vllm-openai:v0.33.0`, pinned to the linux/amd64 digest `sha256:91ee972ab751fb7180bc71c175865e36b091686600dca783d52b2511399810b3`. Installed cache-related source files matched image build commit `4ba787ec9959e566d3b587a796dff07673324da5` (PyTorch 2.14.0+cu130, Triton 3.8.0).

The same serving command ran on two matching B300 nodes, with a fresh container for verification:

```bash
vllm serve Qwen/Qwen3-0.6B \
  --revision c1899de289a04d12100db370d81485cdf75e47ca \
  -tp 1 --port 18765 --max-model-len 4096 \
  --max-num-seqs 16 --gpu-memory-utilization 0.25
```

Generation and serving used Slurm/enroot. The bake used an actual `docker build --platform linux/amd64` on an arm64 build host, then converted that built image for enroot. Model weights stayed on a separate mount. `VLLM_CACHE_ROOT=/root/.cache/vllm` and DEBUG logging were held fixed; AOT/mega compilation resolved enabled, and verification added `VLLM_FORCE_AOT_LOAD=1`.

- **Generation:** saved one AOT model and three compiled artifacts; three greedy requests repeated with identical text, finish reasons and token counts.
- **Fresh-image verification:** loaded the matching AOT model, reconstructed all three artifacts with cache-hit evidence for all 29 submodules, and produced the same outputs. No expected-region compilation markers or cache-hiding mounts were observed; the baked compile tree matched the staged context.
- **Negative control:** masking the baked cache with an empty directory, with force-loading still enabled, exited before readiness with the missing AOT artifact error.

The generation job initially failed during staging because `cp -a` could not preserve metadata on NFS. Its serving/cache-generation checks had passed. The original cache was retained and transferred with GNU tar without ACL restoration; all 353 staged payload files matched the original fingerprints, with POSIX modes and timestamps preserved before baking. The skill now names this fallback and requires checking the extracted metadata. The actual Docker build and subsequent positive/negative GPU checks passed after that recovery; no GPU generation rerun was needed.

This validates one root-user, linux/amd64 AOT/mega configuration, using enroot for GPU containers. Docker's GPU runtime, non-root images, arm64 serving, other models and the non-mega path were not exercised. The output comparison is a three-request consistency smoke, not a model-accuracy evaluation. No repeated startup benchmark or speedup claim.

## Details

Existing documentation covers cache persistence and copying. This skill joins preparation, packaging and verification into a workflow agents can discover. Open-PR searches for `startup-cache-image` and warm-image skills found no equivalent workflow.

Source review and the agent-use/runtime trials tightened the instructions: pin the target platform, stage portable cache subtrees rather than host probe results, inventory external kernel caches, check expected worker/graph coverage rather than one hit line, and compare outputs while the server is running. The linked cache-path docs now agree with the observed compiler behavior.
