# [ROCm][Kernel] Support persistent_topk on ROCm

[Upstream PR](https://github.com/vllm-project/vllm/pull/63847) · state: open · merged: False

## Original PR description

- Build `persistent_topk`, its FilteredTopK and sampled_topk tiers, and the shared exact overflow recovery from #62936 with hipcc (wave64-safe `TOPK_*` ballot/shuffle macros, HIP acquire load, clang-compatible `exact_topk_rescan` defaults).
- On gfx950 (at least 144 KiB of LDS), run every batch through `sampled_topk_kernel`, one workgroup per row, and cut clustered rows at the exact sampled rank. gfx942 keeps the persistent kernel. Return early on an empty batch.
- Place the decode logits of `rocm_fp8_paged_mqa_logits` after the top-k workspace, so `persistent_topk`'s row states no longer overwrite them.
- Allow the explicit `persistent` sparse-indexer backend on ROCm; `auto` still resolves to `per_row`.
- Route `cooperative` / `persistent` through `SparseIndexerTopk._row_ends`, so `(B,)` `seq_lens` with `next_n > 1` no longer raise "lengths size mismatch".
- Run the `persistent_topk` tests on ROCm, including #62936's candidate-overflow cases, add a test for the logits overlap, and add `persistent` to `benchmark_top_k_per_row_decode.py`.
- Document `persistent` on ROCm in the `KernelConfig` docstring, and run the persistent top-k tests in the MI355 DeepSeek V4 kernels step (MI300 already runs the file).

On ROCm the sparse indexer could only use the in-tree `per_row` top-k or AITER, and asking for `persistent` failed because the op was compiled out. This PR builds it on top of #62936, which is now merged and makes the persistent and filtered paths exact on candidate overflow, so the ROCm-only rescan forks from earlier revisions are gone and ROCm shares that code. Wiring it into GLM-5.3-Flash showed that its decode logits and the top-k workspace both start at offset 0 of the shared workspace, which corrupts row 0 whenever the multi-CTA path runs (gfx942). CUDA is not affected, because its paged MQA logits are not workspace views, and ROCm on main is not either, because it rejects this backend. The backend stays opt-in, so default ROCm top-k selection does not change, but on gfx942, gfx950 and RDNA the decode logits now sit 1 MiB further into the workspace for every backend. On MI355X with k=2048 it is 2.2-2.6x faster than `per_row` and on par with AITER, and in GLM-5.3-Flash serving on this revision it selects exactly what `per_row` selects, with unchanged GSM8K 25-shot accuracy and throughput. This branch is stacked on #62298 (head b47c6178f1), so until that merges the diff against main includes #62298; this PR's own changes are `a2f04ca777..11871cef49` and `2fe6f7e5df`, plus merges of main and #62298.

After merging main (b4a0830f66) and #62298's head (85e0eae614), the persistent group gave the same 206 passed, 50 skipped in all 10 runs, the AITER group the same 1 failed, 403 passed, and the sparse-attention group 177 passed, 271 skipped (main added tests), with one failure in `test_sparse_backend_decode_correctness[...-large_q_pure_prefill-ROCMAiterMLA]`. That test feeds synthetic top-k indices to the attention backend, never reaches this PR's code, and failed 1 of 10 times when looped alone.

The skips in the persistent group are CUDA-only, cooperative, FlashInfer and DeepSelect cases. A randomized `SparseIndexerTopk("persistent")` stress run compared values against `torch.topk`: 2,000 cases, 0 failures (k ∈ {512, 1024, 2048}, 0-64 requests, `next_n` 1-4, 1-D and 2-D `seq_lens`, empty batches, NaN/inf, ties, clustered rows). The ROCm-only clustered-rows test from the previous revision (16K, 32K and 128K rows of `randn * 0.01 + 3`, every case failed before) passes on #62936's shared paths, so it was dropped in favour of #62936's overflow test. Because gfx950 always dispatches to `sampled_topk`, some re-enabled tests (for example `test_persistent_topk_reused_group_after_short_row` and `test_persistent_topk_sampled_graph`) pass there without reaching the persistent kernel; the multi-CTA paths get real coverage on MI300 CI and in the gfx942-dispatch runs below. Validation covers gfx950 (MI355X) and gfx942 (MI300X); RDNA (wave32) compiles and admits the backend but was not tested.

**gfx942 dispatch (persistent kernel).** On MI300X (`sharedMemPerBlockOptin` is 64 KiB, so the persistent kernel runs instead of `sampled_topk`), the persistent group gave 176 passed, 80 skipped in 10 of 10 runs; the skips are the sampled-top-k tests that need 144 KiB of LDS and the CUDA-only backends. Before MI300X was available, a local build that capped `max_smem_per_block` and occupancy at 64 KiB on MI355X gave the same counts, and the stress run on it gave 2,000 cases with 0 failures. The cap was never committed.

**Logits overlap.** `rocm_fp8_paged_mqa_logits` returned its logits at workspace offset 0, the same place `SparseIndexerTopk` takes the `persistent_topk` workspace from. On the multi-CTA path the op clears its per-group row states there (`cudaMemsetAsync` in `topk.cu`) and then keeps barrier counters and histograms in them. In GLM-5.3-Flash serving with gfx942 dispatch this made 17,346 of 18,964 calls return wrong rows, all in row 0. The logits now come from the same `get_simultaneous` call as a top-k slot in front of them, and the profiling reservation uses the same layout. `test_persistent_topk_on_rocm_paged_mqa_logits` changed 3,088 logits (four groups' row states) with gfx942 dispatch before the fix and none after. On MI300X the test fails the same way with the logits moved back to offset 0 and passes with the fix:

```
pytest tests/kernels/test_top_k_per_row.py -k test_persistent_topk_on_rocm_paged_mqa_logits   # MI300X
1 failed: Tensor-likes are not equal! Mismatched elements: 3088 / 327680 (0.9%)   # logits at offset 0
1 passed                                                                          # this PR
```

Native gfx950 never runs that path, so there it passes either way; ROCm CI runs `test_top_k_per_row.py` on MI300, and the persistent group on MI355.

**End to end, GLM-5.3-Flash (amd/GLM-5.3-Flash-Quark-MXFP4, TP2, MI355X, AITER on, `FULL_AND_PIECEWISE` graphs, k=512 under kpool 4), on this revision (11871cef49) against its base (1966abc5b2).** For this model, prompts of at most 2,048 tokens never reach the top-k: both decode (`_fill_short_decode_causal_indices`) and prefill (`short_prefill`) fill every causal index and skip it. GSM8K 5-shot (at most 1,521 tokens) and a 1K/1K bench therefore cannot tell the backends apart, so accuracy is compared on GSM8K 25-shot (3,289-5,091 tokens; every request runs the top-k).
- Exactness: an in-model hook re-ran `per_row` on a pre-call copy of the logits for every `persistent` call and compared the selected values per row. It found 0 mismatching rows in 6.94M decode rows per TP rank (2.51M without MTP, 4.43M with MTP 3-token speculation; GSM8K 25-shot plus 1K/8K/32K serving). Fewer than 0.01% of rows pick a different index among tied values.
- The same check with gfx942 dispatch (the 64 KiB LDS cap described above) found 0 mismatching rows in another 4.48M decode rows per rank, including 140K-token prompts with MTP that take the radix path. A capped server with graphs completed 1K/8K/32K serving and 8 of 8 140K-token requests with no fault.
- GSM8K 25-shot (flexible-extract), default vs `persistent`: 0.9295/0.9287 vs 0.9295/0.9265 over two runs each.
- Default backend, this PR vs base, serving throughput (tok/s) and mean TPOT (ms): 1K/1K at c=32 1837.0 vs 1843.6 and 16.53 vs 16.52; 8K/1K at c=16 844.3 vs 844.5 and 16.12 vs 16.01; 32K/1K at c=8 385.8 vs 387.0 and 15.34 vs 15.20. The new logits offset did not trip the locked workspace.
- `persistent` vs default on this PR: 8K/1K 851.3 vs 844.3 tok/s (TPOT 15.80 vs 16.12 ms) and 32K/1K 386.9 vs 385.8 tok/s (15.13 vs 15.34 ms). With MTP (both servers measured side by side on other GPUs): 865.3 vs 863.2 and 405.8 vs 414.0 tok/s.
- MI300X (gfx942, native persistent kernel), same model at TP2 on e707c976bd: the same check found 0 mismatching rows in 2.51M decode rows per rank and in 2.76M with MTP, including 140K-token prompts on the radix path. GSM8K 25-shot, `per_row` vs `persistent`: 0.9196/0.9257 vs 0.9196/0.9166. With graphs, `persistent` completed 8K/32K serving and 8 of 8 140K-token requests with no fault, at 73.5 vs 72.3 tok/s (8K/1K) and 36.6 vs 36.1 tok/s (32K/1K) against `per_row`. Decode takes about 210 ms per token for both backends on this node, so these throughput numbers say little about the top-k itself.
- On the previous revision, the radix path with gfx942 dispatch and 135K-190K-token prompts showed 0 wrong rows in 5.28M checked radix rows with #63475, and 37 of 37 benchmark runs completed. Without #63475 there were 107-137 wrong rows per 2.6M, and every server died with a GPU memory access fault within minutes. Those runs gave `persistent_topk` a private copy of the logits to keep the overlap above out of the measurement.

**Intermittent corruption seen on 2026-10-24.** In an earlier round, 8 of 144 test runs failed with buffers corrupted that the op never writes. It did not reproduce in more than 400 later runs, including every run above. The dumps showed corruption in buffers written before the op ran while the op was exact on what it read, so it is attributed to the environment during a busy window on the shared node, and it is being retested on ROCm 10.

Against the previous revision with the ROCm-only forks, #62936's shared paths are 5.7% slower on randn (mostly 32K rows) and 10% faster on clustered logits.

**Duplicate check.** Searched open PRs for `persistent_topk ROCm`, `persistent topk hip`, `ROCm sparse indexer topk`, `rocm_fp8_paged_mqa_logits workspace`, `topk workspace alias`, `_row_ends`, `lengths size mismatch` and `sampled_topk`:
- #50470 routes sparse-indexer decode top-k through AITER, a different backend that complements this one.
- #55122 changes how `persistent_topk` selects ties on CUDA and does not build it for ROCm.
- #38704 moves ROCm sparse-indexer allocations into the workspace manager and does not touch the top-k workspace.
- #41748 replaces the `cudaMemsetAsync` of the row states in `topk.cu` with in-kernel cleanup. It does not build for ROCm or move the logits, but it touches the same code and will need a rebase against whichever lands second.

No open PR builds `persistent_topk` for ROCm, fixes the logits overlap or fixes the `_row_ends` routing.
