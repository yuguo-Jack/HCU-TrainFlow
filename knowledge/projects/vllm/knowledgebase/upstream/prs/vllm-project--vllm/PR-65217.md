# [Spec Decode][MRV2] Load only the context K/V weights of DFlash drafters on prefill instances

[Upstream PR](https://github.com/vllm-project/vllm/pull/65217) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

On a P/D prefill instance (`kv_role="kv_producer"`), a DFlash/DSpark drafter only needs to store the context K/V that the decode instance reads. This PR makes such an instance schedule no drafts, reserve no lookahead KV slots, capture no draft CUDA graphs, and free the draft weights that only the query pass reads. It follows #62784 (per-step K=0) and takes its lookahead and speculator-flag handling from #56957.

Related: #62923 does the same for Qwen3 DSpark only, behind an opt-in flag with a separate model class. #56957 adds a DSpark prefill-only mode for PP > 1 with non-NIXL connectors and the DeepSeek-V4 draft. This PR covers the general case and keeps `num_speculative_tokens` unchanged, because it also sizes target state the decode instance loads (e.g. the Mamba conv state).

Since this PR takes similar approaches, the authors of #56957 (@lucifer1004) and #62923 (@LLLZeSheng) are added as co-authors.

## Claims

- Prefill instance with a `dflash`/`dspark` drafter (MRV2): no draft tokens scheduled, no lookahead KV slots, no draft CUDA graphs, draft-logits cache or warmup spec-decode steps. Requests that decode there run without speculation.
- Draft models that declare `context_kv_modules()` free every other draft weight after loading. Qwen3 DFlash, DSpark, DFlash2, XPress, Gemma4 DSpark, MiniMax-M3 DSpark and Muse Spark DSpark declare it; other drafts keep their weights.
- Prefill KV cache on one GB300: +5.0% tokens for Qwen3.8-27B + DSpark, +2.9% for Qwen3-8B + DFlash.
- Decode outputs and acceptance do not change. `kv_both`, `kv_consumer`, non-P/D instances and MRV1 are unchanged.

## Validation

1P1D over `NixlConnector` on one GB300 node, `main` (`b8c04dd3b4`) and this PR side by side, 24 greedy chat requests:

| Pair | Prefill weights | Prefill KV cache | Decode outputs | Decode drafts / accepted |
|---|---|---|---|---|
| `Qwen/Qwen3-8B` + `z-lab/Qwen3-8B-DFlash-b16` (k=16) | 17.3 → 15.5 GiB | 209.3 → 215.5 GiB | 24/24 identical | 1,391 / 3,374 in both |
| `Qwen/Qwen3.8-27B` + `RedHatAI/Qwen3.8-27B-speculator.dspark` (k=8)\* | 55.3 → 52.0 GiB | 167.5 → 175.8 GiB | 24/24 identical | 1,200 / 3,349 in both |

\* Both stacks include #64059; on `main` this draft accepts almost nothing under FULL CUDA graphs.

A prefill instance with DP=2 and an idle rank works, and requests sent straight to it decode without speculation.

Weight freeing per draft model (dummy weights, public configs): the context K/V written before and after freeing is byte-identical for every draft listed above (both MiniMax-M3 paths). A model without its own declaration frees nothing. With the inherited base list instead of their overrides, Gemma4, MiniMax-M3 and Muse Spark fail.

- njhill · comment · 2026-11-03T02:56:30Z · [source](https://github.com/vllm-project/vllm/pull/65217#discussion_r4450458913)

File: `vllm/config/vllm.py` · line 650

This brings back gating on method names, which #63205 removed: behavior should be read from `speculative_config.speculator_config`, not from `use_dflash()` / `use_dspark()`. In practice:
- A custom speculator registered on a `DFlashSpeculatorConfig` subclass gets `method="dflash"`, so it's opted in silently even if its `speculator_class` doesn't inherit from `DFlashSpeculator` and doesn't implement this mode.
- A speculator that isn't DFlash-based can't opt in without editing `VllmConfig`.

Could this be a capability on the config instead, e.g. `supports_context_kv_only: ClassVar[bool] = False` on `SpeculatorConfig`, set to `True` on `DFlashSpeculatorConfig`? This property would then just combine that with the KV role and `use_v2_model_runner`.

- njhill · comment · 2026-11-03T02:56:30Z · [source](https://github.com/vllm-project/vllm/pull/65217#discussion_r4450458920)

File: `vllm/v1/core/sched/scheduler.py` · line 1711

This mode is applied at five separate call sites, each reading `vllm_config.draft_context_kv_only`: the `num_lookahead_tokens` override, here, `warmup.py`, the `DraftModelSpeculator` base, and `DFlashSpeculator`. It also puts P/D- and DFlash-specific logic in the core scheduler.

Could the mode be resolved once instead (e.g. an `init=False` field on `SpeculativeConfig` set in `VllmConfig` post-init from `kv_transfer_config`), with the speculator config's properties reflecting it? `DFlashSpeculatorConfig.num_lookahead_tokens` would return 0, so `VllmConfig.num_lookahead_tokens` would need no special case. The scheduler and warmup would read one generic speculator-config property for drafts scheduled per step, rather than a DFlash/P-D flag. (`proposes_draft_tokens` might be reusable for this if it became a property instead of a `ClassVar`.) That would also make it clear why `num_speculative_tokens` itself stays unchanged.

- njhill · comment · 2026-11-03T02:56:30Z · [source](https://github.com/vllm-project/vllm/pull/65217#discussion_r4450458926)

File: `vllm/model_executor/models/qwen3_dflash.py` · line 977

The opt-in here has three layers: the `type(self.model).__dict__` check, the class-attribute aliases in subclasses (`context_kv_modules = DFlashQwen3Model.context_kv_modules` in dflash2/dspark/xpress), and the `hasattr(self.model, "context_kv_modules")` check in the speculator. It's easy to get wrong.

Simpler: make the base `DFlashQwen3Model.context_kv_modules()` return `None` (keep all weights), move the shared list into a helper (e.g. `_qwen3_context_kv_modules()`), and have the opted-in subclasses override the method and call it. Or, to follow the `SpeculativeDraftModel` style from #63205, a small protocol in `interfaces.py`.

- njhill · comment · 2026-11-03T02:56:30Z · [source](https://github.com/vllm-project/vllm/pull/65217#discussion_r4450458933)

File: `vllm/v1/worker/gpu/spec_decode/dflash/speculator.py` · line 255

Subclasses run setup after `super().load_model()`, so this frees weights before that setup runs. For example, `DSparkSpeculator.load_model` then calls `_try_enable_sharded_sequential_sampling()`, which inspects `self.model.lm_head`. Today that only reads attributes, but anything that later touches a freed module (EPLB, LoRA, a future weight reload) will see zero-size params and fail in confusing ways. Could subclass setup that's irrelevant in this mode be skipped (DSpark's sharded sampling, for example)? Or could the freeing be done as the last step after all `load_model` overrides, e.g. from the model runner?
