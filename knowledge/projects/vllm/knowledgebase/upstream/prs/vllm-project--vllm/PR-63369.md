# [Multimodal] Add TorchCodec image decoding backend

[Upstream PR](https://github.com/vllm-project/vllm/pull/63369) · state: open · merged: False

## Original PR description

## Overview

Add an opt-in TorchCodec image decoding backend (`--media-io-kwargs '{"image": {"image_backend": "torchcodec"}}'`) and bump the torchcodec floor to 0.16, its first release with image decoders. 1/3 of a stack: #PR2 converts tensor images for processors that need PIL so it works everywhere, #PR3 makes TorchCodec the default on the models that natively accept tensors.

## Claims

- JPEG, PNG, WebP and AVIF images are decoded by TorchCodec into CHW `uint8` tensors that HF image processors consume directly, skipping their PIL-to-tensor conversion.
- `pixel_values` are bit-identical to the Pillow backend.
- Decode + preprocessing is 1.05-1.33x faster on CPU for Qwen2.5-VL / InternVL3.5 / Mistral-Small-3.1 (see Validation).
- Default behavior is unchanged (`pil`).

## Validation

**Unit tests** (`tests/multimodal/media/test_image.py`): bit-exact parity with Pillow for JPEG/PNG/WebP/AVIF × RGB/grayscale × all 8 EXIF orientations; Pillow is used for transparency, CMYK, 16-bit, GIF, animated and non-RGB targets; limits are enforced before decoding; fallback to Pillow on TorchCodec errors (corrupt input still returns 400); hash parity; `video/jpeg` frame lists.

```
pytest tests/multimodal/media/test_image.py tests/multimodal/test_hasher.py tests/multimodal/media/test_video.py
```

**Microbenchmark**: bytes → `pixel_values` through `ImageMediaIO` and the HF image processor (1 torch thread, median of 21 interleaved runs, transformers 5.20, torchcodec 0.17):

**Model outputs**: since `pixel_values` are bit-identical, model outputs are unchanged; no GPU end-to-end serving benchmark was run (the change only affects API-server preprocessing).

## Details

- Pillow still opens the image first (header only), so the format allowlist, `VLLM_MAX_IMAGE_PIXELS` and the decoded-bytes budget are enforced before TorchCodec decodes anything; TorchCodec has no header-only probe yet.
- Images whose TorchCodec output would differ from the Pillow path stay on Pillow: transparency (TorchCodec drops alpha instead of compositing onto `rgba_background_color`), CMYK, 16-bit, animated images, and `image_mode != "RGB"`.
- AVIF is decoded single-threaded, at the same per-thread cost as Pillow (45.7 vs 44.9 ms for 1080p). Pillow's AVIF plugin uses all cores by default, so a single isolated AVIF request decodes faster with Pillow (~19 ms), but under concurrent load one thread per image avoids oversubscribing the media thread pool. GIF stays on Pillow: TorchCodec's GIF decoder is ~1.7x slower than Pillow's (single-threaded on both sides).
- Any TorchCodec exception falls back to Pillow, which either decodes the image (e.g. codecs disabled in a source build of torchcodec) or raises the usual client error.
- The hasher treats a 3D tensor in `MediaWithBytes` like a PIL image (bytes + `io_config`), so the cache key doesn't depend on the backend.
- `video/jpeg` frame lists decoded through `ImageMediaIO` are converted back to HWC.
- Packaging: floor `torchcodec >= 0.16` (CUDA/CPU/XPU); lockfiles now resolve 0.17.0. s390x builds torchcodec 0.17 with scikit-build-core (0.16+ dropped `setup.py`) and `TORCHCODEC_BUILD_IMAGE=0`, so it uses Pillow; **I couldn't build the s390x image locally**. ROCm still builds torchcodec 0.10 from source and uses Pillow.
- Limitation: some processors call PIL-only methods on images (vLLM's InternVL, DeepSeek-VL2/OCR and Step3-VL processors, remote-code ones like Kimi-VL, ...), so they fail with `image_backend="torchcodec"`. The docs say so; #PR2 converts tensors to PIL for them.
- Torchcodec bundles its own libjpeg/libpng/libwebp, so security fixes for those come through torchcodec releases.
- Duplicate check: no open PR or issue proposes TorchCodec image decoding.

- NicolasHug · comment · 2026-10-26T12:21:21Z · [source](https://github.com/vllm-project/vllm/pull/63369#discussion_r4377131960)

You're right that TorchCodec and PIL will reduce from uint16 to uint8 slightly differently:

- Pillow keeps the high byte, v >> 8. That's effectively dividing by 256 instead of 257 and truncating.
- torchcodec scales exactly and rounds to nearest: round(v * 255 / 65535), equivalent to (v * 255 + 32895) >> 16.

Strictly speaking the torchcodec behavior is closer to preserving the original values. Pillow is off by up to 0.99 of a level and torchcodec by at most 0.5.

This leads to pixel differences between PIL and TorchCodec of at most 1 in the [0, 255] range.

Models won't care, but consistency between backends might be the right move here. Waiting on e.g. @Isotr0py 's thoughts on this.
