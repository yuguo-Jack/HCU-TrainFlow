# [Bugfix][Kernel] Preserve batch invariance in Triton unified attention on SM100

[Upstream PR](https://github.com/vllm-project/vllm/pull/60531) · state: open · merged: False

## Original PR description



## Overview

Preserve batch invariance in Triton unified attention by excluding batch-invariant execution from the SM100-family large-head tuning path. The regression compares each causal query alone with the same query inside a multi-query block.

Related tracking issue: https://github.com/vllm-project/vllm/issues/27433 (this does not close the broader tracker).

## Claims

- Restores exact attention-output agreement for the tested BF16 head-size-256 SM100 configurations when batch invariance is enabled.
- Leaves batch-invariant-off tuning unchanged; head-size-512 cases are regression controls.
- Public Gemma3 checks show exact selected-token log-probability agreement after the fix. Generated-token divergence was not observed in those model checks; full speculative-serving correctness is not claimed.

## Validation

## Details

**Root cause.** With `VLLM_BATCH_INVARIANT=1`, `unified_attention` always launches the 2D kernel, so decode and speculative verification share one kernel. On SM100 with head size 256, however, the large-head tuning path is gated on `max_seqlen_q > 1`. It switches multi-query calls to `BLOCK_M=32`, `TILE_SIZE=128`, 8 warps and 2 stages, while single-query decode keeps the defaults (`BLOCK_M=16`, `TILE_SIZE=32`). The different tile and warp configuration changes the floating-point reduction order, so a token's attention output depends on how many other query tokens are in the same call. That breaks the batch-invariance guarantee: a token verified alongside speculative proposals does not match the same token decoded alone.

**Fix.** Skip the tuned path when batch invariance is enabled, so every call uses the same launch configuration regardless of query length. Behavior with batch invariance disabled is unchanged, and other GPUs and head sizes never take this path.

**Tradeoff.** With batch invariance enabled, SM100 head-size-256 prefill and verification no longer use the large-head tuning (+4.5% latency with FULL CUDA graphs in the Gemma3 check above). This matches existing batch-invariant behavior, which already trades throughput for determinism, e.g. by disabling the 3D decode kernel.

**Test.** `test_batch_invariant_multi_query_matches_single_query` runs each query alone at its causal KV length and compares the result bit-exactly with a single call over all queries (`rtol=0, atol=0`). Exact equality is the property under test, not a tolerance choice. Head-size-512 cases serve as controls because they never take the tuned path.
