# Stop non-output workers after collective RPC failures

[Upstream PR](https://github.com/vllm-project/vllm/pull/60940) · state: open · merged: False

## Original PR description

## Overview

Fixes #60928.

Stop a failed non-output worker from entering a later collective after one of the three model-step RPCs fails, without changing failure handling for other single-reply RPCs.

## Claims

- Treat failures from `execute_model`, `sample_tokens`, and `execute_dummy_batch` as fatal on non-output ranks.
- Preserve existing non-fatal behavior for `take_draft_token_ids` and other non-model-step single-reply RPCs.
- Add direct coverage for the scoped policy and a loop-level regression proving that no second RPC is dequeued after a fatal model-step failure.

## Validation

- `ruff check vllm/v1/executor/multiproc_executor.py tests/v1/executor/test_multiproc_executor.py` — passed.
- `ruff format --check vllm/v1/executor/multiproc_executor.py tests/v1/executor/test_multiproc_executor.py` — passed.
- `python -m compileall -q vllm/v1/executor/multiproc_executor.py tests/v1/executor/test_multiproc_executor.py` — passed.
- A source-level behavioral harness against the actual `WorkerProc` methods reproduced the overly broad termination before the fix, then passed after the fix for all three fatal RPCs, the non-fatal control, and the no-second-dequeue assertion.
- The targeted pytest module could not be collected on Windows because the vLLM test/runtime dependency graph includes Unix-only packages (`uvloop`, `xgrammar`, and `runai-model-streamer`). The repository-wide pre-commit bootstrap was also blocked because the Windows hook environment could not obtain `typos==1.43.5`; the Python checks above were run directly instead.
- Full upstream CI has not run because this PR still requires a maintainer `ready`/`verified` gate. No model evaluation is needed because this changes worker failure control flow, not model output or accuracy.

## Details

The root cause is that a non-output TP rank previously logged a model-step RPC exception and resumed its dequeue loop. It could then enter the next collective while peer ranks were still handling the failed step, creating rank desynchronization and a possible cross-node deadlock.

The initial implementation re-raised every single-reply RPC failure on a non-output rank. That was broader than #60928. This revision limits fatal propagation to the three model-step RPCs named by the issue and leaves all other RPC behavior unchanged.

I searched open PRs referencing #60928; this is the only one. #60401 is an open draft addressing stale reply correlation by adding RPC sequence IDs. The loop regression here asserts externally visible dequeue behavior rather than tuple layout so it remains compatible with that work.
