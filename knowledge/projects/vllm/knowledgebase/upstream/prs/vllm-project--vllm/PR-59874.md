# [Bugfix][NIXL] Time out stalled KV loads and release aborted pulls

[Upstream PR](https://github.com/vllm-project/vllm/pull/59874) · state: open · merged: False

## Original PR description



## Overview

A decode request in `WAITING_FOR_REMOTE_KVS` keeps its KV blocks until every TP worker reports it in `finished_recving`. When its READ stays `PROC`, or it is aborted while its handshake is pending, no report comes, so the blocks leak until restart and no metric moves. This adds a pull-side consumer deadline, `kv_load_timeout`, and passes aborts to the workers so a request with no READ posted releases its blocks right away.

Fixes #59872

## Claims

- An aborted request with no READ posted frees its blocks on the next step. If its handshake completes later, the worker only notifies the producer, so the prefill side still frees its blocks right away.
- A request whose READs are still outstanding after `kv_load_timeout` (default `decoder_kv_blocks_ttl`, 480 s) fails under `kv_load_failure_policy`, logs a `transfer_timeout` failure and counts in `vllm:nixl_num_failed_transfers`. Its blocks stay allocated until every handle leaves `PROC`, since a released handle can still DMA into them.
- The remote engine stays connected. Releasing it makes NIXL report the stalled READs as `ERR` while they can still write into the blocks (ai-dynamo/nixl#2338), so nothing here frees blocks on that report.
- `kv_load_timeout <= 0` disables the deadline. Push mode is unchanged.

## Details

Root cause: `Scheduler.finish_requests` defers the free of a `WAITING_FOR_REMOTE_KVS` request until `_update_from_kv_xfer_finished` sees it in `finished_recving` from every worker. A worker reports it only when `_pop_done_transfers` sees all of its handles leave `PROC`, which has no deadline, and the abort never reaches the worker. On a deployment with TP2 decode and PCP8 prefill this left about 11 aborted requests per day on one decode rank, and KV usage reached about 97% with `vllm:nixl_num_failed_transfers` at 0. Details in #59872.

Abort: `NixlPullConnectorScheduler` tracks the requests it parks in `WAITING_FOR_REMOTE_KVS` and sends one in `reqs_to_abort` when it finishes before that report. A worker that has no READ posted for it drops it and reports it in `finished_recving`. Posted READs are left alone, since only their completion says the blocks are no longer written.

Timeout: the deadline is armed when the READs are posted. On expiry the request's blocks go to `_invalid_block_ids`, so under `fail` the scheduler fails the request in the same step and keeps its blocks while the handles are outstanding. Under `recompute` the request is rescheduled only after `finished_recving`, so it never recomputes into blocks a READ can still write.

Why the engine stays connected: on NIXL 1.3.2 through current main, `nixlAgent::getXferStatus` returns `NIXL_ERR_NOT_FOUND` once `invalidateRemoteMD` has dropped the remote section, before the backend `checkXfer` runs, and `check_xfer_state` maps that to `ERR`. So if the worker released the engine, it would see a stalled READ fail right after `remove_remote_agent` and free its blocks. That status says nothing about the DMA: `invalidateRemoteMD` destroys the remote rkeys with the GET possibly outstanding, the backend `disconnect` only drops the connection from `remoteConnMap`, and the request handle keeps a `CONNECTED` endpoint that is closed in flush mode on release. Reclaiming those blocks depends on ai-dynamo/nixl#2338: NIXL stops the outstanding operations by force-closing the endpoint before it releases the remote metadata and rkeys, and reports a terminal status only after that. Until a NIXL release carries it, the blocks of a stalled READ stay quarantined; releasing the engine on timeout can follow once it does. `release_dlist_handle` needs no deferral, since `makeXferReq` copies the descriptors.

Limitations:
- With HMA, invalid block ids are unsupported for more than one KV cache group, so a timed-out request is counted at the deadline and fails only when its handles resolve.
- A timed-out request counts once at the deadline and once per handle that later reports `ERR`, as any failed handle does.
- An aborted request with a READ posted keeps its blocks until the READ completes, fails or hits the deadline.
- The default deadline applies to every pull. A READ outstanding for 480 s is treated as broken.
