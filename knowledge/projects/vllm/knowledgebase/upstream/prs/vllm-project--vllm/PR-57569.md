# [Perf][KV Offload] Calibrate the DMA/Triton load cutoff at handler init (opt-in)

[Upstream PR](https://github.com/vllm-project/vllm/pull/57569) · state: open · merged: False

## Original PR description

## Purpose

Part of #57555. Stacked on #57343, so the first two commits here are from that PR.

**Updated 2026-10-05:** the first version timed the default-stream fallback instead of `cuMemcpyBatchAsync`, and inside a server it didn't run at all ([details](https://github.com/vllm-project/vllm/pull/57569#issuecomment-5981553144)). Fixed in a0cc5ad4e; 8eed6a0f4 adds a 5% margin and e26e6e9d4 calibrates on rank 0 only. The numbers below are re-measured inside `vllm serve`.

The CPU→GPU load path picks between `cuMemcpyBatchAsync` and the Triton kernel with two constants tuned on one H100 (`THRESHOLD_BYTES = 28 KiB`, `MIN_N = 16`). The numbers in #57555 (H100, A30, GB10) show that where the two paths cross depends on the copy size, the batch size and the machine, so this lets a worker measure it instead.

With `"calibrate_load_path": true` in `kv_connector_extra_config`, rank 0 times both paths when the offloading worker is created, for its copy sizes, at N = 16, 32, 64, 128, 256, on a dedicated stream like real transfers. Every rank then uses the smallest N from which Triton is more than 5% faster at every larger N; where the two are within 5%, the default decides. If Triton never gets there the handler stays on DMA. The source is the real pinned CPU tensor and the destination is a scratch GPU buffer (at most 16 MiB), so no KV block is written. Copy sizes above 64 KiB would need a bigger scratch and are not measured. If anything goes wrong (no room for the scratch, host region too small, the op raising) the handler keeps the defaults and logs a warning.

The worker init is the natural place for this: the real GPU tensors, the pinned host region and the copy sizes all exist there, the GPU is idle, and `_select_swap_blocks_fn` already runs at that point.

To carry the result, the size cutoff and `MIN_N` are resolved into one `min_n` per handler at init and passed to the Triton wrapper, which still does a single comparison per call. With the option off the values are the same as today, so the default behaviour does not change.

On handlers with more than one copy size (the point @hclsys raised in #57555): one transfer sends all of a handler's sizes in a single call, so the per-size results are reduced to one. I kept that conservative, the largest `min_n`, and DMA for everything if any size never wins on Triton, which is what `max(sizes)` does today. When the sizes disagree the handler logs it, so it is visible how often this happens. Splitting the call by size is left for a follow-up once there is data from a hybrid model.

New tests:

- `test_batches_below_min_n_use_dma`: the wrapper falls back to DMA below the `min_n` it is given (runs without CUDA).
- `test_pick_min_n`: Triton taking over at N=64, ahead everywhere, never ahead, a win at N=32 that doesn't count because N=64 loses again, and cells within the 5% margin left to the default.
- `test_measure_load_paths_times_every_probed_n`: times every probed N on a real pinned tensor, and returns nothing when the host region is too small.
- `test_measure_load_paths_reads_strided_host_rows`: measures on a strided view like the shared offload region (fails on the first version).
- `test_measure_load_paths_avoids_default_stream`: both paths are timed off the default stream (fails on the first version).
- `test_calibrated_load_path_uses_measured_min_n`: the measured value replaces the default, also for a 32 KiB page that defaults to DMA, the handler stays on DMA when Triton never wins, and a size the calibration didn't cover keeps its default.
- `test_calibration_failure_keeps_defaults`: an exception or a skipped measurement leaves `MIN_N`.
- `test_calibration_runs_on_rank0_only`: only rank 0 measures, and every rank gets its result.
- `test_mixed_copy_sizes_reduce_to_one_min_n`: the largest `min_n` is used, and one DMA-only size keeps the handler on DMA.

```
  64K   min_n: [128, 256, 128, 32, 32, 32, 128]
```

Five times the reps tightens 16 KiB but not 64 KiB, so this isn't only a rep-count problem.

The underlying medians at 16 KiB, six runs:

```
run   arm    N=16     N=32     N=64     N=128    N=256
0     dma    0.0489   0.0790   0.1292   0.2434   0.5520
0     tri    0.0473   0.0382   0.0381   0.0752   0.0928
3     dma    0.0483   0.0771   0.1261   0.2300   0.4388
3     tri    0.2140   0.1979   0.1275   0.1086   0.1234
```

The DMA arm is steady to about 2%. The Triton arm's median at N=16 moves between 0.037 and 0.25 ms across identical calls, roughly 6x, and it is right at that N that the crossing gets decided.

What I ruled out before blaming variance: the co-tenant on this card holds 16.9 GB but is not computing (utilization sampled at 0-1%), and the SM clock sits at 2411 MHz with the part at 53 C for the whole run, so no throttle. It is not JIT either, since `run_ms` already discards a warm-up and the fast runs are as often first as last.

The reduction then amplifies it. `pick_min_n` walks down from the largest N and breaks on the first `tri > dma`, with no tolerance, so one cell landing the wrong side of 1.0 at N=128 or 256 truncates the whole walk. That is how 16 KiB gets both 16 and 256 out of the same machine minutes apart.

Two things that might help, in the order I'd try them:

- require a margin rather than `tri > dma`, so a cell within noise of parity doesn't break the walk
- repeat the whole measurement two or three times and take the consensus pick, rather than more reps inside one measurement

I also tried a variant with the destination slots permuted instead of contiguous, since real loads write scattered block ids and the contiguous scratch is friendlier to the copy engine than production is. The run-to-run spread above swamps it, so I have nothing to report there yet, and it seems worth settling the stability first.

Caveats: one machine, load direction only, nothing above 64 KiB, and I drove the two functions directly rather than through a real serve, so I have not seen what a handler picks in situ.

Hi @Etelis, thanks for the review.

Starting with 4, since it affects the rest. You were right, and I should have checked this at runtime before opening the PR.

The calibration was running on the legacy default stream (`0x0` at handler init, same inside `vllm serve`). `swap_blocks_batch` doesn't use `cuMemcpyBatchAsync` on that stream ([cache_kernels.cu#L163-L166](https://github.com/vllm-project/vllm/blob/5ea23ad9b80e8c22fc7a4f326a9e378f81639d84/csrc/libtorch_stable/cache_kernels.cu#L163-L166)) and falls back to one `cudaMemcpyAsync` per copy. So what I measured as "DMA" was the fallback, not the path real transfers take.

While checking this I found a second problem: inside a real server the calibration wasn't running at all. The worker's CPU tensors are strided views of the shared mmap region, and `measure_load_paths` returns None for non-contiguous tensors, so the handler just kept the defaults without logging anything. The numbers in the description are from a standalone worker with its own contiguous tensor, which is why I didn't notice.

Fixed in a0cc5ad4e. The calibration now runs on its own stream and reads the strided rows like real loads do. I added two tests that fail without the fix. 8eed6a0f4 adds the margin, more on that in 2.

The server now logs:
```

Triton/DMA time at N=16/32/64/128/256: 1.43 1.15 1.01 0.90 0.82
```

The numbers in the description are wrong because of this, so I'll update it. Results for 1-3 on the fixed code are in the next comment.
