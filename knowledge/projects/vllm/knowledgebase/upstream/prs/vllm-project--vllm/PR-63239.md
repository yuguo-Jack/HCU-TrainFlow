# [Perf][Spec Decode] Warm up the speculative variant of the Qwen GDN recurrent update kernel

[Upstream PR](https://github.com/vllm-project/vllm/pull/63239) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

With speculative decoding on Qwen3.5/3.6 GDN models, the first step that batches a prefill with spec rows still JIT-compiles the speculative variant of `fused_sigmoid_gating_delta_rule_update_kernel` during serving, triggering `Triton kernel JIT compilation during inference: ...` from the JIT monitor and a stall on that step (and a hard failure under `--jit-monitor-mode=error`). The Qwen Triton warmup builds only the non-speculative variant. Regression from #56531 (first released in v0.32.0).

## Claims

- The Qwen GDN warmup also compiles the speculative variant (`IS_SPEC_DECODING=True`, `stride_indices_seq = num_spec + 1`) when the layer has `num_spec > 0`, read from the layer as the Kimi-K3 warmup does.
- The added launch uses state index 0, so the kernel returns before it touches state.
- Also fixes a stale comment in the MRV2 warmup.

## Validation

End to end, `nvidia/Qwen3.6-35B-A3B-NVFP4` + MTP k=3, `--jit-monitor-verbose`, RTX PRO 6000, empty Triton cache:

| Config | Runtime JIT before | Runtime JIT after |
|---|---|---|
| MRV1, `warn`, nightly `e0d00e4b8e` | `fused_sigmoid_gating_delta_rule_update_kernel` `IS_SPEC_DECODING=True`, `stride_indices_seq=4` at the first mixed step | none from this kernel |
| MRV2, `error`, nightly `3f1bcfd82` | same kernel, engine stops (`EngineDeadError`) | none (earlier revision of this PR) |

The new compile-count test fails on `main` and passes with this PR (0.59 s, RTX PRO 6000, nightly `e0d00e4b8e` with this PR's two non-test files). It also fails when only the speculative launch is removed: one extra compile key, the speculative variant.

No model evals: the kernel is unchanged; only when it is compiled moves.

## Details

**Root cause.** The kernel specializes on `IS_SPEC_DECODING` (`num_accepted_tokens is not None`) and on the `ssm_state_indices` strides, and the Qwen warmup calls it once, without `num_accepted_tokens` and with `(1, 1)` indices. Pure spec steps take the fused MTP decode instead, so on CUDA the spec variant is first reached by spec rows batched with a prefill, which pass `num_accepted_tokens` and `[n, num_spec + 1]` indices. Before #56531 the MRV2 warmup's mixed decode step reached it; that step is now purely speculative.

**Scope.** Qwen3.5/3.6-style GDN models with a speculative config, where the fused MTP decode is used (the CUDA default). Without a speculative config `num_spec` is 0 and the warmup is unchanged.

**Warmup contract.** Like the existing launch in this function and #61855, this warms by launching the kernel, which `docs/contributing/jit_kernel_warmup.md` asks to avoid; moving the kernel to `VllmJitKernel` would be a separate refactor.

**Related PRs.**
- #62343 (draft) rewrites this warmup function for non-speculative prefill rows.
- #61952 compiles this variant only under `VLLM_USE_BREAKABLE_CUDAGRAPH=1` with the Triton GDN prefill.

**Known remaining gap, not addressed here.** On MRV1, other kernels (e.g. `store_cache_checkpoints_kernel`, `eagle_step_slot_mapping_metadata_kernel`) still JIT at the first mixed step, so this PR alone would not make MRV1 pass `--jit-monitor-mode=error` (not run).

**Not run** on SM90 or ROCm. The NVIDIA `Model Executor` CI step is disabled; the MI300 job selects the new test.
