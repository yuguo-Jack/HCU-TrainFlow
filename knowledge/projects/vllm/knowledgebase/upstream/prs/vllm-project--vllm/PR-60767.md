# [Bugfix][V1] Null sliding-window block-table entries below the window

[Upstream PR](https://github.com/vllm-project/vllm/pull/60767) · state: open · merged: False

## Original PR description

## Purpose

Fixes #60560.

The sliding-window KV manager frees blocks once they fall wholly outside a request's window, but the worker's persistent block table keeps the freed block ids. Attention kernels load KV in tiles (FA4 uses 128-key tiles on SM100). With 64-token pages, the tile that holds the window start can include one page lying wholly below the window. That page is masked, but masked NaN still propagates (0 × NaN). After the freed block is reused, its bytes can decode as NaN in the layer that reads it, and that request's attention output turns NaN.

#60560 has the full analysis. In short, on B300 with a DFlash2 drafter (all 6 layers sliding window, 2048) under the hybrid KV cache manager and `--block-size 64`:
- draft acceptance falls from about 40% to 27–29% at 32 concurrent sessions;
- the first divergence is NaN in the last draft layer's attention;
- about 21% of that layer's in-tile stale pages contain fp8 NaN bytes.

This PR makes the worker never hand those entries to attention. When `gather_block_tables` builds the forward-pass tables, every sliding-window entry wholly below `first_scheduled_position - (sliding_window - 1 + extra_retained_tokens)` is replaced by the null block:
- **No query of the step can attend those positions.**
- **The cutoff is never below the manager's free boundary.** The manager frees on the processed-token count, which is at most the first scheduled position, so every block it may have freed is covered.
- **Only the forward-pass copy changes.** Slot mappings and the persistent tables are untouched.
- **GPU only.** The first scheduled position is the request's `num_computed_tokens`, already on the device, so there is no host sync.
- **Specs can opt out.** `SlidingWindowSpec.num_retained_tokens` gives the reach; `KpoolTailSpec`, a one-block ring every position maps into, returns `None` and is left untouched.
- **Context parallelism is excluded.** Masking is disabled when `cp_size > 1`, where a block-table column is not a contiguous token range.

Speculator steps that reuse the gathered tables (e.g. DFlash) are covered too, since their queries sit at or after the target's first scheduled position.

### Scope

The change is not specific to any model or drafter. It applies to every KV cache group whose spec is a `SlidingWindowSpec` (including `SlidingWindowMLASpec`), target or draft, with any attention backend. Why it is safe:
- **No KV write is redirected.** Every KV write slot is computed from the persistent tables (`compute_slot_mappings`), or, for DFlash, from this step's positions, which are above the cutoff.
- **Kernel blocks are handled.** With several kernel blocks per KV block, the zeroed id still falls inside null block 0.

Not covered:
- **The V1 model runner.** The default V2 runner is covered; V1 is still selected for some speculators, DBO and some ROCm architectures.
- **Context parallelism (DCP/PCP).** Excluded on purpose, since a block-table column is not a contiguous token range there.
- **Chunked-local attention.** Not changed. Its chunk boundaries are multiples of the KV tile, so no wholly-outside page shares a tile.

**Assumption:** the null block holds no NaN. The KV cache is zero-allocated, and the null entries the tables already contain (sliding-window prefix hits, P/D tail clipping) rely on the same thing.

**Validation:** end-to-end validation so far covers a DFlash2 drafter under the hybrid KV cache manager. A check on a target model with sliding-window layers (e.g. gpt-oss, Gemma 3) at high concurrency is still to do.

### Relation to existing PRs

- **#42276** (for #42273, "SWA eviction leaves stale block table entries") targets the same stale entries from the scheduler side: it resends the full rewritten block table to the worker after an eviction. It has had merge conflicts since May and no review. This PR is a worker-only alternative: no scheduler or `SchedulerOutput` change, and no table resend. If maintainers prefer #42276's direction, I'm happy to close this one in its favour, and the regression test here should carry over.
- **#53628** fixes the same NaN symptom inside the ROCm prefix-prefill kernel, by masking block-table loads. That is complementary kernel hardening; this PR keeps freed blocks out of every backend's tables.

- stu-cao · comment · 2026-10-10T16:26:34Z · [source](https://github.com/vllm-project/vllm/pull/60767#issuecomment-6099674039)

@TheEpicDolphin thanks for the review, all three addressed in 7a659e9e08.

- **KpoolTailSpec:** you're right. The tail ring is one block that every position maps into through `pos % block_size`, so the nulling would have hit its only entry once a request passed `2 * ring - 1` tokens, and the tail would stop being written. I added `SlidingWindowSpec.num_retained_tokens` (`sliding_window - 1 + extra_retained_tokens`) as you suggested, with `KpoolTailSpec` returning `None` to opt out; the runner maps `None` to a reach of 0, which the kernel already treats as disabled. `SlidingWindowMLASpec` keeps the base value, since it uses the same `SlidingWindowManager` and free boundary.
- **num_computed_tokens:** `seq_lens` is itself computed as `num_computed_tokens[req] + query_len`, so `seq_len - query_len` was always `num_computed_tokens[req]`. The kernel now reads that tensor directly by request slot, and the two batch-indexed arguments are gone. The test now places the requests in non-consecutive slots, so slot-vs-batch indexing is covered.
- **Load mask:** applied as written.
