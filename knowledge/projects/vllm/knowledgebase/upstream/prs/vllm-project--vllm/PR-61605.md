# [Bugfix][LoRA] Reject checkpoints with mismatched tensor ranks

[Upstream PR](https://github.com/vllm-project/vllm/pull/61605) · state: closed · merged: False

## Original PR description

## Overview

Withdrawn after maintainer review and a numerical GPU follow-up. A physical rank smaller than the configured rank can be a valid zero-padded representation; strict equality is too restrictive.

## Claims

No correctness or performance fix is claimed for the proposed configured-rank equality rule. The earlier acceptance/rejection tests established the behavior of the check, not a computation error in the original loader.

## Validation

On 2026-10-27 I ran three fresh NVIDIA L20 engines with the original loader, the same seeded tiny OPT model and the same rank-4 factor values:

| Representation | Configuration | Result |
| --- | --- | --- |
| Physical A/B rank 4 | rank 8, alpha 16 | Accepted |
| Same factors explicitly zero-padded to rank 8 | rank 8, alpha 16 | Accepted |
| Physical A/B rank 4 | rank 4, alpha 8 | Accepted |

Every pair matched all 8 output token sequences; the maximum selected-logprob difference was 0. All three encode the same update, with scaling 2. The proposed check would reject the first representation.

These were separate real CUDA-engine runs, using the tracked Python sources from `d0d37d6` with only the loader restored to its original implementation. Native binaries and generated runtime files were reused from precompiled `be4ce2e5`. The run covers a two-layer synthetic OPT model, not all layouts, MoE models or production workloads. Existing resident services were unchanged and the selected GPU was released.

## Details

The numerical result supports [the maintainer's objection](https://github.com/vllm-project/vllm/pull/61605#pullrequestreview-5648959691). I am closing this version rather than imposing the restriction. Missing-factor diagnostics and genuinely incompatible dimensions would need a separately justified change.

The branch and the earlier [rejection/control validation](https://github.com/vllm-project/vllm/pull/61605#issuecomment-6393448946) remain available for provenance. Those earlier results do not establish a need to reject compatible lower-rank factors.

- linitra24 · COMMENTED · 2026-10-26T08:02:17Z · [source](https://github.com/vllm-project/vllm/pull/61605#pullrequestreview-5648959691)

Thanks for your work and the detailed validation!

However, I'm not fully convinced that we need to enforce a strict match between the configured rank and the actual tensor rank.

For regular LoRA layers, vLLM copies the weights into zero-padded buffers based on their actual shapes. As long as the A/B dimensions are compatible and fit within `max_lora_rank`, a mismatch with the configured rank doesn't necessarily cause an issue. The configured rank does affect scaling, but that alone doesn't mean the checkpoint should be rejected.

I'm also concerned about the additional restrictions this introduces. As this PR already demonstrates, some MoE layouts require special handling, and other packed or non-standard LoRA layouts may introduce similar exceptions in the future.

Is there a concrete correctness issue caused by this mismatch, beyond accepting a checkpoint with inconsistent metadata? Without a clear failure case, I'm leaning toward keeping the current behavior to avoid unnecessary restrictions and maintenance overhead.
