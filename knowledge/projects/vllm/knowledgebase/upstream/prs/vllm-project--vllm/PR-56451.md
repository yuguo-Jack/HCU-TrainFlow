# [ROCm][Spec Decode] Enable adaptive DSpark verification for MiniMax M3

[Upstream PR](https://github.com/vllm-project/vllm/pull/56451) · state: open · merged: False

## Original PR description

## Summary

PR adaptive DSpark verification for MiniMax M3 on ROCm. Part of the adaptive DSpark backend expansion (#51303): each model needs varlen-capable sparse kernels before adaptive verification can redistribute draft tokens across requests
It was validated end to end with amd/MiniMax-M3-MXFP4 and nvidia/MiniMax-M3-DSpark on MI325.

Scope: only the ROCm Triton indexer and sparse-decode paths gain ragged decode support. The CUDA and AITER MiniMax M3 backends still report device/CPU query-length mismatch as unsupported, so adaptive verification stays disabled there. With adaptive verification off, the uniform decode path is unchanged.

## Changes

- MiniMax M3 indexer and sparse attention (ROCm Triton): device-side ragged decode metadata; both AMD index-score launch policies, the fused top-k selector, and sparse decode map packed query tokens to requests from device `query_start_loc`.
- `kernel_paged_attention_2d`: return for `query_len != 1` (previously `> 1`). FULL cudagraph replay can pad the request dimension with zero-length rows, which fell into the decode path and read one row past the logical query buffer.
- Rejection sampler: adaptive verification allows the regular chunked path for batches with no draft tokens, whose logits layout isnever compacted.
- Warmup: synthetic draft rows are bounded by the same rejection-sampler budget used at runtime, so large `max_num_seqs` configs nolonger fail at startup.
- Adaptive verification overhead: confidence D2H copies use a non-blocking ring, and only TP rank 0 computes the draft budget, thenbroadcasts it.
- DSpark config: prefer speculators-format top-level confidence-head fields and fall back to NVIDIA's legacy `dflash_config` fields.


Token-to-request mapping uses upstream's `compute_token_to_req_indices`, a device-side binary search over `query_start_loc`. It doesn't depend on `max_query_len` and handles zero-length rows and the padding tail.

## Not a duplicate

Searched open PRs (adaptive verification, MiniMax M3 DSpark, token-to-request mapping, paged-decode zero-length). The closest is #52893, which skips AITER sparse PA under spec decode; this PR adds ragged decode to the Triton path instead.

## Testing

On MI325:
- `tests/v1/spec_decode/test_adaptive_verification.py`, `tests/v1/worker/test_gpu_rejection_sampler_chunking.py`, `tests/v1/worker/test_gpu_warmup_blocks.py`, `tests/v1/worker/test_attn_utils.py`: 138 passed, 1 skipped.
- `tests/kernels/attention/test_minimax_m3.py`: all passed.
- `test_prefix_prefill.py::test_contexted_kv_attention` (`chunked_prefill_paged_decode`, source build of this branch): 128 passed, 256 skipped.

- Stress test of the ragged index top-k and sparse decode kernels at serving-sized batches: 60 random batches of 380–512 requests (1–8 query tokens each, up to 4K context, zero-length padding rows), reference-checked every 10th batch: all passed.

## End-to-end results 

MI325, `nvidia/MiniMax-M3-DSpark` drafter with its default confidence head, `num_speculative_tokens=7`, FULL cudagraphs, default memory settings, `--max-model-len 4096 --max-num-seqs 512`. Fixed vs adaptive verification on the same build.

GSM8K, full test set (1,319 questions, 5-shot, greedy, concurrency 64):

| Checkpoint | TP | Fixed | Adaptive |
|---|---:|---:|---:|
| `amd/MiniMax-M3-MXFP4` | 2 | 0.8196 | 0.8226 |
| `MiniMaxAI/MiniMax-M3-MXFP8` | 4 | 0.8779 | 0.8711 |
| `MiniMaxAI/MiniMax-M3` (BF16) | 8 | 0.8704 | 0.8688 |

Repeated MXFP8 runs vary by about ±0.01 for both modes (fixed 0.860–0.878 over 6 runs, adaptive 0.867–0.879 over 9 runs). One earlyadaptive MXFP8 run scored 0.801; it did not reproduce in 9 later runs and is still being investigated.

| 256 | 882.77 → 930.58 (+5.4%) | 2560.18 → 2605.40 (+1.8%) | 4005.66 → 4063.85 (+1.5%) |

The gain shrinks as verification gets cheaper: TP=4 and TP=8 leave little verify cost for adaptive budgeting to save. MXFP8 fixed verification at concurrency 500 runs out of memory allocating the full verification logits (1.6 GB) at the default `--gpu-memory-utilization`; adaptive verification bounds that allocation and completes all requests.

### Known issue: BF16, TP=8, adaptive, concurrency ≥ 380

The adaptive BF16 server aborts with `HW Exception by GPU node-N ... reason: GPU Hang` under sustained load at concurrency 380–420 (reproduced twice; fixed verification is stable at the same load, MXFP4 TP=2 and MXFP8 TP=4 adaptive are stable through concurrency 500). The ragged MiniMax kernels pass the stress test above. Most likely root cause fix in #56831 - this is well-known issue at this point. Need to run TP=8 test with this PR applied).
