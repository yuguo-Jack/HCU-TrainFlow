# [Kernel] Calibrate the NVFP4 W4A16 Marlin/CuTe-DSL choice per layer shape on sm_12x

[Upstream PR](https://github.com/vllm-project/vllm/pull/65334) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Choose between Marlin and FlashInfer CuTe-DSL for NVFP4 W4A16 linear layers on sm_12x GPUs, per layer shape and per number of tokens, from timings taken once while the weights load. It is selected automatically when the W4A16 backend is chosen automatically, and `VLLM_NVFP4_W4A16_DISPATCH=0` turns it off. Related open PRs on the same kernels: #56553, #55405, #59598.

## Claims

- On GB10 (sm_121) the faster of the two kernels depends on the layer shape and on the number of tokens. For the 4096x18560 projection of Nemotron-3.5-Bolt-74B-A9B-24GB CuTe-DSL is about 28% faster than Marlin above 64 tokens, while for the 8192x4096 one Marlin is as fast or faster at every token count. A single token threshold for all layers would be wrong, so the choice is calibrated per shape.
- End to end on GB10 with that model (dflash with 7 speculative tokens, tp=1) it gives +4 to 6% tok/s/user at batch size 32, is within noise of Marlin at batch sizes 1 and 8, and shows no clear gain at 16. The first token of a 2048-token prompt arrives after 1032 ms against 1124 ms (single runs).
- Costs: 9 seconds of calibration for the 9 layer shapes of this model, and 1.5 GiB more weight memory, because the layers where CuTe-DSL wins keep both weight formats. A shape where it never wins keeps only Marlin.
- Nothing changes on other GPUs, or when a backend is forced with `--linear-backend` or `--kernel-config`.

## Validation

Setup: one GB10, `vllm serve nvidia/NVIDIA-Nemotron-3.5-Bolt-74B-A9B-24GB` with the flags of the community recipe for this model (`--kv-cache-dtype fp8 --max-num-seqs <bs> --trust-remote-code --gpu-memory-utilization 0.8 --max-num-batched-tokens 8192 --speculative_config.method dflash --speculative_config.model nvidia/NVIDIA-Nemotron-3.5-Bolt-74B-A9B-24GB-LiLiCorr --speculative_config.num_speculative_tokens 7 --load-format instanttensor --reasoning-parser nemotron_v3 --block-size 64 --prefix-match-unit 64`), client aiperf at concurrency equal to the batch size on SPEED-Bench `qualitative` (`--osl 2048`, no EOS forcing). The "CuTe-DSL" column adds `--kernel-config '{"linear_backend_per_quant":{"nvfp4_w4a16":"flashinfer_cutedsl"}}'` and the calibrated runs use the defaults.

tok/s/user, mean and standard deviation over n runs (a list is one run per value):

| batch | Marlin | CuTe-DSL for all layers | calibrated dispatcher |
|---|---|---|---|
| 1 | 93.5 ± 1.5 (n=3) | 91.9 ± 2.3 (n=4) | 93.8, 94.1, 95.5 |
| 8 | 35.7 ± 1.5 (n=4) | 36.3 (n=1) | 35.9, 35.4 |
| 16 | 23.1 ± 0.1 (n=3) | 23.5 ± 0.7 (n=3) | 24.2, 22.2 |
| 32 | 11.3 ± 0.3 (n=6) | 12.0 ± 0.2 (n=6) | 12.0, 12.0, 11.8 |

The first calibrated run used an earlier version of the rule that also chose CuTe-DSL for some very small layers. The dflash acceptance length is the same as with Marlin. With 2048-token prompts at batch size 1 the time to first token is 1124 ms with Marlin and 1050 and 1032 ms for two calibrated runs.

What the calibration decided for this model (load log): the 4096x18560 layers use CuTe-DSL from 96 tokens (41 MiB of extra weights per layer), the 24576x4096 layers of the draft model do too (54 MiB), and the other seven shapes, including the 8192x4096 projection, keep Marlin only.

For context, the kernels alone on the real layers (CUDA graph, 40 distinct weight copies), microseconds per call:

| tokens | 4096x18560 Marlin / CuTe-DSL | 8192x4096 Marlin / CuTe-DSL |
|---|---|---|
| 8 | 195.7 / 199.8 | 86.1 / 88.2 |
| 64 | 213.1 / 222.3 | 94.5 / 109.8 |
| 80 | 405.0 / 292.6 | 127.8 / 133.6 |
| 128 | 414.3 / 301.0 | 121.4 / 139.3 |
| 256 | 803.8 / 570.7 | 209.6 / 277.1 |
| 2048 | 6279 / 4512 | 1582 / 6264 |

This predicts the direction of the end-to-end gain but not its size, and at 2048 tokens it predicted a slowdown on the 8192x4096 projection that the time to first token did not show.

What was not done: the measurements applied these changes to the files of an image built from upstream 3966924d56 plus an unrelated KV cache change that only acts with `--kv-cache-host-pinned`, which these runs did not use. The branch is rebased on `upstream/main`. It was not tested on other GPUs (sm_120 in particular) or other models, and there is no accuracy evaluation, no `VLLM_GPU_SYNC_CHECK=error` run and no run of the rest of the vLLM test suite. The pre-commit hooks pass on the changed files.

Tests: `tests/kernels/quantization/test_nvfp4_w4a16_dispatch.py`, 15 tests, run with `pytest -v -s tests/kernels/quantization/test_nvfp4_w4a16_dispatch.py`. Eight need no GPU: the choice of the longest run of consecutive wins (six cases) and the table that maps a number of tokens to the calibrated count at or above it. Seven need an sm_12x GPU: the output of the dispatch is bit-for-bit that of the kernel it says it picked (`uses_cutedsl`), for 2048x1024 and for the 18560x4096 projection at 8 token counts, and when it picks CuTe-DSL the test checks that the two kernels give different results, so it can tell them apart; two layers of one shape make the same choice; and the automatic selection returns the dispatch, goes back to Marlin with `VLLM_NVFP4_W4A16_DISPATCH=0` and leaves an explicit `--linear-backend` alone. On a GB10 all 15 pass, five runs in a row. With the dispatch changed to always use Marlin the exactness test fails on both shapes (14 of 131072 and 410 of 1206400 elements differ, by up to 0.03), so it does detect that.

CI: the step that runs `tests/kernels/quantization` (L4) now also depends on `vllm/model_executor/kernels/linear/`, so a change to the dispatch triggers it, and it runs the eight tests that need no GPU. The seven sm_12x tests are skipped there because CI has no sm_12x machine; they were run on a GB10 as described above.

## Details

The kernel is in a new file, `vllm/model_executor/kernels/linear/nvfp4/dispatch.py`. In `init_nvfp4_linear_kernel` it is returned from the branch that automatically selects Marlin, when the device is sm_12x, both kernels are supported and `VLLM_NVFP4_W4A16_DISPATCH` is not 0. The environment variable is registered in `vllm/envs.py`, whose comment generates its reference entry.

The first layer of each (output size, input size, device) times both kernels on 10 token counts from 8 to 2048, with a CUDA graph when it can be captured, and the result is shared by all layers of that shape. CuTe-DSL counts as faster when it takes less than 97% of Marlin's time and saves at least 5 microseconds, and only the longest run of at least two consecutive wins is kept, so timing noise cannot decide. A step with m tokens follows the smallest calibrated token count that is at least m, or the last one. If the calibration fails the shape uses Marlin and a warning is logged. The load log reports each shape, the calibration time and the extra memory.

Each backend repacks the weights in place into its own layout, so CuTe-DSL repacks a copy before Marlin repacks the layer, and both stay resident for the shapes where it wins. The choice is made inside the custom op `vllm::nvfp4_w4a16_dispatch`, so `torch.compile` does not specialize on the number of tokens and each captured CUDA graph size bakes in one kernel.

Limitations and risks: the default changes behaviour for every NVFP4 W4A16 model on sm_12x, and the evidence is one GPU and one model, so maintainer attention is needed on whether this should be the default. The table is a snapshot taken at load time, so a noisy GPU at that moment can affect it. About 292 added lines of code (and 174 of tests), above the 250 mark of the checklist, for a gain of about 5% at large batch sizes. #56553 would restrict CuTe-DSL W4A16 to SM100/103: the dispatcher is then not selected and Marlin is used as before.

Not a duplicate: I searched open PRs for "NVFP4 W4A16 Marlin CuTe-DSL dispatch", "nvfp4 linear backend by batch size tokens" and "flashinfer cutedsl bf16 fp4 W4A16" with `gh pr list --state open --search`. None switches kernel per call. The related ones are #56553, #55405 and #59598 (CuTe-DSL W4A16 selection and priority).
