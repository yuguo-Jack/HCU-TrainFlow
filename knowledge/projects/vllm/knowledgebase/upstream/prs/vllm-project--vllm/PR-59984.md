# [Bugfix] Keep force-killing the process tree when a child exits mid-walk

[Upstream PR](https://github.com/vllm-project/vllm/pull/59984) · state: open · merged: False

## Original PR description

## Overview

Fix a regression from #52314: `kill_process_tree` stops early, leaving the rest of the tree and the target alive, when a child exits between `parent.children()` and `child.name()`. Also handle the related case where the target itself exits right before its children are listed.

## Claims

- `kill_process_tree` now SIGKILLs every remaining descendant and the target pid even if a child is reaped while it walks the tree.
- `kill_process_tree` also returns quietly if the target exits and is reaped right after its lookup. In that case psutil's `children()` raises `NoSuchProcess` (pointed out by @andyxning).
- Before this change, `psutil.NoSuchProcess` escaped the function in both cases. Callers such as `vllm/v1/utils.py::shutdown()` then abandoned their loop over the remaining processes, so EngineCores, API servers or workers that were meant to be force-killed survived.

## Validation

Both tests use real processes, so the `NoSuchProcess` comes from psutil itself:
- `test_kill_process_tree_skips_child_that_exits_mid_walk` lists three live children, then kills and reaps one before the walk reaches it. It checks that the other two children and the target still exit with SIGKILL.
- `test_kill_process_tree_returns_when_target_exits_before_children` kills and reaps the target right before psutil lists its children. It checks that `kill_process_tree` returns without raising.

Results on Linux (base `04462732a4`, Python 3.12, psutil 7.2.2), with each version of `vllm/utils/system_utils.py`:

| `system_utils.py` | child exits mid-walk | target exits before `children()` |
|---|---|---|
| `main` | fails: `NoSuchProcess: process no longer exists`, from `name()` | fails: `NoSuchProcess: process PID not found`, from `children()` |
| first commit only | passes | fails |
| this PR | passes | passes |

- `pytest tests/utils_/test_system_utils.py`: 6 passed.
- `pre-commit` (ruff, typos) and `mypy` (`--python-version 3.12`) pass on the changed files.

## Details

**Root cause.** #52314 added `logger.warning(..., child.name(), child.pid)` inside the existing `contextlib.suppress(ProcessLookupError)`. On Linux, `psutil.Process.name()` re-reads `/proc/<pid>/stat` on every call; only Windows caches it. Once the child has been reaped it raises `NoSuchProcess`, which is not a `ProcessLookupError`. Before #52314 the loop only read `child.pid`, which is a plain attribute, so this path could not raise.

**Why the window is real.** The force-kill path runs when a process did not exit within its grace period. Typically that process is still tearing down and reaping its own children, for example EngineCore joining its workers after SIGTERM, so a child listed by `children()` can be gone by the time `name()` runs.

**A related, older case.** In psutil 7.x, `children()` looks the target up again (`Process(self.pid).create_time()`) outside any `try`. So it raises `NoSuchProcess` if the target exits and is reaped between our own `Process(pid)` lookup and the `children()` call, for example while another thread reads the dead child's `exitcode`.

**Fix.** Move `children()` into the existing `try`, so that case returns early like a failed lookup. Also suppress `NoSuchProcess` for each child. The child is already gone, so it needs no SIGKILL, and skipping it avoids signalling a pid that may have been recycled. This matches the existing `psutil.NoSuchProcess` guard at the top of the same function and `vllm/entrypoints/launchers/dp_supervisor.py`.

**Affected callers.**
- `vllm/v1/utils.py::shutdown()`, used by `CoreEngineProcManager`, `APIServerProcessManager` and the DP coordinator.
- `RustFrontendProcessManager._shutdown_subprocesses`.
- `dp_supervisor.py` already suppresses the exception, but before this fix it silently skipped killing the rest of the tree.

**Not a duplicate.** I found no issue or PR that reports or fixes this. I searched `kill_process_tree`, `NoSuchProcess` and "force killing sub process" for anything after #52314 was merged on 2026-09-30. #52314 itself has no review comments.
