# [Bugfix] Keep force-killing the process tree when a child exits mid-walk

[Upstream PR](https://github.com/vllm-project/vllm/pull/59984) · state: closed · merged: True

## Original PR description

## Overview

Fix a regression from #52314: `kill_process_tree` stops early, leaving the rest of the tree and the target alive, when a child exits between `parent.children()` and `child.name()`.

## Claims

- `kill_process_tree` now SIGKILLs every remaining descendant and the target pid even if a child is reaped while it walks the tree.
- Before this change, `psutil.NoSuchProcess` escaped the function. Callers such as `vllm/v1/utils.py::shutdown()` then abandoned their loop over the remaining processes, so EngineCores, API servers or workers that were meant to be force-killed survived.

## Validation

The new test `tests/utils_/test_system_utils.py::test_kill_process_tree_skips_child_that_exits_mid_walk`:
- starts four real processes and makes `children()` report three of them as the target's children;
- ends one of the three with SIGTERM and reaps it before `kill_process_tree` runs, so psutil's own `name()` raises `NoSuchProcess` for it;
- asserts that this child exited from that SIGTERM, and that the other two children and the target exit with SIGKILL.

Results on Linux (base `04462732a4`, Python 3.12):

| psutil | `main` | this PR |
|---|---|---|
| 6.1.0 (pinned in vLLM's CUDA/CPU test requirements) | fails: `NoSuchProcess: process no longer exists`, from `child.name()` | passes |
| 7.2.2 (latest; pinned in vLLM's ROCm/XPU test requirements) | fails: same | passes |

- `pytest tests/utils_/test_system_utils.py`: 5 passed with each psutil version. The new test also passed 30 runs in a row with each.
- `pre-commit run --hook-stage manual` (the stage CI runs) passes on the changed files, including ruff, typos and mypy.

## Details

**Root cause.** #52314 added `logger.warning(..., child.name(), child.pid)` inside the existing `contextlib.suppress(ProcessLookupError)`. On Linux, `psutil.Process.name()` re-reads `/proc/<pid>/stat` on every call; only Windows caches it. Once the child has been reaped it raises `NoSuchProcess`, which is not a `ProcessLookupError`. Before #52314 the loop only read `child.pid`, which only returns the stored pid, so this path could not raise.

**Why the window is real.** The force-kill path runs when a process did not exit within its grace period. Typically that process is still tearing down and reaping its own children, for example EngineCore joining its workers after SIGTERM, so a child listed by `children()` can be gone by the time `name()` runs.

**Fix.** Also suppress `NoSuchProcess` for that child. The child is already gone, so it needs no SIGKILL, and skipping it avoids signalling a pid that may have been recycled. This matches the existing `psutil.NoSuchProcess` guard at the top of the same function and `vllm/entrypoints/launchers/dp_supervisor.py`.

**Affected callers.**
- `vllm/v1/utils.py::shutdown()`, used by `CoreEngineProcManager`, `APIServerProcessManager` and the DP coordinator.
- `vllm/v1/utils.py::_shutdown_subprocesses()`, used by `RustFrontendProcessManager`.
- `dp_supervisor.py` already suppresses the exception, but before this fix it silently skipped killing the rest of the tree.

**Not a duplicate.** I found no issue or PR that reports or fixes this. I searched `kill_process_tree`, `NoSuchProcess` and "force killing sub process" for anything after #52314 was merged on 2026-09-30.

You're right for psutil 6.1.0, which vLLM's CUDA/CPU test requirements pin: up to 7.0, `children()` reuses the cached create time and doesn't raise. One note in case it comes up later: since 7.1 it calls `Process(self.pid).create_time()`, so it can raise `NoSuchProcess` if the target is reaped (e.g. by another thread) between the initial `psutil.Process(pid)` lookup and `children()`. That's what my earlier test hit on 7.2.2 (the latest release, pinned in the ROCm/XPU test requirements). It's a narrow window and not from #52314, so agreed it belongs outside this PR.
