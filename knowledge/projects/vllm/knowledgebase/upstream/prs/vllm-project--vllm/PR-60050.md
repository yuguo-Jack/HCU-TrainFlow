# [Perf][GDN] Internal prefill checkpoints for the FlashInfer GDN prefill backend

[Upstream PR](https://github.com/vllm-project/vllm/pull/60050) · state: closed · merged: True

## Original PR description

## Overview

Internal prefill checkpoints (RFC #52959) for Qwen GDN models (Qwen3-Next, Qwen3.5) on the FlashInfer GDN prefill backend. With prefix caching on (Mamba align mode), a prompt that crosses its cacheable block boundary no longer needs two forward passes: FlashInfer's prefill emits the boundary state in the same call. Kimi-K3 does the same with FlashKDA (#52789, #53614). Qwen4Exp (Qwen3.8-Flash-Next) keeps main's split prefill and block: its PLE short-conv Mamba layer cannot export checkpoints, and the scheduler takes them only when every Mamba layer can.

## Claims

- Qwen3.5-35B-A3B, 1x GB200, 8000-token prompts, on main `716961c`: TTFT −20% at concurrency 1, −12% at 4, −10% at 16. TPOT and accuracy are unchanged.
- Only enabled when the GDN prefill backend resolves to FlashInfer, prefix caching is on, and every Mamba layer of the model can export checkpoints; nothing is reserved otherwise. Triton/FLA, CuteDSL and ROCm are unchanged.
- No flags needed: align-mode blocks are put on FlashInfer's 64-token grid automatically (Qwen3.5-35B: 1056 → 1088 tokens), and only when the checkpoints are taken. Qwen3.8-Flash-Next keeps its 800-token block and main's TTFT.

## Details

- **Kernel.** `flashinfer.gdn_prefill.chunk_gated_delta_rule` can emit a state every N tokens of each sequence (`state_checkpoints`, `checkpoint_cu_starts`, `checkpoint_every_n_tokens`), where N is a multiple of 64. On GB200, each emitted state matches a separate run truncated at that position (max abs err 5e-3), and the final state is bit-identical with checkpoints on.
- **Plan.** Computed once per step on the host from `MambaPrefillCheckpointBuilder`'s offsets, so the scheduler and `MambaManager` agree on which rows checkpoint.
  - N is the gcd of the batch's offsets.
  - The plan also has the per-sequence checkpoint counts and each row's index into the emitted states.
  - It uses the host copies of the offsets (from #57329) and of the rows' query lengths on `MambaPrefillCheckpointMetadata`, so there is no device→host sync, and the counts and rows go to the device in one copy. It runs only in steps that take a checkpoint; at 16 rows the host work is a few µs.
- **Forward.** A step with checkpoints calls `fi_chunk_gated_delta_rule` directly with the plan; every other step calls `ChunkGatedDeltaRule` as before, whose signatures are unchanged.
- **Export.** Exporting a checkpoint is the same copy for every backend: the conv window ending at the offset, and one recurrent state picked out of a buffer the prefill kernel emitted.
  - `MambaPrefillCheckpointExporter` was an ABC with one implementation (Kimi-K3's, in `kda_checkpoint.py`). That implementation now is the class, in `layers/mamba/checkpoint.py`, with an optional `recurrent_rows` that picks each row's state out of the buffer; by default row `i` holds checkpoint `i`'s.
  - GDN passes FlashInfer's buffer and the plan's rows, so the only copy is one state per checkpointed row; decode rows and rows without a checkpoint are masked.
  - `FlashKDAPrefillCheckpointExporter` stays as a subclass, so the Kimi-K3 and GLM-5.3-Flash code is untouched. Mamba2's `ssd_checkpoint` kernel is the same copy with `chunk_idx` as the rows; folding it in is left to #61466.
  - GDN exports `conv_kernel_size - 1` columns of the conv window. Under MTP the conv cache has `num_spec` more, which the conv kernels never read (thanks @fuscof-ibm).
  - FlashInfer computes in an FP32 state (the wrapper upcasts), so the checkpoint buffer is FP32. The store casts it to the cache dtype.
- **Block alignment.** Offsets must be multiples of 64. Qwen3.5-35B's align block is 1056 (16 × 66), so every other checkpoint would be declined and fall back to a split prefill.
  - Mamba layers declare the alignment their checkpoints need through `MambaBase.get_prefill_checkpoint_alignment()`; GDN returns 64 when it takes FlashInfer checkpoints. When every Mamba layer declares one (`get_mamba_prefill_checkpoint_alignment`), `Platform._align_hybrid_block_size` makes align-mode blocks a multiple of their LCM (1056 → 1088). Otherwise the scheduler never takes internal checkpoints, so the block and the GDN spec stay as on main. sglang avoids this the same way, by keeping its Mamba cache grid at max(64, page_size).
  - The spec's `prefill_checkpoint_alignment` is the prefix-cache grid: the block, or `lcm(prefix_match_unit, 64)` when a finer match unit is set. A checkpoint off it falls back to the split prefill.
- **Workspace.** With every offset on the grid, FlashInfer's stride (their gcd) is a multiple of it, so a batch emits at most one state per grid step. The buffer holds `cdiv(max_num_batched_tokens, grid)` FP32 states, sized at profile time once the block is final: 16 states (32 MiB) on Qwen3.5-35B TP1 with 16384 batched tokens.
- **Warmup.** FlashInfer compiles separate CuTeDSL kernels for its context-parallel and regular routes, each with and without checkpoints. The GDN warmup now calls all four (`use_cp="auto"` and `False`). Before this, it only reached the route a single 64-token sequence takes, so the others compiled during serving (seconds on a cold cache).

**Tradeoffs.**

- The 64-aligned block is ~3% larger.
- Qwen4Exp gains nothing yet: its PLE short conv would need its own checkpoint export.
- With a `prefix_match_unit` finer than the block, the grid shrinks to `lcm(prefix_match_unit, 64)`, and the workspace and the states FlashInfer writes grow with it. In the worst case (a 64-token grid) this is 0.5 GiB and about 1 ms per 8k-token step.
- Validated on SM100 (GB200) only. FlashInfer also supports these checkpoints on SM90 and SM120.
- The shared Triton store kernel still compiles on first use, because its strides depend on the allocated KV cache.
