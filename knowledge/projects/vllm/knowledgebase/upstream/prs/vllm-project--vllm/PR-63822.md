# [Bugfix][Multimodal] Reduce retained arena and encoder-cache memory

[Upstream PR](https://github.com/vllm-project/vllm/pull/63822) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Multimodal inference can retain a large allocation even when it only needs a small part of it. This PR fixes two such cases:

- **CPU transport storage:** the SHM tensor arena registers its entire default 2 GiB mapping on first use, even for a single eligible image tensor just above the 8 MiB threshold.
- **GPU encoder storage:** cached per-image outputs can be views into one batch allocation. Evicting some images does not release their share of that allocation while another cached view still owns it.

This builds on #51207 and the already merged #57368. The latter releases consumed worker CPU inputs; this follow-up reduces arena registration and excess storage behind cached GPU encoder outputs.

## Claims

**1. Register only the used portion of each arena slot.**

Each reader tracks a registered prefix for each slot. Prefix sizes are rounded up to 8 MiB and grow geometrically, up to the slot capacity. For example, a 13.5 MiB tensor needs a 16 MiB prefix; using all eight slots at that size registers 128 MiB per reader instead of 2048 MiB. Readers map the same shared physical pages, so the host-memory saving must not be multiplied by TP size.

Registration growth uses the existing slot-reuse contract: all readers must have released the previous storage and completed H2D before a slot is reused. Growth replaces the old registration with a larger one. CUDA registration errors are cleared before falling back; if failed unregistration leaves a partially pinned source, the reader returns an owned pageable copy so H2D does not cross registered and unregistered memory.

The benefit is lower resident **CPU memory** when used prefixes are much smaller than the arena capacity. Prefixes are normally kept for reuse rather than shrunk after each request, and large inputs can still grow them to full capacity. The arena remains opt-in through its existing CLI flag.

**2. Compact partially retained encoder allocations when the reclaimed storage justifies copying.**

For example, four 5 MiB encoder outputs may share a 20 MiB GPU allocation. Keeping just one cached output can retain all 20 MiB. The cache can instead copy that surviving 5 MiB output into its own allocation and release its reference to the old batch storage.

`EncoderCache` first applies the entire eviction batch, then groups surviving entries by their underlying storage. In the ordinary cache path, it copies a group only when `storage_bytes - live_bytes >= live_bytes`: the potentially reclaimed bytes must be at least as large as the data copied. A fully evicted allocation needs no copy. The same check handles cropped outputs and duplicate hashes at insertion.

Replacement entries are published only after every copy in the group succeeds. An allocation failure leaves the original entries intact. With an EC connector, the cache instead attempts to isolate shared views at insertion, before the connector registers their addresses, and disables later relocation to preserve address stability.

This reduces excess **GPU encoder-cache storage** without changing the retained embedding values or logical cache contents. It adds copies and temporary allocation pressure; it does not impose a hard memory bound when compaction fails, and allocator-reserved memory need not fall immediately. Model weights and KV-cache budgets are unchanged.

## Details

The changes stay in the existing transport and cache ownership boundaries: `ShmTensorArena` manages host registration, while `EncoderCache` manages storage for GPU outputs. The model runner supplies the whole eviction batch and disables post-insertion relocation when an EC connector is configured. No new configuration fields, environment variables, CLI arguments, or dependencies are added.

The CPU PSS result above belongs to the recorded earlier revision and measures host residency, not GPU memory. Latest-revision model regressions separately exercise both memory-retention bugs. No latency, throughput, or universal memory-bound claim is made. Real EC networking, PP/speculative-decoding combinations, and ROCm have not been rerun on this candidate.

Duplicate-work checks found no open implementation of these two fixes. #51349 adds a different paged-SHM processor-cache backend; #50871 concerns EngineCore raw inputs in resumable sessions. #57368 is already in the baseline and its savings are not attributed to this follow-up.

AI assistance (OpenAI Codex) was used for implementation, review, and validation. The human submitter's per-line review and independent test confirmation have not been attested.
