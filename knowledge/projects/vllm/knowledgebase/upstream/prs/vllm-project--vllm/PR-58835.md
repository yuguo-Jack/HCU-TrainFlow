# [Qwen4Exp] Checkpoint-mapped PLE: read a decode step's cold pages with readahead

[Upstream PR](https://github.com/vllm-project/vllm/pull/58835) · state: open · merged: False

## Original PR description

## Purpose

Follow-up to #58439 (stacked on it; the diff to review is the last commit, [3f2142c](https://github.com/jschmied/vllm/commit/3f2142c11117), +94/−1 in 3 files).

With `checkpoint_mapped`, a freshly started server holds almost none of the PLE table in the page cache: loading
the weights streams them through it and evicts the table (0.03 of 47.7 GiB resident at ready on DGX Spark). A
decode step's rows are known only once the previous step has sampled, so the host prefetch has no lead: the GPU
lookup reaches the step's ~57 missing pages at the same time. Today the prefetch touches them serially in one
thread (the `< 4096 rows` path), and the GPU faults them itself, one at a time (~150 µs each).

The misses are not limited to that cold window. Under concurrent agent traffic on new text, steps keep touching rows that are not resident: an independent port of this fill path on v0.30 took eight coding-agent sessions from 62.5 to 93.1 tok/s in aggregate and cold 50K prefill from 1,144 to 1,896 tok/s (@antoniocuegervas, one GB10; [comment](https://github.com/vllm-project/vllm/pull/58835#issuecomment-5862458756)).

This PR fills decode-sized row sets with `MADV_WILLNEED` for every page, which queues readahead and returns at once
so the SSD serves the pages in parallel, followed by `MADV_POPULATE_READ` per page (both through ctypes, which
releases the GIL). The GPU's faults then wait on reads already in flight instead of issuing them one by one. There
is no new option and no wait on the lookup. Larger row sets keep the thread-pool touch; before Linux 5.14 (no
`MADV_POPULATE_READ`) the table falls back to the plain touch.

## Test Plan

- Unit tests (`tests/models/qwen4_exp/test_ple_pageable.py`), on the branch base (main `378504a54` wheel + #58439):
  30 passed; the two new tests (`test_fill_populates_the_rows`,
  `test_touch_falls_back_when_populate_is_unsupported`) fail on the #58439 head.
- Page fill on an idle box (57 cold pages, page cache dropped, 25 reps).
- Serving A/B on DGX Spark (GB10, sm_121, TP=1), Qwen3.8-Flash-Next, MTP n=3, KV 4 GiB,
  `checkpoint_mapped`: per fresh start, 6 different 300-token requests (cold pass), then the same 6 again (warm
  pass); 2 starts per arm, alternating; output hashes compared per request.
  Our locally converted checkpoints do not load on current main (`MergedColumnParallelLinear.load_weights` falls
  back to the module for keys it does not know), so the serving A/B ran on our serving stack (nightly
  `1ea7c63f4` + #58439) with this PR's fill path applied to the same `MappedTable.touch`.

## Test Result

Page fill, idle box (median of 25):

| fill | ms |
|---|---|
| serial touch (current) | 4.6–4.7 |
| `MADV_WILLNEED` all pages, then `MADV_POPULATE_READ` per page (this PR) | **0.36** |

Serving (ms per decode step):

| | base, start 1 / 2 | this PR, start 1 / 2 |
|---|---|---|
| cold pass (6 requests) | 59.15 / 59.41 | **56.80 / 56.50** (−2.35 / −2.91) |
| warm pass | 54.73 / 54.71 | 54.95 / 54.75 (+0.22 / +0.04) |

- Faster on 12/12 paired cold requests (−1.37 … −3.78 ms/step); major faults per step during the cold pass
  29–33 → 0.1. Output hashes identical to base in all 48 requests.
- Not measured: TP > 1; discrete GPUs (the backend targets unified memory); tables on slower storage than NVMe.

A data point for this PR from a port of its fill path (`MADV_WILLNEED` over the step's pages, then
`MADV_POPULATE_READ` per page, from host threads before the forward) onto v0.30.0 with MiaAI-Lab's file-mapped
PLE table instead of `checkpoint_mapped`. One GB10, TP=1, `nvidia/Qwen3.8-Flash-Next-NVFP4`.

On real text under concurrency the faults are not limited to a cold window after start. Eight coding-agent
sessions went from 62.5 to 93.1 tok/s in aggregate over several hours. Minutes with no prefill went from 60 to
103 to 108 tok/s while NVMe reads fell from 2,647 to about 1,270 a second. On fresh boots with the table
evicted, cold prefill of a 50K prompt of new text went from 1,144 to 1,896 tok/s (real Python source) and from
1,413 to 2,143 (random filler), and single-stream decode after it from about 33 to about 40.

Two differences in the port. The hook is in the model state's `prepare_inputs` (V2 runner): a pinned copy of
the ids plus a CUDA event hand the step to a worker thread. The step then waits up to 250 ms for its pages, so
decode steps find them present rather than in flight. A debug comparison of host and GPU ids found 0 mismatches
in 3,597 steps. Details, including the unmodified recipe measured on the same box:
https://github.com/MiaAI-Lab/Qwen3.8-Flash-Next-Single-DGX-Spark/issues/78

On the one design difference, the 250 ms wait: we measured a gated wait against no wait at one stream, and the no-wait fill was faster on 12 of 12 paired cold requests (−0.14 to −0.60 ms per step). Once the readahead is in flight, the GPU's remaining faults land on reads that are already under way, so the host keeps its one-step lead without waiting ([§4x](https://github.com/jschmied/qwen38-flash-next-gb10/blob/05becde3c22b19bfeaf640d34be792a7e381f6ea/notes/speed-of-light.md#L781-L813)). *Written and posted by Claude (Anthropic's AI assistant) on behalf of @antoniocuegervas, who reviewed it before posting.*

We compared it this morning under load: one fresh boot each at 0, 250 and 1,000 ms, the same cells on each
(four cold 50K single requests with the table evicted, then eight streams of real text at 50K).

| | no wait | 250 ms | 1,000 ms |
|---|---|---|---|
| Cold 50K prefill, real Python source | 1,903 tok/s | 1,878 | 1,822 |
| Cold 50K prefill, random filler | 2,210 | 2,124 | 2,184 |
| Eight streams, decode | 139.6 tok/s (6.04 steps/s) | 142.5 (6.30) | 140.4 (6.22) |

Everything sits within 4%, inside the run-to-run spread of these cells. The one consistent sign was the
eight-stream step rate, about 4% lower with no wait. The 250 ms bound fired on 185 of 997 steps in those
prefill-heavy cells, and on 229 of 48,497 steps (0.5%) over five hours of eight agent sessions. The average
wait was 106 to 158 ms a step, but most of that is the worker waiting on the CUDA event for the previous step,
which the ids depend on, not the fill itself (6 to 32 ms a step on average). So under our load the wait neither
helps nor hurts measurably, and we kept it. Your no-wait result at one stream fits that.
