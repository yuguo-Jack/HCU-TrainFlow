# [Bugfix][Spec Decode] Use the target's kernel block sizes for EAGLE draft attention

[Upstream PR](https://github.com/vllm-project/vllm/pull/64777) · state: open · merged: False

## Original PR description

[by Claude Code]

## Purpose

Fixes #64652.

In the V2 model runner, EAGLE draft acceptance collapses after the first position whenever the target's backends need smaller kernel blocks than `--block-size`. For example, MiniMax-M3's sparse attention only runs 128-token pages, so this happens at `--block-size 256/512` on GB200.

**Cause:** the target model runner picks one kernel block size per KV cache group across all of that group's backends (`init_attn_backend` → `prepare_kernel_block_sizes`), and the KV cache is laid out in those kernel blocks. `DraftModelSpeculator.set_attn` then calls `init_attn_backend` again with only the draft layers. That re-selects the kernel block size from the draft backend alone and discards the result (`_`).

On GB200, FlashInfer (and Triton) accept the full 512-token block, so the draft's attention groups get no kernel split. Logged on the MiniMax-M3 repro at `--block-size 512`:

```
target group FLASHINFER          kernel_block_size 128
target group MINIMAX_M3_SPARSE   kernel_block_size 128
draft  group FLASHINFER          kernel_block_size None   # reads 512-token pages
```

Draft prefill reuses the target's attention metadata, so draft position 1 is correct. Draft decode steps 2+ build metadata from the draft's own groups and read the cache with the wrong page size, so their proposals are almost never accepted.

**Fix:** `init_attn_backend` takes optional `kernel_block_sizes`. `set_attn` passes `prepare_kernel_block_sizes(kv_cache_config, target_attn_groups)`, so the drafter uses the same selection policy as the target (including block-outermost packed caches, which keep the allocation's block size).

## Test Plan

- New unit test `tests/v1/worker/test_gpu_attn_utils_kernel_block_size.py`: a 512-token group whose target backend only supports 128 and whose draft backend also supports 512. It checks that the draft keeps 128 when selected from the target's groups, and that with a block-outermost packed cache the draft gets the 512 allocation size.
- End-to-end on 1× GB200 (4 GPUs), `nvidia/MiniMax-M3-NVFP4` TP2 + `Inferact/MiniMax-M3-EAGLE3-GQA` (3 speculative tokens), using the repro from #64652 (48 coding requests, concurrency 2).

## Test Result

Unit tests: both pass on H100 with the PR's sources over the latest nightly image (0.33.0rc1.dev573). `tests/v1/worker/test_attn_utils.py` gives 84 passed with or without this PR; its 10 DeepSeek-V4 cases fail on a circular import in both runs, which comes from loading the source over the image.

Accepted share at draft positions 1 / 2 / 3:

| `--block-size` | Before | After |
| --- | --- | --- |
| 512 | 0.83 / 0.16 / 0.03 | 0.80 / 0.62 / 0.48 |
| 128 (control) | 0.80 / 0.63 / 0.48 | — |

After the fix the draft's FlashInfer group logs `kernel_block_size 128`. Without the fix, a small dense model (Qwen3-8B + EAGLE3 on H100, `--block-size` 64/128/256) already gives identical acceptance at every block size, because its target and draft pick the same kernel block size.

Could we reuse the existing allocation-size selection helper here? For block-outermost packed caches, `prepare_kernel_block_sizes()` deliberately keeps manager-sized blocks, while `AttentionGroup.create_metadata_builders()` can choose a smaller kernel size for an individual backend. That means `groups[0].kernel_block_size` need not be the size used to allocate this KV group.

`target_attn_groups` already contains the full set of backends used by the runner, so this reuses the existing selection policy, including its packed-cache handling:

```suggestion
            kernel_block_sizes=prepare_kernel_block_sizes(
                kv_cache_config, target_attn_groups
            ),
```

Also extend the existing import in this file:

```python
from vllm.v1.worker.utils import AttentionGroup, prepare_kernel_block_sizes
```

A packed-cache regression case would help cover this distinction; the current test has `kv_cache_tensors=[]` and replaces `create_metadata_builders`, so it does not exercise the per-backend subdivision.

Validation scope: code inspection and a synthetic selection-only check using the original helper functions with stand-in backends/specs. The check showed a packed allocation of 512 with effective target/draft sizes of 128/512, where the first-group expression forwards 128. I have not reproduced a GPU serving failure for that configuration.

Thanks, good catch. You're right that `groups[0].kernel_block_size` is a per-backend choice and can differ from the size the group was allocated with in the block-outermost packed layout. I've switched to your suggestion: `set_attn` now passes `prepare_kernel_block_sizes(kv_cache_config, target_attn_groups)`, so the drafter goes through the same selection policy as the target, including its packed-cache handling.

Since that always yields a full list, `init_attn_backend` no longer needs the per-group `None` fallback. It now uses the given sizes as-is when they are provided and selects them otherwise.

I also added `test_packed_cache_keeps_allocation_block_size`, which uses a block-outermost `KVCacheTensor`. It checks that the drafter gets the 512 allocation size rather than the target backend's 128. As you noted, the test still stubs `create_metadata_builders`, so it covers the size handed to the drafter, not the per-backend split itself.
