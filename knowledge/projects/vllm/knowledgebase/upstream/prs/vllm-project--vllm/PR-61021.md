# [ROCm][Perf] Fuse add-RMSNorm into AITER FlyDSL INT4 QuickReduce

[Upstream PR](https://github.com/vllm-project/vllm/pull/61021) · state: closed · merged: False

## Original PR description


> **Needs AITER >= 0.1.27** (ROCm/aiter#6369, `QuickAllReduceInt4.allreduce_rmsnorm`). It is called directly, with no fallback. Draft until `docker/Dockerfile.rocm_base` pins it.

<!-- markdownlint-disable -->

## Overview

FlyDSL INT4 QuickReduce is the INT4 path since #59478, but with `fuse_allreduce_rms` on it ran the prefill all-reduce and then a separate add-RMSNorm. AITER v0.1.27 adds the add-RMSNorm epilogue to the FlyDSL kernel; this routes the payload through it when FlyDSL takes it. #61020 builds on this PR to also fuse the MXFP4 activation quant.

Not a duplicate: searched open PRs for "FlyDSL QuickReduce RMSNorm", "quick reduce rmsnorm" and "flydsl allreduce". #56326 fuses AR + RMSNorm + per-token FP8 quant in the custom all-reduce kernel, and #55917 adds a plain FlyDSL all-reduce for RDNA4; neither touches the QuickReduce path.

## Claims

- With INT4 QuickReduce on, `fuse_allreduce_rms` takes the fused FlyDSL kernel for the prefill all-reduces the fusion pass covers (up to 4096 tokens at hidden 8192; see Limitations). The "fusion does nothing" warning from #59478 is gone.
- `amd/Qwen3.8-2.4T-A95B-Quark-MXFP4`, TP8, MI355X, `max-num-batched-tokens 8192`, two runs per arm, against main with the same flag: **mean TTFT -1.2% geomean** (-0.7% without the noisiest point), output throughput +0.5%, mean TPOT -0.3%. Most prefill chunks at 8192 tokens are above the pass's range, which is why the effect is small. Stacking #57547, which lifts that range, gives TTFT -2.2% and throughput +0.6% geomean.
- GSM8K (greedy, 1319 problems) is unchanged: C vs B flips go both ways, exact McNemar p >= 0.09.

## Details

**Before.** With FlyDSL QuickReduce owning a payload, `_rocm_aiter_fused_allreduce_rmsnorm_impl` ran FlyDSL all-reduce plus a separate add-RMSNorm, so `fuse_allreduce_rms` did nothing for the prefill-sized all-reduces FlyDSL is fastest on.

**After.** On the non-one-stage branch, `_rocm_aiter_fused_allreduce_rmsnorm_impl` asks `QuickAllReduce` first:

- `should_fused_allreduce_rmsnorm(inp, residual, weight)` accepts the call when `all_reduce` would run the payload through FlyDSL (`uses_flydsl_int4`), the kernel supports the hidden size (`QuickAllReduceInt4.supports_rmsnorm`, owned by AITER), and the residual and weight are bf16, contiguous and 16-byte aligned. It reads only tensor metadata, so it adds no host-device synchronization.
- `fused_allreduce_rmsnorm(...)` runs the fused kernel and returns `(out, residual_out)`, with Gemma (`1 + weight`) norms supported.

Decode sizes, which the one-stage custom all-reduce owns, keep their path. A payload FlyDSL takes but the kernel declines keeps #59478's unfused all-reduce + RMSNorm. The methods live on `QuickAllReduce` because it already owns the FlyDSL object. +53 / -17 non-test lines.

**Limitations and CI gaps**

- **Prefill coverage.** The fusion pass's range stops at the custom all-reduce's 64 MiB limit (4096 tokens at hidden 8192 in bf16). With `max-num-batched-tokens 8192`, chunks of 4097 to 8192 tokens keep the unfused path. #57547 (open) lifts the limit; with it applied in both arms the same sweep gives TTFT -2.2% and throughput +0.6% geomean, and the 128 MiB payloads of 8192-token chunks take the fused route.
- **Arms.** B and C both enable the one-stage decode fusion that the flag turns on, so C vs B isolates this PR; B vs A is reported separately. A is a single run.
- **Coverage.** Measured on gfx950, TP8, one model. The AITER kernel admits gfx942 but was tested only on gfx950. TP2/TP4 end to end and a second model are not run.
- **CI.** The unit tests run in the MI355 "Distributed Features" step. The end-to-end runs need 8x MI355X and the 2.4T checkpoint, so they ran outside CI.
