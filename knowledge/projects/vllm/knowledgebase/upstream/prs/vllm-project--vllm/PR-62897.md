# [Spec Decode] Fix race on the drafter's backup next-token ids

[Upstream PR](https://github.com/vllm-project/vllm/pull/62897) · state: open · merged: False

## Original PR description



## Overview

Fixes a GPU memory fault in EAGLE/MTP speculative decoding with async scheduling: the drafter's backup next-token ids live in one pinned host buffer that the CPU refills for step N+1 before step N's non-blocking upload has run, so the drafter can embed the async-scheduling placeholder `-1`. Related, none of which covers this race: #47029, #46947 / #46946, #53029, #57562, #42572 / #42261.

## Claims

- No more `vectorized_gather_kernel` fault (`F.embedding` with index -1) in the drafter under async scheduling + prefix caching + an unsharded draft vocab embedding (e.g. `-tp 1 -dp 8 --enable-expert-parallel` with MTP).
- `SpecDecodeBaseProposer` and `ExtractHiddenStatesProposer` upload backup ids from a double-buffered host buffer (`DoubleBufferedCpuGpuBuffer`), so a pending copy's host values are never overwritten.
- `eagle_prepare_next_token_padded` (Triton and CPU C++) range-checks the backup token like it already does sampled tokens; an out-of-vocab backup becomes 0. Rows that use the backup are discarded or have no accepted token, so outputs are unchanged.

## Validation

End to end, 8x MI355X (ROCm 7.14), a large MoE model with MTP (`num_speculative_tokens=1`), lm_eval RULER `niah_single_1` @8K run right after an 8k/1k load ladder. The "with fix" column used an equivalent out-of-tree patch on an earlier vLLM:

| config | without fix | with fix |
|---|---|---|
| DP8/EP8 + MTP1 (defaults) | engine crash (2 of 2 nodes) | 0.998, no fault; gsm8k 0.955 |
| DP8/EP8 + MTP1, `--no-enable-prefix-caching` | 0.994 | n/a |
| DP8/EP8, no MTP | 0.998 | n/a |
| TP8 + MTP1 | 0.998 (vocab-parallel embedding masks the id) | n/a |

## Details

**Root cause.** `prepare_next_token_ids_padded` writes each request's backup id (`get_token_id(num_tokens_no_spec - 1)`) into a pinned `CpuGpuBuffer` and calls `copy_to_gpu`, a non-blocking H2D copy that reads host memory only when the stream reaches it, after the target forward. The buffer is written in `sample_tokens`, outside the `prepare_inputs_event` / `synchronize_input_prep` guard. With async scheduling and a long step N (e.g. a 16K-token prefill), the CPU prepares step N+1 and refills the host buffer before step N's copy runs, so step N's drafter uploads step N+1's values. For a request that just became a decode, that value is the `-1` placeholder, and the kernel stored it unchecked as the drafter's next input id.

Prefix caching puts a discarded row where a decode lands one step later: in step N a partial prefill with a cache hit (`num_computed > 0`) is reordered to row 0 as a long extend and uses the backup; in step N+1 the two prefills that just finished are decodes in rows 0-1, and row 0 of the overwritten buffer is `-1`. With TP>1 the vocab-parallel embedding masks out-of-range ids, which hides the bug.

**Cost.** `acquire()` synchronizes on the event of the copy issued from the same host buffer two steps earlier, which has normally completed, so it should not block in steady state. One event record per step.

**Not included.** Clamping the target `input_ids` for the NaN-logits case (id == vocab size) is #53029's territory.

**Tests.** The CPU test stands a recording fake in for `torch.Event` to check that the two buffers alternate and that each waits on its own previous copy, an ordering a real device event cannot expose deterministically. The kernel test is a real Triton launch. `tests/v1/spec_decode/test_eagle.py::test_prepare_next_token_ids` covers the proposer path in CI.
