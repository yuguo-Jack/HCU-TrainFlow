# [Kernel] Fuse AWQ dequantization with GEMM in batch-invariant mode on SM89

[Upstream PR](https://github.com/vllm-project/vllm/pull/57047) · state: open · merged: False

## Original PR description

## Summary

Adds a fused W4A16 Triton kernel (`awq_gemm_fused_fp32`) that unpacks AWQ int4 weights and performs the GEMM without materializing the full FP16 weight, replacing the existing full-dequantize + `torch.matmul` path under `VLLM_BATCH_INVARIANT=1` for AWQ Triton (`AutoAWQLinearMethod`). Scoped to SM89, FP16 activations/scales, asymmetric AWQ int4, group size 128, contiguous tensors, K a multiple of the group size, N aligned to 32; all other configurations keep the existing fallback unchanged.

## Why this is not a duplicate

- Searched #27433 (the batch-invariance tracking issue) and its comments — no existing claim or in-progress work on an AWQ-specific fused kernel.
- `gh pr list --search "awq_gemm_fused"` / `"auto_awq.py in:body"` / `"awq_triton in:body"` and `gh search code --owner vllm-project "awq_gemm_fused_fp32"` all return no hits.
- #46639 (Marlin MoE batch invariance) and #53403 (docs: tested-models list) touch related but disjoint code (Marlin MoE, not AWQ Triton GEMM).

## Test commands and results

```
.venv/bin/python -m pytest tests/kernels/quantization/test_awq_triton.py -v
.venv/bin/python -m pytest tests/quantization/test_auto_awq.py -v
```
65/65 pass on a real RTX 4090 (SM89): 48 shape-sweep cases (incl. tiling-boundary M=127/128/129), 5 validation-rejection cases, 8 batch-invariance byte-exact cases (`torch.equal` on raw bytes, not `assert_close`, so +0.0/-0.0 can't hide), 4 dispatch cases (contiguity-independence, BI-off, unsupported group-size, real-model integration).

**Independent numerical check**: a from-scratch NumPy FP64 reference (no vLLM dequant code reused) against the real `Qwen/Qwen3-4B-AWQ` checkpoint weights, 4 real projection shapes (qkv/o/gate_up/down) at M=1/32/129. Fused kernel's max abs error vs. this reference is consistently at or below the existing dequant+matmul path's error vs. the same reference, at every shape and M tested (including M=129, a large-M point not covered by the byte-exact batch-invariance tests).

**Real-engine checks** (`vllm.LLM`, Qwen3-4B-AWQ, real Attention + paged KV cache):
- BS1 vs BS32 and prefill-vs-decode logprobs: bit-exact (max abs diff 0.0).
- CUDA graph capture/replay: eager vs. compiled match at M=128/129/256, contiguous and non-contiguous inputs, including replay after buffer update.
- Baseline (legacy dequant+matmul) vs. fused kernel next-token logprobs on 3 fixed prefixes (24/85/391 chars): top-1 token matches on all 3; max logprob diff ~1.3e-2 to 2.3e-2. This is a numerical spot-check, not a bit-exactness claim — the two algorithms use different reduction orders and are not expected to be identical, only both individually batch-invariant.

## Model evaluation

Full GSM8K (1319 questions, 5-shot, greedy), same checkpoint/prompts/decoding config, baseline (`VLLM_BATCH_INVARIANT=0`) vs. prototype (`VLLM_BATCH_INVARIANT=1`, exercising the fused kernel):
- Baseline accuracy: 82.87%. Prototype: 82.94%. Δ +0.08pp (~1 question of 1319). Invalid rate 0.0% both arms.

## Known limitations

- The fused kernel is not yet in vLLM's JIT kernel-warmup path, so the first live inference call compiles it inline (observed latency spike). Warmup registration is out of scope for this PR.
- An unrelated, pre-existing lm_head `OutOfResources` (shared memory) bug in vLLM's own `linear_batch_invariant` persistent-matmul kernel was reproduced via one lightweight test harness at this vocab size; not related to this patch, not yet filed upstream, root cause not confirmed.

## 3. `vllm bench serve` — end-to-end perf

Both arms run with `VLLM_BATCH_INVARIANT=1` (the fused kernel only activates under batch-invariant mode, so a `BI=0` vs `BI=1` comparison would conflate "cost of batch-invariant mode itself" with "this kernel's effect," which isn't what this PR claims). Isolated legacy-dequant+matmul vs. the fused kernel via a `sitecustomize.py` monkeypatch of `awq_gemm_fused_fp32`, loaded into both the API server and its spawned engine-core worker via `PYTHONPATH` — real multiprocess `vllm serve`, not an in-process shortcut.

```
vllm serve Qwen/Qwen3-4B-AWQ --quantization auto_awq --dtype float16 --max-model-len 2048 \
  --gpu-memory-utilization 0.85 --trust-remote-code

vllm bench serve --backend vllm --model Qwen/Qwen3-4B-AWQ --dataset-name random \
  --random-input-len 512 --random-output-len 128 --num-prompts 200 --seed 0
```
