# [ROCm][Perf] Add AITER FlashKDA prefill backend for GLM KDA

[Upstream PR](https://github.com/vllm-project/vllm/pull/63568) · state: open · merged: False

## Original PR description



## Overview

On ROCm, `--kda-prefill-backend flashkda` is rejected at argument parsing
(`--kda-prefill-backend=flashkda is only available on CUDA.`). This PR makes it
run AITER's FlashKDA chunked prefill (`chunk_kimi_delta_attn`) for the
GLM-5.3-Flash KDA layers on ROCm gfx950. `auto` is unchanged and stays on Triton.

## Claims

- ROCm gfx950: `--kda-prefill-backend flashkda` runs GLM-5.3-Flash KDA prefill
  through AITER FlashKDA. AITER reads and updates the paged fp32 recurrent state
  in place and writes into the layer output, so the state gather, the state
  scatter and the merge copy are skipped.
- Measured (MI355X, TP2, image+text requests): output
  throughput +5.6 % to +7.4 % at concurrency 16–64, TTFT −7 % to −9 %, TPOT
  −5 % to −7 %; the gold-answer probability check shows no change beyond noise.
  With breakable CUDA graphs (`FULL_AND_PIECEWISE`): +4.8 % to +7.3 %.
- An unmet requirement is a startup error, not a silent fallback.
- Unchanged: `auto` and `triton` on ROCm, all CUDA paths, and steps that carry
  speculative-decode tokens (they keep the Triton chunk path). Other ROCm KDA
  models still reject `flashkda`, now when their layer is built.

## Validation

**Serving.** Speculative decoding off.

- Image: `vllm/vllm-openai-rocm:nightly-rocm72-c50aca14416ef29f6ed0ed256302f30646726dcd`

  three files are identical in `c50aca144` and this PR's base.
- Hardware: AMD Instinct MI355X (gfx950), tensor parallel 2.
- Model: `amd/GLM-5.3-Flash-Quark-MXFP4`, revision `b5688f25491202978c19c4d036eef579f61bbe07`.

  text per request, 1024 input / 128 output tokens (range ratio 0.8), request

## Details

- **Scope.** `Glm5NextLinearAttention` (`vllm/models/glm5next/common/kda.py`),
  used only by GLM-5.3-Flash, on ROCm gfx950; CUDA is unchanged. The Kimi-K3,
  Kimi-Linear and AliceAI KDA layers also read `--kda-prefill-backend`: on ROCm
  `flashkda` now passes argument parsing, and their layers reject it when built.
- **Requirements**, checked at layer construction; the error lists every unmet
  one: `VLLM_ROCM_USE_AITER=1`, gfx950, AITER 0.1.23 or later (paged
  `state_cache` and `out`), head_dim 128, bfloat16, `lower_bound` in [−5, 0),
  and an fp32 recurrent state (not `--mamba-ssm-cache-dtype bfloat16`).
- **Backend name.** On ROCm the layer stores `aiter_flashkda`, so the CUDA
  FlashKDA code, which reserves prefix-cache checkpoint blocks, is not entered.
- **Numerics.** FlashKDA uses chunk size 32 and Triton 64; outputs agree to
  bf16 precision, not bit for bit.
- **Host read.** AITER reads `cu_seqlens` on the host to plan its chunks, so the
  call runs under `gpu_sync_allowed()`, as the FLA path does for its chunk
  indices. ROCm/aiter#6912 adds a `cu_seqlens_cpu` argument that would let a
  follow-up pass the host bounds instead.
- **Not measured:** concurrency outside 16–64, long inputs, TP 1/4/8,
  speculative decoding, AITER 0.1.23 to 0.1.25.
- **Related PRs** (checked 2026-10-25). None routes GLM-5.3-Flash KDA prefill to
  AITER.
  - #55737 (merged): CUDA FlashKDA for GLM-5.3-Flash; this PR gives `flashkda`
    a ROCm path.
  - #56036 (open): AITER `chunk_kimi_delta_attn` for Kimi-K3 under the same
    value, with the same `arg_utils.py` change. It returns the final state for
    the layer to scatter; this PR uses the paged `state_cache`.
  - #59552 (merged): `rocm_aiter_ops.kda_chunk_prefill`; the new
    `kda_flashkda_prefill` follows it.
  - Nearby edits without functional overlap: #63072 and #61614 (other branches
    of `kda.py`), #61951 (Triton checkpoints; `aiter_flashkda` reserves none),
    #61250 (FlashInfer selection in the same resolver).

I read the code and the AITER v0.1.26 entry points but ran nothing myself. I think the change is well contained: an opt-in backend name, `auto` unchanged, spec steps kept on the Triton path. The perf methodology is sound (same image, interleaved launches, A/A-based standard error, kernel provenance from the Triton cache). In my opinion, the existing performance/accuracy tests already justify this PR. However:

- Testing with long-context inputs would be a valuable addition because AITER may switch to a segmented recurrence once a sequence reaches 64 chunks of 32 tokens (`flash_kda.py:821-857`, `flash_kda.py:1082-1096`). The reported runs and the GPU parity test stay around 1K tokens or below. @amd-sriram's TP4 sweep covers the throughput and TTFT point, but 1) it measures more than this PR, and 2) addresses accuracy only partially: a perfect NIAH score only indicates accuracy that is above a certain threshold for both arms. What is still missing is a triton versus flashkda accuracy comparison at the maximum supported length, with a score that is less than perfect (like the logprob checks in this PR).


- One serving comparison with prefix caching left on would also be useful. A cache hit passes `has_initial_state` and the saved state slot directly to AITER (`gdn_attn.py:560-561`, `kda.py:761-764`).

`vllm/engine/arg_utils.py:2875` — With this, `flashkda` reaches every ROCm KDA layer. The shared Kimi GDN layer rejects it only by `assert` (`kimi_gdn_linear_attn.py:285`), so under `python -O` the flag is ignored and the Triton kernel runs. Turning that check into `raise ValueError` would keep the rejection. The Kimi-K3 path still raises later, making the issue more cosmetic. (PR #56036 also touches this hunk for Kimi-K3.)
