# [Rust Frontend] Reject max_tokens above max_model_len like Python

[Upstream PR](https://github.com/vllm-project/vllm/pull/63964) · state: closed · merged: True

## Original PR description

## Overview

Python's chat and completions reject an output budget larger than the whole context window. `build_tok_params` passes the request's budget and `max_model_len` to `TokenizeParams`, whose `__post_init__` (`vllm/renderers/params.py`) raises a 400 before rendering: "`max_tokens=N cannot be greater than max_model_len=M. Please request fewer output tokens.`", with `param` naming the field (`max_completion_tokens` when the chat request sets it, otherwise `max_tokens`). A budget that fits the window is then clamped to the room the prompt leaves by `get_max_tokens()`. The Rust frontend only clamps: `vllm_text::resolve_max_tokens` takes the minimum of the requested budget and `max_model_len - prompt_len`, so `max_tokens=100000` against a 4096-token window succeeds and generates up to the window instead of returning 400. This PR adds the rejection to the chat and completions handlers and their render handlers.

## Claims

- Chat and completions requests whose output budget is above `max_model_len` return 400, as do their render requests; `param` names `max_completion_tokens` or `max_tokens`.
- A budget within `max_model_len` but above the room the prompt leaves is still clamped and returns 200.
- `/inference/v1/generate` is unchanged and still clamps any budget.

## Details

| Request | Python | Rust before | Rust after |
|---|---|---|---|
| chat or completions, budget > `max_model_len` | 400 | 200, clamped | 400 |
| chat or completions, `max_model_len - prompt_len` < budget ≤ `max_model_len` | 200, clamped | 200, clamped | 200, clamped |
| chat or completions render, budget > `max_model_len` | 400 | 200 | 400 |
| `/inference/v1/generate`, any budget | 200, clamped | 200, clamped | 200, clamped |

**Ownership and layering.** The rejection is protocol policy, not a property of the shared lowering: Python's generate route builds `TokenizeParams(max_total_tokens=None)` and only clamps, and Rust's generate route lowers through the same `vllm_text::lower_sampling_params`, so putting the check in `resolve_max_tokens` would wrongly reject generate requests. The check is a small shared helper in `routes/openai/utils` (`validate_max_output_tokens`) called by the chat and completions handlers and their render handlers on the lowered request's `max_tokens`, right after `prepare_*`/`lower_*` (so the model-not-found and other compat checks still come first, as in Python). Those handlers are where `max_model_len` is known (the engine's value on serve, the configured value on the render server, unlimited when unset); passing it into `prepare_*` instead would touch about 70 test call sites.

**Deviations.**

- Rust normalizes the deprecated chat `max_tokens` into `max_completion_tokens` when the request is parsed, so a chat request that sends only `max_tokens` is reported with `param` and message `max_completion_tokens`, where Python says `max_tokens`. The status code and the budget/limit values match.
- Python's final message carries `VLLMValidationError`'s ` (parameter=max_tokens, value=65)` suffix and Rust's does not. Rust error messages omit that suffix throughout and carry the field in `param`, so this is the same wording difference as for every other ported validation.

Python reference: the check came with `TokenizeParams` in vllm-project/vllm#32863; vllm-project/vllm#57035 later stopped subtracting the output budget from the prompt budget, which left this check as the only rejection of a large budget. No Python test pins the message.

Overlaps vllm-project/vllm#63649, which adds the same check to the chat and completions routes (not the render routes). The closed vllm-project/vllm#58711 rejected a different case (a budget above the room the prompt leaves, which both frontends clamp since vllm-project/vllm#57035) and did it in the shared `resolve_max_tokens`, which also rejected generate requests.
