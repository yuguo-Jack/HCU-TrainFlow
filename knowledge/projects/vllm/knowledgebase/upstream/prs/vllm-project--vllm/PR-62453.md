## Original PR description

# [Bugfix][NIXL] Fix host-buffer P/D for hybrid Mamba models

## Overview

With `kv_buffer_device="cpu"`, P/D disaggregation of a hybrid Mamba/GDN model (e.g. Qwen3.5) is broken on the latest main in two places. It works on v0.28.0 with the same model and configuration, so both are regressions. Reproduced at `b2456c622b`; both affected functions are unchanged at `fb61ac07bd`, current main as of 2026-10-19.

1. **Startup crash on the latest main.** Both engines fail in `register_kv_caches` with `NIXL_ERR_NOT_FOUND`, because a Mamba layer's host buffer drops the page padding that the NIXL descriptors assume. On v0.28.0 the same deployment starts normally.
2. **Corrupted KV on the decoder.** Once the engines start, D's host-to-device sync overwrites received KV with host pages NIXL never filled, so outputs are garbage. 

Bug 1 traces back to #51718 (padded layer views, in v0.29.0+) from code history; Bug 2 regressed in #53780 (per-region transfer geometry, in v0.30.0+).

## Claims

- Engines with `kv_buffer_device="cpu"` and a hybrid Mamba model start again. Host buffers of padded layers keep the padded page stride that registration and descriptors use.
- D keeps the KV it received: each KV cache group syncs only its own layers at its own blocks.
- No change for `kv_buffer_device="cuda"` or for layers without page padding.

## Details

**Background: the shared block pool.** With HMA, every KV cache group allocates from one block pool of uniform pages. A KV cache tensor is shared by one layer from each group, and a block id belongs to exactly one group at a time. Every layer's view spans all pages, but a layer only uses the pages of its own group's blocks. Uniform pages mean a GDN state (2,146,304 bytes) is padded to the attention page (2,359,296 bytes), recorded as `MambaSpec.page_size_padded`.

**Flow with `kv_buffer_device="cpu"`**, for one request whose GDN group 0 owns block 40 and whose attention group owns blocks 31-37:

1. *Register (P and D).* `initialize_host_xfer_buffer` allocates one host buffer per layer. `register_kv_caches` registers each buffer's storage with NIXL and builds descriptors. For `MambaSpec` layers, the block length and stride are `page_size_bytes`, the padded page.
2. *Save (P).* After the prefill, `save_kv_to_host` copies the request's blocks D2H into the host buffers.
3. *Read (D).* NIXL READ fills D's host buffers. Since #53780, each group's descriptors cover only its own layers' regions, so a layer's host buffer is filled only at its own group's blocks: the attention buffers at 31-37, the GDN group 0 buffers at 40.
4. *Sync (D).* `sync_recved_kv_to_device` copies host buffers H2D into the device views, then D computes the last prompt token.

**Bug 1: host buffers lose the page padding.** Since #51718, a padded layer's device view has shape `(num_blocks, 1, 1, state_content_size_bytes)` with block stride `page_size_padded`. `initialize_host_xfer_buffer` allocated `torch.empty(kv_cache.shape)`, which copies the shape but not the stride, so the host buffer is contiguous with the unpadded block size. Registration nevertheless strides descriptors by the padded page. The descriptors run past the end of the registered buffer and `prep_xfer_dlist` fails. Even with a larger registration, the data would be misaligned: D2H/H2D copy blocks by index at the tensor's own stride, while NIXL reads at the padded stride.

*Fix:* when a layer's spec has `page_size_padded`, allocate `num_blocks * page_size_padded` bytes and view them with the device view's shape and a block stride of one padded page. The inner dims stay contiguous. Layers without padding are allocated as before.

**Bug 2: D's sync overwrites received KV** The sync flattened all groups' block ids and copied every layer at all of them. Because device pages are shared across groups, copying attention layer *k* at block 40 writes attention's never-filled host page 40 over the GDN state just received in that same device page. Likewise, GDN layers overwrite the attention KV at 31-37. Which one is corrupted depends on copy order, but one always is.

*Fix:* iterate `kv_cache_config.transfer_groups` together with the request's per-group block ids, and copy each group's layers only at that group's blocks. Each layer is still copied once per request, as after #54483. KV-sharing layers are no longer copied; they are not in any transfer group.
