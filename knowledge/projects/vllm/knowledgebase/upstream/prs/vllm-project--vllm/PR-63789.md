# [Perf][Rust Frontend] Skip detokenization for gRPC requests that read no text

[Upstream PR](https://github.com/vllm-project/vllm/pull/63789) · state: closed · merged: True

## Original PR description

## Overview

A gRPC `Generate` request with `ResponseOptions.output_text=false` no longer detokenizes, and stop strings are rejected for such requests, as Python does with `detokenize=False`. Today the server still runs the incremental decoder and decodes every logprob candidate, and then [`to_sequence_output`](https://github.com/vllm-project/vllm/blob/e4db46c79bca354fef07197465faea14ca563c09/rust/src/server/src/grpc/convert.rs#L362-L366) throws the text away.

**Size: about 60 lines of non-test Rust** (+61/−16, not counting tests, comments, blank lines and reindentation). The logic is three small pieces:
- the decoder choice: one `Option<&Tokenizer>` decides both decoding and logprob strings, and `None` selects `TokenOnlyDecoder`, an 18-line no-op trait impl;
- `Option<&Tokenizer>` threaded through logprob decoding, about 14 lines;
- the stop-string check in `TextRequest::validate` and its error variant, about 12 lines.

The rest of the +381/−55 diff is tests (about 260 added lines, mostly gRPC test setup and one snapshot) and doc comments.

## Claims

- **No detokenization** for `output_text=false`. No decode stream is created (and so no prompt copy), no `decode` runs per token, nothing is flushed, and no token strings are built for logprobs or prompt logprobs. This uses the same per-request switch as Python's `SamplingParams.detokenize=False`.
- **Text-layer CPU per output token drops 85%** without logprobs (0.31 → 0.046 µs) and **76%** with top-5 logprobs (1.27 → 0.29 µs), medians of 5 runs. This is a microbenchmark; see Validation.
- **Token IDs, logprob values, usage and finish info are identical.** The proto is unchanged: `CandidateTokenInfo` has no text field.
- **`output_text=false` with stop strings now returns `INVALID_ARGUMENT`.** Stop strings are matched on decoded text, so the two contradict each other. Python's `SamplingParams` rejects `stop` with `detokenize=False` the same way. This is a wire behavior change; see Details.
- `/v1/completions` and `/v1/chat/completions` are unchanged; both set `detokenize: true`.

|---|---|---|---|

fn outputs(prompt: &Arc<[u32]>, text_ids: &[u32], top_k: usize) -> Vec<GenerateOutput> {
    let ids: Vec<u32> = text_ids.iter().copied().cycle().take(OUTPUT_TOKENS).collect();

    let last = chunks.len() - 1;

        .into_iter()
        .enumerate()
        .map(|(i, chunk)| {
            let mut out = GenerateOutput::for_test(
                (i == 0).then(|| Arc::clone(prompt)),
                chunk.to_vec(),
                (i == last).then_some(FinishReason::Length),
            );
            if top_k > 0 {
                out.logprobs = Some(Logprobs {
                    positions: chunk
                        .iter()
                        .map(|&token_id| PositionLogprobs {

                                    token_id: token_id.wrapping_add(rank) % 150_000,
                                    logprob: -(rank as f32),
                                    rank: rank + 1,
                                })
                                .collect(),
                        })
                        .collect(),
                });
            }
            out
        })
        .collect()
}

## Details

**Why.** Token-in/token-out gRPC clients such as Dynamo's vLLM sidecar detokenize and match stop strings themselves, so they send `output_text=false`. For every such request the server still:
- copies the prompt into a `DecodeStream` ([`incremental.rs:63`](https://github.com/vllm-project/vllm/blob/e4db46c79bca354fef07197465faea14ca563c09/rust/src/tokenizer/src/incremental.rs#L63)) and seeds it from the prompt tail;
- runs up to two windowed `decode` calls per generated token, the second only when the token releases text ([`incremental.rs:180`](https://github.com/vllm-project/vllm/blob/e4db46c79bca354fef07197465faea14ca563c09/rust/src/tokenizer/src/incremental.rs#L180), [`:226`](https://github.com/vllm-project/vllm/blob/e4db46c79bca354fef07197465faea14ca563c09/rust/src/tokenizer/src/incremental.rs#L226));
- decodes every logprob candidate and every prompt-logprob position ([`logprobs.rs:119`](https://github.com/vllm-project/vllm/blob/e4db46c79bca354fef07197465faea14ca563c09/rust/src/text/src/output/logprobs.rs#L119)), although the proto has no field for them;
- flushes the final text, which `to_sequence_output` then replaces with `""`.

All of this runs inline on the server's tokio workers.

**Change.**
- `TextDecodeOptions` gains `detokenize: bool` (default `true`), Python's name and meaning. gRPC maps `output_text` onto it; unset means `true`, as the proto documents.
- When `detokenize` is false, `decoded_text_event_stream` uses a zero-sized `TokenOnlyDecoder` instead of `create_decode_stream`. It is the counterpart of Python's base `IncrementalDetokenizer`, which `OutputProcessor` picks when `detokenize=False`.
- `TextRequest::validate` rejects non-empty stop strings when `detokenize` is false (`Error::StopStringsRequireDetokenize`). It is a request validation error, so gRPC returns `INVALID_ARGUMENT`. The message suggests enabling detokenization or using stop token IDs. The check sits in `vllm-text`, which owns stop-string matching, so every route gets it.
- Python rejects the same combination in two places:
  - [`SamplingParams._verify_args`](https://github.com/vllm-project/vllm/blob/e4db46c79bca354fef07197465faea14ca563c09/vllm/sampling_params.py#L737-L740);
  - the token-in/token-out server with `--tokens-only` ([`serving.py:222`](https://github.com/vllm-project/vllm/blob/e4db46c79bca354fef07197465faea14ca563c09/vllm/entrypoints/scale_out/token_in_token_out/serving.py#L222-L231)), which likewise points users at `stop_token_ids`.
- The unary path now moves decoded logprobs into the collected output instead of cloning them. This predates the PR but is in the same function.
- Logprob decoding takes `Option<&Tokenizer>`, as Python's `LogprobsProcessor` does. Without one, token strings stay empty. Python uses `None` here; the Rust type is a `String`, and gRPC never reads it.

**Wire behavior change.**
- `output_text=false` with non-empty `stop_strings` used to succeed: the server decoded internally to match the strings, then dropped the text. It now returns `INVALID_ARGUMENT`.
- **Who sent it:** no released Dynamo. v1.6.0 always sends `output_text=true`. Dynamo `main` sent the combination only between ai-dynamo/dynamo#15550 and ai-dynamo/dynamo#17324, and now sends `output_text=false` with no stop strings.
- A client that wants vLLM to stop at a string can send `output_text=true` and ignore the text.
- The proto comment on `output_text` now states the rule. The proto's shape is unchanged, so vllm-proto stays at 0.6.0.
- Because `ServerInfo.proto_version` doesn't change, a client can't detect the new rejection from the version; it sees the `INVALID_ARGUMENT`.

**Limits.**
- With logprobs requested, the no-text path still builds `DecodedLogprobs` with empty strings on each update. That's one `Vec` per position, and it accounts for most of the remaining 0.29 µs/token.
- gRPC requests with `output_text=true` still decode logprob strings the wire can't carry. Skipping those too is a possible follow-up.
- The request path still reads `vocab_size()` once per request. That isn't detokenization.

**Related.**
- #56851 (RFC) asks for per-request text output on `/inference/v1/generate`.
- #51904 adds stop strings to that route and checks `detokenize` with stop strings in the route, because the shared layer had no `detokenize`. `TextDecodeOptions.detokenize` and the shared validation now cover that.
- #46723, #51281 and #54050 make decoding cheaper when it runs. This PR removes it when nobody reads the result.
