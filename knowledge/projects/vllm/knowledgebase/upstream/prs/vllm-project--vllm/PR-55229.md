# [Bugfix][DP] Prevent mismatched collectives on duplicate resume

[Upstream PR](https://github.com/vllm-project/vllm/pull/55229) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Repeated `resume_generation()` calls can make DP ranks take different branches when request-wave notifications arrive at different times. Use the flag established by pause consensus so a duplicate resume cannot leave only some ranks entering the resume collective.

## Claims

- Skip duplicate resumes consistently across ranks, preventing a hang or collective failure.
- Preserve resume synchronization for paused engines and newly joined Elastic EP ranks.
- Continue rejecting a resume while a MoE DP pause is still in flight.

## Validation

A real-engine regression reproduces the failure without a mock, and it passes with the fix. GPU results used NVIDIA B200 GPUs with driver 580.95.05 and a precompiled build of main `b8c04dd3b4`, which this branch includes. The comparison tree is this branch with only the production files restored to main.

The test uses `AsyncLLM` with DP=2, expert parallelism, and `ibm-research/PowerMoE-3b`. It resumes rank 1 while idle, adds a request to rank 0, and then resumes rank 0, so the ranks disagree on whether the engines are running.

```sh
RAY_ADDRESS=local .venv/bin/python -m pytest \
  tests/v1/distributed/test_async_llm_dp.py::test_dp_duplicate_resume_while_one_rank_starts_a_wave -q
```

```text
Without the fix: only EngineCore_DP1 logs "setting pause state to UNPAUSED".
                 +++ Timeout +++ after the marker's limit, then pytest-timeout dumps the stacks and stops the process.
With the fix:    the test passes.
```

This result is from this branch merged onto main `410ab341a8`, with the same build, because no native code changed between the two commits, at both sizes that CI uses: TP=1 with DP=2, and TP=2 with DP=2. The same result holds at `b8c04dd3b4` at TP=1 with DP=2 and the earlier 600 s limit.

The marker uses `method="thread"` because the hang is in the engine, so a signal cannot end the test reliably. The limit is 1200 s because an earlier 600 s limit expired during `Building JIT module fused_moe_trtllm_sm100` on a pod with an empty JIT cache, before the test reached its resume calls. A later run on that pod took 515 s while it rebuilt those modules. With a warm cache, the test takes about 30 s.

Related engine tests also pass. `test_async_llm.py` ran from a scratch copy with `Qwen/Qwen3-0.6B`, because its Llama checkpoint is gated on this host, and the result is the same on main. `test_streaming_input.py` and `test_engine_core.py` pass, except `test_engine_core_tp`, which fails the same way on main.

These runs ran on the same hardware against main `3a90cc6fd0`, before the latest commits on this branch. The later commits change only a code comment and the test marker:

- A stress run sent duplicate resumes during new waves with no forced order. The engine hung within the first 25 rounds without the fix. With the fix, all 200 rounds completed, and a pause with `mode="keep"` over in-flight requests followed by two resumes also completed.
- The complete `test_async_llm_dp.py` file passes. The Ray variants need an isolated Ray instance in my environment, so that run used `RAY_ADDRESS=local`.
- `tests/distributed/test_elastic_ep.py` passes for the `enforce_eager_none`, `enforce_eager_light`, `enforce_eager_heavy`, and `cuda_graphs_heavy` variants. The test ran from a copy without its `ray stop --force` fixture, because that command stops the Ray instance of the host environment. The `cuda_graphs_heavy_nixl_ep` variant fails at server startup with `Server failed to start in time` and a `Process group` error, before any resume call. It fails the same way without this change.

Model accuracy was not evaluated, because this change only affects which ranks enter the resume collective.

**CI coverage:** `(L4) Distributed DP Basic` runs the regression file at TP=1 with DP=2, and the optional `(L4) [Nightly] Distributed DP Extended` runs it at TP=2 with DP=2. Their `(MI355)` mirrors also select it, but ROCm was not run. The NVIDIA step for `test_elastic_ep.py` is commented out, and the changed files do not trigger the optional `(MI300) Elastic EP Scaling` step, so Elastic EP has only the local run above. The regressions of this PR also pass with this branch merged onto main `b2a9480dc7`, with its own precompiled build and `VLLM_WORKER_MULTIPROC_METHOD=spawn` as in CI. Upstream checks are stopped at contributor authorization, so Buildkite has not run this branch.

## Details

`engines_running` can differ across ranks because wave messages arrive independently. `ignore_start_dp_wave` is set by pause consensus, so ranks agree on collective participation. The change follows the [review feedback](https://github.com/vllm-project/vllm/pull/55229#discussion_r4170893423). The async RL guide now documents duplicate-resume safety and the in-flight-pause restriction.

This does not duplicate an open PR. Merged #59559 changes wave wake-up announcements and does not change this resume check.

I think `ignore_start_dp_wave` alone is enough here, and it's the safer thing to key the barrier on. It's set at pause consensus (same step on every rank) and only cleared in this function, so every rank agrees on it whenever a resume shows up. The scheduler pause state is set whenever each rank's pause message lands, so it depends on per-rank timing.

The only state where the two conditions would give different answers is "paused without consensus", and that already hits the `pending_pause` raise above. So behavior is the same today, and your test table passes unchanged.

```suggestion
        # ignore_start_dp_wave is set at pause consensus (same step on every
        # rank) and cleared only below, so all ranks agree on it when a
        # resume arrives. Skip the barrier iff it is clear.
        if not self.ignore_start_dp_wave:
```
