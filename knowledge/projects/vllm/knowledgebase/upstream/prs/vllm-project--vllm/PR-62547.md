# [Security][CI/Build] Add pre-commit check for hardcoded trust_remote_code=True

[Upstream PR](https://github.com/vllm-project/vllm/pull/62547) · state: closed · merged: True

## Original PR description

## Overview

Adds a pre-commit check that flags a literal `trust_remote_code=True` passed in a call inside `vllm/`. Hardcoding it overrides the user's `--trust-remote-code` setting, which was CVE-2026-27893 (GHSA-7972-pg2x-xr59, fixed in #36192).

## Claims

- Catches the CVE-2026-27893 pattern at the exact vulnerable lines, and the later reintroduction in #37408.
- Zero findings on current `main`, so it adds no churn.
- Not a duplicate: no open or closed PRs add a check for this pattern. #18018 added the pickle-import ban and mentioned broader security checks as a possible follow-up.

## Validation

- `pytest tests/tools/test_check_trust_remote_code.py`: 14 passed
- `pre-commit run check-trust-remote-code --all-files` on `main`: passed (0 findings)
- `pre-commit run` on the changed files: all applicable hooks pass, including `check-test-tethering`
- Against real code:

| Code | Result |
|---|---|
| `nemotron_vl.py` / `kimi_k25.py` before #36192 (`git show 00bd08e^:…`) | flags lines 459 and 177, the two CVE lines |
| Same files after #36192 | clean |
| `quark.py` at the head of #37408 | flags line 96, the reintroduced pattern |

## Details

- **Why:** the pattern keeps coming back. CVE-2026-27893 was itself the pattern surviving two earlier fixes (CVE-2025-66448, CVE-2026-22807) in different code paths, and #37408 reintroduced it 12 days after the fix. Review caught that one; this catches it in CI first.
- **AST-based**, like `check_boolean_context_manager.py`, so docstrings, strings and comments never trigger it.
- **Only a literal `True` passed in a call** is flagged. `model_config.trust_remote_code`, `False`, and default values in function signatures are fine.
- **Scoped to `vllm/`**: tests, examples and benchmarks intentionally pass `trust_remote_code=True` for specific models (hundreds of occurrences), which is the user's choice.
- **Escape hatch:** `# trust-remote-code: ok (reason)` on the same line.
- **Limitation (intentional):** it targets accidental reintroduction, not deliberate evasion (e.g. `x = True; f(trust_remote_code=x)`). That's the job of review.

**AI assistance:** I used Claude to help draft the check and tests. I reviewed every line, ran the validation above myself, and can answer questions about any part of it.
