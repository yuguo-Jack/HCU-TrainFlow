# [Bugfix][LoRA] Use 3D MoE LoRA wrapper for Gemma4

[Upstream PR](https://github.com/vllm-project/vllm/pull/64437) · state: open · merged: False

## Original PR description



## Overview

Fixes #64436. Gemma4 MoE expert LoRA adapters produced by PEFT use the fused 3D layout, but Gemma4 does not declare `is_3d_moe_weight`, so loading them with the default configuration raises a `ValueError` inside EngineCore and kills the engine. This PR declares `is_3d_moe_weight` on both Gemma4 model classes and fills in the text config `architectures` that the 3D wrapper needs when a nested checkpoint is loaded through `Gemma4ForCausalLM`.

## Claims

- PEFT-format (fused 3D) expert LoRA adapters load on Gemma4 MoE with the default configuration, for `Gemma4ForConditionalGeneration`, a standalone `Gemma4ForCausalLM` checkpoint, and a multimodal checkpoint loaded with `hf_overrides={"architectures": ["Gemma4ForCausalLM"]}`.
- Served output with the adapter matches the base model with the LoRA delta merged into the expert weights, and matches a Hugging Face PEFT fp32 reference within bf16 noise.

## Validation

It covers the multimodal checkpoint, a standalone text checkpoint, and the multimodal checkpoint loaded through `Gemma4ForCausalLM` via `hf_overrides`. ## Details

Root cause: Gemma4 keeps all experts in fused 3D tensors, so PEFT expert adapters store one flat `lora_A`/`lora_B` pair per projection. `LoRAModelManager` chooses `FusedMoE3DWithLoRA` only when the model sets `is_3d_moe_weight`; Gemma4 did not, so it used the 2D `FusedMoEWithLoRA`, and `_validate_moe_lora_format` rejects fused 3D weights for 2D wrappers unless mixed format is enabled. The fix follows the other fused 3D MoE models (Qwen3.5 MoE, Qwen3-VL-MoE, gpt-oss). No checkpoint name mapping is needed: on current main the experts are registered as `layers.N.experts`, which already matches the PEFT names.

`FusedMoE3DWithLoRA` reads `architectures` from the model config. Released Gemma4 checkpoints declare it only at the top level, so `Gemma4ForCausalLM` (which keeps the nested `text_config`) sets `architectures` when it is missing, as PaliGemma and LLaVA do for their text configs. The multimodal class already passes `architectures=["Gemma4ForCausalLM"]` when building its language model.

Tradeoff: Gemma4 now defaults to the 3D wrapper, so a 2D (per-expert, megatron-style) Gemma4 adapter needs `--enable-mixed-moe-lora-format` with `is_3d_lora_weight=false`, as documented in `docs/features/lora.md`. The Hugging Face Gemma4 model has no per-expert submodules, so PEFT produces only the fused 3D layout.

Not duplicating existing work: #43254 adds `is_3d_moe_weight` and `get_expert_mapping` to `Gemma4ForCausalLM` only (the multimodal class used to serve the released checkpoints is unchanged, and `get_expert_mapping` is already provided by the MoE layer on main); it has had no updates since 2026-10-13. #50252 changes `_GEMMA4_EXPERT_PARENT_MAPPER`, which no longer exists on main. Unsloth exports Gemma4 MoE expert adapters in the same fused 3D layout (see the MoE comment in #41754).

Limitations: validated on Intel XPU only, TP=1, with tiny random models; no CUDA run and no full-size checkpoint with a trained adapter. EP and fully sharded LoRA use the existing `FusedMoE3DWithLoRA` paths and were not exercised here.
