# [Feature] Fused K-RoPE + static FP8 per-tensor KV Cache write

[Upstream PR](https://github.com/vllm-project/vllm/pull/45370) · state: open · merged: False

## Original PR description

Addresses the "RoPE + Quant | FP8 per-tensor" support in #36066.

This implements a custom fused K-RoPE + static FP8 per-tensor KV cache write operator for both CUDA and AMD ROCm. The fused kernel performs Key rotary embedding (RoPE) and per-tensor static quantization (converting from FP16/BF16 input to FP8 E4M3 cache) in a single GPU pass, eliminating the HBM round-trip to separate unfused kernels. 

E2E model serving (ROCm 7.0, gfx1201, Qwen2.5-7B-Instruct with FP8 KV cache): verified correct coherent generation and latency reduction.

Hardware details:
AMD Radeon AI PRO R9700
RDNA4 Architecture

🟡 **Severity: MEDIUM**

Out-of-bounds shared memory read in NeoX RoPE path. When `rot_dim % 8 == 0` but `rot_dim % 16 != 0` (e.g. `rot_dim=8,24,40,...`), `embed_dim` is not 8-aligned, so the 8-element `int4` vector load at `smem_k[peer_base]` can cross the head boundary and read past the `total_elems`-sized shared memory allocation for the last KV head.
Helpful? Add 👍 / 👎

<details>
<summary>💡 Fix Suggestion</summary>

**Suggestion:** The root cause is that `embed_dim = rot_dim / 2` may not be 8-aligned when `rot_dim % 16 != 0` (e.g. rot_dim=8,24,40,...). This causes two problems: (1) the int4 vector load at `smem_k[peer_base]` can read past the shared memory allocation, and (2) the 8-element chunk can straddle the embed_dim boundary, making the single `peer_base` calculation incorrect for some elements in the chunk.

The simplest and safest fix is to add an input validation check in the host-side launcher (near line 369, alongside the other TORCH_CHECKs) to reject configurations where embed_dim is not 8-aligned when using NeoX RoPE:

```cpp
if (is_neox) {
    TORCH_CHECK(rot_dim % 16 == 0,
                "NeoX RoPE requires rot_dim to be a multiple of 16 "
                "(embed_dim = rot_dim/2 must be 8-aligned for vectorized kernel)");
}
```

This ensures embed_dim is always a multiple of 8, so the 8-wide int4 vector loads never cross head boundaries or the embed_dim boundary within a head. If support for non-16-aligned rot_dim is needed in the future, the NeoX RoPE path would need to be reworked to use element-wise loads with per-element peer_base computation instead of vectorized int4 loads.
