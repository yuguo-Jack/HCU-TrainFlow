# [Bugfix] Pad Marlin FP8 MoE weight dims to tile alignment under TP > 1

[Upstream PR](https://github.com/vllm-project/vllm/pull/36807) · state: closed · merged: False

## Original PR description

The Marlin kernel requires `size_n % 64 == 0` (tile_n_size) and `size_k % 16 == 0` (tile_k_size). When tensor-parallel sharding splits MoE weights across GPUs, per-rank dimensions can violate these constraints and cause a crash at model load time on any GPU that falls back to the Marlin FP8 MoE path (CC < 9.0: L40S, A100, A10G).

Example — Nemotron Nano 3 at TP=4 (intermediate_size=1856):
  w13 gate+up: size_n = 1856 / 4 * 2 = 928... actually 464 per-shard → 464 % 64 = 16 ✗
  w2  down:    size_k = 1856 / 4     = 464... actually 232 per-shard → 232 % 16 = 8  ✗

This error is never triggered on Hopper+ (CC >= 9.0) because vLLM selects native FP8 MoE kernels (CUTLASS/Triton) on those GPUs and never enters the Marlin path.

Fix:
- marlin_utils_fp8.py repack_weight(): pad size_n to the next multiple of 64 and size_k to the next multiple of 16 before calling gptq_marlin_repack.
- marlin_utils_fp8.py permute_scales(): pad scales to match padded size_n.
- fused_marlin_moe.py _fused_marlin_moe(): compute padded sizes, use them for GEMM calls, trim w13 padding before activation, pad intermediate activation output before w2 GEMM.

Padding with zeros is mathematically a no-op: zero weights and zero inputs contribute nothing to GEMM outputs. For already-aligned dimensions all padding amounts are zero and no tensor operations are performed.

- alvinttang · COMMENTED · 2026-03-12T03:46:20Z · [source](https://github.com/vllm-project/vllm/pull/36807#pullrequestreview-3933727593)

The padding approach is correct in principle: aligning `size_n` to `MARLIN_TILE_N=64` and `size_k` to `MARLIN_TILE_K=16` at weight-load time, then mirroring the same padding at inference time to keep the GEMM shape contract intact. A few things worth verifying: (1) The trim after the w13 GEMM (`intermediate_cache1[:, :_w13_n].contiguous()`) introduces an extra allocation — if this is on the hot path under high load, it may be worth only trimming when `_w13_n_padded \!= _w13_n` (which the code already guards, good). (2) The zero-padding of `intermediate_cache2` before the w2 GEMM assumes that the repacked w2 weight's zero-padded columns produce zero output — this is only safe if the padded columns of the repacked weight are also zero; please confirm `pack_fp8_to_int32` + `gptq_marlin_repack` preserve zero-padding in the repacked layout. (3) There are no tests added for the TP>1 path — a unit test parameterized over non-tile-aligned intermediate sizes (e.g., `N=232`) would make this much safer to maintain.

- ptempier · comment · 2026-06-27T10:52:33Z · [source](https://github.com/vllm-project/vllm/pull/36807#issuecomment-4816916339)

We hit the same crash independently on `NVIDIA-Nemotron-3-Super-120B-A12B` with a ModelOpt FP8 checkpoint, TP=4 (`intermediate_size=2688`, so `672` per rank — not a multiple of 64). The repro and root cause described here match exactly.

For the record, our local workaround (predates finding this PR) only padded the **w13 (gate+up) N dimension**, and only in `_fused_marlin_moe`'s GEMM call / intermediate buffer sizing — not at weight-load/repack time, and not the **w2 (down_proj) K dimension**:

```python
N = marlin_moe_intermediate_size(w1, w2)
w13_num_shards = 2 if activation.is_gated else 1
_logical_n13 = w13_num_shards * N
_tile_n13 = 64
_pad_n13 = (_tile_n13 - _logical_n13 % _tile_n13) % _tile_n13
_padded_n13 = _logical_n13 + _pad_n13
# ... use _padded_n13 for buffer sizing and the GEMM's size_n,
# then intermediate_cache1 = intermediate_cache1[:, :_logical_n13].contiguous()
# before the activation step.
```

This is **narrower than your fix** — it's inert if N is already aligned, but it doesn't touch weight-load-time repacking (`repack_weight`/`permute_scales`) and doesn't handle the w2 K-alignment case at all. After this got us past the w13 crash, we immediately hit a second crash on w2 (`Invalid thread config`, `K=672` not aligned to 64 after TP=4 sharding of `intermediate_size=2688`). We worked around *that* with `--enable-expert-parallel` (which makes `intermediate_size_per_partition` the full 2688, already aligned, instead of padding K) rather than fixing K-padding — so it's a deployment-level dodge, not a fix, and it's not generally applicable (doesn't help anyone who can't use EP). We never got a fully clean validation on this checkpoint: after working around the w13/w2 crashes we hit a separate, unrelated weight-loading correctness bug in the TP-sharding offset math (not related to padding at all) and abandoned the FP8 checkpoint for an AWQ-4bit one instead, so we can't offer a tested end-to-end confirmation of your PR specifically — just confirmation that the underlying N/K-alignment crash is real and independently reproduced.

Your fix is more complete than what we had (handles both N and K, at both weight-load and inference time), so we have nothing to add fix-wise — just corroboration that this is a real, recurring problem worth unblocking. The `needs-rebase` + the open correctness question from @alvinttang's review (whether `gptq_marlin_repack`'s padded columns stay zero) seem to be what's stalling it.

Cross-referencing two other open PRs that look like the same root-cause family — Nemotron's MoE `intermediate_size` not dividing evenly across TP ranks, tripping different kernels' alignment/group-size constraints:
- #44563 — WNA16 INT4 kernel, `BLOCK_SIZE_K // group_size` must be in `{1,2,4,8}` (we found a counter-example where that PR's clamp doesn't fully fix it either, see our comment there)
- #37296 — Marlin FP4 (NVFP4) N-dimension alignment, also reproduced on a Nemotron-3 checkpoint

Might be worth a shared test/utility across all three quant paths rather than three separate ad hoc fixes, given how consistently Nemotron's intermediate sizes trip this class of bug.

*(Disclosure: this analysis was produced with AI assistance — Claude — based on a real crash reproduced on our own deployment; I've reviewed the reasoning and the patch excerpt above myself.)*
