# [Bugfix] Validate tensor dtypes and topk_weights length in the moe_wna16 GEMM op wrappers

[Upstream PR](https://github.com/vllm-project/vllm/pull/50561) · state: open · merged: False

## Original PR description

## Purpose

`moe_wna16_marlin_gemm` and `moe_wna16_gemm` pass untyped data pointers to kernels that reinterpret them as a fixed type, and never check the tensors they get. A wrong dtype or a short `topk_weights` gives silently wrong results (and, for narrower dtypes or short tensors, out-of-bounds reads) instead of an error. This PR adds host-side checks:

- `moe_wna16_marlin_gemm`: `topk_weights` must be fp32 (the kernel reads it as `const float*`), plus the same assert at the `_fused_marlin_moe` Python seam.
- `moe_wna16_gemm`: `b_scales` and `output` must match `input.scalar_type()`, which alone picks the kernel's `scalar_t`. The check runs before `zero_()`, so a rejected `output` is not modified first.
- Both ops: `topk_weights.numel() >= size_m * top_k`. Both kernels index `topk_weights` up to `size_m * top_k` without looking at its length (`marlin_template.h#L434`, `#L490-L491`; `moe_wna16.cu#L56`, `#L217`, at `fa6c407d`).

All in-tree callers already pass the right dtypes and an fp32 `topk_weights` of `size_m * top_k` elements, so these are misuse traps, not live bugs, and there is no behaviour change for in-tree callers. The marlin checks also run when `mul_topk_weights=False`, so an out-of-tree caller passing a placeholder there is now rejected. The out-of-bounds reads are derived from the source, not observed under a sanitizer. Related: https://github.com/vllm-project/vllm/issues/48895.

## Test Plan

```bash
pytest tests/kernels/moe/test_moe.py -k "topk_weights or mismatched_dtypes"
```

Three negative tests (10 cases) that call the ops directly and expect `RuntimeError`:

- `test_fused_marlin_moe_rejects_invalid_topk_weights`: bf16, fp16, and a 15-element fp32 `topk_weights` with `size_m * top_k = 16`
- `test_moe_wna16_gemm_rejects_mismatched_dtypes`: `{b_scales, output}` × `{bfloat16, float32, int8}`
- `test_moe_wna16_gemm_rejects_short_topk_weights`: a 15-element fp32 `topk_weights`

The marlin test uses n = k = 128, because at 64 no marlin thread config fits and the call fails before reaching the kernel.

- Shreyas-jk · comment · 2026-09-24T20:23:54Z · [source](https://github.com/vllm-project/vllm/pull/50561#issuecomment-5821660395)

The `topk_weights` check here would have saved time on #48895, though not in the way that thread might suggest at a glance.

That issue's minimal repro passes `topk_w.to(torch.bfloat16)` straight into `moe_wna16_marlin_gemm`, so it never reaches the Python-side assert and lands exactly on the case this PR rejects. What makes it worth a check rather than a docstring is that the resulting garbage looks reasonable. bf16 and f32 share the sign and exponent layout, so on little-endian each f32 the kernel reads is built from the second bf16 of a pair. Running that layout on CPU at the repro's shape (128 routing weights, torch 2.13, no GPU):

```
bf16 buffer: 128 elems, 256 bytes -> kernel reads 128 f32 = 512 bytes; rows >= 64 are out of bounds
rows 0..63: f32[r] vs bf16 row 2r+1: max rel err 1.90e-03, bf16 ulp ~ 7.81e-03
rows 0..63 landing within 5% of their own weight: 4/64
```

So each row gets another row's routing weight at a plausible magnitude, and the back half of the buffer is read past its end. In #48895 that presented as "the epilogue applied the wrong row's weight", and a good deal of that thread went into looking for an indexing bug in `marlin_template.h`.

To be clear about what this would and wouldn't have caught: the in-tree callers all pass fp32 (`fused_marlin_moe` asserts it, the batched path builds fp32), and the reporter's replay scripts pass engine-captured fp32 weights and still fail, so there is a separate real bug in that issue that this check does not address. What it would have done is invalidate the minimal repro on the spot, instead of after several rounds of forensics.

One gap, optional: the kernel bounds its index by `size_m * top_k` (`marlin_template.h:434` and `:490`), not by the length of `topk_weights`. A correctly-typed but short fp32 tensor is still read past the end, which is the same class of hole this PR is closing. `ops.cu` already checks `c.size(0) == size_m * top_k`, so a matching `topk_weights.numel() >= size_m * top_k` would fit right next to the dtype check. No in-tree caller can hit it today, since they all pass `(M, topk)`.

Edit (2026-10-05): the fp32 dtype of the capture blob's topk_weights was inferred, not verified, and the replay failures I cited are reported only in prose (the issue and the reporter's notes); I found no replay logs in their repo. Measured results: https://github.com/vllm-project/vllm/issues/48895#issuecomment-6005811616
