# [CI] Split (B200) LM Eval Humming Activation FP8/INT8 into per-model jobs

[Upstream PR](https://github.com/vllm-project/vllm/pull/58195) · state: closed · merged: False

## Original PR description

## What

`:nvidia: (B200) LM Eval Humming Activation FP8/INT8 TEMPORARY` runs 16 GSM8K activation-quant configs (9 FP8 + 7 INT8) as two sequential pytest invocations in one optional pod, well over the 20-minute target. Following the per-model-job convention from #57965, this replaces it with five content-named jobs, one config list each, so the timeline and job names say exactly what ran.

## Old

```
lm-eval-humming-b200-act   "(B200) LM Eval Humming Activation FP8/INT8 TEMPORARY"
├── config-act-fp8.txt   (9 configs)
└── config-act-int8.txt  (7 configs)
```

## New

```
lm-eval-humming-b200-qwen35-35b          (B200) LM Eval Humming Qwen3.5 35B               config-b200-qwen35-35b.txt
lm-eval-humming-b200-qwen3-30b-act-fp8   (B200) LM Eval Humming Qwen3 30B Activation FP8  config-b200-qwen3-30b-act-fp8.txt
lm-eval-humming-b200-qwen3-30b-act-int8  (B200) LM Eval Humming Qwen3 30B Activation INT8 config-b200-qwen3-30b-act-int8.txt
lm-eval-humming-b200-gpt-oss             (B200) LM Eval Humming GPT-OSS                   config-b200-gpt-oss.txt
lm-eval-humming-b200-small-models        (B200) LM Eval Humming Small Models              config-b200-small-models.txt
```

Old → new key: `lm-eval-humming-b200-act` → the five `lm-eval-humming-b200-*` keys. `config-act-fp8.txt` and `config-act-int8.txt` stay unchanged, because the (H100) activation job still runs both. The 16 YAML configs are untouched; coverage is multiset-identical to the two lists on current `main`, including the AWQ config that runs in both the FP8 and INT8 commands today.

## Expected runtime and overhead

Predictions from per-config log timestamps on a recent passing `main` run, as a share of the old job's pytest time:

| job | pytest (share of old) | non-pytest overhead | main overhead cause |
| --- | ---: | ---: | --- |
| Qwen3.5 35B | ~32% | <1m | pod setup + checkout |
| Qwen3 30B Activation FP8 | ~29% | <1m | pod setup + checkout |
| Qwen3 30B Activation INT8 | ~18% | <1m | pod setup + checkout |
| GPT-OSS | ~11% | <1m | pod setup + checkout |
| Small Models | ~11% | <1m | pod setup + checkout |

- Slowest job stays under the 20-minute target; timeouts drop 50 → 30.
- Aggregate: about +3 worker-minutes versus the unsharded job (four repeated pod setups), well inside the ≤20 budget.
- The 30B family is the only one split further, along the activation-dtype axis the old label already used; together it would sit just under 20m with no headroom for new configs.

## Notes

- **Same 16 configs, unchanged.** Multiset equality against `main`'s `config-act-fp8.txt` + `config-act-int8.txt` checked locally after rebasing onto #46528, which renamed the Qwen3-4B RTN config to `Qwen3-4B-mixed-quant-RTN-no-w4a4-humming.yaml`; the Small Models list uses the new name.
- **Convention:** content-named single-replica jobs with per-job config lists, as in #57965 — no `parallelism`, no `Shard %N`, no indexed shard lists.
- **Five block steps instead of one.** Each job is `optional: true` with its own block step (same tradeoff as #57965).
- No test files move; these steps have no AMD mirror; no other consumer references `lm-eval-humming-b200-act`. The (H100) activation job is split separately in a stacked follow-up.
