# [Core] Update PyTorch to 2.14.0, torchvision to 0.29.0, triton to 3.8.0 (release channel)

[Upstream PR](https://github.com/vllm-project/vllm/pull/52183) · state: closed · merged: True

## Original PR description

## Purpose

Update the PyTorch ecosystem to **2.14.0**, resolving wheels from the **release** channel:

- `torch`: → **2.14.0**
- `torchvision`: → **0.29.0**
- `triton`: **3.8.0** (unchanged — current for 2.14.0)
- `torchaudio`: **2.11.0** (unchanged — newest published on every channel)

CUDA stays on **cu130**.

This PR originally targeted the 2.14.0 release candidate on the test channel. That premise has
expired: **2.14.0 went GA on 2026-09-02 and 2.14.1 on 2026-09-30**, both published to the release
index. Continuing to pin an RC from `whl/test/` would ship a version that is two releases stale.

### Verified availability on the release channel before pinning

| Artifact | `whl/cu130` | `whl/cpu` |
| --- | --- | --- |
| `torch==2.14.0` | present (`2.14.0`, `2.14.0+cu130`) | present |
| `torchvision==0.29.0` | present (`0.29.0`, `0.29.0+cu130`) | present |
| `torchaudio==2.11.0` | present | present |
| `triton==3.8.0` | present | n/a |
| `torchao==0.18.0` | present | n/a |

`torch==2.14.0` is also on PyPI.


| Removed | File |
| --- | --- |
| `ENV UV_NO_CACHE=1` | `docker/Dockerfile.cpu` |
| `--no-cache` on the image build | `.buildkite/image_build/image_build_cpu.sh` |
| `--no-cache` on the test build | `.buildkite/scripts/hardware_ci/run-cpu-test.sh` |
| test-channel `--extra-index-url` | `tests/standalone_tests/python_only_compile.sh` |

Dropping the two `--no-cache` flags restores CPU image layer caching, which the comments noted had
been disabled at a measured cost (build 84705: 28 cached layers, zero torch downloads).

## Deliberately unchanged

**`.buildkite/scripts/check-ray-compatibility.sh`** already offers the resolver both the stable and
the test channel and lets `uv --index-strategy unsafe-best-match` pick. It resolves 2.14.1 from
stable today and still works for a future RC, so it needs no edit.

**The CPU shard timeouts in `.buildkite/hardware_tests/cpu.yaml`** (50m → 90m, 90m → 120m) are a
*different* workaround: torch 2.14 made CPU model-execution shards up to ~6.6x slower, tracked by
[pytorch/pytorch#193951](https://github.com/pytorch/pytorch/issues/193951). That issue is now closed
as completed, so by its own comment these are revertable — but the timings in the comment were
measured against the RC and there is no 2.14.1 measurement yet. Left in place deliberately: a
too-generous limit costs nothing, a too-tight one kills a shard mid-run. Worth one measured run
before reverting, as a follow-up.

## CI status

Triage of the last full run ([build 91655](https://buildkite.com/vllm/ci/builds/91655)) is in a
comment below: 14 blocking failures, of which 2 are plausible torch regressions — an NVFP4
divergence that matches the already-filed
[pytorch/test-infra#8785](https://github.com/pytorch/test-infra/issues/8785), and a ROCm
`vllm._deepselect_C` extension build failure. The rest are pre-existing on `main`, infrastructure,
or flake-shaped. That run was against 2.14.0 from the test channel; it will need a re-run on these
pins.

Pushed a follow-up commit aligning the NVIDIA pins with torch 2.14.0.

torch pins these with `==` in its wheel metadata (`PYTORCH_EXTRA_INSTALL_REQUIREMENTS` in pytorch `release/2.14`), so the values `requirements/test/cuda.txt` was compiled against for 2.13 made the lockfile unresolvable alongside the new torch — not a silent drift, an actual resolution failure on the CUDA test path.

| package | was | now | torch 2.14 (cu130) |
| --- | --- | --- | --- |
| `nvidia-cudnn-cu13` | 9.20.0.48 | **9.24.0.43** | `==9.24.0.43` |
| `nvidia-nccl-cu13` | 2.29.7 | **2.30.7** | `==2.30.7` |

Unchanged because they already satisfy 2.14: `cuda-toolkit` (13.0.3.0 normalises to `==13.0.3`), `cuda-bindings` (13.0.3 within `>=13.0.3,<14`), `nvidia-cusparselt-cu13` (0.8.1), `nvidia-nvshmem-cu13` (3.4.5).

Both new versions are published on the test channel (`test/cu130`) and on PyPI.

Checked the rest of the tree for other NVIDIA pins that might need the same treatment — there are none. `requirements/cuda.txt` only has `nvidia-cudnn-frontend>=1.19.1` and `nvidia-cutlass-dsl[cu13]==4.6.2`, neither torch-derived; no `nccl`/`cudnn`/`cusparselt`/`nvshmem` pins in any Dockerfile, `pyproject.toml`, `.in` file or buildkite config; and `requirements/test/{cpu,xpu}.txt` carry no `nvidia-*` pins.

Caveat for reviewers: this was hand-edited, not recompiled — I don't have a working `uv pip compile` path against the test index. Worth regenerating the lockfile properly to pick up any transitive changes these two bumps imply.

## Triage of [build 91655](https://buildkite.com/vllm/ci/builds/91655)

16 failures (14 blocking + 2 soft) out of 588 jobs. Compared against five `Full CI run` builds on `main` from Sep 26–29 ([91957](https://buildkite.com/vllm/ci/builds/91957), [91759](https://buildkite.com/vllm/ci/builds/91759), [91672](https://buildkite.com/vllm/ci/builds/91672), [91540](https://buildkite.com/vllm/ci/builds/91540), [91486](https://buildkite.com/vllm/ci/builds/91486)).

**Two are plausible torch 2.14 regressions. The other fourteen are not attributable to this PR.**

### 1. NVFP4 numerical divergence — reopen, don't file new

[`(B200) AsyncTP Correctness`](https://buildkite.com/vllm/ci/builds/91655#01a0e993-49cb-4f8c-b2d6-66234ac5970f)

```
tests/compile/correctness_e2e/test_async_tp.py::test_async_tp_pass_nvfp4_correctness
AssertionError: Results for model='nvidia/Llama-3.1-8B-Instruct-NVFP4' are not the same.
```

Byte-identical to [pytorch/test-infra#8785](https://github.com/pytorch/test-infra/issues/8785), which was filed against torch **2.15** and closed as completed on Sep 24. Different job there (`(B200) Sequence Parallel Correctness`), same divergence. Its reappearance on the 2.14 RC suggests either the fix didn't cover 2.14 or the bug predates where it was thought to start. I'd reopen #8785 rather than open a duplicate.

### 2. DeepSelect extension missing on ROCm — probable, not confirmed

[`(MI355) Qwen3.8-Flash-Next-FP8 Accuracy Eval`](https://buildkite.com/vllm/ci/builds/91655#01a0e9a1-698c-4f75-958f-12cdd382df50)

```
Failed to import the DeepSelect extension (vllm._deepselect_C): No module named 'vllm._deepselect_C'
ValueError: no module or parameter named 'ngram_embedding.weight_scale' in Qwen4ExpNGramEmbedding
RuntimeError: Server exited unexpectedly.
```

The weight-loading error is downstream of the missing extension, not a separate problem. Consistent with torch-ABI fallout from the bump, but "extension missing" is equally consistent with an unrelated ROCm image build problem. Confirming it needs one look at whether `_deepselect_C` compiles in the ROCm image on `main` — worth doing before attributing it to torch.

### The other fourteen

| Category | Jobs |
|---|---|
| **Pre-existing on `main`** (fails on 2–5 baselines) | `(B200) Distributed`, `(B200) LM Eval HiSparse Nightly`, `(B200) MoE Refactor DP Integration`, `(H100) Qwen3-30B-A3B-FP8-block Sync EPLB`, `XPU V1 test` |
| **Infrastructure** | `(DGX) Spark b12x Linear Kernels` (ECR DNS, 3 retries exhausted), `Intel HPU Test` (git fetch failed, soft), `GH200 Test` (soft) |
| **Environment / flake-shaped** | `(H200 MIG 35GB) Multimodal Ext Gen 1` (`finding the available memory: Insufficient Permissions` ×7), `(H200 MIG 35GB) Spec Decode AL DFlash` (`No available memory for the cache blocks`), `(H100) Fault Tolerance E2E` (45s hang assertion), `(H200 MIG 18GB) Rust Frontend OpenAI Coverage` |
| **Application-level** | `(H200 MIG 35GB) Entrypoints Integration (LLM)` (outlines grammar conversion), `(H200) LM Eval DeepSeek V3.2 TP` |

Two patterns worth knowing before anyone chases these:

- **Three separate "GSM8K collapses to 0.0000" failures are each preceded by `TimeoutError: RPC call to sample_tokens timed out`.** The accuracy threshold is reporting a hang, not a numerical regression. Easy to misfile as a model-quality issue.
- **`XPU V1 test` fails on `Simulated send_notif failure` and `forced FSM compilation error`** — those are deliberately injected faults, so that job's red is about the harness.

### Method caveat

The baselines are different commits 1–3 days either side of this build, not the same-commit twins the nightly triage automation pairs. For finding 1 that matters little, since the signature matches a known torch regression. For finding 2 it matters more: a single-occurrence build failure with no same-commit baseline is weaker evidence, and re-running that job would settle it cheaply.

For contrast, the torch-**nightly** lane is currently at 137 blocking failures, ~87 of them one memory regression ([pytorch/test-infra#8940](https://github.com/pytorch/test-infra/issues/8940)) that does **not** affect this RC — H200 MIG fails 3/92 here versus 63/87 there. On that comparison the 2.14.0 RC looks clean.
