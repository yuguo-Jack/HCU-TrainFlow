# [Bugfix][Model] Share one RoPE cache across Muse Spark NVIDIA layers

[Upstream PR](https://github.com/vllm-project/vllm/pull/65206) · state: closed · merged: True

## Original PR description


_Requested by **Simon**_



## Overview

The NVIDIA Muse Spark model builds a private fp32 RoPE table in each of its 46 RoPE attention layers. The tables are identical and cost 11.5 GiB per GPU. This PR shares one table, as #62757 did for the ROCm path.

Fixes #65205

## Claims

- Model loading drops from 81.0 to 69.75 GiB per GPU on 8x B200, TP8, `Muse-Spark-Open-816B-A42B-NVFP4`.
- The KV cache grows from 9,248,688 to 10,589,618 tokens (+14.5 %).
- Output does not change: greedy output is bit-identical, and GSM8K-100 is 96/100 on stock and 95/100 with this PR, which is within run-to-run noise.

- Two target layers must hold the same fp32 `RotaryEmbedding`.
- It uses its own empty `_ROPE_DICT`, so the CPU tables it builds do not leak into later GPU tests (the failure #65138 and #65140 fixed for the ROCm twin).

Sanity pass on fresh starts of the same setup. ## Details

Root cause, in `vllm/models/muse_spark/nvidia/model.py`:

- Each target `MuseSpark1xAttention` with RoPE constructs its own `RotaryEmbedding` with an fp32 `cos_sin_cache` of `[max_position, 64]`.
- `MuseSpark1xDecoderLayer` passes `max(config.max_position_embeddings, max_model_len)`, so the table has at least 1,048,576 rows whatever `--max-model-len` is.
- 46 of the 62 layers use RoPE, all with theta 500000. 46 × 1,048,576 × 64 × 4 B = 11.5 GiB.

Change:

- Target layers take their table from `get_rope(..., dtype=torch.float, rope_parameters={"rope_theta": theta, "rope_type": "default"})`. `get_rope` caches one instance per key, so all 46 layers share one table.
- `MuseSpark1xDecoderLayer` sizes the target table by `max_model_len`, since target positions never reach it. With a smaller `--max-model-len` the table shrinks too (64 MiB at 262,144); that case was not run end to end.
- The DSpark draft keeps its private table, dtype and size.

Numerics: each row of the table is computed the same way whatever the table length, and sharing does not change any value. On the unfused path, `_match_cos_sin_cache_dtype` now converts one shared table instead of 46 identical ones, with the same result.

Related: #63078 (open) keeps these tables fp32 at the unfused call sites. It touches different lines of `nvidia/model.py` and applies cleanly on top of this branch. #65170 (open, ROCm) moves the shared table to CUDA before the ROCm monokernel reads it; the NVIDIA path has no monokernel, and the fused kernel worked with the shared table in the runs above.
