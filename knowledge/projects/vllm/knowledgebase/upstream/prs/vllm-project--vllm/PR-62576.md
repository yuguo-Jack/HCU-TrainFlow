# [Bugfix] Defer MRV2 Triton validation to worker startup

[Upstream PR](https://github.com/vllm-project/vllm/pull/62576) · state: closed · merged: True

## Original PR description

## Overview

Defer MRV2's Triton availability check from `VllmConfig` construction to worker startup, allowing CPU frontends to build configs for GPU deployments.

## Claims

- CPU prompt-rendering processes can retain the deployment's speculative config without requiring a local Triton driver.
- Actual MRV2 workers still raise `Model Runner V2 requires Triton.` when Triton is unavailable. Feature compatibility checks remain in `VllmConfig`.

## Validation

- Config construction succeeds with Triton imports blocked, including Beam NVFP4 and Qwen3-4B with DFlash2. Prompt rendering and tokenization also succeed.
- MRV2 worker startup still rejects unavailable Triton.
- Both new regression tests and 73 related config/scheduler tests pass.

## Details

This fails when a CPU-only frontend constructs a full engine config for prompt rendering while inference runs on separate GPU nodes. For example, Ray Serve's `KVAwareRouter` starts an `LLMRouter` on each proxy node, including the CPU-only head. A deployment with speculative decoding needs MRV2, but the head has no active Triton driver. With MRV2 selected, config validation raises `Model Runner V2 requires Triton.`, preventing that router from starting and leaving the head's HAProxy on load-only routing.

`HAS_TRITON` reflects local runtime availability. Using it during config construction incorrectly requires the frontend to have the worker's runtime. This change removes the availability-based runner fallback and config-time rejection, and checks Triton in the shared worker constructor instead.

Related PR: https://github.com/ray-project/ray/pull/67174.

Open-PR searches found no equivalent CPU-frontend fix. Related [#50612](https://github.com/vllm-project/vllm/pull/50612) addresses TPU-specific config exemptions; this change moves the runtime requirement to the worker boundary.
