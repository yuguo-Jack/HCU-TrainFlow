# [Frontend] generate: keep sample logprobs as engine rows and render them without objects

[Upstream PR](https://github.com/vllm-project/vllm/pull/60542) · state: open · merged: False

## Original PR description

## Purpose

Part of RFC #57479 (cheap frontend after an RL `pause(mode="abort")`).

A non-streaming `output_mode="tokens"` `/inference/v1/generate` request with top-k logprobs costs Python objects proportional to tokens × candidates:
- a `Logprob` per (position, candidate) in the output processor;
- a pydantic `GenerateLogProbs` entry per candidate when the response is built;
- one `model_dump` and one `JSONResponse` over all of it.

After an abort, every in-flight request is rendered at once on the API server's event loop. At this PR's GPU benchmark load (32 requests × about 12.5k tokens × top-128), `/pause?mode=abort` itself takes 82–86 s to return on current main. The full RL shape (245,760 tokens × top-128) exhausted node memory on main in the RFC #57479 runs.

## Changes

**1. `FlatLogprobs` is stored as numpy columns** (`vllm/logprobs.py`).
- Entries live in append-only numpy columns, each one buffer that doubles when full: int32 token ids and float32 logprobs (the engine's dtypes), per-position first-entry ranks, and per-position end offsets only once positions have different widths. That is about 8.5 bytes per entry instead of about 90.
- A column switches to int64 / float64 when a value would not round-trip, so values read back exactly.
- Per-entry ranks and decoded tokens are kept only when needed: a non-engine rank layout, or a non-None decoded token.
- The list-like API is unchanged: `len`, `flat[i]` returning `dict[int, Logprob]`, iteration, slicing, `append`, `append_fast`, `extend`.
- New: `append_rows()` for engine rows in bulk, `rows()` for the `[N, S]` arrays, `num_entries`, `first_token_ids()`.
- This replaces the separate `ArrayLogprobs` container from the earlier revision of this PR, per review, so there is one flat logprobs container.

**2. `LogprobsProcessor` appends engine rows in bulk** when no decoded tokens are needed, for both sample and prompt logprobs. With a tokenizer it still detokenizes per position, as before.

**3. The generate endpoint renders tokens-mode logprobs from the arrays.**
- For non-streaming `output_mode="tokens"` requests with `logprobs >= 0` and no `prompt_logprobs`, it sets `flat_logprobs=True` and a private `SamplingParams._detokenize_logprobs=False`. Tokens mode never reads decoded tokens, and clients can't set the private flag.
- It then writes `GenerateLogProbs` JSON straight from `rows()`, with no Python object per entry.
- The bytes are the same as the per-entry pydantic path (`_create_tokens_logprobs` + `model_dump` + `JSONResponse`), including clamping and `rank` 0 → `null`.
- The render runs on the event loop in blocks of 8k logprob entries, with `await asyncio.sleep(0)` between blocks, like the output handler. No thread pool.
- Renders longer than one block hold a per-`ServingTokens` `asyncio.Lock`, so one API server renders one large response at a time. They share the loop's one core, so interleaving them adds no throughput; it only keeps every in-flight render's partial output alive at once. Single-block renders don't take the lock, so small requests never wait behind a large one.
- Rows that don't map directly to the per-entry shape fall back to the per-entry path for that choice. That covers irregular widths, repeated top-k ids, a sampled id not in slot 0, and values JSON can't represent.
- Unchanged: streaming, `output_mode="text"`, `logprobs=-1`, and requests with prompt logprobs. The response returns prompt logprobs as lists, so those requests keep list storage.

There is no HTTP API or output change.

**Behavior notes for direct Python users of `FlatLogprobs`.** Nothing inside vLLM depends on these, but code outside vLLM could:
- `token_ids`, `logprobs`, `ranks`, `start_indices`, `end_indices` and `decoded_tokens` are now read-only views over the columns rather than lists. Indexing, slicing, iteration, `len` and `==` against a list work as before, at O(1) per element read; they can't be mutated, and `json.dumps` needs `list(...)` first.
- `FlatLogprobs` is no longer a `@dataclass`: `dataclasses.asdict` / `replace` don't apply, and `repr` is a summary.
- Objects pickled by the old version don't unpickle with the new one.
- Stepped slices (`flat[::2]`) now return the right positions; the old code mixed in entries in between.

**Based on:** aoshen02/vllm#109 and aoshen02/vllm#111 (by @aoshen02), the Python "container hook" and "default fast render" PRs from the RFC #57479 work, ported to current main. The render targets the integer-id `GenerateLogProbs` shape of #58181 and respects `output_mode` (#58588).

**Not a duplicate.** No open PR changes how generate logprobs are stored or rendered:
- `gh pr list --repo vllm-project/vllm --state open --search "57479 in:body"` returns only #58278 and #58314 (the `/v1/completions` serializer).
- #57442 (`return_token_logprobs`, the k=0 sampled-only path) is complementary: it handles k=0, this PR handles k>0. #57442 reads `FlatLogprobs.logprobs` and `start_indices`, which still return the same values here. #60915 (packed top-k) is stacked on this PR and no longer includes #57442.

**Abort stress:** all 32 requests passed in every run. Each run left about 400k aborted positions, about 3.0 GB of response bodies. Two runs each.

| | main (`fc9b7e6546`) | this PR |
|---|---|---|
| `/pause?mode=abort` returns | 82.1 / 86.1 s | 0.37 / 0.29 s |
| abort → all bodies received and parsed | 88.5 / 86.3 s | 7.4 / 6.7 s |
| peak RSS, largest server process | 7.8 GiB | 4.1 GiB |
| peak RSS, whole server process tree | 29.9 / 29.8 GiB | 17.5 / 18.2 GiB |

The `/pause` row is the event loop being freed. On main the pause request queues behind the per-entry builds of every aborted response.

The previous revision also compared main with `/generate` switched to the existing list-backed `FlatLogprobs` (160–177 s, slower than main), so turning on the existing class alone doesn't help.

**Why no thread pool.** The previous revision built large bodies in a two-thread pool. Profiling with py-spy showed the renderer holds the GIL about 78% of the time, so the pool overlapped only the remaining ~22% (numpy and large `bytes.join`):
- At DP2 (2 API servers, ~16 aborted bodies each) the pool was about 10–15% faster than rendering on the loop: 5.4–6.2 s vs 7.0–7.9 s abort → parsed.
- At the DP8 RL shape below, nearly all of the earlier gap came from block size, not threads. The pool version rendered 1,024-row blocks (~132k entries at k=128). Under 32 concurrent renders the renderer is memory-bandwidth bound, and big blocks slow each render 3.5× vs 2.2× for 8k-entry blocks. With small blocks, the pool version (10–12 s) and this PR (11–14 s) are close there.
- Without the render lock, rendering on the loop interleaved all of a server's large bodies and used about 3.5 GiB more RSS at DP2 (21.1–21.5 GiB). The lock removes that, with latency unchanged.

So this PR keeps the existing pattern (chunked work on the loop) and adds no thread pool or tunable.
