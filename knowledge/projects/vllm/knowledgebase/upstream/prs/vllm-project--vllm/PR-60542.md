# [Frontend] generate: keep sample logprobs as engine rows and render them without objects

[Upstream PR](https://github.com/vllm-project/vllm/pull/60542) · state: open · merged: False

## Original PR description

## Purpose

Part of RFC #57479 (cheap frontend after an RL `pause(mode="abort")`).

A non-streaming `output_mode="tokens"` `/inference/v1/generate` request with top-k logprobs costs Python objects proportional to tokens × candidates:
- a `Logprob` per (position, candidate) in the output processor;
- a pydantic `GenerateLogProbs` entry per candidate when the response is built;
- one `model_dump` and one `JSONResponse` over all of it.

After an abort, every in-flight request is rendered at once on the API server's event loop. At this PR's GPU benchmark load (32 requests × about 12.5k tokens × top-128), `/pause?mode=abort` itself takes about 92 s to return on main. The full RL shape (245,760 tokens × top-128) exhausted node memory on main in the RFC #57479 runs.

## Changes

**1. `FlatLogprobs` is stored as numpy columns** (`vllm/logprobs.py`).
- Entries live in append-only numpy columns, each one buffer that doubles when full: int32 token ids and float32 logprobs (the engine's dtypes), per-position first-entry ranks, and per-position end offsets only once positions have different widths. That is about 8.5 bytes per entry instead of about 90.
- A column switches to int64 / float64 when a value would not round-trip, so values read back exactly.
- Per-entry ranks and decoded tokens are kept only when needed: a non-engine rank layout, or a non-None decoded token.
- The list-like API is unchanged: `len`, `flat[i]` returning `dict[int, Logprob]`, iteration, slicing, `append`, `append_fast`, `extend`.
- New: `append_rows()` for engine rows in bulk, `rows()` for the `[N, S]` arrays, `num_entries`, `first_token_ids()`.
- This replaces the separate `ArrayLogprobs` container from the earlier revision of this PR, per review, so there is one flat logprobs container.

**2. `LogprobsProcessor` appends engine rows in bulk** when no decoded tokens are needed, for both sample and prompt logprobs. With a tokenizer it still detokenizes per position, as before.

**3. The generate endpoint renders tokens-mode logprobs from the arrays.**
- For non-streaming `output_mode="tokens"` requests with `logprobs >= 0` and no `prompt_logprobs`, it sets `flat_logprobs=True` and a private `SamplingParams._detokenize_logprobs=False`. Tokens mode never reads decoded tokens, and clients can't set the private flag.
- It then writes `GenerateLogProbs` JSON straight from `rows()`, with no Python object per entry.
- The bytes are the same as the per-entry pydantic path (`_create_tokens_logprobs` + `model_dump` + `JSONResponse`), including clamping and `rank` 0 → `null`.
- Bodies from 2^15 logprob entries are built off the event loop, in a shared `ThreadPoolExecutor` of two threads.
- Rows that don't map directly to the per-entry shape fall back to the per-entry path for that choice. That covers irregular widths, repeated top-k ids, a sampled id not in slot 0, and values JSON can't represent.
- Unchanged: streaming, `output_mode="text"`, `logprobs=-1`, and requests with prompt logprobs. The response returns prompt logprobs as lists, so those requests keep list storage.

There is no HTTP API or output change.

**Behavior notes for direct Python users of `FlatLogprobs`.** Nothing inside vLLM depends on these, but code outside vLLM could:
- `token_ids`, `logprobs`, `ranks`, `start_indices`, `end_indices` and `decoded_tokens` are now read-only properties that return new lists. Writing to them no longer changes the container, and reading one copies the column.
- `FlatLogprobs` is no longer a `@dataclass`: `dataclasses.asdict` / `replace` don't apply, and `repr` is a summary.
- Objects pickled by the old version don't unpickle with the new one.
- Stepped slices (`flat[::2]`) now return the right positions; the old code mixed in entries in between.

**Based on:** aoshen02/vllm#109 and aoshen02/vllm#111 (by @aoshen02), the Python "container hook" and "default fast render" PRs from the RFC #57479 work, ported to current main. The render targets the integer-id `GenerateLogProbs` shape of #58181 and respects `output_mode` (#58588).

**Not a duplicate.** No open PR changes how generate logprobs are stored or rendered:
- `gh pr list --repo vllm-project/vllm --state open --search "57479 in:body"` returns only #58278 and #58314 (the `/v1/completions` serializer).
- #57442 (`return_token_logprobs`, the k=0 sampled-only path) is complementary: it handles k=0, this PR handles k>0. #57442 reads `FlatLogprobs.logprobs` and `start_indices`, which still return the same values here. I also checked the stacked #60915 (#57442 + packed top-k) on top of this commit; details below.

Co-authored-by: @aoshen02

## Test Plan

```bash
pytest -q tests/test_logprobs.py tests/v1/engine/test_logprobs_processor.py tests/test_outputs.py \
  tests/entrypoints/scale_out/token_in_token_out/
pre-commit run --files <changed files>   # incl. mypy 3.10 and 3.12 (manual stage)
```

- `tests/test_logprobs.py`:
  - the existing `FlatLogprobs` tests pass unchanged;
  - a new randomized test checks that mixes of every append path read back like `list[dict]` across buffer growth, mixed widths, `None` positions and ranks, and int32 / float32 overflow. I checked that it catches planted bugs in offsets, widening, stepped slices and ranks.
- `test_logprobs_processor.py`:
  - bulk-stored rows read like the list path, including `logprobs=-1` and irregular widths;
  - `_detokenize_logprobs=False` keeps no decoded tokens even with a tokenizer.
- `test_logprobs_render.py` (new) covers:
  - byte identity of the rendered body against `JSONResponse(model_dump)` for k ∈ {0, 1, 3, 8}, up to 1,500 rows, and n > 1;
  - rank 0, NaN, ±inf, −0.0 and large ids;
  - each fallback case;
  - the sampled id repeated in the top-k;
  - which requests use the flat storage;
  - the offload threshold.

Real-GPU end to end (GB200, Qwen3-0.6B, `--data-parallel-size 2`, default API servers), using a driver script that is not part of this PR:
- **Parity:** sequential greedy requests with `ignore_eos` and k ∈ {0, 1, 8, 128}, compared against main with the `created` timestamp blanked.
- **Abort stress:** 32 concurrent non-streaming requests at top-128, with `POST /pause?mode=abort` 45 s after submission. The client only receives bytes while the clock runs and parses afterwards. Server RSS is sampled from the process tree.

## Test Result

- **pytest:** 221 passed, 0 failed, including the live-server tests in `test_serving_tokens.py` on GB200.
  - The 3 tests in `test_serving_multimodal_tokens.py` error at engine startup on my host: Qwen3-VL needs `vllm.vllm_flash_attn.layers`, which my precompiled build lacks. That is unrelated to this change.
  - `tests/v1/engine/test_output_processor.py` needs the gated Llama tokenizer, which my host can't download. With Qwen3-0.6B substituted it gives 40 passed and the same 7 `test_stop_token` failures as the parent commit, which are tokenizer-specific.
- **pre-commit:** clean, including mypy 3.10 and mypy 3.12.

**Parity:** the default response bytes are identical to main for all 16 requests (4 prompts × k ∈ {0, 1, 8, 128}, 256 tokens each).

**Abort stress:**
- Runs were interleaved: main, ArrayLogprobs, numpy `FlatLogprobs`, then the reverse.
- The "old `FlatLogprobs`" column is main with `/generate` switched to the list-backed `FlatLogprobs`. It was run before and after a third main run (92.6 s), to show that turning on the existing class alone doesn't help.
- All 32 requests passed in every run. Each run left about 405k aborted positions, about 3.05 GB of response bodies.

| | main | old `FlatLogprobs` | `ArrayLogprobs` (previous revision) | this PR (numpy `FlatLogprobs`) |
|---|---|---|---|---|
| `/pause?mode=abort` returns | 92.2 / 93.9 s | 159.9 / 177.1 s | 0.43 / 0.35 s | 0.45 / 0.31 s |
| abort → all bodies received | 96.0 / 94.1 s | 160.1 / 177.3 s | 6.6 / 6.1 s | 6.4 / 5.8 s |
| peak RSS, largest server process | 7.9 GiB | 6.1 / 6.3 GiB | 4.0 / 3.9 GiB | 4.0 / 4.1 GiB |
| peak RSS, whole server process tree | 29.1 GiB | 25.9 / 25.0 GiB | 17.7 / 17.8 GiB | 17.5 / 17.8 GiB |

The `/pause` row is the event loop being freed. On main the pause request queues behind the per-entry builds of every aborted response.

**CPU microbenchmarks** (one request, one engine row per step, through `LogprobsProcessor` and `_build_full_response`; best of several runs, pinned to one core).

At 12.5k tokens × top-128:

| | list (main) | old `FlatLogprobs` | `ArrayLogprobs` | numpy `FlatLogprobs` |
|---|---|---|---|---|
| ingest per engine row | 157 µs | 15.8 µs | 3.7 µs | 4.4 µs |
| stored bytes per entry | 181 | 90 | 10.5 | 10.6 |
| response build | 5.7 s | 7.6 s | 0.41 s | 0.42 s |
| build peak memory | 1216 MiB | 1216 MiB | 181 MiB | 181 MiB |

At the full RL shape (245,760 tokens × top-128), `ArrayLogprobs` and numpy `FlatLogprobs` both build the same 1.78 GB body in 8.1 s with a 3.5 GiB peak.

Other `FlatLogprobs` paths, old → new, µs per position:

| | k=5 | k=128 |
|---|---|---|
| prompt logprobs via `LogprobsProcessor` (no tokenizer) | 1.7 → 0.09 | 18 → 0.16 |
| `extend` (DELTA aggregation) | 3.5 → 1.3 | 57 → 1.4 |
| sample logprobs with a tokenizer | 58 → 67 | 333 → 335 |
| DELTA streaming (ingest + `[-1:]` slice per step) | 9.4 → 20.8 | 64 → 62 |
| `flat[i]` | 2.6 → 5.3 | 47 → 48 |
| direct `append_logprobs_for_next_position` | 1.7 → 9.2 | 18 → 35 |

The small-k per-position paths are slower; the slice costs a few numpy calls. No server endpoint enables `flat_logprobs` for streaming.
