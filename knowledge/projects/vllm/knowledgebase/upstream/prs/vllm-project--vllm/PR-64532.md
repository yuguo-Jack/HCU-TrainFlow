# [ROCm][DSv4.1] Lift the skinny-GEMM cap in the gfx942 draft lm_head test

[Upstream PR](https://github.com/vllm-project/vllm/pull/64532) · state: closed · merged: True

## Original PR description

## Overview

The gfx942 draft lm_head test still counts wvSplitK after #63179. The 315 MiB shard is over the skinny-GEMM cap, so 4- and 5-row calls leave wvSplitK and the monokernel pad is no longer visible.

## Claims

* `test_draft_lm_head_takes_5_rows_off_wvsplitk` again sees wvSplitK for up to 5 rows, and no wvSplitK for the 5-row `--monokernel` pad.
* The guard's own tests are unchanged. This test sets `VLLM_SKINNY_GEMM_MAX_WEIGHT_BYTES` to the shard and clears the cached cap on the way out.

## Validation

The failure is the three assertions on MI300 in [CI #98321](https://buildkite.com/vllm/ci/builds/98321#01a18811-a03a-4400-b411-1fcfcc35b60b) and [CI #98239](https://buildkite.com/vllm/ci/builds/98239#01a18750-a7f6-4589-af2c-ec7e5f855074). The same cases passed in [CI #97749](https://buildkite.com/vllm/ci/builds/97749#01a17f2a-f37d-40fe-8728-d233a1de50ee), before #63179. Ruff check and format pass on the file. The test skips off gfx942, so it was not rerun here.

## Details

#63179 skips wvSplitK when the weight is over the memory-side cache and `1 < n <= 5`. This shard is 32320×5120 bf16, 315 MiB, and the MI300 cap is 256 MiB. #60731's test still expects those calls. The cap in this test is the shard itself, so the row count still shows the pad. Noted on #63179 with no follow-up yet.
