# [ROCm][Quantization] NVFP4 MoE re-quantization and fused shared experts through online quantization

[Upstream PR](https://github.com/vllm-project/vllm/pull/64378) · state: closed · merged: True

## Original PR description



## Overview

Second PR of the split of #63232, stacked on #64111. Its base is `minimax-m31-flash-model`, so only this PR's commit shows up; it will be retargeted to `main` after #64111 merges. The change lets ROCm serve NVFP4-expert checkpoints such as MiniMax-M3.1-Flash: the routed experts are re-quantized to MXFP4/MXFP8 at load. It also makes fused shared experts (FSE) work with online quantization.

## Claims

- **NVFP4 MoE re-quantization without an NVFP4 backend:** main can already re-quantize serialized NVFP4 MoE (ModelOpt, compressed-tensors, Quark) to an online MoE method. This PR makes that work where no NVFP4 MoE backend exists (ROCm):
  - The NVFP4 oracle skips backend selection for layers whose checkpoint method only serves as the dequantization source (`requantization_source_scope`).
  - `dequantize_weight` for MoE now yields `(experts, w13, w2)` per group of experts, which bounds the staging memory.
- **FSE with online quantization:** `OnlineSharedExpertLoader` stages the shared expert at load and quantizes it into its routed slot after loading. It replaces `RoutedExperts._fused_shared_expert_quantizer`, which only handled full-precision shared experts. Supported combinations:
  - NVFP4 routed experts re-quantized to MXFP4, with the shared expert re-quantized to the same scheme;
  - Quark MXFP4 routed experts (kept as stored) with an MXFP8 shared expert quantized to MXFP4 online.

  FSE is refused with a warning when the shared and routed experts would not run with the same `(weight, activation)` keys. Two cases raise `NotImplementedError`: BF16 routed experts quantized online combined with a quantized shared expert, and reloading weights with FSE.
- **MiniMax-M3 on ROCm:** a clear error for the NVFP4-expert checkpoint unless the routed experts are re-quantized (`--quantization-config.moe mxfp4` or `mxfp8`).
- **Two small ROCm fixes from the same branch:**
  - gfx942: the online FP8 PTPC MoE quantizes W13 in torch, because `dynamic_per_token_scaled_fp8_quant` can crash there during load.
  - The MXFP8 Triton activation quant uses a tuned block size for M == 1.

## Details

- **Not a duplicate:** #63547 (draft) also serves the NVFP4 M3.1 checkpoint on AMD, but converts NVFP4 → MXFP4 inside the model (`minimax_m3/common/nvfp4_mxfp4.py`). This PR goes through the generic online quantization API instead, so it applies to any ModelOpt, compressed-tensors or Quark NVFP4 MoE and supports FSE.
- **Shared code touched (all at load time, no forward-path change):**
  - `resolve_quant_method` builds the checkpoint method of re-quantized experts under `requantization_source_scope`.
  - `select_nvfp4_moe_backend` returns the emulation backend inside that scope.
  - `QuantizeMethodBase.dequantize_weight` returns an iterator for MoE. All three MoE implementations (ModelOpt, compressed-tensors, Quark NVFP4) and the one caller are migrated.
  - `RoutedExperts.weight_loader` and `load_weights` route shared-expert slots through the loader.
  - `process_weights_after_loading` finalizes the staged shared experts. It is a no-op unless FSE and online quantization are both used.
  - `is_shared_expert_quant_fse_compatible` now compares the effective `(weight, activation)` keys of the routed and shared experts.
  - `QuarkLinearMethod.dequantize_weight` supports MXFP8.
- **Conflicts with main:** main's #61457 (per-layer FSE selection) landed after the source branch. I kept main's `resolve_layer_fused_shared_expert`. The source branch's extra warning, for `VLLM_ROCM_USE_AITER_FUSION_SHARED_EXPERTS` set without AITER MoE, was dropped: it also fires on CUDA, where AITER is unavailable.
- **Docs:** `docs/features/quantization/online.md` already documents NVFP4 MoE re-quantization; FSE with online quantization is not documented yet.

AI assistance (Claude) was used to port these changes from #63232 and resolve the conflicts with main. The original code is by fxmarty-amd (re-quantization + FSE), andyluo7 (gfx942 FP8) and hongxiayang (MXFP8 M=1), credited in the commit. The submitter reviewed the port and ran the tests above.

Since per-layer FSE (#61457, merged from main), `MiniMaxM3Model.load_weights` redirects a checkpoint shared expert into its routed slot only when `rocm_aiter_ops.is_fusion_moe_shared_experts_enabled()` and `extract_layer_index(name) in self.fused_shared_expert_layers`. The test stub was written for the former model-level `is_fused_shared_expert_enabled` bool. The fix:
- set `fused_shared_expert_layers = frozenset({0})` on the stub instead of `is_fused_shared_expert_enabled = True`;
- name the checkpoint weights `layers.0.block_sparse_moe....` and register the experts under `model.layers[0]`, so the layer index can be parsed;
- enable the global AITER FSE gate only around `load_weights` (monkeypatch). Enabling AITER MoE for the whole test would also switch the expert kernels, and their weight layout, that the test compares against.

## End-to-end: `vllm serve` combinations on MI355X

Commands for the routed / shared expert online requantization combinations supported by this PR, on the base models:
- `MiniMaxAI/MiniMax-M3.1-Flash`: NVFP4 routed experts, MXFP8 shared experts.
- `amd/MiniMax-M3.1-Flash-Quark-MXFP4`: MXFP4 routed experts, MXFP8 shared experts.

FSE (fused shared experts) is enabled with `VLLM_ROCM_USE_AITER_FUSION_SHARED_EXPERTS=1` (default `0`). `VLLM_ROCM_USE_AITER_MOE` defaults to `1`.

This is tested on MI355X, TP4.

Common arguments, from the [MI355X recipe](https://recipes.vllm.ai/MiniMaxAI/MiniMax-M3.1-Flash?hardware=mi355x):

```bash
COMMON_ARGS=(
  --block-size 128
  --disable-hybrid-kv-cache-manager
  --tensor-parallel-size 4
  --kv-cache-dtype nvfp4
  --attention-config '{"indexer_kv_dtype": "nvfp4", "indexer_decode_cp": true}'
  --tool-call-parser minimax_m3
  --enable-auto-tool-choice
  --reasoning-parser minimax_m3
  --speculative-config '{"method":"dspark","num_speculative_tokens":3,"attention_backend":"TRITON_ATTN","kv_cache_dtype":"fp8","draft_sample_method":"probabilistic"}'
)
```
