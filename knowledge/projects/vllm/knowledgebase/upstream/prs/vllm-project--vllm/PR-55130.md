# [Bugfix][Scheduler] Configure non-causal prefill before startup

[Upstream PR](https://github.com/vllm-project/vllm/pull/55130) · state: open · merged: False

## Original PR description

## Purpose

HRM-Text uses bidirectional attention during prefill. Chunked prefill and prefix caching are therefore unsafe, but vLLM previously discovered this only after workers had started and KV-cache specs reached `EngineCore`.

The original patch revalidated the token budget after disabling chunked prefill there. Review correctly pointed out that this changed the default HRM setup from a hang into a startup error: the API-server default was still `max_num_batched_tokens=2048` for `max_model_len=4096`, and worker configuration had already been created.

This revision moves the decision to configuration time. Models can declare whether they support chunked prefill and prefix caching; HRM-Text declares both unsupported. As a result, the existing default-budget logic sees chunked prefill disabled and raises the default budget to 4096 before workers are created. Explicit attempts to enable either unsupported feature fail immediately with a clear configuration error.

The late `EngineCore` check remains as a defensive fallback for non-causal layers that do not yet declare their capabilities.

## Why this is not duplicate work

I searched open vLLM PRs for `non-causal chunked prefill scheduler` and `max_num_batched_tokens non-causal`. No other open PR addresses this configuration-order issue; the only matching result was this PR.

## Manual validation

On one Ascend 910B3 using local `sapientinc/HRM-Text-1B` weights and no chunked-prefill, prefix-cache, or token-budget flags:

```text
enable_chunked_prefill=False
enable_prefix_caching=False
max_num_batched_tokens=4096
max_model_len=4096
```

The engine proceeded past the former 2048/4096 configuration failure and loaded the 2.2 GiB checkpoint. A later Ascend-plugin-specific `No common block size for 16` failure prevented an inference evaluation in that older matched plugin image; it is downstream of this scheduler/configuration path. This patch does not change model computation or output values.
