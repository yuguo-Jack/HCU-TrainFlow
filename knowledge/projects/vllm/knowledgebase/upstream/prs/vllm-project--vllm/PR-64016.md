# [Model] Add Unlimited-OCR-2 DASH attention support

[Upstream PR](https://github.com/vllm-project/vllm/pull/64016) · state: closed · merged: True

## Original PR description

Add native [Unlimited-OCR-2](https://huggingface.co/baidu/Unlimited-OCR-2) support with DASH sparse attention and page-aware RoPE.

- FlashAttention and FlashInfer for chunked prefill and decode, using Model Runner V2.
- R-SWA retains input KV and bounds output KV to 128 tokens; full decode graphs and opt-in segmented prefill graphs.
- Model-specific preprocessing, decoder construction and optional GPU page-count guard. Shared DeepSeek decoder and scheduler files match main.

<details>
<summary>Usage and limitations</summary>

```bash
VLLM_USE_V2_MODEL_RUNNER=1 python examples/generate/multimodal/vision_language_multi_image_offline.py \
    --model-type unlimited_ocr2 --num-images 2 --method generate
```

Use `"<PAGE><image>" * len(pages) + "Multi page parsing."` with images in page order, `temperature=0` and `skip_special_tokens=False`. `mm_processor_kwargs={"crop_mode": False}` selects a 1024-square global view. Invalid page/image sequences are rejected before worker execution.

FA is the default; select FI with `attention_config={"backend": "FLASHINFER"}`. The vision encoder falls back from FI to FA. `hf_overrides={"rswa_window": 0}` retains full output KV. Segmented prefill graphs require `VLLM_USE_BREAKABLE_CUDAGRAPH=1` and `cudagraph_mode="FULL_AND_PIECEWISE"`; dynamic DASH routing, attention and KV writes remain eager breaks. Whole-prefill FULL graphs are unsupported.

The page-count guard is opt-in through `vllm.model_executor.models.unlimited_ocr2:PageCountGuardLogitsProcessor`; it respects existing sampling masks, preserving EOS when it is the only finite choice. Its `SamplingParams.extra_args` include `page_token_id`, `eos_token_id` and `max_page_tokens` (default 20000; 0 disables the cap).

V1, prefix caching, quantization, PP/CP, LoRA, speculative decoding and KV transfer are unsupported. Validated on GB200/BF16 with prebuilt extensions; clean-build validation remains pending.

</details>

<details>
<summary>Evaluation and validation</summary>

MPDocBench historical full run (before chunked-prefill changes): 420 documents / 3,135 pages, V2. Overall is **84.7407** with the published-client fallback budget and **84.8430** with available-context budgets (paper reference **84.5900**). The latter has no length stops or page-count mismatches. This uses a local evaluation adapter and does not establish identical paper deployment or unpublished per-PDF budgets. MarathonDocBench was cancelled.

The preceding `f5033fd` 4-document / 29-page FA check (B=4, 513-token chunks) retains byte-identical raw and Markdown predictions. Real-weight `pytest tests/models/multimodal/generation/test_unlimited_ocr.py -k 'batched_pages and False' -x -q` passes all 6 FA/FI eager/decode/prefill-graph cases. No new throughput claim.

The [EOS-only guard review](https://github.com/vllm-project/vllm/pull/64016#issuecomment-6523759526) is fixed: `allowed_token_ids=[EOS]` previously emitted `[0,0,0,0]`; it now emits exactly `[EOS]` and stops. CPU/GPU retain EOS when masking it would remove the last finite choice. GPU checks run within the existing kernel, stop at the first finite alternative, and perform no host readback. The same FA/FI eager/decode/prefill generation command above covers this case alongside normal OCR content.

Merged main `f1fd044b`. Prefill request metadata is prepared once from existing CPU buffers and shared across decoder layers. The mixed decode/prefill forward fails the CUDA-sync check before this change and passes afterwards with identical output.

**Open review issue:** the excess-marker raw-logit regression remains unresolved; its `atol=0.5, rtol=0` and source are unchanged. A zero-preemption control reproduces a 0.9375 difference at output 123 when comparing B=1 with B=2. A B=2/no-preemption vs B=2/preemption experiment passed FA/FI once, then failed FA with 0.875 on final confirmation, so that test rewrite was discarded. This establishes numerical sensitivity but does not rule out a simultaneous recomputation defect. Reconstructed pre-fix routing still fails (2.75). No passing preemption claim is made for this head. Reproducer: `VLLM_USE_V2_MODEL_RUNNER=1 pytest tests/models/multimodal/generation/test_unlimited_ocr.py -k excess_markers -x -q`.

CI compatibility: FA2/3 use paged segment addressing, reduced-layer test configs resize DASH metadata, and vision/cold-shape initialization avoid blocking transfers. On GB200, FA2 real OCR and all 12 FA4/FI eager/decode/prefill-graph generation cases (with/without crops), plus both encoder-pressure cases, pass with `VLLM_GPU_SYNC_CHECK=error`. Hopper FA3 execution, ROCm and clean-build CI remain pending.

🔴 With the page-count guard enabled, any API client can crash the engine or corrupt other requests' logits via `vllm_xargs`. `validate_params` only checks that `eos_token_id`, `page_token_id` and `max_page_tokens` are ints. It sets no upper bound. Fix: reject values outside int64 in `validate_params`, and in the kernel/`add_request` treat any `eos_token_id`/`page_token_id` >= vocab size as invalid. Masking the `tl.store` at line 339 with `eos < VOCAB_SIZE` meets this; the guard must still accept 0 for `max_page_tokens`, which disables the cap. Without a bound, an oversized eos writes past its logits row in `_page_count_guard_kernel`.

<details>
<summary>Why this was flagged</summary>

An OpenAI-compatible request reaches `SamplingParams.extra_args` through `vllm_xargs` (completion/protocol.py:400,431). The server was started with `--logits-processors vllm.model_executor.models.unlimited_ocr2:PageCountGuardLogitsProcessor`. `validate_params` (unlimited_ocr2.py:411-421) accepts any non-negative int. With `eos_token_id` >= vocab and a multi-page prompt, `markers < expected` is true. The unmasked `tl.store(Logits + row * LOGIT_STRIDE + eos * LOGIT_COL_STRIDE, -inf)` at line 339 then writes into another request's logits row, or past the fp32 logits buffer (an illegal address, so a CUDA error). A value >= 2**63 (for example `max_page_tokens`) passes validation. It then raises OverflowError in `StagedWriteTensor.stage_write` (array typecode for int64) inside the worker's `Sampler.add_request` (sampler.py:102), which has no isolation. Either way the engine dies for all users. The `LogitsProcessor` contract says `validate_params` exists precisely so bad arguments fail the request instead of reaching the sampler. On the base branch this processor does not exist.

**Verification:** Nothing in unlimited_ocr2.py compares either token id with the vocab size. In `_page_count_guard_kernel`, the store at line 339 has no mask. If `eos` is above vocab, the store writes -inf into another request's row of the logits tensor, and a huge value gives an illegal memory access, which takes down the engine. Before this PR there was no such guard, so this is new.

</details>

File: `vllm/v1/attention/ops/dash_attention.py` · line 537

🔴 After a preemption, a resumed Unlimited-OCR-2 request recomputes its generated tokens with different attention than they were decoded with. Its continuation can then differ from an unpreempted run. `paged_dash_prefill` sets the R-SWA prefix to `length`, the whole sequence, and never uses `metadata.rswa_prefix_lens`. The V2 scheduler re-prefills resumed requests over `req._all_token_ids`, so output tokens are treated as input prefix. Fix: pass each request's prompt length from `_attention` (unlimited_ocr2.py:182) into `paged_dash_prefill`, and use `min(length, prompt_len)` as the prefix whenever R-SWA is on.

<details>
<summary>Why this was flagged</summary>

Under KV-cache pressure, a running request is preempted. When it resumes on Model Runner V2, scheduler.py:1620-1625 builds `NewRequestData` with `prefill_token_ids=req._all_token_ids` (prompt plus generated tokens). `prefill_len` covers all of them, so the generated tokens go through the multi-token branch of `UnlimitedOCR2Attention._attention` (models/unlimited_ocr2.py:182-198). That branch calls `paged_dash_prefill`, which builds `prefix = torch.full_like(lens[start:end], length)` (ops/unlimited_ocr2.py:533). In the original decode, `paged_dash_decode` received `metadata.rswa_prefix_lens`, which is the prompt length. So `_scores` and `_gather_segments` limited remote reads and summaries to the input prefix. On recompute, a block holding both input and output tokens is summarized and gathered including the output tokens. The rebuilt hidden states and KV therefore differ from those that produced the tokens.
