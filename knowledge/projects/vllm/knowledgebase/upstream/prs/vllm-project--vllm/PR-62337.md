# [Core][KVConnector] Connector "ready" state for asynchronous connector startup

[Upstream PR](https://github.com/vllm-project/vllm/pull/62337) · state: open · merged: False

## Original PR description

Cleaning up implementation in https://github.com/vllm-project/vllm/pull/51414/ while addressing some of the limitations rightfully pointed out re: block allocation tracking.
To recap, this PR only covers the interface changes required to allow connectors to initialize asynchronously (`is_ready` behaviour), so that the various implementations we support can opt in with ad-hoc methods.

One of the differences wrt original PR is how connectors can opt-in ie
```
class MyAsyncConnector(SupportsAsyncInit):  # instead of KVConnectorBase_V1
    def __init__(self, vllm_config, role, kv_cache_config):
        super().__init__(vllm_config, role, kv_cache_config)
        if role == KVConnectorRole.WORKER:
            # Connector-specific: start slow setup however suits the connector (Future here).
            self._init = ThreadPoolExecutor(1).submit(self._allocate_host_buffers)

    def is_init_done(self) -> bool:
        # Polled on workers each step until True; raising here (or exceeding
        # VLLM_KV_CONNECTOR_INIT_TIMEOUT) fails the engine.
        if self._init.done():
            self._init.result() 
        return self._init.done()
```

A connector that is either ready or does not initialize asynchronously should have zero-overhead from the scaffolding added here.

Thanks for following up!

I feel like it could be simpler though with a less code in core.

Right now the scheduler hides early requests from the connector. That is what pulls `without_requests`, the `BlockPool` tracking and `allocated_block_ids` into core.

How about letting the connector own the gate instead? It sees every request and just declines the ones that came before ready. A small helper in `async_init.py` can hold the shared parts. Then scheduler, block pool and worker stay as on main.

The cost is a few guards per async connector. I think that's fine, since the opt-in is per connector anyway.

WDYT?

- YannikHinteregger · comment · 2026-10-22T21:06:12Z · [source](https://github.com/vllm-project/vllm/pull/62337#discussion_r4353528412)

File: `vllm/distributed/kv_transfer/kv_connector/v1/async_init.py` · line 29

Connector authors only need to implement `is_init_done()`, right? 
The other public methods here (`is_connector_ready()`, `requires_allocation_tracking()` and the two init status hooks) are only used internally in the handler. Still, every connector can override them. MultiConnector actually overrides all of them.

How about moving them into the handler, with a small MultiConnector handler for the aggregation? Then a connector would only see three methods:
```python
# async_init.py
class SupportsAsyncInit(KVConnectorBase_V1):
    def enable_async_init(self) -> None:
    @abstractmethod
    def start_init(self) -> None:
    @abstractmethod
    def is_init_done(self) -> bool:
```
1. `enable_async_init()`: the connector calls it when its config turns async init on
2. `start_init()`: the worker calls it once after cuda graph capture
3. `is_init_done()`: polled every step, raises on failure
