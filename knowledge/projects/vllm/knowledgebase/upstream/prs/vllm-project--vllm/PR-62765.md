# [Feature] [Frontend] [Reasoning] Support Prompt Embeds inputs for reasoning traces

[Upstream PR](https://github.com/vllm-project/vllm/pull/62765) · state: closed · merged: True

## Original PR description



## Overview



Allow assistant messages in `/v1/chat/completions` to supply a single `prompt_embeds` part as `reasoning`, using the existing support for prompt embeddings in message content.

I found no existing relevant issues and PRs that are currently open. This follows-up to a whole slew of work done in the past enabling prompt embeds support for `/v1/chat/completions` request.

## Claims



- Accepts `reasoning` as text or a prompt embedding part, including through the legacy `reasoning_content` alias.
- Reuses existing embedding decoding, validation, and rendering, preserving embedding order when both reasoning and content contain embeddings.
- Prevents forwarded `kv_transfer_params.prompt_token_ids` from bypassing reasoning embedding processing.

I also have a script to manually validate that prompt embedding-encoded inputs are passed to the engine when provided.

It asks the model to repeat back a secret code, but the secret code is only provided in the reasoning trace of a previous message. We expect the answer to be correct and identical regardless of whether the reasoning traces are passed in as prompt embeddings or plain text.

# SPDX-License-Identifier: Apache-2.0

"""vLLM OpenAI-Compatible Client with Prompt Embeddings.

Adapted from the official vLLM docs. 
https://github.com/vllm-project/vllm/blob/main/examples/features/prompt_embed/prompt_embed_inference_with_openai_client.py

This adapted version uses Qwen 3.5, which does respect reasoning (albeit only in the current turn) in its chat
template. It also only exercises the /v1/chat/completions path, as that is the only path that supports reasoning
with prompt embeds.

It runs chat completions with prompt embeddings inputs. The first time, the entire conversation, including reasoning traces, is encoded into prompt embeds.
The second time, the reasoning traces are left as plaintext.

This shows that outputs are identical with reasoning being prompt embeddings or plaintext. 

Furthermore, the prompt can only be answered correctly if the model sees the reasoning traces (which contain the secret code).
"""

import transformers
from openai import OpenAI

from vllm.utils.serial_utils import tensor2base64

def encode(tokenizer: transformers.PreTrainedTokenizerBase, embedding_layer, text: str) -> str:
    token_ids = tokenizer(text, return_tensors="pt", add_special_tokens=False).input_ids
    prompt_embeds = embedding_layer(token_ids).squeeze(0)
    return tensor2base64(prompt_embeds)

def encode_message(msg: dict, tokenizer, embedding_layer, encode_reasoning:bool) -> dict:
    if msg.get("role") == "tool":
        return msg
    encoded_msg = {
        "role": msg['role'],
        "content": msg['content']
    }
    if "reasoning" in msg:
        encoded_msg['reasoning'] = {
            "type": "prompt_embeds",
            "data": encode(tokenizer, embedding_layer, msg['reasoning']),
        } if encode_reasoning else msg['reasoning']
    if "tool_calls" in msg:
        encoded_msg['tool_calls'] = msg["tool_calls"]

    return encoded_msg


def run_chat_completion_prompt_embeds(
    client: OpenAI,
    model_name: str,
    tokenizer: transformers.PreTrainedTokenizerBase,
    embedding_layer,
    messages: list[dict],
    encode_reasoning: bool,
) -> None:
    """Run a Chat Completions API request using prompt_embeds content parts."""
    api_messages = [
        encode_message(message, tokenizer, embedding_layer, encode_reasoning) for message in messages
    ]

    chat_completion = client.chat.completions.create(
        model=model_name,
        max_tokens=1024,
        temperature=0.0,
        messages=api_messages,
    )

    print("-" * 30)
    print("Chat Completions API")
    print(f"Encoding reasoning traces to prompt embeds: {encode_reasoning}")
    print("-" * 30)
    print(chat_completion.choices[0].message.content)
    print("-" * 30)



def main() -> None:
    client = OpenAI(
        api_key="EMPTY",
        base_url="http://localhost:8000/v1",
    )

    model_name = "Qwen/Qwen3.5-0.8B"

    tokenizer = transformers.AutoTokenizer.from_pretrained(model_name)
    transformers_model = transformers.AutoModelForCausalLM.from_pretrained(model_name)
    embedding_layer = transformers_model.get_input_embeddings()

    messages_with_reasoning  = [
    {
        "role": "user",
        "content": "What was the secret code I established?",
    },
    {
        "role": "assistant",
        "reasoning": (
            "The secret code is A1dhgl3ihz. "
            "I must remember it after checking the tool."
        ),
        "content": "",
        "tool_calls": [
            {
                "id": "call_1",
                "type": "function",
                "function": {
                    "name": "check_status",
                    "arguments": "{}",
                },
            }
        ],
    },
    {
        "role": "tool",
        "tool_call_id": "call_1",
        "name": "check_status",
        "content": "Status: OK",
    },
]
    run_chat_completion_prompt_embeds(
            client, model_name, tokenizer, embedding_layer, messages_with_reasoning, encode_reasoning=True
        )
    run_chat_completion_prompt_embeds(
            client, model_name, tokenizer, embedding_layer, messages_with_reasoning, encode_reasoning=False
        )

if __name__ == "__main__":
    main()

## Details




Prompt embeddings let callers supply representations in the model’s continuous input space. Extending this capability to reasoning inputs supports experimentation with richer reasoning representations, motivated by work such as [Training Large Language Models to Reason in a Continuous Latent Space](https://arxiv.org/abs/2412.06769) and [Hybrid Reasoning Agents](https://arxiv.org/abs/2610.18861). 

It also makes reasoning inputs available to the same applications as content embeddings: prompt compression, custom encoders, and Protopia’s [Stained Glass Transform](https://protopia.ai/stained-glass-transform/) (a custom prompt-privacy encoder).

Example assistant message:

```json
{
  "role": "assistant",
  "reasoning": {
    "type": "prompt_embeds",
    "data": "<base64_encoded_tensor>"
  },
  "content": ""
}
```

The implementation changes two production files and delegates to the existing content-part parser. Reasoning embeddings are parsed before content embeddings to match their order in the rendered prompt. The existing `--enable-prompt-embeds` flag and tensor requirements apply, and the chat template must render `reasoning` or `reasoning_content`.

Open PR searches found no existing implementation of reasoning prompt embedding inputs. Related [PR #59930](https://github.com/vllm-project/vllm/pull/59930) addresses embedding decode budgets.

AI assistance was used in implementation, tests, documentation, and this description.

File: `vllm/renderers/hf.py` · line 142

🟡 (optional) Embeddings can be silently spliced into the wrong spans when a chat template renders placeholders in a different order than they were parsed. `_filter_prompt_embeds_by_template` keeps the surviving tensors in parse-index order, which is reasoning first, then content, then later messages. It then turns every indexed marker into the same plain token, so the splice step fills spans in rendered order. Fix: order `visible_tensors` by each marker's position in `rendered` (e.g. sort by `rendered.index(marker)`), and reject markers that appear more than once, so tensor order always matches the order of the token spans.

<details>
<summary>Why this was flagged</summary>

The trigger is an assistant message with prompt_embeds in both `reasoning` and `content`, under a chat template that emits content before reasoning. Indexes come from `mm_tracker.num_items("prompt_embeds")` (chat_message.py:526), and reasoning is parsed first (chat_message.py:619-627). At hf.py:129-133 the kept tensors stay in index order. Then `normalize_placeholders` swaps every marker for the same `PROMPT_EMBEDS_PLACEHOLDER_TOKEN` (hf.py:120-123), so the index-to-position link is gone before `_apply_prompt_embeds_to_prompt` splices tensors into spans by position. Mismatched lengths then fail the whole request, and swapped tensors of equal length silently feed the wrong embeddings to the model.
