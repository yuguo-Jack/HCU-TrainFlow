# [Bugfix][Model] Qwen3.8-Flash-Next: load checkpoints with quantized q/k/v and a BF16 QSA indexer

[Upstream PR](https://github.com/vllm-project/vllm/pull/62318) · state: closed · merged: True

## Original PR description

## Overview

Fixes #62308. Since #59533, `Qwen4ExpForCausalLM.packed_modules_mapping["qkv_proj"]` lists `indexer.index_qk_proj`. Quant configs read that class-level mapping before the model is built, so they check q/k/v and the QSA indexer as one fused layer. Checkpoints that quantize q/k/v but keep the indexer in BF16 fail to load with `Found different quantization schemes for the shards of ...qkv_proj`.

This PR keeps the indexer out of the mapping that quant configs see, and fuses it into `qkv_proj` only when both resolve to the same quant method.

## Claims

- Checkpoints with quantized q/k/v and a BF16 indexer load again, for example `ukisai/Swift-1.5-Qwen3.8-Flash-Next-W4A16-AWQ`. Their indexer runs as its own GEMM, as before #59533.
- No change for BF16, ModelOpt FP4, and checkpoints that treat q/k/v and the indexer the same way: the indexer stays fused.
- The `--enable-lora` mapping override is removed. It is no longer needed, and it never reached the quant config.

## Validation

End to end on 4x A100-PCIE-40GB (TP4 + EP) with the `vllm/vllm-openai:nightly` image built from `1b2a666` (2026-10-18). Its `model.py` and `qsa.py` match this PR's base `371745e`; for "after", the two files from this PR were mounted over them. A test-only hook (not part of this PR) logged the fusion decision of every QSA layer.

| Checkpoint | Code | Server start | QSA layers (12 per worker, 4 workers) | Check |
|---|---|---|---|---|
| `ukisai/Swift-1.5-Qwen3.8-Flash-Next-W4A16-AWQ` (q/k/v W4A16, indexer BF16) | before | fails: `ValueError: Found different quantization schemes ... layers.3.self_attn.qkv_proj` | - | - |
| same | after | ok | 48/48 unfused: `QKVParallelLinear` (`CompressedTensorsWNA16`) + BF16 `index_qk_proj` | GSM8K 86.2% (n=500), 0 invalid |
| `cyankiwi/Qwen3.8-Flash-Next-AWQ-INT4` (attention BF16) | before | ok | 48/48 fused (`Qwen4ExpQSAQKVIndexerLinear`) | - |
| same | after | ok | 48/48 fused, same layer and quant method | sample request ok |

Both GPU runs used an earlier revision of the fusion check. The final check makes the same decision for both checkpoints: different quant methods for Swift, the same for cyankiwi.

GSM8K (an API key header was added by a small wrapper):

```bash
python tests/evals/gsm8k/gsm8k_eval.py --port 8002 --use-chat-completions \
  --model swift-1.5-flash-next-awq --reasoning-effort none --num-shots 0 \
  --num-questions 500 --max-tokens 512 --temperature 0 --max-concurrency 32
```

The default 5-shot completions mode does not suit this model family: it emits EOS right after `Answer:` once the prompt is longer than about 400 tokens, on vLLM and on llama.cpp alike.

- Unit test (CPU): `test_qkv_proj_mapping_allows_bf16_indexer` in `tests/models/qwen4_exp/test_config.py`. With the old mapping, both cases fail with the error from #62308.
- `pre-commit run --files <changed files>`: passed.
- CI: the test runs in the existing CPU Qwen4 Exp step (`qwen4-exp-unit-tests-cpu`). CI has no Flash-Next checkpoint with this layout (about 165 GB), so the end-to-end load is validated only as above.

## Details

- Root cause: `configure_quant_config` passes the class-level `packed_modules_mapping` to the quant config before `__init__` runs. Even the plain `QKVParallelLinear` built before fusion is resolved as a four-shard layer. The LoRA branch rebinds the mapping on the instance, so the quant config never saw it.
- Change:
  - `packed_modules_mapping["qkv_proj"]` is `["q_proj", "k_proj", "v_proj"]` for both model classes.
  - `Qwen4ExpQSAAttention` builds q/k/v and the indexer as before, then fuses only if both resolve to the same quant method type. Without a quant config for the fused layer (BF16, or ModelOpt FP4 via `without_modelopt_fp4`) it fuses as before.
- Limitation: if q/k/v and the indexer are both quantized with the same quant method but a different scheme or parameters (bits or group size), they are still fused, and loading fails at weight loading. I have not seen a checkpoint with this layout.
