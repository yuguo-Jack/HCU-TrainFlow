# [ROCm] Add paged FP8 prefix path to AITER FA extend_forward

[Upstream PR](https://github.com/vllm-project/vllm/pull/58713) · state: open · merged: False

## Original PR description

## Purpose

Add an opt-in path to the ROCm AITER FA backend that attends the extend tokens to the whole FP8 prefix with one `aiter.ops.mha.mha_batch_prefill_func` call. It replaces the loop that gathers 32k context tokens at a time into a workspace, runs dense FMHA on each chunk and merges every chunk output. At a 983k prefix that loop runs 30 times per full attention layer. The path is off by default. `VLLM_ROCM_AITER_PAGED_PREFIX=1` turns it on.

This PR is stacked on #53823, which adds prequantized FP8 QKV for Qwen3.8-2.4T-A95B with an FP8 KV cache and the direct FP8 context gather. Until #53823 merges, the diff here also shows its commits up to 192f15d403b7. The change in this PR is the last commit, 6ebfd196dce0. Related to #57149.

The kernel is the gfx950 head-size-256 FP8 paged-varlen prefill kernel from ROCm/aiter#4971 (`fmha_fwd_hd256_fp8_paged_varlen`). AITER v0.1.21.post2 and later include it, so this needs no AITER bump.

What changes:

- `VLLM_ROCM_AITER_PAGED_PREFIX` is registered in `vllm/envs.py` and defaults to off.
- `AiterFlashAttentionMetadataBuilder` builds a 64-token page table (`kv_indptr`, `kv_page_indices`, `kv_last_page_lens`) when the batch has one extend request and no sliding window. It still builds the chunk tables, so a layer without prequantized QKV falls back to the loop.
- `extend_forward` calls `mha_batch_prefill_func` once on the prefix with per-tensor FP8 Q, K and V scales. One `merge_attn_states` call then merges that result with the causal result on the new tokens.
- The KV cache keeps 32-token kernel blocks, so decode is unchanged. With `--block-size 64`, two adjacent kernel blocks are one 64-token page in memory, and `paged_prefix_cache_views` builds that view with `as_strided`. The view needs one KV head per rank.
- If the flag is set but a precondition fails, the builder logs the reasons once and keeps the loop. The preconditions are prequantized FP8 QKV from the model, which #53823 turns on for Qwen3.8-2.4T-A95B, an FP8 KV cache, one KV head per rank, an AITER build with `mha_batch_prefill_func` and an attention block size that is a multiple of 64.
- `block_table` is not passed to `mha_batch_prefill_func`. It selects the 2D vLLM page table layout, and AITER then falls back to the CK kernel without an error.

No open PR uses `mha_batch_prefill_func` or changes the AITER FA extend path. I searched open PRs for `mha_batch_prefill`, `extend_forward aiter`, `cp_mha_gather_cache` and `rocm_aiter_fa chunked prefill`.

I wrote this change with AI assistance (Cursor). The commit has a `Co-authored-by: Cursor` trailer.

## Test Result

These are early results. They come from the same paged path on an older vLLM build that carries an earlier version of the #53823 commits and some other ROCm changes that are not in main, with the ROCm/aiter#4971 kernels added to AITER. The absolute times will differ on this branch. In every comparison, the flag-off and flag-on runs use the same build and the same server config.

Unit tests: `tests/v1/attention/test_rocm_aiter_paged_prefix.py` 5 passed. The AITER op test above 8 passed.

Kernel benchmark on one MI355X: 8 query heads, 1 KV head, head size 256, FP8 KV cache, 32,768 new tokens. The time covers the causal FMHA on the new tokens plus all context attention.

| Prefix tokens | Gather loop (main) | This PR | One causal paged call (not wired) |
|---|---|---|---|
| 32,768 | 5.62 ms | 5.55 ms | 5.19 ms |
| 131,072 | 16.35 ms | 15.00 ms | 14.76 ms |
| 524,288 | 59.82 ms | 53.14 ms | 53.14 ms |
| 983,040 | 110.46 ms | 97.69 ms | 97.70 ms |

At a 983k prefix the loop runs 30 dense FMHA launches (101.8 ms) and 30 merges (6.4 ms). The paged kernel takes 95.6 ms. `--profile` shows that the paged calls ran the ASM kernel and not the CK fallback. One causal paged call over the prefix and the new tokens brings nothing over two calls at 1M, so this PR keeps the two calls.

Against an FP32 reference on random FP8 inputs (64 query rows), the paged path matches the loop bit for bit at a 32k prefix. At a 983k prefix its relative L2 error is 3.72%, against 3.23% for the loop. The paged kernel runs one pass over the whole prefix, and the loop merges 32k chunks in FP32. The model output checks below show no difference beyond run-to-run noise.

Server: `amd/Qwen3.8-2.4T-A95B-Quark-MXFP4`, TP8 on 8x MI355X, `--attention-backend ROCM_AITER_FA --kv-cache-dtype fp8 --block-size 64 --max-num-batched-tokens 32768 --max-model-len 1010000 --no-enable-prefix-caching`, `max_position_embeddings` overridden to 1010000, `VLLM_ROCM_FP8_DIRECT_CONTEXT_GATHER=1` (the flag of the earlier #53823 version, which the current #53823 no longer needs), full and piecewise CUDA graphs. Only `VLLM_ROCM_AITER_PAGED_PREFIX` differs between the two sides.

| One request on an idle server | Flag off | Flag on |
|---|---|---|
| 1M prompt (999,873 tokens), end-to-end time | 69.3 s (mean of 8) | 66.0 s (mean of 4) |
| 128k prompt, end-to-end time | 4.66 and 4.9 s | 4.64 and 4.8 s |
| 1M prompt, last 4 prefill steps, prefix attention on rank 0 | 8,045 ms | 6,972 ms |
| 1M prompt, last 4 prefill steps, whole step time on rank 0 | 12,018 ms | 11,004 ms |

In those 4 steps the flag-off server runs 2,622 gathers, 2,622 dense FMHA chunks and 2,622 merges over the 23 full attention layers. The flag-on server runs 92 paged calls and 92 merges.

Serving benchmark with the random dataset: 2 prompts of 1,000,000 input and 1,000 output tokens, range ratio 1.0, max concurrency 2, temperature 0, after 2 warmup requests. I ran it in two rounds with a fresh server for each run.

| | Flag off | Flag on |
|---|---|---|
| Mean TTFT, round 1 | 104.27 s | 99.89 s |
| Mean TTFT, round 2 | 104.69 s | 98.62 s |
| Median ITL, both rounds | 16.2 ms | 16.2 ms |

Mean TTFT is 5.2 s (5.0%) lower with the flag. Decode does not change.

Output checks, flag off and on: 32 greedy tokens with the top 5 logprobs on 2k, 128k and 1M prompts, and a passphrase question at 37% depth with thinking off. At 2k both flags give the same tokens. At 128k and 1M the greedy text already varies between requests on the same server with either flag, and the flag does not change that spread. Both flags return the passphrase at 2k, 128k and 999,885 tokens.

gsm8k and `vllm bench serve` on this branch are still to do, as listed in the Test Plan.
