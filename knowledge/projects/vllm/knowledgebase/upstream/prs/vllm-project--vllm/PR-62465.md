# [Bugfix][KV Connector] Pass hf3fs_metadata_server_url to Hf3fsMetadataClient

[Upstream PR](https://github.com/vllm-project/vllm/pull/62465) · state: open · merged: False

## Original PR description

## Overview

Pass the configured `hf3fs_metadata_server_url` to `Hf3fsMetadataClient` in both scheduler and worker initialization in `HF3FSKVConnector`. Fixes #62387.

## Claims

- Fixes issue #62387 where `HF3FSKVConnector` silently ignored `hf3fs_metadata_server_url` and defaulted to `http://localhost:18000`.
- Adds unit tests in `TestHF3FSKVConnectorMetadataServerUrl` verifying both scheduler and worker roles pass the configured URL.
- Guards `signal.SIGQUIT` registration with `hasattr` to prevent crashes on non-POSIX platforms.

Ran unit tests with pytest on the new and existing test suites:

- sivabreddy · comment · 2026-10-21T09:27:28Z · [source](https://github.com/vllm-project/vllm/pull/62465#issuecomment-6312639090)

We ran the same two-line change (both `Hf3fsMetadataClient()` calls given `self._metadata_server_url`) in a two-instance test on real 3FS: vLLM v0.32.0, Llama-3.1-70B-Instruct TP4, one instance per H100 host, both pointing at one shared metadata server through `hf3fs_metadata_server_url`. Both instances used the shared server, and the second instance loaded what the first one stored (1,792 of 1,850 tokens from 3FS). Without the change, each instance talks to its own `localhost:18000` and nothing is shared (#62387). The test was for #62693, which needs this fix for any setup with more than one host; results: https://github.com/vllm-project/vllm/pull/62693#issuecomment-6291048457.
