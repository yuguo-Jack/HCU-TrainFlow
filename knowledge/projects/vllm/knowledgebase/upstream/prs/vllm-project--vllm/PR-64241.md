# [CI] Pin existing dependency hashes and enforce immutable references

[Upstream PR](https://github.com/vllm-project/vllm/pull/64241) · state: closed · merged: True

## Original PR description



## Overview

Pin archive hashes for the dependencies already present in the five compiled requirement files and enforce immutable GitHub Actions references. This initializes hash pinning and its checks; automatic dependency updates remain in #59667.

## Claims

- Add SHA-256 archive hashes to all **1,458 existing requirement entries**, preserving every package version from current main. All five pre-commit compile hooks emit hashes without upgrading pins.
- Add a check rejecting tags, branches, and short commits in external Actions/reusable workflows; require image digests for Docker actions. Pin the recipe reusable workflow to its current main commit.
- Keep hashed requirement consumers working: remove complete continued Torch requirements, filter whole CPU requirements, preserve complete fastsafetensors requirements and enforce source hashes in both remaining ROCm rebuilds, emit hashes during CUDA nightly/arm64 recompilation, and require hashes in the documentation install.

## Details

This PR supplies hash initialization, compile/check enforcement, install compatibility, and contributor documentation. It contains no scheduled updater, publishing workflow, or Dependabot grouping changes. Merge this prerequisite before the automatic updater in #59667, whose helper requires hash-generating compile hooks.

uv verifies supplied hashes in existing test-image installs. Hash coverage is limited to archives named in the five compiled files; handwritten lint/build/bootstrap dependencies, separately built wheels, and packages deliberately excluded from the ROCm lock remain outside it. Hashing a source archive does not hash its build dependencies, so mixed installs do not globally require hashes. The documentation install uses a complete lock and explicitly requires them.

Contributor documentation is linked from the contributor index at `docs/contributing/ci/dependency_hashes.md`. Local documentation discovery passed; hosted preview validation remains pending.

**Duplicate-work check:** this extracts the pinning changes from #59667, where they are removed. No other open PR found initializes these five hashed files and adds these checks. #38500 pins setup-uv in a different workflow, which this PR does not modify; #64010 restores already-version-locked CI jobs; #63574 raises dependency floors.


**Other notes**

- **No Buildkite run on the current head.** The only run is #97918 on the first commit. I'm triggering `/ci run` now; it needs green CUDA/ROCm/CPU/XPU image builds before merge.

**Coverage gap: NCCL (not blocking, but worth a follow-up)**

`requirements/test/cuda.txt` pins `nvidia-nccl-cu13==2.30.7` with hashes. The CUDA image never installs that version, though: `UV_OVERRIDE=/etc/uv-overrides.txt` (from `NCCL_VERSION=2.31.2`) replaces it with 2.31.2. I checked locally that uv drops the lock's hashes when an override replaces a pin. Without `--require-hashes`, uv also accepts a package that has no hashes. So 2.31.2 is installed from PyPI with no hash check, even though the lock makes NCCL look covered. That isn't a regression, since nothing is checked today, and the build won't break. A tampered 2.31.2 wheel would still go into every CUDA CI image unnoticed.

Suggested fix: pin `nvidia-nccl-cu13==2.31.2` in the `.in` inputs, so the lock carries the real version's hashes and the override has nothing to change. A later `NCCL_VERSION` bump then has to update the lock too.

The same issue applies more broadly: outside the docs install, uv only checks hashes that are present and doesn't require them. Anything an image installs that isn't a hashed lock entry goes in unchecked, including:
- packages replaced by an override, like NCCL;
- the hand-written requirement files (`requirements/{common,cuda,rocm}.txt`, build and lint), which the hashed locks only partly constrain;
- packages named directly in Dockerfiles, e.g. `quart`, `msgpack` and `aiohttp` in `Dockerfile.rocm`.

None of these block this PR. Please list them in `docs/contributing/ci/dependency_hashes.md` so the doc doesn't overstate what is covered.
