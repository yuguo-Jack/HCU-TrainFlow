# [ROCm][Perf][Muse Spark] Keep the residual stream token-sharded between layers under EP

[Upstream PR](https://github.com/vllm-project/vllm/pull/63723) · state: open · merged: False

## Original PR description

## Overview

Depends on https://github.com/vllm-project/vllm/pull/63722; this branch is stacked on it.

That PR runs the MoE block's router, pooler, norm and unpooler on each rank's \(T/8\) token slice, then all-gathers the block output so the rest of the layer sees all tokens. Everything outside the block still runs replicated: the FP32 residual adds, the gated post-norms, the pre-QKV and pre-FFN norms, and the `o_proj` all-reduce.

With `--enable-expert-parallel`, EP over the whole TP group and DP1, this PR keeps the residual stream split over tokens through all layers (Megatron-style sequence parallelism) for batches of 256 or more tokens:

1. `MuseSpark1xModel.forward` takes each rank's slice of the embeddings (`sequence_parallel_chunk`).
2. Each decoder layer norms its slice, all-gathers the BF16 attention input, runs attention on all tokens, and reduce-scatters `o_proj` (built with `reduce_results=False`).
3. The post-attention norm, residual add and pre-FFN norm run on the slice. The MoE block runs its token-sharded path on the slice (`forward_local_tokens`) and skips the final all-gather.
4. The final norm runs on the slice and its output is all-gathered once.

Below 256 tokens (decode), the model takes the existing path, and attention all-reduces `o_proj` itself. The path is off for DSpark draft layers, under PP, and when aux hidden states are requested (EAGLE-style drafters).

## Claims

- Serving PTPC-FP8, TP8 + EP on 8× MI300X, on top of https://github.com/vllm-project/vllm/pull/63722: +2.5–3.6% total throughput at 8k input and +4.9–6.4% at 16k input for concurrency 16–64 (1k output), and +0.3–2.5% at lower concurrency. Median TTFT is 9–10% lower at every 8k and 16k point except 16k c32 (2.66 → 2.88 s). At 1k input the change is within ±2%. Together with that PR: +12.5% at 8k c64 and +18.7% at 16k c64 over the unpatched nightly.
- GSM8K 5-shot is unchanged within error: 95.00% vs 95.38% flexible-extract with https://github.com/vllm-project/vllm/pull/63722 alone (±0.6%).
- MXFP4 on 4× MI355X (gfx950), TP4 + EP, real weights, on top of https://github.com/vllm-project/vllm/pull/63722: +4.5–5.8% total throughput at 8k input and +5.9–8.6% at 16k input for concurrency 16–64. Against the unpatched nightly the stack gives +3.3–4.8% at 8k and +4.4–6.7% at 16k for the same points, with median TTFT about 10% lower. GSM8K is unchanged within error (94.54% vs 94.92%, ±0.6%).

## Details

- **Collectives per layer at 8,192 tokens.**
  - Before: an `o_proj` all-reduce (128 MB BF16), plus the MoE block's logits and pooled all-gathers, a reduce-scatter, and a 128 MB output all-gather.
  - After: a 128 MB attention-input all-gather and an `o_proj` reduce-scatter (together, the same bytes as the all-reduce), plus the MoE block's collectives without the output all-gather.
  - Net: one fewer 128 MB all-gather per layer. All norms and FP32 residual math also run on 1/8 of the tokens.
- **Padding.** `sequence_parallel_chunk` pads \(T\) to a multiple of the TP size. Before attention, the gathered input is sliced back to \(T\) so it matches `positions` and the attention metadata. The `o_proj` output is padded again before the reduce-scatter. Padded rows only pass through norms and the MoE block, and the final `[:num_tokens]` drops them.
- **Gating.** `_token_sharded_parallelism` checks `enable_expert_parallel` explicitly: the EP group is TP-sized even without EP, and under plain TP the MoE output must be reduced before the post-expert norm.
- **Limitations.** PTPC-FP8 serving and accuracy are measured on MI300X and MXFP4 on MI355X. Off under PP, for DSpark draft layers and when aux hidden states are requested.
