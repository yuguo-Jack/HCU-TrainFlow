# [Perf] Keep a 512-token floor on the default CUDA graph capture size

[Upstream PR](https://github.com/vllm-project/vllm/pull/60265) · state: open · merged: False

## Original PR description

## Purpose
Fixes #60264.

The default `max_cudagraph_capture_size` is `min(2 * max_num_seqs * decode_query_len, 512|1024)`. At small `max_num_seqs` it is tiny (16 tokens at 8), so short prefills run in eager mode. A 1-token call with a ~200-token prompt is 2.3–3.0x slower at `--max-num-seqs 8` than at 256 (numbers in the issue).

This PR floors the default at 512 tokens, still capped by the platform default and by `max_num_batched_tokens`:

```python
max_cudagraph_capture_size = min(
    max(max_num_seqs * decode_query_len * 2, 512),
    default_max_graph_size,
)
```

Defaults with `max_num_seqs * decode_query_len >= 256` do not change. Explicit `cudagraph_capture_sizes` do not change.

Integer `compile_sizes` up to the ceiling are now added to the generated capture list. The dispatcher rejects a compile size that padding would change, so without this the floor would turn configs like `max_num_seqs=8, compile_sizes=[100]` into a startup failure. On main the same failure already happens from `max_num_seqs >= 52`. This also applies when only `max_cudagraph_capture_size` is set.

Tests that encoded `2 * max_num_seqs` for small `max_num_seqs` now expect the floor. `test_default_cudagraph_capture_size_unchanged_without_speculation` is renamed to `..._without_speculation`.

## Test Plan
- `pytest tests/compile/test_config.py` on unmodified main and with this PR (1x B200).
- `vllm serve deepseek-ai/DeepSeek-V2-Lite-Chat --max-num-seqs 8` on unmodified main and with this PR, plus `--max-num-seqs 256` as reference; the latency script from the issue.

## Test Result
Latency script from the issue (1x B200, DeepSeek-V2-Lite-Chat, median of 10):

| | default ceiling | n=1 | n=2 | CUDA graph memory | capture time |
|---|---|---|---|---|---|
| main, `--max-num-seqs 8` | 16 | 36 ms | 65 ms | 0.68 GiB | 2 s |
| this PR, `--max-num-seqs 8` | 512 | **16 ms** | **21 ms** | 1.15 GiB | 10 s |
| main, `--max-num-seqs 256` (reference) | 512 | 15 ms | 22 ms | 1.23 GiB | 13 s |

`tests/compile/test_config.py`: 59 passed, 19 failed, both on unmodified main and with this PR (at fba31f3, 1x B200). The failing set is the same apart from the renamed test; these 19 already fail on unmodified main on this machine.

After the rebase onto 75e3b17 (`-k "cudagraph or capture or compile_sizes"`): the same 13 tests fail on main and with this PR, all for environment reasons on this machine. The renamed test and the new `test_default_capture_sizes_include_compile_sizes` pass. With `compile_sizes=[100]` over `max_num_seqs` 1–299, main rejects 247 configs (52–299) and this PR rejects 0.

#20628 set `2 * max_num_seqs` to avoid OOM with small `max_num_seqs` in tight-memory setups. For those configs this PR raises the default to 512 tokens: CUDA graph memory +0.47 GiB (table above), KV cache memory 131.91 → 131.54 GiB (−0.37 GiB). Sizes above 512 are still not captured by default. Not tested on memory-tight GPUs.

## Not a duplicate
No open PR changes the default ceiling. #37865, #55004 and #58524 fix truncation and decode coverage under an *explicit* `max_cudagraph_capture_size`. #24011 (closed, WIP) proposed a new knob for prefill capture sizes. This PR only changes the default, and touches neither code path.

Thanks, confirmed. At `max_num_seqs=8` the old default ceiling was 16, so `compile_sizes=[100]` sat above it and skipped the padding check. With the floor, 100 lands between the captured 96 and 104, and startup fails.
