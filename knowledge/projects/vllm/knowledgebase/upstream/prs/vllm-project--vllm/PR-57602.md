# [ROCm] Enable Hisparse on ROCm : Sparse MLA Hot-Buffering

[Upstream PR](https://github.com/vllm-project/vllm/pull/57602) · state: open · merged: False

## Original PR description

# [ROCm] HiSparse: host-resident sparse-MLA hot-buffering on gfx950

## Purpose

Enables HiSparse (#53781) on AMD ROCm, verified on gfx950 (MI350X, CDNA4).
HiSparse keeps the bulk of the sparse-MLA KV cache in pinned host memory and
pulls back only the indexer-selected rows just in time, so long-context agentic
sessions stop getting preempted. #53781 landed it CUDA-only.

## Changes

**Route HiSparse attention through the int64-safe Triton kernel.** HiSparse
points attention at a view over the *whole multi-layer KV slab*, so emitted row
indices scale with total block count: max row index is 33 off HiSparse and 7.5M
on. AITER's decode kernel computes `row_index * row_width` in int32, so on
GLM-5.3 (`row_width=576`) it wraps above row 3,728,270 and returns approximately
zero — no NaN, no assert. Force Triton kernel for HiSparse for time being. 

**ROCm backend wiring.** CUDA HiSparse backends consume a dense `[tokens, topk]`
tensor; AITER's decode kernel consumes a ragged list plus indptr. Bridging that
is most of the diff: `ROCMAiterMLASparseImpl` registers with an
`index_group_builder` (which is what makes `mla_attention.py` pick up
`hisparse_cache`), decode converts dense physical top-k to ragged and attends
against the hot buffer, and prefill stages host rows via `stage_prefill_rows`
when the context is not fully resident. One new Triton kernel,
`compact_topk_to_ragged_triton` — `fetch_id_to_ragged_triton` was not reusable
because a mid-row `-1` must drop out rather than displace a valid entry.
AITER's persistent work-stealing metadata is disabled under HiSparse (its
buffers are sized in `build()`, but HiSparse rewrites the indptr at forward
time); noted as a perf follow-up.

**HIP kernel port (`csrc/`).** The four fused HiSparse cache ops build and run
on ROCm. Mechanical: vectorized copy widths, `__nv_bfloat16` → `hip_bfloat16`,
warp-primitive shims in `csrc/cuda_compat.h`. CUDA codegen unaffected.

**Config gate.** Opens HiSparse for ROCm; `fp8_ds_mla` (656-byte packed row) is
rejected by name rather than failing deep in a kernel.

**Keep batched KV copies off the HIP blit path.** HIP routes copies at or below
`GPU_FORCE_BLIT_COPY_SIZE` through a blit kernel that faults once enough are
outstanding, and HiSparse's host mirror submits ~160k descriptors per step.
Defaulting it to 2 (KB) sends them to SDMA instead. A 2x2 crossover isolates
the engine rather than the dtype: forcing fp8 onto SDMA passes 20/20, forcing
bf16 onto blit fails 0/20.

The constant has to sit below the *smallest* KV page in play, not just
HiSparse's. At 4 it lifts HiSparse's 9216 B page off blit but leaves
`OffloadingConnector`'s 2112 B rope page on it, and that path still dies; at 2
both clear. This also fixes CPU offload above concurrency 1 on ROCm, which
previously crashed outright - see the throughput table.

**Pass `indexer_slot_mapping` in the amd module.** `common/kernels.py`
substitutes `slot_mapping` when `indexer_slot_mapping` is `None`, and the amd
path never passed it, so the fused norm+rope kernel wrote the indexer's keys at
the MLA slots. Invisible without HiSparse, where the indexer and MLA groups
share one slot mapping.

## Platform-neutral fixes

These are in shared code and affect CUDA too.

- **`index_group.py` — event record does not survive nested `torch.compile`.**
  `record(...)` is traceable, so Dynamo lowers it to a node whose event lives in
  a process-global side table that `reset_user_object_tracking()` clears on
  compile entry. vLLM nests compiles, so an inner compile wipes the entry an
  outer graph depends on. Replaced with an opaque custom op keyed by an integer
  handle. CUDA appears to escape this only because its call path reaches
  `set_logical_topk_ready` from outside the compiled region.
- **`hisparse/worker.py` — mirror guard for unbracketed runs.** Warmup runs the
  model with the connector disabled, so `_per_layer_mirrored` is never cleared
  and the second pass trips `HiSparse layer 0 mirrored twice`. Added a
  `_step_in_flight` flag; the double-mirror check is unchanged inside a step.
- **`worker_base.py` — layout query runs outside the config scope.**
  `get_supported_kv_cache_layouts` calls `get_current_attn_backends(...)` with
  no config set, but a backend's supported set can depend on it. Wrapped in
  `set_current_vllm_config`.
- **`hisparse/runtime.py` — `cudaGetLastError` is absent on ROCm**, so the
  unregister-failure handler raised `AttributeError` and masked the real error.
  Guarded with `getattr`; the clear is best-effort cleanup.

## Required AITER fix (out of tree)

**This branch does not run on stock AITER.** With HiSparse enabled, gfx950 takes
a `Memory access fault` in AITER's 1-stage fp8-blockscale MoE
`fmoe_fp8_blockscale_g1u1`. Not a HiSparse bug, but HiSparse is what makes it
fire. [ROCm/aiter#5764](https://github.com/ROCm/aiter/pull/5764) backs the tail
with real memory at the `per_1x128` launch site, returning a view with the
original shape so no observable value changes. **Every number below was produced
with that patch applied.**

## Accuracy

GSM8K, 200 questions, 5-shot, greedy (`temperature=0`), seed 42. GLM-5.3, TP4,
78 layers, gfx950, 32k context, cudagraphs on, 128 GiB pinned host pool.
Model Runner V2 forced in **both** arms.

| Arm | KV dtype | Accuracy | invalid | Latency |
|---|---|---|---|---|
| HiSparse **off** | bf16 | 0.915 | 0.00 | 18.1 s |
| HiSparse **on** | bf16 | **0.940** | 0.00 | 34.4 s |
| HiSparse **on** | fp8 | **0.920** | 0.00 | 36.7 s |

**Accuracy while the host path is live.** GSM8K runs below HiSparse's offload
watermark, so it does not exercise the feature. A needle probe (TP8,
`--max-model-len 80000`, 256 GiB host pool, bf16) loads the pool with holder
requests until KV usage sits just under the watermark, then measures with short
probes alongside: **60/60**, 12/12 at every depth (10/30/50/70/90%), **245.4 GiB
host→device during the probe window**, 0 preemptions. A 25-probe run at lighter
load agrees (25/25), as does a below-watermark control.

## Throughput

The GLM-5.3 hybrid-offloading blog workload: OpenHands-style agentic
conversations, 13 turns, first turn ~74k tokens, output pinned to 220. **TP4 on
4x MI350X** (the blog ran TP8 on H200), `--max-model-len 131072`, bf16 KV,
sequential arms, fresh server per point. All three arms run to completion.

## Limitations

- **AITER's tuned ASM sparse decode is unusable under HiSparse** until its row
  offset is widened to 64 bits
- **`fp8_ds_mla` is not supported on ROCm**
- **Gated on [ROCm/aiter#5764](https://github.com/ROCm/aiter/pull/5764).**
- **Imported IPC events cap at 32 record/wait cycles on ROCm** 
- **`MultiConnector` combining HiSparse with `OffloadingConnector` crashes** on
  ROCm; each works alone.
