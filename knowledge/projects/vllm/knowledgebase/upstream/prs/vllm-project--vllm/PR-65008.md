# [CI] Lower gpu_memory_utilization in test_gemma4_lora

[Upstream PR](https://github.com/vllm-project/vllm/pull/65008) · state: closed · merged: True

## Original PR description



## Overview

Fix `lora/test_gemma4_tp.py::test_gemma4_lora`, which has failed `:nvidia: (H200 MIG 35GB) LoRA Shard 2/3` on every main build since [98943](https://buildkite.com/vllm/ci/builds/98943) (latest checked: [99008](https://buildkite.com/vllm/ci/builds/99008)), by setting `gpu_memory_utilization=0.8` like the other LoRA engine tests.

## Claims

- Fixes the engine startup failure `Free memory on device cuda:0 (29.86/32.5 GiB) on startup is less than desired GPU memory utilization (0.92, 29.9 GiB)`.

## Validation

- Not run locally. The LoRA CI step runs on this PR because it touches `tests/lora`.
- Headroom at 0.8 (26.0 GiB): in the last passing run ([98937](https://buildkite.com/vllm/ci/builds/98937)) this test used 10.54 GiB for weights + non-torch and 0.82 GiB peak activation, leaving ~14.6 GiB of KV cache for `max_model_len=1024`.

## Details

The failure began with a change in shard composition, not a code change. The only commit between the last passing build (98937) and the first failing one (98943) is #64338, an unrelated FlashInfer warmup fix. Comparing the shard 2/3 logs:

| Build | Shard 2/3 size | Runs before `test_gemma4_tp.py` | Free at engine start |
|---|---|---|---|
| 98937 (pass) | ~58 tests | `test_default_mm_loras.py` | 32.28 GiB |
| 98943 (fail) | ~4,856 tests | `test_fused_moe_lora_kernel.py` (in-process GPU kernel tests) | 29.86 GiB |

The in-process kernel tests leave ~2.4 GiB of the 32.5 GiB MIG slice in use, so the default 0.92 utilization misses by 0.04 GiB. Lowering the utilization makes the test robust to whichever tests share its shard. Freeing memory between modules in the LoRA conftest would be a broader alternative.
