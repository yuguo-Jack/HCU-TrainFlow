# [ROCm][Perf][MiniMax-M3.1] Emit the o_proj MXFP8 input from the NVFP4 sparse decode kernel

[Upstream PR](https://github.com/vllm-project/vllm/pull/65508) · state: open · merged: False

## Original PR description

## Purpose

On ROCm, every MiniMax-M3.1 decode layer runs the NVFP4 sparse decode attention, then a separate `_kernel` launch (the MXFP8 activation quant of its bf16 output, K = 2048 per TP4 rank), then the `o_proj` GEMM. In the profile of a real decode step (rank-0 profile windows at N=4 and N=16) that quant is 60 launches per step, ~4.4-4.6 us each (profiled, inflated ~1.6x).

This PR adds an `fp8_out` variant of the FlyDSL sparse decode kernel (`m3_nvfp4_sparse_decode_*_q8`) whose final store writes E4M3 values and row-major E8M0 scales instead of bf16, and hands them to `o_proj` as a `QuantizedActivation` (same mechanism as #63637 for `qkv_proj` and the FFN fusion in #65478).

## How it works

- Output layout: in the final store a lane owns head `n`, dims `32g..32g+31`, i.e. exactly one 32-element MX block, so the quantization needs no cross-lane exchange. With split-K (`splits > 1`) the last workgroup of a row merges the partials and stores O; the quant runs there on the merged O, so every 32-block sees the final values.
- Arithmetic: it quantizes the *bf16-rounded* values the bf16 store would have written (`pk_bf16`), computes the block amax on their integer bit patterns and the E8M0 byte as `clamp(exponent_field - 8 + (mantissa > 0.75), 0, 254)` (448 = 1.75 x 2^8, so this is `ceil(log2(amax/448)) + 127` exactly, no log2/division), scales by the exact power of two `2^(127-sb)` and converts with `v_cvt_pk_fp8_f32` (RNE). Hence the output is bit-identical to `mxfp8_e4m3_quantize` of the same kernel's bf16 output (not "more accurate": it is the same values, unlike the swiglu fusion in #65478).
- The scale formula was checked on CPU against `_mxfp8_e4m3_quantize_torch` on 20,000 random bf16 blocks over ~2^60 dynamic range plus edge blocks (zeros, subnormals, 447/448/449, the 1.75 boundary and the value just above it): 0 mismatches. The whole kernel compiles for gfx950 for splits 1/4/8 (`FLYDSL` compile-only on CPU). Bit-exactness on MI355X: see Tests.
- Gating: `fp8_out` is a compile-time variant; the bf16 kernel and all other callers are unchanged. The attention layer uses it only for decode-only batches (`num_prefills == 0`) in eager or full-CUDA-graph mode and when `o_proj` can take MXFP8 input (`_can_fuse_input_norm_mxfp8`); mixed batches, piecewise graphs and non-NVFP4 impls keep the bf16 path and the linear's own quant.

## Files

`ops/nvfp4_sparse_decode/kernel.py` (epilogue), `host.py` (new optional `out_q`/`out_scale`; `output` may be `None` then), `sparse_attention_nvfp4.py` (`forward_decode_mxfp8`), `model.py` (`MiniMaxM3SparseAttention` NVFP4 branch + `_run_attention` keyword outputs), `tests/kernels/attention/test_minimax_m3_nvfp4_sparse_decode.py`. `host.py` is also touched by the open split-heuristic PR #65481 (different hunks: it patches cleanly with offsets).

## Tests (MI355X, gfx950)

New in `test_minimax_m3_nvfp4_sparse_decode.py`: (1) N = 1,2,3,5,8,12,16,24 requests x 4/8 rows x 30K/150K/500K context at the default split choice, (2) every split count 1/2/4/8 x XCD on/off x 1/4 KV heads x 1/4/8 rows with padding requests and a wide magnitude range. Both assert bitwise equality of values and scales with `mxfp8_e4m3_quantize` of the bf16 kernel output and that rows past the batch are untouched. Result: the 96 new tests pass, and the whole file passes (176 passed), i.e. the existing decode tests are unchanged. The `i8` scale store and the split-merge path were correct on the first run.

## Limitations

gfx950 FlyDSL decode only; decode-only batches; K = 2048 per rank assumes 16 query heads per KV head with TP4 (generalizes to any heads x 128 since each block is within one head).

- Fangzhou-Ai · comment · 2026-11-04T03:46:51Z · [source](https://github.com/vllm-project/vllm/pull/65508#issuecomment-6621994460)

Thanks for the review. On your two asks:

**1. Decode-only and graph capture.** `_emits_o_proj_mxfp8` returns True only for a decode-only step: it needs `num_prefills == 0 and num_decodes > 0` in the sparse metadata and a runtime mode other than PIECEWISE. Prefill and mixed steps keep the bf16 output and the separate quant path. The cached `_o_proj_mxfp8` flag depends only on static module state (whether the impl has `forward_decode_mxfp8`, and whether `o_proj`'s kernel/quant key accepts MXFP8 input), not on the batch or on capture state, so it cannot flip mid-capture. The per-step part is re-read from the forward context each forward. FULL graphs are only keyed on uniform-decode batch descriptors in the cudagraph dispatcher, so a graph captured with the MXFP8 hand-off is only replayed for decode-only steps; mixed batches run PIECEWISE or eager, which take the bf16 path. In the decode profile (graph replay) the fused path is active. I have not added a unit test for the dispatch decision itself; happy to add one if you'd like.

**2. Multi-request / multi-XCD splits.** Added `test_decode_mxfp8_output_multi_request_xcd_splits` (2d8d5e5): DSpark 7 rows (8 per request) on the 8-XCD grid, explicit `splits` of 2 and 4, with 1, 5, 8, 9, 16, 17 and 24 requests, checking the fp8 output and scales bit for bit against `mxfp8_e4m3_quantize` of the same kernel's bf16 output. The existing multi-request test (1-24 requests, 30K-500K context) runs at the default split choice, so it also covers whatever the heuristic picks once #65481 lands. #65481 is not in this branch, which is why the new test passes the split counts explicitly. All 110 MXFP8 epilogue tests pass on gfx950.
