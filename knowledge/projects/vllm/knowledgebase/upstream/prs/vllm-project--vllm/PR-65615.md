# [Bugfix][Multimodal] Molmo2: snap NTSC frame rates in fps sampling

[Upstream PR](https://github.com/vllm-project/vllm/pull/65615) · state: open · merged: False

## Original PR description



## Overview

Molmo2's `frame_sample_mode="fps"` sampling truncates the source frame rate with `int()`, so NTSC videos (29.97 / 59.94 / 23.976 fps) become 29 / 59 / 23 fps. Those are primes, so the request fails for `sampling_fps=2` (Molmo2's default) and silently drops to ~1 fps for `sampling_fps=1`. This PR treats NTSC-style rates as the integer rate they approximate, in both copies of the sampling helpers.

Related: #55893 (fixed the `sampling_fps is None` guard in the `vllm/multimodal/video.py` copy only), #30997 (added Molmo2).

## Claims

- An NTSC clip is sampled exactly like the same clip at the integer rate (29.97 fps gives the same frame indices as 30 fps), both in the `molmo2` video loader and in the `molmo2.py` helpers used when the HF processor samples frames.
- Requests that failed with `ValueError: sampling_fps=2 must divide video_fps=29.` now succeed.
- Integer frame rates, and non-integer rates not within 0.2% of an integer, keep bit-identical sampling (old-vs-new sweep below).
- The `sampling_fps is None` guard in `molmo2.py` now raises the intended `ValueError` instead of a `TypeError` (the change #55893 made in the other copy).

## Details

Root cause: `get_candidate_target_fps` builds the candidate rates from the divisors of `int(video_fps)` and requires `sampling_fps` to divide it; the step size `int(video_fps / target_fps)` truncates the same way. `int(29.97)` is 29, so no `sampling_fps > 1` is valid. The helpers mirror `video_processing_molmo2.py` in the `allenai/Molmo2-*` remote code, which behaves the same; the native transformers Molmo2 processor does not use this candidate-fps logic. The default `frame_sample_mode` (`uniform_last_frame`) is unaffected, so this hits users who opt into fps mode, e.g. `--media-io-kwargs '{"video": {"frame_sample_mode": "fps"}}'`.

Fix: `snap_ntsc_fps()` in `vllm/multimodal/video.py` (also used by `molmo2.py`) returns the nearest integer when the rate is within 0.2% of it. NTSC is 0.1% below the integer, and containers often store the rounded value (OpenCV reports 29.97, 59.94, 23.976 for these clips), which a 0.1% tolerance misses by float error. The helpers apply it before the divisor logic and before computing the step. Frame timestamps still use the real source fps.

Why not `round()`: on the same 0.01-step grid, plain `round()` would make 3,010 non-NTSC rates that work today raise for `sampling_fps=2` (for example 2.51 → 3).

Limitations: integer rates such as 25 fps with `sampling_fps=2` still raise, since 2 does not divide 25; that is the helpers' documented contract and is unchanged. For NTSC inputs vLLM now differs from the allenai remote code, which raises or samples ~1 fps; I can propose the same change on the HF repos if you want parity. The two helper copies remain duplicated; I'm happy to dedupe them in a follow-up.

Duplicate check (2026-11-03, repeated 2026-11-04): GitHub searches for "29.97", "NTSC", `get_candidate_target_fps`, `frame_sample_mode`, open PRs mentioning molmo2, and the HF discussions of allenai/Molmo2-8B, -4B and -O-7B found no report or fix for this. The closest open PR, #56207, changes the `frame_sample_mode=None` branch of the same loader and does not touch the fps helpers.

CI: the loader test runs in the `cpu_test` multimodal step, the helper tests in the CPU "Multimodal Processor" shards, and the end-to-end test (`core_model`) is selected by "Multimodal Models (Standard) 4: other + whisper" (H200 MIG 35 GB).
