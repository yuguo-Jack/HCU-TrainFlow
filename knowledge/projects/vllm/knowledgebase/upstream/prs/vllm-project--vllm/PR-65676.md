# [Quantization] Prefer Humming over Marlin for int4 g128 on SM120

[Upstream PR](https://github.com/vllm-project/vllm/pull/65676) · state: open · merged: False

## Original PR description

## Overview

Part of #65560 (Phase 2): on SM120, prefer Humming over Marlin for int4 symmetric group-128 weights with bf16 activations in the mixed-precision linear path. Same idea as #63561 for SM100, written as one helper keyed by compute capability so the two can share it.

## Claims

On an RTX PRO 6000, with this branch picking Humming by default, Humming takes 11-17% less time than Marlin for prefill and 1.6-3.5% less per decoded token on Qwen3.5-4B and Qwen3.8-27B int4 checkpoints.

GSM8K accuracy holds on both models: the 4B model is within one question of Marlin, and the 27B model gets 15 more questions right (strict match). The full GSM8K run finishes 3-9% sooner.

The trade-off: Humming's outputs are not bit-identical from run to run, while Marlin's are (details below). --linear-backend marlin keeps Marlin. Other weight formats, fp16 activations and other GPUs keep today's behavior.

Measured on vLLM a8718969 with this change applied. Prefill is the end-to-end latency of a request with 1 output token, median of 5, with the prefix cache reset before each request (VLLM_SERVER_DEV_MODE=1). Decode is (T(128 tokens) - T(1 token)) / 127 with 128-token prompts, mean of 2 rounds. Models are RedHatAI/Qwen3.5-4B-quantized.w4a16 and RedHatAI/Qwen3.8-27B-INT4. One server per arm:

```bash
vllm serve <model> --dtype bfloat16 --language-model-only --max-model-len 16576 \
    --gpu-memory-utilization 0.85 --seed 20261103   # add --linear-backend marlin for the Marlin arm
```

Without --linear-backend, the server log shows "Using HummingLinearKernel for mixed-precision linear" for both models. Qwen/Qwen3-4B-AWQ (asymmetric, so outside this change) still shows MarlinLinearKernel. An earlier session on vLLM b2a9480, with both kernels forced, measured a smaller 4B prefill gain (10.1% at 4K, 9.4% at 16K). Marlin was within 1% of this run there, but Humming was slower (117 ms vs 109 ms at 4K, on two separate servers). The cause was not isolated.

Figure 2 comes from that earlier session. Almost all of the saved GPU time is in the int4 GEMMs.

No two Humming passes are bit-identical: the logprobs already differ at the first or second generated token, and before the tokens split the per-token gap reaches about 0.2 within a server and 0.3 between launches. The cause is Humming's default Stream-K split, which adds partial sums across CTAs in arrival order (humming-kernels 0.1.18). A local test patch that sets use_batch_invariant to True in get_humming_linear_compute_config turns off Stream-K and the SM120 tuning. That makes both models bit-identical, but decode 33-73% slower than Marlin. VLLM_BATCH_INVARIANT=1 cannot be used with these GDN models today (the attention selector rejects GDN_ATTN; #45819 would add support), so --linear-backend marlin is the way to get identical outputs. vLLM does not promise reproducible outputs by default (docs/usage/reproducibility.md).

Humming compiles its kernels during startup. In the earlier session (4B model), a server started with an empty HUMMING_CACHE_DIR compiled 69 kernels during startup, and 30 prefill requests of 16 to 16384 tokens afterwards compiled nothing new. Startup took 82.6 s with the empty cache, 70.6 s with a warm one and 68.1 s with Marlin (one launch each).

Tests on the RTX PRO 6000 with this branch: the first command below gives 28 passed and 1 skipped, the second 128 passed and 3 skipped. The skipped tests are CPU, ROCm or XPU only.

## Details

The helper moves Humming directly ahead of Marlin when the capability is in _HUMMING_INT4_G128_CAPABILITIES (only 120 here) and the weights are uint4b8, group size 128, no zero points, with bf16 activations. It is separate from _HUMMING_PREFERRED_CAPABILITIES because adding 120 there would move Humming ahead of Marlin for every linear and MoE format on SM120, and only int4 g128 linears were measured. A --linear-backend that has a mixed-precision kernel, such as marlin, leaves only that kernel, so nothing is reordered; a backend without one falls back to automatic selection and gets the new order. SM121 (DGX Spark) was not measured and keeps Marlin. The RTX 5090 is also SM120, so it gets the change, but it was not measured. If #63561 lands first, adding 100 to the set replaces its helper; the only difference is that this one also requires bf16 activations.

GPTQ and Quark symmetric int4 g128 layers, and compressed-tensors W4A8 and W4A4 int checkpoints with the same weights, take the same path; only compressed-tensors W4A16 was measured. Marlin ran the W4A8 and W4A4 ones as W4A16. On SM120 Humming runs the W4A8 ones as W4A16 too, and the W4A4 ones with int8 activations.

VLLM_MARLIN_INPUT_DTYPE is only applied when Marlin is picked, so on SM120 compressed-tensors int4 g128 checkpoints now need --linear-backend marlin to keep Marlin's int8 or fp8 activation path. #65542 would remove that variable.

If run-to-run reproducibility matters more than speed for this path, the alternative is to keep Marlin on SM120 until Humming's Stream-K reduction is made order-independent. Humming already has an ordered fixup path that it uses for some shapes; that change belongs in Humming rather than in this PR.

No open PR changes the int4 order on SM120. Related: #63561 (SM100), #63265 (SM90), #63777 (MXFP8 MoE on SM12x), #65540 (Marlin PTX on SM12x), #65542 (Marlin 8-bit activations). The docs now mention the SM120 default and the --linear-backend marlin opt-out.
