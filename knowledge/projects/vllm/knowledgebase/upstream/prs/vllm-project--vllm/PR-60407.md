# [Feature][Observability] Add production-ready Grafana dashboards

[Upstream PR](https://github.com/vllm-project/vllm/pull/60407) · state: open · merged: False

## Original PR description



## Overview

Adds five Grafana dashboards for vLLM's Prometheus metrics to `examples/observability/dashboards/grafana/`. **Service Status** is a large-print status board for the people who use a vLLM service. The other four are for the team that runs it: **Overview** (with latency SLOs), an **Instances** drill-down, **KV Cache**, and **Speculative Decoding**. The PR also updates the dashboard READMEs and adds a short *Grafana Dashboards* section to `docs/usage/metrics.md`.

The existing dashboards (`performance_statistics.json`, `query_statistics.json`, `prometheus_grafana/grafana.json`) and the Perses specs are unchanged. There are no Python code changes. No issue is linked; see *Duplicate-work check* under Details.

## Claims

- **Coverage:** the new dashboards chart 69 `vllm:*` metrics; the three existing Grafana examples chart 17 between them. The added coverage includes:
  - per-engine (data-parallel) views and SLO attainment
  - prefix caching by cache tier, KV block residency, KV connectors (NIXL) and KV offloading
  - speculative decoding, sleep mode, LoRA and MFU
  - the API server's HTTP and process metrics
- **Built for fleets:** every panel aggregates across instances and engines. Variables cover data source, job, model, instance and engine, plus ad hoc filters such as `namespace`. The dashboards link to each other and keep the time range and filters. Clicking a row in the per-model or per-instance table drills down to it.
- **Robust queries:**
  - ratios are guarded against division by zero
  - quantiles are computed from summed bucket rates
  - token-length panels use only the bucket boundaries that all selected servers share
  - the status board shows *Down*, and blanks its numbers instead of freezing them, as soon as a model's servers stop reporting
- **End-user view:** `vLLM / Service Status` shows one strip per model with Status (Online / Sleeping / Down), response time, output speed, success rate and requests per minute. The tiles are color-coded, readable from across a room, and work in kiosk mode.
- **Compatibility:** Grafana 10.4+ (tested on 10.4, 11.6 and 13.2) and Prometheus 2.26+ (including 3.x, Thanos and Mimir). Every queried metric name is defined on `main`.

## Details

**Motivation.** The existing examples have 13–16 panels each and chart 17 metrics between them, mostly request latency and throughput. They have no instance or engine dimension, no SLO view, and nothing aimed at the people who use the service.

**Design.**
- **Format and naming.** The dashboards are plain Grafana JSON (schemaVersion 39), so they work with UI import, the HTTP API or file provisioning. They are prefixed `vllm_`, tagged `vllm`, and have stable `vllm-*` uids so links between them work. The existing dashboards are kept so current imports keep working.
- **Optional features.** Rows for optional features are collapsed, and their titles name the flag they need (for example *requires --kv-cache-metrics*).
- **SLO tiles.** These count requests below a histogram bucket boundary, so the selectable targets are default boundaries; other targets need `--custom-histogram-buckets`, which the docs explain.
- **Status board.**
  - Tiles are instant queries that only return a value while the model is reporting.
  - *Output speed* is generated tokens per second divided by the average number of running requests. Unlike 1/TPOT, it counts every token of a speculative decoding step.
  - The color thresholds (1 / 3 s, 10 / 20 tok/s, 95 / 99 %) are defaults to tune.
- **Diff size.** Almost all of the diff is dashboard JSON (11,853 lines). The docs change is 120 added and 50 removed lines.

**Limitations.**
- No CI check covers the dashboards, so a renamed metric would not be caught automatically. The metric-name check above was run by hand.
- Real-server validation ran on CPU, not on a GPU deployment. GPU-only features (sleep mode, NIXL, offloading) are covered only by the simulator.
- Ray metrics (`RayPrometheusStatLogger`) use other names and are not covered. The Perses specs are not updated.
- HTTP and process metrics are not labelled by model, and process metrics are missing with `--api-server-count` > 1. The README documents both.
- Not charted: HiSparse, Mooncake store, HF3FS, KV-offload tiering, diffusion, realtime WebSocket and tool-parser metrics.
