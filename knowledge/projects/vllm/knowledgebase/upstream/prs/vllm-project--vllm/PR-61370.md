## Overview

Adds a CI test that serves MiniMax-M3 with DSpark in 7 deployments on one 4×B200 node, to catch regressions in the combinations that work on main today. The combinations come from the sweep in #60791; known failures are tracked there and are not in the test.

## Claims

- `tests/models/minimax_m3/test_feature_matrix.py`: MiniMax-M3 cut to 6 layers (3 dense + 3 MSA/MoE), `--load-format dummy`. Only config and tokenizer files are downloaded.
- CI step `:nvidia: (4xB200) MiniMax-M3 Feature Matrix`, one shard, 12 min locally.
- Each deployment also checks DSpark with a JSON-schema request.

## Validation

All deployments run DSpark (k=3) and check that:
- a JSON-schema chat request ends with `stop` and parses;
- 8 concurrent requests of mixed lengths complete;
- `vllm:spec_decode_num_drafts_total > 0`;
- P/D: `vllm:prompt_tokens_by_source{source="external_kv_transfer"}` grows on the decoder, and logprobs match a recompute on the decoder (same-TP pairs only, since dummy weights differ across TP);
- CPU offload: after `/reset_prefix_cache?reset_external=false`, a resend has `cached_tokens > 0` and the same logprobs;
- image input is accepted (`*-image`).

## Details

- Dummy weights avoid a multi-GB download per run. Outputs are meaningless, so correctness is checked as logprob equality between two paths, the JSON schema is bounded and uses `disable_any_whitespace` so it terminates, and DSpark is checked for proposing drafts rather than for acceptance.
- Deployments with a KV connector pass `--disable-hybrid-kv-cache-manager`: with DSpark's sliding-window layers the hybrid manager mixes block sizes, which NIXL and the CPU offload connectors do not support (#60791, items 2 and 6).
- Left out: known failures (#60791), MooncakeStore and PP (see above), single-GPU and TP2 variants that a larger deployment covers, and plain chat/streaming, which other suites test.
- No other MiniMax-M3 end-to-end serving test exists in `tests/` or `.buildkite/`. The layout follows the Kimi K3 prefix-cache test (#59229).
