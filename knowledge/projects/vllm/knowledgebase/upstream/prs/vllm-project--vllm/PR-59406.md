# [ROCm][Perf][Bugfix] Probe the preshuffled FP4 GEMM config by logical K

[Upstream PR](https://github.com/vllm-project/vllm/pull/59406) · state: closed · merged: True

## Original PR description

## Purpose

With `VLLM_ROCM_USE_AITER_FP4_ASM_GEMM=1`, `AiterMxfp4LinearKernel` sends decode-sized MXFP4 linears (M ≤ 64) to AITER's Triton `gemm_afp4wfp4_preshuffle` when `rocm_aiter_ops.is_triton_gemm_afp4wfp4_presh_ws_tuned(N, k_bytes)` reports a tuned config, and to the ASM `gemm_a4w4` otherwise.

The gate checks the wrong file. `k_bytes` is `weight.shape[1]`, i.e. K/2, and the gate probes `GEMM-AFP4WFP4_PRESHUFFLED-N={N}-K={4 * k_bytes}.json`, which is 2K. `gemm_afp4wfp4_preshuffle` itself resolves `N={N}-K={2 * k_bytes}`, the logical K. So the gate asks about a different shape than the one the kernel then runs:

- If the layer's own shape is tuned but 2K is not, the gate says no and the layer falls back to ASM.
- If 2K is tuned but the layer's own shape is not, the gate says yes and the layer runs the Triton kernel on AITER's generic default config.

Of the 25 `gemm_afp4wfp4_preshuffled` configs AITER ships for gfx950 (ROCm/aiter@89a47b8), 19 are never selected on main. Another 19 shapes are accepted only because a file exists at twice their K:

| | (N, K) |
| --- | --- |
| Tuned, rejected on main | (1280, 8192), (2112, 7168), (2560, 8192), (3072, 1536), (4096, 512), (4096, 14336), (5120, 8192), (7168, 8192), (8192, 8192), (8192, 28672), (10240, 8192), (14336, 8192), (16384, 16384), (16384, 53248), (18432, 16384), (28672, 8192), (36864, 7168), (57344, 8192), (106496, 16384) |
| Untuned, accepted on main | (1280, 4096), (2112, 3584), (2560, 4096), (3072, 768), (4096, 256), (4096, 7168), (5120, 4096), (7168, 4096), (8192, 512), (8192, 1792), (10240, 4096), (14336, 4096), (16384, 8192), (16384, 26624), (18432, 8192), (28672, 4096), (36864, 3584), (57344, 4096), (106496, 8192) |

This PR probes `2 * k_bytes`, the same file the kernel loads.

The existing tuned-shape case in `tests/kernels/quantization/test_rocm_mxfp4.py`, `(M, N, K) = (32, 8192, 16384)`, only passed because `N=16384-K=16384` exists. It is replaced by `(64, 4096, 8192)` and `(32, 16384, 16384)`, and the test now also asserts that the kernel resolves a tuned config for the shape. `test_aiter_fp4_preshuffled_tuned_gate_uses_logical_k` pins the gate itself: `(N=16384, K=16384)` is tuned and `(N=16384, K=8192)` is not.

## Test Plan

- Hardware: 8× MI355X (gfx950)
- Unit tests: `tests/kernels/quantization/test_rocm_mxfp4.py -k preshuffled`
- Model: `amd/Qwen3.8-2.4T-A95B-Quark-MXFP4`, TP8, `max_num_batched_tokens=8192`. The GDN `in_proj_qkvz` (N=4608, K=8192) and `out_proj` (N=8192, K=2048) linears are quantized online to MXFP4 and served with `VLLM_ROCM_USE_AITER_FP4_ASM_GEMM=1`.
- Serving A/B (same image except this change and one AITER config file, see below): random dataset, ISL=8192, OSL=1024, range-ratio=0.8, concurrency `{4, 8, 16, 32, 64}` with 32/64/96/128/256 prompts and one warmup request per concurrency slot
- Accuracy: GSM8K, 1319 problems, 5-shot, thinking off, temperature=0.0, max-tokens=2048. Same servers as the A/B.

The PR arm also carries a gfx950 `GEMM-AFP4WFP4_PRESHUFFLED-N=4608-K=8192.json` from https://github.com/ROCm/aiter/pull/5998 tuned for `in_proj_qkvz`. Without this change the file is never read, because the gate probes `N=4608-K=16384`, so `in_proj_qkvz` runs the ASM `gemm_a4w4` in the control either way (confirmed in the control trace below). `out_proj` uses AITER's existing `N=8192-K=2048` file and runs the preshuffled kernel in both arms, only because `N=8192-K=4096` also exists.
