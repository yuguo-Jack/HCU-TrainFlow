# [Bugfix][Core] Set TRITON_CACHE_DIR at worker startup to stop Triton kernels rebuilding on every start

[Upstream PR](https://github.com/vllm-project/vllm/pull/63083) · state: open · merged: False

## Original PR description

## Overview

vLLM now sets `TRITON_CACHE_DIR` when a worker starts, so Triton's JIT kernels are cached under `VLLM_CACHE_ROOT` instead of `~/.triton/cache`.

Run the same `vllm serve` command three times:

| | AOT compile cache | Triton JIT cache |
| --- | --- | --- |
| first run | miss, writes under `VLLM_CACHE_ROOT` | miss, writes under `VLLM_CACHE_ROOT` |
| second run | **hit** | **miss**, falls back to `~/.triton/cache` |
| third run | hit | hit |

The first run compiles, which constructs an Inductor autotuner, and torch exports `TRITON_CACHE_DIR` as a side effect of that constructor. The second run hits the AOT cache, constructs no autotuner, and so nothing exports the variable.

In most deployments this costs one extra Triton compile and then stops mattering, because the third run is warm. It becomes permanent when a container runs `vllm serve` once and that environment is then sealed into an image. The image carries `VLLM_CACHE_ROOT` but not `~/.triton`, so every container started from it is a second run, and pays the Triton compile again.

## Claims

- The second time vLLM starts against a warm compile cache, it rebuilds its own Triton kernels from scratch. It no longer does. On Qwen3.5-2B that was 172 kernels and 69 s.
- Setting `TRITON_CACHE_DIR yourself still works: vLLM only fills it in when it is unset.
- Inference is untouched: the call runs once when a worker starts, and the same prompt gives the same completion.

## Validation

Qwen3.5-2B on an AMD Radeon 8060S (gfx1151), running the same command three times in one environment:

| second run | wall time | kernels compiled into `~/.triton/cache` |
| --- | --- | --- |
| before | 274 s | 172 |
| after | 205 s | 0 |

Those 172 are not new work: every one of them is already under `VLLM_CACHE_ROOT`, written by the first run. Both arms end with the same 381 distinct cache keys and print the same completion; the change only decides where the keys live.

`tests/utils_/test_triton_cache_dir.py` is the regression test. Without the change it fails with `restart compiled 46 Triton kernels into a private Triton home`; with it, it passes.

They are recompiled because Triton cannot find them: the first run leaves them in torch's own Inductor tree, which Triton reads only while `TRITON_CACHE_DIR` points there. After the change they are in one `triton_cache/` that every run reads.

The change catches all three, which also confirms the hook runs early enough. The fourth is Triton's `hip_utils`, a driver helper rather than a JIT kernel.

## Details

### Root cause

torch exports `TRITON_CACHE_DIR` from `CachingAutotuner.__init__`. On an AOT cache hit, torch restores the autotuner through `__setstate__`, which skips `__init__`. Nobody then exports the variable. That is the first against second run above.

Inductor's kernels still find their directory, because `triton_cache_dir()` falls back to `TORCHINDUCTOR_CACHE_DIR`. vLLM's own `@triton.jit` kernels have no fallback: Triton reads `TRITON_CACHE_DIR` and nothing else. They land in `~/.triton/cache` and rebuild there at every start.

#39718 nested the Inductor cache under the AOT compile directory. This is Triton's own JIT cache, which that change does not reach: on an AOT hit no Inductor compile happens at all. No open PR addresses it.

In short: the rule for where Triton keeps its artifacts lives in a constructor that pickle legitimately skips.

### Limitations

- The directory grows without a limit, as `~/.triton/cache` did.
- Ranks on one host share the directory, as they did with `~/.triton/cache`.
- `vllm/v1/attention/backends/rocm_segmented_attn.py` already does the same `setdefault` for one backend. That call is now a no-op. I left it in place, and a follow-up can remove it.
- Triton's `hip_utils` driver helper is still built in `~/.triton`, because the driver initialises at import time, before any worker exists. Catching it would mean setting the variable from `vllm/__init__.py`, which would mutate the environment of anyone importing vLLM as a library. It is one small file, model-independent, and built once.

<details>
<summary>Design notes and documentation</summary>

- **`WorkerBase.__init__`.** The rule is process-wide, not per-compilation, so the compilation path is the wrong layer. `gpu_worker.Worker` is the only direct subclass, and `CPUWorker` and `XPUWorker` reach it through `super().__init__()`, so one hook covers every platform in `worker_cls`.
- **Timing.** `super().__init__(...)` is the first statement of `Worker.__init__`, which runs before `init_device()` and `load_model()`, and before torch builds any autotuner. A value that is already set at that point came from the operator. The code therefore needs no heuristic to tell the two apart, and no existing code changes.
- **A separate function for one call site.** Inlining the seven lines into `WorkerBase.__init__` would add environment and `makedirs` logic to a core file. Keeping it in `system_utils.py`, beside the other environment helpers, leaves the core file with one call and keeps the behaviour unit-testable.
- **`$VLLM_CACHE_ROOT/triton_cache`.** These kernels are not model-specific, so they do not belong under the per-model compile cache. Inductor's kernels already travel inside the AOT artifact.
- **`VLLM_DISABLE_COMPILE_CACHE`.** It still disables only vLLM's `torch.compile` artifacts. Triton's JIT cache was already persistent in `~/.triton/cache`. This change moves it, and does not make it persistent.

`docs/usage/security.md` gains a `TRITON_CACHE_DIR` row in the cache table, and its claim that Triton falls back to `~/.triton/cache` when compile caching is off is corrected. The discoverability check in the contributing guide found that a reader looking the variable up would start at the environment variable reference, which is generated from `vllm/envs.py` and so cannot list a variable without a `VLLM_` prefix, so `docs/configuration/env_vars.md` now names it and links to the cache section.

</details>
