# [Perf][DSv4.1] Split fused_wqa_wkv by token across TP ranks on SM90

[Upstream PR](https://github.com/vllm-project/vllm/pull/58872) · state: closed · merged: True

## Original PR description

## Purpose

Without sequence parallelism, every TP rank computes DeepSeek-V4.1's `fused_wqa_wkv` (5120 → 1280 + 512) for all tokens, so all ranks do the same work. The checkpoint stores this weight as FP8 with UE8M0 block scales, which vLLM runs through its MXFP8 path. On SM90 that path is a W8A16 Marlin GEMM: on H20 it takes 1.79 ms per layer for an 8192-token prefill chunk, 72 ms per chunk over the 40 layers.

This PR splits the projection by token for batches of at least 2048 tokens. Each rank projects its token shard (`sp_shard`), and `sp_all_gather` rebuilds `qr_kv`. The change is confined to `DeepseekV4Attention._fused_wqa_wkv_gemm`:
- `_run_parallel_input_projections` is unchanged, so the multi-stream decision is the same as on main.
- The all-gather is issued on the current stream, right after the GEMM that produces its input.

`_shard_fused_wqa_wkv` in the NVIDIA decoder layer enables the split only when all of the following hold:
- **SM90.** On SM100, `fused_wqa_wkv` runs as a native MXFP8 GEMM, far cheaper than W8A16 Marlin, so the gather would be a much larger share of the cost. I have not measured SM100, and the H20 results below do not carry over to it.
- **No sequence parallelism.** There the hidden states are already sharded, and #57257 splits this projection for that case.
- **No LoRA.** The LoRA wrapper maps every token of the batch.
- **No micro-batching.** Two micro-batches would share the custom all-gather buffer.
- **No batch invariance.** Whether a token takes the split depends on the batch size.
- **The custom all-reduce is enabled and fully connected.** This serves only as a proxy for NVLink between all TP ranks. From 6144 tokens at TP8, the shard exceeds the custom all-gather's 2 MiB limit, so the gather itself runs on NCCL.

TP4 and TP2 take the same gate but were not measured. On Hopper they need pipeline parallelism to hold the checkpoint.

The compressor's `fused_wkv_wgate` and the indexer's `weights_proj` stay replicated, and `_run_parallel_input_projections`, which can run them on separate streams, is unchanged. They appear in only a few layers:
- the compressor in the 4 KV-source layers (2, 8, 14, 20);
- the indexer in the 8 index-source layers, which are those four plus 24, 28, 32 and 36.

At 8192 tokens, splitting them as well would save at most another 457 µs in a KV-source layer (last column of the second table; layer 20's compressor is half as wide). In the four indexer-only layers the projection is only 5120 → 32. This PR saves about 1.45 ms in each of the 40 layers, so it limits the split to this dominant projection.

**Why 2048 tokens.** On H20 the split is faster from 48 tokens (first table below). H100 and H200 have about 6.7 times H20's dense throughput with the same 900 GB/s NVLink, so the replicated GEMM costs much less there while the gather costs the same.

I have no H100 or H200 to measure on, so I scaled the H20 numbers pessimistically:
- a GEMM of 1024 rows or more runs 6.7 times faster than on H20;
- one of 512 rows runs 3.7 times faster, and one of 256 rows or fewer only twice as fast;
- the gather runs no faster.

Under these assumptions the break-even is about 1450 tokens, and 2048 is the next power of two. A measurement on H100 or H200 would confirm or retune it.

**Related work.** I found no upstream PR for the case without sequence parallelism. The fork commit bytedance-iaas/vllm@383776ac20 splits `fused_wqa_wkv` the same way, but behind an environment variable that is off by default, and not when speculative decoding is on.

## Test Plan

**Kernel benchmark.** Setup:
- Hardware: 8× H20 (SM90, 96 GB, NVLink), TP8.
- Software: torch 2.13.0+cu130, NCCL 2.29.7, vLLM nightly `0.30.1rc1.dev85+g8b84e1506` with this diff applied as a Python overlay.
- What it runs: `fused_wqa_wkv` is built as the model builds it, with random weights and the checkpoint's quantization, so SM90 runs Marlin. The second table times `_run_parallel_input_projections` from this branch, which calls `_fused_wqa_wkv_gemm`, with the model's projection shapes and three aux streams.

Timing follows `.agents/skills/kernel-microbenchmark`:
- One CUDA graph per candidate.
- Before every measured replay, an L2 flush (twice the L2 size) and a device-side barrier, both outside the timed interval.
- The time of a replay is the CUPTI span of its kernels. Each sample is the maximum over the 8 ranks, and the tables report the median of 50 samples.
- Candidates alternate within every round, and correctness is checked before timing.

The benchmark script is not part of this PR; I can add it under `benchmarks/kernels/` if that helps.

**Serving.** TP8 without expert parallelism. DSpark uses synthetic acceptance with a mean acceptance length of 3.51, the same distribution in both arms:
