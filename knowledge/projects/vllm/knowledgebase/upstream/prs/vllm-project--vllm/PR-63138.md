# [Frontend] Expose --sleep-mode-backend on the CLI

[Upstream PR](https://github.com/vllm-project/vllm/pull/63138) · state: closed · merged: True

## Original PR description



## Overview

Adds `--sleep-mode-backend` to `EngineArgs` and the CLI so a sleep-mode backend registered by a plugin (RFC #34303) can be selected from `vllm serve` or `LLM(...)`. Fixes #63056.

## Claims

- `vllm serve --sleep-mode-backend <name>` and `LLM(..., sleep_mode_backend=<name>)` now set `ModelConfig.sleep_mode_backend`. Before this, the field existed but no engine argument reached it.
- The default stays `cumem`, so nothing changes for existing users.
- `docs/features/sleep_mode.md` gets a short section on choosing a backend.

## Validation

New unit test `tests/engine/test_arg_utils.py::test_sleep_mode_backend_arg` checks the default, the CLI parse and the value that lands on `ModelConfig`.

Before the fix (base `fdc5fde9d7`):

```text
$ python -m pytest tests/engine/test_arg_utils.py -k sleep_mode_backend
E       AttributeError: 'EngineArgs' object has no attribute 'sleep_mode_backend'
1 failed, 115 deselected
```

With the fix:

```text
$ python -m pytest tests/engine/test_arg_utils.py tests/v1/worker/test_sleep_mode_backend.py
125 passed
```

End to end on an RTX 4060 (8 GB, WSL2) with `facebook/opt-125m`. I registered a small backend that subclasses `CuMemBackend` and logs `suspend`/`resume`, then selected it by name:

```python
SleepModeBackendFactory.register_backend(
    "logging_cumem", "toy_sleep_backend", "LoggingCuMemBackend"
)
llm = LLM("facebook/opt-125m", enable_sleep_mode=True,
          sleep_mode_backend="logging_cumem", enforce_eager=True)
# generate -> llm.sleep(level=1) -> llm.wake_up() -> generate
```

```text
INFO [sleep_mode_backend.py:202] Using sleep-mode backend: logging_cumem
[toy backend] suspend(level=1)
[toy backend] resume(tags=None)
identical after sleep/wake: True   (greedy, 16 tokens)
```

With an unregistered name, the engine starts and the first sleep raises the factory's existing error:

```text
ValueError: Unsupported sleep-mode backend 'not_registered'. Registered backends: cumem, logging_cumem.
```

`ruff check` and `ruff format` are clean. `tools/pre_commit/mypy.py 3.11 vllm/engine/arg_utils.py` reports the same two errors (`dtype` at L511, `lora_dtype` in `create_lora_config`) on the base commit as on this branch, so this change adds none.

The test runs in the existing Engine Core Buildkite step (`pytest -v -s engine`), which already covers `vllm/engine/` and `tests/engine`.

## Details

- This follows the pattern of the neighbouring sleep-mode flags: a field that defaults to `ModelConfig.sleep_mode_backend`, `add_argument` from `model_kwargs`, and a pass-through in `create_model_config`. The help text comes from the existing `ModelConfig.sleep_mode_backend` docstring.
- The flag takes any string and has no `choices`. Plugin backends register when `load_general_plugins()` runs in `EngineArgs.__post_init__`, which is after argparse, so a fixed list would reject the backends this flag exists for.
- An unknown name is still only caught when the worker first creates the backend, as before. I left early validation out to keep this PR to the wiring; I'm happy to add a check after plugin loading if reviewers want it here.
- Choosing a non-`cumem` backend turns off `--sleep-mode-offload-cudagraph` (`vllm/config/vllm.py`). That is existing, documented behaviour, and the new docs section points to it.
- Not a duplicate: no open PR adds `sleep_mode_backend` to `arg_utils.py`. #58183 and #58066 read the config field but don't expose it. The issue author asked me to take this on in the issue thread.
- AI assistance was used to write this change. I reviewed every line and ran the tests and the end-to-end check above myself.
