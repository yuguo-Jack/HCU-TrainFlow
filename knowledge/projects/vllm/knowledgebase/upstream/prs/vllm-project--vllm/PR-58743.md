# [ROCm][Kimi-K3] Support BF16 KDA recurrent state

[Upstream PR](https://github.com/vllm-project/vllm/pull/58743) · state: open · merged: False

## Original PR description

## Overview

Honor `--mamba-ssm-cache-dtype bfloat16` in the ROCm Kimi-K3 KDA path, including paged prefill states and checkpoints.

## Claims

- Plan recurrent caches using the requested dtype.
- Read and write BF16 paged states directly in HIP prefill, retaining FP32 accumulation and scan workspaces.
- Select BF16-compatible backends under `auto`, preserving the existing FP32 backend priority.

## Validation

```bash
VLLM_ROCM_USE_AITER=1 VLLM_SSM_CONV_STATE_LAYOUT=SD .venv/bin/python -m pytest tests/models/kimi_k3/test_amd_kda_{chunk,decode}.py -q
# 133 passed
VLLM_ROCM_USE_AITER=0 VLLM_SSM_CONV_STATE_LAYOUT=SD .venv/bin/python -m pytest tests/models/kimi_k3/test_amd_kda_{checkpoint,adaptive_verification}.py -q
# 28 passed
```

Coverage includes BF16/FP32 state writes, checkpoint resume, graph replay, padded rows, backend selection, and Gluon FP32 kernels. The two BF16 selection cases fail against the pre-guard code. Metadata tests use AITER=0 because their borrowed Qwen configuration otherwise selects the unrelated GDN FlyDSL backend.

Real Kimi-K3 weights, TP8/DCP8, FP8 KV, BF16 SSM, AITER enabled, default KDA `auto`, eager execution; full GSM8K, 5-shot, concurrency 64, `max_tokens=512`:

| Decode | Correct | Accuracy | Error / abort |
|---|---:|---:|---:|
| Ordinary | 1266 / 1319 | 95.98% | 0 / 0 |
| DSpark K4, standard rejection | 1258 / 1319 | 95.38% | 0 / 0 |

Both modes completed all requests and produced the same single whitespace-only answer. DSpark accepted 71.50% of proposed tokens. Observed pure and mixed batches used HIP BF16 prefill and Triton BF16 decode/verify while AITER remained available.

Validation used the complete candidate source and rebuilt HIP extension with `vllm/vllm-openai-rocm:nightly-rocm100-e68efc685ab1e6f1eda004ced7157e3ca411da2f`. A previous same-runtime wrapper/native prefill comparison had identical output and state tensors for three operator cases. These results establish correctness, not an end-to-end speedup.

## Details

The model and layer previously dropped the requested recurrent-state dtype. The HIP prefill kernel also assumed FP32 persistent states. This update propagates the dtype and adds native BF16 state I/O, including checkpoint stores. FP32-only Gluon and HIP decode paths are excluded when the recurrent cache is BF16; AITER BF16 support can be enabled separately once available. This extends the existing PR rather than introducing an overlapping change.
