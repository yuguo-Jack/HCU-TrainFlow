# [ROCm][Kimi-K3] Support BF16 KDA recurrent state

[Upstream PR](https://github.com/vllm-project/vllm/pull/58743) · state: closed · merged: True

## Original PR description

## Overview

Honor `--mamba-ssm-cache-dtype bfloat16` in the ROCm Kimi-K3 KDA path, including paged prefill states and checkpoints.

## Claims

- Honor the requested SSM cache dtype in both the model and attention layer.
- Support BF16 paged states and checkpoints in HIP prefill, keeping accumulation and scan workspaces in FP32.
- Select compatible backends under `auto` without changing FP32 backend priority.

## Validation

Both GPU test commands passed on the current PR head.

```bash
VLLM_ROCM_USE_AITER=1 VLLM_SSM_CONV_STATE_LAYOUT=SD .venv/bin/python -m pytest tests/models/kimi_k3/test_amd_kda_{chunk,decode}.py -q
# 139 passed
VLLM_ROCM_USE_AITER=0 VLLM_SSM_CONV_STATE_LAYOUT=SD .venv/bin/python -m pytest tests/models/kimi_k3/test_amd_kda_{checkpoint,adaptive_verification}.py -q
# 28 passed
```

Tests cover BF16/FP32 state writes, checkpoint resume, graph replay, padded rows, and backend selection. Both BF16 selection regressions fail without the guard. Metadata tests disable AITER to avoid an unrelated Qwen GDN FlyDSL path. Lint, type checks, and test tethering passed after rebasing.

### GSM8K

Evaluated Kimi-K3 on the full GSM8K test set (1,319 questions) using `lm-evaluation-harness` with 5-shot chat prompts, 48 concurrent requests, `temperature=0`, `top_p=1`, and `max_tokens=12288`.

Both configurations used TP8/DCP8, DSpark K4, HIP fused prefill, and Triton recurrent decode. Only the SSM cache dtype differed.

| SSM cache dtype | Correct answers | Strict-match accuracy |
|---|---:|---:|
| FP32 | 1,283 / 1,319 | 97.27% |
| BF16 | 1,278 / 1,319 | 96.89% |

All requests completed without empty responses or output-length truncation.

## Details

- The model and attention layer previously ignored the requested SSM dtype, while HIP prefill assumed FP32 states.
- Native BF16 paged-state I/O avoids extra gather/cast/scatter and supports checkpoint export.
- Gluon BF16 support merged in ROCm/aiter#6672 but is not in vLLM's pinned AITER release; keep its dtype guard until the dependency and integration are updated. HIP non-speculative decode remains FP32-only.

### Backend selection and performance

FP32 keeps its existing backend priority: AITER/Gluon when available, with HIP fused decode available for supported non-speculative workloads. BF16 currently uses HIP fused prefill and Triton recurrent decode/verification; enabling Gluon BF16 requires the newer AITER implementation and a follow-up routing change.

In completed 1-hour AgentX runs on 8× MI355X (single-node TP8/DCP8, c48, DSpark K4 with synthetic acceptance 3.36), BF16 achieved **16,210 total tokens/s/GPU** versus **14,904 for FP32 (+8.76%)**. Throughput includes input and output tokens. Both used the same nightly plus this PR, HIP fused prefill, and Triton recurrent decode; the FP32 control used a test-only routing override to select the same backends.

To enable BF16 with this PR, keep `VLLM_ROCM_USE_AITER=1` and set:

```text
--mamba-ssm-cache-dtype bfloat16
```
