# [Perf] Add mm_tensor_ipc=cuda_ipc TP-aware GPU transport

[Upstream PR](https://github.com/vllm-project/vllm/pull/49462) · state: open · merged: False

## Original PR description

# [Perf][Multimodal] Add `mm_tensor_ipc="cuda_ipc"`: TP-aware GPU-to-GPU transport for multimodal features

## Summary

Adds a new value to the existing `--mm-tensor-ipc` option: **`cuda_ipc`**. It
transports GPU-resident multimodal feature tensors (e.g. `pixel_values` produced
by a GPU image processor) from the API-server (frontend) process to every
tensor-parallel worker **without a host round trip**, and — unlike the existing
`torch_shm` mode — it **supports `tensor_parallel_size > 1`**.

It reuses the out-of-band tensor hooks already in `vllm/v1/serial_utils.py`
(`OOBTensorConsumer` / `OOBTensorProvider`), so the wiring mirrors `torch_shm`.

## How it works

- **Sender (frontend):** one persistent GPU pool is allocated once and its CUDA
  IPC handle exported once. Each request copies its feature tensor into a free
  slice (device-to-device) and the OOB consumer returns only a small
  msgpack-native metadata dict (pool handle + offset). No per-request
  `cudaIpcGetMemHandle`, no pickle.
- **Deferred decode:** the frontend→engine provider returns a lightweight,
  picklable `CudaIpcPoolProxy` (a few dozen bytes) instead of a tensor, so it
  survives engine-core scheduling and the engine-core→worker broadcast as
  metadata.
- **Receiver (every TP worker):** the handle is opened once per process and
  cached; each request slices the cached mapping and copies its tensor out on
  the worker's own device — rank 0 (same device as the pool) is a plain D2D
  copy, other ranks read over NVLink/P2P. No per-request open/close.
- **Recycling:** each in-flight slice owns a row of lock-free per-consumer flag
  cells in shared memory; a slice is reclaimed once `tensor_parallel_size`
  distinct consumers have read it.

CPU features are rejected (encoder falls back to `direct_rpc`), so this only
engages for GPU-preprocessed features (e.g. `mm_processor_kwargs={"device":
"cuda"}`). Requires `mm_ipc_gpu_memory_gb > 0`, which both sizes the pool and
reserves the headroom for it (validated in config).

## Why this is not a duplicate

- `torch_shm` (the existing OOB transport) is explicitly single-API-server /
  `tensor_parallel_size == 1` only and routes through a host shared-memory
  queue. This change fills the documented `TP > 1` gap and stays on-device.
- Duplicate-work checks run before opening the PR:
  ```bash
  gh pr list --repo vllm-project/vllm --state open --search "mm_tensor_ipc"
  gh pr list --repo vllm-project/vllm --state open --search "cuda ipc multimodal"
  gh issue list --repo vllm-project/vllm --search "multimodal tensor parallel broadcast"
  ```

## Files changed

- `vllm/multimodal/gpu_ipc_memory.py` — add the `cuda_ipc` transport (persistent
  pool + picklable `CudaIpcPoolProxy` + `CudaIpcTensorSender(OOBTensorConsumer)`
  + `cuda_ipc_provider` + lock-free recycling) alongside the existing
  frontend GPU-memory admission control. Kept in this one module (rather than a
  separate file) per review, so all frontend GPU multimodal memory lives
  together.
- `vllm/config/multimodal.py` — add `cuda_ipc` to `MMTensorIPC`; validate it
  requires `mm_ipc_gpu_memory_gb > 0`; docs.
- `vllm/v1/engine/core_client.py` — wire the sender for `cuda_ipc` (pool sized
  from config, `tp_size` from `parallel_config`).
- `vllm/v1/engine/core.py` — wire the provider for `cuda_ipc`.
- `vllm/multimodal/inputs.py` — worker-side: materialize deferred proxies in
  `reduce_data` before batching; skip `pin_memory` for on-device batches.
- `tests/v1/test_cuda_ipc_transport.py` (new) — unit + cross-process tests.

Device selection uses the `torch.accelerator` API (per RFC #30679), not
`torch.cuda`.

## Model evaluation / performance

All runs on Qwen3.5-35B-A3B, unique-per-request (all cache-miss), ViT attention
backend on a healthy path (`--mm-encoder-attn-backend TORCH_SDPA`), median TTFT
(ms) at concurrency=1. Comparing `cpu` (`direct_rpc` + CPU preprocessing),
`cpu+shm` (`torch_shm`-style host cache + CPU preprocessing), and `cuda_ipc`
(GPU preprocessing + on-device transport).

**TP=4, 2048x2048 images** (transport-unfriendly: a single huge image makes the
O(seq^2) ViT compute dominate, diluting the transport share):

| input | cpu (direct_rpc) | cpu+shm | cuda_ipc | vs cpu | vs shm |
|-------|------------------|---------|----------|--------|--------|
| 1 img | 982.9            | 727.9   | 547.1    | +44.3% | +24.8% |
| 4 img | 5860.2           | 4843.5  | 4267.3   | +27.2% | +11.9% |

**TP=8, transport-bound case** (largest benefit): high TP amplifies the baseline
broadcast (the tensor is copied to every worker over the host / PCIe, whereas
`cuda_ipc` keeps it on-device and each worker reads via NVLink P2P), and many
moderate-sized images make the `pixel_values` payload large while per-image ViT
attention stays cheap:

| input          | cpu (direct_rpc) | cpu+shm | cuda_ipc | vs cpu | vs shm |
|----------------|------------------|---------|----------|--------|--------|
| 8 x 1024x1024  | 1725.5           | 1048.5  | 709.6    | +58.9% | +32.3% |
| 16 x 512x512   | 750.7            | 439.0   | 275.0    | +63.4% | +37.4% |

`cuda_ipc` is most effective at low concurrency, where transport sits on the
critical path. In the transport-bound case it is **~2.4-2.7x faster than
`direct_rpc`** and **~1.5-1.6x faster than `cpu+shm`**; the gain shrinks toward
single digits when a single very large image makes ViT compute (not transport)
dominate TTFT. Output correctness is unchanged (opt-in, off by default).

## Notes

- Single-node only (requires shared GPUs / peer access); wider or multi-node TP
  falls back to the host transport.
- AI assistance was used in developing this change; every line was reviewed by
  the submitter.

## Unrelated finding (separate issue, not part of this PR)

On this build the default ViT attention backend (FLASH_ATTN/FA3) is ~10x slower
than TORCH_SDPA for Qwen3-VL vision (head_dim=72, a non-standard flash size):
single 2048x2048 image TTFT 6711ms (FA3) vs 640ms (SDPA). Worth a separate
issue.

- SangChengC · comment · 2026-07-23T08:56:10Z · [source](https://github.com/vllm-project/vllm/pull/49462#discussion_r3636799337)

File: `vllm/multimodal/cuda_ipc.py` · line None

Good idea, I checked — but they're not the same kind of pool, so reuse wouldn't actually help here.

MultiModalGPUMemoryPool is just a byte-counting semaphore for admission control: it doesn't own any device memory, it only blocks until there's enough budget before a caller allocates. It's also already in use by the GPU video-decode path (video.py calls acquire()).

The cuda_ipc sender needs the opposite — a real persistent torch.empty(..., device="cuda") buffer that it (a) sub-allocates into slices via a free list, (b) exports once as a CUDA IPC handle, and (c) recycles with lock-free per-consumer flags in shared memory. It's non-blocking too (falls back to the host path when full instead of waiting). The semaphore can't back any of that; the slab allocator + IPC export + cross-process recycling are the whole point and are orthogonal to byte-budget gating.
