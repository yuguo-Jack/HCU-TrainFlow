# [Core][Rust Frontend] Report structured-output compile failures as validation errors

[Upstream PR](https://github.com/vllm-project/vllm/pull/62872) · state: closed · merged: True

## Original PR description



## Overview

A structured-output constraint that EngineCore fails to compile finishes the request as `FINISHED_ERROR` with no error attached. The Python frontend rarely sees this, because it validates constraints with the backend library before submitting. The Rust frontend cannot, so its clients get HTTP 500 for an invalid regex or grammar, and an empty 200 when llguidance builds a matcher in an error state (for example a schema with `uniqueItems`). This PR reports compile failures with the `validation_error` code that #49625 introduced for backend mismatches, so both frontends return 400, and makes the guidance backend fail compilation instead of continuing with a broken matcher.

## Claims

- When a request's grammar fails to compile, its error output carries `RequestError(code="validation_error", message="Invalid structured outputs: <compile error>")`. Python already maps that code to `VLLMValidationError` (400) since #49625.
- The guidance backend raises on a matcher that reports an error (`Grammar error: ...`) instead of logging a warning and generating nothing.
- The Rust frontend maps `validation_error` to HTTP 400 (an SSE `BadRequestError` event when streaming) and gRPC `INVALID_ARGUMENT`. This also covers #49625's backend-mismatch rejection, which the Rust frontend reported as 500.
- Rust non-streaming `/inference/v1/generate` fails the request on every engine-typed error, as Python raises every `RequestError`; before, only retryable ones did.

## Details

**Root cause.** Grammar compilation runs asynchronously after `StructuredOutputManager.grammar_init`. Since #47312, a failed compilation finishes only that request, through `grammar_compile_error_reqs`, but without a `RequestError`, so every frontend reports an internal error. #49625 added `validation_error` for the separate case where a request names a backend other than the one the engine already uses; that check runs in `grammar_init`, before compilation, and does not cover a constraint that the right backend fails to compile. The guidance backend creates its `LLMatcher` without failing on a build error: `check_error()` only logs it, and the matcher allows nothing, so the request ends with empty output.

**Why `validation_error`.** It is the existing "the request itself is invalid" signal on `RequestError`, and Python's `to_exception` already maps it to 400; a compile failure of the request's own constraint is the same kind of error. Python's frontend validation already returns 400 for these constraints when it can check them, so this only changes requests that reach the engine unvalidated. The Rust side adds `RequestError::VALIDATION_ERROR` and `is_validation_error()` next to the existing `retryable` handling rather than an enum: `code` is an open string on the Python side, and no other code needs distinct Rust behavior.

**Not changed.**
- A streaming request still gets HTTP 200 with an SSE error event, as with Python, since compilation finishes after the response starts.
- xgrammar error messages include its log prefix (`[time] /project/cpp/...:line:`). Python's HTTP layer rewrites such paths with `sanitize_message`; the Rust frontend passes the message through.

**Not a duplicate.**
- #49625 (merged) rejects backend mismatches before compilation; this PR reports compilation failures with the same code.
- #45012 (open, inactive since 2026-08-19) handles failed grammar futures leaving requests blocked and reports them through the internal-error path (500); #47312 has since fixed the hang. This PR changes the status of those failures to 400.
- vllm-project/vllm#62456 (open) gives every Rust route one backend, which removes the mismatch case for the Rust frontend; the two PRs are independent.
