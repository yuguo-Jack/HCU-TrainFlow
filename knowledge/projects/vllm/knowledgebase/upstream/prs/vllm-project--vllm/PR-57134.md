# [ROCm][Bugfix] Support FP8 KV cache for NoPE sparse MLA

[Upstream PR](https://github.com/vllm-project/vllm/pull/57134) · state: open · merged: False

## Original PR description

## Summary

- route rope-free sparse MLA to the ROCm Triton implementation for every KV-cache dtype
- dequantize FP8 KV rows in the Triton ragged-prefill kernel using the layer KV scale while keeping Q in model dtype
- use 64-bit query-row offsets so wide, long-context prefills cannot overflow 32-bit pointer arithmetic
- preserve custom MLA geometry and FP8 cache dtype in the attention benchmark harness

## Problem

AITER precompiled sparse MLA kernels assume the DeepSeek cache-row geometry: 512 latent elements plus 64 RoPE elements. GLM-5.3-Flash is rope-free and stores a 512-element row. FP8 NoPE requests currently reach the AITER path, whose 576-element assumption can read past the cache row and cause a ROCm GPU memory fault.

The existing Triton ragged path already handles the NoPE geometry. This change makes its routing geometry-based instead of BF16-only, adds scaled FP8 KV dequantization, and avoids FP8-quantizing Q for that path.

## Duplicate-work check

No open PR found addresses ROCm NoPE FP8 sparse-attention KV rows. #39168 overlaps the ROCm ops file but changes the separate FP8 indexer-cache MQA path; the open GLM-5.3 NoPE FP8 PRs target NVIDIA backends. The previously bundled SharedTopkIndicesBuffer no-op was dropped because #57252 already landed ROCMAiterMLASparseImpl.record_logical_topk_ready().

## GSM8K

Same recipe as other GLM-5.3-Flash PRs (#57590, #56960, #56176, #55738, #54925): EleutherAI `lm_eval` against `/v1/completions`, 5-shot, greedy. Not chat completions.

```
VLLM_ROCM_USE_AITER=1 vllm serve .../GLM-5.3-Flash \
    --tensor-parallel-size 4 --kv-cache-dtype fp8_e4m3 \
    --attention-backend ROCM_AITER_MLA_SPARSE --max-num-seqs 64

lm_eval --model local-completions \
  --model_args model=glm53,base_url=http://127.0.0.1:9610/v1/completions,tokenizer=.../GLM-5.3-Flash,num_concurrent=64,tokenized_requests=False \
  --tasks gsm8k --num_fewshot 5 --batch_size 1 --gen_kwargs temperature=0 --seed 12345
```

`gen_kwargs`: `until=['Question:', '</s>', '<|im_end|>']`, `do_sample=False`, `temperature=0` (lm_eval gsm8k.yaml defaults). Full 1,319 questions. No GPU faults.

**Question**: Is it expected that the perf is unaffected (and worse for 8k/1k conc 16) when using fp8 kv? I'd expect TPOT to improve since we should be able to load the KV faster in fp8, or is the dequant overhead offsetting this?

- amd-dlimpus · comment · 2026-10-15T17:22:25Z · [source](https://github.com/vllm-project/vllm/pull/57134#issuecomment-6198070631)

> Is it expected that the perf is unaffected (and worse for 8k/1k conc 16) when using fp8 kv? I'd expect TPOT to improve since we should be able to load the KV faster in fp8, or is the dequant overhead offsetting this?

@simondanielsson Yes, for this model that's expected, and it isn't dequant overhead. FP8 does make the attention kernel faster; attention is just a small share of a GLM-5.3-Flash decode step:

- Sparse top-k caps each query at 2,048 KV rows regardless of context length. The 512-wide latent is shared by every head (MQA), so a decode token reads about 2 MB of KV per layer in BF16 and 1 MB in FP8. That doesn't grow with the 8k context.
- Split-K decode kernel on MI355X, TP=4 per-rank shapes (16 heads, top-k 2,048):

| decode tokens per rank | BF16 µs | FP8 µs | FP8 / BF16 |
|---|---|---|---|
| 1 | 27.7 | 27.6 | 0.99 |
| 8 | 26.5 | 27.7 | 1.05 |
| 16 | 31.3 | 26.8 | 0.86 |
| 32 | 45.5 | 34.2 | 0.75 |

- Across 45 layers, the best case is about 0.2 ms of the 15.8 ms TPOT at c=16 (about 1%) and 0.5 ms of 20.4 ms at c=32 (about 2.5%). At c=1–8 the kernel is latency-bound, so FP8 doesn't help. The measured TPOT gain was 0.2–0.3%, so not all of the kernel-level gain shows up end to end. I haven't profiled where the rest goes, so I won't claim more than that.
- The c=16 "worse" number is TTFT, not TPOT. It comes from prefill queueing; see the per-repetition values under the table in the description.

The main benefit of FP8 KV here is capacity: half the KV memory per token, so roughly twice the cached tokens or concurrency for the same memory.
