# [ROCm][Bugfix] Support FP8 KV cache for NoPE sparse MLA

[Upstream PR](https://github.com/vllm-project/vllm/pull/57134) · state: open · merged: False

## Original PR description

## Summary

- Route rope-free (NoPE) sparse MLA to the ROCm Triton kernels for every KV-cache dtype. Routing now depends only on geometry (`head_size == kv_lora_rank`) and workload, not on `kv_cache_dtype`.
- Add per-tensor-scaled FP8 KV support to both Triton kernels: the ragged prefill kernel, and the split-K decode kernel from #58584. KV is upcast through BF16 in registers. K and V are the same latent row, so the scale is folded in once into the QK scale and once into the accumulator, never per tile.
- Keep Q in model dtype on the Triton route. The AITER asm route and the `VLLM_ROCM_USE_AITER_TRITON_SPARSE_MLA` opt-in still quantize Q to FP8.
- Use 64-bit query-row offsets in the ragged prefill kernel, so wide, long-context prefills cannot overflow 32-bit pointer arithmetic.
- Preserve custom MLA geometry and the FP8 cache dtype in the attention benchmark harness.

## Problem

AITER's precompiled sparse MLA kernels assume the DeepSeek cache-row geometry: 512 latent elements plus 64 RoPE elements. GLM-5.3-Flash is rope-free and stores a 512-element row. On main, FP8 NoPE requests reach the AITER path, whose 576-element assumption can read past the cache row and cause a ROCm GPU memory fault, so GLM-5.3-Flash cannot serve with `--kv-cache-dtype fp8`.

The Triton ragged and split-K paths already handle the NoPE geometry for BF16. This PR makes their routing geometry-based, adds scaled FP8 KV dequantization, and skips FP8-quantizing Q on that path.

## Duplicate-work check

No open PR addresses ROCm NoPE FP8 sparse-attention KV rows. #39168 overlaps the ROCm ops file but changes the separate FP8 indexer-cache MQA path, and the open GLM-5.3 NoPE FP8 PRs target NVIDIA backends. This PR reuses #58584's split-K decode kernel instead of adding its own.

## Serving performance (BF16 KV vs FP8 KV)

Measured at head `291fe72f80`, before the ragged-prefill scale folding, which only touches prefill. Both arms used the same build, so FP8 and BF16 decode both go through the split-K kernel. Main cannot boot FP8 NoPE, so the baseline is BF16 KV.

`vllm bench serve` random dataset, same recipe as #57590 and #57979: `--backend vllm --dataset-name random --random-input-len 8000 --random-output-len 1000 --random-range-ratio 0 --ignore-eos --seed 5678 --num-prompts $((8*CONC)) --num-warmups $CONC`. TP=4 on MI355X, `--max-model-len 16384 --max-num-seqs 64 --max-num-batched-tokens 16384 --no-enable-prefix-caching`. Each point is the median of 3 runs. 2,736/2,736 requests succeeded.

| ISL/OSL | conc | BF16 TPOT ms | FP8 TPOT ms | TPOT Δ | BF16 tok/s | FP8 tok/s | tok/s Δ | BF16 TTFT ms | FP8 TTFT ms | TTFT Δ |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 8000/1000 | 1 | 8.75 | 8.76 | +0.2% | 111.0 | 110.9 | -0.1% | 262 | 261 | -0.5% |
| 8000/1000 | 8 | 11.36 | 11.33 | -0.3% | 639.2 | 640.4 | +0.2% | 1159 | 1160 | +0.1% |
| 8000/1000 | 16 | 15.78 | 15.74 | -0.2% | 919.8 | 918.9 | -0.1% | 1632 | 1831 | +12.2% |
| 8000/1000 | 32 | 20.41 | 20.35 | -0.3% | 1444.7 | 1446.8 | +0.1% | 1849 | 1860 | +0.6% |

FP8 TPOT and throughput are within 0.3% of BF16 at every concurrency. Attention is a small share of a GLM-5.3-Flash decode step, as explained in [this comment](https://github.com/vllm-project/vllm/pull/57134#issuecomment-6198070631). The c=16 TTFT delta comes from prefill queueing: 16 concurrent 8k prompts fill the 16k-token prefill budget about two at a time, and both arms hit both values across repeats. The main benefit here is capacity: FP8 halves the KV memory per token.

@simondanielsson Yes, for this model that's expected, and it isn't dequant overhead. FP8 does make the attention kernel faster; attention is just a small share of a GLM-5.3-Flash decode step:

- Sparse top-k caps each query at 2,048 KV rows regardless of context length. The 512-wide latent is shared by every head (MQA), so a decode token reads about 2 MB of KV per layer in BF16 and 1 MB in FP8. That doesn't grow with the 8k context.
- Split-K decode kernel on MI355X, TP=4 per-rank shapes (16 heads, top-k 2,048):

| decode tokens per rank | BF16 µs | FP8 µs | FP8 / BF16 |
|---|---|---|---|
| 1 | 27.7 | 27.6 | 0.99 |
| 8 | 26.5 | 27.7 | 1.05 |
| 16 | 31.3 | 26.8 | 0.86 |
| 32 | 45.5 | 34.2 | 0.75 |

- Across 45 layers, the best case is about 0.2 ms of the 15.8 ms TPOT at c=16 (about 1%) and 0.5 ms of 20.4 ms at c=32 (about 2.5%). At c=1–8 the kernel is latency-bound, so FP8 doesn't help. The measured TPOT gain was 0.2–0.3%, so not all of the kernel-level gain shows up end to end. I haven't profiled where the rest goes, so I won't claim more than that.
- The c=16 "worse" number is TTFT, not TPOT. It comes from prefill queueing; see the per-repetition values under the table in the description.

The main benefit of FP8 KV here is capacity: half the KV memory per token, so roughly twice the cached tokens or concurrency for the same memory.

Two things changed in `_use_rocm_sparse_triton`, and the parametrize list follows them.

- **`kv_cache_dtype` is gone:** FP8 KV no longer excludes the Triton path, and that is the bug this PR fixes. With GLM's 512-wide NoPE row, FP8 KV used to fall through to AITER's precompiled kernels, which assume a 576-element row (512 latent + 64 RoPE) and cannot serve it. The Triton kernels now dequantize FP8 KV in registers, so routing depends only on head size and workload. The old `("fp8", 512, ..., False)` row would now assert the wrong answer. FP8 dispatch is covered by `test_forward_mqa_fp8_kv_query_contract`, which checks that Q stays in model dtype, that `kv_scale` reaches the Triton wrapper, and that the asm and AITER sparse MLA routes still quantize Q.
- **`num_decode_tokens` and `max_query_len` are gone:** the function body never read them on main, so 2a8695876 dropped them. The two MTP rows (`num_decode_tokens=4, max_query_len=2` and `12, 6`) passed the same effective inputs as the plain-decode row, so they collapse into `(512, 0, 2, True)`.
