# [Attention] Decode FlashInfer spec queries with fa2 on SM90 NVFP4

[Upstream PR](https://github.com/vllm-project/vllm/pull/63143) · state: open · merged: False

## Original PR description



## Overview

Follow-up to #60532. On SM90 an NVFP4 KV cache already decodes with FlashInfer's fa2 tensor-core decode, because XQA reads NVFP4 only on SM12x. #60532 sends uniform spec-decode queries through that decode only below SM90, so SM90 with NVFP4 still splits verification steps off as prefills and reports `UNIFORM_SINGLE_TOKEN_DECODE`. This applies the same fa2 path there.

## Claims

- With an NVFP4 KV cache on SM90, FlashInfer spec decode runs its verification steps in full CUDA graphs. With Qwen3.8-27B NVFP4 and MTP (3 tokens), decode goes from 97.3 to 130.4 tok/s at TP=1.
- Other KV cache dtypes on SM90, and every other architecture, keep their decode selection and graph support.

## Validation

`test_flashinfer_nvfp4_decode_correctness` now also runs on SM90. It decodes single-token and 4-token queries over an NVFP4 cache, eager and under CUDA graph replay, against the fa2 prefill that wrote the cache, and checks that 4-token queries are planned with `q_len_per_req=4`.

On SM80, where nothing changes, with the FlashInfer 0.7.2 release wheel that vLLM pins: `pytest tests/v1/attention/test_attention_backends.py tests/v1/attention/test_flashinfer_dcp_spec_reorder.py -k "flashinfer or FLASHINFER"` gives 35 passed, 5 skipped.

On SM90, Qwen3.8-27B NVFP4 weights, NVFP4 KV cache, TP=1, batch 1, MTP with 3 tokens: 97.3 tok/s on `main` (`PIECEWISE`) and 130.4 tok/s with this PR (decode `FULL`).

## Details

- `_use_fa2_native_decode()` takes the cache's NVFP4 flag and is true on SM90 when the cache is NVFP4. The builder passes `is_kvcache_nvfp4`, so `supports_spec_as_decode` and the explicit `backend="fa2"` decode wrapper from #60532 follow.
- `get_cudagraph_support` takes the fa2 branch when every attention spec decodes with fa2. Otherwise the existing XQA checks apply unchanged, and they already report `UNIFORM_SINGLE_TOKEN_DECODE` for an NVFP4 spec on SM90.
- `get_varlen_cudagraph_max_query_len` is unchanged: on SM90 the decode kernel is XQA, never trtllm-gen, so the bound is already `None`.
