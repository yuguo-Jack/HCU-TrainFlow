# [Bugfix] Honor FP32 precision in batch-invariant matmul

[Upstream PR](https://github.com/vllm-project/vllm/pull/55466) · state: open · merged: False

## Original PR description

## Purpose

Batch-invariant mode explicitly selects IEEE FP32 precision in `init_batch_invariance()`, but the pointer-based persistent matmul and BMM kernels leave `tl.dot` at its default input precision. On NVIDIA, [that default is TF32](https://triton-lang.org/main/python-api/generated/triton.language.dot.html), independently of PyTorch's matmul precision setting. This can truncate FP32 inputs and produce errors that the existing FP16/BF16 tests do not catch.

Set `input_precision="ieee"` at both dot sites and extend the existing matmul suite with FP32 correctness and batch-invariance coverage. The correctness cases include strided/transposed RHS layouts and a long, narrow routing-projection shape; their reference is CPU FP64 rounded to FP32, independent of GPU TF32 settings. The bitwise batch-invariance test covers both MM and BMM: for a batched RHS, the same pair of operands is moved from a singleton batch into a larger random batch. Existing FP16/BF16 tolerances are retained.

This addresses the **FP32 precision part** of #55131. It does not claim to resolve every batch-invariance concern in that issue. The XPU descriptor matmul is unchanged; the shared BMM change has only been validated on CUDA.

Duplicate-work check: reviewed #55131 and its comments, searched open PRs for `55131 in:body`, `batch invariant TF32`, and `batch-invariant fp32`. No open PR addressing these two FP32 dot sites was found. Related #54503 and #49131 address shape/configuration selection, rather than explicit FP32 input precision.

AI assistance: Codex assisted with diagnosis, implementation, regression tests, and local validation.
