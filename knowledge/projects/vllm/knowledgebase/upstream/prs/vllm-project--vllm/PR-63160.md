# [Feature] Add request-level prefill progress to gRPC streaming

[Upstream PR](https://github.com/vllm-project/vllm/pull/63160) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Expose optional, request-level prefill work snapshots on the Rust gRPC `GenerateStream`, allowing routing clients to update in-flight work while prefill runs.

Closes #63140. Related: Router [colocated #444](https://github.com/vllm-project/router/pull/444), [P/D #469](https://github.com/vllm-project/router/pull/469), and [design RFC #294](https://github.com/vllm-project/router/issues/294).

[#40371](https://github.com/vllm-project/vllm/pull/40371) exposes prompt progress to Python OpenAI streaming clients; this PR adds a Rust gRPC signal for routing consumers.

## Claims

- `GetServerInfo.supports_prefill_progress` advertises support. A client opts in with `GenerateRequest.include_prefill_progress`; progress arrives separately from generated output as sequenced `GenerateResponse.prefill_progress` snapshots. New snapshots replace the previous remaining-work estimate.
- Snapshots report remaining prompt work and cache accounting. An initial queued snapshot can have `cache_accounting_final=false`, because prefix reuse has not yet been reconciled. Pending remote KV is not credited until usable; remaining work can increase after preemption or recomputation.
- The scheduler throttles ordinary decreases and targets a one-second refresh while it is active. The engine keeps one pending pure-progress snapshot per request; newer progress may replace older progress without dropping ordinary output, metadata, or finish events.
- The flag defaults to false. Unsupported workers can be detected through capability discovery; unary `Generate` rejects the opt-in. See [usage and examples](https://github.com/KaisennHu/vllm/blob/d16847dafe120afd3ca7e90311e71c3f2ae665f9/docs/serving/prefill_progress.md).

### Downstream performance: preliminary C4

One off/on pair with Router #444 `cf5bc54`, this PR `d16847d`, Qwen3-4B BF16, four colocated B300 workers, and an [AgentX-style replay](https://github.com/openJiuwen-ai/agent-infer/blob/main/docs/zh/how-to/run-trace-replay.md) of 32 sessions / 730 requests derived from [WekaTrace](https://huggingface.co/datasets/semianalysisai/cc-traces-weka-062126/tree/23f152f6f0f9399a85901b89a6458def0ef16729):

| Off → on | Worker prefill mean | Client TTFT mean | Total token/s | Session JCT mean |
| --- | ---: | ---: | ---: | ---: |
| C4 | 178.71 → 176.17 ms **(−1.42%)** | 198.88 → 196.05 ms **(−1.42%)** | 80,134 → 80,665 **(+0.66%)** | 86.27 → 86.15 s **(−0.14%)** |

Output throughput was 775.57 → 780.71 token/s (+0.66%). Cache hit rate (93.03%) and newly computed prompt tokens (3,943,216) were unchanged. Other GPUs were active on the shared host. This single pair evaluates the combined Router/worker system; it does not establish a stable gain or its cause. Higher concurrency and repeats are in progress.

## Details and limits

Remaining tokens are a work estimate, not a latency prediction. Refresh depends on scheduler activity, and receipt time does not establish sample age. The single progress slot bounds additional pure-progress buffering, not the existing lossless model-output FIFO. Consumers must handle stale updates and clean up on completion, error, or cancellation.
