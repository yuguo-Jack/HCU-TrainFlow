# [Perf][MoE] Skip the token-count load on the low-latency fused-MoE path

[Upstream PR](https://github.com/vllm-project/vllm/pull/64978) · state: open · merged: False

## Original PR description



## Overview

The Triton fused MoE has a low-latency path for small batches (`num_tokens * top_k * 4 <= num_experts`, #29354 / #39016): it skips `moe_align_block_size` and launches exactly one program per (token, expert) pair. On that path the `num_tokens_post_padded` early exit in `fused_moe_kernel` can never fire (the grid is exact), yet `_prepare_expert_assignment` still materialized the count with `torch.full` on every call. Under CUDA graphs that fill is captured and replays as a ~1.9 us `FillFunctor<int>` kernel on the MoE stream, right before the first `fused_moe_kernel`, in every MoE layer of every decode step.

This PR makes `fused_moe_kernel` skip the load on the low-latency path (its `naive_block_assignment` constexpr already selects the token mapping; the LoRA MoE kernels already guard the load the same way) and has `_prepare_expert_assignment` hand it a one-element view of the ids in place of the count. No fill kernel, no new allocation, and the helper stays traceable: `fused_mova_impl` (K2-Horizon) calls it directly under `torch.compile`, so a Python-side cache keyed by the token count would have specialized on the batch size.

## Claims

- **Trace, `Qwen/Qwen3.6-35B-A3B-FP8` on H200 TP=1, one request:** 40 `FillFunctor<int>` kernels per decode step removed (1194 -> 1154 kernels/step), 1.7-1.9 us each plus the launch gap, all on the MoE stream, which is the critical stream of the layer at this batch size (the shared expert on the main stream finishes earlier).
- **E2E, same model:** median TPOT -2.8% at one request (3.880 -> 3.775 ms), -0.9% at 2, -1.3% at 4, -1.2% at 8 (the path applies up to 8 tokens for this model: 256 experts, top-8).
- **E2E, `Qwen/Qwen3-30B-A3B-FP8` (128 experts, top-8: path applies up to 4 tokens):** -1.3% at 1 request, -1.1% at 2, -0.6% at 4; 8 requests (aligned path, unchanged code) within noise.
- **Applies to** any model on the Triton fused-MoE path at `num_tokens <= num_experts / (4 * top_k)` (e.g. 8 tokens for 256 experts / top-8, 4 for 128 experts / top-8), i.e. the latency-bound decode regime. Nothing changes above that bound (the aligned path is untouched) or for other MoE backends.

### Tests

`tests/kernels/moe/test_moe.py::test_naive_block_assignment_fills_no_token_count` (new, CPU) checks the low-latency path returns `sorted_token_ids=None`, the ids buffer as `expert_ids`, and a `(1,)` placeholder that aliases the ids (no fill). The existing `test_fused_moe` cases at small M exercise the kernel on this path. `tests/kernels/moe/test_moe.py` on H200 (nightly image with this branch's file applied): 1000 passed, 127 skipped for the first version; the launcher, low-latency and `test_fused_moe` subsets re-run on the final version (33 passed).

## Details

- **Why the kernel side.** The aligned path still reads the count (it decides how many padded blocks the grid covers); the low-latency path's grid is `num_tokens * top_k` programs along M, so the check is dead there. The `gptq_awq` kernel keeps its load: it only runs with a block shape, which the low-latency condition excludes.
- **The placeholder.** The Python side returns `topk_ids.view(-1)[:1]` where the count used to be: a view, no kernel, an int32 tensor of shape `(1,)` like before for callers that look at the shape. Nothing reads it on this path.
- **CUDA graphs and compile.** Nothing is created at call time, so there is no first-call difference between warmup and capture, and no tensor cache to poison under `FakeTensorMode` or to specialize on under Dynamo.
- The aligned path is unchanged: there the count comes out of `moe_align_block_size`.
