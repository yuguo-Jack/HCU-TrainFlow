# [Rust Frontend] Support n > 1 choices

[Upstream PR](https://github.com/vllm-project/vllm/pull/65625) · state: open · merged: False

## Original PR description



## Overview

Support `n > 1` on `/v1/chat/completions` and `/v1/completions` in the Rust frontend, following Python's parallel sampling: render and tokenize the prompt once, then submit one engine request per sample. Today the Rust frontend rejects any `n > 1` with `400 Only n=1 is supported.`

Supersedes inactive vllm-project/vllm#58914, which fans out by calling `chat()`/`generate()` `n` times in the server and so renders the prompt (multimodal processing included) `n` times.

## Claims

- Chat and completions accept `n > 1`, streaming and non-streaming. Each choice carries its `index`; usage counts the prompt once and sums completion and reasoning tokens across choices.
- Like Python's `ParentRequest`, the prompt is rendered once, child requests use IDs `{index}_{request_id}` and `seed + index` when seeded, and the caller's external request ID stays on every child, so an abort or a client disconnect reaches every sample.
- `n` is validated like Python's `SamplingParams`: at least 1, at most `VLLM_MAX_N_SEQUENCES` (16384 by default; the chat DTO's old cap of 10 is gone), and 1 under greedy sampling, with Python's error messages.
- Metrics follow Python: `vllm:request_params_n` and `vllm:request_max_num_generation_tokens` are observed once per request, the other request histograms per sample, and per-request metrics in the response only for `n = 1`.
- `n = 1` takes the same path and is unchanged on the wire. `/inference/v1/generate` and gRPC still accept only `n = 1`; the render routes forward `n` into the rendered generate request, so `n > 1` keeps failing there explicitly instead of being dropped.

## Details

The fan-out happens where Python does it, and each layer above returns one stream per sample instead of pushing a choice index through every stream type:

- `vllm-llm`: `Llm::generate_n(request, n)` submits the `n` child engine requests like `ParentRequest`. Seeds wrap on overflow, and `-1`, Python's unseeded sentinel, stays `-1` on every child (Python normalizes it to `None` before the fan-out). A shared `ParallelSamplingStats` observes the request-level histograms once, when the last child finishes (max over the children). `n = 1` submits the request unchanged; `generate` is `generate_n(.., 1)`.
- `vllm-text`: `TextLlm::generate_n` lowers once and decodes each child stream. It owns the greedy rule, checked against the resolved temperature (after generation-config defaults). Python first raises a positive temperature below 0.01 to 0.01, so only `temperature = 0` is greedy. Submission goes through the existing `submit` step, which now takes `n`, so the `--skip-tokenizer-init` structured-output check covers every sample.
- `vllm-chat`: `ChatLlm::chat_n` renders once and builds one output processor per sample, since parsers are stateful; the output grammar is built once and applied to the shared request.
- `vllm-server`: the routes resolve `n` like Python's `_verify_num_sequences`, run the existing per-choice chunk stream or collector for each sample, and merge. Streamed chunks interleave as the samples produce them, stamped with their choice index; the per-choice final usage chunks fold into one (`Usage::add_choice`); non-streaming responses append the choices in index order, with prompt-level fields from the first choice.
- `VLLM_MAX_N_SEQUENCES` is read once at startup through a hidden `--max-n-sequences` argument bound to the env var (and to the `--args-json` env fallbacks), parsed like Python's `int()`, and carried in `ApiServerOptions` and `RenderConfig`. An invalid value fails startup, where Python fails each request.

Ownership and layering: the fan-out (IDs, seeds, request-level metrics) sits in `vllm-llm`, the engine-client facade that mirrors `AsyncLLM`; the greedy rule in `vllm-text`, which owns `SamplingParams` semantics; per-sample parsing in `vllm-chat`; wire DTO checks and response merging in `vllm-server`. `n` is passed as an argument rather than added to the shared request types, since only the fan-out and the greedy rule read it. The `n` range check stays in request lowering, which is configuration-free and shared with the render routes, separate from the configured upper limit.

Behavior notes:

- Chunk order across choices follows arrival; Python sends every choice's role chunk before any content chunk. Clients key on `index`, so this is not a wire contract.

Not a duplicate: the only open PR implementing `n` in the Rust frontend is vllm-project/vllm#58914, inactive since 2026-10-12 and built on a different design (see Overview); searched open PRs for `n choices`, `parallel sampling`, `n > 1` and `Only n=1`. The open beam-search PRs (vllm-project/vllm#47705, vllm-project/vllm#64862) cover a different feature.
