# [Perf][MoE] Size the DeepGEMM MegaMoE symmetric buffer for one sequence-parallel shard

[Upstream PR](https://github.com/vllm-project/vllm/pull/63541) · state: closed · merged: True

## Original PR description

## Overview

With `--moe-backend deep_gemm_mega_moe`, `--enable-expert-parallel`, TP > 1 and PP = 1, Kimi K3 runs its MoE layers sequence parallel: each rank feeds MegaMoE at most `cdiv(max_num_batched_tokens, tp_size)` tokens. The MegaMoE symmetric buffer is still sized for `max_num_batched_tokens` tokens per rank. This PR sizes it for the shard.

## Claims

- Kimi K3, `-tp 8 --enable-expert-parallel`, `--max-num-batched-tokens 16384`: MegaMoE buffer per GPU **10.73 GiB → 2.50 GiB**.
- MegaMoE outputs do not depend on the buffer size (bitwise equal in a one-off check).

## Validation

**Buffer per GPU** (one buffer shared by all MoE layers), allocated on GB300 by the vendored DeepGEMM with the arguments `KimiMoE` passes: 896 experts, top-k 16, `routed_expert_hidden_size` 3584, intermediate 3072, `fp8xfp4`, `situ`, no fused shared experts. EP = TP, DP = 1; TP8 ran on two 4-GPU nodes.

| TP = EP | `--max-num-batched-tokens` | main | this PR |
|---|---|---|---|
| 8 | 16384 | 10.73 GiB | 2.50 GiB |
| 8 | 32768 | 21.29 GiB | 3.68 GiB |
| 4 | 8192 | 3.74 GiB | 1.66 GiB |
| 4 | 16384 | 6.52 GiB | 2.34 GiB |
| 4 | 32768 | 12.80 GiB | 3.74 GiB |

DeepGEMM rounds the per-rank token bound up to a multiple of 1920 before sizing (the TP8 shard of 2048 tokens is sized for 3840).

- `pre-commit`: pass.

## Details

- **Why it is safe:** DeepGEMM sizes every region from `num_max_tokens_per_rank`. Its expert ring assumes every EP rank sends its full `num_max_tokens_per_rank`, so routing imbalance fits. With sequence parallelism each rank's MoE input is its shard, at most `cdiv(max_num_batched_tokens, tp_size)` rows at any DP size. The DeepGEMM warmup already uses this bound, and `forward()` raises above it.
- **Why outputs match:** DeepGEMM picks `BLOCK_M` from the token count, not from the buffer capacity.
- **Scope:** `DeepGemmMegaMoEExperts` gets an optional `max_num_tokens` (default unchanged); only `KimiMoE` passes the shard bound. DeepSeek-V4 has the same sequence-parallel MegaMoE path and is left for a follow-up.
- **Not validated end-to-end yet:** no `vllm serve` run of Kimi K3 with this change, and no KV-cache measurement.
- **Not a duplicate:** no open PR changes the token bound of this buffer. Draft #53556 adds fused shared-expert space to the same buffer. #54347 enables Kimi K3 sequence parallelism with PP, where this bound also holds.
