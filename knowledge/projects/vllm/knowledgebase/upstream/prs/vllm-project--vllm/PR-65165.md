# [Quantization] Extend int8_per_channel_weight_only to LinearBase.

[Upstream PR](https://github.com/vllm-project/vllm/pull/65165) · state: open · merged: False

## Original PR description



## Overview
Online INT8 quantization today covers routed experts only: `--quantization int8_per_channel_weight_only` leaves every `LinearBase` in BF16. This PR adds the missing online per-channel INT8 linear method, so the same flag also quantizes dense linear layers through the int8 scaled-mm kernels that already serve compressed-tensors W8A8 INT8 checkpoints.
No new shorthand, no kernel changes, no default changes. Closes the "linear half" gap left by #38463 (which consolidated `experts_int8` into the online framework, MoE only) after #39187 moved the MoE side to W8A8.
## Claims
- `--quantization int8_per_channel_weight_only` now quantizes `LinearBase` weights to INT8 per output channel at load time; activations are quantized per token to INT8 inside the kernel (W8A8). The resulting `weight` / `weight_scale` layout is the one a compressed-tensors W8A8 INT8 checkpoint produces, so the runtime path is the same one already validated for that checkpoint format.
- Because the method goes through `OnlineRequantizationMixin`, partially pre-quantized checkpoints (NVFP4 / MXFP8 modelopt, compressed-tensors, quark) can be re-quantized to INT8 online with no extra code.
- MoE behaviour, defaults, kernels and the `quantization_config` schema are unchanged: this adds one dispatch-table entry and one `linear=` field to an entry that previously had none.

## Details
### Motivation
- **A100/Ampere has no FP8 dense path.** `cutlass_scaled_mm` dispatches SM89+ to the FP8 kernels and falls back to the int8-only CUTLASS 2.x kernels for SM75–SM87 (`csrc/quantization/w8a8/cutlass/scaled_mm_entry.cu`, `scaled_mm_c2x_sm80_dispatch.cuh`). On SM80, INT8 W8A8 is the native online dense scheme; `fp8_per_channel` is not an alternative there.
- **The MoE-only scope was provenance, not design.** The scheme came from `experts_int8` (#32689 tracked its removal, which ended in consolidation rather than deletion), which quantized expert weights only and returned `UnquantizedLinearMethod` for `LinearBase`. #38463 consolidated it into `online/*` and deliberately named the new shorthand `int8_per_channel_weight_only` ("weight-only per-channel quantization for MoE expert weights") — accurate at the time, since that path used `int8_w8a16_moe_quant_config` (W8A16). #39187 later moved the MoE side onto the shared int8 oracle with `activation_key=kInt8DynamicTokenSym`, i.e. W8A8, so the `_weight_only` suffix has been stale since then. No issue or PR ever asked for INT8 linear, and it is not on the online-quantization roadmap (RFC #52167).
- **No new kernel was needed.** `init_int8_linear_kernel` / `Int8ScaledMMLinearKernel` already existed for checkpoint formats; this PR wires the online front-end to them.
### Implementation
- `online/int8.py`: `Int8OnlineLinearMethod` (`OnlineLinearBase` subclass) — `create_weights` keeps the BF16/FP16 meta parameter that layerwise loading materializes, `process_weights_after_loading` quantizes per output channel, `apply` delegates to the int8 scaled-mm kernel.
- `online/linear_base.py` (new): `OnlineLinearBase` + `_is_tp_sharded` moved verbatim out of `online/fp8.py` so both FP8 and INT8 methods share them (`fp8.py` re-exports the names, so existing imports keep working). `fp8.py` is −86 lines, no behaviour change.
- `online/base.py`: one entry, `kInt8StaticChannelSym: Int8OnlineLinearMethod` in `_ONLINE_LINEAR_METHODS` (the MoE entry is untouched).
- `config/quantization.py`: `int8_per_channel_weight_only` gains `linear=QuantSpec(weight=kInt8StaticChannelSym)`; the comment records the W8A16→W8A8 naming history so the suffix does not get re-litigated. `experts_int8`'s docstring is fixed — it pointed at `--quantization int8_per_channel`, a name that never existed.
- Numerics mirror the runtime activation quantization in `csrc/quantization/w8a8/int8/scaled_quant.cu`: scale is `amax / 127`, codes are `round(weight · (127 / amax))` with round-half-even, saturated to `[-128, 127]`. An all-zero output channel gets a neutral scale of 1.0 and all-zero codes, so it reconstructs exactly.
- Two lifecycle details that are easy to get wrong: `weight_scale` is registered lazily in `process_weights_after_loading` (registering a tensor the checkpoint does not have in `create_weights` breaks layerwise `load_numel` accounting, so the layer would never be quantized), and the per-channel `amax` is all-reduced over TP only for row-parallel layers (`_is_tp_sharded(..., reduces_output_dim=False)`), since per-output-channel scales do not reduce over the sharded dim on column-parallel layers.
### Tradeoffs and limitations
- **This is a behaviour change for the existing flag** and the only real design cost of reusing the name:
  | | before | after |
  | --- | --- | --- |
  | `LinearBase` layers | BF16/FP16 | INT8 W8A8 per-channel |
  | routed experts | INT8 W8A8 | unchanged |
  Users who want MoE-only can keep `--quantization experts_int8` (unchanged, still leaves linear unquantized) or exclude layers with `--quantization-config.ignore`. It also propagates to OOT configs: `vllm-ascend`'s `AscendOnlineQuantizationConfig` will now receive `args.linear` for this flag, which is why the release note matters more than usual here.
- **The name is historical.** `int8_per_channel_weight_only` is W8A8, not weight-only. Renaming belongs in a separate deprecation PR (via `DEPRECATED_QUANTIZATION_METHODS`, the mechanism used for `fbgemm_fp8` / `fp_quant`), not here.
- **No padding fallback on the int8 path.** `cutlass_scaled_mm` requires 16-byte-aligned leading dimensions, i.e. `K % 16 == 0` and `N % 16 == 0` for the weight; the FP8 kernel has an unaligned padding path (`UNALIGNED_MNK_FACTORS` in `tests/kernels/quantization/test_cutlass_scaled_mm.py`), INT8 does not. This matches the existing compressed-tensors W8A8 INT8 constraint; layers with e.g. 3420/6840 dims need `ignore`/`targets`.
- **No batch-invariant path.** FP8 online falls back to BF16 dequant under `VLLM_BATCH_INVARIANT`; there is no int8 equivalent, so int8 output is not bitwise batch-invariant. Out of scope here.
- **ROCm/XPU:** both keep a `supported_quantization` allow-list that does not contain this flag name (pre-existing), so the shorthand remains CUDA-only until those lists are updated.
- **Ordering with in-flight PRs:** this deliberately uses the current boolean `init_int8_linear_kernel(is_channelwise=..., is_static_input_scheme=...)` signature. #63504 converts `Int8ScaledMMLinearLayerConfig` to QuantKeys; whichever lands second changes one call site. #51808 (activation-quant key override) is not needed by this method, which pins dynamic per-token activations internally.
