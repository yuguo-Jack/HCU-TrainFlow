# [Perf][MoE] Let GateLinear's low-latency router GEMM serve bf16-output routers

[Upstream PR](https://github.com/vllm-project/vllm/pull/64905) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

`GateLinear` tier 1 (`ll_bf16_gemm`, the CuTe DSL low-latency router GEMM for `M <= 16` on SM90+) was gated on `out_dtype == torch.float32`. Routers that keep bf16 logits, i.e. every `GateLinear(hidden_size, num_experts)` built without an `out_dtype` (Qwen2-MoE, Qwen3-MoE, Qwen3-Next, Qwen3.5 / 3.6 MoE), therefore skipped every specialized tier and ran the decode router GEMV through `F.linear` -> cuBLAS.

#62042 gave `ll_bf16_gemm` a bf16 epilogue (`output_dtype=torch.bfloat16`, fp32 accumulation unchanged). This PR lets tier 1 use it:

- `GateLinear.ll_bf16_out_dtype` resolves once what tier 1 writes: the requested `out_dtype`, or bf16 (the activation dtype, i.e. the `ReplicatedLinear` default) when none was requested. `allow_ll_bf16_gemm` accepts fp32 and bf16 there, and `forward` passes it to the kernel.
- Kernel warmup (`_warmup_ll_bf16_router_gemm`) groups the model's router shapes by that dtype and compiles for it, and also compiles the PDL weight-prefetch instance that `ll_bf16_gemm` selects at `M == 1` (previously only the fp32 variants of the generic instance were warmed, so the first M=1 decode compiled on the fly even for fp32 routers).

Nothing changes for fp32-output routers' numerics, for other dtypes, for `M > 16`, or for quantized / biased gates.

## Claims

- **Router GEMV, H200, K=2048, E=256 (Qwen3.6-35B-A3B):** cuBLAS bf16 `F.linear` takes 5.18 us at every M from 1 to 32 (`nvjet 8x64` tile, 32 CTAs, 164 KB smem for a 1 MB weight read). `ll_bf16_gemm` with the bf16 epilogue takes 1.71 us at M=1, 1.83 at M=2, 2.16 at M=4, 2.77 at M=8 and 2.87 at M=16, the same as its fp32 epilogue.
- **Numerics:** the bf16 logits are bitwise equal to cuBLAS at M <= 8 (dot-product path) and within 1.2e-4 at M=16 (split-K path) for this shape, so routing is unchanged in practice. Keeping bf16 logits matters: fp32 logits would change the top-8 set for about 4% of random tokens.
- **E2E, `Qwen/Qwen3.6-35B-A3B-FP8`, H200 TP1:** median TPOT at concurrency 1 drops from 3.884 to 3.684 ms (-5.2%), output throughput 237.2 -> 248.3 tok/s (+4.7%); concurrency 8 TPOT 5.783 -> 5.708 ms (-1.3%); concurrency 32 unchanged (M > 16, cuBLAS path as before). TTFT unchanged. An nsys trace of the concurrency-1 decode step shrinks from 3863 to 3662 us with the same 1194 kernels per step; the 6 us `nvjet` router GEMM per MoE layer is replaced by the 1.7 us `ll_bf16_gemm` kernel.
- **`Qwen/Qwen3-30B-A3B-FP8`, H200 TP1 (`torch.compile` model, router K=2048, E=128):** median TPOT at concurrency 1 4.444 / 4.469 -> 4.278 / 4.290 ms (-3.9%), output throughput 213.7 -> 222.0 tok/s (+3.9%); concurrency 32 10.145 / 10.163 -> 9.917 / 9.904 (-2.4%; the decode batch drops to M <= 16 as requests drain); concurrency 8 within this model's run-to-run spread (main 6.445 / 6.694, PR 6.522 / 6.452).
- **Accuracy:** GSM8K 5-shot (greedy, 1319 questions, vLLM's `tests/evals/gsm8k/gsm8k_eval.py`) on Qwen3-30B-A3B-FP8: main 0.8886, with this change (overlaid together with the Triton-experts fp32-scale change from #64906) 0.8999; the harness's run-to-run spread is about one point.
- **No change** for routers with `out_dtype=torch.float32` (DeepSeek, GLM, MiniMax, ...), for `M > 16`, or on platforms without the CuTe DSL kernel.

### Tests

`pytest tests/kernels/test_ll_bf16_gemm.py` on H200 (vLLM nightly image): **162 passed**.

- `test_gate_linear_uses_ll_bf16_for_bf16_fast_path` is parametrized over `out_dtype` in fp32 / bf16 / None and checks the dtype handed to the kernel and the output dtype.
- New `test_gate_linear_bf16_out_matches_linear` runs the real kernel through `GateLinear` at M = 1, 2, 4, 8, 16 with the bf16 output requested three ways (default `out_dtype`, explicit `torch.bfloat16`, `set_out_dtype(torch.bfloat16)` after construction) and compares with `F.linear`.

## Details

- **Why the cuBLAS path is slow here.** At decode the router is a 1 MB weight read producing 256 logits per token. cuBLAS picks a 64x16 macro tile with 164 KB of shared memory and 32 CTAs; the kernel is launch- and pipeline-latency bound at ~5 us regardless of M. `ll_bf16_gemm` was written for exactly this shape class (one CTA per expert slice, dot-product for M <= 4, split-K above) and is 3x faster.
- **Relation to #60681.** That PR wraps tier 1 in a custom op so `torch.compile` does not freeze the `M <= 16` branch. This PR only widens which routers reach tier 1 and inherits whatever branch handling lands there; the Qwen3.5 family runs without `torch.compile` since #51012, so the branch is evaluated at run time there today.
- **Routing precision.** The kernel accumulates in fp32 and rounds once to bf16, the same as cuBLAS, which is why the logits match bitwise on the dot-product path. Switching these routers to fp32 logits would be a behaviour change (top-k differs on ~4% of tokens in a random test) and is not done here.
