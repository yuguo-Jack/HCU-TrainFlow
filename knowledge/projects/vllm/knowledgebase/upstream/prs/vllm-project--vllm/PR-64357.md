# [Model Loader] Run the model-level post-load hook once at the end of every load and reload

[Upstream PR](https://github.com/vllm-project/vllm/pull/64357) · state: closed · merged: True

## Original PR description

Thanks to Tony Wang (@new-TonyWang) for design and review contributions.

PR 1 of the direct weight reload stack (RFC #54477). It replaces #57733. The code is the same, plus the Llama4 DP-vision fix that #57733 dropped when it was narrowed.

## Problem

RL weight updates do not load a model in one `load_weights` call. The weight-transfer engines (NCCL, IPC, M2N, sharded RDT) and `reload_weights` call it once per bucket, or once per tensor, between `initialize_layerwise_reload` and `finalize_layerwise_reload`. On main, three things go wrong with that:

1. **The model-level hook never runs after a reload.** `finalize_layerwise_reload` only finishes the layers. The model's `process_weights_after_loading()` runs only from the cold-load path. So any state a model derives from its weights in that hook, such as fused buffers or broadcast copies, keeps the old weights' values after an update.
2. **Some models do that work inside `load_weights` instead.** It then runs once per bucket, on partial weights. Under layerwise reload it runs while the layers are still on meta, which fails with `Cannot copy out of meta tensor`. This affects DeepSeek-V4/V4.1, the DFlash/DSpark drafters and Muse Spark.
3. **Checks on "what this call loaded" fire on every bucket.** A bucket that happens not to contain a layer or head raises "MTP layer N weights missing", or silently sets the DSpark `confidence_head` to `None`.

## Fix

- **One finish step.** New `finalize_model_weights(model)` calls the model's `process_weights_after_loading()`. It is called once at the end of a cold load (as before, after per-layer quant processing) and once at the end of every `finalize_layerwise_reload`. That covers `reload_weights` and the NCCL, IPC, M2N and sharded-RDT engines.
  - The sparse NCCL engine patches weights in place without layerwise reload; its `finish_weight_update` now calls `finalize_model_weights` once.
  - An M2N update whose plan is all direct does not call `finalize_layerwise_reload`, so it still skips the hook, as on main.
  - The torchao reload decorator and the expert-substitution error path finish the layers in the middle of a load. They now call `finalize_layerwise_processing`, so they do not run the model hook early.
- **Post-load work moves from `load_weights` into the hook.** Each `load_weights` below now only loads, and the hook runs at the end:
  - DeepSeek-V4 NVIDIA, V4.1 NVIDIA/AMD: the mHC broadcast (V4.1 AMD's `finalize_mega_moe_weights` is a no-op).
  - DeepSeek-V4.1 NVIDIA: the Engram checkpoint page-cache drop and THP collapse. They now also run after every reload and after dummy loads; both are harmless to repeat.
  - DeepSeek-V4 XPU target, MTP and DSpark: `finalize_mega_moe_weights`. The lazy call in MegaMoE `forward()` is removed, since dummy loads run the hook too.
  - Qwen3 DFlash / Qwen3 DSpark / Gemma4 DSpark / Muse Spark DSpark: `_build_fused_kv_buffers`.
    - The hook now runs after quant processing.
    - In Qwen3 DFlash/DSpark and Gemma4 DSpark, the fused path that reads `.weight` directly is used only when the projections are unquantized and not CPU-repacked (`_reads_raw_weights`). Otherwise each projection runs through its quant method.
    - Muse Spark DSpark still slices `qkv_proj.weight` directly, now after quant processing, so a quantized or CPU-repacked Muse Spark drafter would read kernel-layout weights.
    - Qwen3 DFlash's MXFP8 context K/V projection copied the K/V rows of each layer's QKV weight and scales, which is only valid before quant processing. It is now created at construction and loaded from the checkpoint's K/V tensors as they stream through `load_weights`, so its own post-load step runs and a reload refills it in place.
  - Muse Spark AMD and Muse Spark DSpark: `materialize_residual_path_constants`.
- **The DeepSeek-V4/V4.1 VL wrappers drop their workaround.** They had reordered the weight stream so that the language model's in-`load_weights` finalization saw all its weights (`stream_language_model_first`, `finalizes_weights_during_load`, `_weights_finalized`). That is no longer needed and is removed.
- **"Complete load" checks are gated on `is_mtp_completeness_check_enabled()`**, which the weight-transfer engines turn off during an update:
  - The MTP layer checks in DeepSeek-V3.2 AMD, GLM5-next and Kimi-K3 (AMD/NVIDIA).
  - The DSpark `confidence_head` drop in Qwen3, Gemma4 and DeepSeek-V4/V4.1 (NVIDIA/AMD).
  - The Qwen3 DSpark vocab checks.
  - `AutoWeightsLoader._check_skipped_aliases`.
- **dots3 vision: the block compile runs once.** The vision hook now reruns after every reload, and main's `compile_block_modules` would wrap the blocks in another `torch.compile` each time. It now compiles in place with `Module.compile` (parameter names keep no `_orig_mod`) and only once. The vision MoE is unchanged from main: its hook fuses the experts into FP8 once, deletes the checkpoint experts and returns early afterwards, so a reload leaves the vision experts as they are.
- **Llama4 DP vision (`mm_encoder_tp_mode="data"`).**
  - Before: the vision attention used `ReplicatedLinear`, and `load_weights` gathered `q_proj`/`k_proj`/`v_proj` and called `torch.cat` once all three had arrived. An update that sends them in separate calls failed on `torch.cat` of `None`.
  - Now: it uses `QKVParallelLinear` / `RowParallelLinear` with `disable_tp=True` in DP mode, so q/k/v go through the normal stacked mapping and each part is written into its rows as it arrives. `_consolidate_qkv_weights` is removed.
- **Raw Tensorizer loads use the shared loader path.** Loading a non-vLLM-tensorized checkpoint used its own `_load_model_serialized_cpu`, which ran the model hook but skipped per-layer `process_weights_after_loading`. It now goes through `BaseModelLoader.load_model`.

## Not in this PR

- **Weights combined from several checkpoint tensors inside `load_weights`.** A weight plus its scale, or a fused FP8 qkv, still need every part in the same call, as on main:
  - the FP8 indexer `wk` dequant;
  - GLM5-next MLA projections;
  - MiMo-V2 fused qkv;
  - Molmo/Molmo2 split embedding.

  These are later PRs in the stack (PR 6).
- **Drafters that still finish inside `load_weights`, unchanged from main:**
  - LiLiCorr: the coverage check and `materialize_inference_buffers`.
  - Laguna DFlash: the fused KV build.
  - Qwen3 XPress: the `mix.L` check, `fold_from_raw_` and the fused buffers. It also inherits the new DFlash hook, so at cold start its fused KV buffers are built twice, the second time after quant processing.

  A bucketed update of these drafters behaves as on main. LiLiCorr and Laguna are in the F9 follow-up.
- **Hooks that are not safe to rerun.** Every model-level hook reachable from a top-level model was checked for a second run on reloaded weights. These are not fixed here:
  - **DeepSeek-V4 on ROCm (model, MTP, DSpark): a reload now fails instead of leaving wrong weights.**
    - On main this hook ran only at cold start, so a reload left the mega-MoE experts and the preshuffled attention and gate/up weights unshuffled or stale.
    - With this PR it reruns at the end of a reload. With `fuse_shared_expert`, the first run sets `shared_experts = None` (`finalize_mega_moe_weights`), so the second run raises `AttributeError` in `load_shared_expert`.
    - Without it, the mega-MoE `finalize_weights` returns early (stale experts), and `prepare_attn_preshuffle` / `prepare_gateup_preshuffle` shuffle in place again, so layers that the update did not resend are shuffled twice.
  - **dots3 vision MoE: stale, as on main.** Making it reloadable without keeping the BF16 experts resident (about 11 GiB per GPU on dots3-note-prev-fp8 TP4) needs a loader that quantizes each expert into the fused FP8 buffers as it arrives; that is a follow-up.
  - **Muse Spark NVIDIA: stale, as on main.** The router multiplier is folded once and then dropped, and the mega-MoE `finalize_weights` returns early after dropping `w13_weight`.
  - **DeepSeek-V4 XPU mega-MoE: guarded, as on main.** `finalize_weights` returns early once the weights are transformed. The XPU runtime currently rejects mega-MoE, so the hook is a no-op.
  - **Rebuilt as new tensors.** Kimi-K3 AMD's MLA `_w_fold` and Muse Spark's residual `alpha`/`beta` are re-created by the hook, so a captured CUDA graph keeps reading the old ones.
    - On main Kimi-K3's hook did not run on reload, and Muse Spark rebuilt them the same way from `load_weights`, so neither is worse than main.
    - The DFlash/DSpark (Qwen3, Gemma4, Muse Spark) and Beam DFlash2 context K/V buffers, and Kimi-K3 NVIDIA DSpark's `_context_kv_norm_weights`, are also re-created. The V2 speculator's FULL CUDA graph reads the context K/V buffers, so after a reload it reads freed memory and draft acceptance drops (Beam DFlash2 TP4, split reload: 7.03 → 4.89; MiniMax-M3.1 MXFP8 DSpark TP4: 5.70 → 4.07). Outputs stay correct because the target verifies the drafts. Writing these buffers back in place is PR 5 (`refill_derived`); with it, acceptance after the reload matches the cold start.

after the per-layer quant methods, and `_reads_raw_weights()` routes quantized
layers away from the fused path entirely.

(stub model, two fake attention layers, real method call; CPU, ~2 s). On
`ced6857` it reports:

On the guard: in-tree, quant_method is a good enough proxy. After post-load processing, UnquantizedLinearMethod leaves .weight as a plain matrix on every platform except CPU, which repacks it and is excluded by name.

- AscendUnquantizedLinearMethod subclasses UnquantizedLinearMethod (vllm_ascend/ops/linear.py). Its process_weights_after_loading calls maybe_trans_nz(layer.weight.data).
- With the default weight_nz_mode=1, bf16/fp16 weights stay ND, so the fused path reads plain weights.

so maybe we should have a better check in a follow up. Testing on ascend would be great! useful to have the result for record, but i don't think it will block this pr whatever the result.
