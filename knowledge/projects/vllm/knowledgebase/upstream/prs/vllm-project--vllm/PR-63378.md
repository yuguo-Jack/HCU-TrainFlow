# [Bugfix][Quantization] Thread input_quant into MXFP8 MoE dispatch

[Upstream PR](https://github.com/vllm-project/vllm/pull/63378) · state: open · merged: False

## Original PR description

## Summary

The compressed-tensors MXFP8 MoE dispatch (`compressed_tensors_moe.py:83`) checks only `weight_quant` via `_is_mxfp8()` and ignores `input_quant`, so a weight-only checkpoint (`input_activations: null`) silently gets routed to `CompressedTensorsW8A8Mxfp8MoEMethod`, which hardcodes dynamic MXFP8 activation quantization.

This is the same structural bug as #56770 / PR #55232, but in the MXFP8 path — which neither #55232 nor #56803 touches.

## Root Cause

1. `compressed_tensors_moe.py:83` — `_is_mxfp8(weight_quant)` matches on weight only
2. `compressed_tensors_moe.py:88` — `CompressedTensorsW8A8Mxfp8MoEMethod(layer.moe_config)` constructed without `input_quant`
3. `compressed_tensors_moe_w8a8_mxfp8.py:43` — `__init__` takes only `moe`, calls `select_mxfp8_moe_backend` with no activation key
4. `oracle/mxfp8.py:96-97` — `_select_kernel_cls` hardcodes `(kMxfp8Static, kMxfp8Dynamic)` regardless of checkpoint

Compare with the NVFP4 path (lines 145-159) which correctly passes `use_a16=(input_quant is None)`.

## Fix

Thread `input_quant` through MoE dispatch, method, and oracle, mirroring the NVFP4 pattern:
- `compressed_tensors_moe.py`: validate `input_quant`, pass `use_a16=(input_quant is None)`
- `compressed_tensors_moe_w8a8_mxfp8.py`: accept `use_a16`, forward to oracle
- `oracle/mxfp8.py`: `select_mxfp8_moe_backend` and `_select_kernel_cls` pass `activation_key=None` when `use_a16=True`, so the oracle picks a weight-only backend (e.g. Marlin) instead of hardcoding `kMxfp8Dynamic`

The dense MXFP8 path (`compressed_tensors.py:814`) has the same pattern but is left for a follow-up since `init_mxfp8_linear_kernel` does not yet support weight-only mode.

## Test Plan

- `test_moe_weight_only_mxfp8_sets_use_a16` — weight-only config produces `use_a16=True` (fails on main, passes with fix)
- `test_moe_w8a8_mxfp8_does_not_set_use_a16` — explicit MXFP8 activations produce `use_a16=False`
- `test_moe_mxfp8_weights_with_invalid_input_raises` — non-MXFP8 input with MXFP8 weights raises `ValueError`
- **Needs GPU**: serve a weight-only MXFP8 MoE checkpoint on SM90+ and verify Marlin is selected as the W8A16 backend

- shivmgg · comment · 2026-10-26T16:23:13Z · [source](https://github.com/vllm-project/vllm/pull/63378#discussion_r4379703194)

File: `vllm/model_executor/layers/fused_moe/oracle/mxfp8.py` · line 99

When `use_a16=True`, the oracle passes `activation_key=None`. FlashInfer TRTLLM and DeepGemm require `kMxfp8Dynamic` so they are skipped. `MarlinExperts` accepts `(kMxfp8Static, None)` and is selected — it runs the MXFP8 weights as W8A16, dequantizing to BF16 for the GEMM.

Real-world scenario: a compressed-tensors checkpoint quantized with llm-compressor using MXFP8 weights but `input_activations: null`. Without this fix, activations are silently quantized to MXFP8. With it, Marlin handles it as weight-only.
