# [Metrics] Explore GPU iteration timing through output readiness

[Upstream PR](https://github.com/vllm-project/vllm/pull/61842) · state: closed · merged: False

## Original PR description

## Overview

Explore an alternative timing contract to #61690: correlate the target model’s scheduled batch composition with GPU output-readiness time, using the existing model-output delivery path. Related: #61423; prerequisite: #61424.

**Discussion draft:** This implementation is based on the GPU timing work in #61690 by @tedzhouhk. It was generated by Codex and has **not yet been human-reviewed or human-validated**. The goal is to encourage discussion about which timing and delivery constraints are essential.

[Review only this layer](https://github.com/markmc/vllm/compare/a33a88263f41d0e99dc0e4568f9df5e2a7833ff0...iteration-metrics-gpu-timings): this compares `markmc/iteration-metrics-gpu-timings` against the `markmc/iteration-metrics` revision it builds on. The base branch has since advanced, so its commit is pinned to keep the comparison limited to timing changes.

## Claims

- Replace EngineCore’s CPU result-wait measurement with a worker CUDA-event duration.
- Return each duration with its own `ModelRunnerOutput`, then include it in the existing `SchedulerStats` iteration details.
- Enable instrumentation directly with `enable_logging_iteration_details`. Preserve counts when a duration is unavailable and omit that duration from console logging.

## Validation

**The following checks were run by Codex; human reproduction and validation are pending.**

Focused pytest suites and pre-commit hooks passed, including Ruff and mypy. The tests cover duration propagation, optional serialization, event ownership across queued outputs, and disabled instrumentation.

```bash
.venv/bin/python -m pytest \
  tests/v1/engine/test_iteration_logging.py \
  tests/v1/metrics/test_stats.py \
  tests/v1/worker/test_gpu_worker.py \
  tests/distributed/aux_output_connector/test_store.py -q
```

Four Qwen3-0.6B eager smoke runs on an A100 80GB covered MRV1/MRV2 with async scheduling enabled and disabled, using `VLLM_GPU_SYNC_CHECK=error`. Each run delivered 11 positive iteration durations, including intermediate prefill and final iterations. Scheduled-token totals were checked, and greedy outputs agreed across the four runs.

Overhead benchmarking and broader compatibility qualification remain deferred.

## Details

The existing `elapsed_ms` measures how long EngineCore waits when retrieving a result. With queued execution, substantial GPU work can produce an almost-zero result wait. We want a timing signal that correlates usefully with the scheduled prefill/decode request and token counts.

This proposal starts a CUDA event immediately before the worker calls `model_runner.execute_model()`. For asynchronous outputs, the existing output-copy completion event supplies the endpoint. After the existing copy wait, the duration is ready to accompany that batch’s output. EngineCore’s existing batch/future association pairs it with the scheduling snapshot.

The simplified implementation follows these relaxed constraints:

- **Output readiness defines the interval.** Full accounting of every postprocessing and drafting operation is not required. The interval includes CPU-submission gaps and, on the asynchronous path, result transfer.
- **Runner-dependent coverage is acceptable initially.** MRV2 can copy outputs while postprocessing and drafting continue. MRV1 can draft before copying; synchronous MRV1 uses an end marker before its blocking result read, excluding transfer time.
- **Timing follows normal output delivery.** Durations are optional, including for dummy execution without a timed model output. Independent reporting of pending timings and a final timing flush are outside this proposal.
- **Initial enablement and allocation are simple.** Instrumentation follows the existing logging option and uses per-batch events. Configuration restrictions, event pooling, overhead measurements, and broader defaults can follow qualification.

These choices make the duration available with the corresponding model output. Delivery uses the existing iteration-details payload and frontend route, without an independent timing collector, timing RPCs, idle polling, or shutdown draining. Reading the duration uses the output path’s existing GPU completion wait.

The central discussion is whether these constraints provide sufficient operational value. Do we need an interval that includes all postprocessing and drafting, consistent coverage across runners, or independently timed non-request activity? Which requirements should shape the first implementation, and which can follow later?
