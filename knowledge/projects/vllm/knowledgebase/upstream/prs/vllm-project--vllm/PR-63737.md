# [Perf][dsv4-flash-vision] Accelerate long-context C128 prefill on Hopper

[Upstream PR](https://github.com/vllm-project/vllm/pull/63737) · state: open · merged: False

## Original PR description

## Overview

Accelerate long text prefills in DeepSeek V4's C128 attention on Hopper by processing eight neighboring queries together. Preserve the pinned FlashMLA accumulation and rounding order with unnormalized FP32 intermediate state.

## Claims

- Speed up the C128 attention operation by **1.39× at 64k**, **2.05× at 128k**, and **5.27× at 1M** on H200 with 8,192 query tokens, including query packing and intermediate-buffer allocation.
- Increase measured end-to-end total token throughput by **33.69% at 1M context** on `DeepSeek-V4-Flash-Vision-Exp` at TP8/concurrency 1, with TTFT reduced by **25.43%**, using identical serving parameters.
- Match the original FlashMLA BF16 output bits on the tested synthetic cases and sampled real-model C128 outputs. This is an operator-level result; it does not establish whole-model batch invariance or general task accuracy.
- Automatically select the optimization for eligible SM90 text prefills with eight local heads, at least 512 compressed rows, and at least 4,096 query tokens. Other inputs continue through the existing FlashMLA path.

## Validation

Context lengths use **k** and **M**: **1k = 1024 tokens**, **1M = 1024 × 1k**. Reproduction commands retain the integer token counts required by the CLI.

Measured on 2026-10-26, using 8 × H200 (141 GB), PyTorch 2.14.1+cu130, and CUDA toolkit 13.2.78. Baseline source is unmodified `b689feb9f22129cb9ba65ea72e3e67e4a9c95355`; the candidate adds this C128 implementation. Both reuse the same installed non-C128 native libraries. FlashMLA is pinned to `e2afa5fd8c220fbd05fe03fc24c9d5e64c24641b`.

**Operator benchmark.** BF16 Q/KV, head dimension 512, eight active heads in the existing 64-head layout, 8,192 query tokens. The optimized measurement includes the Python wrapper, Triton query packing, allocations, and both CUDA launches. The reference uses prebuilt sparse indices; excluding their construction favors the reference. Each point uses `triton.testing.do_bench(warmup=100, rep=300)`.

**Serving benchmark.** Checkpoint: `DeepSeek-V4-Flash-Vision-Exp`, architecture `DeepseekV4ForConditionalGeneration`, text requests only. No parameter adjustment is counted as a code speedup.

Each request has `context - 128` input tokens and exactly 128 generated tokens; concurrency 1, request rate `inf`, greedy sampling, and EOS ignored. Before each round, reset prefix caching. Each length has a separate one-request warmup. Report the median of three four-request rounds at 16k/128k/256k/512k and one four-request round at 1M. Both arms use seeds 20261024–20261026 for formal rounds and 8675309 for warmup.

## Details

The original Hopper sparse prefill processes each query with 64 head rows, although this TP8 workload has only eight active heads. Neighboring queries in C128 layers attend to almost the same long, contiguous compressed prefix. Packing eight queries × eight heads fills those 64 rows with useful work and shares prefix KV loads.

A Triton helper packs Q. A native CUDA shared-prefix kernel computes complete common prefix tiles and saves the unnormalized FP32 output accumulator, maximum, and unreduced denominator state. A second CUDA kernel resumes each query's remaining compressed tiles and sliding window, applies its attention sink, and normalizes once. Keeping this raw state preserves the reference's reduction and rounding sequence; normalizing and reconstructing prefix state would introduce BF16 differences. The attention computation uses CUDA; there is no Triton attention fallback.

Dispatch stays inside the existing DeepSeek V4 NVIDIA attention implementation. It requires the native extension, SM90, BF16 Q, compression ratio 128, eight local heads, a 128-token window, no extended image visibility, non-batch-invariant execution, one prefill request in the workspace group, at least 512 compressed rows, and at least 4,096 queries. The compressed-row threshold corresponds to approximately 64k original context tokens. It is checked per workspace group and query chunk, rather than against global client concurrency.

The change does not modify scheduler, model-runner, KV-cache manager, indexer configuration, or decode logic. It continues using the existing BF16 KV gather. `_c128_C` is an optional SM90a extension built alongside FlashMLA; installations without it use the original path. The vendored adaptation retains the upstream FlashMLA MIT notice and identifies the source version.

**Tradeoffs and limits.** Packing and the separate tail kernel add overhead, motivating the dispatch thresholds. Staging uses 203,689,984 bytes (194.25 MiB) per rank at 8,192 query tokens, and scales with query count. The existing dummy profiling path does not explicitly allocate this added staging. The tested 8,192-token configuration completed long-context serving; this does not validate memory budgeting at 32k batched tokens or at higher concurrency. Multi-image requests, other head counts, other architectures, decode speed, and full model quality benchmarks are outside the measured claims. Exact output agreement is scoped to the tested Hopper implementation and pinned dependency/compiler versions.

<summary>Related work and duplicate check (2026-10-26)</summary>

Query grouping is an existing optimization direction. [vLLM #48726](https://github.com/vllm-project/vllm/pull/48726) includes structure-aware C128 query packing on SM100 alongside indexer optimizations. This change targets SM90, uses BF16 gathered KV, and preserves legacy FlashMLA arithmetic through explicit prefix-state continuation. [#63104](https://github.com/vllm-project/vllm/pull/63104) groups queries for FA4 sparse prefill with 16–64 local heads on SM100. [SGLang #32779](https://github.com/sgl-project/sglang/pull/32779) uses Triton sparse-query unions, including on SM90, rather than this native C128 continuation.

[#59131](https://github.com/vllm-project/vllm/pull/59131) reuses gathered KV across layers; [#41836](https://github.com/vllm-project/vllm/pull/41836) avoids BF16 gathering via a KV-cache path. This implementation retains gathering and shares KV within a query tile. [FlashMLA #170](https://github.com/deepseek-ai/FlashMLA/pull/170) changes producer scheduling; [FlashMLA #227](https://github.com/deepseek-ai/FlashMLA/pull/227) targets fused H64 attention on B200.

The base already includes [#61615](https://github.com/vllm-project/vllm/pull/61615), enabling the existing small-head operation for V4.1. That per-query implementation does not share the C128 prefix or expose raw prefix state. The inspected work does not implement this SM90 C128 prefix/state/tail specialization. This is a scoped search result, not a claim of novelty or an exhaustive duplicate-work guarantee.
