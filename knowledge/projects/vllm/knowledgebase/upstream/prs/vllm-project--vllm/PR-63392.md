# [ROCm][Perf] AITER FA: trim the sliding-window decode table with fewer ops

[Upstream PR](https://github.com/vllm-project/vllm/pull/63392) · state: open · merged: False

## Original PR description

## Overview

Cut the ROCM_AITER_FA sliding-window decode-table trim (`_build_swa_decode_tables`, q == 1 decodes) from 10 aten ops to 7 per call, with byte-identical results.

This PR started as an opt-in trim of the block table for spec-decode verify (q > 1), which only paid off with a window-bounded AITER split. AITER instead merged a window-aware split, ROCm/aiter#6889 (`b6c376cfa6`). Its split covers only each sequence's window tiles, so an untrimmed verify table gets the same split as a trimmed one, and the verify trim would only add ops. That part and `VLLM_ROCM_AITER_FA_SWA_VERIFY_TRIM` are dropped. vLLM picks up the AITER split with the next AITER bump; main pins v0.1.27, which predates it.

## Claims

- 7 aten ops per call instead of 10. The old ops were `sub`, `clamp`, `floor_divide`, `_to_copy`, `add`, `clamp_`, `gather`, `mul`, `sub`, `copy_`; the new ones are `sub`, `clamp_`, `floor_divide`, `add`, `clamp_`, `gather`, `sub`.
- The table, seq lens and max seq len are byte-identical to the previous formula.
- The table is built once per decode step for each sliding-window KV-cache group.

## Validation

In a ROCm image with no GPU work (the branch's source over the image's compiled vLLM):

```
$ pytest tests/v1/attention/test_rocm_aiter_fa_swa_decode_tables.py
1 passed
```

- The new CPU test compares the trimmed table, seq lens (and their dtype) and max seq len with the previous formula. It covers contexts across the window and block edges, from 1 to 200000.
- A mutant that rebases the seq lens by one block too many fails it.
- Op counts come from a `TorchDispatchMode` counter over the old and new code on the same inputs, which also confirms identical outputs.
- `tests/kernels/attention/test_rocm_aiter_fa.py` (GPU, unchanged) still runs the q == 1 trimmed table through AITER `paged_attention_v1` against the full table.

## Details

- The clamp of the first visible key runs in place.
- `_swa_block_offsets` is int64, so adding it promotes the gather index and the int64 cast copy is not needed.
- The rebased seq lens are written straight into the persistent buffer with `torch.sub(lens, first_block, alpha=block_size, out=...)`, instead of a temporary followed by `copy_`.
