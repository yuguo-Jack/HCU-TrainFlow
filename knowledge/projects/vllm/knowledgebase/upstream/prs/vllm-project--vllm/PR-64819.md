# [Bugfix][KV Offload][P2P] Disconnect a peer whose registration fails

[Upstream PR](https://github.com/vllm-project/vllm/pull/64819) · state: closed · merged: True

## Original PR description



## Overview

When this side's registration of a peer's NIXL agent fails, `_poll_registration` only marks the local connection dead. The peer has registered us and keeps its session waiting for our ack. Our next connection to it is routed into that session, which acks our ConnectMsg without sending its own: our session becomes `ready` without registering the peer, the peer never gets our ack and queues its `LookupRespMsg`s, and each lookup on that session waits out the 8 s lookup timeout. Send a best-effort `DisconnectMsg`, as the other teardown paths do, so the peer drops that session and the next connection gets a fresh handshake. Record the failure as a data-plane fault so the reap applies the reconnect backoff.

The routing of a reconnect into the peer's existing connection is discussed on #64060; this change does not depend on how that is resolved.

## Claims

- A failed registration sends a best-effort `DisconnectMsg`. When it is delivered, the peer drops its half-open session, and the next connection does a fresh handshake in which this side registers the peer again.
- A failed registration counts as a data-plane fault, so repeated failures use the existing reconnect backoff: no wait after the first, then 1, 2, 4 ... 60 s.
- No transport change. A reconnect that reaches the peer while its ROUTER still holds the old routing id is still dropped (#63740). If the `DisconnectMsg` is lost, for example when a handover drops the displaced pipe's messages as in #64060, the half-open state remains.

## Validation

New `TestBidirectionalManager::test_failed_registration_drops_the_peer_session`: two managers built with their constructors from `make_offloading_config()`, on real `NixlTransport` and `ZmqTransport`, with only the NIXL agent faked; A's agent fails `add_remote_agent`. It checks that B drops its session for A and that A counts the failure as a data-plane fault. It does not reconnect: whether a reconnect gets through depends on #63740, so the backoff that follows a repeated failure is covered by `data_plane_fault` here and by the existing `TestReconnectBackoff` tests. `TestConnectHandshake::test_failed_registration_rejects_peer` gains two assertions: a `DisconnectMsg` is sent, and `data_plane_fault` is set.

With `UCX_TLS=all`, which re-enables the `rc_gda` lanes that #63498 excludes, A's registration of B's replacement B2 fails on every attempt. These timings measure requests naming a peer A cannot use, including local fallback; B2 made no successful pulls in these runs. Same node, builds alternated:

|---|---|---|---|---|---|
| main | graceful delete | 2 | 4.373-4.377 / 8.32 s | 12 / 11 | 448-451 / 106-116 |

With this change, each of A's 8 failed registrations is followed in the same second by B2 ending its session on `peer disconnected`, and A's attempts are spaced by the backoff: 0, 1, 2, 4, 8, 16 and 32 s, plus the handshake.

Without `UCX_TLS=all`, this change, one run each. "Pulled" means A submitted a P2P load for the request:

| SIGSTOP for 60 s, then SIGCONT | 620 of 620 | 0.021 / 4.9 s | 244 of 244 | none |
| kill, restart at the same IP | 511 of 511 | 0.024 / 0.088 s | 400 of 400 | B once, from the kill |
| rolling replacement | 594 of 594 | 0.048 / 0.076 s | 400 of 400 | none |

Under SIGSTOP, one lookup sent as B stopped ended on the 8 s lookup timeout; the 4.9 s maximum is over requests issued during the fault. No engine logged a `UnicodeDecodeError` or an engine-core fatal error in any run; the only tracebacks were `EngineDeadError` from vLLM's shutdown when a pod was deleted, in both builds.

No `LLM`/`RemoteOpenAIServer` regression test is included: reaching this path end to end needs a NIXL registration failure, which the CPU tests inject by faking the NIXL agent and the GPU runs above force with `UCX_TLS=all`. Asking maintainers to accept that test scope.

## Details

The failure is recorded like an unacknowledged abort (`_abort_ack_fault`): `data_plane_fault` returns it, and the reap's existing backoff takes over. The `DisconnectMsg` is best-effort, like the other teardown paths: a send failure is suppressed and the connection is marked dead without waiting for the peer.
