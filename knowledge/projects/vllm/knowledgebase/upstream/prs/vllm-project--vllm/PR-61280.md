# [Benchmark][Spec Decode] Build synthetic_acceptance_rates from a measured drafter

[Upstream PR](https://github.com/vllm-project/vllm/pull/61280) · state: open · merged: False

## Original PR description



## Overview

`synthetic_acceptance_length` resolves a target mean to the minimum-variance schedule, which no real drafter occupies. This adds a helper that builds `synthetic_acceptance_rates` from an acceptance distribution vLLM already records, plus a docs note. Related: #59650 (per-request synthetic acceptance *length*), #59750 (RFC on empty responses in synthetic acceptance benchmarks).

## Claims

- `synthetic_acceptance_length` yields the least-dispersed distribution with the requested mean. At mean acceptance length 1.967, `_acceptance_length_to_rates` gives `[0.967, 0, 0, 0, 0, 0, 0]` (variance 0.032). A measured EAGLE-3 drafter at the same mean is `[0.557, 0.292, 0.084, 0.027, 0.007, 0, 0]` (variance 1.171), i.e. **36.6x** the variance.
- No new measurement is needed to fix this. `acceptance_histogram` from `--per-request-spec-decode-metrics` and the `Per-position acceptance rate` log field are both already the unconditional survival function that `synthetic_acceptance_rates` consumes.
- `benchmarks/spec_acceptance_rates.py` converts either into a paste-ready `--speculative-config` fragment.
- No behavior change. `_acceptance_length_to_rates` is untouched, so existing configs and published golden acceptance lengths produce identical fixtures.

## Validation

The helper's derivation cross-checks against vLLM's own documented example. Feeding the `acceptance_histogram` from `docs/features/speculative_decoding/acceptance_metrics.md` (`[39, 1, 0, 3]`), it recovers the mean acceptance length that doc independently reports as `1.2325581395348837`:

```
$ python benchmarks/spec_acceptance_rates.py --histogram 39 1 0 3
source                 acceptance_histogram
measured rates         [0.093023, 0.069767, 0.069767]
mean acceptance length 1.2326
variance of accepted   0.5971
min-variance schedule  [0.232557, 0.0, 0.0]
its variance           0.1785
ratio measured/minvar  3.3x
```

Log mode, against a real server log (L40S, Qwen2.5-7B target, `thoughtworks/Qwen2.5-7B-Instruct-Eagle3` drafter, `num_speculative_tokens=7`, ShareGPT prompts, 41 stats windows):


Per-window variance was 1.28-1.37 across all 41 windows, so the figure is stable rather than one noisy sample. The emitted vector round-trips: it satisfies `_resolve_synthetic_acceptance_rates`'s range, length and monotonicity validation.

## Details

The minimum-variance schedule is the right default and I have deliberately not changed it. It makes a fixture reproducible, it is what the published golden-acceptance-length recipes depend on, and for throughput measurement the mean is the only thing that matters. The gap is narrower than that: a benchmark that reads a latency *distribution* sees a drafter committing a near-constant number of tokens per step, whereas a real drafter's per-position rates decay geometrically. Mean yield is reproduced; burstiness is not.

Two input forms, because the two sources suit different situations. `acceptance_histogram` is exact and per-request but needs `--per-request-spec-decode-metrics` enabled up front. The log field is pooled across requests and available from any server already running at INFO with stats on.

Implementation notes. From `acceptance_histogram`, index `j` counts steps accepting exactly `j` draft tokens, so the survival function is a suffix sum. From the log, `num_accepted_tokens_per_pos[i]` is incremented for `i in range(num_accepted)`, so position `i` already counts drafts with at least `i + 1` tokens accepted, and `np.sum(pos_matrix, axis=0) / num_drafts` is the survival function directly. Pooling across windows can introduce a small inversion, so the output is clamped monotonically non-increasing to satisfy the validator.

Limitation worth stating: the 36.6x figure is one drafter, one target, one GPU. The direction generalizes by construction, since the schedule is the variance minimizer at any mean, but the magnitude will vary by drafter.

Why this is not duplicating #59650: that PR varies which *mean* each request gets, still resolved through the minimum-variance schedule. This varies the *shape* at a given mean. They compose rather than overlap.
