# [Perf][DSv4] Process 4 heads per program in fused_inv_rope_fp8_quant

[Upstream PR](https://github.com/vllm-project/vllm/pull/63540) · state: open · merged: False

## Original PR description

## Overview

`fused_inv_rope_fp8_quant` applies inverse RoPE to the attention output and quantizes it to block FP8 for `wo_a`. It launched one single-warp program per (token, head), which ran at 1.5 TB/s on B200 and took 8.6% of a 16k-token DeepSeek-V4-Flash prefill step (TP2).

This PR makes each program handle 4 heads of one output group, swaps the RoPE pairs in registers instead of re-loading them, and picks `num_warps` from the grid size. Outputs are bitwise identical to `main`.

## Claims

- Kernel, 16k tokens, 32 heads per rank (V4-Flash TP2): B200 536 → 152 µs (3.53x), H200 631 → 208 µs (3.04x), H100 631 → 293 µs (2.15x). At decode sizes it is at most 0.3 µs slower per call.
- `vllm bench forward`, V4-Flash TP2 + EP on 2×B200: prefill and mixed batches are 6% faster; decode is unchanged.
- `vllm bench serve`, 8k in / 1k out: TTFT p99 drops 5.1–5.6% at concurrency 1 to 128. Throughput stays within run-to-run noise.
- FP8 values and scales are bitwise identical to `main`, gsm8k is unchanged, and there are no runtime JIT compiles.

## Validation

Measured on Modal (CUDA 13.0, torch 2.14.0+cu130, Triton 3.8.0) at base `5f63ea461c`. Rebased onto `71a8275604` (the newest `main` commit with a published precompiled wheel; it does not touch these files) and re-ran the unit tests.

**Correctness**

- Unit tests: 106 passed on B200, including the new `H24_G4` case. They cover both scale layouts, quant groups 32 and 128, `quantize=False` and both `num_warps` branches. On H100 and H200, 93 passed and 8 SM100-only cases were skipped. The 5 `test_einsum_end_to_end` failures there also happen on `main`: the test hard-codes the SM100 einsum recipe, which DeepGEMM rejects on SM90.
- Bitwise comparison with `main`'s kernel on B200, H100 and H200: every (BLOCK_H, num_warps) config, T = 1 to 16384, H = 16/32/64, plus head-padded and offset input views and extreme values. No mismatch.
- gsm8k with the B200 CI config `DeepSeek-V4-Flash-deepgemm-mega-moe.yaml` (TP2 + EP, FP8 KV, MTP), three runs each: `main` 0.9469 / 0.9492 / 0.9507, this PR 0.9492 / 0.9500 / 0.9484. All pass the CI threshold with 0% invalid answers and MTP acceptance length 2.63–2.64.

## Details

**Root cause.** Each program moved only 1.5 KiB with one warp: 524,288 programs at 16k tokens and 32 heads. With at most 32 resident per SM, too little data is in flight to keep HBM busy. `main`'s kernel takes the same 631 µs on H100 and H200 although the H200 has 43% more bandwidth, so it is latency-bound.

**Changes** in `vllm/models/deepseek_v4/common/ops/fused_inv_rope_fp8_quant.py`:

1. **Heads per program.** `BLOCK_H = gcd(heads_per_group, 4)`. All V4 configs have 8 heads per group, so `BLOCK_H` is 4. The heads in one program share an output group, so addressing only gains a leading `[BLOCK_H]` dimension.
2. **RoPE in registers.** Instead of re-loading each element's partner (`offsets ^ 1`), the kernel splits each row into even and odd halves with `tl.split`, rotates them and joins them with `tl.join`. The fp32 operations and their order are unchanged, so the output is bitwise identical. This matters only together with change 1: with 4 heads per program, keeping the re-load is 1.66x slower (252 vs 152 µs, B200, 16k tokens).
3. **`num_warps` from the grid size.** 4 warps below 2048 programs (decode), 1 otherwise (prefill). `num_warps` is a `CompileKey` field warmed with `WarmupChoices(1, 4)`, so both variants compile at startup.

**Tuning.** BLOCK_H 4 with 1 warp was fastest at large T on B200 (BLOCK_H 8 took 166 vs 152 µs). At small T, 4 warps stayed closest to `main`, with the crossover near 2048 programs. On H100 and H200 the same config is within 4% of the best one, so there is no per-arch tuning.

**Affected paths.** The interface does not change. Callers: V4 on CUDA through `deep_gemm_fp8_o_proj` (FlashMLA sparse, and FlashInfer sparse unless it fuses RoPE and quant into attention, which needs 128 heads per rank; V4-Flash always calls this kernel), V4.1 batches that do not take the fused WO-A path (quant group 32), and V4 on XPU.

**Batch invariance.** `num_warps` depends on the batch size, but every config gives bitwise-identical output and each program handles one token, so a token's output does not depend on the batch size.

**Limitations.** Forward, serving and gsm8k ran on B200 only. V4.1 (quant group 32) and XPU were not timed; I have no XPU hardware. Decode sizes are up to 0.3 µs slower per call, at most 13 µs per step over 43 layers (0.2% of TPOT at concurrency 1).
