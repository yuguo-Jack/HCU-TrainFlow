# feat(kv-cache): expose block allocation generations

[Upstream PR](https://github.com/vllm-project/vllm/pull/62819) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Expose allocator-issued KV block generations through allocation and request-finish connector handoffs, so asynchronous connectors can reject stale control completions after physical slot reuse. Closes #62810.

## Claims

- `BlockPool` issues a process-local allocation epoch in the existing allocation loop; `(block_id, generation)` is scoped by connector session, KV group, and owning pool.
- `KVCacheBlocks` reports null/unissued blocks explicitly and preserves the legacy positional `KVCacheBlock` constructor.
- Generation-bearing finish and partial-tail hooks reach ordinary, HMA, and `MultiConnector` consumers while existing connector overrides remain compatible.
- This identity is not a DMA/RDMA/CUDA termination receipt and never authorizes early block reuse.

## Validation

- Staged pre-commit suite: all applicable hooks passed, including Ruff, formatting, mypy, SPDX, test tethering, forbidden imports, and configuration checks.
- Focused allocation/finish/MultiConnector suite: `11 passed`.
- Broader connector selection: `32 passed, 1 skipped`; one model test could not start because the CPU-only isolated environment had no detectable device, before candidate behavior ran.
- Allocation-only CPU micro-control, 7 repeats of 5,000 cycles × 64 blocks:

| revision | median |
| --- | ---: |
| base `b3047819e0` | 65.83 ms |
| candidate `b37aa38cc4` | 66.14 ms |

The +0.46% descriptive delta is limited to this synthetic allocator loop; it is not serving or GPU performance evidence.

Reproduction commands and exact outputs are retained in the linked issue and PR discussion; the focused pytest command uses Python 3.12, `requirements/common.txt`, pytest 9.1.0, and Torch 2.14.0 CPU.

## Details

The root cause is that connectors receive reusable physical `block_id` values while the owning allocator previously exposed no identity for the current writable allocation. Request/session metadata cannot distinguish an old transfer completion from a newer allocation of the same slot.

The generation is arbitrary-precision and process-local. Null padding is `None`; the surrounding connector session, KV-group position, and immutable pool configuration provide scope. Existing connector implementations continue through default forwarding hooks, while generation-aware connectors override the new methods. The hot path adds no extra list traversal: epoch assignment is folded into the existing per-block allocation loop.

Duplicate-work checks searched open PRs by issue number and by `block allocation generation KV connector`. No matching implementation exists; results such as #61056, #60061, and #57751 address copy batching, range validation, or state fill rather than allocator identity.

No model evaluation is required because this metadata-only change does not affect model output or accuracy.
