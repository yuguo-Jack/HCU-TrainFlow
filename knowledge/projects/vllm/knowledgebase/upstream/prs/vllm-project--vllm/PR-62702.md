# [Perf][Core] Keep prompt token ids as int32 buffers

[Upstream PR](https://github.com/vllm-project/vllm/pull/62702) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Keep prompt token ids as one int32 buffer from the frontend to the GPU workers. The frontends send `prompt_token_ids` as a rank-1 ndarray (out of band when long), `Request` stores them in `TokenBuffer` (an int32 `array` that reads like a list), and the MRV2 worker stages them as one chunk.

Merged with main and tested at `fc510b3710` (main at `dd4e40142a`, 2026-11-04). #65300 is on main and already sends a new request's prompt to workers once, so that is not counted below. What is left is the per-token work: main still creates or walks one Python int per token on every hop, and keeps one per token in memory.

## Claims

CPU time per admitted request and EngineCore memory, main -> this PR, on one 128K-token prompt:

- **Step's critical path:** pickle + unpickle + staging, 6.86 -> 0.17 ms (40x). Pickle and unpickle run before the worker reaches the step's DP all-reduce, so a rank admitting a long prompt makes every rank wait.
- **Input thread, with frontend hashes:** decode + `Request()`, 3.99 -> 0.24 ms (16x). This thread holds the GIL the engine loop needs.
- **EngineCore memory:** 6.45 -> 1.68 MB per request (3.8x).
- **Costs:** the Python frontend's encode goes from 3.53 to 4.33 ms (+23%). Requests hashed in the engine (e.g. multimodal) do not gain on the input thread.
- **Not shown:** end-to-end throughput on this head. These are per-stage CPU measurements.

## Validation

**What this means for a decode instance (arithmetic, not a measurement).** The reference is a DeepSeek-V4.1-Flash P/D run with `max-num-seqs` 128 and ~0.36 admissions per step per DP rank:

- Critical path: ~6.86 ms x 0.36 = ~2.5 ms per step on average on each rank, or ~14 ms on a step where one rank admits 2 requests. All-reduce makes the other ranks wait for the part before it. This PR makes both negligible.
- Input thread: 3.99 ms x 15.5 req/s = ~6% of a core holding the GIL, against ~0.4%.
- Memory: 128 running requests x 4.77 MB = ~0.6 GB less per EngineCore at 128K, not counting requests waiting for a slot.

```python
#!/usr/bin/env python
"""CPU and memory one long prompt costs with list[int] (main) and int32 (#62702).

Run from a vLLM checkout, on main and on #62702 (no GPU needed; staging is skipped
without one). Times one request through each CPU stage, in-process, with random ids:
    PYTHONPATH=. numactl --cpunodebind=0 --membind=0 \
        python repro_prompt_ids_after_65300.py 2>/dev/null

The frames come from the Python encoder, which produces the same (dtype, shape, data)
ndarray wire format as vllm-rs. The transfer through the ring or zmq is not measured.
"""

import json
import pickle
import time
import tracemalloc

import numpy as np
import torch

from vllm import SamplingParams
from vllm.utils.hashing import get_hash_fn_by_name
from vllm.v1.core import kv_cache_utils as kcu
from vllm.v1.core.sched.output import NewRequestData
from vllm.v1.engine import EngineCoreRequest, PrefixHashConfig, core_client
from vllm.v1.request import Request
from vllm.v1.serial_utils import MsgpackDecoder, MsgpackEncoder
from vllm.v1.worker.gpu.buffer_utils import StagedWriteTensor

BLOCK = 16
OOB_BYTES = 1 << 20  # MessageQueue sends buffers of at least this size out of band
pack = getattr(core_client, "_with_packed_prompt", lambda request: request)
enc, dec = MsgpackEncoder(), MsgpackDecoder(EngineCoreRequest)
sha256 = get_hash_fn_by_name("sha256")
kcu.init_none_hash(sha256)
hasher = kcu.get_request_block_hasher(BLOCK, sha256)
hash_config = PrefixHashConfig(
    hash_algo="sha256", hash_block_size=BLOCK, none_hash=kcu.NONE_HASH
)
staged = None
if torch.cuda.is_available():
    staged = StagedWriteTensor(
        (2, 1 << 20), torch.int32, torch.device("cuda"), uva_instead_of_gpu=True
    )
rng = np.random.default_rng(0)


def best_ms(fn, n=10):
    times = []
    for _ in range(n):
        start = time.perf_counter()
        fn()
        times.append(time.perf_counter() - start)
    return min(times) * 1e3


def dumps(obj):
    oob = []

    def callback(buf):
        raw = buf.raw()
        if len(raw) < OOB_BYTES:
            return True
        oob.append(raw)
        return False

    return pickle.dumps(obj, protocol=5, buffer_callback=callback), oob


def admit(frames, block_hasher):
    """EngineCore's input thread: decode a request and build the Request."""
    request = dec.decode(frames)
    return Request.from_engine_core_request(
        request, block_hasher, kcu.frontend_block_hashes(request, hash_config)
    )


def engine_request(ids, block_hashes=None):
    return EngineCoreRequest(
        request_id="r",
        prompt_token_ids=ids.tolist(),
        mm_features=None,
        sampling_params=SamplingParams(max_tokens=16),
        pooling_params=None,
        arrival_time=0.0,
        lora_request=None,
        cache_salt=None,
        data_parallel_rank=None,
        block_hashes=block_hashes,
    )


def encode(ids, block_hashes=None):
    return [bytes(f) for f in enc.encode(pack(engine_request(ids, block_hashes)))]


def held_mb_per_request(make, count=8):
    tracemalloc.start()
    live = [make() for _ in range(count)]
    held = tracemalloc.get_traced_memory()[0]
    tracemalloc.stop()
    del live
    return held / count / 1e6


for n in (131072, 875520):
    ids = rng.integers(0, 129280, n, dtype=np.int32)
    plain = encode(ids)
    req = admit(plain, hasher)
    hashed = encode(ids, list(req.block_hashes))
    assert admit(hashed, hasher).block_hashes == req.block_hashes
    prefill = getattr(req, "prefill_token_ids", req._all_token_ids)
    new_req = NewRequestData.from_request(req, ([],), prefill)
    blob, oob = dumps(new_req)
    data = pickle.loads(blob, buffers=[bytearray(b) for b in oob])
    assert list(data.prefill_token_ids) == list(data.prompt_token_ids) == ids.tolist()

    row = {
        "python_frontend_encode": best_ms(lambda: encode(ids)),
        "input_frontend_hashes": best_ms(lambda: admit(hashed, hasher)),
        "input_no_hashing": best_ms(lambda: admit(plain, None)),
        "input_engine_hashes": best_ms(lambda: admit(plain, hasher), n=3),
        "pickle": best_ms(lambda: dumps(new_req)),
        "unpickle": best_ms(
            lambda: pickle.loads(blob, buffers=[bytearray(b) for b in oob])
        ),
    }
    if staged is not None:

        def stage():
            staged.stage_write(0, 0, data.prefill_token_ids)
            staged.apply_write()
            torch.cuda.synchronize()

        row["stage_apply"] = best_ms(stage)
        assert torch.equal(staged.gpu[0, :n].cpu(), torch.from_numpy(ids))

    row["engine_mb_per_request"] = held_mb_per_request(lambda: admit(hashed, None))
    row["pickle_mb"] = (len(blob) + sum(len(b) for b in oob)) / 1e6
    print(json.dumps({"n": n, **{k: round(v, 3) for k, v in row.items()}}), flush=True)
```

## Details

**Why main still pays per token.** An N-token prompt is N Python ints when msgspec decodes it, again when the scheduler output is pickled and unpickled, and again in worker staging. Each int also takes ~32 bytes plus an 8-byte list slot, and `Request` keeps two lists. With an int32 buffer, each hop copies one block of memory, and stored ids take 4 bytes per copy.

- `TokenBuffer` subclasses `array('i')`. Indexing returns `int`; slices and `copy()` return lists; it compares equal to lists; `+` returns a list. Type checkers see it as a `list[int]` subclass. A third-party consumer that JSON- or msgpack-encodes `request.prompt_token_ids` directly would need `list(...)`.
- Both frontends send a 32-bit int ndarray: vllm-rs as `WireNdArray`, the Python frontend through `_with_packed_prompt`. Above `VLLM_MSGPACK_ZERO_COPY_THRESHOLD` it goes in its own frame. `EngineCoreRequest.prompt_token_ids` is an ndarray only in its runtime annotation; in-process clients still pass a list. Token ids must fit in 32 bits.
- `TokenBuffer` pickles as a `PickleBuffer`, which `MessageQueue` sends out of band at 1 MiB and above.
- The Rust block hasher decodes the ids into a `Vec<u32>` once per request with `WireNdArray::to_u32_vec`; hashes are byte-identical to main's.
- Reasoning parsers and other engine scans use `rfind_tokens`, so a `TokenBuffer` is searched with numpy rather than one Python int at a time.

**Tradeoffs and limitations:**

- The Python frontend pays one list -> int32 conversion per request (+23% encode).
- Engine hashing pickles Python ints, so requests hashed in the engine only move the int creation from decode to hashing. #63454 (draft) adds an opt-in hash over int32 buffers, which would help them.
- Output tokens are unchanged: `_output_token_ids` stays a list.
- This touches 50 files (+794/-283), much of it call sites that assumed a list. Reviewers should weigh that against the numbers above, which do not yet include end-to-end throughput.

**Not a duplicate:** #65300 (merged) shares the send-once change, already on main, and none of the costs measured here. #59908 covers the scheduler -> worker hop only; #51334 is inactive.
