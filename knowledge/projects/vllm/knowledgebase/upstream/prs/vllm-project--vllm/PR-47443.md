# [Attention Backend] Select split-K per shape in HPC Attention Decode Backend, add integration tests

[Upstream PR](https://github.com/vllm-project/vllm/pull/47443) · state: closed · merged: False

## Original PR description

## Purpose

`HpcAttentionImpl.forward()` (part of the HPC attention backend, which wraps the decode / prefill kernels from [`Tencent/hpc-ops`](https://github.com/Tencent/hpc-ops)) hard-coded `splitk=True` on the decode path, but empirical measurements show split-K only wins for **small batches or long sequences** — for mid-sized batches with short contexts (e.g. `num_decode_tokens=8, max_seq_len=1k`) the non-split-K path is faster. This PR replaces the flag with a shape-aware selector `_hpc_decode_use_splitk()` keyed on `(splitk_seq_len_hint, num_decode_tokens, num_heads, num_kv_heads)`.

**Changes:**
- `vllm/v1/attention/backends/hpc_attn.py`
  - Add `_hpc_decode_use_splitk()` (hand-tuned table; auto-tune left as TODO).
  - Add `decode_splitk: bool = True` to `HpcAttnMetadata`, precomputed in `build()` so `forward()` just reads it (one selector call per batch instead of per layer).
  - `build()` feeds the selector with `common_attn_metadata.max_seq_len` (CPU int, no D2H sync — matters on the async spec decode path).
  - `build_for_cudagraph_capture()` recomputes with `max_model_len` as the seq_len upper bound so the split-K bool baked into the graph stays valid for any replay length.
  - Drop `self.splitk = True`. BF16 decode uses `attn_metadata.decode_splitk`; FP8 decode keeps `splitk=True` (the actual FP8 schedule is driven by the per-request `split_flag` tensor from `HpcRopeNorm`).
- `tests/kernels/attention/test_hpc_attention.py` 
- `benchmarks/attention_benchmarks/configs/hpc_attention.yaml`

**<sub><sub>![P2 Badge](https://img.shields.io/badge/P2-yellow?style=flat)</sub></sub>  Avoid syncing seq_lens_cpu when choosing split-K**

When async spec decode is enabled, `gpu_model_runner.py` clears the CPU shadow for sequence lengths, and `CommonAttentionMetadata.seq_lens_cpu` falls back to `self.seq_lens.to("cpu")`. This new access therefore forces a GPU-to-CPU synchronization on every HPC metadata build just to choose the split-K path, defeating the async scheduling path for decode; use an existing CPU upper bound/max length or keep this heuristic graph/device-safe instead.

Useful? React with 👍 / 👎.

**<sub><sub>![P2 Badge](https://img.shields.io/badge/P2-yellow?style=flat)</sub></sub>  Use a graph-safe length for split-K capture**

With FULL CUDA graphs, uniform decode capture seeds dummy `seq_lens` with `max_query_len` (1), and this builder inherits the default `build_for_cudagraph_capture()`. As a result, captured decode graphs for batch sizes where the table disables split-K at length 1 will replay that fixed Python `splitk=False` launch even for long-context requests where `_hpc_decode_use_splitk()` would return true, so long-context decode under CUDA graphs never gets the intended split-K kernel.

Useful? React with 👍 / 👎.
