# [Test] Harden NVFP4 KV scale-layout validation

[Upstream PR](https://github.com/vllm-project/vllm/pull/50336) · state: open · merged: False

## Original PR description

## Summary

Harden the native NVFP4 KV-cache writer test with a relative-L2 error bound of 0.15, and make its V-scale reference match the native writer on SM120. This changes tests only.

Rebased onto `main` at `d15be0856d` on 2026-10-30. Main already has the shared dequantizer's `swizzled_scales` option, so the remaining change is confined to `tests/kernels/attention/test_cache.py`.

## Why this matters

The native `reshape_and_cache_nvfp4_dispatch` writer in `csrc/nvfp4_kv_cache_kernels.cu` stores K scales linearly and V scales in the 4x4 swizzle on every supported architecture. Main's test had selected linear V scales on SM120, conflating that native writer with FlashInfer's separate cache-update path. The reference now follows the native writer actually invoked by this test.

The relative-L2 bound supplements the existing elementwise check; neither tolerance is loosened. This catches structurally wrong scale ordering.

## Validation

RTX 5090 / SM120, Python 3.12, PyTorch 2.13.0+cu130. Reused the prior precompiled native extension. Its corresponding NVFP4 writer source differs from this base only in three include paths after the shared-header move; no native kernel modification is included in this PR.

```bash
.venv/bin/python -m pytest -q tests/kernels/attention/test_cache.py \
  -k 'test_reshape_and_cache_flash and nvfp4' --tb=short
# 24 passed, 264 skipped, 1008 deselected

.venv/bin/python -m pre_commit run --files tests/kernels/attention/test_cache.py
# passed, including mypy
```

Red/green evidence in the same environment:

- Unmodified main's first applicable case fails its elementwise V comparison (986/10752 mismatched elements, greatest absolute difference 24.875).
- Adding the stricter bound while retaining main's incorrect linear-V interpretation fails all 24 applicable cases; the first has relative L2 2.1458.
- Correcting only that reference to the native writer's swizzled V layout passes all 24 cases with the 0.15 bound intact.

The skips are existing dtype/layout/implementation guards. No SM100 hardware execution or model evaluation is claimed; this is test/reference code only.

## Non-duplicate rationale

Main absorbed the explicit dequantizer layout option, which is preserved rather than duplicated here. This remaining change fixes the native-writer test reference and adds the relative-L2 guard; it does not modify the separate FlashInfer SM12x implementation or reintroduce the runtime fix from closed #50085.

## Operational validation update from an eight-stream NVFP4-KV stack

A follow-up datapoint supporting the need for strict NVFP4 KV scale/layout validation. This is integration evidence from a combined SM120 stack, not an isolated run of this test-only PR.

Environment: RTX 5090 / SM120, Qwen3.8-27B NVFP4 weights, NVFP4 KV, MTP-3, CUDA 13, async scheduling.

- 8 GiB NVFP4 KV allocation produced a **373,797-token pool**
- FULL_AND_PIECEWISE graphs captured through the 32-token MTP-3/c8 shape
- 2.3 GiB remained free after graph capture
- Raw c8 decode reached **744.1 tok/s**
- A 57-second forced eight-active replay reached **857.4 tok/s**
- A real agent soak processed **1,461,705 prompt tokens + 33,230 generated tokens**
- Peak KV utilization was 81%; zero OOM, grammar/FSM, request, or visible output-corruption failures

The earlier failure signature on this route was catastrophic token-id-0 collapse from scale/layout mismatch, while this long mixed workload stayed clean. That is why I still think catching layout/scale assumptions in a small CPU-side regression test is valuable even when end-to-end SM120 CI is unavailable.

_Disclosure: AI-assisted analysis and comment posting; the runs and measurements were produced and verified by me on the hardware described._
