# [DSv4.1][BI] Bitwise batch invariance for DeepSeek-V4.1-Flash with CUDA graphs

[Upstream PR](https://github.com/vllm-project/vllm/pull/62365) · state: open · merged: False

## Original PR description

## Purpose

Make DeepSeek-V4.1-Flash inference bitwise batch invariant under `VLLM_BATCH_INVARIANT=1` with CUDA graphs on (FULL_AND_PIECEWISE), DEP4, DSpark MTP and MegaMoE. Under BI, token ids and logprobs are bitwise identical regardless of batch composition and order, chunk size, decode vs `prompt_logprobs` re-feed, prefix-cache hit vs miss and DP rank placement. Target is RL true on-policy rollouts.

BI=0 behavior is unchanged except for the DSv4.1 model fixes in the first commit (Engram stack entry, SWA block stride alignment, stale `-1` tail in combined indices).

## Changes (grouped)

1. **DSv4.1 fixes**: Engram stack entry, 32 B SWA block stride, combine index tails, replay-disable conditions.
2. **BI CUDA op library** (`csrc/batch_invariant/`): K32 block-scaled GEMM, fused SiLU-mul + group quant, deterministic radix top-k (larger index wins ties), sparse paged indices, SWA-first index combine, ordered expert permute/combine.
3. **Dense**: row-invariant BF16 / MXFP8 projections, RMSNorm, logits and logprobs.
4. **Attention**: FlashMLA sparse and indexer under BI. Every causal row (decode, spec verify, prefill, `prompt_logprobs` re-feed) runs in one call on the unsplit sparse decode kernel (`flash_mla_with_kvcache(enable_batch_invariant=True)`), reading the fp8 SWA and nvfp4 compressed caches directly; the BI CUDA op `sparse_paged_indices` derives each token's slots and lengths from (request, position) only. The opt-in mega attention keeps decode on its decode kernel and makes prefill match it (SWA-first layout, compressed length by position).
5. **Exact SWA bounded replay**: replay stays on but becomes exact under BI (decoder trimming keeps W+(n-1)(W-1) rows, prefix-hit replay recomputes W+L(W-1) tokens), optional layer-wise staging, padding rows masked.
6. **MoE**: MegaMoE under BI, ordered BF16 EP reduce-scatter + rank-order FP32 combine, router pinned, `empty_cache` before symmetric-memory allocation.
7. **mHC**: fixed split counts for every M, fused post+pre-norm kernel with warmup.
8. **DSpark**: draft rows and aux hidden-state capture under BI.
9. **Opt-in faster BI tiers** (`VLLM_BI_*`): tensor-core MXFP8/BF16 GEMM (non-split-K tactics only), MXFP8 prequant, startup precompile of every reachable M.
10. **Opt-in Mega tier**: Mega mHC with fixed split, split-mHC overlap side stream, mega attention under BI, Mega Gate in deterministic mode.

Opt-in tiers are bitwise batch invariant but round differently from the default BI path. A trainer that wants true on-policy must call the same kernels.

Thanks for putting the full DSv4.1 BI stack in one place. We built this branch (0ea532fdb) on GB200 and ran a BI=1 consistency matrix. One problem we can reproduce reliably: **very short prompts are not deterministic under `VLLM_BATCH_INVARIANT=1`**.

**Setup**
- Model: the first 4 decoder layers of DeepSeek-V4.1-Flash (release weights; the other layers are dropped). We use this as a small proxy model.
- 1× GB200, TP1/DP1, `kv_cache_dtype=nvfp4_ds_mla`, `attention_backend=FLASHMLA_SPARSE_DSV41`, `attention_config={"indexer_kv_dtype": "mxfp4", "indexer_sparse_logits": false}`, `moe_backend=deep_gemm`, chunked prefill on, `max_num_batched_tokens=8192`, `max_num_seqs=8`, `logprobs_mode=raw_logprobs`, `hf_overrides={"head_dtype": "float32"}`.
- Engram: `cpu_offload=true, embedding_across_dp=true, dp_shared_memory=false`.
- `VLLM_BATCH_INVARIANT=1`, every `VLLM_BI_*` left at its default. Also tried `VLLM_BI_BF16_GEMM=tensor_core` + `VLLM_BI_MHC_OVERLAP=1`.
- Prompts: random token ids with lengths 5, 131, 700, 2113, 4900; greedy, 24 new tokens each; also full-vocab logprobs and seeded sampling.

**Observation**
- Only the **5-token prompt** differs. Its first generated token (prefill) is already different, and every token after it diverges. Logprob deltas on the first token reach 0.05–0.66, and different runs pick different tokens.
- It shows up in eager, FULL_AND_PIECEWISE graphs, with prefix caching, and in mixed prefill/decode. It shows up both in a repeated identical single-request run and in batch / reversed-batch runs.
- All other prompts (131–4900 tokens) are bitwise identical across every scenario: batch, reversed batch, prefill vs decode, cache hit, mixed scheduling, FULL graph, full-vocab logprobs, sampling.
- Same result with the default BI tier and with the tensor-core + mHC-overlap tier.
- Our older BI branch for DSv4.1 is 0 diff on the identical script and prompts. That branch is based on 9e2b579aa and reuses the sparse-prefill index workspace after a host-side `fill_(-1)` reset, plus skips empty prefill chunks.

**Narrowing so far**
- With per-module forward hooks that copy each module's output to the CPU (this forces stream synchronization), 5-, 7- and 33-token prompts give identical outputs within one process and across processes. That points to a race or an uninitialized read that the synchronization hides, not a deterministic arithmetic difference.
- Our main suspect is the short-row path where the row length is below the indexer top-k: the BI top-k and the sparse index workspace tail (`-1` padding), or the compressed-KV / indexer cache tail for a sequence shorter than one compression block. The decode path in `flashmla.py` also has no `query_end == query_start` guard for empty chunks; our older branch needed one.

We are bisecting without hooks next and will post the first diverging tensor and a minimal fix if we find one. Happy to share the driver script.

Two updates on the report above.

**1. Correction: the short-prompt divergence is not a race.**
More probing changes the picture from my first comment:
- The 5-token prompt is fully deterministic in each mode on its own. Eager, `CUDA_LAUNCH_BLOCKING=1` and multi-stream disabled each give identical tokens over 12 runs. The PIECEWISE graph mode is also identical over 12 runs.
- The two modes disagree with each other: graph gives token 114044, eager gives 13265.
- Padding is not the cause. With capture sizes that include exactly 5 and 7 (no padding), graph mode still differs from eager, and its output is bitwise the same as with the default sizes, which pad to 8.
- Prompts longer than the capture range (131+ tokens) match eager.

So a prefill of ≤16 tokens that runs inside a breakable PIECEWISE graph computes something different from eager. We are now checking whether part of the per-step preparation (compressor state, KV insert, indexer preparation) is recorded into the piecewise graph and replayed with stale inputs, similar to #51430. I will post the first diverging tensor when we have it.

**2. A stream bug when the BI CuTe DSL GEMMs run on autograd backward threads.**
This matters for the true on-policy training use case this PR targets, where a trainer calls the same kernels in its backward. It is not specific to this PR; the code is the same on main.

`cute_dsl/_ll_router_common.py:current_cuda_stream()` gets the stream from `vllm.utils.torch_utils.current_stream()`. That cache only updates when Python calls `torch.cuda.set_stream`, and its docstring assumes nobody sets the stream from C++. The PyTorch autograd engine does exactly that on its backward threads. On those threads the CuTe kernels (`bf16_fixed_mm` K256 and the `ll_fp32w` / skinny paths) therefore launch on a stream that does not wait for their inputs.

On GB200, `bf16_fixed_mm` called inside an autograd backward:
- Before the fix: the second backward differs from a fp32 reference by rel **95.6**, and repeated runs are not bitwise equal.
- After the fix: repeated runs are bitwise equal, rel **1.66e-3** vs the fp32 reference (normal BF16 error).

Minimal fix we use:
```diff

+    # Ask torch, not vLLM's thread-local stream cache: the autograd engine sets
+    # the stream from C++ on its backward threads, which that cache misses.
     _, CUstream = cute_context()
-    from vllm.utils.torch_utils import current_stream
-
-    return CUstream(current_stream().cuda_stream)
+    return CUstream(torch.cuda.current_stream().cuda_stream)
```
`torch.cuda.current_stream()` costs a bit more per call than the cache. If that matters on the serving path, a variant that only falls back to torch when not on the thread that owns the cache would also work. DeepGEMM, FlashMLA and Triton launches are not affected.


- ISEEKYAN · comment · 2026-10-19T06:21:15Z · [source](https://github.com/vllm-project/vllm/pull/62365#issuecomment-6261029968)

Follow-up on the short-prompt divergence: we found the root cause. It is an import-order problem, and the fix is a small change to `eager_break_during_capture`.

**What happens**
- `eager_break_during_capture` (`vllm/compilation/breakable_cudagraph.py`, from #42304) checks `VLLM_USE_BREAKABLE_CUDAGRAPH` at **decoration time**. If the flag is off at that moment, it returns the undecorated function, so that function can never break out of a capture.
- With `VLLM_BATCH_INVARIANT=1` (and also in the generic auto-enable case), the flag is not set by the user. `VllmConfig` sets it in `os.environ` during its init (`_maybe_enable_breakable_cudagraph`).
- Before that, `ModelConfig` resolves the quantization config. On CUDA, `get_quantization_config()` runs `from vllm.models.deepseek_v41 import DeepseekV4FP8Config`, and the package `__init__` imports the whole model (`nvidia.vl_model` → `attention.py`, `engram.py`, ...). Every `@eager_break_during_capture` in DeepSeek-V4.1 is therefore evaluated while the flag is still off, and all of them become plain functions. An engine forked after this point inherits the same modules.
- The log shows the order: `Defaulting to tokenizer_mode='deepseek_v41'` comes first, then `Auto-enabling VLLM_USE_BREAKABLE_CUDAGRAPH=1`, then model loading.
- Result: a prefill batch that fits in the capture range (≤ `max_cudagraph_capture_size`) is dispatched to a PIECEWISE graph, but there is no eager break around `_sparse_indexer_and_attn`. Sparse attention and the indexer are recorded into the graph together with the host-side state of the capture batch (prefill chunk plan, `query_start_loc_cpu`, decode/prefill split), which is a dummy batch of one-token decodes. On replay the real prefill runs with that baked-in state. The output is deterministic but different from eager.
- Prompts longer than the capture range run eagerly and are unaffected, which matches what we saw (131+ tokens bitwise equal to eager; the 5-token prompt equal to eager when batched above the capture limit).

**How we narrowed it down** (4-layer proxy, 1×GB200, BI target tier as before)
- First diverging tensor: layer 2 (the first layer with compressed KV, ratio 2) attention output. Rows 1–4 differ and row 0 is equal. All of its inputs are bitwise equal: q, `fused_wqa_wkv`, `wq_b`, indexer q/scale/weights, and the valid rows of the compressor and `indexer.wk` outputs. Row 0 has no compressed entry to read.
- A wrapper on `forward_mqa` is called once per layer in eager and **zero times** in graph mode, so there is no eager break at all.
- `cudagraph_mode=FULL` (prefill stays eager) matches eager. Disabling multi-stream does not help. Forcing the wide `_prepare_and_attn_eager` region does not help either, because it uses the same decorator.
- Setting `VLLM_USE_BREAKABLE_CUDAGRAPH=1` explicitly before the process starts makes graph mode bitwise equal to eager:
  - 5- and 7-token prompts match eager in-process and in a multiprocess engine over 12 repeats (alone, after a 3000-token prompt, batched);
  - the C3 graph scenarios are all 0 diff.

**Fix we use** (decide the break at call time; without a capture the wrapper just calls the function, so eager numerics are unchanged):
```diff
--- a/vllm/compilation/breakable_cudagraph.py
+++ b/vllm/compilation/breakable_cudagraph.py
@@ -95,9 +95,10 @@ def eager_break_during_capture(fn: F) -> F:
         def unified_attention_with_output(...):
             ...
     """
-    if not is_breakable_cudagraph_enabled():
-        return fn
 
+    # Always wrap: VLLM_USE_BREAKABLE_CUDAGRAPH may be auto-enabled by the
+    # config after this module was imported. Without a capture the wrapper
+    # just calls ``fn``.
     @functools.wraps(fn)
     def wrapper(*args: Any, **kwargs: Any) -> Any:
         capture = BreakableCUDAGraphCapture.current()
```
Other possible fixes are making the quantization registry import only `vllm.models.deepseek_v41.quant_config`, or setting the flag before any model module is imported. The decorator change covers every model and every import path. `tests/kernels/test_engram.py` already works around the same import order ("imported Engram before breakable graphs were enabled").

- Same consistency matrix as in the first comment (graph / graph + prefix cache / eager / mixed prefill-decode; single, batch, reversed batch, prefill-vs-decode, cache hit; greedy token + raw logprob + top-5, full-vocab logprobs, seeded sampling), run with the fix and **without** setting the flag by hand (the log shows the config auto-enabling it): **every scenario is bitwise identical**. ## 3. Other findings worth reporting upstream

- **N1 — `f1ff0f034` sparse decode path.** That head routes all BI causal rows (prefill and decode) through the FlashMLA sparse **decode** kernel with `enable_batch_invariant`, removing the gather → prefill-kernel path used at `d667e410e`. For head64, the decode and prefill kernels are different CUDA kernels. The new test checks index metadata only; nothing checks that the old and new paths give the same bits. This affects training-side parity for anyone mirroring the sparse path. The mega path (#1) is unaffected.
- **N2 — Candidate-block selection above 16K uses DeepSelect with no batch-invariance guard** (`kernels/attention/dsa/candidate_blocks.py:181-213`).
  - When it applies: any prefill chunk that sees ≥ 16384 compressed positions on the candidate source layer, and **every decode step** once `max_model_len ≥ 16384` (decode logits are max_model_len wide).
  - What we measured: C3-style batch / prefill-vs-decode invariance at prompts up to 64K with `max_model_len` 65536 stayed bit-exact, with the DeepSelect path verified to execute (hundreds of calls, decode rows 1–8, i.e. both sides of DeepSelect's ≤6-row kernel switch).
  - Caveat: random-token prompts. Ties in block scores were not measured, so this is evidence, not proof. Long-context cases should be added to the PR's C3 test, which currently stops at 4.9K.
- **N3 — DeepInfer requires `max_model_len ≥ 16384` for DS4.1.** The candidate layer asserts `topk_blocks ≤ ceil(width / block_size)` with width = `runtime_max_model_len` (`v4_modules/index_attn.py:95,213,305`). vLLM falls back to `torch.topk` instead. For contexts < 16K both select all blocks, so this is not a parity issue, only a configuration constraint.
- **N4 — mega_mhc CUDA-graph race.** The race on the vLLM DeepGEMM pin is fixed upstream by `5081f851`. Until the pin moves, `VLLM_BI_MEGA_MHC=1` with CUDA graphs is unsafe.
- **N5 — DeepInfer build notes**, relevant if the PR author wants to reproduce:
  - FlashMLA `2e5429fc`'s post-build register-spill gate fails with nvcc 13.2 and 13.4 on four instances of `sm100::decode::sparse::head64::flash_fwd_splitkv_mla_fp8_sparse_kernel`. That non-fused kernel is not used by DS4.1 under BI; `FLASH_MLA_SKIP_REG_SPILL_CHECK=1` is FlashMLA's own opt-out.
  - The FlashMLA extension is not linked against `libcuda` (undefined `cuDriverGetVersion`); preload the driver library.

for ratio in (0, 1, 2):

                  else ((pos + 1) // ratio).clamp_max(k))
