# [Bugfix][DeepEPv2] Fix ElasticBuffer over-allocated by sp_size× under sequence parallelism

[Upstream PR](https://github.com/vllm-project/vllm/pull/59687) · state: open · merged: False

## Original PR description

## Overview

With sequence parallelism (TP>1, DP>1, EP), each EP rank only dispatches a `cdiv(max_num_batched_tokens, sp_size)` shard. Despite that, the DeepEP v2 `ElasticBuffer` is sized for the full `max_num_batched_tokens`, so it is over-allocated by `sp_size`×. This PR sizes the buffer for the shard. It also caps the per-step dispatch bound at the buffer capacity.

Follows #57210, which bounded the dispatch by `sp_size` but left the buffer sizing unchanged. Related: #57440.

## Claims

- Frees **~2.7 GiB per GPU** (ElasticBuffer 3.56 → 0.89 GiB) for KV cache on Kimi-K3 TP4×DP4×EP16 (B200). The saving is `(1 − 1/sp_size)` of the buffer and grows with `max_num_batched_tokens`.
- Fixes a latent overflow. The power-of-2 dispatch bound could exceed a non-power-of-2 buffer capacity and trip DeepEP's host assert. Example: mnbt 10240 with sp 4 gives capacity 2560 and bound 4096. The same holds for sp 1 with mnbt 10240.
- No numerics change. With real weights, 12/12 greedy prompts were identical, including top-20 logprobs.

## Validation

## Details

**Root cause**: `_do_dispatch` bounds each rank by `cdiv(max(num_tokens_across_dp), sp_size)` (#57210), but two places disagree with that bound:
1. `all2all_utils.py` created the `ElasticBuffer` with `num_max_tokens_per_rank=moe.max_num_tokens`, which is the unsharded count.
2. `_do_dispatch` rounded the bound up to a power of 2 without capping it at the capacity. This was harmless only while the buffer was oversized. It is also reachable at `sp_size=1`, since the bound is used for prefill whenever CUDA graphs are on.

**Fix**:
- Compute `max_tokens_per_rank = cdiv(moe.max_num_tokens, sp_size)` once. Pass it to both `ElasticBuffer` and `DeepEPV2PrepareAndFinalize`.
- Cap the rounded bound at `max_tokens_per_rank`.
- Raise a clear `ValueError` if a step exceeds the capacity, instead of hitting a DeepEP host assert.
- The capacity is passed in explicitly rather than read from DeepEP, because `ElasticBuffer.num_max_tokens_per_rank` is gone on DeepEP main.
- `do_expand=True` (eager) is unchanged.

**Notes**:
- *Hybrid mode*: DeepEP pads internally (`kNumMaxTokensPerChannel = ceil_div(num_max_tokens_per_rank, kNumChannels)`), so a capacity that is not a multiple of the channel count is fine.
- *Spec decode*: EAGLE/MTP/draft proposer inputs are sized to `max_num_batched_tokens`. DFlash is bounded by `max(max_num_seqs*(1+k), max_cudagraph_capture_size)`. If a config ever exceeds the capacity, it now gets the explicit error.
- *Other backends*: other all2all backends also size their buffers from `moe.max_num_tokens`. Whether the ones that support SP MoE need the same sharding is left for a follow-up.
- *Duplicate check*: I searched open PRs for `ElasticBuffer`, `num_max_tokens_per_rank` and DeepEPv2 + SP, and none changes the buffer sizing. #51589 (sync-less prefill dispatch) edits the same `_do_dispatch` block for a different purpose. Whichever lands second will need a rebase.
- *Related*: #57440 (fastsafetensors weight-loading memory not reclaimed) has the same symptom, forcing lower `max-num-seqs`/mnbt on DeepEP v2 + B200, but a different cause. The two fixes are independent; the real-weight runs above used `safetensors` to avoid it.
