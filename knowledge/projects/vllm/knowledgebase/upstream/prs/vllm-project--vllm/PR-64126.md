# [KV Offload] KV checksums for KV offloading connectors and the Mooncake store

[Upstream PR](https://github.com/vllm-project/vllm/pull/64126) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Check KV loaded back from KV offloading against checksums stored with it, and implement it for `MooncakeStoreConnector`. Each stored checksum is bound to the block it was stored for, so a value that is intact but belongs to another prefix fails the check like corrupted KV.

Stacked on #62211 (connector-agnostic KV checksums for P/D): the first commit adds the offloading contract to it, the second implements it for the Mooncake store. Review only the last two commits until #62211 merges.

## Claims

- With `enable_kv_checksum`, `MooncakeStoreConnector` stores each block's checksum with the block's KV, and every load from the store is checked against it, per block, with the same kernel and scheduler path as P/D loads.
- The stored checksum is XORed with a tag of the block's hash and its KV cache group's layers. The scheduler removes the tag that the request's own block hashes give for each position before it compares. KV at the wrong position or from another TP/PP shard already fails, as #62211 weighs every piece by its token position, head and layer; the tag adds a value stored for the same position of another prefix (another request's key, a reused or late-written value, e.g. kvcache-ai/Mooncake#4491) and a value stored by a model with other layers or dtypes.
- A failed check is a KV load failure (`kv_load_failure_policy`), and the failing blocks are removed from the store on every rank, so later requests do not load them again.
- Layouts that cannot carry the checksums (store TP sharding, non-full-attention groups, hash block size != block size, `custom_mem_pool`, HiSparse) are reported at startup instead of left silently unchecked.
- No change to P/D loads or to deployments with checksums disabled.

Out of scope: KV that never leaves the GPU (e.g. a kernel reading past a request's own blocks). These checksums only check KV that is loaded from elsewhere.

## Details

**Contract** (first commit). The checksum worker gives a connector a `(num_blocks,)` int64 device tensor (`init_block_checksums`) and fills the entries of full blocks before the connector offloads them (`save_block_checksums`). The connector passes each block's hash with it, moves a block's entry wherever it moves the block's KV, and writes it back before it reports the load finished. `get_kv_checksum_sources(request)` names the cache tiers whose loads bring the checksums back; such an asynchronous load is checksummed on its finishing step and compared per block by the scheduler. `on_kv_checksum_failure` lets the connector drop the bad KV.

**Why the tag.** A P/D load is checked against a reference that comes from the producer of the same request, separately from the KV, so KV from the wrong place cannot match it. An offloaded checksum travels with its KV, so on its own it only shows that a value is internally consistent. The checksum already depends on the token position, head and layer, so KV loaded at the wrong position or into another shard fails; what it cannot tell is whether the value at the right position belongs to this prefix. The tag (`block_checksum_tags`: `block_hash[:8] ^ group fingerprint`) binds the stored checksum to what the reader expects: the block hash covers the prefix tokens, LoRA, multimodal inputs and cache salt, and the fingerprint (from #62211) covers the group's layer names, types and dtypes. The scheduler derives the expected tag from `request.block_hashes`, not from the store. Leaving the rank out of the tag keeps replicas' stored checksums equal. P/D is unchanged. The tag adds no new requirement: cross-instance hits already need reproducible block hashes, since they are the store keys.

**Mooncake store** (second commit). The checksum tensor is registered with the store and appended as one more 8-byte region of every value, so put and get carry a block's entry with its KV and need no extra round trip. `wait_for_save` queues the checksums, with the blocks' hashes from the request, before the CUDA event the sending thread waits on. Keys are rank-local because each rank checks its own shard; values with checksums use a separate key namespace (`@kv_checksums`), so they never mix with values stored without one, at the cost of not reusing blocks stored before checksums were enabled. On failure, rank 0 runs `batch_remove(keys, force=True)` over the LookupKey channel (new `REMOVE_MSG`); force is needed because the failing load still holds a read lease.

**Size.** About 330 non-test lines in the first commit and 260 in the second, most of it the per-block plumbing in the checksum worker and scheduler and the Mooncake register/put/get/remove paths; the tag itself is about 30.

**Limitations.** Synchronous loads (`load_async=False`) are not checked; Mooncake store asserts asynchronous loads. This detects misplaced values; it does not fix their cause (kvcache-ai/Mooncake#4491 should be fixed in Mooncake).

**Not a duplicate.** #57912 adds CRC32C for the filesystem offload tier; this reuses #62211's GPU checksums and its scheduler path, and covers the Mooncake store.

- caikun-pjlab · comment · 2026-11-04T07:05:37Z · [source](https://github.com/vllm-project/vllm/pull/64126#issuecomment-6624840937)

Thanks for the checksum+tag design. It is a nice way to catch misplacement after the fact, and I appreciate the explicit limitation note.

One scenario from Mooncake Issue(https://github.com/kvcache-ai/Mooncake/issues/4491), I'm unsure this can catch: a batch_get times out, stored_requests[req_id] hits zero, and vLLM releases the KV block—but the underlying RDMA writes may still be in flight. If Request B then reuses that block, we have two concurrent writers to the same memory. Since the checksum is a post-hoc snapshot (computed after the producer considers the write "done"), it seems like a late-arriving write after that snapshot—or a checksum computed during the race—wouldn't be detected at the moment of concurrent write, only (maybe) by a future consumer.

So does this PR actually defend against this concurrent-write-to-the-same-block case, or is that outside what a post-hoc checksum can detect? If the latter, are there other mitigations (e.g., waiting for Mooncake's physical DRAINED state, or a write barrier like #62282 does for P2P), or is the real fix only on the Mooncake side as the limitations note suggests?
