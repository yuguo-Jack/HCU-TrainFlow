# [Perf][Model Loader] Auto-prefetch safetensors on VirtioFS

[Upstream PR](https://github.com/vllm-project/vllm/pull/51339) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

VirtioFS checkpoints currently require manual opt-in to the existing safetensors prefetch path. Include VirtioFS in the RAM-guarded automatic selection, while retaining explicit `lazy` as the opt-out.

## Claims

- Automatically prefetch VirtioFS safetensors when the checkpoint fits the existing 90% available-RAM guard.
- Preserve explicit load strategies and the existing prefetch implementation.
- Document that benefits depend on backing storage and guest page-cache topology.

## Validation

Automatic prefetch reduces real VirtioFS load time by about 11 times on B200, with the same generated text. GPU results used NVIDIA B200 GPUs with driver 580.95.05 and a precompiled build of main `b8c04dd3b4`, which this branch includes. The comparison tree is this branch with only the production files restored to main.

```sh
VLLM_TARGET_DEVICE=cpu HF_HUB_OFFLINE=1 \
  .venv/bin/python -m pytest tests/model_executor/test_weight_utils.py -q
```

```text
Without the change: FAILED tests/model_executor/test_weight_utils.py::test_auto_prefetch_selection[virtiofs]
With the change:    the file passes
```

The test controls filesystem and RAM discovery, checks strategy selection, and loads real safetensors values. It gives the same result with this branch merged onto main `410ab341a8`, with the same build, because no native code changed between the two commits. `test_ep_weight_filter.py` and the fastsafetensors and instanttensor loader tests also pass. `test_reload.py` passes with `VLLM_WORKER_MULTIPROC_METHOD=spawn`, except `test_reload_weights_with_lora_moe`, `test_kv_scale_reload`, and one `test_online_quantize_reload` case, which also fail on main on this host.

The load test used GLM-5.3-Flash-BF16 (598.52 GiB, 120 safetensors files) with TP=8 on one VM from a real `virtiofs` mount. Before each run, `posix_fadvise(POSIX_FADV_DONTNEED)` emptied the guest page cache, and `mincore` confirmed 0% residency. The table shows the `Loading weights took` log line. The first table ran on the same hardware against main `3a90cc6fd0`, before the latest commits on this branch, and this branch at `b8c04dd3b4` measured 72.96 s and 73.91 s with the default strategy and the same text.

| VM and order | Configuration | Strategy used | Load time |
| --- | --- | --- | --- |
| A, run 1 | Main, default | Lazy | 884.67 s |
| A, run 2 | This PR, default | Prefetch | 76.04 s |
| A, run 3 | This PR, explicit `lazy` | Lazy | 899.05 s |
| A, run 4 | This PR, default | Prefetch | 79.55 s |
| B, run 1 | This PR, default | Prefetch | 75.27 s |
| B, run 2 | Main, default | Lazy | 840.42 s |

Lazy stays slow after prefetch runs, and prefetch stays fast when it runs first, so the run order does not explain the result. Available RAM was about 1547 GiB, so the 90% guard allowed prefetch.

A real TP=16 engine across two VMs gives a smaller benefit, as the documented limitation predicts. Each run started with an empty guest page cache on both VMs.

| Configuration | Strategy used | Load time on VM A | Load time on VM B |
| --- | --- | --- | --- |
| This PR, default | Prefetch | 422.52 s | 639.67 s |
| This PR, explicit `lazy` | Lazy | 782.50 s | 1180.23 s |
| Main, default | Lazy | 795.97 s | 1163.85 s |

After the prefetch step, 53.2% and 47.8% of the checkpoint was resident on the two VMs, because each rank prefetches a share based on its global rank. The two-VM engine needed `VLLM_ALLREDUCE_USE_SYMM_MEM=0`, `VLLM_ALLREDUCE_USE_FLASHINFER=0`, and `--disable-custom-all-reduce`. Without them it hangs at engine startup on these hosts, before any weights load, which is unrelated to this change.

**Not validated:** The host-side VirtioFS cache could not be controlled, and these runs did not measure `cache=none` or DAX mounts. The 90% guard has only the focused unit test.

**CI coverage:** Only `(MI300) Model Executor` selects this test, because the NVIDIA model-executor step is commented out. ROCm was not run. The regressions of this PR also pass with this branch merged onto main `b2a9480dc7`, with its own precompiled build and `VLLM_WORKER_MULTIPROC_METHOD=spawn` as in CI. Upstream checks are stopped at contributor authorization, so Buildkite has not run this branch.

## Details

The change extends the existing filesystem allowlist rather than introducing a new loader. The RAM guard, cgroup-aware memory query, and explicit strategies are unchanged.

VirtioFS cache policy and backing storage vary, so filesystem type does not guarantee a speedup. Global-rank prefetch partitioning can leave each guest's separate cache only partly warmed in multi-VM deployments. This existing limitation is retained and documented in the generated configuration reference. The `eager` recommendation is unchanged, because this work measured only `lazy` and prefetch on VirtioFS.

This does not duplicate an open PR. No competing VirtioFS fix was found. Open #47412 and #52931 add CephFS to the same allowlist, so whichever lands second keeps both filesystems.

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Prefetch every shard within each VirtioFS guest**

When distributed ranks span multiple VMs using VirtioFS guest page caches, enabling this default does not warm the complete checkpoint on any VM: `_prefetch_all_checkpoints` partitions files using the global rank and world size, even though those page caches are not shared between guests, while every rank subsequently iterates all checkpoint files. Each guest therefore prefetches only roughly `1 / num_nodes` of the data and must still perform uncached reads for the remaining shards, potentially negating the startup improvement and adding redundant I/O. Partition prefetch work only among ranks that share a page cache, or prefetch all shards once per guest.

Useful? React with 👍 / 👎.
