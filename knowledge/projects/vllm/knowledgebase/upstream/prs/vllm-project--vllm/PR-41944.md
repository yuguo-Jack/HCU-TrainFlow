# Gemma4 KV-projection optimization: Remove redundant V projection on k_eq_v layers

[Upstream PR](https://github.com/vllm-project/vllm/pull/41944) · state: open · merged: False

## Original PR description

## Summary

This PR optimizes Gemma4 attention by removing the redundant V projection weight matrix on global-attention layers where `k_eq_v=True` (K and V share the same input). The optimization uses the existing `v_head_size=0` parameter in `QKVParallelLinear` to skip the V projection slot entirely, then derives V from the pre-norm K tensor via `v_norm(k_pre)` in the forward pass — mathematically identical to the prior approach of duplicating K weights into the V slot. This saves ~10% of QKV parameters per affected layer, yielding 2% overall QKV parameter reduction.

**Change scope**: Minimal and surgical — only `vllm/model_executor/models/gemma4.py` is modified; no changes to foundational linear layers.

The optimization applies to all full-attention layers that have `attention_k_eq_v=True` in the model config. On these layers, the V projection weight matrix is entirely eliminated. For Gemma4-31B and 26B-A4B, this saves ~10% of QKV parameters per full-attention layer, resulting in the observed **2.00% QKV parameter reduction**.

## Notes

- This optimization is Gemma4-specific and only affects layers where `attention_k_eq_v=True`
- Smaller Gemma4 models (E2B, E4B) have `attention_k_eq_v=False` and are unaffected
- The optimization is mathematically equivalent to the prior approach; all attention semantics are preserved
- No changes to foundational layers (`vllm/model_executor/layers/linear.py`); the optimization uses existing `v_head_size` parameter

- soby · comment · 2026-10-06T21:46:31Z · [source](https://github.com/vllm-project/vllm/pull/41944#issuecomment-6026046826)

This change also fixes a LoRA correctness bug on `k_eq_v` layers, which may help it get reviewed.

On `main` (and v0.31.0), `_gemma4_layer_weights_mapper` copies the base K weight into both the K and V shards of `qkv_proj` (`orig_to_new_stacked` `k -> [k, v]`). The LoRA path doesn't apply that stacking: `vllm/lora/worker_manager.py` builds its mapper with `hf_to_vllm_mapper.get_rename_mapper()`, which ignores stacking. A PEFT adapter on these layers has `q_proj`/`k_proj` but no `v_proj`, since transformers has `v_proj=None` there and computes `value_states = key_states`. So `_create_merged_loras_inplace` packs `[q, k, None]` and the V slice gets no delta.

transformers applies a `k_proj` LoRA delta to both K and V. vLLM applies it to K only, silently, on every global layer. For gemma-4-26B-A4B-it that's layers 5, 11, 17, 23 and 29; 31B is affected the same way. Any adapter that targets `k_proj` is served differently from how it was trained.

Deriving V from the K projection output, as this PR does, makes the `k_proj` LoRA delta reach V the same way it does in transformers. Until then, a workaround is to train without `k_proj` LoRA on `k_eq_v` layers, or to add a `v_proj` LoRA pair equal to the `k_proj` pair for those layers in a serving-only copy of the adapter.

In the `else` block for `is_kv_shared_layer`, the code assumes `v` is present in `qkv`. However, if `use_k_eq_v` is true, `qkv` only contains `[Q, K]` and `v` will be an empty tensor. For KV-shared layers, `K` and `V` are shared, so if `use_k_eq_v` is true, `v` should be set to `k` (or derived from `k`).

```python
v = qkv[..., self.q_size + self.kv_size :] if not self.use_k_eq_v else k
```
