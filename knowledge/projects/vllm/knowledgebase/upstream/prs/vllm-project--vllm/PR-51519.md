# [Perf] Add fused-MoE tuned configs for NVIDIA GeForce RTX 5090 (E=128, bf16, TP=1/TP=4)

[Upstream PR](https://github.com/vllm-project/vllm/pull/51519) · state: open · merged: False

## Original PR description

## Purpose

Requested in #48732: consumer Blackwell (RTX 5090, sm_120) has no fused-MoE tuned configs in-tree for any dtype, and MoE decode runs on default configs with the startup warning "Using default MoE config. Performance might be sub-optimal!". This PR contributes bf16 tuned configs for the Qwen3-30B-A3B / Qwen3-Omni-30B-A3B MoE geometry:

- `E=128,N=768,device_name=NVIDIA_GeForce_RTX_5090.json` (TP=1)
- `E=128,N=192,device_name=NVIDIA_GeForce_RTX_5090.json` (TP=4, the reporter's serving layout)

Tuned with `benchmarks/kernels/benchmark_moe.py --tune` on a single RTX 5090, driver 580.173.02, torch 2.11.0+cu130, triton 3.6.0, otherwise-idle card, 18 batch sizes (1 to 4096) per config.

It also hardens the tuner for this hardware class: on sm_120, certain candidate configs crash Triton compilation itself (`RuntimeError: PassManager::run failed` from `make_ttgir`) rather than raising `triton.runtime.autotuner.OutOfResources`, which aborted the whole tune. The added guard skips those candidates like any other invalid config. Without it, `--tune` cannot complete on this GPU for these shapes.

## Test Plan

- Both JSONs produced by the in-tree tuner on the target hardware; `triton_version` stamped in each file.
- Config pickup verified on the target device: with the files installed, `get_moe_configs(E=128, N=768)` and `get_moe_configs(E=128, N=192)` both resolve to the tuned tables (18 batch-size entries each) on an RTX 5090 running vLLM 0.26.0.
- @qqq-tao offered in #48732 to benchmark contributed configs on their 8x RTX 5090 production workload; end-to-end before/after numbers from that rig would be the strongest validation and we would welcome them on this PR.

## Test Result

Tuner-internal timings selected the best of ~1.9k candidate configs per batch size. No end-to-end serving numbers from this side: the tuning host is a single 32 GB card, and the target workload in #48732 is TP=4 across 8 GPUs.

- manunicholasjacob · comment · 2026-11-02T03:06:41Z · [source](https://github.com/vllm-project/vllm/pull/51519#issuecomment-6568064536)

Heads up that the `except RuntimeError` hunk has since landed on main, so this PR may be carrying it unnecessarily.

It came in on 2026-10-20 as part of #41197 ("[ROCm][benchmark][perf] fix moe tuning script for RDNA"), commit `4a30738d2`, and first shipped in v0.33.0. Current main:

```python
                except triton.runtime.autotuner.OutOfResources:
                    # Some configurations may be invalid and fail to compile.
                    continue
                except RuntimeError as e:
                    logger.warning("Skipping config %s: %s", config, e)
                    continue
```

The two are not equivalent, which is worth deciding on explicitly rather than resolving as a conflict:

- main continues on **any** `RuntimeError` and logs the config it skipped.
- this PR continues only when the message contains `PassManager::run failed`, and re-raises anything else.

Yours is the tighter guard, since main's will now also swallow an unrelated `RuntimeError` from a config that was otherwise fine. Main's does tell you which configs were dropped, which this one does not.

Either way it is a separate argument from the tuned configs. If you drop the handler hunk, this becomes two config files and should go in easily; if you think the narrow guard is the right behaviour, that is worth raising against #41197's version on its own rather than inside a configs PR.

Context for why it matters here: this is the same abort as #37191, which has been open since May with people hitting it on 0.20 through 0.32.
