# [Rust Frontend] Report the engine's VllmConfig in /server_info

[Upstream PR](https://github.com/vllm-project/vllm/pull/63765) · state: closed · merged: True

## Original PR description

## Overview

Python's `GET /server_info` (dev mode) returns the API server's `VllmConfig`, synced from every engine's ready response. The Rust frontend returns its own frontend `Config` under the same key, which has no `model_config`, `cache_config` or `parallel_config`, so the DP `server_info` tests (`v1/distributed/test_{internal,external,hybrid}_lb_dp.py -k server_info`) fail under Rust with `KeyError: 'parallel_config'`. This PR has each engine send its `VllmConfig` dump in the ready response (dev mode only), and the Rust `/server_info` reports it with the API-server view applied.

## Claims

- Under the Rust frontend, `/server_info` returns `vllm_config` in the shape Python returns, with the fields Python's API server derives from its engines (`data_parallel_size`, summed `num_gpu_blocks`, minimum `max_model_len`, common `effective_attention_block_size`, `_api_process_count`/`_api_process_rank`).
- The Rust frontend's own config moves to a separate `rust_frontend_config` key.
- Outside `VLLM_SERVER_DEV_MODE`, engines do no extra work: the ready-response field stays `None`.

## Details

Rust has no `VllmConfig` of its own. A Python launcher could pass one at startup, but `vllm-rs serve` launches the Python engine itself, and remote headless engines have no launcher on the frontend's node. Every engine already sends `EngineCoreReadyResponse` for post-initialization config (`max_model_len` after auto-fit, `num_gpu_blocks` after profiling), so the config travels there.

- Python engine (`vllm/v1/engine/__init__.py`, `core.py`): `EngineCoreReadyResponse` gets a trailing `vllm_config: dict[str, Any] | None = None`. `_make_ready_response` fills it with the same JSON-mode dump Python's `/server_info` uses, only when `VLLM_SERVER_DEV_MODE` is set. The struct is a msgpack map, so an older peer on either side ignores or defaults the key. The Python client ignores it.
- Rust protocol (`engine-core-client`): the matching `#[serde(default)] vllm_config: Option<serde_json::Value>`; the Python fixture and the key-drift test cover it.
- Rust `/server_info` (`server/src/server_info.rs`): `ServerInfoSnapshot::from_engine` takes the first engine's dump and replaces the fields Python reports from the API server's view, because each engine reports its own values:

  | Field | Value | Source |
  |---|---|---|
  | `parallel_config._api_process_count`, `_api_process_rank` | 1, 0 | the Rust frontend is the only API process |
  | `parallel_config.data_parallel_size`, `data_parallel_rank` | deployment size, first engine's rank | same as the gRPC `GetServerInfo` parallelism view |
  | `cache_config.num_gpu_blocks` | sum over engines | `total_num_gpu_blocks()`, as Python sums |
  | `cache_config.effective_attention_block_size` | the common value, or `null` if engines differ | as Python |
  | `model_config.max_model_len` | minimum over engines | `max_model_len()`, as Python |

  An engine that sends no dump (a remote headless engine started without `VLLM_SERVER_DEV_MODE`, or an older engine) gives `vllm_config: null`. Engines started by `vllm serve` or `vllm-rs serve` inherit the frontend's environment, so in dev mode they always send it.
- The Rust frontend `Config`, which shares none of `VllmConfig`'s structure, is reported as `rust_frontend_config`. `config_format=text` renders both with the existing Rust renderer, not Python's `str(VllmConfig)`.

The engine owns the config and only serializes it; the frontend view belongs to the Rust server's `/server_info` snapshot, next to the gRPC server-info view it mirrors.

Remaining differences, unchanged here:

- `--api-server-count N` cases expect N API processes; the Rust frontend runs one.
- Per-engine fields that Python's API server does not sync (for example `data_parallel_rank_local`, `data_parallel_index`) show the first engine's values. So does `data_parallel_size_local`: the frontend knows how many engines it connects to, not how many run on its node.
- `system_env` stays the Rust subset (`arch`, `family`, `os`).

Not a duplicate: no open PR changes `/server_info` on the Rust frontend.
