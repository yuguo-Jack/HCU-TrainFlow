# [ROCm][Perf][MiniMax-M3.1] Score DSpark 7 decode locally below 3 requests instead of via indexer CP

[Upstream PR](https://github.com/vllm-project/vllm/pull/65432) · state: closed · merged: True

## Original PR description


## Purpose

With `indexer_decode_cp` at TP4 (#64448), every DSpark 7 decode step scores through the context-parallel
push kernel (`m3_nvfp4_index_score_push_cp`), whatever the batch size. Its two cross-rank handshakes (index-q
exchange, then score push plus a four-rank done barrier) cost a fixed ~13 us per layer that does not shrink with
the batch, so at 1-2 requests the kernel spends its time waiting, while the single-head scorer
(`m3_nvfp4_index_score_decode_r8h1`, each rank scores its own head over the whole context, no cross-rank traffic)
takes 6-9 us. This PR scores steps of fewer than `CP_MIN_REQS = 3` requests (8 rows each) with the single-head
scorer, which is the path the scorer already takes when CP is off. Steps of 3 or more requests, and DSpark 3 (4 rows
per request), are unchanged.

Not covered by an existing PR: #64448 (merged) enables CP for DSpark 7 at any batch size; #65087/#65267 only touch the top-k.

## Root cause (kernel level)

Per-layer kernel durations from the torch profiler (rank 0, 120 decode steps per window, 150K-token real-text
contexts, DBO off, `VLLM_ROCM_USE_SKINNY_GEMM=0`), before / after this change:

| N requests | scorer before | scorer after |
|---|---|---|
| 1 | `m3_nvfp4_index_score_push_cp` 15.8 us avg (p50 13.0) | `m3_nvfp4_index_score_decode_r8h1` 7.0 us |
| 2 | `m3_nvfp4_index_score_push_cp` 14.9 us avg (p50 13.3) | `m3_nvfp4_index_score_decode_r8h1` 9.7 us |

(58 sparse layers per step: 0.92 -> 0.41 ms/step at N=1 and 0.87 -> 0.57 ms/step at N=2.)

CP is a fixed ~14-15 us up to 4 requests; the single-head scorer grows with the pages it reads (one head, all
blocks) and loses once a step reads ~4-5K index pages in total (4 requests at 150K, 2-3 at 400K). The gate is on the
request count because under CUDA graphs `max_seq_len` is the model maximum, so the batch's context is not known when
the graph is captured. 3 requests at 150K would also win (11.3 vs 14.5 us) but loses at 400K (17.6 vs 15.4 us) and
showed no end-to-end gain, so the gate stops at 2 requests.

## Correctness

* The scorer is not changed. The scores of the CP kernel and the single-head scorer are bit-identical (existing
  `test_index_decode_cp_push_matches_single_head` and the 28-cell sweep above), so the top-k ids and the attention
  output are bit-identical to the CP path: this change only picks which of the two bit-identical scorers runs.
* New `test_decode_cp_gate` (8 cases, unit test of `_decode_cp`).
* `pytest tests/kernels/attention/test_minimax_m3_nvfp4_index.py`: 182 passed (174 existing + 8 new) on MI355X.
* End-to-end sanity: "What is 17*23?" answers 391 at TP4 on a tree with this change (stacked with #65087 and a
  split-count change; greedy; the synthetic-acceptance recipe garbles some of the surrounding text with or without them).

## Limitations

* Measured at 150K contexts (and 30K-800K in the isolated sweep) on MI355X, TP4, DSpark 7 only. DSpark 3 keeps
  CP at every batch size; the crossover for 4-row requests was not measured.
* The gate is conservative for short contexts: at 30K the single-head scorer also wins at 3-16 requests (4 requests 7.0 vs
  14.8 us, 16 requests 13.3 vs 15.8 us). A context-aware choice would need it inside the kernel or two graphs per batch size.
* Requests of ~800K tokens or more at 1-2 requests are slower with the single-head scorer than with CP (800K:
  16.4 vs 14.9 us at 1 request, 23.7 vs 18.4 us at 2). Contexts that long are rare in the target agentic workload
  (30K-500K, mean ~150K).
* DBO on (the recipe): not measured for this change alone. Decode steps do not split under the recipe thresholds, so
  CP is used outside microbatches exactly as before; stacked with two other changes the step was 2-8% lower at N=1..16.
* Server-to-server variation of the decode step is +-0.6% within one machine state; the shared machine also had
  MoE kernel changes land between runs, so only runs from a frozen copy of the install (same state) are compared.

Related: #64448 (DSpark 7 CP), #57909 (indexer CP), #65087 (top-k, independent).
