# [XPU][Quantization] Support asymmetric (sym=false) GPTQ int4 linear layers on XPU

[Upstream PR](https://github.com/vllm-project/vllm/pull/61731) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Allow asymmetric (`sym: false`) 4-bit GPTQ checkpoints for linear layers on XPU. Today `AutoGPTQConfig` raises `Unsupported quantization config: bits=4, sym=False` on every platform, although the XPU WNA16 kernel (`int4_gemm_w4a16`) already takes zero points (the compressed-tensors and AWQ asym paths use it).

Not a duplicate: open PRs searched for `gptq asym`, `gptq sym xpu` and "asymmetric GPTQ XPU". The only nearby open PRs are #53643 (tests for the Triton qzeros reshape), #39475 (MTP vs moe_wna16) and #32899 (CT W4A16 MoE on XPU); none enables GPTQ `sym=false` on XPU. No open issue covers this.

## Claims

- Asymmetric GPTQ int4 linear layers load and serve on XPU. CUDA/ROCm and symmetric GPTQ are unchanged.
- Per-module `dynamic` rules (e.g. GPTQModel's `-:.*mtp.*`) accept the same `(bits, sym)` as the base config.
- Asymmetric GPTQ MoE experts raise a clear `NotImplementedError` instead of reaching an untested path.

## Validation

CPU unit tests, which run in CI:

```
pytest tests/quantization/test_gptq_asym_zeros.py   # 7 passed
```

They cover the qzeros layout, the v1 (`z - 1`) and v2 offsets, no carry at z = 0, config plus `dynamic` overrides on XPU, and rejection off XPU. Without the `override_config` change, the 3 dynamic-rule tests fail with the same ValueError the real checkpoint hit.

End to end on an Intel Arc Pro B70 (32 GB), `vllm/vllm-openai-xpu:v0.31.0` with this patch, eager, 16K context, greedy, serving [darioooooo0o/Qwen3.8-27B-GPTQ-Int4-asym](https://huggingface.co/darioooooo0o/Qwen3.8-27B-GPTQ-Int4-asym) (`sym: false`, `checkpoint_format: gptq`, `dynamic: {"-:.*mtp.*": {}}`):

| arm | result |
|---|---|
| unpatched v0.31.0 | `ValueError: Unsupported quantization config: bits=4, sym=False` at config validation |
| this patch | loads and serves; canary OK; greedy outputs of a 100-prompt arithmetic battery **byte-identical** (`cmp`) to the reference loader |
| reference loader (out-of-tree patch, validated against BF16: KL 0.039) | 51/100 on the battery, the same as this patch |

On the real checkpoint, the converted zero points are also bit-identical to the reference loader (25 qzeros tensors from layers 0-3, 0 differing elements).

CI coverage gap: CI has no XPU runner with this checkpoint, so the end-to-end path is validated only by the B70 run above.

## Details

- `AutoGPTQConfig.get_quant_type()` maps `(4, sym=False)` to `uint4` only on XPU (`XPU_ASYM_TYPE_MAP`). `__init__` and `override_config` both use it. An earlier revision changed only `__init__` and failed at load on this checkpoint, because its `dynamic` rule sends every layer through `override_config`.
- `AutoGPTQLinearMethod` passes `zero_points=not is_sym` / `has_zp` to the kernel config and the support check.
- `gptq_qzeros_to_standard_format()` converts GPTQ qzeros `(G, N // 8)` to raw zero points in the `(N // 8, G)` layout that `_convert_awq_to_standard_format` already produces for AWQ, so `XPUwNa16LinearKernel`'s existing zero-point transpose yields the right tensor and `xpu.py` is untouched. The v1 `z - 1` offset is undone per element (mod 16), so it never carries into the neighbouring value. `checkpoint_format`/`format` = `gptq_v2` (raw z) is respected. It is a separate function, although it has one call site, so the tests can check the layout directly.
- The tests monkeypatch `current_platform.is_xpu`, so the XPU branch is covered on CPU-only CI.
- Limitation: linear layers only; MoE experts with `sym=false` are rejected explicitly.
- Motivation: on Qwen3.8-27B an asymmetric GPTQ quant with MSE clipping reaches KL 0.039 vs BF16, against 0.069-0.078 for the symmetric GPTQ exports we compared. Part of that gap is the clipping, not only the zero points.
