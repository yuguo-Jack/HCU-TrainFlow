# [Bugfix] Create cuBLAS handles before memory profiling to avoid OOM

[Upstream PR](https://github.com/vllm-project/vllm/pull/61044) · state: closed · merged: True

## Original PR description

Fix https://github.com/pytorch/pytorch/issues/199944
Purpose
On small GPUs (e.g. an H200 35GB MIG slice), engine startup can fail during the memory profiling run with:
```
RuntimeError: CUDA error: CUBLAS_STATUS_ALLOC_FAILED when calling `cublasCreate(handle)`
```
This was seen in tests/v1/e2e/general/test_kv_sharing_fast_prefill.py with google/gemma-3n-E2B-it on torch 2.14.1 and the 2.15.0 RC (pytorch/pytorch#199944).

### Root cause

cuBLAS(Lt) asks CUDA for its handle memory directly. When torch's own cudaMalloc fails, torch frees its unused cache and retries, but a cuBLAS request never triggers that because torch doesn't see it. Profiling can grow torch's cache until the GPU is full, and the first cuBLAS call then fails even though torch holds idle memory it could have given back.
In this case:

- Loading weights does no matmuls, so the first cuBLAS call in the process happens inside profile_run, at the gemma3n vision projection. That call creates the handle.
- By then, torch had reserved 29.5 GiB, while live tensors peaked at 21.9 GiB. That left 0.04 GiB free on the device, and cublasCreate failed with about 19 GiB sitting unused in torch's cache.
- The scoped max_split_size_mb:20 from #58430 makes this more likely, adding about 2.9 GiB of reserved memory during profiling.

### Fix

Create the handles while memory is still free. At the start of Worker.determine_available_memory, call torch.cuda.current_blas_handle() and run one tiny linear with a bias, which also sets up cuBLASLt. Every GEMM during profiling then reuses the existing handles, so profiling needs no allocations outside torch's allocator.

The handles are created after init_snapshot, so their memory is still counted in total_consumed and comes out of the KV-cache budget as before. In the repro the KV cache was about 0.1 GiB smaller, which is the handle cost.

### Test Result

Without fix (2 runs) | FAIL ×2, CUBLAS_STATUS_ALLOC_FAILED | 29.52 / 0.04 GiB
With fix (4 runs) | PASS ×4 | 29.43 / 0.07 GiB

Both parametrizations (`[1]` and `[None]`) fail:

```
        if current_platform.is_cuda_alike():
            ...
            torch.cuda.current_blas_handle()
>           x = torch.ones(16, 16, dtype=self.model_config.dtype, device=self.device)
E           AttributeError: 'types.SimpleNamespace' object has no attribute 'model_config'
```

The test builds a fake worker with `SimpleNamespace(cache_config=..., model_runner=..., init_snapshot=...)` (`tests/v1/worker/test_gpu_worker.py:218`) and calls `determine_available_memory` on it. The new warmup block reads `self.model_config.dtype` and `self.device`, which the fake worker doesn't define. It fails on ROCm too, because `is_cuda_alike()` is true there.

Two possible fixes:
- Add `model_config=SimpleNamespace(dtype=torch.float16)` and a `device` to the fake worker in the test.
- Or don't depend on the model dtype in the warmup. Any dtype creates the cuBLAS/cuBLASLt handles, so a fixed `torch.float16`/`bfloat16` tensor on `torch.cuda.current_device()` would work and keep the warmup independent of worker state.

- njhill · comment · 2026-10-13T00:36:05Z · [source](https://github.com/vllm-project/vllm/pull/61044#discussion_r4253576345)

File: `vllm/v1/worker/gpu_worker.py` · line None

Would it make more sense to do this once in `init_device`, right after `torch.cuda.set_device` and before the `init_snapshot` is taken? That way it runs on every startup path (e.g. the elastic EP scale-up path skips `determine_available_memory` entirely), and the handle/workspace memory gets cleanly accounted as part of the baseline rather than showing up inside the profiling window.

Also worth noting this only pre-empts the specific allocations triggered here. Any later cuBLAS handle/workspace allocation that bypasses torch's allocator (e.g. a handle for a new thread/stream, or a library like DeepGEMM's cuBLASLt path) could still hit the same failure, since torch's cache won't be released for it.

- njhill · comment · 2026-10-13T00:36:05Z · [source](https://github.com/vllm-project/vllm/pull/61044#discussion_r4253576348)

File: `vllm/v1/worker/gpu_worker.py` · line None

An fp16 `linear` with a 1D bias only exercises the cuBLASLt fp16 path. Depending on dtype and config, the model's actual GEMMs may go through a different backend that still lazily allocates its handle/workspace later, e.g. bf16/fp8, non-Lt `cublasGemmEx` (no bias, or `DISABLE_ADDMM_CUDA_LT=1`), an overridden `preferred_blas_library` (`batch_invariant.py` sets cublaslt), or hipBLASLt on ROCm. Might be worth using the model dtype and/or covering both the Lt and non-Lt paths.
