# [Rust Frontend] Match Python union-type coercion precedence

[Upstream PR](https://github.com/vllm-project/vllm/pull/47203) · state: open · merged: False

## Original PR description

## Summary

The Rust tool-call argument converter resolved union (`anyOf` / `["a","b"]`) types by **schema declaration order**, while Python's canonical `coerce_to_schema_type` (driven by `ParserEngine`) uses a **fixed precedence**: `null > integer > number > boolean > object > array > string`.

This made, e.g., a `["string", "integer"]` parameter coerce `"42"` to the string `"42"` in Rust but the integer `42` in Python — a real argument-type divergence for any tool whose schema uses a type union.

This PR:

1. Orders union members by Python's fixed precedence so **both** declaration orders agree with Python (`["integer","string"]` and `["string","integer"]` both yield `42`).
2. Fixes a related null case left open by #46827. That PR kept literal `"null"` a string for **bare** `string`-typed params (guard: `param_type != Some(&String)`), but a `["string","integer"]` union is not the bare `String` type, so the guard still fired and turned `"null"` into JSON `null`. Python keeps it the string `"null"` whenever a `string` member is admissible. The guard now checks `admits_string` (a bare `string` **or** a union containing one), extending #46827's fix to unions.
3. Adds a **differential property test** that ports `coerce_to_schema_type` as an oracle and fuzzes `(value, types)` pairs, pinning the parity mechanically rather than with hand-written assertions.

## Why this is not duplicating an existing PR

No open PR addresses Rust union-type coercion precedence (searched open PRs for "union coercion precedence" and for issue #47179 references). The null portion is the natural follow-on to the **merged** #46827, which handled bare `string`-typed `"null"` but did not cover unions; this PR extends that same guard to `OneOf` members rather than re-doing it. This is a follow-up to the discussion in #47179 about Rust↔Python tool-parser divergences; it implements the coercion divergence that was verified against the canonical Python path, in the direction (match Python) confirmed by maintainers in that thread.

Thanks @BugenZhao and @chatgpt-codex-connector — all three points addressed in c96072cd6.

**1. Flatten nested unions before ranking.** You were right: `precedence_rank` ranked a nested `OneOf` last (7), so for `anyOf: [{"type":"string"}, {"type":["integer","null"]}]` the sibling `string` was tried before the parser descended into the nested union, leaving `"42"`→`"42"` and `"null"`→`"null"`. Python's `extract_types_from_schema` recursively flattens `anyOf`/`oneOf`/`allOf` into a flat type set first, so it yields `42` and `null`. Added `flatten_union_members` (recursive) which runs before the precedence sort, so every leaf competes at its own rank.

**2. `null` for `string | null`.** This is the same flatten gap in its nested form. Verified against the **live** Python `coerce_to_schema_type`:
- flat `["string","null"]` on `"null"` → `null`, on `"42"` → `"42"` (no integer member)
- nested `[string,[integer,null]]` on `"42"` → `42`, on `"null"` → `null`, on `"3.14"` → `"3.14"` (no number member)

The fix now matches Python on all of these, and still keeps `["integer","string"]`/`"null"` → `"null"` (no regression to #46827, where no `null` member is admissible).

**3. Pin explicit cases, don't rely only on the ported oracle.** Agreed the oracle can drift. Added two explicit pinning tests (`nested_union_flattens_before_precedence`, `string_or_null_union_coerces_literal_null`) with the expected values copied from live Python. I also extended the differential proptest to generate nested `anyOf` layouts (not just flat `type: [...]`) — and confirmed that proptest **fails** on a reverted no-flatten version, so it's a real regression guard for this exact bug.
