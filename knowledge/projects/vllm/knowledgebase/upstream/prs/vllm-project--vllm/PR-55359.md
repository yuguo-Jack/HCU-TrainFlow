# feat(pooling): load Sentence Transformers CrossEncoder heads

[Upstream PR](https://github.com/vllm-project/vllm/pull/55359) · state: open · merged: False

## Original PR description

## Purpose

Closes #54981.

Sentence Transformers can serialize CrossEncoders as explicit module stacks, but vLLM does not currently reconstruct the Transformer → Pooling → Dense layout. The saved pooling behavior and trained Dense scoring head therefore require custom code or manual configuration.

This PR adds bounded support for that exact layout:

- maps cls, mean, and lasttoken pooling to vLLM
- loads the saved Dense weights, bias, and activation
- supports structured text and multimodal query-document messages using the saved chat template
- uses the explicit multimodal text configuration when selecting bidirectional attention
- rejects unsupported pooled configurations rather than silently changing their semantics
- leaves existing non-pooled sequence-classification and CausalLM plus LogitScore paths unchanged

- tomaarsen · COMMENTED · 2026-09-18T11:32:34Z · [source](https://github.com/vllm-project/vllm/pull/55359#pullrequestreview-5247298008)

From the Sentence Transformers side, I’m supportive of this approach. Transformer -> Pooling -> Dense is a valid and very reasonable CrossEncoder layout that gives a lot of flexibility with e.g. multimodality in ST. Overall, I'm a big fan of the ST data being parsed and loaded directly, so both vLLM and ST work from the same checkpoint. I also think it's smart to read `modules.json` like you're doing and explicitly reject unsupported ST module configurations (i.e. that don't map to anything meaningful in vLLM at this time). It's also smart to check the `transformer_config` to make sure its a `feature-extraction` ('base model') variant.

I believe the other common variant, just a Transformer except it's a `sequence-classification` variant, is also still supported via the `config.json` where it recognizes the `transformers` classification head.

And then another common format, Transformer -> LogitScore (with the Transformer as a `text-generation` or `any-to-any` variant) is explicitly not implemented here yet, which is okay. That setup 'generates' the logits for the next token, and then either grabs the logits of a specific token ID (e.g. for "yes" or "1") or subtracts the logits of 2 specific token IDs (e.g. "yes" - "no" or "1" - "0") to produce a score.

Lastly, the reported multimodal parity check would probably work well as an integration test. The tests that save a model with Sentence Transformers, load it in vLLM, and compare the scores are a good setup in my opinion.

cc @hmellor as I know you've been interested in easier embedding model deployment as well. Sentence Transformers is really just transformers with some extra small layers on top (dense, pooling, normalize, etc.). It's pretty accessible for vLLM I think.

- tomaarsen · comment · 2026-09-18T12:15:44Z · [source](https://github.com/vllm-project/vllm/pull/55359#discussion_r4046621142)

File: `vllm/model_executor/models/transformers/base.py` · line 699

This is a relatively common "magic field" added in Transformers v5.2.0: https://github.com/huggingface/transformers/pull/43705
In short, decorators in `transformers` will pass the config `is_causal` to the attention module and mask creation. It turns the mask bidirectional, as you might've expected. Embedding models and rerankers get a pretty consistent 1-2% improvement with bidirectional attention at a low cost (after all, you can't reuse KV caches with embeddings/rerankers anyways), so I think the majority of new embedding/reranker models are bidirectional (probably still 30-40% of new models just stick with the original causal backbone though).
