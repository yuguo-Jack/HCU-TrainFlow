# [Rust Frontend] Detect Lark grammars like the Python engine

[Upstream PR](https://github.com/vllm-project/vllm/pull/63709) · state: closed · merged: True

## Original PR description



## Overview

The Rust frontend's `answer_format` decides whether a request's `structured_outputs.grammar` is XGrammar EBNF, and so can be composed into a parser-built output grammar, or another syntax such as Lark, which stays on its own wire field. It treated any grammar containing `::=` as EBNF. This ports Python's `grammar_is_likely_lark`, which the engine's xgrammar backend also uses for a grammar left on its wire field, so both frontends and the engine agree on a grammar's syntax.

## Claims

- A Lark grammar whose comment mentions `::=` (e.g. `// Like root ::= "a" in EBNF.`) is no longer composed as an EBNF `grammar` leaf, which XGrammar fails to compile. It stays on its wire field, where the engine compiles it as Lark, as it would for the same request on the Python frontend's native path.
- An EBNF grammar with `#` or `//` comments is still composed.

## Validation

- `cargo nextest run -p vllm-chat --lib`: 427 passed; `cargo clippy -p vllm-chat --all-targets -- -D warnings` and `cargo fmt --check` clean.
- Red-green: with the old `contains("::=")` rule restored, `answer_format_leaves_other_constraints_on_their_wire_field` fails on the new Lark-with-comment case (`left: Some(Grammar(..))`, `right: None`).
- Differential against Python's `grammar_is_likely_lark` source on 15 inputs (empty, comments with `#`/`//`, `#` or `//` inside string literals, tabs, `\r\n`, `::=` inside a Lark string literal): no mismatch.
- XGrammar 0.2.8, for the misclassified input: as an EBNF `grammar` leaf inside a structural tag it fails (`EBNF lexer error at line 1, column 1: Unexpected character: /`); through `Grammar.from_lark`, the engine's path for a native Lark grammar, it compiles.
- No model run: the change only selects between two existing paths, both covered by the tests above.

## Details

- The rule is Python's, line by line: a grammar is Lark unless some line, before its first `#` or `//`, contains `::=`; an empty grammar counts as EBNF. Python's comment stripping also cuts at `#` or `//` inside string literals; it is kept as is, because the point is to match the engine's own classification of the same string, not to improve on it on one side.
- Out of scope: a Lark grammar still cannot be composed on Rust, because XGrammar's structural-tag `grammar` leaf accepts only EBNF and Rust has no counterpart of Python's `Grammar.from_lark` conversion. That limitation predates this PR (vllm-project/vllm#60781) and is unchanged here.
- Not a duplicate: no open PR touches Rust Lark detection.
