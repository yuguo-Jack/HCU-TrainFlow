# [ROCm][Docker] Shrink the ROCm release image

[Upstream PR](https://github.com/vllm-project/vllm/pull/60890) · state: closed · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Shrink the ROCm release image (`vllm/vllm-openai-rocm`) by keeping pip's download cache, build-only apt packages, and triton debug info out of it. Rebased onto the TheRock-based ROCm 10 base image (#58761, #62276).

## Claims

- Compressed release image size: **18.14 GB → 10.06 GB (-45%)**, against today's published `vllm/vllm-openai-rocm:nightly` (built from main, with LMCache). Most of the saving comes from pip's download cache: `Dockerfile.rocm_base` leaves 7.0 GB of ROCm SDK and torch wheels in `/root/.cache/pip`, and every image built on it ships them.
- The final image no longer carries build-only packages (`libsuitesparse-dev`, `libfmt-dev`, `libmsgpack-dev`, `ccache`, `mold`, `sqlite3`) or the build's `MAX_JOBS`.
- No functional change. vLLM serves correctly with AITER, and GSM8K on Qwen3-0.6B gives the expected accuracy (see Validation).

## Validation

Full build of `docker/Dockerfile.rocm_base` (target `final`, default arch list `gfx90a;gfx942;gfx950;gfx1100;gfx1101;gfx1200;gfx1201;gfx1150;gfx1151`), then `docker/Dockerfile.rocm` (target `vllm-openai`, `INSTALL_LMCACHE=true`) on an MI300X host. Both succeed, including the base's own triton/pybind11 version and fingerprint checks.

**Size** (compressed, summed from each image's manifest):

| Image | Compressed | Largest layer (per-arch `torch`/`rocm` device wheels) |
|---|---|---|
| `vllm/vllm-openai-rocm:nightly` (main, 2026-10-22) | 18.14 GB | 11.34 GB |
| This PR without `PIP_NO_CACHE_DIR` | ≈17.5 GB | — |
| This PR | **10.06 GB** | 5.68 GB |

The baseline was built by the release pipeline from a slightly different main commit, so small per-layer differences are expected. The large deltas are in the pip-install layers. Uncompressed, the base image's pip-install layers shrink from 25.05 GB to 17.58 GB, matching the 7.0 GB measured in `/root/.cache/pip`.

**In the built release image:**
- `/root/.cache/pip` is absent, and the build-only packages above are not installed.
- `torch 2.13.0+rocm10.0.0`, `triton 3.8.0`, `vllm` and `lmcache 0.5.3` import. The MoRI NIC libraries (`libionic`, `libbnxt_re`) are present.
- None of triton's `.so` files contain `.debug_info`.

**On the GPU (MI300X):**
- torch conv2d, matmul, FFT and SVD match CPU/fp64 references.
- `torch.utils.cpp_extension.load_inline` JIT-compiles and runs a HIP kernel.
- A triton kernel runs correctly.
- `aiter.rms_norm` matches the reference.
- `vllm serve Qwen/Qwen3-0.6B --max-model-len 4096` with `VLLM_ROCM_USE_AITER=1` starts, uses the AITER rms_norm path, and returns correct completions with no errors in the log.

**GSM8K** through that server (`lm_eval --model local-completions --tasks gsm8k --num_fewshot 5`, all 1319 questions):

| Model | strict-match | flexible-extract |
|---|---|---|
| Qwen/Qwen3-0.6B (bf16) | 0.3920 ± 0.0134 | 0.3745 ± 0.0133 |

This is in line with the repo's threshold for the FP8 variant (`tests/evals/gsm8k/configs/Qwen3-0.6B-FP8.yaml`: 0.375). I did not run a main-image eval for comparison. The change only affects packaging.

**Tests and lint:**
- `pytest tests/tools/test_docker_build_metadata_args.py`: 13 passed. The 14th (`test_rust_build_cache_excludes_git_metadata`) fails locally only because torch isn't installed in my venv; it is unrelated.
- The new test fails without the `Dockerfile.rocm` change and passes with it. It runs in the existing AMD "Docker Build Metadata" CI step.
- `shellcheck`, `typos`, `ruff`, `check-filenames`, `update-dockerfile-graph` and `check-dockerignore-tracked` pass.
- `docker buildx build --check` on both Dockerfiles shows only the `SecretsUsedInArgOrEnv` warnings already present on main.
- `tools/install_mori_nic_deps_rocm.sh` was run in an `ubuntu:22.04` container with `NIC_BACKEND=none`, `all` and an invalid value. It behaves like main's inline block, including exit code 2 for the invalid value.

**Not run:**
- The ROCm CI image build and test suite.
- Multi-GPU and RDMA data paths (RCCL, MoRI, NIXL moving data).
- Pull and extract timing for the new images.

## Details

- **`docker/Dockerfile.rocm_base`**
  - Sets `ENV PIP_NO_CACHE_DIR=1` before the first pip call. This keeps the cache out of every layer, including the multi-GB `rocm[libraries,devel]`, torch and per-arch `[device-*]` installs.
  - `build_triton` strips debug info (`strip --strip-debug`) from the wheel's `.so` files before repacking. `wheel pack` regenerates `RECORD`. The wheel filename, and so the version used to repack torch in `debs_wheel_release`, is unchanged. `TRITON_SHA256` is computed from the installed, stripped files in both Dockerfiles, so it stays consistent.
- **`docker/Dockerfile.rocm`**
  - Splits `base` into `runtime_base` (uv, `WORKDIR`, `PYTORCH_ROCM_ARCH`) and `base` (adds the build-only packages, ccache/sccache setup and `MAX_JOBS`).
  - `final_common` now starts from `runtime_base` instead of `mori_base`. Every build stage and `ci_base` still derive from `base`.
  - Nothing in the final image links against the removed packages. `csrc/` and the NIXL/LMCache wheels don't use them, and runtime JIT still has gcc, Python headers and `libnuma-dev` from the base image.
- **`tools/install_mori_nic_deps_rocm.sh`**: the MoRI NIC install, previously an inline `bash -lc` block in `mori_base`, now runs from both `mori_base` and `final_common`.
- **`.buildkite/scripts/ci-bake-rocm.sh`**: `runtime_base` and the new script are added to the content-hash stage and file lists.
  - The hash only counts ARGs that a listed stage references. Once the install moved into a script, `NIC_BACKEND`, `AINIC_VERSION` and `UBUNTU_CODENAME` would have dropped out, and a change to them would reuse a stale `ci_base`. The RUN lines now pass them explicitly, and a test covers this.

**Tradeoffs and behavior changes:**
- Containers built from the release image no longer have the removed `-dev` packages, `ccache`, `mold` or the `sqlite3` CLI. gcc, cmake and ninja remain.
- `PIP_NO_CACHE_DIR=1` stays set in the image, so `pip install` inside it doesn't cache. uv is unaffected.
- `MAX_JOBS` is no longer set in the runtime environment. It was inherited from build args, not a deliberate runtime default.

**History:** an earlier revision also deleted unused ROCm SDK components (composable_kernel, rocALUTION, hipTensor, flang) from `/opt/rocm` via `dpkg -L`. After main moved to the pip-installed TheRock SDK on `ubuntu:22.04`, that no longer applies and was dropped, along with its size numbers.

**Duplicates and related work:** before rebasing I searched open PRs for ROCm image size, `Dockerfile.rocm` and `PIP_NO_CACHE_DIR`; none overlap. #60258 (non-reproducible top layer in ROCm 10 `ci_base` images) is related, but this PR does not address layer reproducibility. #62758 also edits the ROCm runtime image stages and may need a trivial rebase against this one.
