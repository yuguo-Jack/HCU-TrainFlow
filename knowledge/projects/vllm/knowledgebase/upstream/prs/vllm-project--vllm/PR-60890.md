# [ROCm][Docker] Shrink the ROCm release image

[Upstream PR](https://github.com/vllm-project/vllm/pull/60890) · state: open · merged: False

## Original PR description

## Overview

Shrink the ROCm release image (`vllm/vllm-openai-rocm`) by removing ROCm SDK
components nothing in the image uses, stripping debug info from `triton`,
and keeping build-only packages out of the final image.

## Claims

- Compressed release image size: **11.5 GB → 9.49 GB (-17%, -2.0 GB)**; on
  disk: 46.2 GB → 36.8 GB (-20%, -9.4 GB). Measured with a full build for the
  default `gfx90a;gfx942;gfx950;gfx1100;gfx1101;gfx1200;gfx1201;gfx1150;gfx1151`
  architecture list.
- No functional change: nothing removed is linked, imported, or otherwise
  used by anything shipped in the image (vLLM, torch, triton, aiter,
  flash-attention, MoRI, NIXL, LMCache).
- `docker/Dockerfile.rocm`'s final image no longer carries build-only
  packages (`libsuitesparse-dev`, `libfmt-dev`, `libmsgpack-dev`, `ccache`,
  `mold`, the `sqlite3` CLI) or a leftover `MAX_JOBS=16` from the release
  build args.
- Decompress + extract time for a cold pull of the image's layers: **184.5s
  → 148.5s (-19.5%)**, measured directly (not inferred from the size delta
  alone — see Validation).

## Validation

All of the below on an MI300X host, building for the default architecture
list (`gfx90a;gfx942;gfx950;gfx1100;gfx1101;gfx1200;gfx1201;gfx1150;gfx1151`):

- Full `docker/Dockerfile.rocm_base` build, then `docker/Dockerfile.rocm`
  `vllm-openai` target (with `INSTALL_LMCACHE=true`), both succeed.
- `composablekernel-dev`, `rocalution`(`-dev`), `hiptensor`(`-dev`), and
  flang are fully removed (`dpkg -L` shows no remaining files;
  `/opt/rocm/include/ck{,_tile}` and `/opt/rocm/lib/cmake/composable_kernel`
  are empty/absent); `apt-get check` still passes.
- `hipBLASLt` kernels are present for all 12 architecture variants the
  default list implies.
- GPU convolution, bf16 matmul, FFT, and SVD run correctly (`torch`).
- `hipcc` compiles and runs a HIP kernel; `torch.utils.cpp_extension.load_inline`
  JIT-compiles and runs a HIP kernel at runtime.
- A `triton` kernel executes correctly with its stripped `libtriton.so`.
- `aiter`, `mori`, `nixl_rocm`, `lmcache` (+ `lmcache.c_ops`), `flash_attn`,
  `torchvision`, and `torchaudio` all import.
- Deleted a prebuilt `aiter` kernel module that depends on `composable_kernel`
  and forced `aiter` to recompile it at runtime with the system CK package
  completely absent — it rebuilds and imports successfully, confirming
  `aiter` only ever uses its own vendored CK copy
  (`aiter_meta/3rdparty/composable_kernel`), never the system package.
- `vllm serve Qwen/Qwen3-0.6B --max-model-len 4096` with
  `VLLM_ROCM_USE_AITER=1` starts and serves a correct completion.
- `.venv/bin/python -m pytest tests/tools/test_docker_build_metadata_args.py`:
  13/13 pass (this suite covers the `ci-bake-rocm.sh` content-hash logic
  this PR's stage-list changes touch).
- `pre-commit` (`shellcheck`, `typos`, `check-filenames`,
  `update-dockerfile-graph`) passes on the changed files.

### Pull/extract time, not just size

A compressed-size reduction doesn't necessarily translate proportionally
into wall-clock savings: decompression/unpack can dominate over network
transfer. So I measured it directly instead of inferring it from the size
delta, by decompressing and extracting every layer blob of both images from
containerd's content store (the same work `docker pull` does when applying
layers), on the same host/disk:

| | Compressed in | Extracted | Wall time |
|---|---|---|---|
| Old release image (36 layers) | 11.48 GB | 33 GB | 184.5s |
| This PR's image (31 layers) | 9.49 GB | 26 GB | 148.5s |
| **Delta** | **-17%** | **-21%** | **-19.5%** |

(Two runs of the old image agreed within 1%, 184.5s vs. 186.7s.) The
extracted totals are larger than each image's final merged size (46.2 /
36.8 GB) because this method extracts each layer's diff independently and
doesn't account for later layers overwriting/deleting earlier ones — that's
a property of the measurement, not a discrepancy in the image.

Reproduction: for each layer digest/size in an image's manifest,
`ctr -n moby content get <digest> | tar -xzf - -C <scratch-dir>/layer_<digest>`,
timed as one batch per image.

Network transfer time is more host/path-dependent, so this isn't an
end-to-end "time to pull" number; network transfer at a few representative
bandwidths, from the same compressed-byte delta:

| Link | Old | New | Saved |
|---|---|---|---|
| 100 Mbps | 918s | 759s | 159s |
| 1 Gbps | 92s | 76s | 16s |
| 10 Gbps | 9.2s | 7.6s | 1.6s |

For context on which of these actually dominates: AMD's internal cluster
measured, for a similarly-sized ROCm image, that **≥88% of total pull
wall-clock was decompression/unpack, not network transfer**
(#60258) — bandwidth wasn't their bottleneck. If that holds generally, the
measured extraction-time savings above likely matter more in practice than
the network table, which is the part that's actually uncertain here.

Caveat: this only helps a pull that re-downloads the shrunk layer. The
largest single layer in both images is the ROCm SDK (squashed and made
reproducible by this PR specifically so it's shared across base-image
rebuilds — see Implementation); a node that already has that layer cached
from a prior pull of the same lineage has already banked most of this
saving, and a cold pull sees the full numbers above.

Model evaluation: not applicable. This only changes what ships in the Docker
image; it does not change vLLM's Python code, kernels, or default
configuration, so model output/accuracy/serving behavior is unaffected.

Not run: the ROCm CI test image build and test suite (needs AMD CI
infrastructure this PR was developed without direct access to — the
equivalent validation above was run manually against the actual Dockerfile
targets instead), and multi-GPU/RDMA transfer paths (RCCL, MoRI, NIXL
actually moving data across GPUs/nodes).

## Details

### Why these components were safe to remove

`docker/Dockerfile.rocm_base`'s upstream ROCm base image ships
`composable_kernel`, `rocALUTION`, `hipTensor`, and a Fortran compiler
toolchain (`flang`) that nothing downstream needs:

- `torch`, `flash-attention`, and `aiter` each compile against their *own*
  vendored copy of `composable_kernel` (visible in their build logs: e.g.
  `aiter`'s build args point at
  `aiter_meta/3rdparty/composable_kernel/include`, never
  `/opt/rocm/include/ck`), so the system package is never consulted.
- Nothing links `librocalution*` or `libhiptensor*` — checked via `ldd`
  across every `.so` in the image.
- Nothing invokes `flang`/`amdflang` — no Fortran is compiled anywhere in
  this image.

This PR removes every file `composablekernel-dev`, `rocalution`(`-dev`),
and `hiptensor`(`-dev`) install (not just their static libraries), so that a
stray `find_package(composable_kernel)` (or similar) fails cleanly at
configure time instead of resolving a config whose libraries are missing.

### Implementation

- `docker/Dockerfile.rocm_base`: a new `rocm_sdk` stage runs directly on
  `${BASE_IMAGE}` and deletes the above via `dpkg -L <pkg>` (so it stays
  correct if the packaged file list changes upstream, and `apt-get check`
  keeps passing since the `rocm-libs` meta-package stays dpkg-consistent).
  Directory deletion alone doesn't shrink an image — the deleted files would
  still exist in the lower (base-image) layer — so the result is copied into
  a fresh `scratch`-based layer (`rocm_sdk_squashed`). Parent-directory
  mtimes are restored before that copy so the squashed layer's content (and
  thus its digest) is reproducible across rebuilds: verified by building
  this stage twice with `--no-cache` and comparing `RootFS.Layers` — both
  bit-identical. This matters because this large layer is otherwise
  redownloaded by anyone rebuilding the base image if its digest isn't
  reproducible (as e.g. #60258 describes for a different, non-public
  ROCm-10.0 build lineage — see below).
  `build_triton`'s stage also now strips `--strip-debug` from `libtriton.so`
  and friends before packaging the wheel (debug info only, symbol names and
  backtraces are unaffected).
- `docker/Dockerfile.rocm`: splits the `base` stage into a `runtime_base`
  (what the final image needs: `uv`, the ROCm env vars) and `base` (adds the
  build-only packages: `libsuitesparse-dev`, `libfmt-dev`, `libmsgpack-dev`,
  `libnuma-dev`, `ccache`, `mold`, `sqlite3`). The final image now derives
  from `runtime_base` directly instead of `mori_base` (which derived from
  the build `base`), so those packages — and the release build's
  `MAX_JOBS=16` leaking into the runtime environment via `ARG`/`ENV`
  inheritance — no longer ship.
- `tools/install_mori_nic_deps_rocm.sh`: the MoRI NIC-backend install logic
  (previously an inline `bash -lc '...'` block in `mori_base`) is extracted
  into a standalone script, since both `mori_base` (CI base image) and
  `final_common` (release image) now need to run it independently.
- `.buildkite/scripts/ci-bake-rocm.sh`: the new `runtime_base` stage and
  `tools/install_mori_nic_deps_rocm.sh` are added to the existing
  content-hash stage/file lists (the mechanism #48746/#48646 introduced),
  following the same pattern as every other tracked stage/file, so the CI
  `ci_base` cache correctly invalidates when either changes.

### Not a duplicate of #60258

I searched for open PRs/issues before starting (and again just before
opening this PR) and found none addressing ROCm Docker image size. The one
closely related issue, #60258, reports a non-reproducible top layer in a
*different*, ROCm-10.0-via-wheels CI base lineage built from a bare
`ubuntu:22.04` image — that parameterization (the `ROCM_NIGHTLY_WHEELS_*`/
`ROCM_RELEASE_WHEELS_*` ARGs and wheel-based ROCm install it describes)
doesn't exist anywhere in `docker/Dockerfile.rocm_base`,
`docker-bake-rocm.hcl`, `ci-rocm.hcl`, or `ci-bake-rocm.sh` in this repo, so
it's evidently driven by infrastructure outside vLLM's own repo. This PR
doesn't touch or claim to fix that lineage; it only affects the
default, apt-based ROCm base image path. I'm noting it here since it's the
closest prior art on image-layer reproducibility, and because this PR's
`rocm_sdk_squashed` reproducibility technique may be a useful reference for
whoever picks that issue up.

### Tradeoffs / behavior changes

- The final image no longer has `libsuitesparse-dev`, `libfmt-dev`,
  `libmsgpack-dev`, `ccache`, `mold`, or the `sqlite3` CLI. Anyone compiling
  something against those headers, or invoking those tools, inside a
  container built `FROM vllm/vllm-openai-rocm` now needs to `apt-get
  install` them first. gcc, cmake, and ninja are still present, so ordinary
  source builds (e.g. `pip install` of a package with a C extension) still
  work.
- `MAX_JOBS` is no longer set to `16` in the final image's environment (it
  was previously a leak from the release build's `--build-arg max_jobs=16`
  into the runtime `ENV`, not an intentional runtime default — vLLM, torch,
  and `triton` don't read it at runtime, and `aiter` only reads it when
  JIT-compiling a kernel that wasn't prebuilt, where it now falls back to
  its own CPU/RAM-based heuristic instead of being capped at 16).
- This PR doesn't change `docker/Dockerfile.rocm_gfx1250` or
  `docker/Dockerfile.rock`.
