# [Bugfix][MoE] Fail fast when batched_triton lacks batched prepare/finalize

[Upstream PR](https://github.com/vllm-project/vllm/pull/60448) · state: open · merged: False

## Original PR description

## Overview

Fixes #60432 by rejecting incompatible MoE prepare/finalize and experts activation formats before the experts constructor runs.

The validation now lives in one shared construction helper used by all modular MoE oracle factories, including unquantized, FP8, INT8, NVFP4, MXFP4, WNA16, W4A8, and W4A8-INT8.

## Claims

- Replaces the reported raw `BatchedTritonExperts.__init__` `TypeError` with a clear `ValueError` naming both incompatible components and activation formats.
- Applies the activation-format contract to quantized and unquantized methods instead of special-casing `batched_triton` in the unquantized factory.
- Preserves the existing batched-experts constructor setup (`max_num_tokens` and `num_dispatchers`) in the shared helper and removes the duplicated setup from the individual factories.
- Rebases the change onto current `main` and preserves the upstream quantization-only backend fallback test added since the original PR.

## Details

`moe_backend="batched_triton"` selects `BatchedTritonExperts`, whose constructor requires the `BatchedExperts` activation format and its associated constructor arguments. Without an all-to-all path, `maybe_make_prepare_finalize` can instead return a `Standard`-format prepare/finalize stage. Previously the experts constructor ran first and failed on missing arguments, while the existing `FusedMoEKernel._post_init_setup()` compatibility check was reached too late.

`make_fused_moe_experts` now compares `experts_cls.activation_format()` with `prepare_finalize.activation_format` before construction. Only compatible `BatchedExperts` pairs receive `max_num_tokens` and `num_dispatchers`. Every modular oracle factory calls this helper, so the invariant is enforced consistently without adding inference-path overhead.
