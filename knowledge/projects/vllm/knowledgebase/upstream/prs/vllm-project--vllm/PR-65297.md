# [Perf] SM90 FP8 scaled_mm: 64x256 tiles for M just above a multiple of 256

[Upstream PR](https://github.com/vllm-project/vllm/pull/65297) · state: open · merged: False

## Original PR description



## Overview

`cutlass_scaled_mm` for FP8 with per-token activation scales and per-channel weight scales (the `Fp8LinearOp` path on Hopper) uses one config for every M in (128, 8192): 128x128x128 tiles in a 2x1x1 cluster. The cluster pairs two 128-row tiles, so when M is just above a multiple of 256 most of the last 256 rows are padding:

- with an odd number of 128-row tiles (0 < M % 256 <= 128), the partner CTA of the last cluster runs the full mainloop on zero rows (it still has to load its half of the multicast B tile);
- with 128 < M % 256 <= 192, the last 128-row tile is at least half padding.

As a result M = 272 takes 2-3x longer than M = 256 and up to 1.8x longer than M = 512 (twice the work). The same step repeats above every multiple of 256. Chunked prefill and mixed decode + prefill batches land on such M values all the time (the last chunk of a prompt, a few decode rows plus a chunk).

This PR adds one config, 64x256x128 tiles without clustering, for M in (128, 1024] with 0 < M % 256 <= 192, which caps the padding at 63 rows. Every other M keeps the current config, so multiples of 256 and all M > 1024 run exactly the same kernel as today.

## Claims

- **Kernel time, H200, five GEMM shapes:** the changed M values run 1.42x faster on geomean (min 0.99x, max 2.47x, 50 points); the unchanged ones are within run-to-run noise (geomean 1.00x).
- **Root cause, Nsight Compute:** at M = 272 the current config does exactly the tensor-core work of M = 512 and reads the weight 1.65 times from DRAM; the new config does 0.62 of it and reads the weight about once (table below).
- **Correctness:** `tests/kernels/quantization/test_cutlass_scaled_mm.py` passes on H200 with four new M values that hit the new config.
- **End to end, H200, Llama-3.1-8B-Instruct-FP8-dynamic:** TTFT of a 272 / 528 / 784-token prompt -21% / -22% / -19% (1.27x / 1.28x / 1.23x), unchanged at multiples of 256 and above 1024; mixed 128-1024-token load at 8 concurrent requests: median TTFT -13%, throughput +2%, TPOT unchanged (section below).

### Alternatives measured and rejected

- 128x128 tiles with cluster 1x1x1 for all M in (128, 1024]: no gain at multiples of 256 and up to 4% slower at some M with M % 256 > 192, where the current config has an even tile count and no idle partner.
- 64x128 tiles (any cluster): up to 0.55x at multiples of 256.
- Cluster 1x2x1: 0.8-0.9x. Cooperative schedules: 0.9-0.95x.
- 64x192 and 128x256 tiles: slower than 64x256 at the tail points.
