# [Bugfix][Multimodal] Place Qwen3-VL EVS M-RoPE slices by placeholder offset

[Upstream PR](https://github.com/vllm-project/vllm/pull/62975) · state: closed · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Fixes #62969. With video pruning (EVS / VidCom2) on Qwen3-VL-family models, a chunked-prefill boundary inside a video placeholder gave wrong M-RoPE positions to every following token, and a wrong `mrope_position_delta` for decode. Both model runners now pass each media slice's placeholder offset into `recompute_mrope_positions`, and the 5-channel slices are placed from it.

## Claims

- M-RoPE positions for Qwen3-VL-family models (Qwen3-VL, Qwen3-VL-MoE, Qwen3.5, Cosmos3, Cosmos3-Edge, InternS1-Pro) and Cohere Compass no longer depend on where chunked prefill splits a video or image placeholder. This applies to both Model Runner V1 and V2.
- The same change places 5-channel media from the placeholder offset, not from a `vision_start` search, so it also covers the cases below. The fallback search used by the 4-channel path (Qwen2.5-VL) is unchanged.
  - The outer `<|vision_start|>` that transformers >= 5.10 keeps (#62937).
  - Several media items in one chunk, and the `vision_start | media` split (#48833).

## Details

**Root cause.** Qwen3-VL's pruned video placeholder is registered with `PromptUpdateDetails.from_seq`, so `is_embed` is `None`. The runner then passes `encoder_output[start_idx:end_idx]`, a positional slice of the placeholder whose t/h/w values are relative to the placeholder's first token. Placing that slice needs two things: the placeholder offset, for the anchor (the position of the token before the placeholder + 1), and the slice start (`max(num_computed_tokens, offset)`). `recompute_mrope_positions` received neither. It inferred them from prompt-side `vision_start` indices and media-token counts, and that breaks inside a placeholder in three ways (traces in #62969):
1. Inside frame 0's video, the anchor was the frame's inner `vision_start` + 1, while the slice values already count frame 0's timestamps and that marker. Positions came out `num_timestamp_tokens + 1` too high.
2. The write offset counted only video tokens, so a split inside timestamps or past frame 0 was written at the wrong index.
3. The prompt lumps every retained video token on frame 0 (`tokens_per_frame=[n, 0, ...]`), while the model spreads them across frames. Past frame 0's video tokens, the "all media tokens seen" early exit fired, and the later frames were never written.

**Change.**
- `recompute_mrope_positions` takes an optional `multimodal_offsets` argument. When it is given and the entries have 5 channels, each slice goes through a small separate loop that anchors at `positions[-1, offset - 1] + 1`, writes at `max(num_computed_tokens, offset)`, and extends the trailing text positions as before.
- `GPUModelRunner._gather_mm_embeddings` (V1) and `MultiModalPruner` (V2) pass the offsets, which they already compute while windowing. In V2, `_num_window_embeds` became `_window_offsets`.
- The protocol and the three in-tree implementations (Qwen3-VL, Qwen2.5-VL, Cohere Compass) take and forward the new keyword.
- Without offsets, or for 4-channel entries, the old code path runs unchanged.

**Compatibility.**
- The new keyword argument defaults to `None` in the protocol and in every in-tree implementation. Both runners now pass it, though, so an out-of-tree model that implements `SupportsMultiModalPruning.recompute_mrope_positions` without it would need to add it.
- The new path calls fewer `nonzero` / `count_nonzero` ops than the old one and keeps the single `.item()` for the delta.

**Not changed.** The V1 drafter pass (`_gather_mm_embeddings(shift_computed_tokens=1)`) still calls the recompute with the unshifted `num_computed_tokens` (#43820). For a draft window that starts inside a placeholder, its write-back is now off by one token, where it used to be wrong in the ways listed above. V2 doesn't recompute in the draft pass.

**Related PRs.** #62959 (mine) fixes #62937 inside the `vision_start` search. In-tree models no longer use that search for 5-channel media, so #62959 is not needed once this lands. #48835 is still relevant for the 4-channel path.
