# Patch for vLLM + FlashAttention4 + torch for GRPO colocated training

[Upstream PR](https://github.com/vllm-project/vllm/pull/36535) · state: closed · merged: False

## Original PR description

Fixes https://github.com/vllm-project/vllm/issues/36651

## Summary

- **cumem.py**: Track per-allocation mapped state to prevent double `cuMemRelease` when `sleep`/`wake_up` are called on already-unmapped or already-mapped allocations. Add a `sleeping` flag so `_python_free_callback` returns a dummy handle during sleep, avoiding CUDA ops on freed memory. Remove `gc.collect` + `empty_cache` in `sleep()` which can trigger frees during the sleeping window.
- **cumem_allocator.cpp**: Clear stale `error_code` at the top of `create_and_map`, `unmap_and_release`, and `my_free` to prevent leftover errors from previous operations propagating. Skip CUDA ops in `my_free` when `recv_d_mem == 0` (sleeping block already freed). Fix size mismatch by using `recv_size` instead of `size` in `unmap_and_release` and `cuMemAddressFree` calls. Log a warning when `unmap_and_release` fails and `cuMemAddressFree` is skipped to make virtual address leaks visible.
- **rotary_embedding/common.py**: Replace `find_spec` check with `try/except` for `flash_attn.ops` import to support Flash Attention 4 which restructured its module layout.

## Test plan

- [ ] Verify no regressions in standard vLLM inference with cumem allocator enabled
- [ ] Verify rotary embedding works with both Flash Attention 2/3 and Flash Attention 4

## Code Review

This pull request addresses several critical issues in the `cumem` allocator, particularly around the `sleep`/`wake_up` functionality. The changes prevent double-free errors by tracking allocation mapping state and handle stale error codes by resetting a global error variable. The use of a `sleeping` flag to manage frees during the sleep window is a good solution. Additionally, the update to support Flash Attention 4 by using a more robust import mechanism is a welcome improvement. Overall, the changes are well-reasoned and correctly implemented. I have one point of feedback regarding error handling in `csrc/cumem_allocator.cpp`, where the current fix for preventing crashes could lead to a silent resource leak. Addressing this would make the error handling more robust.

This error handling logic, while preventing a crash from calling `cuMemAddressFree` on a still-mapped memory region, introduces a silent virtual address space leak. If `unmap_and_release` fails, `cuMemAddressFree` is skipped, but the address space reserved by `cuMemAddressReserve` for `d_mem` is never freed. In long-running applications, this can lead to resource exhaustion. Consider logging this event as a warning to make debugging easier if memory issues arise later.
