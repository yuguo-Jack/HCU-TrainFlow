# [Bugfix][KV Offload] Fail clearly when cuMemcpyBatchAsync is missing instead of segfaulting

[Upstream PR](https://github.com/vllm-project/vllm/pull/59974) · state: open · merged: False

## Original PR description

## Overview

`SimpleCPUOffloadConnector` segfaults the EngineCore on CUDA drivers older than 12.8, because
`_resolve_batch_memcpy` wraps a NULL `cuMemcpyBatchAsync` pointer without checking it. This PR
checks the symbol status and the pointer and raises the `RuntimeError` that the function's
docstring already promises.

## Claims

- On a pre-12.8 driver the connector now fails at engine startup (KV cache registration:
  `register_kv_caches` -> `DmaCopyBackend.init` -> `build_params` -> `_resolve_batch_memcpy`)
  with a `RuntimeError` naming the driver version, instead of a segfault during serving.
- No behavior change when the symbol is found (driver 12.8+) or on ROCm.

## Validation

Unit tests (new `tests/v1/simple_kv_offload/test_cuda_mem_ops.py`, no GPU needed;
`cuda.bindings.driver` is replaced by a fake module), run CPU-only on main `ae8f41238cc7`:

```
patched:   4 passed
unpatched: 3 failed, 1 passed
  FAILED test_missing_symbol_raises_instead_of_returning_null[CU_GET_PROC_ADDRESS_SYMBOL_NOT_FOUND]
  FAILED test_missing_symbol_raises_instead_of_returning_null[CU_GET_PROC_ADDRESS_VERSION_NOT_SUFFICIENT]
  FAILED test_null_pointer_with_success_status_raises
```

`test_found_symbol_is_returned` passes on both; it guards the new check against rejecting a
working driver. `ruff check` / `ruff format --check` (v0.14.0, the pre-commit pin), the mypy hook
(`tools/pre_commit/mypy.py 3.11`) and `typos` pass on both files.

Real driver, RTX 4090, driver 550.144.03 (`cuDriverGetVersion` = 12040), vLLM v0.30.0 (`+cu129`
wheel):

```
cuGetProcAddress(b"cuMemcpyBatchAsync", 12080, 0)
  -> (CUDA_SUCCESS, 0, CU_GET_PROC_ADDRESS_SYMBOL_NOT_FOUND)   # enum members shown by name
calling the wrapped pointer -> Fatal Python error: Segmentation fault
```

Serving, before and after, same machine and driver, one command for both runs (Qwen3-1.7B, one GPU):

```
vllm serve Qwen/Qwen3-1.7B --max-model-len 8192 --gpu-memory-utilization 0.6 \
  --kv-transfer-config '{"kv_connector":"SimpleCPUOffloadConnector","kv_role":"kv_both",
    "kv_connector_extra_config":{"cpu_bytes_to_use":4294967296,"lazy_offload":false}}'
```

followed by one 1280-token prompt with 512 forced output tokens, then distinct 4096-token prompts
with `max_tokens: 1`.

Without this change, the server starts and becomes healthy; on the first request the EngineCore
prints `!!!!!!! Segfault encountered !!!!!!!` and every request returns HTTP 500
(`EngineDeadError`). (Earlier, with Qwen2.5-7B-Instruct, `cpu_bytes_to_use` 16 GiB and
`lazy_offload: true`, the segfault came on the fifth request, in 5 of 5 server starts.)

With this change, the same command fails at startup instead:

```
(EngineCore pid=...) ERROR [core.py:1366] EngineCore failed to start.
  ...
  File ".../vllm/v1/simple_kv_offload/cuda_mem_ops.py", in _resolve_batch_memcpy
    raise RuntimeError(
RuntimeError: cuMemcpyBatchAsync is not available from the installed CUDA driver (driver API version 12040, symbol status CU_GET_PROC_ADDRESS_SYMBOL_NOT_FOUND); SimpleCPUOffloadConnector requires a driver supporting CUDA 12.8+.
(APIServer pid=...) RuntimeError: Engine core initialization failed. See root cause above. Failed core proc(s): {}
```

(The patched module was loaded over the installed v0.30.0 wheel for this run; the installed
`cuda_mem_ops.py` is identical to main's.)

## Details

The CUDA branch of `_resolve_batch_memcpy` (`vllm/v1/simple_kv_offload/cuda_mem_ops.py:125-128`)
checks only the `CUresult`:

```python
err, ptr, _ = drv.cuGetProcAddress(b"cuMemcpyBatchAsync", 12080, 0)
if err != drv.CUresult.CUDA_SUCCESS:
    raise RuntimeError(f"cuGetProcAddress(cuMemcpyBatchAsync) failed: {err}")
return _BATCH_MEMCPY_FUNC_TYPE(ptr), 1
```

A driver that predates `cuMemcpyBatchAsync` returns `CUDA_SUCCESS` with a NULL pointer and
`CU_GET_PROC_ADDRESS_SYMBOL_NOT_FOUND` (or `VERSION_NOT_SUFFICIENT`) in the third value, which is
discarded. The C++ path (`swap_blocks_batch`, `csrc/cache_kernels.cu:155`) already checks
`fn_ptr == nullptr` and falls back to per-copy `cudaMemcpyAsync`; the Python path does not.

The fix reads the symbol status, treats a non-SUCCESS status or a NULL pointer as unavailable,
and raises with the driver version from `cuDriverGetVersion` and the status name (`.name`, so
the message is the same on IntEnum and FastEnum builds of cuda-bindings). The tests replace
`cuda.bindings.driver` with a small fake, as `test_hip_mem_ops.py` in the same directory does for
the HIP loader, because CI GPUs have drivers new enough that the failing branch cannot be reached
for real.

Related: #61054 (opt-out env var for vGPU, issue #61052) adds a `cuMemcpyAsync` per-descriptor
path right after this function. It addresses a different failure (the symbol resolves but faults
at runtime on vGPU) and does not add the NULL check; the two touch adjacent lines, so whichever
lands second needs a trivial rebase. A per-descriptor fallback for pre-12.8 drivers, as the C++
path has, would make the connector usable there; this PR keeps the change to the missing check.

AI assistance: Claude (Anthropic) was used to locate the cause, draft the fix, the tests and this
description. I reviewed every changed line, reproduced the crash and the fix on the driver above,
and ran the tests.
