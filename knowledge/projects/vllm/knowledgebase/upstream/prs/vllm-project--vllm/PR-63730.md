# [ROCm][Perf] Kimi-K3 prefill GEMMs on AITER tuned kernels

[Upstream PR](https://github.com/vllm-project/vllm/pull/63730) · state: open · merged: False

## Original PR description

Ready for review. No blocking issues.



## Overview

Online FP8 prefill for Kimi-K3 on MI355X is slower than BF16 today. This PR quantizes `routed_expert_down_proj` online and builds AITER's tuned GEMMs at startup.

## Claims

- `routed_expert_down_proj` follows the online quantization config. Its checkpoint weights are BF16, so the checkpoint config is still bypassed.
- `kernel_config.enable_rocm_aiter_gemm_warmup` (off by default) runs one dummy forward per AITER GEMM M bucket during kernel warmup.
- Kimi-K3 agentic PD benchmark, with in_proj padded to 128 on AITER v0.1.24.post1: +2.1% total tok/s/GPU and mean TTFT 5.35 s to 4.05 s over online FP8 prefill without this PR, +0.7% over BF16 prefill.

## Validation

- New `test_rocm_aiter_gemm_warmup.py` covers bucket coverage and the opt-in. A new KDA online-loading test checks the alignment padding: loading completes after six shards and the padding stays zero. pre-commit clean; GPU reload tests in `test_reload.py` not run.
- End to end: one run per configuration, below. No accuracy evaluation. Variance not measured; the closest pair, BF16 with and without warmup, differs by 0.4% in throughput and 0.01 s / 1.2 s in mean / p90 TTFT.
- KDA in_proj keeps main's 16-row alignment: AITER v0.1.27, main's pin, tunes 6288x7168 at the latency of 6400x7168. Not re-run end to end on v0.1.27.

<details><summary>End-to-end benchmark</summary>

Kimi-K3, agentic multi-turn trace at concurrency 48, 1 prefill + 1 decode instance on 2 nodes of 8x MI355X, TP8 + DCP8, FP8 KV cache, MoRIIO. vLLM ROCm nightly `81198e97` with these changes mounted as file overlays. Online FP8 prefill means `--quantization-config` with `fp8_per_channel` targets on the attention projections, shared experts and dense MLPs, plus `re:.*\.routed_expert_down_proj$: mxfp4` and `VLLM_ROCM_USE_AITER_FP4_ASM_GEMM=1` from the down_proj step on.

| Online FP8 | [run](https://github.com/ROCm/ATOM/actions/runs/39226586488) | 10626 | 5.35 s / 13.31 s |

| BF16 GEMMs + warmup only | [run](https://github.com/ROCm/ATOM/actions/runs/39487012805) | 10729 | 4.51 s / 10.45 s |

The `+ in_proj pad 128` step was needed on that nightly's AITER v0.1.24.post1, whose table tunes 6400x7168 but not 6288x7168; this PR no longer pads. In v0.1.27's `a8w8_bpreshuffle_tuned_gemm_kimik3.csv` (gfx950, 256 CUs) the 6288/6400 latency ratio has median 1.00 and range 0.92 to 1.09 over the 52 M values from 256 to 8192, and both shapes use the same FlyDSL kernel at M=8192. Padding alone is slower because the newly tuned kernels are built on first use while serving; the warmup moves that to startup. Warmup without online quantization gives no gain.

Load-time checks: 92 `routed_expert_down_proj` on `Mxfp4OnlineLinearMethod`, 69 `in_proj_qkvgfab` on `AiterPreshuffledPerTokenFp8ScaledMMLinearKernel`.

## Details

- Warmup sizes: AITER buckets up to `max_num_batched_tokens`, multiples of 8 up to 512, and `max_num_batched_tokens - 1` for Triton's divisibility specialization; 164 forwards at 8192 tokens, 541 to 585 s on the Kimi-K3 prefill instance (104 s without online quantization). The measured runs added a second timing sweep, dropped here.
- An online config whose `linear` default does not ignore `routed_expert_down_proj` now quantizes it; add it to `ignore` to keep BF16.
