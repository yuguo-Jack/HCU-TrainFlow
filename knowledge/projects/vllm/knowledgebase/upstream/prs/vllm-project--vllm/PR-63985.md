# [Bugfix] Preserve FlexAttention block masks across compiled builds

[Upstream PR](https://github.com/vllm-project/vllm/pull/63985) · state: open · merged: False

## Original PR description

## Overview

Fixes #63945. Compile FlexAttention block-mask construction without `reduce-overhead` so masks remain valid across subsequent builds, including EmbeddingGemma 2 encoder requests.

## Claims

- Prevents the overwritten-CUDAGraph-output error while retaining `fullgraph=True` compilation.
- Adds a mask-lifetime regression and extends encoder embedding parity coverage to EmbeddingGemma 2, eager/compiled execution, repeated batches, and inputs crossing its sliding window.

## Validation

Tested on Ubuntu 24.04 WSL2, RTX 3050 OEM 8 GB, Python 3.12, PyTorch 2.14.0+cu132, Transformers 5.19.0. Existing wheel CUDA extensions were reused. Serving tests ran with unrelated plugins disabled (`VLLM_PLUGINS=`) and `CUDA_HOME` pointing to the environment's `nvidia/cu13` package.

| Check | Before | After |
| --- | --- | --- |
| Compiled block-mask lifetime | Fails with overwritten-output error | Passes |
| EmbeddingGemma 2 eager embedding request | `InternalTorchDynamoError`, then `EngineDeadError` | Passes |
| Encoder parity against default backend | — | BGE and EmbeddingGemma 2 pass in eager and compiled modes, three repeated batches each |
| Independent EmbeddingGemma 2 evaluation against Sentence Transformers 6.2.0 | — | Cosine 0.9999207–0.9999872; unit norms within 1e-5 |

## Details

`reduce-overhead` enables Inductor CUDA graph trees independently of vLLM's eager/CUDA-graph settings. Their reusable output buffers can invalidate tensors retained by earlier `BlockMask` objects. This reproduces even when vLLM uses `enforce_eager=True`. Default compile mode avoids that output-buffer lifetime mismatch while preserving compiled mask construction.

This changes only the mask builder's compilation mode. The direct mask path and compiled attention remain unchanged. Removing internal CUDA graph replay may add mask-construction launch overhead; no throughput improvement is claimed or benchmarked. No public configuration or API changes.

Duplicate checks found no open PR referencing #63945 or matching `create_block_mask` plus `reduce-overhead`. AI assistance was used to implement and validate this change.

- vuquoctrungbk · comment · 2026-10-27T07:55:58Z · [source](https://github.com/vllm-project/vllm/pull/63985#issuecomment-6436645296)

Thanks for picking this up! I filed #63945 and had reached the same one-line fix locally, so I'll back this PR rather than open a duplicate. Here is some evidence from my side that may help review.

**Exact mechanism (instrumented).** I added prints to `build_block_mask()` and `FlexAttentionImpl.forward()` on unpatched `main` (nightly `00b6c4c5`, RTX 3060) and served EmbeddingGemma 2 with `FLEX_ATTENTION --enforce-eager`:

```
build_block_mask meta=…6870 sw=None n=38          # group A (sliding layers) pre-builds in build()
build_block_mask meta=…2600 sw=None n=38          # group B (full layers) pre-builds in build()
forward layers.0 meta=…6870 sw_layer=513 rebuild=True
build_block_mask meta=…6870 sw=513 n=38           # rebuild for group A overwrites the graph outputs
forward layers.1..4 meta=…6870 rebuild=False
forward layers.5 meta=…2600 sw_layer=None rebuild=False   # group B reads its stale pre-built mask -> error
```

So the trigger is **an encoder-only model with two or more KV cache groups**. Each group's metadata pre-builds a mask through `create_block_mask_compiled`. The first sliding layer's rebuild then overwrites the buffers that the other group's mask still points to.

A control: `Alibaba-NLP/gte-modernbert-base` also alternates sliding and full layers, but it has a single KV cache group. It passes FLEX vs the default backend on unpatched `main`, because its mask is rebuilt and used right away. This explains why the bge test never caught the bug, and it suggests that EmbeddingGemma 2 (or any multi-group encoder) is the right model for the regression test.

**Please don't switch to `torch.compiler.cudagraph_mark_step_begin()`.** I listed it in #63945 as an alternative, and that was wrong. Calling it between builds tells the graph tree that earlier outputs are dead. The error goes away, but the pre-built mask then silently aliases the new one, so attention is wrong and nothing fails. Dropping `reduce-overhead` (this PR) is the safe fix. Cloning the mask tensors after each build would also be correct, but costs extra copies for about 0.1 ms.

**Cost data**, in case a reviewer asks. Median of 50 calls, bidirectional sliding-window mask, 128x128 blocks, RTX 3060:

| N tokens | `reduce-overhead` | default `torch.compile` |
| --- | --- | --- |
| 512 | 0.094 ms | 0.204 ms |
| 4096 | 0.168 ms | 0.234 ms |
| 16384 | 1.215 ms | 1.114 ms |

Only builds with `direct_build` off reach this function: `EncoderOnlyAttentionSpec`, torch < 2.9, or `kv_block_size != block_size`. Decoders on paged KV are unaffected.

**Independent validation of the same change** on RTX 3060 (sm_86), image `nightly-00b6c4c5`, torch 2.14.0+cu130: `main`'s `tests/kernels/test_flex_attention.py` plus my own two regression tests (16 tests) all pass with the fix, and both of my new tests fail without it. and EmbeddingGemma 2 served via FLEX matches sentence-transformers reference vectors (cosine 0.99993 to 0.99996), with and without `--enforce-eager`.

Two small notes on the tests:
- The existing encoder test now passes `gpu_memory_utilization=0.7` for both models. If that was only for your 8 GB card, CI may not need it.
- #62236 (open) adds a faster encoder mask path, but only when `sliding_window is None`. Sliding-window encoders will still use `create_block_mask_compiled`, so this fix stays relevant after that PR lands.

LGTM from a user's perspective. Happy to rerun anything on sm_86 if useful.
