# [Bugfix][CPU] Default to V1 model runner on CPU backend (#58565)

[Upstream PR](https://github.com/vllm-project/vllm/pull/58600) · state: open · merged: False

## Original PR description


## Purpose
Fixes #58565.

### Background & Root Cause
In `v0.28.0`, the CPU backend defaulted to the V1 model runner because `triton-cpu` was not bundled in the release image (`HAS_TRITON=False`).

Starting in `v0.29.0` (commit `373592ef57`), the `triton-cpu` wheel was bundled into `docker/Dockerfile.cpu`, causing `HAS_TRITON` to evaluate to `True`. Because `VllmConfig.use_v2_model_runner` did not guard against the CPU platform, CPU began unintentionally defaulting to Model Runner V2.

Model Runner V2 was only experimentally introduced for CPU in #43225 and is not production-ready for general serving, particularly for embedding and pooling models. In Model Runner V2, the pooling execution path returns an `AsyncPoolingOutput` that relies on CUDA stream synchronization and event-based asynchronous copies. On the first request to `/v1/embeddings`, the worker process died abruptly (`Worker proc VllmWorker-0 died unexpectedly (exit code: None)`), crashing EngineCore with `RuntimeError: cancelled`.

### Solution
1. In `vllm/config/vllm.py`, default to the V1 model runner when `current_platform.is_cpu()` and `VLLM_USE_V2_MODEL_RUNNER` is not explicitly set (`None`).
2. Retain support for explicitly setting `VLLM_USE_V2_MODEL_RUNNER=1` so ongoing experimental CPU Model Runner V2 development and tests remain functional.
3. Added unit tests in `tests/test_config.py` verifying that CPU defaults to V1 and that explicit overrides (`1` and `0`) are respected.

**Config.** Taken from the `dump_input` line in #58565:

`dtype=torch.bfloat16`, `max_seq_len=8192`, `enforce_eager=False` with
`DYNAMO_TRACE_ONCE`, `custom_ops=['none']`, `VLLM_CPU_KVCACHE_SPACE=2`, six
bound OMP threads, `VLLM_WORKER_MULTIPROC_METHOD=spawn`. Dependency versions
match their `collect_env` as well: torch `2.13.0+cpu`, `transformers 5.17.0`,
triton-cpu `3.7.0+git270e696d`.

**Result.** `POST /v1/embeddings` returns **200** with a correct 1024-dim embedding and the engine still healthy afterwards. No `died unexpectedly`, no `EngineDeadError`, no `RuntimeError: cancelled` anywhere in the server log.

**`373592ef57` (#52092) is already in `v0.28.0`**: it landed Aug 13, the tag is Aug 23. So triton-cpu bundling can't be why 0.28 was safe. What protected 0.28 is that `use_v2_model_runner` called `_is_default_v2_model_runner_model()` first,
and that helper opened with:

```python
if model_config.runner_type != "generate":
    return False
```

Pooling models were excluded from MRV2 regardless of Triton. #48290 deleted those two lines and #53183 removed the helper entirely; neither is in 0.28, both are in 0.29.
