# [Kernel] ReplaySSM: cache SSM inputs for faster Mamba2 speculative decode

[Upstream PR](https://github.com/vllm-project/vllm/pull/49847) · state: closed · merged: False

## Original PR description

## Background

This is the third sub-PR split from the larger ReplaySSM draft PR (#47576), which contains the complete Mamba2 and Gated DeltaNet implementation for both standard and speculative decode. The first sub-PR, Mamba2 standard decode (#48018), landed as `866fea2b9`, so this PR is based directly on `main` and adds Mamba2 speculative decode. ReplaySSM caches recent SSM inputs instead of writing the recurrent state back to HBM on every step. It is a collaboration between Dao AI Lab and NVIDIA, and the full derivation and figures are in the [blog post](https://dao-lab.ai/blog/2026/replayssm/). AI assistance was used for parts of this work, and the authors have reviewed every changed line.

## Core concept

To roll back rejected drafts, vLLM's native Mamba2 spec path keeps a separate recurrent state snapshot for every draft token, so a step with `T = 1 + num_speculative_tokens` tokens writes `T` full `(nheads, head_dim, dstate)` states and reads one back. Cost grows linearly in `T`, which is why the native path can fall below plain standard decode at serving batch.

ReplaySSM replaces the snapshots with one checkpoint state plus a small circular buffer of the per-step SSM inputs (`x`, `dt`, `B`). This changes three things:

- Rollback is a cursor move.
- Verification is parallel. Every draft output is computed from the same checkpoint in one GEMM, which removes the length-`T` serial recurrence.
- Traffic is flat in `T`. The full state is materialized only on a periodic flush. In most of the steps (non-flush steps), no state is store back to HBM.

The table below is the measured per-step DRAM traffic at bs256, Nemotron-3-Super-120B geometry, fp32 state, cold L2. Baseline traffic scales with `T`; ReplaySSM does not.

| T | baseline GB | ReplaySSM non-flush GB | ReplaySSM flush GB |
|---:|---:|---:|---:|
| 2 | 3.18 | 1.18 | 2.21 |
| 4 | 5.35 | 1.20 | 2.23 |
| 6 | 7.53 | 1.22 | 2.26 |
| 8 | 9.73 | 1.23 | 2.30 |

## What this PR adds

Everything is behind a flag. With ReplaySSM disabled, the decode path is unchanged.

- The Mamba2 cached spec kernel `selective_state_update_replayssm_spec`, its device-side cursor helpers `commit_replayssm_spec` and `reset_replayssm_spec_cursors`, and their hardware-keyed launch configs in `replayssm_config.py`.
- One new config flag, `--use-replayssm-spec`. It reuses `--replayssm-buffer-len` from #48018 for the history block `B` (default 16). It requires speculative decoding, `--mamba-cache-mode none` and the Triton mamba backend, and is mutually exclusive with `--use-replayssm`.
- Integration. The Mamba2 mixer dispatches to the kernel under the flag, the metadata builder owns the block-keyed ring cursors, and the state-shape and state-dtype calculators size the `post_conv_cache` and `dt_cache` ring on the paged state. The conv path reuses vLLM's `causal_conv1d_update` unchanged, with rollback handled by its existing `num_accepted_tokens` shift.
- A throughput benchmark, `benchmarks/replayssm/e2e_spec_decode_throughput.py`, which runs standard decode, native spec and ReplaySSM spec on GSM8K in separate subprocesses.

## Design notes

### When the ring flushes

`B` is the maximum history the ring carries into a verify step (default 16). A verify step consumes a whole window at once, so the flush rule is `history + T > B`: flush whenever the next window would not fit. That guarantees every verify step has room for a full `T`-draft window, so a window never truncates. The ring holds `L = B + T` logical slots, rounded up to `next_pow2(L)` so wraparound indexing is a bit mask rather than a modulo.

### Paged cache layout

The ring caches and the checkpoint live inside the paged KV block, appended as two extra tensors on the baseline `(conv, ssm)` state, for four tensors total. They stay live across decode steps, so they must sit in HBM between launches, and appending them onto the paged state reuses vLLM's per-request block allocation and block-table indexing directly. Only `x` and `B` are cached, while `C` is read from the conv output each step. `dt` is always stored in fp32; the state checkpoint follows `mamba_ssm_cache_dtype` and the input ring follows the activation dtype.

Only the small per-block cursors live outside the page: `write_pos` (committed history offset), `post_origin` (the window's circular base) and `is_flush`, all shaped `(num_gpu_blocks,)` and indexed by physical block id.

One design difference from #48018 (feedback welcome):
Standard decode caches x, dt, and B as three head-major tensors, while speculative decode caches dt together with a single token-major post_conv_cache. Although the layouts differ, they represent the same three logical caches. The launcher simply slices post_conv_cache into x and B views, which the kernel receives as separate strided pointers. The layout is chosen based on how the cache is written. Standard decode appends one token at a time after the tensors have already been split, so storing separate head-major tensors is natural. Speculative decode, on the other hand, scatters an entire T-token window from causal_conv1d_update, whose output is packed in channel-last order. Keeping the cache in that layout turns the scatter into a simple strided copy instead of requiring a transpose into three differently shaped tensors.

### CUDA graphs and continuous batching

The number of accepted tokens is only known after the step's forward and sampling, so `commit_replayssm_spec` runs at the *next* build and does two jobs at once: it commits the previous step's acceptance (`write_pos += num_accepted`, or advances `post_origin` on a flush) and decides this step's `is_flush`. Folding it into the next build rather than issuing a separate post-forward launch keeps every cursor update on-device, so there is no device-to-host sync on `num_accepted_tokens`.

Every step issues both a verify launch and a flush launch, each compiled for its single role with `is_flush` as a compile-time constant, and every row early-exits from the launch that does not apply to it. Which rows flush is routed on-device by the flags.

### Entering decode

A request's ring must start empty on its first verify step, including when it lands on a recycled block. The builder derives that from `replayssm_decode_base`, the context length recorded at admission by #48018: a row resets when `num_computed == decode_base`. Because `decode_base` is re-anchored when a request is readmitted, a preempted and recomputed request re-fires the reset and does not inherit its old cursors.

One row needs more care. A final single-token prompt chunk is reclassified as a decode (full-cudagraph dispatch is shape-based, so leaving it a prefill lets a decode graph replay against a stale cursor), which puts it one token short of `decode_base`. Those rows reset the ring and are forced to flush in the same step. Without the forced flush they would append a token to a freshly emptied ring without advancing the checkpoint, and the next step's reset would drop it.

## Results

Nemotron-3-Super-120B-A12B on one B300, TP1, fp32 SSM state, `B=16`, MTP drafter, greedy GSM8K with `ignore_eos`, CUDA graphs on. `T = 1 + num_speculative_tokens`. Produced with `benchmarks/replayssm/e2e_spec_decode_throughput.py`.

### End-to-end throughput

ReplaySSM spec over native spec, NVFP4 checkpoint:

| bs | T=2 | T=4 | T=6 | T=8 |
|---:|---|---|---|---|
| 1 | 0.88x | 1.04x | 1.05x | 1.17x |
| 32 | 1.15x | 1.13x | 1.03x | 1.38x |
| 128 | 1.24x | 1.29x | 1.48x | 1.90x |
| 256 | 1.34x | 1.77x | 1.91x | 2.09x |
| 512 | 1.78x | 1.85x | 2.11x | 2.34x |

| bs | T=2 | T=4 | T=6 | T=8 |
|---:|---|---|---|---|
| 1 | 1.36x | 1.88x | 1.89x | 1.81x |
| 32 | 1.52x | 1.85x | 1.74x | 1.73x |
| 128 | 1.67x | 1.92x | 1.92x | 1.64x |
| 256 | 1.88x | 2.13x | 1.97x | 1.73x |
| 512 | 2.11x | 2.16x | 2.12x | 1.83x |

Compared with native spec decoding, ReplaySSM speedup grow with `T` since native spec decoding stores `T` state snapshots per step. Compared with standard decode, ReplaySSM provides 1.8x to 2.2x speedup across all batch sizes (acceptance provides the gain even at small batch.)

### Kernel-level

Isolated per-kernel latency on the Super-120B geometry, fp32 state, cold L2, `ncu` at base clock. The baseline is `_selective_scan_update_kernel` at its swept-best config, with its shipped default config in parentheses (no tuned config JSON ships for B300, so the engine actually runs the default).

Baseline microseconds at bs256, growing linearly in `T`:

| T | tuned (default) |
|---:|---|
| 2 | 611 (960) |
| 4 | 1110 (1690) |
| 6 | 1620 (2450) |
| 8 | 2140 (3270) |

ReplaySSM remains nearly flat at bs256: the verify kernel is 264 to 314 us across T=2 to 8, the flush kernel 678 to 707 us, and the fused scatter 21 to 29 us. Amortizing over the exact flush cadence, and taking the worst-case acceptance `a = T` at every step, gives the speedup against the tuned baseline:

| T | bs 32 | bs 128 | bs 256 | bs 512 |
|---:|---|---|---|---|
| 2 | 1.17x | 1.53x | 1.59x | 1.67x |
| 4 | 1.84x | 2.21x | 2.33x | 2.41x |
| 6 | 2.30x | 2.76x | 2.86x | 2.95x |
| 8 | 2.98x | 3.54x | 3.75x | 3.86x |

Small batch is not the target regime: the SSM kernel is latency-bound there, and in a hybrid model the step is dominated by the MLP layers.

### Serving capacity

Native spec holds `1 + num_speculative_tokens` states per request for rollback. ReplaySSM holds one checkpoint plus the small input ring, so more requests fit in the same HBM. Maximum decode concurrency at `max_model_len=2048`, `(B, T) = (16, 4)`, B300:

| native spec | ReplaySSM | ratio |
|---:|---:|---:|
| 211.7 | 649.7 | 3.07x |

These are worst-case caps at the full request length. Beyond this point, throughput saturates.

## Tests

Per-step kernel correctness is covered by `tests/kernels/mamba/test_replayssm_spec_decode_mamba2.py`. A `T`-window verify step is checked against decoding the same window one token at a time, over multi-flush sequences, across three state and activation precision combinations, the production model geometries (small, tiny, Nemotron-Nano-4B, Super-120B, Ultra-550B), `B` in {16, 32} and `T` in {2, 4, 6, 8}. It covers rollback across a flush, continuous batching with per-row cursors and null-padded slots, and the builder's `bc_pre` scratch shape. Non-flush checkpoints are asserted bit-exact, since a non-flush step won't touch the state. A "teeth" case corrupts one history slot and asserts the output changes, so the history is provably being read.

Metadata builder unit tests are in `tests/v1/attention/test_replayssm_spec_metadata_builder.py`. The cursor logic is the riskiest new code, so it is covered without a model: commit advances `write_pos` by the accepted count, a flush advances `post_origin` past committed history and restarts `write_pos`, the early-flush rule fires exactly one window before the ring would overflow, rejected drafts and zero-accept rows commit nothing, a first decode resets a recycled block, a resumed request re-anchors after preemption, a steady-state row is left alone, a mixed batch resets only the entering rows, and null-padded rows are skipped. Two cases pin the parts that a captured graph depends on: the per-row scratch widens to the padded batch and stays the persistent buffer, and the block-keyed cursors are passed through whole. One case covers the forced flush for a final single-token prompt chunk, and one asserts the builder rejects a page that is not the four-tensor spec layout.

Engine-level parity lives in `tests/v1/e2e/test_replayssm_decode.py`, which compares native spec against ReplaySSM spec with greedy decode and `check_logprobs_close` on Nemotron-3-Nano-4B with an ngram drafter.

Results: the kernel file is 149 passed and the builder file is 14 passed. Engine parity passes. The pre-existing suites (standard-decode kernel, prefill/decode equivalence, standard metadata builder, block-table update) still pass unchanged at 164 passed together with the new builder file.

```
pytest tests/kernels/mamba/test_replayssm_spec_decode_mamba2.py \
       tests/v1/attention/test_replayssm_spec_metadata_builder.py \
       tests/v1/e2e/test_replayssm_decode.py -q
```

I think we can (and should) use the same cache layout as ReplaySSM STP here instead of introducing a new token-major one.. i.e. separate head-major buffers `x_cache [nheads, ring, head_dim]`, `dt_cache [nheads, ring]`, `B_cache [ngroups, ring, dstate]` (dt_cache is already head-major, so only x and B change).

The token-major layout is here to avoid a transpose when writing the conv output into the cache. But:
1. Both the no-flush and flush kernels read all tokens for a single head (same as the STP kernel), so they benefit from head-major exactly like STP does.
2. The kernels don't read the cache directly anyway.. they read `x_view`/`B_view`, which are strided views over the token-major buffer. So the reads are strided either way, and the token-major layout isn't saving a read-side transpose.
3. For MTP the cache is read many more times than it is written (~L positions read per step vs ~T tokens written), so we should optimize the load, not the store.
4. The scatter kernel already does the write-side reorder (reads with strides, writes element-by-element), so we don't need a torch-level transpose to store head-major.. we just need the buffer to be physically contiguous head-major (a view isn't enough).

On top of that, the conv output is split into x/B/C anyway, so there's no real gain from a packed x|B buffer vs separate buffers like STP. We could also pass x/B/C (`hidden_states_d`/`B_d`/`C_d`) directly into the kernel instead of `conv_out`, which drops the channel-index math in the scatter.

This only touches MTP (STP stays as-is), so it's in scope here. Might be worth a quick profile to confirm the head-major write penalty (a scattered T-token store) is outweighed by the read-locality win, but a-priori it should be since reads dominate.

Two things about the ring here:
  
1. This ring + rotating origin design is the least obvious part of the PR and I think it deserves a comment. IIUC the reason MTP needs it (vs just reading/writing from position 0 like STP) is: the flush can only fold the *committed* history into the checkpoint, not the current window.. we don't know num_accepted until after sampling, and the flush runs in the forward to produce the output. So a data-dependent tail of accepted tokens always survives the flush and has to carry over as the next step's history. We carry it by bumping `post_origin` (O(1)) instead of copying it back to 0 or re-folding it into the checkpoint, which is what makes the ring wrap. A short comment capturing that ("partial flush => carried tail => rotating origin => circular ring, and we bump the origin instead of copying/re-folding to avoid an extra full-state HBM read") would save the next reader a lot of time.
  
2. nit / question on the pow2 sizing: we round the ring up to next_pow2 so the wraparound can be a bitmask (`& (buf-1)`) instead of a modulo. `1 << (buffer_len + num_spec).bit_length()` is a bit cryptic.. a `buf = next_pow2(L)` comment would help. Also this pads the ring (default B=16, T=4 => L=20 => buf=32, ~1.6x on the ring tensors and the `bc_pre` scratch), and since the flush threshold is L (not buf) the extra slots never hold more history.. we pay the memory only to get the bitmask, no cadence benefit. The kernel is memory bound so I'd expect the modulo (or a ring sized exactly L with `% L`) to be mostly hidden. Might be worth a quick profile.. if the mask doesn't move the needle, sizing exactly L avoids the padding.

I think there's a correctness issue on the forced-flush path for a leftover single-token prompt chunk, and it isn't covered by the tests.

The reset comment says the forced flush advances the checkpoint past the leftover token so the next step's reset is safe. But when a leftover chunk hits this path, the reset sets `write_pos=0`, and the flush then runs with `write_pos=0`.. so `S_1 = S_0` (empty history) and this store is guarded by `if write_pos > 0`, so the checkpoint is not written. The token's output is correct, but its state contribution only lands in the ring (committed as history at the next step).

Then on the next step (`num_computed == decode_base`) `first_decode` fires again and resets the ring, dropping that committed history. So the leftover prompt token's `(dt*x*B)` contribution is lost from both the checkpoint and the ring for the rest of the sequence.

I think this only triggers with chunked prefill + full cudagraph when a prompt's final chunk is exactly 1 token, which is probably why the greedy e2e test doesn't catch it (and a builder test can't.. it only checks cursor values). Could you check with a 2-step case: reset + forced-flush one token at `write_pos=0`, reset again, and assert the checkpoint matches the baseline `selective_state_update` state after folding that token?

The fix is probably to fold the leftover token into the checkpoint on the forced-flush step (it's a certain prompt token, not speculative, so folding it is safe), or to not re-reset on the step right after a forced flush.
