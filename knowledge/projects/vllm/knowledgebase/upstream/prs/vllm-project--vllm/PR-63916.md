# [Bugfix][Multimodal] Return 422 when a media URL is unreachable after retries

[Upstream PR](https://github.com/vllm-project/vllm/pull/63916) · state: closed · merged: False

## Original PR description



## Overview

An `image_url`/`video_url`/`audio_url` whose host cannot be resolved or reached returns HTTP 500. This PR returns HTTP 422 (`UnprocessableEntityError`) for those requests, the same status already used for 4xx responses from the media host.

Follow-up to #47165. Related: #47163, #47960, #48092.

## Claims

- DNS failures, connection errors, timeouts and 5xx responses from the media host now return 422 instead of 500, once `VLLM_MEDIA_FETCH_MAX_RETRIES` attempts have failed. The retry behavior is unchanged.
- The 422 message is generic ("Could not connect to host", "Request timed out", "HTTP 503 error"). It does not echo the resolved address or the exception text, so it does not expose internal network details.
- Local resource exhaustion while fetching (EMFILE, ENFILE, ENOMEM, ENOBUFS, ENOSPC) still returns 500. 408 and 429 keep their current behavior.

## Validation

End-to-end on 1x H100, `vllm/vllm-openai:nightly` (0.32.1rc1.dev505+g00b6c4c56), `Qwen/Qwen2-VL-2B-Instruct`, `VLLM_IMAGE_FETCH_TIMEOUT=1`. Same container, before and after applying this diff:

| `image_url` | Before | After |
|---|---|---|
| valid image (HF) | 200 | 200 |
| `https://nonexistent-host.invalid/cat.jpg` (DNS) | 500 `Cannot connect to host nonexistent-host.invalid:443 ssl:default [Name or service not known]` | 422 `Failed to fetch media from URL: Could not connect to host` |
| `http://127.0.0.1:9/cat.jpg` (refused) | 500 `Cannot connect to host 127.0.0.1:9 ssl:default [Connect call failed ('127.0.0.1', 9)]` | 422 `Failed to fetch media from URL: Could not connect to host` |
| missing file on HF (404) | 422 | 422 |

Both runs log `HTTP fetch failed ... (attempt 1/3)` and `(attempt 2/3)` before the response, so retries still happen before the error is returned.

Unit tests:

```bash
pytest tests/multimodal/media/test_unprocessable_entity_error.py tests/multimodal/media/test_connector.py tests/multimodal/media/test_image.py tests/test_connections.py
# 127 passed
```

`test_fetch_image_dns_error_retried_then_422` drives the real `HTTPConnection` retry decorator. It checks that the fetch is attempted `VLLM_MEDIA_FETCH_MAX_RETRIES` times before the 422 is raised. On `main` without this change, 5 of the 16 tests in that file fail (DNS, connection, timeout, 5xx and the retry test) because the raw exception propagates.

## Details

Root cause: `HTTPConnection.get_bytes` and `async_get_bytes` are decorated with `_sync_retry`/`_async_retry`, which retry the errors `_is_retryable` accepts (timeouts, connection errors, 5xx). `MediaConnector.load_from_url(_async)` calls `_wrap_media_fetch_error` only after `get_bytes` raises, which is after the last retry. Its docstring said transient errors are returned as-is "to allow retry logic to handle them", but no caller retries them again. The exception reaches the API server unmapped and becomes a 500.

The fix reuses `_is_retryable`, so the set of errors mapped to 422 is exactly the set that was already retried. `_is_local_resource_error` checks `os_error`, `__cause__` and `__context__`, because aiohttp wraps a local `OSError` (for example EMFILE) in `ClientConnectorError`, which `_is_retryable` treats as a connection error.

`parameter` stays `image_url` for all modalities, as in the existing 4xx path. That is unchanged by this PR.

A 5xx from the media host is mapped to 422 rather than 502. vLLM has no 502 error class, and the request names a media URL that could not be fetched. The docs note in `docs/features/multimodal_inputs.md` and the `VLLM_MEDIA_FETCH_MAX_RETRIES` comment state this behavior.
