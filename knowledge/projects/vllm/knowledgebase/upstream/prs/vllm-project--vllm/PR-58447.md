# [Model] Align Nemotron vision compute dtype

[Upstream PR](https://github.com/vllm-project/vllm/pull/58447) · state: open · merged: False

## Original PR description

## Summary

Align the Nemotron VL vision boundary with vLLM's configured model dtype instead of mixing FP32 image tensors with a hardcoded BF16 feature cast.

- cast raw pixel inputs to `self.llm_dtype` before vision-tower execution
- cast vision features to `self.llm_dtype` instead of unconditionally using `torch.bfloat16`
- cover BF16 and FP16 for both fixed-resolution and dynamic-resolution image paths

## Problem

The multimodal processor produces normalized `pixel_values` as FP32 tensors. `NemotronH_Nano_VL_V2` then passes those tensors directly to the vision tower, even though vLLM may initialize the model for another compute dtype through `ModelConfig.dtype`. After the vision tower returns, both image extraction paths unconditionally convert its features to BF16.

The resulting boundary is inconsistent:

```text
FP32 pixel_values -> configured-dtype vision tower -> forced-BF16 features -> configured-dtype projector / language model
```

This creates two independent dtype assumptions:

1. The vision tower receives FP32 activations even when its parameters and execution dtype are BF16 or FP16. Operators that require matching input and parameter dtypes can fail, while other operators may introduce unintended conversions.
2. Vision features are always changed to BF16. When vLLM is configured for FP16, the downstream multimodal projector and language-model embedding path can therefore receive BF16 tensors despite being initialized for FP16.

The second problem can be hidden by the common BF16 configuration, but the FP32 input mismatch still remains. The same behavior exists in both `extract_feature`, which processes fixed-resolution images and videos in micro-batches, and `extract_feature_dynamic`, which processes dynamic-resolution images.

## Fix

Use `self.llm_dtype`, which records vLLM's selected model dtype, as the source of truth at both sides of the vision tower:

```text
FP32 pixel_values -> configured dtype -> vision tower -> configured dtype -> projector / language model
```

The input conversion is assigned to a local tensor, so the caller-provided FP32 tensor remains unchanged. This PR does not change image normalization, patch layout, token placement, model weights, LoRA behavior, or text-only execution. It only makes the raw-pixel vision compute boundary consistent with the configured model dtype. The explicit conversion also avoids depending on an ambient autocast context during vLLM model execution.

## Test plan

The regression test records the tensors seen by the vision tower and projector and checks all four combinations:

- BF16, fixed-resolution path
- BF16, dynamic-resolution path
- FP16, fixed-resolution path
- FP16, dynamic-resolution path

It also verifies fixed-resolution micro-batching and confirms that the original FP32 `pixel_values` tensor is not modified.

- `pytest -q tests/models/multimodal/test_nano_nemotron_vl.py -k aligns_vision_boundary_dtype`
