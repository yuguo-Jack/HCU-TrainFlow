# [Bugfix][Frontend] Honor allowed_tools tool_choice in the Responses API

[Upstream PR](https://github.com/vllm-project/vllm/pull/60585) · state: open · merged: False

## Original PR description



## Overview

The Responses API accepts `tool_choice={"type": "allowed_tools", ...}`, but the Python server ignored it: calls were not limited to the allowed tools, and non-streaming responses returned them as message text. This change makes the server use the structural-tag support for `allowed_tools` that already exists. It replaces #56368, whose named-`tool_choice` part is now covered by #59723.

This fixes the Qwen case reported in #62639 (thanks @princess-melie for testing it). The Gemma4 case there is still not restricted, because Gemma4 has no structural tag (see the limitations below).

## Claims

- When a structural tag applies (the default `VLLM_ENFORCE_STRICT_TOOL_CALLING=true`, with a tool parser that supports structural tags), an `allowed_tools` choice limits tool calls to the listed function and custom tools. `mode="required"` requires a call; `mode="auto"` also allows a text reply.
- Non-streaming responses return `allowed_tools` calls as `function_call` items, as streaming responses already did.
- `function` and `custom` entries are resolved like a named `tool_choice` (#59723), so a namespace function can be listed by its local name. Unknown or ambiguous names get a 400, as for a named `tool_choice`, and the not-found message now names the missing tool.
- With `mode="auto"`, a requested `text.format` still applies: the model either calls an allowed tool or returns output in that format.
- Custom tools, which the model is shown as single-string function shims since #57322, can be allowed like functions.
- Entries for built-in tools (for example `web_search` or `mcp`) are ignored for models that are only shown function and custom tools, instead of failing grammar construction.
- The `hf` response-template parser rejects `allowed_tools` with a 400, as it already does for the other tool guarantees it cannot enforce.

## Details

Root cause: #45396 added `allowed_tools` handling to the structural-tag registry (`get_structural_tag_tools`, `_dump_tool_choice_for_xgrammar`). However, `DelegatingParser._apply_structural_tag` only builds a tag for `auto`, `required` and named choices, so the server never reached that code. `_extract_tool_calls` also only runs the tool parser for `auto`, so non-streaming responses returned the raw call markup. Streaming already fell through to the auto parser.

Changes:

- `_apply_structural_tag` now builds the tag for `ToolChoiceAllowed`. For structured outputs, `mode="auto"` follows the `auto` path, and the forced variant keeps the allowed subset (`mode="required"`) instead of switching to plain `"required"`.
- `_extract_tool_calls` parses `allowed_tools` calls like `auto`.
- `get_model_structural_tag` keeps only function and custom entries for models outside `_BUILTIN_TOOL_STRUCTURAL_TAG_MODELS`, matching the tools `get_structural_tag_tools` shows them, and builds no tag when none remains. Otherwise xgrammar rejects the other entries ("Allowed builtin tools are not found"), and an empty list yields a grammar that does not compile for GLM-4.7 and PLaMo3.
- `_dump_allowed_tool_ref_for_xgrammar` dumps `custom` entries as function references, matching the function shims their tools are dumped as (#57322). Otherwise xgrammar treats them as built-in tools and rejects them.
- `ResponsesRequest.check_tool_usage` resolves the `function` and `custom` entries with `_resolve_named_tool_choice`, so local namespace names reach xgrammar as `namespace__function`.
- `ResponseTemplateParser` lists `allowed_tools` among the guarantees it cannot enforce.

Tradeoffs and limits:

- `allowed_tools` gets a structural tag, and so a per-token grammar cost, even when no tool is `strict`, unlike plain `auto`, because the tag is what limits the calls.
- Unknown or ambiguous `function` or `custom` entries now fail with a 400 at request validation, including on servers that do not enforce the list. This matches named `tool_choice` validation. Before, these requests failed during grammar construction, or the list was ignored.
- A `namespace` key on an entry is not interpreted, as for a named `tool_choice`. An ambiguous local name must use the full `namespace__function` name.
- Without structural tags, `allowed_tools` is still not enforced. Mapping it onto the JSON-schema path is out of scope. Harmony models build their own tag from all tools and are unchanged by the entry filtering.
- If every allowed entry is a built-in tool on a model whose tag only covers function and custom tools, no tag is built, so calls are not limited, as on `main`. Rejecting that case for `mode="required"`, like `tool_choice="required"` does, is left for a follow-up.

Duplicate check: no open PR or issue covers `allowed_tools` in the Python server. I searched PRs and issues for `allowed_tools`, `"allowed tools"` and `ToolChoiceAllowed`. #51535 and #44280 cover the Rust frontend, #45512 covers MCP `allowed_tools` at tool execution time, and #53099 refactors structural-tag capabilities without changing this gate.
