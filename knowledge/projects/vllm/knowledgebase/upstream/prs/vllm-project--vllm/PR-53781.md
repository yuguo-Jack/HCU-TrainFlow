# [3/N] HiSparse: host-resident sparse-MLA decode hot-buffering

[Upstream PR](https://github.com/vllm-project/vllm/pull/53781) · state: closed · merged: True

## Original PR description

## Summary

HiSparse adds a host-resident tier beneath vLLM's normal GPU KV cache for sparse-MLA decode. Unlike the original always-host-resident design in #46326, this implementation keeps as much KV as possible in the normal device cache and spills pages to pinned host memory only when GPU capacity must be reclaimed.

Supersedes #46326.

## Design overview

```text
resident GPU pages
        |
        | spill under pressure
        v
  pinned host pool ---- selected top-k misses ----> per-request GPU hot buffer
        ^                                                     |
        |                                                     v
        +---------------- prefix reuse ---------------- sparse attention
```

The active indexer cache remains device-resident and produces the logical top-k positions needed by sparse attention. A fused CUDA resolver maps each selected position through three possible locations:

1. a normal resident GPU page;
2. an existing row in the request's GPU hot buffer;
3. the pinned host pool.

Resident hits return before the hot-cache lookup. Hot hits update a GPU-side LRU, while misses replace LRU entries by gathering only the selected host rows. Resolution, replacement, and LRU updates remain on the GPU and are compatible with CUDA graph replay.

HiSparse does not maintain a private host-side copy of indexer KV. The indexer remains a normal prefix-cacheable GPU cache group. When OffloadingConnector is configured alongside HiSparse, generic KV offloading preserves and restores the indexer while HiSparse continues to own only sparse-MLA residency. If the sparse host prefix extends beyond the available indexer prefix, the scheduler restores only the missing indexer suffix, capped at the sparse host boundary. Without generic offloading, the request falls back to the shorter shared prefix and recomputes the remainder.

## Residency and ownership

The normal KV cache manager continues to own GPU block allocation. `HiSparseCoordinator` owns logical host blocks, host-prefix identity, and residency transitions.

When GPU pressure requires reclaiming a resident page, the coordinator reserves its host destination and sends a transfer command to the worker. The resident GPU block becomes reusable after every worker has acknowledged that the copy is enqueued in stream order. The host page is not published for prefix reuse until every copy has completed.

The main components are:

- `HiSparseCoordinator`: scheduler-side host allocation, prefix state, and spill policy.
- `HiSparseConnector`: carries residency commands and transfer acknowledgements between scheduler and workers.
- `HiSparseConnectorWorker`: manages the pinned host-pool lifecycle and executes copies.
- `HiSparseRuntime`: owns each cache's host/hot views, GPU LRU state, and fused attention-time resolution.

Host blocks use the same token hashes as their resident counterparts, but their hashes are published only after the contents are durable. Spilling therefore preserves prefix-cache value without allowing an incomplete host write to be reused.

## P/D and NIXL integration

NIXL remains the P/D transport; HiSparse determines the decoder-side landing policy. The decoder chooses one policy per request during admission:

- If the imported prefix fits in the normal GPU pools, NIXL writes it into resident device pages.
- Otherwise, the bulk sparse-MLA KV lands in the registered HiSparse host pool. Device-only regions such as the indexer are still imported to GPU, the request receives its fixed hot-buffer allocation, and pages needed immediately are mirrored into resident GPU pages.

The two generic connector prerequisites below are intentionally separate from HiSparse:

- #53779 lets connectors select externally transferable cache groups while retaining their scheduler group IDs.
- #53780 carries stride, capacity, block size, group mapping, and identity per NIXL region, allowing P/D peers with different layouts and memory placement.

#53263 is a separate, optional optimization for same-node P/D. It stages device-to-host NIXL reads through decoder GPU memory to avoid UCX's slow TCP loopback path. It is not required by the intended multi-node P/D design.

## Scope

This PR implements the NVIDIA sparse-MLA path and includes the staging required for correct local or mixed prefill on a decode worker. Metrics are split into #53782, and DeepSeek V4's compressed cache geometry is split into #53592.

- samsja · comment · 2026-08-28T18:31:08Z · [source](https://github.com/vllm-project/vllm/pull/53781#issuecomment-5456280681)

Ran this stack (up through 5/N, `feat/nixl-host-read-staging` @ dfc3f675e) on GLM-5.2-FP8 / GLM-5.3 (`glm_moe_dsa`, 78L, index_topk=2048) in a disaggregated P/D deployment on 8xH200 nodes — 2 prefill + 2 decode engines (tp=8, dp=1 each), NIXL over source-built UCX 1.19, nixl 0.10.1, torch 2.13.0+cu130, `hisparse_config.host_pool_gib` set on both roles. Single-node HiSparse works great; P/D needed two workarounds and has one open correctness issue. Reporting all three since GLM-family shapes don't seem covered by CI:

**1. NIXL region geometry breaks on GLM's packed cache pool (startup crash).**
GLM-5.2/5.3 allocate the indexer/resident/hot caches in one shared storage. In `NixlBaseConnectorWorker.register_kv_caches`, the packed-storage MLA branch registers whole-row regions (`storage_block_len = registration_len // num_blocks`), so a `hisparse_resident` layer's region is the full packed row — 4x its page here — and `HiSparseNixlAdapter.register_region` rejects it:
```
ValueError: HiSparse host page is smaller than its transfer region:
layer=model.layers.0.self_attn.attn.hisparse_resident, host_stride=73728, region_block_len=294912
```
`block_size` doesn't change it (tried 64, the e2e-test value). Local workaround: for `hisparse_resident` layers, emit per-cache regions `(cache.data_ptr(), physical_page_size, row_stride)` instead. This may not be the right general fix (see finding 3).

**2. Host-pool NIXL registration includes unpinned slop → UCX "already mapped" (startup crash).**
`allocate_pinned_host_pool` over-allocates `padded_size + page` and `cudaHostRegister`s only the page-aligned slice, but `register_region` records the *whole* backing storage in `_host_registration_ranges`. UCX's cuda_copy MD then `cuMemHostRegister`s a range that overlaps the already-pinned middle and fails hard:
```
UCX ERROR cuMemHostRegister_v2(...) failed: part or all of the requested memory range is already mapped
nixl_cu13._bindings.nixlBackendError: NIXL_ERR_BACKEND
```
Reproduces at any `host_pool_gib` (tried 4 and 24). Local workaround: shrink each recorded range to the pinned sub-range (`base + (-base % 4096)`, `nbytes - 4096`) before `register_memory` — UCX's memory-type probe then dedupes. (Skipping the pool's own pinning instead is rejected by the `hisparse_backup` kernel's "host_cache must be pinned" check.)

**3. Open correctness issue: long-prefix P/D transfers garble output on GLM shapes.**
With the two workarounds above, the P/D fleet serves and *short* routed requests are byte-correct, but long-prefix requests (e.g. 40k-token prompt) return garbled text through the router while the same prompt direct-to-decode (local prefill) is coherent — i.e. multi-block transfer of hisparse KV corrupts data. This may well be my workaround for finding 1 mis-addressing blocks under `_physical_blocks_per_logical_kv_block` packing rather than a bug in the stack itself — but either way the GLM packed-pool P/D path appears unexercised upstream. Happy to test a proper fix or provide more detail (logs, configs, exact geometry dumps).

Also worth a docs note: the NIXL handshake (`Number of KV layers must match between prefill and decode`) means `hisparse_config` must be enabled on **both** P/D roles, not just the decoder — enabling decode-only fails at the first transfer.

Great work on this stack overall — the P/D win on our setup was 40k-token prefill in 10s via prefill nodes vs 3m20s decode-local, and the HMA path works exactly as documented on a single node.

## Three Blocking Issues Found While Testing HiSparse

### 1. Engine initialization crashes with `NotImplementedError` for `tokens_per_state`

With prefix caching enabled, GLM produces a multi-group KV cache configuration containing:

- Approximately 20 resident/hot groups
- An indexer
- A host-source group

`resolve_kv_cache_block_sizes` in `v1/core/kv_cache_utils.py:790` evaluates:

```python
spec.prefix_cacheable
isinstance(spec.tokens_per_state, int)
```

However, `HiSparseHotSpec` and `HiSparseResidentSpec` inherit:

```python
prefix_cacheable = True
```

from the base class without implementing `tokens_per_state`. This causes the engine to crash during startup.

#### Workaround

The following workaround fixed the issue in our environment:

```python
prefix_cacheable = False
```

This is consistent with:

- Their `enable_prefix_caching=False` group construction
- The existing `KpoolTailSpec` behavior

---

### 2. First forward crashes with `"HiSparse GPU slots have no scheduler mapping envelope"`

Our instrumentation shows:

- The scheduler constructs `row_mirrors` correctly.
- On the worker, `state.candidates` is empty when `_resolve_row_mirrors` runs.

#### Root cause

The new base stack defers `start_load_kv` until after the forward pass when:

```python
has_sync_kv_loads = False
```

This is the normal path in:

```text
v1/worker/gpu/kv_connector.py::pre_forward
```

As a result, the connector's `start_step`, which publishes the mirror-mapping envelope, runs only after the following functions have already attempted to consume it:

- `stage_row_mirror_mapping`
- `finish_forward`

The execution order is effectively:

```text
stage_row_mirror_mapping
  -> finish_forward
  -> start_step publishes the mirror-mapping envelope
```

Therefore, the mapping information is unavailable when the worker needs it.

---

### 3. Host pool becomes full and never recovers, causing an admission livelock

After running 16 concurrent requests of approximately 26K tokens each, with roughly half of their KV cache spilled to the host pool, every new request remains in `WAITING` indefinitely.

At this point:

- EngineCore keeps busy-looping.
- No new request is scheduled.
- The host pool never recovers.

#### Instrumentation results

For one blocked request:

```text
GPU pool:  free 124206 >= need 7518
Host pool: free 261 < need 358
```

The GPU pool has enough capacity, but the host pool does not.

The 5,974-block host pool is entirely occupied by blocks belonging to requests that have already finished. Their hashes were never published.

Replaying the exact same prompt produces:

```text
computed=0
no prefix-cache hit
```
