# [Perf][XPU][Kernel] Fix register spills in the Triton W8A8 INT8 GEMM above M = 64 (prefill GEMM 13 -> 206 TOPS)

[Upstream PR](https://github.com/vllm-project/vllm/pull/64244) · state: open · merged: False

## Original PR description




## Overview

On XPU, W8A8 INT8 linears run through `triton_scaled_mm`, and above M = 64 its heuristic picks `(64, 128, 128)` up to M = 128 and `(128, 128, 128)` beyond, both with the default 4 warps. On XPU these tiles spill registers heavily, and at prefill sizes (M >= 192) the INT8 GEMMs take 9 to 17 times longer than they need to. This changes the tile on XPU to `(128, 128, 32)` with 16 warps for 64 < M <= 128 and `(256, 128, 128)` with 32 warps above. Other platforms keep the current tiles.

#64190 changes M <= 64 on XPU; this is independent of it and branches from main. Both add the `current_platform` import and pass `num_warps` to the kernel, so whichever lands second needs a small rebase. #45126 (NVIDIA tiles) and #61091 (ROCm FP8) also change this function.

## Claims

On Arc Pro B70:

- The current tiles above M = 64 spill: at M = 2048, `(128, 128, 128)` with 4 warps reports 29,632 bytes of spill and runs at 11.6 TOPS on an 8704 x 5120 weight. The same tile with 32 warps does not spill; the `(256, 128, 128)` tile chosen here, with 32 warps, spills 448 bytes and runs at 208 TOPS.
- The INT8 GEMMs of one forward pass at M = 192 to 2048 take 9.1x to 17.0x less time, on Qwen3.8-27B TP=1 and TP=2 shapes and on Muse-Glimmer-30B TP=2 shapes; at M = 96 and 128, 1.6x to 1.8x. At M = 2048 on the Qwen3.8-27B TP=2 shapes this is 13.4 TOPS before and 206.3 TOPS after. The new tiles take at most 4.5% longer than the best tile found at any M and shape set.
- For comparison, the unquantized bf16 path (`F.linear`, oneDNN), timed the same way, runs these GEMMs at M = 2048 at 124 TFLOPS (403 ms per forward pass); in the same run INT8 with this change takes 244 ms (204 TOPS), 1.65x faster, which is 83% of the 2x ratio of the int8 to bf16 XMX peaks.
- End to end, TP=2, W8A8 INT8, time to first token goes down **6.8x to 7.1x** on Qwen3.8-27B (34.44 to 5.09 s for 14,507 tokens) and **7.2x to 8.1x** on Muse-Glimmer-30B (33.95 to 4.21 s for 13,005 tokens).
- For int8 inputs the result does not depend on the tile (int32 accumulation). End to end at temperature 0 after prompts of about 3,100 to 3,500 tokens, the output is identical before and after on both models: tokens and top-5 logprobs. These prompts run the M > 128 branch; 64 < M <= 128 is covered by the unit test.

### Why the current tiles are slow

The kernel accumulates a `BLOCK_M x BLOCK_N` int32 tile in registers. With 4 warps on a 128 x 128 tile that is more than the register file holds, even after the Triton XPU backend recompiles it with 256 GRF per thread (which it does on its own when spills exceed 1,000 bytes). One GEMM, M = 2048, N = 8704, K = 5120; spill is the Level Zero `spillMemSize` of the compiled kernel, as Triton reports it in `n_spills`:

| tile | warps | GRF per thread | spill bytes | us | TOPS |
|---|---|---|---|---|---|
| 128, 128, 128 | 4 | 256 | 29,632 | 15,703 | 11.6 |
| 128, 128, 128 | 8 | 256 | 6,592 | 1,675 | 109.0 |
| 128, 128, 128 | 16 | 256 | 448 | 1,498 | 121.9 |
| 128, 128, 128 | 32 | 128 | 0 | 1,438 | 127.0 |
| **256, 128, 128** | **32** | 256 | 448 | **876** | **208.4** |

For 64 < M <= 128 the same holds. At M = 128, N = 17408, K = 5120, the current `(64, 128, 128)` with 4 warps spills 6,592 bytes at 256 GRF and takes 383 us (59.6 TOPS); `(128, 128, 32)` with 16 warps does not spill at 256 GRF and takes 225 us (101.4 TOPS).

Setting `grf_mode` explicitly did not help: `256` and `auto` match the default (which already escalates to 256), and `128` is slower. So the warp count and the tile are what can be changed. These probes reuse one weight, so their times are with the weight in L2; the kernel table below is not.

## Details

The two branches follow where the current heuristic already splits (M = 128). Up to 128, a 128-row tile covers M in one row block, so every weight is read once, as in #64190. Above that, the 256 x 128 tile with 32 warps was the best or at most 3.1% slower at every M from 192 to 2048 on all three shape sets, so one tile serves the whole range rather than a table per M.

The branch is gated on `current_platform.is_xpu()` and reads only the shape, as in #64190. fp8 inputs are not affected in practice: no XPU linear passes fp8 to `triton_scaled_mm` (the Triton FP8 linear kernel is CUDA/ROCm only).

I have only measured an Arc Pro B70; other Intel GPUs may prefer other tiles.

## AI disclosure

Claude Code with Opus 5.5 medium (Anthropic) found the slow tiles above M = 64 while setting the cut for #64190, traced the time to first token to them, read the spill sizes of the compiled kernels, ran the tile sweeps and the end-to-end measurements, quantized Muse-Glimmer-30B to INT8, wrote the change and drafted this description. I proposed Muse-Glimmer-30B as a second model so that the rule is not fitted to one architecture. I asked whether it had been measured end to end, which it had not, and had those runs go first, with the unit tests rerun after the tile for 64 < M <= 128 changed. I asked what the existing tests cover, which showed that no case reaches 64 < M <= 128, and chose to add one case at M = 96 rather than two. It also compared the result with the GPTQ INT4 checkpoint; I had it check which path GPTQ takes on XPU (oneDNN, with bf16 compute) and withdraw the comparison. It framed this as a `[Perf]` change; I had the title also say that it fixes register spills, and state the speedup. I reviewed the diff, the description, and the end-to-end results with the commands that produced them in full.
