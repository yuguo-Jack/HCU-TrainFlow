# [Perf][KV Connector][Mooncake] Vectorize transfer descriptor build

[Upstream PR](https://github.com/vllm-project/vllm/pull/62478) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

`_build_transfer_params` groups the same block ids again for every registered region and builds each descriptor in a Python loop. This PR groups once per KV group and request and computes each region's descriptors with NumPy. The output is unchanged: same values, same order, Python ints.

The branch is rebased on #63142 and keeps its normalization. That PR reduces how many descriptors there are; this one makes building the remaining ones cheap. Related: RFC #63006.

## Claims

Measured against main `41f5146b5`, which includes #63142.

- In a 1P1D serving run, `_build_transfer_params` takes 0.77 ms instead of 12.8 ms on fragmented calls (median). Those calls are about half of all calls under load.
- Mean TTFT drops by 6.5 / 10.8 / 7.9 ms at 3 / 5 / 6 req/s. The paired 95% CIs exclude zero.
- Greedy outputs are identical to main.

## Validation

**Unit tests** (nightly `41f5146b5`, `huggingface-hub==1.31.0` as in CI): `test_mooncake_connector.py` and `test_mooncake_connector_hybrid_mamba.py` give 140 passed on main and 146 passed with this PR. The 6 new tests cover run boundaries, and fragmented ids that #63142 does not merge. The hybrid test now patches `_contiguous_runs`.

**Equivalence.** I extracted `_build_transfer_params` from main and from this PR and ran both on 2,000 randomized inputs. Inputs covered multiple layers, KV groups, Mamba null blocks, shared packed regions, heterogeneous TP, non-coalescible rows and prefix trimming. Outputs were identical.

**Microbenchmark.** One request through the real method, 64 KiB regions, Xeon 8358P:

| Layers × blocks | Block ids | Descriptors | main | this PR |
|---|---|---:|---:|---:|
| 28 × 224 | ascending or jointly descending | 28 | 1.93 ms | 0.38 ms |
| 28 × 224 | random | 6,272 | 13.07 ms | 0.80 ms |
| 64 × 500 | random | 32,000 | 74.50 ms | 2.54 ms |

**End to end.**
- Setup: 1P1D on two hosts, A800 + ConnectX-6 200 Gb/s, DeepSeek-MoE-16B BF16, TP=1, block size 16, no prefix caching, `mooncake_connector_proxy.py`.
- Load: open-loop Poisson arrivals of 3,584-token prompts, 80 per rate, with the same seed for every run.
- Runs alternated main / PR / PR / main, and requests were compared pairwise.

| | main | this PR |
|---|---:|---:|
| `_build_transfer_params`, fragmented calls, median / p90 | 12.83 / 20.08 ms | 0.77 / 1.32 ms |
| `_build_transfer_params`, other calls, median | 2.73 ms | 0.45 ms |
| TTFT Δ, 3 / 5 / 6 req/s (paired mean, 95% CI) | — | −6.5 [−9.9, −3.1] / −10.8 [−15.4, −6.4] / −7.9 [−13.2, −2.5] ms |
| TTFT p50 Δ, single 3,584-token request | — | −11.5 ms |

Block ids under this load stay fragmented after #63142. Only about 1% of requests merge into one run. The median request (224 blocks) has 101 runs per layer, down from 213 without #63142.

## Details

- After #63142's normalization, block ids are the same for every region of a KV group. So `_contiguous_runs` computes the runs once per `(group_index, shared_group_ids)`, and each region's addresses come from one NumPy expression. Regions are visited in the original order. Heterogeneous TP, replicated KV, shared packed regions and Mamba handling are unchanged. `_contiguous_runs` replaces `group_concurrent_contiguous`.
- #60605 rewrites that same helper. Before #63142, on the same setup, a fragmented call took 2.7 ms with #60605 and 0.7 ms with this PR. If this one is preferred, I'm happy to carry over its tests and credit @feidudeqiu.
