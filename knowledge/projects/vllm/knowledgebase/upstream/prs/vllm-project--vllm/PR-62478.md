# [Perf][KV Connector][Mooncake] Vectorize transfer descriptor build

[Upstream PR](https://github.com/vllm-project/vllm/pull/62478) · state: open · merged: False

## Original PR description



## Overview

`MooncakeConnectorWorker._build_transfer_params` groups the same block ids again for every registered region, then builds each descriptor in a Python loop. This PR groups the ids once per KV group and request, and computes each region's descriptors with NumPy. The returned `(src_ptrs, dst_ptrs, lengths, err_reqs, err_msg)` are unchanged: same values, same order, still Python ints.

Related: #60605 targets the same cost by rewriting `group_concurrent_contiguous`. This PR takes a different approach and replaces that helper. The subsection "Comparison with #60605" under Validation compares the two on the same setup.

## Claims

- In a 1P1D serving run, `_build_transfer_params` drops from 13.4 ms to 0.70 ms (median) when block ids are fragmented. That is 6,272 descriptors per call, and it was 70% of calls under load. With #60605 the same calls take 2.7 ms.
- Mean TTFT drops by 7.0 / 19.0 / 9.8 ms at 3 / 5 / 6 req/s (paired, 95% CIs exclude zero), and the single-request p50 drops by 13.3 ms at 3,584 tokens.
- Compared with #60605, the function is 3.8× faster in serving (2.73 → 0.71 ms). At the shapes benchmarked in #60605, it is 6.0–6.7× faster: 48 × 500 goes from 11.25 to 1.87 ms, and 64 × 500 from 16.00 to 2.38 ms, a further 9.4–13.6 ms per request.
- Greedy outputs are identical to the unpatched connector.

### Comparison with #60605

Both PRs target the same function. #60605 keeps the per-region structure and replaces the NumPy split inside `group_concurrent_contiguous` with a Python scan. This PR restructures the build: ids are grouped once per KV group, and descriptors are computed with NumPy.

| | #60605 | this PR |
|---|---|---|
| Grouping | once per registered region (28–64 times per request), Python scan | once per KV group and request, NumPy, no split (`_contiguous_runs`) |
| Descriptor addresses | Python append per descriptor | one NumPy expression per region |
| Output | unchanged | unchanged |
| Fragmented call in serving (6,272 desc), median | 2.73 ms | 0.70–0.71 ms |
| 48 × 500 descending, microbenchmark | 11.25 ms | 1.87 ms |
| 48 × 500 ascending (coalesced), microbenchmark | 2.42 ms | 0.50 ms |
| TTFT vs main, 3 / 5 / 6 req/s | −9.5 / −9.2 / −5.8 ms | −7.0 / −19.0 / −9.8 ms |
| TTFT vs #60605, single request 3,584 tokens | — | −2.0 ms |
| TTFT vs #60605, 3 / 5 / 6 req/s (paired, interleaved runs) | — | −0.7 [−2.2, +1.1] / −2.1 [−5.3, +1.5] / −2.3 [−4.3, −0.3] ms |

This PR covers what #60605 fixes, the NumPy split. It also removes the two costs #60605 leaves in place: regrouping the same ids for every region, and one Python append per descriptor. Both of those scale with layers × blocks, so the gap widens on larger models. Per request, this PR saves a further 1.9 ms at 28 × 224, 9.4 ms at 48 × 500 and 13.6 ms at 64 × 500; the last two are the shapes benchmarked in #60605. In the 28-layer end-to-end setup here, the further saving is about 2 ms per request. TTFT is 2.0 ms lower for a single 3,584-token request, and 0.7 / 2.1 / 2.3 ms lower at 3 / 5 / 6 req/s, which is significant at 6 req/s. Once grouping happens once per request, the grouping implementation itself no longer matters: about 0.02 ms in NumPy on these inputs.

Both PRs edit the same helper, so only one of them should land. If #60605 lands first, I will rebase on top of it. If this one is preferred, I am glad to bring over #60605's grouping tests and its equal-length check, crediting @feidudeqiu.

## Details

- **Where it runs.** D sends its block ids. P waits until the request's prefill is done, then the sender calls `_build_transfer_params` and `batch_transfer_sync_write`. The build therefore sits between "KV ready" and "transfer starts" for every request.
- **Why ids fragment.** With prefix caching off, the free block queue behaves like a stack, as noted in #60605, so a request often receives descending block ids. Only runs that ascend on both sides coalesce. Every (layer, block) then becomes its own descriptor: 28 × 224 = 6,272 for a 3,584-token prompt in this setup.
- **What changes.** Block ids are the same for every region of a KV group. Runs are therefore computed once per `(group_index, shared_group_ids)` with `np.diff`, without splitting. Each region's addresses are then one NumPy expression, either over run starts (coalesced) or over all blocks (per-block). Regions are still visited in their original order, so the output order is unchanged. Heterogeneous-TP offsets, replicated-KV skips, shared packed regions and Mamba handling are untouched.
- **Not changed.** Descending runs still produce one descriptor per block. Merging runs that descend on both sides would cut the descriptor count by up to the number of blocks, and with it the transfer engine's per-descriptor work. It changes the output, though, so it is left for a separate PR.
