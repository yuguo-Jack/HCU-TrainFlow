# [Model] Add NVIDIA Canary (nvidia/canary-1b-v2) speech-to-text support

[Upstream PR](https://github.com/vllm-project/vllm/pull/64215) · state: closed · merged: True

## Original PR description



## Overview

Adds `CanaryForConditionalGeneration` for [`nvidia/canary-1b-v2`](https://huggingface.co/nvidia/canary-1b-v2) (FastConformer encoder + Transformer decoder; 25 European languages, ASR + X↔En speech translation). It targets the native Transformers checkpoint layout (`model_type: canary`, available since Transformers 5.16, which vLLM already pins), so no `.nemo` conversion or `trust_remote_code` is needed.

A user asked on the vLLM Slack whether `nvidia/canary-1b-v2` could work. No existing issue or PR: `gh pr list --search canary` / `gh issue list --search canary` only return unrelated NIXL "import canary" CI items.

The decoder is built from vLLM layers; the FastConformer encoder reuses the Transformers module, as `parakeet.py` already does (see Details).

## Claims

- `nvidia/canary-1b-v2` loads and serves via `LLM` and `/v1/audio/transcriptions` + `/v1/audio/translations` (source language from `language`, target from `to_language`, default `en` for translations).
- Greedy output is token-identical to Transformers `CanaryForConditionalGeneration.generate` on the clips below (fp32 and bf16, batched).
- WER on the existing `test_wer_correctness` earnings22 slice: 12.34 (vLLM, bf16, CPU) and 12.336 (vLLM, bf16, L40 GPU, unmodified test) vs 12.46 (Transformers, fp32); 12.34 is added as the expected value for `nvidia/canary-1b-v2`.

## Details

- **Decoder** is native vLLM: reuses `CohereASRAttention` / `CohereASRCrossAttention` / `CohereASRMLP` from `cohere_asr.py` (Transformers' Canary is itself a subclass of its Cohere ASR model). Differences from Cohere ASR: `[sin | cos]` positional table (vs interleaved), no encoder→decoder projection, `proj_out` with bias. Weight renames are decoder-scoped regexes in `hf_to_vllm_mapper`.
- **Encoder** currently reuses Transformers' `ParakeetEncoder` as-is, the same way `parakeet.py` does for Nano Nemotron VL. Checkpoint names match 1:1, so correctness comes from the reference implementation. I'm keeping it this way in this PR: no ASR encoder in vLLM uses tensor-parallel layers yet (`cohere_asr.ConformerEncoder` also uses plain `nn.Linear`), so swapping in the Cohere ASR encoder would remove duplicated code without a TP or kernel benefit, and the model fits on one GPU. Sharing `cohere_asr.ConformerEncoder`, which needs a config adapter because it reads NeMo-style config dicts, could be a follow-up if reviewers prefer.
- **Processor**: `CanaryProcessor` renames `input_ids` → `decoder_input_ids`, so `_call_hf_processor` calls `ParakeetFeatureExtractor` and the tokenizer directly. Features are extracted per clip and passed with `feature_lengths`; the encoder mask is rebuilt after padding.
- **Prompt**: the same control-token sequence as the checkpoint's `chat_template.jinja` (`<|startofcontext|><|startoftranscript|><|emo:undefined|><|src|><|tgt|><|pnc|><|noitn|><|notimestamp|><|nodiarize|>`).
- **Languages**: `validate_language` rejects languages outside the 25 trained ones instead of the base class's warn-and-continue, because the prompt needs a trained language token; with `ja` the model silently returned empty text.
- **Limitations / TODO**: `max_audio_clip_s=40` is my choice for vLLM's chunker (NeMo uses its own dynamic chunking for long-form); no timestamps/ITN/diarization control tokens exposed yet (always `noitn/notimestamp/nodiarize`, punctuation on); TP not tested.

🔴 Translation requests without a `language` field, the stock OpenAI SDK default, return a plain en→en transcription instead of a translation. `validate_language` turns a missing language into "en", and `get_generation_prompt` then defaults the target to "en". The prompt therefore asks for an English→English transcription, so German audio is decoded as English. Only a warning that names TranscriptionRequest is logged. Fix: for `task_type == "translate"`, reject the request with a 400 when the source language was not supplied or equals the target, while still allowing the transcription default of "en".

<details>
<summary>Why this was flagged</summary>

A client calls `/v1/audio/translations` with German audio and no `language`. This is the stock OpenAI `client.audio.translations.create`, which has no language parameter. In serving.py:269 the request goes through `CanaryForConditionalGeneration.validate_language(None)` (canary.py:457-463), which logs a warning and returns "en". In `get_generation_prompt` (canary.py:492-497) the source is "en", and because `to_language` is None the target also becomes "en". The decoder prompt is therefore `<|en|><|en|>`, an English ASR prompt. The endpoint returns HTTP 200 with the audio forced through English transcription, not an English translation. No error tells the client to supply `language`. Nothing in the code guards against this: Canary sets no `supports_explicit_language_detection`, so serving.py:286 never auto-detects the language. The `get_generation_prompt` check at canary.py:493 cannot fire because the language was already defaulted.

**Verification:** In base/serving.py:269, Canary's `validate_language` (canary.py:457-463) sets a missing `language` to "en". For task_type "translate", canary.py:497 sets `target_language = stt_params.to_language or "en"`, which is also "en". The decoder prompt built at canary.py:505 therefore has `<|en|><|en|>`. The request returns 200 with wrong text, and the only signal is a server-side warning.

</details>

🟡 (optional) Translation requests between two non-English languages (for example `language=de`, `to_language=fr`) are accepted, but the model was never trained for them, so output is silently unreliable. In `get_generation_prompt`, a translate task only checks that the target is in `supported_languages`, not that one side is `en`. canary-1b-v2 translates only X→En and En→X. Fix: for `task_type == "translate"`, raise ValueError unless `source_language == "en"` or `target_language == "en"`, the same reject-don't-guess policy `validate_language` uses. Translation from or to English keeps working.

<details>
<summary>Why this was flagged</summary>

A client calls `/v1/audio/translations` with `language=de` and `to_language=fr`. `serving.py:269-273` runs both values through `CanaryForConditionalGeneration.validate_language`, and both pass because both codes are in `CANARY_SUPPORTED_LANGS`. `get_generation_prompt` (canary.py:496-503) then builds the prompt `<|de|><|fr|>` without checking the pair. The model card for nvidia/canary-1b-v2 lists only English→24 languages and 24 languages→English translation. A non-English pair is outside training, so the request returns HTTP 200 with low-quality or empty text instead of a 400. The PR description says `validate_language` was made strict because an untrained language token made the model silently return empty text (the `ja` case). The pair check leaves that same failure mode open for translation.

**Verification:** Trigger: a translation request where neither side is English (e.g. `language=de`, `to_language=fr`). In `get_generation_prompt` (canary.py ~491-503), the translate branch only checks `target_language not in cls.supported_languages`. Nothing checks whether either side is `en`. `supports_transcription_only = True` does not block this. The request is accepted silently and returns output of unknown quality.

</details>
