## Original PR description

# [Bugfix] Floor the M-RoPE cache on the served window

Fixes #62383. This was a regression introduced in v0.32 where the engine can crash with Qwen 3.8 Flash Next.

## TL;DR

For scaling rope types (`yarn`/`longrope`), `get_rope()` builds the rope instance with
**`original_max_position_embeddings`** — the *pre-scaling* window — while served
positions still reach the full window (`max_model_len` = original × factor).
`MRotaryEmbedding` then allocated `base × 4` rows unconditionally, which silently
covered the gap for any scaling factor ≤ 4. #59853 correctly made that headroom
conditional (`positions_factor=1` for text serving) but did not account for the
scaling gap it was masking: since v0.32.0, **any m-RoPE model served with length-
extension rope scaling reads past the end of its cos/sin cache as soon as positions
cross `original_max_position_embeddings`**. The first consumer to fault is the MTP
draft path under CUDA graph replay.

Fix: `cache_max_position_num = max(base × positions_factor, max_model_len)` — exact
for every (model, rope type, served window) combination, bit-identical to current
behavior for native-window serving.

## Root cause, step by step

1. `get_rope()` (`rotary_embedding/__init__.py`), yarn branch:

   ```python
   elif scaling_type == "yarn":
       original_max_position = rope_parameters["original_max_position_embeddings"]
       ...
       rotary_emb = MRotaryEmbedding(head_size, rotary_dim, original_max_position, ...)
   ```

   Whatever the model passed as `max_position` is discarded; the constructor base is
   the *native* window. (The neighboring deepseek branch still carries the commented
   `# assert max_position == original_max_position * scaling_factor` — the invariant
   this class quietly depends on and nothing enforces.)

2. `MRotaryEmbedding.__init__`: `cache_max_position_num = max_position_embeddings *
   positions_factor`. `scaling_factor` is used only for inv-freq/mscale math — never
   to size the table. So with YaRN factor 2.0 and `positions_factor=1`, a deployment
   serving 524,288 positions allocates 262,144 rows.

3. Under CUDA graphs, the MTP draft path captures kernels with dummy (small)
   positions and replays with real ones; at the first prefill chunk whose positions
   cross the native window, a captured gather indexes past the cache allocation.
   The fault surfaces asynchronously against whatever kernel is resident — host
   `dmesg` shows it precisely: **`Xid 31 ... MMU Fault: ... FAULT_PDE
   ACCESS_TYPE_VIRT_READ` from `VLLM::Worker`**. The target-only path did not fault
   at these positions, which is why the repro needs spec-decode + cudagraphs — the
   same factorization independently reproduced in #62383 (H200, `enforce_eager`
   × spec-off 2×2 matrix) and here (SM120).

## Instrumentation evidence

Printing every `MRotaryEmbedding.__init__` (cache size + construction stack) on the
stock v0.32.0 image with `--max-model-len 524288`, YaRN 2.0 via `--hf-overrides
text_config.rope_parameters`, MTP(3) + CUDA graphs:

```
[MRDEBUG] cache_max_position_num=262144 ctor_max_position_embeddings=262144 factor=1
  stack=__init__.py:114 | qsa.py:427 | model.py:254 | mtp.py:224 | ...
[MRDEBUG] cache_max_position_num=262144 ctor_max_position_embeddings=262144 factor=1
  stack=__init__.py:260 | qsa.py:427 | model.py:254 | model.py:440 | ...
```

Both instances — target *and* MTP drafter — get 262,144 rows while the engine happily
accepts prompts to 524,288 positions. The crash boundary equals this row count in
both deployments (#62383's H200 repro crashes at 262,400 positions with a 262,144-row
cache; ours faults at 280,069 with the same cache). The drafter's instance is built
through the `default` branch, so the undersizing does not even require the yarn
branch — the model-supplied base is *already* native.

## Discriminator experiments (all on stock v0.32.0 images, single-variable)

| Change | Result |
|---|---|
| stock | crash at >262,144 positions, Xid 31 READ; pass at 260,069 |
| restore `* 4` in `mrope.py` only | pass at 480K → defect is cache *size*, not YaRN math |
| model-side `max_position=max(cfg.max_position_embeddings, max_model_len)` at the `get_rope` call site | **still crash, ctor still prints 262,144** → the factory overrides the caller's base; model-side fixes cannot work |
| `--hf-overrides` forcing `max_position_embeddings` (either nesting level) | cannot change the cache size — nested form is ignored by this code path; top-level form fails boot validation because the derived ceiling is `native × factor` regardless |
| `max_model_len` floor on `vllm_config.model_config` only | target cache grows to 524,288 but the drafter stays 262,144 (draft-time config resolves to the draft's own `ModelConfig`) — **still crashes**: both instances must follow the target's window |
| this patch (target-aware floor) | both instances build with `cache_max_position_num=524288`; 280,070-token retrieval passes (`prompt_tokens=280070`, needle `5d0a5ccffe18a92014f9`) and 480,071-token passes (`2aa985f46a298ee1b219`) on the exact stock-crashing config, engine healthy after both — the only runs that ever survived those lengths on unpatched v0.32.0 |

## How this was introduced, and why six weeks went by unnoticed

| Commit | Date | Role |
|---|---|---|
| `bf3b79efb` ([VLM] Qwen2.5-VL) | 2025-02-05 | adds the blanket `cache_max_position_num = max_position_embeddings * 4` for video-duration positions — this also (accidentally) covered scaling-factor ≤ 4 for YaRN-served m-RoPE models |
| `6ad6b8e11` (#22192 ROPE refactor) | 2025-08-04 | moves the headroom into `mrope.py` unchanged |
| `e126687a9` (#53896 Qwen3.8-Flash-Next) | 2026-08-31 | first m-RoPE model family that is commonly deployed with YaRN beyond its native window (ships in v0.29.0, masked by the 4x) |
| `a98247ab4` (#59853) | 2026-10-10 | headroom → conditional `positions_factor`; first released in v0.32.0 — unmasking the sizing gap |

Invisibility had three layers: the 4x headroom itself; no upstream test serving an
m-RoPE model past its native window; and the async, spec-decode-and-graphs-only fault
delivery (eager and target-only runs at the same prompt lengths pass cleanly, so CI
and manual prefill tests see nothing).

## The fix

```python
served_window = 0
try:
    from vllm.config import get_current_vllm_config

    vllm_config = get_current_vllm_config()
    # Same resolution as mrope_positions_factor(): a drafter gets the
    # target's positions, so its cache must cover the target's window.
    spec = vllm_config.speculative_config
    model_config = (spec and spec.target_model_config) or vllm_config.model_config
    served_window = int(model_config.max_model_len or 0)
except Exception:
    # No engine context (unit tests constructing rope directly).
    pass
self.cache_max_position_num = max(
    max_position_embeddings * positions_factor, served_window
)
```

- `max_model_len` is the engine's own hard bound on positions (validation in
  `ModelConfig` enforces it against the derived window, and `VLLM_ALLOW_LONG_MAX_MODEL_LEN`
  users get exactly the allocation they asked for), so every raw index any path —
  target, drafter, indexer — can produce is in-bounds by construction.
- The `spec.target_model_config` indirection is not decoration: an experiment with
  the simpler `vllm_config.model_config`-only floor fixed the target instance
  (524,288 rows) but left the drafter's at 262,144 — during MTP construction the
  current config resolves to the draft's own `ModelConfig`, whose `max_model_len`
  is natively derived — and the repro still crashed. #59853's
  `mrope_positions_factor()` had already solved and documented exactly this ("A
  drafter gets the target's positions, so it follows the target"); this patch
  mirrors its resolution rule.
- Memory: native-window serving is unchanged (base × factor ≥ window there). Video
  pruning keeps its 4x. YaRN-scaled serving grows the table by exactly the extra rows
  the scaling requires — strictly *less* than the pre-#59853 blanket 4x for factors
  below 4, and no wasted headroom above.
- Alternative considered and rejected: multiplying by `scaling_factor` inside
  `MRotaryEmbedding` — fails for models whose undersize comes from the caller's
  native base through the `default` branch (our MTP drafter instance is exactly
  that case), and duplicates config logic the engine already validates.

## Test plan

- [x] Stock v0.32.0 repro: crash at 280,069 (Xid 31 READ), pass at 260,069
- [x] Instrumented ctor: 262,144-row cache on both target and drafter instances
- [x] Model-side call-site patch proven ineffective (factory override) — motivates fixing in `MRotaryEmbedding`
- [x] With this patch, exact repro config: both ctor prints show `cache_max_position_num=524288`; 280,070 and 480,071 retrieval pass, engine healthy after both
- [x] Native-window regression: serve at 262,144 with no rope overrides — single shared rope instance, `cache_max_position_num=262144` (bit-identical to stock), 8K retrieval green
- [x] Spec-off and `enforce_eager` at the same lengths remain green on unpatched v0.32.0 — established independently by the #62383 factorization matrix; this patch does not alter their code paths (only adds cache rows when the served window exceeds the rope base)
