# [Perf][Core] Keep per-block KV cache state out of the cyclic GC

[Upstream PR](https://github.com/vllm-project/vllm/pull/64700) · state: closed · merged: False

## Original PR description



## Overview

Keep EngineCore's per-block KV cache state out of CPython's cyclic GC: each request's block hashes live in one `bytearray`, each request's block table is an `array('i')` of block ids, and the prefix-cache index maps hashes to block ids. Before, each full GC pass visited one Python object per block of every running request and of every cached block. This removes the cost that #63306 hides with `gc.freeze()`, for the per-block structures; #62702 does the same for token ids (see RFC #63363).

## Claims

- 256 running requests × 128K-token prompts with prefix caching, real `Scheduler`, token ids as int32 (as with #62702): a full GC pass drops from 86 ms (1 KV cache group) / 295 ms (4 groups) to 0.1–0.2 ms. With token ids still `list[int]`, it drops from 216 / 427 ms to 129 ms; the rest is the token lists.
- GC-tracked container items: 6.3M → 14K (1 group), 18.9M → 14K (4 groups).
- Scheduler decode step is not slower: 4 groups 3.58 → 3.53 ms (−1.5%, from a cheaper early return in `cache_blocks`), 1 group within noise.
- No behavior change: same blocks, hashes, prefix hits and KV events. Each block reference shrinks from an 8-byte pointer to a 4-byte id, each hash from a `bytes` object (~65 B plus an 8-byte pointer) to 32 bytes.

from array import array

import tests.v1.core.utils as u
from vllm.utils.gc_utils import freeze_gc_heap
from vllm.v1.kv_cache_interface import KVCacheConfig, KVCacheGroupSpec
from vllm.v1.outputs import ModelRunnerOutput

NUM_GROUPS = int(sys.argv[1])
NUM_REQS, PROMPT, BLOCK = 256, 131072, 16


def multi_group_config(*, kv_cache_groups, **kw):
    spec = kv_cache_groups[0].kv_cache_spec
    groups = [KVCacheGroupSpec([f"layer{i}"], spec) for i in range(NUM_GROUPS)]
    return KVCacheConfig(kv_cache_groups=groups, **kw)

    max_num_seqs=NUM_REQS, max_num_batched_tokens=NUM_REQS * PROMPT,
    num_blocks=NUM_GROUPS * (NUM_REQS * (PROMPT + 4096) // BLOCK) + 1024,
    block_size=BLOCK, max_model_len=PROMPT + 4096, enable_prefix_caching=True,
    use_v2_model_runner=True,

freeze_gc_heap()  # what EngineCore does after startup
reqs = u.create_requests(num_requests=NUM_REQS, num_tokens=PROMPT,
                         block_size=BLOCK, max_tokens=4000)
for r in reqs:
    sched.add_request(r)
ids = [r.request_id for r in reqs]
idx = {rid: i for i, rid in enumerate(ids)}


def step():
    out = sched.schedule()
    sched.update_from_output(out, ModelRunnerOutput(
        req_ids=ids, req_id_to_index=idx, sampled_token_ids=[[7]] * NUM_REQS,
        logprobs=None, prompt_logprobs_dict={}, pooler_output=[]))


def full_gc_ms():
    ts = []
    for _ in range(3):
        t = time.perf_counter(); gc.collect(2); ts.append(time.perf_counter() - t)
    return min(ts) * 1e3


step()
print(f"full GC, token ids list[int]: {full_gc_ms():.1f} ms")
for r in reqs:  # token ids as int32, as with #62702
    r.prompt_token_ids = array("i", r.prompt_token_ids)
    r._all_token_ids = r.all_token_ids = array("i", r._all_token_ids)
print(f"full GC, token ids int32: {full_gc_ms():.1f} ms")
gc.disable()
for _ in range(20):
    step()
ts = []
for _ in range(5):
    t = time.perf_counter()
    for _ in range(64):
        step()
    ts.append((time.perf_counter() - t) / 64 * 1e3)

## Details

**Root cause.** A full collection visits every element of every tracked container. Three EngineCore structures hold one GC-tracked object per block and grow with context length:

- `Request.block_hashes`: `list[bytes]`, one entry per hash block.
- `SingleTypeKVCacheManager.req_to_blocks[req]`: `list[KVCacheBlock]` per request and KV cache group.
- `BlockPool.cached_block_hash_to_block`: a dict from hash to `KVCacheBlock`, one entry per cached block, alive whether or not requests are running.

**Changes.**

- `BlockHashBuffer` (`vllm/v1/request.py`): hashes of one width packed back to back in a `bytearray`; indexing returns `bytes`, slicing returns `list[bytes]`. It supports the list operations the code uses (`len`, indexing, slicing, iteration, `extend`, `clear`, tail deletion for streaming sessions).
- `KVCacheBlockList` (`vllm/v1/core/kv_cache_utils.py`): an `array('i')` subclass of block ids that maps back through the pool's `blocks` list (`blocks[i].block_id == i`). Subclassing `array` keeps `len()` in C; a Python `__len__` cost 5–10% of the decode step at 4 groups in an earlier version.
- `BlockHashToBlockMap` stores block ids. CPython does not track a dict whose keys and values are all atomic, so the hash → id dict is never traversed. Keys cached by several blocks keep all their ids in a small side dict, since a container value would make the main dict tracked again.
- `cache_blocks` returns early when `num_tokens // block_size` shows no new full block, before reading `len(request.block_hashes)`; this skips most decode steps and offsets the Python-level `__len__` of `BlockHashBuffer`.

**Serialization.** `BlockHashBuffer` pickles, but msgspec cannot encode it, so every path that sends block hashes out of the scheduler was checked:

| Path | Serializer | Result |
|---|---|---|
| SchedulerOutput and KV connector metadata to workers (incl. Mooncake store `ReqMeta`, which holds `block_hashes` by reference) | pickle via `shm_broadcast` | OK: the buffer pickles; workers only index, slice and take `len` |
| KV events (`BlockStored` to routers) | msgspec | OK: every builder passes a new list or tuple built from slices or elements (core `block_pool.py`, offloading, UMBP, simple offload, Mooncake worker); LMCache events come from LMCache's own objects |
| Aux output connector | its own bytes packing | OK: slices, then `b"".join` |
| LMCache MP | to the LMCache server | OK: `len`, slicing and `islice` over single `bytes` |
| Other msgspec users (NIXL, Mooncake P2P, MoRIIO, engine core and client) | msgspec | OK: they do not touch `block_hashes` |

**Tradeoffs and limitations.**

- Relies on CPython GC behavior: `array` and `bytearray` are not GC containers, and a dict of only atomic keys and values stays untracked. Both hold on all supported CPython versions.
- Block hashes must share one width, which every `--prefix-caching-hash-algo` produces (32 bytes for sha256, 16 for xxhash). Test helpers that used the builtin `hash` now default to `sha256`.
- `KVCacheBlockList` assumes a manager only stores blocks of its own pool, which all managers do.
- Tests that read `BlockHashToBlockMap._cache` or popped from `block_hashes` are updated to the new layout.

**Related work.** Not a duplicate: no open PR changes these structures for GC. #63306 freezes the heap after admitting requests and covers everything at once, but hides objects rather than removing them and leaves young-generation passes over requests not yet frozen; the two are complementary, and with this PR plus #62702 the freeze becomes a safety net. #58891 (collapse a duplicate entry back to one block after eviction) is subsumed by the new map, which drops the side entry when one id remains. #59380 refactors `get_one_block` and would conflict textually. SGLang avoids per-page objects through a path-compressed radix tree whose nodes hold token arrays and KV-index tensors; vLLM keeps its hash index, which KV events, connectors and hybrid models rely on, and only stops it from holding objects.
