# [Bugfix][Kernel] Apply one more decay step in lightning_attention prefill

[Upstream PR](https://github.com/vllm-project/vllm/pull/63446) · state: open · merged: False

## Original PR description

## User impact
Sequences longer than one prefill block (256 tokens) computed with lightning attention come out wrong: the reported repro shows ~2.6x the output RMS error on tokens 256+ against a fixed-seed fp64 reference, and even the first token is wrong (error 4.9 vs 1.7e-6) when `kv_history` is non-zero. Any model using lightning attention with prefill beyond 256 tokens or chunked prefill produces silently degraded outputs. Independently reproduced by another user on main (comment on #61730: 2.6 relative error vs ~3e-6 reference).

## Technical cause
`_fwd_kv_reduce` stores into `KV[i]` the prefix state *before* block `i` (it writes `kv_pre` into the slot, then folds block `i`'s outer product into `kv_pre`), i.e. the state as of token `i*BLOCK - 1`. `_fwd_none_diag_kernel` then multiplies the query at intra-block offset `r = off_c*CBLOCK + c` by `exp(-s * r)` — but the distance from the stored state to that query is `r + 1` steps. The decay is one step short for every query.

The sibling kernel in the same file already uses the +1 convention: the diagonal kernel builds its key decay as `torch.exp(-s * (BLOCK - array))` with `array = arange(0, BLOCK) + 1`, i.e. distance-from-key-to-block-end counts the extra step.

## Fix
One line in `_fwd_none_diag_kernel` (line 381):

```python
q_decay = tl.exp(-s.to(tl.float32) * (off_c * CBLOCK + c_array[:, None] + 1))
```

This should bring prefill error from ~2.6x RMS down to numerical-noise level (~1e-5), and fix the kv_history first-token error. The backward kernels use a different formulation and are not touched; they are not exercised during inference.

Verified by code trace (this environment has no GPU to run the repro); happy to run the issue's fixed-seed repro in CI if a GPU runner is available.

Closes #61730
