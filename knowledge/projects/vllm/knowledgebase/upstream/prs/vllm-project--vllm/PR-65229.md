# [Bugfix][Spec Decode] Avoid catastrophic cancellation in the acceptance estimator

[Upstream PR](https://github.com/vllm-project/vllm/pull/65229) · state: open · merged: False

## Original PR description

## Overview

Follow-up to #52228, which added the estimator to do adaptive verification without a confidence head.

The adaptive-verification acceptance feature loses its entire signal to catastrophic cancellation whenever the drafter is confident. Every draft row more confident than `1 - 6e-8` reports the same acceptance feature, `40.0`, whatever its true confidence is. The feature is specified as a log-odds, `logit(q(m*))`, but it recovers the complement mass by subtracting 1 from a sum that includes the max's own unit term, which in fp32 destroys the quantity being measured — no NaN, no warning, just the clamp.

**Headline:** at temperature 0.5 on source code, **11.5% of draft positions** had their confidence score destroyed and replaced with a constant. The failing positions are not exotic or adversarial — the single worst case in the sample is completing `tl.int64` from `tl.int6` (see the `Details` section for the error analysis).

This PR computes the complement directly instead fixing completely the numerical issue.


## Claims

- The feature is accurate to fp32 relative precision across the full range it is clamped to. Previously it saturated to the `_MAX_LOG_ODDS` clamp for any row more confident than `1 - 6e-8`, collapsing a ~23-nat span of distinct confidences onto a single value.
- No change to the feature's definition, the fit, the trimming policy, or any buffer layout the rest of adaptive verification reads.
- One extra fp32 partial per (token, vocab block): 0.1% of the kernel's memory traffic (311 KiB against 311 MiB of logit reads at 1024 tokens and a 152k vocab). No extra kernel launch.
  
## Validation

`tests/v1/spec_decode/test_acceptance_estimator.py` — **18 passed in 7.08s**
on an NVIDIA H100  GPU, covering the pre-existing tests plus three new ones:

- `test_feature_resolves_a_tiny_complement_mass` — δ ∈ {1e-3, 1e-6, 1e-12} against an fp64 reference computed without ever forming `1 + δ`. Fails at 1e-6 and 1e-12 on `main`.
- `test_feature_combines_blocks_around_the_global_max` — parametrized over which of three vocabulary blocks holds the top token. Every pre-existing test used a 2048-token vocabulary, narrower than the kernel's 4096-wide block, so `num_blocks` was always 1 and the cross-block combine was dead code in the suite.
- `test_feature_drops_exactly_one_tied_maximum` — k tied maxima must leave k-1 in the complement, giving `-log(k-1)`. Parametrized over ties within one block and across blocks, which catch different mistakes and are each blind to the other's.

## Details

The estimator introduced in #52228 basically trains a logistic regression using as a feature the probability of the most likely draft token, $qmax$ , to construct a feature:

```math
f={logit}(qmax)                                                          
    =\log\!\left(\frac{qmax}{1-qmax}\right)
```

Let the temperature-scaled logits be $x_1 \ldots x_V$, and let $m=max_i x_i$, then

<!--
the *complement mass* $S$. Practically speaking, this is the sum of all the elements except for the maximum. In what follows, first I describe the math of what the current feature is and how it is computed, and then I introduce a block based approach that is not exposed to the same catastrophic cancellation. 



The estimator fits a logistic on one regressor per draft position: the log-odds of the draft distribution's most likely token,

```
feature = logit(q(m*)) = -log δ,     δ = Σ_{z ≠ m*} e^(z - m*)
```


δ is the *complement mass* — everything except the top token, relative to it. The original code recovered δ by summing all of it (the top token contributes `e^0 = 1`) and subtracting that 1 back off in fp32. Since fp32 spacing on `[1, 2)` is `2^-23 ≈ 1.19e-7`, the subtraction cancels δ away entirely once it drops below `2^-24`, and `-log(0) = inf` lands on the `±40` clamp.

The fix has each block emit its sumexp with the block argmax excluded, and substitutes that partial for the block holding the global max when combining. Every term is then non-negative and nothing cancels. The exclusion is by position rather than by value, so ties and `-inf` vocabulary padding each drop exactly one entry.


fp32 spacing on `[1, 2)` is `2^-23 ≈ 1.19e-7`, so `1 + δ` carries ~6e-8 of absolute error however small δ is, and for `δ < 2^-24` it rounds to exactly `1.0`. The subtraction then yields 0, `-log(0) = inf`, and the `±40` clamp turns that into a plausible-looking `40.0` — no NaN, no warning.
-->


####

```math
qmax=q_{i^*}=\frac{e^m}{\displaystyle\sum_{j=1}^V e^{x_j}}=\frac{1}{1+\sum_{j\ne i^*}e^{x_j-m}}
```

Let's define 

```math
S=\sum_{j\ne i^*}e^{x_j-m}
```

Then : 

```math
\begin{aligned}
q_{\max} &= \frac{1}{1+S} \\[6pt]
1-q_{\max} &= 1-\frac{1}{1+S} = \frac{1+S}{1+S}-\frac{1}{1+S}= \frac{S}{1+S}  
\end{aligned}
```

We can rewrite as:

```math
f=\log\left(\frac{qmax}{1-qmax}\right)=\log\left(\frac{1}{S}\right)=-\log S.
```




The computation of $S$ is what makes the current code in `main` exposed to catastrophic cancellation.

The previous approach (in `main`) computes $S$ (see the logic in the `_predict_kernel`) by summing the totals (`total_sumexp` in the code, $A$ in what follows) and then subtracting `1`:

```math
A = \sum_{j=1}^V e^{x_j-m} = 1 +S
```

```math
S = A - 1 = \left(\sum_{j=1}^V e^{x_j-m}\right)-1
```

The problem is that when there is a confident prediction (i.e. $qmax$ is high) $S$ must be small as $qmax=\frac{1}{1+S}$.  The result is that for a small $S$ (e.g. $S= 10^{-12}$) $A = 1.0 + S = 1.0 $. Therefore, $1.0 - 1.0 = 0.0$, and the final feature becomes $+\inf$, leading to a clamped value of $40.0$. The real value for the feature when $S= 10^{-12}$ would be instead $f = -\log(10^{-12}) \approx 27.63 \ldots$.


This PR introduced a block based algorithm to compute $S$ as a sum of positive quantities:

```math
S = \sum_{j\ne i^*}e^{x_j-M}
```

We introduce the function `_max_and_sumexps` which returns three quantities for each vocabulary block: its maximum logit, its full exponential sum, and its sum excluding *one* maximum position. 

For one block $b$, let $m_b$ denote its maximum, and $j_b$ a single index where that maximum occurs, the routines compute: 

```math                                                 
$$
\begin{aligned}
m_b &= \max_{j\in b} x_j,\\
A_b &= \sum_{j\in b} e^{x_j-m_b},\\
E_b &= \sum_{\substack{j\in b\\j\ne j_b}} e^{x_j-m_b}.
\end{aligned}
$$
```

The vocabulary is split into blocks (the new tests identify a width of \(4096\) elements). Each block has a different $m_b$, so its local $A_b$ and $E_b$ are expressed in a different exponential scale. They cannot be added without rescaling. 

Let's the global maximum and one selected winning block as:                           

```math
$$
M = \max_b m_b,\qquad b^* \in {argmax}_b m_b.
$$
```

For any token in block $b$, the identity $e^{x_j-M} = e^{x_j-m_b}\,e^{m_b-M}$  shows how to convert the block's local exponential sum to the global scale. Its factor is $e^{m_b-M}$.
This allows to perform the sum in blocks. What want to achieve is that the block that contains the actual max provides the sum omitting exactly one index, while the other blocks provide the full sum. 

This formula is simply a partition of $\sum_{j\ne i^*}e^{x_j-M}$ into blocks. 

```math
S=\sum_b e^{m_b-M}                                                                     
 \begin{cases}                                                                          
 E_b,&b=b^*,\\                                                                          
 A_b,&b\ne b^*.                                                                         
 \end{cases}     
 ```

- If $ b = b^* $, one globally maximal token must be left out, so use $E_{b^*}$.
- If $b \neq b^*$, every token in block $b$ belongs in the complement and the contribution is $e^{m_b-M}A_b$.


 
#### Error analysis setup

To simplify the analysis/data collection we use CPU code in python. The Triton path on the GPU (before the fix) has the same cancellation problem.

**Model: `Qwen/Qwen3-0.6B`**, loaded from the local Hugging Face cache in fp32 on CPU via `transformers`:

```python
tok = AutoTokenizer.from_pretrained("Qwen/Qwen3-0.6B")
model = AutoModelForCausalLM.from_pretrained("Qwen/Qwen3-0.6B", dtype=torch.float32).eval()
ids = tok(text, return_tensors="pt").input_ids[:, :512]
logits = model(ids).logits[0][:-1]        # drop the last row: no next token follows it
```

Chosen for three reasons:

1. **Plausible drafter size.** 0.6B is in the range actually used for draft models
2. **Production-scale vocabulary — 151,936 tokens.** The complement sums over the *whole* tail, so a large vocabulary adds roughly `log(V)` to δ and makes saturation **harder**. Measuring on a large vocabulary is therefore the `conservative choice`; a smaller-vocabulary drafter would saturate more often, not less.
3. **It spans three vocabulary blocks.** The kernel reduces in 4096-wide blocks, so 151,936 tokens exercise the cross-block combine rather than the single-block degenerate case.
   
   
We compute the `new` and `old` values as follows:

   ```python
# old: everything, then subtract the top token's own unit term
total = (sumexps * rescale).sum(dim=1)
old   = (total - 1.0).clamp(min=0.0)

# new: the max's own block contributes its excluding sum, so nothing cancels
use = sumexps.scatter(1, best_block[:, None], excl.gather(1, best_block[:, None]))
new = (use * rescale).sum(dim=1)
```

Reading this:

- **At temp 1.0 the bug is nearly invisible** — 0.2% of code rows, 0% of prose. A benchmark run at temperature 1.0 will show nothing, on any metric. This is worth stating plainly because it means "we A/B tested and saw no difference" is the *expected* result at that setting, not evidence the bug is benign.
- **The knee is between 0.8 and 0.5.** Saturation roughly doubles per 0.1 step of temperature through that range: 1.2% → 2.3% → 6.3% → 11.5%.
- **Greedy decoding (temp = 0) is a separate case.** `temp == 0` is mapped to `1.0` rather than dividing by zero, so greedy rows land in the temp-1.0 row of this table. They also mix an unscaled feature into the same shared slope as temperature-scaled rows, which is its own modelling issue and out of scope here.
- **Prose saturates slightly *more* than code below 0.6.** That surprised me; I had expected code to dominate throughout. Natural language has plenty of near-deterministic continuations too (fixed phrases, inflections, markup), and at low temperature those cross the wall just as easily. **The failure is not code-specific — code is simply where low temperatures are _*conventional*_.**

The practical reading: **temp ≤ 0.7 is where this starts to matter, and temp ≤ 0.5 is where it is common.
** Both are ordinary settings for code completion and structured-output serving.

## Fitted slope ω and intercepts b[k]

The estimator fits `p(accept) = σ(ω·f + b[k])`, where k is the draft position. Values
are medians over the second half of each pass, then across passes.

**Comparing ω across temperatures.** The feature is computed on temperature-scaled
logits, so roughly `f ≈ gap / T`: the same draft gives about twice the feature at T=0.5.
ω therefore halves from T=1.0 to T=0.5 even if nothing is wrong. The comparable quantity
is the slope per unit of logit gap, ω/T.

| model | arm | ω, T=1.0 | ω, T=0.5 | ω/T, T=1.0 → T=0.5 |
|---|---|---|---|---|
| DSV4 | main | — | 0.26 | — → 0.53 |
| DSV4 | pr | — | 0.29 | — → 0.58 |
| MiMo | main | 0.51 | 0.17 | 0.51 → **0.34** |
| MiMo | pr | 0.49 | 0.23 | 0.49 → **0.45** |
| Glimmer | main | 0.44 | 0.23 | 0.44 → 0.45 |
| Glimmer | pr | 0.45 | 0.27 | 0.45 → 0.54 |

- **MiMo:** on main, the slope per logit gap drops by a third at T=0.5. The fix recovers
