# [Perf][Qwen4Exp] Fuse HyperConnection up projection and gate mix for long prefills

[Upstream PR](https://github.com/vllm-project/vllm/pull/64898) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Fuse the HyperConnection up projection (rank 320 → 4 × 2560) and the gate mix (sigmoid gate, mean over the 4 HC streams) into one tcgen05 kernel for Qwen3.8-Flash-Next prefill on SM100.

`GatedResidual.mix` / `combine_and_mix` in `vllm/models/qwen4_exp/nvidia/hyperconnection.py` take the fused kernel once a forward has **≥ 512 tokens**. Below that, the existing GEMM + `hc_gate_mix` path stays.

At prefill sizes the serving chain writes a `[M, 10240]` bf16 gate (20 KB per token) only to read it back in `hc_gate_mix`. The fused kernel keeps the gate in TMEM. It is `csrc/qwen4_exp/hc_up_gate_mix.cu`, exposed as `torch.ops._C.qwen4_exp_hc_up_gate_mix`, and built for the SM100 family with CUDA ≥ 13, like the Kimi-K3 AttnRes kernel.

This is the NVIDIA/SM100, large-M counterpart of #64263, which fuses the same two ops in Triton for ROCm at decode sizes. It complements #58957, which fuses the HC *down* projection for decode batches of ≤ 48 tokens. Related work is under Details.

## Claims

1. **Kernel speed.** On B300, against the serving chain (cuBLAS GEMM + Triton `hc_gate_mix`), the fused kernel is **1.37× at M = 1280, 2.01× at 4096 and 2.26× at 16384**, reaching 53% of the HBM speed of light at M = 16384. It is faster than the chain from M = 32 up (0.84× at M = 1). Measured with CUPTI, cold L2 and CUDA graphs; the spread across processes is ≤ 2.6% from M = 64 up.
2. **Accuracy.**
   - **ULP bound:** max 0.51 bf16 ULP against an fp32 reference (gate, sigmoid and mix all in fp32). The unfused chain is at 1.87, because it rounds the gate to bf16. The ULP is taken relative to the magnitude of the summands.
   - **GSM8K:** full GSM8K is 0.964 / 0.968 / 0.970 on three PR servers vs 0.970 / 0.966 on `main`.
   - **Not bitwise:** the output is not bitwise equal to the chain, because the gate stays in fp32 and the sigmoid uses `tanh.approx`; it differs from the chain by at most 0.0078. See E2E accuracy for greedy outputs.
3. **E2E prefill, TP1.** Qwen3.8-Flash-Next-FP8 on one B300 per engine, 8k-token prompts, 1 output token. Input throughput rises **+3.1% at c1 and +3.8% at c4 / c16 / c64 on average** (+2.8% to +4.2% across 3 placements). Main-vs-main noise is −0.8% to 0.0%. The gain is close to what the kernel time predicts (+3.2% at c1, +3.9% to +4.0% at c ≥ 4), and TTFT drops by about the same amount.
4. **Where it does not apply.** All of these keep the existing code (the dispatch table is under Details):
   - batches below 512 tokens (decode and MTP verify);
   - non-SM100 GPUs and CUDA < 13 builds;
   - `VLLM_BATCH_INVARIANT=1`;
   - LoRA-wrapped HC projections.

The fused kernel's time is flat at about 6.7 µs up to M = 32 (one 128-row tile per column block), while the chain jumps between 48 and 64 tokens. The dispatch threshold in this PR is still 512 tokens. Lowering it towards 32 would also move decode and MTP-verify batches onto the fused path, so I'd rather do that separately, with decode E2E numbers.

SOL = max(ideal bytes / 8 TB/s, FLOPs / 2.25 PFLOP/s):
- **Ideal bytes:** `lowrank`, `xn` and `w_up` read once, and the output written once.
- **FLOPs:** 2·M·10240·320.
- **Regime:** the op is memory-bound but close to balanced: ~246 FLOP/B against a ridge of ~281. At M = 16384, SOL = 54.6 µs.

**How close to the practical ceiling.** At M = 16384:
- a streaming kernel that touches only the ideal bytes reaches 6.2 TB/s (70.3 µs), the same as `cudaMemcpy` of the same size;
- a data-path-only build of this kernel (same TMA loads, pipeline, barriers and stores; no MMA, no math) takes 97.8 µs;
- the full kernel takes 102.0 µs.

So the math and MMA add about 4% on top of the data path (the data-path-only build predates the last two changes, so this is approximate). The remaining gap to the copy ceiling is the data path itself: only one `xn` stage fits next to four operand stages, and `lowrank` / `w_up` are re-read from L2 for every tile.

# SPDX-License-Identifier: Apache-2.0
# SPDX-FileCopyrightText: Copyright contributors to the vLLM project
"""Benchmark the fused Qwen4Exp HC up projection + gate mix on SM100.

Compares ``hc_up_gate_mix`` with the serving chain it replaces: the Qwen4Exp
up-projection GEMM (planned skinny GEMM or ``F.linear``) followed by
``hc_gate_mix``. Shapes are Qwen3.8-Flash-Next's: hc_count 4, hidden 2560,
rank 320, with ``lowrank`` a column slice of the merged down+inject output.

    python bench_hc_up_gate_mix.py --seed <process index> --output <file>

Timing is FlashInfer CUPTI with CUDA graphs and a cold L2. Before timing, the
fused output is checked against an fp32 reference in bf16 ULPs of the
summands' magnitude (sum over streams of |sigmoid(gate) * xn| / 4).
"""

import argparse
import json
import random
import statistics
from pathlib import Path

import torch
import torch.nn.functional as F
from flashinfer.testing import bench_gpu_time_with_cupti

import vllm._custom_ops  # noqa: F401
from vllm.models.qwen4_exp.nvidia.low_latency_gemm import (
    QWEN4_EXP_GEMM_PLANS_BY_CAPABILITY,
)
from vllm.models.qwen4_exp.nvidia.ops.hc import (
    hc_gate_mix,
    hc_up_gate_mix,
    hc_up_gate_mix_supported,
)
from vllm.platforms import current_platform

HC, HIDDEN, RANK = 4, 2560, 320
D = HC * HIDDEN
DOWN_N = RANK + HC + 12  # merged down+inject output width, 16-row padded


def make_inputs(m: int, seed: int):
    gen = torch.Generator(device="cuda").manual_seed(seed)
    kwargs = dict(device="cuda", dtype=torch.bfloat16, generator=gen)
    down = torch.randn(m, DOWN_N, **kwargs)
    xn = torch.randn(m, D, **kwargs)
    w_up = torch.randn(D, RANK, **kwargs) * RANK**-0.5
    return down[:, :RANK], xn, w_up


def bench_us(fn, args) -> list[float]:
    return [
        statistics.median(
            bench_gpu_time_with_cupti(
                fn,
                use_cuda_graph=True,
                cold_l2_cache=True,
                dry_run_iters=5,
                repeat_iters=args.repeat,
            )
        )
        * 1000
        for _ in range(args.trials)
    ]


def benchmark(m: int, args) -> list[dict]:
    lowrank, xn, w_up = make_inputs(m, args.seed)
    gemm = torch.ops.vllm.qwen4_exp_low_latency_gemm
    gate = gemm(lowrank, w_up)
    arms = {
        "unfused": lambda: hc_gate_mix(xn, gemm(lowrank, w_up), HC),
        "fused": lambda: hc_up_gate_mix(lowrank, xn, w_up),
        "gemm": lambda: gemm(lowrank, w_up),
        "gate_mix": lambda: hc_gate_mix(xn, gate, HC),
    }
    expected = arms["unfused"]()
    assert torch.equal(expected, hc_gate_mix(xn, F.linear(lowrank, w_up), HC))
    actual = arms["fused"]()
    # fp32 reference (gate, sigmoid and mix in fp32); errors in bf16 ULPs.
    g = F.linear(lowrank.float(), w_up.float()).unflatten(-1, (HC, HIDDEN))
    prod = torch.sigmoid(g) * xn.float().unflatten(-1, (HC, HIDDEN))
    ref = prod.mean(-2)
    # bf16 ULP of the summands' magnitude (sum |sigmoid * xn| / HC), so that
    # cancellation between streams does not inflate the error.
    scale = prod.abs().mean(-2).clamp_min(2.0**-126)
    ulp = 2.0 ** (torch.frexp(scale).exponent.float() - 8)
    err = {}
    for name, t in (("fused", actual), ("chain", expected)):
        d = (t.float() - ref).abs()
        err[name] = dict(max_abs=d.max().item(), max_ulp=(d / ulp).max().item(),
                         mean_ulp=(d / ulp).mean().item())
    err["bitwise_vs_chain"] = torch.equal(actual, expected)
    err["max_abs_vs_chain"] = (actual.float() - expected.float()).abs().max().item()
    print(json.dumps(dict(m=m, err=err)), flush=True)
    if args.check == "bitwise":
        assert err["bitwise_vs_chain"], f"fused != unfused at M={m}"
    elif args.check == "tol":
        assert err["fused"]["max_ulp"] <= args.max_ulp, err

    # Ideal traffic reads every input and writes every output once.
    weight_bytes = D * RANK * 2
    io_bytes = {
        "fused": weight_bytes + m * (RANK + D + HIDDEN) * 2,
        "gemm": weight_bytes + m * (RANK + D) * 2,
        "gate_mix": m * (2 * D + HIDDEN) * 2,
    }
    io_bytes["unfused"] = io_bytes["gemm"] + io_bytes["gate_mix"]
    flops = 2 * m * D * RANK
    rows = []
    names = args.arms or list(arms)
    random.Random(args.seed + m).shuffle(names)
    for name in names:
        trials = bench_us(arms[name], args)
        us = statistics.median(trials)
        rows.append(
            dict(
                m=m,
                arm=name,
                us=us,
                trials_us=trials,
                tflops=flops / (us * 1e6) if name != "gate_mix" else None,
                gbps=io_bytes[name] / (us * 1e3),
                # Lower bound on the time of the fused op at the given rates.
                sol_us=max(
                    io_bytes["fused"] / (args.peak_tbps * 1e6),
                    flops / (args.peak_tflops * 1e6),
                ),
            )
        )
    return rows


def main():
    parser = argparse.ArgumentParser(description=__doc__)
    parser.add_argument(
        "--num-tokens",
        type=int,
        nargs="+",
        default=[1, 4, 16, 64, 256, 512, 1024, 1280, 2048, 4096, 8192, 16384, 32768],
    )
    parser.add_argument("--repeat", type=int, default=100)

## Details

**Dispatch and eligibility**

| Case | Path |
|---|---|
| SM100 family (B200 / B300 / GB200 / GB300), CUDA ≥ 13 build, HC count 4, hidden 2560, rank 320, bf16 HC weights, ≥ 512 tokens in the forward | **fused** (single-CTA 32-column tiles below 1024 tokens, CTA-pair 64-column tiles from 1024) |
| < 512 tokens: decode, MTP verify and draft steps, short prefills or prefill chunks | unchanged (skinny GEMM / cuBLAS + `hc_gate_mix`) |
| SM90, SM120, ROCm, CPU, XPU | unchanged (op not built or not dispatched) |
| CUDA < 13 build | unchanged (op not built) |
| `VLLM_BATCH_INVARIANT=1` | unchanged |
| LoRA wrapping `input_mix_weight_up` | unchanged (the LoRA delta is never skipped) |
| Checkpoint quantization (BF16 / FP8 / NVFP4 / MXFP4) | HC projections are always unquantized bf16 (`quant_config=None`), so eligibility does not depend on it. Measured with the FP8 checkpoint. |
| MTP | the MTP block's `GatedResidual` follows the same rule (fused only for ≥ 512-token draft prefills) |
| TP / HC sequence parallelism | weights are replicated; M is the per-rank token count |

**Design**
- **Structure.** Persistent and warp-specialized:
  - warp 0 TMA-loads `lowrank` and `w_up`;
  - warp 1 issues `tcgen05.mma`, with fp32 accumulators in TMEM;
  - warp 2 allocates TMEM;
  - warp 3 TMA-loads the `xn` tile with `EVICT_FIRST` into swizzled shared memory;
  - 2 or 4 epilogue warpgroups each own 16 output columns.
  - The warp index comes from `cutlass::canonical_warp_idx_sync()`, so the compiler treats the role branches as warp-uniform.
- **Tiling.** An output tile is 128 rows × BC hidden columns. Its GEMM tile has N = 4·BC: the same BC columns of all 4 HC streams, loaded by one TMA box per stream. Each epilogue thread therefore holds all four gates of its output elements in one TMEM row. No permuted copy of `w_up` is needed, and nothing is built at load time or on first call.
- **Two configurations, picked by M:**
  - **Below 1024 tokens:** single CTAs with BC = 32, 4 operand / 4 accumulator / 2 `xn` stages.
  - **From 1024 tokens:** CTA pairs (`tcgen05.mma.cta_group::2`, 256-row tiles) with BC = 64. Each CTA of the pair loads its own 128 rows of `lowrank` and two of the four `w_up` streams. The halved `w_up` tile leaves room for 4 operand stages next to the 64 KB `xn` stage. The leader's MMA commits are multicast to both CTAs, and both CTAs' epilogue warps release the accumulator to the leader.
- **Epilogue.**
  - The gate stays in fp32; the chain rounds it to bf16 as the GEMM output.
  - sigmoid(x) = 0.5·tanh.approx(0.5·x) + 0.5.
  - The streams are accumulated 0..3 with fp32 FMAs and scaled by 1/4.
  - Each warpgroup stages its 128 × 16 output block in double-buffered shared memory. After a warpgroup barrier, one thread issues a single TMA store, which also clips rows past M.
  - A `fence.proxy.async.shared::cta` before an `xn` stage is released keeps the next TMA load from overtaking the epilogue's `ld.shared` reads.
- **PDL.** The kernel launches with programmatic stream serialization. It waits on the grid dependency before allocating TMEM (and releases the allocation permit right after), so a preceding kernel that allocates TMEM after triggering its dependents cannot deadlock with it.
- **Input layout.** `lowrank` is the row-major column slice `out[:, :320]` of the 336-wide down+inject output (#60027). TMA reads it in place with its row stride of 336 elements, so there is no copy. The other inputs only need 16-byte-aligned rows.
- **Dispatch.** The size check is a Python branch in `GatedResidual._up_gate_mix`, as in #58957. #64263 has to choose inside the op because its path is compiled once for all batch sizes. The NVIDIA Qwen4Exp model runs without `torch.compile` (#55272), and breakable CUDA graphs evaluate the branch per captured size.
- **Why CUDA rather than CuTe DSL as in #58957.** The kernel is AOT-compiled in the existing CMake build, so there is no JIT at startup. It uses only CUTLASS/cute headers already in the build.

**Limitations**
- Measured on B300 (SM103) only. The kernel is built for and dispatched on the whole SM100 family; B200/GB200 should behave the same, but the crossovers were not measured there.
- At M = 16384 the kernel is at 53% of the HBM speed of light and 69% of the practical copy ceiling (70.3 µs). The remaining gap is the data path, as shown above. More `xn` stages would need smaller operand stages or a different split of the shared memory.

Yes, I took this; it was the biggest single win.
- **How:** a dedicated producer warp TMA-loads the `[4 × 128 × BC]` `xn` tile into swizzled shared memory with `EVICT_FIRST`.
- **Measured:** at M = 16384 it is 105.6 µs vs 124.3 µs for a per-thread 256-bit `ld.global.nc` (`L2::evict_first`) into registers, with the same kernel otherwise. TMA wins by 15–18% at M ≥ 4096, and the wider tiles (64 columns, CTA pairs) only paid off once `xn` came through TMA.
- **Gotcha:** the epilogue reads the tile with `ld.shared`, so a `fence.proxy.async.shared::cta` is needed before the stage is released. Without it, the next TMA write can overtake the reads; I saw rare wrong elements (a few per 16k × 2560 output, not every run).
