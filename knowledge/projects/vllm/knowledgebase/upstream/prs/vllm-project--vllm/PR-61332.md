# [ROCm][Attention] Honor VLLM_ROCM_USE_AITER=1 by ranking ROCM_AITER_FA above ROCM_ATTN

[Upstream PR](https://github.com/vllm-project/vllm/pull/61332) · state: open · merged: False

## Original PR description



## Overview

On CDNA (MI300X/MI325X/MI355X), `VLLM_ROCM_USE_AITER=1` never selected `ROCM_AITER_FA` for MHA decode: `ROCM_ATTN` sits ahead of it in `_get_backend_priorities()` and wins whenever it is valid. This demotes `ROCM_ATTN` below the explicit AITER opt-in, so the opt-in is honored. Fixes #46596.

## Claims

- With `VLLM_ROCM_USE_AITER=1` (and default `VLLM_ROCM_USE_AITER_MHA=1`) on CDNA, MHA decode now selects `ROCM_AITER_FA` instead of `ROCM_ATTN`, matching the documented behavior in the [ROCm attention-backend blog](https://blog.vllm.ai/2026/02/27/rocm-attention-backend.html).
- No default changes: without the env opt-in, or with `VLLM_ROCM_USE_AITER_MHA=0`, selection is byte-for-byte identical to before. RDNA is untouched (`is_mha_enabled()` is falsy off CDNA via `@if_aiter_supported`). The KV-connector path (which excludes `ROCM_ATTN` and already picks `ROCM_AITER_FA` first) is unchanged.
- Configs `ROCM_AITER_FA` rejects (head sizes outside 64/128/256, non-fp16/bf16, non-decoder attention) still fall back to `ROCM_ATTN`, which remains in the list directly behind it.

## Validation

**Unit** — `tests/v1/attention/test_rocm_attention_backends_selection.py`, 78 passed on MI300X (gfx942, ROCm 7.14):
- Case 6 updated: `VLLM_ROCM_USE_AITER=1` → `ROCM_AITER_FA` (fails on the unfixed code — verified by stashing only the `rocm.py` change).
- New: head_size 96 (AITER FA rejects, `ROCM_ATTN` accepts) with the opt-in → falls back to `ROCM_ATTN`.
- New: opt-in + `use_kv_connector=True` → still `ROCM_AITER_FA`.
- New `refreshed_aiter_env` autouse fixture: `rocm_aiter_ops` captures env flags at import time and nothing in the selection path refreshed them, so the old Case 6 assertion was insensitive to the flag; the fixture syncs flags around each test.

**End-to-end** — Qwen/Qwen3-0.6B (MHA, head_dim 128), single MI300X (gfx942, DKMS amdgpu 6.19.14, ROCm 7.14), greedy:
- `VLLM_ROCM_USE_AITER=1`: engine log `Overriding with ROCM_AITER_FA out of potential backends: ['ROCM_AITER_FA', 'ROCM_ATTN', 'ROCM_AITER_UNIFIED_ATTN', 'TRITON_ATTN']` — before this change the same line ended `Overriding with ROCM_ATTN`. The engine instantiates the AITER FA backend and proceeds through model load and warmup.
- Without the env: unchanged, `Overriding with ROCM_ATTN out of potential backends: ['ROCM_ATTN', 'ROCM_AITER_UNIFIED_ATTN', 'TRITON_ATTN']`; greedy generation completes on ROCM_ATTN.
- Generation on the AITER FA kernels did not run on this dev container: aiter's `pa_v1` JIT module fails to compile under the venv's `rocm_sdk_devel` hipcc (`ck_tile` "only one target architecture can be defined during device compile" static assert), a toolchain mismatch unrelated to this change. The failure occurs inside the aiter kernel build, after backend selection — AMD CI builds/run these kernels on matched ROCm stacks.

**Performance**: this change makes the fast path automatic for opt-in users; the expected magnitudes are those measured by the issue reporter on 8× MI300X (Qwen3-VL-235B-FP8 + EAGLE3: spec-decode TPOT 11.10→5.62 ms at mc=1, throughput 416→1083 tok/s at mc=16 when forcing `ROCM_AITER_FA` manually — exactly what selection now does automatically). I did not re-measure the 235B workload; the small-model run above validates selection and correctness only.

## Details

Root cause: `_get_backend_priorities()` appended `ROCM_AITER_FA` *after* `ROCM_ATTN`; selection picks the first valid candidate, so the explicit opt-in only controlled list membership, never the winner. The fix moves the `is_mha_enabled()` append above the `ROCM_ATTN` append, keeping `ROCM_ATTN` in the list as the fallback for configs AITER FA rejects.

Not in scope, deliberately: making AITER the default (closed #21805 / #21366 territory), and skipping `ROCM_ATTN` for sliding-window models (#42798 — separate, and both backends declare SWA support so no interaction here). This also removes the main manual-override users needed for the workaround recommended in #60316 (PD workers with KV connectors, where `ROCM_ATTN` is excluded anyway and `ROCM_AITER_FA` is already first).

Tested this PR end to end on gfx950. Setup: one MI350X, the stable `vllm/vllm-openai-rocm:v0.31.0` image with this PR's `rocm.py` hunk (head b840c090a6) applied to the image's own copy and bind-mounted. The code region is identical in v0.31.0, and I checked the file's sha256 before and after patching. `Qwen/Qwen3.5-122B-A10B-FP8`, TP1, batch 1, `VLLM_ROCM_USE_AITER=1`, no `--attention-backend`.

**Backend chosen.** Stock logs `Overriding with ROCM_ATTN out of potential backends: ['ROCM_ATTN', 'ROCM_AITER_FA', 'ROCM_AITER_UNIFIED_ATTN', 'TRITON_ATTN']`. With this PR it logs `Overriding with ROCM_AITER_FA out of potential backends: ['ROCM_AITER_FA', 'ROCM_ATTN', 'ROCM_AITER_UNIFIED_ATTN', 'TRITON_ATTN']`.

**Speed and perplexity.** Decode tokens/s at ~200 / 2k / 12k / 30k prompt tokens, all on the same droplet:

| | ~200 | 2k | 12k | 30k | wikitext-2 PPL |
|---|---|---|---|---|---|
| stock (picks `ROCM_ATTN`) | 130.5 | 100.9 | 44.8 | 21.6 | 3.9273 |
| this PR (picks `ROCM_AITER_FA`) | 134.0 | 133.6 | 133.6 | 133.1 | 3.9295 |
| this PR + `--kv-cache-dtype fp8` + MTP (1 token), mean of 3 runs | 195.9 | 177.0 | 186.8 | 178.4 | |

- **MTP:** the server makes one attention-backend choice, `ROCM_AITER_FA`, and the draft layer reuses that cached choice. Mean acceptance length is 1.84.
- **No change without the opt-in:** with `VLLM_ROCM_USE_AITER` unset, and with `VLLM_ROCM_USE_AITER=1 VLLM_ROCM_USE_AITER_MHA=0`, stock and this PR both pick `ROCM_ATTN` from the same list, `['ROCM_ATTN', 'ROCM_AITER_UNIFIED_ATTN', 'TRITON_ATTN']`.
- **No errors** in any server log.

**One gfx950 caveat, not caused by this PR:** until an AITER release includes ROCm/aiter#6336, bf16 KV with MTP on `ROCM_AITER_FA` still slows with context, because multi-token decodes go through AITER's Gluon `unified_attention` (#60408). fp8 KV avoids it.
