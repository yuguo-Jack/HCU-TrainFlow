# [Spec Decode] Fix Dspark adaptive verification cost model

[Upstream PR](https://github.com/vllm-project/vllm/pull/62960) · state: open · merged: False

## Original PR description

## Summary

Adaptive verification picks, every step, the draft budget `b` that maximises

```
expected accepted tokens(b) / step cost(b)
step cost(b) = drafter cost + base + (price of b draft slots)
```

The argmax depends only on how the slot price compares with the base. The current cost model gets both wrong, because it reads everything off a single profiled curve. This PR profiles the two separately and prices the base from the batch's real shape and context.

On Qwen3-4B with DSpark at batch size 256 (TP1, H100), this gives **+2.7% output throughput on SPEED-Bench throughput_1k** and **+8.4% on MT-Bench**. The fixed model won all 10 paired runs.

## The bug

`batches_to_profile` ran one family of dummy batches: *n* requests, one token each, every request carrying `VLLM_ADAPTIVE_VERIFICATION_PROFILE_CONTEXT_LEN` (default 8192) tokens of fabricated KV context. That produced `verify_cost_ms[n]`, whose index means *n sequences, each reading 8k tokens of KV*. `get_num_tokens` then priced every budget as

```python
costs = draft_cost_ms[num_reqs] + verify_cost_ms[num_non_draft_tokens : num_non_draft_tokens + max_draft_budget + 1]
```

That one lookup has three errors.

1. **A draft slot is priced as another whole sequence with 8k of context.** Walking `b` steps along `verify_cost_ms` charges each draft token as one more request reading 8k of KV. A draft slot is really one more query token on a sequence already in the batch, so it reads no new KV.
2. **The base always assumes 8k of context per request.** Workloads with short contexts, such as MT-Bench, carry a few hundred tokens, so most of the base's attention cost is fictional.
3. **The base is looked up by token count on a request-count axis.** `num_non_draft_tokens` counts tokens, but the curve is indexed by requests at one token each. With chunked prefill in the step, every prefill token is charged as an extra 8k-context sequence.

### Example (Qwen3-4B, H100)

Qwen3-4B stores 36 layers × 8 KV heads × 128 dims × 2 (K and V) × 2 bytes = 144 KiB of KV per token, so one 8k-context sequence reads about 1.2 GB of KV per step.

- **Draft slot (error 1).** Take 64 decoding requests, each with 7 drafts. The old model prices draft slot 1 as `verify_cost_ms[65] - verify_cost_ms[64]`, which is one more 8k-context sequence. At ~3.3 TB/s that is roughly **0.36 ms per slot** of KV read alone. The draft-axis profile in this PR measures the real price at **10.4–11.7 µs per slot** on the same GPU, about 30× lower. At long context the old model therefore declines draft slots that would have paid for themselves.
- **Base (errors 2 and 3).** Take 256 MT-Bench requests decoding at ~400 tokens of context. The old base prices 256 × 8k × 144 KiB ≈ 300 GB of KV reads (tens of ms). The batch really reads 256 × 400 × 144 KiB ≈ 15 GB. With the base overstated by an order of magnitude, every draft slot looks nearly free relative to the step. The sizer then buys slots whose acceptance doesn't justify them. A step that also carries a 190-token prefill chunk is charged as 190 more 8k-context sequences instead.

## The fix

**Profiling** (`batches_to_profile`, `set_initial_cost_curves`):

- The one-token-per-request pass at the profiled context runs as before and still produces `verify_cost_ms`.
- A second pass runs the same shapes with **no fabricated context**. Samples now record their context (`StepTimingSample.context_len`, set by `StepTimingCollector.record_batch` only while collecting), so the two passes are never pooled.
- **Draft-axis probes** run at each captured request count with the full query length `K + 1`. `_dummy_run` takes a `num_reqs` kwarg so the request count stays fixed while tokens grow.

Three new curves come out of these passes:

- `slope_curve`: price of one draft slot by request count. It is the rise from a one-token-per-request step to a full-query step at the same request count, divided by the slots added. Everything that depends only on the request count (weights, KV reads, launch overhead) cancels in the difference.
- `token_curve`: step cost by token count with no KV context. This covers matmuls, the padding staircase, and the loss of CUDA graphs past the capture limit.
- `kv_curve`: price of reading one context token, by request count. It is computed as (with-context step − no-context step) / (requests × context).

**Runtime** (`_budget_costs_ms`, called from `get_num_tokens`). For a batch of `R` requests running `N` non-draft tokens with `C = sum(num_computed_tokens)` tokens of context:

```
base        = token_table[N] + kv_table[R] * C
cost(b)     = drafter[R] + base + slot_table[R] * b          if N + b <= capture limit
```

**Past the CUDA-graph capture limit.** The formula above is linear in `b`, but the real step cost is not. Once `N + b` exceeds the largest captured size (`max_cudagraph_capture_size`), the target forward stops replaying a full CUDA graph and runs piecewise or eager. That adds a one-time jump in cost at the limit, and past it the cost grows with the step's token count at the ungraphed rate. A constant per-slot price can't represent either. Without a correction, the sizer would see no cliff and push budgets across the limit as if they were as cheap as the graphed ones.

The old single curve did contain this cliff, because it was indexed by total token count. Splitting the cost into a base plus a per-slot price would lose it, so `_budget_costs_ms` restores it from the context-free token table. That table is profiled on both sides of the limit: the captured sizes, then tail sizes at 1.5× and doubling up to `max_num_batched_tokens`, which run piecewise or eager. It is interpolated only between points on the same side of the limit. For budgets that cross the limit:

```
fixed       = drafter[R] + kv_table[R] * C                  # parts drafts don't change
linear(b)   = fixed + token_table[N] + slot_table[R] * b    # the formula above
cost(b)     = max(linear(b), fixed + token_table[N + b])    if N + b > capture limit
```

The context-dependent KV read and the drafter cost are kept as they are. Only the token-count term is re-looked-up at the step's real size `N + b`, which picks up the graph-loss jump and the ungraphed per-token rate. Taking the `max` means an ungraphed budget is never priced below the linear estimate. The token table has no context behind its requests, so on its own it can undercount the extra attention that the draft slots do.

For example, Qwen3-4B at batch size 256 captures sizes up to 512, and 256 decoding requests give `N = 256`. Budgets `b <= 256` stay inside the graphs and use the linear price of about 11 µs per slot. From `b = 257` on, the step is 513+ tokens, and `cost(b)` takes the jump to the ungraphed token-table price. The sizer therefore verifies more than 256 drafts only when the extra expected acceptance pays for losing the graph, not just for the slots.

Everything at runtime is host-side numpy over arrays the runner already holds, so the fix adds no device syncs. The memory-profiling capture pass samples only the largest graphs, so it has no draft-axis shape to probe. That pass leaves slots unpriced, and the real capture pass reprofiles. A warning fires only if probes ran and still produced no price. The profiled tables are logged at debug level (`DSpark cost tables: ...`).

## Tradeoffs and limitations

- **Startup time.** The context-free pass and the draft-axis probes add about 20 s of profiling on Qwen3-4B at batch size 256: the graph-capture phase goes from about 30 s to 50 s. Per step, the added cost is one numpy sum over the batch.
- **Linear slot price inside the graphed range.** Within the captured sizes, a slot's cost is a constant per request count. Padding steps between captured sizes are not modelled per slot.

## Results

Setup:

- Model and hardware: Qwen3-4B with `deepseek-ai/dspark_qwen3_4b_block7` (`num_speculative_tokens` 7), adaptive verification on, TP1 on one H100 80GB.
- Batching: `--max-num-seqs 256`, `--max-concurrency 256`, about 250 requests running and 0 waiting throughout.
- Requests: 1,280 per run, T=0, output up to 512 tokens or EOS, prefix caching off, chat endpoint with `enable_thinking=false`.
- Repeats: 5 per dataset. Each pair ran on the same GPU, alternating which variant ran first.

| Dataset | Before (tok/s) | After (tok/s) | Speedup | Per-pair speedup | Acceptance length (before / after) |
|---|---|---|---|---|---|
| SPEED-Bench throughput_1k | 9,898 (sd 41) | 10,165 (sd 41) | **+2.7%** | +2.3, +3.2, +3.2, +2.2, +2.7% | 3.38 / 3.37 |
| MT-Bench (80 first-turn prompts, oversampled to 1,280) | 22,198 (sd 190) | 24,072 (sd 268) | **+8.4%** | +7.4, +8.3, +8.2, +8.8, +9.4% | 3.77 / 3.67 |

MT-Bench gains the most because its contexts are the furthest from the 8k the old base assumed. Acceptance length drops slightly while throughput rises: the sizer now declines slots whose expected acceptance doesn't pay for their real cost.
