- gordan12 · comment · 2026-11-03T13:11:58Z · [source](https://github.com/vllm-project/vllm/pull/62093#issuecomment-6604739652)

Took a look against main — the root cause and fix make total sense. Under PP > 1, `maybe_share_target_embed` returns early when `has_own_embed_tokens` isn't declared, and since `InklingMultiTokenPredictor` intentionally keeps `embed_tokens = None`, the last rank ends up missing the target's table.

Opting in via `has_own_embed_tokens = False` fits nicely with existing conventions, and verified that `InklingModel` allocates embed_tokens across all PP ranks (not a `PPMissingLayer`), so the sharing works as intended. Overall LGTM!

Just one quick sanity check: the current validation confirms the engine boots and serves under PP, but if the embedding were somehow unmapped or empty on the last rank, it likely wouldn't crash — it would just silently tank the acceptance rate.

Did you happen to compare the MTP acceptance length (AL) between PP=1 and PP=2? (We ran a similar check for the PP aux-hidden-state relay in #64320 ). If the AL numbers line up, that'd give 100% confidence that the weights are properly loaded and effective.
