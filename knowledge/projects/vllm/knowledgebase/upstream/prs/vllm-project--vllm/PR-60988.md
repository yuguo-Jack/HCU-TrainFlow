# [Feature][Frontend] Add optional fastapi-guard security middleware

[Upstream PR](https://github.com/vllm-project/vllm/pull/60988) · state: open · merged: False

## Original PR description

Closes #60987

## Overview

The API server currently has no in-process request-level security: docs/usage/security.md recommends authentication, rate limiting, and logging at the reverse-proxy layer, which is the right default for deployments that have one. This PR adds an opt-in middleware for the ones that don't, built on [fastapi-guard](https://github.com/Guard-Core/fastapi-guard): IP block/allow lists, rate limiting with auto-ban, user-agent blocking, penetration-attempt detection, optional passive mode, optional security headers, optional IPInfo geo/cloud-provider blocking, and optional Redis-backed shared state.

Design fit, per the checklist: strictly opt-in via `VLLM_GUARD_ENABLED`. When the variable is unset, nothing is imported and no middleware is attached, so the disabled path has zero runtime cost. The dependency is optional (`pip install "vllm[guard]"`); enabling without it fails loudly at startup with the install command instead of silently running unprotected.

## Claims

- New `vllm/entrypoints/serve/middleware/guard.py` with `is_guard_available()` and `init_guard_middleware(app)`, registered in `init_entrypoints_middleware` right after the api-key middleware, following the same conditional lazy-import pattern as `XRequestIdMiddleware`
- `VLLM_GUARD_*` env family in `vllm/envs.py` (annotations + lambdas, same style as the rest of the file); `VLLM_GUARD_IPINFO_TOKEN` and `VLLM_GUARD_REDIS_URL` are added to the credential exclusion list since both can hold secrets
- `guard` extra in setup.py: `fastapi-guard>=8.0.3,<9.0.0` (Python floor unchanged: vLLM requires >=3.11, fastapi-guard requires >=3.10, no marker needed)
- Docs: short "Optional In-Process Security Middleware" section in docs/usage/security.md next to the existing reverse-proxy guidance

## Validation

- New `tests/entrypoints/serve/middleware/test_guard_middleware.py`: disabled-by-default no-op, fail-loud when enabled without the package, blocked IP 403, rate-limit 429, passive mode never blocks. No engine needed (TestClient-style app with mock routes, like test_authentication_middleware.py). Tests skip cleanly where fastapi-guard isn't installed, matching the existing importorskip pattern
- Locally I validated the real `vllm/envs.py` and `guard.py` standalone (envs.py is stdlib-only, so it loads without the full package): lambda parsing, blocked IP 403, `[200, 200, 429]` at limit 2, passive mode 200, all green against fastapi-guard 8.0.3
- ruff format/check clean at 88 columns on all touched files

## Details

- `enable_redis` is explicitly false unless `VLLM_GUARD_REDIS_URL` is set. fastapi-guard's own default is a localhost Redis, which would turn a running Redis into a hidden dependency for an opt-in feature
- `vllm serve` runs a single API-server process (the engine core is the separate one), so in-memory counters are fine per replica; multi-replica deployments should set the Redis URL to share limits and bans
- Middleware ordering: guard attaches after CORS and the api-key middleware, before the user `--middleware` hook, so operator-supplied middleware can still observe or post-process
- fastapi-guard's `SecurityMiddleware` is a `BaseHTTPMiddleware`; the debug response logger in this file already uses `app.middleware("http")`, so this matches existing usage in the entrypoints layer
