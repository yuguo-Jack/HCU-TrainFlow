# [Perf][Core] Admit async KV loads in linear time per scheduling step

[Upstream PR](https://github.com/vllm-project/vllm/pull/64379) · state: open · merged: False

## Original PR description



## Overview

When a P/D decode instance gets a burst of requests, each one usually starts with an async KV load. One `schedule()` parks all of those loads, and its cost grows with the square of the burst: about 0.5 s for 1,024 parked loads and 8 s for 4,096 in a CPU run of the real scheduler. Every running request stalls for that long. This PR makes the same admission decisions in linear time.

## Claims

- One `schedule()` that parks k async loads calls `_request_remaining_blocks` k times instead of about k²/2, also when the scan alternates loads with requests it admits directly (those add a call only if they stay prefilling).
- Admission decisions are unchanged. The #44560 reservation still applies; the new test checks that exactly the loads that fit are parked.
- No behaviour change outside that scan.

<details><summary>Benchmark script</summary>

```python
"""Time one Scheduler.schedule() that parks N async KV loads (CPU only).

Run from the repo root:
  VLLM_TARGET_DEVICE=cpu python bench_async_load_burst.py 256 1024 4096
"""
import sys
import time

from tests.v1.core.utils import create_requests, create_scheduler, mock_kv
from vllm.v1.request import RequestStatus


def burst(n: int) -> tuple[float, int]:
    s = create_scheduler(
        max_num_seqs=n,
        num_blocks=n * 8 + 100,
        use_kv_connector=mock_kv(matched_tokens=64, is_async=True),
    )
    for r in create_requests(n, num_tokens=80, max_tokens=10):
        s.add_request(r)
    t0 = time.perf_counter()
    s.schedule()
    dt = time.perf_counter() - t0
    parked = sum(
        r.status == RequestStatus.WAITING_FOR_REMOTE_KVS for r in s.requests.values()
    )
    return dt, parked


for n in map(int, sys.argv[1:]):
    best = min(burst(n)[0] for _ in range(3 if n <= 1024 else 1))
    print(f"{n:5d} loads parked: {best * 1e3:9.1f} ms per schedule()")
```

## Details

<details><summary>Root cause and fix</summary>

Since #44560, each async-load admission checks that the load fits in the free blocks minus what in-flight prefills still reserve (`_inflight_prefill_reserved_blocks()`, [scheduler.py:3076](https://github.com/vllm-project/vllm/blob/c4973d94fed25a3bf32d601873755a9bcd951886/vllm/v1/core/sched/scheduler.py#L3076)). That sum calls `_request_remaining_blocks()` ([:3037](https://github.com/vllm-project/vllm/blob/c4973d94fed25a3bf32d601873755a9bcd951886/vllm/v1/core/sched/scheduler.py#L3037), a full `coordinator.get_num_blocks_to_allocate`) for every request in `_inflight_prefills`, and the set includes the loads admitted earlier in the same scan. So the k-th admission re-sums k-1 loads. Async loads take no token budget and `max_num_seqs` does not bound them (with `max_num_seqs=16`, one `schedule()` parks all 512 of 512 requests), so only KV capacity limits k.

The fix sums the reservation once per waiting scan and adds each parked load's remaining blocks as it is admitted. A request admitted directly adds its remaining blocks only if it stays prefilling, since only then does it join `_inflight_prefills`. The sum is recomputed only when the admitted request was already in the set, for example a finished load resuming. Nothing else changes an in-flight request's block needs during the scan: preemption happens before it, and the scan is skipped in a step that preempted.

</details>

Not a duplicate: no open PR changes how the in-flight reservation is summed. #63136 and #63288 edit the lines next to this change (the spec decode step term and the decode-step margin), so whichever lands second needs a small rebase. #61725 caps how many async loads one step admits; it merges cleanly with this, and the two compose. #57418 adds another caller of `_inflight_prefill_reserved_blocks()` in a new path, and #59343 (draft) uses the reservation without changing it. The reservation's deadlock rules come from #57104 and #58947; this keeps them as they are.
