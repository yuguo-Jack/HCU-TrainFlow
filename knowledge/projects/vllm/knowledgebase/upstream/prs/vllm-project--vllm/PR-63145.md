# [MM][Mistral] Use real-valued RoPE in the compiled Pixtral ViT

[Upstream PR](https://github.com/vllm-project/vllm/pull/63145) · state: closed · merged: True

## Original PR description



## Overview

With `compile_mm_encoder` (#57168), the Mistral-format Pixtral ViT blocks still run the RoPE as a complex multiply. Inductor does not generate code for complex operators (`UserWarning: Torchinductor does not support code generation for complex operators. Performance may be worse than eager.`), so most of the compile gain is lost. This PR keeps the RoPE table as the real view of the complex frequencies and rotates q/k with real ops under `torch.compile`; eager mode keeps the complex multiply.

## Claims

- Compiled Pixtral ViT encoder is 8-25% faster than with the complex RoPE (Pixtral-12B, H100, one image).
- Eager mode is unchanged: same complex multiply, same numerics.
- No more "complex operators" fallback warning when compiling the Pixtral vision encoder.

## Validation

Encoder latency, `vllm bench mm-processor`, `mistralai/Pixtral-12B-2409` (`--load-format dummy`), 1× H100, 1 image per request, 100 prompts, median `encoder_forward_ms`. Main and this branch were each run as Python sources over the `vllm/vllm-openai:nightly` image (one job per branch):

| image | main, eager | main, compile | this PR, eager | this PR, compile |
| --- | --- | --- | --- | --- |
| 512×512 | 15.11 ms | 10.78 ms | 15.78 ms | **8.05 ms** (−25%) |
| 1024×1024 | 20.97 ms | 15.97 ms | 21.76 ms | **14.63 ms** (−8%) |

The eager path is unchanged code-wise (the eager differences are within the run-to-run std of 0.9-2.2 ms). On main, the compile log has `Torchinductor does not support code generation for complex operators`; on this branch it does not.

## Details

- `VisionTransformer.freqs_cis` now caches `torch.view_as_real(precompute_freqs_cis_2d(...))`, a float32 `(H, W, head_dim / 2, 2)` table. Indexing it gives `(num_patches, head_dim / 2, 2)`, which is what the compiled `TransformerBlock` receives (`freqs_cis` keeps dynamic dim 0). As a side effect, positions are no longer gathered from a complex tensor (the problem #49669 works around for NPU).
- `apply_rotary_emb_vit` dispatches on `torch.compiler.is_compiling()`. The all-real formulation in eager mode costs several elementwise kernels per tensor; we measured it ~14% slower than the complex multiply end to end on the model, so eager keeps the complex path.
- Only the Mistral-format path (`PixtralForConditionalGeneration`) is touched; the HF path already uses cos/sin.
- Interaction with #56277 (Pixtral encoder CUDA graphs): its capture inputs build `rotary_freqs` as complex64 ones; with this PR they should be a real `(capacity, head_dim / 2, 2)` tensor with cos = 1, sin = 0. 

Duplicate check: no open PR changes the Pixtral ViT RoPE for torch.compile (searched "pixtral rope", "pixtral complex", "view_as_complex inductor"); #49669 only changes the gather for NPU.
