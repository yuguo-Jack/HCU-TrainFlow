# [Docs][Distributed] Document GLOO_SOCKET_IFNAME for docker pipeline parallel deployments (#59109)

[Upstream PR](https://github.com/vllm-project/vllm/pull/61103) · state: open · merged: False

## Original PR description

Fixes #59109

## Purpose

When running pipeline parallelism (PP > 1) in Docker with default bridge networking, PyTorch's Gloo backend resolves the container hostname to the Docker bridge IP (e.g. 172.17.0.2) instead of loopback (`lo`). This causes per-step control metadata transfers (`isend_object`) to traverse the virtual bridge network stack, adding ~535ms latency per send. As context length grows and block table metadata expands, this manifests as severe long-context decode throughput collapse (>50% regression).

This PR addresses this by:
1. Documenting the root cause, symptom, and `GLOO_SOCKET_IFNAME=lo` fix in:
   - `docs/serving/parallelism_scaling.md`
   - `docs/serving/distributed_troubleshooting.md`
   - `docs/usage/troubleshooting.md`
2. Updating `init_distributed_environment` in `vllm/distributed/parallel_state.py` to:
   - Automatically default `GLOO_SOCKET_IFNAME="lo"` when unset for single-node multiprocessing (`nnodes == 1` and `distributed_executor_backend in ("mp", None)`).
   - Log an informative warning if single-node PP is enabled with other executors without `GLOO_SOCKET_IFNAME`.
3. Adding unit tests in `tests/distributed/test_file_store.py` verifying the defaulting, preservation, and multi-node handling.
