# [ROCm][Perf][Qwen3.8] Dense mono decode on 128-CU gfx950 (MI350P)

[Upstream PR](https://github.com/vllm-project/vllm/pull/65078) · state: open · merged: False

## Original PR description

## Overview

Dense mono decode for Qwen3.8-27B on 128-CU gfx950 (MI350P). **Stacked on #61573**, which adds the dense mono decode
for MI355X; the first two commits are #61573's and the rest are this PR's. Review the later commits. Draft until
#61573 lands.

AI assistance was used in developing this PR (code, tests, measurements and this description).

## Claims

- The K1 (GDN mixer) and K2 (MXFP4 FFN) persistent kernels of #61573 build and run with the grid width taken from the
  device's CU count: 256 (MI355X, MI350X) or 128 (MI350P). Other counts are refused with a message; #61573 refuses
  everything below 256 CUs.
- 256-CU builds are unchanged apart from one numerics fix: of the 80 K1 / K2 configurations, the 32 K2 compile to
  byte-identical code objects (sha256) with and without this PR, and the 48 K1 differ only by keeping beta in fp32
  (last bullet); with that line reverted all 80 are identical to #61573's.
- On MI350P (TP1, MTP off, same image, flag on vs off, default row caps): output throughput +19.1 % at one request
  (8k / 1k, TPOT 9.21 → 7.67 ms), +14.8 % at two, +12.0 % at four, +0.5 % at eight. Above the caps nothing changes.
- With MTP-3 (TP1), mono now runs the verify steps (until now the flag refused speculative decoding): K1 takes each
  request's 1 + 3 tokens through the conv and the recurrence in order, as vLLM's spec-decode kernels do, and K2 the
  rows. Output throughput +19.9 / +18.7 % at one request (two prompt seeds, TPOT 3.98 → 3.29 ms), +3.7 % at two
  (a verify step of two requests is 8 rows, above the default caps of 4), unchanged at four and eight. On a recent
  nightly whose stock MXFP4 decode GEMM is AITER's FlyDSL A4W4 kernel, one request gains about 6 % (verify step
  9.67 → 7.88 ms).
- Accuracy on MI350P is unchanged within run-to-run noise: GSM8K in the model card's setting (paired over three
  seeds, −0.18 ± 0.36 pt thinking, −0.45 ± 0.45 pt non-thinking), GSM8K chat, GPQA Diamond, RULER NIAH 64k / 128k;
  with MTP-3 at one request (K1 and K2 on every verify step), GSM8K card setting +0.53 ± 0.67 pt thinking,
  −0.68 ± 0.80 pt non-thinking.
- K1 and K2 are bit-exact on MI350P with the stock paths #61573's tests and startup checks compare against: K2 with
  the Triton `gemm_afp4wfp4` (TP1 S 1-8, TP2 S 1-16), K1 with the stock GDN decode (TP1 S 1-8; TP2 S 1-16 without
  out_proj; with out_proj see Details) and, on MTP-3 verify steps of one and two requests, with the spec-decode
  path vLLM serves: `causal_conv1d_update` with either the sigmoid-gated delta rule kernel + RMSNormGated (this
  base) or main's fused MTP decode kernel (#61855; checked on a recent nightly). A server that runs the MXFP4 linears on the AITER ASM GEMM (`VLLM_ROCM_USE_AITER_FP4_ASM_GEMM=1`, as
  here) accumulates differently, so mono's greedy outputs are not byte-identical to that server's; accuracy is
  compared statistically.
- Fixes that apply to #61573 independently of the CU count: K2 follows the installed AITER's split-K (the bit-exact
  startup check failed with current AITER); the mono graph no longer takes over Model Runner V2's piecewise-cudagraph
  capture (the engine died on the first prefill); the GDN state-slot mapping runs once a step instead of in every GDN
  layer (144 launches a step); a GDN layer above K1's row cap no longer hands out_proj's output to K2 in place of its
  input (the skip hook was never installed); K1 rounded beta to bf16, which the stock decode kernel stopped doing
  in #53877 (K1's strict test failed by one bf16 ulp in ≈ 4 % of the outputs).

## Details

**Why #61573 does not run on 128 CUs.** K1 and K2 run one CTA per CU, all co-resident, exchanging data through
spin-waited mailboxes, so the grid must equal the CU count; #61573 hard-codes 256 and refuses smaller GPUs (a
256-CTA grid would deadlock on 128 CUs). Several stage layouts also assume 256: one o_proj owner per CTA for 160
owners, one whole down row group per CTA (320 = 256 + 64 split), 4 in_proj_qkvz groups per CTA filling the 8 waves,
and the flag / scratch regions sized by 256.

**What changed.**
- `mono/tiling.py` (new, pure Python): `resolve_grid(cus, override)` picks the width (256, 128; else `ValueError`
  naming the validated widths); `VLLM_ROCM_QWEN38_DENSE_MONO_GRID` may select a validated width at most the CU
  count (to run the 128-CTA build on a 256-CU GPU). The FFN / GDN geometries move here with the grid as a field,
  plus the per-stage pass plans and their invariants (checked at import for both widths).
- K1 / K2 (`dense_gdn.py`, `dense_ffn.py`): the grid is a field of the build key (so it is in FlyDSL's JIT key; the
  128-CTA kernel symbols end in `_g128`). Stages whose tasks outnumber the CTAs take more passes per CTA, each task
  computed exactly as before: o_proj / out_proj / K1 front owners `bid + p * grid` (a second pass on CTAs 0..31 at
  128); in_proj_qkvz in passes of 4 groups; down's whole row groups and its split group in tile passes; gate_up 8
  whole groups and 8 columns of a split one per CTA; GDN tasks in one pass at TP1 (up to 48 tasks) and in passes of
  whole tokens at TP2 above 24 (a token's tasks all run in the same pass, so no CTA waits on a later pass). At 256
  every stage is one pass and the traced program is unchanged (offsets of 0 emit nothing; the down store keeps its
  original form).
- `dense_mono.py`: refuses with the resolver's message instead of `< 256`; passes the grid to both build keys; a
  build wider than the device's CUs raises instead of hanging.
- K2 split-K: K2 is bit-exact with the stock Triton `gemm_afp4wfp4` only if it splits K the same way. #61573
  hard-codes 4 / 4 / 2 splits; AITER's current `get_splitk` gives gate_up 2, down 2 at TP1 and 1 at TP2 (not
  CU-dependent), so #61573's startup self-check refuses to start with current AITER. K2 probes the stock split
  counts once per width at startup and builds them (`FfnBuild.gu_split / d_split / o_split`; 0 keeps the default).
  Without the probe `DenseFfnTest::test_bit_exact` fails on this stack; `StockSplitTest` checks the probe against
  AITER's `get_splitk`. The probe runs once in model preparation, so there is no new host synchronization in
  steady-state decode.
- Model Runner V2: its PIECEWISE cudagraphs for the stock model are captured by dummy steps that look like pure
  decode; #61573's mono graph took them over, the stock piecewise graphs for widths up to the cap were never
  captured, and the first prefill of such a width tried to capture at run time on the default stream
  (`CUDA graphs must be captured on a non-default stream`). The mono graph now skips PIECEWISE runtime-mode steps;
  pure decode runs under FULL cudagraphs and still takes it. Reproducer: the serve command below with the flag on
  and any request; before the fix the engine dies on its first prefill, after it the smoke requests, the benchmarks
  and the evals above run. Not covered by a unit test (it needs a capturing engine).
- K1 front on 128 CTAs (up to 4 rows): every CTA runs the input norm on the whole rows itself with K2's
  `run_norm`, which reduces in the owners' order, in place of 160 owner tasks (a second pass on CTAs 0..31) and two
  grid-wide hand-offs. x is bit-identical; K1 27.6 / 32.3 / 40.5 µs at 1 / 2 / 4 rows (was 30.3 / 35.1 / 43.5).
  Wider steps keep the owners (the kept rows spill there). 256-CTA builds keep the owners.
- GDN state slots: the copy + null-slot mapping of the state indices ran in every GDN layer (3 launches x 48); GDN
  layers of a KV-cache group share the indices, so it runs once per group a step. −0.5 ms of GPU time a step at one
  request.
- Speculative decoding (TP1): `K1Build.spec` = tokens a request in a verify step (1 + k). A GDN task becomes a
  request's tokens in order: the conv slides its window from offset `n_acc - 1` and rewrites the widened conv state
  (slot `idx[r, 0]`, length 2 + spec), the recurrence starts from slot `idx[r, n_acc - 1]` and stores each token's
  state to `idx[r, j]`, null slots (≤ 0) are skipped — the semantics of
  `causal_conv1d_update(num_accepted_tokens=…)` and `fused_sigmoid_gating_delta_rule_update(ssm_state_indices=[R,
  1 + k])`. The spec kernel holds one q / k element a lane over two waves, so on spec builds K1's l2 norm reduces each
  wave and adds the two sums (bit-exact; with the decode kernel's order the core differed by one bf16 ulp in a few
  elements a step). The accepted counts ride in the `w_os` argument (unused without out_proj), so the kernel ABI and
  the non-spec code objects are unchanged. `dense_mono.py` reads vLLM's persistent spec buffers and enters only whole
  verify steps (requests x (1 + k) == rows, from tensor shapes, no host sync); partial verify steps and warm-up
  batches run stock. A startup self-check runs K1 on verify steps against the stock spec kernels and an fp32
  reference. Where the GDN layers serve verify steps with the fused MTP decode kernel
  (`enable_fused_gdn_spec_decode`; main since #61855), `K1Build.spec_fused` takes its numerics: launched, it keeps the
  decode kernel's state layout, so the recurrence is unchanged, but its q / k l2 norm sums each of two warps with
  the first DPP step contracted into an fma, and its gated norm sums the squares in tiles of 32 rows (rows 16 apart
  contracted, then xor 8 … 1; tiles added (t0 + t2) + (t1 + t3)); the self-check then compares against that kernel.
  The default caps (4) take a verify step of one MTP-3 request. With K1 switched off, each GDN layer is the compiled stock layer up to out_proj's input (a shallow
  view with out_proj as passthrough, so inductor fuses it as in the stock graph) and K2 takes the rows. TP2 still
  refuses speculative decoding.
- Tests: `test_amd_dense_mono_tiling.py` (new, CPU only, wired into the existing Buildkite job) replays every
  stage's task placement at both widths (each task exactly once; GDN passes closed under their hand-offs) and checks
  the grid selection with the device query replaced. The GPU tests build for the device's grid and the probed split
  counts, set a `VllmConfig` with custom ops on (the references construct `SiluAndMul` / `RMSNormGated`), and import
  the Gemma norm by name. The MI355 Buildkite job now also runs them with `VLLM_ROCM_QWEN38_DENSE_MONO_GRID=128`,
  which covers the 128-CTA builds in CI (not run here: no MI355X available for this PR).

**K1 strict bit-exactness.** `DenseGdnTest` (strict equality with the stock GDN path) failed on this stack at every
width by about one bf16 ulp in ≈ 4 % of the core outputs; none of it was the 128-CTA decomposition. Three causes,
all fixed (`K1Build` fields from `stock_fields(rows, tp, oproj, cus)`):
- beta: K1 rounded `sigmoid(b)` to bf16, as `fused_recurrent_gated_delta_rule_packed_decode` did before #53877
  ("Keep packed GDN decode beta in FP32"). K1 keeps it in fp32. This is the only change to the 256-CTA code objects.
- Gated norm layout: FLA's `layernorm_guard` gives a program two rows once rows x heads exceed 2 x CUs, which on 128
  CUs happens at 6+ rows (TP1) and 11+ (TP2), never at TP1 on 256 CUs. Its sum is then a thread's 4 columns as two
  pairs added elementwise, then xor 16 … 1 over 32 threads; K1 reproduces that order (`K1Build.norm_rows`,
  `tiling.gated_norm_rows`).
- TP2 out_proj split-K: probed from AITER like K2's (`K1Build.o_split`). Current AITER splits it in 3, which K1's
  out_proj partial cannot reproduce, so with K1's out_proj (the TP2 default) `dense_mono.py` refuses at startup and
  names the split (the self-check would fail anyway); `VLLM_ROCM_QWEN38_DENSE_MONO_OPROJ=0` leaves out_proj stock.
  The strict test skips those widths.

**Tradeoffs and limitations.**
- On MI350P the gain is limited to 1-4 decode rows (+12 to +19 % without MTP); at 8 rows mono is about equal to the
  stock path. The stock MXFP4 ASM GEMMs already reach 2.75-2.9 TB/s at one row on MI350P (≈ 3.1 TB/s achievable), so
  mono removes launch / glue overhead and the poorly utilized o_proj GEMM, not GEMM time; #61573's larger MI355X gain
  comes from the same overhead being a larger share of a step on a GPU with twice the bandwidth.
- MTP: mono helps at one and two requests (+19 %, +10 %); verify steps of three or more MTP-3 requests (12+ rows)
  are above the K1 / K2 builds (8 rows at TP1) and run stock. Adaptive (variable-length) verification runs stock.
- `spec_fused` reproduces the fused MTP kernel's 32-row tiles (its launch while requests x value heads < CUs, which
  holds for every verify step inside the 8-row caps); a wider tile is refused with a message.
- TP2 on 128 CUs is built and covered by the numerics tests but was not served; with current AITER it needs
  `VLLM_ROCM_QWEN38_DENSE_MONO_OPROJ=0` (above).
- 10.8 GiB of shuffled weight copies (as in #61573); on MI350P the KV cache shrinks accordingly (2.79 M → 2.44 M
  tokens with MTP-3 on the nightly above).
- The best row caps depend on the stock MXFP4 decode GEMM (above); the defaults are the safe choice for both
  measured stacks.
- `VLLM_ROCM_QWEN38_DENSE_MONO_GRID` is read like #61573's other `VLLM_ROCM_QWEN38_DENSE_MONO_*` switches (not
  registered in `vllm/envs.py`).
- #61573's commits carry no `Signed-off-by` (DCO); this PR's do.
- Size: about 2,010 lines added and 500 removed under `vllm/` on top of #61573 (README included), of which
  `tiling.py` (460 lines) is the pass plans with their invariants and the geometry moved out of the kernel files.
- #61573 currently conflicts with main (`.buildkite/test_areas/models_basic.yaml`, `vllm/envs.py`,
  `vllm/models/qwen3_5/__init__.py`); this branch conflicts in the same three files only and is rebased once #61573
  is. On main, `vllm/models/qwen3_5/__init__.py` is now a hardware-split entry point (#61573's license-only file
  goes; `amd/` sits beside it) and `VLLM_ROCM_MONO_DECODE` is no longer in `envs.py` (the hunk is re-anchored by
  hand). Applied that way on a recent nightly, the branch's kernels compile (K1 / K2 at TP1, including the
  verify-step builds) with no spills.

**Not a duplicate.** Open PRs searched for "mono decode 128", "MI350P mono", "dense mono": the closest is #63341
(DSv4.1 mono, draft), which resolves the grid from the CU count and refuses 128 pending the task decomposition
described in #63340; this PR does that decomposition for the Qwen3.8 dense kernels, with the width as a per-build
