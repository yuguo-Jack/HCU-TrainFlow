# [ROCm][Build] Compile paged attention kernels in parallel (7.6x faster attention build)

[Upstream PR](https://github.com/vllm-project/vllm/pull/62475) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Disclosure

AI assistance was used. The changes were reviewed and tested manually.

## Overview

`csrc/rocm/attention.cu` is a single 3.9k-line translation unit whose kernel instantiation is the tail of the ROCm build: ~9 min of a ~10.5 min build, on one core. This PR splits the instantiations into one translation unit per (dtype, kv-cache dtype, head size) combination so ninja builds them in parallel.

Not a duplicate: no open issue or PR addresses this (searched issues and PRs for `attention.cu` split / translation unit / ROCm compile time / `MAX_JOBS`). The closest open items are #17419 (general "builds are too slow" RFC) and #60906 (reuse the CMake build dir for editable installs); both are orthogonal to removing the single-TU bottleneck.

## Claims

- Attention kernel compile drops from **547 s on 1 core to 72 s on 12 cores** (7.6×); the full editable install from ~10 min 40 s to ~1 min 35 s.
- `_rocm_C.abi3.so` link drops from ~2 s to 0.26 s (it no longer waits behind one 9-minute object).
- No behavior change: identical template instantiations, identical dispatch order, unchanged `paged_attention` signature and op registration.
- Cost: `_rocm_C.abi3.so` grows 196.3 MB → 219.2 MB (+11.6%) and aggregate CPU work grows ~30%, both traded for the 7.6× wall-clock win.

## Validation

Compile times on MI350 in `vllm/vllm-openai-rocm:nightly-rocm100-39983a5e7a5a575a7829f5d5ada50a33d9337ec1` with `PYTORCH_ROCM_ARCH=gfx950`; no compiler flags were set by hand, `-O2 -g` comes from the default `RelWithDebInfo` build type:

| Step | `main` | this PR |
|---|---|---|
| attention kernel compile (wall) | 547 s on 1 core | 72 s on 12 cores (58–72 s per TU) |
| `attention_dispatch.cu` (now the dispatch TU only) | — | 15 s |
| `_rocm_C.abi3.so` link | ~2 s | 0.26 s |
| full `MAX_JOBS=64 pip install -vvv -e . --no-deps --no-build-isolation` | 10 min 40 s | 1 min 35 s |
| `_rocm_C.abi3.so` size | 196.3 MB | 219.2 MB |

Per-edge timings come from `.ninja_log` of a cold build (`CCACHE_DISABLE=1 ninja -j64 _rocm_C`); all 12 attention TUs start within 2 ms of each other and finish 58–72 s later, so the split parallelizes as intended.

Kernel correctness — the positive matrix covers head 64/128 × block 16/32 × fp16/bf16 × kv auto/fp8 × alibi on/off × interleaved-V on/off × GQA 1/4/8, i.e. every one of the 12 instantiation TUs:

```bash

# 128 passed, 256 deselected, 414 s

# fp8 MFMA path (*_fp8_fp8 TUs)

```

No model eval is included: the split does not change kernels, dispatch, or numerics, only how many objects they are compiled into.

## Details

**Root cause.** A HIP translation unit is compiled by one clang process on one core; there is no clang equivalent of `nvcc --threads`, and additional `--offload-arch` values are also processed serially inside that process. `attention.cu` instantiates 12 kernels across 6 dtype/kv-cache combinations × 2 head sizes × 2 block sizes × alibi on/off × fp16/fp8 output × 2 v-cache layouts × CDNA/NAVI, so the whole tail is one serial 9-minute compile that `MAX_JOBS=64` cannot help with. (The popular "`Linking _moe_C_stable_libtorch.abi3.so` is slow" symptom is a ninja progress artifact: the link is 159 ms and the following line is simply not printed until `attention.hip.o` finishes.)

**Why splitting helps, measured.** Compile time is linear in the number of instantiations: restricting head size to 64 (half the instantiations) gives 270 s vs 547 s for the full set. So distributing the instantiations over N TUs gives ~N× wall-clock, minus a fixed cost.

**Why not just drop debug info.** Building the same TU with `-g0` gives 451 s vs 547 s, i.e. `-g` is only ~18% of the cost, and it would change the shipped build type. Splitting removes 475 s while keeping `RelWithDebInfo`.

**Design.** `csrc/rocm/attention_kernels.cuh` (renamed from `attention.cu`) holds the device helpers, all kernel and launcher templates, and the parameter-list macro. Each `csrc/rocm/attention_paged_attn_<head>_<dtype>_<kv>.cu` is ~4 lines: it includes the header and instantiates one combination via `ATTN_LAUNCH(...)`, exposing a fixed-head-size entry point. `csrc/rocm/attention_dispatch.cu` keeps `is_navi_gpu()` and the dtype/kv-cache dispatch (unchanged order) and forwards to those entry points. The instantiation sets are disjoint, so nothing is compiled twice on purpose. hipify follows quoted includes, so the new header is hipified like any other (`attention_kernels_hip.cuh`) and no build-system special-casing is needed beyond listing the new `.cu` files in `VLLM_ROCM_EXT_SRC`. Renaming `attention.cu` to `attention_kernels.cuh` keeps the 3.9k moved lines recorded as a rename, so `git blame`/`--follow` survive.

**Tradeoffs and limitations.**
- `.so` grows 196.3 → 219.2 MB (+11.6%), and the extra is debug info, not code: `.hip_fatbin` carries the device DWARF, and each TU emits its own copy of it for the headers/types it includes (the split's objects total 207.6 MB vs 169.4 MB, of which `.hip_fatbin` is 188.8 MB with `-g` but 42.2 MB with `-g0`, i.e. the ISA does not duplicate). Building these TUs with `-g1` gives a 96.1 MB `.so` and `-g0` a 74.9 MB one, both well below `main`'s 196.3 MB; that is left out here because it changes shipped debug info for the ROCm kernels, so it belongs in its own PR (there is exactly one out-of-line device helper, `warpReduceMax`, so marking helpers `__forceinline__` recovers nothing).
- Adding a head size, dtype, or kv-cache combination now means adding a TU and a `CMakeLists.txt` entry; the comments in `attention_kernels.cuh` and `CMakeLists.txt` point at this.
- The split is unbalanced: head size 128 TUs take ~70 s vs ~59 s for head size 64. Splitting within head size 128 (e.g. by block size) would lower the 72 s further, but the floor is ~20 s of frontend parsing per TU (measured with `-fsyntax-only`), so gains beyond 12–24 TUs are small unless a precompiled header is added.
- `attention_kernels.cuh` is hipified (`attention_kernels_hip.cuh`) like the ~15 other headers already in the tree (`quant_utils.cuh` → `quant_utils_hip.cuh`, `layernorm_utils.cuh`, …). `hipify_all` is an `add_custom_target` with no output file, so ninja treats it as always dirty and re-runs hipify on every build (~1 s), which regenerates those headers; editing the source header is therefore re-hipified normally and picked up by the next compile.
