# [CI] Cap CPU threads for (H200 MIG 18GB) Multimodal Processor

[Upstream PR](https://github.com/vllm-project/vllm/pull/58707) · state: closed · merged: False

## Original PR description

## What

The `(H200 MIG 18GB) Multimodal Processor` shards spend most of their time in CPU-bound Hugging Face processor calls. The container can see every host CPU while it shares the host with the other MIG slices, so each shard sizes its torch/OpenMP thread pools to the whole machine. This sets `OMP_NUM_THREADS=4` on this step only.

## Old

```yaml
- label: ":nvidia: (H200 MIG 18GB) Multimodal Processor Shard %N"
  key: multi-modal-processor
  parallelism: 4
  commands:
    - pytest -v -s models/multimodal/processing/test_tensor_schema.py --num-shards=... --shard-id=...
```

## New

```yaml
- label: ":nvidia: (H200 MIG 18GB) Multimodal Processor Shard %N"
  key: multi-modal-processor
  parallelism: 4
  env:
    OMP_NUM_THREADS: "4"
  commands:  # unchanged
```

## Notes

- **Why.** Since the job was sharded 1→4 (#56316), the same 39 cases in one shard vary by more than 3× in pytest time on recent `main`, and the variation tracks how busy the host's CPUs are, not which cases run. The extra time is inside the processor call. During a slow run, one of these shards was a single pytest with ~340 threads using 16–24 cores.
- **Scope.** A step-level `env:` only reaches this step's containers, through the Docker plugin's `propagate-environment`. No other job is affected. The `mirror.amd` job inherits step `env:` in the generator, so the MI355 mirror gets the same cap and is included in validation.
- **vLLM respects it.** `vllm/utils/torch_utils.py` leaves an externally set `OMP_NUM_THREADS` alone.
- **No coverage change.** Same file, same shard flags, same 160 cases.

## Expected runtime and overhead

| Job | pytest | running wall | non-pytest overhead | main overhead cause |
|---|---|---|---|---|
| Shard 1–4 (prediction) | runs on busy hosts move toward the uncontended range; uncontended runs roughly unchanged | pytest + ~1–2m | unchanged | image pull / setup |

This is a prediction, not a measurement: the thread cap has not been timed yet. The validation build will report per-shard pytest time and how busy each shard's host was. If the cap slows shards on uncontended hosts, the value will be adjusted. Aggregate worker-minutes should not go up, because the replica count is unchanged.

## Test plan

- `yaml.safe_load` on the edited file; the parsed step has `env: {OMP_NUM_THREADS: "4"}`, and its mirror inherits it.
- Scoped validation build with `multi-modal-processor` and `amd-multi-modal-processor`: all shards pass, `OMP_NUM_THREADS=4` visible inside the container, per-shard pytest time compared to recent `main`.

## Validation

Build [91203](https://buildkite.com/vllm/ci/builds/91203) at `561bc251da` (0 behind `main`), scoped to `multi-modal-processor` and `amd-multi-modal-processor`. All 8 shards passed.

- **Coverage unchanged.** 38 + 39 + 45 + 38 = 160 cases per lane, all passed. Every shard logged `HEAD is now at 561bc251da`.

### Primary lane (measured)

| Shard | pytest | running wall | non-pytest overhead | main overhead cause |
|---|---|---|---|---|
| 1 (38 cases) | 14.2m | 15.6m | 1.4m | container start + checkout (unattributed) |
| 2 (39 cases) | 16.6m | 18.0m | 1.4m | same |
| 3 (45 cases) | 13.4m | 14.8m | 1.4m | same |
| 4 (38 cases) | 13.4m | 14.8m | 1.4m | same |

- **Worker-minutes:** 63.2 in total, against a mean of about 71–116 on recent `main`, depending on host load. No extra cost, since the replica count is unchanged.
- **Slowest shard:** 16.6m of pytest, inside the 20m target.
- **Against the prediction:** it matches. Shard 2 runs the same 39 cases on every build. Its CPU-bound outlier cases, which took 5–20× longer on contended recent `main` runs, came back to their uncontended times. For example, `allenai/Molmo2-8B` took 30s, compared with 263–474s on slow `main` runs and 25s on fast ones.

### Mirror lane

All 4 replicas passed. Each one's runtime is in line with its own recent `main` baseline and well inside the timeout, so the inherited cap caused no regression there.

### Caveat

This is one build. The host was moderately loaded (about 4–5 concurrent jobs), not at its worst. The per-case signature that marked the slow runs is gone, but the p90 effect should be confirmed on `main` over the day after merge.
