# [Bugfix] Make collect_env list the running interpreter's packages under uv

[Upstream PR](https://github.com/vllm-project/vllm/pull/60191) · state: open · merged: False

## Original PR description

## Purpose

In a uv-created venv (which has no `pip`), `collect_env` falls back to
`uv pip list --format=freeze`. That call does not say which environment to
inspect, so uv discovers one from the working directory. Two things go wrong:

1. **Wrong packages are reported.** When the venv is not activated
   (e.g. `/path/to/.venv/bin/python -m vllm.collect_env`, or a systemd unit),
   uv lists a different environment. On my machine the venv had
   `torch==2.14.1+cpu` / `numpy==2.5.3`, but `collect_env` printed the system
   environment's `numpy==2.2.6` and `nvidia-*` packages. This is silent and
   ends up pasted into bug reports.
2. **It crashes when the command fails.** If `uv` is not on `PATH`, or uv finds
   no environment, `run_and_read_all` returns `None` and the script dies with
   `AttributeError: 'NoneType' object has no attribute 'splitlines'`
   (this is the crash mentioned in the environment section of #44538).

This PR passes `--python sys.executable` so the listed packages belong to the
interpreter running the script, and returns `None` when the command fails so
the report shows `[pip3] Could not collect` (the existing convention) instead
of crashing.

Follow-up to #13888 / #15792, which added the uv fallback.

**Not a duplicate:** checked open PRs with `gh pr list --search "collect_env"`
and `--search "13888 in:body"`. #48354 touches `get_pkg_version` (non-Linux
assert) and #39817 touches ROCm reporting; neither changes `get_pip_packages`.
The new tests live in `tests/test_collect_env_pip.py` to avoid colliding with
the `tests/test_collect_env.py` that #48354 adds.
