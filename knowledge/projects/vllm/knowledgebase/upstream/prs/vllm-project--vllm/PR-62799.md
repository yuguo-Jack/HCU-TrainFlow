# [ROCm][Perf] Add Triton skinny GEMM for 6-128 rows on RDNA4

[Upstream PR](https://github.com/vllm-project/vllm/pull/62799) · state: open · merged: False

## Original PR description




## Overview

On RDNA4, unquantized BF16/FP16 GEMMs with 6–128 rows fall through from `wvSplitK` (1–5 rows) to hipBLASLt, which runs these weight-bound shapes at 420–470 GB/s versus about 600 GB/s for `wvSplitK`. This PR adds a Triton GEMM for that range on RDNA4 and routes the DSpark/DFlash fused context-KV projection through the same dispatch.

## Claims

- Qwen3-8B BF16 on one R9700 (gfx1201): output throughput +28–29% with DSpark at concurrency 1–16, and +20–25% without speculative decoding at concurrency 16–64.
- GEMM time for 6–128 rows drops to 0.75–0.81× of main across 36 shapes. Other row counts are unchanged.
- GSM8K accuracy and DSpark acceptance length are unchanged.
- Only RDNA4 takes the new path. A new row count does not recompile, and cold start is unchanged.

## Validation

R9700 (gfx1201, 64 CUs), ROCm 7.2.3, torch 2.13.0+git733fca1, triton 3.8.0+git669b31ac. The baseline is this PR's base, 852989f58. Performance A/Bs ran back to back on the same GPU with separate compile caches.

## Details

**Root cause.** `wvSplitK` keeps the activation in LDS and only has templates for 1–5 rows (other counts throw), `wvSplitKrc` is gfx950-only, and hipBLASLt uses `MT128x128x32` for the Qwen3-8B shapes at every row count from 6 to 512. GEMM time therefore jumps at 6 rows (gate_up: 323 µs at 5 rows, 473 µs at 6). DSpark verifies 8 rows per request, so it pays this from concurrency 1, where GEMMs take 42 of the 45 ms of GPU time per step.

**Design.**

- Kernel (`vllm/kernels/triton/skinny_gemm.py`): one BM×BN tile per program over the full K, FP32 accumulation, optional bias, no split-K, `num_stages=1`, `do_not_specialize=["M"]`. The tile depends only on the row count, plus an N split at 65–128 rows. The rules come from a sweep of 17,694 configurations and are within 2.9% (geomean) of the best tile per point.
- Dispatch (`vllm/model_executor/layers/utils.py`): a new branch after `LLMM1`, taken on `on_rdna4()` for FP16/BF16 with 6–128 rows, N ≥ 512, K % 64 == 0, contiguous weight rows (a padded stride is allowed) and a contiguous bias. The checks read only tensor metadata, so there is no host sync, and they run inside the existing custom op, so the compiled graph is unchanged.
- `qwen3_dflash.py`: the fused context-KV projection called `F.linear` directly. It now uses `dispatch_unquantized_gemm()` like the other linear layers, which is still `F.linear` on CUDA.

**Limitations.**

- The range stops at 128 rows. From 129 to 256 rows hipBLASLt switches to better kernels, and one rule per band loses on 33 of 81 points. DSpark at concurrency 32 and above therefore gains nothing in steady state.
- Qwen3-14B o_proj and qkv run up to 5% slower than hipBLASLt at 64–128 rows.
- The rules were tuned on the 64-CU R9700.  RDNA3 is not enabled.
- CI has no RDNA4 runners, so the numerical tests skip there.
