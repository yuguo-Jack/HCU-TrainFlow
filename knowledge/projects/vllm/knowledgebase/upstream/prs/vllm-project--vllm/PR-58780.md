# [Bugfix][Parser] Stream DeepSeek V4/V3.2 string tool arguments incrementally

[Upstream PR](https://github.com/vllm-project/vllm/pull/58780) · state: closed · merged: True

## Original PR description

## Purpose

Fixes #52846.

DeepSeek V4, V4.1 and V3.2 streamed a long string tool argument as one fragment when `</｜DSML｜parameter>` arrived. The configs set `arg_structural_chars=frozenset(">")`, so the engine skipped every plain body delta.

The fix now uses the per-parser `arg_value_extender` hook, the same way GLM (#61253) and Gemma4 (#61494) do. The earlier engine-level gate change is dropped.

- `vllm/parser/deepseek_v4.py`: `_dsml_arg_value_extender` returns an extender while the last parameter is an open `string="true"` value. Each delta streams as escaped JSON text without rerunning the converter. It stops on a parameter tag, keeping a tail so a tag split across deltas is caught.
- Wired into `deepseek_v4_config`, `deepseek_v32_config`, and `deepseek_v41_config` (spaced DSML tags via `functools.partial`).
- `_param_patterns`: the trailing-partial regex holds back an unfinished next `<｜DSML｜parameter` tag, so a streamed value never includes it (implicit close case).

- bbrowning · comment · 2026-10-16T19:58:39Z · [source](https://github.com/vllm-project/vllm/pull/58780#discussion_r4298771284)

File: `vllm/parser/deepseek_v4.py` · line None

I believe this new regex is itself quadratic in time. It tries the optional `{start}[^>]*` branch at every `<｜DSML｜parameter` inside the value, and each attempt scans ahead to the next `>`. Both the converter and the extender factory run it on every conversion.

The lazy group plus `$` also causes a smaller bug: `$` matches just before a trailing `\n`, so for `...string="true">def f():\n` the check `pm.end(3) != len(raw_args)` is true and the extender never arms. Those deltas then go back to waiting for the next `>`.

My coding assistant suggested a fix like below for this to avoid the quadratic regex and take a test with 2,200 literal markers in one string value from 3.7 seconds for the converter + extender call down to 5 milliseconds on my machine.

Below is one suggested fix and analysis created by my coding assistant, but please review this suggestion and only copy it verbatim if it also looks good to you.

---

  Suggested fix: match greedily and do the holdback in Python. The holdback is the earliest `param_start` after the last `>`. That is exactly what the current regex selects, in O(n):
 
  ```python
  re.compile(rf"{head}(.*)\Z", re.DOTALL)  # trailing-partial regex
 
 
  def _match_open_param(
      raw_args: str, pos: int, partial_param_re: re.Pattern, param_start: str
  ) -> tuple[str, str | None, str, bool] | None:
      """Return ``(name, is_str, value, held_back)`` for the trailing open param."""
      pm = partial_param_re.search(raw_args, pos)
      if pm is None:
          return None
      value = pm.group(3)
      cut = value.find(param_start, value.rfind(">") + 1)
      if cut >= 0:
          return pm.group(1), pm.group(2), value[:cut], True
      return pm.group(1), pm.group(2), value, False
  ``` 
 
  The converter and `_dsml_arg_value_extender` both call this. The extender skips arming when `held_back` is true, which replaces the `pm.end(3)` check. `_dsml_arg_converter` takes a `param_start` kwarg, and `deepseek_v41_config` passes `DSML_PARAM_START` to it. I fuzzed this against the current regex on 200k inputs: results match except for trailing-`\n` inputs.

  Please also add tests for the holdback, which currently has no direct coverage:
  - V4: `_dsml_arg_converter(open + 'a > b<｜DSML｜parameter name="j', True)` returns `{"k": "a > b"}`, and the extender returns `None` for the same input.
  - V4.1: the same check through `deepseek_v41_config().arg_converter` with the spaced tags.
  - The extender arms for an open value ending in `"\n"`. This fails on the current head.
