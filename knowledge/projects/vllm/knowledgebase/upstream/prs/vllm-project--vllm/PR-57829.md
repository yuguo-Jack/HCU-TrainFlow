# [KVConnector] Add priority-aware transfer ordering

[Upstream PR](https://github.com/vllm-project/vllm/pull/57829) · state: open · merged: False

## Original PR description

## Purpose

In disaggregated prefill/decode deployments, P-to-D KV transfer is on the
TTFT critical path. It may share the same NIC with background Store or
offload traffic, especially when `MultiConnector` combines connectors such
as NIXL and `OffloadingConnector`.

Priority is currently lost at two points:

- `Request.priority` affects scheduler ordering, but is not propagated to
  connector workers. NIXL workers therefore process requests in metadata
  insertion order.
- `MultiConnector` invokes child connectors in config order. A background
  connector listed before a P/D connector is submitted first.

This PR adds priority-aware ordering at both levels:

- NIXL request metadata carries `Request.priority`, and save and receive work
  is ordered using the scheduler convention: lower values run first.
- Connectors expose a default `TransferPriority`. NIXL, Mooncake, and MoRIIO
  use `CRITICAL`; other connectors use `BACKGROUND` by default.
- `MultiConnector` uses this priority when calling `start_load_kv` and
  `save_kv_layer`. Connectors with equal priority keep their config order.
- The transfer order is computed once during initialization to avoid sorting
  in the per-layer forward path.
- The default priority can be overridden through
  `kv_connector_extra_config`.

The original connector list is not reordered because its config order is
used for metadata mapping and load selection. Existing behavior is preserved
when all connectors have the same priority, and request priority defaults to
zero.

This changes transfer submission order only. It does not preempt in-flight
transfers or enforce bandwidth limits. The optional TransferGate proposed in
Step 3 of #46016 is outside the scope of this PR.

## Test Plan

configuration, critical-before-background ordering, and stable config order
