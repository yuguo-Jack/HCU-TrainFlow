# [ROCm][Perf] Fuse the MXFP4 activation quant into the GDN gated RMSNorm

[Upstream PR](https://github.com/vllm-project/vllm/pull/59553) · state: open · merged: False

## Original PR description

## Purpose

With online MXFP4 on the GDN `out_proj` and `VLLM_ROCM_USE_AITER_FP4_ASM_GEMM=1`, the GDN output path at decode runs three launches: `RMSNormGated`, a separate `per_1x32_f4_quant_hip` activation quant, and the GEMM. 

This PR adds `AiterRMSNormGatedMxfp4GemmPattern` to `RocmAiterRMSNormQuantFusionPass`. It matches `RMSNormGated -> reshape -> gemm_with_dynamic_quant` and lowers it to a new `rocm_aiter_fused_rms_gated_mxfp4_gemm` op:

- **Below M=32, on a shape with a tuned preshuffled FP4 GEMM config:** AITER's `fused_rms_gated_mxfp4_quant` produces the MXFP4 activation and unshuffled per-1x32 scales, which go straight to `gemm_afp4wfp4_preshuffle` via `x_scales`.
- **Everywhere else:** the gated norm (FLA `rmsnorm_fn`), then the GEMM, exactly as today. This covers M ≥ 32 (shuffled scales) and untuned shapes (ASM `gemm_a4w4`).
- **When the pattern registers:** per GDN layer shape, gate activation and epsilon. Only for layers whose `out_proj` runs `AiterMxfp4LinearKernel` in ASM mode (online MXFP4 via `quant_method.kernel`, or Quark via `scheme.ocp_mx_linear`), with `norm_before_gate=True` and `group_size=None`, head dims divisible by 32, and when AITER has `fused_rms_gated_mxfp4_quant`.
- **Symbolic flatten:** `RocmAiterRMSNormQuantFusionPass` now rewrites a `reshape` whose target shape has exactly one symbolic size to `-1` before applying its patterns (`reshape_symbolic_dim_to_minus_one`). GDN's `_output_projection` flattens heads with `core_attn_out.flatten(-2)`, which compiles under a dynamic token count to `reshape(x, [s, hidden])`, with `s` a graph input. The gated-norm patterns are traced with `reshape(-1, hidden)`, so before this change they never matched in serving, even though the unit test (which flattened with `reshape(-1, ...)`) passed. With one unknown size the two reshapes are the same op, so the rewrite only widens matches. The existing FP8 gated pattern (`AiterRMSNormGatedFp8GroupQuantPattern`) traces the same `reshape(-1, hidden)`, so it presumably had the same miss on GDN models in serving and now matches too (TODO: confirm on an FP8 GDN checkpoint, e.g. Qwen3-Next FP8).
- **`MatcherRMSNormGated`:** gains an `activation` argument, default `swish` as before. Without it, sigmoid-gated models such as Qwen3.8-Flash-Next (`output_gate_type: sigmoid`) never match. The existing FP8 gated pattern does not match them either, and is left unchanged here.

This does not cover the `in_proj_qkvz` activation quant. On Qwen3.8-2.4T that one is fused into the AR+RMSNorm by #59483. On Qwen3.8-Flash-Next the input of `in_proj_qkvz` comes from the HyperConnection two-stage kernel, not from an AR+RMSNorm, so #59483 has nothing to match. That quant needs an MXFP4 epilogue in the HC kernel (subsequent work needed).

## Test Plan

- Hardware: MI355X (gfx950)
- Unit tests: new `tests/compile/passes/test_fusion.py::test_aiter_fusion_rmsnorm_gated_mxfp4_gemm`:
  - a real `AiterMxfp4LinearKernel` in ASM mode at N=8192, K=2048 (a shipped tuned shape);
  - M=8 (fused) and M=64 (fallback);
  - SiLU and sigmoid gates;
  - (N·H, D) and (N, H, D) layouts, the latter flattened with `reshape(-1, H·D)` and with `flatten(-2)` (GDN's form; it fails without the symbolic-reshape rewrite);
  - checks one match, the fused op present after the pass, and the output against the unfused graph.
  - The existing `test_aiter_fusion_rmsnorm_gated_quant*` FP8 tests are run alongside.
- Model: `amd/Qwen3.8-Flash-Next-Quark-MXFP4`, TP2, GDN `in_proj_qkv`/`in_proj_z`/`out_proj` quantized online to MXFP4, `VLLM_ROCM_USE_AITER_FP4_ASM_GEMM=1`, `pass_config.fuse_norm_quant=true`, FSE on.
- Serving A/B on one image with this PR, ROCm/aiter#6038 and the tuned GDN configs (ROCm/aiter#6039): `fuse_norm_quant=true` vs `false`, everything else identical. On this checkpoint the gated pattern is the only one the pass replaces (it logs `Replaced 0 patterns` per GDN subgraph without it), so the flag toggles exactly this fusion. 8k/1k c4, c16, c64 and 60k/600 c4; four repeats in two waves, with the arms on rotated GPU pairs.
- GSM8K 5-shot on the checkpoint card's recipe, both arms, same servers as the A/B.

### Unit tests

On MI355X, in `vllm/vllm-openai-rocm:nightly-ac68c308` with this change and the AITER kernel applied:

```bash
python -m pytest -q tests/compile/passes/test_fusion.py -k rmsnorm_gated
```

```text

```

With the `flatten(-2)` cases added: 12 gated MXFP4 cases pass (the 4 `flatten(-2)` ones fail on the previous commit), and all 31 `-k aiter` tests in `test_fusion.py` pass.

In serving (Flash-Next TP2), the pass logged `Replaced 0 patterns` on every GDN subgraph before the rewrite and `Replaced 1 patterns` after it.

### Kernels

Decode trace, one image, `fuse_norm_quant` off vs on, one profiled window of four 8k-input / 128-output requests at c=4 (128 decode steps at M=4). Per decode step, rank 0 (rank 1 agrees within 5 µs):

| | `fuse_norm_quant` off | on (this PR) |
| --- | --- | --- |
| GDN gated RMSNorm (Inductor-generated Triton) | 36 launches, 154 µs | – |
| `out_proj` MXFP4 activation quant (`aiter::dynamic_per_group_scaled_quant_kernel`) | 36 launches, 151 µs | – |
| `_fused_rms_gated_mxfp4_quant_kernel` | – | 36 launches, 164 µs |
| Decode step, GPU busy | 7.379 ms | 7.236 ms (−1.9%) |

The pattern matches on all 36 GDN layers. Each replaced kernel takes 4.2–4.3 µs at M=4 and the fused one 4.5 µs, so the saving is one launch per layer: 142 µs per step, the whole decode-step difference (144 µs). The `in_proj_qkvz` quant (the other 36 `dynamic_per_group_scaled_quant_kernel` launches) is unchanged, as described above.

| --- | --- | --- | --- | --- | --- |
| 8,192 | 1,024 | 4 | 454.9 → 446.1 (−1.9%) | 7.51 → 7.48 (−0.4%) | +4.1% / −4.1% / −4.6% / −3.1% |
| 8,192 | 1,024 | 16 | 937.7 → 892.5 (−4.8%) ¹ | 14.13 → 15.10 (+6.9%) | −12.4% / +0.4% / −10.1% / +2.7% |

No serving change is measurable: the trace's −1.9% decode step (0.14 ms at 7.4 ms TPOT) is below this A/B's resolution, and the only cell whose repeats agree in sign (8k c64) moves by about 1%. ### Known issue, not changed here

With `+rms_norm_gated`, the existing FP8 gated pattern (`AiterRMSNormGatedFp8GroupQuantPattern`) fails to register with "Duplicate pattern". The FLA custom-op trace does not depend on epsilon, so the 1e-5 and 1e-6 registrations collide. With `-quant_fp8`, the two head layouts also collide. `RocmAiterRMSNormQuantFusionPass.__init__` then raises for any GDN model. This PR's pattern registers once per epsilon the layers use, to stay clear of that. The new test runs `-rms_norm_gated`, the form serving uses: the served graph dump shows the decomposed native norm (`pow`/`mean`/`rsqrt`/`sigmoid`/`mul` in fp32) feeding `out_proj` (TODO: add `+rms_norm_gated` coverage once the FP8 pattern is fixed).
