# [Bugfix][compile] Fix AOT artifact loading in DYNAMO_TRACE_ONCE mode

[Upstream PR](https://github.com/vllm-project/vllm/pull/60661) · state: open · merged: False

## Original PR description



## Overview

Fixes #60611

AOT artifacts saved in compilation mode `DYNAMO_TRACE_ONCE` can't be loaded because `_try_load_aot_compiled_fn` at [`vllm/compilation/decorators.py:315`](https://github.com/vllm-project/vllm/blob/458ba2edf85bc9b7ebc0d5141f34ea658520faf5/vllm/compilation/decorators.py#L315) doesn't check whether the loaded artifact is a `VllmSerializableFunction` or a pytorch `BundledAOTAutogradSerializableCallable` (that doesn't have `finalize_loading`); this resulted in every startup recompiling the model.

## Claims

AOT artifacts saved in `DYNAMO_TRACE_ONCE` mode now load so the CPU backend reuses it's compile cache. I modified `test_save_and_load` (in `tests/compile/test_aot_compile.py`) to cover both `VLLM_COMPILE` and `DYNAMO_TRACE_ONCE`.

## Validation

I built the `vllm-cpu-test` image from this branch and tested with and without the fix in `decorators.py`, with the fix both tests pass, without both fail, since the `VLLM_COMPILE` mode gets overwritten to `DYNAMO_TRACE_ONCE` in [`CpuPlatform.check_and_update_config:349`](https://github.com/vllm-project/vllm/blob/458ba2edf85bc9b7ebc0d5141f34ea658520faf5/vllm/platforms/cpu.py#L349).
```
docker build -f docker/Dockerfile.cpu --target vllm-test --build-arg max_jobs=4 -t vllm-cpu-test .

# with the fix
docker run --rm --shm-size=4g vllm-cpu-test pytest -v tests/compile/test_aot_compile.py -k "save_and_load and not slice"

# without the fix
git show upstream/main:vllm/compilation/decorators.py > /tmp/decorators_main.py
docker run --rm --shm-size=4g -v /tmp/decorators_main.py:/opt/venv/lib/python3.12/site-packages/vllm/compilation/decorators.py:ro vllm-cpu-test pytest -v tests/compile/test_aot_compile.py -k "save_and_load and not slice"
```

## Details

The fix consisted of the following guard inside `decorators.py`:
```python
if isinstance(loaded_fn._artifacts.compiled_fn, VllmSerializableFunction):
    with maybe_use_cudagraph_partition_wrapper(model.vllm_config):
        loaded_fn._artifacts.compiled_fn.finalize_loading(model.vllm_config)
```

The `VllmSerializableFunction` requires an additional step implemented in `finalize_loading`, however if the artifact is `BundledAOTAutogradSerializableCallable` then the additional step is not required and calling `finalize_loading` causes an attribute error.

- hossiendehghan989 · comment · 2026-10-09T02:12:29Z · [source](https://github.com/vllm-project/vllm/pull/60661#issuecomment-6072841622)

I independently reviewed the guard and the parametrized save/load coverage. The `isinstance(..., VllmSerializableFunction)` check is a good boundary: it avoids calling `finalize_loading()` on bundled AOT callables while preserving the existing path for vLLM-owned serializable functions.

One useful detail in the current test is that it exercises both `VLLM_COMPILE` and `DYNAMO_TRACE_ONCE` through the real save/load path, rather than only testing the branch in isolation. The remaining thing I would keep an eye on during review is artifact-type coverage: if the fixture can be made to assert that the loaded callable is the bundled/non-vLLM serializable form, that would make the regression contract explicit and prevent a future fixture change from silently testing only the old `VllmSerializableFunction` path.

The implementation itself is narrowly scoped and the behavior change is appropriately conservative: skip eager finalization only for the callable type that does not provide that contract.
