# [Bugfix][Quantization] Keep AWQ batch-invariant under torch.compile

[Upstream PR](https://github.com/vllm-project/vllm/pull/60013) · state: open · merged: False

## Original PR description



## Overview

Fix #59086: with `VLLM_BATCH_INVARIANT=1`, AWQ models served through the Triton AWQ path (`AutoAWQLinearMethod`) are not batch-invariant under torch.compile. `AutoAWQLinearMethod.apply` now calls `mm_batch_invariant` directly in batch-invariant mode, as `UnquantizedLinearMethod` already does with `linear_batch_invariant`. The aten `matmul` override it relied on is bypassed once Inductor lowers the graph.

## Claims

- `Qwen/Qwen3-8B-AWQ` with `VLLM_BATCH_INVARIANT=1` and the default compile + CUDA graphs is batch-invariant on SM89 (RTX 4090) and SM86 (RTX A5000), using the reporter's reproducer.
- No GSM8K accuracy change in batch-invariant mode (0.876 → 0.878).
- The non-batch-invariant path is unchanged.

## Validation

## Details

**Root cause.** On SM8x, `enable_batch_invariant_mode()` makes matmuls batch-invariant by overriding `aten::mm/addmm/matmul/linear` at the CUDA dispatch key. In eager mode, the `torch.matmul` in `AutoAWQLinearMethod.apply` reaches that override, which matches the issue's `--enforce-eager` result. Under torch.compile, the call is traced to `aten.mm`, and Inductor lowers it to `extern_kernels.mm(..., out=...)`. That goes to `aten::mm.out`/cuBLAS, which is not overridden, and cuBLAS chooses kernels by M. Generated code on main:

```python
buf2 = torch.ops._C.awq_dequantize.default(arg4_1, arg5_1, arg6_1, 0, 0, 0)
...
extern_kernels.mm(buf4, buf3, out=buf5)
```

Unquantized and FP8 (CUTLASS) linears are unaffected because they call batch-invariant kernels directly. Dynamo keeps those calls as user-defined Triton kernels.

**Relation to #57047.** #57047 replaces this path with a fused W4A16 kernel, but only on compute capability ≥ 8.9 and, off SM89, only for tuned shapes. Every other case falls back to the `torch.matmul` path fixed here, including all of SM80/SM86 (A100, A10, RTX 3090). The two changes compose: the fused kernel takes the shapes it supports, and this fix makes the fallback correct. I also ran the issue's Qwen3-8B-AWQ reproducer on #57047's head (on its own base, `988d9b67`) on an RTX 4090, and it is batch-invariant there (3/3).

**Tradeoffs and limitations.**
- In batch-invariant mode, the AWQ fallback uses the Triton persistent matmul on every CUDA arch. That includes SM90/SM100, where it previously went to cuBLAS with the restricted workspace. This matches what unquantized linears already do in this mode. Hopper/Blackwell were not tested here (no hardware).
- Throughput in batch-invariant mode drops (the GSM8K run above: 688 → 581 output tok/s on an RTX 4090). Eager mode already paid this cost, since it hit the same kernel through the override.
- INC (AutoRound) WNA16 checkpoints that select `AutoAWQLinearMethod` get the same fix.
- Out of scope: `Fp8LinearMethod`'s batch-invariant fallback for per-tensor/per-channel weights (dequant → `F.linear`) depends on the override in the same way. It is not touched or tested here.

**CI.** The new test is added to the `(A100) Batch Invariance` step. SM80 is the arch where the aten override is the only mechanism and #57047 does not apply. It was validated on SM86 and SM89, not on A100 itself.

**Not a duplicate.** Searched open PRs for the issue number and for AWQ / batch invariance / torch.compile keywords. The only related PR is #57047, which is complementary (see above).
