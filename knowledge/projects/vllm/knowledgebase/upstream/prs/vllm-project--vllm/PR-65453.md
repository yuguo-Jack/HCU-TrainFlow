# [Bugfix][Multimodal] Keep FlashInfer `cu_seqlens` halves aligned in GLM-5.3-Flash/Kimi-K2.5 encoder CUDA graph replay

[Upstream PR](https://github.com/vllm-project/vllm/pull/65453) · state: open · merged: False

## Original PR description



## Overview

Follow-up to #64984. GLM-4.1V/4.5V (and GLM-OCR and GLM-5.3-Flash, which inherit its config) and Kimi-K2.5 have the same FlashInfer `cu_seqlens` misalignment in encoder CUDA graph replay. This registers the existing `_pad_flashinfer_cu_seqlens_buffer` for both.

## Claims

- GLM-4.1V family: with video enabled, capture pads `cu_seqlens` to `max_frames_per_batch`, but image replays pad to `max_batch_size`. With FlashInfer backend, image replays then result in a smaller batch bucket than the capture.
- Kimi-K2.5: capture pads to `max_batch_size + 1`, but replays are unpadded, so the buckets differ once `max_batch_size >= 8`.
  - FlashInfer now uses `_pad_flashinfer_cu_seqlens_buffer`.
  - Other backends keep the existing `pad_cu_seqlens`.

## Validation

```shell
pytest tests/v1/cudagraph/test_encoder_cudagraph.py -v

# 99 passed in 30.30s
```

## Details

There is no model architectures left:

- DeepSeek-V4.1 and MiniMax-M3 reject FlashInfer when encoder CG is on.
- Qwen3-Omni is covered by #63809.
- Kimi-K3, unlike its predecessor, pads capture and replay to the same size.
