# [Bugfix][LoRA] Apply DeepSeek-V4 compressor and wo_a adapters

[Upstream PR](https://github.com/vllm-project/vllm/pull/64880) · state: open · merged: False

## Original PR description



## Overview

Since #53361 ("Support LoRA for DeepSeek V4") and #55897, DeepSeek-V4 has declared `SupportsLoRA`. On the CUDA path, though, adapters on the compressor's `wkv`/`wgate` and on `wo_a` are silently dropped. Both projections run their GEMM directly on the base weight, which bypasses the LoRA wrapper.

#57245 already fixed this for DeepSeek-V4.1. It added LoRA wrappers plus V4.1-local copies of the two layers those wrappers match. This PR builds V4's projections as the same layers and moves the layers from V4.1 into V4, so the two models share one copy.

## Claims

- Adapters on `compressor.wkv`/`wgate`, `indexer.compressor.wkv`/`wgate` and `wo_a` now apply on all three V4 CUDA attention backends (FlashMLA, FlashInfer SM100, FlashInfer SM120).
- Without LoRA, every changed V4 projection runs the same kernels on the same inputs as before, so outputs are bit-identical (the tests assert this).
- FlashInfer RopeQuant (SM100) is turned off when LoRA is enabled. It writes only FP8 attention output, and the `wo_a` adapter needs the BF16 input.
- DeepSeek-V4.1 behavior is unchanged. It now imports the two layers from V4 instead of keeping copies that matched V4's apart from import paths.

## Details

**Root cause.**
- The compressor kv_score closures in `DeepseekV4Attention._run_parallel_input_projections` call `torch.mm(hidden_states, fused_wkv_wgate.weight.T, out_dtype=torch.float32)`.
- Every CUDA `_o_proj` passes `self.wo_a` to `deep_gemm_fp8_o_proj`, which runs `fp8_einsum`/`torch.bmm` on `wo_a.weight`.
- Under LoRA, both modules are LoRA wrappers whose `weight` (and `weight_scale`) resolve to the base layer, so these GEMMs never see the adapter. Nothing raises an error.

**Compressor.**
- `DeepseekV4CompressorKVScoreLinear` is a `MergedColumnParallelLinear` whose forward is that FP32 GEMM. It moved unchanged from `deepseek_v41/compressor.py` to `deepseek_v4/compressor.py`. V4's closures now call the layer.
- `DeepseekV4CompressorKVScoreWithLoRA`, added in #57245, matches the layer by class name and adds the adapter delta.
- CPU keeps the plain layer:
  - Its packed GEMM frees the raw weight (`dispatch_cpu_unquantized_gemm(remove_weight=True)`).
  - CPU attention calls the layer and upcasts the result itself.
  - The CPU V4 model does not declare `SupportsLoRA`.

**`wo_a`.**
- `DeepseekV4GroupedWoA` is the `ColumnParallelLinear` `wo_a`, plus two methods:
  - `grouped_forward`, which wraps the unchanged `deep_gemm_fp8_o_proj`.
  - `grouped_input`, which returns the BF16 inverse-rotated groups.
- The class moved from `deepseek_v41/common/grouped_wo_a.py` to `deepseek_v4/common/grouped_wo_a.py`. Only the docstring and one import path differ, and V4.1's `fused_inv_rope_fp8_quant` already re-exports V4's.
- The three V4 CUDA `_o_proj`s call `wo_a.grouped_forward(...)` and then `wo_b`.
- `DeepseekV4GroupedWoAWithLoRA`, added in #57245, adds each group's delta:
  - LoRA-A is shared.
  - Group `g` uses LoRA-B rows `g*o_lora_rank:(g+1)*o_lora_rank`, each kept as its own buffer.
  - Under fully sharded LoRA, every rank keeps the full LoRA-A.
- This PR changes only the wrapper's type-only import.
- `deep_gemm_fp8_o_proj` keeps its signature and behavior.

**Sharing with V4.1.**
- V4.1 already imports many pieces from V4: attention helpers, ops and model classes. Its `attention.py` and `compressor.py` now also import these two layers, and `deepseek_v41/common/grouped_wo_a.py` is deleted.
- Both LoRA wrappers match by class name, so they serve both models.

**Compatibility.**
- Both layers are plain subclasses. Nothing outside `vllm/lora` checks `type(...) is ColumnParallelLinear`/`MergedColumnParallelLinear`.
- The quant methods' `is_bmm` handling and #64827's `fp8_einsum` warmup read `wo_a` attributes, which the wrapper forwards.
- ROCm keeps reading `.weight` directly (fused compressor GEMM, mono decode, FP8 `wo_a`). Neither the AMD nor the CPU V4 model declares `SupportsLoRA`.
- XPU declares `SupportsLoRA` and picks up the compressor fix through the shared closures. Its `_o_proj` still reads `wo_a.bmm_weight` directly, so its `wo_a` adapters are still dropped. That is left for a follow-up.

**Tests.**
- The new V4 tests construct the real layers, LoRA wrappers and punica wrapper. They call the real `_run_parallel_input_projections` and the three backends' `_o_proj`.
- They check only V4's call sites. With an adapter set, V4's output must match the LoRA layer's own output. Without one, it must match the raw GEMM bit for bit.
- The wrapper's own math is covered by the existing V4.1 tests on the same layers: per-group LoRA-B, FP8 `wo_a`, the pointer cache, `reset_lora` and fully sharded LoRA.
- A `SimpleNamespace` stands in for the attention module, because building a real `DeepseekV4Attention` needs a full V4 config and GPU backends.
- The tests run in the H200 `LoRA` step and are skipped on its AMD mirror. That step doesn't watch `vllm/models/deepseek_v4/`, so a later V4-only change won't rerun them.

**Not a duplicate.**
- No open PR addresses this. I searched "deepseek v4 lora", "fused_wkv_wgate", "wo_a lora", "grouped_wo_a", "RopeQuant lora" and "pointer cache lora".
- #57245 (DeepSeek-V4.1 LoRA, merged) added the LoRA wrappers and V4.1-local copies of these layers. This PR applies them to V4 and removes the copies.
- #64827 (DeepGEMM warmup for the V4 o_proj) does not touch `deep_gemm_fp8_o_proj` or the call sites.
- #44847 edits a different function in `o_proj.py`.
