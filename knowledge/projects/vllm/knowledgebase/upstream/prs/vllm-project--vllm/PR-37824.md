# [Feature] RIY: Runtime expert pruning for MoE models

[Upstream PR](https://github.com/vllm-project/vllm/pull/37824) · state: open · merged: False

## Original PR description

## Summary

**RIY (Reap It Yourself)** adds runtime expert pruning for MoE models — load a JSON profile at startup to skip unused experts, saving GPU memory and keeping routing correct. Zero performance overhead in production mode.

**Key features:**
- `--riy-expert-profile profile.json` CLI flag: per-layer expert pruning at load time via logit mask + expert_map
- Real VRAM savings: pruned experts not allocated (local_num_experts reduced)
- Optional monitoring (`VLLM_RIY_MONITOR=1`): per-expert activation stats + HTTP API on port 8019
- Stats collection → profile generation → production deployment workflow

**Design:**
- Profile mask applied at FusedMoE init via logit mask on router (zero hot-path overhead)
- Monitor mode (stats + HTTP + live mask) guarded behind env var — measured 5% overhead when active, 0% when inactive
- Compatible with EP, TP, CUDA Graphs, torch.compile
- Works with quantized models (GPTQ, NVFP4, FP8) and speculative decoding (MTP/EAGLE)

## Benchmarks (Qwen3.5-397B-A17B INT4, TP=2, DGX Spark GB10)

| Config | tok/s (medium) | Overhead |
|--------|---------------|----------|
| Baseline (no RIY) | 28.0 | — |
| RIY 20% pruned (no monitor) | 27.9 | **0%** |
| RIY 20% pruned (with monitor) | 26.4 | ~5% |

## Profile format

```json
{
  "version": 1,
  "model": "qwen3.5-397b-vl",
  "workload": "live capture",
  "pruned_experts": [[0, 3], [0, 11], [4, 7], ...]
}
```

Hi @Alizen-1009, thanks — and great timing.

**Status:** Yes, I'm actively maintaining it. The PR has been queued behind a research deadline (paper in preparation), which is also why I built the live monitor + JSON profile format on top of the load-time pruning. Happy to coordinate.

**On your routing question — confirming the mechanism:**
RIY does both, in the right order:

1. **Logit mask before top-k** (`vllm/model_executor/layers/fused_moe/router/base_router.py:307-308`): `router_logits = router_logits + self.prune_logit_mask` where pruned experts hold `-inf`. The router never selects them, so no top-k slot is "wasted".
2. **Renormalization** (`vllm/model_executor/layers/fused_moe/riy.py:384-404`, `apply_riy_mask()`): topk_weights for pruned experts are zeroed and renormalized over the surviving experts (`topk_weights = topk_weights / denom`).
3. **expert_map = -1** is set additionally as a kernel-level guard (`riy.py:369-377`) — but the logit mask is the quality-preserving piece. You're right that `expert_map=-1` alone would silently drop the contribution and waste the top-k slot.

**Load-time vs runtime:** Both. `local_num_experts` is reduced at load (`layer.py:513-520`), so pruned experts are never allocated. The logit mask is rebuilt at runtime when the live monitor pushes a new profile, so a new prune set takes effect without reload.

**TP/EP:** TP is orthogonal (TP shards inside experts; RIY shards across experts). EP is composed: `determine_expert_map()` runs first, then RIY replaces the EP `expert_map` (`layer.py:518-520`). I've verified TP=2/4 in practice; **EP I have only run smoke-tested, not paper-grade**. Dedicated EP+RIY tests are missing — that's a real gap.

**Concrete coordination — yes to all three of your offers:**
- **Rebase onto main**: yes please, that unblocks the rest.
- **Qwen3-30B-A3B memory/throughput/quality numbers**: yes — those would land directly in the paper ablation if you're OK with a citation/co-credit in the experiments section.
- **EP routing tests + EP-mode verification**: yes, this is exactly the gap above. A focused test that exercises EP rank N>0 with a non-trivial prune set would be very welcome.

**Framing — your Shapley work is complementary, not redundant:** RIY is the *mechanism* (load-time + runtime mask + monitor + profile format); your Shapley-MoE is the *selection criterion* that decides which experts to prune. The JSON profile is decoupled from the selection method by design — Shapley scores can write into the same format and benefit from the load-time allocation savings without any RIY-internal changes. That's the kind of layering this should converge to.

![critical](https://www.gstatic.com/codereviewagent/critical.svg)

The `ensure_riy_server` function has a race condition. The check for `_riy_server_started` and its subsequent update are not atomic. In a multi-threaded environment where `on_forward()` could be called concurrently for the first time, this could lead to multiple threads attempting to start the HTTP server, causing a port binding conflict. This should be protected with a lock.

```suggestion
_riy_server_started = False
_riy_server_lock = threading.Lock()


def ensure_riy_server(port: int = 8019):
    """Start RIY HTTP server once (idempotent)."""
    global _riy_server_started
    if _riy_server_started:
        return
    with _riy_server_lock:
        if _riy_server_started:
            return
        _riy_server_started = True
        t = threading.Thread(target=_start_riy_server, args=(port, ), daemon=True)
        t.start()
```
