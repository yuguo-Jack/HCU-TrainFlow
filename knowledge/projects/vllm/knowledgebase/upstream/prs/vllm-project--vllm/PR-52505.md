# [Frontend] Write run-batch responses incrementally instead of at the end

[Upstream PR](https://github.com/vllm-project/vllm/pull/52505) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

`vllm run-batch` buffered every response and wrote the output only when the whole batch finished. Responses are now written in input order as the batch runs, and frontend memory no longer grows with the input. Follows #53500, which moved this file. Related: #30268.

## Claims

- An interrupted or failed run leaves the responses for a prefix of the input on disk, instead of nothing.
- Output stays in input order, as before.
- At most `--max-inflight` requests run at once, and at most 16 times that many are dispatched but not yet written.
- A malformed batch or a bad `--output-file` fails before the model loads. A dead engine fails the run at its first error response, so the output stays a prefix of real responses, instead of exiting 0.

## Validation

At 5dbc1cbe30 on an RTX A6000:

| Check | Result |
|---|---|
| `pytest tests/entrypoints/launchers/test_run_batch.py -v` | 52 passed, including the model-launching tests |
| 4000 requests, SIGINT after 1000 written | 1024 lines, all status 200, exactly the first 1024 input lines |

Pre-commit passes. @vinitrbl's A10G run showed SIGTERM and SIGKILL leaving every finished line, where v0.31.0 left no file, and peak frontend RSS on 50k requests dropping from 1876 to 1159 MiB.

On an L4: killing EngineCore at 417 of 4000 requests left 448 rows with no errors, exit 1, and no URL upload at d73fed12ac, where the previous head wrote all 4000 rows with 3580 errors. With both queue limits cleared, 200 requests went from 196 rows of 503 to 0 at `--max-num-queued-reqs 8` with `n=4`, and from 199 to 0 at `--max-num-queued-tokens 64`.

**Reorder window.** Writing in input order lets one long request hold back everything behind it. Throughput against writing in completion order, on an H100 with 4000 chat requests, median of 3:

| Workload | Window 1x `--max-inflight` | 4x | 16x |
|---|---|---|---|
| Uniform | +2% | 0% | +1% |
| 2% of requests 16x longer | −54% | −9% | 0% |
| Heavy tail | −49% | −6% | +1% |
| A long request every window | −60% | −15% | −3% |

Qwen3-0.6B on the heavy tail gave −41%, −4%, and +1%. Peak frontend RSS was about 1.1 GB throughout.

## Details

- **Memory.** Finished responses wait as serialized JSON, at most 16x `--max-inflight` of them, which is about 45 MB of chat responses at the default.
- **Defaults.** `--max-inflight` is twice `max_num_seqs` across data-parallel engines, at least 1024. `--max-num-queued-reqs` and `--max-num-queued-tokens` are ignored with a warning, since the engine would answer requests past them with 503s.
- **Input.** Opened once and read twice. A pipe or URL is staged first.
- **Output.** A local file is truncated at start. A URL output is uploaded only on success.
- **URL input.** The download has the same 300s total timeout as before and now retries a stall, with a longer timeout each attempt. A timeout on stalled reads alone, allowing arbitrarily long downloads, would need a change to `vllm/connections.py`.
- **Duplication.** No other open PR changes how run-batch handles requests.
- **Follow-up: resume.** An interrupt discards responses that finished but were waiting behind an earlier request, up to the reorder window, so a resume reruns them. A follow-up PR would write them on Ctrl+C or a failed run to a side file such as `results.jsonl.ahead`, in the same format and input order. A resume, or a later `--resume` flag, could then skip both the written prefix and that file. Handling SIGTERM the same way would cover preemption too.

Found one issue with Ctrl+C though. After SIGINT the output has the 1664 real responses plus 951 lines with status 400 and "Client disconnected". Those are the in-flight requests that get cancelled in the `finally` of `dispatch_batch`: the chat handler catches the `CancelledError` and returns an error response instead of raising, so `run_and_write` writes it out like a normal result. Probably the same happens when one request raises and the rest get cancelled. The existing cancel test monkeypatches `run_one_request`, so it never goes through the real handler.

So an interrupted output looks like it has a bunch of genuine 400s, and anything that reads the file to figure out what's left would think those requests are done. Maybe set a flag before cancelling the in-flight tasks and skip the write in `run_and_write` when it's set? Then SIGINT leaves the same thing behind as SIGTERM and SIGKILL.

Separate from this PR, but it bit me while testing: after SIGTERM or SIGKILL, `VLLM::EngineCore` keeps running with ~21 GB allocated (still there after 3 minutes), so rerunning on the same GPU fails until you kill it by hand. run-batch doesn't handle SIGTERM the way `vllm serve` does, so even a plain SIGTERM leaves it behind. That's #55510, and #55846 fixes it for run-batch too. I left numbers there.

Also noticed `vllm/entrypoints/launchers/` has no CODEOWNERS entry since the move in #53500, which might be why nobody got auto-requested on this one. cc @simon-mo

🔴 Operators running `vllm run-batch -i https://...` can now hang forever if the download stalls, where the base timed out after ~5 minutes. open_batch_input calls `global_http_connection.async_download_file(path_or_url, download_path, chunk_size=...)` (run_batch.py:389-391) without a timeout, and that helper defaults `timeout` to `None`; aiohttp treats an explicit `None` as disabling its session timeout rather than applying the 300s default. The old `read_file` used `aiohttp.ClientSession().get(url)` with aiohttp's default sentinel, so a stalled connection failed after ~300s. Fix: pass an explicit positive timeout (e.g. a stall/read timeout) into `async_download_file` for the batch input download, matching the PR's own noted need for a stall timeout in `vllm/connections.py`.

<details>
<summary>Why this was flagged</summary>

Trigger: `vllm run-batch -i https://host/batch.jsonl` where the server accepts the connection then stalls mid-download (slow link, firewalled middlebox, hung server). open_batch_input (run_batch.py:389-391) awaits `global_http_connection.async_download_file` with no `timeout` kwarg; `HTTPConnection.get_async_response` (vllm/connections.py:384-397) forwards `timeout=None` straight into aiohttp's `session.get`, and aiohttp treats an explicit `None` as 'no timeout', unlike the sentinel default. Before this diff, `read_file` used `aiohttp.ClientSession().get(url)` with aiohttp's session default (~300s), so a stalled download eventually failed. Now the whole run-batch process can hang indefinitely before the model even loads. The PR text calls this a known limitation deferred to a later `vllm/connections.py` change, but it is a real new regression for this code path, not just a documented gap in a brand-new feature.

**Verification:** The base `read_file` (base run_batch.py:342-344) downloads via `aiohttp.ClientSession().get(path_or_url)` with no explicit timeout, so aiohttp's default `ClientTimeout(total=300)` applies, failing a stalled download after ~5 minutes.

</details>

🔴 If the engine dies mid-run, the local output file gets error rows for every remaining request. Resuming "past the last line written", as the new README says, then silently skips all of them. Each request whose handler raises the engine's dead_error is turned into an error response by run_request, and run_and_write writes it at line 971. The `engine_client.errored` check at run_batch.py:1059 runs only after the whole batch has been dispatched. Fix: stop the run as soon as the engine is dead, so the output holds only responses produced while it was alive. For example, check `engine_client.errored` before writing each response and raise `dead_error`.

<details>
<summary>Why this was flagged</summary>

Trigger: the engine core crashes (OOM, CUDA error) partway through `vllm run-batch -o results.jsonl`. The nonzero exit code does not help here: it says the run failed, not which rows are real. On the base branch every row was also written as an error, but the base never documented prefix-resume, and this PR's stated claim is that a failed run leaves only a prefix of responses.

**Verification:** Trigger: the engine core dies partway through `vllm run-batch -o results.jsonl`. run_request (run_batch.py:610-613) catches every Exception with `response = create_error_response(e)`, and each error row is written at lines 971-975.
