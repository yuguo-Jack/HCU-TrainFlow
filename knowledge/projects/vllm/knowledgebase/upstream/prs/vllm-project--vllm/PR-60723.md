# [Frontend] Accept each connection on the least loaded API worker

[Upstream PR](https://github.com/vllm-project/vllm/pull/60723) · state: closed · merged: True

## Original PR description



## Overview

With `--api-server-count N > 1`, accept each new connection on the API worker with the fewest open connections, so requests are spread evenly across workers. Part of RFC #57479. This is an alternative to #58278 (SO_REUSEPORT listeners, and the accept-pacing rewrite on that branch) and builds on its accept loop.

## Claims

- Connections are spread evenly across API workers in bursts, when they arrive one at a time, and under overload. On main, one worker often takes most of a burst.
- RL `pause(mode="abort")` on GB200, DP2, 8 API servers: abort → all response bodies received goes from **40.0 s on main to 21.5 s** (Ao's accept pacing: 26.6 s; SO_REUSEPORT: 29.8 s).
- Ordinary serving with many short requests (Qwen3-0.6B, output length 1): **+43–85% requests/s** and lower TTFT than main, because on main a client's keep-alive pool lands on a few workers.
- A single API server is unchanged, and no new flags are added.

## Details

**Root cause.** All API workers inherit one listening socket. The event loop's own server accepts every queued connection on each wakeup, so whichever worker wakes first takes the whole burst. Connections that arrive one at a time tend to go to the most recently active worker.

**Design.**
- `APIServerProcessManager` shares one `RawArray("i")` slot per worker. This is the same mechanism as the existing `mp_admission_counters`.
- Each worker serves the shared socket with its own accept loop, instead of starting an asyncio server through uvicorn.
- When the socket becomes readable, a worker refreshes its own open-connection count and accepts only if it is the least loaded.
- Otherwise it rechecks every 1 ms, up to 5 times, then accepts anyway. That way a least-loaded worker that is blocked mid-render can't stall new connections.
- Accepted sockets go through uvicorn's own protocol via `loop.connect_accepted_socket`, each in its own task, so TLS handshakes don't hold up the accept loop. On shutdown, pending accepts and handshakes are cancelled; uvicorn already drains open connections.
- Slots start at INT32_MAX, so a worker that hasn't started is never chosen.

**Why not #58278.**
- SO_REUSEPORT gives each worker its own listener, and the kernel assigns connections by hash. That's random, and it clumps: about 25% over the fair share in bursts, and the 29.8 s tail above.
- Accept pacing (accept one connection, then pause 1 ms) balances bursts. With staggered arrivals the same worker keeps getting woken first, so some workers get no connections (99–146 on one worker against a fair share of 64 in the overloaded CPU case).

**Trade-offs.**
- Balancing has a cost: when every worker is busy rendering, short requests such as `/health` wait behind a render on whichever worker accepts them. In a mixed benchmark (the ~60% CPU case above plus `/health` polled at 100/s), `/health` p99 is about 50–100 ms with this PR, against under 1 ms with main or accept pacing, which leave some workers idle. SO_REUSEPORT is 0.6–1.9 s. When the CPU is overloaded, every balanced scheme sits around 1.5 s. A 20 ms recheck window doubled this cost for little extra balance, which is why the window is 5 ms. Faster rendering reduces both sides of this trade-off.
- It balances connections, not requests: a keep-alive client stays on its worker, as with any accept-level scheme.
- Every idle worker still wakes for each new connection, as on main.

- njhill · comment · 2026-10-08T22:58:23Z · [source](https://github.com/vllm-project/vllm/pull/60723#discussion_r4224986705)

File: `vllm/entrypoints/launchers/launcher.py` · line 87

If lifespan startup fails, `uvicorn.Server.startup()` returns early with `should_exit=True` and `started=False`, but this override carries on: it publishes a load of 0 (making this worker the most attractive target for peers), calls `listen()`, and starts the `_accept` tasks. `_serve()` then skips both `main_loop()` and `shutdown()` (the latter is gated on `self.started`), so nothing ever cancels those tasks and the worker keeps accepting connections onto an app that failed to start.

Suggest bailing out here:

```suggestion
        await super().startup(sockets=[])
        if not self.started:
            return
```

- njhill · comment · 2026-10-08T22:58:23Z · [source](https://github.com/vllm-project/vllm/pull/60723#discussion_r4224986715)

File: `vllm/entrypoints/launchers/launcher.py` · line 158

The accept tasks are cancelled but not awaited, and `super().shutdown()` closes the listening socket synchronously (before its first `await`). So the cancellation is only delivered afterwards, and `_readable`'s `finally: loop.remove_reader(sock)` runs against an already-closed socket. uvloop tolerates this (its io-ref on the socket defers the real close), and stdlib asyncio only gets by via the selector's exhaustive-search fallback, with the closed fd still registered in the meantime.

Suggest awaiting the cancelled tasks before handing off, e.g.:

```python
        tasks = list(self._accept_tasks)
        for task in tasks:
            task.cancel()
        await asyncio.gather(*tasks, return_exceptions=True)
        await super().shutdown(sockets)
```

Related nit: the slot in `peer_loads` is never reset on shutdown, so a stopped worker keeps advertising its last count. Setting it back to `2**31 - 1` here would match the "not started" sentinel.
