# [Bugfix][Kernel] NVFP4 KV cache: fix block_size/layout detection for physically shaped HND caches

[Upstream PR](https://github.com/vllm-project/vllm/pull/53681) · state: open · merged: False

## Original PR description

## Overview

Fix `reshape_and_cache_flash` for NVFP4 KV caches passed in their physical HND shape: the kernel read `block_size` from the wrong dim and inverted its layout detection, silently corrupting the cache whenever `num_heads % 4 == 0`. FIX #49012.

## Claims

- The NVFP4 cache-write kernel (`csrc/nvfp4_kv_cache_kernels.cu`) now handles the physically shaped HND cache `[num_blocks, num_heads, block_size, dim]` that runtime callers (the FlashInfer backend) allocate, as well as the logical `[num_blocks, block_size, num_heads, dim]` view the existing tests pass.
- A shape that is neither is now a loud error instead of silent corruption.
- A regression test drives the kernel exactly as a runtime HND caller does and fails on `main`.

## Validation

Rebased build on `main` @ 3ddc6702a, torch 2.14.0+cu130, RTX 5090 (SM120), `_C_stable_libtorch` rebuilt from source with and without the kernel change:

| kernel | `test_reshape_and_cache_nvfp4_physical_hnd_shape` (new) | `test_nvfp4_4over6_selects_lower_error_scale` |
| --- | --- | --- |
| `main` (unfixed) | **fails** (`assert_close` on the dequantised cache) | — |
| this PR | passes | passes |

Reproduce:

```
pytest tests/kernels/attention/test_cache.py -k nvfp4
```

The existing parametrized `test_reshape_and_cache_flash[...nvfp4...]` cases only exercise the logical view and cannot hit this bug. On the SM120 card used here they fail identically with and without this patch, on the value half only: since #55908 the test expects linear V scales on `is_device_capability_family(120)` (the layout the SM12x FlashInfer readers consume) while the kernel still writes them 4x4-swizzled on every architecture. That is the open writer-layout bug #50084, with fixes proposed in #55976 and #56550; this PR does not touch the scale layout and is independent of it. The nvfp4 cases require compute capability >= 10.0 and are skipped on pre-Blackwell CI runners.

## Details

Root cause: the kernel read `block_size = key_cache.size(1)` and probed the physical layout with hard-coded dims (`stride(2) > stride(1)`). Both only hold for the logical view. With the physically shaped HND cache the kernel misreads `num_heads` as `block_size` and inverts the layout detection; the only downstream check is `block_size % 4 == 0`, which every common head count passes, so the cache is written to the wrong positions with no error (garbage decode output, as the issue reports).

Fix:

- Disambiguate the head/block dims at the kernel entry using `num_heads` from `key`; keep the logical-view interpretation when the shape is ambiguous (`size(1) == size(2)`, both dims agree on `block_size`); check the shape and raise otherwise.
- Make the stride-based HND/NHD detection follow the disambiguated dims instead of hard-coded dim indices.
- Regression test: `num_heads=8` hits the former silent-corruption path (`8 % 4 == 0`), `block_size=16` keeps the shape unambiguous.

Scope: the reporter hit this via `VLLM_KV_CACHE_LAYOUT=HND` while prototyping nvfp4-KV on SM120 (#49011). On current `main` the serving paths reach this kernel differently from when the issue was filed: since #46963 the SM8x / SM12x (and SM90, #60620) NVFP4 caches are written by FlashInfer's `nvfp4_quantize_append_paged_kv_cache_with_slot_mapping` and never call this op; the SM100 trtllm-gen path still calls it, with the logical `(B, N, H, dim)` view that the kernel already handled. So this PR hardens the exported `reshape_and_cache_flash` op (and `nvfp4_4over6`) against the physically shaped HND cache the issue's caller passed, and turns the remaining ambiguous shape into a loud error; it does not change any current serving output. Verification is at the op level, under the conditions the report describes.

History: rebased onto current `main` on 2026-10-16. The earlier test-utility change in this PR (dequantising V scales in the layout the kernel writes) was superseded by #55908 and dropped; the kernel file moved in #60721 and the patch follows it.
