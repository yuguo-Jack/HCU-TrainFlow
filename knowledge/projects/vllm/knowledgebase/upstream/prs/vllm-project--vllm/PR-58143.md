# [Bugfix] Preserve padding token types for cross encoders

[Upstream PR](https://github.com/vllm-project/vllm/pull/58143) · state: closed · merged: True

## Original PR description

## Purpose

Fixes #58138.

`padding="max_length"` currently extends `token_type_ids` with the last real token's type, so right-padded BERT pairs assign type 1 to padding even when the tokenizer's `pad_token_type_id` is 0. The existing scalar compression also cannot represent the correct `0*1*0*` shape.

This change:

- pads with `tokenizer.pad_token_type_id`;
- compresses token types as the document segment's half-open `(start, end)` range;
- reconstructs that range in both pooling worker paths; and
- adds regressions for padded pairs and invalid disjoint type-1 ranges.

Unpadded `0*1*` inputs retain the same reconstructed token types.

AI assistance was used for implementation and validation.

## Test Result

The source-level reproducer showed the bug before the change:

```text
actual=[0, 0, 0, 1, 1, 1, 1, 1]
expected=[0, 0, 0, 1, 1, 0, 0, 0]
compressed=3
```

After the change:

```text
actual=[0, 0, 0, 1, 1, 0, 0, 0]
expected=[0, 0, 0, 1, 1, 0, 0, 0]
compressed=(3, 5)
reconstructed=[0, 0, 0, 1, 1, 0, 0, 0]
```

The targeted tests pass: `4 passed`. Ruff check and format check pass on the touched files. `UP038` is ignored because `gpu_model_runner.py` has five pre-existing findings outside this diff.

## Real BERT cross-encoder comparison (H200, 2026-10-13)

Executed the actual Python source from main `816173ca9d9256f85c36d09d133a7ed219ccbd8e` and PR branch `13a08eb29f8d3ffd32ecc98aa24a31e715a8504b`, using the same isolated runtime and three query/document pairs. The fixed checkpoint is `cross-encoder/ms-marco-MiniLM-L-6-v2`, revision `233902d25c440f23af6f7d6e94d2946bac0bee0a`, architecture `BertForSequenceClassification`.

Configuration: H200, FP16 model weights, raw logits (`PoolingParams(use_activation=False)`), eager execution, TP=1, and `attention_config={"backend": "FLASH_ATTN", "flash_attn_version": 2}`.

### Matching padding and masking

HF tokenization used `padding="max_length", max_length=128` for the padded case. vLLM used `tokenization_kwargs={"pad_prompt_tokens": 128}` and produced the same right-padded 128 input IDs on main and branch. Unpadded input lengths were 17, 22, and 18; all six main/branch ID arrays matched exactly.

`pad_prompt_tokens` supplies padding IDs as visible sequence positions in this vLLM path. Therefore the matching padded HF reference explicitly uses an all-ones attention mask and the tokenizer's padding token type 0. This is not conflated with standard HF masked padding. No production attention-mask behavior was changed.

| 2 | unpadded | 7.329526 | 7.329526 | 7.328125 |
| 3 | unpadded | -7.128927 | -7.128927 | -7.128906 |
| 1 | padded to 128 | 7.273251 | 3.266776 | 3.265625 |
| 2 | padded to 128 | 7.249307 | 4.620015 | 4.621094 |
| 3 | padded to 128 | -8.581070 | -3.295383 | -3.294922 |

Unpadded main-versus-branch maximum absolute difference: `0`. Unpadded branch-versus-HF maximum absolute difference: `0.001400948`.

Padded main-versus-HF maximum absolute difference: `5.286148071`; padded branch-versus-HF: `0.001150846`. These are observed numerical differences, not a substituted or loosened test assertion.

As a separate mask control, standard HF masked padding returns `9.265625`, `7.328125`, and `-7.12890625`, matching its unpadded scores. Those masked-padding scores are not claimed to match vLLM's visible-padding requests.

### Runtime and validation boundary

Both source checkouts ran with PyTorch `2.11.0+cu130`, Transformers `5.19.0`, humming `0.1.16`, actual CuTe DSL `4.8.0`, and matching FlashInfer Python/cubin `0.7.0.post1`. No mocks or disabled FlashInfer version checks were used.

The existing vLLM `0.25.1` native extensions were reused for both Python checkouts. This is an actual H200 source-level model comparison, not a fresh build of all native extensions or validation of the main branch's declared PyTorch 2.13 dependency matrix. HF goldens were obtained with the same PyTorch/Transformers versions and fixed checkpoint.

AI assistance was used for environment preparation, execution, and reporting.
