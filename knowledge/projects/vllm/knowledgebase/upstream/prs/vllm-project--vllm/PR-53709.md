# [Model][Quant] DeepSeek-V4: opt-in MXFP4→block-FP8 expert dequant (Hopper prefill speedup)

[Upstream PR](https://github.com/vllm-project/vllm/pull/53709) · state: closed · merged: False

## Original PR description

**Update (Oct 27): rebased onto current main (incl. #61875's MoE dispatch), and a fail-closed exactness contract was added in response to review feedback below.** The conversion now *rejects* input it cannot encode exactly instead of assuming exactness: invalid e8m0 scales (0xFF) fail the load, and per-value representability is verified against a per-e2m1-code exponent-spread bound (the byte-110 underflow and byte-255 cases from @AranKomat's review now raise, before any layer parameter is replaced). The exactness claim is therefore **exact for inputs accepted by the load-time check**, not unconditional. Verification counters are aggregated on device with a single host sync per converted tensor, keeping the load-time cost off the hot path.

## Purpose / positioning after #61875

Since this PR was opened, #61875 landed a native SM90 route for the same checkpoints: `Mxfp4MoEMethod(activation_key=kMxfp8Dynamic)` + Humming W4A8 kernels (4-bit storage kept, decode-heavy focused). On stacks with humming-kernels ≥0.1.18 that path is the strictly better choice (no 2× expert memory).

This PR covers the remaining gap: **weight-dequant → block-FP8 runs on the existing block-FP8 MoE kernel**, no humming-kernels dependency, and targets prefill/TTFT rather than decode — measured single-request TTFT prefill throughput 1.38–1.53× over Marlin W4A16 at 2k–8k input (H20, TP=4, numbers below unchanged). It is opt-in (`VLLM_DSV4_FP4_DEQUANT=1`, default off, Marlin untouched) and fail-closed at load. If maintainers prefer to consolidate on the W4A8 direction and drop this, no objection — happy to pivot. The platform-independent fail-closed conversion contract and its tests may still be independently useful.

## Measured evidence (unchanged from original post)

- End-to-end prefill (single request, TTFT, unique prompts, TP=4, H20):
  | input len | Marlin W4A16 (default) | dequant→FP8 | speedup |
  |---|---|---|---|
  | 2048 | 7020 tok/s | 10752 tok/s | 1.53× |
  | 4096 | 8129 tok/s | 11882 tok/s | 1.46× |
  | 8192 | 8396 tok/s | 11623 tok/s | 1.38× |
- GSM8K (full 1319, 8-shot, greedy, H20, TP=4): Marlin 94.47% vs dequant→FP8 w8a8 93.93% (Δ −0.54pp, within run-to-run noise at this n). Re-encoded expert *weights* are exact for inputs accepted by the load-time check; the only added quantization is w8a8 activations.

## Changes

- `vllm/envs.py`: `VLLM_DSV4_FP4_DEQUANT` (default off).
- `vllm/models/deepseek_v4/fp4_dequant.py`: `cast_mxfp4_to_fp8_block` (fails closed on inexact input) + `DsV4Fp4DequantMoEMethod(Fp8MoEMethod)` (MXFP4 create_weights → validated re-encode → FP8 kernel).
- `vllm/models/deepseek_v4/quant_config.py`: opt-in routing ahead of the `Mxfp4MoEMethod(activation_key=kMxfp8Dynamic)` dispatch.
- `tests/quantization/test_dsv4_fp4_dequant.py`: exactness over sampled shapes/spreads, byte-110 underflow, byte-255 non-finite scale, per-value spread boundary (14/15/17), extreme-spread rejection, and no-partial-parameter-replacement on failure. (New rejection tests to be exercised on the next CI/H20 run.)

Additional throughput A/B on Hopper for this opt-in path (H20, TP=4, `DeepSeek-V4-Flash-0731`, `--max-model-len 524288`, `--kv-cache-dtype fp8`, 32 concurrent requests, 0% prefix-cache hit). ### Decode (1-token input, forced N-token output via `ignore_eos`, 32 concurrent)

| output len | default (Marlin W4A16) | this PR (dequant->FP8) | speedup |
|---|---|---|---|
| 2k  | 1,642 tok/s | 1,856 tok/s | 1.13x |
| 10k | 1,637 tok/s | 1,841 tok/s | 1.12x |

Per-request ~51 -> ~58 tok/s. Both engines are fully batched (`Running: 32`), and decode rate is independent of output length. So the FP8-tensor-core expert path also helps decode (~1.13x), not just prefill.

### Prefill (unique random prompts, `max_tokens=1`, 32 concurrent)

| input len | default (Marlin W4A16) | this PR (dequant->FP8) | speedup |
|---|---|---|---|
| 8k  | 6,545 tok/s | 13,335 tok/s | 2.04x |
| 64k | 8,242 tok/s | 11,370 tok/s | 1.38x |

The prefill speedup narrows as context grows (attention increasingly dominates over the MoE GEMM), but stays positive.

### Trade-off (unchanged)

FP8 experts use 2x the weight memory vs MXFP4, which lowers KV capacity: at this config per-GPU available KV cache is 83.9 GiB (Marlin) -> 53.7 GiB (this PR), i.e. GPU KV cache size 5.70M -> 3.65M tokens. Accuracy is unaffected (GSM8K 1319-item parity, 94.47% vs 93.93%, within noise), as noted in the PR body.

### How to use

Opt-in via the `VLLM_DSV4_FP4_DEQUANT=1` env var (default off; without it the model runs the usual MXFP4/Marlin path). Example on Hopper:

```bash
VLLM_DSV4_FP4_DEQUANT=1 \
vllm serve deepseek-ai/DeepSeek-V4-Flash-0731 \
  --tensor-parallel-size 4 \
  --kv-cache-dtype fp8 \
  --max-model-len 524288 \
  --gpu-memory-utilization 0.90
```

To go back to the default (MXFP4/Marlin W4A16), just unset the variable. On startup the worker log shows the FP8 path is active: `Using TRITON Fp8 MoE backend` and the MoE running as `fp8_w8a8` block `[128, 128]`.

- AranKomat · comment · 2026-09-14T13:41:54Z · [source](https://github.com/vllm-project/vllm/pull/53709#issuecomment-5664921646)

Follow-up from the AMD/TP8 review against `b575b5fc05d65a809c68cf3137ac925b3fb30294`.

### 1. Existing ROCm normalization should be reused

`Fp8MoEMethod.process_weights_after_loading` already performs FN-to-FNUZ normalization and scale compensation. I verified that tensor arithmetic against the re-encoded values on CPU, so an additional byte reinterpretation in this loader would be unnecessary.

### 2. The current MXFP4 conversion is not unconditionally lossless

This limitation is platform-independent.

A 128x128 matrix of packed `0x11` weights, with microscale byte 127 except for one group at byte 110, contains `2^-18` values that the current conversion rounds to zero. Microscale byte 255 also produces non-finite values without rejection.

These are synthetic contract counterexamples, not evidence that a released checkpoint contains either case. The existing exactness test samples scale bytes 119..127, so it does not exercise these boundaries.

I have a local fail-closed reconstruction check plus a 128-aligned allocation extension for 288-wide TP shards. The allocation change uses the packed loader's existing separate gate/up halves and unpadded rank offsets; it does not change global `expert_dtype` or dense UE8M0 scales.

Initial local status:
- 13 CPU source-contract cases pass.
- Both new rejection cases fail against the parent implementation as expected.
- These tests exercise extracted tensor/loader logic only. They do not establish native loading, ROCm execution, clamp correctness, or model quality.

### 3. Native gfx942 loader qualification

A later native pass reached 36 actual-import CPU/GPU tests across all eight TP offsets and the conversion/normalization cases.

That exposed an ordering constraint: `Fp8MoEMethod` chooses/refines its backend before the later dimension-rounding hook. A local width of 288 therefore selects an unsupported 32x32 block scheme unless the method's copied config is 128-aligned before backend selection.

Keeping checkpoint metadata unpadded while changing that internal ordering passes native allocation and FN/FNUZ post-load checks for eight synthetic experts. The observed extra allocation cost was roughly 1.8-2.4 s and 122-123 MiB peak HBM in this synthetic test, not a full-checkpoint measurement.

The loaded expert was not yet qualified at this point: M=1 failed the independent positive-clamp oracle, and the selected two-stage CK SiLU path exposes no stage-1 clamp argument. I did not treat this as evidence about split-K or other arithmetic, and no model startup or serving claim followed.

### 4. Native layer compute qualification

A subsequent guarded Triton fallback passed the native layer compute gate.

Two changes were required:

1. Preserve the requested FP8 backend while giving the temporary MXFP4 allocation helper its own `auto` backend.
2. Exclude clamp-active inputs from the existing unclamped SiLU/block128-FP8 shortcut, matching the guard already discussed in #53875.

With those changes, 40 actual-import CPU/GPU tests pass. Real packed allocation/post-loading and clamped M=1/8/16 forwards pass the unchanged independent FP32 oracle, along with three changed-route graph replays per size. Eager NRMSE was 0.059519 / 0.051727 / 0.055704. M=1 is close to the 0.06 bound, so this is still not a substitute for full checkpoint/model validation.

A four-arm diagnostic also separated two CK issues: the M=1 split-K defect and ignored positive clamp are distinct. Disabling split-K repairs only the unclamped case. We are not claiming a CK fix.

### Scope

All of the above is local candidate work with packaged vLLM / Torch / ROCm dependencies. It is **not** a test of this entire PR head or current main, and there is still no endpoint speedup claim.

The extension remains local pending human review, coordination on the base PR, full-checkpoint coverage, and paired model testing. I will not open a duplicate loader PR while this work is being coordinated here.

Thanks for the careful counterexamples and for keeping the ROCm work coordinated here. I confirmed both issues against `b575b5fc`.

The current unconditional **lossless** wording is too broad:

- With a block maximum scale byte of 127, byte 110 gives `s = 2^-17`. For an E2M1 value of 0.5, the value presented to E4M3FN is `0.5 * 64 * 2^-17 = 2^-12`, below E4M3FN's minimum positive subnormal (`2^-9`). It therefore rounds to zero even though the decoded source value is `2^-18`.
- Scale byte 255 propagates a non-finite value through `amax` and the block scale, and the current conversion does not reject it.

The existing exactness test samples scale bytes only in `119..127`, so it proves exactness for that sampled range, not for arbitrary MXFP4 scales. Likewise, the successful DeepSeek-V4-Flash-0731 load and model evaluations are useful corruption/non-inferiority checks, but they are not an exhaustive load-time reconstruction check. I therefore cannot claim from the current evidence that every tensor in the released checkpoint satisfies an unconditional exactness contract. Conversely, the synthetic cases do not show that the released checkpoint actually contains such values.

I agree this should fail closed before retaining any lossless claim. The fix I intend for this PR is to:

1. reject invalid/non-finite E8M0 scales before conversion;

3. add targeted tests for the byte-110 underflow and byte-255 cases, plus the exactness boundary; and
4. narrow the wording to **lossless for inputs accepted by the load-time exactness check**.

The validation can be aggregated on device and checked once per converted tensor/layer so that it does not add a host synchronization per expert. Until a full checkpoint scan reports zero mismatches, I will keep the released-checkpoint claim limited to the serving/evaluation evidence already reported.
