# [Bugfix] Unify per-layer KV cache dtype selection across v1/v2 model runners

[Upstream PR](https://github.com/vllm-project/vllm/pull/47618) · state: open · merged: False

## Original PR description

Edit:
The main issues has been resolved in #47609 and #47716 . This PR now just make the two fix in sync for both v1 and v2 runner.

## Purpose

  1. DeepSeek V4 Flash on SM121: `Expected packed SM120 DSV4 swa_kv_cache head dim 584, got 512` (reported in #42890 comments)

  **Root cause:** #42890 passes `"auto"` to `get_kv_cache_shape()` when `spec.kv_quant_mode == NONE` (so skipped layers get the unquantized shape). But specs whose layout is encoded in the dtype **string** (`fp8_ds_mla`, `turboquant_*`) also have `kv_quant_mode == NONE`, so they wrongly received `"auto"`.

  **Fix:** trust `spec.cache_dtype_str` when present (already on the MLA specs from #40860), falling back to the skip-layer heuristic otherwise. Adds the field to
  `TQFullAttentionSpec` and sets it at construction. No behavior change for other configs.

  Not duplicating an existing PR: #47604 is a revert, not a fix; no other forward-fix is open.

  ## Test Plan

  - Repro script driving the real `_reshape_kv_cache()` with real DSV4-SWA / TurboQuant specs, run before and after the fix.
  - E2E of the #42890 feature: gpt-oss-20b, `kv_cache_dtype=nvfp4` + `kv_cache_dtype_skip_layers=["sliding_window"]`, FlashInfer, both v1/v2 model runners.
  - `ruff check` on touched files.

  ## Test Result

  - Before: Case A last dim **512** (FlashInfer expects 584); Case B raises `Unknown TurboQuant cache dtype: 'auto'`.
  - After: Case A → `(4, 64, 584)` ✅; Case B → `(4, 16, 8, 134)` (TQ slot layout) ✅. Verified fail→pass both directions via stash/pop.
  - E2E: both runners exit 0, coherent 2048-token greedy output, byte-identical v1 vs v2. Ruff clean.
  - Caveat: DSV4/SM121 verified at reshape-unit level (no SM121 hardware); would appreciate confirmation from the original reporter.

- rikki · comment · 2026-07-06T09:46:39Z · [source](https://github.com/vllm-project/vllm/pull/47618#issuecomment-4891369821)

Another confirmation here — this PR's fix also resolves the GLM-5.2 MLA **main attention layer** path (not just DSV4 SWA / TurboQuant), which hits the same root cause from the opposite direction.

(Not a precision/accuracy report — the NVFP4 weight-only path on SM90 via Marlin is working as intended. This is a KV cache reshape crash that fires before any inference, independent of weight quantization; FP8 checkpoints hit it too.)

**Repro:**
- Model: `nvidia/GLM-5.2-NVFP4` (`GlmMoeDsaForCausalLM`, deepseek_v2 code path)
- Hardware: 8× H200 (SM90), single node, TP=8, EP=8
- Flags: `--kv-cache-dtype fp8` (also reproduces with `--kv-cache-dtype fp8_ds_mla`), `--attention-backend` left at auto → `FLASHMLA_SPARSE` selected
- Image: `vllm/vllm-openai:nightly` @ `69715823df89` (07-06 nightly, contains #42890)

**Error** during `profile_cudagraph_memory` → `_init_minimal_kv_cache_for_profiling` → `_reshape_kv_cache_tensors`:

```
RuntimeError: shape '[192, 64, 576]' is invalid for input of size 8060928
  File ".../vllm/v1/worker/gpu/attn_utils.py", line 248, in _reshape_attention_kv_cache
    kv_cache = kv_raw_tensor.view(dtype).view(permuted_kv_cache_shape)
```

**Arithmetic:** `192 × 64 × 576 = 7,077,888` (expected by reshape), but the raw tensor is `8,060,928 = 192 × 64 × 656`. The 80-element-per-token delta is exactly the FP8 ds_mla scale padding (576 KV + 80 scale = 656, per `flashmla_sparse.py:65-87`).

**Mechanism (same as the DSV4 SWA case eugr described, but on the MLA main layer):**

`MLAAttention.get_kv_cache_spec` (`mla_attention.py:1004-1010`) creates `MLAAttentionSpec` with `cache_dtype_str="fp8_ds_mla"` (canonicalized by `_canonicalize_sparse_mla_kv_cache_dtype` at `__init__` time, which also rewrites `cache_config.cache_dtype`), but **does not set `kv_quant_mode`** → defaults to `KVQuantMode.NONE`.

On the allocation side, `MLAAttentionSpec.real_page_size_bytes` (`kv_cache_interface.py:381-388`) reads `cache_dtype_str == "fp8_ds_mla"` → returns `block_size * 656`, so the raw tensor is sized for 656/token.

On the reshape side, #42890's `layer_cache_dtype_str = "auto" if kv_quant_mode == NONE else ...` collapses to `"auto"` (because `kv_quant_mode == NONE`), so `FlashMLASparseBackend.get_kv_cache_shape(cache_dtype_str="auto")` (`flashmla_sparse.py:140-144`) takes the `else` branch and returns `(num_blocks, block_size, head_size=576)`. Hence the 576-vs-656 view failure.

**This PR's fix addresses it correctly:** trusting `spec.cache_dtype_str` first (which is `"fp8_ds_mla"` on the MLA spec) makes `get_kv_cache_shape` take the 656 branch, matching the physical allocation. Verified by reading the diff against `mla_attention.py:1004` + `kv_cache_interface.py:381` + `flashmla_sparse.py:140`.

I haven't been able to run the patch end-to-end on H200 yet (k8s deployment, would need a custom image build); reporting now in case it helps expand the verified coverage beyond DSV4-SWA / TurboQuant. Happy to test a build if that's useful.

**Related:** the mnnvl issue (#47219 / #47284) is independent and still needs `VLLM_FLASHINFER_ALLREDUCE_BACKEND=trtllm` on single-node H200 without NVSwitch multicast — but once that's worked around, this reshape bug is the next blocker.
