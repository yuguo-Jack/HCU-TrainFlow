# [Bugfix][Core] Unblock scheduling after a failed async KV load

[Upstream PR](https://github.com/vllm-project/vllm/pull/59901) · state: open · merged: False

## Original PR description



## Overview

With `kv_load_failure_policy="recompute"`, a request whose async KV load fails with no usable prefix can sit in WAITING forever, even on an idle engine, and the requests queued behind it never run. Nothing errors. It takes a connector that offers the same async load again on the retry, e.g. MooncakeStoreConnector (async by default) or a MultiConnector whose offloading child holds the prefix after NIXL fails.

Related: #59096, #59099, #59102, #59325, #59329 (independent fixes in nearby KV load paths).

## Claims

- The failed request is admitted again once its load fits.
- Requests holding loaded blocks are no longer stuck behind it.
- No change when the failed load keeps a valid prefix.

## Details

After the failure, `_update_waiting_for_remote_kv` frees the request's blocks ([scheduler.py:3097](https://github.com/vllm-project/vllm/blob/84bcbc62644356270aaaa5e2d0237d03adc9bb3a/vllm/v1/core/sched/scheduler.py#L3097)) but leaves it in `_inflight_prefills` and `kv_holding_waiting`.

- Async admission reserves the remaining blocks of every in-flight prefill (#44560, [scheduler.py:1214](https://github.com/vllm-project/vllm/blob/84bcbc62644356270aaaa5e2d0237d03adc9bb3a/vllm/v1/core/sched/scheduler.py#L1214-L1217)). Holding nothing, the request now reserves its whole sequence against its own retry, so the gate ([kv_cache_manager.py:575](https://github.com/vllm-project/vllm/blob/84bcbc62644356270aaaa5e2d0237d03adc9bb3a/vllm/v1/core/kv_cache_manager.py#L575-L579)) needs room for the load plus its full size. In the test: 10 usable blocks, a 6-block prompt, a 5-block hit, and 10 - 6 < 5 on every step.
- `kv_holding_waiting` is drained first so that a block holder never waits behind a request whose failed allocation stops the scan (#58947). The freed request is exactly that request.

The fix discards it from `_inflight_prefills` when its blocks are freed, as preemption does, and moves a request that no longer holds blocks (by `_holds_kv_blocks`, which the queues already route by) from `kv_holding_waiting` to the front of `waiting` before scheduling it. The reservation itself is unchanged.

Not a duplicate: no open PR changes these lines on current main. #55297 makes MooncakeStore's next lookup a miss after an invalid-block failure; it is complementary and leaves the scheduler state, `failed_recving` and other connectors as they are. #57418 and #59343 use the reservation without touching this path; #53298, #54733 and #56733 handle sync or hybrid failures, and #59603 forwards failed loads to LMCache's scheduler side.

- sohom-cs · comment · 2026-10-28T02:58:44Z · [source](https://github.com/vllm-project/vllm/pull/59901#discussion_r4396456614)

File: `vllm/v1/core/sched/scheduler.py` · line 1089

It asks the connector again. After the free, num_computed_tokens is 0, so the request is admitted like a new one and calls `get_num_new_matched_tokens` ([scheduler.py#L947-L969](https://github.com/vllm-project/vllm/blob/b46b98a1145d14cb6c490ea4ca156dbb9e073aba/vllm/v1/core/sched/scheduler.py#L947-L969)); a failure that kept a valid prefix skips that lookup and recomputes locally from the first bad block. For a NIXL remote prefill the retry is a local recompute, because `do_remote_prefill` is cleared after the first transfer ([pull_scheduler.py#L187-L189](https://github.com/vllm-project/vllm/blob/b46b98a1145d14cb6c490ea4ca156dbb9e073aba/vllm/distributed/kv_transfer/kv_connector/v1/nixl/pull_scheduler.py#L187-L189)). You're right that a connector that offers the same hit again, like MooncakeStore, can loop on a persistent failure, but that loop is on main too whenever the retry fits in the cache (for a failed async load nothing makes the next lookup miss, so main re-admits the request every cycle too); this PR only removes the case where the retry is never admitted and blocks the requests behind it. I think the loop fix belongs in the connector: #55297 adds an `on_load_failure` hook so the next lookup misses, though today it is only called from the invalid-block path, so `failed_recving` would need the same call.
