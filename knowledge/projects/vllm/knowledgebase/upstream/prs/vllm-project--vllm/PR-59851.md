# [Core] Add startup snapshot capture to ordinary serving

[Upstream PR](https://github.com/vllm-project/vllm/pull/59851) · state: open · merged: False

## Original PR description

## Overview

Allow ordinary `vllm serve` to prepare an initialized engine for external capture, then activate the original process or a restored copy through the normal OpenAI-compatible server. This gives capture systems a path through the standard serving entrypoint, including its authentication and routes.

Depends on #59832 and builds on #51360. This draft targets upstream `main`, so the PR includes the two foundation commits from #59832. The ordinary-serving follow-up is commit `9027bd5190`; its [incremental diff](https://github.com/matteso1/vllm/compare/14903f61d1aa80f6b52b93ba9e866a4e21b0ff7d...9027bd5190dcbba226282ab6891aa1d38840bc05) changes eight files. Related design: #54940.

## Claims

- Add opt-in startup capture to the ordinary Python launcher. The engine remains private and its public socket unbound until recovery and a private generation check complete; normal application construction follows.
- Reuse the shared snapshot session through a file adapter with explicit donor/copy activation, native-completion acknowledgement and a fresh challenge. Stale/invalid control and partial recovery failure terminate the startup instance with phase/error diagnostics.
- On the recorded single-GPU fixture, both model runners serve correctly from the continuing donor and two sequential restores after donor shutdown, including authenticated, concurrent and streaming requests.

## Details

The initial profile is one local CUDA rank, one Python frontend and a dense unquantized generation model using the existing compact release/reload policy. Unsupported launchers, topology and model/loading combinations fail before worker construction. The default serving path keeps its existing startup ordering.

The opt-in configuration is `--snapshot-config '{"mode":"startup","control_dir":"/absolute/private/empty/dir","timeout_s":300}'`. The new documentation describes the activation/challenge protocol and the capturer's filesystem, namespace and stdio obligations. Capture, storage, placement and native CUDA completion remain external. A `validated` control status means private recovery validation passed; ordinary HTTP probing establishes public readiness.

This is the ordinary-launcher follow-up to #59832. It adds startup capture before public traffic, while #54942/#54943/#54946 propose a broader externally coordinated lifecycle and HTTP control API; #52132 captures an engine subtree while retaining its frontend. The configuration schema here is proposed for review alongside #54940. There is no new live-server admission API or artifact manager. Public-provider integration, concurrent clones, TP2 and another-worker restoration remain separate qualification work.
