# [Perf][MRV2] Bound staged-write grid size for mixed-length batches

[Upstream PR](https://github.com/vllm-project/vllm/pull/63539) · state: open · merged: False

## Original PR description



## Overview

Follow-up to #62698. Bound the `_apply_write_kernel` launch grid so a single long staged write next to many short ones no longer launches `num_writes x max_chunks` mostly-idle programs, and have the kernel stride over chunks so any grid size is correct.

## Claims

- Mixed-length staged writes (e.g. a long prompt admitted alongside a full decode batch) are 2-4x faster than after #62698: 1x128K + 255x1 tokens goes 18.6 -> 5.7 us.
- No measurable change for decode, block-table, or single long writes up to 855K elements.
- The kernel no longer silently drops data if the launch undercounts chunks.

## Validation

**Kernel microbenchmark**, GB200, FlashInfer CUPTI with CUDA graph, int32, real `_apply_write_kernel` + grid code from each tree, outputs checked equal to a torch reference before timing. Two runs with the order of the versions swapped; the table shows run 1 / run 2 (us), `StagedWriteTensor.apply_write` path:

| writes | programs per write (#62698 -> this PR) | #62698 | this PR |
| --- | :---: | ---: | ---: |
| 256 x 1 (decode) | 1 -> 1 | 1.82 / 1.83 | 2.03 / 1.84 |
| 256 x 8 (block table) | 1 -> 1 | 2.01 / 2.04 | 2.24 / 2.04 |
| 1 x 128K | 128 -> 128 | 2.03 / 1.84 | 2.03 / 2.24 |
| 1 x 855K | 855 -> 855 | 2.45 / 2.62 | 2.65 / 2.65 |
| 8 x 128K | 128 -> 128 | 2.65 / 2.65 | 2.65 / 2.65 |
| 1 x 2M | 2048 -> 1024 | 3.26 / 3.27 | 3.64 / 3.68 |
| 1x128K + 63x1 | 128 -> 32 | 5.92 / 5.93 | 3.26 / 3.23 |
| 1x128K + 255x1 | 128 -> 8 | 18.62 / 18.69 | 6.12 / 5.72 |
| 1x855K + 255x8 | 855 -> 8 | 116.40 / 116.47 | 27.23 / 27.18 |

The `FusedStagedWriter` (multi-group) path shows the same pattern (18.8 -> 5.9 us and 116.5 -> 27.6 us for the two largest mixed cases). The CUPTI timer resolution is ~0.2 us, and small-case differences flip sign between runs.

An ablation also showed that an early return for programs past the end of a short write gives no benefit: the cost comes from the number of programs launched, not from their loads.

**Tests**: TODO, run `tests/kernels/core/test_uva.py` and `tests/v1/worker/test_gpu_block_table.py` on GPU.

No end-to-end serving benchmark yet. The target is the admission step described in #62698 (DEP decode with long prompts), where mixed-length writes occur.

## Details

- `_write_grid` uses `min(cdiv(max_len, 1024), 1024, 2048 // num_writes)` programs per write, at least 1. The caps are `_MAX_WRITE_PROGRAMS` and `_MAX_TOTAL_WRITE_PROGRAMS`.
- The tradeoff: in large batches, a long write gets fewer programs. 1x855K + 255x8 takes 27 us here vs 2.6 us for the 855K write alone, but 116 us in #62698. A larger total budget, or a flattened chunk grid driven by a host-built chunk-to-write table, could close more of that gap at the cost of more complexity.
- Writes over 1M elements (the 1024-program per-write cap) loop inside the kernel, costing ~0.4 us at 2M elements. This also keeps grid dim 1 below CUDA's 65535 limit.
