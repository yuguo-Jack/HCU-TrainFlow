# [Bugfix][LoRA] Preserve idle DP adapters and remap MoE slots

[Upstream PR](https://github.com/vllm-project/vllm/pull/63077) · state: open · merged: False

## Original PR description

## Overview

Preserve real LoRA adapters during idle DP forwards and resolve gathered MoE tokens against each receiver's adapter slots. This is the follow-up discussed with @almogtavor in #61453, building on #61714.

**Depends on #61714.** Its commit is retained as a separate prerequisite; the [follow-up-only diff](https://github.com/MagellaX/vllm/commit/faf4a54103bee17f479786226c551404427e93ef) is separate from its active-peer fix. Both commits are rebased onto main at `3fbc8d8b`; I'll drop the prerequisite commit after #61714 lands. This covers already-resident adapters, not a distributed loading/eviction protocol or #59819's slot-weight API.

**Overlap:** #63526 also addresses idle-adapter preservation. This PR additionally remaps gathered logical adapter IDs to receiver-local slots and covers opposite load orders in DP serving. The shared lifecycle changes need sequencing with #63526; they are not claimed as a separate missing fix. I can drop that part here after #63526 lands while retaining the remapping and its regressions.

## Claims

- First and repeated idle forwards no longer create zero-weight warmup adapters or remove real adapters. Profiling, warmup and capture keep their existing lifecycle.
- The naive DP/EP dispatch carries int64 adapter IDs, then remaps them to receiver-local slots on GPU. Different load orders no longer mix expert deltas; missing residency triggers a device-side assertion.
- Regression coverage includes both model runners, pinned/unpinned adapters, opposite slot orders, large IDs, stale padded metadata and CUDA graph replay.

## Details

Idle runtime forwards used the warmup adapter setup/cleanup path. An explicit idle flag now selects a local no-LoRA mapping without touching resident weights, shared by MRV1 and MRV2. MRV1 still has the same bug in supported deployments, so it needs the fix too.

Gathering sender-local slot indices is unsafe when ranks load the same adapters in different orders. Persistent GPU ID tables and a receiver-local remap preserve identities without adding a per-layer CPU collective or host readback. This adds metadata copies and GPU remapping; no throughput improvement is claimed.

All participating workers must already hold identical weights for each adapter ID, and `max_loras` must fit that resident set. The device assertion is a fail-closed check, not coordinated admission. Dynamic eviction, concurrent hot updates, multi-node deployments, EP serving, Blackwell TRT-LLM, AMD/XPU and a full external-launcher deployment were not validated. The source-selection rules wire the added regressions into the existing LoRA CI steps.
