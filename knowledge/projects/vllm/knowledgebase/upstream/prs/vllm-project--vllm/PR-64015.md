# [Bugfix][Frontend] Support min_tokens in Responses API

[Upstream PR](https://github.com/vllm-project/vllm/pull/64015) · state: open · merged: False

## Original PR description



## Overview

Add `min_tokens` support to the Responses API request path and forward it to `SamplingParams`. Fixes #64009.

## Claims

- `/v1/responses` accepts the vLLM-specific `min_tokens` request parameter.
- The value reaches engine sampling with the same default (`0`) used by the chat and completions protocols.
- A serving-path regression covers request parsing and validation, while a focused unit test covers the protocol-to-sampling mapping.

## Validation

- Baseline focused regression on `5314c582817faa57bc2fb0acdf05fdb6bbe97c3c`: failed because `sampling_params.min_tokens` remained `0` instead of the requested value. Current main `90309f6b742cdb1d6305778b81063918cf61be81` was separately inspected and still omits the field and forwarding.
- `.venv/bin/python -m pytest tests/entrypoints/openai/responses/test_sampling_params.py -q`: **11 passed**.
- `.venv/bin/python -m pytest --collect-only -q tests/entrypoints/openai/responses/test_simple.py::test_min_tokens_validation`: **1 test collected**.
- `.venv/bin/pre-commit run --files vllm/entrypoints/openai/responses/protocol.py tests/entrypoints/openai/responses/test_sampling_params.py tests/entrypoints/openai/responses/test_simple.py`: **passed**, including Ruff, mypy, CI test tethering, SPDX, and config validation.
- `git diff --check`: **passed**.

The serving-path test was also started locally, but the test server could not initialize because this CPU environment lacks the compiled `vllm._C_AVX2` / `torch.ops._C.init_cpu_memory_env` operation. The test is selected by the existing Responses API integration CI step.

Model evaluation is not applicable because this only exposes and forwards an existing sampling parameter; it does not change model implementation, accuracy, or sampling semantics.

## Details

The Responses request schema omitted `min_tokens`, so the field never reached `SamplingParams.from_optional` and the engine used its default of `0`. The patch adds the field inside the existing rendered Responses API extra-parameters snippet and forwards it through the existing sampling conversion.

The serving regression submits `min_tokens=2` with `max_output_tokens=1` through `RemoteOpenAIServer` and requires the engine's exact user-facing validation error. Without forwarding, that request is accepted because the engine sees `min_tokens=0`.

This does not duplicate an existing fix. Immediately before implementation and publication, searches across open and closed PRs by issue number, `ResponsesRequest min_tokens`, and `responses API min_tokens` found no PR implementing this issue. The older merged sampling-parameter PR #32609 explicitly left `min_tokens` out.

AI assistance was used to investigate, implement, test, and independently review this change. I reviewed every changed line and reran the checks above on the exact submitted head.
