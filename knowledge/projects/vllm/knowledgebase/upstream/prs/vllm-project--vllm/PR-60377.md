# [Bugfix] Report vocab ranks for `logprob_token_ids` on Model Runner V1

[Upstream PR](https://github.com/vllm-project/vllm/pull/60377) · state: open · merged: False

## Original PR description



## Overview

Fixes the Model Runner V1 side of #60357: entries requested through `logprob_token_ids` came back with their position in the request list as `rank` instead of their vocab rank. The Rust engine-core client also learns to decode the per-entry ranks this now sends. The V2 side is covered by #36746 (see Details).

## Claims

- On Model Runner V1, every `logprob_token_ids` entry reports its vocab rank, using the `>=` definition vLLM already uses for the sampled token. Untied tokens match `logprobs=-1` exactly; tied ones report the end of their tie group.
- The Rust frontend decodes the per-entry ranks. Without that, a gRPC request with a `token_ids` candidate selector on a V1 engine would fail with `new_logprobs.token_ranks: expected rank-1 array, got rank 2`.
- The top-k and `logprobs=-1` paths are untouched, and typical label lists (2 to 10 ids) cost nothing measurable.

## Details

**Root cause.** Only the sampled token got a real rank: `selected_token_ranks` is one value per position. `append_logprobs_for_next_position` then gave the remaining entries `1..k`, which is right for the top-k path because those columns are sorted, but `logprob_token_ids` columns are in request order. When the sampled token was also in the list, its real rank was overwritten by its list position in the per-position dict.

**Change.**
- `Sampler.gather_specific_token_logprobs` ranks every gathered column with `batched_count_greater_than_per_value`, a compiled reduction next to `batched_count_greater_than`. It never materializes the `[batch, ids, vocab]` comparison, and the batch and column dims are marked unbacked so a new list length doesn't recompile. In this mode `selected_token_ranks` is `[num_positions, max_num_logprobs + 1]`.
- `append_logprobs_for_next_position` accepts a rank per entry; the scalar path is unchanged.
- Rust: `token_ranks` may be 1-D or 2-D, and 2-D ranks are used as-is.

A per-column loop over the existing helper was my first version; at batch 128 with 128 ids the call took 23.4 ms instead of 2.8 ms, so I compared it against sort + `searchsorted` and a hand-written Triton kernel. The single compiled reduction was the best overall; sorting only won at the very largest size.

**Why V1.** V1 is still selected for some ROCm architectures, without Triton, and for features MRV2 doesn't support yet (sequence parallelism, prefill context parallelism, several spec-decode methods), so scoring there still returns wrong ranks. MRV2 has the same bug.

**Relation to #36746** (cc @mvanhorn). It already moves V2 to per-entry 2-D ranks while de-duplicating `top_logprobs`, but keeps the V1 sampler 1-D, so this isn't a duplicate. I used the same representation (2-D `selected_token_ranks`, a rank list in `append_logprobs_for_next_position`, 1-D or 2-D `token_ranks` in Rust) so the two compose: whichever lands second will hit textual conflicts in those spots but no design change. The V2 case of the new end-to-end test is `xfail` (non-strict) until #36746 lands.

**Ties.** Ranks keep the existing `>=` definition, which also keeps NaN at rank 0 as the Rust decoder documents. `logprobs=-1` numbers tied tokens sequentially, so the two modes can differ within a tie group; the test accepts any position inside the group.

**Out of scope.** Under speculative decoding `logprob_token_ids` currently returns almost no logprobs; that's #42592 / #44727.
