# [ROCm][Perf] Defer GDN spec decode state stores in the Triton MTP kernel

[Upstream PR](https://github.com/vllm-project/vllm/pull/64325) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

On ROCm, the Triton fused GDN MTP decode kernel now stores the recurrent state once per spec step instead of once per draft token, when the state is FP32 and `mamba_cache_mode="none"`. It records the inputs of the other tokens, and the next step replays only the accepted ones. CUDA and the other configurations are unchanged.

Related:
- #61855 made the Triton port of the fused GDN MTP decode kernel the ROCm default for spec decode.
- #61434 applies the same deferred state to `fused_sigmoid_gating_delta_rule_update` (the `VLLM_GDN_DECODE_KERNEL=triton` path). The two PRs are independent.
- ROCm/aiter#7069 adds the same option to aiter's Triton GDN decode kernel.
- #61761 (RFC) tracks DFlash2 performance on ROCm.

## Claims

- Qwen3.8-27B + `z-lab/Qwen3.8-27B-DFlash2` (7 draft tokens) on MI355X, prefix caching off: output throughput is +6.1% at concurrency 16 and +8.2% at concurrency 64. Concurrency 1 is unchanged.
- The fused MTP decode op (update + gated RMSNorm) drops from 382 µs to 213 µs at 64 sequences (T=8, HV=48, K=V=128).
- Outputs match the per-token mode up to fp32 rounding. A unit test checks the outputs and states over 8 consecutive steps.

## Details

**Why.** The kernel stores the full state (HV × V × K fp32, 3 MiB per sequence per layer for Qwen3.8-27B) after every token, so that the next step can start from slot `num_accepted - 1`. With 7 draft tokens that is 8 stores per step, and only one of them is read. At concurrency 64 these stores take most of the kernel time.

**How.** With `defer_spec_state=True`:
- Slot 0 of each `state_indices` row keeps the state after the step's first token.
- For tokens 1..T-1, each program writes a record to slot 1: the normalized k (K), its v tile (BV), the decay and beta. That is K + BV + 2 floats instead of a BV × K state tile. `deferred_spec_state_fits` checks that the records of all draft tokens fit in one slot.
- The next step loads slot 0 and replays `num_accepted - 1` records with the same update as the main loop. A barrier separates the replay reads from the new record writes.
- The update kernel is split out of `fused_gdn_decode_post_conv_mtp_triton` as `gdn_decode_mtp_update_triton`, which returns the pre-norm outputs and the per-tile sums of squares. The fused op calls it and then the norm kernel, as before.

**Exactness.** The replay recomputes the same fp32 recurrence from the same inputs. With a bf16 state the per-token mode rounds between tokens and the replay does not, so the mode requires an FP32 state. Qwen3.5/3.8 checkpoints set `mamba_ssm_dtype=float32`.

**Launch configuration.** The deferred mode moves much less memory per token, so the serial token loop limits it. It uses BV=16 and one warp, the best of a sweep; a single sequence uses 4 warps, because one warp per program leaves the GPU mostly idle. BV fixes the record layout, so it does not depend on the batch size.

**When it is enabled.** `QwenGatedDeltaNetAttention.defer_gdn_spec_state` is set at init when all of the following hold:
- ROCm, and the fused spec decode path is enabled (`gdn_decode_kernel == "cuda"`, which runs the Triton port on ROCm). The CUDA op does not implement this mode.
- `mamba_cache_mode == "none"`.
- The SSM state dtype is fp32.
- The records fit in one slot (true for Qwen3.8-27B up to 14 draft tokens).

Every spec step of a request must use the same mode. Pure spec batches take the fused op. Spec rows of mixed batches go through `_forward_core`, which now calls `gdn_decode_mtp_update_triton` with the same flag instead of `fused_sigmoid_gating_delta_rule_update`. The flag is fixed per layer, so all steps agree.

**Limitations.**
- With prefix caching on (`align`), `preprocess_state` copies per-token states at block boundaries, so this mode does not apply there. Supporting it means replaying the records before that copy.
- Nothing else may read the per-token slots. In `none` mode, decode rows always take the spec path, and a new request starts with `num_accepted = 1`, which replays no records.
- No host synchronization is added.
- Validated end to end on MRV2 only.
