# [Rust Frontend] Return 501 instead of 404 for Python-only routes

[Upstream PR](https://github.com/vllm-project/vllm/pull/62432) · state: open · merged: False

## Original PR description



## Overview

The Python API server registers several routes for a generate model that the Rust frontend does not serve; under `VLLM_USE_RUST_FRONTEND=1` they fall through to axum's default fallback, a bare 404 with an empty body, so clients cannot tell a missing feature from a wrong URL. This PR registers those routes in the Rust router under Python's gating and answers them with an explicit 501 that names the route and points at `VLLM_USE_RUST_FRONTEND=0`.

Addresses vllm-project/vllm#55994 (scale-out routes returning 404) without implementing the routes themselves.

## Claims

- `POST /v1/messages`, `/v1/messages/count_tokens`, `/v1/chat/completions/batch`, `/v1/decisions`, `/v1/systemone`, `/scale_elastic_ep`, and `/is_scaling_elastic_ep` return 501 instead of 404.
- The scale-out routes Python registers alongside `/inference/v1/generate` (`/inference/v1/abort_requests`, `/v1/{chat/completions,completions,messages,responses}/render`, `/v1/{chat/completions,completions}/derender`) now follow the same gate as `/inference/v1/generate`: Python's 403 `PermissionDeniedError` stub without `--enable-scale-out`, and 501 with it.
- `--enable-tokenizer-info-endpoint` is parsed into `ApiServerOptions` (it was accepted as a no-op) and registers `GET /tokenizer_info` with a 501; without the flag the route stays unregistered, as in Python.
- No route the Rust frontend already serves changes behavior.

Example response:

```json
{"error": {"message": "POST /v1/messages is not supported by the Rust frontend yet. Set VLLM_USE_RUST_FRONTEND=0 to use the Python frontend.", "type": "NotImplementedError", "param": null, "code": "501"}}
```

The Rust frontend only serves generate models, so the "generate task" gate is always true there.

Ownership and layering:

- Route registration and gating stay in `routes.rs`. The placeholders reuse the existing `ErrorResponse` shape and the existing `disabled_scale_out` stub, and add one `not_supported` handler that reads `MatchedPath` and `Method` to name the route, instead of one handler per route. Each registration carries a `TODO` for the real implementation.
- `--enable-tokenizer-info-endpoint` follows the `--enable-scale-out` path: parsed in the CLI layer, carried in `ApiServerOptions`, read by the router. It moves out of the no-op args list into `SharedRuntimeArgs`, so the value Python forwards through `--args-json` now reaches the router.

Scope and limitations:

- This only replaces 404s with explicit errors; implementing any of these API families is separate work. Implementing the scale-out render routes on the main router can reuse the standalone `vllm-rs render` handlers, which take `RenderState` rather than `AppState`.
- Not touched, because open PRs implement them: the Responses routes (vllm-project/vllm#58783) and `/generative_scoring` (vllm-project/vllm#46427). Cohere `/cohere/v2/chat` is left out because Python registers it only with `VLLM_ENABLE_COHERE_API=1` and the `cohere` SDK installed. FastAPI docs routes (`/openapi.json`, `/docs`, `/redoc`) are not an API contract and are not stubbed.

Not a duplicate: vllm-project/vllm#56124 stubs only the two chat/completions render routes and only when scale-out is enabled (still 404 otherwise); it has had merge conflicts and no activity since 2026-10-07. This PR covers its scope with the gating Python uses. Related open PRs that implement individual families and would replace a placeholder here: vllm-project/vllm#52896 (Anthropic Messages and `count_tokens`, last updated 2026-08-19), vllm-project/vllm#46081 (`/tokenizer_info`, last updated 2026-06-29), vllm-project/vllm#53418 and vllm-project/vllm#53419 (derender, last updated 2026-09-10). vllm-project/vllm#50698 adds an elastic EP control channel but no REST routes.
