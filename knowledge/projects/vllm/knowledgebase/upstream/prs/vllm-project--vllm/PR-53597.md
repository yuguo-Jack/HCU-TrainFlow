# [Multiproc] Fail fast on concurrent worker exceptions via background error pipe monitor

[Upstream PR](https://github.com/vllm-project/vllm/pull/53597) · state: open · merged: False

## Original PR description

## Purpose

When multiple workers process RPCs in `MultiprocExecutor`, if a worker encounters an unhandled exception while other ranks continue executing and enter collective operations (such as all-reduce or barrier), reading response queues sequentially causes `EngineCore` to block on healthy workers waiting on collectives indefinitely, leading to a silent hang/deadlock.

This PR introduces a dedicated lightweight error pipe per worker that reports unhandled exceptions directly to the executor background `MultiprocWorkerMonitor` thread. When an exception occurs on any worker:
1. The failing worker writes the exception message and traceback to its error pipe before idling.
2. The background monitor thread detects the error pipe event, logs the error, and initiates executor shutdown.
3. In-progress shared memory reads are cancelled via `_spin_condition.cancel()`, ensuring the main process fails fast immediately rather than hanging on deadlocked collectives.
4. Preserves 100% native sequential dequeue and zero polling overhead on the normal execution path.

## Test Plan
- Unit tests for `MultiprocExecutor` error monitor.
- Verified on multichip / distributed clusters with injected worker exceptions: executor cleanly shuts down and raises the root cause error instead of deadlocking.

[P1] A broken diagnostic message can bypass both shutdown and the failure callback. Connection readiness only means bytes/EOF are available, not that the entire framed message has arrived. If a worker dies after sending part of a large error payload, this `recv()` raises `OSError: got end of file during message`, which the EOFError-only handler does not catch.

I reproduced this using the actual submitted monitor, a real Linux child, `multiprocessing.Pipe`, and an actual `Connection.send((large_error_string, traceback))`. After the reader becomes ready, terminating the sender mid-send and resuming the receive gives `executor_failed=True`, but `shutdown_calls=0` and `failure_callback_calls=0`. Only scheduling is gated; the receive/error is real. Cleanup/callback are spies, so this proves the control-path failure rather than claiming a full multi-GPU hang.

Please make teardown/notification independent of successfully receiving diagnostic text. Also avoid an unbounded framed read in the sole liveness monitor: even another `poll()` does not ensure the complete payload is present. A lightweight failure notification with diagnostics retained in worker logs, or separately bounded diagnostic retrieval, would keep fail-fast behavior reliable.
