# [Bugfix][Multiproc] Fail fast when a worker hits a fatal RPC failure

[Upstream PR](https://github.com/vllm-project/vllm/pull/53597) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

When a worker fails an RPC that already fails the engine, the worker now exits. The executor's existing worker monitor then shuts down the other ranks, instead of leaving them blocked in a collective with the failed one. #61558 (@olivierzach) builds on this PR to cover workers on other nodes.

## Claims

- A fatal RPC failure on any rank now fails the engine within seconds. Before, a failed startup RPC hung forever, because those RPCs have no timeout. A failed step RPC waited up to `VLLM_EXECUTE_MODEL_TIMEOUT_SECONDS` (300 s by default).
- If the failing rank is one the engine reads replies from, the engine still gets the root-cause error.
- Recoverable RPC failures keep the current behavior: the failure is only returned to the caller. An example is loading an invalid LoRA adapter. `--enable-fault-tolerance` also keeps the current behavior.

<details>
<summary>Why the worker flushes zmq before exiting</summary>

`os._exit` drops zmq messages that haven't been sent yet. I ran a probe of the real failure path with a shared-memory reply queue and an idle reader:

- Without the flush, the reader's wake-up was lost in 3 of 8 runs (sync) and 1 of 8 (async). The reader then saw the reply only at the 5 s recheck, by which time the executor shutdown may already have cancelled the read.
- With the flush, 0 of 8.

Over TCP, replies of 4 MB or more were lost in 20 of 20 runs without the flush, and 0 of 20 with it.
</details>

## Details

**Root cause.** `WorkerProc._execute_worker_rpc` catches every exception, replies FAILURE, and keeps serving. `collective_rpc` reads replies in rank order, or from the output rank only. When one rank fails mid-step, its peers block in a collective, so the rank the engine waits on never replies. Nothing tells the executor that a worker has failed. @olivierzach [hit this on a two-node GLM deployment](https://github.com/vllm-project/vllm/pull/61558#issuecomment-6229008239): a TP rank that wasn't the output rank failed in `execute_model`, and generation stalled for over 20 minutes while health checks kept passing.

**Design**

- **Which RPCs.** The worker exits only when one of `WorkerProc.FAIL_FAST_RPCS` fails, and only with fault tolerance off. Those RPCs are `determine_available_memory`, `initialize_from_config`, `compile_or_warm_up_model`, `execute_model`, `sample_tokens` and `execute_dummy_batch`. Catch-and-continue is still needed for recoverable RPCs and for fault-tolerance recovery.
- **No new IPC channel.** The existing worker monitor sees the exit. It shuts down the executor, which terminates the other workers and cancels pending reads, and then calls the failure callback.
- **Flush before exit.** The worker waits up to 5 s for the async output thread to drain. It then destroys the reply queue's zmq context with a 1 s linger.
- **`os._exit(1)`.** The normal teardown (`destroy_model_parallel`) can block on the stuck peers, and `worker_main` would exit with code 0.
- **Ray.** `RayExecutorV2` workers inherit this; their monitor watches the actors' `run()` refs. This was not tested on Ray.
- **Size.** About 50 lines in `multiproc_executor.py`.

Earlier revisions of this PR added an error pipe from each worker to the monitor. Following @njhill's suggestion, the worker now exits instead.

**Limitations**

- Failures of workers on other nodes are not detected by the head node here; #61558 covers that.
- `os._exit` skips cleanup. The resource tracker reclaims the worker's shared-memory segment at shutdown and logs a warning, as it does after a crash.
- An existing bug that this PR doesn't change: after an RPC that waits on every rank fails, `collective_rpc` doesn't read the other ranks' replies. The next such RPC can then read a stale one, for example after an invalid LoRA with TP > 1.

**Related PRs.** #58738 targeted multi-node peer failures with a separate heartbeat protocol. Its author is not continuing it and supports #61558, which depends on this PR.

The normal path and model outputs are unchanged, so model evaluations don't apply. AI assistance was used for this PR. I reviewed every change and ran the CPU tests above.

[P1] A broken diagnostic message can bypass both shutdown and the failure callback. Connection readiness only means bytes/EOF are available, not that the entire framed message has arrived. If a worker dies after sending part of a large error payload, this `recv()` raises `OSError: got end of file during message`, which the EOFError-only handler does not catch.

I reproduced this using the actual submitted monitor, a real Linux child, `multiprocessing.Pipe`, and an actual `Connection.send((large_error_string, traceback))`. After the reader becomes ready, terminating the sender mid-send and resuming the receive gives `executor_failed=True`, but `shutdown_calls=0` and `failure_callback_calls=0`. Only scheduling is gated; the receive/error is real. Cleanup/callback are spies, so this proves the control-path failure rather than claiming a full multi-GPU hang.

Please make teardown/notification independent of successfully receiving diagnostic text. Also avoid an unbounded framed read in the sole liveness monitor: even another `poll()` does not ensure the complete payload is present. A lightweight failure notification with diagnostics retained in worker logs, or separately bounded diagnostic retrieval, would keep fail-fast behavior reliable.
