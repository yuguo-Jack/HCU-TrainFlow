- Oxygen56 · COMMENTED · 2026-06-10T07:49:41Z · [source](https://github.com/vllm-project/vllm/pull/44745#pullrequestreview-4465662663)

Thanks for this
  fix! I had opened #45076 for the same issue before finding this PR — closing
  mine in favor of this one. Two small suggestions from my investigation that
  could make this even more robust:

  ### Suggestion 1: Add empty_cache() before each measurement

  The original code calls empty_cache() once before the outer for-mode loop, but
  multiple modes and per-mode captures can accumulate allocator fragmentation
  between measurements. Flushing the caching allocator before each mem_get_info
  snapshot reduces noise:

    for i, desc in enumerate(profile_descs):
        torch.accelerator.empty_cache()  # add this
        mem_before = torch.cuda.mem_get_info()[0]

  ### Suggestion 2: Emit a warning when negative deltas are detected

  A silent clamp hides a genuine anomaly. If free_after > mem_before, something
  unusual is happening (allocator fragmentation, lazy buffer cleanup, page
  migration). Logging it helps users and maintainers diagnose:

    delta = mem_before - free_after
    if delta < 0:
        logger.warning(
            "CUDA graph capture freed memory (%d MiB); "
            "this may indicate allocator fragmentation or lazy buffer cleanup. "
            "Clamping to zero.",
            -delta // (1 << 20),
        )
    mem_samples.append(max(delta, 0))

  The tests look great — thanks for adding those!
