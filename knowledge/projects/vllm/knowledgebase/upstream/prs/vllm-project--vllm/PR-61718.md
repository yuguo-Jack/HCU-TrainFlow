# [Bugfix] Fix NaN output of the Mamba2 chunk scan kernel on sm90

[Upstream PR](https://github.com/vllm-project/vllm/pull/61718) · state: closed · merged: True

## Original PR description

## Overview

Fixes #61603. On Hopper (sm90), the Mamba2 SSD kernel `_chunk_scan_fwd_kernel` writes NaN/Inf into whole output rows from finite inputs with some of its autotune configs (8 of 23 in the reproducer). The autotuner picks configs by speed only, so it can pick one of them. This PR drops these configs on CUDA sm90 only. It uses one rule taken from the compiled code: drop a config when `num_warps % 4 == 0`, `BLOCK_SIZE_M % 64 == 0` and `num_stages > 1`.

Compared with #61664, this fix:

- also drops three configs (M/N/K, warps, stages) that compile to the same racy code on Triton 3.7.1: 64/32/32 8w 2s, 128/256/64 8w 3s and 128/32/32 4w 4s. On the [#61664](https://github.com/vllm-project/vllm/pull/61664) tree the reproducer still prints `configs producing NaN from finite inputs: 1 of 15` (128/32/32 4w 4s gave NaN in 81 of 100 calls), and 128/256/64 8w 3s gave NaN in 50 of 50 calls at dstate 256.
- adds a test that runs the real kernel with every config in the list. It fails on the old code and on the [#61664](https://github.com/vllm-project/vllm/pull/61664) tree. The tests in [#61664](https://github.com/vllm-project/vllm/pull/61664) are mock-only and never run the kernel; on the old code they fail only with an `ImportError` that comes from that PR's own refactor.

## Claims

- On sm90, no config left in the autotune list gives NaN on the reproducer: `0 of 12`, against `8 of 23` before.
- Other platforms keep all 23 configs. The filter returns the list unchanged unless the device is CUDA with capability 9.0.
- No speed cost at the shapes measured on an H20-3e: the fastest config of the old list is kept.
- The new test `test_chunk_scan_fwd_every_config_matches` fails on the old code and passes with the fix.

## Validation

Setup: 1 x NVIDIA H20-3e (sm90), torch 2.13.0+cu130, Triton 3.7.1, vLLM at commit `77154ca6116ae34cbfe314beef1016bde9b63989`, then the same commit plus this PR.

Reproducer: the issue's script, changed to force each config of `_chunk_scan_fwd_kernel` in turn and run it 100 times on finite inputs (seed 0, 181 tokens, 2 chunks). Run it with `python sweep.py`. I swept the whole list because the issue's `GOOD` config is not in the list at this commit.

```python
import torch, triton
from vllm.model_executor.layers.mamba.ops.ssd_chunk_scan import (
    _chunk_scan_fwd, _chunk_scan_fwd_kernel)

print("triton", triton.__version__, "torch", torch.__version__, torch.cuda.get_device_name(0), torch.cuda.get_device_capability(0))
seqlen, nchunks = 181, 2
dev, g = "cuda", torch.Generator(device="cuda").manual_seed(0)
rn = lambda *s, dt=torch.bfloat16, sc=0.5: (torch.randn(*s, generator=g, device=dev)*sc).to(dt)
x, C = rn(seqlen,64,64), rn(seqlen,8,128)
cb = rn(nchunks,8,128,128, dt=torch.float32, sc=1.0)
dt_ = (torch.rand(64,nchunks,128, generator=g, device=dev)*0.1).float()
dA  = (-torch.rand(64,nchunks,128, generator=g, device=dev).cumsum(-1)*0.05).float()
states = rn(nchunks,64,64,128, dt=torch.float32, sc=0.1)
cu  = torch.tensor([0,128,181], dtype=torch.int32, device=dev)
sidx = torch.zeros(nchunks, dtype=torch.int32, device=dev)


ALL = list(_chunk_scan_fwd_kernel.configs)
print("inputs finite:", all(bool(torch.isfinite(t.float()).all()) for t in (x,C,cb,dt_,dA,states)))
nbad = 0
for i, c in enumerate(ALL):
    _chunk_scan_fwd_kernel.configs = [c]
    hits = 0
    try:
        for _ in range(100):
            out = torch.empty(seqlen,64,64, dtype=torch.bfloat16, device=dev)
            _chunk_scan_fwd(cb, x, dt_, dA, C, states, cu, out, sidx, D=rn(64,64, dt=torch.float32, sc=0.1))
            hits += int((~torch.isfinite(out.float())).any().item())
    except Exception as e:
        print(i, c.kwargs, c.num_warps, c.num_stages, "ERR", type(e).__name__); continue
    nbad += hits > 0
    print(i, c.kwargs, "warps", c.num_warps, "stages", c.num_stages, "-> NaN in", hits, "/100 calls")
print("configs producing NaN from finite inputs:", nbad, "of", len(ALL))
```

## Details

Root cause. In the K loop, `acc += tl.dot(cb, x)` uses `cb` built in registers (decay `exp`, `dt`, causal mask, cast to bf16). With whole warpgroups (`num_warps % 4 == 0`) and `BLOCK_SIZE_M % 64 == 0`, Triton lowers this dot to wgmma with the A operand in registers. With `num_stages > 1`, Triton's `TritonGPUPipeline` pass splits the dot into async wgmmas and waits with `pendings = 1`. So the last wgmma of an iteration is still running when the loop jumps back. The next iteration loads the next `cb` tile into the same registers before it waits for that wgmma. The PTX ISA does not allow changes to the A registers of `wgmma.mma_async` before `wgmma.wait_group`. The running wgmma reads raw fp32 bits as bf16, which gives NaN, Inf and values near 3.4e38 in whole output rows. The race depends on timing, so the NaN rate changes by config and by run. The bug is in Triton's pipeliner, which vLLM cannot change. The vLLM part is that the autotune list offers configs that Triton compiles this way.

<summary>SASS of the K loop, 128/128/32 with 4 warps and 4 stages</summary>

```
/*58f0*/ LDS.128 R160, [R234] ;              <- overwrites R160..R163
/*5b90*/ LDS.128 R156, [R234+0x1000] ;       <- overwrites R156..R159
...
/*70a0*/ HGMMA.64x128x16.F32.BF16 R88, R160, gdesc[UR12].tnspB, R88 ;     <- A = R160..R163
/*70b0*/ HGMMA.64x128x16.F32.BF16 R24, R156, gdesc[UR12].tnspB, R24, gsb0 ; <- A = R156..R159
/*71d0*/ WARPGROUP.DEPBAR.LE gsb0, 0x1 ;      <- leaves the 0x70a0/0x70b0 group running
...
/*7720*/ @!P5 BRA 0x5750 ;
```

</details>

The fix. `_drop_racy_wgmma_configs` wraps the existing list. On CUDA sm90 it drops 11 of the 23 configs (old indices 2, 9, 10, 12, 13 to 19).

- It keeps the 1-stage wgmma configs: Triton waits on them with `pendings = 0` right after the dot. It keeps the 2-warp and `BLOCK_SIZE_M = 32` configs: they use `mma.sync`, which is synchronous.
- Only sm90 has wgmma, so other GPUs keep the full list. `is_cuda()` is needed because ROCm gfx90a also reports capability (9, 0).
- The filter is a rule, not a list of configs that failed once. Configs 2, 10 and 12 have the same racy code but gave little or no NaN at the reproducer's shape (12 does not fit there). At dstate 256, config 10 gave NaN in 1 of 20 calls and config 12 in 20 of 20. A TTGIR check of all 23 old configs at dstate 128 and 256 found 0 mismatches between the rule and the racy pattern.
- The filter runs when the list is built, not as `early_config_prune`. Triton skips pruning when the list has one config, and `VLLM_TRITON_FORCE_FIRST_CONFIG` walks `self.configs` without pruning, so pruned configs could still run.
- A TTGIR scan of the other Mamba2 SSD kernels (`_bmm_chunk_fwd`, `_chunk_state_fwd`, `_state_passing_fwd`, `_chunk_cumsum_fwd`) found no register-A async wgmma, so only this kernel changes.

Reading the diff: `ruff format` re-indents the config list because it is now a function argument. With whitespace hidden (`git diff -w`), the change in `ssd_chunk_scan.py` is about 25 lines. No config is added, removed or edited by hand.

Limitations: this works around a Triton bug seen with Triton 3.6.0 (in the issue) and 3.7.1 (here). The new test does not check that non-sm90 platforms keep the full list.

Thanks for the root-cause analysis and the fix! The pipeliner/register-conflict explanation is consistent with everything we observed while investigating the original issue.

As an additional data point from the original environment (H20-3e, sm90; vLLM 0.19.1, Triton 3.6.0), we tested all 23 autotune configs of `_chunk_scan_fwd_kernel` individually — each in a fresh process, with 100 replays of a captured input bundle that had previously triggered NaNs.

All 8 configs that produced NaNs (at rates ranging from 14% to 100%) satisfy this PR's filter rule (`num_warps % 4 == 0 && BLOCK_SIZE_M % 64 == 0 && num_stages > 1`). The rule also excludes 2 configs that showed no NaNs in our tests (0/100). So the filter covers all 8 failing configs we identified, plus 2 that appeared clean — a conservative approach, consistent with your H200 findings.

One observation that may help with reproduction: the failure appears intermittent across process restarts. In our environment, the autotuner re-benchmarks configs in each new process, so the selected config can change between restarts. Once an affected config is selected, the process may continue using it, making the same node appear stable for hours and then fail for hours without any code or configuration changes. This may help explain why the issue has been difficult to reproduce.

We've been running the same mitigation (pruning the config list at startup) on our serving node, and it has been stable so far.

I'm also happy to test this PR branch on our H20-3e node and report back if that would be helpful.
