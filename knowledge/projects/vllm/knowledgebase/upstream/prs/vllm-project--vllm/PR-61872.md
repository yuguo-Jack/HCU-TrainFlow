# [Bugfix][ROCm] Restore MoE weight padding dropped by #46009

[Upstream PR](https://github.com/vllm-project/vllm/pull/61872) · state: open · merged: False

## Original PR description



## Overview

Re-enables ROCm MoE weight padding (`VLLM_ROCM_MOE_PADDING`, on by default) for unquantized MoE on the TRITON path. It has been silently inactive since #46009. On Radeon Pro W7900 with GLM-4.7-Flash at concurrency 1, this restores 4.5–10.8 % output throughput and 10–13 % TTFT. Related: #46009, #46381 (earlier fix for this padding), #59332 (padding tests).

## Claims

- **Bug fix:** expert weights on ROCm get their padded layout again after loading. On current `main` the padding is computed and then discarded.
- **Performance** (GLM-4.7-Flash, 4× W7900, concurrency 1): TP4 output tok/s **+4.5 %**, TTFT **−10.3 %**; TP2 output tok/s **+10.8 %**, TTFT **−12.9 %**.
- **No regression of #46009:** an in-place weight update (`process_weights_after_loading()` called again after CUDA graph capture) still keeps the expert weight storage addresses.
- **Tests:** new regression tests assert that the padded layout persists after loading and after a weight update. Both fail on `main`.
- **No accuracy change:** the MoE output is bitwise identical with and without padding. GSM8K generations at concurrency 1 are identical to `main` (250 / 250).

## Validation

### End-to-end

We observed lower concurrency-1 throughput and TTFT for GLM-4.7-Flash on W7900 with recent `main`, and traced it to #46009. We measured `main` (`e37e51dd2`) against the same build with this patch:
- Setup: bf16, `--max-model-len 4096`, random 1024 input / 256 output tokens, `--ignore-eos`, 20 prompts, 3 warm-ups, 3 cycles per configuration.
- TTFT is the mean of cycles 2–3 (cycle 1 includes one-off JIT warm-up). TPOT and tok/s are the mean of all 3 cycles.
- Run-to-run spread: TPOT was identical across cycles, and tok/s varied by ≤ 0.03 between cycles 2 and 3. There were no failed requests.

| GPUs | `--gpu-memory-utilization` | Build | TTFT (ms) | TPOT (ms) | Output tok/s |
|---|---|---|---|---|---|
| TP4 (4× W7900) | 0.8 | `main` (mean of 2 runs) | 54.27 | 19.56 | 50.57 |
| TP4 (4× W7900) | 0.8 | **this PR** | **48.66** (−10.3 %) | **18.73** (−4.3 %) | **52.85** (+4.5 %) |
| TP2 (2× W7900) | 0.9 | `main` | 68.89 | 23.48 | 42.08 |
| TP2 (2× W7900) | 0.9 | **this PR** | **60.02** (−12.9 %) | **21.20** (−9.7 %) | **46.61** (+10.8 %) |

Controls that isolate the cause:
- `main` with `VLLM_ROCM_MOE_PADDING=0` performs the same as `main` (TP4: 50.52 tok/s, TPOT 19.58 ms), so the padding is already inactive on `main`.
- `main` with only the pre-#46009 line restored performs the same as this PR (TP4: 52.84 tok/s, TPOT 18.74 ms).
- A second `main` run at the end of the series matched the first (50.60 vs 50.54 tok/s).

TP2 uses 0.9 because, with the padding restored, it has no memory left for the KV cache at 0.8 (see *Trade-off*). Concurrency-1 results do not depend on KV cache size.

### Accuracy (lm-eval GSM8K, 5-shot, TP4, `--gpu-memory-utilization 0.8`)

Padding changes only the row stride, never the values. With identical inputs, the fused MoE output from padded weights is **bitwise identical** to the output from dense weights. We checked this at GLM-4.7-Flash TP4 shapes (64 experts, H = 2048, I = 384, top-4) for 1, 7, 64, 512 and 2048 tokens.

| Setting | `main` | this PR | Identical generations |
|---|---|---|---|
| Concurrency 1, first 250 questions | 0.844 ± 0.023 | **0.844 ± 0.023** | **250 / 250** |
| Concurrency 64, full set (2 runs each) | 0.8514, 0.8393 | 0.8355, 0.8355 | ~30 % between versions |

Scores are strict-match exact match; flexible-extract is within 0.001 of strict.

With no batching (concurrency 1), the outputs are identical. At concurrency 64, generations depend on batch composition, which depends on timing. The two `main` runs differ from each other by 1.2 points and share only 33 % of generations, partly because the first run was slowed by Triton JIT compilation. The two runs of this PR were identical to each other (100 %). The differences between versions at concurrency 64 therefore reflect scheduling, not numerics.

## Details

**What the padding does.** For eligible unquantized MoE weights (row size a multiple of 512 B), `_maybe_pad_weight` returns a view with the same shape and values but a 256 B larger row stride, backed by new storage (`F.pad(w, (0, n))[..., :-n]`). The fused MoE Triton kernel reads weights through their strides, so consecutive weight rows land on different DRAM channels instead of the same ones.

**Root cause.** The padding only takes effect if the parameter is pointed at the padded storage. #46009 changed

```python
layer.w13_weight.data = self._maybe_pad_weight(layer.w13_weight.data)
```

to

```python
layer.w13_weight.data.copy_(self._maybe_pad_weight(layer.w13_weight.data))
```

so that storage addresses stay stable for CUDA graphs during weight updates. However, `copy_` writes the values back into the original dense storage and discards the padded layout. `process_weights_after_loading()` also runs on the initial load, so the padding has been disabled for every model on this path. Values are unchanged, so accuracy tests and #46009's address-stability test cannot detect this. Only a stride check or a benchmark can.

**Fix.** Point the parameter at the padded storage only on the initial load (`self.moe_kernel is None`). This is the same first-load / weight-update check `_setup_kernel()` already uses for `replace_parameter(..., prefer_copy=...)`. On a weight update the padding is skipped:
- The parameters already carry the padded layout.
- The MoE weight loaders write into it in place (`narrow().copy_()`).
- Layerwise reload copies the processed values back into the original tensors.
So storage addresses stay unchanged, which is the guarantee #46009 added.

**Scope.**
- **ROCm only.** `_maybe_pad_weight` is gated on `current_platform.is_rocm()`, `VLLM_ROCM_MOE_PADDING` and the absence of EPLB. On other platforms it returns its input, and the changed lines are a no-op, as they were before.
- **Not architecture-specific.** On ROCm the padding is architecture-independent. This PR restores the behaviour from before #46009 and does not extend padding to anything new.

**Trade-off.** Restoring the padding also restores its memory cost, which disappeared together with the speed-up:

| Config (GLM-4.7-Flash) | Extra memory per GPU |
|---|---|
| TP4 (`w13` padded) | +0.54 GiB |
| TP2 (`w13` and `w2` padded) | +2.52 GiB |

Deployments sized on recent `main` with little memory headroom may need a higher `--gpu-memory-utilization`. Our TP2 run at 0.8 failed with "No available memory for the cache blocks". Alternatively, `VLLM_ROCM_MOE_PADDING=0` trades the speed-up for memory.

**Limitations.**
- End-to-end validation was done on Radeon Pro W7900 (gfx1100) only.
- The change runs at load time only and adds no CPU/GPU synchronization during inference.
