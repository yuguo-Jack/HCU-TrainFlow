# [Bugfix][Kernel] Pass packed rows to the sm90 FlashInfer FP8 block-scale GEMM

[Upstream PR](https://github.com/vllm-project/vllm/pull/64040) · state: open · merged: False

## Original PR description

## Overview

Fixes wrong results from the SM90 FlashInfer FP8 block-scale GEMM (`flashinfer.gemm.fp8_blockscale_gemm_sm90`) when the activation is not row-contiguous. The kernel binding takes only a data pointer and assumes rows of exactly K elements, but the dynamic FP8 block-scaled linear kernel forwards every M < 32 batch as-is, so a strided input (e.g. a column slice) is read from the wrong memory for every row after the first. The fix passes packed (contiguous) rows in both wrappers and adds a regression test.

## Claims

- **Bugfix:** the sm90 FlashInfer FP8 block-scale GEMM no longer misreads strided activations. Previously, rows 1..M-1 of a non-contiguous input were computed from the wrong memory; they now match the packed-row result bit-exactly.
- **Scope:** only the small-batch (M < 32) FlashInfer path is affected; M >= 32 already goes through DeepGEMM, which honours strides. Already-contiguous inputs are untouched (`Tensor.contiguous()` is a no-op), so there is no overhead in the common case and no host synchronization is added.

## Validation

- New regression test `test_flashinfer_fp8_blockscale_gemm_strided_input` in `tests/kernels/quantization/test_block_fp8.py` (parametrized over M in {2, 31}): feeds the wrapper a column slice whose row stride is larger than K and asserts the result is bit-exact against the packed copy. It executes on SM90 + FlashInfer and skips elsewhere.
- `pytest tests/kernels/quantization/test_block_fp8.py -k "strided_input or flashinfer"`: validated on an H200 by the original author — 42 passed, 5 skipped. This PR's environment has no CUDA device, so the module skips here; the new test needs an SM90 machine (or the relevant CI job) to execute.
- Wrapper semantics additionally smoke-tested on CPU with a stubbed kernel binding: a strided input reaches the kernel packed with identical values, and a contiguous input passes through without a copy.
- `ruff check`, `ruff format --check`, and the full pre-commit hook set (including mypy and the test-tethering check) pass on the changed files.

## Details

**Root cause.** `flashinfer_fp8_blockscale_gemm` wraps `flashinfer.gemm.fp8_blockscale_gemm_sm90`, whose SM90 kernel takes only a data pointer and assumes packed rows of K elements. `_flashinfer_fp8_blockscale_gemm_impl` and the swapAB branch of `_dynamic_flashinfer_deepgemm_blockscale_gemm_impl` forwarded the activation unchanged, so a non-contiguous input (row stride > K) was misread from row 1 onward. Any Hopper caller that hands this path a non-contiguous FP8 block-scaled activation with M < 32 is affected — e.g. a row-parallel input projection that passes column slices of an `[M, hidden]` tensor, as some speculative-decoding drafters do.

**Fix.** Call `input.contiguous()` before the kernel in both wrappers. The copy happens only when the input is actually strided; packed inputs pass through unchanged.

**Trade-offs / limitations.** The copy is at most M x K bf16 elements on the M < 32 path (a few hundred KB at most), one small D2D copy per call, only for strided inputs. No model-level evaluation was run for this PR (no GPU in this environment); this is a correctness fix on a narrow kernel path, covered by the bit-exact unit test. End-to-end validation on Hopper with an affected configuration is welcome as a follow-up.

**Not a duplicate.** Searched open PRs for `fp8_blockscale_gemm`, strided/packed-row fixes, and related kernel bugfixes — none cover this.
