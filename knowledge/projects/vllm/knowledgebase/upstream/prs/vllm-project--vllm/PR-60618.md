# [Perf][Kernel] Single-launch fused scoring+top-k kernel for sparse-indexer prefill, without materializing logits

[Upstream PR](https://github.com/vllm-project/vllm/pull/60618) · state: closed · merged: True

## Original PR description

(this PR description was manually written by me)

## Summary

* Adds one persistent CUDA kernel that scores every visible key of a sparse-indexer prefill chunk and selects each row's top-k keys (k = 512, 1024 or 2048) **without materializing the `[rows, keys]` logits matrix**.
* One launch covers a prefill chunk of up to 16,384 query rows and up to 1M keys, including multi-request chunks. The dense path needs up to 127 call pairs (`fp8_mqa_logits` + `top_k_per_row_prefill`) for the same chunk.
* The output matches the dense path up to ties at the top-k boundary: the gated path ranks 24-bit score codes, and rows the gate cannot serve are rescanned exactly in fp32.

## Acknowledgements 

We'd like to acknowledge the authors of LiteTopK ([arXiv:2607.11976](https://arxiv.org/abs/2607.11976), #48726), who were the first to fuse sparse-attention indexer scoring with top-k selection without materializing the full logits matrix, using classic sample-based threshold filtering. I open a separate PR because:

* **Scope:** LiteTopK fuses only single-request chunks of exactly 8192/8128 rows with 192K–1M keys. Other chunks keep dense chunking, and even a fused chunk needs a separate seed-logits launch and about 2.6 GiB of workspace. Here every eligible chunk (≤ 16384 rows, ≤ 1M keys, multi-request) is one launch with no logits buffer and a 296 MiB workspace.
* **Correctness:** on B300 (commit `c7184685`) I found an undersized shared-memory allocation (4100 memcheck errors), racecheck hazards in the candidate ring and the seed/radix-select kernels, and no recovery from candidate-buffer overflow (the mapping kernel traps). LiteTopK's selection is also approximate (99.998% recall); this PR matches dense up to boundary ties.
* **Performance:** the only B300 serving data in #48726 shows TTFT within ~1% of  stock at ~200K tokens. This PR measures 1.10× at 256K and 2.05× at 1.04M (different setups, so not like-for-like).

However, most of this kernel is largely an adaptation of DeepSeek's code. This PR replaces the logits write-out with a sampled gate, candidate emission and in-kernel top-k selection.

## Motivation: what materializing the scores costs

The dense prefill path writes the fp32 scores of every (query row, visible key) pair to HBM, then reads them back to select the top-k. One 16,384-row prefill chunk needs `16,384 × keys × 4 B` of logits:

| Keys | Logits for one 16K-row chunk | Dense calls under the 512 MiB budget | Logits HBM traffic (write + read) |
|---|---|---|---|
| 16K | 1 GiB | 2 | 2 GiB |
| 128K | 8 GiB | 16 | 16 GiB |
| 512K | 32 GiB | 64 | 64 GiB |
| 1M | 64 GiB | 127 | 128 GiB |

This produces the following pattern:

It gets worse with context, e.g. at ISL 512K:
<img width="3727" height="279" alt="Screenshot 2026-10-08 at 12 19 32" src="https://github.com/user-attachments/assets/9a00072a-b55f-40e5-bed5-667394b1abdf" />

Two consequences:

1. **The logits budget trades KV-cache capacity against indexer speed.** During memory profiling, `sparse_attn_indexer` allocates a dummy `VLLM_SPARSE_INDEXER_MAX_LOGITS_MB` buffer, so the logits budget is part of the  peak memory the KV cache is sized from. On GLM-5.x with an FP8 KV cache, one token costs 47.7 KB per GPU (78 MLA layers × 576 B + 21 indexer layers × 132 B;  MLA KV is replicated across TP ranks). Measured at startup (TP4, B300, `--max-model-len 1048576`):

   | Configuration | Available KV memory | KV cache tokens |
   |---|---|---|
   | Dense, 512 MiB budget (default) | 115.66 GiB | 2,603,456 |
   | Dense, 8 GiB budget | 109.23 GiB | 2,458,816 (−5.6%) |
   | Fused (this PR) | 115.37 GiB | 2,596,928 (−0.25%) |

   At the default budget the logits buffer fits under the profiling run's other peak allocations, so it costs no KV cache. The cost is speed: rows per dense call shrink as keys grow (2²⁷ / keys), so a 128K-token prefill in 16K-token steps needs 76 dense call pairs and a 1M-token prefill needs 4,217. With the fused path (top-2048), the first four steps, whose rows see fewer than 64K keys, stay dense (21 call pairs) and every later step is one fused call: 4 at 128K, 60 at 1M. Buying fewer dense calls means raising the budget, and that memory comes straight out of the KV cache: an 8 GiB budget (one dense call per 16K-row chunk at 128K keys) costs 144,640 tokens of KV cache. One dense call per chunk at 1M keys would need 64 GiB, more than the KV cache of the entire 1M-token sequence (46.6 GiB). The fused kernel serves long-context chunks in one call each with a fixed 296 MiB workspace.
   
2. **The logits round trip is pure overhead.** Only k of the `keys` scores per row are needed. The fused kernel writes only a gated candidate set, about 1K–4.5K candidates per row depending on k (median on the captures below) at 6 B each, i.e. about 0.1–0.45 GB per 16K-row chunk, against 16–128 GiB of logits traffic at 128K–1M keys.

## What this PR does

<img width="2925" height="291" alt="Screenshot 2026-10-08 at 12 18 53" src="https://github.com/user-attachments/assets/c829d24b-9d43-4a4d-94ab-95df6f5053d7" />

**Kernel** (`csrc/fused_mqa_topk/`). One CTA per SM; each CTA claims 8-row blocks from a global counter (heaviest first) and keeps one continuous Q/KV/TMEM pipeline across blocks:

* **Scoring:** the FP8 MQA-logits pipeline adapted from DeepGEMM (TMA loads, UMMA into TMEM, warp-specialized producers). Since relu(s) = (s + |s|) / 2, the weighted sum of the linear halves is a single query (the heads folded with their weights) times the key; it runs on the tensor core as extra UMMA rows, so the math warps only accumulate the |s| terms.
* **Sampled gate:** a strided sample of the block's keys gives each row a threshold that keeps a few thousand candidates. The sample histogram is binned relative to each row's maximum over the first sample tile, so rows whose scores share a large common offset still get a tight gate.
* **Candidate emission:** keys above the gate are buffered per warp and drained to a per-row candidate slab by two drain warps while the scan continues.
* **Selection:** one warp per row selects the top-k from its candidates in shared memory (a sampled bracket, then histogram levels in registers), right after the block's scan, before its slot is reused.
* **Exact rescan:** a row whose candidate count leaves `[k, 16384]`, a row with weights unsafe to scale, or a block whose candidates exceed the selection scratch is rescanned exactly in fp32 (the dense scoring pipeline with a streaming top-k merge), so the output never depends on the gate being right.

### Memory

* Fused workspace: a pool of 2 eight-row slots per SM, fixed size, independent of rows, keys and context. It is 296 MiB on a 148-SM B300, allocated once per device during the profiling run, so it is accounted against the KV cache: −6,528 tokens (−0.25%) versus dense at the default budget (table above).
* The profiling run still reserves the dense logits budget: chunks below the dispatch threshold take the dense path.

### Limitations of this PR -- TODOs

Anything outside these bounds takes the existing dense path, unchanged.

* **Hardware:** SM100 family only (i.e., B200/GB200, B300/GB300). 
* **Models:** 32 index heads × 128 dims (e.g., GLM-5.2/5.3, GLM-5.3 kpool, DeepSeek-V4.1-Flash), top-k 512/1024/2048, FP8 indexer cache. 
    * Not supported yet: DeepSeek-V3.2 (64 index heads), MXFP4 indexer cache, and the DeepSeek-V4.1 two-level candidate selection layers (below).
* **Parallelism:** TP, DP (with or without EP) and PCP (with or without DCP) are supported. DCP without PCP is not: each rank holds only a shard of the KV cache, so it keeps the dense path. GLM-5.3-Flash's kpool indexer does not support PCP + DCP itself. Only TP4 is validated end to end.
* **Sizes:** up to 1M keys and 16,384 rows per call. The row cap is not a kernel-limitation: larger chunks are not validated end to end yet, so are excluded. Only chunks whose longest row sees ≥ 32K keys (≥ 64K for top-2048) use the kernel.

**DeepSeek-V4.1 two-level candidate selection.** DeepSeek-V4.1-Flash has 8 indexer layers (`index_source_layer_ids` 2, 8, 14, 20, 24, 28, 32, 36). Only layers 2, 8 and 14 use the kernel at this point, which is why its e2e gain is smaller than GLM-5.x (every GLM-5.x indexer layer uses the kernel). See figure below.

* **Layer 20 (candidate source)** also writes, per row, the top 2,048 blocks of 8 keys ranked by their max score. The kernel would need a second output and a second selection over block maxima, which rank far deeper than its 512-key gate.
* **Layers 24–36 (consumers)** mask their scores to those blocks before the top-512. The kernel would need the block list as an input.
* **`indexer_sparse_logits`** (opt-in) already speeds up the consumers by scoring only the candidate blocks, but it requires the MXFP4 indexer cache. https://github.com/vllm-project/vllm/pull/62011 addresses this.

**Kernel.** B300, real GLM-5.x indexer inputs captured from serving (MRCR 2- and 8-needle and random prompts, layers 0, 9 and 19), one 16,384-row prefill chunk, top-2048, median of `do_bench_cudagraph(rep=200)` over captures. Dense is chunked by the 512 MiB budget exactly as in vLLM and captured in one CUDA graph.

"Exact top-k": the selected keys' scores equal the fp32 top-k scores. The current dense path rounds its logits to bf16, so it is not exact at the boundary. See https://github.com/vllm-project/vllm/pull/61149#issuecomment-6412098207

**End to end.** TP4, B300, FP8 KV cache, prefix caching off. Dense is the upstream base of this PR.

<img width="1728" height="1007" alt="e2e_ttft_three_models_glm52_bs8" src="https://github.com/user-attachments/assets/45385c88-712e-457b-8a6d-51146e7347a0" />

Up to 32K every chunk stays dense (below the dispatch threshold of 64K visible keys). At 64K only the last chunk of each prompt reaches it. At 1.04M, TTFT drops by 711 s (55%). 

The two Flash models gain less in the same concurrency sweep, for different reasons:

* **GLM-5.3-Flash: every indexer layer uses the kernel, but each one gains less.** All 45 layers compute the indexer and all take the kernel. Its kpool indexer scores pools of 4 tokens and selects 512 of them, so a 1M-token prompt is 256K keys at top-512 per layer. There the kernel is 1.7× faster than dense, against 4.4× at 1M keys. The kernel's advantage grows with keys, because dense needs more logits windows and each one re-reads every key. The kernel also only starts at 128K tokens (the 32K-key top-512 threshold).
* **DeepSeek-V4.1-Flash: only some indexer layers use the kernel at this point (see detailed explanation above in Limitations/TODOs).** 8 of its 40 layers compute the indexer (the rest reuse one). Only layers 2, 8 and 14 take the kernel, at half-length keys (ratio-2 compressed, 512K keys for 1M tokens) and top-512. **Extending this kernel to other layers is a TODO for follow-up PRs**.
* **GLM-5.2/5.3,** by comparison: 21 of 78 layers compute the indexer, all 21 take the kernel, at 1M keys and top-2048.

## Fixes requested

### 1. Missing `fence.proxy.async` on three generic-to-TMA paths (`csrc/fused_mqa_topk/persistent_epoch.inc`)

The selection scratch starts at `kSelBase = offsetof(KernelSmem, kv)`, so it aliases `kv[]` and `sf_kv[]`. On three paths, generic shared-memory accesses are followed by a TMA write of the same bytes with no proxy fence between them (PTX ISA 8.6 proxy causality, 9.7.10.28.2):

1. A block with `samples == 0` after a selection on the same CTA. The producer waits on `sel_done`, skips the sample loop that holds the only fence (L173), and issues the scan TMA (L194). The fences at L490 and L587 come before the selection.
2. The switch from the epoch to the rescan (L691). Only `__syncthreads()` separates the selection from the rescan's first TMA into `smem_kv`.
3. `dense::invalidate_barriers` (L717) before the next rescan block or epoch. The fence has to go after the inval, so at L724.

We could not make this show on B300. A debug build overwrote the dead scratch with NaN as its last generic stores before each release, and forced `samples == 0` on every 4th block. It ran about 307K such paths on real GLM-5.3-Flash captures with 0 NaN scores. The same probe catches a deliberately broken order. So this is a spec issue, not an observed bug. The fix is three lines:

```diff
@@ persistent_epoch.inc (math warps, end of a block)
+    cutlass::arch::fence_view_async_shared();
     __syncwarp();
     if (lane == 0) sel_done.arrive();
@@ persistent_epoch.inc (before the rescan)
+cutlass::arch::fence_view_async_shared();
 __syncthreads();
 if (warp_idx == 0) cute::TMEM::Allocator1Sm().free(0, 512);
@@ persistent_epoch.inc (end of each rescan block)
     cur = uint32_t(__ldcg(defer_next + vblock));
+    cutlass::arch::fence_view_async_shared();
     __syncthreads();
```

The timing below shows no measurable cost.

### 2. The end-of-kernel counter reset has no acquire (`persistent_kernel.cuh` L580-586)

Each CTA does `__threadfence(); atomicAdd(counter + 1, 1u)`, which is the release half. The last CTA then runs `atomicExch(counter, 0u)` with no acquire after it reads `gridDim.x - 1`. So the other CTAs' final `atomicAdd(counter, 1)` are not causality-ordered before the reset. Today only the no-thin-air axiom (PTX 8.10.4) rules out a nonzero counter at the next launch. A fence inside the `if` makes it a plain release/acquire pair:

```diff
     if (atomicAdd(counter + 1, 1u) == gridDim.x - 1) {
+      __threadfence();
       atomicExch(counter, 0u);
       atomicExch(counter + 1, 0u);
```

It costs one fence in one thread per launch.

### 3. Ties and `VLLM_BATCH_INVARIANT` (`fused_mqa_topk.py`, `use_fused_mqa_topk`)

On real GLM-5.3-Flash indexer captures (10 chunks, 50 launches each), 0.24% of rows change their index set between launches. Every differing key ties with the k-th key's 24-bit code (1535 keys) or is one code away (15). No row is ever wrong. So this is the documented tie behaviour, but it happens run to run, not only between fused and dense.

The kernel also depends on chunk composition. The sample stride and tile count come from the chunk's total keys, so a row's candidate set depends on what else is packed with it. `use_fused_mqa_topk` does not check `VLLM_BATCH_INVARIANT`, while the indexer's row sharding does (`indexer.py:266`). Today the flag cannot start a sparse-MLA model anyway, because no backend supports sparse attention with batch invariance. So this keeps the path right for later:

```diff
     return (
         envs.VLLM_USE_FUSED_MQA_TOPK
+        and not envs.VLLM_BATCH_INVARIANT
         and not fp4_cache
```

Could you also add a sentence to the `VLLM_USE_FUSED_MQA_TOPK` help saying that ties at the k-th score can resolve differently between runs?

### Gate reference in packed multi-request chunks (`persistent_kernel.cuh`, `sample_ref`)

FYI: the per-row reference is the row's maximum over sample tile 0, which covers only the start of the gathered chunk. Rows of later requests in a packed chunk get no reference and fall back to absolute bins. With concurrent long prompts, GLM-5.3-Flash produced 130K-key chunks where 11,105 of 15,457 rows have no reference.

On real packed captures this costs nothing: 0 rescans, 0 wrong rows, and fused is 1.46x to 1.65x faster than dense. It would matter on a model with a large score offset, such as GLM-5.2 layer 1, which we could not run. A possible change is to take the reference from the first sample tile that holds the row's own keys. A test where a later request's rows need the reference would also help, since the offset-gate test only covers `starts = 0`. A follow-up PR is fine.

### Nit: `compute-sanitizer --check-tensor-ops` can't run the tests (`fused_mqa_topk.cu`, `make_strided_kv`)

The strided sample map declares `groups * stride` keys, which can exceed `keys` by up to `stride / 2`. As the comment there says, only offset `stride / 2` is ever loaded, so this is safe, and plain memcheck is clean. But memcheck with `--check-tensor-ops` checks the declared footprint. It reports "Access to <K base> is out of bounds" once per CTA and kills the launch (error 719), so `pytest tests/kernels/attention/test_fused_mqa_topk.py` aborts.

If you want that option to work, you could base the map at `ptr + (stride / 2) * kHeadDim` with a dimension-2 extent of 1 and coordinate 0. That keeps the same loads with a footprint inside K. We haven't built it.

Hi @LopezCastroRoberto, we found an issue in the sampled gate on real GLM-5.2 data.

**Problem.** `sample_bin` bins samples by fp16 code >> 5, i.e. 32 bins per power-of-two octave. A bin's width therefore depends only on the score's magnitude: it is about 2.0 at |x| ~ 100. On GLM-5.2 layer 1 every row's top scores sit around +100, and ranks 1024..4096 lie within only 1.6-2.6 of each other, so the gate cannot resolve the threshold and ends up far too low. The result on layer 1 is up to 61K candidates per row, 104-839 of 1024 blocks exactly rescanned (64K..1M keys), and the kernel runs 2.5-3.4x slower than on layer 0. At 256K it is even slower than the dense path.

**Fix.** Bin each row's samples relative to a per-row reference: the row's max over its first sample tile. We bin `x - ref` with one more mantissa bit, which gives 64 bins per octave of the distance and 4096 bins in total, using 16-bit counters so shared memory stays the same. The gate is `ref` plus the bin's lower edge, so it is still a lower bound and the output stays exact.

**Speedup on layer 1** (B200, 8192 rows, top-2048; ms, blocks rescanned in brackets):

| keys | 64K | 128K | 256K | 512K | 1M |
|---|---|---|---|---|---|
| before | 7.21 (92) | 15.03 (278) | 36.08 (602) | 56.46 (614) | 117.30 (839) |
| after | 2.53 (0) | 4.42 (0) | 8.19 (0) | 15.56 (0) | 29.82 (0) |
| speedup | 2.8x | 3.4x | 4.4x | 3.6x | 3.9x |

Layer 1 now runs about as fast as layer 0. Layers 0/2/6/10/14 are unchanged or up to 3% faster (4-14% fewer candidates). Every row is exact up to boundary ties on all 6 layers x 24K..1M. Happy to send the patch (~140 lines in `sample.cuh`, `finish_sample_histogram` and the sample loops).

Hi @LopezCastroRoberto, I, from the LiteTopk team, has the following suggestions to improve this pr:


**Changes**
1. **Per-row offset binning of the gate sample.** Samples are binned as `fp16(x - ref)`, where `ref` is the row's max over its first sample tile (4096 bins in the same shared memory), instead of absolute `fp16(x) >> 5` bins, which are ~2.0 wide at |x| ~ 100. This fixes the gate collapse on GLM-5.2 layer 1 (scores at ~+100 with a narrow top tail), where this PR rescans 104-839 of 1024 blocks.
2. **B200-tuned gates and sample sizes** (slab targets 2816/3328/3584/4096 by length, 16-48 sample tiles). The B300-tuned gates leave a few exact rescans on B200, and those land in the tail; with ours we see none in any measured cell.
3. **Candidate emission:** ballot-compacted per-(warp, row) staging lists instead of per-lane rings, so there is no global-atomic overflow; fully visible tiles skip the per-key bounds.
4. **Candidate drain:** per-row slot counters in shared memory, and one shared atomic per row and interval reserves a contiguous slab range; the store loop has no shuffles or atomics.
5. **UMMA issue:** one elected lane runs a block's whole tile loop and waits for the next tile's KV stage before the current tile's last MMA. This removes one tensor-core bubble per tile (MMA-only time ~1350 -> ~1155 cycles/tile; the bound is 1152).
6. **Short and padding rows** (at most top-k visible keys) get a +inf gate. They are written directly and no longer send their warpgroup's keys through the emission path, which mattered for the partial last block of single-wave launches.
7. **Streaming selection** for launches of up to 196608 keys: one coalesced pass over the candidate slab, with the bracket on the full 24-bit code. The 16-bit bracket sends 59-72% of layer-1 rows to the slow `select_row` fallback.
8. **Fix:** the exact-rescan path's scheduler strides by 4096 blocks, so launches with more than 32768 rows score out-of-bounds blocks (illegal memory access at 40960 rows x 64K keys).

**Kernel time, this PR's head vs ours.** Both kernels are built the same way (`sm_100f`, CUTLASS 4.7.1, DeepGEMM `6ce1c5ec`) and timed in one process with cold L2 and paired, shuffled rounds. Speedup = this PR's time / our time; brackets give this PR's exactly rescanned blocks.

| data | 64K keys | 256K keys | 1M keys |
|---|---|---|---|
| layer 0, 16384-row causal chunks | 1.70x | 1.44x | 1.23x |
| layer 1, 8192-row chunks | 4.11x (104) | 5.10x (602) | 4.45x (839) |
| layer 6, 8192-row chunks | 1.49x | 1.36x | 1.51x (2) |

Layer 0 at 24K / 128K / 512K keys: 2.04x / 1.49x / 1.26x. The layer 1/6 "1M" column is a 1016K-key prompt. Our kernel rescans no block in any of these cells.

The reference implementation is in https://github.com/sgl-project/sglang/pull/46434#differences-from-vllm-pr-60618

@LopezCastroRoberto, adding a concrete memory example to my earlier decode follow-up: the motivation is the **remaining BF16 logits intermediate at high concurrency and large speculative K**, beyond removing the FP32 copy.

We have complementary PRs addressing redundant FP32 logits materialization: [#62172](https://github.com/vllm-project/vllm/pull/62172) for cooperative top-k and [#64138](https://github.com/vllm-project/vllm/pull/64138) for persistent top-k. Direct BF16 consumption still materializes the dense BF16 logits tensor, which contributes to retained CUDA graph pool memory.

For a more representative capacity example, consider the **DeepSeek-V4.1 dense indexer path with 1M logits columns**, rather than V4's 4×-compressed width. The dense BF16 intermediate alone requires approximately `2 × num_requests × (K + 1) × logits_width` bytes for uniform verification, before padding:

| Requests | Speculative K | Query rows | BF16 logits alone |
| ---: | ---: | ---: | ---: |
| 512 | 7 | 4096 | **8 GiB** |
| 1024 | 7 | 8192 | **16 GiB** |

These are **tensor-capacity calculations**, not measured end-to-end allocations or fusion savings. The 8192-row example assumes capture coverage is extended to that size; #63406's current default uniform-decode token cap is 4096. The model-derived 1M-column dense-path capacity is documented in [#64138](https://github.com/vllm-project/vllm/pull/64138); it does not describe candidate-consuming sparse-logits layers. The [memory analysis in #63406](https://github.com/vllm-project/vllm/pull/63406) provides the measured graph-memory context. Importantly, this BF16 intermediate remains even after removing all redundant FP32 copies.

I'm preparing an SM100 decode row-chunking PR, which is not pushed yet, to bound this allocation. Chunking may trade memory for additional scheduling/scoring/top-k launches and smaller execution batches; capturing those launches in a CUDA graph does not eliminate their GPU work.

A decode extension of fused scoring + top-k could potentially avoid materializing the full BF16 matrix and offer a better memory/latency trade-off. The actual graph-pool savings and latency benefit still need matched decode benchmarks, including the fused implementation's own workspace. High-concurrency, large-K verification would be a useful follow-up case to evaluate.
