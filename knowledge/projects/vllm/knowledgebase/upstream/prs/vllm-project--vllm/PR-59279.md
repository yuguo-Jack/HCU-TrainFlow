# [Model][DCP] Support Qwen4Exp QSA

[Upstream PR](https://github.com/vllm-project/vllm/pull/59279) · state: open · merged: False

## Original PR description

## Purpose

Enable decode context parallelism (DCP) for Qwen4Exp QSA.

Each rank reads its own shard of the main KV cache. The QSA selector and its side caches stay replicated on every rank. The ranks then combine their partial results with the base-2 log-sum-exp convention that QSA uses.

Four further changes make this work:

- The selector and the main KV cache share one block table. In separate groups the selector takes most of the blocks that a request needs, and DCP loses capacity instead of gaining it.
- A packed compressed cache binds one whole manager block. Its kernel blocks are mapped afterwards through the stride between manager blocks. Without this the server stops at startup, because a packed block cannot be cut into evenly spaced kernel blocks.
- The QSA side caches skip their stores when the block table points at the null block.
- Every attention metadata builder in a group takes the block table row width that the runner allocated. A replicated layer in a DCP-sharded group has a larger block than the group, so a builder that derives the width from its own layer spec sizes its kernel block table too small. The mapping now rejects a row that does not fit instead of writing past it.

An empty DCP batch now returns both an output tensor and a log-sum-exp tensor.

Draft #61242 covers the same feature with a sharded selector. This PR keeps the selector replicated, so selection stays identical to DCP=1.

@sungsooha While testing this branch on 8 × A100 for the follow-up, we found an engine start-up failure. It happens on `c9de36da9` with no other change.

### Summary

- **Problem:** at DCP 4 the engine fails at start (CUDA graph capture) with `unflatten: Provided sizes [140, -1] don't multiply up to the size of dim 1 (548)`. At some other shapes there is no error, but the selector's kernel block table is wrong.
- **Cause:** two places size the same block-table row with different block sizes. The runner uses the group block (480): 140 columns. `AttentionGroup.create_metadata_builders` uses the replicated selector's own block (480 × 4 = 1920): 137 columns. They round 137 blocks to different multiples.
- **Fix (how):** compute the row width once, from the group spec, with one helper (`get_kv_cache_group_block_table_width`). The runner uses it, and `init_attn_backend` passes the same number to `create_metadata_builders` (new optional `block_table_width`), so the kernel block table is always runner width × (layer block / kernel block). Here: 140 × 4 = 560.
- **Result so far (CPU, vLLM code of both branches imported as is, 3,564 shapes):** before the fix 1,276 shapes raise and 75 give a wrong table without an error; after the fix all 3,564 are correct, including the production shape and the short shape that was silently wrong. **GPU check is pending** (details at the end).

### Proposed fix

Commit [`8e212b229`](https://github.com/kimseunghyun-kr/vllm/commit/8e212b229) on top of `c9de36da9` (branch `kimseunghyun-kr:qsa-dcp-59279-blockfix`).

**Idea:** compute the row width in one place, from the group spec, and give that same number to the builders.

1. New helper `get_kv_cache_group_block_table_width(group_spec, vllm_config, max_len)` in `vllm/v1/worker/block_table.py`. It is the runner's formula from step 2, moved into one function. The V2 runner now calls it.
2. `init_attn_backend` calls the same helper for each group and passes the result to `create_metadata_builders`:
   ```python
   block_table_width = get_kv_cache_group_block_table_width(
       kv_cache_config.kv_cache_groups[kv_cache_group_id].kv_cache_spec,
       vllm_config,
       vllm_config.model_config.max_model_len,
   )
   group.create_metadata_builders(..., kernel_block_size=kernel_block_size,
                                  block_table_width=block_table_width)
   ```
3. `create_metadata_builders` uses that width when it is given, and keeps the old per-layer formula when it is not:
   ```diff
   -   max_num_blocks = self.kv_cache_spec.max_num_blocks_per_req(...)
   -   width = get_block_table_width(max_num_blocks, self.kv_cache_spec.block_size)
   +   if block_table_width is None:
   +       max_num_blocks = self.kv_cache_spec.max_num_blocks_per_req(...)
   +       block_table_width = get_block_table_width(max_num_blocks, self.kv_cache_spec.block_size)
   +   width = block_table_width
       width *= self.kv_cache_spec.block_size // kernel_block_size
   ```

So the kernel block table is always "runner row width × blocks per kernel block". In our case: 140 × 4 = 560 columns.

Tests added in `test_qsa_dcp_cache_policy.py` (CPU): the production shape (group 140 vs selector spec 137), and a full-width row mapped at DCP 4.

Not changed: the V1 runner path. Encoder-decoder models (the runner widens their rows past `max_model_len`) behave as before.
