# [Bugfix] Disable CUTLASS FP4 MoE backend on sm_110

[Upstream PR](https://github.com/vllm-project/vllm/pull/62275) · state: closed · merged: True

## Original PR description

## Overview

`CutlassExpertsFp4` claims device capability family 110, so NVFP4 MoE auto-selection picks
`VLLM_CUTLASS` on sm_110 (Jetson AGX Thor) and faults in `profile_run` instead of falling
back to Marlin.

110 has been in this predicate since #33417 normalised it from
`has_device_capability((10, 0))`, a `>=` check that sm_110 already passed. That PR was about
SM120 and was tested on an RTX PRO 6000. Doesn't look like 110 was ever tried on Thor.

## Claims

- NVFP4 MoE auto-selection on sm_110 reaches a backend that works instead of one that faults.
- Scoped to the MoE predicate. Dense NVFP4 (`cutlass_scaled_mm_supports_fp4`) is untouched
  and still works on sm_110.
- No behavioural change elsewhere: sm_100 and sm_120 evaluate identically.
- No regression in `tests/kernels/moe/test_cutlass_moe.py`.

## Validation

Jetson AGX Thor, sm_110, 20 SMs, 122.8 GiB unified.

`CutlassExpertsFp4._supports_current_device()` returns True before, False after. Checked
against 837e87e1c5.

Before, serving `RadixArk/Qwen3.8-Flash-Next-NVFP4` (512 experts):

```
Error: Failed to initialize the TMA descriptor 700
RuntimeError: run_fp4_blockwise_scaled_group_mm_sm100,
  csrc/libtorch_stable/quantization/fp4/nvfp4_blockwise_moe_kernel.cu:410,
  Failed to initialize GEMM: status=7 workspace_size=261120
  num_experts=512 M=81920 N=1280 K=2560
```

After, the run gets through load, `profile_run` and KV alloc, then stops at an unrelated QSA
kernel on the same device (#56084). With that one fixed as well it serves: 0 errors, coherent
output at temperature 0.

Ran `test_cutlass_moe.py` on Thor before and after the patch, no failures either time. The
`[nvfp4]` padded-routes case goes from pass to skip, since the backend is no longer offered
on this device.

### Reproducing

You only need an sm_110 device to check the predicate.

The serving runs don't reproduce on stock vLLM. That checkpoint is ~126 GiB and the board has
122.8 GiB, so these runs mmap the 47.7 GiB PLE n-gram table from NVMe instead of holding it
resident. It's a lookup table, never a GEMM operand, so it can't affect which backend gets
picked. No upstream equivalent, #54129 was closed unmerged.

No sm_110 runner in CI, so no test added and everything above was run on hardware.

## Details

**Root cause.** `select_nvfp4_moe_backend` walks an ordered list and takes the first backend
that claims support. `VLLM_CUTLASS` sits above `MARLIN`. sm_90 falls through because it fails
the FP4 check; sm_110 passes and stops there. The fault lands in `profile_run`, after
selection, so there's no retry.

**Scope.** `cutlass_scaled_mm_supports_fp4(110)` is correct for dense, confirmed by calling
`cutlass_scaled_fp4_mm` on device. Only the grouped kernel is broken, so the MoE predicate is
the right place to fix it, not the global helper.

**Tradeoff.** Small shapes do work on CUTLASS here, the 4-expert unit test passes unpatched,
and those now go to Marlin, which is W4A16 and slower on prefill. Taking that: selection
happens once, before shapes are known, and it faults at real MoE sizes. The failure is
shape-dependent too, at 16k context the same call dies in the torch stable-ABI dispatcher
instead of TMA init.

**Why not `--moe-backend marlin`.** It's global, and this checkpoint leaves `mtp.*`
unquantized, so it dies earlier:

```
ValueError: moe_backend='marlin' is not supported for unquantized MoE.   (mtp.py:201)
```

Auto-selection has to be right because the flag can't express per-layer choice.
