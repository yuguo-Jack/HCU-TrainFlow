# [Kernel] Batch invariance: pin row-invariant GEMM paths

[Upstream PR](https://github.com/vllm-project/vllm/pull/62192) · state: open · merged: False

## Original PR description



## Overview

Under `VLLM_BATCH_INVARIANT=1`, pins four GEMM paths that could still pick a batch-dependent schedule: the MoE router, FlashInfer's FP8 `bmm`, W4A16 NVFP4 linears, and two Blackwell persistent-matmul shapes.

This is one self-contained part of #62017 by @aoshen02, split out unchanged for separate review. The commit keeps his authorship. An earlier revision was reviewed as aoshen02/vllm#92.

## Claims

Everything below applies only under `VLLM_BATCH_INVARIANT=1`; without it, behavior is unchanged.

- **Router.** For a BF16 router weight with FP32 logits (`GateLinear` without bias), the logits come from one persistent matmul, `mm_batch_invariant(x, W.T, out_dtype=torch.float32)`. That keeps one K order at every M, and the FP32 accumulator is rounded only once. Previously this case fell through to `F.linear`, which rounds to the weight dtype first, because #59985 turns the specialized tiers off under BI.
- **`mm_batch_invariant`** gains an optional `out_dtype`. The tile config still follows the input dtype; only the epilogue cast changes. This applies to both the CUDA and the XPU descriptor kernels.
- **FP8 `bmm`.** `flashinfer_scaled_fp8_mm` pins FlashInfer's `bmm_fp8` backend to `cutlass`, because `"auto"` may choose a different backend per problem shape.
- **W4A16 NVFP4 linears** use the Humming kernel. Selecting another backend with `--linear-backend` logs a warning and is overridden.
- **Blackwell (sm100) BI matmul table.** Two tuned M buckets are added for the `(4608, 2688)` and `(2688, 4096)` shapes (Nemotron-H `qkv_proj` and `o_proj`).
- **CI.** The B200 batch-invariance step also triggers on `vllm/utils/flashinfer.py`.

## Details

- **Scope.** The router and W4A16 changes apply to every model under BI, not only Nemotron-H. They change which kernel runs, and therefore the bits, for BI users with a BF16 router and FP32 logits, or with W4A16 NVFP4 linears. They still give batch-invariant results.
- **Throughput.** Humming and the pinned `cutlass` FP8 `bmm` are chosen for invariance, not speed. Throughput under BI was not measured for this split.

Related open PRs:
- #60047 registers the `aten::mm.dtype` overloads for batch invariance, so that `torch.mm(..., out_dtype=...)` hits the Triton overrides. That PR is complementary: the router here calls `mm_batch_invariant` directly.
- #60681 wraps the `GateLinear` `ll_bf16_gemm` tier in a custom op. It touches nearby code, but not the BI branch added here.
