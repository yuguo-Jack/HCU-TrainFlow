# [Bugfix][Benchmark] Harden SSE handling: split separators and CRLF framing

[Upstream PR](https://github.com/vllm-project/vllm/pull/61534) · state: open · merged: False

## Original PR description


## Purpose

The two follow-ups from the #51172 review, both in `StreamedResponseHandler`:

1. **Early emit after a split separator** (@esmeetu's suggestion there). The early-emit path only fires when the buffer starts with `data: `. When a `\n\n` separator is split across reads, the leftover `\n` at the front of the buffer makes the next event wait for its own separator instead of being emitted the moment its JSON is complete. Output is unaffected; the event's timestamp (TTFT/ITL sample) is late by up to one read. Fix: check and emit on the buffer with leading newlines stripped.

2. **CRLF/CR event separators** (found by @HarshShroff while validating #51172). Events are split on `\n\n` only, but the SSE spec also allows `\r\n` and `\r` line endings (sse-starlette defaults to `\r\n`). Against such a server no separator is ever found and every request fails. vLLM's own server emits `\n\n`, so this only bites third-party OpenAI-compatible backends — which `vllm bench serve` explicitly targets. #60177 fixes this in the Rust client; this is the Python side. Fix: wrap the existing incremental UTF-8 decoder in `io.IncrementalNewlineDecoder(translate=True)`, which converts `\r\n`/`\r` to `\n` and correctly handles a `\r\n` split across reads (a per-chunk `str.replace` would turn a split `\r|\n` into a spurious `\n\n` separator).

## Test Plan

```
pytest tests/benchmarks/test_endpoint_request_func_timing.py
```

- New handler test: feed `data: {...}\n` then `\ndata: {...}`, assert the second event is emitted on arrival.
- The split-invariance test from #51172, parametrized over the three spec separators (`\n\n`, `\r\n\r\n`, `\r\r`): every two-way split must succeed with byte-identical output, for completions, chat, and audio.

## Test Result

Before: the early-emit test holds the second event until a later separator; every crlf/cr variant fails at all 113–129 split points per endpoint (matches @HarshShroff's 141/141 measurement on the equivalent stream). After: 28/28 in the file pass.
