# [Rust Frontend] Advance streamed completion text_offset by reported tokens

[Upstream PR](https://github.com/vllm-project/vllm/pull/63764) · state: closed · merged: True

## Original PR description

## Overview

Since vllm-project/vllm#60668, Python's streaming `/v1/completions` advances each choice's next `text_offset` by the tokens it just reported, not by the streamed delta text, so streamed offsets equal the non-streaming ones. The Rust stream still advanced by the delta text. This PR advances it by the reported tokens.

## Claims

- Streamed completions `logprobs.text_offset` equals the non-streaming offsets when the detokenizer holds text back (stop strings, incomplete UTF-8).
- An echoed prompt still starts the offset at the prompt's length.

## Validation

Commands from `.buildkite/scripts/run-rust-frontend-cargo-ci.sh` (`style-clippy` and `test`), run from the repo root:

```
cargo fmt --manifest-path rust/Cargo.toml --all -- --check   # ok
cargo sort --workspace --check rust                          # ok
cargo deny --manifest-path rust/Cargo.toml --config rust/deny.toml check bans   # ok
cargo clippy --manifest-path rust/Cargo.toml --workspace --all-targets --all-features --locked -- -D warnings   # ok
cargo nextest run --manifest-path rust/Cargo.toml --workspace --all-features --locked --no-fail-fast
# 2311 tests run: 2311 passed, 13 skipped
```

- `completion_chunk_stream_advances_text_offset_by_reported_tokens` ports Python's case from `tests/entrypoints/openai/completion/test_completion_text_offset.py` (tokens `abc`, ` de`, `!` with text deltas `ab`, `c d`, `e!`) and adds a two-byte character split across two tokens. On `main` they stream `[0, 2, 5]` and `[0, 0, 1]`; with this change `[0, 3, 6]` (Python's value and Rust's own non-streaming value) and `[0, 1, 2]`.

## Details

Root cause: `completion_chunk_stream` advanced `visible_text_len` by the streamed delta text. The detokenizer holds text back for stop strings and incomplete UTF-8, so the delta text lags the tokens already reported, and the next chunk's offsets started too early.

Change: the stream keeps `next_text_offset` and advances it to the offset just past the last token of each chunk's `logprobs` (new `text_end_offset`, also used by the non-streaming echo path, which already did this inline). The offset is a property of the OpenAI completions `logprobs` wire shape, so it stays in the completions route next to `decoded_logprobs_to_openai`; the text layer's holdback is correct and unchanged.

The UTF-8 case pins that offsets follow the token strings Rust reports. Python additionally repairs split-character token strings in logprobs, which this PR does not touch.

Not a duplicate: open vllm-project/vllm#63607 (hidden stop-token logprobs) edits the same streaming loop but not the offset advance; the two overlap only textually.
