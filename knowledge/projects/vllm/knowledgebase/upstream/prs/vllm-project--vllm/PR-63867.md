# [ROCm][Perf] Skip masked-out context tiles for sliding-window models in Triton prefix-prefill

[Upstream PR](https://github.com/vllm-project/vllm/pull/63867) · state: open · merged: False

## Original PR description

## Overview

On sliding-window layers, the Triton prefix-prefill kernel now starts its context loop at the first tile the window can reach instead of tile zero. The optimization applies to sliding-window layers, where some models — such as Gemma2/3, Mistral/Zephyr, GPT-OSS, MiniMax-M2, Cohere2 and Granite — cap how far back a layer can attend; tokens older than the window are already masked to `-inf`, so skipping them changes nothing about the output. Only `ROCM_ATTN` calls this kernel (through `chunked_prefill_paged_decode`), with query length > 1: chunked prefill, cached-prefix prefill and speculative verification. CUDA's Triton backend uses `triton_prefill_attention.py` and is unchanged.

## Claims

On one MI300X (ROCm 10.0, Triton 3.8.0) unless marked MI325X:

- Same output: `torch.equal` to the kernel without this PR on 15 shapes, with KV caches under and over 2 GB, and on all 179 `context_attention_fwd` calls recorded while serving zephyr-7b-beta. Prompt logprobs match on zephyr-7b-beta and gemma-3-1b-it for prompts up to 30,000 tokens.
- MI325X: bit-identical output to the kernel without this PR on 3,331 launches, including sinks, non-causal attention, cached K/V, FP8 KV cache and output, and block sizes 48, 544 and 1056.
- Serving zephyr-7b-beta: TTFT 1.69x faster at 32,000-token prompts and 1.46x at 16,384. MI325X, gemma-3-1b-it: 2.18x at 32,000 and 1.40x at 16,384.
- Up to 38.4x faster kernel time at a 32,000-token context (head size 256, 512-token window, KV cache over 2 GB).
- Where nothing is skipped: 0.99-1.05x kernel time (KV cache over 2 GB), and zephyr-7b-beta TTFT at 2,048-token prompts is unchanged.
- No new option, env var or kernel variant.

## Details

- A fully masked tile is already a no-op, so skipping it changes nothing. The start comes from the lowest query row the program owns, rounded down to `lcm(32, block size)`: tiles keep the boundaries they have without this PR, and the block table moves by whole blocks.
- The loop counts from 0 over the remaining context, with the block table offset. On MI325X with KV caches over 2 GB, a loop that starts at a runtime value is 4-16% slower at unroll 4, because the V-cache loads lose `dwordx4` in the 64-bit addressing variant. b56cb2a's slowdown came from unroll 1 at head sizes 64 and 128: counting from 0 at unroll 1 is within 1% of it.
- The start is clamped to the context length; with a start past the end, an unrolled `tl.range` still runs leftover iterations.
- On gfx942 (`get_cdna_version() == 3`), sliding-window layers with head size above 128 use `num_unroll_cache=1`, since unroll 4 spills there (head size 256, KV cache over 2 GB: 268 bytes of scratch per thread without this PR, 36 with it). Other architectures keep unroll 4; compiled for gfx950, that variant has no scratch with or without this PR. MI355X was not measured.
- No `SWA_SKIP` constexpr; `CTX_SKIP_ALIGN` follows the KV block size. Each zephyr-7b-beta server above compiles one `_fwd_kernel` variant at warmup and each gemma-3-1b-it server two (sliding and global layers); none compile another after the first 32,000-token prompt, the benchmarks or GSM8K, with and without this PR.
- CI runs this test file on NVIDIA L4 and MI300. The new test cases have not been run on NVIDIA yet; the head size 256 cases are skipped there.
- Not a duplicate: #61433 ranks unified attention above `ROCM_ATTN` for spec decode and hybrid models; this PR speeds up `ROCM_ATTN` where it is still used. Related: #62605 changes this kernel's grid; happy to rebase either way.

When `block_start_loc >= SLIDING_WINDOW`, `ctx_loop_start` can pass `cur_batch_ctx_len`. With `loop_unroll_factor=4`, ROCm Triton still runs up to 3 iterations of the loop, sometimes at negative `start_n`. Those read another request's KV blocks; in my repro (W=16 or 40, short context) that turned 896 of 1024 output rows into NaN. Clamping before rounding fixes it at the same speed:
```suggestion
        ctx_loop_start = tl.maximum(
            0, cur_batch_ctx_len + block_start_loc - SLIDING_WINDOW + 1
        )
        ctx_loop_start = tl.minimum(ctx_loop_start, cur_batch_ctx_len)
        ctx_loop_start = (ctx_loop_start // BLOCK_SIZE) * BLOCK_SIZE
```
