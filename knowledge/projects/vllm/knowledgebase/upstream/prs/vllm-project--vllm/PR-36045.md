## Original PR description

…race analyzer

- iterations.py: batch iteration benchmark for precise prefill/decode measurement with compilation warmup, server-side step stats, and trace analysis
- api_router.py: debug endpoints for profiling, traces, step_stats, batch_info
- core.py: engine step timing accumulation (get_step_stats/reset_step_stats)
- tpu_trace_analyzer.py: TPU trace parser for kernel breakdown by category

Server-side step timing measures dispatch-to-completion for each engine step, filtered to steady-state only. Results show both server and client Per-Iter latency plus per-category kernel breakdown from traces.

## Code Review

This pull request introduces a sophisticated new benchmark for measuring prefill and decode performance with fine-grained control over the engine's scheduler. It adds several new debug endpoints to the API server for profiling, controlling scheduling, and gathering stats. The changes are extensive, touching core engine components, and include a new TPU trace analyzer. My review focuses on the correctness of the new benchmark script and the supporting infrastructure. I've identified an issue in the benchmark script where a hardcoded value is used instead of a dynamically fetched configuration from the server, which could impact the accuracy of the benchmark results. The rest of the changes appear to be well-implemented.

The `fetch_server_config` function is not fetching `max_num_batched_tokens` and `max_num_seqs` from the server configuration. This is inconsistent with the `ServerConfig` dataclass and leads to `run_benchmark` using a hardcoded default for `max_num_batched_tokens`. This can result in inaccurate benchmark measurements for the DP>1 decode mode.

```suggestion
            return ServerConfig(
                data_parallel_size=data.get("data_parallel_size", 1),
                tensor_parallel_size=data.get("tensor_parallel_size", 1),
                pipeline_parallel_size=data.get("pipeline_parallel_size", 1),
                world_size=data.get("world_size", 1),
                real_data_parallel_size=data.get("real_data_parallel_size"),
                real_tensor_parallel_size=data.get("real_tensor_parallel_size"),
                max_num_batched_tokens=data.get("max_num_batched_tokens"),
                max_num_seqs=data.get("max_num_seqs"),
            )
```

- gemini-code-assist[bot] · comment · 2026-03-04T20:29:45Z · [source](https://github.com/vllm-project/vllm/pull/36045#discussion_r2885938240)

File: `vllm/benchmarks/iterations.py` · line None

![high](https://www.gstatic.com/codereviewagent/high-priority.svg)

The `max_batched` variable is hardcoded. For more accurate benchmark results, it should use the `max_num_batched_tokens` value fetched from the server configuration. This is particularly important for calculating `ramp_up_tokens` correctly in DP>1 decode mode. A fallback to a default value is reasonable if the server doesn't provide this configuration.

```suggestion
            max_batched = server_config.max_num_batched_tokens or 10240
```
