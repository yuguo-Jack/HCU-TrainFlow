# [Bugfix][LoRA][MoE] Process reloaded weights of LoRA-wrapped MoE layers

[Upstream PR](https://github.com/vllm-project/vllm/pull/63319) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

With LoRA enabled, a layerwise weight reload (`reload_weights` with checkpoint-format weights, as used for RL weight sync) skips the post-load processing of quantized MoE experts. This PR makes `FusedMoEModularMethod.process_weights_after_loading` delegate to the wrapped quant method.

## Claims

- After this change, reloading a LoRA-enabled MoE model whose quant method converts weights after loading (e.g. compressed-tensors W4A16) gives the same base and adapter outputs as before the reload. On main the reload fails with a shape mismatch. If a kernel layout has the same shapes as the checkpoint, checkpoint-format tensors can instead stay in place silently.
- When the wrapped method builds a new kernel, the new experts and prepare/finalize receive the existing LoRA context, and the LoRA layer keeps using the same `FusedMoEKernel` object. If the new object cannot take the context, this fails instead of dropping the context silently. The test below does not cover this part (see Validation).
- Methods that keep their kernel on reload (e.g. unquantized) behave as before.

## Validation

Test `test_reload_weights_with_lora_moe` in `tests/model_executor/model_loader/test_reload.py` (CUDA only), on `RedHatAI/Qwen3-30B-A3B-quantized.w4a16` (compressed-tensors WNA16 MoE, `TritonWNA16Experts` on GB300), in eager mode:
- start the model with LoRA and record prompt logprobs, without an adapter and with `jeeejeee/qwen3-moe-text2sql-spider`;
- check that the adapter changes the logprobs;
- reload the model's own checkpoint;
- re-request the adapter, which the reload removed, and check that both logprob lists are exactly unchanged.

The test sets `VLLM_BATCH_INVARIANT=1`. Without it, repeating the same request in one process changed prompt logprobs by up to 3.0 (mean 0.2 to 0.4), so an exact comparison would be flaky. Expert names are sent in the LoRA-wrapped form (`experts.N.down_proj.base_layer.weight`), which is what `RoutedExperts` matches once LoRA has wrapped the layer. Eager mode makes sure the logprobs after the reload come from the rebuilt kernel.

```bash
pytest -v tests/model_executor/model_loader/test_reload.py::test_reload_weights_with_lora_moe
```

Run on 1x GB300 with the nightly image at `8e2beaa3bf`, which is older than this PR's base. These files are the same in both: `fused_moe_modular_method.py`, `vllm/lora/layers/fused_moe.py`, `vllm/model_executor/model_loader/reload/`, and the base version of `test_reload.py`.

| `fused_moe_modular_method.py` | Result |
|---|---|
| base | FAILED: `The size of tensor a (1024) must match the size of tensor b (256) at non-singleton dimension 2` |
| this PR | PASSED |
| this PR without the LoRA-context transfer | PASSED |

What the test does not cover: the LoRA-context transfer. Without it, an instrumented run showed that after the reload all 48 MoE layers run the rebuilt `TritonWNA16Experts` with no LoRA context, which skips the expert LoRA. Even so, the adapter's logprobs matched the pre-reload values exactly. I have not found out why the expert part of this adapter has no visible effect in this setup, so the transfer is kept based on the code path (`TritonExperts`, `MarlinExperts` and the TRT-LLM LoRA experts read `_lora_context` in `apply`), not on a test.

I did not extend `test_reload_weights` instead. Its MoE cases are DeepSeek-V3 debug checkpoints, and with LoRA enabled, a checkpoint-format reload of those fails before reaching this code, in `DeepseekV2` weight loading (`KeyError: 'layers.0.mlp.gate.e_score_correction_bias'`, because the LoRA-wrapped gate's parameters are named `gate.base_layer.*`). This happens on main too and is not changed here.

The test is not marked `slow_test`, so the H200 Model Executor step selects it. It loads a ~16 GB checkpoint and a ~1.7 GB adapter.

`pre-commit` hooks `ruff-check`, `ruff-format`, `check-forbidden-imports` and `mypy` (Python 3.11) pass on the changed files.

Other checks, outside the test:
- **Different checkpoint state:** I reloaded a copy of the checkpoint with expert scales perturbed, back and forth, with CUDA graphs on and off. After returning to the original weights, base and adapter prompt logprobs matched a cold start within run-to-run noise. This is the same result as reloading the same weights.
- **Reload to the perturbed state:** after this reload, outputs differed from a cold start of the perturbed checkpoint (mean |Δlogprob| ≈ 0.5, against a noise level of ≈ 0.06). The expert parameters were equal to the cold start. The same difference appears **without LoRA**, so it is not caused by this change.
- **Kernel-format reload:** a checkpoint reload followed by a kernel-format reload (`is_checkpoint_format=False`) gives wrong outputs in eager mode. Rebuilt kernels keep references to the temporary tensors from the checkpoint reload. With CUDA graphs the outputs are correct. This also happens **without LoRA**, where the unwrapped method rebuilds its kernel the same way.

Not run: an end-to-end RL weight sync on this head, NVFP4 or other backends in the test (no NVFP4 MoE backend supports batch-invariant mode), and EP/DP.

## Details

Root cause: `FusedMoEWithLoRA` replaces the experts' quant method with `FusedMoEModularMethod`, which wraps the original method and holds the kernel that the LoRA layer also holds. The wrapper does not override `process_weights_after_loading`, so it is the base no-op. On the first load this does not matter, because the wrapper is installed after processing. On a layerwise reload, the reload code calls the wrapper's no-op and then copies the unprocessed checkpoint-format tensors into the kernel tensors.

Fix: the wrapper calls the wrapped method's `process_weights_after_loading`. Most quantized methods build a new kernel there. In that case the wrapper:
- passes the LoRA context of the current experts and prepare/finalize to the new ones (the LoRA layer sets it only once, at creation),
- puts the new kernel's `impl` into the existing `FusedMoEKernel`,
- points the wrapped method at that kernel and refreshes `moe_quant_config`.

This follows what the unwrapped method does on reload. The kernel-format reload issue above, and graph-captured tensors that belong to replaced experts (e.g. the TRT-LLM MXFP4 experts' `gemm1_alpha`), apply to that shared rebuild-on-reload behaviour as well. For GPT-OSS with LoRA, the reload fails before processing, in the model's weight-name mapping (`KeyError: 'layers.0.mlp.experts.w2_bias'`).

A side note, not changed here: when the checkpoint names of expert weights do not have the `base_layer.` part, the weights of LoRA-wrapped experts are skipped during a reload. A warning (`RoutedExperts: Failed to load weights`) is logged and no error is raised.
