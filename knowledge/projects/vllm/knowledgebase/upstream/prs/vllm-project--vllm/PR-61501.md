# [Perf][Mamba] Opt-in FlashInfer SSD prefill scan; per-step ReplaySSM seed

[Upstream PR](https://github.com/vllm-project/vllm/pull/61501) · state: open · merged: False

## Original PR description



## Overview

Adds an opt-in FlashInfer fused SSD scan for Mamba2 prefills (`--mamba-prefill-backend flashinfer`)
and draws the ReplaySSM stochastic-rounding seed once per step instead of once per layer. This PR is
part of a series that brings piecewise CUDA graphs to Mamba2 prefill steps, and it is stacked on
#61497. Tested with #61293 applied, but it does not depend on it. Requires a FlashInfer build with
flashinfer-ai/flashinfer#6100, which is not in a release yet.

## Claims

- Up to 1.11x output throughput (OTPS/gpu) over #61497 on 1x B200 with
  Nemotron-3.5-Lightning-NVFP4-W4A4 and MTP=2: 1.06-1.11x at concurrency 8-32, 1.05-1.06x at 64-128
  and 1.03x at 1-4.
- The FlashInfer scan takes 2 launches per layer instead of 5, and host time per scan drops from 174
  us to 97 us (214 us to 125 us for continued prefills with initial states).
- One seed launch per step instead of one per ReplaySSM layer (23 to 1 on this model), in both eager
  mixed steps and the decode CUDA graph.

## Validation

End-to-end serving throughput, before vs after, on the same node, served back-to-back with identical
flags except the new one:

- **Before:** `main` + #61293 + #61497. **After:** the same, plus this PR, with

- **Hardware:** 1x B200, TP1.
- **FlashInfer:** upstream main at `2a2cceab0`, which includes flashinfer-ai/flashinfer#6100

## Details

Mamba2 prefills run the chunked SSD scan as 5 Triton launches per layer (cumsum, chunk state, state
passing, bmm, chunk scan). Continued prefills add a gather and a `torch.where` for their initial
states. In eager prefill and mixed steps, these launches and their host overhead add directly to
step latency. FlashInfer's fused SSD (`SSDCombined`, Cake backend) runs the scan in 2 launches from
the packed-varlen `cu_seqlens` and derives its chunk metadata on the device.

Changes:

- `--mamba-prefill-backend {triton,flashinfer}` (`MambaConfig.prefill_backend`, default `triton`).
  Prefills that store Mamba checkpoints need every chunk state, so they keep the Triton scan.
- `mamba_chunk_scan_flashinfer()` (`ops/ssd_flashinfer.py`):
  - gathers initial states (one launch) only when some sequence has one, and otherwise starts from
    a zero state;
  - runs one `SSDCombined` runner per (stream, heads, groups, state dtype, initial states), so final
    states come out in the cache dtype;
  - scatters each final state into its cache slot.
- The gather and scatter kernels do not specialize `indices_ptr` on alignment. Its alignment changes
  with the number of decode rows, so this avoids new compiles while serving.
- The mixer keeps a bfloat16 copy of `D` for FlashInfer, refreshed when the parameter changes.
- The backend needs SM100/SM103, bfloat16 activations, head dim 64 and state size 128 (the shapes
  FlashInfer compiles). `MambaConfig` and `MambaMixer2` reject other setups, and the SSD warm-up runs
  both FlashInfer variants.
- ReplaySSM seed: with `--enable-mamba-cache-stochastic-rounding`, each FlashInfer ReplaySSM layer
  drew its Philox seed with its own `torch.randint`. The layers now read their seeds from slots of
  one shared buffer, which the first layer refreshes with a single `random_()` per step. Every layer
  still gets an independent seed each step.
