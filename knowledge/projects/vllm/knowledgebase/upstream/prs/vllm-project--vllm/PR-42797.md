# [Bugfix] Avoid HTTP 200/null responses on client disconnect

[Upstream PR](https://github.com/vllm-project/vllm/pull/42797) · state: closed · merged: False

## Original PR description

## Purpose

Fixes #42794.

`with_cancellation` currently returns `None` when its disconnect listener wins the race against the wrapped route handler. For FastAPI routes without an explicit response model, that `None` return value is serialized as a successful HTTP 200 response with JSON body `null`.

This can surface as intermittent empty/null successful responses. We hit it through `/v1/audio/transcriptions` with long audio uploads: the server received the full multipart body, scheduled no engine request, and returned `200 null`; the client reported a broken pipe/write-body failure.

This PR changes the disconnect path to raise `asyncio.CancelledError` instead of returning `None`, so the disconnected-client path is represented as cancellation and FastAPI does not serialize a malformed successful response.

This is closely related to the closed, unmerged PR #32945, which identified the same root cause and proposed the same core fix. It also relates to #10087 / #11190, which introduced `with_cancellation` to avoid polling `request.is_disconnected()` with middleware.

## Changes

- Replace the final `return None` in `with_cancellation` with `raise asyncio.CancelledError("Client disconnected")`.
- Add a focused regression test for the decorator.
- Add an ASGI-level FastAPI regression test that sends a complete request body followed by `http.disconnect` and verifies the app does not emit `HTTP 200` with body `null`.
