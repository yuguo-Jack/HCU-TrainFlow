# [ROCm][DP] QuickReduce combine for allgather/reducescatter MoE

[Upstream PR](https://github.com/vllm-project/vllm/pull/64428) · state: open · merged: False

## Original PR description



## Overview

Opt-in `VLLM_ROCM_DP_MOE_QUICK_REDUCE=1` (ROCm, default off): the `allgather_reducescatter` MoE combine under data parallelism uses a QuickReduce all-reduce of the gathered output plus this rank's slice, instead of an RCCL bf16 reduce-scatter. Measured on MI355X DP groups of 2, 4 and 8; for groups of 4 and 8 it applies above a few MB (see Details).

## Claims

- The combine is ~2.5x faster with INT4 QuickReduce than the RCCL bf16 reduce-scatter on a 2-GPU MI355X pair.
- DeepSeek-V4.1-Flash DPATP2 (attention TP1 × DP2) step time is 3–5% lower in decode, prefill and mixed steps.
- Against the serving baseline (AITER's custom reduce-scatter where it accepts the message, RCCL otherwise), QuickReduce INT4 is 1.1–1.7x faster at 2 ranks at every size, and 1.1–1.7x (4 ranks, from 5 MB) and 1.1–1.6x (8 ranks, from 10 MB) faster above the crossover. Below it AITER's reduce-scatter is faster, so the combine's QuickReduce defaults to a minimum size of 4 MB at 4 ranks and 8 MB at 8 ranks.
- Default off. Generic all-reduces on the DP group keep their backend. Tensors QuickReduce cannot take fall back to the reduce-scatter.

## Details

- The DP group gets its own `QuickAllReduce` (`moe_qr_comm`) instead of `qr_comm`, so only the MoE combine uses the quantized codec. `AgRsAll2AllManager.combine` / `combine_into` try it first and keep the reduce-scatter otherwise.
- **Tradeoffs:**
  - The all-reduce moves the whole gathered tensor rather than 1/world of it, which still wins on MI355X's fully connected xGMI once the tensor is a few MB. Below that (4 ranks: 4 MB, 8 ranks: 8 MB by default) AITER's custom reduce-scatter is faster and is kept; `VLLM_ROCM_QUICK_REDUCE_MIN_SIZE_BYTES_MB` overrides the default.
  - QuickReduce casts bf16 to fp16 by default (`VLLM_ROCM_QUICK_REDUCE_CAST_BF16_TO_FP16`), so values above ~6.5e4 are out of range: the FP/INT8/INT6 return inf/NaN and INT4 returns finite but wrong values (relative error ~1) for them. Real MoE outputs in the evals above are far below this, but it is a property of QuickReduce (the TP all-reduce has it too).
  - Per-op error against an exact fp32 sum on unit-variance activations: bf16 RCCL 0.2–0.4%, QuickReduce FP 0.17%, INT8 0.8%, INT6 3%, INT4 11% (relative L2). The unquantized FP codec is as accurate as the RCCL path but 1.5–2x slower than RCCL, so it is not a useful fast path.
  - QuickReduce holds IPC buffers sized by `VLLM_ROCM_QUICK_REDUCE_MAX_SIZE_BYTES_MB`. 192 MB covers 8K-token chunks at hidden 5120 and leaves the rest for KV cache.
- **Docs:** the env var is documented in `envs.py` (rendered on the env vars page).
- **No duplicate:** no open PR routes the DP MoE combine through QuickReduce (searched "quick reduce combine", `VLLM_ROCM_DP_MOE_QUICK_REDUCE`). #61021 fuses add-RMSNorm into QuickReduce for the TP all-reduce, a different path.
- **Note:** intermittent DPATP2 hangs seen during this work were not caused by QuickReduce. They come from aiter split-K semaphores first allocated inside graph capture, fixed in ROCm/aiter#7126.

<summary>Setup</summary>

- **Arms:** identical servers; the only difference is `VLLM_ROCM_DP_MOE_QUICK_REDUCE=1` (INT4) vs unset.
- **Serving config:**
  - TP1 × DP2, MoE TP across both ranks;
  - DSpark speculative decoding with real verification (`rejection_sample_method=block`, not the synthetic benchmark setting);
  - `--max-model-len 1048576`.
- **Pairing:** each comparison runs both arms concurrently on separate GPU pairs, with the same samples, seeds and request order.
- **Statistics:** deltas are per-sample/per-task paired differences with bootstrap CIs.

<details>
<summary>3. TerminalBench → τ²-bench airline (and BFCL multi-turn, in progress)</summary>

- **Why not TerminalBench:** it runs every task in Docker containers, and this node cannot run a container runtime. As the container-free agentic stand-in I used **τ²-bench airline**: 50 tasks, the same server as agent and simulated user, temperature 0, substring communicate scorer (its semantic judge defaults to an OpenAI model).
- **Replicates:** two independent replicates of 3 trials per arm.

| pass^1 | QR off | QR on |
| --- | ---: | ---: |
| replicate 1 | 0.887 | 0.853 |
| replicate 2 | 0.867 | 0.880 |
| all 6 trials | 0.877 | 0.867 |

- **Paired per-task delta over 6 trials:** −0.010 [−0.040, +0.017].
- **Noise floor:** the same arm differs between its own two replicates by −0.020 (QR off) and +0.027 (QR on), so this benchmark can't resolve differences under ~3 pt here.
- **Why replicates disagree:** I checked every trial whose outcome differed. They diverge at the simulated user's *opening* message, which varies between trials in both arms. All failures in both arms are wrong final DB states; none involve malformed tool calls, broken JSON, repetition or garbled tokens.
- **Follow-up:** because of that simulator variance, I'm also running **BFCL v3 multi-turn**: 800 entries, scripted user turns, state-based grading, a GorillaFileSystem shell-like environment, no judge. It runs 3× on each of 4 servers to get a measured noise floor. I'll post the numbers here when it finishes.
</details>

<details>
<summary>4. Teacher-forced numerics (no sampling)</summary>

- **Method:** identical token sequences sent to each server with `prompt_logprobs=5`, comparing the logprob of every actual next token and the top-1 prediction.
- **Baseline:** QR off vs itself is the same server answering the same request twice.

| context | QR on vs off: mean \|Δlogprob\| / top-1 differs | QR off vs itself: mean \|Δlogprob\| / top-1 differs |
| --- | --- | --- |
| HLE Q+A (~1–3K tokens) | 0.138 / 5.6% | 0.122 / 4.9% |
| τ² conversations | 0.108 / 6.0% | 0.082 / 5.2% |
| MRCR 32K / 128K | 0.095 / 4.8%, 0.092 / 4.8% | 0.078 / 4.1%, 0.075 / 4.1% |
| MRCR 512K / 896K | 0.087 / 4.7%, 0.085 / 4.5% | 0.072 / 3.9%, 0.072 / 3.9% |

- **Baseline nondeterminism:** this stack is not bitwise reproducible. Repeating a request changes ~4–5% of top-1 predictions. That is also why the τ² trials diverge at temperature 0.
- **QR's extra perturbation:** INT4 QR adds ~20% to that baseline deviation (about +0.6 pt of top-1 changes).
- **No accumulation:** the effect is flat from 2K to 896K tokens of context.
</details>

- **Scope:** results are for DPATP2 (DP=2) on MI355X only. The PR only claims a speedup there; at DP=4 a microbenchmark showed no consistent win, so I'd keep it off there.
</details>

**1. Precision without quantization.** There is no `BF16` value; the unquantized codec is `FP` (`NONE` turns QuickReduce off). I measured the all-reduce error against an exact fp32 sum of the same inputs (relative L2, 4096 x 5120 bf16, unit-variance activations, two outlier-heavy distributions gave the same picture):

| | 2 ranks | 4 ranks | 8 ranks |
| --- | ---: | ---: | ---: |
| bf16 RCCL all-reduce (current path) | 0.18% | 0.27% | 0.37% |
| QuickReduce FP | 0.18% | 0.17% | 0.17% |
| QuickReduce INT8 | 0.8% | 0.8% | 0.8% |
| QuickReduce INT6 | 3.0% | 3.0% | 3.0% |
| QuickReduce INT4 | 11% | 11% | 11% |

So `FP` is as accurate as the RCCL bf16 path (it communicates in fp16, which has more mantissa than bf16). It is also 1.5-2x *slower* than RCCL's reduce-scatter in my sweep, so it is not a useful fast path; the speedup comes from the INT4 codec, which is why the evals I posted use INT4.

One real limitation, which applies to QuickReduce in general (the TP all-reduce too): with the default `VLLM_ROCM_QUICK_REDUCE_CAST_BF16_TO_FP16=1`, values beyond fp16's range (|x| above ~6.5e4, e.g. a cross-rank sum of 2e4-sized activations) are not handled. FP/INT8/INT6 return inf/NaN there (2-36% of elements for FP, up to 100% for INT8/INT6 with more ranks) and INT4 returns finite but wrong values (relative error ~1). With `CAST=0`, FP/INT8/INT6 are fine, INT4 is not. Real MoE outputs in the evals I posted are far below that range, but it is worth knowing; I added it to the PR description.

**2. QuickReduce reduce-scatter kernel vs all-reduce + slice** (the AITER `qr_reduce_scatter` you linked). It is a single-phase INT4 kernel on a 4-rank communicator, so it only applies at DP=4 (not the DP=2 case this PR targets, and not 8). I benchmarked it against what the PR does on the same 4 GPUs (hidden 5120, bf16, INT4; ms per op, CUDA-graph timing):

| gathered tensor | RCCL RS | vLLM QR all-reduce + slice | AITER QR all-reduce + slice | AITER `qr_reduce_scatter` |
| ---: | ---: | ---: | ---: | ---: |
| 2.5 MB | 0.028 | **0.018** | 0.026 | 0.021 |
| 10 MB | 0.068 | **0.045** | 0.055 | 0.049 |
| 40 MB | 0.228 | **0.144** | 0.171 | 0.179 |
| 160 MB | 0.878 | 0.515 | 0.582 | **0.486** |
| 320 MB | 1.687 | **0.999** | 1.136 | 1.042 |

It does move less data, but at 4 ranks it is no faster than the all-reduce + slice through vLLM's FlyDSL INT4 QuickReduce, except at 160 MB (6%). It is more accurate (8.6% vs 11% relative L2 on unit-variance data), since it quantizes once instead of twice. So I'd keep all-reduce + slice, which also covers 2 and 8 ranks; it would become attractive if the native reduce-scatter got the FlyDSL treatment. The script for this one is local; happy to share it.

**3. Heuristic to auto-enable.** Agreed we should not make INT4 default. What I could do is the size heuristic from my other reply: the default minimum size (4 MB at 4 ranks, 8 MB at 8 ranks) so QuickReduce is only used where it beats AITER's reduce-scatter. That is in cc1bf3739e.
