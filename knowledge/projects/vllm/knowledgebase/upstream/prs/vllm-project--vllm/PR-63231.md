# [Core] Change default --block-size from 16 to 64

[Upstream PR](https://github.com/vllm-project/vllm/pull/63231) · state: open · merged: False

## Original PR description

## Overview

Changes the default `--block-size` for `vllm serve` / `EngineArgs` from 16 to 64, via `CacheConfig.DEFAULT_BLOCK_SIZE`. Also teaches `RocmAttentionBackend` to prefer 16-token blocks for default-sized runs, keeping ROCm on its native paged-attention kernel.

## Claims

- `CacheConfig()` (and therefore `vllm serve` without `--block-size`) now resolves to `block_size=64`; an explicit `--block-size` still sets `user_specified_block_size=True` and takes precedence.
- Platforms/attention backends that declare a preferred or restricted block size continue to override the default exactly as before: `update_block_size_for_backend` only consults `DEFAULT_BLOCK_SIZE` when the user did not specify `--block-size`.
- ROCm runs without an explicit `--block-size` keep the native C++ paged-attention kernel (block sizes 16/32) instead of silently falling back to the slower Triton path that any other multiple of 16 routes to.

## Validation

- Full Buildkite CI build [#97300](https://buildkite.com/vllm/ci/builds/97300) passed (171 jobs), including the suites that caught regressions in the first run (#96922): H200/MI355 KV connector offload, MI250 PyTorch fullgraph cudagraph compatibility, and model executor.
- First CI run (#96922, default alone) failed exactly where 16-token assumptions were baked in: offloading-connector chunk sizes (48/16 vs the 64 GPU block), shared-storage connector hash-count expectations, an autotune cache-key test using 64 as a "non-default" control, and a 25-minute MI250 hang in RocmAttn with 64-token blocks (engine never returned from a step). All are fixed by this PR; the MI250 job went from timeout to passing in 8m51s, confirming the hang was block-size-related, not a flake.
- `tests/config/test_config_utils.py` (includes new `test_cache_config_default_block_size`): 28 passed.
- `tests/v1/core/test_kv_cache_utils.py`: 159 passed.
- `tests/kernels/attention/test_attention_selector.py`: 16 passed, 93 skipped.
- `tests/model_executor/test_flashinfer_autotune_warmup.py::test_autotune_cache_key_normalizes_kv_init_fields`: passed locally.
- `pre-commit run` on changed files: passed (ruff check/format, mypy, new-test CI-tethering check).
- Sanity check on CPU: `CacheConfig().block_size == 64`, `CacheConfig(block_size=16).user_specified_block_size is True`.

Still missing: a 16-vs-64 throughput/memory benchmark on a real serving workload. This change is motivated by per-block bookkeeping overhead; reviewers with GPU access should run `vllm bench serve` (or equivalent) on a representative model before merging if quantitative gains are required.

## Details

Motivation: a 64-token block reduces per-block bookkeeping overhead (block tables, allocator metadata, prefix-cache hash operations per token) and matches the granularity many attention backends already prefer. `user_specified_block_size` keeps explicit user settings authoritative, and the per-platform `get_preferred_block_size` / `get_supported_kernel_block_sizes` negotiation in `Platform.update_block_size_for_backend` is unchanged, so backends that cannot run with 64 still select a supported size automatically.

ROCm specifics: the native ROCm paged-attention C++ kernel only supports block sizes 16 and 32 (shared-memory/LDS constraints); every other multiple of 16 is routed to a Triton fallback (see `get_supported_kernel_block_sizes` in `vllm/v1/attention/backends/rocm_attn.py`). With the new default, `get_preferred_block_size(64)` returned 64 because 64 is nominally "supported", pushing every default-sized ROCm run onto that fallback — which is where build #96922's MI250 job hung. The new `RocmAttentionBackend.get_preferred_block_size` returns 16 unless the user passes an explicit `--block-size`, restoring pre-PR behavior on ROCm.

Tradeoffs:
- Prefix-cache hits land on 64-token boundaries instead of 16, so short shared prefixes (< 64 tokens) may no longer hit. Workloads with many short shared prefixes can pass `--block-size 16` to restore old behavior.
- Coarser blocks waste more KV memory per request on ragged tails (up to 63 tokens per request, vs 15).
- Third-party configs that hardcode chunk/block sizes as multiples of 16 (e.g. KV connector `kv_connector_extra_config["block_size"]`) now fail validation at startup against the 64-token default; the error message suggests the nearest valid value.
- This is a user-visible behavioral default change; docs use 16 only as an illustrative example and were not updated.

Not a duplicate: searched open PRs/issues (`block size default`, `block_size in:title`) — no open PR changes the global default. Related but distinct open PRs (e.g. #62265, #60880) fix backend-specific preferred-size selection, which this change composes with.

These tests assume the old default of 16 and fail in CI with 64. I verified each fix locally on an RTX A6000 (fails before, passes after):

  The test needs a block size different from the default, and 64 is now the default.

- `tests/v1/kv_connector/unit/test_example_connector.py`
  Add `block_size=16` to `LLM(...)`.
  The two text-only prompts are shorter than 64 tokens, so they hash to the same folder.

  Change `CPU_BLOCK_SIZES = 48` to `192`.
  The offloaded block size must be a multiple of the GPU block size, and 48 is not a multiple of 64. 192 works for both 16 and 64.
  In the same file, `test_mamba_cpu_offload_boundary` hardcodes 16, so it likely also needs `block_size=block_size` in its `LLM(...)` (not tested locally).
