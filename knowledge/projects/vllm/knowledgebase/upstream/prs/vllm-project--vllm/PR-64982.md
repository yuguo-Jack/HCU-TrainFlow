# [Perf] Skinny GEMM: eager fast path and SM90 plans for the Qwen3.5 MoE BF16 projections

[Upstream PR](https://github.com/vllm-project/vllm/pull/64982) · state: open · merged: False

## Original PR description



## Overview

Follow-up to #64979 (SM90 plans for dense models). Qwen3.5 / 3.6 MoE keep two small BF16 projections in their FP8 checkpoints: the GDN fused b/a projection `(64, 2048)` and the shared-expert gate `(1, 2048)`. cuBLAS runs each as a single CTA (an `nvjet 64x8` tile, or a `dot_kernel` + `reduce_1Block_kernel` pair for N = 1) in 4.6-6.0 us, 70 times per decode step, i.e. about 7% of a single-request decode step of `Qwen/Qwen3.6-35B-A3B-FP8` on H200. This PR:

1. adds SM90 plans for those two shapes (2.2-2.5 us per call; 2.0x-2.7x), and
2. gives `cuda_unquantized_gemm` an eager fast path. These models run without `torch.compile` (#51012), and there the custom-op dispatch costs about 5 us of host time per call at every token count, planned or not, because the plan lookup happens inside the op. With ~1000 kernels per step that showed up as +2.6% TPOT at 8 concurrent requests (where no plan applies) in a first version. In eager execution the dispatch now reads the plan cached on the layer (`layer.skinny_gemm_plan`, set by `maybe_use_skinny_gemm`) and calls the kernel directly or falls through to `F.linear`; under `torch.compiler.is_compiling()` the custom op is kept, since the token count must stay out of the traced graph.

## Claims

- **Host cost, eager dispatch (H200):** unplanned token count (M = 8): `F.linear` 9.9 us, custom op 14-16 us, this PR 10.9 us. Planned (M = 1): custom op 17-23 us, this PR 13-15 us.
- **Kernels:** `(64, 2048)` 5.9 -> 2.2 us (2.7x), `(1, 2048)` 5.0 -> 2.5 us (2.0x) at one token, cold L2; both shapes also win at 2 and 4 tokens.
- **E2E, `Qwen/Qwen3.6-35B-A3B-FP8`, H200 TP=1:** median TPOT -3.7% at one request (3.598 -> 3.464 ms), -3.0% at 2 and 4 requests, unchanged at 8 (no plan applies there, and the eager fast path removes the custom-op cost that a first version paid: +2.6% at 8 requests).
- **No change** for compiled models (same custom op as before) or for shapes without a plan.

## Validation

### Per-cell GEMM time

Same method as #64979 (H200, CUDA graph replay, weight read from HBM, spacer kernel before each GEMM, median of 7 paired repeats, cuBLAS -> plan in us):

| projection | (N, K) | M=1 | M=2 | M=4 |
|---|---|---|---|---|
| Qwen3.5/3.6 MoE shared-expert gate | (1, 2048) | 5.0 → 2.5 (2.00x) | 4.0 → 2.6 (1.55x) | 4.2 → 2.7 (1.57x) |
| Qwen3.5/3.6 MoE GDN b/a projection | (64, 2048) | 6.0 → 2.2 (2.69x) | 6.0 → 2.3 (2.61x) | 6.0 → 2.4 (2.48x) |

In an nsys trace of a single-request decode step of Qwen3.6-35B-A3B-FP8, the 70 cuBLAS launches (30 x `nvjet 64x8` 170 us + 40 x `dot_kernel` 88 us + 40 x `reduce_1Block_kernel` 123 us = 381 us per step) become 70 skinny GEMM launches totalling 125 us.

### E2E

H200 NVL, TP=1, `vllm serve Qwen/Qwen3.6-35B-A3B-FP8 --max-model-len 4096 --no-enable-prefix-caching`, `vllm bench serve --dataset-name random --random-input-len 1024 --random-output-len 256 --ignore-eos --seed 0`; 32 prompts at concurrency 1, 8x the concurrency otherwise. Both arms run the same nightly image with #62956 and #64980 applied (the FP8 layers of this model take the W8A16 skinny GEMM in both arms); the PR arm adds this branch. `VLLM_DISABLE_COMPILE_CACHE=1` in both arms. Four server launches on one GPU in the order base, PR, PR, base. Median TPOT (ms), both runs:

| conc. | without | with this PR | change |
|---:|---|---|---:|
| 1 | 3.597 / 3.599 | 3.464 / 3.464 | -3.7% |
| 2 | 4.100 / 4.101 | 3.978 / 3.978 | -3.0% |
| 4 | 4.809 / 4.814 | 4.662 / 4.676 | -3.0% |
| 8 | 5.912 / 5.912 | 5.912 / 5.904 | 0 |

Without the eager fast path (plans only, custom-op dispatch at every token count), the same comparison interleaved on two GPUs gave +2.6% at 8 requests (5.728 / 5.765 -> 5.909 / 5.886) with the same gains at 1-4.

### Tests

`pytest tests/kernels/test_bf16_skinny_gemm.py` on H200 (nightly image with #62956 and this branch applied): 388 passed, 458 skipped (other architectures). `test_maybe_use_skinny_gemm` now also checks the plan cached on the layer.

## Details

- **Why a Python branch is safe here.** `cuda_unquantized_gemm` is called from the layer's `apply`; when Dynamo traces the model (`torch.compiler.is_compiling()`), the code takes the custom-op branch exactly as before, so compiled models see no change. The eager branch only runs for models that execute Python per step; there a shape-dependent branch costs a dict lookup.
- **CUDA graphs without torch.compile.** Qwen3.5 captures CUDA graphs per batch size; the eager branch runs during capture, so each graph holds the right kernel for its size.
