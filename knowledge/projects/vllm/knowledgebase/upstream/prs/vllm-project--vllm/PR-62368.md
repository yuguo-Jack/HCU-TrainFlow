# [Bugfix][Frontend] Constrain Qwen3 XML tool calls written without <tool_call>

[Upstream PR](https://github.com/vllm-project/vllm/pull/62368) · state: open · merged: False

## Original PR description



## Overview

With `--tool-call-parser qwen3_coder` (or `qwen3_xml`), the Python parser returns `<function=NAME>...</function>` as a tool call with or without the `<tool_call>` wrapper, but the `qwen_3_coder` structural tag only triggers on the wrapped form. Under `tool_choice="auto"`, an unwrapped call is free text to the grammar, so a `strict: true` tool (or `--tool-strict-level parameter`) does not constrain it. This PR adds triggered tags for the unwrapped form, so the grammar constrains every call the parser extracts.

## Claims

- With a structural tag active (`strict: true` tools, or `--tool-strict-level function|parameter`), unwrapped `<function=...>` calls are now constrained like wrapped ones: the arguments must match the schema, the function must be one of the request's tools, and `parallel_tool_calls=false` stops after the first call. On `main` none of the three applied to unwrapped calls.
- Unchanged: wrapped calls, named (forced) tool choice, and requests without a structural tag (`auto` with non-strict tools at the default strict level).

## Details

- **Root cause:** `qwen3_config` in `vllm/parser/qwen3.py` has a `CONTENT` -> `<function=` transition ("Fallback: `<function=` without a preceding `<tool_call>`", covered by `test_extract_tool_calls_fallback_no_tags`). `Qwen3EngineToolParser` builds its grammar from xgrammar's builtin `qwen_3_coder` tag, whose `TriggeredTagsFormat` has the single trigger `<tool_call>\n<function=`. So the parser and the grammar disagree on what a tool call is, and only the wrapped form is checked.
- **Fix:** `Qwen3EngineToolParser.get_structural_tag` post-processes the builtin tag with a new `allow_unwrapped_qwen_xml_tool_calls` helper in `structural_tag_registry.py`, next to `limit_to_single_tool_call`. For each `TriggeredTagsFormat`, the helper adds a copy of each wrapped tag without `<tool_call>\n` / `\n</tool_call>` (same schema content) and a `<function=` trigger. The wrapped tags stay byte-identical to xgrammar's, so the builtin remains the single source of the format. `auto` and `required` both use `TriggeredTagsFormat`; named tool choice is a plain `TagFormat` that already forces the wrapped form, so it is unchanged. `limit_to_single_tool_call` runs after this and covers the new tags.
- **Tradeoff:** while a structural tag is active, `<function=` in free text must now continue as a valid call to a request tool. The parser already treated that text as the start of a call, so this does not newly block output that would have reached the client as content.
- **Not changed:** the Rust frontend's `Qwen3CoderToolParser` only parses wrapped calls, so its grammar already matches it. `step3p5` and `mimo` share the `qwen3_config` fallback but have their own call formats; they could reuse the helper in a follow-up.
- Found while serving `nvidia/Cosmos3-Edge` with `--model-impl transformers`, which writes unwrapped calls.
- Not a duplicate: `gh search prs/issues` for "qwen3_coder structural tag", "qwen_3_coder structural tag", "Qwen3EngineToolParser structural", "qwen3_xml structural tag", "structural tag function= without tool_call" and "triggered tags qwen" found only unrelated work (#60770, #53752, #54808, #62078).
