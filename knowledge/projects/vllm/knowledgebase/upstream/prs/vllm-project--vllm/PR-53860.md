# [Bugfix] Fix out-of-bounds attrIdxs in cuMemcpyBatchAsync batch KV offload

[Upstream PR](https://github.com/vllm-project/vllm/pull/53860) · state: open · merged: False

## Original PR description

# Fix out-of-bounds `attrIdxs` in `cuMemcpyBatchAsync` batch KV offload

## Summary

`copy_blocks()` in `vllm/v1/simple_kv_offload/cuda_mem_ops.py` passes a **single** `size_t` as the `attrIdxs` array to `cuMemcpyBatchAsync` / `hipMemcpyBatchAsync`, regardless of the descriptor count. The CUDA Driver API contract for `cuMemcpyBatchAsync` requires `attrIdxs` to be an array of `count` entries — one index per descriptor, each `>= 0` and `< numAttrs`. Passing one entry while `count` is large leaves the driver reading past the end of that scalar: an out-of-bounds read / undefined behavior.

## Root cause

The CUDA Driver API documentation for `cuMemcpyBatchAsync` specifies `attrIdxs` as an array of `count` elements (indices into the `attrs` array, each less than `numAttrs`). The current code:

```python
class BatchMemcpyParams(NamedTuple):
    ...
    attrs: _CUmemcpyAttributes
    attrs_idx: ctypes.c_size_t      # ONE entry, regardless of descriptor count
    ...

err = fn(..., cnt, ..., ctypes.byref(params.attrs_idx), params.num_attrs, ...)
```

`cnt` is typically 4096 or more — one descriptor per 64 KiB KV block, and `copy_blocks()` is called with the request's full block list. The driver is permitted to read `attrIdxs[0..cnt-1]`; everything past the first element is whatever bytes happen to sit adjacent to that scalar in the heap-allocated NamedTuple.

Still present at upstream `main` (`f47792af7`): the `attrs_idx: ctypes.c_size_t` field is at line 181 of `cuda_mem_ops.py`, initialized at line 220, and passed via `ctypes.byref(params.attrs_idx)` at line 264 (the file is unchanged between `5efbf0886` and `f47792af7`, so the line numbers are current). This branch is rebased onto `f47792af7`.

## Why it currently "works"

This is undefined behavior that happens to work: in current builds the bytes adjacent to the scalar read as values the driver tolerates. That is luck, not correctness — stack/heap layout changes (compiler, Python version, unrelated edits) can turn it into a crash at any time. Intermittent `cuMemcpyBatchAsync` segfaults in the KV-offloading path have already been observed in the wild (#40259, closed after "disappearing" on a nightly build — consistent with layout-dependent UB rather than a deterministic logic bug).

## Fix

Allocate the per-descriptor index array explicitly. All-zero indices preserve the existing semantics exactly (every descriptor uses `attrs[0]`):

```python
attr_idxs = np.zeros(cnt, dtype=np.uint64)
err = fn(..., cnt, ..., attr_idxs.ctypes.data, params.num_attrs, ...)
```

`uint64` matches the `size_t` element type the driver expects.

## ROCm path

Behaviorally unaffected: on ROCm runtimes older than 7.13 the code already passes `num_attrs = 0`, and with `num_attrs == 0` the driver ignores `attrIdxs` entirely. On ROCm 7.13+, however, `_num_attrs_for_hip_version()` returns 1 and the `attrIdxs` pointer **is** consumed — the out-of-bounds read is live there too, mirroring the `runtime_accepts_attrs` gate in the C++ path (#53971). The fix is correct on both sides of the gate.

Note: the same single-entry pattern also exists in the C++ batch-copy path (`csrc/cache_kernels.cu`, moved there from `csrc/libtorch_stable/` by #60721). It is tracked in #53863 and fixed separately in #53971, keeping this PR minimal (Python-only, no compile-matrix impact).

## Testing

Items 1-2 use a standalone reproducer/verifier (resolves `cuMemcpyBatchAsync` directly via `cuGetProcAddress`; does not import vllm). Item 3 is the in-tree regression test this PR adds:

1. **Fixed path**: batch of 4096 descriptors x 64 KiB, D2H + H2D roundtrip, data verified byte-for-byte against torch reference copies. PASS.
2. **OOB demonstration** (`--oob` mode): places the single `size_t` directly before a `PROT_NONE` guard page and issues `count = 2`. If the driver dereferences `attrIdxs[1]`, the process faults — demonstrating the read is real, not hypothetical. (Survival only means this driver build skipped the read; the API contract still allows it.)
3. **In-tree regression test**: this PR adds `test_copy_blocks_passes_one_attr_idx_per_descriptor` to `tests/v1/simple_kv_offload/test_hip_mem_ops.py`. It monkeypatches the batch-memcpy entry point (no GPU or HIP runtime needed) and asserts, while the pointers are still alive, that `attrIdxs` is an array of `num_layers * num_blocks` entries, all zero:
   - On this branch: `22 passed in 5.90s`.
   - With only `vllm/v1/simple_kv_offload/cuda_mem_ops.py` reverted to upstream `main` (`5efbf0886`), keeping this branch's test file: `7 failed, 15 passed in 6.08s` — the new test fails, and the remaining failures are `TypeError`s from existing tests constructing `BatchMemcpyParams` with this branch's field layout (the single-scalar `attrs_idx` field removed).

Items 1-2 tested on: RTX PRO 6000 (Blackwell), CUDA 12.8, torch 2.8.0+cu128, Python 3.12. Item 3 ran host-only under pytest 9.1.1 (driver calls monkeypatched).
