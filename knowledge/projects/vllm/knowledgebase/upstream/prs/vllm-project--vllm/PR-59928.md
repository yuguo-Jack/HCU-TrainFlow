# [Bugfix][Parser] Recover genuine tool calls after unclosed Qwen3 <function= opener in prose

[Upstream PR](https://github.com/vllm-project/vllm/pull/59928) · state: closed · merged: True

## Original PR description



## Overview

Fixes #58227. Recovers subsequent genuine tool calls in `Qwen3Parser` (`qwen3_config`) when the model writes an unclosed `<tool_call>` + `<function=...` header in prose, while preserving literal `<tool_call>` strings inside `<parameter=...>` values.

## Claims

- Recovers genuine `<tool_call>\n<function=...>` calls that follow an unclosed `<tool_call>\n<function=function_name` (without `>`) or `<tool_call>\n<function=function_name>` (with `>`) written in prose or reasoning, in both non-streaming (`extract_tool_calls`) and streaming (`parse_delta`) modes.
- Preserves literal `<tool_call>` text inside parameter values (e.g. `<tool_call><function=write_file><parameter=content>Document <tool_call> usage</parameter></function></tool_call>`) without truncating the argument span.
- Keeps the fix localized to `qwen3_config` in `vllm/parser/qwen3.py` with zero changes to core engine files.

## Details

### Root Cause
In `qwen3_config`, once `<tool_call>` (`TOOL_START`) transitions to `ParserState.TOOL_PREAMBLE` and `<function=` (`FUNC_PREFIX`) transitions to `ParserState.TOOL_NAME`:
1. If the prose example never writes `>` (`FUNC_NAME_END`), `TOOL_NAME` only had a transition on `FUNC_NAME_END` (`>`). Any later `</think>`, `<tool_call>`, or `<function=get_weather>` was accumulated into `TOOL_NAME` until the first `>` of the genuine tool call, naming the call after the prose fragment and swallowing the genuine function name.
2. If the prose example writes `<function=function_name>` (`ParserState.TOOL_ARGS`) without `</function>` or `</tool_call>`, `TOOL_ARGS` only exited on `FUNC_END` (`</function>`) or `TOOL_END` (`</tool_call>`). A subsequent genuine `<tool_call>\n<function=get_weather>` was swallowed as part of the unclosed span's argument body.

### Design & Trade-offs
- **Why transition `(ParserState.TOOL_ARGS, "FUNC_PREFIX")` instead of `(ParserState.TOOL_ARGS, "TOOL_START")`:** As noted in [#58227 (comment)](https://github.com/vllm-project/vllm/issues/58227#issuecomment-5851527797), transitioning out of `TOOL_ARGS` on `TOOL_START` (`<tool_call>`) truncates valid tool calls whose parameter value contains literal `<tool_call>` (such as `<parameter=content>Document <tool_call> usage</parameter>`). Because a genuine Qwen3 tool call always begins its header with `<function=` (`FUNC_PREFIX`), transitioning `(TOOL_ARGS, "FUNC_PREFIX") -> TOOL_NAME` with `(EventType.TOOL_CALL_END, EventType.TOOL_CALL_START)` recovers the subsequent real tool call while leaving `<tool_call>` inside `<parameter=...>` untouched as content.
- **Why `ParserState.TOOL_NAME` transitions on `TOOL_END`, `TOOL_START`, and `FUNC_PREFIX`:** A valid function identifier cannot contain `<tool_call>`, `</tool_call>`, or `<function=`, so encountering any of those terminals before `>` unambiguously indicates the `<function=...` header was unclosed.
- **Why this does not duplicate existing PRs:**
  - #57553 handles markdown code fences (```` ``` ````), not unfenced prose.
  - #56661 checks for a `<function=` header before committing a span, which is already present in `<function=function_name`.
  - #50986 (`validate_tool_names`) filters unknown tool names (`function_name`), which works together with this PR: once this PR splits the unclosed prose span from the subsequent genuine `get_weather` span, `get_weather` is preserved even when `function_name` is filtered out.
  - #59821 defers `<tool_call>` inside `<think>...</think>` blocks; this PR also recovers unclosed `<tool_call>\n<function=...` spans in non-thinking mode or post-`</think>` assistant prose without buffering the entire reasoning stream.
