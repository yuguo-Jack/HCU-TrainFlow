# [Bugfix][KV Offload]Defer async loads in mixed steps

[Upstream PR](https://github.com/vllm-project/vllm/pull/64236) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

In mixed sync/async CPU-tier loads, submit and wait for sync jobs before the forward, then defer independent async-job submission until OffloadingConnector collects transfer results. This removes async host-side submission from the pre-forward path; it does not guarantee a lower TTFT or higher throughput.

## Claims

- Sync jobs remain submitted and awaited before the forward. Independent async jobs are staged and submitted once from OffloadingConnector's existing `get_finished()` hook.
- The change can reduce forward-start delay when async host submission would otherwise hold up the model runner. It does not make the async H2D copy overlap the current target forward.
- The size of any end-to-end benefit depends on available forward work to overlap and on how long async submission takes. If the GPU is already continuously busy, this change does not add GPU capacity; deferred submission can also delay async-load completion.

## Validation

Focused tests cover mixed sync/async loads, deferred submission through `get_finished()`, no-forward steps, and transfer completion/error handling. Ruff and pre-commit checks passed.

A timeline probe used Qwen3-4B, TP=2, and 24 concurrent requests (16 with a warmed 512-token CPU-cache prefix plus a 480-token uncached suffix; 8 uncached 992-token prompts; one output token each). Each captured mixed step had 2 sync and 14 async jobs, with 9 requests and 7904 tokens scheduled. One burst was recorded for each of four scenarios.

The `Before` panels are a controlled pre-forward-submission reference using the same instrumented code and workload. They are not measurements from a checkout of the historical PR base.

| Runner path | Before: async submission overlap with target forward | PR: async submission overlap with target forward |
| --- | ---: | ---: |
| MRv1 | 0 ms | 15.47 ms |
| MRv2 | 0 ms | 17.28 ms |

## Details

[#61961](https://github.com/vllm-project/vllm/pull/61961) introduced sync CPU-tier hits. In a mixed step, only sync loads must complete before the current forward, but the previous submission loop also submitted independent async loads before it. This change stages those async jobs and submits them during existing result collection, without changing the shared connector interface or other connectors.

The lifecycle hook occurs at different points by runner version: MRv1 collects transfer results after forward and before sampling, so a long host submission can push sampling later if it extends past the forward's remaining GPU time. MRv2 collects results in `post_forward()` after sampling work and the token-output copy have been enqueued; host submission can still delay the runner returning its output. In both cases, async H2D completion may be later because the jobs are submitted later.

This is a follow-up to #61961 addressing mixed sync/async submission; #61961 did not split submissions by job type. AI assistance was used.
