# [Core][DP] Prefix-affinity tie-break in the internal DP load balancer

[Upstream PR](https://github.com/vllm-project/vllm/pull/52464) · state: open · merged: False

## Original PR description

## Purpose

Partial mitigation for #52463: the tie-break rotation added in #47420 degrades prefix-cache locality for multi-turn / shared-prefix traffic under the internal DP load balancer. Consecutive turns of one conversation are tied decisions at low load, so they rotate across DP ranks and every turn misses the prefix its previous turn cached.

This PR remembers which engine served a prompt's first-block prefix (LRU of 16k entries, keyed on `cache_salt` + LoRA id + first `block_size` prompt token ids) and prefers that engine **only when scores tie**:

- Load-aware decisions unchanged — a lower-scored engine always wins.
- Unrelated tied requests still rotate — #47420's fairness fix is preserved (regression-tested).
- Explicit `data_parallel_rank` and late-interaction routing bypass affinity, unchanged.
- Stale entries from elastic-EP scale-in are discarded; sub-block prompts (which cannot hit the cache) are exempt.

## Test Plan

- `tests/v1/engine/test_dp_lb_prefix_affinity.py` — 8 CPU-only unit tests driving `get_core_engine_for_request` directly: session stickiness across turns, tied-unrelated rotation preserved, load-beats-affinity, sub-block exemption, cache_salt separation, explicit-rank bypass, scale-in staleness, LRU bound.
- Hardware A/B on 8×H100 (DeepSeek-V4-Flash-0731, DP=4+EP, `--api-server-count 4`, fp8 KV, aiperf mooncake trace designed for 81.7% prefix reuse — full methodology in #52463): identical runs, only this patch differs.

**Known limitation (why this is a mitigation, not the full fix):** with `--api-server-count N` each frontend process has its own client and affinity map, and SO_REUSEPORT spreads one session's connections across processes — client-side affinity only sees its own process's requests (this bounds the c=1 recovery at 61.5% vs 81.6% measured on v0.23.0, a pre-#47420 release — a version-level baseline, not a single-commit revert of #47420). The complete fix needs prefix-awareness at a shared layer (DP coordinator or a shared affinity table); #52463 is the home for that design discussion.

- richajoy · comment · 2026-10-24T16:29:41Z · [source](https://github.com/vllm-project/vllm/pull/52464#issuecomment-6386669216)

Tested this PR on a different model and layout: 8x H100 SXM5, vLLM v0.32.0 (PR head `5e9ab1b`, `core_client.py` rebased onto v0.32.0), Qwen3-235B-A22B-Instruct-2507-FP8, `--data-parallel-size 8 --enable-expert-parallel`, block 64, prefix caching on.
Workload (AIPerf): 64 concurrent multi-turn sessions, +600 input / 200 output tokens per turn, 8 +- 2 turns, full history resent, 512 requests. Prefix cache reset before each point; base and PR launches interleaved. Hit rate = per-engine `prefix_cache_hits / prefix_cache_queries`, pooled.

**No shared system prompt, `--api-server-count 1`, 3 launches per arm:**

| | prefix hit (runs) | req/s | TTFT p50 / p90 / p99 (ms) | ITL p50 (ms) |
|---|---|---|---|---|
| base | 21.8% (23.6 / 22.1 / 19.6) | 6.46 | 2022 / 4064 / 5300 | 26.1 |
| PR | 51.3% (50.5 / 52.2 / 51.1) | 7.36 | 1572 / 2781 / 3231 | 25.1 |
| change | +29.5 pt | +14% | -22% / -32% / -39% | -4% |

No overlap between arms on any column. My estimate of the ceiling for this workload (perfect stickiness, no eviction) is ~77-82%, so the PR closes about half the gap at c=64, which fits "affinity only on exact ties".

**Same workload, default `--api-server-count` (8 here), 2 launches per arm:** hit 18.8% -> 38.5% (20.3 / 17.3 -> 40.1 / 37.0), req/s +8%, TTFT p50 / p99 -26% / -23%, ITL p50 flat (~29 ms). So the per-process maps cost about a third of the gain but do not remove it. Per-engine request counts stay uneven (max/min 1.10-1.20, vs 1.00 at api-server-count 1), with or without the PR. Given that, I doubt the per-process limitation alone explains your c=64 row (10.9% -> 11.1% at api-server-count 4); your hit rate falling with concurrency on that trace may point at KV pressure instead, but I have not tested that.

**With a 2,000-token shared system prompt (otherwise identical, api-server-count 1, 3 launches per arm):** no change in hit (49.0% vs 48.8%), req/s, TTFT p50/p90 or ITL. TTFT p99 is slightly higher with the PR in all 3 pairs (5637 / 5541 / 5459 -> 5993 / 5867 / 5839 ms, +6.4%); small, and it rests on ~5 tail requests per run.

This follows from the key, `hash((cache_salt, lora_id, tokens[:block_size]))`: when sessions share a system prompt longer than one block, every session gets the same key, the map holds one entry that every request overwrites, and a tied request goes to whichever engine served the most recent request of any session. That is my guess for the p99 cost too (tied requests stacking on one engine; request spread 1.03 vs 1.00), not verified. Most agentic and chat traffic starts with a shared system prompt, so this is probably the common production case.

Suggestion (not implemented or measured by me): key on the longest matching prefix rather than the first block. For example, store the engine against the chained per-block hashes every N blocks and look up from the longest match down, or skip any key that many distinct sessions map to and fall back to the next stored block. Either keeps the tie-only rule and the 16k LRU bound, and should carry the gain above over to shared-prompt traffic. An explicit session id when the client sends one (#48049) is the other option.

Limits: one concurrency (c=64), one model, PR rebased onto v0.32.0 rather than run at its own base.

Happy to rerun on this setup: a revised key on the shared-prompt workload, or other concurrencies.
