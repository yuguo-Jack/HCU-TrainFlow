# [Bugfix][Attention] Keep DSA shared-indexer top-k state per DBO microbatch

[Upstream PR](https://github.com/vllm-project/vllm/pull/60734) · state: open · merged: False

## Original PR description



## Overview

With `--enable-dbo`, GLM-5.x (DSA with shared top-k layers, `index_topk_freq > 1`) loses about a third of its GSM8K accuracy: 0.93 with DBO off, 0.61 with DBO on. The layers that reuse an earlier layer's sparse-attention top-k (57 of GLM-5.3's 78 layers) read it from buffers that have no microbatch dimension. DBO runs microbatch 1's index-producing layer between microbatch 0's producer and its consumers, so microbatch 0's consumers attend over microbatch 1's token selection. This PR gives every DBO microbatch after the first its own copy of that state. With it, DBO-on accuracy matches DBO off.

Companion to #60732 (DSA indexer crash under DBO, which hid this bug). The two fixes are independent; DBO with DeepEP high-throughput needs both. No existing issue or PR covers this (searched `dbo topk`, `index_topk_freq dbo`, `shared indexer microbatch`, `GLM-5 dbo accuracy`: 0 results). Related open PR: #56476 fixes the same class of bug for DeepSeek-V4.1 (its top-k and candidate buffers, via a new `dbo_select_buffer` helper). It does not cover the DeepSeek-V3.2 / GLM-5.x IndexCache path changed here; if it lands first, this PR can switch to its helper.

## Claims

- Fixes GLM-5.x accuracy under DBO on Model Runner V1 and V2: GSM8K 0.61 → 0.92 (DBO off: 0.92–0.93). Also with DBO microbatches replayed from FULL decode CUDA graphs (DeepEP low-latency): 0.44 → 0.85 (DBO off: 0.84–0.86).
- No change without DBO, and none for DSA models without shared top-k layers (DeepSeek-V3.2, GLM-5.1: every layer computes its own top-k, so no microbatch state is allocated). Measured: both score the same with DBO on as off, with and without this change, and report identical KV cache memory with and without it.
- Memory under DBO, per GPU and per extra microbatch: `(max_num_batched_tokens + G * (max_decode_rows + 1)) * index_topk * 4` bytes, where `G` is the number of index groups with followers (19 for GLM-5.3). GLM-5.3 at `max_num_batched_tokens=8192`, `max_num_seqs=1024`: 216 MiB, measured as 0.22 GiB less KV cache memory.
- No host syncs, no extra kernels. The per-microbatch lookup is one dict read per access, the same one DBO already uses everywhere (`dbo_current_ubatch_id()`).
- HiSparse with DBO and shared top-k layers now raises at startup (it previously ran with the same corruption); supporting it needs per-microbatch HiSparse staging, out of scope here.

## Details

**Root cause** (main @ 240785b8). GLM-5.x configs set `index_topk_freq=4`, `index_skip_topk_offset=3`: only 21 of 78 layers run the sparse indexer ("leaders": 0, 1, 2, 6, 10, …, 74); each of the other 57 reuses the top-k of the leader before it. That hand-off goes through state with no microbatch dimension:
- the model-wide logical buffer `DeepseekV32Model.topk_indices_buffer`, which the leader writes (`fused_norm_rope`, `sparse_attn_indexer`) and every follower's sparse MLA impl reads;
- per index group, `SparseMLAIndexGroup.physical_topk_indices` / `valid_topk_counts` (logical → physical conversion, done once by the leader and reused by its followers) and the `logical_topk_ready` / `physical_topk_ready` events.

DBO yields inside MoE dispatch/combine, so between microbatch 0's leader L and its follower L+1, microbatch 1 runs its own layer L and overwrites all of the above. Every follower of microbatch 0 except layer 3 (layers 0–2 are dense, so there is no yield between leader 2 and follower 3) then attends over microbatch 1's selected tokens, with block-table conversion done for microbatch 1's requests. Microbatch 1's followers read their own data and are unaffected. Leaders without followers (DeepSeek-V3.2, GLM-5.1, layers 0 and 1 here) are unaffected because they write and read within one layer.

**How it was found:** while validating #60732, GSM8K with DBO on came out at ~0.6 against 0.93 off, with or without that fix and with SM partitioning disabled. The table above narrowed it to decode-step microbatching independent of prefix caching and SM count; GLM-5.1 (same architecture, no shared top-k) was unaffected, which pointed at the shared top-k hand-off. A prototype that gave each microbatch its own converted top-k restored 0.920; the long-prompt test below shows it is not enough on its own.

**Fix:**
- `SparseMLAIndexGroupBuilder` takes `num_ubatches`. When a group gets its first follower, it allocates one `UbatchTopkState` (physical indices, valid counts, two events) per extra microbatch for that group, and, once per builder, one logical buffer per extra microbatch. Groups without followers allocate nothing.
- `SparseMLAIndexGroup._topk_state()` and `SharedTopkIndicesBuffer.topk_indices_buffer` return microbatch 0's existing state, or the extra microbatch's copy when `dbo_current_ubatch_id() > 0`.
- The leader's writers (`fused_norm_rope`, `sparse_attn_indexer` in `DeepseekV32Attention`) now take the buffer from `self.impl.topk_indices_buffer`, so writer and readers resolve the same per-microbatch buffer.
- `DeepseekV32Model` passes `num_ubatches=get_num_ubatches(parallel_config)`.

The extra buffers are allocated at model construction, before the KV-cache profile, so they come out of KV cache memory. In FULL-graph DBO capture, each microbatch thread resolves its own buffers at capture time.

<details>
<summary>Alternatives considered</summary>

1. Add a microbatch dimension to `topk_indices_buffer` itself: touches the MTP proposer's buffer sharing and every reader; the per-impl property was already the single resolution point.
2. Make followers recompute top-k under DBO: correct but runs the indexer on all 78 layers, which is what `index_topk_freq` exists to avoid.
3. Disable DBO for models with shared top-k layers: loses the overlap for exactly the models (GLM-5.x) that use DBO in production.
4. Allocate per-microbatch state in every index group: wastes memory for DeepSeek-V3.2 and GLM-5.1, which have no followers.
</details>

**MTP:** the draft's indexers are re-pointed to the target buffer through the module setter, which clears any microbatch buffers. The MTP layer is a leader-only group and the draft runs outside the microbatch threads, so it is unchanged.

**Not covered:** the ROCm DSA model (`vllm/models/deepseek_v32/amd`) and the non-CUDA fallback in `deepseek_v2.py`/`glm4_moe_lite.py` still build their groups with one microbatch; they keep the old behavior if they run DBO with shared top-k layers. HiSparse raises instead (see Claims).
