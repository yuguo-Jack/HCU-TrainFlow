# [Spec Decode][GLM-5.3-Flash] Support KDA RecoverSSM (--use-replayssm)

[Upstream PR](https://github.com/vllm-project/vllm/pull/61566) · state: open · merged: False

## Original PR description

## Overview

Let GLM-5.3-Flash's KDA layers use the Kimi-K3 RecoverSSM verify/commit path (`--use-replayssm`) during speculative decoding, so each request holds one KDA state block per group instead of `2 + num_speculative_tokens`. Follows #59147 (which made `--mamba-ssm-cache-dtype` reach the GLM KDA state).

## Claims

- `--use-replayssm` now works for `Glm5NextForCausalLM` / `Glm5NextForConditionalGeneration` with MTP / DFlash speculative decoding, reusing Kimi-K3's kernels and metadata builder unchanged (no new kernels).
- Per-request KDA state footprint during spec decode drops from `2 + K` state blocks per group to one checkpoint plus small per-draft records (fp32 `[H, K+1, D]` correction and bf16 `[H, K+1, 2D]` key/gate), i.e. about 2.8x less state-pool share per running request at K=4.
- Verify outputs and committed recurrent states match GLM's native per-slot speculative path (`fused_recurrent_kda` with `K+1` state slots).
- `--use-replayssm` without speculative decoding is rejected for GLM (as for Kimi-K3), and RecoverSSM now requires Model Runner V2 with or without prefix caching, since only the V2 runner commits the accepted state after sampling.

## Details

GLM-5.3-Flash's KDA is the same recurrence as Kimi-K3's KDA: l2-normalized q/k, bounded sigmoid gate, sigmoid beta and an `[H, V, K]` state. The only parameter-layout differences are `A_log` stored as `[1, 1, H, 1]` (flattened before the kernels) and a flat `dt_bias`, so the Kimi-K3 RecoverSSM kernels apply as-is.

What changes with `--use-replayssm`:

- **Config**: `validate_mamba_cached_kernel` treats the two GLM architectures as KDA models, so `use_kda_recoverssm` is derived for them exactly as for Kimi-K3 (Triton Mamba backend, PP=1, no stochastic rounding). Both model classes declare `SupportsReplaySSM`. The Model Runner V2 requirement for RecoverSSM, previously only checked with prefix caching, is now unconditional: `commit_recoverssm_state` is driven by the V2 runner's `RecoverSSMState` only, so on V1 decode would continue from a stale checkpoint. KV connectors remain rejected with `--use-replayssm`, unchanged.
- **State layout**: `get_state_shape` / `get_state_dtype` (layer and model-level) append the RecoverSSM correction and key/gate records after the conv and recurrent state, so the Mamba page is `(conv, checkpoint, correction, kg)`; the base shapes are unchanged when the flag is off.
- **Backend**: the KDA layer selects `KimiK3KDAAttentionBackend`, whose builder produces one state slot per request plus the commit plan, and carries GLM's prefill-checkpoint metadata (it is a `GDNAttentionMetadata` subclass). Because that builder leaves `spec_sequence_masks` unset for all-spec batches, the spec/non-spec split is decided by `num_spec_decodes`.
- **Verify**: the spec path calls `kda_recoverssm_verify` (read-only on the checkpoint, writes the per-token records); the accepted state is rebuilt after sampling by the existing `RecoverSSMState.commit_step`. The spec conv window is the verify length `K+1` rather than the state-slot count.

Trade-off: with the Kimi-K3 kernels the KDA part of a decode step costs roughly 1.5x the native per-slot path (verify re-runs the recurrence and commit rebuilds the accepted state). This is a win when decode is bound by state capacity (long outputs, many concurrent requests, larger K), not when it is bound by step time. GLM-specific kernels that close most of that gap are a follow-up.

Not duplicating other work: no open PR touches GLM-5.3-Flash + RecoverSSM (`gh pr list --search "RecoverSSM GLM"`, `"replayssm GLM-5.3"`); the Kimi-K3 RecoverSSM path itself is unchanged apart from flattening `A_log` in the commit context and the unconditional Model Runner V2 check.

When `VLLM_USE_V2_MODEL_RUNNER=0` is used with speculative decoding and prefix caching is off, these entries set `use_kda_recoverssm=True` and validation permits the configuration because the runner check below is align-mode-only. The MRV1 path in `vllm/v1/worker/gpu_model_runner.py` never invokes `KimiK3KDAMetadata.commit_recoverssm_state`; that hook is only called by `vllm/v1/worker/gpu/model_states/recoverssm.py`. Since verify is read-only, accepted KDA state is never folded into the checkpoint and subsequent decode steps run from stale state, so this mode should require MRV2 unless the commit hook is wired into MRV1.
