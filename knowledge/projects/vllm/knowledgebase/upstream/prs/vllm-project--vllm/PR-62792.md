# [Core] Registerable device-transfer backend seam for KV offloading workers

[Upstream PR](https://github.com/vllm-project/vllm/pull/62792) · state: open · merged: False

## Original PR description



## Overview

Extracts the device-bound operations of the CPU offloading worker behind a pluggable `KVTransferBackend` interface with a per-platform registry, so platform plugins can supply their own KV copy paths without forking the offloading core. Motivated by the CASE-1 executor extensibility discussed in [RFC #59708](https://github.com/vllm-project/vllm/issues/59708) ([our comment](https://github.com/vllm-project/vllm/issues/59708#issuecomment-6305834117)) and required for Ascend NPU support of KV offloading / request-free prefetch.

## Claims

- **Behavior-preserving refactor**: CUDA-alike/XPU transfer paths are unchanged; the free-pass/failure test baseline is identical before and after (see Validation).
- **Plugin injection point**: platform plugins register a backend via `register_kv_transfer_backend(device_type, backend)`; registration takes precedence over the built-in backend, and `cpu/spec.py`'s platform gate now admits registered platforms.
- The seam concentrates exactly the four device-bound operations the worker needs: batched copy-op selection, descriptor pointer dtype, device-tensor validation, and host-memory pinning (register/unregister).

## Validation

Behavior preservation (CPU-only host, `VLLM_TARGET_DEVICE=cpu` runtime):

```
pytest tests/v1/kv_offload/ tests/v1/kv_connector/unit/offloading_connector/ -q -n 8
# after refactor: 1351 passed, 25 skipped, 32 failed
# before refactor (same host, same commands): identical failure set
#   (32 = test_gpu_worker.py cases requiring Triton GPU kernels; pre-existing)
```

New contract tests: `tests/v1/kv_offload/cpu/test_transfer_backend.py` (10 cases: registry precedence/lifecycle, default backend resolution per platform, monkeypatch-compat delegation of host_register/dtype/copy-op selection, handler injection). Existing monkeypatch-based tests (`test_gpu_worker.py`, `test_shared_offload_region.py`, `test_canonical_layout.py`) pass unchanged because the built-in backend resolves module globals at call time.

CI coverage note: real transfer paths (CUDA streams, swap kernels, pinned DMA) require GPU; they remain exercised by the existing `test_gpu_worker.py` suite on GPU CI. Local validation ran without GPU, which is also the platform where the seam is consumed by out-of-tree backends.

## Details

- **Interface** (`vllm/v1/kv_offload/transfer_backend.py`): `select_copy_op` returns a callable with the uniform signature `(src, dst, sizes, is_src_access_order_any=...)` shared by `_custom_ops.swap_blocks_batch` and the Triton variant; `descriptor_ptr_dtype` (CUDA int64 vs XPU uint64); `validate_device_tensor`; `host_register`/`host_unregister` are best-effort optimizations — they must not raise, and `False`/no-op degrades transfers to pageable copies (correctness unaffected).
- **Publication rule** (documented on the interface): a submitted transfer becomes observable only via the worker's `get_finished()`; successful submit never implies readiness.
- **Streams/events are intentionally excluded**: they are already platform-generic through `Platform.__getattr__` delegation to `torch.<device_type>`, so conforming platforms (e.g. NPU via `torch.npu`) need no additional seam.
- **Monkeypatch compatibility**: the built-in `PlatformTransferBackend` resolves `gpu_worker` module globals at call time, keeping the existing test patching style (`gpu_worker.host_register`, `HAS_TRITON`, `_select_swap_blocks_fn`) working unchanged.
- **Complexity**: ~210 new source lines (Medium); the hot path adds one indirection (`self._backend.select_copy_op` resolved once at handler init; `descriptor_ptr_dtype` per buffer allocation) with no steady-state impact.
