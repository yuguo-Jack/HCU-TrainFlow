# [Bugfix][MoE] Cap float32 fused MoE tile sizes and stages to prevent shared-memory OutOfResources (#61847)

[Upstream PR](https://github.com/vllm-project/vllm/pull/61931) · state: open · merged: False

## Original PR description

## Overview

Fixes #61847 by capping default Triton fused-MoE tile sizes (`BLOCK_SIZE_M`, `BLOCK_SIZE_N`, `BLOCK_SIZE_K <= 64`) and pipeline stages (`num_stages = 2`) when executing with float32 activations/weights, preventing `triton.runtime.errors.OutOfResources` shared memory crashes on Ada / SM89 GPUs.

## Claims

- **Prevents OutOfResources Crash**: Eliminates the `triton.runtime.errors.OutOfResources: out of resource: shared memory, Required: 131072, Hardware limit: 101376` crash during startup profiling on SM89 when unquantized MoE models are run with `dtype="float32"`.
- **Hardware-Conforming Shared Memory Allocation**: Caps maximum shared memory usage per thread block for float32 fused MoE to `<= 65,536` bytes, safely fitting within SM89's 101,376-byte limit and other GPU hardware architectures.
- **Preserves Existing Paths**: Default configurations for `bfloat16`, `float16`, and `fp8_w8a8` remain completely unchanged.

## Validation

- **Unit Testing**: Added `test_fused_moe_default_config_float32` in `tests/kernels/moe/test_moe.py` covering all batch sizes (`M in [1, 16, 32, 64, 128, 512, 1024]`) across string and tensor representations (`"float32"`, `"fp32"`, `torch.float32`), asserting that required shared memory stays `<= 101,376` bytes.
- **Lint / Code Quality**: Tested with `ruff check` on both modified files with zero errors.

## Details

On SM89 GPUs (e.g. RTX 4090, RTX 5880 Ada, L40, L40S), the hardware shared memory limit per thread block is 101,376 bytes. Float32 elements use 4 bytes per element (2x the 2 bytes of FP16/BF16).
In `get_default_config()`, the general unquantized fallback previously selected `BLOCK_SIZE_K = 128` (when `M <= 64`) and `num_stages = 4` (when `M <= 32`). Because float32 doubles the size of tiles in shared memory, this caused Triton to allocate 131,072 bytes for the software pipeline, exceeding the hardware limit of 101,376 bytes and failing during `profile_run` / dummy forward.

This fix:
1. Detects float32 in `get_default_config` (`dtype in ("float32", "fp32", torch.float32)`).
2. For float32, caps `block_m <= 64`, `block_n = 64`, and `block_k = 64`, and sets `num_stages = 2` (mirroring ROCm's shared memory protection).
3. Caps shared memory requirements per block to at most `2 * (64*64*4 + 64*64*4) = 65,536` bytes, comfortably below 101,376 bytes.
