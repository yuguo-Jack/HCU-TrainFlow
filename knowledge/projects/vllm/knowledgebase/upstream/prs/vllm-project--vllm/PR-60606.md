# [ROCm][Perf] Gather MLA DCP query with AITER all-gather

[Upstream PR](https://github.com/vllm-project/vllm/pull/60606) · state: open · merged: False

## Original PR description



## Overview
On ROCm, DCP's query all-gather runs through RCCL. This PR routes it through AITER's custom all-gather, which has already existed in vLLM's AITER custom collectives, through a dedicated communicator instance for the aiter DCP group.


## Claims
- On Kimi-K3, MI355X x8 with TP8 and DCP8, using AITER's all-gather achieves ~1% - ~4% output throughput across concurrency
- The aiter gathered query is identical to gathering through the RCCL path, and end-to-end accuracy is unchanged.
- Settings with DCP disabled are unaffected

## Details

When DCP is enabled, each MLA layer gathers the decode query across ranks in the DCP group before attention. On ROCm, it currently goes through RCCL, and since RCCL concatenates along dim 0, this path requires copying results so that the head ordering is correct. AITER's all-gather gathers along the last dimension, so gathering a query viewed as `[T, H * D]` is exactly gathering along the heads, and it's able to write into the final layout with no reordering copy. Measuring on Kimi-K3 with TP8 and DCP8, this decreases per-layer gather latency from RCCL path's 31.9us to AITER path's 16.2us in decode traces.

The is enabled for ROCm and only in single-node DCP settings when AITER custom all-reduce is enabled. When its requirements are not met, this gather falls back to using RCCL.

### Suggestion: reuse TP's AITER instance when the DCP group equals the TP group

When `decode_context_parallel_size == tensor_parallel_size` and PCP is 1, the DCP group contains the same ranks as TP, in the same order (`parallel_state.py`: DCP spans PCP, then TP). TP already has an `aiter_ar_comm` on ROCm by default. So the extra DCP instance only adds a second set of IPC buffers, and on Kimi-K3 TP8/DCP8 that costs about 0.36 GiB of KV cache per rank. Reusing TP's instance also removes the need for the `graph_capture` change in this case, because TP's capture already enters it. Configs where the DCP ranks differ from TP (DCP < TP, or PCP > 1) still build the dedicated DCP instance, exactly as this PR does now.

### Results

Setup: Kimi-K3 on MI355X x8, TP8/DCP8, `--dcp-comm-backend a2a`, `vllm/vllm-openai-rocm:nightly-rocm100-77154ca6`. The serve flags match the PR description, except that prefix caching is disabled. Benchmark: `vllm bench serve`, random 8192/1024, `num_prompts = 4 x conc`, run after a warmup pass. One run per arm.

| | main | this PR | this PR + TP reuse |
|---|---|---|---|
| GPU KV cache size | 33,896,102 tokens | 33,684,031 (-0.63%) | **33,978,575** (+0.24%) |
| Output tok/s, conc 16 | 569.65 | 587.95 (+3.2%) | 587.48 (+3.1%) |
| Output tok/s, conc 32 | 868.42 | 893.95 (+2.9%) | 891.68 (+2.7%) |
| Output tok/s, conc 64 | 1,189.90 | 1,212.22 (+1.9%) | 1,213.71 (+2.0%) |
| Output tok/s, conc 128 | 1,474.56 | 1,493.83 (+1.3%) | 1,490.85 (+1.1%) |
| Mean TPOT, conc 16 / 128 (ms) | 26.09 / 78.85 | 25.23 / 77.78 | 25.25 / 77.94 |
| gsm8k 20-shot, flexible / strict | 0.9682 / 0.9682 | 0.9636 / 0.9644 | 0.9666 / 0.9674 |

- **Memory:** with TP reuse, the KV cache goes back to main's level. This PR alone loses about 212k tokens, roughly 0.36 GiB per rank.
- **Performance:** the TP-reuse variant is within ±0.3% of this PR at every concurrency, so it keeps the gather speedup. TTFT is flat across all three arms.
- **Accuracy:** gsm8k differences between all three arms are within about 1 stderr (±0.005).
- **Correctness:** `test_distributed_aiter_q_gather_matches_rccl` (bf16 and fp8, including CUDA graph replay) passes with the TP-reuse variant. For that run the test was adapted to assert that the DCP communicator has no instance of its own and to use TP's instead.

Not covered here: DCP < TP (e.g. TP8/DCP4), which should take the dedicated-instance path unchanged.

Stress test results with the AgentX workload: with this PR we see a reproducible all-rank hang at higher concurrency. The same setup without the PR runs clean.

**Setup**
- MI355X x8, Kimi-K3 FP4, TP8 / DCP8, `dcp_comm_backend=a2a`, DSpark spec decode (4 tokens, synthetic acceptance length 3.36)
- `SimpleCPUOffloadConnector` (CPU KV offload), `FULL_AND_PIECEWISE` cudagraphs, `max-num-batched-tokens 8192`
- `VLLM_USE_DIRECT_DCP_Q_GATHER=0`, so the query gather goes through this PR's path (log: `Using AITER custom all-gather for the MLA DCP query.`)
- Image `vllm/vllm-openai-rocm:nightly-rocm100-49cb2bbf71cfd36ee5aa33d1e184b1cddff55294` (aiter 0.1.25), PR applied at `8033f2c`
- AgentX trace replay (`semianalysis_cc_traces_weka_062126`), 1 h measured run after warmup

**Hang signature on g10** (identical on both tries)
- Engine throughput drops to 0 with about 55–60 running requests, while CPU-offload KV loads are in flight.
- About 600 s later, every rank (0–7) times out on the same NCCL all-gather:
  ```
  Watchdog caught collective operation timeout: WorkNCCL(SeqNum=21277, OpType=_ALLGATHER_BASE, NumelIn=5529600, NumelOut=44236800, Timeout(ms)=600000)
  ```
  (try 1: `SeqNum=326677, NumelIn=4755456`)
- `NumelIn` is exactly `num_tokens x 12 heads x 576` (800 and 688 tokens), which matches the DCP query gather. In bf16 that is above the `should_custom_ag` limit (8 MiB per rank, about 606 tokens), so it is this PR's NCCL fallback inside `_aiter_query_gather`.

**Possible mechanism (hypothesis, not confirmed)**
- With the PR, the DCP group alternates between AITER `allgather_lastdim` (small batches, cudagraph decode) and NCCL `all_gather` (large mixed-prefill batches).
- One rank's GPU stream may have been blocked by an earlier AITER custom kernel still spinning in `start_sync`/`end_sync`. For reference, ROCm/aiter#4786 (open) changes the cross-device flag loads in `start_sync`/`end_sync` from `DEVICE` to `SYSTEM` scope. aiter 0.1.25 in this image still uses `DEVICE`.

**Review note:** the DCP direct workspaces are allocated per ubatch (`num_ubatches`), but the new AITER instance on the DCP group (one signal buffer, one staging buffer) is shared. With ubatch overlap enabled, two concurrent query gathers could use the same instance. That was not enabled in our runs.
