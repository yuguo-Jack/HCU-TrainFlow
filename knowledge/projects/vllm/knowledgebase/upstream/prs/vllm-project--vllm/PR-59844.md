# [Bugfix][DeepEP] Close GIN barrier data-visibility race in vendored DeepEP (per-context signals + NVLink fence)

[Upstream PR](https://github.com/vllm-project/vllm/pull/59844) · state: open · merged: False

## Original PR description

## Summary

DeepEP `d4f41e4e` (the commit we pin in `docker/Dockerfile` / `tools/ep_kernels/install_python_libraries.sh`) has a data-visibility race in `gin_barrier_wo_local_sync`, the completion barrier of low-latency dispatch/combine over NCCL GIN (GDAKI):

- The barrier publishes completion with a **single context-0 signal**, while dispatch/combine data rides **contexts 1..N as RDMA puts** and, for same-node peers, **NVLink TMA stores** to LSA symmetric memory.
- Signals and puts on different QPs are not ordered at the receiving NIC (confirmed by NVIDIA in nccl#2302; NCCL's own `ncclGinBarrier` with `ncclGinAllContexts` exists for exactly this failure mode), and GIN signals are not ordered with NVLink stores from other threads (fixed upstream in deepseek-ai/DeepEP#715, not in `d4f41e4e`).
- The receiver's copy epilogue (PDL-launched) can therefore read **stale raw-buffer rows from the previous dispatch**: phantom/missing expert routes, double-assigned slots, unwritten `recv_x` rows, occasionally OOB slots — the latter surfacing as the `combine_impl` illegal-memory-access crashes seen in DP=8 direct-mode nightlies.

Root-cause evidence (pristine DeepEP, host-side audit, zero kernel instrumentation): internal repro `repros/pr57991-waldorf-20260928/.../count-discrepancy-audit-20261002/REPORT.md`.

## The patch

`tools/ep_kernels/patches/deepep-gin-barrier-data-visibility.patch` — one file (`deep_ep/include/deep_ep/common/comm.cuh`), two changes mirroring shipped upstream fixes:

1. **Per-context signals**: after the existing flush + grid sync, signal every peer on every GIN context (`ginContextCount × kNumRanks` signals) and wait on the per-(context, signal id) slots. A signal posted on context `c` is SQ-FIFO-ordered behind all WQEs previously reserved on context `c`, covering the RDMA data puts. Mirrors NCCL's `ncclGinBarrierSession` with `ncclGinAllContexts` (`nccl_device/impl/gin_barrier__funcs.h`).
2. **`fence.acq_rel.sys` for world-team barriers** before the barrier signal, so same-node peers' NVLink TMA stores are visible before the GIN signal is published. Mirrors upstream DeepEP #715 (11d1cab), which postdates our pinned commit.

Applied in `install_python_libraries.sh` after the DeepEP clone, guarded to the pinned commit `d4f41e4e` (skips on any other ref) and idempotent (grep guard). `docker/Dockerfile` copies the new `tools/ep_kernels/patches` dir into the extensions-build stage.

## Why this is not duplicating an existing PR

No vLLM PR touches the DeepEP barrier. Upstream DeepEP has neither an issue nor a PR for this (checked 2026-10-03); v2.5 (93eb6eb) has the #715 fence but still signals on context 0 only, so it closes only one of the two holes.

## Test commands and results

  - Context: per-context signals alone (without the NVLink fence) did **not** pass validation — faulted with the same stale-row signature at a same-node (NVLink) sender pair within ~25 min, which is what motivated adding the fence. Pristine DeepEP faulted during warmup within ~3.5 min.

## Cluster validation of this patch (2026-10-03, 3× H200 4+2+2, DP=8 direct mode)

Same harness and config that reproduced the fault on pristine DeepEP and on per-context-signals-only:

| Build | Result |
|---|---|
| Pristine `d4f41e4e` | **FAULT** at warmup, ~3.5 min after server start (host/device cursor mismatch, impossible token-0 row header → stale raw-buffer row) |
| Per-context signals only (no NVLink fence) | **FAULT** at ~24 min — same stale-row signature, faulting sender was a **same-node (NVLink) peer** (rank 4→5), i.e. the fabric the patch didn't cover |
| **This patch (per-context signals + `fence.acq_rel.sys`)** | **NO-FAULT**: clean warmup + all 6 probe rounds (64/64 requests each), all 3 vLLM servers exited 0, all 8 audit ranks flushed `checkpoint` (not `fault`/`peer-fault`), no barrier timeouts, no IMAs |

Build provenance for the validated wheel: pristine `d4f41e4e` archive (sha256 `322b6f90…`) + this PR's patch (sha256 `fbde7fef…`, identical to `tools/ep_kernels/patches/deepep-gin-barrier-data-visibility.patch`), NCCL 2.30.7, `EP_NUM_TOPK_IDX_BITS=64`, `TORCH_CUDA_ARCH_LIST=9.0`.

The intermediate failure is what pinned the second hole: in `dispatch.cuh`, same-node (NVLink-accessible) peers receive data via TMA stores to LSA symmetric memory while the barrier signal is a GIN atomic — different fabrics, no ordering — which is exactly what upstream DeepEP #715 fixed with `fence.acq_rel.sys` after our pinned commit.

## Remaining caveats before this leaves draft

1. One clean ~41-min validation run is positive evidence, not proof (pristine hit rate was ~1 fault/run-day in production, though the warmup-churn harness faulted within minutes on both unfixed builds; both captured faults were NVLink-peer pairs, and a longer soak would raise confidence for the RDMA/per-context path).
2. No throughput regression visible in the probe rounds (steady ~12–14 tok/s, ITL ~570 ms across all 6 rounds), but a proper perf comparison against an unpatched baseline at prefill-heavy batch sizes has not been run.
3. Upstream issue for DeepEP is being filed separately; ideally this patch is replaced by a DeepEP-side fix and the pin bumped.
