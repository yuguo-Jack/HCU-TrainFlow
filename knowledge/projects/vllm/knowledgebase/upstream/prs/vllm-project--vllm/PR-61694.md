# [ROCm][Perf][Kimi-K3] Specialized decode: verify steps of 17-32 rows

[Upstream PR](https://github.com/vllm-project/vllm/pull/61694) · state: open · merged: False

## Original PR description

## Summary

Extends the Kimi-K3 MI355X specialized decode (#60683, now on `main`) from verify steps of at most 8 rows to **17–32 rows**: conc4 serving with DSpark k5 (24 rows) or k7 (32 rows). The switch is unchanged (`additional_config={"decode_backend": "latency_specialized"}`), and so are the refusals and the fail-stop. All changes are under `vllm/models/kimi_k3/amd/specialized_decode/` and its tests. No core files, no new CI step.

- **Widths**: every whole-request width up to 16 rows, plus 18, 20, 24, 28, 30 and 32 rows (those measured faster than vLLM's decode). Any other width runs vLLM's layers.
- **K1**: 16-row token tiles of whole requests, each with its own mailboxes. At the measured shapes (`kda.tuned`), 32 state rows per KDA task and in_proj weights parked in LDS.
- **K2** (`layer.tuned`):
  - Past 16 rows: a compact route table with per-expert pick lists.
  - At 8 block sources: AttnRes re-reads the blocks instead of holding them in LDS.
  - From 28 rows: the all-reduce and AttnRes run in 16-row panels, and the router and the latent and shared projections start on each panel as it lands.
  - Producer-side latent quantization.
- **30–32 rows**: a KDA layer runs vLLM's AttnRes and in_proj, then K1's KDA stages (`kda_post`, one independent CTA per request and head, no mailbox). It is a layer kernel behind `Step.layer(i)`; vLLM's own KDA forward is unchanged.

No weight is copied. Every new in-kernel wait goes through the health-checked `Mailbox`, so #60683's 10 s give-up and fail-stop cover them.

### Changes from the previous revision of this PR

The previous revision was stacked on #60683's old `mono/` layout (`9c6c96d8ef`). This revision is rebuilt on the merged #60683 and follows RFC #60904:

- **Removed**: the `VLLM_ROCM_MONO_DECODE` switch, the breakable-cudagraph dependency, the serialized CPU KV-offload path, and the edits to vLLM's KDA/MLA forward.
- **Dropped**: the combined K1+K2 launch for ≤16 rows. It only ran outside FULL graphs.
- **Dropped**: the packed copy of the in_proj weights (about 6 GB per rank). Its performance effect is being re-measured; see below.
- **Pruned**: K1/K2 experiment switches that no served shape selected.

## Not a duplicate

- **#60683** (merged) serves up to 8 rows. This PR adds the widths past it.
- **#61435** builds K1/K2 up to 64 rows but serves at most 16 (`MAX_ROWS = 16`). In its measurements, 32- and 64-row steps lost to vLLM (k=3: conc8/32 rows −20% to −22% tok/s, conc16/64 rows −36% to −38%). Its main additions are the MLA prologue/epilogue (M1a/M1b) and DCP8. This PR targets the 17–32-row steps #61435 leaves to vLLM, and does not touch MLA.
- Both PRs change K1/K2's multi-row code in `kda.py`, `layer.py` and `moe.py`, so whichever lands second rebases onto the other. Per-launch K2/K1 times at 24 and 32 rows for vLLM, #61435's kernels and this PR will be added below.

### AgentX conc4 (InferenceX recipe)

`kimik3/vllm/mi355x-fp4-mtp/agentic.yaml`, `override_tp8_c4`: TP8, DCP1, DSpark k=7, GPU-resident FP8 KV, prefix caching, FULL_AND_PIECEWISE (even capture sizes to 64), max-num-seqs 8. Synthetic acceptance at the recipe's golden length 3.84, as InferenceX CI sets it. 3600 s each, one run per arm, same node and image, run back to back. Every arm passed the InferenceX validator (request errors ≤ 0.6%).

The specialized decode needs the BF16 in_proj, so its arms drop the recipe's `--quantization-config` (FP8 in_proj). `main` BF16 isolates that change.

This PR compared with each reference:
- **vs the recipe as is**: +9.6% output tok/s, −19.0% mean TPOT, +13.5% p90 interactivity.
- **vs `main` BF16**: +8.7% output tok/s, −20.3% mean TPOT, +18.9% p90 interactivity.
- **vs #60683's specialized decode**: +5.5% output tok/s, −12.1% mean TPOT, +14.0% p90 interactivity.
