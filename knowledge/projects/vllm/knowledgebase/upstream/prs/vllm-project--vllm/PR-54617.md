# [Kernel][Quant][MoE] Per-forward NVFP4 W4A4/W4A16 selection for routed experts on SM12x

[Upstream PR](https://github.com/vllm-project/vllm/pull/54617) · state: open · merged: False

## Original PR description

## Purpose

Select the NVFP4 routed-expert precision per forward on SM120/SM121: W4A16
(BF16 activations) for small token counts, where decode is weight-bandwidth
bound, and W4A4 for larger ones, where FP4 tensor cores win. Both precisions
read one prepared expert weight copy, so the switch costs no extra memory.

This mirrors the dense NVFP4 dynamic selection in #54614 for MoE.

### How it works

- New NVFP4 MoE backend `moe_backend="flashinfer_cutile"`
  (`FlashInferCuTileNvfp4Experts`), built on FlashInfer's unified MoE API.
- At load, the checkpoint experts are converted once into the FlashInfer
  cuTile weight view (packed E2M1 weights, SM12x-swizzled E4M3 block scales,
  per-expert global scales, `[gate; up]` order). That view is registered for
  both runners:
  - W4A4 (`kernel_config.nvfp4_moe_dynamic_w4a4_backend`): `CuTileNvfp4Config`
    (`"cutile"`, default) or `SM12xNvfp4Config` (`"sm12x"`); both quantize
    activations in-kernel.
  - W4A16 (`kernel_config.nvfp4_moe_dynamic_w4a16_backend`):
    `CuTileNvfp4Bf16Config` (`"cutile"`, default) or `SM12xNvfp4Bf16Config`
    (`"sm12x"`).
  - The recommended configuration on SM12x is `"sm12x"` for both.
- `kernel_config.nvfp4_moe_dynamic_max_tokens=N` (opt-in, default 0): forwards
  with at most N tokens run W4A16, larger ones W4A4. The choice is made from
  the token count before any activation quantization, so each captured CUDA
  graph records the path for its size.
- During FlashInfer autotune passes both paths are tuned, so decode-sized
  buckets of the W4A16 path are not left on fallback tactics.
- Padding rows (expert id -1 under `VLLM_MOE_SKIP_PADDING`): the SM12x
  runners skip ids outside `[0, E)` themselves. When a cuTile runner is in
  use they are routed to expert 0 with a zero weight before dispatch, since
  the cuTile expert sort has no sentinel for -1 and otherwise places those
  slots over the first expert's assignments, corrupting real tokens in
  CUDA-graph padded batches.

### What is not included

- FlashInfer CUTLASS W4A4 MoE is not a candidate: it reorders w13 to
  `[up; gate]`, so pairing it with a `[gate; up]` W4A16 reader would need a
  second expert weight copy.
- Expert parallelism is not supported (same as the cuTile runners).

This replaces the earlier content of this PR (a layout key and
`VLLM_NVFP4_MOE_A16_MAX_M`), which only recorded why per-forward selection was
not possible with the B12X preparation path.

### Requirements

- FlashInfer with the unified MoE cuTile NVFP4 backends
  (flashinfer-ai/flashinfer#4646, flashinfer-ai/flashinfer#5099) and
  `cuda-tile`. `CuTileNvfp4Bf16Config` is first tagged in FlashInfer
  v0.7.1rc1; vLLM currently pins 0.7.0.post1, which has only the W4A4 runner,
  so with the current pin the W4A16 path reports itself unsupported. The
  FlashInfer bump is left to a separate PR.
- The `"sm12x"` candidates need flashinfer-ai/flashinfer#5735 (W4A16) and
  flashinfer-ai/flashinfer#5863 (W4A4, stacked on #5735), both open.

### Known limitations

- With the cuTile W4A4 backend, prefill is slower than the default
  FlashInfer CUTLASS NVFP4 MoE (TTFT +14% to +26% at 2K input below). With the
  SM12x W4A4 backend TTFT is at parity with the default.
- The cutoff is a fixed per-deployment value; per-GPU defaults will follow
  once end-to-end numbers on more models are collected.

## Test Plan

- `pytest tests/kernels/moe/test_flashinfer_cutile_nvfp4_moe.py -v` on DGX
  Spark (GB10, SM121), with both W4A16 candidates (`cutile`, `sm12x`): selection by token count, identical weight and scale pointers on
  both paths, correctness against a dequantized reference on both sides of the
  cutoff for SwiGLU and ReLU2, CUDA graph replay across the cutoff with new
  inputs and routing, and cutoff 0 never building the W4A16 path.
- Serving smoke test with `nvidia/Qwen3-30B-A3B-NVFP4`, `--moe-backend
  flashinfer_cutile` and `nvfp4_moe_dynamic_max_tokens=8`.

### End-to-end

DGX Spark (GB10, SM121), one node for all arms, SM clock locked at 1500 MHz.
`nvidia/Qwen3-30B-A3B-NVFP4`, TP1, FP8 KV, max model len 40960, max num seqs 8,
chunked prefill 2048, prefix caching off, CUDA graphs. SPEED-Bench prompts, 2K
or 32K input, 1024 output tokens, 12 measured requests after 3 warmup per
cell. Image `vllm/vllm-openai@sha256:b5406fca282e` with this change overlaid,
FlashInfer flashinfer-ai/flashinfer#5863 at e270c166 (includes #5735).

- A: default (`FLASHINFER_CUTLASS` NVFP4 MoE)
- C: `flashinfer_cutile`, W4A4 cuTile, W4A16 SM12x for <= 12 tokens
- D: `flashinfer_cutile`, W4A4 SM12x, W4A16 SM12x for <= 8 tokens (D2: repeat)

Cutoffs come from a per-layer crossover sweep on the same GPU. Median TTFT

## Notes for reviewers

- New backend: `vllm/model_executor/layers/fused_moe/experts/flashinfer_cutile_moe.py`
  (`CuTileNvfp4DynamicMoE` holds the two runners and the selection;
  `FlashInferCuTileNvfp4Experts` is the modular-kernel adapter).
- Weight conversion and quant config: `FLASHINFER_CUTILE` branches in
  `oracle/nvfp4.py`. Config: two `KernelConfig` fields in `vllm/config/kernel.py`.
- Opt-in only: nothing changes unless `--moe-backend flashinfer_cutile` is set.

## Duplicate check

No open PR adds unified-MoE cuTile NVFP4 support or per-forward precision
selection for MoE (searched open PRs for "cutile", "nvfp4 moe w4a16",
"W4A16 W4A4 MoE" and "nvfp4 dynamic moe"). #52032 (dynamic GEMM2 activation
quantization) and #59460 (explicit activation-quantization fallbacks) touch
nearby code but address different problems.

AI assistance was used to write this change; it has been reviewed and tested
by the submitter.



### Results on Qwen3.8-Flash-Next-NVFP4 (H2560, I640, E512, top-10), MTP with confidence stop

Same node, interleaved repeats, aiperf 2K in / 1K out, decode tok/s per user:

| GPU | Cutoff | c=1 | c=4 | c=8 | GSM8K-256 |
|---|---|---|---|---|---|
| DGX Spark (GB10) | 8 | +1.1% (within run spread) | +1.8% | +2.0% | 245 -> 249 |
| RTX PRO 6000 Blackwell Server Edition (600 W) | 16 | +7.5% | +4.0% | +2.5% | 248 -> 245 |

Baseline is `--moe-backend flashinfer_cutlass`; the drafter MoE stays on Marlin.
Acceptance length is unchanged. An agentic multi-turn replay finishes 1.7% faster
on GB10 and 3.9% faster on the RTX PRO 6000.

Per-layer routed-MoE time with real Flash-Next routing (CUDA graph, 48 rotating layers):
W4A16 wins at M <= 5 on GB10 and at M <= 16 on the RTX PRO 6000; SM12x W4A4 wins above
that and also beats CUTLASS W4A4 at prefill sizes. Decode on GB10 is close to the DRAM
floor (distinct experts x 2.76 MB / 273 GB/s), so the GB10 gain comes mostly from
dropping the CUTLASS expand/prefix-sum/activation/quant helpers.

Follow-ups in this PR:
- The SM12x W4A4 runner now gets the checkpoint activation scale (1/amax of the input
  scale, as the FlashInfer CUTLASS path uses) instead of a unit global scale.
- MoE layers with the same geometry share the SM12x W4A4 per-bucket scratch. Before
  this, every layer kept its own copy (about 5 KB per token per layer), which at
  max_num_batched_tokens 8192 took KV cache and doubled c=8 TTFT on the RTX PRO 6000.
- Layers without calibrated activation scales run as W4A16 at every token count.
