# [Bugfix][KV Connector][MoRIIO] WRITE: wait for every decode DP rank's handshake before writing

[Upstream PR](https://github.com/vllm-project/vllm/pull/63879) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

In MoRIIO WRITE mode with more than one decode instance (xPyD, y ≥ 2), the prefill can start writing a request's KV to a decode instance whose DP ranks are not all handshaked yet. The write task then fails with `KeyError: '<host>:<port>_dpN'`, and the decode request hangs in `WAITING_FOR_REMOTE_KVS`. This PR gates each WRITE on every DP rank of the target decode instance having a session, and waits for each instance met for the first time, not just the last one.

## Claims

- Fixes the `KeyError: '<decode-host>:<handshake-port>_dpN'` and the hung requests on first contact with a second decode instance.
- Starts one set of handshakes per decode instance while they are in flight. Previously they were re-submitted on every layer call until dp0 registered.
- Steady state, where every session exists, is unchanged. READ mode is unchanged.

## Details

**Request flow (WRITE, 1 P + 2 D, P already serving D1):**
1. The proxy sends request R to P with D2's handshake endpoint. P's scheduler adds R to `reqs_to_save`.
2. In each forward, `save_kv_layer` runs per attention layer. It must have a session for the D2 DP rank that will own R. D2's scheduler chooses that rank later, when it sends its block allocation (`RemoteAllocInfo.decode_dp_rank`). So **every** D2 DP rank needs a session.
3. P's first contact with D2 starts one handshake per D2 DP rank on a single-thread executor.
4. The write worker posts the per-layer RDMA writes to the chosen D2 rank (`_get_built_session`), then sends `write_done`.

**Root cause, in step 2 on `main`:**
- (a) Readiness is `"<engine>_dp0" in _remote_agents` (comment: "we only need to check if dp0 in rank"). dp0's callback registers it while dp1..N−1 are still queued behind it. From then on, R's layers are written, and the worker raises `KeyError` for `_dpN`.
- (b) The post-loop wait only checks the **last** request's engine. If the batch is `[R→D2 (new), R'→D1 (ready)]`, the loop sees D1 ready and returns. R is not written for that layer, and on the next layer (a) lets it through.
- (c) The inner check `remote_engine_id not in self._remote_agents` compares the base id against keys that always end in `_dpN`, so it is always true. Every layer call re-submits all handshakes until dp0 registers.

The `KeyError` is caught by the write worker ("Write task failed … marking done"). That frees P's blocks but tells D nothing, so D's request waits forever.

**Why only xPyD with y ≥ 2:** with one decode instance, the first contact goes through the wait loop and blocks until the handshakes finish. After that, every session exists.

**Fix:**
- Readiness is now "every `(dp[, tp target])` session key is in `_remote_agents`". These are the same keys `_background_moriio_handshake` creates.
- A handshake starts only if none of those keys has an in-flight future. A failed handshake leaves no future behind, so it is retried.
- After the loop, the code waits (bounded by `transfer_timeout`, as before) for **each** instance still handshaking. Then it writes that instance's deferred requests for the current layer.
- Two small supporting changes:
  - The handshake future is registered before its done-callback is attached. A future that finished early could otherwise leave a stale in-flight entry.
  - The WRITE producer no longer puts entries on `_ready_requests`, which only the READ path drains.

**Compatibility and limits:**
- Changes are limited to the WRITE-producer branch of `save_kv_layer` and the handshake future bookkeeping.
- There is no new host/device synchronization.
- The first-contact wait still blocks the forward thread for the duration of the handshakes. That matches the existing single-instance behavior, typically 8 sequential ZMQ round-trips of about 1–10 ms each.

**CI coverage gap:** xPyD WRITE needs at least 3 multi-GPU MI300X/MI355X nodes with RDMA, which CI doesn't have. The E2E results above were measured outside CI.

Related:
- #62552 (draft) fixes the same `KeyError` in the write worker instead: each write task waits until its target decode rank's metadata is present, and a task that still fails sends `write_failed`. This PR gates earlier, in `save_kv_layer`, on all DP ranks of the instance, and also fixes the per-layer handshake re-submission (c) and the last-engine-only wait (b). The two merge without textual conflicts; reviewers may prefer one approach, and I'm happy to fold the parts of this PR that #62552 lacks into it instead.
- #63855 replaces the busy-wait in `save_kv_layer` with parking and will conflict with this PR.
- #58962 adds a consumer-side WRITE timeout, which would bound the hang but not prevent it. #39276 touches the same file for a different DP issue.
