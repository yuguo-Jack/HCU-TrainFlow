🔴 Chat Completions callers with no chat template now get a 500 Internal Server Error instead of 400 Bad Request. ChatTemplateResolutionError used to subclass ValueError (caught by error_response.py's ValueError fallback -> 400); here it's redefined as VLLMServerError, which is checked first and maps to 500. It's raised in vllm/renderers/hf.py:796 and reaches users via render_messages -> render_chat (vllm/entrypoints/openai/chat_completion/serving.py:279) uncaught. Fix: keep this a client-facing 4xx (e.g. VLLMValidationError/VLLMClientError) so a missing/invalid chat_template still reports 400, not 500.

<details>
<summary>Why this was flagged</summary>

A chat completion request for a model whose tokenizer has no chat template and no chat_template is supplied triggers safe_apply_chat_template to raise ChatTemplateResolutionError at vllm/renderers/hf.py:796. This propagates through render_messages/render_chat, called uncaught at vllm/entrypoints/openai/chat_completion/serving.py:279, into create_error_response in vllm/entrypoints/serve/exception_handling/error_response.py, which now matches the VLLMServerError branch (status 500) instead of the old ValueError fallback branch (status 400). This is a client-fixable condition (pass a chat_template) so it should be 400 as on the base branch; the commit e4c38db kept the misleading docstring 'subclass of ValueError for backward compatibility' while changing the base class to VLLMServerError.

**Verification:** Base branch defined `class ChatTemplateResolutionError(ValueError)` (bc3ddb1:vllm/renderers/chat_utils.py:90), which falls through to the ValueError fallback → 400 BadRequest. HEAD redefines it as `class ChatTemplateResolutionError(VLLMServerError)` (vllm/exceptions.py:65), which matches the VLLMServerError branch first → 500 InternalServerError.

</details>

🟡 (optional) Importing vllm.renderers.chat_utils now permanently pollutes types.py's own __all__ list with names it never defines, a bug the old monolithic chat_utils.py (no __all__ at all) could not have. Line 24 does `from .types import __all__ as all_types`, which binds the same list object as `vllm.renderers.chat_utils.types.__all__`; line 26 `__all__ = all_types` aliases it into this module, and the `__all__ += [...]` on lines 27, 32, 33, 38, 45 mutate that shared list in place, appending names like ChatTemplateConfig into types.py's __all__ even though types.py defines none of them. Fix: build a new list (e.g. `__all__ = [*all_types, "ChatTemplateConfig", ...]`) instead of mutating the imported list in place, so types.__all__ stays scoped to names types.py actually defines.

<details>
<summary>Why this was flagged</summary>

Any import of vllm.renderers.chat_utils (which almost every renderer/entrypoint module does) runs __init__.py top to bottom. `all_types` at line 24 is the same list object as types.py's module-level __all__, not a copy. The `+=` list augmented-assignment on lines 27-45 calls list.__iadd__, mutating that shared object, so `vllm.renderers.chat_utils.types.__all__` ends up containing names like 'ChatTemplateConfig' and 'MultiModalItemTracker' that are not defined anywhere in types.py. A later `from vllm.renderers.chat_utils.types import *` (a pattern already used inside this same package's __init__.py) or any introspection/doc tool that reads types.__all__ and does getattr for each name would hit AttributeError. On the base branch this situation cannot occur: chat_utils.py was a single module with no __all__.

**Verification:** nit. Line 24 `from .types import __all__ as all_types` binds the same list object as `types.__all__` (defined at types.py:28-54). Line 26 `__all__ = all_types` aliases that object; the `__all__ += [...]` on lines 27/32/33/38/45 mutate in place, so `types.__all__` ends up containing names it never defines. The base monolithic chat_utils.py had no __all__, so this is new.
