# [Security] Apply media byte limits to Rust frontend

[Upstream PR](https://github.com/vllm-project/vllm/pull/61067) · state: open · merged: False

## Original PR description



## Overview

Pass vLLM's configured media byte limits to the supervised Rust frontend. The pinned multimodal crate already rejects oversized responses while streaming, but its default audio ceiling is 256 MiB rather than vLLM's 25 MiB default.

## Claims

- The Rust child receives the smaller of the vLLM media download limit and the audio filesize limit for audio, and the media download limit for image and video.
- Existing stricter crate limits remain in force; values above the crate's 256 MiB default do not loosen its protection.
- The process environment of the Python supervisor is unchanged.

## Details

The Rust frontend constructs the pinned multimodal connector using its defaults. Its audio input cap is 256 MiB, while vLLM documents a 25 MiB default compressed audio cap. The launcher now sets the crate's input-limit environment variables before starting the Rust child, so all HTTP and gRPC routes that share that connector receive the same bound. The change also honors a lower operator-configured crate cap.

The crate's input cap applies to local and inline media as well as remote media. Thus an operator who sets a lower general download limit will also lower those inputs in the Rust frontend. The 256 MiB crate default remains the ceiling when vLLM is configured higher.

The change does not add an aggregate request or process budget. It closes the discrepancy between the documented per-item limits and the Rust connector's effective limits; aggregate media resource use is a separate concern.
