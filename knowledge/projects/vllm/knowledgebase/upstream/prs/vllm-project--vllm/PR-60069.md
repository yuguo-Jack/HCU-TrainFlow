# [Bugfix][Kernel] Share FlashInfer b12x MoE workspaces across layers

[Upstream PR](https://github.com/vllm-project/vllm/pull/60069) · state: open · merged: False

## Original PR description



## Overview

`FlashInferB12xExperts` allocates a separate b12x workspace and output buffer for every MoE layer. This PR makes identically-shaped layers share one set through FlashInfer's `shared_*` wrapper arguments (flashinfer-ai/flashinfer#4603, shipped in the pinned 0.7.0). Fixes the startup OOM in #49476.

**Draft:** the OOM fix is validated in eager mode, but with CUDA graphs on, a 32 GB RTX 5090 hits an illegal memory access during graph-capture profiling. I couldn't determine on that card whether the fault comes from this change or was already present (see Validation). Help from anyone who can run v0.31 b12x unpatched on a larger SM120 card would settle it.

## Claims

- `nvidia/Qwen3.6-35B-A3B-NVFP4` with `--moe-backend=flashinfer_b12x` at 256K context now passes `profile_run` on a single 32 GB RTX 5090. On unmodified v0.31.0 it fails there with OOM regardless of `--max-num-batched-tokens` (tried 4096 / 2048 / 1024).
- b12x wrapper memory goes from one copy per MoE layer to one per (shape, device). FlashInfer's PR measured ~68 GiB → ~1.2 GiB for Qwen3.5-397B. @jahnclawdmonet measured an 11.47 GiB KV-cache gap between b12x and marlin for the 35B on a PRO 6000 in #49476.

Hardware: RTX 5090 (SM120, 32 GB), vLLM v0.31.0 image with the patched file mounted, FlashInfer 0.7.0.post1, torch 2.13.0+cu130.
Config: `--moe-backend=flashinfer_b12x --kv-cache-dtype=fp8 --max-model-len=262144 --gpu-memory-utilization=0.92 --max-num-batched-tokens=4096 --max-num-seqs=16 --enable-prefix-caching`

**Open question:** unpatched v0.31 cannot get past `profile_run` on 32 GB, so I have no like-for-like control for the capture fault. Reasons it may predate this change: eager mode exercises the same shared buffers at batch sizes 1–16 without faults; nothing in `launch_sm120_moe` caches per-layer state on the workspace (the per-expert `dm_*` scale planes are rewritten on every launch); and #50189 reports Xid 31 with b12x and no sharing. I haven't proven it, though. If someone with a PRO 6000 could run unpatched v0.31 + b12x with CUDA graphs, that would answer it.

Unit tests (`tests/kernels/moe/test_flashinfer_b12x_moe.py`, run on an RTX 5070 Ti / SM120 inside the v0.31.0 image): **49 passed**, including the new `test_flashinfer_b12x_moe_shares_buffers_across_layers`. The existing correctness tests run back to back in one process, so they also exercise the module-level cache across tests.

CI: SM120 hardware is needed; the test file skips elsewhere.

## Details

**Root cause.** `FlashInferB12xExperts._ensure_wrapper()` lazily builds a `B12xMoEWrapper(use_cuda_graph=True, max_num_tokens=...)` per layer, and each one's `_allocate_buffers()` allocates its own static workspace, its own dynamic workspace (when `max_num_tokens` crosses the cutover) and its own output buffer. This happens inside `profile_run`, before the KV cache is sized, so `--gpu-memory-utilization` can't help.

**Fix.** A module-level `weakref.WeakValueDictionary` maps (experts, top_k, hidden, intermediate, max_num_tokens, local experts, activation, device) to the first wrapper built for that shape. Later wrappers pass its buffers as `shared_static_workspace` / `shared_dynamic_workspace` / `shared_output`. Per-wrapper caches (weight views, padded weights, folded alphas) stay per layer. Weak values mean the cache never keeps a freed model's buffers alive.

**Safety (as argued in flashinfer#4603):** layers execute sequentially on one stream; CUDA graphs record fixed addresses that stay valid; barrier state is epoch-based and restored after each launch; `apply()` copies the returned output slice out immediately.

**Tradeoffs and limitations:**
- Reads the owner wrapper's private attributes (`_static_workspace`, `_dynamic_workspace`, `_moe_output`). FlashInfer has no public accessor; the alternative is calling its internal `allocate_sm120_moe_workspace` and duplicating its static/dynamic selection logic, which seemed worse. Happy to switch if FlashInfer exposes one.
- Assumes no two MoE layers with the same shape run concurrently on one device. Dual-batch overlap would break that, but b12x already rejects EP (`_supports_parallel_config`), which DBO depends on.
- Requires FlashInfer ≥ 0.7.0 for the `shared_*` kwargs (currently pinned to 0.7.0.post1).

- adi-suresh01 · comment · 2026-10-15T07:01:08Z · [source](https://github.com/vllm-project/vllm/pull/60069#issuecomment-6186436650)

Test data for this on SM120, which answers the open question in the description: a like-for-like control for the capture fault.

The illegal memory access under CUDA graphs isn't caused by this PR. Unpatched v0.31.0 hits it on a 96 GB RTX PRO 6000 at the same capture size (2). It's the `-1` padding sentinel reaching the b12x kernels, and FlashInfer 0.7.1 or #57946 fixes it. Full table in #49476.

What this PR does on its own (1x RTX PRO 6000, v0.31.0, the flags from #49476):
- 96 GB, eager: KV cache 47.55 GiB -> 64.74 GiB
- 31.45 GiB memory cap (5090 stand-in), eager: OOM in `profile_run` -> boots with 6.14 GiB of KV cache
- 31.45 GiB cap, CUDA graphs, FlashInfer 0.7.1: boots with 5.55 GiB of KV cache, 3 concurrent requests coherent

With FlashInfer 0.7.1, which `main` already pins, this PR is the only change the 5090 case needs.
