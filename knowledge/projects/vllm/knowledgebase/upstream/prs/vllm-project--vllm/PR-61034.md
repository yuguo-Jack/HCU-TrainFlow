# [Perf][GDN] Cut host op calls in the eager prefill path of mixed steps

[Upstream PR](https://github.com/vllm-project/vllm/pull/61034) · state: closed · merged: False

## Original PR description



## Overview

Cut host-side PyTorch op calls in the GDN (gated delta net) layer's eager prefill path. That path runs in every mixed prefill + decode step, between the piecewise CUDA graph pieces. This PR changes no kernel and no numerics; outputs and states are bit-identical.

CUDA parity tests pass on A100 (below). The end-to-end serving A/B gives +1.0 point SLO pass and +2.4 % goodput at concurrency 20, and lets concurrency 18 pass in all three repeats. nsys shows mixed steps 11 ms shorter; py-spy shows the host-time drop in the GDN path.

No new CPU/GPU sync: the new `spec_tokens_first` flag is computed from a CPU tensor in the metadata builder, and py-spy shows 0 % of the worker's main thread in host syncs with the change. Validated outside CI (no A100 in CI). The new kernel tests need SM80+ and run on any such CI GPU. Written with AI assistance (Claude Code); the submitter reviewed every line.

## Claims

- **(a) Prefill SSM state gather / zero / scatter:** Python indexing becomes `index_select`, one `masked_fill_` and `index_copy_`. The metadata builder computes the mask and an int64 copy of the prefill state indices once per step.
- **(b) Spec / non-spec token split and merge:** the builder sets a CPU flag, `spec_tokens_first`, when all spec-decode rows lead the batch. MRv2 `sort_batch_req_ids` normally gives that order. With the flag set, the layer uses slices and 2 `copy_` instead of 6 `index_select` and 2 `index_copy_`. Other orders keep the gather path.
- **(c) q/k/v:** `rearrange_mixed_qkv(..., contiguous=False)` returns strided views at the three call sites that feed the recurrent update kernel. That kernel already calls `.contiguous()`. Other callers are unchanged.
- **Expected effect (estimate):** about 9–14 ms less host time per mixed step on Qwen3.8-Flash-Next (36 GDN layers), A100, TP8. The estimate comes from a py-spy profile, summarised below.

## Validation

**Why (measured, py-spy at 100 Hz on all TP workers, MRv2, Qwen3.8-Flash-Next-FP8, TP8 + EP, 8 × A100-SXM4-40GB, MLPerf agentic set at 16 concurrent sessions):**
- Mixed steps are host-paced. The worker's main thread spends about 80 ms of Python per mixed step, and 0 % of it is in host syncs.
- 71 % of that piecewise-forward host time is the eager GDN core.
- The three blocks changed here take about 8.0 ms (a), 8.1 ms (b) and 6.1 ms (c) per mixed step. These ms values are estimated from the sample shares.

## Details

- **Assumptions:**
  - Prefill state indices are non-negative and unique. Padded rows use `NULL_BLOCK_ID` 0.
  - `causal_conv1d_update` writes in place into its input. With (b), that input is a slice of `mixed_qkv`, so the spec rows of `mixed_qkv` are overwritten. The spec-only and decode-only paths already do this, and no later code reads those rows.
- **Not done:** the FLA chunk kernel reading and writing the state in place through indices, and folding (c) into `fused_post_conv_prep`. Both need kernel changes. With them the saving would be about 15–18 ms (estimate).
- **Size:** `qwen_gdn_linear_attn.py` +66 / −13 (with the int64 fix), `gdn_attn.py` +24; tests +371.
- **Commits:** (a), (b), (c), plus a fix that uses int64 indices for `index_copy_`. The A100 run caught that bug: the GDN state indices are int32. I am happy to squash.

I close this PR. Reasons:

If the eager path matters again (for example with internal prefill checkpoints, where the capture is off), I will measure it there first and open a new PR only with a clear end-to-end gain.
