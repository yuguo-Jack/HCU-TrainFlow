# [CI] Shard Humming B200/H100 evals, LM Eval Spec Decode and two entrypoints AMD mirrors automatically

[Upstream PR](https://github.com/vllm-project/vllm/pull/62513) · state: open · merged: False

## Original PR description



## Overview

Enrolls three long LM eval steps and two entrypoints AMD mirrors in `automatic_shard`. Two of the eval steps were taken out of #61473 because they failed on main at the time; main passes them again now. `lm-eval-humming-h100-default` also moves from three per-shard config lists to one combined list, as #62120 did for the MoE Refactor steps.

## Claims

| Step | Was | Planned shards |
|---|---|---:|
| `lm-eval-humming-b200-default` | one job | 3 |
| `lm-eval-humming-h100-default` | 3 config-list shards | 5 |
| `lm-eval-spec-decode-4xb200` | one job | 3 |
| `amd-entrypoints-integration-api-server-generate` | one job | 2 |
| `amd-entrypoints-integration-api-server-openai-chat_completion` | one job | 2 |

- Every test and every config runs exactly once across the shards, with the same environment as before.
- A config added later to `humming/config-h100.txt` is placed by the planner rather than by editing a shard list.
- The two AMD mirrors' base steps are already enrolled; a native mirror shards only when its own `mirror.amd` sets the flag too.

## Validation

- Planned each step with ci-infra main's `runtime_shard.plan_step` against this branch and main's timings.
- Rendered each step and mirror with the pipeline generator and ran every shard's commands against a mock test tree, as a PR build and with main's `pytest -p ci_otel` wrapper. Every test of every command ran in exactly one shard, with the same env (6/6 NVIDIA cases, 4/4 AMD mirror cases).
- For the three gsm8k steps, also ran the generated shard jobs against vLLM's real `tests/evals/gsm8k/conftest.py` and config lists, with the test body stubbed. All 14, 15 and 3 configs ran once each, and the plan matched every config ID main has timings for.
- `/ci run` covers the two AMD mirrors. The three LM eval steps are optional, so a build scoped to their keys follows the `/ci run` build.

## Details

- **`lm-eval-spec-decode-4xb200`** has three configs, one per shard. The longest is about the 20-minute target on its own, so the planner flags the step over budget. The wait still roughly halves.
- **Planner estimates for eval steps.** The planner counts test time, not the model load and server start that each shard repeats. #62120's H100 MoE Refactor step came in longer than planned for this reason, so `lm-eval-humming-h100-default` (5 shards of about 3 configs) is the one to watch in the scoped build.
- **`caplog`.** Two files in the Generate mirror assert on log text; the same files already run sharded in the enrolled NVIDIA step on main.
- **Timeouts unchanged (human).** As in #62077 and #62120, `timeout_in_minutes` stays per job. A single-job fallback (no plan, or the `VLLM_CI_RUNTIME_SHARD` rollback switch) would outrun it; fallback-aware timeouts belong in a central timeout setting.
- **Left out.** The spec decode AMD mirror runs under 20 minutes as one job. #61473 also touches two of these steps; it continues as #61831, which doesn't include them.
