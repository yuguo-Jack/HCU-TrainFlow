# [Bugfix] Reject prompt_logprobs=0 with --kv-sharing-fast-prefill

[Upstream PR](https://github.com/vllm-project/vllm/pull/62167) · state: open · merged: False

## Original PR description

Fixes #62122

## Purpose

With `--kv-sharing-fast-prefill`, requests asking for prompt logprobs are meant to be refused with a 400. `prompt_logprobs=0` (also produced by `echo=true` with `logprobs=0` / `top_logprobs=0`) bypassed this: the V2 runner silently returned wrong prompt logprobs, and the V1 runner hit an assertion in `gpu_model_runner.py` that took EngineCore down.

**Root cause:** the guard in `AsyncLLM.add_request` (`vllm/v1/engine/async_llm.py`) used `and params.prompt_logprobs`, which is falsy for `0`. It also only lived in the async front-end, so the offline `LLM` path was never checked.

**Fix:** move the guard to `InputProcessor._validate_params` (`vllm/v1/engine/input_processor.py`), next to the existing `prompt_logprob_token_ids` fast-prefill check, and test `params.prompt_logprobs is not None`. This covers both AsyncLLM and offline `LLM`, and can be unit-tested without a GPU. The error message is unchanged; it now also sets `parameter="prompt_logprobs"`. Pooling params are unaffected (the check sits in the `SamplingParams` branch).

## Test Plan

New unit test `tests/v1/sample/test_logprobs.py::test_prompt_logprobs_rejected_with_kv_sharing_fast_prefill`, parametrized over `prompt_logprobs` in `0, 1, -1`. It checks that:
- the request is rejected when fast prefill is on,
- requests without prompt logprobs are still accepted,
- prompt logprobs are accepted when fast prefill is off.

```
pytest tests/v1/sample/test_logprobs.py -k "fast_prefill" -v
```

Without the fix, all three cases fail (no error raised from `InputProcessor`).

## Test Result

- `ruff check` and `ruff format --check` on the 3 changed files: pass. `git diff --check`: clean.
   - `pytest tests/v1/sample/test_logprobs.py -v -k "fast_prefill or prompt_logprob_token_ids_require"` on CPU (torch 2.14.0, vLLM from source tree): **4 passed** (the new test for `prompt_logprobs` = 0, 1, -1, plus the existing `prompt_logprob_token_ids` test).
   - With the source change reverted and the test kept: **3 failed** (all three parametrizations), since `InputProcessor` had no `prompt_logprobs` guard before. The `0` case is the original bug; `1` and `-1` were previously caught only in `AsyncLLM`.
   - Not run: e2e with `--kv-sharing-fast-prefill` on a Gemma model (needs GPU).
