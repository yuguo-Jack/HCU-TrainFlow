# [Perf][Spec Decode] Drop 8 host torch dispatches per step on the DFlash/DSpark draft path

[Upstream PR](https://github.com/vllm-project/vllm/pull/58631) · state: closed · merged: False

## Original PR description

> [!IMPORTANT]
> **Scope: this is a host-dispatch microbenchmark, not an end-to-end throughput claim.**
> The numbers below are measured on the host draft path, with per-call dispatch counts. Against a multi-millisecond decode step a
> change of this size sits inside run-to-run variation (~1% on a conc=1 arm), so
> **no measurable serving throughput improvement is claimed, and none should be
> inferred.** The value is removing host torch dispatches that serialize against the GPU on a path that is
> on the critical path at low concurrency. Details under "Scope".

## Purpose

Two spots on the per-decode-step speculative draft path reduce tiny CPU tensors through torch ops, where the dispatch costs far more than the arithmetic. Both run once per decode step, on every rank. Same class as #58381.

### 1. `DFlashSpeculator.propose` — reduce a CPU tensor without torch dispatch

```python
max_seq_len = input_batch.seq_lens_cpu_upper_bound[:num_reqs].max().item()
```

`seq_lens_cpu_upper_bound` is already a CPU tensor, so the slice/max/item chain buys nothing. A zero-copy `.numpy()` view performs the identical reduction. At concurrency 1 the chain reduces a **single element**. This mirrors the `.numpy()` view already used in `rejection_sampler.py`.

### 2. `DraftModelSpeculator._build_attn_metadata` — `max_query_len` is already known

```python
max_query_len = int((query_start_loc_cpu[1:] - query_start_loc_cpu[:-1]).max())
```

The uniform caller builds

```python
query_start_loc_np = self.arange_np[: num_reqs + 1] * num_query_per_req
```

— a ramp of **constant stride**, whose padded tail is filled with a constant. So consecutive differences are `num_query_per_req` for real requests and `0` for padding, and the max is `num_query_per_req` whenever there is a request at all. Recovering it from the tensor costs two slices, a subtract, a max and an `int()`.

`max_query_len` is threaded through as an **optional argument defaulting to `None`**, so the existing computation still runs unchanged for every other caller — including the non-uniform `multi_module_mtp` path. `query_start_loc_cpu` is still built, since it is consumed downstream; only the reduction over it is skipped.

## Measurement

CPU only, no GPU and no profiler, so the numbers are uninflated. Measured at the concurrency-1 shape:

| | current | with this PR | removed |
|---|---|---|---|
| `seq_lens` reduction | 1.662 us | 1.325 us | 0.34 us |
| `max_query_len` recovery | 3.14 us | ~0 | 3.14 us |

About **3.5 us of host dispatch per decode step per rank**, and 8 torch dispatches.

To be clear about scope: this is a **host-dispatch claim, not an end-to-end one**. Against a multi-millisecond decode step it sits well below run-to-run variation, and I am not claiming a measurable throughput change. The motivation is the same as #58381 — host-side work on the draft path serializes against the GPU and propagates across ranks through the next collective.

@okorzh-amd Thanks for the careful review — I've reproduced all three findings, and they're all correct.

**The test.** You're right, and it's worse than "passes under broken versions": it passes with vLLM made entirely unimportable — 25/25 with `import vllm` raising. Every case either asserts torch/numpy's own semantics or exercises `_build_query_start_loc`, a *local reimplementation* of the function it claims to pin. It has no regression value.

**The `.numpy()` substitution.** Confirmed, and your point is stronger than the comment — it doesn't just cost time, it *adds* a dispatch:

```
buf[:n].max().item()        -> 3   slice, max, item
int(buf.numpy()[:n].max())  -> 4   detach, to.dtype_layout, resolve_conj, resolve_neg
```

which is the opposite of what this PR claims to do.

**`mamba_hybrid.py`.** Right on both counts — it's a target-model path affecting every hybrid model, outside the "draft path" scope in the title and unmentioned in the description, and the same pattern remains in `default.py:201`, `encoder_decoder.py:138`, `encoder_only.py:203`. If that pattern is worth changing it belongs in its own PR, applied consistently.

**On what was left.** With those dropped, the remaining idea is the `max_query_len` pass-through: `_build_uniform_attn_metadata` builds `query_start_loc` as a ramp of constant stride with a flat padded tail, so it already knows the max query length, and `_build_attn_metadata` then spends a slice/slice/sub/max/item chain rediscovering it from the tensor. Passing the value it already has removes 5 dispatches per call, with the fallback intact for every other caller. I still think that's a correct simplification — the code computes an answer it was handed — but it's a small, bounded host-side win that won't show up end-to-end, and it isn't worth more of your review time on its own.

So I'm closing this rather than re-pushing a much-reduced version. If the `max_query_len` idea is worth having later I'll bring it back as a focused PR with a test that actually exercises the call path and fails without the change.

Thanks again — the "passes under every deliberately broken version" check in particular was the right thing to run, and I should have run it myself.
