# [ROCm] Fix MiniMax-M3 sparse PA KV block count

[Upstream PR](https://github.com/vllm-project/vllm/pull/61889) · state: open · merged: False

## Original PR description


## Overview

MiniMax-M3 LBHNC interleaves K and V inside each block, so the V cache view has fewer rows than K. AITER `pa_decode_gluon` requires those leading dimensions to match and fails on the sparse decode path.

## Claims

- `_run_gluon_decode` now passes one page count to `pa_decode_gluon` by trimming K to V's length.
- The dropped K rows are the last block's V pages. No block-table page id addresses them (max id is `127 * 16 + 7 = 2039`).
- The trim stays inside `_run_gluon_decode`, so `_sides_are_packed` and `minimax_m3_sparse_block_page_stride` still see the original shapes and keep a block page stride of 16.

## Validation

Reproduced on MiniMax-M3 with the AITER sparse paged-attention decode path. Before the change, K and V enter the kernel as:

```text
k_cache  [2048, 1, 8,  16, 16]
v_cache  [2040, 1, 1, 128, 16]
```

## Details

LBHNC places a token's V pages a fixed half-block after its K pages. The gluon decode kernel carries one page id and applies it to both caches, so V's view is rebased by that half-block and is shorter than K. Using V's length for both the cache views and the FP8 scale arguments satisfies the kernel without changing the stride logic that reads the untrimmed shapes.
