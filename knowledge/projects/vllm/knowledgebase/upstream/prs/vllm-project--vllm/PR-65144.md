# [Bugfix][Rust Frontend] Include error sources in HTTP 400 messages

[Upstream PR](https://github.com/vllm-project/vllm/pull/65144) · state: closed · merged: True

## Original PR description



## Overview

The Rust frontend's HTTP 400 responses drop the source chain of request validation errors. A request pinned with `X-data-parallel-rank` to a rank the frontend does not own returns only `"engine-core error"`, hiding which ranks are connected. Related: vllm-project/vllm#64801.

## Claims

- HTTP 400 validation errors from `text_submit_error` / `chat_submit_error` include the full error report, matching the 500 branch and the gRPC path (`text_error_to_status`).
- Hyper connection errors in the trace log include their source chain.
- No other validation error message changes: `InvalidDataParallelRank` is the only one wrapped by a non-transparent layer.

## Validation

New test `chat_completions_unconnected_data_parallel_rank_reports_connected_ranks` mirrors the existing gRPC test `unary_generate_unconnected_data_parallel_rank_returns_invalid_argument`. It connects a mock engine at global rank 3 and pins the request to rank 0.

| | `error.message` |
| --- | --- |
| Before (test fails) | `engine-core error` |
| After | `engine-core error: data parallel rank 0 is not connected to this frontend; connected ranks: [3]` |

- `cargo nextest run -p vllm-server`: 553 passed, including the existing `error::tests` that pin other 400 messages.
- `cargo clippy -p vllm-server --all-targets -- -D warnings` and `cargo fmt --check`: clean.

## Details

`text_submit_error` and `chat_submit_error` formatted 400 messages with `"{error}"` (`Display`), while their 500 branch uses `to_report_string()`. The data-parallel rank error reaches them as `vllm_chat::Error::Text` → `vllm_text::Error::Llm` → `vllm_llm::Error::EngineCoreClient` → `InvalidDataParallelRank`. The first two layers are transparent, but `EngineCoreClient` is `#[error("engine-core error")]`, so `Display` stops there and the rank detail lives only in `source()`.

For the trace log: hyper 1.x prints only the error kind in `Display` (e.g. "connection error") and keeps the underlying I/O error in `source()`.

Other error formatting sites in production code were audited. The remaining `Display` uses format leaf errors (serde, I/O, join, parse errors), or types whose `Display` already embeds the inner error.
