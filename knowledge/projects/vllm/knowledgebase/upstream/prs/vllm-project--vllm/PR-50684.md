# [Bugfix] Preserve message-level tools on system messages (DeepSeek-V3.2/V4)

[Upstream PR](https://github.com/vllm-project/vllm/pull/50684) · state: open · merged: False

## Original PR description

## Summary

`_parse_chat_message_content()` (now in `vllm/renderers/chat_utils/chat_message.py`) only copies a message's `tools` field onto the resulting `ConversationMessage` when `role == "developer"`, dropping it for `role == "system"`.

The DeepSeek-V3.2, V4 and V4.1 encoders all read `msg.get("tools")` for system messages to render an inline tool-schema block. This is separate from the request-level `tools` parameter, which DeepSeek-V4's `apply_chat_template` already handles through a synthetic system message. A caller attaching tools directly to a system message through the `CustomChatCompletionMessageParam.tools` extension field had them silently discarded before they reached the encoder.

Found while deploying deepseek-ai/DeepSeek-V4-Flash-0731 on vLLM 0.26.0.

## Fix

- Keep `tools` on system messages when the message carries them. Plain system messages get no `tools` key, so existing conversations (e.g. `test_parse_chat_messages_empty_system`) are unchanged. Developer behaviour is unchanged.
- Correct the `tools` field docstring on `CustomChatCompletionMessageParam` and `ConversationMessage` ("The tools for developer role").

## Tests

`tests/renderers/chat_utils/test_text_only.py`:
- `test_parse_chat_messages_preserves_message_level_tools` (system and developer)
- `test_parse_chat_messages_system_without_tools_has_no_tools_key`

## Note

This PR originally also fixed the DeepSeek-V4 "high" `reasoning_effort` prefix. That was fixed upstream in #50580, so it has been dropped; the PR is rebased on current main.

- the-crypt-keeper · comment · 2026-08-02T19:56:09Z · [source](https://github.com/vllm-project/vllm/pull/50684#issuecomment-5160075282)

Independently confirmed bug 1 on a third stack: 4× L40S (sm89, TP=4), DeepSeek-V4-Flash-0731

`REASONING_EFFORT_MAX` holds the reference's **high** text byte-for-byte, and `grep "Beyond maximum"` returns nothing anywhere in the tree, so the real `max` prompt has never existed in vLLM. This also means any published `reasoning_effort="max"` numbers for this model measured through vLLM were actually `high`.

One thing worth catching before this lands, though: **the patch doesn't fix `low`, and in fact regresses it.**

The API-value → tier mapping lives in `vllm/tokenizers/deepseek_v4.py:43-52`, which this PR doesn't touch:

```python
elif reasoning_effort in ("max", "xhigh"):
    reasoning_effort = "max"
else:
    reasoning_effort = "high"      # low, minimal, medium all land here
```

Today that's harmless, because `"high"` renders no prefix — so `low` is correct purely by accident. Adding the `high` branch in `render_message()` removes the accident, and `low` starts emitting the high prefix.

Measured end-to-end: reference encoder from the checkpoint vs. `main` vs. this PR's head, `[{"role":"user","content":"Hello!"}]` in thinking mode, counting prompt tokens with the shipped `tokenizer.json`. Ground truth is **low=6, high=85, max=98**.

```
  request | want |          main |      PR#50684
----------------------------------------------------
     None |  low |         6 ok  |         6 ok
  minimal |  low |         6 ok  |        85 BAD
      low |  low |         6 ok  |        85 BAD
   medium | high |         6 BAD |        85 ok
     high | high |         6 BAD |        85 ok
    xhigh |  max |        85 BAD |        98 ok
      max |  max |        85 BAD |        98 ok

reasoning_effort='low'  ->  internal tier 'high'
  on main : 6 tok      with PR : 85 tok  (changed)      reference : 6 tok
```

So the PR converts "max silently becomes high" into "low silently becomes high." Both failure modes are in the wild right now across different providers — there's a writeup on [r/DeepSeek](https://www.reddit.com/r/DeepSeek/comments/1vdqjwr/openrouter_reasoning_effort_levels_are_broken_for/) that pins providers with fallbacks disabled and finds exactly these two signatures, using the same 6/85/98 fingerprint.

**The catch is that this is a genuine design conflict, not just an oversight.** #40982 (merged) explicitly documented `low`/`medium`/`minimal → high` as the intended compatibility mapping. That was never observable before, because `high` was a no-op — this PR is the first thing that makes it real. So the mapping needs a deliberate decision rather than a silent inheritance, and it'd be worth pulling @BugenZhao in.

For what it's worth, I'd argue for following the reference ladder: it ships with the checkpoint, it's what the model was trained against, and a user sending `reasoning_effort="low"` almost certainly does not want the maximum-effort prompt — that reading also makes the ladder monotonic, which the current one isn't. Concretely:

```python
_REASONING_EFFORT_ALIASES = {
    "minimal": "low", "low": "low",
    "medium": "high", "high": "high",
    "xhigh": "max",   "max": "max",
}
```

with unknown values falling back to `low` and warning, rather than being silently promoted. That's the full 7-value surface from the `Literal` in `chat_completion/protocol.py:245`, and it makes all seven rows above pass.

Two smaller notes on the encoding change itself:

- `assert reasoning_effort in ['max', None, 'high']` still can't express the reference's `low` tier — `None` is doing double duty as "unset" and "low". Since `DEFAULT_REASONING_EFFORT = "low"` upstream, accepting a literal `"low"` (rendering `""`) would make the two encoders line up 1:1 and makes the tier set self-documenting.
- Rather than two module-level constants, mirroring the reference's `REASONING_EFFORT_PROMPTS: Dict[str, str]` keyed by tier keeps this diffable against `encoding_dsv4.py` when the checkpoint updates the text — which is how both of these bugs would have been caught mechanically.

Separately: **bug 2 is real and I'd like to see it merged regardless of how the above shakes out.** Traced the path — `render_message()` reads `tools = msg.get("tools")` (`deepseek_v4_encoding.py:219`) and renders it under `role == "system"` (:235), but `_parse_chat_message_content()` only ever copies `tools` through for `developer`, so a system-role message loses them before the encoder ever sees them. Worth stating the scope explicitly in the PR description, since "tools dropped" reads scarier than it is: request-level `tools` are unaffected, because DSV4's `apply_chat_template` injects its own synthetic system message downstream of the parse. What breaks is specifically the `CustomChatCompletionMessageParam.tools` extension field on a system message — which is a documented vLLM API, and the DSV3.2 encoder has the same expectation, so this isn't DSV4-specific.

Given they're independent bugs in different subsystems with different reviewers, these might land faster as two PRs — the `chat_utils.py` change looks uncontroversial, whereas the reasoning ladder now has a semantics question attached to it.
