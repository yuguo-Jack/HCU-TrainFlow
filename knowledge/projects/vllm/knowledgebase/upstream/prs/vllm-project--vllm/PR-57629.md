# [Bugfix][Core] Release pinned host cache before discarded wake remap

[Upstream PR](https://github.com/vllm-project/vllm/pull/57629) · state: open · merged: False

## Original PR description

Assisted-by: Claude

## Purpose

Fixes #50011.

On unified-memory systems such as DGX Spark / GB10, PyTorch's pinned-host allocator can retain a freed CPU backup in its cache after `wake_up()` restores it to device memory.

Because host and device allocations compete for the same physical memory on these systems, that cached pinned memory can contribute to the wake-time memory spike.

This PR keeps the existing `wake_up()` flow unchanged and makes the smallest possible modification after restoring a CPU-backed allocation:

1. drop the remaining local reference to the backup tensor;
2. call `torch.accelerator.empty_host_cache()` so the freed pinned-host memory can be returned before wake continues.

No public API or C++ allocator changes are introduced.

## Test Result

The current two-line implementation passes Python syntax compilation:

PASS


The underlying pinned-host-cache behavior was previously validated on an NVIDIA DGX Spark (GB10, unified memory):
pinned-host allocated memory before empty_host_cache(): 1024 MiB
pinned-host active memory:                                  0 MiB

after torch.accelerator.empty_host_cache():

pinned-host allocated memory: 1024 MiB -> 0 MiB
process RSS: decreased by ~1 GiB


During the earlier DGX Spark investigation, releasing the pinned-host cache before continuing wake also allowed the previously failing ~60 GB KV-cache case to wake successfully.
