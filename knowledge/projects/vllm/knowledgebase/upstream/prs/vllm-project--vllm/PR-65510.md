# [Mamba] Store ReplaySSM ring trackers in the Mamba page; put the dt ring last

[Upstream PR](https://github.com/vllm-project/vllm/pull/65510) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Stores the ReplaySSM ring trackers in the Mamba page and puts the dt ring last, which removes `MambaSpec.state_alignment`. Stacked on #55688 and drafted until it merges: until then the diff includes its commits, so review the last two commits. Needs [flashinfer-ai/flashinfer#8548](https://github.com/flashinfer-ai/flashinfer/pull/8548) (strided trackers) and a FlashInfer release that contains it.

## Claims

- The per-slot `(ring_start, num_committed)` trackers are a sixth Mamba state. Block copies, the align pre-copy and KV cache accounting cover them, so the off-page tracker allocation, binding, block-copy tensors and cleanup are removed from both model runners, the extensible KV cache and the worker utils.
- The page order is conv, ssm, x, B, dt, trackers. FlashInfer's 16-byte-sensitive states (ssm, x, B) start aligned without per-state padding, so `MambaSpec.state_alignment` is removed. A one-time check raises a clear error if a layout would misalign them.
- On Nemotron-3.5 Lightning NVFP4, GSM8K accuracy, MTP acceptance and prefix-cache hits match #55688 within run-to-run variation.
- Serving performance is unchanged within measurement resolution: with MTP acceptance and MoE routing fixed, the output-throughput change is between −0.34% and +0.05% at concurrency 1–32, with 95% confidence intervals inside [−1.05%, +0.44%], and −0.13% [−1.33%, +1.07%] at 64. nsys shows the only added GPU time is ~0.1% of a step, from the per-layer tracker copies and writes.

## Validation

**E2E:** Nemotron-3.5 Lightning 30B-A3B NVFP4, one B200, V2 model runner, FlashInfer ReplaySSM (`--replayssm-buffer-len 16`), FP16 SSM state with stochastic rounding (5 Philox rounds), MTP3, FP8 KV cache, prefix caching with `--prefix-match-unit 326` (the Mamba block is 2608 tokens). Baseline is #55688's head `a8877fadf6`; both runs use FlashInfer with [flashinfer-ai/flashinfer#8548](https://github.com/flashinfer-ai/flashinfer/pull/8548) and the same server command.

GSM8K: two runs per side, each with its own server start; values are means with the range in brackets.

GSM8K, 1,319 questions, five shots, greedy, concurrency 64:

| | Accuracy | Mean acceptance length | Prefix-hit tokens (each run) |
|---|---:|---:|---:|
| #55688 | 85.45% [85.4–85.5] | 3.439 | 859,336 of 958,923 |
| This PR | 84.55% [84.5–84.6] | 3.444 | 859,336 of 958,923 |

The GSM8K difference is within run-to-run variation: even without stochastic rounding, at concurrency 1, two runs of #55688 give identical completions for only 95 of the first 200 questions (85.5% and 85.0%). This PR matches them on 88 and 86 (84.5%). Both sides hit the prefix cache for the same 129,748 of 145,415 tokens.

Serving, output throughput of this PR relative to #55688:

| Concurrency | Change | 95% CI | Server starts per side |
|---:|---:|---|---:|
| 1 | +0.05% | [−0.06%, +0.15%] | 6 |
| 8 | −0.34% | [−0.68%, +0.00%] | 10 |
| 32 | −0.31% | [−1.05%, +0.44%] | 10 |
| 64 | −0.13% | [−1.33%, +1.07%] | 6 |

For scale, #55688 serves 849 / 2,814 / 5,687 / 7,794 output tok/s at concurrency 1 / 8 / 32 / 64 on one node. How the runs were made low-noise:

- Same work per step on both sides: MTP acceptance fixed by synthetic rejection sampling at the acceptance length measured above (`"rejection_sample_method": "synthetic", "synthetic_acceptance_length": 3.441`), MoE routing fixed with `VLLM_MOE_ROUTING_SIMULATION_STRATEGY=uniform_random`, greedy sampling, `--ignore-eos`.
- Random prompts around 1024 in / 512 out with per-request lengths (`--random-range-ratio 0.5`), seeded identically on both sides. With fixed lengths, requests move in lockstep and throughput at concurrency 32 varied by up to 5% between identical runs.
- An untimed warm-up, then each point with its own seed, so later points do not hit the prefix cache from earlier ones.
- A whole B200 node per run, with the server and client pinned to the GPU's NUMA node. On a shared node, identical runs varied by up to 6%.
- Server starts interleaved between the two sides on two nodes, two repeats per start, compared per seed. Identical runs of #55688 on one node agree within 0.0–2.0%.

nsys (benchmark window only, c = 8 and 64) shows the same total GPU kernel time on both sides (−0.05%, +0.30%). The PR's two Mamba bookkeeping kernels are slower, `precopy_mamba_align_fused_kernel` by 17–20% and `postprocess_mamba_fused_kernel` by 16–19%, as they now copy and write the trackers of every layer: about 3 µs per step at concurrency 8 and 20 µs at 64, roughly 0.1% of a step.

## Details

- Each layer's page holds its own copy of the group's trackers. The ReplaySSM kernels read a group's first layer and write all of its layers: `num_layers × num_reqs` int32 stores per step instead of `num_groups × num_reqs`.
- The fresh-slot reset now runs after the align pre-copy, in V1 and V2. The pre-copy copies a continuing slot's page, trackers included, and reads the null block when a group has no source; resetting afterwards keeps fresh slots at zero.
- The Triton decode planner takes a strided `ring_pos` and indexes it in 64 bits.
- Alignment relies on hybrid models padding the Mamba page to the attention page, a multiple of 16. A layout that misaligns ssm, x or B now fails at startup instead of being padded per state.
- The tracker offset in FlashInfer uses 32-bit operands with a 64-bit product; vLLM's FlashInfer pin is unchanged until a release includes [flashinfer-ai/flashinfer#8548](https://github.com/flashinfer-ai/flashinfer/pull/8548). With the current pin, FlashInfer rejects the strided trackers (`ring_start must be contiguous`).
