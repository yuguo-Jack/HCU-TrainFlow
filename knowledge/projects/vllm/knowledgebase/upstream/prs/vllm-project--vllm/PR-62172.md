# [Perf][Kernel] Let cooperative_topk read the BF16 indexer logits

[Upstream PR](https://github.com/vllm-project/vllm/pull/62172) · state: open · merged: False

## Overview

Stacked on #62171 (row-length single pass); only the last commit is new.

`cooperative_topk` now also reads BF16 logits. On SM100 the DSA indexer then keeps the paged MQA logits in BF16
instead of upcasting them to FP32 before the decode top-k. This extends what main already does for
`deep_select`.

## Claims

- One fewer kernel per indexer decode call on SM100/SM103 (the FP32 upcast `as_fp32_logits`), and the top-k reads
  half the bytes.
- The selected top-k values are the same as from the FP32 upcast: BF16 widens to FP32 exactly. Among exactly
  equal logits, which index wins was already unspecified.
- DCP, top-k backends that take only FP32, and BF16 rows that are not 16-byte aligned still upcast as before.
- On InferenceX AgentX, GLM-5.3 vs SGLang: together with #62170 and #62171, decode time on the same turns drops 2.0-2.9% on 4x GB200 (2.5-4.1% on 4x B300) at concurrency 1-16; by the forward benchmark this PR is about 1/3 of that.

## Validation

- `tests/kernels/test_top_k_per_row.py` on B300 (SM103): 285 passed, 37 skipped.
  - `test_cooperative_topk_rows_shorter_than_stride` now runs FP32 and BF16 logits through every cluster size and
    both paths. It compares the selected values with `torch.topk` and checks that no index repeats.
  - `test_sparse_indexer_topk_backend_resolution` checks when BF16 logits skip the upcast: `auto` or `cooperative`
    within the row limit, with a 16-byte-aligned stride. `persistent` and over-limit batches still upcast.
- Kernel time on B300 is the same for BF16 and FP32 input (10.3 us at 4 rows x 40K, 11.1 us at 16 rows), so the
  saving is the upcast kernel and its extra pass over the logits.
- Target verify forward latency (`vllm bench forward`, GLM-5.2-NVFP4, TP4, dummy weights, exact KV lengths, MTP verify shapes of B requests x 4 tokens, `max_model_len` 1M, CUDA graph; spread < 0.1%), B300, on top of #62170 and #62171:

## Details

- `CooperativeTopKParams`, the TMA staging buffers and the histogram loads are templated on the input type.
- TMA units are 16 bytes (8 BF16 or 4 FP32 elements), so the stride and per-block alignment follow the element
  size.
- Scores are widened to FP32 when binned, so both input types use the same radix keys.
- The extension dispatches on `logits.scalar_type()`.
- `SparseIndexerTopk.takes_bf16_logits` reports whether the resolved backend reads BF16 directly: `cooperative`
  (also as `auto`'s choice) when its constraints hold, and `deep_select`. The indexer upcasts only when it doesn't
  or when DCP is on. This replaces main's `topk_backend != "deep_select"` check with the same rule extended to
  `cooperative`.
- Candidate-block selection (DeepSeek-V4.1) already handles BF16 logits under `deep_select`. With `cooperative` it
  now gets them too. I could not run that model here.
