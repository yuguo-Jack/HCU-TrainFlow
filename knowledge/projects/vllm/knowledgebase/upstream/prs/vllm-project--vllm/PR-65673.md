## Overview

Fuse the two routing layouts needed by Humming indexed experts when w13 and w2
select different row block sizes. On small SM90 batches, one Triton launch
replaces two alignment/count-and-sort chains while preserving both GEMM tiles.

Related: [#53911](https://github.com/vllm-project/vllm/pull/53911) fuses DeepEP-v2
globalization with one alignment. This change handles two independently padded
layouts from already-globalized routes; deferred globalization keeps its existing
implementation.

## Claims

- Removes repeated routing work for small decode batches: the measured TP8 path
  uses one metadata kernel per layer instead of four, with no backend or tuning
  configuration change.
- DeepSeek-V4.1-Flash-1017 on 8×H200, TP8, concurrency 1: approximately 5% lower
  TPOT, with 4.46% / 1.25% lower complete-request latency at 16K / 128K input.
- Uses existing alignment operations for other architectures and larger workloads.
  Equal block sizes continue sharing one alignment. No prefill, memory-saving,
  or DP+EP speedup is claimed.

## Validation

Tested against `6b3488cc97eed1f3b0414d84699e95c686723ebb`, using the same native
extensions, environment and checkpoint for both sources. Humming 0.1.19,
PyTorch 2.13.0+cu130, Triton 3.7.1, FlashInfer 0.7.2.post1; MRV2,
MXFP4 experts, FP8 KV, block size 64, Engram CPU offload, no speculative decoding
or prefix caching.

**End-to-end serving.** TP8, concurrency 1, 8192 batched tokens, 128 output tokens.
Each entry is the median of three per-round request means, four requests per round.
Timings are from unprofiled requests.

| Input tokens | Baseline TPOT (ms) | This PR (ms) | Reduction | Baseline request latency (ms) | This PR (ms) | Reduction |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 16,384 | 6.721 | 6.346 | 5.58% | 1203.735 | 1150.028 | 4.46% |
| 131,072 | 6.309 | 5.990 | 5.04% | 3658.121 | 3612.308 | 1.25% |

The experiment used A1 / B / A2, including a return to the original source.
A1's 16K results drifted, so the table uses the faster control median for each
metric, rather than the slower first control. All rounds are retained.
Comparing the fastest control round with the slowest patched round still gives
5.39% / 3.66% lower TPOT at 16K / 128K. TPOT is a mean-per-request metric here,
not a token-latency p50.

**Mechanism.** A separate rank-0 trace over five decode steps shows routing
metadata launches decreasing from 800 to 200, including 200 calls to the new
kernel. Summed routing GPU time decreases from 2.067 to 0.309 ms. Other trace
categories also vary; these profile times are diagnostic, not end-to-end speedup.

**Operator and model checks.**

- Alignment suite: 677 passed, including 146 added cases covering route boundaries,
  invalid/nonlocal experts, local remapping, int32/int64 IDs, strided/offset
  inputs, padding and CUDA Graph replay after routes/maps change.
- Existing Humming routing, shape and output-buffer integration tests: 9 passed.
- Cold-L2 CUPTI under CUDA Graph, ABBA order, 200 samples per implementation:
  126 cases; all 60 fused cases improve 1.82–16.38×. The 66 reuse/fallback cases
  remain within approximately 2%. For 384 experts, six routes and blocks 8/40,
  the two layouts take 9.728 → 1.408 μs.
- TP8: 72 timed requests and 24 semantic checks succeed. A1/B match all eight
  semantic completion texts; maximum matched-token logprob difference is
  approximately 1.31e-4. These are smoke checks, not a full quality benchmark.
- 24 production-wrapper calls pass `VLLM_GPU_SYNC_CHECK=error`. Generated code
  has no spills in the inspected six- and 64-route cases. Applicable local
  formatting, lint, typing and CI-selection hooks pass.

**DP+EP coverage.** Separate TP1/DP8/EP8 serving A/B tests use 1024 input and
256 output tokens, three rounds per concurrency. Default grouped C1/C8/C64 and
explicit indexed C1/C8/C16/C64 complete all 42 timed points, 2016 requests and
32 semantic checks. Every accepted arm passes GPU-isolation auditing.
Neither backend shows an attributable improvement: grouped bypasses this helper;
indexed selects equal w13/w2 tiles and already shares alignment. C1/C8 profiles
show zero paired-kernel launches. The small measured throughput differences
(-0.54% to +2.00%) are not reported as gains from this change.

## Details

For `R = topk_ids.numel()`, the fused path requires SM90, `1 <= R <= 64`,
different positive block sizes and a maximum block size of 256. These bounds
limit the quadratic route comparison and padding initialization; they do not
depend on model name, weight dimensions, expert count, TP degree or weight dtype.

The kernel maps global to local expert IDs before grouping and ignores invalid
or nonlocal routes. It shares per-expert counts and route ranks, computes each
layout's padded offsets, and writes both layouts. It initializes all output padding on every
invocation, including graph replay. No device-to-host read or host synchronization
is introduced in the production wrapper.

The implementation stays in the existing alignment module, with a small Humming
call-site change. Weight padding, quantization, GEMM heuristics, backend defaults,
DeepEP deferred globalization and scatter retain their existing behavior. There
is no new environment variable or package dependency. Unlike
[#64978](https://github.com/vllm-project/vllm/pull/64978), which removes a count
load/fill from TritonExperts' alignment-free path, this prepares two layouts for
the existing indexed Humming GEMMs.

The alignment suite is added to the existing H100 CI job so CI can exercise the
SM90 path; existing MoE jobs cover fallback selection. Physical validation here
is H200 only. H100/non-SM90 hardware, DeepEP serving and a full model-quality
evaluation have not been run locally; upstream CI results are not yet available.
