# [Security] Restrict default CORS origins

[Upstream PR](https://github.com/vllm-project/vllm/pull/61009) · state: closed · merged: True

## Original PR description

## Overview

Default CORS settings currently allow any website to read responses from a browser-reachable vLLM server. Require operators to opt in to browser origins in both Python and Rust serving frontends.

## Claims

- Default requests from foreign origins receive no `Access-Control-Allow-Origin` header, and JSON preflight requests are not authorized.
- Explicit `--allowed-origins` settings continue to permit selected browser origins.

## Validation

- `VLLM_TARGET_DEVICE=cpu .venv/bin/python -m pytest --noconftest tests/entrypoints/serve/middleware/test_cors_middleware.py tests/entrypoints/launchers/test_cli_args.py -k cors -q` — 3 passed.
- `cargo fmt --all -- --check` — passed.
- `git diff --check` — passed.
- `pre-commit run --all-files` — relevant hooks passed; overall run failed on an unrelated XPU lockfile drift, existing Linux-only mypy attributes, and a `/private/var` path comparison in the non-root entrypoint test.
- Rust CORS tests: pending Linux run. A local macOS build fails in untouched `engine-core-client` because `socket2::Socket::domain` is unavailable on macOS.

## Details

The default allowed origin list was `["*"]` in both serving implementations. Browser scripts could therefore read API responses from reachable deployments that did not configure an API key. The new default is an empty list, while explicit origin allowlists and wildcard opt-in continue to work. Deployments that intentionally serve browser applications must configure `--allowed-origins` with their trusted origins.

This changes CORS response and preflight behavior. CORS is a browser access control and does not replace API authentication or prevent all simple cross-origin requests from being sent.
