## Original PR description

# optimized batched MoE token alignment kernel




## Purpose
This PR optimizes the `batched_moe_align_block_size` kernel to drastically reduce latency in high-throughput and long-context pre-fill scenarios. 

The previous implementation was hardcoded to launch exactly 1 block of 1024 threads. While this performed acceptably for small micro-batches (bound by CUDA launch overhead), it severely underutilized GPU resources (e.g., leaving 45+ SMs idle on modern GPUs) when scaling to large `max_tokens_per_batch` or high expert counts. It also suffered from uncoalesced memory writes and wasteful `O(N)` initialization loops for the sentinel values.

**Key Changes:**
*   **Grid-Scale Parallelism:** Removed the 1-block limitation. The kernel now maps 1 Thread to 1 Output Index, allowing dynamic grid scaling (`blocks = CEILDIV(sorted_ids_size, 1024)`) to fully saturate all available SMs.
*   **100% Coalesced Memory Access:** By mapping threads to global target indices instead of iterating via token counts, global memory writes are perfectly coalesced. 
*   **Eliminated O(N) Initialization:** Sentinel values are now written concurrently alongside valid token IDs, completely removing the upfront stride loops over `sorted_ids_size` and `block_ids_size`.
*   **Shared Memory Prefix Sum:** A redundant prefix sum over the batch tokens is calculated in dynamic shared memory per block, allowing massive multi-block scaling without cross-block atomic dependencies.

## Test Plan
*   Validated accuracy against a pure PyTorch reference implementation (checking `sorted_ids`, `block_ids`, and `num_tokens_post_pad` arrays).
*   Ran the official benchmark suite (`benchmarks/kernels/benchmark_moe_align_block_size.py`) to ensure no regressions in small-scale/decode performance.
* Ran the official test suite (`tests/kernels/moe/test_moe_align_block_size.py`) with all 441 tests passed.
*   Ran a custom high-stress benchmark sweeping over `num_experts` (8 to 256) and `max_tokens` (1024 to 16384) to measure pre-fill behavior.

## Test Result
Performance on small-scale routing (e.g., total tokens < 4096) remains identical to the baseline, as execution time is entirely dominated by the ~10µs CUDA launch overhead. 

Under heavy load (large `max_tokens_per_batch`), this optimization yields a **>2.5x speedup**.
