# [ROCm][Perf] Tune the Triton unified-attention 2D path for gfx1151

[Upstream PR](https://github.com/vllm-project/vllm/pull/56232) · state: open · merged: False

## Original PR description

## Summary

vLLM has no launch configuration for the 2D unified-attention path on ROCm, so it falls back on defaults. On gfx1151 (Strix Halo) that leaves long prefill an order of magnitude below the hardware's bf16 peak.

This series gives gfx1151 a 2D KV tile that matches the paged-cache block, a launch configuration for the 2D path, a wider query block for long prefill, and ranks `TRITON_ATTN` above `ROCM_ATTN` on gfx1151 so the tuned kernel is what gfx1151 actually runs.

End to end on gfx1151 against `upstream/main`, TTFT improves in 20 of 21 model/prompt-length cells (−1.4% to −34.4%). The remaining cell, Gemma-2B-AWQ at 128 tokens, is flat (+0.2%). Decode throughput improves in 20 of 21 cells; the remaining cell, Qwen3-4B-AWQ at 128 tokens, is flat (−0.1%).

## Commits

| commit | what it does |
|---|---|
| `[ROCm] Match the unified-attention KV tile to the block size on gfx1151` | A tile that straddles two KV blocks turns every tile load into a scatter, because the blocks are not contiguous in the paged cache. The 2D tile becomes the largest power of two that divides `block_size`, capped by the 64KB LDS budget. Matching them is worth 21% of TTFT on Qwen3-8B at an 8k prefill. Because the tile always divides the block, the last tile never reads a block-table entry past the end of the sequence, including for non-power-of-2 block sizes such as 1056. The 3D (split-KV decode) tile is not changed. |
| `[ROCm] Give the unified-attention 2D path a gfx1151 launch config` | Sets `num_warps`, `waves_per_eu` and a per-phase pipeline depth for the 2D kernel, with the depth bounded by the same LDS budget. |
| `[ROCm] Widen the unified-attention query block for long gfx1151 prefill` | Moves the query-block choice into `_select_query_block`; only gfx1151 is opted in. |
| `[ROCm] Prefer TRITON_ATTN over ROCM_ATTN on gfx1151` | On gfx1151, `ROCM_ATTN`'s custom paged-attention kernel only covers head_size 128 / block_size 16 / GQA 3-16 / unquantized KV / no SWA, alibi or sinks. Everything else already falls back to an internal Triton path. |

## Scope

Everything is gated on gfx1151 alone. gfx1151 is the only part benchmarked here, so the rest of the gfx11 family keeps upstream behaviour.

- **Existing code touched:** only the 3 lines of `BLOCK_M`/`BLOCK_Q` selection in `unified_attention`, which move into `_select_query_block`. Everything else is additive.
  - `_get_tile_size` is unchanged, so the INT4 per-token-head and TurboQuant kernels that share or mirror it are untouched.
- **Verification:** the kernel launch parameters `unified_attention` picks match `upstream/main` in all 2,800 bf16 shapes checked off gfx1151. The parameters compared are the grid, `BLOCK_M`, `BLOCK_Q`, `TILE_SIZE`, `num_warps`, `num_stages`, `waves_per_eu` and the `reduce_segments` launch. The shapes cover:
  - head sizes 64–256;
  - MHA/GQA/MQA;
  - block sizes 16–1056;
  - with and without a sliding window;
  - 2D and 3D decode, speculative decode, short and long prefill, and mixed batches.
- **3D decode on gfx1151:** also identical to `upstream/main`.

## Non-power-of-2 block sizes

Hybrid models, such as Qwen3.5-35B-A3B, pad the attention block size to a multiple of 16, for example 1056. Rounding such a block up to the next power of two would make the tile straddle blocks and read block-table entries past the end of the sequence. Using the largest power of two that divides the block avoids both.

Measured on gfx1151 by calling `unified_attention` directly (`triton.testing.do_bench`, bf16), against the first revision of this PR:

| shape | block | head_dim (q/kv heads) | first revision | this revision |
|---|---:|---|---:|---:|
| prefill 4096 | 1056 | 128 (32/8) | 19.70 ms | 12.22 ms |
| prefill 512 | 1056 | 128 (32/8) | 1.71 ms | 0.56 ms |
| prefill 4096 | 1056 | 256 (16/2), Qwen3.5-35B-A3B | 10.04 ms | 10.10 ms |
| spec decode, 32 × q4 | 1056 | 256 (16/2), Qwen3.5-35B-A3B | 1.77 ms | 1.23 ms |
| 3D decode, 1 × kv 2112 | 1056 | 256 (16/2), Qwen3.5-35B-A3B | 115 µs | 55 µs |
| 3D decode, 4 × kv 3000 | 128 | 128 (32/8) | `OutOfResources` | 0.40 ms |
| prefill 4096 | 48 | 256 (16/2) | 9.96 ms | 11.38 ms |
| prefill 4 × 100 | 48 | 80 (32/8) | 0.96 ms | 1.17 ms |

`block_size` 48 is the case where this costs time: the only power-of-two tile that divides it is 16. #56862, which masks the block-table load, would make a wider tile safe there. This PR does not depend on it.

## Accuracy

Setup:
- Full GSM8K test set: 1319 questions, 5-shot, greedy (`temperature 0.0`, `seed 42`).
- `Qwen/Qwen3-8B` in bf16, via `tests/evals/gsm8k/gsm8k_eval.py` against a `vllm serve` instance on each arm.
- Measured on `53b7271`. Qwen3-8B runs with `block_size` 16, whose attention launch parameters are identical in this revision.

| arm | attention backend | accuracy | correct | invalid |
|---|---|---:|---:|---:|
| `upstream/main` | `ROCM_ATTN` | 0.8802 | 1161 / 1319 | 0.0% |
| this branch | `TRITON_ATTN` | 0.8901 | 1174 / 1319 | 0.0% |

No accuracy regression is visible. The +0.99 points should not be read as an improvement:
- The two arms run different attention kernels (`ROCM_ATTN` vs tuned `TRITON_ATTN`), so their outputs are not expected to be bit-identical.
- A net difference of 13 correct answers does not say how many individual answers changed.
- The eval script records aggregates only, so no paired (McNemar) test was possible.

## Not a duplicate

- `_select_query_block` is modelled on #52684, which tunes the same code path for **gfx1100** and is still open. The two are complementary and conflict only textually: whichever lands first, the other should rebase and add just its own branch to the shared helper. This series deliberately carries no gfx1100 tuning, since that part is not ours and is not measured here.
- #56862 masks the block-table load in the same kernel. It is complementary: this series avoids the out-of-row read by construction and does not depend on it.
