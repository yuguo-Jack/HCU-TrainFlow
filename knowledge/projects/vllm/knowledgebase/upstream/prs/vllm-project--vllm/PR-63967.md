# [Bugfix][Rust Frontend] Check min_tokens against max_completion_tokens when both limits are set

[Upstream PR](https://github.com/vllm-project/vllm/pull/63967) · state: open · merged: False

## Original PR description



## Overview

The Rust frontend rejects chat requests that set `min_tokens`, a `max_tokens` below it, and a larger `max_completion_tokens`, even though `max_completion_tokens` overrides `max_tokens` and the Python frontend accepts them. This PR checks `min_tokens` only against the limit that is actually used.

## Claims

- `{"min_tokens": 2, "max_tokens": 1, "max_completion_tokens": 8}` on `/v1/chat/completions` and `/v1/chat/completions/render` now returns 200 with `min_tokens=2, max_tokens=8`, as on the Python frontend. On main it returns 400 `min_tokens cannot be greater than max_tokens`.
- `min_tokens` above the effective limit is still rejected, both when only `max_tokens` is set and when `max_completion_tokens` is.

## Validation

macOS arm64, Cargo 1.95, main `5d35ce393`. CPU only; no model weights needed.

- New unit test `validate_checks_min_tokens_against_the_effective_max_tokens` (six combinations of the three fields): fails on main on the `(2, 1, 8)` case, passes with this PR.
- HTTP check through the in-process router with the scripted engine used by `routes/tests.rs`: render, non-streaming chat and streaming chat with the request above. On main all return 400. With this PR they return 200, and the engine receives `min_tokens=2, max_tokens=8`. I ran these route tests locally and left them out of the PR, since the unit test covers the changed check.
- `cargo test -p vllm-server --lib routes::openai::chat_completions::`: 87 passed. `cargo fmt --check` and `cargo clippy --tests` are clean.

```sh
cargo test --manifest-path rust/Cargo.toml -p vllm-server --lib routes::openai::chat_completions::
```

## Details

`ChatCompletionRequest::normalize` moves `max_tokens` into `max_completion_tokens` only when the latter is unset, so with both set the deprecated `max_tokens` is kept but never used as the output limit. `validate_chat_cross_parameters` still compared `min_tokens` with it. Python resolves the limit with `max_completion_tokens` taking precedence whenever it is not `None` (`ChatCompletionRequest.build_tok_params`). It checks `min_tokens` only against that resolved value (`SamplingParams._verify_args`), so the stale `max_tokens` has no effect there. The fix skips the `max_tokens` check when `max_completion_tokens` is set, using the same `is not None` precedence.

Not covered: completions has no `max_completion_tokens` field, so it is not affected.
