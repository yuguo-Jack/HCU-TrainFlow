## Purpose

Paged shared memory storage for mm tensor ipc.

0. This compares two approaches for IPC of mm tensors:  

- **Paged shared memory (pshm):** mm tensor → shm → swap_blocks_batch → GPU  
- **ZMQ RPC:** mm tensor → ZMQ IPC → CPU Buffer → Pin Memory → GPU  

1. CPU‑to‑GPU (H2D) bandwidth saturates when transferring 1 MiB blocks, so a page size of 1 MiB is a reasonable choice for shared memory storage.

2. A typical multimodal data payload is around 10 MiB, which is larger than page size of 1 MiB. Therefore, using paged shared memory for storing and transferring mm tensors is practically meaningful.

3. For payloads smaller than one page (e.g., 0.5 MiB), shared memory space is wasted, and the performance is nearly identical to that of ZMQ RPC. Hence, such small payloads offer no practical advantage.

4. Every copy operation along the mm data path introduces overhead, with dynamic memory allocation and pin memory being particularly expensive. Thus, removing the ZMQ IPC → CPU Buffer → Pin Memory steps in the ZMQ RPC path would bring significant performance gains.

5. For server memory, multi-threaded copying is needed to achieve maximum server memory throughput. We use a Numba multi-threaded copy to accelerate it.

## Design

Recommended review order: cache.py -> serial_utils.py -> client.py -> storage.py -> manager.py -> server.py.

<details>

Currently, a very simple transport protocol is used:

- **Sender (P0) cache** (`PagedShmSenderCache`)

1. Call `open_write(item)` to allocate blocks for a given mm item.
2. async copy tensor data into the allocated SHM blocks (e.g., via `storage.write()`).
3. Call `close_write(uuid)` to finalize the write, making the item readable.

- **Receiver (P1) cache** (`PagedShmReceiverCache`)

1. Call `open_read(uuid_or_token)` to acquire a read lock and obtain the block list. If the item is still being written, the call may wait (with a configurable timeout).
2. Read the data from SHM into CPU.
3. After reading, the read lock is **released immediately** by calling `close_read(token)`. This is safe because the data has been copied to the target device; any asynchronous H2D transfers should be synchronized upfront if needed. The immediate release simplifies the lifecycle and avoids extra reference counting.

### Shortcomings

1. Currently, multiple mm items for the same request are allocated separately, which can lead to [the dining philosophers problem](https://en.wikipedia.org/wiki/Dining_philosophers_problem). This can be resolved by a single atomic operation `open_write(items)` for multiple requests. Furthermore, `open_write_or_read` could atomically allocate new blocks for cache misses and open existing ones for cache hits in a single call.

2. When `close_write(uuid)` is called, the corresponding `uuid` is briefly set to `IDLE`, which may cause the data to be evicted before P1 can read it. To address this, `open_write` supports `generate_read_token`, which creates a read token to temporarily pin the data and prevent eviction. When P0 calls `close_write(uuid)`, it will notify any waiting P1 that `open_read(token)` can now proceed. Of course, the read token must be transferred from P0 to P1.

3. A read token can be used by multiple `open_read` calls to support tensor parallelism. When `close_read(token)` is called, the token becomes invalid and can no longer be used for `open_read`.

4. This raises a timing issue for `close_read(token)`. Due to the inherently asynchronous nature of CUDA, an H2D transfer may not have completed when the launch returns, so `close_read(token)` cannot be called immediately unless a CUDA stream synchronization is performed. Another feasible timing for `close_read(token)` is when the request is fully completed. Regardless, we must ensure that close_read(token) is called for every opened token to avoid token leaks and to keep all items pinned.

5. Currently, batching of multiple requests is performed on the CPU, which prevents the low‑latency H2D path from SHM to GPU from being utilized.

</details>

#### Performance

Now you can use 100G+ of SHM as cache, and it uses the LRU eviction algorithm and is thread-safe.

Currently, aside from being able to use paged shared memory storage for the MM processor cache, paged_shm cache is slightly slower compared to LRU cache and SHM cache, because it does not yet use the fastest data flow channel. 

Currently, batching of multiple requests is performed on the CPU, which prevents the [low‑latency H2D path from SHM to GPU](https://github.com/vllm-project/vllm/pull/51349/changes#r3922552107) from being utilized. Based on a copy speed of 5 GB/s, every 10 MB takes 2 ms, which would block ZMQ IPC, whereas asynchronous writes to SHM do not block ZMQ IPC. 


> frankly, hitting the mm processor cache only saves 4ms in this test, so we should focus on the mm encoder cache instead.

`client.read()` internally releases the SHM read reference (`close_read`) when its context manager exits, but the CUDA DMA copy (`swap_blocks_batch`) launched via `_batched_transfer` is **asynchronous** on a non-default stream and is **not synchronized** before the lock is released. Helpful? Add 👍 / 👎

<details>
<summary>💡 Fix Suggestion</summary>

**Suggestion:** The race condition has two facets:

1. **`client.read()` releases the SHM read lock (`close_read`) before the async DMA completes.** The `read()` method bundles `open_read`, the actual data transfer, and `close_read` inside a single `read_context` context manager. Because `_batched_transfer` launches `swap_blocks_batch` on a non-default CUDA stream without synchronizing, the context manager's `__exit__` calls `close_read()` while the DMA is still in flight. Another writer can then overwrite the SHM blocks before the GPU read finishes.

2. **The `wait_stream` call at lines 254-255 is a no-op.** Inside `with stream:`, `torch.cuda.current_stream()` returns the same `stream` object, so `current_stream.wait_stream(stream)` is `stream.wait_stream(stream)` — waiting on itself, which does nothing.

To fix this properly:

**Option A (recommended — fix in `client.py`):** In `PagedShmClient.read()` (client.py ~line 478-492), after `read_to_tensor`/`read_to_device` returns but *before* the `read_context` exits, synchronize the current CUDA stream if it is a non-default stream. For example, add `torch.cuda.current_stream().synchronize()` (or the specific stream's `.synchronize()`) before the `with self.read_context(...)` block exits. This ensures the DMA is complete before `close_read` releases the lock.
