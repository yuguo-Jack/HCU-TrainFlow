# [CPU] Keep the hybrid block size across the engine core's config rerun

[Upstream PR](https://github.com/vllm-project/vllm/pull/61805) · state: closed · merged: True

## Original PR description



## Overview

On the CPU platform, prefix caching never hits for hybrid (Mamba / GDN) models when a prompt's prefill fits in one chunk: the block size the workers raise to fit the Mamba state pages is reset to the CPU default in the engine core, so Mamba prefill checkpoints are aligned to 128 tokens instead of the block size.

## Claims

- A repeated prompt on a hybrid model hits every full block on the CPU platform (Qwen3.5-0.8B: 640 of 960 tokens, previously 0), with one or more ranks.
- The CPU default block size (128, or what the attention backends prefer, e.g. 16 for CPU MLA) is applied in `update_block_size_for_backend()`, as on the other platforms, instead of in `check_and_update_config()`.

## Validation

Real forward, dummy weights, CPU build (x86, AVX-512), `max_num_batched_tokens` large enough for one prefill chunk, prompt of 4.5 blocks, sent twice:

| | TP=1 | TP=2 |
| --- | --- | --- |
| main | hits `[0, 0]` | hits `[0, 0]` |
| this PR | hits `[0, 2560]` | hits `[0, 2560]` |

New test `test_prefix_cache_hit_reaches_last_full_block` in `tests/v1/e2e/test_cpu_linear_attn_chunked_prefix.py` (run by the CPU CI's `cpu_model` job): fails on main with `assert [0, 0] == [0, 640]`, passes with this PR.

```bash
pytest tests/platforms/test_cpu.py tests/v1/e2e/test_cpu_linear_attn_chunked_prefix.py tests/v1/e2e/test_cpu_spec_decode.py tests/quantization/test_cpu_w8a8.py
# 22 passed; test_v2_speculator_smoke[eagle3] fails on main too here (gated model repo, no access)
```

Block sizes resolve as on main: Qwen3-0.6B 128; DeepSeek-V2-Lite 128 with AMX MLA and 16 with the reference CPU MLA backend.

## Details

**Root cause.** `CpuPlatform.check_and_update_config()` set the default block size whenever it was not user-specified:

1. The workers build the model and `update_block_size_for_backend()` raises the block size so an attention page fits a Mamba state page (640 tokens for Qwen3.5-0.8B).
2. The engine core takes that size from the KV cache groups.
3. After its handshake the engine core reruns `VllmConfig.__post_init__()`, which reruns `check_and_update_config()` and resets `cache_config.block_size` to 128. The scheduler and KV cache manager keep 640.
4. In `align` Mamba cache mode, `Scheduler._mamba_block_aligned_split()` reads `cache_config.block_size`, so it ends the prefill at the last 128-token boundary instead of the last 640-token one, and no Mamba state is cached at a block boundary. The next request finds full-attention hits but no Mamba hit, so the hybrid hit is 0.

When a prefill spans several chunks, a chunk boundary can land on a block boundary by chance, which is why `test_prefix_cache_hit_matches_cold_cache` (which asserts `num_cached_tokens > 0` without forcing one chunk) did not catch it.

**Fix.** Other platforms set the default block size in `update_block_size_for_backend()`, which runs once after the model is built; the CPU platform now does the same, taking the backends' preferred size for 128 (`_preferred_block_size_for_backends`). `check_and_update_config()` keeps only what is idempotent: the sizes CPU MLA and DeepSeek-V4 force, and the multiple-of-32 warning for a user-specified size.

**Found while** running vLLM's simulated execution (#61506) on the CPU platform; this fix is independent of it.
