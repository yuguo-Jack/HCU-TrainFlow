# [Core][Scheduler] Batch small prefill chunks under decode load

[Upstream PR](https://github.com/vllm-project/vllm/pull/54145) · state: closed · merged: False

## Original PR description

## Review summary

- Default-off, text-only scheduler policy; existing behavior is unchanged when `--min-prefill-chunk-tokens=0`.
- Batches sub-threshold prefill chunks only while decode work is runnable, with a bounded delay and cleanup on schedule/abort/finish/preemption.
- Targets long-prompt mixed prefill/decode workloads where the objective is to maximize stable per-GPU QPS under an average E2E latency budget.
- In controlled single-GPU RTX PRO 5000 experiments with the policy predecessor, enabling Small Prefill reduced average E2E from 2.931s to 2.388s at QPS 12 (-18.5%) in one fixed configuration, and moved the stable <=3s capacity knee from 11 to 13 QPS (+18.2%) in another.
- Timeline analysis showed context tokens per step increasing from 1,669 to 4,785, while incremental prefill GPU time fell from 15.069 to 8.788 us/token (-41.7%).
- Focused scheduler/CLI tests and changed-file pre-commit pass; the policy lineage is also operating on approximately 1,600 RTX PRO 5000 workers.

## Purpose

Decode-heavy workloads can leave small text prefill chunks in the remaining
token budget. Launching those chunks individually may underutilize the GPU.

This PR adds an opt-in scheduler policy that:

- defers text prefill chunks smaller than `--min-prefill-chunk-tokens` while
  decode work is runnable;
- releases deferred chunks when their combined size reaches that threshold or
  `--max-prefill-chunk-delay-steps` expires;
- clears pending state on schedule, abort, finish, and preemption; and
- excludes multimodal requests.

The feature is disabled when `--min-prefill-chunk-tokens=0` (the default), so
the existing scheduling path is unchanged by default.

### Duplicate-work check

I searched open PRs for the CLI names and for small-prefill/deferred-prefill
batching and found no implementation of this policy.

Two adjacent policies use different control signals:

- #54627 applies `prefill_schedule_interval` to single-engine runs. It defers
  all prefills on a fixed cadence to protect decode interactivity.
- This PR is size-aware: it defers only sub-threshold text chunks and releases
  them by aggregate tokens or bounded per-request age. It targets batching
  efficiency under an E2E capacity budget.

They are not duplicates. If both are eventually composed, precedence should be
defined because the cadence gate currently runs before this PR's threshold/age
check. They should not be enabled together by default without an interaction
benchmark.

The adjacent P-PAS RFC (#52906) controls the aggregate prefill token budget
under pressure, whereas this PR keeps global budgets unchanged and batches
sub-threshold chunks. A controlled 2x2 experiment found that these policies are
also not universally additive.

### SLA-oriented serving validation

The primary use case is not maximum QPH with a relaxed latency target. It is
long-prompt mixed prefill/decode serving where the objective is the highest
stable per-GPU QPS satisfying all of the following:

- average E2E latency <=3s;
- completed QPS keeps up with offered QPS;
- no failures, OOMs, core dumps, or restarts; and
- running and waiting requests do not grow persistently.

The controlled workload used a single RTX PRO 5000 72GB GPU, a Qwen3.5-0.8B
model, TP=1, non-streaming open-loop requests, and a production-derived request
distribution averaging about 5.4K prompt tokens and 300 output tokens. MTP was
disabled; chunked prefill, an 8,192-token batch budget, and FP8 KV cache were
enabled.

The following comparisons changed only Small Prefill within each fixed
configuration:

| Comparison | Fixed configuration | Result |
|---|---|---|
| C -> F | BF16 LM Head + FP8 KV | At QPS 12, average E2E fell from 2.931s to 2.388s (-18.5%); the stable <=3s knee remained at 12 QPS. |
| D -> E | FP8 LM Head + FP8 KV | The stable <=3s knee moved from 11 to 13 QPS (+18.2%). E at QPS 13 measured 2.661s and 2.700s across two GPUs; QPS 14 measured 3.408s and 3.528s and failed the SLA. |

Timeline analysis explains the gain: context tokens per step increased from
1,669 to 4,785 (2.87x), raw context GPU time fell from 16.699 to 9.390 us/token,
and incremental prefill GPU time fell from 15.069 to 8.788 us/token (-41.7%).

These controlled measurements used the production predecessor of this policy.
The PR retains the threshold/delay behavior while hardening per-request age and
lifecycle cleanup. A separate run of the hardened implementation at `3072/384`
sustained QPS 12 at 2.462s average E2E with no failures, preemptions, or
sustained waiting; QPS 13 measured 3.096s. That later baseline was not a fully
matched crossover, so it is supporting reproduction rather than the main
capacity-delta claim.

### Production validation

This policy lineage is currently deployed in a production serving cluster with
approximately 1,600 single-GPU NVIDIA RTX PRO 5000 workers and is serving live
traffic. The production configuration uses:

- `--min-prefill-chunk-tokens 3072`
- `--max-prefill-chunk-delay-steps 192`

At the time of verification, all allocated workers were ready and available.
This operational deployment is separate from the controlled `3072/384`
experiments. It demonstrates production-scale operational viability, but is
not used to claim a fleet-wide capacity or latency improvement.

### Interaction with adjacent prefill policies

In a separate peak-throughput 4B experiment, Small Prefill alone improved
QPH/GPU by 1.90%, while combining it with P-PAS was 7.06% below Small Prefill
alone. This is an interaction warning, not the primary performance claim. Both
policies gate prefill admission, so the tested combination is not recommended
without workload-specific validation.

Documentation for both CLI options and the TTFT trade-off is included.
