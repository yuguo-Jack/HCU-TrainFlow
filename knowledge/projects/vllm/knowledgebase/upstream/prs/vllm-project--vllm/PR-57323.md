# [Frontend] Replay Responses reasoning via encrypted_content blobs

[Upstream PR](https://github.com/vllm-project/vllm/pull/57323) · state: open · merged: False

## Original PR description

## Purpose

Second of the smaller PRs splitting #56285 per review ("encrypted_content ... could be handled separately"). @chaunceyjiang

With `include=["reasoning.encrypted_content"]` the non-Harmony Responses API attaches an opaque reasoning blob to reasoning items — streamed (`response.output_item.done` for reasoning) and non-streamed alike — instead of discarding the reasoning text, and replays the blob back into the prompt on the next turn, enabling `store=false` clients (Codex-style) to continue sessions without resending reasoning. The blob is encoded, not encrypted: vLLM holds no key, it only has to survive a client round trip (zlib + urlsafe base64 with a `vllm-reasoning-v1.` prefix). Replayed items prefer explicit `content` over the blob; foreign blobs fall back to `summary` with a warning; main's previous behavior of raising `VLLMValidationError` on any `encrypted_content` input is replaced by this decode path.

**Coordination note.** Per the review comment on #56285, `encrypted_content` may also serve the proposed `/responses/compact` endpoint — #56970 (draft) adds that endpoint and is the natural place to unify the two, so the encoding format here (`_REASONING_STATE_PREFIX`) is intentionally self-describing and cheap to adopt there.
