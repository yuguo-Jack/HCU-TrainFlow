# [RL] Support per-update source ranks for NCCL weight transfer

[Upstream PR](https://github.com/vllm-project/vllm/pull/62557) · state: closed · merged: True

## Original PR description

## Overview

Support pipeline-parallel (partitioned) trainers in the dense NCCL weight-transfer backend. Each parameter is broadcast by its first `ParamMeta.owners` rank, as planned in #63256 (step 4). Single-sender behavior and wire format are unchanged.

## Claims

- A source whose ranks own different parameters (e.g. pipeline stages with `owners=(stage ranks...)`) is now accepted. Each stage's first owner broadcasts its own parameters to all inference workers within one start/finish lifecycle.
- No trainer-side coordination channel: every rank derives the same plan from `metadata`, which is identical on every rank. Broadcasters join the existing NCCL rendezvous at group ranks `[0, rank_offset)`, and rank 0 sends one `update_weights` per broadcaster, tagged with `src`.
- Workers receive each update from its `src`, which must be below `rank_offset`, and reuse metadata per `(model, src)`.
- Backward compatible: single-sender payloads are byte-identical to `main` (`rank_offset=1`, no `src` key), and a missing `src` defaults to 0.
- Invalid layouts are rejected at `trainer_init` on every rank before any NCCL call: a rank owning parameters of two broadcasters, unowned parameters with several broadcasters, or a `world_size` with no workers.

## Details

- Rank 0 is always group rank 0 and drives the control plane. Other broadcasters open their endpoints directly. Ranks that broadcast nothing stay out of the group and only drive `iter_full()` for their gathers.
- During each broadcaster's turn, the other broadcasters receive and discard its parameters to stay in the collective.
- Every parameter a rank owns must share its first owner, so that gathers and turns line up.
- A broadcaster failure during an update is fatal: that rank raises immediately, but peers can stay blocked in NCCL, so the job must be torn down. This is the same exposure as single-sender NCCL on `main`, and it is documented.
- No duplicate: #63256 explicitly leaves multi-sender NCCL to this PR.

- hao-aaron · comment · 2026-10-26T22:45:25Z · [source](https://github.com/vllm-project/vllm/pull/62557#issuecomment-6429112559)

An agent flagged a couple of possible cleanups that make sense to me, I haven't verified yet:

- **The receive-and-drop path (`_discard`) allocates real buffers on trainer GPUs every turn.** Packed goes through `packed_nccl_broadcast_consumer`, which allocates a fresh bucket each time (up to ~2 GiB in flight with the defaults). Unpacked allocates one full-size tensor per parameter. This lands on trainer GPUs during sync, so a broadcaster can OOM because of another stage's parameters. Since the data is thrown away, a single reusable scratch buffer would do: size it to the largest bucket (`buffer_size_bytes` plus the largest tensor, since a bucket can overshoot by one tensor) and receive every bucket into it on one stream. For unpacked, use one buffer of the largest foreign parameter's bytes and broadcast into views of it.
- **`_discard` duplicates the worker's receive path.** Both have to match the producer's chunking exactly, so it'd be nice to share one helper, e.g. `_receive(meta, src, device, sink)`, with the worker passing `model.load_weights` and the discard passing a no-op. Or have `packed_tensor.py` expose the bucket sizes computed from metadata, which the scratch-buffer version needs anyway.

On the `_discard` buffers, I looked into it and I think it's a fair cleanup, though the risk is a bit smaller than flagged:

- **Packed:** the discard memory is reused, not accumulated, and it's bounded by the packing config rather than the other stage's size: at most `num_buffers` buckets of `packed_buffer_size_bytes` plus one tensor, so ~2 GiB at the defaults. That's the same as what a broadcaster already uses in its own turn (and what rank 0 uses on `main`). The only new part is the one-tensor overshoot, which depends on the other stage's largest parameter.
- **Unpacked:** buffers are allocated and freed one at a time, so the peak is about one tensor.
- **Duplication:** packed discard already goes through the same `packed_nccl_broadcast_consumer` as the worker, so the chunking is shared; only the small unpacked loop is duplicated.

A single scratch buffer would still save about one bucket (~1 GiB at the defaults) on discard turns. It's small, but it adds a second copy of the bucket-size rule (or a refactor of the consumer to share it), so I'd rather do it as a follow-up PR and keep this one stable. Happy to put that up right after this lands if that works for you.
