# [ROCm][Perf] Opt-in AITER FlyDSL INT4 QuickReduce

[Upstream PR](https://github.com/vllm-project/vllm/pull/59478) · state: open · merged: False

## Original PR description

## Purpose

[ROCm/aiter#4970](https://github.com/ROCm/aiter/pull/4970) (merged) added a FlyDSL INT4 two-shot all-reduce, `aiter.ops.flydsl.QuickAllReduceInt4`, for gfx942/gfx950 at TP 2/4/8. It ships as a standalone Python launcher and is not wired into the HIP QuickReduce dispatch, so nothing in vLLM uses it today. On MI355X at TP8 the AITER PR measures it 29–47% faster than HIP QuickReduce INT4 (512 × 4096: 18.1 vs 26.5 µs; 32768 × 5120: 558 vs 1061 µs), with better numerics (SQNR ~19.2 dB vs ~18.3 dB against an fp32 all-reduce).

With `VLLM_ROCM_QUICK_REDUCE_USE_FLYDSL=1` and `VLLM_ROCM_QUICK_REDUCE_QUANTIZATION=INT4`, this PR makes `QuickAllReduce` create the FlyDSL communicator in place of the HIP one and route eligible payloads through it:

- **Opt-in:** `VLLM_ROCM_QUICK_REDUCE_USE_FLYDSL` defaults to off, which keeps HIP QuickReduce exactly as today. A new env var is justified here because the swap is not model-specific: it would replace HIP QuickReduce in every ROCm TP>1 run that uses INT4 QuickReduce, and the FlyDSL kernel has not yet been validated as widely as the HIP kernels. Setting the flag with any other quantization level logs a warning and keeps HIP QuickReduce.
- **Eligibility:** bf16, contiguous, 16-byte-aligned, byte size a multiple of 16, between the QuickReduce min size and `min(max size, 4 GiB)`. The 4 GiB cap is the FlyDSL buffer window.
- **Min size:** when `VLLM_ROCM_QUICK_REDUCE_MIN_SIZE_BYTES_MB` is unset, the floor is 2 MiB, since below that the FlyDSL kernel's fixed launch cost loses to the custom all-reduce.
- **No import fallback:** vLLM's ROCm images pin AITER v0.1.24.post1, which ships `QuickAllReduceInt4` (added in v0.1.23). The world sizes, archs and process groups its constructor rejects are already rejected earlier in `QuickAllReduce.__init__`.
- **Fused all-reduce + RMSNorm:** FlyDSL QuickReduce has no fused all-reduce + RMSNorm kernel. With `fuse_allreduce_rms` on, fused all-reduces in the QuickReduce size range keep running AITER's HIP QuickReduce + RMSNorm, so the ROCm AITER all-reduce fusion pass logs a warning when the flag is set. Set `fuse_allreduce_rms` to false to route those all-reduces through FlyDSL.
- **Unchanged:** FP, INT8 and INT6 QuickReduce. With the flag on, fp16 payloads, which FlyDSL does not support, go to the next all-reduce backend instead of HIP QuickReduce.

The FlyDSL communicator owns its own IPC buffers, so the HIP QuickReduce buffers are not allocated when it is active.

## Test Plan

- Hardware: 8× MI355X (gfx950)
- Unit tests:
  - `tests/distributed/test_quick_all_reduce.py`: two new CPU-only tests cover the FlyDSL eligibility gate (dtype, size window, contiguity, pointer alignment) and that `quick_all_reduce` and `close` go to the FlyDSL communicator and never to HIP QuickReduce.
  - `tests/distributed/test_rocm_quick_reduce.py`: two new tests cover parsing `VLLM_ROCM_QUICK_REDUCE_USE_FLYDSL` and its default (off).
  - `tests/compile/passes/distributed/test_fusion_all_reduce.py`: a new CPU-only test checks that `RocmAiterAllReduceFusionPass` warns when the flag is set and stays silent when it isn't.
- Model: `amd/Qwen3.8-2.4T-A95B-Quark-MXFP4`, TP8, `max_num_batched_tokens=8192`, `VLLM_ROCM_QUICK_REDUCE_QUANTIZATION=INT4`
- Image: `vllm/vllm-openai-rocm:nightly-92044241a02f05de51420d654daf669de20b4691` (AITER v0.1.24.post1) with this PR applied
- Serving A/B: one image, each server starting from empty vLLM and AITER caches. Control leaves `VLLM_ROCM_QUICK_REDUCE_USE_FLYDSL` unset (HIP QuickReduce INT4) with the fused all-reduce + RMSNorm pass on (`fuse_allreduce_rms: true`). Candidate sets the flag to `1` with that pass off, since FlyDSL QuickReduce has no fused all-reduce + RMSNorm variant. Everything else is identical. Random dataset, OSL 128, ISL 2k–128k, concurrency 2–64.
- Accuracy: GSM8K (5-shot, 1319 examples), same servers as the A/B

- maeehart · comment · 2026-10-07T15:41:44Z · [source](https://github.com/vllm-project/vllm/pull/59478#issuecomment-6041349828)

**MI325X (gfx942), DeepSeek-V4.1-Flash at TP2, TP4 and TP8, and NIAH**

@mjkvaak-amd, I ran the same A/B on MI325X with `deepseek-ai/DeepSeek-V4.1-Flash` at TP2, TP4 and TP8, in the same image with this PR applied at `7d4a0975`. With the flag set, every rank logged `Using AITER FlyDSL INT4 QuickReduce for BF16 payloads from 2 MiB through 2048 MiB`, and without it no rank did. All servers ran without errors, and every request completed.

The gain grows with the TP size. At TP8, FlyDSL lowers the mean TTFT geomean by 10.5%, with 6.5 to 19.8% per cell, and raises output throughput by 9.1%, which is close to the −11.3% of your MI355X TP8 table. At TP4 the geomean is −1.9%. The four TP4 cells with a spread below 0.2% over seeds (8k at concurrency 4, and 32k, 60k and 128k) are 1.0 to 1.4% lower, and the cells at concurrency 16 and 64 move within their spread. At TP2 the geomean is +0.0%, because the 2k cell at concurrency 16 varies by about 10% between seeds, while every TP2 cell from 8k up is 0.7 to 2.0% lower.

I think that the gain is largest at TP8 because each rank computes only an eighth of every layer there, so the all-reduce takes a larger part of each prefill step. Also, at TP2 HIP QuickReduce INT4 starts at 1 MiB instead of 2 MiB, so steps of about 103 to 204 tokens use HIP QuickReduce in the control and the custom all-reduce with FlyDSL, because this PR keeps the 2 MiB floor at every TP size.

Decode does not change at any TP size, with median ITL within 0.5%, because one token of this model is 10 KiB, so decode all-reduces of up to 64 tokens stay below the 2 MiB floor and go to the custom all-reduce in both arms. Mean TPOT is still 6.7% lower at TP8, because TPOT also counts the steps where decodes run together with a prefill chunk, and those steps are shorter with FlyDSL.

`DeepseekV41ForCausalLM` is not torch-compiled in this image, and vLLM logs that the model does not support `torch.compile`, so `fuse_allreduce_rms` has no effect on it. The two arms therefore differ only in the QuickReduce kernel, and these numbers do not show what FlyDSL costs on a model where the all-reduce and RMSNorm fusion runs.

GSM8K does not show a loss. FlyDSL is 1.3 points higher at TP4, equal at TP2 and 1.1 points lower at TP8, and each difference is at most 1.3 standard errors of the difference, so I read them as run-to-run variation. For long context, I ran lm_eval `niah_single_2` at TP4 with 500 questions at each of 4k, 64k and 128k tokens. Both arms answered all 1500 correctly, and every prompt has the same hash in both arms. Both arms are at 100%, so this test cannot show a difference as small as the one in the Kimi-K3 results above, but it shows that FlyDSL loses no answer on this model.

No second `_ptr` is needed, and enabling FlyDSL does not break the fusion. The fused op never uses `QuickAllReduce._ptr`. `_rocm_aiter_fused_allreduce_rmsnorm_impl` creates its own AITER communicator (`_get_or_create_aiter_qr_rmsnorm_comm`) the first time it runs, and it asks `qr_comm` only two things: whether it is `disabled`, and whether `should_quick_allreduce(input_)` accepts the payload. So with `fuse_allreduce_rms` on, an all-reduce that the pass fused into AR + RMSNorm keeps running AITER's HIP QuickReduce + RMSNorm, and a standalone all-reduce goes through `qr_comm.quick_all_reduce` and so through FlyDSL. That is the split you describe.

Notice that FlyDSL QR doesn't yet support fusions with RMSNorm and/or Quant kernels.
