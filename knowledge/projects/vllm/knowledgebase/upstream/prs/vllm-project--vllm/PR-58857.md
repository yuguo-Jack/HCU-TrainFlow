# [Model] DeepSeek-V4/V4.1 VL: stream language-model weights instead of sorting the checkpoint

[Upstream PR](https://github.com/vllm-project/vllm/pull/58857) · state: closed · merged: True

## Original PR description

## Purpose

The DeepSeek-V4 VL wrapper and the NVIDIA DeepSeek-V4.1 VL wrapper sort the whole mapped weight stream so that the `language_model.` group reaches the child loader contiguously. The NVIDIA children finalize fused expert weights inside `load_weights`, so the group must not be interleaved. `sorted()` materializes the iterator, so every tensor the loader yields is alive before the first copy:

- **Loaders that yield materialized tensors** (`--safetensors-load-strategy eager`, or `--load-format fastsafetensors`, which yields a separate tensor per weight): nearly the whole checkpoint is held at once (DeepSeek-V4.1-Flash is 475 GiB). #58782 reports host OOM from the same sort on the AMD V4.1 wrapper.
- **The default mmap views**: this costs no extra anonymous memory. But every shard stays mapped for the whole load and name order jumps between shards. In our runs that meant ~20–30 GiB more mapped page cache per rank, more storage reads and a slower load (below).

Contiguity needs only a non-interleaved group, not a total order. This PR adds `stream_language_model_first`, which yields `language_model.*` as it arrives and defers the rest (vision tower, aligner), cloned in case the loader reuses its buffers. Both wrappers use it.

**Not a duplicate:** #58782 applies the same idea to the AMD V4.1 wrapper as one part of a ROCm fix, and could reuse this helper. This PR covers the V4 wrapper and the NVIDIA V4.1 wrapper. #57733 keeps the in-load finalize, so the contiguity requirement stays.

## Test Plan

```bash
pytest -v tests/models/test_deepseek_v4_vl_stream_weights.py
```

The test is parametrized over both wrappers and uses the real `AutoWeightsLoader` with a language model that finalizes in `load_weights`. It asserts that a weight is loaded before the stream is drained, that the child is called once, and that it finalizes after all of its weights. It is registered in the Basic Models (Other) CUDA step.

## Test Result

Both cases pass on current main (GB10, torch 2.13.0+cu130). Without the change, both cases fail at the mid-stream assertion: the stream is drained before anything loads.

DeepSeek-V4.1-Flash at TP4 on 4x DGX Spark with `--load-format auto`, page cache dropped before each boot. These runs used a 0.28.1-based build with the same change minus the clone. Two nodes had `read_ahead_kb=1024` and two had 128, the same in both arms, which is why reads vary by rank:

| | boots | read per rank | load, slowest rank |
|---|---|---|---|
| sorted | 1 | 179–357 GiB | 248 s |
| streamed | 2 | 158–265 GiB | 202 s, 212 s |

With `--load-format fastsafetensors`, #55985 and some fastsafetensors fixes that are not upstream yet, streaming is what lets this model load on a 121.7 GiB node at all: ~88 s, against 202–212 s for `auto` above.

This changes only the order in which weights reach the loader. The child's per-tensor loaders don't depend on order, and it still finalizes once, after all of its weights.

AI assistance (Claude Code) was used for the change, the tests and the measurements. I reviewed every line and ran the tests and boots.

- adi-suresh01 · comment · 2026-10-17T00:14:08Z · [source](https://github.com/vllm-project/vllm/pull/58857#issuecomment-6227186731)

Some GPU data for this, from the host-memory side: 4x RTX PRO 6000 Blackwell (sm_120, PCIe), TP4, DeepSeek-V4.1-Flash with `--engram-config.cpu_offload true` and DSpark, nightly `49cb2bbf` + #60762, in a RunPod container with a 702.2 GiB memory limit.

- With the `sorted()` on main (checkpoint on a FUSE volume), the 48-shard progress bar finished in 7m35s and the real copy only started after it. The workers sat in D state while container memory climbed about 9 GiB/min to 695.1 GiB, and RunPod stopped the container at 98% of its limit. It never served.
- With the same approach as this PR (my own overlay, not this branch: stream `language_model.*` in checkpoint order, load the vision tensors after), plus evicting each finished shard from page cache and exact-size pinned Engram tables (`PYTORCH_ALLOC_CONF=pinned_max_round_threshold_mb:64`, the torch-side equivalent of #59849), the progress bar covered the copy (13:27, `Loading weights took 814.49 seconds`), page cache stayed at 6-13 GiB during the main load, peak container memory was 290.6 GiB, and the server answered 10.7K and 106K-token prompts with DSpark and CUDA graphs.

The second run also moved the checkpoint from FUSE to local disk, so it doesn't isolate the sort, but the copy now happens inside the progress bar instead of after it, which is the part this PR changes.

Two things from those runs:

- `vllm/models/deepseek_v41/amd/vl_model.py:343` has the same `sorted()`. #58782 changes it inside a larger ROCm PR, so `stream_language_model_first` could cover that wrapper too.
- After streaming, the last shard (an Engram table here) is still referenced when `load_weights` returns, so its page cache stays until the kernel needs the memory. A `drop_checkpoint_cache(...)` right after `loader.load_weights(...)` in the wrapper released it in my run (92.1 to 6.2 GiB).

The code here still applies cleanly to main at `523d74e2`; only `.buildkite/test_areas/models_basic.yaml` conflicts.
