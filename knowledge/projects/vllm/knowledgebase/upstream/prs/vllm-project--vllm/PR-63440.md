# [ROCm][Perf][Muse Spark] FlyDSL decode monokernel for DSpark verify steps on MI355X (--monokernel)

[Upstream PR](https://github.com/vllm-project/vllm/pull/63440) · state: closed · merged: True

## Original PR description

## Overview

With `--monokernel`, Muse Spark Open MXFP4 on 8x MI355X (TP8 + expert parallelism, 7-token DSpark draft) runs
decoder layers 1-60 of every verify step of 1-16 requests as persistent FlyDSL launches. One launch, or three, cover
the work from a layer's attention output to the next layer's q, o-gate and KV insert. All other steps and layers 0 and
61 run the stock path. The flag is off by default.

## Claims

- AgentX (agentic-coding traces, DSpark at synthetic acceptance length 4.05, all requests, full mode), this PR's head
  with `--monokernel` vs the faster stock recipe on its base (main 3d81a51): interactivity (1000 / p90 ITL) / total
  tok/s/GPU of 413.8 / 2974 vs 263.1 / 2325 at c = 1 (+57 % / +28 %), 314.1 / 3056 vs 232.7 / 2368 at c = 2
  (+35 % / +29 %), 295.2 / 4430 vs 217.3 / 3585 at c = 4 (+36 % / +24 %) and 208.4 / 7384 vs 143.3 / 6126 at c = 8
  (+45 % / +21 %).
- Accuracy contract (GPQA-Diamond, AIME25, RULER NIAH; method of #60397), `--monokernel` vs stock: GPQA-Diamond
  88.7 vs 88.5 (delta +0.1 ± 0.5; boxed-letter prompt -0.7 ± 0.6), AIME25 98.6 vs 98.3 (+0.3 ± 0.4), RULER NIAH 348 vs 346 of 360.
- Accuracy and DSpark acceptance, real acceptance, stock (main 3d81a51) and `--monokernel` (c0f424a) with the same
  server flags: GSM8K (full set, 5-shot) 0.9651-0.9735 with `--monokernel` and 0.9666-0.9742 stock at c = 1-16, mean
  acceptance length 4.512 vs 4.431. Long-context needle retrieval at 33k-529k tokens: 192/192 in both arms, mean
  acceptance length 3.638 vs 3.600.
- Opt-in only. If the deployment is not supported, vLLM refuses it at startup with every reason. Steps that the
  kernels do not cover run stock. Nothing changes without `--monokernel`.

## Details

### Hook point

- `MuseSpark1xForCausalLM.process_weights_after_loading` calls `maybe_attach_mono`. This runs after the per-layer quant
  finalize, so the experts are already in their shuffled kernel layout. The call is collective over the TP group.
  `MuseSpark1xModel.mono` is `None` without `--monokernel`.
- `MuseSpark1xModel.forward`: if `mono.try_forward(...)` returns the residual stream, the stock layer loop does not
  run. Otherwise the stock loop runs as before.
- `MuseSpark1xAttention.forward` ends in a new `back` (o-norm, o-gate, o_proj), and `MuseSpark1xDecoderLayer.forward`
  in a new `after_attention`. The monokernel runs layer 1 up to the attention with the stock functions and calls these
  two at the seams. The stock path calls the same code in the same order.
- `compute_logits` and `compute_logits_local` start an asynchronous read of the kernels' health words (every 64
  steps, outside graph capture). A peer-rank wait that timed out raises there, instead of a hang.
- The model runner, the scheduler and the attention backends are not changed.

### Eligibility

- At startup (default deny; one `ValueError` with every reason, agreed over the TP CPU group): gfx950 with 256 CUs,
  the checkpoint's text config, TP8 + `--enable-expert-parallel` (linear placement, no EPLB), no PP / DP / DCP / PCP,
  DSpark with 7 draft tokens, no LoRA, sleep mode or weight transfer, no KV connector or offloading, bf16 model and KV
  cache, Quark OCP-MXFP4 W4A4 experts on AITER (shuffled weights and scales), the fused QK-norm / RoPE / KV insert,
  `ROCM_AITER_FA`.
- Every step, from rank-invariant data only (the batch shape and the attention metadata counts, because all ranks
  must take the same path). The step must be a uniform verify step of 1-16 requests x 8 tokens, in FULL CUDA graph
  or eager mode, with dense bf16 LBHNC KV caches (block size 16). All other steps run stock.

### Buckets

| rows (requests) | build | launches a layer |
|---|---|---|
| 8 (1), 16 (2) | K3, S = 8 / 16 | 1 |
| 24-32 (3-4) | HA + HM + HB, S = 32 | 3 |
| 40-128 (5-16) | HA + HM + HB, S = 64 / 96 / 128 (rows padded up; `nrows` = real rows) | 3 |

`--max-num-seqs` selects the builds that the server compiles. Weights are views of vLLM's parameters. The kernels
write KV into vLLM's pages through `slot_mapping` (padding slots are skipped). The peer buffers are plain `cudaMalloc`
memory, opened over IPC on the TP CPU group. All launch arguments are fixed pointers, so vLLM's FULL CUDA graphs
capture the launches.

### Fused verify attention (8, 16 and 32 rows)

From layer 2 on, layer i's verify attention runs at the head of K3_i / HA_i, for both the sliding-window and the full
layers. It is split over all 256 CTAs by (request, KV head, key range) and merged before o_proj. It reads the layer's
bf16 KV cache through its KV cache group's `block_table` / `seq_lens`, the impl's softmax scale, and the window
(2047, 0). Only blocks inside the window are read. The descriptor tables hold pointers and counts only. They are
keyed by their contents and written once, so captured graphs read fixed tables. If `max_model_len` is above the 1M
keys that the builds stage block ids for, vLLM's op runs. Builds of 40 rows and more keep vLLM's op.

### Numerics: a16w4, opt-in behind `--monokernel`

The kernels keep the MoE activations in bf16 (MXFP4 weights x bf16 activations). The stock path is W4A4: it
quantizes the expert inputs and the SwiGLU output to MXFP4. Thus `--monokernel` output is close to the stock output,
but not bit-identical. Prefill runs stock (W4A4). Other differences are the reduction order (fixed rank order in fp32)
and the bf16 norm multipliers. The flag help, the module README and the recipe describe this.

### Known issues

- With the DFlash2 draft (not the recipe's draft), `--monokernel` lowers the real acceptance length: AgentX c = 4
  4.83 -> 3.52. The aux-hidden-state bookkeeping is the same as in the stock loop: the new tests compare the aux
  states for the DSpark, DFlash2 and seam target layers. The cause is open (per-rank draft divergence, or a draft
  that is more sensitive to the a16w4 numerics). The recipe's DSpark draft is not affected on AgentX (2.83 vs 2.87).
- The FlyDSL cleanup keeps some unused launch arguments (the timeline and EPLB-replica pointers) and LDS slots. With
  them, every build compiles to the same code objects as the validated kernels: identical `.text` for all 30 server
  builds.
- CI cannot run the kernels: they need 8x MI355X and the checkpoint's shapes. The CI test runs the host side on one
  MI355X (below). The kernel paths were validated with the serving runs above.

### Vendored kernels

`vllm/models/muse_spark/amd/mono/kernels/` (about 6.7k lines) holds AMD's Muse Spark FlyDSL monokernel sources,
reduced to the builds that vLLM launches. They carry their MIT license header after vLLM's SPDX lines (as in
`rocm_block32_gemm.py`). They import FlyDSL and AITER's FlyDSL helpers only when the monokernel attaches. The host code
(mono/ without kernels/, model.py and two small core edits) is about 1.3k lines.
