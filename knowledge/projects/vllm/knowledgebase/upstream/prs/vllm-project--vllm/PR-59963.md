- sohom-cs · comment · 2026-10-30T01:50:26Z · [source](https://github.com/vllm-project/vllm/pull/59963#issuecomment-6512968181)

I filed #59907. On this head (d1a48516d8), `tests/v1/core/test_deferred_block_free.py::test_allocation_retry_waits_for_fence_then_succeeds[priority-2]` fails with `assert '1' not in {'1': 1}` (CPU run).

With the priorities set before `add_request`, the blocked allocation is the first call under both policies, and the retry trigger is `trigger`, the highest-priority request. So `failed_call` and `retry_trigger` need to change too:

```diff
-        ("priority", 2),
+        ("priority", 1),
```

```diff
-    retry_trigger = requests[failed_call - 1]
+    retry_trigger = trigger if policy == "priority" else requests[0]
```

With that, both cases pass on this head (CPU only).

I also have one regression test per symptom from #59907, five in `tests/v1/core/test_scheduler.py`. I can send them as a follow-up PR once this merges.

### Verification Results
1. **Reproduction Suite**: All 5 tests in `tests/v1/core/test_repro_step_unschedule.py` pass cleanly (6.66s), confirming that keeping `self.running` sorted eliminates same-step priority un-scheduling and prevents encoder cache / prefix-cache hash state corruption.
2. **Deferred Free Failure & Fix**: Confirmed `@sohom-cs`'s finding on `test_allocation_retry_waits_for_fence_then_succeeds[priority-2]`. Because request priority is established before admission, `trigger` (priority 0) occupies index 0 in `running` and is scheduled first, so the allocation failure occurs on call 1 rather than call 2. 
Applying the 2-line update in `tests/v1/core/test_deferred_block_free.py`:
```diff
@pytest.mark.parametrize(
    ("policy", "failed_call"),
    [
        ("fcfs", 1),
-       ("priority", 2),
+       ("priority", 1),
    ],
)
...
-   retry_trigger = requests[failed_call - 1]
+   retry_trigger = trigger if policy == "priority" else requests[0]
```
Resolves the failure, and both parameterized cases pass (4.68s).
3. **Core Scheduler Tests**: Ran the priority preemption suite in `tests/v1/core/test_scheduler.py`; all 6 priority preemption tests pass (6.97s).

### Rebase Note
Once rebased on latest `main` (`971378f466`), the `continue` statement under `if new_blocks is None:` introduced by #61976 is redundant: with `self.running` sorted, a request only preempts itself as `running[-1]`, so breaking immediately is sufficient.
