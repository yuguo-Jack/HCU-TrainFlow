# [Bugfix][Kernel][Benchmark] Fix benchmark_moe.py crash on TP-refined FP8 block shapes; add H100 E=128,N=192 fp8 [64,64] config

[Upstream PR](https://github.com/vllm-project/vllm/pull/63484) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

`benchmarks/kernels/benchmark_moe.py` crashes for block-FP8 MoE when the TP shard is not a multiple of the checkpoint block (e.g. Qwen3-235B-A22B-FP8 at TP8, reproduced below; Qwen3-30B-A3B-FP8 at TP4/TP8 has the same non-multiple shard, 192 and 96). This PR makes it tune with the refined block shape the runtime uses since #53896 (`refine_fp8_moe_block_shape`), and adds the resulting tuned H100 config for Qwen3-235B-A22B-FP8 at TP8 (E=128, N=192, `[128, 128] -> [64, 64]`).

## Claims

- **Fixes a crash in the tuner.** `benchmark_moe.py --dtype fp8_w8a8` on these layouts fails today with ``AssertionError: the last dimension of `x` 192 must be divisible by `group_size` 128``, both for benchmarking and `--tune`. The tool passed the checkpoint block (`[128, 128]`) through while the shard is 192 wide. With this PR it applies the same refinement as serving, runs, and saves `...block_shape=[64,64].json`, the file the runtime looks up. No change for EP or block-aligned shards.
- **New tuned config, two models benefit.** `E=128,N=192,device_name=NVIDIA_H100_80GB_HBM3,dtype=fp8_w8a8,block_shape=[64,64].json` (H100 80GB HBM3 SXM5, Triton 3.7.1). The filename keys only on E, N, device, dtype and block, so it serves both:
  - Qwen3-235B-A22B-FP8 at TP8 (the shape it was tuned for): fused-MoE kernel 1.39-1.57x faster than the default config at batch 96-256 and 1.16-1.33x at 512-4096. At batch 1-8 it takes 0.92-0.96x of default time, and at 16-64 it is within -1.0%/+1.3% of default (n=3).
  - Qwen3-30B-A3B-FP8 at TP4 (same E/N, hidden 2048): 1.16-1.48x faster at batch 96-4096, no batch slower than default by more than 0.7% (n=2).
- **End to end** on Qwen3-235B-A22B-Instruct-2507-FP8, pure TP8: +11% req/s, -14% TTFT p50, -10% ITL p50 on a prefill-bound workload (16k in / 256 out, c=16), n=3 launches per arm with non-overlapping ranges. Agentic multi-turn at c=64: +2% req/s, no regression. GSM8K unchanged.

## Details

**Root cause.** `main()` sets `block_quant_shape = get_weight_block_size_safety(config)` (the checkpoint's `weight_block_size`, `[128, 128]`) and passes it to the search-space filter, the benchmark workers and `save_configs`. Serving instead calls `resolve_fp8_moe_weight_block_shape`, which refines the block to `gcd(block_n, block_k, intermediate_size_per_partition, hidden)` when the shard is not a block multiple. In the benchmark the 192-wide shard is quantized with group size 128, which trips the per-token-group quantization assertion. Even past that, the result would be saved under a filename (`[128,128]`) that `get_config_file_name` never builds for this layout.

**Fix.** Call the runtime's own `refine_fp8_moe_block_shape` with the benchmark's sharded intermediate size and the same TP semantics as `FusedMoEParallelConfig`: EP uses `tp_size=1` with the full intermediate size, so EP never refines. The fix reuses the runtime function instead of re-implementing the rule, so the two cannot drift. The function only reads three attributes from its config argument, so a `SimpleNamespace` stands in for a full `FusedMoEConfig`. Building a real one in the benchmark would need a parallel config and a quant config for no benefit.

**Not covered.** Serving skips refinement when an explicit `--moe-backend` cannot consume refined blocks; it pads the shard to whole blocks instead (`pad_tp_shard_to_weight_blocks`, #55867). The tuner models the default `auto` path, which is the one that uses Triton configs. `--use-deep-gemm` tuning of refined shapes is not meaningful, since DeepGEMM needs 128x128.

**Config notes.** Some entries have `BLOCK_SIZE_K` 128/256, above block_k 64. `invoke_fused_moe_triton_kernel` (`vllm/model_executor/layers/fused_moe/fused_moe.py`) clamps `BLOCK_SIZE_K` to `min(block_shape)` at runtime, so these entries launch the same kernel as `BLOCK_SIZE_K` 64, and the tuner timed them through that same clamped path. They are left as the tuner wrote them so the file is reproducible with `--tune`. The B200 refined-shape configs from #55890 contain only `BLOCK_SIZE_K` equal to the block; I can normalize these entries to 64 (no runtime change) if reviewers prefer. Pruning `BLOCK_SIZE_K > block_k` from the search space would also cut tuning time, but that is out of scope here.

**Tests.** No unit test added. The refinement rule is already covered by `tests/kernels/moe/test_fp8_tp_loading.py`. The new code is the benchmark's call into it, inline in `main()` of a script that no test imports: it imports `ray` at module level and needs a GPU past argument handling. The before/after GPU runs in section 1 are the reproducer.

**Recommendation for users unchanged.** TP8 + EP8 (FlashInfer CUTLASS, native `[128, 128]`) was still faster than tuned TP8 on the prefill-bound point (1.19 req/s, single run on the earlier node, vs 1.11; default TP8 was 1.00 on both nodes). The config closes about 58% of that req/s gap for users who run pure TP.
