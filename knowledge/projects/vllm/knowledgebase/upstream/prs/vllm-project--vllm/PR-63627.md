## Original PR description

# [Perf] Tuned batch-invariant fused MoE configs on Blackwell, +48% decode throughput

## Summary

With `VLLM_BATCH_INVARIANT=1` the Triton fused MoE kernel always runs one fixed config (`BLOCK 64x64x32, GROUP_SIZE_M 8, SPLIT_K 1`) because `get_moe_configs()` returns `None` and `get_default_config()` has no batch-invariant table. This PR adds a small per-architecture table of tuned configs, one config per expert shape used for every M, and looks it up from `get_default_config()` under the flag. Shapes without an entry keep the fixed config. Entries were tuned on GB300 (SM 10.3) for the TP=4 fp8 shapes of Qwen3-235B-A22B-FP8, DeepSeek-V3.1 and GLM-5.3 and the bf16 shape of Qwen3-30B-A3B.

## Why one config per shape (and not M-bucketed tiles)

The first version of this table selected BLOCK_SIZE_M/N, num_warps and num_stages per M bucket with a fixed BLOCK_SIZE_K/SPLIT_K, like the dense `batch_invariant_configs.py` does for matmul. A kernel-level checker (8 probe rows inserted into random batches of M = 1 … 16384, 5 contexts per M, fp8 block-quant, GB300) showed bitwise-identical rows across every bucket boundary. The model-level needle test still failed:

| tree (Qwen3-235B-A22B-FP8, TP=4, `VLLM_BATCH_INVARIANT=1`) | `test_v1_generation_is_deterministic_across_batch_sizes_with_needle[default-FLASH_ATTN]` |
|---|---|
| main | PASS, PASS |
| M-bucketed tiles + fixed BLOCK_K=128 | FAIL 5/5 trials, FAIL 5/5 trials (batched outputs identical to each other, different from the batch-1 baseline) |
| fixed tiles (main's 64×64), BLOCK_K=128 only | PASS |
| M-bucketed tiles, BLOCK_K=32 (main's) | FAIL 1/5 trials |
| one config per shape for every M (this PR) | PASS |

So on Blackwell the per-row result of the Triton fused MoE kernel does depend on the tile configuration for real activations even when the K reduction is fixed, and the only safe table is one config per shape. The sweep data still favours this strongly over the fixed 64×64×32 config (Qwen3-235B shape, M=32: 381 µs fixed vs 211 µs single tuned config vs 132 µs bucketed), and the E2E numbers below are measured with exactly this diff.

## What changed

- `vllm/model_executor/determinism/batch_invariant_configs.py`: `_BATCH_INVARIANT_MOE_CONFIGS[(arch family, dtype, block_shape, E, N, K)] -> config` and `get_batch_invariant_moe_config()`; N and K are what the kernel sees (per-rank `w2.shape[2]`, `w1.shape[2]`). The family comes from the existing `_get_tuned_matmul_arch_family()` (major 10 → `blackwell`).
- `fused_moe.py::get_default_config()`: under `VLLM_BATCH_INVARIANT` return the table entry when there is one, else the existing fixed config.

## How the entries were chosen

Per shape: sweep `BLOCK_SIZE_M ∈ {16,32,64,128} × BLOCK_SIZE_N ∈ {64,128,256} × num_warps ∈ {4,8} × num_stages ∈ {2,3,4} × BLOCK_SIZE_K ∈ {32,64,128}` (`GROUP_SIZE_M=8`, `SPLIT_K=1`) through `fused_experts()` under `VLLM_BATCH_INVARIANT=1` at M = 1…4096 (CUDA-graph timed, median of 20), reject anything not within 3% of the fixed config's output, and take the config with the lowest total time over all M. The sweep data (`timings.json`, raw per-candidate medians) is in the attached evidence archive.
