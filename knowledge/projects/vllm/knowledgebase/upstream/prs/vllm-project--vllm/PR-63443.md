# [Perf][Pooling] Start offline pooling before all prompts are preprocessed

[Upstream PR](https://github.com/vllm-project/vllm/pull/63443) · state: closed · merged: False

## Original PR description

## Overview

Offline pooling (`LLM.encode`, `embed`, `classify`, `score`) already feeds the engine incrementally, but it preprocessed the entire prompt list before adding the first request, so the GPU sat idle for the whole preprocessing phase. This makes the offline request factory lazy and replaces the eager `Executor.map` in `_run_tiling_engine` with a bounded prefetch, so the first requests reach the engine after a bounded amount of preprocessing instead of all of it.

Independent of the multi-item scoring RFC and of the other pooling PRs in this series; it applies to any offline pooling call.

## Claims

- The engine receives its first requests after at most `2 * max_num_seqs` prompts have been preprocessed, instead of after all of them.
- GPU utilization at the start of a large offline pooling call (`LLM.encode`, `embed`, ...) rises earlier; the larger the prompt list (and the larger the per-request `PoolingParams`), the longer the idle window that is removed.
- Outputs are unchanged: same values, same order.
- No Python API change. The only caller-visible difference is *when* a malformed prompt is reported: an error from `parse_model_prompt` now surfaces when that prompt is reached rather than before the first request is added. The existing abort-on-exception path in `_run_tiling_engine` already aborts whatever was added before the failure; a test now pins that.

## Validation

Environment: 1x H100 80GB, vLLM main @ 2d40c0609f (nightly wheel), torch 2.14.0+cu130, FlashInfer 0.7.2, Model Runner V2 (`VLLM_USE_V2_MODEL_RUNNER=1`).

Three unit tests are added to `tests/entrypoints/pooling/test_io_processor.py`, which runs on CPU with a stubbed engine and needs no model:

- the engine receives its first `add_request` after at most `2 * max_num_seqs` items have been produced by the request factory, while the full list is 1,000 prompts, and all outputs still come back in request order;
- a request factory that fails partway through propagates the error and the requests already added to the engine are aborted;
- the caller's `PoolingParams` object is not mutated — the yielded requests carry the pooling task, the caller's object keeps `task is None`.

The file is already covered by the existing Buildkite entrypoints job, so no CI configuration change is needed. The benchmark below was run by hand and is not part of CI.

### Benchmark

Workload: `Qwen/Qwen3-Embedding-0.6B`, one `LLM.embed` call with 20,000 synthetic token-id prompts of 200-400 tokens (uniform), on 1 GPU, `max_num_batched_tokens=32768`, `max_model_len=1024`, prefix caching off. One untimed warmup call, then 3 timed calls; two separate runs per branch. GPU utilization sampled with `nvidia-smi --query-gpu=utilization.gpu -lms 50`.

| Metric | main | this PR |
|---|---|---|
| per-call wall time, run 1 / run 2 | 16.11 / 16.92 / 16.64 s and 16.15 / 17.37 / 16.46 s | 15.41 / 16.27 / 15.62 s and 15.36 / 15.71 / 16.14 s |
| median call time | 16.55 s | 15.67 s |
| prompts/s | 1,151-1,242 | 1,229-1,302 |

That is **+5.6% throughput** on the medians; comparing the same call index between branches, the individual calls are +2% to +11% faster.

Output check: the embeddings are identical to main within main's own run-to-run variation — max |diff| 0.0 in one run and 3.0e-8 in 1 of 20,000 rows in the other, which is exactly what two main runs differ by.

## Details

**Lazy offline request factory.** `PoolingIOProcessor.get_request_factory_offline` used to run `parse_model_prompt` over every prompt and `PoolingParams.clone()` over every parameter object in two list comprehensions, then return a generator over the already-built lists. Both moves into the generator, one request per `yield`. The validation that must still fail before anything is added — a request whose `PoolingParams.task` conflicts with the model's pooling task, with the existing `plugin` exception — stays up front; it only reads the uncloned parameters and does not touch the prompts, so it is cheap. The caller's parameters are still never mutated: the clone now happens inside the generator, just before the task is filled in.

The other `get_request_factory_offline` implementations were checked. The cross-encoder scoring factory (`ScoringIOProcessor`) is already lazy and is untouched. The bi-encoder scoring, Jina ranking and token-embed factories delegate to the base one and become lazy with it. The `IOProcessorPlugin` factory still clones and merges parameters eagerly before delegating, because a plugin's `pre_process` has to produce the whole prompt list anyway; its eager clone is left alone.

**Bounded prefetch instead of `Executor.map`.** `_run_tiling_engine` called `self._executor.map(io_processor.render, request_factory())`. `concurrent.futures.Executor.map` submits every item of the iterable when it is called — Python before 3.14 has no `buffersize` parameter — so it drained the generator up front and undid the laziness above. It is replaced by a deque of render futures that is topped up to `max_requests_in_core` (`2 * max_num_seqs`, the number of requests the loop is about to add) at the top of each loop iteration and consumed in order. Rendering therefore still overlaps with the engine's steps, but never runs more than one batch ahead; output order and the exception behaviour are unchanged, and any futures left pending when the loop exits are cancelled.

I chose the bounded version rather than the lazy `map(io_processor.render, request_factory())` fallback because the latter would render on the calling thread, serializing preprocessing with the engine loop and giving up the overlap the thread pool exists for; the bounded version is only a few lines and keeps both properties.

Thank you for the question — you are right for text prompts, and I measured it.

1x H100 80GB, `Qwen/Qwen3-Embedding-0.6B` bf16, one `LLM.embed` call with 20,000 prompts of
200-400 tokens, 3 timed calls after a warmup:

| input | main mean | this PR mean | change | GPU util, seconds 1/2/3 (main → this PR) |
|---|---|---|---|---|
| text, 2 runs x 3 calls | 22.8 s | 23.1 s | -1%, within noise | 0/0/0-9% → 0/0/58-69% |
| token ids, 1 run x 3 calls | 16.7 s | 15.9 s | +4.5% | 0/22-83/84-86% → 55-63/85-89/84-90% |

On main, `Executor.map` submits every render up front, so the thread pool tokenizes continuously;
this PR renders at most `max_requests_in_core` ahead. The GPU starts about a second earlier, but
fewer renders are in flight in steady state, and the two effects cancel. The gain only shows with
pre-tokenized input, where rendering is cheap and main's serial up-front phase dominates.

Since the gain is limited to pre-tokenized input and the change adds complexity, I am closing this
PR; thanks again for the question.
