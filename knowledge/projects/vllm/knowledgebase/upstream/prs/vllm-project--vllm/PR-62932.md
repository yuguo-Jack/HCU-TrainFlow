# [KV Offload] Bound staged loads by primary tier capacity

[Upstream PR](https://github.com/vllm-project/vllm/pull/62932) · state: open · merged: False

## Original PR description

## Overview

Fixes #62931: with `TieringOffloadingSpec`, a secondary-tier hit larger than the CPU primary tier loaded nothing, so the whole prompt was recomputed. This revision follows the approach suggested in review: the scheduler looks the KV cache groups up together by token position, checks against the CPU tier's actual free and evictable space, and stops at the last point where every group fits, so a full CPU tier shortens the load instead of zeroing it.

## Claims

- A secondary-tier hit larger than the CPU tier loads the prefix that fits and recomputes the rest, instead of loading nothing. This holds for hybrid models too (full attention plus sliding-window or Mamba groups) when `prefix_cache_retention_interval` is positive, since those groups keep state only at retained checkpoints.
- A hit that fits is looked up exactly as on `main`; the new walk runs only when the hit's chunks and the boundary's lookups exceed the space left.
- A primary-tier hit stays pinned until the step ends, so a promotion started by the same (or another) lookup in that step cannot evict it before its load is prepared.
- Engines without secondary tiers are unchanged (`get_load_capacity()` is `None`).

## Validation

**Regression through `LLM`** (GPU): `tests/v1/kv_connector/unit/test_offloading_connector.py::test_tiering_hit_larger_than_primary_tier_loads_a_prefix`. `facebook/opt-125m` stores a prompt three times the size of the CPU tier in an `fs` tier through a larger CPU tier; a new engine with the small CPU tier then serves it. On `main` it loads nothing (`num_cached_tokens == 0`, the test fails); with this PR it loads a prefix that fits.

**Hybrid model** (GPU, manual): `google/gemma-3-1b-it` (one full-attention and six sliding-window groups), `prefix_cache_retention_interval=512`, a 32,000-token prompt stored through a 4 GiB CPU tier and served again through a 128 MiB one: cold prefill 1.71 s; through the 128 MiB tier 1.10 s with 29,184 of 32,000 tokens cached and identical output; on `main` the same request caches 0 tokens.

**Scheduler-level test** (CPU): `test_hit_larger_than_bounded_tier_loads_every_group_at_one_boundary` drives the real `OffloadingConnectorScheduler` over a bounded tier with an async secondary tier (one full-attention and two sliding-window groups): every group loads to one boundary that fits. Tiering manager tests cover the pin (`test_lookup_pins_primary_hits_until_step_end`) and `get_load_capacity()`.

## Details

**Root cause.** `TieringOffloadingManager.lookup()` promotes a secondary-tier hit by reserving its CPU-tier slot at once (`_initiate_promotion` → `primary_tier.prepare_write`). `OffloadingConnectorScheduler._lookup_complete_chunks()` walked the groups one after another and, for full-attention groups, queried every chunk up to the prompt end, so for a hit larger than the CPU tier the first group reserved every free slot, the next group's promotions failed (`MISS`), and the hit became 0.

**Fix.**
- `OffloadingManager.get_load_capacity()` (default `None`) reports how many more blocks lookups may bring this step into the tier that loads read from. `TieringOffloadingManager` returns the primary tier's free and evictable chunks (`CPUOffloadingManager.get_num_allocatable_chunks()`), `None` without secondary tiers.
- `TieringOffloadingManager.lookup()` pins a primary-tier hit (`prepare_read`) until `on_schedule_end()`, so that count stays exact and nothing evicts a hit before its load is prepared. `reset_cache()` drops the pins with the rest.
- Before its regular lookup, the scheduler's `_fit_load_to_capacity()` walks the full-attention groups' chunks together, ordered by the token where each ends. After each lookup it checks the capacity left; once a chunk that took room leaves less than the boundary needs (each windowed group's window rounded out to whole chunks, an EAGLE group's extra chunk, a partial tail's chunk and block per group, plus one), it stops before that chunk. A pending secondary-tier lookup (`RETRY`) counts as room it will take. The regular lookup then runs up to that boundary, rounded down to every group's chunk size, the mamba alignment and, with windowed groups, `prefix_cache_retention_interval`; with an interval of 0 those groups keep no state below the replay boundary, so the walk sets no bound.

**Limits.**
- A hit loads at most what the CPU tier can hold at once; the rest is recomputed. Loading a larger hit in several rounds through the CPU tier would need the scheduler to load part of a request's prefix over several steps, which is out of scope here.
- The capacity is read at lookup time; promotions of other requests in the same step are counted as they happen, so concurrent large hits share the space rather than each getting all of it.

**Not a duplicate.** Searched open PRs and issues for "promotion allocation", "primary tier capacity", "staged load", "secondary tier hit" and "tiering promotion". #49902 (issue) reports promotions for many waiting requests filling the CPU tier; #50014 and #62615 protect promotions or lookup hits from being evicted by *other* promotions; #60128 defers the FS tier's CPU allocation; #60000 gates promotions on tier backpressure; #53087 bounds how long one key may stay `HIT_PENDING`. None of them bounds one request's load by the space the CPU tier has, so a single hit larger than it still fails there.

- javieratomic · comment · 2026-10-26T16:58:56Z · [source](https://github.com/vllm-project/vllm/pull/62932#issuecomment-6422133795)

@orozery thanks, I reworked the PR along those lines and rebased it on `main` (d4146a203e):

1. **Interleaved lookup:** the scheduler walks the full-attention groups together by token end and checks after each lookup, so no group is exhausted before the others.
2. **Actual free and evictable space:** `OffloadingManager.get_load_capacity()` replaces the fixed cap; for the CPU tier it is free plus evictable chunks. `TieringOffloadingManager` pins the primary-tier hits of a lookup until the end of the scheduling step, so a later lookup in the same step cannot evict them.
3. **Stop at the last point where every group fits:** the walk stops when the remaining capacity cannot hold the next boundary, and the load is rounded to `prefix_cache_retention_interval` so sliding-window groups land on a stored boundary. A full CPU tier now shortens the prefix instead of loading nothing.

Tested on DGX Spark: the GPU regression through `LLM` loads a prefix where `main` loads nothing, and with `google/gemma-3-1b-it` (one full-attention and six sliding-window groups) a 32,000-token prompt served through a 128 MiB CPU tier gets 29,184 tokens cached with identical output (0 on `main`). Confirmed, thanks. I ported the real-manager test to this head (`TieringOffloadingSpec`, `TieringOffloadingManager`, `example` secondary tier, full + 8-token SWA, 4-token chunks, `prefix_cache_retention_interval=None`, 64-token request with every hash in the secondary tier). With two slots, `d4146a2` returns `(0, False)` on the first lookup.

**What was wrong.** Two things. First, the reserve was fixed: the whole window plus its edge chunks (4 chunks here), whatever the length of the load. Second, it also kept one extra slot for the chunk the walk stops at, because the walk looked up a chunk before checking whether it fit. After the first full-attention chunk took a slot, one slot was left, which was less than the reserve of 5, so the walk returned `start_token=0`. Computing the reserve per prefix alone would not fix this: a 4-token load needs 1 window chunk, and with the extra slot that is still 2 slots against the 1 that is left.

**What changed** (`3f42aae30f`, `scheduler.py` only):
- `_boundary_lookup_chunks(num_computed_tokens, end_token)` now computes the reserve for the candidate load. Each windowed group counts `min(window + edges, cdiv(end, tokens_per_chunk) - num_computed_tokens // tokens_per_chunk)`, because the SWA lookup slices its keys at the load end and cannot query more chunks than that. The EAGLE and partial-tail chunks are counted as before.
- Once the walk's lookups have taken room, it checks before each lookup that the space left holds that chunk plus the boundary of a load ending with it. If it does not, the walk stops before that chunk without looking it up. The chunk after the load is therefore never promoted, so the extra slot is gone.
- Before any lookup has taken room, every chunk is already in the primary tier or on its way, so the walk looks chunks up without the check, as before. Otherwise a hit whose promotions are still in flight could be cut to 0. The check after each lookup stays for the first chunk that takes room.

**Proposal: split lookup from commit**

Today `lookup()` starts promotions in the middle of the walk. That is why one group can fill the CPU tier ahead of the others, why a request's own promotions evict its own HITs, and why this PR has to estimate capacity from outside the manager. Suggested design (the connector stays unaware of tiers; `LookupResult` is unchanged):

1. **`lookup()` has no side effects.** Existing results: `HIT` (readable now), `HIT_PENDING` (exists, not readable yet, e.g. write in flight or in a secondary tier), `RETRY`, `MISS`. It may start async existence checks, but never allocates CPU slots.
2. **Add `commit_lookup(keys, req_context)` to `OffloadingManager`.** Called once the lookup pass converges, with every key the hit needs (full-attention chunks, sliding-window window, EAGLE extra chunk, partial-tail keys). All-or-nothing: the manager re-checks each key, pins the readable ones, and makes the rest readable (for tiering: allocates promotion slots; in-flight writes are pinned when they land), or rolls back and reports how many slots it was short. Default: always succeeds.
3. **On failure, lower the hit end and commit again**, on a boundary every group can end on (retention interval, mamba alignment). A full CPU tier then gives the longest prefix that fits instead of nothing (still 0 if not even one aligned prefix fits, or for windowed/Mamba groups with `prefix_cache_retention_interval=0`).
4. **A committed request is not looked up again.** It waits until the manager reports its committed keys readable (one per-request query), then reports the hit. It goes back to lookup only if its GPU prefix shrinks below the committed start, a promotion fails, or `reset_cache` runs; if the prefix grows, committed keys below it are released.
5. **Committed keys stay pinned until `prepare_load`**, which takes over the pins; finish, abort, `reset_cache` and a return to lookup release them. Commits are all-or-nothing, so no request holds part of a hit and this cannot deadlock. Optional follow-up: limit how much of the tier one request may hold.

5. **Pinned until load.** `get_hit_status` is O(1). A committed request is not looked up again; `prepare_load` / `create_store_job` take over the pins; finish, abort and `reset_cache` release them. Shared or lost keys give `MISS` without lowering the budget (your point 5).
6. **Store reserve** sized from measured store/cascade occupancy, capped as a safety limit (your point 3).
7. **P2P/KVCR** use the same flow instead of relying on `lookup()` to promote.

**Cost vs. today:** same for a hit that fits (one set update per lookup). Fewer lookups and no wasted promotions for an over-size full-attention hit. Up to ~window + 2 extra passes only for an over-size hit with sliding-window groups.

**Re #60128:** with the ban gone, a doomed promotion retries once per round trip. Each retry does O(keys) work under `manager_lock` before failing (inline on the scheduler thread for example/obj/kvcr/p2p) and also skews the access counts and ARC learning. Item 4's bound covers this.
