# [Rust Frontend] Select one structured outputs backend for every route

[Upstream PR](https://github.com/vllm-project/vllm/pull/62456) · state: open · merged: False

## Original PR description



## Overview

EngineCore compiles every structured-output request with the backend of the first one it sees. The Rust frontend sends gRPC constraints and parser-built output grammars as xgrammar, but every other HTTP constraint as guidance (#44729), so one server that takes both kinds of traffic is order-dependent: after a native constraint reaches the engine first, every later strict, `required`, or named tool call and every `response_format` composed with a reasoning parser fails with `KeyError: 'triggers'` (HTTP 500). This PR makes every Rust route use one backend, chosen by the operator with `--structured-outputs-config.backend` and defaulting to xgrammar, as Python's `auto` does for most requests. It is the follow-up named in #61892.

## Claims

- Every Rust route (chat, completions, gRPC) sends one backend: `--structured-outputs-config.backend`, default `xgrammar`. `auto` selects xgrammar; `guidance`, `outlines`, and `lm-format-enforcer` are accepted. A server no longer depends on which request arrives first.
- With xgrammar, Rust HTTP rejects JSON schemas whose keywords xgrammar ignores with 400, as gRPC does since #61892 and as Python does with `backend=xgrammar`.
- With another backend, chat does not build parser output grammars (they are xgrammar structural tags): the request keeps its own constraint, which the engine applies after reasoning, and tool calls are parsed without a grammar. `--tool-strict-level function|parameter` fails startup unless the backend is xgrammar.
- Constraints the selected backend cannot compile return 400 instead of failing in EngineCore, following Python's per-backend validation: `format`-shape structural tags on guidance, and the constraint kinds outlines and LM Format Enforcer reject.
- `vllm-rs serve` forwards `--structured-outputs-config` to the managed engine, so engine-side options such as `disable_any_whitespace` take effect.

## Details

**Root cause.** `StructuredOutputManager.grammar_init` creates one backend from the first structured request and keeps it until shutdown. Python chooses `_backend` in `SamplingParams` validation, which the Rust frontend skips, so #44729 defaulted Rust to guidance; guidance handled `choice`, which xgrammar could not compile then. Parser-built output grammars (#46057) and gRPC (#61892) later moved to xgrammar, and guidance reads only the legacy `triggers`/`structures` structural tag.

**Where the backend lives.** The backend is now a field of the EngineCore request type only (`EngineCoreStructuredOutputsParams`). `StructuredOutputsParams`, the type the HTTP/gRPC entry points and chat build, carries no backend, so nothing picks one implicitly. `TextRequestProcessor` holds the configured backend, and text lowering, which HTTP and gRPC share, attaches it and validates the final constraint against it. gRPC no longer selects a backend itself.

**Why one backend per server, not per request.** The engine still holds one backend, so a per-request choice would bring the order dependence back. Python's `auto` fallback has the same limit in a mixed workload. Engine-side multi-backend support (#62246, draft) would allow request-level selection later; a single configured backend maps onto a one-element list then.

**Tradeoffs.**
- HTTP constraints that used guidance now use xgrammar by default. Schemas with keywords xgrammar ignores (`multipleOf`, `uniqueItems`/`contains`, unsupported string `format`s, `pattern` with length bounds, ...) return 400 instead of being enforced by guidance; `--structured-outputs-config '{"backend": "guidance"}'` restores that. llguidance does not implement `uniqueItems` either: Python `auto` rejects it in guidance validation, while the Rust frontend on `main` returns an empty 200 when the matcher errors in EngineCore.
- Lark grammars now compile with xgrammar's Lark support (#58321); llguidance-only extensions need `backend=guidance`.
- Schemas composed into a parser grammar are not checked for xgrammar-unsupported keywords, as in Python.
- `vllm-rs serve` reads only the JSON form of `--structured-outputs-config`; the dotted form (`--structured-outputs-config.backend guidance`) goes to the Python engine only, like other dotted flags on that path. The `vllm serve` path reads both.

**Not a duplicate.**
- #61892 (merged) moved gRPC to xgrammar and named this change as its follow-up.
- #62431 (open) no longer touches `--structured-outputs-config`; the two PRs are independent.
- #62246 (draft) and #49625 (open) address the single-backend limit inside the engine. This PR changes only what the Rust frontend sends.
- #55153 (open) teaches guidance some `format`-shape structural tags; with it, more guidance requests would pass the new check, which can be relaxed then.
