# [Perf][DSA] Add FlashInfer gvr_2 as a sparse-indexer top-k backend

[Upstream PR](https://github.com/vllm-project/vllm/pull/57109) · state: open · merged: False

## Original PR description

## Overview

Add FlashInfer's exact self-sampling top-k `gvr_2` (flashinfer-ai/flashinfer#4811, hint-free in the pinned 0.7.2) as an opt-in DSA sparse-indexer top-k backend, `sparse_indexer_topk_backend=flashinfer_gvr2`, for both the DeepSeek-V3.2 and the GLM-5.3-Flash kpool indexers. `auto` is unchanged from main.

## Claims

- Opt-in only. gvr_2 derives its threshold from a sample of each row, so its latency depends on the logit distribution, and `auto` keeps the cooperative -> persistent -> per_row chain.
- Decode: on real GLM-5.3-Flash rows gvr_2 is faster at the median (10.3 vs 12.4 us for a single row, 12.4 vs 24.8 us for 64-row batches), but its single-row tail is worse (p99 23 us, max 33 us, vs a flat ~13 us for cooperative).
- Prefill: chunks with at least 1024 row-relative rows use gvr_2, which makes prefill top-k 1.77x faster on real GLM-5.3-Flash prefill logits. Unlike decode, the gain does not depend on the distribution (1.81x on Gaussian data of the same shapes).
- Results are exact (same value multiset as `torch.topk`). With the backend selected, end-to-end accuracy and throughput match main within run-to-run noise. This PR makes no end-to-end speedup claim.

## Details

- The dispatcher calls FlashInfer's production entry `run_varlen` hint-free. The public `top_k_varlen` wrapper adds about 50 us of host validation per call. gvr_2 compiles per row-count band, so the first eager decode call warms up every decode row count (about 0.2 s).
- CUDA graphs: `run_varlen` gets `max_seq_len`, so it never reads lengths on the host. Launchers and the workspace are warmed eagerly before capture, and FlashInfer raises rather than compiling under capture.
- Since #61149, CUDA prefill logits are row-relative (`row_starts is None`), which matches gvr_2's rows-start-at-column-0 contract. XPU still passes row starts and stays on `top_k_per_row_prefill`. Under #54951 TP row sharding, the 1024-row gate applies per rank. Chunks below 1024 rows are faster on `top_k_per_row_prefill`.
- `as_fp32_logits` now allocates whole padded rows. gvr_2 reads the logits as `[rows, stride]`, and the old `empty_strided` storage ended at the last row's width, which aborted CUDA-graph capture. `_gvr2_constraints` checks this, together with the float4 row pitch and alignment.
- Requirements: SM100 family, fp32 logits, `topk` in {512, 1024, 2048}, flashinfer-python >= 0.7.2 (feature-detected; without it the explicit backend raises).
- Not a duplicate: no other open PR wires FlashInfer `gvr_2` in. #62172 (BF16 logits for `cooperative_topk`) and #60802 (DeepSelect preference) change other backends.

File: `vllm/model_executor/layers/indexer_topk.py` · line 301

This caps the warmed row counts at 256MB / (stride x 4). At a 128K width that’s 512 rows.

But `_gvr2_max_rows` is `max_num_seqs × (1 + num_spec)`. With 256 sequences and 3 MTP tokens that’s 1024, and SM100’s default largest CUDA-graph size is `min(2·max_num_seqs·q_len, 1024)`.

`warmup_varlen` only allocates up to its largest representative row count, not every requested row, so pass the full range.
