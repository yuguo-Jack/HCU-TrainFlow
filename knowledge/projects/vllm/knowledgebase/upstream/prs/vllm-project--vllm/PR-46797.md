# [Bugfix][Frontend] Accept Anthropic server tools without input_schema

[Upstream PR](https://github.com/vllm-project/vllm/pull/46797) · state: closed · merged: False

## Original PR description

Fixes #46790.

Anthropic server tools (`web_search_20250305`, computer use, bash, text_editor, code_execution) are sent without an `input_schema`. `AnthropicTool.input_schema` was required, so Claude Code's WebSearch tool 400'd at validation before anything ran.

Make `input_schema` optional and skip schema-less server tools in the OpenAI function conversion (vLLM can't run them as function tools). Normal function tools are unchanged; a non-dict schema is still rejected.

Scope: this fixes the validation crash only — actually executing server tools (real web search) is out of scope.

Verified locally (GPU stack unavailable here, so direct import):
```
PASS: web_search server tool validates; input_schema = None
PASS: normal tool unchanged, type defaulted to object
PASS: non-dict input_schema still rejected -> ValidationError
```
Conversion-skip covered by the added test in tests/entrypoints/anthropic/test_anthropic_messages_conversion.py (runs in CI).

- rahuja23 · comment · 2026-09-17T09:15:21Z · [source](https://github.com/vllm-project/vllm/pull/46797#issuecomment-5711936685)

I looked at fixing this and want to flag a divergence between #46797's approach and what deferred
tools (as opposed to server tools) seem to need.

#46797 makes `AnthropicTool.input_schema` optional (matches this issue's root cause exactly), but
then has `_convert_tools` skip any tool whose `input_schema` is `None`:

    if tool.input_schema is None:
        continue

For server tools (`web_search_20250305`, `computer_*`, `bash_*`, ...) that's fine — vLLM can't run
them as function calls anyway, so dropping them from the OpenAI-format tool list is a no-op in
practice.

For deferred tools from Claude Code's tool-search flow, though, skipping means the tool is dropped
from the request entirely rather than being forwarded with `parameters: null`. The model never
even learns the tool's *name* exists on that turn. That seems like it would silently break the
deferred-tool mechanism rather than unblock it — the whole point of announcing a deferred tool is
so the model knows it exists and can request it later, even without a schema yet.

An alternative: keep `input_schema` optional (as #46797 does) but only skip tools that are
actually unrunnable server tools, and pass everything else through with `parameters: None`
untouched (I verified `FunctionDefinition.parameters` on the OpenAI-compat side already accepts
`None`, so downstream doesn't choke on it).

I don't have full visibility into the intended contract for how a deferred tool is supposed to
render to the model when name-only, so flagging this rather than asserting it — happy to be
corrected if skip-everywhere is actually the right call. If it's not, I have a small patch
(protocol.py change identical to #46797's, serving.py change that forwards instead of skips, plus
regression tests) ready to open as a PR against this issue once we're aligned on the approach.


- hclsys · comment · 2026-09-17T09:21:18Z · [source](https://github.com/vllm-project/vllm/pull/46797#issuecomment-5712011593)

You're right, and it's worse than a design divergence — it's a straight bug in what I wrote. I
reproduced it on this branch before touching anything:

```
client sent   : ['web_search_20250305', 'deferred_grep', 'normal']
model receives: ['normal']
```

`deferred_grep` has `defer_loading=True` and no schema, and my `continue` ate it. The thing that
makes it clearly wrong rather than arguable: the loop already forwards `defer_loading` a few lines
down, so the skip was killing the tool right before the code that exists to handle it.

Pushed the fix (1c5152d):

```python
if tool.input_schema is None and not tool.defer_loading:
    continue
```

so only schema-less tools that aren't deferred get dropped, and the rest go through with
`parameters=None` — same as your suggestion. After:

```
model receives: ['deferred_grep', 'normal']    deferred_grep parameters=None defer_loading=True
```

One assumption worth naming, since you have more context on the tool-search flow than I do: I'm
using `defer_loading` as the discriminator rather than matching server-tool name prefixes. That
holds only if Claude Code actually sets `defer_loading` on a name-only announced tool. If it
doesn't, this is still broken and the prefix match is the right call — say so and I'll switch it.

Sorry for the wasted effort on your patch. Since this PR was already open and green it seemed
better to fix it here than have two PRs for one issue, but the catch is yours. A review on it
would be welcome if you have the time.

FYI @hclsys: #64575 has merged and takes the other approach to #46790. Anthropic-defined tools are rejected with a 400 that names the tool type, not accepted and dropped.
