# [Bugfix] Skip prompt_embeds passthrough items in set_active_mm_loras

[Upstream PR](https://github.com/vllm-project/vllm/pull/63190) · state: closed · merged: True

## Original PR description

## Purpose

`set_active_mm_loras` crashes any request that uses `prompt_embeds`
(raw precomputed embeddings passed directly via `EmbedsPrompt`, bypassing
the tokenizer and all encoders) when `--enable-tower-connector-lora` is
set:

```
ValueError: Unsupported modality: prompt_embeds
```

`set_active_mm_loras` iterates every item in `scheduled_encoder_inputs`
and calls the model's `get_mm_lora_token_counts()` for each one,
including items whose modality is the special `"prompt_embeds"`
passthrough value. That modality isn't image/video/audio and has no
tower or connector output to apply LoRA to in the first place, since no
encoder ever runs for it — the tensor is already in the model's
embedding space.

Three other call sites in the v1 worker already treat `"prompt_embeds"`
as a passthrough modality to skip:
- `vllm/v1/worker/gpu/mm/encoder_runner.py`
- `vllm/v1/worker/gpu_model_runner.py`
- `vllm/v1/worker/gpu/model_states/default.py`

`set_active_mm_loras` didn't, so any item with that modality fell
through to the model's `get_mm_lora_token_counts()`, which doesn't (and
shouldn't have to) know about it.

## Who this affects

This is generic LoRA runtime code, not specific to any one model. Every
model declaring `supports_tower_connector_lora = True` goes through this
same function — at time of writing that's 21 models: `Qwen2VLForConditionalGeneration`,
`Qwen2_5_VLForConditionalGeneration`, `Qwen3VLForConditionalGeneration`,
`Qwen3ASRForConditionalGeneration`, the LLaVA family (`LlavaForConditionalGeneration`,
`LlavaNextForConditionalGeneration`, `LlavaNextVideoForConditionalGeneration`),
`Gemma3ForConditionalGeneration`, `Gemma4ForConditionalGeneration`, `PaliGemmaForConditionalGeneration`,
`InternVLChatModel`, `Glm4vForConditionalGeneration`, `KeyeForConditionalGeneration`,
`Idefics3ForConditionalGeneration`, `Lfm2VlForConditionalGeneration`, `DotsOCRForCausalLM`,
`Blip2ForConditionalGeneration`, `PixtralForConditionalGeneration`, `Llama4ForConditionalGeneration` (mllama4),
`UltravoxModel`, and `NemotronH_Nano_VL_V2`/`NemotronH_Nano_Omni_Reasoning_V3`.

Any of them, combined with `--enable-tower-connector-lora` and a request
using `prompt_embeds`, hits this exact crash — I found it while testing
LoRA support for Nemotron Nano/Omni VL (#58658), but it's unrelated to
that model specifically.

## Fix

Skip `prompt_embeds` items in `set_active_mm_loras`'s loop, before they
ever reach the model, matching the exact comment/pattern already used at
the three call sites above.

## Test Plan

Added `tests/v1/worker/test_mm_lora.py`, a focused unit test with mocked
model/encoder-cache/lora-manager objects. Confirmed it:
- **fails** on the pre-fix code, reproducing the crash (`get_mm_lora_token_counts`
  gets called with `modality="prompt_embeds"` and would raise there)
- **passes** after the fix, and confirms the real (non-passthrough) item
  in the same batch still gets its LoRA mapping built correctly.

```
pytest tests/v1/worker/test_mm_lora.py -v
# 1 passed
```
