# [Rust Frontend] Validate, deduplicate and cap bad words like Python

[Upstream PR](https://github.com/vllm-project/vllm/pull/63315) · state: closed · merged: True

## Original PR description

## Overview

The Rust frontend tokenizes `bad_words` in `tokenize_bad_words` (`rust/src/text/src/lower.rs`), which has drifted from Python's `SamplingParams` (`__post_init__`, `_verify_args`, `update_from_tokenizer`). This PR aligns it with Python's validation, whitespace handling, deduplication, and early cap (vllm-project/vllm#53433, vllm-project/vllm#51447).

## Claims

| Input | Python | Rust before | Rust after |
|---|---|---|---|
| `bad_words: ["x", ""]` | 400 `bad_words cannot contain an empty string.` | accepted; the empty word's `" "` encoding is compared against the previous word's | 400, Python's message |
| `bad_words: ["  "]` (tokenizes to nothing once leading whitespace is dropped) | 400 `bad_words entries must tokenize to at least one token.` | accepted; bans the whitespace tokens | 400, Python's message |
| `bad_words: [" blocked"]` | bans `blocked` and ` blocked` | bans only ` blocked` | bans both |
| the same word 200 times | one word, two sequences | 400 `Too many bad words: 400. ...` | one word, two sequences |
| 129 distinct words | 400 `Too many bad words after tokenization: 129. ...`, before tokenizing the rest | tokenizes every entry, then 400 `Too many bad words: 129. ...` | Python's message, stops at the cap |

Applies to chat and `/inference/v1/generate`. `/v1/completions` drops `bad_words` before lowering today; that separate gap is vllm-project/vllm#48951.

## Details

Two commits, one per Python change, both in `tokenize_bad_words`:

1. **Reject bad words that tokenize to nothing.** An empty entry is rejected up front. Both encodings use the word without its leading whitespace; an empty plain encoding is a 400, an empty space-prefixed encoding is skipped. The plain encoding is now always pushed first, so the prefixed form is compared against its own word's plain encoding.
2. **Deduplicate and cap while tokenizing.** Duplicate words are dropped before tokenization, and tokenization stops with Python's message once the sequences exceed `VLLM_MAX_NUM_BAD_WORDS`. The existing combined check over raw `bad_words_token_ids` (gRPC) plus tokenized words (vllm-project/vllm#61933) stays: it guards the engine's per-request buffer. Both checks read the cap from one `max_num_bad_words()` helper.

`tokenize_bad_words` is the only code that encodes `bad_words` strings and already owns the bad-words limits, so the checks and the new `TokenIdsError` variants live there and surface as 400s through the existing `Error::TokenIds` mapping.

Differences kept: Python sets `param: "bad_words"` on these errors, while `vllm_text::Error::param` reports no param for any `TokenIds` error today, including the existing bad-words limits; Python's empty-entry message also appends `Got bad_words=[...]`.

Not a duplicate: no open PR changes `tokenize_bad_words`.
