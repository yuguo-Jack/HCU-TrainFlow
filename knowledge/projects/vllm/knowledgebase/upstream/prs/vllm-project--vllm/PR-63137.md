# [Rust Frontend] Accept duplicate reasoning aliases in chat messages

[Upstream PR](https://github.com/vllm-project/vllm/pull/63137) · state: closed · merged: True

## Original PR description

## Overview

Fixes #63130: the Rust frontend rejected chat requests whose assistant message carries **both** `reasoning` and `reasoning_content` with an opaque serde `duplicate field` parse error, while the Python frontend accepts the identical body. This permanently breaks multi-turn agent loops because the offending assistant turn stays in history and every follow-up request fails.

The fix normalizes the reasoning aliases to the primary `reasoning` field in `ChatMessage::deserialize` before dispatching to the derived impl, mirroring the Python frontend's `_normalize_messages_before` (`vllm/entrypoints/openai/chat_completion/protocol.py:556`).

## Claims

- A chat request with an assistant message carrying `reasoning` + `reasoning_content` (in any key order, plus the `thinking` alias) is now accepted, matching the Python frontend's behavior matrix from the issue.
- Non-null `reasoning` wins (including an empty string); a JSON-null `reasoning` falls back to `reasoning_content`, exactly mirroring the Python normalization semantics.
- The thinking text is carried exactly once into the rendered assistant reasoning block.

## Validation

Reproducer from the issue (both keys together) and the alias precedence matrix (key order, null and empty `reasoning`, wrong-type alias, `thinking`) are covered by one table-driven test at the deserialization layer, `assistant_reasoning_aliases_fold_into_reasoning`:

```bash
cargo test -p vllm-server --lib
# test result: ok. 504 passed; 0 failed
```

Regression proof: with the `normalize_reasoning_aliases` call removed, `assistant_reasoning_aliases_fold_into_reasoning` fails because alias values no longer reach `reasoning`; restored, all tests pass. `cargo fmt --check` and `cargo clippy -p vllm-server --all-targets -- -D warnings` are clean.

## Details

**Root cause.** `ChatMessage::Assistant` declares `reasoning` with `#[serde(alias = "reasoning_content")]` / `#[serde(alias = "thinking")]`. Serde's derived `Deserialize` treats every key mapping to one field as a candidate and raises `duplicate field` when two of them appear, before any normalization can run. The Python frontend instead pops `reasoning_content` in a `model_validator(mode="before")` and fills `reasoning` only when it is absent/null, so the same payload is accepted there.

**Fix.** The manual `Deserialize` impl already materializes each message as a `serde_json::Value` for role dispatch; a small `normalize_reasoning_aliases` step runs on that value first (removes both alias keys, promotes the first non-null alias when `reasoning` is absent/null). Because it is key-based rather than order-based, it is deterministic regardless of client key order. The `#[serde(alias)]` attributes are removed, so this step is the only place that defines the alias set.

**Intentional deviation (Python parity note).** The Python frontend does not normalize a top-level `thinking` string on messages (it is an unknown field there), while the Rust frontend deliberately accepts it as an alias. The collision handling therefore orders precedence as `reasoning` > `reasoning_content` > `thinking`, keeping the existing Rust-only `thinking` extension but making it tolerant of duplicates too.

**Not duplicating an existing PR.** Verified with `gh pr list --search "63130 in:body"` (0 results) and issue search; no open PR addresses this. Note: a comment on the issue mentions a similar effort in progress; this PR is a narrow, tested fix at the same layer and is offered in case it is useful — happy to yield or rebase on a competing approach if maintainers prefer.

**Limitation.** This restores wire-level acceptance parity for the reasoning alias family. The Python frontend's separate semantic rejection of typed `thinking` content blocks combined with top-level `reasoning` (PR #41718) is not ported here; that is a distinct validation concern and would merit its own change.
