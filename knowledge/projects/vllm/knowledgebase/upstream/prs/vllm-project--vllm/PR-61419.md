# [Feature][Pooling] Add late chunking HTTP API and retrieval example

[Upstream PR](https://github.com/vllm-project/vllm/pull/61419) · state: closed · merged: False

## Original PR description

## Overview

Expose fixed length late chunking through `/pooling`, with chunk vectors and source ranges in the response. Completes the remaining C, D and E scope of #58774, following #60164.

## Claims

- Plain text `token_embed` requests can opt in with `late_chunking_params.chunk_size`.
- Chunk metadata stays in the frontend and follows each document through rendering and output collection. Requests without the option keep their existing response format.
- A retrieval example shows how to index chunk vectors and recover the matching source text.

## Validation

- 236 unit tests passed locally.
- Both model runners passed all 15 HTTP tests on an A100 80GB with multilingual E5 small in BF16. Coverage includes chunk means checked against unnormalized token outputs, source ranges, input validation, concurrent requests and existing token embedding behavior.
- The retrieval example passed with default behavior, an explicitly saved index and chunk size 1.
- Pre-commit, including mypy and CI test discovery, passed.

```bash
VLLM_WORKER_MULTIPROC_METHOD=spawn VLLM_USE_V2_MODEL_RUNNER=1 \
  python -m pytest tests/entrypoints/pooling/token_embed/test_online.py -v
# Repeat with VLLM_USE_V2_MODEL_RUNNER=0.
```

### Measurements

multilingual E5 small, BF16, A100 80GB. Baseline: request unnormalized token vectors, then compute chunk means, normalization and source ranges on the client. Both modes use loopback HTTP, with two warmups and nine measured requests per case. Times include JSON parsing and client pooling. Values in each pair are baseline / server chunking.

Source ranges matched, with a minimum vector cosine similarity of 0.99999839. These timings show the benefit of smaller responses and less client processing; they do not establish faster model compute. Measured CUDA allocator peaks were unchanged. With `chunk_size=1`, the added metadata increased response size and latency.

The [measurement script, reproduction commands and raw samples](https://github.com/LinzeShi/vllm/tree/bec47cc79d090c05f2ae6171c0b07b57ffee8f30/review-artifacts/late-chunking-online-20261013) are available separately from the implementation.

## Details

The online path reuses the reducer and source mapping helpers from #60164. It adds no scheduler or worker changes. The initial online mode accepts plain text and float output; other pooling endpoints reject the option instead of silently ignoring it.

Both the HTTP and Python APIs require `0 < chunk_size < 2**63`. A chunk size larger than the input token count produces one chunk.

The example uses E5 document/query prefixes and can optionally save the index as JSON. Documentation covers deployment, response fields and source range conventions.

- claude[bot] · comment · 2026-10-14T02:44:56Z · [source](https://github.com/vllm-project/vllm/pull/61419#discussion_r4266235103)

File: `vllm/entrypoints/pooling/pooling/protocol.py` · line None

🔴 An HTTP client can send a huge `chunk_size` and leave a request permanently stuck in the frontend. On the base branch, no HTTP client can set this field. `LateChunkingConfig.chunk_size` only checks `gt=0`, so a JSON integer of 2**64 or more passes validation and render. Encoding the engine request then raises an overflow error. By then `_add_request` has already registered the request in the output processor, and nothing removes it. Fix: give `chunk_size` an upper bound (for example `le=2**63 - 1`, matching `priority`, or the model's `max_model_len`). That rejects every out-of-range value with a 400 before engine handoff.

<details>
<summary>Why this was flagged</summary>

The trigger is a POST to /pooling on a token_embed server with `"late_chunking_params": {"chunk_size": 18446744073709551616}`. That value is 2**64, which pydantic accepts as a strict int. `LateChunkingConfig` (protocol.py:32) checks only `gt=0`. `LateChunkingParams.verify` (pooling_params.py:57) checks only that the value is positive. `AsyncLLM._add_request` registers the request with `output_processor.add_request` (async_llm.py:572), then awaits `engine_core.add_request_async`. That call msgpack-encodes the EngineCoreRequest (core_client.py:1247). msgspec cannot encode ints above 2**64-1 and raises OverflowError. `encode()` hits `except Exception` with `q is None` (async_llm.py:1065-1070), so `abort` never runs and the entry stays in `request_states`. With `max_num_queued_reqs` or `max_num_queued_tokens` configured, repeated requests like this eventually make the server return 503 to everyone. On the base branch no HTTP field reaches this path.

**Verification:** Trigger: an HTTP client sends `late_chunking_params.chunk_size` >= 2**64 to /pooling. At protocol.py:32, `chunk_size: int = Field(gt=0, strict=True)` sets no upper bound. core_client.py:1247 msgpack-encodes the EngineCoreRequest, and msgspec raises OverflowError for ints above 2**64-1. In `encode()` (async_llm.py:1017-1070), `q` is still None, so the `except Exception` branch skips `self.abort(...)`.

</details>
