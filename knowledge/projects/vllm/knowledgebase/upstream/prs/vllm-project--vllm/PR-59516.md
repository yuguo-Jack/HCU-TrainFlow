# [Bugfix][Quantization] Set orig_dtype in ModelOpt FP8 channel/block schemes

[Upstream PR](https://github.com/vllm-project/vllm/pull/59516) · state: open · merged: False

## Original PR description



## Overview

Below SM89, ModelOpt FP8 linear layers use `MarlinFP8ScaledMMLinearKernel`. Before this change, `FP8_PER_CHANNEL_PER_TOKEN` and `FP8_PB_WO` checkpoints failed to load there because their weight schemes never set `layer.orig_dtype`, which Marlin's weight prep reads. This PR sets it in both schemes and adds a hardware-independent regression test.

Found while verifying #55008 on Ampere: now that #55884 selects Marlin there instead of CUTLASS, these two schemes reach Marlin for the first time. Related: #56660 (ModelOpt FP8 on SM75, which also runs through Marlin).

## Claims

- ModelOpt `FP8_PER_CHANNEL_PER_TOKEN` and `FP8_PB_WO` checkpoints load and serve on GPUs below SM89 (tested on SM86). Before this change they failed with `AttributeError: 'QKVParallelLinear' object has no attribute 'orig_dtype'`.
- GSM8K accuracy for both checkpoints on the Marlin path is within about 1 standard error of the BF16 base model.
- New unit test `test_modelopt_fp8_weight_schemes_set_orig_dtype` fails without the fix on any GPU, including the SM89+ machines CI uses.

## Validation

## Details

**Root cause:** `ModelOptLinearMethod` builds each layer's parameters through per-quant-key weight schemes. `KFp8StaticTensor.create_weights` sets `layer.orig_dtype = shapes.params_dtype`, but `KFp8StaticChannel` and `KFp8Block128` do not. On SM89+ these schemes use CUTLASS, which never reads the attribute. Below SM89 they fall back to Marlin, and `prepare_fp8_layer_for_marlin` casts `weight_scale` to `layer.orig_dtype`. Before #55884, kernel selection on Ampere picked CUTLASS FP8 instead (#55008), so these schemes never reached Marlin there, which hid this bug.

**Fix:** set `orig_dtype` in both schemes, in the same place and the same way as `KFp8StaticTensor`. An alternative was to make Marlin's weight prep fall back to another dtype source when the attribute is missing. I kept the change on the scheme side, which is consistent with the existing scheme and minimal. Happy to switch if maintainers prefer the Marlin-side approach.

**Scope checked:** the only other layer-level readers of `orig_dtype` in the kernel utils are `prepare_fp8_moe_layer_for_marlin` (the ModelOpt MoE method already sets it) and the block branch of `prepare_fp8_layer_for_marlin`. MXFP8 uses `prepare_mxfp8_layer_for_marlin`, which does not read it, so `KMxfp8Static` is unaffected.

**CI coverage gap:** CI GPUs are SM89+, so CI never exercises the Marlin path for these schemes. The new unit test checks the attribute directly, so it catches a regression on any GPU. The existing `test_modelopt_fp8_{pc_pt,pb_wo}_checkpoint_setup` tests also run on SM80/86. There they fail before this change with the same `AttributeError`. After it, they get past loading and then fail on layout assertions that assume non-Marlin weights (`weight.dtype == fp8`, while Marlin repacks to `int32`). Making those assertions kernel-aware is left as a possible follow-up, not part of this PR.

**Duplicate check:** I searched issues and PRs for `orig_dtype`, `FP8_PER_CHANNEL_PER_TOKEN`, `FP8_PB_WO marlin`, `KFp8StaticChannel`, `KFp8Block128`, `prepare_fp8_layer_for_marlin` and `modelopt Ampere fp8`. There is no existing report or fix. #56660 enables the same Marlin path on SM75, but its tests used a per-tensor checkpoint, which already set `orig_dtype`. #50617 (stale) touches these scheme classes but does not add the attribute to the Channel or Block128 schemes.

**AI assistance:** Claude Code helped with the investigation, the repro script and the test structure. I reviewed every changed line, and I ran all of the validation above on my own hardware.
