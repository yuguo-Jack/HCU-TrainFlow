# [Perf][DSA] Token-sharded sparse-MLA prefill under TP; remove indexer row sharding

[Upstream PR](https://github.com/vllm-project/vllm/pull/63956) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Shard DSA sparse-MLA prefill across TP ranks by token instead of by head ("ShardQ", Ulysses style) and remove the indexer TP row sharding from #54951, which it supersedes, including in GLM-5.3-Flash's k-pool indexer. Enabled by default for steps with >= 1024 tokens after the decodes (`sparse_mla_shard_q_min_tokens`), including mixed prefill + decode steps (whose decode tokens stay head-sharded); at 4K the gain is small and within end-to-end noise. Validated on GLM-5.3; GLM-5.3-Flash is covered by a forward-time microbenchmark and a greedy retrieval A/B.

## Claims

- GLM-5.3 (NVFP4, TP4, GB200, default FlashInfer sparse MLA backend) TTFT at concurrency 1: **1.24x at 32K, 1.29x at 64K, 1.40x at 128K** prompts.
- Per-step prefill forward is **1.11x-1.70x faster** than main, growing with context length (16K-token chunk at 128K context: 926 ms -> 544 ms), and **1.18x-1.25x faster than the removed row sharding** even with row sharding forced on. With default settings row sharding never engages: it needs >= 65536 prefill rows in one step, above the default `max_num_batched_tokens`.
- At 64K-token chunks, where main's row sharding engages by default, per-step forward is **1.14x-1.26x faster than row sharding** (B300; 64K chunk at 1M context: 11.17 s -> 9.83 s).
- GLM-5.3-Flash (k-pool indexer, now ShardQ-enabled): per-step forward at 64K-token chunks is **1.08x-1.13x faster than row sharding**, which this PR replaces there too.
- Mixed prefill + decode steps (one prefill chunk plus 32 decodes, GLM-5.3, B300): per-step forward is **1.16x-2.90x faster than main** on FlashInfer and **2.04x-2.97x** on FlashMLA sparse with `fp8_ds_mla`. Before mixed-step support, this PR was up to 2.4x slower than main's row sharding on such steps at a 64K budget.
- B300 serving A/B with the #54951 protocol (GLM-5.3 NVFP4, TP4, concurrency 1, 256 output tokens, four fresh-process pairs): server TTFT **1.19x at 8K, 1.29x at 32K, 1.46x at 128K, 1.99x at 512K and 2.62x at 1M** (162.5 s -> 62.0 s); 1K-4K prompts (below the threshold) unchanged; generated tokens identical to main in 132/132 matched retrieval probes.
- No accuracy change on gsm8k (5-shot and ~10K-token 45-shot prompts) or long-context passkey retrieval.

## Validation

The performance and accuracy numbers below were measured before the restructure from ZJY0516/vllm#24 (exchanges around the regular `forward_mqa`, indexer chunked over each rank's tokens) and with the earlier 8192-token default threshold; they have not been re-run on the current head.

All numbers: GLM-5.3 NVFP4, TP4 on one GB200 tray (4 GPUs).

**TTFT** (real weights, `vllm serve` defaults plus `--max-model-len 524288`; `vllm bench serve` random prompts, 1 output token, concurrency 1, 3-8 prompts per length after a warmup; both servers on the same node, one after the other):

| prompt | ShardQ off | ShardQ on | |
|---|---|---|---|
| 4K (below the threshold, ShardQ inactive) | 191 ms | 233 ms | run-to-run noise |
| 8K | 203 ms | 232 ms | within noise |
| 16K | 327 ms | 294 ms | 1.11x |
| 32K | 634 ms | 511 ms | 1.24x |
| 64K | 1228 ms | 950 ms | 1.29x |
| 128K | 2546 ms | 1819 ms | 1.40x |

`--max-model-len 524288` is needed because the 1M default needs 46.6 GiB of KV cache per GPU at TP4, independent of this PR.

**Accuracy** (real weights, same server settings, greedy):

| eval | ShardQ off | ShardQ on |
|---|---|---|
| gsm8k 5-shot, concurrency 128 (short prompts take dense MHA; ShardQ inactive) | 0.9196 | 0.9196 |
| gsm8k 45-shot (~10K-token prompts), concurrency 1, 200 samples: every prefill goes through ShardQ | 0.930 | 0.925 |
| passkey retrieval, 8K-128K prompts, 15 prompts | 15/15 | 14/15 |

The one passkey miss is a near tie on the first answer token (the off run picks the key with p = 0.64); the off run has a similar near-tie detour at 32K that still contains the key. Confident tokens have matching logprobs.

- **Row sharding is effective at this size:** 2.41x over no sharding at 512K, unlike at the 16K chunks above.
- **The margin narrows with context:** both methods split the indexer, whose cost grows with context. ShardQ also splits the sparse attention, whose per-token cost is fixed by the top-k.
- **Checks:**
  - This PR with `sparse_mla_shard_q=false` measures 2429 / 3135 / 4645 / 11463 ms on a different node, within 0.7% of main with row sharding off.
  - Sample spread is at most 0.7%.
  - A 16K @ 128K reference case in the same runs gives 920 ms for main and 534 ms for this PR, consistent with the table above.
- **Setup:**
  - One process per arm.
  - The KV cache is capped with `--kv-cache-memory-bytes 64424509440` so the 64K-token graph fits.
  - Both trees include the FlashInfer sparse MLA fix from #64122. Without it, main's 65,536-token steps silently skip the attention kernel (see "Batch budget" below).
- **Mixed prefill + decode steps:** ShardQ now also covers them (see "Where it applies" and the mixed-step table below).

```bash
torchrun --nproc-per-node=4 -m vllm.entrypoints.cli.main bench forward \
  --model nvidia/GLM-5.3-NVFP4 -tp 4 --max-model-len 1048576 --max-num-batched-tokens 65536 \
  --kv-cache-memory-bytes 64424509440 --kv-len-jitter 0 --iters 5 --samples 3 \
  --case f64k=65536 --case c128k=65536@131072c --case c256k=65536@262144c \
  --case c512k=65536@524288c --case c1m=65536@1000000c --case ref16k_128k=16384@131072c
# row sharding off (on main): --attention-config.indexer_tp_shard_min_rows 1000000000
# this PR without ShardQ: --attention-config.sparse_mla_shard_q false
```

| 64K @ 512K c + 32 decodes | 4807 ms | 4821 ms | 4136 ms | 1.16x | 1.17x |

- **FlashInfer (default backend):** main's row sharding engages by default only for the 64K chunks.
  - Without mixed-step ShardQ, this PR measured 3154 ms and 11513 ms on the two 64K rows, up to 2.4x slower than main's row sharding.
  - The 32 decodes add about 9 ms per step; the same 16K @ 128K chunk alone takes 536 ms.

FlashMLA sparse with `--attention-backend FLASHMLA_SPARSE --kv-cache-dtype fp8_ds_mla`, same cases:

| step | main | this PR | vs main |
|---|---|---|---|
| 16K @ 128K c + 32 decodes | 1339 ms | 656 ms | 2.04x |
| 16K @ 512K c + 32 decodes | 3753 ms | 1263 ms | 2.97x |
| 64K @ 128K c + 32 decodes | fails | 2442 ms | |
| 64K @ 512K c + 32 decodes | fails | 4618 ms | |

- **Why main fails at 64K:** main's fp8 mixed-batch kernel takes all 65,568 tokens in one call, padded to 64 heads, and fails with `[FlashMLA] Stride exceeds int32 limit: 2417098752`. Under ShardQ each rank attends about a quarter of the prefill tokens, so this PR stays under the limit, but non-ShardQ configurations (TP1, DCP) still hit it.

**Mixed-step accuracy:** #54951's retrieval probe with mixed steps, real weights, TP4, ShardQ on vs `sparse_mla_shard_q=false`.
- **Setup:** 24 2K-token prompts and six 64K/128K-token prompts (needles at 10/50/90% depth) submitted together, so the long prompts' prefill chunks share steps with the short prompts' decodes. Greedy, 32 tokens, `--max-num-batched-tokens 16384 --max-num-seqs 32`.
- **Results:** strict answer 30/30 in both arms, and generated tokens identical in 30/30, for each of:
  - GLM-5.3 on FlashInfer
  - GLM-5.3 on FlashMLA sparse with `fp8_ds_mla`
  - GLM-5.3-Flash on FlashInfer

|---|---|---|---|---|
| fresh prefill 64K | 1173 ms | 1159 ms | 1030 ms | 1.13x |
| 64K @ 128K c | 1254 ms | 1181 ms | 1057 ms | 1.12x |
| 64K @ 256K c | 1407 ms | 1218 ms | 1099 ms | 1.11x |

- **The gain over row sharding is about 120 ms per step at every context length.** Only 11 of GLM-5.3-Flash's 45 layers are sparse MLA, and both methods split the k-pool indexer. ShardQ also splits the sparse attention, which costs about 150 ms per step regardless of context.
- **Setup:**
  - Row sharding off and on were measured in the same runs as each other. Row sharding on and this PR ran concurrently on the same node, and row sharding on repeated within 0.2% on a second node.
  - Sample spread is at most 0.15%.
  - The linear-attention state tensors are not paged, so the bench's per-case KV zeroing skipped them (local bench change, not in this PR).
- **Accuracy:** GLM-5.3-Flash (`zai-org/GLM-5.3-Flash@46a050b`, TP4, real weights) on #54951's retrieval probe:
  - Setup: 16K, 64K, 128K and 256K prompts with needles at 10/50/90% depth; greedy, 32 tokens, one request at a time; `--max-num-batched-tokens 16384`, so every prefill chunk takes ShardQ.
  - Strict answer: 12/12 with ShardQ and 12/12 with `sparse_mla_shard_q=false`.
  - Generated tokens are identical between the two in 12/12 prompts.
- **Not measured:** GLM-5.3-Flash end-to-end serving performance.

Improvement is `1 - PR/main` for latency and `PR/main - 1` for throughput. Throughput is input + output tokens over the wall time of the measured requests at concurrency 1, not saturated serving throughput. From 8K up, the four restart pairs agree to within ~0.5%, and every 95% interval excludes zero (details below). Below the 8192-token threshold ShardQ is inactive and TTFT stays within noise.

TPOT is 0.2-1.6% lower with this PR in every pair. ShardQ does not run on decode steps, and the cause of this small difference has not been investigated.

- Hardware and model: GLM-5.3 NVFP4 (`nvidia/GLM-5.3-NVFP4@e3b8f9f`), TP4 on 4x B300 in one node; torch 2.14.0+cu130, FlashInfer 0.7.2.post1 (matching cubin and jit-cache), Transformers 5.19.0.
- Arms: main at the merge base `ed1a730` and this PR at `c937e6f`. Both use identical compiled extensions from the official `ed1a730` wheel. A check of `/proc/<pid>/maps` confirmed that all six processes of every server loaded their own arm's source tree.
- Server: `vllm serve` defaults (FlashInfer sparse MLA backend, FP8 KV cache, default CUDA graphs) plus `--max-model-len 1048576 --max-num-batched-tokens 16384 --max-num-seqs 8 --gpu-memory-utilization 0.90 --no-enable-prefix-caching --enable-per-request-metrics`.
- Protocol, the same as #54951:
  - Runs: eight fresh server processes in ABBA/BAAB order (main, PR, PR, main, PR, main, main, PR), forming four adjacent restart pairs. Each process runs 3 excluded warmups and 8 measured requests per length.
  - Prompts: exact-token prompts from #54951's generator, the same in both arms. 1M means 1,000,000 input tokens.
  - Sampling: temperature 0, 256 output tokens with `ignore_eos`.
  - Server timings: TTFT runs from scheduling to the first token, and TPOT is the server's mean inter-token latency.
  - Aggregation: the per-process median, then the geometric mean over the four processes of each arm. 95% intervals resample the four restart pairs (20,000 bootstrap draws).
  - Measured requests: 352 main and 352 PR, every one with exactly 256 output tokens.
  - Only difference from #54951's client: the GLM-5.3 non-thinking boundary `<|assistant|><think></think>` in place of GLM-5.3-Flash's.
- **Batch budget:** #54951 used `--max-num-batched-tokens 65536`. On B300 with the default FlashInfer sparse MLA backend, main fails on 65,536-token prefill steps:
  - Every request of 64K or more logs `CUDA_ERROR_INVALID_VALUE` at `flashinfer/trtllm/fmha/fmhaKernels.cuh:478`, about 312 times per request.
  - Those requests return garbage, with 0/15 retrieval correct from 64K to 1M.

  This run therefore uses GLM-5.3's default budget of 16,384. At that budget, main's indexer row sharding, which this PR removes, never engages, so the baseline is main's default path. Both arms logged zero CUDA errors while serving.

## Details

**How it works.** Under TP every rank holds `H / tp` heads, so each rank runs the indexer over all prefill tokens, and the sparse attention kernel processes all tokens for its few heads. ShardQ instead gives each rank a slice of the step's tokens:

1. Tokens split zigzag: each request cuts into `2 * tp` chunks, and rank `r` owns chunks `r` and `2 * tp - 1 - r`, which balances the causal indexer cost.
2. The indexer scores only this rank's tokens and writes their top-k compactly, after the decode tokens' top-k, to the shared top-k buffer.
3. An all-to-all moves the MQA query from `[T, H / tp, D]` to `[T / tp, H, D]`; the sparse attention kernel attends all heads over the replicated KV cache.
4. A second all-to-all restores `[T, H / tp, 512]` for the `W_UV` projection.

The exchanges sit around the regular `forward_mqa` call, next to DCP's `query_gather` and combine; there is no ShardQ-specific attention entry point. They push tokens directly into peers' symmetric-memory buffers with one Triton kernel, falling back to NCCL `all_to_all_single` when the TP group has no symmetric memory. The fp8 query of the FlashInfer backend is exchanged as is.

**Where it applies.**
- Steps with at least `sparse_mla_shard_q_min_tokens` tokens after the decodes, one of whose requests is longer than the top-k; shorter prefills already take dense MHA.
- Mixed prefill + decode steps:
  - Only the tokens after the decodes are split. Decodes here are requests of at most `1 + num_speculative_tokens` tokens, and stay head-sharded.
  - The indexer scores every decode token in place, then this rank's tokens compactly after them, so tokens that the indexer treats as prefill but MLA treats as decode stay consistent.
  - The attention layer calls `forward_mqa` twice: once for the decode tokens with the step's metadata, once for this rank's tokens with ShardQ's narrowed metadata (`ShardQMetadata.attn_metadata`, which reads the top-k from `topk_start`). FlashMLA's token-sharded call uses its own lazily initialized scheduler metadata.
  - The decode output is written in place before the restored tokens rather than concatenated.
- The indexer metadata builder chunks only the decode tokens and this rank's tokens (`shardq_gather_indices`), each at its own position, so it makes fewer, fuller launches.
- TP > 1, no DCP/PCP/HiSparse, and no FULL CUDA graphs for mixed batches.
- Backends opt in with `SparseMLACommonImpl.supports_shardq`: FlashInfer sparse MLA and FlashMLA sparse (fp8 mixed-batch path).
- Models mark eligible layers with `MLAAttention(shardq_eligible=...)`: DeepSeek-V3.2 / GLM-5.3 and GLM-5.3-Flash (NVIDIA k-pool indexer) do. Other sparse MLA models keep the head-sharded path.
- The sparse MLA and indexer metadata builders both call `build_shardq_split` and, like every TP rank, derive the same split from the same batch.
- MTP layers are not eligible, including GLM-5.3-Flash's: draft steps reuse each token slot's top-k.

**Config.** New `AttentionConfig` fields `sparse_mla_shard_q` (default `True`) and `sparse_mla_shard_q_min_tokens` (default 1024). `indexer_tp_shard_min_rows` is deprecated, has no effect, and is removed in v0.34.0.

**Tradeoffs and limitations.**
- Memory: the exchange buffers (above) come out of the KV cache budget.
- GLM-5.3-Flash's k-pool indexer, which #54951 row-sharded, now follows the ShardQ split instead. Its MTP layers no longer shard the indexer.

**Not duplicating existing work.** No open PR implements token-sharded sparse-MLA prefill. #54394 and #56944 shard only the indexer rows (like the removed `PrefillRowShard`) and keep attention head-sharded.
