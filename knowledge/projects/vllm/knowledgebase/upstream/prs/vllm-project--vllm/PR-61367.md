# [Bugfix] Fix wrong output when MoE ops are in splitting_ops under PIECEWISE CUDA graphs

[Upstream PR](https://github.com/vllm-project/vllm/pull/61367) · state: open · merged: False

## Original PR description

## Overview

Fixes #61150. With `vllm::moe_forward` or `vllm::moe_forward_shared` in `splitting_ops` under PIECEWISE CUDA graphs, decode output turns to garbage after the first token (` Par Par Par ...`). With `VLLM_LOGGING_LEVEL=DEBUG`, the `CUDAGraphWrapper` replay address check fails. This PR makes the split MoE op write into an output buffer that is allocated in the captured piece before it, the same way attention works. The piece after the op then reads a fixed address on replay.

Compared with #61179, this fix:

- Keeps the user's `splitting_ops` as written. [61179](https://github.com/vllm-project/vllm/pull/61179) renames the MoE ops in it to new ops, so the existing `test_moe_splitting_ops_deepep_ht_inductor_partition` fails on [61179](https://github.com/vllm-project/vllm/pull/61179) unless the test is edited. That test passes here unchanged.
- Is much smaller outside `tests/`: +47/-9 in `moe_runner.py` only, with no new ops. [61179](https://github.com/vllm-project/vllm/pull/61179) adds about 180 lines across `moe_runner.py` and `compilation.py`, including two new registered ops.
- Tests all three broken paths: `moe_forward` with the FX split, `moe_forward` with Inductor graph partition, and `moe_forward_shared`. The GPU test in [61179](https://github.com/vllm-project/vllm/pull/61179) covers only `moe_forward` with the FX split.

## Claims

- With the MoE ops in `splitting_ops` under PIECEWISE, output now matches the default split and eager. Before, it was garbage after the first token.
- The DEBUG replay input-address assertion no longer fires.
- `moe_forward_shared` and the Inductor graph partition path had the same bug, and the same change fixes them.
- When the MoE op is not in `splitting_ops` (the default), the bare op is still called, with no extra buffer or copy.

## Details

Root cause: when a MoE op is a splitting op, it runs eagerly between two captured pieces. It returns a tensor that the MoE kernel allocates fresh on every call. That tensor comes from the caching allocator, not from the graph pool. `CUDAGraphWrapper` does not copy inputs into static buffers, so the next piece reads its input from the address it had at capture time. On replay the op returns a tensor at a new address, and the piece reads freed or reused memory. Debug prints confirmed this. At capture, `moe_forward` returned one address, and the next piece (`submod_4`) recorded it as its input. At replay, `moe_forward` returned another address, and the replay check reported that address for `submod_4`. The MoE input address did not change. Attention does not have this problem: its output buffer is allocated in traced code, and the op writes into it. `breakable_cudagraph.py` states the same rule for eager segments.

Fix (only `vllm/model_executor/layers/fused_moe/runner/moe_runner.py`):

- `moe_forward` gets an optional `output` argument. `moe_forward_shared` gets optional `shared_output` and `fused_output` arguments. All are declared in `mutates_args`. When they are given, the op copies its result into them.
- `MoERunner._select_forward` checks whether the op is in `compilation_config.splitting_ops`, with or without `.default`, like `should_split`. If it is, the runner calls a small wrapper. The wrapper allocates the buffers in traced code with the op's own fake function and passes them to the op. The buffer then lives in the captured piece before the op, so its address stays fixed for each batch size.
- Otherwise the bare op is called as before. The TPU and CPU paths are unchanged.
- The change is in the MoE layer, not in a model runner, so both runners get it. The reproducer ran on V1. The new tests and the regression checks ran on V2.

Tradeoffs and limits:

- With the MoE op split, each MoE layer does one extra allocation and one device-to-device copy of its output.
- `moe_forward_shared` now declares `mutates_args`, so on the default path it goes through `auto_functionalized`. Output is the same as before, bit for bit, but I did not measure default-path throughput.
- The Inductor partition path for `moe_forward_shared` uses the same code but has no test. In that config the shared test saw no `CUDAGraphWrapper` capture or replay, so the address check could not catch anything.
- I did not run a shared-experts model with real weights. That path is checked only by the dummy-weight test.
- `vllm::transformers_moe_forward` (Transformers backend) also returns a fresh tensor. If a user adds it to `splitting_ops` under PIECEWISE, output is still garbage with this PR (0/10). It is a separate op and is not changed here.
- `test_moe_forward_as_splitting_op[False]` prints a `UserWarning` for one prompt at token 25, and `check_logprobs_close` accepts it. The same change appears with no graph replay at all (capture sizes `[1]`), so it comes from where the graph is cut, not from this bug.
- The older comment above `_moe_forward` says these functions only pass control along. It is now slightly out of date, because they also copy into the given buffers.
