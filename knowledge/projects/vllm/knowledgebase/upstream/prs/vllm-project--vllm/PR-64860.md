# [Bugfix][NIXL] Fix bidirectional P-side hang after the first D->P pull

[Upstream PR](https://github.com/vllm-project/vllm/pull/64860) · state: open · merged: False

## Original PR description



## Overview

With `bidirectional_kv_xfer`, a turn-2 request on the prefill node that goes back through the connector lookup after its first D->P pull waits in `WAITING_FOR_REMOTE_KVS` forever and keeps its blocks. This makes that second lookup prefill locally.

Fixes #64859

## Claims

- After its first pull attempt, a P-side turn-2 request prefills locally instead of waiting for a read that is never issued.
- Both ways back into the lookup are covered: a failed pull under `kv_load_failure_policy=recompute`, and preemption after a successful pull with the pulled blocks evicted (default `fail` policy).
- The first pull, and a request that keeps its pulled blocks, don't change.

## Validation

One fails the D->P read under `recompute`; the other preempts the request after a successful pull and calls `reset_prefix_cache()` to stand in for eviction. Each runs the request to completion and checks that the scheduler is empty.

## Details

The flow, P = prefill node, D = decode node:

1. Turn 2 reaches P with `do_remote_decode` and D's `remote_block_ids`. The lookup offers D's tokens, and `update_state_after_alloc` registers the D->P read and sets `_remote_blocks_processed`.
2. The read fails under `recompute` (for example, P declines it because D's blocks are close to their TTL), or the request is preempted after the pull and its blocks are evicted. Either way it goes back through the lookup.
3. On main the lookup offers the load again ([pull_scheduler.py#L67-L103](https://github.com/vllm-project/vllm/blob/a20280f30e3169d33a7e21d1d117e9719bace00b/vllm/distributed/kv_transfer/kv_connector/v1/nixl/pull_scheduler.py#L67-L103)), but a read is registered only while the flag is unset ([#L130-L134](https://github.com/vllm-project/vllm/blob/a20280f30e3169d33a7e21d1d117e9719bace00b/vllm/distributed/kv_transfer/kv_connector/v1/nixl/pull_scheduler.py#L130-L134)). The request waits for a `finished_recving` that never comes, and an abort doesn't free its blocks, because the free waits for it too.
4. With this change the lookup checks the same flag and returns 0, so the request prefills locally, as the D side already does after one attempt.

Pulling again would not be safe after a successful pull: the first read's completion notification lets D free those blocks.

Not a duplicate: #59872 reports, and #59874 and #61238 address, D-side reads that were issued and stall; here no read is registered. #47021 (merged) added the turn-2 expiry decline, one way into step 2; it doesn't change the lookup. No open PR adds this check; the open PRs that touch `pull_scheduler.py` change other parts of it.
