# [Bugfix][CPU] Default Triton to the CPU backend

[Upstream PR](https://github.com/vllm-project/vllm/pull/63366) · state: open · merged: False

## Original PR description

## Overview

Fixes #62484. CPU engine configuration now defaults Triton to its CPU backend, so a visible NVIDIA driver does not cause CPU inference to enter CUDA-only PyTorch APIs.

## Claims

- CPU inference works with the NVIDIA driver visible and `TRITON_DEFAULT_BACKEND` unset.
- Explicit `TRITON_DEFAULT_BACKEND` values are preserved.
- Greedy generation matches the existing `TRITON_DEFAULT_BACKEND=cpu` workaround exactly on the tested model and prompts.

## Validation

Ubuntu 24.04 / WSL2, Intel Core i5-14600KF (AVX2), NVIDIA RTX 4060 Ti visible, Python 3.12.3, PyTorch 2.14.0+cpu and Triton 3.8.0+cpu. The baseline used Python source from `4bceda5dbf26`; the final confirmation used `3ed2d10cd433`. Both used the same precompiled native artifacts from CPU nightly `0.32.1rc1.dev361+g83c078d95.cpu`; the native extensions were not rebuilt.

| Check | Base + regression test | This change |
| --- | --- | --- |
| New `LLM` regression, `facebook/opt-125m`, FP32, eager, 2 prompts, greedy, up to 8 tokens each | Fails: `Torch not compiled with CUDA enabled` | Passes; default and explicit CPU runs have identical token IDs and text |
| CPU platform and Triton utility suites | Not rerun on base | 28 passed |
| Relevant pre-commit hooks, including Ruff, mypy, Markdown lint and CI test tethering | Not rerun on base | Passed |

The model snapshot was `27dcfa74d334bc871f3234de431e71c6eeba5dd6`. This is a generation equivalence check, not a model-quality or performance benchmark.

The warning concerns the unavailable source-checkout `_version` module. The test durations include process startup and slow imports from a Windows-mounted checkout; they are not inference timings.

## Details

Triton CPU's driver selection prefers an active GPU unless a backend is explicitly selected. vLLM correctly selects `CpuPlatform` for a CPU build, but did not pass that choice to Triton. Set the default in `CpuPlatform.check_and_update_config`, before engine workers initialize Triton. No common GPU path or kernel is changed.

The regression extends the existing language-generation suite and uses real `vllm_runner` instances and weights. It is selected by the existing CPU language-generation Buildkite job (`cpu_model`); that job already tracks both changed Python paths. Reproducing the original failure also requires a visible NVIDIA driver, which ordinary CPU-only CI may lack; the before/after run above covers that condition locally.

Duplicate checks: #62511 references this issue but changes AVX-512 test eligibility, not runtime backend selection. #61564 addresses XPU platform detection and honors an already-specified Triton backend; it does not establish the CPU default. #60705 and #59860 change separate CPU kernels. No open PR implementing this CPU default was found. Another contributor expressed interest on the issue, but had not linked a fix when checked.

The CPU installation page documents the default, explicit overrides, and the WSL2/NVIDIA case.
