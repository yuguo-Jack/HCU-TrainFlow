# [Bugfix] Include multimodal limits in the model compile-cache hash

[Upstream PR](https://github.com/vllm-project/vllm/pull/54642) · state: closed · merged: True

## Original PR description

## Problem Description:

If we start VLLM_CACHE_ROOT first with vision enabled, next time, if vision is disabled, because the currently way of hashing kernel cache miss the multimodal config, the start will run into compilation error. 


## Reproduction

On `main` (nightly `0.32.1rc1.dev80+gaa3564cee`, torch 2.14.0+cu130), Qwen2.5-VL-3B-Instruct,
one H100. The cache must be primed by a multimodal start first — a cold start in text-only mode
compiles fresh and succeeds, which is why this is easy to miss.

Verified in Qwen, Gemma (E4B) model for this issue. 

```bash
MODEL=Qwen/Qwen2.5-VL-3B-Instruct

# step 1: normal multimodal start, then stop the server
VLLM_CACHE_ROOT=/tmp/cache vllm serve $MODEL --max-model-len 4096 --gpu-memory-utilization 0.8 --port 9256

# step 2: restart text-only, same VLLM_CACHE_ROOT, everything else identical
VLLM_CACHE_ROOT=/tmp/cache vllm serve $MODEL --max-model-len 4096 --gpu-memory-utilization 0.8 --port 9256 \
    --limit-mm-per-prompt '{"image":0,"video":0}'
```

## Fix

Extend the existing `if self.multimodal_config:` block with the two remaining switches that decide
whether the MM code path runs.

## Test Plan

- Unit test: Adding: New regression tests in `tests/config/test_multimodal_config.py`:
  `test_zero_mm_limits_affect_model_hash`, `test_enable_mm_embeds_affects_model_hash`. Both fail on
  base (the two `compute_hash()` results are identical) and pass with the change.
- E2E Test: End-to-end `vllm serve` reproduction above, plus `lm_eval` and `vllm bench serve` on both arms —
  raw logs in the review thread. Greedy decoding at one request at a time is byte-identical
  between `main` and this patch in both multimodal and text-only mode, as expected for a change
  that only adds entries to a hash computed once at startup.

Verified locally on head 6b78409 (CPU env):

**Regression proven.** The 2 new tests FAIL on base d61b6e18 (both `compute_hash()` results identical — the limits/embeds factors are absent) and PASS on head. Full `tests/config/test_multimodal_config.py` on head: 48 passed (46 pre-existing + 2 new; the pre-existing `test_language_model_only_affects_model_hash` also passes).

**Hash logic matches the runtime switch exactly.** I checked `MultiModalRegistry.supports_multimodal_inputs` (registry.py:103): the MM code path is disabled (text-only, `input_ids` with `inputs_embeds=None`) precisely when `all(get_limit_per_prompt(m) == 0 for m in info.supported_mm_limits)` — and `enable_mm_embeds=True` keeps the MM infrastructure alive. Both factors are now in the compile-cache key, so a compiled artifact traced for one graph can never be reused for the other. `language_model_only` was already covered; this closes the remaining graph-affecting switches.

**Safety of `opts.count`:** `_validate_limit_per_prompt` (multimodal.py:267) normalizes every entry (int → `{"count": v}`, then `*DummyOptions(**v)`), so every value is a DummyOptions instance with `count: int = Field(999, ge=0)` — `opts.count` can never raise AttributeError. The `isinstance(opts, int)` branch is defensive/dead post-validation, which is fine.

**Direction check (no false negatives):** a text-only flip requires every supported modality to carry an explicit 0 entry in `limit_per_prompt`, and those entries are exactly what gets hashed — so any graph-changing config always produces a distinct hash. Limits on modalities the model does not support only cause conservative extra cache misses (hash differs while the graph is identical) — harmless, just slightly less cache sharing.

One non-blocking nit: the factor includes limits for all modalities, not just `supported_mm_limits` — filtering to supported modalities would preserve cache hits for irrelevant-limit configs, but the current choice errs on the safe side. Approve.
