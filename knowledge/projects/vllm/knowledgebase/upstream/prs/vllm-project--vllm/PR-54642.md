# [Bugfix] Include multimodal limits in the model compile-cache hash

[Upstream PR](https://github.com/vllm-project/vllm/pull/54642) · state: open · merged: False

## Original PR description

## Purpose

`ModelConfig.compute_hash()` keys the torch.compile / AOT compilation cache. It already accounts
for `language_model_only`, with this note:

```python
# NOTE: For some models (e.g, Qwen3-VL), whether the MM code path is enabled
# affects the computation graph of the language model, therefore we add it
# here early.
if self.multimodal_config:
    factors["language_model_only"] = self.multimodal_config.language_model_only
```

The problem is that `language_model_only` is not the only switch that disables the MM code path,
and vLLM says so itself — in `MultiModalConfig`:

```python
language_model_only: bool = False
"""If True, disables all multimodal inputs by setting all modality limits to 0.
Equivalent to setting `--limit-mm-per-prompt` to 0 for every modality."""
```

So two configurations are documented as **equivalent**, but only one of them takes part in the
hash: `limit_mm_per_prompt` is listed in `ignored_factors`, and `enable_mm_embeds` is absent too.
Both feed `ModelConfig._supports_multimodal_inputs()`, which falls back to text-only mode when
every supported modality is limited to 0 (unless `enable_mm_embeds` is set).

That matters because the two modes call the model with different arguments.
`GPUModelRunner._dummy_run()` takes the `_prepare_mm_inputs()` path on multimodal (passing
`inputs_embeds`, and `input_ids=None` unless the model sets `requires_raw_input_tokens`), and the
plain `input_ids` path with `inputs_embeds=None` in text-only mode. Those are structurally
different graphs and must not share a compile-cache entry.

Running a multimodal model text-only is documented usage
(`docs/configuration/conserving_memory.md`):

```python
# You can even run a multi-modal model for text-only inference:
llm = LLM(model="google/gemma-3-27b-it", limit_mm_per_prompt={"image": 0})
```

## Reproduction

Serve a multimodal model normally, then restart it with every modality limit set to 0 **under
otherwise-identical flags**:

```

                    running in text-only mode.
INFO [decorators.py:312] Directly load AOT compilation from path
     .../torch_aot_compile/22ed387f93b431f5.../rank_0_0/model
```

> **Note for reviewers:** the cache entry must first be **primed by a multimodal run under
> identical flags**. Starting straight into text-only mode on a machine with no prior cache entry
> compiles fresh and succeeds, which hides the bug.

* **B vs C** — identical configuration; the only difference is whether the cached artifact is

  Note C computes the *same* key as A: without this patch the two modes are indistinguishable to
  the cache, and C only survives because there was no artifact to load.
* **D2 vs B** — with the patch the two modes hash differently, so text-only no longer resolves to
  the multimodal artifact, and the server starts.

At the config layer on current `main`, the three relevant configurations collide while the mode
they select differs:

|---|---|---|---|
| default | True | `84e9fd8586284e12` | `5fb3b4c1e1558b85` |

| all limits 0 + `enable_mm_embeds` | True | `84e9fd8586284e12` | `8c3ca71ae836089d` |

## Not fixed by anything else on main

Between `v0.31.0` and `81f7c69577` the only change to the compile-cache key is the new
`factors["video_pruning"]`, which does not help here — setting the modality limits to 0 does not
change `is_multimodal_pruning_enabled()`. The `_dummy_run()` multimodal/text-only branch is
unchanged, and the AOT loader still uses a hash-matched artifact without validating it against
the traced signature (the new per-module `use_aot_compile` flag is only set by the Transformers
backend). `limit_mm_per_prompt` is still listed in `ignored_factors`, and `enable_mm_embeds` is
still absent from the factors.

## Not model-specific

The hash collision is config-layer and reproduces across models and versions
(`ModelConfig(...).compute_hash()`, with and without `limit_mm_per_prompt={"image": 0, ...}`):

| model | vLLM 0.27.1 | vLLM 0.28.0 | vLLM 0.31.0 | `main` 81f7c69577 |
|---|---|---|---|---|
| `llava-hf/llava-1.5-7b-hf` | collides | – | – | – |
| `Qwen/Qwen2.5-VL-3B-Instruct` | collides | collides (crash reproduced) | collides (crash reproduced) | collides (crash reproduced) |
| `google/gemma-3-4b-it` | collides | – | – | – |
| `nvidia/Gemma-4-26B-A4B-NVFP4` | – | collides (crash first seen here) | – | – |

The crash was observed on three independent stacks: Qwen2.5-VL-3B / BF16 / H100 (sm_90) on both
0.28.0 and 0.31.0 + `main`, and Gemma-4-26B-A4B / NVFP4 / RTX PRO 6000 Blackwell (sm_120).

## Fix

Extend the existing `if self.multimodal_config:` block with the two remaining switches that decide
whether the MM code path runs.

Only the per-modality `count` is hashed: it is what decides whether a modality is disabled, the
other dummy-data options (e.g. image width/height) only shape profiling inputs, and `count` keeps
the factors JSON-serializable — `hash_factors()` uses `json.dumps` while `limit_per_prompt` values
are `BaseDummyOptions` dataclasses (hashing the objects directly raises
`TypeError: Object of type AudioDummyOptions is not JSON serializable`).

## Test Plan

- New regression tests in `tests/config/test_multimodal_config.py`:
  `test_zero_mm_limits_affect_model_hash`, `test_enable_mm_embeds_affects_model_hash`.
- The existing `test_language_model_only_does_not_affect_mm_hash` still passes: this change is in
  `ModelConfig.compute_hash()`, not `MultiModalConfig.compute_hash()`, so the ViT-scoped hash is
  deliberately left untouched.
- End-to-end matrices above, on `main` and on 0.31.0.

## Note on cache invalidation

This changes the compile-cache key for multimodal models, so the first start after upgrading
recompiles once. Text-only models are unaffected — the block is guarded by `if self.multimodal_config`.

**Regression proven.** The 2 new tests FAIL on base d61b6e18 (both `compute_hash()` results identical — the limits/embeds factors are absent) and PASS on head. Full `tests/config/test_multimodal_config.py` on head: 48 passed (46 pre-existing + 2 new; the pre-existing `test_language_model_only_affects_model_hash` also passes).

**Hash logic matches the runtime switch exactly.** I checked `MultiModalRegistry.supports_multimodal_inputs` (registry.py:103): the MM code path is disabled (text-only, `input_ids` with `inputs_embeds=None`) precisely when `all(get_limit_per_prompt(m) == 0 for m in info.supported_mm_limits)` — and `enable_mm_embeds=True` keeps the MM infrastructure alive. Both factors are now in the compile-cache key, so a compiled artifact traced for one graph can never be reused for the other. `language_model_only` was already covered; this closes the remaining graph-affecting switches.

**Safety of `opts.count`:** `_validate_limit_per_prompt` (multimodal.py:267) normalizes every entry (int → `{"count": v}`, then `*DummyOptions(**v)`), so every value is a DummyOptions instance with `count: int = Field(999, ge=0)` — `opts.count` can never raise AttributeError. The `isinstance(opts, int)` branch is defensive/dead post-validation, which is fine.

**Direction check (no false negatives):** a text-only flip requires every supported modality to carry an explicit 0 entry in `limit_per_prompt`, and those entries are exactly what gets hashed — so any graph-changing config always produces a distinct hash. Limits on modalities the model does not support only cause conservative extra cache misses (hash differs while the graph is identical) — harmless, just slightly less cache sharing.

One non-blocking nit: the factor includes limits for all modalities, not just `supported_mm_limits` — filtering to supported modalities would preserve cache hits for irrelevant-limit configs, but the current choice errs on the safe side. Approve.
