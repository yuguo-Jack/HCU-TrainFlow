## Overview

Pass allocator-produced axis semantics alongside KV tensors at connector registration. This distinguishes `[B, 2, H, 1, N, D]` from `[2, B, H, 1, N, D]` even when `B == 2` and shape and strides are identical.

Related: #42082, [RBLN producer PoC](https://github.com/RBLN-SW/vllm-rbln/pull/1297), [LMCache#5866](https://github.com/LMCache/LMCache/issues/5866).

## Claims

- `create_kv_cache_views` declares `[BLOCK, HEAD, STATE, CONTENT]` when it creates each standard view. Both GPU model runners forward those declarations, including shared-layer aliases; HiSparse host views use the same view creator. Raw storage remains unspecified.
- `MultiConnector` forwards descriptors to each child. Existing connectors inherit a default that validates metadata and calls their tensor-only registration hook.
- Custom allocators can declare separate KV and singleton axes. Actual tensor shape, strides, dtype and storage offset remain authoritative for addressing; axis roles do not imply identical hybrid-cache formats.

## Details

Axis declarations are generated alongside actual view creation, rather than inferred later by `KVCacheConfig`. Allocators accept an optional fresh `tensor_layouts` output dictionary, preserving existing return types and tensor-only callers. Both runners propagate it to registration and copy descriptors for shared views.

This complements #42082: `KVCacheLayout` describes physical stride order, while the descriptor describes the registered view before attention-private kernel-block mappings. `STATE` follows the cache spec's token granularity; `CONTENT` stays opaque. Packing, encoding, tuple/multi-plane descriptors and external transport schemas remain follow-up work. MRV1 uses the same compatibility hook so existing deployments receive the same contract as MRV2.

RBLN is a concrete downstream user of this API: [vllm-rbln#1297](https://github.com/RBLN-SW/vllm-rbln/pull/1297) declares axes where its custom attention cache shape is chosen, then passes them with the registered per-layer tensors through `register_kv_caches_with_layouts`. Its `[B, 2, H, 1, N, D]` view declares `(BLOCK, KV, HEAD, SINGLETON, STATE, HEAD_DIM)`; the `[2, B, H, 1, N, D]` view swaps the first two roles. RBLN does not need to use the standard BHNC allocator to use this registration hook. The downstream draft depends on this upstream API merging and becoming available in its supported vLLM dependency; it is not a prerequisite for this PR. RBLN hardware validation and the LMCache consumer remain downstream work.

Duplicate checks found no existing registration-axis API. #42374 standardizes allocation; #62107 changes FlashInfer's physical K/V placement. Neither carries these per-view axis declarations to connectors.
