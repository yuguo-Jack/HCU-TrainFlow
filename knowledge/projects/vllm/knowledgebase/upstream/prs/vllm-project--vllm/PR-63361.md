## Overview

Successive chat turns often resend a long conversation with only a small addition. This PR avoids tokenizing the unchanged text again by retaining the previous rendered prompt and token IDs for each session. Clients continue to send complete requests; an agent hint—the existing `session_id` field—selects the previous prompt to compare, and text comparison determines what can be reused. See [RFC #63359](https://github.com/vllm-project/vllm/issues/63359).

## Claims

- Opt-in reuse of tokenized text across session turns, with a configurable CPU memory budget; disabled by default.
- In a synthetic replay of growing chat histories, frontend CPU time per request decreased **25.1%** and mean time to first output decreased **19.7%** across four pairs of runs. End-to-end request latency decreased about **1.0%**. Short independent requests did not show a consistent benefit.

## Validation

Qwen3-0.6B on an RTX 3090, FP16, four concurrent clients, with prefix caching, chunked prefill and CUDA graphs enabled. For each workload, each configuration is tested in four fresh-server runs of 80 requests. The memory budget for cached text and token IDs is 512 MiB.

| Metric | Baseline | Token reuse | Result |
|---|---:|---:|---|
| Growing histories: frontend CPU time/request | 389.5 CPU-ms | 291.7 CPU-ms | −25.1% |
| Growing histories: mean time to first output | 641.1 ms | 515.3 ms | −19.7%; individual runs −27.0% to −2.2% |
| Growing histories: mean end-to-end latency | 8.391 s | 8.306 s | approximately −1.0% |
| Independent requests: mean time to first output | 99.7 ms | 98.0 ms | individual runs −9.5% to +10.9% |
| Independent requests: P95 time to first output | 133.9 ms | 137.1 ms | tail latency increased |

Growing histories contain 16K–35K input tokens and generate 448 tokens; independent requests contain 512/1024/2048 input tokens and generate 64 tokens. Time to first output is measured at the client, from request start to the first non-empty streamed output chunk. CPU time/request is the CPU time used by the API server process divided by request count. Percentages average the relative changes between matched baseline and reuse runs; P95 values average the four run P95s.

Clients send their next request when the previous response finishes. Latency gains varied substantially between runs and should not be assumed for other arrival patterns. Reported prefix-cache hit token counts matched request by request between configurations.

Validation performed by the author: **371 CPU tests**, applicable pre-commit checks, and **36 requests to running Qwen3 and Llama servers** with reuse enabled and disabled.

The performance results above were measured before the latest commit, [04d5f00e8](https://github.com/RichealYoung/vllm/commit/04d5f00e8bf6836c3a4ead37e9ec7dc04ec68ee8), and were not rerun. That commit only lowers the cost of memory accounting; in a CPU component measurement, prefix-hit encoding took about 0.8 ms less per request.

## Details

### How it works

After applying the chat template, compare the prompt with the previous prompt in the same session. Reuse cached token IDs up to a safe tokenizer boundary within their common prefix, and tokenize only the remaining suffix. To locate it, scan backward for an added token (such as a chat delimiter) whose matching rules allow independent tokenization on either side, then verify its position against the cached token IDs. If no safe boundary exists, use normal tokenization.

### Usage and limits

Enable with `--session-token-cache-mb <MiB>` and send the existing `session_id` field or `X-Session-ID` header. Each renderer stores one previous prompt for each session and `cache_salt` value.

<details>
<summary>Usage example and tokenizer compatibility</summary>

Start a server with a 32 MiB budget for cached text and token IDs per renderer:

```bash
vllm serve Qwen/Qwen3-0.6B \
  --tokenizer-revision c1899de289a04d12100db370d81485cdf75e47ca \
  --session-token-cache-mb 32
```

Send the same session ID with successive complete chat histories:

```json
{
  "model": "Qwen/Qwen3-0.6B",
  "session_id": "conversation-123",
  "messages": [
    {"role": "user", "content": "..."},
    {"role": "assistant", "content": "..."},
    {"role": "user", "content": "..."}
  ]
}
```

The default budget is zero, which disables reuse. Tested library combinations are Transformers 5.16.1, 5.17.0, 5.18.0, 5.19.0, 5.20.0, 5.20.1 or 5.20.2 with tokenizers 0.23.2 or 0.23.3. The tokenizer backend configuration and encoding implementation must also match a supported configuration; a library version or model name alone is insufficient. The feature documentation in this PR lists the tested tokenizers and revisions. Requests containing media use normal tokenization.

</details>

The history memory limit covers stored entries, space reserved for pending entries, and entries still in use; it does not cap total process memory. Cancellation, failures and resets prevent incomplete or outdated entries from being cached.

Short prompts, frequent edits, conversations that branch from earlier turns, and requests routed between processes can reduce reuse or make its overhead outweigh the savings.

Related frontend work: [#47583](https://github.com/vllm-project/vllm/pull/47583), [#45514](https://github.com/vllm-project/vllm/pull/45514), [#61335](https://github.com/vllm-project/vllm/pull/61335). The agent hint selects one previous prompt from the same session for comparison.
