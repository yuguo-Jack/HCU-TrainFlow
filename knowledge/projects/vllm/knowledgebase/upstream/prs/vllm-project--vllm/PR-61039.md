# [Perf][DSv4.1] Length-aware candidate block selection in the decode indexer

[Upstream PR](https://github.com/vllm-project/vllm/pull/61039) · state: open · merged: False

## Original PR description

## Purpose

DeepSeek-V4.1's decode indexer writes its logits into a `[rows, max_model_len]` buffer, a width that must stay static for CUDA graphs (1M with the default `max_model_len`). Each row only holds its own context, but `select_candidate_blocks` scored every block of the full width and then ran `torch.topk(2048)` over all of them. At 1M that costs about 850 us per decode step, whatever the actual context length. This PR makes candidate selection length-aware.

- **Score only valid blocks.** `_block_scores_kernel` now runs a fixed `(rows, 32)` grid that walks each row's tiles only up to the row's end, and it writes each row's valid block count.
- **DeepSelect instead of `torch.topk`.** On the DeepSelect path, the block count is passed as DeepSelect's per-row `end`. Short rows are padded with -1. Candidate order does not matter, because the sparse expansion sorts. The full-width `torch.topk` path stays as the fallback for no DeepSelect, non-contiguous output, `topk > 4096` and narrow logits, and its behaviour is unchanged.
- **NaN rows.** DeepSelect leaves NaN rows only partly written, which can happen during warmup or capture on an uninitialized KV cache. On the DeepSelect path, NaN blocks are pinned like the newest block, as `torch.topk` ranks NaN first. NaN rows therefore still get complete, in-range candidates.
- **bf16 decode logits.** The decode indexer now asks DeepGEMM for bf16 logits when the top-k backend is `deep_select` and DCP is off. This halves the bytes that the top-k and candidate passes read. The logits kernel still accumulates in fp32 and only rounds the output, which is byte-identical to `bf16(fp32 logits)`. The other top-k backends and the DCP merge still get fp32.
- **Footprint.** `candidate_blocks.py`, the decode call in `sparse_attn_indexer.py`, and a `logits_dtype` passthrough on `fp8_fp4_paged_mqa_logits` (default fp32). The DeepSelect availability check reuses `has_deep_select()`.

## Kernel microbenchmark

`select_candidate_blocks` alone, DeepSeek-V4.1-Flash decode shapes: 384 rows (64 requests x 6 tokens), logits width 1,048,576 (default `max_model_len`, ratio-1 candidate-source layer), 2048 candidate blocks of 8. 1 x GB300, FlashInfer CUPTI timing with CUDA graph replay and cold L2, median. Logits are continuous random values; random FP4 inputs give heavily tied logits, which is pathological for radix selection and does not match the model.

| context (tokens) | main, fp32 logits (us) | this PR, fp32 logits (us) | this PR, bf16 logits (us) | speedup (bf16 vs main) |
|---:|---:|---:|---:|---:|
| 131,072 | 847.8 | 77.0 | 42.9 | 19.8x |
| 176,000 | 861.2 | 116.8 | 62.2 | 13.8x |
| 400,000 | 884.0 | 205.9 | 119.9 | 7.4x |
| 1,048,576 | 939.0 | 408.2 | 254.9 | 3.7x |

main's cost is flat because it always scores and sorts the full width. This PR scales with the context and is still faster at the full 1M.

The dense indexer top-k reads the same logits, so the bf16 switch also speeds it up. DeepSelect top-512 at 131K context, ratio-2 layer (65K keys) / ratio-1 layer (131K keys): fp32 42.2 / 62.7 us, bf16 28.8 / 45.4 us. The logits kernel itself takes the same time with fp32 and bf16 output (93.0 vs 94.2 us, 180.6 vs 181.5 us).

Also checked locally, without adding tests:
- Against the previous implementation, on 384-row decode inputs (1M width, random ends, `row_repeat=6`, rows shorter than 2048 blocks, empty rows, ends past the width), prefill rows with starts, and the fallback path: the selected candidate sets are identical. The only exception is an exact score tie at the 2048th block, where either choice is valid.
- The fallback path forced on is identical to the previous implementation (fp32). With bf16 logits, the DeepSelect path and the fallback select the same blocks, compared by score so ties do not count.
- NaN rows (fully NaN, and partly NaN) on the DeepSelect path: every id is in range and unique, nothing stale is left, and the NaN blocks are selected.
- bf16 paged MQA logits are byte-identical to the fp32 output rounded to bf16.
