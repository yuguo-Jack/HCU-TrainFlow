# [NIXL][Metrics] Add push-mode registration-expiry and writer-loop-error counters (O1)

[Upstream PR](https://github.com/vllm-project/vllm/pull/57722) · state: open · merged: False

## Original PR description

## Summary

Adds two new NIXL push-connector reliability metrics from the [`NixlPushMode` (WRITE) Roadmap - Reliability Issue Inventory](https://github.com/vllm-project/vllm/issues/48633), item **O1** ("No push-specific metrics"):

- `vllm:nixl_num_registration_expired` — a D-side registration whose watchdog deadline passed without a corresponding push completion (`push_scheduler.py`'s existing watchdog currently only logs a warning; this makes the event observable).
- `vllm:nixl_num_writer_loop_errors` — an exception caught by the push connector's writer thread loop (`_push_writer_loop`'s existing `except Exception: ...continuing`, which today fails silently from an operator's perspective).

Both follow the exact existing pattern in `stats.py` (`record_*()` → `reset()`/`is_empty()`/`aggregate()` → `NixlPromMetrics` counter + `observe()`), so there's no new metric plumbing introduced — just two more counters using machinery that's already there.

## Why this doesn't duplicate existing work

Per `AGENTS.md`, ran the required duplicate-work checks before starting:

```
gh issue view 48633 --repo vllm-project/vllm --comments
gh pr list --repo vllm-project/vllm --state open --search "48633 in:body"
gh pr list --repo vllm-project/vllm --state open --search "nixl push stats"
```

This surfaced #55854 (NickLucche, open, `mergeStateStatus: CLEAN`), which reworks `stats.py`'s *existing* failure-counter grouping (splitting transport failures from KV-expiry). This PR deliberately does not touch that grouping or add another failure-classification counter — it only adds the two counters above, which #55854 doesn't cover. Also checked #50754 (open, touches `push_worker.py`/`metadata.py` for a different C2-adjacent bug) and #54757 (open, handshake hardening) — neither touches `stats.py` or these two metrics.

Two O1 sub-items were deliberately left out of this PR and are called out as follow-up rather than silently dropped:
- **Unmatched-registration / unmatched-finished-block gauges** — these are a Prometheus `Gauge`, a metric type this file doesn't use anywhere yet. Introducing that is a small design decision on its own (this PR only adds `Counter`s matching the existing pattern), so it's better as a separate, reviewable PR.
- **Dropped/partial-WRITE counter** — #50754 already reuses the existing `record_failed_transfer()` for this case rather than adding a dedicated counter. Given #55854 is actively re-litigating failure-metric taxonomy in this same file right now, adding another failure-classification counter here risked colliding with in-flight maintainer work rather than complementing it.

### Note on rebasing against #55854

This branch was originally written against a `main` predating #55854 (merged 2026-09-18), which reworked `stats.py`'s failure-counter grouping and reshaped `NixlPromMetrics.observe()`'s per-counter loop from one data-key per counter to a tuple of data-keys per counter. Rebasing required adapting the two new counters to that new shape (a naive re-apply would have compiled but silently never incremented them), and moving the two new fields into `reduce()`'s CLI output as their own `push_reliability_counts` group, matching the CLI-exposure convention #55854 established for failure counts. Also added `.get(key, [])` defensive access for the two new fields in `is_empty()`/`reduce()`, since `NixlKVConnectorStats` can be reconstructed from a serialized dict from a different code version (worker/logger process version skew) that predates these fields — a real `KeyError` this surfaced via `test_reduce`/`test_log_renders_plain_scalars` in `test_multi_connector.py` during rebase testing, not just a test-fixture quirk.
