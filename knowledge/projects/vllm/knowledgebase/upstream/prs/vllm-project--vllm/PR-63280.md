# [ROCm][Kernel] Add AITER W4A16 linear kernel (gemm_a16w4) for gfx942

[Upstream PR](https://github.com/vllm-project/vllm/pull/63280) · state: open · merged: False

## Original PR description



## Overview

Add `AiterW4A16LinearKernel`, an `MPLinearKernel` that runs int4 weight-only linears (GPTQ, AWQ, compressed-tensors W4A16) on MI300 (gfx942) with AITER's Triton `gemm_a16w4` (ROCm/aiter#6778, merged). It is registered ahead of `TritonW4A16LinearKernel` and used when `VLLM_ROCM_USE_AITER=1` (with the default `VLLM_ROCM_USE_AITER_LINEAR=1`) and the installed AITER provides `gemm_a16w4`. AWQ checkpoints on ROCm are routed to the `MPLinearKernel` path when this kernel is enabled.

Related: #34008 (W4A16 GEMM kernels for AMD, closed as stale). This supersedes #42640 (`CDNAHybridW4A16LinearKernel`, a new Triton kernel for the same slot; stale, needs rebase): it reuses AITER's tuned kernel instead of adding one to vLLM, and covers AWQ. #62736 (split-K tiles for `TritonW4A16LinearKernel` on gfx950) does not conflict: it changes only the gfx950 Triton path.

The end-to-end decode gain matches the kernel numbers: for Qwen2.5-7B in fp16 at M = 1, the summed linear-layer time over 28 layers is 18.7 ms (TritonW4A16) vs 2.2 ms (`gemm_a16w4`), a 16.5 ms difference; the measured TPOT difference is 15.8 ms.

Re-run with the final version of this PR (Qwen2.5-7B-GPTQ, A2 vs B, 2 repetitions): TPOT 19.67 -> 3.82 ms, concurrency 64 2698 -> 6689 tok/s, batch-1 latency 5.02 -> 0.97 s, GSM8K B 0.712 / 0.824 (A2 0.720 / 0.828). With the warmup (4 weight shapes x 28 M values; 31.6 s cold, 0.2 s with a warm Triton cache), the JIT monitor reported no `_gemm_a16w4_kernel` compilation during serving or latency runs, for GPTQ and AWQ. With stock AITER v0.1.26 and `VLLM_ROCM_USE_AITER=1`, GPTQ selects `TritonW4A16LinearKernel` and AWQ stays on `AutoAWQLinearMethod`, and both serve normally.

Compile cache, same image, `VLLM_ROCM_USE_AITER=1`, Qwen2.5-7B-GPTQ, persistent `~/.cache/vllm`: without the hash change, a cache built with stock AITER v0.1.26 (TritonW4A16) was loaded after adding `gemm_a16w4` and the server failed at startup (`AssertionError: expected size 4608==3584`). With it, stock and `gemm_a16w4` builds get different AOT cache entries; switching stock -> `gemm_a16w4` -> stock -> `gemm_a16w4` starts and serves each time (TritonW4A16 / AiterW4A16 / TritonW4A16 / AiterW4A16), reusing the matching entry on the second visit.

### Tests

```bash
# gfx942, AITER with gemm_a16w4, VLLM_ROCM_USE_AITER=1
pytest tests/kernels/quantization/test_aiter_w4a16.py \
  tests/kernels/quantization/test_w4a16_kernel_selection.py \
  tests/kernels/quantization/test_triton_w4a16.py \
  "tests/quantization/test_auto_awq.py::test_auto_awq_rocm_routes_to_mp_linear_with_aiter_w4a16"
# 131 passed
# same with stock AITER v0.1.26 (no gemm_a16w4): test_aiter_w4a16.py skips; 6 passed, 1 skipped
# without VLLM_ROCM_USE_AITER: test_w4a16_kernel_selection.py 4 passed
```

`test_aiter_w4a16.py` checks the kernel against a fp32 reference through `process_weights_after_loading` + `apply_weights` for the GPTQ/AWQ layout (`[K // 8, N]`) and the compressed-tensors layout (`[N, K // 8]`), uint4b8 and uint4, groups -1/32/128, fp16/bf16, M = 1/16/33/256 with bias; the fake impl under `make_fx`; `can_implement` (group sizes, quant types, batch-invariant mode); and the warmup. `test_auto_awq.py` checks the ROCm AWQ routing and that Marlin verification is skipped only on that route. `test_w4a16_kernel_selection.py` also checks that the compile-cache factor agrees with the selection gate and that `KernelConfig.compute_hash` changes with it.

Test environment: `vllm/vllm-openai-rocm:nightly-df6603f0583375f244d1ac6d36265462b7490392` (torch 2.13 + ROCm 10.0, Triton 3.8.0+git669b31ac, AITER v0.1.26) with this PR applied, and the files added by ROCm/aiter#6778 (`gemm_a16w4` wrapper, kernel and gfx942/gfx1100 configs, from aiter b818d3571) copied into the installed AITER v0.1.26. The PR adds files only; their dependencies exist in v0.1.26. The kernel table above was measured with AITER at #6778 on torch 2.10 + ROCm 7.0, Triton 3.8.0.

## Details

- **Kernel.** The GPTQ, AWQ (after `_convert_awq_to_standard_format`) and compressed-tensors loaders hand `MPLinearKernel`s int32 words that hold 8 sequential K values. That is `gemm_a16w4`'s weight layout viewed as uint8, so `process_weights_after_loading` only permutes the weight to `[N, K // 8]`, keeps scales as `[N, K // G]` in the activation dtype, and unpacks zero points to uint8 `[N, K // G]`; no weight copy beyond the permutation. uint4b8 uses the kernel's default zero point 8.
- **Gating.** `rocm_aiter_ops.is_linear_w4a16_enabled()` = `is_linear_enabled()` (`VLLM_ROCM_USE_AITER` and `VLLM_ROCM_USE_AITER_LINEAR`) and gfx942 and `gemm_a16w4` importable. The importability check follows the existing `_gdn_triton_kernels_importable` / `_kda_gluon_decode_importable` pattern (cached guarded import). gfx942 only: of the archs vLLM builds AITER for, only gfx942 has tuned configs (AITER also ships gfx1100 configs; see Limitations). `VLLM_DISABLED_KERNELS=AiterW4A16LinearKernel` disables it.
- **Custom op.** The GEMM runs as `torch.ops.vllm.rocm_aiter_gemm_a16w4` with a fake impl; it works with `VLLM_COMPILE` and FULL_AND_PIECEWISE CUDA graphs (all runs above).
- **Warmup.** AITER picks a config per power-of-two M bucket and Triton specializes M on 1 and multiples of 16. CUDA graph capture covers only decode sizes, so without a warmup the first prefill in a new bucket compiled the kernel during serving (reported by the JIT monitor). `aiter_w4a16_warmup` runs from `kernel_warmup` (when `enable_jit_warmup`) and calls each distinct layer shape once per bucket (M = 2^k and 2^k - 1, up to `max_num_batched_tokens`).
- **Batch invariance.** AITER's tuned `BLOCK_SIZE_K` and split-K change with the M bucket, so `can_implement` rejects the kernel under `VLLM_BATCH_INVARIANT`, which keeps the existing path (as `mxfp4/aiter.py` does for its split-K path).
- **AWQ routing.** On ROCm, `AutoAWQConfig` always used `AutoAWQLinearMethod` (Triton AWQ GEMM), so AWQ never reached the `MPLinearKernel` registry. When `is_linear_w4a16_enabled()`, it now returns `AutoAWQMarlinLinearMethod` (the generic `choose_mp_linear_kernel` path, already used on CPU/XPU) and skips the Marlin capability check on that route only. With the gate off, ROCm AWQ behavior is unchanged.
- **Compile cache.** The selected kernel changes the weight layout the compiled graph sees, but the torch.compile cache key did not record it: with the same vLLM version and settings, installing or removing an AITER build with `gemm_a16w4` loaded a graph compiled for the other layout and failed at startup (`AssertionError: expected size 4608==3584` in the compiled graph). `KernelConfig.compute_hash` now includes `rocm_aiter_ops.linear_w4a16_compile_factor()` on ROCm. That factor is HIP-free (it checks the env/arch gate and that `aiter/ops/triton/gemm/basic/gemm_a16w4.py` exists via `find_spec`, without importing aiter), because config hashes are also computed in the API server process and importing aiter initializes HIP. A test checks that it agrees with the selection gate and that the hash changes with it.
- **Dependency.** vLLM pins AITER v0.1.26, which predates ROCm/aiter#6778, so the kernel stays inactive in the current image until the AITER pin includes it. This PR does not bump AITER.

### Limitations

- gfx942 only. On gfx1100 (W7900) `gemm_a16w4` is 1.1-2.1x faster than `RDNA3W4A16LinearKernel` for M >= 8 but 0.7-0.95x at M <= 4, and vLLM does not build AITER for gfx1100; not enabled there. gfx950 has no AITER configs.
- Compared with the BF16 model (config C), not the existing int4 path: at concurrency <= 8 the int4 model with this kernel matches or beats BF16 (Qwen2.5-7B TPOT 3.83 vs 4.39 ms, concurrency-8 throughput 1644 vs 1345 tok/s; Qwen3-8B-AWQ 1281 vs 1196 tok/s). At concurrency 32-64, BF16 has 3-6% higher throughput for Qwen2.5-7B and 16-17% for Qwen3-8B-AWQ, and lower TTFT from concurrency 8 on (Qwen2.5-7B 62/81/158 vs 156/117/188 ms at 8/32/64). The cause is prefill-sized GEMMs: for M >= 256 the kernel runs at 0.68-0.85x of dense hipBLASLt BF16. Routing large M to a dequantize-to-BF16 + hipBLASLt path would be a natural follow-up; this PR does not change prefill routing.
