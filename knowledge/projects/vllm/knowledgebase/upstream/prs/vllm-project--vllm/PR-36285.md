# Add structured output support for beam search in online serving

[Upstream PR](https://github.com/vllm-project/vllm/pull/36285) · state: open · merged: False

## Original PR description


> [!NOTE]
> This PR builds on top of the existing work done in #35022 by @guan404ming to add support for beam search with structured output while serving the model online. **I recommend holding this PR merge until the original PR gets merged.**

## Purpose

This PR adds structured output support (JSON schema, choice, grammar) to beam search for the **online OpenAI-compatible server** (chat completions & completions APIs), addressing #34782.

Previously, beam search and structured outputs were mutually exclusive — users could use one or the other, but not both. This PR integrates grammar-based token filtering into the beam search loop so that every beam candidate is constrained to produce grammatically valid output at each decoding step.

**Supported backends:** xgrammar, guidance, outlines, lm-format-enforcer (with `"auto"` resolving to xgrammar).

**Design note:** Grammar state is recompiled and replayed per beam per step (O(n²) in sequence length) because structured output backends do not currently support cloning FSM state. This is consistent with the approach used in the offline path.

@arpera @DarkLight1337  Thanks for the review, and for pushing on the benefit-vs-maintenance tradeoff — those are fair questions. Let me lay out the case.

**1. The gap.** In vLLM online serving today, a request can use beam search *or* structured output, not both. This PR allows both together.

**2. Why a request would need both.** When you want the top-*k* outputs that all satisfy a structured-output constraint — e.g. a `choice` over a fixed set of allowed strings — you need beam search to return the top-*k* list *and* structured output to keep every candidate valid. Structured output without beam returns a single answer (greedy) or temperature-collapsed samples; beam without structured output can return invalid outputs. Neither alone covers this.

**3. Measured benefit.** I used a retrieval benchmark where the output must match one of a fixed candidate list — the ToolSense Realistic Retrieval Benchmark (Hathidara et al., 2026, https://arxiv.org/abs/2606.12451), 500 queries, Qwen2.5-7B, W=8. All three arms enforce the same constraint:

| decoding | Recall@8 | set-recall@8 |
|---|---|---|
| structured output, no beam | 0.732 | 0.377 |
| structured output, sampled n=8 | 0.788 | 0.419 |
| beam + structured output, W=8 | **0.962** | **0.766** |

Beam+SO roughly doubles gold-set coverage and lifts Recall@8 to 0.96; the gap widens when more than one output is correct (hard tier set-recall: 0.61 vs 0.17).

Happy to narrow the scope if this use case isn't worth the maintenance cost.

Only full-vocab does; that is what gives the impossibility guarantee.

I chose retain-as-truncated over raising an error because the over-cap allowed set is near-full, the retained prefix is itself grammar-valid, and a hard error would regress the common case where the model's natural top tokens do fall in the allowed set. The distinct `stop_reason` lets callers who want strictness detect and reject it. Unit tests cover `resolve_over_cap_logprobs` across the `-1`, finite-ceiling, vocab-bounded, and below-base cases.
