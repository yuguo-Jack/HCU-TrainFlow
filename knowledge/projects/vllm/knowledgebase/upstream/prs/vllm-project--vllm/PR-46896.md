# [KV Connector][Hybrid]  Enable GDN all-mode Mamba prefix caching with Mooncake Store retention

[Upstream PR](https://github.com/vllm-project/vllm/pull/46896) · state: open · merged: False

## Original PR description

## Purpose
This PR enables GDN `all`-mode Mamba prefix caching with Mooncake Store. It targets the same hybrid-cache gap discussed in #37898: full-attention KV can already identify and reuse a shared prefix, but the corresponding Mamba/GDN recurrent state may not exist at the same reusable boundary.

#37898 improves this for local `align` mode by using regular attention KVCache hits to detect shared prefixes. When FA KV has hits but SSM/Mamba cache lags behind, it admits a Mamba state at a block-aligned position. This PR takes a complementary `all`-mode + Mooncake Store path. Based on #26807, GDN `all` mode materializes recurrent states at block boundaries during prefill. Mooncake Store can then persist those block-boundary Mamba states together with FA KV blocks.

The goal is that when a future request hits FA KV from Mooncake Store, the matching GDN Mamba state should also be available at the same block boundary, so the hybrid model can resume cleanly from that prefix.

## Design
The key idea is to separate local residency from remote persistence.

Keeping every `all`-mode Mamba state resident in local HBM would put heavy pressure on the KV pool. Therefore the intended local setting is:

```bash
VLLM_PREFIX_CACHE_RETENTION_INTERVAL=0
```

With this setting, local vLLM keeps only the latest Mamba state required for continuing execution.

Mooncake Store retention is decoupled from that local interval. Store-side logic can still write the intermediate block-boundary GDN states produced by `all` mode, so future remote prefix-cache hits have both required states:

- full-attention KV blocks;
- matching GDN Mamba recurrent states at the same block boundaries.

Main changes:

- port GDN `all`-mode APC from vllm-project/vllm#26807 to current main;
- extend GDN metadata for all-mode block/state indexing;
- make GDN prefill produce and persist intermediate block-boundary recurrent states;
- keep the final scheduled block's Mamba state locally for continuing execution;
- decouple Mooncake Store retention from local  `VLLM_PREFIX_CACHE_RETENTION_INTERVAL`.

- lHrHenry233 · comment · 2026-06-29T03:56:38Z · [source](https://github.com/vllm-project/vllm/pull/46896#issuecomment-4828850483)

> we don't plan to support all mode for GDN

I agree that dense local GDN `all` mode is usually not attractive because it puts much more pressure on HBM than `align`.

The motivation here is narrower: use `all` mode only to materialize block-boundary GDN states for Mooncake Store, not to keep all of them resident locally.

The intended policy is:

- local HBM uses sparse retention, e.g. `VLLM_PREFIX_CACHE_RETENTION_INTERVAL=0`;
- Mooncake Store still persists intermediate GDN states;
- future remote prefix-cache hits can restore both FA KV and matching Mamba/GDN state from the same boundary.

This follows the same local-residency vs remote-persistence direction as #46906. If #46906 can help DSV4-style FA + SWA reuse, I think the same pooling pattern is worth evaluating for FA + Mamba hybrid models. I will add the relevant tests as soon as possible.

- ivanium · comment · 2026-06-30T08:12:38Z · [source](https://github.com/vllm-project/vllm/pull/46896#issuecomment-4841280424)

Even with kv offloading enabled, I still don't think all mode is a good choice because CPU and disk spaces are also limited in many cases. And I don't think all mode will effectively increase the cache hit rates. The reason we introduce cache retention to both HBM and offloading space is largely because of mamba (and SWA) prefix caches will consume too much space if caching all blocks and trigger intense evictions.

I would like to keep this PR open for now to conduct detailed testing. Scenarios to test include: 
- vLLM baseline (align mode) + pooling;
- "All mode" + various retention interval policies + pooling (decoupled vs. non-decoupled).
