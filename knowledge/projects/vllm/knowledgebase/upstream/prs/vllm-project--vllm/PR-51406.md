# [ROCm] Enable fused QK-norm+RoPE+gate Triton kernel for Qwen3-Next/Qwen3.5

[Upstream PR](https://github.com/vllm-project/vllm/pull/51406) · state: open · merged: False

## Original PR description

## Purpose

`Qwen3NextAttention` fuses the gated QKV split + QK-RMSNorm + (partial) NeoX RoPE + gate copy into a single Triton kernel (`fused_qk_rmsnorm_rope_gate`, added in https://github.com/vllm-project/vllm/pull/44176). The kernel is pure Triton and backend-agnostic, but it is gated behind `current_platform.is_cuda()`, so ROCm falls back to the slow multi-op eager path, even though the kernel runs correctly and fast on AMD GPUs.

This PR relaxes that one-line guard to `is_cuda_alike()` so ROCm gets the same fusion. It affects the whole `Qwen3NextAttention` family: Qwen3-Next, Qwen3.5, Qwen3.5-MoE

Measured on MI325X (gfx942), bf16, against the model's real eager branch
(`GemmaRMSNorm` + the `rotary_emb` custom op), 300 timed iters after 50 warmup:

| Seq len (tokens) | Eager (µs) | Fused (µs) | Speedup |
|---|---|---|---|
| 1 (decode) | 279.4 | 33.0 | 8.47× |
| 8 | 279.3 | 33.6 | 8.32× |
| 64 | 281.7 | 33.9 | 8.32× |
| 512 | 277.4 | 33.7 | 8.22× |
| 4096 | 562.3 | 138.7 | 4.05× |

Note: https://github.com/vllm-project/vllm/pull/47719 is an opt-in AITER path that additionally fuses the KV-cache write.

## Test Plan

Add a test case in `tests/kernels/core/test_fused_qk_norm_rope.py`

#### 1. 🟠 Should fix: Test fused args diverge from production norm weight and beta
`tests/kernels/core/test_fused_qk_norm_rope.py:193`

The test passes `q_norm.weight.float()+1.0` with default `norm_beta=0.0`, while production passes the raw bf16 weight with `norm_beta=1.0`, exercising a different Triton specialization. It also never reaches the only production change (the `is_cuda_alike` gate), so it passes even if that gate is reverted. Compare `_project_qkv_gate` fused vs eager output via a `Qwen3NextAttention` stub.

**Who is affected:** ROCm CI coverage for Qwen3-Next/Qwen3.5: the AMD-run test does not exercise the production `norm_beta=1.0` / raw-weight call, nor the `is_cuda_alike` gate.

_Verified by running it._

#### 2. 🟠 Should fix: New test duplicates existing weaker kernel test with looser tolerance
`tests/kernels/core/test_fused_qk_norm_rope.py:151`

The new test largely duplicates the existing `test_fused_qk_norm_rope_gate.py` case with looser tolerance (5e-2 vs 1e-2), missing fp16, interleaved-MRoPE, and TP-sharded shapes. The real gap is that AMD CI does not run the existing file. Register the existing test in `.buildkite/test-amd.yaml` instead of adding a weaker copy.

**Who is affected:** Maintainers/CI: the kernel is tested twice on NVIDIA, and AMD gets only the weaker copy.

_Verified by running it._

#### 3. 🟠 Should fix: AMD CI never runs the dedicated kernel test or deps
`.buildkite/test-amd.yaml:1607`

The AMD `Core Operation Kernels` job does not run the kernel's dedicated `tests/kernels/test_fused_qk_norm_rope_gate.py`. Its `source_file_dependencies` do not include `vllm/model_executor/layers/fused_qk_norm_rope.py`. Now that the kernel is enabled on ROCm, changes to the kernel will not trigger the AMD kernel test. Add the dedicated test and the kernel path to that AMD job, as `kernels.yaml` does for H200.

**Who is affected:** ROCm CI: future edits to `fused_qk_norm_rope.py` are not validated on AMD kernel jobs.

_Verified by running it._

#### 4. 🔵 Nit: Test builds fp32 cos_sin_cache not matching production bf16
`tests/kernels/core/test_fused_qk_norm_rope.py:174`

`get_rope()` is called without `dtype=`, so `cos_sin_cache` is fp32 (default dtype). The fused call therefore reads an fp32 cache. The eager `rotary_emb(...)` call later casts the cache to bf16 via `_match_cos_sin_cache_dtype`. Production builds rope under the model dtype, so the fused kernel always gets a bf16/fp16 cache. Pass `dtype=dtype` so the test exercises the production cache dtype and both sides use the same cos/sin.

**Who is affected:** Only test fidelity: the new test in `kernels/core` (run on AMD CI) never exercises the bf16-cache case used by Qwen3-Next/Qwen3.5 on ROCm.

_Verified by running it._

#### 5. 🔵 Nit: Test uses contiguous tensors, skipping QKV split strides
`tests/kernels/core/test_fused_qk_norm_rope.py:191`

The test passes freshly allocated contiguous `q_gate`/`k` tensors. Production passes `qkv.split(...)` views whose row stride spans the full QKV width. The kernel's `q_gate.stride(0)`/`k.stride(0)` handling for wide rows is therefore never exercised; build one `qkv` tensor and split it as the model does.

**Who is affected:** Test coverage only; production layout (strided views) is untested on ROCm and CUDA alike.

#### 6. 🔵 Nit: Loose q/k tolerance can hide ROCm numeric regressions
`tests/kernels/core/test_fused_qk_norm_rope.py:218`

The q/k `atol=5e-2` is five times looser than the sibling test's 1e-2 on the same kernel and geometry, loose enough to hide systematic rounding regressions. The comment claims the non-rotary region is bit-identical but never asserts it. Assert exact equality on the `[rotary_dim:head_dim)` slice and keep the looser tolerance only for the rotary slice.

**Who is affected:** Test strictness only.

_Verified by running it._
