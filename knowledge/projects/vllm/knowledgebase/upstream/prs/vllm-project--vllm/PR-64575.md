# [Frontend] Reject Anthropic-defined tools by type in /v1/messages

[Upstream PR](https://github.com/vllm-project/vllm/pull/64575) · state: closed · merged: True

## Original PR description



## Overview

`/v1/messages` rejects Anthropic-defined tools (`web_search_20250305`, `bash_20250124`, ...) with `input_schema: Field required`. This changes the 400 to name the unsupported tool type instead.

Tracking: #64810. Related: #46790 (Claude Code's WebSearch fails against vLLM). Alternative to #46797, which accepts these tools and drops them; see Details.

## Claims

- A request with an Anthropic-defined tool gets one 400 error: `tool type 'web_search_20250305' is not supported; only custom tools with an input_schema are supported`.
- Custom tools are unchanged, with or without an explicit `"type": "custom"`, and they still require `input_schema`.

## Validation

New unit tests in `TestToolDefinitions`, run on the base `protocol.py` and with this fix (macOS, CPU-only):

```
$ pytest tests/entrypoints/anthropic/test_anthropic_messages_conversion.py -k TestToolDefinitions
# base
E       assert "'web_search_20250305' is not supported" in 'Field required'
E       assert "'bash_20250124' is not supported" in 'Field required'
2 failed, 3 passed
# this PR
5 passed
```

The full `test_anthropic_messages_conversion.py` run gives 132 passed and 3 failed. The 3 failures are `TestDetectMergeInlineSystem::test_probes_non_jinja_renderer[deepseek-*]` (`Failed to infer device type`), and they fail the same way on base on a machine with no accelerator.

The response through the real Anthropic router (FastAPI `TestClient` with `attach_router` and the validation exception handler):

```
400 {"error":{"message":"1 validation error:\n  {'type': 'value_error', 'loc': 'body.tools.0', 'msg': \"Value error, tool type 'web_search_20250305' is not supported; only custom tools with an input_schema are supported\", ...
```

`test_messages.py::test_anthropic_server_tool_is_rejected` sends the same request end to end with the Anthropic SDK through `RemoteOpenAIServer`. **I have not run that test locally (no GPU here); it runs in the existing `entrypoints/anthropic` CI step.**

## Details

**Root cause.** `AnthropicTool` models only custom tools: `input_schema` is required and there is no `type` field. Anthropic-defined tools carry a versioned `type` and no `input_schema`, so pydantic reported the missing field. A `mode="before"` validator now rejects any `type` other than `custom` before field validation runs, so the error the client sees is about the tool type.

**Why reject instead of dropping the tool (#46797).** The Anthropic API never drops a server tool it can't run:
- With web search disabled for the org, it returns `400 invalid_request_error` saying web search is not enabled, not an error inside a search result ([docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-search-tool)).
- Bedrock lists server tools as unsupported ([docs](https://platform.claude.com/docs/en/build-with-claude/claude-in-amazon-bedrock#features-not-supported)) and reports `ValidationException: tool type 'web_search_20250305' is not supported for this model`.

If vLLM drops the tool, a client that asked for search gets an answer from training data with no error and no citations. #46797 also drops `bash_*` and `text_editor_*`. Those are Anthropic-defined *client* tools: the client runs them, and Bedrock supports them. Dropping them means the model can never call a tool the client is waiting to run.

**Limitations / follow-ups**
- Supporting Anthropic-defined client tools (`bash_*`, `text_editor_*`, `memory_*`) properly would mean supplying their built-in schemas to the chat template. That's a feature, left for a separate PR; until then they get the same named 400.
- Request-body validation errors on `/v1/messages` still use the shared OpenAI-style envelope (`"type": "Bad Request"`) rather than Anthropic's `{"type": "error", "error": {"type": "invalid_request_error", ...}}`. That is pre-existing and not changed here.
