# [Perf][Attention] 16-byte-align per-token-head KV slots so Triton vectorizes loads

[Upstream PR](https://github.com/vllm-project/vllm/pull/62113) · state: open · merged: False

## Original PR description

## Overview

TRITON_ATTN packs int8/fp8 per-token-head KV as `[K | k_scale | V | v_scale]`. The slot stride (520 B at head_size 256, 264 B at 128) and the V offset (+260/+132 B) are not multiples of 16, so `kernel_unified_attention` loads K/V one byte at a time. This PR pads each K/V half to 16 bytes. Related: #56081, #56164, #61925.

AI assistance was used: an AI coding agent wrote the code and tests under my direction, drafted this description, and automated the test and benchmark runs; I chose the approach and reviewed every changed line and the results.

## Claims

- `ld.global.b8` K/V loads: 64 → 0 (sm_86 PTX).
- `int8_per_token_head` kernel time, RTX 3080: 1.56–1.83× faster for decode at 8k–128k, 1.25–1.50× for 8-token verify and 1.65–1.96× for an 8k prefill chunk at 32k–128k; every int8 cell measured is ≥ 1.25× faster.
- End to end (TP=2, 27B hybrid, MTP): 128k TTFT −21 %, 128k decode pass 62.1 → 48.0 ms.
- Memory: +4.6 / +9.1 / +17.6 % at head_size 256 / 128 / 64 (KV pool −4.3 % in the run below). INT4 unchanged.
- Kernel outputs bit-identical to main; writer and kernels unchanged.

## Details

**Root cause.** Triton 3.8.0 marks an argument 16-divisible only if `arg % 16 == 0` / `data_ptr() % 16 == 0` (`triton/backends/compiler.py:75-92`). Offline compile of `kernel_unified_attention` (3D, D=256, GQA 6, TILE 16, 4 warps):

| layout | slot stride | V offset | `ld.global.v4.b32` | `ld.global.b32` | `ld.global.b8` |
|---|---|---|---|---|---|
| bf16 KV | 512 B | – | 4 | 4 | 0 |
| int8 per-token-head, main | 520 B | 260 B | 4 | 24 | 64 |
| int8 per-token-head, this PR | 544 B | 272 B | 4 | 4 | 0 |

*sm_86 compile, image `8c1434bf…5035e`, Triton 3.8.0; the RTX 3080 benchmark runs JIT-compiled the same counts.*

The kernel test missed this (separate aligned K/V tensors, 2D path only). It now reads the packed cache, runs `seq_threshold_3D` ∈ {0, 8} with a q=4 batch, and asserts split-K ran.

**Change.** `customize_spec` sizes each INT8/FP8 half as `round_up(head_size * dtype_size + 4, 16)`; `_ensure_scale_caches` takes `head_size` from the layer. Scale placement and the `content // 2` split are unchanged.

| head_size | bytes per token and KV head | change | vs bf16 |
|---|---|---|---|
| 64 | 136 → 160 | +17.6 % | 0.53 → 0.63 |
| 128 | 264 → 288 | +9.1 % | 0.52 → 0.56 |
| 256 | 520 → 544 | +4.6 % | 0.51 → 0.53 |

*Computed by `customize_spec`; the RTX 3080 runs above (image `8c1434bf…5035e`, Triton 3.8.0) saw 544/288 B strides.*

**Alternative: one pad.** `[K | V | k_scale | v_scale | pad]` (528/272/144 B, +1.5/+3.0/+5.9 %) also removes every byte load and passes the same tests. Cache populated (n=5 processes per arm): 8k prefill chunks at head_size 256 take 9–17 % less time with this PR (q8ks32k/q8ks128k at 12/2, 24/4); decode and verify match within ±3 % except 32/8/128 q1s8k (this PR −7 %). Hence two pads; one pad is ready if reviewers prefer a smaller cache.

**Related.**
- #56081: same misalignment in a gather-based sparse kernel (sm_121) needing 128-byte alignment or side tensors; not fixed here.
- #56164 is not a duplicate: it opts out of inline scales, this PR pads them. They conflict in `customize_spec` and `_ensure_scale_caches` but compose (its early return stays first).
- Inline packing from #36893 (closed PR) / #38378 (merged PR) is kept.

**Layout change.** Persisted offload stores and prefill/decode pairs on different versions are invalid across this PR. On hybrid models the attention block size follows the page size (816 → 784 above).

**Limits.**
- Measured only on RTX 3080 (sm_86, power-capped); A100, L4 and H100 not measured; PTX compiled only for sm_86.
- fp8 per-token-head shares the layout code but cannot run on sm_86; not timed.

**CI.** No sm_86 runner. `test_per_token_kv_cache.py` runs in the H200 Quantization step (`.buildkite/test_areas/quantization.yaml:5`), attention kernel tests on L4 (`kernels.yaml:315`).
