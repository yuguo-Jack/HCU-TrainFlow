# [Bugfix][kv_offload] Dedup gpu_block_ids in eager-mode SCO (store + load paths)

[Upstream PR](https://github.com/vllm-project/vllm/pull/42903) · state: open · merged: False

## Original PR description

Fixes #42085. Same defect class as #42571.

## What's broken

`SimpleCPUOffloadScheduler` emits duplicate `gpu_block_ids` in two places:

### Store path (`_prepare_eager_store_specs`)

Doesn't dedup `gpu_block_ids` within a single request's scan. `state.block_ids[g]` accumulates physical block ids appended every step, and sliding-window groups reuse the same physical block at multiple logical positions as the window slides. `_in_flight_store_gpu_blocks` only dedups across requests, not within. 

Additionally, inter-request duplicates within a single scheduler step can occur because `_in_flight_store_gpu_blocks` is only updated at the end of each request's processing, not during — if two requests in the same step share a block (prefix sharing), both schedule it.

### Load path (`update_state_after_alloc`)

Back-traces from the tail of each group's block table to build GPU↔CPU load pairs. For SWA groups, when the ext range spans reused logical positions, the same `gpu_block_id` appears N times in the load list.

### Crash mechanism (both paths identical)

Duplicates flow through:
1. `gpu_pool.touch` — same block N times → `ref_cnt += N`
2. `free_blocks` on completion — same `KVCacheBlock` object yielded N times → all N decrements happen, and if ref_cnt math lands at exactly 0 the filter passes all of them
3. `FreeKVCacheBlockQueue.append_n` — iterates N times on the same block, each iter sets `block.prev_free_block = last_block` overwriting the previous and leaving the previous predecessor's `.next_free_block` stranded
4. Free list becomes Y-shaped; next `popleft_n` walks into a dangling pointer and asserts → engine dead

Two failure modes: silent ref_cnt leak (request still active at completion) vs. crash (request finished first, dups end at ref_cnt == 0, filter passes all, append_n corrupts).

## Fix

### Store path (commit 912cef22)

Replace the per-request `seen_in_req: set[int]` with **eager population of the global `in_flight` set** (`self._in_flight_store_gpu_blocks`) during the scan. The early `gpu_block_id in in_flight` check (right after the `is_null` check) and eager `in_flight.add` handle both intra-request SWA reuse and inter-request per-step prefix sharing with one mechanism. The existing `in_flight.update(gpu_block_ids)` at end-of-request is now additive (set no-op for already-present elements) and serves as defense-in-depth.

### Load path (commit 26c8b3b7)

Build a per-group `load_map: dict[gpu_bid, (cpu_bid, cpu_block)]` during the back-trace. Dict insertion keeps the **LAST** occurrence for each GPU block, which carries the most recent CPU data (the correct content to load into the physical block). Unlike the store path where any occurrence is equivalent, the load path must keep the latest because each logical position has different KV data.

## Repro

Deterministic on DeepSeek-V4-Flash (sliding window enabled) with `SimpleCPUOffloadConnector` + `--no-disable-hybrid-kv-cache-manager` + `--enable-prefix-caching` + `--async-scheduling`, on long-context conversational continuation.

The current deduplication logic in the load path is incomplete and may still lead to the same crash mechanism described in the PR. While `load_map` correctly deduplicates by `gpu_bid`, it does not deduplicate by `cpu_blk`. 

In scenarios with repeating content (e.g., a prompt with identical blocks at different logical positions), multiple distinct `gpu_bid` values can map to the same `cpu_blk`. This results in `cpu_blocks_to_touch` (line 314) and `cpu_block_ids` (stored in `TransferMeta`) containing duplicate physical CPU blocks. 

When these duplicates reach `BlockPool.touch` (line 317) and subsequently `BlockPool.free_blocks` (in `_cleanup_load_request`), the `ref_cnt` will be over-incremented and then decremented back to zero while the block is still present multiple times in the list. This causes `append_n` to be called multiple times for the same block, leading to the free list corruption and engine crash mentioned in the PR description. 

To fix this, you should ensure that the lists used for resource management (`touch` and `free_blocks`) only contain unique blocks, while the parallel lists used for the actual transfer (the pairs) retain duplicates if necessary for the worker.
