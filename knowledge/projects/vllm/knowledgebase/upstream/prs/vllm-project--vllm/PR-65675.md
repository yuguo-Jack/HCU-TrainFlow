# [Perf] Tune FlashInfer MNNVL all-reduce cutoffs for single-node TP4/TP8 on SM90

[Upstream PR](https://github.com/vllm-project/vllm/pull/65675) · state: open · merged: False

## Original PR description



## Overview

On a single SM90 node, standalone FlashInfer all-reduce (MNNVL under the auto backend) only takes inputs up to the AR+RMSNorm fusion defaults, 2 MiB at TP4 and 0.5 MiB at TP8. Larger inputs go to the custom or symm-mem all-reduce, though on H20 MNNVL is faster at most sizes up to 64 MiB. This PR sets the SM90 MNNVL cutoff to 64 MiB for TP4 and TP8, the value TP2 already uses. Tuned cutoffs now apply only to an MNNVL workspace, so a TRTLLM fallback keeps the default cutoff and workspace size.

## Claims

- **Per all-reduce on 8×H20** (bf16, hidden 5120). Other sizes take the same path as main.
  - TP8, 720 KiB–64 MiB: up to 39% faster, including 17–20% at 24, 48 and 64 MiB. It is 0.4–1.0% slower at 32, 40 and 56 MiB.
  - TP4, 2.8–64 MiB: 12–27% faster up to 32 MiB, and 0.3–2% faster from 40 to 64 MiB.
- **DeepSeek-V4.1-Flash TP8 forward step:** decode (DSpark k=5) at C12–C64 is 0.5–1.5% faster, and prefill and mixed steps are up to 0.6% faster. C1–C8 are within 0.1%.
- **Memory:** unchanged on this H20. FlashInfer allocates the MNNVL workspace in 512 MiB fabric pages, so it takes 514 MiB per GPU on main and with this PR.
- **Unchanged:** SM90 nodes where the MNNVL workspace cannot be created (e.g. no NVSwitch multicast), groups that resolve to TRTLLM (e.g. HiSparse), and SM100/SM103 nodes with multicast.

## Details

- **Why 64 MiB.** At TP8, MNNVL is 14% slower than NCCL at 80 MiB. Caps above ~85 MiB also double FlashInfer's MNNVL allocation to 1 GiB, which made MNNVL about 20% slower at 16–80 MiB. TP2 already uses 64 MiB.
- **TRTLLM fallback.** On a single node, auto picks MNNVL and falls back to TRTLLM when the MNNVL workspace cannot be created, e.g. without NVSwitch multicast (H100 PCIe, H200 NVL).
  - On main, `get_fi_ar_workspace()` grows the workspace to the tuned cutoff before trying MNNVL, so the fallback inherits it, and so does `FlashInferAllReduce`'s cutoff.
  - Now only the MNNVL attempt is grown. The fallback is created at the requested size, and `FlashInferAllReduce` drops to the default cutoff when it gets a TRTLLM workspace.
  - With MNNVL creation forced to fail on 8×H20, the 64 MiB entries without this handling give a 2050 MiB TRTLLM workspace at TP8 (1028 MiB at TP4) that takes inputs up to 64 MiB. With it: 18 MiB (36 MiB) and main's 0.5 MiB (2 MiB) cutoff.
  - This also covers the existing SM100/SM103 entries.
- **Memory with other handle types.** Where FlashInfer uses POSIX file-descriptor handles (2 MiB granularity), the workspace would grow from ~4 MiB to ~385 MiB per GPU. This is computed from FlashInfer's buffer sizes, not measured.
- **Other SM90 parts.** H100 and H200 SXM share H20's 900 GB/s NVSwitch, and every backend is bandwidth-bound at these sizes, so the crossovers should carry over. This was not measured. H800 (400 GB/s) was not measured either.
- **Duplicates.** #53852 adds a user override for this cutoff; this PR changes the SM90 defaults. No open PR changes those defaults.
