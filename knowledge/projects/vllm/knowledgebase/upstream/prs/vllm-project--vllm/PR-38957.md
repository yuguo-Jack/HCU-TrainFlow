# [Bugfix][cmake] fix FP4 ARCH for CUDA>=13.0

[Upstream PR](https://github.com/vllm-project/vllm/pull/38957) · state: closed · merged: False

## Original PR description

## Purpose
**Issue**
For CUDA >= 13.0, FP4_ARCHS uses "12.0f" to match, which drops the architecture specific suffix.
for example: it breaks nvfp4 on DGX Spark.

**Fix**
Match with `12.0a;12.1a` first, then keep `12.0f` as catchall.

## Test Plan
- [x] test vllm build success with CUDA >= 13.0 on DGX Spark
- [ ] test vllm build sucess on B200

- ubehera · comment · 2026-05-28T16:21:36Z · [source](https://github.com/vllm-project/vllm/pull/38957#issuecomment-4566102538)

This fix is correct for `FP4_ARCHS`/`QUTLASS_ARCHS`, and the same `"12.0f"`-only pattern appears in six other places in the CUDA-13 conditional branch of `CMakeLists.txt`. Each has an asymmetric pair where the `CUDA < 13.0` branch uses `12.0a;12.1a` (correct) but the `CUDA >= 13.0` branch drops to `12.0f` (loses NVFP4 MMA PTX `.kind::mxf4nvf4` / `.kind::mxf4` — these are arch-specific to `sm_120a`/`sm_121a` and are not emitted by the `sm_120f` family target).

Verified against `4bfa0f2b`:

| Line | Arch list | CUDA-13 branch | CUDA<13 branch |
|------|-----------|----------------|----------------|
| 371 | `MARLIN_ARCHS` | `"8.0+PTX;12.0f"` | `"8.0+PTX;12.0a;12.1a"` |
| 379 | `MARLIN_BF16_ARCHS` | `"8.0+PTX;9.0+PTX;12.0f"` | `"8.0+PTX;9.0+PTX;12.0a;12.1a"` |
| 388 | `MARLIN_FP8_ARCHS` | `"8.9;12.0f"` | `"8.9;12.0a;12.1a"` |
| 740 | `SCALED_MM_ARCHS` (c3x SM12x) | `"12.0f"` | `"12.0a;12.1a"` |
| 883 | `CUTLASS_MOE_DATA_ARCHS` | `"9.0a;10.0f;11.0f;12.0f"` | `"9.0a;10.0a;10.1a;10.3a;12.0a;12.1a"` |
| 912 | `FP4_ARCHS` (this PR) | `"12.0f"` → fix | `"12.0a;12.1a"` |
| 1013 | `MLA_ARCHS` | `"10.0f;11.0f;12.0f"` | `"10.0a;10.1a;10.3a;12.0a;12.1a"` |

Empirically on DGX Spark (GB10, `sm_121`, CUDA 13.0): builds with `TORCH_CUDA_ARCH_LIST="12.1a"` produce `12.0f`-only cubins for `scaled_mm_c3x_sm120`, `moe_data`, and `MLA` kernels even though `12.1a` was requested — the family target loads but the arch-specific PTX intrinsics aren't in the binary. Some kernels then fail at runtime with `cutlass::Status::kErrorInternal` from `can_implement()`.

Happy to extend this PR with the other six lines if you'd prefer one change-set, or open a follow-up — your call. Note that a separate gate issue exists at line 104 (CUDA-13 `CUDA_SUPPORTED_ARCHS` doesn't include `12.1`), which strips `12.1a` from user-supplied `TORCH_CUDA_ARCH_LIST` before reaching any of the per-kernel intersections above; that needs fixing too for these per-kernel changes to actually take effect (filed separately as a comment on #38484).

Test setup: NVIDIA GB10 (DGX Spark, `sm_121`), Ubuntu 24.04.4, CUDA 13.0, torch 2.11.0+cu130 nightly aarch64.

The fix for CUDA 13.0+ architecture matching should also be applied to the second `FP4_ARCHS` block (starting at line 934). The current change only addresses SM12x (consumer Blackwell), but DGX Spark (mentioned in the PR description) and other data center Blackwell systems typically use SM100 (B100/B200). Without updating line 935, FP4 support will remain broken on those systems when using CUDA 13.0+. Additionally, this pattern of using only forward-compatible suffixes (e.g., `10.0f`) for CUDA 13.0+ appears in several other places in this file (MLA, ES_MXFP8, etc.) and likely needs similar corrections to ensure robust architecture matching.
