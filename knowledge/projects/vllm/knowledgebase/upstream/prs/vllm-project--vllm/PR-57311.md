# [Perf][Startup] Move atomic_writer out of weight_utils so the model-info cache save stays light

[Upstream PR](https://github.com/vllm-project/vllm/pull/57311) · state: open · merged: False

## Original PR description

## Purpose

When the model-info cache misses (which is the normal case for the Docker images, see #51746), `_LazyRegisteredModel._save_modelinfo_to_cache` writes a small JSON file. To do that it imports `atomic_writer` from `model_loader/weight_utils.py`, and that import drags the whole model-loader / quantization / distributed stack into the API-server process: +943 modules, about a second on my machine, before the engine even starts (twice if there's a draft model).

`atomic_writer` only needs `os` and `tempfile`, so I moved it to a new `vllm/utils/file_utils.py`, import that from the registry, and left a re-export in `weight_utils` so nothing else changes. Added two small tests for the atomic replace and the error path, since it had none.

Related: #48193 (cold start), #23558 (where the cache and this import were introduced).

## Test Plan

```
pytest tests/utils_/test_file_utils.py
pytest tests/model_executor/test_weight_utils.py
VLLM_CACHE_ROOT=$(mktemp -d) pytest tests/models/test_registry.py -k lazy_modelinfo
```

And one manual check: inspect `Qwen3ForCausalLM` with an empty `VLLM_CACHE_ROOT`, confirm the JSON gets written and `weight_utils` is not in `sys.modules` afterwards.

## Test Result

All of the above pass (2 / 32 / 2). The import the save path used to do costs 0.8-1.0 s and +943 modules in a process that already has vllm loaded; the replacement costs nothing measurable.

Written with AI assistance; I've reviewed every line and ran the tests myself.

Hi @zsun6, thanks for this change. I independently traced a **correctness issue through the same `atomic_writer` import**, so this may have value beyond startup performance.

Your PR already covers atomic replacement/error cleanup and a manual cold-cache import check. The additional coverage I can contribute is **cold model-info cache + fork + automatically enabled breakable CUDA graphs**.

I reproduced this on unpatched vLLM `a9eafde59cbd55182dc2265cc398b7186f0a0eaa`, using TinyLlama-1.1B-Chat-v1.0 with `model_impl="transformers"`, BF16, TP=1, FlashAttention, one L20, PyTorch 2.13.0+cu129 and Transformers 5.15.1. **I have not run your PR head**, so these are baseline/control results, not a claim that the PR has passed this regression.

With `VLLM_BATCH_INVARIANT=1`, `VLLM_WORKER_MULTIPROC_METHOD=fork`, and `VLLM_USE_BREAKABLE_CUDAGRAPH` **unset**:

| Experiment | Observed result |
|---|---|
| Fresh model-info cache, fork, automatic breakable enablement | Incorrect output; 2/32 token sequences differed from the warm reference in the uninstrumented rerun |
| Two subsequent fresh-process starts with the same cache root | Identical tokens and top-5 logprobs |
| Fresh process/cache environment with **only `modelinfos` copied**, no compiled artifacts | All 32 token sequences and top-5 logprobs exactly matched the warm reference |
| Cold cache with `spawn` | All 32 matched the warm reference, including top-5 logprobs |
| Cold cache with breakable explicitly enabled **before importing vLLM** | All 32 matched the warm reference, including top-5 logprobs |

A separate one-prompt diagnostic used `The capital of France is`, greedy decoding, and 16 output tokens. The cold run began with token `14066` (`ometric`, followed by repeated `of`); the warm run began with `3681` (` Paris`). In worker-side diagnostics, the cold run lacked the breakable wrapper around `unified_attention_with_output`: each of the four capture sizes `[1, 2, 4, 8]` had **1 graph / 0 eager breaks**, versus **23 graphs / 22 eager breaks** in the warm and early-enabled controls. These counts are specific to this 22-layer model and configuration.

The import trace was:

```text
cold model-info cache write
  -> model_loader.weight_utils.atomic_writer
  -> model_loader.__init__ -> base_loader -> reload.layerwise
  -> attention imported before breakable is enabled
  -> eager_break_during_capture returns the original function
  -> VllmConfig later auto-enables breakable
  -> fork inherits attention without its eager-break wrapper
```

A CPU probe also confirmed that a function decorated while breakable was disabled did not call `add_eager` after late enablement, whereas one decorated after enablement did. This supports removing the early import; it does not require changing decorator semantics in this PR.

Two useful additions to the validation would be:

1. **Automate the import boundary you already checked manually.** In a genuinely clean `subprocess` interpreter, exercise the model-info JSON save/read roundtrip and assert that neither `vllm.model_executor.model_loader` nor `vllm.model_executor.layers.attention.attention` is imported. Assert the clean precondition as well. Avoid importing `tests.utils` in the child: its imports can preload the loader, and a multiprocessing `spawn` helper that reimports that test module does not provide the required isolation. Keep any legacy `weight_utils.atomic_writer` compatibility check in a separate process.
2. **Run the cold-fork model case before/after this patch**, with warm and early-enabled runs as controls. Check the actual worker wrapper/graph structure as well as output; the final breakable flag was already `1` in our failing run. For this setup, the candidate cold run should match the correct early-enabled reference and restore the attention eager breaks. The baseline/control experiments above are completed; this patch-specific red/green check remains to be done.

<summary>Small reproduction recipe, adapted from our recorded harness</summary>

This reduced script has not itself been rerun. The results above came from the original harness, which also recorded worker wrappers and graph segmentation. Use the same existing local TinyLlama checkpoint/tokenizer for every run, so changing `HOME` does not change model resolution.

```python
# tinyllama_modelinfo_repro.py
import json
import os


def main():
    from vllm import LLM, SamplingParams

    llm = LLM(
        model=os.environ["MODEL_PATH"],
        model_impl="transformers",
        dtype="bfloat16",
        seed=0,
        tensor_parallel_size=1,
        max_model_len=512,
        max_num_batched_tokens=512,
        max_num_seqs=8,
        gpu_memory_utilization=0.8,
        attention_config={"backend": "FLASH_ATTN"},
        compilation_config={"cudagraph_capture_sizes": [1, 2, 4, 8]},
    )
    ids = llm.get_tokenizer().encode(
        "The capital of France is", add_special_tokens=True
    )
    output = llm.generate(
        [{"prompt_token_ids": ids}],
        SamplingParams(temperature=0, seed=0, max_tokens=16, logprobs=5),
        use_tqdm=False,
    )[0].outputs[0]
    print(json.dumps({
        "prompt_token_ids": ids,
        "token_ids": list(output.token_ids),
        "text": output.text,
        "logprobs": [
            {str(t): p.logprob for t, p in step.items()}
            for step in output.logprobs
        ],
    }))


if __name__ == "__main__":
    main()
```

Run in the intended checkout/environment with one selected GPU. Set `MODEL_PATH` to an absolute local snapshot path. Before the cold run, use an empty `VLLM_CACHE_ROOT`, enable batch invariance, force `fork`, and leave the breakable override unset. Also remove unrelated compilation/AOT overrides from the environment. Start a second Python process with the same cache root for the warm comparison. In our harness, each process had fresh `HOME`, `TMPDIR` and `XDG_CACHE_HOME` directories; only the vLLM cache root persisted.

For independent controls, use separate empty cache roots and change only the worker method to `spawn`, or set `VLLM_USE_BREAKABLE_CUDAGRAPH=1` before process startup. Verify that auto mode really enables breakable CUDA graphs; testing with an explicit value of `0` exercises a different path. Keep baseline and PR cache roots separate.

The token IDs above are observations from our fixed checkpoint/configuration, not a portable oracle. Compare each candidate with its matching early-enabled reference. The instrumented 32-prompt run differed on 3 prompts rather than the uninstrumented run's 2, so I would also avoid asserting a fixed number of affected prompts.
