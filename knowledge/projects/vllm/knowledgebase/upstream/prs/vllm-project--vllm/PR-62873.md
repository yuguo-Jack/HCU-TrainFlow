# [Speculative] Mask draft logits with the request grammar (grammar_mask_draft_logits)

[Upstream PR](https://github.com/vllm-project/vllm/pull/62873) · state: closed · merged: False

## Original PR description

## Motivation

Fixes #62130.

Under structured outputs the target verifier only accepts grammar-valid
tokens, but the drafter samples unconstrained: most drafted tokens are
grammar-invalid and rejected at verify time, collapsing acceptance length.
Measured on the issue (vLLM 0.11.2, xgrammar, Qwen2.5-7B-Instruct, A100,
batch=1, agentic JSON workload, K=5): unmasked EAGLE3 accepted 1.44 draft
tokens per propose call and was 0.97x slower than no speculation.

This PR adds opt-in `SpeculativeConfig.grammar_mask_draft_logits`, which
applies the same grammar bitmask to the drafter's logits at every
speculative position.

## Measured effect (issue #62130, single-session, 12 agentic prompts, 3
timing iterations)

| Config | TPOT (ms) | tok/propose | vs no_spec | vs baseline |
|---|---|---|---|---|
| no_spec | 11.09 ± 0.01 | — | 1.00x | — |
| EAGLE3 (unmasked) | 11.47 ± 0.04 | 1.443 | 0.967x | 1.00x |
| **EAGLE3 + grammar mask** | **9.61 ± 0.03** | **1.969 (+36.5%)** | **1.154x** | **1.193x** |

On a second enum-heavy tool-call schema (nested enums + arrays), the mask
also restored JSON validity (5/8 valid, matching no_spec) where unmasked
speculation produced only 3/8 valid outputs, at 1.31x TPOT speedup vs
no_spec. Acceptance rises because 39.1% of draft-position argmaxes change
under the mask: grammar-invalid high-probability drafts are replaced by
the next-most-likely *valid* token.

## Design (V2 model runner only)

V1 `gpu_model_runner.py` is deprecated on main; the wiring targets
`vllm/v1/worker/gpu/model_runner.py` and the `BaseSpeculator` /
`DraftModelSpeculator` stack.

- **Why worker-side:** the mask for draft position `t >= 1` depends on
  draft tokens that do not exist at schedule time, so the engine cannot
  precompute them. Each `propose` rebuilds matcher state by replaying the
  request's committed output tokens (accepted-only; the engine's
  `pending_structured_output_tokens` deferral guarantees its FSM is current
  at mask time, so both sides advance identical state). This also follows
  the issue's own finding that a fresh matcher per propose (rather than
  carrying matcher state or relying on `rollback()`) was the robust
  lifecycle.
- **Hook:** `DraftModelSpeculator.sample_draft` masks the
  `compute_draft_logits` output before gumbel/argmax and stages the sampled
  draft so the next position's matcher can advance. Session
  begin/cleanup lives at the top of `propose` in the three supported
  speculators (target-dependent AR, standalone AR, multi-module MTP).
- **CUDA graphs:** when any scheduled row has an active grammar, draft
  forwards force eager mode (`need_eager` in `dispatch_cg_and_sync_dp`);
  graph capture runs dummy proposes with masking disabled.
- **Accepted-mask invariant:** the draft mask equals the engine's
  verify-row state, so drafting only removes tokens the engine would have
  rejected anyway — rejection-sampling exactness is preserved.
- **Fail-open:** non-xgrammar backends, grammars still compiling or failed
  to compile, replay desync, vocab mismatch, and unexpected apply errors
  all leave the affected row unmasked. An unmasked draft row is a superset
  of the engine's mask and always safe; a narrower mask could not be.

## Config validation

`verify_config` (called from `VllmConfig.__post_init__`) rejects the flag
with: methods other than eagle/eagle3/draft_model/mtp (incl. ngram,
dflash, dspark, custom), `parallel_drafting`,
`use_local_argmax_reduction`, `use_heterogeneous_vocab`, the V1 model
runner, `skip_tokenizer_init`, and a reasoning parser without
`enable_in_reasoning`.

## Model evaluation

Draft-side masking changes the draft sampling distribution only; verified
tokens still pass through engine rejection sampling unchanged, so the
output distribution is preserved by construction (locally projected
grammar-constrained distribution, same as vLLM's non-speculative
structured-output path). Benchmark numbers above are from the issue
author's measurements; no additional eval suite was run in this
environment (see Testing).

- yzong-rh · comment · 2026-10-21T21:58:30Z · [source](https://github.com/vllm-project/vllm/pull/62873#issuecomment-6327464244)

Looks like the PR is updated since this morning. Now we only constrain the first draft token.
However, among other issues, the main blocker is `_next_draft_grammar_bitmask` misalignment
   1. `model_executor.sample_token(step N)` runs, generating drafts for step N+1
   2. `scheduler.update_from_output` runs, grammar is updated from step N output
   3. `_next_draft_grammar_bitmask` is computed, it constrains the first token after step N
   4. `model_execute.execute_model(step N+1, _next_draft_grammar_bitmask)` runs. However the drafts for step N+1 were already generated. `_next_draft_grammar_bitmask` didn't apply.
   5. `model_executor.sample_token(step N+1)` runs applying `_next_draft_grammar_bitmask`. However, the mask is stale and doesn't account for the output samples at step N+1 

`_next_draft_grammar_bitmask` is always incorrect and stale by the time it is applied.

To fix this, we'd need to split the `sample_token` step into two, one that samples the tokens, and another generates drafts for step N+1.

Not sure if this will help with performance. As Ben points out, this would add a synchronization point on the async scheduling path (engine-side is blocked by step N's tokens being sampled before it can compute `_next_draft_grammar_bitmask` and schedule step N+1) and defeat async scheduling for any structured outputs request.
