- tjtanaa · comment · 2026-10-17T06:53:01Z · [source](https://github.com/vllm-project/vllm/pull/61790#discussion_r4301797774)

File: `tests/v1/kv_connector/unit/test_umbp_core.py` · line 68

Could we add a layout-planner regression for a `UniformTypeKVCacheSpecs` group containing layers with different page sizes?
The implementation inherited from #61789 currently reads `group.kv_cache_spec.page_size_bytes` for every layer. For this wrapper, that property is the sum of all member layers’ page sizes, not the page size of the current layer. For example, layers with 64-byte and 128-byte pages would each be assigned a 192-byte region.
Please resolve `kv_cache_specs[layer_name]` before constructing each region, and test the per-layer sizes, addresses, and object offsets. A byte-copy round trip with guard regions would also help catch copying beyond the intended page. Using `first_spec` would not fix the unequal-page-size case.

- tjtanaa · comment · 2026-10-17T06:53:23Z · [source](https://github.com/vllm-project/vllm/pull/61790#discussion_r4301798798)

File: `tests/v1/kv_connector/unit/test_umbp_core.py` · line 137

Could we extend namespace coverage to incompatible per-layer specs inside `UniformTypeKVCacheSpecs`?
The namespace implementation inherited from #61789 records the wrapper’s class and `getattr(group.kv_cache_spec, "dtype", None)`, but does not fingerprint its inner specs. Consequently, changing an inner layer’s dtype can leave the namespace unchanged when the other serialized fields stay the same.
Please add a negative compatibility test that keeps the model, revision, layer names, block size, and topology constant while changing an inner layer’s dtype, and assert that the derived namespaces differ. Please also cover compatibility-relevant per-layer geometry and quantization format. Equivalent configurations should still produce the same namespace.
This is particularly important before the later standalone layer enables cross-engine object reuse.
