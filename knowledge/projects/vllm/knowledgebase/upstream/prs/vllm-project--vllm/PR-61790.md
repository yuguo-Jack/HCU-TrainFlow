Thanks for the careful review. All three points are addressed in this PR rather than a separate prerequisite PR, so the regression tests and the fixes land together:

- [`fbfb4514`](https://github.com/vllm-project/vllm/pull/61790/commits/fbfb4514a9) adds the regressions first. On its own they fail (9 failures), demonstrating the existing bugs.
- [`eef3fd6d`](https://github.com/vllm-project/vllm/pull/61790/commits/eef3fd6d3b) sizes each KV region from the layer's own spec.
- [`3f1f9ddf`](https://github.com/vllm-project/vllm/pull/61790/commits/3f1f9ddfd0) fingerprints per-layer specs in the namespace and bumps `layout_version` to 2.
- [`2489de71`](https://github.com/vllm-project/vllm/pull/61790/commits/2489de717f) fixes a related issue found while writing the namespace regression: the scheduler's KV cache config flattens each `UniformTypeKVCacheSpecs` group to one representative layer spec, so the scheduler derived a different namespace from its workers and could never match their objects. Workers now report their namespace through handshake metadata, and the scheduler binds its lookup handle and codec once all workers agree. An explicit `key_namespace` still binds immediately.

With all five commits applied, all 80 tests in `test_umbp_core.py` pass at this PR's head. The runtime-dependent tests moved to #61794.

End-to-end on ROCm with the full series:

- `gemma-4-12b-it` with the hybrid KV cache manager disabled produces a `UniformTypeKVCacheSpecs` group with 131072 B and 32768 B layer pages. Before the fix, worker startup fails with `KV region bytes (5505024) exceed its stride (131072)`. After the fix, 2800 of 2810 prompt tokens restore externally, generated tokens match cold and GPU-cache runs exactly, and logprob deviation matches the GPU prefix-cache hit.
- A tiny GLM-5 checkpoint (MLA + DSA indexer, pages of 18432 B and 2112 B) shows the same pattern: startup failure before the fix, and an exact token match after the fix with 2160 tokens restored externally.

- tjtanaa · comment · 2026-10-17T06:53:01Z · [source](https://github.com/vllm-project/vllm/pull/61790#discussion_r4301797774)

File: `tests/v1/kv_connector/unit/test_umbp_core.py` · line 125

Could we add a layout-planner regression for a `UniformTypeKVCacheSpecs` group containing layers with different page sizes?
The implementation inherited from #61789 currently reads `group.kv_cache_spec.page_size_bytes` for every layer. For this wrapper, that property is the sum of all member layers’ page sizes, not the page size of the current layer. For example, layers with 64-byte and 128-byte pages would each be assigned a 192-byte region.
Please resolve `kv_cache_specs[layer_name]` before constructing each region, and test the per-layer sizes, addresses, and object offsets. A byte-copy round trip with guard regions would also help catch copying beyond the intended page. Using `first_spec` would not fix the unequal-page-size case.

- tjtanaa · comment · 2026-10-17T06:53:23Z · [source](https://github.com/vllm-project/vllm/pull/61790#discussion_r4301798798)

File: `tests/v1/kv_connector/unit/test_umbp_core.py` · line 194

Could we extend namespace coverage to incompatible per-layer specs inside `UniformTypeKVCacheSpecs`?
The namespace implementation inherited from #61789 records the wrapper’s class and `getattr(group.kv_cache_spec, "dtype", None)`, but does not fingerprint its inner specs. Consequently, changing an inner layer’s dtype can leave the namespace unchanged when the other serialized fields stay the same.
Please add a negative compatibility test that keeps the model, revision, layer names, block size, and topology constant while changing an inner layer’s dtype, and assert that the derived namespaces differ. Please also cover compatibility-relevant per-layer geometry and quantization format. Equivalent configurations should still produce the same namespace.
This is particularly important before the later standalone layer enables cross-engine object reuse.

- charxwu · comment · 2026-10-20T05:48:01Z · [source](https://github.com/vllm-project/vllm/pull/61790#discussion_r4321854646)

File: `tests/v1/kv_connector/unit/test_umbp_core.py` · line 194

Fixed in [`3f1f9ddf`](https://github.com/vllm-project/vllm/pull/61790/commits/3f1f9ddfd0). Each group now records a per-layer fingerprint of every field of the layer's own spec, which covers kind, dtype, geometry, and `kv_quant_mode`. `layout_version` is bumped to 2.

`test_namespace_fingerprints_uniform_type_layer_specs` keeps the model, revision, layer names, block size, and topology constant. It checks that changing only an inner layer's dtype, geometry, or quantization changes the namespace, and that an equivalent config keeps it.

While adding this test I found that the scheduler and worker could not agree on the namespace for these models. The scheduler receives a flattened config, so it cannot see per-layer specs. [`2489de71`](https://github.com/vllm-project/vllm/pull/61790/commits/2489de717f) has the workers report their namespace through handshake metadata, and the scheduler adopts it. Tests cover agreement, deferred lookup before the handshake, and rejection of inconsistent or missing reports.
