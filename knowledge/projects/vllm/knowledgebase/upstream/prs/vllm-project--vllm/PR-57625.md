# [Build] Cap default build parallelism by available memory in setup.py

[Upstream PR](https://github.com/vllm-project/vllm/pull/57625) · state: open · merged: False

## Original PR description

## Purpose

Fixes #56717.

`cmake_build_ext.compute_num_jobs()` sizes the build's parallel job count off
the host's CPU core count only (`os.sched_getaffinity(0)` / `os.cpu_count()`)
whenever `MAX_JOBS` is unset. It does not check available memory.

Compiling vLLM's CUDA/C++ extensions can use >1-2GB per `cc1plus`/`nvcc` job.
On hosts with a high core-count-to-RAM ratio (e.g. a 16-thread laptop CPU
with 16GB RAM), the unthrottled default spawns more concurrent jobs than
memory can support, causing heavy swapping, OOM kills, or a system freeze
during source builds.

## Fix

Add a stdlib-only `_available_memory_bytes()` helper using `os.sysconf`
(`SC_AVPHYS_PAGES` * `SC_PAGE_SIZE`), and use it in `compute_num_jobs()` to
cap `num_jobs` by available memory (~2GB/job estimate) whenever `MAX_JOBS`
is not explicitly set. An explicit `MAX_JOBS` override is never
second-guessed. Platforms that don't expose these sysconf names (e.g.
macOS) get `None` back and fall through to the existing unthrottled
behavior, so there's no change for non-Linux hosts.

## Duplicate-work check

Searched `gh issue list` / `gh pr list` for `MAX_JOBS`, `compute_num_jobs`,
and build-parallelism/OOM terms. #45188 addresses an unrelated `MAX_JOBS`
invalid-literal parsing error; no open issue or PR implements
memory-aware job throttling.

## Test plan

Verified the throttling logic with standalone simulation (this machine is
macOS, where `SC_AVPHYS_PAGES` is unsupported, so the memory-aware branch
itself falls back to a no-op here and I could not exercise it end-to-end
via an actual source build):

- 16 cores, 16GB available -> capped to 8 jobs (matches the reported
laptop OOM scenario)
- 16 cores, 128GB available -> unaffected (16 jobs)
- 16 cores, memory unknown (e.g. macOS) -> unaffected (16 jobs, existing
behavior preserved)
- 16 cores, 500MB available -> floors at 1 job, never 0

Ran `pre-commit run --files setup.py` (ruff check, ruff format, mypy,
SPDX headers, etc.) - all pass.

I was not able to run an actual memory-constrained Linux build to confirm
the throttling fires correctly under `os.sysconf`; would appreciate a
Linux-based reviewer confirming behavior on real hardware before merge.
