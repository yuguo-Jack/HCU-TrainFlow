# [Bugfix][Frontend] Preserve finish_reason=length for truncated tool calls

[Upstream PR](https://github.com/vllm-project/vllm/pull/58286) · state: closed · merged: False

## Original PR description

## Purpose

Fixes #58228.

When a non-streaming chat completion produced a parsed tool call but the engine stopped on `max_tokens`, the response reported `finish_reason="tool_calls"`, hiding the `"length"` stop. Clients (e.g. agent frameworks) then execute a possibly truncated tool call instead of retrying with a larger token budget.

This PR only translates an engine `"stop"` into `"tool_calls"` in the non-streaming path, matching the existing `tool_choice="required"` branch. Any other engine finish reason (e.g. `"length"`) is preserved.

The streaming path was fixed the same way in #46303, which was merged while this PR was open; this PR has been rebased on it and now covers only the remaining non-streaming path, so streaming and non-streaming behave consistently.

**Not a duplicate:** #46303 covers streaming only. #57482 addressed the non-streaming path but was closed by its author without review. No other open PR addresses this.

## Test Plan

Added `test_non_streaming_tool_call_finish_reason` in `tests/entrypoints/openai/chat_completion/test_serving_chat.py` (mocked engine, no GPU or model weights needed), parametrized over engine finish reason `stop` → `tool_calls` and `length` → `length`, mirroring the streaming parametrization added in #46303.

    pytest tests/entrypoints/openai/chat_completion/test_serving_chat.py -k "tool_call_finish_reason or n_gt1_independent" -v
    pytest tests/entrypoints/openai/chat_completion/test_serving_chat.py

## Test Result

- **Before the fix:** `test_non_streaming_tool_call_finish_reason[length-length]` fails with `AssertionError: assert 'tool_calls' == 'length'`; `[stop-tool_calls]` passes.
- **After the fix:** both new cases pass, as do the streaming cases from #46303.
- Full test_serving_chat.py on a CPU-only machine (rebased on current main): 183 passed, 0 failed. The server-based GPU tests could not be run locally.

- DaAitch · comment · 2026-10-12T13:16:31Z · [source](https://github.com/vllm-project/vllm/pull/58286#issuecomment-6125047577)

We independently reproduced the nonstreaming bug addressed by this PR and verified a local fix over HTTP. Here are our results in support of this PR.

Environment: NVIDIA `vllm:26.09-py3`, vLLM `0.29.0+5013de39.dev`, model `unsloth/Qwen3.8-27B-NVFP4`, tool parser `qwen3_coder`, reasoning parser `qwen3`, running on OpenShift with an NVIDIA RTX PRO 6000 Blackwell Max-Q Workstation Edition.

We used a simple `echo_payload(text)` tool with a required string argument, `tool_choice="auto"`, temperature 0, thinking disabled and `stream=false`. We tested 13 token budgets (`8, 16, 24, 32, 48, 64, 76, 78, 80, 82, 84, 96, 256`), twice each, for both Chat Completions and Responses: 52 requests per run, with four concurrent requests within each API.

| Check | Before our finish-reason fix | After |
| --- | --- | --- |
| Chat: 22 budget-limited requests | 22/22 incorrectly reported `tool_calls` | 22/22 correctly reported `length` |
| Chat: 4 complete controls | 4/4 exact arguments, `tool_calls` | Unchanged |
| Responses: 22 budget-limited requests | 22/22 global `incomplete`, reason `max_output_tokens` | Unchanged |
| Responses: 4 complete controls | 4/4 exact arguments, `completed` | Unchanged |

The requests and returned tool arguments were identical before and after the fix in all 52 cases. The change corrected Chat's termination status.

One concrete example: at a budget of eight tokens, the actual decoded output was only:

```text
<tool_call>
<function=echo_payload>
```

Chat nevertheless returned a tool call with `arguments="{}"` and `finish_reason="tool_calls"`. Near the completion boundary, arguments could already be complete while the engine still stopped on the token limit. Both cases need to retain `length`.

Our local patch simply gives `output.finish_reason == "length"` priority over `tool_calls`. **We have not run this PR's patch directly.** Our results support its handling of `length` and normal completion; they do not validate every other finish reason covered by its broader approach of relabeling only `stop`.

For completeness, Responses preserved the global cutoff status, but individual function-call items still reported `completed`. We therefore checked the overall response status before considering any tool call executable.

<summary>Deterministic before/after check (no GPU or inference required)</summary>

This checks the actual finish-reason expression from the server source and applies our patch **in memory only**. It complements the HTTP measurements above; it does not reproduce the 52-request API run.

Save as `check_finish_reason.py`, then run it against the original, unpatched file:

```bash
python3 check_finish_reason.py /path/to/vllm/entrypoints/openai/chat_completion/serving.py
```

```python
import ast
import hashlib
import sys
from pathlib import Path
from types import SimpleNamespace

# Pass the original, unpatched serving.py from the tested build.
source = Path(sys.argv[1]).read_text()
assert hashlib.sha256(source.encode()).hexdigest() == (
    "ea1f76074a9587c8054f54d30a6ba748b6a5fc4d90dd82c801504505c1da1f92"
), "Expected the original NVIDIA 26.09 / upstream v0.29.0 source"

before = '                finish_reason="tool_calls"\n'
after = ('                finish_reason="length"\n'
         '                if output.finish_reason == "length"\n'
         '                else "tool_calls"\n')
assert source.count(before) == 1
patched = source.replace(before, after)
compile(patched, "patched_serving.py", "exec")

for label, text in (("original", source), ("patched", patched)):
    nodes = [n.value for n in ast.walk(ast.parse(text))
             if isinstance(n, ast.keyword) and n.arg == "finish_reason"
             and "is_finish_reason_tool_calls" in ast.unparse(n.value)]
    assert len(nodes) == 1
    expression = compile(ast.Expression(nodes[0]), "finish_reason", "eval")
    failures = []
    for reason in ("length", "stop", None):
        for has_tools in (False, True):
            expected = ("length" if reason == "length" else
                        "tool_calls" if has_tools else reason or "stop")
            actual = eval(expression, {
                "output": SimpleNamespace(finish_reason=reason),
                "is_finish_reason_tool_calls": has_tools,
            })
            if actual != expected:
                failures.append((reason, has_tools, actual, expected))
    print(label, "failures:", failures)
    assert failures == ([("length", True, "tool_calls", "length")]
                        if label == "original" else [])
```

Expected output:

```text
original failures: [('length', True, 'tool_calls', 'length')]
patched failures: []
```

The check covers `length`, `stop` and the existing `None` fallback, each with and without a parsed tool call. The hash guard deliberately restricts this reproducer to the source we tested.
