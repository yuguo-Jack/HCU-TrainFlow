# [Bugfix][Rust Frontend] Fail token-less streams in vllm-bench openai-chat

[Upstream PR](https://github.com/vllm-project/vllm/pull/59736) · state: closed · merged: True

## Original PR description

## Purpose

Fixes #59722.

The `openai-chat` backend in the Rust `vllm-bench` marked a request as successful whenever the stream ended cleanly, even if no token ever showed up. The completions backend and Python `vllm bench serve` only count it as a success once the first token arrives, so chat was the odd one out.

So a 200 response with no tokens got counted as a success, with `ttft`, `latency` and `output_tokens` all left at their defaults. Thanks to @aron-intframe for pointing out in the issue that this goes beyond Mean TTFT:

- Mean TTFT and Mean E2EL get pulled down, since both are `0` for those requests.
- The `1 + output.itl.len()` fallback in `metrics/calculator.rs` counts each one as a phantom output token, which inflates total output tokens and output throughput.
- They pass every goodput SLO, because TTFT/TPOT/E2EL are all `0`.

The fix gates `success` on the `first_token_received` flag that's already there, and fails the request with the same error as the completions backend and Python. That message now lives in a shared `NO_VALID_CHUNK_ERROR` const so the two backends can't drift apart.

This also lines up with #64626 (thanks @dilberx). That PR stopped counting vLLM's opening role chunk as a token, so the stream vLLM actually sends when it generates nothing (a role chunk, then usage) now reaches this check and fails as it should.

**Heads up for multi-turn:** `multi_turn.rs` branches on `output.success`. Right now a token-less turn gets appended to the history as an empty assistant message and the run keeps going. After this change that turn is reported as failed, like any other failed turn, which is what the completions backend and Python already do.

## Not a duplicate

Claimed in #59722. Other PRs that touch `openai_chat.rs`:

- #55809 adds server queue time / TTFT to the detailed results, which is a different change.
- #59694 (mine, merged) changed the usage-chunk block a few lines up. This branch is rebased on top of it.
- #64626 (merged) decides which chunks count as tokens, and this PR decides what happens when none do, so the two fit together.
- #57519 handles server error events, but only on the Python side.

## Test Plan

Two new tests in `openai_chat::tests`:

- `test_tokenless_stream_is_failed`: the local SSE test server sends zero token chunks, then usage and `[DONE]`.
- `test_role_only_stream_is_failed`: the role chunk plus usage that vLLM sends when nothing is generated. It uses the `run_chat` helper from #64626, and thanks @esmeetu for suggesting it.

Both check that `success == false` and `error == NO_VALID_CHUNK_ERROR`.

```bash
cargo test -p vllm-bench --lib
cargo clippy -p vllm-bench --all-targets --locked -- -D warnings
cargo fmt --all -- --check
```

For the end-to-end check, I used a mock OpenAI-compatible server that returns 200 with only the usage chunk and `[DONE]` for every 8th request, run with `--dataset-name random --random-input-len 100 --random-output-len 8 --num-prompts 32 --max-concurrency 8`.

## Test Result

- `cargo test -p vllm-bench --lib`: 225 passed on current `main`. Clippy and fmt are clean.
- If I revert the fix, both new tests fail.

End-to-end against the mock server. I re-ran the Rust rows after the rebase and got the same counts (28 ok, 4 failed, 224 tokens). The mock doesn't send a role chunk, so that case is covered by the unit test instead.

| client | Successful | Failed | Total generated tokens | Mean TTFT |
|---|---|---|---|---|
| Python `vllm bench serve` (`openai-chat`) | 28 | 4 | 224 | 212.28 ms |
| Rust `vllm-bench` (`openai`), reference | 28 | 4 | 224 | 203.13 ms |
| Rust `vllm-bench` (`openai-chat`), before | 32 | 0 | 228 | 178.32 ms |
| Rust `vllm-bench` (`openai-chat`), after | 28 | 4 | 224 | 202.93 ms |

In the "before" row you can see the four phantom output tokens (228 vs 224) and the TTFT skew. With the fix, chat matches the completions backend and Python.
