# [Kernel] Support SiTU in UnfusedOAITritonExperts

[Upstream PR](https://github.com/vllm-project/vllm/pull/63978) · state: open · merged: False

## Original PR description



## Overview

`UnfusedOAITritonExperts` now accepts SiTU, giving Kimi-K3 MXFP4 MoE layers a native backend on GPUs without an AITER SiTU kernel, e.g. MI250X (gfx90a).

## Claims

- Kimi-K3 (`moonshotai/Kimi-K3`, MXFP4) serves on 4 nodes x 8 MI250X GCDs with `--moe-backend triton_unfused`; without this change no native backend accepts SiTU there and `EMULATION` is used.
- GSM8K (full test set, 1319 questions, greedy): 97.50% (see Validation).
- One-line change; the activation already exists in `apply_moe_activation`.

## Validation

New `test_unfused_oai_triton_moe_situ` in `tests/kernels/moe/test_modular_oai_triton_moe.py` compares the unfused Triton MoE with SiTU (Kimi-K3's `beta=4.0`, `linear_beta=25.0`) against a torch reference, for the existing MNK cases.

On 1x MI250X GCD, vLLM v0.31.0 ROCm image with this change bind-mounted:

```
pytest tests/kernels/moe/test_modular_oai_triton_moe.py -k situ
# without this change:
E       AssertionError: assert False
E        +  where False = <function UnfusedOAITritonExperts._supports_activation ...>(<MoEActivation.SITU: 'situ'>)
5 failed
# with this change, whole file:
pytest tests/kernels/moe/test_modular_oai_triton_moe.py
26 passed
```

Model evaluation, Kimi-K3, 4 nodes x 8 MI250X (LUMI), TP=8 PP=4, `--enable-expert-parallel --moe-backend triton_unfused`, CUDA graphs, max-model-len 8192:

| Eval | Result |
| --- | --- |
| GSM8K, 1319 questions, greedy, chat, answer = last number, max 2048 tokens, `--gpu-memory-utilization 0.88` | 97.50% (1286 correct; 31 wrong; 2 client timeouts counted as wrong) |
| Throughput, 128-token outputs | 6.8 tok/s at 1 request; 110 / 178 / 193 tok/s at 64 / 128 / 256 concurrent |

Without this change (same setup, automatic selection) the engine selects `EMULATION`.

## Details

- Root cause: `UnfusedOAITritonExperts` runs GEMM1, then the activation through the base `activation()` → `apply_moe_activation` (which implements SiTU with `activation_situ_beta`/`activation_situ_linear_beta` from the MoE config), then GEMM2. Its `_supports_activation` list omitted SiTU.
- SiTU takes the `[gate | up]` layout (as SiLU does), not the interleaved layout of SWIGLUOAI; the MXFP4 weight conversion for `TRITON_UNFUSED` already keeps that layout. This matches the contiguous `[w1; w3]` layout listed for SiTU on `TRITON_UNFUSED` in #52240. The test helper `make_weights()` gains an `interleave_gate_up` switch and pads each half separately so the split point stays in the middle; existing callers are unchanged.
- Limitation (existing code, not changed here): the unfused path accumulates expert outputs in a temporary float32 tensor (\`acc.index_add_(..., down.to(torch.float32))\`) whose size follows how many tokens reach a rank's experts. With expert parallelism and 128 concurrent prefills, real routing exceeded what memory profiling reserved and one rank ran out of memory at \`--gpu-memory-utilization 0.95\`; the evaluation uses 0.88.
- Not a duplicate: no open PR adds SiTU to the OAI Triton experts.
