# [ROCm][Perf][MLA] Use AITER Triton bf16 BMM for the decode W_UV when tuned

[Upstream PR](https://github.com/vllm-project/vllm/pull/63397) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

On ROCm, run the MLA decode W_UV up-projection (`MLAAttention._v_up_proj`) on AITER's Triton bf16 batched GEMM when AITER has a tuned config for the layer's exact shape; otherwise keep `torch.bmm`. With the Kimi-K2.6 config from ROCm/aiter#6780 this speeds up Kimi-K2 / K2.5 / K2.6 decode at TP8 on MI355X.

All numbers below were measured with #61863 (now merged) applied to both the baseline and this PR; without it, Kimi-K2.6 takes the FP8 MLA prefill path, which produced wrong output (GSM8K 0.027 vs 0.93).

Requires AITER with ROCm/aiter#6780 (merged `c617bd42f2`, included in v0.1.27; the vLLM image bump is #63774).

## Claims

- Kimi-K2.6 MXFP4, TP8, MI355X: the decode W_UV GEMM drops from 9.1 µs to 5.0 µs per layer (hipBLASLt → AITER Triton), about 260 µs per decode step at 64 tokens.
- Serving: mean TPOT −3.0% at 1k/1k c=16, −2.2% at c=128 and −2.3% at 1k/8k c=64; at 1k/1k c=64, −3.4% with 256 prompts and +0.3% with 640 prompts.
- Same bf16 weights and math as `torch.bmm`; GSM8K and GPQA Diamond are unchanged within stderr.
- Only the W_UV kernel changes. Shapes AITER has no tuned config for keep `torch.bmm`.

## Details

- **Dispatch rule.** `rocm_aiter_ops.is_triton_bf16_bmm_tuned(B, M, N, K)` asks AITER's config lookup whether the exact shape has a tuned entry on the current GPU (cached per shape). It reuses `_triton_gemm_config_is_tuned`, which now takes optional `M` and `B`, and follows `is_triton_gemm_w8a8_tuned`. There is no env var or model check; FP4/FP8 BMM still take precedence.
- **Scope with ROCm/aiter#6780.** The config is keyed on 8 heads (`B=8-N=128-K=512`), so it applies to the Kimi-K2 family at TP8, and to DeepSeek-V3 at TP16, which has the same per-GPU shape. AITER's lookup never reports an `any` entry as tuned, so the 16,384-token `any` config is not used: above 128 decode tokens W_UV stays on `torch.bmm`.
- **Safety.** `_v_up_proj` runs inside the MLA attention custom op, so torch.compile doesn't trace into the Triton call, and CUDA graphs capture it per batch size. It uses vLLM's existing strided views; there are no copies or weight changes.
- **Test.** `test_mla_v_up_proj_runs_tuned_aiter_triton_bf16_bmm` (ROCm only) uses a shape AITER already ships tuned gfx942/gfx950 configs for (N=1024, K=4096), so the real tuned lookup passes in CI without patching. It checks via the profiler that the AITER kernel ran, and compares against the `torch.bmm` path it replaces. Kimi's own shape needs the new AITER config, which the CI image may not have yet; it was validated on MI355X as above. The test reuses the existing hand-built `MLAAttention` setup in `test_mla_backends.py` (now a shared `_bare_mla_layer` helper) and runs in the MI355 V1 Attention step.
- **Not a duplicate.** Open PRs searched for `batched_gemm_bf16`, `_v_up_proj` and AITER bf16 BMM: #53003 and #61926 use AITER's `batched_gemm_bf16` for DeepSeek-V4's einsum (a different call site); #36297 and #59856 fuse FP8 output quantization into `_v_up_proj`; #55741 refactors MLA BMM selection into an `MLABmm` abstraction without a Triton bf16 path. This change would fit #55741 as one more implementation.
- **Limitation.** "Tuned in AITER" is taken to mean faster than hipBLASLt. AITER's tuner compares Triton configs against each other, not against `torch.bmm`; for this shape it holds in every bucket exercised above.
