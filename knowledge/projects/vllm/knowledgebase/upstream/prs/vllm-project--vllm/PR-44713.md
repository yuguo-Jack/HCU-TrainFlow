# [Rust Frontend] Add Granite tool and reasoning parsers

[Upstream PR](https://github.com/vllm-project/vllm/pull/44713) · state: closed · merged: False

## Original PR description

### Summary

Adds Rust-frontend parser support for the Granite model family (tracking: #44280), mirroring the existing Python parsers as three self-contained, additive modules:

- **Granite reasoning parser** (`granite`, covers 3.x and 4) — plain-text phrase delimiters (`Here is my thought process:` / `Here is my response:`), not special tokens.
- **Granite 3.0/3.1 tool parser** (`granite`) — optional `<|tool_call|>`/`<tool_call>` marker followed by a JSON array of `{"name","arguments"}` calls.
- **Granite 20B FC tool parser** (`granite-20b-fc`) — one `<function_call>` marker per call (repeated, no closing marker), each followed by a `{"name","arguments"}` JSON object.


### Notes

- **Reasoning is a custom parser** because Granite's markers are multi-word phrases rather than single vocab tokens, so `DelimitedReasoningParser` doesn't fit; it runs a small before-think → reasoning → content phase machine.
- `granite4` standalone parser split out to #45216

- tahsintunan · comment · 2026-06-16T12:25:32Z · [source](https://github.com/vllm-project/vllm/pull/44713#issuecomment-4718706796)

For v3, reusing the shared core isn't really possible. The payload is a JSON array of calls and the core has no array concept (only a delimiter between bare objects), plus the leading marker is optional and can be either form. So it needs its own grammar.

For 20b we could reuse it, except for one thing: it drops the text between and after tool calls (only the prefix is content), and the shared core does the opposite and emits that text. So 20b would come out wrong if we just reuse it as-is.

And it's not just 20b, that drop is the shared Python convention (hermes, internlm2, seed_oss, deepseek all do it). Which means the core already diverges from Python for hermes/internlm2 today, the hermes streaming test even bakes in normal_text "preface  suffix" where Python gives just "preface ".

So if this divergence is not intentional, I'd keep 20b standalone for now since it's the parity-correct one, and fix the core's content handling in a separate PR (which also fixes hermes/internlm2). Then 20b can move onto the shared core on top of that. wdyt @BugenZhao?
