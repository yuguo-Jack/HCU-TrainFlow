# [Bugfix][Multimodal] Honor RGB PNG transparency when loading images

[Upstream PR](https://github.com/vllm-project/vllm/pull/61986) · state: closed · merged: True

## Original PR description



## Overview

An RGB PNG can mark one color as transparent with a tRNS chunk. vLLM loads such images as opaque, so the transparent pixels keep their hidden color instead of the white (or `rgba_background_color`) background that RGBA and palette images get. This covers the RGB case that #44974 meant to handle (`_has_transparency` lists tRNS in RGB PNGs) but that the same-mode early returns skip.

## Claims

- Transparent pixels of RGB PNGs with a tRNS chunk are now filled with the default white or the configured `rgba_background_color`, both for image URLs/data URLs and for PIL images passed offline, so the two pipelines give the same pixels.
- Opaque RGB images and `image_mode=None` are handled as before.

## Details

`convert_image_mode` returned `image` when `image.mode == to_mode`, before `_has_transparency` was checked, and `ImageMediaIO._convert_image_mode` had its own same-mode return before calling it. I moved the same-mode return in `convert_image_mode` after the transparency check, and `ImageMediaIO` now calls `convert_image_mode` for every conversion instead of special-casing RGBA (which `convert_image_mode` already composites the same way).

The automated review pointed out that `Image.open(gif).convert("RGB")` keeps the GIF's transparent color in `info`, so opaque pixels that share that color are treated as transparent too. The second commit applied the color key only to images vLLM decodes itself, but that made the offline and online pipelines disagree: Pillow saves `info["transparency"]` as a tRNS chunk, so the same image sent to the server as a PNG was still composited. Following review, the third commit goes back to handling it in `convert_image_mode` for both pipelines, which also matches what Pillow's `convert("RGBA")` does with that image, and replaces the unit test with the offline vs online comparison above.

The docs said the background color only applies to RGBA images; I updated them to say it applies to images with transparency, including tRNS PNGs.

Duplicate check: I searched open and closed PRs and issues for transparency, tRNS, `convert_image_mode`, `ImageMediaIO`, `rgba_background_color` and the file paths. #44974 (merged) added the tRNS handling but kept both same-mode returns. Open PRs touching these files are #60308 (decompression-bomb errors as HTTP 400) and #57752 (a "don't merge" lazy-decoding experiment that keeps the same-mode return); neither changes this.

File: `vllm/multimodal/image.py` · line 113

🔴 Offline users who flatten a GIF or palette PNG with `.convert("RGB")` now get every pixel matching the old transparent colour painted white. Opaque pixels of that colour are hit too. Pillow keeps `info["transparency"]` as an RGB tuple after P->RGB conversion. `_has_transparency` now sends these already-RGB images to `convert("RGBA")`, which matches by colour, not palette index. Fix: apply the RGB colour-key composite only to freshly decoded files, e.g. `ImageMediaIO.load_bytes` or `image.format == "PNG"`. In-memory RGB images should keep the mode-match early return.

<details>
<summary>Why this was flagged</summary>

Trigger: offline `LLM.generate` with a PIL image built as `Image.open(gif_or_P_png).convert("RGB")`. Pillow's convert keeps `info["transparency"]` on P->RGB as the RGB value of the transparent palette entry, e.g. (0, 0, 0). The image reaches `convert_image_mode(normalize_image(item), "RGB")` at vllm/multimodal/parse.py:773. Before this change the early return at old image.py:107 gave the image back untouched. Now image.py:107 sees `_has_transparency` true and runs `image.convert("RGBA")`, a colour-key conversion. Every pixel equal to that RGB value becomes alpha 0 and is filled with white by `rgba_to_rgb`. That includes pixels from other, opaque palette indices that share the colour, such as black text when the transparent entry is (0,0,0). The model sees a corrupted image that matches neither the user's RGB pixels nor the original indexed transparency. Nothing guards against this: `_has_transparency` cannot tell decoder-supplied tRNS from metadata left over after a user's convert.

**Verification:** The diff moves the same-mode return in `convert_image_mode` (vllm/multimodal/image.py:107-115) below the transparency branch. Pillow's `Image.convert` keeps `info["transparency"]` on P->RGB. Every pixel with that RGB value gets alpha 0, including pixels from a different, opaque palette index that shares the colour.

</details>
