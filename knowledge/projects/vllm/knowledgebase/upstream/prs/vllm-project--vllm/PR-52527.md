# [Metrics] Report shared-prefix tokens lost to a missing sparse-retention checkpoint

[Upstream PR](https://github.com/vllm-project/vllm/pull/52527) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Adds a counter and startup message that explain when a hybrid model loses prefix-cache reuse because a Mamba or sliding-window group has no usable saved state. This helps operators understand why repeated prompts still need processing. Relates to #45238.

## Claims

- Reports shared-prefix tokens lost to missing sparse state through `vllm:prefix_cache_sparse_retention_misses`.
- Fixes attribution: dense-cache eviction and EAGLE's required replay/alignment are excluded from this counter.
- Explains at startup when zero retention keeps only selected checkpoints. Cache-hit decisions and model computation are unchanged.

## Details

The original counter subtracted the final hit from the shared-prefix retention boundary. That boundary can also include tokens lost to dense eviction or EAGLE replay, so it could incorrectly blame sparse retention. The coordinator now records reductions made by sparse groups during the existing lookup. Sliding-window diagnostics separate intentional EAGLE costs using the same cache queries, and the request carries the result to admission-time statistics.

The existing boundary still controls checkpoint retention. This change adds no cache lookups, changes no hit decisions and adds no GPU synchronization.

Issue and open PR searches for #45238, the metric name and sparse retention found no other open PR exposing this counter. Related PRs such as #50551, #53479, #57613 and #58549 change checkpoint retention or materialization; this PR reports missing-state losses. The startup message from the closed #53596 is consolidated here, with @jschmied's authorship preserved through the rebase.

### End to end

`Qwen3.5-4B` (AWQ 4-bit), single GPU, `--enable-prefix-caching --enforce-eager`, `--max-model-len 8192`, concurrency 1, 32 prompts over 8 prefix groups. Engine selected `mamba_cache_mode="align"` and `block_size=528`, matching the geometry in #45238. Workloads are `vllm bench serve --dataset-name prefix_repetition`, differing only in where the 1584-token block boundary falls:

| | 1600 / 600 (boundary inside shared prefix) | 1500 / 700 (boundary in unique tokens) |
|---|---|---|
| `prefix_cache_queries` | 70,400 | 70,400 |
| `prefix_cache_hits` | 38,016 (54.0%) | 17,952 (25.5%) |
| **`prefix_cache_sparse_retention_misses`** | **0** | **8,448** |
| Mean TTFT | 245.95 ms | 300.25 ms |

The counter stays at exactly zero on the healthy workload and reports 8,448 tokens (16 × 528, whole blocks) on the geometry-unlucky one, alongside a halved hit rate and a 22% TTFT regression that is otherwise unattributable.

Note the unlucky case is 25.5%, not 0% — the Marconi admission policy (#37898) recovers most of it. The original 0% case from #45238 was not reproduced in that tested main build; the measurements above show the residual loss this counter is intended to expose.

Independent reproduction: @jschmied traced the same found-then-discarded pattern live on a GB10 (https://github.com/vllm-project/vllm/pull/52527#issuecomment-5398286287) — Qwen3.8-27B-NVFP4 hybrid GDN, MTP, block size 1,600, measured at the default `prefix_cache_retention_interval=0`. The default cost one extra cold prefill per fresh prefix on unaligned prompts there (first hit on request 3 rather than 2), with hit amounts unchanged once warm.

- Sahil170595 · comment · 2026-09-26T02:23:46Z · [source](https://github.com/vllm-project/vllm/pull/52527#issuecomment-5842346699)

Self-review summary, plus a small test update pushed today.

**What this does:** adds a Prometheus counter, `vllm:prefix_cache_sparse_retention_misses`, for shared-prefix tokens that some KV cache group matched but that were not reused because a sparse-retention group (align-mode Mamba or sliding window) held no checkpoint at that position. It also logs once at startup when `prefix_cache_retention_interval` is 0 on a model that has such a group (jschmied's commit, consolidated from #53596).

**Why:** on hybrid models the prefix-cache lookup intersects the per-group hits, so when the Mamba group has no checkpoint at a shared prefix, the attention group's match is discarded and the request looks like a plain miss. `vllm:prefix_cache_hits` cannot tell "these requests share nothing" apart from "they share a prefix, but a checkpoint was missing". The coordinator already computes the size of that gap to pin the shared-prefix junction, so the counter records it: the pinned boundary minus the hit that was actually used.

**Self-review changes:** the existing metric tests called `record_prefix_cache_stats()` directly with a hand-set `shared_prefix_boundary`, so nothing checked that `schedule()` stores the lookup's boundary on the request before the admission-time stats call reads it. The new `test_sparse_retention_miss_recorded_at_admission` in `tests/v1/core/test_scheduler.py` drives a vetoed hybrid lookup through `schedule()` and reads the counter back from `make_stats()`; with that boundary store removed from `schedule()` it fails, so it now guards the wiring. The clean-hit test also asserts its 4-block hit now, since it could otherwise pass without any hit.

- tzulingk · comment · 2026-11-03T01:34:09Z · [source](https://github.com/vllm-project/vllm/pull/52527#issuecomment-6593074489)

Thanks for this. It fills a real gap: today a vetoed hybrid lookup looks exactly like "no shared prefix". I read the head (56281bdc; line numbers below are from it) and ran the new tests plus two extra unit cases on CPU. I have four suggestions.

**1. Preempted re-admissions are counted, but `queries`/`hits` skip them.** `PrefixCacheStats.record` adds the value before the `if preempted:` return (`vllm/v1/metrics/stats.py:152`). `_preempt_request` resets `num_computed_tokens` to 0 (`scheduler.py:1594`), so every re-admission runs the lookup and records again (`scheduler.py:950`, `:1305`). A request preempted k times is added k+1 times here but only once to `vllm:prefix_cache_queries`. On re-admission the lookup can also span the request's own generated tokens. If I take your vetoed-lookup test and set `num_preemptions = 1`, I get `queries=0, hits=0, sparse_retention_misses=32`. Preemption is most common under KV pressure, which is also when these losses matter, so a misses/queries ratio gets skewed. Suggestion: record after the early return, or add a separate `preempted_sparse_retention_misses` the way `preempted_hits` works, and drop "Counted for preempted and new requests alike".

**2. With fine-grained hits, part of the value cannot be recovered by any retention setting.** When `prefix_match_unit` is smaller than the Mamba block, full attention hits at hash granularity. Mamba states, though, are only cut at block-floored junctions unless `enable_mamba_shared_prefix_checkpoint` is set (`scheduler.py:516-526`). My test used a 16-token hash unit, 64-token Mamba blocks and an 80-token shared prefix, with the seed chunked at 64. With `retention_interval=None`, the hit is 64 tokens and the counter is 16 tokens. With `retention_interval=0`, the hit is 0 and the counter is 80 tokens. Those 80 tokens are 64 tokens of missing state plus the same 16-token tail. Under dense retention those 16 tokens recur on every such request. They read as "raise retention", but retention cannot fix them. The loop already has the values for an O(1) split:
```python
if isinstance(spec, MambaSpec):
    upper = min(curr_hit_length, longest_hit_length)
    floor = round_down(upper, group_block_size)
    self.state_granularity_misses += max(upper - max(_new_hit_length, floor), 0)
    self.sparse_retention_misses += max(floor - _new_hit_length, 0)
```
Block-aligned mode needs no split. `FullAttentionManager.find_longest_cache_hit` already rounds the hit down to `scheduler_block_size` (`single_type_kv_cache_manager.py:853`), so that tail never reaches the counter.

**3. The name implies a cause that the value does not always have.** Your own `test_sparse_retention_misses_exclude_sliding_window_eagle_drop[evict=True]` expects 32 tokens with `retention_interval=None`. That loss comes from eviction of window blocks, not from retention. A cause-neutral description would keep dashboards honest, for example: "not reused because a Mamba / sliding-window group had no state there: sparse retention, state eviction, or block granularity". A `group_type` label would do the same.

**4. Docs: connector paths.** The value covers only the local lookup. With a connector that lacks `supports_divergent_local_hybrid_hits` (OffloadingConnector, LMCache, or a MultiConnector unless every child supports it), these tokens may be loaded through the connector instead of recomputed. On a P/D decode instance, they are transferred from the prefill side again. With NIXL, and on current main also Mooncake and MoRIIO in their state-pulling modes, `get_computed_blocks_for_connector` sets the value to 0 (`kv_cache_manager.py:348`). It is counted only when the lookup falls back to `get_computed_blocks`. One sentence about this in `docs/design/metrics.md` would prevent misreadings on P/D deployments.
