# [MoE] Generalize unquantized backend fallback for all quantization-only backends (follow-up to #60219)         

[Upstream PR](https://github.com/vllm-project/vllm/pull/56964) · state: open · merged: False

## Original PR description

## Purpose
Fixes #56832.

When serving quantized base models (such as `Qwen3.8-Flash-Next NVFP4`) alongside speculative decoding (e.g. MTP draft models) or when layers are excluded via `modules_to_not_convert`, passing `--moe-backend marlin` sets `moe_config.moe_backend = "marlin"` across the engine.

When `select_unquantized_moe_backend()` is called for the unquantized draft layers, it attempts to resolve `marlin` through `map_unquantized_backend()`, which raises:
```text
ValueError: moe_backend='marlin' is not supported for unquantized MoE. Expected one of ['triton', 'batched_triton', 'flashinfer_trtllm', 'flashinfer_cutlass', 'aiter'].
```

Following the precedent in commit `d891b9bd` for the quantization-only backend `"humming"`, this PR allows `"marlin"` to fall through to `"auto"` when selecting backends for unquantized MoE layers. This enables the quantized base model to run with Marlin kernels while unquantized layers gracefully fall back to an available unquantized backend (e.g. Triton or FlashInfer).

cc @secinto @BrightMoon-000 for verification against your speculative MTP setups.

Hit the same bug from the other end — same model as in your description (Qwen3.8-Flash-Next NVFP4 +
MTP), but with `--moe-backend flashinfer_b12x`. **This PR as written would not fix that case**, and I
think the allowlist is the reason.

`flashinfer_b12x` is not in `["auto", "humming", "marlin"]`, so it still reaches
`map_unquantized_backend()` and raises at drafter construction:

```
ValueError: moe_backend='flashinfer_b12x' is not supported for unquantized MoE.
   Expected one of ['triton','batched_triton','flashinfer_trtllm','flashinfer_cutlass','aiter'].
-> Engine core initialization failed
```

`MoEBackend` has ~22 values and only 5 have unquantized equivalents, so every other one is
quantization-only by construction — `flashinfer_b12x`, `deep_gemm`, `cutlass`, `flashinfer_cutedsl`,
`marlin`, `humming`, and whatever is added next. Each will need its own allowlist entry.

Inverting the test covers them all, and makes the `humming` special case disappear:

```python
_UNQUANTIZED_BACKEND_MAP = {  # hoisted out of map_unquantized_backend()
    "triton": UnquantizedMoeBackend.TRITON,
    "batched_triton": UnquantizedMoeBackend.BATCHED_TRITON,
    "flashinfer_trtllm": UnquantizedMoeBackend.FLASHINFER_TRTLLM,
    "flashinfer_cutlass": UnquantizedMoeBackend.FLASHINFER_CUTLASS,
    "aiter": UnquantizedMoeBackend.AITER,
}

runner_backend = moe_config.moe_backend
if runner_backend != "auto" and runner_backend not in _UNQUANTIZED_BACKEND_MAP:
    logger.info_once(
        "moe_backend='%s' is quantization-only; using 'auto' for this "
        "unquantized MoE layer.", runner_backend)
    runner_backend = "auto"
if runner_backend != "auto":
    ...
```

Measured on DGX Spark GB10 (`sm_121`), Qwen3.8-Flash-Next NVFP4 (E=512, K=2560, N=640, top-k=10),
`--moe-backend flashinfer_b12x` with `mtp` / `num_speculative_tokens=3`, no `speculative_config.moe_backend`
set:

| | result |
| --- | --- |
| stock, and with this PR's allowlist | `ValueError` at drafter construction, server never starts |
| with the inverted check | **serves in 720 s**, generates correctly |

and the drafter logs the fall-through once:

```
moe_backend=flashinfer_b12x is quantization-only; using auto for this unquantized MoE layer.
Unquantized MoE backend out of potential backends: ['FlashInfer TRTLLM','FlashInfer CUTLASS','TRITON','BATCHED_TRITON']
```

while the body keeps b12x (`nvfp4.py:261 Using 'FLASHINFER_B12X' NvFp4 MoE backend`, both the worker
and the PLE offload worker). That was the first time this model has run b12x with MTP at all.

Two notes in case they are useful:

- Your unit tests parametrise `humming` and `marlin`; adding a quantization-only backend that is
  *not* on the allowlist (e.g. `flashinfer_b12x` or `deep_gemm`) would fail against the current diff
  and pass against the inverted form, which makes the distinction explicit in CI.
- `speculative_config.moe_backend` is the other route to this, and it was fixed for Model Runner V2
  in #54788 — but it only helps when the user sets it. The fall-through is what makes the default
  case work, so I think both are worth having.

Happy to test any revision on this hardware; the repro is one `vllm serve` invocation.
