# [Bugfix][Attention] Keep FlashInfer TRTLLM prefill query offsets in a persistent buffer

[Upstream PR](https://github.com/vllm-project/vllm/pull/65598) · state: open · merged: False

## Original PR description

## Purpose

Fix an illegal memory access / segfault during CUDA graph replay of the standalone draft-model prefill on Blackwell (SM100), reported in https://github.com/vllm-project/vllm/pull/60989#issuecomment-6620438731.

Since #60989, the standalone draft model (`method: "draft_model"`) captures FULL CUDA graphs for its prefill. That prefill is a uniform batch of `num_speculative_tokens + 2` tokens per request, because it adds a correction token. That is one token more than FlashInfer's `reorder_batch_threshold` (`1 + num_speculative_tokens`). The builder therefore classifies every request as a prefill and, on SM100, takes the TRTLLM prefill path.

On that path, `build()` allocated `cum_seq_lens_q` as a new tensor (`qo_indptr[prefill_start:] - qo_indptr[prefill_start]`). Attention metadata is built outside the graph, so a FULL graph keeps the address that tensor had at capture time. The tensor is freed after capture and its memory is reused. At replay, the attention kernel reads query offsets from that reused memory. The result is wrong drafts or, for large batches, `CUDA error: an illegal memory access` or a segfault in `cuGraphLaunch`.

This PR writes the offsets into a persistent buffer owned by the builder, the same way `paged_kv_indptr` already works, so every build updates the memory the graph reads. The other tensors on this path (`seq_lens`, `block_tables`, `cum_seq_lens_kv`) are already views of persistent buffers.

Not covered here: with an FP8 KV cache and a non-FP8 query, the same path also makes a contiguous copy of `block_tables` on each build, which would have the same problem under a FULL graph. That configuration was not tested, so this PR leaves it alone.

## Test Plan

- New unit test `tests/v1/attention/test_flashinfer_trtllm_prefill_cudagraph.py`. It builds TRTLLM prefill metadata twice, for uniform batches wider than the reorder threshold, and checks that `cum_seq_lens_q` holds the right offsets and stays at the same address.
- End to end on 1x GB200 with model runner V2:

```bash
VLLM_USE_V2_MODEL_RUNNER=1 vllm serve Qwen/Qwen3-8B \
  --max-model-len 4096 --max-num-seqs 256 \
  --speculative-config '{"method": "draft_model", "model": "Qwen/Qwen3-0.6B", "num_speculative_tokens": 3}'

python tests/evals/gsm8k/gsm8k_eval.py --port 8000 --num-questions 1319 \
  --max-concurrency 256 --max-tokens 256 --temperature 0 --seed 0
# and again with --max-concurrency 32
```

## Test Result

- Unit test: passes with this PR. On main it fails with `cum_seq_lens_q moved between builds`.
- GSM8K end to end (1319 questions, greedy decoding; target Qwen/Qwen3-8B, draft Qwen/Qwen3-0.6B, K=3):

| Setup | C256 | C32 | Mean accepted tokens per draft |
|---|---|---|---|
| Uniform decode graphs up to 256 requests (as in #63406), without this fix | crash (illegal memory access) | n/a | n/a |
| Same, with this fix | 0.886 | 0.886 | 2.44 |
| `cudagraph_mode=PIECEWISE`, attention runs eagerly (reference) | 0.886 | 0.886 | 2.44 |
| main, with this fix | 0.886 | 0.886 | 2.44 |

On main without this fix, the crash is intermittent: graphs there stop at about 200 requests, so a crash depends on what the freed memory holds. With the fix, accuracy and acceptance match the PIECEWISE reference, which shows the replayed draft prefill now reads the correct query offsets.
