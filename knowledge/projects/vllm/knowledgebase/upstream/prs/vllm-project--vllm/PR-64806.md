# [Bugfix][Attention] Bound SM100 decode indexer logits with query-row chunks

[Upstream PR](https://github.com/vllm-project/vllm/pull/64806) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

On SM100, compute the sparse indexer's decode logits in chunks of query rows, each at most `VLLM_SPARSE_INDEXER_MAX_DECODE_LOGITS_MB` (default 2 GiB), instead of one tensor for all decode rows of a step. This applies to every model that uses this indexer (DeepSeek-V3.2, V4, V4.1, GLM-5.x (`GlmMoeDsaForCausalLM`), HY-V4), with either the FP8 (default) or the MXFP4 indexer cache.

It removes most of the memory these logits take at long context, and it unblocks the CUDA graph refactor (#63406), whose wide decode graphs would otherwise hold the full logits.

### Motivation

The sparse indexer scores every cached KV position of a request for each query row and keeps the top-k (512 for DeepSeek-V4/V4.1, 2048 for V3.2 and GLM-5.x). On SM100, the decode scores come from one DeepGEMM `fp8_fp4_paged_mqa_logits` call, which writes a dense BF16 tensor of shape `[decode rows, W]`:

- `decode rows` = requests × (1 + speculative tokens);
- `W` = `max_model_len / compress_ratio`, fixed by the model length, not by the requests' actual context.

At 1M context with 8192 decode rows this tensor is 16 GiB, and main's memory profile reserves it plus an FP32 copy (48 GiB). The copy is no longer made at runtime, since persistent top-k reads BF16 (#64138). The tensor costs memory in two places:

- **Eager and PIECEWISE steps** (mixed prefill + decode steps, and decode steps wider than the largest FULL graph) allocate it at runtime. So the memory profile reserves the worst case, and that memory is taken from the KV cache.
- **FULL CUDA graphs** allocate it inside the graph memory pool, which grows with the widest captured decode graph. #63406 captures decode graphs up to the full `max_num_seqs`.

### Change

When a step's decode logits would exceed the budget, the decode rows are split into balanced, 16-row-aligned chunks. Each chunk runs the same operations as the unchunked path on its own rows, and writes its rows of the shared top-k output:

1. DeepGEMM schedule metadata for the chunk;
2. logits;
3. V4.1 candidate-block selection or masking;
4. top-k.

Rows are independent, so nothing is merged across chunks. A step that fits the budget runs the existing single call unchanged, and so do prefill rows (already chunked by `VLLM_SPARSE_INDEXER_MAX_LOGITS_MB`). The memory profile reserves one BF16 chunk instead of every decode row plus an FP32 copy.

### Correctness

**Chunked vs single call, on the real kernels.** A standalone check on GB200 runs DeepGEMM logits, candidate selection or masking, and the `auto` or `persistent` top-k. It compares chunking against a single call for FP8 and MXFP4 caches, 1000–8192 rows, W from 256K to 1M, and chunks down to ≤ 64 rows (which take the cooperative top-k and an FP32 upcast):

- chunked logits are bit-identical to the single call;
- candidate blocks are identical;
- the selected top-k values match an exact `torch.topk` on the same logits in every row (indices may differ only among tied scores).

The same check shows that main's single call returns a wrong top-k once one call exceeds 2^32 logits elements. At 1M context this happens above about 4094 rows: 4097 of 8192 rows were wrong, for both cache types and both top-k backends, while the logits themselves were correct. At the default budget a chunk holds at most 2^30 elements, so this PR avoids it. A separate fix for the top-k kernel's addressing will follow.

## Details

- **Where it applies:** SM100, top-k backend `auto` or `persistent`, top-k ∈ {512, 1024, 2048}, no decode or prefill context parallelism. Both indexer cache types, and V4.1's candidate source and masked candidate consumer layers. V4.1's compact sparse consumers (`indexer_sparse_logits`) already score only candidate blocks and are unchanged.
- **Mixed steps:** chunking depends only on the number of decode rows, so it also applies to the decode rows of a mixed prefill + decode step; prefill rows are unchanged. These steps run PIECEWISE or eager, where each extra chunk adds a few kernel launches.
- **When to raise the budget:** a step chunks once its decode rows exceed `budget / (2 bytes × W)` on the widest indexer layer (1024 rows at 1M with the default). If running requests × (1 + speculative tokens) is usually above that and the KV cache is not the bottleneck, raise `VLLM_SPARSE_INDEXER_MAX_DECODE_LOGITS_MB` (for example to 4096). At 1M, keep it below 8192, where one call would exceed 2^32 elements; `0` turns chunking off.
- **Disaggregated prefill/decode:** prefill rows are unchanged, and prefill instances also get the smaller reservation. The decode instance produces the first token, so time to first token includes one decode step, which pays the chunking cost above if that step is wider than the limit.
- **Interaction with #64580:** #64580 would make SM100 logits FP32 again by default. Whichever PR lands second must pass the logits dtype to the chunk's `mqa_logits_mx_inputs` call and size the budget by the logits element size.
- **Models measured:** DeepSeek-V4.1-Flash (FP8 and MXFP4 indexer caches) and GLM-5.3-NVFP4. DeepSeek-V3.2, V4 and HY-V4 run the same indexer code but were not measured end to end; at their usual context lengths (≤ 256K) decode steps chunk only above 4096+ rows, so the main change for them is the smaller memory-profile reservation.
- **Not covered:** decode context parallelism, non-default top-k backends (e.g. `deep_select`), the V4.1 GB300 specialized decode path, and indexers with their own implementation (GLM-5-Next, MiniMax-M3) keep their current path.

## Not a duplicate

#62169 chunks the SM90 / SM120 uniform decode path by request, and excludes SM100 varlen decode. No other open PR bounds the SM100 decode logits.
