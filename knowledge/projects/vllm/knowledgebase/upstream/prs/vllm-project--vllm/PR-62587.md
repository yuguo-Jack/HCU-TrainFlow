# [Bugfix][Engine] Ignore clear_cache for pause mode=keep

[Upstream PR](https://github.com/vllm-project/vllm/pull/62587) · state: open · merged: False

## Original PR description

## Summary

Fixes https://github.com/vllm-project/vllm/issues/62123.

`POST /pause?mode=keep` is documented to ignore `clear_cache` ("Ignored when
mode=keep"), but `AsyncLLM.pause_generation` cleared the frontend multimodal
cache and forwarded `clear_cache=True` to the engine for every mode. With
`--mm-processor-cache-type shm`, that resets the writer-side ring buffer while
requests frozen in the queue still hold `(address, monotonic_id)` handles into
it. When such a request is scheduled after `/resume`, the worker's handle
validation raises `ValueError: Data for address:id ... has been modified or is
invalid.` inside `execute_model`, which kills EngineCore (`EngineDeadError`):
every in-flight and later request fails and `/health` stops answering 200.

The fix makes `pause_generation` honor the documented semantics: when
`mode="keep"`, `clear_cache` is forced to `False` so neither the frontend MM
cache nor the engine-side caches are touched. `abort`/`wait` behavior is
unchanged.

## Test commands and results

New regression tests in `tests/v1/engine/test_llm_engine.py` (mocked
renderer/engine core, no GPU needed):

- `test_pause_generation_keep_ignores_clear_cache` — `mode="keep"` with
  `clear_cache=True` clears nothing and forwards `clear_cache=False`
- `test_pause_generation_abort_honors_clear_cache` — `abort` still clears
- `test_pause_generation_wait_honors_clear_cache` — `wait` still honors
  explicit `clear_cache=True`

The fix logic was additionally verified by executing the method source
extracted verbatim from `vllm/v1/engine/async_llm.py` against mocked
renderer/engine-core objects; all four mode/flag combinations behave as
documented (keep never clears; abort/wait honor the flag).

Full server-level reproduction from the issue (Qwen2-VL on GPU) was not
re-runnable in this environment (no GPU); the change is confined to the pause
request path and does not touch model execution, sampling, or any model
output, so no model evaluation results are applicable.

`pre-commit` hooks pass on the change; DCO sign-off included.

- hivaze · comment · 2026-11-03T14:58:45Z · [source](https://github.com/vllm-project/vllm/pull/62587#issuecomment-6607155423)

This also removes the reset weight sync relies on. `docs/training/async_rl.md` pauses with `mode="keep", clear_cache=True` and says that clear is why tokens after resume come only from the new weights. From reading, block hashes don't cover the weights and nothing on the update path resets the prefix cache, so with this PR requests after `/resume` would read KV from the old weights with no error. #57970 says the same for `clear_cache=False`: "Tokens generated after resume attend to KV computed with the old weights."

One CPU run on main at `8b30f56b1` (real `AsyncLLM`, `EngineCore` and `Scheduler`, no model or weights, not a server): after a keep pause with the default `clear_cache`, the same 64-token prompt reused 0 tokens from the prefix cache on main and 48 with this PR. A request in flight across the pause was preempted on main and kept its KV with this PR.

The crash in #62123 comes from the multimodal caches, which hold processor output and, from reading, don't depend on the weights. Could keep mode skip only those clears, in the frontend and the engine, and still reset the prefix and encoder caches? A local patch doing that, same run, gave 0 reused tokens and a preempted request, and real SHM caches gave no `ValueError` where main does. puncsky's storage change in #62123 is another option that leaves the KV reset alone. The `Ignored when mode="keep"` docstring looks like the stale part: #60744 says so and #60764 changes it.

[Halo](https://github.com/whitecircle/halo) pauses with `mode=keep` and the default `clear_cache` around each weight sync and counts on this reset. I can share the script and the patch. AI assistance was used for the check and this comment.
