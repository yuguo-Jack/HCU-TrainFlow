# [Doc][ROCm] Add verified MI300X/MI325X entries to Qwen3.8-27B recipe

[Upstream PR](https://github.com/vllm-project/vllm/pull/65021) · state: open · merged: False

## Original PR description



## Overview

The Qwen3.8-27B recipe lists no AMD GPU, and its `docker_image` comment says the ROCm path was never exercised. This PR adds that path for two gfx942 GPUs: `meta.hardware` gains `mi300x: verified` and `mi325x: verified`, `docker_image` gains an `amd:` pin (`vllm/vllm-openai-rocm:v0.32.0`), and the `fp8` variant gets one override shared by both GPUs that carries the validated flags and `VLLM_ROCM_USE_AITER=1`. The command the builder now renders for MI300X + FP8 and MI325X + FP8 is the command that was run on each. Selecting either GPU still opens on the BF16 variant, so a `notes[]` entry on that command says the verified runs used FP8.

## Claims

- On 1× MI300X and 1× MI325X with `vllm/vllm-openai-rocm:v0.32.0`, the rendered FP8 command boots, serves `Qwen/Qwen3.8-27B-FP8`, splits reasoning from content, makes streamed and non-streamed tool calls, answers from a tool result and reads an image. GSM8K scores 0.948 (MI300X) and 0.950 (MI325X) at 1024 tokens, and 0.705 and 0.720 at the eval script's default 256. The guide's AMD section now lists the tested image, GSM8K and KV capacity for both GPUs.
- The native 262,144-token context fits at `--gpu-memory-utilization 0.9`: 4,298,257 KV tokens on MI300X (16.40x concurrency) and 6,112,173 on MI325X (23.32x). A single 217,017-token request on MI300X returned the hidden number.
- `--attention-backend ROCM_AITER_FA` needs no environment variable on v0.32.0. `VLLM_ROCM_USE_AITER=1` leaves accuracy unchanged (GSM8K 0.703 without it, 0.720 with it on MI325X) and moves the FP8 linear layers, RMSNorm and the vision encoder onto AITER kernels; the same GSM8K run then takes 422 s instead of 937 s.
- Known limit of the pinned image: with several long prompts in flight, v0.32.0 can lose a request's KV context. On MI325X, 3 of 20 needle prompts of 131k tokens came back wrong; the same image with #59098 applied found 20/20.
- Of the recipe's 304 renderings, 283 are byte-identical. The MI300X and MI325X FP8 commands and their Mooncake alternatives change; 15 other AMD renderings change only the image tag, `:latest` → `:v0.32.0` (the same digest today). No NVIDIA, Intel or Ascend rendering changes, and no other recipe's output changes.
- Not tested: TP > 1, BF16 and the other variants on these GPUs, MI350X / MI355X, spec decoding, long context past 262,144 tokens, `text_only`, KV offload (including the four Mooncake renderings above), multi-node.

## Validation

**Setup.** One AMD Instinct MI300X (gfx942, 192 GB) and one MI325X (gfx942, 256 GB), each running `vllm/vllm-openai-rocm:v0.32.0` (`sha256:14f6a575e1fb0a580b0f633c09e06f648709d60405b85f6a7ff3f80d49f39905`): vLLM 0.32.0 (`5df63a7203cd`), ROCm 7.2.3, torch 2.13.0, Triton 3.8.0, AITER 0.1.24.post1, transformers 5.19.0. Checkpoint `Qwen/Qwen3.8-27B-FP8` at `017b9c7`. Every server started from an empty compile cache.

**Command.** The builder's MI300X + FP8 and MI325X + FP8 Docker command (`/Qwen/Qwen3.8-27B?hardware=mi300x&variant=fp8`, and the same for `mi325x`), run as rendered apart from GPU selection and the host port:

```bash
docker run --device=/dev/kfd --device=/dev/dri \
  --security-opt seccomp=unconfined --group-add video \
  --privileged --ipc=host -p 8000:8000 \
  -v ~/.cache/huggingface:/root/.cache/huggingface \
  -e VLLM_ROCM_USE_AITER=1 \
  -e VLLM_USE_RUST_FRONTEND=1 \
  vllm/vllm-openai-rocm:v0.32.0 Qwen/Qwen3.8-27B-FP8 \
  --attention-backend ROCM_AITER_FA \
  --max-model-len 262144 \
  --max-num-seqs 8 \
  --max-num-batched-tokens 30720 \
  --gpu-memory-utilization 0.9 \
  --kv-cache-dtype fp8 \
  --enable-chunked-prefill \
  --compilation-config '{"mode":3,"cudagraph_mode":"FULL_AND_PIECEWISE","custom_ops":["+rms_norm","+quant_fp8"]}' \
  --disable-log-stats \
  --tensor-parallel-size 1 \
  --enable-auto-tool-choice \
  --tool-call-parser qwen3_coder \
  --reasoning-parser qwen3 \
  --mm-encoder-tp-mode data
```

**Results**, one run per row. GSM8K is `tests/evals/gsm8k/gsm8k_eval.py` from `main`: 5-shot, all 1319 questions, `/v1/completions`, temperature 0.

|---|---|---|---|---|---|---|
| MI300X | Rendered command | Rust | 5/5 | 0.705 (0.017) | 0.948 (0.022) | 4,298,257 tokens |
| MI325X | Rendered command, three boots | Rust | 5/5 on each | 0.720 (0.019) | 0.950 (0.019) | 6,112,173 tokens |

The 256-token cap is the script's default; it cuts off this reasoning model's longer answers, which is why the 1024-token runs score higher. The script sends all 1319 questions at once, and its default 600 s request timeout is too short for the server without AITER, so that row used `--request-timeout-seconds 7200`. No other run hit the timeout. On MI325X the 256-token run took 422 s with `VLLM_ROCM_USE_AITER=1` and 937 s without it.

The smoke checks: `17 * 23` returns `391` with the reasoning outside `content`; a non-streamed `get_weather` call with valid arguments and `finish_reason: tool_calls`; a second turn that answers from the tool result; a streamed tool call reassembled from deltas; a solid-red 64×64 PNG answered as red. Prefix caching, on by default, was also checked on MI325X with 12 questions about one 8k-token document sent one after another: 12/12 correct, with time to first token 0.70 s for the first request and 0.11 s median for the rest.

```bash
python3 tests/evals/gsm8k/gsm8k_eval.py --port 8000                     # 256 tokens
```

## Details

- **Why the needle prompts fail on v0.32.0.** Under Model Runner V2, `sort_batch_req_ids` can place a request that already has KV context (a later chunk of a long prompt, or a prefix-cache hit) after a fresh prefill. `split_decodes_prefills_and_extends` then treats it as a prefill, and the prefill path attends without the KV cache, so the answer is wrong with no error. #59098 fixes both functions; it is open and not in v0.32.0. The misses come from the pinned image, not from this PR's flags: the A/B above differs only by #59098. Once a release carries it, the `amd:` pin can move to that release.
- **Why `ROCM_AITER_FA` starts without AITER enabled.** An explicit `--attention-backend` is checked only against that backend's `validate_configuration`. `rocm_aiter_ops.is_mha_enabled()` filters the auto-selection list alone (`_get_backend_priorities` in `vllm/platforms/rocm.py`), on v0.32.0 and on `main`. `VLLM_ROCM_USE_AITER_MHA` is not needed; it defaults to on.
- **What `VLLM_ROCM_USE_AITER=1` changes here**, from the startup logs on both GPUs: `AiterFp8BlockScaledMMKernel` instead of `TritonFp8BlockScaledMMKernel` for the FP8 linear layers, AITER RMSNorm instead of the native one, and `ROCM_AITER_FA` instead of `FLASH_ATTN` for the vision encoder.
- **Scope.** The flags live in `variants.fp8.hardware_overrides.mi300x` and are shared with `mi325x` through a YAML anchor, as GLM-5.3-Flash does for its gfx950 parts, so MI350X and MI355X keep their current commands. The `amd:` image pin is brand-wide, as in the GLM-5.3 recipe.
- **Why pin rather than use `:latest`.** `:latest` is v0.32.0 today, so the pin changes no image now. It keeps the AMD command on the image both runs used when `:latest` moves, and makes the move to a release with #59098 an explicit change.
- `+rms_norm` in `custom_ops` has no effect on v0.32.0 for this model; vLLM says so at startup, because RMSNorm now goes through the IR op path. It stays so the recipe matches the command that was run. On both GPUs the Rust frontend also logs that `enable_auto_tool_choice` has no effect there; tool calls work regardless.
- This PR and #64770 both change `meta.date_updated`; whichever merges second needs a one-line rebase.

Not a duplicate: no open PR adds AMD hardware to this recipe. I searched open PRs in vllm-project/vllm and vllm-project/recipes for Qwen3.8-27B with MI300X, MI325X, ROCm and AMD. #64770 (a RedHatAI NVFP4 variant for Blackwell) is the only open PR that touches this file. #52752 adds MI300X FP8 kernel configs and #61573 an MI355X model-code path; neither changes the recipe.
