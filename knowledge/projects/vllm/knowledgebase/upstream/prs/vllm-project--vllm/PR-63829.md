# [Bugfix] FlashInfer flashinfer_b12x MoE backend runs W4A16 checkpoints as W4A4

[Upstream PR](https://github.com/vllm-project/vllm/pull/63829) · state: open · merged: False

## Original PR description

## Overview

Add W4A16 (NVFP4 weights, BF16 activations) support to the FlashInfer `flashinfer_b12x` fused-MoE backend on SM12x. Weight-only NVFP4 MoE checkpoints currently run through this backend as W4A4: FlashInfer quantizes the BF16 activations to FP4 inside the kernel. Supersedes #56535 (same change rebased on current `main`, minus the FlashInfer version guard, which is no longer needed now that `flashinfer-python==0.7.2.post1`, vLLM's current pin, carries the forced-tile validation fix).

Not a duplicate: no other open PR plumbs `quant_mode="w4a16"` into `FlashInferB12xExperts` (searched open PRs for "b12x w4a16", "flashinfer_b12x", "SM12x MoE W4A16").

## Claims

- `--moe-backend flashinfer_b12x` now serves weight-only NVFP4 MoE checkpoints (e.g. `nvidia/Qwen3.6-35B-A3B-NVFP4`) through FlashInfer's `B12xMoEWrapper(quant_mode="w4a16")` with BF16 activations, instead of silently quantizing activations to FP4.
- Matches Marlin W4A16 GSM8K accuracy on the same checkpoint and recovers the ~2 point deficit of the previous W4A4 behavior (table below).
- Token counts are bucketed to vLLM's CUDA-graph capture sizes (and 128-token buckets above them) and pre-compiled in the b12x warmup, so the shape-specialized W4A16 kernels do not JIT during serving.

## Validation

All runs on a single DGX Spark (GB10, SM121), `flashinfer-python==0.7.2.post1`, torch 2.13.0+cu132.

GSM8K, `nvidia/Qwen3.6-35B-A3B-NVFP4`, 1319 questions, 5-shot, greedy, `--max-model-len 4096`:

| MoE path | Activations | GSM8K accuracy |
|---|---|---|
| **flashinfer_b12x W4A16 (this PR)** | BF16 | 0.9189 (1319 questions, latency 840 s at concurrency 8) |
| marlin (weight-only) | BF16 | 0.9136 (1319 questions, latency 805 s at concurrency 8) |
| flashinfer_b12x W4A4 (behavior before this PR, from #56535) | FP4 | 0.890 (mean of 4 runs: 0.8886, 0.8817, 0.8908, 0.9007) |

Both configs are in `tests/evals/gsm8k/configs/models-sm12x.txt` with identical threshold (0.90) and tolerance (0.03), so the two SM12x backends are held to the same bar.

- Kernel tests: `tests/kernels/moe/test_flashinfer_b12x_moe.py` -- 96 passed on GB10 (W4A4 and W4A16 cases). The W4A16 reference runs `torch_moe` on the exact dequantized NVFP4 weights (same methodology as the Marlin MoE tests), so quantization error cancels and the tolerance is `atol=4e-2, rtol=0`.
- `pre-commit run --files <changed files>`: all hooks pass (ruff, ruff format, typos, mypy, SPDX, test tethering).

Reproduce:
```bash
pytest tests/kernels/moe/test_flashinfer_b12x_moe.py
pytest -s -v tests/evals/gsm8k/test_gsm8k_correctness.py --config-list-file=configs/models-sm12x.txt
```

CI note: the kernel and eval tests require SM12x hardware (GB10 / RTX Pro 6000) plus FlashInfer with `B12xMoEWrapper(quant_mode=...)`; they skip elsewhere. The DGX Spark nightly in `.buildkite/test_areas/kernels.yaml` is currently disabled, so `models-sm12x.txt` is not wired into CI; validation above was run manually on GB10.

## Details

- **Why W4A16:** weight-only NVFP4 checkpoints have no activation scales. The previous path synthesized unit FC2 input scales and let FlashInfer quantize activations to FP4 dynamically, costing ~2 GSM8K points. W4A16 keeps activations BF16 and is numerically equivalent to Marlin stage-for-stage (exact FP4 to BF16 dequant, BF16 block scales before the MMA, FP32 accumulation and split-K, FP32 top-k combine).
- **Quant-config routing:** `make_nvfp4_moe_quant_config` now returns `nvfp4_w4a16_moe_quant_config` for `FLASHINFER_B12X` when `use_a16`, the same as it already did for `MARLIN` and `B12X`. `FlashInferB12xExperts` reads `quant_config.quant_dtype is None` as W4A16, skips the W4A4-only block-scale bake-in (which would re-round the FP8 block scales), and constructs the wrapper with `quant_mode="w4a16"`.
- **Capability gate:** `has_flashinfer_b12x_w4a16_moe()` probes for the `quant_mode` kwarg on `B12xMoEWrapper.__init__`. On FlashInfer builds without it, `(kNvfp4Static, None)` is reported unsupported and backend selection falls through as before.
- **Token bucketing:** FlashInfer's W4A16 kernels specialize on the token count (~1-3 s per new shape). `w4a16_padded_num_tokens` pads eager batches to the capture-size grid and to 128-token buckets above 512; padding rows route to expert 0 with zero weight. `get_b12x_warmup_unit` compiles every reachable bucket during the existing b12x warmup.
- **Versus #56535:** that PR carried a version guard for FlashInfer 0.6.18 to 0.7.0.post1, whose forced-tile re-validation rejected the TC-decode fc2 tile (`tile_k=32`) during CUDA-graph capture. FlashInfer 0.7.2.post1 re-validates forced tiles without the search-space floor, and vLLM now pins that version, so the guard and its `VLLM_FLASHINFER_B12X_W4A16_IGNORE_BROKEN` escape hatch are dropped here.
- AI assistance (Claude Code) was used for the test-reference rework, token bucketing, numerics investigation, and the rebase onto `main`; all changes were reviewed and validated by the submitter.

I don't think W4A4 had the same cost. In 0.7.2.post1 the W4A4 path (`_get_weight_views`) caches only the converted block scales and alphas, and runs on the layer's FP4 weights in place (it copies them only when the intermediate size is not a multiple of 128). The W4A16 path (`_get_w4a16_packed_weights`) caches a full repacked copy of w13/w2, keyed on the source pointers, so the originals can't be freed either. That matches the low footprint you saw before this PR. `B12xMoEWrapper` has no way to take prepacked weights or pack in place yet, so avoiding the second copy here needs a FlashInfer change. On the two backends: `b12x` runs the standalone b12x package and `flashinfer_b12x` runs FlashInfer's port of it, and only `b12x` packs in place today.
