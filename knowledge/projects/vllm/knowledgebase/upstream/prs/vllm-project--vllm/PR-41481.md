# [Spec Decode][V1][V2] Warm spec-decode helper kernels at startup

[Upstream PR](https://github.com/vllm-project/vllm/pull/41481) · state: closed · merged: False

## Original PR description



## Summary

Fixes #39790. The spec-decode helper kernels in `vllm/v1/spec_decode/utils.py`
(5 `@triton.jit` kernels + 1 `@torch.compile` function) are not exercised by
the existing `_dummy_run` / `warmup_kernels` warmup paths because they only
run inside `drafter.propose()` and the model_runner's padded-batch input
prep — both of which the warmup never reaches. The first real request after
server start therefore pays the full JIT cost.

This PR adds a `dry_run_helper_kernels()` strategy method on
`SpecDecodeBaseProposer` that subclasses extend for their per-method
kernels, and wires it into both the V1 and V2 worker warmup paths. A V1-
only warmup of the async-spec `@torch.compile` correction
(`update_num_computed_tokens_for_batch_change`) is added in
`Worker._warmup_spec_decode_helpers`.

## Scope and honest framing

The original report enumerates 4 first-call cost sources; this PR addresses
**1 of the 4** (the `utils.py` kernels). Remaining sources called out by
@ccs668899 — FlashAttention drafter-shape autotune, drafter CUDA module
loading (~188 ms), lazy drafter KV/hidden-state allocation — are not
touched here and are good follow-up candidates.

## Files changed

- `vllm/v1/spec_decode/llm_base_proposer.py` — `dry_run_helper_kernels()`
  base implementation warms `eagle_prepare_next_token_padded_kernel`,
  `eagle_prepare_inputs_padded_kernel` (used by both Eagle and DFlash via
  base-class methods), and `copy_and_expand_eagle_inputs_kernel` when
  `needs_extra_input_slots=True` (parallel-drafting Eagle and
  `DraftModelProposer`).
- `vllm/v1/spec_decode/eagle.py` — `EagleProposer` override adds
  `eagle_step_update_slot_mapping_and_metadata` warmup, gated on
  `num_speculative_tokens > 1 and not parallel_drafting` so it only runs
  when sequential Eagle's inner draft loop will actually execute.
- `vllm/v1/spec_decode/dflash.py` — `DFlashProposer` override adds
  `copy_and_expand_dflash_inputs_kernel` warmup with both
  `HAS_NUM_REJECTED=True` and `False` constexpr variants.
- `vllm/v1/worker/gpu/warmup.py` — V2 path: invoke
  `drafter.dry_run_helper_kernels()` after the existing prefill+decode
  warmup.
- `vllm/v1/worker/gpu_worker.py` — V1 path: new
  `_warmup_spec_decode_helpers()` invoked after the post-`capture_model`
  `_dummy_run`. Also warms
  `update_num_computed_tokens_for_batch_change` (V1-only — V2 does not
  call it).
- `tests/v1/spec_decode/test_helper_kernel_warmup.py` — smoke tests pin
  the synthetic shapes against each kernel signature so future kernel
  changes break the test instead of silently regressing TTFT.

the only difference between rows is the 5 modified files reverted to

| Metric | Baseline (main @ c3868bbbe) | With this PR |
|---|---|---|
| TTFT prompt 1 (ms) | 2306.8 | 1372.7 |
| TTFT median prompts 2–50 (ms) | 270.8 | 271.8 |
| First/steady ratio | 8.52× | 5.05× |

Net effect: **TTFT for the first request after server start drops by
~934 ms (-40.5%)**, and the JIT spike-ratio drops from 8.52× to 5.05×.
Steady-state TTFT is unchanged (within noise).

The remaining 5.05× ratio is dominated by the 3 cost sources this PR
does not address (FlashAttention drafter-shape autotune, drafter CUDA
module loading, lazy drafter KV/hidden-state allocation), per
ccs668899's profiling in the issue thread.

Hardware: 1× RTX A6000 (driver 570.195, CUDA 13.0), torch 2.11+cu129,
vLLM @ `c3868bbbe` precompiled wheel.

Thanks @benchislett — investigated this carefully and want to share what I found before picking a direction.

## V2 — already covered, hook was dead code

You're right that an E2E step is cleaner. Looking at the V2 path, it **already does this naturally**:
- `vllm/v1/worker/gpu/warmup.py` runs `worker_execute_model(decode_output)` during init
- That flows into `GPUModelRunner.execute_model` which unconditionally calls `self.speculator.propose(...)` at `gpu/model_runner.py:1248` when speculator is configured

So V2's existing warmup already JIT-compiles V2's spec kernels (which live separately in `vllm/v1/worker/gpu/spec_decode/eagle/`, not in `vllm/v1/spec_decode/utils.py`).

My V2 hook was actually **a dead no-op the whole time**: V2's model runner has no `drafter` attribute (it has `speculator`), so `getattr(model_runner, \"drafter\", None)` always returned None and the body never ran. Pushed e7e54c41e removing it + cleaning up the misleading comments — net -9 LOC and clearer semantics.

## V1 — needs a different fix

V1 (still the default per `VLLM_USE_V2_MODEL_RUNNER: bool = False`) doesn't go through the `execute_model` warmup path. Its \`compile_or_warm_up_model\` uses \`model_runner._dummy_run(num_tokens=max_num_reqs)\` + \`_dummy_sampler_run\`, which exercises the draft model forward but never calls \`drafter.propose()\`. So the spec helper kernels in \`vllm/v1/spec_decode/utils.py\` only JIT on the first real request — that's the regression in #39790.

To make V1 do an E2E step, we'd basically need to add the equivalent of V2's \`warmup_kernels()\` to the V1 worker init flow: build a synthetic \`SchedulerOutput\` and feed it through \`execute_model\`. That's ~150 LOC of new V1 warmup infrastructure and feels like its own PR scope.

## Asking your call

Three options for V1, ranked by scope:

1. **Land this PR as V1-only per-kernel warmup**, with a TODO pointing at \"V2-style execute_model warmup for V1\" as follow-up. (current state after my push)
2. **Refactor V1 in this PR** to add a synthetic-SchedulerOutput-driven warmup mirroring V2's pattern. Roughly +150/-180 net.
3. **Direct synthetic \`propose()\` call** in V1 instead of full SchedulerOutput plumbing. Roughly +80/-180 net but more bespoke.

I lean toward (1) since (2)/(3) likely overrun the natural scope of #39790 and could surface follow-up issues, but happy to take it further if you'd prefer (2) or (3) for this PR.

Current PR head (e7e54c41e) is now V1-only with the V2 dead code removed.

![high](https://www.gstatic.com/codereviewagent/high-priority.svg)

The `block_size_tokens` calculation here uses `total_output_tokens`, which includes `num_padding_slots_per_request`. However, the production code in `set_inputs_first_pass` (line 703) calculates `BLOCK_SIZE_TOKENS` based on `max_num_tokens_per_request` (which is `query_len + net_num_new_slots_per_request`). For the first request after startup (typically a decode with `query_len=1`), these values will differ, causing a JIT cache miss and negating the warmup benefit. To ensure a cache hit, the warmup should use the same logic as the expected first real request.

```suggestion
            block_size_tokens = min(256, next_power_of_2(num_query_per_req))
```

The `num_context` is set to `num_query_per_req`, leading to `max_tokens_per_req = 2 * num_query_per_req`. In production (`set_inputs_first_pass`, line 125), `max_tokens_per_req` is `max_ctx_per_req + num_query_per_req`. For the first request after startup, `max_ctx_per_req` is typically 1, leading to a JIT mismatch (e.g., if `num_query_per_req` is 5, warmup JITs for 16 while production JITs for 8). Setting `num_context = 1` matches the production sizing for the first request and aligns with the intent described in the comment on line 321.

```suggestion
        num_context = 1
```
