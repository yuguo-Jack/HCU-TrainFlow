# [Bugfix][Spec Decode] Cap varlen decode graph requests at the draft pass capacity

[Upstream PR](https://github.com/vllm-project/vllm/pull/63225) · state: open · merged: False

## Original PR description

## Overview

Fixes #62939. With DSpark adaptive verification, startup can crash when `max_num_seqs * num_query_per_req` exceeds `max_num_batched_tokens`. The issue's command (Qwen3-8B, `--max-num-batched-tokens 512`) on main:

```
Assertion `index out of bounds: 0 <= tl.broadcast_to(tmp29, [XBLOCK, R0_BLOCK]) < 40960` failed.
...
  File "vllm/v1/worker/gpu/model_runner.py", line 1133, in capture_model
    self._dummy_run(**batch)
...
torch.AcceleratorError: CUDA error: device-side assert triggered
```

`_dummy_run` caps requests at `max_num_batched_tokens // num_query_per_req` so the draft pass fits its buffers (#56448). But adaptive verification's startup profiling replays varlen decode graphs padded to `max_num_seqs` requests, and the drafter drafts for every padded slot: up to 256 * 7 query rows against 512-row buffers (#58984 clamps this only for DP > 1). This PR pads those graphs only up to the same cap, which the scheduler already enforces (#59468); configs where the cap does not bind are unchanged.

Not a duplicate: no other open PR targets #62939; #53970 takes a different route, growing the drafter buffers and the default budget.

The new CPU test fails if either the request cap or its matching token bound is reverted. The e2e test runs in the nightly `Spec Decode AL DSpark` job and is skipped on ROCm, where it is untested.

All GPU runs above used the first revision (01d0d0b, on 6ee316eaea). Since then #63406 has reworked how varlen decode graph sizes are chosen, so the cap now sits in its varlen branch with the same logic (now on 2a777ce26e), and the unit test expects that branch's token grid.
