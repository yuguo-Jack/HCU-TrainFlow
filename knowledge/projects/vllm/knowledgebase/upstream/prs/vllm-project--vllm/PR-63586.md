# [Feature][KV Offload] Enable compressed-MLA support for TP agnostic offloading

[Upstream PR](https://github.com/vllm-project/vllm/pull/63586) · state: closed · merged: False

## Original PR description



## Overview
  
Fix a KV-offloading correctness/namespace-collision bug for compressed-MLA models (e.g. DeepSeek-V4 sparse MLA, `tokens_per_state > 1`): the offloading stack previously treated one stored "state" as equivalent to one token, and did not distinguish compression ratio in the on-disk storage namespace, causing silent byte-mapping corruption and namespace collisions between configs with different compression ratios.  Fixes Compressed MLA slice in "Coverage to add" section of #61886.


## Claims
- Certify compressed-MLA (`tokens_per_state` as an integer compression ratio > 1) for the canonical/offloading byte-mapping path, previously rejected outright (fail-closed) by `spec_certifiable`/`_layer_mapping`.  
- Fix `_layer_mapping`'s MLA branch to compute row/byte-region arithmetic in units of `num_states` (`block_size // tokens_per_state`) instead of incorrectly using `block_size`/`bs` directly, which assumed 1 token == 1 stored row for MLA only path.  
- Make the on-disk storage namespace (`FileMapper`/`base_path` hash) fork on `tokens_per_state` where `tokens_per_state` is other than the default set `1`, so configs that differ only in per-layer compression ratio no longer collide under the same cache directory. Existing configs are left untouched to make sure deployed state is not curropted. 
- Explicitly keep Fraction-based `tokens_per_state` (Whisper-style pooling, < 1) and non-divisible int ratios out of scope — both fail closed, not silently mishandled.  


## Validation
- Unit tests added/updated and passing locally:  
  - `tests/v1/kv_connector/unit/offloading_connector/test_canonical_mapping.py` — new compressed-MLA `_layer_mapping`/`derive_canonical_mappings` cases (valid int ratios, non-divisible ratios, Fraction rejection, DCP interaction).  
  - `tests/v1/kv_connector/unit/offloading_connector/test_config.py` — `spec_certifiable`/`build_offloading_config` updated for compressed MLA, including mixed-ratio layers inside a single `UniformTypeKVCacheSpecs` group; two pre-existing tests (`test_canonical_layout_gate[uniform-uncertifiable-inner]`, `test_uncertifiable_canonical_layout_resets_replication[compressed-mla]`) updated since compressed MLA is now a certifiable case rather than a fail-closed one.  
  - `tests/v1/kv_offload/test_file_mapper.py` — new tests asserting namespace forks on `tokens_per_state`.
  
  E2E validation is pending yet. will update the description once done.


## Details
**Root cause:** `AttentionSpec.tokens_per_state` (and `MLAAttentionSpec` by inheritance) already modeled compression ratio (`int > 1` compresses multiple tokens into one stored state), but two parts of the offloading stack assumed `tokens_per_state == 1` implicitly:  
1. `_layer_mapping` (`canonical_mapping.py`) used `block_size`/`bs` directly as the row count for MLA byte-region computation, which is only correct when one row == one token.  
2. `spec_certifiable` (`config.py`) statically gated any MLA spec with `tokens_per_state != 1` as uncertifiable, and `OffloadingGroupConfig`/`FileMapper` had no field at all representing compression ratio, so even if certification were relaxed, two configs differing only in compression ratio would hash to the same storage namespace.  
  
**Design decisions:**  
- `tokens_per_state` is per-layer, not per-group: a single `KVCacheGroupSpec`/`UniformTypeKVCacheSpecs` group can legitimately contain layers with different compression ratios (same `block_size`/block-count requirement, different physical page size per layer) — so `OffloadingGroupConfig.tokens_per_state` is `tuple[int, ...]` (one entry per distinct spec as grouped via `iter_layer_specs`), not a scalar, mirroring but independent from the existing `tokens_per_block` scalar field.  
- Defaults to `(1,)` so existing non-compressed models/tests are unaffected without explicit changes.  
- Serialized into `FileMapper.fields["kv_cache_groups"]` as `[str(ts) for ts in ...]` since `Fraction` values aren't natively JSON-serializable and the hash only needs stable string identity, not numeric fidelity.  
- Guard logic (`type(spec.tokens_per_state) is int and spec.block_size % spec.tokens_per_state == 0`) explicitly distinguishes DSv4-style integer compression (in scope) from Whisper-style `Fraction` pooling (out of scope, fails closed) and non-divisible ratios (fails closed).  
  
**Limitations / explicitly deferred:**  
- CP (`dcp_size`/`pcp_size > 1`) for compressed MLA: DCP sharding of compressed-MLA states is supported and tested by `_layer_mapping`; the deferred limitation applies specifically to the `is_parallelism_agnostic`/replicated-layout gate reusing a single namespace across differing CP degrees for compressed MLA — a pre-existing scope limitation that applies broadly, not unique to this PR's change. 
- `SlidingWindowMLASpec` compressed variants are tracked separately, not covered here.  
- `tokens_per_state <= 0` is not explicitly validated (relies on HF-config-derived construction making this unreachable in practice); can be hardened later if needed.  
- Possible overlap with unmerged PR #56331 (`model_config_hash` from full HF config) — if it lands, this PR's explicit `tokens_per_state` field becomes redundant-but-harmless in file mapping; not blocking on it since this PRexists independent of that proposal.

- tejachavali · CHANGES_REQUESTED · 2026-10-25T15:58:31Z · [source](https://github.com/vllm-project/vllm/pull/63586#pullrequestreview-5644029599)


Request changes. The direction is right, but the MLA guard in `_layer_mapping` is inverted as written, so the feature does not work yet.

In `canonical_mapping.py`, the rejection condition starts with `type(spec.tokens_per_state) is int`. That term is true for exactly the in-scope case, so every integer ratio, including plain MLA with ratio 1 and compressed MLA with ratio 2, returns None. Using the test file's own numbers (block size 4, 64B per state), ratio 2 gives page 128B and `num_states` 2, but the guard rejects it before the mapping is built. The Fraction case goes the other way: `4 % Fraction(1, 2)` is 0 and page 512 % `num_states` 8 is 0, so it returns a mapping instead of failing closed. That means the new compressed MLA tests, the existing uncompressed MLA tests, and the Fraction fail-closed test cannot all pass with this guard, and `derive_canonical_mappings` would fall back to the opaque layout (256B canonical page, not the asserted 128B) for the compressed layer. The `spec_certifiable` side has the correct positive form (`type(...) is int and block_size % ... == 0`), so this looks like the positive form copied into a negative guard without negating the first term. Did you mean `type(...) is not int` here, and can you re-run the three test files after fixing it? That one change also makes the two gates agree.

The rest of the change looks sound on inspection. The `num_states` row arithmetic, the per-layer `tokens_per_state` tuple for mixed-ratio uniform groups, and the namespace forking in `FileMapper` (including order sensitivity and Fraction stringification) are all covered by tests that would fail without the change. A few smaller questions, none blocking on their own. First, after the guard fix, does `tokens_per_state` of 0 raise `ZeroDivisionError` in both guards instead of failing closed, and is that worth one explicit rejection? Second, the non-MLA branch now passes `num_states` instead of `block_size` to `_interleave_cp_tokens` for every spec, which changes behavior for Whisper-style pooled non-MLA specs too. Is that intentional, or should the substitution stay in the MLA branch? Third, `spec_certifiable` checks page divisibility by `block_size` while `_layer_mapping` checks divisibility by `num_states`, making the certifier strictly stricter. Is that deliberate? Fourth, is dict order guaranteed to match `layer_names` order when building the mixed-ratio tuple, since `FileMapper` treats it positionally? Fifth, adding the new field changes the `base_path` hash for uncompressed models as well, orphaning existing on-disk caches. Is that blanket invalidation intended? Finally, the description says CP for compressed MLA is not addressed, but the new DCP test shards states with `dcp=2`. Is that limitation meant to refer only to the parallelism-agnostic gate? Also a nit: the fail-closed test comment says "block_size must divide tokens_per_state", but the case tests the reverse.
