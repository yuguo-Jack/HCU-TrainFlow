# [ROCm][Perf][DSv4.1] Mono decode on MI300X and MI325X (gfx942)

[Upstream PR](https://github.com/vllm-project/vllm/pull/60731) · state: open · merged: False

## Overview

This PR ports the DeepSeek-V4.1-Flash mono decode kernels of #60397 to gfx942 (MI300X and MI325X). A standard decoder layer then runs as 2 kernels instead of 32. The path is opt-in with `VLLM_ROCM_MONO_DECODE=1`, as in #60397. No other open PR ports these kernels to gfx942.

The PR is stacked on #60397 and merges its head 9a24c32a17. Its own commits are the 8 after 73f40ed and the 7 after that merge. Until #60397 merges, the diff against `main` includes #60397.

**Speculative decoding works at every concurrency.** The mono path takes decode steps of up to 42 rows on gfx942, which is up to 7 concurrent requests with 5 DSpark drafts. A step of 8 or more requests runs vLLM's path, with the same speculative decoding, and gets none of the speedup. That limit needs to be fixed, and we are working on it (see Follow-ups).

## Claims

MI325X, TP4, 5 DSpark drafts. Each AgentX run is 3,600 s and is scored with InferenceX's own result code.

- AgentX at concurrency 1, against `main`: interactivity P50 goes from **216.85 to 503.53 tokens/s/user** (2.32×), P90 from **182.25 to 411.26** (2.26×), and total throughput per GPU from 4,024 to 6,546 tokens/s (1.63×).
- AgentX at concurrency 2, 4 and 8, against InferenceX's published MI325X points, because there is no `main` run at these concurrencies: P90 goes from **153.22 to 368.64** (2.41×), from **142.75 to 316.28** (2.22×) and from **81.52 to 162.61** (1.99×). Total throughput per GPU goes from 4,255 to 6,729 tokens/s (1.58×), from 6,315 to 8,882 (1.41×) and from 10,998 to 14,839 (1.35×).
- A standard decoder layer runs as 2 kernels instead of 32, in 115 µs instead of 320 µs. A decode period of one request takes 7.2 ms instead of 17.9 ms.
- GSM8K strict match at concurrency 7, 3 runs each: `main` averages 0.9247 and this PR 0.9270 (pooled p 0.49). Over all 5 runs of `main` and the 9 runs of this PR's versions, the mono path is 0.14 points lower (p 0.54). Neither difference is significant. The mono kernels quantize the activations to MXFP8, where vLLM's gfx942 path keeps bf16.
- gfx950 is unchanged. A compile-only gfx950 build of the 20 kernels before and after this PR gives the same instruction counts, apart from 1 or 2 `s_waitcnt` and `s_nop`. No MI355X was used.
- The gfx942 kernels run only with the switch on, on gfx942. Two small changes apply without the switch, see "Changes outside the switch".

## Requirements of the gfx942 mono path

Mono kernels are built for fixed shapes. A deployment or a step outside these limits runs vLLM's own path.

| | gfx942 (this PR) | gfx950 (#60397) |
|---|---|---|
| Tensor parallel size | 4 | 2 or 4 |
| Rows a decode step, requests × (1 + drafts) | at most 42 | at most 48 |
| Concurrency with 5 DSpark drafts | up to 7 | up to 8 |
| Concurrency without drafts | up to 40 with FULL CUDA graphs, 42 in eager mode | up to 48 |
| Steps | decode only, eager or a FULL CUDA graph | same |
| KV cache | `fp8_ds_mla` | same |
| MoE | DeepSeek-V4.1 routing: 384 experts, top 6, sqrtsoftplus, ×1.5, a shared expert. The draft layers use 128 experts and top 3. | same, no draft layers |

- The row limit comes from LDS. A gfx942 workgroup has 64 KB of LDS, against 160 KB on gfx950. So a gfx942 GEMV pass holds the x rows of 6 tokens instead of 16, and a step of 12 to 42 rows runs 2 to 7 passes on weights loaded once.
- A FULL CUDA graph step runs padded to the next graph size, and the mono path takes the padded step. With 5 DSpark drafts the graph sizes are 6, 12, 18, 24, 36, 42 and 48 rows, so a step of 5 requests runs as 36 rows.
- At TP2 on gfx942 the path logs one line, and every layer runs vLLM's path. A TP size other than 2 or 4 is an error at startup, as in #60397.
- A step outside the limits, for example prefill, a mixed step, more than 42 rows or a PIECEWISE graph, runs vLLM's path on every layer and every rank. Both paths take and return the same tensors at each layer, so the engine can switch between them from one step to the next.

### Accuracy

**GSM8K.** `lm_eval` `gsm8k` (the stock task), 5-shot, all 1,319 questions, greedy, at most 512 new tokens, through `/v1/completions`. Both arms use DSpark block rejection for these runs, so the target model checks every draft token. At concurrency 7 the steps have 6 to 42 rows, and with this PR all of them take the mono path. Strict-match of each run:

| | `main` | This PR |
|---|---|---|
| Concurrency 1 | 0.9340, 0.9318 | 0.9272 (827fb9d) |
| Concurrency 7 | 0.9242, 0.9257, 0.9242 | 0.9295 (827fb9d), and 0.9242, 0.9265, 0.9303 (4f0fc5d) |

Two runs of the same code differ by up to 0.6 points, so the runs are pooled with a Cochran-Mantel-Haenszel test with one stratum a question. At concurrency 7, over the 3 runs on each side, this PR scores 0.23 points more than `main` (p 0.49, bootstrap 95% interval from 0.40 points less to 0.83 points more). Over all 5 runs of `main` and the 9 runs of this PR's versions, the mono path scores 0.14 points less (p 0.54, 95% interval from 0.65 points less to 0.36 points more). An earlier version of this description said 0.66 points less (p 0.05). That pool had `main`'s 2 runs at concurrency 1 only, and `main`'s 3 runs at concurrency 7 average 0.82 points below them. ### What this PR changes

- **The mono kernels on CDNA3** (4a36cc4). gfx942 has no scaled FP4 or FP8 MFMA and uses FNUZ FP8. The kernels compute the same layer with FNUZ FP8 MFMAs on their own copies of the dense weights and dequantize the FP4 experts in VALU. The FP4 and FP8 weight bits do not change.
- **More layers take mono launches than on gfx950.** The window layers 0 and 1 run whole. The 8 index layers run K1, then vLLM's compressor and indexer, then K2. The 3 DSpark draft layers take the FFN launch. On gfx950 the window and index layers run vLLM's attention and then the FFN launch, and the draft layers run vLLM's path.
- **Steps of up to 42 rows** (2dd3ff8). A GEMV pass takes 6 tokens, so that its x rows fit in 64 KB of LDS, and a step of 12 to 42 rows runs up to 7 passes on weights loaded once.
- **gfx942 ops around the mono launches:** the indexer's decode top-512 and candidate logits (d14f7e7), the SWA decode metadata and the top-k packing as one launch each (628c987), and DSpark's Markov sampling as one launch a draft step (cfab906).
- **Load and reload** (f5994b7, 4f0fc5d). The gfx942 copies of the weights are made when vLLM processes the weights at load, so vLLM counts them as model memory when it sizes the KV cache. A reload writes the new copies into the first ones in place, because the kernels and the captured CUDA graphs hold the addresses of the first copies.

### Changes outside the switch

- `rocm_unquantized_gemm_impl`: on gfx942 the `wvSplitK` skinny GEMM now takes at most 4 rows, for every model. At 5 rows it read the DSpark draft's 32320 × 5120 lm_head shard at 1.1 TB/s (297 µs, against 91 µs on hipBLASLt). Only that shape was measured. Other 5-row unquantized GEMMs on gfx942 now also run on hipBLASLt.
- `_prepare_dflash_inputs_kernel`: the padding loops step 1,024 entries at a time instead of the step's block size, on every platform. They write the same values. It took about 44 µs a call on MI325X. It was not measured on other platforms.

### Memory

The gfx942 kernels read their own copies of the weights: the routed experts in the byte order of the gfx942 GEMVs, without vLLM's padding columns, and the dense linears as e4m3 bytes, because vLLM dequantizes those to bf16 on gfx942. vLLM keeps its own tensors for prefill and for the steps that run its path. At TP4 the weights take 170.11 GiB a rank instead of 98.88 GiB (+71.23 GiB). On MI325X (256 GiB) with `--gpu-memory-utilization 0.9` the KV cache gets 28.59 GiB instead of 100.0 GiB, 11.18 million tokens instead of 39.11 million, which still holds 10 requests of 1M tokens. Before f5994b7 the dense copies were made in the first decode step, inside vLLM's memory profile, and the KV cache got 27.77 GiB (10.86 million tokens). MI300X (192 GiB) does not fit this well. Before f5994b7 the server did not start at 0.9, and at 0.955, about the most that is free at worker startup, the KV cache held 149K tokens. So the numbers and the recipe of this PR are for MI325X. Most of the 71 GiB are the routed-expert copies (about 69 GiB). One copy of the experts would remove them, see Follow-ups.

### Notes

- `topk512_gfx942.cu` is built with hipcc when the model is created, because the installed `vllm` package has no `csrc`. If the build fails, a warning is logged and the indexer runs vLLM's top-k ops. Its helpers are vLLM's `csrc/libtorch_stable/sampler.cu` lines 48 to 571, unchanged.
- `VLLM_ROCM_MONO_SHADOW=1` is a debugging aid for eager steps. It runs vLLM's own layer after each mono layer, logs how far apart the outputs are, and continues with vLLM's outputs.
- Every TP rank takes the same path at every layer, as in #60397, because the kernels wait on each other's pushes.

### Follow-ups

- Steps of more than 42 rows on gfx942, so that 8 or more concurrent requests with 5 DSpark drafts also take the mono path. This needs to be fixed, and we are working on it. At 48 rows the shared expert has 288 units for 256 CTAs, so some CTAs have to run two. At high concurrency vLLM's path may be faster, so the largest step that takes the mono path should come from measurements.
- One copy of the routed experts instead of two, for example with vLLM's prefill MoE reading the gfx942 copies.
- Other TP sizes on gfx942. Only TP4 is built and tested.
- `topk512_gfx942.cu` as a compiled vLLM op in `csrc/` instead of an extension built at startup.
- The two changes outside the switch as their own small PRs.

**2. `tests/models/test_dsv41_mono_decode.py` fails 6 of 26 with this PR**, none of them hardware-dependent: the CDNA message is now "needs CDNA3/4", the mocks lack `layer.engram`, `runner.ffn()` takes `topk`, and a path needs the TP group. ### Recommended, fine as follow-ups

**5. Reloaded weights don't reach the copies.** `_capture_plain_experts` skips the rebuild when `mono942` exists, and the dense copies are cached on first use, so after `reload_weights` or an RL weight update, prefill uses the new weights while ≤6-row decode silently uses the old ones. Captured graphs hold the copies' pointers, so a fix would `copy_` into them in place.

**6. The two changes outside the switch** (the `wvSplitK` ≤4 rows on gfx942 for every model, and the DFlash padding on every platform) each have a single measurement behind them. They'd be easier to land and to bisect as their own small PRs.

### Nits

- The dense copies (~1.8 GiB) are built at the first eager decode step, which by default is the cudagraph memory-profiling pass, so they're counted as graph memory (estimate 5.74 GiB with mono vs 3.40 without). That works, but only by accident: with graph-memory profiling off or `enforce_eager` they'd escape accounting. Building them at load would be clearer.
- `common/arch.py` decides `GFX942` from the `ARCH` env var, while `_on_gfx942()` asks the platform. A stray `ARCH` (a generic name) can make the weight copies and the kernel builds disagree.
- A gfx942 twin of the parent's new 300-replay graph stress (both widths, one graph, bit for bit) would guard the FNUZ copies' path; the shadow mode (`VLLM_ROCM_MONO_SHADOW`) already provides the harness.

For what it's worth, the FNUZ re-encoding traced as exact: the bf16 → e4m3 round trip, the halved bit patterns with scale code +1, subnormals and −0. The checkpoint's scale codes (dense 109–121, experts 115–127) are well clear of the E8M0 edge cases.
