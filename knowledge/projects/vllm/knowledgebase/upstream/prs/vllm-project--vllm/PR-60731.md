# [ROCm][Perf][DSv4.1] Mono decode on MI300X and MI325X (gfx942)

[Upstream PR](https://github.com/vllm-project/vllm/pull/60731) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

This PR ports the DeepSeek-V4.1-Flash mono decode kernels of #60397 to gfx942 (MI300X and MI325X). A standard decoder layer then runs as 2 kernels instead of 32. The path is opt-in with `--monokernel`, as on gfx950.

The PR was rebased onto `main` after #61082 as one commit. The commits after it merge `main` and answer the second review (see Details). gfx942 now runs the same layers whole as gfx950, with the switch of #61082 (see Details). The latest commits take the PR out of shared code, as RFC #60904 asks, and merge `main` with #62131 (see Details). The AgentX and GSM8K comparisons below are from 67206b7 and the commits before it, when the switch was `VLLM_ROCM_MONO_DECODE=1`. The checks of the latest commits are at the end of Validation.

## Claims

MI325X, TP4, DSpark with 5 drafts. Each AgentX run is 3,600 s and is scored with InferenceX's own result code.

- AgentX at concurrency 1, against `main`: interactivity P50 goes from **216.85 to 503.53 tokens/s/user** (2.32×), P90 from **182.25 to 411.26** (2.26×), and total throughput per GPU from 4,024 to 6,546 tokens/s (1.63×).
- AgentX at concurrency 2, 4 and 8, against InferenceX's published MI325X points: P90 goes from **153.22 to 368.64** (2.41×), from **142.75 to 316.28** (2.22×) and from **81.52 to 162.61** (1.99×).
- A standard decoder layer takes 115 µs instead of 320 µs. A decode period of one request takes 7.2 ms instead of 17.9 ms.
- GSM8K strict match at concurrency 7, 3 runs each: `main` 0.9247 and this PR 0.9270 on average (pooled p 0.49). The difference is not significant.
- On a2ce22d7e317 at concurrency 7, GPQA-Diamond is 85.0%, AIME25 99.0% and RULER NIAH 40 of 40 in every cell, against 85.3%, 99.4% and 40 of 40 for the reference arm of #60397 on MI355X.
- The gfx942 code runs only with `--monokernel`, on gfx942. Outside `vllm/models/deepseek_v41/` and the tests, the PR adds an 8-line hook to the DSpark speculator and two CI jobs.
- On gfx950 all 76 builds of the mono kernels, the 12 of the DSpark draft's runner included, have the same register and LDS use as on `main` and the same count of each instruction, apart from 1 or 2 more `s_waitcnt` in K2 and the FFN launch. The draft runner's scratch is now laid out for its MoE, see Details.
- On MI355X with `--monokernel` at TP2, two runs of each arm on 6caadd0, before #62131: GSM8K strict match 0.9257 and 0.9242 against 0.9249 and 0.9272 for `main` (see Validation).

## Limits on gfx942

- TP4 only. At TP2 the path logs one line and every layer runs vLLM's path.
- Decode steps of up to 42 rows, which is 7 requests with 5 DSpark drafts. A gfx942 workgroup has 64 KB of LDS, against 160 KB on gfx950, so a GEMV pass takes 6 tokens instead of 16. A larger step, prefill, a mixed step and a PIECEWISE graph run vLLM's path on every layer and every rank.
- gfx942 has no scaled FP4 or FP8 MFMA and uses FNUZ FP8, so the kernels read their own copies of the weights. At TP4 the weights take 170.11 GiB a rank instead of 98.88 GiB. On MI325X with `--gpu-memory-utilization 0.9` the KV cache still holds 11.18 million tokens. MI300X (192 GiB) does not fit this well, so the numbers here are for MI325X.

## Details

- **Layers.** gfx942 runs every backbone layer whole, as gfx950 does since #61082. The index layers use vLLM's FP8 indexer, because the MXFP4 indexer cache needs CDNA4. vLLM's compressor and indexer run between K1 and K2, as on gfx950. On gfx942 `mono/keylist.py` then writes the layer's key lists, so K2 is the build without the key table. On gfx942 the 3 DSpark draft layers take the FFN launch after vLLM's attention, built for the draft's 128 experts and top 3, on the target's runner. On gfx950 they run whole on a runner of their own, as #62131 added.
- **gfx942 helper ops** in `vllm/models/deepseek_v41/amd/ops/`: the sparse indexer's decode top-512 (`topk512_gfx942.cu`) and its candidate logits, the SWA decode metadata and the top-k packing as one launch each, and DSpark's Markov sampling as one launch a draft step. With `--monokernel` on gfx942 the V4.1 ROCm attention takes the indexer layer of `sparse_indexer.py`. It runs vLLM's ROCm indexer op on every step except a step of only decode rows, which runs the decode path of that op with the top-k launches in front of vLLM's ops. The DSpark speculator asks the draft model's `sample_sequential` first, and the DSv4.1 draft model runs the fused Markov launches there. `draft_lm_head.py` pads the DSpark draft's 5-row logits GEMM to 6 rows, so that vLLM's dispatch takes the torch GEMM instead of `wvSplitK`. For the 32320 × 5120 lm_head shard that takes 96 µs instead of 295 µs on MI325X. Each helper leaves a call it cannot take to vLLM's own op. `topk512_gfx942.cu` is built with hipcc when the model is created. If the build fails, a warning is logged and the indexer runs vLLM's top-k ops.
- **Weight copies.** The routed experts are copied in the byte order of the gfx942 GEMVs, without vLLM's padding columns, and the dense linears as e4m3 bytes, because vLLM dequantizes those to bf16 on gfx942. The copies are made when vLLM processes the weights at load, so vLLM counts them as model memory when it sizes the KV cache. A reload writes the new copies into the first ones in place, because the kernels and the captured CUDA graphs hold their addresses.
- **Changes outside the model directory.** One hook in the DSpark speculator: `_sample_sequential` asks the draft model's `sample_sequential` first, if the model has one, and runs its own loop when the call returns False. Only the DSv4.1 draft model has one, and it takes a step only with `--monokernel` on gfx942. The rest are the two CI jobs. The earlier hooks in `rocm_aiter_mla_sparse.py` are now the indexer layer of `sparse_indexer.py`. The change of the padding loops of `_prepare_dflash_inputs_kernel` is dropped, because #58633 parallelises the same padding.
- **Merge of #62131.** #62131 runs the DSpark draft layers whole on gfx950, on a runner of their own whose MoE takes one FP4 group an ug task (`DRAFT_UG_GROUPS`). Its scratch was laid out for the default two groups, and with one group the ug flags take twice the room. So the flags of the upper half of the tasks were written over the start of the `normed` rows that the MoE reads as its input, at TP 2 and 4 and for every step width. Only the draft layers could be affected, not the target's output, and in a GSM8K check on MI355X `main` accepted as many drafts as this PR, so the overlap did not show there. `scratch_layout` and `scratch_bytes` now take the runner's groups. `run_ffn` checks that each MoE region of a build fits the layout, and that check found the overlap when the draft runner's K2 was built. The FFN launch reads the target's layout, because it runs on the target's runner, also for a gfx942 draft layer.
- **Since the first review.** The branch is rebased onto `main` as one commit. The gfx942 ops moved from `vllm/model_executor/layers/dsv41_gfx942/` into `vllm/models/deepseek_v41/amd/ops/`, as RFC #60904 asks for model kernels. `VLLM_ROCM_MONO_SHADOW` and its layer-by-layer check are removed. The rebase onto #61082 takes its switch and its layer plan on gfx942 too. That removes the gfx942 paths of their own for the first layer, the window layers and the index layers, apart from `mono/keylist.py`.
- **Since the second review.** The kernel tests moved to `tests/kernels/models/amd/`. The fused Markov test checks each draft token against vLLM's `_sample_logits` on the same step's cached logits. The change to vLLM's skinny GEMM dispatch is reverted, and only the DSpark draft's lm_head avoids `wvSplitK`, with `--monokernel` on gfx942. `test_dsv41_mono_layers.py` and a gfx942 graph replay test in `test_dsv41_mono_numerics.py` run at TP4 in a new four-GPU MI300 job. On gfx942 the first layer's output bound in `test_dsv41_mono_layers.py` is 6% instead of 3%, because vLLM's gfx942 MoE keeps bf16 activations and the kernels quantize them to MXFP8, which alone moves the FFN output of the test's random weights by 4.65%. The residual stream then differs by up to 2.5% instead of 0.4 to 0.7%, so past the first layer a routing near-tie there is a gap of up to 0.02 instead of 0.01, and up to a third of the tokens may flip an expert instead of a quarter (22% seen).
- **Relation to other PRs.** Draft #61482 moves the FlyDSL stages to `vllm/models/common/amd/mono/`, and this PR edits the files it moves. Whichever of the two merges second needs a rebase. If this PR merges first, its gfx942 tests can check #61482's move on MI325X. #62131 is merged into this branch, see Merge of #62131. #58633 parallelises the padding of `_prepare_dflash_inputs_kernel`, which this PR changed until the latest commits, and neither PR needs the other. #61311 moves `amd/mono/` to `amd/specialized_decode/mono/` and replaces `mono_decode.py`, as RFC #60904 describes. A trial merge of the two conflicts in 15 files, among them `mono_decode.py` and `tests/models/test_dsv41_mono_decode.py`, which #61311 deletes and this PR changes. So whichever of the two merges second needs a port. #61869 adds a fused Markov sampler at the start of `_sample_sequential`, next to this PR's hook, and the two merge there without a conflict.
- **Follow-ups.** Steps of more than 42 rows on gfx942, so that 8 or more concurrent requests with 5 drafts also take the mono path. One copy of the routed experts instead of two. Other TP sizes on gfx942. The whole DSpark draft layers on gfx942, as on gfx950. `topk512_gfx942.cu` as a compiled op in `csrc/`.

### Would like to see before merge

**1. `topk512_gfx942.cu` is JIT-built with `torch.utils.cpp_extension.load` at the first decode step.** vLLM builds its kernels through `csrc/` and CMake; a runtime hipcc build needs hipcc and a writable extension cache at serve time, fails mid-serving instead of at startup, and has no fallback. Please move it into `csrc/` (or at least build at startup with a fallback to `top_k_per_row_decode`).

**2. `tests/models/test_dsv41_mono_decode.py` fails 6 of 26 with this PR**, none of them hardware-dependent: the CDNA message is now "needs CDNA3/4", the mocks lack `layer.engram`, `runner.ffn()` takes `topk`, and a path needs the TP group. It runs in the MI355 Basic Models step, so CI goes red once it runs.

**3. MI300X doesn't really fit.** With the copies, the description's own `--gpu-memory-utilization 0.9` fails at startup on MI300X; the ceiling is ~0.955 (only ~184 of 192 GiB free at worker startup), leaving 2.31 GiB of KV — 149K tokens, about two 64K requests, and not one at the recipe's 1M context. Most of the +70 GiB is the routed-expert copies (~69 GiB). I'd scope the claims to MI325X, or document the MI300X limits.

**4. The rebase onto #60397's new head needs care.** The parent's new `MonoLayerWeights.check` asserts the gfx950 layout (fp4x2 `w13`, E8M0 block scales, padded intermediate); on gfx942 the tensors are the `weights942` copies (FNUZ bytes, tile-major, padding cut), so the check needs a gfx942 variant or the copies go unchecked — the exact gap the parent's fix closed. The unit test file also changed there (new MoE-rejection and padded-step cases), so it's a reconcile, not just fixing the 6 failures.

### Recommended, fine as follow-ups

**5. Reloaded weights don't reach the copies.** `_capture_plain_experts` skips the rebuild when `mono942` exists, and the dense copies are cached on first use, so after `reload_weights` or an RL weight update, prefill uses the new weights while ≤6-row decode silently uses the old ones. Captured graphs hold the copies' pointers, so a fix would `copy_` into them in place.

**6. The two changes outside the switch** (the `wvSplitK` ≤4 rows on gfx942 for every model, and the DFlash padding on every platform) each have a single measurement behind them. They'd be easier to land and to bisect as their own small PRs.

### Nits

- The dense copies (~1.8 GiB) are built at the first eager decode step, which by default is the cudagraph memory-profiling pass, so they're counted as graph memory (estimate 5.74 GiB with mono vs 3.40 without). That works, but only by accident: with graph-memory profiling off or `enforce_eager` they'd escape accounting. Building them at load would be clearer.
- `common/arch.py` decides `GFX942` from the `ARCH` env var, while `_on_gfx942()` asks the platform. A stray `ARCH` (a generic name) can make the weight copies and the kernel builds disagree.
- A gfx942 twin of the parent's new 300-replay graph stress (both widths, one graph, bit for bit) would guard the FNUZ copies' path; the shadow mode (`VLLM_ROCM_MONO_SHADOW`) already provides the harness.

For what it's worth, the FNUZ re-encoding traced as exact: the bf16 → e4m3 round trip, the halved bit patterns with scale code +1, subnormals and −0. The checkpoint's scale codes (dense 109–121, experts 115–127) are well clear of the E8M0 edge cases.
