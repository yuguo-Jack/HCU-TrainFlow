# [Bugfix][Model Runner V2] Profile the batch-sharded all-to-all before sizing the KV cache

[Upstream PR](https://github.com/vllm-project/vllm/pull/61025) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

With `--enable-batch-sharded-sampling` (#50465), the memory profile run samples through the gathered `compute_logits` path. So the sharded path's `all_to_all_single` first runs in the kernel warm-up, after the KV cache has already taken the memory budget. On memory-tight GPUs, NCCL then cannot allocate its all-to-all buffers, and start-up fails. This PR runs the sharded path once in `_dummy_sampler_run`, so those buffers exist before the KV cache is sized.

## Claims

- With batch-sharded sampling on, the profile run executes the same all-to-all as serving. NCCL's buffers for it are then counted in the memory profile, not allocated after the KV cache.
- No change when the flag is off.

## Validation

**Reproducer (measured):**
- Setup: Qwen3.8-Flash-Next-FP8, TP8 + EP, 8 × A100-SXM4-40GB, `--gpu-memory-utilization 0.9`, FP8 KV, MTP 3, `--enable-batch-sharded-sampling`. The model support comes from #61018.
- Without this fix, start-up fails in `warmup_kernels` → `sample_tokens` → `all_to_all_logits` → `all_to_all_single`, with `RuntimeError: NCCL Error 1: unhandled cuda error`. On all 8 ranks the NCCL log shows `include/alloc.h:320 (ncclCuMemAlloc) NCCL WARN Cuda failure 2 'out of memory'`.
- Before the failure, every rank logged "Batch-sharded sampling enabled."

**With this fix (measured, same node type and command):**
- Start-up passes warm-up on all 8 ranks. All ranks log "Batch-sharded sampling enabled.", there is no NCCL OOM, and the server answers requests.
- The memory profile now counts the all-to-all's NCCL buffers. Per GPU, at `--gpu-memory-utilization 0.9`:

| | Flag off (control) | Flag on, with this fix |
|---|---:|---:|
| Weights + non-torch memory | 17.75 GiB | 20.62 GiB (+2.87 GiB) |
| Peak activation | 1.98 GiB | 1.97 GiB |
| CUDA graphs | 0.71 GiB | 0.71 GiB |
| KV cache memory | 15.82 GiB | 12.95 GiB |
| KV cache size (tokens) | 2,128,699 | 1,742,619 (−18 %) |

- So on 40 GB GPUs, batch-sharded sampling costs about 2.9 GiB per GPU of NCCL point-to-point buffers. Without this fix, that memory is not reserved and start-up fails. With it, the cost is visible as a smaller KV cache. A possible mitigation for users is to limit NCCL point-to-point channels (for example `NCCL_MAX_P2P_NCHANNELS`), because this all-to-all moves only a few MB per step. I have not measured that yet.
- Serving (MLPerf agentic full set, 20 concurrent sessions, 3 × 60 min): the server ran all three repeats with no error. The goodput was lower than with the flag off (1.35–1.38 vs 1.83–1.89 req/s), because of the smaller KV cache on this capacity-bound workload; that is a property of batch-sharded sampling on 40 GB GPUs, not of this fix. Without this fix the same command does not start.

- `ruff check` and `ruff format --check` (ruff 0.14.0): clean.
- Unit tests: none added. The existing `tests/v1/worker/test_gpu_batch_shard.py` covers the routing math with mocks; the profile path needs a multi-rank NCCL group and the memory pressure of a real model to show the failure, so the validation above is end to end. I will add a unit test if reviewers want one.
- Duplicate check: no open PR or issue covers this (searched `batch-sharded profile all_to_all`, `sharded sampling OOM`).

## Details

- **Root cause:** `profile_run` → `_dummy_sampler_run` always called `self.model.compute_logits` (all-gather) and the sampler. `torch.distributed.all_to_all_single` on the TP device group allocates its NCCL point-to-point buffers on first use. That first use was in `warmup_kernels`, which runs after `determine_available_memory` and the KV cache allocation.
- **Fix:** in `_dummy_sampler_run`, when `batch_sharder` is set, shard the dummy batch with `shard_sampler_inputs`, compute `compute_logits_local` on the owner-sorted rows, and run `all_to_all_logits`. This is the same sequence as `sample()`. A rank that owns no dummy request skips the sampler. All ranks reach the collective, because `profile_run` runs on every worker.
- **Size:** +16 / −1 lines in `vllm/v1/worker/gpu/model_runner.py`, in the profile path only.
- **Trade-off:** the KV cache is smaller by the size of the NCCL all-to-all buffers. That memory was needed anyway; without the fix, start-up fails instead.
