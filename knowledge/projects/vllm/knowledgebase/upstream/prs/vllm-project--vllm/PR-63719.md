# [Bugfix][ROCm] Take DSA candidate scores and sampler fp32 logits from persistent buffers

[Upstream PR](https://github.com/vllm-project/vllm/pull/63719) · state: open · merged: False

## Original PR description

## Overview

Stop two per-step tensors that scale with the number of decode rows from being allocated fresh every step: the DSA indexer's candidate-block scores and the sampler's fp32 logits copy. On MI300X with DeepSeek-V4.1-Flash and DSpark, the fresh copies outgrow the caching allocator's blocks while the batch ramps up, reserved memory climbs ~21 GiB/GPU above the profiled peak, the device fills, and the TP group hangs at ~200-250 running requests.

## Claims

- Fixes the engine hang at high concurrency on ROCm (same signature as #41530 and #36921): with this change two TP4 engines serve 512 concurrent agentic users through 268 running requests each with no hang, on the same `gpu_memory_utilization` and `max_model_len` that hung before.
- Reserved memory stays within ~6 GiB of the peak measured at startup instead of ~21 GiB above it.
- No numerics change: same kernels, same values, speculative acceptance length and inline task accuracy unchanged. Throughput unchanged.

## Validation

**Reproducer.** DeepSeek-V4.1-Flash on 8x MI300X (gfx942), ROCm nightly image `vllm/vllm-openai-rocm@sha256:e7d4d864…` (v0.31.1rc1.dev376, `5555a2d8`), two independent TP4 engines, `--max-num-seqs 320 --gpu-memory-utilization 0.9 --max-model-len 1048576`, DSpark k=5, `FULL_AND_PIECEWISE` graphs, MLCommons Endpoints v1.0 agentic client at 512 concurrent users (1,024 trajectories). Every run on this configuration hung within ~8 min at 240-285 running requests per engine; workers park in `shm_broadcast` and the sampling RPC times out.

| | live tensor memory, peak | reserved by the allocator | running requests | outcome |
|---|---|---|---|---|
| main | 161.1 GiB | 182 GiB and rising | 251 / 247 | hang after 8.5 min |
| this PR | 161.8 GiB | 167.6 GiB, flat from minute 15 | 268 / 255 | completed, 6,043 tok/s |

Live memory never exceeded the 161 GiB that the startup profile measured; the growth was entirely freed-but-cached blocks. Allocator snapshots (`torch.cuda.memory._record_memory_history`) attribute them to `candidate_blocks.py:select_candidate_blocks` (`scores`, 0.5 MB per decode row) and `sampler.py:apply_sampling_params` (fp32 logits copy, 0.49 MB per row): 46 blocks of 320-720 MiB, each one step's copy, each larger than the last as the batch grew.

**Numerics (same configuration, fix vs. none):** speculative acceptance length 3.544 / 3.555 vs 3.537 / 3.550 per engine; inline accuracy 54.46 % vs 54.68 %; mean output length 928 vs 937 tokens (debug-length points; the spread between identical points is larger than these differences).

**Tests.** `tests/kernels/attention/test_dsa_candidate_block_scores_buffer.py` and `tests/v1/worker/test_gpu_sampler_fp32_buffer.py`: the output equals the fresh-tensor path (including after a larger previous step has left values in the buffer), a step larger than the buffer still works, and the peak allocation during the call is below one row-proportional tensor. The memory assertions fail on main.

## Details

**Root cause.** The caching allocator serves a request from a cached block only if one is at least as large. While the batch ramps up, each step's `scores` / fp32 logits is larger than every cached copy, so every step `cudaMalloc`s a new segment and the outgrown copies stay cached. Nothing trims them: PyTorch only releases cached blocks when a `cudaMalloc` fails, and on this ROCm stack a full device does not fail the allocation but stalls the worker (allocator retry count stayed at 0 through the hang). vLLM's startup profile is correct about live memory; it cannot see allocator growth driven by step-to-step shape changes. Allocator settings do not help here: `expandable_segments:True` deadlocks the TP workers during initialization on ROCm, and `garbage_collection_threshold` requires a per-process memory fraction vLLM does not set.

**Change.**
- `select_candidate_blocks` scores into a workspace resource reserved during the memory profile (`reserve_candidate_scores`, called from the ROCm indexer's profiling early-exit, sized `max_num_seqs * (1 + num_speculative_tokens) * ceil(max_model_len / candidate_block_size)` floats, ~1 GiB at the reproducer's settings). Without a reservation, or for a larger step, it allocates as before. The kernel writes every score it reads, so the buffer's previous contents do not matter, same as the previous uninitialized `new_empty`.
- `Sampler` keeps one fp32 logits buffer sized `max_num_reqs * (1 + num_speculative_tokens) x vocab_size` and copies each step's logits into its first rows; a larger step falls back to the previous allocation.
- The attention-kernels CI step gains `vllm/model_executor/kernels/attention` as a source dependency so the new test runs when the DSA kernels change.

**Trade-offs and limitations.** Both buffers are allocated before the memory profile, so they come out of the KV budget (~2 GiB/GPU at TP4 for this model). The remaining per-step growth (~6 GiB in the reproducer: indexer prefill logits, norm scratch, all-gather outputs) is bounded and did not matter at 512 users; the logits all-gather output was left alone because a shared buffer there could alias a result still in use. The ROCm behaviour of stalling instead of failing an allocation on a full device is unchanged by this PR and is being reported separately; a self-contained process group (alone, under RCCL, under aiter's IPC all-reduce) fails cleanly, so that stall needs vLLM's full state to reproduce.
