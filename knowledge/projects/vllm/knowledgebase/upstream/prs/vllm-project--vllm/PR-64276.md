# [Bugfix][Model] Kimi-K3: shard the latent-MoE tail over the TP group

[Upstream PR](https://github.com/vllm-project/vllm/pull/64276) · state: open · merged: False

## Original PR description



## Overview

Without expert parallelism, `FusedMoEConfig.tp_size` is DP x PCP x TP: FusedMoE folds the DP replicas into its expert-sharding width. The NVIDIA Kimi-K3 `LatentMoERunner` uses that number as the size of the TP group. With DP > 1 its column-parallel tail (more than 256 tokens per rank) then adds the routed expert output to only the first 1/DP of the 7168 hidden columns. This PR uses the TP world size there instead, as #54956 already did for the ROCm runner.

## Claims

- Kimi-K3 with TP x DP and no expert parallelism: every hidden column now gets the routed expert output in the column-parallel tail. On main, only 3584 of 7168 columns get it with TP8 x DP2, and 1792 of 7168 with TP4 x DP4. These two layouts are what the Kimi-K3 recipe's `multi_node_tp_dp` strategy runs (no `--enable-expert-parallel`), on H200 and on GB200/GB300 respectively.
- The tail's fused all-reduce + RMSNorm (`allreduce_norm_latent_out`) now gets the TP world size for its FlashInfer workspace, and the TP=8/16 check for the SM100 tail-fusion op now looks at the TP world size. On main, both get DP x TP.
- TP-only and expert-parallel runs are unchanged. Without DP or PCP, `moe_config.tp_size` already equals the TP world size. With expert parallelism `moe_config.tp_size` is 1 and the runner does not take this path: the `_use_fused_path()` gate is left as is.

## Details

**Root cause.** Without expert parallelism, `FusedMoEParallelConfig.make` (`flatten_tp_across_dp_and_pcp`) sets the MoE `tp_size` to DP x PCP x TP and shards every expert across all of those ranks. The naive DP all2all all-gathers the tokens over DP and reduce-scatters the expert output back, so after the combine each rank holds a TP-partial latent for its own tokens. From there on only the TP group shares a token's hidden vector. `_shard_up_proj_tail` (tier 2) computed `shard_size = 7168 // moe_config.tp_size`, took the shard at `tp_rank * shard_size`, and added `latent @ W_shard.T` into that slice of the TP-partial shared-expert output before the final TP all-reduce. With TP8 x DP2 that is a 448-column shard per TP rank, so the 8 TP ranks cover columns 0-3583. Columns 3584-7167 get only the shared experts.

**Related sites.**
- `allreduce_norm_latent_out` (tiers 1 and 2) passed `moe_config.tp_size` as `world_size` to the FlashInfer fused all-reduce + RMSNorm, whose workspace is built on the TP group. For DP x TP = 16 on sm90 there is no FlashInfer size entry, so main already fell back to a plain TP all-reduce there. On SM100 a 16-rank workspace was requested on an 8- or 4-rank TP group. I have not run that case.
- The SM100 tail-fusion check `moe_config.tp_size not in (8, 16)`: TP4 x DP4 passed it (16), and `KimiK3LatentMoETailOp` then rejects its TP=4 contract with a `ValueError`. With this PR the runner logs the existing "supports TP=8 and TP=16" warning and falls back. This is from reading the code; I could not run it.
- `_use_fused_path()` keeps `moe_config.tp_size > 1`. That is what excludes expert parallelism (MoE `tp_size` 1). For TP1 x DP2 it now runs with a full-width shard and no-op TP collectives, which is correct.
- The ROCm `ROCmLatentMoERunner` already uses `get_tensor_model_parallel_world_size()` (#54956, whose description lists "TP=2 x DP=2: shards by 4, covers half the hidden dim").

**Impact.** On main, a Kimi-K3 deployment with TP x DP and no expert parallelism loses the routed experts' contribution in (DP-1)/DP of the hidden columns of every MoE layer, for every step where a rank has more than `VLLM_SHARED_EXPERTS_STREAM_TOKEN_THRESHOLD` (256) tokens: prefill chunks and large decode batches. Smaller steps use tier 1, which up-projects the full hidden dim on every rank, or on SM100 the tier-0 op, which shards over its own TP group. I did not measure the end-to-end effect on outputs.

**Fix choice.** Shard by the TP world size, rather than falling back to an unsharded tail when DP > 1. Each TP rank still computes 1/TP of the up-projection, the shared-expert all-reduce is still folded into the same all-reduce, and the code matches the ROCm runner.

**Limitations.**
- The only multi-GPU run is the TP2 x DP2 run above, with dummy weights. I have not run the Kimi-K3 checkpoint and have no model eval (lm_eval / GSM8K) for it. `AGENTS.md` asks for one when a change affects output.
- No SM100 or GB200/GB300 run, so the tier-0 and FlashInfer changes above are from reading the code.
- The test builds `LatentMoERunner` with `object.__new__` and sets `moe_config` and `routed_output_transform`. A real runner needs a full `FusedMoE` layer with experts, a router and a quant method. `tests/AGENTS.md` asks for real constructors and a regression test through `vllm_runner`. A `multi_gpu_test` with a small dummy-weight Kimi-K3 config at TP2 x DP2 would cover that. The run above does this with a plugin; I have not turned it into a test.
- CI: the test file is run by the ":nvidia: (B200) Kimi K3" and ":amd: (MI355) Kimi K3" steps (`models/kimi_k3`), and the new test needs no SM100 features.
