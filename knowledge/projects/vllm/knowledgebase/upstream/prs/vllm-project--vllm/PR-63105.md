# [ROCm][Build] Reland #62475: paged attention kernel split with `--offload-compress` => x4-x7 wheel build speedup on ROCm

[Upstream PR](https://github.com/vllm-project/vllm/pull/63105) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

**Only difference compared to #62475:** one line in `CMakeLists.txt`, adding `--offload-compress` to `VLLM_ROCM_EXT_FLAGS`.

**Toolchain scope:** `--offload-compress` exists since clang 18 (LLVM PR #67162, 2023-10: https://github.com/llvm/llvm-project/pull/67162). I only tested it with **ROCm 7.2.0 and 7.2.3 (clang 22)** and **ROCm 10.0.0 (clang 23)**; ROCm 6.x was not tested.

## Overview

`csrc/rocm/attention.cu` is a single 3.9k-line translation unit whose kernel instantiation is the tail of the ROCm build: ~9 min of a ~10.5 min build, on one core. This inflation was probably especially caused by recent: #42755  (adds `USE_INTERLEAVED_V_CACHE` as a template parameter to all 12 kernels = interleaved + non-interleaved instantiation (+50%))

This PR splits the instantiations into one translation unit per (dtype, kv-cache dtype, head size) combination so ninja builds them in parallel.

*Not a duplicate: no open issue or PR addresses this. The closest open items are #17419 and #60906.*

## Why #62475 broke the nightly build?

**TL;DR.** #62475 splits one huge kernel file into 12 smaller ones so they compile in parallel. Side effect: each of the 12 files now carries its own copy of the GPU debug info, so the linked library grows. #62475 measured that growth on **1 architecture** (+23 MB), but the nightly library is built for **9** architectures:
https://github.com/vllm-project/vllm/blob/49dbf7c44f8157285db653fbe789daa30df6cfc4/docker/Dockerfile.rocm_base#L26

At 9 architectures the library measures ~2200 MiB (its objects alone are 2149 MiB), and past ~2100 MiB a 32-bit relative address inside the library can no longer reach its target — the failing link overflowed at 2104 MiB — so both mold and lld refuse to link it:

```text
FAILED: [code=1] _rocm_C.abi3.so 
mold: error: /usr/local/lib/python3.12/dist-packages/_rocm_sdk_devel/lib/llvm/lib/clang/23/lib/linux/clang_rt.crtbegin-x86_64.o:(.text): relocation R_X86_64_PC32 against .eh_frame out of range: -2206798738 is not in [-2147483648, 2147483648)
clang++: error: linker command failed with exit code 1 (use -v to see invocation)
```

Plain `main` links fine but is already 2011.5 MiB, i.e. only ~93 MiB below where the split overflowed, while the split adds ~119 MiB of duplicated debug info. So the reland has to make the 9-architecture library *smaller* than today (e.g. `-Xarch_device -g0`, `--offload-compress`), not merely "not bigger".

Mold is selected for the `csrc-build` wheel at the main HEAD used for the measurements (49dbf7c44f8157285db653fbe789daa30df6cfc4):
  https://github.com/vllm-project/vllm/blob/49dbf7c44f8157285db653fbe789daa30df6cfc4/docker/Dockerfile.rocm#L335

Sizes measured at 9 archs, `RelWithDebInfo`, on e8ae84bf and on main, `MAX_JOBS=64`:

| | `main` (1 attention TU) | #62475 (12 attention TUs) |
|---|---|---|
| attention objects | 1088 MiB (`attention.hip.o`) | 1214 MiB (**+119 MiB** of duplicated device DWARF) |
| attention `.hip_fatbin` | 1070 MiB | 1189 MiB |
| `.hip_fatbin` in the link | 1983 MiB | 2103 MiB |
| build | 85 min 28 s | 21 min 34 s |
| build errors | none | none |
| link errors | none | `relocation R_X86_64_PC32 ... out of range` |

**Not a linker bug.** Switching mold for `lld` reproduces the same overflow, so this is the 32-bit PC32 reach and not a mold defect:

```text
ld.lld: error: CMakeFiles/_rocm_C_skinny.dir/csrc/rocm/skinny_gemms.hip.o:(.rodata+0x0): relocation R_X86_64_PC32 out of range: 2206616580 is not in [-2147483648, 2147483647]; references section '.text'
>>> referenced by skinny_gemms.hip
```

**Exact command that fails**, run at e8ae84bf7e992c63570905fce3073fd7a7de2412 (the merge of #62475) inside `vllm/vllm-openai-rocm:nightly-rocm100-39983a5e7a5a575a7829f5d5ada50a33d9337ec1` (same compiler, mold, 9 archs and `RelWithDebInfo` build type as the `csrc-build` stage of `docker/Dockerfile.rocm`):

```bash
PYTHONDONTWRITEBYTECODE=1 LDFLAGS="-fuse-ld=mold" \
  PYTORCH_ROCM_ARCH="gfx90a;gfx942;gfx950;gfx1100;gfx1101;gfx1200;gfx1201;gfx1150;gfx1151" \
  VLLM_DISABLE_SCCACHE=1 MAX_JOBS=64 \
  python3 setup.py bdist_wheel --dist-dir=dist
```

## Claims

- Cold 9-arch build drops from **85 min 28 s to 21 min 25 s** (4×, `MAX_JOBS=64`, mold): the attention kernels stop being one serial ~9-minute compile and become 12 parallel TUs of 58–72 s each (at 1 arch), and the `_rocm_C.abi3.so` link no longer waits behind them.
- The module now fits: instead of the ~2200 MiB that #62475 alone could not link, `_rocm_C.abi3.so` is **125.9 MiB** and `.hip_fatbin` **95.8 MiB** (from 2103 MiB), with no change to the shipped `RelWithDebInfo` build type or to the device debug info.
- No behavior change: identical template instantiations, identical dispatch order, unchanged `paged_attention` signature and op registration; the compressed kernels were executed on gfx950 (see Validation).
- Costs: aggregate CPU work grows (~30% more work, measured in #62475), and the module is decompressed at load — ~0.6 s moves from the first attention call into `import vllm`, while per-process RAM ends ~135 MiB lower.

**How the file got this big.** The instantiation matrix was grown one axis at a time:

| PR | landed | what it added | effect |
|---|---|---|---|
| #8310 | 2024-09-13 | initial ROCm custom paged attention | 1,038 lines, 4 kernels; already `{fp16,bf16}` × head `{64,128}` × block `{16,32}` × alibi `{on,off}` |
| #8577 | 2024-09-19 | fp8 KV cache | adds the `KV_DTYPE`/`cache_t` axis (fp8, `kFp8E4M3`) |
| #12348 | 2025-03-04 | "Faster Custom Paged Attention" rewrite | 4 → 6 kernels (`mfma16`, `mfma4`, partition `reduce`), +1,084/−422 |
| #17139 | 2025-05-07 | FP8 output fusion | `if (fp8_out_scale) → OUTT=uint8_t` = ×2 |
| #17004 | 2025-05-21 | RDNA/NAVI support on v1 | duplicates the kernel set for gfx11/gfx12, 6 → 12 `__global__`, ≈×2, +1,880/−171 |
| #22222 | 2025-09-15 | fp8 paged attention update | adds `MFMAType` (`Fp8` vs `F16`) = ×2 on the fp8 path |
| #42755 | 2026-10-15 | Qwen3-30B QK-norm/RoPE/KV-cache fusion | adds `USE_INTERLEAVED_V_CACHE` to all 12 kernels = +50% |

Cumulative, per architecture: 6 dtype/kv-cache combinations × head (2) × block (2) × fp8-out (2) × alibi (2) × {NAVI, non-NAVI, interleaved} ≈ 288 launcher instantiations → ~860 device kernels in one file. `--offload-arch` values are additionally compiled serially inside that file, so the 9-arch release build pays ~9× the per-architecture cost.

- `MAX_JOBS=64`, `VLLM_DISABLE_SCCACHE=1`, cold build directories.

| | `main` (pre-split `attention.cu`) | #62475 as merged | this PR (#62475 + `--offload-compress`) |
|---|---|---|---|
| cold build, 9 archs | 85 min 28 s | 21 min 34 s (**fails at link**) | **21 min 25 s** |
| `_rocm_C.abi3.so` | 2011.5 MiB | not produced (link fails) | **125.9 MiB** |
| `.hip_fatbin` | 1983 MiB (in the module) | 2103 MiB (sum of objects) | **95.8 MiB** (in the module) |
| `_rocm_C` objects, total | 2022 MiB | 2149 MiB | **142 MiB** |
| 12 attention TUs | `attention.hip.o` 1088 MiB | 1214 MiB | **84.5 MiB** (6.0–8.3 MiB each) |
| `skinny_gemms_int4.hip.o` | 846 MiB | 846 MiB | **32.1 MiB** |
| wheel | 379 MiB | not produced (no wheel) | 266 MiB |

The split is the 4× build win (21 min 34 s vs 85 min 28 s) and `--offload-compress` costs nothing measurable in compile time (21 min 25 s vs 21 min 34 s, within noise); the revert buys ~100 MB of link margin at the price of ~64 min per build.

Load cost on MI350 (gfx950): 10 runs per module, interleaved, one process per run, page cache dropped before every run (`sync; echo 1 > /proc/sys/vm/drop_caches`), vLLM installed from each wheel — the only difference is `vllm/_rocm_C.abi3.so`. Medians with min–max in parentheses:

| metric | `main` (2011.5 MiB module) | this PR (125.9 MiB module) |
|---|---|---|
| `import vllm` (dlopen + decompression) | 3.64 s (3.39–3.81) | 4.25 s (3.51–5.41) |
| first `paged_attention` call (HIP module load, gfx950) | 0.657 s (0.629–0.838) | **0.034 s** (0.029–0.059) |
| total to first kernel | 4.31 s (4.02–4.54) | 4.28 s (3.55–5.47) |
| RAM used by the vLLM process after `import vllm` | 836 MiB | 1168 MiB |
| RAM used by the vLLM process after first kernel | 1746 MiB | **1612 MiB** |

Compression moves ~0.6 s of work from the first attention call into `import vllm`, so time-to-first-kernel is unchanged (4.31 s vs 4.28 s) while the first request is 19x cheaper to serve (0.657 s → 0.034 s) and steady-state RAM use ends ~135 MiB lower.

### Why vLLM import uses more RAM now?

Same runs, showing the RAM used by the vLLM process (RSS from `/proc/self/statm`) split into anonymous (per-process, private) and file-backed (page cache, shared and reclaimable) at the three stages:

| point | `main` (2011.5 MiB module) | this PR (125.9 MiB module) |
|---|---|---|
| after torch init | 652 MiB = 303 anon + 346 file | 651 MiB = 303 anon + 344 file |
| after `import vllm` | 837 MiB = 430 anon + 403 file | 1168 MiB = 660 anon + 504 file |
| after first kernel | 1747 MiB = 1101 anon + 601 file | 1613 MiB = 1053 anon + 546 file |

Growth relative to torch init:

| stage | `main` | this PR |
|---|---|---|
| import (dlopen, decompression) | +127 anon, +57 file | **+357 anon**, +160 file |
| first kernel (module load) | **+671 anon**, +198 file | +393 anon, +42 file |
| total | +1094 | +962 |

Both builds converge on **~1.05 GiB anonymous** once the gfx950 code object is loaded: that is the loaded kernels, identical in both, which is why the final RAM use is comparable. Compression only changes *when* the device code is materialised — decompressed at import instead of paged in from a 2 GiB file at first kernel use — and ends ~134 MiB lower because the uncompressed module keeps more of its 2 GiB resident (`+601` vs `+546` file over baseline) plus ~48 MiB of extra anonymous data from parsing the larger fatbin. The file-backed share is page cache (shared, evictable); only the anonymous share is per-process, so a worker's private cost is the ~1.05 GiB, not the total.

and `load_time_bench.py`:

```python
"""Time `import vllm` (dlopen of _rocm_C + device-code decompression) and the
first paged_attention call (HIP module load for the current arch)."""
import ctypes, os, time
import torch


def rss_mb():
    return int(open("/proc/self/statm").read().split()[1]) * 4096 / 2**20


t0 = time.perf_counter()
torch.cuda.init()
torch.cuda.synchronize()
rss_torch = rss_mb()

import vllm, vllm._custom_ops as ops  # noqa: E402
t_import = time.perf_counter() - t0
rss_vllm = rss_mb()

so = os.path.join(os.path.dirname(vllm.__file__), "_rocm_C.abi3.so")
ctypes.CDLL(so, mode=ctypes.RTLD_GLOBAL)

# same tensors as tests/kernels/attention/test_attention.py
num_seqs, num_query_heads, num_kv_heads = 1, 8, 1
head_size, block_size, max_seq_len = 64, 16, 256
PARTITION_SIZE_ROCM, NUM_BLOCKS = 256, 4321
x = 16 // 2
torch.set_default_device("cuda")
scale = 1.0 / head_size**0.5
query = torch.empty(num_seqs, num_query_heads, head_size,
                    dtype=torch.float16).uniform_(-scale, scale)
seq_lens = torch.tensor([max_seq_len], dtype=torch.int)
block_tables = torch.tensor(
    [[1] * ((max_seq_len + block_size - 1) // block_size)], dtype=torch.int)
key_cache = torch.randn(NUM_BLOCKS, num_kv_heads, head_size // x, block_size, x,
                        dtype=torch.float16)
value_cache = torch.randn(NUM_BLOCKS, num_kv_heads, head_size, block_size,
                          dtype=torch.float16)
k_scale, v_scale = torch.tensor(1.0), torch.tensor(1.0)
out = torch.empty_like(query)
npart = (max_seq_len + PARTITION_SIZE_ROCM - 1) // PARTITION_SIZE_ROCM
tmp_out = torch.empty(num_seqs, num_query_heads, npart, head_size,
                      dtype=torch.float16)
exp_sums = torch.empty(num_seqs, num_query_heads, npart, dtype=torch.float32)
max_logits = torch.empty_like(exp_sums)
torch.cuda.synchronize()

t = time.perf_counter()
ops.paged_attention_rocm(out, exp_sums, max_logits, tmp_out, query, key_cache,
                         value_cache, num_kv_heads, scale, block_tables, seq_lens,
                         None, block_size, max_seq_len, None, "auto", k_scale,
                         v_scale)
torch.cuda.synchronize()
t_first = time.perf_counter() - t

print(f"so={os.path.getsize(so) / 2**20:.1f} MiB  import_vllm={t_import:.2f}s  "
      f"first_paged_attn={t_first:.3f}s  total={t_import + t_first:.2f}s  "
      f"rss: torch={rss_torch:.0f} vllm={rss_vllm:.0f} kernel={rss_mb():.0f} MiB")
```

## Details

**Root cause.** A HIP TU is one clang process on one core, and extra `--offload-arch` values are processed serially inside it too, so `attention.cu`'s ~860 device kernels (6 dtype/kv-cache combinations × head 2 × block 2 × alibi 2 × fp8-out 2 × {CDNA, NAVI, interleaved} ≈ 288 launcher instantiations) were one ~9-minute serial compile that `MAX_JOBS` cannot help with. (The "`Linking _moe_C_stable_libtorch.abi3.so` is slow" symptom is a ninja progress artifact: the link is 159 ms, the line is only printed once `attention.hip.o` finishes.)

**Design.** `csrc/rocm/attention_kernels.cuh` (renamed from `attention.cu`, so the 3.9k moved lines stay a rename and `git blame`/`--follow` survive) keeps the device helpers, the kernel and launcher templates, and the parameter-list macro. Each `csrc/rocm/attention_paged_attn_<head>_<dtype>_<kv>.cu` is ~4 lines: include the header, instantiate one combination with `ATTN_LAUNCH(...)`, expose a fixed-head-size entry point. `csrc/rocm/attention_dispatch.cu` keeps `is_navi_gpu()` and the dtype/kv-cache dispatch (unchanged order) and forwards to those entry points. The instantiation sets are disjoint, so nothing is compiled twice, and hipify follows the quoted include, so the new header is hipified like the ~15 other headers already in the tree.

**Tradeoffs.**
- The split duplicates device DWARF: at 9 archs the attention TUs go from 1070 to 1189 MiB of `.hip_fatbin` (+119 MiB), which is what pushes the link over 2 GiB — hence `--offload-compress` here, which keeps the device debug info that `RelWithDebInfo` ships.
- Adding a head size, dtype, or kv-cache combination means adding a TU and a `CMakeLists.txt` entry; the comments in `attention_kernels.cuh` and `CMakeLists.txt` point at this.
- The split is unbalanced (head 128 TUs take ~70 s vs ~59 s for head 64), and the floor is ~20 s of frontend parsing per TU (`-fsyntax-only`), so a finer split would not buy much.
