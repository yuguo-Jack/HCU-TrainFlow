# [Fast Start] Detect weight cache daemon exit in zero-copy engines

[Upstream PR](https://github.com/vllm-project/vllm/pull/62734) · state: closed · merged: True

## Original PR description

## Purpose

Part of the **Daemon-loss semantics** item in #56049.

The roadmap assumed that if the weight cache daemon exits, a running zero-copy engine's weights become invalid. **That is not what happens.** On B300 + Qwen3-30B-A3B-NVFP4 (TP1, `zero_copy`, `fallback: false`):

| | `main` |
|---|---|
| greedy output before daemon `kill -9` | `" Paris. The capital of Germany is Berlin. The capital of Spain is Madrid. ..."` |
| greedy output after daemon `kill -9` | identical |
| `/health` after daemon loss | 200 |
| GPU 0 memory: engine + daemon → after daemon kill | 167.2 GB → 165.5 GB (only the daemon's context is freed) |
| after starting a replacement daemon | 184.5 GB, and the engine's output is still identical |

The CUDA driver keeps IPC-imported allocations alive until the importing process exits. So failing fast would kill a healthy engine. The actual hazards are silent:

- a restarted daemon holds a **second copy** of the weights on the GPU, and the old copy is pinned until the engine exits;
- the engine never learns that the daemon it mapped from is gone, so nothing tells the operator.

This PR makes the loss observable:

- **Daemon:** a new `watch` command. The daemon keeps the connection open for its lifetime, so it closes exactly when that daemon instance exits, whether it crashes or shuts down. A daemon restarted on the same socket does not mask the loss. Watches of engines that have exited are pruned on the next watch.
- **Engine (`IpcModelLoader`, zero-copy only):** after mapping the weights, a background `WeightCacheDaemonWatch` thread waits on the connection. On EOF it logs a warning that explains the consequences and sets `IpcModelLoader.daemon_lost`.
- **Compatibility:** daemons that predate `watch` reject it and loading proceeds unchanged. A failed watch is best-effort and never triggers the disk fallback.

Not in this PR (left for the rest of the roadmap item): surfacing `daemon_lost` in engine health checks or metrics, and an opt-in policy to exit the engine on daemon loss, so orchestrators can restart both and reclaim the pinned copy.

## Test Plan

- `pytest tests/model_executor/model_loader/test_weight_cache.py -k "not cold_start"`, including the new tests:
  - `test_ipc_loader_detects_daemon_exit`: two engines watch one daemon, the daemon exits, both detect it; a watcher whose engine exited is pruned.
  - `test_ipc_loader_skips_watch_on_old_daemon`.
- `pre-commit run --files <changed files>` (ruff, mypy, etc.).
- End-to-end on B300, TP1 daemon (`vllm preload`) and `vllm serve ... --load-format ipc_cache --model-loader-extra-config '{"socket_dir": DIR, "mode": "zero_copy", "fallback": false}' --gpu-memory-utilization 0.6 --max-model-len 8192`:
  1. greedy completion, then `kill -9` of the daemon rank, then completion and `/health`;
  2. new daemon → engine A → stop A → engine B (warm restart and watcher pruning);
  3. `SIGTERM` of the daemon launcher while engine B is running.

## Test Result

- Unit tests: 45 passed. pre-commit: all hooks pass.
- `kill -9` of the daemon: the engine logs `Weight cache daemon at .../vllm_weight_cache_<id>.sock exited. This engine keeps serving: ...` about 0.1 s later. Greedy output is identical before and after, and `/health` returns 200.
- `SIGTERM` of the daemon: also detected.
- Warm restart A → B: both map 1444 tensors. `Available KV cache memory: 140.06 GiB`, the same as `main`. Outputs are identical. The daemon's socket fd count stays at 13 (A's watch was pruned, B's was added). No errors in the daemon log.
- The final change (catching every exception from the watch request instead of only `ConnectionError`/`OSError`) only touches an error path and landed after the e2e run. Unit tests and pre-commit were re-run on it.
