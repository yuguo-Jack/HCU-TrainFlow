# [KV Connector][NIXL] Add connector checkpoint hooks and restore NIXL P/D workers independently

[Upstream PR](https://github.com/vllm-project/vllm/pull/64371) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Lets KV connectors take part in the process checkpoint lifecycle added in #62570, and implements it for NIXL so prefill and decode instances can be checkpointed and restored independently, with several replicas restored from one checkpoint. Two commits: the connector hooks and checkpoint gate, then the identity refresh with the NIXL implementation.

## Claims

- KV connectors get `checkpoint_prepare()` and `checkpoint_restore()`, which do nothing by default. `MultiConnector` forwards them. Preparing calls them once the engine has drained and released its KV cache: first the scheduler-side instance, then every worker-side instance, before the device communicators. Restoring calls them on every worker-side instance after the device communicators, then on the scheduler-side instance, before the KV cache wakes.
- An engine with a KV connector prepares only if the connector supports process checkpoints with its config. `supports_checkpoint(vllm_config)` is False by default, so `/checkpoint/prepare` returns 400 and `--checkpoint-prepare-on-startup` fails at startup for other connectors. A `MultiConnector` needs every child to support them.
- Each restore gives the instance a new identity. The engine draws a restore ID and passes it to its workers. `VllmConfig.refresh_identity` appends it to the KV engine id on both sides, and `MultiConnector` refreshes the config copy of each connector it wraps. NIXL re-reads it on restore, so peers handshake again instead of reusing metadata cached under the old engine id.
- NIXL supports process checkpoints only with `--checkpoint-prepare-on-startup`. Its workers then create their agent at restore, not at startup, and every agent gets the backends and `ucx_backend_params` of the first. A worker that already had an agent, as in a prepare and restore in one process, drops the old agent's peers, gets a new agent and republishes its handshake metadata under the new engine id.
- The NIXL scheduler binds and advertises the restored pod's side-channel address. If the handshake listener cannot bind, startup or restore fails instead of hanging.

Capture took 53-114 s per instance and restore to serving 13-41 s, not counting an image pull on a new node.

Why NIXL needs `--checkpoint-prepare-on-startup`. Same setup, with the snapshot taken after the source served and then got `/checkpoint/prepare`:

| Before capture | After restore |
| :-- | :-- |
| NIXL agent created at startup | The restored process dies on its first request |
| Same, but prepare destroys the agent first (an experiment, not in this PR); sockets went from 45 to 10 | Dies the same way |
| No KV connector | Serves correctly |
| `--checkpoint-prepare-on-startup` (UCX never initialized before capture) | Serves correctly |

So process-wide UCX state outlives the agent, and the agent must not exist before capture. With the gate, a NIXL engine without the flag gets 400 from `/checkpoint/prepare`, stays running and keeps serving; with the flag it prepares, restores and serves as above.

## Details

Flow with a prefill instance P and a decode instance D:

1. P starts with `--checkpoint-prepare-on-startup`. Its workers register KV regions but create no NIXL agent. Preparing stops the handshake listener and records which interface carries the side-channel host. P is checkpointed.
2. A new pod restores P and calls `/checkpoint/restore`. The engine draws restore ID `r`, so the engine and workers now use engine id `<id>_r`. The workers create a fresh agent. The scheduler takes the same interface's address in the new pod.
3. The KV cache wakes. The workers register with the new agent and publish handshake metadata, which restarts the listener.
4. P returns `remote_engine_id=<id>_r` and its new host in `kv_transfer_params`. D does not know that engine id, so it handshakes with P and reads the KV cache.
5. Another replica restored from the same checkpoint uses `<id>_s`, so D keeps the two apart.

The scheduler side stops before the workers release what it uses, and restarts after they rebuild it. Workers create connectors after the communicators, so connectors release first and rebuild last.

The gate is opt-in because most connectors hold state a checkpoint cannot carry. For example, `MooncakeConnector` passes the sleep-mode gate but keeps its RDMA transfer engine open, which CRIU cannot capture, and caches its engine id at init, so replicas restored from one checkpoint would share an id. This changes #62570's behavior: preparing with any connector other than NIXL with `--checkpoint-prepare-on-startup`, or a `MultiConnector` of such, is now refused.

Relation to #56852 (#55155): that PR adds four worker-side KV hooks (`quiesce`, `release_for_checkpoint`, `reinitialize`, `verify`) for an external coordinator to call. Since #62570 the engine drives the checkpoint lifecycle itself: it drains before preparing, and failures move the checkpoint state to FAILED. This PR wires two hooks into that lifecycle on both the scheduler and worker sides, gates prepare on connector support, and refreshes identity so replicas from one checkpoint stay distinct. #56852 also covers NIXL push mode, which this PR leaves out.

Limitations:

- A restored NIXL engine can prepare and restore again in one process, but cannot be checkpointed again: it has an agent, and the Snapshot agent does not capture an already restored process either.
- Only the KV engine id is refreshed. `instance_id` is kept, since shared-memory regions are keyed by it.
- NIXL push mode and the P2P offload tier are out of scope.
- EC connectors get the hooks with the first EC connector that needs them.
