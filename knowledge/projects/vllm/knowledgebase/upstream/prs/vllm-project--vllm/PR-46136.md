# [Bugfix] Fix Humming kernel weight conversion for unpacked CompressedTensors W4A8 INT checkpoints

[Upstream PR](https://github.com/vllm-project/vllm/pull/46136) · state: open · merged: False

## Original PR description




## Summary

Fixes #46036 (bug 1: the `AssertionError: weight shape mismatched` crash). Found
two distinct bugs in the Humming GPU kernel path for `CompressedTensorsW4A8Int`,
both confirmed and fixed:

1. **Shape bug (the reported crash).** `CompressedTensorsW4A8Int.create_weights`
   stores int4 weights *unpacked* — one signed value per int8 byte — which is
   correct for its original CPU-kleidiai consumer. When the Humming GPU kernel
   is selected instead (CUDA + `humming` installed, symmetric weights, no
   `g_idx`), `convert_linear_layer_to_humming_standard` reinterpreted that
   tensor's raw bytes as `int32` via a plain `.view()` instead of actually
   bit-packing it. That's a 4-bytes-per-int32 reinterpretation where humming's
   schema expects true 8-values-per-int32 nibble packing, producing a tensor
   exactly 2x too wide — matching the issue's reported
   `attr['shape']=(6144, 320)` vs `tensor.shape=(6144, 640)` (320 × 2 = 640).

2. **Value bug (silent, found while validating the fix on real GPU).** Even
   after packing correctly, the dequantized weight values were wrong. Humming's
   own weight dequant (`humming/utils/weight.py:dequantize_weight`) expects
   **unsigned-biased** storage (`stored_value = signed_value + 2**(n-1)`), not
   raw signed two's-complement — confirmed by humming's own
   `CompressedTensorsWeightSchema.convert_humming`, which does `weight = weight
   + 128` for its (8-bit-only) native compressed-tensors path. The conversion
   was missing this bias for the int4 case.

## Fix

In `convert_linear_layer_to_humming_standard`
(`vllm/model_executor/layers/quantization/utils/humming_utils.py`):
- Use `pack_quantized_values_into_int32` (already used by the
  machete/exllama/cpu/rdna3 kernels for the same purpose) to do real bit-packing
  instead of a raw dtype bitcast.
- Apply the `+ 2**(size_bits-1)` bias before packing.
- Tensors that are already packed int32 (e.g. `PackedvLLMParameter` from
  `CompressedTensorsW4A8Fp8`, loaded directly in `pack-quantized` format) are
  left untouched via a dtype check — this path was already correct and is
  unaffected.

`HummingLinearKernel.process_weights_after_loading`
(`vllm/model_executor/kernels/linear/mixed_precision/humming.py`) now threads
`weight_type` through to the conversion function.


## Test plan

 I validated this against the **real**
`humming-kernels==0.1.4` package and **real** vLLM `CompressedTensorsW4A8Int`
/ `HummingLinearKernel` code (not a reimplementation) via WSL2 GPU passthrough
on an RTX 3050 Ti:

- Reproduced the exact reported `AssertionError` against the broken code
  using a real GPTQModifier-quantized checkpoint (channelwise int4 weight +
  dynamic per-token int8 activation, matching the issue's recipe).
- After the fix: `process_weights_after_loading` succeeds, no assertion.
- Numerical correctness: a one-hot-input test across 14 positions spanning
  every packing group predicts the exact expected output analytically
  (avoids needing to reverse-engineer the kernel's internal activation
  quantization) — went from 0/14 matching within 5% (bug 2, pre-bias-fix) to
  14/14 matching within 0.1%.
- Broader random-input forward pass: median relative error dropped from 1.72
  to 0.002 (residual is bf16 rounding only).

## Pull request overview

This PR targets a correctness bug in the Humming GPU path for `CompressedTensorsW4A8Int` by ensuring int4 weights that are stored “unpacked” (one value per int8 element) are converted into the actual bit-packed int32 format (and biased to Humming’s expected unsigned storage) before handing tensors to Humming’s schema/validator.

**Changes:**
- Update `convert_linear_layer_to_humming_standard` to (a) bias signed quantized values by `2**(bits-1)` and (b) bit-pack them into int32 using `pack_quantized_values_into_int32` when needed.
- Thread `weight_type` through `HummingLinearKernel.process_weights_after_loading` so the conversion function can pack using the correct bit-width.
