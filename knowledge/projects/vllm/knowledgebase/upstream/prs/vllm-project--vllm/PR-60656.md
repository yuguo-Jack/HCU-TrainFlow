# [Bugfix][LoRA] Map adapter keys back through Transformers' reversed WeightRenamings

[Upstream PR](https://github.com/vllm-project/vllm/pull/60656) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Transformers v5 renames some checkpoint weights at load time (the `WeightRenaming`s in its `conversion_mapping`), and PEFT saves adapters under those renamed module names. Native vLLM models name their modules after the checkpoint, so LoRA weights on renamed modules match nothing and get dropped without a warning. This PR catches those adapter keys at load time and maps them back through the reversed renames, using the mappings Transformers already ships.

This is the generalised version of #60131, which hard-codes the rename for GLM-5.3-Flash only. The idea comes from @hmellor, who pointed at how the Transformers modeling backend reuses `WeightRenaming` ([base.py#L318-L320](https://github.com/vllm-project/vllm/blob/4ed4c4433b87e45d72f401f27f1b56c932c90071/vllm/model_executor/models/transformers/base.py#L318-L320)). Root-cause discussion is in huggingface/peft#3896. #60666 is the bigger version of this, which applies the renames to the checkpoint itself. This one is LoRA-only and can land on its own.

## Claims

- GLM-5.3-Flash LoRA on `f_b_proj` (saved as `self_attn.forget_gate.f_b_proj`) is applied, without any model-specific change. With #56327, `f_a_proj` is applied as well.
- Mixtral router LoRA (saved as `mlp.gate`, vLLM has `block_sparse_moe.gate`) is applied. On `main` it is silently dropped.
- Adapter keys that resolve to a module on `main` are mapped exactly as before, so nothing that works today changes.

## Validation

Tested on `main` at d80ddaac73 (the base of this branch), 1x H100, `VLLM_USE_PRECOMPILED=1`.

**Log-probs.** I used small random-weight models (2 layers, real head geometry) with the real configs' naming, and random nonzero LoRA weights. I compared vLLM's `prompt_logprobs` on 200 tokens with transformers 5.19 + PEFT 0.21.2 on the same token IDs. Each cell shows the mean absolute log-prob difference to HF with the adapter, and to HF without it. The second number is what a dropped adapter would score.

| model, adapter | `main` | this PR |
|---|---|---|
| GLM-5.3-Flash, `f_b_proj` | 0.0528 / 0.0068 (dropped) | 0.0068 / 0.0519 (applied) |
| GLM-5.3-Flash, `f_a_proj` (B x64), both columns with #56327 | 0.3943 / 0.0068 (dropped) | 0.0059 / 0.3968 (applied) |
| Mixtral, router `mlp.gate` | 0.1677 / 0.0019 (dropped) | 0.0028 / 0.1692 (applied) |
| LLaVA, `q_proj`+`v_proj` | 0.0026 / 0.3590 | 0.0026 / 0.3590 |
| Qwen2-VL, `q_proj`+`v_proj` | 0.0037 / 0.4664 | 0.0037 / 0.4664 |
| GLM-5.3 / Laguna / Mixtral, `o_proj` | applied | applied, same numbers |

Without any adapter, vLLM and HF differ by 0.0068 (GLM-5.3), 0.0039 (Laguna) and 0.0019 (Mixtral). That is the noise floor.

**Every adapter name, per model.** For each vLLM model with LoRA support whose checkpoint Transformers renames, I built both the Transformers and the vLLM model on the meta device. I took every module PEFT can wrap (anything with its own 2-D weight), and ran its adapter key through `parse_fine_tuned_lora_name` with `main`'s mapper and with this PR's. 17 of the 32 architectures build from their default configs on CPU; the other 15 need real configs or a GPU-only backend.

| | modules |
|---|---|
| resolve on `main`, unchanged here | all of them, in all 17 models |
| resolve only with this PR | Mixtral router (32), Laguna and HY-V3 shared experts (117, 237), every module of AudioFlamingo3, GLM-ASR, Granite Speech and Granite Speech Plus (391-419 each) |
| changed by this PR | none |

Each newly resolved key lands on the module with the same layer index and leaf name as in Transformers. The audio models' adapters are entirely dropped on `main` today, because their mappers don't handle the v5 `model.language_model` prefix.

## Details

When an adapter is loaded, each key is first mapped as on `main`, through the model's `hf_to_vllm_mapper`. If the result names a LoRA target (a module, or a constituent of a packed module), it is used as is. If not, the key goes through the reversed renames and then the model's mapper. The result is used only if that names a LoRA target, and otherwise the original result is kept. The renames come from `get_checkpoint_conversion_mapping` for the model's `model_type`, its text config's `model_type` and its `architectures`, reversed with `reverse_transform()`, which is what Transformers uses for `save_pretrained(save_original_format=True)`. Weight loading is not touched.

The first version of this PR applied the reversed renames to every key, skipping any rename whose new name the model already used. That broke LLaVA, Gemma 3, InternVL, Mistral3 and PaliGemma. Their mappers already handle the v4.52 `model.language_model` prefix, and reversing a prefix rename on its own doesn't give the checkpoint name back: on LLaVA, `q_proj`/`v_proj` LoRA went from 0.0026 to 0.3584, i.e. dropped. Deciding per key avoids that by construction.

If this goes in, #60131 is no longer needed. It also works on top of #60131, so the merge order doesn't matter.

Caveats:

- Validated on toy random-weight models, not full checkpoints. The code path is the same, but no real 100B+ model was run with this branch.
- A key that already names some module on `main` is never renamed, even if it's the wrong module. I found no such case in the 17 models above.
- `WeightConverter`s (the many-to-one MoE expert merges) are skipped. Expert LoRA in the 3D format is a separate problem.
- Laguna's shared expert (`mlp.shared_experts.down_proj`) now resolves, but its log-probs are off from HF by about as much as an adapter already saved under vLLM's own name (`shared_expert`) on `main`. That looks like a separate bug in shared-expert LoRA.
- No test is added. An end-to-end check needs a model with a rename and HF log-probs, which CI doesn't have.
