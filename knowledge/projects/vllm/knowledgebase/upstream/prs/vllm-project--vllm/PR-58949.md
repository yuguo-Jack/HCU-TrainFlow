# [HiSparse] Log steady-state max concurrency and expose host-tier utilization gauges

[Upstream PR](https://github.com/vllm-project/vllm/pull/58949) · state: closed · merged: True

## Original PR description

## Purpose

HiSparse's host KV pool is invisible at runtime, and the startup `Maximum concurrency` line understates a warm server's capacity: it charges every request its full admission footprint, while running requests that read from host pin only their active tail pages. This PR adds:

- **Startup log**: steady-state maximum concurrency, `1 + (num_blocks - admission) / steady` (all but one request at its active tail, plus one being admitted), capped by the host pool. Logged from the scheduler-side connector, so it uses the KV cache config after the cross-rank minimum.
- **Gauges**, sampled by the scheduler each engine step (constant-time read of the host block pool, no device sync):
  - `vllm:hisparse_host_cache_usage_perc`: host pool usage, mirroring `vllm:kv_cache_usage_perc`. Evictable cached blocks count as free.
  - `vllm:hisparse_pending_page_transfers`: write-backs and restores not yet completed.
- **CLI**: `HiSparse host KV cache usage %` in the `KV Transfer metrics` line.
- **Docs**: a HiSparse section in `docs/usage/metrics.md` (metric names are now literals so the generator picks them up) and the two bounds in `docs/design/hisparse.md`.

Supersedes #58805.

- **A**: TP2, `MultiConnector[HiSparseConnector (host_pool_gib 4), OffloadingConnector (cpu_bytes_to_use 4e9)]`, `--kv-cache-memory-bytes 1000000000`; `vllm bench serve` random 8000 in / 512 out, 64 prompts, concurrency 32.
- **B**: TP1, `HiSparseConnector` (host_pool_gib 4), `--kv-cache-memory-bytes 250000000 --max-model-len 16384`; random 15000 in / 1300 out, 40 prompts, concurrency 40 (saturates the GPU pool).

## Test Result

Unit: 45 passed at HEAD (with `test_multi_connector.py`) (`test_draft_layer_rows_mirrored_after_drafter` needs CUDA, not run on macOS).

E2E at `f792b5bd11` (later commits switch the ratio to the equivalent `BlockPool.get_usage()` and trim comments/docs). All requests succeeded, no errors.

A:

```
GPU KV cache size: 1,016,234 tokens, Maximum concurrency for 163,840 tokens per request: 6.20x
HiSparse steady-state maximum concurrency for 163,840 tokens per request: 8.07x (running requests reading from host).

vllm:hisparse_host_cache_usage_perc        0.0 -> 0.161 (32 running) -> 0.0
vllm:hisparse_pending_page_transfers       up to 256 during prefill, 1-2 during decode, 0 idle

KV Transfer metrics: HiSparseConnector={..., 'HiSparse host KV cache usage %': 15.8}, OffloadingConnector={...}
```

One series per gauge; peak usage matches 32 requests x ~129 pages / 25574 host blocks, so nothing is counted twice across ranks or connectors.

B: logged 3.88x generic and 9.50x steady state; observed up to 10 running requests, sustained, while reading from host. Like the generic line, the steady-state value is an estimate, not a hard limit: requests prefilling together do not all hold their full window at once.

Logging and metrics only; no change to attention, caching or scheduling.
