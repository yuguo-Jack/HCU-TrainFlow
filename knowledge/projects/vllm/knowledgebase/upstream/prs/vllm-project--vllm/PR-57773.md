# [ROCm][Perf] Enable DPA+ETP prefill compute/comm dual-batch-overlap for DeepSeek-V4

[Upstream PR](https://github.com/vllm-project/vllm/pull/57773) · state: closed · merged: True

## Original PR description

## Purpose

This PR enables prefill dual-batch-overlap (DBO) for DeepSeek-V4 on ROCm in data-parallel deployments: attention DP, experts TP via flattened TP, no EP (e.g. `--data-parallel-size 8`).

Today `--enable-dbo` splits a step into two ubatches and runs them as a two-thread ping-pong on a compute stream and a comm stream. However, only the DeepEP-HT prepare/finalize moves its collectives to the comm stream. The naive DP/EP path (`allgather_reducescatter`, used by DP deployments without `--enable-expert-parallel`) runs its MoE all-gather (dispatch) and reduce-scatter (combine) synchronously on the compute stream. Both ubatches therefore serialize, and DBO gives no benefit in prefill. On ROCm this path was also blocked by the microbatching config check.

This PR makes the naive DP/EP prepare/finalize hand each collective to the comm stream, using the same compute/comm handoff as DeepEP-HT. While one ubatch's all-gather/reduce-scatter is in flight, the peer ubatch runs attention/MoE compute. It also fixes several DBO correctness issues that DeepSeek-V4 hits on this path.

### Key Changes

**MoE prepare/finalize (DBO comm overlap):**
- **`MoEPrepareAndFinalizeNaiveDPEPModular`** (`fused_moe/prepare_finalize/naive_dp_ep.py`): `dispatch()` / `combine_into_output()` now run inside a new `_comm_region()` context. Under an active DBO context, it yields the CPU to the peer ubatch, switches to the comm stream for the collective, and syncs back to the compute stream on exit. Outside DBO, and during cudagraph capture, it does nothing: the collective stays on the calling stream, so non-DBO behavior is unchanged on every platform. The class reports `supports_dbo()` only on ROCm, the only platform where this path has been validated.
- **`FusedMoEPrepareAndFinalize.supports_dbo()`** (`modular_kernel.py`): New capability, defaulting to `supports_async()`, so existing implementations behave exactly as before. The synchronous `_prepare` / `_finalize` paths now assert `not dbo_enabled() or supports_dbo()`. The naive DP/EP class keeps `supports_async()` as `False`. This avoids overloading `supports_async()`, which also drives MK-internal shared-expert overlap on every forward.
- **`VllmConfig`** (`config/vllm.py`): Allows `allgather_reducescatter` with microbatching on ROCm.

**Ubatching fixes:**
- **`UBatchWrapper._run_ubatches`** (`v1/worker/gpu_ubatch_wrapper.py`): Eager ubatch threads now call `torch.accelerator.set_device_index(self.device)`, as `_capture_ubatches` already did. A new thread starts on device 0. Without this call, each thread's first `current_stream()` created a stream on GPU 0 and waited on it, so every DP rank put work on GPU 0. That slowed rank 0, and every rank then waited on rank 0 at each MoE collective. This was the main cause of the earlier ~30% regression with DBO.
- **`maybe_create_ubatch_slices`** (`v1/worker/ubatch_utils.py`): The last split point (`cu_num_tokens[-1]`, a `np.int32`) is cast to `int` at the source. Previously the numpy scalar reached the DeepSeek-V4 C128A metadata builder and failed Triton specialization (`TypeError: failed to specialize argument of type: numpy.int32`). An explicit `list[int]` `split_point` is now handled as explicit split points instead of being list-multiplied.
- **`_make_metadata_with_slice`** (`v1/worker/ubatch_utils.py`): Slices `CommonAttentionMetadata.positions` per ubatch. Without this, startup fails with `positions is required for C128A metadata build`.
- **`UBatchContext.token_offset` / `dbo_current_ubatch_token_offset()`** (`v1/worker/ubatching.py`): Exposes each ubatch's row offset in the parent batch. It returns 0 outside DBO.

**DeepSeek-V4 (AMD):**
- **`DeepseekV4Model.forward`** (`models/deepseek_v4/amd/model.py`): Writes `_mtp_hidden_buffer` at the current ubatch's token offset. Previously both ubatch threads wrote from row 0, so the MTP drafter read misaligned hidden states for the step.

**Tests:**
- `tests/kernels/moe/test_naive_dp_ep_dbo.py`: Covers `_comm_region` handoff, the no-op without DBO, skip during graph capture, compute-stream restore on error, `supports_dbo()` being ROCm-only while `supports_async()` stays `False`, and the default `supports_dbo()` contract.
- `tests/v1/worker/test_ubatch_offsets.py`: Covers per-thread ubatch token offsets and Python-int ubatch slice bounds.

> [!NOTE]
> **`supports_dbo()` vs. `dbo_enabled()`**
>
> - `supports_dbo()` is a static **capability** of the prepare/finalize class: *can* it run correctly under DBO? It does not depend on the current step. For the naive DP/EP class it is `current_platform.is_rocm()`. It is used only as a guard in the modular kernel: `assert not dbo_enabled() or supports_dbo()`.
> - `dbo_enabled()` is per-thread **runtime state**: is the calling thread *currently* inside a ubatch context? It is True only inside the ubatch threads of a step that was actually split. It is used in `_comm_region()` to decide, per call, whether to hand the collective to the comm stream.
>
> | Platform | Step | `supports_dbo()` | `dbo_enabled()` | Behavior |
> |---|---|---|---|---|
> | ROCm | not split (below threshold, a DP rank opted out, or DBO off) | True | False | Collective stays on the calling stream (unchanged) |
> | ROCm | split prefill | True | True | Collective runs on the comm stream, overlapped with the peer ubatch |
> | Others | any | False | False | Unchanged. Microbatching with `allgather_reducescatter` is still rejected at config time. |
>
> Neither replaces the other. With only `dbo_enabled()`, a synchronous prepare/finalize that never handled DBO could silently run under it. With only `supports_dbo()`, `_comm_region()` could not tell a split step from a normal one. Previously the PR overloaded `supports_async()` to return `dbo_enabled()`, which mixed the two concepts. It also changed MK-internal shared-expert scheduling per thread, because `can_overlap_shared_experts` reads `supports_async()`.

Thanks for this. I reproduced the numbers and tested each part of the change on MI355X (8x, ROCm 10
nightly and the ROCm 7.2.3 nightly, DSV4-Pro, DP8, your launch flags, InferenceX agentic replay at

**Summary**

- The ~30% regression comes from a bug in main's DBO path rather than from the overlap: the eager
  microbatch threads never set their device, so work that uses the current device runs on GPU 0.
  One-line fix below; I'd like to see it go in with this PR.
- With the fix, DBO is at parity with no-DBO end to end (958 vs 917-977 output tok/s over three
  no-DBO runs), and accuracy matches with microbatching actually active (see section 2).
- I could reproduce the failures behind the `positions` slicing and the numpy-int casts. I could not
  reproduce the reasons given for disabling FULL-graph microbatching on ROCm or for the extra profile
  run.
- #46990's changes are gated on `deepep_high_throughput`, so they don't apply on this path.

### 1. Device not set in `_run_ubatches` threads

`_run_ubatches` starts a new thread per microbatch and never sets the device, so the thread's
current device is 0. `_capture_ubatches` already sets it:

```python
        def _ubatch_thread(results, model, ubatch_metadata):
            torch.accelerator.set_device_index(self.device)
            with ubatch_metadata.context:
```

Before the fix:
- With the server idle after startup, GPU 0 was 100% busy and the other seven idle (main: all idle).
- In kernel traces only rank 0's kernels were slow (fused MoE ~1.8x normal). DP ranks wait on each
  other every step, so every rank slows down, which matches the TPOT regression in the description.
- Agentic throughput: 670-717 tok/s with DBO before the fix, 958 after.
- On the ROCm 7.2.3 nightly, DBO without the fix crashed a worker with `HSA_STATUS_ERROR_EXCEPTION`
  (0x1016) in 2 of 6 runs. With the fix, 4 of 4 runs were clean (931-955 tok/s vs 899-938 without
  DBO). Too few runs to call it fixed, and I haven't found the faulting kernel.

### 2. Comm-stream overlap for the naive DP/EP path

Performance: on a prefill-heavy burst (every rank on full 8192-token chunks), the comm stream's RCCL
kernels run on a separate HW queue and the collectives are almost entirely hidden; with them forced
back onto the compute stream the same burst is 20-75% slower (two runs). It is still ~9% slower than
not microbatching at all (3.67 s vs 3.37 s GPU time on rank 0, one clean run). The MoE and several
GEMM kernels run noticeably slower while RCCL overlaps them, so I suspect contention, but I haven't
isolated it.

How often it applies: microbatching is all-or-none across DP ranks, so a step is only split if every
rank qualifies. In a gsm8k run with DBO on, most steps that met the threshold weren't split because
some rank opted out; as far as I can tell that was mostly FULL-graph decode (the check in section 3)
and, with prefix caching on, the prefix-cache hazard check. In the agentic replay ~8% of steps were
split at a threshold of 8192, so the end-to-end effect is small either way.

Accuracy: gsm8k (your test plan) and ARC-challenge matched main, but with prefix caching on, DBO
barely split any steps. With prefix caching off, ARC-challenge (25-shot) split ~70 steps and matched
main within error (acc 0.707 vs 0.715, acc_norm 0.730 vs 0.727, ±0.013). That covers prefill
log-likelihoods, not generation.

On the implementation, I'd suggest keeping this in the base class rather than adding a ROCm
subclass: the `_comm_region` handoff is a no-op without DBO, so it could live in
`MoEPrepareAndFinalizeNaiveDPEPModular` for all platforms, without the factory swap (which currently
changes the class for every ROCm naive DP/EP user) or the ROCm-only config check. And rather than
having `supports_async()` return `dbo_enabled()` to get past the modular-kernel assert, an explicit
"supports DBO" capability would say what's meant; `supports_async()` is also read by the
shared-experts scheduling on every forward, so overloading it has side effects beyond the assert.

Have you measured DBO with DP+EP on this model? That path already has an overlapping
dispatch/combine, and it would help to know how it compares before adding a second overlap path.
(If you do, note that #46990's ROCm-specific changes on that path, the async-scheduling disable, the
`comm_sms = 0` override and the post-dispatch/combine `synchronize()`, may be unnecessary and likely
cost performance; see the reasoning in ROCm/vllm@1e708140206bce5f0e518b636c7193c18f920bba and
ROCm/vllm@997dce5602326b08431ec28056452e9eb6f7b756. It may be worth trying with them reverted.)

### 3. Disabling microbatching for FULL cudagraphs on ROCm

With this hunk removed, microbatched FULL graphs captured and replayed without errors on both ROCm 10
and ROCm 7.2.3. Microbatched decode was ~1.8x slower per token, so keeping decode out of DBO is
right, but `--dbo-decode-token-threshold` already does that on any platform (with the hunk removed
and a high threshold, decode matched main). I'd drop the platform check. If you have the hipBLASLt
error text and ROCm version, I'd like to look at it.

### 4. Extra profile run on ROCm

With this removed I saw no "Workspace is locked" error, in long-prompt bursts or in a 900 s agentic
run. Do you have a failing config?

### 5. numpy int casts

Reproduced: without them startup fails with `TypeError: failed to specialize argument of type:
numpy.int32` in `build_c128a_topk_metadata`. The numpy value comes from the last split point in
`maybe_create_ubatch_slices`; casting there instead covers every consumer (tested in place of the
casts in this PR):

```python
    all_points = token_split_points + [int(cu_num_tokens[-1])]
```

### 6. Slicing `positions` per microbatch

Reproduced (startup fails with `positions is required for C128A metadata build`). Looks right.

### 7. MTP hidden-buffer offset

From reading the code this looks like a real bug: both microbatch threads write
`_mtp_hidden_buffer` from row 0, and the drafter reads the buffer in token order for the whole step.
It only affects draft quality, not output. The same write is in the other DeepSeek-V4 backends (and
DeepSeek-V4.1 / Qwen4-Exp); should they get the same offset?
