# [Frontend] Apply each endpoint's top_logprobs cut in derender

[Upstream PR](https://github.com/vllm-project/vllm/pull/59518) · state: closed · merged: True

## Original PR description

## Purpose

Fixes #59513. Builds on the generate logprobs shape from #58181 (merged); rebased on main, one commit.

The engine's per-position logprobs hold the sampled token first and then ranks `1..k`, so `k` distinct entries when the sampled token is in the top `k` and `k + 1` when it is not. `/v1/chat/completions` keeps the first `k` and `/v1/completions` the first `k + 1` (the OpenAI completions convention). Generate cut to `max(k, 1)` and derender passed that through, so `/v1/completions/derender` returned `k` entries where the coupled endpoint returns `k + 1` whenever the sampled token was outside the top `k`. The greedy parity tests never produce that case. Following @shimib's suggestion on #58181:

- **Generate** (Python and Rust, both `output_mode`s) returns every candidate the engine produced, sampled first, with no cut. Rust drops the repeated sampled entry (its engine row lists a sampled top-1 token twice) by skipping later entries equal to the sampled token (linear, no allocation, even for `logprobs=-1`).
- **Derender** applies the coupled endpoint's cut through the same helpers the coupled endpoints now use (`chat_top_logprobs_limit` / `completion_top_logprobs_limit`), read from `chat_request` / `completion_request`: chat keeps entry `i` when `logprob_token_ids` is set, `top_logprobs == -1` or `i < top_logprobs` (`_get_top_logprobs`); completions when `logprob_token_ids` is set or `logprobs >= i`. The cut happens before decoding. Without the request derender returns every candidate (documented).
- **Rust `/v1/chat/completions`** drops the repeated sampled entry, like Python; before, a sampled top-1 token appeared twice and one candidate was lost.
- Docs: `renderer.md` (what generate returns) and `derenderer.md` (the per-endpoint cut).

## Test Plan

- New `tests/entrypoints/scale_out/derender/test_logprobs_endpoint_parity.py`: engine dicts built with the engine's own `append_logprobs_for_next_position` and detokenized as the engine does, with the sampled token at rank 1, inside and outside the top `k`, run through the real coupled chat / completions helpers and through generate + derender; `k` in 0, 1, 2, 5 (and -1 for chat). Plus: without the request, every candidate is kept.
- Updated generate unit tests to engine-realistic dicts; Rust tests for the generate dedup (no cut) and the chat dedup.
- End-to-end on a live server (`--enable-scale-out`, Qwen3-4B, L20): the same request (`temperature=1.5`, seeds 7/11/23, `k` = 1/2/5, 96 tokens) through the coupled endpoint and through render -> `/inference/v1/generate` -> derender, compared per position (token ids, `top_logprobs` length, tokens, bytes, logprobs within 1e-4), before and after this change.
- Benchmark of generate and derender cost at `top_logprobs=20`.

## Test Result

End-to-end, 18 trials (9 chat, 9 completions), 1,632 comparable positions:

| | before | after |
| --- | ---: | ---: |
| positions where generate + derender differs from the coupled endpoint | 215 | **0** |
| of which the sampled token was outside the top `k` | 215 | 0 |
| chat positions that differ | 0 | 0 |

Before the change the mismatches were exactly the 215 completions positions with the sampled token outside the top `k`. One chat trial is excluded on both sides because the coupled endpoint itself is not run-to-run deterministic there (two identical coupled requests diverge at position 73 once the prefix is cached, at `temperature=1.5`); generate is repeatable.

Benchmark (1,000 positions, `top_logprobs=20`, 30% of positions with the sampled token outside the top `k`, Qwen2.5 tokenizer, median of 7):

| | before | after |
| --- | ---: | ---: |
| generate `_create_tokens_logprobs` | 14.8 µs/token | 13.5 µs/token |
| generate response size | 1,043 B/token | 1,057 B/token |
| chat derender | 66.2 µs/token | 65.2 µs/token |
| completions derender | 67.4 µs/token | 69.3 µs/token (decodes the entry it used to drop) |

Tests on an L20 with live servers (tiny Llama, gpt2, Qwen3-0.6B): `test_derender.py` 27, `test_derender_stream.py` 52, `test_logprobs_endpoint_parity.py` 10, `test_generate_logprobs_conversion.py` 5, `test_serving_tokens.py` 13, `test_generate_stream.py` 31, `test_tokens_logprobs.py` 7 passed; not run there: the DeepSeek parser and gpt-oss harmony tests (model size) and the LoRA test (adapters not downloaded). CPU-only runs: 414 passed across `scale_out`, `test_serving_chat.py` and `openai/completion` (3 failures that fail identically on main). Rust: `vllm-server` 440 passed, `cargo clippy -D warnings` and `cargo fmt` clean. mypy (`tools/pre_commit/mypy.py 3.12`) reports only the 2 existing `Parser` errors in `online_derenderer.py` that main has too; ruff and typos clean.

AI assistance (Claude Code) was used for this change; the submitter reviewed every changed line and ran the tests above.
