# [CI] Enroll three standalone AMD steps in automatic sharding

[Upstream PR](https://github.com/vllm-project/vllm/pull/64181) · state: closed · merged: True

## Original PR description

## Overview

Enrolls three standalone AMD steps in automatic sharding (`automatic_shard: true`), continuing #64115, #62513 and #62077 down the list on ci.vllm.ai/sharding. The pipeline generator plans standalone AMD steps since vllm-project/ci-infra#871, and each of these splits into 2 shards on main's timings. No test changes.

## Claims

| Step | Plan |
|---|---|
| `fusion-e2e-tp2-ar-rms-inductor-partition-amd` | 2 shards |
| `fusion-e2e-tp2-ar-rms-dynamo-partition-amd` | 2 shards |
| `minimax-m3-monokernel-mi355` | 2 shards |

- Each shard runs its part of the same commands, with the same environment and timeout as on main; every test runs exactly once.

## Validation

- `/ci run` on the previous head (build 98765, after ci-infra#871 merged): all three steps passed as 2 shards each, every shard under the 20-minute target.
- A fresh `/ci run` follows on this head.

## Details

- **Left out: steps the generator can't shard.** It only shards a step whose commands after the first pytest are all plain pytest, and ignores `automatic_shard` elsewhere. An earlier revision also enrolled Distributed Features, Examples and PyTorch Compilation (each with its AMD mirror); they ran as one job regardless (`python3` example scripts, and a `find … | xargs pytest` pipe), so this PR no longer touches them.
- **PyTorch Compilation's `find`.** It runs each `compile/test_*.py` in its own process and picks up new files automatically. Listing the files would lose that, and one `pytest compile/` command needs test isolation fixes first, so it stays as it is.
- **CPU steps left out.** Main records no test timings for CPU jobs yet.
- **Timeouts unchanged.** `timeout_in_minutes` stays as it is on every step.
