# [Bugfix][NIXL] Harden handshake listener against bad requests

[Upstream PR](https://github.com/vllm-project/vllm/pull/54757) · state: open · merged: False

## Original PR description

## Purpose

The prefill-side NIXL handshake listener (`_nixl_handshake_listener` in `base_scheduler.py`) is a single background thread for each engine. It lives for the whole process and answers metadata queries from every decode worker that pulls KV cache from this engine. It handled only the idle-poll timeout. Any bad request killed the thread silently, and nothing restarted or reported it.

A bad request is anything on the side-channel port that is not a well-formed request from a real `REQ` client: a peer that does not send the `REQ`/`ROUTER` envelope (e.g., a bare `DEALER` socket, which sends 2 frames instead of 3), malformed or deeply nested msgpack, or a request for a pp/tp rank that this engine does not serve. After the thread dies, every handshake against this engine times out for every decode worker until the process restarts. Thus, one bad request causes a silent denial of service (DoS) for the full engine.

No issue is filed for this. We found it in production and reproduced it locally. I searched the issues, the PRs and the current `main` of `vllm-project/vllm`, and found no work on the exception handling of this listener. The nearest related work, vllm-project/vllm#48633 and vllm-project/vllm#49238 / vllm-project/vllm#50047, is about different NIXL reliability gaps (push-mode handshake latency, stale peer state after a restart).

## Changes

- `base_scheduler.py`: validate each request before the listener uses it, as suggested in review:
  - Check that the request has 3 frames.
  - Decode the message with `msgspec.msgpack.Decoder(tuple[bytes, int, int])`. This decoder raises only `msgspec.DecodeError` for any bad payload, also for a payload nested past the recursion limit. Only this step has a `try`.
  - Skip a request whose message is not `GET_META_MSG`. Before, the listener logged a warning and sent the metadata anyway. `GET_META_MSG` is the only message that a decode worker sends.
  - Look up the metadata with `encoded_data.get(...)` and skip a request for an unknown rank.
  - For each bad request, the listener logs a one-line warning and continues. An error in the reply path is still a bug and still crashes the thread loudly.
  - Check `stop_event` on every loop iteration, not only after a receive timeout. Otherwise a client that sends requests back-to-back makes `shutdown()` block on `join()`.
- `base_worker.py`: when the decode-side handshake times out (`zmq.error.Again`), raise an error that gives the remote address, the pp/tp rank and the timeout. ZMQ hides the connection state, so before this change the only message was "Resource temporarily unavailable".
- `test_nixl_connector.py`:
  - `test_handshake_listener_survives_bad_request` runs the real listener on a live socket. It is parametrized over the bad envelope, malformed content, deeply nested content, unknown rank and wrong message cases. For each case it checks that the listener does not reply and stays alive, and that a real `GET_META_MSG` request still gets its reply.
  - `test_handshake_listener_shutdown_with_continuous_bad_requests` checks that shutdown is not blocked while a `DEALER` client sends bad frames continuously.

AI assistance (Claude Code) was used to investigate, reproduce and implement this fix, and to apply the review changes. I reviewed every changed line.

- localityv-hash · comment · 2026-10-09T01:45:00Z · [source](https://github.com/vllm-project/vllm/pull/54757#issuecomment-6072555946)

We hit this in production. A stray frame killed the handshake listener with `not enough values to unpack (expected 3, got 2)` on three different model deployments. In every case it was a single unexpected two-part message on the listener's port.

We backported this PR onto a recent main and replayed the frames our deployments had received at a real `NixlBaseConnectorScheduler` listener bound to TCP:

- Before the PR, the listener thread dies on the first frame.
- With it, every frame is logged and dropped, and a genuine `GET_META_MSG` request afterwards still gets its reply.

The three tests in this PR pass in our image. We had to run them from a file of their own, because `test_nixl_connector.py` imports ray and our serving image doesn't have it. That doesn't matter for upstream CI.

One gap we found and closed on our side: a request whose content is nested past the recursion limit (for example a well-formed REQ envelope carrying `b"\x91" * 20000 + b"\x01"`) makes the decode raise `RecursionError`, a `RuntimeError`, which the except tuple does not catch, so the listener thread still exits. Adding `RecursionError` to that tuple, plus a test that sends such a message and then checks a real `GET_META_MSG` still gets its reply, closes it.

This fix has been in one of our production images since 2026-10-08. It would be great to see it merged once the conflict is resolved.
