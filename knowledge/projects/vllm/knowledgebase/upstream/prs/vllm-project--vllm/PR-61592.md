# [CI] Merge the target branch into stale PRs on /ci run

[Upstream PR](https://github.com/vllm-project/vllm/pull/61592) · state: closed · merged: True

## Original PR description



## Overview

When `/ci run` (or `/amd-ci run`, including `all`/`nightly`) finds the PR branch behind its target branch, the bot now merges the target branch into the PR branch (same as the **Update branch** button) and starts CI on the resulting merge commit, instead of refusing and asking the contributor to update manually.

Builds on @mgoin's #58424, which proposes the same behavior using the workflow `GITHUB_TOKEN`; he is credited as co-author. This PR differs in two ways that I believe block #58424 in practice (details below), so it is opened separately rather than as a duplicate.

## Claims

- Stale branches are merged with the target branch automatically on run commands, for every user already authorized to run CI (committers, and PR authors after approval or `ready`).
- Uses a dedicated `CI_BRANCH_UPDATE_TOKEN` secret instead of `GITHUB_TOKEN`, so fork branches can be updated and the push triggers the required `pre-commit` / `pre-run-check` workflows on the new head.
- Rerun limit: users without write access cannot start another full run (`/ci run`, `all`, `nightly`, with or without `--allow-stale`) on a head that already has a non-canceled CI build; the bot points them to pushing changes or `/ci retry`. This replaces the rate limit the old freshness rule gave in practice, which auto-merge would otherwise remove.
- Fail-safe: with the secret unset, or when the merge fails (conflict, fork without "Allow edits by maintainers", PR head moved), no build is started and the bot explains why. `--allow-stale` and retry/cancel are unchanged.

Three new tests cover the new path: a successful merge builds the merge commit; a rejected merge (422 conflict) starts no build and tells the user to merge themselves or use `--allow-stale`; a repeat `/ci run` or `/ci run --allow-stale` on an already-tested head is refused for a contributor but allowed for a committer. Not yet exercised against a live fork PR; that requires the secret.

## Details

**Why not `GITHUB_TOKEN` (#58424):**
- `GITHUB_TOKEN` is scoped to `vllm-project/vllm` and cannot push to fork branches. 196 of the latest 200 open PRs are from forks (188 of those allow maintainer edits).
- Pushes made with `GITHUB_TOKEN` do not trigger `pull_request` workflows, so the required `pre-commit` and `pre-run-check` checks would never report on the merge commit and the PR would be blocked until the author pushes again.

**Flow:** freshness check → `PUT /pulls/{n}/update-branch` with `expected_head_sha` → poll the PR until the head changes (≤ 2 min) → verify open, same base, 0 behind → create the Buildkite build for the new head. The success reply tells the author to pull before pushing more changes.

**Setup needed (admin):** add repo secret `CI_BRANCH_UPDATE_TOKEN`: a **classic** PAT for vllm-bot with `public_repo` + `workflow` scopes. Fine-grained PATs cannot write to repositories outside their resource owner, so they cannot update fork branches; `workflow` is needed when the merged-in commits touch `.github/workflows`.

**Tradeoffs / open questions:**
- The bot adds a merge commit to contributors' branches. The `main` ruleset has `dismiss_stale_reviews_on_push: false`, but `require_extra_approval_for_unattributed_changes: true` may require a fresh approval after a bot push. Needs confirmation on a live PR.
- The merge commit has no `Signed-off-by`; the DCO app is expected to skip merge commits, to be confirmed.
- The "CI is now available" message describes the auto-merge unconditionally, so the secret should be added when this lands.
