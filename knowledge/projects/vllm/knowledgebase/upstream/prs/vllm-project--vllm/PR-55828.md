# [Core] Size the KV cache, including the extensible one, from this process's own device memory

[Upstream PR](https://github.com/vllm-project/vllm/pull/55828) · state: open · merged: False

## Original PR description

## Purpose

`memory_profiling()` derives `total_consumed` (weights + non-torch overhead, the base of the KV cache budget) from the
device-wide free-memory delta between the worker's init snapshot and the end of the profile run. Anything another
process allocates or releases on the same device in that window is charged to, or credited against, this instance:
two instances started at the same time on one GPU shrink each other's KV cache or fail with
`No available memory for the cache blocks` or `To serve at least one request with the model's max seq len ...`, and a release by another process trips the
`init_free_memory >= free_gpu_memory` assertion. Fixes #55827; #55169 hit the same mechanism with sleep/wake
model swapping (closed as interference from concurrent GPU use), #35920 is the UMA variant, and #56830 is the
assertion side of the same mechanism (a co-tenant releasing memory during profiling, or host memory moving on
a unified-memory part with no co-tenant at all).

Since #56492, the KV cache on CUDA and ROCm with the V2 model runner is extensible by default. It is sized a second
time after warmup, in `measure_kv_cache_bytes`, again from the drop in free device memory since startup. With only
the profiling fix (the first two commits), both instances in the concurrent run start, but the after-warmup sizing
leaves them at 7.16 / 2.57 GiB instead of 11.49 / 6.60 GiB. This PR covers both steps.

Changes:

- `Platform.get_process_memory_usage(device_id)` returns the device memory used by the current process
  (`None` when the platform cannot attribute memory to processes); `NvmlCudaPlatform` implements it through
  `nvmlDeviceGetComputeRunningProcesses` and returns `None` for any NVML error, missing PID entry (e.g. a container
  whose PID namespace NVML does not see), WDDM/MIG (`usedGpuMemory` unavailable).
- `MemorySnapshot` records it as `process_memory`; `memory_profiling()` uses `after − before` of that value as
  `total_consumed` when both snapshots have it (`MemoryProfilingResult.process_scoped = True`) and logs a warning when
  the device-wide delta differs from it by ≥ 128 MiB (other processes changed their usage while we were loading).
  Without per-process data the behaviour is unchanged.
- `Worker.determine_available_memory` keeps the release-during-profiling assertion only for the device-level path;
  with per-process accounting a release by others is logged and ignored.
- `measure_kv_cache_bytes` (the extensible KV cache's sizing after warmup) takes this process's own growth since the
  init snapshot in place of the drop in free memory when the platform reports it. The cap from what is physically
  free on the device stays as it is.

`gpu_memory_utilization` keeps its meaning (this instance uses at most that fraction of the device). Co-tenants that
together ask for more than the device has still fail rather than silently. Without the extensible KV cache, the
start-time check stops an instance started after the others have loaded, and instances started together fail when
they allocate the KV cache, as before. The extensible KV cache never grows past what is free on the device after
warmup, less a margin.

## Test Plan

- `tests/utils_/test_mem_utils.py`: mocked platform — another process allocating between the snapshots is not
  counted (`process_scoped`), fallback to the device delta when per-process usage is unavailable, snapshot
  subtraction; real device — a spawned helper process allocates 512 MiB while this process profiles, `total_consumed`
  must reflect only this process's 256 MiB (skipped when the platform cannot report per-process usage). Existing
  `test_memory_profiling` unchanged (own allocations are counted identically by both methods).
- `tests/v1/worker/test_extensible_kv_cache.py`: another process allocating or releasing 2 GiB before the after-warmup
  measurement changes the budget computed from free memory, but not the one computed from this process's own growth.
- End to end (repro from #55827): `Qwen/Qwen3-ASR-1.7B` at util 0.35 and `Qwen/Qwen3-ForcedAligner-0.6B` at
  util 0.20 started sequentially (reference), concurrently, and the aligner 1 s after killing the ASR, with the
  default (extensible) KV cache and with `--no-enable-extensible-kv-cache`. Also one ASR instance alone at util
  0.9 and 0.97, where both ways of counting should agree.

The #53591 fallback is gated on `is_rocm()`, so it does not reach that row. Per-process accounting does.

To be clear about scope: I did not run a full `vllm serve` with your patch applied. I verified the NVML behaviour the patch relies on, on the hardware in question. Happy to run the end-to-end startup on the Spark if that would be useful to you.

**Results.**
- **Release 1:**
  - The 4 GiB release is smaller than what the instance itself takes (about 8 GiB), so free memory still drops overall (4.13 GiB).
  - The `init_free_memory >= free_gpu_memory` assertion passes.
  - The KV cache is sized as if the instance used 4 GiB less than it does. The process ends up 3.2 GiB (22%) over budget.
  - The only trace in the log is the negative `non-torch forward increase memory`.
- **Release 2** did not inflate, with the same timing. I have no explanation for that.
- **Grab runs:** both shrank the KV cache by an amount consistent with the 4 GiB hog.
- **Per-process NVML usage:** minus the KV size, it comes out at 8.05–8.07 GiB in all four runs. Over the same runs the non-KV memory that vLLM measured ranged from 4.83 to 13.41 GiB. The per-process counter this PR uses gives a stable value in exactly the runs where the device-wide delta does not.
- **Baseline drift:** quiet starts also vary. Two unperturbed starts with the same CLI args, about 40 minutes apart, got 5.89 and 8.02 GiB of KV cache. Only the log level differed. So I am not quoting a "vs quiet" delta.

**Why this matters for the fix:**
- **Guards keyed on free memory growing** cannot see this case: the current assertion, the opt-in in #45534, and a torch-reserved fallback of the `maybe_rocm_profiling_fallback` shape (generalized in #62806, closed). The release in release 1 only shrinks the delta.
- **Main** has the same dependence. The calculation is now written as `total_consumed = before_create.free_memory - after_profile.free_memory`, with psutil `available` used as free memory on integrated GPUs. Since #65413, the extensible KV cache's after-warmup sizing reads the same value. I have not run main.
- **The device-level path of this PR** keeps that behaviour unchanged when per-process data is unavailable. So the PID question below decides whether GB10 docker users get the fix.

1. Wait until the host has at least 20 GiB available, plus the hog size in release mode. For release mode, start the hog first and wait until it reports "ready".
   - Hog: `b = bytearray(4 << 30); b[::4096] = b'\x01' * ((4 << 30) // 4096)`, then sleep.
2. Start the server: `docker run --gpus all --ipc=host -e VLLM_LOGGING_LEVEL=DEBUG vllm/vllm-openai:v0.25.1-aarch64 <model> --gpu-memory-utilization 0.12 --max-model-len 4096 --max-num-seqs 4 --no-enable-prefix-caching --seed 0`.
3. Follow the log. As soon as `worker init memory snapshot` appears, kill the hog (release mode) or start it (grab mode).
4. Wait for `/health`, then take these lines from the log: `Initial free memory`, `Free memory after profiling`, `Memory profiling takes`, `Available KV cache memory`.
5. On the host, read per-process usage: `nvidia-smi --query-compute-apps=pid,used_memory --format=csv`.
