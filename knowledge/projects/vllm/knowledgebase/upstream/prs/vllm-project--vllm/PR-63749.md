# [Bugfix][Rust Frontend] Return 400 for media the request got wrong

[Upstream PR](https://github.com/vllm-project/vllm/pull/63749) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

With the Rust frontend, a chat request whose media is wrong (data that is not base64, bytes that do not decode as audio or an image, a URL the media connector refuses) gets a 500 `InternalServerError`. For bad data and bytes that do not decode, the Python frontend answers with a 400.

## Claims

- Media errors that `llm_multimodal::MediaConnectorError::fault()` classifies as `MediaFault::Client` now return a 400 `BadRequestError`. This covers chat completions and `/tokenize`, and a gRPC request whose media is at fault now gets `INVALID_ARGUMENT` instead of `INTERNAL`.
- `Transient` errors (a fetch timeout, a 5xx from the media host) and `Internal` ones (a decode task or decoder I/O failing on the server) stay 500, as in Python.
- An `input_audio` part whose `format` is neither `wav` nor `mp3` gets a 400, as Python's request validation gives it, instead of a 500. Rust still accepts `WAV`/`MP3` and a missing `format`, which Python also rejects with a 400.

## Validation

Qwen/Qwen3-ASR-0.6B on one RTX 6000 Ada. The same `/v1/chat/completions` requests against the Python frontend, and against `vllm-rs` built from 75fc05a53 (the commit of the installed wheel, which pins an older llm-multimodal with the same `fault()`) without and with this change, selected with `VLLM_RUST_FRONTEND_PATH`:

| Audio input | Python | Rust, main | Rust, this PR |
|---|---|---|---|
| `input_audio` data that is not base64 | 400 | 500 | 400 |
| `input_audio` data that is base64 text, not audio | 400 | 500 | 400 |
| `input_audio` with empty data | 400 | 500 | 400 |
| `audio_url` data URL whose payload is not audio | 400 | 500 | 400 |
| `audio_url` `ftp://example.invalid/a.wav` | 400 | 500 | 400 |
| `audio_url` `http://127.0.0.1:9/nope.wav` | 500 | 500 | 400 (see below) |
| valid WAV, labelled `wav` and `mp3` | 200 | 200 | 200, same transcript |

An `input_audio` part labelled `flac` gets a 400 from Python's request validation and a 500 from Rust on main (checked on 50a184f43). The second commit makes it a 400; that is covered by the unit test below, not by the GPU run above.

Tests:

- `non_stream_chat_rejects_invalid_media_as_bad_request` (`vllm-server` route test): image data URLs that are not base64 or not an image, and a `file://` URL. All three return 500 on main.
- `input_audio_uses_connector_data_urls` (`vllm-chat`): an unsupported `input_audio` format is a validation error. It fails on the first commit.
- `media_error_is_request_validation_error_only_when_the_request_is_at_fault` (`vllm-chat`): a client error is a validation error; a timeout and a decoder I/O error are not. It fails if every media error is treated as a validation error.
- `cargo fmt --all -- --check` and `cargo clippy --workspace --all-targets --all-features --locked -- -D warnings` pass. `cargo test --workspace --all-features --locked` on Linux passes except `roundtrip_step5`, `roundtrip_mimo_v26` and `roundtrip_kimi_k25`, which load live Hugging Face checkpoints (for example, `stepfun-ai/Step-5-Preview` fails with "the model config does not define `vocab_size`") and do not touch this code. `audio_pipeline_attributes_stage_timings_to_request` also fails, on main too, when it shares a process with the other `vllm-chat` tests; it passes on its own, and CI's nextest runs each test in its own process.

## Details

`vllm-chat` turned every `MediaConnectorError`, directly and through `MultiModalError::Media`, into `Error::Multimodal(String)`. `is_request_validation_error()` counts `Multimodal` as a server error, which fits its other uses (a missing processor config, a placeholder that does not tokenize). The connector already reports whose fault each error is, so this keeps the typed error in a new `Error::Media` variant and asks `fault()`.

`Error::Media` displays the connector error's whole chain. The 400 body uses `Display`, and reqwest keeps the reason for a failed fetch (a refused connection, a TLS error) in its source, so without that the 400 would only say "error sending request for url (…)".

Where Python answers differently, this follows the connector's classification:

| Case | Python | This PR |
|---|---|---|
| Media host answers 4xx (other than 408 and 429), or the download is over the size limit | 422 | 400 |
| Media host answers 408 or 429 | 500 | 400 |
| Host cannot be resolved or refuses the connection | 500 | 400 |
| Private or loopback address | fetched like any other host | 400 (the connector never fetches these here; it was a 500 before) |
| Data URL that is not base64-encoded | 501 | 400 |

The Rust frontend has no 422 error class; adding one for the first row can be a follow-up. In the first table, nothing listens on `127.0.0.1:9`, so Python's request fails to connect, while the Rust connector refuses the address before connecting.

No open or closed PR or issue covers this; I searched for Rust frontend media error codes. #63580 adds a different variant to `is_request_validation_error()`.
