# [Bugfix][Core] Fix Gemma-4 MTP prefix-cache hit loss when lookahead block hashes are off

[Upstream PR](https://github.com/vllm-project/vllm/pull/65263) · state: open · merged: False

## Original PR description

## Overview

Follow-up to #64808, which reported that Gemma-4 MTP gets about half the prefix-cache hits of MTP0.

On latest main the default setup no longer shows it. Since #61589 (lookahead block hashes), prefix caching without a KV connector turns the EAGLE trailing-block drop off. However, the two underlying bugs still exist:
- any KV connector (`--kv-offloading-size`, LMCache, NIXL/P-D, `--kv-transfer-config`);
- `"disable_lookahead_block_hashes": true`.

This PR fixes those edge cases.

## Claims

- **Gemma-4 MTP no longer drops the last block of a prefix-cache hit.** EAGLE drafters drop it because their draft KV for that block depends on the next token. The Gemma-4 MTP drafter writes no KV of its own (it reuses the target model's), so it has nothing to recompute. `needs_eagle_block_drop()` now returns False for it, as it already does for DFlash/DSpark.
- **Keep the blocks that MTP requests actually hit at a retention checkpoint.** With EAGLE-style drafting, a request that shares a prefix up to a checkpoint can only hit one alignment unit before it (e.g. 16352 instead of 16384 with Triton, where the alignment is 32 tokens). The sliding-window layers only kept the blocks ending at the checkpoint, so that hit missed and fell back to the previous checkpoint (8192). `SlidingWindowManager.reachable_block_mask` now keeps `alignment_tokens // block_size` more blocks before each checkpoint (2 for Gemma-4), so the request hits at 16352. This applies to any EAGLE-style drafter on a sliding-window model.
- **No change to the default setup.** Without a KV connector, lookahead block hashes already turn the drop off.

## Validation

Same setup as #64808. 4 sequential requests sharing a 16384-token prefix, cached tokens per request. Connector rows show local GPU hit + CPU hit.

Setup:
- B200, TP2
- `nvidia/Gemma-4-31B-IT-NVFP4` with `google/gemma-4-31B-it-assistant` as MTP3 drafter
- `TRITON_ATTN` backend, FP8 KV
- `--prefix-cache-retention-interval 8192`

| Config | main `3fbc8d8b4` | This PR |
|---|---|---|
| MTP0 | 0 / 16384 / 16384 / 16384 | – |
| MTP3 (default) | 0 / 16384 / 16384 / 16384 | 0 / 16384 / 16384 / 16384 |
| MTP3 + `disable_lookahead_block_hashes` | 0 / 8192 / 16352 / 16352 | 0 / 16384 / 16384 / 16384 |
| MTP3 + OffloadingConnector | 0 / 8192+8192 / 8192+8192 / 8192+8192 | 0 / 16384+0 / 16384+0 / 16384+0 |

To see what each change does on its own, I also applied them separately (MTP3 + `disable_lookahead_block_hashes`):

| What was applied | Cached tokens |
|---|---|
| Nothing (main) | 0 / 8192 / 16352 / 16352 |
| Only the second change: keep 2 more blocks at each checkpoint (Gemma-4 still drops the last block) | 0 / 16352 / 16352 / 16352 |
| Only the second change, but keeping 1 more block instead of 2 | 0 / 8192 / 16352 / 16352 |
| Both changes (this PR) | 0 / 16384 / 16384 / 16384 |

Results:
- **Hits.** With this PR, Gemma-4 MTP3 matches MTP0 in every row. With OffloadingConnector, all hits are now served from GPU. The periodic-tail change alone removes the 8192 fallback; the remaining 32 tokens are the block drop, which the first change removes.
- **Acceptance.** Greedy outputs and acceptance length (3.46) are identical to main's default config with and without `disable_lookahead_block_hashes`. The check used 8 GSM8K prompts and 6 long-prefix requests.
- **Unit tests.** On B200, `tests/v1/core/test_prefix_caching.py`, `tests/v1/core/prefix_cache/`, `tests/v1/core/test_single_type_kv_cache_manager.py` and the eagle-block-drop tests in `tests/test_config.py` all pass, with no failures before or after this change.
- **Lint.** `pre-commit run --files` on the changed files passes.

New tests:
- `tests/test_config.py::test_gemma4_mtp_needs_no_eagle_block_drop`
- `tests/v1/core/test_prefix_caching.py::test_swa_reachable_block_mask_eagle_periodic_tail_reaches_sibling`: covers SWA block < alignment.

Both new tests fail on main and pass with this change.

## Details

**Root cause** (see #64808):
1. Gemma-4 MTP falls into the coordinator fallback that flags every KV group as EAGLE, because its KV-shared draft layers own no group.
2. The periodic tail uses `shift = 1`, so for the checkpoint at 16384 it caches the run whose peek block sits past the boundary.
3. A sibling diverging in [16384, 16384 + alignment) needs the run one alignment unit lower. That run is never cached, so the lookup falls back a full retention interval, to 8192.

**Why exclude Gemma-4 MTP in `needs_eagle_block_drop()` rather than change the fallback.** The fallback is a conservative default for any drafter whose layers are not annotated. Changing it would affect all such drafters. This change touches only the one drafter known to write no KV.

**Why `alignment_tokens // block_size` and not one block.** One block is enough only when the SWA block equals the hit alignment. Gemma-4 has SWA block 64 vs alignment 128 (FlashInfer) and 16 vs 32 (Triton), so widening by one block still leaves the 8192 fallback (last row above).

**Cost.** Under EAGLE with sparse retention, each periodic checkpoint keeps `alignment_tokens // block_size` more blocks per SWA group: 17 → 19 for Gemma-4. Dense retention (`retention_interval` unset or equal to the alignment) is unchanged.
