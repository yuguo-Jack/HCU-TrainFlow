# [ROCm][CI] Fix the test_qwen.py failure when AITER is on

[Upstream PR](https://github.com/vllm-project/vllm/pull/63166) · state: open · merged: False

## Original PR description

## Overview

models/multimodal/generation_ppl_test/test_qwen.py fails when AITER is on. The cause is AITER's RMSNorm has different implementation compared with HF version, and the inductor generates different fused kernels when AITER is on. More important, the results are so sensitive to those small diffs is because the ppl calculation is not accurate. Those prompt tokens outside the reference answer --- the system prompt, the question and the chat-template markup --- those tokens are nearly unpredictable, so their log-probs sit in the softmax tail, where tiny numerical differences move them a lot. They made up 20%+ of the scored tokens but about two-thirds of the total loss, and those are just numerical noises. As a fix, I updated the PPL calculation based on only answer tokens, and reference PPL is also updated accordingly.

Also, the other file, test_glm.py, is also updated with the new calculation.

- AndreasKaratzas · CHANGES_REQUESTED · 2026-10-26T20:24:10Z · [source](https://github.com/vllm-project/vllm/pull/63166#pullrequestreview-5658478489)

@qli88 The old PPL isn't "incorrect". It measures something noisier. For a vLLM-vs-HF agreement test, the question isn't which PPL definition is textbook, it's whether the test fails on real bugs and passes on harmless differences. Answer-only scoring changes that trade-off, and it isn't obvious in which direction. The old metric is dominated by low-probability prompt and template tokens, whose log-probs move almost one-for-one with any logit change. That's why harmless AITER differences push it past 1%. The answer tokens are mostly confident, so the new metric damps every logit change, harmless or not. It will still catch bugs that change the answer (vision features, rope, prompt processing), but subtle text-path drift (kernel precision, accumulation, small attention errors) becomes much harder to see at the same 1% tolerance. The tolerance was never recalibrated for the new metric. As it stands, this lowers the bar for every backend. 

For this PR, keep the change narrow:
- keep the current metric and reference values;
- parametrize aiter_off / aiter_on / aiter_on_rmsnorm_off;
- for aiter_on only, either use the fp32-accumulating RMSNorm path @divakar-amd pointed to (use_model_sensitive_rmsnorm), or apply a wider tolerance with a comment explaining why.

That fixes the failure and leaves every other configuration exactly as strict as today. The answer-only metric goes in a separate PR, and it has to show it is at least as good at catching bugs, with data for both metrics:
1. Noise floor: the vLLM-vs-HF difference for each model × the three AITER configs, plus CUDA. These should pass.
2. Detection: two or three injected regressions that must fail, e.g. a small perturbation of the vision features, a rope position offset, and reduced-precision accumulation in attention.
3. The case you mentioned where the old metric missed a real issue. You've cited it twice as the reason for this change; please post it and show the new metric catches it.
4. Provenance for any new hf_ppl values: hardware, dtype and transformers version, in a comment next to the constants. @divakar-amd asked for this three days ago.

If answer-only shows a clearly better gap between noise and detection, I'll support it. Without that data it's a relaxation, not a fix. Longer term, comparing per-token logprobs directly (check_logprobs_close-style, as other model tests do) would be stricter than either PPL and would show exactly which token diverges. Also, in the current code: _answer_span tokenizes the answer on its own and searches for it inside the prompt. BPE can merge the first answer token differently in context, so rows can fail with Reference answer tokens not found. If this approach comes back, render the conversation with and without the assistant answer and take the tokens after the shared prefix.

Several requests in this thread were answered by changing the PR's direction instead of with the data asked for: the failure log, the AITER reproduction script, the split and the provenance. Please address these directly.

> We are still changing the expected values and the evaluation loop? I thought the other option was to just simply increase tolerance for the aiter on rmsnorm on option only and that the other two configs would just pass.

The original PPL test scored the wrong tokens. Each prompt was the full conversation: system prompt, chat-template markup, image, question and the reference answer as the assistant turn. That part is correct. But when computing PPL, the test masked only the image tokens, so the metric also included the system prompt, the question, the template tokens and the trailing generation prompt. Those tokens aren't conditioned on anything meaningful and have very high perplexity. They dominated the average and made the result sensitive to small numerical differences, such as switching AITER RMSNorm on or off.

My current change keeps the same input but scores only the reference-answer tokens. The same mask is applied on both the vLLM and Hugging Face sides, and the hardcoded Hugging Face baselines were regenerated. They are now between 4.2 and 6.3, down from 6.5 to 22.2.  @AndreasKaratzas

- qli88 · comment · 2026-10-26T20:46:45Z · [source](https://github.com/vllm-project/vllm/pull/63166#issuecomment-6426936328)

@AndreasKaratzas  Thanks, this is a fair review, and I agree with most of it.

**On "incorrect":** agreed, that was the wrong word. The old metric is a valid vLLM-vs-HF comparison, since both sides use the same mask. My concern is its noise, not its correctness.

**On direction:** I measured this on Qwen2.5-VL-3B (60 llava-bench samples, BF16, MI350X), and I think it answers the "not obvious which direction" point for at least one bug class:

| | Full-prompt PPL | Answer-only PPL |
|---|---|---|
| Spread across 8 harmless configs (AITER off / on / on with RMSNorm off, × emulated precision casts / SiLU variants) | 2.57% | 0.10% |
| Shift from an injected bug (`do_normalize=False`), vs vLLM without the bug | +0.45% | +1.30% |
| vLLM vs HF with the bug, at the 1% tolerance | +0.15% (**passes**) | +1.40% (**fails**) |

To be clear, this was an injected bug, not one found in the wild. The full-prompt metric is dominated by tokens with no image dependence. The 840 system-prompt tokens before the image have perplexity around 12,000 and varied by up to 12% across the configs above from numerical noise alone. You're right that confident answer tokens damp logit changes, but that damping applies to noise and bugs alike, and here the net signal-to-noise ratio was about 13× better.

I also agree the data is incomplete. With the same injected bug, Qwen3-VL-4B came out at only −0.48% vs HF and Qwen3.5-4B at +0.004%, so 1% is not the right tolerance for the new metric. I also haven't tested text-path regressions.

**Plan:**
1. **This PR:** keep the current metric and reference values, parametrize `aiter_off` / `aiter_on` / `aiter_on_rmsnorm_off`, and handle `aiter_on` with `use_model_sensitive_rmsnorm` (add a commented wider tolerance).
2. **A follow-up PR for answer-only scoring**, including:
   - the noise floor for each model × the three AITER configs on MI350X, plus CUDA;
   - detection results for injected regressions (vision-feature perturbation, rope position offset, reduced-precision attention accumulation) under both metrics;
   - a tolerance calibrated from that data;
   - provenance comments next to the `hf_ppl` constants;
   - span extraction by rendering with and without the assistant turn.
   For the record, the current constants were generated with Transformers 5.20.2, BF16 (`hf_dtype="auto"`), torch 2.13.0+rocm10.0.0, on an AMD Instinct MI350X.
