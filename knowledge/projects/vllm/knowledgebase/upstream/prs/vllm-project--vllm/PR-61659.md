# [Bugfix][HiSparse] Pad staged prefill KV to avoid a trtllm-gen out-of-bounds read

[Upstream PR](https://github.com/vllm-project/vllm/pull/61659) · state: closed · merged: True

## Original PR description

## Problem

HiSparse prefill randomly crashes with `CUDA error: an illegal memory access` in `sparse_mla_attention.forward_mqa` → `_forward_mqa_kernel` on the staged prefill cache. `HiSparseRuntime.gather_prefill_cache` stages a request's KV into an exact-size buffer (often 1–3 blocks of 64 rows), and FlashInfer's trtllm-gen sparse MLA decode kernel reads ~170–250 rows from the start of its KV cache regardless of the cache's size or the top-k indices (flashinfer-ai/flashinfer#6484). It faults whenever the caching allocator puts the staged buffer near an unmapped page. Surfaced in #61487 (HiSparse + DBO); DBO makes it more frequent but it is not DBO-specific.

## Fix

Allocate at least 256 rows behind the staged buffer and return the exact-size view, so all downstream shapes are unchanged. Cost: ≤168 KB of transient allocation per staged layer.

## Test plan

Hardware: 2x B200 (pirate2 dell-b200-01), flashinfer 0.7.0.post1, torch 2.13.0+cu130, CUDA 13.0. vLLM `2f18d13cf` with and without this PR's diff.

**Kernel.** The flashinfer#6484 repro places an FP8 KV cache so it ends at an unmapped 2 MiB page. It faults with 1–3 pages (64–192 rows) and is clean with 4, 5, 6, 8 and 16 pages, at batch sizes 1–128. Bisecting the slack shows the kernel reads about 170–227 rows from the start of the cache, under the 256-row floor.

**Server.** GLM-5.3 NVFP4 with dummy weights and 8 layers, DP2 + EP, eager. Each server takes 3 rounds of 128 concurrent 30-word completions with `max_tokens=128`.

```bash
VLLM_USE_V2_MODEL_RUNNER=1 vllm serve RedHatAI/GLM-5.3-NVFP4 --load-format dummy --hf-overrides '{"num_hidden_layers": 8}' \
  -tp 1 -dp 2 --enable-expert-parallel --all2all-backend deepep_low_latency \
  --kv-cache-dtype fp8 --block-size 64 --max-model-len 8192 \
  --attention-config '{"hisparse_config":{}}' \
  --kv-transfer-config '{"kv_connector":"HiSparseConnector","kv_role":"kv_both","kv_connector_extra_config":{"host_pool_gib":24}}' \
  --compilation-config '{"cudagraph_mode":"NONE"}'
# The DBO rows add: --enable-dbo --dbo-decode-token-threshold 2 --dbo-prefill-token-threshold 512
```

| Revision | DBO | Servers | Result |
|---|---|---|---|
| main | on | 2 | 2/2 illegal memory access in round 1. With `CUDA_LAUNCH_BLOCKING=1` the trace points at `sparse_mla_attention.py:858` (`_forward_mqa_kernel` on the `stage_prefill_rows` cache) → `trtllm_batch_decode_with_kv_cache_mla` |
| main | off | 2 | 1/2 illegal memory access in round 2 |
| main + this PR | off | 2 | 768/768 requests 200 |
| main + this PR | on | 4 (+3 with launch blocking) | No illegal memory access. 2/4 servers die in round 1 from the separate #61487 crash (`dbo_register_recv_hook`, which hides microbatch 1's `CUDA error: invalid argument`); 0/3 with launch blocking |

The crash is not DBO-specific; DBO only makes it show up sooner. The remaining DBO failure is #61487 and is out of scope for this PR.
