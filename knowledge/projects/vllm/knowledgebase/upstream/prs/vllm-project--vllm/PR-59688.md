# [Bugfix][HiSparse] Reject cudagraph_mode=FULL at startup

[Upstream PR](https://github.com/vllm-project/vllm/pull/59688) · state: closed · merged: True

## Original PR description

## Purpose

HiSparse cannot capture prefill or mixed batches in CUDA graphs. It picks its prefill path from per-step page residency (resident pages, or spilled pages staged from host), and it mirrors prefill KV to host outside the graph. With `cudagraph_mode=FULL`, a backend reporting `ALWAYS` support (FlashInfer sparse MLA on SM100) has prefill/mixed batches captured as FULL graphs. A replay could then take the branch frozen at capture and skip the host mirror.

## Changes

HiSparse rejects `cudagraph_mode=FULL` at config validation, next to its other unsupported-config checks (PP, DCP). The error points to `FULL_AND_PIECEWISE` (the default), which keeps FULL graphs for decode batches. Being a config check, it covers every backend HiSparse runs on.

Separately, `FULL` with FlashInfer sparse MLA on SM100 currently crashes on prefill replay even without HiSparse: #59681.

## Test Plan

- New `test_hisparse_rejects_full_cudagraph_mode` in `tests/test_config.py`.
- B200, shrunk GLM-5.3 (dummy weights), `FLASHINFER_MLA_SPARSE`, `cudagraph_mode=FULL`, a small pool so prefill context spills to host: TRTLLM ragged and FlashAttention prefill.

## Test Result

- The new test fails without the change; `tests/test_config.py -k hisparse`: 13 passed.
- B200, before: `FULL` + HiSparse crashed in both runs: a mixed active/empty query rows error with TRTLLM ragged prefill, an illegal memory access with FlashAttention prefill. Now it fails at startup with the error above.
