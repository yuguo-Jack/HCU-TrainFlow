# [Bugfix] Fix multimodal sender-cache invalidation race with queued renders

[Upstream PR](https://github.com/vllm-project/vllm/pull/62164) · state: closed · merged: True

## Original PR description

## Overview

Fixes #62121. Apply sender-cache invalidations between generation renders on the single-worker multimodal executor so an engine cache-miss report cannot remove an entry between the processor's cache lookup and merge.

## Claims

- In-flight generation renders on the single-worker multimodal executor complete without the reported `Expected a cached item` assertion; already-queued renders consume pending invalidations before looking up cached data.
- Unrelated outputs keep flowing while multimodal processing or cache invalidation is blocked.
- Ignore uncached hashes and coalesce duplicate miss reports, avoiding unbounded notification growth on pre-rendered `features` traffic that never invokes the renderer.

## Details

The output handler previously invalidated the sender cache on the asyncio thread while the renderer performed its lookup and merge on its single-worker multimodal executor.

The handler now records missed hashes before publishing the associated outputs. Only hashes currently present in the sender cache are retained. When a processor cache is present, a short lock protects a pending set; each render swaps that set before its first lookup. Both helpers return immediately when there is no cache. Enqueue also returns for empty input or when filtering leaves no live hashes, before acquiring the lock. Membership checks and cache invalidation execute outside the lock. Failed invalidation restores the current and remaining hashes without discarding newly arrived notifications. Cache clear retains its existing behavior; stale notifications become no-ops at the next render boundary.

This avoids a second executor job and queue/set mirrored state. Pending records can briefly outlive the cache entry they reference, so this does not claim that their count always equals the instantaneous live cache size. Sync LLM retains direct invalidation.

This is distinct from #34749's assertion-to-error conversion and #61656's endpoint retries. P1 drift itself, automatic HTTP retries, and #62123's SHM handle issue are out of scope. The [pre-existing pooling/embedding cross-executor race](https://github.com/vllm-project/vllm/pull/62164#discussion_r4311154000) is also not addressed by this fix. The issue came from a public report and was investigated with constructed reproductions; it was not encountered in the submitter's production workload. AI assistance was used for investigation, implementation and validation, including this follow-up review.

File: `vllm/renderers/base.py` · line None

🟡 (optional) Servers that only receive pre-rendered `features` requests will keep growing a miss-hash backlog in memory that is never freed. On the base branch these misses cost nothing. `queue_mm_cache_invalidations` appends every reported miss hash to `_pending_mm_cache_invalidations`. Only `_process_multimodal` drains it, and the `/generate` features path never calls that method. Fix: bound the backlog by distinct live entries. Skip hashes the sender cache does not hold (`is_cached_item`), and dedupe pending hashes so the queue never outgrows the cache.
