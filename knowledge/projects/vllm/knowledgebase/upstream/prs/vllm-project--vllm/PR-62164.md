# [Bugfix] Fix multimodal sender-cache invalidation race with queued renders

[Upstream PR](https://github.com/vllm-project/vllm/pull/62164) · state: open · merged: False

## Original PR description

## Overview

Fixes #62121. Apply sender-cache invalidations between multimodal renders so an engine cache-miss report cannot remove an entry between the processor's cache lookup and merge.

## Claims

- In-flight renders complete without the reported `Expected a cached item` assertion; already-queued renders consume pending invalidations before looking up cached data.
- Unrelated outputs keep flowing while multimodal processing or cache invalidation is blocked.
- Ignore uncached hashes and coalesce duplicate miss reports, avoiding unbounded notification growth on pre-rendered `features` traffic that never invokes the renderer.

## Details

The output handler previously invalidated the sender cache on the asyncio thread while the renderer performed its lookup and merge on its single-worker multimodal executor.

The handler now records missed hashes before publishing the associated outputs. Only hashes currently present in the sender cache are retained. A short lock protects a pending set; each render swaps that set before its first lookup. Membership checks and cache invalidation execute outside the lock. Failed invalidation restores the current and remaining hashes without discarding newly arrived notifications. Cache clear retains its existing behavior; stale notifications become no-ops at the next render boundary.

This avoids a second executor job and queue/set mirrored state. Pending records can briefly outlive the cache entry they reference, so this does not claim that their count always equals the instantaneous live cache size. Sync LLM retains direct invalidation.

This is distinct from #34749's assertion-to-error conversion and #61656's endpoint retries. P1 drift itself, automatic HTTP retries, and #62123's SHM handle issue are out of scope. The issue came from a public report and was investigated with constructed reproductions; it was not encountered in the submitter's production workload. AI assistance was used for investigation, implementation and validation, including this follow-up review.

🟡 (optional) Servers that only receive pre-rendered `features` requests will keep growing a miss-hash backlog in memory that is never freed. On the base branch these misses cost nothing. `queue_mm_cache_invalidations` appends every reported miss hash to `_pending_mm_cache_invalidations`. Only `_process_multimodal` drains it, and the `/generate` features path never calls that method. Fix: bound the backlog by distinct live entries. Skip hashes the sender cache does not hold (`is_cached_item`), and dedupe pending hashes so the queue never outgrows the cache. Hashes an in-flight render repopulates have already resent data, so dropping them is safe.

<details>
<summary>Why this was flagged</summary>

The trigger is a token-in-token-out `/generate` server whose multimodal traffic arrives as `features` with `kwargs_data` items set to None. The `features` branch in serving.py builds `mm_input` directly. That branch never calls `render_cmpl_async` or `_process_multimodal`. When P1 lacks the hash, `get_and_update_features` raises `MultiModalCacheMissError` (cache/base.py:478). The output handler at async_llm.py:882-891 queues every such hash whenever `renderer.mm_processor_cache` is not None, which holds with the default LRU sender cache. The only reader is `_drain_mm_cache_invalidations`, called at base.py:926 from `_process_multimodal`. So on such a server the `SimpleQueue` grows by one string per missed item per failed request and is never freed. The base branch called `invalidate` (a `dict.pop` in lru.py:80) right away and kept nothing.

**Verification:** `queue_mm_cache_invalidations` (base.py ~396-400) puts every reported hash on `_pending_mm_cache_invalidations`. The only drain is at the top of `_process_multimodal` (base.py ~926), which the `features` branch (serving.py 269-290) never calls. On the base branch the handler called `mm_processor_cache.invalidate(mm_hash)` right away, so nothing was kept.

</details>

🟣 pre-existing, not blocking: pre-existing: Online pooling and embedding requests with images can still hit `Expected a cached item` after this fix. Their sync renders run on the multi-worker `_executor`, not the single-worker `_mm_executor`. The drain at base.py:932 then runs on a pool thread. It can pop a hash while an async render on `_mm_executor`, or another pool render, is between lookup and merge. Fix: make sure no other render can be between lookup and merge when pending invalidations are applied. One way is to send every online `_process_multimodal` call through `_mm_executor`. Another is to hold one lock across the drain plus `mm_processor.apply`.
_A small fix can ride a push you are already making; otherwise a short reply is enough._

<details>
<summary>Why this was flagged</summary>

Online pooling serving calls `io_processor.render_async`. That is `make_async(self.render, executor=self.renderer._executor)` (pooling/base/io_processor.py:71-72), and `renderer._executor` is a `_SwappableExecutor(max_workers=renderer_num_workers)` (renderers/base.py:144). `render` calls sync `render_cmpl`/`render_chat` (io_processor.py:260-275), which goes through `_process_tokens` and calls `_process_multimodal` directly (base.py:978). So `_drain_mm_cache_invalidations` (base.py:932) runs on a pool thread, concurrently with renders on `_mm_executor`. A queued miss hash is popped from the LRU (`invalidate` is `self._cache.pop`, lru.py:83) in the middle of the other render. That render's later `get_and_update_item` then fails `assert mm_item is not None, f"Expected a cached item for {mm_hash=}"` (lru.py:60). The base branch had the same race, with invalidation on the event-loop thread, so this is not a regression. The PR's claim that renders cannot lose an entry between lookup and merge does not hold for this path, because the drain only serializes with work on `_mm_executor`.

**Verification:** A `/tokenize` request with an image runs on `_mm_executor`, and its drain at base.py:932 calls `self.mm_processor_cache.invalidate(...)` while a pooling render on the `_executor` thread is between lookup and merge. That pooling render can then still hit `Expected a cached item`. On the base branch, async_llm.py called `mm_processor_cache.invalidate` directly and already raced the same way.

</details>
