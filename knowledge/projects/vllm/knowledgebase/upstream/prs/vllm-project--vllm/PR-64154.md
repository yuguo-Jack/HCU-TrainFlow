# [ROCm][KVConnector][MoRIIO] Fence a stuck WRITE producer so decode can free its blocks

[Upstream PR](https://github.com/vllm-project/vllm/pull/64154) · state: open · merged: False

## Original PR description

﻿<!-- markdownlint-disable -->

## Overview

**Draft, stacked on #58962 and depending on ROCm/mori#848 (not merged).** Only the last two commits ("Fence a stuck WRITE producer ..." and "Drop the WRITE fence debug fault injection") are new here; the rest is #58962. This branch is based on the previous revision of #58962 and will be rebased onto its current head.

With `write_recv_timeout` (#58962), a timed-out MoRIIO WRITE request is failed but its decode KV blocks stay allocated, because the prefill may still write into them (one-sided RDMA). This makes them safe to free: decode fences the stuck prefill with the MoRI-IO receiver fence before freeing.

## Claims

- Opt-in `kv_connector_extra_config.write_recv_fence`: when a WRITE receive times out, decode fences that prefill, then frees the blocks of every request still waiting on it instead of holding them until restart.
- Freeing is gated on the fence succeeding on every prefill TP rank; otherwise the existing keep-the-blocks behaviour from #58962 applies.
- The prefill drops the aborted transfers and recovers its connection to the decode; serving continues.
- Prefill write failures no longer raise out of the model step; they are reported to decode as `write_failed`.

## Validation

- Unit tests: `tests/v1/kv_connector/unit/test_moriio_write_fence.py` (32 tests, MoRI engine mocked), covering the decode fence/abort/ack/unfence state machine, the prefill abort handling, and the real vLLM `Scheduler` freeing a fenced request's blocks. In the `vllm-openai-rocm` nightly image for main `e4a5b55` on MI308X, all MoRIIO unit tests, `test_output_aggregator.py` and `tests/v1/core/test_scheduler.py` pass with this branch (1193 passed; 1131 without it, the difference being the tests added here and in #58962). `ruff check` / `ruff format --check` (v0.14.0) are clean.
- Hardware: 1P1D, TP8, `gpt-oss-120b` on MI355X with MoRI built from ROCm/mori#848. One transfer's writes were held on the prefill with a local fault-injection patch (not part of this PR). The stuck request fails at the timeout, decode and prefill KV usage return to zero, and serving continues at 10 req/s; only requests sent during the abort round trip fail.

## Details

**Why a fence.** A timeout alone cannot prove the prefill's NIC has stopped writing into the decode blocks, so freeing on timeout risks silent corruption of the request that gets those blocks next. Asking the prefill whether it is safe (as in Z.AI's fix) does not cover a prefill that is dead or unreachable. The MoRI-IO receiver fence (`IOEngine.fence_remote_engine` / `unfence_remote_engine`, ROCm/mori#848) revokes the peer's access on the decode side, so once it succeeds no late write can land, whether the prefill is slow or dead.

**Decode.**
1. On a receive timeout, the decode scheduler issues a fence order for that prefill (DP rank) covering every request still waiting on it.
2. Each decode TP rank fences all TP ranks of the prefill.
3. If the fence succeeded on every rank, the requests are reported failed and finished, so their blocks are freed; otherwise they are only failed and keep their blocks.
4. Decode sends the prefill a `fence_abort`, re-sent every `FENCE_ABORT_RESEND_INTERVAL` (10 s) until acked, and unfences once every prefill rank has acked. A `write_done` / `write_failed` arriving for a fenced transfer is dropped.

**Prefill.** On `fence_abort` it drops the aborted transfers, resets its connections to that decode rank, and acks; a repeated abort is re-acked without another reset. A failed transfer is marked done and, when nothing is still in flight, reported to decode as `write_failed`, which decode counts across writers before failing the request. A dead session is rebuilt before the next write.

**Limitations.**
- A dead prefill never acks, so it stays fenced on the decode until restart (its blocks are freed; only the fence entry remains).
- Requests sent to that prefill during the abort round trip fail.
- Requires MoRI with ROCm/mori#848; enabling `write_recv_fence` on a MoRI build without `IOEngine.fence_remote_engine` fails at startup.
