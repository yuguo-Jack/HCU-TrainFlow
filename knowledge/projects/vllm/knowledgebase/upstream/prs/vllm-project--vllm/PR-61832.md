# [CI] Shard draft decoding, Qwen eval and scheduling automatically

[Upstream PR](https://github.com/vllm-project/vllm/pull/61832) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

Takes over #61476 (Kevin's batch 4), rebased onto main, and enables `automatic_shard` on three steps and two AMD mirrors. It changes no tests. `elastic-ep-scaling-test` dropped out of the batch because main has since disabled it (#63609).

## Claims

| Step | Command | Shards in [97476](https://buildkite.com/vllm/ci/builds/97476) |
|---|---|---:|
| `e2e-scheduling-accuracy-1-gpu` | one `pytest` over `v1/e2e/general` scheduling tests | 3 |
| `lm-eval-qwen3-5-models-2xb200` (nightly) | one `pytest` over `evals/gsm8k` | 2 |
| `spec-decode-draft-model-nightly-b200` (nightly) | one `pytest` | 2 |
| `amd-e2e-scheduling-accuracy-1-gpu` | inherits the base command | 2 |
| `amd-lm-eval-qwen3-5-models-2xb200` (nightly) | inherits the base command | 2 planned |

- Every test runs exactly once across the shards, with the same commands and environment as before.

## Validation

- `/ci run` [97476](https://buildkite.com/vllm/ci/builds/97476), rebased on main after ci-infra#836: every shard of the three steps and the E2E Scheduling Accuracy mirror passed, with passed/skipped counts equal to main's single job ([97527](https://buildkite.com/vllm/ci/builds/97527), [97472](https://buildkite.com/vllm/ci/builds/97472)), and machine time in line with or below main.
- The Qwen3.5 AMD mirror was added through the build's "Run more jobs" step and passed as one job; that path uploads a picked step without planning shards, so its 2-shard plan was checked with the harness below and first runs sharded on a nightly.
- Rendered each step and mirror with the pipeline generator and ran every shard's commands against a mock test tree, as a PR build and with main's `pytest -p ci_otel` wrapper: every test ran in exactly one shard.

## Details

- **AMD mirrors.** Both run past the 20-minute target as one job on main, so they are enrolled with their base steps. In each, one test takes about as long as the target by itself, so the slowest shard sits near the target and can't go lower without splitting that test.
- **Left out.** `kv-offload-large`: its two tests land one per shard, so each shard repeats the multi-GPU model startup for a few minutes of tests.
- **Timeouts unchanged (human).** As in #62077 and #62120, `timeout_in_minutes` stays per job; fallback-aware timeouts belong in a central timeout setting.
