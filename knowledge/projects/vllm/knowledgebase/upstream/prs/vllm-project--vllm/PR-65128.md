# [MORI][DBO] Dual batch overlap with MoRI EPv2 (native and AsyncLL), and DBO fixes on ROCm

[Upstream PR](https://github.com/vllm-project/vllm/pull/65128) · state: open · merged: False

## Original PR description

## Overview

Lets `--all2all-backend mori` run MoRI EPv2 with `--enable-dbo`, adds MoRI EPv2's AsyncLL path (SDMA) under `MORI_ENABLE_SDMA=1`, and fixes DBO bugs found with DeepSeek-V4 on ROCm (MI355X, DP8+EP8), on both the V2 and the V1 model runner. No new flags or environment variables.

MoRI EPv2:
- Each DBO microbatch uses its own EPv2 op, since an op's buffers are only valid until its next call. Ops for later microbatches are sized to their share of the batch.
- Native: dispatch and combine run on the comm stream after yielding to the other microbatch (`_comm_region`, as in naive DP/EP).
- AsyncLL: dispatch and combine split into send and receive (`prepare_async` / `finalize_async`); under DBO each microbatch runs the other's pending receive before its own send, as with deepep_ll.
- **Behavior change:** on gfx950, with a MoRI that has the EPv2 AsyncLL kernels, `MORI_ENABLE_SDMA=1` now selects EPv2 AsyncLL instead of falling back to EPv1. `VLLM_MORI_EP_V2=0` still forces EPv1.

DBO fixes:
- A rank's last microbatch can be pure DP padding. Such a step now runs eager instead of replaying a FULL graph, and two DeepSeek-V4 ROCm ops (MXFP4 indexer compressor, sparse decode) no longer fault on it.
- Every microbatch's workspace is sized before capture locks it.
- hipBLASLt handles are created on every stream, including the model's side streams, before capture (otherwise `HIP error 900`).

## Recommendation

Use DBO for prefill only: set a large `--dbo-decode-token-threshold`, or with PD disaggregation enable DBO on the prefill instances only. Decode runs as a FULL graph, where native microbatches run back to back and AsyncLL receives spin-wait, so splitting decode makes it slower. The threshold defaults are shared by all backends and are not changed here.

## Validation

DeepSeek-V4-Pro, 8× MI355X, DP8+EP8, `--max-num-batched-tokens 8192 --gpu-memory-utilization 0.92`, CUDA graphs on. Prefill: 8k in / 1 out, c256. Decode: 1k in / 1k out, c512. Changes are against DBO off with the same EPv2 mode.

| EPv2 | DBO | prefill tok/s | decode tok/s |
|---|---|---|---|
| native | off | 51,902 | 8,716 |
| native | on | 57,994 (+11.7%) | 6,365 (−27.0%) |
| native | on, decode not split | 59,176 (+14.0%) | 9,008 (+3.4%) |
| AsyncLL | off | 53,368 | 8,096 |
| AsyncLL | on | 64,944 (+21.7%) | 6,092 (−24.8%) |
| AsyncLL | on, decode not split | 65,076 (+21.9%) | 8,284 (+2.3%) |

GSM8K is 0.945–0.955 in all runs. A final run on the submitted code (V2 and V1 runners, including thresholds 2 / 2 for many empty microbatches) matched these within 3% with no faults, apart from the V1 run noted below. `tests/v1/worker` and the MoRI EPv2 tests pass, except 3 `test_gpu_pcp_manager` cases that need `ray`.

## Notes

- V1 runner + DBO: its CUDA graph memory profile does not count the microbatched graphs (upstream behavior), so leave a few GiB more headroom. One V1 AsyncLL decode run ran out of GPU memory at 0.92.
