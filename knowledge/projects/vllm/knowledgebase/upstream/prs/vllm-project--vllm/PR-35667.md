# [Bugfix] Fix tool call ID collision in Anthropic endpoint

[Upstream PR](https://github.com/vllm-project/vllm/pull/35667) · state: open · merged: False

## Original PR description

## Purpose

Fix tool call ID collision in the Anthropic Messages API endpoint.

## Problem

When an Anthropic request contains `tool_use` blocks without an explicit
`id`, the fallback ID was generated using `int(time.time())`. This causes
ID collisions when multiple tool calls are processed within the same second
— all of them get the same ID.

## Fix

Replace `f"call_{int(time.time())}"` with `f"call_{uuid.uuid4().hex[:24]}"`.
`uuid` is already imported and used elsewhere in this file for signature
generation.

Also removed the now-unused `time` import.

## Test Plan

Existing Anthropic API tests cover tool call conversion paths. The change
is minimal and maintains backward compatibility (IDs are still prefixed
with `call_`).

While refactoring to use `self.stop_reason_map` is a good improvement for maintainability, this change introduces an inconsistency with the streaming path's logic, which this change aims to unify.

- **Unknown `finish_reason`**: This implementation maps unknown `finish_reason` values (e.g., `content_filter`) to `"end_turn"` because of the default value in `.get()`. The streaming path does not provide a default, so unknown reasons correctly map to `None`.
- **`None` `finish_reason`**: This implementation results in `stop_reason` being `None` if `choice.finish_reason` is `None`. The streaming path handles this with `finish_reason or "stop"`, resulting in `"end_turn"`.

To truly unify the logic and handle all cases consistently with the streaming path, I suggest using the same expression.

```python
        result.stop_reason = self.stop_reason_map.get(choice.finish_reason or "stop")
```
