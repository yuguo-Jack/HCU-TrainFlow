# [HiSparse] Read resident KV directly for FlashMLA BF16 prefills

[Upstream PR](https://github.com/vllm-project/vllm/pull/60419) · state: closed · merged: False

## Original PR description

## Purpose

Part of #60420 (does not close it: host-backed prefills still stage).

With HiSparse, the FlashMLA sparse BF16 path stages every prefill: it copies the request's full history from host into a transient GPU buffer (`stage_prefill_rows`), even when all of its pages are GPU-resident, and joins decode and prefill outputs with `torch.cat` in mixed batches. Startup profiling doesn't cover either allocation (its dummy run is one chunk of short prefills), so a long accepted prompt can OOM a running server. The same failure was reproduced on the FlashInfer path; see #60417.

Fix: when every scheduled page is resident (`all_context_pages_resident`), convert all rows against resident pages and run one kernel. Host-backed prefills still stage; making that buffer accounted is tracked in #60072.

Independent of #60417. Both PRs carry the same 4-line `index_group.py` routing change (and its test case), so whichever lands second rebases trivially.

`test_hisparse_mixed_batch_bf16_row_split` keeps its KV in the host pool, so it now sets `all_context_pages_resident = False` to match that scenario. The default of `True` only went unnoticed before because this path never checked the flag.
