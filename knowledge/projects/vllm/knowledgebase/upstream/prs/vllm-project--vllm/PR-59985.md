# [Bugfix] Keep GateLinear batch invariant under VLLM_BATCH_INVARIANT

[Upstream PR](https://github.com/vllm-project/vllm/pull/59985) · state: open · merged: False

## Original PR description

## Overview

With `VLLM_BATCH_INVARIANT=1`, MoE models whose gate uses `GateLinear`'s specialized router GEMM tiers are not batch invariant. I found this while validating models for #27433 on NVIDIA GB300: `zai-org/GLM-4.5-Air`, `MiniMaxAI/MiniMax-M2` and `baidu/ERNIE-4.5-21B-A3B-PT` all fail the batch-invariance suite. This PR makes `GateLinear` use the batch-invariant linear path in that mode.

## Claims

- GLM-4.5-Air, MiniMax-M2 and ERNIE-4.5-21B-A3B pass the full batch-invariance suite on GB300 (22/22 each). Without the fix they fail 12, 16 and 6 of the 22 tests.
- New regression test `tests/v1/determinism/test_gate_linear_batch_invariant.py` fails without the fix on both Blackwell and Ampere and passes with it.
- No change when `VLLM_BATCH_INVARIANT` is off.

## Validation

NVIDIA GB300 (SM 10.3), driver 580.167.08, CUDA toolkit 13.1, torch 2.13.0+cu130, vLLM `f590eb2448` (`gate_linear.py` is unchanged between that commit and this PR's base).

## Details

**Root cause.** `UnquantizedLinearMethod.apply` is where `VLLM_BATCH_INVARIANT` is honored for linear layers (it calls `linear_batch_invariant`). `GateLinear.forward` returns from tiers 1 to 4 before reaching it. Those tiers also dispatch on the number of tokens:

- tier 1 (`ll_bf16_gemm`) is used for `M <= 16`, otherwise the cuBLAS `out_dtype` tier;
- tier 2 (fp32 kernel) is used for `M <= 32`, otherwise BF16x3 or `F.linear`;
- tier 3 (BF16x3) picks its tile size and split-K from the token count in `_pick_tile_config`.

So the router logits of one row can come from a different kernel, or a different K-reduction order, depending on how many tokens share the batch. A small difference in the logits can change the selected experts, which then changes logprobs and tokens. GLM-4.5-Air and ERNIE-4.5 have fp32 gates that take the BF16x3 tier on Blackwell; MiniMax-M2's gate shape (3072 x 256) also has the fp32 kernel, so it switches kernels at `M = 32`.

To localize it I compared the same prompt alone and inside a mixed batch on GLM-4.5-Air. Disabling fused grouped top-k did not restore bitwise-equal logprobs; disabling the `GateLinear` tiers did.

These tiers were added between June and September (#46385, #42562, #47973, #55899), and #58234 moved all MoE models to `GateLinear`, after most of the batch-invariance model validation was done.

**Fix.** The tier eligibility flags are now false when `envs.VLLM_BATCH_INVARIANT` is set, so `forward` falls through to tier 5 (`ReplicatedLinear`), which uses the batch-invariant matmul. The flags are also what `set_out_dtype` and the kernel warmup read, so warmup for the unused kernels is skipped too.

**Cost.** In batch-invariant mode the gate no longer uses the specialized kernels. Median time of one `GateLinear.forward` call on GB300 (bf16 input, 200 iterations after warmup):

| Gate (hidden x experts) | M | Specialized tiers | Batch-invariant path |
| --- | ---: | ---: | ---: |
| fp32, 3072 x 256 | 1 | 54 us | 139 us |
| fp32, 3072 x 256 | 1024 | 134 us | 145 us |
| fp32, 4096 x 128 | 1 | 105 us | 146 us |
| fp32, 4096 x 128 | 1024 | 98 us | 155 us |
| bf16 with fp32 output, 7168 x 256 | 1 | 73 us | 131 us |
| bf16 with fp32 output, 7168 x 256 | 1024 | 72 us | 133 us |

That is 1.1x to 2.7x per call, between 10 and 90 microseconds, and only when the mode is on. I disabled all four tiers because that is the configuration I validated. If a tier can be shown to be batch invariant on its own, it could be re-enabled separately.

**CI.** The new test is added to the H100 and B200 Batch Invariance jobs, where the specialized tiers exist.

**Related.** #57016 and #57092 are about batch invariance of the MoE experts, a different component.
