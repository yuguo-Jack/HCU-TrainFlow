# [Bugfix][KV Offload] Preserve running request prefixes across LRU store batches

[Upstream PR](https://github.com/vllm-project/vllm/pull/61050) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

Preserve the reusable head of CPU-offloaded prefixes while their requests are still running, across store batches and KV groups. Related to [the unfinished-request observation in #58804](https://github.com/vllm-project/vllm/issues/58804#issuecomment-6098736505); this addresses that eviction pattern rather than the issue's entire throughput regression.

## Claims

- Positioned keys share a provisional request rank, with later token positions evicted first across batches.
- `insert(key, chunk, req_context)` assigns new chunks their final provisional rank directly. First observations still handle resident prefixes reused by load/store and anchor requests before allocation retries.
- Finalization commits recency and ARC frequency accounting; transfer pinning, newer shared accesses, reset and keys without positions retain their behavior.

## Details

Insertion previously made an unfinished request's head older than its tail until finalization. Evicting the head makes every remaining suffix unreachable by contiguous-prefix lookup.

LRU uses `(request_rank, -token_position)` and the existing lazy heap update/compaction paths. The request rank is anchored at first observation; new chunks receive it inside `insert`, while existing resident accesses preserve any newer shared recency. This avoids revisiting the full prefix after every store batch. Cache reset invalidates provisional state. Chunks remain evictable and finalization still commits recency.

Custom `CachePolicy` implementations must accept the additional `req_context` insertion argument; policies that do not use it can ignore it. The custom-policy guide and ARC implementation reflect that interface. ARC frequency promotion remains at finalization.

The fix is distinct from optional in-flight pin protection (#57813), session-aware policies (#50422), GPU-local reuse recording (#57746) and KVCR recency changes (#60469); those target different policies or access sources. This revision addresses the existing review request on #61050.

Thanks for picking this up. I ran it on the Qwen/DFlash workload from my #58804 comment, which the description lists as unmeasured: it brings back the second-turn reuse that 0.31.0 loses there, with no chunk 0 evicted.

Setup: a native RTX 3090, Qwen3.8-27B W4A16 (GDN + attention, DFlash drafter, 9 KV-cache groups), vLLM 0.31.0 with an out-of-tree patch series (on the offload path it only adds a boot-time warning and a device-pointer translation that adds 0 on native Linux), `--kv-offloading-size 8`, two ~60K-token conversations in flight at once, then each conversation's second turn. The PR cherry-picks onto 0.31.0 without conflicts (the series leaves those three files as upstream ships them). One boot per row:

| | turn 2 cached | read back from CPU |
|---|---|---|
| 0.30.0 | 57,664 and 57,664 (96.3%) | 2.16 GB |
| 0.31.0 | 0 and 0 | 0 |
| 0.31.0 + this PR | 50,880 of 59,718 (85.2%) and 49,184 of 59,887 (82.1%) | 1.90 GB |

With the PR the tier evicts 120 chunks, tail-first within each request, none of them a chunk 0; on 0.31.0 the first victims are chunk 0 of all nine groups.

I had also tried re-ranking a running request's whole observed prefix after each of its store batches. On this workload that gives the same counts to the token and the same victims, so your cheaper bookkeeping costs nothing in hits here. This workload does not exercise the cross-request order, though: at each eviction burst only one request had evictable chunks, so the shared provisional rank had nothing to choose between. That reading comes from the victim list, not from a run built to test it.

Unit, on the same 0.31.0 tree, CPU only: `tests/v1/kv_offload/cpu/test_manager.py` and `tests/v1/kv_offload/cpu/policies` give 73 passed with the PR, including a test of mine that stores a positioned four-chunk prefix in two batches and expects the tail to go first. Without the PR, those 12 fail (your 11 and mine).

Still unproven: one boot per row and one workload. The rest of the gap to 0.30.0 is tail chunks of every group, attention groups included; for a hybrid model a windowed group's chunks inside the hit would be better victims, but that needs each group's window, so it is a separate change.

This was measured and written with AI assistance (Claude); every number above comes from our own runs.
