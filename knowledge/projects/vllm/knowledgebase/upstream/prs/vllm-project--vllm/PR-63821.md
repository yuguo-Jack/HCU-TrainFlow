# [ROCm][Perf][DSv4.1] TP1 MXFP8 GEMM tiles and a pre-quantized wo_b input for DEP8 on MI355X

[Upstream PR](https://github.com/vllm-project/vllm/pull/63821) · state: open · merged: False

## Original PR description



## Overview

Speeds up DeepSeek-V4.1-Flash at TP1 (data-parallel attention, e.g. DP8/EP8) on MI355X with three changes:
- **Block32 tiles:** TP1 entries in `rocm_block32_gemm._TUNED` for `wo_b`, `wq_b` and the shared expert's `gate_up` and `down`.
- **`wo_a` tiles:** 8-group tiers for the `wo_a` BMM.
- **Pre-quantized `wo_b` input:** the `wo_a` BMM hands `wo_b` its MXFP8 input from the epilogue, instead of a bf16 tensor that `wo_b` quantizes in a separate launch.

Related open PRs:
- **#62533** (@karverma-amd, closed) added TP1 tables for three of the same shapes: `(4608, 5120)`, `(5120, 8192)` and `(32768, 1280)`. This PR also covers the shared expert's `down`, `(5120, 2304)`, and sweeps every CUDA graph size. Its `wo_b` tiers are faster at the decode sizes (Details).
- **#63179** (merged) and **#59782** quantize the activation inside the block32 GEMM at tiny M; #63179 does it up to M = 8, on packed tiles. Here the quant moves into `wo_b`'s producer instead, only where the `wo_a` tile is at least 32 columns wide (T·G > 128, so at least 17 tokens with 8 groups). Below that, `wo_b` quantizes the bf16 `wo_a` output through `rocm_mxfp8_block32_gemm_quant`, as its linear does on main, so #63179's fused quant still applies at tiny batches.
- **#64459** (@zovonoir) tunes the same four TP1 shapes up to M = 512. Side by side on main's block32 code (one MI355X, median of three rounds; speedup over main, geometric mean over each range, lowest to highest of the four shapes):

  | tokens | this PR | #64459 |
  |---|---|---|
  | 1–32 | 1.00–1.08× | 1.01–2.01× |
  | 48–512 | 1.20–1.69× | 1.21–1.80× |
  | 640–4096 | 1.08–1.19× | 0.99–1.00× |

  #64459 is faster at small batches, where this PR keeps the default packed tiles, and this PR past 512 tokens, where #64459 keeps the default. Both PRs add these four keys, so whichever lands second has to drop its copies.

## Claims

- **End to end**, DeepSeek-V4.1-Flash on 8× MI355X (DP8 attention, EP8 MoRI, DSpark K6), agentic workload at 256 concurrent conversations:
  - median TPOT 7.14 and 7.11 ms over two runs, against 7.34–7.39 over three baseline runs;
  - 17,557 output tok/s (one run), against 16,809–17,238;
  - 91.12 tok/s per user (one run), against 87.2–88.8.
- **Per layer on one MI355X** (HIP graphs, weights cold in the LLC):
  - `o_proj` (`wo_a` + `wo_b`): 67.0 → 56.5 µs at 224 tokens per rank, and 111–126 → 62–66 µs at 288–384;
  - `wq_b` + shared `gate_up` + `down`: 68.3 → 53.5 µs at 224, and 106.4 → 65.4 µs at 288.
- **No numerical change from the hand-off.** It is bit-identical to `mxfp8_e4m3_quantize` of the bf16 `wo_a` output. The new tiles only reorder fp32 accumulation; the relative error against an fp32 reference is unchanged at 1.7e-3.

## Validation

Unit tests on MI355X, in the upstream ROCm nightly `vllm/vllm-openai-rocm:nightly-rocm100-3966924d`, with the modules these tests exercise taken from this branch (merged with main at 55b677b2d, so #63179 included):

```
166 passed, 249 deselected

240 passed
```

The second run includes the block32 reference test on the four TP1 shapes at 1 and 7 tokens, where #63179's fused quant now runs on this PR's packed tiles.

- **`test_rocm_mxfp8_wo_a_bmm`:** new 8-group cases at 300, 700, 1100 and 1600 tokens, plus 1600 tokens with `o_lora_rank=256` for the 256-wide tile, all against an fp32 reference.
- **`test_rocm_mxfp8_wo_a_bmm_mxfp8_matches_quantized_bmm` (new):** the fused values and scales are bit-identical to `mxfp8_e4m3_quantize(rocm_mxfp8_wo_a_bmm(...))` on each of the nine fused-epilogue tiles. This also covers the narrow-tile fallback and both weight-scale layouts.
- **`test_wo_b_takes_wo_a_mxfp8_gate` (new):** `wo_b` takes the fused input only from `RocmDotScaledMxfp8LinearKernel` on an e4m3 weight with 32×32 block scales. A different kernel class with the same weight layout, per-row scales, a bf16 weight, a bias, a TP reduce and a preshuffled scale all fall back.
- **`test_rocm_mxfp8_wo_a_bmm_o_proj_matches_wo_b_linear` (new):** on both sides of T·G = 128, at G = 8 and 4, the `o_proj` op takes `wo_a`'s MXFP8 epilogue only where the tile can quantize, and `rocm_mxfp8_block32_gemm_quant` below that. Its output is bit-identical to `wo_b`'s linear on the bf16 `wo_a` output.
- **`test_rocm_mxfp8_linear_block32_matches_dequant_reference`:** the four TP1 shapes were added, and the sweep now also runs 96, 300 and 2100 tokens.

Per kernel, on one MI355X (HIP-graph replay, weights cold in the LLC; error is the max relative error against a dequantized reference): every new tile is faster than or equal to main at every size except `wo_b` at 1024 tokens (0.99×), and the error is unchanged at 1.7e-3 everywhere.

## Details

- **Why:** `_TUNED` only has TP2/TP4 entries. At TP1, these four shapes fall back to `_default_config`, which switches to a 128×128×128 tile past M = 256. For example, `wo_b` goes from 36.0 µs at 256 tokens to 72.8 µs at 288.
- **Sweep:** for each shape, every CUDA graph size from 48 to 4096. The first pass varies tile, split-K (a second launch or in-launch) and warps. The second refines the best tiles over `n_first`, `matrix_instr_nonkdim`, `waves_per_eu` and stages. All timings use graph replay, with weights rotated over 2× the LLC. Neighbouring sizes share a tier only when one config is within 2% of each size's best and never slower than the current tier. M ≤ 32 keeps `_default_config`'s packed tiles, since those sizes weren't swept.
- **Against #62533:** for `wo_b` at the per-rank decode sizes of DP8 c256 (224–512 tokens), these tiers measure 31–49 µs, against 34–56 µs for #62533's.
- **`wo_a` BMM:** the 8-group tiers past 256 tokens are 1.06–1.25× faster at 288–512 tokens and 1.1–1.2× faster past 1536. The 256-wide tile is only taken when `o_lora_rank % 256 == 0`. `_mxfp8_wo_a_bmm_config` now also returns the compiler hints each tile was tuned with.
- **Hand-off:** with `QUANT_OUT`, `_mxfp8_wo_a_bmm_kernel`'s epilogue rounds the fp32 tile to bf16, then applies the per-32-column E8M0 quant of `_mxfp8_e4m3_quantize_triton`. That gives identical bits and saves the quant launch plus a bf16 round trip: 2.3–19 µs per layer from 48 to 4096 tokens. The new opaque op `rocm_dsv41_mxfp8_wo_a_bmm_mxfp8` returns `(values, scales)`.
- **When `_o_proj` uses it:** only when `wo_b`'s linear would run exactly `rocm_mxfp8_block32_gemm` on `mxfp8_e4m3_quantize(x)`. That means `RocmDotScaledMxfp8LinearKernel` as `wo_b`'s kernel (as `can_fuse_query_quant` checks its consumer), an e4m3 weight with 32×32 block scales, no bias and no TP reduce. It isn't used with a preshuffled FP8 `wo_b`, with per-row scales (e.g. `VLLM_BATCH_INVARIANT`), or with a row-parallel reduce at TP > 1. `wo_a` and `wo_b` then run as one opaque op, `rocm_dsv41_mxfp8_o_proj`: it takes the hand-off where the `wo_a` tile is at least one MX block wide (T·G > 128) and otherwise feeds the bf16 `wo_a` output to `wo_b`'s `rocm_mxfp8_block32_gemm_quant`. The branch is inside the op, so the compiled `o_proj` does not freeze the token count.
- **Scope:** tuned and measured on MI355X (gfx950) only. The TP2/TP4 tables and the 2- and 4-group `wo_a` tiers are unchanged. No new CPU-GPU syncs, env vars or user-visible behavior. The `wo_a` and gate tests run in ":amd: (MI355 DPX) MLA Kernels" (added to its AMD mirror here), and the block32 sweep in the MXFP8 linear step.

AI assistance (a coding agent) was used to run the sweeps, write the change and tests, and draft this description. The submitter reviewed every changed line before marking this ready for review.
