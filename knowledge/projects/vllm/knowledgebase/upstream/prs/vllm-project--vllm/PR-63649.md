# [Bugfix][Rust Frontend] Reject max_tokens greater than max_model_len in OpenAI routes like Python

[Upstream PR](https://github.com/vllm-project/vllm/pull/63649) · state: closed · merged: False

## Original PR description



## Overview

The Rust frontend accepts `max_tokens` greater than `max_model_len` on the OpenAI chat and completions routes and silently clamps it, returning 200. The Python frontend rejects these requests with 400. This PR adds the check to those two routes only, so other routes keep matching Python.

## Claims

- `POST /v1/chat/completions` and `POST /v1/completions` with `max_tokens > max_model_len` return 400 `BadRequestError` with Python's message: `<param>=<n> cannot be greater than max_model_len=<m>. Please request fewer output tokens.`
- `/inference/v1/generate` and gRPC generate are unchanged and still accept such requests, as Python does.
- Ordering matches Python: an unknown model still returns 404 first, and the check runs before the prompt-length check.
- `max_tokens <= max_model_len` is unchanged (still clamped to the remaining context).

## Validation

**Behavior before the fix** (`vllm/vllm-openai:latest` v0.32.0 for Python; the Rust behavior is unchanged on current `main`):

| Route | Python | Rust |
|---|---|---|
| `/v1/chat/completions` | 400 `max_tokens=100000 cannot be greater than max_model_len=8192. Please request fewer output tokens.` | 200, clamped |
| `/v1/completions` | 400 | 200, clamped |
| `/inference/v1/generate` (`--enable-scale-out`) | **200**, generation starts (see below) | 200, clamped |

```bash
curl -sN localhost:8000/inference/v1/generate -H 'Content-Type: application/json' \
  -d '{"token_ids":[9707,1879],"sampling_params":{"max_tokens":100000},"stream":true}'
# data: {"request_id":"generate-tokens-...","output_mode":"tokens","choices":[{"index":0,"finish_reason":null,...,"token_ids":[54851],...}]}
```

**Regression tests** (`rust/src/server/src/routes/tests.rs`), each confirmed to fail on the broken variant:

| Test | What it guards | Fails when |
|---|---|---|
| `chat_completions_max_tokens_above_max_model_len_returns_400` | chat check | the check is removed (`left: 200, right: 400`) |
| `completions_max_tokens_above_max_model_len_returns_400` | completions check | the check is removed (`left: 200, right: 400`) |
| `chat_completions_max_tokens_equal_max_model_len_returns_200` | the boundary (`>`, not `>=` or "any value") | the comparison is dropped (`left: 400, right: 200`) |
| `inference_generate_accepts_max_tokens_above_max_model_len` | the check stays out of the shared `vllm-text` path | the check is moved into `vllm_text::resolve_max_tokens` (`left: 400, right: 200`) |

The tests send `DEFAULT_MOCK_MAX_MODEL_LEN` (± 1), so they track the mock engine's limit. Error mapping is validated with in-process route tests against the mock engine, as described in the Validation section of `rust/AGENTS.md`.

## Details

**Root cause.** In Python, each request type builds its own `TokenizeParams` via `build_tok_params`, and `TokenizeParams` validation (`vllm/renderers/params.py`) rejects `max_output_tokens > max_total_tokens`. The OpenAI chat and completions requests pass the user's value; the token-in-token-out generate request passes `max_output_tokens=0`, so it is never checked, and the engine's input processor does not reject it either. The Rust frontend never ported the check for the OpenAI routes.

**Why the OpenAI routes, not `vllm-text`.** I first put the check in `vllm_text::resolve_max_tokens`, next to the existing `truncate_prompt_tokens` check. But `lower_text_request` is shared with `/inference/v1/generate` and gRPC generate, so that version also rejected requests Python accepts (the last test above fails on it). `truncate_prompt_tokens` doesn't have this problem because only OpenAI requests carry it. In Python the rule belongs to the OpenAI request types, so here it lives in the two OpenAI handlers. The duplication across the two handlers mirrors Python's two `build_tok_params` implementations.

**Placement.** The check runs after `prepare_chat_request` / `prepare_completion_request`, so an unknown model still returns 404 first, and before the request is submitted, so it precedes the prompt-length check in `vllm-text`. `max_model_len` comes from `state.chat.engine_core_client().max_model_len()`, as in `/tokenize`.

**Deviation from Python (parameter name).** For chat requests that use the deprecated `max_tokens`, Python names `max_tokens` in the message and `param`; here they say `max_completion_tokens`. `ChatCompletionRequest::normalize` (run by `ValidatedJson` before the handler) moves `max_tokens` into `max_completion_tokens` and clears it, so the handler cannot tell which name the client used. Requests that use `max_completion_tokens`, and all completions requests, match Python exactly.

**Alternative for exact parity.** `normalize` could record the original name in a `#[serde(skip)]` field on `ChatCompletionRequest`, and the handler would report it. That makes the message match Python in every case, at the cost of an extra field on the request DTO and updating places that construct it. Happy to add it if preferred.

**Not a duplicate.** I found no open issue or PR for this (searched for Rust frontend `max_tokens` / `max_model_len`).
