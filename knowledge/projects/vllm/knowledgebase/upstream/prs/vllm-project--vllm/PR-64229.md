# [Bugfix][KV Offload] Count bounded-replay SWA allocations in the lazy walk target

[Upstream PR](https://github.com/vllm-project/vllm/pull/64229) · state: closed · merged: True

## Original PR description



## Overview

In lazy mode, SimpleCPUOffload does not offload blocks when requests free them. Each step it walks the GPU free queue from the eviction end and offloads the cached blocks it passes, so a block is already on CPU by the time the allocator reuses it. This only works if the walk length (`_target_free`, from `_estimate_lazy_target_blocks`) covers every block one step can take from the free queue.

`_estimate_lazy_target_blocks` only iterates over `prefix_cacheable_groups`. DeepSeek-V4.1's bounded-replay SWA groups (`SlidingWindowSpec(bounded_replay=True)`) are not prefix-cacheable: on a prefix hit their state is rebuilt by replaying the window, so they are never offloaded. They still allocate blocks for every scheduled token from the same GPU free queue, up to `cdiv(max_num_batched_tokens, block_size)` per group per step, just like full attention. Since they are left out of the target, the walk covers less than one step allocates. Cached prefix blocks just past the walk go to the SWA groups and are overwritten before they are offloaded, so their CPU copy never exists and later requests miss the CPU cache.

This PR counts non-cacheable `SlidingWindowSpec` groups in the target at `cdiv(max_num_batched_tokens, block_size)`. It complements #59383, which fixes where offloaded blocks are returned in the free queue; this PR fixes how far the walk goes.

## Claims

- In lazy mode, one walk covers the blocks every group can allocate in the next step, including bounded-replay SWA groups.
- No change for models without non-cacheable SWA groups, or for eager mode.

## Validation

- New `test_lazy_walk_covers_bounded_replay_swa_groups` fails on main (the walk stores 8 of the 12 blocks the next step can take) and passes with this PR.
- `pytest tests/v1/simple_kv_offload/`: 165 passed, 8 skipped.
- Step simulation on the scheduler (walk, store completes, allocator takes one step's blocks from the free-queue head; 128 cached blocks; `max_num_batched_tokens=64`, block size 16). Cached blocks reallocated before being offloaded:

| | FA only | FA + 3 bounded-replay SWA groups |
|---|---|---|
| main | 120 / 128 | 120 / 128 |
| #59383 | 0 / 128 | 64 / 128 |
| #59383 + this PR | 0 / 128 | 0 / 128 |

No E2E run. The scheduler-level simulation reproduces the issue directly.

## Details

- Not a duplicate: #59383 returns lazily offloaded blocks to the eviction end of the free queue; it does not change the walk length. On main, #59383's issue dominates, so this PR shows its full effect on top of #59383. The two are independent and can merge in either order.
- Only non-cacheable `SlidingWindowSpec` groups are counted, at `cdiv(max_num_batched_tokens, block_size)` like full attention. Other non-cacheable specs (`CircularBufferSpec`, `HiSparseHotSpec`) hold a fixed number of blocks per request and stay excluded.
- Tradeoff: with bounded replay on, the target grows, so each walk may offload more blocks per step. That is what the allocator consumes anyway.
