# [Perf][Frontend] Add bounded segment tokenizer cache to HF renderers

[Upstream PR](https://github.com/vllm-project/vllm/pull/61335) · state: open · merged: False

## Original PR description

## Purpose

Add an opt-in CPU segment tokenization cache to the HF renderer's chat and completion request paths. Repeated conversation turns can reuse token IDs while preserving the normal HF encoding result.

`--tokenizer-cache-gb` defaults to `0`. A positive value supplies a separate byte budget per renderer/API process. Exact text keys, immutable cached token tuples, and LRU eviction bound retained cache state. Tokenization runs outside the cache lock.

This change targets renderer request execution through the existing tokenizer interface. The configured tokenizer mode is preserved, and cache state and the retained-byte budget belong to each renderer. Supported default HF ByteLevel BPE methods use added-token boundaries; custom encoding methods, unsupported normalization, offsets, tensors, and other unsupported options retain regular encoding. Model-runner and KV-cache behavior are unchanged.

Current head: `45a0e62f241dffeefdb701c4c1c60b874c1be373`; base: `df6c7ad03194a3051a197d57ca4a94e4a063014e`.

### Compatibility-backport serving validation

The Ascend-compatible backport at [b37f01391ec3b0c028ab6947e4ea3b6f7846504d](https://github.com/Liuchenbing-2026/vllm/commit/b37f01391ec3b0c028ab6947e4ea3b6f7846504d), based on `f408c863ad572024a292e8fcb2abf7ccddcfe8be`, contains the strict standard-HF-method guard. Its segment-cache module is byte-identical to this PR head. The compatibility regression passed 112 CPU tests, including the custom-encoding counterexample; local checks passed. This is a separate runtime version, not full serving of `45a0e62f`.

Fresh native HTTP measurements used the same real Qwen3-8B, one Ascend 910B4, BF16/eager TP1/DP1, 128,000 input tokens, client concurrency 32, one output token, and the same 8-CPU/32-GiB frontend allocation. Each OFF/ON mode completed three windows of 32 requests. All 384 measured requests succeeded; 256 complete HF render checks passed, and returned OFF/ON output text matched. Eight warmup requests were excluded from timing. This output comparison does not establish generated-token-ID equality or task accuracy.

| 1 | 1.673 → 5.808 | +247.23% | 9.995 → 4.362 s |
| 8 | 5.249 → 5.275 | Basically unchanged (+0.49%) | 4.505 → 4.626 s |

Eight-thread median latency regressed 2.70%. Formal ON windows recorded 1,164 cache hits / 1,164 eligible segment lookups; OFF had no cache object. Both modes recorded the same 12,275,712 KV prefix-hit tokens / 12,288,000 queried tokens. The benefit is observed with warmed CPU and device caches; cold KV was not rerun on this backport.

The fresh runtime used the recorded v0.30.0 image and prebuilt `0.30.0+empty` package, with an isolated package copy and fingerprinted task Python files; it was not a rebuilt full wheel. The source path was prepended while retaining the image's CANN Python paths. The paired Ascend wheel remained `0.1.dev1+g4ea839b81`, with its older tokenizer-cache budget zero. Attempting full current-main Python serving with that plugin failed before model startup because the plugin imports the unavailable private `_approximate_gcd` symbol. Current-head full CUDA/NPU serving remains unvalidated; this result establishes the cache behavior in the stated compatibility composition.

### Historical end-to-end measurements

Qwen3-8B real weights; one Ascend 910B4; BF16/eager, TP1/DP1; **128,000 input tokens, client concurrency 32, one output token**; 8 frontend CPUs/32 GiB RAM; a 1 GiB CPU cache versus zero. Device prefix caching remained enabled in both modes. Each hot mode used three windows of 32 requests, with CPU/KV warmups outside timing. Cold-KV modes used one window of 32 requests each and a warmed CPU cache.

| Device KV / renderer threads | Cache OFF → ON, requests/s | Throughput change | Median end-to-end latency OFF → ON |
|---|---:|---:|---:|
| Warm / 1 | 1.988 → 5.475 | +175.33% | 8.431 → 5.162 s |
| Warm / 8 | 5.334 → 5.474 | +2.61% | 4.705 → 4.925 s |
| Cold / 1 | 0.016162 → 0.016192 | Basically unchanged | 1,019.956 → 1,018.613 s |

The hot one-thread window throughput ranged from 1.731–2.157 requests/s OFF and 5.251–5.655 ON. The eight-thread ranges were 5.063–5.523 OFF and 5.296–5.617 ON. Aggregate throughput is total successful requests divided by summed window wall time.

Eight-thread median latency regressed 4.68%; the single cold-KV sample does not establish a speedup. Client concurrency 32 does not imply 32 fully resident 128K contexts. The benefit is workload-dependent, and retained cache bytes do not cap total frontend RSS or temporary encoding buffers. One-token output equality is not a task-quality benchmark; CUDA and current-head full NPU serving have not been rerun.
