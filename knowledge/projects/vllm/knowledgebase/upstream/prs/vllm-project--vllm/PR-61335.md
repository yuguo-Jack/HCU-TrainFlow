# [Perf][Frontend] Add bounded segment tokenizer cache to HF renderers

[Upstream PR](https://github.com/vllm-project/vllm/pull/61335) · state: open · merged: False

## Original PR description

## Purpose

Add an opt-in, bounded CPU segment tokenization cache to HF renderer chat and completion paths. `--tokenizer-cache-gb` defaults to zero and sets a separate byte budget per renderer/API process. Exact text keys and immutable cached token tuples avoid hash collisions and caller mutation; LRU eviction bounds retained state.

Eligible standard HF ByteLevel BPE tokenizers can reuse added-token-delimited segments. Supported NFC normalization and empty normalizer sequences are handled explicitly. Unsupported encoding overrides, normalization, offsets and chat options retain regular encoding. Template-only overrides can use the cache only after the rendered text and normal chat token IDs agree. Device KV-cache and model-runner execution are unchanged.

Source: `8ed45c8853e05a9bb35aa4a43fe80d8c4d6f0ff0`; synchronized main: `7a64fb8fc9239cb65e0df9313fa759594dfb206a`.

## Compatibility changes

- Keep the DeepSeek V4 `(prompt, image_order)` result contract on both cached and regular paths. Preserve the V4.1 implementation and image-order processing.
- Pass the cache argument to the asynchronous HF embedding-visibility callback, including when the cache is disabled.
- Extend the existing tokenizer test file with real renderer construction, cache OFF/ON, sync/async rendering, and exact sync/async embedding comparisons. Existing Buildkite selection collects this file.

### Historical end-to-end measurements

Qwen3-8B real weights; one Ascend 910B4; BF16/eager, TP1/DP1; **128,000 input tokens, client concurrency 32, one output token**; 8 frontend CPUs/32 GiB RAM; a 1 GiB CPU cache versus zero. Device prefix caching remained enabled in both modes. Each hot mode used three windows of 32 requests, with CPU/KV warmups outside timing. Cold-KV modes used one window of 32 requests each and a warmed CPU cache.

| Device KV / renderer threads | Cache OFF → ON, requests/s | Throughput change | Median end-to-end latency OFF → ON |
|---|---:|---:|---:|
| Warm / 1 | 1.988 → 5.475 | +175.33% | 8.431 → 5.162 s |
| Warm / 8 | 5.334 → 5.474 | +2.61% | 4.705 → 4.925 s |
| Cold / 1 | 0.016162 → 0.016192 | Basically unchanged | 1,019.956 → 1,018.613 s |

The hot one-thread window throughput ranged from 1.731–2.157 requests/s OFF and 5.251–5.655 ON. The eight-thread ranges were 5.063–5.523 OFF and 5.296–5.617 ON. Aggregate throughput is total successful requests divided by summed window wall time.

Eight-thread median latency regressed 4.68%; the single cold-KV sample does not establish a speedup. Client concurrency 32 does not imply 32 fully resident 128K contexts. The benefit is workload-dependent, and retained cache bytes do not cap total frontend RSS or temporary encoding buffers. One-token output equality is not a task-quality benchmark; CUDA and current-head full NPU serving have not been rerun.

- alexbi29 · comment · 2026-10-21T00:42:56Z · [source](https://github.com/vllm-project/vllm/pull/61335#issuecomment-6305116632)

Thanks for this. We hit the same cost on long agentic Gemma 4 chats. The current gate disables the cache for Gemma 4, although segmented encoding is exact there.

Gemma 4 fails two structural checks:

- its normalizer is `Replace(" " -> "▁")`, not None/NFC
- its pre-tokenizer is `Split(" ")` with no ByteLevel

Its added tokens are all `normalized=False` with no lstrip/rstrip/single_word, and nothing is prepended only at the start of the input. Pieces between added tokens therefore encode independently, and your probe self-test passes on this tokenizer.

On real traffic, we replayed 4,115 multi-turn Gemma-4-26B-A4B requests through an equivalent segment cache, rendered with the served chat template. All 4,115 matched the full encode. Median tokenization of 50K+-token prompts went from 59.9 ms to 7.6 ms.

Suggestions:

1. Also accept a per-character `Replace` normalizer and Split-only pre-tokenizers, keeping the probe self-test as the final check.
2. Optionally, re-check about 1 in 1024 cache-served encodes against a full encode and disable the cache on mismatch.

Happy to send (1) as a follow-up PR with a Gemma-style test tokenizer, or you can fold it in here.
