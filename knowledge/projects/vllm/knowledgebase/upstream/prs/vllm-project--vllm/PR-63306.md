# [Perf][Core] Freeze GC after scheduling new requests

[Upstream PR](https://github.com/vllm-project/vllm/pull/63306) · state: closed · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Call `gc.freeze()` in `EngineCore` after a scheduling step that admits new requests, follows a request's arrival, or runs while requests wait. The last two cover P/D decode, where a new request gets its KV blocks while it waits for remote KV, steps before it is scheduled. Without it, each full (gen-2) GC pass traverses every live request's token lists and KV block lists. With long contexts and DP, this stalls every DP rank for tens of milliseconds several times a minute. Related: #62086, which tunes GC thresholds after the startup freeze; the two changes are complementary.

## Claims

- Removes the EngineCore gen-2 GC pauses for long-context serving: ≥10 ms pauses drop from ~13/min per rank to 1–2 per rank over the whole ~4-minute run (max 10.7 ms), and the 38–57 ms gen-2 passes are gone.
- DeepSeek-V4.1-Flash decode on GB300 DEP4 (129K-token prompts, 256 requests/rank, DSpark speculative decoding with 5 tokens): decode step 28.86 → 28.38 ms (−1.7%), +1.7% output tokens/s.
- P/D decode with NIXL (pull and push): with 256 long requests waiting for remote KV, a full GC pass takes 39–47 ms when freezing only on `scheduled_new_reqs`, and 0.0 ms with this PR, including when the requests are admitted over several steps (CPU reproducer below).
- No leak found: over a 1,920-request P/D lifecycle the frozen object count stays flat and `gc.unfreeze()` + `gc.collect()` at the end finds 0 unreachable objects.
- Negligible per-step cost: `gc.freeze()` is O(1) and runs only on steps that admit requests, follow an arrival, or run while requests wait.

## Details

**Root cause**
- `EngineCore` freezes its startup heap (`freeze_gc_heap`), but every object created while serving stays visible to the cyclic GC.
- Each admitted request keeps, for its whole lifetime:
  - its prompt and all-token lists, with one reference per token;
  - per KV cache group, a `req_to_blocks` list with one entry per block, including `null_block` placeholders for skipped sliding-window blocks.
- A gen-2 pass walks every element of these lists, even though they never form cycles.
- Hybrid models with many KV groups multiply the second item. DeepSeek-V4.1-Flash has 10 KV cache groups with block sizes 32×8, 128 and 8, giving ~51K block references per 133K-token request, or ~13M for 256 requests.
- The serving log shows gen-2 passes over only ~7.7K objects taking 38–57 ms, every ~5 s per rank. They are all in the EngineCore process; worker GC passes stay under 5 ms.

**Why it matters with DP**
- Each DP rank's EngineCore collects independently.
- Every step ends in a DP all-reduce (`sync_cudagraph_and_dp_padding`), so a pause on one rank stalls all ranks.
- The profile shows ~20 ms GPU-idle gaps, each with a different late rank. The cost grows with the number of DP ranks.

**Why freeze, and why there**
- `gc.freeze()` moves all tracked objects to the permanent generation. Later full passes skip them, and appending to a frozen list doesn't make it visible again.
- Calling it right after `schedule()` catches the request objects and the KV block lists, which are allocated inside `schedule()`. Freezing in `add_request` would miss the block lists.
- It is gated on `scheduled_new_reqs` so steady decode steps don't call it.
- P/D decode: with a KV connector, `schedule()` allocates the blocks of a new remote-prefill request and moves it to `WAITING_FOR_REMOTE_KVS` without scheduling it, for both NIXL pull and push. It only appears in `scheduled_new_reqs` once its KV has arrived; in push mode that includes the prefill time. When admissions are limited (block budget, or a cap on new async KV loads per step), later requests get their blocks in later steps.
- So `add_request` sets a flag, and `_schedule()` freezes after every `schedule()` that follows an arrival or runs while any request waits (`SchedulerInterface.get_request_counts()`, already used by `EngineCore`). With nothing waiting, as in steady decode, nothing changes.

**Trade-off**
- Any cyclic garbage created before a freeze is never collected; reference-counted objects are still freed normally.
- In the run above, EngineCore's GC found 0 unreachable objects in ~26K collections (gen 0/1/2 combined), so in practice there is nothing to leak. RSS was flat over the run (see the table).
- A workload that creates cyclic garbage in the engine loop would leak it slowly. `VLLM_GC_DEBUG=1` shows whether collections ever find garbage.
