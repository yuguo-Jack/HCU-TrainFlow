# [ROCm][Perf] Kimi-K3: token-sharded residual stream for long prefills

[Upstream PR](https://github.com/vllm-project/vllm/pull/59693) · state: open · merged: False

## Original PR description

### Purpose

**Scope: ROCm only, Kimi-K3 only, opt-in.** All model changes are in
`vllm/models/kimi_k3/amd/`, which is only loaded on ROCm, and the new path only
runs for Kimi-K3's attention-residual layers. It is off by default
(`VLLM_KIMI_K3_AMD_PREFILL_SP_MIN_TOKENS=0`). NVIDIA, other models and
CUDA-graph decode are unaffected.

With TP, every rank repeats the same per-token work (attention-residual mixing,
MoE router, latent down-projection, top-k) on all tokens. For eager steps with
at least `VLLM_KIMI_K3_AMD_PREFILL_SP_MIN_TOKENS` tokens (1024 recommended),
this PR shards the residual stream over tokens instead, padded to a multiple of
TP:

- Each block output all-reduce becomes a reduce-scatter plus an all-gather
before the next block. For attention and dense MLP blocks the communication
volume is unchanged. Latent-MoE layers also all-gather the latent and the
top-k, about 17% more bytes per MoE layer at K3's sizes; the measured numbers
below include this.
- Attention-residual mixing, the router and top-k run on the local shard only.
- The latent-MoE tail reduce-scatters its output over tokens instead of
all-reducing it.

It is off with PP, with DP > 1, during graph capture and specialized-decode
steps, when aux hidden states
are requested (EAGLE drafters), and with `--enable-return-routed-experts` or
EPLB, since routing would only see this rank's token shard.

The NVIDIA Kimi-K3 path has something similar (`use_sequence_parallel` in
`nvidia/model.py`), but it only turns on with expert parallelism plus DP > 1
or DeepGEMM MegaMoE, for every step. This PR covers plain TP on ROCm, and only
for long prefill steps.

### Test Plan

- New `tests/models/kimi_k3/test_amd_prefill_sp.py`:
  - The MoE tail, regular and token-sharded, matches the replicated result at
    TP4/TP8 for both the `ColumnParallelLinear` and replicated up-projection
    layouts.
  - The decoder layer's sharded MLP step matches the unsharded rows at TP4 for
    a dense `KimiMLP`, a shard-routed latent `KimiMoE`, and a latent `KimiMoE`
    that takes the all-gather fallback, with a token count that does not divide
    TP.
  - The routing all-gather and the gather of pre-quantized FP8 activations
    (data plus per-token scale) are bit-exact, padded gather/scatter
    round-trips at TP4/TP8, and the enable conditions are covered.
- With the existing Kimi-K3 AMD runner, KDA/MLA direct-return and sequence
parallel tests: 78 passed on `vllm/vllm-openai-rocm:nightly` (vllm 5555a2d8f).
After merging main, with the attention-residual tests added, 94 pass on the
merged tree.
- gfx942, same image: the unit tests above pass on 8x MI300X (78). On 8x
MI325X, the full Kimi-K3 MXFP4 checkpoint at TP8 matches stock on GSM8K 5/20-shot
and passkey, with the same first-token top-1 on 20/20 prompts up to 190K tokens,
and cuts TTFT by 5-9% (MoE runs through the `EMULATION` MXFP4 backend there, so
absolute numbers are not representative).
- End to end: 8x MI355X, Kimi-K3 MXFP4, TP8. Both arms use the same
`vllm/vllm-openai-rocm:nightly` image (vllm 5555a2d8f); the PR arm applies
this PR's diff to the image's vllm and sets the flag. The agentic TP8 + DCP8
config (prefix caching, CPU KV offload, 24576 batched tokens) also serves
160/160 requests with and without the flag.

Serve (the PR arm adds `-e VLLM_KIMI_K3_AMD_PREFILL_SP_MIN_TOKENS=1024`):

```bash
docker run --rm --device=/dev/kfd --device=/dev/dri --group-add video --group-add render \
  --security-opt seccomp=unconfined --ipc=host --shm-size=128g --network host \
  -e HSA_NO_SCRATCH_RECLAIM=1 -e HIP_FORCE_DEV_KERNARG=1 -e SAFETENSORS_FAST_GPU=1 \
  -e VLLM_ROCM_USE_AITER=1 -e VLLM_ROCM_USE_AITER_MOE=1 \
  vllm/vllm-openai-rocm:nightly \
  vllm serve <Kimi-K3> --served-model-name k3 --trust-remote-code \
    --tensor-parallel-size 8 --max-model-len 204800 --max-num-seqs 32 \
    --gpu-memory-utilization 0.95 --no-enable-prefix-caching
```

Benchmark (one warmup run first; `N = max(2 * C, 4)`):

```bash
vllm bench serve --backend vllm --model <Kimi-K3> --served-model-name k3 \
  --trust-remote-code --port 8000 --dataset-name random \
  --random-input-len $ISL --random-output-len 1000 --random-range-ratio 0 \
  --max-concurrency $C --num-prompts $N --ignore-eos --seed 42 \
  --percentile-metrics ttft,tpot,itl,e2el
```

Accuracy, against `/v1/completions` with temperature 0 on the same servers:

- GSM8K: the first 400 test questions, with a k-shot prefix built from the
first k train examples as `Question: ...\nAnswer: ...\n\n`. Settings are
`max_tokens` 320 and stop on `Question:` or three newlines, and the last number
is compared with the `####` answer. 5-shot prompts are only about 550 tokens,
so they are sent in synchronized waves of 32 to put every prefill step above
the threshold. 20-shot prompts (over 2K tokens) are sent at concurrency 32.
Each is run 3 times per arm.
- Passkey: a 5-digit key in filler text at depths 0.1/0.5/0.9 of
8K/50K/100K/190K-token prompts (12 cases, 12 output tokens), plus 20 cases at
depths 0.1-0.9 (48 output tokens).
- First-token top-1: 20 real-text prompts (concatenated GSM8K train Q/A, 4
offsets at each of 2K/10K/50K/100K/190K tokens), sent one at a time with
`logprobs=5`, run twice per arm.

`vllm/models/kimi_k3/amd/linear.py:696`
