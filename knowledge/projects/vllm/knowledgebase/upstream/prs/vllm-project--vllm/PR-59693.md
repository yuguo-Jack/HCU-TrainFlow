# [ROCm][Perf] Kimi-K3: token-sharded residual stream for long prefills

[Upstream PR](https://github.com/vllm-project/vllm/pull/59693) · state: open · merged: False

## Original PR description

### Purpose

**Scope: ROCm only, Kimi-K3 only, opt-in.** All model changes are in
`vllm/models/kimi_k3/amd/`, which is only loaded on ROCm, and the new path only
runs for Kimi-K3's attention-residual layers. It is off by default
(`VLLM_KIMI_K3_AMD_PREFILL_SP_MIN_TOKENS=0`). NVIDIA, other models and
CUDA-graph decode are unaffected.

With TP, every rank repeats the same per-token work (attention-residual mixing,
MoE router, latent down-projection, top-k) on all tokens. For eager steps with
at least `VLLM_KIMI_K3_AMD_PREFILL_SP_MIN_TOKENS` tokens (1024 recommended),
this PR shards the residual stream over tokens instead, padded to a multiple of
TP:

- Each block output all-reduce becomes a reduce-scatter plus an all-gather
before the next block, so communication volume is unchanged.
- Attention-residual mixing, the router and top-k run on the local shard only.
- The latent-MoE tail reduce-scatters its output over tokens instead of
all-reducing it.

It is off with PP, with DP > 1, during graph capture, and when aux hidden
states are requested (EAGLE drafters).

The NVIDIA Kimi-K3 path has something similar (`use_sequence_parallel` in
`nvidia/model.py`), but it only turns on with expert parallelism plus DP > 1
or DeepGEMM MegaMoE, for every step. This PR covers plain TP on ROCm, and only
for long prefill steps.

### Test Plan

- New `tests/models/kimi_k3/test_amd_prefill_sp.py`: the MoE tail, regular and
token-sharded, matches the replicated result at TP4/TP8 for both the
`ColumnParallelLinear` and replicated up-projection layouts. The routing
all-gather and the gather of pre-quantized FP8 activations (data plus per-token
scale) are bit-exact, padded gather/scatter round-trips, and the enable
conditions are covered.
- With the existing Kimi-K3 AMD runner, KDA/MLA direct-return and sequence
parallel tests: 68 passed on `vllm/vllm-openai-rocm:nightly` (vllm 77154ca61).
- End to end: 8x MI355X, Kimi-K3 MXFP4, TP8, `vllm/vllm-openai-rocm:nightly`
with and without `VLLM_KIMI_K3_AMD_PREFILL_SP_MIN_TOKENS=1024`,
`vllm bench serve`, random data, 1K output tokens. The agentic TP8 + DCP8
config (prefix caching, CPU KV offload, 24576 batched tokens) also serves
160/160 requests with and without the flag.

### Test Result

Δ vs stock nightly (same image, 2026-10-14); throughput is (input + output)
tok/s/GPU.

| Input | Conc. | Throughput | TTFT   |
| ----- | ----- | ---------- | ------ |
| 10K   | 32    | +4.4%      | -15.1% |
| 50K   | 32    | +8.5%      | -10.4% |
| 200K  | 8     | +7.4%      | -9.5%  |

An earlier 8-point sweep of the previous revision gave a geomean of +6.1%, with
1K prompts within run-to-run noise.

Accuracy matches stock (measured on the previous revision; the sharded path now
uses the same latent all-reduce as stock): GSM8K 5-shot 0.989 vs 0.982 (mean of
3 runs), passkey retrieval up to 190K 0.95-1.00 vs 0.95, and first-token top-1
agreement 20/20 on real-text prompts from 2K to 190K.

N, K = 7168, 3584
W = torch.randn(N, K, dtype=torch.bfloat16, device="cuda") * 0.02

    A = torch.randn(M, K, dtype=torch.bfloat16, device="cuda")

This forces `reduce_results=False` for all `RowParallelLinear` modules. Even though self_attn and mlp contains only the intended o-proj and down_proj as RowParallelLinear, for readability, can we make this more targeted for the intended modules? Something like

```
@staticmethod
@contextlib.contextmanager
def _output_unreduced(proj: RowParallelLinear):
    # Row-parallel outputs stay partial so the caller can reduce-scatter.
    assert isinstance(proj, RowParallelLinear) and proj.reduce_results
    proj.reduce_results = False
    try:
        yield
    finally:
        proj.reduce_results = True
```

then call it with `self.self_attn_o_proj` and `self.mlp.down_proj`
