# fix(xpu): Add opt-in W8A16 path for XPU block FP8 to improve performance

[Upstream PR](https://github.com/vllm-project/vllm/pull/62773) · state: open · merged: False

## Original PR description

### Summary of Changes
This patch adds an opt-in W8A16 (weight 8-bit, activation 16-bit) path for XPU block FP8 operations to improve performance on Intel Arc Pro B70 GPUs. The W8A16 path uses oneDNN's `fp8_gemm_w8a16` directly on fp16 activations with checkpoint's 128x128 scales, bypassing the activation quantization step that was causing performance regression in vLLM 0.31.0.

### Motivation & Context
Closes #62762

The issue describes a performance regression where vLLM 0.31.0 was 40% slower than 0.26.0 for single-stream decode on Intel Arc Pro B70 GPUs. The root cause was that the block FP8 W8A8 path in `XPUFp8BlockScaledMMKernel` was quantizing activations to FP8 at every M dimension, whereas the 0.26.0 build used oneDNN's `fp8_gemm_w8a16` directly on fp16 activations with checkpoint's 128x128 scales.

This patch provides an opt-in W8A16 route that:
1. Skips input quantization when `XPU_BLOCK_FP8_W8A16=1` environment variable is set
2. Uses `fp8_gemm_w8a16` for fp16 activations when shape conditions are met (N and K multiples of 128, K > 128, weight group shape is 128x128)
3. Falls back to the original W8A8 path for other cases
4. Provides logging to indicate which path is being used

### Verification
This change can be verified by:
1. Setting `XPU_BLOCK_FP8_W8A16=1` environment variable
2. Running the same benchmark tests as described in the issue
3. Observing that single-stream decode performance improves from ~35 tok/s to ~57 tok/s
4. Checking that the log messages indicate which path is being used (W8A16 active, below min_m, or fallback)
