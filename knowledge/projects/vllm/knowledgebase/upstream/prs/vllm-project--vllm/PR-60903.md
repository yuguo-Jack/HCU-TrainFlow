# [Perf][Kernel][Quantization] Triton row kernel for per-token-group FP8 quant at large token counts

[Upstream PR](https://github.com/vllm-project/vllm/pull/60903) · state: open · merged: False

## Original PR description

### Purpose

`per_token_group_quant_fp8` dispatches to `torch.ops._C.per_token_group_fp8_quant`, which assigns 16 threads per group. After #56478 and #55330 this kernel is fast at small token counts, but at prefill-sized inputs it remains well below bandwidth-bound for a pure streaming op that reads each element once and writes fp8 plus one scale per group.

This PR adds a Triton kernel with one program per row: the full row is loaded in one coalesced read, reshaped in registers to `H/group_size` groups, all group scales computed at once, and the row stored in one write. It is exposed as `torch.ops.vllm.per_token_group_fp8_quant_row` with the **same signature as the `_C` op**. The token-count dispatch lives inside the opaque op, so torch.compile never traces a data-dependent branch: `T >= 2048` takes the row kernel, and smaller inputs keep the CUDA kernel, which wins there on launch cost. The `_C` kernel itself is unchanged and still handles every case the row kernel does not: UE8M0 scales, non-power-of-two hidden size, H > 8192, 3-D inputs, and non-contiguous inputs. ROCm and XPU behavior is untouched.

Because `per_token_group_quant_fp8` now emits the new op on CUDA, the fusion-pattern `QUANT_OPS` tables in `compilation/passes/fusion/matcher_utils.py` and `rms_quant_fusion.py` are pointed at it there, so RMSNorm+quant and MLA+quant pattern matching continues to fire. This is the lesson of #49621, where a Triton wrapper over this op broke pattern matching by changing op identity; this PR keeps the matchers and the emitted op in lockstep.

### Correctness

Bitwise-identical to `_C.per_token_group_fp8_quant`, bit for bit rather than approximately: fp32 absmax with the same eps floor, IEEE round-to-nearest division via `tl.math.div_rn` since plain `/` may compile to approximate division, and round-to-nearest-satfinite fp8 conversion. The included tests assert zero differing bits on quantized values and scales across token counts 1..17083, H in {2048, 4096}, all three scale layouts: row-major, column-major, and TMA-aligned, fp16 and bf16 inputs, all-zero rows for the eps floor, and inf inputs for the satfinite clamp. `torch.library.opcheck` passes for the registered op. The test_schema subcheck is skipped because torch's clone-and-compare harness calls `allclose` on the mutated fp8 output and `mul_cuda` has no fp8 kernel.

### Microbenchmark

H200, CUDA 13, torch 2.13, `group_size=128`, bf16 input, pre-allocated outputs, 300 timed iterations after warmup:

| T x H | `_C` after #55330/#56478 | this PR | speedup |
| --- | --- | --- | --- |
| 512 x 4096 | 7.9 us | n/a | dispatches to `_C` |
| 4096 x 4096 | 29.2 us | 17.8 us | 1.64x |
| 17083 x 4096 | 112.6 us | 61.5 us | 1.83x |
| 4096 x 2048 | 15.1 us | 13.1 us | 1.16x |
| 17083 x 2048 | 57.7 us | 36.6 us | 1.58x |

### End-to-end

On an FP8 block-quant MoE serving workload with prefill-heavy multimodal traffic, Qwen3-VL-235B-A22B-Instruct-FP8 at 2 replicas x TP=4 on 8x H200, a 4-run A/B measured a consistent ~0.5% throughput gain with all pairwise comparisons positive. This is modest, as expected for a kernel that is a small share of step time, and in family with the 0.85-1.7% reported in #55330. Outputs are bitwise-identical by construction.
