# [Perf][Attention] Add bounded FP8 page expansion for native prefill

[Upstream PR](https://github.com/vllm-project/vllm/pull/64942) · state: open · merged: False

## Original PR description



## Overview

Accelerate native FlashInfer prefill on SM120 by converting referenced FP8 KV
pages once into bounded BF16 scratch. The earlier release implementation
improved input-token throughput by up to **10.1%** in recorded paired
cold-prefill tests, while retaining persistent FP8 storage and BF16 queries.

## Claims

- Disabled by default; BF16 queries and decode retain their existing precision.
- Most promising for large prefill chunks with repeated KV reads; the extra
  copy and memory cost can outweigh any benefit on other workloads.
- Separate scratch ownership per live metadata object, with native fallback
  for unsupported modes, small prefills, budget limits and allocation failure.

## Validation

Measured on the earlier release implementation with identical request bytes,
checkpoint and speculative-decoding settings in both arms:

| Cold-prefill case | Native input tok/s | Expanded input tok/s | Improvement |
| --- | ---: | ---: | ---: |
| Shorter | 8,823 | 8,936 | +1.3% |
| Intermediate | 6,145 | 6,525 | +6.2% |
| Longest | 3,478 | 3,828 | +10.1% |

These are input tokens divided by server-reported prefill time, with zero
prefix-cache hits and one measured pair per case. The longest case's prefill
latency fell **9.2%**. These measurements describe the prior implementation;
they are not current-main benchmarks or decode-throughput gains. Workload
and checkpoint details are withheld; the supplementary validation document
provides a public-model follow-up procedure.

Validation combines earlier GPU numerical/reference and end-to-end serving
checks with checks of this upstream port:

- The release-based implementation passed GPU and serving checks. Its host
  helper logic is preserved, and eight compiled SM120 kernel instruction
  sections match byte for byte using the same toolchain.
- On this checkout: 10 CPU metadata tests with upstream conftest, 50 Triton
  CPU-interpreter cases, CLI setting/bounds checks, eight offline SM120
  compilations, and all applicable pre-commit hooks passed. Kernel cases
  cover every finite E4M3 encoding and addresses beyond 2 GiB.

The supplementary [validation record](https://github.com/tireiron/vllm/blob/349c772899cbda8349ae6a096b7fccc5571019f4/VALIDATION.md)
contains reproduction commands; the [portable CPU check](https://github.com/tireiron/vllm/blob/349c772899cbda8349ae6a096b7fccc5571019f4/validate_kernel_cpu.py)
is available alongside it. CPU checks used released runtime
dependencies. This port's SM120 serving integration, performance and model
evaluation have not been rerun with current-main dependencies because a
dedicated test device is unavailable. Added GPU helper tests are selected
by existing attention CI; that CI does not exercise the SM120-only serving
path. No current-main speedup or model-accuracy result is asserted.

## Details

The native mixed-dtype prefill path converts FP8 cache tiles for successive
query tiles. Gathering referenced page entries once per layer and prefill
step lets BF16 attention reuse the converted values. The cast preserves finite
E4M3 values exactly, and attention still applies the original K/V scales.
Attention reductions may differ numerically.

The scratch cap is per live metadata object; overlapping objects allocate
independent buffers up to that capacity. This can reduce serving capacity.
Compare prefill/first-token latency with expansion disabled, including the
copy cost, and check mixed-load decode latency, throughput and memory. A
kernel speedup alone does not establish an end-to-end serving benefit.

Related work: [#55065](https://github.com/vllm-project/vllm/pull/55065) uses
FP8 queries and a different SM120 backend;
[#63328](https://github.com/vllm-project/vllm/pull/63328) handles sparse MLA/FA4
on datacenter Blackwell. This change targets dense/GQA native prefill with
BF16 queries. Earlier cache-conversion work also exists in
[FlashInfer #1304](https://github.com/flashinfer-ai/flashinfer/pull/1304);
the merged [FlashInfer #6445](https://github.com/flashinfer-ai/flashinfer/pull/6445)
materializes NVFP4 pages to FP8 for a different TRTLLM prefill path.
The separate query-scaling fix
[#53754](https://github.com/vllm-project/vllm/pull/53754) is not included.
The existing TRTLLM dequantizer applies scales while converting and uses a
rectangular block table; this path preserves raw FP8 values and compact native
paged metadata instead. Maintainer feedback on placing this optimization in
vLLM versus FlashInfer would be useful.
