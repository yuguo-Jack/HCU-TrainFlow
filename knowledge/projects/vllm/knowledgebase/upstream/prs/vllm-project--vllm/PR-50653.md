# [Bugfix][KV Offloading] Fix CPU offload block count mismatch across PP ranks

[Upstream PR](https://github.com/vllm-project/vllm/pull/50653) · state: open · merged: False

## Original PR description

### Motivation

Native CPU offloading computes CPU cache capacity from each worker's KV cache tensors. Under pipeline parallelism, workers may own different numbers or types of layers, so different PP ranks can derive different CPU offload chunk counts.

The scheduler uses the first worker's KV cache config, while workers build offloading specs from their local configs. If the scheduler-side chunk count is larger than a worker's local CPU buffer capacity, offloaded chunk ids can exceed that worker's allocated CPU cache range.

This is a stability fix, not just a consistency one: when an out-of-range id is actually used, the failure is not an assertion — it is a SIGSEGV inside the CUDA driver, 10–24 minutes into a run, with no traceback and nothing in the kernel log (second reproduction in #50821).

The divergence is not specific to uneven layer counts: it also occurs with a balanced pipeline when speculative decoding places the draft (MTP) layers on the last stage — both stages can own the same number of groups and the same
num_blocks and still compute different chunk counts.

### Runtime Validation

  I reproduced the issue with vLLM v0.26.0 using:

  - Model: `GLM-5.2-NVFP4`
  - `pipeline_parallel_size=4`
  - `tensor_parallel_size=1`
  - Native CPU offloading via `OffloadingConnector`
  - Prefix caching enabled
  - No SSD offloading

  Before the fix, different PP ranks computed different CPU offload block counts from their local KV cache tensors:

  ```text
  scheduler/rank0 CPU num_blocks: 35341
  worker/rank0 CPU num_blocks: 35341
  worker/rank1 CPU num_blocks: 34435
  worker/rank2 CPU num_blocks: 34435
  worker/rank3 CPU num_blocks: 36561
  ```
  This confirms the mismatch. Since the scheduler allocates CPU block IDs based on its own CPU block count, rank1/rank2 only had capacity for 34435 blocks while the scheduler could allocate IDs up to 35340. Those IDs would be outside rank1/rank2's CPU buffer range.

  After applying the fix, all PP ranks used the same unified minimum CPU block count:
  ```text
  scheduler CPU num_blocks: 34435
  worker/rank0 CPU num_blocks: 34435
  worker/rank1 CPU num_blocks: 34435
  worker/rank2 CPU num_blocks: 34435
  worker/rank3 CPU num_blocks: 34435
  ```
  The fixed server also started successfully and returned successful responses:

  GET /health -> 200
  POST /v1/completions -> 200

### Proposed Changes

- Compute the CPU offload chunk capacity for every worker KV cache config and take the minimum across workers, so the scheduler can never allocate an id beyond any worker's capacity. The unification lives in the offloading subsystem (`unify_cpu_offload_num_chunks` in `vllm/v1/kv_offload/config.py`) and reuses the CPU backend's own `cpu_offload_layout` sizing, so a worker's view and the scheduler's unified count cannot be derived differently. This also resolves the connector's own config when it is nested inside a MultiConnector, so the unification applies there too.
- Carry the unified count on the pre-existing `CacheConfig.num_cpu_blocks`  (no new field on `KVCacheConfig`): the engine core computes it where all worker configs are visible, and each worker recomputes the same value from the full `kv_cache_configs` list in `initialize_from_config`.
- Propagate it through `OffloadingConfig.num_cpu_blocks` into `CPUOffloadingSpec`.
- Reject out-of-range block ids in `compute_sub_block_ptrs` instead of computing a wild pointer (from @yqszxx, also open as #60061), turning a delayed SIGSEGV into an immediate ValueError.
- Thanks to @yqszxx, who rebased the original fix onto current main and contributed the CPU-tier geometry dedup and the bounds guard.
