# [Perf][CPU][DiffusionGemma] Run one-step DiffusionGemma reads in a single forward pass

[Upstream PR](https://github.com/vllm-project/vllm/pull/61480) · state: open · merged: False

## Original PR description



## Overview

This PR runs DiffusionGemma one-step reads in a single forward pass on the CPU backend. It adds `DiffusionConfig.single_pass_reads`, off by default. It is split out of #60527 and holds only the single-pass part.

A one-step read sets `diffusion_read_only` and `diffusion_max_steps=1`. It is the default structured read in examples/features/structured_diffusion. Today it takes two engine steps. The first prefills the prompt and emits nothing. The second runs the canvas. With the flag on, the canvas runs in the step that finishes the prompt.

No other open PR or issue covers this. I searched open PRs for single_pass_reads, single pass diffusion, DiffusionGemma one-step and DiffusionGemma CPU.

I used Claude Code to help with this PR. OpenAI Codex was used for the rebase and validation below. I reviewed every changed line and ran the tests below.

## Claims

- On a 44 vCPU Xeon with AMX, one-step reads are **21 to 25% faster for 188-token prompts and 12 to 13% faster for 1250-token prompts**. Reads with a cached prompt prefix are 21% faster.
- Bursts of 4 reads are faster in all 8 shapes when comparing the fastest of 3 bursts per arm: 11 to 14% for 188-token prompts and 3 to 5% for 1250-token prompts. Medians of 3 bursts are noisier, see Validation.
- Constrained reads (`diffusion_constrained`) fuse too, with the same gains.
- Each read takes one engine step instead of two. Over 144 timed calls, engine steps fell from 312 to 168.
- With the flag off, single reads are bit-identical to main.
- With the flag on, outputs are close but not bit-identical. No label decision flipped across 216 reads.
- Reads that request prompt logprobs keep the two-step path.
`single_pass_reads` is rejected on platforms other than CPU, with pipeline parallelism, and with KV connectors or KV offloading.

## Details

Design:

- `Scheduler` gets a no-op hook, `_final_prefill_spec_tokens`, called in the running and waiting loops before KV allocation. The core scheduler change is the hook and its two call sites. `DiffusionScheduler` overrides it. It returns one canvas of placeholder draft tokens when the step finishes the prompt of an eligible read, the canvas fits the step's token budget, and the prompt plus canvas stays below `max_model_len`.
- `is_single_pass_read` in `vllm/utils/diffusion.py` is the one eligibility rule. The scheduler uses it to attach the canvas. The sampler uses it to seed the canvas into the draft tokens when the request is added. The two always agree.
- The DiffusionGemma model state splits each fused request into a causal prompt row and a bidirectional canvas row on the same block table. Self-conditioning covers only the canvas rows. The sampler moves fused requests out of the encoder phase in the same step.

Tradeoffs:

- Outputs are not bit-identical with the flag on, which is why it is off by default. The README tells users to validate on their workload first.
- An eligible read waits until the free KV cache holds its prompt and canvas, rather than falling back to two steps.

Limitations:

- CPU only, which is where the fused pass was measured and validated.
- No CI job runs a fused forward pass of the model. `TestFusedAttention` checks the fused attention against two passes on the CPU kernel, in the CPU CI job.
- #60663 batches self-conditioning on the assumption that a request's whole query span is its canvas. A fused request's span also holds the end of its prompt. Whichever PR lands second has to start the canvas at `end - num_logits`.
