# [KV Connector][1/N] KV checksums: verify P/D KV transfers, with NIXL pull

[Upstream PR](https://github.com/vllm-project/vllm/pull/61578) · state: open · merged: False

## Original PR description

## Overview

First of a series adding connector-agnostic checksums of transferred KV for P/D disaggregation, so that transfers that complete without error but deliver the wrong KV are caught before the request runs: a read after the producer has already reused its blocks, or KV placed at the wrong position because the two sides disagree on the layout. This PR adds the framework and makes NIXL pull its first connector.

With `kv_transfer_config.enable_kv_checksum` on both sides, the producer checksums a request's KV in the step that finishes its prefill. The checksums travel to the consumer with the request in `kv_transfer_params`, and the consumer compares every load against them. Under `kv_checksum_fail_closed`, a mismatched or unverifiable load is handled as a KV load failure, so `kv_load_failure_policy` applies (`fail`, or `recompute` locally).

Series (each PR stacks on the previous one; only its own commits are new):
1. **This PR**: the framework plus NIXL pull.
2. #61579: KV heads replicated across TP, and different producer and consumer block sizes.
3. #61580: NIXL push, on a connector-owned carrier.
4. Mooncake P2P (in #61488 for now).
5. Mamba state (in #61488 for now).
6. Triton kernel (in #61488 for now).

#61488 holds the whole series in one draft as the reference implementation, along with its end-to-end validation.

Not a duplicate: #57912 and RFC #54363 add integrity checks for the filesystem KV offload tier, while this series covers producer-to-consumer transfers. No other open PR checksums P/D transfers.

## Claims

- With NIXL pull, the consumer detects corrupted or misplaced KV before the request runs. The checksums do not depend on the TP split, the PP split or the KV cache layout, so producers and consumers with different TP/PP sizes compare them directly.
- Enabling checksums does not change model outputs. Results reach the host on a side copy stream, not through a sync on the engine step.
- Off by default, and a connector that declares no carrier is unaffected.
- Groups this PR does not checksum yet are skipped and left out of the comparison. These are Mamba state, KV heads replicated across TP ranks (including MLA), and layers with several caches; later PRs in the series cover them.

## Details

The commit messages give the design, the alternatives that were rejected, the known limitations and the tests. Two commits:

1. **Framework.** No connector declares a carrier in this commit.
   - Workers checksum their KV slices in global coordinates. Per (layer, KV head) slice, s = Σ x_j (2j+1) over 8-byte pieces numbered from the request's first token, weighted by m = 2(layer·H + head) + 1, all mod 2^64.
   - The scheduler sums the TP and PP parts. The producer adds the sums to `kv_transfer_params["kv_checksums"]`. The consumer compares each KV cache group separately and reports it as matching, mismatched or unverified.
   - This adds the connector API `kv_checksum_carrier`, and MultiConnector delegates it to its sub-connectors.
   - The checksum definition and the wire format stay fixed for the rest of the series, so mixed versions never report a false mismatch.
2. **NIXL pull** declares the `kv_transfer_params` carrier (11 lines). Bidirectional loads, where a prefiller reloads a decoder's KV, are not checksummed.

Cost: the producer does its checksum work in the step that finishes a prefill, and the consumer in the step where a load completes. This PR uses the PyTorch path; the Triton kernel comes in 6/N. With that kernel, the full series on Qwen3-8B P/D TP2 -> TP2 adds +3.5 ms TTFT at 1K prompts with concurrency 1, and −3.8% request throughput at concurrency 32. The change is under 1% for 8K prompts under saturation and for 32K prompts.

Limitations:
- Enable checksums on producers before consumers; otherwise consumers see loads without checksums, which are unverified.
- Proxies must forward unknown `kv_transfer_params` keys.
- ROCm is untested.

- yubofredwang · comment · 2026-10-16T20:46:08Z · [source](https://github.com/vllm-project/vllm/pull/61578#issuecomment-6224374407)

Hi @sawsa307 thanks for the great work. Regarding this feature. Have you evaluated make the checksums be triggered from the model runner and the connector instead of the scheduler?
Model runner: right after a step writes KV, checksum exactly the rows that step wrote (its slot mappings already list them).
Connector: when a transfer actually completes, verify the received blocks against those checksums.
Each step, model runner already knows exactly which cache rows it wrote: those are the slot mappings it passes to the attention kernels. Checksum those rows right after they are written. Then verify on the consumer when the connector reports that the transfer really finished.

Each of these hooks decides “the KV is final” from counters that were wrong this year (#34616, #58259, #58668). A checksum driven by those counters doesn’t raise false alarms in these cases, but it can’t catch them either: when the counters say rows are computed and the rows hold the wrong tokens, both sides checksum the same wrong bytes and agree. A checksum triggered by the KV writes themselves, recording which token was written at which position, does catch them.

Thanks @yubofredwang for the comment. The checksums only verify that the consumer received the same bytes, at the same positions, as the producer holds. If a bookkeeping bug leaves the wrong KV under a request on the producer, both sides hash the same bytes and agree.
 
That is the intended scope: transfers that complete without error but deliver the wrong KV. Transports already checksum bytes in flight, so these come from lifetime and layout bugs, e.g. reading blocks after the producer reused them (#61229), or a P/D layout mismatch (#58860, #61526).

Hashing at write time wouldn't change this: it would hash the wrong KV when it is written. I don't think that check belongs in the P/D checksums for the following reasons:
- The linked bugs are in the engine's own bookkeeping and also affect deployments without P/D, which a check on the P/D consumer would not cover.
- By the time the consumer detects it, the wrong KV already exists. The best it can do is fail or recompute the request.
- It would add a per-step cost in production to guard against rare scheduler bugs.

I think a better place for it is as a test oracle. Extend the randomized scheduler tests (e.g. `tests/v1/core/test_priority_scheduler_random.py`) with a mock model runner that records the (position, token) written to each slot. Randomize spec decode acceptance and stop trimming, async scheduling, preemption, prefix caching and resumable sessions. After every step, assert that each slot below `num_computed_tokens` holds the request's token at that position. That runs on CPU in CI, and over-counted tokens like #58668 or a block shared between two requests would fail it.

> 1. The linked bugs are in the engine's own bookkeeping and also affect deployments without P/D, which a check on the P/D consumer would not cover.

Agreed. Checksums could be useful beyond connectors, but if the scope is P/D only, bugs that also hit deployments without P/D belong in the test oracle you describe, and a scheduler-driven checksum is fine for that scope. One counterexample is #34616. It was on the consumer's async-load path, so it existed only in P/D. Its shape, D computing over rows P never sent, still passes this PR under fail-closed.

> 2. By the time the consumer detects it, the wrong KV already exists. The best it can do is fail or recompute the request.

That is the behavior we want. Failing or recomputing is what keeps one tenant's KV out of another tenant's request, which is @njhill's motivation. It is also what this PR does for the bugs.

> 3. It would add a per-step cost in production to guard against rare scheduler bugs.

For agentic multi-turn traffic it is the other way around. `add_send` checksums `[0, N)` on every request, so every turn re-hashes the whole conversation, and that cost lands on the step that finishes the prompt, on the TTFT path. A write-time accumulator hashes each row once, when it is written, and hit blocks keep their value. Over a session of T turns with equal deltas, that is about (T+1)/2× fewer bytes.

I benchmarked both triggers with this PR's checksum definition: `_LayerView` compiled from `8063d8aaf4`, Qwen3-8B shape, 128k context, 94% prefix hit:

| | prefill-finish (this PR) | write-time |
|---|---|---|
| eager (PyTorch ops per layer, as in this PR) | 43.8 ms (8.4% of the turn's prefill) | 3.1 ms (0.6%) |
| fused (one Triton kernel) | 3.38 ms (0.65%) | 0.26 ms (0.05%) |

- CaoManhDat · comment · 2026-10-19T07:13:32Z · [source](https://github.com/vllm-project/vllm/pull/61578#issuecomment-6261789783)

General idea, I think this checksum is hard to avoid:
- D pulls data from P, so D has to be sure it got the right data. Either P locks the memory until D is done, or D checks the data itself with a checksum.
- Locking does not work here — P has to reuse memory to keep running, so it cannot wait for a slow D forever. When the lease runs out, D can read new garbage with no error. Locking also can’t catch broken bytes or blocks put in the wrong place.
- So D must check by itself. Locks make the bad window smaller, checksums catch what still slips through.
