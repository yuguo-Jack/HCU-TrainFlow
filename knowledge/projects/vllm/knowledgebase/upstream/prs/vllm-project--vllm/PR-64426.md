# [Frontend] Serve all multi-port DP ranks from one Rust frontend

[Upstream PR](https://github.com/vllm-project/vllm/pull/64426) · state: open · merged: False

## Original PR description



## Overview

With `--data-parallel-multi-port-external-lb`, add an opt-in mode (`VLLM_RUST_FRONTEND_RANK_PORTS=1` with `VLLM_USE_RUST_FRONTEND=1`). It serves every local DP rank's port from one Rust frontend, instead of running one full `vllm serve` per rank.

## Claims

- New Rust `frontend` flag `--rank-listen-fd RANK=FD`, repeatable. Each one is an extra inherited HTTP listener pinned to one DP rank:
  - Every request on it reaches that rank's engine, through the existing `X-data-parallel-rank` pinning.
  - Its `/metrics` lists only that rank's per-engine series.
- `vllm serve` with multi-port external LB and the new env var starts one hybrid-LB server for the local ranks. Its Rust frontend listens on:
  - `--port + local_rank` for each rank. These are the same ports the per-rank servers use today.
  - `--data-parallel-supervisor-port`, balanced across the local ranks.
- Default behavior is unchanged. Without the env var, multi-port external LB still runs the DP supervisor with one `vllm serve` per rank.

## Details

**Motivation.** With multi-port external LB, each local DP rank runs a full `vllm serve`: a Python API server process plus a Rust frontend. A router that addresses ranks by port needs separate ports, not separate processes. Two examples are llm-d's routing sidecar and an endpoint picker that scrapes `/metrics` per port. One Rust frontend can already connect to all local engines and pin a request to a rank with `X-data-parallel-rank`. So it can serve all of those ports and save the memory of the extra processes per rank.

**Rust frontend**

- `Config.rank_listeners: Vec<RankListener { rank, mode }>`.
  - `validate()` requires the ranks to be distinct and inside the connected engine range `[engine_start_index, engine_start_index + engine_count)`.
  - Managed `serve` always leaves the list empty.
- `serve_with_router_extension` binds each rank listener up front, next to the main HTTP listener and the gRPC listener.
  - Each one serves the same router, with the same TLS config and connection timeouts.
  - `try_join_all` joins them with the main listener under the same shutdown token, so graceful drain and force shutdown behave as before.
  - gRPC is unchanged. `--grpc-port` is already rejected with multi-port external LB.
- `middleware::with_data_parallel_rank` wraps the router for a rank listener.
  - It overwrites `X-data-parallel-rank`, so a client-supplied header cannot move a request that arrived on one rank's port to another rank.
  - It also adds a `ListenerRank` extension.
- On a rank listener, `/metrics` drops the sample lines whose `engine` label names another engine.
  - Comment lines and samples without an `engine` label (HTTP and process metrics) are kept.
  - Label values are parsed with escape awareness, so a quoted `engine="…"` inside another label value is not matched.
  - The main listener's `/metrics` is unchanged.
  - Tradeoff: frontend-wide series, such as HTTP request counters, appear on every rank port. A per-port scrape therefore matches a single-rank frontend for per-engine series only.

**Python**

- `dp_supervisor.build_rank_ports_server_args(args)`:
  - Reuses `validate_multi_port_external_lb_args` and `infer_multi_port_external_lb_start_rank`.
  - Returns hybrid-LB args for one server that owns all local ranks and listens on the supervisor port, plus `{start_rank + r: port + r}`.
- `run_multi_api_server(args, rank_ports=...)`:
  - Binds the rank sockets with `create_server_socket` before the engines start, so a port that is already taken fails fast.
  - Passes the rank sockets to `RustFrontendProcessManager(rank_socks=...)`, which adds `--rank-listen-fd rank=fd` and inherits those fds.
- `VLLM_RUST_FRONTEND_RANK_PORTS` is documented in `envs.py`. It is excluded from compile-cache factors because it only changes the launch topology.

**Limitations**

- Rust frontend only. The Python API server has no equivalent, and `run_multi_api_server` raises if `rank_ports` is passed without the Rust frontend.
- The supervisor's own process model goes away in this mode:
  - The supervisor port serves the full API, including `/health`, instead of the supervisor's aggregated health endpoint.
  - One process serves all local ranks, so it is a shared failure domain. Today a failure in one rank's server process leaves the other ranks up.

I checked open PRs for `rank-listen-fd`, Rust-frontend rank ports and multi-port Rust frontend and found no duplicate.
