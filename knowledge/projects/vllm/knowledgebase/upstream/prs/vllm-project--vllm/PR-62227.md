# [Bugfix][LoRA] Keep no-lora requests out of the torch punica ops

[Upstream PR](https://github.com/vllm-project/vllm/pull/62227) · state: open · merged: False

## Original PR description

## What this fixes

Fixes #62225.

On the CPU backend, a base-model request scheduled in the same batch as LoRA requests is computed with an adapter applied, and returns the adapter's output with no error or warning. The reporter's minimal repro (random adapter, three-phase concurrency probe) shows 0/40 base requests in the mixed phase matching their base-alone outputs, and 35/40 byte-identical to the adapter's gibberish.

## Root cause

`vllm/lora/ops/torch_ops/lora_ops.py` backs `PunicaWrapperCPU`. Its `bgmv_shrink`, `bgmv_expand` and `bgmv_expand_slice` gather stacked adapter weights with the raw per-token indices:

```python
selected_loras = lora_b_weights[lora_indices_tensor]
```

An index of -1 is the documented "no adapter" marker (`token_lora_indices`: "An index of -1 means no lora should be applied"). Python negative indexing reads it as the last stacked slot instead, so every no-lora row silently receives that slot's output. The triton kernels exit early on `lora_id == -1`, and the tests' own reference implementations skip `lid < 0`, so only the torch (CPU) path diverges. `sgmv_*` delegate to `bgmv_*`, so the linear, logits (`LogitsProcessorWithLoRA` always uses bgmv) and embedding paths are all covered by fixing the three `bgmv_*` functions.

Base-only traffic is unaffected because `no_lora` short-circuits the wrappers; adapter-only traffic has no -1 entries. Only the mixed case hits the bug, exactly matching the issue's observations.

## The fix

Clamp the index before gathering (`clamp_min(0)`, the same pattern `_select_full_linear_output` already uses) and mask the adapter output on inactive rows:

- `bgmv_shrink` / `bgmv_expand` / `bgmv_expand_slice` zero the adapter output for -1 rows, so `add_inputs=True` leaves those rows untouched and `add_inputs=False` preserves their prior values via `torch.where` (matching the kernels' early exit, which writes nothing).

Batches without any -1 entries are bit-identical: the clamp is the identity on non-negative indices and the mask multiplies by 1.

## Verification

- New `test_torch_ops_respect_no_lora_index` in `tests/lora/test_punica_ops.py`: mixed `[-1, 0, 1, -1]` indices through shrink, expand (both write modes) and expand_slice; inactive rows must keep prior values, active rows are checked against a manual two-stage matmul. Fails on the unpatched ops, passes with the fix (verified both ways locally, `VLLM_TARGET_DEVICE=cpu`).
- Standalone probes driving the op functions directly: on the unpatched tree all six shapes (shrink, expand add/set, expand_slice add/set) corrupt -1 rows; on the patched tree all keep them clean. This is CPU-only evidence on macOS (torch 2.x, no GPU); the GPU kernel paths are untouched.
- `ruff check` and `ruff format` clean.

## Notes

- The XPU path dispatches to oneMKL custom ops and is out of scope here; worth a separate look if those kernels treat -1 the same way.
- The existing torch-ops-vs-triton comparison tests never generate -1 indices (`torch.randint(0, ...)`), which is why CI did not catch this; the new test closes that gap for the torch path.

- javabbgit · comment · 2026-10-18T17:12:17Z · [source](https://github.com/vllm-project/vllm/pull/62227#issuecomment-6252746195)

Tested this PR end-to-end on the machine from #62225: vLLM 0.31.0 CPU wheel, torch 2.13.0+cpu, Ryzen 7 5800H (AVX2 only), WSL2 Ubuntu 24.04, Qwen2.5-0.5B-Instruct fp32, greedy.

The installed `vllm/lora/ops/torch_ops/lora_ops.py` was byte-identical to v0.31.0, so I replaced just that file with the one from 1dad732 and cleared the torch.compile caches before restarting. Same commands before and after.

**Minimal repro** (server exactly as in the issue: one random r=8 adapter, `--max-lora-rank 8`, default `--max-loras`):

| | 0.31.0 | + #62227 |
| --- | --- | --- |
| op check, rows with index -1 left untouched | 2/7 | 7/7 |
| base mixed == base alone | 0/40 | 40/40 |
| base mixed == lora alone | 35/40 | 0/40 |
| lora mixed == lora alone | 40/40 | 40/40 |

No side effects where no -1 index is involved:
- base-alone and lora-alone outputs are byte-identical before vs after the patch: 40/40, 40/40
- after the patch, base-mixed matches base-alone from the unpatched run: 40/40
- op-level checksum for a batch without -1 indices: identical

**Real adapters** (r=8 and r=32 triage adapters, `--max-loras 2`, 3 models interleaved at concurrency 8, 80 items): base accuracy 60% -> 10% (10% is what it scores alone, now with identical per-field scores); adapters unchanged at 98% / 100%.

**Speed**, single request / concurrency 8: base 13.5 / 76.9 -> 14.1 / 77.5 tok/s; LoRA 9.0 / 42.4 -> 8.9 / 40.8 and 41.7 on a rerun. Within run-to-run noise (about ±4% here); if anything LoRA at concurrency 8 is ~2-4% slower.

**One extra observation that may be useful:** with `--max-loras 3` and only one adapter in use, the -1 index lands on an empty last slot. Base outputs then look normal (0/40 match the adapter), but before the patch only 2/40 matched base-alone; a base-only control at the same concurrency (8 -> 16) gave 40/40, so batch size is not the cause. After the patch this case is also 40/40. So base requests were affected whenever they shared a batch with LoRA requests, even when the wrapped-to slot held no adapter.

Looks good from the reporter's side. Thanks @he-yufeng for the quick fix.
