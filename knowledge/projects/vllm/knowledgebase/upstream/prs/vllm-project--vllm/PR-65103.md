## Overview

`rejection_sample` accepts a precomputed fp64 `target_lse`, and `RejectionSampler` passes the one `topp_cutoffs_lse` (#65101) already computes alongside the cutoffs, so on the top-p-on-load path (#65102) the stats kernel no longer reduces the target logits a second time. 4/4 of a stack; part of #61024.

**Stacked, draft.** Contains #65101 and #65102 (with #61344's commits), then the commit of #64242 (by AlejandroParedesLT, authorship kept), which fixes the near-1 collapse of the global log-sum-exp by promoting it to fp64. **New code is five commits:** the target log-sum-exp from the cutoff op; #64242's per-element math in fp32 (co-authored with AlejandroParedesLT); dropping the op's log-sum-exp when verification narrows the vocab; the global combine itself in fp32 with #64242's precision; and, last, keeping the max's 1 out of the block sums and the resample residual nonzero, from #65176 (co-authored with shiannn13). The two commits before the last are #65101's kernel rework, cherry-picked. After those come the 2026-11-03 fixes carried from #65101 and #65102: #65101's int64 index-mapping fix, #65100's commit with its block skip firing on the on-load path, and #65102's end-to-end `LLM` test.

**Fix (2026-11-03).** The first top-p request took EngineCore down: `topp_cutoffs_lse` accepted only an int32 `expanded_idx_mapping`, while Model Runner V2 builds int64 index mappings (#60736). Fixed in #65101 and carried here with the rest of #65102's fixes (details there).

## Claims

- Verification step for top-p requests (K = 3, top-p 0.95, Qwen3-0.6B creative-writing logits, GB300), after #65102: 457 → 400 µs at 256 requests with T = 1 and 485 → 410 µs with T = 0.7 (vLLM main: 2,122 and 2,158 µs).
- MiniMax-M3.1-like verification (DSpark K = 7, block verification, V = 200,064, top-p 0.95): **2.8–5.3× faster than main at T = 0.95** from 1 to 128 requests, 2.9–5.5× at T = 1.
- With #65100's resample skip firing on the on-load path (from #65102), `rejection_sample` with the op's cutoffs and log-sum-exp (real Qwen3-0.6B rows, K = 3, top-p 0.95, T = 1) goes **262 → 138 µs** at 256 requests, 72 → 42 µs at 64 and 29 → 22 µs at 16, bitwise identical. The step times below predate it.
- **#64242's fix without its fp64 cost.** As written, its fp64 math made block verification 2–4× slower than main on GB300 (low fp64 throughput; the combine runs in every program of the per-block kernels). Here the combine is fp32 and as precise: each block's sum leaves out its own max and the combine adds the other blocks' 1 back, so the max token's 1 is never added; `log1p` of the rest keeps a runner-up far below the max, and the result is an exact `hi + lo` pair that `x - lse` consumes as `(x - hi) - lo`. #64242's own test passes (its probe's block sums follow that convention); on 65K synthetic partial sets the log-sum-exp is within 5.5×10⁻⁷ of fp64 (the fp64 combine: 5.2×10⁻⁷; both set by the fp32 block sums).
- **Resampling stays in the target's support** (#61383; fixes and test from #65176 by shiannn13). When the draft puts all but e^-gap of its mass on the one token the target allows, two fp32 roundings emptied the residual and the resample emitted token 0: `1 + e^-gap` inside an 8,192-token block, and `exp(log q - log p)` rounding to 1 in the residual. Block sums now leave one max element out, and the residual is `log p + log(1 - exp(log q - log p))` with the existing series for `1 - exp` near 0 (no libdevice). The previous head resamples token 0 at gap 25; this keeps the allowed token. Cost: +4% of the step at 256 requests (K = 3), +2–4% elsewhere, by counting the max's ties instead of taking its index (an argmax per block cost +20%).
- Never slower than main across a 360-configuration stress matrix (1.04–8.3×, median 3.6×, run with #65101's first commit), and within 4% of #65102 at the median; the largest remaining gap is +3.7 µs (+13%) at 1 request, K = 7, block verification, top-p = 1, where no op log-sum-exp is available and the combine runs serially per position.
- Same samples as the stats pass's own log-sum-exp (test below). The value is over the same `x / T` (rounded to nearest) the verify kernels use, so the max token's log-probability is never positive: with top-p = 1 on 2,048 real rows, vLLM main's fp32 log-sum-exp leaves p_max at exactly 1.0 in 77 rows (T = 1), #64242 alone in none, this in none.

Precision of the target log-sum-exp against fp64 on the same `x / T`, 1,024 real rows per profile, top-p ∈ {0.95, 1}, T ∈ {0.7, 1}: vLLM main (fp32 blocks, fp32 combine) ≤ 2.1×10⁻⁶; #64242 ≤ 4.8×10⁻⁷; `topp_cutoffs_lse` ≤ 1.2×10⁻⁷. ## Details

- **How.** The op's log-sum-exp reaches every kernel that combines target partials as two fp32 partials per row (`-inf`/0 in the other blocks), so none of those kernels changes; the stats kernel skips its target pass under `HAS_TARGET_LSE`, and greedy rows still compute their block maxes for the argmax. Vocabularies of one 8,192-token block, or wider than the draft's, recompute it.
- **The combine (`_compute_global_logsumexp`)** returns `(hi, lo)`; fp64 appears only where a log-sum-exp is stored for the resample kernel. `log1p` is an fp32 `atanh` series plus an exact multiple of ln2_hi (no libdevice, which MRV2 avoids for other backends; error < 1.3×10⁻⁷ absolute). The one-hot residual `1 - exp(log p)` uses a short series instead of fp64 `exp`. With fewer registers, the residual-mass kernel is faster at 4 warps again on the on-load path (#65102 uses 8).
- **Relation to #64242.** Its goal (no near-1 collapse) and test are kept; its fp64 implementation is replaced. If #64242 lands first, the fp32-combine commit rebases onto it as a follow-up.
- **Relation to #65176.** Its `(max, correction)` pair is this PR's `hi + lo`; its per-block sum and residual fixes, and its test, are folded in here with its author as co-author.
- **Not duplicating.** This folds in #64242 and #65176 (their authors are credited) and removes the target reduction #64242's combine works on. Searched open PRs for "rejection sampler logsumexp", "draft logsumexp", and #61024.
- **Stack.** 1 #65100 (included here) · 2 #65101 · 3 #65102 · **4 this**. #65104 (draft log-sum-exp from the drafter) closed: a net loss once the drafter's cost is counted.

- shiannn13 · comment · 2026-11-02T15:55:24Z · [source](https://github.com/vllm-project/vllm/pull/65103#issuecomment-6581644936)

Hi @zyongye, I've been working on #61383 too, and part of my change overlaps with yours. I opened #65176 as a draft to share it.

Like this PR, it carries the log-sum-exp as a (max, correction) pair and computes (x - max) - correction. That part overlaps with your (hi, lo) approach, so there's no need to duplicate it. It also does two things that #61383's failing state still needs.

**Per-block sumexp without the max's 1:**
I noticed that the latest commit subtracts the max token's contribution of 1 during the global merge. However, when the max and runner-up share an 8,192-token block, `1 + exp(-18)` already rounds to `1.0` in the per-block stats pass, so subtracting 1 during the merge cannot recover the lost correction.

In #65176, the stats kernel instead excludes one max element from each block's sum to avoid this precision loss. In #61383, this issue occurs on the draft side, where `q(") ≈ 1 - exp(-gap)` and there's no op-provided log-sum-exp.

**expm1 residual:** 
_resample_kernel computes log_p + log(-expm1(log_q - log_p)) instead of log1p(-exp(delta)). With delta ≈ -1.5e-8, exp(delta) rounds to exactly 1.0, so the residual is empty even when both log-sum-exps are exact.
On a reconstruction of the issue's state (real XGrammar + Qwen3-4B tokenizer, top-k/top-p, a draft that isn't grammar-masked), main and #64242 both still emit token 0 at gap ≥ 18.

I also ran the test on this branch (ae6817425a, RTX 2050), with the test added unchanged to test_rejection_sampler_utils.py. Gaps 10 and 14 pass, but gap 25 fails under both standard and block verification: assert [1, 2, 0] == [1, 2, 3], i.e. it still resamples token 0. The other 134 tests in that file pass.

If #65103 lands first, I'm happy to rebase #65176 onto it as a follow-up with just the per-block sumexp, the expm1 residual and the test. If you'd rather fold those into your stack instead, that works for me too.

- zyongye · comment · 2026-11-02T20:13:59Z · [source](https://github.com/vllm-project/vllm/pull/65103#issuecomment-6587393475)

Thanks @shiannn13, you're right on both counts. The `(hi, lo)` combine here only dropped the max's 1 after each 8,192-token block had already rounded `1 + e^-gap` to 1, and the residual still went through `exp(log_q - log_p)`.

I folded both fixes and your test into this PR as e7251a11e3, with you as co-author (`Co-authored-by: Andy Shih <shiannn@icloud.com>`). Two changes from #65176:

- **Ties counted instead of an index.** The block sum leaves out one max element by counting the max's ties (`sum over x != max` plus `ties - 1`), not by taking its index. On GB300 the per-block argmax cost +20% of the verification step (K = 3, 256 requests). The tie count costs +4%, and +2–4% elsewhere.
- **Series instead of `expm1`.** The residual uses the file's existing `1 - exp(x)` series near 0 instead of libdevice `expm1`. That removes libdevice from the resample kernel and is slightly faster.

`test_resample_stays_in_target_support` is unchanged. On the previous head (78b066a8c1) it fails at gap 25 for both standard and block verification (`[1, 2, 0] == [1, 2, 3]`), as you found; it passes now along with the rest of the suite (234 passed on GB300). #64242's probe test now feeds block sums in the new convention.

Since the `(max, correction)` pair is already here, this should cover #65176 completely. Feel free to close it, or keep it open as the fallback if this stack stalls.
