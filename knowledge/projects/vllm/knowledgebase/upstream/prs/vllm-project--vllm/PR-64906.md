# [Perf][MoE] Keep fp32 activation scales on the Triton FP8 experts and re-enable their fused SiLU+quant path

[Upstream PR](https://github.com/vllm-project/vllm/pull/64906) · state: open · merged: False

## Original PR description



## Overview

`is_deep_gemm_e8m0_used()` answers a platform-wide question: it is `True` whenever DeepGEMM is importable (it is vendored as `vllm.third_party.deep_gemm`, so always in the wheel and the docker image) and `VLLM_USE_DEEP_GEMM_E8M0` keeps its default of 1, on Hopper and Blackwell alike, whatever MoE backend the fp8 oracle actually selected.

The Triton FP8 experts followed that answer in two places:

1. `per_token_group_quant_fp8` defaults `use_ue8m0` to it, so both activation quants of a block-FP8 MoE layer served by the **TRITON** backend round their 1x128 scales up to a power of two. The consumer is `fused_moe_kernel`, which multiplies by whatever fp32 scale it is given; UE8M0 is a requirement of DeepGEMM's kernels, not of this path. The rounding only coarsens the quantization (scale 1.31x the fp32 scale on average, up to 1.99x; quant RMSE +3.6% on Gaussian input, +15% on heavy-tailed input).
2. The fused `silu_and_mul_per_block_quant` fast path from #42497 is gated on `not is_deep_gemm_e8m0_used()` because it writes fp32 scales. With the global `True`, that path is dead code in every default NVIDIA deployment; the tests reach it only through the `disable_deepgemm_ue8m0` fixture. The activation runs as `act_and_mul` + `per_token_group_quant` instead.

This PR makes the scale format a property of the kernel that consumes the activations rather than of the platform:

- `FusedMoEExpertsModular.act_scale_ue8m0` (default None = no preference). `TritonExperts` returns False for block-fp8 w8a8, since `fused_moe_kernel` takes any fp32 scale.
- `FusedMoEQuantConfig.act_scale_ue8m0: bool | None` plus a `use_ue8m0_act_scales` accessor. `FusedMoEKernelModularImpl.__init__` copies the experts' preference into the config when the config has none, so a preference set explicitly by a caller wins.
- `moe_kernel_quantize_input` / `_fp8_quantize` take `use_ue8m0`; the prepare steps that quantize block-fp8 a1 for standard-format experts (no-EP, naive DP/EP, DeepEP HT, DeepEP v2, NIXL EP) and the Triton experts' own quant calls pass the config's value, so every activation quant of one layer uses one format.
- The fused SiLU+quant condition tests `quant_config.use_ue8m0_act_scales` instead of the global.

DeepGEMM-backed experts (`DeepGemmExperts`, `TritonOrDeepGemmExperts` when the oracle picks DeepGEMM, the batched variants) and every other backend see no change. Setting `VLLM_USE_DEEP_GEMM_E8M0=0` already produced exactly this numerics for the Triton path; the PR makes it the default for that backend only.

## Claims

- **`Qwen/Qwen3.6-35B-A3B-FP8`, H200 TP1 (Triton FP8 MoE backend by default):** median TPOT at concurrency 1 3.888 -> 3.836 ms (-1.3%), concurrency 8 5.797 -> 5.657 ms (-2.4%), concurrency 32 10.10 -> 9.87 ms (-2.3%, p99 12.9 -> 10.5 ms); output throughput +1.3% / +2.2% / +3.3%. Two interleaved runs per arm with the GPUs swapped between runs.
- **`Qwen/Qwen3-30B-A3B-FP8`, H200 TP1 (same backend, `torch.compile` model):** median TPOT at concurrency 1 4.469 -> 4.295 ms (-3.9%), concurrency 32 10.163 -> 9.778 ms (-3.8%); concurrency 8 is within this model's run-to-run spread (main 6.445 / 6.694 on two runs).
- **Trace, Qwen3.6 concurrency 1:** per MoE layer the `act_and_mul_kernel` + `per_token_group_quant_8bit_register_kernel` pair on the routed-experts stream becomes one `silu_and_mul_per_block_quant` launch, and both quant kernels drop the `exp2(ceil(log2(s)))` rounding. nsys over ~500 steady decode steps: 1194 -> 1154 kernels per step (one fewer per MoE layer), median step 3863 -> 3769 us (-2.4%); the remaining `per_token_group_quant_8bit_register_kernel` instances (40, the first GEMM's input) now instantiate `SCALE_UE8M0=false`, and `silu_and_mul_per_block_quant_kernel` appears 40 times at 2.4 us.
- **Accuracy:** GSM8K 5-shot (greedy, 1319 questions, vLLM's `tests/evals/gsm8k/gsm8k_eval.py`) on Qwen3.6-35B-A3B-FP8: main 0.7377 / 0.7286 (two runs), this PR 0.7415. Run-to-run spread of the harness at concurrency 64 is about 1 point.
- **No change** for DeepGEMM-backed experts, for clamped SwiGLU (falls back to the unfused path, now with fp32 scales), for LoRA, for non-fp8 or non-128-block MoE, or for users who already set `VLLM_USE_DEEP_GEMM_E8M0=0`.

### Tests

`pytest tests/kernels/moe/test_block_fp8.py -k "not deep_gemm and not deepgemm"` on H200 (vLLM nightly image, DeepGEMM importable, `VLLM_USE_DEEP_GEMM_E8M0` default): **176 passed, 3 failed, 20 skipped**, and the same 3 fail on main at the same commit (`test_w8a8_block_fp8_fused_moe` at K=7168 with 1-2 elements out of 10^7 one bf16 ulp past the tolerance; unrelated to this change).

- New `test_w8a8_block_fp8_fused_silu_quant_ignores_deepgemm_ue8m0`, parametrized over `VLLM_USE_DEEP_GEMM_E8M0` = 0 / 1: a default block-fp8 config run through the Triton modular kernel must end up with `act_scale_ue8m0=False`, call `silu_and_mul_per_block_quant`, and match the fp32-SiLU torch reference. Without this change the `1` case fails on any machine where DeepGEMM is importable (the fused op is never called).
- New `test_triton_experts_request_fp32_act_scales_for_block_fp8`: building the modular kernel fills `act_scale_ue8m0=False` into a block-fp8 config, leaves an explicit `True` alone, and leaves a per-tensor fp8 config at None.
- The `VLLM_USE_DEEP_GEMM_E8M0=1` case skips where DeepGEMM E8M0 is unavailable, so it only counts as a regression check where it can fail.
- `torch_w8a8_block_fp8_moe` takes `use_ue8m0`, and `test_w8a8_block_fp8_fused_moe` / `test_w8a8_block_fp8_fused_moe_expert_map` check the modular output against a reference of matching precision (fp32 SiLU and the kernel's scale format) on every platform; the previous ROCm-only fp32-SiLU branch existed because the fused path only ran there.
- `test_w8a8_block_fp8_clamp_skips_fused_silu_quant` keeps covering the clamp fallback.

## Details

- **Why not add UE8M0 to the fused kernel instead (#43399).** That keeps UE8M0 scales on a path whose only consumer gains nothing from them, and keeps the extra rounding. If an EP dispatch ever needs the fused kernel's output in UE8M0, #43399's flag is the right tool there; it is orthogonal to this change.
- **Why the experts declare it and the kernel copies it into the config.** The first GEMM's input is quantized by the prepare/finalize step, which does not know which experts class consumes it; the quant config travels with both, and the modular kernel is the one place that sees both halves (the same way `expects_unquantized_inputs` is forwarded as `defer_input_quant`). A per-backend special case in the fp8 oracle would have to be mirrored in every prepare step by hand. An a2-only version of this change (fused path on, a1 still UE8M0) was measured and rejected: it mixes two scale formats in one layer, the modular test reference (which quantizes with the platform default) then diverges by 1.5-2.6% of elements, and GSM8K moved by -1.5 points in two runs. The full version keeps every activation quant of the Triton path in one format.
- **Callers left alone.** The DeepEP-LL and NIXL packed-UE8M0 dispatch paths (`use_ue8m0_dispatch`, batched DeepGEMM experts), the batched Triton experts' `batched_moe_kernel_quantize_input`, and the FlashInfer NVLink prepare steps keep the platform default: they feed kernels with their own scale expectations, or have no fused path to gain. `BatchedTritonExperts` could take the same preference in a follow-up once its a2 quant helper carries the flag.
- **Why the cost showed up in traces.** The `per_token_group_quant` and `topk_softmax` kernels launch with PDL, so their CUPTI durations include the wait on the previous kernel and overstate their cost; the fused kernel still removes one launch and one gap per MoE layer and the `log2`/`exp2` scale rounding in the remaining quant.
