# [Rust Frontend] Group prompt-cache usage and report created_cache_tokens

[Upstream PR](https://github.com/vllm-project/vllm/pull/63292) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

This PR is taken over and reworked from zylen-det's original change, whose description is kept at the end. The original reported `created_cache_tokens` on chat only, through a separate chat constructor. This version restructures the usage types first and keeps the original's CLI help fix. It supersedes vllm-project/vllm#63953.

The Python frontend reports `usage.prompt_tokens_details.created_cache_tokens` (the prompt tokens newly written to the prefix cache, vllm-project/vllm#48535); the Rust frontend does not. Adding it to the current Rust usage path means editing every route and dozens of test literals. Each prefill-stats count travels as a loose scalar through four separate accumulators. The wire usage block also has two constructors, and a route-specific field would have to be patched in at each call site. This PR first groups the counts and gives the wire usage block one constructor, then adds the field on top.

## Claims

- With `--enable-prompt-tokens-details`, the Rust frontend reports `created_cache_tokens` next to `cached_tokens` in non-streaming responses and in streaming usage chunks.
- The first commit is a pure refactor. Afterwards, adding a prefill-stats count touches only `PromptCacheUsage` (`vllm-llm`) and `Usage::from_token_usage` (`vllm-server`). The second commit shows this: 2 production files. The third commit, from the original PR, corrects the `--enable-prompt-tokens-details` help text.

- `routes::tests::prompt_tokens_details_report_created_cache_tokens` sends chat and completions requests through the HTTP router against a mock engine. The engine sends its prefill stats on the first output only. The test asserts `{"cached_tokens": 2, "created_cache_tokens": 3}` after the later decode output.
- `collect_output_aggregates_raw_tokens_logprobs_and_terminal_metadata` (`vllm-llm`) now also checks the count on the collected output.
- Both tests fail when `PromptCacheUsage::merge` drops the new count.
- The original PR's real-engine comparison (below) covers chat on its implementation; this rework was not rerun against a real engine. The value is the engine's `PrefillStats.num_cache_creation_tokens`, which Python's output processor reads too.

## Details

**Refactor (no behavior change):**
- `PromptCacheUsage` groups the counts that come from the engine's prefill stats. It replaces the loose `cached_token_count` on `GenerateOutput` and `TokenUsage`.
- Prefill stats arrive on one output only, so `PromptCacheUsage::merge` keeps the largest value seen. All four accumulators call it:
  - `GenerateOutput::merge` (stream interval);
  - `collect_output`;
  - the text decode stream;
  - the `/generate` stream.
- `Usage::from_counts` is removed. `Usage::from_token_usage` is the only constructor of the wire usage block. The streaming running-usage snapshot (`ContinuousUsage`) goes through it too, still without prompt details. It destructures its input exhaustively, so a new usage field fails to compile until it is mapped there.

**New field:** `PromptCacheUsage::cache_creation_token_count` → `PromptTokenUsageInfo::created_cache_tokens`.
- As in Python, a remote prefill's `remote_prefill_cached_tokens` overrides only `cached_tokens`.
- gRPC `FinishInfo` is unchanged.

**Divergence:** Python reports `created_cache_tokens` on chat only, where it feeds the Anthropic Messages `cache_creation_input_tokens`. On completions, Python leaves it `null` in non-streaming responses and omits it from streaming usage chunks. Rust reports it wherever `prompt_tokens_details` is reported. This is a strict superset of Python's output. Keeping the chat-only asymmetry would need a per-route switch at the call sites.
