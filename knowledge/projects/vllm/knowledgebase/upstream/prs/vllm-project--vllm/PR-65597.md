# [ROCm][UMBP] Add waiting-request prefetch to UMBPStoreConnector

[Upstream PR](https://github.com/vllm-project/vllm/pull/65597) · state: open · merged: False

## Original PR description



## Overview

Add opt-in UMBP prefetch for waiting requests through `prefetch_waiting_requests`. Uses MORI's [`batch_prefetch`](https://github.com/ROCm/mori/pull/850) API to populate the local DRAM tier before normal restoration.

## Claims

- Supports embedded and standalone UMBP modes.
- Prefetch runs separately from lookup; rejected hints and submission errors leave normal lookup and restore active.
- Controlled standalone benchmarks showed **6.6–19.1% lower mean TTFT**.

## Validation

**Performance:** MI355X, AITER and decode graphs enabled. Each arm runs `vllm bench serve` twice with identical random prompts: first to populate SSD, then to measure restoration after clearing HBM. Temperature zero, 16 requests, concurrency 4, and one active sequence per server.

| Model | TP | Input / output tokens | Mean TTFT off → on | Reduction |
|---|---:|---:|---:|---:|
| Qwen3-0.6B | 1 | 2,048 / 32 | 284 → 230 ms | **19.1%** |
| Qwen3-32B | 1 | 2,048 / 32 | 1,224 → 1,142 ms | **6.7%** |
| Kimi-K3 | 8 | 4,096 / 32 | 3,038 → 2,838 ms | **6.6%** |

All measured requests restored external KV, with equal restored bytes between arms and zero transfer failures. These are single matched pairs. 

**Accuracy:** Replayed 100 captured lm-eval GSM8K 20-shot prompts per model, using temperature zero and a 256-token output limit. HBM was cleared before each scored request.

| Model | Fresh computation | SSD restore | Prefetch + restore |
|---|---:|---:|---:|
| Qwen3-32B | 94/100 | 96/100 | 93/100 |
| Kimi-K3 | 100/100 | 100/100 | 100/100 |

Both restore passes hit external cache on all 100 prompts. Kimi's final answers matched throughout. Qwen had four answer differences between restore modes: three involved truncation and one involved arithmetic. 

## Details

The scheduler builds existing UMBP object keys when a request arrives and submits a best-effort prefetch hint through a separate executor. Embedded mode routes keys to their owning workers; standalone mode contacts the shared server directly.

MORI retains SSD copies while creating DRAM-tier copies. Admission counts do not establish completion; normal lookup and restore always run. Requires a MORI build exposing `batch_prefetch`.

Prefetch completion tracking, per-request cancellation, and a bound on the Python submission queue remain outstanding.

*Note: All benchmarks in this PR used MORI’s [async-prefetch PR](https://github.com/ROCm/mori/pull/850), which queues batch_prefetch() work internally; its new Submit/Status APIs were not used.
