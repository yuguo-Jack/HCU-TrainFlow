# [Bugfix][Platform] Fall back to torch when device-level NVML memory is unsupported (GB10)

[Upstream PR](https://github.com/vllm-project/vllm/pull/57378) · state: closed · merged: True

## Original PR description

## Problem

`nvmlDeviceGetMemoryInfo` is not implemented on integrated parts. On GB10 (DGX Spark) it raises
`NVMLError_NotSupported`, and `nvidia-smi --query-gpu=memory.total` returns `[N/A]`. The platform
still resolves to `NvmlCudaPlatform` (`is_integrated_gpu()` is `True`), so
`get_device_total_memory()` propagates that error.

The visible damage is in `EngineArgs.get_batch_defaults()`, which wraps the call in
`try/except Exception` and falls back to `device_memory = 0`. A 121.7 GiB card therefore misses the
`>= 70 GiB` branch and lands on the smallest defaults, with nothing logged.

On this machine, before:

```
card reports (torch)                    121.7 GiB
current_platform.get_device_total_memory()  -> NVMLError_NotSupported
resolved max_num_batched_tokens  API=2048   LLM=8192
resolved max_num_seqs            API=256
```

after:

```
current_platform.get_device_total_memory()  -> 130669424640 (121.7 GiB)
resolved max_num_batched_tokens  API=8192   LLM=16384
resolved max_num_seqs            API=1024
```

So every DGX Spark is currently serving with batch defaults 4x lower than the ladder intends.

There is a second caller, `startup_plan.py:66`, which is *not* wrapped — with
`VLLM_ENABLE_STARTUP_PLAN=1` the same `NVMLError_NotSupported` aborts worker startup outright. That
path is opt-in (default `0`), which is why this shows up as quiet misconfiguration rather than a
crash for most users.

## Fix

Catch `NVMLError` and fall back to `torch.cuda.get_device_properties().total_memory` — the same
source `NonNvmlCudaPlatform.get_device_total_memory` already uses, and the same NVML-tolerance
shape as `is_fully_connected()` a few lines below. The discrete-GPU path is unchanged; the fallback
only runs when NVML refuses.

## Test

Verified on the affected hardware (NVIDIA GB10, compute capability 12.1, driver 580.95.05,
aarch64 / CUDA 13); the fallback value matches `torch`'s `total_memory` exactly.

I have not run this on a discrete NVIDIA GPU — I do not have one to hand — but that path is
untouched. No unit test here since it would be all pynvml mocking for a six-line guard; happy to add
one if you'd prefer it.

Hi @hclsys, thanks for the contribution.

The visible effect of the fix is that every DGX Spark moves from the small tier (API 2048 batched tokens / 256 seqs) to the H100/H200 tier (8192 / 1024). The `>= 70 GiB` branch uses memory as a proxy for a large discrete GPU, and GB10 has the memory but not the compute. Larger prefill chunks mean longer decode stalls behind them, the profiling peak and sampler warmup grow, and with spec decode `max_num_seqs=1024` adds 16 more decode CUDA graph sizes (request counts 272 to 512). Do you have Spark serving numbers for old vs new defaults (TTFT/ITL at a couple of concurrencies, KV capacity, startup time)? If they do not show a win, keeping integrated GPUs on the small tier in `get_batch_defaults()` and fixing only the `NVMLError` would be the safer split.

Minor: the mocked-pynvml unit test you offered would be cheap and would pin the fallback.

- stecasta · comment · 2026-10-13T04:39:42Z · [source](https://github.com/vllm-project/vllm/pull/57378#discussion_r4254789891)

File: `vllm/platforms/cuda.py` · line None

IIUC `torch.cuda.get_device_properties()` initializes CUDA in the calling process. `get_batch_defaults()` runs in the parent (`LLM(...)` / API server) before workers start, so on GB10 this creates a CUDA context there and `_maybe_force_spawn()` then switches workers from fork to spawn. That is the regression #46141 fixed on ROCm (spawned workers lose in-process `ModelRegistry` registrations). Could the fallback use `cuda_get_device_properties(device_id, ("total_memory",))[0]` from `vllm/utils/platform_utils.py`, which reads the property in a forked subprocess when CUDA is not initialized yet?
