# [Docs][KV Connector] Diagnose CUDA IPC latency after cache reuse

[Upstream PR](https://github.com/vllm-project/vllm/pull/62188) · state: open · merged: False

## Original PR description

## Overview

Add a troubleshooting procedure for same-host KV transfers that get slower after cache reuse. Related to #55434, which also reports submission stalls affecting running decode requests.

## Claims

- Help catch descriptor-heavy CUDA IPC submission that short, fresh-instance benchmarks can miss.
- Show how to verify the selected transport, inspect NIXL 1.5.0's merged descriptor counts, and separate submission time from transfer and client latency.

## Validation

- `.venv/bin/pre-commit run typos --files docs/features/nixl_connector_usage.md` — passed.
- `npx --yes markdownlint-cli2@0.21.0 --config tools/pre_commit/.markdownlint.yaml docs/features/nixl_connector_usage.md` — passed.
- `git diff --check` — passed.

Checked the log format and telemetry against NIXL 1.5.0 source. Documentation only; no serving changes or new GPU benchmarks.

## Details

I hit this while benchmarking prefill/decode transfers for [my llm-d router evaluation](https://github.com/rayhanmemon/llm-serving-routing/blob/main/results/2026-09-21-layout-local/RESULT.md). On H200s, identical 120K-token Qwen3-32B requests moved the same 7.5 GiB per rank but alternated between about 23 ms and 467 ms of connector transfer time. The slow case spent roughly 414 ms in submission. A fast NVLink connection was not enough to make local transfers fast.

The guide turns that kind of observation into a repeatable investigation, including checking later transfers after block reuse. Existing transport-setup and metrics-documentation PRs do not cover this procedure; this builds on the existing metrics and merging implementation.
