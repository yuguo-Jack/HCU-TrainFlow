# [Model] Add Xing4_0 support

[Upstream PR](https://github.com/vllm-project/vllm/pull/57135) · state: open · merged: False

## Original PR description

## Summary

This PR adds native vLLM support for the upcoming **Xing4_0** MoE causal model.

Xing4_0 reuses the DeepSeek-V2/V3 backbone (MLA attention, MoE block, optional DSA indexer) and replaces the standard residual connection with **Manifold-constrained Hyper-Connections (mHC)**: the residual stream is expanded into `num_residual_streams` parallel streams mixed by input-dependent, doubly-stochastic matrices produced via Sinkhorn-Knopp projection. The mHC math matches the shared ops in `vllm.model_executor.layers.mhc`, so no private kernels are introduced.
Additionally, this PR enables optional FlagOS/FlagGems acceleration for Xing4_0: it enables the hot-path kernels (MoE, attention, softmax, topk, etc.) and brings measurable end-to-end inference speedups — up to 19.87% TTFT and 26.32% TPOT reduction on high-concurrency long-prompt workloads (H100 benchmark), opt-in and disabled by default.

## Changes

1. `vllm/model_executor/models/xing4_0.py`: full model implementation (`Xing4_0ForCausalLM`), including forward pass, mHC adapter, and tensor-parallel `load_weights()`.
2. Register `Xing4_0ForCausalLM` in `vllm/model_executor/models/registry.py` and related `__init__.py`.
3. Reasoning parser (`vllm/reasoning/xing4_0_reasoning_parser.py`) for reasoning-capable variants.
4. Tool parser (`vllm/tool_parsers/xing4_0_tool_parser.py`) for auto tool calling.
5. Register `xing4_0` in `vllm/config/speculative.py`, `vllm/transformers_utils/model_arch_config_convertor.py`, and `vllm/transformers_utils/config.py`.

## Optional FlagGems acceleration (opt-in)

An optional acceleration path is gated behind the env var `USE_FLAGOS=1` (disabled by default). When set, it enables a curated subset of FlagGems kernels via `flag_gems.only_enable(include=[...])`.

> **Scope note:** The acceleration is only enabled from the Xing4_0 model path — the flag_gems.only_enable(...) call lives exclusively inside xing4_0.py and is gated behind the env var, so no other model load path triggers it. The whitelist is intentionally narrow (...), and with the env var unset the behavior is fully unchanged. 
 For completeness: only_enable substitutes operators at the PyTorch dispatch level, so once enabled the kernels apply to any op in the same process that matches the whitelist — we therefore consider this an acceleration prototype and welcome feedback on a more scoped kernel backend.

```bash
pip install flagtree==0.6.1 flag-gems==5.3.4 -i https://resource.flagos.net/repository/flagos-pypi-nvidia/simple            # see version constraints in the PR discussion
USE_FLAGOS=1 vllm serve ${model_path} \
    --chat-template ${model_path}/chat_template.jinja \
    --host 0.0.0.0 \
    --port 8000 \
    --served-model-name $mode_name \
    --trust-remote-code \
    --dtype bfloat16 \
    --nnodes 1 \
    --tensor-parallel-size 1 \
    --max-model-len 262144 \
    --gpu-memory-utilization 0.90 \
    --max-num-seqs 64 \
    --max-num-batched-tokens 2048 \
    --enable-prefix-caching \
    --reasoning-parser xing4_0 \
    --enable-auto-tool-choice \
    --tool-call-parser xing4_0 \
    --uvicorn-log-level info \
    --enable-log-requests \
    --disable-custom-all-reduce
```

All Xing4_0 hot-path tests below run with FlagGems **disabled**.

## Benchmark method (H100 × 1)

- Framework: this branch vs. vanilla vLLM baseline (same branch, env var unset).
- Metric: **TTFT** (time to first token) and **TPOT** (time per output token).
- Workload: cold cache for each (input tokens + output tokens) pair.
- Each run: 5 repetitions, report the **median**; standard deviation in parentheses when ≥ 1%.
- No kernel warmup excluded; results reflect end-to-end served latency.

| input+output | concurrency | vanilla TTFT (ms) | flaggems TTFT (ms) | TTFT Δ | vanilla TPOT (ms) | flaggems TPOT (ms) | TPOT Δ |
|---|---|---|---|---|---|---|---|
| 50K+500 | 1 | 3965 | 3971 | ~0% | 10 | 10 | ~0% |
| 50K+500 | 10 | 23827 | 23050 | 3.26% | 60 | 62 | ~0% |
| 10K+500 | 1 | 486 | 483 | 0.62% | 8 | 8 | ~0% |
| 10K+500 | 10 | 1439 | 1153 | 19.87% | 38 | 28 | 26.32% |
| 1K+500 | 1 | 98 | 98 | ~0% | 8 | 7 | 12.50% |
| 1K+500 | 10 | 185 | 189 | ~0% | 17 | 17 | ~0% |

**Reading:** gains concentrate in the high-concurrency long-prompt case (10K+500, concurrency=10): ~19.87% TTFT / ~26.32% TPOT. Low-concurrency and short-prompt cases are neutral. The benefit is workload-specific, not universal.

## Known limitations / open items for review

- **mHC checkpoint biases** (`bias_pre` / `bias_post` / `bias_res`) and the `h_res` clamp: currently merged/omitted to match the shared `MHCPreOp` signature. **Please review whether the folded formula is equivalent to the official checkpoint** — this is the main correctness item I need confirmed.
- `_xing4_0_transpose_contiguous` custom op exists to keep `comb_mix` C-contiguous for the TileLang `mhc_post` kernel that torch.compile cannot prove. Happy to simplify if reviewers prefer.
- Pipeline parallelism is not supported in mHC mode (n_streams > 1); tensor parallelism is.

Thanks for this PR! I tested it on an NVIDIA DGX Spark (GB10, SM121, aarch64) and see garbled output that the official HF reference does not produce. Sharing in case it helps.

**Setup**
- Base image `eugr/spark-vllm:nightly-20260927` (vLLM `0.30.1rc1.dev220+g24c9772d1`, transformers 5.17.0) + this PR's diff at `091d993b` (applied cleanly). The prebuilt `xingchen-inference-vllm` image is amd64-only.
- `XingChen-AGI/Xing4.0-29B-A4B` BF16, rev `baae3c3e`, `--dtype bfloat16`, TP=1, no MTP.
- Backends selected automatically: `TRITON_MLA` (decode), `FLASH_ATTN` MLA prefill, FlashInfer CUTLASS unquantized MoE.

**Symptom:** the text is coherent at the sentence level, but words lose their middle subword. Greedy, no thinking, prompt `Explique em português, em duas frases, o que é um modelo de linguagem.`:
- vLLM: `Um **modelo de linguagem** é uma arqução matemática treada em grande quantição de texto ... palavras e frências ...`
- HF reference (`modeling_xing4_0.py`, eager attention, same tokens): `Um **modelo de linguagem** é uma arquitetura computacional treinada para compreender e gerar texto ...`

**Teacher-forced comparison.** I fed vLLM's greedy tokens through the HF reference. 51 of 60 argmax positions agree. The divergent ones are the dropped subwords, where the reference is very confident:

| pos | vLLM token | reference logp of vLLM token | reference argmax |
|---|---|---|---|
| 11 | `ção` (after `arqu`) | -26.56 | `itet` (logp -0.00) |
| 16 | `ada` (after `tre`) | -13.88 | `in` (-0.00) |
| 20 | `ição` (after `quant`) | -10.47 | `idade` (-0.03) |
| 34 | `ências` (after `fr`) | -12.14 | `ases` (-0.01) |

vLLM's own `prompt_logprobs` for these tokens are about -1.9 / -0.1 / -1.0 / -0.3. So the prefill path is affected as well, not only decode.

**Ruled out**
- **mHC ops:** `mhc_pre_tilelang` + the PR's transpose + `mhc_post_tilelang` with real layer-10 `attn_hc` weights match the official `Xing4_0HyperConnection` + `post*out + comb @ h` math (rel. err 3.4e-3; without the transpose it's 7.4e-2). So the transpose is correct. Comb logits stay in [-1, 1], so the commented-out ±30 clamp is not the cause.
- **RoPE:** config resolves to `rope_type: yarn`, and `DeepseekV2MLAAttention` switches it to `deepseek_yarn` with the mscale² softmax scaling. That matches the reference. `rope_interleave` defaults to True in the official config, which matches `is_neox_style=False`.
- **MoE backend:** `--moe-backend triton` gives the same errors (logp -1.87 / -0.08 / -1.01 / -0.38).
- **torch.compile / CUDA graphs:** `enforce_eager=True` gives the same errors.

The remaining suspect is the MLA attention path for this config (q_lora_rank 768, kv_lora_rank 512, 32 heads, qk_nope 128 / rope 64 / v 128). I haven't bisected per layer yet. Have you validated the PR on vLLM ≥0.30 or on non-Hopper GPUs? Happy to run a specific check if useful.
