# [KV Connector][Mooncake] Fail pulls from a lost prefill worker

[Upstream PR](https://github.com/vllm-project/vllm/pull/65575) · state: open · merged: False

## Original PR description



## Overview

When a prefill worker dies, the Mooncake decoder does not notice. Its pull waits up to `VLLM_MOONCAKE_ABORT_REQUEST_TIMEOUT + 60` = 540 s for P's reply while holding the request's KV blocks, because ZMQ reconnects silently instead of reporting the lost peer. D also keeps the dead worker's address cached, so the requests queued behind send their pulls there and wait another 540 s. Under load, D's KV stays full of requests that can never finish.

This PR fails a pull as soon as its connection is lost, and makes D look P up again. It is the decoder-side counterpart of #64193.

## Claims

- **P process dies:** the requests waiting on it fail within 2–4 s, instead of after 545 s plus a second 540 s wave.
- **P frozen or unreachable:** they fail once heartbeats or the existing timeouts expire, all within 102 s.
- No change for a live P and no new option. Failures follow `kv_load_failure_policy`.

## Validation

**Unit tests:** `pytest tests/v1/kv_connector/unit/test_mooncake*.py` → 750 passed, 5 skipped. 4 more cases hit Hugging Face Hub fetch errors and pass on rerun. CI does not run these files today, because the V1 KV Connectors step is disabled.
- The new test runs a ZMQ ROUTER in a subprocess that takes the pull and never answers. The ROUTER is then killed, frozen with `SIGSTOP`, or never listening. All three cases time out on main and pass in about 1 s with this PR.
- This PR also fixes `test_mooncake_stats.py::test_expired_request_bumps_counter`, which has been broken since #64193.

`pre-commit` passes.

**End to end:**
- Setup: 2× A800, DeepSeek-MoE-16B, TP=1 per side, `kv_lease_duration=30`.
- Load: 128 requests at 2.4× D's KV capacity.
- Failure: P's process group gets the signal at t≈41 s. Times are measured from the signal.

| | main, `SIGKILL` | this PR, `SIGKILL` | this PR, `SIGSTOP` |
|---|---|---|---|
| Stranded requests fail | 545 s, then 1,084 s | 2–4 s | 12–102 s |
| D's KV usage below 50% | 556 s | 5.5 s | 109 s |
| Requests ok / failed | 53 / 75 | 54 / 74 | 53 / 75 |

## Details

**Root cause**
1. D allocates blocks for a request, sends a pull to P's ZMQ ROUTER, and waits for the reply.
2. If P dies, D's DEALER silently reconnects, or keeps retrying a refused connect, so the wait runs to the 540 s timeout. The reply can never arrive: the DEALER has no routing id, so P's ROUTER drops replies addressed to a lost connection.
3. `_remote_agents` is never invalidated, so later requests pull from the same dead address.

**Fix**
- D monitors each pull socket for `EVENT_DISCONNECTED | EVENT_CONNECT_RETRIED`. On either event, it fails the pull through `_handle_failed_recv`, and drops the cached addresses of every engine that lists this worker. Later requests then query the bootstrap server again: a dead P fails at once, and a restarted P is found.
- ZMTP heartbeats (2 s / 10 s, as in `kv_offload/tiering/p2p/control/zmq.py`) make a frozen or unreachable P drop the connection too. libzmq applies them only when they are set before `connect()`, so `make_zmq_socket` takes them as arguments.

**Tradeoffs and limitations**
- A pull whose connect hits a transient network error now fails, where ZMQ would have retried it.
- Frozen P: pulls sent before D notices wait for ZMQ's 30 s handshake timeout. Requests queued after that wait for the bootstrap query to time out (3 × `VLLM_MOONCAKE_CONNECTOR_TIMEOUT`), hence the 102 s.
- Cost: one inproc monitor socket per pull, about 30 µs.

#35943 and #37745 reported this hang and were closed as not planned. No open PR covers it.
