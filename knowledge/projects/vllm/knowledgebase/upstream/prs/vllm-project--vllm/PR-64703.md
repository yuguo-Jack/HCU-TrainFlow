# [Bugfix][Benchmark] Reject incomplete completion streams

[Upstream PR](https://github.com/vllm-project/vllm/pull/64703) · state: open · merged: False

## Original PR description



## Overview

Prevent `vllm bench serve` from counting partial HTTP 200 completion streams or in-stream server errors as successful requests. Apply the completion check to `openai`/`vllm` and `openai-chat`, matching the existing Responses backend's terminal-event requirement.

## Claims

- Require streamed output and `[DONE]`, with no in-stream error, before marking a completion request successful.
- Preserve partial text and error details for diagnosis. Normal usage, token timing, tool-only Chat output, and length-limited completions remain supported.
- Document the success boundary alongside the benchmark latency definitions. This is client accounting, not a change to model generation or serving.

## Details

Previously, the Completions and Chat request functions ignored `[DONE]` and made success depend only on receiving an output chunk. A proxy's clean EOF could therefore turn partial output into a successful request. An error object after output could likewise be ignored, even when followed by `[DONE]`. These false positives entered the existing successful-request metric aggregation.

Track the terminal sentinel and retain any server error independently of token/usage parsing. Success is set only after checking both. Do not require usage or a specific finish reason: `finish_reason: "length"` plus `[DONE]` is a completed benchmark request, and an output token can legitimately render as an empty string. The stricter result may reduce reported success on nonconforming endpoints that omit `[DONE]`; this is intentional and documented.

Searched open PR titles/bodies for benchmark stream completion, `[DONE]` plus `endpoint_request_func`, premature/truncated streams, and terminal-event accounting; no equivalent open Python Completions/Chat benchmark fix was found. The merged Responses backend PR #54628 covers a different backend, whose existing behavior is retained. Open cache-metric PRs #51155/#46938 and Rust benchmark fixes do not address this Python stream-success path.
