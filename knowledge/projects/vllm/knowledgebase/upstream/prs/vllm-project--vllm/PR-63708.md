# [Bugfix][KV Offload][P2P] Never block in ZmqConnection.send()

[Upstream PR](https://github.com/vllm-project/vllm/pull/63708) · state: closed · merged: True

## Original PR description

## Purpose

Part of #63602 (gap 1).

`ControlConnection.send()` is documented as non-blocking (`control/base.py`: "ControlConnection.send() must not block"), but `ZmqConnection.send()` called `dealer.send(data)` without `NOBLOCK`, at libzmq's default `SNDHWM` and with no `SNDTIMEO`. Once the queue toward a peer that stops reading fills, the send blocks. Every caller holds the tiering manager lock: the tier-poll thread holds it for a whole round, and `OffloadingConnectorScheduler._acquire_step()` waits on it with no timeout. A blocked send therefore stalls healthy-peer servicing and the engine's next scheduler step.

This PR:

- Sends with `zmq.NOBLOCK` at an explicit `SNDHWM` (1000, unchanged from the libzmq default but no longer implicit) and raises `ConnectionError` when the queue is full. `P2PSession._do_send` already marks the connection dead on any send error, so a stalled peer is reaped and its pending work fails over to local prefill. #63664 routes the ConnectAck send through the same path.
- Bounds DEALER `LINGER` to 500 ms. While writing the test I found that, with the default (-1), closing a DEALER that still has messages queued for an unreachable peer makes `Context.destroy(linger=0)` hang forever. The context-level linger only applies to sockets that are still open. Before this change that path was rare, since a full queue blocked the sender first; now that queued-then-dead is the normal failure path, it has to be bounded.
- Leaves `ZMQ_IMMEDIATE` at its default of 0. With `IMMEDIATE=1`, a `NOBLOCK` send fails before the TCP connect completes, which would break the `ConnectMsg` sent right after `connect()`.

On the issue's policy question (fail now vs. retry on later polls): this fails now. Control messages are small, so a full queue means the peer went 1000 messages without reading while its TCP connection stayed up. That isn't short-lived backpressure, and a retry outbox would need its own bound plus ordering against the pre-ack queue.

Not a duplicate: the only open PRs referencing #63602 are #63628 (gap 4) and #63664 (gap 5). #63207 changes the DEALER monitor teardown, not `send()`.
