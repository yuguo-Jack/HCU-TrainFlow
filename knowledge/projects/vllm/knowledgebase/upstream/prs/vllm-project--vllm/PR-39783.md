# [Feature] Add Int8/FP8-quantized all-reduce

[Upstream PR](https://github.com/vllm-project/vllm/pull/39783) · state: open · merged: False

## Original PR description



## Purpose

This PR adds quantized two-shot all-reduce kernels (int8 and fp8) for tensor-parallel inference on NVIDIA GPUs (with NVLink). The kernels quantize activations before NVLink communication, reducing bandwidth by ~2x compared to bf16 all-reduce, and dequantize on the receiving side. This is implemented as a Triton kernel using PyTorch symmetric memory and building on the [Kraken](https://github.com/meta-pytorch/kraken/tree/main) library. Conceptually, our kernels are similar to [QuickReduce](https://github.com/vllm-project/vllm/pull/19744), which is available in vLLM for AMD ROCm.

#### How to enable

```bash
# Int8 quantization
VLLM_ALLREDUCE_QUANTIZATION=int8 vllm serve <model> --tensor-parallel-size <tp_degree>

# FP8 quantization
VLLM_ALLREDUCE_QUANTIZATION=fp8 vllm serve <model> --tensor-parallel-size <tp_degree>
```

Our kernels speed up all-reduce when it is bandwidth-bound, i.e., large message sizes encountered in prefill. For Llama-3.3-70B served with `tensor_parallel_size=4`, our kernels reduce TTFT by 1.03x - 1.08x for typical prefill lengths with negligible impact on accuracy (see below). When all-reduce is latency-bound (i.e., small message sizes during decoding), there is no benefit in using our kernels, and hence even if our kernels are enabled, for small message sizes the default all-reduce operation is used. Quantization is performed per group, i.e., a certain number of elements share a scaling factor. The group size is configurable in the kernel API and tuned configs are provided for group sizes 128 and 256, but the default of 256 is used in the vLLM integration.

Thanks @ilmarkov!

Regarding your questions:

- I don't think the proposed kernel can be much improved for TP=8 within the two-shot framework, but a different algorithm (e.g., ring-based quantized all-reduce) might do better. We haven't explored that.
- We have implemented a 4-bit version of our quantized all-reduce kernel, but while it gives much higher speed-up, it also results in significant accuracy degradation (e.g., GSM8K exact_match, flexible-extract drops from ~94% to ~31%). Unless we develop techniques to mitigate that drop, there is not much value in the 4-bit version.


 

- matkle · comment · 2026-04-28T15:55:05Z · [source](https://github.com/vllm-project/vllm/pull/39783#issuecomment-4336933387)

Thanks again @ilmarkov!

Yes, it is known from the literature that without special mitigation techniques 4-bit all-reduce quantization can result in clear accuracy drops (e.g., [FlashCommunication V2: Bit Splitting and Spike Reserving for Any Bit Communication](https://arxiv.org/abs/2508.03760)). We also implemented a 6-bit version of our kernel. The issue is that six bits don't align to byte boundaries, so packing/unpacking requires bit-shifting operations that add compute cost. This leads to the 6-bit kernel being only marginally faster than the 8-bit kernel, but coming with a detectable drop in accuracy.
