# [Bugfix][MRV2][LoRA] Disable KV-sharing fast prefill for LoRA batches

[Upstream PR](https://github.com/vllm-project/vllm/pull/61162) · state: closed · merged: True

## Original PR description

## Overview

MRV2 KV-sharing fast prefill reduces the batch to logits rows while LoRA mappings still describe the full batch, causing incorrect outputs or CUDA illegal memory access. Following review, this PR chooses a batch-level fallback over additional LoRA metadata and graph-capture machinery: batches containing LoRA use regular prefill, while base-only batches retain fast prefill.

## Claims

- LoRA and mixed base/LoRA batches fall back; base-only batches retain fast prefill, including after LoRA requests.
- Removes the previous compact-metadata and graph-capture changes.

## Validation

- CPU mock regression: **1 passed**, with GPU visibility disabled. Verifies LoRA fallback and subsequent base fast-prefill recovery. Worker test file: **53 passed**.
- Local real-weight E2E: CUDA illegal memory access before the fix; passes afterward. Kept outside the repository CI tests.
- Gemma4 E2B on NVIDIA GB10: compile-only, breakable PIECEWISE, and FULL_AND_PIECEWISE each completed **20/20 requests** and **20/20 full-prefill controls**, with finite logits and correct fallback routing.
- Pre-commit and `git diff --check` pass.

## Details

`FastPrefillHelper.prepare()` returns `None` when `num_active_loras > 0`, preserving full-batch attention metadata and LoRA mappings. The tradeoff is losing fast-prefill savings for the entire mixed batch.

I'm a bit concerned about the scope of the changes. KV-sharing fast prefill is a relatively specialized optimization, and I'm not sure it's worth introducing additional complexity into the general LoRA infrastructure to support it.

Would it be simpler to disable fast prefill for batches containing LoRA requests? It looks like we could do this in `FastPrefillHelper.prepare()` by checking `num_active_loras`, allowing those batches to fall back to regular prefill while preserving fast prefill for non-LoRA batches.

I'd prefer exploring this simpler approach before moving forward with the broader changes in this PR. What do you think?
