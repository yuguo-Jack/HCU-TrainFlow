# [Attention][MLA] Add NVFP4 KV cache for dense MLA with FlashInfer Cake decode

[Upstream PR](https://github.com/vllm-project/vllm/pull/63203) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Adds `--kv-cache-dtype nvfp4` for dense MLA models (DeepSeek-V3.x, Kimi-K3) on `FLASHINFER_MLA`: 352 B/token (512 latent dims NVFP4 + 64 RoPE dims FP8) vs 576 for FP8. Decode uses FlashInfer's Cake NVFP4 MLA kernel (flashinfer-ai/flashinfer#6242); writes and prefill read-back reuse the `nvfp4_ds_mla` kernels (#51724, #58744). Part of #59725.

> [!NOTE]
> **Requirements:** a FlashInfer with Cake (flashinfer-ai/flashinfer#6242) and a CUDA 13.4+ toolkit, since Cake JIT-compiles its kernels. If either is missing, `nvfp4` on dense MLA is refused at startup with an error naming the missing piece.
> - **CUDA 13.4:** vLLM's nightly CUDA 13.4 images, built for Rubin, ship `nvcc` 13.4 and include the SM100 kernels, so they run this on Blackwell.
> - **FlashInfer:** flashinfer-ai/flashinfer#6242 is merged but not yet in a release (main pins 0.7.2.post1). We will bump FlashInfer once a release has it; this PR then works with no further change.

## Claims

- **Feature:** `nvfp4` KV for dense MLA on SM100/SM103 (BF16 activations, kv_lora_rank 512, RoPE 64), including chunked prefill, prefix caching, spec decode and DCP, up to 48 query rows per request (see Limitations).
- **Capacity:** 3.28x the KV tokens of BF16 (DeepSeek-V3.1, TP4) and 1.58x of FP8 (Kimi-K3, TP8).
- **Accuracy:** Kimi-K3 matches FP8 KV on 5 tasks (|Δ| ≤ 0.72 pt). DeepSeek-V3.1 matches BF16 KV on GPQA, AA-LCR and LiveCodeBench (−0.8 pt, within noise) but loses on long-context retrieval (GraphWalks −3.3, MRCR −2.0).
- **Serving** (DeepSeek-V3.1, GB300 TP4, vs FP8 KV): 1.52x output tok/s at 8K/8K × 256 users, 1.18x at 32K/1K × 128, 0.98x at 1K/1K × 64.
- **Decode kernel** (one layer, B200, Kimi-K3 TP8 shape, vs FP8 trtllm-gen): 1.31x faster on ≥ 256K cached tokens per call (2.15x with 4 query tokens); 0.65–0.86x on small calls (≤ 16K), 0.52–1.03x when planned for `max_model_len` as in a full CUDA graph.

## Details

- **Layout:** each token is `nvfp4_ds_mla`'s 352 bytes (256 B E2M1 NoPE, 64 B E4M3 RoPE, 32 B E4M3 block scales) with two differences: the block scales are in plain order, which Cake requires, and the cache stores x / k_scale (the checkpoint KV scale, as for FP8). Cake reads the three parts as zero-copy strided views; `FlashInferMLABackend.customize_spec` sets the 352-byte page size.
- **Reuse:** `concat_and_cache_mla` and `cp_gather_and_upconvert_nvfp4_kv_cache` run the `nvfp4_ds_mla` writer and reader. A template flag picks the scale order and the k_scale use, so `nvfp4_ds_mla` compiles to the same arithmetic as before; the reader op gains `kv_cache_dtype` and `scale` arguments with defaults. The shared reader is faster than main's FP8 context gather (24.6 vs 28.7 µs at 60K tokens).
- **Decode:** the BF16 query is quantized per row to NVFP4 NoPE + FP8 RoPE, since Cake's QK runs FP4 × FP4. Spec-decode batches pass a packed query; DCP passes `cp_world`/`cp_rank` and gets the LSE.
- **48-row limit:** above 48 (token, head) rows per request, Cake's wide route zeroes V blocks with scales below 2^-3 (flashinfer-ai/flashinfer#7163), which corrupts real latents. `FlashInferMLAImpl` refuses such configs at startup (heads per GPU × DCP × max decode query tokens).
- **Other refusals:** sparse MLA still rejects plain `nvfp4` (it uses `nvfp4_ds_mla`); `nvfp4` with `--kv-cache-dtype-skip-layers` on hybrid MLA; an MLA draft whose KV dtype mixes `nvfp4` and `fp8` under FP8 prefill; Kimi-K3's RoPE MLA layers (DSpark draft) and latency-specialized decode.
- **Outside the NVFP4 path:** hybrid block-size alignment sizes MLA pages through the backend's `customize_spec`, as it does for other attention. The MLA RoPE + KV-cache fusion pass (off by default) now skips `nvfp4`, `fp8_ds_mla` and `nvfp4_ds_mla` layers: its fused kernel only writes the plain per-element layout.

**Limitations:** needs a FlashInfer release with flashinfer-ai/flashinfer#6242 (bumped once released) and a CUDA 13.4 toolkit (in vLLM's CUDA 13.4 images); at most 48 query rows per request (heads per GPU × DCP × decode query tokens: DeepSeek-V3 needs TP ≥ 4, with no spec decode or DCP at TP4); small decode calls are slower than FP8, and in eager or mixed steps a decode call costs ~155 µs of host time (FP8: 22 µs), mostly FlashInfer setup; DeepSeek-V3.1 loses on long-context retrieval; FP8 prefill with an MXFP8 `kv_b_proj` needs #56911; Kimi-K3 with MTP, or with DCP or BF16 prefill on real weights, is not validated.

**Not a duplicate:** no open or merged PR adds plain `nvfp4` KV for dense MLA or uses Cake's NVFP4 MLA decode (searched 2026-10-28). Related: #59342 (`nvfp4_ds_mla` on `FLASHINFER_MLA_SPARSE`), #55449 (changes the same hybrid-alignment function; a small merge for whichever lands second).

**Follow-ups:** bump FlashInfer once a release has flashinfer-ai/flashinfer#6242 and rerun the Cake test on a CUDA 13.4 image; cut the eager host cost (needs FlashInfer); lift the 48-row limit after flashinfer-ai/flashinfer#7163.
