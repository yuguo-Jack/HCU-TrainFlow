# [Bugfix][Compile] Fix QK-norm + RoPE fusion aborting on an unsupported head size

[Upstream PR](https://github.com/vllm-project/vllm/pull/64247) · state: open · merged: False

## Original PR description

## Overview

`QKNormRoPEFusionPass` skips unsupported attention layers inconsistently: `qk_norm_rope_fusion.py` returns from `__init__` on the first layer whose `head_size` is outside `SUPPORTED_FUSED_QK_NORM_ROPE_HEAD_DIMS = (64, 128, 256)`, while the sibling `QkNormRopeKvCacheFusionPass` skips such a layer with `continue` and keeps registering patterns for the rest.

This also overshoots the intent stated when the guard was introduced in #42749. The review there describes it as making the pass "skip pattern registration when head_size isn't supported, instead of matching/replacing and failing at runtime" — i.e. a per-layer skip. `return` instead drops registration for every layer, and a reviewer on that PR already asked whether the guard "will be restrictive to the existing qk_norm_rope usecase".

This also conflicts with the heterogeneous-geometry support added in #48671: when a model mixes head sizes across layers, one unsupported layer still disables fusion for geometries that #48671 made registrable. Gemma 4 (256 sliding / 512 full) is one instance: #53115 widens the set to include 512 but does not change the guard, so any head size outside `{64, 128, 256, 512}` still disables the whole pass.

## Claims

- Layers whose `head_size` is unsupported are skipped individually; the pass no longer returns early on the first one.
- If no layer has a supported head size, the pass still exits early (unchanged fast path).
- Supported layers fuse exactly as before; unsupported layers stay unfused (correct fallback), matching `QkNormRopeKvCacheFusionPass`.
- No change to pattern/replacement code, pass ordering, or the UUID inputs.

## Validation

New regression test with one supported (`head_size=128`) and one unsupported (`head_size=96`) attention layer. `96` is deliberately not a multiple of 64, so it cannot become a kernel specialization without relaxing the `static_assert(head_dim % 64 == 0)` in `csrc/fused_qknorm_rope_kernel.cu:166,384` — the test stays valid even after head dims like 512 are added. `matched_count` is reassigned on every pass call, so the test asserts `== 1` right after compiling the supported layer and `== 0` after compiling the unsupported one. It fails on `main` (the first assert sees `0`) and passes with the fix; verified locally on a CUDA device (RTX 5060).

    pytest -q tests/compile/passes/test_qk_norm_rope_fusion.py -k skips_unsupported_head_size
    # before fix: 1 failed (assert 0 == 1); log: "QK Norm+RoPE fusion not enabled: layer head_size=96 is not supported ..."
    # after fix:  1 passed

## Details

**Root cause.** `qk_norm_rope_fusion.py:228-237` `return`s from `__init__` on the first unsupported `head_size`, before the per-geometry registration loop, so no pattern is registered at all — including for layers whose head size the kernel supports.

**Fix.** Warn per unsupported layer, filter `_attention_geometries` to supported layers, and `return` only when the filtered set is empty. This keeps the guard's stated purpose (never match an unsupported head size, so the fused kernel is never called with one) while restoring per-layer behavior.

**Scope note (no default-path speedup claimed).** `enable_qk_norm_rope_fusion` is off by default; `docs/design/fusions.md` lists a 2-3% speedup but also states it is disabled "due to perf issues on H100" (#34391). Kernel-level work on this op is still ongoing (#37376, Helion #44010), so whether the default-off status gets re-evaluated is out of scope for this PR. Inductor `combo_kernels` also already does horizontal qk-norm/qk-rope fusion. The primary value here is code/behavior consistency, not a claimed default-path speedup; any perf benefit applies only to users who explicitly opt in on models with heterogeneous per-layer head sizes.

**Duplicate check.** Searched all PRs/issues for `SUPPORTED_FUSED_QK_NORM_ROPE_HEAD_DIMS`: only #53115 (open, widens the set to 512 + kernel) and #51934 (open, E2E test) match; neither changes the guard, and no PR proposes a per-layer `continue`. I checked #53115's diff: it only adds 512 to the whitelist and touches the kernel; the `return` is unchanged. Gemma 4's fusion work is tracked in #58841, which lists #53115 as one component; it does not touch the guard either. #48671 (merged) made the pass geometry-aware but does not filter by head size; #42749 introduced this guard, and its review thread only discusses whether to guard, not `return` vs `continue`.
