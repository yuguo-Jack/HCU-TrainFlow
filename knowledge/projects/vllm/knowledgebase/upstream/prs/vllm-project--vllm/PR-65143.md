# [Metrics][Quantization] Let quantization configs report weight bytes for MFU

[Upstream PR](https://github.com/vllm-project/vllm/pull/65143) · state: open · merged: False

## Original PR description

## Overview

The MFU/MBU estimator (`--enable-mfu-metrics`) looks up bytes per weight by quantization method name, so out-of-tree methods lose their attention and FFN estimates. This adds `QuantizationConfig.get_weight_byte_size()`, checked before the table, so a config can report its own layout. Motivated by vllm-project/vllm-metal#1183, where MLX 4-bit checkpoints are billed at bf16.

## Claims

- A quantization config that overrides `get_weight_byte_size()` keeps its attention and FFN estimates, at the size it reports.
- In-tree methods are unchanged: the default returns `None`, the table answers as before, and unknown names still raise `InvalidComponent`.

## Validation

`tests/v1/metrics/test_perf_metrics.py` adds `test_quantization_config_parser_config_reported_size`. I ran the file on the macOS CPU build of v0.32.0 with this diff applied, since `perf.py` is byte-identical between v0.32.0 and main (`5689c27`):

```text
# without the diff
E   vllm.v1.metrics.perf.InvalidComponent: Unsupported quantization method for attention metrics: out_of_tree_quant
1 failed, 72 passed

# with the diff
73 passed
```

`pre-commit run --files <changed files>` passes (ruff, typos, markdownlint, test tethering, SPDX, forbidden imports). I did not run the mypy hook, which needs the full dev environment. A scoped `mypy` on the two source files reports the same three prometheus `union-attr` errors as main and nothing new.

End to end on vllm-metal (M5 Pro, 48 GB), serving with `--enable-mfu-metrics --no-enable-prefix-caching`, with a vllm-metal branch that registers an `mlx` config reporting `bits/8 + 4/group_size` bytes per weight. Read bytes per decode step come from `vllm:estimated_read_bytes_per_gpu_total`, as (Δ for 200 tokens − Δ for 100 tokens) / 100, greedy with `ignore_eos`:

| Model | main | this PR + `mlx` config | Weights on disk |
|---|---|---|---|
| `mlx-community/Qwen3-0.6B-4bit` | 1.212 GB | 0.579 GB | 0.335 GB |
| `mlx-community/Qwen3-1.7B-4bit` | 3.461 GB | 1.436 GB | 0.968 GB |

FLOPs per step are identical on both arms (1.230e9 and 3.479e9). Most of the remaining gap to the file size is the tied LM head, which `UnembedMetrics` bills at the model dtype for every method; this PR leaves that alone. Registering the same `mlx` config without this diff drops attention and FFN, leaving only the unembedding (0.31 GB for the 0.6B model, by the estimator).

## Details

- Why a hook rather than a table entry: the table is keyed by in-tree names, and the GGUF (#39612) and bitsandbytes (#43529) entries went away when those methods moved out of tree. The plugin that owns a format knows its layout. For MLX it also depends on the checkpoint: 3, 4, 6 and 8-bit affine and the mxfp4/nvfp4 modes range from 0.44 to 1.06 bytes per weight with scales, which one constant per name cannot express.
- The two parsers now share one lookup (`_quant_weight_byte_size`) instead of repeating it.
- #58915 and #64313 (for #58742) change the same lookup for renamed in-tree methods and add a dtype fallback for unknown names. This is independent of them: whichever lands second puts the `get_weight_byte_size()` check first in the shared lookup.
- The six parser tests used duck-typed configs that only define `get_name()`. They now subclass a minimal real `QuantizationConfig`, so they inherit the default.
- Duplicate check: no open PR adds a per-config size; searched `get_weight_byte_size`, `weight_byte_size`, `_QUANT_WEIGHT_BYTE_SIZE`, and MFU/MBU quantization.
