# [Bugfix][MoE] Refuse flashinfer_cutlass MoE on SM120/SM121: silently corrupt output

[Upstream PR](https://github.com/vllm-project/vllm/pull/63473) · state: closed · merged: False

## Original PR description

## Why

`--moe-backend flashinfer_cutlass` on **SM120/SM121** serves silently corrupted output. The backend routes to FlashInfer's TRT-LLM gen fused-MoE kernels (`fused_moe_120` JIT + `trtllm::fused_moe::gemm1/gemm2`), which **FlashInfer only guarantees on SM100/SM103** — its own `tests/moe/utils.py` skips the entire suite elsewhere:

```
SKIPPED [6063] tests/moe/utils.py:299: These tests are only guaranteed to work on SM100 and SM103 GPUs.
```

Nobody hits this by accident because (a) the `auto` selector never picks this backend on SM120 (the priority list selects `DEEPGEMM_MXFP4`), and (b) the users who do set it explicitly (e.g. flashinfer#5898, same GPU class) previously died earlier at the cold-autotune NCCL timeout and never reached serving. Now that the autotune pathology is fast on current flashinfer (0.7.2), the explicit path reaches serving — and serves garbage with no error.

## Evidence (8× RTX 6000D 84G, SM120, DeepSeek-V4.1-Flash-1017, TP8+EP8, vLLM `0.32.1rc1.dev440` + flashinfer `0.7.2`)

| config | output |
|---|---|
| `auto` (→ DEEPGEMM_MXFP4) + DSpark k4 + PIECEWISE | correct (`17*19=323`, Chinese QA, tool call) |
| `flashinfer_cutlass` + DSpark k4 + PIECEWISE | garbage from token 1 (`6131 > 6131*19=...`) |
| `flashinfer_cutlass`, no spec, PIECEWISE | corrupted (`323?323*19=6137...`, looped answers) |
| `flashinfer_cutlass`, no spec, **eager** | semantically corrupted (wrong `9.11 vs 9.9` verdict, template-refusal on factual QA) |

Same weights, same engine config, single variable = MoE backend. Eager-mode corruption rules out CUDA-graph padding; no-spec rules out DSpark interaction. FlashInfer's own SM12x MXFP8×MXFP4 CuteDSL kernels pass their reference tests on the same host, so the damage is specific to the TRT-LLM gen cubin path this backend selects.

## What this PR does

`FlashInferExperts.is_supported_config` now returns `(False, reason)` when the device capability is exactly **(12, 0)** **and the activation key is `kMxfp8Dynamic`** (the MXFP4-experts × MXFP8-activations variant). Scope narrowed twice on reviewer datapoints: NVFP4 variants serve correctly on family-12 (@hclsys GB10), and MXFP4xMXFP8 is clean on SM121/GB10 with gpt-oss-20b — only cc 12.0 × MXFP8 has corruption evidence (DSV4.1-Flash-1017 on 8x RTX 6000D).

- explicit `--moe-backend flashinfer_cutlass` fails at startup with a `ValueError` naming the reason and the working alternative (`auto` → DEEPGEMM_MXFP4) instead of serving corrupted completions;
- `auto` behavior is unchanged (this backend is not in the auto priority list, so nothing new is skipped);
- SM100/SM103 (B200/B300) behavior is unchanged, and NVFP4 expert variants on SM120/SM121 keep their current backend selection (FLASHINFER_CUTLASS) unchanged.

No perf is lost on SM120: FlashInfer's own tracking notes the SM120 `fused_moe_120` path is latency-bound (flashinfer#4990), so this backend has no upside on this GPU class even where it correct.

## Testing

- new unit test `tests/kernels/moe/test_flashinfer_cutlass_moe_sm120_guard.py` (monkeypatched platform: SM120-family refusal asserts `(False, reason)`; non-12.x passthrough does not produce the refusal)
- guard verified live on the failing host: with the patch applied to the same venv, the `flashinfer_cutlass` boot aborts at startup with the new error instead of serving garbage, and the `auto` boot still comes up READY and correct.

cc flashinfer#5898 (same GPU class; the reporter's config selects exactly this backend)
