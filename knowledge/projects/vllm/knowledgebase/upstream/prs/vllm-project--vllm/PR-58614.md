# [CPU][MoE] Add AVX2 fallback for symmetric GPTQ INT4 experts

[Upstream PR](https://github.com/vllm-project/vllm/pull/58614) · state: open · merged: False

## Original PR description

## Why

On x86 CPUs without AMX, vLLM cannot select a WNA16 MoE backend for a symmetric AutoGPTQ INT4 checkpoint. On a 2-vCPU AVX2 Xeon in Colab, `Qwen/Qwen3.5-35B-A3B-GPTQ-Int4` previously stopped before generation with `NotImplementedError: No WNA16 MoE backend supports the deployment configuration.` This PR adds a functional AVX2 fallback for that configuration.

## Changes

- Build and register the existing `cpu_gemm_wna16` operator in the AVX2 extension, with AVX2 INT4 unpacking and a null-zero-point fix for symmetric GPTQ.
- Add a `CPU_VEC` WNA16 MoE backend after the existing CPU AMX backend. Repack GPTQ weights one expert at a time, then run gate/up, SiLU, down, and top-k accumulation through the vector GEMM.
- Restrict selection to symmetric AutoGPTQ INT4 without `desc_act` or zero points and to dimensions/group sizes supported by the operator. Add numerical and selection tests.

This is separate from #51546, which extends the AMX CPU route for DeepSeekV3 routing and group-size-32 checkpoints. It is also separate from #54024, which adds dynamic W4A8 on Zen CPUs. I checked the open PRs for the roadmap issue #37979 and for CPU W4A16 MoE AVX2 before submitting.

## Validation

- Full editable CPU extension build on the AVX2 Xeon completed; `torch.ops._C.cpu_gemm_wna16` was registered and exercised.
- `tests/quantization/test_moe_wna16.py` and `tests/kernels/moe/test_cpu_wna16_vector_moe.py`: **24 passed, 7 skipped**. The skips were for hardware/backend paths unavailable on this Xeon.
- Ruff check and format passed for the modified Python files; `git diff --check` passed.
- The official Qwen3.5-35B-A3B-GPTQ-Int4 checkpoint loaded from its 14 shards and generated 32 deterministic tokens in 41.67 s. A five-question GSM8K smoke test scored 3/5; this is too small to establish model accuracy.
- With the same smaller `Qwen/Qwen1.5-MoE-A2.7B-Chat-GPTQ-Int4` checkpoint and identical chat-template input token IDs, vLLM and GPTQModel matched the first 21/24 output tokens on one prompt, matched the full answer through the end-of-message token on a second prompt, and matched 24/24 tokens on a third. In a separate raw-text prompt, the eighth output token differed and a logprob probe confirmed a ranking reversal. The isolated AVX2 expert output matched explicit PyTorch dequantization with cosine similarity 0.999998629. Full-model logit equivalence is **not** claimed.
- On that smaller checkpoint and 2-vCPU VM, three warmed 24-token requests took 98.054 s with vLLM versus 27.185 s with GPTQModel. This fallback is for compatibility, not a speed improvement. The engines use different PyTorch builds and cache policies, so the ratio does not isolate kernel performance.

The full build and model runs were performed before rebasing this commit onto the current `main`. During the rebase I dropped two local GCC 13 compatibility guards because equivalent compiler-feature guards had already landed upstream. The eight remaining changed files contain the fallback and its tests.
