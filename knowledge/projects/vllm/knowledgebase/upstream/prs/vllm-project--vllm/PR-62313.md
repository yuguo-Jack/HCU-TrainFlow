# [Bugfix][KV Connector][ROCm] MoRIIO READ: skip zeroing READ destinations for mixed-precision caches

[Upstream PR](https://github.com/vllm-project/vllm/pull/62313) · state: open · merged: False

## Original PR description

## Overview

#59164 removes synchronous MoRIIO READ destinations from `new_block_ids_to_zero`, but only for models with Mamba layers. `needs_kv_cache_zeroing` is also true for mixed-precision attention caches (#47574). DeepSeek-V4 is one: its MLA cache is `uint8` (`fp8_ds_mla`) and its compressor state cache is `float32`. Its READ destinations are still zeroed on the compute stream, and the zeroing can run after the RDMA READ has landed. This PR applies the same exclusion to every READ group of models without Mamba layers.

## Claims

- Closes the race between zeroing and synchronous READ for attention-only models with mixed-precision KV caches (DeepSeek-V4) in MoRIIO READ mode.
- No change for Mamba hybrids: they still exclude only the aligned attention pages, as in #59164.
- No change for uniform-precision models: the scheduler sends no zeroing list, so the branch does not run.
- Local recompute tails, pages that are not READ destinations, and later allocations of the same pages are still zeroed.

## Details

**Flow (decode side, one step, `--async-scheduling`).**
1. The scheduler allocates the new request's blocks. DeepSeek-V4's cache is mixed precision, so they all go to `new_block_ids_to_zero`.
2. `build_connector_meta` keeps the list unchanged, because `_has_mamba` is False.
3. The V2 runner's `update_requests` queues `kv_block_zeroer.zero_block_ids` on the current stream. The stream is still running the previous step's forward, so the zeroing kernel waits behind it.
4. `pre_forward` -> `start_load_kv` posts the RDMA READs from the host. The NIC writes the pages directly and does not wait on the stream.
5. If the READs finish before the previous forward, the queued zeroing kernel then overwrites the KV it just received.

**Fix.** `build_connector_meta` subtracts the READ destinations of every group when the model has no Mamba layers. The Mamba path keeps `block_ids[:1]`, the aligned attention pages. This is the exception that `KVConnectorBase_V1.build_connector_meta` already documents for synchronous READ connectors.

**Why skipping the zeroing is safe here.**
- MoRIIO READ copies `block_len` bytes per block (`compute_block_transfer_offsets`), so each destination page becomes a byte copy of the prefiller's page. The prefiller zeroed that page when it allocated it.
- The worker awaits every READ before the forward (`_await_reads_issued_this_step`; #60808 makes this unconditional), so no kernel reads a destination page before the READ has landed.
- `_reqs_need_recv` holds only the aligned destination blocks. The decode-side recompute tail is not a READ destination, so it stays in the zeroing list (covered by the existing test).

**Alternative considered.** A stream sync before posting READs (what our internal build does) also closes the race. It makes the host wait for the previous forward on every step that receives KV, so the READs cannot overlap it. The exclusion needs no synchronization.

**Related PRs.**
- #60867 (MoRIIO hybrid READ for several attention groups) changes the same set comprehension for the Mamba path to `block_ids[: len(self._attn_group_ids)]` and keeps the `_has_mamba` condition. The two compose. Whichever lands second needs a one-line rebase.
- #54301 and the async READ RFC #49643 avoid the race differently: async loads already pass `skip_zeroing_group_ids` (#59504).

**Duplicate check.** I searched open PRs for `moriio zeroing`, `moriio zero`, `new_block_ids_to_zero`, `READ destinations zeroing` and `moriio mixed precision`, and checked the diffs of #60867, #60808, #61726 and #54301. Only #60867 touches this exclusion, and only for Mamba hybrids.
