# [Spec Decode][MRV2] Speculative round contract for custom speculators

[Upstream PR](https://github.com/vllm-project/vllm/pull/64844) · state: open · merged: False

## Original PR description



## Overview

This PR lets a custom speculator (added in #63205) decide the whole speculative round on the V2 model runner: what the target verifies, which rows are accepted, how many drafts the next step takes and how many requests run. vLLM keeps execution, memory, CUDA graphs and parallelism, and checks every plan against what the model's layers can verify.

Builds on #63205. Replaces #62962 and #62963.

## Claims

- A speculator plugin can own the verify plan (a chain, a tree, or rows with a custom attention mask), the accepted path, a per-step candidate budget and an admission cap. It does this through optional hooks on `BaseSpeculator` and `SpeculatorConfig`, and it can supply its own verify and commit kernels by key.
- A speculator that overrides nothing runs as it does on main. Every hook defaults to the current behaviour, chains keep main's conv, GDN and SSU kernels (bitwise-identical outputs on B300), and on an earlier version of this series stock EAGLE-3 measured 0.997x to 1.004x of the same build without it, with identical greedy outputs at C1.
- At startup vLLM asks each layer what it can verify and lowers the plan kind (mask, tree, chain) to what every layer verifies, with one log line per limit. A speculator that must not run lower raises in `adapt_resources`.
- GDN and Mamba2 hybrids verify trees. With recurrent layers, a request holds recurrent-state blocks only for the drafts it verifies that step, so a budget that drops drafts under load frees blocks for more running requests.
- FlexAttention verifies custom masks and trees on full and sliding-window attention.

## Details

#63205 gives a plugin a place to register a speculator: a `SpeculatorConfig` and a `BaseSpeculator`. The round itself still runs one way, a chain of K drafts with the same K every step. Tree speculators, per-step budgets and admission control each need changes inside the model runner and the scheduler today. This PR adds the round as optional hooks with chain defaults:

```text
startup   SpeculatorConfig.resources(max_num_seqs) -> SpecResources
          each worker reports what its layers verify, the engine lowers the plan kind
          SpeculatorConfig.adapt_resources(declared, capabilities) -> SpecResources
per step  scheduler  SpeculatorConfig.admit_limit(BudgetView) -> int
                     SpeculatorConfig.candidate_budget(BudgetView) -> int   (1 skips the drafter)
          worker     BaseSpeculator.plan(PlanInputs) -> (VerifyPlan, PlanBound) | None
                     target forward, accept(plan, VerifyOutput, sampler) -> AcceptResult | None
                     commit the accepted path (KV, recurrent state, conv window)
                     observe_step(StepObservation), then propose(...)
```

`None` from `plan` or `accept` means vLLM runs that part of the round as it does on main. The Dynamic SD schedule (`num_speculative_tokens_per_batch_size`) becomes the default `candidate_budget`, with the same schedule. `docs/features/speculative_decoding/round_contract.md` documents every hook.

| The speculator owns | vLLM owns |
| --- | --- |
| The rows the target verifies: chain, tree or mask (`plan`) | The target forward, its CUDA graphs and its parallelism |
| Which rows are accepted (`accept`) | KV cache and recurrent-state memory, sized at startup |
| The candidate budget for the next step (`candidate_budget`) | Scheduling, preemption and the waiting queue |
| A cap on running requests (`admit_limit`) | Committing the accepted path to the KV cache and recurrent state |
| Its drafting (`propose`) and policy such as tree width | What each layer can verify |
| Optional kernels by key (`spec_kernel_providers`) | The in-tree kernel for every key a speculator does not provide |

Plan kinds are lowered once at startup, so memory and CUDA graphs are sized once. Plan buffers belong to the speculator and keep their addresses, so captured graphs replay them. Kernels are keyed by layer kind and op: a provider can replace one key, and a missing or declining kernel lowers that layer to chains.

How to review, commit by commit:

1. Start with commit 1 (the types in `round.py` and the chain plan, no behaviour change) and the docs page in commit 12.
2. Commits 2 and 3 hold the tree layout, the greedy tree walk, the KV and recurrent-state commit, and the GDN and Mamba2 tree kernels, which take a parent per row. Chains keep main's kernels unchanged. The runner side of the round lives in `spec_decode/round_runner.py` (`SpecRound`), so `model_runner.py` grows by 174 lines.
3. Commits 4 to 6 add `accept`, `observe_step` and `candidate_budget`.
4. Commit 7 is the only change to the KV cache manager and the hybrid allocator, kept separate for the owner of `kv_cache_manager.py` and `single_type_kv_cache_manager.py`. It is on only for models with a Mamba group on the V2 runner without pipeline parallelism, a KV connector or adaptive verification.
5. Commit 8 adds `admit_limit`. The scheduler calls it only when the speculator config overrides it.
6. Commit 9 adds the per-layer capabilities (`AttentionMetadataBuilder.spec_verify_limit`, default `"chain"`) and the downgrade. Commit 10 adds the kernel registry and commit 11 the masks and FlexAttention.

Limits:

- A plan has at most 64 rows per request.
- Trees and masks run as chains under pipeline parallelism, prefill and decode context parallelism, batch-sharded sampling and micro-batching. A step with a prefill, a prefix-reading logits processor or structured output verifies chains.
- About 19 small plan, accept and commit launches per tree round run outside the CUDA graph, as the rest of the V2 runner's input preparation and sampling do. Fusing or capturing them is follow-up work.
- Overlapping drafting with the verify forward is not part of this PR.
- Policy (tree shape and width, budgets, admission) belongs to the speculator. vLLM ships the chain defaults.

I pushed a follow-up fix, `[Mamba] Capture full decode graphs for any uniform query length up to K+1`.

A speculator can declare decode shapes below 1 + K, for example a tree's chain fallback, and the CUDA graph manager captures one decode graph per declared shape. The Mamba capture builder asserted that the length equals 1 + K, so a Mamba2 hybrid such as Nemotron-H failed at startup with such a speculator. The decode path already takes any per-request length up to 1 + K, so the fix keeps only the existing upper bound, as GDN, short-conv and linear attention already do. Chain configs capture only 1 + K, as before. A builder test captures lengths 1, 2 and 4 with K = 3; lengths 1 and 2 fail without the fix.

With this change, a Nemotron TP4 tree speculator starts and serves 880 prompts. On one B300 (measured before the main merge, which does not touch these files), the 13 GPU test files listed in the description pass with the same counts (770 passed, 2 skipped) and `test_mamba_metadata_builder.py` passes 4 tests. `pre-commit`, mypy included, passes.
