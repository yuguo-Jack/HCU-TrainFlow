# [EPLB] Add lifecycle hooks for out-of-tree devices

[Upstream PR](https://github.com/vllm-project/vllm/pull/49700) · state: open · merged: False

## Original PR description

## Overview

Expose narrow EPLB lifecycle hooks so out-of-tree devices can reuse upstream load collection, expert migration, and map installation. This stage preserves the existing policy interface and tensor result; it does not introduce a stateful policy framework. Related discussion: #49702; MoE construction is handled separately in #51006.

## Claims

- Synchronous and asynchronous planning call `EplbState.rebalance_experts()` with the model state and existing policy arguments. Aggregate loads remain CPU `[layers, experts]` tensors, and the result remains a CPU integer placement tensor.
- Platforms select and validate EPLB configuration. Built-in selector aliases remain `Literal` types, while config fields explicitly allow `| str` extensions. Built-in defaults, XPU/XCCL selection, and async communicator restrictions are preserved.
- Factories select device-specific layer state, policy, and model communicators. Without a layer mapping callback, the router preserves the existing platform implementation, including the identity fallback outside CUDA/ROCm/XPU. `on_layer_committed(model_state, layer_idx)` runs after weights and maps are installed and before the async receive buffer is acknowledged.
- A drained async worker can stop without fabricating a device event. Pending transfers and join timeouts are reported, and normal worker exit synchronizes its stream.

`AbstractEplbPolicy`, `DefaultEplbPolicy`, the policy-registry consistency assertion, `AsyncEplbLayerResult`, and the original algorithm tests are unchanged from the upstream base. No `EplbPlan`, `EplbPolicyState`, `EplbRebalanceContext`, or `EplbTopology` API is added.

## Validation

CPU regressions at `5e43cec36a`; the NPU diagnostics below were run at `93e7d0f535`:

```bash
VLLM_TARGET_DEVICE=cpu VLLM_PLUGINS='' HF_HUB_OFFLINE=1 \
GLOO_SOCKET_IFNAME=lo0 .venv/bin/python -m pytest -q --tb=short \
  tests/distributed/test_eplb_extension_hooks.py \
  tests/distributed/test_eplb_algo.py \
  tests/distributed/test_eplb_migration_scheduler.py \
  tests/distributed/test_eplb_utils.py
```

- **67 passed, 2 accelerator-dependent cases skipped** on CPU. `lo0` is the macOS loopback interface; use the local interface on other hosts.
- The router fallback regression produced **1 failed, 1 passed** against `93e7d0f535`: without a callback, the non-CUDA/ROCm/XPU path raised instead of returning the IDs unchanged. The corrected router suite covers both callback dispatch and the platform's default behavior, including load recording on CUDA/ROCm/XPU. Router source changes select the NVIDIA and AMD EPLB CI steps.
- Regressions cover the unchanged policy result through both planning paths, platform names and defaults, communicator compatibility, commit-before-acknowledgement ordering, callback failures, router metadata, and worker shutdown. An `LLM` entry-point regression rejects invalid configuration before weight loading.
- Tests specific to the deferred policy-state framework were removed; the original algorithm tests were restored unchanged. The retained tests are selected by the EPLB Buildkite step and AMD mirror.
- Applicable pre-commit hooks passed for all touched files, including Ruff, formatting, mypy 3.11, configuration validation, CI test tethering, and sign-off. `git diff --check` passed.

Real two-rank Ascend A3 diagnostic validation used a small PyTorch model and a minimal out-of-tree platform/layer-state consumer, HCCL collectives, and Gloo-staged expert transfers. Two models with three total layers exercised six requested combinations of sync/async planning, default/forced cross-rank placement, and migration batching. With graph-input reset explicitly completed before replay in the external harness, all six configurations passed ten cycles each: migrated weights, exact outputs, live graph maps/counts, per-model commit callbacks before acknowledgement, and shutdown.

**Unresolved hardware qualification:** Two earlier runs without that graph-input preparation barrier failed load-count assertions in different async configurations, while the parent `b149591df6` passed the original harness, including ten cycles per configuration. The synchronized diagnostic is consistent with a timing dependency but does not establish its cause or qualify the unsynchronized graph path. No production synchronization or speculative workaround was added, and full hardware success is not claimed.

The diagnostic used real `torch_npu` operations with no kernel mocks. The isolated runtime's incompatible Triton installation was disabled; vLLM native custom operators and checkpoint-backed serving were not exercised. Earlier checkpoint results at `9aa1912195` used the superseded policy contract and are historical evidence only. CUDA/ROCm/XPU runtime, HIXL, multi-node, and current-head checkpoint coverage remain outstanding.

## Details

This is an independently usable first stage, not a claim that every downstream EPLB patch is removed. Stateful policy histories, temporal load bins, STAIR-specific planning metadata, explicit transfer sources, and initial-placement policy remain outside this PR. A later policy-contract proposal should demonstrate those requirements with a real downstream adapter.

`EPLBConfig` enforces field types and numeric bounds. For enabled EPLB, the platform hook selects the default communicator and validates names and combinations. Standalone config construction does not validate selector names or communicator compatibility. Downstream overrides own validation of their extensions.

The existing communicator, generic streams, migration scheduler, and workspace commit path retain execution ownership. Device callbacks receive model identity without adding generic policy state to `EplbModelState`. Stop requires every rank to drain transfers and retain communicator resources until it succeeds. Plugin documentation describes these boundaries.

GitHub currently reports conflicts against main; rebasing and maintainer hardware validation remain pending. This updates the existing PR rather than opening a duplicate. AI assistance was used for implementation, review, validation scripts, and this description. Human line-by-line review and validation confirmation remain required before merge.
