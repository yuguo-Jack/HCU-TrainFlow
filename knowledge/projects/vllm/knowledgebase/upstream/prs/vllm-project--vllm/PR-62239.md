# [ROCm][Perf] MXFP8 emulation: run the dequantized weight through the platform GEMM

[Upstream PR](https://github.com/vllm-project/vllm/pull/62239) · state: open · merged: False

## Original PR description

## Purpose

Since #56560, `EmulationMxfp8LinearKernel` dequantizes MXFP8 weights to BF16 once at load time, but `apply_weights` still calls `F.linear` directly. That skips the platform's unquantized-GEMM dispatch, which a BF16 checkpoint of the same layer would use.

On ROCm, that dispatch (`rocm_unquantized_gemm`) picks the skinny wvSplitK / LLMM1 kernels at decode batch sizes, while `F.linear` runs the 1-row GEMM on large hipBLASLt tiles. This PR calls `dispatch_unquantized_gemm()` instead. On CUDA and XPU the dispatcher returns `F.linear` for the default backend, so nothing changes there.

This affects every MXFP8 linear on ROCm GPUs without native MX (all but gfx95x), for example the DeepSeek-V4.1 attention and shared-expert linears.

## Duplicate-work check

- #56751 (closed) added a skinny dispatch table for DeepSeek-V4.1 on SM100 only.
- #48427 and #59782 / #60169 / #60384 / #62088 add requantized or native MXFP8 paths on CDNA; none changes the emulation path.
- #51511 proposes disabling skinny GEMM on gfx1151. The results below are on gfx1151 with skinny GEMM on, and the output matches `F.linear`.

## Test Plan

```
pytest tests/kernels/test_minimax_m3_amd_ops.py -k mxfp8_linear_emulation
```

The existing `EmulationMxfp8LinearKernel` test now also runs 1 token, which takes wvSplitK on ROCm; 7 tokens takes hipBLASLt as before.

End-to-end: `deepseek-ai/DeepSeek-V4.1-Flash-1017` on 4x Strix Halo (gfx1151), TP=4 over Ray, llama-benchy pp2048 / tg128, mirrored A B B A in one server instance.
