# [ROCm][Perf] Fold Q fp8 quantization into QkNormRopeKvCacheFusionPass

[Upstream PR](https://github.com/vllm-project/vllm/pull/59035) · state: open · merged: False

## Original PR description

## Purpose

Fixes #59022 

Fold the per-tensor Q→fp8 quantization into the AITER fused QK-norm+RoPE+KVcache kernel, so `QkNormRopeKvCacheFusionPass` no longer emits a separate `scaled_quant` per attention layer on the fp8-attention path. The fused kernel already fp8-quantizes K/V into the cache but returned Q in bf16, so the pass re-quantized Q separately (`_quantize_query` → `rocm_aiter_per_tensor_quant`). With the kernel emitting fp8 Q directly (ROCm/aiter#5914), the per-tensor path consumes it and drops that op.

Scope: RoPE + static per-tensor only. MRoPE and the per-head/group static-quant form keep the separate quantization.

**Stacked on #53918** (this edits the `quant_query` path #53918 introduces) and **depends on ROCm/aiter#5914** (the kernel change). Until #53918 merges, the commit/file list here includes #53918's commits; the q_out_fp8 change is the single commit `d809c50`. Relates to #58841.

## Test Plan

- AITER op-test (ROCm/aiter#5914): kernel fp8 Q vs a torch fp8 quant of the same Q by the same scale.
- vLLM `test_qk_norm_rope_kvcache_fusion_quark_scalar_query_scale` (added): tp2 = per-tensor (folded), tp4/tp8 = per-head (separate quant remains).
- E2E on `RedHatAI/gemma-4-31B-it-FP8-block`, `ROCM_AITER_UNIFIED_ATTN`, `--kv-cache-dtype fp8`, `--compilation-config '{"use_inductor_graph_partition": true, "pass_config": {"fuse_qk_norm_rope_kvcache": true, "rope_kvcache_fusion_max_token_num": 16384}}'`; trace + gsm8k.

## Test Result

- **Trace**: the per-layer `scaled_quant<bf16,fp8>` (separate Q quant) drops from **12000 → 0**; the fused `fused_mrope_rms_kv_kernel` (head_dim 256 + 512) still fires; **60/60** layers fused; 0 `reshape_and_cache`, 0 standalone rotary.
- **Accuracy**: gsm8k strict **0.712** (limit 500) vs 0.738 for the prior fused build — within gsm8k@500 run/config noise (~0.02 SE; this run used `use_inductor_graph_partition`, the baseline used `splitting_ops: []`). The AITER op-test shows the kernel's fp8 Q is **bit-identical** to the previous separate quant, so no numerical change is expected (a scale-convention error would collapse accuracy, not land at 0.712).
- **Known gap**: the fusion unit test currently fails at `check_before_ops` (`rocm_aiter_triton_rotary_embedding` / `_C::rotary_embedding` not in pre-pass graph) — **pre-existing** staleness from the #58838 RoPE→IR migration in this stacked env (the existing `test_qk_norm_rope_kvcache_fusion` fails identically); `ops_in_model_before` needs updating for the IR rope op. Independent of this change.
