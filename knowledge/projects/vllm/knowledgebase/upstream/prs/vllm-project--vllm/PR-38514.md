# [Core] Priority-based KV-cache retention via kv.retain hints (#37003)

[Upstream PR](https://github.com/vllm-project/vllm/pull/38514) · state: open · merged: False

## Original PR description

## Purpose

Implements the Context-Aware KV-Cache Retention API proposed in #37003 on top of the merged KV-hints request envelope (#53423, RFC #53421): a `kv.retain` action lets an orchestrator that knows the workflow (an agent runtime, a router) tell vLLM which token ranges of a request's prompt it will reuse soon, so the prefix cache keeps them while the session waits on a tool call, instead of evicting them in pure LRU order.

This is a rewrite of the earlier revision of this PR, cut down to what the replay benchmarks validated: full-attention models only, one policy knob (the directive's priority), no sliding-window/Mamba handling, no measurement-only code. Ten commits, each reviewable on its own.

**Not a duplicate of**
- #59714 / RFC #59708 (@karen-sy): same envelope, a `vllm.set_priority` action executed by a scheduler-side dispatcher at request completion. That PR is a draft with the contract still open; this PR applies ranges in the block pool when blocks are cached and is meant to be aligned with that contract (action name/fields) once it lands. I will do the alignment on this PR.
- #47837: eviction order driven by the *scheduling* priority of requests, no per-range hints.
- #48704: retention policies for the tiered/offloaded store, not the GPU prefix cache.

## Design

Wire format (top-level `kv_hints` on `/v1/chat/completions`, validated with a 400 on malformed input):

```json
{"kv_hints": {"protocol_version": "0.1", "message_id": "t1",
  "actions": [{"action_id": "t1:retain", "action_type": "kv.retain", "action_version": "1.0",
    "payload": {"scope": "session-id", "directives": [
      {"start": 0,    "end": 1200, "priority": 80, "duration": 86410},
      {"start": 1200, "end": null, "priority": 40, "duration": 86410}]}}]}}
```

- A directive protects the token range `[start, end)` of the prompt (`end: null` = to the end of the prompt, `covers_output: true` = the generated tail) with a priority 1–100 for `duration` seconds; priority 0 releases. Priorities must be non-increasing along the token axis (a later block is useless without its prefix).
- Protection is **soft**: the LRU free list is drained first, then protected blocks go lowest priority first; an expired protection is demoted to the LRU tail, not evicted. Hinted requests change the eviction *order*, never the capacity.
- A block keeps one hold per `scope` and is protected at the strongest hold; a scope only edits its own hold. `scope` is not authenticated (see `docs/usage/security.md`).
- With no hints the pool runs the upstream LRU path: retention bookkeeping starts with the first `kv.retain` of the process.

Commits:
1. `[Core] Add the kv.retain KV-hint action schema and parser` — `vllm/v1/kv_hints/retain.py`, strict (frontend) / lenient (engine) parsing, caps on actions and directives.
2. `[Frontend] Accept a kv_hints envelope on chat completions` — `ChatCompletionRequest.kv_hints`, validated, forwarded as request metadata; security note.
3. `[V1][Core] Priority-based KV-cache eviction driven by kv.retain hints` — `PriorityEvictionQueue` sidecar (lazy heap, expiry index) wired into `BlockPool`.
4. `[V1][Core] Drop a stale free copy when its hash is cached again` — an unreachable old copy no longer sits protected.
5. `[V1][Core] Keep one retention hold per scope and protect at the maximum` — per-scope holds; a scope lowering a block lowers its holds below it; orphaned descendants are reaped when the last copy of a hash leaves.
6. `[V1][Core] Link blocks into the hash chain only for full-attention KV groups` — the chain rules assume a lookup walks the chain from the first block; sliding-window and Mamba groups are left alone (keeps `test_hybrid_per_group_hit_divergence_with_connector` green).
7. `[V1][Core] Keep the hint-free path at upstream cost until the first kv.retain hint` — see the microbenchmark below.
8. `[V1][Core] Test that the hint-free path leaves no retention state` — manager-level invariants (see Test Result).
9. `[V1][Core] Apply kv.retain hints to adopted cache hits` — a request that only reuses cached blocks (no new full block) now applies its set/renew/lower/release too. Found and fixed by @RichealYoung.
10. `[V1][Core] Carry live holds over when a duplicate copy is replaced` — recomputing the last block of a fully cached prompt no longer drops other scopes' unexpired holds on that content. Found and fixed by @RichealYoung.

Out of scope here: hybrid/sliding-window specific retention (a follow-up), gRPC/Responses endpoints.

- RichealYoung · comment · 2026-10-19T13:40:45Z · [source](https://github.com/vllm-project/vllm/pull/38514#issuecomment-6268625653)

I found a case where `kv.retain` updates are skipped for reused cache blocks. I've attached a proposed fix with regression tests.

**Reproducer**

For FA with a block size of 16:

1. A request populates a 64-token cached prefix and sets a hold with `scope="owner"`, `priority=50`, and `duration=30`.
2. A second request has the same 64-token prefix plus 2 additional tokens, and sends `priority=0` for the same scope.
3. It reuses the 64 cached tokens but finishes without publishing another full block. The old holds remain instead of being released.

Setting, renewing, and lowering holds are affected as well. If the continuation publishes a new full block, the existing publication hook applies the hints, so whether the update takes effect depends on crossing a block boundary.

**Proposed fix**

Apply the request's hints to adopted local FA/MLA full-block cache hits after successful allocation. This reuses the existing retention handler, preserving scope handling, TTL calculation, and descendant handling.

Failed admission does not update holds, and ordinary decode steps do not trigger this additional update. The existing publication path remains unchanged. This does not extend retention support to SWA/Mamba or partial checkpoints.

**Tests**

The patch adds `TestRetentionOnAdoptedCacheHits` to `tests/v1/core/test_priority_eviction.py`, covering set/renew/lower/release, failed admission, and decode without repeated renewal.

With only these tests added to the original implementation, five fail and one passes; with the fix, all six pass. The 262 existing tests in `test_priority_eviction.py` and `test_prefix_caching.py` also pass on both implementations. These were isolated component test runs, not full CI or real-model serving validation.

The attached patch is against `92b4241b1493d682e01ebd857110ce98a7781e02`. Does applying hints when cached blocks are adopted match your intended semantics? Happy to open a PR against your branch if that would be easier to review.

- RichealYoung · comment · 2026-10-19T15:38:40Z · [source](https://github.com/vllm-project/vllm/pull/38514#issuecomment-6271103197)

I noticed another case while testing this PR.

Suppose session A caches 64 tokens and asks to retain them for 100 seconds. Shortly afterward, session B sends the same 64 tokens without any retention hints. With 16-token blocks, vLLM reuses the first 48 tokens and recomputes the last block to get logits.

When that new block is cached, `_drop_stale_copies` removes the old copy, including A’s hold. The new copy can still serve a cache hit, but A’s protection is gone even though it hasn’t expired. If B sends 65 tokens instead, it reuses all four original blocks and A’s holds remain.

It looks like the cleanup assumes a duplicate was recomputed because the old prefix chain was broken, but normal last-block recomputation can also trigger it.

I’ve attached a small patch that carries the old copy’s unexpired holds over to the replacement before removing it. It keeps their original expiry times, then lets the current request’s hints apply as usual, so an explicit downgrade or release still works.
