# [Bugfix][Rust Frontend] Support batch prompts in completions

[Upstream PR](https://github.com/vllm-project/vllm/pull/62495) · state: open · merged: False

## Original PR description

## Overview

Fixes #62460: with `VLLM_USE_RUST_FRONTEND=1`, `/v1/completions` currently returns HTTP 400 for `prompt: ["Hello", "World"]`. This change accepts homogeneous text/token-ID batches while preserving single-prompt inputs and `n=1`.

## Claims

- Assigns choices in prompt order and sums usage across batch items.
- Streams corrected choice indices, one final aggregate usage event when requested, and one `[DONE]`; unfinished generations are cancelled on errors or disconnects.
- Matches Python's empty-array rejection and streaming error termination for invalid batch items.
- Handles echoed single-token prompt logprobs, including the unscored first token, in full responses and streams.

```bash
# Before: HTTP 400. After: HTTP 200, choice indices 0/1 and summed usage.
# Also tested: token-ID batches, stream=true, echo/logprobs and invalid inputs.
```

## Details

A route-owned, nonrecursive input union expands batches before existing request preparation and generation. The shared single-prompt `vllm_text::Prompt`, scheduler and model runner are unchanged.

The route rejects `[]` before opening a stream. Invalid batch items use Python-style SSE errors after HTTP 200 for streaming requests; nonstreaming requests return an error response. Existing guards clean up unfinished requests. Single-token prompt scores may legitimately be absent from engine output; echoed responses reuse the existing first-token null-logprob fallback instead of returning 500. Streaming echo collects the prompt scores needed to render the same logprobs contract.

The batch aggregator drops sibling streams before yielding an error, so cancellation does not depend on the client consuming another event. Batch fan-out still retains per-prompt state and submits all prompts before response consumption; this change adds no new admission limit or concurrency scheduler and makes no large-batch memory-bound guarantee.

Scope stays at `n=1`. Rust retains strict token-ID parsing; Python's coercion of booleans, integer-valued floats and numeric strings is deliberately unchanged. Those three input categories in both streaming modes account for the six remaining status differences in the matrix. Existing error-code naming, optional metadata and chunk boundaries are not made byte-identical.

Production additions exceed 250 lines because the batch contract requires submission, ordered collection, indexed multiplexing, usage aggregation and cleanup. Existing conversion/serialization are reused; no dependency or shared architecture changes. New tests extend the existing route suite covered by Rust workspace CI.

Duplicate checks found no existing PR implementing this fix. Related #62434 validates unsupported fields, while #58914 adds multiple choices for a single prompt; neither implements batch prompt inputs. Their overlapping files may require coordination if merged first.
