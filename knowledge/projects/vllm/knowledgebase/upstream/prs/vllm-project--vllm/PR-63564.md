# [Bugfix][MRV2] Bound prompt-logprobs chunks by max_num_reqs

[Upstream PR](https://github.com/vllm-project/vllm/pull/63564) · state: open · merged: False

## Original PR description



## Overview

Fixes #63563. Model Runner V2 computes prompt-logprobs logits in fixed 1,024-row chunks, while `profile_run` only
measures one logits row per request. This caps the chunk at `max_num_reqs` rows, so the transient stays within what the
memory profile saw.

## Claims

- With `max_num_seqs < 1024`, a prompt-logprobs step no longer allocates more logits than the profiled sampler step.
- Prompt logprobs are unchanged (rows are independent).
- No change when `max_num_seqs >= 1024`, and none for requests without prompt logprobs.

## Validation

CPU (x86, torch 2.14.0+cpu, `VLLM_TARGET_DEVICE=cpu`):

```
pytest tests/v1/worker/test_gpu_prompt_logprob_chunking.py
main:      1 failed   assert max(rows_seen) <= max_num_reqs  ->  assert 10 <= 4
this PR:   1 passed
```

The test runs a real `PromptLogprobsWorker` and `InputBatch` with `max_num_reqs=4` and a 10-token prompt, records the
rows of every `compute_logits` call, and checks the result equals a single-chunk computation exactly.
`pre-commit run --files <changed files>`: all hooks pass.

GPU (4 × Intel Arc Pro B70, torch 2.14.0+xpu, vllm-xpu-kernels 0.1.15.4): Qwen3.6-35B-A3B BF16, TP 4,
`--enforce-eager --max-num-seqs 8 --max-num-batched-tokens 4096 --gpu-memory-utilization 0.88`, Model Runner V2.
One completion request with a 4,000-token prompt, `prompt_logprobs=20`, `max_tokens=1`, after one short warm-up request.
Device memory is the sum of the engine processes' `drm-total-vram0` (xe fdinfo), per rank.

| | main | this PR | this PR, same request without prompt_logprobs |
|---|---|---|---|
| device memory added by the request | +2.36 GiB | +0.85 GiB | +0.47 GiB |
| host MemAvailable after the request | −11.4 GiB | −3.4 GiB | −1.5 GiB |
| request time | 4.21 s | 4.69 s | 1.58 s |

On main the prompt-logprobs work adds ~1.9 GiB per rank over the control, in line with one 1,024-row chunk; with the
bound it adds ~0.4 GiB. Prompt logprobs and sampled logprobs on a short prompt are identical between main and this PR
(exact comparison).

## Details

`PromptLogprobsWorker` computes logits for prompt rows in chunks of `CHUNK_SIZE = 1024`, then full-vocabulary scores in
float32: at a 248K vocabulary about 0.47 GiB of bf16 logits plus 0.95 GiB of scores per chunk. `profile_run` runs
`_dummy_sampler_run`, whose logits have one row per request, so unless the profiled forward pass happens to peak higher,
the KV cache is sized without the chunk. With little headroom after the KV pool the step exceeds the budget (on CUDA this would
surface as an OOM; on XPU, where it was observed, the driver backs it with host memory and does not release it).

The chunk is now `min(1024, max_num_reqs)`, applied in both prompt-logprobs paths (`compute_prompt_logprobs` and
`compute_prompt_token_id_logprobs`). `compute_prompt_logprobs_with_chunking` takes the chunk size as an argument,
defaulting to `CHUNK_SIZE`.

Tradeoff: with a small `max_num_seqs`, a long prompt with prompt logprobs needs more `compute_logits` calls (each an
lm_head matmul plus, under TP, an all-gather): +0.48 s on the 4,000-token request above. At `max_num_seqs=1` this is one `compute_logits` call per prompt token.
Requests without prompt logprobs are not affected.

Not covered: the V1 runner has the same unprofiled transient, addressed by the open PRs #52054 / #45327. The float32 score tensor of a
sampling step that returns logprobs for every request is also not profiled (`NOTE(woosuk)` in `_dummy_sampler_run`);
that is a separate question.

Why this is not a duplicate: searched open and merged PRs on 2026-10-24 for "prompt_logprobs chunk", "prompt logprobs
memory", "MRV2 prompt logprobs" and "prompt_logprob CHUNK_SIZE". #52054 and #45327 change the V1 runner only.
#53842, #54575, #61679, #61693, #53267 and #62049 edit `vllm/v1/worker/gpu/sample/prompt_logprob.py` for other reasons
(LoRA mapping, distributed prompt logprobs, scored-row selection, prompt end, fused LM head); none changes the chunk
size. Whichever lands second needs a small rebase.
