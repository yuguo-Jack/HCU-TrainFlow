# [Perf][Frontend] Count prompt-closed reasoning tokens incrementally for continuous usage stats

[Upstream PR](https://github.com/vllm-project/vllm/pull/63153) · state: open · merged: False

## Original PR description



## Overview



With `stream_options.continuous_usage_stats=true`, chat streaming counts reasoning tokens over the whole output after every delta. For engine-based reasoning parsers, when the prompt already closes reasoning (thinking disabled or `continue_final_message`), each of those counts re-decodes and re-parses the entire output. That makes per-delta frontend cost linear and total cost quadratic in output length. This PR makes that count incremental.

This matters in production because gateways and routers often force `continuous_usage_stats` on every stream, for per-request token accounting and token rate limiting.

Follows #56067, which removed the per-delta recount for non-continuous streams and kept it for continuous usage. Complements #61379, which removes the per-delta `tuple()` copy in `serving.py` and notes that "the parser's full-scan recount itself remains quadratic and it not changed here.

## Claims



- `ParserEngineReasoningAdapter.count_reasoning_tokens` no longer re-parses the full output when called again with an extension of the previous token ids. It feeds only the new tokens to the counting engine.
- For a 30K-token streamed output with a prompt-closed reasoning block (GLM-5.3 parser), the frontend cost of the per-delta count drops from 20.9 ms to 0.28 ms per delta at the end of the stream. Total cost drops from 54.8 s to 0.88 s, against ~50 s of generation.
- Counts match the live streaming count. Once the output has left reasoning, the final count equals a single-pass parse; new tests cover growing prefixes with multi-byte characters.

<summary>Benchmark script</summary>

```python
import sys
import time

from vllm.entrypoints.openai.chat_completion.protocol import ChatCompletionRequest
from vllm.parser.parser_manager import ParserManager
from vllm.tokenizers import get_tokenizer

NUM_TOKENS, DELTA, REPORT_EVERY = 30000, 6, 3000
TOOL = {
    "type": "function",
    "function": {
        "name": "bash",
        "parameters": {"type": "object", "properties": {"command": {"type": "string"}}},
    },
}
TOOL_CALL = (
    "<tool_call>bash<arg_key>command</arg_key><arg_value>"
    + "echo 'hello world' >> /tmp/out.txt\n" * 20000
    + "</arg_value></tool_call>"
)

tok = get_tokenizer("zai-org/GLM-5.3-Flash")
parser_cls = ParserManager.get_parser(
    tool_parser_name="glm47",
    reasoning_parser_name="glm45",
    enable_auto_tools=True,
    tokenizer=tok,
)
messages = [{"role": "user", "content": "Write a long shell script."}]
request = ChatCompletionRequest(
    model="m",
    messages=messages,
    tools=[TOOL],
    stream=True,
    stream_options={"include_usage": True, "continuous_usage_stats": True},
)
kwargs = {"thinking": True}
prompt = tok.apply_chat_template(
    messages, tools=[TOOL], add_generation_prompt=True, tokenize=False, **kwargs
)
prompt_ids = tok.encode(prompt, add_special_tokens=False)  # ends with <think>


def run(name, prompt_ids, output):
    parser = parser_cls(tok, request.tools, chat_template_kwargs=kwargs)
    out_ids = tok.encode(output, add_special_tokens=False)[:NUM_TOKENS]
    generated, window, total = [], 0.0, 0.0
    print(f"[{name}]")
    for start in range(0, len(out_ids), DELTA):
        delta_ids = out_ids[start : start + DELTA]
        t0 = time.perf_counter()
        # What chat_completion/serving.py does for every delta.
        parser.parse_delta(
            tok.decode(delta_ids),
            delta_ids,
            request,
            prompt_token_ids=prompt_ids,
            finished=False,
        )
        t1 = time.perf_counter()
        generated.extend(delta_ids)
        parser.count_reasoning_tokens(tuple(generated))
        t2 = time.perf_counter()
        window += t2 - t1
        total += t2 - t0
        if len(generated) % REPORT_EVERY < DELTA:
            per_delta = window / (REPORT_EVERY // DELTA) * 1e3
            print(f"  {len(generated):6d} tokens: count {per_delta:.3f} ms/delta")
            window = 0.0
    print(f"  total {total:.2f} s")


reasoning = "Let me think step by step about the script. " * 200
run("reasoning open", prompt_ids, reasoning + "</think>" + TOOL_CALL)
end_think = tok.convert_tokens_to_ids("</think>")
run(
    "prompt closes reasoning",
    prompt_ids + [end_think],
    "Here is the script.\n" + TOOL_CALL,
)
```

## Details



**Root cause.** `ParserEngineReasoningAdapter` returns the live streaming count only once `extract_reasoning_streaming` has been called (`_streaming_count_valid`). When the prompt already closes reasoning, `DelegatingParser.parse_delta` marks reasoning as ended from the prompt and never calls the reasoning parser. Every `count_reasoning_tokens` call then falls back to `_single_pass_parse(decode(all_ids), all_ids)` on a separate counting engine. With continuous usage stats this runs on every delta, on the API server event loop.

We hit this in production: GLM-5.3 behind a router that requests `continuous_usage_stats`. Long, highly repetitive outputs at ~600 tok/s pushed the API server event loop behind real time. The stats log interval grew from 5 s to 15 s while engine throughput was normal.

**Change.** The counting engine keeps the ids it has counted.

- First call, or ids that do not extend the previous ones (e.g. Responses rounds): same single-pass parse as before. Non-streaming results are unchanged.
- Ids that extend the previous call: only the new tokens are fed.
  - The delta text is decoded with 4 tokens of left context, then diffed against the context-only decode, so it matches the full decode.
  - An incomplete trailing multi-byte character is held back until a later call completes it.
  - If the previous call was a single-pass parse, which finishes the engine, the counted prefix is replayed once without `finish()`.
- `set_prompt_token_ids` resets the counted ids.

**Duplicate check.** No open or closed PR changes this fallback. Searched for `count_reasoning_tokens`, `continuous_usage_stats`, `_counting_parser_engine`, reasoning quadratic, and prompt-closed reasoning. #56067 (merged) and #61379 (open) touch adjacent code and are complementary, as described above. #59588 (open) keeps token counts across empty-text deltas in the lexer and scanner. The single-pass fallback never produced such deltas, but the incremental path can, so #59588 is complementary rather than unrelated.

**Limitations.**

- Tokens ending in an incomplete multi-byte character stay uncounted until the character completes. A stream that ends there leaves them uncounted.
- The prefix comparison against the counted ids is still linear in output length. At 30K tokens it is part of the remaining 0.28 ms per delta.

**AI assistance.** I wrote the incremental counting change, `test_prompt_closed_streaming_count_parses_once`, the benchmark, and this description. I used Claude Code to review them, and it contributed:

- In `_feed_counting_tokens`, moving the engine reset after the incomplete-character check. Before this, a delta ending mid-character right after a single-pass parse reported 0.
- `test_incremental_count_matches_single_pass`, `test_incremental_count_holds_split_character_after_single_pass`, and the rename of the first test.
- Edits to this description: the counts claim, the test list, the Limitations section, and the #59588 note.

I reviewed every changed line and ran the tests and benchmark above. Model evaluation is not included because the change only affects usage accounting, not model outputs.

Thanks for working on this. The incremental count looks right, and the speedup reproduces here (1.03 to 0.04 ms per delta at 6K tokens). I think the mid-character hold should cover only the unfinished character, though: holding the whole delta can stall the count for many deltas.

With 3 tokens per delta and 𝔘𝔫𝔦𝔠𝔬𝔡𝔢 in the reasoning, every boundary in that word lands mid-character (`minimax_m2`, prefill prompt):

```
main:    [2, 5, 8, 11, 14, 17, 20, 23, 26, ...]
this PR: [2, 2, 2, 2, 2, 2, 2, 2, 26, ...]
```

If the output stops in that run, say at `max_tokens`, the final `reasoning_tokens` is 2 where main gives 24. Feeding up to the last token that completes a character keeps the lag within one character (inline suggestion). With it, `tests/parser/` passes and the per-delta cost stays at 0.04 ms.
