# [Lora][Gemma4]: gemma4 fix lora online serving

[Upstream PR](https://github.com/vllm-project/vllm/pull/39816) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->
Fixes: #39815 


  ## Purpose

  This PR fixes Gemma4 LoRA online serving when aliased module paths point to the
  same physical module.

  Gemma4’s fast-prefill / YOCO split added `self_decoder` and `cross_decoder`
  wrappers. Those wrappers reference existing decoder layers, so the same module
  can show up under multiple paths:

  ```text
  model.layers.0...
  model.self_decoder.decoder_layers.0...
  ```

  Before this PR, LoRA activation could load weights through one path and then
  reset the same wrapper through the alias path:

  ```text
  set_lora(...)   for model.layers.0...
  reset_lora(...) for model.self_decoder.decoder_layers.0...
  ```

  Since both names point to the same live wrapper, the reset could wipe out the
  weights that were just loaded. This made the adapter behave like the base model.

  ## Fix

  Keep `remove_duplicate=False` during module discovery so all valid LoRA paths
  stay registered:

  ```python
  self.model.named_modules(remove_duplicate=False)
  ```

  Then dedupe only during activation by physical module identity. This keeps the
  module names LoRA needs for adapter matching, while making sure `set_lora()` /
  `reset_lora()` only run once per actual wrapper.

  This matters for Gemma4ForConditionalGeneration because adapter paths can map to
  prefixed vLLM paths like:

  ```text
  language_model.model.layers...
  language_model.lm_head...
  ```

  Deduping during `_create_lora_modules()` can drop names that are still valid for
  LoRA, so the dedupe needs to happen at activation time instead.

  ## Test Plan

  ```bash
  .venv/bin/python -m pytest tests/lora/test_model_manager_aliasing.py -q
  ```

  ## Test Result

  ```text
  PASSED
  ```

  The regression test checks that:

- the toy model exposes both canonical and aliased module paths
- both paths resolve to the same physical LoRA wrapper
- activation keeps nonzero LoRA weights loaded instead of zeroing them through the alias path

Also worth noting that this bug was surfaced after aliasing was introduced in the gemma4 implementation in this PR: #38879

Confirming this fix works for the offline `vllm` Python module path too (answering @NilsHellwig's question on #41754):

**Setup**
- vLLM `0.20.1` + this PR (cherry-picked onto the `v0.20.1` tag)
- `google/gemma-4-E2B-it`
- LoRA trained via **HF transformers + PEFT** (not Unsloth) — `LoraConfig(r=16, target_modules=r"^model\.language_model\.layers\.\d+\.self_attn\.(q_proj|k_proj|v_proj|o_proj)$", task_type=CAUSAL_LM)`, ~80 examples, 4 epochs
- Offline path: `LLM(model=..., enable_lora=True).generate(..., lora_request=LoRARequest(...))`
- Sanity-checked the adapter independently via `transformers + peft` — adapter does flip generations to ALL CAPS

**Without the fix** (vanilla v0.20.1): vLLM loads the adapter without error, emits no `language_model.* will be ignored` warnings (only the expected `vision_tower.*` ones), but the LoRA-on output is **byte-identical** to base across all test prompts. Silent no-op.

**With this PR**: ALL CAPS output matches what `transformers+peft` produces locally. Confirmed.

So the bug class covers at least:
- Online serving (per the PR title)
- Offline `LLM(...).generate(...)` (this comment)
- Unsloth adapters (#41754)
- HF transformers + PEFT adapters (this comment)

i.e. it's not adapter-tooling-specific — anything PEFT-shaped that targets the text decoder hits it. Worth retitling away from "online serving" if a maintainer's editing during merge.

**Diagnostic notes for reviewers**, in case useful:
The clobber is observable by instrumenting `LoRAModelManager.activate_adapter`'s loop and counting wrappers by `id(module)`. On Gemma 4 E2B with our adapter: 212 unique wrapper objects, 210 of them registered in `self.modules` under 2+ names (under `layers.X`, `self_decoder.decoder_layers.Y`, `cross_decoder.decoder_layers.Z`). For every adapter LoRA that found a match (70 of them, post-`_create_merged_loras_inplace`), the same wrapper had at least one alias name with no match → `set_lora` for the canonical path was followed by `reset_lora` for the alias path, exactly as the PR description says.

I also tried `remove_duplicate=True` in `_create_lora_modules` as a one-line alternative — it works for our specific case because Gemma 4's `self.layers` is inserted before `self_decoder`/`cross_decoder` so `layers.X` ends up as the first-encountered (canonical) name. But ShubyM's reasoning in #39815 is right that this is too broad: it relies on canonical-name-first attribute order, and would silently drop names that are still valid LoRA targets for other adapter conventions. Deduping at activation by `id(module)` is the safer fix.

- excepshenal · comment · 2026-06-01T18:55:39Z · [source](https://github.com/vllm-project/vllm/pull/39816#issuecomment-4595563078)

This patch seems to rely on an assumption that the module iteration will always iterate over canonically named modules first before aliased modules. If the iteration iterates over aliased modules first, then canonical modules would be skipped and `set_lora` would never be called. I'm not sure if this assumption is robust?

Perhaps a better implementation that is more robust would use two passes:
```
# Pass 1: find one applicable name per physical module, preferring one with weights
chosen: dict[int, tuple[BaseLayerWithLoRA, LoRALayerWeights | None]] = {}
for module_name, module in self.modules.items():
    mid = id(module)
    weights = self._get_lora_layer_weights(lora_model, module_name)
    if mid not in chosen or (weights is not None and chosen[mid][1] is None):
        chosen[mid] = (module, weights)

# Pass 2: apply, free of iteration-order assumptions
for module, weights in chosen.values():
    if weights is None:
        module.reset_lora(index)
    else:
        module.set_lora(index, weights.lora_a, weights.lora_b)
```
