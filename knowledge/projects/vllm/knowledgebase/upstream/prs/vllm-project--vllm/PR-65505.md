# [Perf][Kernel][Attention] Binary-search mm_prefix spans in Triton unified attention

[Upstream PR](https://github.com/vllm-project/vllm/pull/65505) · state: open · merged: False

## Original PR description

## Purpose

Prefix-LM multimodal models (Gemma 4, Gemma 3, PaliGemma, ...) attend bidirectionally inside each image or video frame. vLLM stores those blocks as one `(start, end)` span per frame in `mm_prefix_range`, and the Triton unified attention kernel loops over **every** span for every query block and every KV tile, in both `compute_tile_loop_bounds` and `compute_kv_seq_mask`. A video prompt carries one span per frame, so the mask cost grows as tiles × spans: on Gemma 4 31B a 7 minute 5 fps chunk (about 2,100 frames, 161k tokens) spends about 220 ms per sliding-window layer call in those loops and prefills at 500 tok/s where text-only runs at 4,300 tok/s.

The spans are sorted by position and pairwise disjoint (features are sorted by offset and a feature's ranges never overlap), so this PR replaces the scans with two binary searches:

- `compute_tile_loop_bounds`: the spans intersecting a query block form one contiguous run; only its first start and last end bound the allowed keys.
- `compute_kv_seq_mask`: a query lies in at most the last span starting at or before it (or the one just before, when two spans touch).

The search depth is derived from `MAX_MM_RANGES` at trace time, so prompts with one image keep the same number of loads as before. `compute_mm_prefix_range_tensor` now drops degenerate `start >= end` ranges before padding, so the kernel's invariant (valid, sorted spans, then padding) holds whatever the model's span builder produced; the old loop ignored those entries wherever they sat.

The output is bit-identical to the current kernel: the mask tile and loop bounds are the same booleans and integers, computed with fewer loads.

## Test Plan

New tests in `tests/kernels/attention/test_triton_unified_attention.py`:

- `test_kv_seq_mask_with_many_mm_prefix_spans[sw, clamp]`: materialises the kernel's mask for a 2,048-token prompt with ~290 spans (some touching) and compares it exactly with the mask definition.
- `test_clamped_mm_prefix_tile_bounds_with_many_spans`: every query block's tile range against a per-span reference.
- `test_triton_unified_attn_clamped_mm_matches_dense_reference` gained a many-spans case through `unified_attention`.

New `benchmarks/kernels/benchmark_triton_mm_prefix_attn.py` times one prefill step of one sliding-window layer with a configurable number of spans (default: the Gemma 4 31B video chunk above).

Commands run on an H100 (`vllm/vllm-openai:nightly`, 0.33.0rc1.dev573+g40941f2c4, with this branch's files dropped in):

```
pytest tests/kernels/attention/test_triton_unified_attention.py
python benchmarks/kernels/benchmark_triton_mm_prefix_attn.py --spans N   # N in 0,1,8,64,450,2100, before and after
```

Bit-equality against the replaced helpers: 2,400 random `(spans, query block, KV tile)` mask tiles and 2,400 loop-bound cases over `MAX_MM_RANGES` in {1, 2, 8, 64, 2112}, sliding window in {0, 64, 128, 512, 1024}, clamped and unclamped — 0 differences (probe script in the PR comments on request).

- Noezor · comment · 2026-11-03T21:31:00Z · [source](https://github.com/vllm-project/vllm/pull/65505#issuecomment-6615913427)

**Alternative considered: a per-query-token lookup table instead of the binary search.**

A `(start, end)` row per scheduled query token, as `fill_mm_prefix_query_ranges` builds for the FlashAttention path, would replace the search with one load per query row: spans are disjoint, so "key shares a span with the query" reduces to "key lies in the query's own span", and the tile bounds come from a min/max over the block's rows.

I did not take that route because the microbenchmark shows the search already costs nothing measurable: 4.95 ms at 1 span vs 4.97 ms at 2,100 spans. The remaining 1.2 ms over the no-span kernel (3.72 ms) is the `USE_MM_PREFIX` mode itself (full-sequence read via `max_seq_prefix_len = seq_len`, pruning widened by the clamped union, the extra mask ANDs), which a table would not change. The search is memory-latency bound on a ~17 KB span array that sits in cache; a table would be cache-resident too but has to be rebuilt on the host every step and plumbed through `TritonAttentionMetadata`, `unified_attention` and the int4 kernel, so it would widen the diff for the same cost profile.

If the Triton and FA prefix-LM metadata are unified later, the table comes for free and the search can be dropped for it.
