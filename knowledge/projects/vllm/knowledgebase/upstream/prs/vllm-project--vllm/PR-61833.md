# [CPU] Cap auto OpenMP thread binding at the cgroup CPU quota

[Upstream PR](https://github.com/vllm-project/vllm/pull/61833) · state: open · merged: False

## Original PR description


## Overview

With `VLLM_CPU_OMP_THREADS_BIND=auto` (the default), the CPU worker starts one OpenMP thread per selected core of the scheduling affinity and ignores the cgroup CPU quota. In a container with a CPU limit (`docker run --cpus`, or a Kubernetes `limits.cpu` without the static CPU manager), the affinity is still the whole host, so the worker starts more spinning threads than the quota allows and spends most CFS periods throttled. This PR caps the auto-selected OpenMP threads at the quota, using the existing `available_cpu_count()` helper in `vllm/utils/torch_utils.py`.

## Claims

- Auto binding no longer starts more OpenMP threads than the cgroup CPU quota allows (cgroup v2 `cpu.max` and v1 CFS quota, through the existing helper). The quota is split evenly across ranks with at least one thread per rank, and one warning is logged when the cap applies.
- On a 20-thread laptop with `docker run --cpus=4`, Qwen2.5-0.5B-Instruct offline throughput goes from 11.3 to 25.7 output tok/s (median of 5 interleaved runs each).
- No change when there is no quota, for user-specified bind lists, for `nobind`, or for CPU reservation.

## Validation

**Unit tests** in `tests/utils_/test_omp_cpu_quota.py`. They mock the CPU topology and the cgroup v2 files (`/proc/self/cgroup`, `cpu.max`). Cases: `400000 100000` on 16 CPUs gives 4 threads; `max` leaves the lists unchanged; a 5.5-CPU quota over 2 ranks gives 3 + 2; the one-thread-per-rank floor; 2 API processes sharing one quota.

```bash
VLLM_TARGET_DEVICE=cpu .venv/bin/python -m pytest --confcutdir=tests/utils_ \
  tests/utils_/test_omp_cpu_quota.py tests/utils_/test_cpu_resource_utils.py -v
```

Before the change, 4 of the 5 new tests fail (the unlimited case passes). After the change, all 17 pass. `pre-commit run --files` on the three changed files passes (ruff, typos, markdownlint, mypy, test tethering, SPDX).

**End to end.** Laptop: i7-12700H under WSL2 (lscpu: 10 cores / 20 threads, 1 NUMA node). Each run uses Docker with a 4-CPU quota: `cpu.max` is `400000 100000` and `nproc` is 20. Image `vllm/vllm-openai-cpu:nightly-5555a2d8f`; its `ompmultiprocessing.py` is byte-identical to `main`. For the patched arm, the changed file is bind-mounted over the installed one. Arms are interleaved, with the order alternated each rep. "Throttled" is `nr_throttled / nr_periods` from the container's `cpu.stat` over the whole container lifetime.

```bash
docker run --rm --cpus=4 --shm-size=4g -e VLLM_CPU_KVCACHE_SPACE=2 ... vllm/vllm-openai-cpu:nightly-5555a2d8f \
  vllm bench throughput --model Qwen/Qwen2.5-0.5B-Instruct --dtype bfloat16 --dataset-name random \
  --random-input-len 128 --random-output-len 128 --num-prompts 64 --max-model-len 1024 --seed 0
```

| arm (auto binding) | OpenMP threads | output tok/s, median (min to max), n=5 | throttled periods, median |
|---|---|---|---|
| main | 9 | 11.3 (11.1 to 13.3) | 86% |
| this PR | 4 | 25.7 (20.4 to 26.0) | 47% |

The two ranges do not overlap. An earlier session gave the same picture: main 11.6 (11.5 to 12.2), n=5.

## Details

- Root cause: `_get_autobind_cpu_ids` builds the per-rank lists from `cr_utils.get_allowed_cpu_list()`, which filters only by `os.sched_getaffinity(0)`. A CFS quota does not change the affinity, so `configure_omp_envs` sets `OMP_NUM_THREADS` from the host's core count.
- Budget: `available_cpu_count()` (affinity capped by `int(quota)`), divided by `_api_process_count`, because the API processes on a node share the container's quota. `startup_omp_num_threads()` already uses the same split for weight loading. The cap is applied after reservation and trims only the OpenMP lists. Each rank keeps its lowest CPU ids, the order the lists are already sorted in.
- Why reserved CPUs are not counted against the budget: my first version also counted the reserved CPU, which gave 3 threads plus 1 reserved under a 4-CPU quota. I compared it, interleaved, against 4 threads (`VLLM_CPU_OMP_THREADS_BIND=1,3,5,7`, the same binding this PR produces). 3 threads: 19.8 (18.4 to 20.3) tok/s with 9% of periods throttled. 4 threads: 22.0 (19.9 to 22.4) tok/s with 46% throttled. Less throttling did not mean more throughput, so the PR caps threads at the quota and leaves reservation alone. Reserved CPUs only remove CPU ids from the OpenMP lists; no process is pinned to them, so under a quota they buy no CPU time.
- Not duplicating: I searched issues and PRs for "OMP_THREADS_BIND cgroup", "autobind", "cpu.max", "cgroup quota CPU backend" and "ompmultiprocessing" and found nothing on this path. Two related open PRs change other things. #56353 intersects NUMA nodes with CPU affinity (for #43240). #55703 handles nested cgroup traversal inside `_cgroup_cpu_limit`. This change is independent of both. The tests are in their own file, so they do not collide with the `tests/utils_/test_ompmultiprocessing.py` that #56353 adds. If #55703 lands first, the cap simply uses its fixed helper.
- Limitations: the quota is read once, at startup. A fractional quota rounds down (5.5 CPUs gives 5 threads). End-to-end runs cover one rank on one NUMA node; the multi-rank split is covered only by unit tests. Absolute tok/s on this AVX2 laptop is low; the claim is the ratio. Run-to-run spread is larger in the patched arm (20.4 to 26.0) than in main.
