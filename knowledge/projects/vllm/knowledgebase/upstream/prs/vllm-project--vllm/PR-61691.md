# [Feature] Add workload snapshots to iteration metrics

[Upstream PR](https://github.com/vllm-project/vllm/pull/61691) · state: open · merged: False

## Original PR description

## Overview

Extend completed iteration records with scheduled attention-workload and queued-request snapshots for Dynamo performance modeling. Collection is optional, disabled by default and transport-independent. This is the workload layer split from #52061, reusing #61424's scheduling counters rather than implementing them again. Related: #61423, #39979, #38760.

Dependency order: #61690 (timing) → **#61691 (this PR)** → #52061 (FPM exporter), after prerequisite #61424. ## Claims

- `--enable-iteration-workload-metrics` derives required timing at startup without enabling verbose logging. There is no separate timing CLI/constructor option and no ZMQ/OTLP dependency. Unsupported required timing fails validation rather than producing untimed records.
- Each completed record joins scheduled counts, prefill/decode attention-context sums and population variances, queued workload and GPU duration for its own iteration. Transport-independent types/accumulation live in `iteration_workload.py`; the reusable Welford helper is in `utils/math_utils.py`. Scheduler metadata is extended rather than rescanning scheduled requests on the default path.
- For prefill with `kv_read=x` and `scheduled_tokens=y`, attention length is `x + y/2`; variance is across those current-iteration lengths, not full prompts. Decode statistics represent logical attention context, not physical KV residency or speculative-token counts.
- Async speculative rejection corrections use existing CPU sampled-token results, preserving the original snapshot, request identity and preemption generation. They add no D2H transfer, events, kernels or sampling changes.
- Queued snapshots preserve FPM v1 conventions: preempted/remote-KV-waiting requests count as queued decode; other waiting requests as queued prefill. Both waiting queues are included without double counting. Normal snapshots follow the associated output; dummy snapshots are captured at submission.
- Timed attention-DP dummy records have empty scheduled work and may contain queued work. EngineCore emits zero-duration idle records at most once per second only after `has_work()` is false, input queues are empty and pending timings have drained. DP work includes coordinated wave state; publisher silence is never used to infer idle. Dummy associations survive beyond the ordinary batch-queue depth.
- The synchronous offline frontend filters idle-only records without dropping control/output messages. Later publication is EngineCore-owned and does not depend on frontend consumption. Self-benchmark orchestration remains in Dynamo.

## Details

Required timing supports generative CUDA models, `uni`/`mp` executors and out-of-process EngineCore; pooling, non-CUDA, Ray/external-launcher and in-process configurations are rejected. PP measures only the last-stage output worker, not whole-pipeline latency. Best-effort shutdown can discard tails.

Enabled collection adds CPU bookkeeping/queue scans; default-off does not collect these snapshots. Previous native-MTP PP2 qualification covers only MRV2 async eager; other attempted combinations failed on the timing-off baseline. Prior DP oracle checks completed before shutdown, but workers needed force-kill; graceful teardown is not established.
