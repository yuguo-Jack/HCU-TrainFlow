# [Bugfix][Worker] Stage startup plans in a unique temp file before publishing

[Upstream PR](https://github.com/vllm-project/vllm/pull/63388) · state: open · merged: False

## Original PR description

## Overview

`maybe_save_startup_plan` stages the plan at `<path>.tmp.<pid>` before `os.replace`. When several containers share `VLLM_CACHE_ROOT` and boot the same config at once, the PIDs can collide, both writers truncate one staging file, and the second rename fails. Stage in a `tempfile.mkstemp` file in the plan directory instead. Related, not overlapping: #60143 (fingerprint omits `gpu_memory_utilization`).

## Claims

- Concurrent savers with the same fingerprint on one cache root both publish without a failed save; one complete plan remains and no staging files are left behind.
- Same atomic-write pattern as `flashinfer_autotune_cache.py`: `mkstemp` in the destination directory, write through the descriptor, `os.replace`, unlink the staging file on failure.
- No change to the fingerprint, the apply gate, or the plan format.

## Validation

Two tests in `tests/v1/worker/test_gpu_worker.py`, both through `caplog_vllm` (vLLM's logger does not propagate, so plain `caplog` cannot see the save warning):

- `test_startup_plan_concurrent_save`: two saves on threads (same PID, same fingerprint, different payloads) with `os.replace` held at a barrier until both staging files are written and closed; asserts both threads finished without exceptions, no "Failed to save startup plan" record, the plan directory holds the plan file and nothing else, and that the surviving plan applies.
- `test_startup_plan_save_failure_keeps_old_plan`: with a valid plan on disk, an injected `os.replace` `OSError` on the next save leaves the old plan applied, logs the failure, raises nothing, and leaves no staging file.

On `tests/AGENTS.md`: the test reuses the file's existing `SimpleNamespace` plan fixtures and there is no `LLM`/server-level test, since the defect is a filesystem race in a worker-side helper. I am requesting a scoped exception for that; if a maintainer wants it on a real `Worker` or exercised through an engine start, I will restructure.

Where the configuration arises: Runpod Serverless workers run with `VLLM_CACHE_ROOT` on a shared network volume (runpod-workers/worker-vllm sets it), so containers that boot the same model config concurrently save the same fingerprint into one directory; container PIDs for the worker process are commonly identical. The race needs matching fingerprint, matching PID and overlapping writes, so it is intermittent in practice; the deterministic test above is the evidence for this PR.

## Details

- `mkstemp` creates the staging file 0600; after `os.replace` the published plan keeps that mode, where the previous `open(..., "w")` produced umask-filtered 0644-style files. `flashinfer_autotune_cache.py` and `weight_utils.atomic_writer` already publish `mkstemp` files the same way. A reader under a different UID on a shared volume would no longer be able to read the plan and would re-profile (the safe direction). Flagging in case the maintainers would rather `os.chmod` to the previous behaviour.
- Not reused: `weight_utils.atomic_writer` does the same thing but pulls model-loader imports into the worker startup path; this follows `flashinfer_autotune_cache.py`'s inline pattern instead.
- Scope is the staging-file collision only. Last writer still wins at the destination, and this makes no new promises about crash durability or network-filesystem semantics beyond what `os.replace` already gave.
