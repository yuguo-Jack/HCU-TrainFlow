- hclsys · comment · 2026-10-04T20:52:20Z · [source](https://github.com/vllm-project/vllm/pull/59674#issuecomment-5984269843)

Ran this on a GB10 (sm_121, Triton 3.7.1) since the description says it's waiting on a GPU run. Qwen2.5-1.5B-Instruct, TRITON_ATTN, eager, main 2a52715e vs this head.

PPL on ~2000 tokens of prose: bf16 5.46, int4 on main 10649 (garbage), int4 with this PR 5.55 (int8 5.54). Greedy continuations at 12/64/200/800-token prompts are coherent with the PR, garbage without. Batch-1 latency, 1024 in / 256 out: bf16 4.64 s, int4 main 5.35 s, int4 + PR 5.69 s.

`test_int4_attention_restores_position_dependent_key_bias` fails on the GPU (it's skipped without CUDA): corrected output is 0.79-1.16 vs the expected 1.0 +-0.1. The correction itself is right, corrected / uncorrected is 4.0 in every dim (weights [1,0,0,0] vs [.25]*4); the spread is int4 + RHT noise on a constant V row, so the tolerance is too tight. Asserting the ratio would test the key-bias part on its own.

One thing that isn't this PR: int4 on Qwen2.5 isn't reproducible run to run yet. With the PR, the same prompt gave different completions on the 1st, 2nd and 4th request, and 3 int4 tests in tests/quantization/test_per_token_kv_cache.py fail on main here. That's the hadacore tail-warp race fixed by #53167: with its kernel behind hadacore_transform those go 3 -> 1 failing and the completions are identical on every request, matching bf16 (numbers on that PR).

- Theodore-Liu · comment · 2026-10-22T07:08:30Z · [source](https://github.com/vllm-project/vllm/pull/59674#issuecomment-6334937914)

We can confirm the failure this PR addresses. On a 300-item retrieval set, Qwen2.5-7B and Qwen2.5-1.5B answer 297 and 262 unquantized and 0 of 300 under `int4_per_token_head`, and the engine reports success. This holds on three GPUs (RTX 5090, L40S, H100) and two releases (0.28.0, 0.31.0).

The PR's attribution, the layer-0 key bias meeting the per-token grid, matches what we found by intervention. Adding a constant offset to the keys of a bias-free model collapses it the same way. Centring the keys before quantization and restoring the bias in the scores, which is what this PR does, recovers the counts.
