# [Model] dots.ocr: support encoder CUDA graph

[Upstream PR](https://github.com/vllm-project/vllm/pull/63074) · state: open · merged: False

## Original PR description

## Overview

Add encoder CUDA graph support (`SupportsEncoderCudaGraph`) for dots.ocr, so its ViT can be captured and replayed by the existing `EncoderCudaGraphManager`. Part of #38175.

## Claims

- dots.ocr implements `SupportsEncoderCudaGraph`; with `compilation_config={"cudagraph_mm_encoder": True}` its vision encoder runs through captured graphs.
- Graph outputs are **bit-identical** to eager on the same padded inputs; end-to-end OCR text is identical to eager.
- Images up to 512 tokens get faster when kernel launch is the bottleneck: single-request latency for a 224×224 image is **3.0× (A100) / 4.4× (RTX 4090)** faster; on an RTX 3090 with a fast CPU the gain is small (1.07×).
- The default budget range is capped at 512 tokens. Larger images fall back to eager, so typical document pages are not slower than eager.

## Validation

**Correctness** (RTX 3090 and RTX 4090; bf16):
- Graph vs eager on the *same padded input* (same budget, same zero padding, same `cu_seqlens` padding), 5 batching cases (single page, two pages in one batch, a tiny image that the manager puts in its own batch, an oversize image that falls back to eager, mixed graph/eager): **bit-identical** in all cases.
- Comparing against *unpadded* eager differs by up to ~5% relative. This is not specific to graphs: running the same page in eager with a different batch composition changes its output by ~6% as well, because the bf16 GEMMs pick different kernels for different row counts.
- End-to-end greedy OCR on 3 rendered pages (256 tokens each): identical text to eager on RTX 3090, RTX 4090 and A100.
- Test: added `dots_ocr` to `tests/models/multimodal/generation/test_vit_cudagraph.py` (image modality, single 4096 budget so both test images — 1426 and 2646 tokens — replay through the encoder graph rather than falling back to eager). Passes locally on RTX 3090: `pytest tests/models/multimodal/generation/test_vit_cudagraph.py -k "dots_ocr and image"`.

**Performance**, default config after this PR (budgets 64–512, `max_batch_size` = 8). Encoder only, p50 of 50 runs, graph and eager interleaved:

| Single image | RTX 3090 + i5-12400 (4.4 GHz) | RTX 4090 + Xeon 6133 (2.5 GHz) | A100 + Xeon 8380 (2.3 GHz) |
|---|---|---|---|
| 64 tokens | 1.41× | 6.22× | 4.47× |
| 128 tokens | 0.99× | 4.14× | 2.86× |
| 256 tokens | 1.02× | 2.47× | 1.83× |
| 384 tokens (padded to 512) | **0.71×** | 1.35× | 1.09× |
| 512 tokens | 1.01× | 1.29× | 1.05× |
| ≥ 513 tokens / 1000×800 page | 1.00× (eager) | 1.00× (eager) | 1.00× (eager) |

End-to-end (`LLM.generate`, `max_tokens=1` latency ≈ TTFT, p50 of 20 requests, each with a new image; throughput = 32 pages / 64 small images with `max_tokens=128`):

| | RTX 3090 | RTX 4090 | A100 |
|---|---|---|---|
| 224×224 latency | 37 → 34 ms | 92 → 21 ms | 55 → 18 ms |
| 448×448 latency | 99 → 98 ms | 106 → 45 ms | 62 → 37 ms |
| 1000×800 latency | 381 → 380 ms | 179 → 179 ms | 137 → 136 ms |
| 32 pages throughput | 0.96× | 1.02× | 0.96× |
| 64 small images throughput | 0.89× | 1.07× | 0.98× |
| KV cache memory | −0.23 GiB | −0.23 GiB | −0.23 GiB |

Why cap at 512: with the manager's default range (up to `max_num_batched_tokens`, 4096 here), a 1000×800 page (1044 tokens) is padded to the 2048 budget and runs at **0.56–0.61×** of eager on all three GPUs; 513–1023-token images run at 0.67–0.84×. In no tested GPU did a budget above 512 beat eager. The cap also reduces graph memory from 1.43 GiB to 0.23 GiB and removes ~12–19 s of startup capture time.

How measured: encoder numbers call `EncoderCudaGraphManager.execute` (graph) and `vision_tower(pixel_values, grid_thw)` (eager) on the same inputs in one process, interleaved, CUDA events with synchronize, 10 warmup + 50 timed runs. Budget caps other than the default were simulated by overriding `get_encoder_cudagraph_budget_range`. Happy to share the scripts.

## Details

- `DotsVisionTransformer.forward` is split into `prepare_encoder_metadata()` (outside the graph: rotary embeddings, `cu_seqlens` computed on CPU and padded to `max_batch_size + 1` with the last offset, `max_seqlen` kept on CPU) and in-graph compute, shared by the graph and eager paths. `max_seqlen` is captured as `budget × 4` (spatial merge 2×2) because the attention call bakes it into the graph via `.item()`.
- dots.ocr is image-only and each image is one attention sequence, so `cu_seqlens` is padded to `max_batch_size` only (no frames axis).
- `min_budget = 64` (same as Qwen2-VL/Qwen3-VL): the smallest dots.ocr image is 4 tokens, but a smaller minimum would shrink the inferred `max_batch_size` (`min(max // min, min)`).

**Limitations**
- The benefit depends on the GPU/CPU speed ratio: when the CPU is fast relative to the GPU (e.g. RTX 3090 + 4.4 GHz desktop CPU), eager is GPU-bound and the graph gains little; padding to the next power-of-two budget can then make 257–511-token images slower (0.71× at 384 tokens on RTX 3090).
- Batched throughput is roughly neutral (0.89–1.07×): in batched mode eager runs many images in one large call, while the graph path splits them into budget-sized batches.
- Run-to-run variation: on the dual-socket 4090 host, eager latency varied by ~15% between processes (launch-bound, sensitive to CPU placement); graph latency was stable. Numbers above are from a single process per configuration.
- Not measured: online serving under concurrency; H100.
