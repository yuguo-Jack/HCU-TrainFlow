# [Bugfix] Cast MRV2 int32 idx_mapping row offsets to int64 to fix overflow

[Upstream PR](https://github.com/vllm-project/vllm/pull/60535) · state: closed · merged: False

## Original PR description

## Overview

Fixes #57030.

Cast the request-slot index to int64 at load in the 11 MRV2 kernels where the row offset `slot * stride` can overflow int32, so engines at long context no longer abort with `Memory access fault by GPU node-N` (or silently write the wrong row). No dtype, layout, or memory change.

## Claims

- **Fixes #57030 end to end**: the issue's reproducer (Qwen2.5-VL-3B, MRV2, `max-model-len 128000 --max-num-seqs 8192`) crashed in startup warmup with the byte-identical fault; with this PR the same command completes startup and serves requests.
- Closes the whole int32 row-offset class in MRV2, not just the reported site: staged-write, penalties bincount/counts, every-sampled-token update, prefill copy, prompt-logprobs, bad-words, thinking-budget, mrope positions (trips at slot 716, below the default `max_num_seqs`), trace replay. A single-site fix only moves the fault to the next kernel.
- Also fixes the silent-corruption variant (wrapped offset that re-lands in-bounds writes a different row with no error).
- No API/config change, `idx_mapping` stays int32 as #57980 intends.

## Validation

```bash
vllm serve Qwen/Qwen2.5-VL-3B-Instruct \
  --max-model-len 128000 --max-num-seqs 8192 \
  --gpu-memory-utilization 0.9 --tensor-parallel-size 1
```

| run | before | with this PR |
|---|---|---|
| startup (MRV2 warmup) | `Memory access fault by GPU node-2 ... Reason: Unknown` at `_prepare_rope_positions_kernel` (traceback in warmup) | **`Application startup complete`, 0 faults** |
| chat request after startup | n/a (never listened) | **200 OK**, `finish_reason=length` completion |

(The prefill-inputs site was likewise reproduced end to end on a Qwen3-32B, `--max-model-len 40960 --max-num-seqs 52430` run: fault at `_prepare_prefill_inputs_kernel` before this PR.)

```
pytest tests/v1/worker/test_gpu_row_offsets_i64.py -v 
```
Pytest passed. 

## Details

`req_state_idx` is loaded from the int32 `idx_mapping` (#57980 keeps the mapping int32) and multiplied by a host-scalar stride, so the offset math runs in int32 and wraps once `slot * stride >= 2**31`. At 1M context that is row 2148 and slots are handed out top-down, so the very first request dereferences a wrapped pointer; mrope trips even earlier (row 716, 3-strided positions). Fixing only the originally-reported kernel merely moves the fault to the next one (observed: penalties `bincount`, mrope positions and prefill-inputs during warmup).

@njhill: this PR takes the cast-at-the-load option from the issue thread (the #57980 pattern, already in `watermark.py` / `gumbel.py`) rather than making the mapping int64 at upload. Happy to receive feedback, and glad to switch designs if you prefer the other option.
