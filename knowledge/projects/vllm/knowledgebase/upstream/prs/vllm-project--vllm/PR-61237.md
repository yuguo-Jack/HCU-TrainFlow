# [Bugfix] Share PCP-aware local GPU indexing for NUMA binding

[Upstream PR](https://github.com/vllm-project/vllm/pull/61237) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

Fix PCP-aware NUMA binding for colocated data-parallel GPU workers and their EngineCore processes by sharing GPU-index calculation with device selection.

Identified while evaluating [ivanium/vllm#53](https://github.com/ivanium/vllm/pull/53). This PR only fixes indexing; automatic default enablement is separate work.

## Claims

- Use one `ParallelConfig.get_local_gpu_index()` helper for GPU device selection, NUMA worker lookup, and EngineCore DP shard starts.
- Use the existing PCP-aware `ParallelConfig.world_size` for DP offsets and EngineCore shard bounds, so both account for TP × PCP × PP.
- Preserve existing local-rank behavior for Ray, external launchers, and DP replicas spanning multiple nodes; preserve manual binding overrides and memory-policy fallback.

Seven PCP regression cases failed before the fix. The passing suite covers PCP/PP DP offsets, manual CPU-list indexing, local/global DP rank precedence, launch-rank overrides, complete EngineCore shard coverage, and unchanged non-offset branches.

A helper reproducer using a real `ParallelConfig` with TP=2, PCP=2, PP=1, DP=2 and local DP rank 1 confirms `world_size=4`, first-worker GPU index 4, and NUMA node 1 for both worker and EngineCore with topology `[0,0,0,0,1,1,1,1]`.

The existing Buildkite `utils_` suites include these tests on NVIDIA and AMD jobs.

Validation limitations: no Linux/GPU serving run, model evaluation, or performance benchmark has been performed. A PCP × DP serving reproducer checking actual worker and EngineCore binding is still needed. The normal local pytest invocation is blocked by missing `tblib` in `tests/conftest.py`; the focused run above bypasses that conftest and does not establish a full-suite pass.

## Details

GPU device selection already includes PCP in the DP stride, but the NUMA helper used only TP × PP. EngineCore also used a too-small, incorrectly offset shard range. This can select another shard's NUMA node or omit nodes needed by PCP workers.

For colocated single-node MP with TP=2, PP=1, local DP rank=1, and worker local rank=0:

| PCP | Actual worker GPU | Old NUMA lookup | New NUMA lookup |
|---|---:|---:|---:|
| 1 | 2 | 2 | 2 |
| 2 | 4 | 2 | 4 |
| 4 | 8 | 2 | 8 |

GPU selection is unchanged; NUMA lookup now matches it. With PCP=2, EngineCore's NUMA lookup covers GPUs `[4, 5, 6, 7]` instead of `[2, 3]`.

DCP groups existing ranks; it does not introduce another worker-count multiplier. The worker world size remains TP × PCP × PP.

The new config helper centralizes the existing device-selection rules and uses the already computed worker world size. NUMA worker lookup calls that helper, and EngineCore uses it for the shard start plus `world_size` for the shard length. No steady-state inference operation or synchronization is added.

Duplicate-work searches on 2026-10-12 for open upstream PRs mentioning NUMA with PCP or `prefill_context_parallel_size` found no other PR addressing this GPU binding mismatch. The predecessor trial concerns automatic default enablement, not this fix.

Human review and confirmation of relevant tests are required; they are not claimed by this description.
