# [ROCm][AITER] Enable AITER by default on CDNA3+, keep AMD CI on the non-AITER path

[Upstream PR](https://github.com/vllm-project/vllm/pull/62092) · state: open · merged: False

## Original PR description

- Default `VLLM_ROCM_USE_AITER` to on (`envs.py`). When it is unset, `_aiter_ops.py` turns AITER on only on CDNA3+ with aiter installed. An explicit value is kept, and RMSNorm priority and the MoE oracles use the gated check.
- Keep AMD CI off AITER unless a test opts in: `ENV VLLM_ROCM_USE_AITER=0` in the `ci_base` stage of `Dockerfile.rocm`, plus the same default in `run-amd-test.sh` until `ci_base` is rebuilt.
- Only select AITER kernels for shapes they handle: int8 scaled-mm needs per-token × per-channel scales, and FP8 block-scaled MoE needs hidden size % 512.
- On gfx942, skip AITER RMSNorm, the fused add+RMSNorm+FP8 per-token quant and the fused allreduce+RMSNorm, including with an explicit `=1`, because AITER v0.1.25 rounds bf16 by truncation there. Each has a TODO to revert.
- Fuse SiLU-mul with AITER's static per-tensor FP8 quant (`matcher_utils.py`, `act_quant_fusion.py`) so per-tensor FP8 models keep that fusion when AITER is on.
- Launch 4 blocks per token up to 512 tokens in `silu_and_mul_quant` (`activation_kernels.cu`). With 1 block per token from 33 tokens, the fused kernel was slower than the unfused path. Output is bit-identical.
- Don't enable the QK-norm/RoPE/KV-cache fusion without a model config (`vllm.py`).
- Tests: a shared `use_aiter` fixture (`conftest.py`) runs the fusion, config and backend-selection tests with AITER both on and off, and the rest are updated for the new defaults.

AITER is the fast path on MI300/MI355, but users had to export `VLLM_ROCM_USE_AITER=1` to get it. Running the suites with it on, at the pinned AITER v0.1.25, turned up problems that every `=1` user already hits:
- the int8 kernel asserts on valid configs and silently computes garbage for per-tensor scales;
- FP8 block-scaled MoE faults the GPU for hidden sizes that are not a multiple of 512;
- on gfx942, truncated bf16 stores cost gsm8k strict-match on Llama-3.1-8B-Instruct: 66.0 vs 70.4 (bf16), 64.6 vs 70.0 (FP8-dynamic) and 67.0 vs 70.3 (bf16 TP=2).

The RMSNorm rounding is fixed upstream in ROCm/aiter#6300, which is not tagged yet; the custom allreduce module still truncates on aiter main (fix in ROCm/aiter#6640). AMD CI stays pinned off for now, so CI coverage does not change.

Behavior changes to be aware of when AITER is on:
- `fuse_norm_quant` defaults on for every model, because the AITER FP8 linear path adds `+quant_fp8` (since #25552).
- With a KV connector, attention auto-selection picks AITER FA before unified attention.
- An explicit `=1` with an unsupported FP8 block-scaled hidden size now errors at startup instead of faulting.
- Known AITER v0.1.25 issue, already hit with `=1`: the persistent fused-MoE kernels launch more workgroups than they plan for when `inter_dim / tile` does not divide the CU count, so FP8 block-scaled and per-token MoE outputs are off during prefill for e.g. Qwen3-30B-A3B, Qwen3-235B and GLM-4.5-Air. Per call this is about 5% relative error, but gsm8k and serving on Qwen3-30B-A3B-FP8 are unchanged. The fix is ROCm/aiter#6639 and arrives with the next AITER bump.
- MLA attention + static FP8 output quant still has no AITER pattern (already the case with `=1`). Its AITER-on test variant is a strict xfail, so it flags itself once a pattern lands.

#61595 attempts the same default flip. This PR differs in three ways: it keeps AMD CI off, it gates on hardware for every consumer of the flag, and it fixes the kernel-selection bugs above rather than leaving them reachable.

Validation on MI300X, pinned AITER v0.1.25, with `VLLM_ROCM_USE_AITER` unset, `=1` and `=0`:
- `pytest` runs (fresh compile cache each run):
  - `compile/passes/test_silu_mul_quant_fusion.py`, `test_functionalization.py`, `test_fusion.py`, `ir/test_inplace_functionalization.py`: 10/10 in the unset mode.
  - The tests with AITER on/off variants pass in every mode, e.g. `compile/test_config.py` (89 passed).
  - `kernels/moe/test_unquantized_backend_selection.py`, `test_mxfp8_aiter_backend_selection.py`, `test_fp8_tp_loading.py`: 10/10 in each mode.
  - `quantization/test_quark.py::test_quark_int8_w_per_tensor_a_per_tensor`: 10/10 on aiter 0.1.24.post1 and v0.1.25.
  - `quantization/test_quark.py::test_quark_fp8_w8a8_per_block_moe`: 10/10 on aiter 0.1.24.post1 and v0.1.25 with the variable unset. Its model has hidden size 128, so with an explicit `=1` it errors at startup, as described above.
  - With `=0` (what CI runs), the compile, config, MoE, quantization and attention-selection groups all pass.
- `lm_eval` gsm8k 5-shot (full 1319) after the gfx942 gates, branch defaults vs control:
  - Llama-3.1-8B-Instruct FP8-dynamic: 69.9 / 69.5 vs 70.0 (paired McNemar p = 0.70 / 0.43).
  - bf16 TP=2: recovers to the unfused level (p = 6e-5 vs the old fused default).
- SiLU-mul + AITER per-tensor FP8 fusion on RedHatAI/Meta-Llama-3.1-8B-Instruct-FP8, with #61716: median TPOT at concurrency 4 is 0.99x unfused, throughput at rate inf is 1.01x, and gsm8k shows no significant change.
- `silu_and_mul_quant` launch grid on MI300X: bit-identical on 2400 shapes plus 2720 more at 130-609 tokens. The kernel is 1.8-2.6x faster at 17-128 tokens and 1.0-1.56x at 129-512, unchanged elsewhere; above 512 four blocks per token stops paying off (3-9% slower at 576-608 tokens), hence the cutoff. `vllm bench latency` on Llama-3.1-8B-Instruct-FP8 is 1.0% faster at batch 32 and 2.2% at batch 64; the 129-512 step is below its ~0.5% resolution. `tests/kernels/test_fused_quant_activation.py` passes 10/10. Not measured on NVIDIA, where the old 16/32 cutoffs may have been tuned.
- `vllm bench serve` cost of the gfx942 gates: +3.2% median TPOT at concurrency 4 for the FP8 fused-add gate. The allreduce+RMSNorm gate is within noise.

Caveats: on gfx942 the new default changes nothing that runs for bf16 TP1 Llama (ROCM_ATTN and native RMSNorm in both arms; the logs confirm this, and one on run and one off run produced byte-identical gsm8k generations). For bf16 TP2 the only change is AITER custom all-reduce, which is neutral within noise. The clear win is the AITER FP8 MoE and block-scaled GEMM path on Qwen3-30B-A3B (+24-38% throughput). Per-tensor FP8 Llama is now within about 1% of AITER off: with main merged, #52831 fuses RMSNorm with AITER's per-tensor quant through AITER's Triton kernel (c4 TPOT +0.5%; before the merge it was +3.7%, because the quant ran as a standalone AITER kernel). The other rows were measured before the merge. gsm8k sampling is not deterministic run to run at seed 1234 (same-arm reruns differ by up to p=0.023), so no accuracy change is detectable in any model.

- AndreasKaratzas · comment · 2026-10-18T10:27:22Z · [source](https://github.com/vllm-project/vllm/pull/62092#issuecomment-6248748524)

@ChuanLi1101 `activation_kernels.cu` is back to main.

It was there because this PR's SiLU-mul + AITER per-tensor FP8 fusion called `silu_and_mul_quant`, and with 1 block per token from 33 tokens that kernel was slower than leaving the two ops unfused. The pattern now swaps in native SiLU-mul + quant, which Inductor fuses into the same Triton kernel it generates with AITER off, so the PR no longer calls `silu_and_mul_quant` at all.

On MI300X with Llama-3.1-8B-Instruct-FP8, the Inductor kernel is 1.2-1.45x faster than `silu_and_mul_quant` (1-16384 tokens) and bit-identical to the AITER-off path. Decode is about 1% faster than before (0.990x / 0.993x ms/step at batch 4 / 32), which puts AITER on within 0.5% of AITER off, and gsm8k is unchanged.

Previously only up to 16 tokens got 4 blocks per token, then 2, then 1 from 33 tokens on. - AndreasKaratzas · comment · 2026-10-18T07:47:01Z · [source](https://github.com/vllm-project/vllm/pull/62092#discussion_r4306224931)

File: `vllm/compilation/passes/fusion/act_quant_fusion.py` · line 126

Why a new class: with AITER FP8 linear on, `QuantFP8` emits AITER's per-tensor quant op. The parent pattern only matches vLLM's quant op, so without this class SiLU-mul and quant stay two separate kernels in every MLP of a per-tensor FP8 model.

Why a subclass, and why here: it's the same fusion with the same inputs. Only the quant op being matched differs, so it reuses the parent and sits next to it. Attention does the same with `RocmAttnFp8StaticQuantPattern` in `attn_quant_fusion.py`.

- AndreasKaratzas · comment · 2026-10-18T07:47:01Z · [source](https://github.com/vllm-project/vllm/pull/62092#discussion_r4306224932)

File: `vllm/compilation/passes/fusion/act_quant_fusion.py` · line 142

AITER's quant op marks `scale` as mutated because it's shared with the dynamic variant, so the scale shows up as a graph output. If the pattern doesn't return it, nothing matches. For static quant the scale is unchanged, so the replacement passes it straight through.

- AndreasKaratzas · comment · 2026-10-18T07:47:01Z · [source](https://github.com/vllm-project/vllm/pull/62092#discussion_r4306224938)
