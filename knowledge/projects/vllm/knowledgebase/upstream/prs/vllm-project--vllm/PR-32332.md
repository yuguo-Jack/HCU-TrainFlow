## Code Review

This pull request introduces a request tiering system for SLO management, allowing requests to be dropped based on system load and a request-specific tier. The changes are extensive, touching configuration, engine logic, and API entrypoints.

My review has identified two main issues:
1.  A critical flaw in the token-based scheduling logic that allows the pending token limit to be bypassed by large requests, which could lead to OOM errors or service degradation.
2.  A high-severity issue in the custom exception handling that causes error messages to be lost in logs, hindering debugging.

I've provided detailed comments and a code suggestion to address these points. The new test file is a good start, but it would benefit from more integrated tests that cover the full request lifecycle, including tokenization, to catch issues like the one I've pointed out.

![critical](https://www.gstatic.com/codereviewagent/critical.svg)

The current implementation of token-based scheduling has a critical flaw. It only checks the number of pending tokens *before* adding the new request, and does not account for the size of the incoming request. As noted in the comment, this is intentional to allow large requests to be scheduled. However, this allows a single large request to easily bypass the `max_pending_context_tokens` limit, potentially causing out-of-memory errors and service degradation for all users. This fundamentally undermines the SLO protection this feature is meant to provide.

For example, if `max_pending_context_tokens` is 1000 and `current_pending_tokens` is 100, a request with 2000 prompt tokens would be accepted, bringing the total to 2100, more than double the configured limit.

To fix this, the validation should occur *after* the prompt has been tokenized, and it should check if the `proposed_pending_tokens` (current tokens + new request's tokens) would exceed the hard limit. This would likely require refactoring `add_request` to move the validation call after `self.input_processor.process_inputs`.

![high](https://www.gstatic.com/codereviewagent/high-priority.svg)

The `__init__` method of `GracefulHTTPError` should pass the `message` to its parent `ValueError` constructor. Currently, it calls `super().__init__()` with no arguments. This means that when an instance of this exception (or its subclasses) is caught and converted to a string, the result is an empty string, because the error message is not part of the `ValueError`'s state. This can make debugging very difficult as important error information is lost in logs.

For example, a log statement like `logger.info("... failed: %s", e)` would print an empty message.

```suggestion
    def __init__(self, message: str, http_status: HTTPStatus):
        super().__init__(message)
        self.message = message
        self.http_status = http_status
```

### Accessing `.n` on `PoolingParams` causes AttributeError

**High Severity**

<!-- DESCRIPTION START -->
The `_validate_max_num_reqs_scheduling` method accesses `sampling_params.n` but receives a union type `SamplingParams | PoolingParams` from `add_request`. The `PoolingParams` class doesn't have an `n` attribute, so when `encode()` is called (which passes `PoolingParams`) and `max_num_reqs` is configured, the code will raise an `AttributeError`. This breaks all pooling/encoding functionality when SLO rate limiting is enabled.
<!-- DESCRIPTION END -->

### Wrong comparison operator allows requests at exact capacity

**Medium Severity**

<!-- DESCRIPTION START -->
The comparison `current_pending_tokens > max_pending_tokens` uses strict greater-than (`>`) instead of greater-than-or-equal (`>=`). When pending tokens exactly equals the limit (e.g., 1000/1000), the check passes and requests are accepted. The test explicitly expects `MaxPendingTokensError` when "at token limit" but the implementation only rejects when strictly over. With `tier=1.0`, requests at exact capacity slip through both checks since `1000 > 1000` is false and `1.0 > 1.0` is also false.
<!-- DESCRIPTION END -->

### HTTP status codes from exceptions are never used

**Medium Severity**

<!-- DESCRIPTION START -->
The new exception classes (`QueueOverflowError`, `MaxPendingTokensError`, `MaxTierPendingTokensError`, `TooManyRequestsError`) define `http_status` attributes with specific HTTP status codes (503 SERVICE_UNAVAILABLE or 429 TOO_MANY_REQUESTS). However, the `create_error_response` method in `serving.py` checks `isinstance(exc, ValueError)` before it could check for `GracefulHTTPError`, causing all these exceptions to return HTTP 400 BAD_REQUEST instead of their intended status codes. The `http_status` attribute is effectively dead code.
<!-- DESCRIPTION END -->
