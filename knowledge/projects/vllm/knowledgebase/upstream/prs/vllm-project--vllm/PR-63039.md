## Scope

Draft implementation of `aiter_mimo_mega_moe_tp` for MiMo-V2.6-Pro routed experts on gfx950 TP8/DP1. Separate from MiMo mono MLP and DeepSeek-V4 TP MegaMoE.

Geometry: E384, top-k8, hidden6144, global intermediate2048, **TP-local intermediate256**, sigmoid routing with correction bias.

## Evidence

- focused ROCm contract test passes;
- real MiMo-V2.6-Pro TP8 server initialized all ranks with `MiMo MegaMoeTP ar: I=256 E=384 K=8 max_rows=256`;
- one OpenAI completion completed.

### Operator Performance (2026-10-22)

**These are standalone AITER expert-operator measurements, not vLLM end-to-end throughput or model accuracy results.** They do not validate the complete adapter lifecycle in this PR.

Both arms use the same generated logical MXFP4 weights, BF16 inputs, precomputed normalized top-8 routing, MXFP8 activations, BF16 intermediate rounding, and BF16 output. TP=8, H=6144, global I=2048, local I=256, E=384. Router GEMM/top-k is excluded; input quantization, route organization, expert combination, and TP reduction are included.

- Baseline: explicitly configured FlyDSL split MoE plus `torch.distributed.all_reduce`.
- Candidate: `MegaMoeTP(comm_mode="ar", act_dtype="fp8", comm_dtype="bf16", ar_gather="bf16")`; no external all-reduce.
- Both arms use CUDA Graph and preallocated outputs. Each graph contains 10 calls; each sample replays it 50 times. Reported latency is per operator call, taking the slowest of eight ranks, then the median of seven alternating baseline/candidate pairs.
- Three split tile configurations were tested first. One configuration per M was selected using mean balanced/random baseline latency, then held fixed for an independent confirmation run. This is the best of those tested configurations, **not a claim of a production-optimal baseline**.
