# [CI] Bump Transformers version to 5.20.2

[Upstream PR](https://github.com/vllm-project/vllm/pull/61983) · state: closed · merged: True

## Original PR description

## Overview

Bump Transformers to [v5.20.2](https://github.com/huggingface/transformers/releases/tag/v5.20.2). Follows #60381.

5.20.2 rather than 5.20.0 because it includes huggingface/transformers#49684. Since huggingface/transformers#49404 the Gemma 4 audio encoder always builds its mask with `eager_mask`, which did a host-to-device copy that fails vLLM's GPU sync check (`test_gemma_ragged_audio`).

## Claims

- `requirements/common.txt` allows `transformers >= 5.16.1, < 5.21.0`.
- Test requirements pin `transformers==5.20.2` (cuda, rocm, xpu, cpu, nightly-torch).
- A.X-K1 reads `mlp_layer_types`, which 5.20 builds from `first_k_dense_replace` and `moe_layer_freq` (and stops storing them). Older versions fall back to the old fields.
- The Transformers backend accepts image encoders that return one entry per batch row rather than per item. huggingface/transformers#49557 (5.20.1) made Idefics2/3, SmolVLM and ModernVBERT do this, which broke `idefics3-transformers` ("Expected number of multimodal embeddings to match number of input items: 2, but got 1").
- The Transformers backend treats `num_nextn_predict_layers=None` as 0. Mellum's 5.20 config aliases it to the new `num_mtp_layers`, which defaults to `None`.
- `min_transformers_version="5.20.0"` on `Kolibri1ForCausalLM` is kept, since 5.16.1 to 5.19.x are still supported. The `transformers-upgrade` skill now says to keep such gates until the floor reaches them, instead of removing them on a pin bump.

## Validation

- `pre-commit run` on the changed files passes. The `pip-compile` hooks for cuda, rocm, xpu and cpu resolve the pinned version and leave the hand-edited lock files unchanged.
- `pytest tests/transformers_utils tests/config tests/tokenizers_` on 5.20.0 (macOS, no GPU): 1202 passed, 253 skipped, 2 failed. Neither failure is from this change: `test_ray_runtime_env` needs Ray, and `test_mp_reducer` can't start an engine on this machine (it fails the same way on 5.19.0).
- Checked against the 5.20 breaking changes:
  - Every vendored config that declares `sub_configs` builds and round-trips through `to_dict()` (`SubConfigSpec`, huggingface/transformers#48282).
  - The `embedding_gemma2` imports vLLM uses still resolve (huggingface/transformers#49473).
- A.X-K1 (`skt/A.X-K1`) and Mellum: `dump_model.py` on this branch with 5.20 matches `main` with 5.19 (0 diffs). `main` with 5.20 fails to build A.X-K1 (`AttributeError: first_k_dense_replace`).
- Gemma 4 audio: on 1x B200 with `VLLM_GPU_SYNC_CHECK=error`, the audio tower raises a sync error in `eager_mask` on 5.20.0 and runs without one with the fix from huggingface/transformers#49684, with bitwise identical output.
- `test_common.py -k idefics3-transformers` on 1x B200, 5.20.2, `VLLM_GPU_SYNC_CHECK=error`: 2 failed without the fix, 2 passed with it.
- CI on this PR: the A.X-K1, Mellum and Gemma 4 audio failures from the first run are fixed. The remaining failures in build 95621 also failed on `main` at the time and have since been fixed there.
