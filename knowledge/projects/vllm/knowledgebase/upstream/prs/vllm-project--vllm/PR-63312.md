# [Bugfix][Tokenizer] Fix Kimi-Audio special token encoding and skipping

[Upstream PR](https://github.com/vllm-project/vllm/pull/63312) · state: open · merged: False

## Original PR description

## Overview

`KimiAudioTokenizer` registers only 6 hardcoded tokens while `tokenizer_config.json` declares 421, and the call sites that need that set disagree: `encode()` rejects every prompt, `all_special_tokens` returns `AddedToken` objects, and streaming leaks `[EOS]`.

## Changes

- `allowed_special` = config tokens ∪ the 6 hardcoded ones. On main, `encode("<|im_user_msg_start|>hello")` raises `ValueError: Encountered text corresponding to disallowed special token`: 415 config tokens are registered as tiktoken special tokens but not allowed, and the chat template emits them.
- `all_special_tokens` returns `list[str]`; `AddedToken` never compares equal to a token string and made `_build_drop_info` raise `TypeError` on every parser-engine stream.
- `convert_ids_to_tokens(skip_special_tokens=True)` skips the same ids as `decode()`, using one `frozenset` built in `__init__` (no per-token rebuild).

## Validation

`pytest tests/tokenizers_/test_kimi_audio.py -v` — 3 of 4 assertions fail on main, all pass here. Against `moonshotai/Kimi-Audio-7B-Instruct`:

- `detokenize_incrementally` per step: 5.78 µs → 5.52 µs
- `encode("<|im_user_msg_start|>hello")`: `ValueError` → `[151646, 14990]`
- streaming with `skip_special_tokens=True`: leaks `[EOS]` → clean

## Notes

- Special-token strings in the prompt are now encoded instead of raising, as in HF tokenizers. `encode()` costs ~68 µs vs ~32 µs per call (tiktoken rebuilds its matcher over 421 strings); once per request.
- Known gap: `convert_tokens_to_ids` / `skip_special_tokens=False` still only know the 6 hardcoded tokens, so the rest come back as `<|unk|>`. Visible only when a client sets `skip_special_tokens=False` (default `True`).
