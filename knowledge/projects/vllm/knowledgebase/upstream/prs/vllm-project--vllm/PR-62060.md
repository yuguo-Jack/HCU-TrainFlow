# [MoE] Stage UVA-offloaded expert weights in VRAM for large steps

[Upstream PR](https://github.com/vllm-project/vllm/pull/62060) · state: open · merged: False

## Original PR description



## Overview

With UVA weight offloading (`--offload-backend uva --cpu-offload-gb N --cpu-offload-params experts`), the fused-MoE kernel reads offloaded experts from host memory in place, once per M-tile (64 tokens with the default config here) of the tokens routed to each expert, so in prefill every offloaded expert crosses PCIe several times per step. This adds an opt-in `--cpu-offload-stage-min-tokens` (default 0 = off; `auto` = every step that runs without CUDA graphs): such steps copy each layer's offloaded `w1`/`w2` into a reusable device buffer right before the expert kernel, which reads the copy. Decode and every graph-captured step keep today's zero-copy reads.

## Claims

vLLM 0.31.0 with this patch against stock 0.31.0; Qwen3-30B-A3B-Instruct-2507-FP8, one RTX 4090 (PCIe 4.0 x16), 16 GiB of experts offloaded.

- **End to end** (16 multi-turn sessions, 16–19k-token prompts, 4 turns, 2 in flight; 3 interleaved runs per arm, spread < 0.1%): wall time **1.785× shorter at 2048-token chunks, 2.687× at 8192**; new-session TTFT p50 17.52 → 8.51 s and 21.89 → 4.93 s.
- **Decode unchanged** (ShareGPT at 1 and 4 in flight within 0.05 tok/s). **Exact:** staging off vs `auto` in one build gives byte-identical greedy output on 18/18 requests; GSM8K 0.896 vs 0.900 (±0.019) against stock.
- **Cost:** one buffer per offloaded expert-weight shape (576 MiB here), allocated in the profiling run so the KV cache is sized with it: −6,144 KV tokens at 8192-token chunks (exactly the buffers), −6,752 at 2048 (~57 MiB more, not traced).
- **235B-A22B FP8, TP8** (16 GiB experts/GPU, one run per arm): 1.52× on 4 sessions × 2 turns at 1 in flight, 1.39× on a following 16-request run at 2 in flight; decode unchanged. Not checked for identical output: this setup is not reproducible run to run even without the patch.

## Details

**Root cause.** `fused_moe_kernel` gives each program one M-tile of one expert and streams that expert's weights, so every tile re-reads the expert. In VRAM that is cheap; over UVA each re-read crosses PCIe (0.97–0.98 host reads per tile). A tuned `BLOCK_SIZE_M` 128 config helps UVA 1.4–1.9× but copying in is still 1.1–6× faster, and it slows the all-in-VRAM case 8–12% at ≥ 2048 tokens.

**Design.** `BaseOffloader.maybe_stage(weight, num_tokens, slot)` returns the weight unchanged except in `UVAOffloader`, whose `UVAExpertStager` copies a weight carrying the UVA marker when the step meets the threshold and the stream is not capturing. `FusedMoEKernelModularImpl.apply` calls it for `w1`/`w2` after `_prepare`, unless the experts set `reads_weight_args = False` (FlashInfer MoE-EP and b12x run on weights prepared at load time). It is a copy, not a cache: no routing inspection (no device-to-host sync), no eviction, any layout the kernel reads, nothing to invalidate after EPLB or weight updates. One buffer per (slot, shape, stride, dtype, device) is shared by all layers; copy and kernel run on the same stream, so layer l+1's copy waits for layer l's kernel (also under DBO, whose micro-batches share the stream). `auto` resolves in `VllmConfig.__post_init__` to `max(max_cudagraph_capture_size + 1, 512)`; an explicit N at or below the capture size warns, since captured steps never stage. The threshold is left out of `compute_hash` (it acts inside the opaque `moe_forward` op). Like the other offload options, the flag is documented through the CLI help; there is no offload docs page to extend.

**Why opt-in.** It shrinks the KV cache of every `--cpu-offload-gb` user by the buffers (several GiB for large BF16 MoE layers), and it is unmeasured on NVLink-C2C systems and APUs, where reading in place may already be fast enough.

**Limitations.** CUDA only: ROCm AITER kernels read a per-tensor attribute (`is_shuffled`) that the buffer does not carry, and a backend keyed on the weight's `data_ptr` would see one address for every layer (none in the modular path is); such backends must opt out via `reads_weight_args`. Measured with Triton experts and FP8 block weights only; FlashInfer, DeepGEMM and CUTLASS experts untested. Only the modular fused-MoE path; monolithic kernels read in place as before. Under DBO each micro-batch copies the layer. With all2all EP the threshold counts tokens before dispatch. The buffers are not in the sleep-mode pool, and come on top of `--kv-cache-memory-bytes`. Copy and compute are sequential: double-buffering would save 4% at 2048-token steps and 12–19% at 8k–16k (microbenchmark), for a second buffer; left as a follow-up.

**Not a duplicate.** #37190 (open) is an opt-in GPU expert *cache*: it inspects routing each forward (`topk_ids.unique().tolist()`, a sync per layer), copies missing experts one by one, evicts with LFRU, and runs the MoE layer outside CUDA graphs (it caps `cudagraph_mode` at PIECEWISE). RFC #38256 asks to load each distinct expert once in batched prefill; this is the narrow form of that for the existing UVA path. Residency work (#54610, #56177, #57794, #57943) decides which experts live in VRAM; this composes with it, since only weights carrying the UVA marker are staged. #51710 extends the *prefetch* backend, which copies every step including decode. #54972 edits a different `UVAOffloader` method. Searched 2026-10-09 and rechecked 2026-10-16: none stages UVA experts for large steps.
