# [Bugfix] Register the aten::mm out_dtype overloads for batch invariance

[Upstream PR](https://github.com/vllm-project/vllm/pull/60047) · state: open · merged: False

## Original PR description

## Overview

With `VLLM_BATCH_INVARIANT=1` and an fp32 lm_head (`--hf-overrides '{"head_dtype": "float32"}'`, which
`ModelConfig` documents as "required for RL training-inference consistency"), the head runs
`torch.mm(x, w, out_dtype=torch.float32)`. That call dispatches to `aten::mm.dtype`, a separate overload
from `aten::mm`, so on CUDA SM8x, where batch-invariant mode installs the Triton matmul overrides, it
stays on cuBLAS. Whether the result then depends on the batch size depends on the shape: on an A40,
Mistral-7B-v0.1 (vocab 32000) shows it and Qwen3-0.6B/1.7B (vocab 151936) do not. This PR registers
`aten::mm.dtype` and `aten::mm.dtype_out` next to `aten::mm`.

## Claims

- **Bug:** on `main`, Mistral-7B-v0.1 with an fp32 head gives different logprobs at batch size 1 and 32
  for 32 of 32 prompts on an A40. In an earlier run on an A40 (`main` 34051ad714, driver 595.91.07,
  2026-10-05), Qwen3-0.6B (bs 32) and Qwen3-1.7B (bs 64) with an fp32 head showed no difference; there,
  `torch.mm(out_dtype=fp32)` gave the same row 0 for every M tested at N = 151936, but not at N = 4096,
  8192 or 32000.
- **Root cause:** `aten::mm.dtype` and `aten::mm.dtype_out` are separate overloads of `aten::mm`, and
  `enable_batch_invariant_mode()` does not register them.
- **Fix:** one function, `mm_dtype_batch_invariant`, is registered for both overloads.
  `matmul_persistent()` takes an `out_dtype` and allocates its output in that type; the kernel already
  accumulates in fp32 and casts on store. The function keeps ATen's dtype checks for these overloads
  (for each case the same `RuntimeError` and message as `_mm_dtype_out_cuda`); shape errors still come
  from `matmul_persistent`, as with the existing `aten::mm` override.
- **Scope:** only the CUDA SM8x branch, and every `torch.mm(..., out_dtype=)` there, not just the
  lm_head. In-tree, that is also `GateLinear` tier 5 (the cuBLAS bf16→fp32 router GEMM), the non-SM90
  branch of the Inkling MoE router and the DeepSeek-V4 compressor/indexer scores. On the A40, `GateLinear`
  tier 5 was batch dependent on `main` at all four router shapes tested and is invariant with this PR.
  The lm_head runs eagerly (`compute_logits` is outside the compiled graph) and reaches `aten::mm.dtype`;
  `aten::mm.dtype_out` is what Inductor emits for the compiled callers. Hopper and Blackwell do not install
  the Triton overrides. XPU is unchanged: the fp32-head path is CUDA/ROCm only, and XPU's `aten::mm`
  override uses `matmul_descriptor_persistent`, which this PR does not touch. ROCm has no Triton matmul
  overrides on `main`; #52231 adds them and registers `aten::mm.out`, not `aten::mm.dtype`, so the same
  gap would reach ROCm when it lands.
- **Cost:** with the flag on, the fp32 head GEMM runs on the Triton persistent matmul instead of
  cuBLASLt. On the A40 that is 0.2–0.3 ms slower per call up to M=32 (Mistral-7B head shape), about the
  same at M=128 and 9% slower at M=512. It did not show in `vllm bench serve`.

Thanks for the work!

Please take a look at this AI generated comment:

```bash
I think we should preserve the dtype contract of the ATen overloads here.

`mm_dtype_batch_invariant()` currently forwards any `out_dtype` to `matmul_persistent()`, and for `dtype_out` it unconditionally does `out.copy_(result)`. This means enabling batch invariance can make otherwise-invalid calls silently succeed/cast. For example, bf16 inputs with `out_dtype=torch.float16` can now produce an fp16 result, and an fp32 `out_dtype` with a bf16 `out` tensor would be silently cast by `copy_()`.

PyTorch's CUDA/XPU `mm(..., out_dtype=...)` contract only permits the input dtype itself, or fp32 for fp16/bf16 inputs, and the out variant should also require the output tensor dtype to match `out_dtype`.

Could we preserve those checks in this override (and ideally add a small negative test)? Since this replaces the CUDA implementation globally under batch-invariant mode, I think we should avoid changing the operator's semantics beyond the kernel used.
```

# VLLM_BATCH_INVARIANT=1 python repro_60047.py
# Run 32 prompts one at a time (bs=1), then all together (bs=32). With batch invariance
# the sampled tokens' logprobs must be bitwise identical. The lm_head is fp32 here.
import random

from vllm import LLM, SamplingParams

llm = LLM(
    model="mistralai/Mistral-7B-v0.1",
    hf_overrides={"head_dtype": "float32"},
    attention_config={"backend": "TRITON_ATTN"},
    enforce_eager=True,
    max_model_len=2048,
    gpu_memory_utilization=0.6,
    seed=0,
)
random.seed(12345)
words = "the a of to and in is it you that was for on are with as his they be at one have this from".split()
prompts = [" ".join(random.choice(words) for _ in range(random.randint(10, 50))) for _ in range(32)]
params = SamplingParams(temperature=0.0, max_tokens=16, logprobs=5)


def tokens_and_logprobs(output):
    o = output.outputs[0]
    return list(o.token_ids), [step[t].logprob for step, t in zip(o.logprobs, o.token_ids)]


alone = [tokens_and_logprobs(llm.generate([p], params, use_tqdm=False)[0]) for p in prompts]
together = [tokens_and_logprobs(o) for o in llm.generate(prompts, params, use_tqdm=False)]

differ, max_delta, token_diverged = 0, 0.0, 0
for (t1, l1), (t2, l2) in zip(alone, together):
    token_diverged += t1 != t2
    delta = max(abs(a - b) for a, b in zip(l1, l2))
    differ += delta != 0
    max_delta = max(max_delta, delta)
print(f"prompts whose logprobs differ between bs=1 and bs=32: {differ}/32")
print(f"max |logprob(bs=1) - logprob(bs=32)|: {max_delta:.3e}")
print(f"prompts whose greedy tokens differ: {token_diverged}/32")
