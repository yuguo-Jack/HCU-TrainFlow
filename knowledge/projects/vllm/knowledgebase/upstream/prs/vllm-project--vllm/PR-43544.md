## Purpose

Adds support for **Gumiho** as a new speculative decoding method
(`speculative_config={"method": "gumiho", ...}`).

Gumiho is a hybrid drafter:

1. The first two speculative tokens are generated autoregressively by a
   small EAGLE-style transformer head.
2. Every additional speculative token is generated **in parallel** by
   per-position MLP heads conditioned on the embeddings and hidden states
   of the first two draft tokens.

This trades a small amount of acceptance rate for a meaningful reduction in
drafter latency when `num_speculative_tokens > 2`, with no change to the
verifier or rejection sampler.

The drafter wraps a 2-layer Llama backbone, so it is implemented as an EAGLE
proposer subclass (`GumihoProposer`) plus a separate drafter model
(`GumihoLlamaForCausalLM`). All EAGLE-style infrastructure (padded drafter
batch, KV slot bookkeeping, cudagraph dispatch, attention metadata building,
rejection sampling) is reused as-is.

## Design Notes

### Why a new proposer instead of extending `EagleProposer`?

`GumihoProposer` is a one-class subclass of `EagleProposer` that overrides
exactly two hooks (`_init_draft_hidden_states_list`,
`_maybe_get_mlp_draft_token_ids`) on the shared `SpecDecodeBaseProposer`.
Everything else — padded drafter batch, KV slot mapping, attention metadata,
cudagraph dispatch — is inherited unchanged. The hooks are no-ops in the
base class so this PR is non-functional for every other proposer.

### Where the MLP heads fit in

```
target model forward
    -> target hidden states
    -> GumihoProposer.propose() (inherits SpecDecodeBaseProposer.propose)
        -> transformer draft head: token 1   (sample_hidden_states)
        -> transformer draft head: token 2   (first loop iteration)
        -> _maybe_get_mlp_draft_token_ids:
             GumihoLlamaForCausalLM.generate_mlp_draft_token_ids
             -> remaining tokens generated in parallel by MLP heads
        -> break out of the sequential loop
    -> V1 target verify
    -> V1 rejection sampler
```

### Greedy-only MLP path

The MLP heads currently produce argmax token ids only, so when
`draft_sample_method=probabilistic` the proposer falls back to the regular
sequential drafting path. Extending the MLP heads to emit logits/probs is
left to a follow-up.

### Not in this PR (potential follow-ups)

- Tree attention / FTA verification (the released Gumiho training code has
  this; the V1 verifier does not support tree drafts yet).
- Multimodal drafters.
- The V2 GPU model runner path.

```bash
python examples/features/speculative_decoding/spec_decode_offline.py \
  --method gumiho --gumiho-dir /cache/gumiho/amd-Gumiho-llama3-8b \
  --num-spec-tokens K \
  --dataset-name hf --dataset-path philschmid/mt-bench --num-prompts 80 \
  --temp 0 --top-p 1.0 --max-model-len 8192 --output-len 256
```

| Method | K | mean acceptance length | acc@pos0 | acc@pos1 | acc@pos2 | acc@pos3 | acc@pos4 | acc@pos5 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| (no spec) | – | 1.00 | – | – | – | – | – | – |
| **gumiho** | 3 | **2.11** | 0.61 | 0.33 | 0.18 | – | – | – |
| **gumiho** | 6 | **2.26** | 0.60 | 0.32 | 0.17 | 0.09 | 0.05 | 0.03 |

`K=6` exercises 4 of the 5 MLP heads contained in the released
``amd/Gumiho-llama3-8b`` checkpoint and is closer to the configuration
reported in the paper. Acceptance lengths align with the paper's Llama-3
8B numbers (Table 1) within the differences expected from the V1 verifier
not yet using tree attention.

### Throughput (batched, 80 prompts, single MI300X)

| Configuration | output tokens/s | wall-clock |
| --- | --- | --- |
| no spec | 4682 | 3.6 s |
| gumiho, k=3 | 3026 | 5.6 s |
| gumiho, k=6 | 2907 | 5.9 s |

**Note**: ``mt-bench --num-prompts 80`` runs all 80 prompts as one fully
batched offline job that finishes in a few seconds, which is the
throughput-saturated regime — speculative decoding deliberately trades some
of that aggregate throughput for lower **per-request latency** at low
QPS / batch=1, where the speedups in the paper were measured. A
latency-focused benchmark (single request, ``benchmark_latency.py``) is a
better fit for comparing against EAGLE/EAGLE-2 here and is left for a
follow-up commit.

## Backward Compatibility

- All hook methods in `SpecDecodeBaseProposer` are no-ops by default. No
  existing proposer changes behaviour.
- `use_eagle()` returns True for `gumiho`, but the drafter branch in
  `gpu_model_runner.py` matches `method == "gumiho"` first, so existing
  EAGLE / EAGLE3 / MTP / DFlash paths are unaffected.
- V2 GPU model runner raises `NotImplementedError` for Gumiho with a clear
  message instead of silently falling back.

I'm generally a fan of block-wise decoding for speculative-decoding as opposed to fully autoregressive or fully parallel. I've done some studies in the past indicating that 2-parallel + 9-parallel would be more effective than 11-parallel drafting. However, I'm skeptical of this implementation:

File: `vllm/model_executor/models/gumiho.py` · line None

![high](https://www.gstatic.com/codereviewagent/high-priority.svg)

The current implementation performs the LM head projection (`compute_logits`) and argmax sequentially in a Python loop for each speculative token. Since the LM head is typically the most computationally expensive part of the drafter (especially with large vocabularies), batching these operations into a single projection will significantly reduce drafter latency and improve overall throughput.

```python
        all_hidden_states = []
        for block in self.mlp[:num_tokens]:
            all_hidden_states.append(block(mlp_input))

        # Batch the MLP heads and LM head projection for better efficiency.
        # [num_tokens, batch, hidden_size] -> [num_tokens * batch, hidden_size]
        stacked_hidden_states = torch.stack(all_hidden_states, dim=0)
        batch_size = mlp_input.shape[0]
        flat_hidden_states = stacked_hidden_states.view(-1, self.config.hidden_size)

        all_logits = self.compute_logits(flat_hidden_states)

        # [num_tokens * batch] -> [num_tokens, batch] -> [batch, num_tokens]
        all_token_ids = all_logits.argmax(dim=-1).view(num_tokens, batch_size)
        return all_token_ids.transpose(0, 1)
```
