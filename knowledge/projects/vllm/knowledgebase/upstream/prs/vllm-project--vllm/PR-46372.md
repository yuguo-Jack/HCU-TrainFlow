# fix: make NCCL collectives eager break points in breakable cudagraph

[Upstream PR](https://github.com/vllm-project/vllm/pull/46372) · state: closed · merged: False

## Original PR description

Cross-node NCCL collectives (host-staged, no GPUDirect) cannot be captured in CUDA graphs. They were causing 'illegal memory access at capture_end' errors when captured by breakable_cudagraph.

Changes:
- Add @eager_break_during_capture to tensor_model_parallel_all_reduce, tensor_model_parallel_all_gather, and tensor_model_parallel_reduce_scatter
- Copy result back to input buffer for correct cudagraph replay
- Remove FULL mode skip from eager_break_during_capture decorator so communication ops break regardless of cudagraph mode

Fixes the capture phase crash on multi-node GB10 (no GPUDirect RDMA).
fixes #46253

- DoctorMasterNewb · comment · 2026-06-23T13:35:19Z · [source](https://github.com/vllm-project/vllm/pull/46372#issuecomment-4779778585)

Sharing results from the original GB10 (DGX Spark) 2-node setup in #46253 — we independently prototyped this exact eager-break approach via monkeypatch, so a few things this PR will hit downstream:

**1. The `copy_` back is shape-incorrect for `all_gather` / `reduce_scatter`.**
`input_.copy_(result)` assumes `result` and `input_` share a shape. That only holds for **all-reduce** (sendbuf==recvbuf). `all_gather` returns a tensor `world_size×` *larger* along `dim`; `reduce_scatter` returns one `world_size×` *smaller*. Neither is broadcastable to `input_`, so those two lines raise `RuntimeError: shape mismatch` the moment the op runs on a TP>1 path. In our patch we deliberately applied the in-place copy-back to **all-reduce only**. The all-gather/reduce-scatter eager-break needs to return a fresh (but stable-addressed) buffer instead — see point 2.

**2. Capture succeeding is the easy half — replay is the wall.** With the all-reduce eager-break in place, capture finished cleanly for us ("Graph capturing finished in 1 secs"), matching the PR's intent. But **replay produced ~zero/garbage logits**. We tried both an out-of-place+copy all-reduce and a true in-place `torch.distributed.all_reduce` — both garbage, so the collective wrapper isn't the cause. The captured compute *segments around the break* need to share **static buffers** with the eager-break output across the break boundary; a fresh tensor (or one whose address changes per replay) corrupts the downstream captured segment. This is the part worth designing before merge — eager-breaking the collective without guaranteeing stable buffering on both sides gives correct capture and wrong output.

**3. Without `CUDA_LAUNCH_BLOCKING=1`, capture deadlocks** (`shm_broadcast: No available shared memory broadcast block found in 60 seconds`) — a lazy-Triton-JIT/NCCL desync between ranks *during* capture on the host-staged (no-GPUDirect) multi-node transport. CLB serializes the ranks and avoids it but cripples throughput. So a complete fix also needs all Triton kernels (incl. spec-decode/sampling) pre-warmed before capture so a lazy JIT can't desync ranks mid-capture.

**4. Re removing the FULL-mode skip:** on single-node/NVLink the custom all-reduce *is* graph-capturable, so unconditionally eager-breaking it there is a likely perf regression for the common case (consistent with @BoyuanFeng's NCCL-2.9 point). A transport-capability probe (is this collective graph-capturable on this transport?) selecting whether to break would scope the change to the host-staged case that actually needs it.

Happy to test revisions on the 2-node GB10 pair. Full root-cause writeup is in #46253.

Follow-up from the 2× GB10 (DGX Spark) pair — I ran the **faithful M3 case** (the model in #46253),

**Result: still crashes at capture, same as #46253.** The model loads fully, then:
```
[breakable_cudagraph.py] Breakable CUDA graph enabled
[gpu_model_runner.py] Profiling CUDA graph memory: PIECEWISE=3 (largest=4)
[rank0] ProcessGroupNCCL: CUDA error: an illegal memory access was encountered
```
So eager-breaking `tensor_model_parallel_all_reduce` is **not sufficient** for this model. Note our run
actually carried an even *fuller* eager-break than this PR (also covering the fused-AR fallback across
multiple modules) and it **still** faulted — so the gap isn't just the all-reduce.

The most likely remaining culprit: M3 runs **expert-parallel (EP=2)**, and its expert-dispatch
collectives go through a separate **`ep:0`** PYNCCL group (reduce_scatter / all_gather), which an
all_reduce-only eager-break doesn't touch. Those cross-node collectives get captured and fault on the
host-staged (no-GPUDirect) transport, exactly like the all-reduce did. (I can't fully rule out the
separate sm_121 large-MoE capture issue without the faulting kernel, but the NCCL-watchdog signature
points at a captured collective.)

Suggestion: to fix the real models, the eager-break needs to cover **all** cross-node collectives on
the capture path — `all_gather` and `reduce_scatter` (incl. the EP groups), not just `all_reduce` —
with the shape-correct buffer handling we discussed earlier, and ideally gated to the host-staged
transport so single-node/NVLull isn't penalized. Happy to test a revision on the pair.

Two practical notes for anyone reproducing on current main:
- This PR's top-level `from vllm.compilation.breakable_cudagraph import eager_break_during_capture` in
  `communication_op.py` triggers a **circular import** on dev537 (`communication_op` is imported during
  early `vllm.config` init → `compilation.monitor` → `vllm.config`). A lazy/deferred import avoids it.
- `enforce_eager=False` + custom-quant auto-enables `VLLM_USE_BREAKABLE_CUDAGRAPH`, which is the path
  that captures the collective; that's the configuration that reproduces #46253.

Quick correction/refinement to my last comment — I tested the EP-collective hypothesis directly and it does **not** hold.

I captured a **single** cross-node `all_gather`, `reduce_scatter`, `all_to_all` (the EP-dispatch primitives) and `all_reduce`, each into its own `torch.cuda.CUDAGraph`, on the 2× GB10 pair (host-staged NCCL, no GPUDirect):

```
all_reduce      CAPTURE: OK
all_gather      CAPTURE: OK
reduce_scatter  CAPTURE: OK
all_to_all      CAPTURE: OK
```

So the EP collectives are **not** uncapturable here — they all graph-capture cleanly in isolation. That means M3's capture crash is **not** an uncovered/uncapturable EP collective (my earlier guess was wrong). The residual fault is therefore either the **sm_121 large-MoE kernel capture itself** (independent of any collective — large-expert MoE dispatch is known to fail cudagraph capture on this arch with `illegal memory access`, even single-node), or a collective captured **in-context** (buffer interaction with surrounding captured ops), which an isolated single-op capture won't reveal.

Net for this PR: eager-breaking collectives doesn't get M3 cross-node cudagraphs working, and the blocker doesn't appear to be collective *capturability*. The eager-break may still be the right call for the in-context buffer case, but for a large EP-MoE like M3 the dominant wall looks like the MoE-kernel capture, which this PR can't address. Happy to share the repro scripts.
