# [Attention] Support FlashInfer attention sinks on SM8x

[Upstream PR](https://github.com/vllm-project/vllm/pull/59878) · state: open · merged: False

## Original PR description

## Purpose

The FlashInfer backend serves attention sinks only where XQA (SM90, SM12x) or trtllm-gen (SM100) handles decode, so on SM8x a sink model such as gpt-oss cannot use it. On SM8x this leaves gpt-oss on TRITON_ATTN, and an FP8 KV cache has no backend at all, since Triton's FP8 KV cache needs SM89+.

This routes every layer with sinks through FlashInfer's fa2 sink wrappers for causal and non-causal prefill and for decode, and `supports_sink()` returns True on SM8x. As a result, on SM8x:

- gpt-oss with an FP8 KV cache now runs.
- gpt-oss with a BF16 KV cache now selects FLASHINFER instead of TRITON_ATTN, by backend priority. Measurements are below.

This depends on [FlashInfer #6021](https://github.com/flashinfer-ai/flashinfer/pull/6021), which adds `BatchDecodeWithAttentionSinkWrapper`, the decode counterpart of `BatchAttentionWithAttentionSinkWrapper`. That PR is merged but not yet in a FlashInfer release; it will ship in the next one. The wrapper is imported unconditionally, so this can merge only after that release and a bump of vLLM's FlashInfer pin.

The open draft #37949 would instead keep sink models on TRITON_ATTN on SM8x. With that policy, this PR still gives FP8 KV caches a backend on SM80 and SM86.

I used Codex and Claude while implementing and preparing this PR. I reviewed the final diff and ran the tests below.

## Test Plan

```
python -m pytest tests/v1/attention/test_attention_backends.py -k flashinfer
pre-commit run --files vllm/v1/attention/backends/flashinfer.py
vllm bench latency --model openai/gpt-oss-20b --attention-backend <TRITON_ATTN|FLASHINFER> --input-len 1024 --output-len 128 --batch-size <1|32>
vllm bench throughput --model openai/gpt-oss-20b --attention-backend <TRITON_ATTN|FLASHINFER> --dataset-name random --random-input-len 1024 --random-output-len 256 --num-prompts 200
```

## Test Result

All runs are on sm_80 with [FlashInfer #6021](https://github.com/flashinfer-ai/flashinfer/pull/6021) applied.

- `test_attention_backends.py -k flashinfer`: 20 passed, 8 failed. The 8 failures (`test_flashinfer_cross_layer_layout`) also fail on `main`, because the test model `meta-llama/Meta-Llama-3-8B` is gated in this environment. pre-commit passes.
- gpt-oss-20b, teacher-forced on TRITON_ATTN's own BF16 output (339 tokens over four chat prompts of up to 1,840 tokens), compared with TRITON_ATTN:

| KV cache | Backend | Mean abs. logprob diff | Max | Top-1 agreement |
| --- | --- | ---: | ---: | ---: |
| BF16 | FLASHINFER | 0.018 | 0.260 | 335/339 |
| FP8 | FLASHINFER | 0.037 | 0.391 | 332/339 |

Performance with a BF16 KV cache, averaged over two GPUs that each ran both backends back to back, in opposite orders:

| Measurement | TRITON_ATTN | FLASHINFER | FLASHINFER vs TRITON_ATTN |
| --- | ---: | ---: | --- |
| Latency, batch 1, 1024 in / 128 out | 0.671 s | 0.682 s | 1.73% higher |
| Latency, batch 32, 1024 in / 128 out | 3.974 s | 3.864 s | 2.76% lower |
| Throughput, 200 prompts, 1024 in / 256 out | 11,283 tok/s | 11,546 tok/s | 2.34% higher |

The batch-1 gap is in decode, about 0.07 ms per step, while prefill matches. In an nsys profile of batch-1 decode, FlashInfer's decode attention kernel takes 9.07 µs per layer against 4.73 µs for Triton's.

The BF16 teacher-forced run stalled twice, with the GPU at 100% and the engine waiting on its first step, while another job was also using the GPUs. Four standalone runs completed, so the stall has not been reproduced and its cause is not determined.

Not verified: SM12x and SM90 hardware, and non-causal attention with a sliding window (xfail in FlashInfer's own tests).
