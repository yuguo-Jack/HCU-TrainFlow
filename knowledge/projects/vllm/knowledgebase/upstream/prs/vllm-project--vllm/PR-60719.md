# [Bugfix] Reject `--convert embed/classify` with non-pooling runners at config time

[Upstream PR](https://github.com/vllm-project/vllm/pull/60719) · state: open · merged: False

## Original PR description

## Overview

Fixes #60435. `ModelConfig` now rejects `convert="classify"` or `"embed"` with `runner="generate"` or `"draft"` and raises a clear `ValueError`. Before, this pair passed validation for natively generative models and then crashed during model load with a bare `AssertionError` in `_init_pooler`.

## Claims

- `LLM(model="Qwen/Qwen2.5-0.5B-Instruct", convert="classify", runner="generate")` now fails in `EngineArgs.create_engine_config()` with: ``--convert classify` is not supported with `--runner generate`. Use `--runner pooling` or `--runner auto` instead.`` No engine process starts.
- The same check covers `embed` and the `draft` runner, which had the same gap.
- Valid pairs work as before. With `convert="auto"`, generate and draft still resolve to `none`. `classify`/`embed` with `runner="pooling"` or `"auto"` still get a pooling config.
- Adds `test_convert_rejected_for_non_pooling_runner` in `tests/test_config.py`.

## Details

**Root cause.** `_RUNNER_CONVERTS` in `vllm/config/model.py` lists the converters each runner can use: `{"generate": [], "pooling": ["embed", "classify"], "draft": []}`. But `ModelConfig.__post_init__` only checked this table when `runner_type == "generate" and not is_generative_model`. `Qwen2ForCausalLM` is generative, so the check was skipped and `convert_type="classify"` stayed with `runner_type="generate"`. `pooler_config` is only built for the pooling runner, so it stayed `None`. The model loader still applied `as_seq_cls_model` because `convert_type == "classify"`. The resulting `Qwen2ForSequenceClassification` then hit `assert pooler_config is not None` in `_init_pooler`. A debug run showed these values: `is_generative_model=True`, `convert_type='classify'`, and `pooler_config=None` in `_init_pooler`. `as_embedding_model._init_pooler` has the same assert (`adapters.py:275`). The check has looked like this since `ModelConfig` moved to `vllm/config/model.py` (#25252), so this is not a recent regression.

**Why reject the pair.** The embed and seq-cls adapters build the model without `LogitsProcessor` and `ParallelLMHead`, but the generate runner needs vocab logits. To check this, I forced a pooler config for this pair and loaded dummy weights. The engine got past `_init_pooler` and then failed in `compute_logits` with `RuntimeError: StageMissingLayer(stage_name='output') should not be called`. So the pair cannot work. The real bug is the config check that was scoped too narrowly.

**Fix.** Right after `convert_type` is resolved, check it against `_RUNNER_CONVERTS[runner_type]` for every runner. `"none"` is excluded because it is in no list. With `convert="auto"`, the generate and draft runners never get `embed` or `classify`: every generate entry in `_SUFFIX_TO_DEFAULTS` maps to `none`, and there are no draft entries. The speculative draft config does not pass `convert`. So the new check only rejects an explicit `--convert` that the runner cannot run.

**Notes for review.**

- The older generate-only check below the new one is now partly redundant. I left it unchanged to keep the diff small.
- A pure pooling model with an explicit `--convert embed --runner generate` now gets the new message instead of "Embedding models do not support `--runner generate`". Both are `ValueError`s.
- The new test uses `Qwen/Qwen2.5-1.5B-Instruct` from the Hub. `test_draft_runner` in the same file already uses it.
- Related open PR: #60441 adds a check in the same place for the same issue, but it covers only `classify` and does not use `_RUNNER_CONVERTS`. This PR applies the existing table, so it also covers `embed` and the `draft` runner.
