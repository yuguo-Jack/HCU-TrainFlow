# [ROCm][Bugfix] W4A16 dense prefill cache: count cached allocator blocks as free in the budget check

[Upstream PR](https://github.com/vllm-project/vllm/pull/64744) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

With `kernel_config.rdna_hybrid_w4a16_prefill_dequant=enable` (#60710), `_fits_in_memory_budget` treats blocks held by the torch caching allocator as used. Configs that fit fail at load time with `Not enough room in the gpu_memory_utilization budget ...`. This change counts those blocks as free. Port of ROCm/vllm#1411.

## Claims

- Fixes spurious startup failures of the dense prefill cache when the allocator holds cached-free blocks from load-time temporaries.
- Gemma-4-31B AWQ-4bit + MTP-3 on gfx1151: minimum accepted `gpu_memory_utilization` drops from 0.891 to 0.840, and configs in between now start and serve.
- No runtime cost: the check runs only during weight loading and adds no flush or device sync.

## Validation

End to end: `cyankiwi/gemma-4-31B-it-AWQ-4bit`, MTP draft `google/gemma-4-31B-it-assistant` (3 tokens), `max_model_len=4096`, `max_num_seqs=1`, `kernel_config={"rdna_hybrid_w4a16_prefill_dequant": "enable"}`; greedy chat prompt "What is the capital of France?".

## Details

Blocks the caching allocator keeps after load-time temporaries (checkpoint loading, int4 unpack/dequant scratch) are reused by the next allocation, and KV-cache sizing already excludes them, so the check over-reserved by an amount that depends on allocator state (5.4 GiB here, 15.4 GiB on a build that also loads an int8 lm_head, where the same model failed at 0.99). The check now adds `MemorySnapshot`'s `torch_memory - torch_allocated` to free memory; headroom, min-KV reservation and all-or-nothing behavior are unchanged.

Alternatives considered:
- `torch.accelerator.empty_cache()` before or after a failed check: also works, but adds a sync and fresh allocations, and would also run on weight reload and sleep/wake.
- `PYTORCH_ALLOC_CONF=expandable_segments:True`: worse (more cached-free).
- `garbage_collection_threshold`: no effect without a per-process memory fraction, which vLLM does not set.

Not a duplicate: no open PR touches `_fits_in_memory_budget`. #61193 is a different dense-prefill approach and does not have this check.
