# [Rust Frontend][Feature] Support separate tokenizer and config sources

[Upstream PR](https://github.com/vllm-project/vllm/pull/57178) · state: closed · merged: False

## Original PR description




## Purpose

The Rust frontend currently rejects `--tokenizer`,
  `--tokenizer-revision`, and `--hf-config-path` during startup.

  Its model-file resolver also assumes that tokenizer files, model config,
  chat template, generation config, and processor metadata all come from
  one repository and revision. This prevents deployments from pairing model
  artifacts with a compatible tokenizer or config stored separately, including
  repackaged checkpoints.

  The Rust frontend now has the underlying revision-aware file resolution,
  cache, offline, and config override capabilities needed to support independent
  tokenizer and config sources. Supporting these options also aligns the Rust
  frontend with the Python serving path and keeps managed launches consistent
  end to end.

  Add support for all three options with the following source mapping:

  - Tokenizer files, tokenizer config, and the default chat template use
    `--tokenizer`, which defaults to the model source, and
    `--tokenizer-revision`, which defaults to `--revision`.
  - Model config and generation config use `--hf-config-path`, which defaults
    to the model source, together with `--revision`.
  - Multimodal processor metadata continues to use the model source and
    `--revision`.
  - Managed launches forward explicitly provided options to the Python engine.
  - The existing single-source resolution path remains unchanged when none
    of the new options are provided.

  When separate-source resolution is active, the selected config source is
  required to contain `config.json`. Separate sources use the same
  local-directory, Hub-cache, offline, and remote-resolution order as the
  existing resolver.
