# [Dependency] Upgrade numba to 0.68.1

[Upstream PR](https://github.com/vllm-project/vllm/pull/64366) · state: open · merged: False

## Original PR description



## Overview

Upgrade numba from 0.65.0 to 0.68.1 (llvmlite 0.47.0 -> 0.50.0) for CUDA, CPU, ROCm and XPU. numba 0.65.x is one of the Python 3.15 blockers listed in #60467. On Python 3.13/3.14 it is also the requirement that holds NumPy below 2.5.

## Claims

- Removes the numba blocker from #60467. numba 0.65.0 refuses to build on Python 3.15 (`Cannot install on Python version 3.15.0; only versions >=3.10,<3.15 are supported`), while 0.68.x ships cp315 wheels.
- A fresh install on Python 3.13/3.14 now resolves NumPy 2.5.4 instead of 2.4.6: numba 0.65.x requires `numpy<2.5`, 0.68.1 allows `numpy<2.6`. On 3.11/3.12, NumPy stays at 2.3.5 because `mistral-common` caps it below 2.4 there.
- vLLM's numba kernels (the N-gram proposer and the fused Kimi image preprocessing) behave the same: identical results, N-gram drafts and acceptance metrics, and compile and run times within noise.
- The test lock files change only in `numba` and `llvmlite`. The s390x image now builds LLVM 22.1.8 instead of 20.1.8, because llvmlite 0.48+ requires LLVM 22.
- The ppc64le build script keeps installing numba from IBM's DevPI index when it has matching numba and llvmlite wheels. Otherwise it builds LLVM 22.1.8, llvmlite and numba from source; today DevPI has no usable wheels, so it builds from source. The wheels for IBM's index are proposed in https://github.com/ppc64le/build-scripts/pull/8869 (llvmlite 0.50.0) and https://github.com/ppc64le/build-scripts/pull/8870 (numba 0.68.1); after they are built and published, the script takes the fast path.

## Details

**Changes between 0.65.0 and 0.68.1 that matter to vLLM.** vLLM uses:
- `@njit(parallel=True)` with `prange` and a reflected `list` argument (N-gram proposer);
- `@njit(parallel=True, cache=True)` (fused Kimi preprocessing);
- `numba.config.THREADING_LAYER` and the `workqueue` layer (`vllm/utils/jit_monitor.py`);
- `get_num_threads` and `set_num_threads`.

The [0.66.0](https://numba.readthedocs.io/en/stable/release/0.66.0-notes.html), [0.67.0](https://numba.readthedocs.io/en/stable/release/0.67.0-notes.html), [0.68.0](https://numba.readthedocs.io/en/stable/release/0.68.0-notes.html) and [0.68.1](https://numba.readthedocs.io/en/stable/release/0.68.1-notes.html) release notes deprecate or remove none of these APIs. Reflected lists still only warn. The relevant upstream changes:
- llvmlite 0.48+ is built on LLVM 22 (numba 0.66.0). Only source builds are affected: `docker/Dockerfile.s390x` and the s390x install docs. UBI 9 still ships LLVM 21 (`llvm-21.1.8-2.el9`), so LLVM 22 is still built from source.
- NumPy 2.5 support came in 0.67.0, Python 3.15 wheels in 0.68.0.
- The cache index now stamps sources by content hash instead of mtime (0.68.0). Old caches are rebuilt, as shown above.
- Linux x86_64 wheels are now `manylinux_2_28`. `torch==2.14.0` already requires `manylinux_2_28`, so the glibc floor does not move.
- `NUMBA_ENABLE_SYS_MONITORING=1` (opt-in) is broken on Python ≥ 3.14.4 in 0.65.0 and works in 0.68.1. On 3.14.7, cProfile saw 0 of 100 jitted calls with 0.65.0 and 100 of 100 with 0.68.1.

**Platforms.**
- TPU: `requirements/tpu.txt` does not list numba (`tpu-inference==0.32.0` pins `numba==0.62.1`), so it is unchanged.
- s390x: `Dockerfile.s390x` builds LLVM, llvmlite and numba from source; their versions move together in this PR.
- ppc64le: `docker/build_vllm_ppc64le.sh` keeps installing numba from IBM's DevPI index when it has both `numba==0.68.1` and `llvmlite==0.50.0` wheels for the interpreter in use (checked with the script's `is_available_on_devpi`). Otherwise it builds LLVM 22.1.8, llvmlite 0.50.0 and numba 0.68.1 from source and installs the two wheels. LLVM uses the PowerPC target and the same CMake flags as `Dockerfile.s390x`. The build runs in a subshell, so the script's LLVM 15 `PATH`/`LLVM_CONFIG` stay as they are for everything else, and the LLVM tree is deleted afterwards (llvmlite links LLVM statically). Today DevPI has no usable wheels for UBI 9 (glibc 2.34): it lists numba up to 0.65.1 and llvmlite up to 0.49.0, and its numba 0.67.0 wheels are `manylinux_2_39`. So the Power build currently takes the source path, which adds an LLVM build to the image build time. That path was validated on x86_64 only; see Validation.

**Not a duplicate.** No open or closed PR or issue targets numba 0.66, 0.67 or 0.68. Earlier numba bumps landed in #15692, #16376 and #34770 (0.65.0). #34764 was closed as included in #34770. Dependabot group PRs that included numba 0.67.0 (e.g. #58081) were closed unmerged. #36981 (riscv64 markers) edits the same `requirements/cpu.txt` line, so whichever PR lands second needs a trivial rebase.
