# [Core][KV Connector] Start capped async KV loads while the batch is full

[Upstream PR](https://github.com/vllm-project/vllm/pull/65319) · state: closed · merged: True

## Original PR description



## Overview

Lets async KV loads (e.g. P/D NIXL pulls on a decode instance) start while the running batch is full, capped by a new `--max-num-inflight-kv-loads`, so a freed slot can go straight to a request whose KV has already arrived. Alternative to #64628 and #61725, which address the same problem; their authors are co-authors of the first commit.

## Claims

- New `--max-num-inflight-kv-loads N` (default `None`: behaviour unchanged). It caps requests holding KV blocks for an async load before they run: loads in progress plus finished loads waiting for a slot.
- With the cap set, requests that may load asynchronously wait in their own queue. Their loads also start while the batch is full or the token budget is spent. A full batch scans only the head of that queue, so requests needing a running slot aren't re-scanned each step.
- New connector hook `KVConnectorBase_V1.may_load_async(request)` decides which requests use that queue. The default keeps the P/D `do_remote_prefill` convention; `MultiConnector` ORs its connectors. An offloading connector can opt in later.

## Validation

- Unit tests (`tests/v1/kv_connector/unit/test_remote_prefill_lifecycle.py`): loads start while the batch is full up to the cap, and a finished load counts until it runs; requests over the cap don't hold back local ones; routing follows `may_load_async`.
- First commit: `test_remote_prefill_lifecycle.py`, `test_kv_load_failure_recovery.py`, `test_remote_decode_lifecycle.py`, `tests/v1/core/test_scheduler.py`, `test_priority_scheduler_random.py`: 334 passed.
- Both commits plus `test_multi_connector.py` and the offloading-connector suites: 1084 passed, 9 failed in multi-connector/offloading tests. **TODO:** confirming whether those also fail on main.
- **TODO: end-to-end P/D benchmark.** Not done yet: high-concurrency decode with a full batch, comparing the default, a sweep of `--max-num-inflight-kv-loads`, and #61725's `--max-async-kv-loads-per-step 4`.

## Details

**Problem.** On a P/D decode instance, a request starts its async KV load only when a running slot is free, although the load takes no slot until its KV arrives. When the batch is full:
1. A slot frees, and the next step starts loads for every waiting request whose blocks fit. #61725 measured 90-140 requests per engine at ~1.6 ms each, a 150-290 ms step that every DP rank waits on.
2. The freed slot then sits idle for a whole transfer, since nothing had been loading for it.
3. Finished loads pile up holding KV blocks until slots free; #61725 measured each 10 adding 0.12-0.15 ms per step.

**This change.** Loads start ahead of free slots, and the cap counts both in-progress and finished-but-waiting loads. That bounds the burst per step (at most `cap − existing` new loads) and the pile-up. In steady state, new loads start as earlier ones are admitted.

**Scheduling.**
- When slots are free, the async-load queue and `waiting` are merged in policy order (FCFS arrival time or priority).
- A head blocked by the cap, or one that needs a running slot while none is free, stops only its own queue for the step.
- `on_new_request` now runs before the request is queued, so `may_load_async` can use what it records.

**Tradeoffs and limitations.**
- The cap must be sized ≈ slot-free rate × load latency. Too low and loads aren't ready when slots free; too high and the first fill can still start up to `cap` loads in one step. A per-step start limit could be layered on if that matters.
- A `may_load_async` false positive holds back the async loads queued behind it until a slot is free.
- Loads in progress still sit in `kv_holding_waiting` and are skipped on steps with a free slot; the cap bounds that cost.
- An adaptive default for the cap was prototyped but left out pending benchmarks.
