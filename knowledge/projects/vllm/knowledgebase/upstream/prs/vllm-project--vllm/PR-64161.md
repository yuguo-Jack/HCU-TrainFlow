# [Core] Mamba align: advance sub-block instead of idling the prefill budget when blocks are large

[Upstream PR](https://github.com/vllm-project/vllm/pull/64161) · state: open · merged: False

## Original PR description

## Purpose

In Mamba `align` mode (the default for hybrid models when prefix caching is on), every non-final prefill chunk must end on an attention-block boundary, because block-aligned chunk ends are where Mamba states get cached. Today, a request whose share of the step budget can't reach its next boundary is **deferred (0 tokens)** whenever a full block would fit in the budget. Sub-block progress is allowed only when the block is wider than the whole budget.

Once the block is a sizable fraction of the token budget, that deferral leaves up to a block's worth of every step's budget unused while other prefills wait. The block size is not a free knob: hybrid models force it to `mamba_page_bytes / attention_bytes_per_token`, so smaller KV formats get *larger* blocks. For example, Qwen3.8-Flash-Next at TP2 on MI355X gets a 3136-token block with FP8 KV and a 5904-token block with a 4.25-bit KV format. Against the default 16,384-token budget:

- a long prompt prefills 5 × 3136 = 15,680 tokens/step with 3136-token blocks, but only 2 × 5904 = 11,808 with 5904-token blocks;
- the leftover budget can't go to other waiting prefills unless they can reach a boundary.

This PR lets such a chunk advance sub-block instead of being deferred, **when the block exceeds a quarter of the prefill budget** (see "The 1/4 guard" below). The existing mid-block stop (`next_block_boundary` for a chunk that starts mid-block) then re-aligns it at its next boundary. So the invariant behind the cached Mamba states, "slot `p` holds the state after exactly `(p + 1) * block_size` tokens", is unchanged. The only behavior change is that, with large blocks, budget which used to sit idle now makes progress. With blocks of at most a quarter of the budget, the code path is exactly the previous one.

**Policy change:** this affects every hybrid model running in `align` mode (prefix caching on), e.g. Qwen3-Next/Qwen3.5-style GDN hybrids and Mamba2 hybrids. It relaxes the previous "sub-block only when no step can fit a full block" rule to "sub-block when the block is more than a quarter of the budget". The trade-off is that a request may take an extra, shorter chunk to re-align. In exchange, no step leaves a large share of its budget unused while prefills are waiting.

**The 1/4 guard.** A sub-block chunk can recover at most one block of a step's budget, but it costs that request one extra, shorter re-align step. When the block is small relative to the budget, the cost wins. On the public model below at the default 16,384-token budget (block 1056, 6% of the budget), taking sub-block chunks unconditionally cost 2.2% output throughput and raised P90 TTFT by 23%. With the guard, that configuration runs the previous code. The wins were measured with blocks at 33% (public model, 3168-token budget) and 36% (Qwen3.8-Flash-Next with a 4.25-bit KV format) of the budget. The neutral-or-negative results were at 6% and 19%. A quarter is between the two. The budget is the scheduler's token budget, capped by `long_prefill_token_threshold` when that is set, as in the previous rule.

## Changes

- `vllm/v1/core/sched/scheduler.py` (`_mamba_block_aligned_split`): truncate to the aligned end when it lies past `start` or the block is at most 1 / `MAMBA_ALIGN_SUB_BLOCK_BUDGET_DIVISOR` (= 4) of the prefill budget; otherwise keep the sub-block chunk.
- Tests: `test_mamba_align_split_when_block_exceeds_scheduling_budget` pinned the old deferral for a block equal to the budget and is updated. `test_internal_checkpoint_split[3602-512-True-*]` (block 10% of the budget) keeps its previous expectation of deferral. New `test_sub_block_chunk_only_when_block_exceeds_budget_fraction` pins the threshold: it defers at budget 16384 and at exactly 4 x block, and takes the sub-block chunk at 4 x block - 1. Every checkpoint-consistency ("poisoning") test passes unchanged.
- New test `test_mamba_align_split_fills_the_step_budget_with_large_blocks` (block 3000, budget 8192): the first request gets 6000 tokens, the second gets the remaining 2192 instead of 0, and the second's next chunk stops at its block boundary (`block_size - 2192`).

`long_prefill_token_threshold` needs no handling here: at both `_mamba_block_aligned_split` call sites, `num_new_tokens` is already capped by the (adaptive) threshold and by the remaining budget, so the split only ever shortens an already-capped chunk.

## Test Result

`pre-run-check` is a label gate for this account, so CI has not run yet. `pre-commit` and the tests below were run locally.

**Unit tests**, MI355X (ROCm nightly image, branch head):

- At the branch head `546231282`: the Test Plan command above, minus `test_hybrid_prefix_cache_hit_rate.py` (which boots a server, below), 816 passed on MI355X.
- `test_hybrid_prefix_cache_hit_rate.py` (boots a server): 2 passed (base and MTP) at the first commit `c13cb9464` (before the guard), with its Python tree over the ROCm nightly image. Not re-run at the head.

**Serving on main, public model, 3168-token budget** (measured before the guard; at block/budget = 1/3 the guard allows sub-block chunks, so this is the code path that ships). `Qwen/Qwen3.5-35B-A3B` (BF16, TP1) on one MI355X, nightly ROCm image at main `5d35ce393`. Both arms are the same image; the after arm overlays only this PR's `scheduler.py`. Align mode forces the attention block to 1056 tokens, so `--max-num-batched-tokens 3168` (block/budget = 1/3). Other flags: `--enable-prefix-caching --mamba-cache-mode align --max-model-len 16384 --max-num-seqs 128 --gpu-memory-utilization 0.42`. Four boots in the order before, after, after, before. Each boot ran a warmup, then `vllm bench serve` with random 7K-in / 512-out prompts, `--ignore-eos`, seed 0 (64 prompts at 16 concurrent, 128 at 64 concurrent).

| point | before (2 boots) | after (2 boots) | change (mean) |
|---|---|---|---|
| 64 concurrent: output tok/s | 1593 / 1639 | 1740 / 1723 | +7.2% |
| 64 concurrent: mean TTFT | 4.69 / 4.45 s | 3.53 / 3.73 s | -21% |
| 16 concurrent: output tok/s | 741 / 751 | 763 / 757 | +1.9% |
| 16 concurrent: mean TTFT | 997 / 952 ms | 955 / 994 ms | 0% |
| 16 concurrent: median TTFT | 637 / 593 ms | 734 / 778 ms | +23% |
| 16 concurrent: P99 TTFT | 3981 / 3789 ms | 3261 / 3370 ms | -15% |
| 64 concurrent: P99 TTFT | 15.89 / 15.15 s | 12.34 / 12.93 s | -19% |

At 64 concurrent the two arms' ranges do not overlap. Median ITL is unchanged (15.6 ms at 16 concurrent, 22.0 ms at 64). The higher median TTFT at 16 concurrent is the trade-off described above: a typical request takes one extra, shorter chunk to re-align, while requests that used to sit deferred are served sooner. The mean stays flat and P99 improves, with non-overlapping ranges at both concurrencies. With 64 requests per run at 16 concurrent, P99 is roughly the single slowest request. Those runs saved only P99, not P90.

**Default budget, public model: why the guard exists.** The same model and flags at `--max-num-batched-tokens 16384` (block 1056, 6% of the budget), 7K in / 512 out at 16 concurrent, ABBA boots, with sub-block chunks taken unconditionally (`3c75ae74a`, before the guard):

| point | before (2 boots) | sub-block always (2 boots) | change (mean) |
|---|---|---|---|
| output tok/s | 830.6 / 831.8 | 814.2 / 811.9 | -2.2% |
| median TTFT | 1170 / 1170 ms | 1162 / 1163 ms | -0.6% |
| mean TTFT | 1081 / 1083 ms | 1191 / 1195 ms | +10% |
| P90 TTFT | 1731 / 1729 ms | 2135 / 2137 ms | +23% |
| P99 TTFT | 2498 / 2534 ms | 2749 / 2780 ms | +10% |

The runs repeat closely (the two before boots are within 0.2%), so this is a real cost, not noise. With the guard, this configuration runs the previous code, so it is unchanged by construction.

**Accuracy.** GSM8K, full test split (1319), 5-shot CoT, greedy, thinking off, same model and server flags, one boot per arm: before 95.83% (1264/1319), after 95.75% (1263/1319). Exact McNemar: 8 problems correct only before and 7 only after, p = 1.0. A greedy output-equality check was also run (32 long prompts, cold and prefix-cached rounds), but it is not informative for this model under concurrent batching: the two *before* boots already agree on only 7/32 (cold) and 5/32 (cached) outputs. Before-vs-after agreement (3–6/32) is at that same floor.

**Serving, larger model** (measured before the guard). Qwen3.8-Flash-Next at TP2 on MI355X, default 16,384-token budget, 7K in / 512 out at 64 concurrent. With a 4.25-bit KV format from #64123 (block 5904, 36% of the budget, so the sub-block path applies), output went from 1069 to 1201 tok/s (+12%) and mean TTFT from 9.54 to 6.07 s. With FP8 KV (block 3136, 19%) the result was within noise, and that configuration now runs the previous code. ITL was unchanged in both.
