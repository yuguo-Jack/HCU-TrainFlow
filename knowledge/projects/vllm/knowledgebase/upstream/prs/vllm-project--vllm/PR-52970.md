# [ROCm][aiter] officially supporting aiter Triton kernels+dsv4 on RDNA3

[Upstream PR](https://github.com/vllm-project/vllm/pull/52970) · state: closed · merged: True

## Original PR description

## Purpose

Enable the AITER Triton FP8 paths on **RDNA3**, bringing it to parity with the gfx12/RDNA4 enablement. This also completes full GPU kernel support for **dsv4** models.
## Major Changes
* enable AITER unified attention if `VLLM_USE_AITER`=1. the priority is after `ROCM_ATTN` and before `TRITON_ATTN`.
* enable AITER GDN kernel.
* Widen most gates to all of RDNA which were only for RDNA4.

**Relationship to prior work:**

- **Continuation / mirror of #43615**. This PR
extends the exact same mechanism to gfx11/RDNA3 — both are RDNA, neither has a CK build, so only aiter's Triton kernels exist on either. Instead of duplicating the gate for a third arch, it switches the two RDNA gates to the canonical `on_rdna()` predicate (`gfx11 + gfx12`, minus CDNA gfx1250), so every downstream site (fp8 MoE oracles, blockscale linear, quant-fusion passes, pass-manager, GDN, sparse-MLA) lights up for gfx11 with no per-site edits.

- **Supplement to #47017**. That PR made DSV4
*run* on gfx11 but relied on the op-level **CPU/torch
fallback**, without broadly enabling AITER. The usage of "item()" from PyTorch fail cudagraph capture and can only be used with --enforce-eager". 
This PR removes that torch-fallback dependence for gfx11 by registering **all** aiter ops through the general path and
partially reverted the fragile _direct_register_custom_op_() for single kernel.

- **Supersedes #51555** . It adds a *separate* kernel that dequantizes fp8 → bf16 **in-kernel** before `tl.dot`, when the Triton compiler already implicitly does the same work during lowering, after minor fix https://github.com/ROCm/aiter/pull/4764. Simply adapting the Aiter's kernel is cleaner.

## Fix applied

Two gfx1151-scoped changes were applied:

The finalized branch applies two narrow gfx1151 compatibility changes. First, gfx1151 is routed away from the non-stage1 AITER paged-MQA decode kernel and through the existing stage1 path, because the non-stage1 path faults on gfx1151 under non-eager mode with multiple active decode rows. Other RDNA/CDNA targets keep the existing non-stage1 dispatch.

Second, the block-scaled FP8 Triton matmul keeps the explicit FP8-to-upcast workaround only on gfx1151 with Triton versions earlier than 3.8. This preserves the validated Triton 3.7 behavior while allowing Triton 3.8 or newer runtimes to use the direct FP8 `tl.dot` path.

Been spending to to fix a regression introduced in #57451: it moved the DSv4 decode inverse-RoPE into the sparse decode-reduce kernel, but that fused rotation only exists in the gfx942/gfx950 split-K reduce kernel.

On RDNA, decode falls to the fallback kernel, which does not rotate — yet
`rocm_sparse_attn_decode` still returns every decode row as rotated, so the standalone
`rocm_inverse_rope_rows_ pass` skips them. Decode output is therefore never inverse-RoPE'd
→ garbage generation (prefill/TTFT stays coherent). 

Fix: exclude RDNA from `fuse_decode_inv_rope` exactly as `gfx1250` already is, so decode rows fall to the standalone
pass (rotated=0 → rotate every row). 

dsv4 Model eval has been updated to main PR body. It would be nice we can merge this PR soon as it should fix the same issue on gfx12. Although no one reports it yet, the output emits GARBAGE before this PR.
