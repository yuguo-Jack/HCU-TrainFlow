# [Core] Priority scheduling: hold lower-priority prefill for first tokens

[Upstream PR](https://github.com/vllm-project/vllm/pull/63351) · state: closed · merged: False

## Original PR description

## Overview

Stacked on #63350 ("[Core] Priority scheduling: preempt for a waiting request under KV pressure"; review that first, this PR's diff is the second commit). Under priority scheduling, a high-priority request's first tokens share every step with the prefill chunks of lower-priority requests; this adds `--priority-prefill-budget-cap`, off by default, to keep those chunks out of the steps of its first tokens.

## Claims

- With the cap, prefills of a strictly lower priority, running or waiting, sit out the steps from the one in which the waiting request of the highest priority fits, or in which its KV load from a KV connector is done, while it prefills, until it has its first `--priority-prefill-budget-cap-tokens` output tokens (16 by default), with async scheduling as without. Decodes are never cut.
- A KV load in flight holds them out for its first `--priority-prefill-budget-cap-tokens` steps only, so a load that never completes holds nothing after those.
- A waiting request that does not fit (no free running slot, or no KV cache room) holds nothing back, nor does a KV load while no running slot is free, so the prefills that will free them go on.
- Off (the default), scheduling is unchanged: the same byte-identical schedules and scheduler test results as #63350.
- Counters, `vllm:priority_prefill_held_steps` and `vllm:priority_prefill_held_tokens`, count the steps in which the cap holds lower-priority prefill back and the prefill tokens it holds back in them, at most each step's budget; they are registered only with the cap on.
- On an RTX 5060 Ti (both PRs ported to vLLM v0.32.0): behind three lower-priority prefills, a priority 0 chat turn's 16th token after 575 ms instead of 1,500 ms on v0.32.0 and 1,350 ms with #63350 alone (medians); beside 12 closed-loop agent sessions, the calls' TTFT p95 at 388 and 358 ms instead of 6,830 and 7,158 ms on v0.32.0 and 4,111 and 1,073 ms with #63350 alone.

With an earlier version of the cap that did not count in-flight prefills, the calls' p95 stayed above 3 s, and every slow turn was in `WAITING_FOR_REMOTE_KVS` with KV to spare, as the scheduler's state logged each step showed: once its load was done, the request waited for the waiting loop, which runs only on budget the running loop leaves, and the agents' prefill chunks left none, for up to 4 s. A load that never completes would then hold lower-priority prefill back for good, so a load in flight holds it for its first `--priority-prefill-budget-cap-tokens` steps only. ## Details

- **Which requests hold prefill back.** The running requests with fewer than `--priority-prefill-budget-cap-tokens` output tokens, those of the step in flight under async scheduling included, and those still prefilling among them; while a running slot is free, a request whose KV load is done (the waiting loop promotes it in the step, but only on budget the running loop leaves) and, for its first `--priority-prefill-budget-cap-tokens` steps, a load in flight; and the waiting request of the highest priority that the waiting loop can schedule, if it fits: a free running slot, as the waiting loop checks it, and no block short as #63350's preemption counts it, deferred frees included. Only strictly lower priorities are held back, so at one priority nothing changes.
- **How.** A running prefill chunk of a lower priority gets no tokens, and vLLM skips it as any request with no new tokens; a waiting request of a lower priority is not admitted. A lower-priority request that holds KV blocks is skipped rather than waited on: the waiting loop drains those requests first, and the request whose first tokens are due may be behind it. No room is made for a waiting request the cap holds back, since it would not be admitted in the step.
- **No stall on a full running queue.** Without a free running slot, neither the waiting request nor a KV load counts, since none could be admitted or promoted; otherwise the lower-priority prefills holding the slots would sit out every step. A test with two slots, both taken while a higher-priority request loads, covers it.
- **Costs and limitations.** Lower-priority prefill makes no progress while a higher-priority request prefills or has its first tokens, so a steady stream of higher-priority requests whose first tokens overlap holds it back for as long as the stream lasts; their decodes are never cut. A load holds it for at most `--priority-prefill-budget-cap-tokens` steps before it is done. Per step with the cap on: one pass over the running requests and the loads in flight, and, while a request of a lower priority than the waiting request of the highest priority runs or waits (a pass over half of each waiting queue's heap tells), that request's prefix cache lookup and #63350's block count for it; the CPU cost table above gives the time. Untested: a request whose KV has loaded but finds no blocks to be promoted into (only a lower-priority request that holds KV blocks without being in flight, such as a streaming session's next chunk, can take them), while every running request is a lower-priority prefill and #63350's preemption is off.
- **Sizing the window.** `--priority-prefill-budget-cap-tokens` should cover the first output the application acts on; for a voice agent, the first sentence it hands its TTS. For this agent, 16 tokens covered 180 of 320 measured first sentences (56%) and 48 covered all 320 (median 15 tokens, p95 29, longest 39), which is why the end-to-end p95 above falls from 3,094 ms at 16 tokens to 2,232 ms at 48. A larger window holds lower-priority prefill back for more steps, so 16 suits shorter first chunks. Open question: should the default be 48, voice-sized, or stay at 16?
