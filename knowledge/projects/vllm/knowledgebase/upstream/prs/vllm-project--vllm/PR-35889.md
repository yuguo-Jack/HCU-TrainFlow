# [Bugfix] Fix LoRA + TP > 1 crash due to non-contiguous input tensor in lora_shrink_op.py

[Upstream PR](https://github.com/vllm-project/vllm/pull/35889) · state: closed · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Purpose

Fix `AssertionError` crash when using LoRA adapters with tensor parallelism (TP) > 1.

When `--tensor-parallel-size` > 1, weight sharding can produce non-contiguous tensor views for the `inputs` tensor passed to the Triton LoRA shrink kernel. The existing code had `assert inputs.is_contiguous()`, which crashes instead of handling this valid runtime condition.

**Root cause:** `vllm/lora/ops/triton_ops/lora_shrink_op.py` asserts contiguity on `inputs` rather than making the tensor contiguous. TP sharding via `torch.tensor_split()` returns views that share the underlying storage but are not contiguous in memory.

**Fix:** Replace the assertion with `inputs = inputs.contiguous()`, which:
- Makes non-contiguous tensors contiguous (fixes the crash)
- Is a no-op when the tensor is already contiguous (zero overhead for TP=1)

**Stack trace before fix:**
```
AssertionError
  File "vllm/lora/ops/triton_ops/lora_shrink_op.py", line 174, in _lora_shrink
    assert inputs.is_contiguous()
```

**Reproduction conditions:**
- Any model + LoRA adapter with `--tensor-parallel-size 2` (or higher)
- Tested with `kldzj/gpt-oss-120b-heretic` + `cmacboyd/gpt-oss-120b-heretic-4sight-query-lora-r64` on 2× GPUs

**Audit of related files:** The other three Triton LoRA op files were audited and do not have the same issue:
| File | Contiguity assertion on `inputs`? | Status |
|---|---|---|
| `lora_shrink_op.py` | `assert inputs.is_contiguous()` | **Fixed in this PR** |
| `lora_expand_op.py` | No (only `assert output_tensor.is_contiguous()`) | Safe |
| `fused_moe_lora_op.py` | No assertions | Safe |
| `fused_moe_lora_fp8_op.py` | No assertions | Safe |

### Additional context: This bug is not limited to tensor parallelism

We've since confirmed this same `assert inputs.is_contiguous()` crash also occurs on **single GPU (TP=1)** deployments. A coworker hit the identical assertion when deploying with [llm-d](https://github.com/llm-d/llm-d) using LoRA + KV cache disaggregation (`NixlConnector`).

#### Confirmed failing configurations

- **8x A100 80GB** with TP=8 + LoRA (original report)
- **1x H200** with TP=1 + LoRA + `--kv-transfer-config '{"kv_connector":"NixlConnector","kv_role":"kv_both"}'` (llm-d deployment)

The fix (`inputs = inputs.contiguous()`) is a defensive approach regardless of what upstream operation produces the non-contiguous view.
