## Original PR description

# [Feature] [KV Offload] Support sharing SimpleCPUOffload prefix caches across local DP replicas

## Summary

Implement #58240. `SimpleCPUOffloadConnector` currently keeps an independent CPU prefix cache
in each DP replica. When a request is routed to another local replica, that replica recomputes
a prefix even though a completed CPU copy is available. This change adds an opt-in
`cpu_offload_shared=true` mode that lets local DP replicas reuse completed CPU prefixes.

This builds on [#37160](https://github.com/vllm-project/vllm/pull/37160), which
introduced `SimpleCPUOffloadConnector` and its private per-replica CPU cache.
This PR extends that connector with opt-in cross-DP publication and lookup; it
does not change the native offloader's per-replica semantics.

## Configuration

Add `cpu_offload_shared`, a JSON boolean in `kv_connector_extra_config`,
defaulting to `false`. Set it to `true` to share completed CPU prefixes with
compatible DP replicas in the same IPC namespace and distributed DP group.
Leaving it unset retains the existing private CPU pools.

The CPU capacity remains a per-worker budget: `cpu_bytes_to_use_per_rank`
reserves each worker's write partition. Corresponding local DP peers can read
published entries from one another's partitions, while writes remain owned by
the worker that allocates the slot. For example, two local DP peers configured
with 8 GiB each expose a 16 GiB node-local region for published slots and
metadata; this is shared visibility, not a dynamically rebalanced write pool.

Pass the following to `--kv-transfer-config`:

```json
{
  "kv_connector": "SimpleCPUOffloadConnector",
  "kv_role": "kv_both",
  "kv_connector_extra_config": {
    "cpu_offload_shared": true,
    "cpu_bytes_to_use_per_rank": 8589934592,
    "lazy_offload": false
  }
}
```

Shared mode requires the CPU backend, eager offloading (`lazy_offload=false`),
prefix caching, compatible model/KV layouts and reproducible prefix hashes.
It supports fixed MoE DP groups and TP, with `PP=DCP=PCP=1` and no LoRA or
elastic EP. Each TP coordinate shares its own KV shard with corresponding
local DP peers. Cross-node transfer requires a network-capable connector or tier.

## Implementation

Use the existing `SharedOffloadRegion` type, as established for native
`CPUOffloadingSpec` storage by
[#50094](https://github.com/vllm-project/vllm/pull/50094), and the DMA/`BlockPool`
interfaces for storage and transfers; the cross-DP publication index, locking
and reader reference semantics are new code in this PR. Each writer owns a
fixed partition, and the shared pool does not dynamically move free write slots
between workers. Lookup and pinning use `flock` on the metadata region's descriptor;
prefixes are published after all worker stores complete, and reader references
prevent slot reuse until peer loads finish. The workers use the existing DMA
backend for transfers.

The rebased base also includes the upstream prefix-cacheable-group handling from
[#56810](https://github.com/vllm-project/vllm/pull/56810). This PR consumes that
group eligibility behavior and adds cross-DP publication; it does not duplicate
the upstream hybrid-model bug fix.

## Why this is not a duplicate

The following open PRs address adjacent behavior, but none adds cross-DP CPU
prefix publication and peer loading for `SimpleCPUOffloadConnector`:

- [#53073](https://github.com/vllm-project/vllm/pull/53073) targets shared mmap
  startup ownership and cleanup. This PR targets completed-prefix visibility
  and safe peer reads after asynchronous DMA. It follows the mmap lifetime
  rules but adds a different metadata publication and reader-lifetime protocol.
- [#53474](https://github.com/vllm-project/vllm/pull/53474) targets node-local
  sizing and worker placement for native `OffloadingConnector`. This PR targets
  node-local prefix reuse for `SimpleCPUOffloadConnector`, including one pool
  per TP coordinate. The connectors, allocation path and target behavior differ;
  this PR has no code dependency on #53474.
- [#47324](https://github.com/vllm-project/vllm/pull/47324) targets a GPU
  load/compute stream race inside one worker. This PR targets host-side slot
  ownership when another worker reads a completed prefix. It does not implement
  the open PR's load-path stream-ordering fix; the two changes are complementary,
  and this PR adds separate cross-worker reader references.
- [#57418](https://github.com/vllm-project/vllm/pull/57418) targets concurrent
  requests waiting for the same in-flight load inside one engine. This PR
  targets completed CPU prefixes shared by different DP engines; it does not
  change connector-side coalescing of simultaneous loads.
- [#43483](https://github.com/vllm-project/vllm/pull/43483) targets routing a
  request to the DP rank that already owns a GPU prefix. This PR targets actual
  CPU KV publication and peer loading when routing selects another replica;
  routing-only ownership hints cannot provide that transfer.
- [#57422](https://github.com/vllm-project/vllm/pull/57422) targets inode-safe
  unlinking of existing shared mmap files. This PR uses the existing mmap
  lifetime model but adds cross-DP prefix metadata and reader references.
- [#54743](https://github.com/vllm-project/vllm/pull/54743) targets which KV
  groups receive offload configuration. This PR keeps the existing group
  eligibility rules and adds sharing only for groups already handled by
  `SimpleCPUOffloadConnector`.
- [#52921](https://github.com/vllm-project/vllm/pull/52921) targets aligning
  scheduler and worker pool sizes across PP/speculative workers. This PR keeps
  the existing per-worker capacity calculation and adds node-local sharing
  after those capacities agree.

### Experiment setup

Use the same source commit and model weights for both modes. The launch below
shows the TP2×DP2 settings used for the TP shard and recovery probe. Run one
process for each logical launch rank in the table above: ranks 0 and 2 on the
first host, and ranks 1 and 3 on the second. Here `--nnodes 4` counts four logical
launches across two physical hosts; the DP size is 2.

Set `MODEL` to the
[DeepSeek-V4-Flash-0731](https://huggingface.co/deepseek-ai/DeepSeek-V4-Flash-0731)
weights, then set `NODE_RANK`, `DP_RANK`, `DP_PORT` and the coordinator ports and
address for the deployment. Use distinct HTTP ports for DP0 and DP1, one shared
DP RPC port, and one shared TP master port. Logical ranks 1 and 3 are headless.
The host-specific network environment is intentionally omitted.

```bash
KV_CONFIG='{"kv_connector":"SimpleCPUOffloadConnector","kv_role":"kv_both","kv_connector_extra_config":{"cpu_offload_shared":true,"cpu_bytes_to_use_per_rank":2147483648,"lazy_offload":false}}'

PYTORCH_CUDA_ALLOC_CONF=expandable_segments:False \
.venv/bin/python -m vllm.entrypoints.cli.main serve "$MODEL" \
  --host 0.0.0.0 --port "$DP_PORT" \
  --data-parallel-size 2 --data-parallel-rank "$DP_RANK" \
  --data-parallel-external-lb \
  --data-parallel-address "$HEAD_IP" --data-parallel-rpc-port "$DP_RPC_PORT" \
  --tensor-parallel-size 2 --enable-expert-parallel --enable-ep-weight-filter \
  --nnodes 4 --node-rank "$NODE_RANK" \
  --master-addr "$HEAD_IP" --master-port "$TP_MASTER_PORT" \
  --distributed-executor-backend mp --disable-custom-all-reduce \
  --trust-remote-code --tokenizer-mode deepseek_v4 --reasoning-parser deepseek_v4 \
  --kv-cache-dtype fp8 --block-size 256 --max-model-len 32768 \
  --gpu-memory-utilization 0.47 --kv-cache-memory-bytes 2147483648 \
  --max-num-seqs 16 --max-num-batched-tokens 2048 \
  --max-cudagraph-capture-size 64 \
  --compilation-config '{"cudagraph_mode":"FULL_AND_PIECEWISE","custom_ops":["all"]}' \
  --kernel-config '{"enable_flashinfer_autotune":false}' \
  --enable-prefix-caching --prefix-caching-hash-algo sha256 \
  --enable-prompt-tokens-details --per-request-spec-decode-metrics detailed \
  --speculative-config '{"method":"dspark","num_speculative_tokens":5,"draft_sample_method":"probabilistic"}' \
  --kv-transfer-config "$KV_CONFIG"
```

Add `--headless` for logical ranks 1 and 3. For the private control, change only
`cpu_offload_shared` to `false`. Keep `expandable_segments:False` in both
connector runs because the upstream KV-connector guard rejects
`expandable_segments:True`.

External DP routing gives one configured endpoint port to DP0 and another to DP1
on the coordinator host; the TP followers are headless. Send case `i` to DP rank
`i % 2` for the cold phase and to `1 - (i % 2)` for the peer phase, preserving
the prompt and `cache_salt`. The port selects the replica; it is not part of the
prefix hash.
Between phases, wait for requests and stores to finish, then POST to
`/reset_prefix_cache?reset_external=true` on both endpoints for a cold run, or
`/reset_prefix_cache?reset_external=false` to clear only GPU caches before peer
replay. Check that both resets succeed before issuing requests. Confirm reuse
with the external CPU-prefix counters.

#### Performance improvement test

The rebased-source one-shot test used 24 unique approximately 6K-token prefixes,
one in-flight request per endpoint and streaming `max_tokens=1` requests. Each
prefix was populated on its owner, GPU caches were reset, and the prefix was
requested exactly once from its local DP peer.

| Mode | Peer TTFT p50 | Peer TTFT p95 | External transfer | Local compute |
| --- | ---: | ---: | ---: | ---: |
| Private | 9.17 s | 12.22 s | 0 / 140,652 | 140,652 |
| Shared | 4.91 s | 9.29 s | 129,024 / 140,652 | 11,628 |

Shared peer TTFT was 46.4% lower in this rebased-source diagnostic run. All 24
peer requests had zero errors, empty outputs, replacement characters,
invalid controls or cold/peer output mismatches. This is a diagnostic result;
the topology with two logical workers per GB10 is not a production throughput
setup.

### Accuracy validation

The rebased-source GSM8K evaluation used three fresh cold/peer pairs with the
same 200 five-shot questions, `temperature=0`, `seed=0`, concurrency 32 and a
512-token output limit:

| Configuration | Round 1 | Round 2 | Round 3 | Mean | Min–max | DSpark acceptance |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Private cold | 189 | 189 | 189 | 94.50% | 94.50–94.50% | 64.10% |
| Private peer | 191 | 189 | 190 | 95.00% | 94.50–95.50% | 64.20% |
| Shared cold | 188 | 189 | 189 | 94.33% | 94.00–94.50% | 63.94% |
| Shared peer | 190 | 190 | 189 | 94.83% | 94.50–95.00% | 64.60% |

All 2,400 requests completed without request errors, empty output, replacement
characters or invalid control characters. These repeated evaluations show normal
serving-workload variation and are not a statistical equivalence claim. The
TP2×DP2 recovery probe separately passed 8/8 cold and 8/8 peer requests in both
modes with token-exact output; private peer CPU hits were 0 and shared peer CPU
hits were 45,056 tokens. The independent TP-shard/publication probe also passed.
