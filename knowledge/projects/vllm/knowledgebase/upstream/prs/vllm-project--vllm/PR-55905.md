## Purpose

Stacked on #57539 and #55627 (the exact-replay step and its wiring) and on #55895 (the pinned SSD tiles): this PR adds row-gated decode on top of those dependencies. Tracked in #55524.

#55627 makes Mamba2 prefill, chunked prefill and decode bitwise identical in `VLLM_BATCH_INVARIANT=1` mode, but its decode step re-runs the chunked-scan kernels over the whole partial chunk and runs outside CUDA graphs. That costs about 10x decode throughput on a pure Mamba2 model and 12x on a hybrid. This PR keeps the semantics and the state layout of #55627 and replaces the decode step.

- Row-gated kernels compute only the new token's output row from the buffered inputs and the fp32 boundary state, and write the token's x, dt and B into the buffers. They reproduce the reduction order of the pinned prefill kernels (same head tile for the dt cumsum, same K blocks for the C·B row, same M/N/K tiles for the scan's dot products; smaller M tiles change the bits), so every row is bitwise that of a single-shot prefill. They grew out of the emit kernels of an earlier batch-invariant Mamba prototype, whose author is credited as co-author on that commit.
- A fold kernel runs over every row and returns early unless the row's token completes a chunk; for those rows it repeats the pinned chunk_state kernel over the buffered chunk and folds the result into the boundary state with an explicit `tl.fma`, the same instruction the state-passing kernel now uses, so the two round identically by construction.
- The decode metadata shrinks to one int32 tensor with each row's position inside its partial chunk, computed on the device and kept in a persistent buffer per KV cache group. CUDA graph padding rows get position 0 and never fold. Every step has shapes that depend only on the batch size, so decode-only batches run in full CUDA graphs as in default mode.
- Prefill keeps the replayed scan of #55627.

The kernels take their tiles from the pinned configurations of #55895; with autotuning the prefill side is not guaranteed to use them.

Not a duplicate: #54993 targets decode == recompute through a multi-token SSU replay; this PR targets decode == single-shot prefill through the chunked-scan arithmetic.

## Trade-offs

Each decode row still pays for a full 64-row M tile of the chunk-scan MMA to reproduce the prefill kernel's rounding, and the cumsum and C·B kernels are small launches, so the gap to the single-token update grows with the number of concurrent sequences. Throughput on GB200 (`vllm bench throughput`, 256-token prompts, 512 output tokens, FlashAttention 2 pinned on both sides, two repetitions, requests/s; measured on earlier revisions of the CUDA-graph commit, f198a7ec4 for the 128-request rows and 0b7c7ad3b for the rest; the later commits change kernel launch parameters and the split's imports but not the arithmetic, and were not re-benchmarked):

| model | prompts | default mode | #55627 | this PR |
|---|---|---|---|---|
| mamba2-130m decode | 128 | 72.6, 72.2 | 7.4 | 30.8, 39.3 |
| mamba2-130m decode | 512 | 130.7, 131.6 | | 41.4, 47.5 |
| granite-4.0-h-350m decode | 128 | 38.1, 38.4 | 3.2 | 27.6, 25.0 |
| granite-4.0-h-350m decode | 512 | 63.2, 62.7 | | 31.3, 34.1 |
| mamba2-130m prefill (2048-token prompts) | 256 | 156.8 | same as this PR | 155.6 |
| granite-4.0-h-350m prefill | 256 | 143.5 | same as this PR | 95.5 |

Prefill is unchanged by this PR; the granite prefill row shows the cost of the mode on a hybrid, whose attention and MLP layers also run the batch-invariant kernels.
