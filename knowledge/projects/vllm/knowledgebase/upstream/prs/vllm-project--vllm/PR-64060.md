# [Bugfix] Fix P2P ZMQ reconnect dropped while the ROUTER still holds the old routing id

[Upstream PR](https://github.com/vllm-project/vllm/pull/64060) · state: open · merged: False

## Original PR description


## Overview

Fixes #63740. A P2P KV offload peer may reconnect soon after a disconnect. If the other side's ZMQ ROUTER still holds the old connection's routing id, it drops the new connection without any error, and the session handshake stalls. This PR sets `ZMQ_ROUTER_HANDOVER` on the `ZmqTransport` ROUTER. It also drops leftover messages from the replaced connection.

## Claims

- Fixes the flaky `TestBidirectionalManager::test_lookup_expiry_allows_zmq_reconnect` (`Failed: P2P session did not reach the expected state` at `test_manager.py:1341`). Under CPU load it failed 35 of 400 runs before this PR and 0 of 1200 runs after.
- A reconnect that reuses a routing id the ROUTER still holds now replaces the old connection instead of being lost.
- Unread messages from the replaced connection are dropped. With handover alone, they raise `UnicodeDecodeError` out of `ZmqTransport.poll()`.
- No wire-format change. The routing id is still `host:port`.
- Adds a deterministic regression test: `TestZmqReconnect::test_reconnect_before_old_connection_retired`.

## Details

**Root cause.** Every DEALER of a `ZmqTransport` uses the transport's `local_id` as its routing id. So when a peer reconnects, the other side's ROUTER sees the same id as the connection being replaced. libzmq frees a ROUTER routing id only after two things: the ROUTER's own thread has read the old pipe to its end, and the `pipe_term` / `pipe_term_ack` round trip with the I/O thread has finished. This happens lazily, inside later `recv` calls. That is after the monitor has already reported `EVENT_DISCONNECTED`. Without `ZMQ_ROUTER_HANDOVER`, `router_t::identify_peer` ignores a new pipe whose id is still held. The new pipe's routing-id frame and then its first message, the `ConnectMsg`, are consumed and lost. No error is raised. The handshake then stalls. CPU load slows the I/O-thread round trip, which makes the window wider. Either direction can hit it: A's DEALER at B's ROUTER, or B's DEALER back at A's ROUTER.

**How it was found.** I added debug logging in `_recv_router` and ran the same load: 18 of 128 runs failed. In 17 of them, B's ROUTER delivered nothing from A after A opened its new DEALER. In the other one, the same thing happened in the reverse direction. With only `ROUTER_HANDOVER` set, the same loop had 0 failures in 128 runs.

**Why the drop rule.** With handover, libzmq gives the replaced pipe a reserved routing id: a zero byte plus 4 bytes. Messages still unread in that pipe come out under this id, and `identity.decode()` raises. libzmq reserves ids that start with a zero byte for its own use. vLLM DEALERs always set `host:port`. So a message with such an id cannot come from a live vLLM connection. It is a leftover from a connection the peer has already replaced.

**Rejected alternatives.**
- Handover alone (the issue's first proposal). It crashes `poll()`, as the new test shows.
- A unique routing id per DEALER (the issue's alternative). It changes the wire protocol: a peer on the old code would read `host:port#n` as the peer id and try to dial it. Also, a stale `DisconnectMsg` from the old connection would map to the same peer and could kill the new session.

No other ROUTER in `vllm/` gets DEALERs with a fixed routing id. The engine-core ROUTER already sets handover.

**Limitations.**
- One window is improved but not closed: A reconnects before B has read A's `DisconnectMsg`. A's new `ConnectMsg` then reaches B's old session. That session treats it as `duplicate connect after handshake` and disconnects. In a probe of this case, both reconnect attempts on the base code were still not ready after 5 s. A's session stayed stuck until the 30 s handshake timeout. With this PR, the first attempt is torn down with that protocol error, and the second is ready after 0.02 s. Closing this window needs a change in the session layer, so it is not part of this PR. The test in the issue does not reach this window, because it waits until B has dropped its session.
- Security: with handover, a new connection can take over a routing id that is still connected. The P2P ROUTER does not authenticate peers. So even without handover, anyone who can reach the port can already use any id that is not connected right now. `docs/usage/security.md` already says KV transfer traffic is insecure by default and must be on an isolated network.
- The reproduction ran the test alone in a fresh pytest process each time, not inside the full CI step. It used a full H200, not the H200 MIG 35GB slice from the report.

Output on this PR:

```
b_conn_old.alive=True new_inbound=0 msgs_into_old=[{'type': 'connect', 'seq': 2}]
new_inbound=0 into_old=[{'type': 'connect', 'seq': 2}] into_new=[]

What this means:

1. **The fix only works on a receiver with no session for the peer.** Handover swaps the ROUTER pipe, but B's own DEALER to A never disconnects, so B's `ZmqConnection` for A stays registered and `_recv_router` routes the reconnect's ConnectMsg into it via `_connections.get(sender_id)`. From reading `session.py:_on_connect` (not run end to end): B's existing session then sees a second ConnectMsg after its handshake and raises `duplicate connect after handshake`, so the new handshake fails anyway.
2. **In this case the PR makes things worse.** A's DisconnectMsg went out on the replaced pipe, so the new `\x00` drop discards it, and B is never told the peer left. Before the PR, B at least learned of the disconnect.
3. The PR's own test passes because `transport_b` is never polled before the reconnect, so this state is never reached. Variant 2's 0.2 s wait forces the overlap, so these tests prove the gap exists but not how often it happens under the stress loop.

Suggested direction: give each DEALER a unique routing id (for example `f"{local_id}#{nonce}"`) and take the logical peer id from the ConnectMsg, or strip the suffix. Old and new connections then never share a ROUTER id, the old pipe's DisconnectMsg still reaches the old session, and neither `ROUTER_HANDOVER` nor the reserved-id filter is needed. That also covers the duplicate-live-peer and `decode()` points from my earlier inline comments.

Point 1 also happens on main without handover, and when B's session is still waiting for A's ack it does not raise: the reconnect goes half-open.

The trigger is a failed registration. When A's registration of B's NIXL agent fails, `_poll_registration` marks A's connection dead and sends nothing, so B keeps a session that has registered A and acked but never got A's ack. Once B's ROUTER frees A's routing id, A's reconnect is routed into that session by `_connections.get(sender_id)`. `_on_connect` accepts the ConnectMsg, since the session is neither ready nor registering, registers A again and acks. B's own ConnectMsg went out only when that session was created, so A's new session is `ready` without A registering B. B never gets A's ack and queues every `LookupRespMsg`, so each lookup from A ends at the 8 s lookup timeout.

CPU, main `b2f46e785`, two managers built with their constructors on real ZMQ transports, A's registration of B always failing (test below), same result in 3 of 3 runs:

| pause between A's failed registration and its next request | A's lookup | A->B ready | B->A ready | A's registration attempts |
|---|---|---|---|---|
| 0 s | MISS | False (reconnect dropped) | False | 1 |
| 0.5 s | RETRY | True | False | 1 |
| 2 s | RETRY | True | False | 1 |

With this PR's handover the 0 s row goes half-open as well, since the reconnect is no longer dropped.

On GPUs (three single-GPU Qwen3-0.6B engines sharing an H200 node, a nightly plus #64256, #64251 and #64501, no handover), with `UCX_TLS=all` making A's registration of a replacement peer fail: in 5 of 6 runs across two such nodes, requests naming the replacement took p50 4.4 s and up to 8.4 s for the rest of the run instead of falling back at once, A logged 11 lookup timeouts per run, and the replacement queued 446-451 `LookupRespMsg`.

I think this supports the per-connection routing id. We tried fixing it in the session instead, by resending our ConnectMsg when a second one arrives before the peer's ack. That needs B to reuse its existing registration of A, since registering again goes through `_publish_peer`, which overwrites `_remote_dlists[peer_id]` without releasing the previous descriptor list (main already takes that path here). It also still loses the new ConnectMsg in variant 2, because the DisconnectMsg has marked the session dead before the ConnectMsg is dispatched. With per-connection ids the reconnect arrives as a new inbound connection, so the requirement moves to the manager: a ConnectMsg on a new connection for a peer that already has a session replaces that session.

Separately, the failed-registration path should send a `DisconnectMsg`, as the other teardown paths do, and count as a data-plane fault so the reconnect backoff applies instead of a new registration attempt for every request naming the peer. That does not depend on the routing change, so it is in #64819.

Two P2P managers built with their constructors on real ZMQ transports. Their
NixlTransport objects are replaced by fakes; A's registration of B always
fails. A rejects B, B keeps its session waiting for A's ack, and a later
request from A reconnects into that session.

import time
from concurrent.futures import Future
from types import SimpleNamespace

import pytest
import zmq

from vllm.v1.kv_offload.base import ReqContext
from vllm.v1.kv_offload.tiering.p2p import manager as manager_module
from vllm.v1.kv_offload.tiering.p2p.manager import P2PSecondaryTierManager

from .test_manager import _FakeData, _init_offloading_spec, _remote_kv_source_kv_params

class _RegistrationFails(_FakeData):
    attempts = 0

    def add_remote_peer_async(self, *args, **kwargs):
        self.attempts += 1
        future: Future[None] = Future()
        future.set_exception(RuntimeError("NIXL_ERR_INVALID_PARAM"))
        return future


def _ready(mgr, peer):
    s = mgr._sessions.get(peer)
    return None if s is None else s.ready


@pytest.mark.parametrize("pause", [0.0, 0.5, 2.0])
def test_reconnect_after_failed_registration(monkeypatch, pause):
    monkeypatch.setattr(
        manager_module.FileMapper,
        "from_offloading_spec",
        lambda **k: SimpleNamespace(get_run_config=lambda: {}),
    )

    def build(data_cls):
        for _ in range(8):
            port = _free_port()
            data = data_cls(f"127.0.0.1:{port}")
            monkeypatch.setattr(manager_module, "NixlTransport", lambda *a, d=data, **k: d)
            try:
                mgr = P2PSecondaryTierManager(
                    _init_offloading_spec(), memoryview(bytearray(16)),
                    host="127.0.0.1", port=port)
            except (zmq.ZMQError, OSError):
                continue
            return mgr, data, f"127.0.0.1:{port}"
        pytest.fail("could not bind a ZMQ port")

    mgr_a, data_a, peer_a = build(_RegistrationFails)
    mgr_b, _, peer_b = build(_FakeData)
    port_b = int(peer_b.rsplit(":", 1)[1])

    def poll_for(seconds, condition=lambda: False):
        deadline = time.perf_counter() + seconds
        while time.perf_counter() < deadline:
            list(mgr_a.get_finished_jobs())
            list(mgr_b.get_finished_jobs())
            if condition():
                return
            time.sleep(0.005)

    def request(req_id):
        ctx = ReqContext(req_id=req_id, kv_transfer_params=_remote_kv_source_kv_params(
            "127.0.0.1", port_b, req_id))
        mgr_a.on_new_request(ctx)
        return ctx

    try:
        request("req-1")
        poll_for(5.0, lambda: data_a.attempts > 0)
        assert data_a.attempts == 1, "A never tried to register B"
        poll_for(pause)

        result = mgr_a.lookup(b"key", second)
        print(f"\npause={pause}s lookup={result.name} "

Examples are a misconfigured advertise host (127.0.0.1, a shared Service IP with the same port) or a stale process still alive after a restart.

The two DEALERs then keep stealing the pipe from each other. Each displaced peer's in-flight lookup/fetch messages are dropped by the `\x00` filter below, so both sides hang until the lookup/load timeouts, and nothing above debug level is logged.
