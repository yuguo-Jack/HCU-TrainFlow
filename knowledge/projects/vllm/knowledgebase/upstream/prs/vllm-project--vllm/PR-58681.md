# [Bugfix][DeepGEMM] Restore SM12x alignment behavior for grouped GEMMs

[Upstream PR](https://github.com/vllm-project/vllm/pull/58681) · state: open · merged: False

## Original PR description

## Fixes

Fixes #58624

## Problem

On SM12x (GB200, GB10, RTX PRO 6000 Blackwell), DeepGEMM's `get_theoretical_mk_alignment_for_contiguous_layout` returns alignment 128 regardless of per-expert M. DeepGEMM 2.6.1 returned alignment 64 when each expert gets at most 64 rows, which is significantly faster for decode-shaped batch sizes.

This causes ~15% decode throughput regression since #56876 moved to DeepGEMM `e1f418c`.

## Solution

Add an SM12x-specific override in `get_theoretical_mk_alignment_for_contiguous_layout` that computes per_group_m and returns alignment 64 when per_group_m <= 64, matching the pre-#56876 behavior.

The fix is placed after the degenerate case guards (`num_groups <= 0`) as suggested by @hclsys in the issue discussion.

## Validation

- Issue author @lucamotz measured ~15% decode throughput improvement on GB10 (SM121) with the fix
- Contributor @bluemelov1 independently confirmed on RTX PRO 6000 Blackwell (SM120)
- Bit-identical outputs confirmed with and without the fix (correctness suite: needle, greedy repeats, shared-prefix divergence, DSpark acceptance)

## Testing

Hardware validation was performed by issue reporters on GB10 (SM121) and RTX PRO 6000 Blackwell (SM120).

AI assistance was used for code changes, validated against the issue reporter's provided diff and reviewer feedback.

- hclsys · comment · 2026-09-25T09:16:35Z · [source](https://github.com/vllm-project/vllm/pull/58681#issuecomment-5829945842)

Checked on a GB10 (sm_121, cc 12.1), `family120 True`:

```
num_groups  expected_m  per_expert  align
         8          64           8     64
         8         512          64     64
         8         513          65    128
        16        1024          64     64
        16        1025          65    128
        32        2048          64     64
        32        2049          65    128
num_groups=0  -> ValueError
num_groups=-3 -> ValueError
```

Boundary lands exactly at 64/65 for every `num_groups`, and both degenerate guards still fire — so the placement after them does what it needs to.

One dead-but-harmless note: the `expected_m is None -> 128` half can't be reached. The only caller, `compute_aligned_M_and_alignment`, always passes `expected_m = M * num_topk` and `num_groups = local_num_experts`, so `None` never arrives with a positive `num_groups`.


- bluemelov1 · comment · 2026-10-07T12:05:55Z · [source](https://github.com/vllm-project/vllm/pull/58681#issuecomment-6037537161)

The SM12x step-down this wraps already exists as a library change: https://github.com/vllm-project/DeepGEMM/pull/18

That PR restores `get_theoretical_mk_alignment_for_contiguous_layout` on SM12x, with the floor at 64 rather than 32. This fork's SM120 host heuristics only emit BLOCK_M 64 or 128 (`kMinBlockM = 64`); alignment 32 makes every grouped-contiguous GEMM reject all candidates and hit `DG_HOST_ASSERT(not candidates.empty())`.

Once vLLM's DeepGEMM pin includes that commit, this override and the pin fix would both return 64 for the same decode shapes. Prefer landing the library change and dropping the wrapper, instead of keeping two copies of the rule.
