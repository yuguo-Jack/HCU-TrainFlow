# [Bugfix][Spec Decode] DFlash: run the aux hidden state FC in the draft dtype

[Upstream PR](https://github.com/vllm-project/vllm/pull/63436) · state: closed · merged: True

## Original PR description

## Overview

A DFlash / DFlash2 drafter fails to start when the target model gives it FP32 aux hidden states (Muse Spark keeps its residual stream in FP32). The drafter's bf16 `fc` gets an FP32 input. This PR casts the input of `fc` to the FC's `params_dtype` in `DFlashQwen3ForCausalLM.combine_hidden_states`.

## Claims

- Bug fix: Muse Spark Open with a DFlash2 draft (`"method": "dflash"`) now loads and serves. Before this change, the profile run failed with `expected mat1 and mat2 to have the same dtype`.
- No change for targets whose hidden states are already in the draft dtype: `Tensor.to()` returns the same tensor and adds no kernel.
- This PR makes no performance claims.

## Details

**Root cause.** Muse Spark keeps its residual stream in FP32, so the aux hidden states that it captures for the drafter are FP32. `DFlashQwen3Model.fc` is a `ReplicatedLinear` with `params_dtype = model_config.dtype` (bf16). `combine_hidden_states` called `fc` on the FP32 tensor directly, and the GEMM rejects the mixed dtypes. `DFlash2Qwen3ForCausalLM` inherits this method, so DFlash2 drafters fail the same way.

**Fix.** Cast the input to `self.model.fc.params_dtype` before `fc`. We use `params_dtype` and not `fc.weight.dtype`: `params_dtype` is the activation dtype that the FC's linear method expects, also when the FC is quantized (an FP8 or packed int weight has a different dtype or no `weight`). For an unquantized FC the two are equal.

**Muse Spark DSpark.** `MuseSparkDSparkForCausalLM` (subclass of `Qwen3DSparkForCausalLM` -> `DFlashQwen3ForCausalLM`) has its own `combine_hidden_states` override that casts to `fc.weight.dtype` and then calls this method. Its draft checkpoint is bf16 and unquantized, so the second cast is a no-op. This PR does not change that file.

**Not a duplicate.** #40334 proposed the same one-line cast for an AWQ + `cpu_offload_gb` case. Its author closed it without a merge after pre-commit failures, and it did not cover the FP32-residual target case. Issue #42588 (ROCm, `float != c10::Half` at the same line) was closed after #42646, which changed the RMSNorm path and not `combine_hidden_states`. No open PR changes `combine_hidden_states` (searches: `dflash dtype`, `dflash fp32`, `dflash mat1 mat2`, `combine_hidden_states dtype`, `aux hidden states dtype draft`).

**Cost.** The cast is not a host-device sync and is safe in CUDA graphs. For a bf16 target it is a no-op. For an FP32 target it is one cast kernel on the `fc` input, which the FC needs anyway.

**CI.** `tests/v1/spec_decode/test_dflash2.py` runs in the "V1 Spec Decode" step (`pytest -m 'not slow_test' v1/spec_decode`; `source_file_dependencies` include `vllm/model_executor/` and `tests/v1/spec_decode`). The new test runs the model on CPU tensors. We cannot add a CI regression test through `LLM` with real weights: the only FP32-residual target that we know is the 816B Muse Spark model, which needs 8 GPUs. We did the end-to-end validation above outside CI.
