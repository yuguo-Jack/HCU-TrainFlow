# [Cleanup][Attention] Remove unused slot_mapping field from 5 backend metadata classes

[Upstream PR](https://github.com/vllm-project/vllm/pull/62951) · state: open · merged: False

## Original PR description

## Overview

Picks up #32335 with a scoped cleanup: removes redundant `slot_mapping` field declarations from five backend metadata classes.

## Claims

- Removes the redundant `slot_mapping` field declarations from `FlashInferMetadata`, `TritonAttentionMetadata`, `RocmAttentionMetadata`, `FlexAttentionMetadata`, and `XPUMLASparseMetadata`. Standard attention and shared MLA cache updates obtain the mapping through forward context; the cross-attention wrapper continues to attach its own mapping before use.
- The other eight backend metadata fields (`flash_attn`, `b12x`, `cpu_attn`, `hpc_attn`, `mla/indexer`, `mla/sparse_swa`, `rocm_aiter_fa`, `turboquant_attn`) are outside this PR's scope. Some have active consumers; others have additional forwarding or mutation sites that need separate auditing before removal.
- Updated `test_attention_backends.py` to pass `common_attn_metadata.slot_mapping` to `do_kv_cache_update`, since this cleanup removes the backend-specific field the test previously used.

## Validation

The cache-write paths support removing these five field declarations:

- For standard self-attention, the four non-MLA backends set `forward_includes_kv_cache_update=False`. The external `unified_kv_cache_update()` in `vllm/model_executor/layers/attention/attention.py` obtains the per-layer mapping from forward context. Cross-attention uses a wrapper that overrides this flag to `True`: its builder dynamically attaches `slot_mapping`, and its implementation reads that attribute for the cache write. These metadata classes permit dynamic attributes, so removing the dataclass field declaration preserves that wrapper behavior.
- XPU sparse MLA uses the shared MLA cache-update path in `vllm/model_executor/layers/attention/mla_attention.py`. That path obtains the per-layer slot mapping from forward context and passes it through `update_kv_cache()` to the inherited `MLAAttentionImpl.do_kv_cache_update()`. It does not require the removed metadata field.

Both touched test files are included in the configured Buildkite `v1/attention` suites in `.buildkite/test_areas/attention.yaml`; this is configuration coverage, not a claim that upstream CI has completed.

Remaining failures:
- 60 cases stop at Triton's explicit FP8 capability check: native FP8 KV cache requires SM89+, while this GPU is SM86.
- Four cases cannot access the gated `google/embeddinggemma-300m` model configuration.

No missing-`slot_mapping` errors occurred in this run. The failed and skipped cases remain unverified; some tests loop over multiple backends, so a failure can prevent later backend checks in the same test. ROCm, XPU, and end-to-end serving were not exercised locally.

## Details

Root cause: #25954 introduced `do_kv_cache_update()` as a separate op fed from `CommonAttentionMetadata.slot_mapping`, making the backend-local copy of `slot_mapping` redundant wherever a backend adopted that split and never diverges from the common value. #32335 tracked rolling that split out to every backend, but nobody went back to delete the now-dead field — a prior attempt (#41272) scoped only `flash_attn.py` and stalled/closed unmerged.

This PR limits the deletion to the five metadata classes whose cache-write paths are described above. It leaves the other eight backend fields unchanged without asserting that all eight are necessary. An assignment, a forwarded argument, or a copy into sub-batch metadata alone does not establish that a field has an active consumer; those paths need to be traced before deciding on further cleanup.

The test-helper adjustment in `test_attention_backends.py` is required by this field removal. Before the cleanup, the affected builders assigned the same tensor from `common_attn_metadata.slot_mapping` to the backend-specific field, so either access supplied the same mapping. Removing the field broke the test's old access; the helper now reads the common metadata directly. This is an accompanying test adaptation, not a fix for a demonstrated pre-existing correctness bug.
