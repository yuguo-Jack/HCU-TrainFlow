# [Model] Add ZAYA1 support

[Upstream PR](https://github.com/vllm-project/vllm/pull/65302) · state: closed · merged: True

## Original PR description



## Overview

Adds native support for Zyphra's ZAYA1 models (`ZayaForCausalLM`: [ZAYA1-8B](https://huggingface.co/Zyphra/ZAYA1-8B), [ZAYA1-74B-preview](https://huggingface.co/Zyphra/ZAYA1-74B-preview)), with `zaya` tool and reasoning parsers. Closes #42286.

This builds on Zyphra's #41999 (thanks @yury-tokpanov and the Zyphra team), reimplemented against current `main`: it reuses the Transformers `ZayaConfig`, the existing Mamba state and `ShortConv` metadata for CCA, `FusedMoEFactory`, and the `Qwen3Parser` grammar, so it adds ~870 lines (≈600 for the model) instead of ~2.8k, and needs no changes to shared MoE/Mamba/config code.

## Claims

- `ZayaForCausalLM` matches Transformers in float32 (greedy-exact on 8B; logprobs on a 5.2k-token 74B prompt) and runs with chunked prefill, prefix caching, CUDA graphs, TP, EP and online FP8.
- CCA state handling has no host syncs and no per-request loop (`VLLM_GPU_SYNC_CHECK=error` passes).
- `--tool-call-parser zaya --reasoning-parser zaya` parse ZAYA's `<zyphra_tool_call>` calls, including calls that end reasoning without `</think>`. `zaya_xml` is an alias matching the model cards.

## Validation

**Tests** (B300):

```bash
pytest tests/models/language/generation/test_hybrid.py -k zaya   # 1 passed
pytest tests/tool_parsers/test_zaya_tool_parser.py                 # 3 passed
pytest tests/models/test_initialization.py tests/models/test_registry.py -k Zaya  # 2 passed
```

`test_zaya_cca_state` builds a random tiny ZAYA1 (full and sliding-window layers) and compares vLLM against Transformers in fp32 with chunked prefill (`max_num_batched_tokens=32`) and prefix caching (cold pass, then cached pass). It fails if decode history, prefill/prefix-cache history, or the delayed value state is dropped (each mutation checked). The released tiny checkpoints (`tiny-random/zaya1`) predate the released config format, so the test builds its own.

**Correctness vs Transformers**

| Model | Setting | Result |
|---|---|---|
| ZAYA1-8B | fp32, 3 prompts × 60 greedy tokens, single and batched | 60/60 each |
| ZAYA1-74B-preview | fp32, TP=2, prompt logprobs over 5,200 tokens (past the 4,097 sliding window) | mean \|Δlogp\| 2.2e-4; 6 tokens > 0.05 (max 0.21); max after token 4097: 0.0009 |

Transformers' own one-shot vs chunked prefill differs by up to 0.77 logprob on 8B: the hard top-1 router flips experts on near-ties (203 of 104k routing decisions on a 2.6k-token prompt), so bf16 and long-prompt greedy outputs are not token-exact across implementations or batch shapes. vLLM's deviations land on the same positions.

**Eval** (GSM8K, chat, `--reasoning-parser zaya`, temperature 1.0 / top-p 0.95 per the model card, 16k max tokens):

| Model | GPUs | Accuracy | Invalid | Mean output tokens |
|---|---|---|---|---|
| ZAYA1-8B | 1× B300 | 0.893 | 0.001 | 2,315 |
| ZAYA1-74B-preview | 1× B300 | 0.893 | 0.001 | 1,085 |

Full 1,319-question test set, single run with `--seed 0`. The model cards report no GSM8K score, so this checks end-to-end serving health rather than reproducing a published number.

```bash
vllm serve Zyphra/ZAYA1-8B --max-model-len 32768 --reasoning-parser zaya
python tests/evals/gsm8k/gsm8k_eval.py --use-chat-completions --max-tokens 16384 \
    --temperature 1.0 --top-p 0.95 --seed 0 --num-shots 0 --request-timeout-seconds 7200
```

**Other runs** (ZAYA1-8B): TP=2; EP (`--data-parallel-size 2 --enable-expert-parallel`) with a parsed tool call and a `json_schema` response after reasoning over `/v1/chat/completions`; `--quantization fp8`; default prefix caching (4,752 of 4,756 prompt tokens hit, cached output identical to cold).

## Details

- **CCA** (Compressed Convolutional Attention) mixes q/k with a two-stage causal conv over the current and two previous tokens, and takes half of v from the previous token's projection. Each layer keeps the last two raw q/k rows and the previous delayed value as Mamba state, reusing `ShortConvAttentionMetadata` (only per-request slots and query offsets are needed). Most tokens go through one conv over the flattened batch; only each request's first two tokens are recomputed against their saved history.
- **Router**: MLP router over `num_experts + 1` classes (the extra one skips the experts), with balancing biases and the previous layer's router state (EDA). Routing runs in the model and is passed to `FusedMoEFactory` through `custom_routing_function`. The weights slice is made contiguous: MoE kernels ignore the stride of a `[:, :topk]` view of the packed routing tensor and read token IDs as weights.
- Attention, CCA and router projections are replicated across TP ranks (2 KV heads); experts are TP/EP-sharded, as in #41999.
- Not supported: speculative decoding (raises), pipeline parallel, LoRA, EPLB.

- claude[bot] · comment · 2026-11-03T06:57:31Z · [source](https://github.com/vllm-project/vllm/pull/65302#discussion_r4451730138)

File: `vllm/model_executor/models/zaya.py` · line None

🔴 Running ZAYA1 with TP>1, DP>1 and `--enable-expert-parallel` on the default all2all backend will likely fail on the first MoE forward. The block sets `is_sequence_parallel=parallel_config.use_sequence_parallel_moe`, which turns on sequence-parallel dispatch. It still passes the full, TP-replicated `hidden_states` and `routing` to `self.experts`, and it never all-gathers the output. Fix: when that flag is set, chunk both tensors with `sequence_parallel_chunk` before the experts call, then `tensor_model_parallel_all_gather` the result and trim it to `num_tokens`, as qwen3_moe.py:227-238 does. Otherwise pass `is_sequence_parallel=False`.

<details>
<summary>Why this was flagged</summary>

`ParallelConfig.use_sequence_parallel_moe` (vllm/config/parallel.py:858-876) is True whenever EP is on, TP>1, DP>1 and `all2all_backend` is one of the listed backends. The default `allgather_reducescatter` (parallel.py:228) is in that list. With SP on, the dispatch in vllm/distributed/device_communicators/all2all.py:130-132 uses the EP group. It takes per-rank sizes from `dp_metadata.get_chunk_sizes_across_dp_rank()` and asserts `sizes[dist_group.rank_in_group] == hidden_states.shape[0]`. Those sizes assume each TP rank holds 1/TP of the tokens. ZayaSparseMoeBlock.forward (zaya.py:426-430) passes every token, so that assert fails, or the gather and reduce-scatter sizes are wrong. moe_runner.py:443-444 also says that under SP 'there is a separate AG step handled in the model', which ZAYA leaves out. Other MoE models such as qwen3_moe.py:227-238 chunk the input and all-gather the output. The PR's EP run used DP=2 with TP=1, where SP is off, so this setup was not exercised.

**Verification:** zaya.py:422 passes `is_sequence_parallel=parallel_config.use_sequence_parallel_moe`, but `ZayaSparseMoeBlock.forward` never calls `sequence_parallel_chunk` before the experts. With TP>1, DP>1 and EP on the default backend, all2all.py:102 asserts `sizes[dist_group.rank_in_group] == hidden_states.shape[0]`, so ceil(n/tp) != n fails on the first MoE forward.

</details>
