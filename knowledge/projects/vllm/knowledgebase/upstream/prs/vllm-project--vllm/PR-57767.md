# [ROCm] Add native HIP RDNA3/RDNA4 custom all-reduce backend

[Upstream PR](https://github.com/vllm-project/vllm/pull/57767) · state: open · merged: False

## Original PR description



## Purpose

Refs #55916.

This PR adds an opt-in native HIP custom all-reduce backend for homogeneous,
single-node RDNA3 and RDNA4 tensor-parallel groups. The kernel is compiled into
vLLM's existing `_rocm_C` extension and is enabled with:

```text
VLLM_ROCM_USE_RDNA_ALL_REDUCE=1
```

The default behavior is unchanged when the option is disabled. Unsupported
operations continue through the existing communicator dispatch chain and fall
back to PyNCCL/RCCL in the tested configuration.

The implementation currently supports:

- `gfx1100` (RDNA3) and `gfx1201` (RDNA4);
- TP2 and TP4 on homogeneous, single-node GPU groups;
- BF16 and FP16;
- HIP graph capture and replay;
- two-dimensional `[batch_size, hidden_size]` tensors with
  `batch_size <= 128` and `hidden_size <= 8192`.

`gfx1200` is included as a compile target but is not enabled at runtime because
it was not available for hardware validation.

### Decode-aware routing

The custom backend is deliberately restricted to uniform single-token decode.
An all-reduce is selected only when a forward-context batch descriptor is
available, `num_reqs == num_tokens`, the tensor's first dimension matches the
decode batch size, and all shape, dtype, architecture, TP-size, and graph-mode
requirements are satisfied.

Prefill, mixed batches, eager execution, calls without a forward context,
DBO/microbatch overlap, batch-invariant execution, and unsupported shapes all
fall back to the existing path. RDNA3 additionally falls back when
`numel >= 131072`, because its larger-message region did not consistently
outperform RCCL in graph benchmarks. RDNA4 does not use this additional RDNA3
threshold.

The implementation also coordinates peer-access and HIP IPC initialization
across ranks. If setup fails on any rank, the whole group disables this backend
and falls back consistently. Concurrent replay of the same communicator
context on multiple streams is not currently supported.

### Why this does not duplicate #55917

#55917 addresses the same general RDNA all-reduce problem, but the two changes
use materially different implementations and production policies:

| Area | This PR | #55917 |
| --- | --- | --- |
| Kernel | Native HIP/C++ in `_rocm_C` | Python/FlyDSL |
| Architectures | RDNA3 and RDNA4 | RDNA4 |
| TP sizes | TP2/TP4, hardware validated | TP2/TP4 hardware validated; TP8 implemented and unit-tested but not hardware validated |
| Execution | Graph replay only | Graph replay plus selected eager cases |
| Routing | Serving-aware, decode-only admission | Size-based measured routing |
| Dependency | No FlyDSL dependency | Requires FlyDSL |

This PR is not intended to claim superiority over the FlyDSL implementation.
No direct native-HIP-versus-FlyDSL benchmark has been performed. It provides a
separate native HIP design, adds RDNA3 coverage, and uses a more conservative
decode-only integration policy. RFC #55916 is referenced for maintainer
coordination on whether this should proceed as a separate contribution.

## Test Plan

The implementation was built and tested in a ROCm container with PyTorch
2.12.0+rocm10.0.0, HIP 7.15.26333, and RCCL 2.30.4.

```bash
export PYTORCH_ROCM_ARCH="gfx1100;gfx1201"
export TRITON_KERNELS_SRC_DIR=/opt/python/lib/python3.14/site-packages/vllm/third_party/triton_kernels

cmake -S . -B .venv/rdna_integration/build -G Ninja \
  -DCMAKE_BUILD_TYPE=Release \

```

### Kernel correctness and performance matrix

The kernel benchmark was run for BF16 and FP16 on RDNA3 and RDNA4, with
TP2 and TP4. It loads the `_rocm_C` extension produced by the preceding CMake
build; it does not depend on a prebuilt or temporary standalone library.
Devices 0-3 were RDNA3 and devices 4-7 were RDNA4 on the test host:

```bash
RDNA_AR_LIBRARY="$PWD/vllm/_rocm_C.abi3.so"
RDNA_AR_RESULTS="$PWD/.venv/rdna_benchmark_results"
test -f "$RDNA_AR_LIBRARY"
mkdir -p "$RDNA_AR_RESULTS"

for dtype in bf16 fp16; do
  HIP_VISIBLE_DEVICES=0,1 .venv/bin/python -m torch.distributed.run \
    --standalone --nproc-per-node=2 \
    benchmarks/kernels/benchmark_rdna_custom_all_reduce.py \
    --library "$RDNA_AR_LIBRARY" \
    --dtype "$dtype" --output "$RDNA_AR_RESULTS/rdna3_tp2_${dtype}.json"

  HIP_VISIBLE_DEVICES=0,1,2,3 .venv/bin/python -m torch.distributed.run \
    --standalone --nproc-per-node=4 \
    benchmarks/kernels/benchmark_rdna_custom_all_reduce.py \
    --library "$RDNA_AR_LIBRARY" \
    --dtype "$dtype" --output "$RDNA_AR_RESULTS/rdna3_tp4_${dtype}.json"

for dtype in bf16 fp16; do
  HIP_VISIBLE_DEVICES=4,5 .venv/bin/python -m torch.distributed.run \
    --standalone --nproc-per-node=2 \
    benchmarks/kernels/benchmark_rdna_custom_all_reduce.py \
    --library "$RDNA_AR_LIBRARY" \
    --dtype "$dtype" --output "$RDNA_AR_RESULTS/rdna4_tp2_${dtype}.json"

  HIP_VISIBLE_DEVICES=4,5,6,7 .venv/bin/python -m torch.distributed.run \
    --standalone --nproc-per-node=4 \
    benchmarks/kernels/benchmark_rdna_custom_all_reduce.py \
    --library "$RDNA_AR_LIBRARY" \
    --dtype "$dtype" --output "$RDNA_AR_RESULTS/rdna4_tp4_${dtype}.json"
done
```

The default benchmark matrix was used in every run:

```text
batch_size = 1, 2, 4, 8, 16, 32, 64, 128
hidden_size = 1024, 2048, 4096, 5120, 8192
dtype = BF16, FP16
TP = 2, 4
```

This gives 40 shapes per architecture/TP/dtype combination and 320 total
performance configurations.

Each output JSON records the native HIP and RCCL latency, all nine raw timing
samples, per-rank samples, speedup, and the changed-input correctness result
for every shape.

### End-to-end serving benchmark

The serving benchmark used Qwen3.6-35B-A3B BF16 with TP4:

- 160 requests;
- maximum concurrency 16;
- fixed 1024-token inputs;
- fixed 128-token outputs with EOS ignored;
- maximum 20 active sequences;
- identical serving configuration for the custom and RCCL arms.

The custom arm enabled `VLLM_ROCM_USE_RDNA_ALL_REDUCE=1` and disabled other
optional custom all-reduce providers. The RCCL arm disabled the RDNA backend
and used `--disable-custom-all-reduce`.

### Model-output evaluation

Qwen3-8B BF16 was evaluated on RDNA4 with the repository GSM8K evaluator using
32 questions, 2-shot prompting, deterministic decoding, and TP2/TP4.

also verify that the input remains unchanged and that every custom-all-reduce
rank produces the same output.

| RDNA4 | 2 | BF16 | 0.001953125 | 0.001953125 |
| RDNA4 | 4 | BF16 | 0.005615234375 | 0.0054931640625 |
| RDNA3 | 2 | FP16 | 0.000244140625 | 0.000244140625 |

A separate precision and stress suite covered zero inputs, random inputs at

| GPU / TP | Non-diagnostic cases | Extreme diagnostic cases | Non-diagnostic failures |
| --- | ---: | ---: | ---: |
| RDNA3 TP2 | 288 | 0 | 0 |

For finite-value cases, this suite used FP64 accumulation over the quantized
BF16/FP16 inputs as its reference.

The focused precision shapes were:

```text
[1, 8], [1, 2048], [1, 2056], [16, 8184], [16, 8192],
[17, 8192], [32, 8192], [33, 8192], [128, 8192]
```

The 72 diagnostic cases intentionally exercise intermediate-overflow
cancellation such as `[max, max, -max, -max]`. Both custom reduction orders and
RCCL can produce NaN/Inf for these inputs even when the mathematical sum is
finite, so these are reported separately rather than counted as ordinary
correctness failures. The implementation does not claim bitwise equivalence
with RCCL because BF16/FP16 accumulation order can differ.

Stress coverage included 512 mixed-size eager calls and graph sequences with
40 nodes, three launch orders, and 64 changed-input replays per order for each
RDNA/TP configuration. RDNA3 TP4 additionally completed a 32770-replay test
covering ring-tag wraparound.

### Kernel-level performance

The graph benchmark compares the native HIP operation with PyNCCL/RCCL over
the same 320 configurations used for the changed-input checks.

Each captured graph performs a device-side collective before the timing event
to align ranks, followed by ten measured all-reduces. Each provider receives
ten warm-up replays and 100 timed replays per sample. Nine samples are
collected with alternating native-HIP/RCCL order. Each replay is reduced to the
slowest rank, and the reported value is the median of the nine sample means.

The measurements use fixed pointers and warm caches. The native HIP operation
is out-of-place and RCCL is in-place. Input initialization, Python dispatch,
model execution, and optional layout-staging copies are outside this
kernel-level timing.

Across the complete 320-case matrix, native HIP was faster in 299 cases and
reached at least 1.05x speedup in 290 cases. The production-selected regions
have the following equal-shape geometric-mean speedups:

| GPU | TP | Dtype | Selected shapes | Geomean speedup | Native HIP faster |
| --- | ---: | --- | ---: | ---: | ---: |
| RDNA3 | 2 | BF16 | 27 | 2.075x | 27/27 |
| RDNA3 | 2 | FP16 | 27 | 1.972x | 27/27 |
| RDNA3 | 4 | BF16 | 27 | 2.215x | 27/27 |
| RDNA3 | 4 | FP16 | 27 | 2.160x | 27/27 |
| RDNA4 | 2 | BF16 | 40 | 1.532x | 32/40 |
| RDNA4 | 2 | FP16 | 40 | 1.427x | 32/40 |
| RDNA4 | 4 | BF16 | 40 | 2.057x | 39/40 |
| RDNA4 | 4 | FP16 | 40 | 1.939x | 36/40 |

Speedup is defined as `RCCL latency / native HIP latency`, so values greater
than 1.0 favor native HIP.

The complete batch-size and hidden-size matrices follow. RDNA3 measurements at
or above 131072 elements are included for completeness, but the production
router rejects those shapes and uses RCCL.

### Runtime routing

The final RDNA4 TP4 serving run recorded the expected dispatch decisions:

```text
non_decode_rccl:
shape=(16384, 2048), selected=False

no_context_warmup_rccl:
shape=(40, 2048), descriptor=None, selected=False

decode_custom:
shape=(20, 2048), num_reqs=20, uniform=True, selected=True
```

This verifies that prefill and the no-context startup embedding all-reduce use
RCCL, while an eligible single-token decode graph uses the native HIP backend.

### End-to-end serving performance

Qwen3.6-35B-A3B BF16 TP4 serving completed successfully with both the native
HIP backend and the PyNCCL/RCCL baseline on:

- 4x AMD Radeon Pro W7900 (`gfx1100`, RDNA3);
- 4x AMD Radeon AI PRO R9700 (`gfx1201`, RDNA4).

All measured runs completed 160/160 requests with zero failures. No OOM,
illegal-memory-access, segmentation-fault, or fatal-error report was observed.

| GPU | Native HIP custom all-reduce | PyNCCL/RCCL | Output throughput improvement |
| --- | ---: | ---: | ---: |
| RDNA3 (`gfx1100`) | approximately 221 tok/s | approximately 206 tok/s | approximately **7.5%** |
| RDNA4 (`gfx1201`) | approximately 520 tok/s | approximately 423 tok/s | approximately **23%** |

These are native-HIP-versus-PyNCCL/RCCL results, not a comparison against the
FlyDSL implementation in #55917.

### Model-output evaluation results

For the Qwen3-8B BF16 GSM8K sample:

| Configuration | PyNCCL/RCCL | Native HIP |
| --- | ---: | ---: |
| TP2, 256-token output limit | 28/32 | 28/32 |
| TP4, 256-token output limit | 28/32 | 27/32 |
| TP4, 512-token output limit | 30/32 | 30/32 |

The TP4 difference at the 256-token limit came from a response being truncated
before its final answer. With the limit raised to 512 tokens, both backends
scored 30/32. Different all-reduce accumulation orders can still produce small
floating-point differences, so these results are not presented as bitwise or
token-by-token equivalence.

- maketechworkllc · comment · 2026-10-26T04:06:18Z · [source](https://github.com/vllm-project/vllm/pull/57767#issuecomment-6407979361)

Heads-up from testing this PR on top of v0.32.0rc2. `CudaCommunicator.__init__` now has a function-local `from vllm.config import get_current_vllm_config_or_none` inside the ROCm `tp` branch. Newer main also calls `get_current_vllm_config_or_none()` further down the same `__init__` (the `# cuMem graph buffers cannot be IPC-registered` block). Because of the local import, Python treats the name as local to the whole function. So for any group whose name is not `tp` and that has more than one rank (in practice the `ep` group, which is created for MoE models or when there is no model config), init fails with:

```
File ".../cuda_communicator.py", line 156, in __init__
    config = get_current_vllm_config_or_none()
UnboundLocalError: cannot access local variable 'get_current_vllm_config_or_none' where it is not associated with a value
```

I hit it in `tests/distributed/test_custom_all_reduce.py` (TP=2, no model config, so the `ep` group exists). Dense-model serving is not affected because no `ep` group is created. A MoE model at TP>=2 should hit it once this PR is rebased on current main. The module already imports the name at the top, so deleting the local `from vllm.config import get_current_vllm_config_or_none` line fixes it.

With that line removed (in memory, test only), the TP=2 tests in `tests/distributed/test_custom_all_reduce.py` from #61848 pass on 2x R9700 (gfx1201).
