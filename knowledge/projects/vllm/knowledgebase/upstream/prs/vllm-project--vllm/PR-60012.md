# [ROCm][Perf] gfx950 device length aware top-k split policy for k=2048

[Upstream PR](https://github.com/vllm-project/vllm/pull/60012) · state: open · merged: False

## Original PR description

This fixes #55327.

The change generalizes `topKPerRowDecodeGfx950DeviceLengthAware` to work with different values of k, and adds `gfx950TopK2048ActiveBlocks`. The grid still only depends on `numRows`, so graph capture stays stable, and the number of splits is now determined on device per row, ensuring that there are at least 2048 real indices in each split. Rows under 4096 can be processed by a single block, skipping the merge step.

GLM-5.2 and GLM-5.3 use `index_topk` 2048, which goes through the generic path on gfx950 and has 10 splits. In the merge step, all 20480 candidates are processed by a single block for each row. For rows with fewer active tokens this can lead to significant overhead. With this PR, the number of candidates per row in the merge step will be reduced to between 0 and 12288, a 70 percent reduction in the median case.

I also added two new tests for gfx950 and k 2048, to make sure we're covering the different numbers of splits and graph capture and replay.

I've checked this with a CPU model on all 35 shapes mentioned in the issue, and the result is an exact match with exact top-k for all of them. The kernel compiles fine for gfx950, and I'll provide timings on MI355X in this PR.
