# Raise OpenAI LM-eval server startup budget

[Upstream PR](https://github.com/vllm-project/vllm/pull/56725) · state: open · merged: False

## Original PR description

## Summary

- give the OpenAI LM-eval correctness server 600 seconds to become healthy on every platform
- keep TPU behavior unchanged while extending the NVIDIA fallback from 480 to 600 seconds

## Why

The exact H200 LM-eval test has repeatedly exhausted the fixed 480-second server-start budget while normal initialization was still progressing:

- daily main [#88612](https://buildkite.com/vllm/ci/builds/88612): `test_lm_eval_accuracy_v1_engine` failed after 518.71 seconds; its exact retry passed
- daily main [#88685](https://buildkite.com/vllm/ci/builds/88685): the same test failed after 521.52 seconds; CUDA-graph capture completed about 15 seconds after timeout cleanup began
- main [#98836](https://buildkite.com/vllm/ci/builds/98836): H200 OpenAI API Correctness timed out at the same 480-second boundary after a 356-second graph capture
- main [#98857](https://buildkite.com/vllm/ci/builds/98857): H200 OpenAI API Correctness and Rust Frontend Core Correctness ran concurrently on two `h200-ci-5` MIG slices, spent 203 and 219 seconds in their first graph captures, and both reached the same 480-second boundary

Both exact lanes passed on intervening main [#98843](https://buildkite.com/vllm/ci/builds/98843), which rules out a deterministic source regression and points to variable host contention/cold-start time. This change adds two minutes of headroom for those slow but healthy starts. Fast starts do not wait longer, and no serving or model-output behavior changes.

## Duplicate work

I searched open vLLM PRs and issues for `test_lmeval`, `max_wait_seconds`, `OpenAI API Correctness timeout`, and `server failed to start`; I found no other open fix for this test's startup budget.
