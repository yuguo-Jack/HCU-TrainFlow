# [Rust Frontend] Add request observers to vllm-llm

[Upstream PR](https://github.com/vllm-project/vllm/pull/61936) · state: open · merged: False

## Original PR description



## Overview

Adds a request-completion seam to `vllm-llm`: every request that reaches a terminal state produces one `FinishedRequest`, which the built-in Prometheus recording and any registered `RequestObserver` consume. First of the two PRs proposed in #58313; the `vllm-server` registration (`ServeExtensions`) is #61937, stacked on this one. Related: #44757.

## Claims

- Both terminal points of `GenerateOutputStream` (engine finish in `poll_next`, frontend abort or stop-string match in `Drop`) notify observers exactly once per request.
- Prometheus and observers derive from the same `FinishedRequestStats`, so the latency breakdown cannot drift between them. Existing metric values are unchanged.
- No behavior change and no extra allocation when no observer is registered.

## Validation

The same commands as the `Rust Frontend Cargo` CI jobs (`.buildkite/test_areas/rust_frontend_cargo.yaml`), which run on `rust/` changes:

```bash
cd rust
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --all-features --locked -- -D warnings
cargo nextest run --workspace --all-features --locked --no-fail-fast
```

fmt and clippy pass. nextest: all of `vllm-llm` (28) and `vllm-server` pass. Two unrelated failures in the workspace run: `vllm-chat::roundtrip roundtrip_mimo_v26` (grammar snapshot mismatch) fails the same way on origin/main in my environment, and `vllm-engine-core-client` `connect_times_out_without_ready_message` (a timeout test in a crate below `vllm-llm`) failed once under the parallel run and passed 5/5 when rerun alone.

New tests cover:

- an engine finish followed by a drop, and a live stream dropped (reported as an abort), each notifying exactly once
- `events` being `None` when engines do not record stats, as opposed to a zero queue time

The existing request-metrics tests pass unchanged. No model or serving output is affected, so no model evals were run.

## Details

**Motivation.** Per-request data is computed in `RequestMetricsTracker::record_finished` and written straight to Prometheus, so nothing else can consume it. An out-of-tree module, for example per-tenant usage metering that also covers streams the client aborts, needs the same data. This is the Rust counterpart of the Python `vllm.stat_logger_plugins` hook. Details are in #58313.

**Design.**

- `record_finished` now returns a `FinishedRequestStats`, and the derived durations (e2e, queue, prefill, decode, inference, TPOT) are methods on it. Prometheus reads them from there.
- `GenerateOutputStream::finish()` is the single terminal point for both paths. It takes the observer context, so notification happens at most once.
- `RequestObserver::on_finished` is synchronous and runs on the request path, possibly inside `Drop`, so it must not block or perform I/O. Observers that need I/O hand each request to a task of their own and drain it in `shutdown`, which runs after the engine client shuts down. It must not panic either: observer panics are not caught, because the workspace builds with `panic = "abort"`, where `catch_unwind` has no effect.
- `Llm::with_request_observers` is the only entry point in this PR. It is a composition hook, not a stable plugin API.

**Relation to Python `FinishedRequestStats`.** The fields are the same: token counts, `max_tokens_param`, preemptions, `is_corrupted`, and the queue/prefill/decode/inference/e2e/TPOT breakdown. Two differences:

- Observers receive the raw timestamps and the derived durations are methods, rather than precomputed floats. A timestamp is `0.0` when the event was never observed, matching `RequestTimestamps` and the tracker.
- The derived durations keep the existing `diff_or_zero` clamping that Prometheus already applies, which Python does not.

**Relation to `RequestTimestamps` (#59314).** `FinishedRequestStats` does not embed `RequestTimestamps`. Observers also need the arrival and finish times, and they need to tell engines that do not record stats (`events: None`) apart from an event that was never observed (`0.0`). `RequestTimestamps` reports both cases as `0.0`.

**Relation to RFC #44757.** The `llm_request` span planned there can be one more observer on top of this seam, and metrics and spans then derive from the same value. I kept the seam in `vllm-llm` for that reason and am happy to adjust it to fit that plan.

**Alternatives considered.**

- *A `tracing` span plus a subscriber `Layer`, as `RequestTimingLayer` does for stage timings.* That suits diagnostics, but usage accounting would then depend on the log filter (that layer needs spans at `INFO` or above), and a layer sees fields only through `Visit`, not as typed values such as `FinishReason`. The span planned in RFC #44757 can still be built on top of this seam.
- *Asynchronous observers behind a queue owned by `vllm-llm`.* Capacity, back pressure (drop or wait), and batching depend on the consumer, and cheap consumers such as Prometheus or an OTel span (whose SDK already batches) would pay for a channel hop they do not need. An observer that does I/O puts a bounded queue in front of a task of its own and only calls `try_send` on the request path. I have such an adapter in an out-of-tree prototype and can upstream it if that is preferred.

**Limitations.**

- Only requests submitted to the engine are reported. A failure in `client.call(...)` produces no stream, so no notification.
- A request whose stream ends in a stream error (engine connection lost, unexpected close) is not reported either. This matches the Prometheus recording today: `Drop` skips streams that have already terminated. Errors the engine reports as a finish reason (`finish_reason=error`) are reported.
- Nothing in `vllm-server` registers observers in this PR; #61937 does.

**Not duplicating existing work.** I searched open PRs for #58313, "Rust Frontend observer", and "Rust Frontend tracing". None adds a request-finish hook. #50370 propagates trace headers to the engine, which is a different scope. #59314 (merged) exposes per-request timing in API responses; this PR exposes the finished-request record to in-process consumers. #53454 (open, resumable streaming sessions) wraps the same two `record_finished` calls in a `note_finished` helper and records the finish once per session. Whichever lands second merges that helper with `GenerateOutputStream::finish`, so observers also fire once per finished session.
