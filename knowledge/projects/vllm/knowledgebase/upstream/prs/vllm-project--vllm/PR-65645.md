# [ROCm][MiniMax-M3] Default to breakable CUDA graphs on ROCm

[Upstream PR](https://github.com/vllm-project/vllm/pull/65645) · state: open · merged: False

## Original PR description



## Overview

Default MiniMax-M3 (`MiniMaxM3SparseForCausalLM`, `MiniMaxM3SparseForConditionalGeneration`) to breakable CUDA graphs on ROCm, as DeepSeek-V4.1 and HY4 (#64763) already are. Draft until the accuracy checks below are done.

## Claims

- On ROCm, steps whose prefill + decode rows fit the prefill capture size (512 tokens by default) replay piecewise graphs, with the sparse attention running eagerly between the pieces, instead of running the whole step eagerly; decode steps keep their full graphs.
- MI355X TP4: a 64-512-token prompt alone reaches its first token 58-75% sooner; next to 2 running decodes, a 64-384-token prompt 42-52% sooner. Prompts above the capture size are unchanged.
- InferenceX AgentX on the same setup with the prefill capture cap raised to 2048 (first 20 min, one run per side): c16 TTFT p50 -15.5% and interactivity p90 +5.7%; c32 within noise (+1-2% interactivity).
- Cost: 6.1 GiB more graph memory per rank (~2 MiB per captured HIP graph on ROCm, see Details), 3.4% fewer KV cache tokens, engine init 8 s longer.
- `VLLM_USE_BREAKABLE_CUDAGRAPH=0` restores today's behavior.

## Details

Why: M3 cannot `torch.compile` on ROCm, so the default `FULL_AND_PIECEWISE` falls back to `FULL_DECODE_ONLY` ("the loaded model provides neither a compiled submodule nor breakable CUDA graphs"), and every step that carries prefill rows runs eagerly. An eager step of up to ~1K tokens costs 65-80 ms regardless of its size (launch-bound); the piecewise replay costs 17-32 ms. The AMD model already marks its sparse attention as the break (`@eager_break_during_capture` on `MiniMaxM3SparseAttention._run_attention`). Short prefills are common in agentic serving: in a 15-minute InferenceX AgentX c16 run on the nightly image, 55% of the prefill or mixed steps carried at most 2048 tokens and 18% at most 512 (566 such steps, 1.2% of all steps).

Tradeoffs / limitations:
- Only steps up to `max_prefill_cudagraph_capture_tokens` (default 512 on ROCm) benefit. Raising it is left to the deployment. The same setup with the cap at 2048 (`max_cudagraph_capture_size` on that image: 147 sizes instead of 51), one round each on the same 4 GPUs, TTFT p50 ms:

  | prompt tokens | alone: cap 512 -> **2048** | next to 2 decodes: cap 512 -> **2048** |
  |---|---|---|
  | 64-256 | equal | equal (+1-2%) |
  | 512 | 32.0 -> 32.0 | 91.9 -> **58.8** (-36%) |
  | 768 | 78.6 -> **40.1** (-49%) | 90.4 -> **67.7** (-25%) |
  | 1024 | 79.3 -> **47.8** (-40%) | 92.8 -> **71.3** (-23%) |
  | 1536 | 79.7 -> **57.5** (-28%) | 91.9 -> 86.5 (-6%) |
  | 2000 | 83.3 -> **68.5** (-18%) | 94.6 -> 94.2 (0%) |
  | 2048 | 80.8 -> **68.5** (-15%) | 97.6 -> 98.4 (a 2064-token step: eager) |
  | 3072 / 4096 | equal | equal |

  Cost per rank: graph memory 7.49 -> 19.30 GiB, KV cache 12.96M -> 12.07M tokens (-6.9%), capture 21 -> 32 s. The cost grows linearly with the number of capture sizes, ~123 MiB each: a breakable capture of this model is 61 HIP graphs (60 attention breaks), and every HIP graph currently holds ~2 MiB of VRAM for its kernel-argument pool (ROCm/rocm-systems#15012, fix proposed in ROCm/rocm-systems#14794). The gain per size shrinks as steps grow: next to decodes it is gone by ~1.5-2K tokens.
- The mono decode path (`VLLM_ROCM_MINIMAX_M3_MONO=1`) only runs under decode-only graphs; it now needs `--compilation-config '{"cudagraph_mode": "FULL_DECODE_ONLY"}'` or `VLLM_USE_BREAKABLE_CUDAGRAPH=0` (documented in the new `docs/models/minimax_m3.md`).
- Not a duplicate: #56075 only enables breakable graphs in the AMD disaggregated CI config; #63070 does the same default change for GLM-5.3-Flash.
