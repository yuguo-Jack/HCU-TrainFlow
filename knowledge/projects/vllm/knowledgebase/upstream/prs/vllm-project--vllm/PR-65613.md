# [KV Transfer] Integrate layerwise transfer into MooncakeConnector

[Upstream PR](https://github.com/vllm-project/vllm/pull/65613) · state: open · merged: False

## Original PR description



## Overview

Integrate @nwpu-zxr's layerwise and chunk-wise KV WRITE implementation from #62504 into `MooncakeConnector`. Request-level transfer remains the default. Users can opt into layerwise transfer through `kv_connector_extra_config.transfer_mode`.

Both modes share common code while retaining separate scheduling and completion lifecycles.

## Claims

- Once D is ready, layerwise mode sends completed KV blocks across layers and prefill chunks while P continues computing. This can reduce the transfer time remaining after prefill and improve TTFT, particularly for long prompts.
- Users select the transfer mode explicitly. The connector does not switch modes automatically.
- Both paths reuse transfer descriptor generation directly. Layerwise tasks no longer need temporary bulk request metadata.
- Common initialization, handshake metadata construction, and D-side receive submission each have one implementation, reducing the code that must be maintained across both modes.

## Details

### Why integrate into the existing connector?

Compared with #62504, this implementation removes several adapters between layerwise transfer and the existing Mooncake code:

- Each mode selects its own blocks, then calls `_build_block_descriptors()` for physical block expansion, TP offsets, region addressing, and coalescing. Layerwise sends no longer construct temporary `SendBlockMeta` objects, unused events, or copies of peer metadata to reuse the bulk planner.
- Both modes follow the normal Mooncake constructor, so future common initialization changes have one place to go.
- `_build_pull_metadata()` constructs shared fields once and adds layout or layerwise fields as needed. This removes metadata subclass conversion through `__struct_fields__` and decoder replacement. D-side receive submission and lease heartbeats also share one path.
- Registration explicitly validates the layerwise layout before registering memory and publishing the endpoint. The ordering no longer depends on a subclass bootstrap override.

Request-level and layerwise scheduling retain separate lifecycles. The shared code handles common mechanics, reducing the places that must change when Mooncake evolves.
