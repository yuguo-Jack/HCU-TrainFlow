# [Bugfix][DSA] Reserve the decode indexer logits in the memory profile

[Upstream PR](https://github.com/vllm-project/vllm/pull/62860) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

The DSA indexer's decode logits are not counted by the memory profiler, so eager and piecewise steps can OOM at runtime. This PR reserves them in the profiling run, the way DeepInfer's profile run does.

### OOM

DeepSeek-V4.1-Flash, 4×B200 DEP4 (InferenceX recipe, `--max-num-seqs 256`, `--max-model-len 1048576`, 5 spec tokens, `--gpu-memory-utilization 0.97`), AgentX at concurrency 512. Rank 0 died 5 minutes into the load:

```
File "vllm/models/deepseek_v41/nvidia/model.py", line 1086, in forward
    hidden_states, pre_mix, *late_aux = self.decoder_replay_layers(
...
File "vllm/model_executor/layers/sparse_attn_indexer.py", line 893, in sparse_attn_indexer
    logits = as_fp32_logits(logits, seq_lens.view(-1))
File "vllm/model_executor/layers/sparse_attn_indexer.py", line 312, in as_fp32_logits
    out = torch.empty_strided(
torch.OutOfMemoryError: CUDA out of memory. Tried to allocate 3.07 GiB. GPU 0 has a total capacity of 178.35 GiB of which 3.04 GiB is free.
```

### Why

- The indexer's decode path allocates the paged MQA logits on every call. DeepGEMM returns `[decode rows, max_model_len]`, in BF16 on SM100.
- Every top-k backend except `deep_select` then reads an FP32 copy made by `as_fp32_logits`. Here that copy alone is 786 rows (131 decodes × 6) × 1,049,088 columns × 4 B = 3.07 GiB.
- The profiling run reserves only `VLLM_SPARSE_INDEXER_MAX_LOGITS_MB` (512 MiB, the prefill chunk budget), so the KV cache takes this memory.
- FULL decode graphs keep the logits in their graph pool. Mixed batches, batches above the capture sizes, and eager mode allocate them from whatever the KV cache leaves.

### How DeepInfer handles it

[DeepInfer@774ce24](https://github.com/deepseek-ai/DeepInfer/tree/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01) sizes the decode logits the same way: `max_kv_len = runtime_max_model_len // kv_compress_ratio` ([index_attn.py#L95](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/model_executor/models/v4_modules/index_attn.py#L95), [#L434-L441](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/model_executor/models/v4_modules/index_attn.py#L434-L441)). It keeps them in BF16 ([#L87](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/model_executor/models/v4_modules/index_attn.py#L87)).

On decode engines, its `profile_run` runs `max_num_seqs` sequences of `1 + nextn` query tokens ([model_runner.py#L444-L511](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/worker/model_runner.py#L444-L511)). So the `[max_num_seqs × (1 + nextn), max_kv_len]` logits are part of the measured peak before the KV cache is sized.

### Fix

vLLM's shared indexer now does the same accounting. Its profiling (dummy) path reserves the larger of the prefill budget and the decode worst case:

- **Rows:** `min(max_num_seqs, max_num_batched_tokens) × (1 + num_speculative_tokens)`. The profiling branch reads it from the current vLLM config.
- **Width:** `max_model_len`, padded as DeepGEMM pads the rows: whole KV splits (384 columns on SM100, 256 elsewhere) at a 1024-byte stride, i.e. 1536 BF16 columns on SM100 (1,049,088 for 1M, as in the OOM above) and 256 FP32 columns elsewhere.
- **Bytes per element:** 6 on SM100 (BF16 + FP32 copy), 2 with `deep_select` and no DCP, 4 on other platforms (FP32).

The runtime upcast and the reservation use the same predicate, so they cannot drift apart.

### Memory

Same configuration, KV cache per rank at startup:

| | top-k backend | decode logits reserved | CUDA graphs | KV cache / rank |
|---|---|---:|---:|---:|
| main | `auto` | none (512 MiB budget) | 18.40 GiB | 41,050,274 |
| this PR | `auto` | 9.0 GiB (1536 rows × 1M × 6 B) | 18.40 GiB | 36,636,372 (−10.8%) |
| main | `deep_select` | none (512 MiB budget) | 12.39 GiB | 48,253,887 |
| this PR | `deep_select` | 3.0 GiB (1536 rows × 1M × 2 B) | 12.39 GiB | 48,163,989 (−0.2%) |

Measured before the width was aligned to 1536 columns, which adds 4.5 MiB (`auto`) or 1.5 MiB (`deep_select`) to the reservation.

The KV cache shrinks by less than the reservation, because the reservation stacks on top of what is live inside the indexer, not on top of the run's global peak. With `deep_select` the reservation costs 0.2% of the KV cache. The decode graphs also drop the FP32 copy, so `deep_select` leaves 17.5% more KV cache than `auto` on main.
