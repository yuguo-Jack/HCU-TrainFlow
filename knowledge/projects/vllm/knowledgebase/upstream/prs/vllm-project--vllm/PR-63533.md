# [Bugfix][MoE] Dynamic per-group BLOCK_M for SM120 DeepGEMM contiguous-grouped MoE

[Upstream PR](https://github.com/vllm-project/vllm/pull/63533) · state: open · merged: False

## Original PR description

## Why

On SM120 (RTX 6000D / RTX PRO 6000), the vendored DeepGEMM reports a fixed
contiguous-group alignment of 128, so every routed expert in a MoE batch is
padded to 128-row multiples and the grouped GEMM runs BLOCK_M=128 tiles.
At decode-time token counts (per-expert M is often 1-6), most of each tile
is padding — the whole MoE chain runs ~2x slower than it needs to.

The SM120 kernels support BLOCK_M in {64, 128}; nv_dev's DeepGEMM fork
already applies a per-group policy on SM120. This PR ports that policy into
the vLLM glue layer as a **shape-dynamic** cap.

## What this PR does

When `ceil(num_tokens * num_topk / local_num_experts) <= 64`, cap the
alignment at 64 instead of 128. Deterministic per token-count shape, so
cudagraph capture/replay stay consistent. Applied at the three call sites
that must agree (permute, both apply variants, warmup planning).

## Validation (8x RTX 6000D 84G SM120, DSV4.1-Flash-1017, TP8+EP8, DSpark k=7)

| tier | stock (128) | dynamic | delta |
|---|---|---|---|
| 1K c1 | 252.4 tok/s | 284.0 | +12.5% |
| 1K c32 | 973.5 tok/s | 1094.3 | +12.4% |
| 8K c8 | 546.1 tok/s | 826.1 | +51.3% |

Quality probes (17*19=323 / 9.11-vs-9.9 / factual zh / tool call) all
correct on both legs. Cross-machine check on a second host (vLLM dev440):
8K c8 triple-repeat 663/666/642 vs stock 605.8 (+8.5%, stable), c32 within
its variance band — no regression.

A global `set_mk_alignment_for_contiguous_layout(64)` was also measured and
is **not** the fix: it regresses c32 by ~7% because it also flips every
other DeepGEMM GEMM to 64. The scoped, shape-dynamic patch above only
downshifts the MoE group layout.

Full A/B logs + the validation matrix (7 tiers x 2 rounds) are archived at
xzwgit/llm-test `sm120opt-162/see-align-dyn/`.
