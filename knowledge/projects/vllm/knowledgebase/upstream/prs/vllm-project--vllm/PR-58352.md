# [ROCm][DSV4][Perf] Pack sparse-MLA ragged decode metadata into graph buffers

[Upstream PR](https://github.com/vllm-project/vllm/pull/58352) · state: open · merged: False

## Original PR description

## Overview

On ROCm, every DeepSeek-V4 / V4.1 sparse-MLA decode `build()` packs its ragged indices into scratch tensors and then copies them into the FULL decode graph buffers, and the ROCm SWA builders cannot refresh those buffers after a draft step; this PR packs straight into the graph buffers and adds the in-place draft refresh, so the ROCm SWA builders set `supports_draft_decode_metadata_update = True`.

`build_ragged_indices_from_dense_out()` runs the count → scan → compact kernels from #58058 into caller-owned buffers, writing counts into `indptr[1:]` and scanning them in place; `build_ragged_indices_from_dense()` becomes an allocating wrapper, so the `-1` filtering has one implementation and prefill output is unchanged. `build_ragged_into_graph_buffers()` and `refresh_decode_swa_ragged()` sit beside it in `rocm_aiter_mla_sparse.py` and are shared by the V4 C128A/SWA and V4.1 SWA builders; each ROCm SWA `update_draft_decode_metadata()` is `super()` plus one call. The gfx950 width narrowing is unchanged. The draft refresh comes from #52628 (Tres Popp, co-author), closed in favour of this PR.

When every draft attention group can update in place, the MRV2 draft speculators record the update in their FULL draft graph instead of rebuilding the draft metadata eagerly on every draft step; since #60692 that includes DSpark, whose draft layers are SWA-only on V4 and V4.1.

## Claims

- The packing runs 7 times per decode step on V4.1 and 3 on V4. Each call drops from 5 kernels, 3 allocations and 2 `hipMemcpyAsync` to 3 kernels, saving 14.2–14.6 µs (27 %) at every shape on MI355X.
- End to end on V4.1-Flash the effect is marginal: −1.5 % per verify step with DSpark and −0.4 % TPOT without spec at concurrency 1, within run-to-run spread at concurrency 4 and 64.
- All of it comes from the packing. The in-graph draft update removes main's eager draft rebuild (on 948 of 950 draft steps under DSpark) and its `Attention backend(s) DEEPSEEK_SPARSE_SWA cannot update draft decode metadata in place; falling back to rebuilding attention metadata eagerly.` log, but gives no measurable speedup: with the flag forced off, DSpark is within 0.5 % of the PR at every concurrency.
- GSM8K and DSpark acceptance agree with main as closely as a repeated main run does.

## Validation

Unit, MI355X (gfx950), main `5c4b94beec`, main's and the PR's `tests/` against each tree: the PR's tests pass on the PR; main's tests fail on the PR only where they import the removed `_copy_ragged_to_graph_buffers`; forcing the flag off fails only `test_rocm_swa_builder_enables_fused_draft_decode`; a no-op `refresh_decode_swa_ragged()` fails the four draft-update cases.

Micro, MI355X, main `5c4b94beec`, the production helpers at the e2e configs' V4.1 SWA shapes (1–384 rows × 128), 5 % `-1` sentinels, median of runs 2–4, same `indptr` and indices on both arms: main 53.5–53.9 µs per call, PR 39.0–39.4 µs, −14.2 to −14.6 µs (27 %) at every shape.

e2e, V4.1-Flash, TP=2, MI355X, main `5c4b94beec`, `--kv-cache-dtype fp8`, `VLLM_ROCM_USE_AITER=1`, DSpark as `{"method": "dspark"}`. `vllm bench serve`, random 1031 in / 509 out, 32 × concurrency prompts, one server on the host at a time, fresh server per run, median (range) of runs 2–4. "Flag off" is this PR with `supports_draft_decode_metadata_update = False`. ## Details

With `--monokernel` (off by default), V4.1 decode batches of up to 32 rows get their SWA metadata from `swa_decode_meta`, on gfx942 since #60731 and on gfx950 since #63885, which also writes into the graph buffers; this PR covers the default configuration, larger V4.1 batches, and V4. #57860 fuses indptr into a different V4.1 pack kernel and composes with this.
