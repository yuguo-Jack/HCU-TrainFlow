# [Bugfix] Apply the mHC input RMSNorm in forward_native

[Upstream PR](https://github.com/vllm-project/vllm/pull/56856) · state: open · merged: False

## Original PR description

## Purpose

`MHCPreOp` and `MHCFusedPostPreOp` accept `norm_weight` / `norm_eps` and their callers expect a normalized `layer_input`. On `main` the unfused paths disagree about who applies that norm:

| path | applies the norm? |
|---|---|
| `forward_cuda` | yes, inside the fused kernel |
| `forward_hip` with AITER or TileLang | yes, inside the fused kernel |
| `forward_hip` fallback | yes, `_apply_mhc_norm` on top of `forward_native`'s output |
| `forward_native` | **no** — takes both parameters and ignores them |

`CustomOp.forward_oot` falls back to `forward_native`, so every out-of-tree backend loses the normalization. The failure is silent: nothing raises, no NaN appears, the numbers are just wrong.

I hit this running GLM-5.3-Flash on Intel Gaudi 2. All 45 mHC layers lost their input norm; generation degraded to unrelated tokens with a near-uniform logit distribution (top-1 probability 0.99%, top-10 nearly equiprobable), while every per-layer NaN/Inf check stayed clean. @shiweijiezero hit the same thing independently on the MetaX backend.

## Change

`forward_native` of both ops now applies `_apply_mhc_norm` to the mix it returns. The HIP fallback branches, which used to apply it on top of `forward_native`, now return `forward_native`'s result directly — otherwise they would normalize twice. That is the shape `MHCPreDelayedOp.forward_hip` already has. The AITER and TileLang branches are unchanged. (HIP fallback fix suggested by @shiweijiezero.)

Not in scope: `forward_cpu` does not go through `forward_native`; it calls `mhc_pre_cpu`, which also accepts `norm_weight` / `norm_eps` without applying them. Its only in-tree caller today, the DeepSeek-V4 CPU model, passes no norm weight, and I cannot build the CPU kernel to test a change there.

## Test Plan

Two tests in `tests/kernels/mhc/test_mhc_kernels.py`, each parametrized over both unfused paths — `forward_native`, and `forward_hip` with AITER and TileLang disabled — for 8 cases in total:

- `test_mhc_pre_unfused_applies_norm_once`
- `test_mhc_fused_post_pre_unfused_applies_norm_once`

Each compares `layer_input` against the `norm_weight=None` mix normalized once by hand, and asserts the two differ *before* comparing, so the test cannot pass vacuously. On the HIP fallback they also check that with `norm_weight=None` every output matches `forward_native` exactly (suggested by @shiweijiezero). Every other mHC test is gated on `HAS_TILELANG_MHC` or AITER, which is why neither unfused path had coverage.

```bash
pytest tests/kernels/mhc/test_mhc_kernels.py -k unfused_applies_norm_once
```

The magnitude of the difference, measured on CPU with GLM-5.3-Flash's shapes (hidden 4096, hc_mult 4, 20 sinkhorn iterations):


End-to-end on Gaudi 2 with GLM-5.3-Flash, greedy decoding, prompt `中国的首都是` ("The capital of China is"):

| | output |
|---|---|

Single-token top-1 probability went from 0.99% (`'Å'`) to 43.1% (`'北京'`). That run used the first revision, whose `forward_native` is unchanged since; the review change touches only the HIP fallback, which Gaudi never executes.

`ruff check` and `ruff format --check` pass on both changed files.
