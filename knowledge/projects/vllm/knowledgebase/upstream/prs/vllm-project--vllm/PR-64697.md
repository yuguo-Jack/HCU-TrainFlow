# [Rust Frontend] Support --skip-tokenizer-init

[Upstream PR](https://github.com/vllm-project/vllm/pull/64697) · state: closed · merged: True

## Original PR description

## Overview

Support `--skip-tokenizer-init` in the Rust frontend: serve token IDs only, without loading a tokenizer, like Python's `skip_tokenizer_init`. The flag was declared unsupported, so `vllm-rs serve` with it exited at startup, and so did `vllm serve` with `VLLM_USE_RUST_FRONTEND=1`, where it arrives through `--args-json`. `tests/entrypoints/openai/completion/test_token_in_token_out.py` (a model directory without tokenizer files) is exactly this use case.

## Claims

| Input | Python | Rust after this PR |
|---|---|---|
| `/v1/completions` with a token-ID prompt | runs; `text` is `""`, token IDs returned on request | same |
| `/inference/v1/generate`, gRPC generate | runs | runs |
| text prompt, chat request, `/tokenize`, `/detokenize` | error | 400 ``"this request needs a tokenizer, which is not loaded when `--skip-tokenizer-init` is set"`` |
| `echo` of a token-ID prompt without `return_token_ids` | `AssertionError` (500) | 400 |
| structured outputs | 400 | 400 (the engine skips its tokenizer too, so it cannot compile grammars); the render server forwards them, since it does not configure the downstream engine |
| `stop` strings, `bad_words` | silently ignored | 400: neither can take effect without a tokenizer (vllm-project/vllm#46310 proposes the same for Python's stop strings) |
| completions `logprobs` | error when a token string is needed; `return_tokens_as_token_ids` works | 400 unless `return_tokens_as_token_ids` (request or server default) applies |
| token-ID range check | model vocab size (vllm-project/vllm#62911) | model vocab size |
| primary EOS | `None`; `generation_config` EOS ids become stop tokens | first `config.json` EOS id (the existing fallback when the tokenizer has no EOS); the rest stay stop tokens |

## Details

**Design.** The tokenizer is a null object, not an `Option`. Under the flag the text backend holds an `UnavailableTokenizer` whose text operations fail with `TokenizerError::Unavailable`, mapped to `vllm_text::Error::TokenizerUnavailable` (a request validation error, so 400). The `Tokenizer` interface and its consumers (prompt encoding, `tokenize_bad_words`, `/tokenize`, `/detokenize`, echo decoding) are unchanged and fail through their existing error paths. Only two places know the tokenizer is absent: loading, and one `TextBackend::has_tokenizer` flag for the checks that have no tokenizer call to fail.

- **Tokenizer (`vllm-tokenizer`).** `TokenizerError` becomes an enum, `Backend { message }` and `Unavailable`; the rest of this crate's diff is the mechanical rename of its error macro. `UnavailableTokenizer` reports the model vocabulary as its size.
- **CLI (`vllm-cmd`).** `skip_tokenizer_init` moves from the unsupported markers to `ModelArgs`, next to `--tokenizer`, `--revision` and `--hf-config-path`, because like them it decides which model files are read. `ModelArgs::python_args` forwards it to the managed engine, whose structured-output manager would otherwise load a tokenizer. The render server shares `ModelArgs`.
- **Loading (`vllm-text`, `vllm-chat`).** `ModelFileSources::skip_tokenizer_init` reads no tokenizer-side file (tokenizer, `tokenizer_config.json`, chat template; an explicit `--tokenizer` source is not opened), so a cached snapshot only needs `config.json`. `load_model_backends` builds a `TokenizerlessChatBackend` that rejects every chat request, since rendering and output parsing both need a tokenizer.
- **The flag.** `TextRequestProcessor::prepare` sets `detokenize = false`, which reuses the token-only output path and the stop-string rejection from vllm-project/vllm#63789. Structured outputs are rejected in `TextLlm` just before engine submission, since the engine skips its tokenizer too. Completions `logprobs` are rejected up front unless `return_tokens_as_token_ids` applies, because token strings would all be empty and collapse the candidate map instead of failing.
- `/tokenize` and `/detokenize` now map tokenizer errors through `text_submit_error` instead of a blanket 500, so request validation errors there (including prompt truncation) become 400.

**Differences from Python.**

- Stop strings and `bad_words` are rejected rather than silently ignored.
- gpt-oss chat is rejected too. Python's Harmony path happens to work without an HF tokenizer, but nothing tests or documents chat under `--skip-tokenizer-init`; a tokenizer-optional Harmony chat backend is a possible follow-up.
- Structured outputs are rejected even if an independently started engine has its own tokenizer: `skip_tokenizer_init` is one `ModelConfig` field shared by frontend and engine, and Python's frontend rejects them under it regardless of the engine.

Not a duplicate: no open PR implements `--skip-tokenizer-init` in the Rust frontend (searched open PRs for `skip-tokenizer-init` and `skip_tokenizer_init`). AI assistance (Claude Code) was used to prepare this change; the human submitter reviewed every changed line.
