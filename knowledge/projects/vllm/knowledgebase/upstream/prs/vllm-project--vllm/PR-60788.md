# [Bugfix] Fix invalid streaming JSON for duplicate argument keys in HYV4 tool parser

[Upstream PR](https://github.com/vllm-project/vllm/pull/60788) · state: open · merged: False

## Original PR description


_Requested by **Therapy** · [project thread](https://claude.ai/code/project/chan_01UUTMSzhBXeRgzWLB6g7Je4?thread=cmsg_01UUTMSzhBXeRgzWLB6g7Je4MmuNqD3ySDVwyKCwoEjH2o)_



## Overview

Fix `hy_v4` tool-call streaming when the model repeats an argument key: streaming emitted unterminated JSON (string keys) or a different value than non-streaming (non-string keys).

## Claims

- Streamed `arguments` for a call with a repeated key are now valid JSON. Before the fix, `{"city": "Paris", "city": "Berlin` was never closed.
- Streaming and non-streaming now agree: the last value wins (`{"city": "Berlin"}`, `{"days": 2}`). Before the fix, streaming gave `{"days": 1}` for an integer key.
- Output for calls without repeated keys is byte-for-byte unchanged. When no conflicting value was streamed yet (e.g. the whole call arrives in one delta), the output equals non-streaming exactly.

## Validation

- New test `tests/tool_parsers/test_hy_v4_duplicate_arg_key.py`: two consecutive calls in one output (a string key and an integer key, each repeated) streamed per token and in one delta. The test drives `HYV4ToolParser` through `run_tool_extraction_streaming` with a stub tokenizer that only provides the structural vocab, so no download is needed. Both cases pass with the fix and fail on `main`.
- Through `HYV4ToolParser` with a real tokenizer (gpt2 + HYV4 structural tokens added), via `tests/tool_parsers/utils.run_tool_extraction{,_streaming}`:

  | case | non-streaming | streaming on `main` | streaming with fix |
  |---|---|---|---|
  | `city`=Paris, `city`=Berlin | `{"city": "Berlin"}` | `{"city": "Paris", "city": "Berlin` (invalid JSON) | `{"city": "Paris", "city": "Berlin"}` → `{"city": "Berlin"}` |
  | `days`=1, `days`=2 | `{"days": 2}` | `{"days": 1}` | `{"days": 1, "days": 2}` → `{"days": 2}` |

- A differential fuzz of streaming vs non-streaming (27 inputs × delta sizes 1/2/5/all × guided on/off) shows no new mismatches. The duplicate-key mismatches are gone. The remaining ones are pre-existing and unrelated (see Details).
- `pytest tests/tool_parsers -k hy` passes. `pre-commit` (ruff, mypy) passes.
- Not validated end-to-end against a served HYV4 checkpoint: I have no HYV4 weights or a GPU that can run them. The change is confined to the extractor's string building, and the validation above exercises the same `HYV4ToolParser.extract_tool_calls_streaming` entry point the serving layer calls.

<summary>Minimal reproducer</summary>

```python
from vllm.tool_parsers.hy_v4_tool_parser import HYV4ToolExtractor

tags = ["<tool_calls>", "</tool_calls>", "<tool_call>", "</tool_call>",
        "<arg_key>", "</arg_key>", "<arg_value>", "</arg_value>"]
vocab = {t: 1000 + i for i, t in enumerate(tags)}
tools = [{"name": "get_weather", "parameters": {"type": "object",
          "properties": {"city": {"type": "string"}}}}]
text = ("<tool_calls><tool_call>get_weather"
        "<arg_key>city</arg_key><arg_value>Paris</arg_value>"
        "<arg_key>city</arg_key><arg_value>Berlin</arg_value>"
        "</tool_call></tool_calls>")

def tokens(s):
    i = 0
    while i < len(s):
        t = next((t for t in tags if s.startswith(t, i)), s[i])
        yield vocab.get(t, ord(t[0])), t
        i += len(t)

ex = HYV4ToolExtractor(vocab, "", strict=True)
prev, ids, args = "", [], ""
for tid, t in tokens(text):
    d = ex.extract_tool_calls_streaming(prev, prev + t, t, ids, ids + [tid], [tid], tools)
    args += "".join(tc["arguments"] or "" for tc in (d["tool_calls"] if d else []))
    prev, ids = prev + t, ids + [tid]
print(args)  # main: '{"city": "Paris", "city": "Berlin'  (unterminated)
```

## Details

**Root cause.** `_extract_streaming_incremental` stored closed arguments in a dict and skipped a key it had already seen (first value wins). The partial value of the repeated key was still appended to the streamed snapshot. At `</tool_call>`, the final JSON was rebuilt from the dict and came out shorter than what had already been streamed, so the closing `"}` was never sent. For non-string keys the repeat was dropped, so streaming kept the first value. Non-streaming builds a dict in order, so the last value wins there.

**Fix.** Keep closed arguments as an ordered list of `(key, value)` pairs, appending only pairs beyond those already recorded (`args_text` always starts at the call's first `<arg_key>`). At `</tool_call>`, the final JSON is `json.dumps(dict(pairs))` (identical to non-streaming) when that still extends the bytes already sent. Otherwise it is built from the pairs with the same manual join as the streamed snapshot, so it always extends the bytes already sent. `prev_tool_call_arr` still records `dict(pairs)` (last value wins).

**Trade-off.** Once an earlier value of a repeated key has been streamed, the key stays repeated in the streamed JSON, e.g. `{"city": "Paris", "city": "Berlin"}`. Bytes already sent for the first value cannot be retracted, so the alternatives are a value that disagrees with non-streaming, or (today) unterminated JSON. RFC 8259 §4 allows duplicate names but says behavior on them is unpredictable. Python `json` and JS `JSON.parse` keep the last value, which matches non-streaming. Parsers that reject duplicates (e.g. serde with a strict struct) still fail on these outputs. For string keys this is no regression, because `main` emitted unterminated JSON. For non-string keys `main` emitted valid JSON with the first value, so such parsers now see a duplicate there, but only when the first value was already streamed. Without repeated keys, the output is unchanged: the manual join uses the same `", "` / `": "` separators as `json.dumps`. With duplicates, `streamed_args_for_tool` and `json.dumps(prev_tool_call_arr[i]["arguments"])` differ, so `get_remaining_unstreamed_args()` returns `""`, which is correct here because everything was already streamed.

**Related PRs.** #55550 (name boundary / nameless calls), #55788 (newline-separated parallel calls) and #59620 (unterminated arguments on truncated streams) touch the same file but different code paths (name slicing and the drain loop). This change only touches argument accumulation. The test is in its own file so it does not conflict with the `test_hy_v4_tool_parser.py` those PRs add. Other pre-existing streaming/non-streaming differences the fuzz found are out of scope: whitespace inside `<arg_key>` (stripped only in streaming), a newline between `</arg_key>` and `<arg_value>`, and a second `<tool_calls>` block.
