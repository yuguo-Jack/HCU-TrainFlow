# [RFC][KV Cache] Implementation of programmable KV cache (#57103)

[Upstream PR](https://github.com/vllm-project/vllm/pull/62382) · state: open · merged: False

## Original PR description

## Purpose

This is our **draft reference implementation of [RFC #57103: Programmable KV Cache](https://github.com/vllm-project/vllm/issues/57103)**, shared for design discussion and implementation review. It does not close the RFC or claim complete acceptance.

Agentic sessions span multiple inference requests, tool pauses, and branches. The RFC lets an application express lifecycle and cache intent through the existing `KvHintsEnvelope`, while the engine resolves targets, approves resources, executes operations, and reports actual completion.

### How this implementation maps to the RFC

- **Common control and logical state:** request-attached hints and independent Python/HTTP control share the envelope, dispatcher, and engine approval path. Hash/session/continuation/range selectors resolve logical content separately from physical residency. Results are correlated by message/action IDs, with bounded replay, queries, ACK, cancellation, and engine epochs. Existing backend-owned KVCR payloads retain opaque forwarding.
- **Execution through existing cache infrastructure:** `SET_PRIORITY`, `COPY_TO`, and `MOVE_TO` use `KVCacheManager`/`BlockPool` and CPU/Mooncake Store adapters. GPU-source operations run at successful request completion before references are released; accepted transfers can outlive the request. COPY publishes reusable GPU content only after all participating ranks finish. MOVE stores first and reclaims eligible source copies afterward. Shared loads share reservations and transfer holds; a resume can wait for an existing load.
- **Optional policies and rollout integration:** retention, tool-wait movement, and quota/prefix-reuse scheduling consume engine observations and submit proposals through the same approval boundary. Explicit commands keep their meaning. Startup configuration controls policy registration. The benchmark harness connects real verl `ToolAgentLoop` calls, tools, token logprobs, response masks, and rewards; weight-update checks exercise draining, invalidation, and cache namespace isolation.

Implementation contracts: [native primitives and lifecycle](https://github.com/zhhangBian/vllm-note/blob/rfc-hint/vllm/v1/kv_hints/README.md). Reproduction: [benchmark commands](https://github.com/zhhangBian/vllm-note/blob/rfc-hint/benchmarks/programmable_kv_cache/README.md).

### Current conclusions

Recorded local experiments use Qwen3.8-27B BF16, two A100 80GB GPUs, TP=2, concurrency 16, and 32 rollouts from 8 GSM8K questions. Each fixed-work replay has 113 model calls and 8,121 output tokens. The principal comparisons use three runs per configuration and report median throughput relative to native APC at the **same GPU KV budget**; movement additionally uses a host Store.

| GPU KV per GPU          | Configuration                 | Native / reference elapsed | Throughput change |
| ----------------------- | ----------------------------- | -------------------------: | ----------------: |
| 2 GiB, constrained      | Quota/prefix-reuse scheduling |          449.06 / 219.63 s |           +104.5% |
| 2 GiB, constrained      | Retention + movement + quota  |          449.06 / 247.60 s |            +81.4% |
| 8 GiB, working set fits | Retention + movement + quota  |            54.09 / 56.13 s |             -3.6% |

These measurements support executable lifecycle/resource contracts and a scheduling benefit under constrained KV capacity. They do **not** establish an additional benefit from movement/composition over quota alone, or a general serving speedup. The 2 GiB setting is an artificial pressure diagnostic. When the working set fits, both arms have zero preemptions and equal cache hits; control overhead produces a regression.

Separate live tool runs took 452.37 / 288.73 / 214.34 s for native/full-policy/quota, each scoring 32/32 rewards. These are single runs with different generated trajectories and only 8 independent questions. Fixed replay reruns model generation but does not rerun tools or evaluate rewards.

The [experiment report](https://github.com/zhhangBian/vllm-note/blob/rfc-hint/docs/programmable-kvc/rollout-report-2026-10-12.md) records variability, tail-latency regressions, missing Store objects, methodology, and unfinished acceptance. Raw traces/logs remain local and are not included in this PR.

### Related work and remaining scope

Duplicate checks covered #57103's discussion, open PRs referencing it, and KV-hint/programmable-cache searches. [#58198](https://github.com/vllm-project/vllm/pull/58198) supplies a minimal request-free CPU-to-GPU primitive; [#59714](https://github.com/vllm-project/vllm/pull/59714) and [#38514](https://github.com/vllm-project/vllm/pull/38514) cover retention priority. This reference has a broader purpose: a runnable control/lifecycle/resource/execution path plus policy and rollout experiments. Its overlapping primitive, dispatcher, and priority code needs consolidation with those contributions before upstream merge. The experimental COPY/MOVE schema follows the direction discussed in #59708 and remains open to revision.

This draft preserves development baseline `30f5c01d4ebb5c493ed86195db24d0ec5b3ce3d7` and currently has conflicts with upstream `main`. Rebase and validation against current `main` remain open. Other gaps include the full prediction/fairness/outage/restart matrix, a fresh final 128-question evaluation, other models/layouts, Dynamo/llm-d integration, and full RL trainer/optimizer performance. CPU control requires one block per chunk; native Mooncake movement requires PCP=DCP=1. Cold-tier retention/deletion and mixed native/backend envelopes are unsupported.
