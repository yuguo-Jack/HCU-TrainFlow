# [Mamba] Export Mamba1 internal prefill checkpoints

[Upstream PR](https://github.com/vllm-project/vllm/pull/63815) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Mamba1 layers (Jamba, Mamba, FalconMamba) now export internal prefill checkpoints in align mode, as Mamba2, GDN and KDA already do. The scheduler no longer has to split their prefills at the replay boundary to cache it. This is one step in moving every Mamba backend off the align-mode chunk split (see #63670).

## Claims

- **Mamba1 prefills that fit the token budget take one step instead of two** with prefix caching on. A resend hits the same number of tokens as before.
- **Outputs stay correct.** Resent prompts that hit the checkpoint match an APC-off run, and gsm8k on falcon-mamba-7b is within one stderr of both main and APC off.
- **No kernel change.** The CUDA selective scan stores only each sequence's final state. So the metadata builder cuts each checkpointed prefill row at its checkpoint, and the mixer scans twice. The shared `MambaPrefillCheckpointExporter` copies the head's state and conv window into the checkpoint block between the two passes.

## Details

**Why two scans.** The CUDA `selective_scan_fwd` stores only each sequence's final state. Mamba2 gets its checkpoint from the SSD chunk states, but Mamba1 has nothing like that. So `Mamba1AttentionMetadataBuilder` asks the shared `MambaPrefillCheckpointBuilder` where each prefill row checkpoints, and cuts each such row into a head `[0, offset)` and a tail `[offset, query_len)`. That builder makes the same decision as the scheduler and `MambaManager`. The mixer then:

1. scans the heads and the uncut rows, with the tails' cache index set to `NULL_BLOCK_ID`, which the kernel skips;
2. runs `MambaPrefillCheckpointExporter` to copy each head's final state from the running slot, and the conv window before the checkpoint, into the checkpoint block;
3. scans the tails from the running slot (`has_initial_state=True`), with the heads masked instead.

The two scans cover disjoint tokens, so the total scan work is unchanged. A step with checkpoint rows costs one more scan launch and one exporter launch per Mamba1 layer. Steps without a checkpoint take the old single-scan path.

**Tradeoffs.**

- The tail resumes from the state stored in the cache, so the state is rounded to `mamba_ssm_cache_dtype` once at the checkpoint. A scheduler chunk boundary at the same position, which is what main does today, rounds the same way.
- Extending the CUDA kernel to store a mid-sequence state would avoid the second launch. It would also change the `selective_scan_fwd` op signature, which the XPU op shares, and need a native rebuild. The two-scan approach needs no kernel change.

**Multiple KV cache groups.** The runner builds metadata for the first Mamba group only and calls `update_block_table` for the other groups with the same spec. The head/tail slots and the checkpoint blocks are block-table entries, so `update_block_table` re-gathers them from the new group's table, as Mamba2 does for its checkpoint.

**Spec.** `MambaMixer.get_kv_cache_spec` declares `num_prefill_checkpoint_blocks=1` and `prefill_checkpoint_alignment=1`, the same as Mamba2 on main. Any token offset works because the cut can be anywhere.

**Not a duplicate.** Searched open PRs for Mamba1 / `selective_scan` prefill checkpoints. #62232 and #63742 touch Mamba2 only.
