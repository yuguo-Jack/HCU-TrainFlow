# [Bugfix][Core] Forward `extra_args` to beam search's per-step `SamplingParams`

[Upstream PR](https://github.com/vllm-project/vllm/pull/63525) · state: open · merged: False

## Original PR description

# [Bugfix][Core] Forward `extra_args` to beam search's per-step `SamplingParams`

## Summary

Custom logits processors never receive their arguments under beam search. `BeamSearchParams` has no `extra_args` field, and the per-step and per-beam `SamplingParams` built in `beam_search/{offline,online}.py` do not carry one -- so a processor that reads `SamplingParams.extra_args` silently sees an empty mapping, declines the request, and generation proceeds as if unconfigured. There is no error and no warning. It works as documented under ordinary sampling.

Adds `extra_args` to `BeamSearchParams` and forwards it at the three construction sites.

## Motivation

The V2 logits-processor plugin mechanism documents `extra_args` as how a processor receives per-request arguments (REST `vllm_xargs`, OpenAI SDK `extra_body`). Under beam search a caller sees plausible output that silently ignored their parameters.

Verified on a live engine (A10G, `facebook/opt-125m`): with the patch the processor's read point receives `target_token=128` on every request; without it, `None`.

The use case this blocks is prefix-dependent constrained decoding over a large closed set -- generative retrieval, where the constraint is a catalog-sized structure the processor owns. The declarative alternative is not a substitute: the beam path calls `backend.compile_grammar()` once **per beam per step**, because backends cannot clone grammar state and tokens are replayed instead. Measured with xgrammar 0.1.29 on a `choice` grammar, multiplied by W*C for width 10, depth 5:

| catalog | one compile | per request |
|---|---|---|
| 1,000 | 0.96 s | 48 s |
| 10,000 | 2.08 s | 104 s |
| 100,000 | 23.2 s | 1,161 s |

So for catalog-sized constraints a plugin is the only viable mechanism, and `extra_args` is how it is configured.

## Approach

`extra_args` is already `dict[str, Any] | None` on `SamplingParams`, documented as "arbitrary additional args, that can be used by custom sampling implementations, plugins, etc." This mirrors it onto `BeamSearchParams` and passes it through unchanged. No behaviour change for callers who do not set it.

### Three sites, not one

`offline.py` builds `SamplingParams` **twice** -- a base per step, and a per-beam one in `_build_beam_sampling_params()` when structured outputs are active. Forwarding only the base would leave the grammar path silently dropping the arguments, the same class of bug as the original. `online.py` has the server-side equivalent.

Each internal request gets its own mapping. The per-step params are built with `skip_clone=True`, so `SamplingParams.clone` shallow-copies and every beam would otherwise share one dict, unlike the ordinary generate path which deep-copies; a processor that mutated its arguments could then change what later beams observe. Values are shared, only the mapping is fresh.

## Changes

- `vllm/sampling_params.py` -- `BeamSearchParams.extra_args: dict[str, Any] | None = None`.
- `vllm/entrypoints/generate/beam_search/offline.py` -- forward in `base_sampling_params` and in `_build_beam_sampling_params`.
- `vllm/entrypoints/generate/beam_search/online.py` -- forward in the server-side per-step params.
- `vllm/entrypoints/generate/beam_search/utils.py` -- `copy_extra_args()`.
- `tests/entrypoints/unit_tests/test_beam_search_extra_args.py` (new) -- 4 tests.
- `tests/v1/logits_processors/test_custom_offline.py` -- 1 test.

## Test Plan

```
pytest -v tests/entrypoints/unit_tests/test_beam_search_extra_args.py
pytest -v tests/v1/logits_processors/test_custom_offline.py::test_custom_logitsprocs_beam_search
```

The unit tests assert `BeamSearchParams` has the **field** (parsed from the AST, not grepped -- the first version searched for the string `extra_args`, which the field's own docstring satisfies, so deleting the field left the test green), and that **every** `SamplingParams(...)` construction in the beam-search modules passes `extra_args`.

The live test asserts the processor *receives* its argument, through a recording subclass of the existing `DummyLogitsProcessor`. It deliberately does **not** assert that the processor changes the output: beam search selects from the *returned* logprobs, which are computed before logits processors run under the default `logprobs_mode`, so a processor cannot steer beam selection without further configuration. Asserting output forcing would make this test fail for a reason this patch is not responsible for.

## Test Result

A10G, vLLM at `c50aca1441`:

```
tests/entrypoints/unit_tests/test_beam_search_extra_args.py ....            [100%]
4 passed in 0.06s

tests/v1/logits_processors/test_custom_offline.py::test_custom_logitsprocs_beam_search PASSED
1 passed in 615.96s
```

Negative-controlled: with the forwarding reverted and the test unchanged, it fails with `processor received [None], expected every request to carry 128; extra_args did not reach the per-step SamplingParams`. Each of the unit-test edits was also reverted individually and the corresponding test watched to fail.

**Wins:** a documented plugin mechanism becomes reachable under beam search; no behaviour change for callers who do not set `extra_args`.

**Cost (honest tradeoff):** this is plumbing only. It makes the arguments arrive; it does not by itself let a plugin shape beam-search output, because the returned logprobs beam search selects from are computed before logits processors run. That needs `logprobs_mode="processed_logprobs"` and a non-null `allowed_token_ids` as well -- verified working, but out of scope here.

**Not verified:** the structured-outputs path. I had a parametrization covering the per-beam construction site, but it cannot run: `backend_name == "auto"` is unhandled in `beam_search/offline.py`, so any beam request with `structured_outputs` set raises `ValueError: Unsupported structured output backend: auto` on the default config. That looks like a separate upstream bug and I will file it separately; this PR therefore has no coverage of the second construction site, which I would rather state than paper over. vLLM's own beam-search suite has not been run either (needs an engine; single-GPU box).
