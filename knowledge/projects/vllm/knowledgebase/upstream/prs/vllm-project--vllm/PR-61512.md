# [Bugfix][Distributed] Eagerly map the MNNVL multimem reduce-scatter buffer

[Upstream PR](https://github.com/vllm-project/vllm/pull/61512) · state: open · merged: False

## Original PR description

## Overview

`CustomAllreduce` maps the MNNVL multimem reduce-scatter symmetric-memory buffer at construction instead of lazily on first in-window use mid-serving, and the two MNNVL reduce-scatter size ceilings are now configurable through env variables. Addresses #61169 (both of its suggested fixes).

## Claims

- The multimem buffer is allocated and rendezvoused during `CustomAllreduce.__init__` — like the communicator's other MNNVL buffers — but only for groups where this backend is actually reachable (`mnnvl_multimem_rs_supported`, window non-empty). Non-MNNVL deployments and `VLLM_BATCH_INVARIANT` builds map nothing they did not map before; the eager allocation is confined to setups that would have lazily mapped it at first window hit.
- The `mnnvl_multimem` backend is selected only when its multicast pointer is already mapped; unsupported and failed setups fall back to NCCL exactly as before, with the same warning paths now firing at startup instead of mid-serving.
- The two size ceilings are configurable: `VLLM_MNNVL_REDUCE_SCATTER_MAX_BYTES` (Lamport ceiling, default 16 MiB) and `VLLM_MNNVL_MULTIMEM_RS_MAX_BYTES` (multimem ceiling, default 64 MiB). Setting the multimem ceiling to 0 (or at/below the Lamport ceiling) disables only this backend without touching the other custom collectives — a deployment can now stay out of the multimem window per #61169. An empty window reports the backend unsupported, so nothing extra is mapped at startup.

## Validation

**Hardware:** 4× NVIDIA GB300 (SM103), single NVSwitch node (4-GPU NVLink domain), CUDA 13.x, Python 3.12.

- **Unit gates at current main** (`388a610df` + this PR): `tests/distributed/test_custom_all_reduce.py` backend/backend-selection/window-disabled/platform-gate/fake-rendezvous tests — **44/44 passed**, including the new `test_mnnvl_multimem_window_disabled_gate` (multimem ceiling 8 MiB: Lamport still selected below its ceiling, NCCL above, multimem never).
- **Distributed red/green** (development base, NGC torch build on 4×GB300): with this change `tests/distributed/test_custom_all_gather_reduce_scatter.py` + `test_custom_all_reduce.py` → **57 passed, 1 skipped** (tp_size=8 needs 8 GPUs); against base main the multimem distributed test fails at the constructor-state asserts (buffer absent → lazy), **2 failed / 1 skipped** — the exact red of this red/green is the invariant the patch pins: `fa.mnnvl_multimem_rs_initialized` after construction.
- `pre-commit` on changed files: ruff/mypy clean.

**CI coverage gap (documented per checklist):** the eager-init assertions need SM100/SM103 NVLink *multicast* groups of world size 2/4/8 — upstream CI has no such pool; the runs above were executed manually on GB300. A serving-level A/B of this hazard needs an NVL72-class fabric: in our k8s containers the symmetric-memory rendezvous returns `multicast_ptr=0` for same-node groups, MNNVL mode never engages, and the multimem window is unreachable by code path (selection requires `mnnvl_multicast_ptr`), so no serving run on this cluster can exercise the lazy-init path that #61169 describes. If maintainers have an NVL72 research-preview/CI lane, the observable delta of this PR is the `Using the low-SM MNNVL multimem reduce-scatter kernel.` log line moving from the first in-window request to construction time.

## Details

#61169 reports two 8×B300 serving runs that crashed (Xid + `CUBLAS_STATUS_EXECUTION_FAILED`) in the same second the multimem buffer was first mapped mid-serving; dozens of runs that never hit the 16–64 MiB window ran clean. The issue author states causation is not proven, and the crashing build predates #60468 — so this PR does not claim to fix the Xid; it removes the one first-time event unique to the crashing runs (multicast symmetric-memory allocation/rendezvous while CUDA graphs and kernels are live), which is the issue's first suggested fix. The size knobs implement its second suggested fix and give operators the per-backend opt-out requested in review.

Design: `_init_mnnvl_multimem_reduce_scatter_buffer` already tolerates startup failure (warning + permanent NCCL fallback), so moving the call into `__init__` lets `_select_reduce_scatter_backend` drop the lazy-init escape hatch and lets `custom_reduce_scatter` drop its `_IS_CAPTURING` bail-out for this backend — the pre-mapped buffer and fixed kernel addresses are capture-safe like the lamport path. The thresholds moved from class constants to `envs.py` entries read at communicator construction, so explicit `CustomAllreduce(max_mnnvl_multimem_reduce_scatter_size=...)` callers keep working unchanged.

Build note (environment only, not part of this diff): building on aarch64 with torch 2.14 required a local disambiguation in DeepGEMM's vendored `csrc/utils/torch_compat.hpp` (ADL ambiguity between the scalar wrappers and torch's curated stable-op wrappers) — follow-up proposed in vllm-project/DeepGEMM#36.
