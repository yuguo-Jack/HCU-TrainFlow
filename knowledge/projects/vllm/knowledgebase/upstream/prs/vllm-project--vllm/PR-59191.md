# [Bugfix][Distributed] Guard cross-node symmetric-memory rendezvous with fabric support

[Upstream PR](https://github.com/vllm-project/vllm/pull/59191) · state: closed · merged: False

## Original PR description



## Purpose

Fixes https://github.com/vllm-project/vllm/issues/59185.

On two B200 nodes without a multi-node NVLink (MNNVL) fabric, a TP=4 group with two GPUs per node can hang during communicator initialization and fail at the 1,800-second Gloo timeout. `SymmMemCommunicator` currently enters symmetric-memory rendezvous without checking whether the topology supports cross-node memory handles. An error on some ranks can leave other ranks blocked, so catching `RuntimeError` alone does not provide a safe fallback.

This change checks locality before allocating symmetric memory. Single-node groups retain the existing path; cross-node groups enter rendezvous only if every rank reports fabric support. The fabric probe returns false when unavailable or unsuccessful. CustomAllreduce's existing group-wide MNNVL gate also requires fabric support, since local multicast capability alone is insufficient.

The branch is based on upstream `main` at `3e2a7e74a556623ddee3a327299d7bf04055501e`. The previously tested patch was adapted to retain main's `_all_ranks_true` helper. Regression tests extend the existing distributed suites to cover non-fabric groups, partial fabric support, supported groups, and avoiding allocation/rendezvous when disabled.

Duplicate-work check on September 29, 2026: issue #59185 had no comments or open PR referencing it. An open-PR search for `SymmMemCommunicator fabric` returned #41834, which concerns DeepSeek V4 support on SM12x and does not modify the three communicator files changed here. The merged #53253 added CustomAllreduce gating but did not guard the separate `SymmMemCommunicator` rendezvous.

AI assistance was used to prepare this change and description (OpenAI Codex), building on an internal recorded experiments.

## Test Plan

Re-run the two-node B200 reproduction from #59185 against the unmodified base and this branch using the same pinned software and workload configuration. Verify that TP=4 (two GPUs per node) starts and completes model evaluation, and retain the TP=2 control (one GPU per node). Also exercise single-node and MNNVL-connected configurations; the prior experiment did not cover those paths.

The change adds one same-node probe during SymmMemCommunicator construction and one CPU MIN all-reduce for cross-node groups. Check startup behavior on supported topologies as well as fallback on unsupported ones. An unavailable FlashInfer fabric probe conservatively disables cross-node symmetric-memory fast paths.

## Test Result

| Configuration | Unmodified vLLM | Combined candidate |
|---|---|---|
| Qwen3.6-35B-A3B-FP8, TP=4, two nodes × two B200 GPUs | Startup fails; workload ends after ~1,921 s, including the 1,800-second Gloo timeout | Startup and GSM8K 10% subset evaluation complete in ~455 s; accuracy 0.4545 |
| Nemotron Super V3 120B-A12B FP8, TP=2, two nodes × one B200 GPU | Completes; GSM8K subset accuracy 0.9697 | Completes; accuracy 0.9394 |

Those experiments used vLLM `0.29.1rc1.dev573+ge97573215` and the same upstream base digest, `sha256:f75fec992c293dd41042745f8aa71bfdf12b188b6a01e0baf075e4bca5d297e5`, with separate node allocations. They tested both communicator changes together, once per arm and configuration, and measured total workload time rather than startup latency. The evaluation subset had 132 questions and no pass threshold; the TP=2 score difference is four questions. These results support the candidate's startup fix but do not establish accuracy equivalence, isolate either change, or validate this rebase. Single-node, MNNVL, TP=8, and NVFP4 coverage remain outstanding.
