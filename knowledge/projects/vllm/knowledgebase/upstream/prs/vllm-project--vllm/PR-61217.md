# [Bugfix][Parser] Forward skipped tool spans verbatim in the reasoning pass

[Upstream PR](https://github.com/vllm-project/vllm/pull/61217) · state: open · merged: False

## Original PR description

## Overview

Fixes the first problem reported in #61206: with an engine-based Qwen3 reasoning parser, the reasoning-only pass (`skip_tool_parsing=True`) removes literal think markers quoted inside a tool parameter value before the tool pass sees the span. The forwarded argument must remain verbatim, while a tool opener merely mentioned in reasoning prose must not suppress the real reasoning/content boundary.

## Claims

- In the reasoning-only pass, a skipped tool span is forwarded to the tool pass verbatim: non-tool terminals inside it emit their text instead of applying their reasoning-channel transitions.
- Both `<think>` and `</think>` quoted in tool arguments survive the reasoning pass.
- Qwen3's duplicate-`</think>` absorb in CONTENT still applies outside the span; only in-span handling changes.
- A `<function=...>` opener mentioned in reasoning prose does not open a skipped span or swallow the following real `</think>`.
- No change to normal (non-skip) parsing, streaming deltas, or generation.

## Validation

The reproducers run through the same chain the serving layer uses: a reasoning pass with `skip_tool_parsing=True`, followed by the tool pass on the forwarded content.

```bash
pytest tests/parser/engine/test_engine.py::TestSkipToolParsingMarkerPassthrough \
  "tests/parser/engine/test_qwen3.py::TestNonStreaming::test_think_marker_quoted_in_parameter_survives_reasoning_pass" \
  "tests/parser/engine/test_qwen3.py::TestNonStreaming::test_tool_opener_mentioned_in_reasoning_does_not_hold_content"
```

- The marker-passthrough regressions fail on main and pass on the final head.
- The reviewer-provided tool-opener-in-reasoning case is also a real red/green regression: the intermediate head returned the real `</think>` and subsequent prose as reasoning; the final head restores the expected reasoning/content split.
- Final head: `pytest tests/parser/engine/`: **5868 passed**.
- Pre-commit passes on all three files changed by the final review follow-up.
- Parser-level validation only: this machine has no GPU, so no served-model run. The gate sits in the skip pass and cannot affect sampling or kernels; generated text is unchanged, only the forwarding of already-generated text is repaired.

## Details

Root cause: in `StreamingParserEngine._on_terminal`, the `skip_tool_parsing` gate intercepts tool terminals and tracks `_in_skipped_tool_span`, but any other terminal with a transition reachable from CONTENT still went through `_apply_transition` inside the span. For qwen3 that is `(CONTENT, THINK_END) -> (CONTENT, ())`, the rule that absorbs a duplicate `</think>`. Models can quote think markers as ordinary text inside string arguments, and the absorb deleted them from the text handed to the tool pass.

Fix: while `_in_skipped_tool_span` is set and the terminal is not one of the config's tool terminals, emit the value for the current state instead of applying the transition. Tool terminals keep their existing span-tracking path, so openers and the exit that clears the span behave exactly as before. An intermediate attempt also treated a tool terminal with no transition in the current state as an opener; that was removed after review because it incorrectly captured tool syntax mentioned in reasoning prose. The change lives in the engine rather than `qwen3.py` because the skip pass promises verbatim forwarding for every declarative config.

Relation to nearby open PRs (checked before opening):

- #60256 keeps a text-spelled marker as content in non-streaming parse when it arrives as ordinary tokens; it does not cover a marker token inside a skipped tool span.
- #56661 defers a quoted `<tool_call>` opener in prose; this is the opposite direction, a marker inside an already-open span.
- #58407 balances `</parameter>` closers inside values within the tool parser; this fix is in the reasoning pass that runs before it.

The second problem in #61206 (finish_reason) already has #58286; the third (out-of-order tool results against an ID-less template) is a separate design question, left out of this PR.
