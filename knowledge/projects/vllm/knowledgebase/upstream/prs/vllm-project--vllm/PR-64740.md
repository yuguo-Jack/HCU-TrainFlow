# [ROCm][CI] Run MI355 MoE Kernels on a full MI355 instead of DPX

[Upstream PR](https://github.com/vllm-project/vllm/pull/64740) · state: closed · merged: True

## Original PR description

## Purpose
`:amd: (MI355 DPX) MoE Kernels` failed in shards 2-5 of the nightly [amd-ci#15747](https://buildkite.com/vllm/amd-ci/builds/15747). Each of these shards ran one case of `test_aiter_moe_sort_backend_dispatch_env_matrix_mxfp4` (added in #62976), and all four failed with `Expected this MXFP4 DSV4 shape to set aiter's internal output_aux flag`. Shard 1 passed only because pytest-shard placed none of the four cases there.

The test relies on aiter selecting a tuned DSV4 MXMOE kernel, which sets `output_aux`. aiter keys its tuned MoE configs by `(gfx, cu_num, ...)`, and `dsv41_fp4_tuned_fmoe.csv` only has `gfx950,256` rows. The DPX agents expose 128-CU partitions, so aiter falls back to a heuristic FlyDSL config without `output_aux`. No gfx950 MoE config in aiter has 128-CU rows.

This PR moves the step from `mi355_dpx` to `mi355_1` (full MI355X, 256 CUs). 

## Test Plan
Full MI355X (gfx950, SPX, 256 CUs), in the `rocm/vllm-dev:ci_base` image with aiter 0.1.26, vLLM at 617135eed3.
The whole step ran as in CI: its three commands from `test-amd.yaml`, 5 shards in parallel with one GPU each, and the `run-amd-test.sh` environment.
The DSV4 cases were also run on their own:
```bash
cd tests
VLLM_ROCM_USE_AITER=1 VLLM_ROCM_USE_AITER_MOE=1 pytest -v -s kernels/moe/test_modular_kernel_combinations.py \
  -k test_aiter_moe_sort_backend_dispatch_env_matrix_mxfp4
```
