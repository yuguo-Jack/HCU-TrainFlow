# fix(attention): fix high head dim model(Gemma4) support on limited shared memory

[Upstream PR](https://github.com/vllm-project/vllm/pull/39018) · state: open · merged: False

## Original PR description

## Purpose

Fix Triton and Flex attention kernel crashes on Turing GPUs (SM 7.5, e.g. RTX 2080 Ti) when running models with large `head_dim` (≥ 512), such as Gemma4's global attention layers (`global_head_dim: 512`).

**Root cause:** Both `TRITON_ATTN` and `FLEX_ATTENTION` backends launch kernels requiring ~96KB shared memory (`TILE_SIZE=32` / `BLOCK_M=BLOCK_N=32/64` with `HEAD_SIZE_PADDED=512`), but Turing's hardware limit is 64KB per SM block. This causes `triton.runtime.errors.OutOfResources` on the first request (TRITON_ATTN) or during warmup (FLEX_ATTENTION).

**Fix:** Dynamically reduce tile/block sizes from 32 to 16 when `head_dim >= 512` and the GPU's max shared memory per block is < 96KB (98,304 bytes). This brings shared memory usage to ~48KB, well within Turing's 64KB limit.

Changes:
- `triton_unified_attention.py`: Add hardware-aware safety check in `_get_tile_size()` to reduce `TILE_SIZE` 32→16 with an info-level log message
- `flex_attention.py`: Add early cap of `BLOCK_M`/`BLOCK_N` to 16 for large `head_dim` on shared-memory-constrained GPUs in `get_kernel_options()`
- Align shared memory threshold (`< 98304`) consistently across both backends

**No impact on modern GPUs:** Ampere+ GPUs have ≥163KB opt-in shared memory, so the new conditions never trigger.

Fixes issue #38918 

## Test Plan

## Code Review

This pull request introduces hardware-aware safety checks for large head dimensions (>= 512) on GPUs with limited shared memory (less than 96KB). Specifically, it reduces block sizes in the flex attention backend and tile sizes in the unified attention ops to prevent shared memory exhaustion. A review comment suggests that the INFO level logging added to _get_tile_size could lead to significant log spam during inference and should be moved or downgraded.
