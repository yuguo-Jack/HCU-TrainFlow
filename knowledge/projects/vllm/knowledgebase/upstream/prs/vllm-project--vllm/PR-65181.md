# [Bugfix][Quantization] Respect non-gated shard count in FP4 Marlin

[Upstream PR](https://github.com/vllm-project/vllm/pull/65181) · state: open · merged: False

## Original PR description

## Overview

Nemotron's `RELU2_NO_MUL` MoE has one `w13` projection, but FP4 Marlin preparation assumes two and aborts during checkpoint loading. This change sizes both Marlin preparation paths from `moe_config.w13_num_shards`.

Related: [#51125](https://github.com/vllm-project/vllm/pull/51125) added the shard-count property and fixed allocation/iteration sites, but did not change `marlin_utils_fp4.py`; this PR covers that separate conversion path. No open PR for this helper was found.

## Claims

- Non-gated MoE layers use one `w13` shard during weight and scale repacking; gated layers retain two.
- The regression test covers both the in-place FP4 helper used by compressed-tensors and the pure MXFP4 conversion helper.

## Validation

- The new CUDA regression test fails before the change at the `weight.shape` assertion and passes after it (`1 passed` on H100).
- Reproduced the user's local Nemotron MXFP4A16 checkpoint on vLLM `0.33.0rc1.dev277+g4440f0e26` with the patched helper: server startup completed and a 3-token completion returned HTTP 200. No evaluation dataset run was performed.
- `pre-commit run ruff-format --files tests/quantization/test_compressed_tensors.py vllm/model_executor/layers/quantization/utils/marlin_utils_fp4.py` passed.
- `pre-commit run ruff-check --files tests/quantization/test_compressed_tensors.py vllm/model_executor/layers/quantization/utils/marlin_utils_fp4.py` passed.

## Details

The failing layer reported `activation=RELU2_NO_MUL`, `w13_num_shards=1`, and `w13_weight.shape=(128, 1856, 1344)`. `prepare_moe_fp4_layer_for_marlin` instead expected `(128, 3712, 1344)` by unconditionally using `2 * intermediate_size_per_partition`; it failed before inference. The pure MXFP4 helper also derived its intermediate size assuming two shards, which made its `w2` dimensions inconsistent for a non-gated layer. Both paths now use the actual shard count.

This reproduction is MXFP4A16 (`input_activations` is null) and exercises the H100 Marlin weight-only path. The fix addresses the startup failure in that path; it does not add MXFP4A8 support. The source helper already contained the two-shard assumption in the older vLLM revision, so these results do not establish that v0.33 alone introduced it or that the older successful run exercised the same configuration.
