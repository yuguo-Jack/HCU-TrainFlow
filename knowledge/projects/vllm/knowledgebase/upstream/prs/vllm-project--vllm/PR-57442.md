# [Frontend][Core] Sampled-token logprob fast path for /inference/v1/generate (return_token_logprobs)

[Upstream PR](https://github.com/vllm-project/vllm/pull/57442) · state: open · merged: False

## Original PR description

## Purpose

> **Update (2026-10-07):** rebased on main after #58181. The flat list is now `logprobs.sampled` on `GenerateLogProbs`, the shape agreed in #57574 (`content=None` and no `content[i]` entries in the sampled-only mode), instead of a separate `choices[].token_logprobs` field; it is tokens-mode only, and NaN is clamped to `-9999.0`. The transport and output-processor path measured below are unchanged. The live-server tests in `test_serving_tokens.py` are updated for the new shape but have not been rerun on a GPU since this change; the unit tests and the Rust crates pass locally.

RL rollout collectors using `/inference/v1/generate` need one float per generated token: the sampled token's logprob. Today that means requesting `logprobs=0` and reading `choices[].logprobs.content[i].logprob`. On the server, that one float travels a path built for top-k logprob objects: the scheduler slices a `LogprobsLists` (token ids, logprobs, ranks — three numpy arrays) per request per step, encodes it into `EngineCoreOutput`, the output processor `.tolist()`s it, detokenizes every entry and appends `Logprob` objects (or `FlatLogprobs`), and the frontend builds a `ChatCompletionLogProbsContent` Pydantic object per token before JSON.

Measured on one L20 with an 8-core host (Qwen2.5-0.5B-Instruct, 256-token rollouts with `ignore_eos`, prompts = 2 × concurrency, `temperature=1, top_k=50, top_p=0.95`), `logprobs=0` takes throughput to **0.67–0.73× of no-logprobs** at concurrency 64–512. Where the cost sits, established by switching layers off one at a time (raw runs linked below): the GPU kernels are not it (skipping `_ranks_kernel` is within noise; skipping every logprob kernel is worth ≤5 points); the D2H copy and `tolists()` are free; the per-request `LogprobsLists` slicing → IPC → output-processor → Pydantic path is the whole cost (skipping the slicing alone restores 1.00× at c256).

This PR adds a sampled-token logprob fast path, end to end:

- `GenerateRequest.return_token_logprobs` (request field) and an internal `SamplingParams.sampled_logprobs_only` (requires `logprobs == 0`).
- The scheduler emits `EngineCoreOutput.new_sampled_logprobs`: one float per new token, read from column 0 of the step's logprobs array (the sampler stores the sampled token first), through the `cu_num_generated_tokens` boundaries. No `LogprobsLists` for these requests.
- The output processor keeps a plain float list and the cumulative logprob; it never builds `Logprob` entries and never detokenizes.
- The response carries `choices[].logprobs.sampled: list[float]` (`GenerateLogProbs.sampled`), clamped like `content` (`-inf` and NaN become `-9999.0`). With `logprobs=0` that is all it carries: `content` is `null` and no per-token entries are built. With `logprobs > 0` `content` is returned alongside (the sampled column then comes from the existing flat representation). `sampled` is omitted from responses that did not ask for it, so the existing schema is unchanged.
- `output_mode="tokens"` only (400 otherwise): text mode returns `ChatCompletionLogProbs`, which has no `sampled`.
- Requires `--logprobs-mode raw_logprobs` or `processed_logprobs` (400 otherwise): the field is named for log-probabilities and does not hand back logits under that name. `stream=True` is rejected with a 400 (the per-chunk shape is a separate decision).
- The Rust frontend rejects the field with an explicit `invalid_request_error` instead of ignoring it (its `GenerateRequest` flattens unknown fields); the Rust engine-core client mirrors the new last-appended `EngineCoreOutput` field. `cargo check -p vllm-server --tests` and `cargo test -p vllm-engine-core-client --lib engine_core_output` pass.

It composes with `--return-sampling-mask` (#54901): the rollout contract "mask + sampled-token logprob" is then one ragged list and one flat list per request.

## Test Plan

- `tests/entrypoints/scale_out/token_in_token_out/test_serving_tokens.py -k "return_token_logprobs or sampled_token_logprobs or omits_sampled"` (live server, plus two unit tests for the clamp): flat array equals the object path's per-token `logprob` (greedy; and under n-gram speculative decoding, where steps produce a ragged number of tokens per request, on a `VLLM_BATCH_INVARIANT=1` server — without batch-invariant execution the object path was not a stable numerical oracle in that configuration: repeated object-path requests returned identical tokens but sampled logprobs differing by up to ~2e-2, while under batch-invariant execution object and sampled-only paths match exactly across fresh server lifetimes); `logprobs` unset defaults to 0; `logprobs=2` returns both representations with matching values; `n=2` / `n=4` return one aligned array per choice; `-inf`/extreme values clamp like the object path; `stream=True` → 400; `output_mode="text"` → 400; `sampled` absent unless requested.
- `tests/v1/test_outputs.py`: column-0 selection with and without `cu_num_generated_tokens`, including the ragged `[0, 3, 4, 6]` case; `tests/v1/engine/test_logprobs_processor.py`: float-list accumulation and cumulative logprob, `SamplingParams` validation.
- Exactness under sampling: one server with `VLLM_BATCH_INVARIANT=1` and `--return-sampling-mask`, 16 seeded prompts × 64 tokens, each sent once as `logprobs=0` (objects) and once with the field: token sequences identical 16/16, array length equals generated length 16/16, max abs difference 0.0.
- Serving A/B: one `vllm serve` per condition, 3 interleaved rounds, per-round API-server and EngineCore CPU from `/proc`.

## Test Result

vLLM 0.29.0 + #54901 backported, one L20, driver 580.159.04, `/inference/v1/generate`, non-streaming. "vs gen" is relative to the same server with no logprobs requested.

| Model | Concurrency | no logprobs | `logprobs=0` objects | `return_token_logprobs` |
| --- | ---: | ---: | ---: | ---: |
| Qwen2.5-0.5B | 64 | 18,592 tok/s | 13,495 (0.73×) | **17,868 (0.96×)** |
| Qwen2.5-0.5B | 256 | 23,038 | 15,451 (0.67×) | **21,846 (0.95×)** |
| Qwen2.5-0.5B, `--return-sampling-mask` | 64 | 16,452 | 11,106 | **15,453 (0.94×)** |
| Qwen2.5-0.5B, `--return-sampling-mask` | 256 | 20,313 | 13,088 | **19,132 (0.94×)** |
| Qwen3-4B | 64 | 3,524 | 3,351 (0.95×) | **3,503 (0.99×)** |
| Qwen3-4B, `--return-sampling-mask` | 64 | 3,442 | 3,320 | **3,443 (1.00×)** |

On the 0.5B model the field recovers ~84–86% of the throughput that `logprobs=0` costs; response size per request goes from ~41 KB to ~6.8 KB; API-server CPU with logprobs returns to the no-logprobs level (0.39 vs 0.37 of a core at c256) and the EngineCore is at parity. On the GPU-bound 4B model the sampled-token logprob becomes essentially free.

Raw runs, the layer-by-layer decomposition, and the exactness check: <https://github.com/yinli-systems/single-gpu-inference-lab/tree/stage2-compact-sampling-mask/benchmarks/results/l20-flat-token-logprobs> and `.../l20-logprob-engine-decomposition`.

Related: #42259 (logprobs semantics RFC), #54901 (compact sampling masks), #48314 (RL roadmap: RL artifacts data plane). #42283 (FlatLogprobs tail slices) is orthogonal. The AuxOutput connector work (#45635) targets persistence/prefix reuse/external transfer of auxiliary outputs; this change stays on the request-local serving path and does not add a new artifact plane.
