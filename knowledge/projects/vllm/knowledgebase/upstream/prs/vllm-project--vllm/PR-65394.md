# [Bugfix][Quantization] Honor the activation scheme in MXFP8 linear kernel selection

[Upstream PR](https://github.com/vllm-project/vllm/pull/65394) · state: open · merged: False

## Original PR description

## Summary

`init_mxfp8_linear_kernel` dropped the activation quant key, so a weight-only
(W8A16) MXFP8 checkpoint could select a kernel that quantizes activations to FP8
(the FlashInfer W8A8 kernels on SM100), silently clipping BF16 activations to
E4M3 with no warning. The sibling MXFP4/MXFP6 selectors already thread the
activation key and gate on it; MXFP8 did not.

This threads an optional `activation_quant_key` through `init_mxfp8_linear_kernel`
and adds a permissive `_supports_quant_scheme` classmethod on the kernel base.
The self-quantizing kernels (FlashInfer CUTLASS/CuTe-DSL, ROCm dot-scaled, and
torch-native on CUDA) override it to decline a weight-only request, so it falls
through to the W8A16 Marlin kernel. The parameter defaults to a sentinel, so
callers that do not declare a scheme keep the historical selection (no gating);
only the Quark OCP-MX caller is migrated here. compressed-tensors/modelopt (both
W8A8) and the online path can follow up, and this aligns with #59460's
`executed_activation_key()` direction.

Fixes #65193

## Testing

`pytest tests/kernels/quantization/test_mxfp8_kernel_selection.py` — 45 passed
(CPU-only). Added cases: a weight-only request on SM100/103 now selects
`MarlinMxfp8LinearKernel`; an explicit W8A8 (`kMxfp8Dynamic`) request still
selects the FlashInfer kernel; an unspecified request keeps the historical
selection. Verified the new weight-only test fails without the gate (selects the
W8A8 FlashInfer kernel) and passes with it. `pre-commit` clean (ruff, ruff-format,
mypy).

## Duplicate check

`gh pr list --state open --search "activation ... mxfp8"` and the issue tracker:
no open PR fixes the MXFP8 **linear** selector. #63378 (MoE MXFP8 input-quant)
and #59460 (global strict-scheme flag) are complementary, not duplicates.
