# [Bugfix] Free cuMem allocations with the aligned size in my_free

[Upstream PR](https://github.com/vllm-project/vllm/pull/61935) · state: open · merged: False

## Original PR description

## Overview

`my_free` in the cuMem allocator unmapped and freed with the byte count PyTorch requested instead of the granularity-aligned size `my_malloc` actually reserved and mapped. Part of #36651 (item 4, listed as not covered by any PR in https://github.com/vllm-project/vllm/issues/36651#issuecomment-5892039123). Independent of #60081 and #59228, which touch other lines of the same file.

## Claims

- `my_free` now passes `recv_size` (the aligned size recorded at `my_malloc`) to `unmap_and_release` and `cuMemAddressFree` on both the CUDA and ROCm paths.
- An unaligned free no longer returns `CUDA_ERROR_INVALID_VALUE`, so the physical handle and the address range are released instead of leaked, and the sticky `error_code` no longer makes the next `my_malloc` return null.
- New regression test `test_free_with_unaligned_size` fails on `main` and passes with this change; the existing cumem tests still pass.

## Validation

Hardware: 1x H100 80GB HBM3, driver 580.126.16, CUDA 13.0, allocation granularity 2 MiB. The extension was built from `main` and from this branch and swapped into an installed vLLM.

**1. Direct calls through the extension ABI** (same signature PyTorch's pluggable allocator uses):

| request | aligned by `my_malloc` | `main`: free with request size | this PR: free with request size |
|---|---|---|---|
| 1 B | 2 MiB | `invalid argument` at `cuMemUnmap` and `cuMemAddressFree`, 2 MiB leaked, `error_code=1` | clean, 0 leaked, `error_code=0` |
| 3 MiB + 1 | 4 MiB | same, 4 MiB leaked | clean |
| 2 MiB | 2 MiB | clean | clean |

After the leaking free on `main`, the next `my_malloc` returns null because `error_code` is still set.

**2. End to end through PyTorch**, with the extension installed as the process-wide allocator via `torch.cuda.memory.change_current_allocator` (no caching-allocator rounding, so every tensor's exact byte count reaches `my_malloc`/`my_free`):

| build | 50x `torch.empty(1000, uint8)` alloc + free |
|---|---|
| `main` | first free leaks 2 MiB with two driver errors; second allocation returns a null pointer |
| this PR | 0 MiB leaked, `error_code=0`, a follow-up 64 MiB allocation succeeds |

**3. Regression test**

```
pytest -s tests/basic_correctness/memory/cumem/test_cumem.py -k "unaligned or python_error or basic_cumem"
main:     1 failed (test_free_with_unaligned_size: "driver rejected the unmap or address free"), 2 passed
this PR:  3 passed
```

The test runs in the existing `basic-correctness-cumem` Buildkite step. It asserts on the extension's exported `error_code` rather than on `cudaMemGetInfo`, which the file's own helper notes is device-wide and noisy.

<summary>Reproducer for table 1</summary>

```python
import ctypes, torch
import vllm.device_allocator.cumem as cumem
from vllm.device_allocator.cumem import CuMemAllocator

alloc = CuMemAllocator.get_instance()
with alloc.use_memory_pool():
    torch.empty(1, device="cuda")  # registers the Python callbacks
lib = ctypes.CDLL(cumem.lib_name)
lib.my_malloc.restype = ctypes.c_void_p
lib.my_malloc.argtypes = [ctypes.c_ssize_t, ctypes.c_int, ctypes.c_void_p]
lib.my_free.argtypes = [ctypes.c_void_p, ctypes.c_ssize_t, ctypes.c_int, ctypes.c_void_p]
err = ctypes.c_int.in_dll(lib, "error_code")

for size in (1, 3 * 2**20 + 1, 2 * 2**20):
    torch.cuda.synchronize(); base = torch.cuda.mem_get_info()[0]
    p = lib.my_malloc(size, 0, None)
    aligned = alloc.pointer_to_data[p].handle[1]
    err.value = 0
    lib.my_free(p, size, 0, None)          # what PyTorch passes
    torch.cuda.synchronize()
    print(size, aligned, "error_code", err.value, "leaked", base - torch.cuda.mem_get_info()[0])
    err.value = 0
```

## Details

Root cause. `my_free(ptr, size, ...)` receives `size` from PyTorch, which is the byte count given to `my_malloc` (`CUDAPluggableAllocator` stores it per allocation and hands it back on free). `my_malloc` rounds that up to `cuMemGetAllocationGranularity` before `cuMemAddressReserve`/`cuMemCreate`/`cuMemMap`, and the Python callback records the rounded value, which `my_free` reads back as `recv_size`. `cuMemUnmap` and `cuMemAddressFree` require the size used at map/reserve time; with an unaligned `size` the driver returns `CUDA_ERROR_INVALID_VALUE`, `CUDA_CHECK` records it and `unmap_and_release` returns before `cuMemRelease`, so the handle and the VA range leak. Because `error_code` is a file-scope global, the next `my_malloc` sees it and returns null.

Scope. Through vLLM's normal `use_memory_pool` path this does not trigger on H100: the caching allocator hands `my_malloc` segments that are already 2 MiB multiples, and the H100 granularity is also 2 MiB. Those two constants live in PyTorch and in the driver respectively; the bug surfaces as soon as they differ (a larger granularity, or any caller that bypasses the caching allocator, as in validation table 2).

On ROCm, `unmap_and_release` already ignores `size` and walks the per-chunk sizes; only `cuMemAddressFree` was affected there, same one-line change.
