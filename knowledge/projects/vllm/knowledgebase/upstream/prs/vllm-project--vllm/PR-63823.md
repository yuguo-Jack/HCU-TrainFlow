# [MRV2][DBO] Replay FULL microbatch graphs when a microbatch is all padding

[Upstream PR](https://github.com/vllm-project/vllm/pull/63823) · state: open · merged: False

## Original PR description



## Overview

Keep MRV2 DBO on its FULL microbatched CUDA graph when a DP rank's real decode tokens don't reach every captured microbatch region. An alternative to #63556 (row staging) and #57020 (eager fallback at the boundary).

**Draft: not yet validated end to end** (see Validation).

## Claims

- Under FULL, each microbatch keeps the request rows its graph region was captured with. A region with no real tokens replays as ordinary graph padding: query length 0, seq_len 0, slot −1.
- DP no longer drops to eager microbatching when one rank's last microbatch is empty. For example, loads 63/97 at bucket 128 replay FULL on both ranks.
- No rows are reordered, so there is no output gather or input restore. The production diff is +32/−6, confined to `gpu/ubatch_utils.py` and `gpu/dp_utils.py`.

## Details

**Root cause.** `create_ubatch_slices` clamps a trailing all-padding microbatch's request slice onto the last real request, which keeps eager metadata non-degenerate. Under FULL, that gives the region more request rows than it was captured with: 66 instead of 64 for 63 real tokens at bucket 128. Every row is then offset by two requests. A partially filled non-last region (k > 2, or region 0 when real tokens < split) is similarly short. The DP gate in `sync_cudagraph_and_dp_padding` avoided this by forcing eager. #57020 tightens that gate's boundary.

**Change.** FULL microbatch graphs only exist for uniform decodes (`_maybe_ubatch_twin`). Under FULL, the request slice for every region is `token_slice // tokens_per_req`, which is exactly the capture layout, and the eager gate is removed. Padding requests already carry query length 0 and seq_len 0 from `prepare_inputs`, the same as padding rows in a normal FULL graph. The only new case is a region with *no* real rows. For that region, `_slice_input_batch` sets `max_query_len` to the captured uniform length, so `prepare_attn` does not call `.max()` on an empty array. Eager and PIECEWISE microbatching are unchanged.

**Compared with #63556.** Replay cost is fixed by the captured shape, so spreading real rows across regions does not reduce graph work. This change gets the same FULL-instead-of-eager benefit without staging, restoration or a capability vote. Under EP, the light rank's padding region still runs expert work for tokens routed from other ranks, so the DBO overlap structure is preserved.

**Risks / reviewer attention.**
- Every attention backend used with FULL microbatched graphs must tolerate a region whose rows all have seq_len 0, with `max_seq_len` 0 at build time. For FA3 (`FLASH_ATTN_MLA`), `get_scheduler_metadata` gives `num_n_blocks = 0` and so 1 split, and zero query lengths should schedule no tiles; that comes from reading the source, not from testing it. FlashMLA, FlashInfer MLA, CUTLASS MLA and Triton MLA are unverified.
- Assumes split points are multiples of the uniform query length (asserted). DBO currently excludes speculative decoding, so this is 1 in practice.

Your approach matches my initial idea: **the simplest and most direct solution is to let an empty microbatch run entirely as padding, keeping the captured layout and FULL CUDA Graph replay.** For context, my original staging prototype is [#57184](https://github.com/vllm-project/vllm/pull/57184).

I initially chose staging because I was unsure whether padding-related metadata, KV updates, EP participation, and post-forward bookkeeping stayed consistent when a microbatch became entirely padding. Reading your code now, I see several existing protections:

- **Stale metadata after active → padding transitions:** the [FA3 MLA builder](https://github.com/LucasWilkinson/vllm/blob/77d369994150a28054c50e7b6ee1fdbd59ea0bf0/vllm/v1/attention/backends/mla/flashattn_mla.py#L250-L263) copies the new scheduler metadata and explicitly clears the unused tail. This appears to address my original stale-tail concern.
- **Padding slots accidentally writing KV:** the [MLA KV-update kernel](https://github.com/LucasWilkinson/vllm/blob/77d369994150a28054c50e7b6ee1fdbd59ea0bf0/csrc/cache_kernels.cu#L529-L550) immediately returns for negative slots, protecting this kernel's `slot_mapping=-1` path.
- **Unwritten padding outputs reaching real tokens:** padding outputs need not be zero if they remain isolated. The default [fused top-k path](https://github.com/LucasWilkinson/vllm/blob/77d369994150a28054c50e7b6ee1fdbd59ea0bf0/csrc/moe/topk_softmax_kernels.cu#L550-L565) assigns padding expert IDs of `-1`; the relevant end-to-end check is that the mask reaches the actual routing path.
- **A locally empty microbatch skipping necessary EP work:** it can still receive real expert inputs from other ranks. Your [forward contexts](https://github.com/LucasWilkinson/vllm/blob/77d369994150a28054c50e7b6ee1fdbd59ea0bf0/vllm/v1/worker/gpu/ubatch_utils.py#L425-L455) use padded slice capacity for DP metadata, and I do not see this change introducing a local-empty shortcut that skips EP.

**Avoiding reordering is a real advantage of your approach.** My early staging implementation introduced genuine sampling-position and returned-route bugs because restoring model outputs alone did not restore everything their consumers read. <summary>Additional context from my staging experiments</summary>

**Sampling positions and returned routes.** Staging rewrote input IDs and positions in place. I restored outputs but initially left the sampler reading staged input buffers through the original logical `logits_indices`. With 63 tokens distributed as 32+31 in a 128-row graph, some logical rows pointed into padding: one recorded position was 146 but the sampler read 0. With the same logits, seed and sampling settings, correcting the logical inputs changed sampled tokens. DP2/DP4 shadow observations recorded 21/19 differences; repeating the original inputs produced zero. The position-dependent `min_tokens` mask was also affected.

Routing needed two separate fixes: restoring logical slot order (one 63-token observation had 31 slots of `-1` in the logical prefix), and using physical microbatch offsets so DBO capture callbacks did not overwrite the same buffer prefix. I restored inputs/positions/slots before post-forward consumers and restored route order after offset-aware writes. A later campaign completed 5,124 requests with the recorded sampling/routing checks passing; this was not an independent oracle for every returned token. The independent capture-offset fix is already in your base through `dbo_current_ubatch_token_offset()`.

**NIXL with `k>2`.** In my later extension, the installed low-latency implementation reused two receive buffers. Extending the handles array alone did not preserve activations, expert counts, optional scales and combine-handle tensors until use. Aliased-snapshot negative controls detected corruption for `k=3/4/8`, while `k=2` was unaffected; FP8 coverage used mock tuples. This is outside your current two-microbatch change, and staging itself did not solve ownership either.

**BF16 and layout effects.** Earlier DeepSeek BF16 tests showed compact-versus-fixed-layout differences even in the unmodified baseline, while same-layout FULL/eager matched. Computing all 26 shared-expert down projections in FP32 before capture removed the observed differences in those campaigns. This supported a shape-dependent numerical contribution in those samples, not a BF16 kernel bug or qualification of the original BF16 path.

**DBO performance.** Early comparisons were eager fallback versus staging + FULL. These are historical figures from archived reports, not new GPU runs or independently reprocessed raw data for this comment. They are neither a padding-only-versus-staging comparison nor measurements of your current head. They motivate separating replay correctness, layout-dependent numerical effects and matched performance comparisons.
