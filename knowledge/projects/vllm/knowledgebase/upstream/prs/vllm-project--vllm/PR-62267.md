# [Doc][RL] Document the weight-transfer HTTP protocol for trainers without vLLM

[Upstream PR](https://github.com/vllm-project/vllm/pull/62267) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

Documents the HTTP wire protocol for the `nccl` and `ipc` weight-transfer backends, for a trainer that does **not** import vLLM. The contract goes into the existing NCCL and IPC engine pages, and the PR adds two minimal reference trainers. Until now the contract was only described by the code in `nccl_common.py`, `ipc_engine.py`, `packed_tensor.py`, and `clients.py`.

## Claims

- `docs/training/weight_transfer/nccl.md`: new section **"Trainer Without vLLM over HTTP"** covering:
  - `init_info` fields, including `nccl_unique_id_b64`
  - the worker rank formula
  - the one-element fp32 warm-up `all_reduce`
  - `update_info` (`names` / `dtype_names` / `shapes`)
  - broadcast order, which runs concurrently with `/update_weights`
  - packed chunking: a chunk closes *after* it overflows
  - torch-only communicator options, with the caveat that reading store key `"0"` relies on torch internals
  - init has no timeout
- `docs/training/weight_transfer/ipc.md`: same section for IPC, covering:
  - the `ipc_handles_pickled` format
  - the GPU UUID key, which has no `GPU-` prefix
  - `VLLM_ALLOW_INSECURE_SERIALIZATION=1` on the server
  - `tensor_sizes`
  - packed chunking: a chunk closes *before* it overflows
  - keeping tensors alive until finish, then `ipc_collect`
  - multi-rank handle gathering to rank 0
- `docs/training/weight_transfer/README.md`:
  - the endpoint table gains the missing `/shutdown_weight_transfer_engine` row
  - a short paragraph says a trainer may implement the protocol directly and links both sections. The motivation: the trainer stays decoupled from vLLM, with no vLLM install or version pin, so trainer and server can upgrade independently, and non-PyTorch trainers such as JAX can use it
  - the shared failed-update caveat is stated once
- `examples/rl/rlhf_http_nccl_no_vllm.py` and `examples/rl/rlhf_http_ipc_no_vllm.py`:
  - import only `torch`, `requests`, `safetensors`, `pybase64` and the stdlib
  - a `sys.meta_path` blocker makes any `vllm` import fail
  - print generations before and after the sync
- `tools/pre_commit/check_forbidden_imports.py`: one-line `pickle` allowlist entry for the IPC example, because pickle is the only HTTP encoding for IPC handles.

## Validation

Ran the example trainers from this branch on GB200 (aarch64) with image `vllm/vllm-openai:cu134-nightly-aarch64-dev-20261016-49cb2bb`. That image is within a few commits of `main`, with no differences in the dense nccl/ipc paths or the routes. Model: Qwen3-0.6B.

Each server started with `--load-format dummy`. After each sync, `/weight_checker compare` checked the weights against checksums from a server cold-loaded with the same checkpoint at the same TP. `/weight_checker reset` zeroed the weights between runs.

- Every trainer exited 0, and `vllm` never appeared in its loaded modules.
- Before each sync, generation was gibberish (dummy weights) or `!!!!` (zeroed weights).
- The NCCL runs also exercise `/shutdown_weight_transfer_engine`, then re-init on a fresh unique id.
- The documented fields were checked against current `main` source.
- The torch-communicator table and the failed-update caveat come from an earlier verification on `ac9126e58`:
  - `torch.cuda.nccl.init_rank` fails with `PY_SSIZE_T_CLEAN`
  - ctypes against torch's bundled `libnccl` works
  - a failed `/update_weights` leaves the model mid-reload
- Since that GPU run, the examples changed only in docstrings, so they were not re-run.

## Details

- **No duplicate:** `gh pr list --search` for "weight transfer http", "nccl_unique_id_b64", "JAX trainer", and "[Doc] weight transfer" finds no open PR documenting this contract.
- **#57854** (failed-update handling) may change the README caveat. If it merges first, that line should be updated.
- **No server spawn:** the examples assume an already running server instead of starting `vllm serve`, because a trainer without vLLM usually runs in a different environment from the server.
- **Torch internal:** the NCCL example gets the unique id from `ProcessGroupNCCL.eager_connect_single_device` through store key `"0"`. The doc and the example both label this as a torch implementation detail, and the ctypes route is listed as an alternative.
- **Not in Buildkite:** the examples need a separately launched server and a local checkpoint. The existing `rlhf_http_{nccl,ipc}.py` CI steps already exercise the same server-side paths.
