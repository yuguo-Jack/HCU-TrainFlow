# [Feature][KV Offload] Add mamba_aware_lru CPU-tier eviction policy for hybrid models

[Upstream PR](https://github.com/vllm-project/vllm/pull/63578) · state: open · merged: False

## Original PR description

## Overview

Adds `mamba_aware_lru`, an opt-in eviction policy for the CPU offload tier of hybrid models (attention plus Mamba or other state-space layers). Under `lru`, a turn that loads a Mamba state from the tier also refreshes that state's rank, so states that the session's later turns no longer need outlive the cached context of idle sessions. `mamba_aware_lru` evicts those states first. On an AgentX replay (agentic coding traces) with Nemotron 3.5 Super, it cut recomputed prompt tokens per request by 18% and raised throughput by 3–6% over `lru`.

#63808 applies the same rule to the GPU prefix cache, for serving without a CPU tier or with one smaller than the GPU cache. Related work, none of which changes how the CPU tier orders Mamba states: #50422 (session-aware eviction, model-agnostic), and #61282 and #50551 (keep more Mamba states in the GPU prefix cache).

## Claims

- New built-in `"eviction_policy": "mamba_aware_lru"` for `CPUOffloadingSpec` and `TieringOffloadingSpec`. The default stays `lru`.
- When a request finishes, each Mamba state it superseded moves to the eviction end (it is demoted). A state is superseded when an earlier request stored it as its deepest state (its tip), and this request's prefix passes it and holds a deeper cached state. Attention chunks, the deepest state, and states stored below their writer's tip, such as shared-prefix junctions (where prompts that share a prefix diverge), keep their LRU order. On models without Mamba groups, the policy evicts exactly like `lru`.
- Outputs do not change: the policy only reorders evictions, and the load and store paths are untouched.
- Eviction policies get two optional inputs. The manager passes a `mamba_group_ids` constructor argument only to a policy whose constructor declares it, so out-of-tree policies keep working. `ReqContext.get_offload_key_positions()` returns the end-token position of every chunk key of the request, which the scheduler already records.
- On an AgentX replay before the rebase onto #61050 (GB200, 64 sessions per server, two runs per policy), compared with `lru`: 18% fewer recomputed prompt tokens per request, 3.3% and 5.9% more requests per hour, and 7–8% more output tokens/s.

## Details

### Motivation: a worked example

A session on a hybrid model whose prompts grow from 3 to 5 blocks:

1. Turn 1 offloads attention chunks A1–A3 and its Mamba state S3. S3 is the request's tip.
2. Turn 2 loads A1–A3 and S3 from the CPU tier, computes blocks 4–5, and offloads A4, A5 and S5.
3. S3 now helps only requests that branch off this session between S3 and S5, such as a regenerated turn 1 or a sub-task forked after turn 1. Every later turn resumes at block 5 or deeper.

When turn 2 finishes, LRU ranks its keys tail-first, so the CPU tier evicts them in this order:

| Policy | Eviction order (first → last) |
|---|---|
| `lru` | A5, S5, A4, A3, S3, A2, A1 |
| `mamba_aware_lru` | **S3**, A5, S5, A4, A3, A2, A1 |

Under `lru`, S3 counts as just used. With many concurrent sessions, such superseded states pile up in the tier, and the live context of idle sessions is evicted instead: in the AgentX run above, `lru` evicted about 1,200 attention chunks while it kept superseded states.

### Design

- **Rule.** In `on_request_finished`, the policy reads the request's chain: every chunk key of its prefix with its token position, as the scheduler records them. This also covers prefixes served by the GPU prefix cache.
  - The deepest Mamba states the request stored become tips.
  - Each cached tip below the deepest cached state on the chain moves to the eviction end. Demoted chunks are evicted before every LRU-ranked chunk, oldest demotion first.
- **Never demoted:** attention chunks; the deepest state on the chain; and states that their writer stored below its own tip, such as shared-prefix junctions.
- **Reuse.** LRU's request-scoped recency update gives any reused chunk a fresh rank. If the request that reloads a demoted tip then stores a deeper state on the same chain, the tip is demoted again when that request finishes.
- **Partial tails.** With a prefix match unit below the chunk size, boundary keys carry their token positions, so a sub-chunk tip is a tip like any other.
- **Cost.** One pass over the request's chain keys per finished request, for hybrid models only, which adds about one LRU recency update. Measured on an M-series laptop: +10 µs at 32 chunks × 6 groups, +54 µs at 256, +0.44 ms at 2,048. Hybrid models use large blocks, so chains are short. It all runs in the scheduler, with no GPU work and no synchronization.

### Tradeoffs and limitations

- **Branching from older turns.** Workloads that resume from older states, such as regenerate, rewind or tree search, lose them sooner than under `lru`. A reload restores a state's rank, but only if the state is still cached.
- **Fallback under heavy pressure.** LRU's tail-first order evicts a request's newest tip right after any demoted state. Under `lru`, an older tip could then still serve as a fallback; under `mamba_aware_lru` it is gone. A possible follow-up is to rank a request's deepest tip with the head of its prefix instead of its tail.
- **States below a writer's tip are kept.** This covers chunked-prefill boundaries and, with a prefix match unit below the block size, the full-chunk state below a sub-chunk tip. They keep their LRU rank even when nothing will resume there. Telling them apart from real branch points needs more than the chain's positions.
- **Orphaned partial attention chunks.** A sub-chunk attention chunk whose Mamba states were evicted can no longer be hit, but it keeps its LRU order.
- **Failed tip store.** If a request's new tip fails to store after the request finishes, the older tip was already demoted. Only eviction order is affected.
- **Coupling.** The policy subclasses `LRUCachePolicy` and edits its ranks and lazy heap directly, so a change to LRU's rank layout must update it too. Both live in `vllm/v1/kv_offload/cpu/policies/`.
- **Not caused by this PR:** a promotion started by `TieringOffloadingManager.lookup()` can evict a chunk the same request matched moments earlier. #63551 (scheduler path) and #62615 (P2P path) fix this. The policy only changes which chunk such a promotion evicts.

- #63808 (ours) applies the same rule to the GPU prefix cache, which has its own free queue.
- #50422 (SAE) groups each request's chunks into a session and evicts session-worst-first. It is model-agnostic and changes the `CachePolicy` and manager APIs, and reviewers asked for less pervasive hooks. This PR uses the existing request-finish hook and adds one optional constructor argument.
- #61282 and #50551 change the GPU prefix cache (`vllm/v1/core`) and do not touch CPU-tier eviction. #64975 (draft) also demotes superseded Mamba states, in the GPU prefix cache only.
- #64213 adds `CachePolicy.demote()` and implements it in `lru`. `mamba_aware_lru` would inherit it, and superseded states would still go before the chunks it demotes. Whichever lands second can move both onto `demote()`.
- #57813 (draft) adds an optional third `evict()` argument and a manager parameter. It is orthogonal, but whichever lands second needs a small rebase; with #57813, `MambaAwareLRUCachePolicy.evict` would take the new argument.
