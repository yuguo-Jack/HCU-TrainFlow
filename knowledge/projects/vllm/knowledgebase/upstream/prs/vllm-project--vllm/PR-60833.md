# [ROCm][Perf][Qwen3.8] Mono decode layer for Qwen3.8 on MI355X

## Overview

**Draft, stacked on #60683.** Until #60683 merges, the compare view also shows #60683's two commits (`e2e886c372`, `1fc98fba1b`); this PR is the commits after them.

This PR ports the Kimi-K3 mono decode (#60683, @hyukjlee) to Qwen3.8 (`Qwen3_5MoeForCausalLM`, `amd/Qwen3.8-2.4T-A95B-Quark-MXFP4`) at TP8 on MI355X (gfx950). It is opt-in behind the existing `VLLM_ROCM_MONO_DECODE=1`. On pure decode steps of up to 8 rows without spec decode, each decoder layer runs as at most two persistent launches instead of the stock chain of GEMMs, norms, all-reduces and MoE kernels. It reuses #60683's mono framework (`vllm/models/kimi_k3/amd/mono/common`): mailboxes, the peer buffer and the GEMV stage.

Not a duplicate: I searched open PRs for "mono decode", "mono decode Qwen" and "Qwen3.8 mono". #60683 (Kimi-K3) and #60397 (DeepSeek-V4.1-Flash) are the same technique for other models; neither covers GDN layers or softmax top-10 routing.

## Claims

Measured on `nightly-8cbd5d03`; TPOT, NIAH and the model-card GSM8K at `3346929b27`; GSM8K lm_eval and GPQA at `6a1c13b2fc`. The two revisions compute the same outputs bit for bit: the one path that changed (x quantized once by the norm CTAs at 6–8 rows) was asserted bitwise equal to the path kept.

- Mean TPOT −48.2% at concurrency 1, −32.6% at 4 and −22.0% at 8 (8k/1k); −52.0% at 60k/600 concurrency 1. `amd/Qwen3.8-2.4T-A95B-Quark-MXFP4` TP8 on MI355X; see End to end.
- No loss past the 8-row cutoff: from concurrency 12 to 64, TPOT matches stock to within ±0.6% at 1k and 8k ISL. The gain at concurrency 8 shrinks from −24% at 1k to −6% at 128k ISL; see Where it stops helping.
- Launches per decode step 1684 → 1160 (8k/64, concurrency 4): no MoE launches and one all-reduce left; K1 + K2 are 161 of them.
- Accuracy unchanged: GSM8K with the model card's recipe 0.971 → 0.971 (all 1,319 questions, 8 threads). RULER NIAH (single 2), two paired runs: 0.888 → 0.896 and 0.856 → 0.864 at 64k, 0.760 → 0.796 and 0.766 → 0.794 at 128k, p ≥ 0.14. GPQA Diamond 0.924 → 0.934 at 8 client threads (unpaired; within noise).

## Details

**Path.** The step is chosen as a whole in `Qwen3_5ForCausalLMBase.forward`, the uncompiled outer forward. Eligible steps are pure decode, 1–8 rows, no spec decode, no `inputs_embeds` or intermediate tensors, and no Eagle3 aux layers. They run the mono forward; everything else runs the stock compiled model unchanged. The FULL decode graph captures the mono forward once per width, and vLLM's eager warmup at each capture size compiles the kernels before capture.

- **K1** (69 GDN layers): residual add + `input_layernorm` → `in_proj_qkvz` / `in_proj_ba` → causal conv1d update → gated delta rule → `RMSNormGated`, writing `out_proj`'s input. No cross-rank traffic.
- **K2** (all 92 layers): `out_proj` / `o_proj` + its TP all-reduce → residual add + `post_attention_layernorm` → softmax top-10 renormalized router → MXFP4 routed experts → sigmoid-gated shared expert → MoE all-reduce.
- **Full-attention layers** (23) run vLLM's `qkv_proj` and attention, with the input norm, q/k norm + RoPE and output gate as one fused Triton kernel plus two compiled elementwise helpers (`f3c2ec988b`), then K2.

**Design decisions.**
- The dispatch is at the model level rather than per layer as in #60683. The Qwen3.8 serving config runs a FULL decode graph with no breakable cudagraph, so per-layer eager breaks are no-ops. Choosing the whole step keeps the compiled stock path byte-for-byte unchanged.
- **Numerics contract:** K1 reproduces AITER's decode kernels, including the conv's bf16 rounding of each product and softplus threshold 20. Pad rows (state index ≤ 0) write no state and output zero. Both residual add + norm stages follow vLLM's native `fused_add_rms_norm`, which `GemmaRMSNorm` uses: the residual is stored rounded to bf16, but the norm reads the unrounded fp32 sum.
- **Routed experts:** at 1–8 rows, stock runs AITER's one-stage `fmoe_bf16_pertokenMXfp4_g1u1_flat`. It takes bf16 input but runs both x and silu(g)·u through dynamic MXFP4 (1×32 blocks, scale `ceil_pow2(amax / 6)`). K2 does the same, and feeds the codes to the scaled fp4 MFMA.
- **Buffers:** each width has its own scratch for K1 and for K2. The peer buffer layout is width-independent, so consecutive steps of different widths never share a region; this guards against the #60397 race class. Mailbox tags carry a device epoch bumped once per step, so nothing is zeroed between steps.
- **Refusals, as in #60397:** an explicit `VLLM_ROCM_MONO_DECODE=1` that cannot run raises at init, listing every reason (CDNA4, TP8, no PP, no expert / data / context parallelism or EPLB, no LoRA, no spec decode, no KV connector, at least 256 CUs so the grid is resident). A weight layout the kernels cannot read raises at the first decode step (`AITER_MXFP4_MXFP4` experts shuffled and all local, `in_proj_qkvz` and `out_proj` / `o_proj` bf16 or online MXFP4 on the ASM FP4 GEMM, the other dense weights bf16, `A_log` fp32). A model variant outside the kernels (other shapes, a replicated shared expert, layer scale, sequence parallelism) stays on the stock path, logged once. Launch arguments are checked with `ValueError`, not `assert`.
- **RFC #60904:** the layout follows #60397 as merged (`amd/mono_decode.py` + `amd/mono/`). The runtime still comes from #60683's `kimi_k3/amd/mono/common`: main's `deepseek_v41/amd/mono/common` lacks pieces K1 / K2 use (`ranks`, sync `shift`, the GEMV stage's API), and the RFC moves this code to a shared `common/mono/` once more models land. Bounded waits, error words and fail-stop are not in yet; they come with the shared library.

**Shared code.** `qwen3_5.py` gains 8 lines: the import, the constructor hook and the forward dispatch. With the env var unset, or off ROCm, `_mono` is `None` and nothing else changes; CUDA is unaffected.

**Limitations and CI gaps.**
- **Scope:** TP8, gfx950, MXFP4 W4A4 routed experts only. gfx942 is not supported because the MXFP4 checkpoint does not run there and the kernels target gfx950 MFMA and LDS sizes. On gfx942 an explicit `VLLM_ROCM_MONO_DECODE=1` raises at init (the CDNA4 refusal).
- **No spec decode:** MTP steps take the stock path. MTP support is a follow-up.
- **CI:** the numerics tests need gfx950 and 8 GPUs; the host-only tests run in the same step.
- **Size:** about 2,700 new lines of kernel code plus ~480 lines of glue, under `vllm/models/qwen3_5/amd/`, and an 840-line test file. Each kernel builds one fixed schedule per width and layout, with no tuning switches.
