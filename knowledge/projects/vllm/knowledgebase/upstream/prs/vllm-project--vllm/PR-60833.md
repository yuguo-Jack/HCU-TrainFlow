## Overview

**Draft, stacked on #60683; #61325 (Qwen3.8-Flash-Next) is stacked on this PR.** Until #60683 merges, the compare view also shows #60683's two commits (`c8a3845fb0`, `5efc7825e2`, its earlier head rebased onto main at `2eb491e18b`); this PR is the commits after them: 4,715 added lines in 16 files ([this PR's commits only](https://github.com/mjkvaak-amd/vllm-project/compare/5efc7825e2...rocm/qwen38-mono-decode); Files changed shows 10.9k, #60683's 6.1k included).

This PR ports the Kimi-K3 mono decode (#60683, @hyukjlee) to Qwen3.8 (`Qwen3_5MoeForCausalLM`, `amd/Qwen3.8-2.4T-A95B-Quark-MXFP4`) at TP8 on MI355X (gfx950). It is opt-in behind the existing `VLLM_ROCM_MONO_DECODE=1`. On pure decode steps of up to 8 rows, and on MTP verify steps of up to 8 rows, each decoder layer runs as at most two persistent launches instead of the stock chain of GEMMs, norms, all-reduces and MoE kernels. It reuses #60683's mono framework (`vllm/models/kimi_k3/amd/mono/common`): mailboxes, the peer buffer and the GEMV stage. The MoE, GDN and host code are written as a shared Qwen mono base (`vllm/models/qwen3_5/amd/mono/{moe,gdn}.py`, `mono_base.py`) parameterized by shape dataclasses, which #61325 reuses at Flash-Next's TP2 shapes.

Not a duplicate: I searched open PRs for "mono decode", "mono decode Qwen" and "Qwen3.8 mono". #60683 (Kimi-K3) and #60397 (DeepSeek-V4.1-Flash) are the same technique for other models; neither covers GDN layers or softmax top-10 routing.

## Details

**Path.** The step is chosen as a whole in `Qwen3_5ForCausalLMBase.forward`, the uncompiled outer forward. Eligible steps are pure decode or MTP verify steps, 1–8 rows, no `inputs_embeds` or intermediate tensors, no Eagle3 aux layers, and not a piecewise cudagraph step (those graphs also serve short prefills, so they must be captured from the stock model). They run the mono forward; everything else runs the stock compiled model unchanged. The FULL decode graph captures the mono forward once per width, and vLLM's eager warmup at each capture size compiles the kernels before capture.

- **K1** (69 GDN layers): residual add + `input_layernorm` → `in_proj_qkvz` / `in_proj_ba` → causal conv1d update → gated delta rule → `RMSNormGated`, writing `out_proj`'s input. No cross-rank traffic.
- **K2** (all 92 layers): `out_proj` / `o_proj` + its TP all-reduce → residual add + `post_attention_layernorm` → softmax top-10 renormalized router → MXFP4 routed experts → sigmoid-gated shared expert → MoE all-reduce.
- **Full-attention layers** (23) run vLLM's `qkv_proj` and attention, with the input norm, q/k norm + RoPE and output gate as one fused Triton kernel plus two compiled elementwise helpers (`f3c2ec988b`), then K2.
- **MTP verify steps:** a request's rows are consecutive tokens of one sequence, and K1's recurrence keeps no per-draft-token state to roll back rejected drafts. So a GDN layer runs the input norm, vLLM's `in_proj_qkvz` / `in_proj_ba`, then vLLM's GDN core (`qwen_gdn_attention_core` on the step's spec-decode metadata) and the gated norm compiled into one launch, then K2. Full-attention layers and K2 run as on decode steps, so `out_proj` / `o_proj`, the all-reduces and the MoE stay on the kernels.

**Design decisions.**
- The dispatch is at the model level rather than per layer as in #60683. The Qwen3.8 serving config runs a FULL decode graph with no breakable cudagraph, so per-layer eager breaks are no-ops. Choosing the whole step keeps the compiled stock path byte-for-byte unchanged.
- **Numerics contract:** K1 reproduces AITER's decode kernels, including the conv's bf16 rounding of each product and softplus threshold 20. Pad rows (state index ≤ 0) write no state and output zero. Both residual add + norm stages follow vLLM's native `fused_add_rms_norm`, which `GemmaRMSNorm` uses: the residual is stored rounded to bf16, but the norm reads the unrounded fp32 sum.
- **Routed experts:** at 1–8 rows, stock runs AITER's one-stage `fmoe_bf16_pertokenMXfp4_g1u1_flat`. It takes bf16 input but runs both x and silu(g)·u through dynamic MXFP4 (1×32 blocks, scale `ceil_pow2(amax / 6)`). K2 does the same, and feeds the codes to the scaled fp4 MFMA.
- **Buffers:** each width has its own scratch for K1 and for K2. The peer buffer layout is width-independent, so consecutive steps of different widths never share a region; this guards against the #60397 race class. Mailbox tags carry a device epoch bumped once per step, so nothing is zeroed between steps.
- **Refusals, as in #60397:** an explicit `VLLM_ROCM_MONO_DECODE=1` that cannot run raises at init, listing every reason (CDNA4, TP8, no PP, no expert / data / context parallelism or EPLB, no LoRA, spec decode only as MTP with at most 7 draft tokens and AITER's Triton GDN kernels, no KV connector, at least 256 CUs so the grid is resident). A weight layout the kernels cannot read raises at the first decode step (`AITER_MXFP4_MXFP4` experts shuffled and all local, `in_proj_qkvz` and `out_proj` / `o_proj` bf16 or online MXFP4 on the ASM FP4 GEMM, the other dense weights bf16, `A_log` fp32). A model variant outside the kernels (other shapes, a replicated shared expert, layer scale, sequence parallelism) stays on the stock path, logged once. Launch arguments are checked with `ValueError`, not `assert`.
- **RFC #60904:** the layout follows #60397 as merged (`amd/mono_decode.py` + `amd/mono/`). The runtime still comes from #60683's `kimi_k3/amd/mono/common`: main's `deepseek_v41/amd/mono/common` lacks pieces K1 / K2 use (`ranks`, sync `shift`, the GEMV stage's API), and the RFC moves this code to a shared `common/mono/` once more models land. Bounded waits, error words and fail-stop are not in yet; they come with the shared library.

**Shared code.** `qwen3_5.py` gains 8 lines: the import, the constructor hook and the forward dispatch. With the env var unset, or off ROCm, `_mono` is `None` and nothing else changes; CUDA is unaffected.

Within `vllm/models/qwen3_5/amd/`, code a second Qwen model can use is split out of Qwen3.8's kernels, after #61482's `MonoSpec` / `Dims`:
- `mono/moe.py` on `MoeDims`: the fp4 GEMV, x quantization, `o_proj`, the route, the expert stages and the split-K row reduction;
- `mono/gdn.py` on `GdnDims`: the GDN tasks (conv, gates, recurrence, norm, `in_proj_ba` with the K split a parameter), with the model's b / a source and z gate as hooks;
- `mono_base.py` (`QwenMonoDecode`): the refusals, the step gate, the buffers, the weight checks' common part and the MTP verify steps. `mono_decode.py` keeps Qwen3.8's shape checks, weights and forward.

**Limitations and CI gaps.**
- **Scope:** TP8, gfx950, MXFP4 W4A4 routed experts only. gfx942 is not supported because the MXFP4 checkpoint does not run there and the kernels target gfx950 MFMA and LDS sizes. On gfx942 an explicit `VLLM_ROCM_MONO_DECODE=1` raises at init (the CDNA4 refusal).

@mjkvaak-amd, I think that the GDN projections in this PR should be MXFP6 instead of MXFP4. With the online MXFP4 targets for `in_proj_qkv`, `in_proj_z` and `out_proj`, the gsm8k score stays within noise, but the answers get about 30% longer and about three times as many of them run into the token cap before the answer line. MXFP6 E2M3 brings the answers back to the bf16 length, and K2 reads it as fast as MXFP4.

**Accuracy.** lm_eval gsm8k, 5-shot completions, `max_gen_toks=2048`, 8 concurrent, all 1,319 questions. `amd/Qwen3.8-2.4T-A95B-Quark-MXFP4` TP8 on MI355X, `vllm/vllm-openai-rocm:nightly-8cbd5d03006c33185f402249ff2b448efd594986`, the shared expert in online MXFP4 in every row. The standard error of the score is about 0.006, so the answer length shows the difference more clearly than the score.

| GDN projections | Mono decode | gsm8k flexible | Mean answer length (characters) | Answers at the 2048-token cap |
| --- | --- | --- | --- | --- |
| bf16 | off | 0.9492 | 433 | 8 |
| online MXFP8 | off | 0.9560 | 458 | 9 |
| online MXFP4 | off | 0.9424 | 564 | 27 |
| online MXFP4 | on, `6a1c13b2fc` | 0.9477 | 560 | 21 |
| MXFP6 E2M3 | on, K1 and K2 read MXFP6 | 0.9500 | 452 | 9 |

The MXFP6 row also has the attention `qkv_proj` and `o_proj` in MXFP6, so it quantizes more weights than the MXFP4 rows and still keeps the bf16 length.

**How to make the MXFP6 weights.**

1. Serve the GDN projections in bf16, so the targets keep only the shared expert: `--quantization-config.targets '{"*shared_expert*": "mxfp4"}'`. `in_proj_ba` stays bf16 as before.
2. After loading, round every bf16 weight of `in_proj_qkvz` and `out_proj` (and the attention `qkv_proj` and `o_proj`) to its MXFP6 E2M3 value in place, one block of 32 along K at a time. The block scale follows AITER's `dynamic_mxfp4_quant` with the E2M3 maximum of 7.5. The block maximum is rounded to 3 mantissa bits, and the scale is 2 to the power of its exponent minus 2, so no value in the block is above 7.5 times the scale. Each value then rounds to the nearest E2M3 value, ties to even. An E2M3 value times a power of two fits in bf16 exactly, so prefill, the steps wider than 8 rows and K1 and K2 all multiply the same values.
3. Pack a copy for the kernels with the OCP E2M3 codes (sign at bit 5, then 2 exponent and 3 mantissa bits) and one e8m0 byte a block. 32 codes are 24 bytes, with code i at bits 6i to 6i+5 in little-endian order, which is the order in which `v_cvt_scalef32_pk32_bf16_fp6` reads them. One such instruction turns a lane's 32 codes times `2^(e8m0 - 127)` into 32 bf16 values exactly, and they go into the bf16 MFMA with the bf16 activations (W6A16). We store a tile of 16 rows and 128 K as 64 lanes of 24 bytes, with the first 16 bytes of every lane together and the last 8 together, so a lane loads one dwordx4 and one dwordx2. The converted dwords then come out in the order in which K2 reads an MXFP4 tile, so the MFMA loop does not change.

The rounding of step 2:

```python
def round_e2m3(x: torch.Tensor) -> torch.Tensor:
    v = x.float().reshape(-1, x.shape[-1] // 32, 32)
    amax = v.abs().amax(dim=-1, keepdim=True)
    # Adding 2**19 to the fp32 bits of the block maximum rounds its mantissa
    # at the third bit, and a carry moves into the exponent. The mask keeps
    # only the exponent field.
    exp = (((amax.view(torch.int32) + 0x80000) & 0x7F800000) >> 23) - 127 - 2
    # An all-zero block keeps a normal scale, because a scale of zero would
    # turn 0 / 0 into NaN.
    scale = torch.exp2(exp.clamp(-126, 127).float())
    a = v.abs() / scale
    q = torch.where(
        a < 2.0,
        torch.round(a * 8.0) / 8.0,
        torch.where(a < 4.0, torch.round(a * 4.0) / 4.0, torch.round(a * 2.0) / 2.0),
    )
    return (torch.sign(v) * q.clamp(max=7.5) * scale).reshape(x.shape).to(x.dtype)
```

**Cost.** In our build on top of `6a1c13b2fc`, K2 with an MXFP6 `out_proj` or `o_proj` takes 34.7 µs a launch at 2 rows, as fast as with MXFP4. K1 with an MXFP6 `in_proj_qkvz` takes 14.41 µs at 2 rows, against 13.37 µs with MXFP4 and 28.54 µs with bf16, so about 0.07 ms a decode step over the 69 GDN layers. The bf16 weights stay for prefill and for the steps wider than 8 rows, and the packed copies of `in_proj_qkvz`, `out_proj` and `o_proj` add 3.24 GB a GPU. At `--gpu-memory-utilization 0.9` the KV cache goes from 81.44 GiB (7.33M tokens) with the MXFP4 targets to 72.57 GiB (6.53M tokens). A W6A16 GEMM for the stock path would let the bf16 weights go.
