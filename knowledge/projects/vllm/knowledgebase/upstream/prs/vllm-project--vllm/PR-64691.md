# [RL] NCCL weight transfer: release cached memory after a weight update

[Upstream PR](https://github.com/vllm-project/vllm/pull/64691) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

After an NCCL weight update, release the unused memory held by torch's caching allocator: one `torch.accelerator.empty_cache()` at the end of `NCCLWeightTransferEngine.finish_weight_update`. Part of the direct weight reload work (RFC #54477); independent of the other PRs.

## Claims

- After every NCCL weight update, the server's torch reserved memory is back to its cold-start level. On Qwen3-30B-A3B-FP8 (TP=2), each rank has 3.7–4.4 GiB more free device memory after a sync than on main.
- Weights, accuracy, throughput and KV cache size are unchanged.
- Cost: the next update allocates its receive buffers again. Median sync time went from 6.67 s to 7.13 s (+7%, one run per arm).

## Validation

Both setups use GB200 and Qwen3-30B-A3B-FP8 with the server at TP=2. The trainer runs on other GPUs and sends the weights over NCCL.

**Weight-sync bench.** The [state-transition verifier](https://github.com/hao-aaron/vllm-state-transition-verifier) `run_bench.py` setup:
- trainer `fsdp=2`, `--backend nccl`;
- 1 warmup + 3 measured syncs, each with a perturbed checkpoint;
- server `--max-model-len 2048 --gpu-memory-utilization 0.8`;
- every tensor is compared against a fresh server at the end.

Server memory per rank after each sync (all four syncs agree within 2 MiB):

| | allocated | reserved | device free | median sync |
|---|---|---|---|---|
| main | 146.30 GiB | 150.72 GiB | 29.82 GiB | 6.67 s |
| this PR | 146.28 GiB | 146.36 GiB | 34.18 GiB | 7.13 s |

Weights compared with a fresh server: 0 mismatched, 0 moved, in both arms. Both arms also report the same 192 `moe_quant_config._w1/_w2.scale` tensors re-created by layerwise reload; that happens on main and is unrelated to this change.

**A/B after one update.** Main vs this PR on the same nightly wheel, same node, back to back:
- each arm cold starts, receives one NCCL update of the same checkpoint, then is measured;
- GSM8K: 5-shot greedy, all 1319 questions;
- throughput: `vllm bench serve`, random 1024 in / 256 out, concurrency 64;
- server: `--max-model-len 4096 --gpu-memory-utilization 0.8`.

| | GSM8K | output tok/s | KV cache | device free after the sync | torch reserved after the sync |
|---|---|---|---|---|---|
| main | 0.8954 | 8276 | 2.794M | 31.23 GiB | 147.92 GiB |
| this PR | 0.8946 | 8407 | 2.794M | 34.89 GiB | 144.27 GiB |

- **Noise:** GSM8K differs by one question and throughput by 1.6%. Running the same code as both arms gives ±1 question and 1.8%.
- **Memory:** with this PR, reserved memory after the sync equals its cold-start value. Free memory is 0.62 GiB below cold start, which is the NCCL communicator created during the first sync. On main it is 4.28 GiB below.
- **Why the gain differs from the bench (3.66 vs 4.36 GiB):** this setup uses a different nightly, a different `--max-model-len`, and one sync instead of four.

**CI:** no unit test. The effect only shows up in device memory after a real NCCL update between two processes. The existing NCCL engine tests don't run one, and a mocked test would only assert that the call happens.

## Details

After `finalize_layerwise_reload`, the caching allocator keeps the freed receive buffers and post-load temporaries reserved. Torch can reuse that memory; nothing outside torch can. That includes other processes on the GPU (e.g. a colocated trainer) and allocations that bypass the caching allocator (NCCL, e.g. a newly created communicator).

`empty_cache()` releases the unused cached segments once per update, after all weights are loaded, so the transfer itself is unaffected. Blocks still in use and CUDA graph pools are not touched. `base_loader.py` already calls `empty_cache()` after loading and after post-processing at cold start.

Only the NCCL engine is changed, as that is the path measured here. The other layerwise engines (IPC, M2N, sharded RDT) could get the same call in a follow-up.
