[Upstream PR](https://github.com/vllm-project/vllm/pull/65588) · state: open · merged: False

## Original PR description

# [Spec Decode] Measure the Dynamic SD table instead of writing it by hand

Towards #62740.

## Why this is needed

**What vLLM supports.** PR #32374 added the Dynamic SD hardcoded table. PR #57053 makes V2 honor the runtime K. This PR builds on both. It writes the table that #32374 reads.

**What is missing.** The values of the table. The #32374 branch drafted an offline profiler which was removed before merge. The docs tell the user to write the table by hand.

**Why that matters.** The documented example works on some dense models but on a MoE model it loses up to 18% throughput. The failure is silent, as reported in https://github.com/vllm-project/vllm/issues/49548 and https://github.com/vllm-project/vllm/issues/49986. No user can tell which case their model is in. The best fixed K loses 12.7% at some load on the same setup where a measured table loses 3.4% — so the table mechanism pays, but only with the right values.

**Relation to adaptive verification.** AV does one job: it decides how many drafted tokens to verify. It does not set how many tokens the engine drafts. The Dynamic SD table sets that number. The two features do different jobs, and they compose: the table caps drafting at each batch size, and AV trims verification inside that cap.

**This is where production systems are going.** DeepSeek does the same in production: their [DeepInfer](https://github.com/deepseek-ai/deepinfer) inference stack, built on vLLM, drafts 5 tokens per step with DSpark and schedules verification from a profiled hardware throughput curve ([their deployment Q&A](https://github.com/deepseek-ai/deepinfer/blob/main/doc/inference_deployment_qa.md)). Their gains also grow with the load, up to 11% at 96 sequences per rank. The principle is the same one this PR applies to the Dynamic SD table: measure the hardware, then decide how much to speculate.

**The method generalizes across hardware.** It was evaluated on three GPU generations — T4, A10G and H100 — with different drafters and runners (full study: https://arxiv.org/pdf/2610.38968). On the H100 the tuned table stays within 3–6% of the best fixed K for most drafters; on the older GPUs the same method holds, and the controller repairs mistuned tables on all three (up to 58% on the H100, 36% on the T4, 14% on the A10G).

## What this adds

Three pieces, **no engine changes**:

1. **`vllm bench sweep tune`** — a new sweep subcommand that measures
   `num_speculative_tokens_per_batch_size` for a target model and drafter on
   the user's own GPU, in minutes:

   ```bash
   vllm bench sweep tune --target Qwen/Qwen3-8B \
       --drafter Qwen/Qwen3-8B-speculator.eagle3 --prompts-file prompts.jsonl
   ```

   It prints the measured table ready to paste into `--speculative-config`,
   and writes `schedule.json`, `costs_k*.json` and `acceptance.json` for
   reproducibility.

2. **An opt-in controller** that keeps the table current while serving. It
   reads the acceptance counts the scheduler already computes, re-fits the
   table from the tuner's step costs and live acceptance, and holds K near
   table edges (hysteresis). It only uses K values already in the table, so
   it never needs new CUDA graph shapes.

3. **Docs** — the Dynamic SD page now says the example table is only an
   example, shows how to measure one, and documents the controller's
   `VLLM_DSD_*` variables.

## Implementation

- **Step costs**: for each K, the engine runs with a Dynamic SD table pinned
  to K and vLLM's own **synthetic rejection sampler**
  (`rejection_sample_method: "synthetic"`) at 0% acceptance, so every step
  does the full drafting and verification work of K tokens while the batch
  stays fixed. Step time = `(t(N+1) - t(1)) / N` over a grid of batch sizes,
  on the serving path, through the same table lookup the deployment uses.
- **Acceptance**: one run at the longest K on user prompts, reading vLLM's
  own spec-decode counters (`vllm:spec_decode_num_accepted_tokens_per_pos`).
- **Table**: `goodput(B, K) = B · tokens_per_step(K) / step_time(B, K)`, best
  K per batch size with two rules against switching (eps tie-breaking;
  narrow-range merging), so the table is short and stable at its edges.
- Each measurement stage runs in its own process so it gets the whole GPU.
- **Shared computation** (`vllm/v1/spec_decode/dynamic/schedule.py`): pure
  functions, no vLLM imports — the tuner and the controller build identical
  tables from the same code, and it is unit-tested without a GPU.
- **Controller** (`controller.py`, pure + unit-tested; `controller_plugin.py`
  attaches it): registered under the existing `vllm.general_plugins`
  entry-point group (the same mechanism as the in-tree LoRA resolvers). The
  plugin wraps `Scheduler.__init__` and `make_spec_decoding_stats`; the
  scheduler's source is untouched, the install is idempotent, and a missing
  hook fails at startup naming the methods. If maintainers prefer a
  first-class scheduler hook instead of the wrapper, that is a small
  follow-up — the controller class does not change.
- **Controller failure policy**: invalid settings raise at startup; while
  serving, a failed re-fit keeps the current table and three failures in a
  row turn re-fitting off. Serving never stops.

## Choices

K=0 is not measured by default. On current builds, a K=0 step still runs one
drafter forward pass. That extra pass makes the measured K=0 step slower than
a step with speculation truly off. The tuner compares step times, so it would
never put K=0 in the table: the engine would keep drafting at every batch
size, even where not drafting is faster. `--include-k0` measures K=0 anyway.

The controller is opt-in. It is off until the user sets `VLLM_DSD_CONTROLLER=1`.
A user who upgrades vLLM gets the same behavior as before. The PR adds a
capability. It does not change any existing deployment.

## Known limitations

On some builds a table that steps from K=2 to K=1 can stall decode. That is a
piecewise CUDA graph bug in the engine, not the tuner. See the discussion in
#62740.

## Test plan

- [x] `tests/v1/spec_decode/test_dsd_schedule.py`: interpolation, tokens/step,
      goodput, both switching rules, compression/expansion, allowed-K
      restriction, cost and acceptance file validation.
- [x] `tests/v1/spec_decode/test_dsd_controller.py`: hysteresis, K clamping,
      observation clamping, prior/live blending, re-fit rebuild and CUDA-graph
      restriction, failure policy, env gating and validation.
- [x] `tests/benchmarks/sweep/test_tune.py`: config emission, K=0 default.
- [x] End-to-end on one H100 80GB, vLLM main `eaf1627c0` (Oct 27, 2026),
      Qwen3-8B + EAGLE-3 speculator, ISL 32 code prompts at T=1.0,
      batch grid 1–128 (30 batch sizes × 3 K values, 90 timed points): the
      tuner measured `[[1, 52, 3], [53, 128, 2]]` in about 6.5 minutes. A
      closed-loop sweep of that table (3 runs) keeps it within 3.4% of the
      best fixed K at every load.
- [x] Controller serving check on the same setup: with the measured table and
      `VLLM_DSD_CONTROLLER=1` (hysteresis 8, re-fit every 200 steps from the
      tuner's cost and acceptance files), the controller attaches, serves, and
      re-fits the table live; with the variable unset, nothing changes.
- [x] Hardware generalization: the same method and controller were also
      evaluated across several drafters (EAGLE-3, DFlash, n-gram) and both
      model runners, on the GPUs listed above — details in the study link.
