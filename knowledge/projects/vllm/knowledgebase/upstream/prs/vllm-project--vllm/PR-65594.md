# [Bugfix][Frontend] Handle non-string HTTPException details

[Upstream PR](https://github.com/vllm-project/vllm/pull/65594) · state: open · merged: False

## Original PR description



## Overview

Preserve the status and original message of `fastapi.HTTPException` when `detail` is a dictionary, list, number, or boolean. Previously, the HTTP handler raised a `TypeError`, and the fallback replaced the exception with a 400 containing the type error—even for an original 429 or 503.

## Claims

- Convert `detail` to a string before applying the existing message sanitizer; string details keep their existing behavior.
- Preserve HTTP status, error code, and diagnostic content, including when the OpenAI SDK classifies rate-limit and service-unavailable responses.
- Document the default error handling for endpoint plugins.

## Details

[FastAPI permits JSON-compatible `detail` values](https://fastapi.tiangolo.com/tutorial/handling-errors/#the-resulting-response). The vLLM handler passed them directly to a string sanitizer, whose regex operation raised `TypeError`. The general exception handler then mapped that new exception to 400 and discarded the original status and detail. A 503 with a dictionary detail consequently became `openai.BadRequestError`, rather than `openai.InternalServerError`.

Use `str(detail)` at the HTTP-to-OpenAI error boundary, matching `ErrorInfo.message`'s string contract, and retain the existing sanitization. This is one changed production line with no new dependency or shared sanitizer contract change.

Duplicate checks searched open PRs for `"HTTPException" "detail"` and `"http_exception_handler"`, plus all-state PR titles for `"HTTPException" "detail"`. No matching fix was found. Related [#62127](https://github.com/vllm-project/vllm/pull/62127) preserves response headers; [#54140](https://github.com/vllm-project/vllm/pull/54140) and [#59386](https://github.com/vllm-project/vllm/pull/59386) modify proxy examples. They do not handle non-string details in this handler.
