# [ROCm][DSv4.1][Perf] Fused router gate for gfx950

[Upstream PR](https://github.com/vllm-project/vllm/pull/57478) · state: closed · merged: False

## Original PR description

## Purpose and measured status

Optimize the gfx950 BF16 router `X[M,7168] @ W[384,7168].T` plus sqrtsoftplus scoring, correction bias, and expert selection. The tested M values are all **33 distinct products** of `[1,2,4,6,8,16,32,64,128,256] × [1,2,3,4,5,6]`, through 1536; both top-k 6 and 8 are measured below.

The optimized operation beats the runnable unfused baseline at every measured size: **1.47–3.86× with cold rotating inputs**. **It does not reach the raw hardware roofline.** At M=1536/top-k6, the full operation takes **23.17 µs cold** versus **3.450 µs** for the ideal bandwidth/compute-only bound (**14.9%**). The analysis below identifies the remaining costs.

The original draft fails compilation at `tl.arange(0,384)`. The runnable baseline here is BF16→FP32 `torch.mm` (the gate GEMM operation used by GateLinear) followed by `fused_topk_bias(scoring_func="sqrtsoftplus")`.

## Implementation

- M=1–2 uses a vector GEMV; other batches use tiled BF16 MFMA with deterministic FP32 split-K partials.
- The second kernel fuses partial reduction, scoring, bias-aware ranking, normalization, and scaling. Larger batches use a single-wave Gluon selector; smaller batches use packed-key Triton top-k. This is a **two-kernel** implementation.
- Ranking keys retain the entire FP32 score and inverse expert ID. Equal computed ranks prefer the lower expert ID; output weights retain the unbiased score.
- Compensated `log1p` preserves small negative-tail scores without the slower general OCML path. A direct maximum handles top-k1, which otherwise fails to compile with the installed Triton `topk(k=1)`.
- M>768 uses larger MFMA32 tiles and an XCD-aware launch order. The supported token cap increases to 1536; input storage/device and ID dtype validation are enforced.

The fused gate is wired into the MoE runner for DeepSeek-V4.1-Flash (and the
7168-hidden DeepSeek-V4 shape); see "Model wiring" below for the dispatch,
the accuracy check, and the end-to-end measurement.

## Measurement protocol

Measured commit: `f894dba7781cda88aab4edb1fbc8012fc4c2b87f`. MI355X/gfx950, one GPU (physical GPU4), BF16 inputs, FP32 accumulation/output weights, int32 expert IDs, correction bias, renormalization, scaling=1.5. PyTorch `2.12.0+rocm10.0.0`, HIP `7.15.26333`, Triton `3.8.0`. Environment: `HIP_VISIBLE_DEVICES=4 HIP_FORCE_DEV_KERNARG=1 ROCPROFILER_QUEUE_INTERPOSITION=0`.

Both arms measure the complete GPU operation using HIP graph replay. Compilation, allocation, random inputs, and copies are outside timing. Events surround 128 operations; three rounds alternate arm order with 15 samples each. Tables report medians; the JSON artifact retains p10/p90 and kernel source SHA256 `de8dd90626b18179a16bf49b0d3ff8298401f002901da3c71903a368368f0e99`. Correctness is checked before timing.

**Warm** reuses one input set. **Cold** rotates 128 independent input sets: gate weights alone occupy **672 MiB**, exceeding the 256 MB last-level cache. This defeats reuse between operations while preserving legitimate reuse inside each operation. Warm throughput is not evidence of HBM bandwidth. CUPTI is unavailable on ROCm; per-dispatch event timing was rejected because it inflated a no-op control from 1.684 to 8.52 µs.

## Roofline analysis

The dense MI355X specifications are **8 TB/s HBM**, **2.5166 PFLOP/s BF16 matrix compute**, and **256 MB LLC**. The higher sparse compute number is not applicable. Source: [AMD MI355X datasheet](https://www.amd.com/content/dam/amd/en/documents/instinct-tech-docs/product-briefs/amd-instinct-mi355x-gpu-brochure.pdf).

For N=384, K=7168, and k selected experts:

```text
F = 2*M*N*K
B_min = 2*(M*K + N*K) + 4*N + 8*M*k
AI = F / B_min
T_peak = max(B_min / 8e12, F / 2.5166e15)
TFLOP/s = F / latency_us / 1e6
Effective GB/s = B_min / latency_us / 1000
```

Bytes count each BF16 input and FP32 bias once and one FP32 weight plus int32 ID per selected expert. They exclude scratch and repeated tile loads. The FLOP count includes GEMM, but not nonlinear scoring, comparison, or reduction. Effective bandwidth is mathematical operation traffic, not measured HBM traffic.

Independent large-workload controls on GPU6 reached **6.533 TB/s** for a checked 1 GiB streaming read and **1.403 PFLOP/s** for 8192-square BF16 GEMM with FP32 output after sustained warmup. A live sample during GEMM recorded 1766 MHz SCLK/1399 W, versus the datasheet's boost conditions. These are measured calibration points, not proven ceilings for this router. Their illustrative bound is `max(B_min/6.533e12, F/1.403e15)`.

Representative top-k8 bounds and achieved full-operation throughput:

The peak ridge is 314.575 FLOP/B, so the entire requested sweep is memory-bound in that ideal model (M1536/top-k8 reaches 306.09 FLOP/B). The calibration ridge is 214.76 FLOP/B, making its larger-M bound compute-dominated. Neither model captures launch/selection latency or limited workgroup residency.

**Small M:** a graph no-op measured 1.684 µs and a rotating ~5.5 MB read measured about 2.78 µs, already above the 0.69 µs bulk-bandwidth ideal. Two dependent launches, scalar/vector scoring, and wave communication are substantial fixed costs. These controls provide context; subtracting their latency from the operation would not be a valid measured speedup.

**Large M:** split-K trades extra traffic for occupancy. At M1536/S7, partial logits occupy 16.515 MB and add **33.030 MB of logical write+read traffic**. Final BM128/BN128 tiling issues approximately **132.121 MB of logical input loads**, despite only 27.525 MB of unique BF16 input data. Those repeated loads can hit cache; they are not an HBM-byte count.

Counter ablation at M1536, prior BM64/BN128/MFMA16 versus final BM128/BN128/MFMA32/XCD order:

| Counter/resource | Prior tile | Final tile |
| --- | ---: | ---: |
| FetchSize beyond L2, KiB | 64,534.5 | 33,589.5 |
| WriteSize, KiB | 16,128 | 16,128 |
| L2 hit rate | 64.4% | 74.6% |
| MFMA utilization | 13.45% | 15.12% |
| VMEM latency, cycles | 807 | 710 |
| VALU instructions | 1,316,448 | 695,584 |
| Register spills / LDS bank conflicts | 0 / 0 | 0 / 0 |

FetchSize is traffic beyond L2, not proof of off-chip HBM bytes on this LLC-equipped GPU. Counter collection perturbs cache/timing, so these counters are separate from the unprofiled latency tables. The ablation changes tiling, MFMA shape, and ordering together; it does not attribute the entire gain to ordering alone.

The final large tile uses 99,808 B (97.5 KiB) LDS and launches 252 useful CTAs at M1536, allowing only one resident CTA per CU. Lower memory latency and higher cache hit rate support improved locality; low MFMA utilization and limited residency remain consistent with a memory/dependency-latency bottleneck. **The raw roofline gap remains; it is not explained by missing matrix instructions or register spills.**

Further tests rejected no-split GEMM, a fully fused all-expert tile, explicit Gluon double buffering, prepared weights, wider tiles, and increased-residency configurations. They either slowed GEMM or increased partial-buffer/selection cost enough to lose end-to-end. Prepared weights additionally required a ~2.7 µs packing pass and 5.5 MB persistent storage. The final choice preserves the original contiguous weight input format.

Extreme exponential subnormals can flush on this ROCm configuration.

Existing evaluation artifacts belong to another change and are not reused as evidence. ## Model wiring (DeepSeek-V4.1-Flash)

- **Router:** `FusedTopKBiasRouter.bind_gate` absorbs the gate GEMM when
  routing is sqrtsoftplus without a hash table, on gfx950, with a bias-free
  gate of a supported shape. `select_experts_from_hidden_states` then runs
  the fused kernel and reuses the router's normal post-processing (fused
  shared-expert slots, routed-expert capture, EPLB mapping, index dtype,
  routing replay).
- **Runner:** `MoERunner` skips the router-logits GEMM only when the batch
  qualifies. Experts must be modular (monolithic kernels consume logits),
  there must be no naive DP/EP or PCP dispatch (both move logits between
  ranks), and the router must accept the batch. Everything else is unchanged.
- **Kernel additions** needed to replace `topk_hash_softplus_sqrt` in serving:
  - V4.1-Flash's `(5120, 384)` shape
  - the image-sentinel `bias_vl` per row
  - padding rows returning expert `-1`
  - a runtime token count, so serving no longer recompiles per batch size

At K=5120 (cold, HIP graphs, vs the serving `torch.mm(out_dtype=fp32)` +
`topk_hash_softplus_sqrt`), the fused gate is 1.48-3.34x faster across
M = 1..1536: M=1 19.2 → 5.8 µs, M=32 19.7 → 8.8 µs, M=192 21.9 → 12.3 µs,
M=1536 32.5 → 21.9 µs.

### End to end (TP2, conc 32, DSpark ×5, T = 192 tokens/step)

Baseline (`6831f4c159`, kernel present but unwired) and this commit ran side
by side under identical load. Run 2 swapped the GPU pairs to cancel
placement effects. Per decode step, rank 0, 24 steps:

| kernel (µs/step) | run 1 base | run 1 fused | run 2 base | run 2 fused |
|---|---|---|---|---|
| hipBLASLt gate GEMM (`Cijk_Alik_Bljk_BSS_…`) | 716.7 | — | 790.9 | — |
| `topkGatingSoftplusSqrt` | 552.8 | — | 546.3 | — |
| `_router_gate_gemm` + `_router_gate_reduce_topk_gluon` | — | 639.4 | — | 635.5 |
| **router total** | **1269.5** | **639.4 (−50%)** | **1337.2** | **635.5 (−52%)** |
| `mfma_moe1` + `mfma_moe2` | 15587 | 16231 | 15003 | 15726 |
| median GPU time per step | 33.60 ms | 33.44 ms (−0.5%) | 33.02 ms | 33.19 ms (+0.5%) |

| `vllm bench serve` (random 1k/1k, `--ignore-eos`, conc 32, 160 prompts) | output tok/s | mean TPOT | median TPOT |
|---|---|---|---|
| run 1 base / fused | 1870.3 / 1772.0 | 15.59 / 16.44 ms | 15.40 / 15.76 ms |
| run 2 base / fused | 1745.2 / 1774.8 | 16.71 / 16.45 ms | 16.40 / 16.16 ms |

**No end-to-end gain is claimed at this configuration.** The router work
halves, but GPU step time is unchanged within ±0.5%. The throughput runs
disagree in sign and vary as much as 7% run to run for the same arm.

In both GPU placements the routed-expert GEMMs grow by about what the router
saves. The likely reason is that the shared expert, which runs on a second
stream, now overlaps the expert GEMMs instead of the router, so the routed
path's critical path does not shorten. Realizing the saving end to end
likely needs the shared-expert overlap re-balanced or fused as well.
