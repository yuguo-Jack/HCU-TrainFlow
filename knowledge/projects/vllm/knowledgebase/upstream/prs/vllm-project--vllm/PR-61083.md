# [Core] Add sparse_disk weight transfer backend

[Upstream PR](https://github.com/vllm-project/vllm/pull/61083) · state: open · merged: False

## Original PR description

## Overview

This PR adds a `sparse_disk` weight transfer backend. The trainer writes each round's sparse patches to a safetensors file on storage shared with the inference workers, and the workers apply the patches in place.

It covers the sparse, update-from-disk part of #48644. I described the idea there first: https://github.com/vllm-project/vllm/issues/48644#issuecomment-6008358757.

## Claims

- You can send sparse patches without an NCCL group between the trainer and the inference servers, and without a GPU on the trainer.
- The trainer API is the same as `sparse_nccl`: the same `SparseWeightPatch`, `send_weights(patches)` and `send_weight_chunk(patches)`. Only the transport changes.
- Workers reject any safetensors file that is not a patch file. Pointing the backend at a full checkpoint by mistake fails without touching the model.

- The worker rejects a safetensors file that does not carry the patch format marker.
- A trainer rank that is not the sender writes no file and makes no RPC.

`mypy` on the new module and `ruff check` / `ruff format` on the changed Python files are clean.

**End to end on a GPU** (1x L4, main `2bea2200` plus this change, torch 2.13.0+cu130). I ran `vllm serve <model> --weight-transfer-config '{"backend": "sparse_disk"}'` and built the trainer engine with `WeightTransferTrainerFactory.trainer_init` and an `HTTPVLLMWeightSyncClient`. Qwen3-0.6B ties `lm_head` to the embedding, and its checkpoint lists both names, so I left `lm_head.weight` out of the patches. If I keep it in, the update fails with the #60151 error (`'lm_head.weight' was skipped because it is tied to 'model.embed_tokens.weight' ...`). #60188 fixes that.

## Details

**Why a separate backend.** `sparse_nccl` needs a GPU and an NCCL rendezvous on the trainer. When the trainer and the inference servers run separately, a filesystem is often the only thing they share. Sparse patches are small (1 to 3 percent of elements per AdamW step in my runs), so a file is a cheap way to move them.

**How it works.**

- Each update is one file. It holds tensors `{i}.indices` and `{i}.values`, and the names and full shapes go in the safetensors metadata under `format = vllm-sparse-patch-v1`. The file is written under a `.partial` name and then renamed, so a worker never reads a half-written file.
- The worker engine keeps no state. `init`, `start` and `finish` do nothing, as in `sparse_nccl`. `receive_weights` loads the file onto the worker's device and calls `load_checkpoint_weight_patches`, so TP slicing and packed parameters go through the model's own loader.
- The trainer engine writes the file under `patch_dir`, calls `update_weights` with its absolute path, and deletes the file when the call returns.
- `save_sparse_patches` and `load_sparse_patches` are public, so an orchestrator that wants to manage the files itself can do that.

**Why this is not a duplicate.**

- #52152 (draft) adds a `disk` backend that reloads a whole checkpoint directory through the layerwise path. This PR sends sparse patches that are applied in place. The two share no code.
- `modelexpress` installs published weight versions through an external service. This backend needs nothing beyond safetensors.
- I checked `gh pr list --state open --search "48644 in:body"` and `--search "sparse disk weight transfer"` on 2026-10-10.

**Limits.**

- The sparse loader's limits apply: floating-point, unquantized weights, where the final copy has the same shape as the checkpoint tensor.
- Models with tied embeddings need #60188 (the fix for #60151) when a patch carries both names.
- Each TP rank reads the whole file. There is no rollback after a partial failure, same as `sparse_nccl`.
- Workers open whatever path `update_weights` names. The docs say to expose the weight transfer endpoints only to trusted callers. I did not add a configured root directory because I wanted to leave `WeightTransferConfig` alone, but I'm happy to add one if you prefer.
- An update needs free GPU memory on every rank: the patch, plus the loader's full checkpoint-shaped tensor for the largest weight. Llama-3.1-8B ran out of memory at `--gpu-memory-utilization 0.85` and passed at 0.6.
- Tested with tensor parallelism up to 4 (see the comment below). Not tested: pipeline or expert parallelism, a network filesystem, several replicas reading the same patch file.

Size: 167 lines of code in the new module (242 with docstrings), plus 19 lines in the factory and config.
