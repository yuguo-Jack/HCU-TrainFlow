#  [Bugfix] Fix KV cache sizing and allocation for hybrid Mamba/attention models

[Upstream PR](https://github.com/vllm-project/vllm/pull/37429) · state: closed · merged: False

## Original PR description

## Summary

- Fix KV cache block count overestimation for hybrid Mamba/attention models (e.g. Qwen3.5) by detecting mixed groups and sizing each independently
- Fix token capacity reporting to only count Mamba groups when `mamba_cache_mode="all"`
- Add compact Mamba allocation: Mamba layers self-manage a dedicated O(1) block pool instead of sharing the attention pool, eliminating 7x memory waste and OOM
- Fix compact pool exhaustion causing 4x throughput regression by capping "none" mode allocation at `1+spec` blocks per request and making `remove_skipped_blocks` a no-op for permanent Mamba state

Supersedes #37124 (closed due to rebase notification issue).

## Code Review

This pull request introduces a new 'compact Mamba allocation' strategy to significantly improve memory efficiency and token capacity for hybrid Mamba+attention models like Qwen3.5. The changes involve decoupling Mamba layer memory allocation from attention layers, allowing Mamba (which has O(1) state per request) to use fewer blocks. This is achieved by adding new logic to `kv_cache_utils.py` for determining KV cache configurations and concurrency estimates for mixed models, including separate block pools for Mamba layers in 'none' and 'align' cache modes. The `MambaManager` in `single_type_kv_cache_manager.py` is updated to handle this compact allocation, managing its own private block pool and ensuring blocks are allocated and freed correctly without interfering with the shared attention block pool. Extensive new test cases are added to validate the correctness, efficiency, and concurrency behavior of this new allocation scheme, including regression guards for pure attention/Mamba models and specific tests for the 'none' and 'align' Mamba cache modes.

## Downstream secondary assert in `KVBlockZeroer`

One thing the #42102 port did **not** address but our config still
needed: with FP8 target KV + BF16 drafter KV (the canonical post-fix
shape for DFlash with quantized target), `KVBlockZeroer.__init__` in
`vllm/v1/worker/utils.py:155` accumulates a single `page_size_el`
across **all** AttentionSpec groups. The drafter group's BF16 pages
are 2× the size of the target group's FP8 pages, and the iteration
asserts uniformity:

```
AssertionError: Non-uniform page sizes: 827392 vs 1654784
```

This sits downstream of the partition: even after drafter and target
end up in separate KV cache groups, `KVBlockZeroer.__init__` iterates
the combined `attn_groups_iter` and sees both. It would be worth
confirming on your test matrix whether your `gpu_model_runner.py`
changes already split the zeroer's page-size tracking per-group, or
whether this is a follow-up issue.

The cheap workaround (mirrors the existing encoder-only escape hatch)
is to add isolated drafter layer names to `runner_only_attn_layers`
before constructing the zeroer:

```python
# in GPUModelRunner._init_kv_zero_meta
drafter_layers = _get_dflash_isolated_layer_names(
    self.vllm_config,
    self.compilation_config.static_forward_context.keys(),
)
self.runner_only_attn_layers |= drafter_layers
```

It's benign because the drafter's blocks come zeroed from the CuMem
pool allocator and the per-position seq_mask in
`kernel_unified_attention` prevents reads of unwritten positions. The
more correct fix is to extend `KVBlockZeroer` to track `page_size_el`
per-group; the workaround is here so the partition fix isn't blocked
on the more invasive change.
