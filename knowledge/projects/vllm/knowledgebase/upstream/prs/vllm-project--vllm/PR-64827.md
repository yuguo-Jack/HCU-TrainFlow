# [DeepSeek-V4] Warm up DeepGEMM fp8_einsum for the o_proj

[Upstream PR](https://github.com/vllm-project/vllm/pull/64827) · state: open · merged: False

## Original PR description

In summary, deepseek failed to warm up some kernels, which triggers JIT compilation in the inference will harm the quality. It has very **strong impact for production deepseek serving usecase**, because we don't want any JIT compile when actually serving a customer.

## Motivation

We found that some JIT compilation with VLLM in Production has produced harm for the performance -> JIT caused **not only slowness, but also the RPC engine failed error**, such as mentioned TP Worker hang issue in this: https://github.com/vllm-project/vllm/issues/41530.

Need to mention that, the impact of this depends on the hardware and data center setting as well which can impact the JIT compile performance. 

## Detailed purpose

DeepSeek-V4's o_proj (`deep_gemm_fp8_o_proj`) runs `deep_gemm.fp8_einsum("bhr,hdr->bhd")` with M = the attention tokens of the step. DeepGEMM picks the tile config from M at runtime and JIT-compiles a kernel for every config it hasn't seen.

Nothing warms `fp8_einsum` today:
- `wo_a` is an `is_bmm` linear, so `DeepGemmFp8BlockScaledMMKernel` deliberately doesn't register it as a `fp8_gemm_nt` warmup provider ("bmm layers bypass this kernel and run through fp8_einsum").
- `deep_gemm_warmup` covers only `fp8_gemm_nt`, the grouped contiguous GEMM and Mega-MoE.
- CUDA graph capture compiles the M ≤ 512 configs as a side effect. Any prefill chunk that lands on another config compiles on a live request.

Under DP + EP every rank waits for the compiling rank, so the whole engine stalls. On engines with slow DeepGEMM compiles, a few of these in one step exceed `VLLM_EXECUTE_MODEL_TIMEOUT_SECONDS` (300 s). That raises `RPC call to sample_tokens timed out` → `EngineDeadError`, the symptom reported in #41530.

This PR adds an `fp8_einsum` warmup to `deep_gemm_warmup`, alongside `fp8_gemm_nt`:
- **Detection:** a DeepSeek-V4 attention layer is one with an FP8 `is_bmm` `wo_a` plus the `_einsum_recipe` / `_tma_aligned_scales` that the NVIDIA backends set.
- **M values:**
  - `relax` reuses `_generate_optimal_warmup_m_values`, with N = the einsum output width, plus every M ≤ 32;
  - `full` warms every M in 1..`max_num_batched_tokens`.
- **Inputs match the runtime layout** of `fused_inv_rope_fp8_quant`: a `[T, G, D]` view over a `[G, T, D]` FP8 buffer, with TMA-aligned scales (FP32 on SM90, INT32-packed UE8M0 on SM100).
- **Progress-bar count:** warmup iterations are counted once per (weight shape, scale dtype, recipe, layout).


I put up a diagram illustrating why this would happen. It is like we want to cover missed shape for **swap** case. Following diagram illustrates how shapes are missing for the kernel.
```

M:  32   64        128  152   192        256    304 320    384         448 456    512
    |    |          |    |     |          |      |   |      |           |   |      |
----+----+----------+----+-----+----------+------+---+------+-----------+---+------+---->
         \__ hole __/            \_ hole _/
          65..127                 193..255

config staircase (steps start only at M % 16 == 1; K@x = config first seen at M=x):

    K@1   K@33  K@65   K@97  K@129 K@161 K@193  K@225 ...
    |-----|-----|------|-----|-----|-----|------|-----|---->
                   ^                        ^
                   |                        |
            BLOCK_M=48               BLOCK_M=112
            swap_ab=true             swap_ab=true
            selected only inside     selected only inside
            the hole                 the hole
                   \________________________/
                              |
                     never compiled at startup
                     ──> compiled on a live request

Root cause: the warmup models block_ms = [64, 128, 256] -- SM90's candidate list --
so it only ever emits multiples of 64 plus wave boundaries.

   what the old model assumes:   64 -------- 128 -------- 256
   what SM100 swap-A/B does:   16 32 48 64 80 96 112 128 144 ... 256
                                     ^           ^
                                   the two that were missed

Why only the swap branch is 16-granular:

   no swap:  MMA's M = block_m  ──> coarse, only 32/64/128
      swap:  D^T = B^T * A^T, so MMA's N = block_m  ──> 16-granular,
             capped at 256 by TMEM's 512 columns
             (in code: umma_n = swap_ab ? block_m : block_n)
```


## Test Plan

1. Unit tests in `tests/model_executor/test_deep_gemm_warmup.py`, all on CPU:
   - detection matches only FP8 `is_bmm` o_proj layers (not bf16, not non-bmm, not missing a recipe);
   - the `relax` M set covers M ≤ 32 plus the boundary heuristic, using N = `o_lora_rank`; `full` covers every M;
   - warmup inputs match the runtime layout (shape, stride, dtype) for SM90 and SM100, and a repeated call is a cache hit;
   - `_count_warmup_iterations` counts each einsum shape once across layers.
2. GPU check on H200 (SM90), DeepGEMM 2.6.1, DeepSeek-V4-Flash o_proj shapes (8 groups, d = 1024, r = 4096), fresh `DG_JIT_CACHE_DIR`:
   - run this PR's warmup functions verbatim with `max_tokens = 8192`;
   - then drive the real runtime o_proj path (`fused_inv_rope_fp8_quant` + `fp8_einsum`) for every M in 1..4096, and count kernels compiled after warmup.

## Test Result

1. `pytest tests/model_executor/test_deep_gemm_warmup.py`: **14 passed** (8 existing, 6 new).
2. H200:

| | einsum kernels compiled | compiles during the runtime sweep (M = 1..4096) |
|---|---|---|
| No warmup | – | **9** (configs start at M = 1, 17, 33, 65, 129, 257, 513, 641, 1025) |
| This PR (`relax`, 207 M values, 16.5 s) | 9 | **0** |

On a cold DeepSeek-V4-Flash DP4 + EP engine without this warmup, prompts of about 450–1,500 tokens compiled the 513–640 and 641–1,024 configs during serving.

Not covered here: other DeepGEMM entry points that DeepSeek-V4 also compiles at runtime (`fp8_mqa_logits` in the indexer). mHC prenorm splits are already covered on `main` by the JIT warmup registry.

### Open questions for reviewers

- **SM100 has not been tested on a GPU.** The SM100 layout (INT32-packed UE8M0 scales, recipe `(1, 1, 128)`) is covered only by the CPU layout test. The GPU validation above is H200 (SM90) only.
- **The extra M ≤ 32 values come from #49930.** On SM90 they aren't needed: `relax` already includes M = 24 and 40, which cover the config boundaries at 17 and 33. They're kept because #49930 apparently needed them on SM100, and they cost about 30 calls.
- **The fused RopeQuant path (`_fuse_rope_quant`, SM100) builds its `fp8_einsum` input differently.** It slices `o.data[:, :n_groups]`, so its strides differ from the layout this warmup uses. If DeepGEMM's JIT key depends on strides, that path may still compile at runtime; this needs a B200 check.
