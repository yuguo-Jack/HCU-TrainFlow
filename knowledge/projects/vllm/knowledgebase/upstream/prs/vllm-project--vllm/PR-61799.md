# [Bugfix][LoRA] Account for CLIP CLS rows in LLaVA tower mappings

[Upstream PR](https://github.com/vllm-project/vllm/pull/61799) · state: open · merged: False

## Original PR description

## Overview

Count CLIP's CLS token before feature selection when sizing LLaVA tower LoRA buffers and constructing per-image LoRA mappings. Related to #61608, limited to the LLaVA case.

## Claims

- Fixes LLaVA tower-LoRA profiling/startup when ten 576-embedding images require 5770 tower rows but the wrapper allocates 5760.
- Keeps connector counts and non-CLIP vision configurations unchanged.

## Validation

- Focused default/full feature-selection, zero-image and Siglip checks pass on actual imported model source; the original source fails the nonempty default-selection cases.
- Affected-file full pre-commit and commit hooks passed.

| Actual NVIDIA L20 check | Original | Changed |
| --- | --- | --- |
| Pinned `llava-hf/llava-1.5-7b-hf`, FP16 eager TP1, ten-image encoder profile | Engine initialization fails at `assert token_lora_mapping.size(0) == M` | Initializes with a 5770-row tower wrapper |
| Pretrained CLIP/projector, two nonzero synthetic rank-8 Q adapters, ten images; QKV output vs direct matrix reference | Original per-image mapping: maximum absolute error 4.7422 | Maximum absolute error 0.00391 |
| Same ten-image pretrained encoder output | Correct 5770-row mapping cannot fit original 5760-row buffer | Output shape `(10, 576, 4096)`, finite values and correct row mappings |
| 7B model, two synthetic rank-8 tower/connector adapters, ten image prompts, eight greedy tokens per prompt | Startup blocked | All requests complete; controlled batch-vs-individual run has 10/10 identical token sequences and passes the existing `check_logprobs_close` comparison |

An earlier default-mode run completed all requests with 9/10 identical greedy sequences; one result changed the order of “yellow” and “square”. That initial result is retained. These checks establish this serving/LoRA regression path, not pretrained-model accuracy improvements or general batch invariance.

GPU validation used an isolated working Python source snapshot with the exact changed LLaVA source and official native wheel `be4ce2e50545c6c1bf13f224022aeb2bcf0c0070`; a full current-main native source build was not performed. No CUDA/C++ code changes.

## Details

The language model and projector consume selected CLIP features, but the tower's linear layers process the CLS row before selection. The old hook treated both counts as the selected embedding count. Reuse the existing vision encoder and feature-selection helpers to recover the number of complete fixed-size CLIP images, then return their pre-selection tower count. No shared runner/scheduler contract changes or GPU synchronization are introduced.

Open-PR searches for the issue number, LLaVA LoRA and LLaVA CLS found no overlapping accounting fix. Related weight-renaming work and other model-specific fixes address different paths.

AI assistance was used to investigate, implement and validate this change.
