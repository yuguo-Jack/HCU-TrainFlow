# [Bugfix][Kernel] Fill K-padded output in silu_and_mul_nvfp4_quant

[Upstream PR](https://github.com/vllm-project/vllm/pull/61755) · state: open · merged: False

## Original PR description



## Overview

Fixes #48898. Under torch.compile, NVFP4 models whose per-rank MLP width K is 16 mod 32 (e.g. Qwen2.5-72B / Qwen2.5-VL-72B at TP=8, K = 3696) produce garbage once a batch has more than one token. The SiluMul+NVFP4 fusion replaces the K-padded `scaled_fp4_quant` of the CUTLASS NVFP4 linear (#42774) with `silu_and_mul_nvfp4_quant`, which ignored the padding.

## Claims

- `silu_and_mul_nvfp4_quant` fills a K-padded output the way `scaled_fp4_quant(..., padded_n=...)` does: row pitch from the output width, zero data and zero block scales in the padding.
- Compiled output matches eager again on a padded-K model (perplexity NaN → 29.45, eager 29.43).
- Unpadded outputs keep the same data and in-range scales. Kernel time stays within ±3% for M ≥ 1000 and rises by at most 0.42 µs below that.

import torch
from vllm import _custom_ops as ops
from vllm.model_executor.layers.quantization.utils.nvfp4_utils import (
    pad_nvfp4_weight_for_cutlass, swizzle_blockscale)

rows, k, n = 4, 3696, 512
x = torch.randn(rows, 2 * k, dtype=torch.bfloat16, device="cuda")
weight = torch.randn(n, k, dtype=torch.bfloat16, device="cuda") * 0.02
y = torch.empty(rows, k, dtype=torch.bfloat16, device="cuda")
torch.ops._C.silu_and_mul(y, x)
w_gs = (448.0 * 6.0 / weight.abs().amax().float()).reshape(1)
w_fp4, w_sf = ops.scaled_fp4_quant(weight, w_gs, is_sf_swizzled_layout=False)
w_sf = swizzle_blockscale(w_sf.view(torch.float8_e4m3fn))
w_fp4, pad = pad_nvfp4_weight_for_cutlass(w_fp4)
x_gs = (448.0 * 6.0 / y.abs().amax().float()).reshape(1)
alpha = 1.0 / (x_gs * w_gs)
eager = ops.scaled_fp4_quant(y, x_gs, padded_n=k + 2 * pad)
fused = ops.create_fp4_output_tensors(rows, k, y.device, True, padded_n=k + 2 * pad)
torch.ops._C.silu_and_mul_nvfp4_quant(*fused, x, x_gs)
ref = y.float() @ weight.float().T
for name, (a, a_sf) in {"eager": eager, "fused": fused}.items():
    out = ops.cutlass_scaled_fp4_mm(a, w_fp4, a_sf.view(torch.float8_e4m3fn), w_sf, alpha, torch.bfloat16)
    print(name, [round(float((out[r].float() - ref[r]).norm() / ref[r].norm()), 3) for r in range(rows)])

## Details

**Root cause.** The fused kernel writes into the buffers allocated for the padded quant: `[M, (K + 16) / 2]` data and a `torch.empty` 128x4 scale tile. It had two gaps:

1. It used K instead of K + 16 as the row pitch, so every row after the first is shifted against its scales. Single-token checks still pass.
2. It never wrote the padded scale columns and rows, which `scaled_fp4_quant` zero-fills since #53568, so the GEMM reads stale bytes. This is the stale-column failure analysed in #48898.

**Fix.** The kernel now mirrors `cvt_fp16_to_fp4`. The launcher passes the output width, the loops cover the whole padded scale tile and load zeros in the padding, and a `PADDED_OUTPUT` instantiation writes rows at the output pitch. Unpadded launches keep the old data addressing, and their tile padding is now zeroed as `scaled_fp4_quant` does. A `TORCH_CHECK` rejects a scale buffer smaller than the padded tile; every in-tree caller already allocates the full tile.

**Scope.** In practice only the down_proj input (K = intermediate size / TP) gets padded; the other quant fusions feed K = hidden size or heads × head_dim and are unchanged. Skipping the fusion for padded outputs would be simpler but would drop it on exactly these layers.

**Duplicate check.** No open PR fixes #48898. #49092 and #49093 came out of the same investigation and fix other problems. #59467 (open) rewrites this kernel to add GELU-tanh; whichever lands second carries the padded-output handling, and I can rebase this one onto it.

**CI coverage and limitations.** The kernel test needs SM100+ and is skipped on CI's L4 runners; the `(B200) Fusion and Compile` job runs the two fusion tests. I validated on SM120 only, with a CUDA 13.4 build (16-element path; the 8-element path of CUDA < 12.9 builds has the same change but was not run). The model-level check used the narrowed 0.5B model on one GPU, not a TP=8 72B deployment.
