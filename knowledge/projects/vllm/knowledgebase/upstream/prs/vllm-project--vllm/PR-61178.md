# [Perf][Attention] FlashInfer prefill for DiffKV attention on SM12x

[Upstream PR](https://github.com/vllm-project/vllm/pull/61178) · state: open · merged: False

## Original PR description



## Overview

On SM12x (RTX 50 series, RTX PRO 6000, DGX Spark/GB10) there is no FA3/FA4, so
DiffKV models (K/V head sizes differ; MiMo-V2: 192/128) run every attention
step on `TRITON_ATTN_DIFFKV`.

This PR adds `TRITON_FLASHINFER_DIFFKV`, built with the existing
`create_composite_attention_backend`. It routes batches that contain a prefill
on plain causal full-attention layers to FlashInfer's paged prefill
(`head_dim_vo`), using the same packed cache. Decode-only and
verification-only batches, and all CUDA graph capture and replay, stay on
`TRITON_ATTN_DIFFKV`.

Related:
- #58177 and #59673 optimize the Triton DiffKV kernel. They are complementary
  and are benchmarked against below.
- #59052 pins Triton DiffKV to `UNIFORM_BATCH` CUDA graphs, the same support
  level this composite reports.
- #46963 also uses FlashInfer prefill on SM12x.

## Claims

All on DGX Spark (GB10, SM121), MiMo-V2.6-Flash.

- **Prefill attention, one full-attention layer at TP2,** vs Triton DiffKV with
  #58177 + #59673 applied. Cold-L2 CUDA-graph timing; `plan()` host time is
  reported separately below.
  - 2.27–2.29× for 512+-token chunks over a 32K prefix;
  - 2.17× for a fresh 8K chunk, 1.84× fresh 2K, 1.24× fresh 512;
  - 3.07× for 64 tokens and 6.41× for 17 tokens over a 32K prefix;
  - slower for fresh chunks of ≤64 tokens: 0.45–0.83×, i.e. 1.2–3.6 µs per
    layer.
- **End to end on the PR base** (main `18c19eaf2` with and without this PR):
  cold-prefill TTFT at 96K tokens goes from 72.3 s to 40.6 s (**1.78×**);
  1.46× at 48K, 1.23× at 24K.
  - Single-request decode is unchanged.
  - Fresh 23–34-token prompts are 2–6 ms slower at p50 (1–4%); 66–515-token
    prompts are 4–10 ms faster.
- **Accuracy:** no observed degradation in gsm8k or full-vocabulary logprobs.
- **Cost:** on this configuration the KV cache is 0.59 GiB smaller (6.6% fewer
  tokens), mostly from FlashInfer's workspace (details below).
- **Off switch:** `VLLM_DIFFKV_FLASHINFER_PREFILL=0` restores
  `TRITON_ATTN_DIFFKV` for every layer.

## Details

### Selection

`MiMoV2Attention` keeps its order: FA DiffKV when FA3/FA4 is usable, then
`TRITON_FLASHINFER_DIFFKV`, then `TRITON_ATTN_DIFFKV`. The new backend is
auto-selected only when all of these hold:
- CUDA, compute capability 12.x, FlashInfer present;
- full attention: no sliding window, no sinks;
- FP16/BF16 compute with a 16-bit KV cache;
- head sizes (192, 128), the only pair tested.

It is also selectable with `--attention-backend TRITON_FLASHINFER_DIFFKV`.

### Routing

- FlashInfer when the batch's longest query exceeds
  `max(16, max_decode_query_len)`; Triton otherwise, and for image-prefix
  batches.
- Decode or verify rows that share a batch with a prefill run on FlashInfer
  with it.
- `capture_variant = 0`. The threshold is never below the uniform
  decode/verify width, so CUDA graph replay always selects Triton.
- A KV cache group containing any layer FlashInfer does not cover (window,
  sinks, ALiBi, soft-cap, FP8 KV) always uses Triton.
- The 16-token floor is not tuned for fresh prompts. Over a cached prefix,
  FlashInfer wins from 17 tokens; fresh prompts break even around 64 tokens.

### Metadata

- `plan()` runs once per step in the builder, shared by every layer in the
  group.
- As in `FlashInferMetadataBuilder.build`, the query offsets, page offsets,
  last-page lengths and an explicit `seq_lens` are staged in pinned memory, so
  `plan()`'s non-blocking copies stay asynchronous.
- The builder reuses `_copy_page_indices_kernel` and joins the composite's
  workspace sharing.

### Host sequence lengths

- `seq_lens_cpu_upper_bound` is exact for prefill rows, and for all rows
  without speculative decoding, so those batches never read back from the
  GPU.
- A batch with a row that may be a spec-decode row (query length ≤
  `max_decode_query_len`) reads exact `seq_lens` back inside
  `gpu_sync_allowed()`. That row's upper bound assumes every draft was
  accepted, and FlashInfer needs exact lengths.
- Without async scheduling the bound is often exact too. That is not used,
  because MRV2 adaptive verification also makes per-row token counts an upper
  bound.

### Cache and FlashInfer path

- The FlashInfer child subclasses the Triton DiffKV backend, so both share one
  cache spec and tensor. K/V are passed as last-dim strided views of the
  packed cache, in HND or NHD physical layout, with or without layer
  interleaving.
- The call is `BatchPrefillWithPagedKVCacheWrapper(workspace, "HND")` with
  `plan(..., head_dim_vo=128, causal=True, seq_lens=...)`; the wrapper
  resolves to the `fa2` backend on SM12x.
- The SM120 fused 192×128 kernels reported unreachable in the 0.6.18/0.7.0
  wrappers are not used.
- **JIT build on 0.7.0.post1.** The aarch64 `flashinfer-jit-cache` wheel is a
  stub that depends on per-architecture packages vLLM does not install, so the
  192/128 module is JIT-built on first use: 19 s in isolation. In serving it
  completes during startup; the first long prompt after a restart was not
  measurably slower.

### Memory

- **Workspace.** It is sized like the FlashInfer backend's:
  `max(VLLM_FLASHINFER_WORKSPACE_BUFFER_SIZE, tokens × heads × head_dim × 16)`.
  With this config's 2048-token budget, that resolves to the 394 MB default.
- **KV cache.** On the PR base, KV cache memory went from 19.01 to 18.42 GiB
  (1,428,918 → 1,335,006 tokens).
- **Possible follow-up.** A smaller floor for this prefill-only use could
  recover most of it. It is not changed here: FlashInfer errors rather than
  grows when the workspace is too small, and the default is the same one the
  FlashInfer backend uses.

### Why decode and CUDA graphs stay on Triton

- Decode is bandwidth-bound with short queries. Triton DiffKV already has
  2D/3D split-KV paths for it, and measured decode was unchanged.
- Only Triton is captured. Moving decode/verify-only batches to FlashInfer
  needs a graph-safe DiffKV decode/verify plan (persistent buffers,
  `fast_plan`), which is a separate change.
- **Cost.** The composite reports `UNIFORM_BATCH` instead of `ALWAYS`.
  - Under the default `FULL_AND_PIECEWISE`, uniform decode still runs as full
    graphs, and mixed batches already ran piecewise.
  - Only `cudagraph_mode=FULL` with mixed batches loses full graphs on these
    layers.

### Complexity

About 460 new lines in one new backend file, plus small edits:
- selection: 18 lines in `mimo_v2.py`;
- the env var;
- the registry entry;
- docs.

There are no changes to the model runner, scheduler, KV cache manager or the
Triton kernel.
