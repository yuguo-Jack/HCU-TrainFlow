# Added SVE128 and SVE256 support to vectorizer backend. 

[Upstream PR](https://github.com/vllm-project/vllm/pull/50573) · state: open · merged: False

## Original PR description

Added Sleef to SIMD and SVE builds. Added AOR er function.

Co-authored-by: GPT 5.6 sol

## Purpose

Enabled sleef for SIMD, SVE-128 amd SVE-256. 
Added SVE-128 and SVE-256 support to the vectorizer backend. SIMD, SVE128 and SVE256 targets are all built and the appropriate one loaded at runtime.
Added a new wrapper PartialVectorizedRegWrapper to handle the half-width vectorized types for sve256. Could remove this support as the types are unused.
Added sve fast exp support to match current macro usage in SIMD.
Added AOR er implementation for SVE as PyTorch with Sleef uses a large general code path when values are > 2.5, so it's less performant than the compact approximation used by ASIMD (in PyTorch sleef is explicitly bypassed for ASIMD erf()).

### Improvements from enabling SVE-256 (with sleef)
Comparing the performance of sve256 to simd we see significant improvements across 61 ops.
No need here for the AOR tanh implementation as the pytorch implementation for sve256 is already very well optimised.
We do need the er() AOR implementation as Sleef uses a large general code path when values are > 2.5, so it's less performant than the compact approximation used by ASIMD (in PyTorch sleef is explicitly bypassed for ASIMD erf()).
We see significant regressions to the performance of the vec types that only use half the vector width: FP32Vec4, BF16Vec8 and FP16Vec8, but we don't care about these (they are not used in vLLM).
The only remaining regression is in another noisy abs() benchmark (< 3 ns).

We can either try to fallback to vllm._C when vllm._C_SVE failed, or we can always build vllm with vllm._C_SVE as well and let cpu.py pick the correct extensions like it's doing now.
