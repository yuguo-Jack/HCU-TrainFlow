# [Kernel] Scale swigluoai_and_mul and situ_and_mul launches with the device

[Upstream PR](https://github.com/vllm-project/vllm/pull/61560) · state: closed · merged: False

## Original PR description

## Overview

`swigluoai_and_mul` (GPT-OSS) and `situ_and_mul` (Kimi) launch `grid(num_tokens)` with one
block per token and stride that block over the hidden dim, so one token is one block
whatever the hidden size. They have the same shape as the `act_and_mul` family, so they
can reuse the launch helper from #61404.

**Stacked on #61404**, which introduces `vllm_elementwise_launch_config()`. The commit
here is 17 lines; please merge #61404 first.

## Claims

- Up to 7.05x on `situ_and_mul` and 4.36x on `swigluoai_and_mul` at decode-sized batches;
  median 1.58x over 108 shapes.
- Unchanged where the batch already fills the device: slowest case 0.98x.
- Output is bit-identical to the unpatched kernels on every tested shape.
- No API change, no new helper, 17 lines in one file.

## Validation

Bitwise: 108 shapes (both kernels, bf16 and fp16, hidden 4096 / 14336 / 28672, 1 to 2048
tokens) compared by SHA-256 of the raw output bytes against the unpatched build.

Performance, MI355X (gfx950, 256 CUs), ROCm 7.2.4, HIP-graph replay, minimum of 3 runs:

| kernel | shape | before | after | |
|---|---|---|---|---|
| `situ_and_mul` | d=28672, 1-2 tokens | 14.9-15.3us | 2.1-2.2us | **7.0x** |
| `situ_and_mul` | d=28672, 8 tokens | 15.5us | 2.5us | 6.2x |
| `swigluoai_and_mul` | d=28672, 1 token | 9.0us | 2.1us | 4.4x |

Median over all 108 shapes: 1.58x. The five slowest cases are all large-batch, where the
configuration is unchanged by construction: 0.98x to 0.99x.

## Details

**Root cause.** `grid(num_tokens)` is as wide as the batch, not as wide as the device. At
one token these kernels put a single block on 256 CUs.

**Change.** Both take `vllm_elementwise_launch_config()`, which returns the previous
configuration once `num_tokens >= sm_count` and otherwise splits a token's work across
`chunks` blocks in `gridDim.y`. The kernels' loops become `gridDim.y`-aware, with the
stride hoisted out of the loop body.

`situ_and_mul` gains the most because its loop is scalar, so it had no other source of
parallelism within a token.

**Scope.** Not every `grid(num_tokens)` kernel can take this helper. It fits kernels whose
loop strides over the hidden dim, where any `(threads, chunks)` split is valid. It does
*not* fit kernels that give each `blockIdx.y` a contiguous chunk and vectorize inside it —
there, a small chunk leaves too few elements per thread to form a wide load. Both kernels
here are the first kind.
