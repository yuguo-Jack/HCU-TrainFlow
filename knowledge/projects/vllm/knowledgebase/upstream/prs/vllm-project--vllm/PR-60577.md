# [Perf][Model] Gemma 4: remove trailing image padding to enable FlashAttention in vision SDPA

[Upstream PR](https://github.com/vllm-project/vllm/pull/60577) · state: open · merged: False

## Original PR description

## Summary

Gemma 4's image processor pads every image to `max_soft_tokens × 9` patches. The padding is represented by a trailing block at `(-1, -1)`, which the Hugging Face vision tower converts into a boolean attention mask.

When an attention mask is present, PyTorch SDPA cannot use the FlashAttention backend and falls back to the memory-efficient backend. On RTX 5090 with this shape, that is about 3.6× slower per attention call.

This PR removes the trailing padding before the vision encoder, allowing SDPA to select FlashAttention, then pads the encoder output back to the processor's original length before pooling.

The change is 35 lines in `gemma4_mm.py` and does not add a new kernel.

## Performance

On an RTX 5090 with `nvidia/Gemma-4-26B-A4B-NVFP4` (main 08567505b0 + this diff only; `gemma4_mm.py` and the test file are identical to the PR base 0f112d1800; `--kv-cache-dtype fp8`, TRITON_ATTN, marlin MoE):

| Prompt                                                                    |       main |         PR |          Δ |
| ------------------------------------------------------------------------- | ---------: | ---------: | ---------: |
| 1 image @280 (default), TTFT                                              |    74.3 ms |    57.1 ms | **−23.2%** |
| 16 images, mixed sizes @280, TTFT                                         |    1019 ms |     747 ms | **−26.7%** |
| 16 images @70, TTFT                                                       |     221 ms |     206 ms |  **−6.8%** |
| 46 images @560 (~25k tokens), TTFT                                        |    7703 ms |    5022 ms | **−34.8%** |
| `vllm bench serve`, 6 images/request @560, max-concurrency 1, median TTFT |     942 ms |     592 ms | **−37.2%** |
| Same benchmark, throughput                                                | 1.01 req/s | 1.56 req/s |   **+54%** |

The two server runs for each arm differed by ≤1%. The prompts used different images, so they did not hit prefix or encoder cache.

Decode TPOT was unchanged (see Additional validation).

### Why does removing a small amount of padding help so much?

The padding itself is only 5–7% of the rows in the ChartQA inputs, but the mask changes the SDPA backend.

Microbenchmark: B=1, 16 heads, head_dim=72, bf16, sm_120, torch 2.13+cu132.

| SDPA input                           |     Time | Kernel                                      |
| ------------------------------------ | -------: | ------------------------------------------- |
| 5040 padded + boolean mask           | 2.541 ms | `fmha_cutlassF_bf16_aligned_64x128_rf_sm80` |
| 5040 padded, no mask                 | 0.741 ms | `pytorch_flash::flash_fwd_kernel`           |
| 4788 after removing padding, no mask | 0.706 ms | `pytorch_flash::flash_fwd_kernel`           |

Forcing FLASH with the mask fails with `No available kernel`. Forcing cuDNN with the mask works, but on the 46-image prompt it gives −19.5% TTFT, compared with −34.8% for this PR.

The same per-call measurement was repeated on a second RTX 5090 from inside `_process_image_input`: 2.709 ms for memory-efficient attention vs. 0.713 ms for FlashAttention.

On ChartQA, 100% of images contain padding at `max_soft_tokens=280` and 99.9% at 560, so the change applies to almost every image. Since the padding is only 5–7% of the rows, the gain comes from the kernel switch (first vs. second row above), not from processing fewer rows (second vs. third row).

## Correctness

The transformation preserves the semantics of the padded encoder path:

1. For the valid rows, attention over padded inputs with a mask is equivalent to attention over only the valid rows.
2. The resulting hidden states are padded back with zeros to the original processor length.
3. The pooler therefore sees the same shape, `output_length`, and position IDs as on `main`.
4. The pooler masks padded rows to zero before pooling, so the restored padding does not contribute.

A float64 comparison over three images with different valid lengths, plus an equal-length case, produced matching per-image embeddings with `atol=1e-12`, with and without memory-based chunking.

The implementation also leaves inputs unchanged when there is no trailing padding or when padding is not at the end.

## Tests

On CPU:

```text
VLLM_TARGET_DEVICE=cpu python -m pytest tests/models/multimodal/processing/test_gemma4.py -q

36 passed in 72s
```

Six new tests (`-k "strip_trailing_padding or image_unpadding"`):

`test_gemma4_image_unpadding_matches_padded_encoding` runs `_process_image_input` on a tiny HF `Gemma4VisionModel` in float64, checks that the encoder saw the unpadded lengths, and verifies that the unpadded path produces the same embeddings as the masked padded path.

`test_strip_trailing_padding` covers:

* trailing padding
* no padding
* padding that is not trailing

Mutation checks were also performed (an off-by-one in the slice, returning `None` as the padded length, and dropping the leading valid-block check); each mutation caused at least one test to fail.

## Quality evaluation

ChartQA test set: 2500 questions (1250 human / 1250 machine), one image per question, greedy decoding.

For each setting, four engine processes were run with the same prompts and ordering:

* `main_a`
* this PR
* a cuDNN-with-mask variant
* `main_b`, a second identical `main` process used as a noise floor

The evaluation uses paired relaxed accuracy, mean NLL of the correct answer from `prompt_logprobs`, 95% confidence intervals, and exact McNemar tests, all against `main_a`.

| Setting | Comparison           | Changed answers |            Δ accuracy |    p |     Δ NLL ± SE |
| ------- | -------------------- | --------------: | --------------------: | ---: | -------------: |
| 280     | `main_b` noise floor |             206 | +0.44 (−0.26 … +1.14) | 0.26 | −0.004 ± 0.010 |
| 280     | **this PR**          |             241 | +0.04 (−0.72 … +0.80) | 1.00 | +0.009 ± 0.013 |
| 280     | cuDNN + mask         |             230 | +0.44 (−0.21 … +1.09) | 0.23 | +0.015 ± 0.013 |
| 560     | `main_b` noise floor |             165 | −0.08 (−0.67 … +0.51) | 0.89 | +0.000 ± 0.008 |
| 560     | **this PR**          |             189 | −0.44 (−1.09 … +0.21) | 0.23 | −0.008 ± 0.010 |
| 560     | cuDNN + mask         |             191 | −0.48 (−1.12 … +0.16) | 0.18 | −0.010 ± 0.010 |

At 560, the accuracy estimate is −0.44 points with a 95% CI of −1.09 to +0.21 and p=0.23. The NLL of the correct answer does not increase. The cuDNN-with-mask variant has a point estimate of the same sign.

Across both settings, the combined accuracy difference is −0.20 points (95% CI −0.70 … +0.30), with combined NLL difference +0.0002 ± 0.008.

The evaluation rules out a regression of roughly 1 point or more and rules out an NLL regression, but it does not rule out a smaller accuracy effect below 1 point.

The second identical `main` process itself differed on 6.6–8.2% of answers. The PR differed on 9.6% / 7.6% of answers at 280 / 560, roughly one percentage point above that noise floor and similar to the cuDNN-with-mask variant (9.2% / 7.6%).

The PR's disagreement rate does not grow with the fraction of padding removed (at 280, bins of 2–4 / 4–9 / 9–10% padded rows: 9.9 / 9.5 / 10.5% for the PR vs. 6.9 / 8.3 / 8.6% for the noise floor). The answers that flip are largely the same borderline items for the PR, the cuDNN variant, and `main_b` (at 560: 24 shared between the PR and cuDNN, 15 between the PR and `main_b`; ~1 expected if independent).

## Scope and limitations

* Measurements were performed on one GPU (RTX 5090, sm_120) and one checkpoint.
* The masked path forces SDPA onto the memory-efficient backend on GPUs where SDPA would otherwise select FlashAttention. The performance benefit on other GPU architectures has not been measured.
* The `cudagraph_mm_encoder` path is disabled by default and retains the mask, so it does not benefit from this change.
* MM-LoRA, video frames, and images without padding are unchanged.
* `_strip_trailing_padding` performs one host read per image (the valid count and the leading-valid count are combined into a single `.tolist()`). This is executed inside `gpu_sync_allowed()`, as are the existing encoder and pooler calls in the same function that already synchronize in the HF mask construction path.
* Because encoder buckets are keyed by true sequence length, images of different sizes no longer share the same encoder batch. A 16-image mixed-size prompt was still faster with this change, and profiling showed batch size 1 for the encoder in both arms.

## Compatibility with related work

This change is compatible with #60478.

#60478 changes the pooling path by batching according to sequence length and fusing norm/RoPE, while this PR removes the mask before the encoder and restores the original sequence length before pooling. The restored hidden states therefore remain compatible with the batching logic in #60478.

The two changes touch adjacent code and can be rebased together.

A search of open PRs/issues on 2026-10-08 did not find another open change that modifies the Gemma 4 vision attention/mask path in the same way.

## Additional validation

An earlier run of the same diff on main 956960f85f (with two unrelated local patches outside the vision path, identical in both arms) gave the same 46-image TTFT (−34.8%). Its profile of one 46-image prompt showed:

* `main`: 1242 memory-efficient attention calls, 3382 ms
* PR: 0 memory-efficient calls, 1242 FlashAttention calls, 878 ms
* total GPU kernel time: 7107 ms → 4445 ms

TPOT decode at ~26k context was unchanged in the same run (−0.1% / −0.2% for c1 / c8).

The final clean-tree runs also verified the kernel identity separately for each process: `main` used the memory-efficient kernel, while the PR used FlashAttention.

GPU synchronization checks with `VLLM_GPU_SYNC_CHECK=error` and `=warn` reported no unexpected synchronization. As a positive control, removing the `gpu_sync_allowed()` wrapper caused the expected `RuntimeError: GPU<->CPU sync detected` at the new host read.

Vision embedding differences were also compared against the difference caused by changing attention backends. For 48 images in bf16, median relL2 was:

* PR vs. main: `4.7e-02`
* FlashAttention vs. cuDNN on the same unpadded input: `4.9e-02`

This is consistent with the observed bf16 sensitivity of the vision tower to the attention backend.
