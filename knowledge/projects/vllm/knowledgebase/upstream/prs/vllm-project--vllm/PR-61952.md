# [Perf][GDN] Capture the GDN core in breakable CUDA graphs of mixed batches (CUDA graph 2/2)

[Upstream PR](https://github.com/vllm-project/vllm/pull/61952) · state: open · merged: False

## Original PR description



## Overview

Capture the Qwen GDN core in the breakable CUDA graphs of mixed (prefill + decode) steps, instead of running it as an eager break in every GDN layer. This is the second of two PRs and is stacked on #61779 (persistent padded mixed-batch metadata and static-grid GDN prefill kernels); only the last 5 commits are new here. It also works with prefix caching (Mamba `align` mode).

On an 8 × A100 hybrid model deployment it cuts the mixed-step host time from 99 to 55 ms and gives TPOT P50 −9 to −10 % and requests/s +4 to +7 % at 32 concurrent agentic sessions. Related: SGLang issue [#35851](https://github.com/sgl-project/sglang/issues/35851) (same per-layer break cost).

## Claims

- Inside a breakable PIECEWISE capture, the GDN core ops (`qwen_gdn_attention_core`, `qwen_gdn_attention_core_fused_norm_packed`) are captured into the current graph segment when the static form applies; otherwise they break as before.
- The captured core (`_forward_core_static`) is branch-free. It reads only persistent capture buffers at full length and sizes every grid by the graph's token count and `max_num_seqs`, so one graph replays correctly for any batch padded to that count: spec decodes, non-spec decodes, prefills, any mix, zero-length rows. Pad rows write only the null state block and a scratch output row.
- With prefix caching, `mamba_cache_mode="align"` is supported when the Mamba spec has no internal prefill checkpoint blocks (`num_prefill_checkpoint_blocks == 0`); otherwise the core breaks as before.
- Speed on current main (nightly 335dd77b09, Qwen3.8-Flash-Next-FP8, 8 × A100, agentic workload, 8 sessions): TPOT P50 −11 %, P95 −15 %; TTFT P50 −20 %; output tok/s +8 % (two pairs in opposite arm orders; table below).
- FULL decode steps skip the capture-buffer staging, because a FULL replay never reads those buffers (last commit). This cuts the staging host cost from about 5 % to 0.4 % of worker samples at 8 sessions.
- No change: the eager forward, FULL decode graphs, FlashInfer / CuteDSL / AITER FlyDSL / XPU / ROCm paths, the V1 runner. No new host sync.

## Details

**Motivation.** In mixed steps the GDN core runs as an eager break between graph segments because its metadata and grids change every step. On the deployment above that is 36 breaks per step, 55.2 ms of host time and 720 of 1,348 launches. Removing Python-level indexing alone (#61034) did not change the step (99.3 vs 99.6 ms), so the launches themselves must go into the graph.

**Design.**
- `eager_break_during_capture(capturable=...)`: a per-call predicate; an accepted call runs inline and is captured. `BreakableCUDAGraphCapture.run_uncaptured(fn)` runs a warm-up between two segments without recording it, so Triton compiles and autotunes outside the capture.
- Builder: `captures_mixed_batches` (breakable PIECEWISE graphs, MRV2, CUDA, Triton/FLA backend, base builder, no internal prefill checkpoint blocks). Then every batch is staged into the persistent buffers of #61779 at full length (`GDNAttentionMetadata.capture_buffers`), because the graph of a token count replays for every batch padded to it. Two capture-only cu_seqlens describe the non-spec rows as one token stream with the peeled decodes first.
- Layer: one static path. The spec part runs on `max_num_seqs` padded rows like FULL decode; the non-spec conv uses `num_programs`; the decode peel uses zero-length pads; the FLA chunk uses `use_graph=True` and absolute cu_seqlens; the output merge is a fixed-length `index_copy_` into a scratch row.
- `build_for_cudagraph_capture` keeps its decode-only check: PIECEWISE capture metadata comes from `build()`, and no static grid depends on the capture batch. FULL mixed graphs (`AttentionCGSupport.ALWAYS`) are out of scope.

**Trade-offs.**
- GPU work per mixed step rises about 10–15 % at the same prefill size: the GDN core now runs at the graph's padded token count. The host saving is larger, so the step is still faster.
- Capture memory: the gathered SSM states of `max_num_seqs` rows plus FLA workspaces of `cdiv(T, 64) + max_num_seqs - 1` chunks, in the graph pool. Measured on the deployment: 1.73 GiB of graph memory per GPU against 1.41 GiB without.

**Limitations.**
- A batch with only non-spec decodes that replays a PIECEWISE graph runs `causal_conv1d_fn` instead of `causal_conv1d_update`; a spec-only batch on the fused-norm op runs the Triton spec kernels instead of the fused CUDA MTP kernel. Both are correct, but not bitwise identical to eager.
- Every PIECEWISE or eager step stages about 12 more small device copies when the static form is enabled. FULL decode steps skip them.
- Internal Mamba prefill checkpoints (#60050, #60659) and capture are exclusive for now: with checkpoint blocks the core breaks as before. A static checkpoint export inside the captured segment is possible but out of scope. #60659 also writes split metadata into the chunk-index buffers that #61779 makes persistent; whichever lands second must keep the split metadata separate.

**Size:** +492 / −17 outside tests (`qwen_gdn_linear_attn.py` +275, `gdn_attn.py` +180, `breakable_cudagraph.py` +40, `mamba_hybrid.py` +6); tests +666.
