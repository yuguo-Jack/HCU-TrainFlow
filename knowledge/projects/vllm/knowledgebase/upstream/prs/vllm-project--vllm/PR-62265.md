# [Bugfix][Attention] Let b12x pick its default KV block size

[Upstream PR](https://github.com/vllm-project/vllm/pull/62265) · state: closed · merged: True

## Original PR description

## Overview

`--attention-backend b12x` fails at startup unless `--block-size 64` or `128` is also passed:

```
ValueError: b12x requires --block-size in (64, 128), got 16.
```

The backend already declares its supported and preferred block sizes, but the impl rejected the default 16 before the platform could apply the preferred one. This removes that check and adds a regression test. Fixes #62264.

## Claims

- The documented command (`vllm serve <model> --attention-backend b12x`, see docs/design/attention_backends.md) now starts. vLLM picks block size 128 on its own and logs `Setting kv cache block size to 128 for B12X backend(s).`
- Explicit `--block-size 64` / `128` behave as before.
- An unsupported explicit size (e.g. `--block-size 16`) is still rejected, now at backend selection: `Selected backend B12X is not valid for this configuration. Reason: ['block_size not supported']`.
- No change outside the b12x impl; one check removed, one test added.

## Validation

DGX Spark (GB10, sm_121, aarch64), CUDA 13.0, torch 2.14.0+cu132, flashinfer-python 0.7.2 (provides the `b12x` module), vLLM main @ f98ae6a9f.

```python
from vllm import LLM
LLM("Qwen/Qwen3-0.6B", attention_config={"backend": "B12X"})
```

| `block_size` | before | after |
|---|---|---|
| not set | `ValueError` from the impl constructor | starts, block size 128, generates |
| 64 | ok | ok |
| 16 | same `ValueError` | rejected at backend selection with `block_size not supported` |

Greedy outputs of the default run are token-identical to the FLASH_ATTN backend on the same prompts (4 short prompts and a 13k-token prompt).

```
$ pytest tests/v1/attention/test_b12x.py
41 passed in 109.45s   # DGX Spark, GB10
```

The new test fails on main with the original `ValueError` and passes with this change. `pre-commit run --files ...` is clean.

CI note: the b12x tests only run where the b12x module and an SM120/SM121 GPU are present and skip elsewhere, like the existing GPU tests in that file.

## Details

Ordering problem:

1. When the user does not pass `--block-size`, `Platform.update_block_size_for_backend()` replaces the default 16 with the backend's `get_preferred_block_size()` (128 for b12x).
2. That hook runs after `load_model()` in every executor, because it discovers the backends from the model's attention layers.
3. `B12xPagedAttentionImpl.__init__` runs inside `load_model()`, read `cache_config.block_size` while it was still 16, and raised. The preferred size was unreachable.

Removing the check instead of moving it: an unsupported user-specified size is already rejected during backend selection (`validate_configuration` -> `supports_block_size`, applied only when `cache_config.user_specified_block_size` is set), the hybrid and skip-layer alignment paths both end in `_check_aligned_block_size`, and at runtime the impl reads the page size from the KV cache tensors (`_kv_page_size`) and already prepares plans for every supported size. So there is no path left on which an unsupported page size reaches the kernel. The existing tests pass `block_size=64/128` explicitly, which is why this was never hit.

Not a duplicate: no open issue or PR mentions this (`gh search issues/prs --repo vllm-project/vllm "b12x block-size"`); the open b12x PRs (#54976, #54669, #54719, #55405) are about MoE/MLA selection.

I found this while testing attention backends on my DGX Spark. I used Claude Code to help trace the root cause and run the validation; I reviewed every changed line and ran the tests myself.
