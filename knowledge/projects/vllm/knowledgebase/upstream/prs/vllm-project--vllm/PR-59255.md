# [ROCm] Enable expert parallelism for AITER Triton W4A16 MoE

[Upstream PR](https://github.com/vllm-project/vllm/pull/59255) · state: closed · merged: True

## Original PR description

## Purpose

Enable expert parallelism for the AITER Triton W4A16 monolithic MoE (`AiterW4A16ExpertsMonolithic`, `--moe-backend aiter_triton_mxfp4_bf16`). Previously `expert_map` was dropped, so under `--enable-expert-parallel` the kernel indexed the rank-local weight shard with global expert ids (memory-access fault), and the backend was rejected for EP.

- Pass `expert_map` to both `moe_gemm_a16w4` calls, plus a per-gate `gate_valid` mask built from `routing_data.topk_ids`, so non-local gates are skipped in the combine (ROCm/aiter#5863, included in the pinned v0.1.25).
- `_supports_parallel_config`: allow naive EP; still reject all2all and EPLB.
- Works with DeepSeek-V4 hash routing (#60282): `routing_from_hash` also returns `topk_ids`.
- gfx1250 SILU falls back to an a8w4 kernel without `expert_map` support, so it now raises under EP instead of faulting.
- Drop the duplicate `hash_kwargs` block left in `FusedMoEKernelMonolithicImpl.apply` after #58800 and #60282 both landed.

Not a duplicate: no other open PR enables EP for this backend.

## Test

UTs (MI355X, `vllm/vllm-openai-rocm:nightly`, ROCm 10, aiter 0.1.25):
- `tests/models/quantization/test_gpt_oss.py -k "expert_parallel or padded_rows"`: 8 passed. The new `test_aiter_w4a16_moe_expert_parallel_matches_full` (EP 2/4) checks that per-rank outputs sum to the full MoE output; it fails if `gate_valid` is dropped.
- `tests/kernels/moe/test_topk_softplus_sqrt.py -k "selection or hash"`: 662 passed. The new `test_aiter_w4a16_expert_parallel_selection` covers naive EP accepted on hash layers, EPLB and all2all rejected.

E2E, MI355X TP8 `--enable-expert-parallel`, ISL/OSL 1024/1024, output tok/s at conc 1/8/32/64/128, gsm8k 5-shot (200, flexible-extract):

| Model | Backend | tok/s | gsm8k |
|---|---|---|---|
| gpt-oss-120b (16/128 experts per rank) | `aiter_triton_mxfp4_bf16` (this PR) | 263 / 1321 / 3748 / 5778 / 8681 | 0.920 |
| gpt-oss-120b | `triton` | 180 / 1185 / 3499 / 5286 / 7545 | 0.905 |
| DeepSeek-V4-Pro (48/384) | `aiter_triton_mxfp4_bf16` (this PR) | 63 / 309 / 649 / 908 / 1277 | 0.940 |
| DeepSeek-V4-Pro | `triton_unfused` | 59 / 356 / 883 / 1258 / 1684 | 0.935 |

Prompt NLL vs baseline: gpt-oss 2188.3 vs 2185.9, DeepSeek-V4-Pro 1237.0 vs 1232.6 (1.6k-token passage).

DeepSeek-V4 EP is correct but slower than `triton_unfused` at conc ≥ 8: routing is still global, so the grid covers all 384 experts and most tiles early-exit. A follow-up will build local routing metadata.

gfx942 (MI300X) validation, TP8 `--enable-expert-parallel`, same ISL/OSL + gsm8k setup. DeepSeek-V4-**Flash** here, since V4-Pro's 863 GB does not fit this box:

| Model | Backend | tok/s | gsm8k |
|---|---|---|---|
| gpt-oss-120b (16/128 experts per rank) | `aiter_triton_mxfp4_bf16` (this PR) | 243 / 883 / 2099 / 3127 / 4449 | 0.880 |
| gpt-oss-120b | `triton` | 67 / 687 / 1937 / 3057 / 3965 | 0.905 |
| DeepSeek-V4-Flash (32/256) | `aiter_triton_mxfp4_bf16` (this PR) | 87 / 402 / 920 / 1335 / 1924 | 0.970 |
| DeepSeek-V4-Flash | `triton_unfused` | 42 / 405 / 976 / 1460 / 1908 | 0.955 |

All arms boot fault-free under EP (the pre-fix `_moe_gemm_a16w4` memory-access fault is gone) and generate coherently. gpt-oss `aiter_triton_mxfp4_bf16` beats `triton` at every concurrency (3.6× at conc 1, +12% at conc 128); gfx942 has no CK W4A16 backend, so this is its only performant EP MoE. DeepSeek-V4-Flash shows the same global-routing regression at conc 32–64 noted above. gsm8k is within run-to-run noise (±0.02 at limit 200).
