# [Rust Frontend] Report error type and code like Python

[Upstream PR](https://github.com/vllm-project/vllm/pull/62663) · state: closed · merged: True

## Original PR description

## Overview

Python's error body is an `ErrorInfo` (`vllm/entrypoints/serve/engine/protocol.py`): `type` names the error class and `code` is the HTTP status as an integer. The Rust frontend sends OpenAI-style types (`invalid_request_error`, `server_error`) and string codes (`"model_not_found"`, `"engine_paused"`, `"403"`). A client that switches frontends sees a different `type` for the same failure, and one that reads `code` as an integer, as Python's schema declares it, cannot parse Rust errors. This PR reports Python's class names and integer status codes.

## Claims

Every Rust error response, including streaming `data: {"error": ...}` events, now matches Python's shape:

| Rust error | Status | `type` before → after | `code` before → after |
|---|---|---|---|
| invalid request | 400 | `invalid_request_error` → `BadRequestError` | `"invalid_request_error"` → `400` |
| body fails to parse | 400 | `invalid_request_error` → `Bad Request` | `"json_parse_error"` → `400` |
| unknown model | 404 | `invalid_request_error` → `NotFoundError` | `"model_not_found"` → `404` |
| profiler already active | 409 | `conflict_error` → `Conflict` | `"conflict_error"` → `409` |
| internal error | 500 | `server_error` → `InternalServerError` | `"server_error"` → `500` |
| retryable engine rejection | 503 | `service_unavailable_error` → `ServiceUnavailableError` | engine code, e.g. `"engine_paused"` → `503` |
| disabled scale-out route | 403 | `PermissionDeniedError` (unchanged) | `"403"` → `403` |

## Details

The classes follow `create_error_response` (`serve/exception_handling/error_response.py`). A body that fails to parse into the request model goes through FastAPI's validation handler in Python, which reports the status phrase `Bad Request`, so Rust's `JsonParseError` does the same. Python has no class for 409; like its `HTTPException` handler, `Conflict` uses the status phrase.

The payload is built in one place, `ApiError::to_error_response` (`server/src/error.rs`), and `code` is derived from `status_code()`, so the two cannot disagree. `ErrorDetail.code` becomes a `u16`. `ServiceUnavailable` drops its engine code string: Python surfaces only the engine's message for a retryable rejection (`RetryableRequestError(message)`).

Remaining differences, out of scope here: Python reports `Bad Request` for checks in its pydantic model validators, while the matching Rust DTO `#[validate]` checks report `BadRequestError` (both 400); and Python's LoRA routes use `InvalidUserInput` for bad load/unload input.

Batch integration: vllm-project/vllm#62432 merged before this PR, and vllm-project/vllm#62642 landed earlier in the batch. This PR's `u16` code change needed a one-line update in the 501 route (`code: 501`), recorded in follow-up commit `732b553bd0`.

Not a duplicate: no open upstream PR changes the Rust error body shape.
