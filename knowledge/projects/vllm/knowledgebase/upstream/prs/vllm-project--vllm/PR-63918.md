# [Bugfix][Kernel] Gate ReplaySSM tf32x3 dot precision to CUDA

[Upstream PR](https://github.com/vllm-project/vllm/pull/63918) · state: open · merged: False

## Original PR description

The Mamba2 ReplaySSM output-only kernel passes `input_precision="tf32x3"` to `tl.dot` on every non-ROCm platform. `tf32x3` is CUDA-only: ROCm already falls back to its backend default via the `is_rocm()` guard (#49909), but other Triton backends receive a value they reject at kernel compile time (triton-ascend accepts only `ieee`/`hf32`), so the ReplaySSM decode path cannot compile on those platforms at all.

## Overview

The current guard is an exclusion list with only ROCm opted out (#49909):

```python
dot_input_precision = None if current_platform.is_rocm() else "tf32x3"
```

Any other non-CUDA platform (e.g. Ascend NPU via triton-ascend) therefore receives `tf32x3` and fails at kernel compile time, so `--use-replayssm` cannot run there at all. This PR inverts the guard into a CUDA-only whitelist:

```python
dot_input_precision = "tf32x3" if current_platform.is_cuda() else None
```

`is_cuda()` is true only for `PlatformEnum.CUDA` (`vllm/platforms/interface.py`), so ROCm keeps exactly the behavior #49909 established.

## Claims

- CUDA: unchanged — still `tf32x3`, bit-identical kernels.
- ROCm: unchanged — still backend default (`None`), same as #49909.
- Other Triton backends: receive `None` (backend default) instead of an unsupported value. On triton-ascend the default is `ieee`, i.e. full fp32 precision — `tf32x3` only approximates fp32.
- The flag only `tl.dot`, in the flush branch of `_replayssm_output_only_kernel`; the non-flush path uses elementwise `tl.sum` and is unaffected by it.
- Single call site: this file contains the only `tf32x3` usage under `vllm/model_executor/layers/mamba/`.

## Validation
Ascend NPU 910B3 validation: the legacy guard reproduces the tf32x3 compilation error in the flush tl.dot. With this PR, FP32 and BF16 ReplaySSM pass 9-step staggered-window oracle tests covering repeated flush, output, checkpoint state, and ring caches. Nemotron‑3‑Nano‑4B also completes 2×32-token ReplaySSM engine decode with the Triton Replay backend; all 64 greedy tokens match the dense baseline. Engine testing used a separate Ascend metadata compatibility shim because the current V1 runner does not yet populate replayssm_decode_base_cpu for ReplaySSM.


## Details

```diff
+    # backend default. CUDA retains tf32x3 to preserve fp32 parity with the
+    # elementwise baseline.

```

The change sits in the ops layer and is runner-agnostic; it does not change which runners upstream supports for this path.
