# [WIP][FT] Pause healthy engines for recovery

[Upstream PR](https://github.com/vllm-project/vllm/pull/65200) · state: open · merged: False

## Original PR description

Fixes #64249.

## Overview

Let the controller pause healthy engines before retry or scale-down, without waiting for traffic to trigger fault detection.

## Claims

Pause rejects new requests, waits for device work, then enters recovery. Repeated pauses don't block retry.

## Details

Compared with #64254, this closes admission early and waits for device completion through the existing worker hook. NPU review is still pending. In-flight collectives may still need the backend timeout.

## Tests

4x H100 80GB, Qwen3-30B-A3B, DP/EP=2 and 4, MRV2, BF16 eager, NIXL EP. Production source `06b7e3027e`.

- `pytest tests/v1/fault_tolerance/test_fault_tolerance_e2e.py -k 'pause or injected' -v -s`: 4 passed. Baseline idle pause returned 400; patched idle and busy pause/retry passed.
- Strict idle worker-kill/scale-down rerun: passed, all survivors entered `FaultTolerancePause`; 256-question GSM8K **91.8% -> 91.8%**.
- `pytest tests/v1/fault_tolerance/test_engine_core_sentinel.py -v`: 2 passed. Pre-commit, including mypy, passed.

Upstream FT GPU CI is currently disabled; these GPU checks ran outside CI.

### inline_comments

- fangyuchu · comment · 2026-11-03T01:06:29Z · [source](https://github.com/vllm-project/vllm/pull/65200#discussion_r4449670957)

File: `vllm/v1/engine/core.py` · line 1900

Could we move the logic in the worker side into a `pause()` method in `WorkerSentinel` and call it from here? This would allow different hardware backends to provide their own implementations. For example, the GPU backend could call `synchronize_device()` in `WorkerSentinel.pause()`.

- fangyuchu · comment · 2026-11-03T02:07:55Z · [source](https://github.com/vllm-project/vllm/pull/65200#discussion_r4450138795)

File: `vllm/v1/fault_tolerance/engine_core_sentinel.py` · line 277

`pause()` can build a `DIAGNOSING` payload, then a concurrent `on_fault()` can publish `UNHEALTHY` before that payload is enqueued. The stale `DIAGNOSING` then overwrites the client cache while the busy loop is already waiting for recovery.

- fangyuchu · comment · 2026-11-03T07:16:40Z · [source](https://github.com/vllm-project/vllm/pull/65200#discussion_r4451859466)

File: `vllm/v1/engine/core_client.py` · line 1484

Could we accept `pause` only when the engine is `HEALTHY`, and return a clear rejection reason otherwise? There is no additional pause work needed in `DIAGNOSING` or `UNHEALTHY`. 

This can also resolve the current issue:
_After a failed recovery, pause updates last_ft_request_id and clears ft_error, but leaves ft_state="failed". Since pause on an unhealthy engine succeeds without pushing another status, the cache incorrectly associates the failure with the successful pause._
