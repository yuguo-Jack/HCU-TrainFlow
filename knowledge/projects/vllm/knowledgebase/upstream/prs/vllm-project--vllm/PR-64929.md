# [ROCm] Add VLLM_ROCM_USE_AITER_QUICK_REDUCE to keep INT4 QuickReduce on the HIP kernel

[Upstream PR](https://github.com/vllm-project/vllm/pull/64929) · state: open · merged: False

## Original PR description

> **Interim escape hatch** while AITER's FlyDSL INT4 QuickReduce clips group scales above 480 (wrong outputs on models with large activations, e.g. MiniMax-M3: MMMU 0.27–0.30). The kernel fix is ROCm/aiter#7258 (approved); once vLLM's AITER pin includes it, this switch is optional. Applies to gfx942 and gfx950 (both use the FlyDSL kernel); validated on gfx950.

## Purpose

Since #59478, BF16 INT4 QuickReduce always uses AITER's FlyDSL kernel when `VLLM_ROCM_USE_AITER=1`; there is no way back to vLLM's HIP INT4 kernel short of disabling AITER entirely (which also drops AITER MoE/attention). The FlyDSL INT4 kernel in AITER ≤ v0.1.27 clips group scales above 480 and gives wrong results on models with large activations (fix: ROCm/aiter#7258). This adds `VLLM_ROCM_USE_AITER_QUICK_REDUCE` (default on = current behaviour); off keeps INT4 QuickReduce on the HIP kernel with the rest of AITER on. Mainly an escape hatch until vLLM pins an AITER release with the fix.

## Test Result

MiniMax-M3 VL on MI355X, MMMU val: FlyDSL INT4 0.27–0.30 (TP2/TP4/TP8); with this switch off (HIP INT4) 0.656 (TP4) / 0.644 (TP8), throughput 106% / 115% of a B200 reference run on the same benchmark.

## Verified on this PR's head (2026-11-03)

MI355X, TP2, MiniMax-M3 VL (`amd/MiniMax-M3-MXFP4-AttnFP8`), vLLM nightly 40941f2c + this branch, MMMU val (900 questions):

| arm | QuickReduce path | MMMU |
|---|---|---|
| default (`VLLM_ROCM_QUICK_REDUCE_QUANTIZATION=INT4`) | AITER FlyDSL INT4 | 0.292 ± 0.015 (chance ≈ 0.25) |
| `VLLM_ROCM_USE_AITER_QUICK_REDUCE=0` | vLLM HIP INT4 | **0.656 ± 0.015** |

Throughput on an image row is the same within noise (560 vs 570 tok/s).
