# [Bugfix][Tool Parser] ernie45: keep content when no complete tool call is found

[Upstream PR](https://github.com/vllm-project/vllm/pull/65346) · state: open · merged: False

## Original PR description



## Overview

`Ernie45ToolParser.extract_tool_calls` reports `tools_called=True` with an empty `tool_calls` list when the output contains `<tool_call>` but no complete `<tool_call>...</tool_call>` block, and drops everything after the start marker. This PR returns the full output as content with `tools_called=False` in that case.

## Claims

- Truncated tool-call output (e.g. generation stopped by `max_tokens` in the middle of a call) is no longer silently lost: the request now gets the full text back as `content`.
- `tools_called` is consistent with `tool_calls`, as `tests/tool_parsers/utils.py` already asserts for other parsers (`extracted.tools_called == bool(extracted.tool_calls)`).
- Outputs that contain at least one complete tool call are unchanged.

## Validation

New regression test `test_extract_tool_calls_truncated_keeps_content` in `tests/tool_parsers/test_ernie45_moe_tool_parser.py` (real ERNIE 4.5 tokenizer, real parser).

Before the fix (parser from `main`, new test):

```
$ pytest tests/tool_parsers/test_ernie45_moe_tool_parser.py -k truncated

E        +  where True = ExtractedToolCallInformation(tools_called=True, tool_calls=[], content='Sure.').tools_called
FAILED tests/tool_parsers/test_ernie45_moe_tool_parser.py::test_extract_tool_calls_truncated_keeps_content
1 failed, 7 deselected
```

After the fix:

```
$ pytest tests/tool_parsers/test_ernie45_moe_tool_parser.py

```

`pre-commit run --files <changed files>` passes (ruff check/format, mypy, typos, check-test-tethering).

Environment: CPU only (ARM Neoverse-N1, 4 cores), Python 3.12, torch 2.14.0, transformers 5.20.2. I did not run an end-to-end `RemoteOpenAIServer` test with real ERNIE 4.5 weights because I have no GPU; the change is confined to the non-streaming parser and is covered at that level by the test above.

## Details

Root cause: `tool_call_regex` only matches complete `<tool_call>...</tool_call>` blocks, but the code returned `tools_called=True` whenever `<tool_call>` appeared in the output, even if the regex found nothing. `DelegatingParser._extract_tool_calls` (`vllm/parser/abstract_parser.py`) then replaces the content with the text before the marker, so the rest of the output is dropped.

The fix adds an early return when no call was extracted, matching what other parsers already do (e.g. `step3_tool_parser.py`, `functiongemma_tool_parser.py`). The streaming path is not touched.

Duplicate check: `gh pr list --state open --search "ernie45 tool"` returns #57677 (regex timeouts), #52841 (Rust frontend parser), #48295 (streaming path) and #48386 (reasoning parser); none changes the non-streaming empty-result handling. `deepseekv31_tool_parser.py` has the same pattern, but I left it out because #59589 is changing the adjacent lines.

AI assistance was used to help find the issue and draft the change; I reviewed every changed line and ran the tests above.
