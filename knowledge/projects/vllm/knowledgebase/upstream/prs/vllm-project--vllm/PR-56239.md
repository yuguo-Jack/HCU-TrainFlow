# [Bugfix][Core] Avoid initializing CUDA while resolving AllReduce+RMSNorm fusion config

[Upstream PR](https://github.com/vllm-project/vllm/pull/56239) · state: open · merged: False

## Original PR description

## Purpose

On Hopper/Blackwell with `tensor_parallel_size > 1` and flashinfer installed, building the engine config initializes CUDA in the calling process. vLLM then sees "CUDA is initialized" and overrides `VLLM_WORKER_MULTIPROC_METHOD` from `fork` to `spawn`, which logs a warning on every `LLM()` call and breaks tests that rely on monkeypatching (`tests/v1/shutdown/`).

Addresses item 1 under "Side effects at import time" in #59433.

## Root cause

`PassConfig.default_fi_allreduce_fusion_max_size_mb()` imported the whole `allreduce_rms_fusion` pass module just to read the `FI_ALLREDUCE_FUSION_MAX_SIZE_MB` table. That module imports `flashinfer.comm` at module level, and importing it initializes CUDA. The import direction was backwards: config resolution should not depend on a pass module.

```
create_engine_config() → PassConfig.flashinfer_max_size()
  → default_fi_allreduce_fusion_max_size_mb()
  → import allreduce_rms_fusion → import flashinfer.comm → CUDA initialized
```

## Fix

Move `FI_ALLREDUCE_FUSION_MAX_SIZE_MB` into `vllm/config/compilation.py` and drop the cross-module import. `allreduce_rms_fusion.py` never read the table, and its own flashinfer import is unchanged. Also replace the stale copy of the table in the `PassConfig` docstring with a pointer to the single definition. No runtime logic change.

`tests/standalone_tests/lazy_imports.py` now also asserts that `PassConfig().flashinfer_max_size(2)` does not import the fusion pass module.

## Test Plan

On the original branch (before the rebase), the three `tests/v1/shutdown/test_forward_error.py` cases that failed under the forced `spawn` pass, and the spawn warning is gone.

This takes flashinfer off the API server's path only; workers still import it where they need it.
