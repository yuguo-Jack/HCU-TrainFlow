# [Bugfix][Core] Abort requests still running at the --shutdown-timeout drain deadline

[Upstream PR](https://github.com/vllm-project/vllm/pull/64991) · state: open · merged: False

## Original PR description



## Overview

With `--shutdown-timeout N > 0`, EngineCore drains in-flight requests on SIGTERM but has no deadline of its own: the drain branch of `_handle_shutdown` only logs, and the engine keeps stepping until it has no work. The only bound is the process manager, which SIGKILLs EngineCore `N` seconds after sending SIGTERM. A request still running at that point never gets a final output: its stream ends on an ordinary content chunk, with no `finish_reason` and no `data: [DONE]`, and the API server then waits for that connection forever (`Waiting for connections to close`), so the process does not exit until something kills it. With the default `--shutdown-timeout 0` the same request ends cleanly with `finish_reason="abort"`, so enabling a drain makes the requests that outlive it end worse than not draining at all.

This PR gives the drain its deadline in EngineCore, where the drain already runs: when it passes, EngineCore aborts what is left through the same path abort mode uses, and the API server gives EngineCore `N` + 5 s before the process manager kills it, so those aborts reach the clients.

## Claims

- With `--shutdown-timeout N > 0`, a request still running `N` s after SIGTERM ends with `finish_reason="abort"` followed by `data: [DONE]`, and `vllm serve` exits within `N` + 5 s. On `main` the stream stops mid-generation without a final chunk and the server does not exit.
- Requests that finish within `N`, including ones still queued (`waiting`) when SIGTERM arrives, complete as on `main`: EngineCore keeps scheduling them during the drain.
- `--shutdown-timeout 0` is unchanged.
- The 5 s teardown margin matches the one #62967 gave the gRPC server (`_ENGINE_TEARDOWN_S`).

## Details

**Root cause.** `_handle_shutdown` in drain mode sets `SHUTTING_DOWN` and returns `True` until `has_work()` is false; nothing aborts requests at the timeout. `MPClient.shutdown(timeout=N)` meanwhile has the process manager SIGKILL EngineCore once `N` elapses after it sent SIGTERM. That timer starts before EngineCore receives the signal, so even an engine-side deadline of `N` would always lose the race without a margin. Once EngineCore is gone, `AsyncLLM.shutdown` cancels the output handler, and the requests still waiting on their output queues get neither an output nor an error, which is why the HTTP connection and the process hang.

**Fix.** `_handle_shutdown` records `time.monotonic() + shutdown_timeout` when the drain starts and, once that passes, runs the abort-mode path (`scheduler.finish_requests(None, FINISHED_ABORTED)` and `_send_abort_outputs`) once. The busy loop calls `_handle_shutdown` every iteration, so the check runs every engine step while there is work. `serve_http` passes `N + _ENGINE_TEARDOWN_S` to `engine_client.shutdown()` in drain mode.

**Why EngineCore rather than the API server.** I first drained from the API server with `pause_generation(mode="wait")` and aborted with `pause_generation(mode="abort")` at the deadline (EngineCore rejects pause calls once it has SIGTERM, so this has to happen before `engine_client.shutdown()`). It fixed the long-request case but broke queued requests: the "wait" pause completes once the running requests finish, and requests still waiting in the scheduler are neither scheduled nor aborted. With `--max-num-seqs 1`, the queued request in the second table was left without a final chunk and the server hung. EngineCore's own drain already schedules waiting requests (`has_work()` counts `scheduler.has_requests()`) and already rejects new adds during shutdown; it was only missing the deadline. It also already reads `shutdown_timeout` itself to choose between abort and drain.

**Data parallel.** `DPEngineCoreProc.run_busy_loop` calls `_handle_shutdown` at the top of each iteration as well. Every rank reads the same timeout and gets SIGTERM at about the same time; a rank that aborts its requests keeps running dummy batches while `engines_running` reports work on another rank, so the collective steps stay aligned.

**Scope.** Only the single-API-server path (`serve_http`) gets the teardown margin. `run_multi_api_server` and `run_headless` also stop EngineCore with `shutdown_timeout`; the engine-side deadline applies there too, but they need the same margin to deliver the aborts. I left them out because #61562 is reordering the multi-API-server shutdown.

**Not changed here.**
- New requests that arrive during the drain on a single API server still fail with HTTP 500 (the renderer's executor is shut down first) while `/health` returns 200. #61562 makes the server stop accepting at SIGTERM, which addresses both.
- If EngineCore does not exit within the 5 s margin, the requests waiting on it still hang because the output handler is cancelled without propagating an error. With this PR that no longer happens on the normal path; making `AsyncLLM.shutdown` fail pending requests with `EngineDeadError` is a separate change.

**Related.** #24885 (shutdown semantics RFC), #36666 (`--shutdown-timeout`), #62967 (the same deadline and margin for the gRPC server), #61562 (stop accepting during the drain; multi-API-server ordering).
