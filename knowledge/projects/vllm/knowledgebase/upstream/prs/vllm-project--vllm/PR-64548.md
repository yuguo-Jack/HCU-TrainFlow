# [Perf][Attention][DCP] Gather the MLA DCP context rows by index instead of reorg_kvcache

[Upstream PR](https://github.com/vllm-project/vllm/pull/64548) · state: open · merged: False

## Original PR description

## Overview

Under DCP, the MLA chunked-context loop un-shards the all-gathered context rows with `reorg_kvcache`: a host loop that slices the latent and rope rows of each (request, rank), then two `torch.cat` calls, for every chunk in every MLA layer. This PR builds the row indices once per batch with the chunk metadata (`ContextChunk.context_row_indices`) and replaces `reorg_kvcache` with one Triton row-gather launch per chunk and layer. Split out of #63935 (fp8 DCP context), which builds on this PR.

## Claims

- Per chunk and MLA layer, in the five chunks below: GPU time 21.8–397.0 us → 7.1–29.4 us, host time 104.5–3,458.7 us → 47.2–49.4 us.
- Cost: 214–376 us more host time per batch in `build_mla_chunked_context_metadata`, under DCP only, once per batch (not per layer), with no device sync.
- `kv_b_proj` and the prefill backend get bit-identical inputs (same rows, order, dtype, shapes, contiguity). Kimi K3 prompt logprobs match main bit for bit.
- End to end on Kimi K3 with a 129K-token cached prefix, latency matches main within run-to-run noise. The other end-to-end runs below are up to 3.6% lower in throughput and up to 3.0% higher in median TTFT than main, one run per arm and node pair. The saving per chunk is largest for chunks of many requests (host time 3,458.7 → 48.2 us per chunk and layer at 64 requests).
- `reorg_kvcache` is removed; nothing else called it.

## Validation

**Per chunk and MLA layer.** One GB300 GPU, DCP 8, bf16 rows of 512 + 64 values, chunks from `build_mla_chunked_context_metadata`. Only the un-shard step is timed, on an all-gathered workspace: `reorg_kvcache` on main, `gather_dcp_context_rows` here. GPU time: CUDA events queued behind a GPU sleep, so host launch gaps are excluded. Host time: wall time of the call. Median of 300 calls after 20 warm-ups.

|---|---|---|---|---|
| 66,304 rows, 1 request with a 129,024-token context | 142.3 us | 29.4 us | 106.9 us | 49.4 us |
| 66,304 rows, 2 requests, from a batch of 4 such requests | 138.9 us | 29.4 us | 162.8 us | 48.2 us |
| 51,968 rows, last chunk of that batch | 115.2 us | 23.5 us | 105.7 us | 48.4 us |
| 64,000 rows, 64 requests of 1,000 tokens | 397.0 us | 29.4 us | 3,458.7 us | 48.2 us |
| 4,096 rows, 1 request of 4,096 tokens | 21.8 us | 7.1 us | 104.5 us | 47.2 us |

**Added host time per batch** in `build_mla_chunked_context_metadata`: 214 us (1 request of 4,096 tokens, 1 chunk), 249 us (1 request of 129,024 tokens, 2 chunks; 64 requests of 1,000 tokens, 1 chunk), 376 us (4 requests of 129,024 tokens, 8 chunks). In each batch, the host time saved over all its chunks repays this within four MLA layers.

Both measurements above come from an earlier revision of this PR with the same kernel body, which launched the kernel directly rather than through the JIT-warmup dispatcher; host times were not re-measured at this head.

**End to end.** Kimi K3 on 2 nodes of 4 GB300 GPUs (TP 8, DCP 8, fp8 KV cache, `TOKENSPEED_MLA` with `TRTLLM_RAGGED` (cute-dsl) prefill and fp8 prefill queries, DSpark speculative decoding with 4 tokens, prefix caching, direct symmetric-memory DCP KV gather). Each request adds 64 new tokens to a cached 129,024-token prefix (token-id prompts, `max_tokens=1`, prefix-cache hit rate 0.9995). Median latency of 24 requests at concurrency 1 and 48 at concurrency 6, warm second pass. Two runs on two node pairs, arms in opposite order:

| Median latency, run 1 / run 2 | main | this PR |
|---|---|---|
| Concurrency 1 | 130.6 / 127.6 ms | 129.9 / 130.7 ms |
| Concurrency 6 | 435.3 / 435.1 ms | 406.4 / 434.1 ms |

Against main: −0.54% / +2.43% at concurrency 1, −6.64% / −0.23% at concurrency 6. This PR's concurrency-6 median moved 6.8% between the two runs (406.4 vs 434.1 ms), so the differences are within run-to-run noise.

**Correctness and tests**

- **Prompt logprobs.** 4 prompts of 135,000–150,000 tokens, each sent with greedy prompt logprobs and then again without them. A prompt-logprobs request does not read the prefix cache, so the first send was prefilled in chunks of at most 16,384 tokens (`max_num_batched_tokens`), each chunk after the first reading the earlier ones through the DCP context loop; the second send read 134,912–149,888 tokens from the prefix cache. Every prompt logprob and both sends' generated tokens matched main bit for bit (570,032 values, 0 differ), in both runs.

## Details

- **JIT warmup.** `MLADCPManager` registers the kernel with the JIT warmup when `enable_jit_warmup` is set. The DCP workspace dtype moves into `get_dcp_context_workspace_dtype`, so the warmup uses the same dtype (no behavior change).
- **Why a kernel and not `torch.index_select`.** One `index_select` of whole rows, with the latent and rope parts read as views, gives the same bytes. Its gather took 1.41–1.88x the kernel's GPU time (16,384 to 131,072 rows of 576 bf16 values; one GB300, CUDA graph, CUDA events, L2 not flushed). With an illustrative `kv_b_proj` GEMM and K concat reading the rows, the total was 2.0% higher with `index_select`, and `index_select` took 17 us of host time to issue against 36 us for the kernel (mean of 200 back-to-back calls, a different harness from the per-chunk table).
- **Not a duplicate.** #52239 (open, has merge conflicts) publishes prefill KV in the final MLA layout on the direct multicast KV gather only, and keeps the all-gather plus `reorg_kvcache` as its fallback. This PR replaces `reorg_kvcache` on every path and keeps both KV gathers. A search of open PR titles and descriptions for `reorg_kvcache` finds only this PR and #63935.
- **Follow-up.** The ROCm AITER fused DCP path still builds the same indices per chunk with its own helper (`context_row_indices` in `rocm_aiter_mla_prefill.py`). Switching it to `ContextChunk.context_row_indices` would remove that duplicate.
