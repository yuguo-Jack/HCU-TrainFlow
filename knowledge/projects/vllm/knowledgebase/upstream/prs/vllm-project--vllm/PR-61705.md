# [Perf][Multimodal] Use FA4 for long-sequence ViT attention on Hopper

[Upstream PR](https://github.com/vllm-project/vllm/pull/61705) · state: open · merged: False

## Original PR description

## Problem


The problem is to make full use of the FA4 kernels, via dispatching solutions to achieve better vision encoder efficiency for long sequence VIT models. MR as the selection based logic for low latency VE attention part. 

Detailed kernel profiling result is included below. 

## Reproducing 

1x H100 80GB , `vllm/vllm-openai:nightly` pinned to
`ai.vllm.build.commit=77154ca6116ae34cbfe314beef1016bde9b63989` (pull
`vllm/vllm-openai:nightly-77154ca6116ae34cbfe314beef1016bde9b63989`, since `:nightly`
has moved since). The PR is pure Python, so both arms share byte-identical compiled
kernels and differ by exactly the PR diff.


## What changes on the GPU

Server + `--profiler-config '{"profiler": "torch", "torch_profiler_dir": "/prof"}'`,
then 4 profiled single-stream requests of one image each, then sum GPU time per CUDA
kernel over the rank0 trace. Three runs per arm for Qwen2-VL, four or five for
Nemotron-Parse, interleaved main/Now.

```bash
vllm bench serve ... --max-concurrency 1 --num-prompts 4 --num-warmups 4 --profile
python3 trace_kernels.py 'prof_dir/rank0.*.pt.trace.json.gz'
# trace_kernels.py sums event["dur"] per name over cat=="kernel" events whose name
# contains "flash"; names truncated to 110 chars.
```

- head_size 80 crosses 1.0 between 6k and 8k: 4k `1.076`, 6k `1.012`, 8k `0.974`, and

- 16k split into 256 x 64-token windows is 1.89x-2.61x **slower** under FA4 at every head
  size. That is why the switch is gated on `max_seqlen`, not applied per layer.
- head_size 64 behaves like 80 (crosses at 8k, better beyond) and is still left out of
  `_VIT_LONG_SEQ_FA4_HEAD_SIZES` for want of a long-sequence head_size-64 model to
  validate end to end. 72 only reaches 0.961 at 16k; 96 and 128 never beat the control.
- FA3 and FA4 have the same relative error against fp32 at every shape (2.26e-3-2.33e-3),
  so this is a speed change, not an accuracy change - but see the greedy-output section.

## E2E accuracy - greedy output equality (Nemotron-Parse-2.0)

There is no lm_eval task for a document parser, so instead: greedy
(`temperature=0`) decode of the same 32 requests (16 distinct real ChartQA images, each
sent twice) with the model-card prompt
`</s><s><predict_bbox><predict_classes><output_markdown><predict_no_text_in_pic>`,
captured from each arm and compared byte-for-byte. The two A/A rows are the control:
each arm restarted into a second server and re-run.


Read this honestly: **each arm is fully deterministic (32/32 A/A on both), and the arms
do not agree.** At 180 tokens half the outputs differ; most of those differ only in
`<x_>/<y_>` bounding-box coordinates by about one quantisation step (median |delta|
0.0008 on a 0-1 scale), but 4/32 requests (2 distinct images) also differ in the
extracted markdown - in one case the table values themselves. Example of the most common
kind of difference:

```
--- image idx 0, first difference at char 15
    main: '<x_0.709><y_0.3602>Our World\nin Data<x_0.7451><y_0.3758><class_Caption>'
    Now : '<x_0.709><y_0.3594>Our World\nin Data<x_0.7451><y_0.3758><class_Caption>'
```

This is the expected consequence of swapping to a kernel with equal-but-different
rounding (same 2.3e-3 relative error, different reduction order) in front of a long
greedy decode, and it is the same effect the PR already reports for Qwen2-VL. It does
mean the current PR text's "identical greedy output" for Nemotron-Parse-2.0 does not
hold on this input set and should be corrected.
