# [Perf][Attention] Larger prefill Q tile for Triton unified attention on sm80/sm89

[Upstream PR](https://github.com/vllm-project/vllm/pull/63746) · state: open · merged: False

## Original PR description

## Overview

The 2D unified attention kernel prefills with `BLOCK_M=16`, so each program covers only `16 // num_queries_per_kv` query positions and KV tiles are re-read many times. This uses a 64/128-row tile for prefill-heavy batches on sm80/sm89. gpt-oss always runs this kernel there (FA2 and FlashInfer can't do sinks on those GPUs).

Related: #20690 (same idea, closed as stale), #52684 (same technique on ROCm), #60317 (head_dim 256/512 tuning, same launch code), #37949 (draft, KV tile for sink prefill on SM8x), #59878 (would move gpt-oss on SM8x to FlashInfer).

## Claims

- gpt-oss-20b and Qwen3-8B on A100: TTFT of a long prompt −9 % (4k) to −32 % (32k), throughput up to +43 %. Under open-loop mixed load TTFT and TPOT are lower than main in all four workloads I ran.
- Prefill kernel 1.95x (A100) / 2.17x (L4) geomean on batches of 2048+ tokens where the tile is used.
- Not bitwise identical to main. bf16 greedy outputs change, and the RMS logprob error against fp32 is about 4 % higher than main's. Top-1 accuracy is not significantly different.

## Validation

A100-SXM4-40GB and L4 (Colab), vLLM wheel `0.32.1rc1.dev481+gb3466364b` with the changed files copied in (the base versions of both files equal upstream `6674eedd2`), torch 2.14.0+cu130, triton 3.8.0. Benchmark scripts and raw data are kept locally; I can post them if useful.

The sweep, closed-loop and numerics runs used an earlier revision of the gate (sm12x allowed, no token floor in the closed-loop runs); for the measured shapes the final gate picks the same batches. Saturated, `FULL_AND_PIECEWISE` and test runs used the final code (the last commit only changes comments and docstrings).

Tests (L4 is the CI GPU for these tests; sm80 isn't in CI):

```bash
pytest tests/kernels/attention/test_triton_unified_attention.py -k "prefill_block_m or prefill_tile"
pytest tests/kernels/attention/test_triton_unified_attention.py
```

| GPU | `-k` selection | whole file |
|---|---|---|
| L4 | 13 passed | 1930 passed |
| A100 | 12 passed, 1 skipped (fp8 output needs sm89) | not run |

The tests check the launched `BLOCK_M`/`num_warps` with and without opting in, compare against a reference with sinks (sliding window, softcap, fp16, GQA 5/7/12, head 80/96, Gemma-3-like shape), and check that ALiBi, non-causal and fp8-output calls keep the default tile.

Kernel, tile on vs off, 570 batches per GPU, batches of 2048+ tokens where the tile is used:

| GPU | batches | geomean | worst |
|---|---|---|---|
| A100 | 184 | 1.95x | 0.95x |
| L4 | 184 | 2.17x | 1.08x |

Closed loop, A100, TTFT of one request / throughput (8 requests in flight for gpt-oss, 4 for Qwen), median of 3 runs. Qwen3-8B is forced onto `TRITON_ATTN`; it defaults to FA2 on these GPUs, so that comparison is Triton against Triton.

| model | 4k | 8k | 16k | 32k |
|---|---|---|---|---|
| gpt-oss-20b | −9 % / +6 % | −15 % / +13.5 % | −23 % / +26 % | −32.5 % / +43 % |
| Qwen3-8B | −10.6 % / +4.5 % | −18 % / +10.7 % | −25.6 % / +19.7 % | −30 % / +28 % |

Open loop, A100, ratio to main (Poisson arrivals, 70 % prompts of 256–2048 tokens, 30 % of 4096–12000, 128 output tokens; main and tile alternate between windows with identical arrivals; 150–300 requests per run, so p99 rests on 2–3 requests; bootstrap CIs over requests are optimistic):

| workload | TTFT p50 / p95 / p99 | TPOT p50 / p95 / p99 |
|---|---|---|
| gpt-oss-20b, 2 req/s | 0.59 [0.52, 0.97] / 0.78 / 0.80 [0.75, 0.84] | 0.94 / 0.82 / 0.74 [0.59, 0.83] |
| gpt-oss-20b, 2 req/s, other seed | 0.65 / 0.76 / 0.68 [0.59, 0.79] | 0.85 / 0.73 / 0.67 [0.62, 0.75] |
| Qwen3-8B, 1.8 req/s | 0.84 / 0.84 / 0.91 [0.87, 0.92] | 0.94 / 0.99 [0.95, 1.00] / 0.96 [0.95, 0.98] |
| gpt-oss-20b, 12 decoders at 16k + short requests, 3 req/s | 0.63 / 0.74 / 0.70 [0.65, 0.75] | 0.82 / 0.81 / 0.82 [0.82, 0.83] |

Saturated closed loop (gpt-oss-20b, A100, 64 in flight, 240 mixed requests, about 51 s), req/s:

| Triton cache | main | tile |
|---|---|---|
| warm | 4.718 | 4.818 (+2.1 %), TTFT p99 11.6 s → 10.5 s |
| cold | 4.719 | 4.564 (−3.3 %), TTFT p99 11.6 s → 13.4 s |

The tile adds about 96 Triton cache files (513 vs 417) and the cold run is slower than the warm one only with the tile, so I think the cold loss is first-use JIT (compile time not timed). Unified attention isn't in the startup JIT warmup, so a mixed workload pays a few seconds early on. On L4 with an empty cache the first 4100-token prefill was 0.2 s slower than main and the first 9000-token one 0.6 s (single runs). In my very first saturated run (default cache dir) the tile was 3.7 % slower even in its second server, which I couldn't explain; later runs on the same dir didn't repeat it. Adding the kernel to the JIT warmup would fix the cold start; I left that out.

Numerics, Qwen3-4B, 24 prompts of 3k–12k tokens (182,291 positions), fp32 reference:

| | top-1 disagreement | mean \|Δlogprob\| |
|---|---|---|
| main | 1.042 % | 0.0212 |
| tile | 1.052 % (McNemar vs main p = 0.65) | 0.0213 |
| FlashAttention-2 | 1.037 % | 0.0213 |

RMS error: tile +0.0020 over main (95 % CI +0.0006 to +0.0036, about 4 %); FlashAttention-2 +0.0007 (CI includes 0). On 32 long prompts, 17 greedy continuations differ from main within 64 tokens (11 for FlashAttention-2). gpt-oss has no usable logprob comparison (its run-to-run noise on main is 0.05–0.19 nats with the Marlin MoE). GSM8K for gpt-oss-20b (5-shot, A100, earlier gate, tile used in 76 % of calls): 0.303 on both; it has little power (16–17 % invalid answers). Kernel output vs an fp32 reference: worst abs error 0.0104 for main and tile over 82 configs.

`FULL_AND_PIECEWISE` (default cudagraph mode), Qwen3-4B on L4, main vs tile: no errors or NaN, mean |Δlogprob| 0.0235–0.0262, the same size as the tile's own effect.

## Details

- Gate (`_get_prefill_block_m`, host values only): 2048+ tokens, 6+ query blocks per sequence on average, 4+ programs per SM; bf16/fp16, head size 64–128, GQA ≤ 16; exactly sm80 or sm89; off under `VLLM_BATCH_INVARIANT`. Tile is 64 rows (head ≤ 64) or 128, 4 warps, 2 stages. Below 2048 tokens an earlier version was up to 19 % slower. No new setting, so no docs.
- `unified_attention(..., prefill_tile=True)` is set only by `TritonAttentionImpl`. `ultraquant_attn.py`, `segmented_attention.py` and the ROCm callers keep the default launch. Also excluded: quantized KV, tensor-descriptor path, ALiBi, qq bias, mm-prefix, per-sequence or non-causal masks, rswa, chunked attention, fp8 output. Only plain causal attention (sliding window, sinks, softcap allowed) was tested.
- sm86/sm87/sm90/sm100/sm12x keep the default (sm12x only has an early kernel run).
- Not covered: a saturated open-loop run around 20 req/s (what the #20690 reviewer measured; mine reach 3 req/s, and L4 open loop used an earlier gate), H100/B200/sm12x, multi-GPU, Gemma-3 end to end, `FULL` graphs with the final code.
- #52684 touches the same BLOCK_M lines (ROCm gfx1100/1151): one conflict region, keep both functions, the gates don't overlap. #60317: the kernel file merges cleanly, only the tests file needs a manual merge. The patch also conflicts textually with #62581, #61760, #61646, #61630, #60418, #51506 and #39018 (adjacent hunks, imports). If #37949 lands too, sm89 would get BLOCK_M 64 with a KV tile of 16, which I haven't measured. If #59878 lands, gpt-oss on sm80/sm89 may stop using this path.
- No merged or open PR does this for CUDA (open, closed and merged PRs and issues searched with 13 query variants).
- AI assistance: Claude (Anthropic) wrote the code, tests, benchmark scripts and this description.
