# [Bugfix][MoRIIO] READ abort before alloc: release producer without reading into freed blocks

[Upstream PR](https://github.com/vllm-project/vllm/pull/63417) · state: closed · merged: False

## Original PR description

## Purpose

Fix a decode-side MoRIIO READ abort path that can post RDMA reads into KV blocks the scheduler has already freed.

When a READ request finishes with `do_remote_prefill` still set, it was aborted before `update_state_after_alloc` ran. In that case `MoRIIOConnectorScheduler.request_finished` adds the request to `_reqs_need_recv` so the worker can release the producer's blocks, and returns `delay_free_blocks=False`.

The hybrid branch queued the request's **allocated local blocks**: attention plus the per-request KDA slot.

- The scheduler frees those blocks in `_free_request` right away. They can be handed to another request in the next `schedule()`, or stay in the prefix cache.
- In the next step, `_read_blocks` sees `any(local_block_ids)` and posts RDMA reads from the producer into them.
- No error is raised. The KV of a different or cached request is overwritten.

The fix queues empty groups and keeps the group count. `_read_blocks` already has a `not any(local_block_ids)` branch that sends only the `release` notify. That branch runs before the group-count check and the KDA missing-slot guard, so the guard that the old comment worried about cannot trip.

This matches the non-hybrid path, which already queued empty groups.

Note: in the normal scheduler flow, `allocate_slots` and `update_state_after_alloc` run back to back. A request that still has `do_remote_prefill` set at finish therefore usually has no blocks, and old and new code behave the same. The previous comment says a request can still hold blocks here. If it does, those blocks are freed by this same call, so reading into them is never correct.
