# [ROCm][Attention] Add an mxfp4_mla KV cache for rope-free sparse MLA (read/write path)

[Upstream PR](https://github.com/vllm-project/vllm/pull/60321) · state: open · merged: False

## Original PR description

## Overview

Adds an `mxfp4_mla` KV cache dtype for the ROCm AITER sparse MLA backend on rope-free (NoPE) latents such as GLM-5.3-Flash. Each 512-wide latent is stored as 256 bytes of E2M1 codes plus 16 inline E8M0 scales (one per 32 values): 272 bytes per token against 1024 for bf16, or 3.76× more tokens per GiB of KV cache.

This is the first of the smaller PRs split out of #59739, as requested there. It contains the cache format, the write path, and a Triton read path for both the ragged kernel and the split-K decode kernel from #58584. Everything is Triton or Python: no HIP or C++ sources, and no new environment variables.

## Claims

- **KV capacity:** 3.76× more tokens per GiB than bf16 (272 vs 1024 bytes per token).
- **Correctness:** attention over the packed cache is bit-identical to attention over the same dequantized values stored as bf16.
- **No change for other KV dtypes.** The only shared-kernel change is a branch on the cache pointer's element type, which Triton resolves at compile time, so the bf16 and FP8 specializations compile to the same code as before.
- **Same serving speed as bf16, no speedup claimed.** The Triton read path unpacks to bf16 before both dots, so the gain is capacity, not arithmetic. End to end on the current head (GLM-5.3-Flash TP=4, 2048 in / 128 out, 16 prompts, concurrency 8, one run per arm): bf16 322.5 output tok/s (median TTFT 1596 ms, TPOT 9.8 ms) vs `mxfp4_mla` 323.9 tok/s (1608 ms, 9.8 ms). An earlier single run on 2026-10-08, on a development tree before the last rebases, showed 195.9 vs 299.3 tok/s; it did not reproduce on the current head, where both arms take the same split-K decode path, so it is not claimed.

## Validation

**Unit tests** (MI355X / gfx950):

```
pytest tests/v1/attention/mxfp4_mla/ tests/v1/attention/test_rocm_glm5next_sparse.py
```

`tests/v1/attention/mxfp4_mla/` (plumbing, read, store; 16 passed on gfx950 at 37b843f, CPU-only rerun after the last main merge) covers:
- the format math, checked bit-for-bit against AITER's `per_1x32_f4_quant`;
- the store kernel, including padding slots and launches past 2^31 source elements;
- the Triton read path, checked against a dequantize-then-attend reference, with both the hardware and software unpack;
- the startup plumbing (KV spec bytes, hybrid block sizing, config validation);
- the routing that sends both prefill and decode through the ragged kernel.

**Accuracy** (GLM-5.3-Flash, TP=4 on MI355X, seed 42; both arms served from the same image of this PR's head b7b9232, 2026-10-28):

| Benchmark | bf16 | `mxfp4_mla`, this PR |
|---|---|---|
| GSM8K (5-shot, 1319 questions, greedy) | 96.97% (1279) | 97.04% (1280) |
| GPQA-Diamond (198 questions, temperature 1.0, top_p 0.95) | 91.41% (181) | 89.90% (178) |
| RULER NIAH multikey-2, 32K (50 prompts, greedy, string-match recall) | 100% (50/50) | 100% (50/50) |

Neither gap is significant. On GSM8K the arms disagree on 19 of 1319 questions (10 right only with MXFP4, 9 right only with bf16; exact McNemar p = 1.00). On GPQA-Diamond they disagree on 7 of 198 (2 vs 5; p = 0.45), with 2 generations at the token limit in each arm. Both GPQA scores sit in the 88.9–91.9% range of earlier bf16 and MXFP4 runs. These runs include the indexer page-addressing fix #59412 (#58858), now on main; before it, GPQA-Diamond fell to 80.8–85.4% for bf16 and MXFP4 alike on GLM-5.3-Flash.

## Details

**Format and write path.** The `mxfp4_mla` row is 256 bytes of packed E2M1 (low nibble holds the lower index) followed by 16 E8M0 scales. Scales use the round-up exponent, so no value clamps. `MLAAttention.get_kv_cache_spec` reports the 272-byte row through `state_content_bytes`, and `Platform._align_hybrid_block_size` uses the same size so the mamba state still fits one attention page on hybrid models. `concat_and_cache_mla` can't express per-group scales (its `scale` is a single float), so a Triton store kernel behind `do_kv_cache_update` quantizes and writes the row.

**Read path.** The ragged Triton sparse-attention kernel and the split-K decode kernel (#58584) each gain a branch for a uint8 (packed MXFP4) cache, selected by a compile-time `is_mxfp4` flag. It unpacks each gathered tile to bf16 once and feeds both existing `tl.dot` calls:
- On gfx950 the unpack uses the hardware FP4 converter (`v_cvt_scalef32_pk_bf16_fp4`) via inline asm.
- On other GPUs it uses a software unpack. The two are tested bit-identical on gfx950, but I haven't run the software path on gfx942.

The decode-only kernels used by DeepSeek-V4 have no MXFP4 branch, so they refuse a packed cache rather than misread it.

## Follow-ups (stacked on this PR)

Separately, two decode-overhead trims that apply to every KV dtype (host-side `paged_kv_indptr` for pure-decode steps, and skipping the NoPE `q_concat` copy) will go up as their own PR against main.

## 1. [High] `mxfp4_mla` maps to `KVQuantMode.NONE`, and the PR skips the existing custom-dtype registry
`get_kv_quant_mode("mxfp4_mla")` (`vllm/v1/kv_cache_interface.py`) has no branch for this dtype, so it returns `KVQuantMode.NONE` and `is_quantized_kv_cache("mxfp4_mla")` returns `False`. Any generic code that relies on `kv_quant_mode` / `is_quantized_kv_cache` will treat a packed uint8 cache as unquantized. This includes the `MLAAttentionSpec(kv_quant_mode=...)` built in `Platform._align_hybrid_block_size`, attention-selector decisions, KV-transfer/offload connectors, and the spec-merging logic. Today this only works because of `state_content_bytes` and string checks scattered across files.

`vllm/config/cache.py` already has `register_kv_cache_dtype` / `KVCacheDTypeHandler`, with `torch_dtype()` and `quant_mode()` (`KVQuantMode.CUSTOM` means "quantized, the backend selects its own kernel"). Registering `mxfp4_mla` through it (on ROCm only) would replace:
- the entry in the global `CacheDType` Literal, which is exposed on every platform (see item 5),
- the `STR_DTYPE_TO_TORCH_DTYPE` entry,
- and it would make `is_quantized_kv_cache` correct.
Please either use the handler or add an explicit `KVQuantMode` entry, and confirm that no consumer of `NONE` mis-handles this dtype.

## 2. [High] The page size is computed in two places, and the `ds_mla` path is still inconsistent
`state_content_bytes` is computed both in `MLAAttention.get_kv_cache_spec` and in `Platform._align_hybrid_block_size`, and only `mxfp4_mla` gets the platform-side treatment. `test_hybrid_block_size_matches_the_layer_page` guards this, but only for 512 / GLM-5.3 at TP=4. A single helper, e.g. `mla_state_content_bytes(cache_dtype, head_size)`, used at both sites would remove the drift risk. The current inline `if mxfp4 ... else {dict}.get()` is also awkward. If `row_bytes` should not raise in that dict, the helper can be lazy, for example by mapping to lambdas. The author argues that also fixing `fp8_ds_mla` / `nvfp4_ds_mla` at the platform site is out of scope. That is fair, but this looks like a latent bug for hybrid `ds_mla` models and should at least get a TODO or an issue.

## 3. [Medium] Kernel names and the dtype plumbing are now misleading or stringly-typed
- `rocm_sparse_attn_decode_bf16`, `_rocm_sparse_attn_decode_ragged_bf16_triton`, `_sparse_attn_decode_ragged_bf16_partial_kernel` and `rocm_sparse_decode_bf16_num_splits` all now accept a packed uint8 cache. The docstring still says "unquantized KV cache". Either rename them or at least fix the docstrings.
- `kv_cache_dtype: str = "auto"` is added to the public ops and then converted again in each wrapper with `kv_cache_dtype == "mxfp4_mla"`. Compare once in the impl and pass `is_mxfp4: bool` down, or use a `QuantKey` / `KVQuantMode` as already requested. The `"mxfp4_mla"` string literal appears in about 10 places across 4 files.
- `_use_rocm_sparse_triton` routes mxfp4 to Triton only implicitly, through `not startswith("fp8") and head_size == kv_lora_rank`. Its docstring says "rope-free BF16 path". Add an explicit `kv_cache_dtype == "mxfp4_mla"` term, or assert that this dtype never reaches the AITER kernels. A future change to that predicate (e.g. letting AITER handle bf16 NoPE) would silently send packed rows to a bf16 kernel. `_aiter_sparse_mla_unsupported_reason` already rejects the dtype, but that check only runs when `is_triton_sparse_mla_enabled()`.

## 4. [Medium] Numerical edge cases in the E8M0 exponent-add are untested
`_apply_e8m0_scale` adds `(scale-127) << 23` to the fp32 bit pattern. This is exact only when the result stays a normal fp32 value. The store clamps the encoded scale to `[1, 254]`. For tiny groups (absmax < ~6·2^-127) or huge ones near the top, the exponent field underflows or overflows into the sign bit, producing garbage or a sign flip instead of 0 or inf. The software and hardware paths also differ here: `v_cvt_scalef32` is given scale 1.0, so both rely on the same integer trick. These cases are unrealistic for post-RMSNorm latents, but a single test with clamped scales (encoded 1 and 254), plus a group of all subnormals, would document the behaviour. Alternatively, apply the scale with `tl.where`-guarded `ldexp`-style handling. Also, `store_mxfp4_mla` never checks for NaN/Inf inputs. Should it, or does NaN propagate by design?

## 5. [Medium] `mxfp4_mla` is accepted globally, but works only on one ROCm backend, and docs are missing
Adding the dtype to `CacheDType` makes `--kv-cache-dtype mxfp4_mla` valid on CUDA/XPU/CPU. Backends whose `supported_kv_cache_dtypes` is empty or `None` accept any dtype (`backend.py:117`), so a non-ROCm or non-sparse MLA backend could be selected with a uint8 cache it cannot read. Please check that the selector fails cleanly, e.g. `TRITON_MLA` or the dense `ROCM_AITER_MLA` with a non-sparse model. Per AGENTS.md, user-visible changes need doc updates. Neither `docs/features/quantization/quantized_kvcache.md` nor the `CacheConfig.cache_dtype` docstring (which documents `nvfp4_4over6`) mentions `mxfp4_mla`, its ROCm, sparse-MLA and NoPE-only constraints, or the `kv_lora_rank` constraints.
