# [Bugfix][Benchmark] Handle usage-only chunks in multi-turn streaming

[Upstream PR](https://github.com/vllm-project/vllm/pull/64992) · state: closed · merged: False

## Original PR description



## Overview

Fix multi-turn streaming benchmarks against servers started with `--enable-force-include-usage`. The final usage-only chunk currently raises `IndexError` and aborts the benchmark request.

## Claims

- Skip only empty `choices` with nonempty `usage`, retaining content chunks that also carry continuous usage.
- Preserve existing error handling, timing definitions, and tokenizer-based token counts.
- Reuse the force-usage server test suite and include the benchmark source in its Buildkite dependencies.

## Validation

Real Qwen3-0.6B weights on an H100 80GB. Both runs used the same final regression tests; the baseline was `5d55ef1590c92213e3893dc8e8712f7f2e0bc508`, and the second run added only the two-line client fix.

```bash
VLLM_USE_FLASHINFER_SAMPLER=0 .venv/bin/python -m pytest \
  tests/entrypoints/openai/chat_completion/test_enable_force_include_usage.py \
  -q --tb=short
```

| Revision | Result |
| --- | --- |
| Base plus regression tests | 1 failed, 2 passed in 30.97s |
| Base plus tests and fix | 3 passed in 32.39s |

The sole baseline failure was the streaming benchmark:

```text
benchmarks/multi_turn/benchmark_serving_multi_turn.py:323: in send_request
    delta = data["choices"][0]["delta"]
E   IndexError: list index out of range
```

The tests compare full streaming/non-streaming benchmark text with the same server's SDK response and check response validity, first-chunk retention, and timing order. The fixture uses greedy/eager generation, disabled prefix caching, `VLLM_BATCH_INVARIANT=1`, and 128 MiB of KV cache.

Additional local aiohttp protocol validation: 14 passed, covering ordinary/final/continuous usage, fragmented writes, HTTP/SSE errors, streams without content, and second-turn request history. These supplemental cases were not added to CI.

Final checks passed:

```bash
.venv/bin/python -m pre_commit run --files \
  benchmarks/multi_turn/benchmark_serving_multi_turn.py \
  tests/entrypoints/openai/chat_completion/test_enable_force_include_usage.py \
  .buildkite/test_areas/entrypoints.yaml docs/benchmarking/cli.md
git diff --check
```

Repository-wide manual hooks also passed after resolving a local certificate configuration issue. The full run used `.venv/bin/python -m pre_commit run --show-diff-on-failure --all-files --hook-stage manual`; only the five dependency-lock hooks failed initially with the proxy's `UnknownIssuer` error. Re-running them with `UV_SYSTEM_CERTS=true .venv/bin/python -m pre_commit run pip-compile --show-diff-on-failure --all-files --hook-stage manual` passed all five. The validation checkout remained clean.

Environment: Python 3.12.16, Torch 2.14.0+cu130, exact Python source with existing precompiled vLLM extensions. Both GPU runs used the native sampler because the host's older nvcc could not build the FlashInfer sampler. Setup failures were recorded separately and excluded from the before/after results. This changes client parsing, with no model-computation changes or performance claims.

## Details

The server's force-usage option overrides the client's `include_usage=false` and emits a final chunk with `choices=[]`. The client previously indexed that array unconditionally. The fix follows the choices/usage separation used by the existing vLLM benchmark client and OpenAI SDK, without replacing the multi-turn client's different result and timing interfaces.

Public duplicate-work checks on 2026-11-01 found no PR covering this fix. The closed, unmerged [#33649](https://github.com/vllm-project/vllm/pull/33649) adds API token counts but still indexes choices unconditionally. [#53075](https://github.com/vllm-project/vllm/pull/53075) adds a separate asyncio client for deadlock handling, and [#57181](https://github.com/vllm-project/vllm/pull/57181) changes queue handling.

AI assistance was used for investigation, implementation, and validation.
