# [Bugfix][Quantization] Fix Humming FP8 linear for per-tensor/per-channel FP8 weights

[Upstream PR](https://github.com/vllm-project/vllm/pull/60163) · state: closed · merged: True

## Original PR description



## Overview

Fixes #60162. With the Humming FP8 linear kernel, `fp8` checkpoints with per-tensor weight scales and online `fp8_per_tensor` / `fp8_per_channel` quantization crash while loading weights. On Ampere with `VLLM_BATCH_INVARIANT=1`, Humming is the only FP8 linear kernel left (Marlin opts out of batch-invariant mode), so these models cannot start in that mode. Humming FP8 is W8A16, so `fp8_per_channel` (PTPC, which asks for per-token FP8 activations) now gets the same clear error as on Marlin instead of running.

## Claims

- `Fp8LinearMethod` (non-block) and `Fp8PerTensorOnlineLinearMethod` load and run on Humming. GSM8K accuracy is within about one standard error of Marlin.
- On Ampere with `VLLM_BATCH_INVARIANT=1`, these models start and are batch-invariant under the default torch.compile + CUDA graphs.
- `Fp8PtpcOnlineLinearMethod` rejects Humming with the same error it already raises for Marlin.

## Details

**Missing layout tag.** `process_fp8_weight_tensor_strategy` returns the weight as a `(K, N)` transposed view, and `Fp8PerTensorOnlineLinearMethod` transposes it itself. Humming's `convert_linear_layer_to_humming_standard` reads `layer.processed_weight_dims` (falling back to the parameter's checkpoint `input_dim`/`output_dim`) to detect the layout. Without it, Humming assumes `(N, K)` and calls `.view(torch.int32)` on the transposed view, which fails. Since #62326, CompressedTensors, fbgemm, ModelOpt and Quark FP8 set `processed_weight_dims = (0, 1)` after transposing. This PR does the same in the two methods that lacked it. Humming is the only FP8 scaled-mm kernel that reads it, so other kernels are unaffected.

**PTPC.** `Fp8PtpcOnlineLinearMethod` already refuses Marlin because PTPC requires per-token FP8 activations and Marlin FP8 is W8A16. `HummingFP8ScaledMMLinearKernel` builds its layer without an input schema, so it is W8A16 too. With the layout fixed, PTPC would silently run as weight-only FP8 on Humming, so this PR adds Humming to that check. `Fp8LinearMethod` and `fp8_per_tensor` already accept Marlin's W8A16 fallback, and Humming matches it.

**Batch-invariant `apply`.** In batch-invariant mode these methods call the kernel only when `fp8_scaled_mm_is_batch_invariant()` (from #52231) says so; otherwise they dequantize `layer.weight` and run `F.linear`. After Humming's `process_weights_after_loading`, `layer.weight` is in Humming's packed layout, so that fallback fails (`a and b must have same reduction dim, but got [s, 4096] X [256, 24576]`). Humming has its own batch-invariant mode (`use_batch_invariant` in its compute config), and the block-FP8 path and compressed-tensors already call it in this mode. This PR makes `fp8_scaled_mm_is_batch_invariant()` return True for Humming. Humming FP8 is weight-only here, so the dynamic per-tensor activation amax that the helper guards against doesn't apply.

**Notes.**
- Without batch-invariant mode, two identical requests on Humming were not bitwise identical (first difference at token 4). With `VLLM_BATCH_INVARIANT=1` they were. vLLM only promises this in batch-invariant mode, and it does not come from this change.
- CI: the new `humming` case is in `tests/quantization/test_fp8.py`, whose Quantization step is temporarily disabled by #63608. The layout bug does not depend on the GPU architecture. I validated on SM86 only.

**Not a duplicate.** Searched open issues and PRs for Humming FP8 linear, the stride error message, the layout tags, and FP8 batch invariance on Ampere. #59460 also edits `scaled_mm/humming.py` (activation-quantization fallbacks) but not the weight layout or batch-invariant dispatch, and this PR does not touch `humming.py`.

import httpx


def prompt(seed, n_words):
    rng = random.Random(seed)
    return " ".join(f"w{rng.randrange(10000)}" for _ in range(n_words))


def gen(base, model, text, n):
    r = httpx.post(base + "/v1/completions", json={"model": model, "prompt": text, "max_tokens": n,
                                                    "temperature": 0.0, "logprobs": 1}, timeout=600)
    r.raise_for_status()
    ch = r.json()["choices"][0]

def diff(x, y):
    n = min(len(x[0]), len(y[0]))
    first = next((i for i in range(n) if x[0][i] != y[0][i]), None)
    agree = n if first is None else first

Humming then uses its default `HummingInputSchema()` (`a_dtype=None`), which means 16-bit activations with input quantization disabled. That is W8A16, the same as Marlin FP8. With the layout fix alone (the earlier version of this PR), PTPC would silently run as weight-only FP8 whenever it lands on Humming. That happens in two cases:
- on Ampere with `VLLM_BATCH_INVARIANT=1`, where the other FP8 kernels need SM89+ and Marlin opts out;
- with `--linear-backend humming`.

970068e adds Humming to the existing Marlin check in `Fp8PtpcOnlineLinearMethod.create_weights`, so PTPC now raises the same `ValueError`, and the message names the selected kernel. The commit also drops the layout tag that the earlier version set in PTPC, since PTPC no longer reaches Humming. `Fp8LinearMethod` and `fp8_per_tensor` still run on Humming. They already fall back to W8A16 Marlin on GPUs without FP8 support, so Humming matches their existing behavior.
