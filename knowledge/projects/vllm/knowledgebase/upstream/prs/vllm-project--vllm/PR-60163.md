# [Bugfix][Quantization] Fix Humming FP8 linear for per-tensor/per-channel FP8 weights

[Upstream PR](https://github.com/vllm-project/vllm/pull/60163) · state: open · merged: False

## Original PR description



## Overview

Fixes #60162. With the Humming FP8 linear kernel, `fp8` checkpoints with per-tensor weight scales and online `fp8_per_tensor` / `fp8_per_channel` quantization crash while loading weights. On Ampere with `VLLM_BATCH_INVARIANT=1`, Humming is the only FP8 linear kernel left (Marlin opts out of batch-invariant mode), so these models cannot start in that mode.

## Claims

- `Fp8LinearMethod` (non-block), `Fp8PerTensorOnlineLinearMethod` and `Fp8PtpcOnlineLinearMethod` load and run on Humming. GSM8K accuracy matches Marlin.
- On Ampere with `VLLM_BATCH_INVARIANT=1`, these models start and are batch-invariant under the default torch.compile + CUDA graphs.

## Details

**Missing layout tags.** `process_fp8_weight_tensor_strategy` / `process_fp8_weight_channel_strategy` return the weight as a `(K, N)` transposed view, and the online methods transpose it themselves. `replace_parameter` drops the parameter's `input_dim`/`output_dim`. Humming's `convert_linear_layer_to_humming_standard` reads those tags to detect the layout. Without them it assumes `(N, K)` and calls `.view(torch.int32)` on the transposed view, which fails. `CompressedTensorsW8A8Fp8` and ModelOpt's per-tensor FP8 scheme already retag the weight for Humming (added in #41652). This PR adds the same tags in the three methods that lacked them. Humming is the only FP8 scaled-mm kernel that reads these tags, so other kernels are unaffected.

**Batch-invariant `apply`.** In batch-invariant mode these methods call the kernel only when `fp8_scaled_mm_is_batch_invariant()` (from #52231) says so; otherwise they dequantize `layer.weight` and run `F.linear`. After Humming's `process_weights_after_loading`, `layer.weight` is in Humming's packed layout, so that fallback fails (`a and b must have same reduction dim, but got [s, 4096] X [256, 24576]`). Humming has its own batch-invariant mode (`use_batch_invariant` in its compute config), and the block-FP8 path and compressed-tensors already call it in this mode. This PR makes `fp8_scaled_mm_is_batch_invariant()` return True for Humming. Humming FP8 is weight-only here, so the dynamic per-tensor activation amax that the helper guards against doesn't apply.

**Notes.**
- Without batch-invariant mode, two identical requests on Humming were not bitwise identical (first difference at token 4). With `VLLM_BATCH_INVARIANT=1` they were. vLLM only promises this in batch-invariant mode, and it does not come from this change.
- ModelOpt's `KFp8StaticChannel` also stores the `(K, N)` weight without tags. I have no checkpoint to test it, so it is left unchanged.
- CI: the new `humming` case runs in the Quantization step (H200). The layout bug does not depend on the GPU architecture. I validated on SM86 only.

**Not a duplicate.** Searched open issues and PRs for Humming FP8 linear, the stride error message, the layout tags, and FP8 batch invariance on Ampere. #59460 also edits `scaled_mm/humming.py` (activation-quantization fallbacks) but not the weight layout or batch-invariant dispatch, and this PR does not touch `humming.py`.
