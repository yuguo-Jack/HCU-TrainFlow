# [KV Offload] Check /dev/shm for every local DP engine; explain EFAULT

[Upstream PR](https://github.com/vllm-project/vllm/pull/62058) · state: open · merged: False

## Original PR description

## Overview

With data parallelism, CPU KV offload sizes that fit `/dev/shm` one engine at a time but not all together make the engines fail after loading the model with `OSError: [Errno 14] Bad address`. Nothing in that error mentions `/dev/shm`. This PR refuses such sizes before any engine starts and turns the EFAULT into an error that names `/dev/shm`.

## Claims

- `--data-parallel-size 8 --kv-offloading-size 32` against a 251.9 GiB `/dev/shm` now stops before any engine starts, with: *"Insufficient space in /dev/shm for CPU KV offload buffers of 8 data-parallel engines (32.0 GiB each, set by --kv-offloading-size): 262144 MiB required, 257895 MiB free. Increase /dev/shm (e.g. --shm-size or --ipc=host)."* Before this change, all 8 engines loaded the model, then 6 of them failed with "Bad address" and the server exited after 90 s.
- If a full `/dev/shm` is still hit while pre-faulting (other processes using it, or launch modes the check cannot see), the error says so: *"Ran out of /dev/shm while pre-faulting the CPU KV offload shared region (… GiB; /dev/shm has … GiB free of … GiB)…"*, chained from the original `OSError`.
- No new refusals where `/dev/shm` is not used: the CPU spec on ROCm and CPU keeps a private tensor per rank and is not checked (on XPU it maps the shared region, so it is checked). Config-only construction is not checked either; `VllmConfig` is untouched.

## Details

**Root cause.** Each region's creator checks `shutil.disk_usage("/dev/shm").free` against its own size and then calls `ftruncate`. On tmpfs, `ftruncate` creates a sparse file and reserves nothing, so N engines starting together all see the full tmpfs free and all pass. Pages are only claimed when `MADV_POPULATE_WRITE` faults them in. On a full tmpfs, shmem returns `VM_FAULT_SIGBUS`, which `madvise` reports as `EFAULT`.

**Why the check is called from `CoreEngineProcManager`.** The check is `check_local_engines_offload_shm` in a new `vllm/v1/kv_offload/shm_check.py`; `CoreEngineProcManager` calls it once, before starting any engine. It reads the offload config and calls the existing `check_shm_free_space` with the engines' combined size, so `shared_offload_region.py` keeps only the `EFAULT` handling. The launcher is the one place that knows how many engines will share this host's `/dev/shm`. Inside an engine, a dense model's DP rank runs as an independent engine (`reconfigure_for_independent_dp_rank`) with `data_parallel_size_local = 1`. A first version checked in `VllmConfig`, which had two problems. It refused configs on machines that never allocate anything, which broke the config tests above wherever `/dev/shm` is small. It also refused ROCm setups, where the CPU spec never uses `/dev/shm`. The launcher covers internal LB (MoE and dense), multi-node `--nnodes`, `--headless` with `--data-parallel-size-local`, and hybrid LB with `--data-parallel-start-rank`.

**Which specs are checked.** The check asks the spec class (`_uses_shared_region`, now a classmethod): true for `CPUOffloadingSpec` on CUDA and XPU and for `TieringOffloadingSpec` everywhere. A custom spec that does not subclass these is skipped. With `spec_module_path`, the front-end therefore imports that module once. An out-of-tree subclass that overrides the (private) `_uses_shared_region` as an instance method would now fail at launch with a `TypeError`.

**Free space, like every other `/dev/shm` allocation.** At launch the engines have allocated nothing, so the free space is what they will share. The check is `check_shm_free_space` itself, so it uses the same error, and the cgroup headroom log, as a single engine's own check. Something else holding `/dev/shm` at that moment therefore causes a refusal, exactly as it already does for one engine. Anything that fills `/dev/shm` after the check is left to the per-region check and, failing that, to the clearer `EFAULT` message.

**Rejected: reserving with `posix_fallocate`.** It would make the check and the claim atomic, but on tmpfs it allocates the pages under the caller's memory policy. Measured: a file fallocated from NUMA node 3 and then populated from node 5 had 512 of 512 sampled pages on node 3. Every TP rank's slots would land on the creator's node instead of each rank's own.

**Related.** Recent changes to the same region: #59546 splits it across several `/dev/shm` files, #59545 and #60869 spread the pre-fault across workers (`populate_shard`), and #59544 pins only each worker's own slots. None changes how much `/dev/shm` the region needs, when that is checked, or what a full tmpfs reports; the `EFAULT` translation here covers every pre-fault path (per worker, whole region, sharded). Open: #59547 gives each rank its own region and file, and its review notes the same under-detection when several ranks create regions at once; the launcher's per-engine total stays correct under that design. #53073 reworks ownership and cleanup in the same constructor and #61680 adds segments to the HiSparse pool at the call this PR edits, so whichever lands second rebases. #59430 (closed unmerged) had parallelised the pre-fault with a thread pool.

**Limitations.**
- Launch modes where each process starts one engine are not covered by the check, only by the error message: external LB (`--data-parallel-rank`), `--data-parallel-multi-port-external-lb` (its children run with a local size of 1), offline DP with one `LLM` per rank, and independent single-engine servers sharing a host. The Ray backend (`CoreEngineActorManager`) is not checked either.
- Only an `OffloadingConnector` configured directly is checked: one nested in a `MultiConnector` (e.g. with a PD connector) and HiSparse's shared host pool are not added to the sum, though both get the clearer `EFAULT` message.
- After an `EFAULT` in a region without a barrier (the tiering scheduler's), the partly faulted file stays in `/dev/shm`, as it does today, so lowering the size may not be enough until it is removed (#51730, #54619 address cleanup).
- On kernels older than 5.14, there is no `MADV_POPULATE_WRITE`, and the per-page fallback hits a SIGBUS that cannot be translated.
- Under a memory-cgroup limit, the failure is `ENOMEM` or the OOM killer, not `EFAULT`.

Thanks for the review! Makes sense. I've moved the check out of shared_offload_region.py, so that file now only has the EFAULT handling. The check itself now lives in vllm/v1/kv_offload/shm_check.py (new file), and CoreEngineProcManager calls it once before it starts the engines. It adds up the offload buffers of all the engines on the host and passes that total to check_shm_free_space, so the actual comparison, the error message and the cgroup logging all come from check_shm_free_space. As a side effect it now compares against free space instead of total, like the other /dev/shm allocations do.

I didn't put the logic inside check_shm_free_space itself like you suggested because it's a generic helper that just gets a byte count. It's also used by ShmRingBuffer, ShmTensorArena and Engram, and it has no way of knowing how many engines will share the host. The engines can't tell either: a dense model's DP rank gets reconfigured to data_parallel_size_local = 1, so each one only sees its own buffer. And since ftruncate on tmpfs doesn't reserve anything, they all see the same free space and all pass. The launcher is the only place that knows the engine count before anything gets allocated, so that's where the total is computed. I kept the offload-specific parts (the connector, cpu_bytes_to_use, and which specs actually use /dev/shm) in the kv_offload package, so the launcher only gets one import and one call.

I also tried doing it in VllmConfig early on, but that refused configs on machines that never allocate anything (the config tests fail with Docker's 64 MiB /dev/shm), and it refused ROCm setups where the CPU spec doesn't use /dev/shm at all.
