# [Spec Decode][GLM-5.3-Flash] Support adaptive verification

[Upstream PR](https://github.com/vllm-project/vllm/pull/60229) · state: closed · merged: True

## Original PR description

## Motivation

Adaptive verification chooses on the GPU how many draft tokens to verify for each request. During full CUDA graph replay, the physical token buffer and captured control flow remain fixed, while the live request boundaries can change. GLM-5.3-Flash previously made two assumptions that were incompatible with this behavior:

- GDN captured the ordinary one-token decode path, even though replay could group those token rows into fewer requests with multiple verification tokens.
- The k-pool scatter path assumed every physical token row belonged to a live request, but a replayed graph can contain additional padding rows.

This PR updates both paths to handle GPU-selected request lengths and graph padding.

## Changes

- Allow the GDN backend to replay CUDA graphs whose per-request query lengths are chosen on the GPU.
- Capture GDN’s speculative path and the k-pool indexer at the maximum configured verification width.
- Update the k-pool scatter path to safely discard CUDA graph padding without synchronizing lengths back to the CPU.
- Add tests for variable verification lengths, graph padding, and sparse-indexer alignment.

## Testing

Added and ran focused tests covering:

- Mixed per-request GDN verification lengths
- CUDA graph padding in the k-pool scatter path
- Sparse-indexer sequence-length alignment
- Capture-time and replay-time request partition differences

## Throughput results

I benchmarked GLM-5.3-Flash with MTP on four B300 GPUs (TEP4). The sweep covered:

- Speculative depths `kmax = 1...5`
- 18 batch sizes from `B = 1` through `B = 256`
- Prefix lengths `S = 512, 8192, 32768`

The table reports decode throughput for adaptive verification relative to fixed verification at the same maximum depth. Each value is the unweighted mean over the `(B, S)` at that speculative depth.

| Maximum depth | Adaptive / fixed at same depth |
|---:|---:|
| 1 | 0.965× |
| 2 | 0.958× |
| 3 | 0.965× |
| 4 | 1.065× |
| 5 | 1.127× |

<details>
<summary>Why is c1 AV=on faster?</summary>

I profiled the same eight SPEED-Bench prompts with AV on/off using Qwen3.8-27B + RadixArk DSpark v2 at K=15. AV reduced the mean number of positions verified from 16 to 5.91, while producing about the same number of tokens per step (2.60 versus 2.62). Target time fell from 8.82 to 7.48 ms, with a smaller drafter-time change from 1.57 to 1.50 ms. GDN updates recurrent state for each verified token, so extra positions still cost time at c1.

Nsight Systems kernel times, normalized per step per GPU:

| Kernel family | AV off (ms) | AV on (ms) | Saving (ms) | % of total kernel-time saving |
|---|---:|---:|---:|---:|
| GDN recurrence | 1.109 | 0.478 | 0.631 | 69.3% |
| Matrix multiplication and split-K reduction | 6.409 | 6.102 | 0.308 | 33.8% |
| All-reduce | 0.984 | 0.958 | 0.026 | 2.9% |
| Causal convolution | 0.245 | 0.194 | 0.050 | 5.5% |
| Normalization | 0.165 | 0.158 | 0.007 | 0.8% |
| Standard attention | 0.329 | 0.340 | −0.011 | −1.2% |
| Other kernels | 1.331 | 1.433 | −0.101 | −11.1% |
| Total | 10.572 | 9.662 | 0.910 | 100.0% |

GDN recurrence and matrix multiplication provide most of the saving. The last column uses total net kernel-time savings, not elapsed-time speedup. Kernels can overlap, and these totals include target, drafter, and prefill work. Stage times use CUDA events in a separate pass. The profiles used a fourth B300 pair, with both GPUs holding 2,032 MHz during the Nsight trace passes.

Full write-up: [Speculators research submission #1326](https://github.com/vllm-project/speculators/pull/1326).
