# [Perf][Core] Add mamba_aware_lru GPU prefix-cache eviction policy for hybrid models

[Upstream PR](https://github.com/vllm-project/vllm/pull/63808) · state: open · merged: False

## Original PR description

## Overview

Adds `--prefix-cache-eviction-policy mamba_aware_lru`, an opt-in eviction order for the GPU prefix cache of hybrid models in Mamba `align` mode. Under `lru`, the hit that resumes a conversation from a Mamba state also refreshes that state's LRU position, so states that the conversation's later turns no longer need outlive the cached context of idle conversations. `mamba_aware_lru` evicts those states first. On a 1-hour AgentX replay (agentic coding traces) with Nemotron 3.5 Super, it served 5.4% more requests per hour than `lru` and recomputed 15% fewer prompt tokens.

This is the GPU counterpart of #63578, which applies the same rule to the CPU offload tier. Use this one without KV offloading, or with a CPU tier smaller than the GPU cache: a tier at least as large already holds a copy of almost every block the GPU evicts. Related work: #61282, #40270, #55403, #50551 and RFC #57111 (see "Why this is not a duplicate").

## Claims

- New option `--prefix-cache-eviction-policy {lru,mamba_aware_lru}` (`CacheConfig.prefix_cache_eviction_policy`). The default, `lru`, keeps the current behavior.
- With `mamba_aware_lru`, when a request finishes, the Mamba states it superseded move to the front of the free queue (they are demoted). A state is superseded when an earlier request left it as its deepest cached state (its tip), and this request resumed from or passed it and then cached a deeper state. All other blocks keep LRU order, including the request's shared-prefix junction, the state where prompts that share a prefix diverge.
- Outputs do not change: the policy only reorders free blocks, and a demoted state still hits until its block is reused.
- Applies only to Mamba `align` mode with prefix caching on. It runs in the scheduler, with no GPU work and no synchronization: at request finish, one hash lookup per hash block that the request computed past its prefix-cache hit, per Mamba group. With `lru`, the only new work is an empty-list check.
- On a 1-hour AgentX replay (GB200, GPU-only at the default cache size, 64 sessions per server, two servers per policy), compared with `lru`: 5.4% more requests per hour, 5.7% more output tokens/s, 15% fewer recomputed prompt tokens per request and 15% lower p90 TTFT.

## Details

### Motivation: a worked example

A conversation on a hybrid model whose prompts grow from 3 to 5 blocks:

1. Turn 1 caches attention blocks A1–A3 and the Mamba state S3 at its prompt's end. When it finishes, they join the tail of the free queue.
2. Turn 2 hits A1–A3 and S3, computes blocks 4–5, and caches A4, A5 and S5. Once its prefill passes S3, align mode frees S3 again, and S3 rejoins the queue tail as if just used.
3. S3 now helps only requests that branch off this conversation between S3 and S5, such as a regenerated turn 1 or a sub-task forked after turn 1. Every later turn of this conversation resumes at block 5 or deeper.

Under `lru`, S3 is evicted only after every block freed before it, including the cached context of idle conversations. With many concurrent conversations, such states pile up: in the runs above they held 13–14% of the GPU cache. Under `mamba_aware_lru`, S3 moves to the front of the free queue when turn 2 finishes, and the next allocation reuses its block.

### Design

- **When.** The policy runs for each Mamba `align` group when a request finishes. Preempted requests are skipped.
- **Scan.** It reads the request's block hashes from its end down to its prefix-cache hit, so its cost is bounded by what the request computed. The first cached state it meets is the request's new tip.
- **Demotion.** Every other cached state in that range that an earlier request left as its tip moves to the front of the free queue, unless a running request holds it. The block keeps its hash, so a reuse before the next allocation still hits.
- **Memory.** The set of tips is pruned to cached blocks once it grows past the pool size.

### Shared-prefix junctions

A shared-prefix junction (Marconi-style admission) is the state where prompts that share a prefix diverge, such as the end of a long system prompt. Other conversations resume from it, so it must keep its LRU order. It is never a tip unless its writer's own prompt ends on the same block, and that happens often: with 4,224-token blocks, a conversation whose first user message is short ends its first prompt on the system prompt's last block boundary. Its second turn would then demote the junction that every new conversation resumes from.

So the state at a request's own junction (`request.shared_prefix_boundary`, aligned as in `reachable_block_mask`) never becomes a tip and is never demoted. In a short smoke run with a 1,500-block GPU cache and without this exemption, new conversations' first turns fell from 45% to 31% cached. With it, first turns are at parity.

### Tradeoffs and limitations

- **Branching.** Workloads that resume from a superseded state, such as regenerate, rewind, tree search or a sub-task forked from a conversation, lose it sooner than under `lru`. In the 1-hour run, requests that returned after 30 s – 2 min idle were 2.3 points less cached (95.7% → 93.4%, about 330 requests per run). This fits a conversation that resumes after a forked sub-task: the fork resumed from the conversation's tip, cached a deeper state and finished first, which demoted that tip.
- **Light load.** A demoted state goes ahead of never-used blocks, so the next allocation reuses its block even when the cache is nearly empty, where `lru` would keep it until the cache fills. This matters only for branches.
- **First junction.** The first conversation to cache a state at a shared prefix, before any junction there is detected, records it as an ordinary tip. Its own next turn can then demote it, which costs one recompute of that prefix. The next conversation detects the junction, and from then on it is exempt.
- **Deferred frees (KV connectors).** With `pop_blocks_for_free`, the request still holds its blocks when the policy runs, so a superseded state that only this request held keeps its LRU order. Not validated with KV offloading.
- **EAGLE/MTP.** Speculative decoding shifts where prompts that share a prefix resume relative to the junction, and only the junction itself is exempt. Not validated.
- **Duplicates.** If the same state is cached in two blocks, only the one the lookup returns is demoted.
- **Coverage.** One model and one workload; no CPU offload tier and no speculative decoding.

### Why this is not a duplicate

I searched open PRs and issues on 2026-10-26, with terms such as "mamba eviction", "superseded mamba", "prefix cache eviction policy" and "mamba_aware".
- **#63578** (ours): the same rule for the CPU offload tier. This PR covers the GPU prefix cache, which has its own free queue.
- **#61282** keeps a running request's own prompt-boundary state referenced until the request ends, and frees it after its attention blocks. It decides when a request's state reaches the free queue; this PR decides where earlier turns' superseded states sit in it. The two compose: with #61282, the state a turn resumed from is released when the turn ends, which is when this PR demotes it.
- **#40270** adds pluggable, model-agnostic GPU eviction policies (2Q, ARC) under `gpu_eviction_policy`. If it lands first, `mamba_aware_lru` could become one of its values.
- **#55403** keeps blocks masked by sparse retention as low-priority entries, and **#50551** keeps Mamba decode checkpoints. Both keep more Mamba states cached; this policy stops superseded ones from crowding out live context.
- **RFC #57111** reorders a finished request's own blocks around its checkpoints and recomputes missing middle segments. This PR leaves a request's own order alone and evicts earlier turns' superseded states first.
