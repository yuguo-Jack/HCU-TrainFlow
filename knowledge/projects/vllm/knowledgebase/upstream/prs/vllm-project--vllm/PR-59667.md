# [CI] Automate dependency updates with hashes and a 7-day cooldown

[Upstream PR](https://github.com/vllm-project/vllm/pull/59667) · state: open · merged: False

## Overview

Add weekly refreshes that update dependency versions and SHA-256 hashes together, with a **7-day cooldown** for routine updates and an **informational vulnerability/change report**. Vulnerability blocking is **disabled by default**: findings and reporting failures do not stop patch publication. Dependabot security updates remain exempt from cooldown.

**Prerequisite:** merge #64241 for initial dependency hashes and enforcement checks.

**Rollout blocker:** after installing that prerequisite, the full refresh stops at XPU because required wheels, including `triton==3.8.0+xpu`, lack upload timestamps. The index needs timestamp metadata before all five locks can refresh. Required undated archives are rejected; there is no cooldown bypass.

## Claims

- Refresh the five compiled locks using the existing commands, first with `--upgrade`, then with a normalization pass. Both receive one seven-day UTC cutoff, including filtering fresh archives of existing versions. The workflow's helper dependencies also receive a seven-day cutoff.
- Group routine GitHub Actions and Cargo updates with `cooldown.default-days: 7`. Preserve security-only updates for handwritten Python requirements, including build and connector manifests.
- Produce Markdown/JSON reports showing added/removed dependencies, version changes, same-version hash changes, and known OSV advisories across all five locks. Check every environment marker without installing target packages, also querying public versions of vendor builds. Findings and incomplete checks remain informational; the workflow explicitly uses `continue-on-error: true` and omits the helper's opt-in `--enforce` flag.
- Produce a review artifact from a read-only compile job. **Automatic publishing remains disabled**; maintainers review changes before opening an update PR. The separate publisher validates its patch before obtaining App credentials.

## Details

The Python cooldown uses each registry archive's upload time. Required archives that are too new or lack timestamps stop compilation before artifact publication. Git, local, and direct-URL dependencies are outside the cooldown policy. Urgent compiled-lock fixes need a separately reviewed manual update; Dependabot security updates remain prompt. See [uv's cutoff behavior](https://docs.astral.sh/uv/concepts/resolution/) and [Dependabot's cooldown options](https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-options-reference#cooldown).

The review helper queries the [OSV batch API](https://google.github.io/osv.dev/post-v1-querybatch/) directly, avoiding dependence on GitHub manifest detection and host-platform marker evaluation. `dependency-review.md` appears in the job summary and artifact; `dependency-review.json` retains exact before/after hashes, completed queries, coverage errors, and a `complete` flag. Missing/incomplete reporting does not mean no vulnerabilities. This reporting is deliberately nonblocking, including bootstrap/tool failures. The optional `--enforce` mode is unused by the workflow; enabling it there requires an explicit policy change.

Cooldown gives the ecosystem time to detect malicious releases. Hashes identify selected bytes, and advisory queries report known affected versions. None proves package safety or publisher/build provenance. Vendor forks can differ from upstream. These locks do not record artifact sources, so the report cannot detect source changes; review configured indexes and provenance separately.

The workflow preserves platform constraints, Torch backends, indexes, and ROCm exclusions. Dependabot covers handwritten source manifests; the workflow handles the five compiled outputs. Exact incompatible pins and advisories without patched releases require manual remediation. The new report adds a bounded OSV API client and lock comparison helper outside runtime code; it does not change dependency selection.

During rollout, maintainers apply the patch against its recorded base and open the update PR manually. Enabling publishing later requires a repository-scoped GitHub App and an explicit workflow change. Documentation is under CI navigation at `docs/contributing/ci/dependency_updates.md`.

**Duplicate-work check:** #64241 supplies initial hashes and enforcement; this PR supplies ongoing refreshes, cooldown, and informational reporting, with no overlapping changed paths. Open-PR searches found no overlapping dependency-cooldown or dependency-vulnerability-audit implementation. Individual version/floor updates do not implement this automation.
