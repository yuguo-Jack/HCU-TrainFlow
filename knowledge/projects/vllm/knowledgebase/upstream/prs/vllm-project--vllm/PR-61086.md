# [Perf][RL] Batch incremental routed-expert transport

[Upstream PR](https://github.com/vllm-project/vllm/pull/61086) · state: open · merged: False

## Original PR description

## Overview

Batch routed-expert (R3) arrays at existing IPC boundaries without delaying incremental delivery. This addresses return-path overhead related to #56402 and investigated in [fork PR #105](https://github.com/aoshen02/vllm/pull/105); it supersedes the finish-only experiment, which lost partial R3 on frontend abort.

## Claims

- Approximately 19% higher output-token throughput in the original repeated Nemotron/GB200 comparison below; not a universal speedup claim.
- Preserve incremental output, including partial R3 on frontend abort and pause(abort).
- No scheduler, model-runner, async-output, or GPU-to-CPU scheduling changes. With R3 disabled, array packing is skipped; the appended optional wire field adds one nil byte, so wire bytes are not identical.

## Validation

TP1/DP4/EP on one four-GPU GB200 node; Multiproc, async scheduling, prefix caching, R3 and sampled-token logprobs enabled; batch 128, token budget 16,384, GPU memory utilization 0.45.

### Unified worker payload

Worker-to-EngineCore output now uses only `rows + spans`; the separate `materialized` dictionary and lookup fallback are removed. Historical R3 is still read after whole-batch publication, then appended to the same packed array as current-step rows. This preserves request token ranges and partial-output behavior, but copies historical results into the step array once more. The earlier GPU throughput results predate this simplification; its end-to-end throughput impact has not been measured.

The mixed same-batch producer/prefix-consumer test checks both outputs share the packed array. The reusable-SHM-slot test now covers both request spans in that single array. The related Aux/output-processor suite passed 111 tests (34 gated-tokenizer cases deselected); changed-file pre-commit passed.

### Capture/unpack cleanup

Removed redundant ndarray conversion in capture, used one slice assignment for both single-row and multi-row writes, and passed the already-checked packed payload explicitly to unpacking instead of checking for `None` twice. Length, dtype, shape, contiguity and buffer-ownership checks remain intact. The frozen final sources passed 111 Aux/output-processor tests (34 gated-tokenizer cases deselected), seven protocol checks under `python -O`, and changed-file pre-commit including mypy. A CPU-only capture-loop diagnostic measured 5.12 ms before versus 4.42 ms after (128 requests × 32 one-row captures; 30 alternating measured samples per arm); this is not GPU throughput. GB200 A/B runs for both the unified worker payload and this cleanup are still in progress; no new end-to-end speedup is claimed.

## Details

The overhead comes from transporting many tiny NumPy arrays and retaining one array object per incremental chunk. Reduce representation overhead at transport boundaries while preserving existing delivery and lifecycle semantics:

```text
Worker accepted rows
  -> one step array + request spans (including materialized history)
  -> existing EngineCore output thread packs one array + row counts
  -> frontend reconstructs per-request fields
  -> request-owned bytearray
  -> writable final output at existing finish/abort points
```

Mainline #61000 already copies out-of-band SHM payloads before releasing reusable queue slots; this PR does not add another Aux-specific deserialization copy. Ordinary completed requests transfer their request-owned bytearray to the final NumPy view and drop the accumulator reference; resumable streaming-input requests still copy so later appends cannot alter an earlier result. Rust reuses existing ndarray/frame decoding and restores its per-request payload. Clients must upgrade with the R3-enabled wire change. Packing adds CPU copies and bytearray has allocation slack; this is not a zero-copy or lower-RSS claim.

No open duplicate was identified in October 11 checks: #57966 omits prefixes, #57968 adds Mooncake keys, #59567 batches sampling masks, and #52723/#56778 add terminal Rust/gRPC payload support rather than this incremental IPC batching. Mooncake's keys-only frontend does not carry the full arrays targeted here; worker-tail batching would need separate measurements and preservation of `block_keys`. No speculative Mooncake performance PR is included.
