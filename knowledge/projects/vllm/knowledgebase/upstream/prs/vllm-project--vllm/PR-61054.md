# [Bugfix][KV Offload] Pass device pointers of host-registered CPU KV memory to batched copies

[Upstream PR](https://github.com/vllm-project/vllm/pull/61054) · state: open · merged: False

## Original PR description

## Purpose

Fixes #61052. CPU KV offload faults (Xid 31 / illegal memory access) on platforms where host memory pinned with `cudaHostRegister` is mapped at a device address that differs from its host address: NVIDIA vGPU and WSL2.

Both connectors pin pageable host memory with `cudaHostRegister` (`OffloadingConnector`: the mmap region in `pin_mmap_region`; `SimpleCPUOffloadConnector`: the CPU KV tensors) and then use `tensor.data_ptr()`, the host address, as the copy pointer. `cudaMemcpyAsync` translates such addresses itself, but `cuMemcpyBatchAsync` and the Triton swap kernel use them as given. On bare-metal Linux the two addresses are equal, so the bug does not show there.

Changes:

- `OffloadingConnector`: `compute_sub_block_ptrs` translates CPU-side pointers to device pointers. The region is registered in row-aligned chunks of `MAX_HOST_REGISTER_CHUNK_BYTES`, each of which may get its own device mapping, so the device base of each chunk is looked up once with `cudaPointerGetAttributes` and cached per tensor. This covers the direct and canonical layouts and both the batched-copy and Triton paths.
- `SimpleCPUOffloadConnector`: `build_params` uses the device address of each CPU tensor.
- Nothing changes where the two addresses are equal, for pageable (unregistered) memory, or on ROCm and XPU.

The first revision of this PR added `VLLM_KV_OFFLOAD_DISABLE_BATCH_MEMCPY` to fall back to per-copy memcpy. That covered only the batched path and left the cause in place, so this revision replaces it.

## Test Plan

- Unit tests that need no GPU (`cudaPointerGetAttributes` is faked): `tests/v1/kv_offload/test_host_registered_device_ptrs.py`. They cover a single and a multi-chunk device mapping with the device address below the host address, pageable memory, equal addresses, and `SimpleCPUOffloadConnector`.
- H200 NVL with NVIDIA vGPU (H200-70C, guest driver 595.91.x): copies through both connectors' pointer paths into `cudaHostRegister`'ed shared mmap memory, with `cuMemcpyBatchAsync` (3 MiB pages) and the Triton kernel (16 KiB pages), GPU to CPU and back, each case in its own process.
- Same machine, end to end: `Qwen/Qwen3.8-27B-FP8` serving 40 concurrent requests with 8k-token prompts, once with each connector.
- WSL2: pending (@<commenter> offered to test).

## Test Result

Unit tests: 5 passed.

vGPU copies:

| path | host address | device address | store | load |
|---|---|---|---|---|
| `OffloadingConnector` + `cuMemcpyBatchAsync` (3 MiB pages) | `0x7ed1a8000000` | `0x10026000000` | ok | ok |
| `OffloadingConnector` + Triton kernel (16 KiB pages) | `0x7b6e01418000` | `0x10025e00000` | ok | ok |
| `SimpleCPUOffloadConnector` | `0x76f170000000` | `0x10026000000` | ok | ok |

Before this change, the batched copy and the Triton kernel both faulted on the host address of the same kind of buffer (see #61052).

Reworked and force-pushed. The root cause turned out to be the address passed to the batched copy, not `cuMemcpyBatchAsync` itself (see the discussion in #61052): memory pinned with `cudaHostRegister` gets a device address that differs from its host address on vGPU and WSL2. This revision passes the device address in both connectors instead of adding an opt-out env var, which also covers the Triton load path. The description is updated with the new approach and the vGPU results.
