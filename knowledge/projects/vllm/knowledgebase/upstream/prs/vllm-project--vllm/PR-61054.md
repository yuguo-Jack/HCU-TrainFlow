# [Bugfix][KV Offload] Add VLLM_KV_OFFLOAD_DISABLE_BATCH_MEMCPY to bypass cuMemcpyBatchAsync

[Upstream PR](https://github.com/vllm-project/vllm/pull/61054) · state: open · merged: False

## Original PR description

## Purpose

Fixes #61052

On NVIDIA vGPU guests (H200 NVL, vGPU 595.91.x), `cuMemcpyBatchAsync` resolves fine via `cuGetProcAddress` but faults at runtime (host Xid 31, `unspecified launch failure`), even for a single in-bounds descriptor. Plain per-copy memcpy on the same addresses works at full PCIe bandwidth. As a result, CPU KV offload crashes on the first transfer with both connectors on these platforms.

vLLM calls `cuMemcpyBatchAsync` from two independent places:

1. **C++** `swap_blocks_batch` (`csrc/libtorch_stable/cache_kernels.cu`), used by `OffloadingConnector` (and the EC CPU connector / hisparse). It already has a per-copy `cudaMemcpyAsync` fallback for older drivers and the legacy default stream.
2. **Python** `copy_blocks` (`vllm/v1/simple_kv_offload/cuda_mem_ops.py`), used by `SimpleCPUOffloadConnector`, which calls the driver entry point through ctypes and has no fallback.

This PR adds one opt-out, `VLLM_KV_OFFLOAD_DISABLE_BATCH_MEMCPY=1`, honored by both:

- `cache_kernels.cu`: `batch_memcpy_disabled()` reads the env var once (cached, same pattern as `resolve_max_batch_descriptors()`). When set, `batch_fn` resolves to `nullptr`, so the **existing** per-copy fallback is used. No new copy path in C++.
- `cuda_mem_ops.py`: when set (CUDA only), `copy_blocks` issues one `cuMemcpyAsync` per descriptor on the same stream, reusing the already-expanded `src_all` / `dst_all` / `sz_all` arrays. `cuMemcpyAsync` is resolved via `cuGetProcAddress`, matching how the batch entry point is resolved in the same file.
- `envs.py`: register `VLLM_KV_OFFLOAD_DISABLE_BATCH_MEMCPY` (default `False`) next to `VLLM_KV_OFFLOAD_MAX_BATCH_DESCRIPTORS`.

Default behavior is unchanged. ROCm (`hipMemcpyBatchAsync`) is intentionally left untouched in both places since I can only validate on CUDA; happy to extend it if preferred.

Notes:
- `VLLM_KV_OFFLOAD_MAX_BATCH_DESCRIPTORS=1` does not help, since the batch API faults even with one descriptor.
- In `SimpleCPUOffloadConnector`, `build_params()` still resolves the `cuMemcpyBatchAsync` pointer; resolving it is harmless on vGPU, only calling it faults. Kept as-is to minimize the diff.
- The Python fallback loops over `num_blocks × num_layers` descriptors per transfer on the connector's background copy thread. This only applies when the opt-out is set.

## Test Plan

1. Standalone repro (no model), calling `vllm._custom_ops.swap_blocks_batch` with vLLM's own descriptor buffers, `/dev/shm`-backed `cudaHostRegister` memory and in-bounds addresses, 4 MiB per descriptor, both directions: [swap_test.py](https://gist.github.com/jerry102039/860de1bb1810a962c58bab7668bd2a03)
2. End-to-end with `vllm serve Qwen/Qwen3.8-27B-FP8`, once with `OffloadingConnector` (`cpu_bytes_to_use=64 GiB`) and once with `SimpleCPUOffloadConnector` (`cpu_bytes_to_use=128 GiB`), each under a saturating random-dataset benchmark (1000 requests) so that both stores and preemption-driven loads occur.
3. Check host `dmesg` for Xid after each run.

Hardware: H200 NVL vGPU (70 GiB profile), host vGPU manager 595.91.04, guest driver 595.91.07, Python 3.14, TP=1.

## Test Result

| Run | Flag unset (default) | `VLLM_KV_OFFLOAD_DISABLE_BATCH_MEMCPY=1` |
|---|---|---|
| repro (`ops.swap_blocks_batch`) | ❌ crashes on the first call, Xid 31 | ✅ GPU→CPU 48.5 GiB/s, CPU→GPU 47.5 GiB/s, 0 mismatches |
| `OffloadingConnector` end-to-end | ❌ engine dies on the first offload store, Xid 31 | ✅ stores ~50 GiB/s, loads ~49 GiB/s, no Xid |
| `SimpleCPUOffloadConnector` end-to-end | ❌ engine dies on the first store (copy thread), Xid 31 | ✅ stores and loads run continuously
