# [Bugfix][Metrics] Fix waiting and running adapter labels in vllm:lora_requests_info

[Upstream PR](https://github.com/vllm-project/vllm/pull/63261) · state: open · merged: False

## Original PR description


## Overview

Fixes the adapter labels of `vllm:lora_requests_info`, which have been wrong since #26801. Every adapter with a tracked request is listed in both `running_lora_adapters` and `waiting_lora_adapters`, and a request queued at the engine never shows up in `waiting_lora_adapters`.

## Claims

- `running_lora_adapters` lists only adapters with running requests, and `waiting_lora_adapters` lists only adapters with waiting requests. With `--max-loras 1`, `lora-a` requests running and `lora-b` requests queued, upstream main reports `running_lora_adapters="lora-a",waiting_lora_adapters="lora-a"`. With this PR it reports `running_lora_adapters="lora-a",waiting_lora_adapters="lora-b"`.
- A request counts as waiting from the moment the frontend adds it until its first output arrives, as it did before #26801.
- LoRA state is cleared in `OutputProcessor._finish_request`, so a request the engine rejects on arrival (now tracked from `add_request`) leaves no entry behind. #56663 proposes the same one-line move for streaming-input sessions; see Details.
- The change is limited to the frontend's LoRA request bookkeeping. Model outputs and scheduling are unaffected, so no accuracy evaluation is included.

that vLLM tests use, so `vllm serve --enable-lora` has two adapters."""

import os

import torch
from peft import LoraConfig, get_peft_model
from transformers import AutoModelForCausalLM

BASE = "hmellor/tiny-random-LlamaForCausalLM"

for name, seed in [("lora-a", 1), ("lora-b", 2)]:

    )
    peft_model = get_peft_model(model, config)

`client.py`, run as `python client.py --port 8765 --out <dir>`:

```python
"""Send concurrent completions for two LoRA adapters and scrape /metrics
while they are in flight. Prints each change of the current
vllm:lora_requests_info series (the one with the newest timestamp value)
together with the engine-side running/waiting gauges."""

import argparse
import asyncio
import json
import re
import time

import httpx

SERIES_RE = re.compile(r"^(vllm:[a-z_]+)\{(.*)\} (\S+)$")
LABEL_RE = re.compile(r'(\w+)="([^"]*)"')


def parse(text: str):
    lora_series, gauges = [], {}
    for line in text.splitlines():
        m = SERIES_RE.match(line)
        if not m:
            continue
        name = m.group(1)
        labels = dict(LABEL_RE.findall(m.group(2)))
        value = float(m.group(3))
        if name == "vllm:lora_requests_info":
            lora_series.append((value, labels))
        elif name in ("vllm:num_requests_running", "vllm:num_requests_waiting"):
            gauges[name.split(":")[1]] = value
    return lora_series, gauges


async def scrape_loop(client, stop, changes):
    last = None
    while not stop.is_set():
        r = await client.get("/metrics")
        series, gauges = parse(r.text)
        if series:
            _, labels = max(series, key=lambda s: s[0])
            key = (
                labels.get("running_lora_adapters"),
                labels.get("waiting_lora_adapters"),
                gauges.get("num_requests_running"),
                gauges.get("num_requests_waiting"),
            )
            if key != last:
                changes.append((time.monotonic(), key))
                last = key
        await asyncio.sleep(0.01)


async def complete(client, model, max_tokens):
    r = await client.post(
        "/v1/completions",
        json={
            "model": model,
            "prompt": "Hello, my name is",
            "max_tokens": max_tokens,
            "temperature": 0,
            "ignore_eos": True,
        },
        timeout=300,
    )
    r.raise_for_status()
    return r.json()["usage"]["completion_tokens"]


async def main():
    ap = argparse.ArgumentParser()
    ap.add_argument("--port", type=int, required=True)
    ap.add_argument("--out", required=True)
    ap.add_argument("--n", type=int, default=8)
    ap.add_argument("--max-tokens", type=int, default=200)
    args = ap.parse_args()
    async with httpx.AsyncClient(base_url=f"http://127.0.0.1:{args.port}") as client:
        stop, changes = asyncio.Event(), []
        scraper = asyncio.create_task(scrape_loop(client, stop, changes))
        await asyncio.sleep(0.2)
        t0 = time.monotonic()
        tasks = [
            asyncio.create_task(complete(client, "lora-a", args.max_tokens))
            for _ in range(args.n)
        ]
        await asyncio.sleep(0.05)
        tasks += [
            asyncio.create_task(complete(client, "lora-b", args.max_tokens))
            for _ in range(args.n)
        ]
        tokens = await asyncio.gather(*tasks)
        elapsed = time.monotonic() - t0
        await asyncio.sleep(0.3)
        stop.set()
        await scraper
        final = (await client.get("/metrics")).text
    print(
        f"requests: {len(tokens)} completion_tokens: {sum(tokens)} "
        f"elapsed_s: {elapsed:.2f}"
    )
    print("in-flight changes of the newest vllm:lora_requests_info series:")
    print("  t_ms  running_lora_adapters | waiting_lora_adapters | engine running/waiting")
    for t, (run, wait, n_run, n_wait) in changes:
        print(
            f"  {1000 * (t - t0):6.0f}  running={run!r} | waiting={wait!r} | "
            f"{n_run}/{n_wait}"
        )
    print("all vllm:lora_requests_info series after the run:")
    for line in final.splitlines():
        if line.startswith("vllm:lora_requests_info{"):
            print("  " + line)
    with open(f"{args.out}/metrics_final.txt", "w") as f:
        f.write(final)
    with open(f"{args.out}/changes.json", "w") as f:
        json.dump([(t - t0, k) for t, k in changes], f)


asyncio.run(main())
```

## Details

Root cause, both from #26801:

- `LoRARequestStates.update_scheduler_stats` writes every tracked adapter into `waiting_lora_adapters` and `running_lora_adapters`, zero counts included ([stats.py](https://github.com/vllm-project/vllm/blob/db3b0f0fae4bc98492b3863685e541e62bc59576/vllm/v1/metrics/stats.py#L699-L704)). `PrometheusStatLogger.record` joins the dict keys ([loggers.py](https://github.com/vllm-project/vllm/blob/db3b0f0fae4bc98492b3863685e541e62bc59576/vllm/v1/metrics/loggers.py#L1224-L1236)), so an adapter with only running requests is also listed as waiting. The aggregation before #26801 skipped adapters with no waiting or no running requests.
- #26801 also dropped the hook in `OutputProcessor.add_request` that marked a new request as waiting ([output_processor.py](https://github.com/vllm-project/vllm/blob/db3b0f0fae4bc98492b3863685e541e62bc59576/vllm/v1/engine/output_processor.py#L663-L693)). The engine core sends a request's events only with an output, and a request emits no output before it is scheduled and finishes its prefill, so QUEUED and SCHEDULED arrive together in its first output. The frontend never sees the waiting phase, including requests held back because all `max_loras` slots are busy.

Changes:

- `LoRARequestStates.update_scheduler_stats` writes an adapter into a dict only when it has requests in that state.
- `OutputProcessor.add_request` marks a new request as waiting. The streaming-input update path returns before this call, so input chunks for an existing request are not counted again. Child requests of `n > 1` are tracked one by one, as before.
- `OutputProcessor._finish_request` clears the LoRA state, and `_update_stats_from_finished` no longer does. Every path that drops a request goes through `_finish_request` or `abort_requests`, which already cleared it. This PR needs the move for requests rejected on arrival, which `add_request` now tracks. The move also releases streaming-input sessions that close after their last output, which leak on upstream main; that is the fix #56663 proposes with the same hunk.

The design doc names an external user of this gauge (`docs/design/metrics.md`):

> - `running_lora_adapters`: a per-adapter count of the number requests
>   running using that adapter, formatted as a comma-separated string.
> - `waiting_lora_adapters`: similar, except counting requests that are
>   waiting to be scheduled.
>
> [...]
>
> This was added in <https://github.com/vllm-project/vllm/pull/9477> and there is
> [at least one known user](https://github.com/kubernetes-sigs/gateway-api-inference-extension/pull/54).

The gateway's [model server protocol](https://github.com/kubernetes-sigs/gateway-api-inference-extension/blob/db75ec81b80f8728835b56cdb445e8ff1fbfd430/docs/proposals/003-model-server-protocol/README.md) reads these labels for LoRA affinity routing and defines `waiting_lora_adapters` as "A comma separated list of adapters that are waiting to be served".

Rust frontend: `rust/src/engine-core-client` (#45030) tracks LoRA phases per request in its own registry. A request registers as waiting (`client/state.rs`), events move it, and each adapter goes only into the set of its requests' phase. Its exporter test already expects `running_lora_adapters="d",waiting_lora_adapters=""`. It does not read the Python `SchedulerStats` dicts, so this PR leaves it unchanged.

Related open PRs (searched on 2026-10-22 for `lora_requests_info`, `waiting_lora_adapters`, `running_lora_adapters`, `LoRARequestStates`, `request_waiting`, and recently updated LoRA metrics PRs):

- #56663 (open, needs rebase) moves the same `request_finished` call into `_finish_request` and adds a streaming-input test. It does not touch the label filtering or `add_request`, which are the bug fixed here. The `output_processor.py` hunks are identical and merge cleanly in either order (`git merge-tree` shows no conflict there); this PR leaves the streaming-input test to #56663.
- #54830 marks `vllm:lora_requests_info` as deprecated in its help text and docs, keeps it emitted, and adds LoRA load metrics. It does not touch `LoRARequestStates`, `OutputProcessor` or the label code, and this PR does not touch `loggers.py` or the docs.
- #56238 changes the QUEUED timestamp handling in `IterationStats.update_from_events`, another hunk of `stats.py`.
- #31740 and #41834 match the search terms but do not modify these files.
- No open issue reports this bug.

Unchanged limitations: the frontend learns about scheduling only from events attached to outputs. A request counts as waiting until its first output, including during a multi-step chunked prefill, and a preempted request counts as running until it produces output again. Both match the behavior before #26801. A streaming-input session also keeps its last state (running) between input chunks, as on upstream main.
