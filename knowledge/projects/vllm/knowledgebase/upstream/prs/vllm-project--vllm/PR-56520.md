# [Bugfix][Frontend] Keep inline system messages in place for encoder-based tokenizers (Anthropic API)

[Upstream PR](https://github.com/vllm-project/vllm/pull/56520) · state: closed · merged: False

## Original PR description

## Purpose

Fix prefix caching for Anthropic Messages API clients that send `role: system` messages inside
`messages` (Claude Code appends `<total_tokens>N tokens left</total_tokens>` after every tool
result) when the model uses an encoder-based tokenizer with no jinja chat template
(`--tokenizer-mode deepseek_v4`, `deepseek_v41`).

`_detect_merge_inline_system()` returns `True` whenever `chat_template` is falsy, so every inline
system message is merged into the leading system block. Each turn then changes the prompt right
after the system+tools region and the whole conversation is re-prefilled on every call.
Observed with Claude Code against DeepSeek-V4-Flash: `cache_read_input_tokens` pinned at
8192/12288 for 101 calls while the context grew to 84K tokens (4.97M prompt tokens sent, 4.30M
re-prefilled, 0.52M actually changed).

Fixes #<issue>.

## Changes

- `TokenizerLike.supports_inline_system_messages` (default `False`): the tokenizer's encoder
  renders `role: system` at any position and still emits the generation prompt after a trailing one.
- DeepSeek V4 and V4.1 wrappers set it to `True` (their `encode_messages` already appends the
  assistant header after a mid-conversation or trailing system message).
- `AnthropicServingMessages._detect_merge_inline_system(chat_template, tokenizer)`: with no
  template, merge unless the tokenizer explicitly declares support. Jinja-template detection is
  unchanged. Every other tokenizer keeps today's behavior.

## Test plan

- `tests/entrypoints/anthropic/test_anthropic_messages_conversion.py::TestDetectMergeInlineSystem`:
  4 new cases (no flag → merge, flag → no merge, non-bool truthy attribute → merge, DeepSeek V4
  wrapper declares support). File passes (66 tests).
- pre-commit clean (ruff, mypy, typos, SPDX).
- Live: Claude Code 2.1.268 → vLLM `/v1/messages` → DeepSeek-V4-Flash TP=2 on 2x DGX Spark.
  `cache_read_input_tokens` per consecutive tool turn: stock 15104/15104/15104/15104, patched
  15104/15360/15616/15872; each request is an exact token-level extension of the previous one and
  every prompt still ends with `<|Assistant|><think>` (verified by rendering captured requests).

Note: an older vLLM build (0.25.2.dev, July) lacks the encoder change that appends the assistant
header after a trailing system message; on that build a downstream workaround also emits inline
system text as a user message. `main` already has the encoder change, so this PR only touches the
adapter/tokenizer contract.

- alxrxs · comment · 2026-09-18T12:26:03Z · [source](https://github.com/vllm-project/vllm/pull/56520#issuecomment-5729957239)

Ran into this exact problem with Claude Code against DeepSeek-V4.1-Flash (8×H100, `nightly-dc36fcce`, TP8, `--tokenizer-mode deepseek_v41`) and spent a while chasing it before finding this PR.

Claude Code appends a `role: system` message at the end of every request with a changing token count in it. With the current detector that gets merged into the leading system block, so the prompt head changes every turn and the prefix cache barely hits. On a ~330k token conversation, two consecutive requests that differ only in that trailing message:

- merge on: 14,592 / 331,983 tokens hit, ~75 s prefill
- merge off: 331,776 / 331,983 hit, 1.7 s

The 14.5k that hit is just the base system prompt + tools. Every agent turn was effectively a full re-prefill.

I patched `_detect_merge_inline_system` locally to return False for this tokenizer, which is what this PR does properly via the flag. Been running it for a few days now, outputs unchanged. Would be great to get this merged.
