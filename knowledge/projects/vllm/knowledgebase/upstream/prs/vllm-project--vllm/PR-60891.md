# [Bugfix] Dequantize DeepSeek-V4 wo_a for non-DeepGEMM linear backends

[Upstream PR](https://github.com/vllm-project/vllm/pull/60891) · state: open · merged: False

## Original PR description



## Overview

DeepSeek-V4 fails at engine init with `--linear-backend marlin` (#60587) or `triton`. `deep_gemm_fp8_o_proj` reads `wo_a.weight` directly and only understands the grouped `[g, r, d]` FP8 layout that the DeepGEMM linear kernels leave behind. Other backends lay the weight out for their own GEMM. This PR dequantizes such a `wo_a` to BF16 after loading so the existing BF16 bmm branch handles it.

Fixes #60587.

## Claims

- DeepSeek-V4-Flash starts and generates with `--linear-backend marlin` and `--linear-backend triton` (both crashed in `_o_proj` during profiling before).
- With real weights, GSM8K under `--linear-backend marlin` matches the default backend (table below).
- Default path (DeepGEMM / FlashInfer-DeepGEMM kernels) is unchanged: `wo_a` is already the 3D FP8 tensor, so the new hook returns early.

## Details

Root cause: `wo_a` is a `ColumnParallelLinear` marked `is_bmm`, but it is never called. `deep_gemm_fp8_o_proj` takes `wo_a.weight` (and its scale) and feeds them to `fp8_einsum`, or to a BF16 `bmm` when the weight is not FP8. Only `DeepGemmFp8BlockScaledMMKernel.process_weights_after_loading` (also used by the FlashInfer-DeepGEMM kernel) reshapes the weight to `[g, r, d]` with DeepGEMM scales. The kernel is picked in `create_weights`, before `is_bmm` is set, and `--linear-backend` applies to every FP8 linear, so `wo_a` can end up in Marlin's packed int32 layout or a plain 2D FP8 tensor.

The fix is local to the three CUDA attention layers that call `deep_gemm_fp8_o_proj` (FlashMLA, FlashInfer SM100, FlashInfer SM120). Their new `process_weights_after_loading` runs after every quant method's own processing (deferred attention layers), and calls `maybe_dequant_wo_a`, which uses `get_and_maybe_dequant_weights` (same helper MLA uses for `kv_b_proj`). For Marlin and the DeepGEMM-capable platforms it dequantizes through the kernel's own `apply`, so it does not depend on each backend's layout. ROCm/XPU/CPU subclasses are untouched since their `wo_a` paths differ. On the SM100 FlashInfer layer, RopeQuant was decided in `__init__` against the not-yet-loaded FP8 weight, so it is rechecked after the swap.

Tradeoffs: on non-DeepGEMM backends `wo_a` is held in BF16 (4096x8192 per layer, about 1.5 GB more for DeepSeek-V4-Flash at TP=1, split across TP ranks) and that projection runs as a BF16 bmm. The default backend keeps the FP8 path.

Limitations:
- `cutlass` and `torch` still fail before reaching `_o_proj`: their block-FP8 GEMMs reject the checkpoint's UE8M0 scales (#47988 covers CUTLASS/Triton E8M0 handling). Out of scope here.
- The reporter is on GB10 (SM121), which I don't have. I validated on H100/H200. The SM120 layer gets the same hook.

Not a duplicate:
- #56119 (open, last updated 09-24, merge conflicts, no review) dequantizes `is_bmm` weights inside `Fp8LinearMethod` only when Marlin is selected. This PR keeps shared FP8 code untouched and covers any backend that leaves `wo_a` outside the DeepGEMM layout: Triton is verified above; B12x (used by the GB10 recipe) also keeps a plain 2D FP8 weight and takes the same path, not run.
- #55172 adds a BF16 helper for SM8x. I applied its `o_proj.py` on H100 with `--linear-backend marlin` and it still fails (`marlin_gemm ... a.size(1) = 32768, size_k = 4096`), because it infers the group width from the packed Marlin weight.
- #41834 (SM12x enablement, open since May) makes Marlin refuse block-FP8 layers instead.

AI assistance (Claude Code) was used to find the root cause, write the change and run the validation above.
