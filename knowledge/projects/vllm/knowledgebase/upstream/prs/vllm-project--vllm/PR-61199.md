# [Fix] Warn when unsupported Anthropic system content is ignored

[Upstream PR](https://github.com/vllm-project/vllm/pull/61199) · state: open · merged: False

## Original PR description



## Overview

Fixes #61172. The Anthropic entrypoint's system conversion silently drops any non-`text` content block (e.g. an `image` block) both in the top-level `system` field (`_convert_system_message`) and in inline system messages (`_extract_system_text`). The OpenAI endpoint already warns about this (#34072) but the Anthropic path never did, so unsupported blocks vanished without a trace.

## Claims

- Emit a `logger.warning_once` naming the dropped content type when an unsupported Anthropic system content block is ignored, mirroring the OpenAI endpoint's wording.
- `tool_addition` / `tool_removal` blocks in inline system messages do not warn: they are not ignored, `_resolve_tools` applies them to the tool list (review feedback).
- Keep the existing behavior of ignoring unsupported blocks (backward compatible) — only the warning is added.

## Validation

- `ruff check` / `ruff format` (0.14.0) and mypy clean.
- `tests/entrypoints/anthropic/test_anthropic_messages_conversion.py` + `test_protocol_exports.py`: 116 passed on the branch and on a merge with main `87e7dce3a7`.
- New regression tests: top-level and inline image blocks warn while text is preserved; text-only / string / billing-header cases do not warn; tool changes do not warn and are still applied; a mixed message warns only for the image block (inline and merged-system paths).
- The tool-change tests fail on the previous head and pass now. The warning tests use the existing `disable_log_dedup` fixture; without it, the inline-image test depended on test order.

## Details

Root cause: `_convert_system_message` / `_extract_system_text` drop any content block whose type is not `text` without notifying the caller, so callers can pass e.g. `system: [{"type":"image",...}]` and have it silently ignored. The fix keeps the drop (backward compatibility) but surfaces it with a once-per-type warning.

Thanks @vadiklyutiy, you're right. `tool_addition`/`tool_removal` blocks are only allowed in `role: "system"` messages, and `_resolve_tools` applies them to the tool list, so reporting them as ignored was wrong.

Fixed in 5d07ceb266: `_extract_system_text` now skips those two block types without a warning. Other non-text blocks still warn. The top-level `system` field needs no change, because its validator already rejects tool-change blocks.

Tests:

- A system message with text, `tool_addition` (by reference and by definition) and `tool_removal` produces no warning. The test also checks that `_resolve_tools` still applies the blocks: the deferred tool is loaded, the tool added by value is present, and the removed tool is gone. Both the inline and the merged-system paths are covered.
- Adding an `image` block to that message produces exactly one warning, and it names `image`.
- Both new tests fail on the previous head (4 warnings instead of 0 or 1) and pass now.

While checking this, I found that the previous head's own `test_inline_system_image_block_warns_and_ignored` failed when it ran after the top-level test. `warning_once` deduplicates per process, so the second identical warning never reached `caplog`. The class now uses the existing `disable_log_dedup` fixture. That change is test-only.

`test_anthropic_messages_conversion.py` + `test_protocol_exports.py`: 116 passed, both on the branch and on a merge with current main (`87e7dce3a7`). ruff 0.14.0 and mypy are clean.
