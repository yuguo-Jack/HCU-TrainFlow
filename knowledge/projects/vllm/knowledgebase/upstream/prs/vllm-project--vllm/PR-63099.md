# [Bugfix][ROCm] Match the DeepSeek-V4.1 FP8 config in the shared-expert FSE compatibility check

[Upstream PR](https://github.com/vllm-project/vllm/pull/63099) · state: closed · merged: True

## Original PR description

## Overview

On CUDA and ROCm, `deepseek_v4_fp8` always resolves to the DeepSeek-V4.1 `DeepseekV4FP8Config`, which subclasses `Fp8Config`, not the V4 class. `is_shared_expert_quant_fse_compatible` runs its DeepSeek-V4 checks only for the V4 class, so on these platforms it falls through to the generic `Fp8Config` branch and reports every DeepSeek-V4 shared expert as FSE-compatible. This PR matches both classes for MXFP4 routed experts, as the online-quantization branch of the same function already does.

Founded by Hyperloom.

## Claims

- Fixes the weight-loading failure of DeepSeek-V4-Flash on ROCm with `VLLM_ROCM_USE_AITER_FUSION_SHARED_EXPERTS=1`. Quark MXFP4 checkpoints hit the same failure on the FP8 MTP shared expert.
- No change when the variable is unset: the check is not called.
- No change for FP8-expert checkpoints such as DeepSeek-V4-Flash-Base: they keep the generic FP8 check, as on main.
- Adds `test_deepseek_v41_quant_config_rejects_fp8_mtp_shared_expert_fse` and `test_deepseek_v41_fp8_experts_keep_fp8_fse_check`.

## Validation

MI355X (gfx950), `deepseek-ai/DeepSeek-V4-Flash`, TP1, `--kv-cache-dtype fp8 --block-size 256`, vLLM built from main at 15a78aa88e (the touched files are unchanged on current main).

With `VLLM_ROCM_USE_AITER_FUSION_SHARED_EXPERTS=1`, main fails during weight loading in 2 of 2 runs:

```
KeyError: 'layers.0.ffn.experts.routed_experts.w13_weight_scale_inv'
```

With this PR, all 43 layers reject FSE ("only implemented/tested with Quark MXFP4"), run the shared expert unfused, and serve.

`vllm bench serve`, random 1000 in / 200 out, 400 prompts, concurrency 50, a fresh server per run. 4 runs per arm, median of the last 3, within-arm spread in parentheses:

| Arm | Total tok/s | Median TTFT (ms) | Median TPOT (ms) |
|---|---|---|---|
| main, variable unset | 10061 (±3.5%) | 1026 | 24.68 |
| this PR, variable unset | 10033 (±0.8%) | 1024 | 24.76 |
| this PR, variable = 1 | 10045 (±0.2%) | 1027 | 24.77 |

GSM8K, 5-shot, greedy, 1319 items, `lm_eval --model local-completions`:

| Arm | strict-match | Same verdict as main |
|---|---|---|
| main | 0.9515 ± 0.0059 | - |
| main, repeated (noise floor) | 0.9568 ± 0.0056 | 98.10% |
| this PR, variable = 1 | 0.9538 ± 0.0058 | 97.95% |

DeepSeek-V4-Flash-Base (FP8 experts), TP2, vLLM built from main at b3b0bc3059: with the variable set, main runs the shared expert fused (257 experts, top-7 in the MoE), and GSM8K (same settings as above) stays within the noise of unfused runs: 0.9174 vs 0.9090 and 0.9234 from two runs without the variable. This PR gives the same FSE answer as main for this checkpoint.

Unit tests on MI355X against the built tree, `pytest tests/model_executor/layers/test_fused_shared_expert.py`: this PR 107 passed. Main fails `test_deepseek_v41_quant_config_rejects_fp8_mtp_shared_expert_fse`; `test_deepseek_v41_fp8_experts_keep_fp8_fse_check` passes on both.

## Details

The existing unit test missed the bug because it constructs the V4 class directly. CI does not run DeepSeek-V4 with this variable set; the new tests are CPU-only.

AI assistance (Hyperloom with Claude) was used to find and prepare this change. I reviewed every changed line and reproduced the results above.
