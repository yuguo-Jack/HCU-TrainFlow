# [ROCm][MORI IO]Moriio handshake failure 

[Upstream PR](https://github.com/vllm-project/vllm/pull/65690) · state: open · merged: False

## Original PR description



## Overview

In MoRIIO READ mode, a failed decode→prefill handshake, or a single request rejected by decode's serving layer, killed the whole decode engine. After this change only the affected requests fail or are recomputed, per `kv_load_failure_policy`, and decode keeps serving. Addresses gaps 4 (READ side) and 9 of [ROCm/mori#759](https://github.com/ROCm/mori/issues/759), and fits the reclamation rule proposed in #63336: a failed handshake posts no reads, so nothing has to be proven quiet before prefill's blocks are released.

## Claims

- **Gap 4, failed handshake (READ):** the eager handshake still votes across TP ranks, but a failed engine no longer raises `HandshakeError` from `start_load_kv`. Only the requests of that prefill engine are reported as load errors, prefill is asked to release their blocks, and the engine is retried on the next step that needs it.
- **Multi-group layouts:** block-level load errors (`invalid_block_ids`) are reported only when the scheduler can map them back, i.e. one KV cache group and no recurrent state. Before, a sliding-window model under the hybrid KV cache manager reported block IDs after the forward pass had already used the failed KV, and `_handle_invalid_blocks` then raised. Such layouts now fail the step before the forward pass, as hybrid (Mamba) models already did. The engine still stops for them; recovering them per request needs a scheduler change and is left to follow-up work (see Limitations).
- **Rejected requests:** a P/D request rejected by decode's serving layer (e.g. a prompt over decode's `max_model_len`) crashed decode on the next `schedule()`. MoRIIO READ now skips a release whose prefill address cannot be resolved, as WRITE mode already does.
- **Gap 9:** drop the worker's `_reqs_to_send`, which grew by one entry per prefill request and was never read; producer expiry is owned by the scheduler (`_deferred_send_deadlines`).

## Validation

Single-node P/D pair on MI355X (prefill GPU0, decode GPU1, xGMI, dummy weights, Qwen3-32B layout), built on `moriio_integration/test_write_dummy_e2e_rocm.py`. Faults are injected on the decode worker only: the decode→prefill handshake raises once, or one request is sent straight to decode with a prompt over its `max_model_len`. The nightly image (`edad8b03c5`) was used with this branch's commits applied.

Each request is a `/v1/completions` call through the proxy (600-token prompt, `max_tokens=4`). "Returns 200" means it completed end to end: HTTP 200 with generated tokens, so prefill, the KV transfer and decode all worked. "Fails" means the engine ended that request with an error, as `kv_load_failure_policy=fail` requires. These runs use dummy weights, so they check that requests complete, not the text; output correctness is the separate `test_read_matches_direct_serve` result below.

| Scenario | Before | After |
|---|---|---|
| Handshake fails once, `kv_load_failure_policy=fail` (default) | Decode engine dies; every later request fails | That request fails; decode stays healthy; the handshake is retried and the next 4 requests return 200 |
| Handshake fails once, `recompute` | Decode engine dies | `Recovered from KV load failure: 1 request(s) rescheduled`; the request and all later ones return 200 |
| One request rejected by decode (HTTP 400) | Decode engine dies on the next step (`ValueError: request_id ... does not embed a peer zmq_address`) | 400; decode stays healthy; later requests return 200 |

Unit tests (`pytest tests/v1/kv_connector/unit/test_moriio_*.py`): 886 passed. The new tests fail without the fix: `test_failed_handshake_fails_only_its_requests` (the step raised), `test_failed_handshake_*_without_block_recovery[sliding]`, `test_*_reports_blocks_only_for_one_group[False-False-*]`, and `test_read_abort_before_scheduling_releases_only_routable_requests[False]`. `pre-commit` (ruff 0.14.0) passes.

Across two MI355X nodes over RDMA (prefill and proxy on one node, decode on the other), with the same faults:

| Scenario | Before | After |
|---|---|---|
| Handshake fails once, decode TP1 | Decode engine dies | That request fails; the next 4 return 200 |
| Handshake fails on one of two decode TP workers (TP2 on both sides) | Decode engine dies | The TP vote makes both workers skip the request; the next step re-handshakes only the failed rank; later requests return 200 |
| Prefill container killed before decode reads (real `transport retry counter exceeded`) | Request fails, decode survives (single-group recovery already worked) | Same |

Normal path unchanged: `test_read_matches_direct_serve` passes for the five READ cases (Kimi-Linear, Qwen3.5-MoE, Qwen3 dense with and without the hybrid KV cache manager, DeepSeek-V3; Gemma3 skipped, gated checkpoint).


## Details

<details>
<summary>Root cause: failed handshake (gap 4)</summary>

1. Decode schedules a READ request; `start_load_kv` runs the eager handshake to every prefill DP rank before the forward.
2. One handshake raises (e.g. a malformed reply). The TP-wide vote fails, and `_eager_handshake_all_dp_ranks` raised `HandshakeError`.
3. The exception left `execute_model`, so `EngineCore` died with every request on it.

Now the vote returns the failed engines; their requests go to `get_block_ids_with_load_errors` and get a best-effort `release` to prefill, computed by the same `_read_notify_ports` as a normal read. The vote keeps TP workers consistent, so they all skip the same reads and enter the forward together.
</details>

<details>
<summary>Root cause: rejected request</summary>

1. The router sends decode a request with `kv_transfer_params` (`do_remote_prefill=True`); prefill's address is embedded in the request_id it forwards.
2. Decode's serving layer returns an `ErrorResponse`: a validation error, or the engine failing the request under `kv_load_failure_policy=fail`. `_with_kv_transfer_rejection_cleanup` then calls `notify_kv_transfer_request_rejected`, which submits a pre-aborted request under the serving layer's own request_id.
3. MoRIIO READ's `request_finished` saw `do_remote_prefill=True` ("aborted before scheduling") and queued a release in `_reqs_need_recv`.
4. That request_id embeds no address and the params carry no `remote_host`, so `add_new_req` raised in `build_connector_meta`, killing the engine.

Prefill frees those blocks after its deferred-send timeout. The serving layer also sends this cleanup for requests that did reach the engine; with this change that is harmless for MoRIIO.
</details>

- **Not duplicating:** #62552 (WRITE handshake readiness), #63856 (gap 3: handshake receive timeout), #63855 (gap 6: busy-wait), #64756 (gap 5: listener), and #63854 (gap 12: compatibility check) cover other #759 gaps. #63336 is the umbrella RFC; this PR covers the READ part of its gaps 4 and 9.
- **Limitations:**
  - A READ that fails on a model with several KV cache groups or recurrent state (hybrid models, sliding window under the hybrid KV cache manager) still fails the step, and so does a failed handshake on such a model. The scheduler has no request-level channel for synchronous load failures yet. Recovering them safely also needs the allocator hold proposed in #63336, because a failed MoRI-IO status does not prove that DMA into the blocks has stopped.
  - A dead peer can still block the handshake until a receive timeout exists (#63856). This PR handles handshakes that fail by raising.
