# [Bugfix][Core] Keep Mamba-aligned prefill chunks out of the MTP lookahead window

[Upstream PR](https://github.com/vllm-project/vllm/pull/61845) · state: open · merged: False

## Original PR description

## Purpose

Fixes #61762.

With Mamba `align` prefix caching (the default for hybrid models once prefix caching is on) and multi-module MTP (`num_prefill_lookahead = num_speculative_tokens = L >= 2`), a prompt that ends 1..L-1 tokens past a Mamba block boundary can stop being scheduled. Two clamps in `Scheduler.schedule()` disagree about the same position:

1. `_mamba_block_aligned_split` ends a chunk on a block boundary (a cacheable checkpoint, or a budget-limited chunk floored to a boundary).
2. `_reserve_prefill_lookahead` sees fewer than L tokens left and moves the end back by `L - remaining`, off the boundary.
3. On the next step the chunk starts mid-block, the split stops it at that same boundary, the reservation shortens it to 0, and the request is skipped. This repeats on every step: the request holds its KV blocks and never finishes, and no error is raised.

The report in #61762 (and my follow-up there) only showed this with `disable_eagle_block_drop=True`. While writing the fix I found it also happens with EAGLE block drop on (the default) whenever the chunk that reaches the last boundary is budget-limited. Block size 16, L=3, 49-token prompt, 16-token budget: the chunks end at 16, 32, then 46, and from then on 0 tokens per step. With a shared per-step budget, a long prompt's last full chunk can be budget-limited in this way.

**Fix.** The lookahead is now resolved inside `_mamba_block_aligned_split`, which knows where chunks may end. If a chunk would end inside the window, the split does the first of these that applies:

- **Finish the prefill**, if the budget allows it and it crosses no block boundary from a mid-block start. This gives up the checkpoint inside the window.
- **Stop at the last block boundary before the window.**
- **Keep the aligned end.** `_reserve_prefill_lookahead` now leaves Mamba-aligned ends alone, so the next chunk finishes the prefill. In that case the drafter reads sampled tokens at this one boundary, which is what the reservation tries to avoid. That is a draft-quality cost; the alternatives are a livelock, or a chunk ending mid-block followed by one crossing the boundary, which publishes a Mamba slot at the wrong offset (#43559).

Unaligned (sub-block) chunk ends are still shortened by `_reserve_prefill_lookahead` as before. Nothing changes when `num_prefill_lookahead <= 1` (EAGLE-family drafters, or no drafter). The window condition `N - L < end < N` cannot hold in that case.

## Reachability

As far as I can tell, no public checkpoint reaches this today:
- Qwen3.5 and Qwen3-Next have one MTP layer.
- Ling/Ring-2.5 and Kimi-Linear have none.
- `nemotron_h_mtp.py` asserts a single MTP layer.

`qwen3_next_mtp.py` and `bailing_moe_v3_mtp.py` already iterate over `num_nextn_predict_layers`, and nothing rejects multi-module MTP with `align`. A hybrid checkpoint with two or more MTP layers would hit it. All evidence below is scheduler-level on CPU. I have not run a model, and I am not claiming end-to-end validation.
