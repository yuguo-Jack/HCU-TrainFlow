# [Core] Add default-off preemption_victim="lcf" (least-computed-first) victim policy

[Upstream PR](https://github.com/vllm-project/vllm/pull/53723) · state: open · merged: False

## Original PR description

## What

Adds a scheduler axis `preemption_victim` that controls *which* running request is
evicted when the scheduler must preempt to free KV cache. It is orthogonal to the
existing `policy` axis, which controls admission order.

- `preemption_victim="fcfs"` (default): unchanged behavior. FCFS pops the
  last-admitted running request; `policy="priority"` still evicts
  `max(running, key=(priority, arrival_time))`.
- `preemption_victim="lcf"`: evicts the eligible running request with the least
  sunk compute, `min(..., key=num_computed_tokens)`.

Surface area:

- `vllm/v1/core/sched/request_queue.py`: `PreemptionVictim` enum (`FCFS`, `LCF`),
  separate from `SchedulingPolicy`.
- `vllm/config/scheduler.py`: `PreemptionVictimPolicy` literal and the
  `preemption_victim: PreemptionVictimPolicy = "fcfs"` field.
- `vllm/v1/core/sched/scheduler.py`: `_select_preemption_victim()` and the call at
  the preemption site.
- `vllm/engine/arg_utils.py`: `--preemption-victim`, mirroring `--scheduling-policy`.

## Why

Recompute-based preemption resets the victim's `num_computed_tokens` to zero, so
every already-computed token must be recomputed on resume. The victim choice is
therefore what decides how much compute a preemption destroys, and neither shipped
policy looks at sunk compute at all: FCFS takes the tail of `running`, and PRIORITY
takes the lowest-priority request. Both can land on the request that has computed
the most.

A companion measurement study on Qwen2.5 models (single A100 unless noted) measured
the recompute tax, the fraction of token-compute spent redoing preempted work:

- Offline sweep (0.5B) over the KV-block budget: 0% when memory is ample, rising to
  ~79% under heavy pressure.
- Online serving (7B) via `vllm bench serve` on a ShareGPT trace, sweeping arrival
  rate: 0 at low load, 10-23% under pressure.
- Scale (14B, 32B with tensor parallelism): the tax persists at 15-22%.
- Ablations over prefix caching, chunked prefill, and block size: largely invariant,
  so it is preemption-driven rather than a config artifact.
- Victim-policy comparison (least-computed vs shipped FCFS vs random vs
  most-computed): victim choice alone governs about half the tax.

Across those runs LCF cut wasted recompute 20-59% at no throughput or latency cost.
The mechanism is more preemptions but cheaper ones, since it evicts near-zero-sunk-cost
victims. All models and workloads were public or self-generated.

## Prior art, and how this differs

Victim selection by sunk compute has been proposed twice before and both attempts
died without a maintainer verdict, so this is worth stating plainly:

- **#38080** (`chaunceyjiang`, Mar 2026) preempted the request with fewer
  `num_computed_tokens`. It was closed by the stale bot in Oct 2026 after no human
  review. It changed the FCFS/PRIORITY key in place, with no opt-out.
- **#36980** (`whycoming`, Mar 2026) added an SRTF tiebreaker to the victim key and
  was self-closed for the same reason. In that thread the author asked whether a
  *separate config field* should let users pick a victim strategy independently of
  `policy`. That question was never answered. This PR is that separate field, which
  is the one design difference that matters: the default path is untouched, so there
  is nothing to regress if the heuristic is wrong for a given workload.

On the observability side, a count is not a volume, and the two existing signals are
counts:

- `vllm:num_preemptions` (`loggers.py`) and `vllm:request_num_preemptions` report how
  *many* preemptions happened.
- **#58037** labels *why* each one happened (`kv_full` / `priority` /
  `prefix_cache_reset`).

Neither says how much compute a preemption destroyed, which is the quantity LCF
minimizes. This PR acts on that volume at selection time via `num_computed_tokens`;
it deliberately adds no metric, so it does not overlap #58037 and does not collide
with **RFC #61423**, which is re-evaluating per-iteration metrics and folds every
recomputation chunk into generic prefill.

Outside vLLM, TOPAS (arXiv 2608.25523) carries a redo term
`J_redo = Σ T_decode · y_r(t)` as a live in-engine scheduling objective, charged only
on generated-token KV with retained prefix accounted separately. That is a continuous
objective inside a solver. This PR is a single default-off comparison key at one call
site, with no new scheduling objective and no change to admission order. SGLang ships
`sglang:num_retracted_input_tokens_total` / `..._output_tokens_total`, which are gross
retracted volumes, not a victim policy. BCD-DRO (arXiv 2607.16892) prices a
`C_preempt` term inside joint routing and admission, but gross: prefix caching enters
only its reservation, never `C_preempt`.

## Correctness note (shared bookkeeping)

The LCF victim, like the PRIORITY victim, may be a request that was already scheduled
earlier in the same step, so it cannot use the FCFS `pop()` fast path. LCF and
PRIORITY share one remove-and-restore path that removes the victim by index,
decrements the loop cursor when the victim preceded the current request, and, if the
victim was already scheduled this step, restores the token and encoder compute budgets
and pops `num_scheduled_tokens` / `req_to_new_blocks` /
`scheduled_spec_decode_tokens`. The two policies differ only in the selection key.

`_select_preemption_victim()` returns `None` to mean "fall back to the last-admitted
`pop()`", and LCF returns `None` when no request other than the one being scheduled is
eligible. Two eligibility rules exist because the obvious `min()` is unsafe:

- A request holding a pending same-step encoder allocation is skipped. Cancelling its
  worker-side encoder compute while its `encoder_cache_manager` reservation stays live
  would let a resumed request falsely hit the cache and skip encoder execution. The
  tail request can never hold one, so the fallback stays safe.
- The request being scheduled is excluded, and ties break toward the last-admitted
  victim (the candidate list is built with `reversed()`), so requests with equal
  `num_computed_tokens` cannot make the current request preempt itself into a
  zero-token step.

## Rebase

Rebased from a late-August base onto `e0adacc9a6` (~2900 commits). Two files
conflicted, both because main grew new guards around the preemption site:

- A connector check (`has_pending_block_frees()`) now short-circuits before victim
  selection, and `_request_blocks_can_be_freed(victim)` now gates the removal. Both
  are preserved in order: connector check, then selection, then the free check, then
  removal. The selected victim is held in a local `victim` that is `None` on the FCFS
  fast path, which is what distinguishes "pop the tail" from "remove by index"
  without re-testing the policy.
- `tests/v1/core/utils.py`: `create_scheduler` gained kwargs next to this one; both
  are kept.

Behavior with the default `preemption_victim="fcfs"` is unchanged. Note that
`defer_block_free` is only ever set with a KV connector in consumer role and more than
one in-flight batch, so the new free check is inert on the default path.

## Tests

In `tests/v1/core/test_scheduler.py`:

- `test_lcf_preemption_victim_selection`: three running requests with distinct
  `num_computed_tokens` under zero-free-block KV pressure; asserts LCF preempts the
  least-computed one, which is neither the request being scheduled nor the FCFS
  victim, so it exercises the shared remove-and-restore path.
- `test_fcfs_preemption_victim_unchanged`: same fixture, default policy; asserts the
  last-admitted request is still the victim.
- `test_lcf_victim_skips_pending_encoder_allocation` and
  `test_lcf_victim_avoids_self_preemption_on_tie`: the two eligibility rules above.

## Model evaluation

Not applicable. This does not alter model outputs, logits, or sampling; it changes
which already-running request is evicted under KV pressure, and the default keeps
existing behavior.

## Duplicate check

Searched the change rather than the keyword. #38080 and #36980 are the two prior
attempts, both closed (see above) and neither offering an independent opt-in axis.
#45558 / #45561 add a priority victim key, a different selection key on the other
axis. #51574 / #41952 are priority-queue re-admission fixes. #49675 handles
zero-progress preemption cascades. #58037 labels preemption reasons and adds no victim
logic. No open PR adds a least-computed-first victim or a `preemption_victim` option
(searched "least computed", "lcf", "preemption_victim", "victim selection"). This is
complementary to RFC #51608 (extensible scheduler-plugin framework) and RFC #54644
(victim-selection extension point): a small default-off built-in that can ship
independently of either.

For the encoder allocation issue I went with avoiding the victim rather than rolling back the allocation. LCF now skips any running request that has an encoder input scheduled in the same step, so we never cancel the worker-side encoder work while leaving the cache reservation behind for a resumed request to falsely hit. The FCFS tail fallback can never hold one either, so that path stays safe. Covered by test_lcf_victim_skips_pending_encoder_allocation.

For the tie case, LCF now excludes the request being scheduled and walks the running queue in reverse, so equal-computed-token requests break the tie toward the last-admitted victim instead of the current request preempting itself into a zero-token step. Both new tests pass on CPU. Happy to switch to the explicit allocation rollback instead if you'd rather keep such requests eligible as victims.
