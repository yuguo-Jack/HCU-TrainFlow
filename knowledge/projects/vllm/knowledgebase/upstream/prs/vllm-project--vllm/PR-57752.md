# [Don't merge][Experiment] Move MediaIO decode to MM preprocessing

[Upstream PR](https://github.com/vllm-project/vllm/pull/57752) · state: open · merged: False

## Original PR description




## Purpose

Move media **decoding** (image/video/audio) out of the chat parsing layer and
into the mm processor, behind the processor cache. Downloads stay where they
are (async, concurrent, in the renderer); what crosses the boundary is now a
`LazyMedia` handle (encoded bytes + decode callable) instead of a decoded
object.

- `LazyMedia` (`vllm/multimodal/media/base.py`) decodes on first access,
  thread-safe, with `map()` for stacked transforms and `release_bytes()` for
  early memory release. Hashing uses the encoded bytes (images keep their
  exact eager-path hashes via an eager header-open that preserves EXIF
  ImageID / `io_config` semantics), so a **processor-cache hit skips decoding
  entirely** and the raw bytes are freed right after hashing.
- `apply()` is split into two phases: phase 1 (hash, cache lookup, submit
  miss-item decode futures) runs on the single-worker `_mm_executor`; the
  decode await happens on the event loop; phase 2 (HF processing, cache
  writes) runs back on the worker and re-derives the cache state. The worker
  never blocks on a decode join, so multi-second video decodes overlap across
  requests while the P0/P1 cache ordering protocol is preserved. Processors
  overriding `apply()` / `_cached_apply_hf_processor` (EncDec, ASR, several VL
  models) automatically keep the previous blocking path via
  `supports_two_phase_apply`.
- Memory: cache-hit items cost zero pixel memory; original bytes are released
  after hashing (hit) or after HF processing (miss).

Design doc: `docs/design/lazy-media-decode.md`.

Intentional behavior changes:

- Corrupt-media decode errors now surface as HTTP 422
  (`VLLMUnprocessableEntityError`) from the processor instead of 400 at fetch
  time.
- Audio/video cache keys are derived from the encoded bytes instead of the
  decoded waveform/frames (in-process cache; keys change, no persistence
  concerns). Image keys are unchanged.
- Byte-consuming model processors (e.g. Dots3 NOTE) keep access to
  `original_bytes` through HF processing on the cached path; miss-item bytes
  are released only afterwards (`try/finally`).

## Purpose

Move media **decoding** (image/video/audio) out of the chat parsing layer and into the mm processor, behind the processor cache — and make the value crossing that boundary a single typed reference rather than one of several wrapper shapes.

Downloads stay where they are (async, concurrent, in the renderer). What crosses into the processor is a `MediaRef`: the encoded bytes, a cache key derived from them, and a deferred decode.

### `MediaRef` replaces the wrapper union

Fetched media previously crossed the boundary as one of three shapes — `MediaWithBytes`, `LazyMedia`, or a bare decoded object — and `MultiModalHasher.serialize_item` had to inspect whichever arrived to reverse-engineer a cache key. Audio had no wrapper at all, so its key was computed over resampled PCM; video keyed off whichever of decoded frames or encoded bytes happened to be smaller.

`MediaRef` (`vllm/multimodal/media/base.py`) replaces all three:

- `key` — the cache identity, derived by `derive_media_key(data, spec)` from the encoded bytes and a `DecodeSpec`, **without decoding**. Header parsing at most, never rasterization. sha256 rather than the configurable `MMHasherAlgorithm`, because the key must not vary with which optional hash packages are installed.
- `spec` — the resolved decode configuration that parameterized or mutated the media, already folded into `key`. One place decides what media identity means, so it cannot drift from the key.
- `decode()` — memoized and lock-guarded, so concurrent callers decode exactly once.
- `map()` — stacks a transform (audio resampling, channel normalization, video metadata unpacking) onto the decode step, deriving the new key from the parent's key rather than re-digesting the payload.
- `release()` — drops the decode closure and, for images, the header-opened PIL image whose `fp` holds a second copy of the bytes. That is what actually frees the payload.

`MediaWithBytes` and `LazyMedia` are deleted. `MediaRef` forwards no attributes — no `__getattr__`, `__iter__`, `__getitem__` or `__array__` — so a reference never decodes by accident through logging, attribute access, or being handed to numpy. It pickles by materializing, keeping its key and spec.

Consequences: a **processor-cache hit skips decoding entirely**; `serialize_item` collapses to one `MediaRef` branch plus the branches for media offline users supply directly; `get_mm_hashes` no longer needs `media_io_kwargs` as a separate factor, since the spec is inside the key; and `parse.py` needs two accessors (`get()` for the decoded view HF's `isinstance` checks require, `get_raw()` for identity) instead of four.

### Decoder resolution moves to the processor

Decode *timing* was only half the problem: the fetch layer also decided *how* to decode, which forced the video backend to be derived from the model's HF video-processor class name and threaded up through the request parser.

`BaseProcessingInfo.get_media_io(modality, media_io_kwargs)` (`vllm/multimodal/processing/context.py`) now resolves the decoder, including the video backend, from the model config — the layer that has it. `MediaConnector` is transport only: URL scheme dispatch, allowed-domain check, encoded-size cap, on-disk download cache, redirect policy, error normalization. Its `fetch_*` methods take a caller-supplied decoder.

`use_audio_in_video` therefore serves **one download to two decode specs** (`fetch_video_and_audio`) instead of fetching the same URL twice.

### Two-phase apply

`apply()` is split so the decode wait does not occupy the mm worker: phase 1 (hash, cache lookup, submit miss-item decodes) runs on the single-worker `_mm_executor`; the futures are drained on the event loop; phase 2 (HF processing, cache writes) runs back on the worker and re-derives the cache state, so a miss that another request cached in between is not reprocessed. Processors overriding `apply()` / `_cached_apply_hf_processor()` / `_apply_hf_processor()` keep the blocking path via `supports_two_phase_apply`.

Byte release happens in phase 2, not immediately after hashing. Phase 2 re-derives the cache state, so a phase-1 hit can have been evicted and must be reprocessed from its bytes — and `decode()` raises once they are released. Cache-miss refs keep their bytes until after the HF processor has consumed them, in a `try/finally`.

Design doc: `docs/design/lazy-media-decode.md`.

### Intentional behavior changes

**Cache keys change for image, audio and video.** All three are now derived from encoded bytes plus the decode spec. The processor caches are in-process, but `ECExampleConnector` persists tensors to safetensors files named by `mm_hash`, so that store starts cold after upgrade. Video items differing only in `device`, `hw_decoders` or `pool_size` now share an entry — those are stripped by `merge_kwargs` precisely because they do not affect the decode.

**Breaking change to `MediaConnector` (out-of-tree plugins).** `__init__` no longer takes `media_io_kwargs`, and `fetch_{image,video,audio}[_async]` now require a decoder argument. Custom `MEDIA_CONNECTOR_REGISTRY` entries need updating. The public offline helpers `vllm.multimodal.utils.fetch_{image,video,audio}` are unchanged — they decode before returning.

**Corrupt-media errors now carry the item index and surface as HTTP 422** (`VLLMUnprocessableEntityError`) from the processor instead of 400 at fetch time. Both decode-error paths report the item's index within its own modality, so a client sending many items can tell which one failed. The processor path reports no `parameter`: it cannot see which request field the media arrived in, and `audio_url` and `input_audio` both reach it as modality `"audio"`. The parser-side `vision_chunk` path does report one, since only image and video are remapped there and only a URL-fetched item is a `MediaRef`.

**`use_audio_in_video` shared download.** The single download now carries the *strictest* of the two decoders' size caps, so the video download is also subject to the audio cap it previously escaped; an oversized video produces the same client error with less data transferred. It uses the video fetch timeout rather than the shorter audio one the duplicate fetch used.

**Dots3 NOTE** declares its raw-bytes decode through a `MediaIO` whose `load_bytes` is the identity and whose spec says `video_decode: "raw_bytes"`, instead of reaching for the encoded bytes during HF processing. The choice is now part of cache identity, so a hit and a miss hand HF the same thing.

## Known limitations

- `supports_two_phase_apply` is a runtime reflection probe over three methods. A processor overriding one of them silently falls back to the blocking path, and nothing pins the exclusion set — a new `apply()` override loses the optimization with no test signal. Fifteen in-tree processor classes are excluded today, including every `EncDecMultiModalProcessor` subclass and the generic transformers backend.
- `BaseRenderer._mm_executor` is single-worker for two independent reasons: the frontend `mm_processor_cache`'s `get_and_update` must stay ordered with the engine-core cache's, and `_process_multimodal` can enter numba's workqueue parallel region (Kimi K2.5 vision preprocessing), which aborts the *process* on concurrent access. Neither is enforced in code — only by the pool size and the comment above the warmup submission.
- The single worker serializes the HF processor call across all concurrent requests; only the decode wait is lifted off it.
- The connector's on-disk download cache and its negotiated download-time size cap apply to `http(s)` URLs alone. A `file:` URL shared by two decoders is read once per decoder; per-decoder guards such as audio's encoded-size check stay eager on every scheme.
