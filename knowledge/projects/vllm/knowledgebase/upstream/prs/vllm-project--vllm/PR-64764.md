# [Perf][LoRA] Compute kernel metadata on the CPU to remove per-step GPU syncs

[Upstream PR](https://github.com/vllm-project/vllm/pull/64764) · state: open · merged: False

## Original PR description

## Purpose

The per-step LoRA metadata path is slow on the CPU and blocks on the GPU:

- `convert_mapping` loops over every token in Python (tuple of numpy scalars -> list -> tensor).
- `LoRAKernelMeta.prepare_tensors` runs `sort` / `unique` on the GPU and does `if torch.all(...)`, which syncs the CPU with the GPU. This runs twice per step (token mapping and sampler mapping). See the existing `# TODO avoid gpu<->cpu sync here` in `punica_gpu.py`.

With async scheduling the sync waits for the whole previous forward pass, which cancels the CPU/GPU overlap whenever LoRA is enabled.

## Changes

- `LoRAMapping` keeps `index_mapping` / `prompt_mapping` as int64 numpy arrays (with an array-aware `__eq__`, since `set_adapter_mapping` compares mappings). `make_lora_inputs` no longer builds tuples.
- `convert_mapping` is vectorized (`convert_mapping_cpu`, `searchsorted` over slot ids). Unknown ids still raise `KeyError`. The three index arrays go to the device in one copy.
- New `LoRAKernelMeta.prepare_tensors_from_numpy` computes all fields on the host (`bincount`, stable `argsort`, `cumsum`, no-LoRA flag, cudagraph rounding of the active LoRA count) and does one non-blocking H2D copy from a fresh pinned buffer. It never reads from the device. A fresh buffer per step avoids overwriting data a queued copy still needs under async scheduling.
- `PunicaWrapperGPU.update_metadata` uses it, so the `gpu_sync_allowed()` block is gone.
- `prepare_tensors` is unchanged (still used by the XPU wrapper and existing tests).

## Test Plan / Results

Equivalence: old vs new `convert_mapping` and `LoRAKernelMeta` outputs compared on 300 randomized mappings (empty, all no-LoRA, mixed, `None` slots, with and without cudagraph rounding). All fields matched exactly, including the `KeyError` case. Run on a Modal CPU container.

Microbenchmark of the old vs new update path (vLLM modules loaded standalone, old code taken from `main`). 8 slots, 256 requests, median of 50.

CPU only, per `update_metadata`:

| Tokens | Old | New |
|---|---|---|
| 8k | 2.93 ms | 0.58 ms |
| 16k | 5.67 ms | 0.71 ms |

L4, GPU idle:

| Tokens | Old | New |
|---|---|---|
| 8k | 5.10 ms | 1.39 ms |
| 16k | 9.05 ms | 1.68 ms |

L4, with GPU work already queued (the async scheduling case):

| Tokens | Old | New |
|---|---|---|
| 8k | 87.9 ms | 1.84 ms |
| 16k | 88.9 ms | 2.09 ms |

In a 20 step loop (enqueue GPU work, then update), CPU time spent enqueueing was about 490 ms with the old path (it waits on the GPU each step) and about 40 ms with the new one.

Caveats: the GPU work in the overlap test is a synthetic matmul queue, and total wall time in that loop is about equal since the GPU dominates. I have not run an end-to-end `--enable-lora` serving benchmark. The repo's LoRA tests were not run (they need a GPU / full install); pre-commit passes.
