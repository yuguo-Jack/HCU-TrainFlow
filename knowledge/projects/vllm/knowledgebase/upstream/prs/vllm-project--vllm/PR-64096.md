# [KV Connector][Spec Decode] Support lookahead block hashes in KV connectors

[Upstream PR](https://github.com/vllm-project/vllm/pull/64096) · state: closed · merged: True

## Original PR description

## Overview

Follow-up to #61589, extending lookahead block hashes to NIXL P/D, Mooncake P/D, Mooncake Store, and OffloadingConnector. MultiConnector supports them when all configured children opt in.

This allows compatible connectors to reuse KV whose hashes include the required lookahead tokens, without the additional EAGLE/MTP trailing-block drop. Unsupported connectors retain legacy hashing.

## Implementation

- **Enablement:** Enable lookahead hashing for supported connectors through `supports_lookahead_block_hashes`, and propagate `num_hash_lookahead_tokens`. MultiConnector enables it only when all children support it.

- **P/D connectors:** Enable lookahead hashing for NIXL and Mooncake. Clear and rebuild request hashes after P-side prompt truncation.

  For example, with block size 4 and lookahead 1, hashes are computed when the request is created. In the Mamba P/D path, P then removes the final token for D to process:

  ```text
  Request creation:  ABCDE → hashes = [H(ABCD, E)]
  P-side truncation: ABCD  → hashes = [H(ABCD, E)]  # stale entry
  After rebuilding:  ABCD  → hashes = []           # no lookahead token yet
  ```

  Truncating the token sequence does not automatically remove existing hashes. This PR adds the following after truncation in both connectors:

  ```python
  request.block_hashes.clear()
  request._prompt_embeds_per_block_hashes.clear()
  request.update_block_hashes()
  ```

  Clearing is necessary because `update_block_hashes()` only appends new hashes; it does not remove stale entries.

- **Mooncake Store and OffloadingConnector:** Limit saves to KV covered by available hashes (`len(block_hashes) * hash_block_size`), since computed KV may extend beyond the hashed prefix. Skip the extra EAGLE trailing-block drop in lookahead mode and align hybrid/Mamba cache boundaries with core prefix caching.

  For example, with block size 4 and eight computed tokens:

  ```text
  Computed KV:      [A B C D] [E F G H]

  Legacy hashes:    H(ABCD), H(EFGH)
  Lookahead = 1:    H(ABCD, E), no hash for EFGH yet
                               └─ requires the next token I
  ```

  With lookahead hashing, eight computed tokens do not necessarily mean two available cache keys.

- **Mooncake Store request completion:** Save blocks that become eligible after the final sampled token completes their lookahead hash.

  For example, with block size 4, lookahead 1, prompt `ABCD`, and `max_tokens=1`:

  ```text
  Build metadata:  ABCD  → no lookahead hash; no save scheduled
  Sample E:       ABCDE → H(ABCD, E) becomes available
  Request ends:         → queue a finish-time save for ABCD's KV
  ```

  The hash appears after this step's metadata was built, and the finished request will not return to normal scheduling. `register_finished_lookahead_save()` queues the save, while `_reference_save_blocks()` prevents the source blocks from being reused before the asynchronous save completes.

- 7konigsberg · comment · 2026-10-28T02:32:58Z · [source](https://github.com/vllm-project/vllm/pull/64096#issuecomment-6459065146)

With lookahead hashes on, the partial-tail store in OffloadingConnector can index past `request.block_hashes`. `_build_partial_tail_store_jobs` only checks `boundary + margin` against the prompt tokens computed this step, then `_make_boundary_key` reads `block_hashes[(boundary + margin) // tokens_per_hash - 1]`. With lookahead L a P-token prompt has `(P - L) // N` hashes, so that index can be one past the end. `_lookup` caps by `len(block_hashes)`, the store path doesn't. This needs a partial tail (`prefix_match_unit` below the block size) with an EAGLE/MTP group, e.g. Qwen3-Next MTP with CPU offloading.

I reproduced it on CPU with the existing helpers (`_make_partial_tail_scheduler(eagle=True)`): a 28-token prompt with `use_lookahead_block_hashes = True` has 6 hashes, gets a 20-token offload hit through `get_num_new_matched_tokens` / `update_state_after_alloc`, and the Mamba checkpoint hand-off at 24 (`get_mamba_prefill_checkpoint_position(28, 4, False, 1)`) then raises `IndexError` at `scheduler.py:1124`, which `build_connector_meta` reaches without a guard. With legacy hashes (7) the same flow stores fine. Skipping the store when the proof key's hash isn't there yet fixes it here, and `test_scheduler.py` still passes:

```python
if (
    boundary + self._max_eagle_proof_margin
    > len(req.block_hashes) * self.config.tokens_per_hash
):
    continue
```
