# [Core][Spec Decode] Skip draft tokens instead of preempting under KV pressure

[Upstream PR](https://github.com/vllm-project/vllm/pull/63079) · state: open · merged: False

## Original PR description



## Overview

Under KV cache pressure, the V1 scheduler preempts another running request to make room for a decode's speculative draft tokens. When a decode's verified token fits in its existing blocks and only its drafts need a new block, this PR schedules that decode without drafts for the step. Preemption is now a last resort for when the verified token itself does not fit.

## Claims

- A running request is no longer preempted just to make room for another request's unverified draft tokens. Preemption frees the victim's KV cache, so its work usually has to be recomputed later.
- In the pipelined async-scheduler simulator from `tests/v1/core/test_async_scheduler.py` (PP=3, 3 spec tokens, KV pressure), preemptions drop by 26% across a 48-scenario sweep: 1058 → 785.
- End to end (Qwen3-0.6B, ngram spec decode with k=4, KV pool sized below peak demand): preemptions drop 25% (72.5 → 54.0 mean) and output throughput rises 3.1% (783 → 807 tok/s). The run ranges don't overlap.
- Outputs are unchanged in the checks below. Spec decode stays lossless; the change only alters which draft tokens get verified in a given step.

## Details

**Root cause.** In the running-request loop of `Scheduler.schedule()`, a decode asks `allocate_slots` for `1 + num_drafts` tokens, and a failure goes straight to preempting the lowest-priority running request (`self.running[-1]` under FCFS) before retrying. Only the first token is required. The drafts are speculative and many are rejected, but they need up to `k` KV slots ahead of the verified token, so a request asks for its next block up to `k` tokens earlier than it otherwise would. When the pool is full, that early ask fails while the verified token would still fit, and another request is preempted to satisfy it.

**Fix.** On an allocation failure, drop the request's draft tokens for this step and retry before considering preemption. The draft count reuses the expression the loop already uses for `num_scheduled_spec_tokens`, so the existing bookkeeping applies unchanged. Specifically, `scheduled_spec_decode_tokens` is not set for the request, `spec_token_ids` is reset, and the async scheduler adds one placeholder instead of `1 + k`. Scheduling a decode with fewer drafts than proposed is an existing path: it already happens when the token budget or `max_model_len` truncates drafts.

**Guards and compatibility:**
- Only applies when the request has at least one non-draft token and `num_sampled_tokens_per_step > 0`. Diffusion canvas tokens, which are not optional, are excluded the same way as elsewhere in the scheduler.
- `num_lookahead_tokens` (KV slots for drafters such as EAGLE) is unchanged.
- Runs before victim selection, so it applies equally to FCFS and priority scheduling. With a KV connector that has pending block frees, an allocation failure used to stop scheduling running requests for the step; the decode now retries without drafts first and proceeds if that fits.
- Scheduler-only change: no new CPU/GPU synchronization, and applies to both model runners.

**Trade-offs:**
- A decode scheduled without drafts makes that step's batch non-uniform, so it can miss the uniform-decode CUDA graph for that step. This only happens on steps where the pool is exhausted, and the alternative is a full recompute of another request. The end-to-end numbers above include this cost.
- The request whose drafts are dropped decodes one token per step, rather than up to `1 + k`, for at most the `k` positions before it needs the block anyway.
- Drafts are dropped all-or-nothing. Fitting part of the drafts into the free slots of the last block would recover some speculation but needs per-group slot accounting; I left it out to keep the change minimal.
- The measurements are on one small model, one 4 GB GPU and an undersized KV pool chosen to force preemption. I have not measured larger models, multi-GPU setups, or other drafters (EAGLE, MTP).

**Existing test change.** `test_reset_prefix_cache_with_inflight_output_under_kv_pressure[3]` asserted that every request's stale output share is fully drained at the end. That cannot hold for a request that finishes while its last in-flight step is still pending: `update_from_output` can no longer find the freed request to drain it. `main` already reaches this state in 11 of 48 variants of that scenario (reset schedule, draft-acceptance pattern, `max_tokens`). This PR's change in preemption timing makes the test's fixed parameters reach it too. The assertion now allows at most the tokens of steps that returned after the request was freed. Any accumulated or double-counted share would still fail it.

**Not a duplicate.**
- #28558 and #30916 (merged) clear stale spec tokens on preemption.
- #49620 (open) changes how stale async output is discarded after preemption.
- #62878 (open, for #62752) reserves headroom for hybrid Attention/Mamba state transitions. It targets a different cause of avoidable preemption and does not change how optional draft slots are treated. Both edit `schedule()`; I expect any conflict to be textual.
- #62784 (open) skips drafting in steps where no request can use the drafts. That is a drafter-side decision and does not touch preemption.
- None of these changes the decision to preempt for draft tokens.
