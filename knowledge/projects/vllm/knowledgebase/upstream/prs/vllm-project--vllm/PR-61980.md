# [Feature][KV Offload] Add filesystem I/O deadlines with safe buffer retention

[Upstream PR](https://github.com/vllm-project/vllm/pull/61980) · state: open · merged: False

## Original PR description



## Overview

Add opt-in filesystem KV-offload I/O deadlines while retaining primary buffers until physical I/O completion. Implements Item 2 of #54363; related lifecycle work: #61667.

## Claims

- `io_timeout_seconds: float | None = None` uses monotonic submission deadlines and preserves the default behavior.
- Expired loads become misses while their destination slots remain quarantined; expired stores retain their source pins. Late completion releases resources without reporting a second logical result.
- Physical inflight accounting remains valid through cancellation, drain, reset, and shutdown. New promotions/cascades to a tier pause while timed-out I/O remains unfinished.
- FS deadlines do not change object-storage or P2P protocol behavior, file formats, checksums, cleanup, or retry policies.

## Details

A filesystem syscall may block indefinitely while accessing a primary KV buffer. Returning an ordinary failed completion would allow the allocator to reuse that buffer too early. The manager therefore separates one-time logical failure from physical resource release. Promotions detach failed keys but retain the slot IDs; cascades retain read pins. A late result only releases the retained resources. Primary read/write occupancy remains charged throughout retention.

Pool cancellation and worker start share a condition lock. Never-started jobs are canceled through an index and skipped by workers; running jobs remain physically inflight until they return. Completion is acknowledged under the pool lock, so a result published at or after its deadline is conservatively treated as expired. Timeouts are observed at the next manager poll.

Blocked syscalls cannot be forcibly canceled safely. This PR adds no per-block cancellation to either I/O path: running batches may continue, and drain/reset/shutdown can wait indefinitely. Native tests execute real I/O after a controlled delay; they do not emulate an indefinitely stalled NFS/FUSE syscall.
