# [Bugfix][LoRA] Reject PEFT adapter features vLLM does not implement

[Upstream PR](https://github.com/vllm-project/vllm/pull/60225) · state: closed · merged: True

## Original PR description


## Overview

`PEFTHelper` drops `adapter_config.json` keys it doesn't know, so adapters using PEFT features vLLM doesn't implement loaded without an error and were served with wrong outputs. This rejects them with a clear error, the same way DoRA is rejected, and fixes a regression from #53555 that let `lora_A` / `lora_B` `.bias` tensors replace the LoRA weights.

Fixes #60223

## Claims

- Adapters with `lora_bias`, an `init_lora_weights` that modifies the base model when PEFT loads the adapter (`pissa`, `pissa_niter_*`, `olora`, `corda`, `loftq`) or any other value not on the allowlist, `alora_invocation_tokens`, `layer_replication`, `use_bdlora` or `use_qalora` are rejected in `validate_legal` with a message naming the feature. Before, they loaded and gave outputs that differ from PEFT.
- `parse_fine_tuned_lora_name` accepts `.bias` only for the `score` / `classifier` heads again, not for `lora_A` / `lora_B`. This restores the behavior before #53555 (v0.30.0 rejects these adapters; v0.31.0 loads them and silently drops the bias or swaps it with the weight).
- No change for other adapters: `init_lora_weights` = `true` / `false` / `"gaussian"` / `"eva"` / `"orthogonal"` / `"mica"` / `"lora_ga"` and PEFT's converted PiSSA / OLoRA / CorDA adapters (`init_lora_weights: true`) load as before.
- Not changed: `target_parameters`, `trainable_token_indices` and DoRA, which open PRs #52198, #55796 and #47395 are adding support for. If BD-LoRA support (#28136) lands first, its rejection here can be dropped.

## Validation

Every feature saved with PEFT 0.21.2 on a tiny random Llama (bf16, RTX 3080), loaded with `llm.llm_engine.add_lora` in one engine, then the accepted ones served. Mean absolute difference of per-token prompt logprobs between vLLM and PEFT:

| adapter | main | this PR |
|---|---|---|
| plain | 0.0018 | 0.0018 |
| `use_rslora` | 0.0021 | 0.0022 |
| `init_lora_weights` = `gaussian` / `orthogonal` / `mica` | 0.0021 | 0.0021 |
| `lora_bias=True` | loads (0.33 in the issue repro) | rejected |
| `init_lora_weights="pissa"` | loads (0.10) | rejected |
| `init_lora_weights="olora"` | loads | rejected |
| `alora_invocation_tokens` | loads | rejected |
| `layer_replication` | loads (0.17) | rejected |
| `use_bdlora` | loads (0.44) | rejected |

The rejected adapters fail `add_lora` with the message from `validate_legal` and the engine keeps serving the other adapters afterwards. The same holds for `POST /v1/load_lora_adapter` (new case in `tests/entrypoints/serve/lora/test_lora_adapters.py`). As with DoRA today, an unsupported adapter passed directly in a `LLM.generate` request still ends in `EngineDeadError`.

Real adapters: of the 628 most-downloaded Hugging Face PEFT repos with an `adapter_config.json`, this rejects 2 more than main (both PiSSA). A targeted search found about 100 more PiSSA / OLoRA / aLoRA adapters. For one of them, `AkameV6p5/qwen2.5-3b-agent-pissa-sft` on `Qwen/Qwen2.5-3B`, vLLM main differs from PEFT by 3.44 (mean, PEFT run to run: 1.55 because of its randomized SVD) and matches PEFT with `init_lora_weights` forced to `true` (0.06), i.e. it is served as a plain LoRA on the unmodified base.

Tests (on main e11962fc1c):

The new tests are CPU-only and extend the existing suites. `test_sequence_classification.py` covers the `score.bias` path that #53555 added.

## Details

- The fields are added to `PEFTHelper` with PEFT's defaults only so that `from_dict` keeps them for validation.
- `init_lora_weights` is checked against an allowlist of the values that load in PEFT as a plain LoRA, so a future PEFT init is rejected rather than silently accepted. I checked this by loading one saved adapter in PEFT 0.21.2 with each value: `gaussian`, `eva`, `orthogonal`, `mica` and `lora_ga` give the same logits as `true` (`lora_ga` changes the base weights only during training, when its gradients are attached); `pissa` and `olora` change them (max logit diff 0.15 and 0.23); `corda` fails to load in PEFT without `preprocess_corda`; `loftq` replaces the base weight with the quantized one (`loftq_init` in `peft/tuners/lora/layer.py`). The error points to PEFT's `path_initial_model_for_weight_conversion` and to setting `init_lora_weights` to `true` when the served base already holds the modified weights.
- A shape check in `set_lora` would also catch BD-LoRA / QALoRA style layouts, but it runs at activation time, so it is left for a follow-up next to the load-time validation in #59924.

Thanks for the review. I agree it's the underlying problem. I didn't reject unknown keys here because PEFT writes many keys that don't affect inference (`task_type`, `revision`, `inference_mode`, `base_model_name_or_path`, `peft_version`, ...) and adds new ones every release, so a blanket check would break adapters that work today. A follow-up could log a warning that lists the config keys `PEFTHelper` doesn't read, with an explicit list of keys known to be harmless, so new PEFT features at least show up in the logs. Happy to open that as a separate PR if that sounds useful.
