# [Kernel] CUTLASS blockwise FP8 GEMM for SM89 (Ada) with per-token activation scales

[Upstream PR](https://github.com/vllm-project/vllm/pull/61224) · state: open · merged: False

## Original PR description



## Overview

Add a CUTLASS block-FP8 GEMM for SM89 (Ada: L4, L40S, RTX 4090, RTX 6000 Ada) that takes vLLM's block-quantized layout directly: per-token-group activation scales (1x128) and 128x128 weight scales. Today these GPUs have FP8 tensor cores but block-FP8 checkpoints (e.g. Qwen3-*-FP8, DeepSeek-style) run through Marlin weight-only. vLLM logs "Your GPU does not have native support for FP8 computation" on an L4. Closes the kernel part of #58241. Builds on the SM89 test enablement in #60171.

## Claims

- New SM89 kernel, adapted from CUTLASS's Ada blockwise FP8 example (example 94, which uses one activation scale per 128x128 block) to per-token activation scales. It uses Ada FP8 tensor cores (QMMA e4m3).
- `cutlass_scaled_mm_supports_block_fp8` returns True on SM89 (CUDA >= 12.4), so `CutlassFp8BlockScaledMMKernel` is selected instead of Marlin.
- On an L4, end to end on Qwen3-8B-FP8: ~1.42x throughput, ~1.33x faster at batch 32, ~3.6% slower at batch 1, gsm8k unchanged.
- Built only for SM89 (8.9 in the CMake arch list), so other architectures are unaffected.

## Details

- Main loop: the FP8 MMA results for one 128-wide K block are accumulated unscaled, then scaled once (activation scale per row x weight scale per 128 columns) and added to the output accumulator. Scaling every MMA step needed 255 registers and spilled 600 bytes. With this it runs spill-free.
- Each warp looks up its own weight scale, so N tiles wider than 128 are handled correctly.
- Tile config by M: 16x128 (M<=16), 32x64 (M<=32), 64x128 (M<=64), 128x128 with threadblock swizzle 4 (larger M), chosen from a sweep of 16 configs on the L4.
- Known gap: batch-1 decode is ~3.6% slower end to end, from gate_up_proj and o_proj at M=1 (~8% and ~20% behind Marlin including activation quant; gate_up is the largest layer). Down_proj at large M is ~10% behind Triton. I plan to tune both in a follow-up PR (per-shape dispatch) and would rather keep this PR to the kernel and its wiring.

An AI assistant was used to read the kernel. I wrote, reviewed, and ran every test and benchmark above on an L4 myself.
