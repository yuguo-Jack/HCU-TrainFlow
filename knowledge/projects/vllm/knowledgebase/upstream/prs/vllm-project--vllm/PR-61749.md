# [Bugfix][MoE] Require exact strides for moe_forward custom ops

[Upstream PR](https://github.com/vllm-project/vllm/pull/61749) · state: open · merged: False

## Original PR description



## Overview

Fixes #52308: `nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B-NVFP4` outputs garbage under `torch.compile` with the FlashInfer TRTLLM NVFP4 MoE backend. `--enforce-eager` works. The fix changes the tag on `vllm.moe_forward` and `vllm.moe_forward_shared` from `needs_fixed_stride_order` to `needs_exact_strides`.

This supersedes #52383, which I closed: it moved the pad inside the op based on a wrong diagnosis (CUDA-graph replay), and that approach would break the ROCm RMSNorm+pad fusion (#34636). #49092 (`.contiguous()` in `scaled_fp4_quant`) would be a complementary kernel-side safeguard.

## Claims

- GSM8K accuracy for Nemotron-3-Nano NVFP4 on TRTLLM MoE with default compile goes from ~0.01 back to eager parity.
- A new unit test fails without the fix and passes with it.
- The change is two lines and touches no other code path.

## Validation

Evaluated with `tests/evals/gsm8k/gsm8k_eval.py` on all 1319 questions. Every compiled run used fresh `VLLM_CACHE_ROOT` and `TORCHINDUCTOR_CACHE_DIR` directories (see the cache note in Details).

Unit test: `pytest tests/quantization/test_trtllm_nvfp4_hidden_dim_padding.py -v` gives 5 passed. With the old tag, the new test fails with `[(2816, 1)] == [(2688, 1)]`.

The GPU runs used base commit 8a8e2baa02 with this exact patch. Between that commit and this branch's base, the only change under `fused_moe/` is `oracle/fp8.py`.

## Details

**Root cause.** Nemotron-3-Nano has hidden size 2688. The TRTLLM NVFP4 MoE pads it to 2816, and `MoERunner._maybe_pad_hidden_states` applies `F.pad` inside the compiled graph. Inductor fuses the preceding RMSNorm into the padded buffer. Because `needs_fixed_stride_order` only pins stride *order*, Inductor then passes `shared_experts_input` (the unpadded 2688-wide activations) to `moe_forward_shared` as a view into that buffer: `reinterpret_tensor(buf, (s, 2688), (2816, 1), 0)`. The shared expert's NVFP4 linear calls `scaled_fp4_quant`, whose kernel assumes packed rows. Row 0 is read correctly; every later row is read at the wrong offset. Eager mode never creates the alias. With this PR, the generated code passes a separate packed buffer.

**Why this tag.** `needs_fixed_stride_order` was a torch 2.6 workaround. It was already removed from the other MoE custom ops in #19346, #28974 and #33209; these two ops were missed. Since torch 2.8, `needs_exact_strides` has been the default for custom ops (pytorch/pytorch#148063, #150511), so this restores the default behavior.

**Tradeoff.** Inductor may now insert a copy when its preferred layout differs from eager, which in practice means one `(tokens, hidden)` copy per MoE layer when the hidden dim is padded. When no padding happens, inputs are already contiguous and nothing changes. The change adds no host sync. On ROCm, gpt-oss with the AITER RMSNorm+pad fusion uses `moe_forward` with the padded buffer itself, which is contiguous, so it is unaffected.

**Compile cache note.** Changing the op tag does not invalidate the Inductor FX graph cache or the vLLM AOT compile cache. `VLLM_DISABLE_COMPILE_CACHE=1` does not bypass the Inductor cache either. A dev install at the same vLLM version may keep loading the old aliased graph until those caches are cleared. Release upgrades are unaffected because the vLLM version is part of the cache key.

**Scope and CI.**
- `needs_fixed_stride_order` still appears in `model_executor/layers/transformers/moe.py`, `models/utils.py` and `qwen3_dflash2.py`. I did not analyze those call sites and left them unchanged.
- The new test runs in the H200 Quantization job. It mocks the MoE layer with `Mock(spec=MoERunnerInterface)` because `get_layer_from_name` asserts that type, and checks only the stride the op receives, so the result is deterministic.
- No existing GSM8K CI config covers TRTLLM NVFP4 MoE with compile: the Nemotron NVFP4 configs in `tests/evals/gsm8k/configs/moe-refactor/` use `--enforce-eager` or CUTLASS. I can add one as a follow-up.

**Duplicate check.** No open PR uses `needs_exact_strides` or addresses this stride alias. #52383 (mine, now closed) and #49092 are discussed above. Open PRs #61179 and #61367 touch the same op registration for a different bug.
