# [Bugfix][Multimodal] Release consumed MRV2 CPU inputs

[Upstream PR](https://github.com/vllm-project/vllm/pull/57368) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Long multimodal requests retain raw CPU inputs in every MRV2 worker during decoding, even after those inputs have been consumed. Release the request-local worker inputs after confirmed consumption while preserving EngineCore replay data.

The optional node-local COW tensor transport has been extracted into [a separate branch](https://github.com/Sy0307/vllm/tree/sy03/pr57368-shared-storage-20261012). This PR now contains only the scheduler/worker lifetime protocol and its tests/documentation, following the split requested in review.

## Claims

- Release consumed worker CPU input data by request ID and input index while retaining feature metadata and GPU encoder outputs.
- Account for in-flight prefill and speculative lookahead; reset tracking on preemption/resume/streaming installation and completion.
- Restore previously released inputs when KV-load rollback schedules encoding again. EngineCore keeps replayable inputs; address-only processor-cache SHM handles keep their separate ownership protocol.

## Details

MRV2 `EncoderCache.mm_features` previously retained the raw inputs for the whole request. The scheduler now emits request-local release indices at a confirmed consumption boundary. Workers install requests and positional metadata first, then replace only the selected feature's `data` with `None`. Copying the feature list and replacing entries preserves EngineCore replay inputs and other occurrences of the same hash, including the uniprocess executor case. GPU encoder-output eviction and model computation are unchanged.

Related-work check: #50871 targets EngineCore input release for resumable sessions; this patch targets ordinary MRV2 worker ownership. #51207 merged the optional tensor arena on 2026-10-09; this PR makes no transport changes and introduces no alternate SHM implementation. The extracted COW transport overlaps the arena and remains a separate design-comparison branch, with no new PR opened. #51349 proposes a paged processor-cache/IPC subsystem; #49462 targets CUDA IPC. Open-PR searches for `multimodal memory`, `encoder input`, `shared tensor`, and `57368 in:body` were repeated before preparing the split.

Design: `docs/design/mm_cpu_input_lifetime.md`. The production diff adds 111 lines and removes 2; the additional lines are focused tests and documentation.

Thanks for the thorough work — the lifetime analysis and the B200 validation are impressive. One process-level request: could you split this into two PRs?

1. **Early release of consumed MRV2 CPU inputs** — the scheduler/worker release protocol: `scheduler.py` (consumption boundary + reload detection + tracking resets), `sched/output.py` (the two new `SchedulerOutput` fields), `worker/gpu/mm/encoder_cache.py`, `worker/gpu/model_runner.py`, plus the scheduler/encoder-runner tests.
2. **Node-local shared storage** — the COW file-backed transport: `shared_tensor.py`, `shm_broadcast.py`, `multiproc_executor.py`, `envs.py` (`VLLM_MM_INPUT_SHARED_STORAGE_PATH`), and the shm_broadcast tests.

Rationale: the two mechanisms are independently useful and carry different risk profiles. (1) is a correctness-of-lifetime change on the hot scheduling path that reviewers need to scrutinize line by line; (2) is an opt-in transport feature with POSIX-lease subtleties. Splitting makes each reviewable and revertable on its own — and (1) can likely land much faster without the transport design discussion (e.g. the acknowledged overlap with #51207) gating it.
