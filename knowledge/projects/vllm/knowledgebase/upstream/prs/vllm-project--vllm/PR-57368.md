# [Bugfix][Multimodal] Release consumed MRV2 CPU inputs

[Upstream PR](https://github.com/vllm-project/vllm/pull/57368) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

MRV2 workers retain consumed raw CPU multimodal inputs throughout decoding. Release these request-local inputs after confirmed consumption, while preserving EngineCore replay data, feature metadata and GPU embeddings.

The COW transport was split out as requested in review. It remains a comparison branch; this PR contains no transport changes.

## Claims

- Release by request ID and input index after excluding in-flight prefill, output placeholders, speculative lookahead and inputs being encoded this step.
- Preserve replay data and repeated occurrences. Reset tracking on preemption, request installation and completion; restore inputs if KV-load rollback schedules encoding again.
- Keep address-only SHM processor-cache handles on their existing ownership protocol.

## Validation

Latest-main check: `a686c8e1b7e5870eadfc9f47447de2b8a26211fc`. The CPU reproducer schedules prefill, confirms its output and schedules decode while the request remains alive: upstream emits no raw-input release and retains the worker input; this patch releases it and keeps EngineCore replay data and placeholder metadata. The CPU check applies the worker notification path directly; it is not a GPU model run.

The production patch is identical to the independently model-tested lifetime-only patch `b28caf2b3` (stable patch ID `a2c7c83abc210970f49832d196251e69dfa419a0`).

Smallest CPU regression, requiring no model configuration or weights:

```bash
VLLM_TARGET_DEVICE=cpu .venv/bin/python -m pytest --confcutdir=tests/v1/worker tests/v1/worker/test_encoder_runner.py -k consumed_cpu_input -q
VLLM_TARGET_DEVICE=cpu .venv/bin/python -m pytest --confcutdir=tests/v1/core tests/v1/core/test_scheduler.py -k 'cpu_encoder_input and not schedule_resume' -q
```

**2 + 5 passed.** Include the two synchronous/asynchronous schedule-resume-abort cases with `-k cpu_encoder_input`: **7 scheduler cases passed**, for **9 distinct lifetime regressions** total. These two cases load the LLaVA configuration, without loading weights. All runs also passed with `HF_HUB_OFFLINE=1` using cached configuration metadata. `--confcutdir` avoids unrelated root accelerator fixtures in the local macOS environment; no external logging plugin is needed for these selections.

Changed-file pre-commit (including Ruff, mypy, Markdown, SPDX and CI test tethering) and `git diff --check` passed. Scheduler regressions are covered by the existing CPU V1-core job; encoder-runner tests are in the existing worker suite. Repository CI authorization is separate from test cost.

**Independent lifetime-only model validation, 2026-10-12:** Kimi-K3 on prod-0030/prod-0024, 8 B200s per node, TP8×PP2, DCP8/a2a, MRV2, eager, FLASHINFER_MLA/TRTLLM_RAGGED. C64 × 16 images × approximately 8192 text tokens × 512 output tokens; identical warmup, three formal rounds per arm, MM/prefix caches reset between rounds.

| Measurement | Unmodified base | Lifetime only |
|---|---:|---:|
| Successful formal requests | 192/192 | 192/192 |
| prod-0030 server-session PSS peak, mean (range), GiB | 81.07 (80.17–82.80) | 76.97 (76.59–77.27) |
| Pooled output tokens/s | 103.54 | 104.09 |

Peak PSS decreased by **4.10 GiB / 5.06%** in this workload. All eight first-stage workers released their EncoderCache raw-input storage while requests remained active. This measures that cache's ownership; it does not establish that every process reference or physical page was freed. PSS was sampled approximately every five seconds across the experiment's server process session, not the whole host or cgroup. The second node retained no image inputs, so its PSS fluctuations are not counted as benefit.

Eight fixed image cases matched baseline request hashes, choices (including token IDs/logprobs) and usage exactly. Actual preemption/resume completed 2048 tokens; cancellation drained. `restore_encoder_inputs` was called zero times in the model run: KV-load rollback restoration has CPU coverage only. Stress text hashes also varied within baseline; this is not a full accuracy evaluation.

Model evidence uses Python base `6a7091359` and reused native artifacts from installed commit `94f4170df`; it was not rerun end-to-end on latest main. Each arm had one service start and three sequential rounds; the +0.54% throughput observation is not a stable speedup claim. The independent COW arm's larger memory savings are excluded from this PR's claims.

## Details

`EncoderCache.mm_features` currently retains raw inputs until request removal. The scheduler sends consumed input indices; after request installation and positional-metadata initialization, workers replace only those features' `data` with `None`. A separate list and replaced entries protect EngineCore replay ownership, including the uniprocess executor. GPU embedding eviction remains independent. Design and lightweight commands: `docs/design/mm_cpu_input_lifetime.md`.

Duplicate-work checks were repeated against latest main and open PRs. #50871 is still open and releases EngineCore data for resumable sessions; it does not release ordinary MRV2 worker inputs. #51207 is merged and provides reusable pinned tensor-arena slots, but does not change request-local input lifetime. #59030/#60553 address scheduler stalls and encoder-cache capacity; #56826 optimizes whole-request cache cleanup. None supplies this worker release/replay protocol. #51349 remains an open alternative processor-cache/IPC design.

The extracted COW branch overlaps the merged arena and is not submitted as a second PR. Latest-main CPU checks confirm the arena is inactive with mixed local/remote readers and that lowering its 8 MiB threshold alone does not remove that restriction or solve retained-slot lifetime.

AI assistance was used for implementation, splitting, upstream checks, rebase, tests and PR preparation.

Thanks for the thorough work — the lifetime analysis and the B200 validation are impressive. One process-level request: could you split this into two PRs?

1. **Early release of consumed MRV2 CPU inputs** — the scheduler/worker release protocol: `scheduler.py` (consumption boundary + reload detection + tracking resets), `sched/output.py` (the two new `SchedulerOutput` fields), `worker/gpu/mm/encoder_cache.py`, `worker/gpu/model_runner.py`, plus the scheduler/encoder-runner tests.
2. **Node-local shared storage** — the COW file-backed transport: `shared_tensor.py`, `shm_broadcast.py`, `multiproc_executor.py`, `envs.py` (`VLLM_MM_INPUT_SHARED_STORAGE_PATH`), and the shm_broadcast tests.

Rationale: the two mechanisms are independently useful and carry different risk profiles. (1) is a correctness-of-lifetime change on the hot scheduling path that reviewers need to scrutinize line by line; (2) is an opt-in transport feature with POSIX-lease subtleties. Splitting makes each reviewable and revertable on its own — and (1) can likely land much faster without the transport design discussion (e.g. the acknowledged overlap with #51207) gating it.
