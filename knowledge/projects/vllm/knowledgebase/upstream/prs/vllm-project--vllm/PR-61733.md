# [Bugfix] Reject prompts that cannot be scheduled without chunked prefill

[Upstream PR](https://github.com/vllm-project/vllm/pull/61733) · state: open · merged: False

## Original PR description



## Overview

When `EngineCore` disables chunked prefill after startup validation (models without KV cache, such as a decoder served with `hf_overrides={"is_causal": false}`, or non-causal attention layers), a prompt longer than the per-step token budget is accepted but can never be scheduled. The request waits forever and blocks every request queued behind it. This PR rejects such prompts at admission with a clear error, and fixes the related startup failure of decoders without KV cache under default prefix caching.

Related: #55130 handles the same family of problems for HRM-Text at configuration time. This PR covers the no-KV-cache path, which #55130 does not touch, and replaces the hang with a per-request error rather than a startup error (see Details).

Duplicate check (October 14): open PRs searched for unschedulable prompts, disabled chunked prefill and `is_causal=False` hangs. Only #55130 overlaps (above); #54348 fixes an admission deadlock for blocked-waiting request statuses, a different path.

## Claims

- A prompt that cannot fit in one scheduling step after chunked prefill was disabled now fails immediately with `VLLMValidationError` (HTTP 400 from the API server) instead of hanging the engine. Prompts that fit are unaffected and continue to be served.
- The engine reports its effective `enable_chunked_prefill` setting in `EngineCoreReadyResponse`, so the frontend's input validation uses the same rule as the scheduler, including `max_num_scheduled_tokens` and speculative-decoding draft slots.
- A startup warning states the effective prompt limit when it is smaller than `max_model_len`.
- Decoders without KV cache start with default settings: prefix caching is disabled when there is no KV cache group. Previously the default configuration failed with `AssertionError: HybridKVCacheCoordinator requires at least one cacheable group`.

## Details

Root cause: `SchedulerConfig.verify_max_model_len` only rejects `max_num_batched_tokens < max_model_len` when chunked prefill is disabled at configuration time. `EngineCore` disables it later, after workers are created, in two places: when there is no KV cache group and when a KV cache spec is `non_causal`. Admission still checks prompts against `max_model_len` only, and the scheduler then `break`s on a waiting prompt larger than its budget, so the request never runs and blocks the queue.

Raising the budget at that point is not possible because workers have already been sized with it, and re-running `verify_max_model_len` there turns default configurations into startup errors (the concern raised in review of #55130). This PR keeps serving and rejects only the prompts that can never be scheduled. The limit is `min(max_num_scheduled_tokens or max_num_batched_tokens, max_num_batched_tokens - draft slots)`, the scheduler's own budget, exposed as `SchedulerConfig.max_unchunked_prompt_len`. Multimodal encoder-only models are exempt, as in the scheduler.

Relationship to #55130: there, models can declare missing chunked-prefill or prefix-caching support at configuration time so that defaults raise the budget before workers start, and the late `EngineCore` path re-validates at startup. The two changes touch the same `EngineCore` block. They compose: declared models get correct defaults from #55130, while this PR is the fallback for undeclared models and for decoders without KV cache. Whichever lands second should keep the admission check rather than the startup re-validation.

Not covered: a preempted, resumed request whose prompt plus generated tokens exceeds the budget on a non-causal KV-cache model. Decoders without KV cache are not preempted.

Complexity: about 75 non-test lines across `core.py`, `core_client.py`, `input_processor.py`, `SchedulerConfig` and `EngineCoreReadyResponse`. No scheduler logic changes.
