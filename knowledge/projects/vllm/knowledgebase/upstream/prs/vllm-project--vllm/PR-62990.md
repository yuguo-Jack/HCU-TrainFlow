# [ROCm][Kimi-K3] Allow DSpark adaptive verification with DCP on ROCM_AITER_MLA

[Upstream PR](https://github.com/vllm-project/vllm/pull/62990) · state: closed · merged: True

## Original PR description

## Overview

#59824 enabled DSpark adaptive verification (AV) on `ROCM_AITER_MLA` for `decode_context_parallel_size == 1` only. Kimi-K3 on MI355X serves its mid- and high-concurrency points at TP8/DCP8, where AV was refused after the weight load. This PR enables AV at DCP > 1 on the routes that place verify queries by global position (cprr asm, segmented MLA, gfx942 Triton).

## Claims

- AV produces exact attention at DCP > 1 on the cprr and segmented routes (unit level with real kernels; see Validation).
- Every kernel input stays exactly as in uniform DCP verify: local and global lengths, `g_kv_indptr`, page indices, no `CLAMP_TAIL`. Only the q/o row maps change; unlike DCP1 there is no extra page-index buffer for padded lengths.
- An AV + DCP configuration that no route can serve now fails at backend selection, before the weights load, instead of in the AV manager after the load.
- DCP1 behaviour is unchanged.

## Details

**Why the DCP1 layout is wrong under DCP.** Under AV, the host `query_start_loc_cpu` holds an even split of the draft budget, and the device `query_start_loc` holds each request's admitted length q ≤ W = K + 1. At DCP1, #59824 runs every request as a uniform W-row block:
- Real tokens are left-aligned.
- The kernel KV length is extended by the pad `W - q`.
- The page tail is clamped.

At DCP > 1 that pad lands on the rank-local length, while cprr builds query positions from `g_kv_indptr`, which holds the unpadded global length. Real token t then sits at global position `S - W + t` instead of `S - q + t`, and loses `W - q` causal tokens, its own included.

**Right-align instead.** At DCP > 1 the admitted tokens are written into rows `W - q .. W - 1` of their block (`_fill_varlen_rows`). The routes then line up without touching any length:
- **cprr:** block row i sits at global position `G - W + i`. cprr derives a request's query positions from its `qo_indptr` width and its global length, so real token t lands on `S - q + t` exactly.
- **Segmented / Triton row view:** row t covers global positions `[0, S - W + t]`, which gives the same windows.
- **Pad rows:** they sit at earlier positions and only read pages the request already owns. `varlen_o_rows` drops their outputs.

At DCP1 right-alignment faulted the ASM kernel on contexts shorter than the block. That was because the plain kernel trims the block's causal tail against the local end, which cprr does not do. The GPU numerics cover sequences shorter than the block and than DCP.

**Empty shards.** For a request with nothing on a rank, the cprr kernel leaves the LSE unspecified (finite or NaN). As in uniform DCP verify, the combine masks those rows via `seq_lens == 0`, and `correct_attn_out` zeroes zero-weight partials. The numerics test now runs the merge through this production path.

**Fail early.** `_adaptive_dcp_verify_unsupported_reason` rejects these configurations:
- `cp_kv_cache_interleave_size != 1`;
- no route that places queries by global position: cprr needs gfx950, `W >= 3`, and the env not forced to `segmented`; otherwise segmented MLA or gfx942 Triton is required.

`AiterMLABackend.validate_configuration` raises with that reason rather than returning it. No other ROCm MLA backend supports AV under DCP. Without the raise, auto-selection falls back to `TRITON_MLA`, and that fails in the AV manager only after the weight load.

**Limitations**
- **#62769 is required.** At DCP > 1 the DCP group is the TP group. Each rank computes its own draft budget and per-request split, and the q head gather, the LSE merge and the round-robin KV writes all assume every rank uses the same split. Without consensus, a divergence is silently wrong output, not a hang. This exposure already exists for TP > 1 at DCP1 through the o_proj all-reduce; DCP adds the attention collectives to it.
- **Performance.** At DCP8 every batch still runs `num_reqs × W` attention rows, so AV saves only the MoE, GEMM, KDA and collective work on trimmed tokens. Performance data will come with the end-to-end run.
- **Not covered by tests:** FULL-graph replay of ragged splits at a fixed captured size, the gfx942 Triton row view, and W = 2 (segmented only). The GPU numerics run in the same CI step as the existing cprr numerics.

#### 2. 🔵 Nit: Unsupported config raises instead of appending invalid reason
`vllm/v1/attention/backends/mla/rocm_aiter_mla.py:617-630`

`AiterMLABackend.validate_configuration` raises `ValueError` for unsupported adaptive-verification + DCP configs, unlike every other check, which uses `invalid_reasons.append(...)`. The ROCm selector catches only `ImportError`, so auto-selection stops at `ROCM_AITER_MLA` instead of recording a reason. In practice no fallback could serve this config. `ROCM_AITER_TRITON_MLA` inherits the same check. `TritonMLAMetadataBuilder` (`supports_dcp_with_varlen` defaults to False) is rejected by `_validate_dspark_dcp_support` for DSpark with DCP. So the user sees a hard error either way, and appending the reason is only for consistency and the selector's aggregated diagnostics.

**Who is affected:** ROCm MLA users running DSpark with `enable_adaptive_verification` and `decode_context_parallel_size>1` in an unsupported layout (e.g. `cp_kv_cache_interleave_size!=1`); they get this ValueError instead of a selector or builder ValueError.

#### 4. 🔵 Nit: DCP routing comment and new helpers lack documentation
`vllm/v1/attention/backends/mla/rocm_aiter_mla.py:378-399`

Under DCP, adaptive varlen verify right-aligns rows: `_fill_varlen_rows` shifts `row_pos` by `width - row_qlen`, `seq_lens_for_kernel` is not inflated, and `CLAMP_TAIL` is off.
