# [Perf] Use value-only reduction for FP8 group quantization

[Upstream PR](https://github.com/vllm-project/vllm/pull/59564) · state: open · merged: False

## Original PR description



Fixes #25094 

Slack context: https://vllm-dev.slack.com/archives/C08K1FAHFPH/p1790784879162549

## Summary

 - The issue is simply that the compiled one uses `torch.max(...)[0]` which causes a reduction over values and indices, whereas the cuda one correctly only reduces values.
 - Replacing it with `amax()` immediately resolves the issue and compiled is now uniformly faster than cuda.
 - As per slack discussion, in the bench repro below we compile it with the maximum value of `num_tokens`.
 - The bench also checked that the change preserves the output of the previous implementation exactly.

## Environment

H200 sm90, PyTorch 2.13.0+cu130, Triton 3.7.1, driver 580.126.09, vLLM 2fc3f9

## Long

Initially, the issue seemed to be an autotuning quirk, where inductor was choosing block size `XBLOCK=32` even though it was slower than `XBLOCK=8`, but this is an issue only for small values of `num_tokens` like 1024. Higher than that (relevant values are 8192 and 16384), it did use `XBLOCK=8` and the issue turned out to be an unnecessary reduction over indices in the generated kernel itself, as described below:

For `max()[0]`, Inductor generated:

```py
  tmp5 = tl.broadcast_to(rindex, tmp4.shape)
  tmp3_val, tmp3_idx = triton_helpers.max_with_index(tmp4, tmp5, 1)
  tmp3 = tmp3_val[:, None]
```

The fix, using `amax()`, makes it generate:

```py
  tmp5 = triton_helpers.max2(tmp4, 1)[:, None].to(tl.float32)
```

|  | max()[0] | amax() |
| :--- | :--- | :--- |
| Static instructions | 480 | 360 |
| SHFL.BFLY | 6 | 3 |
| Integer SEL | 33 | 17 |
| Registers | 29 | 30 |


The slowdown is not register pressure related, and seems to be cos of the extra instructions.

<summary>Reproducer</summary>

```py
import torch

from vllm.benchmarks.lib.utils import default_vllm_config
from vllm.model_executor.layers.quantization.input_quant_fp8 import (
    QuantFP8,
    _FP8_DTYPE,
    _FP8_MAX,
    _FP8_MIN,
    _FP8_MIN_SCALING_FACTOR,
)
from vllm.model_executor.layers.quantization.utils.quant_utils import GroupShape
from vllm.triton_utils import triton


torch._dynamo.config.automatic_dynamic_shapes = False


def quantize(x: torch.Tensor, value_only: bool):
    shape = x.shape
    grouped = x.view(-1, x.shape[-1] // 128, 128)
    if value_only:
        absmax = grouped.abs().amax(dim=-1, keepdim=True).float()
    else:
        absmax = grouped.abs().max(dim=-1, keepdim=True)[0].float()
    scales = torch.exp2(torch.ceil(torch.log2(absmax / _FP8_MAX)))
    scales = scales.clamp(min=_FP8_MIN_SCALING_FACTOR)
    output = (grouped / scales).clamp(_FP8_MIN, _FP8_MAX).to(_FP8_DTYPE)
    return output.view(shape), scales.squeeze(-1)


def before(x):
    return quantize(x, False)


def after(x):
    return quantize(x, True)


def run(compile_max: int):
    for hidden in (2048, 4096, 7168):
        quant = QuantFP8(False, GroupShape(1, 128), column_major_scales=False)
        assert quant.use_ue8m0

        before_compiled = torch.compile(before, fullgraph=True, dynamic=False)
        after_compiled = torch.compile(after, fullgraph=True, dynamic=False)

        compile_input = torch.randn(
            compile_max, hidden, device="cuda", dtype=torch.bfloat16
        )
        torch._dynamo.mark_dynamic(compile_input, 0)
        before_compiled(compile_input)
        after_compiled(compile_input)
        torch.cuda.synchronize()

        for tokens in (512, compile_max):
            x = torch.randn(tokens, hidden, device="cuda", dtype=torch.bfloat16)
            old = before_compiled(x)
            new = after_compiled(x)
            torch.testing.assert_close(new[0].float(), old[0].float(), rtol=0, atol=0)
            torch.testing.assert_close(new[1], old[1], rtol=0, atol=0)

            bench = lambda fn: 1000 * triton.testing.do_bench_cudagraph(fn)
            old_us = bench(lambda: before_compiled(x))
            new_us = bench(lambda: after_compiled(x))
            cuda_us = bench(lambda: quant.forward_cuda(x))
            print(
                f"| {compile_max} | {tokens} | {hidden} | "
                f"{old_us:.3f} | {new_us:.3f} | {cuda_us:.3f} |"
            )


@default_vllm_config()
def main():
    from torch._inductor.utils import fresh_inductor_cache

    print("| compile max | tokens | hidden | before (us) | after (us) | CUDA (us) |")
    print("|---:|---:|---:|---:|---:|---:|")

    for compile_max in (8192, 16384):
        with fresh_inductor_cache():
            torch._dynamo.reset()
            run(compile_max)


if __name__ == "__main__":
    main()
```

@ProExpertProg wrote:

> Nice find! You should also submit a fix to pytorch (or at least the issue), I think it would be good to fix inductor in this case as well!

It is a bit subtle in this case. Since `.max()[0]` breaks ties using index, it can return a differently signed zero (+0f or -0f) than `amax()` if zero is indeed the maximum. In our case, we chain `.abs()`, so this is not an issue. I will check the inductor repo to see if a special case for lowering `.abs().max()[0]` to `tl.max` instead of `tl.max_with_index` is harmonious. That is to say, the general optimisation pattern already exists in inductor, it wasn't applied here because of the signed zero edge case.
