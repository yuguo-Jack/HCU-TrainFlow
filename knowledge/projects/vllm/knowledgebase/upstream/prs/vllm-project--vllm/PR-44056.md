# fix(ngram): match async ngram_gpu acceptance rate to CPU

[Upstream PR](https://github.com/vllm-project/vllm/pull/44056) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Fix inflated draft-token counts for async `ngram_gpu` on Model Runner V1. Report worker-trimmed slots to the scheduler and exclude them from both aggregate and per-request acceptance statistics.

## Claims

- Count only valid ngram drafts, preserving statistics already accumulated for other requests when a request has no valid drafts.
- Keep aggregate and optional per-request draft counts consistent, including when grammar-invalidated drafts are also present.
- Correct statistics only: no change to proposal selection, sampling, or scheduled-token trimming; no throughput improvement is claimed.

## Validation

Local environment: Ubuntu 22.04 / WSL2, RTX 5090 Laptop GPU (24 GB), driver 610.62, Python 3.12.13, PyTorch 2.14.0+cu130, Triton 3.8.0. Model: cached `Qwen/Qwen2.5-0.5B-Instruct` at revision `7ae557604adf67be50417f59c2c2f167def9a775`.

Base: `1a5b187066c918b2e23184560d703174dd542828`; initial fix: `14aceba778ea065beb608a416eaead0a4b4a3f6f`. Both used identical native artifacts from the base commit's official cu130 wheel. JSON records retain source SHA-256 hashes and the actual checkout; editable package version metadata alone does not identify the tested checkout.

Settings: `VLLM_USE_V2_MODEL_RUNNER=0`, FP16, greedy, seed 0, eager execution, prefix caching off, maximum output 128 tokens, model length 2048, maximum batched tokens 2048, maximum sequences 4. Ngram: `k=4`, lookup lengths 2–5. Twelve synthetic prompts per workload; a warm-up request was excluded from metric deltas. GPU runs explicitly enabled async scheduling; the CPU proposer reference disabled it (target inference still used the GPU).

| Base, GPU ngram | 4 | 4324 | 453 | 10.48% |
| Fixed, GPU ngram | 1 / 4 | 956 | 448 | 46.86% |

A second GPU run gave 4336/448 on the base and 956/448 on the fix at both batch sizes. The initial batched comparison had one output difference after EOS (generation deliberately continued past EOS); the same difference occurred between two base runs. The repeated base/fix pair matched 24/24 output token sequences. This does not establish general bitwise determinism.

With **normal EOS stopping**, base GPU ngram reported 2952 drafted / 236 accepted (7.99%), versus 622 / 236 (37.94%) after the fix, at both batch sizes. Output token sequences matched **24/24 requests**. A further run with the per-request follow-up enabled retained those counts and all 24 outputs; summed per-request drafted/accepted counts equaled the aggregate counters.

## Details

The V1 worker trims padded speculative slots before execution, while the scheduler retains its original padded draft count. Previously, the removed count never reached the scheduler, inflating the denominator. `update_scheduler_for_invalid_drafts()` now returns per-request removal counts, carried in optional `ModelRunnerOutput.ngram_invalid_spec_tokens`. The scheduler subtracts them alongside grammar-invalidated drafts. Empty/all-invalid requests preserve the aggregate accumulated for earlier requests. The follow-up applies the same deduction to optional per-request metrics.

This remains useful for deployments explicitly using MRV1. MRV2 uses a separate ngram implementation that fills unmatched slots with ordinary rejectable drafts; it does not use this V1 trimming/reporting path. This PR does not claim CPU/GPU acceptance parity for every model or for MRV2. The existing D2H completion wait is unchanged; the patch adds no GPU synchronization.

Independent data point in case it helps review.

Setup: vLLM 0.31.0, Tesla T4, fp16, Qwen2.5-1.5B-Instruct, `num_speculative_tokens=4`, `prompt_lookup_min=2`, `prompt_lookup_max=5`, greedy, 30 single requests, `max_tokens=128`, counters read from `LLM.get_metrics()` (`vllm:spec_decode_num_drafts / _num_draft_tokens / _num_accepted_tokens`). I used vLLM's default scheduling settings and did not record whether async scheduling was active for the `ngram_gpu` runs.

| proposer | drafts | drafted tokens | accepted |
|---|---|---|---|
| `ngram` (CPU) | 322 | 1,283 | 302 |
| `ngram_gpu` | 2,984 | 11,936 | 302 |

Accepted tokens agree, while drafted tokens are ~9.3x higher with `ngram_gpu`, so the reported acceptance rate is ~2.5% instead of ~23.5%. The CPU numbers equal an offline replay of `_find_longest_matched_ngram_and_propose_tokens` on vLLM's own outputs (30/30 requests), so the difference is in the `ngram_gpu` statistics, consistent with this PR's diagnosis. The same ~9-10x ratio appeared in all 9 `ngram_gpu` configurations I ran (greedy and sampling, batched, `max_num_seqs=4`, chunked long prompts, k=8).

Scripts and logs: https://github.com/novain-shibu/spectrace (`kaggle/matrix2/run.py`, `results/logs/spectrace-matrix-2.log`).
