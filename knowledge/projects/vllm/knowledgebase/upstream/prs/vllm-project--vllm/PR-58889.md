# [Bugfix][Model Loader] Restore kernel state post model loading via `TensorizerLoader`.

[Upstream PR](https://github.com/vllm-project/vllm/pull/58889) · state: open · merged: False

## Original PR description


This PR targets issue https://github.com/vllm-project/vllm/issues/55198 about the `TensorizerLoader`. Particularly, the current implementation of `TensorizerLoader` fails to run post-loading processing on the model weights, and also skips computing any state required for the kernel backends to execute the model. As mentioned in the issue, `TensorizerLoader` fails to call either of `process_weights_after_loading` and `finalize_layerwise_processing`, and also fails to return the model in `.eval()` mode.

The reproduction code mentioned in the issue is not very helpful; it only tracks the actual function calls by constructing the call graph. For a minimal reproduction of the issue, I've only focused on the following:

- Model: `Qwen/Qwen3-0.6B-FP8`
- Revision: `e5be08033360965ceca7b0ffd72d521a51331ce0`
- Quantization: block-scaled FP8
- Linear backend: Marlin

Here are my hardware/other specs:

- GPU: NVIDIA GeForce RTX 3050, 6144MiB VRAM
- Ubuntu 22.04
- vLLM checkout: `v0.28.0`

Note that the issue persists in two "paths": one is the raw checkpoint path, where the `TensorizerLoader` is used to load raw checkpoint weights, and is supposed to run post-processing + computing the state. The second path is the "native" vLLM path: here, post-processing is already run, and the loader just needs to compute the state required by the kernels. For this PR, the focus is only on the native vLLM path, since it is trickier.

As it can be seen, the `TensorizerLoader` never constructs the `workspace` object needed by the Marlin kernel. This is because `process_weights_after_loading` was never called.

## Purpose

The PR aims to fix the above error. There is something to note, however: `process_weights_after_loading` is not idempotent for the native path. Particularly, if a checkpoint has already been saved via the native path, then the tensors in the file are already processed. Running `process_weights_after_loading` on those tensors will result in errors.

Instead of calling `process_weights_after_loading`, our solution introduces a new function to the class design: `initialize_runtime_state_after_loading`. This function does a subset of what `process_weights_after_loading` does; particularly, it only computes the state needed for the backend execution. For the case of the Marlin kernel, this function will compute the linear workspace (see the diff in the class `MarlinFP8ScaledMMLinearKernel`). Similar to the design for the `process_weights_after_loading`, we use dynamic dispatch for the introduced function.

However, I'd love to discuss with the maintainers if this is a good design choice (or if they'd like something else to be done). I can also potentially extend the scope of this PR (to involve more linear backends) if the maintainers agree that the proposed solution is good.
