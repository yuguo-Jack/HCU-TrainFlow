## Overview

NVIDIA-Nemotron-Labs-Dory1.0-4B-BF16 is a latent-recurrent / looped large language Model (LLM) trained by NVIDIA. This is the full-precision (BF16) release of Dory1.0-4B. The model employs normalized-GPT architecture with interleaved hybrid sliding window attention (SWA) and full attention layers. By repeatedly applying a shared block of layers, Dory1.0-4B can trade inference compute for accuracy by changing the loop count.

- shan18 · comment · 2026-10-10T16:36:39Z · [source](https://github.com/vllm-project/vllm/pull/60149#issuecomment-6099769162)

Yes, we looked into the Transformers backend. Dory isn’t directly compatible with its current implementation.

Dory is a looped transformer that shares layer weights across loops but keeps a separate KV cache per loop by default.
* The backend creates one attention instance per layer_idx and rejects duplicates, so per-loop caches would need backend support for virtual attention layers. 
* The backend expects every layer to dispatch attention, but half of Dory's layers are MLP-only.
* Dory also has learned per-vocabulary logit scaling that the backend's generic LM head does not handle.

The native implementation keeps all of this self-contained, without changing engine code.

`recurrent_kv_cache_mode="last_loop"` in the engine drifts from the model's own last-loop computation once the context passes the sliding window.

**Setup.** nvidia/NVIDIA-Nemotron-Labs-Dory1.0-4B-BF16 at b366b87f, this PR at 55076950 (Python-only build over the 153a1716 wheel), one H100. Engine: `LLM(model, dtype=..., max_model_len=2048, enable_prefix_caching=False, hf_overrides={"n_recurrent_loops": L, "recurrent_kv_cache_mode": mode})`, one request at a time, greedy, `logprobs=-1`. Two prompts: a short sentence followed by 256 tokens, and 1100 random token ids (`np.random.default_rng(7).integers(1000, 131072, 1100)`) followed by 64 tokens.

**Reference.** This PR's `DoryForCausalLM`, built the way `tests/models/test_dory.py` builds it (that file's `ReferenceAttention` in place of `Attention`, TP stubbed to 1), run in float64 and fed the engine's tokens one at a time at the same positions: prefill the prompt, then decode. In float64 it matches an independent float64 implementation of the model to about 1e-13.

**Metric.** RMS over the decode rows and all 131072 log-probabilities of (engine − float64 model code):

| run | rows before the window | rows past position 1024 |
|---|---|---|
| fp32, 2 loops, per_loop | 0.0046 | 0.0153 |
| fp32, 2 loops, last_loop | 0.0092 | 0.3396 |
| bf16, 2 loops, per_loop | 0.074 | 0.278 |
| bf16, 2 loops, last_loop | 0.167 | 0.496 |
| bf16, 4 loops, per_loop | 0.105 | 0.401 |
| bf16, 4 loops, last_loop | 0.353 | 0.811 |

In fp32, per_loop stays at rounding level past the window, while last_loop is 22× further from the model code than per_loop there. So the engine's shared final-loop KV for sliding-window layers seems to be written or read differently from what the model code specifies (and what `test_last_loop_kv_matches_final_loop_history` checks with the reference attention) once positions exceed the window, for example in how the paged sliding-window blocks are handled for the shared layers. Before the window, last_loop is also about 2× per_loop in every run, which may be the same issue or the shared cache's own rounding. I can share the scripts if that helps.

- hmellor · comment · 2026-10-15T12:38:37Z · [source](https://github.com/vllm-project/vllm/pull/60149#discussion_r4283039807)

File: `vllm/transformers_utils/configs/dory.py` · line None

Here are some notes from Claude:

1. **Use `layer_types` rather than `layers_block_type`.** That's the name new Transformers configs use; `layers_block_type` only survives for backwards compatibility in older models. It's written into `config.json`, so it's best to change it before the checkpoint is released.
2. **A top-level `rope_theta` is silently ignored.** `__post_init__` sets `rope_theta: 10000` before the base class gets a chance to apply it. Set `default_theta = 10_000.0` on the class and leave `rope_theta` out of the default `rope_parameters`.
3. **Some validation is duplicated.** `@strict` already checks types and runs `validate_architecture()`, so you can drop the manual type checks and the explicit `validate_architecture()` call in `DoryForCausalLM.__init__`.
4. **Nit:** fields that can only take one value (`ngpt`, `fngpt`, `input_transform`, etc.) would likely be removed in an upstream port. They're harmless to keep.
