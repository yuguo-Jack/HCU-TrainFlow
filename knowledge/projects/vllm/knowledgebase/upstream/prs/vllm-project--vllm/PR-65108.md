# [Bugfix][LoRA] Fix GPT-OSS triton_kernels 3.8 MoE LoRA row order

[Upstream PR](https://github.com/vllm-project/vllm/pull/65108) · state: open · merged: False

## Original PR description



## Overview

Fix LoRA on the GPT-OSS `UnfusedOAITritonExperts` `triton_kernels` 3.8 path (used on ROCm): expert LoRA deltas were applied to the wrong (token, expert) rows. Introduced with the 3.8 support in #55934; related: #63979 (open) would offer this path for MXFP4 MoE on ROCm before emulation.

## Claims

- Plain (single-adapter) MoE LoRA on the 3.8 path now matches a merged-weight reference; before, outputs were wrong (max relative error 3.23, RMS 0.80 vs. tolerances 0.025 / 0.005).
- No change to the 3.5.1/3.6 path (CUDA default) or to any non-LoRA behavior.

## Validation

New test: `tests/kernels/moe/test_modular_oai_triton_moe.py::test_unfused_oai_triton_moe_lora_matches_merged_weights`. It runs `UnfusedOAITritonExperts` with a real `PunicaWrapperGPU` / `MoELoRAContext` (two adapters alternating across tokens) and compares against the base expert weights plus each adapter's `B @ A`. Top-k ids come back in score order, so the expert-sorted permutation is non-trivial.

For validation only, I installed `triton_kernels` from Triton `v3.8.0` in a scratch environment on the H100 and, inside that environment, passed `mx_axis=-2` (the same axis, spelled as 3.8's Hopper layout requires) in the test helper `mxfp4_w_layouts`. Neither change is part of this PR. In CI, the AMD mirror of "MoE Kernels" (MI300) runs this file on the real 3.8 path; the NVIDIA step runs on L4, where this backend is skipped (SM < 9.0).

## Details

Root cause: `triton_kernels` 3.8's `matmul` no longer scatters and top-k-reduces in-kernel (#55934), so `inter`, `act_out` and `down` are in expert-sorted (ragged) order. The LoRA kernels address rows as `token * topk + slot`. The existing code converted the w2 LoRA output (`down_tt[order] = down`) but passed the ragged `inter` as the w13 LoRA output and the ragged `act_out` as the w2 LoRA input, so those deltas were added to, and read from, other (token, expert) pairs. The error disappears only when the expert sort is the identity (e.g. one token with ascending expert ids), which is why small cases can hide it.

Fix: compute the expert-sort permutation once (it matches `make_routing_data`'s stable sort; `-1` slots are kept as zero-weight rows, so it covers all `M * topk` rows), and convert to token-topk order around both LoRA calls: scatter `inter` before w13 LoRA and gather it back afterwards; give w2 LoRA a token-topk `act_out`.

Test note: `oai_triton_moe_impl` now configures `MoEActivation.SWIGLUOAI`, the activation these tests already pass to `apply`. The LoRA gate/up interleave keys off the configured activation, and the other 21 tests are unaffected.

Found while adding routed (multi-adapter) LoRA for MoE experts under RFC #49705 (follow-up to #51294); this fix is independent of that work.
