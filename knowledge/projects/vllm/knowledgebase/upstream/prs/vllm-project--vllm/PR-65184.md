# [ROCm][CI] Gate MoRI EPv2 modular-kernel cases on the production EPv2 checks

[Upstream PR](https://github.com/vllm-project/vllm/pull/65184) · state: closed · merged: True

## Original PR description

## Overview

Since #61361, `:amd: (MI300) MoE Kernels Multi-GPU` fails on main ([amd-ci#15761](https://buildkite.com/vllm/amd-ci/builds/15761)): all 3 `MoriEPv2PrepareAndFinalize` cases hit a MoRI assertion on MI300X. This test-only PR registers MoRI EPv2 in the modular-kernel harness only where production would select it.

## Claims

- The MI300 Multi-GPU step passes again. The MoRI EPv1 and DeepEP cases are unchanged.
- MoRI EPv2 cases are generated only on gfx950/gfx1250 with MoRI >= 1.2.4, the conditions `RocmPlatform.check_and_update_config` uses.

## Validation

MI300X, `rocm/vllm-dev:ci_base` with MoRI 1.2.3.post1 (as in CI), 2 GPUs:

```bash
cd tests
VLLM_ROCM_USE_AITER=1 VLLM_ROCM_USE_AITER_MOE=1 pytest -v -s kernels/moe/test_modular_kernel_combinations.py -k multigpu
```

| | main | this PR |
|---|---:|---:|
| Collected | 33 | 30 |
| MoRI EPv2 / EPv1 cases | 3 / 8 | 0 / 8 |
| Result | 3 failed, 30 passed | 30 passed |

On main, the EPv2 cases fail locally with the CI error: `AssertionError: combine block_num 304 exceeds xdb_flag_slots 256`.

## Details

The harness sets `mori_ep_v2=True` for the `"mori"` backend. That skips the EPv1 fallback production uses unless MoRI >= 1.2.4 is installed and the GPU is gfx950/gfx1250. On MI300X, MoRI's untuned EPv2 path uses one combine block per CU (304), above its fixed limit of 256. [ROCm/mori#876](https://github.com/ROCm/mori/pull/876) fixes this, but no MoRI release includes it yet.

AI-assisted tooling was used to analyze the CI logs, write the change, and run the validation. The change and the results were manually reviewed.
