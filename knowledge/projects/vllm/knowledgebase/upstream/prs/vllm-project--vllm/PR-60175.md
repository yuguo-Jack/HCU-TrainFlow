# [Docs][Metrics] Document prefix cache hit rate monitoring and add a G…

[Upstream PR](https://github.com/vllm-project/vllm/pull/60175) · state: open · merged: False

## Original PR description



## Overview

The prefix caching guide never mentions `vllm:prefix_cache_hits` or `vllm:prefix_cache_queries`, and none of the example dashboards chart the hit rate. Working out what the number actually counts currently means reading the scheduler. This adds a short Monitoring section to `docs/features/automatic_prefix_caching.md` and a hit rate panel to the Prometheus and Grafana example dashboard.

## Claims

- The guide gives the PromQL for the hit rate and explains why it can differ from the "Prefix cache hit rate" log line, which covers the last 1000 requests rather than a time window.
- It lists what limits the number and what it leaves out: full-block hits, the recomputed last token, the system prompt upper bound, preemption reschedules and requests that skip the lookup. I checked each one against `kv_cache_manager.py`, `scheduler.py` and `stats.py`.
- The panel goes in the empty slot next to TPOT and copies the Cache Utilization panel's settings. No existing panels change.

Docs and the example dashboard only.

## Validation

I ran the Prometheus and Grafana example against vLLM 0.31.0 on one A10G and imported the dashboard from this branch. The only change to the example setup was adding Grafana's image renderer for the screenshot. The model was a randomly initialized 2-layer Llama with a small word-level tokenizer, which is enough because the hit rate only depends on token IDs.

Load came from `vllm bench serve --dataset-name random --random-output-len 16 --ignore-eos --num-prompts 600 --request-rate 4`, run in two phases:

| phase | prompts | hits / queries | hit rate | expected |
|---|---|---|---|---|
| A | `--random-prefix-len 2048 --random-input-len 256` | 1,227,232 / 1,382,400 | 0.888 | 599 × 2048 / (600 × 2304) = 0.887 |
| B | `--random-prefix-len 0 --random-input-len 2304` | 4,576 / 1,382,400 | 0.003 | ~0 |

Hits and queries are the counter deltas over each phase. The panel shows the same two plateaus.

<img width="1000" height="500" alt="vllm-pr2-panel" src="https://github.com/user-attachments/assets/5971e168-8398-47a2-b365-16f668de31d7" />

The log line shows the window difference nicely. It read 88.8% after phase A and 35.8% after phase B, because its 1000-request window still held 400 requests from A: (400 × 2048 + 4,576) / (1000 × 2304) = 0.358.

`pre-commit run markdownlint-cli2` and `typos` pass on both files.

## Details

No open PR touches either file. #56923 also documents metrics, but only in `docs/design/metrics.md` and `loggers.py`.

I only changed the `prometheus_grafana` example. The dashboards in `examples/observability/dashboards/` come in Grafana and Perses pairs, so adding the panel there is better as its own PR.

I used Claude to trace the counting logic and draft the text. I reviewed every line and checked each claim against the code and the run above.
