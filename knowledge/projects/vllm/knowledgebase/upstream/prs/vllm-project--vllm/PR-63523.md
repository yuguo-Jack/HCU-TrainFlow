# [Attention] Take per-step host metadata math off torch dispatches

[Upstream PR](https://github.com/vllm-project/vllm/pull/63523) · state: closed · merged: False

## Original PR description

# Warning: Untested AI-generated code.

Stacked on #63296 and #63393 — the head branch carries both PRs'
commits; only the last four commits are new.

## Motivation

With the decode fusions from the stacked PRs in place, a profiled
DSv4.1-Flash deployment (8xH200, DP=8, MTP, c16 decode) still spends
~820us per ~6ms step in eager Python between CUDA graph launches.
Three clusters of that section are pure host work whose cost is torch
dispatch overhead rather than math:

- the DP coordination tail: after `cpu_all_reduce_` agrees a
  `[7, dp_size]` int32 CPU tensor, `sync_cudagraph_and_dp_padding`
  extracts ~a dozen scalars from it with one torch dispatch per read
  (all/any/min/max/item);
- the batch splits: `split_decodes_and_prefills` and
  `split_decodes_prefills_and_extends` run eq/sub/argmax/any chains on
  `query_start_loc_cpu` and `seq_lens_cpu_upper_bound` — host tensors
  of [num_reqs+1] scalars, where each dispatch costs more than the op
  it runs;
- the batched SWA launch's parameter table: `async_tensor_h2d` builds
  a fresh pinned int64 `[G, 8]` table, allocating per step for eight
  scalars per group.

## What changed

- `sync_cudagraph_and_dp_padding` takes the numpy view of the
  agreement tensor once after the reduce; every field write and scalar
  read runs through it. The torch view handed to `DPSyncState` shares
  the same memory, so the final padded-token fill stays coherent. The
  all-reduce itself still runs on the torch tensor.
- Both split functions take the numpy views of the host tensors once
  per call; comparisons, the first-occurrence argmax, and scalar reads
  run there. `num_prefill_tokens` in the extends variant now returns
  the annotated `int` instead of a 0-dim tensor.
- `_launch_batched` keeps a cached pinned host table and a cached
  device table sized to the largest group count seen, refills the host
  rows through a numpy view, and issues a non-blocking copy into the
  device slice each step, replacing the per-step pinned allocation and
  upload.
- The copy now runs **on change, not per step**: every row holds
  addresses and strides of persistent per-group buffers, so the table
  only differs when a builder reallocates or the group count moves.
  Each step rebuilds the rows as a numpy array and compares against
  the last uploaded one; only a mismatch triggers the refill, copy and
  event record.

## Why the staging refill is race-free

The host table is pinned, so the H2D copy is a true async DMA.
Refilling a pinned source in place is only safe once the previous copy
retired, so a CUDA event recorded after the copy guards the refill:
the cached tables are reused only when the event reports completion,
and a pending event falls back to a fresh table, whose in-flight
lifetime the caching host allocator already guards — the same
guarantee `async_tensor_h2d` relied on. The kernel grid is
`(num_tokens, num_groups)`, so rows past `num_groups` in the cached
table are never read, and the batched path still never runs under
CUDA graph capture (the flush branches to per-group launches there,
as before).

An earlier revision of this PR staged the table in pageable memory on
the theory that a pageable async copy captures its source before the
call returns. That part holds, but CUDA also syncs the stream before
initiating a pageable async copy and stages it through a driver bounce
buffer, so each refill serialized the host against all queued device
work. An H200 PD campaign measured that revision as a uniform ~6-8%
ITL p50 regression at every aiperf concurrency (c8–c128); the
event-guarded pinned table replaces it.

## Safety notes

- No device math changed: every converted op is CPU-tensor host logic
  with identical results (numpy bool argmax is first-occurrence, like
  CPU torch argmax; `.numpy()` on a CUDA tensor fails exactly where
  the old mixed-device ops would have).
- The DP agreement tensor is unchanged on the wire: same `[7,
  dp_size]` int32 layout, same all-reduce, same `DPSyncState` contract
  (`num_tokens_across_dp` is still a torch view of row 0).
- The staging guard only ever trades the cached tables for fresh ones;
  it never reorders, delays, or skips the copy or the launch.
- Equivalence against the previous implementation was checked on CPU
  for both split functions (uniform padded batches, extends/prefills
  mixes, `is_prefilling` overlays, int32/int64 variants), the DP sync
  (no-work, eager/graph/ubatch agreements, uniform-token-count and
  max_query_len agreement and disagreement, skip-drafts votes, skipped
  coordination), and the staging pattern (capacity fill, partial fill
  with an unread stale tail, growth, shrink, pending-event fallback
  leaving the in-flight table intact, numpy-view coherence): identical
  descriptors, sync states, dispatch calls, and padded fills.

## End-to-end measurement

Full-stack H200 PD campaign (8xH200 prefill + 8xH200 decode, DP=8,
MTP spec 3, the same overlay as the stacked A/B baseline), pinned
revision, against the baseline arm carrying the first two stacked
PRs but not this one:

- aiperf ITL p50 at c8/c16/c32/c64/c128: 4.93/5.07/5.77/6.78/8.77 ms
  vs 4.87/5.00/5.79/6.83/8.82 ms — every concurrency within ~1% of
  both baseline arms, the same spread the baseline's own arms show
  between themselves; request counts and prefix-cache hit rates match.
- nyann ITL p50 at c8/c16/c32 (ISL/OSL 2048): 15.51/18.16/22.95 ms
  vs 15.49/18.12/23.00 ms.
- gsm8k 5-shot, full 1319 samples: flexible-extract 0.9697 ± 0.0047
  (baseline arms 0.9704 ± 0.0047 and 0.9719 ± 0.0045), strict-match
  0.9689 ± 0.0048.

The pageable revision this PR originally carried measured a uniform
+5.7–7.2% ITL p50 regression at every aiperf concurrency and
+3.4–6.0% on nyann; with the pinned, event-guarded table the
regression is gone and the stack is performance-neutral against the
baseline arms on every metric above.
