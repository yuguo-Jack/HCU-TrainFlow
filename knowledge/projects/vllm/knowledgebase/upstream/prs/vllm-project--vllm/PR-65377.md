# [Rust Frontend] Drop tool calls under tool_choice=none for split tool parsers

[Upstream PR](https://github.com/vllm-project/vllm/pull/65377) · state: closed · merged: True

## Original PR description

## Overview

With `tool_choice: "none"` and `tools`, drop parsed tool calls and their markup on the Rust frontend's split reasoning-plus-tool-parser path, as structured assembly already does for unified parsers. Today the raw call markup reaches `content`.

## Claims

- With `tools`, `tool_choice: "none"` and a configured tool parser (for example `qwen3_coder`, `glm47`, `kimi_k2`, `deepseek_*`, `minimax_*`), a call the model still emits is parsed and dropped: no `tool_calls`, and no markup in `content`. The surrounding content stays.
- Without a configured tool parser, the output stays plain content and no new error appears.
- `auto`, `required` and named tool choices are unchanged.

```
tools=[search], tool_choice="none", model output:
  Sure.<tool_call>\n<function=search>...</function>\n</tool_call>
before: content = "Sure.<tool_call>\n<function=search>...</tool_call>", tool_calls = []
after:  content = "Sure.",                                             tool_calls = []
```

Tests in `rust/src/chat/src/output/default/mod.rs`:

- `tool_choice_none_drops_parsed_tool_calls` runs a unified parser (gemma4), a split tool parser (qwen3_coder) and the bare-JSON Llama parser through final assembly. `auto` keeps the call each time; under `none` all three drop it (`("Sure.", [])` for gemma4 and qwen3_coder). An ordinary JSON answer stays content under both `auto` and `none`, and without a configured tool parser the markup stays content. With the fix reverted, the qwen3_coder `none` case fails with the raw markup in content.
- `answer_constraint_keeps_optional_tool_calls` asserts that `none` plus a JSON schema constrains the answer alone; it returns `None` with the fix reverted.

## Details

**Python.** `keeps_tool_calls` in `vllm/entrypoints/openai/chat_completion/message_assembly.py` (vllm-project/vllm#63148, vllm-project/vllm#63345) returns false for `none`, and both the non-streaming and the streaming path discard the parsed `tool_calls` while keeping `content`. The parser-engine families also strip the markup from `content`.

**Rust before this change.** Unified parsers (gemma4, kimi_k3, inkling, hf, ...) already drop the calls: `ChatRequest::max_tool_calls()` returns `Some(0)` when tool parsing is off, and structured assembly suppresses every call (vllm-project/vllm#62741). The split path (`CombinedParser`) did not: `DefaultChatOutputProcessor` built no tool parser when tool parsing was off, so the raw call markup reached `content`.

**Change.** With tools present, `DefaultChatOutputProcessor` builds the configured tool parser through one `resolve_tool_parser(&ResolvedToolContext, ..) -> Option<_>` whether tool parsing is on or off, and under `none` leaves dropping to the existing `max_tool_calls = Some(0)`. When no tool parser is configured, it keeps the existing errors with tool parsing on and returns no parser under `none`. Requests without tools still get no tool parser.

- **Layering.** The consumer of `tool_choice` here is structured assembly's `max_tool_calls`, which already serves both parser kinds; this makes parser construction in `vllm-chat`'s default output processor consistent with it. As with `auto`, a family whose parser preserves special tokens (kimi_k2, internlm2, DSML) now decodes with `skip_special_tokens=false` under `none` too, so its markers reach the parser that drops them.
- **Output grammar.** `tool_choice=none` still builds no tool grammar. With a `response_format` and no reasoning parser, the constraint now reaches the engine as a structural tag holding only that answer (`BuiltOutputGrammar::final_output_only(answer)`), the shape `CombinedParser` already builds when a tool parser is active (vllm-project/vllm#60781); it is the same constraint. Harmony is untouched.

**Differences from Python.** Rust drops the calls for every parser. Python's other parsers keep the raw call as content under `none`: the legacy non-engine tool parsers, the HF `ResponseTemplateParser` (`tests/parser/test_response_template.py::test_tool_choice_none_preserves_raw_call_as_content`), and the Llama JSON parser for bare JSON calls (`tests/parser/engine/test_llama_json.py::test_tool_choice_none_preserves_bare_json`). Under `none`, Rust's `llama3_json`/`llama4_json` parse a bare JSON object naming a tool as a call and drop it; other JSON stays content. OpenAI's `tool_choice: "none"` means the model does not call tools, so surfacing calls or their raw markup is wrong either way.

Not a duplicate: no open PR changes tool-call handling under `tool_choice: "none"` in the Rust frontend (searched open Rust frontend PRs for `tool_choice` and tool parser construction). vllm-project/vllm#63580 maps `ParserDisabled` to a 400 for requests with tool parsing on; it is orthogonal, since this change keeps that error where it is raised today.
