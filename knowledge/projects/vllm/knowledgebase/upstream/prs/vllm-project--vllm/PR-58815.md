# [Qwen4Exp] Gather PLE rows on the host from the checkpoint files (`host_file_gather`)

[Upstream PR](https://github.com/vllm-project/vllm/pull/58815) · state: open · merged: False

## Original PR description

## Purpose

Qwen3.8-Flash-Next carries a 47.7 GiB FP8 PLE n-gram table. The storage backends from #54371 keep the whole table in GPU memory or copy it into pinned host memory, so about 48 GiB stays allocated for the life of the server, even though a generation reads only a small part of it. When weights, KV cache and the table do not fit together, the model cannot be served.

This PR adds an opt-in backend, `--engram-config '{"host_file_gather": true}'`, that serves the table from the checkpoint files through the page cache. Rows live in clean, file-backed pages that the kernel can drop and re-read, so the memory a resident table would hold stays available for the KV cache or other work. The table is never mapped into the worker after loading.

## Background from #54129

- A measurement of the access pattern found about 17.6 rows per step, no reuse between consecutive steps, and a 1.6 MiB working set over 800 steps ([comment](https://github.com/vllm-project/vllm/pull/54129#issuecomment-5757052453)).
- Operators ran the previous mmap implementation on discrete GPUs: 8x RTX 3090 ([comment](https://github.com/vllm-project/vllm/pull/54129#issuecomment-5463213366)), an RTX PRO 6000 ([comment](https://github.com/vllm-project/vllm/pull/54129#issuecomment-5463773575)), and a production deployment on 2x RTX 5090 at TP=2, where the weights alone fill host RAM ([comment](https://github.com/vllm-project/vllm/pull/54129#issuecomment-5838606950)). Those numbers are from the previous implementation, not this one.
- Their cold-cache runs showed that misses must be queued rather than faulted one page at a time, which is why this backend issues `POSIX_FADV_WILLNEED` before each gather.
- The illegal-memory-access report on the previous implementation ([comment](https://github.com/vllm-project/vllm/pull/54129#issuecomment-5780599481)) points to the upstream Mamba prefix-cache fix in #53906.

## Design

- **Selection.** `EngramConfig.host_file_gather: bool = False`. Qwen4Exp only; takes precedence over `cpu_offload`; rejected on ROCm and with elastic EP.
- **Storage.** `Qwen4ExpPLEFileGatherEmbedding` allocates no table rows. `load_weights` keeps the default loader's zero-copy safetensors views of each shard. At bind, every view must be file-backed according to `/proc/self/maps` (Hugging Face cache symlinks work; heap, pinned and anonymous memory are rejected), and the shards must cover the whole table. Bind records each shard's file and offset, opens the files read-only and releases the views, so no mapping of the table outlives loading.
- **Staging.** `Qwen4ExpModelState.prepare_inputs` computes each PLE layer's n-gram ids, copies them to pinned host memory, and syncs the stream once per step. It then deduplicates the step's ids, issues `POSIX_FADV_WILLNEED` over the coalesced page ranges of their rows, reads each distinct row with `preadv`, expands duplicates into pinned memory with one `index_select`, and copies the rows into a fixed device staging buffer.
- **Forward.** Reads only the staging buffer, so FULL CUDA graph capture is unaffected. The ids are computed eagerly and consumed on the current stream, so this path is not affected by #58441.
- **Scope.** Rows stay in the checkpoint dtype. Dummy loads serve zeros. Weight reload is rejected. A truncated checkpoint file stops the engine with an error instead of SIGBUS.

## Why this is not a duplicate

#58439 reads the checkpoint mapping directly from the GPU and needs pageable host-page-table access, which unified-memory systems provide. #54070 writes a separate copy of the table to a disk directory and depends on the closed #53899. This PR reads rows on the host from the checkpoint files the loader resolved, so it does not need unified memory.

## Test Plan


End to end on a DGX Spark (GB10, 128 GB unified memory), TP=1, table on local NVMe:

```bash
vllm serve RadixArk/Qwen3.8-Flash-Next-NVFP4 --language-model-only \
  --max-model-len 40960 --max-num-seqs 32 \
  --engram-config '{"host_file_gather": true}' \
  --kv-cache-memory-bytes 17179869184
```

The KV cache was 16 GiB (20 GiB for the default-graph correctness samples, 8 GiB for MTP).

- Correctness: an out-of-tree hook recorded the ids and staged rows of sampled steps (prefill, decode, mixed, MTP draft) and compared them byte for byte with the checkpoint shards.
- Throughput: `vllm bench serve --ignore-eos --random-output-len/--sharegpt-output-len 256` at concurrency 1 and 16, default and FULL graphs, on random prompts and on realistic prompts (GSM8K questions with few-shot turns, 655 to 1,000 tokens).
- Accuracy (before the third commit, with the mapped-view gather): GSM8K, 200 questions, chat template.
- Cold cache: PLE files evicted with `POSIX_FADV_DONTNEED` before startup, then a 30k-token prompt and a decode run at concurrency 1.
- Soak (before the third commit, with the mapped-view gather): MTP n=3 with prefix caching and `--kv-cache-memory-bytes` at 12 GiB, concurrency 8, 16 and 32 for 5 minutes each.
- Memory pressure: two CPU-only processes gathering the same rows from a synthetic table under a cgroup memory cap, with the previous mapped-view gather and with this one.

## Test Result

Unit: 90 passed (`test_ple.py`, `qwen4_exp/test_config.py`); 43 passed (`test_config.py -k engram`); pre-commit and mypy pass.

**Correctness.** 0 mismatches over 1,022,080 staged rows from default graphs, FULL graphs and MTP: prefill 355,072; mixed 661,744; decode 2,704; speculative decode 2,560.

**Accuracy.** GSM8K 98.5% (197/200), measured before the third commit.

**Throughput** (median ITL; staging = host time of the gather and copy per decode step):

| Graphs | Prompts | Concurrency | Output tok/s | Median ITL | Staging / ITL |
|---|---|---|---|---|---|
| default | realistic | 1 | 15.20 | 61.79 ms | 0.38% |
| default | realistic | 16 | 96.29 | 141.89 ms | 7.3% |
| FULL | realistic | 1 | 15.15 | 61.26 ms | 0.39% |
| FULL | realistic | 16 | 98.7\* | 138.0 ms\* | 7.6%\* |
| default | random | 1 | 16.2\* | 59.2 ms\* | 1.7%\* |
| default | random | 16 | 97.1\* | 139.8 ms\* | 7.5%\* |

\* Measured before the third commit, with the mapped-view gather and a 20 GiB KV cache; not re-run.

In the same build and setup at concurrency 1 on realistic prompts, the previous mapped-view gather reached 15.71 tok/s against 15.20 (one run each), with a median time to first token of 567 ms against 615 ms. Prefill pays for the separate read of each distinct row: a warm 2,048-token chunk takes about 32 ms of host staging, against 18 ms before.

At concurrency 16 the staging time is mostly waiting on reads of rows not seen before; major faults stay at 0 per step.

**Cold cache.** A cold 30k-token prompt took 17.40 s to first token, against 15.45 s warm. Disk reads stayed below one 4 KiB page per distinct row. Decode at concurrency 1 after the eviction staged in a median of 0.90 ms per step.

**Memory.** The worker has no mapping of the PLE files after load, at every snapshot from startup through the benchmarks; the table is page cache only. `RssFile` stays flat at about 0.5 GiB, against 2.34 GiB for the previous mapped-view gather after the same warm-up and concurrency-1 run. Anonymous memory stays flat at about 2 GiB, shared memory below 60 MiB, and `VmPin` is 0.

**Memory pressure (synthetic, CPU only).** Two processes gathered the same rows from a 1.9 GiB synthetic table for 40 s under a 2,330 MiB cgroup memory cap (kernel 6.17, MGLRU). With the mapped-view gather they completed 930 and 926 steps, touches of their heap took 64 and 60 ms at p99, and 1.33 GiB of the table was mapped. With this gather they completed 9,648 and 9,647 steps, heap touches took 0.28 ms at p99, and 1.3 MiB was mapped. Both modes still swapped part of each process's heap under this deliberately tight cap.

**Tester result (TP=2, discrete GPUs).** A tester ran this head on 2x RTX 5090 at TP=2, with MoE experts offloaded to host memory out of tree, under a 90 GB cgroup memory cap. Decode on real documents matched their previous mmap build, with a sub-second time to first token; the cold first request ran slowly while the table paged in ([comment](https://github.com/vllm-project/vllm/pull/58815#issuecomment-5865802209)). That was a 15-minute session at up to 2 concurrent requests.

**Soak.** 817 of 817 requests completed across the ramp, plus 177 of 177 on long shared prefixes, with no errors (before the third commit).

## Not covered

- No throughput or memory comparison against the pinned or device backend. On the test machine, the weights (about 70 GiB) plus a resident 47.7 GiB table do not fit in 128 GB with any KV cache, so neither backend can serve this model there.
- Not validated by the author on a discrete GPU or at TP>1; the only such result is the tester's short run above. The author reproduced TP>1 memory-pressure behaviour only on the CPU, with two processes and a synthetic table under a cgroup memory cap.
- Staging is synchronous. At 16 concurrent requests it is 7.3% of ITL; overlapping the host gather with GPU work is possible follow-up work.
- Under memory pressure, evicted pages are read back from NVMe.
- The checkpoint files must stay unchanged while serving: an in-place overwrite serves the new bytes and truncation stops the engine with an error naming the file and offset. Deleting or renaming them is safe.
- Not supported: PP>1, Model Runner V1, ROCm, elastic EP, weight reload.

- Trosfy · comment · 2026-09-27T10:56:34Z · [source](https://github.com/vllm-project/vllm/pull/58815#issuecomment-5855223015)

Thanks for running this on the 5090s at TP=2.

I suspect the shard mappings under the cap. Each rank kept the loader's private mapping of each PLE shard file and gathered rows through it, so every touched page stayed mapped, and so did the neighboring pages the kernel maps on a fault. Reclaim keeps mapped file pages that are still being touched active, and at TP=2 both ranks touch the same pages, so under the cap it tends to swap the workers' own memory out instead of dropping the table's page cache, and every step waits on swap. The old branch mapped the table too, so I may be wrong; the counters below should settle it.

In the latest push I record each shard's file and offset at load, open the files read-only, and release the loader's views, so the worker does not map the table after load. Each step reads the distinct rows it needs with `preadv`, and those pages are plain page cache that reclaim can drop cheaply.

I reproduced this only on a CPU stand-in: two processes under a cgroup cap, reading the same rows of a synthetic table. With the mapped gather the heap the processes touched kept getting swapped out; with the new reads it stayed resident (about 10x the steps, flat heap latency), though both still swapped untouched heap under that tight cap. I have not run this on discrete GPUs or at TP>1.

Could you re-test this head on the same setup? If decode is still slow, these during the slow part:

- `uname -r` and `vmstat 1 10` (`si`/`so`)
- the cgroup's `memory.swap.current` and `memory.stat` (`pgmajfault`, `workingset_refault_anon`)
- per worker, `VmSwap`, `RssAnon` and `RssFile` from `/proc/<pid>/status`
- a `py-spy dump` of a worker

The cap still has to leave room for each worker's anonymous and pinned memory (including the expert pool's staging) plus the table's hot rows, or page cache and the worker heap keep trading places. A quick check is `vm.swappiness=0`: it is system-wide, and under a tight cap it can get the server OOM-killed instead of swapped, but if decode recovers, swap was the problem.
