# [MoE][Offload] Shared GPU expert pool with a device-side planner for NVFP4 Marlin experts (moe_expert_pool_rows)

[Upstream PR](https://github.com/vllm-project/vllm/pull/56177) · state: open · merged: False

## Original PR description

## Purpose

Serve MoE models whose expert weights do not fit in GPU memory with a GPU-resident, device-managed expert pool, so that decode stays inside CUDA graphs. Discussed in #56175.

`--moe-expert-pool-rows N` (`OffloadConfig.moe_expert_pool_rows`, default 0 = unchanged behaviour):

- NVFP4 expert tensors are allocated in pinned host memory at load time; the loader's existing per-layer device round trip does the Marlin conversion and restores the converted tensors to pinned memory.
- After loading, one GPU bank shared by all MoE layers is allocated (initially N rows per layer) and a Marlin consumer is bound to it; the placement is frozen through profiling and graph capture and opened at the end of warm-up.
- The captured decode path runs a device-side LRU step (hits/misses, promotions across layers), fixed-grid row copies from the host source, and one Marlin call with logical alignment and a physical-row remap. No host-side routing readback or cache planning between routing and the GEMM, so the MoE layers stay inside the CUDA graph (`FULL_DECODE_ONLY`).
- Wider batches take a bank + host-view partition path.

Scope: ModelOpt NVFP4 with the Marlin MoE backend, no EP/DP/SP; backend and parallelism are checked at layer construction, cross-layer shape/top-k consistency at pool installation.

Files: `vllm/model_executor/layers/fused_moe/expert_pool/` (tables, copy, pool, layer, install), hooks in `routed_experts.py`, `modelopt.py`, `model_loader/utils.py`, `gpu_worker.py`, config/CLI knob, `docs/features/moe_expert_pool.md`, `benchmarks/expert_pool/` (reproducible client and frozen prompts).

## Test Plan

```
pytest -v -s tests/kernels/expert_pool tests/config/test_moe_expert_pool_rows.py
python -m unittest discover -s benchmarks/expert_pool -p 'test_*.py'
```

`tests/kernels/expert_pool/test_pool_marlin_cuda.py` runs two layers through one bank with the real Marlin kernel (decode with cross-layer eviction, a wide batch through the partition path) and compares against the uncached layers. The other tests are CPU-only (planner tables, copy helpers, installation guards, config/CLI). CI: added to the MoE Kernels shard.

End to end: Qwen3.8-Flash-Next NVFP4 on a 48 GiB GPU budget (RTX PRO 6000 limited by a separate memory-holding process, host 100 GiB), see `benchmarks/expert_pool/README.md` for the exact launch.

- informatico-madrid · comment · 2026-09-26T00:03:23Z · [source](https://github.com/vllm-project/vllm/pull/56177#issuecomment-5841303038)

Big thanks for this PR — it changed our little server overnight. Since your benchmark was single-GPU, I can confirm the pool runs fine under TP=2: we serve Qwen3.8-Flash-Next NVFP4 24/7 on 2x RTX 5090 (32 GB each), installed on top of the rebased PLE mmap port (the #54129 lineage — needed to load the PLE table on this host at all), --moe-backend marlin, no deferred rows, MTP off since the FP8 draft hits the Marlin guard as documented.

We swept the bank size a bit (rows per layer / KV left over / single-request decode):

- rows=64: KV 2.55M, 40-73 tok/s
- rows=128: KV 1.97M, 67-75 tok/s
- rows=192: KV 1.39M, 85-89 tok/s, ~120 combined with two requests in flight (~60 each)

rows=192 is where we settled — 256 would need a bank the size of a whole GPU on this model. VRAM sits at ~31.4/32.5 GiB per card, GPU util 90-100% under load, zero errors across restarts, and the one-time "no native FP4" Marlin warning shows on load as expected on SM120.

FWIW we don't miss MTP at all; the pool more than makes up for it at our scale.


- wyj-IIRtyj · comment · 2026-10-22T02:37:33Z · [source](https://github.com/vllm-project/vllm/pull/56177#issuecomment-6331331247)

Thanks for the pool. We serve `nvidia/GLM-5.3-Flash-NVFP4` with it at 1M context on 2x RTX PRO 6000 (TP=2, `--moe-expert-pool-rows 193`). Running it surfaced three follow-ups, which I opened against your branch as 01554/vllm#51. They are independent commits, so take any subset:

1. **MTP**: the BF16 MTP head no longer trips the layer guard; it stays on the GPU. Decode lanes are also sized for `1 + num_speculative_tokens`. With MTP 3 we see 61% acceptance and 105-114 tok/s single stream.
2. **A guard for Marlin's 32 GiB weight-index limit**: Marlin MoE indexes B with `int b_gl_rd` in 16-byte units, so bank weight tensors above 32 GiB read out of bounds. Here `--moe-expert-pool-rows 240` hit an illegal memory access in `profile_run`. The guard now fails at installation and reports the largest row count that fits.
3. **Prefill staging**: this answers the "dominant term of long-input prefill not profiled" note in the docs. Marlin re-reads each host-view expert once per M-block (~5x PCIe traffic per step). Staging the non-resident rows by DMA, one layer ahead of the compute, cut TTFT at 81.6K tokens from 67.6 s to 13.0 s, and at 12.5K from 9.6 s to 1.8 s, with decode unchanged. I saw that DMA and prefetch lost in your lab (01554/vllm#39, #40). Here they win, probably because whole non-resident runs are copied and the 4608-token Marlin steps hide the copy. The PR has the same-step comparison.

Measurements and tradeoffs are in the PR description. (Prepared with AI assistance; I reviewed and tested it.)
