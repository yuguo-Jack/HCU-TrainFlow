# [Perf][DSv4.1] Size the long-context prefill workspaces by what a chunk can use

[Upstream PR](https://github.com/vllm-project/vllm/pull/60874) · state: open · merged: False

## Original PR description

## Overview

At DeepSeek-V4.1's 1M `max_model_len` on SM90, the indexer K-gather and FlashMLA prefill-gather reservations share a 4.03 GiB workspace per GPU. That workspace is sized for chunks the indexer never forms and FlashMLA rarely forms. This PR sizes both reservations by what one prefill chunk can actually gather, which returns 2.57 GiB per GPU to the KV cache. #55222 fixed the GLM-5.3 counterpart by dividing by the pool ratio; that does not help here, because most DeepSeek-V4.1 index layers have compress ratio 1.

## Claims

- On 8×H20 at TP8 and 1M, available KV cache rises from 19.91 to 22.50 GiB per GPU (+13.0%).
- At the default logits budget, indexer chunking is unchanged outside PCP+DCP, and nothing changes below a `max_model_len` of about 84K. Other models and ROCm's MXFP4 indexer keep their reservations.
- FlashMLA splits a step once its prefills, padded to the widest, gather more than one full-length request (at 1M, a prefill over about 520K plus any other); each request is still computed whole within one chunk.

## Validation

```bash
pytest tests/v1/attention/test_sparse_mla_backends.py -k "split_prefill_chunks or split_indexer_prefill_chunks"
```

The new test runs the real splitter on the densest packing at 128K and 1M, dense and with SM100's fused MQA+top-k. No chunk exceeds the new reservation, and the split is the same as under the generic budget.

## Details

- **Indexer.**
  - `_split_indexer_prefill_chunks` packs dense chunks only while `query_rows * keys <= max_logits_elems`. Each request brings at least one row and at most `max_len` keys, so a chunk has `keys**2 <= max_logits_elems * max_len`. Chunks for SM100's fused MQA+top-k skip that budget but stop at 2^20 keys. At the default budget the reservation only shrinks where it stays above 3.3M rows, so those chunks are unchanged too.
  - The reservation is now `get_prefill_buffer_size()` on the indexer metadata builder. Both DeepSeek-V4.1 builders, dense and sparse-logits, return `max(max_len, isqrt(max_logits_elems * max_len))`, capped at the generic budget. At 1M that is 11.9M rows instead of 16.8M.
  - The splitter uses it as its workspace bound, and the layer sizes its K-gather buffer from the same call, so a multi-request chunk cannot exceed the buffer. A single request skips that bound; at the default budget the reservation is at least `max_model_len` rows, which covers it on both split paths.
  - PCP+DCP counts uncompressed DCP shard rows, so its compressed layers can take more chunks there (not at 1M). V4.1's default two-level candidate filtering does not run with DCP.
- **FlashMLA.** The prefill chunk area now holds as many full-length requests as fit in 2^20 bf16 rows (1 GiB), and at least one. That is one at 1M, three at 256K, and four (unchanged) below about 250K. Warmup and the runtime planner use the same value.
- **Scope.**
  - The FlashMLA part applies wherever FlashMLA runs: SM90's default, and Blackwell with PCP, an explicit FlashMLA backend, or where mega attention is unavailable.
  - Blackwell's default mega attention keeps its own prefill reservation, which still sets the workspace size at 1M, so it saves nothing there. With the recipe's FlashInfer and MXFP4-indexer setup, the indexer part saves an estimated 1.06 → 0.75 GiB.
  - ROCm's MXFP4 indexer reads the paged cache directly and keeps its reservation.
  - ROCm's FP8 (AITER) indexer for DeepSeek-V4.1 uses the same builder, so it also gets the smaller reservation. It gathers one builder chunk at a time, so every chunk fits.
- **Duplicates.** No open PR changes these reservations for DeepSeek-V4.1.

- zyongye · comment · 2026-10-27T17:21:57Z · [source](https://github.com/vllm-project/vllm/pull/60874#issuecomment-6448687679)

Two notes after reading through this:

**1. The memory numbers predate #61023**, which your Oct 13 merge picked up. It defaults `sparse_mla_prefill_workspace_factor` to 2 above 256K, so at 1M main's indexer reservation is already 16.8M rows (2.06 GiB fp8), and FlashMLA's 4 × full-width area (4.03 GiB) is now the larger one. The expected gain on SM90 is then ~4.03 → 1.46 GiB (~2.6 GiB) rather than 3.70, and ~1.06 → 0.75 GiB for the Blackwell MXFP4 indexer. Worth re-measuring.

**2. The builder-subclass idea checks out**, with two caveats:
- Both split paths (normal and PCP+DCP) pass `self.max_prefill_buffer_size` as `workspace_size`, so setting it to `_indexer_prefill_buffer_size(...)` bounds multi-request chunks by the `new_n <= workspace_size` check. Chunking is unchanged: replaying the splitter on ~3k random batches plus the 256 × 1M case (1M at factor 2 and 5, 128K, 512K) gave no differences, and the largest chunk was 11.53M ≤ 11.86M.
- Single-request chunks skip that check (`end == start`); the `max(L, …)` term is what covers them.
- `DeepseekV41SparseIndexerMetadataBuilder` subclasses `DeepseekV32IndexerMetadataBuilder` directly, and `SparseMQAIndexer` gathers into the same buffer, so it needs the same change. ROCm MXFP4 is unaffected either way: its splitter ignores `workspace_size` and its ops don't read `max_total_seq_len`.

As it stands, an overflow wouldn't be caught: `k_quant_full[: chunk.max_local_total_seq_lens]` clamps silently. A size hook on the base builder that both V4.1 builders override, and that the layer reuses, seems worth the two extra files.
