# [Perf][DSv4.1] Size the long-context prefill workspaces by what a chunk can use

[Upstream PR](https://github.com/vllm-project/vllm/pull/60874) · state: open · merged: False

## Original PR description



## Overview

At DeepSeek-V4.1's 1M `max_model_len` on SM90, the indexer K-gather and FlashMLA prefill-gather reservations share a 5.16 GiB workspace per GPU. That workspace is sized for chunks the indexer never forms and FlashMLA rarely forms. This PR sizes both reservations by what one prefill chunk can actually gather, which returns 3.70 GiB per GPU to the KV cache. #55222 fixed the GLM-5.3 counterpart by dividing by the pool ratio; that does not help here, because most DeepSeek-V4.1 index layers have compress ratio 1.

## Claims

- On 8×H20 at TP8 and 1M, available KV cache rises from 19.69 to 23.39 GiB per GPU (+18.8%).
- Indexer chunking is unchanged. FlashMLA splits a step only when several very long prefills share it, and the outputs are bitwise identical.
- Nothing changes below a `max_model_len` of about 84K. Only `vllm/models/deepseek_v41/` changes.

## Validation

**Tests.** The new cases and the existing splitter tests pass:

```bash
pytest tests/v1/attention/test_indexer_deepseek_v4_slot_mapping.py -k dsv41_indexer_prefill_buffer
pytest tests/v1/attention/test_sparse_mla_backends.py -k split_indexer_prefill_chunks
```

The new test runs the real splitter on the densest packing at 128K and 1M. No chunk exceeds the new reservation, and three of the four cases fill it exactly.

**Serving.** 8×H20, TP8, 1M, DSpark k=5.
- Adaptive verification is off, because main cannot start with it at 1M on H20.
- These runs predate the rebase. The reservation formulas are unchanged.

| | main | this PR |
|---|---:|---:|
| Available KV cache per GPU | 19.69 GiB | 23.39 GiB |
| KV cache tokens | 9.24M | 10.97M |
| GSM8K (5-shot chat, greedy) | 96.97% | 96.66% |

- **Pass-key prompts of 120K to 900K tokens:** both arms return identical outputs, and TTFT differs by under 0.04 s.
- **16 sessions × 128K with prefix hits:** each turn's first step carries 10 to 12 long prefills and runs FlashMLA in 2 chunks instead of 1. Turn TTFT is 2.82 s against 2.81 s on main. That is within the 6% spread between the two main servers.
- **GSM8K:** three runs of main on this nightly scored between 96.4% and 97.0%.

**Cost of the extra chunks.** One layer's `_forward_prefill` on H20, timed with FlashInfer CUPTI and a cold L2.
- With 16 × 131K contexts in one step, ratio-1 layers go from 1 chunk to 3: 5,721 → 5,829 µs (+1.9%).
- Ratio-2 layers go from 1 chunk to 2: +0.5%.
- Over all layers that is an estimated 2.6 ms per step. The outputs are bitwise equal.

## Details

- **Indexer.**
  - `_split_indexer_prefill_chunks` packs requests only while `query_rows * keys <= max_logits_elems`. Each request brings at least one row and at most `max_len` keys, so a chunk has `keys**2 <= max_logits_elems * max_len`.
  - The indexer now reserves `max(max_len, isqrt(max_logits_elems * max_len))` rows, capped at the builder's budget. At 1M that is 11.9M rows instead of 41.9M.
  - A DeepSeek-V4.1 builder subclass with this budget would enforce the bound structurally. I kept the change in the model directory instead.
- **FlashMLA.** The prefill chunk area now holds as many full-length requests as fit in 2^20 bf16 rows (1 GiB), and at least one. That is one at 1M, three at 256K, and four (unchanged) below about 250K. Warmup and the runtime planner use the same value.
- **Scope.**
  - The FlashMLA part is SM90's default path.
  - On Blackwell only the indexer part applies. With the recipe's FlashInfer and MXFP4-indexer setup, that is an estimated 2.66 → 0.75 GiB.
  - ROCm is unaffected.
- **Duplicates.** No open PR changes these reservations for DeepSeek-V4.1.
