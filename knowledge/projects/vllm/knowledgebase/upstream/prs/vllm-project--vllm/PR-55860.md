# [ROCm][Perf] Use aiter's tuned decode GEMM for small-M decode under CUDA graphs

[Upstream PR](https://github.com/vllm-project/vllm/pull/55860) · state: open · merged: False

## Original PR description

**AI assistance:** this PR was written with Claude (Anthropic): the code, the tests, the benchmark script and this description. A human (the author) reviewed every change and ran every measurement below. All commits in this PR were AI-assisted.

## Purpose

On ROCm, the skinny-GEMM branch in `rocm_unquantized_gemm_impl` returns early for small-token shapes (`0 < n <= 5`). So `tgemm.mm` further down is unreachable, and aiter's tuned A16W16 config is never consulted, even for shapes where aiter has a tuned decode kernel that is faster than `wvSplitK`.

This adds one branch before the skinny branch. It defers to aiter only when three things hold:

1. a CUDA graph is being captured;
2. the weight and bias are contiguous;
3. aiter's tuned config names a decode kernel for this exact shape.

The branch passes the activation as a 2-D view. A view with a row stride larger than K, such as a column slice of a fused projection output, goes to aiter without a copy. Only an activation whose K elements are not adjacent (e.g. a transposed one) is made contiguous first.

**Which shapes switch.** aiter's tuned rows are keyed by `(gfx, cu_num, M, N, K, bias, dtype, ...)`, not by model. So **every model** that runs a matching shape on the same card switches kernels, not only Kimi-K3. Some of these shapes (for example 2112×7168) also occur in other models; DeepSeek-V3's large GEMMs are FP8 and do not reach this path. The decision is made in aiter, through `aiter.tuned_gemm.is_flydsl_decode_config`; vLLM does not match on labels or keep a shape table.

**How the rows were chosen.** aiter's tuner cannot select `wvSplitK`, so an aiter row does not by itself mean "faster than `wvSplitK`". Every decode row was therefore compared with `wvSplitK` through this code path, under graph capture (level 1 below). Rows that lost were removed from ROCm/aiter#4114 (4 on gfx950, 4 on gfx942), together with 5 rows on the same shapes so that a re-tune reproduces the CSV. For those shapes vLLM keeps using `wvSplitK`. 76 decode rows remain on gfx950 and 82 on gfx942.

**Why capture-only.** aiter's dispatch costs about 20 µs of CPU per call, against about 10 µs for `wvSplitK`. Under graph capture that cost is paid once, and replay keeps only the faster kernel. In eager mode it would be paid on every call and outweigh the GPU gain on most decode shapes. So eager execution (`enforce_eager`, and batch sizes outside the captured set) keeps today's path. In eager mode the cost of this PR is one call to `torch.cuda.is_current_stream_capturing()` (0.15 µs, measured).

**Eager vs graph numerics.** For a shape with a decode row, eager decode now runs `wvSplitK` and graph replay runs the aiter decode kernel. Both use FP32 accumulation and a BF16 output. Their outputs are not bitwise identical: each is within 3.5e-3 relative error of an FP32 reference (level 1).

The helper is a no-op unless `VLLM_ROCM_USE_AITER` and `VLLM_ROCM_USE_AITER_LINEAR` are set. It returns False if aiter is not installed or is too old to have decode rows.

**Architectures.** Rows exist for gfx950 (MI355X, measured) and gfx942 with `cu_num=304` (measured on MI325X). The same key also covers MI300X; Kimi-K3 does not fit on 8× MI300X (192 GB each), so the end-to-end runs use MI325X.

**Dependency.** This needs ROCm/aiter#4114 at `059108489` or later, which is still open (earlier revisions reject a strided activation). After it merges, this PR also needs an aiter release and an `AITER_BRANCH` bump in `docker/Dockerfile.rocm_base` (currently `v0.1.24.post1`). Until then, `get_GEMM_A16W16_config` reports no decode rows, and this branch is never taken.

## Why this is not a duplicate

Open PRs were searched for the same function and the same idea:

- #55090 (weight row-stride padding for L2 cache) edits the same function and test file, but for **gfx11 only**, and for a different purpose. It removes `skinny_operands_compatible`, which this PR now uses, so whichever PR merges second will need a rebase.
- #41883 (port W16A16 linear kernels to the kernel abstraction) is a draft refactor of the same code; it is not a feature overlap.
- #56234 (use AITER FP8 blockscale when the shape is tuned) applies the same idea to the FP8 blockscale path, in different code.
- #50535 (AITER tuned GEMM for the MoE router gate) uses aiter's BF16 GEMM only for the router gate, in different files.

No open PR routes small-M BF16 decode GEMMs to aiter's tuned decode kernels.

## Test Plan

Environment:
- **image:** `rocm/pytorch:rocm7.2.4_ubuntu24.04_py3.12_pytorch_release_2.10.0+rocm7.2.4`
- **aiter:** ROCm/aiter#4114 at `ce8ce2c13` (kernel A/B); `2fde81733` (end to end). The current revision `32f426db9` produces the same machine code for every decode kernel.
- **FlyDSL:** 0.3.4.1, as pinned by aiter
- **GPU:** MI355X (gfx950, 256 CU), one card

Unit tests (new tests cover the aiter branch under capture, with a strided activation, and the eager fallback):
```bash
pytest tests/model_executor/layers/test_rocm_unquantized_gemm.py -v
```

Kernel A/B (level 1): every decode shape on this GPU, with the aiter branch on vs off, under graph replay:
```bash
VLLM_ROCM_USE_AITER=1 VLLM_ROCM_USE_AITER_LINEAR=1 \
    python benchmarks/kernels/benchmark_rocm_aiter_decode_gemm.py --rounds 5 --pairs 10
```
Side B replaces `rocm_aiter_ops.has_tuned_decode_gemm` with a function that returns False. This disables exactly this branch and leaves the rest of the dispatch chain intact. The script:
- uses four rotating weights and alternating A/B pairs;
- times side B against itself as a null control and drops pairs whose null gap exceeds 2%;
- records, per cell, which kernel ran on each side.

End to end (8 GPUs): Kimi-K3, TP8, on one 8× MI355X node, with this PR's diff applied (on) and reverted (off) in the same container:
- image `rocm/vllm-dev:nightly-aiter-bcb56d9-vllm-ac68c308` (vLLM `0.30.1rc1.dev396+gac68c3087`), aiter ROCm/aiter#4114 at `2fde81733`, FlyDSL 0.3.4.1;
- server: `VLLM_ROCM_USE_AITER=1 VLLM_ROCM_USE_AITER_LINEAR=1 vllm serve <Kimi-K3> --tensor-parallel-size 8 --trust-remote-code`;
- accuracy: `lm_eval --model local-completions --tasks gsm8k --num_fewshot 5` (all 1319 questions, strict match);
- serving: `vllm bench serve --dataset-name random --random-input-len 1024 --random-output-len 512 --max-concurrency {1,4,16}`;
- 8 rounds, off and on alternating order each round so machine drift does not favour one side; every side restarts the server, then runs GSM8K and the three serving points;
- `AITER_LOG_TUNED_CONFIG=1` logs which tuned row aiter picks, which shows whether the decode kernel ran.

### 3. Correctness: the new branch drops the contiguity guard

The skinny branch is gated on `skinny_operands_compatible` and passes `x.reshape(-1, x.size(-1)).contiguous()`, and existing tests (`test_rocm_unquantized_gemm_makes_skinny_activation_contiguous`) show non-contiguous activations reach this op. The new branch passes `x` and `bias` straight to `tgemm.mm`. aiter's `gemm_a16w16` doesn't make them contiguous, and `validate_gemm_decode_tensors` in ROCm/aiter#4114 raises `ValueError` on non-packed A/B or a non-contiguous bias. A sliced activation will crash graph capture instead of falling back. The `try/except` only covers the config lookup, not the launch.

```python
if (
    torch.cuda.is_current_stream_capturing()
    and skinny_operands_compatible
    and use_aiter_decode_gemm(n, m, k, x.dtype, bias)
):
    from aiter.tuned_gemm import tgemm

    x_view = x.reshape(-1, x.size(-1)).contiguous()
    out = tgemm.mm(x_view, weight, bias)
    return out.reshape(*x.shape[:-1], weight.shape[0])
```

### 4. No tests

This adds a dispatch branch and a helper, and changes no tests. `tests/model_executor/layers/test_rocm_unquantized_gemm.py` already mocks every branch of this function. Add:
- capture `True` + helper `True` → `tgemm.mm` called, `wvSplitK` not called
- capture `False` → `wvSplitK` still called
- helper returns `False` when `is_linear_enabled()` is `False` or the aiter import fails
- non-contiguous activation under capture → contiguous 2-D view reaches `tgemm.mm`
