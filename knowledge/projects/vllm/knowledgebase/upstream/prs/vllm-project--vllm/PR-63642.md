# [Perf][Kernel] Reduce shared-memory staging for per-tensor FP8 KV dequantization

[Upstream PR](https://github.com/vllm-project/vllm/pull/63642) · state: open · merged: False

## Original PR description

## Overview

For BF16/FP16 queries with per-tensor FP8 KV, the current dequantization code can cause Triton to store dequantized K/V tiles in shared memory and reload them for matrix multiplication. This PR loads each dequantization scale as a one-element tensor and broadcasts it to the tile shape, allowing Triton to eliminate these intermediate shared-memory buffers while preserving the original order of scaling and casting. On SM90, this PR also uses two pipeline stages for selected large-head 2D configurations.

## Claims

- **H20, Gemma 4 26B-A4B, FP8 KV:** for single requests containing approximately 8k or 32k text tokens followed by a screenshot, this PR reduces TTFT from **708.5 ms to 660.6 ms (7.08% lower)** and from **3914.5 ms to 3366.0 ms (14.01% lower)**, respectively.
- **H20 kernel benchmark:** across 37 tested 2D prefill and decode configurations, this PR reduces attention execution time by **23.9%**, measured as the geometric mean of paired PR/original execution-time ratios.

## Validation

On H20, all 96 cases in the FP8 KV regression test and all 72 cases in a separate numerical check passed. In the numerical check, all 72 outputs were bitwise identical to those from the unmodified kernel. Model and kernel performance were each measured over six paired rounds. Test configurations, timing methods and paired results are provided below.

## Details

### 1. Extra shared-memory buffers in the generated code

The TTGIR excerpts in Sections 1–3 compare the original and rewritten kernels for a causal prefill configuration on H20 with Triton 3.8: BF16 queries, FP8 KV, KV-cache block size 64, query length 15931, KV length 32315, head size 512, 16 query heads and 2 KV heads. Both kernels use four warps and three pipeline stages.

The original kernel loads FP8 K/V tiles from shared memory into registers, converts them to FP32, multiplies them by the dequantization scales and casts them to BF16. The resulting BF16 tiles use a blocked layout, which differs from the layout required by the matrix multiplication. To convert between these layouts, the generated code writes each BF16 tile to an intermediate shared-memory buffer and reloads it in the dot-operand layout. The following TTGIR excerpt shows this sequence for K:

```mlir
%K_228 = tt.fp_to_fp %K_load_226
    : tensor<512x32xf8E4M3FN, #blocked1>
   -> tensor<512x32xf32, #blocked1>
%K_229 = arith.mulf %K_228, %K_123
    : tensor<512x32xf32, #blocked1>
%K_230 = arith.truncf %K_229
    : tensor<512x32xf32, #blocked1>
   to tensor<512x32xbf16, #blocked1>
%K_231 = ttg.local_alloc %K_230
    : (tensor<512x32xbf16, #blocked1>)
   -> !ttg.memdesc<512x32xbf16, #shared4, #smem>
%K_240 = ttg.local_load %K_231
    : !ttg.memdesc<512x32xbf16, #shared4, #smem>
   -> tensor<512x32xbf16, #dot>
```

Source locations are omitted, and `#dot` is shorthand for the `#ttg.dot_op` attribute. `#blocked1` and `#dot` describe how tensor elements are distributed across threads and registers; `#smem` denotes shared memory. The `ttg.local_alloc` operation writes the BF16 K tile to shared memory, and `ttg.local_load` reloads it in the layout required by `tt.dot`. V follows the same pattern.

These intermediate buffers hold the dequantized BF16 K/V tiles and are separate from the existing FP8 input buffers. After dequantization, each tile is therefore written from registers to shared memory and then read back into registers.

### 2. Why Triton does not eliminate these buffers

The original dequantization code loads the scale as a scalar:

```python
return (data.to(tl.float32) * tl.load(tensor_scale)).to(Q.dtype)
```

To multiply the tile by this scalar, Triton expands the scale to the tile shape using `tt.splat`:

```mlir
%K = tt.load %k_scale, %acc : !tt.ptr<f32>
%K_123 = tt.splat %K
    : f32 -> tensor<512x32xf32, #blocked1>
```

Triton's layout-conversion pass attempts to move the conversion to the dot-operand layout before dequantization, so that FP8 K/V tiles can be loaded from shared memory directly into registers in that layout and dequantized there. This would avoid writing the resulting BF16 tiles to intermediate shared-memory buffers and reloading them for matrix multiplication. However, the pass cannot move the layout conversion past the scalar `tt.splat` shown above. The compiler debug log reports:

```text
Leaves must be Load, descriptor load-like ops, or Constant.
Got ... tt.splat ... : f32 -> tensor<512x32xf32, ...>
```

In Triton 3.8, [`LayoutRematerialization::hoistConvertDotOperand`](https://github.com/triton-lang/triton/blob/v3.8.0/lib/Dialect/TritonGPU/Transforms/RemoveLayoutConversions.cpp#L1237) traces the operations that produce the values used by dequantization to determine whether the layout conversion can be moved earlier. It can traverse pure elementwise operations, including multiplication, as well as supported broadcasts and views. However, the scalar `tt.splat` above is not covered by these rules, so the pass leaves the layout conversion after dequantization, retaining the intermediate BF16 shared-memory buffers.

>The same extra buffers were also observed with Triton 3.7.1 on SM89; the compiler diagnostics and source-code analysis described here were performed with Triton 3.8.

### 3. Load the scale as a one-element tensor

This PR loads the dequantization scale as a one-element tensor, reshapes it to `(1, 1)` and broadcasts it to the K/V tile shape:

```python
scale_1d = tl.load(tensor_scale + tl.arange(0, 1))
scale_tile = tl.broadcast_to(scale_1d.reshape((1, 1)), data.shape)
return (data.to(tl.float32) * scale_tile).to(Q.dtype)
```

`tl.arange(0, 1)` contains only index zero, so the load reads the same dequantization scale from the same address as before. The scale remains a runtime value, and no array of per-element scales is added. Loading it as a one-element tensor produces a load/reshape/broadcast sequence instead of the scalar `tt.splat` shown above. The layout-conversion pass can traverse this sequence and move the layout conversion before dequantization.

The compiler debug log reports that the K/V layout conversions have been moved before dequantization. The resulting TTGIR shows FP8 K/V tiles being loaded from shared memory directly into registers in the dot-operand layout, followed by the FP32 conversion, scaling and BF16 cast in the same layout. For K:

```mlir
%K = ttg.local_load %K_load_171 token %K_load_220
    : !ttg.memdesc<512x32xf8E4M3FN, #shared2, #smem, mutable>
   -> tensor<512x32xf8E4M3FN, #dot>
%K_221 = tt.fp_to_fp %K
    : tensor<512x32xf8E4M3FN, #dot>
   -> tensor<512x32xf32, #dot>
%K_222 = arith.mulf %K_221, %scale_tile_115
    : tensor<512x32xf32, #dot>
%K_223 = arith.truncf %K_222
    : tensor<512x32xf32, #dot>
   to tensor<512x32xbf16, #dot>
```

`%K_223` is passed directly to `tt.dot`, without an intermediate BF16 shared-memory write and reload. V follows the same pattern. The existing FP8 input buffers remain, while the two intermediate BF16 K/V buffers are eliminated.

| Implementation | Shared memory per thread block| Static `ttg.local_alloc` count |
|---|---:|---:|
| Original kernel | 114,944 B | 8 |
| One-element scale load + broadcast | 50,432 B | 6 |

We compared the original and rewritten kernels across 37 configurations with both two and three pipeline stages. The matrix covers KV-cache block sizes 16 and 64, head-size-512 prefill and decode, and additional prefill configurations with head sizes 128 and 256. Both implementations use four warps; comparisons below hold the stage count fixed.

With three stages, the rewrite reduces execution time in 31 configurations and increases it in six; all six regressions are page-size-16, head-size-512 2D decode cases with 8 query heads and 2 KV heads. With both implementations using two stages, all 37 paired confidence intervals lie below 1.

### 4. Adjust pipeline depth for large-head 2D kernels

The rewrite removes the BF16 shared-memory buffers, but can increase register pressure. We compared two and three pipeline stages to balance this cost against overlap between memory loads and computation: fewer stages may keep fewer values live at once, but also reduce that overlap.

For a synthetic causal prefill case matching the observed Gemma dimensions—query length 15931, KV length 32315, head size 512, 16 query heads, 2 KV heads and KV-cache block size 64—the results are:

| Implementation | Pipeline stages | Execution time (ms) | Registers per thread | Stack size (B) |
|---|---:|---:|---:|---:|
| Original kernel | 3 | 358.848 | 246 | 0 |
| Rewritten kernel | 3 | 288.683 | 255 | 32 |
| Original kernel | 2 | 333.413 | 242 | 0 |
| Rewritten kernel | 2 | 248.965 | 255 | 16 |

Two stages reduce execution time by 13.75% within the rewritten kernel and by 7.22% within the original kernel. The rewrite still reduces execution time by 25.32% when both use two stages. Two stages reduce, but do not eliminate, spill-related stack usage in this example.

The page-size-16 decode group that regresses with three stages also improves with two stages. Page size matters: the corresponding page-size-64 decode group already benefits from the rewrite at three stages. Lower shared-memory usage alone therefore does not determine the best pipeline depth.

The wrapper sets `num_stages=2` for SM90-family 2D kernels with per-tensor FP8 KV, non-FP8 queries and head size ≥512, unless a stage count has already been selected. This setting was evaluated at head size 512. Reported PR performance includes both changes.
