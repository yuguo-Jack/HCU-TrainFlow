# [Bugfix] Fix FP8 NaN from per-call unit scales in ChannelWiseTorchFP8ScaledMMLinearKernel

[Upstream PR](https://github.com/vllm-project/vllm/pull/61890) · state: open · merged: False

## Original PR description



## Overview

`ChannelWiseTorchFP8ScaledMMLinearKernel` passes a fresh `torch.ones(1)` to `torch._scaled_mm` as `scale_a`/`scale_b`
on every call. On GB10 (sm_121), when the MoE shared experts run this kernel on the aux stream while the routed experts
run, the GEMM occasionally computes with a stale scale. The shared-expert output becomes non-finite in every row, and
every request in the step returns NaN logits. This PR allocates the unit scale once per layer, as a non-persistent
buffer, and reuses it.

The failure matches cuBLAS CUB-10409: GEMMs on sm10x/sm12x may read device scale pointers before
`cudaGridDependencySynchronize()` (introduced in 13.1.0, fixed in 13.6.1,
[patch notes](https://docs.nvidia.com/cuda/cublas-patch-release-notes)). Swapping in cuBLAS 13.6.1 alone removes the
NaN, but every current PyTorch release, including the 2.14 that vLLM pins, ships cuBLAS 13.1.1.

This is not a duplicate. #57017 is a different bug (CUDA-graph padding in the MoE, addressed by #61708), and #57094
does not fix this one (34/111 NaN requests on v0.19 with it). No other issue or PR reports this bug or touches the unit
scale.

## Claims

- Fixes batch-wide NaN logits with online FP8 on GB10 when the dense FP8 linears use `torch._scaled_mm`. GSM8K on
  main: 0.712 with 212 of 1319 requests NaN before, 0.829 with none after. The CUTLASS reference is 0.842.
- The GEMM math is unchanged; each call loses one allocation and one fill kernel. Weight reloads and level-2 sleep
  keep the scale.

## Validation

GLM-4.7-Flash (MLA, 64 routed experts with top-4, 1 shared expert), BF16 checkpoint with online FP8, one GB10, main
`2308b6f00`, torch 2.13.0+cu130 with cuBLAS 13.1.1.3 unless noted. One run per arm, fresh server each; the CUTLASS
arm drops `VLLM_DISABLED_KERNELS`.

```bash
VLLM_DISABLED_KERNELS=CutlassFP8ScaledMMLinearKernel VLLM_COMPUTE_NANS_IN_LOGITS=1 \
vllm serve zai-org/GLM-4.7-Flash --dtype bfloat16 --quantization fp8_per_tensor --max-model-len 12288 \
  --enable-prefix-caching --max-num-seqs 32 --max-num-batched-tokens 16384 --gpu-memory-utilization 0.70 --seed 0
python tests/evals/gsm8k/gsm8k_eval.py --port 8000 --request-timeout-seconds 3600
```

| Dense FP8 GEMM | GSM8K | Requests with NaN logits |
|---|---|---|
| CUTLASS (default) | 0.842 | 0 / 1319 |
| `torch._scaled_mm`, unpatched | 0.712 | 212 / 1319 |
| `torch._scaled_mm` + this PR | 0.829 | 0 / 1319 |
| `torch._scaled_mm`, unpatched, cuBLAS 13.6.1.10 | 0.841 | 0 / 1319 |

The NaN also reproduces on v0.19 and v0.31.0 under a synthetic concurrent load. Per-layer probes put the first
non-finite tensor in the shared-expert output, and the NaN goes away with `VLLM_DISABLE_SHARED_EXPERTS_STREAM=1`.
Level-2 sleep followed by `reload_weights` (the `test_deep_sleep` sequence, Qwen3-8B on this kernel) behaves as it does
without the change. Keeping the scale on the kernel object instead broke that sequence, which is why the scale is a
layer buffer.

```bash
pytest -q tests/model_executor/kernels/test_torch_scaled_mm_linear.py
pytest -q tests/compile/passes/test_fusion.py -k "test_fusion_rmsnorm_quant and kernel_groupshape4"  # needs Hub access
```

The new test checks that `torch._scaled_mm` gets the same unit-scale tensor across calls and across a repeated
`process_weights_after_loading`, as a weight reload does. On GB10 it fails without this change and passes with it. The
`test_fusion` cases build this kernel: 16 passed on GB10.

## Details

`process_weights_after_loading` now registers the unit scale as a non-persistent buffer on the layer and reuses it when
it already exists on the weight's device. Weight reloads therefore keep the tensor that captured CUDA graphs read, and
level-2 sleep restores it with the other buffers. `apply_scaled_mm` falls back to a per-call allocation only if that
method was not called or the devices differ, as on the IPC weight-cache path. Before #27814 a single persistent
identity tensor (`TORCH_DEVICE_IDENTITY`) served this role.

Affected setups: GB10 on v0.19–v0.21, where CUTLASS FP8 does not run on sm_121 yet (#35568, v0.22; v0.20 and v0.21
were not tested), and any version with CUTLASS FP8 disabled. sm10x falls under the same cuBLAS issue but was not tested.
Without this change, cuBLAS 13.6.1 or newer or `VLLM_DISABLE_SHARED_EXPERTS_STREAM=1` avoids the NaN.
`PerTensorTorchFP8ScaledMMLinearKernel` writes its dynamic activation scale right before the GEMM, the same pattern;
it is left unchanged here.

Thanks for testing on SM120. The PR only claims GB10 (sm_121), and the race shows up there much more often. On GB10 I replayed one GLM-4.7-Flash MoE layer at kernel level with real weights: the shared FP8 MLP ran on a second stream while the routed experts ran on the main stream, and 3e38 was left in the freed block before each `torch.ones(1)`.
