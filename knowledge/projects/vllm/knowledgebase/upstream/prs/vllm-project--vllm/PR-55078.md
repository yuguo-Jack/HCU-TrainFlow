# [Bugfix][Model] Use Triton attention for Inkling on SM8x

[Upstream PR](https://github.com/vllm-project/vllm/pull/55078) · state: open · merged: False

## Original PR description

Following @Isotr0py's suggestion, I replaced the SM8x FlexAttention path with
Inkling's existing ROCm Triton relative-attention kernels. The portable kernels
now live under `inkling/common/ops/`, and SM8x selects `TritonAttentionBackend`
for metadata and KV-cache integration. AMD-specific Gluon dispatch and the
SM90+ FA4 path are unchanged.

Long-context CUDA decode continues to use the existing split-KV kernel,
including small-page local attention. `INKLING_SPLIT_KV` behavior is unchanged.

This is the same SM8x fix and is separate from #51560, #53317, and the
convolution-cache fix in #51951. It does not add SM12x support.

### Testing

Tested `33c25ab756` on top of `7ee8a6dd0` on September 14, using
Torch `2.13.0+cu130`.

- Pre-commit passed.
- The A100 attention suite passed **88 tests** with one Hopper-only skip.
  Regression coverage includes the selected Triton metadata builder and both
  packed-cache physical layouts.
- Nine additional operator cases passed comparisons against FlexAttention and
  an independent FP32 reference across prefill/decode, shuffled pages, local
  attention, FP16/BF16, GQA/MHA, and 128k context.
- A two-layer synthetic BF16 model matched all **24 greedy tokens**; maximum
  fixed-history logprob difference was `0.00803` against the unchanged `0.02` limit.
- Both backends passed **32 live attention/FP32 checks** each. Loaded parameter
  hashes and fixed-history schedules matched, cache geometry was verified,
  and both local/global candidate layers selected `TritonAttentionBackend`.

The model comparison used TP1 and eager execution with nonzero short
convolutions. Source hashes matched before and after validation.

### Earlier TP4 validation

The following production results are from `6ca6a72bdd`, before the
backend/metadata follow-up. **I have not rerun TP4 on `33c25ab756`.**

On **4× A100 80GB**, the W8A16 production checkpoint passed all ten semantic
smoke checks and an 8,200-token retrieval test under both backends, with
identical generated tokens.

The production checks used identical validation-only loader/Marlin compatibility
patches for both backends; those patches are not included here.

The additional TP4 fixed-history numerical comparison remains unresolved.
Triton vs. Flex exceeded the preset `0.1` logprob-difference limit. However,
repeated runs of the **same backend on identical inputs also showed differences
of similar or greater magnitude**, including after disabling overlap between
shared and routed experts.

That means I have not isolated a Triton-specific regression, but I also cannot
claim TP4 numerical parity from this test. Smoke and retrieval behavior remained
correct, and the runtime, tokenizer, parameter-sample fingerprints and schedules
matched. Source hashes matched before and after execution.

<details>
<summary>TP4 diagnostic details</summary>

The initial paired run reached a maximum absolute logprob difference of `1.38174`.

In the latest three-process TP4 run, shared/routed expert overlap was disabled
and confirmed on every rank. Maximum absolute logprob differences were:

- First Flex process, clean repeat 0 vs. 1: `1.56168`
- Second Flex process, clean repeat 0 vs. 1: `1.81250`
- Triton process, clean repeat 0 vs. 1: `1.125`
- Triton vs. first Flex process, initial probes: `1.19277`

In that cross-backend comparison, 541 of 852 shared logprobs differed by more
than `0.1`, with one top-logprob coverage failure.

All three processes passed smoke and retrieval checks. Runtime, tokenizer,
parameter-sample fingerprints and schedules matched. Source hashes matched
before and after execution. Serializing shared/routed expert work did not
resolve the repeatability issue.

- TheVerdman · comment · 2026-09-03T04:03:53Z · [source](https://github.com/vllm-project/vllm/pull/55078#issuecomment-5520162037)

@Isotr0py Mostly because FlexAttention already exposes the exact hook Inkling needs: its `score_mod` receives logical query/key positions after paged-KV translation, so the learned per-query, per-head relative bias can stay model-local. TritonAttention supports paged KV, but its existing bias paths (`alibi_slopes` and the lower-level `qq_bias`) cannot directly express that bias: `qq_bias` only covers keys in the current query block and is not per-head. Supporting Inkling there would therefore require extending or generalizing the Triton backend and kernel. I’m happy to switch if that’s the preferred direction; FlexAttention was the smallest existing path I could validate.
