# [ROCm][DI] Enable MoRI FP4 dispatch for mxfp4 w4a4 moe 

[Upstream PR](https://github.com/vllm-project/vllm/pull/59596) · state: closed · merged: True

## Original PR description



## Overview

Since #57074, MXFP4 W4A4 MoE models (e.g. [amd/Kimi-K2.6-MXFP4](https://huggingface.co/amd/Kimi-K2.6-MXFP4)) fail during engine startup when served with AITER MoE and --all2all-backend mori_high_throughput|mori_low_latency. This PR dispatches their activations through MoRI as packed FP4 with e8m0 block scales, which AITER's fused MoE consumes directly. It also adds an MXFP4 case to the MoRI EP numerics test.



## Claims


* Fixes the startup crash dynamic_per_group_scaled_quant_kernel not implemented for dtype fp8 for MXFP4 W4A4 MoE under MoRI, a regression from #57074.
* In the new mxfp4 case of tests/kernels/moe/test_mori_moe.py, two-rank MoRI FP4 dispatch matches AITER's non-EP MXFP4 MoE within the test's BF16 tolerances.
* Kimi-K2.6-MXFP4 at DP16/EP16 scores 0.936 on gsm8k, in line with earlier MoRI runs of the same checkpoint (0.927-0.936).

## Validation



### Unit test

* tests/kernels/moe/test_mori_moe.py gets an mxfp4 scheme alongside bf16 and fp8_token_channel. It runs over the same 7 shapes, and the m=32 shape also checks CUDA graph capture and replay. Both ranks sit on one node, so MoRI uses its IntraNode kernel.
* Result on 2x MI350X with the nightly 0.30.1rc1.dev493 image plus this PR: all 21 cases pass, 7 shapes each for BF16, FP8 and MXFP4. The file runs in 12.2 minutes, and the MXFP4 cases add 3.8 of them. Each case takes 31-35 s, mostly process startup. That fits the step's 20-minute timeout.


### E2E test with Kimi K2.6 with EP16/DP16

Model: Kimi-K2.6-MXFP4 (384 experts, top-8, hidden 7168). Hardware: 4x MI350X nodes, 8x gfx950 each.
Setup: PD-disaggregated 2P2D, where each prefill and decode instance is DP16/EP16 across two nodes.
Prefill uses mori_high_throughput 
Decode uses mori_low_latency

| Run | vLLM | MoRI dispatch | gsm8k strict / flexible |
|---|---|---|---|
| Before: main without this PR | nightly `0.30.1rc1.dev396` (+#56073) | FP8 per-tensor | prefill and decode crash in the profile run |
| **After: this PR** | nightly `0.30.1rc1.dev493` + this PR | **FP4 + e8m0** | **0.9356 / 0.9348** (±0.0068) |
| Reference, before #57074 | `0.26.1rc1.dev181`, DP8/EP8 | BF16 | 0.9363 / 0.9356 |
| Reference, before #57074 | `0.26.1rc1.dev942`, DP8/EP8 | BF16 | 0.9265 / 0.9257 |

Before:

```
[AITER] /app/aiter/aiter_meta/csrc/kernels/quant_kernels.cu:1514 dynamic_per_group_scaled_quant_kernel not implemented for dtype fp8
```

The "after" run overlaid this PR's three files on the nightly image. That image's `rocm_aiter_moe.py` predates #58819, but #58819's changes to that file only touch the W4A16 path.
