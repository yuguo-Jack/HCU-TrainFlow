# [Attention][KV Connector] FlashInfer: optional separate K/V head slots for unquantized KV

[Upstream PR](https://github.com/vllm-project/vllm/pull/62107) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Adds an opt-in `--attention-config.flashinfer_separate_kv_head_slots`. With it, FlashInfer stores an unquantized (fp16/bf16) KV cache with K and V as **separate head slots** (`num_head_slots = 2 * num_kv_heads`, content = `head_size`), instead of packing K|V in the content dim. This is the same split the NVFP4 KV cache already uses, and the same idea as ROCm attention and b12x.

Under LBHNC, each page becomes `[K heads (H, N, D) | V heads (H, N, D)]`. The NIXL worker registers the K half and the V half of each page as two regions that step by the full page. A remote engine that keeps K and V in **separate per-layer slabs** then maps onto it region for region, with no post-transfer permute and no extra copy.

## Claims

- New flag, off by default. Nothing changes when it is unset: the spec, layouts, kernels, NIXL regions, compat hash and the KV-update bypass are all as before.
- With the flag on, a single engine resolves a block-contiguous layout (LBHNC). Before the worker fix below, the engine core collected layouts outside any config context and resolved LBNHC.
- With the flag on, FlashInfer decode, prefill and mixed batches match the SDPA reference for bf16 and fp16 under LBHNC and BLHNC, including the KV write path.
- Llama-3.1-8B-Instruct, H100, `--enforce-eager`: the flag gives **bit-identical** logprobs (512/512 tokens over 8 prompts). With CUDA graphs and torch.compile, greedy text is identical (8/8) when both runs use the same KV layout. Against the default packed run, which resolves LBNHC instead of LBHNC, it is 7/8: the one difference is an exact top-2 tie (margin 0.0) that the compiled graphs break differently.
- Throughput is unchanged. Results are below.
- NIXL registers two half-page regions per layer, so a peer with separate K/V slabs (two dense regions per layer, same `block_len`) handshakes and pulls blocks. Heterogeneous TP still works per region, because each region keeps its heads contiguous.
- The NIXL compatibility hash includes the flag. Two vLLM engines that differ only in this flag therefore refuse to pair instead of exchanging pages with mismatched layouts.

## Details

**Why.** Since the KV-cache layout refactor (RFC #42082, #51718), unquantized FlashInfer and FlashAttention pack K|V into each token's content dim. That makes zero-copy NIXL KV exchange impossible with an engine whose attention keeps K and V in separate per-layer slabs, a common layout outside vLLM's CUDA backends. The RFC's model already allows separate K/V head slots, and NVFP4, ROCm and b12x use them. This exposes the same layout for unquantized FlashInfer, behind a flag.

**What changes:**
- `AttentionSpec.has_separate_kv_head_slots`: new property, true only for unquantized KV with `num_head_slots == 2 * num_kv_heads` and `head_size` content per slot. Both connectors use it, so the checks do not touch the other backends that publish `num_head_slots` (ROCm attention, ROCm AITER FA and b12x use `2`; NVFP4 is identified by its quant mode).
- `AttentionConfig.flashinfer_separate_kv_head_slots`: new flag, default `False`.
- `FlashInferBackend.customize_spec`: for unquantized KV with the flag on, returns the NVFP4-style spec (`num_head_slots=2H`, `state_content_bytes = head_size * dtype_size`). Page size is unchanged.
- `FlashInferBackend.supported_kv_cache_layouts`: restricted to `(LBHNC, BLHNC)` when the flag is on. Each K or V half of a page is contiguous only when `[H, N, C]` is contiguous in a block.
- `FlashInferImpl`: `forward` and `do_kv_cache_update` split the cache by head slot instead of by content. The impl detects the split from the cache shape: the last dim is `head_size` for split slots and `2 * head_size` for packed. It therefore always matches however the cache was allocated, with no extra config lookups on the hot path.
- `NixlConnectorWorker.register_kv_caches`: a split-slot attention page (detected from the spec and layout) is registered as two regions `(base, page/2, stride)` and `(base + page/2, page/2, stride)`.
- `compute_nixl_compatibility_hash`: includes the flag.
- `FlashInferBackend.supports_kv_cache_update_bypass`: `False` while the flag is on. Fused external KV writers (e.g. the Muse Spark QK-norm/RoPE/KV insert) write the packed `[B, H, N, 2*D]` page, so they fall back to the backend's own update. This depends on the setting, not on the model.
- `WorkerBase.get_supported_kv_cache_layouts`: evaluates the backends under the worker's config. The engine core calls it through a bare collective RPC, so a backend that narrows its layouts by config saw no current config, and a single engine with the flag resolved LBNHC.
- `gpu_model_runner.get_kv_cache_spec` (MRV1) and `gpu/attn_utils.get_kv_cache_spec` (MRV2): call `customize_attention_spec` under `set_current_vllm_config`, so a backend can read `attention_config` when packing its spec. Without this, `customize_spec` runs with no current config in the worker, and the impl's KV write would see a spec/cache mismatch.

**Scope and limits:**
- FlashInfer only. FlashAttention is not changed.
- Unquantized KV only. fp8 and NVFP4 keep their current paths.
- Only the NIXL connector is taught about the two-region split. Mooncake rejects head re-sharding for split-slot pages only, as it does for NVFP4; same-TP transfers move whole pages and are unaffected. ROCm attention, ROCm AITER FA and b12x layouts are unaffected. Other connectors are unchanged.
- Sliding-window / HMA specs go through the same `customize_spec`, but were only covered by the existing test suite, not by new tests.

**Line count.** About 150 added lines in `vllm/` (about 70 in `flashinfer.py`, 31 in `base_worker.py`, 5 in Mooncake, 5 in `worker_base.py`). Tests add about 540. Docs add 3 lines.

**CI coverage.** The new kernel test runs wherever `test_attention_backends.py` already runs FlashInfer. The NIXL and Mooncake tests are CPU-level unit tests in existing files and directories, so no new CI step is needed.
