# [Bugfix][Attention] Ignore KV cache dtype for encoder-only backend selection

[Upstream PR](https://github.com/vllm-project/vllm/pull/55482) · state: open · merged: False

## Original PR description

## Purpose

Fix embedding / encoder-only serving when a global `--kv-cache-dtype` is set (e.g. `bfloat16`).

`EncoderOnlyAttention` does not allocate a KV cache (`get_kv_cache_spec` returns `None`), but it still passed `cache_config.cache_dtype` into `get_attn_backend()`. CUDA backends then filter on that unused dtype and can raise:

```
ValueError: No valid attention backend found for cuda
```

instead of serving the embedding model (or failing with a clear config error).

This PR selects the encoder-only backend with `kv_cache_dtype="auto"`. `cache_config` is still forwarded to `Attention` for anything that actually needs it.

Fixes #55046

## Why this is not a duplicate

- Open PRs mentioning #55046: none.
- [#55150](https://github.com/vllm-project/vllm/pull/55150) rejects *quantized* KV cache for encoder-only models during `VllmConfig` validation. This change is backend *selection* for encoder-only layers when a global (including non-quantized) `cache_dtype` is set. It does not add or move quantized-KV validation.
- [#55159](https://github.com/vllm-project/vllm/pull/55159) / [#55160](https://github.com/vllm-project/vllm/pull/55160) are about prefix caching on encoder models, not backend selection.

- YeonwooSung · comment · 2026-09-05T21:28:32Z · [source](https://github.com/vllm-project/vllm/pull/55482#issuecomment-5554902993)

Checked the CodeRabbit linked-issue warning against #55046.

The repro is `Qwen3-Embedding` with `--kv-cache-dtype bfloat16 --mamba-cache-dtype float16 --mamba-ssm-cache-dtype float32`. That model is encoder-only: `EncoderOnlyAttention.get_kv_cache_spec()` returns `None`, and the Mamba cache dtypes are unused on this path. The failure was `ValueError: No valid attention backend found for cuda` because the unused global KV cache dtype was fed into `get_attn_backend()`.

The issue's "preflight compatibility error" wording is the symptom they wanted instead of that backend-selection crash. After tracing the code, the combo is not actually incompatible for an encoder-only embedding server — the selector was applying a cache dtype that this layer never stores.

This PR therefore keeps the narrow fix: select the encoder-only backend with `kv_cache_dtype="auto"`. Adding a preflight that rejects this combo would make the reported command fail again, and it would overlap #55150 (quantized-KV validation for encoder-only). Mamba cache-dtype validation belongs with models that allocate those caches, not with encoder-only backend selection.

The docstring-coverage warning is on existing functions this diff only calls; not adding unrelated docstrings.
