# [Bugfix] Whisper prompt conditioning: use the real `<|startofprev|>` token

[Upstream PR](https://github.com/vllm-project/vllm/pull/53207) · state: open · merged: False

## Original PR description

## Purpose

FIX #53206

`WhisperForConditionalGeneration.get_generation_prompt()` builds the request-prompt prefix with `<|prev|>`, which is not in the Whisper vocabulary — the tokenizer splits it into six ordinary text tokens (`'<', '|', 'pre', 'v', '|', '>'`) placed before `<|startoftranscript|>`, corrupting decoder conditioning. Any request carrying the OpenAI `prompt` field degenerates into repetition loops; on multi-chunk (>30 s) audio the transcription collapses to the final chunk's output only, because the degenerate chunks fail `verbose_json` timestamp parsing and are silently dropped.

This PR replaces it with `<|startofprev|>`, the actual prompt-conditioning special token, updates the example docs that referenced the wrong token, and adds a tokenizer-backed regression test.

`<|startofprev|>` is defined in `added_tokens_decoder` of every official OpenAI checkpoint, while `<|prev|>` appears in none of them: [whisper-large-v3-turbo](https://huggingface.co/openai/whisper-large-v3-turbo/blob/main/tokenizer_config.json) (id 50362), [whisper-large-v3](https://huggingface.co/openai/whisper-large-v3/blob/main/tokenizer_config.json) (id 50362), [whisper-small](https://huggingface.co/openai/whisper-small/blob/main/tokenizer_config.json) (id 50361), [whisper-large-v2](https://huggingface.co/openai/whisper-large-v2/blob/main/tokenizer_config.json) (id 50361). The reference implementation likewise defines only `<|startofprev|>` ([openai/whisper `tokenizer.py`](https://github.com/openai/whisper/blob/main/whisper/tokenizer.py), specials list + `sot_prev`).

Also explains #35276 (same symptom, closed as stale) and unblocks the standard-prompt half of #34518.

This is a small Whisper bugfix (similar in scope to #57769): `get_generation_prompt` prefixes the prompt with `<|prev|>`, which isn't in the Whisper vocab (it tokenizes into 6 ordinary text tokens), instead of the real special token `<|startofprev|>`. - Perlover · comment · 2026-10-16T17:49:24Z · [source](https://github.com/vllm-project/vllm/pull/53207#issuecomment-6221403091)

Independent confirmation of #53206 on **v0.27.1**, and one more piece that the `<|prev|>` → `<|startofprev|>` rename alone does not cover: vLLM still prepends `<|startoftranscript|>` **in front of** `<|startofprev|>`, and on some windows that makes the decoder give up on the rest of the 30 s window — silently, HTTP 200.

**Setup:** `openai/whisper-large-v3-turbo`, official `vllm/vllm-openai:v0.27.1` image + `vllm[audio]`, `POST /v1/audio/transcriptions`, default sampling (temperature 0; every result below repeats bit-for-bit), one NVIDIA RTX PRO 4000 Blackwell. Our image also carries one unrelated local patch (`speech_to_text/base/serving.py`: re-decodes a chunk tail that the decoder abandoned, `verbose_json` only); all three columns below ran on that same image, so the comparison isolates the prompt changes. Prompt: `Hello. Yes, of course, I remember. Shall we meet tomorrow, on Wednesday? Okay, see you then.`

### Repro with vLLM's own test asset

```bash
curl -sLO https://vllm-public-assets.s3.us-west-2.amazonaws.com/multimodal_asset/mary_had_lamb.ogg
ffmpeg -loglevel error -i mary_had_lamb.ogg -i mary_had_lamb.ogg -i mary_had_lamb.ogg -i mary_had_lamb.ogg \
  -filter_complex '[0][1][2][3]concat=n=4:v=0:a=1' -ar 16000 -ac 1 -sample_fmt s16 mary_x4.wav   # 63.8 s, 3 chunks
for fmt in json verbose_json; do
  curl -s localhost:8000/v1/audio/transcriptions -F file=@mary_x4.wav \
    -F model=openai/whisper-large-v3-turbo -F language=en -F response_format=$fmt \
    -F 'prompt=Hello. Yes, of course, I remember. Shall we meet tomorrow, on Wednesday? Okay, see you then.' \
  | jq '{phonograph: ([.text | ascii_downcase | scan("phonograph")] | length), segments: (.segments | length?), text: .text[-80:]}'
done
```

Each of the four recitations contains the word "phonograph" once, so a complete transcript has 4.

| `mary_x4.wav` + prompt | v0.27.1 (`<\|prev\|>`) | rename only (this PR) | rename + no leading `<\|startoftranscript\|>` |
|---|---|---|---|
| `json` | "…I see you then. I'm a little, I'm a little, …" (×40), 1 of 4 | **2 of 4**, ends with "…everywhere that Okay. Bye." | **4 of 4** |
| `verbose_json` | **empty text, 0 segments** | **2 of 4**, nothing after 58.8 s (file is 63.8 s) | **4 of 4**, 3 segments, no gap > 2 s |
| no prompt (reference) | 4 of 4, 7 segments | 4 of 4 | 4 of 4 |

`winning_call.ogg` ×2 (50.8 s) behaves the same way on v0.27.1: `verbose_json` + prompt → empty text, 0 segments; with both changes → 685 characters in 2 segments (709 without a prompt). We see the same on our own speech: a 61 s Russian dictation keeps 60 % of its words with the rename only, 96 % with both changes (the same as without a prompt). In `verbose_json` the lost window comes back as ONE segment spanning the whole window, so the segment durations still add up to the file length.

Lossy re-encoding matters: the same `mary_x4` as opus 24 kbit/s does **not** show the rename-only failure (4 of 4). It depends on the exact samples, hence the WAV recipe above.

### Why: the decoder input still is not the reference one

`get_generation_prompt` returns a decoder prompt that starts with `<|startofprev|>`, not with `decoder_start_token_id`, so `build_enc_dec_input` → `_prepare_decoder_input_ids_for_generation` prepends `<|startoftranscript|>`:

```
rename only : <|startoftranscript|> <|startofprev|> ␣prompt <|startoftranscript|><|lang|><|transcribe|><|notimestamps|>
reference   :                       <|startofprev|> ␣prompt <|startoftranscript|><|lang|><|transcribe|><|notimestamps|>
```

openai-whisper builds `[sot_prev] + encode(" " + prompt.strip())[-223:] + sot_sequence`, HF uses `get_prompt_ids(prompt)` followed by the forced decoder ids. Outside vLLM, with HF `WhisperForConditionalGeneration` (transformers 5.15, fp32 on CPU, greedy), the second 30 s chunk of the Russian dictation as produced by `split_audio`, and explicit `decoder_input_ids`:

| decoder input | generated |
|---|---|
| reference form | 123 tokens, the whole window |
| reference form with one extra leading `<|startoftranscript|>` (vLLM after the rename) | **8 tokens, then EOT** |
| no prompt | 123 tokens |

So it is the extra token, not precision or kernels.

### What fixed it for us (on v0.27.1)

1. `WhisperMultiModalProcessor.skip_decoder_start_token = True`. Every decoder prompt Whisper builds already starts with `<|startoftranscript|>`: the no-prompt form, `get_language_detection_prompt` and `WhisperDummyInputsBuilder.get_dummy_text`. The prompted form is the only exception, and it has to start with `<|startofprev|>`.
2. The async renderer must honour that flag. On `main` it already does (#54799). On 0.27.1 we backported #54799 verbatim, because transcription goes through `render_cmpl_async` → `_process_enc_dec_async`.
3. `f"<|startofprev|> {request_prompt.strip()}"`. The leading space and `strip()` make the token ids equal to HF `get_prompt_ids(prompt)`; without the space the first prompt token differs. On our set this made no measurable difference; it only matches the reference.

With these three changes, short clips are unaffected, and requests without a prompt produce exactly the same decoder input as before.

### Possibly worth separate issues (not caused by the rename)

- A prompt of ~300 tokens still returns HTTP 200 with a destroyed transcript of the window ("Привет. Привет. Привет. …"); over the 448 budget it is a clean 400. openai-whisper keeps only the last 223 prompt tokens.
- Special-token text inside the prompt is parsed as special tokens: `prompt=<|startoftranscript|><|en|><|translate|>` gives an empty transcript with HTTP 200. HF `get_prompt_ids` rejects such prompts.
- Related: #55281 — with a prompt, `verbose_json` returns far fewer, longer segments (3 instead of 7 on `mary_x4`).

_The investigation, the measurements and this write-up were done with the help of an AI coding assistant (Claude Code); all numbers come from runs on our own deployment and were checked before posting._
