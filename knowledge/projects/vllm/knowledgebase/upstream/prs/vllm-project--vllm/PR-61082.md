# [ROCm][Perf][DSv4.1] Mono decode on every backbone layer

[Upstream PR](https://github.com/vllm-project/vllm/pull/61082) · state: open · merged: False

## Overview

Follow-up to #60397. The DeepSeek-V4.1-Flash mono decode kernels (MI355X, `VLLM_ROCM_MONO_DECODE=1`) now run all 40 backbone layers whole as K1 + K2. Before, 30 layers ran whole and the other 10 kept vLLM's attention plus the FFN launch: layer 0, the Engram layer 1, and the index sources 2, 8, 14, 20, 24, 28, 32, 36.

## Claims

- AgentX at TP4, concurrency 1, 3,600 s, Rust frontend, against `main` with mono on: P90 interactivity goes from **541.6 to 562.6 tokens/s/user** (+3.9%), P50 from 569.8 to 595.5 (+4.5%), and ITL p50 from 1.760 to 1.680 ms.
- Accuracy is unchanged. GPQA-Diamond and AIME25 pass@1, mono on against off on this branch, differ by +0.1 ± 0.7 and +1.7 ± 1.2 points, both within noise. RULER NIAH scores 1.00 with mono on and off at 32K, 128K and 256K.
- Nothing changes with the switch off, and the 30 standard layers build the same kernels as before.

## Details

- **Settled residual (layers 0, 1, 14).** K1 gets a `fold` build flag. Without it, the seam slice takes the residual as it arrives instead of folding the previous layer's output in. Layer 0's residual is the embedding broadcast to the 4 streams, with an identity incoming pre-mix. The mix projection uses `hc_attn_fn` over the broadcast, which equals vLLM's folded `hc_attn_fn_broadcast` up to summation order. On an Engram layer, `mhc_post` and the Engram write run in torch before K1, as on vLLM's path.
- **Index sources (layers 2, 8, 14, 20, 24, 28, 32, 36).** K1 gets an `index` build flag.
  - K1 also stores its normed input and its bf16 qr (the q_norm output). It skips the key-table stage, because the top-k does not exist yet.
  - Between the two launches, `_select` runs vLLM's own modules: the compressor and its cache insert, the indexer K write, `weights_proj`, `forward_q` and `indexer_op`.
  - K2 then builds the key table on its last CTAs. Each attention split task waits on its token's flag, and the table goes through device scope, since the same launch reads it.
- **Tradeoffs.**
  - The compressor and indexer now run serially between the kernels. vLLM's path overlapped them on side streams, which the persistent kernels can't do, since they need every CU.
  - The indexer's `wq_b` quantizes the bf16 qr itself, where vLLM's fused q-norm hands it fp8 qr. The model-level test bounds the difference.
  - `_select` restates the module call sequence of `_forward_csa2_full` and `_forward_csa2_reindex` without their stream forks.
- **Not covered.** The DSpark draft layers still take vLLM's path. A layer outside the kernels (an MXFP8 KV cache, another indexer type) still takes the FFN launch, and the model-level test no longer exercises that launch; the numerics test does.
- **Model-level test bounds.**
  - Layer 0 now runs whole, so its output is held to 3% at every token. The old 1.5% at a request's first decode token was written for the FFN launch.
  - The near-tie exemption past layer 0 widens from 5e-3 to 1e-2. Every layer's input now carries the earlier layers' kernel differences (0.4–0.7%). One TP4 token flipped an expert at a gap of 0.0072 while every other token stayed near 4%.
- **Relation to other PRs.** #60731 ports the mono kernels to gfx942 and touches the same files. The two don't overlap in function, but whichever merges second needs a rebase.
- **Remaining gap.** On the formal sweep, ATOM's P90 at this point is 574. Moving the indexer's scoring and top-k, and the draft layers, into the kernels are the next steps.

I think this also relates to a broader design choice mentioned in the RFC that we might have to think about:

> There are two layer modes:
> - Whole layer: the kernel runs everything.
> - FFN layer: vLLM runs attention with its output all-reduce turned off. The kernel sums the partials and runs the rest, as https://github.com/vllm-project/vllm/pull/60397 does for 10 of its 40 layers. 

i.e. when developing the abstractions for mono, should we simply allow only "whole layer" mode or should we also allow more fine grained ops to be treated as monokernels. I'm planning on drafting a first suggestion on what this might look like based on the RFC + some of the other PRs
