# [Bugfix][Sampler] Keep tokens top-p must keep in Triton top-k/top-p search

[Upstream PR](https://github.com/vllm-project/vllm/pull/59804) · state: open · merged: False

## Original PR description

## Overview

Fixes #59785.

The monolithic Triton top-k/top-p kernel drops tokens that top-p is required to keep. This ports the failed-search fallback that the split top-p pipeline (`_topp_sb_combine`) already has into the monolithic kernel's three probability-space searches.

## Claims

- Standalone top-p no longer drops the min-prob token when reaching p requires the whole row (the reporter's triton-cpu repro keeps 7 of 8 tokens today, PyTorch keeps all 8).
- The top-k+top-p fifth pass on the CUDA main path no longer drops the k-th token when the top-k renormalized mass needs it to reach p.
- Failed searches now always land on the side that preserves the top-p mass invariant (kept mass >= p) instead of an arbitrary midpoint.
- Tie groups are bit-exact end to end: an absolute 1e-9 probability band merged hundreds of distinct fp32 values at small probs, and the position-ordered trim could keep a lower-probability token while dropping a higher one (NONPREFIX, 386 seeded fuzz rows; the parent kernel had 0).
- The combined top-k+top-p path now masks in probability space with a logit-space replay of the top-k survivor selection, so the prob->logit round trip can no longer leave a boundary survivor below the cut (kept mass 0.480427 under p = 0.5 on a near-flat fuzz row), and trimmed non-survivors no longer add their mass to the pivot search.

## Details

Root cause: all three binary searches evaluate pivots only inside `[min_prob, max_prob]` and count survivors with a strict `probs > pivot`, so the minimum-probability candidate is unreachable by construction. When reaching p requires that candidate, the termination condition can never hold, the loop burns all 18 iterations, and the midpoint fallback settles just above the minimum, masking exactly the token that top-p must keep. On CUDA this is normally hidden because small batches go through the split pipeline (which has a proper fallback), but the monolithic kernel still serves every top-k+top-p row, batches larger than `_SPLIT_MAX_BATCH`, and non-CUDA builds like the reporter's.

Fix: during the walk, track the tightest evaluated pivot whose above-mass still reaches p. On a failed search, fall back to that pivot. If no evaluated pivot ever reached p, then even keeping every candidate undershoots p, so keep the whole row for standalone top-p (`final_pivot = -inf`) or keep the phase-one top-k boundary for the combined path. This is exactly the `best`/`nomask` logic in `_topp_sb_combine`, so the two pipelines now agree on the edge semantics.

Scope: the normal convergence path, iteration budget, and search ranges are unchanged; only the failed-search fallback changes, and only toward keeping more. The existing suite did not catch this because its top-p tolerance is relative (0.5% or 3 values), which hides single-token drops at large vocab; small-vocab rows and CPU builds hit it directly.

Not a duplicate: #59785 has no assignees or comments, and open-PR searches for `59785 in:body` and `topk_topp_triton` came back empty.

- he-yufeng · comment · 2026-10-03T02:23:49Z · [source](https://github.com/vllm-project/vllm/pull/59804#issuecomment-5964568681)

Thanks for the thorough trace, all four rows reproduced exactly here. New commit `18ac2825d7` is up, mapped to your findings:

**1. Keep-all on confident rows.** Root cause is arithmetic bisection starving on ranges that span orders of magnitude: one halving buys a factor of two, so 18 iterations from 0.475 only get down to 5.4e-6 and every evaluated pivot sits above the bulk of the tail mass, exactly like your interpreter trace showed. The search now uses a geometric midpoint while the range spans more than 16x (arithmetic once it narrows), exits on a relative bracket tolerance instead of the absolute 1e-9, and gets 32 iterations. If no evaluated pivot still reaches p, it evaluates the zero pivot once, so a flat row now trims to the exact count instead of keeping everything; only genuinely degenerate rows (NaN/empty) keep all.

**2. num_keep wrap.** The drop is clamped in float before the uint32 cast, so a coarse fallback pivot cannot wrap the counter. The denominator also changed from min_prob to the largest member mass of the 1e-9 tie band, which makes trimmed mass <= (sum - p) hold unconditionally. The trim itself is capped too: it only removes members past num_keep up to the counted group size, so when tile merging undercounts a big tie group (your 16 vs the real group) the extra members are kept instead of over-trimmed below p. The same capped removal went into the top-k+top-p logit path, which had the same latent undercount issue.

**3. Boundary token below p.** Dropped the prob-to-logit round trip for standalone top-p. The mask pass now recomputes exp(logit - max) / sum_exp per token with the same fp ops as the buffer pass and compares against p_pivot in probability space, so the kept set is by construction the search's above-set and your token 434 case cannot happen.

Also: pivot masses accumulate in fp64 now. fp32 sequential summation over ~1k tiles was shedding a couple of tokens' worth of mass on flat/zipf rows, which contributed to row 2's overshoot.

Verification caveat: this box has no GPU or triton, so I validated against a numpy mirror that replicates the kernel's fp32 semantics under the triton-cpu tile config (BLOCK 256 / TRUNC 128). """Seeded fuzz of vLLM's Triton top-k/top-p kernel against an exact float64 top-p reference.

Written for vllm-project/vllm#59804. Runs any number of kernel modules side by side, e.g. the PR file
and a copy of its parent staged next to it:

    git show <parent>:vllm/v1/sample/ops/topk_topp_triton.py > vllm/v1/sample/ops/topk_topp_triton_base.py
    python fuzz_topp.py vllm.v1.sample.ops.topk_topp_triton vllm.v1.sample.ops.topk_topp_triton_base

Add --quick for a smaller run (8 instead of 40 rows per small-V group). Rows come from
np.random.default_rng(59804), so the same numpy version gives the same 32,449 rows (full run).

Classes, for the kept set K of a row with float64 probabilities q and cut p:
  FEWER     mass(K) < p - tol(V)                      (drops mass top-p must keep)
  MORE      mass(K) - min_{i in K} q_i >= p + tol(V)  (a strictly smaller top set still reaches p)
  NONPREFIX keeps a token with q below a dropped token's q
  OK        otherwise (boundary ties included)
"""
import importlib
import json
import sys

import numpy as np
import torch

TOL = 1e-5  # plus 2e-9 * V: float32 sums over V terms (PyTorch's own cumsum is off by ~6e-5 at V=151,936)


def tol(V):
    return TOL + 2e-9 * V


def classify(logits32, keep, p, k):
    """Return (class, kept_mass, exact_mass, n_kept, n_exact) against an exact float64 reference."""
    x = logits32.astype(np.float64)
    live = np.isfinite(x)
    if k is not None and k < live.sum():
        kth = np.sort(x[live])[::-1][k - 1]
        live &= x >= kth  # ties at the k-th logit: every tied token is admissible
    q = np.zeros_like(x)
    xm = x[live].max()
    q[live] = np.exp(x[live] - xm)
    q /= q.sum()
    order = np.argsort(-q, kind="stable")
    cum = np.cumsum(q[order])
    n_exact = int(np.searchsorted(cum, p - 1e-12) + 1)
    n_exact = min(n_exact, int(live.sum()))
    exact_mass = float(cum[n_exact - 1])
    m = float(q[keep].sum())
    if not keep.any():
        return "FEWER", m, exact_mass, 0, n_exact
    t = tol(x.size)
    if m < p - t:
        return "FEWER", m, exact_mass, int(keep.sum()), n_exact
    if (~keep & live).any() and q[keep].min() < q[~keep & live].max() * (1 - 1e-6):
        return "NONPREFIX", m, exact_mass, int(keep.sum()), n_exact
    if m - q[keep].min() >= p + t:
        return "MORE", m, exact_mass, int(keep.sum()), n_exact
    return "OK", m, exact_mass, int(keep.sum()), n_exact


def gen(quick):
    """Yield (group, logits[n,V] float32, k or None, p). Seeded; inputs are also saved."""
    rng = np.random.default_rng(59804)
    nrow = 8 if quick else 40
    # G0: the #59785 reporter row
    row = np.array([[-0.9507, -0.7643, -0.9077, -1.0789, -0.0125, -0.5607, -1.1629, -0.3498]], np.float32)
    yield "G0_reporter_row", row, None, 0.95
    # G1: D-44 E2 part B shapes (same generator family, new seed), V small to mid
    for V in (8, 32, 64, 256, 1024, 4096):
        for kind in ("normal1", "normal3", "zipf", "peaked"):
            for T in (0.5, 1.0, 2.0):
                for k in (None, 3, 50):
                    if k is not None and k >= V:
                        continue
                    for p in (0.3, 0.5, 0.9, 0.95):
                        if kind == "normal1":
                            L = rng.normal(0, 1, (nrow, V))
                        elif kind == "normal3":
                            L = rng.normal(0, 3, (nrow, V))
                        elif kind == "zipf":
                            b = -1.1 * np.log(np.arange(1, V + 1))
                            L = np.stack([rng.permutation(b) + rng.normal(0, 0.1, V) for _ in range(nrow)])
                        else:
                            L = rng.normal(0, 2, (nrow, V))
                            L[np.arange(nrow), rng.integers(0, V, nrow)] += 10
                        yield f"G1_{kind}_V{V}_T{T}_k{k}_p{p}", (L / T).astype(np.float32), k, p
    # G2: dominant token + near-flat tail, crossing inside the tail (search-resolution trap)
    for V in (64, 1024, 32768, 151936):
        for d in (0.5, 0.9, 0.94):
            for jit in (0.0, 1e-4, 1e-2, 0.3):
                for frac in (0.1, 0.5, 0.9):
                    p = d + (1 - d) * frac
                    n = 4 if V >= 32768 else nrow // 4
                    L = rng.normal(0, jit, (n, V)) if jit > 0 else np.zeros((n, V))
                    top = rng.integers(0, V, n)
                    # logit gap so the dominant token carries mass d against V-1 unit tail tokens
                    L[np.arange(n), top] = np.log(d / (1 - d) * (V - 1))
                    yield f"G2_flat_tail_V{V}_d{d}_jit{jit}_frac{frac}", L.astype(np.float32), None, round(float(p), 6)
    # G3: realistic large-V Zipf with noise, several temperatures and p
    for V in (32768, 151936):
        for T in (0.7, 1.0, 1.5):
            for p in (0.8, 0.9, 0.95, 0.99):
                n = 4 if quick else 12
                b = -1.1 * np.log(np.arange(1, V + 1))

@SeverinVisionary Your guess is the right mechanism. The gate summed fp32 per-tile partials into the fp64 accumulator over 256-wide tiles in original row order during the gather, while the search and the stall fallback sum the compacted buffer over 128-wide tiles. Same values, different partial-sum trees, so the two totals disagree by an ulp or two either way. A p inside that gap never lets the search terminate: each probed pivot sums below p, max_range walks down onto outlier_prob, the stalled recompute there comes back under p, and masked=0 keeps the row. It also explains why 1dec7eff moved the case instead of closing it: switching the gate accumulator to fp64 changed the rounding profile, so a different set of rows fell into the gap.

New head b9512d2 removes the gap instead of recovering from it. The gate no longer sums during the gather. After compaction it sums the buffer through _mass_ge_stats, the same helper the search and the stall fallback use, with the same TRUNC tiles and the same theta. The branch test `sum_outlier_probs > p` and the stalled recompute at outlier_prob are then bit-exact the same number, so masked=0 is unreachable while min_range is still outlier_prob.
