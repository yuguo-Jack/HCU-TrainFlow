# [Bugfix][Benchmark] Restore --input-len/--output-len/--prefix-len in vllm bench throughput

[Upstream PR](https://github.com/vllm-project/vllm/pull/64227) · state: closed · merged: True

## Original PR description

## Overview

`vllm bench throughput` silently ignores `--input-len`, `--output-len` and `--prefix-len` on the random dataset and benchmarks 1024 / 128 / 0 instead, while warning that the matching `--random-*` flag was also given. Regression from #29105.

## Claims

- `--input-len/--output-len/--prefix-len` take effect again; an explicit `--random-*` flag still wins, and with neither the defaults stay 1024 / 128 / 0.
- The "Both --X and --random-X are specified" warnings only fire when both are actually passed, and "--prefix-len will be ignored" only when `--prefix-len` is passed.
- The help of all six flags, and so the CLI reference, states the precedence and the effective defaults.

## Validation

```bash
vllm bench throughput --model RedHatAI/gemma-3-1b-it-FP8-dynamic --input-len 2048 --output-len 512 --prefix-len 64 --num-prompts 8
```

| | sampled lengths (log) | prompt / output tokens | warnings |
|---|---|---|---|
| main | input 1023, output 128 (the 1024 / 128 / 0 defaults) | 8192 / 1024 | 3 ("Both --input-len and --random-input-len are specified", same for output and prefix) |
| this PR | input 2047, output 512 | 16896 (8 × (2048 + 64)) / 4096 | none |

(The log reports the input length after the special token; the 64-token prefix shows in the prompt-token total.)

Every flag combination, from the real parser through `validate_args` and `get_requests` (gpt2 tokenizer, random dataset; prompt length includes the prefix):

## Details

- **Root cause.** #29105 moved the random dataset onto the shared `add_random_dataset_base_args`, whose `--random-*` lengths default to 1024 / 128 / 0. `_to_serve_args` (`getattr(args, "random_input_len", input_len)`) and `validate_args` treat `None` as "not passed", but the parser never leaves them `None`, so the legacy value is never used and the conflict warnings always fire.
- **Fix.** The throughput parser leaves the three `--random-*` lengths unset (default `None`), and `_to_serve_args` resolves explicit `--random-*` > legacy flag > `RandomDataset.DEFAULT_*`, from one `_RANDOM_LEN_FALLBACKS` table that also writes the help text. `bench mm-processor` passes its own parsed `--random-*` values (never `None`) and is unaffected.
- **No duplicate.** No open issue or PR reports or fixes this; searched open PRs and issues for `bench throughput` with `--input-len` / `--random-input-len`.
- **`--prefix-len` default.** It defaulted to 0, so it always looked passed: `--random-prefix-len` alone warned, and every non-random dataset warned that `--prefix-len` would be ignored. It now defaults to `None` like `--input-len` / `--output-len`.
- **Docs.** With the `--random-*` lengths unset in the parser, the CLI reference would no longer show their defaults, so all six flags' help now states: explicit `--random-*` > legacy flag > `RandomDataset` default (1024 / 128 / 0).
- **Impact in tree.** The documented example in `docs/cli/README.md` (`--input-len 32 --output-len 1`) has been running 1024 / 128 since #29105, and `benchmarks/benchmark_pin_memory.py` works around the bug by setting the `--random-*` lengths to `None` by hand.
- **Removed check.** `validate_args` required `--input-len` or `--random-input-len` for a random dataset; since #29105 it could not fire, and keeping it would now break runs that pass neither. Those keep today's 1024 / 128 / 0.
