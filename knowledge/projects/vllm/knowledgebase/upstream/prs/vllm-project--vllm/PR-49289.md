# fix(parser): discard matching subword buffer prefix on `PreLexedTerminal`

[Upstream PR](https://github.com/vllm-project/vllm/pull/49289) · state: open · merged: False

## Original PR description

## Title
fix(parser): discard matching subword buffer prefix on `PreLexedTerminal`

## Description
Fixes #49205

### Summary of Changes
- `StreamingParserEngine._process_scanner_items` previously flushed the lexer's buffer unconditionally upon encountering a `PreLexedTerminal`.
- When a model spells out part of a tag via subword tokens before emitting the dedicated special token ID for the same tag, the buffered subword prefix was dumped as a spurious `TEXT_CHUNK` right before the tool call.
- Added a check verifying if `item.text.startswith(self._lexer.buffer)` when a `PreLexedTerminal` arrives. If `True`, the lexer buffer is reset rather than flushed.
- Added regression test in `tests/parser/engine/test_streaming_parser_engine_bug49205.py`.

- bbrowning · comment · 2026-07-21T11:22:10Z · [source](https://github.com/vllm-project/vllm/pull/49289#issuecomment-5033324418)

I'm not sure this is the right fix for the symptoms described in #49205 - it sounds like the model in use does not reliably use its own special tokens for generation tool calls there. If that's the case, then the parser for the model probably should not rely on special tokens at all and just use the text output. A model that outputs a subword token for tool calls followed by a special token for the same tool call sounds quite broken, so relying only on the textual output would be the right thing. The parser engine already supports this mode, and token id matching is designed for better behaved models that reliably output their special tokens for reasoning, tool call, etc delimiters.

If we can find some widely used models that have the same broken behavior then it may be something we have to handle. But, it's not something I've run across yet.
