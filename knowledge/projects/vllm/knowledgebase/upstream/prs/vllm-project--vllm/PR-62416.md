# [Rust Frontend] Support `--tokenizer`, `--tokenizer-revision`, and `--hf-config-path`

[Upstream PR](https://github.com/vllm-project/vllm/pull/62416) · state: open · merged: False

## Original PR description



## Overview

The Rust frontend rejects `--tokenizer`, `--tokenizer-revision`, and `--hf-config-path` at startup, so a checkpoint that ships its weights without a tokenizer or config (for example a GGUF-only repo that borrows both from the BF16 repo) can only be served with the Python frontend. This PR supports all three options. It supersedes the community attempt vllm-project/vllm#57178, keeping its source mapping but restructuring the resolver instead of adding a second resolution path beside the existing one.

## Claims

- `vllm serve` (with `VLLM_USE_RUST_FRONTEND=1`), `vllm-rs serve`, and `vllm-rs render` accept the three options. The managed Python engine receives them too.
- Each group of files is read from the same source as in Python's `ModelConfig`:
  - tokenizer files and the chat template: `--tokenizer` at `--tokenizer-revision`, which defaults to `--revision`;
  - `config.json` and `generation_config.json`: `--hf-config-path` at `--revision`, and that source must contain `config.json`;
  - multimodal processor configs: the model.
- A weights-only model repo resolves from the HF cache, including offline, once the tokenizer and config come from elsewhere.
- Without the new options, resolution behaves as before.

## Validation

- `cargo clippy --workspace --all-targets` is clean, and `cargo nextest run -p vllm-text -p vllm-chat -p vllm-server -p vllm-cmd -p vllm-managed-engine` passes: 1064 tests.
- New tests:
  - `resolved_model_files_read_each_group_from_its_source`: every file exists in all three dirs, and a snapshot records which dir each resolved file came from.
  - A model dir that holds only weights resolves with the overrides and fails without them.
  - `config.json` is required only for an explicit `--hf-config-path`.
  - The offline HF-cache test now covers distinct sources and a cache miss on the config source.
  - CLI coverage: `serve`, `frontend --args-json` (including `--tokenizer-revision` on its own), `render`, and the Python args forwarded to the managed engine.
- **Refactor check:** a temporary binary printed `ResolvedModelFiles` for 14 single-source cases, built once on `main` and once on each commit. The output was identical. Cases: a local dir; cached by branch and by commit SHA; offline misses; fresh downloads of `Qwen/Qwen3-0.6B`, `moonshotai/Kimi-K2.5` (tiktoken), `mistralai/Mistral-7B-Instruct-v0.3`, and `openai/gpt-oss-20b`; a missing repo.
- **Render check:** I took a GGUF-only checkpoint plus its BF16 sibling repo and ran `vllm-rs render` on the BF16 dir alone, then on the GGUF dir with `--tokenizer <bf16> --hf-config-path <bf16>`. The second run used both local paths and offline-cache HF ids. A tool-calling `/v1/chat/completions/render` request returned identical token IDs and sampling params (the `generation_config.json` defaults) in every case. Without the options, the GGUF dir fails with the same tokenizer error as `main`.
- Not run: GPU serving end to end. Only the frontend reads these files; the Python engine already accepted these options.

## Details

All model file access in the Rust frontend goes through `ResolvedModelFiles`. Its output fields stay unchanged, so its consumers don't change. The PR has three commits:

1. **Refactor, no behavior change.** `ResolvedModelFiles::new` had three resolvers (local dir, HF cache, Hub download), each repeating the full file list and its own tokenizer lookup. A private `SourceFiles` now replaces them. It is either a directory (a local dir or a cached snapshot) or a listed remote repo, and the struct is filled through it in one place.
2. **Feature.**
   - `ModelSource { id, revision }` and `ModelFileSources { model, tokenizer: Option, hf_config: Option }` (where `None` means "use the model"), plus `ResolvedModelFiles::from_sources`. Each field names the source it reads from.
   - A cached snapshot is used only if it contains the file that source must provide: the tokenizer file, `config.json`, or nothing for a model whose tokenizer and config both come from elsewhere. Today's rule, "the snapshot has a tokenizer", is the special case where everything comes from the model.
   - Server and render configs gain two typed fields, and the three `Unsupported` markers are removed.
3. **CLI grouping.** `model` and `--revision` move into the flattened `ModelArgs`, next to the new options. It lowers to one `ModelFileSources`, applying the Python defaults in one place, and forwards all four options to the managed engine.

Compared with vllm-project/vllm#57178, this avoids:

- a second resolution path with an early-return short-circuit;
- a third copy of the local/cache/remote resolvers;
- a source-equality matrix with a `require_config` flag;
- a cache-hit rule that accepts any one of five optional files;
- resolving the tokenizer source with the full resolver and discarding its config downloads;
- five positional string parameters;
- loose `Option<String>` fields threaded through every config.

Out of scope: a `model` that is a single `.gguf` file path (Python's `vllm serve x.gguf`). It still fails as an unknown repo id.
