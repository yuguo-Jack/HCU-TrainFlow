# [Perf][Spec Decode] Capture every small decode request count by default

[Upstream PR](https://github.com/vllm-project/vllm/pull/62173) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

With speculative decoding, the default CUDA graph sizes now include every decode batch of 1 to 8 requests. Small
batches stop padding to the next power of two, which runs 1 + K extra tokens per padded request through every
layer.

## Claims

- With MTP K=3, 3, 5 and 7 running requests replay 12-, 20- and 28-token graphs instead of 16, 24 and 32. GLM-5.2-
  NVFP4, TP4, B300: decode -6% to -7% at 3 requests, -2.5% to -3.4% at 5, -2.2% to -2.4% at 7, unchanged at 1.
- Three extra decode graphs (and their piecewise twins) for K=3: capture 6 s -> 7 s, graph memory 0.61 -> 0.65 GiB per GPU.
- Without speculation, and for explicit `cudagraph_capture_sizes`, nothing changes.
- On InferenceX AgentX, GLM-5.3 vs SGLang: decode time on the same turns drops 0.5-0.9% at concurrency 1-8 and 0.1% at 16 on 4x GB200 (0.5-1.1% on 4x B300); batches of 3-7 running requests are a small share of AgentX decode steps.

## Validation

- `tests/compile/test_config.py -k keep_all_sizes_bounded` (expected request grid updated) and
  `tests/v1/cudagraph/test_cudagraph_manager.py` pass. On B300, `tests/compile/test_config.py -k cudagraph` has 12
  failures, the same 12 as on main on that machine (`unchanged_without_speculation`, `respects_platform_ceiling`,
  `still_clamped_by_token_budget`, `test_use_cudagraphs`), so unrelated to this change.
- End to end: B300 x4 (SM103), GLM-5.2-NVFP4, TP4, MTP K=3 with synthetic acceptance length 3.0 (fixed step count),
  `max_model_len` 1M, FP8 KV, default CUDA graph sizes. Decode ms/token per request, median of 9 repetitions of
  (T1200 - T200) / 1000 on cached prompts:

## Details

For speculative decoding, `_set_cudagraph_sizes` appends a request-count grid times `decode_query_len` (1 + K).
That grid started 1, 2, 4, 8, copied from the one-token grid, where padding 3 requests to 4 costs one token. A
decode request is 1 + K tokens, so the same padding costs 1 + K tokens. Padded tokens still go through the
attention, the GEMMs and the MoE (routed like real tokens), and at small batches decode is bound by those layers.
The token grid's 8-token stride already yields even request counts at K=3, so this adds 3, 5 and 7 requests there.
