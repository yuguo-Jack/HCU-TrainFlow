# [Bugfix][Spec Decode] Keep SW draft block a divisor of the primary block

[Upstream PR](https://github.com/vllm-project/vllm/pull/60252) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Related to #60174. **The correctness fix for #60174 is #55601**, not this PR. That bug is the mamba state column being seeded with the lowered `cache_config.block_size`. I briefly added the same one-line fix here (a24c836) without noticing #55601, and have reverted it (thanks @twu3202).

What this PR does: since #53007, a sliding-window layer whose largest fitting kernel block does not divide the primary block gets a padded page instead of an integer-scaled one. With a GDN hybrid target (1648-token block) and a SW DFlash2 drafter on a backend limited to `[16, 32, 64]` (FlashInfer on sm_120), the SW group runs on 64-token blocks. This:

- raises the scheduler block (LCM of all group blocks) from 1648 to 6592, the kind of LCM inflation #53007 set out to avoid;
- lowers `cache_config.block_size` to 64, which is what exposes the seeding bug in #55601;
- disables fine-grained prefix-cache hits (`Disabling fine-grained prefix-cache hits ... SlidingWindowManager`).

This PR keeps the SW block a divisor of the primary block, so `unify_kv_cache_spec_page_size` scales it as on v0.29.0. Configs where the chosen block already divides the primary block (the #53007 target case) are unchanged.

> **History.** Earlier versions of this PR described the padded SW page as the cause of #60174, then added the seeding fix. Both are superseded: the cause is the seeding bug, and its fix lives in #55601. Thanks to @sinmkd, @nej1gotnochill and @twu3202 for the reviews that got there.

## Validation

Single RTX PRO 5000 (sm_120), TP=1, vLLM 0.31.0 wheel with patches applied; Qwen3.8-27B NVFP4 + `Qwen3.8-27B-DFlash2` (k=7), `--kv-cache-dtype fp8`, prefix caching on; fresh engine per run. 5-request replay with growing prefix (33K → 69K tokens):

| build | SW block / LCM | requests 3–5 | prefix-cache hit rate |
|---|---|---|---|
| 0.31.0 | 64 / 6592 | degenerate (all-NaN logits) | – |
| + seeding fix (#55601 equivalent) | 64 / 6592 | coherent | 43.8% |
| + seeding fix + this PR | 1648 / 1648 | coherent | 71.2% |

Independent measurements:
- @stecasta, same-node A/B on DGX Spark (GB10), Qwen3.8-27B NVFP4 + DFlash2 (k=8), only this change: KV groups go from 1648x14 + 64 (scheduler block 6592, fine-grained hits disabled) to all 1648; a 168-turn agentic replay goes from 26.1 to 20.0 min, prefix-cache hits 56.3% → 77.4%, decode tok/s unchanged.
- @twu3202 on sm_89 (SW-only arm: `kv lcm block sizes 1616`, 3 prefix hits vs 1 without it).

On its own, this PR also stops the #60174 corruption in my setup, but only because `min(group block sizes)` becomes the mamba block again. That masks the seeding bug and does not fix it.

Tests:
- `test_largest_kernel_block_within_divisor_of`: the new `divisor_of` option, including the fallback when no supported block divides the primary block.
- `test_sliding_window_spec_unifies_without_padding`: runs `Attention.get_kv_cache_spec` for a SW layer on a `[16, 32, 64]` backend, then `unify_kv_cache_spec_page_size`. It asserts the SW page is scaled, not padded. With the fix disabled, the 1648 case fails and the 1536 case (unchanged path) passes.

These were run as plain assertions on the patched 0.31.0 install (no pytest there). CI covers `tests/v1/attention`. Lint: `ruff check`, `ruff format --check` and `typos` on the changed files.

## Details

`_largest_kernel_block_within` gets a `divisor_of` option. With it, the helper returns the largest fitting block that divides `divisor_of`, and falls back to the previous choice if none does. The SW branch passes the primary block when there is no `shared_page`. Without `divisor_of` the helper behaves exactly as before, so the existing `test_largest_kernel_block_within` cases are unchanged.

**Not a duplicate:** #55601 changes `mamba_hybrid.py`; this PR changes the SW kernel-block selection in `Attention.get_kv_cache_spec`. None of #55818, #59683, #58207, #54163 or #56552 touches that selection. I'm fine with this being reviewed after #55601, or closed if reviewers consider the padded layout acceptable.

- Anchen798 · comment · 2026-10-07T07:18:06Z · [source](https://github.com/vllm-project/vllm/pull/60252#issuecomment-6032992912)

Update: I found the TP=1-specific factor, and it turns out to be the actual root cause. I've pushed a fix (a24c836) and rewritten the PR description.

`MambaHybridModelState.add_request` seeds the align-mode mamba state column as `(num_computed_tokens - 1) // cache_config.block_size`. After KV cache init, `EngineCore` overwrites `cache_config.block_size` with the smallest group block size, which is the drafter's SW group (64) here instead of the mamba block (1648). On the first mamba prefix hit (26368 tokens), the column comes out as 411 instead of 15. That is past the block table, so the initial GDN state is read from the null block, which contains NaN under CUDA graphs. The target logits then become all NaN, and the repeated `duct` / ` Register` tokens are just Triton's argmax returning the last index of a 1024- or 8192-wide block.

This explains @sinmkd's observations:
- **TP=2 does not corrupt with the same layout** because its workers are separate processes and keep `cache_config.block_size=1648`. With TP=1 the worker shares the overwritten config with `EngineCore`.
- **`--enforce-eager` is clean** because the null block has no NaN there (the state is still wrong, just finite).

With only the one-line fix and the SW block left at 64, the 5-request replay is 5/5 coherent, and so is the 3x minimal repro (also with the SW block forced to 32). The original SW-block commits now only restore the v0.29.0 layout (LCM 1648, fine-grained hits on; prefix-cache hit rate 43.8% → 71.2% in the replay). I've kept them but am happy to drop or split them if you prefer a minimal fix.

Sorry for the earlier wrong explanations, and thanks again for pushing on the TP=2 discrepancy. That is what led to this.
