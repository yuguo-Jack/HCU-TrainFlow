# [ROCm] [RDNA] [Perf] Add tuned configs for TRITON_ATTN kernel and swap places of TRITON_ATTN and ROCM_ATTN in priority list

[Upstream PR](https://github.com/vllm-project/vllm/pull/60418) · state: closed · merged: True

## Original PR description

## Purpose

On gfx1201 (RDNA4) and gfx1100 (RDNA3), swap `ROCM_ATTN` and `TRITON_ATTN` in vLLM's attention-backend priority list, so `TRITON_ATTN` becomes the default. This PR also adds launch configs for `TRITON_ATTN` on both GPUs, tuned with synthetic sweeps. With them, `TRITON_ATTN` is faster than `ROCM_ATTN` overall, including where `ROCM_ATTN` uses its HIP paged-attention decode kernel. The same configs are used with an fp8 KV cache.

This PR includes #60658 (closed), which had the launch configs only.

## Changes

**`vllm/platforms/rocm.py`:**
- `get_valid_backends()`, on gfx1201 and gfx1100: `ROCM_ATTN` and `TRITON_ATTN` swap places in the priority list. Nothing else moves.
  - **Exception:** an `fp8_e5m2` KV cache keeps `ROCM_ATTN`. `Attention` quantizes the query to fp8 only for `fp8`/`fp8_e4m3` caches, and rejects `fp8_e5m2` for backends that take an fp8 query, as `TRITON_ATTN` does on gfx1201.
  - **Unchanged:** an explicit `--attention-backend`, and every other GPU (including gfx1200, gfx1101 and gfx1151).
- New `on_gfx1201()` helper.

**`vllm/v1/attention/ops/triton_unified_attention.py`:** only launch parameters change (`BLOCK_M`/`BLOCK_Q`, `TILE_SIZE`, `num_warps`, `num_stages`, split-KV segments) and, on gfx1201, the 2D/3D decode threshold. The kernels themselves are untouched.

How the configs are applied:
- They're looked up by the padded head size (`next_power_of_2`): head 96 uses the 128 configs, 192 the 256 configs.
- They apply to every attention variant (sliding window, sinks, softcap, ALiBi), because those are applied per element inside each tile.
- Batch-invariant mode keeps the default launch.

*gfx1201:*
- **Prefill / chunked / mixed** (`max_seqlen_q > 64`, GQA ≤ 16), as (`BLOCK_M`, `TILE`, warps, stages):

  | head_size | 64 < max_seqlen_q < 4096 | max_seqlen_q ≥ 4096 |
  |---|---|---|
  | 64 | 64, 64, 4, 1 | 128, 64, 8, 1 |
  | 128 | 64, 32, 4, 1 | 128, 32, 8, 2 |
  | 256 | 32, 32, 4, 1 | 128, 32, 8, 1 |
  | 512 | 64, 16, 8, 1 | 64, 16, 8, 1 |

  Decode-heavy mixed batches with `BLOCK_M // GQA > 16` and fewer than 16 new tokens per request keep the default. With an fp8 query (see below), only configs with `TILE ≥ 32` are used, so head 512 keeps the default.
- **2D decode** (decode batches above the split-KV threshold), as (`TILE`, warps, stages): head 64 (16, 1, 1), 128 (16, 2, 1), 256 (16, 2, 1), 512 (16, 8, 1). With an fp8 query, `TILE` is at least 32.
- **2D/3D switch:** pure decode batches with a 16-bit KV cache use split-KV (3D) up to `64 // num_kv_heads` requests instead of `128 // num_kv_heads`.
- **Split-KV (3D) segments**, head 64/128/256. vLLM always uses 16 segments per request, so the kernel launches requests × KV heads × 16 programs: too few for one request (1 × 2 KV heads × 16 = 32 programs on 32 CUs), and too many tiny ones for larger batches. This PR picks the segment count so that requests × KV heads × segments ≈ 128.
  - 16-bit query: 4 to 128 segments; `TILE` 16, 2 warps, 1 stage.
  - fp8 query: only more segments for small batches (head 256: about 64 programs); head 64 `TILE` 32 / 1 warp, others `TILE` 32 / 4 warps / 2 stages above 16 segments.
  - Sliding windows < 2048 keep 16 segments (head 64: `TILE` 32 / 1 warp, head 128: `TILE` 16 / 1 warp).
  - The scratch the metadata builder allocates is reused as rows × segments. The count depends only on the batch size and the model shape, so it is fixed per CUDA graph.
- **fp8 KV cache:** on gfx1201, `Attention` passes `TRITON_ATTN` an fp8 query; the rules above note where that changes the launch. The 2D/3D switch keeps vLLM's threshold with an fp8 KV cache.

*gfx1100:* applied after the 2D/3D choice, so the 2D/3D threshold is vLLM's.
- **Batches with prefill tokens:** three `max_seqlen_q` bands, as (`BLOCK_M`, `TILE`, warps, stages); "–" keeps the default.

  | head_size | ≤ 64 | 65–4095 | ≥ 4096 |
  |---|---|---|---|
  | 64 | 16, 32, 2, 1 | 32, 32, 2, 1 | 128, 64, 8, 1 |
  | 128 | – | 64, 32, 4, 1 | 128, 32, 8, 1 |
  | 256 | 32, 32, 8, 1 | 64, 32, 8, 1 | 128, 64, 8, 1 |
  | 512 | 64, 32, 8, 1 | 64, 32, 8, 1 | 64, 32, 8, 1 |

- **2D decode**, as (`TILE`, warps, stages): head 64 (16, 2, 1), 128 (16, 2, 1), 256 (16, 4, 1), 512 (32, 8, 1). `TILE` is raised to 32 with a per-tensor fp8 KV cache.
- **Split-KV (3D) segments:** `next_pow2(T / (requests × KV heads))`, at most 128, with `T` = 512 / 128 / 128 / 64 for head 64 / 128 / 256 / 512. Sliding windows ≥ 512 use 8× as many segments. Sliding-window decode switches to 2D at requests × KV heads ≥ 32 (head 64) / 8 (head 512).
- **fp8 KV cache:** gfx11 has no fp8 matrix instructions, so the query stays bf16 and the configs apply as they are.

**`tests/v1/attention/test_rocm_attention_backends_selection.py`:**
- New `test_rdna_prefers_triton_attn`. It calls `RocmPlatform.get_attn_backend_cls()` with a mocked arch. Expected selections:
  - gfx1201 and gfx1100 select `TRITON_ATTN`, for the HIP-kernel config (head 128, block 16, bf16, `auto` KV) and for an `fp8` cache;
  - `fp8_e5m2` keeps `ROCM_ATTN`;
  - an explicitly selected `ROCM_ATTN` stays `ROCM_ATTN`;
  - gfx1200 and gfx1101 keep `ROCM_ATTN`.
- Two existing tests that check vLLM's default order now pin `on_gfx1201()` / `on_gfx1100()` to False.

## How it was measured

All measurements call `TRITON_ATTN` (and, for the A/B, `ROCM_ATTN`) as vLLM runs them:
- vLLM's KV-cache allocator, and the backend's own cache writer, metadata builder and `forward()`;
- with an fp8 KV cache, the query is quantized exactly when `Attention` would;
- short-query batches configure speculative decoding, as a server would.

Every output is compared to an fp32 PyTorch reference (causal mask, sliding window, sinks, softcap, ALiBi), within 0.02 + 0.02·|ref|; with an fp8 KV cache, 0.25 + 0.1·|ref|.

Timing:
- each timed call reads its own copy of the KV cache, query and output, with ≥ 512 MB of KV across copies, so data comes from GPU memory and not from L2 / Infinity Cache;
- all copies run in one CUDA graph;
- time per call = graph time / copies.

**Tuning, in order** (each on gfx1201; gfx1100 used the same method):

1. **2D launch configs**, against `TRITON_ATTN`'s default launch.
   - Shapes: head 64/128/256 × GQA 1–16 × KV heads per GPU 1–8 × block 16/528 (138 shapes), plus head 512 (Gemma 4's global layers, 5 shapes).
   - Batches: 214 per shape (decode, prefill, chunked prefill, mixed).
   - Configs: `BLOCK_M` × `TILE` × warps × stages. A pilot timed every config on 2 shapes; a greedy cover kept the fewest configs within 2% of the best on every pilot batch.
   - Rule: per head size and region, the simplest rule (one config per band) close to the per-shape best, and ≥ 0.97× the default on almost every batch.
   - 29,532 measurements, 0 wrong outputs. Over the default launch on prefill-containing batches: 2.32× (head 64), 2.12× (128), 1.82× (256), 3.41× (512).
2. **2D/3D switch:** 3,888 decode and short-query batches, each run forced-2D and forced-3D. Under full CUDA graphs the choice is frozen per captured batch size, so the rule can only depend on batch size. Decode: half of vLLM's threshold; short queries: vLLM's.
3. **Split-KV segments:** 1,534 + 880 batches; segments 4–128 × 6 launch configs; head 64–512, GQA 3–16, KV heads 1–8, sliding windows, fp8. The best count follows requests × KV heads (about 128 programs), in both directions.
4. **Against `ROCM_ATTN`, through the backend:**
   - every HIP-kernel layout (4,245 batches);
   - a head-64 decode sweep: 16 launch variants × 256 batches (found the head-64 2D decode config: 1 warp);
   - a 1-warp sweep over every remaining regression cluster: 12 variants × 538 batches (chose 2 warps for split-KV; 1 warp lost everywhere except head-64 2D decode and short sliding windows).

**Final A/B: upstream vs this PR** (the results below).
- Two checkouts of the same vLLM build: upstream (`dde9aca41c`, this PR's base) and this PR.
- For every config and batch, each tree runs the backend it selects by default. Speedup = upstream time / PR time (> 1: this PR is faster).
- 14,608 batches; KV caches above 4 GB are skipped.

| region | what |
|---|---|
| `hip` | every layout where `ROCM_ATTN` uses its HIP decode kernel: head 128, block 16, bf16/fp16, GQA 3/4/5/6/8/10/12/16 × KV heads 1/2/4/8, plus softcap. Decode 1–64 requests × 1k–128k |
| `nonhip` | plain attention elsewhere: head 64/96/128/192/256/512 × GQA 1–16 × block 16/528, bf16/fp16 |
| `variants`, `fp16_variants` | sliding window 2048, sinks, sliding window 128 + sinks (gpt-oss), softcap, ALiBi; bf16 and fp16 |
| `fp8` | fp8 KV cache, plain and sliding window, head 64–512, block 16/528 |
| `prefill_mixed`, `qlen`, `spec` | prefill (128–8192 tokens, chunks on 16k–128k), mixed batches, query lengths 9–128, spec-decode verification (2–8 tokens) |
| `lowfill_3d`, `highconc` | 1–16 requests at every head size and block size (incl. 64k); 7–256 requests around the 2D/3D switch |
| `swa_decode`, `gptoss`, `blocksizes` | sliding windows 256–4096 (incl. Muse Glimmer); gpt-oss shapes; block 32/64 |

| family | batches |
|---|---|

| spec decode | 2–8 new tokens per request |

Causes, by cluster:
- **softcap:** the cost of the tanh softcap in the Triton kernel. Only Gemma 2 uses an attention softcap in vLLM (head 256, and head 128 at GQA 2), where this PR is faster; the head-128 GQA 3–16 and head-64 softcap shapes don't occur in supported models;
- **split-KV decode at 1k–4k context:** split / merge overhead when each segment covers few tokens;
- **head-128 2D decode at GQA 1–2, 8–64 requests,** and **head-256 2D decode at 32–64 requests:** `ROCM_ATTN`'s Triton decode kernel is a few percent faster there;
- **fp8 KV, head 64, one fresh 1k–4k prompt:** upstream's prefill reads the new tokens unquantized, while `TRITON_ATTN` reads them back from the fp8 cache.

Causes, by cluster:

- **head-64 2D decode at 128–256 requests:** same, `ROCM_ATTN`'s Triton 2D decode kernel is faster at very high concurrency;
- **fp8 KV, head 64, one fresh 1k–9k prompt:** upstream's prefill reads the new tokens unquantized, while `TRITON_ATTN` reads them back from the fp8 cache (as on gfx1201);
