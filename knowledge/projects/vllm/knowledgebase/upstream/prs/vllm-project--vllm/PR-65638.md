# [ROCm][MiniMax-M3] Mono decode on the NVFP4 KV and index caches

[Upstream PR](https://github.com/vllm-project/vllm/pull/65638) · state: open · merged: False

## Original PR description



## Overview

The ROCm MiniMax-M3 mono decode (`VLLM_ROCM_MINIMAX_M3_MONO=1`: one fused launch per sparse layer for decode steps of <= 16 tokens) now runs on the NVFP4 KV and NVFP4 indexer caches (`--kv-cache-dtype nvfp4`, `"indexer_kv_dtype": "nvfp4"`), the caches of the MiniMax-M3.1-Flash recipe. Before, it refused them and needed fp8 caches.

Not a duplicate: #65196 enables the separate `specialized_decode` FFN launch (`--monokernel`, which does not read the KV cache); #64198 adds MXFP4 caches and keeps mono off.

## Claims

- Mono decode serves the NVFP4 caches. MI355X TP4, M3.1-Flash: decode ITL -26% at 1 request and -13% at 2 requests (DSpark 7) against the stock NVFP4 path, on par with fp8-KV mono; gsm8k unchanged.
- The mono kernels' FlyDSL JIT cache key now covers the KV-cache geometry (page stride, static scale, format). Before, two configurations sharing a cache dir loaded each other's binary: an fp8-KV server ran an NVFP4 build (`VLLM_ROCM_MINIMAX_M3_MONO_CHECK` residual rel diff ~1 instead of 1e-2).

## Validation

MI355X, TP4, `vllm/vllm-openai-rocm` nightly at 40941f2c4 with this change's Python files, `amd/MiniMax-M3.1-Flash-Quark-MXFP4`:

```
VLLM_ROCM_USE_AITER=1 VLLM_ROCM_USE_AITER_MOE=1 VLLM_ROCM_USE_AITER_FUSION_SHARED_EXPERTS=0 VLLM_USE_V2_MODEL_RUNNER=1 \
VLLM_ROCM_MINIMAX_M3_MONO=1 vllm serve amd/MiniMax-M3.1-Flash-Quark-MXFP4 -tp 4 --block-size 128 \
  --kv-cache-dtype nvfp4 --attention-config '{"indexer_kv_dtype":"nvfp4","indexer_decode_cp":true}' \
  --moe-backend aiter --disable-hybrid-kv-cache-manager --enable-prefix-caching --max-model-len 1048576 \
  --max-num-batched-tokens 32768 --max-num-seqs 32 --compilation-config '{"cudagraph_mode":"FULL_DECODE_ONLY"}' \
  --speculative-config '{"method":"dspark","num_speculative_tokens":7,"attention_backend":"TRITON_ATTN","kv_cache_dtype":"fp8","draft_sample_method":"probabilistic","rejection_sample_method":"synthetic","synthetic_acceptance_length":4.04}'
```

`FULL_DECODE_ONLY` is what this model already runs: without it vLLM logs "Cudagraph mode FULL_AND_PIECEWISE requires piecewise capture, but the loaded model provides neither a compiled submodule nor breakable CUDA graphs. Overriding to FULL_DECODE_ONLY."

**Decode ITL**, N concurrent requests on fixed random-token prefixes (prefix-cached), 1536 output tokens each, 2 rounds, all columns on the same 4 GPUs:

|---|---|---|---|
| 1 (100K) | 2.52 / 2.47 ms | 1.78 / 1.75 ms | **1.83 / 1.83 ms** |
| 2 (63K, 142K) | 2.69 / 2.75 ms | 2.43 / 2.33 ms | **2.36 / 2.41 ms** |

**gsm8k**, lm-eval `local-chat-completions --apply_chat_template`, 5-shot, `max_tokens=12288, temperature=0`, real rejection sampling (`"rejection_sample_method":"block"`), `--max-num-seqs 2` and 2 concurrent requests so every decode step can run mono; both sides at once:

| 1319 questions | mono off | mono on |
|---|---|---|
| flexible / strict | 0.9659 / 0.9666 | 0.9674 / 0.9682 |

Paired per question: 1307 agree, 7 vs 5 flips.

**Layer check** (`--enforce-eager`, `VLLM_ROCM_MINIMAX_M3_MONO_CHECK=1`: every sparse layer run through mono and the original decoder layer on the same input): residual rel diff (median over layers and tokens) 1.0e-2 - 1.4e-2 for 1, 2, 8 and 16 tokens a step and for contexts of 1.5K (unscored), 3K (scored) and 60K (indexer CP) tokens; fp8-KV mono on the unmodified image: 1.04e-2. The cache bytes mono writes differ from the stock insert's in 20% (K), 30% (V), 17% (index) of code bytes, in the same share for 1 and 16 tokens a step (the difference comes from the values: mono's qkv GEMV runs on FP8-requantized weights).

**Tests**: `pytest tests/models/minimax_m3/test_mono_host.py` (38 passed, in the ROCm image); pre-commit. The layer kernel and K1 compile with `FLYDSL_COMPILE_ONLY=1` at 8 / 16 tokens, one and all index heads, NVFP4 and fp8 into one cache dir (16 distinct binaries, no LDS overflow). CI has no gfx950 job that runs these kernels.

**AgentX c16** (the InferenceX agentic trace, first 20 minutes, `synthetic_acceptance_length` 4.04), both sides on the same 4 GPUs one after the other, one run each:

| first 20 min | stock (mono off) | NVFP4 mono (this PR) |
|---|---|---|
| interactivity p50 / p90 (1000 / ITL) | 210.2 / 140.9 | 220.5 / 143.9 (+4.9% / +2.1%) |
| TTFT p50 / p90 | 309 / 923 ms | 309 / 923 ms |
| output tok/s per GPU | 153.5 | 158.7 (+3.4%) |

68.5% of the decode steps hold 1-2 requests and run mono. The per-step gain (-26% / -13%) shrinks per request because a request's ITL also carries other requests' prefill chunks and the steps of 3+ requests; one run each is within a single point's noise.

## Details

- K1 quantizes as `norm_rope_nvfp4_insert` does (4-lane group amax, e4m3 block scale under the layer's global scale, e2m1 codes). V octet dwords (8 tokens of one dim) are assembled in LDS and written by one lane per dword (read-modify-write, no atomics).
- e2m1 x e4m3 is exact in fp16 (|x| <= 2688), so QK and the index scores use fp16 MFMAs on the exact values (q and index q in fp16; the split's fp16 q shares the P buffer, so LDS use is unchanged). PV keeps the FP8 MFMA with `e4m3_rn_satfinite(e2m1 x scale)`, the stock NVFP4 decode's values. Scales: `_k_scale` / `_v_scale`, index 1.
- Page ids are `page128 * 8 + page16` (stride 8), so the block selector is unchanged.
- `VLLM_ROCM_MINIMAX_M3_MONO_CHECK=1` also counts the cache bytes the mono and stock inserts write differently.
- Limitations: V still dequantizes to e4m3 (1 request: 3.7% behind fp8-KV mono). Unchanged: mono refuses piecewise / breakable CUDA graphs, and steps with prefill tokens or more than 16 tokens run the stock path.
