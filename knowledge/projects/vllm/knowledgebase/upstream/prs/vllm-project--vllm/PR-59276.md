# [Feature][KV Connector] Add UMBP distributed mode

[Upstream PR](https://github.com/vllm-project/vllm/pull/59276) · state: open · merged: False

## Original PR description

## Purpose

Adds the **distributed** mode of the UMBP KV connector (RFC #57187): a `umbp_master`
indexes KV objects cluster-wide, and every vLLM worker is a pool node that serves its
host-DRAM slice to peers over MORI-IO RDMA. Any engine attached to the master reuses
KV stored by any other, on the same host or another one.

**Stacked on the standalone PR (#59275) and #58568**, rebased onto #58568's current
head `37832fa99`. Please review only the last two commits:

- `[UMBP] Add distributed mode backed by a cluster-wide master` - runtime, option
  validation in the adapter, docs (`docs/features/umbp_distributed.md`), unit and
  real-RDMA tests.
- `[UMBP] Treat objects that just failed to load as misses for a while` - workers
  report failed load keys, and the scheduler treats them as misses for
  `load_failure_quarantine_ms` (30 s in distributed mode, off elsewhere). Without it
  a crashed node's objects caused 691 load-fail/reschedule cycles for one request
  until the master expired the node. Loads refused without being attempted are not
  quarantined.

The rebase dropped `[UMBP] Keep a timed-out store's source pinned until MORI
returns`: #58568's new worker already keeps stores pending across steps under a
store event, and the runtime-side stall handling moved into the standalone PR's
shared-pool worker handle, which this mode reuses.

## Design

- Scheduler lookups use a MORI client with no pool, no I/O engine and no peer service,
  so the scheduler allocates nothing and the master never places objects there.
- Each worker registers under a unique identity (host, GPU, pid, random suffix) and
  binds `peer_service_port + physical GPU index`.
- Lookups are bounded by `lookup_timeout_ms`: MORI's lookup RPC has no deadline, and a
  hung master would otherwise stall the scheduler.
- Resetting one engine does not clear the cluster pool.
- Failure of the master, a peer, or a transfer degrades to recomputation
  (`kv_load_failure_policy=recompute`).

## Test Plan

- Unit: fake master/node cluster, `tests/v1/kv_connector/unit/test_umbp_distributed.py`.
- Integration with a real `umbp_master` and two RDMA pool nodes on two GPUs:
  `tests/v1/kv_connector/umbp_integration/test_mori_distributed_gpu.py` (byte-exact
  cross-node restore, node exit, master loss / restart / SIGSTOP). Peer ports are
  now drawn below the ephemeral range so concurrent suites cannot take them.
- Multi-host MI355X e2e (Pollara RDMA) and Kimi-Linear GSM8K, see below.

## Test Result

- This head: unit 281 passed on this branch (282 on the full stack); integration 19
  passed, 1 skipped (needs four GPUs).
- Measured on the pre-rebase head (same runtime code), not yet repeated on this head:
  - Two-host e2e: 37/37 (Qwen3-0.6B); greedy outputs identical to cold computation;
    99.2% of prompt tokens restored externally on average.
  - Three engine hosts plus a master host, Kimi-Linear GSM8K (1319 questions, conc
    64): cold on host 1 89.23%, RDMA hits from host 2 88.78%, host 3 reading host 2's
    replicas after host 1 is stopped 88.93%, a fresh host-1 engine reading host 3's
    copies after host 2 is killed 88.86%; zero failed loads.

## Known limits

- On NICs with small translation caches (AMD Pollara), host memory beyond a few GiB
  registers only when backed by reserved 2 MiB hugepages
  (`dram_use_hugepages=true` plus `vm.nr_hugepages`); MORI aborts the worker when a
  registration fails. The same limit blocks Mooncake's segment registration.
- MORI fixes proposed separately: master RPC deadlines, re-registration of expired
  nodes, reconnect backoff.

Draft until the stack below it lands.

host:

| Phase | Hits come from | Accuracy | External hit tokens | Same answer as baseline |
| --- | --- | --- | --- | --- |
| baseline (no connector) | - | 88.86% | - | - |
| host 1 cold | - | 89.23% | 0 | 1265/1319 |
| host 2 replay | host 1 over RDMA | 88.78% | 245760 | 1252/1319 |
| host 1 stopped; host 3 replay | host 2's copies only | 88.93% | 245760 | 1261/1319 |
| host 2 `kill -9`; fresh engine on host 1 | host 3's copies | 88.86% | 245760 | 1257/1319 |

Replicas made by readers (`cache_remote_fetches`) keep objects served after their
writer leaves; every phase stays within the cold run's spread. No tracebacks besides
shutdown, no RDMA registration failures.
