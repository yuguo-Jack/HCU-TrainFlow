# [Attention] FA4 hd512 GQA on Blackwell for DiffusionGemma

[Upstream PR](https://github.com/vllm-project/vllm/pull/60158) · state: open · merged: False

## Original PR description

## Overview

Run DiffusionGemma's head-size-512 global attention layers on FA4 on Blackwell (SM100/SM110) instead of the Triton fallback. The vLLM side of vllm-project/flash-attention#204: this PR bumps the `vllm-flash-attn` pin to that PR's commit, so it must not merge before #204 does (the pin will be re-pointed at the merged commit).

## Claims

- On B300, the hd512 global-layer attention kernel takes 80 µs instead of Triton's 658 µs (k = 8256, page 128; 101 µs vs 662 µs with page 16).
- End to end, DiffusionGemma-26B-A4B on one B300 goes from ~947 to 1152–1206 block tok/s (+22–27%), with unchanged GSM8K accuracy within noise.
- FA4 is selected for d = dv = 512 on SM100/SM110 only, and falls back to FA2 for features the hd512 kernel lacks.

## Validation

End to end: DiffusionGemma-26B-A4B, BF16, TP1, one B300, concurrency 1. Workload and client from sgl-project/sglang#42099's reproduction gist (8k input, 1024 output positions, 96 requests). Default backend auto-selection puts the hd256 sliding layers on TRITON_ATTN (mm_prefix) and, with this PR, the hd512 global layers on FLASH_ATTN.

| | Block tok/s | Mean end-to-end | First block | GSM8K (128 questions) |
| --- | ---: | ---: | ---: | ---: |
| Triton (main) | ~947 | 1.36 s | 0.55 s | 126/128 |
| FA4 hd512 (this PR) | **1152–1206** (3 runs) | 1.03–1.07 s | 0.39–0.42 s | 125/128 |

Denoising steps per canvas are unchanged (~20); the run-to-run spread tracks step count (20.2–20.9). The GSM8K difference is a single question flip: small numerical changes alter adaptive denoising trajectories.

Tests (B300, with the flash-attention sources from #204):

```
pytest tests/kernels/attention/test_mixed_causal_attn.py      # 9 passed, 4 skipped (SM90-only FA4 cases)
pytest tests/kernels/attention/test_attention_selector.py -k "hd512 or hd256"   # 37 passed
```

- `test_flash_attn4_hd512_mixed_causal` (new, SM100): 16 query / 2 KV heads, d = 512, a batch mixing causal and bidirectional sequences (plus all-causal and all-bidirectional) through `split_dynamic_causal` and `flash_attn_varlen_func(seqused_q=...)`, against the existing reference.
- `test_fa4_hd512_fallback_matrix` (new): FA version selection for hd512, covering SM100 vs SM120, mismatched `head_size_v`, sinks, softcap, FP8 KV cache, DCP, R-SWA, and mm_prefix with and without `is_diffusion`.

CI gap: `tests/kernels/attention` runs on L4 in CI, so the selector cases run there but the SM100 kernel test skips (no B200 attention-kernel job); it was run locally on B300 as above. The flash-attention side has its own tests (130 passed on B300); see #204.

## Details

- **Pin bump** (`cmake/external_projects/vllm_flash_attn.cmake`): to #204's head. Besides #204, this picks up flash-attention #198 (SM90 SplitKV fix, which #59436 also bumps for), #195 and #200 (SM100 sparse MLA decode); those only add optional arguments and a new decode kernel.
- **Selection** (`fa_utils.py`): `uses_fa4_hd512_kernel` mirrors `uses_fa4_hd256_kernel` (d = dv = 512 on SM100/SM110). FA4 is kept for those shapes past the TMEM head-size gate, and `_fa4_hd512_fallback_reason` drops to FA2 for sinks, softcap, quantized KV cache, mm_prefix (except diffusion models, which use a per-sequence causal flag instead), R-SWA and DCP.
- **Per-sequence causal on SM100** (`flash_attn.py`): DiffusionGemma passes a per-sequence causal flag, and FA4's `dynamic_causal` is SM90-only. On other architectures the backend now issues two launches, one causal and one non-causal, each restricted to its own sequences with `seqused_q` (`split_dynamic_causal`, a module-level helper so the kernel test can drive the same split). The split is device-only (no host sync), and costs one extra launch per hd512 layer, already included in the e2e numbers. SM90 keeps the single `dynamic_causal` launch. A per-sequence causal flag combined with a sliding window still requires SM90 and raises otherwise (DiffusionGemma's windowed layers run on Triton).
- **Wrapper** (`flash_attn_interface.py`): passes `seqused_q` through to FA4.

Not a duplicate: open PRs touching this area are #45434 (SM90 FP8 KV cache for hd512) and #59436 (pin bump to the SM90 SplitKV fix, which this pin includes). None route hd512 to FA4 on Blackwell or split per-sequence causal for SM100.

### Should fix: re-pin flash-attention

`cmake/external_projects/vllm_flash_attn.cmake:42` pins `160e64ca07` (vllm-project/flash-attention#204's head). At that commit, the hd512 route stores O past the end of each varlen sequence when there is one query head per KV head (finding 1 in my review on #204). DiffusionGemma does not hit this: its hd512 layers have 16 query heads and 2 KV heads, so per rank they run at 16/2, 8/1, 4/1 and 2/1 from TP1 to TP8. But the selector sends every SM100 hd512 layer to this route without checking the ratio, so any hd512 model with as many KV heads as query heads per rank would get wrong output silently. The two-pass `seqused_q` split in this PR makes it worse: one pass can overwrite rows that belong to the other pass.

The fix is https://github.com/simon-veitner-redhat/flash-attention/commit/025558df8d9d9a6b9331c35421566f327d594d12. Please re-pin to a commit that includes it, or to #204's merge commit once it has the fix.

### Should fix: the head_size > 256 fallback to FA2 cannot run

`_fa4_hd512_fallback_reason` (`fa_utils.py:265`) sends hd512 to FA version 2 for sinks, softcap, R-SWA, DCP and non-diffusion mm_prefix (and SM12x gets FA2 too). FA2 only supports head_size ≤ 256 (`csrc/flash_attn/flash_api.cpp:658` in flash-attention). The selector does not catch it:
- `supports_head_size` accepts 512 whenever FA4 is installed.
- `supports_combination` (`flash_attn.py:466`) re-checks the FA version only for mm_prefix.

So FLASH_ATTN stays selected, and the first forward fails with `FlashAttention forward only supports head dimension at most 256`. That is the error main gives today when Gemma 4 is forced onto FLASH_ATTN.

This is not a regression, and DiffusionGemma's default path is not affected. I found it by reading the code. fp8 KV cache and `VLLM_BATCH_INVARIANT=1` already land on Triton at the PR head.

Fix: https://github.com/simon-veitner-redhat/vllm/commit/0f6f0b221c13444d84dd6bf230d85f9b192ad698 (branch `review/vllm60158-hd512-gates`, on top of this PR's head `e5f17e34e3`, +49/-32):
- `supports_combination` rejects FLASH_ATTN when head_size > 256 and FA4 does not resolve, so selection moves on to another backend.
- The warning no longer says it defaults to FA2.
- The selector tests cover the deselection cases (sinks, softcap, fp8 KV cache, DCP, sliding window, SM120).
- `test_flash_attn4_hd512_mixed_causal` adds uneven query lengths that are not multiples of 64, and prefills the output with NaN so unwritten rows fail.

With both fix commits, DiffusionGemma end to end is perf- and quality-neutral vs this PR: D1 -0.2%, P1 +0.7%, GSM8K 0.9272 vs 0.9265. The logs still show hd512 on FA4 and hd256 on Triton.

### Notes

- **Please add SM100 hd512 entries to `get_warmup_keys`** (`flash_attn.py:145`), covering both split variants (`seqused_q` / causal mode). It has keys for SM100 hd256 and SM90 hd512 only, and `CompileKey` has no `seqused_q` or causal-mode dimension, so both variants compile on the first real batch. The first PR server start took 641 s of engine init vs 204 s for base. Later starts took 202–222 s with a warm cache.
- **Nits:**
  - `split_dynamic_causal` (`flash_attn.py:286`, called at `:1475`) recomputes the split for every hd512 layer on every step. It could be built once in `FlashAttentionMetadataBuilder.build()`, as `rswa_window_tensor` is.
  - `_fa4_hd512_fallback_reason` (`fa_utils.py:265`) is a near copy of `_fa4_hd256_fallback_reason` (`:296`). A shared helper would keep the two lists from drifting.

**Not covered:** TP>1 end to end. The equal-heads spill was tested at the kernel level only.
