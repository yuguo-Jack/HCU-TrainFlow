# [Perf] Reduce multiprocess decode logging CPU by 28%

[Upstream PR](https://github.com/vllm-project/vllm/pull/60498) · state: open · merged: False

## Original PR description

## Overview

A decode iteration can increment nine Prometheus counters by zero. With the multiprocess mmap backend, each call still takes a lock and writes the value. This change skips those writes in the stats logger.

## Claims

- **28% lower CPU time** for complete multiprocess decode logger calls: **3.64 s → 2.62 s** in the benchmark below.
- Zero-valued series, positive increments, label checks, and exemplar behavior are preserved.

## Validation

The benchmark runs complete `PrometheusStatLogger.record` calls on one CPU core. Each call records four generated tokens and four token latencies. Each version has 100 warmup calls and three timed runs of 30,000 calls.

| Counter backend | Baseline CPU median (range) | Patch CPU median (range) |
| --- | --- | --- |
| Multiprocess mmap | 3.64 s (3.40–4.36) | 2.62 s (2.59–3.17) |
| Standard mutex | 0.79 s (0.78–0.79) | 0.80 s (0.78–0.88) |

Live checks used Qwen3-0.6B on one L4 and one CPU, with the real mmap backend. All 40 responses matched text, token IDs, finish and stop reasons, and usage. Streaming chunks and generation-token totals also matched. Request-time medians were 15.711 s and 15.730 s. API CPU medians were 0.775 s and 0.855 s, with overlapping ranges of 0.65–1.44 s and 0.74–1.68 s. The patch API CPU median was 10.3% higher. These results do not confirm lower whole-API CPU cost or request time; the 28% claim applies to logger calls.

Tests run:

```bash
.venv/bin/python -m pytest tests/v1/metrics/test_engine_logger_apis.py -q -k zero_counter
.venv/bin/python -m pytest tests/v1/metrics/test_histogram_buckets.py tests/v1/metrics/test_stats.py -q
```

**31 native tests passed**: two counter tests, 14 histogram tests, and 15 stats tests. Full logger comparisons matched all 644 non-creation-timestamp samples across idle, decode, prefill, multimodal-cache, and completed-request cases on both backends. Counter contract checks passed 28 amount/exemplar cases on each of Prometheus client 0.18.0 and 0.26.0. Local pre-commit and Python 3.12 mypy checks passed. Upstream test CI is blocked by the contributor gate.

After the main update, all applicable pre-commit hooks passed. CPU source checks with Prometheus client 0.26.0 passed 28 counter-contract comparisons on each backend. The new admission counters also preserved zero-valued series and positive increments. Custom counter selection was preserved. These checks use exact source snippets and the real SDK; they do not run full vLLM logger initialization or serving. No new speed result or GPU/model run is claimed.

## Details

Open PR searches found no other fix that skips zero-valued multiprocess counter increments. [#60001](https://github.com/vllm-project/vllm/pull/60001) and [#60038](https://github.com/vllm-project/vllm/pull/60038) initialize gauges. This change reduces repeated counter writes after series initialization.

`MultiprocessCounter` returns early for a zero increment without an exemplar, after checking label values. Other calls use the SDK's `Counter.inc`. The logger selects this class only for the standard counter type with the multiprocess backend. The normal mutex backend and custom classes, including the Ray wrapper, keep their current implementations. Series are still created during label initialization.

The extra check also runs on positive multiprocess increments. The complete logger benchmark includes that cost. The change uses the existing logger module and test suite.
