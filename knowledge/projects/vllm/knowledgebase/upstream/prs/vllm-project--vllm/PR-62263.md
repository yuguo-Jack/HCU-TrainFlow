# [Bugfix][Tool Parser] Coerce only canonical JSON number spellings

[Upstream PR](https://github.com/vllm-project/vllm/pull/62263) · state: closed · merged: False

## Original PR description

## What

Fixes #62252. `coerce_to_schema_type` tries `integer`/`number` before `string`, and Python's `int()`/`float()` accept spellings that are not valid JSON numbers: leading zeros (`0017` becomes 17), underscores (`1_000` becomes 1000), and a leading `+`. For a schema admitting both string and a numeric type (`"type": ["string", "integer"]` or the equivalent `anyOf`), a string value that merely looks like an integer reaches the client rewritten, and quoting does not help, so no model output can deliver the string `0017` at all. Leading zeros and similar spellings carry meaning for identifiers, ZIP codes, account numbers and version components.

## How

Both numeric branches now gate on the RFC 8259 number grammar (`-?(0|[1-9]\d*)` for integer, with the fraction/exponent extension for number) before calling `int()`/`float()`. Non-canonical spellings stay strings, including under a number-only schema (a lossy rewrite is worse than a type mismatch the client can see and reject). Canonical forms are unchanged: `"17"` still coerces, aliases (`int`, `long`, `uint32`, ...) still work, the whole-float-returns-int rule and the non-finite guards are untouched, and `null`/boolean/object/array/string paths are not affected.

The helper backs the qwen3_coder/qwen3_xml/mimo parsers named in the issue and every other caller (dots, k2_horizon, minimax_m3, the parser engine), so all of them pick up the fix.

## Tests

New cases in `tests/tool_parsers/test_utils.py`: `0017`/`1_000`/`+17` stay strings under a mixed schema and under integer-only, `0017.5`/`1_000.5` under number, and canonical spellings still coerce. Verified locally on CPU (macOS, no GPU): the new tests fail against the unpatched helper and pass patched; the full file is 178 passed with no regressions. The repo's conftest global-cleanup fixture segfaults in this environment's torch build during teardown (pre-existing, native, unrelated to this change), so the file was also run isolated from it for a clean signal.

Closing as a duplicate of #62254, which was filed two hours earlier with the same root cause (non-canonical spellings like `0017` reaching `int()`/`float()` before `string` is considered).

The approaches differ slightly: theirs keeps a numeric-looking string when it does not round-trip through `str()`, mine grammar-checks canonical JSON numbers. The only divergence I found is canonical-but-unusual spellings such as `1e-5` (Python pads the exponent to `1e-05`, so the round-trip rule keeps them as strings even though they are valid JSON numbers) — a minor corner that does not justify a second open PR. If a grammar-exact check is ever preferred, the branch stays available.
