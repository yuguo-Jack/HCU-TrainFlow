# [Perf][MoE] OCP MX emulation: dequantize only the routed experts

[Upstream PR](https://github.com/vllm-project/vllm/pull/64406) · state: open · merged: False

## Original PR description



## Overview

On GPUs without native OCP MX support (e.g. MI250X), MXFP4/MXFP6 MoE layers run through `OCP_MXQuantizationEmulationTritonExperts`, which dequantizes every local expert to bf16/fp16 on every forward. A decode batch usually routes to a small fraction of the experts, so this PR dequantizes only the routed ones when they are at most a quarter of the local experts. Related, touching the same class but not this path: #43983 (oracle test coverage), #52868 (`a2_scale` forwarding).

Related prior work: #40055 by @ekuznetsov139 (open since April) applies the same idea to this class for single-token decode (batch 1, no EP, no biases), using a fixed-size sort so it also works under CUDA-graph capture. This PR covers multi-token batches up to a quarter of the local experts but falls back to the full path under capture, so the two overlap only at eager batch 1. I'm happy to fold #40055's capturable batch-1 path in here with credit, or to rebase onto it if it lands first, whichever reviewers prefer.

## Claims

- When a batch routes to at most a quarter of the local experts, `apply` gathers the routed experts' packed weights and scales, dequantizes only those, and renumbers `topk_ids` onto the gathered set (`torch.unique(..., return_inverse=True)`).
- The output is unchanged: each token is multiplied by the same dequantized expert weights. The test checks this with `torch.equal`.
- Past a quarter, for an empty batch, under CUDA-graph capture, and with an `expert_map` (EP), LoRA experts or w1/w2 biases, the existing full dequantization runs unchanged.
- One MoE layer of a 256-expert MXFP4 model at TP8 on MI250X: 6.6 ms per call before, 1.5 ms with 8 routed experts (c=1), 2.3 ms with 31 (c=4). This is a microbenchmark; see Validation.

## Validation

**Microbenchmark, MI250X (gfx90a), one MoE layer** of a large 256-expert MXFP4 MoE model at TP8, measured on a GCD that was busy with other work (the routed rows include the gather):

| routed experts | time per call |
|---|---|
| all (main) | 6.6 ms |
| 8 (c=1 decode) | 1.5 ms |
| 31 (c=4) | 2.3 ms |
| 100 (gather forced) | 6.2 ms |
| 225 (gather forced) | 15.5 ms |

The last two rows were measured with the gather forced, to pick the threshold. With 256 experts the threshold is 64, so this PR sends both to the full path. The layer output was bit-identical in every row.

**No end-to-end number.** This change has not been served end to end on this base. Before the change, c=1 decode of that model (TP8 x PP3) ran at about 2.4 tok/s.

**Test**, `tests/kernels/moe/test_ocp_mx_emulation_routed.py` (ROCm only): a real MXFP4 emulation MoE forward with 32 experts. A spy on `_dequantize_weights` records how many experts each call dequantizes; the test then forces the full path (capture flag patched on) and compares outputs with `torch.equal`. Two cases: 4 tokens routed to 5 experts (routed path), and 5 tokens routed to 9 experts, past the threshold of 8 (full path).

## Details

**Host sync.** Outside graph capture, this change adds one `torch.unique` per MoE layer per forward, which synchronizes with the host. It runs before the threshold check, so batches that end up on the full path pay it too. Captured decode graphs are not affected: under capture the full path runs, as it does today. So the gain applies to eager mode and to batches that fall outside the captured sizes. Making the routed path capturable would need a fixed-size gather (e.g. `topk_ids.numel()` slots), which I left out to keep this change small.

**Threshold.** A quarter of the local experts is where, on MI250X, the gather and renumbering cost about as much as the dequantization they save (the 100-expert row above is already at parity with the full path). It is a constant in `apply`, not a config knob.

**Why not EP/LoRA/bias.** With an `expert_map` the ids are global and would need remapping before the gather; LoRA and biases index per-expert tensors that the gather does not cover. These cases keep the full path rather than growing this change.
