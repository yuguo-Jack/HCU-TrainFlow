# [Bugfix] Don't split a multimodal item that a prefill chunk starts exactly on

[Upstream PR](https://github.com/vllm-project/vllm/pull/52412) · state: closed · merged: True

## Original PR description

FIX #52306

## Purpose

Under `disable_chunked_mm_input=True` the scheduler still splits a multimodal item when the chunk begins exactly on it.

`_try_schedule_encoder_inputs` guards the split with

```python
self.scheduler_config.disable_chunked_mm_input
and num_computed_tokens < start_pos                                            # (A)
and (num_computed_tokens + num_new_tokens) < (start_pos + num_encoder_tokens)  # (B)
```

(A) is false when `num_computed_tokens == start_pos`, so (B) never runs and a chunk too small to cover the item is allowed through. That equality is not an exotic state — it is exactly what the guard itself produces: the rollback sets `num_new_tokens = start_pos - num_computed_tokens`, so the next step starts on the item. If the budget cannot fit the whole item on that step, the item is split at the precise point the flag exists to prevent. For models with bidirectional attention over the item, the tokens that should cross-attend silently cannot.

The fix is `<=` in (A). Only the equality case changes:

- `num_computed_tokens < start_pos` — unchanged, rolls back to just before the item.
- `num_computed_tokens == start_pos` and the chunk does not cover the item — now yields `num_new_tokens = 0`, so the request waits for a step that can fit it. This matches the neighbouring `can_allocate` branch, which already returns 0 rather than scheduling a partial item.
- `num_computed_tokens > start_pos` (prefix caching landing mid-item) — unchanged.

Returning 0 cannot starve the request: `_verify_args` already rejects a `max_num_batched_tokens` smaller than the longest multimodal item when this flag is set (`test_no_mm_input_chunking` asserts that `ValueError`), so a step that can fit the item always exists.

## Test Plan

`tests/v1/core/test_scheduler.py::test_no_mm_input_chunking_at_item_boundary` drives `_try_schedule_encoder_inputs` on a real scheduler and request (mm item at offset 400, length 800) across the three cases: starting before the item, starting on it without room, and starting on it with room. The existing `test_no_mm_input_chunking` only exercises the first, which is why this went unnoticed.

Verified this against the reachable-state analysis from #52306 — the fix is correct and the test assertions trace exactly through the real `_try_schedule_encoder_inputs`. I did the verification by reading the function at this PR's head and replaying the guard arithmetic (item `[400, 1200)`, `shift_computed_tokens=0`); I did not run the suite locally, so treat this as logic-level confirmation.

**The only behavioral delta is the equality row**, which is the bug:

| nct | nnt | old (`<`) | new (`<=`) | |
|---:|---:|---:|---:|---|
| 0 | 500 | 400 | 400 | unchanged |
| 399 | 2 | 1 | 1 | unchanged |
| 400 | 500 | **500 (split)** | **0** | the fix |
| 400 | 799 | **799 (split)** | **0** | the fix |
| 400 | 800 | 800 | 800 | covers the item, unchanged |
| 401 / 800 | 500 | 500 | 500 | prefix-cache resume inside item, untouched |

Three things I checked beyond the boundary itself:

1. **The rollback can't go negative.** With `num_computed_tokens == start_pos` the new branch computes `max(0, start_pos - (num_computed_tokens + shift_computed_tokens))`, which is 0 (or stays 0 under an EAGLE shift), so the request simply waits for a step with enough budget. `num_new_tokens = 0` is already an established return from the `can_allocate` failure branch just below, so callers handle it.
2. **The prefix-caching resume path is untouched.** `num_computed_tokens > start_pos` fails `<=` exactly as it failed `<`, so resuming inside an item behaves identically.
3. **No starvation risk from the newly-guarded case.** An item that can never fit in `max_num_batched_tokens` is rejected at config time (the existing `ValueError` covered in `test_no_mm_input_chunking`), so the equality case always gets a budget that can cover it eventually.

The regression test earns its keep: `ask(400, 500) == 0` fails on the old code (returns 500, splitting the item), and `ask(400, 800) == 800` pins the "exactly covers" boundary so `<` can't sneak back in via off-by-one on the other side. LGTM from my read.


- lindicaphxag-tech · COMMENTED · 2026-10-04T16:56:46Z · [source](https://github.com/vllm-project/vllm/pull/52412#pullrequestreview-5407246881)

I traced this against the current scheduler path and the later reproductions on #52306. The `<=` change is necessary for decoder-only multimodal inputs, but I think this PR still needs two contract fixes before it is safe to merge:

1. **Encoder-decoder must be excluded explicitly.** For encoder-decoder models `start_pos == 0` is a marker for encoder work, not a decoder-token interval. The old strict `<` accidentally kept these models out of the guard. With `<=`, the guard can roll back valid encoder-decoder scheduling to zero; the later #52306 analysis reports failures in `test_cross_attn_blocks_not_over_allocated`, `test_cross_attn_blocks_not_under_allocated`, and `test_variable_length_cross_attn_block_allocation`. I think the condition should make the intended domain explicit, e.g. `not self.is_encoder_decoder and ... <= start_pos ...`, rather than relying on the inequality to encode that distinction.

2. **The no-starvation argument in the PR body is incomplete.** `max_num_batched_tokens >= max_tokens_per_mm_item` only proves that *some* step budget can fit the item. The scheduler applies `long_prefill_token_threshold` before `_try_schedule_encoder_inputs`; if that threshold is nonzero and smaller than the unsplittable MM item, the request can be parked exactly at `start_pos` and receive zero tokens on every contended step. The adaptive threshold does not guarantee safety either: `max(configured_threshold, input_budget // num_eligible_reqs)` can still be below the item for sufficiently many eligible requests.

There is already a natural fail-fast point: `compute_mm_encoder_budget()` knows `max_tokens_per_mm_item` and currently rejects `disable_chunked_mm_input` when the item exceeds `max_num_batched_tokens`. Extending that validation to reject a nonzero `long_prefill_token_threshold < max_tokens_per_mm_item` would make the invariant satisfiable instead of turning the silent split into a possible permanent zero-token wait.

So the stronger invariant I would test is: **for decoder-only MM requests with chunking disabled, every scheduler step either stops before an MM item or covers that item completely; configurations whose per-request prefill cap can never cover the item fail at initialization.**
