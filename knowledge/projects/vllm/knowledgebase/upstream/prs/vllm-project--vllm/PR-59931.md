# [Bugfix] Preserve fp16 in legacy fused MoE LoRA

[Upstream PR](https://github.com/vllm-project/vllm/pull/59931) · state: closed · merged: True

## Original PR description

## Overview

Fixes #59920. Preserve the input dtype in the legacy fused MoE LoRA GEMM instead of unconditionally converting operands to bfloat16.

## Claims
 Prevents silent fp16-to-bfloat16 conversion in the legacy shrink/expand kernel.
Keeps both Triton descriptor and pointer-load paths aligned with the hidden-state input dtype.
Extends large-rank fallback correctness coverage to fp16 and bf16.

## Validation

 `uv run --no-sync ruff check vllm/lora/ops/triton_ops/fused_moe_lora_op.py tests/lora/test_fused_moe_lora_kernel.py`
 `uv run --no-sync ruff format --check ...`
 `uv run --no-sync python -m compileall -q vllm/lora/ops/triton_ops/fused_moe_lora_op.py tests/lora/test_fused_moe_lora_kernel.py`
 The focused Triton test collection/execution could not run in this Windows CPU-only environment: vLLM native extension and `uvloop` are unavailable. CI or an Intel/NVIDIA/AMD GPU runner must execute `tests/lora/test_fused_moe_lora_kernel.py`.
 No kernel benchmark was claimed; this is a correctness fix.

## Details

The legacy two-kernel path previously cast both dot operands to `tl.bfloat16` to work around ROCm type inference across TMA and pointer-load branches. That changes fp16 LoRA arithmetic and can produce incorrect outputs. The kernel now derives the dot dtype from the input pointer element type and casts both operands to that type. The large-rank fallback test is parameterized over the existing fp16 and bf16 dtype matrix.
