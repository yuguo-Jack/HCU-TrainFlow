# [ROCm][Perf] Insert MiniMax-M3 sparse-PA K/V without a contiguous copy

[Upstream PR](https://github.com/vllm-project/vllm/pull/56849) · state: closed · merged: True

## Original PR description

## Summary

- Pass the strided K/V slices straight to AITER `reshape_and_cache` on the MiniMax-M3 sparse-PA path instead of calling `.contiguous()` on them first.
- Add `_kv_insert_operand`, which returns the tensor as-is when the kernel's layout requirements are met and copies otherwise.
- No kernel change, no AITER dependency, no new env var, no change to the NVIDIA path.

## Motivation

`MiniMaxM3SparseAttention._insert_aiter_sparse_pa_kv` gets K and V as column slices of the fused `[q | k | v | index_q | index_k]` projection. Column slices are strided, so they are never contiguous, and the two `.contiguous()` calls copy both tensors on every sparse layer of every forward pass.

Those copies are not needed. `reshape_and_cache` already takes the row pitch as a kernel argument and indexes with it (AITER `csrc/kernels/cache_kernels.cu`):

```cpp
int key_stride = key.stride(0);
...
const int64_t src_key_idx = token_idx * key_stride + i;   // i over num_heads*head_size
```

In other words the kernel does not care how far apart two tokens are, only that each token's heads sit next to each other in memory. A `qkv[:, a:b].view(n, H, D)` slice is always laid out that way, whatever `H` is, which is why the copy buys nothing.

`_kv_insert_operand` skips the copy only when it can confirm that layout, and copies in every other case: a tensor of a different rank, one whose heads are not back to back, or one where tokens are so far apart that the gap would not fit in the kernel's `int` stride argument. So the worst case is the behaviour we have today.

## Existing work and non-duplication

- #53833 (with ROCm/AITER#4813) routes to a new fused AITER op and says it will "retain the existing vLLM preprocessing plus `reshape_and_cache` / index-scatter path when an older AITER build does not provide the operation". This PR fixes that retained fallback, so the two do not overlap and can land in any order.
- #54535 (with ROCm/AITER#5143 and #52664) integrates the consolidated AITER QK-norm op and falls back the same way.
- #55007 was the closest in spirit, a small vLLM-only change in this same function, and it states that "the main K/V cache writer remains AITER `reshape_and_cache`; this PR changes only the BF16 index-cache insertion boundary". It left the K/V boundary alone, which is what this PR covers.
- #54682 and #54681 are about the decode indexer and top-k, not cache insertion.
