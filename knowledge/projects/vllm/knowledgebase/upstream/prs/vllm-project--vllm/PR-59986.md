# [Bugfix][Attention] Keep DSV4.1 sparse prefill out of FULL cudagraphs

[Upstream PR](https://github.com/vllm-project/vllm/pull/59986) · state: closed · merged: True

## Original PR description



## Overview

Fixes #59970. Fixes #62417. The five DSV4.1-specific sparse metadata builders declare `AttentionCGSupport.ALWAYS`, so with `cudagraph_mode=FULL_AND_PIECEWISE` prefill and mixed batches get FULL-graph captured even though their prefill metadata is not graph-safe, and the engine dies with an illegal memory access once adaptive verification runs mixed batches at concurrency. Downgrade them to `UNIFORM_BATCH` and report the speculation width as the varlen decode bound, mirroring the reviewed pattern from #59751.

## Claims

- Prefill and mixed batches leave FULL capture for all five builders named in #59970: `DeepseekV4FlashMLAMetadataBuilder`, `DeepseekV4FlashInferSparseMLAMetadataBuilder`, `DeepseekSparseSWAFlashInferMetadataBuilder`, `DeepseekSparseSWAFlashMLAMetadataBuilder`, `CompressorMetadataBuilder`. `FlashMLAMegaAttnBackend` inherits the same builder, so it is covered too.
- FULL varlen decode graphs are kept for uniform batches sized up to 1 + num_speculative_tokens, so DSpark adaptive verification keeps its decode graphs.

## Validation

```bash
.venv/bin/python -m pytest tests/v1/worker/test_attn_utils.py -q
```

82 passed on CPU. The 10 new parametrized cases pin, per backend and num_speculative_tokens in {0, 7}, that support resolves to `UNIFORM_BATCH`, that decode widths up to the speculation width stay graph-eligible, and that one token wider is rejected with the reported bound. Changed-file pre-commit (ruff-check, ruff-format) passed.

Not run: the B300 (SM103) end-to-end reproducer from the issue, no compatible hardware available here, and CI does not exercise these builders. The change only narrows what FULL graphs capture: prefill moves to the piecewise path that the issue's adaptive-verification-off and FULL_DECODE_ONLY arms already exercise for 30+ minutes under load, so no batch that was not captured before becomes captured.

## Details

Root cause, from the issue's arm table: adaptive verification on + FULL_AND_PIECEWISE hits the IMA 4/4 within a minute; verification off in the same mode is stable; verification on with FULL_DECODE_ONLY is stable. The failing ingredient is prefill inside FULL graphs. Each affected builder now also overrides `get_varlen_cudagraph_max_query_len` to return `max_decode_query_len(vllm_config)` (1 + num_speculative_tokens on MRV2), the same width the V2 runner uses when it builds varlen decode replays.

Not a duplicate of #59751: that PR changes only the generic `FlashInferMLASparseTRTLLMMetadataBuilder` for #59681, while the DSV4.1 model wires its own five builders, which the #59970 reporter calls out explicitly. Checked the issue thread and open PRs referencing #59970 before starting; nothing else covers them.

One idea to deduplicate code is to introduce a mixin class and reuse it across builders. This mixin could live in `vllm/vllm/v1/attention/backend.py`. 

```python
class VarlenDecodeCGMixin:
    _cudagraph_support: ClassVar[AttentionCGSupport] = AttentionCGSupport.UNIFORM_BATCH
    
    @classmethod
    def get_varlen_cudagraph_max_query_len(
        cls,
        vllm_config: VllmConfig,
        kv_cache_spec: KVCacheSpec,
    ) -> int | None:
        # Decode replays use device request boundaries; prefill metadata is
        # not graph-safe.
        return max_decode_query_len(vllm_config)
```
The attribute `_cudagraph_support` can alternatively be left out of the mixin, then each builder class would define it separately. But setting `UNIFORM_BATCH` seems like a recurring pattern.

Reuse:
```python
class DeepseekV4FlashInferSparseMLAMetadataBuilder(
     VarlenDecodeCGMixin, DeepseekV4SparseMLAMetadataBuilder):
    ...
```
