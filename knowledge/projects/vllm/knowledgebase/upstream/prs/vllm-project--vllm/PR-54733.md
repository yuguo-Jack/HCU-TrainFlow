# [Bugfix][DCP] Recover failed KV loads across hybrid cache groups

[Upstream PR](https://github.com/vllm-project/vllm/pull/54733) · state: open · merged: False

## Original PR description

## Summary

Recover failed external KV loads without treating block IDs from different KV cache groups as one global namespace.

This change carries failed destination blocks as:

```text
request_id -> (group 0 block IDs, group 1 block IDs, ...)
```

The scheduler can therefore preserve the valid common prefix of an asynchronous HMA load while avoiding false matches between equal numeric block IDs in different groups. Connectors that only report a request ID retain the existing conservative fallback and recompute the request from zero.

## Design

- Extend `KVConnectorTransferResults` and `KVConnectorOutput` with request-scoped, group-indexed failed destination blocks.
- Preserve and merge the failure detail across TP workers until the corresponding receive is complete.
- Merge reports from multiple connectors without losing group identity. A group-count mismatch discards the detail and falls back to whole-request recomputation.
- Have NIXL, Mooncake, and Mooncake Store report their destination blocks in cache-group order for HMA loads.
- Resolve each failed block only against the corresponding request and cache group.
- Convert the earliest failed group position to tokens and round down to the scheduler block boundary shared by all groups.
- Keep the existing flat `invalid_block_ids` path unchanged for single-group connectors.

## Failure behavior

- `kv_load_failure_policy=fail`: the affected request retains the existing error behavior.
- `kv_load_failure_policy=recompute`: a detailed HMA failure preserves the request prefix before the earliest failed group block; missing or malformed details fail closed by recomputing from token zero.
- Async destination blocks have not entered the prefix cache, so only the validated prefix is cached when the request leaves `WAITING_FOR_REMOTE_KVS`.
