# [Bugfix][KV Offload] Refresh CPU LRU for GPU-hit prefixes in eager SimpleCPUOffload

[Upstream PR](https://github.com/vllm-project/vllm/pull/62444) · state: open · merged: False

## Original PR description

Draft for early review. No blocking issues.



## Overview

With eager `SimpleCPUOffloadConnector`, a prefix that keeps hitting the GPU prefix cache is the first thing evicted from the CPU cache, because its CPU copy never leaves its first-store LRU position. This PR moves those CPU blocks to the MRU end once per request.

## Claims

- Eager mode keeps hot GPU-hit prefixes on CPU; lazy mode is unchanged.
- Kimi-K3 agentic disaggregated benchmark on MI355X: +9.9% total tok/s/GPU, mean TTFT 9.4 s to 5.6 s.

## Details

Root cause on the prefill instance:

1. Turn 1 computes prefix X; the eager store copies X to CPU.
2. Later turns hit X on GPU. Eager stores skip blocks already on CPU, so X's CPU copy is never touched.
3. Other requests' stores evict CPU blocks in LRU order, so X goes first although it is the hottest prefix.
4. When GPU pressure later evicts X, the next turn misses both tiers and recomputes X.

The fix in `get_num_new_matched_tokens` touches and frees the CPU copies of the GPU-hit full-attention prefix, in reverse order like `SingleTypeKVCacheManager.free`. Mamba states are skipped because the request stores a newer one. The cost is one CPU hash lookup per GPU-hit block, once per request, on the scheduler thread.
