# [Bugfix][KV Offload] Refresh CPU LRU for GPU-hit prefixes in eager SimpleCPUOffload

[Upstream PR](https://github.com/vllm-project/vllm/pull/62444) · state: closed · merged: True

## Original PR description

Ready for review.

## Overview

With eager `SimpleCPUOffloadConnector`, a prefix that keeps hitting the GPU prefix cache is the first thing evicted from the CPU cache, because its CPU copy never leaves its first-store LRU position. When a request with a GPU prefix hit is admitted, this PR moves the CPU copy of that prefix to the MRU end.

## Claims

- Eager mode keeps hot GPU-hit prefixes on CPU; lazy mode is unchanged.
- Kimi-K3 agentic disaggregated benchmark on MI355X at `be4275d22`: +8.7% total tok/s/GPU, mean TTFT 8.6 s to 5.3 s.

## Validation

- `tests/v1/simple_kv_offload/` and the SimpleCPUOffload connector, metrics and NIXL unit tests at `be4275d22`: 179 passed, 8 skipped (optional integration tests). pre-commit clean.

## Details

Root cause on the prefill instance:

1. Turn 1 computes prefix X; the eager store copies X to CPU.
2. Later turns hit X on GPU. Eager stores skip blocks already on CPU, so X's CPU copy is never touched.
3. Other requests' stores evict CPU blocks in LRU order, so X goes first although it is the hottest prefix.
4. When GPU pressure later evicts X, the next turn misses both tiers and recomputes X.

In eager mode, `get_num_new_matched_tokens` records the GPU hit length and `update_state_after_alloc` refreshes that prefix once at admission, so a request waiting for blocks does not repeat the CPU lookup each step. The refresh runs `cpu_coordinator.find_longest_cache_hit` over the prefix, then touches and frees the result in reverse order like `SingleTypeKVCacheManager.free`: every full-attention block, the sliding window and the Mamba state at the boundary.
