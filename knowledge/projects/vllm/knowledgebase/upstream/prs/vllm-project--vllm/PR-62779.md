# [Bugfix] Fix out-of-bounds block-table read in Triton unified attention

[Upstream PR](https://github.com/vllm-project/vllm/pull/62779) · state: open · merged: False

## Original PR description

## Overview

Fixes #61803. Sometimes the KV tile is wider than the KV block, for example the 32-wide prefill tile with block size 16. Then `kernel_unified_attention` reads block-table entries past the end of the sequence's row. compute-sanitizer reports invalid global reads at the unmasked block-table `tl.load`, and the launch fails. This PR masks that load with `tile_mask`, which every other load in the loop already uses. It makes the same change in the INT4 per-token-head kernel `_attn_packed`, which has a copy of the loop behind the same `unified_attention` entry point.

Compared with #61810, #61028 and #56862, this fix:

- Also masks the same load in `_attn_packed`, which `unified_attention` runs for `KVQuantMode.INT4_PER_TOKEN_HEAD`. With any of them, the INT4 form of the reproducer still gives 32 invalid reads at `int4_per_token_head.py:498` and a crash.
- Adds tests that fail on the old kernels. None of them adds a test, and the existing cases #61810 points to pass on the old code unless run under compute-sanitizer.

Compared with #56862, this fix:

- Does not pass the block-table width as a `tl.constexpr`. With #56862, Triton compiles a new kernel for each width: 5 variants of about 300 ms each for widths 3, 4, 5, 8 and 64, against 2 here. In the engine the width is fixed per KV-cache group, so this mostly costs direct callers and tests.

## Claims

- The reproducer from the issue now runs clean under compute-sanitizer. Before, it gave 32 invalid reads and a launch failure.
- The INT4 per-token-head path had the same out-of-bounds read, and it is fixed too.
- Output does not change: old and new kernels give bitwise-equal results in 14 modes.
- Two new regression tests, one per kernel, fail on the old kernels in plain pytest and pass with the fix.

## Validation

Setup: 1 x NVIDIA GeForce RTX 5090. vLLM at commit `df3bd094aeea829f27baa0a5282830464f601d9f` (`0.32.1rc1.dev117+gdf3bd094a`), with and without this patch. `compute-sanitizer` from CUDA 13.0. The bug was first reproduced in the `vllm/vllm-openai:nightly-df3bd094aeea829f27baa0a5282830464f601d9f` image (torch 2.14.0+cu130, triton 3.8.0), with the same result.

Reproducer: the script from the issue, plus the last `print`.

```python
import torch
from vllm.v1.attention.ops.triton_unified_attention import unified_attention

torch.manual_seed(0)
dev = "cuda"
D, Hq, Hkv, bs, NB = 64, 2, 2, 16, 4
ctx, qlen = 32, 2
nk = ctx + qlen
W = -(-nk // bs)
q = torch.randn(qlen, Hq, D, device=dev, dtype=torch.float16)
kc = torch.randn(NB, bs, Hkv, D, device=dev, dtype=torch.float16)
vc = torch.randn(NB, bs, Hkv, D, device=dev, dtype=torch.float16)
block_table = torch.randperm(NB, dtype=torch.int32, device=dev)[:W].reshape(1, W).clone()   # 12-byte allocation
out = torch.empty_like(q)
unified_attention(q=q, k=kc, v=vc, out=out,
                  cu_seqlens_q=torch.tensor([0, qlen], dtype=torch.int32, device=dev), max_seqlen_q=qlen,
                  seqused_k=torch.tensor([nk], dtype=torch.int32, device=dev), max_seqlen_k=nk,
                  softmax_scale=D ** -0.5, causal=True, window_size=(-1, -1), block_table=block_table,
                  softcap=0.0, q_descale=None, k_descale=None, v_descale=None)
torch.cuda.synchronize()
print("DONE no exception")
```

Tests: I ran them with `--noconftest`, because the local venv has no `tblib`. The new tests need nothing from `tests/conftest.py`.

- `pytest tests/kernels/attention/test_triton_unified_attention.py -k tile_wider_than_block_stays_within_block_table_row`: `2 passed`. With the old `triton_unified_attention.py`, the core test fails with `CUDA error: an illegal memory access was encountered`. With the old `int4_per_token_head.py`, the INT4 test fails the same way.
- `pytest tests/kernels/attention/test_triton_unified_attention.py -k 'not use_td'`: `1629 passed, 290 deselected`. The 290 `use_td` tests fail to compile on this GPU (`RuntimeError: PassManager::run failed`). The same tests fail with the old kernel.
- `pytest tests/quantization/test_per_token_kv_cache.py -k int4`: `3 failed, 23 passed`. The 3 failures are `test_reshape_and_cache_per_token_head[int4-...]` (`Tensor-likes are not close!`). They test the cache-write kernel, and they fail the same way with the old INT4 kernel.
- I compared old and new output in 14 modes: causal and non-causal prefill, sliding window, softcap, 2D and 3D decode, INT8 and INT4 per-token-head, and 48 sequences of length 4000. The block tables were like the engine's, with spare columns, so the old kernel does not fault. All outputs were bitwise equal. Kernel times moved by a few percent in both directions, which is noise at this size.
- `pre-commit` passes on the three changed files.

## Details

Root cause: `kernel_unified_attention` walks the KV sequence in tiles of `TILE_SIZE`. For every lane it loads `block_table[seq_offset // BLOCK_SIZE]`, with no mask. In the last tile, lanes at or past `max_seq_prefix_len` still compute a block index. When `TILE_SIZE > BLOCK_SIZE`, that index can be past the last block the sequence owns. In the reproducer, block size is 16 and `seq_len = 34`, so the row has 3 entries. `max_seqlen_q = 2` takes the 2D path with tile 32. Tile 1 covers positions 32 to 63, and lanes 16 to 31 (positions 48 to 63) load block 3. That is 12 bytes into a 12-byte table. The K/V loads and per-token-head scale loads that use this value are all masked with `tile_mask`, so the output was right. Only the read itself was out of bounds. Under compute-sanitizer this is an invalid read. If the table ends at unmapped memory, it is an illegal memory access.

The fix adds `mask=tile_mask, other=0` to that load. `compute_tile_loop_bounds` keeps `max_seq_prefix_len <= seq_len` in every mode, so a lane in the mask only reads a column the sequence owns. Every use of `physical_block_idx` is masked with the same `tile_mask`, so the `0` filler is never used. The `USE_TD` scalar load needs no change: it reads the block of `j * TILE_SIZE`, which is below `max_seq_prefix_len` for every `j < loop_hi`. The block table is not too narrow. The kernel's own tests and the engine both pass rows that are exactly as wide as the sequence needs, so padding in the caller would not fix the kernel. `_attn_packed` in `int4_per_token_head.py` is a line-for-line copy of this loop, with the same `compute_tile_loop_bounds` and `tile_mask`. It gets the same change.

Tests: a plain test cannot see this bug, because the bad value is never used and the read usually lands in mapped memory. The new tests use the CUDA VMM driver API (`cuda-bindings`, already pinned in `requirements/test/cuda.txt`). They place the block table at the very end of a mapped granule, with an unmapped one after it, so any read past the row faults. They use the reproducer's shape. The core test checks the output against `ref_paged_attn`. The INT4 test checks it against the same call with a normal block table. Both skip on non-CUDA platforms and when `cuda.bindings` is missing.

Not in this PR: the same unmasked block-table load is also in kernels behind other entry points: `triton_unified_attention_diffkv.py`, `turboquant_soa/triton_turboquant_unified_attention.py` and `ultraquant/triton_unified_attention.py`. The DiffKV one was seen to still read out of bounds. These can go in a follow-up, or in this PR if reviewers prefer.
