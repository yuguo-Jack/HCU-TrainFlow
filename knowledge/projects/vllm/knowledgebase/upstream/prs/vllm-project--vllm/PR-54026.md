# [Bugfix] Return validation errors for malformed OpenAI request fields

[Upstream PR](https://github.com/vllm-project/vllm/pull/54026) · state: open · merged: False

## Original PR description

## Purpose

Prevent malformed OpenAI-compatible requests from returning HTTP 500 when
`mode="before"` validators inspect raw JSON values before Pydantic validates
their field types.

The affected validators previously called `len()`, `.get()`, `list()`, iterated,
or indexed values that clients can supply with an invalid container type. This
leaked `AttributeError`, `KeyError`, or `TypeError` from invalid values such as:

- scalar `structured_outputs` in Chat Completions and Completions
  (`AttributeError` -> HTTP 500);
- malformed `tools` entries (`[{}]`, `[{"function": {}}]`) used with a named
  Chat Completion tool choice (`KeyError` -> HTTP 500);
- scalar `messages` or `messages[].tool_calls` in Chat Completions, and scalar
  `tools` in Chat Completions or the Responses API (`TypeError`). On current
  main these already return HTTP 400 through the raw-`TypeError` fallback
  handler, but with a bare Python message such as `'int' object is not
  iterable` and no `param`; that fallback is marked for removal.

The validators now leave structurally invalid values unchanged so Pydantic's
field validation returns the normal 4xx validation response. Existing semantic
validation remains unchanged for well-formed values.

I searched open vLLM issues and pull requests using combinations of malformed
request, HTTP 500, `structured_outputs`, `tools`, `messages`, and tool-choice
validation. While this PR was open, #53763 merged with an overlapping fix for
malformed Responses namespace tools. That code and its test were removed from
this PR during the rebase; the remaining cases are not covered by #53763.

This contribution was developed with assistance from OpenAI Codex. The human
contributor is responsible for reviewing every changed line and understanding
the change before requesting maintainer review.

## Test Plan
### Live server test (2026-10-06, after rebasing onto main `cbe1f9740d`)

Two `Qwen/Qwen3-0.6B` servers on separate NVIDIA H200s, one from main and one
from this branch, same command:

```bash
vllm serve Qwen/Qwen3-0.6B --max-model-len 4096 --enable-auto-tool-choice --tool-call-parser hermes
```

25 identical requests were sent to both; the branch was run twice to check for
flakiness.

| Request | main | this PR |
|---|---|---|
| `structured_outputs` as `3`, `true`, or `["json"]` on `/v1/chat/completions` and `/v1/completions` | 500 `'int' object has no attribute 'get'` | 400, `param=body.structured_outputs` |
| `tools: [{}]` with named `tool_choice` | 500 `KeyError: 'function'` | 400, `param=body.tools.0.function` |
| `tools: [{"type": "function", "function": {}}]` with named `tool_choice` | 500 `KeyError: 'name'` | 400, "The tool specified in `tool_choice` does not match..." |
| `messages: 3`; `messages[].tool_calls: 3`; `tools: 3` / `[3]` with named `tool_choice` | 400, bare `'int' object is not iterable` / `not subscriptable`, `param=null` | 400, pydantic `list_type` / `model_attributes_type`, `param=body.messages` / `body.tools` |
| `/v1/responses` with `tools: 3` or `true` | 400, bare `object of type 'int' has no len()`, `param=null` | 400, pydantic `list_type`, `param=body.tools` |
| 13 controls: plain chat, `structured_outputs` `choice`/`regex`, two-constraint rejection, valid named tool call, missing named tool, empty `tools`, streamed `tool_choice: auto`, assistant `tool_calls` round trip, Responses plain / empty tools / `required` without tools / named tool call | | identical to main (only a random `call_id` differed) |

Example:

```bash
curl -s localhost:8000/v1/chat/completions -H 'Content-Type: application/json' \
  -d '{"model":"Qwen/Qwen3-0.6B","messages":[{"role":"user","content":"hi"}],"structured_outputs":true}'
```

The main server log shows six 500s with tracebacks in `check_structured_outputs_count`
and `check_tool_usage`; the branch server log shows none. The second run on the
branch matched the first.

Model evaluation is not applicable because this change only affects request
validation and does not alter inference or generated output.
