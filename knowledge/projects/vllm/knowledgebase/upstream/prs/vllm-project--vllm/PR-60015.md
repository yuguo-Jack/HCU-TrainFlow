# [Bugfix][Quantization] Register compressed-tensors block-FP8 weight scale as weight_scale_inv

[Upstream PR](https://github.com/vllm-project/vllm/pull/60015) · state: open · merged: False

## Original PR description

## Overview

`CompressedTensorsW8A16Fp8` registers its block-strategy weight scale as `weight_scale` in
`create_weights`, and only renames it to `weight_scale_inv` in
`process_weights_after_loading` — i.e. *after* loading. A checkpoint that stores that tensor
as `weight_scale_inv` therefore cannot load: `LinearBase.load_weights` finds no matching
attribute (`param = getattr(self, name, self)` in `layers/linear.py`), falls back to the
module itself, and the layer's `weight_loader` raises

    AttributeError: 'MergedColumnParallelLinear' object has no attribute 'data'

Register the block-strategy scale as `weight_scale_inv` from the start — the name the plain
FP8 path registers (`quantization/fp8.py:339`; MoE FP8 uses
`"weight_scale_inv" if self.block_quant else "weight_scale"`, `quantization/fp8.py:486`) and
the name this scheme renames it to anyway — and keep the post-loading rename behind a
presence check so parameters created by the old path still get renamed.

This scheme is not exotic: `CompressedTensorsConfig.get_scheme`
(`compressed_tensors.py:851-868`) falls back to it for block-FP8 weights wherever the FP8
W8A8 kernel is unsupported, so block-FP8 artifacts that carry dynamic activation quant still
land here on SM80-class devices.

Refs #43564 (its load-time strand; the issue was closed stale without a fix).

## Claims

- A compressed-tensors FP8 **block** checkpoint whose scale is stored as `weight_scale_inv`
  now loads instead of failing on the missing parameter name, and such a model serves:
  load + generation verified end-to-end (see Validation).
- A regression test pins the naming contract (red on unpatched `main`, green with the fix).
- No numerics change: only parameter naming at load time. After loading, the block strategy
  ends up with exactly the same single parameter (`weight_scale_inv`) holding the same data.
- TENSOR/CHANNEL strategies and every other compressed-tensors scheme are untouched.

## Validation

All runs below use vLLM at `f03026a548` + this patch, on an NVIDIA A100-PCIE-40GB (SM80),
`tensor_parallel_size=1`, `enforce_eager=True`, engine in-process.

1) Regression test (added by this PR), red/green:

    $ pytest tests/quantization/test_compressed_tensors.py -k w8a16_fp8_block_scale -x -q
    # unpatched main:  1 failed
    #   AttributeError: 'MergedColumnParallelLinear' object has no attribute 'data'
    # with this patch: 1 passed        (1.78s, no model download, no GPU kernel work)

The failing frame is the same one a real deployment hits:
`layers/linear.py:987 load_weights` -> `param.weight_loader(...)` -> `layers/linear.py:767
param_data = param.data`.

2) End-to-end reproducer on a real engine. Scratch conversion of `Qwen/Qwen3-0.6B`: every
`*.weight` under `model.layers.*` is block-128x128 quantized to FP8 E4M3 with per-block
`weight_scale_inv` (the naming a real block-FP8 artifact uses), and `config.json` gets the
`quantization_config` of a real block-FP8 artifact (weights: 8-bit float, block [128,128];
inputs: dynamic group-128) — the configuration that routes to this scheme on SM80:

    $ python -c "from vllm import LLM, SamplingParams; \
      llm = LLM(model=<converted Qwen3-0.6B>, max_model_len=512, enforce_eager=True); \
      print(llm.generate(['The capital of France is'], SamplingParams(temperature=0, max_tokens=16))[0].outputs[0].text)"

    # unpatched main:
    ValueError: There is no module or parameter named 'layers.0.mlp.down_proj.weight_scale_inv'
    in Qwen3Model. The available parameters belonging to layers.0.mlp.down_proj
    (RowParallelLinear) are: {'layers.0.mlp.down_proj.weight_scale', 'layers.0.mlp.down_proj.weight'}

    # with this patch:
    Loading weights took 0.18 seconds
    KV cache size: 99,360 tokens, Maximum concurrency for 512 tokens per request: 194.06x
    init engine (profile, create kv cache, warmup model) took 11.60 s
    OUTPUT>>> ' Paris. The capital of France is also the capital of the French Republic. The'

(The two failure surfaces — `AttributeError` and the loader's name check — are the same
missing parameter name seen along two loader paths.)

Model evaluation: **not applicable** — no weight, scale or activation value changes and no
kernel selection changes; the only difference is the parameter name during loading.

## Details

Root cause: vLLM is internally inconsistent about this tensor's name. The plain FP8 path
registers `weight_scale_inv` for block quant (`quantization/fp8.py:338-339`, commented
"intentional for deepseekv3"), and this compressed-tensors scheme *also* renames to
`weight_scale_inv` after loading — but it registers `weight_scale` *during* loading, so a
`weight_scale_inv` checkpoint has nothing to match.

Why this is not a duplicate (checks run 2026-10-05 against open PRs/issues):

- #43290 and #43723 fix the **opposite** direction (artifacts storing `weight_scale` where
  vLLM expects `weight_scale_inv`) and are model-file specific (DeepSeek-V4).
- #42657 only transposes `weight` in `process_weights_after_loading` (Marlin shape
  heuristic); upstream has since absorbed that with `.t()` + dim tags.
- #53107 / #53118 only make `LinearBase`'s missing-parameter error clearer — the load still
  fails.
- #52966 (merged) added the post-loading rename for Marlin; it does not touch `create_weights`.
- #43564 requested this direction and was closed stale without a fix; the load-time PR its
  comment thread points to (#43655) is closed and unrelated (DSV4 quant_config plumbing).
- Searches that produced this list: `gh issue view 43564 --comments`,
  `gh pr list --state open --search "43564 in:body"` (empty),
  `gh pr list --state open --search "compressed tensors fp8 weight_scale_inv"`,
  `gh pr list --state open --search "compressed_tensors_w8a16_fp8"`.

Compatibility (both readers handle either name, so post-loading behavior is unchanged):

- `quantization/utils/marlin_utils_fp8.py:197-201`:
  `if hasattr(layer, "weight_scale"): … elif hasattr(layer, "weight_scale_inv"): …` — both
  branches write the same permuted scales to whichever name exists.
- `quantization/utils/fp8_utils.py:53-65` `get_fp8_block_weight_scale()`: Quark → `weight_scale`,
  otherwise → `weight_scale_inv`.

The delete-then-rename block stays behind `if "weight_scale" in layer._parameters`, so any
parameter created by the old path is still renamed. Complexity: 1 file changed, 0 lines of
logic removed, well under the "low complexity" bar; the second file is the regression test.
