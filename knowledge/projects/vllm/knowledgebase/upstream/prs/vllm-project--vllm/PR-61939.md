# [ROCm] Revamp CI/release deployment: collapse image tiers, unify build pipeline

[Upstream PR](https://github.com/vllm-project/vllm/pull/61939) · state: closed · merged: True

## Original PR description

> **Companion PR:** vllm-project/ci-infra#820 (dual-mode pipeline generator — must merge together or with ci-infra first)

Currently on CI and deployment, we have:

- **Too many image tiers.** The old pipeline had six distinct image layers (base, ci_base, CI image, wheels, test, smoke), each driven by a separate script with its own cache keys and metadata handoffs. Adding or debugging any step required understanding all six.
- **CI and release were disconnected.** CI built images via `ci-bake-rocm.sh`; release rebuilt everything from scratch with its own scripts, Dockerfiles and keys, so what shipped was never built the way CI tested it.
- **Thousands of lines of bash nobody could operate.** `ci-bake-rocm.sh` alone was 2,737 lines. The ROCm build/deploy surface totalled ~12,000 lines of shell with no human able to read, modify or debug it under pressure.

In this PR, the purpose is to have:

**Content-keyed base images, one Dockerfile, one HCL, three readable scripts.**

1. **Stack** (`rocm/vllm-ci:stack-rocm-<Ks>`) — base OS + ROCm + PyTorch. Built only when `docker/Dockerfile.rocm_base` or `tools/vllm-rocm/therock_wheels.py` changes (content key `Ks`). Pushed once; reused by every subsequent build.
2. **Runtime and test dependencies** (`runtime-rocm-<Kr>`, `test-deps-rocm-<Kr>`) — the runtime layers and the test-only dependencies on top. Content key `Kr` = `Ks` + the Dockerfile above the per-commit marker + pip requirement files + `rust-toolchain.toml` + `tests/vllm_test_utils` + the torchcodec script. Each is built once per key and reused by digest.
3. **Per-commit** (`rocm/vllm-ci:build-<build-id>`) — vLLM compiled on top of `test-deps`. A Python-only commit reuses everything below it and adds ~160 MB; a requirements bump rebuilds the runtime and test-deps; a csrc-only change rebuilds neither.

All images and caches use zstd layers (pulling needs Docker ≥ 23 or containerd ≥ 1.5).

**One shared `docker/Dockerfile.rocm`.** Named BuildKit contexts (`stack`, `runtime`, `test-deps`) are injected by the bake HCL, so the same Dockerfile builds on any stack without duplication.

**One static `docker/docker-bake-rocm.hcl`** replaces the dynamically generated `docker/ci-rocm.hcl`. All parameterisation is through HCL `variable` blocks from environment variables. Targets: stack (+ wheels), runtime, test-deps, the CI test image (+ smoke, compile cache, Python-only wheel), and the release (wheels, `vllm-openai`, smoke).

**`build.sh` (330 lines) replaces ~5,000 lines of shell scripts.** Modes: `keys`, `base`, `ci`, `release` (plus `release-base`, the release stack and runtime only). Each mode is a self-contained named section, readable end-to-end. Bake builds from a `git archive` export of `HEAD` (checked against `BUILDKITE_COMMIT`), so the content keys hash exactly the bytes that are built and file-mode drift on shared agents never busts the csrc cache. A registry error exits 75, which the steps retry.

**Trust.** ci-infra sets `ROCM_CI_REPO`: `rocm/vllm-ci` for non-PR builds of `vllm-project/vllm` main (AITER nightly excluded), else `rocm/vllm-dev` with `pr<N>-` (PRs) or `br-<branch>-<hash>-` (nightlies, branch builds) tags and caches. Trusted builds never read `rocm/vllm-dev`; release reads neither `rocm/vllm-ci` nor its cache.

**Release builds from the same Dockerfiles and keys as CI, in the existing release pipeline.** The ROCm group of `release-pipeline.yaml` runs on its own `cpu_queue_release` agents (no extra Buildkite pipeline, no AMD agents in the release cluster):
- `build.sh rocm release-base` (one at a time) builds the stack and runtime from source into ECR, once per content key. CI agents also run PR code, so release never takes images or build cache from `rocm/vllm-ci`; it uses only its own ECR cache;
- `build.sh rocm release` compiles csrc for all 9 GPU arches (gfx90a/942/950/1100/1101/1200/1201/1150/1151) and pushes `<ecr>:rocm-<commit>{,-wheels,-base}`. The csrc compile uses the shared S3 sccache (as the CUDA release does) and falls back to ccache without it;
- the release image is the same recipe and keys CI tests, not the same bytes: its csrc is the 9-arch compile, which no GPU step runs. Measured locally with fresh builders: 2 h 37 min cold, 4.5 min for the next release with an unchanged csrc.

**`publish.sh` (205 lines) handles release publishing.** It copies digests via `imagetools create` from ECR to the variant tags, Docker Hub (nightly) and S3 (wheels extracted from the `-wheels` image) — no Docker build, no layer transfer.

**ROCm 7.2 (apt) deprecated.** All `rocm_72` stack plumbing removed: `Dockerfile.rocm_72`, `Dockerfile.rocm_72_base`, `stack-rocm_72` bake target, `rocm72-check-amd` CI step, ROCm 7.2 release pipeline group and publish target. TheRock 10 (`rocm`) is the only supported stack.

**ci-infra is dual-mode.** The pipeline generator checks for `.buildkite/scripts/rocm/build.sh` in the vLLM checkout. Present → new pipeline renders. Absent (old checkouts, forks) → existing pipeline unchanged.

**Image pre-warming.** Base tags are content-keyed (`test-deps-rocm-<Kr>` contains the runtime and stack). A cluster cron job can pre-pull the newest one by digest, avoiding the simultaneous pull from every node on rare base rebuilds.

### What is preserved

- **Step key `image-build-amd`** — unchanged. Every AMD GPU test step continues to depend on it.
- **`SETUP_STEP_KEYS = {"ensure-ci-base-amd", "refresh-rocm-base-amd", "pre-commit"}`** (`ensure-ci-base-amd` kept for pre-revamp branch checkouts)
- **Smoke tests** — `test-smoke` and `openai-smoke` stages in `Dockerfile.rocm` (import checks during the build). The release has no GPU smoke step: release images are evaluated before they are pushed.
- **Process lifecycle** — `run-amd-test.sh` handles: `CONTAINER_TIMEOUT_S` wall-clock timeout (TERM, then KILL after 10 s), structured `[amd-ci-teardown]` lifecycle log events, exit-code propagation, DPX GPU partition lock, HF mount check, NFS xet redirect, GPU preflight, diagnostics bundle on failure.
- **Nightly tags** (`vllm/vllm-openai-rocm:nightly*`, `base-nightly*`), S3 wheels and root index, perf-eval ECR image, credential boundaries.
- **AITER nightly** — with `AITER_NIGHTLY=1` the test image's AITER step installs the newest nightly wheel that fits the image's ROCm, torch and Python; `AITER_SPEC` pins one instead. The build checks the wheel with `find_spec` and `ldd` (importing aiter needs a GPU). ci-infra's old-layout path is unchanged.

### Follow-up infra tasks

- **`amd-cpu-pr` queue split** — run PR builds on separate hosts with their own Hub token, scoped to `rocm/vllm-dev`. One comment in `build.sh` marks the boundary.
- **Cluster pre-warm cron** — pre-pull the newest `rocm/vllm-ci:test-deps-rocm-*` on CI nodes, pinned by digest.
- **Hub tag retention** — prune `pr<N>-*` / `build-*` tags in `rocm/vllm-dev`; define an expiry window for the content-keyed tags in `rocm/vllm-ci`.
- **First ROCm release after merge** — it builds the stack and runtime from source and compiles csrc cold unless the S3 sccache is warm (~2.5–3 h). Its build log should show the ECR cache export (`writing cache image manifest`); the next release then reuses it.
- **ci-infra base step** — add the `exit_status: 75` (registry error) automatic retry that `amd.yaml` has.
- **Stacked follow-ups** — csrc cache key and untrusted-namespace scoping; test-image parity (fast-exit plugin in the image, RDMA userspace, Ray compatibility trigger).
- **gfx1250 Dockerfiles** (`Dockerfile.rocm_gfx1250`, `Dockerfile.rocm_base_gfx1250`) — kept as-is, not wired into CI or release; needs owner sign-off before removal.

File: `.buildkite/release-pipeline.yaml` · line None

Dropped the `amd-release` pipeline, so nothing new is needed in Buildkite, ci-infra or from the Inferact folks.

Apparently, the release pipeline runs in its own Buildkite cluster, so starting a pipeline on the AMD agents would have needed an org admin to add a cross-cluster trigger rule, plus the new pipeline itself.

Instead, the ROCm release now builds inside `release-pipeline.yaml` on its existing `cpu_queue_release` agents (`build.sh rocm release`):
- it reuses the CI-tested stack and runtime images from `rocm/vllm-ci` by digest;
- it compiles csrc for all release architectures;
- it pushes the image, `-wheels` and `-base` to ECR, and the existing publish steps copy them on from there;
- it keeps its own build cache in ECR, so a release only recompiles csrc when csrc changed since the previous one. Locally that's about 2.5 h cold and under 5 min with the cache.

The release GPU smoke step is gone too, since release images are evaluated before they're pushed.
