# [Bugfix][Spec Decode] V2 rejection sampler: return logprob_token_ids scores

[Upstream PR](https://github.com/vllm-project/vllm/pull/61219) · state: open · merged: False

## Original PR description

## Overview

With the V2 model runner and speculative decoding, a request that sets `logprob_token_ids` (and no `logprobs`) gets no logprobs back whenever another request in the same batch has draft tokens. `RejectionSampler` only looked at `max_num_logprobs`, so `logprob_token_ids` was dropped on that path. The regular V2 `Sampler` already handles it through `get_logprobs_dims`.

`/v1/systemone` reads are such requests (`max_tokens=1`, `logprob_token_ids`): next to a streaming chat on an MTP model, every read failed with `HTTP 400: No logprobs available for item 0`. This passes the per-request token ids to `compute_topk_scores` in the rejection sampler. Related: #42592 / #44727 (the same kind of mixed batch, on the V1 sampler, a different file).

## Claims

- Qwen3.8-27B with MTP 3, 6 `/v1/systemone` calls (4 questions, 2k-token state) while 4 chat streams run: 6/6 fail before, 6/6 succeed after.
- Chat is not affected: time to first token 0.52 → 0.60 s and inter-chunk latency p50 191 → 192 ms with and without systemone on the engine.
- The returned probabilities are not changed by the chat load: mean absolute difference 0.007 (max 0.041) between a cold call and the same call next to chat, the same as between a cold call and the same call repeated alone on a cached state (0.007, max 0.039).
- Batches without `logprob_token_ids` are unchanged (`compute_topk_scores` takes its fast path when `max_token_ids == 0`); without speculative decoding this code path is not used.

## Validation

Qwen3.8-27B 4-bit with MTP 3 on gfx1151 (Radeon 8060S), nightly `0.31.1rc1.dev273` (`2eb491e18b`), V2 model runner, `--enable-prefix-caching --mamba-cache-mode align --logprobs-mode raw_logprobs`, `--max-num-seqs 8`. The same change was applied to the nightly's copy of the file for the runs. Chat: 4 closed-loop streaming requests (256 tokens).

| | systemone alone | systemone + 4 chats, main | systemone + 4 chats, this PR |
|---|---|---|---|
| errors | 0 / 6 | 6 / 6 (HTTP 400, no logprobs) | 0 / 6 |
| chat errors | | 0 | 0 |

After the review changes the run was repeated (mixed: 0 errors, cold vs next-to-chat mean absolute difference 0.004, max 0.033). The same server also runs `/v1/systemone` accuracy (120 synthetic tickets: 0.90 / 0.67 / 1.00, unchanged) and the question-count cases (6.4 / 8.2 / 11.9 / 28.7 s for 1 / 4 / 16 / 64 questions, unchanged) with the change applied. MTP off, on main: no errors (no drafts, so the batch does not go through the rejection sampler); not re-run with the change.

Tests:

```bash
pytest tests/v1/worker/test_gpu_rejection_sampler_chunking.py tests/v1/worker/test_gpu_batch_shard.py
```

31 passed with the change. New tests in `test_gpu_rejection_sampler_chunking.py` build a real `LogprobTokenIdsState` and check the returned ids and scores against `log_softmax` / the raw logits for every row:
- `test_logprob_token_ids_without_topk_logprobs`: token ids only, raw and logits modes, and nothing is computed when none are requested;
- `test_logprob_token_ids_with_topk_logprobs`: top-k `logprobs=1` narrower than the widest `logprob_token_ids`, requests with and without ids;
- `test_logprob_token_ids_with_adaptive_verification`: one chunk over compacted logits, device `cu_num_logits` and a host-side upper bound, same result as the fixed-boundary layout;
- `test_get_logprobs_dims_with_only_token_ids`.

`test_gather_sampler_output_logprobs_and_nans` is parametrized over top-k only, token ids only and token ids wider than top-k. The CUDA tests of these files are skipped on ROCm by `current_platform.is_cuda()`; I ran them locally with that check replaced by `torch.cuda.is_available()`. The new tests fail on main. The `model_runner.py` call site of the sharded gather (TP > 1) has no test and was not run.

## Details

- `RejectionSampler.__call__` calls `Sampler.get_logprobs_dims` once and passes `logprobs_dims` to `_verify_in_chunks` and `_get_logprobs_tensors`, which also takes the chunk's `expanded_idx_mapping` (`compute_topk_scores` needs it to map each logits row to its request).
- `Sampler.get_logprobs_dims` no longer has `include_token_ids`: the sharded gather in `model_runner.py` sizes its buffers with the token-id columns for batches with draft tokens too.
- Not covered: DSpark and the other speculators were not run; they go through the same `RejectionSampler.__call__`.

The sharded-sampling path still needs updating: https://github.com/vllm-project/vllm/blob/85876aa922a9b2b19a61aea302c6c02195a0cc90/vllm/v1/worker/gpu/model_runner.py#L1666-L1673

```python
logprobs_dims=self.sampler.get_logprobs_dims(
    global_input_batch.idx_mapping_np,
    # Rejection sampler does not return logprob token ids.
    include_token_ids=(
        global_input_batch.num_draft_tokens == 0
        or self.rejection_sampler is None
    ),

```

With this PR that comment is no longer true, so with TP>1 + batch-sharded sampling + spec decode:
- If a request only sets `logprob_token_ids`, `get_logprobs_dims` returns `None`, the logprobs gather is skipped, and the request still gets no logprobs (the bug this PR is fixing).
- If another request in the batch sets `logprobs=k` with `k < len(logprob_token_ids)`, `num_logprob_cols` becomes `1+k`, so the wider rejection-sampler rows get truncated when packed and the extra token-id columns are silently dropped.

I think `include_token_ids` can just be `True` here now (and the comment removed).
