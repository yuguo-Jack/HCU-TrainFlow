# [Feat] Fast EP scaling with NCCL communicator split and fine-grained runtime-state management

[Upstream PR](https://github.com/vllm-project/vllm/pull/44994) · state: open · merged: False

## Original PR description

## Purpose

This PR implements [FastEEP](https://arxiv.org/abs/2610.18451): fast intra-instance EP scaling through **Partial Reuse**. It preserves worker processes, compiled kernels, captured graphs, and reusable communication state while reclaiming GPU memory on inactive ranks.

The server starts at the maximum DP/EP size. Later scaling changes only the active subset, avoiding worker recreation, model reload, and graph recapture. This complements the topology-changing [ElasticEP](https://vllm.ai/blog/2026-05-14-elastic-expert-parallelism) path.

- **Scale down:** shrink request routing, drain inactive ranks, remap experts, split the active DP communicator, and mask sleeping NIXL peers. Then release inactive-rank allocations, including communication and graph buffers where supported.
- **Scale up:** remap GPU memory, restore or refill weights, reconnect communication buffers, and update expert mappings. Open routing to new ranks only after they are ready.

Collective reconfiguration runs in a pause window in both directions. Active ranks continue serving outside that window.

### Main Changes

- **Reclaim communication memory.** Add `ncclCommSplit` support and retain the maximum DP group as the parent for resizing. Destroy obsolete split communicators. When `ncclCommSuspend`/`ncclCommResume` are available, release and restore the maximum communicator's GPU resources without losing its handle. Disconnect sleeping NIXL peers and destroy their RDMA buffers; rebuild and reconnect them on wake.
- **Reclaim CUDA Graph buffer memory.** Route capture allocations into a dedicated CuMem `graphs` pool. Back up its contents to pinned CPU memory, then unmap the GPU pages on sleep. Restore them at the same virtual addresses on wake, preserving captured graphs without recapture. Graph buffers retain a CPU backup even in L2 mode.
- **Support tagged memory sleep.** Separate shared weights, expert weights, KV cache, and graph allocations. L1 backs up selected allocations to CPU; L2 discards weights and KV cache, then refills weights from active peers on wake. Reuse pinned backup buffers across cycles.
- **Coordinate execution and expert placement.** Add logical EPLB sleep state, NIXL peer masking, and V2 Runner support. Sleeping ranks skip forward execution; routing changes only when the target configuration is consistent.
- **Avoid redundant scale-up work.** Refill shared weights only on joining ranks, distribute transfers across active senders, and leave KV cache unmapped on ranks that remain asleep. Record phase timings for memory wake, communication recovery, and expert remapping.

### Memory–Latency Tradeoff and Limitations

- Communication reclamation reduces sleeping-rank memory but adds recovery latency. For lower latency, set `VLLM_FLASH_EPSCALE_SUSPEND_MAX_DP=0` and `VLLM_FLASH_EPSCALE_SKIP_NIXL_TEARDOWN=1` to retain NCCL resources and NIXL buffers. Report these settings with benchmark results.
- Graph-buffer reclamation requires `enable_cumem_allocator=True` and capture in its graph pool. The eager example below does **not** exercise this path; recent V2 smoke tests used eager execution.
- CPU-backed offload can incur a large first-use pinned-memory allocation cost. L2 avoids weight/KV CPU backups; graph-buffer backups still apply when graph offload is active.
- Worker processes, CUDA contexts, and compiled code remain resident. Scaling stays within the startup maximum and requires enough active expert slots to hold every logical expert.
- Current validation focuses on single-node, TP=1 serving. The tested compatibility configuration uses synchronous PyNCCL for expert-weight migration and NIXL for token dispatch/combine; repeated L2 wake with NIXL 1.0.1 expert-weight migration still encounters UCX failures.


## Run Plan

1. Initialize the runtime environment

```bash
git clone -b flash_epscale-cleanup-pause-fix https://github.com/nanookfyf/vllm
cd vllm
uv venv --python 3.12 --seed --managed-python
source .venv/bin/activate
VLLM_USE_PRECOMPILED=1 uv pip install --editable . -v
uv pip install meson ninja pybind11 tomlkit 'ray[default]' nixl-cu13==1.0.1
```



2. Start a serving instance at the maximum DP/EP size (8 GPUs on one node). Update the paths below and run with Bash:

```bash
MODEL="<ModelPath>"
LOG_FILE="<LogPath>"
RAY_HOST="127.0.0.1"
RAY_PORT="9305"
export RAY_ADDRESS="${RAY_HOST}:${RAY_PORT}"
export VLLM_SERVER_DEV_MODE=1

export VLLM_FLASH_EPSCALE_SUSPEND_MAX_DP=1
export VLLM_FLASH_EPSCALE_SKIP_NIXL_TEARDOWN=0
if ! timeout 10s ray status --address="$RAY_ADDRESS" >/dev/null 2>&1; then
    ray start --head --port="$RAY_PORT" --disable-usage-stats
fi
ray status --address="$RAY_ADDRESS"

vllm serve "$MODEL" --trust-remote-code --enable-sleep-mode \
    --host 0.0.0.0 \
    --port 8005 \
    --tensor-parallel-size 1 \
    --gpu-memory-utilization 0.45 \
    --max-model-len 4096 \
    --no-enable-prefix-caching \
    --enable-expert-parallel \
    --enable-eplb \
    --enable-elastic-ep \
    --all2all-backend nixl_ep \
    --eplb-config.num_redundant_experts 64 \
    --eplb-config.communicator pynccl \
    --eplb-config.use_async false \
    --data-parallel-backend ray \
    --distributed-executor-backend ray \
    --data-parallel-size 8 \
    --data-parallel-size-local 8 \
    --data-parallel-rpc-port 9876 \
    --data-parallel-start-rank 0 \
    --enforce-eager \
    2>&1 | tee "$LOG_FILE"
```


3. Trigger fast EP scaling while serving:

```bash
curl -X POST http://localhost:8005/flash_epscale \
  -H 'Content-Type: application/json' \
  -d '{"ep_size": 4, "level": 2}'
```



4. Verify correctness before and after scaling:

```bash
curl http://localhost:8005/v1/completions \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "<SERVED_MODEL_NAME>",
    "prompt": "Explain expert parallelism in one sentence.",
    "max_tokens": 32
  }'
```

- nanookfyf · comment · 2026-06-11T02:57:23Z · [source](https://github.com/vllm-project/vllm/pull/44994#issuecomment-4676771105)

@fangyuchu 
Thanks for the question~

1. These scaled-down "freed" GPUs release GPU memory resources and **can host other workloads**. For example, other serving instances could be launched on these "freed" GPUs.

2. In the **Next Steps**, we will try further to **reduce the residual memory footprint on the GPU side** (for example, by offloading communication buffers). We are also considering reducing CPU-side memory overhead by discarding weights and the KV cache and serving them through other active ranks.

3. One of the purposes of retaining the CuMemAllocator and JIT cache is to **reduce the reconstruction overhead during scale-up**. As for whether these inactive ranks (with some residual footprint but no forward execution) can be used for other purposes, I think this is still a fairly open topic, and we'd be happy to discuss it further with the community~
