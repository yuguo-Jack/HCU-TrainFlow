# [Feat] Add fast EP scaling with NCCL communicator split

[Upstream PR](https://github.com/vllm-project/vllm/pull/44994) · state: open · merged: False

## Original PR description

## Purpose

The community-proposed [ElasticEP](https://vllm.ai/blog/2026-05-14-elastic-expert-parallelism) flow scales an instance at runtime by creating/destroying Ray workers, rebuilding the stateless comm group, migrating and rearranging expert weights, and re-warming the compiled kernels. On DeepSeek-V2-Lite we measured ~31 s to scale up and ~7 s to scale down.

This PR shortens that path. The observation is that in most deployments the **maximum** resource budget is fixed up front, so the cost of weight loading, kernel compilation, and topology construction can be paid **once at startup** and **reused**.

The server boots at the maximum DP/EP size — loading weights, compiling kernels, building the maximum NCCL topology. Each later scaling operation only resizes the **active subset** of that prepared topology, completing in **~3 s** in our 8-GPU single-node H20 tests.

- **Scale down**:
    - **Expert remap** — EPLB rearranges the logical-to-physical expert table.
    - **CPU offload** — model weights and the KV cache on the inactive ranks are moved to pinned CPU memory via the per-rank, tag-based `cumem` allocator, freeing GPU memory.
    - **Comm group resize** — `ncclCommSplit` is called on the prepared maximum DP/EP group to produce a new NCCL communicator restricted to the active ranks, and the live group handle is swapped to that split communicator so all subsequent collectives run on the smaller world.
    - **NIXL all2all masking** — the EP mask buffer is updated so the NIXL all2all backend skips sends/recvs to the sleeping ranks, keeping MoE dispatch/combine correct without rebuilding the transport.
    - **Scheduler routing** — the active DP size is lowered so the request scheduler stops dispatching new requests to the inactive ranks; `gpu_model_runner` skips forward on any inactive rank.
- **Scale up**:
    - **CPU → GPU restore** — the `cumem` allocator wakes the previously offloaded ranks, copying their pinned-CPU weight and KV-cache slabs back into the original GPU buffers.
    - **Comm group resize** — `ncclCommSplit` is called again on the prepared maximum DP/EP group to produce a communicator covering the larger active set, and the live group handle is swapped to that new communicator so subsequent collectives include the woken ranks.
    - **Expert remap + NIXL unmask** — the EPLB logical-to-physical expert table is restored to the wider physical layout (released replicas re-materialize on the woken ranks), and the NIXL all2all mask buffer is cleared so MoE dispatch/combine starts including those ranks again.
    - **Scheduler routing opened** — only after the group, weights, KV cache, expert table and all2all mask are all consistent does the active DP size grow, allowing the scheduler to route new requests to the newly active ranks; `gpu_model_runner` stops short-circuiting forward on them.

### Main changes

- The CuMem allocator (`device_allocator/cumem.py`) is extended with a per-rank, tag-based offload/upload path so weights and KV cache on a chosen EP rank can be parked in pinned CPU memory.

- For the communicator side, pynccl (`device_communicators/pynccl.py`, `pynccl_wrapper.py`) gains `ncclCommSplit` support, and `parallel_state.py` keeps the original maximum `_DP` group as a parent so each scaling call splits or reuses it instead of tearing down and rebuilding the topology. 

- The NIXL all2all backend (`device_communicators/all2all.py`) gets an EP-rank mask buffer so MoE dispatch/combine simply skips sleeping ranks while the same transport keeps running.

- On the model-execution side, `v1/worker/gpu_model_runner.py` short-circuits the forward pass on masked ranks (they stay alive only to keep the engine in sync), and `eplb/eplb_state.py` adds a logical sleep state so the logical-to-physical expert table can be remapped onto the active rank set on scale-down and restored on scale-up.


### Current limitations

- Scale-down offloads weights and KV cache to CPU. The first scale-down has to allocate pinned CPU memory and takes ~20 s; subsequent scale-downs reuse those slabs and run at ~2 s.

- Because only weights and KV cache are offloaded, the residual GPU footprint on a sleeping rank (CuMemAllocator, the Python / CUDA context, the JIT'd kernel cache ) is retained but small (<8 % of the rank's original GPU memory). A dummy worker also stays alive, but it skips the forward pass so the inactive ranks no longer burn compute power.

- Scaling is bounded by the resources allocated at startup. This path only resizes the active subset within the startup maximum.

**Note:** We will resolve the above limitations in ([Next Steps](#NextSteps)).


## Test Plan

1. Start a serving instance at the maximum DP/EP size:

```bash
vllm serve "$MODEL" --trust-remote-code --enable-sleep-mode \
    --host 0.0.0.0 \
    --port 8005 \
    --tensor-parallel-size 1 \
    --gpu-memory-utilization 0.45 \
    --max-model-len 4096 \
    --no-enable-prefix-caching \
    --enable-expert-parallel \
    --enable-eplb \
    --enable-elastic-ep \
    --all2all-backend nixl_ep \
    --eplb-config.num_redundant_experts 64 \
    --data-parallel-backend ray \
    --distributed-executor-backend ray \
    --data-parallel-size 8 \
    --data-parallel-size-local 8 \
    --data-parallel-rpc-port 9876 \
    --data-parallel-start-rank 0 \
    --enforce-eager
```

2. Trigger fast EP scaling while serving:

```bash
curl -X POST http://localhost:8005/flash_epscale \
  -H 'Content-Type: application/json' \
  -d '{"ep_size": 4}'
```

3. Verify correctness before and after scaling:

```bash
curl http://localhost:8005/v1/completions \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "<SERVED_MODEL_NAME>",
    "prompt": "Explain expert parallelism in one sentence.",
    "max_tokens": 32
  }'
```

### Next Steps

The items below are aimed at the limitations called out above.

- [ ] Add `ncclCommGrow`/`ncclCommShrink` semantics so the topology can grow beyond the startup maximum (lifts the startup-bound cap).
- [ ] Auto-route between flash EP scaling (this PR, fixed-topology) and [ElasticEP](https://vllm.ai/blog/2026-05-14-elastic-expert-parallelism) (topology change) based on the requested target.
- [x] Faster GPU-side weight transfer to enable resource release without CPU offloading (`discard=True`), avoiding the ~20 s first-scale-down latency from pinned-CPU allocation.
- [x] Keep remaining ranks serving during scale-up; freeze new requests only during scale-down (further shrinks the pause window).
- [ ] Extend to TP and other parallel modes.

- nanookfyf · comment · 2026-06-11T02:57:23Z · [source](https://github.com/vllm-project/vllm/pull/44994#issuecomment-4676771105)

@fangyuchu 
Thanks for the question~

1. These scaled-down "freed" GPUs release GPU memory resources and **can host other workloads**. For example, other serving instances could be launched on these "freed" GPUs.

2. In the **Next Steps**, we will try further to **reduce the residual memory footprint on the GPU side** (for example, by offloading communication buffers). We are also considering reducing CPU-side memory overhead by discarding weights and the KV cache and serving them through other active ranks.

3. One of the purposes of retaining the CuMemAllocator and JIT cache is to **reduce the reconstruction overhead during scale-up**. As for whether these inactive ranks (with some residual footprint but no forward execution) can be used for other purposes, I think this is still a fairly open topic, and we'd be happy to discuss it further with the community~
