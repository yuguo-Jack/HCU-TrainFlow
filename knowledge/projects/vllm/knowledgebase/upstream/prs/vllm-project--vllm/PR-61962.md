# [AMD][DSV4.1Flash] Quantize MoE activations to MXFP8 before the MoRI dispatch

[Upstream PR](https://github.com/vllm-project/vllm/pull/61962) · state: open · merged: False

## Original PR description

## Motivation

MXFP4 W4A16 experts declare BF16 activations, so MoRI dispatches raw BF16 and
AITER quantizes to group-32 MXFP8 on arrival. A token routed to `k` distinct
ranks is therefore quantized `k` times — expected ~4.4 of 8 ranks at topk=6 for
DeepSeek-V4.1-Flash — and the dispatch carries 2 bytes/element instead of
1 + 1/32.

Quantizing in `prepare()` moves that to once per token on the rank that owns it,
and roughly halves the dispatch payload.

AITER already consumes the result: with a pre-quantized FP8 operand and E8M0
scales, its stage-1 path sorts the scales (`mxfp4_moe_sort_fwd`) instead of
running its own quant. This mirrors the MXFP4 W4A4 dispatch added in #59596,
which takes the same pre-quantized route for a4w4.

## Summary of changes

**`all2all_utils.py`** — adds `mori_use_mxfp8_dispatch()` and wires a third
dispatch mode into `maybe_make_prepare_finalize()`. MoRI infers the payload
dtype from the input tensor and transports `scale_dim` scales of
`scale_type_size` bytes per token, so the new branch sets
`scale_dim = hidden_dim / 32` and a 1-byte scale element. E8M0 exponents are
bytes, not the fp32 the per-token/per-tensor FP8 paths use.

**`prepare_finalize/mori.py`** — adds the `use_mxfp8_dispatch` flag and the
corresponding quant in `prepare()`, via `get_hip_quant(QuantType.per_1x32)` with
`scale_type=dtypes.fp8_e8m0`, matching the FP4 branch directly above it. The
mutual-exclusion assert becomes `sum(...) <= 1` now that there are three modes.

**Gating is deliberately narrow.** A pre-quantized operand is only safe when
AITER would have produced MXFP8 itself: a BF16-activation kernel would cast the
FP8 payload back to BF16 and never apply the scales, silently losing the
scaling. `mori_use_mxfp8_dispatch()` therefore asks AITER directly via
`resolve_activation_dtype()`, which is documented for exactly this case ("lets a
caller that produces the activations itself -- an all-to-all dispatch, a fused
epilogue -- emit that dtype directly") and returns `None` rather than guessing
when the answer would have depended on a token count that does not exist yet.
It also fails closed on `ImportError` and on a hidden dim that is not a multiple
of 32.

## Results

8x MI355X (gfx950), DeepSeek-V4.1-Flash, DEP8, DEP4, DEP2 with `mori_high_throughput`,
speculative decoding off. 8192 in / 1024 out, 256 prompts at concurrency 64,
against a stock nightly (`0.32.0rc1.dev190+g3f1bcfd82`) with **only this change
applied** — this PR was measured on its own, with no AITER-side patches, so the
numbers are attributable to the dispatch change alone.

Engagement was confirmed rather than assumed: `resolve_activation_dtype(M=None)`
returns `torch.float8_e4m3fn` under the `AITER_BF16_FP8_MOE_BOUND=0` that vLLM
pins for this model, and the dispatch kernel switches from
`EpDispatchIntraNodeKernel_bf16` to `EpDispatchIntraNodeKernel_fp8_ocp`.

@bnellnm thanks — added `tests/kernels/moe/test_mori_mxfp8_dispatch.py` (19 tests) in the latest commit.

The core of it pins the gate against AITER itself: each case asserts both the dtype `resolve_activation_dtype()` returns and that `mori_use_mxfp8_dispatch()` follows it, so AITER changing its mind stays distinguishable from the gate drifting away from it. The table covers silu/gelu/swiglu on the pinned FP8 bound, the unpinned bound where AITER defers for want of a token count, and all three SiTUv2 modes — the a4w4/a16w4 disagreement @okorzh-amd caught above is now a regression test.

The rest covers what follows from the gate:
- each guard (w4a4, fp8-block, the DSv4 a4w4 opt-in, a hidden dim not divisible by 32, an activation AiterExperts rejects) turning the DeepSeek-V4.1-Flash config off on its own;
- the MoRI buffer args — FP8 payload, `hidden/32` scales, one byte each rather than the fp32 the per-token/per-tensor paths use — plus the BF16 fallback carrying no scales;
- `prepare()` emitting FP8 with E8M0 scales that dequantize back to within one E4M3 step of the group scale, `defer_input_quant` passing BF16 through untouched, and the three-way mutual-exclusion assert.
