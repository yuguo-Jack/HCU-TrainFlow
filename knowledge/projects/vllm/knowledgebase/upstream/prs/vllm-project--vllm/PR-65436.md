# [Perf][Sampling] Gather vocab-parallel logits into their final layout in one pass

[Upstream PR](https://github.com/vllm-project/vllm/pull/65436) · state: open · merged: False

## Original PR description

## Overview

With a vocab-parallel LM head (TP > 1), every sampled step moves the logits three times:

1. `LogitsProcessor` gathers them with a last-dim all-gather. NCCL fills a rank-major `[world, rows, vocab/world]` buffer.
2. `movedim` + `reshape` copies that into the vocab-major `[rows, vocab]` layout, which is a slow strided copy, and the vocab padding is sliced off.
3. In Model Runner V2, the sampler copies the logits once more into a new FP32 tensor before applying temperature, top-k/top-p and logits processors.

For a 200k vocabulary at 256 rows (DSpark K=7 verify at concurrency 32), that is 102 MB gathered, 205 MB re-laid out and 307 MB copied to FP32 on every rank, per step.

This PR changes this only for models that opt in (MiniMax-M3 / M3.1), and only in Model Runner V2's target logits. Every other model, every draft head and Model Runner V1 keep main's gather and the samplers' FP32 copy unchanged.

- **`all_gather_vocab_parallel_logits`** (`logits_processor.py`) gathers along rows, which needs no copy, then writes the final `[rows, vocab]` layout with one Triton kernel. That kernel also cuts off the padding and casts to the requested dtype. The kernel is compiled once per output dtype (not per row count), and the gather stays off the dim-0 symmetric-memory route (`VLLM_USE_NCCL_SYMM_MEM`), which would add a scratch buffer and a full-size clone.
- **The request travels in the forward context, not on the model.** `ForwardContext` gets one field, `logits_gather_dtype`. `LogitsProcessor` uses the fused gather on CUDA only when that field is set: FP32 if it is `torch.float32` and no scale or soft cap runs after the gather, the head's dtype otherwise. When the field is unset, or there is no forward context, it takes main's gather. A subclass that overrides `_gather_logits` (e.g. the DeepSeek-V4.1 specialized decode's custom all-gather) always keeps its own gather. The model runner sets the field only in a narrow `set_forward_context` around an opted-in model's `compute_logits` call in `_compute_logits`. That call covers both the plain sampling steps and the spec-decode verify steps. The runner no longer changes any attribute of the model or its logits processors, and the `compute_logits` signature is unchanged.
- **No second FP32 copy, when the consumer wants FP32.** For an opted-in model, the runner asks the logits' consumer whether it wants FP32 logits for the step: `RejectionSampler.wants_fp32_logits` on a step with drafts, `Sampler.wants_fp32_logits` otherwise. The sampler's rule is that some request needs processing (the case where it would copy to FP32) and no returned logprobs read the raw logits. The rejection sampler returns the same rule today, because it processes the logits through `Sampler.apply_sampling_params`. When the consumer wants FP32, the gather writes FP32 and the runner passes `logits_writable=True` to `Sampler` / `RejectionSampler`, which then process the FP32 logits in place. The keyword is passed only on those steps. The FP32 request is exact. It applies only when no logit scale or soft cap runs in the `LogitsProcessor` after the gather and the FP32 logits fit the rejection sampler's chunk cap (`get_max_chunk_logits`). When raw logprobs are requested, the gather stays in the head dtype and the sampler makes its one copy, as before. This applies only with the stock samplers: a custom sampler is called exactly as on main, and the model then keeps main's gather.
- **The consumer picks the dtype, so bf16 verify paths keep bf16.** A verify path that reads the head-dtype logits directly, without the FP32 copy (e.g. the bf16 top-p cutoffs of #65102, which require `logits.dtype == torch.bfloat16`), returns False from `RejectionSampler.wants_fp32_logits` for the batches it takes. The gather then writes bf16, and only the layout pass is fused. Without this, an FP32 gather would always send such batches back to the stock path. The hook is one method next to the verify gate; it does not follow a new gate by itself, so whichever of the two PRs lands second adds the override. With #65101–#65103 ported, the override is the gate's own condition without the dtype check: no processed logprobs or sampling mask, and temperature only or temperature + top-p only (see Validation).

- **One per-model opt-in for all of it.** The fused gather, the FP32 request and `logits_writable` apply only to a model that declares `SupportsFP32LogitsGather` (`interfaces.py`, a `supports_fp32_logits_gather: ClassVar[Literal[True]]` flag like `HasNoOps`). A model may opt in only if its `compute_logits` returns the `LogitsProcessor` output unchanged. Otherwise post-processing in `compute_logits` (e.g. HunYuan-V4's or Muse Spark's soft cap) would run on FP32 instead of bf16 logits. MiniMax-M3 / M3.1 (`MiniMaxM3SparseForCausalLM` and `MiniMaxM3SparseForConditionalGeneration`, NVIDIA and AMD) opt in; their `compute_logits` is `self.logits_processor(self.lm_head, hidden_states)` or delegates to it. For every other model the runner sets no gather dtype, so its logits take main's gather and its samplers are called without the keyword, exactly as on main.

Outputs are unchanged for every model. For opted-in models the PR only moves data and casts up exactly, and nothing changes for other models.

## Claims

- **Scope.** Only opted-in models (MiniMax-M3 / M3.1) under Model Runner V2 change, and only their target logits. Other models, draft heads and Model Runner V1 run main's code path. The request is carried in the forward context; nothing on the model is changed.
- **Bitwise-equal logits.** The fused gather equals the last-dim all-gather + slice (+ cast) for bf16, fp16 and fp32 inputs, bf16/fp32 outputs, 0–300 rows, with and without vocab padding, at TP 2 and 4.
- **Faster in both output modes** (GB300, 4 ranks, vocab 200064, CUDA-graph timed, max over ranks, µs; two runs agree within 0.2 µs):

  | rows | main, FP32 consumer: all-gather + layout + FP32 copy | this PR, FP32 | main, bf16 consumer: all-gather + layout | this PR, bf16 |
  |---|---|---|---|---|
  | 8 | 34.0 | 26.2 | 29.1 | 25.6 |
  | 16 | 65.7 | 53.9 | 57.5 | 53.0 |
  | 32 | 82.3 | 61.1 | 68.0 | 59.3 |
  | 64 | 115.7 | 76.4 | 88.3 | 72.3 |
  | 128 | 205.9 | 115.6 | 142.4 | 107.3 |
  | 256 | 392.9 | 205.4 | 266.0 | 191.3 |

  The consumer's choice is exact, so there is no trade-off between the modes: FP32 is written only when the consumer would copy to FP32, and bf16 only when it reads bf16. A wrong choice would cost: the bf16 gather followed by the sampler's FP32 copy takes 315 µs at 256 rows (vs 205 µs for the FP32 gather).

- **End to end:** see Validation.
