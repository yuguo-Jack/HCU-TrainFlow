# [Perf][Multimodal] Make encoder cache free linear in items per request

[Upstream PR](https://github.com/vllm-project/vllm/pull/62850) · state: closed · merged: True

## Original PR description



## Overview

Follow-up to #54284. `EncoderCacheManager.free_encoder_input` scans all of a request's other cached inputs on every call, so freeing a request with N multimodal items is O(N²) on the scheduler thread. This makes it O(N) with the same release semantics.

## Claims

- Freeing a request with N multimodal items is now linear in N: 1,024 items drops from 15.9 ms to 0.29 ms, and 4,096 from 235 ms to 1.2 ms.
- No behaviour change: an entry is still held until the request's last occurrence of that `mm_hash` is freed, as #54284 requires.
- Only matters for prompts with hundreds of items (the default limit is 999 per modality). Typical prompts see under 0.1 ms difference.

## Validation

`EncoderCacheManager.free(request)` timed on `main` vs this PR: 5 runs, median in ms, CPU only (CPython 3.12).

| Items per request | `main` | This PR |
|---|---|---|
| 256 | 1.36 | 0.09 |
| 1,024 | 15.87 | 0.29 |
| 4,096 | 234.64 | 1.21 |

`pytest tests/v1/core/test_encoder_cache_manager.py`: 22 passed (21 existing, including the duplicate-hash tests from #54284, plus 1 new). CI runs the file through `pytest -m cpu_test v1/core`.

I did not do a GPU end-to-end run. This only changes scheduler bookkeeping, so model outputs are unaffected.

## Details

The `any(...)` check added in #54284 runs on every free, so freeing N inputs costs N(N−1)/2 comparisons on the engine-core thread, and the whole batch waits. This PR keeps `request_hash_refs[req_id][mm_hash]`, a count of the request's cached input ids per hash, updated where `request_cached_ids` changes. The check becomes a dict lookup.

Tradeoff: one small dict per request. An out-of-tree manager that subclasses `EncoderCacheManager` and writes `request_cached_ids` directly would also need to update `request_hash_refs`.
