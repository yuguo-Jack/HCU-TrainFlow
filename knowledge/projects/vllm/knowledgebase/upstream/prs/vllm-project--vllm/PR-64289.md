# [Perf][MoE] Enable SM90 MXFP4 MegaMoE via FlashInfer MoE-EP

[Upstream PR](https://github.com/vllm-project/vllm/pull/64289) · state: open · merged: False

## Overview

`--moe-backend flashinfer_moe_ep_cutedsl` now runs MXFP4 MoE checkpoints, such as DeepSeek-V4.1-Flash, on Hopper. It uses FlashInfer's SM90 MXFP4 x FP8 MegaMoE (flashinfer-ai/flashinfer#4843) through the existing FlashInfer MoE-EP adapter. The packed MXFP4 weights go to the kernel as loaded, without a bf16 round trip.

- **Stacked on #62603** (SM90 block-FP8 MegaMoE through the same adapter). Only the last commit, db751d56eb, is new here.
- **Draft until FlashInfer ships [#4843](https://github.com/flashinfer-ai/flashinfer/pull/4843) in a release.** It is not in 0.7.2.post1, main's current pin.
- This answers the question in https://github.com/vllm-project/vllm/pull/62603#issuecomment-6460588074: it is an MXFP4-resident Hopper moe_ep entry, and it applies to an unmodified DeepSeek-V4.1-Flash checkpoint.

Related:
- #64061: the same goal through DeepGEMM's SM90 FP8 x FP4 Mega MoE (vllm-project/DeepGEMM#44). It is measured head to head below. The two kernels trade wins: DeepGEMM is faster in decode and this PR is faster in prefill.
- #54032: FlashInfer's CUTLASS Humming grouped-GEMM MoE for the same quantization. It is not a megakernel.

## Claims

All results are DeepSeek-V4.1-Flash on 8x H200, compared against main's default MXFP4 backend (HUMMING with block-FP8 activations and `allgather_reducescatter`):

- **Decode** (DP8/EP8, 128K/512, DSpark3 with synthetic acceptance): +8% to +18% output throughput and -6% to -13% TPOT p50 at concurrency 32 to 192. No resolved change at concurrency 8.
- **Prefill** (DP4/EP4 at the full 1M context, 2048/1, natural DSpark3): +3.5% saturated throughput and lower TTFT p50 at every offered rate.
- **#64061**, on the same workload: +12% to +21% in decode, but -8.7% in prefill.
- **GSM8K** shows no resolved difference among the three backends.
- The backend is opt-in. Default backends do not change.

## Details

- **Weights.**
  - The MXFP4 oracle keeps the checkpoint's packed E2M1 bytes and E8M0 scales on Hopper. The adapter hands them to FlashInfer as `PrequantizedMoEWeights`.
  - FlashInfer interleaves gate/up rows and folds the scales into its kernel layout, an 11-exponent window per expert; it does not requantize.
  - On Blackwell nothing changes: the CuTeDSL kernel still gets bf16 and requantizes to NVFP4.
- **Activations.**
  - The kernel quantizes activations to E4M3 with one scale per token, and its fc2 input with one scale per 64 channels.
  - main's default uses block-FP8 (1x128) activations, so the arms are not bit-identical. GSM8K shows no resolved difference.
- **Adapter.**
  - `FlashInferMoeEp` takes the Hopper weight format (`"fp8_block"` or `"mxfp4"`) instead of a block-FP8 flag.
  - The MXFP4 path reuses #62603's 64/256/1024-token workspaces. With DeepSeek-V4 routing they now combine with FlashInfer's output view.
  - The kernel requires int64 expert ids, so the adapter converts top-k ids to the kernel's index dtype. This is one device-side cast per layer; nothing new reads back to the host.
- **Limitations.**
  - EPLB is rejected for MXFP4 on Hopper, because FlashInfer keeps a per-expert FP32 scale of these weights outside the layer's parameters.
  - Input-side router weights are rejected, as for block FP8: the kernel weights the activation before fc2.
  - The DeepGEMM MoE-EP backend stays Blackwell-only.
  - With a FlashInfer that lacks [#4843](https://github.com/flashinfer-ai/flashinfer/pull/4843), MXFP4 on Hopper fails at weight processing with a message that names the FlashInfer PR.
- **Versus #64061.** DeepGEMM's kernel is faster in decode at every tested concurrency; the gap is 2% to 10%, smallest at C=192. This kernel is faster in prefill (41.8 vs 36.9 saturated req/s). The two can coexist as backend choices, for example per prefill/decode role.
