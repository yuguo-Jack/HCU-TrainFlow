# [Model] Inkling, Muse Spark: write checkpoint tensors through the parameter's weight loader

[Upstream PR](https://github.com/vllm-project/vllm/pull/64690) · state: closed · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Inkling and Muse Spark write some checkpoint tensors directly into `param.data` instead of through the parameter's `weight_loader`. A layerwise weight reload never sees those writes, so after a reload the model keeps its startup weights for these tensors. This PR routes every such write through the parameter's loader. Part of the direct weight reload work (RFC #54477); independent of the other PRs. Replaces aoshen02/vllm#175.

## Claims

- **Inkling (NVIDIA and AMD):** after a layerwise reload, the routed experts and the sink experts (both the default and the LoRA-capable `InklingSinkExpertsLinear`) hold the new weights. This covers weights, block scales, per-expert global scales and the calibrated input scale. On main they keep the startup values.
- **Muse Spark:** the fused QKV+O-gate projection takes the new weights on a layerwise reload. On main it keeps the startup values.
- **Inkling MTP draft (NVIDIA and AMD):** every tensor goes through the parameter's `weight_loader`, so a layerwise reload updates the draft. On main, tensors whose shape matched the parameter were written with `default_weight_loader` and kept the startup values. `test_mtp_writes_go_through_weight_loader` fails on the previous head and passes with the fix (slurm 43123 / 43120).
- **Cold start is unchanged.** On Inkling-Small NVFP4 (TP=4), every model tensor after cold start is byte-identical to main's on all 4 ranks. GSM8K, throughput and KV cache size are within noise.

How each test works:
- **The NVFP4 test** builds a real NVIDIA `InklingMoE` with `ModelOptNvFp4Config` under single-rank parallel state.
  1. It loads the layer through `load_expert_weight` under a bf16 default dtype, as the model loader does: routed `w13`/`w2`, block scales, `*_scale_2`, `input_amax`, and the sink experts.
  2. It checks that the calibrated input scale is exactly float32.
  3. It reloads layerwise with new weights, restoring layers on the GPU as model loading does, and checks that the routed experts are processed during the load (every element counted), not left to finalize.
  4. It compares every expert tensor, and its address, with a cold start on the new weights.
- **The padded-slot test** covers the quantized AITER padding with the writers alone, because an MXFP4 AITER layer also needs ROCm.

## Details

Layerwise reload restores each layer on the meta device and wraps `param.weight_loader` to buffer the calls. It also counts the copied elements, so it knows when a layer is complete and can run its post-load processing. A write that bypasses the loader goes to the meta tensor and is lost. Direct reload (#64336) writes into the live tensors and already sees these writes; this PR is needed for layerwise reload.

- **Inkling.**
  - Expert tensors were copied into `param.data` slot by slot, because the checkpoint needs de-interleaving and per-expert writes.
  - The routed experts' own parameters now get `write_loader(param, loaded_weight, write)`, which runs the given write. Every expert write goes through it, using writers shared by both backends in `inkling/common/weights.py`:
    - `deinterleave_into` writes the fused `w13`;
    - `copy_padded` writes a slot with padding;
    - `copy_into_slots` writes the per-expert scalars.
  - All writes use `copy_`, so the element count sees them.
  - The sink experts also load through their parameters' loader. The LoRA-capable `InklingSinkExpertsLinear` (used when LoRA is enabled) called the linear module's `weight_loader`; it now calls `w13.weight.weight_loader` / `w2.weight.weight_loader`, the loader a reload wraps. For an unquantized merged-column / row-parallel weight the parameter holds `weight_loader_v2`, which writes the same slices as the module's v1 loader; under LoRA, `w13.weight` resolves to the base layer's parameter.
  - The calibrated input scale is written by `fill(value)`, which fills the parameter in its own dtype (float32) with `copy_`.
- **Only the routed experts' own parameters get `write_loader`** (`parameters(recurse=False)`): `load_expert_weight` writes only those. Parameters of child modules (e.g. an expert-substitution table) load through their own loaders, which must stay in place.
- **AITER padding (AMD).** AITER rounds the per-rank intermediate dim up, so the AMD expert parameters are wider than the checkpoint slice.
  - **Quantized (MXFP4) parameters** count every element. The writers set the padding to the value it is created with (zero for weights, one for scales), so the layer completes as it loads and the padding matches cold start.
  - **Unquantized AITER parameters** declare `weight_loader_numel` (checkpoint elements only), and their method zeroes the padding during post-load processing. The loader leaves that padding alone; writing it would finish the layer early and drop later expert writes.
- **The calibrated input scale is built in float32.** Weights load under `set_default_torch_dtype(model dtype)`, so `torch.tensor(amax / denominator)` without an explicit dtype would be bf16 and round the scale.
- **Inkling MTP.** `_load_inkling_mtp_weights._load` called `default_weight_loader` directly when the tensor's shape matched the parameter; it now always calls the parameter's loader. The MTP layers are dense, and a same-shape tensor only happens for replicated parameters or TP=1, where the parallel loaders narrow nothing, so cold start writes the same bytes.
- **Muse Spark.** `MuseSpark1xQKVOGateParallelLinear.load_weights` called `self.weight_loader` directly. Under v2-loader quant methods the parameter's loader was also bound to `ColumnParallelLinear.weight_loader_v2`. `weight_loader_v2` now points to the layer's loader, and `load_weights` calls `param.weight_loader`. At cold start the same function runs as before.
- **M2N side effect.** The M2N engine places a tensor directly only when the parameter's loader is a known stacked/column loader. Muse Spark's fused projection previously exposed `ColumnParallelLinear.weight_loader_v2`, which M2N accepted even though the per-rank `[q, k, v, o_gate]` layout is head-aware. M2N now falls back to the regular load for it.
- **CI.** The B200 Inkling step now also triggers on `vllm/model_executor/model_loader/reload/`; its MI355 mirror does not, since it runs only `models/inkling/rocm`, which does not exercise the reload code. The B200 step runs the new tests; the AMD input-scale and unquantized-padding changes are covered by CPU layout tests in the B200 step.
- **Not covered:**
  - EP sizes that do not divide `n_routed_experts` (EP-alignment padding experts) are not supported, as on main: the loaders index the checkpoint with the padded expert ids. Their slots are also zeroed in `finalize_load`, outside the loader.
  - Online quantization of the Inkling MoE: `InklingMoE` sets `write_loader` on the routed parameters after the online method installed its own loaders, so those are replaced. This is broken on main too (main writes `.data` directly); online quantization of Inkling is unsupported, as on main.
  - `muse_spark/nvidia/mega_moe.py` also loads through `self.weight_loader`; that path is left to a follow-up.
  - Muse Spark DSpark: `load_weights` (`muse_spark/common/dspark.py`) raises when a chunk lacks `lm_head`/`d2t`, so chunked NCCL draft updates fail (sibling drafters gate this check with `is_mtp_completeness_check_enabled()`). Tracked in #54477.
- **Follow-up (#54477 F19):** the AMD writers (`deinterleave_into`, `copy_padded`) write the AITER padding themselves. Once #64352 lands, they should record it with `mark_padding` like the other MoE loaders, so padding has one mechanism and the load plan (#64418) can fill it without running loaders.
- **Out of scope: other loaders that bypass `param.weight_loader`, left as on main because these models are not RL targets:**
  - BERT MLM (`bert.py`): encoder-only decoder tie.
  - ColBERT, ColPali, ColQwen3, ColQwen3.5: retrieval models.
  - Nemotron-Nano-VL, Nemotron-Parse, Pixtral (vision encoders), Voxtral, Cohere ASR, MiMo-Audio, Nemotron-3.5 Transcribe (audio).
  - Molmo/Molmo2, Phi-3-V: VLMs.
  - Sequence-classification and reward adapters (`adapters.py`, Nemotron-VL seq-cls): pooling heads, not rollout policies.
  - K2-Horizon, Step-3 text, LongCat-Flash n-gram: niche.
  - Llama-4 ModelOpt expert scales (`mllama4.py`, `param.data.fill_` broadcasts one checkpoint scalar to all experts): the parameter's loader is the FusedMoE loader, which takes one expert and shard per call, so the fix is a loop over experts and shards, with no ModelOpt Llama-4 checkpoint to validate it. Tracked in #54477.
  - Flint NVFP4-GGUF experts: GGUF, one-shot repack.
  - Qwen3-XPress drafter: niche; it rebuilds fused buffers in `load_weights`.
  - BatchNorm running statistics (`models/utils.py`): vision-only modules.
  - Non-reload loaders (sharded state, the weight-cache IPC loader, ModelExpress, the sparse NCCL engine): cold-start formats or outside the reload lifecycle.

- hao-aaron · comment · 2026-11-03T22:37:26Z · [source](https://github.com/vllm-project/vllm/pull/64690#issuecomment-6617260011)

This PR can likely be dropped once we stop supporting layerwise reload.

**Why it only matters for layerwise.** Layerwise reload restores each layer's parameters on meta and wraps `weight_loader`. A write like `param.data[slots].copy_(w)` then lands in the meta placeholder and is silently dropped, and the layer is never counted as complete. Routing every write through the parameter's loader (Muse Spark fused QKV, Inkling experts, Inkling MTP) is what fixes that.

Direct reload doesn't intercept writes at all:
- **begin:** each parameter's `.data` is rebound to a checkpoint-layout view of its own storage (`t.data = view`).
- **load:** `load_weights` runs unmodified, so `param.weight_loader(...)`, `default_weight_loader(...)` and `param.data[...].copy_(w)` all write in place into that view.
- **finish:** every module reruns its cold-start post-load processing.

So who performs the write makes no difference. The load-plan bake (#65235) records copies by destination storage, not by loader, so it doesn't need this PR either. #64418's "PR 7 ... so the bake sees it" should be corrected.

**What direct reload does need from here: the Inkling AMD padding.** On main, the AMD loader never rewrites the AITER MXFP4 expert padding. After the view-back, that padding holds the previous post-processed (shuffled) bytes, and post-processing processes them again. The `pad` writes in `deinterleave_into` / `copy_padded` currently cover this. That case is covered by PR 3 (#64352), which is being reworked into a fill at the start of a direct reload: every padded MoE expert parameter is filled with its creation value (0, or 1 for ones-initialised scales), then the loaders overwrite all checkpoint regions. Inkling AMD's padded expert parameters are included. That relies on every update resending every required tensor, which the completeness check (F2) will enforce. It hasn't been verified on ROCm yet.

**Plan:** land the PR 3 fill first, then close this PR. If layerwise support is still needed before then, this PR stays as the fix for it.
