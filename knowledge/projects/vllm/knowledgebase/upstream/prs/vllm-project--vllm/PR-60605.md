# [Perf][KV Connector] Optimize Mooncake contiguous block grouping

[Upstream PR](https://github.com/vllm-project/vllm/pull/60605) · state: open · merged: False

## Original PR description

## Overview

Replace NumPy-based splitting in Mooncake's `group_concurrent_contiguous()` with a single pass over the input lists to reduce intermediate allocations and conversions when grouping block IDs.

## Claims

- Avoids intermediate NumPy arrays and per-group `tolist()` conversions.
- Preserves grouping behavior and output ordering for valid equal-length block ID lists.
- Reduces transfer-parameter construction time in the measured workloads.

## Validation

### Correctness

Added direct unit tests in `tests/v1/kv_connector/unit/test_mooncake_connector.py` covering empty inputs, single blocks, contiguous runs, descending IDs, repeated IDs, different source/destination break positions, input preservation, and rejection of unequal-length inputs.

All 12 parameterized cases passed when the helper and tests were extracted and run in isolation. Ruff lint and formatting checks, and `git diff --check`, passed.

### Performance

Environment: NVIDIA GH200 with a Grace CPU, running Qwen3-32B in BF16.

The 32,000-descriptor workload uses an approximately 8K-token input and 64 model layers. The captured input contains 500 blocks with 16 tokens per block and 64 transfer regions, one per layer. Descending block IDs prevent contiguous grouping, producing 500 × 64 = 32,000 descriptors.

The following results measure `_build_transfer_params()`, which calls the modified helper, rather than the helper in isolation.

| Transfer descriptors | Requests | Before | After | Time reduction |
| ---: | ---: | ---: | ---: | ---: |
| 64 | 50 | 8.593 ms | 6.122 ms | 28.8% |
| 32,000 | 50 | 72.309 ms | 21.842 ms | 69.8% |

The results are workload-specific. They do not establish a speedup for every input pattern, and no end-to-end latency claim is made.

## Details

The previous implementation identifies split points with NumPy, splits the source and destination arrays into groups, and converts every group back to a Python list. Fragmented inputs produce many small intermediate array objects and conversion calls.

The new implementation scans adjacent block IDs and directly slices the original lists at group boundaries. A group continues only when both source and destination IDs increase by one. Descending IDs remain separate groups, and input ordering is preserved.

The change is limited to this helper and introduces no new dependencies.

- staryxchen · comment · 2026-10-08T14:09:51Z · [source](https://github.com/vllm-project/vllm/pull/60605#issuecomment-6061715632)

I measured this PR on an 8× H20 host with Qwen2.5-14B-Instruct, TP=1, 1P1D, block size 16, prefix caching off, and a fixed 8000-token prompt (`max_tokens=1`, streaming TTFT). The only difference between the two runs is  `group_concurrent_contiguous`: NumPy `diff`/`split` versus the single-pass scan in this PR. Timing is inside `_build_transfer_params`.

With prefix caching disabled, the block free list behaves like a stack, so repeating the same prompt alternates between ascending block ids (one coalesced descriptor per layer) and descending ids (one descriptor per block). That gives the  two rows the PR calls out:
  | Block ids | Descriptors | `_build_transfer_params` before | after | delta |
  |---|---:|---:|---:|---:|
  | Ascending, coalesced | 48 | 4.4 ms | 2.2 ms | −2.2 ms |
  | Descending, 48 layers × 500 blocks | 24,000 | 45.5 ms | 11.4 ms | **−34 ms (−75%)** |

End-to-end TTFT (4 samples each, warmup dropped):
  | Block ids | TTFT before | TTFT after |
  |---|---:|---:|
  | Ascending | 1.93 s | 1.87 s |
  | Descending | 1.99 s | 1.89 s |

Both paths moved down by about 50 ms between process starts, so that part is run-to-run offset. On the descending path the extra drop is about 40 ms, which lines up with the 34 ms saved in `_build_transfer_params`. Against a ~2 s prefill that is roughly 2%. The contiguous path only saves ~2 ms in the helper, and that does not show up in TTFT.

This matches the shape reported in the PR (GH200, 64 layers × 500 descending blocks, 72 ms → 22 ms inside the same function). On this workload the win is real, and it shows up in TTFT only when block ids are fragmented enough to produce one descriptor per block.

- staryxchen · comment · 2026-10-08T10:28:35Z · [source](https://github.com/vllm-project/vllm/pull/60605#discussion_r4217802843)

File: `vllm/distributed/kv_transfer/kv_connector/v1/mooncake/mooncake_connector.py` · line 2820

The old NumPy version implicitly enforced equal lengths — np.diff(src) | np.diff(dst) raises on a shape mismatch. The new loop only runs to len(src_indices), and the trailing dst_indices[start:] sweeps up any extra tail, so a longer dst now silently yields src_groups and dst_groups with mismatched last-group lengths instead of failing. Callers pass equal-length lists today, so this is defensive rather than a live bug, but worth keeping the guarantee explicit:
```
assert len(src_indices) == len(dst_indices)
```
