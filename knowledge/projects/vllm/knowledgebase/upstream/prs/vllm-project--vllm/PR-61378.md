# [ROCm][Perf] Enqueue the default chain first in CSA/HCA at small batch sizes for DeepSeek-V4

[Upstream PR](https://github.com/vllm-project/vllm/pull/61378) · state: closed · merged: True

## Original PR description

## Overview

#57407 added a `default_first` option to `execute_in_parallel` (`vllm/utils/multi_stream_utils.py`). When it is set, the default-stream chain is enqueued before the aux-stream chains. The aux streams still wait only on `start_event`, which marks the default-stream work before the fork, so they keep overlapping the default chain.

The DeepSeek-V4 ROCm multi-stream paths still enqueue the aux chains first:

- HCA dual-stream, from #56853: the main compressor runs on aux stream 0.
- CSA three-stream, from #51794: the main and indexer compressors run on aux streams 0 and 1.

On the default stream, both paths run fused `wq_a`/`wkv` GEMM → split + norm → `wq_b` → q-norm/RoPE/KV insert. This is the **longest** chain in the fork. Starting it first shortens the tail of the step when the device is underfilled.

Benchmarks show that this is not true for every batch size. Default-first is faster at small token counts and slightly slower once the batch saturates the device. This PR therefore enables `default_first` only when the step has at most `_DEFAULT_FIRST_TOKEN_THRESHOLD = 96` tokens.

### Changes

All changes are in `vllm/models/deepseek_v4/amd/rocm.py`:

- Add the module-level constant `_DEFAULT_FIRST_TOKEN_THRESHOLD = 96`.
- In `DeepseekV4ROCMAiterMLAAttention._prepare_and_attn`, compute `default_first = hidden_states.shape[0] <= _DEFAULT_FIRST_TOKEN_THRESHOLD` and pass it to the HCA and CSA `execute_in_parallel` calls.

```python
default_first = hidden_states.shape[0] <= _DEFAULT_FIRST_TOKEN_THRESHOLD
...
execute_in_parallel(..., enable=True, default_first=default_first)
```

**Notes:**

- **No runtime cost.** On ROCm, the multi-stream path only runs inside CUDA graph capture or with full-cudagraph metadata (`RocmPlatform.enable_multi_stream_overlap`). `hidden_states.shape[0]` is a concrete Python int at capture time, so each capture size bakes in its own launch order.
- **No change to correctness.** Every aux chain only reads `hidden_states` and its own compressor state, both produced before the fork. The join, where the `done_events` are waited on before returning, is unchanged.
- **Scope.** The threshold is a hard-coded constant, not an env var. It only affects the DeepSeek-V4 ROCm attention class, so DeepSeek-V4.1, CUDA, and other models are untouched. DeepSeek-V4-Flash shares this class and is also gated by the threshold.

### Choosing the threshold

The tests ran with MTP and `num_speculative_tokens=2`, so each decode step runs `3 × conc` tokens. With MTP, capture sizes are rounded to multiples of 3, and both 96 and 144 are capture sizes.

| Conc | Tokens / step | TPOT vs. main | Throughput vs. main |
| ---: | ---: | ---: | ---: |
| 1 | 3 | -7.26% | +7.22% |
| 4 | 12 | -1.26% | +2.99% |
| 16 | 48 | -0.21% | +0.40% |
| 32 | 96 | -0.73% | +0.92% |
| 48 | 144 | +0.65% | -0.49% |
| 64 | 192 | +0.69% | -0.26% |

The sign flips between 96 and 144 tokens. The threshold is set to 96, the last measured point with a gain. The range from 99 to 141 tokens was not measured.

### Performance

Benchmark with SA InferenceX `8k1k` workload with server launch commands below:

```bash
export VLLM_ROCM_USE_AITER=1
export AITER_LOG_LEVEL=WARNING

vllm serve /shared/models/deepseek-ai/DeepSeek-V4-Pro \
    --port 8333 \
    --tensor-parallel-size 8 \
    --data-parallel-size 1 \
    --max-model-len 9472 \
    --max-num-seqs 512 \
    --max-num-batched-tokens 16384 \
    --async-scheduling \
    --no-enable-prefix-caching \
    --distributed-executor-backend mp \
    --gpu-memory-utilization 0.8 \
    --kv-cache-dtype fp8 \
    --trust-remote-code \
    --moe-backend aiter \
    --tokenizer-mode deepseek_v4 \
    --reasoning-parser deepseek_v4 \
    --speculative-config '{"method": "mtp", "num_speculative_tokens": 2}' \
    --compilation-config '{"mode":3,"cudagraph_mode":"FULL_AND_PIECEWISE"}' \
    --load-format fastsafetensors
```

"main" is the version before this PR, where aux chains are always enqueued first.

- mawong-amd · comment · 2026-10-14T00:14:16Z · [source](https://github.com/vllm-project/vllm/pull/61378#issuecomment-6157940191)

Under graph replay on ROCm, the HIP runtime is free to schedule graph segments across internal HIP graph streams without reference to the capture stream. This is a setting governed by the value of `DEBUG_HIP_GRAPH_SEGMENT_SCHEDULING`. At the default value of 1, graph segments are assigned onto internal graph streams (and their pinned HW queues) in BFS discovery order. Enqueuing a stream first during capture often but may not necessarily place it onto the same HW queue as the main decode stream. Segments on different HW queues than the fork (where hipEventRecord is enqueued) start a few us later because they have to wait for an additional barrier packet.

All that is to say, it is true that for best performance the busiest segment should be placed on the main decode stream (HW queue). It is possible to influence this placement with the order in which we enqueue segments during graph capture. However in general the runtime currently does not follow capture streams directly for placement decisions, which may be surprising for users.

Nothing above blocks this PR given the perf gains, but it would be good to have traces confirming that the intended behavior (heaviest segment on same HW queue as the fork) is responsible for the perf increase, as well as traces that perhaps point to why there is a regression at higher batch sizes. Also, do we see the same gains/behavior in traces on ROCm 10?
