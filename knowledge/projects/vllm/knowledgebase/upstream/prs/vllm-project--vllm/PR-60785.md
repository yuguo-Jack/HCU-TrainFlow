# [Bugfix][Attention] Fall back when FlashInfer attention JIT is unavailable

[Upstream PR](https://github.com/vllm-project/vllm/pull/60785) · state: open · merged: False

## Original PR description

## Overview

Fixes #60262 by skipping FlashInfer attention during auto-selection when neither its JIT cache nor runtime build path is available. This lets the selector fall back to `TRITON_ATTN` without changing `has_flashinfer()` semantics.

## Claims

- Add an attention-specific JIT availability check; `flashinfer-cubin` alone does not make FlashInfer attention JIT modules available.
- Skip FlashInfer during configuration validation when neither `flashinfer-jit-cache` nor `nvcc` + `ninja` is available.
- Cover the SM120/FP8 auto-selection fallback with a CPU-only selector test and test the prerequisite combinations.

## Validation

- `.venv/bin/python -m pytest tests/utils_/test_flashinfer_utils.py -q` - 8 passed.
- `.venv/bin/python -m pytest tests/kernels/attention/test_attention_selector.py -q` - 17 passed, 93 skipped; the new fallback test passed.
- No GPU end-to-end serving/model evaluation was run; the added coverage is CPU-only and mocks SM120 selection inputs. The issue's RTX 5090 Badgr command was not run.

## Details

The issue reports that auto-selection chooses FlashInfer even though the attention JIT cannot be built. The new predicate returns false if `flashinfer-python` is absent, true when `flashinfer-jit-cache` is installed, and otherwise requires both `nvcc` and `ninja`. FlashInfer backend validation uses that result, allowing auto-selection to try Triton next. This check stays separate from `has_flashinfer()` and its existing callers. The selector regression test mocks only the predicate and checks the selected backend.

Thanks @nej1gotnochill for the discussion on keeping this check attention-specific and leaving `has_flashinfer()` unchanged.

Duplicate-work check: no equivalent open PR found via gh searches run from my Mac.

FlashInfer 0.7.0.post1 resolves JIT-cache provider/module/architecture coverage per module at runtime. This predicate implements the issue thread's package/toolchain availability contract; it does not check whether a matching provider artifact exists for every module and active architecture. Reviewers should confirm that this is the intended scope.

| jit-cache + nvcc | True | FLASHINFER | ✅ runs |

For reference, without this PR the first case crashes with the same "Could
not find nvcc" error. So this PR fixes the plain pip install on T4.
`tests/utils_/test_flashinfer_utils.py`: 8 passed on the T4.

**The third row is a gap on SM75.** The `flashinfer-jit-cache` wheel doesn't
include SM75 kernels (#55380 adds a warning about this), so on Turing
FlashInfer still JIT-compiles even when the cache is installed, and still
needs nvcc. A possible tweak:

```diff
-    if importlib.util.find_spec("flashinfer_jit_cache") is not None:
+    # flashinfer-jit-cache ships no SM75 kernels, so SM75 always needs the JIT.
+    if importlib.util.find_spec(
+        "flashinfer_jit_cache"
+    ) is not None and not current_platform.is_device_capability(75):
         return True
```

With that applied on the same T4, the third case selects TRITON_ATTN and runs,
and the jit-cache + nvcc case still selects FLASHINFER and runs. One of the new
cases in `test_flashinfer_utils.py` (jit-cache installed means usable) then
fails on an SM75 machine, so it would need the capability mocked.

Only SM75 matters here, and only after #55380, so it could also be left to
that PR. I'm happy to rerun anything on the T4.

- waynehacking8 · comment · 2026-10-19T05:36:43Z · [source](https://github.com/vllm-project/vllm/pull/60785#issuecomment-6260466737)

Reading this against main `153a17166e` and FlashInfer 0.7.2, the jit-cache branch looks too loose. In 0.7.2 `flashinfer-jit-cache` is a shim and the kernels come from per-arch provider packages, so `find_spec("flashinfer_jit_cache")` also passes when no provider is installed (`get_jit_cache_providers()` returns nothing). With a provider but no flashinfer-cubin or usable nvcc, and `VLLM_HAS_FLASHINFER_CUBIN=0`, `has_flashinfer()` is still False, so calling `flashinfer_xqa_batch_decode_with_kv_cache` reaches `_missing`. With `has_flashinfer() and ((nvcc and ninja) or compatible_provider)`, a CPU probe of the selector chooses TRITON_ATTN for both cases and FLASHINFER for cubin plus provider, with package availability, backend order and other capability checks mocked. Widening `has_flashinfer()` instead would also enable `concat_mla_k` for qualifying MLA dimensions, and the sm120f provider lacks its `concat_mla` module.
