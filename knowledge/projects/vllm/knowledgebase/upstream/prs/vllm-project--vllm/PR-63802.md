# [Doc][Benchmark] Note synchronized waves in the max-concurrency load pattern

[Upstream PR](https://github.com/vllm-project/vllm/pull/63802) · state: open · merged: False

## Original PR description

## Overview

Adds a note to the "Maximum Throughput" load pattern (`--request-rate=inf --max-concurrency=N`) in `docs/benchmarking/cli.md`: when all requests do the same work, they tend to run in synchronized waves, and each request's TTFT includes the prefill of the whole wave.

Related: #13412 (closed without an answer: TTFT falls as output length grows under `max_concurrency`, with a sharp drop after the first ~32 requests; consistent with this effect), #54101 (a different effect: the semaphore wait is excluded from latency).

## Claims

- The page recommends this pattern as the most common configuration for production benchmarking, but does not mention its effect on TTFT.
- The note points to existing options for staggered arrivals (a finite `--request-rate`, `--random-range-ratio`). Docs only, no code change.

## Validation

Measured with vLLM 0.32.0, Qwen3-8B BF16, 1x A100-SXM4-80GB, `random` dataset, 1024 input / 256 output tokens, `--ignore-eos`, `--request-rate inf`, `max_num_batched_tokens=8192`, prefix caching off:

| `--max-concurrency` | prompts | TTFT p50 (ms) | TTFT p95 (ms) | E2EL std (ms) |
|---:|---:|---:|---:|---:|
| 1 | 50 | 86.1 | 89.6 | 3.1 |
| 8 | 80 | 484.9 | 538.4 | 7.9 |
| 32 | 320 | 1334.2 | 1968.4 | 114.8 |

- E2EL std of a few milliseconds at C=8 means a wave's requests finish together, so the next wave starts together.
- At C=32 a wave is 32 x 1024 = 32,768 prefill tokens = 4 chunks of 8192. The wave model predicts first tokens in four groups at ~0.49 / 0.98 / 1.47 / 1.96 s: predicted mean 1.225 s vs measured mean 1.233 s; last group 1.96 s vs measured p95 1.968 s.
- GPU telemetry (nvidia-smi, 1 Hz) at C=32 shows exactly 10 prefill bursts (SW power cap clock events) for 320 requests / 32 = 10 waves.

Raw outputs and analysis: https://github.com/vkolupaev/gpu-infra-lab/blob/c62265a5a3a31b724ae39571872f4d46b20d66b2/experiments/2026-10-25-first-number.md

Docs check: `uvx pre-commit run markdownlint-cli2 --files docs/benchmarking/cli.md` -> Passed

## Details

Not a duplicate: searched issues and PRs (title and semantic search; flag names alone match benchmark commands in hundreds of perf PRs) for closed-loop / synchronized requests and TTFT under `--max-concurrency`; found only the related reports above, no doc text or PR covering this.

The Rust `vllm-bench` (`rust/src/bench`) reports steady-state metrics for this mode, but its window only excludes ramp-up and drain; with identical requests the waves continue inside the plateau, so the same caveat applies to its steady-state TTFT. I kept this PR to `docs/benchmarking/cli.md` and can add a sentence to `rust/src/bench/README.md` if that is preferred.

The note avoids calling this a worst case for TTFT: an open loop at a high request rate can have higher TTFT because of queueing. It only states that the pattern differs from staggered arrivals.

Limitations: the measurements come from one GPU, one model and one engine configuration; with other ratios of N to `max_num_batched_tokens` the waves may blur over time, hence "tend to finish together". A finite `--request-rate` below the concurrency limit gives staggered arrivals by construction; the effect of `--random-range-ratio` on wave synchronization is not measured yet.

AI assistance (Claude) was used to search for related issues and PRs and to draft the note; I reviewed every line. The measurements and their analysis are my own. The commit carries a `Co-authored-by: Claude` trailer.
