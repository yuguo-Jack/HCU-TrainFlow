# [ROCm] Portable Triton paged-MQA-logits kernel + vectorized torch fallbacks for the DeepSeek-V4 sparse indexer

[Upstream PR](https://github.com/vllm-project/vllm/pull/51555) · state: open · merged: False

## Original PR description

## Purpose

The DeepSeek-V4 sparse indexer's paged-MQA logits have two tiers on ROCm: the AITER Triton kernels (fp8 `tl.dot`), or a pure-python torch reference that loops over sequences/KV blocks with an `.item()` host sync per iteration, stalling the pipeline once per layer. Platforms whose Triton target cannot compile fp8 `tl.dot` — e.g. gfx1151 / Strix Halo (RDNA3.5), `Unsupported lhs dtype fp8e4nv` — could only use that reference.

Related discussion and full platform context: #51530.

## Changes

1. **Vectorize both torch fallback branches** (`next_n == 1` decode and `next_n > 1` verify): batched tensor ops, static shapes, no host syncs, no full-cache dequantization. The verify branch previously split values/scales per token, so on a block-flat page it multiplied by fp8 value bytes reinterpreted as the fp32 scale — that collapses the logits (~1e-18) or produces NaN. It now uses the same packed per-page layout as decode.
2. **Bound the fallbacks' memory**: both branches walk the paged range in 8192-token chunks instead of gathering every page-table slot at once, so a long `max_model_len` with short contexts cannot allocate several GB before masking anything out. Chunking is exact — each output position is still computed inside one chunk.
3. **Add `portable_fp8_paged_mqa_logits`**: a Triton kernel that dequantizes fp8 → bf16 in-kernel before `tl.dot` (the same pattern as the sparse-attention kernels already in this file), preferred over the torch reference in the existing no-AITER branch. On any failure it latches off and falls back to the torch reference.
4. **Gate the portable kernel on the page layout**: it reads pages in the block-flat layout, which is what `block_size == 1` produces and what the DSv4 C4A compressor writes. Ratio 1/2 caches are stored 16x16-tiled, so they keep the existing path instead of being read as if they were flat.

## Test Plan

`tests/kernels/attention/test_portable_fp8_paged_mqa_logits.py` (runs on any GPU, CUDA included):

- **numeric** — portable kernel vs `fp8_paged_mqa_logits_torch`: exact `-inf` mask equality, relative error and top-k overlap, across decode (`next_n=1`), verify (`next_n=6`) and edge shapes;
- **layout gate** — the portable kernel is used for `compress_ratio=4` and not for 1 or 2 when AITER is unavailable;
- **chunking** — chunked output bitwise equal to single-chunk output, decode and verify;
- **memory** — peak allocation stays under 1 GiB for a long `max_model_len` with short contexts.

## Test Result

Hardware: gfx1151 (Radeon 8060S, ROCm 7.14, torch 2.12), plus a CPU harness for the pure-torch paths. **11/11 tests pass.**

- Portable kernel vs torch reference over 6 shapes (decode, MTP `T=6/2/3`, 2-D `context_lens`, 32k `max_model_len`): max rel 2.4e-7–2.8e-7, top-64 overlap 1.000, `-inf` masks identical.
- Cold Triton compile from an empty cache: **1.13 s** — no fp8 MMA requirement, as intended for RDNA3.5.
- Timing at B=2, T=6, ctx=[64, 1930]: **0.066 ms vs 1.18–1.26 ms** for the torch fallback it replaces (~19x).
- Dispatch with AITER unavailable: `rocm_fp8_paged_mqa_logits` routes to the portable kernel (1 portable call, 0 torch calls), and tiled caches take the torch path unchanged.
- Memory bound for B=32, H=64, D=128, block 64, `max_model_len` 131072, all contexts 64: **5.62 GiB → 0.36 GiB**.

Writer layout, measured by scanning the bytes each writer leaves in a page on gfx1151:

| writer | page layout |
| --- | --- |
| `compress_norm_rope_store_triton` (DeepSeek-V4 compressor) | token-major: 128-byte runs at `slot * 128` |
| `indexer_k_quant_and_cache_triton`, block 64 | 16x16 tiled: 16-byte runs at 0, 16, 48, 256, 272, 304, 512, 528 |

Whole chain without model weights — 128 compressed tokens written by the real DeepSeek-V4 compressor kernel, the intended keys rebuilt independently in torch from the same inputs:

- production writer bytes vs that reconstruction: fp8 code delta **0/128 tokens**, scale difference **0.0**;
- reconstruction vs the baseline torch read path: max rel **0.0**, top-32 overlap 1.000;
- reconstruction vs the portable kernel: max rel **2.1e-7**, top-32 overlap 1.000.

Earlier end-to-end, kept for context: greedy outputs were byte-identical to the torch-fallback baseline while serving DeepSeek-V4-Flash-0731 on the 2-node gfx1151 cluster, and the per-layer host syncs were gone from decode profiles. That comparison pairs two readers that share the same page-layout assumption, so it is not evidence about the layout itself — the writer-level checks above are what pin that down.

Still to run: a full model forward with weights (the DeepSeek-V4-Flash-0731 weights were removed from the machine when the 2-node cluster was retired), TP=2 across two nodes, and CUDA-graph capture with the kernel inside a graph.

Confirming that per-page is the correct layout for the `next_n > 1` branch, with data from gfx1030 (8× Radeon Pro V620, ROCm 7.2.3 user space, `VLLM_ROCM_USE_AITER=0`, GLM-5.3-Flash with MTP on v0.30.0):

- **The writer is per-page.** The kpool compress kernel (`vllm/models/glm5next/amd/ops/kpool_compress.py`) writes each page as all fp8 values followed by all fp32 scales. The scale offset is `S_OFFSET_NBYTES_IN_PAGE = page_size * head_dim`. That's the layout the `next_n == 1` torch branch reads.
- **The current `next_n > 1` branch produces NaN.** It does `kv_cache[..., :dim]` / `[..., dim:]` on the `[num_blocks, block_size, 1, dim + 4]` view, i.e. per-token interleaving, so it multiplies by value bytes reinterpreted as scales. Against a layout-correct reference (the `next_n == 1` path applied per verify row), over 90 cases (next_n 1/2/3 × batch 1/4/8 × live context 700/2049/2100/9000/31000 × 1-D/2-D `context_lens`, `max_model_len` 32768), every multi-token case had **NaN inside the live context: 30 to 11,823 per case**.
- **Consequence:** on ROCm without aiter, MTP verification takes the indexer top-k from those logits. That's harmless below `index_topk` (every token is selected) and wrong above it.

We also have a **row-wise, CUDA-graph-capturable variant** for `next_n > 1`: each verify token becomes one row of an on-device `next_n == 1` loop, with a fixed trip count over `max_model_len`'s pages, a per-row key limit, and no `.item()`. It comes with the 90-case test (bitwise equal to the per-row reference, tie-aware top-k at k = 2048, 20/20 repeatable, capture and replay with changed lengths). - Omnicef · comment · 2026-09-26T03:41:22Z · [source](https://github.com/vllm-project/vllm/pull/51555#issuecomment-5842856286)

A correction to my comment above: "per-page is the correct layout" is only half right. The scales are per page (all values first, then all scales, at `page_size * head_dim`). But on ROCm the writers store the fp8 **values in 16×16 tiles** whenever `block_size > 1`:

- `indexer_k_quant_and_cache_triton` (DeepSeek-V3.2/V4): `layout = "NORMAL" if block_size == 1 else "SHUFFLE"`
- the GLM-5.3 kpool writer (`vllm/models/glm5next/amd/ops/kpool_compress.py`): `PRESHUFFLE=page_size > 1`

The in-page offset is `(t // 16) * 16 * D + (d // 16) * 256 + (t % 16) * 16 + d % 16`. The prefill gather (`cp_gather_indexer_k_quant_cache_triton`) reads that layout. The torch `next_n == 1` branch doesn't: it views each page as token-major `[block_size, D]`.

Measured on gfx1030 (ROCm 7.2.3, `VLLM_ROCM_USE_AITER=0`) with keys written by the real writers, against a reference taken from the writer's own output. Two runs gave identical numbers, and each reader was bitwise repeatable over 20 calls.

| writer | `next_n == 1` torch branch | max rel. diff | top-512 overlap |
|---|---|---|---|
| `indexer_k_quant_and_cache_triton`, block 64, 2,900 keys | as is | 1.77 | 0.18 |
| same | pages de-shuffled first | 1.3e-7 | 1.000 |
| GLM kpool writer, page 32, 2,358 pooled keys | as is | 1.90 | 0.23 |
| same | pages de-shuffled first | 1.4e-7 | 1.000 |

For this PR, that means the new Triton kernel, the vectorized fallbacks and `test_portable_fp8_paged_mqa_logits.py` all assume the token-major layout. The test builds its cache with `vals.reshape(num_blocks, block_size * dim)`. So they agree with the current torch branch, but not with what the ROCm writers put in the cache when `block_size > 1`. On the read side, the fix is one permutation per page before use:

```python
v.view(n, bs // 16, D // 16, 16, 16).permute(0, 1, 3, 2, 4).reshape(n, bs, D)
```

Filling the test cache through the writer, or applying the inverse permutation, would catch it.

What still stands: the old `next_n > 1` branch is per-token interleaved, which matches neither layout, and produces NaN. My 90-case test built its cache token-major too, so its reference was wrong for the values. I'll redo it with the real writers before offering the row-wise variant.
