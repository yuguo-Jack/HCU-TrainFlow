# [Bugfix][Rust Frontend] Bump fastokens to 0.3.5

[Upstream PR](https://github.com/vllm-project/vllm/pull/63707) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

The Rust frontend pins fastokens 0.2.1, whose regex split cache can give a prompt different token ids from Hugging Face depending on the previous prompt encoded on the same thread. This PR bumps fastokens to 0.3.5, which fixes the cache, and keeps the current non-truncating behavior. It covers the Rust frontend part of #63467.

## Claims

- Fixes wrong token ids for prompts that share a ≥4 KiB prefix with the previous prompt on the same thread and diverge inside a whitespace run, e.g. deeper indentation or a newline after trailing spaces. No error is raised today: the wrong ids decode to the same text.
- Ignores `tokenizer.json`'s `truncation` and `padding` in both backends, as the Python frontend does: transformers resets both on every call, and a few published checkpoints set `truncation.max_length` to 512–4096. fastokens 0.3.4+ starts applying them on encode, so the fastokens path clears them to keep main's behavior. The `tokenizers` fallback already applied them on main, silently cutting prompts for such a checkpoint when fastokens couldn't load it; it now clears them too.
- Tokenizers that 0.2.1 rejects (e.g. a `Replace` normalizer or `ByteFallback`/`Strip` decoders, as in Gemma 4) now load with fastokens instead of the `tokenizers` fallback.

## Validation

Served reproducer with `vllm-rs serve Qwen/Qwen3-0.6B` and `vllm-mock-engine` (aarch64). For each pair, one client sends B once, then A and B alternately 20 times to `/tokenize`, and compares each result with Hugging Face `tokenizers`:

| Pair | main | this PR |
| --- | --- | --- |
| ~6 KB prose + `def f():` with 4- vs 8-space indent | B wrong 20/21 | 0/21 |
| 5000 spaces + `x` vs 5000 spaces + `\n` | B wrong 20/21 | 0/21 |

A calls were right on both builds. The same pairs at crate level are wrong on 0.2.1 and right on 0.3.4 for the Qwen3, Qwen3.5, Llama 3.2, gpt-oss and GLM tokenizers. DeepSeek-V3.2 is right on both.

- New test `fastokens_encode_does_not_depend_on_previous_input` fails on main and passes here. The fixture uses a split regex with Qwen's whitespace alternatives and a `Ġ Ġ` merge, so the pieces' boundaries show up in the ids.
- `assert_ordinary_matches_added_empty` now asserts for both backends that the fixture's `truncation` is ignored. The fastokens test fails without `set_truncation(None)`, and the HF test fails without `with_truncation(None)`.
- `cargo test --workspace` (2307 passed) and `cargo clippy --workspace --all-targets -- -D warnings` pass.
- Gemma 4, TinyLlama, ERNIE-4.5 and LFM2.5 tokenizers, which move off the `tokenizers` fallback: 0 encode and 0 decode differences from Hugging Face on 400 text slices each (37 B–40 KB).
- Encode cost with the Qwen3 tokenizer, 320 prompts of 128 KB each, 32 cores. CPU time per prompt drops from 8.1 / 7.0 / 6.0 ms to 1.25 / 1.13 / 1.10 ms at concurrency 1 / 8 / 32. Wall time per batch drops from 296 / 115 / 89 ms to 54 / 53 / 52 ms.

## Details

Root cause: fastokens' regex `Split` keeps a thread-local cache of the previous input's matches. When the next input shares at least 4096 bytes with it, matches ending inside the shared prefix are reused. Whitespace alternatives such as `\s+(?!\S)` and `\s*[\r\n]+` depend on bytes past the end of the match: in `"    x"` the run stops one space early, and with `\n` there the whole run is one piece. So a reused match near the divergence point can be wrong. crusoecloud/fastokens#78 (released in 0.3.4) reuses only matches that end before the whitespace run leading up to the unseen bytes. 0.3.5 adds a Python-binding deadlock fix and opt-in caches, and does not change the default encode path.

Changes in `hf.rs`:

- fastokens 0.3 adds `Decoder` variants. `is_byte_level_only` treats `Fuse` as a no-op, as before (0.2.1 parsed it as an empty `Sequence`). The new transforming decoders disqualify the byte-level decode fast path.
- `new_fastokens` and `new_hf` clear truncation and padding after loading.
