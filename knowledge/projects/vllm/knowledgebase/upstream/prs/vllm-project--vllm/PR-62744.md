# [Bugfix][Reasoning] Accept all K2 Horizon end-of-thinking tags regardless of reasoning_effort

[Upstream PR](https://github.com/vllm-project/vllm/pull/62744) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

K2 Horizon often closes `medium`/`low` thinking with `</ifm|think>` (the `high` end tag), but `K2HorizonReasoningParser` only looks for the end tag of the requested `reasoning_effort`. This PR treats any of the three K2 Horizon end tags as the end of reasoning, and ends reasoning at the earliest boundary, so an end tag inside a tool call that has already started no longer moves the split.

Fixes #62743. Related: #60969 (see Details).

## Claims

- With `reasoning_effort` `medium` or `low`, output closed by `</ifm|think>` is split into `reasoning` and `content` in both streaming and non-streaming. Before, non-streaming put the reasoning, the literal `</ifm|think>` and the answer in `content`, and streaming put the whole answer in `reasoning`.
- Reasoning ends at the earliest end tag or `<ifm|tool_calls>`. When the tool-call start comes first, the whole tool block stays in `content`, even if its text contains an end tag (for example a tool argument with `</ifm|think>`), and the result no longer depends on how the stream is chunked. On `main` the review example was already wrong for `high` (non-streaming and multi-token deltas split inside the tool call and lost it); the first commit of this PR extended it to `medium`/`low`.
- `is_reasoning_end`, `is_reasoning_end_streaming` and `extract_content_ids` use the same set of end tokens as extraction, so the structured-output gate agrees with the frontend about where an explicit end is.
- Output closed by the effort's own end tag parses as before. The start token is still chosen by effort.

## Details

Root cause, part 1: `_EFFORT_TOKENS` maps each effort to one start/end pair, and every boundary check (`_split_model_output`, the streaming buffer search and its partial-tag hold-back, `is_reasoning_end`, `is_reasoning_end_streaming`, `extract_content_ids`) looked only for that effort's end tag. The chat template opens `medium` thinking with `<ifm|think_fast>` and `low` with `<ifm|think_faster>`, but in raw runs the model closed `medium` thinking with `</ifm|think>` 40 of 40 times, and tool-less `low` thinking 5 of 20 times. The parser then never saw an end.

Root cause, part 2 (found in review, thanks @adenzhou1350): `_split_model_output`, the streaming buffer and `extract_content_ids` checked for an end tag before looking for `<ifm|tool_calls>`. An end tag inside a tool call that started earlier therefore won whenever both were in the text being checked: in non-streaming and in a multi-token delta, but not when streaming one token at a time, which stops at the tool-call start. On `main` only the requested effort's own end tag could trigger this (in the review example, `</ifm|think>` under `high`); accepting all three end tags made `</ifm|think>` trigger it under `medium`/`low` too.

Fix: `_END_TOKENS` (the three end tags) and `_end_token_ids` are accepted as ends of reasoning whatever the effort. `_find_boundary` returns the earliest of them and `<ifm|tool_calls>`: content starts after an end tag, or at the tool-call start, which stays in the content. `_split_model_output` and the streaming buffer use it, and `extract_content_ids` does one forward scan that stops at the first end-token id or tool-call-start id. `is_reasoning_end` scans backwards and already returns `True` for either boundary. The start token stays per effort because the template emits it. `end_token` and `reasoning_end_str` still return the effort's own tag, so anything that inserts an end tag keeps using the one the template expects. Unchanged from `main`: `is_reasoning_end_streaming` does not treat `<ifm|tool_calls>` as an end.

Relation to #60969: that PR makes non-streaming return output with no boundary as `reasoning` with `content: null`, matching streaming. Without this fix, `medium`/`low` output closed by `</ifm|think>` has no recognised boundary, so #60969 alone would also move the whole answer into `reasoning` for non-streaming requests. The two PRs change different lines and can land in either order: a three-way merge of both files is clean, and the merged test file passes (26 tests). With both, unfinished output is reasoning and finished output is split correctly.

Not a duplicate: I searched issues and PRs for "K2 Horizon", "k2_horizon", "ifm|think" and "think_fast". #60969 handles output with no end tag. #55195 is about multi-token deltas in `BaseThinkingReasoningParser`, whose streaming path K2 Horizon overrides. #57768 adds regex timeouts to the K2 Horizon tool parser.
