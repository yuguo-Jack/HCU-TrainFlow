# [Rust Frontend] Count gpt-oss reasoning tokens like Python

[Upstream PR](https://github.com/vllm-project/vllm/pull/63960) · state: closed · merged: True

## Original PR description

## Overview

For gpt-oss, the Rust frontend always reports `usage.completion_tokens_details.reasoning_tokens: 0`, even when the response has `reasoning` content. Python counts them since vllm-project/vllm#58626: `HarmonyParser._is_reasoning_token` counts a generated token when the Harmony parser places it in an `analysis` message, or in a `commentary` message with a recipient (a tool call), and it is not a Harmony control token (`<|channel|>`, `<|message|>`, `<|end|>`, ...). Chat Completions and Responses share that rule. The native Harmony output processor (`rust/src/chat/src/output/harmony/mod.rs`) never measured reasoning tokens: every reasoning delta carried `token_count: None` (with a TODO), and the final usage was built with `finished.usage.into()`, which sets `reasoning_tokens: 0`. This PR applies Python's rule in the processor.

## Claims

- The final `usage.completion_tokens_details.reasoning_tokens` for gpt-oss matches Python: tokens in `analysis` messages and in `commentary` messages with a recipient are counted; `final` content, commentary preambles without a recipient, header tokens and Harmony control tokens are not.
- Each reasoning text delta carries the tokens of its own text as `token_count`, so `stream_options.continuous_usage_stats` reports reasoning tokens as they stream, like the unified parsers. A token whose content delta is still empty (a split UTF-8 character) is attributed to the next delta of the same message.
- Tool-call tokens, which Python also counts as reasoning, have no text delta to carry them, so they reach the client only through the final usage.

New tests in `output/harmony/tests.rs`, ported from Python's `TestCountReasoningTokens` (`tests/parser/test_harmony.py`):

- `reasoning_tokens_count_analysis_and_tool_call_content`: analysis text plus a `commentary to=functions.get_weather` call counts both bodies' content tokens, without header or control tokens; the deltas carry the analysis tokens only.
- `reasoning_tokens_exclude_final_and_preamble_content`: a commentary preamble without a recipient and a final message count 0.
- `reasoning_tokens_are_attributed_to_their_streamed_deltas`: one token per decoded update across two analysis messages; each delta carries exactly one token, the separating newline none, and the final count equals the analysis content tokens.
- `reasoning_tokens_of_a_split_character_join_its_delta`: characters that span several byte-level tokens; the tokens that produce no text yet are counted on the delta that completes the character.
- `interrupted_analysis_message_is_preserved` now expects `reasoning_tokens: 1` instead of 0.

Red-green: with the fix reverted, the three positive counting tests and the updated `interrupted_analysis_message_is_preserved` fail; the exclusion test passes on both, as a negative guard.

## Details

- `HarmonyState` applies Python's rule to each token right after the Harmony parser consumes it. Header tokens are not counted, because the oss-harmony parser reports a channel only once the header is complete (in `StreamState::Content`), and control tokens are excluded with the encoding's `is_special_token`.
- The total goes into `ChatTokenUsage::reasoning_tokens` on `Done`, so the final `usage` matches Python.
- Each reasoning text delta carries the tokens of its own text as `token_count`, which feeds continuous usage like the unified parsers do.

**Ownership and layering.** The Harmony output processor in `vllm-chat` is the only Rust consumer of the generated Harmony token IDs (it drives `StreamableParser` over them), so it is the one place that knows each token's channel and recipient. It reports the count through the existing `token_count` and `ChatTokenUsage` path that the server already turns into `completion_tokens_details`; nothing in `vllm-server` changes.

**Known gap.** Tool-call tokens reach continuous usage only at `Done`, while Python counts them as the call streams. No text delta carries them, and widening the tool-call events for a usage counter is out of scope here.

**Scope.** This PR only counts. Whether `completion_tokens_details` is serialized at all when no reasoning parser is configured is a separate change.

Python reference: vllm-project/vllm#58626 (`HarmonyParser.count_reasoning_tokens`, `_is_reasoning_token`).

Not a duplicate: no open PR counts gpt-oss reasoning tokens in the Rust frontend.
