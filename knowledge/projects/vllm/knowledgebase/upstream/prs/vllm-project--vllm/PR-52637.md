# [Quantization][ROCm] Fix symmetric GPTQ loading and optimize RDNA INT4 repacking

[Upstream PR](https://github.com/vllm-project/vllm/pull/52637) · state: open · merged: False

## Original PR description

## Purpose

This PR fixes redundant zero-point handling during symmetric GPTQ loading and reduces the cost of RDNA hybrid INT4 weight preparation.

**GPTQ loader fix.** Symmetric GPTQ `uint4b8` uses a fixed zero point of 8, but checkpoints may still contain packed `qzeros`. Passing these redundant checkpoint zero points to RDNAHybrid can fail during startup, for example:

```text
Zero points must be [320, 16] but got [16, 320]
```

The cleanup lives in `AutoGPTQLinearMethod.process_weights_after_loading()`. GPTQ still registers and loads `qzeros` normally; after loading, the loader removes the checkpoint tensor when the selected kernel has `zero_points=False`, before backend preprocessing. This handles the mismatch at the shared loader boundary.

Only the tensor is removed: `kernel.w_zp_name` stays intact. Symmetric CPU W4A16 can leave zero points unset, while CPU W4A8 can use the retained name to create its required fake zero point. ExLlama and Marlin can likewise create their runtime zero points or placeholders. Explicit-zero-point processing is preserved.

**RDNA loading optimization.** The hybrid preprocessing introduced in #40977 expands every packed INT4 value to INT32, then repacks it into ExLlama order. Reuse the existing `gptq_shuffle` on a contiguous packed clone instead, followed by the transpose into the existing runtime layout. The clone protects checkpoint storage from the in-place shuffle; inference kernels and dispatch are unchanged.

Duplicate checks: #47770/#48998 address Triton zero-point handling; #43389 covers MoE repacking and #46676 covers MXFP4 kernels. Inspected #55711 concerns adjacent stride/layout changes while retaining full unpack/repack. None of these inspected changes implements this combined fix. Public searches were used because GitHub CLI checks were unavailable; coverage is not exhaustive.

OpenAI Codex assisted with implementation, review, and validation.

## Test Plan

The loader regression verifies that redundant `qzeros` is removed before backend processing, its name is preserved, and a backend can register a replacement. Existing RDNA tests cover CT/GPTQ layouts, group sizes 32/64/128, noncontiguous inputs, checkpoint preservation, explicit zero points/scales, and a shuffle tail at N=136.

## Test Result

TinyLlama AutoGPTQ fails on the unmodified upstream RDNAHybrid path with the shape error above and passes with loader cleanup. A targeted CPU W4A8 zero-point replacement check passed, and `JunHowie/Qwen3-8B-GPTQ-Int4` completed end-to-end inference.

Validation of the combined change: **107 tests passed**; pre-commit, mypy 3.12, and diff checks passed. Qwen3-4B-GPTQ and Qwen3-VL-4B compressed-tensors each produced identical hashes for 144 prepared weights and identical token IDs, text, and top-3 logprobs for four greedy prompts. A GPTQ GSM8K regression sample remained **10/16** in both arms.

Performance comparison uses the same loader fix in both arms, changing only repacking. Radeon 8060S/gfx1151, torch 2.13.0+rocm10.0.0; MRV2, TP1, BF16, eager, ROCM_ATTN, AITER/prefix caching disabled, max length 2048, max sequences 4, KV cache 2 GiB. This PR fixes a startup crash we hit with the official AMD image on **gfx1151** (Strix Halo, Radeon 8060S), on two official Qwen symmetric GPTQ checkpoints. Here is the evidence and the cost of the current workaround, in case it helps with review.

### Environment

- Image: `docker.io/rocm/vllm:rocm10.1.0_ubuntu24.04_py3.14-pytorch_2.13.0_vllm-0.29.0`
- vLLM: `v0.29.1.dev0+g98dff2a81` (built 2026-10-02)
- Stack: PyTorch 2.13, ROCm 10.1; host ROCm 10.0, kernel 7.2.7
- Hardware: AMD Ryzen AI Max+ 395, Radeon 8060S (gfx1151), 128 GB unified memory
- Serve flags: `--max-model-len 32768 --max-num-seqs 32 --max-num-batched-tokens 8192 --gpu-memory-utilization 0.90 --no-enable-prefix-caching`, with `VLLM_ROCM_USE_AITER=0`

### Failure

The log selects `Using RDNAHybridW4A16LinearKernel for AutoGPTQLinearMethod`, then the profile run fails in `triton_w4a16_skinny_fmt_gemm`:

| Checkpoint (all `bits=4, group_size=128, sym=True, desc_act=False`) | Error |
|---|---|
| `Qwen/Qwen2.5-7B-Instruct-GPTQ-Int4` @ `e9c932ac1893` | `AssertionError: zp shape mismatch: torch.Size([28, 576]) vs (4608, 28)` |
| `Qwen/Qwen3.5-27B-GPTQ-Int4` @ `8f0c09f227ae` | `AssertionError: zp shape mismatch: torch.Size([40, 4352]) vs (34816, 40)` |

In both cases the checkpoint's redundant `qzeros` arrive still packed (`[K/G, N/8]`). The fix described in this PR, dropping them when the selected kernel has `zero_points=False`, matches what we see.

`Qwen/Qwen3.5-35B-A3B-GPTQ-Int4` loads fine. Its experts go through `TritonWNA16Experts`, and its attention and GDN layers stay BF16 in that checkpoint.

### Workaround cost

Disabling the kernel (`VLLM_DISABLED_KERNELS=RDNAHybridW4A16LinearKernel`, equivalent to `--linear-backend TRITON` from #51971) makes both models load through `TritonW4A16LinearKernel`. That path is much slower than BF16 of the same model.

Setup for the table: tok/s, fresh server per config, prefix caching off, synthetic prompts of exact length, median of 3.

| | 7B BF16 | 7B GPTQ (Triton) | 27B BF16 | 27B GPTQ (Triton) |
|---|---|---|---|---|
| Prefill, 512-token prompt | 2,173 | 1,070 (0.49×) | 551 | 217 (0.39×) |
| Prefill, 16k-token prompt | 1,342 | 322 (0.24×) | 315 | 93 (0.30×) |
| Prefill, 8 × 2k concurrent | 2,006 | 366 (0.18×) | 431 | 105 (0.24×) |
| Decode, 1 stream | 16.6 | 10.5 (0.63×) | 4.3 | 3.0 (0.69×) |
| Decode, 8 streams (per stream) | 15.4 | 10.5 (0.68×) | 4.0 | 2.8 (0.70×) |

So on gfx1151 today, symmetric GPTQ dense models either fail to start or run on a path that is 3–5× slower at prefill than BF16. Landing this fix would let them use the RDNA hybrid kernel, which, with the recent gfx1151 work (#52619, #57199, #60644), should be the fast path.
