# [Rust Frontend] Implement the scale-out render routes on the main server

[Upstream PR](https://github.com/vllm-project/vllm/pull/65180) · state: open · merged: False

## Original PR description

## Overview

Python registers the scale-out render routes together with `/inference/v1/generate`; on the Rust frontend they existed only as the 501 placeholders merged in #62432, while the real rendering pipeline already ships in the standalone `vllm-rs render` server, driven by a dedicated `RenderState`. This PR wires the same pipeline into the main OpenAI router when `--enable-scale-out` is passed.

### Claims

- `POST /v1/chat/completions/render` returns one `GenerateRequest` and `POST /v1/completions/render` returns a one-element list of `GenerateRequest`s on the main server, matching the Python frontend (`vllm/entrypoints/scale_out/render/api_router.py`), Python's echo semantics (transfer params hoisted top-level, `chat_template_kwargs` carried via `reasoning_parser_kwargs`), and the standalone Rust render server.
- The handlers reuse the serving processors the chat and completions routes already hold (`ChatRequestProcessor` + `TextRequestProcessor` from `AppState.chat`), so no second model load or engine handshake happens — mirroring how the Python frontend serves the render endpoints next to generation.
- Requested model names resolve against the dynamic LoRA registry per request, exactly like `/inference/v1/generate`, so a load adapter's name is a valid render target.
- Output budgets above the engine-reported context window are rejected with the same 400 as the chat and completions routes (`max_completion_tokens=... cannot be greater than max_model_len=...`).
- The standalone `vllm-rs render` server keeps its existing behavior: both server flavors now share one `RenderCore` (borrowed processors + validated model names) instead of the handlers being `RenderState`-bound.
- Without `--enable-scale-out`, the two routes still answer 403 with the "Scale-out endpoints are disabled" message, like the other scale-out routes.
- The remaining scale-out routes (`/v1/messages/render`, `/v1/responses/render`, `/v1/chat/completions/derender`, `/v1/completions/derender`, `/inference/v1/abort_requests`) keep their 501 placeholders; derender has active open PRs (#53418, #53419).

## Tests

- `scale_out_render_chat_returns_generate_request_with_header_request_id` and `scale_out_render_completion_returns_generate_requests`: enabled-router happy paths, including request-id sourcing, stream/stream-options echo, cache salt, priority, and the completions list shape.
- `scale_out_render_chat_response_can_be_submitted_to_generate_unchanged`: the rendered request is posted to `/inference/v1/generate` untouched; the mock engine asserts the prompt token ids, reasoning kwargs, and KV/EC transfer params arrive exactly as rendered (same contract the standalone render server is tested with).
- `scale_out_render_rejects_max_tokens_above_max_model_len`: both routes 400 above the context window with the exact error strings.
- `scale_out_render_routes_follow_scale_out_gate`: the implemented routes are validated like ordinary OpenAI routes (400, not 501/404) when scale-out is on, and still 403 behind the gate when it is off.
- The pre-existing `unimplemented_scale_out_routes_follow_scale_out_gate` keeps asserting the 501 behavior for the five not-yet-implemented scale-out routes.
- The pre-existing standalone render server tests keep passing unchanged.
