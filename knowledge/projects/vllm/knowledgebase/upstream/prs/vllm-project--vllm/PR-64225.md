# [ROCm][Perf][GLM-5.3-Flash] MonoKernel: pad a narrow step's inputs once, not every layer (on #61662)

[Upstream PR](https://github.com/vllm-project/vllm/pull/64225) · state: open · merged: False

## Original PR description

## Overview

When a decode step has fewer tokens than the MonoKernel's width (one request on width 2, three on width 4), the runtime copied the four mHC inputs into padding buffers before each of the 41 kernel layers. This PR pads once, at the first kernel layer, and chains each layer's padded outputs straight into the next. At concurrency 1 it cuts median ITL by about 5%, and it doesn't change the kernels at all.

**Stacked on #61662**, which has not landed, so the diff against main includes it. This PR's own change is the last commit, `269796ffc2` (+73 / −6: `runtime/layers.py` plus tests). It is independent of #64207 (the Sinkhorn change, a different file), and the two stack cleanly. I'll rebase when #61662 lands.

**Independent of the KV cache dtype**: the change is in the runtime's per-layer glue, before any attention.

## The change

`FlashLayer.finish` slices each launch's width-S outputs down to the step's n rows for vLLM's layer interface, and `_pad` then copied them back into width-S buffers for the next launch. That is 4 device copies per kernel layer, 164 per step, each about 4 µs and serialized on the stream. `FlashLayer.inputs` now recognises the previous kernel layer's row slices (an identity check) and passes that layer's padded buffers on as they are. Anything else, such as the step's first kernel layer fed by vLLM's layer, is still padded.

The padding rows then carry the previous layer's padding outputs instead of fresh zeros. So a padding row is no longer constant zeros through the 41 layers: it carries garbage that evolves layer to layer, and it routes to whatever experts that state selects. Real rows don't see it, and the MonoKernel time above is unchanged. The kernels already keep each row's values in that row, finite or not; the tests now check this for every input:

- The FFN and KDA NaN-row checks poison all four inputs (`x`, residual, `post`, `comb`) of the padding row, not just one or two.
- The sparse-attention launch gains the same check, and also checks that a padding row writes nothing to the MLA, index or tail caches.
- A CPU test covers the chaining: a narrow step pads once, passes the padded outputs on, and pads again for any other input.

## Performance

Standalone A/B: #61662 at `0ea31fadbd` against this PR's `269796ffc2` (#64207 not included). TP2, FP8 KV, `--monokernel`, image `vllm/vllm-openai-rocm:nightly-rocm100-5d35ce3934a7804b298559d2d99eec33792e1eb9`, MI355X, HIP 6,7 for both arms. Two server boots per arm, interleaved; 10 x concurrency prompts per point; 1,024 output tokens; no profiler. ISL 1024 is real-text prompts, ISL 8192 random. Each cell is the mean of the two boots (per-boot values in parentheses).

| --- | --- | --- | --- | --- | --- |
| 1024 | 1 | 5.92 (5.92, 5.93) | 5.61 (5.62, 5.60) | -5.3% | -5.6% |
| 8192 | 1 | 6.09 (6.09, 6.10) | 5.78 (5.79, 5.77) | -5.2% | -5.2% |
| 1024 | 4 | 7.03 (7.03, 7.03) | 7.03 (7.03, 7.03) | 0.0% | -0.1% |

Output throughput at concurrency 1: +5.5% (ISL 1024) and +5.1% (ISL 8192). At concurrency 4 the steps fill the width, so this PR changes nothing, as expected. At ISL 1024 / concurrency 4 the mean ITL and tok/s vary between boots of the same arm (mean 8.02 vs 7.52 ms with the same median), so the medians and p90s are the numbers to read there.

From the concurrency-1 traces, device copies drop from 190 to 30 a step, and kernels from 420 to 260. Total MonoKernel time is unchanged (4,186 -> 4,177 us a step).

## Accuracy

The kernels are unchanged, and the real rows' outputs don't depend on the padding rows' contents (checked by the poisoned-row tests above), so outputs are bit-identical. Served greedy outputs aren't a usable check on this config, because it's nondeterministic between runs even for identical code (see #64207).
