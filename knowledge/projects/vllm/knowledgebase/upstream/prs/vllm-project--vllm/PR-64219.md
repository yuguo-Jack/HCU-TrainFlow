# [Rust Frontend] Report completion_tokens_details only when reasoning tokens are counted

[Upstream PR](https://github.com/vllm-project/vllm/pull/64219) · state: closed · merged: True

## Original PR description

## Overview

Report `usage.completion_tokens_details` only when the Rust frontend can count reasoning tokens, as the Python frontend does: on chat with a reasoning parser. Elsewhere it is now `null` instead of `{"reasoning_tokens": 0}`.

## Claims

| Route | Before | After (Python) |
|---|---|---|
| chat, reasoning parser configured | `{"reasoning_tokens": N}` | unchanged |
| chat, no reasoning parser | `{"reasoning_tokens": 0}` | `null` |
| completions, generate | `{"reasoning_tokens": 0}` | `null` |

New or changed tests:

- `usage_tests::token_usage_serializes_reasoning_token_details_only_when_counted`: `Some(3)`, `Some(0)` and `None` serialize as Python does.
- `chunk_stream_reports_reasoning_token_details_only_with_reasoning_parser`: every streamed usage reports `{"reasoning_tokens": 0}` with a reasoning parser and `null` without one.
- `non_stream_chat_returns_json_response` and `non_stream_completions_return_json_response` (HTTP, mock engine): `usage.completion_tokens_details` is an explicit `null`.
- `include_reasoning_false_suppresses_reasoning_in_non_stream_chat` (HTTP, auto-selected `qwen3` reasoning parser): hidden reasoning is still counted, `{"reasoning_tokens": 5}`.

Restoring the zero-filled details fails the first four tests; forcing the route's reasoning count off fails the last one.

E2E: `tests/entrypoints/openai/chat_completion/test_chat.py::test_single_chat_session` and `tests/entrypoints/serve/instrumentator/test_orca_metrics.py::test_single_completion` compare the whole usage with `CompletionUsage(...)` without details, and fail under the Rust frontend on `main` because of the zero-filled details.

## Details

Python sets `_include_reasoning_tokens_details = bool(reasoning_parser)` in `OpenAIServingChat` (vllm-project/vllm#45802); completions and generate never build the details. Rust always reported `{"reasoning_tokens": 0}`, because completions and generate share the chat `Usage` type, and vllm-project/vllm#54883 made the details always serialized. That claims zero reasoning where the frontend cannot count any: `null` means unknown.

- `Usage.completion_tokens_details` is `Option<CompletionTokenUsageInfo>`; `Usage::from_token_usage` takes the engine `TokenUsage` and the reasoning count as `Option<usize>`. It still destructures `TokenUsage` and `PromptCacheUsage` exhaustively, as in vllm-project/vllm#63292.
- The chat route counts reasoning tokens when `ChatLlm::reasoning_parser_name()` is set (the effective parser after `auto` resolution) and passes that to response collection and streaming. `ContinuousUsage` carries the count only when counting. Completions and generate pass `None`.

**Layering.** The usage shape is built in the `vllm-server` response layer, where Python's serving class makes the same decision from its configured reasoning parser; the reasoning count itself still comes from `vllm-chat`.

**Deviation.** Python dumps usage-only stream chunks with `exclude_none=True`, so it omits the key there, while Rust serializes `null`, as it already does for `prompt_tokens_details` on stream chunks; omitting unset stream keys is a separate follow-up.

Not a duplicate: overlaps vllm-project/vllm#63780, a first-time contributor's PR that changes chat stream key presence, including these details on chat streams. AI assistance (Claude Code) was used to prepare this change; the human submitter reviewed every changed line.
