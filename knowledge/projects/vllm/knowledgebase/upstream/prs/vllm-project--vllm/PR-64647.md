# [Kernel] Support width-7 causal conv1d

[Upstream PR](https://github.com/vllm-project/vllm/pull/64647) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Extend the Triton `causal_conv1d` prefill and decode kernels to kernel width 7. First step of #64645.

No open or closed PR touches the width branches of these kernels. The last change to them was #41617 (long sequence IMA fix).

## Claims

- `causal_conv1d_fn` handles widths 2 to 7. Before: 2 to 4.
- `causal_conv1d_update` handles widths 2 to 7. Before: 2 to 6.
- Both wrappers raise `ValueError` for widths outside 2 to 7. Before: a wider weight ran with no matching branch and returned wrong values.
- The existing width branches are untouched.

## Validation

- `tests/kernels/mamba/test_causal_conv1d.py`: width 7 added to all four tests, widths 5 and 6 added to the varlen prefill test. The `Mamba Kernels` GPU step and the ARM CPU step both run this file.
- New `test_causal_conv1d_rejects_unsupported_width` checks widths 1 and 8 in both wrappers. I ran its calls directly on macOS; the module skips there.
- I have no CUDA machine, so the Triton kernels are not run locally:
  - On the CPU platform, `pytest tests/kernels/mamba/test_causal_conv1d.py -k "varlen and not ragged"` passes, 96 tests. That is the torch reference, not Triton. The CPU decode tests need the compiled `_C` op, which I could not build; the C++ kernel loops over `state_len`, so it has no width limit.
  - A static check over the kernel AST confirms that for every width 2 to 7, each `col*` and `w_col*` the kernels read is assigned on every path after constexpr pruning. On main the check fails for widths 6 and 7 in the prefill kernel (`col0` unassigned when `load_init_state` is true).
- GPU CI is the real test for this change. WindChimeRan ran the full test file on a B300 (review below): all cases pass on this branch, and the parent commit fails the width-7 cases.
- hungho77 ran the full file with the width guard on an RTX 4070 Ti SUPER (sm_89): 324 passed.

## Details

LFM3 (LiquidAI, 2026-10-27) uses a depthwise causal conv of width 7 in 13 of its 24 layers. Both kernels unroll the taps per width by hand, with one `KERNEL_WIDTH == N` branch per width.

Before:

- Prefill: branches for widths 2 to 4. Width 5 has init-state loads but no weights, tap loop or shift, and widths 6 and 7 leave `col0` unassigned, so the launch fails to compile.
- Decode: branches for widths 2 to 6. Width 7 falls through the tap loop and multiplies `col0 * w_col0` seven times.

After:

- Both kernels have branches up to width 7, in the same unrolled form as the existing ones.
- Other widths fail loudly in the wrappers instead of in the kernels.

Nothing changes outside the two kernels and their tests. The model follows in a separate PR.

**Intent**

This PR extend the shortconv triton kernel, which is a pre-requisite to LFM3 model support. We cannot test it against real model e2e until full model support. So kernel test only below.

**My verification**

Validated on NVIDIA-B300: all 324 repository kernel tests and 291 additional reference checks passed, including the new widths, state updates, speculative decode, and chunked prefill→decode. The parent commit fails the width-7 cases, and sampled existing-width specializations compile identically. No blocking findings—LGTM for this kernel extension.

**Exp on possible future optimization (out of this PR)**

I benchmarked vLLM’s width-7 convolution against the fused gated-convolution implementation in SGLang PR. 

SGLang fuses three operations:
1. Input gating: `B * x`.
2. Causal depthwise convolution over the gated input.
3. Output gating: `C * conv_output`.

Conceptually, the unfused path is:

```python
B, C, x = BCx.chunk(3, dim=-1)
Bx = B * x
conv_output = causal_conv1d(Bx)  # Includes convolution-state updates.
y = C * conv_output
```

SGLang reads the packed `[B, C, x]` projection directly and performs these operations inside one kernel, avoiding intermediate gated-input and convolution-output tensors. The fused kernel also updates the convolution state.

For decode, this reduces three kernel launches to one. For prefill, SGLang additionally launches index clamping and an initial-state snapshot, so the complete operation still uses three launches.

**Default-settings benchmark**

NVIDIA B300 SXM6 AC, BF16, width 7, 2,048 channels. CUDA graph replay with cold L2; CUPTI timings, 100 repetitions per round across three rounds.

The measured operation includes both gates, convolution, and state updates, including SGLang’s prefill snapshot. Input/output projection GEMMs are excluded. All configurations below use the implementations’ default launch settings.

Latency in **µs; lower is better**:

vLLM unfused vs SGLang fused: 

| Workload | vLLM default | SGLang default |
|---|---:|---:|
| Decode, batch 1 | 6.66 | **2.34** |
| Decode, batch 8 | 11.74 | **2.50** |
| Decode, batch 128 | 13.54 | **5.15** |
| Decode, batch 512 | 19.46 | **12.42** |
| Prefill, 512 tokens | **16.03** | 157.20 |
| Prefill, 8,192 tokens | **116.67** | 167.62 |
| Prefill, 8 × 512 tokens | **62.00** | 159.20 |

With these defaults, SGLang’s fused path improves decode by approximately **1.6–4.7×**, but is slower for every tested prefill workload. Its default prefill configuration processes 256 tokens sequentially per block; for a single 512-token prompt, that produces only 32 blocks, limiting parallelism on B300.

Correctness checks passed against reference calculations, and updated states matched exactly. The implementations are not bit-identical: SGLang retains FP32 intermediates, producing approximately 0.34–0.38% relative L2 output difference from vLLM on the BF16 inputs tested.

- hungho77 · comment · 2026-11-02T07:56:35Z · [source](https://github.com/vllm-project/vllm/pull/64647#issuecomment-6572018414)

One suggestion: reject widths above 7 in the two wrappers, so the next wider kernel fails loudly instead of returning wrong values.

With this PR, a width-8 weight still reaches `_causal_conv1d_update_kernel`. Every `KERNEL_WIDTH >= N` load runs, so `col0` and `w_col0` are set. The tap loop and the state shift, though, only have branches up to `KERNEL_WIDTH == 7`. Width 8 therefore adds `col0 * w_col0` eight times and leaves the state unshifted, which is the same failure the description gives for width 7 on `main`. I found this by reading the code, not by running it.

The check I used on a branch with the same kernel change:

```python
# causal_conv1d_fn
_, width = weight.shape
if not 2 <= width <= 7:
    raise ValueError(f"causal_conv1d_fn supports widths 2 to 7, got {width}")

# causal_conv1d_update
_, width = weight.shape
if not 2 <= width <= 7:
    raise ValueError(f"causal_conv1d_update supports widths 2 to 7, got {width}")
```

With it in place, `pytest tests/kernels/mamba/test_causal_conv1d.py` gives 324 passed on an RTX 4070 Ti SUPER (sm_89), with torch 2.14.0+cu130 and Triton 3.8.0 on base `3d23773f10`. Your kernel change is applied unchanged. So this PR also passes on sm_89, alongside the B300 run.
