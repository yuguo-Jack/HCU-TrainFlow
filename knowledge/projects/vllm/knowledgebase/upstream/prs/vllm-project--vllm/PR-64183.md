# [Core] Fail pending utility calls when the engine dies

[Upstream PR](https://github.com/vllm-project/vllm/pull/64183) · state: open · merged: False

## Original PR description

## Overview

Fail pending utility calls when the engine output receiver exits, so control operations do not remain blocked after engine failure. This is the standalone split requested by @aoshen02 in https://github.com/aoshen02/vllm/pull/183, extracted from #58183.

## Claims

- Complete pending synchronous and asynchronous utility futures with `EngineDeadError` when their receiver stops.
- Remove waiters after send failure or caller cancellation, and tolerate late replies to removed or completed waiters.

## Validation

On H20, using main `06e172b5cf8845c80c40a6eaaecbcbde3e38e8df` and this standalone change:

- The same regression suite on unmodified main: **7 failed**.
- With this change: **7 passed**.
- Real H20 / Qwen3-0.6B / single GPU / eager mode: start generation, confirm a sleep request has reached the engine and is draining, then terminate that test EngineCore. On main, sleep remained pending two seconds after the output receiver stopped. With the fix, it raised `EngineDeadError` and the waiter map was empty.
- Applicable pre-commit checks, including mypy, passed.

The real-engine check covers the asynchronous client; synchronous receiver failures are covered by the regression suite. Existing compiled extensions and their generated interface were reused, rather than rebuilt.

Command: `.venv/bin/python -m pytest tests/v1/engine/test_engine_core_client_utility.py -q -rs`.

### Earlier integration evidence from #58183

The combined implementation at `c9171d7ad9eedd77d7633d5cdb0355018ff9b29a` was tested on four H20 GPUs (driver 580.126.09, PyTorch 2.14.0/CUDA 13, NCCL 2.30.7). A real TP2 restore out-of-memory test let one rank restore while the other failed under external GPU memory pressure: the control call failed and both workers were reaped. A helper test also combined a failed rank with a blocked peer and checked bounded helper termination.

These historical results exercise the combined checkpoint executor's failure path; they do not independently prove this standalone client's waiter cleanup. The new 7-case regression and real EngineCore-termination comparison above isolate that behavior. The earlier helper/executor suite had 129 passing tests, but that count belongs to the combined revision, not this two-file PR. See [the original validation](https://github.com/vllm-project/vllm/pull/58183).

## Details

Receiver errors previously reached the generation output queue but left separate utility futures pending. This changes the receiver cleanup and waiter lifetime; it does not implement CUDA checkpointing.

**Overlap:** #56416 addresses the same problem and additional cancellation cases. This PR is submitted as the explicit maintainer-requested split of #58183; these alternatives should be coordinated before merging. It is not a claim that no equivalent proposal exists. Cancellation before the async receiver coroutine starts is not added by this split.
