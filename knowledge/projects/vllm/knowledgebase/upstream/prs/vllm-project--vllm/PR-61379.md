# [Perf][Frontend] Skip O(n^2) per-chunk work in chat streaming generator

[Upstream PR](https://github.com/vllm-project/vllm/pull/61379) · state: open · merged: False

## Original PR description

## Overview

Removes two sources of quadratic per-request CPU cost from the chat
streaming generator loop (`chat_completion_stream_generator`). Both run
inside the asyncio event loop on every streamed chunk, so they add
latency jitter to all concurrent streaming requests.

## Claims

- Streaming chat requests no longer accumulate the full output text
  (`previous_texts[i] += delta_text`) when output logging is disabled
  (the default): that accumulation is O(text_len²) per request
  (subscripted string concatenation has no CPython in-place fast path)
  and its result was only ever read by the output-logging block.
  Measured 14.0 ms/request at 20k chunks / 80 KB streamed text; grows
  quadratically, ~0.03 ms at typical 1k-token responses. Removed entirely
  when logging is off; identical behavior when logging is on.
- Streams with `continuous_usage_stats` + a reasoning parser no longer
  copy the full generated-token list into a tuple on every chunk just to
  call `count_reasoning_tokens(Sequence[int])`. Calibrated against the
  full per-chunk counting path (8k-token reasoning stream): the copy is
  65.6 ms/request of a 868 ms/request path (7.6%) — the parser's
  full-scan recount itself remains quadratic and is not changed here.
- Behavior is unchanged in both configurations (identical streamed
  bytes); this is dead-work removal, not a headline speedup.

## Validation

Unit tests (mocked parsers, no GPU needed):

```
.venv/bin/python -m pytest \
  tests/entrypoints/openai/chat_completion/test_serving_chat.py -q
# 182 passed; 10 errors are TestGPTOSS* cases that spawn a
# RemoteOpenAIServer (need the vllm CLI + model download, unavailable
# in this environment; unrelated to this change)
```

- Updated `test_streaming_reasoning_usage_counts_across_deltas` to
  assert the call argument as a list — `count_reasoning_tokens` is
  documented `Sequence[int]`, the old assertion over-specified the
  caller.
- Added `test_streaming_output_logging_receives_full_text` to pin the
  log-enabled accumulation path that the new guard makes conditional.

Microbenchmarks (CPython 3.12, Apple Silicon; best of 5):

| cost                                        | per request | note                     |
|---------------------------------------------|-------------|--------------------------|
| `previous_texts +=`, 20k chunks / 80 KB     | 14.0 ms     | quadratic in output size |
| guarded accumulation (this PR, logs off)    | 0           |                          |
| `tuple()` copies, 8k-token stream           | 65.6 ms     | 7.6% of that counting path |

Note: end-to-end serving benchmark not included (no multi-GPU serving
environment available to the submitter for this change); the removed
work is pure Python overhead on the streaming path, quantified by the
microbenchmarks above, and the 182-test unit suite covers the
behavioral surface.

Not duplicating existing work: searched open PRs for
`count_reasoning_tokens`, `continuous usage streaming`, and chat
streaming perf; open reasoning-token PRs are counting-correctness fixes
for individual parsers. #56067 previously deferred recounts for
non-continuous streams; this is a continuation of that effort and does
not change when recounts happen.

## Details

- `previous_texts` is read in exactly one place, the final
  `log_outputs` block, which is gated on
  `enable_log_outputs and request_logger`. The accumulation is now
  gated on the same hoisted condition, so both branches (logging
  on/off) are provably unchanged; with logging on, the O(n²)
  accumulation remains — an accepted cost of an opt-in debug feature.
- Every `count_reasoning_tokens` implementation
  (`reasoning/*`, `parser/*`) only iterates/indexes/slices its
  argument, so passing the list directly satisfies the documented
  `Sequence[int]` contract; custom third-party parsers implementing
  the same signature are unaffected (the non-streaming chat path and
  the Responses API already pass lists).
