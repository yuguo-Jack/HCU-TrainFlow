# [HiSparse] Support the FlashInfer SM90 sparse MLA backend

[Upstream PR](https://github.com/vllm-project/vllm/pull/61277) · state: open · merged: False

## Original PR description

## Purpose

`FLASHINFER_MLA_SPARSE_SM90` (first sparse MLA choice on Hopper for NoPE models such as GLM-5.3-Flash) has no HiSparse path: it converts the logical top-k through `block_table` and reads the layer's paged KV, which holds stale rows for pages HiSparse offloaded. On GLM-5.3-Flash (TP4, H200, prefix caching on) GSM8K degrades across repeated passes on one server: 0.901 → 0.834 → 0.745.

This mirrors the HiSparse branch of the other sparse backends:
- decode rows and resident prefill-only batches: HiSparse physical top-k + hot cache;
- otherwise prefill rows: `stage_prefill_rows` + convert over the staging workspace.

SM90-specific: the backend plans one `BatchMLAPagedAttentionWrapper` per batch in `build()`. Decode-only and prefill-only batches keep that single plan (HiSparse's residency output keeps the indexer's valid-prefix layout, which the plan already assumes). Mixed decode + staged-prefill batches read two caches, so with HiSparse the builder plans the prefill rows in a second `_SM90State` (sharing the float workspace); its device `kv_end` clamp takes a row offset so it derives contexts from the right batch rows. Planning stays in `build()`, outside graph capture.

Not a duplicate: no open PR adds HiSparse to this backend. Companion: #61243 adds a `supports_hisparse()` capability; whichever lands second sets it to `True` for this backend.

## Test Result

Unit tests (H200): `test_flashinfer_mla_sparse_sm90.py` 32 passed; the new HiSparse cases fail on `main`.

GSM8K, GLM-5.3-Flash rev eb9eb208, 4x H200 TP4, bf16 KV, HiSparse (32 GiB host pool), prefix caching on, max_num_seqs 32, `--attention-backend FLASHINFER_MLA_SPARSE_SM90`, on top of #61243 + #60805 (needed for Flash to start with HiSparse). Three passes on one server: 1319 Q at concurrency 32 (twice), then 200 Q at concurrency 1:

| | c32 pass 1 | c32 pass 2 | c1 |
|---|---|---|---|
| before (`main` backend, HiSparse) | 0.901 | 0.834 | 0.745 |
| this PR, `--enforce-eager` | 0.911 | 0.915 | 0.930 |
| this PR, CUDA graphs (PIECEWISE) | 0.917 | crashed (see below) | – |

Both runs used `CUDA_LAUNCH_BLOCKING=1`. Two shared HiSparse issues on GLM-5.3-Flash block a clean graph-mode run. Neither is in this backend: FLASH_ATTN_MLA_SPARSE and FLASHMLA_SPARSE show the same failures.
- Without `CUDA_LAUNCH_BLOCKING`, an illegal memory access happens during the capture warmup (and in eager serving on the FA backend). Serializing launches hides it, which points to a missing cross-stream dependency in the HiSparse swap/convert streams.
- In graph mode, `HiSparse swap rows exceed the configured speculative decode capacity: stop=62, capacity=32`. The per-forward `_swap_step` reset (`prepare_group_for_batch`) only runs from the connector's `prepare_forward` or from `prepare_kv_cache_update`. The latter is inside the captured region, so it does not re-run on breakable-graph replay.

These go in separate PRs.
