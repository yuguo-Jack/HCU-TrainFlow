# [Rust Frontend] Support return_weight_versions

[Upstream PR](https://github.com/vllm-project/vllm/pull/64218) · state: closed · merged: True

## Original PR description

## Overview

Support `return_weight_versions` on the Rust frontend's `/v1/chat/completions` and `/v1/completions`, which a placeholder (vllm-project/vllm#62434) rejected with 400. Python returns the per-choice weight-version spans since vllm-project/vllm#61347.

## Claims

- With `return_weight_versions: true`, every finished chat and completions choice carries `weight_versions`, a list of `{version, start, end}` spans over output-token indexes, cut at the stop-string truncated output as Python does. Streaming puts the spans on the final chunk of each choice only.
- Without the option, responses are unchanged. `/inference/v1/generate` keeps returning spans on its final chunk only.

New tests:

- `vllm-text` `stream_stop_string_cuts_weight_version_spans_at_truncated_count`: a stop string ending inside a merged output that spans two more versions; the spans are cut at the truncated count (fails without the cut).
- `vllm-server` `openai_return_weight_versions_reports_spans_on_final_choice`: chat and completions × stream and non-stream × opt-in on and off, through the mock engine with a `v1` → `v2` weight update; spans only on the final choice when opted in (fails with the chat choice wiring reverted).
- `vllm-server` `generate_chunk_stream_returns_weight_versions_on_final_chunk_only` (fails without the final-chunk filter).
- The `vllm-llm` `stream_interval` test now expects cumulative spans on every output.

## Details

Python computes the spans in `OutputProcessor` over the stop-string truncated output (`_weight_version_spans`, `vllm/v1/engine/output_processor.py`). The data already reached Rust: `vllm-llm` tracks the engine's per-step `weight_version` label and builds the spans for `/inference/v1/generate`. The chat and completions paths dropped them.

- **`vllm-llm`**: `GenerateOutput.weight_versions` is now set on every output, as the spans over the output so far, instead of on terminal outputs only. The text layer can finish a request locally after matching a stop string, on an output the engine did not mark terminal, and then needs the spans to cut them, the way Python cuts them at its truncated token count.
- **`vllm-text`**: on the terminal output, the decoder cuts the spans at the stop-string truncated `output_token_count` (drops spans that start past it, clamps the last end) and carries them on `Finished` and `CollectedTextOutput`, next to `sampling_mask`.
- **`vllm-chat`**: the spans go through `AssistantEvent::Done`, `ChatEvent::Done` and `CollectedAssistantMessage`, like `kv_transfer_params`.
- **`vllm-server`**: the placeholder checks are removed; `ResponseOptions.return_weight_versions` gates the field on the non-streaming choice and the final streamed chunk. Completions choices gain the `weight_versions` field (`null` when unset on the non-streaming response, like Python).

**Layering.** `vllm-llm` owns the spans because it sees the per-step engine labels, including steps merged by `stream_interval`; `vllm-text` owns the cut because it owns stop-string truncation of tokens, logprobs and sampling masks. The server only decides per request whether to show them. The cost is one small `Vec` (normally one span) per output instead of per request; a per-output label instead of cumulative spans would lose exactness when outputs merge across a weight update.

**Deviations.** On streaming chunks the field is omitted when unset, as Rust does for `token_ids`, where Python sends an explicit `null` on the final chunk. Prompt-only echo (`echo` with `max_tokens: 0`) reports the span of its one internal token, as Python does.

Not a duplicate: no open PR adds `return_weight_versions` to the Rust frontend. AI assistance (Claude Code) was used to prepare this change; the human submitter reviewed every changed line.
