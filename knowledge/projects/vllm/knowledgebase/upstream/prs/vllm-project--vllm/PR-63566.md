# [Bugfix][KV Offload] Pin a shared-prefix junction when a sparse group cuts the offload hit

[Upstream PR](https://github.com/vllm-project/vllm/pull/63566) · state: closed · merged: True

## Original PR description



## Overview

Fixes #63565. On hybrid models with sparse retention (the default), a prefix that lives only in the CPU offload
tier is never reused by a request that diverges before the single stored Mamba/sliding-window state. The offload lookup
now pins a shared-prefix junction there, as the local prefix cache already does, so the prefix heals after one miss.

## Claims

- A revisit that shares a prefix but diverges inside the prompt's last block hits the offload tier from the second
  revisit on (today: never).
- No change when every group hits, when no full-attention group proves a hit, under dense retention
  (`prefix_cache_retention_interval=None`), or for models without a sliding-window/Mamba group.
- A junction set by the local prefix cache is never lowered.

## Details

Under sparse retention each request keeps one sparse-group checkpoint, in the last block of its prompt. A later request
that shares the prefix but diverges before that block finds its full-attention chunks in the offload tier but no Mamba
state at or below them, so `_lookup_complete_chunks` returns 0 for the whole request. The local prefix cache handles the
same geometry by returning a shared-prefix junction from `KVCacheManager.get_computed_blocks`
(`kv_cache_manager.py:318-326`); the recompute then retains the sparse state there. The offload lookup never set one,
so once the prefix had left the GPU cache every recompute stored its state inside the differing suffix again.

Change (`offloading/scheduler.py`):

- `_lookup_complete_chunks` records, in `RequestOffloadState.full_attention_hit_boundary`, the boundary the
  full-attention groups proved before the first sliding-window/Mamba group narrowed it (not on a deferred lookup).
- `get_num_new_matched_tokens`, when the final hit is shorter than that boundary and retention is sparse, raises
  `request.shared_prefix_boundary` to it.

No core change is needed: the scheduler sets the local junction before it calls the connector
(`sched/scheduler.py:1077-1089`), and everything downstream reads the request field: the align split stops a chunk
there (`sched/scheduler.py:610`), `SingleTypeKVCacheManager` retains it (`single_type_kv_cache_manager.py:511-518`), and
the aligned-boundary hand-off stores it to the offload tier.

Limits: the first revisit still misses (a first-visit hit needs a state retained below the replay boundary, which is
the subject of #57613). Connectors that set `hit_diverged` and load nothing re-read the local junction
(`sched/scheduler.py:1162-1172`) and can overwrite this one; the plain `OffloadingConnector` does not take that path.
If #62278 (junction as a tuple of positions) merges first, this needs a small rebase to add the junction to
`shared_prefix_boundaries`.

Why this is not a duplicate: searched on 2026-10-24 for "shared_prefix_boundary", "junction", "offload
shared_prefix_boundary", "offloading mamba junction" and "OffloadingConnector hybrid". #45238 is the GPU-cache form of
this geometry (main has the GPU junction, #47782 / #37898); #57613 retains a block below sliding-window replay boundaries (first
visit, different mechanism); #59146 keeps the prompt-end checkpoint; #56795 is a different offload-store bug; #52774
backfills GPU-local divergent hits only; #62400 adds junctions to the MooncakeStore connector; #63221 changes the
connector load boundary under EAGLE. None sets a junction from the `OffloadingConnector` lookup.
