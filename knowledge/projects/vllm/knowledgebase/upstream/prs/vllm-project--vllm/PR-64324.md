# [Bugfix] Forward shutdown() in LMCacheConnectorV1 so EngineCore is not force-killed

[Upstream PR](https://github.com/vllm-project/vllm/pull/64324) · state: open · merged: False

## Original PR description

## Overview

Fixes vllm-project/vllm issue 62808. `LMCacheConnectorV1` did not pass `shutdown()` on to the LMCache engine. Because of this, an LMCache thread kept EngineCore alive after SIGTERM, and EngineCore was force-killed after `--shutdown-timeout`. This PR adds `LMCacheConnectorV1.shutdown()`, which calls the engine's `shutdown()`.

## Claims

- With `LMCacheConnectorV1`, SIGTERM to `vllm serve` no longer ends in `force killing remaining process EngineCore`. LMCache's shutdown now runs on both the worker side and the scheduler side.
- The built-in connector now shuts down the same way as LMCache's own wrapper, `LMCacheConnectorV1Dynamic`.
- A new test, `test_engine_shutdown_stops_lmcache_threads`, fails without the fix and passes with it.

## Validation

Setup: 1 x NVIDIA H200 NVL, vLLM at `5d35ce3934a7804b298559d2d99eec33792e1eb9` with and without this commit, LMCache 0.5.6, torch 2.14.0+cu130. Settings from the issue: `--shutdown-timeout 28`, `kv_role: kv_both`, local-disk backend, TP=1. I picked the model (`Qwen/Qwen2.5-0.5B-Instruct`), the LMCache env values and the requests, because the issue does not name them.

The reproducer starts the server, sends 3 chat requests, sends SIGTERM to `vllm serve`, and counts two lines in the server log:

## Details

Root cause: `LMCacheConnectorV1` passes each connector call on to `self._lmcache_engine`, except `shutdown()`. So it inherited the no-op `KVConnectorBase_V1.shutdown()`. vLLM already calls `connector.shutdown()` on the scheduler side (`Scheduler.shutdown()`) and on the worker side (`ensure_kv_transfer_shutdown()`), but the call stopped at the wrapper. As a result, LMCache's `LMCacheConnectorV1Impl.shutdown()` -> `LMCacheManager.stop_services()` never ran. LMCache's `StorageManager` starts a thread named `storage-manager-event-loop`. It is not a daemon thread, it runs `loop.run_forever()`, and only `StorageManager.close()` stops it, which is reached only through that shutdown. So `EngineCore.shutdown()` returned, but at interpreter exit Python waited for that thread forever. To confirm this, I added temporary prints around `engine_core.shutdown()` in `run_engine_core`, on the unfixed code. They showed that `engine_core.shutdown()` returned at once, and that `storage-manager-event-loop` was the only non-daemon thread still alive besides `MainThread`.

The fix calls the engine's own `shutdown()`. It does not stop LMCache threads from vLLM, so the list of services to stop (health monitor, offload server, plugins, API server, lookup server and client, cache engine) stays in LMCache. LMCache's own `LMCacheConnectorV1Dynamic.shutdown()` makes the same call. The `hasattr` guard is for `kv_connector_extra_config.use_native: true`. In that mode the engine is the in-tree `lmcache_integration/vllm_v1_adapter.py:LMCacheConnectorV1Impl`, which has no `shutdown()`. Calling it without the guard would raise `AttributeError` during shutdown. The file already uses `hasattr` for other optional engine methods (`register_kv_caches`, `bind_connector_metadata`). `lmcache_mp_connector.py` already has its own `shutdown()`.

Limitations:

- This fix makes LMCache's shutdown run, so LMCache's `ZMQOffloadServer.close()` now runs too. It closes a ZMQ socket from one thread while `offload-server-thread` is blocked in `recv()` on the same socket. In 1 of the 6 runs, EngineCore aborted there with `Assertion failed: pfd.revents & POLLIN (src/signaler.cpp:238)`. That run had no force kill: the server was gone 2 s after SIGTERM, but the scheduler-side shutdown did not run. In the other runs, and in the control runs, LMCache logs `Offload server thread did not terminate within timeout` and waits 5 s. A standalone pyzmq script (pyzmq 27.2.0, libzmq 4.3.5) with the same pattern aborted in 88 of 200 runs and left the thread stuck in the other 112. This is an LMCache bug, LMCache's own wrapper reaches it the same way, and it should be reported to LMCache separately.
- On the worker side, LMCache's shutdown took about 6 s here, 5 s of which is that join timeout. With a very small `--shutdown-timeout`, EngineCore can still be force-killed before LMCache finishes.
- The new test builds a real `LLM` (`Qwen/Qwen3-0.6B`) with the engine in-process (`VLLM_ENABLE_V1_MULTIPROCESSING=0`), so that it can see LMCache's threads. It needs a GPU and the `lmcache` package. The GPU CI step that runs `v1/kv_connector/unit` is commented out in `.buildkite/test_areas/misc.yaml` ("Disabled until the KV connectors installation is locked"). Until that step is enabled again, this test runs in CI only like the rest of this file, which means it does not. It was run locally as shown above.
