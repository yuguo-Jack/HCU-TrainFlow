# [Bugfix][Multimodal] Use expanded prompt bounds for routed-expert outputs

[Upstream PR](https://github.com/vllm-project/vllm/pull/61097) · state: closed · merged: False

## Original PR description



## Overview

Fix routed-expert output boundaries for multimodal requests whose model-side prompt expands placeholder tokens into longer ranges.

## Claims

- Preserve all R3 routed-expert rows covering model-expanded multimodal prompts.
- Clamp `routed_experts_prompt_start` to the effective expanded prompt boundary.
- Keep text-only request behavior unchanged.
- Add regression coverage for multimodal expansion and P/D prompt cuts

## Validation

Direct connector assertions for expanded multimodal bounds and P/D prompt-cut clamping passed.

## Details

Request.num_prompt_tokens and Request.num_tokens can describe compact client-side token IDs, while the model executes expanded multimodal placeholder ranges from mm_features. The auxiliary-output connector previously used the compact lengths for routed-expert metadata and final slicing, which could drop or misalign image-expanded routing rows.

The fix derives effective model-side prompt and total lengths from multimodal placeholder ranges, uses those lengths for connector metadata and output slicing, and preserves the existing text-only path.

- aoshen02 · comment · 2026-10-16T13:47:09Z · [source](https://github.com/vllm-project/vllm/pull/61097#issuecomment-6216894015)

Thanks for tracking this down. The R3 regression you see is real, but I don't think vLLM keeps two coordinate systems for one request, so this change won't fix it.

**vLLM's scheduler already uses the expanded prompt.** The DeepSeek-V4.1 processor expands `<image>` through a regular `PromptReplacement` (`_get_prompt_updates` in `vllm/models/deepseek_v41/common/mm_preprocess.py`). The input processor runs that before it builds the `EngineCoreRequest`, so `prompt_token_ids` already holds the 270 expanded tokens. As a result:
- `Request.num_prompt_tokens` is 270, and the `mm_position` offsets index into that prompt.
- The scheduler never schedules more than `request.num_tokens`, so the worker cannot capture more rows than the scheduler expects.
- `routed_experts_prompt_start` is validated against the same expanded length.

The new branch only runs when a placeholder ends past `num_prompt_tokens`, which a real request cannot reach. The test reaches it by scheduling 270 tokens for a 78-token request.

**The misalignment is on the trainer side.** vLLM returns one row per token of the 270-token prompt it ran (`RequestOutput.prompt_token_ids` is that prompt). If the trainer holds the compact 77-token prompt and places rows by position, every row after the image is replayed on the wrong token. Nothing fails, and R3 ends up worse than no R3.

**The fix is on the trainer side, and which fix depends on your training forward.** If the trainer's LM runs the compact 77-token sequence, it isn't running what vLLM ran, and R3 can't apply until the prompt builder expands placeholders the way vLLM's processor does (that's what verl does for Qwen2.5-VL). If the trainer's model expands the image to 270 positions internally, the 270 rows are already right, and the trainer must place them on those expanded positions instead of slicing by the 77-token prompt length. Either way, `routed_experts_prompt_start` must use the same coordinate. Could you share how your fork builds `prompt_ids` for DSv4.1 multimodal, and whether the model forward expands the image internally? Meanwhile, we're adding a check in verl that fails loudly when the two prompts differ: https://github.com/verl-project/verl/pull/8263.

**Quick way to confirm:** print `len(output.prompt_token_ids)` on the client (or `len(request.prompt_token_ids)` in the scheduler). If it's 270, vLLM is consistent and #61097 can be closed.
