# [Bugfix][Scheduler] Don't split a multimodal item when a prefix cache hit ends inside it

[Upstream PR](https://github.com/vllm-project/vllm/pull/65271) · state: closed · merged: True

## Original PR description

## Overview

With `disable_chunked_mm_input`, the scheduler still splits a multimodal item when a prefix cache hit ends inside it and the step has no room for the rest of the item. Models with bidirectional attention over the item then prefill its first part without seeing the rest.

#52306 reported these splits and #52412 and #59721 fixed them, but this path remained.

## Claims

- When a cache hit ends inside a multimodal item, the request waits for a step that can schedule the rest of the item.
- Adds tests for a cache hit inside an image, at the scheduler and end to end.

## Validation

On base `51c6dfd8c`:

```text
pytest tests/v1/core/test_scheduler.py -k mm_input_chunking                                   # CPU
pytest tests/models/multimodal/generation/test_mm_prefix_lm.py -k cache_hit_inside_image      # L4
```

With the original `scheduler.py`, three of the new checks fail: the request that hit the cache is scheduled 39 tokens into the image, the guard returns 500 tokens for a chunk that starts inside the item, and end to end the 40 image tokens prefilled first differ from the request run alone (320 / 800 elements, max abs diff 8.5e-3). With the fix, all pass.

## Details

Root cause: the guard assumes a chunk never starts inside an item, which does not hold in these cases:

- The same image is followed by a different question. The last block of the image also holds the start of the question, so that block misses and the hit stops inside the image.
- The KV cache runs short. Blocks are reused tail first, so the hit can stop early in the image, leaving most of it.

With the flag on, startup checks that one item fits in a step (`max_num_batched_tokens`), so the request is not starved. A `long_prefill_token_threshold` smaller than the item stalls it, as it already does on main (#62031, #62030).

#62782 changes the same lines; the two combine in either merge order.

No open issue or PR covers this case (checked 2026-11-02).
