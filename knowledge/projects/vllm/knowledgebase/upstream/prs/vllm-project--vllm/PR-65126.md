# [Bugfix][Frontend] Reject API keys for the Python gRPC server

[Upstream PR](https://github.com/vllm-project/vllm/pull/65126) · state: open · merged: False

## Original PR description

## Overview

`vllm serve --grpc` accepts `--api-key` / `VLLM_API_KEY` but never enforces them: the Python gRPC server has no authentication, so a configured key is silently ignored and every RPC is anonymous. This PR makes it fail at startup instead, as the vLLM security team suggested.

## Claims

- The Python gRPC server refuses to start when an API key is configured through `--api-key`, `api_key` in `--config`, or `VLLM_API_KEY`. This covers every way to launch it: `vllm serve --grpc`, `python -m vllm.entrypoints.launchers.grpc_server`, the deprecated `vllm.entrypoints.grpc_server`, and smg's Rust servicer (`SMG_VLLM_SERVICER_IMPL=rust`).
- No change for API keys on HTTP serving, `vllm launch render` or the Rust frontend's `--grpc-port`. `VLLM_API_KEY=""` is still accepted, because HTTP does not treat it as a key either.

## Validation

| `VLLM_API_KEY=k python -m vllm.entrypoints.launchers.grpc_server --model <m>` (also the deprecated alias) | starts, no auth | `ValueError` |

The new tests fail on main and pass with this change:
- The three `test_cli_args.py` rejection tests fail with `DID NOT RAISE ValueError`.
- The `main()` test with the Rust servicer reaches smg's Rust dispatch instead of raising.

The `test_cli_args.py` tests run in the "Entrypoints Unit" Buildkite step. `test_grpc_auth.py` is selected by the same step but skipped there, like the existing `test_grpc_health.py` and `test_grpc_shutdown.py`, because the CI image does not install `smg-grpc-servicer`. Every release since 0.8.0 needs `grpcio>=1.81.1`, while the test lock pins 1.78.0. I validated those paths locally with smg-grpc-servicer 0.14.1.

## Details

**Root cause:** the `--grpc` branch of `ServeSubcommand.cmd` calls `serve_grpc(args)` before the HTTP app, and with it the `AuthenticationMiddleware`, is built. The launcher calls `add_insecure_port` with no interceptor.

**Fix:** a `validate_grpc_auth_args` check, using the same "is a key configured" rule as the HTTP middleware, runs in three places:
- `ServeSubcommand.validate()`, so `vllm serve` fails before engine startup. It is not in the shared `validate_parsed_serve_args()`, because `vllm launch render` reuses that and serves HTTP. A test pins this.
- The launcher's `main()`, because smg's servicer switch can replace `serve_grpc` with its Rust servicer, which never reaches the check inside it.
- `serve_grpc()`, for programmatic callers.

**Why reject instead of implementing auth:** the server is plaintext only, so a bearer key would travel in the clear. The security guide already treats gRPC as an internal interface to protect at the network level.

**Rust `--grpc-port`, unchanged:** API keys protect its HTTP endpoints but not its gRPC services. Rejecting the combination would break valid deployments that protect HTTP with a key and keep gRPC internal. A warning that then ignores the key is what `rust/AGENTS.md` rules out. The proper fix is to enforce keys on those services in a separate Rust PR. The security guide now states the limitation.

**Docs:** since #59659, the security guide's gRPC section describes `--grpc-port`. I added the Python `--grpc` server there and documented which of the two API keys apply to. I also added short notes to the Kubernetes gRPC recipe, the quickstart's API key paragraph, and the `VLLM_API_KEY` reference.

**Duplicate check:** no open PR covers this. #49020 and #56046 rename `--grpc-port` in the security guide; since #59659 they are outdated, and they do not overlap with this PR. #42721, which tried adding auth to the gRPC server, was closed.

**Behavior change:** `vllm serve --grpc` with an exported `VLLM_API_KEY` now fails to start, where before the key was silently not enforced.
