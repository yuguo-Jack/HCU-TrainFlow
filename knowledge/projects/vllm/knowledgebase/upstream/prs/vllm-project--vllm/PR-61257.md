# [Model Runner V2] Enable batch-sharded sampling for GPT-OSS

[Upstream PR](https://github.com/vllm-project/vllm/pull/61257) · state: closed · merged: True

## Original PR description

## Overview

Fixes #61256.

Enable batch-sharded sampling for GPT-OSS by implementing
`GptOssForCausalLM.compute_logits_local`.

Without this hook, the V2 runner falls back to regular sampling even when
batch-sharded sampling is enabled.

## Claims

- Reuse the existing logits processor with `skip_gather=True` to return
  rank-local vocabulary logits.
- Preserve the default sampling path when sharding is disabled.
- Extend coverage to GPT-OSS and retain Llama coverage, including a
  single-request case that leaves one TP rank with no sampling requests.

## Validation

### Correctness and regression tests

Local validation used two NVIDIA L20 GPUs with TP=2, Python 3.12.14,
PyTorch 2.13.0+cu129, and source base
`61f084b5f3e58aa3d3ebc86aeaf4686c460c478`.

GPT-OSS tests use the organization-hosted checkpoint
`trl-internal-testing/tiny-GptOssForCausalLM`, with both model and tokenizer
pinned to `e82685101216af1953707faa42567d232a5e4d45`.

- `test_sharded_sampling.py`: **12 passed**, including all three GPU cases:
  `llama`, `llama-empty-rank`, and `gpt-oss`.
- GPT-OSS stability check: **10/10 independent-process runs passed**,
  with no skips or retries.
- Shared sharder and dry-sampler regression tests: **18 passed**.

The E2E cases compare generated tokens and log probabilities between
regular and sharded sampling. When sharding is enabled, the generic
helper also checks rank-local vocabulary width and exact equivalence
between gathered local logits and full logits.

Negative tests confirmed that:
- Removing the GPT-OSS hook fails the sharding-enabled assertion.
- Returning full logits from either the GPT-OSS or Llama hook fails the
  shard-width assertion.

Local Llama validation used the ModelScope mirror
`LLM-Research/Llama-3.2-1B-Instruct@master`. The committed test retains
`meta-llama/Llama-3.2-1B-Instruct`.

Relevant checks were run individually and passed. The full pre-commit
invocation was terminated during hook-environment installation, so a
complete pre-commit pass is still pending. Upstream GPU CI remains pending.

### Performance

Previously measured with GPT-OSS-20B on 2× L20, TP=2, concurrency 256,
256 input tokens and 128 output tokens. Each configuration used three
independent server runs, with 8 warm-up and 512 measured requests per run.

| Sampling | Baseline output tok/s | Sharded output tok/s | Throughput change | Mean TPOT change |
| --- | ---: | ---: | ---: | ---: |
| temperature=1, top_p=1 | 4385.4 | 4582.2 | +4.49% | -6.05% |
| temperature=1, top_p=0.95 | 4277.9 | 4533.4 | +5.97% | -7.13% |

These measurements used compilation/CUDA graphs and the default
FlashInfer sampler, with prefix caching disabled. The environment used
source base `61f084b5f` with native extensions from the official cu129
wheel for its parent commit `2eb491e18`.

The review changes affect tests only; these benchmarks were not rerun.
No Llama serving-performance improvement is claimed.

## Details

The production change only adds the GPT-OSS local-logits hook.

The direct logits helper is model-agnostic and runs for every
sharding-enabled test case. Its shard-width assertion catches an
incorrect full-logits implementation that token comparisons alone
may miss.

As discussed in review, shared LoRA compatibility validation is tracked
separately in #56074 as a follow-up.

Assisted by Astra.

File: `tests/v1/e2e/general/test_sharded_sampling.py` · line None

Two concerns with this checkpoint:

1. **Flakiness:** it's random-weight, so logits are close to flat and near-ties are common. The sharded path computes logits on a re-sorted subset of hidden states, so the lm_head GEMM runs with a different M and can pick a different kernel/reduction order than the replicated path. As the module docstring notes, that kind of noise flips near-ties, and one flipped greedy/seeded token diverges the rest of the completion. Have you run this repeatedly to check it's stable? A checkpoint with real weights (or a comparison tolerant of near-tie flips for this case) might be needed.
2. **Personal namespace:** CI would depend on `tengomucho/tiny-random-gpt-oss` with no pinned revision. If it's deleted, gated, or changed, the distributed/AMD jobs break or silently test something different. Could we use (or create) an org-maintained checkpoint, or at least pin a revision?
