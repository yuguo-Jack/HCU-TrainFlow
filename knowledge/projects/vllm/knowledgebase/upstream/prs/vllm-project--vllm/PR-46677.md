# [Frontend][Responses] Accept chat-completions image format on /v1/responses (#46631)

[Upstream PR](https://github.com/vllm-project/vllm/pull/46677) · state: closed · merged: False

## Original PR description

## Summary

Fixes #46631. Multimodal **image** inputs that work on `/v1/chat/completions` still fail on `/v1/responses`.

#57241 fixed the missing `detail` default. The chat-completions image shapes still fail validation:
- `"type": "image_url"` instead of `"input_image"`
- nested `image_url: {"url": X}` instead of the flat `image_url: X` string that `ResponseInputImageParam` expects

## Fix

Extend #57241's `BeforeValidator` (renamed `_normalize_input_images`) so it also maps `image_url` → `input_image` and flattens `{"url": X}` → `X`. Now the same image payload works on both endpoints.

I have attempted to trace it to the best of my abilities. input_image is parsed in chat_utils.py (MM_PARSER_MAP["input_image"] → _ResponsesInputImageParser → mm_parser.parse_image). That parser is TypeAdapter(ResponseInputImageParam), and the type is a TypedDict with detail: Required and image_url: Optional[str] (flat string).

my understanding is that the chat-completions shape (nested image_url={"url": ...}, no detail) is rejected at ResponsesRequest validation, before chat_utils runs (_ResponsesInputImageParser rejects it too). That's why the normalization has to sit at the request-validation layer rather than in the image parser. 

to make  image normalization more clear,  I pulled it out into a named _normalize_chat_completions_image_parts helper  so the intent is explicit.
