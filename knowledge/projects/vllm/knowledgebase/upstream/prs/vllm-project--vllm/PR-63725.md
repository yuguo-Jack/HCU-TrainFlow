# [ROCm][Perf][Muse Spark] Run the unpooler through AITER tuned GEMM on gfx942 and gfx950

[Upstream PR](https://github.com/vllm-project/vllm/pull/63725) · state: open · merged: False

## Original PR description

## Overview

Muse Spark's MoE block wraps the experts in a replicated BF16 pooler (8192 → 4096) and unpooler (4096 → 8192). Both run through `MuseSparkTorchLinearMethod`, which always calls `F.linear`, because AITER's gfx950 tuned-GEMM table picks lossy split-K BF16-accumulating kernels for the pooler shape.

This PR adds `MuseSparkTunedLinearMethod` and uses it for the unpooler only. On CDNA3 and CDNA4 with AITER linear enabled it calls `aiter.tuned_gemm.tgemm.mm`, which looks up AITER's tuned BF16 table and falls back to PyTorch for shapes without a row. The pooler stays on `F.linear`.

AITER already has gfx950 rows for the unpooler shape, which are faster than `F.linear` at decode batch sizes. For gfx942, ROCm/aiter#6945 adds rows at M = 1–8; without them, gfx942 keeps the PyTorch kernels it uses today.

This PR is mainly enablement: it routes the unpooler through AITER's tuned-GEMM lookup, so rows that AITER adds for this shape are picked up with an AITER version bump and no further vLLM change. The gfx950 gain below comes from rows already in AITER. On gfx942 this PR does not depend on ROCm/aiter#6945: without it, the unpooler resolves to the same PyTorch kernel as before.

## Claims

- MI355X, `amd/Muse-Spark-Open-816B-A42B-Quark-MXFP4`, TP4, with the AITER rows available today: +4.3% and +5.6% total throughput at 1k/1k with 1 and 4 concurrent requests, +4.5% at 1k/8k c1 and +8.1% at 1k/8k c64. Median TPOT is up to 8% lower (31.2 → 28.7 ms at 1k/8k c64). Every point measured is positive (+0.1% to +8.1%).
- MI300X with current AITER (no gfx942 row for the unpooler shape): no change. `tgemm.mm` falls back to PyTorch at every M from 1 to 8192, the output is bit-identical to `F.linear`, and the unpooler GEMM time is within ±0.6% of `F.linear`.
- MI300X, `amd/Muse-Spark-Open-816B-A42B-Quark-PTPC-FP8`, TP8 with ROCm/aiter#6945: neutral (−1.6% to +1.5% over two repeats, no point negative in both).
- Accuracy is unchanged. The unpooler `tgemm` output stays inside the BF16 tolerance at every M on both architectures. GSM8K: 0.9484 → 0.9462 on MI355X and 0.9500 → 0.9553 on MI300X, both within one standard error.

## Validation

**Unit test.** `tests/models/test_muse_spark_tuned_linear.py` (new) checks that the method calls `tgemm.mm` when the gate is open and falls back to `F.linear` otherwise. It is wired into the Muse Spark entries of `.buildkite/test_areas/models_basic.yaml`. It passes on MI300X together with the Muse Spark loading and logits tests (16 passed, `vllm/vllm-openai-rocm:nightly-5d35ce3934` with this branch's files mounted).

**GEMM check, one GPU.** `tgemm.mm` against `F.linear` for the unpooler (N = 8192, K = 4096). Both are timed in a CUDA graph that cycles through 12 weight copies so every call streams its weight from HBM, as in serving. Error is max |err| / max |ref| against an FP32 reference.

On MI355X the error matches `F.linear` everywhere except M = 48 and 192 (0.0047 against 0.0025), and no element is outside the BF16 tolerance. On MI300X the outputs are bit-identical from M = 16 upwards. The pooler shape on MI355X is the reason it stays on `F.linear`: its tuned kernels have about twice the error and up to 0.4% of elements outside the tolerance at M = 64.

**GEMM check, MI300X without ROCm/aiter#6945.** Neither AITER main (74502a9f5) nor the AITER in `vllm/vllm-openai-rocm:v0.32.0` (0.1.24.post1) has a gfx942 BF16 row for N = 8192, K = 4096, and the skinny-GEMM default does not apply at N = 8192, so `tgemm.mm` takes its PyTorch fallback. Measured with the same CUDA-graph method in that image, at M = 1, 2, 4, 8, 16, 32, 48, 64, 128, 192, 256, 384, 512, 1024, 2048 and 8192, the lookup resolves to `torch` at every M, the output is bit-identical to `F.linear`, and the `F.linear` / `tgemm` time ratio is 0.994–1.004 (e.g. 26.5 against 26.5 µs at M = 1, 52.6 against 52.7 µs at M = 256, 894.1 against 895.6 µs at M = 8192).

## Details

- **Gate.** `_use_aiter_tuned_gemm()` is cached and true on ROCm when `get_cdna_version() in (3, 4)` and `rocm_aiter_ops.is_linear_enabled()`. CDNA2 and non-ROCm platforms keep `F.linear`.
- **Graphs.** `tgemm.mm` dispatches to registered custom ops, so `torch.compile` and CUDA graphs are unaffected.
- **Limitations.** At M = 384 and 1024 the MI355X table is 3.6–7 µs slower than `F.linear`. Those are prefill-sized batches, where the unpooler is a small fraction of the step.
