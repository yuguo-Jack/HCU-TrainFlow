# [ROCm][CI] Raise the MI355 DeepSeek-V3.2 GSM8K startup wait to 1800s

[Upstream PR](https://github.com/vllm-project/vllm/pull/64734) · state: closed · merged: True

## Original PR description



## Overview

In AMD CI nightly [15747](https://buildkite.com/vllm/amd-ci/builds/15747), both MI355 DeepSeek-V3.2 GSM8K jobs timed out at the 1200 s startup wait while still loading the 642 GiB checkpoint from NFS. This applies the same 1800 s wait that [#59666](https://github.com/vllm-project/vllm/pull/59666) set for the DeepSeek-R1 MI355 configs.

## Claims

- Raises `startup_max_wait_seconds` from 1200 to 1800 in `DeepSeek-V3.2-TP_MI355.yaml` and `DeepSeek-V3.2-DP_MI355.yaml`, matching the DeepSeek-R1 MI355 configs.

## Validation

- `pre-commit run --files tests/evals/gsm8k/configs/DeepSeek-V3.2-TP_MI355.yaml tests/evals/gsm8k/configs/DeepSeek-V3.2-DP_MI355.yaml`: passed.
- Both configs parse with `startup_max_wait_seconds: 1800` and `accuracy_threshold` is unchanged.
- In build 15747 the servers were stopped at 153/163 (TP) and 145/163 (DP) shards, at that rate startup would have finished in about 1350 s. The test stays within the 2400 s pytest timeout and the 65-minute job limit.
- End-to-end coverage comes from the `(MI355) LM Eval DeepSeek V3-2 TP/DP` jobs, which need 4x MI355 and run in the AMD nightly.

## Details

Both jobs ran on the same node and loaded the checkpoint at the same time, so loading took over 20 minutes instead of the usual 5 to 11. No open issue or PR covers these configs; #59666 changed only the DeepSeek-R1 ones.
