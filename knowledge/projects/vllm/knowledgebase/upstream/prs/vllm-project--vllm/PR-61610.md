# [Bugfix] Fix mamba_backend silently overriding an explicit mamba_config.backend choice

[Upstream PR](https://github.com/vllm-project/vllm/pull/61610) · state: closed · merged: False

## Original PR description

## Overview

`mamba_config.backend` passed via the Python API (e.g. `LLM(..., mamba_config={"backend": "flashinfer"})`) was silently overridden back to the Triton default when the engine config was built, because `--mamba-backend`'s own default (`MambaBackendEnum.TRITON`) always won regardless of whether the user actually passed the flag. Closes #61188.

## Claims

- `mamba_backend` (Python API field and `--mamba-backend` CLI flag) now defaults to `None` instead of `TRITON`, mirroring the existing `attention_backend`/`AttentionConfig.backend` pattern.
- `create_engine_config` only overrides `mamba_config.backend` when `mamba_backend` is explicitly set (not when it's left at its own default), so a backend chosen via `mamba_config={"backend": ...}` is no longer silently clobbered.
- Raises `ValueError("mamba_backend and mamba_config.backend are mutually exclusive")` if both `mamba_backend` and a non-default `mamba_config.backend` are set, matching `attention_backend`'s own mutual-exclusion check.
- As a direct consequence, setting `ssu_algorithm` alongside an explicit `mamba_config={"backend": "flashinfer"}` no longer raises a spurious `ValueError` telling the user to do exactly what they already did.
- Adds `test_mamba_config` to `tests/engine/test_arg_utils.py`, mirroring the existing `test_attention_config` test.

## Validation

Ran the issue's own repro against `main` before this change — both symptoms reproduced:
```
mamba_config.backend = MambaBackendEnum.TRITON   # expected FLASHINFER
ValueError: Mamba SSU algorithm selection is only supported with the FlashInfer backend. Please set `--mamba-backend flashinfer`, or omit `--mamba-ssu-algorithm`.
```

Same repro against this branch — both resolved:
```
mamba_config.backend = MambaBackendEnum.FLASHINFER
[main] Test 2: no error raised -- NOT reproduced
```

New regression test (`test_mamba_config`) passes, covering: the default value, setting `backend` via the Python API `mamba_config` dict, the `--mamba-backend` CLI shorthand, both flowing correctly into `VllmConfig.mamba_config`, the mutual-exclusion check, and the exact original bug scenario (explicit `flashinfer` + `ssu_algorithm` no longer raising).

## Details

**Why `--mamba-config.backend` dot-notation isn't used in the test:** unlike `attention_config`, `mamba_config` has no dedicated CLI argument group (no `--mamba-config.backend` flag exists) — it's only settable as a whole via the Python API (`EngineArgs(mamba_config={...})`) or piecemeal via `--mamba-backend`/`--mamba-ssu-algorithm`. Confirmed by reading `EngineArgs.add_cli_args` directly; every other top-level config field with its own argument group (`attention_config`, `kv_transfer_config`, `compilation_config`, etc.) has an explicit `add_argument` call that `mamba_config` lacks.

**Known limitation of the mutual-exclusion check:** `attention_backend`'s equivalent check works cleanly because `AttentionConfig.backend` itself defaults to `None`, so "explicitly set to X" and "never touched" are always distinguishable. `MambaConfig.backend` defaults to `MambaBackendEnum.TRITON` (not `None`), so this PR's check can't tell apart "user explicitly set `mamba_config={"backend": "triton"}`" from "user never touched `mamba_config` at all", both look identical. This means setting `mamba_backend` alongside an *explicit, default-matching* `mamba_config.backend` won't raise, even though it's arguably the same kind of conflict. Fully resolving this would mean changing `MambaConfig.backend`'s own default to `None` and updating every other read site across the codebase (`vllm/config/vllm.py`, `mamba_mixer2.py`, `ssu_dispatch.py`, `nemotron_h.py`, etc.) that currently assumes it's never `None` — out of scope for this fix, which targets the two concrete symptoms reported in #61188.
