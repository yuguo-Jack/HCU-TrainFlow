# [Rust Frontend] Validate cache_salt like Python

[Upstream PR](https://github.com/vllm-project/vllm/pull/62427) · state: open · merged: False

## Original PR description



## Overview

Python's `validate_cache_salt` (vllm-project/vllm#51444, vllm-project/vllm#54353) rejects a `cache_salt` that is empty, longer than 128 characters, or contains `@`, `/`, `\` or NUL, so unvalidated salts never reach downstream cache backends such as LMCache, which may use those characters as key separators. The Rust frontend only checks a non-empty salt on chat and completions and forwards anything else to the engine; this PR applies Python's rule to every Rust entry point.

## Claims

- `/v1/chat/completions`, `/v1/completions`, `/inference/v1/generate`, render, and gRPC `Generate` reject a salt that Python rejects, with a 400 (gRPC `InvalidArgument`) instead of forwarding it to the engine.
- Length is counted in Unicode code points, matching Python's `len`.
- Valid salts and omitted salts behave as before.

New test `vllm-text` `request::tests::validate_rejects_unsafe_cache_salt` covers a valid salt, a salt of exactly 128 code points (`é`, two bytes each), the empty string, 129 characters, and each forbidden character. With the check in `TextRequest::validate` removed, the test fails.

## Details

- **Where the check lives.** `TextRequest::validate` is the shared chokepoint that every Rust entry point calls before tokenization (`TextLlm::prepare`, `tokenize`, `tokenize_in_place`), and it already holds similar request invariants such as `EmptyStopString`. Putting the rule there covers HTTP and gRPC with one check. The new `Error::InvalidCacheSalt` is a request-validation error, so it maps to a 400 through the existing `text_submit_error` and `chat_submit_error`. The DTO-level `#[validate(length(min = 1))]` checks on chat and completions are kept; they only give an earlier message for the empty case.
- **Error message.** Python raises two messages (empty vs. length/charset); Rust uses one message that states the whole rule.
- **Not a duplicate.** vllm-project/vllm#56681 (open, no activity since 2026-09-21) targets the same Rust gap but checks at lowering time (`lower_text_request`), which runs after tokenization, and also adds an engine-side check in `vllm/v1/request.py`. This PR is Rust-only and validates before tokenization at the shared chokepoint; the engine-side check is out of scope. No other open PR touches Rust `cache_salt` validation.
