# [Build] Keep plain CUDA arch when its suffixed variant is also requested

[Upstream PR](https://github.com/vllm-project/vllm/pull/56549) · state: closed · merged: True

## Original PR description

## Purpose

Fixes #56548.

`cuda_archs_loose_intersection` silently drops a plain base arch (e.g. `10.0`) from
`TORCH_CUDA_ARCH_LIST` when the list also contains its `a` suffixed variant (`10.0a`).
Introduced by #38126: the "Symmetric handling" block consumes SRC `10.0` for TGT `10.0a`,
so the plain TGT `10.0` finds nothing afterwards. Generic kernels (`_C`, `_moe_C`) then get
`sm_100a` only, which does not load on B300 (CC 10.3) and fails with
`cudaErrorNoKernelImageForDevice`.

Changes in `cmake/utils.cmake`:

- Symmetric-suffix block: only remove the SRC base arch when TGT does not also request the
  plain base. Both `10.0` and `10.0a` are then emitted, matching torch's handling of the
  same list.
- Exact-base loop: after a suffixed SRC entry (e.g. `10.0f`) matched a plain TGT base, also
  drop TGT's own `a`/`f` variants of that base so the family fallback does not add a second
  cubin (`10.0a` next to `10.0f`) for the same source.

## Test Plan

Ran the function directly with `cmake -P` (no GPU needed), before and after, with
`TORCH_CUDA_ARCH_LIST="7.5 8.0 8.6 8.7 8.9 9.0a 10.0 10.0a 12.0 12.1+PTX"` on CUDA 13
(`CUDA_SUPPORTED_ARCHS="7.5;8.0;8.6;8.7;8.9;9.0;10.0;11.0;12.0"`), plus the per-kernel
lists used in `CMakeLists.txt`. Regression inputs: `10.0a`, `10.0`, `9.0a;10.0f;12.0f`,
`8.0;9.0;10.0;12.0`, `7.5;8.0;8.9;9.0a;12.0`.

## Test Result

| list | before | after |
|---|---|---|
| global `CUDA_ARCHS` | `9.0a;10.0a;7.5;8.0;8.6;8.7;8.9;12.0` | `9.0a;10.0a;7.5;8.0;8.6;8.7;8.9;10.0;12.0` |
| `9.0a;10.0f;10.1f;10.3f;12.0f;12.1f` (cutlass w8a8) | `12.0f;9.0a;10.0a` | `10.0f;12.0f;9.0a` |
| `10.0f` (scaled_mm SM100) | `10.0a` | `10.0f` |
| `8.0;8.6;8.9;9.0a;10.0f;12.0f` | `12.0f;9.0a;10.0a;8.0;8.6;8.9` | `10.0f;12.0f;9.0a;8.0;8.6;8.9` |

All five regression inputs produce identical output before and after. The "after" global list
is what v0.18.x produced for this input (`10.0` present), and the per-kernel lists go back to
the family targets that `CMakeLists.txt` documents as the intended CUDA >= 12.9 path.
