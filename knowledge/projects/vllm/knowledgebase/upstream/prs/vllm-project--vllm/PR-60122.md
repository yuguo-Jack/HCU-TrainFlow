# [Bugfix][Attention] Make TRITON_MLA prefill batch invariant under chunked prefill

[Upstream PR](https://github.com/vllm-project/vllm/pull/60122) · state: open · merged: False

## Original PR description



## Overview

Fixes #60007. With `VLLM_BATCH_INVARIANT=1`, the output of a prompt served by `TRITON_MLA` depends on how the scheduler splits its prefill into chunks. This PR computes prefill rows with the per-row decode kernel in batch-invariant mode, so a row's result no longer depends on the chunk it was scheduled in.

## Claims

- `test_logprobs_bitwise_batch_invariance_ragged_chunked_prefill[TRITON_MLA]` fails on `main` and passes with this PR (DeepSeek-V2-Lite-Chat). The two `bs1_vs_bsN[...-TRITON_MLA]` tests, which also fail on `main` with this model, pass as well.
- Nothing changes when `VLLM_BATCH_INVARIANT` is unset: `tests/v1/attention/test_mla_backends.py` and `tests/kernels/attention/test_triton_mla_causal_verify_flatten.py` have the same set of failing tests on `main` and on this PR (the failures are FP8 KV-cache cases that this GPU does not support).
- gsm8k accuracy in batch-invariant mode is unchanged within the reported standard error.
- Cost: prefill is slower in batch-invariant mode, because the decode kernel works row by row. See the `vllm bench serve` runs below (6: prefill-heavy, 7: mixed).

## Details

**Root cause.** For prefill, `forward_mha` attends to the new tokens of the step and to the cached context separately (`_compute_prefill_context`) and merges the two partial results. Where the split falls depends on the scheduler's chunking, so the rounding of a token's output depends on it too. This is the same mechanism that made #29125 disable prefix caching for `TRITON_MLA` in batch-invariant mode.

**Change.**
- `MLAAttention.forward_impl`: in batch-invariant mode, if the backend opts in (`supports_batch_invariant_mqa_prefill`), all rows of the step go to `forward_mqa`. The KV cache has already been updated for the step, so each row can be computed from the cache alone. This reuses the branch that sparse MLA already has for routing prefill rows to MQA.
- `TritonMLAImpl`: a new `_forward_mqa_all_rows` gives every query row its own causal extent and calls the existing `decode_attention_fwd` (one program per row, `num_kv_splits = 1`). Rows are launched in groups of 256 to bound the scratch buffer; rows are independent, so the group size cannot change results. The existing decode path is unchanged.
- The routing is used only for causal attention without PCP/DCP; otherwise the existing path is kept and a warning is logged once. `Dots3NoteTritonMLAImpl` (sliding window) opts out.

**Trade-offs and limitations.**
- Prefill in batch-invariant mode is slower (run 6 above). Decode is not affected, and nothing changes outside batch-invariant mode.
- Routed prefill allocates per-row latent outputs (`rows x heads x kv_lora_rank`), like the sparse MQA-prefill path does.
- Alternatives I considered: disabling chunked prefill for `TRITON_MLA` in batch-invariant mode (as was done for prefix caching), which costs no prefill speed but restricts scheduling; and canonical chunk boundaries in the prefill path, which is a larger change. I am happy to switch to either if that is preferred.
- Validated on SM 8.6 with BF16 KV cache only. The FP8 KV-cache cases of the MLA backend tests cannot run on this GPU.
