# [Bugfix][LoRA] Reject adapters whose weights match no LoRA module

[Upstream PR](https://github.com/vllm-project/vllm/pull/60039) · state: open · merged: False

## Original PR description



## Overview

Fail loudly instead of silently serving the base model when a LoRA adapter's module names don't match the model. Related to #49354 and #48019.

`activate_adapter` looks up LoRA weights by exact module name and calls `reset_lora` on every layer it finds nothing for. Load-time validation (`check_unexpected_modules`) only compares the *last* name component (`q_proj`, ...), so an adapter whose module *paths* don't match passes it, loads, and is then a complete no-op: generations are bit-identical to the base model, and the only signal is a `debug_once` message. If only some modules mismatch, there is no log at all.

The case we hit: a PEFT adapter trained on the text-only `Qwen3_5ForCausalLM` (keys `base_model.model.model.layers.N...`) served on `Qwen/Qwen3.5-*`, which vLLM loads as `Qwen3_5ForConditionalGeneration` with the LM at `language_model.model.layers.N`. (Note that `AutoModelForCausalLM` on a Qwen3.5 checkpoint instantiates `Qwen3_5ForCausalLM`, so this layout is easy to produce.)

## Claims

- An adapter whose weights match **no** LoRA-wrapped module now fails to load with a `ValueError` naming the unmatched modules, instead of silently returning base-model outputs.
- An adapter where only **some** weights match logs a warning listing the unmatched ones (they are still ignored, as before).
- Designed not to raise or warn spuriously under pipeline parallelism, expert parallelism, `--lora-target-modules`, packed modules, 3D MoE adapters, or pooling models (see Details). PP is unit-tested with a simulated stage; EP, MoE and pooling are covered by reading the code paths, not by a run.

```python
# Repro: a PEFT LoRA adapter created on the text-only class Qwen3_5ForCausalLM
# has keys "base_model.model.model.layers.N...". vLLM serves the checkpoint as
# Qwen3_5ForConditionalGeneration, whose LM lives at "language_model.model.layers.N".
# Compare prompt logprobs of the base model vs. the same random adapter saved in
# the text-only and in the multimodal key layout.
import os
import sys
import tempfile

import torch
from peft import LoraConfig, get_peft_model
from safetensors.torch import load_file, save_file
from transformers import AutoConfig
from transformers.models.qwen3_5 import Qwen3_5ForCausalLM

from vllm import LLM, SamplingParams
from vllm.lora.request import LoRARequest

BASE = sys.argv[1] if len(sys.argv) > 1 else "Qwen/Qwen3.5-0.8B"
PROMPT = "The capital of France is Paris. The capital of Japan is"


def main():
    tmp = tempfile.mkdtemp()
    text_dir, mm_dir = os.path.join(tmp, "text_only"), os.path.join(tmp, "multimodal")

    torch.manual_seed(0)
    text_model = Qwen3_5ForCausalLM(AutoConfig.from_pretrained(BASE).text_config)
    peft_model = get_peft_model(
        text_model,
        LoraConfig(
            r=8,
            lora_alpha=16,
            target_modules=["q_proj", "k_proj", "v_proj", "o_proj"],
            init_lora_weights=False,  # random non-zero lora_B, so the adapter has an effect
        ),
    )
    peft_model.save_pretrained(text_dir)
    tensors = load_file(os.path.join(text_dir, "adapter_model.safetensors"))
    print("text-only adapter key:", next(iter(tensors)))
    peft_model.save_pretrained(mm_dir)
    save_file(
        {
            k.replace("base_model.model.model.", "base_model.model.model.language_model."): v
            for k, v in tensors.items()
        },
        os.path.join(mm_dir, "adapter_model.safetensors"),
    )
    del peft_model, text_model

    llm = LLM(
        model=BASE,
        enable_lora=True,
        max_lora_rank=8,
        max_model_len=512,
        enforce_eager=True,
        gpu_memory_utilization=0.5,
    )
    params = SamplingParams(max_tokens=1, temperature=0.0, prompt_logprobs=0)


    def prompt_logprobs(lora_request=None):
        out = llm.generate([PROMPT], params, lora_request=lora_request, use_tqdm=False)[0]
        return [
            lp[tok].logprob
            for tok, lp in zip(out.prompt_token_ids[1:], out.prompt_logprobs[1:])
        ]


    base = prompt_logprobs()
    for lora_id, (name, path) in enumerate(
        [("multimodal-layout", mm_dir), ("text-only-layout", text_dir)], start=1
    ):
        try:
            lora = prompt_logprobs(LoRARequest(name, lora_id, path))
        except Exception as e:  # noqa: BLE001
            print(f"{name} adapter: {type(e).__name__}: {e}")
            continue
        delta = max(abs(a - b) for a, b in zip(base, lora))
        print(f"{name} adapter: max |logprob(lora) - logprob(base)| = {delta:.4f}")


if __name__ == "__main__":
    main()
```

## Details

**Where.** `LoRAModelManager._validate_lora_module_names` is called from `WorkerLoRAManager._load_adapter`, next to the existing `_validate_modules_to_save` check, so a bad adapter is rejected before it is cached or evicts anything. Dummy warm-up LoRAs don't go through it.

**What counts as matched.** A loaded LoRA module name matches if it is a key of `self.modules`, one of the sub-module names in `self.packed_modules` (e.g. `q_proj` for `qkv_proj`, per-expert names for 2D MoE), `<module>.base_layer` (PEFT 3D MoE `gate_up_proj`), anything under a wrapped `.experts` module (3D/shared MoE), or, for pooling models, the name without the `model.` prefix. These mirror the lookups in `_create_merged_loras_inplace`, `_stack_moe_lora_weights` and `_get_lora_layer_weights`.

**What is skipped on purpose, not reported:**
- *Pipeline parallelism*: weights whose module path runs through a `PPMissingLayer` on this worker (layers owned by another stage, or `embed_tokens`/`lm_head` on middle stages). This is decided per module by walking the module path, so a PP worker that owns none of the adapter's layers gets neither an error nor a warning, while a genuinely misnamed module is still reported on every stage. Modules that live on another stage count as applicable when deciding between error and warning, so a stage never raises just because the adapter's valid modules happen to be elsewhere.
- *Expert parallelism*: non-local expert weights are already dropped at read time (`moe_ep_spec`), and any remaining per-expert names are still sub-modules of a wrapped `experts` module, so they count as matched.
- *`--lora-target-modules`*: weights excluded by the deployment filter (`_match_target_modules`) are skipped by user choice.

**Error vs. warning.** Zero matches raise, because the adapter can't have any effect and continuing would silently return base-model outputs (this is the same failure mode and the same place as the existing `ValueError` for unexpected target modules). A partial mismatch only warns, because there are legitimate adapters in that state that work today, e.g. a VLM adapter that also has vision-tower LoRA weights served with `enable_tower_connector_lora=False`. Raising there would break them.

**Limitations / things to review.**
- As with the existing load-time `ValueError`s, when a never-before-seen adapter is first loaded inside `execute_model` (passing a `LoRARequest` straight to `generate`), the error propagates from the worker; with `/v1/load_lora_adapter` it's returned to the caller.
- The existing `debug_once("No LoRA weights were applied ...")` in `activate_adapter` is left alone.

**Mapping side.** This PR doesn't make text-only-layout adapters work on multimodal wrappers; it only stops them from failing silently. That part is handled by the open PRs #48022 (adds a `model.` fallback to the Qwen3-VL mapper, which `Qwen3_5ForConditionalGeneration` inherits) and #49525 (a shared fallback for all `language_model` wrappers). They're independent of this PR, so maintainers can take this one, either of those, or both: this PR prevents the silent failure for *any* naming mismatch, and the mapping fix makes this particular adapter layout work. With a mapping fix applied on top of this branch, the reproducer's text-only adapter gives exactly the same logprobs as the multimodal-layout adapter (last row above).

**On #49354.** I've used "Related to" rather than "Fixes" because I couldn't confirm the reporter's adapters have the text-only layout: the issue says they were trained on `Qwen3_5ForConditionalGeneration`, but the HF reference loads the base model with `AutoModelForCausalLM`, which gives `Qwen3_5ForCausalLM` and `model.layers.N` keys (and @fooSynaptic's #49525 treats it as the text-only case). The prefix in `adapter_model.safetensors` settles it: `model.layers.` is the text-only layout covered here, and `model.language_model.layers.` is the multimodal layout, which would be a different bug. With this PR, a text-only-layout adapter fails at load time with an explicit message instead of producing base-model outputs.

**Duplicate check.** I searched open PRs for #49354 and for LoRA no-op, unmatched and silent-adapter terms. #48022 and #49525 fix the name mapping for wrapper models, and #59924 validates MoE adapter formats. None of them adds a general check that adapter weights actually reach a LoRA layer.
