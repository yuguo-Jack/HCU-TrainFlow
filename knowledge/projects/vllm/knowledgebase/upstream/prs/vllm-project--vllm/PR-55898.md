# [Bugfix] Preserve decode ordering for stateful attention

[Upstream PR](https://github.com/vllm-project/vllm/pull/55898) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Preserve multi-token decode ordering when stateful attention builders require a higher reorder threshold than another attention group. Fixes the threshold aggregation behind #55894; refreshed against main `c5f8adc0`.

## Claims

- Keep the common minimum for optional-ordering builders, while honoring the largest required stateful decode threshold.
- Include ShortConv and its PLE subclass through the capability flag, and log when the required threshold raises the common minimum, addressing the review suggestions.

## Validation

- `.venv/bin/python -m pytest tests/v1/worker/test_gpu_model_runner.py -k reorder_batch_threshold -v` — **2 passed**.
- Against unmodified main production code, the required-ordering regression fails (`1` instead of `4`); the optional-ordering control passes.
- Pre-commit on the seven changed files and `git diff --check origin/main...HEAD` — **passed**.
- The production mixed-workload results reported earlier in this PR are external validation of the earlier logic on v0.27.1. No current-head model, acceptance-rate or `VLLM_GPU_SYNC_CHECK=error` run was possible here because CUDA cannot initialize.

## Details

The common minimum can leave speculative decode rows behind a continuing prefill. Stateful builders split these rows positionally and may update the wrong recurrent state. The capability defaults off for ordinary token-KV backends; the added ordering and diagnostic use host configuration values, with no new GPU-to-CPU reads.

This fixes the existing MRV1 path still used by the affected released deployments. MRV2 has a separate canonical ordering implementation under `vllm/v1/worker/gpu/model_runner.py` and does not call this aggregation.

Duplicate check: re-read #55894 and searched open PRs by issue number and stateful/decode ordering; no other open fix for this threshold defect was found. Open since 2026-09-08. AI assistance was used, with Signed-off-by and Codex attribution. Human review and current-head GPU validation remain required.

- filipmihal · comment · 2026-09-08T13:36:03Z · [source](https://github.com/vllm-project/vllm/pull/55898#issuecomment-5586003424)

Validated this change on the reproducer from #55894 (`nvidia/NVIDIA-Nemotron-3.5-Lightning-30B-A3B-BF16`, vLLM 0.27.1, RTX PRO 6000; ~30 concurrent pairs of a ~60k-token prompt followed 1.5 ± 1 s later by a short one, 400 requests per arm, production flags with the drafter left on auto-select so it lands on FlashInfer). The runner-side logic of this PR was grafted onto 0.27.1 at import time; the two arms ran back to back on the same node.

| arm | runner `reorder_batch_threshold` | Mamba2 prefill steps containing decode rows | corrupted responses |
|---|---|---|---|
| unpatched | 1 (builders: Mamba2 4, Triton none, FlashInfer 1) | 22 of 422 | 11 / 400, all among the 33 requests whose first decode step sat in the prefill region; 0 of the other 367 |
| with the fix | 4 | 0 of 423 | 0 / 400 |

Earlier unpatched runs of the same load on three other nodes gave 15, 12 and 9 corrupted of 400, so the zero is well outside the noise. Corrupted outputs were either word salad from the first sentence or a few thousand tokens of special tokens rendering to no text (the second signature is easy to miss with a plain garbage detector).

Two small things:
- `short_conv_attn.py` also runs under speculative decoding (its builder pads to a uniform multi-token decode batch, per its own comment) and splits positionally, so it probably wants `requires_decode_ordering = True` as well.
- A `logger.info` when the threshold is raised would make the situation visible in server logs; today nothing indicates that the drafter's backend changed the target's batch ordering.

Scripts (probe, load generator, analysis): https://gist.github.com/filipmihal/ca652065fdd066063998c1bf6d3e9b8e


- he-yufeng · comment · 2026-09-08T17:00:16Z · [source](https://github.com/vllm-project/vllm/pull/55898#issuecomment-5588846454)

Verified the fix against the probe chain in #55894 on current main: with the drafter on FlashInfer (`reorder_batch_threshold=1`, no decode-ordering requirement) and the target on Mamba2 (`1 + k`), the runner now lands on 4, so `reorder_batch_to_split_decodes_and_prefills` sorts the multi-token decode rows ahead of a continuing chunk and the Mamba builder's positional split at 4 lines up with the arrangement. The capability flag defaults off, so token-KV backends keep the old minimum behavior and the docstring's performance-penalty note stays true for them.

One test gap worth closing: the new test pins the ordering-required case (min 1 vs required 4 → 4), but nothing pins that two non-required builders still resolve to the plain minimum. A second case with both flags false would lock the unchanged half of the contract.
