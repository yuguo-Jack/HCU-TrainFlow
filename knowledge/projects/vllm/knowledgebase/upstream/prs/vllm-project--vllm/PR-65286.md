# [Bugfix][Core] Release libgomp workers before every fork

[Upstream PR](https://github.com/vllm-project/vllm/pull/65286) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

A process forked after its parent used OpenMP hangs or crashes in libgomp, and #62884 covers only part of this case. In `fork` mode, run its release in the parent before every fork, so that no child inherits a live OpenMP pool.

## Claims

- In `fork` mode, a process forked from a parent that imported vLLM and has a live libgomp pool can use OpenMP and can launch forked workers, without a hang or a crash.
- The engine processes that #62884 protects stay protected, because `multiprocessing` in `fork` mode goes through `os.fork`.
- `spawn` mode is unchanged, because the hook does nothing there. `subprocess` does not run the hook. In `fork` mode it adds about 1 to 2 ms to each `os.fork`.

## Details

libgomp has no fork handler. #62884 pauses the OpenMP runtime in `get_mp_context()`, which runs in the process that is about to launch a worker. That fixes a parent that used OpenMP. It does not fix a process that was itself forked while its parent had a live pool:

1. A parent runs a parallel region, so its worker threads exist.
2. The parent forks. The child inherits the pool state, but not the threads.
3. The child hangs in its first parallel region. It also hangs or crashes when `get_mp_context()` tries to join those threads.

Skipping the release in such a child would remove the crash but not the hang in step 3. The only safe place for the release is the parent, before the fork, so this PR moves it to `os.register_at_fork(before=...)` and removes the call from `get_mp_context()`. The hook does nothing in `spawn` mode.

The tradeoff is that in `fork` mode the hook runs for every `os.fork` in a process that imports this module, and the parent then recreates its workers on its next parallel region. `docs/design/multiprocessing.md` describes this for applications that embed vLLM. The table above shows the cost.

This PR has one limit. If a parent uses OpenMP before it imports vLLM, the hook did not exist when it forked, so its child still inherits the stale pool. In `fork` mode, that child hangs at its first fork, as it does on main in `get_mp_context()`. I found no way to detect this state from the child. `test_spawn_mode_skips_the_libgomp_release_on_fork` makes sure that `spawn` mode does not gain this hang. That test passes on main too, and it would fail with an unconditional hook.

This does not duplicate an open PR. It follows merged #62884, and searches for `libgomp`, `omp_pause_resource_all`, and `register_at_fork` found no other PR for this.
