# [Bugfix][Tool Parser] Keep raw text for string parameters with union/enum/$ref schemas (Muse, MiniCPM5, Poolside)

[Upstream PR](https://github.com/vllm-project/vllm/pull/64518) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

The `muse`, `minicpm5` and `poolside_v1` tool parsers keep a parameter's raw text only when its schema is exactly `{"type": "string"}`, so `Optional[str]` values such as `"1.10"` or `"1984"` come back as `1.1` or `1984`. This makes them keep the raw text whenever the schema allows a string. The Rust frontend's Muse parser gets the same fix.

FIX #64517

## Claims

- String parameters keep their raw text when the schema allows a string through `anyOf`/`oneOf`, a `type` list, `enum`/`const`, a local `$ref`, `allOf`, or `additionalProperties`. Streaming and non-streaming both get the fix.
- Values that fit another type the schema allows still decode to it: `null` -> `None` for `Optional[str]`, `"25"` -> `25` under `anyOf [integer, string]`.
- Unchanged: plain `type: string`, non-string types, untyped parameters (`{}`), Python `muse_glimmer`, and `extract_types_from_schema` / `ParserEngine` coercion.

## Details

**Root cause.** Each parser compared the schema to `"type": "string"` (Muse `_string_parameters`, MiniCPM5 `_get_argument_type`, Poolside `_is_string_type`, Rust `MuseUnifiedParser::new`) and decoded everything else.

**Change.** `parameter_types` in the new `vllm/tool_parsers/schema_types.py` computes the JSON types each top-level parameter allows (`type`, `const`, `enum`, local `$ref`, `anyOf`/`oneOf` as union, `allOf` as intersection). `convert_value` keeps the raw text unless the parser's own decoder returns another allowed type. Each parser keeps its decoder. In Rust, Muse derives the types from the existing `SchemaRoot::options` walk, which already resolves `$ref` for coercion and the output grammars, and intersects multi-branch `allOf`, where a `number` branch also admits integers.

**Scope.** `extract_types_from_schema` and `ParserEngine` coercion are not touched; consolidating them is #63385. Structured-output schema analysis (RFC #58697) checks grammar-backend features, not value types.

**Limitations.**
- Only top-level parameters are checked; nested values are decoded as a whole.
- A union with an untyped branch (`anyOf [string, {}]`) is unconstrained, so it decodes, as on main.
- `anyOf [string, object]` decodes a JSON body to an object; the schema allows both.
- Poolside V1 streams `Optional[str]` arguments in one delta at `</arg_value>`, as on main.
- The Rust frontend uses one parser for Spark and Glimmer, so Rust Glimmer gets the new rules while Python Glimmer always decodes. This split predates this PR.

**Rust differs from Python** on a few schemas that admit a string:
- `allOf` nested inside `anyOf`;
- an untyped `anyOf` beside a `type` list;
- `$ref` chains deeper than 32, which decode as on main;
- the OpenAPI `nullable` null option.

The decoders also differ. serde_json rejects `NaN`/`Infinity` and reads integers beyond 64 bits as floats, so Rust keeps the raw text in cases where Python's `json.loads` decodes.

@yzong-rh @bbrowning thanks for raising the shared-utility question. I looked at both overlaps before slimming this PR:

- **Structured outputs** (the xgrammar/guidance feature checks, RFC #58697) asks whether a backend supports the keywords in a whole schema. This PR asks something narrower: does one tool parameter admit a string, so the parser can keep the raw text. The RFC's shared schema layer could host that later.
- **`ParserEngine._coerce_value`**: I tried having the XML parsers call `coerce_to_schema_type(raw, extract_types_from_schema(schema))`. That fixes `Optional[str]` but regresses main elsewhere. Untyped `{}` values get stringified, `"1"` under a boolean schema becomes `true`, `$ref` parameters lose their type, and MiniCPM5/Poolside lose their `literal_eval` fallback. The root cause is that `extract_types_from_schema` returns `["string"]` both for "string" and for "unknown", which is the area #63385 works on.

So the PR now leaves `extract_types_from_schema` and `vllm/tool_parsers/utils.py` identical to main and does not conflict with #63385. The new walk stays private to the Muse, MiniCPM5 and Poolside parsers. On the Rust side, Muse reuses the existing `SchemaRoot::options` walk instead of adding a second one.

Once #63385 lands, I'm happy to do a follow-up that puts these walks and the JSON-type helpers behind one utility.
