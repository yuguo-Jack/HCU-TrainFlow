# [ROCm][Qwen3.8-Flash-Next] Specialized decode: MTP verify steps

[Upstream PR](https://github.com/vllm-project/vllm/pull/63124) · state: open · merged: False

## Original PR description



## Overview

**Stacked on #63032** (Qwen3.8-Flash-Next `--monokernel` decode); until it merges the compare view shows its commit too. This PR is the last commit, `77da850940`: `--monokernel` with MTP speculative decoding. A verify step of whole requests (`num_speculative_tokens + 1` rows each, up to 16 rows) runs the hyper-connection fronts, the QSA layers and the o_proj and MoE blocks on the kernels; the GDN layers of a verify step run vLLM's GDN core on the spec-decode metadata, as #61325 did.

## Claims

- MTP-3 with `--monokernel`: 15–16% lower median TPOT than stock MTP-3 at 8k/1k with 1 and 2 concurrent requests, 4% with 4, and 19% at 60k context with one request (5% with four); with 8 requests (32-row verify steps, stock in both arms) the two are level.
- Accuracy and acceptance unchanged: GSM8K 0.963 with `--monokernel` vs 0.965 stock under MTP-3, mean acceptance length 3.46 in both.
- Only MTP is accepted (at most 15 draft tokens); other methods, adaptive verification and dynamic speculative decoding stay refused, each listed in the startup error.

## Validation

Same setup as #63032 (MI355X, TP2, `nightly-df3bd094` with this branch's `vllm/models/qwen4_exp/amd/` overlaid, empty caches), plus `--speculative-config '{"method": "mtp", "num_speculative_tokens": 3}' --max-num-batched-tokens 8192`. Stock and `--monokernel` differ only in the flag.

**Checkpoint.** MTP does not load from `amd/Qwen3.8-Flash-Next-Quark-MXFP4` as published, stock or not: its `quantization_config.exclude` misses the BF16 MTP experts and `fc_embedding`, and names the draft layer `mtp.layers.0.*` where vLLM builds `mtp.layers.48.*`, so the draft is built as MXFP4 (`The size of tensor a (1280) must match the size of tensor b (2560)`). The fix is [the checkpoint's config.json](https://huggingface.co/amd/Qwen3.8-Flash-Next-Quark-MXFP4/discussions/1); these runs mount a `config.json` with `re:mtp\..*` added to `exclude`, weights unchanged.

**Median TPOT (ms), MTP-3.** Both arms at once on HIP 0,1 and HIP 2,3, then swapped; one run per cell on each pair (same `sglang.bench_serving` command as #63032). At 4 rows a request, concurrency 1, 2 and 4 verify on the kernels; concurrency 8 (32 rows) runs stock in both arms.

With random prompts the acceptance length differs from run to run (3.48–3.65 over these runs), which moves TPOT by several percent; the concurrency-8 row, stock in both arms, gives that noise floor.

**GSM8K with MTP-3** (SGLang `run_eval`, 1,319 questions, 4 threads so every verify step is 16 rows or fewer, `max_tokens` 2048, thinking off): stock 0.965, `--monokernel` 0.963 (per-question std 0.19, one standard error 0.005); mean acceptance length 3.46 in both. The `--monokernel` server compiled "widths 4-16 step 4, 20 builds" and took specialized verify steps of 4, 8 and 16 rows.

**Tests.** `test_runtime.py` (CPU) gains 12: MTP accepted at 1 and 3 draft tokens with the verify widths, each MTP refusal, and the routing of verify steps (whole uniform requests filling the width; mixed, ragged or non-spec steps go stock). With #63032's tests, 63 passed on MI355X at `77da850940` (`VLLM_ROCM_USE_AITER=1 pytest -v -s tests/models/qwen4_exp/amd_specialized_decode`).

**Host syncs.** With `VLLM_GPU_SYNC_CHECK=error` and MTP-3, a `--monokernel` server ran the 1k/128 sweep at concurrency 1–16 and GSM8K (200 questions, 4 threads; 0.97) with no sync error, taking specialized verify steps of 4, 8 and 16 rows; a stock server alongside did the same (0.97).

## Details

**Why vLLM's GDN core on verify steps.** A request's rows in a verify step are consecutive tokens: the conv window and the recurrence must run in order, each draft's state kept in its own slot (`spec_state_indices_tensor`) and the next step starting from the last accepted one (`num_accepted_tokens`). The GDN block runs one token a request. So a GDN layer of a verify step runs `in_proj_qkvz` / `in_proj_ba`, `qwen_gdn_attention_core` (AITER's Triton path, which applies the spec-decode metadata) and `RMSNormGated`'s Triton kernel (one launch: this forward is not compiled), and hands the o_proj block its input. Everything around it stays on the kernels. A spec-aware GDN block is a follow-up.

**Steps.** `DecodeConfig.q` is `num_speculative_tokens + 1`; the widths are its multiples up to 16. `plan()` takes a pure verify step whose GDN metadata has uniform spec length `q` and `num_spec_decodes * q` rows; under FULL graphs a replay pads whole requests with the null state slot and one accepted token, which vLLM's GDN core serves. With MTP every decode step is a verify step, so the GDN block is not built and the conv state check allows the drafts' `q - 1` extra entries.

**Drafter input.** The stock forward copies the state before the final mixer into `_mtp_hidden_buffer` for the drafter; the specialized step copies the same tensor.

**Refusals.** Speculative methods other than MTP, more than 15 draft tokens, adaptive verification, dynamic speculative decoding, and MTP without AITER's Triton GDN kernels (vLLM's `GDN_AITER_TRITON_AVAILABLE`).

**Size.** About 160 changed lines in the model-owned `runtime/` (plus README and 75 of tests). No core changes.

**Limitations.** At MTP-3 the kernels cover up to 4 concurrent requests (16 rows); wider verify steps run stock. CI does not run MTP end to end: the published checkpoint does not load MTP until its `config.json` is fixed.
