# [CPU][Zen] Serve MXFP4 and NVFP4 checkpoints through zentorch

[Upstream PR](https://github.com/vllm-project/vllm/pull/64429) · state: open · merged: False

## Original PR description



## Overview

Fixes [#61027](https://github.com/vllm-project/vllm/issues/61027)

Serve MXFP4 and NVFP4 checkpoints on AMD Zen CPUs through zentorch's W4A8 kernel, for MoE experts and dense linear layers, with the weights kept at four bits. MoE experts go through `zentorch_fused_moe` and linear layers through `zentorch_dynamic_qlinear`, the ops the existing DA8W4 paths already use. Needs the next [zentorch](https://github.com/amd/ZenDNN-pytorch-plugin) release, which teaches both ops the E2M1 weight format; the `zen` extra pin moves to it before this merges.

## Claims

- **MXFP4 MoE on Zen** (`Mxfp4MoeBackend.ZEN_CPU`, preferred ahead of `CPU`): gpt-oss-20b runs +6.3% / +7.7% output tokens/s at batch size 32 and +1.8% / +2.8% at batch size 8, compared with vLLM's own MXFP4 MoE kernel. Upstream, that kernel (`CPUExpertsMxfp4`) needs AMX and the emulation experts need CUDA or XPU, so Zen CPUs currently have no MXFP4 MoE backend at all.
- **NVFP4 MoE on CPU** (`NvFp4MoeBackend.ZEN_CPU`): none existed. Qwen3-30B-A3B-NVFP4 now serves.
- **MXFP4 and NVFP4 linear on CPU** (`ZentorchMxFp4LinearKernel`, `ZentorchNvFp4LinearKernel`): the CPU had no kernel for either, so dense checkpoints failed kernel selection. NVFP4 covers W4A4 checkpoints; W4A16 NVFP4 linear is not served.
- **Selection off Zen is unchanged**: every new kernel gates on `has_zentorch_op`, which needs `ZenCpuPlatform`.

## Validation

```bash
export VLLM_CPU_OMP_THREADS_BIND=0-31 VLLM_CPU_KVCACHE_SPACE=40
vllm bench throughput --model openai/gpt-oss-20b --dtype bfloat16 \
  --moe-backend zen_cpu --dataset-name random \
  --random-input-len 1024 --random-output-len 1024 --num-prompts 128 \
  --max-num-seqs 32 --max-model-len 4096 --kv-cache-dtype fp8_e4m3 \
  --no-enable-prefix-caching

lm_eval --model vllm \
  --model_args "pretrained=openai/gpt-oss-20b,dtype=bfloat16,max_model_len=4096,kv_cache_dtype=fp8_e4m3,moe_backend=zen_cpu" \
  --tasks gsm8k --num_fewshot 5 --batch_size auto \
  --gen_kwargs max_gen_toks=2048 --apply_chat_template
```

Turin (EPYC 9005), one 32-core NUMA node per run, with this PR and a zentorch build that carries the E2M1 support.

**Throughput**, gpt-oss-20b, output tokens/s, two interleaved reps per arm on one pod. Settings: random 1024 in / 1024 out, 128 prompts, `--kv-cache-dtype fp8_e4m3`, prefix caching off.

| Batch size | Native (`--moe-backend cpu`) | This PR (`zen_cpu`) | Δ |
|---|---|---|---|
| 32 | 191.3 / 189.5 | 203.4 / 204.2 | +6.3% / +7.7% |
| 8 | 84.0 / 84.3 | 85.4 / 86.7 | +1.8% / +2.8% |

The native arm needed a local one-line change, not part of this PR: `CPUExpertsMxfp4._supports_current_device` was relaxed from AMX to AVX-512 so the kernel could run on Zen at all. Each zen rep was checked against the native arm on the same prompts: the first generated token agrees on 119–120 of 128 prompts.

In a 128/128, batch-size-32 profile, MoE prompt time drops 31%. Decode is within 1.5% per call; that remainder is zentorch's per-call setup.

The other formats have no native CPU kernel to compare against. This PR's numbers, same settings, two reps:

| Model | Layers on zentorch | bs 32 | bs 8 |
|---|---|---|---|
| nvidia/Qwen3-30B-A3B-NVFP4 | MoE (NVFP4, group 16) | 103.4 / 104.6 | 54.6 / 54.4 |
| RedHatAI/Qwen3.8-27B-MXFP4 | dense linear (MXFP4) | 56.3 / 56.3 | 30.3 / 30.4 |
| RedHatAI/Muse-Glimmer-30B-NVFP4 | dense linear (NVFP4) | 42.2 / 41.3 | 21.3 / 21.8 |

**Accuracy**, GSM8K, full set, 5-shot, chat template, flexible-extract:

| Model | This PR | Native |
|---|---|---|
| openai/gpt-oss-20b | 0.872 | 0.868 |
| nvidia/Qwen3-30B-A3B-NVFP4 | 0.857 | — |
| RedHatAI/Qwen3.8-27B-MXFP4 | 0.973 | — |
| RedHatAI/Muse-Glimmer-30B-NVFP4 | 0.713 | — |
