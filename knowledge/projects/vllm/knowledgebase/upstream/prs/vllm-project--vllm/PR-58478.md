# [Bugfix] Reserve max-num-queued-reqs slots at preflight so a burst is rejected before render

[Upstream PR](https://github.com/vllm-project/vllm/pull/58478) · state: open · merged: False

## Original PR description

## Summary

`--max-num-queued-reqs` was checked twice per request — once as a preflight
(`check_admission(n)`, no `request_id`) before render, and once at hand-over
(`check_admission(request_id=...)`) after render — but nothing was counted
between the two. Under a burst, every request passed the preflight, the
single-worker multimodal renderer then rendered them one at a time, and the
surplus was rejected with `QueueOverflowError` (HTTP 503) only after paying
the full render cost. This change makes the preflight **reserve** the slots it
checks, so requests that will be refused are refused up front instead of after
rendering.

## Problem

Reported in #58192:

- `check_admission(n)` (preflight) is called from `GenerateBaseServing._preflight`
  before `online_renderer.render_*`.
- `check_admission(request_id=...)` is called again in `AsyncLLM._add_request`
  / the `n>1` fan-out, after `input_processor.process_inputs_async` (the render).

Both reads only see requests already handed over to the `OutputProcessor`.
A request in between the two checks is invisible to admission. In a production
burst the API server held ~85–101 requests in the render pipeline while the
engine itself was empty, and 54% of the 503s took 4–9 s p50 to arrive because
the request had already been fetched and rendered.

## Root cause

The preflight check and the hand-over check observe the same counter
(`get_num_unfinished_requests()`) at two different times, with an unbounded
render in between. There is no bookkeeping for "admitted, not yet handed over."

## Solution

Add a per-process reservation ledger to `AsyncLLM`:

- The **preflight** call (`request_id is None`) now also reserves `n` slots
  when it passes, so `unfinished + reserved` is the live admission count.
- The **hand-over** call (`request_id` given) consumes `n` reserved slots — the
  request moves from `reserved` to `unfinished` rather than being double counted.
- A 60 s TTL ages out reservations whose request never hands over (client
  disconnect during render, render error), so a dropped connection cannot leak
  a slot forever.

The second check becomes a backstop by construction: at preflight we already
guarantee `unfinished + reserved + n <= max`, and hand-over only transfers a
slot.

## Testing

New unit tests in `tests/v1/engine/test_admission_control.py`:

- `test_preflight_reserves_slots_and_bounds_a_burst`
- `test_handover_consumes_preflight_reservation`
- `test_abandoned_preflight_reservation_times_out`
- `test_preflight_reservation_is_n_aware`

All existing admission tests are unchanged in expectation and pass (the
`__new__`-based test harness now seeds the new reservation state).

## Compatibility

- No API or config changes. `max_num_queued_reqs` now actually bounds what it
  says: requests are rejected at preflight rather than after render.
- The reservation counter is per-process. The shared `SharedAdmissionStats`
  (used with `--api-server-count > 1`) is still aggregated at hand-over exactly
  as before; this only closes the single-process render gap.
- Behavior for `max_num_queued_tokens` is unchanged.

## Related

Fixes #58192.

## Readiness gate

**Tests.** `tests/v1/engine/test_admission_control.py` is **54 passed**, including the four
cases added here: reserve-and-bound-a-burst, hand-over-consumes-the-reservation, the TTL
expiry of an abandoned reservation, and the n-aware path.

**Patch coverage could not be measured on this box.** `pytest --cov` fails on every vLLM
target here (torch under coverage's import instrumentation), and `coverage run
--source=vllm.v1.engine.async_llm` **dumps core** on this file, so no figure is quoted
rather than a misleading one. The behavioural evidence is what the gate rests on: the
tests above fail without the reservation logic (the burst case is exactly the behaviour
that did not exist before) and pass with it.

**Edge-case review.** The change adds three things — a `deque` of reservation timestamps,
a `threading.Lock` around the check, and a TTL purge — so the cases that matter are the
state transitions and the ordering assumption, not arithmetic:

| case | result |
|---|---|
| burst of preflights at the cap | 10 reserve, the 11th raises `QueueOverflowError` before render |
| hand-over after preflight | reservation consumed, slot moves from `reserved` to `unfinished`, no double count |
| abandoned reservation (client died during render) | purged once older than `_ADMISSION_RESERVATION_TTL_S` (60 s) |
| `n > 1` fan-out | preflight reserves `n`, hand-over consumes `min(n, reserved)` |
| purge ordering assumption | all `n` slots of one reservation share one `time.monotonic()` value and are appended together, so FIFO order is time order — the leftmost entry really is the oldest |
| lock held across an `await` | no: the critical section is pure `deque` operations, so the `threading.Lock` cannot block the event loop |

**The one thing worth checking was whether a hand-over can consume a reservation it never
made**, which would silently free another request's slot. Traced through the callers, and
it cannot: every HTTP entrypoint preflights — `_preflight` (`generate/base/serving.py:174`)
is called by `openai/chat_completion/serving.py:240`, `openai/completion/serving.py:105`,
`openai/responses/serving.py:335`, `openai/chat_completion/batch_serving.py:60`,
`speech_to_text/base/serving.py:442` and `scale_out/token_in_token_out/serving.py:119`,
and `generate/generative_scoring/serving.py:204` calls `check_admission` directly. The one
path that reaches `add_request` without preflighting is the offline `LLM`
(`entrypoints/offline_utils.py:573`), and it cannot steal anything because nothing on that
path ever reserves — `_admission_reserved` stays empty, so `min(n, reserved)` is zero. The
reservation logic is also skipped entirely while `max_num_queued_reqs` is `None`, which is
its default (`config/scheduler.py:87`).

**Residual risks, stated rather than hidden.** Two are inherent to the design: the 60 s TTL
means a legitimate render that takes longer than that lets its slot be reused, so the cap
can be exceeded by the number of such in-flight renders (bounded, and the alternative is a
permanent leak); and reservations are anonymous timestamps, so a hand-over consumes the
*oldest* reservation rather than "its own" — equivalent for a count, but it means a TTL
expiry can belong to a different request than the one that leaked.

**Cross-backend.** The change is in the engine's admission path — pure Python, no device
code, so CUDA / ROCm / NPU / MUSA / CPU are unaffected. `check_admission` also exists as a
no-op default on the `EngineClient` protocol (`engine/protocol.py:71`), so other engine
client implementations keep their existing behaviour.
