# [Bugfix][Frontend] Respect item order when adding generative scoring special tokens

[Upstream PR](https://github.com/vllm-project/vllm/pull/63625) · state: open · merged: False

## Original PR description

## Overview

Fix `/generative_scoring` prompt construction when `item_first=true` and `add_special_tokens=true`: a BOS-adding tokenizer produced `item + BOS + query` instead of `BOS + item + query`, changing the scored input. Apply automatic special tokens to the first component in prompt order.

## Claims

- Item-first requests produce the same scores as query-first requests with the fields exchanged, including mixed text/token-ID inputs.
- Query-first requests, `add_special_tokens=false`, and fully pretokenized inputs retain their behavior; caller-supplied special tokens are preserved.
- Add 10 real-server regression/control cases in the existing scoring suite and document the text/token-ID contract.

## Details

`_build_prompts` always enabled automatic special tokens on the query and disabled them on each item, then concatenated according to `item_first`. The fix makes those two tokenization flags follow the requested order. Text components remain separately tokenized. A leading token-ID component is used as supplied, and its trailing text receives no automatic special tokens.

The regression uses the existing query-first path with exchanged fields as its reference, through the real HTTP endpoint and model. It covers text/text, mixed text/token IDs, both special-token settings, and query-first controls. The serving guide and request-field documentation describe the same contract.

**Related work / duplicate check:** #34539 introduced the endpoint. Refreshed open-PR searches for `generative_scoring`, `generative scoring` and `item_first` found no competing Python token-order fix, and current `main` still has the old construction. #46427 adds the separate Rust route; #61363 fixes renderer truncation. Neither fixes this Python prompt-construction path.
