# [Rust Frontend] Export vllm:num_requests_kv_fetch_by_stage like Python

[Upstream PR](https://github.com/vllm-project/vllm/pull/63962) · state: closed · merged: True

## Original PR description

## Overview

vllm-project/vllm#58874 made the scheduler count waiting requests with an async KV load per load stage and send the counts in `SchedulerStats.num_kv_fetch_reqs_by_stage` (`waiting_to_start`, `in_progress`, `completed_waiting`). The Python frontend exports them as the gauge `vllm:num_requests_kv_fetch_by_stage{model_name, engine, stage}` and appends `KV fetch: <n> waiting to start, <n> in progress, <n> completed waiting` to the periodic stats log line when any count is non-zero. The Rust stats decoder ignores the field, so a P/D decode instance on the Rust frontend has neither the gauge nor the log segment. This PR decodes the field, exports the gauge, and adds the log segment.

## Claims

- `vllm:num_requests_kv_fetch_by_stage{model_name, engine, stage}` is exported with Python's help text, with one series per stage (`waiting_to_start`, `in_progress`, `completed_waiting`) per engine, at 0 from startup and updated on every scheduler-stats update.
- Absent stages, and the whole field from engines before vllm-project/vllm#58874, are treated as zero, like Python's `.get(stage, 0)`.
- The periodic stats log line gains the `KV fetch` segment after `Deferred`, when any count is non-zero, as in Python.

- `protocol::stats::tests::scheduler_stats_kv_fetch_reqs_by_stage_defaults_and_decodes`: a MessagePack payload without the field decodes to zeros, and a sparse `{"waiting_to_start": 3, "in_progress": 1}` decodes to `[3, 1, 0]`.
- `metrics::tests::kv_fetch_reqs_by_stage_are_recorded_into_stage_gauges`: the three series exist at 0 from startup and take distinct per-stage values from a `SchedulerStats` update (snapshot).
- Red-green: with the recorder loop disabled, the second snapshot fails; on the base the family does not exist.
- The periodic log segment has no line test: the stats line is built inline in the logger loop with no formatting seam, and its `Deferred` and `Preemptions` segments have no line test either. The new segment reads the same gauges the recorder test pins.

## Details

- `SchedulerStats` decodes the field into a typed `KvFetchReqsByStage` (one `u64` per stage). Python sends a `dict[str, int]`; absent stages, and the whole field from engines before vllm-project/vllm#58874, default to zero, like Python's `.get(stage, 0)`.
- `vllm-metrics` registers `vllm:num_requests_kv_fetch_by_stage` with Python's help text and labels, and the scheduler-stats recorder sets one gauge per stage on every update, next to `vllm:num_requests_waiting_by_reason`.
- The periodic stats logger sums the stage gauges across engines and appends the `KV fetch` segment after `Deferred`, as Python does.

Ownership and layering: the wire field and its stage names live with `SchedulerStats` in `vllm-engine-core-client` (like `CachedTokensBySource`), the family in `vllm-metrics`, and recording in the existing per-engine handles, so the stats logger reads the same gauges it already reads for `Deferred`.

Divergence: Python registers the family only when `kv_transfer_config.is_kv_consumer`. The Rust frontend does not know the KV transfer role, so it pre-creates the three series for every engine, as it already does for the NIXL and Mooncake connector families; without a KV consumer they stay at 0. Making it exact would need the engine to report its KV role in the ready response.

Not a duplicate: no open PR exports `vllm:num_requests_kv_fetch_by_stage` from the Rust frontend.
