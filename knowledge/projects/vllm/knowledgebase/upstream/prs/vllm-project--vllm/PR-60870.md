# [Bugfix] Structured decisions: count Yes/No toward noul labels

[Upstream PR](https://github.com/vllm-project/vllm/pull/60870) · state: closed · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

**Stacked on #60466** (DiffusionGemma read strategy). The first commit is #60466; review only the last one.

Fixes #60862. A `noul` question in `/v1/systemone` now also reads `Yes` and `No` and adds their probability to `yes` and `no`. Without `criteria`, `label_mass` and `confidence` no longer collapse.

## Claims

- On the four Qwen models below, a noul without criteria goes from a median `label_mass` of 0.002-0.92 to 0.996-1.000, and the reply's first token is a label for every question.
- Accuracy stays within one item of main on every model, with and without criteria.
- The API output format does not change, and `choice` and `score` probabilities are bit-identical to main.

## Validation

Unit tests: `pytest tests/entrypoints/generate/structured_decisions/test_question_types.py tests/entrypoints/generate/structured_decisions/test_strategies.py` passes (30 tests). The new test checks that a capitalized reply counts toward its label.

End to end, I served each model on an H200 (`--enforce-eager --logprobs-mode raw_logprobs --max-model-len 8192`), on main and with this PR. The models cover the three architectures `/v1/systemone` supports on main. Each run asked the 74 public JevBench yes/no items (35 expect yes) once without criteria and once with criteria, plus 22 choice and score questions. Each configuration ran once.

Noul `label_mass` without criteria:

| model | median, main | median, this PR | min, main | min, this PR |
| --- | --- | --- | --- | --- |
| Qwen3-4B-Instruct-2507 | 0.002 | 1.000 | 0.000 | 1.000 |
| Qwen3-8B | 0.002 | 1.000 | 0.000 | 0.997 |
| Qwen3.5-9B | 0.923 | 0.998 | 0.607 | 0.982 |
| Qwen3.6-35B-A3B | 0.834 | 0.996 | 0.163 | 0.739 |

`choice` and `score` probabilities did not change on any model. Noul p50 latency was 19-84 ms depending on the model and moved by at most 4 ms.

## Details

Without `criteria`, the noul prompt ends with "Answer with yes or no only." and never lists the labels. Models then start their reply with "Yes" or "No", so most of the probability lands on those tokens and little on the lowercase labels.

`QuestionType.label_aliases` gives each label a second spelling whose probability counts as the label's. Only `noul` sets it, to `("Yes", "No")`. `NextTokenStrategy` reads the aliases' logprobs together with the labels, so `label_mass` and `argmax_is_label` include them. The startup check now also requires `Yes` and `No` to be single tokens after the generation prompt. This holds for all three supported architectures. The structured decisions docs now mention the extra spellings.

### Alternatives tried

I tried three other fixes and ran each with the same models, questions and settings as above.

The first changes the labels themselves to `Yes` and `No` and the instruction to "Answer with Yes or No only." It restores `label_mass` and gains 6 items with criteria in total. But it also shifts how the model answers, not only where the probability goes. On Qwen3.6-35B-A3B without criteria it loses 5 items and leans toward no (31 predicted yes, 35 expected). It changes 19 answers without criteria and 8 with criteria.

The second keeps the labels and, when there are no criteria, lists `yes` and `no` on their own lines in the prompt, as the prompt already does with criteria. It restores most of `label_mass`, but loses 5 items without criteria in total, 3 of them on Qwen3-8B.

The third pre-starts the model's reply with `{"answer": "`, so the next token is a JSON value, where lowercase `yes` and `no` are natural. It has the best total, but it changes the most answers: 22 without criteria and 18 with criteria. It loses 3 items on Qwen3-4B-Instruct-2507 without criteria, and two of that model's items still get a `label_mass` near 0.

This PR never changes an answer with criteria. Without criteria it changes 10, 9 of them on Qwen3-8B. On main that model's `label_mass` was 0.002, so its yes/no split was noise with a yes bias: it predicted yes 47 times, against 35 expected. With this PR it predicts yes 38 times.

I chose this PR because it is the only fix that stays within one item of main on every model and setting. Capitalized labels and the pre-started reply score higher in total, but each loses 3-5 items on some model, and with one run per model I cannot tell those gains from noise.

Related: #60676 (@mgoin) adds a read strategy for LiquidAI/d1-3B that also counts `yes`, `Yes` and `YES` as one label, so the two approaches agree. `CanvasStrategy` from #60466 builds its label ids through the same `type_label_ids` and inherits `read()`, so it gets the aliases without code of its own. On DiffusionGemma, noul `label_mass` without criteria goes from a median of 0.734 to 0.998 (minimum 0.003 to 0.320) at the same accuracy, and `choice` and `score` are unchanged.
