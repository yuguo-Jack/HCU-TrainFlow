# [Bench] Save server queue time and TTFT in detailed results

[Upstream PR](https://github.com/vllm-project/vllm/pull/55809) · state: open · merged: False

## Original PR description


## Purpose
PR #46768 added server-side per-request timing metrics to OpenAI-compatible Chat Completions and Completions responses. However, `vllm bench serve` discarded these metrics and only retained client-observed timing data.

This PR preserves two server-side metrics in detailed benchmark results:

- `server_queue_times`: time spent waiting in the server scheduler queue.
- `server_ttfts`: time from scheduling to first-token generation.

Both values are converted from milliseconds to seconds to match the existing per-request benchmark arrays. Missing values are represented as `null` while preserving request-index alignment. Both arrays are omitted if neither metric is available for any request, or if --save-detailed is not enabled.

The implementation supports both the Python benchmark client and the Rust benchmark client used with `VLLM_USE_RUST_BENCH=1`. Documentation is updated to distinguish these values from the client-side `queue_times` and `ttfts`.

This PR focuses on server-side queue time and TTFT to help **distinguish scheduler waiting time from time to first-token generation**. I’m happy to include the remaining per-request metrics if maintainers prefer a broader scope.

There is no associated issue. This is a follow-up integration to #46768.

I searched open PRs for `server_queue_times`, `server_ttfts`, and the combination of `enable-per-request-metrics` with `save-detailed`, and found no existing PR implementing this behavior.

AI assistance from OpenAI Codex was used during implementation. I reviewed every changed line and can explain and maintain the change.

- Run the targeted Python and Rust tests.

### Python E2E smoke test

Behavior change:

- Before: detailed benchmark results did not contain server-side queue time
  or TTFT.
- After: detailed results include `server_queue_times` and `server_ttfts`
  when these metrics are available.

The smoke test was run on the modified version using
`gemma-4-E2B-it`, with `--enable-per-request-metrics`
enabled on the server:

```bash
vllm bench serve \
  --model /path/to/gemma-4-E2B-it \
  --dataset-name custom \
  --dataset-path toolagent_3k.jsonl \
  --num-prompts 3 \
  --disable-shuffle \
  --custom-output-len=-1 \
  --request-rate 0.6 \
  --save-result \
  --save-detailed \
  --result-dir results \
  --result-filename gemma4_server_metrics_smoke_3.json
```

Results:

- 3 successful requests, 0 failures.
- Both server timing arrays were present in the saved detailed JSON.
- Each array contained 3 non-null, non-negative values and matched the
  length of the existing per-request arrays.

Saved values, in seconds (rounded for readability):

```json
{
  "ttfts": [0.820385, 0.774362, 4.330024],
  "server_queue_times": [0.000060141, 0.000023473, 0.000028463],
  "server_ttfts": [0.709359, 0.729975, 4.277035]
}
```

This E2E run covers the Python client and `/v1/completions` endpoint.
Chat Completions and Rust behavior are covered by the targeted tests above.

- esmeetu · COMMENTED · 2026-10-13T12:30:31Z · [source](https://github.com/vllm-project/vllm/pull/55809#pullrequestreview-5503517681)

Thanks for the follow-up to #46768. The change looks correct and low-risk to me. It's opt-in end to end and doesn't change output when the server flag or `--save-detailed` is off. I'm supportive of merging after a couple of small changes.

**Verified**
- Field semantics and the ms→s conversion match `build_per_request_timing_metrics` (queue = scheduled − queued, TTFT = first_token − scheduled).
- In streaming, `metrics` only rides on the final usage chunk. The bench clients already set `include_usage`, so the values are captured.
- Edge cases behave as documented. With `n>1`, `metrics` is null. With spec decoding on but per-request metrics off, `metrics` only carries `speculative_decoding`, so both arrays are omitted.
- `cargo test -p vllm-bench server_metrics`: 5 passed. The branch merges cleanly onto current main.

**Suggested before merge**
1. **Reuse the existing test helpers.** `tests/benchmarks/test_endpoint_request_func_timing.py` already has `_sse`, `_usage_chunk`, `_build_stream`, `_FakeContent`, `_FakeResponse` and `_FakeSession`. Please move the new cases there, or reuse those helpers, instead of adding a parallel set of mocks in `test_server_metrics.py`.
2. **Docs: spell out how these relate to client TTFT.** `server_ttfts` sits next to `ttfts`, so readers will compare them directly. It would help to state the decomposition, which is the main analytic use: `ttft ≈ server_queue_time + server_ttft + frontend/network overhead` (tokenization, chat template, MM preprocessing, detokenize). Please also:
   - include the `vllm serve ... --enable-per-request-metrics` command in the example;
   - note that only the `openai`/`vllm`/`openai-chat` backends populate these fields;
   - note that the flag adds server CPU overhead at high concurrency, so these runs are best treated as diagnostic runs rather than headline perf numbers.

**Nits / optional**
- Rust `output/json.rs`: `insert_server_metrics` could be called inside the existing `if config.save_detailed { ... }` block. That would remove the extra `save_detailed` parameter and the non-detailed test branch.
- `type(value) in (int, float)` → `isinstance(value, (int, float)) and not isinstance(value, bool)` would be more idiomatic.
- `_update_server_metrics` overwrites on every chunk carrying `metrics`. That's fine today because only the final chunk has it, but a short comment on that assumption would help.
- Follow-up idea: printing mean/P99 server queue time, server TTFT and derived frontend overhead to the console when available. Today users have to post-process the JSON to get anything out of this.

On Rust parity: given how small it is and that it has tests, I'm fine keeping it in this PR.
