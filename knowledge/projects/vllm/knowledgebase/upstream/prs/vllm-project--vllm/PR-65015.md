# [Bugfix][Tool Parser] Keep granite4 streamed text between tool calls

[Upstream PR](https://github.com/vllm-project/vllm/pull/65015) · state: open · merged: False

## Original PR description



## Overview

Fixes the `granite4` tool parser dropping streamed text before a tool call when the previous tool call arrived whole in one streamed delta (one line in `Granite4ToolParser._tool_extraction_step`). This carries forward #46934 (@soovittt), which was closed by the stale bot without review.

## Claims

- With `--tool-call-parser granite4`, streamed `content` no longer loses text that comes after a tool call delivered whole in one delta. Before the fix, text arriving in the same delta as the next `<tool_call>` token, ahead of it, was dropped. The tool calls themselves were still emitted, and text in deltas with no `<tool_call>` token still came through.
- This needs a streamed delta that holds a whole `<tool_call>...</tool_call>` (18 tokens for the first call in the render-server test below), for example:
  - `stream_interval` > 1 (`--stream-interval`, or the per-request `stream_interval` field);
  - speculative decoding when one step accepts a whole call (long drafts, e.g. suffix decoding, which defaults to 24 draft tokens);
  - outputs merged when the API server falls behind the engine (`RequestOutputCollector.put`);
  - streaming chat derender chunks (`/v1/chat/completions/derender` with `stream: true`).
- Non-streaming responses and token-by-token streaming were not affected, and their behavior does not change.

## Details

- Root cause (`vllm/tool_parsers/granite4_tool_parser.py`, `_tool_extraction_step`, line 185):
  - The "entering a new tool call" branch sets `self.in_tc = True`. When the `</tool_call>` token is in the same buffer, it emits the call but then reset `self.start_in_tc`, an attribute that is written only there and read nowhere, instead of `self.in_tc`.
  - The parser therefore stayed in tool-call mode after the call. The next buffer with a `<tool_call>` token went to the "between start and end" or "found the end" branch. Neither emits the text before the start token, so that text was dropped.
- Fix: reset `self.in_tc = False`. The sibling end-of-call branch a few lines below already does this after cutting out a call.
- Why the existing tests missed it: `test_tool_call_parser_complex` used 1-20 character chunks, so a whole `<tool_call>...</tool_call>` never landed in one delta.
- No model eval. The change does not alter generated tokens, tool calls or non-streaming responses. It only restores streamed text the parser dropped.
- No docs change. This restores the documented behavior of `--tool-call-parser granite4` (`docs/features/tool_calling.md`) and adds no flag, field or default.
- Not included:
  - The Rust frontend parser `rust/src/parser/src/tool/json/granite4.rs`, a separate implementation without this flag.
  - Malformed output with a stray `</tool_call>` before a `<tool_call>` in the same delta. `_tool_extraction_step` searches for the end token from the start of the buffer (line 162), so main already mis-streams such a delta (it can drop text); non-streaming rejects this output and returns it as plain content. With this fix, the text between the stray end token and the start token is streamed twice. Searching for the end token after the start token would address that; I kept it out of this fix.
  - Other tool parsers.
- This carries forward #46934 by @soovittt, which was stale-closed with no review. The fix is the same line. The tests differ: a chunk size added to the existing streaming test instead of a new unit test, plus the render-server test.
- Not a duplicate:
  - `gh pr list --state all --search` for `start_in_tc` and for `_tool_extraction_step` finds only #46934.
  - Searches for `Granite4ToolParser` (all states) and `granite4` (open PRs) find no other PR that changes this branch. #47955 (gigachat3, granite, granite-20b-fc), #48295 (llama3_json, jamba, ernie45) and #48348 (internlm2) handle whole tool calls in one delta for other parsers.
  - Of all open PRs, only #54964 touches `vllm/tool_parsers/granite4_tool_parser.py`. It changes `dump_args` only, and its head still has the `start_in_tc` line.
