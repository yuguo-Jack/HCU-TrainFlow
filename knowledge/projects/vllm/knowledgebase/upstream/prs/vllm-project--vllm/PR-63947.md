# [Bugfix] Preserve FunctionGemma escape-delimited string arguments

[Upstream PR](https://github.com/vllm-project/vllm/pull/63947) · state: open · merged: False

## Original PR description

## Overview

Preserve FunctionGemma `<escape>`-delimited argument values as strings instead of decoding them as JSON scalars or containers, unless the tool's parameter schema declares a non-string type for that argument. Fixes #63906 for streaming and non-streaming chat completions.

## Claims

- Escaped numeric, boolean, null, JSON-container and quoted text keeps its literal string value when the parameter is declared `string` or has no schema.
- Arguments whose schema declares a non-string type (`integer`, `number`, `boolean`, `array`, `object`, `null`) are still converted, so typed arguments keep working, including when the bundled chat template wraps them in `<escape>` (see Details).
- The change is confined to the FunctionGemma argument parser and reuses the shared `find_tool_properties` / `extract_types_from_schema` / `coerce_to_schema_type` helpers; no shared parser interfaces or generation logic change.

## Details

Google's [format specification](https://ai.google.dev/gemma/docs/functiongemma/formatting-and-best-practices#delimiter_for_string_values_escape) defines `<escape>` as a string delimiter. `_parse_arguments` was applying `json.loads` to the text inside those delimiters, changing values such as `123`, `true`, `null`, `[1,2]`, `{"x":1}` and `"quoted"` even for parameters declared as `string`.

Keeping every escaped value as a string would regress typed parameters, though: `examples/tool_chat_template_functiongemma.jinja` renders every earlier tool-call argument as `key:<escape>value<escape>`, including integers and booleans, so a model following that history can emit `count:<escape>42<escape>` for an `integer` parameter, which the old `json.loads` turned back into `42`. The parser therefore follows the declared schema type, the same way the K2 Horizon parser does: `string` or no schema keeps the literal text, other declared types are converted, and a value that doesn't convert stays a string. Making the template escape only string values would match Google's format more closely, but it would also need the parser to accept unescaped values, which is out of scope here.

This does not add support for unescaped non-string arguments.

Duplicate-work audit inspected actual diffs and discussions for #48705 (multi-key streaming concatenation), #59754 (single-delta calls), #57768 (regex timeout), #57989 (hyphenated names), #57120 (surrounding content), and #47254 (Rust parser). None implements this escaped-string semantic correction. Related general parser PRs #63385 and #54964 also do not change this path.
