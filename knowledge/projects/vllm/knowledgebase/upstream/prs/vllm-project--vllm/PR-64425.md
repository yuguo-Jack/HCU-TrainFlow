# [Perf] Qwen3.5 GDN: overlap in_proj_ba with in_proj_qkvz on the aux stream

[Upstream PR](https://github.com/vllm-project/vllm/pull/64425) · state: closed · merged: True

## Original PR description

## Overview

On the Qwen3.5 NVIDIA path (no torch.compile, #51012), run the tiny `in_proj_ba` GEMM on the aux stream so it hides behind `in_proj_qkvz`.
- It engages only during CUDA graph capture, for ≤ 256 tokens, and only when `in_proj_ba` is an unquantized cuBLAS GEMM;
- the threshold is hard-coded from a sweep across model sizes, quant formats and TP sizes. 

## Claims

- **Decode TPOT −2.7% / −2.2%** (C=1 / C=16) on `nvidia/Qwen3.8-27B-NVFP4` TP1
- **Decode TPOT −4.4% / −2.6%** (C=1 / C=16) on `nvidia/Qwen3.5-397B-A17B-NVFP4` TP4.
- **Outputs bitwise identical** to the serial path.

### Correctness

- **Gate:** building the layer from the configs of 12 checkpoints (BF16, FP8, GPTQ, NVFP4 V1/V2, Qwen3.6 NVFP4, 2.4T BF16/FP8/NVFP4) enables the overlap on all but `nvidia/Qwen3.8-2.4T-A95B-NVFP4` (FP8 `in_proj_ba`), and on none with `--linear-backend flashinfer_cutedsl`.
- **Why the gate:** overlapping two FP8 per-tensor projections (2.4T per-rank shapes, autotuned FlashInfer `bmm_fp8`, CUDA graph) gives wrong outputs: 172/6400 and 432/6400 mismatching outputs at TP8, M = 1 and 8 (also with forced cuBLAS/cuDNN tactics; CUTLASS was clean). `bmm_fp8` runs every call on one process-wide workspace.
- **Tests:** `pytest tests/models/test_qwen3_5.py tests/kernels/mamba/test_gdn_output_projection.py tests/kernels/mamba/test_gdn_forward_core_split.py`: 20 passed. No new test: the change only moves an unchanged GEMM onto another stream inside graph capture, which the bitwise check covers.
- **Eval:** GSM8K (`tests/evals/gsm8k/gsm8k_eval.py`, 5-shot, temperature 0, full set) on the PR arm with Qwen3.8-27B-NVFP4: 0.964, no invalid responses.

### Choosing the threshold

One CUDA graph replays 8–64 distinct layers (> 512 MB of weights, HBM-cold); median of 3 fresh processes; M = 1..8192 (the 21 rows added for large models and the remaining formats: M = 1..513) including every capture size from 128 to 512. Serial-vs-serial noise: median 0.01%, p95 0.7%.

- **≤ 256 tokens:** the overlap wins or ties everywhere (worst −0.01 µs/layer); typical savings 2–5 µs/layer, 2–3 µs on Qwen3.8-2.4T (TP4–16).
- **First regression:** 27B BF16 TP8 at 272 tokens (+3.7 µs), a cuBLAS kernel switch rather than a gradual crossover; that setup still saves 2.2 µs at 256. 272 is the next capture size, so 256 is the largest threshold that is safe everywhere. Next regressions: 27B FP8 block TP8 at 464, 35B-A3B TP4 at ~1024.

## Details

**Design**

- **Opt-in per caller** (`overlap_ba_proj=True`): only the Qwen3.5 NVIDIA path, which never runs under torch.compile, enables it. A compiled caller would need a custom op or Dynamo's stream tracing. Also off with micro-batching (its threads would share the layer's events) and LoRA (not validated on the aux stream).
- **Only when `in_proj_ba` is a plain cuBLAS GEMM** (`UnquantizedLinearMethod` with the default torch GEMM), checked at init. torch's cuBLAS workspace is per handle and stream, so it cannot collide with whatever kernel runs `in_proj_qkvz` (cuBLAS, FlashInfer `bmm_fp8`/`mm_mxfp8`, CUTLASS block FP8 with a per-call allocator workspace). FlashInfer GEMMs instead share one process-wide workspace per op (`bmm_fp8_workspace`, `mm_bf16_workspace`), so a quantized `ba` (FP8 in `nvidia/Qwen3.8-2.4T-A95B-NVFP4`, where both projections run `bmm_fp8`) or `--linear-backend flashinfer_cutedsl` (`mm_bf16`'s cuBLASLt path above 32 tokens) keeps the serial path. Same restriction as Kimi K3's side-stream path.
- **Only under CUDA graph capture.** Eagerly, the stream switch and events cost ~40 µs of host time per layer, more than the overlap saves.
- **Hard-coded threshold, no env switch**

**Alternatives considered**

- **Merge `in_proj_ba` into `in_proj_qkvz`** (one GEMM; #41457 does this as a 6-way `in_proj`). Both read the same input, but a merge needs the same quant scheme and the same TP sharding:
  - `in_proj_ba` is BF16 in every FP8, GPTQ and NVFP4 Qwen3.5/3.6/3.8 checkpoint except `nvidia/Qwen3.8-2.4T-A95B-NVFP4` (FP8 per-tensor, like its qkvz), while `in_proj_qkvz` is BF16, FP8 per-tensor, FP8 block or MXFP8. Merging would mean quantizing `ba` (a numerics change to the gating inputs) or keeping two GEMMs anyway.
- **#56534** (draft, same idea, different scope): when both projections are static per-tensor FP8 with equal input scales, it quantizes the input once and runs the two FP8 GEMMs concurrently in a custom op. It targets checkpoints like `nvidia/Qwen3.8-2.4T-A95B-NVFP4`, more complex, out of scope for and complementary to this PR.
