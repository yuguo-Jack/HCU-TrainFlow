# [Feature] Add visual token pruning for image inputs

[Upstream PR](https://github.com/vllm-project/vllm/pull/60963) · state: open · merged: False

## Original PR description




## Overview

Adds vision token pruning for image inputs with RATE (redundency-aware token pruning) method. Toggled with --image-pruning-rate in launch cli arg.

## Claims

* Adds image token pruning
* Implement the image token pruning with a method that can be applied to both image and video token pruning, with reasonable performance.

## Validation

Various tests done with vllm 0.19. Tested on Qwen3-8B-VL and Qwen3.5-9B.

Test data sets with image inputs, under 60% pruning rate, tested with Qwen3.5-9B:
| Test set | Model | Non-pruned | DivPrune | OTPrune | RATE |
| ----- | --- | -------- | ---- | --- | --- |
| TextVQA_val (single image) | Qwen3.5-9B | 80.19 | 77.88 | 74.49 | **79.43** |
| MuirBench (multi-image) | Qwen3.5-9B | 52.95 | 52.27 | 51.94 | **52.35** |

Test data sets with video inputs, under 50%/60% pruning rate:
| Test set | Model | Non-pruned | EVS | RATE |
|-------|-----|----------| ---- | --- |
| Video Bench (short video) | Qwen3-8B-VL | 73.25 | 71.3 | **71.68** |
| UCF Crime (medium length video) | Qwen3-8B-VL | 33.68 | 29.58 | **29.68** |
| Moviechat (long video, sampled 32 frames) | Qwen3.5-9B | 43.81 | 42.86 | **43.69** |

Inference speed was tested on 1280*720, 16 frame video inputs. The results suggest that TTFT was only 0.2-0.3% higher than that of EVS, likely due to the several additional matmul operations involved.
| Purning rate | TTFT - EVS | TTFT - RATE |
| --- | --- | --- |
| 0% | 4072.09 | 4072.09 | 
| 20% | 3802.67 | 3816.57 (+0.3%) |
| 50% | 3441.81 | 3448.41 (+0.2%) |

## Details

For long, vllm only holds vision token pruning for video inputs (currently EVS and VidCom), but not for image inputs. This PR adds this capability with RATE method, which, in our tests, demonstrate better performance than concurrent image-pruning methods like divprune or OTprune. Only visual embedding is used for the method, so no significant intrusive modifications are needed. The pruning method can also be applied to video inputs, with better performance than EVS, as shown in the tables above. The video token pruning part will be another PR.

Implemented and tested on Qwen-3 and Qwen3.5 models.

Toggled on with --image-pruning-rate in launch cli arg, similar to how EVS was triggered before VidCom was added.

- grance199981 · comment · 2026-10-21T16:53:33Z · [source](https://github.com/vllm-project/vllm/pull/60963#issuecomment-6321576342)

Hi, thanks for the PR — image pruning for Qwen3-VL / Qwen3.5 is very useful.

While porting RATE into an out-of-tree plugin I noticed that, as of head `06158cbe`, `compute_retention_mask_rate` seems to always keep a **prefix** of the tokens, regardless of the input:

```python
import torch
from vllm.multimodal.image_prune.rate import compute_retention_mask_rate

torch.manual_seed(0)
for n, q in [(784, 0.75), (784, 0.5), (400, 0.6), (64, 0.5)]:
    m = compute_retention_mask_rate(torch.randn(n, 64), q=q)
    k = int(m.sum())
    print(n, q, k, bool(m[:k].all()))   # -> True for every case
```

(The same happens with bf16 inputs of width 2560 and 196 / 784 / 3136 tokens.)

My reading of `_get_diversity_scores`:

- `init_scores.sort(dim=-1, stable=True)` sorts **ascending**, so `denom = sorted_values[skip_num] - sorted_values[-skip_num]` is negative for any non-degenerate input (around −1.4 on random inputs);
- the `if denom <= 0` branch then returns all-zero scores, and the stable `argsort` in `compute_retention_mask_rate` keeps the first `retain_num_tokens` tokens (the top rows of the image).

The bucketing that follows (`q_scale = buckets / denom`, pivots where `sorted_q[:-1] > sorted_q[1:]`) only makes sense with a **descending** sort; with `sort(dim=-1, descending=True, stable=True)` the denominator becomes positive (about +1.4 on the same inputs) and the pivot selection kicks in. Since the PR description mentions the accuracy numbers were measured on v0.19 before the migration, this may have slipped in during the port.

For what it is worth, the direction matters in practice. In my out-of-tree port I ran both variants, identical except for the sort direction (both score on the merger output without the position channels and use seeded projections). Keeping 25% of the tokens on Qwen3-VL-4B-Instruct changed TextVQA-val accuracy by -39.0 points with the ascending sort vs -8.1 with the descending one (DocVQA-val: -47.5 vs -24.1). On Qwen3.5-4B: TextVQA -29.9 vs -2.8, DocVQA -42.4 vs -9.5. All numbers are paired against the unpruned model (TextVQA n = 1500, DocVQA n = 1000).

Two smaller things I noticed while comparing:

1. In `_postprocess_image_embeds_evs` the retention mask is computed on `emb` **after** the 5 M-RoPE position channels are concatenated, so the positions take part in the similarity. Computing it on the features only (`emb[:, :-5]`) might be intended.
2. `_get_random_projections` uses the global RNG (cached per process), so the selected tokens can change between server restarts. A seeded `torch.Generator` would make results reproducible.

Happy to share more details if useful. Apologies if I misread the intended behaviour.

Thanks for the quick fix in 90dc2a751f, and for addressing the position channels and the seeded projections as well. On my side the current head no longer retains a prefix on any of the inputs I tried (60 synthetic cases, 196–3136 tokens, keep 25% / 50%), while the version with the `denom <= 0` guard still does.

One correction to my earlier comment: I wrote that the bucketing "only makes sense with a descending sort". That was wrong. With the ascending sort the denominator is negative, `q_scale` flips sign, and the buckets come out the same; the only problem was the guard. Your fix restores the original behaviour.

The two directions are not interchangeable, though: they pick a different pivot from each bucket (lowest vs highest projection score), so the retained tokens differ (on synthetic inputs, with the same projection matrix, only 34–80% of the kept tokens overlap). The accuracy numbers in my earlier comment ("-8.1 with the descending one", etc.) were measured with the descending variant, so they should not be read as numbers for the fixed PR. I have not measured the fixed version on real tasks.
