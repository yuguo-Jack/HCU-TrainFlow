# [Bugfix][KV Offload] Reject LHBNC at startup

[Upstream PR](https://github.com/vllm-project/vllm/pull/60005) · state: open · merged: False

## Original PR description

## Purpose

Fixes #60004. With `VLLM_KV_CACHE_LAYOUT=LHBNC`, `OffloadingConnector` offloads only head 0 of layer 0 per block, so CPU-tier hits return wrong output; reject that layout at registration instead.

### User case

1. A user sets `VLLM_KV_CACHE_LAYOUT=LHBNC` and enables native CPU offload.
2. In `register_kv_caches`, a layer's block stride (`N*C`, 8 KiB) differs from its page (`H*N*C`, 64 KiB), so the layer takes the packed-layout branch meant for DSv4, where the stride exceeds the page.
3. That branch offloads `block_stride` bytes per block, which is head 0 of layer 0, and the block is still counted as stored and later as a hit.
4. A request whose prefix comes back from the CPU tier decodes from mostly unrestored KV. On DeepSeek-R1-Distill-Qwen-14B a 64K-token prompt stores 33.5 MB instead of 12.9 GB, and a question about Gutenberg is answered with ` _1401401010…` instead of ` Johannes Gutenberg … around 1440.`

The fix raises a `ValueError` in `register_kv_caches` when an attention layer's block stride is smaller than its page, naming the layer, both sizes and a layout to use instead.

Unchanged: LBHNC (the connector's preferred layout), LBNHC and the block-outermost layouts take the same paths as before. A one-head (MLA) cache under LHBNC has stride equal to page and is still accepted.

Not a duplicate: no open issue or PR covers this. The open PRs touching the offloading worker (#53544, #56076, #59265) change mapping placement, pointer resolution and quantized-layout preference, not this check. The stride comparison came in with #51718.

## Test Plan

```bash
pytest tests/v1/kv_connector/unit/offloading_connector/
```

`test_register_kv_caches_covers_whole_page` builds the KV cache for every `KVCacheLayout`, for full attention and single-head MLA, the way the engine does, marks one block in every layer, and checks that the offloaded regions hold all of its bytes. Attention under LHBNC must raise instead; MLA under LHBNC must still pass. The test fails on main.

- hyunnnchoi · comment · 2026-10-30T05:09:57Z · [source](https://github.com/vllm-project/vllm/pull/60005#issuecomment-6515494732)

@vadiklyutiy Sorry for the slow reply. Nothing forces LHBNC by default: OffloadingConnector asks for LBHNC, and resolution uses it whenever the backends allow. LHBNC comes in only when the user sets `VLLM_KV_CACHE_LAYOUT=LHBNC`, which overrides the connector's preference. On ROCm that is a natural choice: `rocm_attn` lists LHBNC first because its native HIP kernels need H outermost, and under LBHNC it falls back to the Triton kernels. Before this PR, that setting plus CPU offload ran without a warning and returned wrong output after a CPU-tier hit; now it stops at startup. #59999 is the FlashInfer side of the same layout.
