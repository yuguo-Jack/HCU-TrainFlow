# [Bugfix][Scheduler] Reject max_num_scheduled_tokens=0 to avoid silent hang

[Upstream PR](https://github.com/vllm-project/vllm/pull/60399) · state: closed · merged: False

## Original PR description

## Overview
Fixes #60349.

Setting `max_num_scheduled_tokens=0` currently passes config validation whenever speculative decoding is disabled: the only non-positive check lives inside `_set_max_num_scheduled_tokens()` in `vllm/config/vllm.py`, whose whole body is guarded by `if self.speculative_config is not None`. The engine then initializes successfully, but the scheduler can never schedule a token, so `LLM.generate()` hangs silently forever.

This change tightens the Pydantic field constraint from `ge=0` to `ge=1`, so the misconfiguration fails fast with a clear `ValidationError` at config construction time. It covers both the `LLM()` Python API and the `--max-num-scheduled-tokens` CLI flag, which flows into the same field.

## Claims
- `max_num_scheduled_tokens=0` now raises a `ValidationError` at config construction instead of hanging at runtime.
- No existing tests or internal code paths set this field to 0 (verified by search; the only programmatic assignment is `max_num_batched_tokens`, itself constrained `ge=1`).

## Validation
- Searched the repo: no test uses 0 for `max_num_scheduled_tokens`.
- Verified no internal code path assigns 0 to this field.
