## Disclosure

AI assistance was used. The changes were reviewed and tested manually.

**Refactor only: line changes in production (non-test) code +416/-713 (net -297); the only behavioural differences are the oracle log and `ValueError` text, and the new activation-format check, listed in `## Claims`.**

## Overview

This PR removes code duplicate in MOE oracles as per https://github.com/vllm-project/vllm/issues/37753. This PR continues #43461 work on `MoEKernelOracle` to share more oracle logic.

Previously, every oracle module carried its own copy of the same two things, and the copies had drifted (`is_monolithic` computed two ways, `use_monolithic` missing from the W4A8 tail, the monolithic-only guard only in W4A8 INT8).

This PR abstracts:

- `_make_log_backend` / `_make_log_unsupported` (7 copies) → the `MoEKernelOracle` methods `make_log_backend()` / `make_log_unsupported()`
- `_return_or_raise` (7 copies) → the `MoEKernelOracle` methods `return_or_raise()` / `try_backend()` (the probe itself)
- prepare/finalize → experts → `FusedMoEKernel` assembly (8 copies under `oracle/`, https://github.com/vllm-project/vllm/blob/f4edf9f0f078ae67392510aafd1871288948a3c3/vllm/model_executor/layers/fused_moe/oracle/fp8.py#L855-L903) → `make_moe_kernel()`
- mxfp8's own `Using '…' MxFp8 MoE backend` lines and rejection message → the same helpers

Per-oracle differences become arguments (`input_dtype`, `per_token_activation`, `b_strides1/2` + `group_size`, the WNA16 `allowed_experts` assert, the W4A8 INT8 guard). Each oracle class declares `name` and binds its own `backend_to_kernel_cls`, and one instance carries the deployment inputs of a selection (`moe_config`, `weight_key`, `activation_key`, `activation_format`), which is what collapses the call sites to one or two lines and lets every auto-selection loop share one probe.

## Claims

- No public function is renamed or re-signatured; selection outcomes and the kwargs handed to prepare/finalize and to the experts constructors are identical. One exception: Standard-only experts (W4A8, W4A8 INT8) behind a `BatchedExperts` prepare/finalize now raise `ValueError` in `make_moe_kernel` instead of `TypeError`; that pairing already failed in `FusedMoEKernel._post_init_setup`, so no working configuration changes.
- `use_monolithic` is `experts_cls.is_monolithic()` everywhere (W4A8 previously relied on the implicit `False`), equivalent to the previous mix with `issubclass(..., FusedMoEExpertsMonolithic)` for every in-tree experts class.
- New coverage: the helpers' message text, first-supported/last-reason probing, each oracle class resolving its own backend→kernel-class list, the prepare/finalize + experts kwargs for 6 of the 8 oracles, and the format-mismatch rejection (49 cases).
- `MoEKernelOracle`'s six not-yet-migrated methods raise `NotImplementedError` and are no longer `@abstractmethod`, so the per-oracle classes are instantiable; restoring the contract is #37753. Activation keys stay typed via the `cast(QuantKey | None, object())` sentinel, and no oracle is mutated after construction.

## Details

- Reviewers should focus on `MoEKernelOracle.return_or_raise`: it is now the single place deciding whether an explicitly requested `--moe-backend` is accepted, and it forwards `(backend, kernel class, weight_key, activation_key, activation_format)` to `is_supported_config`. A mistake there silently changes which kernel runs instead of failing a test.
- The explicit-backend test tolerates two outcomes on purpose: either the mapped backend is returned, or the rejection message must name the mapped backend. That keeps it platform-agnostic while still catching a dropped or remapped override.
- No documentation change: nothing under `docs/` references these helpers or the log strings.
- The five log / `ValueError` text changes, all in `vllm/model_executor/layers/fused_moe/oracle/`: `Using 'X' …` becomes `Using X …` for WNA16/mxfp4/nvfp4/mxfp8 and rejections carrying a reason quote the backend value (fp8/int8/unquantized/W4A8 INT8/mxfp8); `FP8 MoE backend …` becomes `Fp8 MoE backend '…'`; mxfp8's `No supported MXFP8 expert class for …: reason` becomes the shared rejection message and its explicit path loses the `(user-requested)` hint; the explicit `scope="local"` arguments in WNA16/mxfp4 are dropped (`"local"` is the `vllm/logger.py` default, so the dedup key is unchanged); the `out of potential backends: […]` suffix now appears on `return_or_raise` paths that previously omitted it (unquantized MOONEP, nvfp4 explicit) while WNA16/mxfp4 still omit it, so "uniform wording" holds per message, not per oracle.

This is not a duplicate of the closed #44562 / #46901 / #54290 / #54294, which added per-oracle subclasses that only delegated and left the duplicated code in place; here the duplicated code is gone and the subclasses carry only `name` and `backend_to_kernel_cls`, with #37753 continuing the migration of the remaining oracle logic onto them.

I independently verified the main equivalence claims against current `main` while reviewing — sharing the derivations so other reviewers don't have to repeat them, plus one undocumented (benign) behavior change and one question.

**Claims I verified (all hold):**

- `use_monolithic=experts_cls.is_monolithic()` equivalence: `FusedMoEExpertsModular.is_monolithic()` → `False`, `FusedMoEExpertsMonolithic` → `True` (`modular_kernel.py`), and the W4A8 case that previously relied on the implicit default is safe — `maybe_make_prepare_finalize`'s `use_monolithic` defaults to `False` (`all2all_utils.py:195`) and `CutlassExpertsW4A8Fp8` is `FusedMoEExpertsModular` (`experts/cutlass_moe.py:1311`), so old and new agree. One edge worth knowing: an out-of-tree experts class inheriting `FusedMoEExperts` directly (neither Modular nor Monolithic) previously got `False` from the `issubclass` check and now raises `NotImplementedError` — all in-tree classes inherit one of the two, so this only bites hypothetical OOT subclasses, and arguably fail-loud is correct there.
- The explicit-cls call convention `kernel_cls.is_supported_config(kernel_cls, ...)` in `try_backend` matches the existing per-oracle call sites (e.g. old `fp8.py:450`), so no double-`cls` issue.
- The new activation-format `ValueError` in `make_moe_kernel` replaces a *bare assert* in `FusedMoEKernel._post_init_setup` (`modular_kernel.py:1761-1764`) — so besides turning `TypeError` into `ValueError` for the W4A8 cases you list, it also makes the failure survive `python -O`, where the assert would have been stripped. Worth a word in the claims, since it's strictly stronger than "already failed".
- Spot-checked the fp8, w4a8, w4a8_int8 and mxfp8 migrations line-by-line against `main`: selection order, log timing (`info_once` on success / `debug_once` on rejection in the auto loop), and the kwargs handed to prepare/finalize and experts constructors are preserved; the message-text deltas match the list in the description.

**Undocumented behavior change (benign, worth adding to Claims):** the old fp8 `_return_or_raise` did not initialize `reason` before the loop (`fp8.py:449-456` on main), so a backend whose `backend_to_kernel_cls` returned an empty list would have died with `UnboundLocalError` instead of the intended `ValueError`. `try_backend` initializes `reason = None`, so that latent failure mode is now the clean "does not support the deployment configuration." path. (w4a8_int8's copy had the `reason = None` init — one more instance of the drift this PR exists to kill.)

**Question:** now that `make_moe_kernel` checks `experts_cls.activation_format() != prepare_finalize.activation_format` before construction, the bare assert in `_post_init_setup` is redundant on every oracle-built path. Is removing it (or converting it to the same `ValueError`) intended for a follow-up in this series, or kept deliberately as a belt-and-suspenders for kernels assembled outside `make_moe_kernel` (e.g. the Humming path until #57538 lands)?

Nit, feel free to ignore: `MoEKernelOracle.name` defaults to `"MoE"`, so an oracle that forgets to set it logs "Using X MoE MoE backend." — a `ClassVar` without a default (or an `__init_subclass__` check) would catch that at class-definition time, though the new tests would likely catch it anyway.
