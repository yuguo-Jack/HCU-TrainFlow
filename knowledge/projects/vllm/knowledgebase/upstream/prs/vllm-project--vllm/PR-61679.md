# [Perf] Compute MRV2 prompt logits only for scored prompt rows

[Upstream PR](https://github.com/vllm-project/vllm/pull/61679) · state: open · merged: False

## Original PR description



## Overview

This PR makes Model Runner V2 compute prompt logits only for the rows whose prompt logprobs it returns. It is split out of #60527 and holds only the prompt-logprob part. It has no DiffusionGemma code. #61480 holds the single-pass part.

Today `PromptLogprobsWorker.compute_prompt_logprobs` sends every scheduled row of the step through `logits_fn` as soon as one request asks for prompt logprobs. That includes the rows of requests that did not ask and the last prompt row, whose logprob it drops. It then slices each request's rows out of the full result.

With this PR only the rows that `main` returns reach `logits_fn`. A chunk that ends inside the prompt scores all of its rows, and the chunk that finishes the prompt scores all but its last row. When those rows are the whole batch, each chunk slices `hidden_states` as before. Otherwise each chunk of up to 1024 rows gathers its own rows by index. No copy of all prompt rows is made up front.

#53267 and #54575 are open and change the same chunk loop in `compute_prompt_logprobs_with_chunking`. #53267 fuses the vocab-parallel LM head projection for small-k prompt logprobs. #54575 computes exact prompt logprobs from vocab-sharded logits. Both change how a chunk is projected. This PR changes which rows reach the projection. It duplicates neither, but the three edit the same lines. Whichever lands first makes the others rebase. I also searched open PRs for prompt logprobs and for `prompt_logprob.py`.

I used Claude Code to help with this PR. I reviewed every changed line and ran the tests below.

## Claims

- Prompt logits are computed only for the rows that report prompt logprobs. With Qwen3-0.6B, batches where every other request asks for prompt logprobs are faster:
  - NVIDIA L4: **15.0%** with 512-token prompts and **6.6%** with 4000-token prompts.
  - 44 vCPU Xeon (CPU backend): **16.5%** with 256-token prompts and **10.1%** with 4000-token prompts.
  - Batches where every request asks, and the control batch without prompt logprobs, stay within 1.5% of `main` on both.
- When only some requests ask, the transient GPU memory of prompt scoring halves, from 598 to 308 MiB in the 512-token mixed batch.
- Prompt logprobs cover the same rows as on `main`. On the L4 they are bit-identical to `main` at all 104,516 scored positions. On the CPU backend the PR differs from `main` exactly as much as two `main` runs differ from each other.

## Details

Design:

- The worker counts each request's scored rows before the projection instead of slicing them out after it. The count follows `main`: all scheduled rows of a chunk that ends inside the prompt, and all but the last row of the chunk that finishes it.
- `get_prompt_logprobs_token_ids` runs on the compacted row offsets. Each target id still comes from the position after its row.
- `compute_prompt_logprobs_with_chunking` takes an optional `prompt_rows` index. Without it each chunk slices `hidden_states` as before. With it each chunk gathers its rows.
- `PromptLogprobsWorker` had no unit test. The e2e prompt-logprob tests check values, and they would still pass if every row were projected again. 
   - Added `tests/v1/worker/test_gpu_prompt_logprobs.py` that counts the projected rows with a small LM head and checks the values against a reference. 
   - Its three tests cover the paths this PR adds: a plain slice and a final chunk with no row to score (chunked prompt), row offsets across unrequested, decode and padded requests (mixed batch), and a gather that crosses a 1024-row chunk (rows across chunks). 
   - On `main` every case returns the same scores and fails only on the row count. Most of the file is a stand-in for the 10 `InputBatch` fields the worker reads, because `InputBatch.make_dummy` builds only uniform batches without prompt state. 
   - The tests run in seconds with no model. The GPU job "V1 Executor + Worker" picks them up through `tests/v1/worker`. The CPU backend uses the same worker, so this PR also adds the file to the "CPU-Kernel Tests" job, next to the other CPU Triton sampler test.

Tradeoffs:

- Scoring fewer rows changes the shape of the logits GEMM. On a backend whose GEMM result depends on the row count, the last bits can move. On the L4 nothing moved. On the CPU backend any such change stays inside the run-to-run variation above.
- When only some rows are scored, each chunk copies up to 1024 gathered rows of `hidden_states` before the projection. `main` sliced a view but projected every row.
- Each step with prompt logprobs copies the compacted row offsets to the device. A step that mixes scored and unscored rows also copies the row indices.

Limitations:

- `compute_prompt_token_id_logprobs` (`prompt_logprob_token_ids`) is unchanged.
- #53842 rebuilds the `lm_head` LoRA mapping for each prompt-logprob chunk from token positions. With this PR a chunk can hold gathered rows. Whichever lands second has to map the LoRA rows through `prompt_rows`.
- No CI job measures prompt-logprob speed. The L4 runs above are the performance evidence.
