# [Bugfix] Let W4A8 MoE fall back to Humming for non-256-aligned shapes

[Upstream PR](https://github.com/vllm-project/vllm/pull/60711) · state: open · merged: False

## Original PR description



## Overview

Fixes #60700. The 256-alignment that CUTLASS W4A8 needs was an unconditional assert in `CompressedTensorsW4A8Fp8MoEMethod.create_weights`, so a W4A8 (int4 x FP8) MoE whose hidden or per-rank intermediate size isn't 256-aligned (e.g. `moe_intermediate_size=640`) could not load on any backend, and `auto` never fell back to Humming.

## Claims

- `--moe-backend auto` skips CUTLASS for these shapes and picks Humming.
- `--moe-backend humming` loads them.
- `--moe-backend cutlass` with such a shape fails in the oracle with the alignment reason instead of an assert.
- 256-aligned shapes still pick CUTLASS on SM90.

## Validation

## Details

`CutlassExpertsW4A8Fp8.is_supported_config` only checked the dtype, so the oracle picked CUTLASS on SM90 and the shape assert fired later in `create_weights`, for Humming too. The check now lives in `is_supported_config`, same as the shape checks in `b12x.py` and `cpu_moe.py`.

The old assert also implied that both dims divide the group size (128), which the scale layout (`dim // group_size`) needs for every backend. That is now an explicit `ValueError`, copied from `compressed_tensors_moe_w4a8_int8.py`. With TP=2 and no EP, 640 becomes 320 per rank and gets this error.

The new test monkeypatches device support, like the nvfp4 oracle test above it, so the result doesn't depend on which kernels the GPU supports. CI runs this file in the H100 FP8 MoE job.

Not a duplicate: no open PR references #60700; #57538 moves Humming setup into the oracles but does not touch this check.
