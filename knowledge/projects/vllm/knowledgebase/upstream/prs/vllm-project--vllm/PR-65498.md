# [Perf][MoE] Skip the combine staging copy in flashinfer_nvlink_one_sided

[Upstream PR](https://github.com/vllm-project/vllm/pull/65498) · state: closed · merged: True

## Original PR description

## Overview

`flashinfer_nvlink_one_sided` copies the whole expert output into FlashInfer's symmetric workspace before every combine (`moeA2APrepareCombineKernel`). This PR hands the experts the workspace combine region through the existing `allocate_fused_expert_output` hook, as `allgather_reducescatter` already does with its combine input, so FlashInfer detects the workspace-backed payload and skips the copy. Follow-up to #54268.

## Claims

- Removes the staging copy of every received row before combine. On B200 EP4 with Qwen3.5-397B shapes the copy costs 163 us per MoE layer at 16K tokens per rank (~0.5 GB read + 0.5 GB write of HBM).
- One-sided dispatch + combine microbenchmark: −6 / −43 / −161 us at 1K / 4K / 16K tokens per rank.
- End-to-end prefill throughput on Qwen3.5-397B-A17B-NVFP4 (DP4 + EP, 4× B200): +1.4% to +3.2% across ISL 512–32K, faster at every ISL, ~10M input tokens per point. gsm8k unchanged.
- No change when the hook cannot apply: experts that do not reduce top-k themselves, outputs that are not bf16/fp16, or a shape/device mismatch keep vLLM's own buffer and the existing copy.

## Details

**Root cause.** Combine in the one-sided backend is pull-based: each rank reads its tokens' partial results directly from the owners' workspace over NVLink, so the expert output must live in the symmetric workspace. `FlashInferNVLinkOneSidedPrepareAndFinalize` did not override `allocate_fused_expert_output`, so the modular kernel gave the experts a buffer from vLLM's workspace manager and `finalize()` passed that buffer to `combine()`. FlashInfer then launched `moeA2APrepareCombineKernel` with `ep_size * tokens_per_rank` CTAs to copy every received row into the combine region. `NaiveDPEPPrepareAndFinalize` (AGRS) already overrides the hook, so AGRS never paid an equivalent copy.

**Change.** `allocate_fused_expert_output` returns `communication.get_combine_input_buffer(dtype)`, a `[ep_size * tokens_per_rank, hidden]` view of this rank's combine region. `finalize()` is unchanged: `NVLinkOneSidedAlltoAll.combine()` compares the payload pointer with that buffer and passes `payload_in_workspace=True`, and FlashInfer reduces the copy kernel to a single CTA that only bumps the round flag. The hook returns `None` (old behavior) unless the experts reduce top-k themselves (`TopKWeightAndReduceNoOP`), the dtype is bf16/fp16 (the combine region is sized for 16-bit rows), and shape and device match.

**Why it is safe.**

- The combine region starts after the last dispatch payload region (cacheline aligned), so experts can read the dispatched activations while writing their output.
- Peers may still be reading a rank's combine region right after its combine returns. The next layer's experts write that region only after the next dispatch, which waits for completion flags that every peer sets after its own combine. This is the same point where the staging copy writes today.
- The view is valid between dispatch and combine. The modular kernel calls the hook from `_fused_experts`, after `_prepare` (dispatch) and before `_finalize` (combine). The address depends only on the workspace base and `runtime_max_tokens_per_rank`, so CUDA graph capture is unaffected.
- No new host-device synchronization: the hook only builds a tensor view.

**Duplicate check.** No open or closed PR touches `allocate_fused_expert_output` or `get_combine_input_buffer` for this backend (`gh pr list --search` on both names, "nvlink one sided combine copy", and `flashinfer_nvlink_one_sided`). Related but different: #59134 (dispatch sizing for experts that quantize their own inputs).
