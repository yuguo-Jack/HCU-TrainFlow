# [Rust][Benchmark] Keep transport failures visible in measured requests

[Upstream PR](https://github.com/vllm-project/vllm/pull/65284) · state: closed · merged: True

## Original PR description



## Overview


Measured workload requests currently retry connection reset, refused, and
timeout failures up to three times. A later successful attempt can hide an
overloaded or unstable service and report the sample as successful.

The retry also changes the workload being measured: failed attempts and
backoff are omitted from per-request latency, while they still extend the
overall benchmark duration and retain a concurrency slot. This can produce
normal-looking latency and failure counts alongside unexpectedly lower
throughput.

Remove automatic retries only from the measured request path so each
scheduled sample produces one HTTP attempt and one observable result.
Preparation-stage retries remain unchanged.



## Claims


- Report measured connection failures directly instead of replacing them with
  the result of a later attempt.
- Keep the scheduled request count, arrival behavior, and concurrency pressure
  consistent with the configured workload.
- Prevent failed attempts and retry backoff from being excluded from
  per-request latency while still affecting total benchmark duration.
- Preserve endpoint readiness and tokenizer preparation retries, which occur
  outside the measured workload.
- Add an entry-point regression test that resets the first connection, would
  accept a second request, and verifies that the benchmark sends only one
  workload request and reports it as failed.
- Document the measured-request behavior in the Rust benchmark README.



## Validation

```bash
cargo test -p vllm-bench test_measured_request_does_not_retry_connection_failure
cargo test -p vllm-bench
cargo clippy -p vllm-bench --all-targets -- -D warnings
cargo fmt --all -- --check
```



## Details

The previous loop used max_retries = 3 with an inclusive range, allowing one
initial request plus three retries. The concurrency permit remained held
throughout those attempts.

The request start time was recreated before every attempt, and only the final
attempt's output was retained. If a later attempt succeeded:

- the original connection failure disappeared from the failure count;
- E2EL latency represented only the successful attempt;
- retry backoff and earlier attempts still extended benchmark duration;
- the concurrency slot remained occupied during backoff;
- the server could receive more requests than the configured sample count.

Retries are useful for application clients, where completing an operation can
be more important than exposing a transient failure. For a benchmark, however,
the requests and arrival schedule define the workload. Retrying inside the
measurement changes that workload and makes overload less visible.

The Python benchmark provides a useful reference for this behavior: it invokes
the request function once per scheduled sample and returns transport errors as
failed outputs. Using the same one-attempt model avoids a Rust-only recovery
policy and supports meaningful comparisons between the two clients.
