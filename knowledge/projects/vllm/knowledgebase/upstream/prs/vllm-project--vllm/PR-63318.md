# [Rust Frontend] Support --return-tokens-as-token-ids

[Upstream PR](https://github.com/vllm-project/vllm/pull/63318) · state: closed · merged: True

## Original PR description

## Overview

The Rust frontend rejects `--return-tokens-as-token-ids` at startup, although it already honors the per-request `return_tokens_as_token_ids` field. This PR supports the flag with Python's semantics: it is the server-wide default, and a request's own value overrides it.

## Claims

- `vllm serve ... --return-tokens-as-token-ids` (with `VLLM_USE_RUST_FRONTEND=1`) and `vllm-rs serve ... --return-tokens-as-token-ids` start, and chat and completions logprobs render tokens as `token_id:{id}` when the request omits the field or sends `null`.
- An explicit request value wins in both directions: `false` on a server started with the flag returns decoded tokens, `true` without the flag returns placeholders, as before.

- New route test `server_return_tokens_as_token_ids_is_the_request_default`: chat and completions, streaming and non-streaming, against the mock engine, for (server flag, request field) = (on, omitted), (on, `null`), (on, `false`), (off, omitted), (off, `true`); it checks sampled and top-candidate tokens. Ignoring the server flag fails it.
- New CLI test `serve_passes_return_tokens_as_token_ids_into_config`.
- E2E on a GB200 node, `tests/entrypoints/openai/test_return_tokens_as_ids.py` with `VLLM_USE_RUST_FRONTEND=1` and `vllm-rs` built from this branch. The file's server loads a LoRA through `--lora-modules`, which fails at startup on `main` under Rust (the `LoraRequest` layout fix is vllm-project/vllm#63295); with that fix applied for the run, both chat cases pass (`[True]` uses the server flag, `[False]` the request field). The completions cases fail on `token_strs[1:] == top_logprob_keys` with or without this change: Rust builds each completions `top_logprobs` entry as a `HashMap`, so the sampled token is not reliably the first key. Their token strings are `token_id:N` in both variants.

## Details

Python resolves the flag per request in `_create_chat_logprobs` / `_create_completion_logprobs`:

```python
should_return_as_token_id = (
    return_as_token_id if return_as_token_id is not None else self.return_tokens_as_token_ids
)
```

- `vllm-cmd`: the flag moves from the `Unsupported` markers to a `bool` on `SharedRuntimeArgs` (Python's help text), carried into `ApiServerOptions.default_return_tokens_as_token_ids`.
- `vllm-server`: the chat and completions `ResponseOptions` keep the request field as `Option<bool>` instead of collapsing it to `false` during lowering, and each route's response stage, which already receives both `ApiServerOptions` and `ResponseOptions`, resolves it once with `unwrap_or(default)`. DTO lowering stays request-only, so `prepare_*_request` (also used by the render routes) takes no server config.

`/inference/v1/generate` is unaffected: Rust serves only `output_mode="tokens"`, whose logprobs carry integer token IDs, and Python's flag only changes its text levels.

Not a duplicate: no open PR implements the flag in Rust. vllm-project/vllm#62684 edits `routes/openai/completions.rs` for `echo` with `return_token_ids`; this PR touches only the option destructuring in that file.
