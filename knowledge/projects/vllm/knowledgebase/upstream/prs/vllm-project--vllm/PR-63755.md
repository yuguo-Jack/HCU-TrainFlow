# [Doc] Qwen3.8-Flash-Next: add 1x RTX PRO 6000 NVFP4 (TP1) profile

[Upstream PR](https://github.com/vllm-project/vllm/pull/63755) · state: open · merged: False

## Original PR description

Adds a single-card profile for `recipes/models/Qwen/Qwen3.8-Flash-Next.yaml`: the RadixArk NVFP4 checkpoint on one RTX PRO 6000 Blackwell Workstation (96 GB) with the ~51 GB N-gram table offloaded to host RAM. Supersedes vllm-project/recipes#1055, which was opened before the recipes moved into this repo.

## What it adds

- `meta.hardware.rtx_pro_6000: verified`
- New variant `nvfp4_radixark` (`RadixArk/Qwen3.8-Flash-Next-NVFP4`, label "NVFP4 (RadixArk)", `vram_minimum_gb: 163`, `supported_hardware: [rtx_pro_6000]`) with an `rtx_pro_6000` override: `vram_minimum_gb: 80`, `--max-model-len 262144 --max-num-seqs 6 --max-num-batched-tokens 8192 --gpu-memory-utilization 0.95 --mamba-cache-mode align`
- `features.spec_decoding.hardware_overrides.rtx_pro_6000`: K=2 with a separate NVFP4 MTP drafter directory (`/root/.cache/huggingface/Qwen3.8-Flash-Next-MTP-NVFP4`) instead of the checkpoint's bundled BF16 MTP head, which costs a much smaller KV pool on a 96 GB card
- `hardware_opt_in_features.rtx_pro_6000: [spec_decoding]`
- Guide subsection "NVFP4 on a single RTX PRO 6000 (TP1)" under Serving: image digest, rendered command, drafter-directory steps, KV pool, single-stream and parallel decode tables, acceptance, correctness check, `/v1/messages` caveat
- Troubleshooting: the `--max-num-seqs 256` advice now excepts this profile (tested at 6)

## How it was tested

Image `vllm/vllm-openai:nightly` at `sha256:6b90105076216e861cd30fae8828efef9263a0399137b894289f3b6a685bf4ff` (vLLM `0.32.1rc1.dev466+ge4a5b5537`, commit `e4a5b553`, 2026-10-25). The command is the one the builder renders for this hardware (default strategy `single_node_tep` at TP1), run inside its `docker run` wrapper with only the port changed; the last line is the Spec Decoding toggle:

```bash
VLLM_USE_RUST_FRONTEND=1 \
vllm serve RadixArk/Qwen3.8-Flash-Next-NVFP4 --enable-prefix-caching --max-model-len 262144 --max-num-seqs 6 \
  --max-num-batched-tokens 8192 --gpu-memory-utilization 0.95 --mamba-cache-mode align --enable-expert-parallel \
  --tensor-parallel-size 1 --kv-cache-dtype fp8 --attention-config.indexer_kv_dtype fp8 --enable-auto-tool-choice \
  --tool-call-parser qwen3_coder --reasoning-parser qwen3 \
  --speculative-config '{"method":"mtp","num_speculative_tokens":2,"model":"/root/.cache/huggingface/Qwen3.8-Flash-Next-MTP-NVFP4"}'
```

- Parallel decode, MTP K=2, distinct conversations, 512 tokens each, median of 3 bursts: 6 streams at 256 ctx = 565 tok/s total (99 per stream); 4 streams at 100K ctx = 299 total (91 per stream); 6 x 100K exceeds the 702,444-token KV pool and queues (4 running, 2 waiting) with no preemptions or errors.
- Single stream (256 / 16K / 128K ctx): 101.0 / 98.4 / 97.3 tok/s without MTP, 136.1 / 129.5 / 127.4 with MTP K=2; KV pool 975,608 tokens without MTP, 702,444 with it (prefix caching on). MTP acceptance 53.6% on synthetic prompts, workload-dependent.
- Correctness (MTP K=2, prefix caching off, Python frontend): teacher-forced mean logprob -0.42597 (sd 0.00675, n=8) vs -0.42783 (sd 0.00677) from a reference server on the same checkpoint, the same within noise; tool calls, reasoning split and `prompt_logprobs` OK on both frontends.

Caveat: with the Rust frontend (the recipe default) `/v1/messages` returns `501 Not Implemented`; the guide tells Anthropic-Messages-API clients to set `VLLM_USE_RUST_FRONTEND=0`. This was the only ERROR line in any test log.

Credits: the NVFP4 MTP file originates from Inferact; provsalt redistributes it byte-identically (download revision `48d98195ac8da8ff10d9ee497b5d52e7817f058d` tested); Peuqui reported the BF16 MTP head and wrote mtp-quant-transplant.
