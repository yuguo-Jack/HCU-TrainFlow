[Upstream PR](https://github.com/vllm-project/vllm/pull/62319) · state: open · merged: False

## Original PR description

# [Bugfix][NIXL] Save chunked host-buffer prefills after their final chunk 

## Overview

With `kv_buffer_device="cpu"`, the NIXL prefiller copies each request's blocks to the host buffer one step at a time and copies only the blocks newly allocated in that step. A chunked prefill of a hybrid Mamba/GDN model therefore copies its SSM state after the first chunk only, and the decoder starts from that stale state. This PR saves a chunked prefill once, in the step that completes it, with all of its blocks.


## Claims

- With a host buffer, a chunked prefill of a hybrid model transfers its final SSM state. Before this change, Qwen3.5 model series under P/D returned a one-token `<|im_end|>` completion for every chunked prefill.
- Single-step prefills are saved exactly as before: same step, same blocks.
- The total D2H copy volume per request is unchanged. The copy now runs in one step instead of being spread across chunk steps.

## Details

**Flow.** One request from the reproduction above: 3906 prompt tokens after the P-side N-1 truncation, P budget 2048, `kv_buffer_device="cpu"`. Groups 0-2 are GDN (SSM) groups and group 3 is full attention. With the hybrid page-size alignment, an attention block holds 576 tokens: `block_len_per_layer=2359296` in the `Hybrid SSM registration` log line, and 7 blocks cover 3906 tokens.

| Step | Tokens computed | Blocks newly allocated | `_build_save_meta` output → D2H copy | Host copy of the SSM state afterwards |
| --- | --- | --- | --- | --- |
| 1 | 0-2047 | SSM `[40],[39],[38]`; attention `[37,36,35,34]` | `[40],[39],[38],[37,36,35,34]` | state after token 2047 ✔ |
| 2 | 2048-3905 | SSM none; attention `[33,32,31]` | `[],[],[],[33,32,31]` | still the state after token 2047 ✘ |

1. Step 1 allocates the request's SSM state block in each GDN group plus four attention blocks. After the forward, `wait_for_save` → `save_kv_to_host` copies these blocks D2H.
2. Step 2 rewrites blocks 40/39/38 in place on the GPU so that they hold the state after the full prompt. They are not newly allocated, so they are not in the save list, and the host buffer keeps the step-1 values.
3. Attention block 34 holds tokens 1728-2303. Only tokens 1728-2047 had been written when it was copied after step 1. Tokens 2048-2303 are written in step 2, and the block is never copied again.
4. The request finishes. `request_finished` hands D the full list `[40],[39],[38],[37..31]`, and D reads the host buffer through NIXL. Blocks 31-33, 35-37 and the first part of block 34 are correct. The SSM state and the tail of block 34 correspond to the first 2048 tokens only. D recomputes the last prompt token from this state (P truncated it for the Mamba N-1 handoff) and samples `<|im_end|>`.

Without chunking, step 1 covers the whole prompt and every block is final when it is copied. On the default budget of 4096 tokens, this ~3.9k-token prompt alone never chunks. The failure appears once concurrent prefills share the token budget and later arrivals are chunked.

**Fix.** `_build_save_meta` accumulates a request's block ids in `_reqs_save_block_ids` across steps. It emits a single save in the step where `num_computed_tokens + num_scheduled_tokens >= num_prompt_tokens` (the existing completion check), including when that step allocates no new blocks. The copy then runs after the last forward, when every block is final. This is the same approach MoRIIO's write mode uses (`_reqs_need_pending_save`).

- A resumed request carries its full block list, so it replaces the accumulated one.
- Entries whose request has left `_reqs_need_save` are dropped. That happens when an aborted partial prefill is popped in `request_finished`.
- Both NIXL pull and push schedulers use this method, and the save metadata has no other consumer.
