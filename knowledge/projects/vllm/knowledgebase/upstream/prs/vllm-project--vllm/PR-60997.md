# [ROCm][Perf][Kimi-K3] Specialized decode on gfx942 (MI325X)

[Upstream PR](https://github.com/vllm-project/vllm/pull/60997) · state: open · merged: False

## Original PR description

## Overview

This ports the Kimi-K3 specialized decode ([#60683](https://github.com/vllm-project/vllm/pull/60683), MI355X) to gfx942, validated on MI325X. The kernels run on any gfx942 with 304 CUs. But Kimi-K3 at TP8 holds 199.89 GiB of weights a rank (the same with the kernels off and on), more than an MI300X's 192 GB. So MI300X can't serve it either way. 

It keeps the same folder, the same switch (`additional_config={"decode_backend": "latency_specialized"}`), and the same refusals, per-step plan, layer mode and fail-stop.

## Validation

All runs are on 8x MI325X (gfx942, 304 CUs).

- **pytest** `tests/models/kimi_k3`: 343 passed, 200 skipped, 0 failed. This includes:
  - K1 and K2 (TP8) against vLLM's ops at widths 8 / 6 / 4 / 2. Width 6 is the K2 build with the most LDS.
  - A CUDA graph of K2 at each width, replayed 300 times bit for bit.
  - A stalled rank.
  - The served fail-stop test (dummy 8 layers, TP8: requests are served, then all 8 ranks give up at the same step and the server exits).
  - These ran before the rebase onto current `main`. The rebase changed none of the kernel or numerics files. After it, `test_runtime.py`, now with upstream's MoRIIO tests, gives 56 passed.
- **ISA:** gfx950 builds are 28/28 byte-identical to `main`. gfx942 builds use no private memory and spill no VGPRs; the peak LDS is 62,496 B of 65,536 (K2, width 6).
- **Startup refusal:** one deployment with TP4, the V1 model runner, no speculative decoding, gfx942 without the int4 flag and `ARCH=gfx950` gives the same `ValueError` on every rank, listing all five reasons. `decode_backend="fast"` is rejected.
- **pre-commit** (including mypy): passes.

### Performance

The random rows use 1024 output tokens with `ignore_eos` and synthetic rejection sampling. Acceptance length 3.84 at k=7 is the drafter's measured rate. At k=3 and k=1 it is 1.0 (every draft rejected), so TPOT there is the time of one decode step. ## Details

**Duplicate check:** no other open PR ports the K3 specialized decode to gfx942. [#61498](https://github.com/vllm-project/vllm/pull/61498) is MI355X only. 

**What changes on gfx942:**

- `mono/common/arch.py` picks the target the way FlyDSL does (`ARCH`, else the GPU), and sets the LDS size: 64 KB instead of 160 KB.
- **K1:** in_proj streams x a K window at a time (`stage_gemv_pair`). The next window loads under the current window's MFMAs.
- **K2:**
  - The routed experts read vLLM's packed-int4 requant in place (aiter's a16wi4 layout, `mono/common/i4.py`). gfx942 has no MXFP4 MFMA, so the latent and the intermediate stay bf16, staged in K phases / K slices.
  - The dequant reproduces aiter's gfx942 int4 dequant bit for bit.
  - The 16x16x32 bf16 MFMA runs as two 16x16x16, and `shuffle_xor` replaces the permlane swaps.
- **Runtime:**
  - Startup refuses three things:
    - gfx942 without the int4 flag;
    - any GPU with fewer CUs than the 256 CTAs (an MI325X has 304, and the rest idle);
    - an `ARCH` environment variable that differs from the GPU, which would make FlyDSL build the kernels for another GPU than the one the checks and vLLM's MoE follow.
  - The weight guard checks the int4 experts' shape, dtype, shuffle and scale layout.
- The gfx950 code paths are unchanged.

**Serving on gfx942:** these constraints come from vLLM's MLA backends, not from this change:

- The DSpark draft is non-causal. `ROCM_AITER_MLA` has no gfx942 non-causal kernel, and `TRITON_MLA` refuses non-causal attention with DCP. So gfx942 runs DCP 1 with `"attention_backend": "TRITON_MLA"` for the draft.
- AITER's gfx942 fp8 MLA decode takes at most 4 query rows (k=7 needs 8), so the KV cache is bf16.

The README documents this, together with the `--quantization-config` flag.

```
VLLM_USE_V2_MODEL_RUNNER=1 VLLM_ROCM_USE_AITER=1 VLLM_ROCM_USE_AITER_MOE=1 VLLM_ROCM_USE_AITER_MLA=1 \
vllm serve moonshotai/Kimi-K3 --trust-remote-code --language-model-only -tp 8 \
  --max-model-len 16384 --max-num-seqs 4 --reasoning-parser kimi_k3 \
  --quantization-config '{"moe":{"weight":"int4_per_group_32"}}' \
  --compilation-config '{"cudagraph_mode":"FULL_AND_PIECEWISE"}' \
  --speculative-config '{"method":"dspark","model":"Inferact/Kimi-K3-DSpark","num_speculative_tokens":7,"attention_backend":"TRITON_MLA","draft_sample_method":"probabilistic","rejection_sample_method":"block"}' \
  --additional-config '{"decode_backend":"latency_specialized"}'
```

**CI:** a new `mi300_1` step runs `tests/models/kimi_k3/amd_specialized_decode` on one MI300 (K1 and the warm-up compiles). There is no 8-GPU MI300 pool, so the TP8 K2 and served tests skip in CI and were run locally (above).

**Complexity:** about 1,000 lines of kernel code, almost all of it the gfx942 int4 / LDS-windowed variants in `moe.py`, `gemv.py`, `kda.py` and `i4.py`, each behind `GFX942`.
