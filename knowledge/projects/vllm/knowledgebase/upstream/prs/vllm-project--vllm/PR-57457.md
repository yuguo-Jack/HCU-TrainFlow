# [Bugfix][HiSparse] Account for GPU copies during prefix admission

[Upstream PR](https://github.com/vllm-project/vllm/pull/57457) · state: closed · merged: False

## Original PR description

A HiSparse host-prefix cache hit can re-pin free GPU shadow copies before allocating the request's hot region. Those pins were omitted from device-block admission, so a request could pass the capacity check and then crash the engine with `Cannot get 64 free blocks from the pool`.

This change counts the unique, currently free GPU copies associated with the local host-prefix hit. The host manager includes that cost in the existing admission calculation; running requests and already-pinned copies add no cost. Under pressure, admission returns `None` so the scheduler can defer the request instead of exhausting the pool. GPU-copy reuse is preserved.

The regression uses real CPU block pools through `KVCacheManager.allocate_slots`. It exercises three insufficient-capacity cases, an exact-fit case, retry after pressure is released, and preservation of surviving copies when one earlier copy was evicted.

### Model/serving evidence and limits

The equivalent admission accounting was exercised as a local runtime adapter on B300 before this upstream refactor. Configuration: one EP8 prefill node using DeepEP high throughput, one EP8 decode node using DeepEP low latency, GLM-5.3 FP8 revision `aca966e4e02791568aa6a4ced368624b3d897f42`, BF16 KV, HiSparse on decode, index cache, NIXL pull and Mooncake CPU store. GPU KV was capped at 48 GiB/rank to force pressure. The tested vLLM source was `f7f56f01d0f588f46c20035d3ab87cf16f25addf`, with a separate complete-prefix NIXL adapter and the HiSparse layer-offset fix.

- Before the admission adapter, the 2,048-request wave crashed a decode worker with the allocation error above.
- With it, all 2,048 capacity requests completed. Peak active concurrency was 134/GPU with the remainder queued; 25 preemptions occurred in this intentional pressure wave.
- The full suite recorded 3,760 completions and 32 intentional cancellations, zero request errors/empty streams, and healthy idle endpoints at the end.
- The long-generation phase completed 256 requests while reloading 1,234.74 GiB of KV from CPU. There were no NIXL transfer/notification failures or failed required Mooncake GETs. The fixed-size prefill store rejected 15,019 optional PUT keys for lack of space.
- No pathological gibberish was observed in the output screens and inspected samples. Long-request identifier retrieval was 255/256 versus 256/256 in a resident control, whose output cap was shorter (256 versus up to 1,536 tokens). Four capacity responses also copied their identifiers incorrectly. Exact output parity is not established; this is not a general accuracy evaluation.

Those GPU results validate the local adapter's behavior, **not a model run of this new upstream commit**. The final upstream implementation is covered by the regression tests above. No throughput improvement is claimed.

### Duplicate-work check and scope

Reviewed issue #56699 and its comments, open PRs referencing it, and open PRs matching HiSparse/NIXL, admission, prefix, copies, and free blocks.

- #56946 already covers unaligned NIXL host imports, source-page clipping, and notify-only receives. Those changes are intentionally excluded here.
- #55398 adds direct GPU landing for P/D imports and admission-time tier selection. This patch instead fixes the uncounted re-pinning of existing GPU copies on a **local host-prefix hit**, without changing landing tiers.
- #56109 is a broader, not-for-merge resident-eviction design proposal; this patch preserves main's existing design.
- This does not claim to fix #56699's CUDA host-mirror failure, mixed-memory producers, or model accuracy discrepancies. Model/connector configurations and cluster-specific networking changes are not included.
