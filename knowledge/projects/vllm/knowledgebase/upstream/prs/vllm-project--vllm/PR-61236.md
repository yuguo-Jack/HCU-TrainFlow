# [Bugfix][Frontend] Honor request_id and X-Request-Id in chat and completions render

[Upstream PR](https://github.com/vllm-project/vllm/pull/61236) · state: closed · merged: True

## Original PR description

## Overview

Python render now uses the caller's `request_id` / `X-Request-Id` for chat and completions instead of always minting a random one.

## Claims

- `/v1/chat/completions/render` and `/v1/messages/render` return `chatcmpl-{id}` where `id` is the `X-Request-Id` header, else the body `request_id`, else a random UUID
- `/v1/completions/render` returns `cmpl-{id}` for one prompt and `cmpl-{id}-{i}` for several
- Requests that send no ID behave as before

## Validation

New tests in `tests/entrypoints/scale_out/render/test_render.py`:

- body ID is honored
- header beats body
- random IDs are unique across calls
- single-prompt completions
- multi-prompt completions with the suffix

```bash
pytest tests/entrypoints/scale_out/render/test_render.py -v
```

## Details

Rust render and the coupled chat path already honor both the header and the body field. Python render didn't, so an ID couldn't be followed across render, generate and derender. I reused `BaseServing._base_request_id`, so the precedence matches the coupled path.

For multi-prompt completions I only add the `-{i}` suffix when there is more than one prompt. That keeps a single prompt equal to Rust's `cmpl-{id}`. The coupled `OpenAIServingCompletion` always appends `-{i}`, so this differs slightly from it.

`raw_request` is optional on the render methods, so the Cohere and Anthropic callers and the coupled paths are unchanged. Responses render is untouched.

No duplicate: I searched open PRs for render request ID handling and found nothing.
