# [KV Transfer] Connector-agnostic KV checksums for P/D disaggregation

[Upstream PR](https://github.com/vllm-project/vllm/pull/62211) · state: open · merged: False

## Original PR description

## Overview

Connector-agnostic KV checksums for P/D disaggregation: the producer checksums the KV it sends, the consumer checksums what it received, and a mismatch is handled as a KV load failure. 

- Mostly connector agnostic. Connectors which use kv_transfer_params (e.g. NIXL pull) require no changes. Otherwise they just need to propagate the checksums via their side-channel.
- Opt-in via config arg, was no measurable performance overhead when enabled
- Drafter KV is excluded
- Adds method to linear attention classes for determining TP splits

## Claims

This PR opens @njhill's iteration of #61488 (https://github.com/vllm-project/vllm/compare/main...njhill:vllm:kv-checksum-upstream.

Changes relative to #61488 (from @njhill's summary):
- Require Triton, remove the Python fallback, support XPU.
- Fuse kernels: one kernel launch per layout instead of one per layer.
- Fewer data copies for the checksum; faster base64 encode/decode.
- The async D2H copy of checksums follows the sampled-output async flow.
- `KVConnectorOutput.kv_checksums` is a list that `KVOutputAggregator` concatenates; only the first worker reports received checksums.
- TP splits across all attention types, including KDA.
- Drafter KV is not checksummed, so transfers do not wait for the drafter.
- No new KV connector API methods: behavior is driven by the checksum config and `kv_transfer_params`, plus a new `SchedulerOutput` field connectors can read. Connectors that use `kv_transfer_params` (e.g. NIXL pull) need no changes.
- `kv_checksum_fail_closed` is removed: with checksums enabled, a failed or impossible verification always takes the KV transfer failure path.
- Unsupported setups fail at startup instead of logging a warning.

- @njhill's benchmarks show no measurable overhead from enabling checksums across concurrencies and prompt lengths.
- GPU validation on GB200 (harness: P/D behind a proxy + fixed 12-prompt probe), at da6ed7078:
  - `test_kv_checksum_cuda.py`: 12/12 passed.
  - P/D e2e, NIXL pull and push, granite-4.0-h-micro (hybrid Mamba2, DS conv layout) and Qwen3-0.6B: pull P1→D1, push P1→D1, pull P2→D1, all 12/12 outputs identical to fresh single-instance references with 0 mismatches and 0 KV load failures; one eagle3 spec-decode cell (Qwen3-8B + RedHatAI/Qwen3-8B-speculator.eagle3) likewise, with draft acceptance > 0.

Not a ask for more scope into this PR, but some concerns on future expansion for kv checksum feature to persistent KV stores (Mooncake store, CPU offload, LMCache). For example, we can store checksum in the object metadata along with the keys.

The current design, checksum computed goes worker → scheduler → kv_transfer_params. A store needs it to go worker → the connector’s save path, per chunk as it’s saved, stored with the object.

Having two flows like that could mean refactoring later. That’s why I was asking for a block-level hook between the checksum worker and the connector: keep the scheduler compare for P/D, but let connectors take the per-block values at save and supply expected values at load.

- yubofredwang · comment · 2026-10-20T20:51:14Z · [source](https://github.com/vllm-project/vllm/pull/62211#issuecomment-6301202183)

@sawsa307 Many thanks for building the block-level hook; this is the shape I hoped for! 

One additional gap is only the bytes + checksum were checked, which check for the consistency. However, this does not allow us to verify the "identity", which checks on if this is the block we intend to read. For example:

```
A put of key A times out and is revoked, and its address is freed.
A put of key B gets the same address and succeeds.
A's queued slices land afterwards.
Key B now holds [KV_A][checksum(KV_A)], and with the prototype the 8-byte checksum is correct, because it is part of the same put.
```

This has been reported in https://github.com/kvcache-ai/Mooncake/issues/4491 and pretty easy to reproduce locally.

Completely fine if this is a separate follow up PR, but just some additional cases worth covering.

cc: @njhill
