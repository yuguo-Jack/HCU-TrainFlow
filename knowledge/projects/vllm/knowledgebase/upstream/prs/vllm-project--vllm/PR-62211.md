# [KV Transfer] Connector-agnostic KV checksums for P/D disaggregation

[Upstream PR](https://github.com/vllm-project/vllm/pull/62211) · state: open · merged: False

## Original PR description



## Overview

Connector-agnostic KV checksums for P/D disaggregation: the producer checksums the KV it sends, the consumer checksums what it received, and a mismatch is handled as a KV load failure. This PR opens @njhill's iteration of #61488 (https://github.com/vllm-project/vllm/compare/main...njhill:vllm:kv-checksum-upstream. Most of the code on top of #61488 was written by @njhill, and his commits keep him as author.

Depends on #62210, which contains the same change as commit "[NIXL] Drop unreachable producer-side notif counting in push mode" here. Once #62210 merges, that commit will drop out of the diff.

## Claims

Changes relative to #61488 (from @njhill's summary):
- Require Triton, remove the Python fallback, support XPU.
- Fuse kernels: one kernel launch per layout instead of one per layer.
- Fewer data copies for the checksum; faster base64 encode/decode.
- The async D2H copy of checksums follows the sampled-output async flow.
- `KVConnectorOutput.kv_checksums` is a list that `KVOutputAggregator` concatenates; only the first worker reports received checksums.
- TP splits across all attention types, including KDA.
- Drafter KV is not checksummed, so transfers do not wait for the drafter.
- No new KV connector API methods: behavior is driven by the checksum config and `kv_transfer_params`, plus a new `SchedulerOutput` field connectors can read. Connectors that use `kv_transfer_params` (e.g. NIXL pull) need no changes.
- `kv_checksum_fail_closed` is removed: with checksums enabled, a failed or impossible verification always takes the KV transfer failure path.
- Unsupported setups fail at startup instead of logging a warning.

## Validation

- CPU unit tests at this head (`VLLM_TARGET_DEVICE=cpu`): `tests/v1/kv_connector/unit/test_kv_checksum.py`, `test_kv_checksum_scheduler.py`, `test_nixl_push_connector.py`, `test_mooncake_connector.py`, `test_nixl_connector.py`, `test_nixl_heartbeat.py`, `tests/v1/core/test_scheduler.py`, `tests/v1/core/test_async_scheduler.py`: 647 passed, 145 skipped, 2 failed. The two failures are `test_abort_timeout_on_prefiller[ray|None]`, which fail locally on main as well.
- @njhill's benchmarks show no measurable overhead from enabling checksums across concurrencies and prompt lengths.
- Not yet run at this head: the CUDA kernel tests (`test_kv_checksum_cuda.py`) and end-to-end P/D runs on GPU. Earlier GPU validation of #61488 is in that PR.

- yubofredwang · comment · 2026-10-17T23:25:36Z · [source](https://github.com/vllm-project/vllm/pull/62211#issuecomment-6243045740)

Not a ask for more scope into this PR, but some concerns on future expansion for kv checksum feature to persistent KV stores (Mooncake store, CPU offload, LMCache). For example, we can store checksum in the object metadata along with the keys.

The current design, checksum computed goes worker → scheduler → kv_transfer_params. A store needs it to go worker → the connector’s save path, per chunk as it’s saved, stored with the object.

Having two flows like that could mean refactoring later. That’s why I was asking for a block-level hook between the checksum worker and the connector: keep the scheduler compare for P/D, but let connectors take the per-block values at save and supply expected values at load.

`_blocks()` re-derives the SWA keep count (`cdiv(window, block_size) + 1`), the same rule as `blocks_per_sw` in `NixlBaseScheduler` and `MooncakeConnectorScheduler`, so it now lives in three places. If a connector ever narrows its selection (e.g. drops the `+1`), `_blocks()` still checksums a block that was never transferred and every SWA load longer than the window fails.

How about a per-group helper next to `KVCacheConfig.select_transfer_block_ids` that both the connectors and `_blocks()` call. That's also the abstraction the note in `nixl/base_scheduler.py` anticipates ("We will abstract this logic once the interface is more stable"). Offloading/store connectors that want the full sequence just wouldn't apply it.

Happy for this to be a follow-up if it grows the diff too much.
