# [Bugfix][LoRA] Restore LoRA state on wake-up from level-2 sleep

[Upstream PR](https://github.com/vllm-project/vllm/pull/62358) · state: open · merged: False

## Original PR description



## Overview

Waking from level-2 sleep without `reload_weights()` / `finish_weight_update()` left two pieces of LoRA GPU state with garbage contents: the TP logits reindex mapping and the adapter slots. On the first weights wake-up after a level-2 sleep, the worker now calls the existing `reset_lora_state()`, the same reset that `reload_weights()` and the weight-transfer path already run.

## Claims

- **TP logits mapping (TP > 1):** after such a wake-up, every request (LoRA or not) produced corrupted output. `reset_sharded_to_full_mapping()` rewrites the mapping in place, so CUDA graphs keep a valid address.
- **Adapter slots (any TP):** active adapters stayed bound to garbage slots, so LoRA requests silently decoded as the base model. The reset drops registered adapters, and the next LoRA request reloads its adapter from `lora_path`. As after `reload_weights()`, pins are dropped and must be re-applied with `pin_lora`.
- **Scope:** one flag in `Worker` (set by `sleep(level=2)`, cleared on the first weights wake-up) and one call. No LoRA-manager changes.
- **Affected flows:** `sleep_preserve_parameter_names`, or weights updated in place by user code (the "Update the weights" step of the RLHF flow in the sleep-mode docs). `reload_weights()` and the weight-transfer API are unchanged; running them after the wake-up reset is a no-op for LoRA.
- **Tests:** `test_deep_sleep_lora_tp2` checks the mapping right after weights wake-up (fails on main). A worker unit test covers when the reset is triggered.

## Details

**Root cause:** level-2 sleep discards the `weights` cumem pool, which also holds LoRA's logits mapping, slot tensors and punica metadata. `Worker.sleep` only saves registered buffers (plus parameters matched by `sleep_preserve_parameter_names`). LoRA state is otherwise reset only by `reset_lora_state()`, which runs from `reload_weights()` and `finish_weight_update()` (#39935).

**Why reset instead of restore:** `reset_lora_state()` already exists and is what `reload_weights()` and the weight-transfer path run, so wake-up gets the same semantics with no new LoRA-manager API. The cost is that active adapters are reloaded from disk on their next request instead of being rewritten from the CPU cache, and pins are dropped, exactly as after `reload_weights()`.
