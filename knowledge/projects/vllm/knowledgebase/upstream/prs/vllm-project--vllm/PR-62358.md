# [Bugfix][LoRA] Restore LoRA state on wake-up from level-2 sleep

[Upstream PR](https://github.com/vllm-project/vllm/pull/62358) · state: closed · merged: True

## Original PR description



## Overview

Waking from level-2 sleep without `reload_weights()` / `finish_weight_update()` left LoRA GPU state with garbage contents: the TP logits reindex mapping, the adapter slots and the punica metadata. They were allocated inside the `weights` cumem pool, which level-2 sleep discards. This PR allocates them in the existing `runtime` pool instead, which sleep offloads and restores at every level, so they come back intact on wake-up.

## Claims

- **TP logits mapping (TP > 1):** after such a wake-up, every request (LoRA or not) produced corrupted output. The mapping now survives level-2 sleep.
- **Adapter slots (any TP):** active adapters stayed bound to garbage slots, so LoRA requests silently decoded as the base model. Slots, slot layout, LRU order and pins now survive level-2 sleep; nothing is reloaded from disk.
- **Scope:** `LoRAModelRunnerMixin.load_lora_model` builds the LoRA manager inside `use_memory_pool(tag="runtime")` when sleep mode is on (CUDA/ROCm), so MRV1 and MRV2 are both covered. No worker or LoRA-manager changes. SGLang avoids the same problem by initializing LoRA after, and outside, its weights memory-saver region.
- **Cost:** level-2 sleep now copies the LoRA slots (`max_loras` x layer size x rank) to host memory, as level 1 already did, instead of discarding them.
- **Affected flows:** `sleep_preserve_parameter_names`, or weights updated in place by user code (the "Update the weights" step of the RLHF flow in the sleep-mode docs). `reload_weights()` and the weight-transfer API are unchanged and still reset LoRA state.
- **Not covered:** XPU, where nested memory pools are not supported (same exception as the KV-init runtime pool in `gpu_worker.py`).
- **Tests:** `test_deep_sleep_lora_tp2` checks the mapping right after weights wake-up (fails on main).

## Details

**Root cause:** level-2 sleep discards the `weights` cumem pool, which also holds LoRA's logits mapping, slot tensors and punica metadata. `Worker.sleep` only saves registered buffers (plus parameters matched by `sleep_preserve_parameter_names`). LoRA state is otherwise reset only by `reset_lora_state()`, which runs from `reload_weights()` and `finish_weight_update()` (#39935).

**Why the runtime pool:** the `runtime` tag already exists for state that must survive sleep (KV-init metadata), and nested `use_memory_pool` calls restore the outer tag, so the weights pool around `load_model` is unaffected. Restoring from the pool keeps tensor addresses, so CUDA graphs and the cached LoRA kernel pointer tables stay valid, and no wake-up hook or LoRA-manager API is needed.
