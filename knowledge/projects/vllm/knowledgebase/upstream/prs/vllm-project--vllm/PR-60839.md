# [ROCm][Qwen4Exp] Fall back from unsupported AITER FP8 MoE and all-reduce

[Upstream PR](https://github.com/vllm-project/vllm/pull/60839) · state: open · merged: False

## Original PR description



## Overview

With `VLLM_ROCM_USE_AITER=1`, `Qwen/Qwen3.8-Flash-Next-FP8` fails to start at TP2 and TP4, because two AITER paths raise instead of falling back. This PR makes both fall back, as reported in https://github.com/vllm-project/vllm/pull/60021#issuecomment-6037377198. Both failures reproduce on the latest nightly, `nightly-81198e97ba7eee2a22540caaa756b7fdddcb4d93`, on both gfx942 and gfx950.

Only block-FP8 checkpoints hit either path. `amd/Qwen3.8-Flash-Next-Quark-MXFP4` is unaffected: Quark leaves the n-gram embedding tables in BF16 and its MoE uses the MXFP4 path.

## Claims

* The FP8 checkpoint serves at TP2 and TP4 on MI300X with every AITER default on, and at TP4 on MI355X. Before this change it needed `VLLM_ROCM_USE_AITER_MOE=0 VLLM_ROCM_USE_AITER_CUSTOM_AR=0`. TP2 on MI355X gets past both errors but still fails intermittently in CUDA-graph capture, for a reason unrelated to this PR (see "Known issue").
* **FP8 MoE:** `VLLM_ROCM_USE_AITER=1` on its own no longer forces the AITER MoE kernel. When AITER can't serve the layer (here, block scales refined below 128x128), the oracle falls through to the next supported backend (Triton). Setting `VLLM_ROCM_USE_AITER_MOE` explicitly still fails loudly.
* **Custom all-reduce:** non-float tensors no longer reach AITER's custom all-reduce, whose kernel only supports float32, float16 and bfloat16. They fall back to RCCL, as with vLLM's own custom all-reduce.
* No change where AITER already worked: at TP1 both arms select AITER FP8 MoE, and float all-reduces still use AITER. GSM8K is unchanged at TP2.

| --- | --- | --- | --- |

| 4 | All defaults | Fails at model init: same `ValueError`, 32x32 | Starts; GSM8K 0.9712 / 0.9719 |

The unit tests below give the same counts on gfx950. That includes the eager and CUDA-graph AITER all-reduce tests at TP2.

**Known issue, not addressed here.** With this PR, TP2 on gfx950 gets past both errors but then fails intermittently (roughly 70-80% of runs) during the real CUDA-graph capture, which follows the memory-profiling capture and the JIT kernel warmup. One worker, usually rank 1, dies with `SIGABRT` raised from `libhsa-runtime64` and no Python traceback. Less often, both ranks hang instead. The same build starts at TP2 with `--enforce-eager`, at TP4 and TP8 with AITER custom all-reduce on, and on gfx942 at TP2.

I did not find the root cause. Disabling AITER custom all-reduce (`VLLM_ROCM_USE_AITER_CUSTOM_AR=0`) does not fix it: 3 of 4 runs still failed in the same place. Runs with slow capture (about 80 s or more) pass more often, so it looks timing-sensitive. The following made no difference: AITER's graph-buffer flush and IPC registration, the pinned-host n-gram weights, FLA `tensor_cache` eviction, a synchronize per capture size, `HIP_FORCE_DEV_KERNARG`, and real versus zeroed all-reduce output in the capture warmup. The failure is independent of the two fixes in this PR, since both are exercised by the passing configurations above. It needs an AMD ROCm investigation and should be tracked separately.

## Details

**FP8 MoE oracle.** `select_fp8_moe_backend` treated `envs.is_set("VLLM_ROCM_USE_AITER")` as an explicit request for the AITER MoE kernel and called `_return_or_raise`. But `VLLM_ROCM_USE_AITER` is AITER's global switch, and `VLLM_ROCM_USE_AITER_MOE` defaults to on, so any user enabling AITER got a hard failure whenever the MoE kernel couldn't serve a layer.

Here that happens because the TP shard of the 640-wide expert intermediate dimension (320 at TP2, 160 at TP4) is not 128-aligned. Under `auto`, `resolve_fp8_moe_weight_block_shape` refines the scales to 64x64 or 32x32, and only Triton-based kernels accept those layouts. With this change, only an explicitly set `VLLM_ROCM_USE_AITER_MOE` takes the raising path. Otherwise AITER stays first in `AVAILABLE_BACKENDS`: it is still selected wherever it is supported, and the selection log shows when it was passed over.

**AITER custom all-reduce.** The Qwen4Exp n-gram embedding reduces FP8 rows as raw bytes (`embeddings.view(torch.int8)`). Each vocabulary row has one owner, so the sum is exact. `AiterCustomAllreduce.should_custom_ar` delegated to AITER's check, which doesn't look at dtype, so the tensor reached a kernel that raises. The wrapper now applies the same dtype check as `CustomAllreduce.should_custom_ar`, and `CudaCommunicator.all_reduce` moves on to the next backend (PyNCCL/RCCL). Float inputs are unaffected.

**Scope.** Neither change is architecture-specific. Both were validated on gfx942 and gfx950. TP8 is out of scope: there the 80-wide shard is too small to refine, and `Fp8MoEMethod.create_weights` rejects it (`output_size ... = 80 is not divisible by weight quantization block_n = 128`) before either AITER path is reached.

**Trade-off.** On these configurations the MoE runs on Triton rather than AITER, which is what users get today by disabling AITER MoE by hand. Letting AITER serve these layers would need either padded TP shards that keep 128x128 blocks (as `pad_tp_shard_to_weight_blocks` already does for an explicit `--moe-backend`) or smaller-block support in AITER. Both are out of scope here.

- mrodden · comment · 2026-10-15T23:51:51Z · [source](https://github.com/vllm-project/vllm/pull/60839#issuecomment-6204717175)

We independently ran into both failure modes this PR fixes (MI355X, `Qwen/Qwen3.8-Flash-Next-FP8` at TP4: the `QuantKey(...GroupShape(row=32, col=32))...` MoE `ValueError` with all AITER defaults, and the `custom allreduce only supports float32, float16 and bfloat16` error during the profile run with `VLLM_ROCM_USE_AITER_MOE=0`), so we verified it end-to-end on the same hardware.

**Verification (MI355X, FP8 checkpoint, len 16384 / seqs 16, all AITER defaults):**

- TP2 and TP4 both boot and serve — the two configurations that hard-fail without this PR. The fallbacks engage as designed:
  ```
  Using TRITON Fp8 MoE backend out of potential backends: ['AITER', 'FLASHINFER_TRTLLM', ...]
  Using ['AITER_CUSTOM', 'PYNCCL'] all-reduce backends (in dispatch order)
  ```
- Greedy gates (arithmetic + coherence, temp 0) byte-identical at both TP sizes.
- Unit tests on gfx950: `test_fp8_aiter_falls_back_on_refined_blocks` 4/4; `test_rocm_aiter_custom_ar.py` 4/4. (One observation: `test_rocm_aiter_custom_ag_rs` flaked once across three runs on an identical tree — pass/fail/pass — a path this PR doesn't touch; possibly worth a look separately.)
- GSM8K 5-shot, 6 runs: TP2-on-fallback scores identically to our TP1 baseline (flexible 0.895 vs 0.895) — the Triton MoE fallback is quality-neutral.
- Throughput, since the PR doesn't quantify it (decode 7k/512 ×3, conc16 ×3):

| TP | MoE | decode tok/s | conc16 agg tok/s |
|---|---|---|---|
| 1 | AITER (native) | 114.2–114.5 | 509–514 |
| 2 | Triton (fallback) | 102.7–105.3 | 433–440 |
| 4 | Triton (fallback) | 97.9–98.1 | 486–489 |

  i.e. TP2/TP4 cost ~9-14% decode vs TP1 — but those configurations were previously impossible on this checkpoint, and the recipe already ships `VLLM_ROCM_USE_AITER_MOE=0` at TP4, which this PR makes automatic.

We also checked the "why not fix aiter instead" question: the 128×128 scale-group requirement is systemic across aiter's blockscale families (the CK/ASM `fmoe_bf16_blockscaleFp8` and the opus/FlyDSL a8w8 GEMMs alike hardcode `N//128, K//128`), and there's no alternative kernel family to route refined shapes to today — so the fallback looks like the right fix until the FlyDSL/Gluon MoE work lands.

Finally, this composes with the fp8 KV cache work in #61529: at TP2 with `--kv-cache-dtype fp8 --attention-config.indexer_kv_dtype fp8` and all AITER defaults, the combined stack serves with byte-identical greedy gates and a 9.85M-token KV cache.

We've also pushed a rebased version onto current main (the oracle area drifted since Oct 9), in case it saves a rebase round: `mrodden/vllm` branch `fix/aiter-fp8-fallbacks` @ `d06c5e2c66` — your two commits, authorship preserved, cherry-pick clean. Happy to hand it over however is easiest.
