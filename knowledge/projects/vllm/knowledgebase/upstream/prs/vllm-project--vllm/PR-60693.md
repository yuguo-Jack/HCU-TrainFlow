# [ROCm][KV Connector] Support sleep mode with MoRIIOConnector over RDMA

[Upstream PR](https://github.com/vllm-project/vllm/pull/60693) · state: open · merged: False

## Original PR description

## Overview

Supports sleep mode with `MoRIIOConnector` P/D disaggregation over RDMA on ROCm. Today `main` refuses this combination at startup (#59625) because peers keep a stale KV cache registration across sleep; this PR implements the `unregister_kv_caches()` / `restore_kv_caches()` hooks #59625 added for MoRIIO and makes the KV cache registrable under sleep mode.

Builds on the connector hooks merged in #59625 by @aoshen02 , Six commits: the change itself, a hardening of the peer invalidation after an independent review, a switch to MooncakeConnector's approach for reconnecting to a peer after it wakes, review cleanups, a WRITE deadline plus hardening of peer sleep, and a rework after review so that no memory is released while a transfer may still use it (see below, and *Design notes* under Details).

**Needs a MoRI fix to free memory: ROCm/mori#729, merged as ROCm/mori@19e9ea6055** (see Details). It is not in a MoRI release yet; vLLM's `MORI_BRANCH` (`v1.2.3.post1`) needs a bump once one is cut. Without it everything works but sleep frees nothing, as today.

## Claims

- PD with `MoRIIOConnector` (RDMA, WRITE mode) and `enable_sleep_mode` serves correct outputs across sleep/wake of P, D or both, level 1 and level 2, full and selective wake, and `release_kv_cache_memory`.
- With the MoRI fix, each sleep frees the KV cache (277.33 GiB freed, 5.07 GiB left per GPU in the test below). Before: the first request aborted the prefill EngineCore (registration failure → `std::abort()`).
- Sleep mode is accepted for MoRIIO with `backend: rdma` and still refused for `backend: xgmi`.

**Third commit: follow MooncakeConnector (2026-10-15).** Mooncake keeps its connection to a peer across sleep and only refreshes the peer's memory registration; its consumer also bounds each load with a deadline. This commit does the same for MoRIIO:

- An invalidation drops only the peer's region metadata and sessions, and keeps the remote agent and handshake state. The next transfer fetches the new metadata synchronously from the session lookup, instead of the lazy per-layer background handshake, which could race with in-flight requests (ready flags never cleared, a handshake started per layer, duplicate ready entries; these are also on `main`, but only matter once a peer re-handshakes).
- Unlike Mooncake, a transfer never uses the stale memory key and retries: a remote access error leaves MoRI's queue pair unusable, so invalidation before deregistration stays.
- WRITE-mode loads on the consumer are bounded by `recv_abort_timeout`, as Mooncake and MoRIIO READ mode already do: a transfer whose completion never arrives is reported as a failed load (handled per `kv_load_failure_policy`) instead of holding the request, and the drain before sleep, forever. The producer also sends `write_failed` when a write task fails, so the consumer does not wait for the timeout.

**Fourth commit: review comments (2026-10-18).** No behaviour change on ROCm:

- `get_mem_pool_context` drops the redundant `is_rocm()` check, since MoRI runs only on ROCm.
- The worker's sleep-mode state and the WRITE consumer's wait tracking are grouped into separate commented blocks.

A sleeping peer makes this engine drain its transfers to it even without local sleep mode, and the lock keeps a transfer that has already looked up its session from being posted after the drain. Only one thread takes it (the writer thread in WRITE mode, `start_load_kv` in READ mode), so it is uncontended outside a drain (~70 ns per acquire). A PD run without sleep mode, lock vs no lock (MI355X, Qwen3-0.6B TP1, 400 prompts, ISL 1024 / OSL 64, concurrency 32, 2 × 3 rounds each), showed no difference beyond run-to-run noise: 8,914 vs 9,123 output tok/s on average, with rounds of the same build varying by up to 13%.

**Fifth commit: WRITE deadline stops the producer first, harden peer sleep (2026-10-18).** *(Its time-based WRITE deadline is replaced by an acknowledged stop in the sixth commit.)* In the third commit, the consumer could fail a timed-out WRITE load and free its blocks while the producer still wrote into them. As in MooncakeConnector, the producer now gives up first:

- With sleep mode, the consumer sends its deadline (`recv_abort_timeout`) with the allocation. The producer re-checks it under `_transfer_post_lock` right before posting each write, and starts no write once it has passed.
- Before sending `write_failed`, the producer waits for the writes it already posted for that transfer to settle. It stays silent while one may still land.
- The consumer expires a load only at `recv_abort_timeout + max(60s, 2 × transfer_timeout)`.
- Without sleep mode, WRITE loads keep `main`'s behaviour.

It also hardens peer sleep:

- Handshakes are bounded, and no network wait happens under `_handshake_lock` or `_transfer_post_lock`.
- In READ mode, a sleeping or unavailable prefill fails only the affected loads, and TP ranks stay in step.
- Exportable allocations are scoped to the RDMA-registered KV cache and fail instead of silently falling back.
- With sleep mode, KV layouts whose regions cannot be released are refused at startup.

**Sixth commit: never release memory a transfer may still use (2026-10-19).** This addresses @aoshen02's review:

- **A drain that times out fails the sleep.** Transfers still pending after `transfer_timeout` stay tracked. A peer whose drain times out answers the invalidation with `INVALIDATE_NACK` instead of an ack. A negative ack, a missing answer, an unreachable peer, or this engine's own drain timing out all fail the sleep:
  - nothing is deregistered;
  - the engine serves its metadata again;
  - all TP ranks vote, so they fail together;
  - `sleep()` raises before suspending, so the engine stays awake and the sleep can be retried.
- **The WRITE deadline is an acknowledged stop, not a timer on each side.** With sleep mode, once a load is older than `recv_abort_timeout`, the consumer sends `stop_write` to each producer TP rank, and resends it every `recv_abort_timeout` until answered. The producer closes the transfer (nothing more is posted, including queued and deferred tasks), waits for its posted writes to settle, and only then answers with `write_failed`. The consumer frees the blocks only on `write_failed` or `write_done`, never on a timer, so the two hosts' clocks no longer matter.
- **A failed write keeps its source blocks until its posted writes settle.** The producer acknowledges the release and sends `write_failed` only then.
- **Per-peer invalidation generations** replace the bounded history of the last 64 invalidations. A handshake that overlaps an invalidation of its peer discards its result.
- **One registration helper** for initial registration and wake-up.
- **Shorter comments.** Every new comment is at most two lines; the reasoning moved to *Design notes* below.
- **Test changes:**
  - New unit tests cover a sleep refused by a peer, by this engine's pending transfers, or by another TP rank; the stop/resend exchange; and source blocks held while a write is pending.
  - The single-allocation cumem test is ROCm-only.

## Details

**Root causes** (each reproduced outside vLLM with MoRI-only and plain-verbs probes):

1. *KV cache cannot be registered.* On ROCm the cuMem allocator backs an allocation with 256 MB physical chunks. GPU memory can only be registered through dmabuf on these nodes (no peer-memory client, so `ibv_reg_mr` fails), and `hipMemGetHandleForAddressRange` exports only the first chunk's allocation (the dmabuf is 256 MB for an 8 GB range), so `ibv_reg_dmabuf_mr` fails with EINVAL. Fix: `CuMemAllocator.use_memory_pool(single_allocation=True)` backs each allocation with one physical allocation (a small switch in `cumem_allocator.cpp`); MoRIIO requests it for the KV cache through `get_mem_pool_context()` when sleep mode is on, on ROCm. A single 150 GB allocation sleeps and wakes normally.
2. *Stale registration.* The NIC registration pins the old physical pages, so sleep frees nothing; after wake a peer still using the old descriptor gets a remote access error, which moves its queue pair to the error state, and every later transfer to that engine is flushed, even with a new descriptor. So peers must drop the old descriptor before it is deregistered, not on failure. `unregister_kv_caches()` first stops serving region metadata (handshakes get `KV_UNAVAILABLE`) and building sessions, then sends `INVALIDATE <engine_id>` in parallel to every peer worker that fetched its metadata (peers include their handshake listener address in `GET_META`; tracked per listener, since all TP/DP workers of an engine share its engine ID). Each peer drops the metadata, waits for every transfer it has posted (the wrapper now tracks them; session lookup and posting share a lock so none is missed) and acknowledges. The sleeping engine then drains its own transfers and deregisters. `restore_kv_caches()` registers the same regions again and publishes the new metadata together with a session reset; peers handshake again on next use. A handshake that straddles an invalidation of that peer discards what it received.
3. *Export leak (MoRI).* `hipMemGetHandleForAddressRange` on cuMem (VMM) memory keeps a reference to the allocation after the fd is closed, so a registered region is never freed on sleep. Exporting the allocation handle with `hipMemExportToShareableHandle(POSIX_FD)` gives the same kind of dmabuf (the NIC accepts it) without the leak. That needs the allocation to be created with the POSIX fd handle type, which this PR sets for ROCm cuMem allocations, and a change to MoRI's `TryExportDmabufFd`: ROCm/mori#729. ROCm/mori#729 also handles the retained handle per runtime: `hipMemRetainAllocationHandle` adds a reference only from HIP 7.12 on (ROCm 7.2.x does not), so MoRI releases it only there; otherwise the allocation would stay held on newer ROCm. It also falls back to the existing export path when the registered range does not fit in one allocation.


### Design notes

These are the reasons behind the ordering and locking. In the code, each is a one- or two-line comment.

**Allocator**
- A dmabuf export covers one physical allocation. The KV cache is therefore requested as a single allocation instead of ROCm's cuMem chunks, so it can be registered as one region.
- Only single allocations (the RDMA-registered KV cache) are exportable, and the handle type is kept per allocation so that wake-up re-creates the memory the same way.
- The export goes through the allocation handle. An address-range export keeps the memory alive after release.
- There is no silent fallback to a plain allocation, which would leak the KV cache on every sleep. The single-allocation request comes first, since it may refuse before anything else changes.

**Sleep (`unregister_kv_caches`)**
1. Stop serving region metadata (handshakes get `KV_UNAVAILABLE`) and stop building sessions. From then on, the peers recorded so far are all that can still transfer to this engine.
2. Send `INVALIDATE` in parallel to every peer worker that fetched the metadata. Each TP/DP worker has its own handshake listener, and sending in parallel avoids a timeout per peer.
3. Each peer drops the metadata and sessions and drains its transfers to this engine. The metadata is matched by the engine ID it names, since a peer may have dialed another address, such as a proxy hostname. The peer answers with an ack, or a `NACK` if its drain timed out.
4. This engine drains its own transfers. TP ranks vote, and any `NACK`, missing answer or timeout fails the sleep on every rank before anything is deregistered.
5. Deregister every region, continuing past a failure so that the rest are still released.

**Wake (`restore_kv_caches`)**
- Registers the same regions in the same order through the shared helper. Regions shared between layers are registered once.
- A failed restore releases what it registered and stays unregistered, so a retry does not register twice.

**`_transfer_post_lock`**
- Held from session lookup until the transfers are posted, so a drain cannot miss a transfer that is about to be posted.
- It is needed without local sleep mode too: a sleeping peer makes this engine drain its transfers to it.
- Only one thread takes it (the writer thread in WRITE mode, `start_load_kv` in READ mode), and nothing under it waits on the network.

**Handshakes after a peer wakes**
- The next transfer refetches the peer's metadata outside `_handshake_lock` and `_transfer_post_lock`. The fetch is bounded by `transfer_timeout`, and a peer that timed out is not dialed again for `transfer_timeout`.
- Sessions are published only if the peer's metadata is still the object they were built from.
- A per-peer invalidation generation, recorded when a handshake starts, makes a handshake that overlaps an invalidation discard its result.
- Repeated handshakes that return the same regions keep the existing sessions (re-registered regions always differ).

**WRITE loads with sleep mode**
- The consumer must be able to drain before it sleeps, so a load whose completion never arrives is stopped through `stop_write`, as described above.
- A finished request whose load is still in flight stays mapped until the load completes or fails, so the scheduler can free its blocks.
- A completion wait gives up at the first failure or timeout while other writes may still land, so all of that transfer's statuses go to the failure path, which waits for them.

**READ loads**
- A prefill that is asleep or unavailable fails only the affected loads (per `kv_load_failure_policy`) and releases the producer's blocks.
- The set of eagerly handshaked peers only grows, so every TP rank makes the same decision about joining the eager handshake's all-reduce.
- For hybrid models, TP ranks vote on whether a failed read fails the step, so no rank raises alone while the others enter the forward's collectives.

**Layouts refused with sleep mode**
- MoRI tracks a local registration by its start address. A layout in which two registered regions start at the same address (for example a hybrid KDA conv state at the start of the shared registration) could not be fully released, so it is refused at startup.

**Limitations**
- Validated with WRITE mode only. MoRIIO READ mode cannot be validated on these nodes: RDMA READ into GPU memory over the ionic NICs completes successfully but delivers no data, independent of vLLM and MoRI (reproduced with plain ibverbs; AINIC firmware 1.117.1 is below MoRI's documented floor). The release/restore path itself runs in READ mode (memory freed, peers invalidated).
- Tested at TP1 and TP2 (DP1, equal TP on P and D), including sleep with `mode=wait` while requests are in flight. Not tested: DP > 1, hybrid (mamba) models, more than two engines.
- Invalidation matches remote state by the sender's engine ID (`host:handshake_port`). If a deployment addresses a peer by a different host string (e.g. multi-pod wide-EP, or a proxy hostname alias), the peer logs a warning and keeps the stale metadata.
- A transfer to a peer that is asleep cannot fetch its metadata, so that load fails per `kv_load_failure_policy`.
- Heterogeneous TP (from `main`) is covered by unit tests only, including its stop path. With hetero TP and DP > 1, decode DP ranks that do not own a failed request keep a small per-transfer count.
- If a producer never answers `stop_write` (for example, it died), the consumer keeps the load's blocks and keeps resending the stop. Its sleep cannot complete until then.
- A drain waits for every tracked transfer, not only those to the invalidating peer, so a transfer stuck to one peer refuses invalidations from every peer until it settles.
- The ionic NICs need the host's `libionic` in the image (the image's provider does not match the host driver; MoRI otherwise falls back silently to the management NIC). Unrelated to this change.
