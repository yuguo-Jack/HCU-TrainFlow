# [ROCm][KV Connector] Support sleep mode with MoRIIOConnector over RDMA

[Upstream PR](https://github.com/vllm-project/vllm/pull/60693) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Supports sleep mode with `MoRIIOConnector` P/D disaggregation over RDMA on ROCm. Today `main` refuses this combination at startup (#59625) because peers keep a stale KV cache registration across sleep; this PR implements the `unregister_kv_caches()` / `restore_kv_caches()` hooks #59625 added for MoRIIO and makes the KV cache registrable under sleep mode.

Builds on the connector hooks merged in #59625. Five commits: the change itself, a hardening of the peer invalidation after an independent review, a switch to MooncakeConnector's approach for reconnecting to a peer after it wakes, review cleanups, and a WRITE deadline under which the producer stops writing before the consumer frees blocks, plus hardening of peer sleep (see below).

**Needs a MoRI fix to free memory: ROCm/mori#729, merged as ROCm/mori@19e9ea6055** (see Details). It is not in a MoRI release yet; vLLM's `MORI_BRANCH` (`v1.2.3.post1`) needs a bump once one is cut. Without it everything works but sleep frees nothing, as today.

## Claims

- PD with `MoRIIOConnector` (RDMA, WRITE mode) and `enable_sleep_mode` serves correct outputs across sleep/wake of P, D or both, level 1 and level 2, full and selective wake, and `release_kv_cache_memory`.
- With the MoRI fix, each sleep frees the KV cache (277.33 GiB freed, 5.07 GiB left per GPU in the test below). Before: the first request aborted the prefill EngineCore (registration failure → `std::abort()`).
- Sleep mode is accepted for MoRIIO with `backend: rdma` and still refused for `backend: xgmi`.

**Third commit: follow MooncakeConnector (2026-10-15).** Mooncake keeps its connection to a peer across sleep and only refreshes the peer's memory registration; its consumer also bounds each load with a deadline. This commit does the same for MoRIIO:

- An invalidation drops only the peer's region metadata and sessions, and keeps the remote agent and handshake state. The next transfer fetches the new metadata synchronously from the session lookup, instead of the lazy per-layer background handshake, which could race with in-flight requests (ready flags never cleared, a handshake started per layer, duplicate ready entries; these are also on `main`, but only matter once a peer re-handshakes).
- Unlike Mooncake, a transfer never uses the stale memory key and retries: a remote access error leaves MoRI's queue pair unusable, so invalidation before deregistration stays.
- WRITE-mode loads on the consumer are bounded by `recv_abort_timeout`, as Mooncake and MoRIIO READ mode already do: a transfer whose completion never arrives is reported as a failed load (handled per `kv_load_failure_policy`) instead of holding the request, and the drain before sleep, forever. The producer also sends `write_failed` when a write task fails, so the consumer does not wait for the timeout.

**Fourth commit: review comments (2026-10-18).** No behaviour change on ROCm:

- `get_mem_pool_context` drops the redundant `is_rocm()` check, since MoRI runs only on ROCm.
- The worker's sleep-mode state and the WRITE consumer's wait tracking are grouped into separate commented blocks.
- A comment at `_transfer_post_lock` explains why it is unconditional. A sleeping peer makes this engine drain its transfers to it even without local sleep mode, and the lock keeps a transfer that has already looked up its session from being posted after the drain. Only one thread takes it (the writer thread in WRITE mode, `start_load_kv` in READ mode), so it is uncontended outside a drain (~70 ns per acquire). A PD run without sleep mode, lock vs no lock (MI355X, Qwen3-0.6B TP1, 400 prompts, ISL 1024 / OSL 64, concurrency 32, 2 × 3 rounds each), showed no difference beyond run-to-run noise: 8,914 vs 9,123 output tok/s on average, with rounds of the same build varying by up to 13%.

**Fifth commit: WRITE deadline stops the producer first, harden peer sleep (2026-10-18).** In the third commit, the consumer could fail a timed-out WRITE load and free its blocks while the producer still wrote into them. As in MooncakeConnector, the producer now gives up first:

- With sleep mode, the consumer sends its deadline (`recv_abort_timeout`) with the allocation. The producer re-checks it under `_transfer_post_lock` right before posting each write, and starts no write once it has passed.
- Before sending `write_failed`, the producer waits for the writes it already posted for that transfer to settle. It stays silent while one may still land.
- The consumer expires a load only at `recv_abort_timeout + max(60s, 2 × transfer_timeout)`.
- Without sleep mode, WRITE loads keep `main`'s behaviour.

It also hardens peer sleep:

- Handshakes are bounded, and no network wait happens under `_handshake_lock` or `_transfer_post_lock`.
- In READ mode, a sleeping or unavailable prefill fails only the affected loads, and TP ranks stay in step.
- Exportable allocations are scoped to the RDMA-registered KV cache and fail instead of silently falling back.
- With sleep mode, KV layouts whose regions cannot be released are refused at startup.

## Details

**Root causes** (each reproduced outside vLLM with MoRI-only and plain-verbs probes):

1. *KV cache cannot be registered.* On ROCm the cuMem allocator backs an allocation with 256 MB physical chunks. GPU memory can only be registered through dmabuf on these nodes (no peer-memory client, so `ibv_reg_mr` fails), and `hipMemGetHandleForAddressRange` exports only the first chunk's allocation (the dmabuf is 256 MB for an 8 GB range), so `ibv_reg_dmabuf_mr` fails with EINVAL. Fix: `CuMemAllocator.use_memory_pool(single_allocation=True)` backs each allocation with one physical allocation (a small switch in `cumem_allocator.cpp`); MoRIIO requests it for the KV cache through `get_mem_pool_context()` when sleep mode is on, on ROCm. A single 150 GB allocation sleeps and wakes normally.
2. *Stale registration.* The NIC registration pins the old physical pages, so sleep frees nothing; after wake a peer still using the old descriptor gets a remote access error, which moves its queue pair to the error state, and every later transfer to that engine is flushed, even with a new descriptor. So peers must drop the old descriptor before it is deregistered, not on failure. `unregister_kv_caches()` first stops serving region metadata (handshakes get `KV_UNAVAILABLE`) and building sessions, then sends `INVALIDATE <engine_id>` in parallel to every peer worker that fetched its metadata (peers include their handshake listener address in `GET_META`; tracked per listener, since all TP/DP workers of an engine share its engine ID). Each peer drops the metadata, waits for every transfer it has posted (the wrapper now tracks them; session lookup and posting share a lock so none is missed) and acknowledges. The sleeping engine then drains its own transfers and deregisters. `restore_kv_caches()` registers the same regions again and publishes the new metadata together with a session reset; peers handshake again on next use. A handshake that straddles an invalidation of that peer discards what it received.
3. *Export leak (MoRI).* `hipMemGetHandleForAddressRange` on cuMem (VMM) memory keeps a reference to the allocation after the fd is closed, so a registered region is never freed on sleep. Exporting the allocation handle with `hipMemExportToShareableHandle(POSIX_FD)` gives the same kind of dmabuf (the NIC accepts it) without the leak. That needs the allocation to be created with the POSIX fd handle type, which this PR sets for ROCm cuMem allocations, and a change to MoRI's `TryExportDmabufFd`: ROCm/mori#729. ROCm/mori#729 also handles the retained handle per runtime: `hipMemRetainAllocationHandle` adds a reference only from HIP 7.12 on (ROCm 7.2.x does not), so MoRI releases it only there; otherwise the allocation would stay held on newer ROCm. It also falls back to the existing export path when the registered range does not fit in one allocation.

**Limitations**
- Validated with WRITE mode only. MoRIIO READ mode cannot be validated on these nodes: RDMA READ into GPU memory over the ionic NICs completes successfully but delivers no data, independent of vLLM and MoRI (reproduced with plain ibverbs; AINIC firmware 1.117.1 is below MoRI's documented floor). The release/restore path itself runs in READ mode (memory freed, peers invalidated).
- Tested at TP1 and TP2 (DP1), including sleep with `mode=wait` while requests are in flight. Not tested: DP > 1, hybrid (mamba) models, more than two engines.
- Invalidation matches remote state by the sender's engine ID (`host:handshake_port`). If a deployment addresses a peer by a different host string (e.g. multi-pod wide-EP, or a proxy hostname alias), the peer logs a warning and keeps the stale metadata.
- A transfer to a peer that is asleep cannot fetch its metadata and fails (in READ mode it fails the decode step, as any failed handshake does today).
- The ionic NICs need the host's `libionic` in the image (the image's provider does not match the host driver; MoRI otherwise falls back silently to the management NIC). Unrelated to this change.

[Correctness / simplification] Replace the bounded invalidation history with generations

The last-64-events history can forget the invalidation a slow handshake must observe. Evaluating the actual _dropped_since predicate: a handshake at epoch 0 sees peer A's invalidation at event 1, but stops seeing it after 64 unrelated invalidations evict that entry. If the handshake then publishes its old response, stale MR metadata can be cached again. This is a low-frequency overlapping-handshake scenario, not a hardware-reproduced failure. A global generation comparison would be simpler and conservatively retry any handshake crossing an invalidation; per-peer last-invalidated generations can avoid unrelated retries. Either avoids truncating events that an in-flight handshake still needs.
