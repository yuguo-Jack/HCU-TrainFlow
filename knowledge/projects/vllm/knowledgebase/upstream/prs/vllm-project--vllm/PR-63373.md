# [Core] Remove Model Runner V1

[Upstream PR](https://github.com/vllm-project/vllm/pull/63373) · state: open · merged: False

## Original PR description



## Overview

**Draft / preview.** This PR removes Model Runner V1 (MRV1). MRV2 is already the default. MRV1 was only reached through an explicit `VLLM_USE_V2_MODEL_RUNNER=0` or by falling back for features MRV2 lacks. This PR deletes MRV1 together with the code that existed only for it. Features that only worked on MRV1 are dropped rather than ported. Dual Batch Overlap is kept and now runs on MRV2 by default.

A second commit cleans up the tests and deprecates `parallel_drafting`: nothing reads it anymore, since DFlash and DSpark always draft in parallel and no other method supports it. Setting it now logs a deprecation warning, and setting it to `True` for any other method still raises.

## Claims

- **Runner deleted:** `gpu_model_runner.py` (7.2K lines), `gpu_input_batch.py`, `gpu_ubatch_wrapper.py`, `cpu_model_runner.py`, the KV/EC connector runner mixins, and the V1 `BlockTable`.
- **V1-only code deleted:**
  - The V1 spec-decode proposers (`vllm/v1/spec_decode/{eagle,dflash,draft_model,ngram*,suffix_decoding,custom_class_proposer,...}.py`) and their Triton kernels.
  - The V1 sampler and rejection sampler.
  - The V1 custom logits-processor API (`vllm/v1/sample/logits_processor/`). `vllm.v1.worker.gpu.sample.logits_processor` is now the only interface.
  - `cpu_triton_utils` and the CPU kernel overrides.
- **`VLLM_USE_V2_MODEL_RUNNER` and `VllmConfig.use_v2_model_runner` removed.** Every V1/V2 branch in config, worker, scheduler, warmups, models and connectors now takes the V2 path. The scheduler no longer emits `prev_step_scheduled_req_ids`, `all_token_ids` or resumed requests for V1.
- **Dropped features.** These now raise, or the option is gone:
  - the `custom_class` speculative method
  - `use_heterogeneous_vocab` (TLI)
  - `disable_padded_drafter_batch`
  - `parallel_drafting` outside `dflash`/`dspark` (P-EAGLE, PARD)
  - pipeline parallelism with `external_launcher`
  - pooling tasks outside the MRV2 set
  - `NGramPerReqLogitsProcessor` (DeepSeek-OCR)
  - **vLLM on x86 CPU without Triton** (triton-cpu). Non-x86 CPUs (Arm, POWER, s390x) without Triton keep working on MRV2's standalone CPU model runner (`vllm/v1/worker/cpu/standalone_model_runner.py`).
- **Suffix decoding** now always uses the MRV2 GPU suffix speculator (#60339), so the Arctic Inference-based V1 proposer is removed. `suffix_decoding_max_spec_factor` and `suffix_decoding_min_token_prob` are kept but deprecated and have no effect.
- **Triton ReplaySSM** is kept: it is supported on MRV2 since #65033.
- **DBO:** the env gate that pushed `--enable-dbo` onto MRV1 is removed. Combinations DBO still doesn't support raise an error.
- **Docs, examples and requirements:** the PARD docs, the V1 logits-processor design doc, and the V1 logits-processor examples are removed, and the suffix decoding docs now describe only the GPU speculator. `arctic-inference` is dropped from the test requirements.

## Validation

- From the first version of the PR, before the rebases: an import smoke test of the touched core modules (config, workers, scheduler, engine, elastic EP, warmups, models) passed. End-to-end with `Qwen/Qwen3-0.6B` on 1x GB200, with and without `ngram` spec decode, gave identical, sensible greedy outputs.
- On the current branch (rebased onto main after #60339 and #65033): pre-commit passes over the whole diff, including ruff, mypy and the test-tethering check (the `pip-compile*` hooks were skipped locally).
- Tests: tests that only exercised removed V1 code are deleted, and V1/V2 parametrizations now keep only the V2 path. Coverage that would otherwise be lost is ported to MRV2:
  - the M-RoPE prompt-embeds regression test (`tests/v1/worker/test_mrope_prompt_embeds.py`)
  - the deferred SimpleCPUOffload store test
  - the eager fast-prefill-off case of `test_kv_sharing_fast_prefill`
  - the Triton ReplaySSM e2e tests, which run on MRV2 again
- Not run yet: the test suite (including the new and changed tests), model evals, and CI on the current branch.

## Details

Open questions for reviewers:

1. **x86 CPU without Triton.** Non-x86 CPUs without Triton are covered by the standalone CPU model runner, but x86 now requires triton-cpu. Is that acceptable?
2. **Dropped speculative-decoding features** (custom proposer class, TLI, P-EAGLE/PARD). Do we land this before any of them are ported to MRV2, or wait?
3. **Deprecation.** Should `VLLM_USE_V2_MODEL_RUNNER=0` give a targeted error for a release? Today it is just an unknown env var.

Follow-ups not included here:

- Removing `CachedRequestData.resumed_req_ids` / `all_token_ids`, which are now always empty, and the connector branches that read them.
- Further pruning of shared modules (`vllm/v1/spec_decode/utils.py`, `mamba_utils.py`, `kda_metadata._mamba_get_block_table_tensor`).
- Dropping "V2" naming (`GPUModelRunner` lives under `vllm/v1/worker/gpu/`).

Thanks for the preview. A question from an out-of-tree platform before this lands.

[vllm-openvino](https://github.com/belonghim/vllm-openvino) ships its own worker and model runner (OpenVINO executes the model). It cannot use Triton, which is incompatible with OpenVINO, so it runs on MRV1. Of what it imports from `vllm.v1`, this PR removes `InputBatch`/`CachedRequestState`, the V1 `Sampler`/`SamplingMetadata`, `NgramProposer` and `apply_grammar_bitmask` (`WorkerBase`, `bind_kv_cache`, `outputs` and the scheduler/KV-cache types stay). Their MRV2 counterparts (`worker/gpu/input_batch.py`, `block_table.py`, `sample/gumbel.py`, `sample/penalties.py`, ...) are Triton kernels, so we cannot move to MRV2 either.

#61995 lets CPU backends without Triton override MRV2 components with PyTorch implementations, but this PR drops "vLLM on CPU without Triton".

1. Are non-Triton implementations of the MRV2 input batch and sampler still planned (via #61995 or a similar override)? Or is Triton a hard requirement for `vllm.v1.worker.gpu`?
2. If it is, should out-of-tree platforms keep their own copies of the input batch and sampler, and will there be a stable interface for them?

Context: #57684 (same question, still open), #58703 (parked until this removal plan).

Follow-up on my question above: vllm-openvino no longer needs anything this PR removes. It now ships trimmed copies of what it used from MRV1 (`InputBatch`/`CachedRequestState`, the V1 `Sampler`/`SamplingMetadata` with the builtin min_p/logit_bias/min_tokens processors, `NgramProposer`, and the grammar-bitmask apply), checked bit-identical against 0.32. So from our side there is no need to keep a non-Triton MRV1 path. A release-note mention when those interfaces change would help out-of-tree runners.
