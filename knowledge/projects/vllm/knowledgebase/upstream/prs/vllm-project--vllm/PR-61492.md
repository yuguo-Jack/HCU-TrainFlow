# [Bugfix][Metrics] Periodic stats line: dead Preemptions field + Finished count

[Upstream PR](https://github.com/vllm-project/vllm/pull/61492) · state: open · merged: False

## Original PR description

## Overview

The periodic serving-stats line (`Engine 000: Avg prompt throughput: ...`) structurally could not show preemption churn: the interval counters it reports were **reset before the line was built**, so the `Preemptions: N` field introduced in #28522 has never fired — a storm interval with 100 preemptions and high generation throughput logs no Preemptions field at all (reproduced on current `main`, evidence below). This change fixes the reset ordering and adds an unconditional `Finished: N reqs` field, because the thrashing signature is precisely **high generation throughput with zero finished requests** — motion without progress.

Measured motivation (saturated PP deployment, real data): 798 preemptions, 2 completions, healthy tok/s throughout — the line reported the throughput and hid the churn entirely.

**Not a duplicate:** searched — no existing PR touches the stats-line reset ordering or adds a finished-request count to it. #28522 introduced the (dead) Preemptions field. The Prometheus counters (`vllm:num_preemptions_total`, request success counters) are unaffected and already correct — the gap is the log line operators actually read.

## Claims

- Bug fix: `Preemptions: N` in the periodic line was dead since introduction (#28522) — `_update_stats()` reset `num_preemptions` before `log()` read it. After this change the field appears whenever the interval had preemptions.
- New: unconditional `Finished: N reqs` in the same line. `Finished: 0` while generation throughput is high is the preemption-churn signature; the zero is the signal, so the field is not conditional.
- `Corrupted: N reqs` (env-gated) had the same dead-field bug; fixed identically.

## Validation

Hermetic unit tests (`tests/v1/metrics/test_loggers_finished_reqs.py`, first tests for this logger — no GPU):

```bash
pytest tests/v1/metrics/test_loggers_finished_reqs.py -q   # 5 passed
```

- `test_preemptions_survive_the_interval_reset` **fails on vanilla `main`** (dead field) and passes with the change.
- Storm interval (100 preemptions, 50k generated tokens, 0 finished):
  - before: `... Avg generation throughput: 52608543.7 tokens/s, Running: 0 reqs, Waiting: 0 reqs, GPU KV cache usage: 0.0%` — no Preemptions, no Finished.
  - after: `... Finished: 0 reqs, Preemptions: 100, ...` — churn visible.
- Interval reset semantics: a second quiet interval reports `Finished: 0 reqs`, not the previous interval's count.

## Details

**Root cause:** `LoggingStatLogger.log()` calls `_update_stats()` first, which computes throughputs (captured to `last_*` fields) and then calls `_reset()` — clearing `num_preemptions` and `num_corrupted_reqs`. The line is built *after* the reset, so both conditional fields read zero. The throughputs survive because they are captured before the reset; the counters are not. #28522 added `num_preemptions` to `_reset()` in the same commit that introduced the field, so it has never been visible.

**Fix:** snapshot the interval counters into `last_preemptions` / `last_corrupted_reqs` / `last_finished_reqs` before the reset (mirroring the existing throughput pattern), report those, and track `num_finished_reqs` from `IterationStats.finished_requests` (the data was already carried per iteration; only the logging was missing).

**Tradeoffs and limitations:**
- `Finished: N reqs` is unconditional — an always-present field where the previous convention was conditional-on-nonzero. The zero is the diagnostic (thrashing), so conditionality would reintroduce the bug class; log parsers that split on fixed field names may notice the new field.
- The Prometheus side is unchanged: preemption and success counters already exist and are correct; this PR is scoped to the human-readable line.
- Aggregate (multi-DP) loggers extend the same base and read the same fields; this change touches the shared base path only.
