# [Perf][DSpark] Compute windowed draft context for trailing rows only

[Upstream PR](https://github.com/vllm-project/vllm/pull/60320) · state: open · merged: False

## Original PR description

## Purpose

A DFlash/DSpark drafter whose KV groups are all sliding-window only ever reads each request's last `window` context positions, but `DFlashSpeculator.propose` runs `combine_hidden_states` (DSpark's `main_proj`) and the per-layer context K/V precompute over every target row. On a 16K-token DeepSeek-V4.1 prefill step that is ~2.6 ms of GPU work, almost all of it for rows the drafter never reads. This PR projects and stores only each request's trailing rows.

- **Gate.** Trimming is on when every draft KV group is sliding-window with a window larger than `num_speculative_steps`, the dropped rows cannot be served later (prefix caching off, or no draft group is prefix-cacheable, as with DSv4.1's SWA bounded replay), no KV connector is configured, and the drafter has no context anchor (LiLiCorr reads `hidden_states` by target row). Other drafters are unchanged.
- **Threshold.** Only steps that drop at least 2048 context rows trim, since the row gathers cost a few fixed launches; decode steps only pay one integer compare.
- **Rows.** Each request keeps its last `window + num_query_per_req` rows (the query block can shift the window when clamped at `max_model_len`), counted back from the device `query_start_loc`, which adaptive verification may shorten for decodes. Aux hidden states are gathered before `combine_hidden_states`, and context positions and slots are compacted after `prepare_dflash_inputs`.

Not a duplicate: no open PR reduces the rows of the context precompute. #57627 (stacked context KV projection) and #55654 (V4 KV-only insert) make each row cheaper and are complementary; #43594 batches the KV writes; #59511 moves the combine into the draft CUDA graph and would gather the staged rows the same way.

## E2E prefill (DEP4)

DeepSeek-V4.1-Flash, DEP4 on one GB200 node at 385d86a6cf, DSpark with 5 speculative tokens (synthetic acceptance), `max_num_batched_tokens=16384`, model and decoder replay CUDA graphs captured up to 16384, prefix caching off, `--gpu-memory-utilization 0.62`, `max_tokens=1`. Server instances differ by up to 15% at c1, so both sides ran in one server, toggled at runtime by a local-only switch: 12 alternating rounds each, median TTFT in ms.

A profile of one 16K step shows the draft context path drop from 2.57 ms to about 0.2 ms of GPU time, about 0.75% of the step, which bounds the TTFT gain. Each 95% bootstrap interval includes zero, so this is a small, consistent gain rather than a large one. Steps below the threshold (e.g. a single 1K prompt) take the unchanged path.
