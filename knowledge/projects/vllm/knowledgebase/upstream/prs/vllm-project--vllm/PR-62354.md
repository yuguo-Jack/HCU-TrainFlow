# [Bugfix][Model] Route Gemma 4 per-layer embeddings through the CPU weight offloader

[Upstream PR](https://github.com/vllm-project/vllm/pull/62354) · state: open · merged: False

## Original PR description

## Overview

Gemma 4 E2B/E4B build their per-layer embedding (PLE) table (`embed_tokens_per_layer`, 4.4 GiB / 5.25 GiB in bf16) outside `make_layers`, so it never reaches the weight offloader. As a result `--cpu-offload-params embed_tokens_per_layer` is silently a no-op, and plain `--cpu-offload-gb` can only offload decoder layers (slow). This PR routes the table through the UVA offloader.

## Claims

- `--cpu-offload-gb <N> --cpu-offload-params embed_tokens_per_layer` now offloads the PLE table. GPU weight memory: E2B 9.73 → 5.36 GiB, E4B 15.05 → 9.80 GiB, E4B QAT w4a16 11.02 → 5.77 GiB.
- No measurable latency cost with the table offloaded (each token gathers only its own rows over UVA): E2B 0.792 → 0.794 s, E4B QAT 0.802 → 0.801 s, E4B 1.452 → 1.451 s (512 in / 128 out, batch 1).
- Outputs are unchanged: logprobs match HF and the no-offload run for E2B and E4B.
- Side effect on plain `--cpu-offload-gb N`: the table is wrapped before the decoder layers, so it is now offloaded first. With `--cpu-offload-gb 6`: E2B 40.6 → 8.44 s, E4B QAT 11.97 → 0.799 s.
- Models without a PLE table (`hidden_size_per_layer_input == 0`, e.g. 12B, 26B-A4B) and runs without offloading are unaffected.

## Details

**Root cause.** The offloader only sees modules passed to `wrap_modules`, which for Gemma 4 happens via `make_layers` for decoder layers. The PLE table is a `VocabParallelEmbedding` built directly in `Gemma4Model.__init__`, so name filters never match it and byte budgets never reach it.

**Change.** Right after building the table, pass it through `get_offloader().wrap_modules(...)`, the same mechanism the vision/audio tower offload uses (`interfaces.py`). The table is a gather (one row per token), so reading it over UVA is cheap, unlike dense decoder weights.

**Guard.** Only done when `offloader.supports_tower_offload` is true (UVA). `PrefetchOffloader` allows a single `wrap_modules` call per model and would assert; prefetching the whole table every step would also be wasteful. With the prefetch backend the table stays on GPU as before. I reused `supports_tower_offload` since it already means "accepts extra `wrap_modules` calls"; happy to rename it if a more general name is preferred.

**Usage.** Recommended: `--cpu-offload-gb 5 --cpu-offload-params embed_tokens_per_layer` (E2B) / `--cpu-offload-gb 6 --cpu-offload-params embed_tokens_per_layer` (E4B). The budget is checked per parameter before offloading, so the table (a single parameter) is offloaded whole even with a smaller budget; passing at least the table size keeps the number meaningful.

**Limitations.**
- Non-UVA fallback (`VLLM_WEIGHT_OFFLOADING_DISABLE_UVA=1`, or no pinned memory, e.g. WSL) copies the whole table to the GPU on every forward. Correct but slow; same behavior as any module offloaded in that mode.
- No prefetch-backend support for the table (see Guard).
- Gemma 3n has the same per-layer table and the same problem; left for a follow-up.
