# [Bugfix] Drop stray messages on the DP startup handshake socket instead of failing startup

[Upstream PR](https://github.com/vllm-project/vllm/pull/60758) · state: open · merged: False

## Original PR description



## Overview

In multi-node DP, any message on `--data-parallel-rpc-port` that no engine sent
(a port scanner, a metrics scraper) fails startup. This PR drops such messages
with one warning and keeps waiting for the engines. Fixes #38677 (closed as
stale without a fix).

## Claims

- A message that does not parse as an engine's HELLO or READY no longer fails
  `wait_for_engine_startup`: wrong frame count, an identity no engine has, or a
  body that is not an engine's handshake msgpack map (including bodies that make
  untyped decoding raise `UnicodeDecodeError`, `TypeError` or `RecursionError`).
- A well-formed engine message is held to exactly the checks it met before. An
  unexpected rank, a local/remote or `--headless` mismatch, a message out of
  turn, or an engine, coordinator or watched front-end process exiting still
  fails startup.
- Nothing changes after startup: the handshake socket is only read until every
  engine is READY, so model output is unaffected.

## Validation

New tests in `tests/v1/engine/test_startup_watch_processes.py` run the real
`wait_for_engine_startup` on a ROUTER bound to loopback TCP, with
`EngineCoreProc.startup_handshake` on the engine side:

- `test_wait_for_engine_startup_drops_messages_no_engine_sent`: before and
  between the engines' HELLO and READY, DEALER, REQ and ROUTER peers send junk
  (msgpack int, str and map, invalid UTF-8, an unhashable map key, an HTTP
  request line, an empty frame, arrays and maps nested 20,000 deep, a two-frame
  message, an unowned engine-sized identity), a raw TCP client sends the scrape
  from #38677, and one engine sends junk under its own identity before its
  HELLO. Startup must complete.
- `test_wait_for_engine_startup_still_fails_on_an_unexpected_rank`: after the
  same stray traffic, a well-formed HELLO from rank 5 still fails startup.

```bash
.venv/bin/python -m pytest tests/v1/engine/test_startup_watch_processes.py -v \
  -W error::pytest.PytestUnhandledThreadExceptionWarning
```


Without the change both new tests fail on the first stray message the front-end
reads, e.g. `RuntimeError: Message from engine with unexpected data parallel
rank: 453525693440` (a DEALER's auto-generated identity read as a rank).

We also replayed 18 kinds of stray traffic, one kind per run, at the real
`wait_for_engine_startup` on a loopback TCP ROUTER (the payloads above plus raw
TCP). On `main`, 17 of the 18 end startup; with this change, none do. Applied to
an older main commit, #38731 still fails on 2 of them and #47389 on 5.

In a multi-node DP deployment with hybrid load balancing, with a process beside
each leader sending stray traffic at its own handshake port every 10 s for as
long as the port was open, each handshake logged the warning once and completed
(about 400 stray messages each over five and a half minutes), and the deployment
then passed our functional and long-context checks.

CI: the existing `V1 Engine` Buildkite step (`pytest -v -s v1/engine`) runs
this file.

## Details

**Root cause.** In multi-node DP the rank 0 front-end binds a ROUTER socket to
`--data-parallel-rpc-port` on `--data-parallel-address`, a routable address,
and `wait_for_engine_startup` reads it until every engine is READY. Anything
that connects can send to it, and `main` raises on whatever is not an engine's
handshake:

- an identity no engine has raises
  `RuntimeError: Message from engine with unexpected data parallel rank: <n>`;
- a message with other than two frames (a REQ socket's, for one) raises
  `ValueError: too many values to unpack (expected 2)`;
- a body that is not an engine's handshake raises from
  `msgspec.msgpack.decode`, or from `msg["status"]`
  (`TypeError: 'int' object is not subscriptable`) when its identity happens to
  match an engine's.

#38677 reports the first case from a Prometheus scraper: with no ZMTP greeting,
libzmq takes the sender for an unversioned (ZMTP/1.0) peer and the request's
first bytes for its identity, which becomes the huge "rank" in the error. We see
the same class of traffic as the security scanner in #44486: a periodic probe
that connects to every ZMQ port in our pods. On our deployment the
socket is open for about five and a half minutes per start, and one stray
message in that window costs a full restart.

**Fix.** `_decode_engine_handshake` accepts only an engine's shape: two frames,
the second a msgpack map with a `str` `status` and `bool` `local` and
`headless`. Anything else is dropped with `logger.warning_once` and the loop
keeps waiting; the poll path that detects exited processes is untouched.
Untyped decoding of arbitrary bytes can raise `msgspec.DecodeError`,
`UnicodeDecodeError`, `TypeError` (an unhashable map key, msgspec < 0.22;
0.22 raises `DecodeError`) and, for input nested deeper than about 10,000
arrays or maps, `RecursionError`, which is a `RuntimeError` and easy to miss.
All of them mean "not an engine".

**Tradeoff.** A well-formed HELLO from a rank this front-end does not own still
raises instead of being dropped. `wait_for_engine_startup` has no timeout for
remote engines, so dropping a real engine's message would turn a configuration
error into an indefinite wait.

**Why this is not a duplicate.**

- #38677 was closed as stale on 2026-07-31 without a fix; `main` still raises in
  all three cases above.
- #38731 (closed by its author, not merged) skips messages with the wrong frame
  count or an unknown identity. It still fails on a body that does not decode
  under an engine's identity, and it also skips a real engine with an
  unexpected rank, which then waits forever.
- #47389 (closed, not merged) skips identities that are not two bytes long. It
  still fails on the wrong frame count, on an unknown two-byte identity and on
  a body that does not decode.
- #44627 (the DP Coordinator and the client output socket) and #54757 (the NIXL
  handshake listener), both open, harden other sockets against the same traffic.
  Neither touches this socket.
- #50039 (open) adds a deadline to the same `wait_for_engine_startup` loop. It
  does not drop stray messages; the two changes are independent and compose.
