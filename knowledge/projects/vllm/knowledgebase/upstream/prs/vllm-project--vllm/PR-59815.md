# [Quantization] Support compressed-tensors MXFP4 MoE with FP8 activations via Mxfp4MoEMethod

[Upstream PR](https://github.com/vllm-project/vllm/pull/59815) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

Load compressed-tensors checkpoints with MXFP4 weights and dynamic FP8 activations (e.g. `RedHatAI/Qwen3.6-35B-A3B-MXFP4-DSFP8`, `RedHatAI/GLM-5.2-MXFP4xFP8_BLOCK`, `RedHatAI/GLM-5.3-MXFP4xFP8_BLOCK`, DeepSeek-V4-Flash converted to CT) and run them with the FP8 activations the checkpoint declares. Alternative to #59376 (cc @kylesayrs).

**Depends on #61556.** Humming 0.1.16, which `main` pins today, rejects FP8 (GS128) activations with MXFP4 weights, so these checkpoints fail to load with `--moe-backend humming` until #61556 lands.

## Claims

- MoE experts: `CompressedTensorsW4A8Mxfp4MoEMethod(Mxfp4MoEMethod)` only handles the `*_weight_packed` checkpoint naming and the declared activation scheme. Backend selection, weight conversion, size round-up, monolithic kernels and EPLB are inherited from the native MXFP4 method.
- The checkpoint's FP8 activation key reaches the Humming MoE backend. Before, it was dropped and Humming ran BF16 activations (W4A16) unless `VLLM_HUMMING_INPUT_QUANT_CONFIG` was set.
- Dense linears with MXFP4 weights and FP8 inputs (GLM-5.3's dense MLPs target `Linear`) use a new `CompressedTensorsW4A8Mxfp4` scheme that requests FP8 activations, instead of the W4A4 scheme requesting MXFP4 activations.
- `get_moe_method` looks up the expert scheme with the layer's `ckpt_*_proj_name`, and DeepSeek-V4 (NVIDIA) passes `ckpt_names=("w1", "w2", "w3")`, so name-based targets such as `re:.*experts\.\d+\.w\d+$` match.

## Validation

H200 (SM90), `--moe-backend humming`, checked by inspecting the loaded layers.

| Model | Config | Dense MXFP4 linear | MoE experts |
|---|---|---|---|
| Qwen3.6-35B-A3B-MXFP4-DSFP8 (real weights) | TP1 | n/a (FP8 block) | Humming, FP8 GS128 (W4A16 before this PR's 2nd commit) |
| GLM-5.3-MXFP4xFP8_BLOCK (dummy weights, 5 layers) | TP1, TP2, TP2+EP | Humming, FP8 GS128 (FP8 per-token before) | Humming, FP8 GS128 (BF16 before) |

These runs used the v0.32.0 release branch with #61556, and `main` with #61556 applied. With `main` alone, the Humming 0.1.16 schema check rejects the combination. EP selects `HummingGroupedExperts` and TP selects `HummingIndexedExperts`. Greedy outputs match between TP2 and TP2+EP.

GSM8K, Qwen3.6-35B-A3B on 1x H200 (`tests/evals/gsm8k/gsm8k_eval.py --use-chat-completions --chat-template-kwargs '{"enable_thinking": false}' --temperature 0 --max-tokens 1024`, 1319 questions, 5-shot):

| Checkpoint / activations | Accuracy |
|---|---|
| `Qwen/Qwen3.6-35B-A3B` BF16 | 0.956 |
| MXFP4-DSFP8, MoE W4A16 (previous behavior) | 0.958 |
| MXFP4-DSFP8, MoE W4A8 (this PR) | 0.961 |

Tests:

The original commit was also validated on B300 (SM103): a layer harness loading a real `RoutedExperts` with random MXFP4 weights was bitwise equal to native `Mxfp4Config` across the default, monolithic TRTLLM, unaligned-shape, `triton_unfused`, `marlin`, `deep_gemm`, `flashinfer_cutlass` and `flashinfer_trtllm` backends. Converted DeepSeek-V4-Flash-0731 generated the same token ids and logprobs as the original checkpoint on 8 prompts.

## Details

**Root cause of the BF16 fallback.** For `Mxfp4MoeBackend.HUMMING`, the MoE conversion built Humming's input schema only from `VLLM_HUMMING_INPUT_QUANT_CONFIG` (`TODO: read input_quant_config from quant_config`), so an unset env meant BF16. With schema fallback enabled, Humming also demotes group-scaled FP8 to A16 (`prefer wna16 for groupwise weight or groupwise input`). Output still looked correct, so the slower path went unnoticed. `Mxfp4MoEMethod` now takes an optional `activation_key`. The HUMMING conversion uses it with fallback disabled, unless the env override is set. Other backends ignore the key.

**Performance.** At the GLM-5.x expert GEMM shapes (N/K 4096/6144 and 6144/2048, 32 experts, top-8; `benchmarks/bench_humming.py` at the #61556 Humming pin), W4A8 is 1.4-1.8x faster than W4A16 for M >= 256. End to end, the small Qwen3.6-35B-A3B on 1x H200 is 3-8% slower with W4A8 than with W4A16 across prefill- and decode-heavy runs (hidden 2048, expert intermediate 512, so the per-layer activation quantization is not amortized). This PR follows the checkpoint's declared scheme. `VLLM_HUMMING_INPUT_QUANT_CONFIG` still overrides it.

**Limitations**
- ROCm, XPU and CPU have no MXFP4 linear kernel for FP8 activations, so MXFP4 x FP8 dense layers keep the previous MXFP4-activation path there, with a warning. MI300 CI hit this; the linear test is CUDA-only.
- Blackwell: dense linears now use Humming FP8, which is slower than FlashInfer W4A4 on SM100 but matches the checkpoint. The MoE still picks its Blackwell backend without the activation key, so it uses MXFP8 or BF16 activations instead of `DEEPGEMM_MXFP4` (FP8 GS128 x MXFP4). Hooking that up is left for a follow-up issue.
- The AMD, XPU, CPU and V4.1 DeepSeek model variants still need the same `ckpt_names` one-liner; untested here.
- The rename breaks the pre-processed weight cache, so `supports_pre_processed_weights` is off for this method.
- Converting DeepSeek-V4-Flash with vllm-project/compressed-tensors#902 also emits `shared_experts.w\d+` targets, while vLLM names that layer `shared_experts.down_proj`; that needs a fix in the converter or model.

**Not a duplicate:** #59376 targets the same scheme with a different design; only one should merge. #58714 adds a separate CT -> `HummingMoEMethod` route for the same checkpoints; this PR covers that path through the native MXFP4 method. #56523 and #56306 migrate the W4A4 method to the oracle and do not touch this scheme.
