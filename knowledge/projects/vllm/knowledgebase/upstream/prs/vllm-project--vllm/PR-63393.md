# [Attention] Batch the DeepseekV4 per-group SWA decode index builds into one launch

[Upstream PR](https://github.com/vllm-project/vllm/pull/63393) · state: closed · merged: False

## Original PR description

# Warning: Untested AI-generated code.

Stacked on #63296 — the staged build wraps that PR's kernel contract
(`is_valid_token` as a kernel output, the `num_valid_tokens` grid
boundary), so the head branch carries its commit; only the last commit

## Motivation

DeepseekV4 decode builds SWA attention metadata eagerly, once per
attention group, on every step, outside any captured CUDA graph. Each
group's causal decode path launches its own Triton index kernel over the
**same token rows**; the launches differ only in the buffers they write
(per-group `decode_swa_indices`, `decode_swa_lens`, `is_valid_token`,
`slot_mapping`, `block_table`, `replay_start`). At G=8 that is eight
kernel-launch wrapper invocations per step, and the Python cost of those
invocations — Triton signature binding and introspection per launch —
dominates the ~1.6 ms the eight SWA builds spend in Python on a
profiled H200 c16 decode step.

## What changed

- `DeepseekSparseSWAIndexBatch` (new, in `sparse_swa.py`): the
  DeepseekV41ModelState brackets the step's attention-metadata build
  with `begin()` / `flush()`; each armed
  `DeepseekSparseSWAMetadataBuilder` **stages** its causal decode
  build's buffers instead of launching.
- The flush uploads an int64 `[groups, 8]` table of buffer addresses
  and strides (`async_tensor_h2d`, a fresh table per step) and launches
  **one** pointer-indirected kernel, `_compute_swa_indices_and_lens_batched_kernel`,
  with grid `(tokens, groups)` — the address-table idiom already used
  by `_zero_kv_blocks_kernel` in `v1/worker/utils.py`.
- A batch with a single group takes the direct per-group path: at
  G=1 the batched launch fuses nothing and the table upload is pure
  overhead, so it pays for a launch either way. Capture (graph
  recording) keeps the per-group path as before.
- The batched kernel reads its parameter table through
  `_load_ptr` (`v1/worker/gpu/buffer_utils.py`), keeping the
  `tl.multiple_of` 16-byte vectorization hint the hand-rolled loads
  dropped, and bounds its invalid-path index row-clear at
  `num_valid_tokens` exactly like the per-group kernel in #63296.
- The batched kernel body is the `HAS_IMAGE=False` case of the
  per-group kernel, so staged and per-group outputs are bit-identical.
- JIT warmup registers the batched kernel alongside the existing ones
  (`deepseek_v41/attention.py`), keyed on window/index-width/block
  size.

## Why this matters

`t_meta = Σ_{g=1..G} ( t_launch_python(g) + t_kernel(g) )`

becomes one wrapper invocation plus one `[G, 8]`-int64 host-to-device
upload:

`t_meta' = t_launch_python + t_h2d + t_kernel`

At G=8 on the profiled step this removes seven of the eight
launch-side Python costs (signature binding, introspection — ~82
`inspect` calls per launch) while adding one ~64-byte pinned upload
that the CUDA caching allocator recycles only after the copy retires
(no extra stream sync).

## Safety notes

- Fail-closed staging: groups whose shared arguments (query layout,
  seq lens, the threaded token-to-request buffer, window, block size,
  token counts) diverge refuse to stage, naming the offending field.
  Shared-argument comparison is buffer-level (dtype, shape, stride,
  address), matching how the metadata build threads these tensors
  across groups.
- A builder outside an open batch keeps launching its own kernel, so
  every existing caller that is not bracketed (other model states,
  direct `build()` calls) is unchanged.
- While a CUDA graph is recording, the flush launches the per-group
  kernel for each staged group instead: a graph replay would not
  refresh the per-step parameter table, so captured builds must record
  their own launches. Captured and eager builds produce identical
  buffer contents.
- Non-CUDA devices never open a batch (`DeepseekV41ModelState` gates on
  `device.type == "cuda"`).
- The batched kernel's parameter table carries absolute addresses of
  persistent per-group buffers; these are re-read from the staged
  tensors on every step, so nothing assumes a buffer address survives
  across steps.

## Testing

- `tests/v1/attention/test_deepseek_v4_swa_visible.py`: three builders
  staged through one batch produce bit-identical `decode_swa_indices` /
  `decode_swa_lens` / `is_valid_token` (and prefill outputs) versus
  per-group builds, including a padded token and mixed decode/prefill
  batches; divergent shared arguments refuse to stage and the flush
  still launches; an armed builder outside an open batch launches
  directly.
- Needs a GPU run of that suite plus a dsv4.1 decode smoke (the JIT
  warmup exercises the new kernel at startup); draft until that is
  done.
