# [Bugfix][Tool Parser] Keep Step3 parameter values that contain '<'

[Upstream PR](https://github.com/vllm-project/vllm/pull/60968) · state: closed · merged: True

## Original PR description



## Overview

The Step3 tool parser silently drops any parameter whose value contains `<`. This PR makes the parameter regex match up to the closing tag instead of the first `<`.

## Claims

- Step3 tool calls keep parameter values that contain `<`, such as `a < 5` or `<b>hi</b>`, in streaming and non-streaming mode.
- Values without `<` parse exactly as before.

## Validation

New unit test `test_parameter_value_with_angle_bracket`, run in both streaming and non-streaming mode:

```bash
python -m pytest -q tests/tool_parsers/test_step3_tool_parser.py
```

| | Result |
|---|---|
| Before (test only) | `2 failed, 9 passed, 8 xfailed`: `assert {} == {'sql': 'SELECT * FROM t WHERE a < 5', 'html': '<b>hi</b>'}` |
| After | `11 passed, 8 xfailed` |

The 8 xfails already exist on main and are unchanged.

End-to-end check with a Step3 model (`tool_choice="auto"`, a tool with a string parameter, prompt asking for a SQL query with `<`):

Parser check with the real Step3 tokenizer (`stepfun-ai/step3`). A tool call whose `sql` value contains `<` goes through `run_tool_extraction`, the helper the tool parser tests use, in both modes:

| Mode | `main` (`arguments`) | This PR (`arguments`) |
|---|---|---|
| non-streaming | `{}` | `{"sql": "SELECT * FROM orders WHERE total < 100"}` |
| streaming | `{}` | `{"sql": "SELECT * FROM orders WHERE total < 100"}` |

On `main` the call is still emitted, but its arguments come back empty, so a client runs the tool with no input.

Not run end to end: Step3 has 321B parameters and I have no hardware that can serve it. The change is confined to the parameter regex, which the check above drives with the model's real tokenizer.

<summary>Reproduction script</summary>

    import json
    from vllm.tokenizers import get_tokenizer
    from vllm.tool_parsers import ToolParserManager
    from tests.tool_parsers.utils import run_tool_extraction

    tok = get_tokenizer("stepfun-ai/step3")
    out = ("<｜tool_calls_begin｜><｜tool_call_begin｜>function<｜tool_sep｜>"
           '<steptml:invoke name="run_query">'
           '<steptml:parameter name="sql">SELECT * FROM orders WHERE total < 100</steptml:parameter>'
           "</steptml:invoke><｜tool_call_end｜><｜tool_calls_end｜>")
    for streaming in (False, True):
        parser = ToolParserManager.get_tool_parser("step3")(tok)
        _, calls = run_tool_extraction(parser, out, streaming=streaming)
        print(streaming, [json.loads(c.function.arguments or "{}") for c in calls])

</details>

## Details

Root cause: `_parse_steptml_invoke` matched values with `([^<]*)`, so the regex failed on any value containing `<` and the parameter was skipped without a log line. The value group is now `(.*?)` with `re.DOTALL`. It ends at the first `</steptml:parameter>`, and multi-line values still match as before.

Limit: a value that contains the literal text `</steptml:parameter>` still ends early. The format has no escaping, so this cannot be fixed in the parser.

Not a duplicate: I searched open and closed PRs for "step3 tool parser" and issues and PRs for "steptml". #49567 (whitespace in Step3 values) only removes `.strip()` and keeps `[^<]*`. #55115 and #57809 change streaming bookkeeping, not the regex. #55175 changes test fixtures only. No issue reports this bug.
