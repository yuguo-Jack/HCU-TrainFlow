# [Model][LoRA] LoRA support for MiniMax M3

[Upstream PR](https://github.com/vllm-project/vllm/pull/63323) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

LoRA support for MiniMax M3 (`MiniMaxM3SparseForCausalLM` and `MiniMaxM3SparseForConditionalGeneration`). Adapters on attention (q/k/v/o and the indexer's index_q/index_k), the dense MLP, shared experts and routed experts are served without changing the base kernels. Follows the pattern of the Step5 LoRA support (#62498): model-specific LoRA layers live in `vllm/lora/layers/custom_layer.py`.

## Claims

- Both entry points implement `SupportsLoRA`; the VL wrapper targets its `language_model` (`get_mm_mapping`). LoRA is marked supported in `docs/models/supported_models.md`.
- Sparse attention layers fuse q, k, v, index_q and index_k into one `MinimaxM3QKVParallelLinearWithIndexer`, so for LoRA `qkv_proj` packs five modules. This five-entry mapping is set on the model instance, which is what the LoRA manager reads; the class-level `packed_modules_mapping`, which quantization configs use for exclusion lists, keeps q/k/v as on main, so a quantized checkpoint that excludes q/k/v of a dense attention layer (no indexer) still loads. `MiniMaxM3QKVIndexerWithLoRA` gives it five LoRA slices that shard like the base weight: q, k, v as in `MergedQKVParallelLinearWithLoRA`, index_q like k/v (one indexer head per KV head, including KV-head replication), index_k replicated on every rank.
- Dense attention layers (layers 0-2 in the default config) keep a plain 3-way `QKVParallelLinear` under the same five-entry LoRA packing; `MiniMaxM3DenseQKVWithLoRA` applies q/k/v there and drops the two always-empty indexer entries.
- Weight reload under LoRA: wrapped parameters live under `base_layer`, while a checkpoint-format reload (`reload_weights` calls `load_weights`) sends unwrapped names. On main these weights are skipped silently, including routed experts (`fused_moe_make_expert_params_mapping` adds `base_layer.` to the checkpoint side too, so no checkpoint name matches). `load_weights` now resolves wrapped parameters by their unwrapped names.
- `fully_sharded_loras` is rejected at startup; without the check the fused qkv projection would silently stay unwrapped.
- Routed-expert LoRA uses the existing MoE LoRA path (e.g. BF16/FP8 experts, Marlin). NVFP4 experts on the FlashInfer TRTLLM backend additionally need #63024.

After the second commit, the end-to-end check below was rerun with #59941 applied: both architectures still wrap layer 0 with `MiniMaxM3DenseQKVWithLoRA` and layers 1-3 with `MiniMaxM3QKVIndexerWithLoRA`, and outputs with and without the adapter are unchanged from the first commit.

End-to-end, single GB300, CUDA graphs on: a 4-layer MiniMax M3 config (layer 0 dense attention + dense MLP, layers 1-3 sparse attention + MoE with 16 experts, BF16), dummy weights re-initialized to N(0, 0.02), rank-8 adapters on q/k/v/o/index_q/index_k and the dense/shared-expert MLPs, `MiniMaxM3SparseForConditionalGeneration`:

- layer 0 `qkv_proj` is `MiniMaxM3DenseQKVWithLoRA`, layers 1-3 are `MiniMaxM3QKVIndexerWithLoRA`;
- an adapter with B = 0 gives greedy output identical to no adapter (2 prompts x 24 tokens);
- a random adapter changes the first generated token for both prompts; prompt logprobs move by up to 3.56;
- in a batch of [no adapter, random adapter], prompt logprobs of each row equal the single-adapter runs exactly (max abs diff 0.0), so the delta does not leak into the no-LoRA row.

Not verified:

- Real checkpoints, TP > 1, and routed-expert adapters were not served end to end; routed-expert LoRA goes through the unchanged `FusedMoEWithLoRA` path.

NaN seen during validation, root-caused (not from this PR): the image above predates #59941. There, `eager_break_during_capture` is resolved at import time, but `VLLM_USE_BREAKABLE_CUDAGRAPH=1` is auto-enabled later during config setup, so whether MiniMax M3's sparse attention gets its eager break depends on import order. In that image the same tiny model (dummy weights, no LoRA, default `FULL_AND_PIECEWISE` with breakable CUDA graphs) gives different greedy output for two identical requests with either architecture. In some runs every logit is NaN, e.g. `MiniMaxM3SparseForConditionalGeneration` with LoRA disabled. Which architecture and which LoRA setting hits NaN changed between runs. `FULL_DECODE_ONLY` and `enforce_eager=True` were deterministic. With the one-file fix from #59941 (already on main) applied to the image:

- both architectures, with LoRA disabled and enabled (plus `PIECEWISE` for the text architecture with LoRA), give finite logprobs and the same greedy tokens across repeated requests;
- with the same MoE backend (`moe_backend="triton"`, which LoRA selects), prompt logprobs of LoRA-disabled, LoRA-enabled (no adapter), text and VL architectures are bitwise equal (max abs diff 0.0);
- an adapter changes the output, and the output with the adapter is identical across repeats and between the two architectures.

## Details

- Quantization configs receive the class-level `packed_modules_mapping` by reference before the model is built, while the LoRA manager reads the mapping from the model instance. Keeping the five-entry packing on the instance only leaves quantization exclusion checks exactly as on main: every attention `qkv_proj` is checked against q/k/v, which are the only projections of a dense layer; a sparse layer's index_q/index_k are not part of the check, as on main.
