# [HiSparse] Write mixed decode/prefill attention outputs in place

[Upstream PR](https://github.com/vllm-project/vllm/pull/60707) · state: closed · merged: False

## Original PR description

## Purpose

Part of #60420. With HiSparse, a mixed batch runs its decode rows and prefill rows as two sparse-MLA kernels and joins them with `torch.cat`. That's a second output-sized allocation, about 1 GiB at 16K batched tokens, which memory profiling never sees. It's where the original #60420 repro ran out of memory.

FlashInfer, FlashAttn and FlashInfer SM120 now preallocate one output and pass each kernel its slice with `out=`. Decode-only batches are unchanged and keep the kernel's own output, which is the CUDA-graph path. FlashMLA BF16 isn't covered: writing into its output needs the padded-head workspace, which is a separate change.

## Test Result

1×B200, GLM-5.3-NVFP4 cut to 4 layers with dummy weights, fp8 KV (FlashInfer), 1.04M-token prompt with 2 requests decoding:
- Greedy token ids and logprobs are bit-identical to main, including spilled prompts up to 524K with decodes running.
- With #60424 and #60706, per-step peak over profile drops from +1.50 GiB to +0.50 GiB, both with the prompt spilled to host (util 0.90) and with all KV on GPU (util 0.97). On main the 0.97 case runs out of memory in this `torch.cat`.
- `pytest tests/v1/attention/test_sparse_mla_backends.py tests/v1/kv_connector/unit/test_hisparse_connector.py` on B200: 412 passed. `-k "hisparse or HiSparse or flashattn"` on H100: 65 passed.
- New test `test_flashinfer_hisparse_mixed_batch_writes_one_output` fails on main and passes here. The decode-only stub test now asserts that no `out` is passed.
- FlashInfer SM120: not validated (no SM120 GPU available).

Once #60424 lands, this needs a rebase: the staging branches loop over prefill groups, and the new test must mock `staged_prefills` instead of `stage_prefill_rows`.
