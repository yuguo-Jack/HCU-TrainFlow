# [Attention] FlashInfer: add VLLM_FLASHINFER_MULTI_WAVE_KV_SPLIT for trtllm-gen decode

[Upstream PR](https://github.com/vllm-project/vllm/pull/61077) · state: open · merged: False

## Original PR description



## Overview

This PR adds `VLLM_FLASHINFER_MULTI_WAVE_KV_SPLIT` (default off). When it is on and the final decode kernel is trtllm-gen, vLLM sets `FLASHINFER_TRTLLM_GEN_MULTI_WAVE_KV_SPLIT=1` for FlashInfer. It depends on flashinfer-ai/flashinfer#6331. With an older FlashInfer, the flag has no effect.

## Claims

- An explicit opt-in for the FlashInfer multi-wave KV split in trtllm-gen decode. The default behavior does not change.
- The setting reaches Ray workers. A FlashInfer value that the user sets on the driver (for example `0`) wins on every worker.
- XQA, DCP and native FlashInfer decode are not affected.

## Validation

- Unit tests on B200, with this branch and the FlashInfer branch installed from source:
  - `.venv/bin/python -m pytest tests/v1/attention/test_flashinfer_multi_wave_kv_split.py tests/test_ray_env.py -v` → 26 passed.
- `pre-commit run --files` on the 5 changed files: all hooks pass.
- Kernel results: see flashinfer-ai/flashinfer#6331.
- Serving setup: Llama-3.1-8B-Instruct on 1 × B200, `--attention-backend FLASHINFER --kv-cache-dtype fp8 --max-model-len 65536`.
  - The worker log shows `decode_backend=trtllm-gen`.
  - With the flag on, only the engine core process has `FLASHINFER_TRTLLM_GEN_MULTI_WAVE_KV_SPLIT=1`.
  - With the flag off, no process has it.
- `vllm bench serve`: random dataset, output 512, concurrency 18, 72 prompts, 2 runs per setting. Values are the mean of 2 runs, flag off → flag on.

| Input length | Output tok/s | Mean TPOT (ms) | P99 TPOT (ms) | Mean TTFT (ms) |
|---|---|---|---|---|
| 32768 | 657.5 → 654.4 (-0.5%) | 19.61 → 20.28 | 26.13 → 26.26 | 3981 → 3710 |
| 3277-62259 (random) | 592.4 → 617.9 (+4.3%) | 27.25 → 26.85 | 85.44 → 76.09 | 2338 → 1784 |
| 4096 | 2909.9 → 2777.4 (-4.6%) | 5.07 → 5.38 | 6.04 → 6.36 | 572 → 566 |

- With mixed input lengths, the flag raises output throughput by 4.3% and lowers P99 TPOT by 11%.
- With 4096-token inputs, the flag lowers output throughput by 4.6%.
- With 32768-token inputs, the change is smaller than the run-to-run spread of 6%.
- gsm8k, 5-shot, 1319 questions, `lm_eval` `local-completions`, concurrency 32:
  - flexible-extract: 0.761 with the flag off, 0.774 with the flag on.
  - strict-match: 0.677 with the flag off, 0.704 with the flag on.
  - The flag does not lower accuracy.
- Short inputs, with prefix caching off and 3 paired runs per cell (95% interval):
  - At concurrency 18, the flag lowers output throughput by 3.3% at 8192 tokens to 7.2% at 512 tokens, and by 1.5% with random 512-8192.
  - At concurrency 64 and 128, the change is between -0.1% and +0.3%. Every interval contains 0.

## Details

- **Why opt-in:** in FlashInfer, the rule helps long and mixed-length KV, but it is slower at short, uniform KV (up to 0.56× on B200 at 8k). `max_model_len` does not tell the real request lengths, so vLLM does not turn it on automatically.
- **Where:** the FlashInfer metadata builder applies the flag after the XQA and DCP fallbacks, so only the final trtllm-gen kernel turns it on. `os.environ.setdefault` keeps a value that the user set.
- **Order:** FlashInfer reads its env once, at the first call to the trtllm-gen FMHA runner. That call can be a prefill call. The metadata builder runs before warmup and CUDA graph capture.
- **Scope:** the FlashInfer setting applies to the whole engine process, for every layer that uses trtllm-gen decode.
- **Ray:** `FLASHINFER_TRTLLM_GEN_MULTI_WAVE_KV_SPLIT` is added to `DEFAULT_EXTRA_ENV_VARS`. The `VLLM_` flag already reaches the workers.
- **Not a duplicate:** a search of open vLLM PRs for "flashinfer kv split" found no PR for this setting.
