# [Frontend] Add Responses API input token counting

[Upstream PR](https://github.com/vllm-project/vllm/pull/64050) · state: open · merged: False

## Original PR description



## Overview

Add `POST /v1/responses/input_tokens` to count a Responses request's input tokens without generating an answer. The endpoint previously returned HTTP 405.

Closes #49533.

## Claims

- Count the rendered prompt, including instructions, tool definitions, and stored history.
- Match generation's context-length validation and auto truncation.
- Honor prompt-related vLLM extensions and exclude unrelated generation fields.
- Return HTTP 400 for unsupported `conversation` and `personality` parameters.

## Validation

```bash
.venv/bin/python -m pytest tests/entrypoints/openai/responses/test_stateful.py -k count_input_tokens -v
# 16 passed, 7 deselected

.venv/bin/python -m pytest tests/entrypoints/openai/responses/test_protocol.py -q
# 12 passed
```

The HTTP suite includes 10 exact comparisons against generation's `usage.input_tokens`, including auto truncation and stored history. It also checks rejection at the exact context limit. The endpoint regression failed with HTTP 405 on the base commit. All applicable pre-commit hooks passed, including the commit hooks.

Local validation used Qwen3.5-9B GGUF on an RTX 4060 with a 2048-token context. The temporary fixture override is excluded from this PR. The standard Qwen3-1.7B/18192 configuration, multimodal inputs, and Harmony models were not tested locally. The existing Responses API CI step selects these tests.

## Details

Reuse the existing Responses renderer, input-item parsing, and stored-response lookup. The count handler validates the rendered input and returns its length without submitting generation or storing a response. Rendered documentation includes the endpoint and a curl example.

Request and response fields were checked against the official OpenAI SDK types. Issue comments and open PR searches for `49533` and `responses/input_tokens` found no competing implementation.

AI assistance was used for implementation and validation.

- BlueRaddish · COMMENTED · 2026-11-02T09:07:07Z · [source](https://github.com/vllm-project/vllm/pull/64050#pullrequestreview-5734193953)

`previous_input_messages` is silently lost by the new count request, so the Harmony count path receives different history from generation for the same payload.

For example, with the protocol classes at this head:

```python
payload = {
    "input": "What city?",
    "previous_input_messages": [
        {"role": "user", "content": "Remember that my favorite city is Seoul."},
        {"role": "assistant", "content": "I will remember Seoul."},
    ],
}
generation = ResponsesRequest.model_validate(copy.deepcopy(payload))
count = ResponsesInputTokensRequest.model_validate(copy.deepcopy(payload))
assert len(generation.previous_input_messages) == 2
assert "previous_input_messages" in count.model_extra
assert count.to_responses_request().previous_input_messages is None
```

`OpenAIBaseModel` accepts the extra field, but `to_responses_request()` includes only declared fields in its dump. `OnlineRenderer._render_responses_with_harmony()` normally consumes this field through `construct_harmony_previous_input_messages`; the converted count request cannot do so. Supplying this field together with `previous_response_id` also loses generation's explicit mutual-exclusion error because the field is already gone before `_validate_create_responses_input()` runs.

Please either forward this supported prompt-history extension, or explicitly reject it on the count endpoint instead of accepting and dropping it. Add coverage for the stateless Harmony-history path alongside stored `previous_response_id` history.

Offline verification used the exact selected protocol/converter/validator bodies at `ed37b9b812ac679014e7e0323690230f40fb4fa0` with real Pydantic 2.14.1/OpenAI SDK 3.36.1: both chat-format and Harmony-format history dictionaries lose their two messages; three no-history/instructions/previous-id controls pass. This was an isolated source harness, with unrelated type/cache helpers as fixtures and the compatible `openai-harmony` Message class rather than the repository's `oss-harmony` distribution. **No full vLLM import, HTTP server, numerical token count, tokenizer/model/GPU, or whole-suite validation is claimed.** AI assistance was used.
