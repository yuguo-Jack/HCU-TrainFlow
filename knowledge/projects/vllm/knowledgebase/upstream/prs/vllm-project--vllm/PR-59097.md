# [Metrics] Export the prefill token backlog as vllm:num_queued_tokens

[Upstream PR](https://github.com/vllm-project/vllm/pull/59097) · state: open · merged: False

## Original PR description

## Purpose

`--max-num-queued-tokens` (added in #49445) rejects new requests once the prompt tokens of requests still in prefill reach a limit. The API server already keeps that count for the admission check, but the count is not exported, so operators cannot chart the prefill backlog, alert on it, or see how close a server is to the limit.

The PR exports the count as a gauge:

- `vllm:num_queued_tokens{model_name}` is the prompt tokens of requests that have not produced their first output yet, as counted by the API server. It is the same number `--max-num-queued-tokens` checks, so it uses the full prompt length, with no prefix-cache hits or chunked-prefill progress subtracted.
- The gauge is reported whether or not `--max-num-queued-tokens` is set, and it starts at 0.
- Each API server process counts only the requests it handles, across all the engines it routes to. So the gauge has no `engine` label, and it uses `multiprocess_mode="livesum"` to add up the live API server processes, the same way `vllm:websocket_connections_active` handles a per-process value.
- The gauge is set on every batch the API server receives from the engine, including batches with no request outputs, so it drops after an abort without waiting for another request to produce output.

The PR also changes `OutputProcessor.get_num_queued_tokens()` from a sum over every in-flight request to a running total. An earlier proposal for a tokens-in-queue metric, #12286 for the V0 engine, was asked in review not to walk the request list on every engine step. With a running total, reading the count on each batch is one attribute read, and the admission check, which already read the count on every request, gets cheaper as well. The total is updated wherever a request enters or leaves prefill: when it is added, at its first output, when a streaming-input update extends its prompt, and when it is aborted or finished.

#55812 adds `vllm:admission_rejections_total` for the same admission limits and changes some of the same files, so whichever of the two merges second will need a small rebase.

## Test Plan

```bash
VLLM_TARGET_DEVICE=cpu python -m pytest tests/v1/engine/test_admission_control.py
```

- `test_queued_tokens_gauge_tracks_prefill_backlog` reads the gauge from the Prometheus registry. It adds requests with 100 and 50 prompt tokens and expects 150, then expects 50 after the first output of the 100-token request, and 0 after the other request is aborted.
- `test_queued_tokens_follow_streaming_input` checks that a streaming-input chunk is not counted while the previous chunk is running. It then checks that the chunk restarts prefill with the whole extended prompt once the engine finishes the previous chunk, and that an abort clears the count.
- The existing `get_num_queued_tokens` tests now build a real `OutputProcessor` through `add_request` and `process_outputs` instead of assigning `request_states` directly, because the running total is kept by those paths.
- `vllm:num_queued_tokens` is added to `EXPECTED_METRICS_V1` in `tests/entrypoints/serve/instrumentator/test_metrics.py`. That test needs a GPU and was not run locally.

## Test Result

```
52 passed, 15 warnings in 21.33s
```

The run was on macOS with CPU torch and `--noconftest`, because the root conftest needs test packages that were not installed, and the tests in this file do not use its fixtures.

Each update to the running total was also removed in turn to check that a test fails. Removing the update at add, first output, streaming update or abort fails a test. Removing the subtraction in `_finish_request` does not, because every current caller finishes a request after its first output has already taken it out of prefill. The subtraction is kept so that every removal from `request_states` keeps the total equal to the sum it replaces.

@MadhavJivrajani @robertgshaw2-redhat A scheduler-side version could also remove the overestimate instead of copying it.

The scheduler already tracks processed prefill as `num_computed_tokens - num_in_flight_tokens`, the same basis `remove_skipped_blocks` uses, and the prefix hit is folded into `num_computed_tokens` at first schedule. A backlog computed in `make_stats` from that counts only outstanding work for scheduled requests. I drove the v1 `Scheduler` on CPU at 2bea22002. A warm 180K prompt with 9K uncached tokens counts 2,736 after its first chunk instead of 180,000. A cold 180K prompt counts 85,920 after 15 of its 29 chunks. Waiting requests still count their full length, because the hit is only computed at first schedule. A state label (scheduled or waiting) would keep the two apart. It would also make the token-budget starvation suspected in #53130 visible.

This diverges from what `--max-num-queued-tokens` checks today, which matters for the load-balancer use case. The way to close that gap is the follow-up #49445 deferred, where admission reads the same engine-side value. I'd like to take that part.

Madhav, are you planning the refactor here? If not, I can build it on top of your branch with credit to you, or wait for yours and follow with the admission change.
