# [Fast Start] Add weights mirror support for daemon2daemon

[Upstream PR](https://github.com/vllm-project/vllm/pull/64641) · state: open · merged: False

## Original PR description

## Overview

Add daemon-to-daemon weight seeding to the preload stack: a second replica's daemons fill their shards from an already-loaded replica instead of reading the checkpoint again. Builds on the D2D transport from #63088 and adopts the storage-manifest + mover data plane proposed in #60086, reworked so a mirror is an ordinary daemon using a new internal `peer_cache` load format rather than a special tensor-bag daemon.

## Claims

- One new flag: `vllm preload --weight-cache-seed <source>`. Same-host copies go over CUDA IPC (`peer_ipc`), cross-host pulls go over Mooncake RDMA (`rdma`); the backend and the mirror's GPU placement are inferred, no other flags needed.
- A mirror is a normal daemon: it builds its model (meta device), finalizes its config, adopts the FlashInfer autotune table through the ordinary warmup-cache seeding, and serves engines identically — so chained seeding (a mirror seeding another replica, e.g. for failure recovery) needs no special code.
- Fingerprints (`WeightCacheKey`) are compared before any bytes move; a mismatched source/rank pairing is refused, not silently mirrored.
- 502 GiB of DSv4.1-Flash weights move between two nodes in ~9.3s (~54 GiB/s aggregate over 4 RoCE NICs).
- The remote control plane is JSON-only and authenticates before decoding (no pickle from untrusted peers); node-local movers are never served remotely.

## Validation

Startup performance on GB200 (SM100) nodes, `batch` partition; reproduction: `.slurm-logs/d2d_dsv41.sh` / `d2d_qwen30b.sh` / `d2d_xhost2.sh`.

| Startup path | Model / config | Time to READY | Transfer |
|---|---|---|---|
| Cold preload (disk) | Qwen3-30B-A3B, tp=4 | 230s | — |
| **D2D seed** | Qwen3-30B-A3B, tp=4 | **100s** (2.3x faster) | 18.75 GiB/rank in 2.19s (~34 GiB/s aggregate, rdma) |
| Cold preload (first ever) | DeepSeek-V4.1-Flash, tp=4 | 1152s (651s with warm kernel caches) | — |
| **D2D seed** | DeepSeek-V4.1-Flash, tp=4 | transfer done at +9.3s* | 125.53 GiB/rank (~13.5 GiB/s/rank, ~54 GiB/s aggregate, rdma) |
| Cold preload | tiny kimi-k3, tp=1 | 58s | — |
| **D2D seed (same host)** | tiny kimi-k3, tp=1 | 60s | 0.12 GiB in 0.25s (peer_ipc) |

\* DSv4.1's mirror cannot reach READY yet: `DeepGemmMxfp8BmmLinearKernel` does not declare pre-processed-weight support (`modelopt.py`), the same gap the ModelOpt weight-cache series (#63754, #63976, #63672) addresses. The DSv4.1 numbers validate the data plane; Qwen3-30B validates the full loop.

Warm engine restarts against a daemon (`--load-format ipc_cache`) are unchanged by this PR and not separately instrumented here; the E2E tests assert correctness of the whole path instead (see below).

Tests: `tests/model_executor/model_loader/test_weight_cache.py`

- New E2E, run on GB200 (Slurm jobs 40933/40975): `test_d2d_weight_seeding_same_host` and `test_d2d_weight_seeding_cross_host` — a mirror daemon seeds over peer_ipc / rdma with `fallback=False` and serves outputs byte-identical to the disk baseline. Cross-host needs `WITH_NVIDIA_PEERMEM=0` (dmabuf) on hosts without a working nvidia-peermem module.
- Full file + `pre-commit run` (incl. mypy): green. The two GPU failures in the file (`kimi-k3` autotune-table assertion, `tp2_ep` nvcc ICE) reproduce identically on upstream/main.
- Correctness of served weights: Qwen3-30B-A3B served from the source replica and from the mirror replica produce byte-identical greedy outputs (2 nodes, tp=4).

## Details

Design, and how it differs from #60086:

- **Mirror lifecycle**: #60086's mirror holds a bare `MirrorState` (no model, no world group, no warmup, autotune table carried in the seed payload). Here the mirror is a normal daemon whose `load_format` is `peer_cache`: `PeerModelLoader` pulls the post-processed tensors and installs them through `build_model_from_processed_weights`, the same meta-device install pipeline engines use for `ipc_cache`. Config finalization, warmup, and serving need zero mirror-specific code, and future warmup-cache kinds work on mirrors without changes. The price: a mirror forms its own world group and needs the model's config files locally (not its safetensors).
- **Control plane**: one kind-keyed `SeedTransport` serves both `weights` and `flashinfer_autotune`. Same-host peers are served over the daemon's owner-verified Unix socket (pickle, which CUDA IPC handles require); remote peers over the token-authenticated TCP JSON listener. The peer loader fetches through the daemon's own D2D endpoint (injected at load), so there is exactly one configured channel per daemon.
- **Data plane** (as in #60086): storages move, not tensors — the manifest describes each tensor as a view over its storage so shared allocations (e.g. MLA's `W_UV`/`W_UK_T`) are copied once and keep their aliasing and footprint. `peer_ipc` verifies the source GPU by UUID before opening a handle; `rdma` registers each storage once and serves any number of mirrors.
- **Placement**: a same-host mirror must see the source's GPUs at their indices (CUDA IPC physics); the launcher learns the source's GPU UUIDs from its sockets and places the mirror's ranks on the remaining GPUs — no `--device-offset`-style flag.
- **Limitations / follow-ups**: single source per replica (multi-source fan-in is a natural next step); no bandwidth throttling; Mooncake required cross-host; mirror bring-up still pays world-group setup and meta-model construction (pipelining the copy with the meta build is a planned optimization); DSv4.1-class models additionally need per-rank host tables shipped out-of-band (they exceed `MAX_MSG_SIZE`).

Relationship to #60086: this is not a duplicate — it adopts that PR's data plane but reworks the mirror lifecycle and control-plane integration onto the current daemon framework (see Details). Happy to rebase/split if maintainers prefer landing the data plane first.
