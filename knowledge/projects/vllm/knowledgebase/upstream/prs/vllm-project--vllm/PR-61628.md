# [ROCm][MLA][DCP] Drop VLLM_ROCM_AITER_MLA_DCP_VERIFY

[Upstream PR](https://github.com/vllm-project/vllm/pull/61628) · state: open · merged: False

## Original PR description

## Purpose

Remove `VLLM_ROCM_AITER_MLA_DCP_VERIFY` and always select the DCP multi-token (spec-decode) verify kernel heuristically.

Default behavior is unchanged: the builder now always does what `auto` (the default) did.

- **gfx950:** AITER round-robin asm decode (cprr) when the DCP-gathered head count pads to a native kernel (16/32/64/128), otherwise segmented MLA.
- **gfx942:** segmented MLA where it fits in LDS, otherwise Triton split-KV decode. The env var never affected gfx942.

What goes away:
- `segmented`: the opt-out from cprr on gfx950.
- `asm`: the hard error for head counts cprr can't serve. These now fall back to segmented, as `auto` already did. A config with neither kernel still fails at builder init.

This also clears the way for a follow-up gfx942 verify-kernel work to choose a new assembly verify kernel.

### Setup

- 8x AMD Instinct MI325X (gfx942)
- Model: `moonshotai/Kimi-K3` (MXFP4) with the `Inferact/Kimi-K3-DSpark` draft
- Attention backends: `ROCM_AITER_MLA` for the target, `TRITON_MLA` for the draft
- The two runs differ only by this PR. Server flags, eval command and environment are identical.

### Server

```bash
VLLM_ROCM_USE_AITER=1 vllm serve moonshotai/Kimi-K3 \
  --served-model-name kimi-k3 \
  --trust-remote-code \
  --tensor-parallel-size 8 \
  --enable-expert-parallel \
  --max-num-seqs 32 \
  --max-model-len 65536 \
  --max-num-batched-tokens 4096 \
  --gpu-memory-utilization 0.95 \
  --decode-context-parallel-size 8 \
  --dcp-comm-backend a2a \
  --speculative-config '{"method": "dspark", "model": "Inferact/Kimi-K3-DSpark", "num_speculative_tokens": 5, "attention_backend": "TRITON_MLA", "draft_sample_method": "probabilistic", "rejection_sample_method": "block"}' \
  --port 8000
```
