# [ROCm][MLA][DCP] Drop VLLM_ROCM_AITER_MLA_DCP_VERIFY

[Upstream PR](https://github.com/vllm-project/vllm/pull/61628) · state: closed · merged: True

## Original PR description

## Purpose

Remove `VLLM_ROCM_AITER_MLA_DCP_VERIFY` and always select the DCP multi-token (spec-decode) verify kernel heuristically.

Default behavior is unchanged: the builder now always does what `auto` (the default) did.

- **gfx950:** AITER round-robin asm decode (cprr) when the DCP-gathered head count pads to a native kernel (16/32/64/128), otherwise segmented MLA.
- **gfx942:** segmented MLA where it fits in LDS, otherwise Triton split-KV decode. The env var never affected gfx942.

What goes away:
- `segmented`: the opt-out from cprr on gfx950.
- `asm`: the hard error for head counts cprr can't serve. These now fall back to segmented, as `auto` already did. A config with neither kernel still fails at builder init.

This also clears the way for a follow-up gfx942 verify-kernel work to choose a new assembly verify kernel.

- xaguilar-amd · comment · 2026-10-21T18:53:29Z · [source](https://github.com/vllm-project/vllm/pull/61628#issuecomment-6323972986)

@simondanielsson Yes. On gfx950 there is no shape where cprr can run and segmented is faster, so the variable is not an escape hatch for a slow cprr.

Segmented remains only where cprr has no kernel: query length below 3, gathered heads that do not pad to 16/32/64/128, or off gfx950. auto already used that fallback. Setting segmented only redirected batches cprr can serve, and that route is slower because it expands every verify token into its own paged-KV row.

I haven't benched myself on gfx950, but on Kimi-K3, 8× MI355X, TP8/DCP8 (96 heads padded to 128), from the PRs that enabled cprr:

[#56861](https://github.com/vllm-project/vllm/pull/56861), ISL 100k / OSL 256, qlen 8: mean TPOT 22.1 ms to 10.9 ms at concurrency 1, 53.1 ms to 15.6 ms at concurrency 4, and 179 ms to 110 ms at concurrency 8. At qlen 2 the two settings match within noise, because both run segmented.
[#59965](https://github.com/vllm-project/vllm/pull/59965), concurrency 48: segmented 141.0 tok/s and 170.8 ms median TPOT, cprr 212.6 tok/s and 101.0 ms. At OSL 1024 segmented finished no request inside the window.

GSM8K stayed within one standard error. Removing the override only drops the slower opt-out.
