# [Metrics] Add priority-aware labels and metrics for priority scheduling

[Upstream PR](https://github.com/vllm-project/vllm/pull/58078) · state: open · merged: False

## Original PR description

# 🚀 Description

Closes #58077

When `--scheduling-policy priority` is enabled, finished-request metrics now
carry a bucketed `priority` label so latency/throughput can be broken down per
priority tier. Two commits:

1. **priority-aware labels and metrics** — adds the `priority` label to all
   finished-request metrics, plus two new metrics:
   - `vllm:request_priority` (Histogram): raw finished-request priorities;
     registered only under priority scheduling.
   - `vllm:scheduler_policy_info` (Gauge): enum-style indicator of the active
     scheduler policy; always exposed.
2. **priority label for TTFT** — moves the `vllm:time_to_first_token_seconds`
   observation from iteration-level (`IterationStats.time_to_first_tokens_iter`)
   to the finished-request context, via the already-tracked
   `RequestStateStats.first_token_latency`. The measured value is identical;
   only the observation site changes, so the metric can carry the label.

## Label design (cardinality bounding)

The `priority` label is bucketed, not raw:

| Request priority | `priority` label |
|---|---|
| `-1` / `0` / `1` | preserved exactly (high / default / low) |
| any integer `< -1` | `<-1` |
| any integer `> 1` | `>1` |

The three conventional values carry semantic meaning and are preserved exactly;
everything else collapses, bounding cardinality to five values so clients cannot
blow up Prometheus series (e.g. deadline-based priorities). The raw distribution
remains observable via the new `vllm:request_priority` histogram.

## FCFS behavior is unchanged

Under the default `fcfs` policy: no `priority` label on any metric,
`vllm:request_priority` is not registered, and all existing series look exactly
as before. The only always-on addition is the `scheduler_policy_info` gauge
(lowest-cardinality way for a dashboard to discover the active policy).
Verified live — see "End-to-end verification" below.

## Not duplicating existing work

I searched open PRs/issues for priority + metrics/observability before
submitting; none add a priority dimension to request metrics. Related but
disjoint work: priority scheduling behavior (#47837, #45558, #54530, #44166
widening priority to float — orthogonal: the bucketing here is
float-compatible), KV-transfer priority QoS (#46016, #57829).

## Testing

Unit tests (new `tests/v1/metrics/test_priority_labels.py` + additions to
`test_stats.py`): label bucketing, the two new metrics, FCFS engine labels,
multi-engine (DP) series, TTFT label coverage.

```
pytest tests/v1/metrics/test_priority_labels.py tests/v1/metrics/test_stats.py -v
# 32 passed
```

**End-to-end verification** (self-hosted Linux box, RTX 3090, vLLM 0.29.0
wheel with these patches applied, Qwen3-0.6B):

- Started with `vllm serve --scheduling-policy priority`, sent 10 completions
  at priorities `-1`/`0`/`5` (×3 each) and one at `-100`.
- `/metrics` verified: `scheduler_policy_info{policy="priority"}=1`; all four
  buckets present (`-1`×3, `0`×3, `>1`×3, `<-1`×1) on
  `e2e_request_latency_seconds`, `request_queue_time_seconds`,
  `time_to_first_token_seconds`, `request_success_total`;
  `vllm:request_priority` counts match (10 total, correct raw buckets).
- Control run without the flag (fcfs): same traffic — no `priority` label on
  any finished-request metric, `vllm:request_priority` absent,
  `scheduler_policy_info{policy="fcfs"}=1`.
