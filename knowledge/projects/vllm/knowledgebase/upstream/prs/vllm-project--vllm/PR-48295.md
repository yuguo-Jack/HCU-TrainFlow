# [Bugfix][Tool Parser] Stream tool calls that arrive whole in a single delta in llama3_json, jamba and ernie45 parsers

[Upstream PR](https://github.com/vllm-project/vllm/pull/48295) · state: open · merged: False

## Original PR description

FIX #48294

## Purpose

When an entire tool-call message arrives in a single streamed delta (async scheduling, `stream_interval > 1`, or a short message emitted at once), three streaming tool parsers lose tool calls that the non-streaming path extracts correctly:

- **`llama3_json`** (also used for `llama4_json`) and **`jamba`**: the "starting a new tool" branch records state for the newly seen tool and returns `None` without emitting the name or arguments. No further deltas arrive, so the tool call is never emitted — the client gets an empty response.
- **`ernie45`**: only the first complete `<tool_call>...</tool_call>` block in a delta is emitted; the rest stay stranded in the internal buffer and are lost.

This is the same bug class as #47907, fixed for `gigachat3`/`granite`/`granite-20b-fc` in #47955. This PR extends the same approach to the three parsers above:

- `llama3_json`, `jamba`: when the first parsed delta already contains only complete tool calls, emit all of them (name + full arguments) in one `DeltaMessage` via a new `_emit_initial_complete_tool_calls` helper, mirroring #47955.
- `llama3_json`, `jamba`: when several tools appear at once, grow `streamed_args_for_tool` to match `current_tool_id` instead of appending a single slot. Previously the resulting `IndexError` was swallowed by the broad exception handler and silently dropped subsequent argument deltas.
- `ernie45`: drain every complete `<tool_call>...</tool_call>` block from the buffer per invocation instead of at most one, emitting one `DeltaToolCall` per block with correct indices.

**Duplicate check:** #47955 covers only `gigachat3`/`granite`/`granite-20b-fc`; #46934 covers `granite4` content loss. I found no open PR or issue addressing this for `llama3_json`, `jamba`, or `ernie45` (searched open PRs/issues for the parser names, "single delta tool", `check_tool_usage`, and related terms).

So the bug and the fix are both independently confirmed, not just asserted.

While poking at this, I tested a scenario the new tests don't cover: real per-token incremental streaming (not the "whole message in one delta" case this PR targets) with 2 tool calls, using the actual `ai21labs/Jamba-tiny-dev` tokenizer via `split_string_into_token_deltas`. The last tool call's `arguments` comes out truncated — missing its closing quote/brace:

```
get_current_weather {"city": "Dallas", "state": "TX"}      <- tool 0, correct
get_current_weather {"city": "Orlando", "state": "FL       <- tool 1 (last), truncated
```
Non-streaming `extract_tool_calls` on the same text returns both correctly, so it's specifically a streaming-reconstruction gap. Tracing it token-by-token, the token that closes the string+object+array-element (`"}}"`) arrives as its own delta and yields an empty `arguments` string instead of the closing punctuation.

Important: this reproduces identically on the parent commit (735def4fc) too, so it's **not** a regression from this PR — this PR's fast path (`_emit_initial_complete_tool_calls`) actually sidesteps it entirely for the case it targets, since it emits the full `json.dumps`'d arguments in one shot rather than diffing incrementally. The existing `parallel_tools` streaming test in `test_jamba_tool_parser.py` doesn't catch it because its assertion helper runs the accumulated string through `partial_json_parser.ensure_json(...)` before comparing, which silently repairs the truncated JSON before the `assert_tool_calls` check — a real client concatenating raw deltas (like the `StreamingToolReconstructor` this PR adds) would receive invalid JSON for the last parallel tool call. I didn't have access to the gated Llama tokenizer to check whether `llama3_json` has the same tail-loss pattern at real token granularity (a quick char-by-char probe didn't reproduce it there, but that's not representative of real BPE token boundaries), so I can't say whether it's jamba-specific or shared.

Not asking for changes here since it's pre-existing and out of scope for what this PR claims to fix, but worth a follow-up issue given it affects any Jamba response with 2+ parallel tool calls streamed normally (arguably more common than the single-delta case this PR addresses). The fix itself is correctly scoped and verified for what it targets.
