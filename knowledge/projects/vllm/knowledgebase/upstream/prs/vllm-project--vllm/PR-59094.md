# [Bugfix] Secure /scale_elastic_ep: API-key auth, bool rejection, 400 when elastic EP disabled

[Upstream PR](https://github.com/vllm-project/vllm/pull/59094) · state: open · merged: False

## Original PR description

## Summary

Fixes #59088.

The `/scale_elastic_ep` endpoint had three bugs:

1. **API-key authentication bypass.** `AuthenticationMiddleware` only guards the `("/v1", "/v2", "/inference", "/cohere")` path prefixes, while the elastic EP router is mounted at the server root — so the middleware never checked this endpoint. `/scale_elastic_ep` is state-changing: while a scale is in progress, `ScalingMiddleware` returns 503 for every request. Anyone with network access could trigger it without a key. This PR adds `/scale_elastic_ep` to `GUARDED_PREFIX`. The read-only `/is_scaling_elastic_ep` stays unguarded, analogous to `/health`.

2. **Boolean parameters accepted as counts.** `isinstance(True, int)` is `True`, so `{"new_data_parallel_size": true}` returned `200 "Scaled to True data parallel engines"`. Both `new_data_parallel_size` and `drain_timeout` now go through a `_require_positive_int` helper that explicitly rejects bools (keeping the same "must be a positive integer" 400 messages as before).

3. **500 for permanently impossible scaling.** On a server started without `--enable-elastic-ep`, the request fails deep in the engine (`AssertionError` from the `data_parallel_backend == "ray"` assert) and surfaces as a bare `500 "Scale failed"` with an empty log message. The handler now checks `parallel_config.enable_elastic_ep` up front and returns `400` with an actionable message ("Restart the server with --enable-elastic-ep to use /scale_elastic_ep"). 400 was chosen over 501 because the endpoint exists and is implemented — the request is invalid for this server's configuration — consistent with the handler's existing `ValueError` → 400 mapping (e.g. exceeding `--elastic-ep-max-dp-size`). The catch-all handler now uses `logger.exception`, so the server log carries the real traceback.

## Test results

New tests in `tests/entrypoints/serve/elastic_ep/test_api_router.py` (5 tests):

- `test_rejects_boolean_data_parallel_size` / `test_rejects_boolean_drain_timeout` — boolean inputs are rejected with 400 (both fail on the unfixed code).
- `test_rejects_non_positive_and_non_integer` — 0, negatives, floats, and strings still rejected.
- `test_returns_400_when_elastic_ep_disabled` — disabled elastic EP yields 400 with the actionable message instead of 500 (fails on the unfixed code).
- `test_valid_request_still_scales` — valid integer input with elastic EP enabled still returns 200.

Commands run (repo `.venv`, Python 3.12, CPU-only):

- `python -m pytest tests/entrypoints/serve/elastic_ep/test_api_router.py` → **5 passed**
- `python -m pytest tests/entrypoints/serve/middleware/test_authentication_middleware.py` → **20 passed**. This suite auto-discovers routes per supported task and asserts guarded routes require auth; for the `generate` task it now covers `/scale_elastic_ep` (401 without a token) and confirms `/is_scaling_elastic_ep` stays public.
- `ruff check` and `ruff format --check` on all four touched/added files → clean

A TestClient-level repro (mocked engine client) additionally confirmed the before/after matrix: no-key request went from reaching the handler to `401`; boolean input from `200 "Scaled to True data parallel engines"` to `400`; disabled elastic EP from `500 "Scale failed"` to `400` with the actionable message; `/is_scaling_elastic_ep` remains reachable without a key.
