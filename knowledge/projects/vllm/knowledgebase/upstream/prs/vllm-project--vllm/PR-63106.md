# [Feature][DSv4.1] Support arbitrary pipeline stage partitions

[Upstream PR](https://github.com/vllm-project/vllm/pull/63106) · state: open · merged: False

## Original PR description

## Overview

DeepSeek-V4.1 reuses compressed Main KV and indexer K state across groups of layers. The existing NVIDIA implementation resolves these states only from modules on the same PP rank and explicitly rejects a cut inside a KV-sharing group. For this 40-layer checkpoint, whose KV source layers are `[2, 8, 14, 20]`, PP2 is therefore limited to the group boundaries `2/38`, `8/32`, `14/26`, and `20/20`.

Those legal cuts do not balance the actual Prefill work well. With SWA bounded replay enabled, the early layers process the full prompt while the layers after the final KV source process only the trailing 128 tokens. In our 8K, Concurrency 8 profile, the two practical baseline cuts, `14/26` and `8/32`, left 1.92x and 1.62x PP-stage imbalances respectively, producing a substantial pipeline bubble.

This PR supports arbitrary nonempty PP partitions by relaying live Main KV, indexer K, top-k indices, and candidate blocks across stage boundaries and registering receiver-side cache replicas. This adds state-transfer and replica overhead, but the measured overhead is much smaller than the bubble removed by a better partition: `11/29` reduces the stage ratio to 1.08x and improves end-to-end Prefill throughput by about 19% versus the fastest supported baseline. See Validation below.

## Claims

- Support arbitrary nonempty partitions through `VLLM_PP_LAYER_PARTITION`, including cuts inside KV-sharing groups.
- Relay Main KV, indexer K, top-k indices, and candidate blocks across PP stages while retaining paged cache replicas for prefix caching.
- Preserve packed cache bytes and source compression ratios, and reject unsupported execution combinations before layer construction.

### PP bubble and relay overhead

The profile used 24 cold 8192-token / 1-token requests at Concurrency 8 and captured all eight ranks. Values below are GPU kernel time per request averaged over the four TP ranks in each stage. PP SendRecv is excluded and TP collectives are included. The absolute PP0/PP1 work gap is used as the pipeline bubble proxy.

| Partition | PP0 work (ms/request) | PP1 work (ms/request) | Stage-work gap (ms/request) | Longer / shorter |
| --- | ---: | ---: | ---: | ---: |
| Baseline 14/26 | 325.8 | 169.9 | 155.9 | 1.92x |
| Baseline 8/32 | 190.6 | 309.5 | 118.9 | 1.62x |
| PR 11/29 | 258.9 | 239.0 | 19.9 | 1.08x |

At `11/29`, the measured Main KV + indexer K + top-k relay components were 0.034 ms PP0 pack/init, 0.043 ms PP send, 0.037 ms PP receive, 0.116 ms PP1 TP gather, and 0.039 ms PP1 copy/scatter per request per TP lane. Even their conservative arithmetic sum is only 0.269 ms; it is not a wall-clock latency because send/receive overlap and receive time includes peer waiting. This is orders of magnitude smaller than reducing the stage-work gap from 155.9 ms (`14/26`) or 118.9 ms (`8/32`) to 19.9 ms. Candidate-block relay was not exercised by `11/29` because its source is layer 20.

  for CONCURRENCY in 1 8 16; do
    NUM_PROMPTS=$((10 * CONCURRENCY))

      --base-url "${BASE_URL}" \
      --endpoint /v1/completions \

At Concurrency 8/16 across 8K-32K inputs, `11/29` improves Input throughput by 24.5%-25.4% and reduces Mean TTFT by 19.7%-20.3% versus `14/26`. These service-level gains agree with the profile: the benefit from removing the PP bubble is much larger than the cross-stage relay overhead.

All listed arms completed 4740/4740 formal requests with zero cache-hit increments, preemptions, or restarts, and all requests had the expected length finish. The 8K/16K/32K one-token smoke outputs matched across the listed arms. Full accuracy or logit-equivalence evaluation was not run.

Full GSM8K test split with EvalScope 1.11.1, 0-shot, batch 8, `temperature=0`, seed 42, and `max_tokens=65536`:

| Partition | Correct | Accuracy |
| --- | ---: | ---: |
| Baseline 14/26 | 1260/1319 | 95.527% |
| PR 11/29 | 1258/1319 | 95.375% |

## Details

Generalize the cache-relay approach to track live sharing sources at each stage boundary. Reuse PP intermediate tensors and register receiver caches under their original source-layer names so the scheduler retains consistent cache groups across stages. Only newly written rows at completed compression boundaries are copied; padding and skipped slots are masked.

Cross-stage relay requires Model Runner V2, packed FlashMLA caches, and PCP=DCP=1, without speculative decoding, KV transfer, or microbatching. Replicas add cache memory and communication overhead. The existing decoder-side layer-replay guard disables batch shrinking when the final KV source and its consumers span stages. Existing PCP restrictions remain unchanged.

No open PR was found that implements DeepSeek-V4.1 cross-stage cache relay. AI assistance was used to prepare this change.
