# [Core] Add a generation readiness check `/ready`

[Upstream PR](https://github.com/vllm-project/vllm/pull/60505) · state: open · merged: False

## Original PR description

## Purpose

Adds a generation readiness check at `/ready`.

The implementation is based on PR #59179 with some improvements to cover more edge cases with DP > 1 as well as report not-ready details. I've added the author as a committer for this PR. Please refer to the original PR #59179 for context on the initial design of the changes.

### Background

For long running inference deployments for online serving as well as RL use-cases, there can be a variety of inference engine failures or hangs. Broadly there are two sources of failures / hangs:

1. Infrastructure failures: GPU failures, network failures, etc. Some of these are recoverable (transient error that succeeds on retry) while some are not (GPU failure).
2. Software bugs: There are two styles of errors here:
a. Probabilistic, recoverable: Errors that happen due to low-probability events such as:
      1. An illegal memory access with vLLM that occurs once in millions of generations.
      2. A collective hang during weight syncing in DPEP setups.
      3. Generation [hang](https://github.com/vllm-project/vllm/issues/44185) with spec decoding + MoE + DP.  
b. Irrecoverable bugs: Bugs that are deterministic failures in certain state.
      1. Misconfigurations, unsupported kernel on certain hardware, etc.

Providing a readiness endpoint helps users detect and recover from failures of class 1. and 2.a.

### What kind of health checks will detect such failures / hangs?

| Health check | Description | Failures caught |
| :---- | :---- | :---- |
| Existing `/health` endpoint | API server and Engine process liveness. | #54173, #37035, #60109, #59768, once the CUDA/kernel failure surfaces as EngineCore or worker death. |
| `/health_generate` in SGLang | Gets the scheduler to admit a dummy request. If the scheduler is busy (running + waiting > 0), return early with a success response. If the scheduler is idle, execute a dummy forward pass (single token). | #44185, #43547, #36594 / #51481, #54173, #37035, #60109, #59768. However, issues like #45388 are not caught - this is because the scheduler can seem busy (running + waiting > 0) when it's not making any progress (running = 0, waiting > 0) for a long time. |
| Proposed `/ready` (improved version of `/health_generate`) | Gets the scheduler to admit a dummy request. If the scheduler is busy (running + waiting > 0), get the last time since the scheduler has processed tokens. If larger than a timeout, raise, otherwise return a success response. If the scheduler is idle, execute a dummy forward pass (single token). | #44185, #43547, #36594 / #51481, #54173, #37035, #60109, #59768 and #45388. |

One failure that is not caught by any of the methods above is #53130. I would argue that it is out of scope for the current effort, since the issue is a bit unclear on the exact root cause for the bug. A part of the issue also mentions that the hang occurs when the scheduler is already busy and is able to make progress on running prefill inputs, which means that the engine is alive and healthy.

Note that we haven't discussed any recoverable errors from infrastructure failures. Typical failures here lead to collective timeouts or EngineCore process death, which are of a similar nature to the failures above.

### Changes on top of #59179

**DP > 1 fixes**

- Only count a DP dummy batch as ready progress when the rank has no local unfinished requests. A rank that holds requests but schedules nothing (e.g. #45388) keeps the wave alive with dummy batches and was previously reported as making progress.
- Run the idle readiness probe for DP > 1 instead of skipping it. Dense DP ranks are independent engines and run the dummy-batch probe as with DP = 1. MoE DP engines answer with a liveness-only ping, since a dummy batch outside the wave loop could deadlock against peer collectives; a busy loop wedged in a control RPC now times out the probe. (This is minor. I have no idea if users are running DP > 1 for dense models. I have included this fix to be safe.)

**Not-ready details**

- `/ready` returns a JSON body for every not-ready case:
  ```json
  {"status": "not_ready", "reason": ..., "message": ..., <details>, "in_progress": [...]}
  ```
  with `reason` one of `engine_dead`, `sleeping`, `stalled`, `probe_timeout` or `probe_failed`.
- `in_progress` lists the utility call each EngineCore is executing, with its rank and elapsed time. EngineCore publishes the operation on the ready-progress broadcast before running a utility and clears it afterwards, so every API server reports it regardless of which one issued the call.

**Why report additional not-ready details?**

Downstream applications, such as a load balancer or a health monitor daemon, will need to make decisions on tearing down a server or not based on the response. A 503 response from the server does not indicate that the server is unhealthy - it is indicating that the server is not ready to handle generation requests at the moment. For example, the server might return 503 while waiting for weight sync to complete.

### Comparison with the `/fault_tolerance/` APIs

The current fault tolerance APIs can detect failures/hangs during the forward pass in DPEP MoE deployments. This PR targets a broader set of failures/hangs and it is thus useful to introduce a `/ready` endpoint.

## Test Plan

Apart from the unit tests added in #59179, I've additionally added some real E2E tests covering different failure modes from the list above. I think it's important to have these E2E tests to guarantee failure recovery at the engine level.

New tests added:

- Unit tests for the DP probe, reason/in-progress reporting and the engine-side operation broadcast.
- Fault-injection E2E tests (`tests/v1/engine/readiness`) using `--scheduler-cls` / `--worker-extension-cls`: scheduler stall, latent CUDA fault while idle and no-false-positive checks on a single engine, and MoE/dense DP = 2 variants including a rank wedged in a mismatched DP collective. Wired into the V1 Engine and Distributed DP Basic steps.

[P1] Update the Rust output protocol before broadcasting readiness messages

These fields produce readiness envelopes with 11 array elements, while rust/src/engine-core-client/src/protocol/output.rs still defines an eight-field WireEngineCoreOutputs using Deserialize_tuple. A real Python readiness frame passed to the same tuple decoder shape returns LengthMismatch(8). Even after accepting the additional fields, TryFrom<WireEngineCoreOutputs> rejects a readiness-only envelope as "invalid wire shape" because it has no request, utility, or wave payload.

The Rust transport forwards this decode error to the dispatcher, whose error path closes all request and utility registries. This affects ordinary Rust serving: IDLE-to-BUSY transitions and normal utility calls publish these messages even when nobody calls /ready.

Update both the Rust wire schema and readiness-only message handling, or negotiate/filter these notifications for unsupported consumers. Add a cross-language regression using an actual Python-encoded frame and verify that the Rust client continues serving after it.
