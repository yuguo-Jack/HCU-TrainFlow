# [Bugfix][Benchmark] Use concurrency for per-user throughput

[Upstream PR](https://github.com/vllm-project/vllm/pull/56918) · state: open · merged: False

## Original PR description

## Purpose

The documented fallback for concurrent users is max_concurrent_requests, but request_rate takes precedence when the configured user-count key is absent. Dividing tokens/s by requests/s produces tokens/request and can turn an unlimited request rate into zero per-user throughput. Use the documented concurrency fallback.

This only changes runs where the key named by `--user-count-var` is missing from the record. Ordinary `bench serve` output writes `max_concurrency` (as `None` when unset), which already fell through to `max_concurrent_requests`. That measured value is overcounted at second boundaries until #56653 is fixed, so fallback runs can still read low.

Open PRs #55607/#55658 fix frontier dominance and #56111 fixes GPU-count discovery. This changes only user-count inference; no competing fix was found.

- HarshShroff · COMMENTED · 2026-09-29T14:43:54Z · [source](https://github.com/vllm-project/vllm/pull/56918#pullrequestreview-5354223250)

Checked this out locally. The three new test functions (five cases with the parametrization) pass on this branch and the first one fails on main with `user_count_estimate` equal to the request rate instead of 5, so the regression is real. I ran them with the repo's heavy imports stubbed since I don't have a GPU/torch environment here, so treat it as a check of `_prepare_records` alone.

Two notes, neither blocking.

1. The bug needs the user-count key to be absent. `bench serve` always writes `max_concurrency` into the result JSON (it's `None` when the flag isn't set), and `_first_present` returns the first key that exists even when its value is `None`, so `_get_numeric` returns `None` and the old code already fell through to `max_concurrent_requests`. I confirmed that with a record shaped like real `bench serve` output. The `request_rate` fallback only bites when the key named by `--user-count-var` is missing from the record, for example a custom `--user-count-var` that a sweep didn't record. Might be worth saying that in the description so nobody expects a change for ordinary runs. A test with `max_concurrency: None` present would pin the common shape too.

2. After this, the fallback is the measured `max_concurrent_requests`, and that number is currently overcounted at integer-second boundaries (#56653, with #56647, #56675 and #56678 open for it). Until one of those lands, the tokens/s/user for runs that hit the fallback will read low, by up to 2x in the numbers reported in #56653. It's the right fallback, just worth linking in the description.
