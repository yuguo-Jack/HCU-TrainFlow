# [Attention][FlashInfer] Support DiffusionGemma mixed causal/bidirectional attention on TRTLLM-Gen

[Upstream PR](https://github.com/vllm-project/vllm/pull/62516) · state: open · merged: False

## Original PR description



## Purpose

> [!IMPORTANT]
> **Requires FlashInfer PR https://github.com/flashinfer-ai/flashinfer/pull/4905** (TRTLLM-Gen sliding-window FMHA), which adds `window_right`, `variable_window_token_starts/ends`, and the VariableWindow cubins. It is not in `flashinfer-python==0.7.2`, so this PR stays a draft until a FlashInfer release includes #4905 and vLLM's pin is bumped.

Enable the FlashInfer TRTLLM-Gen attention backend for DiffusionGemma on Blackwell. DiffusionGemma batches mix causal (encode/commit) and bidirectional (denoise) requests, which FlashInfer previously rejected with a `ValueError`.

- **Sliding-window layers:** build per-token KV bounds for TRTLLM-Gen's VariableWindow kernel (`variable_window_token_starts/ends`). A causal token attends to `[pos - w, pos]` and a bidirectional token to `[pos - w, pos + w]`, matching the FlashAttention reference path.
- **Full-attention layers (head dim 512):** no VariableWindow kernel exists for this head dim, so the layer runs one causal and one dense launch and keeps each token's own row.
- **Causal flags:** per-request flags may be bool or int32. DiffusionGemma's persistent buffer is int32.
- **FULL CUDA graphs:**
  - Window bounds and causal flags are copied into persistent builder buffers.
  - Tokens map to requests with `searchsorted`, so padded graph batches stay well defined. Padding tokens get `[0, 0]` bounds.
  - The backend keeps reporting `UNIFORM_BATCH`, so the uniform canvas-length denoise steps are captured as FULL graphs.
- **NVFP4 TRTLLM MoE:** FP32 routing weights are cast to BF16, as FlashInfer's precomputed-routing path requires.
- **Not supported yet:** quantized attention output on the merged full-attention path, and DCP. Both raise an explicit `NotImplementedError`.

## Test Plan

- **Unit:** `pytest tests/kernels/attention/test_mixed_causal_attn.py -k flashinfer` covers window bounds, bool and int32 flags, and FULL-graph padding.
- **Server:** 1×B200, TP1. This is the perf server, which uses FlashInfer TRTLLM-Gen with BF16 KV:
  ```bash
  VLLM_USE_V2_MODEL_RUNNER=1 VLLM_SERVER_DEV_MODE=1 \
  vllm serve nvidia/diffusiongemma-26B-A4B-it-NVFP4 \
    --language-model-only --enable-expert-parallel --moe-backend auto \
    --attention-config '{"backend":"FLASHINFER","use_trtllm_attention":true}' \
    --kv-cache-dtype bfloat16 \
    --max-num-seqs 8 --max-num-batched-tokens 8192 --max-model-len 16384 \
    --gpu-memory-utilization 0.9 --no-enable-prefix-caching \
    --diffusion-config '{"canvas_length":256}' \
    --override-generation-config '{"max_new_tokens":null}' \
    --default-chat-template-kwargs '{"enable_thinking":true}' \
    --reasoning-parser gemma4 --tool-call-parser gemma4 --enable-auto-tool-choice \
    --trust-remote-code
  ```
  - FP8 KV: `--kv-cache-dtype fp8`.
  - Baseline: `--attention-config '{"backend":"TRITON_ATTN"}'`.
  - `VLLM_SERVER_DEV_MODE=1` only exposes `/reset_prefix_cache`, which the sweep calls between concurrency levels.
- **Accuracy:** GPQA-Diamond with NeMo-Skills, AA `mcq-4choices` prompt, thinking on, 16 repeats, concurrency 4. The server is the same as above except for `--max-num-seqs 4 --max-model-len 65536 --enable-prefix-caching`.
- **CUDA graphs:** the accuracy server with `--seed 0`. Compare the default `FULL_AND_PIECEWISE` mode against `--compilation-config '{"cudagraph_mode":"PIECEWISE"}'` on 6 GPQA prompts, byte for byte.
- **Perf:** aiperf with SPEED-Bench 1K-throughput prompts (32 requests per concurrency level, ISL ≈ 1.2K, OSL ≈ 3.1K), concurrency 1–8.

## Test Result

- **Unit:** 7 passed.
- **CUDA graphs:** FULL and PIECEWISE produce byte-identical outputs on 6/6 prompts (4.3K–14.9K chars each).
- **GPQA-Diamond** (pass@1, average of 16 runs; the model card reports 68.6 for NVFP4):

| Attention | KV cache | CUDA graph | pass@1 |
|---|---|---|---|
| TRITON_ATTN (baseline) | BF16 | default | 69.95 |
| FlashInfer TRTLLM-Gen | BF16 | PIECEWISE | 68.12 |
| FlashInfer TRTLLM-Gen | BF16 | FULL_AND_PIECEWISE | 67.52 |
| FlashInfer TRTLLM-Gen | FP8 | PIECEWISE | 69.10 |
| FlashInfer TRTLLM-Gen | FP8 | FULL_AND_PIECEWISE | 69.10 |

Paired bootstrap 95% CIs:
- FULL vs PIECEWISE: BF16 −0.6 [−2.7, +1.5], FP8 +0.0 [−2.2, +2.1].
- TRTLLM-Gen vs Triton: BF16 −1.8 to −2.4 (one CI barely excludes 0), FP8 −0.9 [−2.9, +1.2].

FP8 KV runs through the same kernel path and scores 69.10, so I read the BF16 gap as sampling noise. No-answer rates (3.6–4.8%) and output lengths match across all configs.

- **Perf:** SPEED-Bench 1K-throughput prompts, prefix caching off. Each cell is output tokens/s per GPU / per user, with the per-GPU speedup over `TRITON_ATTN` in parentheses:

| Concurrency | TRITON_ATTN, BF16 KV | TRTLLM-Gen, BF16 KV | TRTLLM-Gen, FP8 KV |
|---|---|---|---|
| 1 | 1782 / 2257 | 1965 / 2572 (1.10×) | 1880 / 2401 (1.05×) |
| 2 | 2266 / 1401 | 2838 / 1714 (1.25×) | 2806 / 1795 (1.24×) |
| 4 | 2588 / 834 | 3619 / 1183 (1.40×) | 3890 / 1244 (1.50×) |
| 8 | 2467 / 485 | 3291 / 585 (1.33×) | 3343 / 580 (1.36×) |

The TRTLLM-Gen columns use FULL CUDA graphs, the default after this PR. Compared with PIECEWISE on the same workload, FULL graphs mainly help c1: BF16 per-user throughput goes from 2370 to 2572 (+8.5%). Run-to-run noise is about ±10%, because average output length varies between runs. A 1K shared-prefix workload and prefix caching on show the same trend.
