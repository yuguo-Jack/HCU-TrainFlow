# [Perf][DSv4.1] Capture the decoder replay graphs on the model graphs' stream

[Upstream PR](https://github.com/vllm-project/vllm/pull/63155) · state: closed · merged: True

## Original PR description



## Overview

Capture the DeepSeek-V4.1 decoder replay graphs on the model graphs' capture stream, so that they reuse the model graphs' free blocks in the shared graph pool instead of reserving a second pool. Fixes #62965.

## Claims

- DeepSeek-V4.1-Flash prefill on GB200 (DP4, breakable PIECEWISE graphs up to 16384 tokens): graph capture memory drops from 15.52 GiB to 9.88 GiB per rank, and the replay capture no longer adds a graph pool segment.
- No accuracy or capture-time change beyond run-to-run noise (table below).
- Only the replay graphs move to the shared stream. The speculator and encoder captures, and Model Runner V1, keep a new stream per capture.

## Validation

GB200, DeepSeek-V4.1-Flash, 1P1D, prefill DP4, `max_model_len` 16k, breakable PIECEWISE graphs with capture sizes up to 16384 tokens, DSpark on. Two fresh service starts per arm. Measured on a v0.32.0-based build with this change; see Details for what differs on `main`.

| | separate streams (`main`) | shared stream (this PR) |
|---|---|---|
| prefill graph capture memory per rank | 15.52 / 15.52 GiB | 9.88 / 9.88 GiB |
| capture time | 36 / 36 s | 36 / 37 s |
| GSM8K (1319, greedy) | 97.50 / 97.42 | 97.57 / 97.12 |

- Before the change, `torch.cuda.memory._snapshot()` segments at the end of `capture_model()`, grouped by `(segment_pool_id, stream)`, show the replay graphs' own pool: 5.18 GiB reserved, none of it in use. After the change, the replay capture adds no graph pool segment.
- First-token top-20 logprobs on 64 prompts of 1k-7k tokens (prefix cache off, concurrency 1 and 16) differ across arms by as much as across two starts of the same arm. At concurrency 1: first token equal in 59-62/64 across arms vs. 60-61/64 within an arm; median |Δlogprob| of the first token 0.05-0.06 in both cases.

No test is added: CI has no runner for DeepSeek-V4.1-Flash with replay graphs, and the existing replay capture test (`tests/models/test_deepseek_v41_decoder_replay_layers.py`) calls `capture_replay_graphs()` without a stream, so it keeps today's behavior.

## Details

**Root cause.** Since #59532, `DecoderReplayCudaGraphManager` captures the replay graphs after the model graphs, in a `CudaGraphManager.capture()` call of its own. Every `capture()` enters `graph_capture()`, which creates a new stream. Both managers capture into the global graph pool, but the caching allocator reuses a free block only on the stream that freed it, so the replay graphs cannot use the model graphs' free pool blocks and reserve their own.

**Change.**

- `graph_capture(device, stream=None)` reuses `stream` when one is given.
- `CudaGraphManager.capture(..., stream=None)` captures on it and records the stream it used in `capture_stream`.
- `GPUModelRunner.capture_model()` passes the model graphs' `capture_stream` to `ModelState.capture_inner_cudagraphs()`, and DeepSeek-V4.1 forwards it to `capture_replay_graphs()`.

**Why sharing is safe.** A replay graph runs inside an eager break of a model graph. `DecoderReplayCudaGraphManager.run()` first gathers the layer inputs into its static `input_buffers`, then replays. After the break, the model graph reads only the break's own output buffers (`DecoderReplayLayers._break_outputs`), which live outside the graph pool. KV caches and the replay batch metadata are persistent. So no model graph tensor in the pool is still needed while a replay graph runs.

The one exception is aux hidden states captured before the replay layers: the forward holds them across the break. `DecoderReplayLayers.has_early_aux()` reports whether any aux layer id is below the replay start, and in that case the replay graphs keep their own stream. For DSpark on DeepSeek-V4.1-Flash, the aux layers (37-39) are produced inside the replay layers (from layer 20 on), so the fallback does not apply there.

**Differences from the measured build.** The port to `main` also forwards the stream through the specialized decode model state's `capture_inner_cudagraphs()` override (#61868), and the `graph_capture()` change sits next to #57481's edits. The early-aux fallback is new in this PR. It returns `False` in the measured configuration, so the measured path is unchanged.

**Alternatives.**

- #59537 caches one capture stream per device for every `graph_capture()` call. It would also let the replay graphs reuse the model graphs' pool, but it puts the speculator capture on that stream as well. The speculator runs after the target forward and reads its outputs, so it needs its own lifetime argument. Passing the stream only to the graphs replayed inside the model graphs limits the change to the case argued above.
- Capturing the replay graphs nested inside the model graph capture, as #56752 did, also shares the pool, but then a replay graph is captured inside one model graph size and replayed inside others.
- Smaller `decoder_replay_cudagraph_capture_sizes` shrink the replay pool proportionally, but larger replay batches then run eagerly.
