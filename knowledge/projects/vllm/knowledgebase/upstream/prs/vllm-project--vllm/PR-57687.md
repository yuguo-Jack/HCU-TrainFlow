# [Draft][CPU][GLM5Next] Add sparse MLA / KeyPool backend

[Upstream PR](https://github.com/vllm-project/vllm/pull/57687) · state: open · merged: False

## Original PR description

## Summary

This PR adds a correctness-first CPU sparse MLA / KeyPool execution path for GLM5Next for #57345.

The implementation keeps the common GLM5Next model graph and adds only the GLM-local CPU indexer, KeyPool lifecycle, metadata, and sparse MLA adapters required for execution. It is independent of the CPU KDA work in #57496.

## Self-review / Implementation notes

### Why a GLM-specific path

The existing dense CPU MLA backend does not match the GLM5Next sparse contract. The DeepSeek CPU implementations were useful structural references, but GLM5Next has distinct KeyPool compression, gate-score pooling, pool-level top-k, pool-to-token expansion, incomplete-pool tails, index-cache representation, and request-local pool boundaries.

For that reason this PR does not copy a complete DeepSeek attention object graph and does not introduce a generic sparse framework. The feature-local flow is:

```text
GLM5Next common attention
  -> CPU indexer metadata
  -> KeyPool compression/tail/cache lifecycle
  -> selected-row sparse MLA
  -> existing latent/value/output projections
```

I intentionally did not add `glm5next/cpu/model.py`. The existing model hierarchy remains usable; only sparse indexer/MLA execution and the minimum platform/backend injection differ on CPU.

### KeyPool lifecycle

For complete pools, the CPU path preserves the intended sequence of pooling, BF16 round-trip, Hadamard transform, FP8 quantization, and index-cache write. For incomplete pools it preserves raw K/gate tail state. Decode reads the request-local tail before adding the new token, then performs pool completion, cache write, top-k selection, and token expansion in that order.

The metadata builder carries pool-granular lengths, block tables, slot mappings, request expansion, and physical-page addressing rather than reconstructing those values heuristically inside the backend.

### Runtime cases validated

The focused suite exercises the production metadata builder, paged caches, KeyPool, and sparse MLA together. It covers:

* one-shot and multi-step pool completion;
* mixed prefill/decode and request reorder;
* request-local pool boundaries even when flattened positions look contiguous;
* dirty physical slot reuse;
* block-aligned prefix restore without tail state;
* non-aligned restore with circular tail state;
* relocation of index, latent, and tail caches;
* independent FP8 bytes/scales and pool top-k checks;
* selected-row sparse MLA versus an independent dense calculation;
* real `Glm5NextMLAAttention.forward` through the CPU path.

The final clean branch passes:

```text
24 passed, 15 warnings in 11.73s
```

The extra warning is the expected detached-worktree absence of generated `vllm._version`; the remaining warnings are existing torch.jit deprecations. Targeted Ruff, Ruff format, Typos, SPDX, lazy-import, forbidden-import, torch.cuda, and manual Python 3.12 mypy hooks pass on the final files. `git diff --check` passes.

### Bugs found and fixed by lifecycle tests

The tests exposed several semantic issues that were fixed in the implementation:

* selected history could consume `index_topk` and truncate the incomplete tail;
* the CPU metadata builder lacked pool-granular slot/length information;
* CPU indexer scores omitted the NVIDIA-compatible per-head ReLU;
* CPU platform handling unnecessarily disabled chunked prefill and prefix caching for this GLM sparse path.

These checks are included because a finite end-to-end tensor would not reliably expose cache ownership or intermediate representation errors.

### Deliberate non-goals and remaining boundary

This is a transparent PyTorch correctness baseline. It does not include native C++/AVX-512 kernels, performance claims, padded speculative decode, a generic sparse-attention refactor, KDA changes, or a full GLM-5.3-Flash generation run with a production checkpoint. Those are separate follow-ups.

Please review the local backend injection point, KeyPool metadata/state representation, request-local slot ownership, prefix/tail restoration, and the narrow CPU block-size/platform handling.
