# [ROCm][Perf][GLM-5.3-Flash] Drop int32/int64 copies in the kpool sparse indexer

[Upstream PR](https://github.com/vllm-project/vllm/pull/63910) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

GLM-5.3-Flash on ROCm: the kpool sparse indexer (`vllm/models/glm5next/amd/sparse_indexer.py`) launches int32↔int64 casts, a `+1`, a `-1` fill and a buffer copy around `expand_pools_and_append_tail` in every sparse-attention layer. This PR lets the expand kernel read int32 pool ids and int64 positions as they are (the `+1` moves into the kernel) and write straight into `topk_indices_buffer`, removing 6 launches per sparse-attention layer, 66 per decode step.

## Claims

- 1.7–4.4% lower median TPOT at 1–32 concurrent requests on 1k/1k, 8k/1k, 64k/1k and 128k/1k (MI355X, TP4, `amd/GLM-5.3-Flash-Quark-MXFP4`) against the same ROCm nightly without this PR, and 0.9–1.8% at 64; flat at 64k c16 (−0.2%), where each step carries other requests' long prefill. Two runs per arm on swapped GPU halves; every point except 128k c8 (spread larger than the change, see below) moves the same way in both runs.
- A decode step issues 66 fewer kernels (1,295 → 1,229) and 308 µs less kernel time under the profiler.
- Accuracy unchanged: GSM8K 0.920 vs 0.921, GPQA-Diamond 0.904 and 0.909 vs 0.914 and 0.894.
- Unchanged: the NVIDIA kpool indexer, the padded (`requires_padding`) decode layout, and every other model.

## Validation

Both arms: MI355X, TP4, ROCm nightly `76c6f3f2a9` (AITER v0.1.27), control = the nightly image, arm = the same nightly with this PR applied (`5786027c10`; rebased onto main since as `f493d6d757`, the same diff), nothing else. Run 1 has control on GPUs 0–3 and the arm on 4–7 of one node; run 2 swaps them on a second node.

## Details

- `expand_pools_and_append_tail(..., seq_len_offset=1, out=topk_indices_buffer[rows])`: reads `positions` directly (int64) and computes `seq_len = pos + 1` in-kernel; writes the full buffer row, `-1` past `topk + pool_size - 1`, so the caller's `-1` fill only covers rows after the decode rows on the uniform layout.
- `_kpool_decode_update_batched_kernel` takes int64 positions (no narrowing copy).
- Pool ids stay int32 (< 65k pools), so `pid * pool_size` fits.
- Prefill chunks get the same direct write.
