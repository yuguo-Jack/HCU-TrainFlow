# [ROCm][Step5] Use native fnuz FP8 MFMA in CSA prefill indexer scores

[Upstream PR](https://github.com/vllm-project/vllm/pull/65410) · state: open · merged: False

## Original PR description

## Overview

Run the Step-5 CSA prefill indexer scores on the native FP8 MFMA on fnuz GPUs (MI300X/MI325X, gfx942). The ROCm path gets its own kernel in `vllm/models/step5/amd/ops/indexer_scores.py`, and the Hopper `paged_mqa_logits_sm90` in `common/` stays as it is. Follow-up to #61837.

## Claims

- Prefill indexer scoring is 4.6-4.95x faster on MI325X.
- Step-5-Preview serving throughput improves by up to 117% at 128k input on 8x MI325X.
- Numerically equivalent: the FP8 operands are reinterpreted exactly, and the extra factor of 4 is a power of two.
- No shared or NVIDIA code changes.

## Validation

**Setup:** Step-5-Preview, 8x MI325X, TP=8, FP8 KV cache, `--block-size 32`, `--no-enable-prefix-caching`, `vllm/vllm-openai-rocm` nightly. Before is the same container without this change.


### Tests

New tests in `tests/models/step5/test_amd_csa_indexer_scores.py`:

- `test_scores_match_float64_on_scrambled_pages` compares scrambled page tables against a float64 reference, with `0x80` bytes injected into Q and K.
- `test_scores_exact_on_every_fp8_byte_pair` multiplies every pair of the 254 finite e4m3fn values and expects the exact product, so -0, subnormals and ±448 are covered on both operands.

`pytest tests/models/step5` on MI325X: 31 passed. The 2 failures (`test_select_regions_breaks_ties_by_region_id`, `test_fp8_kv_block_size_32_initializes`) fail the same way without this change, because the nightly image lacks `_C` ops they need.

## Details

The ROCm prefill indexer called `paged_mqa_logits_sm90`, which bitcasts the packed FP8 bytes to `tl.float8e4nv` (OCP e4m3fn). gfx942 MFMA only takes e4m3fnuz, so Triton upcast both operands to f16 in software before the dot, and this kernel became the main prefill cost at long context.

e4m3fnuz has the same bit layout with an exponent bias one higher, so every finite e4m3fn byte read as e4m3fnuz is exactly half its value. The ROCm kernel reads the bytes as `tl.float8e4b8`, runs the native MFMA and multiplies the FP32 dot by 4.

The one byte that differs is `0x80`, which is -0 in e4m3fn but NaN in e4m3fnuz, so it is mapped to `0x00`. The e4m3fn NaN bytes (`0x7f`, `0xff`) would read as finite values, but quantized Q and summary keys never contain NaN.

The ROCm kernel is `paged_mqa_logits_sm90` plus this branch, so the Hopper path is untouched. The branch is a `tl.constexpr` selected by `current_platform.is_fp8_fnuz()`, so gfx950 compiles the same code as before.

This generates inputs using `torch.randn(...).to(torch.float8_e4m3fn)`, which only produces values around [-4, 4] (Plus the injected 0x80 bytes). That leaves the upper exponent range of e4m3fn (up to max normal ±448.0 at 0x7e/0xfe) completely untested, and only rarely hits subnormal values (0x01..0x07 / 0x81..0x87).

Could we also test the boundary bytes—specifically min subnormal (0x01/0x81), the subnormal/normal boundary (0x07/0x08), and max finite normal (0x7e/0xfe = ±448.0)?

Alternatively, _fp8_bytes could sample across all valid byte patterns since there are only 254 or scale randn so the test exercises the full dynamic range and confirms there are no underflow/overflow or subnormal-flushing discrepancies on gfx942
