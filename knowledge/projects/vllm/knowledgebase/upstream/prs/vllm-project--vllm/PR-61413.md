# [Model] Share the Inkling Triton implementation via inkling/common/

[Upstream PR](https://github.com/vllm-project/vllm/pull/61413) · state: open · merged: False

## Original PR description

## Purpose

  `vllm/models/inkling/` has an NVIDIA implementation built on CuTe/FA4 and
  Lamport P2P, and a Triton implementation under `amd/`. XPU has neither of the
  NVIDIA dependencies, so it currently crashes in `nvidia/ops/lamport.py` on a
  `torch.cuda.get_device_capability()` call.

  The Triton implementation is not AMD-specific - it is plain Triton plus vLLM
  layers. Rather than add platform checks inside an AMD-owned directory, this
  moves it to `inkling/common/`, next to the already backend-neutral
  `mm_preprocess.py` and `towers.py`, and routes both ROCm and XPU to it.
  `inkling/amd/` keeps only the gfx950 Gluon kernels, and `inkling/nvidia/` is
  untouched.

  Platform differences move out of the kernels into `common/platform.py`:

  - `gluon_rel_attention()` offers each relative-attention call to the Gluon
    kernels on ROCm and returns `None` elsewhere, which also removes the stubbed
    `on_gfx950` import guard
  - `num_compute_units()` sizes the persistent Triton grids

  The qkvr K/V branch now runs inline when `aux_stream()` is `None`.

  The first commit is the routing plus portability fixes; the second is the move,
  which is renames plus import paths.

  ## Test Plan

  Kernel parity against the torch reference on Battlemage B70, tensor parallel 1
  and 2, page sizes 16/32/64/128, both the plain and the QK-sensitive scaling:
  attention 432 cases, and qkvr/sconv/norm/gate/SwiGLU 89 cases. End to end, the
  model serves on eight B70 cards at tensor parallel 8 and answers sequential and
  concurrent requests. Behaviour was also compared against the pre-move tree under
  an identical configuration and is byte-identical.

  ROCm is unchanged by construction: the moved files are renames, and the Gluon
  dispatch is reached through the new hook. The ROCm-only tests were updated for
  the new paths but not executed, as that requires CDNA4 hardware.

  ## Test Result

  All 521 kernel parity cases pass. The eight-card run serves and responds; 10/10
  sequential and 8/8 concurrent requests succeed.
