# [Model] Share the Inkling Triton implementation via inkling/common/

[Upstream PR](https://github.com/vllm-project/vllm/pull/61413) · state: open · merged: False

## Original PR description

## Purpose

  `vllm/models/inkling/` has an NVIDIA implementation built on CuTe/FA4 and
  Lamport P2P, and a Triton implementation under `amd/`. XPU has neither of the
  NVIDIA dependencies, so it currently crashes in `nvidia/ops/lamport.py` on a
  `torch.cuda.get_device_capability()` call.

  The Triton implementation is not AMD-specific - it is plain Triton plus vLLM
  layers. Rather than add platform checks inside an AMD-owned directory, this
  moves it to `inkling/common/`, next to the already backend-neutral
  `mm_preprocess.py` and `towers.py`, and routes both ROCm and XPU to it.
  `inkling/amd/` keeps only the gfx950 Gluon kernels, and `inkling/nvidia/` is
  untouched.

  Platform differences move out of the kernels into `common/platform.py`:

  - `gluon_rel_attention()` offers each relative-attention call to the Gluon
    kernels on ROCm and returns `None` elsewhere, which also removes the stubbed
    `on_gfx950` import guard
  - `num_compute_units()` sizes the persistent Triton grids

  The qkvr K/V branch now runs inline when `aux_stream()` is `None`.

  The first commit is the routing plus portability fixes; the second is the move,
  which is renames plus import paths.

  ## Test Plan

  Kernel parity against the torch reference on Battlemage B70, tensor parallel 1
  and 2, page sizes 16/32/64/128, both the plain and the QK-sensitive scaling:
  attention 432 cases, and qkvr/sconv/norm/gate/SwiGLU 89 cases. End to end, the
  model serves on eight B70 cards at tensor parallel 8 and answers sequential and
  concurrent requests. Behaviour was also compared against the pre-move tree under
  an identical configuration and is byte-identical.

  ROCm is unchanged by construction: the moved files are renames, and the Gluon
  dispatch is reached through the new hook. The ROCm-only tests were updated for
  the new paths but not executed, as that requires CDNA4 hardware.

  ## Test Result

  All 521 kernel parity cases pass. The eight-card run serves and responds; 10/10
  sequential and 8/8 concurrent requests succeed.

**The gfx950 Gluon path**

Since this PR moves `amd/ops/gluon` to `amd/gluon`, I also wanted the MI355X runs to exercise those kernels. Three things came up. None of them is caused by this PR:

1. **The default MI355X runs don't use Gluon.** On this model the KV block size resolves to 32, and `use_gfx950_gluon_decode` / `_extend` only accept pages of 64/128/256. The default MI355X numbers above are therefore all Triton. With `--block-size 64`, the Gluon decode kernels are selected.
2. **On Python 3.14, Triton 3.7.1 can't compile them.** `@aggregate` hashes PEP 649's `__annotate__`, which fails with `Unsupported function referenced: <function AttentionConfig.__annotate__>`. This happens on both arms. It's fixed in upstream Triton, and I backported that fix for the runs below.
3. **With Gluon decode under decode graphs, the first request faults in `fused_moe_kernel`, on both arms.** It does not fault with `INKLING_GFX950_GLUON=0` or in eager mode. The cause looks like the empty-row case #62902 fixes on the Triton side. A decode graph replayed for fewer live requests than its size has padding rows with `cache_seqlens = 0`. In `_rel_mha_decode_reduce_fp16`, all splits of such a row are masked, so:
   - `m_i = -inf`, and `beta = exp2(-inf - -inf)` is NaN;
   - the row's output is NaN and reaches the MoE gate.

   A two-line guard in the reduce fixes it:
   ```python
   m_i = max(part_lse, axis=0)
   m_i = gl.where(m_i > -float("inf"), m_i, 0.0)
   ...
   output = acc * gl.where(l_i > 0.0, 1.0 / l_i, 0.0)
   ```
   Rows with at least one split compute exactly what they did before. Results:
   - Graphs + `AMD_SERIALIZE_KERNEL=3` still faults in `fused_moe_kernel`. Eager is clean.
   - With the guard, both arms run cleanly with Gluon and graphs on: gsm8k 0.963 (main) and 0.958 (PR), the full sweep with no failures, and the Gluon decode and extend kernels compiled.
   - The arms are again at parity (one run each):

   | c | tok/s/user main | tok/s/user PR | tok/s/GPU main | tok/s/GPU PR |
   |---|---|---|---|---|
   | 1 | 100.9 | 100.4 | 103 | 102 |
   | 4 | 100.0 | 99.4 | 394 | 388 |
   | 16 | 82.3 | 82.1 | 1179 | 1205 |
   | 64 | 52.2 | 51.3 | 2651 | 2614 |
   | 256 | 21.9 | 21.9 | 3517 | 3496 |
   | 512 | 11.1 | 11.1 | 3078 | 3036 |

One more observation, single runs only. At block 64, Gluon versus `INKLING_GFX950_GLUON=0` is:
- 2–3% faster per user at c ≤ 64;
- slower at high concurrency: 3517 vs 3844 tok/s/GPU at c=256 and 3078 vs 3732 at c=512.

The extend kernel only shows up in the Gluon runs, so that may be the place to look.

None of this is caused by the refactor, so I wouldn't hold this PR for it. I'm happy to send the guard as a follow-up against `amd/gluon/` once this lands, or you can fold it in here, whichever you prefer.
