# [ROCm][Attention] Add VLLM_ROCM_AITER_MLA_USE_FP8_PREFILL to disable the FP8 MLA prefill

[Upstream PR](https://github.com/vllm-project/vllm/pull/61863) · state: open · merged: False

## Original PR description



## Overview
Adds `VLLM_ROCM_AITER_MLA_USE_FP8_PREFILL` (default `true`). Setting it to `0` disables the gfx950 FP8 asm MLA prefill, so prefill runs through the bf16 flash-attention path instead. Default behavior is unchanged.

## Claims
- Opt-out only; FP8 asm prefill stays the default where supported.
- Kimi-K2.6-MXFP4 TP8 on MI355X: the bf16 path is ~8-9% faster per prefill step and ~8.6% lower TTFT, with equal GSM8K accuracy.
- End-to-end latency is not a reliable discriminator at 1,024 output tokens; see the note below.

## Validation
Kimi-K2.6-MXFP4, TP8, MI355X. `vllm bench serve`, random 1024/1024, 64 prompts, concurrency 64, `--ignore-eos --temperature 0 --request-rate inf`.

Client-side, no profiler attached:

| Metric | FP8 asm prefill (default) | bf16 (`VLLM_ROCM_AITER_MLA_USE_FP8_PREFILL=0`) |
|---|---|---|
| Mean TTFT | 934.70 ms | 854.10 ms (−8.6%) |
| Mean TPOT | 14.80 ms | 14.50 ms |
| Mean E2EL | 16,079.61 ms | 15,684.85 ms |
| Total token throughput | 8,144.80 tok/s | 8,347.46 tok/s |

Same workload under the torch profiler, rank-0 kernel sums:

| Metric | FP8 asm prefill | bf16 |
|---|---|---|
| Prefill step, 31,745 prompt tokens + 32 decode rows | 531.9 ms | 489.0 ms (−8.1%) |
| Prefill attention core, per layer | ~880 µs | ~155 µs |
| Prefill MoE layer total | 8,701 µs | 8,005 µs |
| Decode step, average | 14.45 ms | 14.71 ms |
| Mean TTFT | 954.7 ms | 873.7 ms |

GSM8K 5-shot, flexible / strict:

| FP8 asm prefill | bf16 |
|---|---|
| 0.9333 / 0.9333 | 0.9303 / 0.9310 |

**On end-to-end numbers.** The prefill difference is ~81 ms of a ~15.7 s request at 1,024 output tokens, about 0.5% of E2EL, and it reproduces across runs (+80.6 ms and +81.0 ms for FP8 in two separate runs). TPOT does not reproduce: it came out 0.30 ms against FP8 in the run above and 0.24 ms in its favor in the profiled run, a ~2% swing either way. That swing lives entirely in the decode MoE GEMMs — the two paths generate different (equally valid) tokens, so each decode step touches a different number of experts. Since the decode noise is roughly four times the prefill share of E2EL, the E2EL column can flip sign between runs and should not be read as a property of the prefill path. TTFT and the per-step prefill kernel sums are the numbers that isolate this change.

## Details
At 8 heads per rank the FP8 path pads q/k/v to 16 heads (~355 µs), casts them to fp8 (~156 µs), and runs the asm kernel plus its reduce (~345 µs) and the copies back; flash attention does the same work in ~155 µs. FP8 prefill was added to avoid the bf16 working set at very long context (#51040), so it stays the default and this only provides a way to opt out on shapes where the padding overhead dominates.

No duplicate: no open issue or PR adds a way to turn off the FP8 prefill path.
