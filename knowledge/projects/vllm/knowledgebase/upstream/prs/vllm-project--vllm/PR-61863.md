# [ROCm][Perf][Attention] Keep the bf16 attention prefill when FP8 padding would double the heads

[Upstream PR](https://github.com/vllm-project/vllm/pull/61863) · state: closed · merged: True

## Original PR description

## Overview
The gfx950 FP8 asm MLA prefill needs 16-aligned heads, so smaller per-rank head counts are padded up to 16. At 8 heads per rank (Kimi-K2.x at TP8) that doubles the kernel's work, and the asm kernel plus its split-tile reduce end up ~2x slower per layer than the bf16 flash-attention prefill. This PR adds `AiterMLAHelper.is_valid_fp8_prefill_num_heads`, which rejects head counts that padding would at least double (1-8 per rank), and uses it in the two places that enable the FP8 prefill. Those counts go back to bf16 flash attention; 9-15 (e.g. Kimi-K3 at TP8, 12 heads) and 16+ are unchanged. Decode still uses `is_valid_num_heads`, so nothing changes there.

#51040 extended the FP8 prefill to smaller head counts for Kimi-K3, whose ranks hold 12 heads at TP8. Its new gate reused the decode head-count predicate, which also accepts counts that divide 16, so Kimi-K2.x at TP8 (8 heads per rank) moved onto the padded FP8 path as a side effect, on a shape the change wasn't tuned or measured for. For Kimi-K2.x at TP8 this PR restores the earlier prefill path:


| | FP8 prefill gate | Kimi-K2.6 TP8 prefill (8 heads/rank) |
|---|---|---|
| Before #51040 | `num_heads % 16 == 0` | bf16 flash attention |
| After #51040 (current main) | `is_valid_num_heads` (pads up to 16) | FP8 asm, padded 8 → 16 heads |
| This PR | `is_valid_fp8_prefill_num_heads` | bf16 flash attention |

## Claims
- Kimi-K2.6-MXFP4 TP8 on MI355X, current main (including #59634's fused q/k/v prep): prefill attention 442 → 213 µs per layer, −14.0 ms on a 31,745-token prefill step and −25.1 ms on a single 1,024-token prefill; mean TTFT −7.9%.
- Only per-rank head counts of 1-8 change; decode is untouched.

## Why the FP8 path is slower at 8 heads per rank
Per-layer prefill attention on the 31,745 prompt tokens + 32 decode rows step, rank-0 kernel sums from the torch profiler:

| Step | FP8 asm path (main) | bf16 path (this PR) |
|---|---|---|
| q/k/v prep | 76.9 µs (`_fused_mla_prefill_qkv_fp8`: k concat, pad 8 → 16 heads, fp8 cast) | 87.4 µs (k concat and copies) |
| Attention kernel | 170.0 µs (`mla_pfl_qh192_vh128_m32x8_n128x1_causal1`, 16 heads; half the output is padding) | 125.1 µs (`gqa_d192_v128_kernel`, 8 heads) |
| Split-tile reduce | 164.0 µs (`kn_mla_reduce_v1_ps<128,16,1>`) | — |
| Copies | 30.8 µs | — |
| **Total per layer** | **441.7 µs** | **212.5 µs** |

#59634 cut the prep cost (previously ~560 µs of padding copies and casts), but the asm kernel at twice the heads plus its reduce still cost more than flash attention on its own. The reduce's cost also depends heavily on the batch shape:

| Prefill step | Reduce, per layer | bf16 attention path | FP8 attention path | Saved by this PR |
|---|---|---|---|---|
| 1,024 tokens, 1 request | 425 µs | 3.4 ms | 28.4 ms | 25.1 ms |
| 32,767 + 1 | 4 µs | 13.4 ms | 17.2 ms | 3.8 ms |
| 31,745 + 32 | 164 µs | 13.0 ms | 27.0 ms | 14.0 ms |

## Validation
Kimi-K2.6-MXFP4, TP8, MI355X, `--kv-cache-dtype fp8`, `VLLM_ROCM_USE_AITER=1` (the backend resolves to `ROCM_AITER_MLA` with or without `--attention-backend`). This branch rebased on main, so the two runs differ only in Python files. `vllm bench serve`, random 1024/1024, concurrency 64, `--ignore-eos --temperature 0 --request-rate inf`.

| Metric | main (FP8 asm prefill) | This PR (bf16 prefill) |
|---|---|---|
| Mean TTFT, 256 prompts, no profiler | 849.01 ms | 782.15 ms (−7.9%) |
| Median TTFT, 256 prompts, no profiler | 636.54 ms | 614.13 ms (−3.5%) |
| P99 TTFT, 256 prompts, no profiler | 1,165.51 ms | 1,116.27 ms (−4.2%) |
| Mean TTFT, 64 prompts, profiled run | 952.50 ms | 914.19 ms (−4.0%) |

TPOT and E2EL are left out on purpose: on current main the FP8 run produces wrong output (see the note below), which changes MoE routing during decode, so its decode timings aren't comparable.

GSM8K 5-shot, flexible / strict:

| main (FP8 asm prefill) | This PR (bf16 prefill) |
|---|---|
| 0.0281 / 0.0235 | 0.9439 / 0.9431 |

Tests: `pytest -v tests/kernels/attention/test_rocm_aiter_mla_head_padding.py tests/kernels/attention/test_rocm_aiter_mla_fp8_prefill.py` on MI355X: <fill in>. The new `test_fp8_prefill_rejects_head_counts_padding_doubles` needs no GPU; it checks that 1-8 heads are rejected for FP8 prefill but still valid for decode, and that 9, 12, 15, 16, 24, 32, 64, 128 and 144 keep FP8 prefill.

## Note on accuracy on current main
Separately from performance, FP8 prefill output on current main is wrong for 8 heads per rank. #59634's fused prep pads heads by tiling (padded head h = real head h % 8), while `_mla_fp8_prefill_attn` unpads divisor counts at stride `nhead // num_heads`, which matches `repeat_interleave` padding. Only head 0 ends up in the right place, hence the GSM8K score above. Before #59634, with the unpad fix in place, the FP8 path scored 0.9333 / 0.9333, so the performance argument above doesn't depend on the bug. This PR keeps 8 heads off that path but does not change the unpad itself, which is still inconsistent with the fused prep for head counts that divide 16. On main, Kimi-K2.x TP8 users can currently avoid it only by changing the KV cache dtype or the decode backend.

## Details
`is_valid_num_heads` itself is not changed because `check_num_heads_validity` asserts it in the `AiterMLAImpl` constructor and in the sparse MLA backend; rejecting 8 heads there would refuse to start the backend instead of falling back. The new predicate is a prefill-only check on top of it. Head counts of 1-7 per rank were not measured; padding costs them at least 2x the work as well, and they were also on bf16 prefill before #51040.

No duplicate: no open issue or PR changes the FP8 MLA prefill head-count gate. #59124 (open) adds a separate opt-in FlyDSL FP8 prefill.
