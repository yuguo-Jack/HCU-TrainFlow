# [Bugfix][ROCm][MoE] Fix tkw1 metadata check, rename AITER QuantMethod

[Upstream PR](https://github.com/vllm-project/vllm/pull/65517) · state: open · merged: False

## Original PR description



## Overview

Follow-up to #63204 (part of #54966 item 5), addressing its post-merge review comments.

## Claims

- **Fix:** `AiterFp8ChannelExperts` again accepts expert-token metadata without token counts on the tkw1 route (e.g. DeepEP v2 under CUDA graphs). #63204 made the check reject any metadata; it now only rejects metadata with counts, as before. ([comment](https://github.com/vllm-project/vllm/pull/63204#discussion_r4447566182))
- **Rename:** `QuantMethod` → `AiterQuantType` (plus `_AITER_QUANT_TYPE`, `quant_type=`, `derive_aiter_quant_type()`), since "quant method" means the weight-loading quantization classes in vLLM. ([comment](https://github.com/vllm-project/vllm/pull/63204#discussion_r4447852851))
- **Removal:** `ActivationMethod`. It only named SILU/GELU; every activation now resolves via `rocm_aiter_ops.get_aiter_activation_type()`, as SWIGLU/SITU already did. ([comment](https://github.com/vllm-project/vllm/pull/63204#discussion_r4447841385))
- No numerical change intended.

## Details

- The new test compares tkw1 output with and without count-free metadata at `rtol=atol=1e-2`: the tkw1 kernel itself differs by ~1 bf16 ulp run to run.
- The enum-value test now checks `AiterQuantType` against `aiter.QuantType` rather than literals, so drift from AITER is caught.
- The mirror enum is kept because subclasses declare `_AITER_QUANT_TYPE` at class definition, in a module imported where AITER isn't installed.
- Raw custom-op tests now pass AITER's own `ActivationType`/`QuantType`.
- `rocm_aiter_ops` custom-op argument names (`quant_method: int`) are unchanged. Out-of-tree callers of `rocm_aiter_fused_experts` must rename `quant_method=` to `quant_type=`.
- Not a duplicate: no open PR touches these names or the tkw1 check.
