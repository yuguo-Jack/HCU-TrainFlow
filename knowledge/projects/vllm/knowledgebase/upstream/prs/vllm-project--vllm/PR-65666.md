# [Kernel][LoRA][MoE] Skip zero intermediate rank tiles in fused MoE LoRA expand

[Upstream PR](https://github.com/vllm-project/vllm/pull/65666) · state: open · merged: False

## Original PR description



## Overview

Record zero intermediate rank tiles in MoE LoRA shrink and skip their expand
dot products when the physical rank is padded beyond the adapter's effective
rank. The A100 non-TMA and H100 TMA paths are separate opt-in flags.

This extends the rank-256 two-kernel fallback introduced by #55161 for
#55158. No open PR was found for this zero-tile mask. #64746 changes
two-kernel tile selection rather than masking intermediate tiles; note that
its proposed default tiles (expand BK=32, shrink BN up to 64) do not satisfy
this patch's `BK = 2 x BN` gate, so the two changes would need to be
reconciled if it lands first. #64748 removes a small-batch kernel and does not
implement this mask.

## Claims

- For eligible sorted, one-slice, split-K=1 calls, shrink writes a per-rank-tile
  nonzero mask and expand can skip zero tile loads and dots.
- Both flags default to off and are restricted to SM 8.0 non-TMA or SM 9.0 TMA.
- The unchanged fallback handles other tile layouts, fully-sharded LoRA,
  multiple slices, and unsupported architectures.

## Details

`max_lora_rank=256` sizes both LoRA weight storage and the shrink/expand
intermediate even if the loaded adapter rank is small. The existing expand
kernel still multiplies the zero-padded rank range. Shrink now writes one byte
per intermediate rank tile; the non-TMA expand path reads two bytes per rank
chunk, while TMA uses the final tile as a quick dense-path sentinel and checks
mask bytes when it is zero. The mask is allocated only for compatible tile
sizes and layouts, with one writer per byte. The current design assumes
finite activations and weights: skipping `0 × NaN/Inf` changes nonfinite
propagation. H100 true rank 256 regressed by 0.5–2.5% in prototype operator
timings, so the flags remain opt-in.

Open #64746 proposes expand BK=32 and shrink BN up to 64, while this patch
requires BK=2×BN. The mask would not activate under those defaults. A
generalized mapping needs new benchmarks and correctness checks.

### When the mask activates

The gate requires `expand_block_size_k == 2 * shrink_block_size_n`, with both
`BLOCK_SIZE` values coming from the MoE tile config:

- shrink `BLOCK_SIZE_N = min(moe_block_n, next_power_of_2(rank))`
- expand `BLOCK_SIZE_K = max(16, min(moe_block_k, next_power_of_2(rank)))`

`try_get_optimal_moe_lora_config` (`lora/layers/utils.py:122,131`) derives both
from `try_get_optimal_moe_config`, which passes the tuned per-model JSON values
through. Shipped A100 tables carry `BLOCK_SIZE_K` values of 64/128/256, so a
model whose config has `BLOCK_SIZE_N=64, BLOCK_SIZE_K=128` yields shrink BN=64
and expand BK=128 at rank 256, and the mask activates.

The path is therefore reachable with stock configs, but only for tile layouts
where `moe_block_k == 2 * min(moe_block_n, next_power_of_2(rank))`. Two follow-ups
worth documenting:

- The LoRA feature page should state what tile layout the flags need, rather
  than implying they apply to A100/H100 rank-256 serving in general.
- The `get_lora_op_configs` path (`utils.py:239,253`, used with
  `VLLM_TUNED_CONFIG_FOLDER`) clamps to shrink BN=64 / expand BK=32, so the mask
  is inactive there. A generalized mask index would remove the constraint.

A masked-path hit rate for at least one real model/config would show the
optimisation is reachable in practice.
