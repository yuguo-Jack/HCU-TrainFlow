# [ROCm][Perf][GLM-5.3-Flash] Mono decode layer for GLM-5.3-Flash on MI355X

[Upstream PR](https://github.com/vllm-project/vllm/pull/61662) · state: open · merged: False

## Original PR description

## Purpose

Opt-in (`--monokernel`) MonoKernel decode for GLM-5.3-Flash (`amd/GLM-5.3-Flash-Quark-MXFP4`) on MI355X (gfx950), in the shape RFC #60904 proposes. Each MoE decoder layer of a decode step is one persistent FlyDSL launch (256 CTAs):

| Launch | Layers | Stages |
|---|---|---|
| KDA layer | 30 of the 41 MoE layers | attention-side mHC seam, in-projections, short conv, KDA gates and recurrence, gated norm, o_proj and its TP reduce, FFN mHC seam, RMSNorm, router, top-8, shared expert and MXFP4 experts, MoE TP reduce |
| Sparse-attention layer | the other 11 | attention-side mHC seam, fused q_a / kv_a, q norm, KV and kpool index-cache writes, q_b, the indexer query (FWHT-128 + FP8), W_UK, pool scoring and top-2048 selection, split attention, W_UV, o_proj and its TP reduce, then the same FFN half |

A decode step issues 220 kernels instead of 1,699 (TP4, 4 rows), and its time between tokens drops 29–45% at TP8, concurrency 1–8; GSM8K is at least at parity at TP8 and TP4.

**Scope**
- **Layers:** the 41 MoE layers 3–43. The dense layers 0–2 and layer 44, whose mHC post contracts the streams, run vLLM's code.
- **Steps:** pure decode, 1 token a request, widths 2 / 4 / 8 at TP4 and TP8, 2 / 4 at TP2 (wider steps there are slower than vLLM's path). FULL graphs (vLLM resolves this model's default to FULL_DECODE_ONLY) or eager.
- **Everything else** runs vLLM's layers unchanged: prefill, mixed and wider steps, PIECEWISE replays. Kernel and vLLM layers take and return the same `(hidden, residual, post, comb)`, so they interleave freely.

### Layout

```
vllm/models/common/mono/          RFC #60904's shared runtime (849 lines)
    spec.py      MonoSpec, LayerKernel, MonoStep, MonoContext, Feature
    guards.py    configure, config-stage refusals (default-deny), graph-mode checks
    layer.py     attach, forward_layer, after_step, health
    routing.py   per-step decision, cache re-binding on (data_ptr, numel)
    failstop.py  error-word health check, fail-stop, VLLM_MONO_UNSAFE_WARN
    peer.py      symmetric peer buffers
    abi.py       error-word and fault-hook layout
vllm/models/glm5next/amd/mono/    the model's spec (885 lines)
    spec.py      MONO_SPEC, geometry and config refusals, declared numerics
    weights.py   weight views and their checks
    kernel.py    model refusals, cache binding, eligibility, build per width, launch
vllm/models/glm5next/amd/ops/mono/  kernel source (4,174 lines; ffn/kernel.py 3,155)
vllm/models/glm5next/common/model.py  the hook (+16 lines)
```

`ops/mono/{ops,layout}.py` and `ffn/{kernel,layout}.py` are adapted from ROCm/aiter#6173 at c39b56c36 (Apache-2.0). Each names its origin. The changes from aiter:
- GLM-5.3-Flash's layer kinds: the KDA path and the sparse-attention path with the kpool indexer, both new;
- the mHC seams of this model, FP8 block-128 or bf16 per attention projection (vLLM loads the checkpoint's FP8 q_a / kv_a as bf16);
- bounded waits with per-stage error words and an early out after the first expiry, so a stalled peer stops the engine with the kernel's error rather than an RPC timeout;
- 64-bit cache-block bases: the caches sit in a ~248 GB pool.

### Design

- **Weights** are views of vLLM's loaded tensors, no second copy. Every view is checked for shape, dtype and sharding at attach and raises on a mismatch. The routed experts stay in AITER's MXFP4 layout, and any other MoE backend is refused.
- **Path selection** is plain Python (the model is not torch.compiled), decided once per step for all kernel layers from metadata every rank holds alike: pure decode, a built width, the spec's eligibility. Under FULL graphs it is baked in at capture. PIECEWISE captures are declined, since they replay mixed batches.
- **Caches** are re-bound whenever a cache tensor's `(data_ptr, numel)` changes, because memory profiling runs real steps on throwaway caches first.
- **Refusals** run at config, after load and at every bind, and report every reason at once. Default-deny on PP, DP, EP, EPLB, DCP, PCP, LoRA, KV connectors, routed-expert capture, speculative decoding, sleep mode, CPU weight offload, weight updates, prompt embeds and EAGLE3 aux layers. The spec adds: gfx950 only, TP 2/4/8, bf16 KV cache, an fp32 KDA recurrent state, no sequence-parallel MoE, the exact model geometry.
- **Failure modes.** Every cross-CTA and cross-rank wait is bounded. An expired wait sets its stage's error word; after each step the health check reads them, and the output rank raises with the stage names while the other ranks exit their workers. `VLLM_MONO_FAULT_INJECT` stalls a chosen rank at a chosen step for the fault test.
- **Numerics** that differ from vLLM's path are listed in the spec and logged at startup. All are at least as precise as vLLM's: expert inputs MXFP8 (vLLM MXFP4); the FP8 attention projections on bf16 activations (vLLM: FP8 per 128); W_UK / W_UV in bf16 from `kv_b_proj` (vLLM: AITER FP4 / FP8 BMM). The attention TP reduce and the split-attention partials are summed in bf16.
- **Dependencies:** the `flydsl` wheel and AITER helpers this path already uses (`aiter.ops.flydsl.kernels.buffer_ops`, `dpp_utils`, `aiter.ops.shuffle`).

## Test Plan

- `pytest tests/models/common/mono` (CPU, wired into the existing models CPU job): refusals reported at once and default-deny, graph modes, routing at every width against mixed / prefill / over-width / PIECEWISE / profiling steps, the decision on every simulated rank, cache re-binding, fail-stop on the output rank and the others, `VLLM_MONO_UNSAFE_WARN`, the fault spec.
- `pytest tests/models/glm5next/amd_mono/test_flash_spec.py` (CPU, the GLM5Next job): model refusals, width caps per TP, layer kinds, FP8 / bf16 projection views rejecting every other format, sparse-attention weight checks, the per-step row table.
- New CI step "(MI355) GLM-5.3-Flash Mono Decode Kernel" (4 × MI355): `test_flash_{ffn,kda,dsa}_kernel.py` check each stage against vLLM's own ops (the mHC op, the KDA conv / recurrent / norm kernels, the kpool and FWHT-quant kernels, the MLA attention) at widths 2/4/8, then capture every width in one graph and replay 300 times, bit for bit against the first run. `test_flash_moe_vllm.py` builds vLLM's real `Glm5NextMoE` from random weights in checkpoint layout through `process_weights_after_loading` and compares. `test_stalled_rank_reports_expiry` stalls one rank in the kernel and expects the error words.
- Compile-only build (`COMPILE_ONLY=1 ARCH=gfx950`) of every launch kind at every width and TP.
- GSM8K: full 1,319, 5-shot, strict match, greedy, 3 runs a path on the same node and day, paired McNemar, TP8 and TP4; 250 questions at TP2.
- Long context: NIAH, 10 needles at each of 32K, 64K and 120K (128K is the served maximum), TP8.
- Sanity per RFC #60904: 50 bare-completion prompts, greedy, first 8 tokens, each server run twice.
- Performance: `vllm bench serve`, graphs against graphs, same batch cap (`--max-num-seqs 256`), bf16 KV cache. Median ITL per width at 512 and 32K tokens of context, median TPOT at 8K in / 256 out, c1–c8 at TP8 / TP4 / TP2; a profiled decode step; cold and warm startup.
- Fault injection in a server: rank 1 stalls 120 s at kernel step 300 under load, TP4 and TP8.

## Test Result

**Unit:** 45 CPU tests pass (rebased build). **Kernel CI step:** passes at TP2, TP4 and TP8 on idle GPUs (rebased build). On a shared node, where another container ran a GEMM tuner on some of the same GPUs, the two sparse-attention `mixed` cases reported an expired wait; see the co-tenancy note below. **Compile-only:** every launch kind builds.

**MoE against vLLM's `Glm5NextMoE`** (random weights): relative error against an fp32 MoE on the dequantized weights and unquantized inputs is 0.044–0.048 for the kernel and 0.211–0.257 for vLLM, whose MoE quantizes expert inputs to MXFP4; routing identical. TP2, TP4 and TP8.

The pre-rebase build measured the same points within 1%, except vLLM at TP4 c8 (11.92 ms then, 12.58 ms now) and vLLM at TP2 c4 (13.22 ms then, 12.70 ms now).

**Startup** (TP4, checkpoint already in the page cache, rebased build): 661 s → 707 s; the 46 s is the FlyDSL compile of 2 launch kinds × 3 widths, which a kept FlyDSL cache skips.

**Fault injection** (pre-rebase build): at TP4 and TP8 every rank logs `GLM-5.3-Flash MonoKernel rank N: expired waits in <stages>; tokens of the affected steps are wrong`, the workers stop, the container exits and no GPU memory stays held. Without the early out the engine still stopped, but on vLLM's 300 s `sample_tokens` RPC timeout.

**Co-tenancy.** The kernel needs every compute unit of its GPU. A TP8 server on the rebased build that shared GPUs 4–7 with another user's GEMM tuning job stopped during GSM8K: ranks 4, 5 and 7 reported expired waits, the fail-stop raised the MonoKernel error and the engine exited, with no hang and no tokens served from the failed step. The same build on an unshared node ran 3 full GSM8K passes with no expiry. Detecting a co-tenant at startup is RFC #60904's open question 3; this PR only documents it.

**Provenance of the numbers.** All on MI355X. *Rebased build:* this PR's head on the `nightly-77154ca6` ROCm image (45 commits behind main), AITER `v0.1.25`, with #50535, #59478 and ROCm/aiter#6435 / #6436 (router-GEMM and fused-MoE tuning for this model) in both arms; the kernel tests, the rebased GSM8K rows, ITL, TPOT and startup come from it. *Pre-rebase build:* the same kernels on the week-41 nightly with AITER `main` at the time (`0.1.25.dev181`), the same four PRs, and the switch still an env var; NIAH, sanity, the profile, the fault runs and the pre-rebase GSM8K rows come from it. The code changes since are the switch, the refusal of a bf16 KDA recurrent state, and CI.
