# [Bugfix][Core] Keep scheduling paused on a tagless wake from level-2 sleep while the weights are incomplete

[Upstream PR](https://github.com/vllm-project/vllm/pull/65326) · state: open · merged: False

## Original PR description

## Overview

After level-2 sleep, a `wake_up()` without tags resumed scheduling as soon as the memory was reallocated, so requests queued during sleep ran before `reload_weights`, returning output computed from the discarded weights, with HTTP 200. Fixes #65325.

## Claims

- Level-2 sleep marks the target weights incomplete in the worker, through the existing `has_incomplete_weight_update` state; `reload_weights` clears it, as `finish_weight_update` already does.
- A tagless `wake_up()` that finds the weights incomplete keeps scheduling paused and returns not fully awake. After the reload, `wake_up()` again resumes; queued requests then return correct output.
- Unchanged: level-1 wakes, tagged wakes (`weights` then `kv_cache`, the RL pattern), and checkpoint restore. `wake_up(tags=["scheduling"])` resumes when the weights were restored some other way; documented in `docs/features/sleep_mode.md`.
- `is_inference_ready()` now reports not ready between level-2 sleep and the reload.

## Details

**Root cause.** `EngineCore.wake_up` resumes scheduling once `model_executor.is_sleeping` is false, i.e. once all memory is resident. After level-2 sleep that memory holds no weights until the caller reloads them, and requests queued while asleep are scheduled in between.

**Fix.** The worker already tracks incomplete weights for weight updates (`_incomplete_weight_updates`, read by `is_inference_ready`). Level-2 sleep adds the target model to it and `reload_weights` removes it. `EngineCore.wake_up` checks it before resuming on a tagless wake. The draft model is not marked: discarded draft weights lower acceptance but do not change the output.

**Why only tagless wakes.** Tagged wakes already let the caller order "wake weights, load, wake KV cache", and RL frameworks load weights there through their own `collective_rpc` callables, which do not clear the state; gating them would leave those engines paused.

**Behavior change.** A caller that does a tagless wake and then `reload_weights` must call `wake_up()` once more (or use the stepwise wake, as the docs show). Before, its queued requests ran on discarded weights. A warning at the held wake says so.

Related: #29341 (level-2 gibberish, closed as no reload), #48310 (RL sleep/wake correctness RFC), #63870 (separates liveness from inference readiness), #64184 (reject resume while memory is asleep).
