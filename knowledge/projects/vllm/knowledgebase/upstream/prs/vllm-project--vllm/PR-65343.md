# [Bugfix][Core] Bound local RPC ring-slot wait by deadline

[Upstream PR](https://github.com/vllm-project/vllm/pull/65343) · state: open · merged: False

## Original PR description

## Overview

Pass the remaining `collective_rpc` deadline to the local shared-memory
broadcast queue's slot acquisition. Fixes #65342.

## Claims

- When the local writer ring is full, a timed RPC no longer waits indefinitely
  for a slot: it raises an RPC-specific `TimeoutError`.
- Calls with `timeout=None` retain unbounded slot-waiting behavior.

## Validation

Focused tests ran on WSL with Python 3.12.16 and CPU PyTorch 2.14.0, with
the root `tests/conftest.py` and normal plugin autoload enabled. The equivalent
command below uses `VLLM_PYTHON` for the isolated environment's Python:

```bash
CUDA_VISIBLE_DEVICES="" VLLM_TARGET_DEVICE=cpu VLLM_LOGGING_LEVEL=ERROR \
PYTHONDONTWRITEBYTECODE=1 PYTHONPATH="$PWD" "$VLLM_PYTHON" -m pytest -q \
  -p no:cacheprovider \
  tests/v1/executor/test_multiproc_executor.py::test_model_rpc_uses_execute_model_timeout \
  tests/v1/executor/test_multiproc_executor.py::test_collective_rpc_without_timeout_does_not_limit_enqueue \
  tests/v1/executor/test_multiproc_executor.py::test_collective_rpc_passes_remaining_timeout_to_enqueue \
  tests/v1/executor/test_multiproc_executor.py::test_collective_rpc_wraps_enqueue_timeout
```

Result: **7 passed, 1 warning** (the generated `vllm._version` module was
absent). In a separate pytest process, a local plugin substituted the exact
parent-commit `collective_rpc` method into the PR checkout after collection:
**6 failed, 1 passed**. This compares the method, not a fully built parent
checkout. Failures included missing enqueue timeouts and missing RPC error
context; the unbounded case still passed.

A separate CPU-only harness used the real Git-source `MessageQueue`,
`EngineCore.step_with_batch_queue`, and RPC methods with synthetic scheduler
and executor objects. In a six-batch window with a 10-slot ring and a
deliberately stalled reader, the parent remained blocked after 0.65 s; this
patch raised `TimeoutError` after 0.2001 s with a 0.2 s deadline. Both a reader
that consumed no messages and one that consumed the first message were tested.
The ring used 4096-byte slots and synthetic small payloads; no actual PP6
engine, model, or worker processes were run. An earlier one-slot harness also
checked unbounded waiting, a successful queue round trip, and a shared
enqueue/response deadline. These harnesses stub unrelated imports and are not
end-to-end serving tests.

**Follow-up (review feedback):** with `VLLM_USE_SPINLOOP_EXT=1`, `acquire_write()` could spin up to `SPINLOOP_TIMEOUT_SECONDS` (100 ms) before checking a shorter deadline. The extension spin is now capped at the remaining budget and skipped once the budget is `<= 1e-9`, which `csrc/spinloop.cpp` would otherwise treat as unbounded. With the real extension compiled, a full ring, CPU only and seven runs per budget, median overshoot dropped from 90.06 ms to 0.057 ms for a 10 ms budget and from 50.05 ms to 0.093 ms for a 50 ms budget. The new `test_writer_spinloop_respects_remaining_timeout` has 7 failures on the parent commit and passes 21/21 with this change.
Ruff lint/format, Python AST parsing, and `git diff --check` passed. Full CI
and end-to-end serving validation have not run. The current unit tests use
test doubles and need review against `tests/AGENTS.md`'s real-object guidance.


## Details

The deadline was already applied when reading responses, but not when waiting
for an outbound ring slot. This change only bounds that local slot wait:
payload serialization and ZeroMQ overflow or remote sends are not bounded by
this patch. It does not claim to fix a separate observed production
reader-side stall or its underlying cause.

**Related work:** #65133 wakes blocked writers when shutdown is explicitly
invoked; it does not propagate an RPC deadline. #59388 resizes worker
**response** rings for in-flight batches, rather than passing a deadline to
the outbound RPC ring. Merged #41357 clamps stale **response** timeouts.
Upstream main at `2173d7121fc6e8d756c884f46691546c61b60c57` still called
outbound `enqueue` without a timeout.

preparation. The submitter has reviewed every changed line. The tests and
measurements above were run in AI-assisted environments.

File: `vllm/v1/executor/multiproc_executor.py` · line 497

Good catch, thanks. Fixed in 15aaa1319f.

`acquire_write()` now passes `min(SPINLOOP_TIMEOUT_SECONDS, remaining)` to the extension. One subtlety: `csrc/spinloop.cpp` treats `timeout <= 1e-9` as unbounded (`have_timeout = timeout > 1e-9`), so the writer skips the extension call once the remaining budget reaches that threshold and falls through to the existing `TimeoutError` path. `timeout=None` behaves exactly as before.

Verified against a full ring with the real extension (`csrc/spinloop.cpp` compiled, `VLLM_USE_SPINLOOP_EXT=1`, CPU-only, seven runs per budget). Median enqueue overshoot past the deadline:

| budget | before | after |
|---|---|---|
| 10 ms | 90.06 ms | 0.057 ms |
| 50 ms | 50.05 ms | 0.093 ms |

I also added `test_writer_spinloop_respects_remaining_timeout` to `tests/distributed/test_shm_broadcast.py` (full ring, budgets `None`, negative, 0, 1e-10, 1e-9, 10 ms, 50 ms and 200 ms). With the native extension loaded, the parent commit has 7 failures (all finite-budget cases) and this commit passes 21/21.

The reader path (`_wait_until_readable`) still uses the pre-existing 100 ms spin granularity for read timeouts. I left it unchanged to keep this PR scoped to the writer-side deadline.
