# [Frontend] Support cross-machine snapshot (step 1: portable attachments)

[Upstream PR](https://github.com/vllm-project/vllm/pull/61544) · state: open · merged: False

## Original PR description

# Purpose

This PR extends the snapshot feature ([https://github.com/vllm-project/vllm/pull/51360](https://github.com/vllm-project/vllm/pull/51360)) from inplace checkpoint/restore to cross-machine checkpoint/restore. The goal is fast startup for auto-scaling scenarios.

## WHAT

Making snapshots work across machines requires solving at least the following problems:

*   Package all intermediate files generated during vllm startup, such as the triton jit cache.

    Some of these files are currently open/mapped by vllm; others may be used later. They must be carried over to the new machine, so the process can still find them after restore.

*   Support cuda device map.

    GPU device uuids change on the new container, so we need to tell cuda-checkpoint how the old uuids map to the new ones.

*   Handle ip changes.

    The new container gets a different ip. Any TCP connections recorded in the snapshot must be re-established on the new ip, and any connections vllm makes afterwards must use the new ip as well.

*   Avoid pid conflicts.

    In the new container, running the vllm snapshot restore cli imports libraries such as cuBLAS, which can start threads before criu restore runs. Those threads may occupy pids that criu restore needs. Nothing currently prevents this conflict; a solution is needed, for example setting `kernel.ns_last_pid`.

This PR is the first step: it packages the intermediate files so they can travel with the snapshot, and introduces the following:

1.  A new `--portable` flag.

    It marks the snapshot as portable, i.e. for cross-machine use. Making this explicit keeps inplace checkpoint/restore free of the extra overhead (inplace does not need to package intermediate files).

2.  A new `--work-dir` argument.

    It specifies where the snapshot feature keeps its own control files (ready.json/release.json) and runtime logs.

    In the cross-machine case, the snapshot may live on a shared filesystem such as NAS, or be mounted read-only. Writing control files and logs into the snapshot dir is then unsafe: multiple instances restoring from the same snapshot would race on them, and on a read-only mount the writes would simply fail.

3.  A new attachments directory.

    Intermediate files produced during vllm startup are archived under the attachments directory, so the process can still access them after restore.

    To bound the archive size in abnormal cases, the per-file and total size limits are configurable through environment variables (default 1G):

    *   `VLLM_SNAPSHOT_ATTACHMENT_MAX_FILE_BYTES`

    *   `VLLM_SNAPSHOT_ATTACHMENT_MAX_TOTAL_BYTES`

## Related Work

Several container-level snapshot solutions already exist:

*   [dynamo snapshot](https://github.com/ai-dynamo/snapshot)

*   [llm-d snapshot-orchestrator](https://github.com/llm-d/llm-d/issues/2365)

They all operate outside vllm, at the container level. They rely on plugins, monkey patches, and similar means to modify vllm's behavior — keeping vllm out of states that criu cannot checkpoint/restore, and fixing things up after restore. None of them is transparent to vllm.

This PR instead builds snapshot support natively into vllm. That gives us 1) finer-grained control over vllm's internal state, and 2) code that evolves with vllm, which makes it easier to maintain.
