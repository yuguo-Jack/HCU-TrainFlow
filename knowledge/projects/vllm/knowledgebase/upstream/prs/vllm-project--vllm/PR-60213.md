# [Metrics][Frontend] Expose request render duration metric

[Upstream PR](https://github.com/vllm-project/vllm/pull/60213) · state: closed · merged: True

## Original PR description

## Overview

We're not tracking pre-processing/rendering time, interesting to spot tokenization bottlenecks, which can be a good signal when to switch to disagg renderer (cc @nt591 who authored).

Adds a `vllm:request_render_duration_seconds` Prometheus histogram measuring the full request render stage — chat templating, tokenization, and multimodal preprocessing — at the shared `OnlineRenderer` boundary, which serves both `/render` (scale-out / disaggregated) and ordinary `/v1/chat/completions` + `/v1/completions` requests. Motivation: render time is currently invisible to operators. Deployments that call `/render` separately (e.g. llm-d with KV-aware routing) pay this stage twice, so a duration metric for the shared stage is needed to attribute frontend latency.

## Claims

- New metric `vllm:request_render_duration_seconds`: histogram with buckets from 0.1 ms through 10 s and bounded `model_name` / `request_type` labels (`chat`, `completion`), exposed on `/metrics`.
- Observed on successful renders through `OnlineRenderer.render_chat` / `render_completion` — the single boundary shared by `/render`, OpenAI serving, and Anthropic serving paths.
- Purely additive: +140/−0 lines; no change to request handling behavior or model outputs.

## Validation

- `ruff check` and `ruff format --check` on the changed files: passed.
- `.venv/bin/python -m pytest tests/renderers/test_metrics.py -v`: 3 passed (lazy registration, label separation + count/sum accumulation, bucket range).
- Import smoke test of `vllm.renderers.online_renderer`: passed.
- Full pre-commit suite (ruff, mypy, SPDX headers, test tethering, sign-off) passed on commit.
- Model evaluation: not applicable — the change adds observability only and does not alter outputs, accuracy, or sampling. No GPU is available in this environment for an end-to-end serving run; the added cost is two `perf_counter()` calls and one histogram observe per successful request on the CPU frontend path.

## Details

- `vllm/renderers/metrics.py` (new): histogram definition with lazy registration (`lru_cache`), following the pattern of `vllm/parser/metrics.py` — registers on the default prometheus registry, which `/metrics` serves via `get_prometheus_registry()` in both single-process and `PROMETHEUS_MULTIPROC_DIR` modes.
- `vllm/renderers/online_renderer.py`: `time.perf_counter()` at the top of `render_chat` / `render_completion`; the observation is recorded just before the successful return. Early error returns are not recorded (successful-request semantics).
- `tests/renderers/test_metrics.py` (new): unit tests for the metrics module.

### Why this is not a duplicate

- No open PR adds a render-stage duration metric (searched open PRs for `request_render_duration` and `render duration`; no matches).
- Closest relative: #50875 (open) instruments finer-grained multimodal preprocessing phases (`vllm:mm_*` metrics). This PR instead measures the whole render stage at the `OnlineRenderer` boundary — including chat templating and tokenization — and covers `/render` requests. The two are complementary.
- #44404 (detailed multimodal preprocessing timing stats) is a profiling-stats mechanism, not a Prometheus serving metric.

### Limitations

- `render_responses` is not instrumented; the port stays faithful to the original PR scope (chat + completion). A follow-up could add `request_type="responses"`.
- The metric name intentionally describes the full render stage: requests that reuse token IDs (disaggregated decode-side reuse via `kv_transfer_params`) skip tokenization but are still timed end-to-end.
