# [Bugfix] Add chat template fallback for OpenVLA

[Upstream PR](https://github.com/vllm-project/vllm/pull/64362) · state: closed · merged: True

## Original PR description

## Overview

`openvla/openvla-7b` (supported since #42654) cannot be served through `/v1/chat/completions`: its tokenizer ships no chat template, so every request fails with HTTP 400. This registers a chat template fallback for `model_type="openvla"`, following the existing fallback mechanism from #17805. The template applies OpenVLA's training prompt format, so a chat request can carry just the instruction.

## Claims

- `vllm serve openvla/openvla-7b` now accepts OpenAI chat requests with an image + instruction (previously HTTP 400 for every request).
- A plain instruction (e.g. `Pick up the red block.`) is rendered as OpenVLA's training prompt, `In: What action should the robot take to pick up the red block?\nOut: `. Already formatted `In: ...\nOut:` prompts pass through unchanged apart from the trailing space.
- The final prompt always ends with token 29871, the token `predict_action()` appends when it is missing, so the prompt IDs match the upstream OpenVLA inference path.
- The prompt produced by the chat endpoint is token-for-token identical to the offline `LLM.generate({"prompt": ..., "multi_modal_data": ...})` path used for the HF parity check in #42654, and so are the generated action tokens.

## Validation

Same image, `temperature=0`, `max_tokens=7`, on `d929755b7a` + this PR. The chat request sends only the raw instruction `Pick up the red block.`; the offline reference uses the model-card prompt `In: What action should the robot take to pick up the red block?\nOut: `:

| Path | Result | Prompt tokens | Action tokens |
|---|---|---|---|
| `/v1/chat/completions`, before | HTTP 400: *"As of transformers v4.44, default chat template is no longer allowed, so you must provide a chat template if the tokenizer does not define one."* | – | – |
| `/v1/chat/completions`, this PR | HTTP 200 | 276 | `[31870, 31871, 31891, 31896, 31880, 31880, 31872]` |
| Offline `LLM.generate` (reference) | – | 276 | `[31870, 31871, 31891, 31896, 31880, 31880, 31872]` |

`prompt_token_ids` (requested with `return_token_ids: true`) are identical between the chat and offline paths: `[BOS] + 256 × image token + instruction tokens`, ending in 29871. All action tokens fall in OpenVLA's action-token range (31744–31999).

Template rendering was also checked against the `predict_action()` input (model-card prompt + 29871) for raw, capitalised/punctuated, and pre-formatted instructions (with and without the trailing space), each as plain-text and image+text content: all token IDs match. `test_openvla_chat_template` covers these cases, and `python examples/generate/multimodal/vision_language_offline.py -m openvla` runs and generates 7 action tokens.

## Details

**Root cause:** the OpenVLA HF repo has no `chat_template`, and `openvla` had no entry in `_MODEL_TYPE_TO_CHAT_TEMPLATE_FALLBACK`. Passing `--chat-template` works around it, but the fallback registry exists so that supported models work out of the box.

**Template design:**
- The last user message is treated as the instruction. It is trimmed, its trailing `.?!` is stripped, and it is lowercased (as in OpenVLA's training transform) before being wrapped as `In: What action should the robot take to {instruction}?\nOut: `. If the text already starts with `In:`, it is used as is.
- The prompt always ends in `Out: `. The trailing space tokenizes to 29871, which `predict_action()` appends when missing; without it the prompt would end in `:` (29901).
- The template deliberately emits **no** image placeholder: `OpenVLAMultiModalProcessor` inserts the image tokens right after BOS (`PromptInsertion`), and #42654 found that a text placeholder breaks HF parity. We confirmed this: a variant that renders a literal `<PAD>` (the image token id) per image leaves a stray token in the prompt (277 vs 276 tokens) and produces entirely different actions (`[31881, 31744, 31905, ...]`).
- System and assistant turns are ignored, since OpenVLA's action-prediction prompt has neither.

**Scope:** registry entry + template, a template unit test, and an `openvla` entry in `examples/generate/multimodal/vision_language_offline.py` showing the prompt format. No model or processor changes. `setup.py` already packages `chat_templates/*.jinja`.

From Codex:

----

The proposed template emits BOS followed by user text verbatim. It never adds OpenVLA’s expected formatting. For example:

| User message | Proposed template produces |
|---|---|
| pick up the red block | <s>pick up the red block |
| In: What action should the robot take to pick up the red block?\nOut: | The correctly formatted prompt, prefixed by BOS |

OpenVLA’s training code constructs What action should the robot take to {instruction}?, and its prompt builder wraps that with In: …\nOut:. The [official model example](https://huggingface.co/openvla/openvla-7b#getting-started) uses the same structure. See also the training transform and prompt builder.

Two other details matter:

- Omitting an image placeholder is correct for the current vLLM processor: it inserts image tokens after BOS, matching upstream’s embedding placement.
- The trailing token matters. Upstream predict_action() ensures the prompt ends with token 29871 before generation. The proposed template provides no such guarantee; validation should compare final prompt IDs against that upstream path. Upstream implementation

The PR’s parity result uses an already formatted user message, so it supports that narrow usage. It does not establish that ordinary instruction messages are formatted correctly

----

It would also be nice to add an example script to show the expected prompt format.
