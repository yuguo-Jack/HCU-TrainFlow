# [Bugfix][ROCm] Force Triton MXFP4 for 96-row ASM scale tiles

[Upstream PR](https://github.com/vllm-project/vllm/pull/58139) · state: open · merged: False

## Original PR description

## Purpose

On ROCm gfx950, AITER ASM MXFP4 (`gemm_a4w4`) is selected when weight-scale tiles have `rows % 32 == 0` and `cols % 8 == 0`. Qwen3.8 TP1 GDN `in_proj_ba` uses **96×160** scales, which pass that layout check, but ASM is numerically wrong for **M ≤ 64** (error ratio ~0.83–0.92; ~22–24 µs broken ASM vs ~7.6–8.9 µs Triton).

This PR forces 96-row scales onto Triton `gemm_afp4wfp4`. Other legal tiles (e.g. 128×160) stay on ASM. TP2/TP4 BA (`N=48/24`) already fail the row-%-32 check and were Triton via #55213.

## Test Plan

- Unit: `tests/kernels/quantization/test_rocm_mxfp4.py::test_asm_fp4_scale_swizzle_supported_shape_rules`
  - `(96, 160) -> False` (Triton)
  - `(128, 160) -> True` (ASM unchanged)
- gfx950 TP1 Qwen3.8-27B MXFP4 serve: GDN `in_proj_ba` should log Triton, not ASM, at decode M≤64.

## Test Result

Dispatch unit cases added. Numerical mismatch for 96-row ASM at M=8/16/32/64 was measured on MI355X. Full e2e accuracy vs Triton path still to be attached from the TP1 patched serve.

I added and pushed `test_qwen38_tp1_ba_96_row_scale_avoids_broken_asm` in commit `2692092232`.

The test reproduces the numerical issue using the Qwen3.8 TP1 GDN `in_proj_ba` shape: N=96, K=5120, with weight scale `(96, 160)`. The guarded Triton path matches the dequantized MXFP4 reference. Direct `gemm_a4w4` on the same inputs produces non-finite output at M=8 and relative L2 errors of 0.80 at M=32 and 0.74 at M=64.

The inaccurate range I observed is M <= 64, rather than M >= 64. At M=128, the relative L2 error drops to 0.039.

Keeping ASM enabled only for larger M would require retaining both weight layouts. The ASM path pre-shuffles the weight and scale during model loading, whereas the Triton path uses the original weight and transposed scale. `use_asm_gemm` is currently selected once per layer, not per invocation. Since decode uses the failing small-M range, this PR keeps the 96-row layer entirely on Triton.

@amd-mghanimi  gsm8k doesn't show an improvement. 

There are two experiments that did surface the bug:
  
  1. AITER GEMM tuning validation (production op vs a dequantized reference): for the TP1 GDN in_proj_ba shape (N=96, K=5120, scale (96,160)), ASM output was zero or partly zero at M=8/16/32/64 (error ratio 0.83-0.92). Triton matched the reference and was ~3x faster (7.6-8.9 us vs 22-24 us).

  2. Instrumented the served model (guard removed, real weights and prompts, eager mode). I compared the in_proj_ba ASM output with the Triton path on the same input over 108k calls. At M=3..64 (decode) the relative L2 is 0.71-0.89 on average, and 52% of calls return at least one all-zero output row (at M=8, 40% of all rows are exactly zero). At M>64 (prefill) the relative L2 is 0.04-0.06 with no zero rows.

  So the kernel is wrong in real decode, but gsm8k is insensitive to it: the model seems to tolerate wrong GDN gate inputs on that many tokens. That is why accuracy doesn't move.
