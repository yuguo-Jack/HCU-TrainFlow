# [Bugfix][KV Connector] Retire in-flight output state on load-failure recompute

[Upstream PR](https://github.com/vllm-project/vllm/pull/59793) · state: open · merged: False

## Original PR description



## Overview

Fixes #45138. When KV-load-failure recompute truncates a request's `num_computed_tokens` at the first invalid block, the scheduler now also retires the request's in-flight output state: output placeholders are zeroed, drafted spec tokens are cleared, and outputs still in flight from the invalid KV are marked stale so they drain and drop as they return instead of landing as valid tokens.

## Claims

- `_update_requests_with_invalid_blocks` retires in-flight output state for every affected request, using the same `drop_stale_output` / `num_stale_output_tokens` idiom as `_handle_stopped_request`: in-flight outputs from invalid KV are dropped on return, placeholders restart at zero, and spec drafts are rebound to empty.
- Stale placeholders no longer leak into the scheduling arithmetic after recompute. That leak is what inflated `num_new_tokens` and stranded requests in the running queue in #45138.
- The reset is a no-op for requests with nothing in flight (sync scheduling, or async loads still waiting for remote KV), so non-failure paths are untouched.

## Validation

New regression test `test_sync_recompute_retires_inflight_output_state` builds the failure state directly: a running request with one outstanding placeholder share beyond the current step's, drafted spec tokens, and an invalid block reported mid-prompt. It asserts the truncated frontier, zeroed placeholders, exactly one stale share still outstanding with drop mode on (this step's share drains in lockstep inside `update_from_output`), and that the draft list is rebound rather than mutated.

## Details

Root cause: the recompute path rewinds `num_computed_tokens` but left the request's output-side state untouched. Under async scheduling a request can have placeholders and in-flight sampled outputs at the moment the failure surfaces; those outputs were sampled from KV that is now known-invalid, and the leftover placeholders kept counting into `num_new_tokens` projections, which is the stranding mechanism reported in #45138.

Why not the existing PRs:

- #45146 fixes the placeholder half of this on an older tree and has been inactive since June. It does not touch in-flight outputs or spec drafts.
- #49252 covers the `num_computed_tokens` truncation for sync + async loads and has been stalled since August; its substance is largely absorbed by the current `_update_requests_with_invalid_blocks` rewrite, and it also leaves output-side state alone.
- This PR supersedes my own earlier #45430 (closed), redone against current main using the stale-output machinery that landed since (`num_in_flight_tokens` / `num_stale_output_tokens` / `drop_stale_output`), which keeps the fix to nine lines in the scheduler by reusing the drain loop in `update_from_output`.

- he-yufeng · comment · 2026-10-05T14:23:16Z · [source](https://github.com/vllm-project/vllm/pull/59793#discussion_r4185067023)

File: `vllm/v1/core/sched/scheduler.py` · line 3302

A miss, thanks for catching it.

Without the rewind the restart frontier can stay above the materialized frontier: the shared-block restore sets `num_computed_tokens` back to prev computed minus this step's scheduled tokens, which still covers the placeholder span whenever the request's in-flight placeholders outnumber what this step scheduled. The truncation branch can land in the tail span too when the first invalid block sits among the last blocks. In both cases those placeholder positions stay marked computed while their output is drained as stale, so they are never re-sampled and the sequence silently loses them.

Fixed in f8536b5dc5: capture the materialized frontier before any truncation mutates `num_computed_tokens`, clamp to it before zeroing the span (same idiom as `_handle_stopped_request`), and charge the rewound tokens to `total_affected_tokens`. Added `test_sync_recompute_rewinds_frontier_below_placeholder_span` to pin the clamp; it drives the truncation path with an oversized placeholder span since no in-tree fixture reaches the shared-block restore, which the docstring calls out. All five tests in the file pass locally, and the new one fails without the fix.
