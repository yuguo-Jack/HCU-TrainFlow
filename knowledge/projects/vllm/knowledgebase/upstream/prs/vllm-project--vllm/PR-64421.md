# [Feature][Elastic EP] Coordinate native local-range resizing

[Upstream PR](https://github.com/vllm-project/vllm/pull/64421) · state: open · merged: False

## Original PR description



## Overview

Coordinate native external Elastic EP resizing when one client owns several
local engines, retaining its fixed local routing and abort identities.

**Draft; blocked by [#62973](https://github.com/vllm-project/vllm/pull/62973).**
This upstreams [the fork PR](https://github.com/julienmancuso/vllm/pull/1) without
changing its tested head. Since the parent branch exists only in the fork, this
PR targets `main` and initially includes the parent's bootstrap changes. The
[resize-only diff](https://github.com/julienmancuso/vllm/compare/aafffff180bc37b7b0743c6eee547124cb0567a8...9f4166a6dba1d4911ccdbd40fb3cb13e30af6a7e)
is **8 files, +504/-108**. Keep #62973 focused on bootstrap; merge it first.

Related: [#42515](https://github.com/vllm-project/vllm/issues/42515) and
[DEP #13121](https://github.com/ai-dynamo/dynamo/issues/13121).

## Claims

- One resize request per existing client prepares, drains, commits and waits for
  every owned engine, rather than only its first engine.
- Growth appends whole clients; shrink retires a whole-client suffix. Reject a
  target that splits a local range before engines begin reconfiguration.
- Planned retirement waits for every local engine without killing siblings
  early. Unexpected exits remain failures; the retired API remains observable
  but refuses inference.
- Surviving clients update global world metadata without adopting remote engines
  or changing their local routing identities.

## Details

Reuse native all-engine utility calls, existing stores and notifications, the
local-range client and its process manager. No additional process owner or
steady-state GPU synchronization is introduced. A pre-prepare owner barrier
propagates invalid local ranges before workers reconfigure; completion waits for
all local acknowledgments. The documented Pod-stop gate requires every old
client's shrink request to succeed, including the retiring client. Serving
readiness remains a separate check.

Operation correlation and bounded submission remain separate in
[#62082](https://github.com/vllm-project/vllm/pull/62082). Composing that PR with
this client requires forwarding `operation_id` unchanged through the native DPLB
delegation and independently qualifying the combination. Those API changes are
not copied here, and the standalone published heads are not claimed to compose
safely without that adaptation. A lost HTTP response alone is not deletion proof.

Duplicate-work checks found no existing packed-client resize PR. #62973 supplies
startup and local routing, #62082 supplies operation correlation, and
[#64155](https://github.com/vllm-project/vllm/pull/64155) supplies parked/checkpointed
joiners, not this multi-engine client's resize lifecycle. Fault-driven removal
and arbitrary selected retirement are also outside this feature's scope.

This is the unchanged, human-signed fork head. A fresh `main` synchronization and
validation will be needed before upstream CI/merge; a non-mutating merge probe
against `66875d3127534183b5ea723964fc7ec388e89722` succeeded. No branch history was
rewritten for publication.
