# [ROCm][Bugfix] Pin AITER back to v0.1.24.post1 for DSv4.1 mono decode numerics

[Upstream PR](https://github.com/vllm-project/vllm/pull/61559) · state: closed · merged: True

## Original PR description

## Overview

Pin the ROCm base image back to AITER `v0.1.24.post1`. With AITER `v0.1.25` (#61230), the gfx950 MXFP4 fused-MoE reference selects different kernels and repeatedly fails `tests/models/test_dsv41_mono_numerics.py::test_mono_decode_layer_matches_vllm[4]`. Because that step's `source_file_dependencies` do not include the ROCm base image, the regression is invisible on `main` and only surfaces as a permanently red step on every PR that touches `vllm/models/deepseek_v41/amd/`.

## Claims

- Restores the `AMD: (MI355) DeepSeek-V4.1 Mono Decode Numerics` step to green.
- Makes an AITER / ROCm base-image change re-run that step, so the next bump cannot land without exercising this test.

## Details

**Failure mechanism.** The mono path runs vLLM's own FlyDSL kernels; the reference uses `DeepseekV4MoE` with `moe_backend="aiter"`. In build 94372, the TP4 shape (model_dim=5120, padded inter_dim=640, token bucket=8) uses the heuristic `flydsl_moe1_afp8_wfp4_bf16_t32x128x256_w2_gui` / `flydsl_moe2_afp8_wfp4_bf16_t32x128x128_atomic_bnt2` pair. In build 94644, AITER selects `..._w2_gui_fp8` / `flydsl_moe2_layout_afp8_wfp4_bf16_t32x256x128_reduce_sbm32`, changing intermediate quantization and reduction. This agrees with TP2 passing and TP4 failing. It does not prove which implementation is more accurate. The failed assertion combines cosine similarity and relative L2 error without printing either value, so exceeding the 1.5% relative threshold specifically is not established. The duplicate-tuning warning also appears in the old passing log and is not evidence of a newly introduced defect.

The regression window is narrow. Between the last green run and the first red run, the only change to the branch was merging `main`; within `main` commits `c19c263ac8` (2026-10-13 20:06 UTC, proven green for this exact step by [94594](https://buildkite.com/vllm/ci/builds/94594)) and `4e0681ed56` (2026-10-14 00:24 UTC, the merge point), `7a9d3db896` (#61230) is the only commit touching anything this step executes. The other MoE-facing commit in that window, `ad8d39cbab`, wires padding into `fused_topk_bias`'s **non**-AITER branch, which this test does not take; `e90158d912` touches the batched Triton MoE, which `moe_backend="aiter"` does not use.

**Why the step never caught it.** The step's dependencies are `vllm/models/deepseek_v41/amd/` and the two DSv4.1 mono test files. An AITER bump touches none of them, so the step is created but stays `blocked` on every `main` build. That is why the regression sat unnoticed and then blocked unrelated PRs (e.g. #57797) that happen to touch that directory.

**Tradeoff.** This reverts an intentional periodic bump, so AITER `v0.1.25` is not re-landed until the DSv4.1 mono numerics are understood — either the AITER kernels regressed accuracy on gfx950, or the new numerics are acceptable and the test's contract needs revisiting. ROCm/aiter has no newer tag than `v0.1.25`, so there is nothing to bump forward to. `docker/Dockerfile.rock_base` is pinned too, to keep the two base images on the same AITER.

**Not covered.** No full-model accuracy evaluation and no MI355 run outside CI. Whether `v0.1.25`'s numerics are wrong or merely different is not established by this PR.

**Duplication.** Checked: no open PR reverts the AITER pin or references #61230.
