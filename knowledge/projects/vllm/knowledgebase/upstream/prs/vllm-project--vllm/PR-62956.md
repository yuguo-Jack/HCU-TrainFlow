# [Perf][glm5next] Add SM121 TP=2 skinny-GEMM plans for GLM-5.3-Flash

[Upstream PR](https://github.com/vllm-project/vllm/pull/62956) · state: closed · merged: True

## Original PR description

## Overview

GLM-5.3-Flash decode TPOT **-15% at concurrency 1 on 2x DGX Spark (SM121, TP=2)** by running the BF16 decode GEMMs on the CuTe DSL skinny GEMM instead of cuBLAS. On `nvidia/GLM-5.3-Flash-NVFP4` the attention projections (KDA and MLA), shared experts and LM head stay BF16 and take roughly 46 of a 68 ms decode step on cuBLAS gemv. `glm5next` has no low-latency GEMM module yet, so this adds one modelled on `qwen4_exp/nvidia/low_latency_gemm.py` (#59753, #59632, #61437) with measured SM121 skinny-GEMM plans for the TP=2 local shapes, installed from `Glm5NextForCausalLM` and `Glm5NextMTP`. Supersedes #62949.

## Claims

- 7 local `(N, K)` shapes at M = 1/2/4 (20 entries), routed only on capability `(12, 1)`; other GPUs, dtypes, token counts and shapes keep the standard linear path (cuBLAS).
- Kernel: skinny GEMM is 1.35x to 1.73x faster than cuBLAS gemv at M=1 (238-283 GB/s vs 162-176 GB/s), 1.04x to 1.36x at M=2/4.
- End to end, no speculation, concurrency 1: TPOT 64.0 -> 54.1 ms (-15%), 15.3 -> 18.0 tok/s. With MTP k=3 the decode step is one verify pass at M=4 plus three draft passes at M=1: ITL -3.6%, TPOT -2.7%, 26.7 -> 27.8 tok/s.
- GSM8K (n=100): 93 with cuBLAS, 94 with skinny GEMM.

## Validation

These are cold-L2 numbers, which is the serving case: decode reads each weight once per step and 45 layers do not fit the 24 MB L2. Weighted by how often each shape runs in a decode step, the entries save about 13 ms per step at M=1 and 3 ms at M=2 or M=4 in the probe; the server gains 10 ms at M=1 because the GEMMs interleave with MoE and attention. MLA o_proj at M=1 is not included: cuBLAS already streams this shape at 231 GB/s (162-176 GB/s on the other shapes), so the best skinny config from the sweep gained only 3% in the module path, under the 5% bar. M=8/16 are within 2% of cuBLAS and are not listed.

End to end, cuBLAS (current main) vs skinny GEMM (this PR): `nvidia/GLM-5.3-Flash-NVFP4` TP=2 on two Sparks, FP8 KV, SPEED-Bench 2K in / 1K out, 8 requests at concurrency 1, greedy (`--temperature 0`), two interleaved runs per arm (each cell lists run 1 / run 2), nightly 8e2beaa3bf:

| | TPOT p50 (ms) | ITL p50 (ms) | Output tok/s | GSM8K (n=100) |
|---|---:|---:|---:|---:|
| cuBLAS (main) | 64.17 / 63.83 | 63.94 / 63.68 | 15.27 / 15.33 | 93 |
| skinny GEMM (this PR) | 54.14 / 54.10 | 54.03 / 53.96 | 18.02 / 18.03 | 94 |
| change (mean of the two runs) | **-15.4%** | -15.4% | +17.8% | +1 |

With MTP k=3 (`--speculative-config '{"method":"mtp","num_speculative_tokens":3}'`, `--gpu-memory-utilization 0.875 --max-model-len 16384 --max-num-seqs 8`, same nightly and sampling):

| | TPOT p50 (ms) | ITL p50 (ms) | Output tok/s | Acceptance length |
|---|---:|---:|---:|---:|
| cuBLAS (main) | 36.05 / 36.11 | 102.72 / 103.27 | 26.79 / 26.66 | 2.87 / 2.87 |
| skinny GEMM (this PR) | 35.08 / 35.16 | 99.18 / 99.41 | 27.51 / 28.02 | 2.85 / 2.90 |
| change (mean of the two runs) | -2.7% | **-3.6%** | +3.9% | +0.2% |

With MTP the ITL is the decode step (one verify pass at M=4 plus three draft passes at M=1); TPOT and tok/s divide it by the tokens accepted per step. Under greedy decoding the acceptance length stays within 2.85-2.90 across the four runs, so the step gain carries over: TPOT -2.7%, tok/s +3.9%. An earlier 4-request run at model-default sampling gave -12% without speculation (the number in the commit message); with MTP its acceptance length swung 3% between repeats, which hid the step gain.

An nsys census of the skinny GEMM arm shows every listed shape on `CuteSkinnyGemm` in the server (45% of GPU time without speculation, 39.5% with MTP); what is left on cuBLAS is KDA `f_b`/`g_b` (4096, 128) (#57617), the fp32-output router gate (288, 4096) and MLA o_proj at M=1.

Tests: `pytest tests/kernels/test_bf16_skinny_gemm.py -k glm5next`, 26 passed on GB10 (table validity, capability routing, hook installation, 20 selected shapes with cosine > 0.999 against `F.linear`). The selected-shape test skips off capability (12, 1), which CI does not have.

## Details

- Plans come from a CUDA-graph sweep over block_size, outputs_per_block, k_unroll, vector_width and static_k with the weight rotated out of L2, keeping entries that beat cuBLAS by more than 5%. `(2048, 4096)` serves both the shared-expert gate/up and the MLA fused q_a/kv_a projection.
- The replacement method follows the quant method the layer carries: a quant config that excludes `lm_head` gives `ParallelLMHead` an `UnquantizedLinearMethod` rather than an `UnquantizedEmbeddingMethod`, and the head stayed on cuBLAS until this was handled.
- Not covered: TP=1 (the model does not fit one Spark), KDA `f_b`/`g_b` `(4096, 128)` (#57617), MTP `eh_proj` (a plain `nn.Linear`), and M=3, which uses cuBLAS.
- AI assistance (Claude Code) was used for the sweep scripts, the module and the tests; all code and measurements were reviewed and run by the author.

- LopezCastroRoberto · COMMENTED · 2026-10-29T12:21:34Z · [source](https://github.com/vllm-project/vllm/pull/62956#pullrequestreview-5697595837)

Thanks for the PR. I tried a different structure on [LopezCastroRoberto:glm5next-skinny-gemm-cleanup](https://github.com/vllm-project/vllm/compare/main...LopezCastroRoberto:vllm:glm5next-skinny-gemm-cleanup?expand=1). It drops `layers/low_latency_gemm.py` and the `GLM5Next` installer. Instead, as in `GateLinear`, each unquantized layer checks its own `(N, K)` against a shape-keyed plan table. This should keep your SM121 numbers unchanged, but please double-check and cherry-pick if looks good to you.

Matching layers then go through one custom op inside the CUDA unquantized GEMM path. GLM code stays untouched, `lm_head` is covered, and `--linear-backend` is respected. Because plans are keyed by weight shape, on SM121 any layer with a listed shape uses them and benefits from it, not just GLM’s. 

This refactor also lets Qwen4Exp’s copied op and installer (`qwen4_exp/nvidia/low_latency_gemm.py`) become table entries, and the plain skinny GEMM projections in GLM-5.2 (`deepseek_v32/nvidia/glm52_low_latency_gemm.py`) and Kimi-K3 (`kimi_k3/nvidia/low_latency_gemm.py`) move onto the same path in follow-up PRs.

`_warmup_skinny_gemm` mirrors `_warmup_ll_bf16_router_gemm`, but queues configs through `request_warmup_configs` for `cutedsl_warmup()` to compile, because `ShapeDynamicSkinnyGemm` is still on the deprecated CuTe DSL provider registry. Compiling directly with `.warmup(shapes=..., m_values=...)` like `ll_bf16` needs its `VllmJitKernel` migration ([vllm-project/vllm#49349](https://github.com/vllm-project/vllm/issues/49349)), which also touches Kimi-K3, GLM-5.2 and Qwen4Exp, so it is left for a follow-up too.
