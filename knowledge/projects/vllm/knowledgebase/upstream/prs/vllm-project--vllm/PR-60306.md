# [Bugfix][Core] Count unscheduled running requests toward max_loras

[Upstream PR](https://github.com/vllm-project/vllm/pull/60306) · state: open · merged: False

## Original PR description

## Overview

Count the LoRA adapters of all running requests, not only those scheduled in the current step, when deciding whether a waiting request fits within `max_loras`. Without this, a skipped running request lets a request with another adapter in, and the next batch holds more than `max_loras` adapters and trips an assertion in `Scheduler.schedule()`.

Fixes #60301

## Claims

- With `--max-loras N`, a waiting request whose adapter would exceed `N` once a currently skipped running request resumes is no longer admitted early. This happens with pipeline parallelism and also on a single GPU, e.g. when a multimodal request is skipped because the step's encoder budget is used up.
- Fixes `AssertionError` in `schedule()` (`assert len(scheduled_loras) <= self.lora_config.max_loras`), which escapes the engine core busy loop and kills the engine.
- No behavior change when every running request is scheduled in the step.
- One-line source change (the iterable the set is built from) plus its comment; `create_scheduler` in the scheduler test helpers gains a `lora_config` argument.

## Details

Root cause: `Scheduler.schedule()` seeds `scheduled_loras` from `scheduled_running_reqs` (`scheduler.py:869-877` on `main`) and the waiting loop admits a request only if its adapter fits in that set (`:918-929`). A running request is skipped in a step when it has nothing to schedule yet: with PP>1 once its prompt is fully scheduled but the output is pending (the `num_new_tokens == 0` case documented in the running loop), and through the other `continue` paths of the running loop (`next_decode_eligible_step` cadence for V2 + PP + async, DP prefill deferral, EC connector and encoder budget waits). Its adapter is then missing from the set, a request with another adapter is admitted, and once the skipped request is scheduled again both end up in one batch. The running loop does not consult `max_loras`, so the existing `assert` is the first thing to notice.

Fix: seed the set from `self.running`. Every request enters `self.running` through the waiting-loop admission check, so the number of distinct adapters among running requests stays at most `max_loras` and the assert holds. This is how the V0 scheduler counted (`curr_loras` was built from all running sequence groups), and what `LoRAConfig.max_loras` ("Max number of LoRAs in a single batch") requires. The variable keeps its name since it is still the set the waiting loop extends as it admits requests.

Scope and limits: the check is more conservative only when a running request that holds an adapter is skipped in the step; that request's adapter slot is kept until it finishes. Two tests cover it: the pipeline-parallel case and, without PP, a running request skipped because earlier requests used up the step's encoder compute budget (suggested in review). Both fail on `main` and pass with this change. Open priority-preemption PRs (#40087, #45558, #45561, #54530) read and update `scheduled_loras` but do not change how it is seeded.

Not a duplicate: I searched issues and PRs on `vllm-project/vllm` for `max_loras`, `scheduled_loras`, `LoRA scheduler`, `LoRA pipeline`, `LoRA async`, `max_loras assertion` and `no free lora slots`, and open PRs for `scheduler.py lora` and `LoRA schedule running requests`. Nothing reports or fixes this. Closest hits: #15422 (merged, introduced the current seeding), #14495 (closed feature request about "No free lora slots" for over-full batches, predates #15422), #17003 (usage question), #10840 (closed, a V0 LoRA scheduling policy), and the open priority-preemption PRs above.

This PR was co-authored with Claude.

End-to-end validation in review: on 2×H20 (Qwen3-0.6B, 3 LoRAs, PP=2, `max_loras=1`) `main` dies with `EngineDeadError` from this assert in all four MRV2/V1 × sync/async combinations and this PR completes with outputs matching per-request runs; the single-GPU encoder-budget case (Qwen3.5-4B, `max_loras=2`) reproduces and is fixed as well.

```python
def test_max_loras_counts_running_request_skipped_for_encoder_budget():
    """No PP: a running request skipped because earlier requests used up the
    step's encoder compute budget still holds its LoRA slot."""
    scheduler = create_scheduler(lora_config=LoRAConfig(max_loras=2))
    scheduler.max_num_encoder_input_tokens = 100
    scheduler.encoder_cache_manager = EncoderCacheManager(cache_size=1000)
    # a: two 100-token images, one per step; b: image at 50, after a's.
    req_a, req_b = create_requests(
        num_requests=2,
        num_tokens=300,
        mm_positions=[
            [
                PlaceholderRange(offset=0, length=100),
                PlaceholderRange(offset=150, length=100),
            ],
            [PlaceholderRange(offset=50, length=100)],
        ],
        req_ids=["a", "b"],
    )
    (req_c,) = create_requests(num_requests=1, num_tokens=10, req_ids=["c"])
    req_a.lora_request = LoRARequest("lora-a", 1, "/path/a")
    req_b.lora_request = LoRARequest("lora-b", 2, "/path/b")
    req_c.lora_request = LoRARequest("lora-c", 3, "/path/c")

    scheduler.add_request(req_a)
    scheduler.add_request(req_b)
    output = scheduler.schedule()
    assert output.num_scheduled_tokens == {"a": 150, "b": 50}
    scheduler.update_from_output(
        output,
        ModelRunnerOutput(
            req_ids=["a", "b"],
            req_id_to_index={"a": 0, "b": 1},
            sampled_token_ids=[[], []],
            logprobs=None,
            prompt_logprobs_dict={},
            pooler_output=[],
        ),
    )

    # a's second image uses the whole encoder budget, so b is skipped; c
    # (a third adapter) must still wait.
    scheduler.add_request(req_c)
    output = scheduler.schedule()
    assert output.num_scheduled_tokens == {"a": 150}
    assert req_c.status == RequestStatus.WAITING
```
